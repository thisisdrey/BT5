### Title
Per-connection stream throttle counters are reset by connection churn, allowing an unstaked attacker to evade `max_streams_per_throttling_interval` - (File: `streamer/src/nonblocking/stream_throttle.rs`)

### Summary
`throttle_stream` enforces `max_streams_per_throttling_interval` using a `ConnectionStreamCounter` that is scoped to a single QUIC connection, not to the source IP/pubkey across time. Because a brand-new `ConnectionStreamCounter` is allocated every time a connection is (re)admitted to the connection table, an attacker can dodge an imminent throttle `sleep` by simply closing the connection and opening a new one, which starts the stream counter back at zero.

### Finding Description
`throttle_stream` reads `stream_counter.stream_count` and, once it reaches `max_streams_per_throttling_interval`, sleeps the calling task for the remainder of `STREAM_THROTTLING_INTERVAL` before allowing more streams to be processed: [1](#0-0) 

This `stream_counter: Arc<ConnectionStreamCounter>` is stored in `SwQosConnectionContext` and is created fresh for each new connection admitted into the connection table via the `|| Arc::new(ConnectionStreamCounter::new())` closure inside `cache_new_connection`: [2](#0-1) 

`on_new_stream` invokes `throttle_stream` using this per-connection counter each time a new QUIC stream is opened on that connection: [3](#0-2) 

Because the counter/last-throttling-instant state lives entirely inside the `ConnectionStreamCounter` tied to one `Connection` object, closing that connection and establishing a new one (even from the same IP/pubkey) produces a brand-new counter starting at zero. An attacker who has just hit the throttle threshold can therefore reset the interval by dropping the connection rather than waiting out `sleep(throttle_duration).await`, and reopen a fresh connection to immediately resume sending streams at full rate.

Unlike the staked path — which additionally consults the global `StakedStreamLoadEMA` (an aggregate load estimator independent of any single connection) — the unstaked cap (`max_unstaked_load_in_throttling_window`) is a pure per-connection quota with no cross-connection or per-IP persisted state, so it is the primary path affected by this churn technique.

### Impact Explanation
This allows an unstaked, unprivileged remote attacker to push more streams into `sigverify`/packet-batch ingestion than `max_streams_per_throttling_interval` is intended to permit per 100ms window, by cycling through new connections rather than idling during the throttle sleep. This falls under the "QoS evasion" bounty category since the throttle mechanism is the QoS boundary meant to bound unstaked traffic ingestion.

### Likelihood Explanation
The practical benefit is bounded by connection-admission controls that already exist: `max_connections_per_unstaked_peer` and `max_unstaked_connections` cap how many connections/IPs can be active, and `prune_unstaked_connection_table` evicts oldest connections at 90% capacity [4](#0-3) . Each churn cycle also costs a full QUIC handshake (crypto/RTT), which is significantly more expensive than the ~100ms throttle sleep being evaded, so the net throughput gain per unit wall-clock time is limited by handshake cost rather than being unbounded. This makes the finding a real but low-severity evasion of the specific per-connection throttle window rather than an unbounded QoS bypass — the outer connection-admission and pruning limits still cap total attacker throughput.

### Recommendation
Persist stream-throttling state (stream count / last-throttling-instant) keyed by `ConnectionTableKey` (IP + pubkey) rather than by the ephemeral `Connection`/`ConnectionStreamCounter`, so that closing and reopening a connection from the same source does not reset the throttle window. Alternatively, retain and reuse `ConnectionStreamCounter` state across reconnects from the same key for a grace period equal to `STREAM_THROTTLING_INTERVAL`.

### Proof of Concept
Integration test plan (using `streamer` test harness / `solana-streamer-transport-benchmarks` style QUIC client):
1. Configure a test QUIC server via `SwQos` with `max_unstaked_connections` and low `MAX_UNSTAKED_TPS`, forcing `max_streams_per_throttling_interval` (unstaked) to a small known number (e.g., 2).
2. Client A opens a connection, opens `max_streams_per_throttling_interval` uni-streams (each sends a minimal packet), hits the throttle threshold on the next stream.
3. Instead of waiting on the throttle sleep, close the connection immediately and open a brand new connection (same IP).
4. Repeat step 2–3 in a tight loop for one wall-clock `STREAM_THROTTLING_INTERVAL` window.
5. Assert that the number of packets delivered to `packet_batch_sender` within that single 100ms window exceeds `max_streams_per_throttling_interval`, i.e., the per-window unstaked stream cap was evaded via churn — the expected (fixed-behavior) assertion is that this count stays bounded to `max_streams_per_throttling_interval` regardless of connection churn.

pub(crate) async fn throttle_stream(
    stats: &StreamerStats,
    peer_type: ConnectionPeerType,
    remote_addr: std::net::SocketAddr,
    stream_counter: &Arc<ConnectionStreamCounter>,
    max_streams_per_throttling_interval: u64,
) {
    let throttle_interval_start = stream_counter.reset_throttling_params_if_needed();
    let streams_read_in_throttle_interval = stream_counter.stream_count.load(Ordering::Relaxed);
    if streams_read_in_throttle_interval >= max_streams_per_throttling_interval {
        // The peer is sending faster than we're willing to read. Sleep for what's
        // left of this read interval so the peer backs off.
        let throttle_duration =
            STREAM_THROTTLING_INTERVAL.saturating_sub(throttle_interval_start.elapsed());

        if !throttle_duration.is_zero() {
            debug!(
                "Throttling stream from {remote_addr:?}, peer type: {peer_type:?}, \
                 max_streams_per_interval: {max_streams_per_throttling_interval}, \
                 read_interval_streams: {streams_read_in_throttle_interval} throttle_duration: \
                 {throttle_duration:?}"
            );
            stats.throttled_streams.fetch_add(1, Ordering::Relaxed);
            match peer_type {
                ConnectionPeerType::Unstaked => {
                    stats
                        .throttled_unstaked_streams
                        .fetch_add(1, Ordering::Relaxed);
                }
                ConnectionPeerType::Staked(_) => {
                    stats
                        .throttled_staked_streams
                        .fetch_add(1, Ordering::Relaxed);
                }
            }
            sleep(throttle_duration).await;
        }
    }

    fn prune_unstaked_connection_table(
        &self,
        unstaked_connection_table: &mut ConnectionTable<ConnectionStreamCounter>,
        max_unstaked_connections: usize,
        stats: Arc<StreamerStats>,
    ) {
        if unstaked_connection_table.total_size >= max_unstaked_connections {
            // Prune the connection table down to 90% capacity
            const PRUNE_TABLE_RATIO: f64 = 0.90;
            let max_connections = (PRUNE_TABLE_RATIO * (max_unstaked_connections as f64)) as usize;
            let num_pruned = unstaked_connection_table.prune_oldest(max_connections);
            stats
                .num_evictions_unstaked
                .fetch_add(num_pruned, Ordering::Relaxed);
        }
    }

    fn on_new_stream(&self, context: &SwQosConnectionContext) -> impl Future<Output = ()> + Send {
        async move {
            let peer_type = context.peer_type();
            let remote_addr = context.remote_address;
