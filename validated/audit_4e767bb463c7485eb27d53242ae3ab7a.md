### Title
`disabledApiList` access-restriction bypass via JSON-RPC alternate path into `Wallet`/`TronJsonRpcImpl` - ([File: framework/src/main/java/org/tron/core/services/jsonrpc/FullNodeJsonRpcHttpService.java])

### Summary
The CVE-2020-10254 bug class is: an access restriction enforced on one code path (direct file download) is not enforced on a functionally equivalent alternate path (image preview), letting an anonymous client reach protected data anyway. In java-tron, the operator-configured `disabledApiList` restriction is enforced independently on the HTTP `/wallet/*` path and on the gRPC path, but there is no corresponding enforcement point in the JSON-RPC HTTP service, even though JSON-RPC methods invoke the same underlying `Wallet` operations.

### Finding Description
`HttpApiAccessFilter` blocks disabled APIs for the `/wallet/*` HTTP surface by checking `endpoint.split("/")[2]` against `CommonParameter.getInstance().getDisabledApiList()`: [1](#0-0) 

`RpcApiAccessInterceptor` independently blocks the same disabled APIs on the gRPC surface by matching `endpoint.split("/")[1]`: [2](#0-1) 

Both interceptors are wired only into their respective HTTP servlet context / gRPC server, e.g. `FullNodeHttpApiService.addFilter` registers `httpApiAccessFilter` on `/wallet/*` and related paths: [3](#0-2) 

However, a search of the JSON-RPC implementation package (`org.tron.core.services.jsonrpc`, including `TronJsonRpcImpl.java`, `JsonRpcServlet.java`, and `FullNodeJsonRpcHttpService.java`) shows no reference to `disabledApiList`/`isDisabled` anywhere in that code path. JSON-RPC methods such as `getABIOfSmartContract` call directly into the same `Wallet` methods (e.g. `wallet.getContractInfo(...)`) that the HTTP `GetContractInfoServlet` and gRPC service also call: [4](#0-3) [5](#0-4) 

Because the JSON-RPC service is registered as an entirely separate Jetty context/service (`FullNodeJsonRpcHttpService`) rather than through the `/wallet/*` context that carries `httpApiAccessFilter`, an operator who disables a sensitive or resource-heavy API via `disabledApiList` (intending to block it on both the wallet HTTP and gRPC surfaces) does not actually block equivalent functionality reachable through JSON-RPC. This mirrors the ownCloud bug class exactly: a security/access-control gate exists on the "front door" (`/wallet/...`, gRPC) but is absent on an alternate, functionally-identical "side door" (JSON-RPC), which an anonymous client can freely use.

### Impact Explanation
`disabledApiList` is the operator's only mechanism to shut off specific Wallet APIs at runtime (e.g., for security incidents, abuse mitigation, or to stop a resource-exhausting query from being served). Because JSON-RPC bypasses this control entirely, an unauthenticated remote client can continue to invoke the disabled functionality (contract/account/data queries and any state-reading or gas-consuming operations exposed via JSON-RPC) even after the operator has explicitly disabled it — effectively restoring "an API the node can no longer serve" from the operator's perspective, and potentially enabling continued resource-exhaustion/DoS abuse the operator was trying to stop by disabling the API on the wallet/gRPC surfaces.

### Likelihood Explanation
High likelihood of reachability: any anonymous client with network access to the node's JSON-RPC port can immediately test this by calling the JSON-RPC equivalent of a disabled `/wallet/...` endpoint (e.g. `eth_getCode`/`getABIOfSmartContract` mapping to `wallet.getContractInfo`) — no signature, permission, or special account state is required. No code change or race condition needed; it's a structural gap in the access-control wiring.

### Recommendation
Add a JSON-RPC-level check equivalent to `HttpApiAccessFilter`/`RpcApiAccessInterceptor` (e.g., a servlet filter or JSON-RPC method-dispatch guard in `JsonRpcServlet`/`FullNodeJsonRpcHttpService`) that consults `CommonParameter.getInstance().getDisabledApiList()` before dispatching to `TronJsonRpcImpl`, mapping JSON-RPC method names to the same disabled-API identifiers used for the HTTP/gRPC surfaces.

### Proof of Concept
1. Node operator sets `node.jsonrpc` disabled list intention via `disabledApiList: ["getcontractinfo"]` (or any Wallet-backed API) in config, confirming via HTTP that `/wallet/getcontractinfo` now returns `{"Error":"this API is unavailable due to config"}`.
2. Send the equivalent JSON-RPC request to the node's JSON-RPC port, e.g. `eth_getCode` (which internally calls `wallet.getContractInfo`) for the same contract address.
3. Observe that the JSON-RPC call succeeds and returns the contract data, demonstrating the operator's disable directive was bypassed via the alternate JSON-RPC path.

  private boolean isDisabled(String endpoint) {
    boolean disabled = false;

    try {
      endpoint = URI.create(endpoint).normalize().toString();
      List<String> disabledApiList = CommonParameter.getInstance().getDisabledApiList();
      if (!disabledApiList.isEmpty()) {
        disabled = disabledApiList.contains(endpoint.split("/")[2].toLowerCase(Locale.ROOT));
      }
    } catch (Exception e) {
      logger.warn("check isDisabled except, endpoint={}, {}", endpoint, e.getMessage());
    }

    return disabled;
  }
