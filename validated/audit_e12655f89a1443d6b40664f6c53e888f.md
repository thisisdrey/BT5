Confirmed: only `ExchangeTransactionContract` has an `expected` field for slippage protection; `ExchangeInjectContract` and `ExchangeWithdrawContract` have no such field.

### Title
Lack of slippage protection in `ExchangeInjectActuator` and `ExchangeWithdrawActuator` enables front-run losses in TRON's Bancor-style exchange - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
Java-tron's on-chain Bancor-formula exchange supports three operations on a token pair pool: inject (add liquidity), withdraw (remove liquidity), and transaction (swap). Only the swap contract, `ExchangeTransactionContract`, carries an `expected` field used as a minimum-output slippage guard [1](#0-0) , enforced in `ExchangeTransactionActuator.doValidate()` via `anotherTokenQuant < tokenExpected` check [2](#0-1) . The `ExchangeInjectContract` and `ExchangeWithdrawContract` messages have no equivalent field [3](#0-2) , so callers cannot bound the counter-token amount they will send (inject) or receive (withdraw).

### Finding Description
Both `ExchangeInjectActuator` and `ExchangeWithdrawActuator` compute `anotherTokenQuant` at execution time strictly from the exchange pool's current `firstTokenBalance`/`secondTokenBalance` ratio [4](#0-3) [5](#0-4) . This pool ratio is state that any account can move by broadcasting an `ExchangeTransactionContract` swap against the same `exchange_id` before the pending inject/withdraw transaction is packed into a block. Because neither `ExchangeInjectContract` nor `ExchangeWithdrawContract` accepts a caller-supplied minimum/maximum bound (`expected`) on the resulting `anotherTokenQuant`, the creator has no way to reject an execution that occurred at an unfavorable, manipulated ratio — this is the same bug class as the report's "lack of slippage and deadline" for `withdraw()`/`deposit()`, where a value computed from mutable external state (there, an oracle price; here, the live AMM pool ratio) can move between transaction submission and execution.

### Impact Explanation
An attacker who observes a pending `ExchangeWithdrawContract` or `ExchangeInjectContract` in the mempool (only the pool's `creatorAddress` may call `ExchangeWithdraw`/`ExchangeInject`, per the `is not creator` check [6](#0-5) ) can sandwich it with `ExchangeTransactionContract` swaps to shift the first/second token ratio immediately before it executes. For a withdraw, this forces the creator to redeem a worse mix of the two tokens than intended (economic loss on withdrawal, i.e., value extracted from the LP). For an inject, the creator can be forced to commit a larger amount of the paired token than they intended for the same `tokenQuant`, since `anotherTokenQuant` is derived from the manipulated ratio at execution time. This is a direct funds-loss impact tied to a single unprivileged/permission-scoped transaction each attacker can trigger by simply trading against the same exchange.

### Likelihood Explanation
The attack requires only broadcasting an ordinary `ExchangeTransactionContract` transaction (no special privilege, SR status, or protocol bug needed) timed around a known pending inject/withdraw transaction, which is realistic given java-tron's public mempool/broadcast model. The precondition (a visible pending exchange-liquidity transaction) is a normal operational occurrence for any actively used on-chain exchange pool, making this readily triggerable.

### Recommendation
Add a slippage-bound field (e.g., `expected_another_token_quant` for withdraw, and `expected_another_token_quant`/max-bound for inject) to `ExchangeInjectContract` and `ExchangeWithdrawContract`, mirroring the `expected` check already present in `ExchangeTransactionActuator.doValidate()` [2](#0-1) , and validate it in `ExchangeInjectActuator.doValidate()` / `ExchangeWithdrawActuator.doValidate()` before execution.

### Proof of Concept
1. Attacker monitors mempool for a pending `ExchangeWithdrawContract` from the pool's creator for `exchange_id=X`, `token_id=firstTokenID`, `quant=Q`.
2. Attacker broadcasts an `ExchangeTransactionContract` swap on `exchange_id=X` that shifts `secondTokenBalance/firstTokenBalance` sharply (e.g., by dumping a large amount of the second token into the pool), and gets it included in the same or an earlier block.
3. The creator's withdraw executes afterward; `anotherTokenQuant` in `ExchangeWithdrawActuator.execute()` is computed from the now-skewed `firstTokenBalance`/`secondTokenBalance` [7](#0-6) , so the creator receives materially less of the second token than the ratio at the time they signed and broadcast the transaction, with no on-chain mechanism to reject the unfavorable outcome.
4. Attacker can then reverse their swap (or exploit the shifted pool further) to realize the value extracted from the creator's withdrawal.
