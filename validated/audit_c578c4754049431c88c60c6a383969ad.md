### Title
Floating-point precision loss in the default (non-hardened) Bancor exchange formula allows value extraction from TRX/TRC10 liquidity pools - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
The `ExchangeTransactionContract`, `ExchangeInjectContract`, and `ExchangeWithdrawContract` handlers use a bancor-style AMM formula to price token swaps in TRON's built-in `Exchange` mechanism. By default the pool math is computed with Java `double` arithmetic in `ExchangeProcessor`, which is used unless the chain has separately activated the `AllowHardenExchangeCalculation` proposal that switches to the `BigDecimal`-based `SafeExchangeProcessor`. Any unprivileged account can invoke `ExchangeTransactionContract` directly, repeatedly exploiting floating-point rounding in the pool balance update to shift value out of the pool, in violation of the invariant (analogous to Umee's TOB-UMEE report item 8) that exchange rates must not be movable by public methods and that the protocol/pool—not the caller—must be the beneficiary of rounding.

### Finding Description
`ExchangeCapsule.transaction()` selects the processor implementation based on the `hardenedCalc` flag: [1](#0-0) 

When `hardenedCalc` is `false` (the default state unless the network committee has passed the `AllowHardenExchangeCalculation` proposal), the swap output is computed by `ExchangeProcessor`, which performs the bancor relay-token math entirely in `double` precision: [2](#0-1) 

The gate that decides which code path is used is `AbstractExchangeActuator.allowHarden()`, which simply reads the dynamic property: [3](#0-2) 

`ExchangeTransactionActuator.doValidate()` invokes `exchangeCapsule.transaction(...)` with this flag and only checks that the caller receives at least their `tokenExpected` — it does not enforce any pool-balance invariant when the non-hardened path is used (that check exists only in the `hardenedCalc` branch of `ExchangeCapsule.transaction()`): [4](#0-3) [5](#0-4) 

Because `double` arithmetic in `exchangeToSupply`/`exchangeFromSupply` truncates via `(long) issuedSupply` and `(long) exchangeBalance` rather than using exact decimal rounding rules that favor the pool, sequences of small, carefully chosen swap amounts accumulate rounding error in the caller's favor across repeated `ExchangeTransactionContract` calls. This is the same rounding/exchange-rate-manipulation invariant class flagged in the external report (module must remain the beneficiary of rounding; user-callable methods must not be able to move the exchange rate outside expected bounds).

The codebase itself acknowledges the risk: it has since introduced a hardened, `BigDecimal`-based, rounding-safe implementation (`SafeExchangeProcessor`) and a `Not precise enough` validation guard in `ExchangeWithdrawActuator`, but these protections are opt-in and gated behind a committee proposal (`AllowHardenExchangeCalculation`) rather than being the default for `ExchangeTransactionActuator`/`ExchangeInjectActuator` swap execution: [6](#0-5) 

### Impact Explanation
On any network where the `AllowHardenExchangeCalculation` proposal has not been activated (the default state), an unprivileged account can call `ExchangeTransactionContract` (and `ExchangeInjectContract`) with attacker-chosen quantities to exploit floating-point truncation in the bancor pricing formula, extracting value from the TRX/TRC10 liquidity pool over many transactions. This constitutes unbacked token creation/loss and theft of funds from other liquidity participants in the affected `Exchange` pool — a direct violation of the AMM's core economic invariant that no party should be able to move the exchange rate for their own benefit through repeated public calls.

### Likelihood Explanation
The attack requires only the ability to broadcast ordinary signed `ExchangeTransactionContract`/`ExchangeInjectContract` transactions against an existing exchange pool — no special privileges, SR/witness status, or contract deployment is required. The exploitability depends on the chain not having activated `AllowHardenExchangeCalculation`; on chains where that proposal remains inactive (which is the historical default), the vulnerable `ExchangeProcessor` double-precision path is unconditionally reachable by any account, making this a Medium-to-High likelihood issue for such deployments, and precisely the "rounding beneficiary" invariant class the external report calls out as needing systematic simulation/fuzzing coverage.

### Recommendation
Make the `BigDecimal`-based, rounding-safe `SafeExchangeProcessor` path the default and mandatory logic for `ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator`, rather than an opt-in proposal-gated feature. Independently of the flag, enforce in `ExchangeCapsule.transaction()` that the constant-product/bancor invariant is checked after every swap for both hardened and non-hardened modes, and add continuous invariant testing/fuzzing (as the external report recommends) asserting that repeated small swaps cannot produce a net gain for the caller.

### Proof of Concept
1. Deploy/observe an `Exchange` pool that has not activated the `AllowHardenExchangeCalculation` committee proposal (default state), so `dynamicStore.allowHardenExchangeCalculation()` returns `false`.
2. From any funded, unprivileged account, submit repeated `ExchangeTransactionContract` transactions against the pool using small `tokenQuant` values chosen so that the `double`-based `exchangeToSupply`/`exchangeFromSupply` truncation in `ExchangeProcessor.exchange()` systematically rounds in the caller's favor.
3. Over many iterations, observe the account's aggregate token holdings increasing beyond what the exact bancor formula would allow, at the expense of the pool's `firstTokenBalance`/`secondTokenBalance` as tracked in `ExchangeCapsule`, with no validation exception thrown since `ExchangeTransactionActuator.doValidate()` only checks `anotherTokenQuant < tokenExpected` and no pool invariant check is performed on the non-hardened path.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }
