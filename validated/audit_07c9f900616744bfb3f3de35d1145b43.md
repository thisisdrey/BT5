### Title
Unbounded temp-file write from attacker-controlled `IgnoreRevisionsBlob` in `RawBlame` enables disk exhaustion - ([File: internal/gitaly/service/commit/raw_blame.go])

### Summary
`createTemporaryIgnoreRevsFile` resolves `IgnoreRevisionsBlob` via `catfile` and writes the full blob content to a temp file with `blobObj.WriteTo(tmpFile)` without ever checking the blob's size beforehand. An attacker who pushes a very large blob to a repository they own and references it as `IgnoreRevisionsBlob` in `RawBlame` can force Gitaly to write that entire blob to local temp storage on every call, and repeated/parallel calls multiply the disk pressure.

### Finding Description
In `RawBlame` (`internal/gitaly/service/commit/raw_blame.go:45-57`), if `in.GetIgnoreRevisionsBlob()` is set, `createTemporaryIgnoreRevsFile` is invoked with the raw attacker-supplied revision string. That function (`internal/gitaly/service/commit/raw_blame.go:152-204`) resolves the object via `objectReader.Object(ctx, git.Revision(revision))`, confirms it `IsBlob()`, then immediately calls `os.CreateTemp("", "ignore-revs-file-*")` and `blobObj.WriteTo(tmpFile)` — copying the entire blob content to disk with no size check, no streaming cutoff, and no cap tied to request/resource limits. `validateRawBlameRequest` only validates `Repository`, `Revision`, `Path`, and `Range` — it never inspects `IgnoreRevisionsBlob` size (`internal/gitaly/service/commit/raw_blame.go:127-150`). Because the attacker fully controls the content of their own repository, they can commit an arbitrarily large blob and reference its OID, causing the full blob to be streamed onto local disk (`os.CreateTemp` uses the default OS temp dir, typically shared across all repositories on that storage node) once per `RawBlame` invocation. Nothing in `git.ValidateRevision` or the locator constrains blob size — those checks only validate revision syntax/repository path, not object size.

### Impact Explanation
Each `RawBlame` call with a large `IgnoreRevisionsBlob` writes a copy of the full blob (potentially many GB, since the attacker only needs to push it once to their own repo and can reference it any number of times) to the shared temp filesystem of the Gitaly storage node. Issued repeatedly or in parallel, this can exhaust local disk space on that node, degrading or failing operations (including for other, unrelated repositories/tenants stored on the same disk) — a resource-exhaustion/DoS of an RPC handler with storage-host-wide blast radius.

### Likelihood Explanation
The precondition is trivial and available to any unprivileged user: push one large blob to a repository they own, then call the public `RawBlame` RPC referencing that blob's OID as `IgnoreRevisionsBlob`. No special role, secret, or non-default configuration is required, and the action is fully repeatable/parallelizable, making this straightforward to exploit and amplify.

### Recommendation
Query the object's size (e.g., via `objectReader`'s object-info lookup) before writing, and reject or cap `IgnoreRevisionsBlob` resolution if the blob exceeds a small, sane limit (an ignore-revs file only needs to contain a list of newline-separated OIDs, so a limit of a few KB/MB is more than sufficient). Alternatively, use an `io.LimitReader`/`io.CopyN` bound to that limit when writing to the temp file, and return an `InvalidArgument` error if the blob is truncated/exceeds the cap.

### Proof of Concept
```go
func TestRawBlame_LargeIgnoreRevisionsBlobDoS(t *testing.T) {
    ctx := testhelper.Context(t)
    cfg, repoProto, repoPath := setupCommitServiceForRawBlame(t, ctx) // existing test setup helper
    client := newCommitServiceClient(t, cfg)

    // Attacker pushes a large blob (e.g. 5GB of zero bytes) to their own repo.
    largeBlobOID := gittest.WriteBlob(t, cfg, repoPath, make([]byte, 5*1024*1024*1024))

    stream, err := client.RawBlame(ctx, &gitalypb.RawBlameRequest{
        Repository:          repoProto,
        Revision:            []byte("HEAD"),
        Path:                []byte("file.txt"),
        IgnoreRevisionsBlob: []byte(largeBlobOID),
    })
    require.NoError(t, err)

    before := diskUsage(os.TempDir())
    _, _ = stream.Recv() // triggers createTemporaryIgnoreRevsFile before blame runs
    after := diskUsage(os.TempDir())

    // Expect temp disk usage grew by ~5GB with no cap applied.
    require.Greater(t, after-before, int64(4*1024*1024*1024))
}
```
Expected result today: temp disk usage grows proportionally to the attacker-chosen blob size with no upper bound, confirming the missing size cap in `createTemporaryIgnoreRevsFile`.
