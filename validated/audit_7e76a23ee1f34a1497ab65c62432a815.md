## Title
Exchange liquidity injection rounds down in favor of the caller instead of the pool - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
`ExchangeInjectActuator` computes the counterpart token amount (`anotherTokenQuant`) that a liquidity injector must simultaneously deposit using integer floor division in both `doValidate()` and `execute()`. Because this amount is *taken from the caller and added to the pool*, rounding down (as EIP‑4626 style reasoning dictates) is the wrong direction here — it should round up so the pool is never diluted. The current implementation systematically lets the caller under-pay the proportional counterpart amount on every injection.

### Finding Description
In `execute()`, the counterpart amount is computed with `floorDiv`: [1](#0-0) 

The same floor-rounding computation (`BigInteger.divide`, which truncates toward zero, i.e. floors for the positive values used here) is repeated in `doValidate()` before the balance/limit checks: [2](#0-1) 

Because the injector supplies `tokenQuant` of one token plus this floor-rounded `anotherTokenQuant` of the paired token, and both are subtracted from the caller's own balance and added into the exchange pool balances via `exchangeCapsule.setBalance(...)`, any fractional remainder from the exact proportional ratio is effectively donated by the pool to the caller rather than the other way around. This is the mirror image of the reported `previewMint()` issue: when calculating how much a party must *supply* to receive/maintain a proportional stake, the calculation should round up in favor of the vault/pool, not down in favor of the caller.

Unlike `ExchangeWithdrawActuator`, which enforces a "Not precise enough" tolerance check on the ratio (`allowHarden` branch, lines 228-243 in `ExchangeWithdrawActuator.java`) to bound imprecision, `ExchangeInjectActuator` has no equivalent precision guard — it only rejects the degenerate case where `anotherTokenQuant <= 0`: [3](#0-2) 

Also notably, `doValidate()` for inject does not require the caller to be the exchange creator (contrast with `ExchangeWithdrawActuator.doValidate()` which enforces `accountCapsule.getAddress().equals(exchangeCapsule.getCreatorAddress())`), so `ExchangeInjectContract` is reachable by any account holding the injected token/TRX, not just the pool owner.

### Impact Explanation
Each injection lets the caller add liquidity while paying slightly less of the counterpart token than the exact bancor-style ratio requires, because the floor-rounded remainder is never collected from the caller. Repeated over many small injections (bounded only by `calcFee()` returning `0` for this actuator, i.e., no explicit fee gate beyond ordinary bandwidth/energy costs), this permits low-cost, repeatable skewing/dilution of the exchange pool ratio in the caller's favor, degrading the pool's backing relative to other participants' claims on it (a form of unbacked-balance drift in the exchange pool state).

### Likelihood Explanation
High: the floor division executes on every single `ExchangeInjectContract` transaction where the ratio is non-integral, and any account (not just the exchange creator) can issue this contract type, so the rounding-favor is trivially and repeatedly reachable from ordinary signed transactions.

### Recommendation
Change the counterpart-amount computation in both `ExchangeInjectActuator.doValidate()` and `execute()` to round up (ceiling division) instead of floor division, ensuring the caller supplies at least the exact proportional counterpart amount and the pool is never diluted. Align this with the same precision-tolerance pattern already used in `ExchangeWithdrawActuator` to bound any residual imprecision.

### Proof of Concept
1. Create/observe an exchange pool with `firstTokenBalance`/`secondTokenBalance` such that the ratio for a chosen `tokenQuant` is non-integral (e.g., `secondTokenBalance * tokenQuant` not evenly divisible by `firstTokenBalance`).
2. Submit repeated `ExchangeInjectContract` transactions with such `tokenQuant` values; each call computes `anotherTokenQuant` via floor division, so the caller consistently supplies less than the exact proportional amount required to keep the pool's ratio and total value unchanged, as seen in `execute()` at [4](#0-3) .
3. Over many such calls, the accumulated shortfall represents value effectively extracted from the pool by the caller relative to a correctly-rounded implementation.
