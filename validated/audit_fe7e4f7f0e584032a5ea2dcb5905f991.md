## Analog Found: Null Pointer Dereference in Market Order Lookup

### Title
Null Pointer Dereference on Missing Market Order Data - (File: `chainbase/src/main/java/org/tron/core/store/MarketOrderStore.java`)

### Summary
CVE-2020-16295 is a null pointer dereference that occurs when GhostScript's `clj_media_size()` dereferences a structure that was never populated because a preceding lookup silently returned nothing instead of failing loudly. The same defect class exists in java-tron's `MarketOrderStore.get()`: when the requested order key is absent from the underlying DB, the method still constructs a `MarketOrderCapsule` from a `null` byte array. `MarketOrder.parseFrom(null)` throws an uncaught `NullPointerException` (not the `InvalidProtocolBufferException` the constructor guards against), leaving the returned capsule half-initialized and any subsequent field access on it throwing NPE.

### Finding Description
`MarketOrderStore.get()` is implemented as: [1](#0-0) 

It declares `throws ItemNotFoundException` but never actually checks for a missing value or throws that exception — it unconditionally forwards whatever `revokingDB.get(key)` returns (which is `null` for a non-existent key) into the `MarketOrderCapsule` constructor: [2](#0-1) 

The constructor only catches `InvalidProtocolBufferException`. Calling protobuf's static `parseFrom(byte[])` with a `null` array throws `NullPointerException`, which is *not* caught here, so it propagates uncaught out of `get()`.

This is reached from the order-matching path in `MarketSellAssetActuator.matchOrder()` / `matchSingleOrder()`, which fetches a maker order directly by ID and immediately dereferences its fields with no null check: [3](#0-2) [4](#0-3) 

Similarly, `MarketOrderIdListCapsule.isOrderExists()` and `getOrderByIndex()` call `orderStore.get(orderId)` and then invoke `.isNextNull()` / other accessors on the result without checking for null internal state: [5](#0-4) [6](#0-5) 

All of these paths are reached during `MarketSellAssetActuator.execute()`, i.e. from a normal, unprivileged `MarketSellAssetContract` transaction submitted by any account.

### Impact Explanation
If the order ID referenced by the maker-side price/order linked list (`pairPriceToOrderStore` → `MarketOrderIdListCapsule`) ever points to an order key that is not present in `MarketOrderStore` (whether due to a state-consistency edge case, a rollback/revoking-DB interaction, or an order that expired/was removed through another path), `orderStore.get(orderId)` returns a corrupt capsule and the very next field access (`getSellTokenQuantityRemain()`, `getSellTokenQuantity()`, etc.) throws an uncaught `NullPointerException`. Because block/transaction application in `Manager` does not distinguish this from other unrecoverable errors, an uncaught NPE during `execute()` for a `MarketSellAssetContract` will abort transaction processing for that node — for a solo node this manifests as a crash/halt of the block-application pipeline (denial of service), matching the "null pointer dereference ⇒ DoS" impact class of CVE-2020-16295.

### Likelihood Explanation
The likelihood depends on being able to produce (or land on) a state where the order-ID linked list references a missing/uncommitted order record. This is a narrower precondition than the original CVE (a "crafted PDF" trivially reaches the bug); I was not able to fully confirm within the available context a guaranteed, single-transaction way to desynchronize `pairPriceToOrderStore`/`MarketOrderIdListCapsule` from `MarketOrderStore` under normal actuator logic, since orders are normally added/removed together. The root-cause defect (wrong exception type caught, no null check on `get()`) is concretely present and verified in code, but the precise unprivileged trigger sequence that forces a stale/missing order reference is not fully demonstrated here and should be verified with a live/instrumented environment (e.g., testing interleavings of `MarketCancelOrderActuator` and `MarketSellAssetActuator` within the same block, or DB rollback scenarios via `TronStoreWithRevoking`).

### Recommendation
- In `MarketOrderStore.get()`, check `revokingDB.get(key)` for `null` and throw `ItemNotFoundException` explicitly instead of silently constructing a capsule from `null` bytes.
- In `MarketOrderCapsule`'s byte-array constructor, catch `NullPointerException` (or guard `data != null` before calling `parseFrom`) in addition to `InvalidProtocolBufferException`.
- Add defensive null checks after every `orderStore.get(...)` call in `MarketSellAssetActuator` (`matchOrder`, `matchSingleOrder`) and in `MarketOrderIdListCapsule` (`isOrderExists`, `getHeadOrder`, `getOrderByIndex`) before dereferencing the returned capsule, converting any inconsistency into a `ContractExeException`/graceful failure rather than an uncaught runtime exception.

### Proof of Concept
Root-cause mechanism (verified in code, without a fully confirmed end-to-end unprivileged trigger):
1. `MarketOrderStore.get(orderId)` is called with an `orderId` that has no corresponding value in the revoking DB.
2. `revokingDB.get(key)` returns `null`.
3. `new MarketOrderCapsule(null)` is constructed; `MarketOrder.parseFrom(null)` throws `NullPointerException`, uncaught by the constructor's `catch (InvalidProtocolBufferException e)` block.
4. The exception propagates out of `get()` into `MarketSellAssetActuator.matchOrder()`/`matchSingleOrder()` (or `MarketOrderIdListCapsule` helper methods), aborting the actuator's `execute()` with an uncaught runtime exception during transaction/block processing. [1](#0-0) [2](#0-1)
