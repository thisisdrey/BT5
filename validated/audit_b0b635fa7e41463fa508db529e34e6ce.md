### Title
Dust deposit-token griefing fills a victim's `MAX_TOKENS_PER_USER` account list and blocks them from depositing or borrowing — ([File: contracts/Pool.sol])

### Summary
An unprivileged attacker can populate a victim's per-account deposit-token list in `Pool` by depositing dust collateral `onBehalfOf_` the victim (or by transferring dust `DepositToken` shares to them). Once `debtTokensOfAccount.length + depositTokensOfAccount.length == MAX_TOKENS_PER_USER (30)`, every `addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` call for the victim reverts with `UserReachedMaxTokens`, permanently blocking the victim from depositing any new collateral type or issuing any new synthetic debt until they manually pay gas to clean up dust entries — which the attacker can re-fill in the same or next block at dust cost. This mirrors CVE-2019-12439's pattern: an attacker squats on a shared, predictable per-user resource (a `/tmp` mount point there; a bounded per-account token list here) to deny service to other users.

### Finding Description
`Pool.addToDepositTokensOfAccount` and `addToDebtTokensOfAccount` are guarded by `onlyIfAdditionWillNotReachMaxTokens`, which reverts when the combined list reaches `MAX_TOKENS_PER_USER = 30` [1](#0-0) . Entries are added whenever an account's balance in a deposit token goes from 0 to positive, on both `_mint` (line 486-488) and `_transfer` (line 518-520) paths of `DepositToken` [2](#0-1) .

The attacker path is fully public:

1. `DepositToken.deposit(amount_, onBehalfOf_ = victim)` accepts any non-zero beneficiary and calls `_mint(victim, dust)`, which calls `pool.addToDepositTokensOfAccount(victim)` [3](#0-2) .
2. Alternatively, attacker deposits into their own account and calls `transfer(victim, 1)` — `_transfer` adds the token to the victim's list when their balance was 0 [4](#0-3) .

There is no opt-in, whitelist, or minimum-amount check: any address can push an entry into any other account's list for the cost of 1 wei of underlying (times a deposit fee). The same cap also guards `DebtToken` issuance, since `addToDebtTokensOfAccount` uses the same modifier and combined count [5](#0-4) .

### Impact Explanation
- Victim cannot `deposit` into any deposit token where their balance is currently 0, cannot `issue`/`leverage` into any new debt token, and cannot receive deposit-token transfers — all revert `UserReachedMaxTokens`. For a fresh account this is a complete lockout from the protocol's core features.
- Cleanup requires the victim to transfer out each dust token one at a time (30 transactions), and the attacker can re-grief atomically or cheaply re-fill slots, making the DoS effectively persistent against the targeted victim.
- While the victim's existing positions stay withdrawable/liquidatable, the impact qualifies as temporary freezing of the victim's ability to use deposited-asset functionality and a direct availability attack on other users — the same "prevent other users from executing" harm as the bubblewrap bug.

### Likelihood Explanation
- No privileged role needed: `deposit`, `transfer`, and `transferFrom` are public; gateways (`NativeTokenGateway`, `VesperGateway`) also work.
- Cost scales with the number of registered deposit/debt tokens (≤30) and is only dust value + gas per entry.
- Feasibility depends on the pool having enough registered deposit tokens to fill the list; on deployments with multiple collaterals this is trivially reachable.

### Recommendation
- Do not add tokens to `depositTokensOfAccount` for transfers/mints below a minimum threshold, or only add on deposits initiated by the beneficiary (`onBehalfOf_ == _msgSender()`), or let `seize`/forced transfers not consume the cap.
- Alternatively allow removal rights to the account itself (a `removeMyDustToken` escape) or drop the `MAX_TOKENS_PER_USER` revert in favor of bounded iteration elsewhere.

### Proof of Concept
Hardhat-style sketch (mirroring `test/Pool.test.ts` setup at `test/Pool.test.ts:1347-1416`):

```ts
it('griefs victim account list', async () => {
  // pool has >= 30 registered deposit tokens: dTokens[0..29]
  for (const dt of dTokens) {
    const underlying = await ethers.getContractAt('ERC20', await dt.underlying())
    await underlying.mint(attacker.address, 1)
    await underlying.connect(attacker).approve(dt.address, 1)
    // 1 wei of underlying minted to victim -> adds dt to victim's list
    await dt.connect(attacker).deposit(1, victim.address)
  }
  expect(await pool.getDepositTokensOfAccount(victim.address)).to.have.length(30)

  // victim cannot deposit a new collateral type nor issue new debt
  await expect(newDepositToken.connect(victim).deposit(1000, victim.address))
    .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')
  await expect(debtToken.connect(victim).issue(100))
    .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')
})
```

A Foundry fork test can target a live `Pool` deployment, enumerate `getDepositTokens()`, and repeat the loop above; the same revert occurs through `NativeTokenGateway.deposit` and `DebtToken.issue` because both funnel into `addTo*TokensOfAccount`.
