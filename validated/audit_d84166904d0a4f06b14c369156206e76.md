### Title
Unbounded array allocation from attacker-controlled length field in TVM precompiled-contract ABI decoding causes OOM DoS - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The helper functions `extractBytes32Array` and `extractBytesArray` in `PrecompiledContracts.java` read an array length directly from attacker-supplied calldata (`words[offset].intValueSafe()`) and immediately allocate a Java array of that size (`new byte[len][]`) without validating it against the actual size of the input data or any energy/gas-derived bound. [1](#0-0) 

This is structurally identical to the Keras "HDF5 shape bomb" bug class: a size/shape field taken from untrusted input controls memory allocation with no upper-bound check, letting a single malicious input trigger an out-of-memory condition before the rest of the (correctly bounds-checked) data is even touched.

### Finding Description
`extractBytes32Array` computes `len` from a caller-controlled `DataWord` via `intValueSafe()` and unconditionally allocates `new byte[len][]`: [2](#0-1) 

`intValueSafe()` can return any value up to `Integer.MAX_VALUE` (2^31-1) since it comes straight from calldata words supplied in a `CALL`/`STATICCALL` to a TVM precompiled contract. Allocating a `byte[Integer.MAX_VALUE][]` reference array alone requires on the order of 16 GB (8-byte object references per slot on a 64-bit JVM), which is enough to trigger an `OutOfMemoryError` immediately, before any subsequent index-bounds check against `words.length` or `data.length` can reject the malformed input.

`extractBytesArray` has a partial guard only for the *offset* (`if (offset > words.length - 1) return new byte[0][];`) but not for `len` itself, which is again taken unchecked from `words[offset].intValueSafe()` before allocating `new byte[len][]`: [3](#0-2) 

Both helpers are internal decoding utilities used by precompiled contracts that accept dynamic arrays of hashes/signatures in their ABI-encoded input (e.g. batch signature/array-based precompiles reachable via `callToPrecompiledAddress`). Energy metering for precompiled contracts is generally computed from `getEnergyForData(byte[] data)` based on `data.length`, not on the decoded/attacker-declared array length, so the cost of the allocation is not charged before it happens — mirroring the Keras issue where the shape/size field is trusted before the corresponding buffer is validated or paid for.

This differs from the well-guarded EVM memory-expansion path (`Memory.extend`, `EnergyCost.checkMemorySize`, `MEM_LIMIT`) which enforces a hard cap and charges energy proportionally before any allocation: [4](#0-3) [5](#0-4) 
No equivalent size cap exists for the `len` value consumed by `extractBytesArray`/`extractBytes32Array`.

### Impact Explanation
An `OutOfMemoryError` thrown inside a precompiled-contract call during TVM execution is an unchecked `Error`, not a checked exception that the surrounding `try`/`catch(ContractValidateException | ContractExeException | ...)` blocks used throughout `Program`/actuator code are written to catch. If it propagates out of the block-processing thread in `Manager` (unhandled `Error`), it can crash or destabilize the node processing that block, i.e. a node crash/halt triggered by a single transaction — satisfying the "node crash or halt" bar for Medium/High impact required by the validation rules.

### Likelihood Explanation
Reachable by any unprivileged account: a smart-contract deployer/caller only needs to issue a `TriggerSmartContract` transaction (or an internal `CALL`/`STATICCALL` from any contract) targeting the affected precompiled address with a crafted calldata word (e.g. `0x00000000...7fffffff` or `0xffffffff`) placed at the position read as the array-length word. No special privilege, stake, or witness/SR role is required — this matches the "unprivileged transaction broadcaster / contract deployer" reachability requirement.

### Recommendation
Bound `len` in both `extractBytes32Array` and `extractBytesArray` against a sane maximum (e.g., derived from `data.length / WORD_SIZE` or a fixed protocol-level cap) before allocating the destination arrays, mirroring the `MEM_LIMIT` check already used for VM memory expansion in `EnergyCost.checkMemorySize`. Reject the precompiled-contract call (return failure/zero) rather than allocating when the declared length is inconsistent with the actual `data` size.

### Proof of Concept
1. Deploy or reuse an existing contract that invokes one of the precompiled contracts whose input is decoded via `extractBytes32Array`/`extractBytesArray` (any address gated behind these helpers in `PrecompiledContracts.getContractForAddress`).
2. Craft calldata where the word at the length-offset position is set to a very large value, e.g. `0x000000000000000000000000000000000000000000000000000000007fffffff`, while the remaining calldata is short/arbitrary.
3. Broadcast a `TriggerSmartContractTransaction` (or trigger via an internal call) invoking the precompiled address with this calldata.
4. During TVM execution, `extractBytes32Array`/`extractBytesArray` allocates `new byte[len][]` with `len` ≈ 2^31, attempting a multi-gigabyte allocation and throwing `OutOfMemoryError` inside the node process handling the transaction/block.

Note: I was not able to fully trace, within the available context window, the exact `execute()` call site(s) that invoke `extractBytes32Array`/`extractBytesArray` and confirm whether any additional upstream validation exists between the precompile's entrypoint and these helper calls; this should be verified directly against the full `PrecompiledContracts.java` source before treating the PoC as final.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
