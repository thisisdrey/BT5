### Title
Repeated PREPARED-phase votes let a single write transaction indefinitely renew its repository write lock, permanently blocking all other writers - ([File: internal/praefect/transactions/manager.go])

### Summary
The external report describes a bug class where a cheap, unprivileged, repeatable action (a micro-trade) is used to keep resetting a time-lock (`lastTradedBlock`), which in turn keeps a shared resource (the pool price) perpetually stuck and blocks a legitimate operation from other actors. The closest structural analog in Gitaly's production code is the Praefect repository reference write-lock renewal mechanism used for serialized writes: an ordinary client driving a Git push can keep a per-repository exclusive lock alive indefinitely by repeatedly emitting `PREPARED_PHASE` votes without ever completing the transaction, thereby starving every other write to that repository.

### Finding Description
Praefect serializes writes per repository using a PostgreSQL-backed lock with a fixed TTL (`renewInterval = 20s`) [1](#0-0) . The lock is acquired at `PREPARING_PHASE`, and is *renewed* every time the same transaction ID sends a vote for `PREPARED_PHASE` (or `COMMITTED_PHASE`): [2](#0-1) 

The renewal itself simply pushes `expired_at` forward by `renewInterval` on every call, without any bound on how many times `Renew` may be invoked for the same lock/transaction, and without any maximum total lock-hold duration: [3](#0-2) 

The reference-transaction hook that drives these votes fires once per phase during a normal Git push (`preparing` → `prepared` → `committed`), and a client is expected to progress linearly through these phases [4](#0-3) . However, nothing in `voteTransaction`/`lockRepoForTransaction` prevents a client (or a compromised/slow Gitaly node relaying votes) from repeatedly re-invoking the `PREPARED_PHASE` vote path for the same, still-open transaction before ever reaching `COMMITTED_PHASE`. Each such call reaches `lock.Renew(ctx)` and extends the lock's `expired_at` by another 20 seconds. As long as the renewal is issued more frequently than the TTL, the lock is kept alive indefinitely — exactly analogous to the pool contract's `lastTradedBlock` being refreshed by a cheap trade "once every 6000 blocks" to keep the price frozen and block a legitimate price update.

While the lock is held, `WriteLockManager.Lock` blocks every other transaction attempting to acquire the same per-repository lock at `PREPARING_PHASE` [5](#0-4) , so all other pushes/writes to that repository (from any user) are denied for as long as the attacker keeps renewing. The only backstops are (a) context cancellation of the offending RPC, which is client-controlled and therefore not a reliable defense, and (b) the 40-second sweep that deletes rows only after `expired_at` has actually passed — which never happens while renewals continue [6](#0-5) .

### Impact Explanation
An unprivileged user who can push to (or otherwise drive a reference transaction against) a single repository can hold that repository's write lock open indefinitely, denying all other legitimate write operations (pushes, branch/tag operations, merges) to the same repository — a persistent, repository-scoped denial of service reachable directly through ordinary Git push activity once `PraefectSerializedWrite` is enabled. This mirrors the reported bug's impact rating: a low-cost, repeatable action fully blocking a shared, contended resource for other users.

### Likelihood Explanation
Reaching `PREPARED_PHASE` requires only a standard push through the `reference-transaction` hook, and there is no explicit cap on the number of `PREPARED_PHASE` votes a single transaction ID may submit before committing, nor a maximum total lock hold time independent of renewal cadence. Exploitability depends on whether a client can cause repeated `PREPARED` votes to be emitted for one transaction without progressing to `COMMITTED_PHASE` (e.g., a slow/adversarial Gitaly node in the replica set, or client behavior that stalls after the prepared vote while re-issuing it). This requires further verification against the exact vote-emission cadence of `git-receive-pack`/the reference-transaction hook, which the available index does not fully expose, so likelihood is assessed as moderate rather than confirmed trivial.

### Recommendation
Bound the total lifetime of a repository write lock independent of renewal frequency (e.g., a hard maximum lock-hold duration measured from initial acquisition, not from the last renewal), and/or cap the number of `PREPARED_PHASE` renewals permitted per transaction ID before forcing the lock to be released and the transaction failed. Additionally, ensure server-side enforcement (not reliant on client context cancellation) that a transaction stuck between `PREPARED_PHASE` and `COMMITTED_PHASE` beyond a reasonable bound is proactively stopped and its lock released, similar to how `StopTransaction`/`cancelTransaction` already release the lock on graceful termination.

### Proof of Concept
1. Enable `PraefectSerializedWrite`.
2. Register a transaction and cast a `PREPARING_PHASE` vote for repository R, causing `WriteLockManager.Lock` to acquire the row in `repository_reference_write_locks` for R.
3. Instead of proceeding to `COMMITTED_PHASE`, repeatedly call `VoteTransaction` with `PREPARED_PHASE` for the same `transactionID` at an interval shorter than the 20-second `renewInterval` (e.g., every 5 seconds), per `lockRepoForTransaction`'s `PREPARED_PHASE`/`COMMITTED_PHASE` branch [7](#0-6) .
4. Concurrently, attempt a second, legitimate write transaction against R via `PREPARING_PHASE`; observe it blocks in `WriteLockManager.Lock` waiting on the notification channel [8](#0-7) , and remains blocked for as long as step 3 continues, since `expired_at` never elapses.

// Lock acquires the write lock for a given virtualStorage, relativePath and txnID,
// blocking until the lock is acquired or ctx is cancelled.
func (r *RepoReferenceWriteLockManager) Lock(ctx context.Context, virtualStorage, relativePath string, txnID uint64,
) (RepoLock, error) {
	for {
		res := r.tryLock(ctx, virtualStorage, relativePath, txnID)
		if res.Err != nil {
			return RepoLock{}, res.Err
		}
		if res.Acquired {
			return RepoLock{Unlock: res.Unlock, Renew: res.Renew}, nil
		}

		select {
		case <-ctx.Done():
			res.Deregister()
			return RepoLock{}, fmt.Errorf("wait for lock: %w", ctx.Err())
		case <-res.NotificationCh:
			// wait for the lock to release
		}
	}
}

type tryLockResult struct {
	Acquired       bool
	Unlock         func() error
	Renew          func(context.Context) error
	NotificationCh <-chan struct{}
	Deregister     func()
	Err            error
}

// renew extends the expiry of the write lock held by txnID by another renewInterval.
// It returns an error if the lock is not currently held by txnID.
func (r *RepoReferenceWriteLockManager) renew(ctx context.Context, virtualStorage string, relativePath string, txnID uint64) error {
	query := `
UPDATE repository_reference_write_locks as locks
SET  expired_at = (NOW() + $3::interval)
WHERE locks.lock_id = $1 AND holder_txn_id = $2
RETURNING expired_at;
`
	lockID := repoLockID(virtualStorage, relativePath)
	start := time.Now()
	rows, err := r.qc.QueryContext(ctx, query, lockID, txnID, r.renewInterval)
	r.operationDuration.WithLabelValues(virtualStorage, "renew").Observe(time.Since(start).Seconds())
	if err != nil {
		return fmt.Errorf("renew repo reference write lock (executing query): %s, %w", lockID, err)
	}
	defer func() {
		if err := rows.Close(); err != nil {
			r.logger.WithError(err).Error("close rows")
		}
	}()
	if rows.Next() {
		return nil
	}
	if err := rows.Err(); err != nil {
		return fmt.Errorf("renew repo reference write lock (iterating rows): %s, %w", lockID, err)
	}
	return fmt.Errorf("renew repo reference write lock (no rows): %s", lockID)
}

func (mgr *Manager) lockRepoForTransaction(ctx context.Context, transactionID uint64, storageName, repoRelativePath string,
	phase gitalypb.VoteTransactionRequest_Phase,
) error {
	if featureflag.PraefectSerializedWrite.IsDisabled(ctx) {
		return nil
	}

	switch phase {
	case gitalypb.VoteTransactionRequest_PREPARING_PHASE:
		lock, err := mgr.repoWriteLockMgr.Lock(ctx, storageName, repoRelativePath, transactionID)
		if err != nil {
			return fmt.Errorf("try lock: %w", err)
		}
		mgr.repoLocks.Store(transactionID, lock)

	case gitalypb.VoteTransactionRequest_PREPARED_PHASE, gitalypb.VoteTransactionRequest_COMMITTED_PHASE:
		v, ok := mgr.repoLocks.Load(transactionID)
		if !ok {
			// No Preparing was cast for this transaction. This happens when Git itself drives
			// the reference-transaction hook on a Git build that doesn't emit "preparing"
			// (i.e. pre-2.54). Skip lock work; serialization is dormant for this path
			// until GIT_VERSION_PREV is bumped past 60d8c1e9.
			mgr.logger.WithFields(log.Fields{
				"transaction.id": transactionID,
				"phase":          phase.String(),
			}).DebugContext(ctx, "skipping lock check: no preparing phase recorded")
			return nil
		}
		lock := v.(datastore.RepoLock)
		if err := lock.Renew(ctx); err != nil {
			return err
		}
	}
	return nil
}
