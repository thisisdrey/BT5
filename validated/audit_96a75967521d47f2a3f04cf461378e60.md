### Title
Protocol fee bypass on high-value NEP-245/IMT transfers via per-leg `amount <= 1` exemption - ([File: contracts/defuse/core/src/intents/token_diff.rs])

### Summary
`TokenDiff::token_fee` grants a complete fee exemption (`Pips::ZERO`) whenever the absolute delta of a single `TokenId::Nep245` or `TokenId::Imt` leg is `<= 1`, with no awareness of the real economic value that "1 unit" represents. Because a solver fully controls the granularity of their own IMT token (self-minted via `ImtMint`) or a deployed NEP-245 contract, and because fee assessment is scoped per `TokenId` per single `TokenDiff` execution rather than across the total value moved, an attacker can always structure transfers to keep every leg at `amount == 1`, permanently avoiding `protocol_fee` on that side of the trade regardless of how much value actually changes hands.

### Finding Description
The intended binding is: for every negative delta of token `T` executed as `token_in`, `fees_collected.amount_for(T) == protocol_fee.fee_ceil(total_amount_moved_of_T)`. Instead, the code in `TokenDiff::token_fee` ( [1](#0-0) ) special-cases `TokenIdType::Nep245 | TokenIdType::Imt` together with `TokenIdType::Nep171`: when `amount <= 1` it returns `Pips::ZERO` unconditionally, bypassing `protocol_fee` entirely.

This exemption is designed for genuine NFTs and NFT-like usages of MT/IMT tokens, where "1 unit" is an atomic, non-divisible item and taking a percentage fee would be meaningless. However, `Nep245` (multi-token) and `Imt` (`ImtTokenId`, minted freely by any user via an `ImtMint` intent, per `crates/primitives/token-id/src/imt.rs`) support arbitrary per-unit value: nothing in `ImtTokenId` or the deposit/mint path ties `amount` to an indivisible real-world quantity. A solver can therefore mint or deploy an IMT/MT asset representing a fungible high-value position (e.g., "1 unit == $1,000,000 of value") and settle every trade in that asset using `delta == -1` legs.

Because `execute_intent` in `contracts/defuse/core/src/intents/token_diff.rs` (lines 59-78) computes `fee = Self::token_fee(token_id, amount, protocol_fee).fee_ceil(amount)` independently for each `(token_id, delta)` pair in the diff, and because nothing accumulates fee assessment across multiple `TokenDiff` intents or `execute_intents` batches, the attacker can:
1. Mint/deploy their own IMT or MT token with unit value far above the effective per-unit value of a NEP-141 token.
2. Sign a sequence of `TokenDiff` intents, each moving `delta = -1` of that `Imt`/`Nep245` token id against a counterparty (which can be the attacker's own second account or a genuine counterparty), splitting what is economically one large transfer into N unit-sized legs.
3. Each execution independently hits `TokenIdType::Imt if amount > 1 => {}` false branch → falls to `TokenIdType::Nep171 | TokenIdType::Nep245 | TokenIdType::Imt => return Pips::ZERO`, so `fee_ceil(1) * 0 == 0` for every leg.
4. Aggregate fee collected on the Imt/Nep245 side of the trade is `0`, while `protocol_fee.fee_ceil(total_moved)` (computed over the true aggregate value) would be nonzero — the divergence the audit's binding describes.

No existing guard prevents this: `MultiPayload::verify`, nonce/salt checks, and `#[private]`/role guards are all about authorization/replay, not about fee correctness across a value axis that the fee model does not track. `Pips::fee_ceil` (crates/primitives/fees/src/lib.rs, lines 116-121) is only ever invoked with the per-leg `amount`, which the attacker controls to always be `1`.

### Impact Explanation
The Verifier's fee collector (`engine.state.fee_collector()`) under-collects `protocol_fee` on the value moved through NEP-245/IMT-denominated legs, for any solver willing to split a transfer into unit-sized legs. This matches the "protocol fees bypassed" Critical category explicitly listed in the rules: value that should have been paid to the fee collector never leaves the trading party's balance. It is fully repeatable — any account, any IMT/MT token, any number of times — and the only asset ordinarily unaffected is `Nep141`, since its branch has no `amount > 1` guard and always charges `protocol_fee`. The blast radius is protocol revenue on any trade routed through NEP-245/IMT assets rather than NEP-141.

### Likelihood Explanation
Preconditions are attacker-only: the ability to mint an `Imt` token via `ImtMint` (self-service) or deploy/control an NEP-245 multi-token contract, deposit it into the Verifier, and sign ordinary `TokenDiff` intents — all within the "unprivileged attacker" profile defined by the rules. The only cost is proportional gas/signature overhead for issuing more, smaller legs/intents instead of one large one; for high-value transfers this cost is negligible relative to the `protocol_fee` saved. The technique is trivially repeatable across accounts and tokens.

### Recommendation
Base the NFT/MT/IMT fee exemption on a token property that actually indicates non-fungibility (e.g., a per-`TokenId` "supply == 1" / decimals == 0 flag verified at registration time, or metadata queried at deposit time) rather than solely on the transient `amount` of a single delta. Alternatively, remove the blanket exemption for `Nep245`/`Imt` and require callers to prove — via on-chain metadata — that a given `token_id` is genuinely non-fungible before it can qualify for `Pips::ZERO`.

### Proof of Concept
```rust
// contracts/defuse/core/src/intents/token_diff.rs (new test)
#[test]
fn imt_unit_leg_fee_bypass() {
    let minter: AccountId = "attacker.near".parse().unwrap();
    let imt_id: TokenId = ImtTokenId::new(minter.clone(), "high-value-unit".into()).into();
    let fee = Pips::ONE_PERCENT; // nonzero protocol_fee

    // Simulate N repeated unit legs instead of one bulk leg of `N`.
    let n = 1000u128;
    let mut fees_collected_total = 0u128;
    for _ in 0..n {
        let f = TokenDiff::token_fee(&imt_id, 1, fee).fee_ceil(1);
        fees_collected_total += f;
    }

    let expected_fee_if_charged_in_bulk = fee.fee_ceil(n); // what should be owed on n total units

    assert_eq!(fees_collected_total, 0);
    assert_ne!(fees_collected_total, expected_fee_if_charged_in_bulk);
}
```
A full end-to-end confirmation would additionally use a `near-workspaces` sandbox: mint the `Imt` token via `ImtMint`, deposit balances for two accounts, execute `n` `TokenDiff` intents each with `diff = {imt_id: -1, nep141_usdc: +k}` against a matching counterparty diff, and assert that `fee_collector`'s NEP-245/IMT balance stays `0` while the NEP-141 leg's fee is charged normally, demonstrating the asymmetric, value-independent fee bypass.

    #[inline]
    pub fn token_fee(token_id: impl Into<TokenIdType>, amount: u128, fee: Pips) -> Pips {
        let token_id = token_id.into();
        match token_id {
            TokenIdType::Nep141 => {}
            TokenIdType::Nep245 | TokenIdType::Imt if amount > 1 => {}
            // do not take fees on NFTs and MTs with |delta| <= 1
            TokenIdType::Nep171 | TokenIdType::Nep245 | TokenIdType::Imt => return Pips::ZERO,
        }
        fee
    }
