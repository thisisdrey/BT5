### Title

Liquidators can bypass `maxLiquidable` through repeated liquidations - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary

`Pool.liquidate()` enforces `maxLiquidable` as a percentage of the victim’s debt at the start of each call, but it does not track cumulative liquidations across calls. Because each successful liquidation immediately burns part of the victim’s debt, the next call recalculates the limit against the reduced balance. The liquidation price is oracle-derived and does not depend on prior liquidation volume, so repeated public calls can exceed the intended liquidation bound.

### Finding Description

`maxLiquidable` defaults to 50% and is documented as the maximum percentage of debt allowed to be liquidated. [1](#0-0) [2](#0-1) 

However, `Pool.liquidate()` applies the check only to `amountToRepay_.wadDiv(_debtTokenBalance)`, where `_debtTokenBalance` is the victim’s current debt at that call. [3](#0-2) 

After the check, the victim’s debt is burned and collateral is seized. [4](#0-3)  Consequently, a liquidator can repay 50% of the original debt in one transaction, then repay up to 50% of the remaining debt in the next transaction, and continue while the position remains unhealthy.

The seized amount is calculated independently for each call from the oracle price, liquidator incentive, and protocol fee. [5](#0-4)  There is no storage for cumulative debt repaid, cumulative collateral seized, liquidation epoch, or cooldown.

For a sufficiently underwater position, the second call can use `quoteLiquidateMax()` or a manually sized repayment to seize nearly all remaining collateral while staying below the recalculated debt percentage cap. `quoteLiquidateMax()` explicitly takes the lesser of the amount needed to seize the account’s collateral balance and the current `maxLiquidable` debt amount. [6](#0-5) 

### Impact Explanation

This breaks the liquidation-bound invariant implied by `maxLiquidable`. A single liquidation may be limited to 50% of the victim’s debt, but sequential liquidations can repay and seize substantially more than 50% of the original position.

For underwater accounts, this can strip all economically meaningful collateral through multiple calls while leaving residual bad debt. The excess collateral transferred as liquidation incentive is an immediate loss to the victim and an immediate gain to the liquidator. `DepositToken.seize()` performs an unrestricted transfer from the victim once called by the authorized `Pool`. [7](#0-6) 

The `debtFloorInUsd` check can constrain liquidation paths that would leave a nonzero debt below the configured floor, but it does not enforce a cumulative liquidation cap. [8](#0-7)  An attacker can size each repayment so the remaining debt stays above the floor or arrange the final repayment to satisfy the floor rule.

### Likelihood Explanation

Any unprivileged liquidator holding or able to obtain the synthetic token can call `Pool.liquidate()`. The only relevant preconditions are:

- the victim is unhealthy;
- the liquidator is not the victim;
- each individual repayment is no more than `maxLiquidable` times the then-current debt;
- the contract is not shutdown;
- the seized amount does not exceed the victim’s collateral balance.

The health check only rejects positions that are already healthy and does not prevent additional liquidations of a still-unhealthy position. [9](#0-8)  `nonReentrant` prevents nested execution but does not prevent sequential calls.

### Recommendation

Define and enforce the intended scope of `maxLiquidable`.

If it is intended as a cumulative liquidation bound, track liquidated debt per victim and reset that amount only after the position becomes healthy or after an explicit liquidation window expires. For example, store `liquidatedDebtSinceUnhealthy[account][syntheticToken]` and check:

```solidity
cumulativeRepaid + amountToRepay_ <=
    initialDebtWhenUnhealthy.wadMul(maxLiquidable);
```

Alternatively, remove `maxLiquidable` if a per-transaction percentage limit is not intended to bound total liquidation, since it provides no cumulative protection and only requires more transactions.

### Proof of Concept

The following Hardhat test can be added to `test/Pool.test.ts` inside the existing fixture where `alice`, `liquidator`, `msdMET`, `msEth`, `msEthDebtToken`, `masterOracle`, `pool`, `metCF`, and `toUSD()` are available. It assumes the liquidator holds enough `msEth`, as in the existing fixture.

```typescript
it('bypasses maxLiquidable through sequential liquidations', async function () {
  // Make Alice moderately underwater.
  await masterOracle.updatePrice(met.address, toUSD('2'))

  const maxLiquidable = await pool.maxLiquidable()
  const initialDebt = await msEthDebtToken.balanceOf(alice.address)
  const initialCollateral = await msdMET.balanceOf(alice.address)

  // First liquidation: exactly the per-call cap.
  const firstRepay = initialDebt.mul(maxLiquidable).div(parseEther('1'))
  await pool
    .connect(liquidator)
    .liquidate(msEth.address, alice.address, firstRepay, msdMET.address)

  const debtAfterFirst = await msEthDebtToken.balanceOf(alice.address)
  const collateralAfterFirst = await msdMET.balanceOf(alice.address)

  expect(debtAfterFirst).to.be.lt(initialDebt)
  expect(collateralAfterFirst).to.be.lt(initialCollateral)

  // Second liquidation: the cap is recalculated using the reduced debt.
  // quoteLiquidateMax returns the amount needed to seize the remaining
  // collateral when that amount is below 50% of the reduced debt.
  const secondRepay = await pool.quoteLiquidateMax(
    msEth.address,
    alice.address,
    msdMET.address
  )

  const secondCallLimit = debtAfterFirst
    .mul(maxLiquidable)
    .div(parseEther('1'))

  expect(secondRepay).to.be.gt(0)
  expect(secondRepay).to.be.lte(secondCallLimit)

  await pool
    .connect(liquidator)
    .liquidate(msEth.address, alice.address, secondRepay, msdMET.address)

  const totalRepaid = firstRepay.add(secondRepay)
  const intendedOriginalLimit = initialDebt
    .mul(maxLiquidable)
    .div(parseEther('1'))

  // Aggregate repayment exceeds the limit measured against initial debt.
  expect(totalRepaid).to.be.gt(intendedOriginalLimit)

  // For the moderately underwater fixture, the second call drains nearly
  // all collateral while debt remains.
  expect(await msdMET.balanceOf(alice.address)).to.be.closeTo(
    ethers.constants.Zero,
    parseEther('0.000001')
  )
  expect(await msEthDebtToken.balanceOf(alice.address)).to.be.gt(0)
})
```

The two transactions each pass the `amountToRepay_ / currentDebt <= maxLiquidable` check, while their combined repayment exceeds `initialDebt * maxLiquidable`. This demonstrates that the configured liquidation bound is bypassed without privileged access or oracle manipulation.
