### Title
Priority-floor pre-filter in `apply_priority_floor_to_batch` performs full transaction parsing/cost-model work per packet ahead of signature verification, letting unstaked flood traffic shift (and amplify) CPU cost onto the leader precisely during saturation - (File: `core/src/sigverify.rs`)

### Summary
When the scheduler is saturated and publishes a non-zero `SchedulerPriorityFloor`, every incoming packet in `SigVerifyWorkerPool::run_transaction_task` is run through `apply_priority_floor_to_batch`, which calls `calculate_priority_from_bytes` on each non-discarded packet before `ed25519_verify_serial` ever runs. `calculate_priority_from_bytes` does a full `SanitizedTransactionView` parse, `RuntimeTransaction` construction, and `CostModel::calculate_cost_for_executed_transaction` + fee computation - none of which require a valid signature. An unstaked attacker can therefore flood syntactically well-formed but garbage-signed, zero/low-priority packets that never pass real sigverify, yet each one forces this heavier pre-sigverify parse+cost-model pass specifically once the leader is already saturated (i.e., under maximum legitimate load).

### Finding Description
In `core/src/sigverify.rs`, `SigVerifyWorkerPool::run_transaction_task` processes each `PacketBatch` as: dedup (`dedup_packets_and_count_discards`) → priority-floor check (`apply_priority_floor_to_batch`, only when `floor > 0`) → `sigverify::ed25519_verify_serial`. [1](#0-0) 

`apply_priority_floor_to_batch` iterates every kept packet in the batch and calls `calculate_priority_from_bytes(bank, data)` for each one to decide whether to discard it as at-or-below the current floor: [2](#0-1) 

`calculate_priority_from_bytes` is not a cheap comparison - it performs a full sanitized-view parse, builds a `RuntimeTransaction`, and runs the cost model plus fee calculation, none of which validate the transaction's signature: [3](#0-2) [4](#0-3) 

Because this happens strictly before `ed25519_verify_serial`, an attacker never needs valid keypairs/signatures to trigger this cost - only bytes that pass structural sanitization (`SanitizedTransactionView::try_new_sanitized` / `sanitize_config()`), which is a purely local, cheap-to-generate operation for the attacker (no cryptographic signing required, no real funded accounts required). The floor mechanism is only active when `SaturationState` has published `floor > 0`, i.e., precisely when the scheduler's buffer is already ≥ 99% full (`SATURATION_BUFFER_PCT`), which an attacker can induce by first flooding with low-priority (e.g., zero-fee) transactions: [5](#0-4) [6](#0-5) 

Once saturated, continued flooding with more such packets forces every worker thread to spend `total_priority_floor_time_us` doing full parse+cost-model work per packet before any signature is checked or any fee is collected, which is tracked (but not bounded) by the stats field: [7](#0-6) [8](#0-7) 

The mechanism's stated purpose is to let sigverify "cheaply" drop below-floor packets ahead of the (supposedly more expensive) `ed25519_verify_serial` call, but the substitute cost - full transaction sanitization plus `CostModel::calculate_cost_for_executed_transaction` and fee-detail computation - is not obviously cheaper than an ed25519 verification, and unlike ed25519 verification it involves multiple heap allocations, instruction-by-instruction cost accounting, and fee-structure lookups. This can make the "optimization" a net amplifier of attacker-controlled CPU cost during exactly the saturation window the mechanism is meant to protect against, since the check runs unconditionally on every syntactically-valid packet regardless of whether it will ultimately be accepted or rejected, and no signature check gates entry into this code path.

### Impact Explanation
This is grossly underpriced pre-fee work: an unstaked attacker pays nothing (no valid signature, no funded account, no fee) to force full transaction parsing and cost-model computation on the leader for every packet, and this cost is incurred specifically during scheduler saturation - the state where leader CPU is most contended. This matches the "Scope: High" bounty category described in the prompt (`bank_forks.rs` scope): sigverify/scheduling work triggerable by unprivileged, unstaked traffic that vastly exceeds any fee ever collected, degrading leader throughput below its true cost. It does not cause a panic, deadlock, consensus-invalid block, or unbounded memory growth by itself, but it is a genuine CPU-cost/QoS-evasion issue in the sigverify hot path that the floor mechanism was specifically designed to prevent.

### Likelihood Explanation
Preconditions are fully attacker-controlled and require only unstaked TPU/QUIC access: (1) flood 0-priority (or minimal fee) syntactically valid packets until `SaturationState::update` reports `saturated == true` (buffer at `SATURATION_BUFFER_PCT` = 99% of `TOTAL_BUFFERED_PACKETS`, or any `num_dropped_on_capacity > 0`), (2) continue flooding with more low/garbage-signed structurally-valid packets. Because sanitization requires no valid signature, packet generation is essentially free for the attacker (pure local byte construction), while each accepted-for-parsing packet costs the validator a full `calculate_priority_from_bytes` call. This is fully repeatable and scales linearly with attacker-sent packet rate and connection count, with no rate limit gating entry into `apply_priority_floor_to_batch` beyond the existing dedup step (which only catches exact duplicates, not distinct garbage packets).

### Recommendation
Reorder or cheapen the floor check so it cannot cost more per packet than the work it's meant to save: e.g., perform a lightweight priority/fee estimate that avoids full `RuntimeTransaction`/cost-model construction (or cache/memoize cost-model results across identical-shape packets), or run a cheap structural/size-based heuristic filter before invoking the full parser, or move the floor check to operate on a cheaper computed value already available at ingestion (e.g., derived directly from static message fields without building the full `RuntimeTransaction`). Alternatively, bound total per-batch/per-worker time spent in `apply_priority_floor_to_batch` and skip the floor pass once the batch has been in the pipeline more than a hard time budget, falling back to straight discard/sigverify.

fn apply_priority_floor_to_batch(
    batch: &mut PacketBatch,
    floor: u64,
    bank: &Bank,
) -> (usize, bool) {
    let mut dropped: usize = 0;
    let mut any_kept = false;
    for mut packet in batch.iter_mut() {
        if packet.meta().discard() {
            continue;
        }
        let Some(data) = packet.data(..) else {
            // Zero-length or otherwise unreadable: leave to downstream
            // stages to reject.
            any_kept = true;
            continue;
        };
        // Unparseable packets are kept and left for downstream rejection.
        match calculate_priority_from_bytes(bank, data) {
            Some(priority) if priority <= floor => {
                packet.meta_mut().set_discard(true);
                dropped = dropped.saturating_add(1);
            }
            _ => any_kept = true,
        }
    }
    (dropped, !any_kept)

pub(crate) fn calculate_priority_and_cost<Tx: TransactionMeta + SVMStaticMessage>(
    bank: &Bank,
    transaction: &Tx,
    transaction_configuration: &TransactionConfiguration,
) -> (u64, u64) {
    let cost = CostModel::calculate_cost_for_executed_transaction(
        transaction,
        u64::from(transaction_configuration.compute_unit_limit),
        transaction_configuration.loaded_accounts_data_size_limit,
        &bank.feature_set,
    )
    .sum();
    let fee_details = solana_fee::calculate_fee_details(
        transaction,
        bank.fee_structure().lamports_per_signature,
        transaction_configuration.priority_fee_lamports,
        bank.fee_features(),
    );
    let reward = bank
        .calculate_reward_and_burn_fee_details(&CollectorFeeDetails::from(fee_details))
        .get_deposit();

    // We need a multiplier here to avoid rounding down too aggressively.
    // For many transactions, the cost will be greater than the fees in terms of raw lamports.
    // For the purposes of calculating prioritization, we multiply the fees by a large number so that
    // the cost is a small fraction.
    // An offset of 1 is used in the denominator to explicitly avoid division by zero.
    const MULTIPLIER: u64 = 1_000_000;
    (
        reward
            .saturating_mul(MULTIPLIER)
            .saturating_div(cost.saturating_add(1)),
        cost,
    )

pub(crate) fn calculate_priority_from_bytes(bank: &Bank, data: &[u8]) -> Option<u64> {
    let view = SanitizedTransactionView::try_new_sanitized(data, &sanitize_config()).ok()?;
    let runtime_tx = RuntimeTransaction::<SanitizedTransactionView<_>>::try_new(
        view,
        MessageHash::Compute,
        None,
    )
    .ok()?;
    let transaction_configuration = runtime_tx
        .transaction_configuration(&bank.feature_set)
        .ok()?;
    let (priority, _cost) =
        calculate_priority_and_cost(bank, &runtime_tx, &transaction_configuration);

    Some(priority)
}
