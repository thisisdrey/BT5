Based on my investigation, the `FinalCheckNewParams` construction in `PrecompiledContracts.VerifyTransferProof` mirrors the ntru-rs bug class most closely: a native Rust FFI call (`librustzcashSaplingFinalCheckNew`) is invoked with separately-computed length arguments (`spendCvLen`/`outputCvLen`) that are passed alongside the byte arrays, rather than the native function trusting `array.length` directly.

### Title
Attacker-influenced length parameters passed to native `librustzcash` FFI calls could desynchronize buffer size from actual array size - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
`VerifyTransferProof.execute()` builds `spendCvs`/`receiveCvs` byte buffers from attacker-controlled `spendCount`/`receiveCount` values parsed out of the precompile calldata, then calls `librustzcashSaplingFinalCheckNew` via `FinalCheckNewParams(valueBalance, bindingSig, signHash, spendCvs, spendCount * 32, receiveCvs, receiveCount * 32)`, passing explicit length integers separately from the arrays across a JNI boundary into native Rust code. [1](#0-0) [2](#0-1) 

### Finding Description
`FinalCheckNewParams.valid()` only checks `validParamLength(spendCv, spendCvLen)` / `validParamLength(outputCv, outputCvLen)` — i.e. it verifies the Java array's length equals the length value that was passed alongside it, not that the length is independently correct for the crypto context (analogous to `EncParams` mismatch in the ntru-rs advisory, where the Rust/FFI layer trusted a size value that could be inconsistent with the actual buffer semantics expected on the native side). [3](#0-2) 

The `spendCount`/`receiveCount` values themselves are bounded only by `spendCount < 1 || spendCount > 2 || receiveCount < 1 || receiveCount > 2` before any buffers are allocated, so the offsets used in `System.arraycopy` calls that build `spendCv[]`/`receiveCv[]`/`spendCvs`/`receiveCvs` are all attacker-controlled combinations bounded to small values. [4](#0-3) 

Because `librustzcashSaplingFinalCheckNew` is implemented in native Rust code (accessed through JNI via `Librustzcash`/`LibrustzcashWrapper`), any place where a length value passed to native code does not perfectly match the true allocated size of the corresponding native-side buffer construction logic can cause native memory to be read or written past bounds — this is exactly the failure mode described in the ntru-rs advisory (wrong API usage / parameter mismatch causing a write past allocated memory in native/FFI code, which in Java bypasses JVM bounds checking once control crosses into native code). [5](#0-4) 

I was not able to directly inspect the native Rust implementation of `librustzcashSaplingFinalCheckNew` (only the JNI wrapper interfaces on the Java side are indexed), so I cannot conclusively prove whether the native side performs its own independent bounds validation that would fully mitigate a length/array mismatch. This is a structural analog based on the calling pattern, not a proven exploit.

### Impact Explanation
If the native library trusts the passed-in length value for buffer traversal/writes without strictly re-deriving it from the actual point/element count, a JNI/native memory-safety violation (heap corruption, crash, or worse) could be triggered by a single crafted transaction calling this precompiled contract (`0x1000008` or similar zk-verify precompile address), impacting node availability (crash/halt) across all nodes processing the transaction — a potential chain-halt-class issue if reliably triggerable. However, this requires the native Rust code to actually mishandle a length parameter, which I could not verify due to index coverage limits on native/non-Java sources.

### Likelihood Explanation
Low-to-moderate. The `valid()` checks do enforce `spendCv.length == spendCvLen` and multiples-of-32, which closes off the most obvious mismatch. Exploitability entirely depends on whether the native Rust `librustzcashSaplingFinalCheckNew` implementation independently trusts these lengths for pointer arithmetic in a way inconsistent with what the Java caller computed — which I cannot confirm from the available Java-side index.

### Recommendation
Have a background engineer (with full repo/native source access) inspect the Rust FFI implementation backing `librustzcashSaplingFinalCheckNew` (and other `librustzcash*New` variants) to confirm that all length parameters received from Java are validated against the native buffer's true element count before being used in unsafe slice/pointer construction, and that `spendCvLen`/`outputCvLen` cannot diverge from the actual `spendCv`/`outputCv` array sizes at any call site in `PrecompiledContracts.java`.

### Proof of Concept
Not conclusively demonstrable from available Java-only source; would require access to the native Rust `librustzcash` FFI implementation to construct a concrete overflow trigger. This limitation stems from index coverage of native/non-Java code, not from absence of the pattern in Java.
