### Title
Stale `YieldIdToDataId`/`DataIdToYieldId`/`PromiseYieldReceipt` rows survive `action_delete_account`, allowing cross-owner authorization escalation on account recreation - (runtime/runtime/src/actions.rs, core/store/src/utils/mod.rs)

### Summary
`action_delete_account` calls `remove_account` (core/store/src/utils/mod.rs) to clean up an account's trie state, but `remove_account` never removes `TrieKey::YieldIdToDataId`, `TrieKey::DataIdToYieldId`, `TrieKey::PromiseYieldStatus`, or `TrieKey::PromiseYieldReceipt` rows. If a self-targeted `promise_yield_create_with_id` was pending (containing privileged actions such as `AddKey`/`DeleteAccount`) when the account self-deletes, the stale mapping and the original pending `ActionReceipt` remain addressable under the same `AccountId` after that name is recreated by anyone else.

### Finding Description
`promise_yield_create_with_id` (runtime/near-vm-runner/src/logic/logic.rs:3727) lets a contract create a self-targeted yielded promise and stores a bidirectional `yield_id <-> data_id` mapping via `set_yield_id_mapping` (core/store/src/utils/mod.rs:281), keyed by `receiver_id` (the account itself, since it is self-targeted) together with the pending `ActionReceipt` under `TrieKey::PromiseYieldReceipt`.

Because the promise is self-targeted (`predecessor_id == receiver_id == account_id`), any privileged actions embedded in it (e.g. `AddKey`, `DeployContract`, `DeleteAccount`, `Stake`) pass the creation-time self-authorization check, and at execution time `check_actor_permissions` (runtime/runtime/src/actions.rs:739-785) only verifies `actor_id == account_id` — a pure string comparison of the `AccountId`, with no concept of "account generation" or key ownership continuity. [1](#0-0) 

When the account calls `DeleteAccount`, `action_delete_account` (runtime/runtime/src/actions.rs:314-390) invokes `remove_account` (core/store/src/utils/mod.rs:504-575), which removes `Account`, `ContractCode`, `AccessKey`/`GasKeyNonce`, and `ContractData` rows, but never touches `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, or `DataIdToYieldId`. [2](#0-1) [3](#0-2) 

If the same `AccountId` is later recreated (e.g. a subaccount deleted and re-issued by its parent to a different keyholder, or a top-level name reused), the orphaned `PromiseYieldReceipt`/`YieldIdToDataId` rows are still present under that account name. Anyone who knows the plaintext `user_yield_id` (which is visible on-chain as a function-call argument in the original creation transaction) can call `promise_yield_resume_with_yield_id` (runtime/near-vm-runner/src/logic/logic.rs:3880) from a receipt executing on the new account's contract. This performs `submit_promise_resume_data_with_yield_id` → `get_data_id_for_yield_id` (runtime/runtime/src/ext.rs:428-440), resolving the stale `data_id`, and creates a `PromiseResume` receipt. Alternatively, if the receiver's contract never resumes it, the original yield's scheduled timeout will independently deliver a `PromiseResume(data=None)` receipt that finds the same stale rows and executes the pending actions automatically, with no attacker interaction required.

When that `PromiseResume` receipt is processed (runtime/runtime/src/lib.rs:1500-1534), the runtime looks up `get_promise_yield_receipt` by `account_id`+`data_id` — finds the stale receipt (never removed by `remove_account`) — and executes its original pending actions. Since `actor_id` is derived from the pending receipt's original `predecessor_id` (the old, self-targeted account_id string), and the new account carries the identical `AccountId` string, `check_actor_permissions` treats the resumed actions as fully self-authorized, executing privileged actions (e.g. `AddKey` with an attacker/old-owner-controlled public key) on the new account without any authorization from its current owner.

### Impact Explanation
This is a cross-owner authorization escalation: an attacker (the original account owner, or anyone who read the on-chain `yield_id`) can plant a self-authorized privileged action (e.g. `AddFullAccessKey`) that lies dormant in the trie past account deletion and executes against whoever later reuses that account name, without the new owner's consent. This matches the "authorization escalation across accounts or promises" bounty category and can lead to full account takeover / theft of the new account's funds.

### Likelihood Explanation
Preconditions: attacker must control an account capable of self-targeting `promise_yield_create_with_id` with a privileged action, self-delete it, and the same `AccountId` must later be recreated (fully realistic for attacker-controlled subaccount namespaces, e.g. `victim.attacker.near` deleted then reissued to a new user by `attacker.near`). No validator/node/RPC privilege is required — only ordinary transaction signing and a deployed/available contract exposing the resume host function (or simply waiting for the automatic yield timeout, which requires no interaction at all). This is fully repeatable and low-cost (a handful of transactions plus the yield timeout window).

### Recommendation
Extend `remove_account` (core/store/src/utils/mod.rs) to also enumerate and remove all `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, and `DataIdToYieldId` trie entries scoped to the deleted `account_id` before `action_delete_account` completes (or reject `DeleteAccount` while any such pending state exists for the account), so that no privileged pending receipt can outlive the account and be delivered to a different owner reusing the same name.

### Proof of Concept
Integration/runtime test-loop plan:
1. Deploy `rs_contract` (test contract) to account `victim.attacker.near`, created as a subaccount of `attacker.near`.
2. From `victim.attacker.near`, call `call_promise` with a batch: `yield_create_with_id` (self-targeted, `receiver_id == victim.attacker.near`) whose batch includes `promise_batch_action_add_key_with_full_access` targeting itself, using a known `yield_id`.
3. Call `DeleteAccount` on `victim.attacker.near` (beneficiary = `attacker.near`), confirming the account is removed (`QueryError::UnknownAccount`).
4. From `attacker.near`, issue `CreateAccount` + `DeployContract` to recreate `victim.attacker.near` (simulating reassignment to a new party) with a fresh access key belonging to a different signer ("new_owner").
5. From an unrelated third-party signer, submit a transaction to `victim.attacker.near` invoking `call_promise` with `yield_resume_with_yield_id` using the previously known `yield_id`.
6. Assert the resumed receipt executes the pending `AddKey` action against the recreated `victim.attacker.near`, i.e., query `view_access_key_list` and confirm the attacker's public key was added with `FullAccess` permission — despite `new_owner` never authorizing it.

**Uncertainty**: I could not fully verify from the indexed code whether the automatic yield-timeout scheduling mechanism (`PromiseYieldTimeout`/`PromiseYieldIndices`) definitely fires a `PromiseResume(data=None)` for an already-deleted-and-recreated account without further guard checks; this reinforces the resume-triggered path but the exact timeout mechanics were not fully traced due to index/context limits — the explicit `promise_yield_resume_with_yield_id` third-party trigger path above does not depend on that mechanism and is independently sufficient to demonstrate the vulnerability.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
