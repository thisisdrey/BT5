### Title
Unsynchronized mutation of the shared/constant-call TVM `JumpTable` singletons enables cross-transaction opcode/energy-cost race (analogous to CI/CD cache poisoning) - (File: `actuator/src/main/java/org/tron/core/vm/OperationRegistry.java`)

### Summary
`OperationRegistry` keeps two process-wide singleton `JumpTable` instances: the "shared consensus table" (`tableMap.get(LATEST_VERSION)`) used by every non-constant transaction, and `CONSTANT_CALL_TABLE` used by every `triggerconstantcontract` / `eth_call` / `estimateenergy` request. [1](#0-0) 
Each top-level VM execution calls `OperationRegistry.prepareAndGetTable(isConstantCall)`, which fetches the singleton and then **mutates it in place** via `adjustTable()` (`adjustMemOperations`, `adjustVoteWitness`, `adjustSelfdestruct`), replacing `Operation` entries in the shared array depending on the *current* `VMConfig` flags. [2](#0-1) 
This mutation happens with no locking, and `JumpTable` itself is a plain, unsynchronized `Operation[256]` array with no `volatile`/atomic semantics. [3](#0-2) 

### Finding Description
The GitLab CVE-2022-1423 class of bug is "a shared, mutable cache keyed/consumed across trust boundaries can be poisoned by one context and consumed by another, altering execution semantics for a victim context." The java-tron analog is the shared/constant `JumpTable` singletons in `OperationRegistry`.

- `VMActuator.execute()` calls `VM.play(program, OperationRegistry.prepareAndGetTable(isConstantCall))` for every top-level transaction/call. [4](#0-3) 
- `prepareAndGetTable` returns the *same* static table object every time (`getTable`) and re-runs `adjustTable`, which overwrites specific opcode slots (`MLOAD`, `MSTORE`, `MSTORE8`, `VOTEWITNESS`, `SUICIDE`) with alternate `Operation` objects depending on live config flags such as `allowHigherLimitForMaxCpuTimeOfOneTx`, `allowEnergyAdjustment`, `allowTvmOsaka`, `allowTvmSelfdestructRestriction`. [5](#0-4) 
- `VM.play` then loops and reads `jumpTable.get(program.getCurrentOpIntValue())` once per opcode executed, for the whole duration of the call (including all internal/nested calls, which reuse the *very same* table object via `OperationRegistry.getTable(isConstantCall())` without re-adjusting it). [6](#0-5) [7](#0-6) 

Because the constant-call table (`CONSTANT_CALL_TABLE`) is a single static instance shared by *every concurrently-processed* `triggerconstantcontract`/`eth_call`/`estimateenergy` request reaching the node from anonymous API clients, and the HTTP/gRPC/JSON-RPC server dispatches such requests on multiple worker threads simultaneously, one in-flight constant call's `prepareAndGetTable(true)` can call `table.set(...)` on the array backing `CONSTANT_CALL_TABLE` while a second, concurrently-executing constant call is mid-loop reading `table.get(opcode)` from the same array in `VM.play`. This is a data race with no happens-before edge (`JumpTable.table` is a non-volatile plain array, `set`/`get` unsynchronized), so a thread can observe a torn/partial update, or transiently observe the "wrong" `Operation` variant (e.g., a different energy-cost function or a different SUICIDE restriction behavior) mid-execution — effectively one request's config-driven adjustment "poisons" the opcode behavior seen by another concurrently running, unrelated request, in the same way that a shared CI cache write from one pipeline job could be read by an unrelated job.

This is a real design risk exposed by the refactor visible in `OperationRegistry`/`JumpTable`/`VMActuator` (note the explicit tests `OperationRegistryTest#transactionExecutionsReuseTable`/`constantExecutionsReuseTable`/`constantAdjustmentsDoNotMutateTransactionTable` and `VMActuatorMockTest#nonConstantCallUsesSharedJumpTable`, which were clearly added to document/guard this exact "shared mutable singleton table" behavior). [8](#0-7) [9](#0-8) 

### Impact Explanation
If exploitable in practice, the impact is a node-wide correctness/consensus hazard rather than a memory-safety RCE: a race on the shared `JumpTable` could cause a concurrently-executing transaction or constant call to charge the wrong energy cost for `MLOAD`/`MSTORE`/`MSTORE8`/`VOTEWITNESS`, or to apply the wrong `SUICIDE` restriction variant, for a single opcode execution. Depending on timing this could let an unprivileged contract caller obtain inconsistent energy accounting (potential underpayment for energy, i.e., "unbacked" execution cost) or trigger divergent behavior between nodes evaluating the same block (chain-split risk) if the race is timing-dependent across full nodes with different thread-scheduling. Given `table.set` only swaps whole `Operation` references (single reference-store, generally atomic on the JVM memory model per array slot), a torn *read* of a half-constructed object is unlikely; the more realistic risk is a stale/inconsistent read of the *previous* config's table entries by threads that started evaluating a call before another thread's `adjustTable` finished, since there is no explicit synchronization guaranteeing all threads observe adjustment changes promptly or atomically.

### Likelihood Explanation
Config flags such as `allowHigherLimitForMaxCpuTimeOfOneTx`, `allowEnergyAdjustment`, `allowTvmOsaka`, `allowTvmSelfdestructRestriction` are hard-fork/proposal-controlled and typically only flip at maintenance-period boundaries, so in normal operation `adjustTable` is usually a no-op re-write of the same `Operation` references (see `adjustedOperationsReuseCachedVariants` test), making the race window rare and low-impact under default conditions. [10](#0-9) 
However, exactly at the moment a hard fork/proposal transitions (a state change every full node processes), concurrently in-flight constant calls from anonymous clients (`triggerconstantcontract`, `eth_call`, `estimateenergy`) racing against `adjustTable` on the shared `CONSTANT_CALL_TABLE` is plausible on any node handling API traffic during that transition window. This significantly lowers likelihood versus a "High" always-exploitable class of bug, and I could not fully verify from static code inspection whether additional external synchronization (e.g., a single-threaded VM executor pool) eliminates this race in practice — this would need to be confirmed by tracing the actual thread pool(s) that invoke `VMActuator.execute` for constant calls.

### Recommendation
- Make `JumpTable.table` construction immutable per configuration snapshot instead of mutating the shared/constant singleton in place: build a fresh `JumpTable` (or copy-on-write) per top-level execution when `adjustTable` would change any entry, rather than calling `table.set(...)` on the globally shared array.
- Alternatively, guard `adjustTable()`/`JumpTable.set()` with proper synchronization (e.g., `synchronized`, `AtomicReferenceArray`, or `volatile` array elements) so concurrent readers cannot observe a mid-mutation state.
- Add an explicit concurrency test that runs `prepareAndGetTable(true)` from multiple threads concurrently with `VM.play` consuming the same table, to validate there is no visible race under the JVM memory model.

### Proof of Concept
Not independently reproducible from static analysis alone; the described race requires precisely timing a hard-fork/proposal flag transition (which flips `adjustMemOperations`/`adjustVoteWitness`/`adjustSelfdestruct`) against concurrently in-flight `triggerconstantcontract`/`eth_call` requests hitting `OperationRegistry.prepareAndGetTable(true)` on the shared `CONSTANT_CALL_TABLE` from multiple API-handling threads — confirming actual exploitability would require dynamic/concurrency testing (e.g., a stress test invoking `VMActuator.execute(isConstantCall=true)` on many threads while toggling `VMConfig` flags) that is outside the scope of static code review.

  public static JumpTable prepareAndGetTable(boolean isConstantCall) {
    JumpTable table = getTable(isConstantCall);
    // Apply configuration-dependent changes once at the top level.
    adjustTable(table);
    return table;
  }

  public static JumpTable getTable(boolean isConstantCall) {
    return isConstantCall ? CONSTANT_CALL_TABLE : tableMap.get(LATEST_VERSION);
  }

  private static void adjustTable(JumpTable table) {
    // Make the corresponding changes, excluding opcode activation.
    adjustMemOperations(table);
    adjustVoteWitness(table);
    adjustSelfdestruct(table);
  }

  public static void adjustMemOperations(JumpTable table) {
    boolean adjusted = VMConfig.allowHigherLimitForMaxCpuTimeOfOneTx();
    table.set(adjusted ? ADJUSTED_MLOAD : DEFAULT_MLOAD);
    table.set(adjusted ? ADJUSTED_MSTORE : DEFAULT_MSTORE);
    table.set(adjusted ? ADJUSTED_MSTORE8 : DEFAULT_MSTORE8);
  }

  public static void adjustVoteWitness(JumpTable table) {
    if (VMConfig.allowTvmOsaka()) {
      table.set(OSAKA_VOTEWITNESS);
    } else if (VMConfig.allowEnergyAdjustment()) {
      table.set(ADJUSTED_VOTEWITNESS);
    } else {
      table.set(DEFAULT_VOTEWITNESS);
    }
  }

  public static void adjustSelfdestruct(JumpTable table) {
    if (VMConfig.allowTvmSelfdestructRestriction()) {
      table.set(RESTRICTED_SUICIDE);
    } else if (VMConfig.allowEnergyAdjustment()) {
      table.set(ADJUSTED_SUICIDE);
    } else {
      table.set(DEFAULT_SUICIDE);
    }
  }
