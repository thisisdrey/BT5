### Title
Sybil attacker can permanently DoS TRC10 exchange matching for a token pair by flooding the order book to exceed `MAX_MATCH_NUM` - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
`MarketSellAssetActuator` limits the number of *matches* a single taker transaction can perform to `MAX_MATCH_NUM = 20` [1](#0-0) , and limits the number of *active resting orders per account* to `MAX_ACTIVE_ORDER_NUM = 100` [2](#0-1) . The per-account cap does not limit the number of *distinct accounts* that can place orders at the same best price for a pair. This mirrors the reported bug class: a queue that is capped for a single spender but not globally can still be flooded by a Sybil attacker using many accounts, permanently blocking legitimate FIFO/price-time processing for everyone else.

### Finding Description
When a taker calls `MarketSellAsset`, `matchOrder` walks the maker order linked list at the best price for the pair, one order at a time, incrementing `matchOrderCount` on every maker order consumed; if this count exceeds `MAX_MATCH_NUM` the method throws `ContractValidateException("Too many matches...")`, which is caught in `execute()` and rethrown as `ContractExeException`, failing the transaction [3](#0-2) .

The only protection against an attacker filling that maker price level with many tiny orders is `MAX_ACTIVE_ORDER_NUM = 100`, but this limit is enforced **per owner address** via `MarketAccountOrderCapsule.getCount()` [2](#0-1) , not globally per token pair/price. An attacker who creates many addresses (trivial and unprivileged — each address just needs enough TRX/TRC10 for the minimal order plus the market sell fee) can place, e.g., 21+ minimal-size sell orders at the best price for a given token pair, spreading them across multiple accounts to stay under the 100-per-account cap on each account.

Once more than `MAX_MATCH_NUM` (20) resting orders exist at the best price, **every** legitimate taker whose order needs to consume more than 20 maker orders at that price to fill (or even just to walk past them to the next price level, since `matchOrder`'s inner loop only advances price level after the current price's `orderIdListCapsule` is fully drained [4](#0-3) ) will unconditionally hit `"Too many matches"` and have their transaction fail. The `MarketOrderIdListCapsule` is a manually maintained doubly linked list with no size cap of its own [5](#0-4) , so the attacker can keep the price level saturated indefinitely by re-adding orders (subject only to the 100-per-account limit, easily bypassed with more addresses) whenever any get consumed.

This is analogous to the reported EigenLayer FIFO-queue griefing: a bound exists per single spender/actor, but the underlying processing structure (linked list / FIFO) has no protocol-wide bound, so a multi-account attacker can indefinitely saturate it and block honest users' larger operations from completing.

### Impact Explanation
Any legitimate large market-sell order against a griefed token pair will permanently revert with `ContractExeException`, meaning legitimate users cannot execute a matchable trade of meaningful size against a busy price level. Because a fee (`calcFee()` → `getMarketSellFee()`) is deducted from the taker's balance in `execute()` before the match loop runs and the exception is thrown afterward [6](#0-5) , victims can repeatedly pay fees for failing transactions while unable to trade. This denies availability of the on-chain exchange feature for a specific token pair — a protocol feature reachable directly by any unprivileged transaction sender — with the attacker's capital cost limited to funding minimal-quantity orders across multiple cheap addresses.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to control multiple accounts and place small orders repeatedly (costing only the `MarketSellFee` and minimal token quantity per account, capped at 100 orders/account), but no special privilege, timing, or race condition is needed — pure Sybil spam using ordinary `MarketSellAssetContract` transactions is sufficient to sustain the block indefinitely as long as the attacker is willing to keep refilling consumed orders.

### Recommendation
Enforce a global (not per-account) cap on the number of orders resting at a single price level per token pair, or make `matchOrder` skip/aggregate many same-price maker orders without failing the taker transaction (e.g., partially fill up to `MAX_MATCH_NUM` and return the remainder instead of throwing). Consider also rate-limiting new order creation per token pair across all accounts, or requiring a minimum order size relative to the pair's total open interest, similar to the report's suggested mitigation of a minimum withdrawal fraction.

### Proof of Concept
1. Attacker creates account A1...An (each below `MAX_ACTIVE_ORDER_NUM`=100).
2. Each account places several `MarketSellAssetContract` orders at the same best price for pair (TokenX, TokenY), such that total resting orders at that price exceed `MAX_MATCH_NUM` (20).
3. A legitimate user submits a `MarketSellAssetContract` for TokenY→TokenX large enough that matching would need to consume more than 20 of the attacker's resting orders at that price.
4. `matchOrder` increments `matchOrderCount` past `MAX_MATCH_NUM` and throws `"Too many matches. MAX_MATCH_NUM = 20"` [7](#0-6) , failing the legitimate user's transaction (and consuming their `MarketSellFee`), while the attacker refills any consumed orders from other accounts to keep the price level saturated indefinitely.

  // add order to linked list
  public void addOrder(MarketOrderCapsule currentCapsule, MarketOrderStore orderStore)
      throws ItemNotFoundException {
    byte[] orderId = currentCapsule.getID().toByteArray();

    if (this.isOrderEmpty()) {
      this.setHead(orderId);
      this.setTail(orderId);
    } else {
      // tail.next = order
      // order.pre = tail
      // this.tail = order
      byte[] tailId = this.getTail();
      MarketOrderCapsule tailCapsule = orderStore.get(tailId);
      tailCapsule.setNext(orderId);
      orderStore.put(tailId, tailCapsule);

      currentCapsule.setPrev(tailId);
      orderStore.put(orderId, currentCapsule);

      this.setTail(orderId);
    }
  }
