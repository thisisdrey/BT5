### Title
Missing Slippage Protection in ExchangeInjectActuator / ExchangeWithdrawActuator Allows Unbounded Value Loss from Front-Run Pool Ratio Changes - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java], [File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java])

### Summary
The Bancor-style TRX/TRC10 exchange in java-tron computes the paired-token amount (`anotherTokenQuant`) for `ExchangeInjectContract` and `ExchangeWithdrawContract` strictly from the exchange's *live* token-pool ratio at the moment the transaction executes, with no caller-supplied minimum/maximum bound. `ExchangeTransactionActuator` (the actual swap actuator) protects callers with an `expected` field checked at execution (`anotherTokenQuant < tokenExpected` → revert), but `ExchangeInjectActuator` and `ExchangeWithdrawActuator` have no equivalent bound. This is the same missing-slippage-protection bug class described in the external USSD.sol report (no `amountOutMinimum`), reachable here by an ordinary account (the exchange creator) submitting a normal signed transaction.

### Finding Description
`ExchangeTransactionActuator` implements slippage protection via the `expected` parameter of `ExchangeTransactionContract`: [1](#0-0) 

By contrast, `ExchangeInjectActuator.doValidate()` computes `anotherTokenQuant` purely from the current pool balances and the caller's `tokenQuant`, with no user-provided bound to enforce a minimum/maximum acceptable ratio: [2](#0-1) 

and re-derives the same unbounded amount again at `execute()` time: [3](#0-2) 

Similarly, `ExchangeWithdrawActuator.doValidate()`/`execute()` compute `anotherTokenQuant` from the live pool ratio without any caller-specified floor on the amount received: [4](#0-3) [5](#0-4) 

Both operations are restricted to the exchange's creator account: [6](#0-5) 
but that account is an ordinary, unprivileged address (anyone can call `ExchangeCreateContract` to become a creator), so this is fully reachable from a single signed transaction.

Because these actuators only bind quantities against the pool state *at execution time* (post-consensus ordering), and `ExchangeTransactionContract` swaps from other accounts can move `firstTokenBalance`/`secondTokenBalance` arbitrarily between when the creator signs their Inject/Withdraw transaction and when it is packed into a block, the resulting `anotherTokenQuant` can differ drastically from what the creator expected when signing — exactly the "no slippage / no minimum-output guard" class of bug flagged in the external report for `USSD.sol`'s `UniV3SwapInput`. A block producer or any account can submit `ExchangeTransactionContract` swaps ahead of a pending Inject/Withdraw transaction (which is straightforward on-chain, since pending transactions and their exchange IDs are visible before block finalization) to shift the ratio, then let the creator's Inject/Withdraw execute at the new unfavorable ratio.

### Impact Explanation
- For `ExchangeInject`: the creator can be forced to deposit far more of the paired asset (`anotherTokenQuant`) than intended to maintain the required pool ratio, resulting in unexpected loss of funds.
- For `ExchangeWithdraw`: the creator can receive far less of the paired asset than expected for the `tokenQuant` withdrawn, resulting in a bad trade / loss of value.
- This satisfies "concrete unauthorized... loss of funds" for the calling account, matching the report's slippage-loss impact class (Medium-High), though the loss is bounded to the acting account's own funds rather than draining arbitrary third parties.

### Likelihood Explanation
Requires an active exchange with variable liquidity and an adversary (or MEV-aware actor) willing to submit competing `ExchangeTransactionContract` swaps timed against a pending Inject/Withdraw transaction. This is realistic given java-tron's public mempool/tx-broadcast model, but exploitation value is capped by pool size and the target's chosen `tokenQuant`, and only affects the transaction submitter (the exchange creator), not arbitrary third parties.

### Recommendation
Add an `expected`-style bound (e.g., `expected_another_token_quant_min` for Inject, `expected_another_token_quant_min`/`max` for Withdraw) to `ExchangeInjectContract` and `ExchangeWithdrawContract`, and validate it in both `doValidate()` and `execute()` the same way `ExchangeTransactionActuator` validates `tokenExpected`, rejecting the transaction if the computed `anotherTokenQuant` falls outside the caller's tolerance.

### Proof of Concept
1. Exchange creator `A` owns exchange `E` with tokens `X`/`Y`.
2. `A` signs and broadcasts `ExchangeInjectContract` injecting `tokenQuant` of `X`, expecting to also deposit ~`Q` of `Y` based on the current ratio.
3. Before `A`'s transaction is included, another account rapidly submits several `ExchangeTransactionContract` trades against exchange `E`, shifting the `X`/`Y` ratio significantly.
4. `A`'s Inject transaction executes at the new ratio; `ExchangeInjectActuator.execute()` (lines 73-82) computes a much larger `anotherTokenQuant` of `Y` than `A` anticipated, and deducts it from `A`'s balance/asset with no check against `A`'s original expectation — since `ExchangeInjectContract` provides no field to bound this value, unlike `ExchangeTransactionContract.expected` used in `ExchangeTransactionActuator` (lines 217-221).
