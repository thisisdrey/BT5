## No vulnerability found for this question.

The claimed broken binding does not hold. Tracing the code path in `contracts/defuse/core/src/intents/token_diff.rs` `TokenDiff::execute_intent`, the two operations on `signer_id`'s balance are:

1. `engine.state.internal_apply_deltas(signer_id, [(token_id, delta)])` [1](#0-0) 
2. `engine.state.internal_add_balance(engine.state.fee_collector().into_owned(), fees_collected)` [2](#0-1) 

`internal_apply_deltas` dispatches to `internal_sub_balance` (negative) or `internal_add_balance` (positive) [3](#0-2) , and both of these ultimately call `Amounts::add`/`Amounts::sub`, which are simple `checked_add`/`checked_sub` mutations of a single scalar value keyed by `(account_id, token_id)` [4](#0-3) . The concrete implementation in `contracts/defuse/src/contract/intents/state.rs` confirms this: `internal_add_balance` and `internal_sub_balance` each just call `owner.token_balances.add(...)` / `.sub(...)` on the account's balance map entry for that token [5](#0-4) .

Because these are two independent, sequential, checked additive operations on the same scalar storage slot, arithmetic composition guarantees `final_balance = pre_balance + delta + fee` regardless of whether `signer_id == fee_collector`. There is no code path where the two writes "collapse" or interact non-additively — order-of-operations on `checked_add`/`checked_sub` over integers is associative and commutative, so crediting the fee to the same account that just had `delta` applied produces exactly the same numeric result as if they were two distinct accounts. No double-crediting, masking, or fee bypass occurs; the fee-collector account, if it is also the signer, simply nets `delta + fee` like any other account would from two additive writes, and the fee itself is still computed correctly via `Pips::fee_ceil` over the negative delta as usual [6](#0-5) .

The premise that "if they collapse or interact non-additively" fees could be bypassed is not supported by any code in this path — there is no special-case, no shared mutable reference aliasing issue (each call independently fetches/creates the account entry), and no interaction beyond ordinary sequential addition. The equality the question is built on holds trivially by construction of the checked arithmetic primitives, so there is no divergence to exploit.

    fn internal_apply_deltas(
        &mut self,
        owner_id: &AccountIdRef,
        tokens: impl IntoIterator<Item = (TokenId, i128)>,
    ) -> Result<()> {
        for (token_id, delta) in tokens {
            let tokens = [(token_id, delta.unsigned_abs())];
            if delta.is_negative() {
                self.internal_sub_balance(owner_id, tokens)?;
            } else {
                self.internal_add_balance(owner_id.to_owned(), tokens)?;
            }
        }
        Ok(())
    }

    fn internal_add_balance(
        &mut self,
        owner_id: AccountId,
        tokens: impl IntoIterator<Item = (TokenId, u128)>,
    ) -> Result<()> {
        let owner = self
            .accounts
            .get_or_create(owner_id)
            // we allow locked accounts to accept deposits and incoming deposits
            .as_inner_unchecked_mut();

        for (token_id, amount) in tokens {
            if amount == 0 {
                return Err(DefuseError::InvalidIntent);
            }
            owner
                .token_balances
                .add(token_id, amount)
                .ok_or(DefuseError::BalanceOverflow)?;
        }

        Ok(())
    }

    fn internal_sub_balance(
        &mut self,
        owner_id: &AccountIdRef,
        tokens: impl IntoIterator<Item = (TokenId, u128)>,
    ) -> Result<()> {
        let owner = self
            .accounts
            .get_mut(owner_id)
            .ok_or_else(|| DefuseError::AccountNotFound(owner_id.to_owned()))?
            .get_mut()
            .ok_or_else(|| DefuseError::AccountLocked(owner_id.to_owned()))?;

        for (token_id, amount) in tokens {
            if amount == 0 {
                return Err(DefuseError::InvalidIntent);
            }

            owner
                .token_balances
                .sub(token_id.clone(), amount)
                .ok_or(DefuseError::BalanceOverflow)?;
        }

        Ok(())
    }
