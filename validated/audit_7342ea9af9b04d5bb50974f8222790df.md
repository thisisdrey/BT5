### Title
Custom section preceding Type/Import causes duplicate ImportSection emission in `prepare_contract` re-encoded wasm - (File: runtime/near-vm-runner/src/prepare/prepare_v3.rs)

### Finding Description
`PrepareContext::run` walks the *original* wasm payloads in file order and re-encodes them into `output_code` ("lightly_steamed"). Per the core wasm binary format, custom sections (id 0) are legal anywhere in the stream and are not part of the section-ordering state machine enforced by `wp::Validator`, so a module with the payload order `[Version, CustomSection, TypeSection, ImportSection, FunctionSection, CodeSection*, End]` is fully spec-legal and passes `wp::Validator`'s per-section calls unmodified [1](#0-0) .

When `config.discard_custom_sections` is `false`, the `CustomSection` arm calls `self.ensure_export_section()`, which cascades into `ensure_memory_section()` and then `ensure_import_section()` [2](#0-1) . Because this custom section arrives *before* any real `ImportSection`/`TypeSection` has been seen, `before_import_section` is still `true`, so `ensure_import_section` immediately writes a synthetic `ImportSection` containing only `env.memory` into `output_code` for non-Wasmtime `VMKind`s, and only then does the code copy the `CustomSection` bytes and, later, the real `TypeSection` bytes [3](#0-2) . This already produces re-encoded output with an `ImportSection` positioned *before* the `TypeSection`, which is not spec-compliant module ordering for non-custom sections.

When the real `wp::Payload::ImportSection` arrives afterward, the match arm unconditionally calls `self.transform_import_section(&reader)` regardless of `before_import_section`'s state [4](#0-3) . `transform_import_section` builds and appends a *second* full `ImportSection` (all real imports plus, for non-Wasmtime, another synthetic `env.memory` import) [5](#0-4) . The result is `lightly_steamed` bytes containing two separate `ImportSection` blobs (one with only `env.memory`, one with the real imports plus a duplicate `env.memory`), with the first appearing out of canonical order relative to `TypeSection`.

This malformed `lightly_steamed` buffer is never re-validated before being handed to `finite_wasm_6::Analysis::analyze` and `InstrumentContext::run`, both of which re-parse it with `wp::Parser::parse_all` without an accompanying `wp::Validator` pass [6](#0-5) . `wp::Parser` does not itself enforce non-custom section ordering (only `wp::Validator` does), so it will happily hand back two `ImportSection` payloads to these downstream consumers, which (per code comments and design) assume a single well-formed import section and use it to build function/type index spaces for gas/stack accounting and instrumentation.

### Impact Explanation
The exact downstream failure mode inside `finite_wasm_6` and `InstrumentContext` (both of which reconstruct the function index space from `ImportSection` payloads, see `runtime/near-vm-runner/src/prepare/instrument_v3.rs` lines 300-317) depends on internal invariants of those two consumers that this repository does not fully expose for external crate `finite_wasm_6`. Two outcomes are plausible: (1) a hard panic/unwrap failure while re-deriving import/function indices from a doubly-imported, out-of-order module, which on the apply path would abort transaction processing outside the `PrepareError` error-handling contract and could halt block/chunk production for that shard, or (2) a "successful" but wrong re-indexing (duplicate `env.memory` imports shifting subsequent function indices), producing a module whose semantics diverge from what the validator actually approved. Either matches the scoped "shard-halting panic" or "deterministic-but-wrong" categories in the prompt. I could not fully confirm which occurs because `finite_wasm_6`'s internal handling of a spec-illegal duplicate-`ImportSection`/out-of-order module is not visible in this codebase (external crate, not indexed).

### Likelihood Explanation
The only precondition is `config.discard_custom_sections == false` and `VMKind != Wasmtime`. I was unable to confirm the exact current value of `discard_custom_sections` in `core/parameters/res/runtime_configs/parameters.yaml` within this session (tool budget exhausted before completing that check), so whether this is reachable on the current mainnet runtime config is unverified. If the flag is `false` for the active protocol version, the attack requires only an unprivileged account able to submit a `DeployContract` action with crafted, well-formed-per-spec wasm bytes — trivial and free to reproduce, no special permissions, and fully deterministic/repeatable.

### Recommendation
- In the `CustomSection` arm, do not trigger `ensure_export_section`/`ensure_import_section`/`ensure_memory_section` merely because a custom section appears early; instead defer emission of the synthetic sections until a genuine boundary (Type/Import/Function/etc.) is reached, or buffer custom sections and re-emit them only after the synthetic import/memory/export sections have been finalized in the correct position.
- In the real `wp::Payload::ImportSection` arm, guard `transform_import_section` behind a check that `ensure_import_section`'s synthetic import block was not already emitted (or refactor so there is a single code path responsible for producing exactly one `ImportSection`).
- Add an internal round-trip validation (`wp::Validator::new_with_features(...).validate_all(&lightly_steamed)`) immediately after `PrepareContext::run()` and before feeding `lightly_steamed` to `finite_wasm_6`/`InstrumentContext`, converting any validation failure into `PrepareError` instead of relying on downstream crates to tolerate malformed input.

2. Build a `Config` with `discard_custom_sections = false` and `vm_kind = VMKind::NearVm` (i.e., not `Wasmtime`).
3. Call `prepare_contract(bytes, features, &config, VMKind::NearVm)`.
4. Assert the call does not panic (wrap in `std::panic::catch_unwind`), and assert it returns either `Ok(code)` where `wp::Validator::new_with_features(features.into()).validate_all(&code)` succeeds, or a well-formed `Err(PrepareError::*)` — flag as a bug any panic or any `Ok(code)` that fails re-validation (indicating two `ImportSection`s / duplicate `env.memory`).
5. Repeat with `VMKind::Wasmtime` for comparison (the wasmtime-only export/memory-section cascade does not synthesize an import section here, so the specific duplicate-import defect is expected not to reproduce for that kind).

    fn transform_import_section(
        &mut self,
        reader: &wp::ImportSectionReader,
    ) -> Result<(), PrepareError> {
        let mut new_section = wasm_encoder::ImportSection::new();
        for import in reader.clone() {
            let import = import.map_err(|_| PrepareError::Deserialization)?;
            if import.module != "env" {
                return Err(PrepareError::Instantiate);
            }
            let new_type = match import.ty {
                wp::TypeRef::Func(id) => {
                    // TODO: validate imported function types here.
                    self.function_limit =
                        self.function_limit.checked_sub(1).ok_or(PrepareError::TooManyFunctions)?;
                    wasm_encoder::EntityType::Function(id)
                }
                wp::TypeRef::Table(_) => return Err(PrepareError::Instantiate),
                wp::TypeRef::Global(_) => return Err(PrepareError::Instantiate),
                wp::TypeRef::Memory(_) => return Err(PrepareError::Memory),
                wp::TypeRef::Tag(_) => return Err(PrepareError::Deserialization),
            };
            new_section.import(import.module, import.name, new_type);
        }
        if self.config.vm_kind != VMKind::Wasmtime {
            new_section.import("env", "memory", self.memory_type());
        }
        // wasm_encoder a section with all imports and the imported standardized memory.
        new_section.append_to(&mut self.output_code);
        Ok(())
    }

    fn ensure_memory_section(&mut self) {
        self.ensure_import_section();
        if self.before_memory_section {
            self.before_memory_section = false;
            if self.config.vm_kind == VMKind::Wasmtime {
                wasm_encoder::MemorySection::new()
                    .memory(self.memory_type())

            }
        }
    }

    fn ensure_export_section(&mut self) {
        self.ensure_memory_section();

                wasm_encoder::ExportSection::new()
                    .export(MEMORY_EXPORT, wasm_encoder::ExportKind::Memory, 0)
