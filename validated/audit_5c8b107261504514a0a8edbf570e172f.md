### Title
`insert_instantiated_attachment` never enforces `attachments_max_size`, allowing oversized attachment blobs written to the local `attachments` table - (File: `stackslib/src/net/atlas/db.rs`)

### Summary
`AtlasDB::insert_instantiated_attachment` (`stackslib/src/net/atlas/db.rs:576-592`) directly inserts `attachment.content` into the `attachments.content` BLOB column with no size check whatsoever, and its only caller in the download path, `AttachmentsDownloader::run`'s `Done` arm (`stackslib/src/net/atlas/download.rs:159-162`), performs no size check either. This is inconsistent with `AtlasDB::should_keep_attachment` (`stackslib/src/net/atlas/db.rs:249-266`), which does check `attachment.content.len() as u32 > self.atlas_config.attachments_max_size` but is used on a different code path (inboxed/uninstantiated attachments), not on attachments resolved through the downloader.

### Finding Description
The intended invariant is `content.len() <= attachments_max_size` for every `Attachment` persisted to the `attachments` table, keyed by `hash TEXT UNIQUE PRIMARY KEY` (`stackslib/src/net/atlas/db.rs:66-71`). This bound is only checked in `should_keep_attachment` [1](#0-0) , but `insert_instantiated_attachment`, which is what actually persists downloaded attachment content, performs no such check [2](#0-1) .

The reachable path is: an `AttachmentInstance` is committed on-chain (e.g., via a BNS name-update contract call) with a `content_hash = Hash160(content)`. An attacker fully controls both `content` and its size before computing the commitment hash, so they can commit to an arbitrarily large blob's hash on-chain. When the node's `AttachmentsDownloader` later requests that content from a peer (which the attacker can be, by serving the URL associated with their own node/data URL), the peer responds with a `GetAttachmentResponse`, whose deserializer (`stackslib/src/net/atlas/mod.rs:69-77`) simply hex-decodes the payload into `Attachment { content: bytes }` with no length cap. Once the batch state machine reaches `Done`, `download.rs:159-162` calls `insert_instantiated_attachment(&attachment)` unconditionally — there is no re-check against `atlas_config.attachments_max_size` at this point.

### Impact Explanation
Any oversized `Attachment` whose hash matches an on-chain-committed `content_hash` is written to the node's local SQLite `attachments` table, unbounded by the configured `attachments_max_size`. This is a persistent, unauthenticated write to node storage that bypasses a configured resource bound, causing disk-storage exhaustion risk on any node that syncs Atlas attachments from the attacker's peer.

### Likelihood Explanation
The attacker needs only to: (1) submit an on-chain transaction to a supported contract (e.g., BNS `name-update`) referencing a `content_hash` for an oversized blob they construct, and (2) serve that oversized blob back to any requesting peer via the plain HTTP Atlas attachment endpoint. No secrets, no privileged role, and no more than being a normal remote peer/data-URL host are required. The cost is bounded by the fee for the on-chain contract call, and the exploit is repeatable per new on-chain commitment (each unique hash is a fresh insert due to the `hash TEXT UNIQUE PRIMARY KEY` constraint).

### Recommendation
Add an explicit size check identical to `should_keep_attachment`'s check inside `insert_instantiated_attachment` (or immediately before calling it in `download.rs`'s `Done` arm and in `check_attachment_instances`), rejecting/discarding any `Attachment` whose `content.len() as u32 > self.atlas_config.attachments_max_size` before it is written to the `attachments` table.

### Proof of Concept
```rust
// stackslib/src/net/atlas/tests.rs (new test)
#[test]
fn insert_instantiated_attachment_no_size_check() {
    let atlas_config = AtlasConfig::new(false); // attachments_max_size = 1_048_576
    let mut db = AtlasDB::connect_memory(atlas_config.clone()).unwrap();

    let oversized = Attachment {
        content: vec![0u8; (atlas_config.attachments_max_size + 1) as usize],
    };

    // No size check enforced here, unlike should_keep_attachment
    let res = db.insert_instantiated_attachment(&oversized);
    assert!(res.is_ok(), "oversized attachment was inserted without any size check");

    let stored = db.find_attachment(&oversized.hash()).unwrap();
    assert_eq!(stored.unwrap().content.len(), oversized.content.len());
}
```
This demonstrates that `insert_instantiated_attachment` (`stackslib/src/net/atlas/db.rs:576`) accepts and stores content exceeding `attachments_max_size`, confirming the missing bound at the storage layer as exercised by the `Done` arm in `stackslib/src/net/atlas/download.rs:159-162`.

```rust
    pub fn should_keep_attachment(
        &self,
        contract_id: &QualifiedContractIdentifier,
        attachment: &Attachment,
    ) -> bool {
        if !self.atlas_config.contracts.contains(contract_id) {
            info!(
                "Atlas: will discard posted attachment - {} not in supported contracts",
                contract_id
            );
            return false;
        }
        if attachment.content.len() as u32 > self.atlas_config.attachments_max_size {
            info!("Atlas: will discard posted attachment - attachment too large");
            return false;
        }
        true
    }
```

```rust
    pub fn insert_instantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let tx = self.tx_begin()?;
        tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)",
            params![attachment.hash(), attachment.content, now],
        )?;
        tx.execute(
            "UPDATE attachment_instances SET is_available = 1 WHERE content_hash = ?1 AND status = ?2",
            params![attachment.hash(), AttachmentInstanceStatus::Checked],
        )?;
        tx.commit()?;
        Ok(())
    }
```
