Based on my investigation, I found a plausible analog: the `extractBytesArray`/`extractSigArray`/`extractBytes32Array` helpers in `PrecompiledContracts.java` decode attacker-controlled length/offset fields from calldata and index into arrays without full bounds validation before the code was hardened with TIP-854 guards.

### Title
Heap buffer over-read / index-out-of-bounds in TVM precompile ABI decoding (`extractBytesArray`, `extractSigArray`, `extractBytes32Array`) - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The CVE describes a heap-based buffer over-read caused by trusting a length field read from untrusted binary data and then using it to read further bytes without validating it stays within the buffer. The closest reachable analog in java-tron is the manual ABI array decoding used by the `BatchValidateSign` (address `0x...9`) and `ValidateMultiSign` (address `0x...a`) precompiled contracts, which any contract can invoke via `STATICCALL`/`CALL` with fully attacker-controlled calldata.

### Finding Description
`extractBytesArray` and `extractSigArray` read a length (`len`) and per-item offsets directly from a `DataWord[] words` array that was parsed from raw calldata via `DataWord.parseArray(rawData)`, and then compute a byte offset into the raw `data` buffer to slice out signature/byte content: [1](#0-0) [2](#0-1) 

The only guard present is `offset > words.length - 1`, which only checks the *first* index used, not `offset + i + 1` (per-item index) or the resulting `bytesOffset`, `bytesLen`, or the final slice `(bytesOffset + offset + 2) * WORD_SIZE .. + bytesLen` against `words.length` or `data.length`. `extractBytes32Array` has no bounds check at all: [3](#0-2) 

`extractBytes` then performs `Arrays.copyOfRange(data, offset, offset + len)`, which will throw `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` if `offset`/`len` derived from attacker-controlled words push it past `data.length` or negative: [4](#0-3) 

These helpers are invoked from `ValidateMultiSign.execute` and `BatchValidateSign.doExecute`, both of which decode offsets straight from attacker calldata (`words[3].intValueSafe() / WORD_SIZE`, `words[1].intValueSafe() / WORD_SIZE`, etc.): [5](#0-4) [6](#0-5) 

`DataWord.parseArray` pads short calldata to `DataWord` boundaries, so `words[offset+i+1]` reads can silently return zero-padded words instead of throwing for out-of-range `offset`, but crafted offsets that are in-range for `words` yet compute a byte range beyond `data.length` will still hit `Arrays.copyOfRange`'s bounds check and throw.

A repo test suite (`BatchValidateSignContractTest`, `ValidateMultiSignContractTest`) documents a TIP-854 mitigation (`isValidAbiEncoding` check gated by `VMConfig.allowTvmOsaka()`) added specifically to reject malformed calldata shapes before this decoding runs: [7](#0-6) [8](#0-7) 

This strongly indicates the pre-TIP-854 code path (i.e., when `allowTvmOsaka()` is not yet active on a given chain/fork) is exactly the bug class described by the CVE: length/offset values taken from untrusted input drive an out-of-bounds read.

### Impact Explanation
An unhandled `RuntimeException` (e.g., `ArrayIndexOutOfBoundsException`, `NegativeArraySizeException`) thrown deep inside `ValidateMultiSign.execute` is not caught by an inner try/catch (unlike `BatchValidateSign`, which wraps `doExecute` in try/catch and downgrades failures to a zero result — see `execute` at lines 1144-1154). If such an exception propagates out of the VM's precompiled-contract dispatch without being caught at a higher layer, it could cause inconsistent execution/energy accounting or node instability during transaction processing on nodes running consensus code that hasn't activated the TIP-854 guard (`allowTvmOsaka`). Where the guard is active, it is a compatibility/DoS-of-availability concern only for chains still pre-fork.

### Likelihood Explanation
Any account can trigger this by deploying a small contract that calls the precompile address (`0x...9` or `0x...a`) with crafted calldata, or by crafting calldata directly if invoked via `staticcall`, since `BatchValidateSign`/`ValidateMultiSign` are ordinary precompile addresses reachable from any signed transaction that triggers VM execution. Reaching the vulnerable pre-guard state requires the network to not yet have activated `allowTvmOsaka`; on chains where it's activated, `isValidAbiEncoding` mitigates most malformed shapes although it does not fully validate every per-item offset used by `extractBytesArray`/`extractSigArray`.

### Recommendation
Add explicit bounds checks in `extractBytesArray`, `extractSigArray`, and `extractBytes32Array` validating that `offset + i + 1 < words.length`, that computed `bytesOffset`/`bytesLen` keep the final byte range within `data.length`, and that `len` is non-negative and within a sane maximum, independent of the `allowTvmOsaka` config gate, so the fix applies unconditionally rather than only post-fork.

### Proof of Concept
1. Construct calldata for `ValidateMultiSign` (`validatemultisign(address,uint256,bytes32,bytes[])`) where the offset word (`words[3]`) or an inner array-item offset word points near/at the end of the `words` array such that `bytesOffset + offset + 2` computed in `extractBytesArray` times `WORD_SIZE`, plus a large `bytesLen` read from another attacker-controlled word, exceeds `data.length`.
2. Invoke this precompile (address `0x000...a`) from a deployed contract via a plain call in a broadcast transaction, on a chain/test environment where `VMConfig.allowTvmOsaka()`/`allowTvmSelfdestructRestriction()` guards are disabled (pre-activation state), matching `testTip854PreActivationNoOp` in `ValidateMultiSignContractTest.java` (lines 244-260), which already documents that "decoder may throw" as pre-activation behavior.
3. Observe an uncaught `RuntimeException` (e.g., `ArrayIndexOutOfBoundsException`) surfacing from `Arrays.copyOfRange` in `extractBytes`, since `ValidateMultiSign.execute` has no surrounding try/catch for this failure mode (unlike `BatchValidateSign`).

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
