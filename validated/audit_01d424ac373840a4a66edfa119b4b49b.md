Based on the investigation, I found a genuine analog to the "unchecked return value causing silent failure to be treated as success" bug class, located in the eth-implicit wallet contract's meta-transaction relay/refund logic.

### Title
Relayer fee is unconditionally paid before the underlying transfer action is known to succeed - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The Solidity report warns that failing to check a transfer's success (return value) before treating it as complete allows funds to move (or fees to be paid) based on an operation that actually failed. In the NEAR eth-implicit wallet contract, `inner_rlp_execute` pays the relayer's fee via an independent `promise_batch_create`/`promise_batch_action_transfer` immediately when parsing an `EOABaseTokenTransfer` or `ERC20Transfer`, before the actual transfer/ERC-20 promise chain (`action_to_promise` / the `storage_balance_of` → `storage_deposit` → `ft_transfer` chain) has even been dispatched, let alone resolved.

### Finding Description
In `inner_rlp_execute` [1](#0-0) , once the RLP transaction is parsed into an `EOABaseTokenTransfer` or `ERC20Transfer` action with a non-zero `fee`, the code immediately builds a **separate** promise batch (`env::promise_batch_create(&context.predecessor_account_id)` + `env::promise_batch_action_transfer(refund_promise, *fee)`) that pays the relayer directly from the wallet contract's own NEAR balance. This happens unconditionally and is dispatched independently of — and prior to — the promise that actually performs the base-token transfer or the `storage_balance_of`/`storage_deposit`/`ft_transfer` chain built later in the same function [2](#0-1) .

Because the fee-payment promise and the transfer-action promise are two independent receipts (not chained with `.then()`), the success or failure of the transfer action has no bearing on whether the fee is paid — there is no check of the transfer's `PromiseResult` before the fee is disbursed. This mirrors the ERC20 report's core concern: a caller (here, the wallet contract) commits value (the fee payment) without verifying that the "transfer" it is paying for actually succeeded.

The code comments in the same function acknowledge this exact risk ("Users should always verify the fee before signing a base token transfer. Relayers should also verify the fee before sending...") [3](#0-2) , showing the developers are aware fee payment is decoupled from transfer success, but the mitigation relies entirely on off-chain diligence rather than an on-chain success check.

### Impact Explanation
A relayer (or a relayer colluding with anyone able to make the token/base transfer fail, e.g. by front-running to drain the sender's token balance or by broadcasting a transaction that is known/engineered to fail after the fee is signed) can collect the fee from the user's wallet contract balance even though the intended transfer never completes. This is a direct loss of funds (the fee) from the wallet owner's account with no corresponding value delivered, since fee payment is not gated on the outcome of the transfer it is meant to compensate.

### Likelihood Explanation
Exploitation requires a relayer to submit a signed transaction whose underlying action is known to fail (e.g., insufficient token balance at execution time due to a race, or a targeted `ERC20Transfer` to a token contract that will reject the call) while the `fee` is still non-zero and payable. Since the fee is signed as part of the RLP transaction by the wallet owner and the relayer chooses when to submit it, a malicious or opportunistic relayer has a reliable way to trigger this outcome deliberately (e.g., waiting until the user's token balance is insufficient, then submitting the tx anyway to collect the fee).

### Recommendation
Chain the fee-payment transfer after the outcome of the primary transfer/ERC-20 action is known (e.g., pay the fee only inside `rlp_execute_callback`/`nep_141_storage_balance_callback` after observing `PromiseResult::Successful`), rather than dispatching it as an independent, unconditional promise in `inner_rlp_execute`.

### Proof of Concept
1. Wallet owner signs an RLP `ERC20Transfer` transaction with a non-zero relayer `fee`, intending to send `token X` to `receiver`.
2. Before submitting, the wallet's `token X` balance is reduced to below the transfer amount (e.g. via a prior/racing transfer).
3. Relayer submits the signed transaction anyway via `rlp_execute`.
4. `inner_rlp_execute` immediately creates and dispatches the fee-transfer promise to the relayer's account [4](#0-3) , deducting `fee` from the wallet contract's NEAR balance.
5. The subsequent `storage_balance_of`/`ft_transfer` promise chain fails (insufficient token balance), and `rlp_execute_callback`/`nep_141_storage_balance_callback` report `success: false` — but the fee has already been paid to the relayer regardless.

            // create a promise to send the refund to the relayer. This allows any relayer
            // to safely serve base token transfers from any wallet without additional
            // on-boarding because the relayer will receive some compensation for sending
            // the transaction. Users should always verify the fee before signing a base token
            // transfer. Relayers should also verify the fee before sending to make sure the
            // user's signed transaction will refund enough to cover the relayer's gas costs.
            if let TransactionKind::EthEmulation(EthEmulationKind::EOABaseTokenTransfer {
                fee,
                ..
            })
            | TransactionKind::EthEmulation(EthEmulationKind::ERC20Transfer { fee, .. }) =
                &transaction_kind
            {
                if !fee.is_zero() && context.predecessor_account_id != context.current_account_id {
                    let refund_promise = env::promise_batch_create(&context.predecessor_account_id);
                    env::promise_batch_action_transfer(refund_promise, *fee);
                }
            }
