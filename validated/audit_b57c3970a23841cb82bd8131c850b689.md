This looks promising — checking `updateTokenSpeed` / `_updateTokenIndex` to confirm the index initialization path.### Title
Uninitialized `accountIndexOf` credits `balance * INITIAL_INDEX` rewards when token index equals `INITIAL_INDEX` - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
`RewardsDistributor._calculateTokenDelta` treats a missing (zero) account index as `INITIAL_INDEX` only when the global token index is strictly greater than `INITIAL_INDEX`. When the token index is exactly `INITIAL_INDEX`, a zero account index is used verbatim, producing `_deltaIndex = INITIAL_INDEX` and `_tokensDelta = balance * 1e18`, letting an attacker drain the distributor's entire reward-token balance in one call.

### Finding Description
The bug-class analog of CVE-2017-5401 (a logic error referencing unassigned memory) is an unassigned storage slot: `accountIndexOf[token][account]` defaults to `0` for accounts that never had their index checkpointed (e.g., deposit-token holders before rewards were enabled for that token). [1](#0-0) 

```solidity
_tokenIndex = _tokenState.index;
uint256 _accountIndex = accountIndexOf[token_][account_];

if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}

uint256 _deltaIndex = _tokenIndex - _accountIndex;
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
```

When a token is first added via `_updateTokenSpeed`, its `TokenState` is initialized to `index = INITIAL_INDEX` with `timestamp = block.timestamp`: [2](#0-1) 

If `_calculateTokenIndex` runs in the same block (`_deltaTimestamps == 0`) — or whenever `speed > 0` has not yet accrued — `_tokenIndex` remains exactly `INITIAL_INDEX`. The guard `_tokenIndex > INITIAL_INDEX` is false, so `_accountIndex` stays `0`, and the attacker is credited:

`_tokensDelta = balance * 1e18` (wad-mul cancels out to `balance` times a factor of 1e18 scaled... i.e., an astronomically inflated accrual, capped only by the distributor's `rewardToken` balance at claim).

Both `updateBeforeMintOrBurn(token, account)` (callable by anyone, per its own docstring) and `claimRewards(accounts, tokens)` are public, unprivileged entry points: [3](#0-2) [4](#0-3) 

`_transferRewardIfEnoughTokens` then transfers `min(accrued, contract balance)` — i.e., the entire reward balance — to the attacker. [5](#0-4) 

### Impact Explanation
Direct theft of all unclaimed yield: the full `rewardToken` (e.g., MET) balance held by the `RewardsDistributor` is transferred to the attacker, destroying other users' accrued-but-unclaimed rewards. No privileged role, oracle, or governance action by the attacker is required.

### Likelihood Explanation
The exploit window is the block in which the governor (or `tokenSpeedKeeper` via `syncTokenSpeed`) first sets a nonzero speed for a token while `tokenStates[token].index == 0`, or any period where speed was set but no timestamp delta has elapsed so the index still equals `INITIAL_INDEX`. An attacker who already holds the tracked `DepositToken`/`DebtToken` — or who front-runs the `updateTokenSpeed` transaction with a flash-loan-funded `Pool.deposit` to obtain DepositTokens in the same block — can call `updateBeforeMintOrBurn` then `claimRewards` atomically in the same transaction. Since `updateBeforeMintOrBurn` is permissionless, no transaction ordering beyond "after the speed-setting tx in the same block" is needed, which is straightforward with standard block-building/flashbots techniques. The same bug also hits honest pre-existing holders the first time their index is lazily initialized while `index == INITIAL_INDEX`, but exploitation requires no privileged actor.

### Recommendation
Treat a zero account index as `INITIAL_INDEX` unconditionally (change `>` to `>=`, or simply `if (_accountIndex == 0) _accountIndex = _tokenIndex < INITIAL_INDEX ? _tokenIndex : INITIAL_INDEX;`), and/or eagerly set `accountIndexOf` for accounts at the moment the token is added. Additionally, when `_updateTokenSpeed` initializes `TokenState`, consider iterating or otherwise ensuring that existing holders cannot claim index `1e18` deltas.

### Proof of Concept
Hardhat fork scenario (pseudocode against deployed mainnet pool):

```ts
// Pre-conditions (fork): RewardsDistributor deployed, rewardToken funded.
// 1. Attacker flash-borrows underlying, deposits into Pool -> receives DepositToken msX
//    (accountIndexOf[msX][attacker] == 0 because rewards not yet enabled for msX).
// 2. Governor tx: rewardsDistributor.updateTokenSpeed(msX, speed) lands earlier in same block
//    -> tokenStates[msX] = {index: 1e18, timestamp: now}.
// 3. Attacker (same block):
await rewardsDistributor.updateBeforeMintOrBurn(msX.address, attacker.address);
//    _calculateTokenDelta: tokenIndex == INITIAL_INDEX, accountIndex == 0
//    -> tokensDelta = balance.wadMul(1e18) (huge)
await rewardsDistributor.claimRewards(attacker.address, [msX.address]);
//    _transferRewardIfEnoughTokens pays out the distributor's entire rewardToken balance.
// 4. Sell reward tokens, repay flash loan, keep profit.
```

The same effect is reproducible in unit tests with smock (mirroring `test/RewardDistributor.test.ts`): set `tokenStates` via `updateTokenSpeed` with `balanceOf` nonzero and `accountIndexOf == 0`, advance zero blocks, then call `updateBeforeMintOrBurn` and observe `tokensAccruedOf == balance * 1e18`.
