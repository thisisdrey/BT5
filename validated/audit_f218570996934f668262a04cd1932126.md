### Title
Unauthenticated relay trigger in `RPCPostBlockRequestHandler::try_handle_request` — `set_relay_message` fires on acceptance regardless of `broadcast`/auth - ([File: stackslib/src/net/api/postblock_v3.rs])

### Summary
The `broadcast=1` auth gate in `try_parse_request` only protects the value stored in `self.broadcast`, but that flag is never consulted when deciding whether to relay the block to the rest of the network. `try_handle_request` calls `node.set_relay_message(...)` solely based on `data_resp.accepted`, so any request that causes the block to be accepted by chainstate — authenticated or not, `broadcast=1` or not — results in the node queuing the block for network-wide relay.

### Finding Description
`try_parse_request` correctly rejects `broadcast=1` from unauthenticated callers: [1](#0-0) 

However, in `try_handle_request`, the flag `self.broadcast` is passed into `Relayer::process_new_nakamoto_block_ext` (affecting only chainstate-side processing/obtain-method bookkeeping), while the actual decision to relay the block to peers is made independently, gated only on `data_resp.accepted`: [2](#0-1) 

There is no check of `self.broadcast` (or `authenticated`) at this call site. Consequently:
1. An attacker (or anyone) posts a valid, already-signed Nakamoto block via `POST /v3/blocks/upload/` with no `broadcast` query param and no `authorization` header.
2. `try_parse_request` accepts it (no auth required since `broadcast` defaults to `false`).
3. `try_handle_request` processes the block; if chainstate accepts it (`accepted.is_accepted()` true — e.g., it's a valid, signer-approved block that just hasn't propagated to this node yet), `data_resp.accepted` is `true`.
4. `node.set_relay_message(StacksMessageType::NakamotoBlocks(...))` fires unconditionally, queuing the block for relay to the P2P network — with no authentication and independent of the `broadcast` flag/secret.

This directly confirms the attacker's hypothesis in the two-step scenario as well: after an authenticated `broadcast=1` upload accepts the block, a second unauthenticated `broadcast=0` submission of the identical bytes will again be evaluated for acceptance (chainstate-level idempotent accept-check returns `accepted=true` for an already-known-valid block) and will again reach the unconditional `set_relay_message` call — a relay path that never required the secret.

### Impact Explanation
This breaks the intended access control: the `authorization` secret is supposed to gate whether the node relays operator-submitted blocks to the network (broadcast=1 path), but the enforcement point (`set_relay_message`) never checks it. Any remote, unauthenticated party who can reach the RPC port and possesses (or can obtain by any means, including sniffing/observing p2p gossip) a validly-signed Nakamoto block bytes can force the node to relay it via the "trusted operator upload" mechanism without the secret — an authentication/authorization bypass on a relay-triggering code path. This matches the Critical category "network-wide propagation of forged/unauthorized data ... auth bypass."

Note: this does not let an attacker forge an invalid block — chainstate/consensus validation of the block itself (signer signatures, etc.) still applies via `process_new_nakamoto_block_ext`'s acceptance logic. The vulnerability is specifically that the `broadcast`-gated authorization is decorative and does not actually control relay, defeating its purpose.

### Likelihood Explanation
- Preconditions: auth (`self.auth`) configured on the node's RPC endpoint; attacker has a validly-signed Nakamoto block (either self-observed via gossip, or replaying one they previously uploaded with the secret, or observed from any peer).
- Attacker cost: trivial — one unauthenticated HTTP POST to `/v3/blocks/upload/` with no query string and no auth header.
- Remote reachability: yes, this is a standard RPC endpoint reachable by any peer/client that can connect to the node's RPC port.
- Repeatable: yes, for every valid block the attacker can obtain.

### Recommendation
Gate the `node.set_relay_message(...)` call on `self.broadcast.unwrap_or(false)` (and, by extension, on `authenticated`), not merely on `data_resp.accepted`, e.g.:
```rust
if data_resp.accepted && self.broadcast.unwrap_or(false) {
    node.set_relay_message(...);
}
```
This restores the intended semantics that only authenticated `broadcast=1` requests cause network relay.
