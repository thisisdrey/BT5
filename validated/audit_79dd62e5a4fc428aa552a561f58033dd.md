### Title
Unauthenticated handshake-stage-1 flooding creates unbounded pending-handshake state with no per-packet cap, enabling a remote resource-exhaustion DoS - ([File: handshake_manager.go])

### Summary
The reported Fenwick-tree bug is a griefing/DoS pattern: a capacity-limited, per-account tracking structure can be filled by an unauthorized caller because the code never validates who is allowed to add an entry, eventually starving legitimate future entries. The closest reachable analog in this codebase is `HandshakeManager.HandleIncoming`, which allocates a brand-new pending-handshake record (`HandshakeHostInfo`) and a random `localIndexId` for *every* inbound stage-1 packet, before any certificate/identity verification has occurred and with no cap on the number of concurrently pending entries.

### Finding Description
`HandshakeManager.HandleIncoming` gates only on message subtype and the remote allow list, then for any packet with `MessageCounter == 1` and `RemoteIndex == 0` unconditionally calls `hm.beginHandshake(via, packet, h)`: [1](#0-0) 

`beginHandshake` (invoked here) creates a new `HandshakeHostInfo`/`HostInfo` pair and registers it via `allocateIndex`, which inserts the entry into `hm.indexes` keyed by a freshly generated random 32-bit index: [2](#0-1) 

Unlike the deposit-count cap in the reported bug (`maxDepositEntries`) or the explicit `maxCachedPackets = 100` cap already applied elsewhere in this same file for per-handshake packet buffering: [3](#0-2) [4](#0-3) 

there is no analogous cap on the *number of pending handshake entries* that can be created in `hm.vpnIps` / `hm.indexes`. Every spoofed or replayed stage-1 UDP packet — which requires no CA-signed certificate at all, since certificates are only exchanged/verified later in the Noise handshake — allocates a new `HandshakeHostInfo`, a new `HostInfo`, and a new random index entry that persists until the outbound retry/timeout logic (`NextOutboundHandshakeTimerTick` / `handleOutbound`, driven by `hm.config.retries`) eventually expires it. An attacker who sends packets faster than this expiry can keep growing `hm.indexes` and `hm.vpnIps` without bound, exactly mirroring the reported pattern of an unauthorized caller filling a shared, capacity-relevant structure to deny legitimate use — except here the "cap" is memory/CPU rather than an explicit array size, so the eventual outcome is resource exhaustion/crash rather than a revert.

### Impact Explanation
Sustained flooding of unauthenticated stage-1 handshake packets can exhaust memory/CPU on the receiving node (each entry allocates a `HostInfo`, a `HandshakeHostInfo`, and machinery state), degrading or crashing the node and denying legitimate peers the ability to establish or maintain tunnels — a remote crash / DoS impact reachable by any off-path or on-path attacker with no valid CA-signed certificate, matching the accepted "remote crash impact" category.

### Likelihood Explanation
Likelihood is Medium: the attack requires no cryptographic material and no valid certificate — only the ability to send UDP packets to the node's listening port that pass the (default permissive) `remote_allow_list`. The main mitigating factor is that entries are eventually reaped by the outbound handshake timeout/retry accounting, so a sustained, sufficiently fast flood is needed to keep memory pressure ahead of reaping.

### Recommendation
Add an explicit upper bound on the number of concurrently pending (unauthenticated) handshake entries in `HandshakeManager` (mirroring the `maxCachedPackets` pattern already used for packet buffering), and/or apply per-source-address rate limiting on stage-1 packet processing in `HandleIncoming` before allocating any `HandshakeHostInfo`/index state, so unauthenticated senders cannot grow this state without bound.

### Proof of Concept
1. From an attacker-controlled host with no Nebula CA-issued certificate, craft raw UDP packets matching the Nebula header for `header.Handshake` / `header.HandshakeIXPSK0`, with `MessageCounter = 1` and `RemoteIndex = 0`, and arbitrary/garbage Noise payloads.
2. Send a high volume of such packets, each with different payload bytes, to the victim's listening UDP port.
3. Each packet reaches `HandshakeManager.HandleIncoming` → `beginHandshake` → `allocateIndex`, inserting a new entry into `hm.indexes`/`hm.vpnIps` before any certificate is verified.
4. Repeat faster than the retry/timeout reaping cycle (`DefaultHandshakeRetries` × `DefaultHandshakeTryInterval`) to accumulate unbounded pending state, driving memory/CPU exhaustion on the target node.

func (hh *HandshakeHostInfo) cachePacket(l *slog.Logger, t header.MessageType, st header.MessageSubType, packet []byte, f packetCallback, m *cachedPacketMetrics) {
	if len(hh.packetStore) < maxCachedPackets {
		tempPacket := make([]byte, len(packet))
		copy(tempPacket, packet)

		hh.packetStore = append(hh.packetStore, &cachedPacket{t, st, f, tempPacket})
		if l.Enabled(context.Background(), slog.LevelDebug) {
			hh.hostinfo.logger(l).Debug("Packet store",
				"length", len(hh.packetStore),
				"stored", true,
			)
		}

	} else {
		m.dropped.Inc(1)

		if l.Enabled(context.Background(), slog.LevelDebug) {
			hh.hostinfo.logger(l).Debug("Packet store",
				"length", len(hh.packetStore),
				"stored", false,
			)
		}
	}
}

// allocateIndex generates a unique localIndexId for this HostInfo
// and adds it to the pendingHostMap. Will error if we are unable to generate
// a unique localIndexId
func (hm *HandshakeManager) allocateIndex(hh *HandshakeHostInfo) (uint32, error) {
	hm.mainHostMap.RLock()
	defer hm.mainHostMap.RUnlock()
	hm.Lock()
	defer hm.Unlock()

	for range 32 {
		index, err := generateIndex(hm.l)
		if err != nil {
			return 0, err
		}

		_, inPending := hm.indexes[index]
		_, inMain := hm.mainHostMap.Indexes[index]

		if !inMain && !inPending {
			hh.hostinfo.localIndexId = index
			hm.indexes[index] = hh
			return index, nil
		}
	}

	return 0, errors.New("failed to generate unique localIndexId")
}
