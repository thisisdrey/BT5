### Title
Reference (`==`) comparison of `ByteString` addresses in `BandwidthProcessor.useAssetAccountNet` makes the asset-issuer bandwidth exemption unreachable, corrupting free-bandwidth accounting for TRC10 assets - (File: `chainbase/src/main/java/org/tron/core/db/BandwidthProcessor.java`)

### Summary
The external report describes a bug where a condition meant to grant a fee exemption ("naming should be free while curated/hold-farming") never actually short-circuits the payment logic, so the exemption is silently dead code. The same root-cause pattern — a boolean condition intended to trigger special (bypass) accounting that can never evaluate `true` due to an incorrect equality check — exists in java-tron's TRC10 bandwidth-billing path, `BandwidthProcessor.useAssetAccountNet`.

### Finding Description
In `useAssetAccountNet`, the method is supposed to detect when the asset transfer's `ownerAddress` account is itself the issuer of the asset and, in that case, let the issuer's transfer be billed against the issuer's own regular bandwidth (`useAccountNet`) rather than being metered against the asset's shared "public free" and "free-asset" bandwidth pools: [1](#0-0) 

The comparison `assetIssueCapsule.getOwnerAddress() == accountCapsule.getAddress()` compares two `com.google.protobuf.ByteString` object references with Java's `==` operator instead of using `.equals()` (or comparing the underlying byte arrays). `ByteString` instances returned from `AssetIssueCapsule`/`AccountCapsule` (which are deserialized independently from the `AssetIssueStore`/`AccountStore`) are essentially never the same object instance even when they encode the identical address, so this branch is effectively unreachable dead code — the "is-issuer" fast path is never taken.

As a consequence, every `TransferAssetContract` broadcast by the asset issuer for their own token falls through into the shared accounting path that consumes `publicFreeAssetNetUsage` and `freeAssetNetUsage` (the pools meant to be shared fairly across *all* holders of the asset) and also consumes the issuer's own `netUsage` a second time via `issuerAccountCapsule` bookkeeping at lines 355-396: [2](#0-1) [3](#0-2) 

This means any unprivileged asset issuer, simply by repeatedly self-transferring or otherwise sending their own asset, can exhaust the asset's shared `publicFreeAssetNetLimit`/`freeAssetNetLimit` pool that is documented/intended to be available to ordinary token holders, since the intended bypass that should keep issuer traffic out of that shared pool never activates.

### Impact Explanation
The shared free-bandwidth pools (`publicFreeAssetNetLimit`, `freeAssetNetLimit`) configured by an asset issuer via `UpdateAssetActuator`/`AssetIssueActuator` are a resource guarantee advertised to all holders of a TRC10 token. Because the issuer-exemption check can never be satisfied, the issuer's own transactions consume from this same finite, block/day-scoped pool, allowing the pool to be exhausted by the party least expected to compete for it (the issuer itself), denying legitimate holders the free-bandwidth benefit the asset issuer configured — a functional resource-accounting integrity break in a path reachable purely by broadcasting standard `TransferAssetContract` transactions.

### Likelihood Explanation
Any account that has issued a TRC10 asset (freely obtainable via `AssetIssueActuator`, cost is just the standard asset-issue fee) can trigger this on every subsequent `TransferAssetContract` it sends for that asset — no special privilege beyond being the asset owner is required, and the flawed comparison is hit unconditionally on this common code path.

### Recommendation
Replace the reference comparison with a content-based comparison, e.g. `assetIssueCapsule.getOwnerAddress().equals(accountCapsule.getAddress())`, so the intended issuer bypass branch actually activates and issuer traffic is billed against the issuer's own bandwidth instead of the shared free-asset pools.

### Proof of Concept
1. Account `A` issues asset `X` via `AssetIssueActuator`, configuring `freeAssetNetLimit`/`publicFreeAssetNetLimit`.
2. Account `A` repeatedly broadcasts `TransferAssetContract` moving asset `X` to any other address (or another holder account it controls).
3. In `BandwidthProcessor.consume` → `useAssetAccountNet`, since `assetIssueCapsule.getOwnerAddress() == accountCapsule.getAddress()` is always `false` for independently-deserialized `ByteString`s, the method never takes the `useAccountNet(accountCapsule, ...)` short-circuit at line 314.
4. Each of `A`'s transfers instead decrements `publicFreeAssetNetUsage`/`freeAssetNetUsage` shared by all token holders, exhausting the free-bandwidth quota meant for other holders even though the operation is conceptually the issuer's own traffic. [4](#0-3)

    }

    String tokenName = ByteArray.toStr(assetName.toByteArray());

              + " Bytes: {}, publicFreeAssetNetLimit: {}, newPublicFreeAssetNetUsage: {}.",
          tokenID, bytes, publicFreeAssetNetLimit,  newPublicFreeAssetNetUsage);
      return false;
    }
