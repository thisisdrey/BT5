## Title
Cross-contract StackerDB chunk signature replay — signature omits contract/StackerDB identity - ([File: libstackerdb/src/libstackerdb.rs])

### Summary
`SlotMetadata::auth_digest()` in `libstackerdb/src/libstackerdb.rs` binds a chunk signature to only `(slot_id, slot_version, data_hash)` and never to the StackerDB's `smart_contract_id`. Because the Stacks signer-set boot contracts (`signers-{set}-{message_id}`) intentionally assign the *same* signer address to the *same* `slot_id` across every `message_id` StackerDB contract in a set, a chunk that a signer legitimately signs and posts for one message-type contract is a valid, verifiable chunk for every other message-type contract that shares that slot assignment. A remote, unprivileged peer can therefore replay an observed, validly-signed chunk from contract A into contract B without knowing any private key, corrupting the target StackerDB with data that appears authentically signed.

### Finding Description
`SlotMetadata::auth_digest()` computes: [1](#0-0) 

and `SlotMetadata::verify()` only checks that this digest recovers to the expected principal: [2](#0-1) 

The contract/StackerDB identity is never part of what is signed. It is only used *externally* to look up which signer address is expected to own a given `slot_id`, both in the write path: [3](#0-2) 

and in the p2p-received-chunk validation path: [4](#0-3) 

The `.signers` boot contract deliberately assigns identical slot lists to every message-id contract within a signer set — `stackerdb-get-signer-slots-page` returns the same list regardless of which `signers-{set}-{message_id}` contract calls it: [5](#0-4) [6](#0-5) 

This is confirmed by the test that asserts the identical signer-slot list is returned for every `message_id` in `0..SIGNER_SLOTS_PER_USER`: [7](#0-6) 

Consequently, the same private key controls the identical `slot_id` in multiple distinct StackerDB contracts (e.g. `signers-1-0` for block responses, `signers-1-1` for transactions, etc., however `MessageSlotID` is enumerated). Since the signature never commits to the contract identity, an unprivileged network observer can capture a validly-signed `StackerDBChunkData` broadcast/posted for contract A and re-submit the exact same bytes (slot_id, slot_version, sig, data) to contract B's `/v2/stackerdb/<contract-B>/chunks` endpoint or replay it over the p2p `StackerDBPushChunk`/download path. `try_replace_chunk` for contract B will resolve the same signer address for that slot (`get_slot_validation`), `slot_desc.verify()` will succeed (digest is contract-agnostic), and — provided B's current slot version is below the replayed version — the chunk will be accepted and stored as authentic content for contract B, even though it was never signed for B and the attacker never possessed any private key.

This breaks the same equality class flagged in the external report: the value that is cryptographically authenticated ("signed for slot X, version V, hash H") does not equal the value that is actually being stored/trusted ("chunk belongs to StackerDB contract B"). The missing binding is directly analogous to the missing `listingId` in the audited blind-auction hash — here it is a missing `contract_id`/`smart_contract_id` binding in the StackerDB chunk-authentication digest.

### Impact Explanation
This allows an unauthenticated, remote attacker (no private key, no admin role) to inject data into a StackerDB contract that other nodes/signers treat as authentically signed by a legitimate signer, by replaying already-observed valid chunks across sibling message-type contracts that share slot assignments. Depending on which message-type StackerDB is targeted (e.g. signer block-response vs. transaction-replay contracts), this can corrupt signer state consumed by miners/signers, be propagated network-wide via the normal chunk-push/gossip and download-sync paths, and mislead nodes into trusting attacker-selected stale/cross-context content as canonical for a different message channel. This matches "unauthenticated/unauthorized write to state or StackerDB" and "network-wide propagation of forged data".

### Likelihood Explanation
Exploitation requires no secret material — only observation of one legitimately broadcast chunk (which is by design publicly gossiped/stored) and reposting it against a different, sibling StackerDB contract endpoint that shares the same signer/slot assignment and has an acceptable (lower) current version. Given the boot-contract design guarantees identical slot assignment across all `signers-{set}-*` message-id contracts, the precondition is met by default in normal network operation, making this a real cross-contract replay rather than a purely theoretical scenario.

### Recommendation
Include the StackerDB's `smart_contract_id` (and ideally the signer-set/reward-cycle identifier) as part of `SlotMetadata::auth_digest()` so that a signature is only valid for the specific StackerDB contract it was produced for. This mirrors the fix pattern from the referenced report (adding `listingId` to the hash to prevent cross-listing replay): binding the digest to contract identity prevents any cross-contract chunk replay regardless of shared slot/signer assignments.

### Proof of Concept
1. Signer `S` owns `slot_id = 5` in both `signers-1-0` (message type: block response) and `signers-1-3` (message type: some other message) — guaranteed by `signers.clar`'s shared `stackerdb-get-signer-slots-page`.
2. `S` legitimately signs and posts `StackerDBChunkData { slot_id: 5, slot_version: 1, sig, data }` to `signers-1-0`; this chunk propagates via `StackerDBPushChunk`/`StackerDBChunkInv` gossip.
3. An attacker with no private key captures this chunk and POSTs the identical bytes to `/v2/stackerdb/<signers-1-3-contract>/chunks` (or replays it into a peer's p2p StackerDB sync for `signers-1-3`).
4. `try_replace_chunk`/`validate_received_chunk` resolve `get_slot_validation`/`get_slot_signer` for `signers-1-3`, find `S` owns slot 5 there too, call `slot_desc.verify(&S)` which succeeds because the digest never referenced the contract, and — if `signers-1-3`'s current version for slot 5 is `< 1` — the chunk is accepted and stored as valid content for `signers-1-3`, despite `S` never signing anything for that contract.

    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }

        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
