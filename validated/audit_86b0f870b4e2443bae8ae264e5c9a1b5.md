## Title
Unbounded array allocation from unvalidated length word in TVM precompiled contract ABI decoding leads to memory-exhaustion crash - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`PrecompiledContracts.extractBytes32Array`, `extractBytesArray`, and `extractSigArray` decode a dynamic array length directly from attacker-supplied calldata and immediately allocate a Java array of that size, with no check that the declared length is consistent with the actual size of the supplied `data` buffer. [1](#0-0) [2](#0-1) [3](#0-2) 

This mirrors the CVE-2016-9376 bug class: a length field taken from untrusted network/message data drove a memory allocation without verifying it was "sufficiently" bounded to the actual payload, causing memory exhaustion. Here the equivalent length field is a 256-bit ABI word (`words[offset]`) fully controlled by whoever crafts the TVM call data to one of these precompiled contracts.

### Finding Description
Each of the three helper methods reads a single word from the ABI-decoded `words` array and converts it with `DataWord.intValueSafe()`, then allocates a `byte[][]` of that exact size before performing any per-element bounds validation against the true length of `data`:
- `extractBytes32Array` allocates `new byte[len][]` where `len = words[offset].intValueSafe()` with no upper bound check.
- `extractBytesArray` and `extractSigArray` behave the same way, additionally deriving per-element offsets from further attacker-controlled words.

There is no comparison of `len` to `words.length`, `data.length`, or any hard cap before the allocation happens. Because the length word is an arbitrary 256-bit value coerced by `intValueSafe()`, an attacker can set it to a very large positive `int` (up to `Integer.MAX_VALUE`) while supplying only a small amount of actual calldata (the rest of the "array" never needs to exist because the loop that reads per-element data will throw only after the allocation has already succeeded or failed). This is architecturally identical to the Wireshark OpenFlow dissector bug: a length header value from the message is trusted for allocation sizing before being checked against how much data is actually present.

This differs from the TVM opcode-level memory metering path (`Memory.extend`, `EnergyCost.checkMemorySize`), which does defend against oversized `newMemSize` via `BigInteger` overflow checks and `Program.OutOfMemoryException` as shown in the vote-witness cost tests. [4](#0-3) [5](#0-4) 
That protection applies to VM memory-expansion gas accounting, not to these precompiled-contract ABI decoding helpers, which perform a raw `new byte[len][]` allocation with no equivalent guard.

### Impact Explanation
A crafted transaction that calls a precompiled contract address whose `execute()` path uses `extractBytes32Array`/`extractBytesArray`/`extractSigArray` can force the node to attempt an allocation on the order of `Integer.MAX_VALUE` array-reference slots (multi-gigabyte on a 64-bit JVM). This throws `OutOfMemoryError`, which is not a checked exception normally caught along the actuator's execution path, risking a node crash or JVM-wide memory pressure that can degrade or halt block processing — a concrete node crash/halt impact, reachable by any unprivileged transaction sender able to invoke a TVM contract that calls the affected precompiled address.

### Likelihood Explanation
Likelihood is high for any caller who can submit a `TriggerSmartContract` transaction targeting a precompiled address that uses one of these helpers: the attacker only needs to control the calldata word at the declared array-length offset, which is a single 32-byte ABI word — no special privileges, signatures, or preconditions beyond normal transaction broadcasting are required.

### Recommendation
Add an explicit sanity bound on the decoded `len` in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` before allocation — e.g., reject if `len` is negative, exceeds `Integer.MAX_VALUE / elementSize`, or exceeds a small constant bound derived from `data.length` / `words.length` (each array element needs at least one word of backing data), throwing a normal validation exception instead of allocating first and discovering failure afterward.

Because I could not confirm within the indexed codebase exactly which precompiled contract dispatches to `extractBytes32Array`/`extractBytesArray`/`extractSigArray` (the call sites were not present in the search index available to me), I cannot provide a fully concrete end-to-end transaction PoC with the exact contract address/selector. Conceptually, the PoC is: craft ABI calldata for the affected precompile where the word at the expected "array length" offset is set to a very large value (e.g., `0x7fffffff`) while the actual calldata is only a few words long, then invoke the precompiled contract via `TriggerSmartContract`; `words[offset].intValueSafe()` returns the large value, and `new byte[len][]` is executed before any per-element data is validated, triggering `OutOfMemoryError`.
