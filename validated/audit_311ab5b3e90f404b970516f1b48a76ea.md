Audit Report

## Title
Discarded `increase_balance` result in `fungibles::Mutate::transfer()` allows silent fund loss while the call reports success - (File: `substrate/frame/support/src/traits/tokens/fungibles/regular.rs`)

## Summary
The default `transfer()` implementation of the `fungibles::Mutate` trait unconditionally debits the source via `decrease_balance` and then calls `increase_balance` on the destination but discards its `Result` with `let _ = ...`, before unconditionally emitting `done_transfer` and returning `Ok(amount)`. Because `can_deposit`/`can_increase` are only advisory pre-checks evaluated before `decrease_balance` mutates storage, and `increase_balance`'s actual mutation (in `pallet_assets::functions::increase_balance`) re-checks conditions such as `AssetStatus::Live` and `TokenError::BelowMinimum` for new accounts at a later point, the destination-side credit can genuinely fail after the source has already been debited.

## Finding Description
`Mutate::transfer` at [1](#0-0)  performs `can_withdraw`/`can_deposit` advisory checks, then calls `Self::decrease_balance(...)?` (propagating errors), but then calls `Self::increase_balance(asset.clone(), dest, amount, BestEffort)` and discards the result with `let _ = ...`, followed unconditionally by `Self::done_transfer(...)` and `Ok(amount)`.

For `pallet_assets`, `Unbalanced::increase_balance` is implemented directly (not via the storage-default) at [2](#0-1) , delegating to the low-level `functions.rs::increase_balance` at [3](#0-2) . That function calls `Self::can_increase(...).into_result()?` and then, inside `Asset::<T, I>::try_mutate`, separately checks `ensure!(details.status == AssetStatus::Live, Error::<T, I>::AssetNotLive)` and, for a not-yet-existing destination account, `ensure!(amount >= details.min_balance, TokenError::BelowMinimum)`, plus a fallible `Self::new_account(...)?` call.

The pre-check `can_deposit` used in `transfer()` maps to `Pallet::<T, I>::can_increase(...)` per [4](#0-3) , which is evaluated before `decrease_balance` runs. Since `can_deposit` and the actual mutation inside `increase_balance` are evaluated at two different points in the same call graph (a TOCTOU window), and the mutation path re-derives `AssetStatus::Live`/`BelowMinimum`/`new_account` outcomes independently, the destination-side credit can fail for reasons the initial `can_deposit` did not conclusively guarantee against. Because `decrease_balance(source, ...)` is gated by `?` and therefore already committed by the time `increase_balance(dest, ...)` runs, an `Err` from the latter is silently swallowed, `done_transfer` still fires the `Transferred` event for the full `amount`, and the caller receives `Ok(amount)`.

This is inconsistent with the same file's `mint_into`/`restore`, which propagate the identical class of `increase_balance` error with `?` at [5](#0-4) .

## Impact Explanation
`fungibles::Mutate::transfer` is a widely reused value-movement primitive for pallets and XCM asset transactors built on `pallet_assets`/`fungibles`. Any caller treating `Ok(amount)` as proof the destination was credited can proceed with downstream effects (crediting a position, marking a deposit as fulfilled) while the destination receives nothing and the debited amount vanishes from circulating balances without a corresponding decrease in `total_issuance` — an unbacked accounting deficit and permanent loss of the debited funds, matching "theft or unbacked mint or unlock" / "value not conserved and settled exactly once" impact classes.

## Likelihood Explanation
Triggering the destination-side failure requires only ordinary public extrinsic/XCM conditions — e.g., a destination account that does not yet exist and cannot satisfy `amount >= details.min_balance`, or an asset whose `AssetStatus` transitions away from `Live` between the initial `can_deposit` check and the later mutation within the same call. No privileged actor, governance, or compromised infrastructure is required.

## Recommendation
Propagate the `increase_balance` error with `?` instead of discarding it, mirroring `mint_into`/`restore`, and use the actually-credited amount for `done_transfer`/return value. If a full rollback is preferred, wrap `decrease_balance` and `increase_balance` in `frame_support::storage::with_transaction` so a failed credit reverts the prior debit.

## Proof of Concept
1. Configure `pallet_assets` so `can_deposit`/`can_increase` passes for a not-yet-existing `dest` account at pre-check time.
2. Call `T::Assets::transfer(asset, source, dest, amount, Preservation::Expendable)` where the actual mutation-time check in `functions.rs::increase_balance` (`amount >= details.min_balance`, `AssetStatus::Live`, or `new_account`) fails for `dest`.
3. Observe `decrease_balance(source, ...)` succeeds and debits `source`.
4. Observe `increase_balance(dest, ...)` returns `Err(...)`, discarded by `let _ = ...`.
5. Observe `done_transfer` still emits `Transferred { amount }` and the call returns `Ok(amount)`, while `source` balance is reduced, `dest` balance is unchanged, and `total_issuance` is unchanged.

	pub(super) fn increase_balance(
		id: T::AssetId,
		beneficiary: &T::AccountId,
		amount: T::Balance,
		check: impl FnOnce(
			&mut AssetDetails<T::Balance, T::AccountId, DepositBalanceOf<T, I>>,
		) -> DispatchResult,
	) -> DispatchResult {
		if amount.is_zero() {
			return Ok(());
		}

		Self::can_increase(id.clone(), beneficiary, amount, true).into_result()?;
		Asset::<T, I>::try_mutate(&id, |maybe_details| -> DispatchResult {
			let details = maybe_details.as_mut().ok_or(Error::<T, I>::Unknown)?;
			ensure!(details.status == AssetStatus::Live, Error::<T, I>::AssetNotLive);
			check(details)?;

			Account::<T, I>::try_mutate(&id, beneficiary, |maybe_account| -> DispatchResult {
				match maybe_account {
					Some(ref mut account) => {
						account.balance.saturating_accrue(amount);
					},
					maybe_account @ None => {
						// Note this should never fail as it's already checked by
						// `can_increase`.
						ensure!(amount >= details.min_balance, TokenError::BelowMinimum);
						*maybe_account = Some(AssetAccountOf::<T, I> {
							balance: amount,
							reason: Self::new_account(beneficiary, details, None)?,
							status: AccountStatus::Liquid,
							extra: T::Extra::default(),
						});
					},
				}
				Ok(())
			})?;
			Ok(())
		})?;
		Ok(())
	}
