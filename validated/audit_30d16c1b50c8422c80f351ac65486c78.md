Based on the analysis, `ProcessCentralDirEntry` in `third_party/ijar/zip.cc` parses each ZIP central directory header's fixed and variable-length fields without any remaining-bytes validation, unlike its sibling `ProcessLocalFileEntry` which calls `EnsureRemaining()` before every read. This is a direct structural analog to the shim MZ out-of-bounds read: a binary header parser trusts attacker-controlled length fields to index into a fixed-size mapped buffer.

### Title
Out-of-bounds read parsing ZIP central directory entries in ijar - (File: third_party/ijar/zip.cc)

### Summary
`InputZipFile::ProcessCentralDirEntry` (used by ijar/singlejar-style consumers of the `third_party/ijar` ZIP reader to process a jar file's/archive's central directory, which is untrusted content fetched or built from external sources) advances a raw pointer `p` through the memory-mapped input file and reads `file_name_length`, `extra_field_length`, and `file_comment_length` directly from attacker-controlled header bytes, then does `memcpy(filename, p, len)` and further pointer arithmetic (`p += file_name_length`, `p += extra_field_length` while walking a zip64 extra-field loop, `p += file_comment_length`) with no check that these advances stay within the memory-mapped file bounds.

### Finding Description
`FindZipCentralDirectory` (third_party/ijar/zip.cc:704-778) validates only that `cd.central_dir_offset + cd.central_dir_size <= in_length` [1](#0-0)  — an aggregate check on the whole central directory region, not a per-entry bound. Individual entries are then parsed by `ProcessCentralDirEntry`, which reads `file_name_length`, `extra_field_length`, `file_comment_length` from the untrusted header and immediately uses them to advance `p` and to `memcpy` from `p` into a fixed `filename[PATH_MAX]` buffer, all without calling any bounds/remaining-length check: [2](#0-1) 

This contrasts with `ProcessLocalFileEntry`, in the same file, which defensively calls `EnsureRemaining()` before reading the file name and extra field: [3](#0-2)  `EnsureRemaining` itself computes `remaining = input_file_->Length() - in_offset` and rejects reads that would exceed the mapped file: [4](#0-3) 

No equivalent check exists in `ProcessCentralDirEntry`. Because the aggregate `central_dir_size` check in `FindZipCentralDirectory` only bounds the *sum* of the central directory region against the file length, a malicious archive can declare consistent aggregate sizes while placing an entry near the end of that region whose own `file_name_length`/`extra_field_length`/`file_comment_length` fields, when actually walked, advance `p` past the end of the memory-mapped buffer — precisely the same class of bug as the shim advisory: fixed-format binary header fields trusted to compute offsets/lengths without validating them against the actual mapped buffer size, producing an out-of-bounds read.

### Impact Explanation
This function is reached whenever ijar's ZIP reader (used to strip interface jars and by tools built on this shared `third_party/ijar` code) processes a jar/zip archive that is not fully trusted — e.g., a jar produced from a third-party dependency, an artifact fetched from a remote repository/mirror, or any archive built from bytes an outside contributor controls in CI. An out-of-bounds read on the memory-mapped input can crash the build process (denial of service) or, depending on what lies adjacent in the memory mapping, leak adjacent heap/mapped-file bytes into the copied `filename` buffer or subsequent processing, which is the same consequence flagged in the CVE-2023-40551 report (crash or possible exposure of sensitive data via an OOB read while parsing an untrusted binary header).

### Likelihood Explanation
The attacker only needs to supply a JAR/ZIP file that is consumed by this code path — no elevated privileges or access to the victim's machine are required, matching the "unprivileged attacker publishing content the build consumes" threat model. Crafting a central directory entry with inflated `file_name_length`/`extra_field_length`/`comment_length` fields near the boundary of the declared `central_dir_size`/file length is straightforward with a hex editor or a small ZIP-crafting script, since `ProcessCentralDirEntry` performs no validation before dereferencing.

### Recommendation
Add an `EnsureRemaining()`-style check inside `ProcessCentralDirEntry` before reading `file_name_length` bytes for the filename, before walking the extra field region, and before skipping `file_comment_length` bytes, mirroring the pattern already used in `ProcessLocalFileEntry`. Additionally, validate that `p` never exceeds `central_dir_ + central_dir_size` (or `zipdata_in_ + in_length`) after each entry is consumed.

### Proof of Concept
A `BuildIntegrationTestCase`/native test analogous to the existing zip tests in `third_party/ijar/test/zip_test.sh` and `third_party/ijar/zip_test.cc`-style harnesses could construct a minimal ZIP file whose EOCD/central-dir-size fields are internally consistent, but whose single central directory entry declares `file_name_length = 0xFFFF` while only a few real bytes remain before the actual end of the mapped file/central directory region, then invoke `ZipExtractor::Create`/`ProcessNext` on it and assert that the process reads/crashes at a page boundary (ASan `heap-buffer-overflow`/`SEGV`) rather than returning a controlled error from `ProcessCentralDirEntry`, in contrast to the already-guarded `ProcessLocalFileEntry` path which returns `-1` under the analogous crafted-length scenario. bool InputZipFile::ProcessCentralDirEntry(const u1 *&p, u8 *compressed_size,
                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
  const u1 *extra_p = p;
  p += extra_field_length;
  while (extra_p != p) {
    const u2 header_id = get_u2le(extra_p);
    const u2 data_size = get_u2le(extra_p);
    const u1 *extra = extra_p;
    extra_p += data_size;
    if (header_id == ZIP64_EXTRA_FIELD_TAG) {
      if (*uncompressed_size == U4_MAX) {
        *uncompressed_size = get_u8le(extra);
      }
      if (*compressed_size == U4_MAX) {
        *compressed_size = get_u8le(extra);
      }
      if (*offset == U4_MAX) {
        *offset = get_u8le(extra);
      }
    }
  }
  p += file_comment_length;
  return true;
}
