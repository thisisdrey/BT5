Audit Report

## Title
XCM `ERC20Transactor` credits/moves the requested `amount` instead of the actual ERC20 balance delta, allowing fee-on-transfer/deflationary tokens to desynchronize the shared checking-account backing - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` call the target ERC20's `transfer()` function and, upon a `true` boolean return, unconditionally treat the full requested `amount` as moved — never reading `balanceOf` before/after to confirm the actual delta. Because `ERC20Matcher`/`IsLocalAccountKey20` accept any local `AccountKey20` contract with no allowlist restricting transfer semantics, an attacker can deploy a fee-on-transfer/deflationary ERC20 that returns `true` while delivering less than `amount`, causing the XCM holding register (on withdraw) or the shared `TransfersCheckingAccount`'s outgoing payouts (on deposit) to be based on a value that exceeds what was actually moved.

## Finding Description
`withdraw_asset_with_surplus` calls `IERC20::transferCall { to: checking_address, value: amount }` and, if the returned boolean is `true`, builds `AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount)))` — crediting the full `amount` into XCM holding regardless of how much the `TransfersCheckingAccount` actually received: [1](#0-0) 

Symmetrically, `deposit_asset_with_surplus` transfers `amount` from the same shared `TransfersCheckingAccount` to the beneficiary and returns success purely based on the boolean transfer result, with no verification that the beneficiary actually received `amount`: [2](#0-1) 

Neither function calls `balanceOf` on the checking account or the beneficiary before/after the transfer; there is no such call anywhere in the file, confirmed by search. The `Erc20Credit` imbalance type itself makes clear this design choice is deliberate but incomplete: its doc comment states "the actual balance constraints are enforced by the ERC20 smart contract itself rather than the runtime" — but this only holds for a token where `transfer(to, amount)` credits exactly `amount` to `to`, which is not guaranteed for non-standard tokens. [3](#0-2) 

The gating matcher, `ERC20Matcher`, only checks that the XCM `Asset` location is a bare local `AccountKey20` junction (`IsLocalAccountKey20`), with no restriction on the token's transfer semantics: [4](#0-3)  This matcher is wired into `ERC20Transactor`, which is included unconditionally in the runtime's `AssetTransactors` tuple: [5](#0-4) 

`TransfersCheckingAccount` (`ERC20TransfersCheckingAccount`, a `PalletId`-derived account) is a single account shared across every ERC20 XCM withdraw/deposit that passes through this transactor instance, so a shortfall created against the checking account by one user's fee-on-transfer withdrawal is effectively backstopped by balance actually contributed by other, unrelated users of the same token. [6](#0-5) 

## Impact Explanation
This violates the invariant that value custodied via public wrappers (here, the ERC20↔XCM bridge on Asset Hub) must conserve value and settle exactly the amount actually moved. Since deploying a `pallet-revive` contract is unprivileged and the matcher/transactor accept it automatically once it exposes `IERC20`, an attacker-controlled deflationary token can cause the XCM engine to believe it holds more value in the shared checking account than actually exists, enabling later withdrawals (by the attacker or anyone) to drain real balance contributed by other users of that same token, or to complete cross-chain forwards backed by phantom value.

## Likelihood Explanation
High: no privileged action, governance, or compromised infrastructure is required. Any account can deploy a PVM/Solidity contract implementing `IERC20` with fee-on-transfer/deflationary semantics and route XCM programs (`pallet_xcm::execute`, `transfer_assets`, reserve transfers) through `ERC20Transactor` using ordinary, permissionless extrinsics. The bug is repeatable on every withdraw/deposit cycle involving such a token.

## Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, read the ERC20 `balanceOf` of the checking account (withdraw) or beneficiary (deposit) immediately before and after the `transfer` call, and use the observed delta rather than the requested `amount` to construct `Erc20Credit` or determine deposit completeness. If the delta is smaller than `amount`, either fail the transact or credit only the measured delta (mirroring `Precision::BestEffort` semantics used elsewhere in the fungible/fungibles traits).

## Proof of Concept
1. Deploy a `pallet-revive` ERC20 contract whose `transfer(to, amount)` deducts a fee (e.g., 5%) but returns `true`.
2. Attacker withdraws `1000` units via XCM; `withdraw_asset_with_surplus` calls `transfer(checking_account, 1000)`, the checking account receives only `950`, but `Erc20Credit(1000)` is placed into XCM holding.
3. The XCM program then issues `DepositAsset` for `1000` to a beneficiary; `deposit_asset_with_surplus` calls `transfer(beneficiary, 1000)` from the shared checking account, which can succeed if the checking account holds enough balance contributed by other users of the same token — paying out `1000` real tokens for only `950` actually deposited, net theft of `50` (or more, with repetition) from the pooled checking account.

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
