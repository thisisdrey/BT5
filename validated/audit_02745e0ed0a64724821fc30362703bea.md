### Title
Unprivileged `migrate_coin_store_to_fungible_store` Bypasses Fungible-Asset Freeze, Allowing Anyone to Unfreeze a Victim's Frozen Store — (`aptos-move/framework/aptos-framework/sources/coin.move`)

---

### Summary

`coin::migrate_coin_store_to_fungible_store<CoinType>` is a `public entry fun` with **no signer or authorization parameter**. It accepts an arbitrary `vector<address>` and calls `maybe_convert_to_fungible_store` for each one. Inside that helper, the migration unconditionally synchronizes the `frozen` flag from the legacy `CoinStore` to the primary fungible store. If the `CoinStore` is unfrozen but the primary fungible store was intentionally frozen by the asset issuer (via `TransferRef`), the migration **silently unfreezes** the fungible store. This is the direct Aptos analog of the Lens `batchMigrateFollows` bug: a migration path callable by anyone that bypasses an access-control invariant enforced on the normal path.

---

### Finding Description

`migrate_coin_store_to_fungible_store` is declared as:

```move
public entry fun migrate_coin_store_to_fungible_store<CoinType>(
    accounts: vector<address>
) acquires CoinStore, CoinConversionMap, CoinInfo {
    accounts.for_each(|account| {
        maybe_convert_to_fungible_store<CoinType>(account);
    });
}
``` [1](#0-0) 

There is no `signer` parameter and no capability check. Any account on mainnet can submit a transaction calling this entry function with any list of victim addresses.

Inside `maybe_convert_to_fungible_store`, after depositing the coin balance into the primary fungible store via `unchecked_deposit_with_no_events` (which itself skips the frozen guard), the code reconciles the two frozen flags:

```move
if (frozen != fungible_asset::is_frozen(store)) {
    fungible_asset::set_frozen_flag_internal(store, frozen);
}
``` [2](#0-1) 

Here `frozen` is the flag read from the now-destroyed `CoinStore`. If the `CoinStore` was **not** frozen (`frozen = false`) but the primary fungible store **was** frozen by the asset issuer (`is_frozen(store) = true`), the condition is `true` and `set_frozen_flag_internal` is called with `frozen = false`, **clearing the freeze**.

`set_frozen_flag_internal` writes directly to the `FungibleStore` resource without any capability check:

```move
public(friend) fun set_frozen_flag_internal<T: key>(
    store: Object<T>, frozen: bool
) acquires FungibleStore {
    let store_addr = store.object_address();
    borrow_global_mut<FungibleStore>(store_addr).frozen = frozen;
    event::emit(Frozen { store: store_addr, frozen });
}
``` [3](#0-2) 

The normal path for freezing requires a `TransferRef` capability:

```move
public fun set_frozen_flag<T: key>(
    self: &TransferRef, store: Object<T>, frozen: bool
) acquires FungibleStore {
    assert!(
        self.metadata == store_metadata(store),
        error::invalid_argument(ETRANSFER_REF_AND_STORE_MISMATCH)
    );
    set_frozen_flag_internal(store, frozen)
}
``` [4](#0-3) 

The migration path bypasses this capability requirement entirely.

The developer comment in `maybe_convert_to_fungible_store` only documents the case of a **frozen** CoinStore + **unfrozen** fungible store (freeze propagation), not the reverse (unfreeze propagation):

```
// In this case, if the account owns a frozen CoinStore and an unfrozen primary fungible store, this
// function would convert and deposit the rest coin into the primary store and freeze it to make the
// `frozen` semantic as consistent as possible.
``` [5](#0-4) 

The reverse case — unfrozen CoinStore + frozen fungible store — was not considered, and it is exploitable.

---

### Impact Explanation

An asset issuer who has frozen a user's primary fungible store (e.g., for regulatory compliance, sanctions enforcement, or protocol-level access control) loses that freeze guarantee. Any third party can call `migrate_coin_store_to_fungible_store` to unfreeze the store, after which the user can freely transfer or withdraw the previously frozen fungible assets. This constitutes **unauthorized state change of user-controlled on-chain assets** (permanent removal of a freeze that the issuer is entitled to enforce).

---

### Likelihood Explanation

The preconditions are realistic and common during the ongoing coin-to-FA migration period on Aptos mainnet:

1. A coin type has a paired fungible asset (all coins with `ensure_paired_metadata` called, including APT and most major tokens).
2. The victim account has a `CoinStore<CoinType>` with `frozen = false` and `coin.value > 0` — the default state for any account that registered before the FA migration.
3. The asset issuer has frozen the victim's primary fungible store via `TransferRef`.
4. Any unprivileged account submits one transaction calling `migrate_coin_store_to_fungible_store<CoinType>([victim])`.

No special keys, governance access, or insider knowledge is required.

---

### Recommendation

`migrate_coin_store_to_fungible_store` should either:

1. **Require the account owner's signer** (matching `migrate_to_fungible_store` which already does this correctly), so only the account holder can trigger their own migration; or
2. **Skip the frozen-flag sync when the fungible store is already frozen** — i.e., only propagate a freeze from CoinStore to fungible store, never an unfreeze:

```move
// Only propagate freeze, never unfreeze an already-frozen FA store
if (frozen && !fungible_asset::is_frozen(store)) {
    fungible_asset::set_frozen_flag_internal(store, true);
}
```

Option 1 is safer and consistent with the single-account variant `migrate_to_fungible_store`.

---

### Proof of Concept

```
1. Asset issuer deploys CoinType with paired FA and holds TransferRef.
2. Alice registers CoinStore<CoinType>; receives 1000 coins (CoinStore.frozen = false, coin.value = 1000).
3. Asset issuer calls primary_fungible_store::set_frozen_flag(transfer_ref, alice_addr, true)
   → Alice's primary FA store is now frozen; she cannot transfer FA.
4. Attacker (any address) submits:
       coin::migrate_coin_store_to_fungible_store<CoinType>([alice_addr])
5. maybe_convert_to_fungible_store runs:
   - Reads CoinStore: frozen = false, coin.value = 1000
   - Deposits 1000 into Alice's primary FA store via unchecked_deposit_with_no_events (bypasses frozen guard)
   - Checks: frozen(false) != is_frozen(store)(true) → calls set_frozen_flag_internal(store, false)
   → Alice's primary FA store is now UNFROZEN.
6. Alice can now freely transfer her 1000 FA units, defeating the issuer's freeze.
```
