### Title
Per-IP connection rate limiter is bypassable via concurrent handshake TOCTOU race - ([File: streamer/src/nonblocking/connection_rate_limiter.rs])

### Finding Description
`ConnectionRateLimiter::is_allowed` (lines 31-40) is a pure read of the current token count and performs no mutation, whereas `register_connection` (lines 42-50) is the only method that calls `consume_tokens` and actually debits the bucket. Because the QUIC accept path calls `is_allowed` before the async handshake completes and only calls `register_connection` afterward (per the connection-setup flow in `streamer/src/nonblocking/quic.rs`), an attacker who opens N concurrent QUIC connection attempts from a single IP can have all N pass `is_allowed` (each reading the same pre-consumption token count) before any of them reaches `register_connection` and actually decrements the bucket. This is a classic check-then-act race: the check and the mutation are two separate, unsynchronized calls into `KeyedRateLimiter`, with an await point (the handshake) between them, so no lock or atomicity spans the pair.

### Impact Explanation
This allows a single unstaked IP to exceed `max_connections_per_ipaddr_per_min` by racing concurrent handshakes, admitting a burst of connections beyond the configured per-IP cap. This falls under QoS/rate-limit evasion — connection-count amplification from a single source — rather than a memory-safety or consensus-breaking bug. The blast radius is bounded by how many concurrent handshakes the attacker can complete within one race window, and by other independent limits (e.g., total connection caps, staked/unstaked connection quotas) that are enforced elsewhere and are not affected by this specific race.

### Likelihood Explanation
Preconditions are minimal: an unstaked remote attacker only needs the ability to fire many concurrent QUIC connection attempts at the leader's TPU port, which is within the standard unprivileged threat model. The race window is the duration of one QUIC handshake, which is generally large enough (network RTT plus crypto handshake time) for an attacker with modest concurrency/bandwidth to land multiple concurrent `is_allowed` reads before any `register_connection` consumption lands. This is repeatable per rate-limit window.

### Recommendation
Make the check-and-consume atomic: replace the separate `is_allowed` (peek) and `register_connection` (consume) calls with a single atomic "try consume" operation performed once, at the point where the connection is provisionally accepted, and hold/reserve the token until the connection is confirmed or roll it back if the handshake fails. Alternatively, collapse the two calls into one critical section (e.g., a single `try_consume_and_confirm` API against `KeyedRateLimiter`) so no other concurrent task can observe stale token counts between the check and the debit.
