## Analysis

Confirmed: `handleCreateRelayRequest` in `relay_manager.go` never checks that `from` (attacker-supplied `m.RelayFromAddr` in the `CreateRelayRequest` control message) matches `h.vpnAddrs[0]` — i.e., the actual authenticated peer identity that sent this control message. The only anti-self checks are against *my own* address (`f.myVpnAddrsTable.Contains(from)`), not against the sender `h`'s own certified address. This is the same bug class as the report: a downstream trust decision is bound to an unverified reference field (`issuance.parent_bond` in the report; `RelayFromAddr` here) instead of the actual authenticated owning entity (the bond account / the sending `HostInfo`'s certificate).

Given the effort budget, I was not able to fully trace every downstream consumer of `AddRelay`'s `from`/`peer` binding (e.g., whether `QueryVpnAddrsRelayFor` or firewall checks later re-validate this address against a certificate), so I cannot be fully certain this reaches an unauthenticated state-poisoning primitive without deeper tracing of `hostmap.go` relay state and `firewall.Drop`'s `RemoteAddr` check path. I flag this uncertainty explicitly rather than asserting exploitability with full confidence.

### Title
Unvalidated RelayFromAddr in CreateRelayRequest allows relay-state poisoning with a spoofed identity - (File: relay_manager.go)

### Summary
`handleCreateRelayRequest` trusts the attacker-controlled `RelayFromAddr` field of an incoming `CreateRelayRequest` control message as the identity on whose behalf relay state is created, without verifying it equals the sending `HostInfo`'s own certified VPN address (`h.vpnAddrs[0]`).

### Finding Description
In `relay_manager.go`, `handleCreateRelayRequest` extracts `from := protoAddrToNetAddr(m.RelayFromAddr)` directly from the control message body sent by peer `h` [1](#0-0) . It checks only that `from` is not one of *my own* addresses [2](#0-1) , then uses `from` to create/query relay state and, in the terminal branch, calls `AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)` [3](#0-2) . There is no check that `from == h.vpnAddrs[0]` (the actual, cert-verified identity of the peer that established the encrypted control channel `h`). This mirrors the report's root cause: a state-mutating function accepts a caller-supplied "owner" reference (`parent_bond` / `RelayFromAddr`) without validating it against the entity that is actually authorized to make the claim (the bond account / the authenticated sender).

### Impact Explanation
A connected peer `h` (who already has a valid certificate and an established tunnel to the relay node) can claim an arbitrary `RelayFromAddr` that does not correspond to its own identity. This lets it install relay state (`TerminalType`, `Established`) associating a spoofed source VPN address with itself on the relay, potentially misdirecting relayed traffic bound for that address, causing hostmap/relay-state confusion, or contributing to a remote-state-poisoning condition on the relay node — without needing a CA-signed certificate for the spoofed identity, since only the initiator's own valid certificate is required to reach this code path.

### Likelihood Explanation
Reachable by any already-connected peer with a valid certificate (not requiring possession of a certificate for the address being spoofed), simply by crafting a `NebulaControl_CreateRelayRequest` message with an arbitrary `RelayFromAddr`. This requires only that `relay.am_relay` is enabled on the target node, which is a normal configuration for relay nodes.

### Recommendation
In `handleCreateRelayRequest`, validate that `from` equals `h.vpnAddrs[0]` (or is otherwise contained in `h`'s certified networks) before creating or updating relay state on behalf of `from`. Reject the request if the claimed `RelayFromAddr` does not match the authenticated sender's own certificate-derived address.

### Proof of Concept
1. Establish a normal Nebula tunnel from a malicious-but-valid-cert host `H` to a relay node `R` (`relay.am_relay: true`).
2. From `H`, send a `NebulaControl_CreateRelayRequest` message where `RelayFromAddr` is set to a victim's VPN address `V` (not `H`'s own address) and `RelayToAddr` is `R`'s own address.
3. Observe that `handleCreateRelayRequest` on `R` only checks `from != myself`, then proceeds to call `AddRelay(..., h, ..., from=V, ..., TerminalType, Established)`, associating `V` as the terminal relay target on host entry `h`, without ever confirming that `h`'s certificate actually authorizes address `V`.

*(Note: full confirmation that this leads to a concrete traffic-forgery/replay/decryption outcome would require additional tracing of `QueryVpnAddrsRelayFor` and firewall address-matching logic beyond what was reviewed in this pass.)*
