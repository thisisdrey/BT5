### Title
Missing StackerDB channel/contract binding in the chunk authentication digest allows cross-lane signature replay - ([File: libstackerdb/src/libstackerdb.rs])

### Summary
`SlotMetadata::auth_digest()` — the digest that a StackerDB writer signs over — commits only to `(slot_id, slot_version, data_hash)`. It does **not** commit to the StackerDB's smart-contract identity (the "channel"/lane). Because the Stacks signer protocol runs multiple StackerDB instances (`signers-<set>-1`, `signers-<set>-2`, `signers-<set>-3`, …) that all derive their slot assignments from the *same* underlying signer list for a given signer set, the same signer address occupies the identical `slot_id` in every one of these parallel StackerDB "lanes." A signature produced for one lane is therefore also valid for every other lane in which that signer has the same slot id, exactly analogous to the reported EIP-712 bug where an incorrectly encoded/incomplete typehash lets a signature validate outside its intended structural context.

### Finding Description
The signing digest is defined here: [1](#0-0) 

Note it hashes only `slot_id`, `slot_version`, and `data_hash` — never the `QualifiedContractIdentifier` (the StackerDB/lane identity) nor the reward cycle. `verify()` (used both by the node's write path and by StackerDB sync/relay code) checks only this same triple against a `StacksAddress`: [2](#0-1) 

Slot ownership is looked up per-database via `get_slot_signer(smart_contract, slot_id)` and enforced in `try_replace_chunk`/`validate_received_chunk`: [3](#0-2) [4](#0-3) 

The critical fact is that slot assignment is identical across all message-type lanes for a given signer set: every `signers-<set>-<message_id>` contract calls the same `stackerdb-get-signer-slots-page u<set>` function, so signer→slot mapping does not depend on `message_id`: [5](#0-4) [6](#0-5) 

Because the contract name only encodes `reward_cycle % 2` and `message_id`, and slot assignment is keyed only by signer_set (not `message_id`), a given signer occupies the same `slot_id` in the `BlockResponse` (id 1), `StateMachineUpdate` (id 2), and `BlockPreCommit` (id 3) StackerDBs simultaneously: [7](#0-6) 

Since `auth_digest` never binds the target contract, a chunk `(slot_id=X, slot_version=V, data)` legitimately signed by signer `S` and observed on lane A's StackerDB (e.g. via gossip, HTTP GET, or the unsolicited-push relay path) carries a signature that also verifies for slot `X` in lane B, C, etc., as long as `S` occupies slot `X` there too and lane B hasn't consumed version `V` yet. Any unprivileged party who can observe the chunk (chunk contents are broadcast/publicly readable, and the write endpoint itself is unauthenticated aside from the embedded signature) can resubmit the identical bytes to a different lane's write endpoint: [8](#0-7) 

`try_replace_chunk` will accept it because `slot_desc.verify(&slot_validation.signer)` succeeds — the check has no way to know the chunk was authenticated for a *different* contract: [9](#0-8) 

This breaks the equality the protocol relies on: "signed for lane/contract X" should imply "only storable in lane/contract X," but the digest makes any lane with the same slot-owner-at-slot-id indistinguishable.

### Impact Explanation
This lets an unprivileged remote observer perform an unauthenticated cross-channel write: replaying a validly-signed chunk into a StackerDB contract other than the one it was produced for, occupying that slot/version there. This can be used to:
- Deny/consume the version slot in the target lane before the legitimate signer writes to it (their real future update at that version is rejected as `StaleChunk`/`TooManySlotWrites`), degrading the signer set's ability to coordinate on block responses / state-machine updates / pre-commits.
- Pollute a lane with data whose type-prefix byte does not correspond to that lane's expected `SignerMessage` variant, which — while filtered at the `libsigner` consumer layer via `signer_message_payload_matches_lane` — still corrupts the StackerDB replica state seen by any consumer that doesn't apply that same filter, and constitutes a `StackerDB` write occurring outside the boundary the signature was meant to authorize.

This maps to a "non-canonical/forged-data propagation" class: a chunk authenticated for one purpose gets propagated node-wide as valid data for a different purpose/contract, without requiring the signer's private key.

### Likelihood Explanation
Exploitation requires only observing one legitimately broadcast chunk (StackerDB chunks are gossiped/readable via `GET /v2/stackerdb/.../chunks` and relayed via `StackerDBPushChunk`) and resubmitting the identical bytes to a sibling lane's write endpoint — no cryptographic work and no privileged role needed. The precondition (same signer occupying the same slot id across all lanes in a signer set) is guaranteed by the contract design shown above, not an edge case.

### Recommendation
Bind the StackerDB's identity (and ideally the reward cycle) into the signed digest, e.g. include the `QualifiedContractIdentifier` (or a per-DB domain identifier) as an additional field hashed into `SlotMetadata::auth_digest()`, so a signature is only valid for the specific StackerDB contract it was produced for. This mirrors the EIP-712 fix of ensuring the signed structure fully and unambiguously encodes its intended context (domain), preventing cross-context signature validity.

### Proof of Concept
1. Signer `S` is assigned slot `3` in both `.signers-1-1` (BlockResponse) and `.signers-1-2` (StateMachineUpdate) for the current reward cycle (guaranteed, since both derive slot assignment from the same `stackerdb-get-signer-slots-page u1`).
2. `S` legitimately signs and pushes a `StackerDBChunkData{slot_id:3, slot_version:5, data:D}` to `.signers-1-1`; this is observable via `GET /v2/stackerdb/<contract>/chunks/3` or via P2P `StackerDBPushChunk` relay.
3. An attacker (no keys required) copies the exact same `slot_id`, `slot_version`, `sig`, and `data` bytes and issues `POST /v2/stackerdb/.signers-1-2/chunks` for slot 3, version 5.
4. `try_replace_chunk` looks up `get_slot_signer(.signers-1-2, 3) == S`, calls `slot_desc.verify(&S)`, which succeeds because `auth_digest()` only depends on `(3, 5, hash(D))` — identical to what was signed for the other contract. The write is accepted into `.signers-1-2`, even though `S` never authorized data for that contract.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }

                slot_validation.signer,
