### Title
`setVault` revokes `MINTER_ROLE`/`BURNER_ROLE` from the vault itself when called with the current vault's address, bricking all deposits and redemptions - (File: `tare-io__tare-contracts/contracts/VaultShareToken.sol`)

### Summary
This is the same root cause as the C4 `updateAdmin` finding: a privileged setter that both reassigns a stored address and revokes a critical role from the *old* value, with no guard preventing `newValue == oldValue`. In `StaderConfig.updateAdmin`, calling it with the current admin revoked `DEFAULT_ADMIN_ROLE` from that same address. In Tare, `VaultShareToken.setVault(newVault)` does the analogous thing to `MINTER_ROLE`/`BURNER_ROLE`.

### Finding Description
`VaultShareToken.setVault`:
```solidity
function setVault(address newVault) external onlyRole(GUARDIAN_ROLE) {
  require(newVault != address(0), ZeroAddress());
  address oldVault = _vault;
  _revokeRole(MINTER_ROLE, oldVault);
  _revokeRole(BURNER_ROLE, oldVault);
  _vault = newVault;
  emit VaultUpdate(_asset, newVault);
}
``` [1](#0-0) 

There is no check that `newVault != oldVault`. If the guardian calls `setVault(currentVaultAddress)` (e.g. re-running a deployment/config script, a copy-paste mistake, or re-applying the same address for an unrelated reason such as re-triggering the `VaultUpdate` event), `oldVault == newVault == _vault`. The function revokes `MINTER_ROLE` and `BURNER_ROLE` from that address and then reassigns `_vault` to the very same address — leaving the live `PortfolioVault` contract without the roles it needs to mint or burn shares:
```solidity
function mint(address to, uint256 amount) external onlyRole(MINTER_ROLE) { _mint(to, amount); }
function burn(address from, uint256 amount) external onlyRole(BURNER_ROLE) { _burn(from, amount); }
``` [2](#0-1) 

`PortfolioVault.approveDeposit`/`approveRedemption` call `mint`/`burn` on the share token as part of the request-approve-claim flow (`vault.md` §"Deposit Flow" / "Redemption Flow"), so once the roles are stripped, every pending and future deposit approval and redemption approval reverts, halting the whole async deposit/redeem pipeline for all shareholders until the guardian notices and re-grants the roles. [3](#0-2) 

The test suite only exercises the case where `newVault` differs from the current vault (`testSetVaultRevokesMinterAndBurnerFromOldVault`, `testSetVaultOldVaultCannotMintAfterRotation`), and never asserts behavior for `newVault == oldVault`, confirming the same-address path is unguarded and untested. [4](#0-3) 

### Impact Explanation
This is a production DoS on core vault flows: after the mistaken call, `PortfolioVault.approveDeposit` and `approveRedemption` (both of which mint/burn shares) revert for every shareholder, freezing all deposits and redemptions across the entire protocol, not just a single loan or investor. This matches the in-scope "Material production DoS ... that blocks funding, disbursement, withdrawals, claims" impact category. Unlike the theft-oriented original report, here the direct consequence is denial of service rather than fund loss, but the underlying invariant break (an operational address setter unexpectedly stripping a system-critical role from the still-current holder) is identical.

### Likelihood Explanation
The trigger requires a `GUARDIAN_ROLE` call, which is a privileged action — however, unlike malicious privilege *abuse* (out of scope per the prompt), this is an honest-mistake / operational-error scenario exactly analogous to the seed report (an admin recording the same address twice), not an adversarial guardian exploiting the bug for gain. Given deployment scripts and manual config tooling repeatedly call `setVault`-style setters (see `DeployVaultLibrary.sol`), and there is no on-chain guard or revert to catch a no-op reassignment, an accidental re-invocation with the unchanged vault address is a realistic operational error, not a contrived edge case.

### Recommendation
Add a no-op guard in `setVault`:
```solidity
function setVault(address newVault) external onlyRole(GUARDIAN_ROLE) {
  require(newVault != address(0), ZeroAddress());
  address oldVault = _vault;
  require(newVault != oldVault, SameVault()); // or simply return early
  _revokeRole(MINTER_ROLE, oldVault);
  _revokeRole(BURNER_ROLE, oldVault);
  _vault = newVault;
  emit VaultUpdate(_asset, newVault);
}
```
This mirrors the C4-recommended fix of checking `oldAdmin != _admin` before proceeding with the role transfer.

### Proof of Concept
1. Deploy `VaultShareToken` with `vault_ = V`; `V` holds `MINTER_ROLE` and `BURNER_ROLE`.
2. Guardian calls `setVault(V)` (same address as the current vault) — by config-script re-run or copy/paste mistake.
3. Inside `setVault`: `oldVault = _vault = V`; `_revokeRole(MINTER_ROLE, V)` and `_revokeRole(BURNER_ROLE, V)` execute, stripping both roles from `V`; `_vault = V` (unchanged).
4. `PortfolioVault` (which is `V`) subsequently calls `approveDeposit`/`approveRedemption`, which internally call `shareToken.mint(...)`/`shareToken.burn(...)`; both revert with `AccessControlUnauthorizedAccount(V, MINTER_ROLE/BURNER_ROLE)`.
5. All pending and new deposit/redeem approvals are blocked protocol-wide until the guardian notices and re-grants `MINTER_ROLE`/`BURNER_ROLE` to `V`.

Shareholders may cancel pending deposit requests:

- Call `cancelDepositRequest(controller, receiver)` to cancel all pending assets
- Assets (USDC) returned to the specified receiver
- Emits `DepositRequestCancelled` event

### Redemption Flow (Asynchronous)

Redemptions follow the request-approve-claim pattern:

1. **Request**: Shareholder calls `requestRedeem(shares, controller, owner)`
   - Shares locked (cannot be transferred while pending)
   - Request recorded as pending for the controller
   - Multiple requests from the same controller are **additive** (increases pending amount)
   - Emits `RedeemRequest` event
2. **Approval**: Manager calls `approveRedemption(controller, shares)` - This is the valuation point
   - Manager specifies exact number of pending shares to approve (partial or full)
   - The resulting `assets` must be `<= idleLiquidity()` (vault USDC balance minus pending deposits and already-claimable redemptions); otherwise the call reverts with `InsufficientLiquidity`. This guarantees every approved redemption is immediately fundable and prevents the NAV finalization formula from underflowing

   - Shares are burned from the vault and `lastNav` is adjusted downward by `assets` — this keeps `totalSupply` and NAV synchronized for any subsequent approvals within the same NAV window
   - Multiple partial approvals accumulate: `claimableRedeemShares` and `claimableRedeemAssets` are additive across calls, and `redeem()` uses the proportional ratio between the two for conversion — naturally handling weighted-average pricing when partial approvals happen at different NAV values
   - Request becomes (partially or fully) claimable
   - Emits `RedeemApproved` event
3. **Claim**: Shareholder calls `redeem(shares, receiver, controller)`
