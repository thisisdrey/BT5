### Title
Out-of-bounds read in ZIP central directory / extra-field parsing due to missing bounds check before dereferencing fixed-size fields - (File: `third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` and its embedded ZIP64 extra-field walking loop read fixed-size fields (`get_u2le`/`get_u4le`/`get_u8le`) from an attacker-controlled ZIP central directory without any `EnsureRemaining()`-style check that enough bytes remain before dereferencing, unlike the sibling local-file-header parser. This mirrors the SCTP `sctp_ifwdtsn_skip` bug class: a walk that is only bounded by an equality/"reached the end" test rather than "at least sizeof(record) bytes remain," letting a malformed trailing/undersized record be read as if it were a full fixed-size structure and letting the cursor overshoot the declared boundary.

### Finding Description
`third_party/ijar/zip.cc` implements two structurally similar parsers:

- `InputZipFile::ProcessLocalFileEntry` calls `EnsureRemaining(n, state)` before every read of a variable-length or fixed field. [1](#0-0) 

- `InputZipFile::ProcessCentralDirEntry`, in contrast, never calls `EnsureRemaining`. It reads the fixed 46-byte central directory header fields, then `file_name_length`, `extra_field_length`, `file_comment_length`, and walks the extra-field area with:
```
const u1 *extra_p = p;
p += extra_field_length;
while (extra_p != p) {
  const u2 header_id = get_u2le(extra_p);
  const u2 data_size = get_u2le(extra_p);
  const u1 *extra = extra_p;
  extra_p += data_size;
  ...
}
``` [2](#0-1) 

The loop condition `extra_p != p` is an equality check, not a "does at least 4 bytes (or 8, for the ZIP64 payload read via `get_u8le`) remain before `p`" check. If an attacker-crafted `data_size` value causes `extra_p` to skip past `p` instead of landing exactly on it, the loop keeps running and keeps dereferencing memory past the declared extra-field region, and past the central directory entry itself, with no bound tied back to the mapped file length. The only global constraint enforced anywhere is in `FindZipCentralDirectory`, which merely checks that `central_dir_offset + central_dir_size <= in_length` for the *whole* central directory as a block; it never validates that each entry's `file_name_length + extra_field_length + file_comment_length` actually stays inside that block. [3](#0-2) 

This is the same bug class as `sctp_ifwdtsn_skip`: the walk checks position against "the end" loosely (equality/overall block size) rather than against "end minus sizeof(record-to-be-dereferenced)," so a short/malformed trailing record gets dereferenced as if it were full-size, and here the loop can additionally overshoot the intended boundary entirely because the termination condition is equality rather than `<`.

### Impact Explanation
`ProcessCentralDirEntry` is invoked by `ijar`, the tool Bazel uses to build interface jars from dependency jars (e.g. Java `srcjar`/`deps` processing, jars fetched from external Maven/HTTP repositories). A malicious jar served by an attacker-controlled dependency URL/mirror/registry (no access to the victim's machine required) that contains a crafted central directory entry with an inconsistent `extra_field_length` / extra-field `data_size` can drive the parser to read past the intended extra-field region and potentially past the mapped input file, corrupting derived `compressed_size`/`uncompressed_size`/`offset` values (used later to index into the mapped file for `ProcessFile`/`UncompressFile`) or crashing the build (out-of-bounds heap read / segfault). Because these derived offsets are then used to compute further pointers into the mapped file, this can cascade into further out-of-bounds reads during actual entry decompression.

### Likelihood Explanation
Reaching this code only requires supplying a JAR whose central directory an attacker fully controls (e.g., as the content behind a `maven_jar`/`http_jar`/`http_archive` URL, or a jar produced by CI on an attacker-influenced branch) — no bypass of any checksum is needed because `ijar` parses the archive's internal structure, which is not covered by a whole-file integrity check at this layer. The missing per-entry bounds validation is a straightforward, deterministic parsing bug, not requiring a race or timing condition, making it reliably triggerable with a crafted archive.

### Recommendation
Add explicit bounds checks in `ProcessCentralDirEntry`, mirroring `EnsureRemaining` used in `ProcessLocalFileEntry`:
- Before reading the fixed 46-byte central directory header, verify `p + 46 <= central_dir_end`.
- After reading `file_name_length`/`extra_field_length`/`file_comment_length`, verify the sum keeps `p` within the previously-validated central directory block bounds before advancing.
- In the extra-field loop, change the termination condition to `extra_p + sizeof(header_id) + sizeof(data_size) <= p` (i.e., "at least a full record header remains") instead of `extra_p != p`, and additionally verify `extra_p + data_size <= p` before advancing, aborting/erroring otherwise — analogous to the upstream SCTP fix that checks position against `end - sizeof(struct sctp_ifwdtsn_skip)` rather than just `end`.

### Proof of Concept
A `BuildIntegrationTestCase`/unit test analogous to the existing `CreateZipWithMalformedExtraField` helper (which already demonstrates the test harness pattern for crafting malformed extra fields for `LH`/`CDH`) could be extended to build a central directory entry whose extra field declares a `data_size` that causes `extra_p` to overshoot the extra-field boundary (e.g., `payload_size` value that is not a multiple of the remaining bytes, such as `extra_field_length = 6` with the first (and only) extra record declaring `data_size = 0xFFFF`), then run it through `devtools_ijar::ZipExtractor::Create`/`ProcessAll` and observe an out-of-bounds read (ASan heap-buffer-overflow) or corrupted `compressed_size`/`uncompressed_size` values rather than a clean parse error. [4](#0-3)

bool InputZipFile::ProcessCentralDirEntry(const u1 *&p, u8 *compressed_size,
                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
  const u1 *extra_p = p;
  p += extra_field_length;
  while (extra_p != p) {
    const u2 header_id = get_u2le(extra_p);
    const u2 data_size = get_u2le(extra_p);
    const u1 *extra = extra_p;
    extra_p += data_size;
    if (header_id == ZIP64_EXTRA_FIELD_TAG) {
      if (*uncompressed_size == U4_MAX) {
        *uncompressed_size = get_u8le(extra);
      }
      if (*compressed_size == U4_MAX) {
        *compressed_size = get_u8le(extra);
      }
      if (*offset == U4_MAX) {
        *offset = get_u8le(extra);
      }
    }
  }
  p += file_comment_length;
  return true;
}

bool FindZipCentralDirectory(const u1 *bytes, size_t in_length, u8 *offset,
                             const u1 **central_dir) {
  static const int MAX_COMMENT_LENGTH = 0xffff;
  static const int CENTRAL_DIR_LOCATOR_SIZE = 22;
  // Maximum distance of start of central dir locator from end of file
  static const int MAX_DELTA = MAX_COMMENT_LENGTH + CENTRAL_DIR_LOCATOR_SIZE;
  const u1* last_pos_to_check = in_length < MAX_DELTA
      ? bytes
      : bytes + (in_length - MAX_DELTA);
  const u1* current;
  bool found = false;

  for (current = bytes + in_length - CENTRAL_DIR_LOCATOR_SIZE;
       current >= last_pos_to_check;
       current-- ) {
    const u1* p = current;
    if (get_u4le(p) != EOCD_SIGNATURE) {
      continue;
    }

    p += 16;  // skip to comment length field
    u2 comment_length = get_u2le(p);

    // Does the comment go exactly till the end of the file?
    if (current + comment_length + CENTRAL_DIR_LOCATOR_SIZE
        != bytes + in_length) {
      continue;
    }

    // Hooray, we found it!
    found = true;
    break;
  }

  if (!found) {
    fprintf(stderr, "file is invalid or corrupted (missing end of central "
                    "directory record)\n");
    return false;
  }

  EndOfCentralDirectoryRecord cd;
  const u1* end_of_central_dir = current;
  get_u4le(current);  // central directory locator signature, already checked
  cd.number_of_this_disk = get_u2le(current);
  cd.disk_with_central_dir = get_u2le(current);
  cd.central_dir_entries_on_this_disk = get_u2le(current);
  cd.central_dir_entries = get_u2le(current);
  cd.central_dir_size = get_u4le(current);
  cd.central_dir_offset = get_u4le(current);
  u2 file_comment_length = get_u2le(current);
  current += file_comment_length;  // set current to the end of the central dir

  if (!FindZip64CentralDirectory(bytes, in_length, &end_of_central_dir, &cd)) {
    return false;
  }

  if (cd.number_of_this_disk != 0 || cd.disk_with_central_dir != 0 ||
      cd.central_dir_entries_on_this_disk != cd.central_dir_entries) {
    fprintf(stderr, "multi-disk JAR files are not supported\n");
    return false;
  }

  if (cd.central_dir_offset + cd.central_dir_size > in_length) {
    fprintf(stderr, "central directory offset/size is invalid\n");
    return false;
  }
