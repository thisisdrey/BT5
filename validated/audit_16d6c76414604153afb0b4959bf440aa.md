### Title
Missing content-hash verification in `extend_with_attachments` allows a malicious peer to poison `AtlasDB` with attacker-chosen attachment content - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` decodes a `GetAttachmentResponse` from an HTTP peer and inserts `response.attachment` into `self.attachments` without ever verifying that `response.attachment.hash()` equals the `content_hash` from the original `AttachmentRequest`. Any peer answering an outbound `/v2/attachments/{hash}` request can therefore return arbitrary content, which is downstream persisted via `insert_instantiated_attachment` and served in the node's attachment set.

### Finding Description
`get_prioritized_attachments_requests` (stackslib/src/net/atlas/download.rs, lines 404-478) builds an `AttachmentRequest` carrying `content_hash: content_hash.clone()` (line 469) — the hash the node is legitimately expecting for a given content-addressed attachment. This request is sent out via the `BatchedRequestsState` machine, and any peer that responds is recorded in `results.succeeded` keyed by the original `AttachmentRequest` (with its original `content_hash`), paired with the raw `StacksHttpResponse` returned by that peer (`stackslib/src/net/atlas/download.rs` line 909, `state.succeeded.insert(request, Some(response));`).

In `extend_with_attachments` (lines 530-558):
```rust
if let Ok(response) = response.decode_atlas_get_attachment() {
    self.attachments.insert(response.attachment);
    report.bump_successful_requests();
} else {
    report.bump_failed_requests();
}
``` [1](#0-0) 

The `request` variable (which holds the original, trusted `content_hash`) is discarded — only the `response` is used, and its `attachment.hash()` is never compared against `request.content_hash`. This breaks the equality the question hypothesizes: "served bytes' hash == requested content_hash" is never enforced. A malicious peer can answer with any byte string; `decode_atlas_get_attachment` only needs to successfully deserialize the response body into an `Attachment`, not match any particular hash.

The resulting `self.attachments` set is drained in `AttachmentsDownloader::run` (lines 152-169):
```rust
AttachmentsBatchStateMachine::Done(ref mut context) => {
    for attachment in context.attachments.drain() {
        let attachments_instances = network.atlasdb
            .find_all_attachment_instances(&attachment.hash())?;
        network.atlasdb.insert_instantiated_attachment(&attachment)?;
        ...
        context.attachments_batch.resolve_attachment(&attachment.hash())
    }
``` [2](#0-1) 

Here, `attachment.hash()` is recomputed from the attacker-supplied bytes (call it `H2`) and used both to look up matching instances and to persist the attachment via `insert_instantiated_attachment`. Because `attachment.hash()` (i.e., `H2`) is self-consistent (the attacker's bytes hash to their own hash), `insert_instantiated_attachment` succeeds and stores the content under `H2` in `AtlasDB`. The `resolve_attachment(&attachment.hash())` call marks the batch entry for `H2` resolved — not the originally requested `H` — meaning it will not match the pending `AttachmentInstance` that was actually waiting for `H`, so that legitimate instance may stay unresolved while a spurious `H2` entry is planted in the database. If `find_all_attachment_instances(&H2)` happens to be empty (the normal case since nothing requested `H2`), no instance gets wrongly paired, but the poisoned attachment content is still inserted into `AtlasDB` under `H2`, an entry no on-chain name operation ever committed to.

No guard elsewhere in this file (or in `get_prioritized_attachments_requests`, `BatchedRequestsState::try_proceed`, or the HTTP response handling in lines 887-913) performs a hash comparison between the served attachment bytes and the originally requested `content_hash`. The only checks present are HTTP status code (`!= 404`) and successful deserialization — no content-integrity check.

### Impact Explanation
Any remote peer that a node syncs attachments from (an outbound peer selected via `get_outbound_sync_peers`, requiring no special privilege beyond being a connected peer with a data URL) can inject arbitrary attachment blobs into the victim's `AtlasDB` under an attacker-computed hash key. This is unauthenticated/unauthorized persistent state pollution: attacker-chosen bytes are written to durable node storage (`AtlasDB::attachments`) that did not correspond to any confirmed name-operation commitment. This matches the "High" impact category of serving/persisting non-canonical state as canonical (attachment/BNS mismatch), since the database can end up holding content under a hash for which no legitimate `AttachmentInstance` exists, and future callers trusting `find_attachment`/`find_uninstantiated_attachment` for that hash would retrieve attacker content.

### Likelihood Explanation
Preconditions: the victim node must have at least one queued `AttachmentInstance` awaiting download and at least one outbound peer that claims (via inventory) to have that attachment — i.e., normal BNS/Atlas sync operation. The attacker only needs to run/control a single peer node the victim syncs Atlas attachments from and answer the outbound HTTP GET with a 200 response containing a different, self-consistent `Attachment` payload. This requires no RPC secret, no signing key, and no privileged role — fully consistent with an "unprivileged remote peer" attacker model. The attack is trivially repeatable per attachment request.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments`, after `decode_atlas_get_attachment()` succeeds, verify `response.attachment.hash() == request.content_hash` before inserting into `self.attachments`; on mismatch, treat it as a failed/faulty response (`report.bump_failed_requests()`, optionally penalize/blacklist the peer) rather than trusting the returned content.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }
