### Title
`try_replace_chunk` never enforces the `write_freq` policy, letting any authenticated slot owner bypass the smart-contract's wall-clock write-frequency limit - (File: `stackslib/src/net/stackerdb/db.rs`)

### Summary
This is a much weaker analog than a confirmed finding — I could not find a hard authorization or auth-bypass equivalent to the `feesUpdatedAt` bug, and I want to be upfront that I'm not fully confident this rises to the bar set by the rules (bounded compute DoS / policy bypass, not a state-corruption or forged-data issue). I'm presenting it because it's the closest structural analog I found, but flag the uncertainty below.

### Finding Description
`StackerDBConfig` carries a `write_freq` field, populated from the controlling smart contract, that is supposed to bound how often a given slot may be rewritten in wall-clock time [1](#0-0) . This value is read and enforced only on the *pull* (sync) side, where a peer decides whether to *fetch* a chunk from a neighbor: `StackerDBSync` skips requesting a chunk if `write_ts + self.write_freq > now` [2](#0-1) .

However, the authoritative server-side write path, `StackerDBTx::try_replace_chunk`, only checks chunk size, slot signer/version staleness, and `max_writes` — it never consults `write_freq` at all [3](#0-2) . This is also the function invoked directly by the unauthenticated HTTP POST-chunk RPC endpoint (`poststackerdbchunk.rs`), which forwards straight to `try_replace_chunk` with no additional throttling [4](#0-3) . A `net_error::TooFrequentSlotWrites` variant exists in the error enum [5](#0-4)  but is never constructed or returned anywhere in the codebase — confirmed by grepping the whole repo for `TooFrequentSlotWrites`, which only matches its 3 definition/usages in `net/mod.rs` (the enum variant, its Display/Debug derive, and one other reference), with no call site raising it.

This breaks the equality the "ideal" behavior in the analog report describes: the smart contract's declared `write-freq` policy (an authenticated, on-chain parameter) is not actually enforced by the code that authenticates and commits writes — only by a client-local heuristic in the sync/pull path. Any signer authorized to write to a slot (i.e., who holds that slot's private key) can call the POST-chunk endpoint on every replica arbitrarily fast, ignoring the wall-clock throttle the DB's owning contract configured.

### Impact Explanation
This does not appear to reach the "Critical" bar in the rules (it requires the caller to be the legitimate slot owner — not an unauthorized write, not forged data, not a crash). It is a bounded-compute/policy-bypass issue: a legitimate signer can push new chunks far faster than the contract-declared `write_freq` intends, which could be abused to increase gossip/storage churn across the whole StackerDB replica set (every replica must validate, sign-check, and store each chunk, then re-broadcast it), i.e. self-inflicted amplification of write/gossip load bounded by `max_writes`. This is closer to the "High: bounded compute DoS on a read/write endpoint" category, but it is arguably out of scope per the rule "reject analogs needing only traffic volume" since the amplification is fundamentally about write frequency/volume rather than a single crafted message breaking an invariant.

### Likelihood Explanation
Low-to-moderate. It requires possessing a valid slot private key (i.e., being a legitimate, provisioned StackerDB signer/miner) — not a fully unauthenticated attacker — and the impact is limited by `max_writes` and `chunk_size` caps that remain enforced.

### Recommendation
Enforce `write_freq` inside `try_replace_chunk` (or immediately before it is called in the RPC handler), comparing the stored `SlotValidation.write_time` against `get_epoch_time_secs()` and rejecting with `net_error::TooFrequentSlotWrites` when the interval has not elapsed, mirroring the client-side check already present in `sync.rs`.

### Proof of Concept
1. Configure a StackerDB contract with a nonzero `write-freq` (e.g., `u60`).
2. As the legitimate owner of a slot, repeatedly POST new, validly-signed, monotonically-increasing-version chunks to a replica's `poststackerdbchunk` endpoint faster than the configured `write-freq` interval.
3. Observe that `try_replace_chunk` accepts every write (bounded only by `max_writes`), because no code path checks `write_freq` on the server side [3](#0-2) , contradicting the intended contract-level throttle described in the module's own documentation of the write-frequency control plane [6](#0-5) .

    /// Add or replace a chunk for a given reward cycle, if it is valid
    /// Otherwise, this errors out with Error::StaleChunk
    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
