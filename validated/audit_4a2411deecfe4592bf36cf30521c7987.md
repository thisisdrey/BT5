### Title
Unbounded `read_to_end` in libsigner's StackerDB RPC client allows a malicious/compromised node to exhaust signer memory - (File: `libsigner/src/http.rs`)

### Summary
`run_http_request()` in `libsigner/src/http.rs` reads an entire HTTP response into memory with `sock.read_to_end(&mut buf)` before any length check or content-length validation is applied. This function is the transport used by `StackerDBSession::rpc_request()` (`libsigner/src/session.rs`) — the client signers use to talk to a Stacks node's StackerDB HTTP RPC endpoints (`list_chunks`, `get_chunks`, `get_latest_chunks`, `put_chunk`). A node that returns a very large (or endlessly streamed) response body will cause the signer process to buffer unbounded data in RAM, exhausting memory — the same bug class as the Mattermost advisory (CWE-789, uncontrolled response size from a server the client trusts to behave correctly).

This is reached from `StackerDBSession::rpc_request`, which every `SignerSession` operation funnels through: [3](#0-2) 

Even the caller-side "too large" checks (e.g. in `get_latest_chunks`) happen only after the full oversized body has already been read and allocated in memory: [4](#0-3) 

So the equality/bound that should hold — "bytes read from an untrusted peer are bounded before being fully buffered" — is broken here, unlike every other network ingestion path in this repo (P2P preamble/payload length checks, StackerDB chunk size checks in `stackslib/src/net/stackerdb/db.rs::try_replace_chunk`, HTTP header size checks in `decode_http_response`).

### Impact Explanation
A node that a signer is configured to talk to (`self.host` in `StackerDBSession`) — which may be operator-misconfigured, compromised, or simply buggy/malicious — can respond to any StackerDB RPC call issued by the signer with an arbitrarily large HTTP body (or keep the connection open and dribble bytes indefinitely up to the socket read timeout). Because `read_to_end` has no cap, the signer process will keep growing its buffer until memory is exhausted, causing the signer process to crash or become unresponsive (DoS). Since `stacks-signer` participates in block signing, taking it down via this vector directly affects availability of the signing set. This is a bounded compute/memory DoS on a component reachable by any peer the signer session connects to, matching the "High" impact tier (bounded compute DoS on a read endpoint) in the rubric.

### Likelihood Explanation
The `StackerDBSession` "host" the signer talks to is a Stacks node HTTP endpoint that the signer is configured to trust for chunk data; it does not require any special privilege beyond being the endpoint the signer is pointed at. Any node (or a network man-in-the-middle capable of injecting/serving responses to that TCP connection, since the connection is plain HTTP over TCP with only a socket read timeout for protection) can trigger this simply by returning a large or slow-drip response to a normal `GET`/`POST` RPC call. No signing key or admin privilege is required to trigger the bug — only the ability to answer the socket connection the signer opens.

### Recommendation
Bound `run_http_request`'s read exactly as the rest of the codebase does elsewhere: wrap `sock` in a `BoundReader`/`RetryReader` limited to `MAX_MESSAGE_LEN` (or an appropriate StackerDB-specific cap such as `STACKERDB_MAX_CHUNK_SIZE`) before calling `read_to_end`, and fail fast with an error once that limit is exceeded rather than allocating unbounded memory first and validating length afterward.

### Proof of Concept
1. Configure a `StackerDBSession` (as `stacks-signer` does) pointed at a controlled/malicious HTTP endpoint.
2. Have that endpoint accept the HTTP request, then continuously write (or write a single multi-gigabyte) response body without closing the connection.
3. Observe `run_http_request`'s `sock.read_to_end(&mut buf)` (`libsigner/src/http.rs:251`) grow `buf` without bound (limited only by the OS/available memory and the `socket_timeout`), leading to memory exhaustion of the signer process before any length validation in `decode_http_response`/`decode_http_body` or the caller-side chunk-size checks in `libsigner/src/session.rs` is ever reached.

pub fn decode_http_body(headers: &HashMap<String, String>, mut buf: &[u8]) -> io::Result<Vec<u8>> {
    let chunked = if let Some(val) = headers.get("transfer-encoding") {
        val == "chunked"
    } else {
        false
    };

    let body = if chunked {
        // chunked encoding
        let ptr = &mut buf;
        let mut fd = HttpChunkedTransferReader::from_reader(ptr, MAX_MESSAGE_LEN.into());
        let mut decoded_body = vec![];
        fd.read_to_end(&mut decoded_body)?;
        decoded_body
    } else {
        // body is just as-is
        buf.to_vec()
    };

    Ok(body)
}
