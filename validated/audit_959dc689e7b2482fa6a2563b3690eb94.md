Audit Report

## Title
`success` field of Snowbridge V2 delivery receipt is decoded but never checked before paying relayer reward - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
`DeliveryReceipt::try_from` decodes the `InboundMessageDispatched(nonce, topic, success, reward_address)` Ethereum event into a `DeliveryReceipt` struct carrying a `success: bool` field, but `Pallet::process_delivery_receipt` never reads or checks this field before paying out the relayer's reward. [1](#0-0) [2](#0-1)  As a result, a relayer can obtain full reward for a message whose dispatched command actually reverted on Ethereum, as long as they can produce a valid inclusion proof of the emitted event.

## Finding Description
`submit_delivery_receipt` is a signed, permissionless extrinsic reachable by any account. [3](#0-2)  After `T::Verifier::verify` confirms the Ethereum event log's inclusion (proving only that the log was emitted, not that the underlying dispatched command executed successfully), the log is decoded via `DeliveryReceipt::try_from`, which captures `success` directly from the `InboundMessageDispatched` event's `success` field. [4](#0-3) 

`process_delivery_receipt` then: (1) checks `receipt.gateway` against `T::GatewayAddress`, (2) resolves `reward_account`, (3) looks up the `PendingOrder` by `nonce`, (4) unconditionally pays `order.fee` via `T::RewardPayment::register_reward` if `fee > 0`, and (5) removes the pending order and emits `MessageDelivered`. [5](#0-4)  At no point is `receipt.success` inspected — a grep across the entire `outbound-queue-v2` pallet confirms the field is never referenced outside of the primitive decode struct itself. This means whether the Ethereum-side dispatched command succeeded or reverted, the reward is paid identically as long as the event log proof validates and the nonce is still pending in `PendingOrders`.

## Impact Explanation
Reward settlement is decoupled from actual successful command execution on Ethereum: the pallet treats "an `InboundMessageDispatched` event was emitted and proven" as equivalent to "the message was successfully processed," even when `success = false`. This violates the required invariant that "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically," and constitutes underpriced/incorrect payout for non-productive work, allowing drain of the reward pool for messages that fail on the Ethereum side.

## Likelihood Explanation
High. `submit_delivery_receipt` requires only `ensure_signed` and a standard proof of a real (but possibly `success=false`) Ethereum event log — no privileged role or compromised infrastructure is needed. [6](#0-5)  Any ordinary relayer submitting a proof of a genuinely failed dispatch (e.g., a command that reverts on the Gateway due to insufficient gas or a downstream call failure) will still collect the full reward under current code.

## Recommendation
Add a check on `receipt.success` in `process_delivery_receipt` before crediting `order.fee`, e.g. `ensure!(receipt.success, Error::<T>::DeliveryFailed);` prior to the `register_reward` call, or explicitly design and document a reduced/zero reward path keyed off `receipt.success` if relayers are intended to be paid for proof delivery regardless of downstream command success.

## Proof of Concept
1. A message dispatched via the outbound-queue-v2 pipeline reaches the Ethereum Gateway and its command execution reverts, but the Gateway still emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
2. Any signed account obtains a standard proof for this event log and calls `submit_delivery_receipt(origin, event)`. [7](#0-6) 
3. `T::Verifier::verify` succeeds, `DeliveryReceipt::try_from` decodes `success = false` correctly, but `process_delivery_receipt` pays `order.fee` to `reward_account` and removes the pending order exactly as it would for `success = true`. [8](#0-7) 
4. `MessageDelivered` is emitted, indistinguishable from a genuinely successful delivery, confirming the reward was paid for a failed cross-chain execution.

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
