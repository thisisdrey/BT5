## Vulnerability Analog Found

### Title
Out-of-bounds read in `Zip64ExtraField::attr64()` via unvalidated attribute index in `CDH`/`LH` size accessors - ([File: src/tools/singlejar/zip_headers.h])

### Summary
Singlejar (`src/tools/singlejar/`) merges Java jars supplied as build inputs (dependency jars, jars downloaded via `http_archive`/`http_jar`, or otherwise fetched from untrusted origins) into a single output jar. When parsing a ZIP64 extra field to recover 64-bit sizes/offsets, the code computes an attribute index from unrelated 32-bit fields and indexes into the extra field's `attr_[]` array without ever checking that the extra field actually contains that many attributes. This mirrors the iccDEV CVE-2026-25585 pattern: "reading through index" without validating it against the declared array bounds, producing an out-of-bounds read of attacker-controlled/malformed input.

### Finding Description
`Zip64ExtraField::attr64(int index)` directly indexes a flexible array member with no bounds check: [1](#0-0) 

The number of valid attributes is tracked separately via `attr_count()` (`payload_size() / 8`), but none of the call sites that read 64-bit values ever consult `attr_count()` before indexing:

- `CDH::compressed_file_size()` computes the index from whether `uncompressed_file_size32()` also needs the ZIP64 extension, and blindly calls `attr64(0)` or `attr64(1)`: [2](#0-1) 

- `CDH::local_header_offset()` goes even further, computing an index up to 2 based on two independent 32-bit fields, with no check that the ZIP64 extra field payload is large enough to hold 3 attributes: [3](#0-2) 

- `LH::compressed_file_size()` unconditionally reads `attr64(1)`, assuming a second attribute exists: [4](#0-3) 

The only validation performed anywhere near this data is `Zip64ExtraField::find()` (via `ExtraField::find()`), which checks that the extra field's declared `payload_size()` fits within the `extra_fields()`/`extra_fields_length()` window of the CDH/LH — it does **not** check that `payload_size()` is large enough for the *index that will be used*: [5](#0-4) 

So a ZIP64 extra field with signature `0x0001` and a valid-but-short payload (e.g. `payload_size = 8`, i.e. `attr_count() == 1`) passes `find()`'s bounds check, but if the corresponding CDH sets *both* `compressed_file_size32` and `uncompressed_file_size32` to `0xFFFFFFFF` (or additionally `local_header_offset32` to `0xFFFFFFFF`), the code computes index `1` (or `2`) and reads 8/16 bytes past the declared 8-byte payload — into whatever bytes happen to follow in the mmap'd input file (comment field, next CDH entry, or in the worst case past the mapped region entirely, causing a segfault).

This code path is reached by `OutputJar::AddJar` while singlejar walks every input jar's Central Directory Header, which is exactly the java_binary/deploy-jar assembly path that consumes jars sourced from `http_archive`/`http_jar`/`maven_install` and other externally-fetched artifacts: [6](#0-5) 

The existing regression test only exercises a *different* bug class — an extra field whose `payload_size` overflows the extra-fields buffer, caught by `AppendToDirectoryBuffer`'s explicit iteration check ("malformed extra field in CDH") — it does not exercise or guard the `attr64()` indexing bug described here: [7](#0-6) [8](#0-7) 

### Impact Explanation
An attacker who controls the content of any jar consumed by a Bazel build (e.g. a jar served at a `http_jar`/`http_archive` URL, a malicious Maven artifact, or a jar committed to an untrusted CI branch) can craft a CDH/LH entry whose ZIP64 extra field declares fewer attributes than the code will index. When Bazel's `singlejar` merges this jar (a routine step for `java_binary`/`java_import`/deploy-jar targets), the out-of-bounds read either leaks adjacent memory bytes into the size/offset value used for further processing (potentially causing further out-of-bounds copies during entry extraction) or crashes the build (`singlejar` operates on `mmap`'d input, so reading past the mapping boundary can SIGSEGV). This matches the CVSS profile of the analog CVE: local, low-complexity, no privileges, memory disclosure or crash.

### Likelihood Explanation
Any of Bazel's supported archive/JAR consumption mechanisms (`http_archive`, `http_jar`, `maven_install`-fetched jars, or jars on an untrusted branch built by CI) can supply the malicious jar; no special access to the victim's machine or credentials is needed, and default flags apply — `singlejar` is invoked unconditionally when building `java_binary`/deploy jars.

### Recommendation
In `Zip64ExtraField::attr64()`, or at every call site (`CDH::compressed_file_size()`, `CDH::uncompressed_file_size()`, `CDH::local_header_offset()`, `LH::compressed_file_size()`, `LH::uncompressed_file_size()`), validate `index < attr_count()` before dereferencing `attr_[index]`, and treat an out-of-range index the same way a missing ZIP64 extra field is treated (return an error/sentinel and abort processing of the malformed jar, consistent with the existing `diag_errx` "malformed extra field" handling used elsewhere in `output_jar.cc`).

### Proof of Concept
Extend `src/tools/singlejar/output_jar_simple_test.cc` with a jar whose CDH declares `compressed_file_size32 = uncompressed_file_size32 = 0xFFFFFFFF`, and whose ZIP64 extra field (tag `0x0001`) has `payload_size = 8` (only one 8-byte attribute, `attr_count() == 1`). Feed it through `OutputJar::Doit()` as in the existing `MalformedExtraField` test — this should either produce a wrong size value from adjacent bytes or crash under ASan/valgrind, in contrast to the current test which only exercises the extra-field-length overflow case guarded in `AppendToDirectoryBuffer`.

class ExtraField {
 public:
  static const ExtraField* find(uint16_t tag, const uint8_t* start,
                                const uint8_t* end) {
    while (start < end) {
      if (ziph::byte_ptr(start) + sizeof(ExtraField) > ziph::byte_ptr(end)) {
        break;
      }
      auto extra_field = reinterpret_cast<const ExtraField*>(start);
      if (ziph::byte_ptr(start) + extra_field->size() > ziph::byte_ptr(end)) {
        break;
      }
      if (extra_field->is(tag)) {
        return extra_field;
      }
      start = ziph::byte_ptr(start) + extra_field->size();
    }
    return nullptr;
  }

void OutputJar::AppendToDirectoryBuffer(const CDH* cdh, int64_t lh_pos,
                                        uint16_t normalized_time,
                                        bool fix_timestamp) {
  // While copying from the input CDH pointed to by 'cdh', we may need to drop
  // Unix timestamp extra field, and we might need to change the number of
  // attributes of the Zip64 extra field, or create it, or destroy it if entry's
  // position relative to 4G boundary changes.
  // The rest of the input CDH is copied.

  // 1. Decide if we need to drop UnixTime.
  size_t removed_unix_time_field_size = 0;
  if (fix_timestamp) {
    auto unix_time_field = cdh->unix_time_extra_field();
    if (unix_time_field != nullptr) {
      removed_unix_time_field_size = unix_time_field->size();
    }
  }

  // 2. Figure out how many attributes input entry has and how many
  // the output entry is going to have.
  const Zip64ExtraField* zip64_ef = cdh->zip64_extra_field();
  const int zip64_attr_count = zip64_ef == nullptr ? 0 : zip64_ef->attr_count();
  const bool lh_pos_needs64 = ziph::zfield_needs_ext64(lh_pos);
  int out_zip64_attr_count;
  if (zip64_attr_count > 0) {
    out_zip64_attr_count = zip64_attr_count;
    // The number of attributes may remain the same, or it may increase or
    // decrease by 1, depending on local_header_offset value.
    if (ziph::zfield_has_ext64(cdh->local_header_offset32()) !=
        lh_pos_needs64) {
      if (lh_pos_needs64) {
        out_zip64_attr_count += 1;
      } else {
        out_zip64_attr_count -= 1;
      }
    }
  } else {
    out_zip64_attr_count = lh_pos_needs64 ? 1 : 0;
  }
  const uint16_t zip64_size = Zip64ExtraField::space_needed(zip64_attr_count);
  const uint16_t out_zip64_size =
      Zip64ExtraField::space_needed(out_zip64_attr_count);

  // Allocate output CDH and copy everything but extra fields.
  const uint16_t ef_size = cdh->extra_fields_length();

  const size_t out_cdh_size = cdh->size() + out_ef_size - ef_size;
  CDH* out_cdh = reinterpret_cast<CDH*>(ReserveCdr(out_cdh_size));

std::string CreateZipWithMalformedExtraField() {
  std::string zip_data;
  const std::string filename = "evil.bin";

  // 1. Local File Header (LFH)
  size_t lh_offset = zip_data.size();
  size_t lh_size = sizeof(LH) + filename.size();
  zip_data.resize(lh_offset + lh_size, 0);
  auto* lh = reinterpret_cast<LH*>(&zip_data[lh_offset]);
  lh->signature();
  lh->version(10);
  lh->file_name(filename.data(), filename.size());

  // 2. Extra field payload containing an oversized payload_size
  uint8_t ef_buffer[8] = {0};
  auto* ef1 = reinterpret_cast<ExtraField*>(ef_buffer);
  ef1->signature(0x000d);
  ef1->payload_size(0);

  auto* ef2 = reinterpret_cast<ExtraField*>(ef_buffer + ef1->size());
  ef2->signature(0xdead);
  ef2->payload_size(0xf000);  // Malformed size exceeding extra field buffer

  // 3. Central Directory Header (CDH)
  size_t cdh_offset = zip_data.size();
  size_t cdh_size = sizeof(CDH) + filename.size() + sizeof(ef_buffer);
  zip_data.resize(cdh_offset + cdh_size, 0);
  auto* cdh = reinterpret_cast<CDH*>(&zip_data[cdh_offset]);
  cdh->signature();
  cdh->version(20);
  cdh->version_to_extract(10);
  cdh->local_header_offset32(lh_offset);
  cdh->file_name(filename.data(), filename.size());
  cdh->extra_fields(ef_buffer, sizeof(ef_buffer));

  // 4. End of Central Directory (EOCD)
  size_t ecd_offset = zip_data.size();
  zip_data.resize(ecd_offset + sizeof(ECD), 0);
  auto* ecd = reinterpret_cast<ECD*>(&zip_data[ecd_offset]);
  ecd->signature();
  ecd->this_disk_entries16(1);
  ecd->total_entries16(1);
  ecd->cen_size32(cdh_size);
  ecd->cen_offset32(cdh_offset);

  return zip_data;
}
