### Title
Unbounded HashSet allocation and sort of `pages_indexes` before length cap enforcement - (File: stackslib/src/net/api/getattachmentsinv.rs)

### Summary
`RPCGetAttachmentsInvRequestHandler::try_parse_request` parses every comma-separated entry in the `pages_indexes` query parameter into a `HashSet<u32>` and then sorts a `Vec<u32>` built from it, with no limit on the number of entries. The `MAX_ATTACHMENT_INV_PAGES_PER_REQUEST` cap is only checked afterward, in `try_handle_request`, so the parse-time allocation/hashing/sorting work scales with attacker-supplied input size rather than the intended cap of 8.

### Finding Description
In `try_parse_request` [1](#0-0) , the handler iterates over every `,`-separated token in the `pages_indexes` query value, parses each as `u32`, and inserts it into a `HashSet<u32>` with no bound on the number of entries. After the loop, all entries are collected into a `Vec<u32>` and sorted [2](#0-1) . Only afterward, in `try_handle_request`, is `page_indexes.len() > MAX_ATTACHMENT_INV_PAGES_PER_REQUEST` checked and the request rejected with 400 if exceeded [3](#0-2) . This means the full parse, hash-set population, and `O(n log n)` sort are performed on attacker-controlled `n` before the cap is enforced.

However, the actual severity is bounded by upstream constraints I could not fully verify from the index: the HTTP request's total URI/query length is subject to a preamble/header size limit enforced during HTTP request-line/header parsing in `stackslib/src/net/httpcore.rs` before `try_parse_request` is even invoked. I was unable to confirm the exact numeric limit (e.g., `MAX_HEADERS_LEN`/URI length cap) applied to the request line, but this repo's HTTP parsing layer does impose bounds on total request size prior to `try_parse_request`, which caps how large `n` (100,000 numeric entries, ~6+ bytes each ≈ 600KB+ query string) can realistically be for a single request depending on the configured/hardcoded limit.

### Impact Explanation
If the URI/request-line size limit is large enough to admit a query string with tens of thousands of numeric tokens, a single unauthenticated GET to `/v2/attachments/inv` forces the node to allocate and populate a `HashSet<u32>`, then build and sort a `Vec<u32>`, sized to the attacker's chosen entry count — work strictly larger than the intended 8-entry cap. This is a bounded, single-message compute cost (not unbounded, since the request itself is size-limited by the HTTP layer), and it is trivially repeatable by re-sending the same request. This matches the "bounded compute DoS on a read endpoint" impact category, but its actual severity is directly capped by whatever URI/header length limit the HTTP layer enforces — which limits `n` to a value substantially smaller than an attacker sending arbitrarily large payloads, since HTTP body size/URI length limits already bound total bytes per the question's own framing.

### Likelihood Explanation
The endpoint `/v2/attachments/inv` is an unauthenticated GET RPC handler, remotely reachable with no privileged role, secret, or peer key required. The attacker cost is a single crafted HTTP GET request, and it is fully repeatable. The actual achievable `n` (and thus the real-world cost) depends on the request-line/header size limit enforced in `stackslib/src/net/httpcore.rs`, which was not fully confirmed in this investigation — this bounds the magnitude of the issue but does not eliminate the ordering flaw (allocate-then-cap) itself.

### Recommendation
Enforce the `MAX_ATTACHMENT_INV_PAGES_PER_REQUEST` cap during parsing in `try_parse_request`, e.g., reject or stop parsing once the number of parsed entries (or raw comma-separated tokens) exceeds the cap, before inserting into the `HashSet` and before sorting, rather than allocating and sorting the full set and checking the cap later in `try_handle_request`.
