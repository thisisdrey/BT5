### Title
Race condition between `updateMerkleRoot()` and `claim()` lets a user keep a revoked entitlement - ([File: contracts/utils/RecurringAirdrop.sol])

### Summary
`RecurringAirdrop` tracks per-account consumption with a cumulative `claimed[msg.sender]` counter, while the governor sets the entitlement via `updateMerkleRoot()` (the leaf encodes the total amount allocated to the account). This is the same "allowance update vs. allowance consumption" race as the Teller `updateCommitment()`/`acceptCommitment()` finding: if the governor lowers an account's entitlement, the user can front-run the root update and claim the old, higher amount. `claimed[]` then underflow-blocks any claim under the new root, but the over-claimed tokens are already gone — the user ends up with more than the (new) intended entitlement and the protocol cannot claw it back.

### Finding Description
In `contracts/utils/RecurringAirdrop.sol`:

```solidity
bytes32 _leaf = keccak256(abi.encodePacked(msg.sender, amount_));
if (!MerkleProof.verify(proof_, merkleRoot, _leaf)) revert InvalidProof();
uint256 _claimable = amount_ - claimed[msg.sender];
``` [1](#0-0) [2](#0-1) 

Attack trace:
1. Governor publishes root R1 where Alice's leaf is `[alice, 10e18]`.
2. Governor notices the allocation is too high and submits `updateMerkleRoot(R2)` where Alice's new leaf is `[alice, 8e18]`.
3. Alice (unprivileged EOA) front-runs in the same block and calls `claim(10e18, proof_R1)` against the still-current root R1. She receives the full 10e18 and `claimed[alice] = 10e18`.
4. `updateMerkleRoot(R2)` executes; `merkleRoot = R2`.
5. Any further `claim(8e18, proof_R2)` reverts via underflow in `amount_ - claimed[msg.sender]`, so the reduction can never be enforced retroactively. Alice keeps 10e18 — more than the 8e18 the governor intended, and unlike a supply cap the excess is permanently extracted rather than merely minted early.

The identical logic is inherited by `MetAirdrop` (`_transferReward` locks MET into `esMET` via `ESMET.lockFor`), so the excess is even silently locked to the attacker there — the contract just pays out whatever the old leaf authorized. [3](#0-2) 

### Impact Explanation
Direct theft of protocol funds: the difference between the old and new entitlement is paid to the user with no recovery path, since `claimed[]` is monotonic and only ever increases. Unlike `maxTotalSupply` caps elsewhere in the codebase (which are checked against `totalSupply` and therefore cannot be double-consumed), the airdrop entitlement is a per-account cumulative allowance, making the front-run consume the revoked allocation irrevocably.

### Likelihood Explanation
Requires a governor root update that reduces some account's allocation — a routine correction scenario for a recurring airdrop — plus standard mempool front-running available to any unprivileged account. No privileged attacker role is needed; `claim()` is permissionless and `nonReentrant` does not help since the exploit uses two separate transactions across a governance update, not reentrancy. Frequency is bounded by how often entitlements are reduced, keeping it medium rather than high.

### Recommendation
Same fix class as the audit report: avoid replacing a consumed allowance with an absolute value. Options:
- Treat each root's leaf amount as *incremental* per epoch (leaf = `epochId` + `epochAmount`, with `claimed` tracked per epoch), so reducing a future epoch never retroactively contends with a past claim.
- Or version leaves with the epoch/root index (`keccak256(abi.encodePacked(msg.sender, epoch_, amount_))`) and store `claimed[epoch][account]`, so an old-root proof cannot be replayed after an update.
- At minimum, ensure corrections only ever increase allocations, or accept and document that in-flight reductions can be front-run.

### Proof of Concept
Hardhat (repo test framework), sketch:

```ts
// Build tree T1: leaf(alice, 10e18); publish via updateMerkleRoot(root1, ...)
// Build tree T2: leaf(alice, 8e18)

// Alice front-runs governor's updateMerkleRoot(root2):
await airdrop.connect(alice).claim(parseEther('10'), proofR1); // succeeds, gets 10e18
await airdrop.updateMerkleRoot(root2, hash2);                  // governor update lands

// Reduction is now unenforceable:
await expect(airdrop.connect(alice).claim(parseEther('8'), proofR2))
  .to.be.reverted; // panic: arithmetic underflow on 8e18 - 10e18

expect(await met.balanceOf(alice.address)).to.eq(parseEther('10')); // > intended 8e18
```

The invariant broken is the per-account distribution bound set by the latest merkle root — equivalent to `commitment.maxPrincipal` being exceeded in the reference finding.

    function claim(uint256 amount_, bytes32[] calldata proof_) external nonReentrant {
        if (merkleRoot == bytes32(0)) revert NothingToClaim();

        bytes32 _leaf = keccak256(abi.encodePacked(msg.sender, amount_));
        if (!MerkleProof.verify(proof_, merkleRoot, _leaf)) revert InvalidProof();

        uint256 _claimable = amount_ - claimed[msg.sender];
        if (_claimable == 0) revert NothingToClaim();

        claimed[msg.sender] += _claimable;

        _transferReward(msg.sender, _claimable);

        emit RewardClaimed(msg.sender, _claimable);
    }
