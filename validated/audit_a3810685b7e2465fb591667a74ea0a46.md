## Finding: `do_burn` does not clear or refund per-item `Attribute` storage/deposits

### Summary
`Pallet::do_burn` (invoked by the unprivileged `burn` extrinsic) unreserves and removes storage for the **item deposit** and, conditionally, the **metadata deposit**, but it never touches the `Attribute` storage map or its associated `AttributeDeposit`s for the burned item. This breaks the required one-to-one binding between a deposit and the state it funds.

### Finding Description
`do_burn` performs the following cleanup steps inside/after the `Collection::try_mutate` closure:

- Unreserves `details.deposit.amount` for the item deposit and removes `Item::<T,I>`. [1](#0-0) 
- Conditionally unreserves the metadata deposit and removes `ItemMetadataOf`, but **only** if `ItemSetting::UnlockedMetadata` is enabled. [2](#0-1) 
- Removes `Item`, `Account`, `ItemPriceOf`, `PendingSwapOf`, and `ItemAttributesApprovalsOf` (the *approvals* map for delegated attribute-setting, not the attributes themselves), and conditionally `ItemConfigOf`. [3](#0-2) 

Nowhere in `do_burn` is the `Attribute` storage map (which stores each key/value attribute together with its own `AttributeDeposit{account, amount}`, set via `set_attribute`/`do_set_attribute` in `substrate/frame/nfts/src/features/attributes.rs`) iterated, removed, or refunded. `ItemAttributesApprovalsOf` only tracks delegate accounts allowed to set attributes under `AttributeNamespace::Account`; it is a different storage item from the `Attribute` map that actually holds attribute values and their reserved deposits.

As a result, after `burn` succeeds:
- The `Item` entry disappears, so the NFT is gone from the owner's/collection's perspective.
- Any `Attribute` entries keyed to `(collection, Some(item), namespace, key)` remain in storage indefinitely, and the currency reserved for their `AttributeDeposit` remains locked on the depositor's account with no code path to release it (since the normal release path is `do_clear_attribute`, which requires the caller to know the item still "exists" in a meaningful sense, and no separate cleanup runs on `burn`).

### Impact Explanation
This does not let an unprivileged caller free a deposit without removing state (the classic exploit shape described in the question) — it is the opposite failure mode: state (`Attribute` entries) is orphaned and deposits for it are permanently locked with no remaining code path to reclaim them, since the item that would let a user reference/clear those attributes no longer exists. This falls under the "permanent user-fund lock" category from the Required Impacts, rather than an unauthorized-mint/transfer scenario. It does not appear to enable unbacked minting or unauthorized transfer of the NFT itself, since the `Item`/`Account` mappings are correctly removed together with the item deposit.

### Likelihood Explanation
Any unprivileged item owner (or approved burn-caller) who has previously set item-scoped attributes with `DepositRequired` enabled and then calls `burn` will trigger this every time — no special conditions, front-running, or privileged access required.

### Recommendation
In `do_burn` (`substrate/frame/nfts/src/features/create_delete_item.rs`), before/while removing the item, iterate and remove all `Attribute` entries for `(collection, Some(item), ..)` and unreserve their associated `AttributeDeposit` amounts to the correct depositor, mirroring the pattern already used for metadata deposits (including updating `collection_details.owner_deposit` where the collection owner covered the deposit).

### Proof of Concept
1. Create a collection and mint an item with `DepositRequired` enabled.
2. Call `set_attribute` on the item, causing an `Attribute` entry with a non-zero `AttributeDeposit` to be reserved from the caller.
3. Call `burn` on the item as its owner.
4. Observe: `Item` is removed and its deposit is refunded, but the `Attribute` storage entry for the (now-nonexistent) item persists, and the reserved attribute deposit is never unreserved — verifiable via `Attribute::<T,I>::get((collection, Some(item), namespace, key))` still returning `Some(..)` and the depositor's `reserved` balance unchanged after burn.

Note: I was not able to verify within this session whether `destroy_collection`'s bulk cleanup (`clear_prefix`-style removal) eventually removes these orphaned `Attribute` entries and their deposits when the whole collection is destroyed — if it does not, the fund lock is permanent rather than merely deferred until collection destruction. This would need to be checked in `substrate/frame/nfts/src/features/create_delete_collection.rs` to fully characterize severity.
