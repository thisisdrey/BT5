## Title
Relayer reward is paid regardless of delivery outcome (`success` flag ignored) - (File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs)

## Summary
`process_delivery_receipt` in the Outbound Queue V2 pallet decodes a `DeliveryReceipt` from a verified Ethereum event log — including a `success: bool` field indicating whether the message dispatch on Ethereum actually succeeded — but never checks this field before paying out the relayer reward. Any signed account can submit a `submit_delivery_receipt` extrinsic with a legitimately-verified proof for a failed dispatch and still receive the full fee.

## Finding Description
The `InboundMessageDispatched` event emitted by the Ethereum Gateway contract carries a `success` flag, decoded into `DeliveryReceipt.success` [1](#0-0) .

`submit_delivery_receipt` verifies the proof and event log via `T::Verifier::verify`, decodes the receipt, and forwards it to `process_delivery_receipt` without ever inspecting `success` [2](#0-1) .

`process_delivery_receipt` looks up the `PendingOrder` by `receipt.nonce`, and if `order.fee > 0`, unconditionally calls `T::RewardPayment::register_reward` — `receipt.success` is never read anywhere in the function body [3](#0-2) . A repository-wide search confirms no reference to `receipt.success` exists in the pallet's production code.

The `PendingOrder` created in `do_process_message` only tracks `nonce`, `fee`, and `block_number` — no outcome data — and is populated purely from the outbound message content at send time, independent of any later execution result [4](#0-3) .

The pallet's own documentation confirms the intended design is that reward is paid "when the message has been verified and executed" — the implementation instead pays regardless of execution outcome, breaking the documented invariant.

## Impact Explanation
This is a public, permissionless payout-correctness bug: the amount paid to a relayer is decoupled from whether the paid-for action (successful dispatch on Ethereum) actually occurred. Any account acting as relayer can be rewarded for messages whose commands failed/reverted on the Ethereum side, draining the reward/fee pool for services that provided no value to the protocol. This matches the "theft or unbacked... duplicate settlement or payout" impact category — reward settles even though the invariant condition (verified success) was not met.

## Likelihood Explanation
No privileged actor or compromised assumption is required. The exploit path uses only the public `submit_delivery_receipt` extrinsic with a legitimately verified proof of a failed dispatch (which can occur naturally, e.g., insufficient gas allowance, or be engineered deterministically by crafting a command destined to revert). Because the `success` check is entirely absent from the code path, every such submission where `order.fee > 0` triggers the erroneous payout deterministically and repeatably.

## Recommendation
Gate the reward payment in `process_delivery_receipt` on `receipt.success`:
```rust
if receipt.success && order.fee > 0 {
    T::RewardPayment::register_reward(&reward_account, T::DefaultRewardKind::get(), order.fee);
}
```
Still remove the `PendingOrder` regardless of outcome to avoid leaving it unresolved, and consider emitting a distinct event (e.g., `MessageDeliveryFailed`) for the failure case for observability.

## Proof of Concept
1. Send an outbound message via the normal XCM flow so a `PendingOrder{nonce, fee, ..}` with `fee > 0` is created in `do_process_message` [5](#0-4) .
2. Ensure the corresponding command dispatch fails on the Ethereum Gateway contract (e.g., insufficient gas or a target designed to revert), producing an `InboundMessageDispatched` event with `success = false`.
3. As any signed account, submit `submit_delivery_receipt` with the legitimate event log/proof for that failed dispatch.
4. Observe `process_delivery_receipt` pays the reward via `T::RewardPayment::register_reward` and removes the `PendingOrder` exactly as for a successful dispatch, since `receipt.success` is never consulted [6](#0-5) . Existing integration tests only construct `DeliveryReceipt { success: true, .. }` and assert reward registration; no test exists asserting `success: false` withholds payment.

		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
