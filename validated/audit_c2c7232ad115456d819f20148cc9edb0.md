### Title
Out-of-bounds read in ijar's ZIP central-directory Zip64 extra-field parser due to unvalidated `data_size` — ([File: third_party/ijar/zip.cc])

### Summary
`InputZipFile::ProcessCentralDirEntry` in ijar (Bazel's interface-jar/zip-processing tool used, e.g., by `zip_main.cc`/`archive_utils.cc` and jar-stripping tooling that operate on `.jar`/`.zip` files consumed by a build) walks a Central Directory Header's "extra fields" region using an attacker-controlled, declared per-field length (`data_size`), but the Zip64 extra-field decoder unconditionally reads a fixed 8 bytes (`get_u8le`) from that field's start regardless of what `data_size` actually declared. This is structurally the same bug class as the GoBGP advisory: a length-prefixed sub-record's declared length is recorded but the concrete decoder does not bound its read to that declared length, so it can consume bytes belonging to the next field/record.

### Finding Description
In `ProcessCentralDirEntry` [1](#0-0) , the extra-fields region of a Central Directory Header is walked as a sequence of `(header_id: u2, data_size: u2, payload: data_size bytes)` triples:

```
const u1 *extra_p = p;
p += extra_field_length;
while (extra_p != p) {
  const u2 header_id = get_u2le(extra_p);
  const u2 data_size = get_u2le(extra_p);
  const u1 *extra = extra_p;
  extra_p += data_size;
  if (header_id == ZIP64_EXTRA_FIELD_TAG) {
    if (*uncompressed_size == U4_MAX) {
      *uncompressed_size = get_u8le(extra);
    }
    if (*compressed_size == U4_MAX) {
      *compressed_size = get_u8le(extra);
    }
    ...
  }
}
```

`extra_p` (the cursor used to detect the end of the loop and locate subsequent fields) is advanced by the *declared* `data_size`, but the actual value extraction via `get_u8le(extra)` (and a second `get_u8le` call immediately after for `compressed_size`, consuming 16 bytes total from `extra`) reads directly from `extra` with no check that `data_size >= 8` (or `>= 16` when both fields are needed). A malicious/corrupted ZIP/JAR can declare a Zip64 extra field with `header_id == ZIP64_EXTRA_FIELD_TAG` and `data_size` of 0, 2, or 4 — smaller than the 8/16 bytes actually consumed — causing `get_u8le` to read past the field's declared boundary into subsequent extra-field bytes, the file name, the comment, or (for a Central Directory Header located near the end of the mmap'd file) past the end of the memory-mapped input file entirely.

None of the primitive readers in `third_party/ijar/common.h` perform bounds checking [2](#0-1) , so nothing downstream stops the over-read. Unlike `ProcessLocalFileEntry`, which calls `EnsureRemaining(...)` before consuming file-name/extra-field bytes [3](#0-2) , `ProcessCentralDirEntry` has no equivalent bound check on the extra-fields walk, and the containing comment in the code even asserts the read is "safe" because "the central directory is always followed by another data structure that has a signature" [4](#0-3)  — an assumption that does not hold for the last Central Directory entry in the file, nor does it bound reads that stay within the mmap but cross into an adjacent field/entry's data (an integrity-relevant confusion, matching the GoBGP "wrong bytes interpreted as the value" pattern).

### Impact Explanation
This is a memory-safety / boundary-validation defect (CWE-125) in native C++ code that runs over attacker-influenced ZIP/JAR bytes (a JAR published as a dependency, or any archive processed by ijar during interface-jar generation). Consequences are:
- Out-of-bounds heap read (potentially past the end of the mmap'd input file for a malformed trailing entry), which can crash the ijar process (SIGSEGV) or leak adjacent memory bytes into the derived `uncompressed_size`/`compressed_size` values used to size subsequent reads (`p += file_name_length`, `UncompressFile()`, etc.), further amplifying corruption of downstream size-dependent processing.
- Consistent with the referenced advisory's severity class: a boundary-validation issue in a length-prefixed record parser, not remote code execution, but a legitimate crash/robustness and data-integrity concern for any build that processes untrusted `.jar`/`.zip` inputs with ijar.

### Likelihood Explanation
Reaching this code only requires providing a ZIP/JAR file with a Central Directory Header whose Zip64 extra field declares `header_id = 0x0001` and a `data_size` smaller than what `get_u8le` will actually consume (0, 2, or 4). This is trivial to construct and does not require breaking any hash/checksum protection at the fetch layer — ijar operates on the archive's own internal structure after it has already been fetched/verified (checksum verification only covers whole-file integrity, not internal ZIP structural correctness), so the crafted archive can still pass an `sha256`/`integrity` check and reach this parser. No authentication, credentials, or root-repo Starlark execution is required — an unprivileged party who supplies a JAR/ZIP dependency the victim's build processes with ijar can trigger it.

### Recommendation
In `InputZipFile::ProcessCentralDirEntry`, bound every read of a Zip64 extra-field's payload to its declared `data_size` before calling `get_u8le`:
- Verify `data_size >= 8` before reading `uncompressed_size`, and `data_size >= 16` before reading `compressed_size` (and `>= 24` for the offset variant), rejecting/erroring out the archive otherwise.
- Additionally bound the extra-fields walk itself so that `extra_p + data_size` never exceeds the previously computed `p` (the declared end of the extra-fields region), and reject the archive on any violation rather than assuming trailing data is always safely followed by a further signature.

### Proof of Concept
A `BuildIntegrationTestCase`/native `zip_headers_test.cc`-style unit test can construct a Central Directory Header byte buffer (as done in the existing `ZipHeadersTest.CentralDirectoryHeader` test [5](#0-4) , adapted to ijar's `zip.cc` structures) where:
1. `uncompressed_file_size32 == 0xFFFFFFFF` (forces Zip64 path),
2. the extra field is `{0x01, 0x00, 0x00, 0x00}` (`header_id=1`, `data_size=0`), placed at the very end of the mmap'd buffer (last CDH entry, no trailing bytes),
3. Call `InputZipFile::ProcessCentralDirEntry` on this buffer under a sanitizer build (ASan) — `get_u8le(extra)` will read 8 bytes starting at `extra` (the position right after the empty declared payload), reading past the allocated/mapped buffer, which ASan reports as a heap-buffer-overflow / out-of-bounds read.

Note: I could not fully trace every call site that invokes `ProcessCentralDirEntry` end-to-end from a Starlark-level `http_archive`/`http_jar` rule within the indexed content (some code paths connecting the fetch pipeline to ijar invocation were not present in the retrieved index), so the exact build-rule reproduction command should be validated with a live checkout; the parser-level defect and its file/line locations above are directly confirmed from source.
