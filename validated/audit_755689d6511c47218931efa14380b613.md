### Title
`SlotMetadata::auth_digest` omits the StackerDB contract identity, allowing a validly-signed chunk from one StackerDB to be replayed as valid data into a different StackerDB - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
The signature that authenticates a StackerDB chunk write commits only to `slot_id`, `slot_version`, and `data_hash`. It never binds the signature to the `QualifiedContractIdentifier` of the StackerDB the chunk is destined for. Whenever the same signer address occupies the same `slot_id` in two different StackerDB replicas (which is normal in this codebase — e.g. sibling signer-message contracts for a reward cycle use the same signer ordering/slot assignment), an unprivileged peer that has merely observed one legitimately-broadcast chunk can resubmit those exact same bytes/signature to the sibling contract and have it accepted as an authentic write there, without ever holding the signer's private key. This is the direct structural analog of the Ajna bug: a field that determines *where/how* a signed artifact is valid (`endBlock_` in Ajna; `smart_contract` here) is excluded from the value that's cryptographically committed to, so an attacker can re-use an honestly-produced artifact in an unintended context.

### Finding Description
`SlotMetadata::auth_digest()` computes the signed digest as: [1](#0-0) 

i.e. `hash(slot_id || slot_version || data_hash)` only. `sign()`/`verify()` operate purely over this digest: [2](#0-1) 

`StackerDBChunkData::verify()` delegates to the same digest, again with no notion of *which contract* the chunk belongs to: [3](#0-2) 

The contract binding is supposed to be supplied out-of-band by the caller, via a lookup of "who owns slot `X` in contract `Y`": [4](#0-3) 

and similarly on the p2p push-chunk validation path: [5](#0-4) 

Neither of these call sites feeds the `smart_contract`/`contract_id` into the signature check — they only use it to look up the expected signer address for that `(contract, slot_id)` pair, then verify the chunk's self-contained (contract-agnostic) signature against that address. If contract `A` and contract `B` both assign the same signer address to `slot_id = X`, a chunk that address legitimately signed and broadcast for contract `A` — an artifact any listening peer can capture off the wire (StackerDB chunks are gossiped p2p and servable over the public `POST .../stackerdb/{contract}/chunks` RPC) — is *also* a validly-signed, validly-versioned chunk for contract `B`'s slot `X`, because `verify()` never checks which contract the signature was meant for. An attacker with no private key, no admin role, and no special privilege can simply retarget the `contract_id` field of the message/request and replay the captured `(slot_id, slot_version, sig, data)` tuple into the other database.

This breaks the intended equality "signature over (slot_id, slot_version, data_hash) authenticates *this specific StackerDB's* slot" — the code treats "signed for slot X" as if it also meant "signed for slot X *in this contract*", which the cryptography does not actually guarantee.

### Impact Explanation
This is an unauthenticated/unauthorized write to StackerDB state: content that was never signed for database `B` gets accepted and stored as authentic data in `B`. Depending on which contracts share slot/signer layouts, this can smuggle stale or out-of-context signer/miner protocol messages (e.g., a message meant for one purpose/topic contract) into a sibling contract where downstream consumers (signers, miners) parse it as legitimate current-context data, and the forged/replayed write then propagates network-wide via the normal StackerDB gossip/replication path (`validate_received_chunk` → `try_replace_chunk` → broadcast). This matches the "Critical: unauthenticated/unauthorized write to StackerDB, network-wide propagation of forged data" bar, since no secret key or privileged role is required — only the ability to observe one legitimately-signed chunk and resend it, with a different `contract_id`, before the real chunk for that slot/version in the target contract is written.

### Likelihood Explanation
Likelihood depends on the concrete deployment fact that two StackerDB contracts genuinely reuse the same `(signer_address → slot_id)` assignment and version numbering starts from a comparable baseline — this is plausible given the codebase's pattern of paired per-cycle signer contracts and shared reward-set-derived slot ordering, but I was not able to fully confirm, within the remaining budget, that any two *currently deployed* contracts have identical slot layouts and overlapping/exploitable version counters (this would need to be verified against the live contract/slot-allocation logic, e.g. `stackslib/src/chainstate/nakamoto/signer_set.rs` and the StackerDB config derivation code, which I did not finish tracing before running out of iterations). The root cause itself — the digest omitting contract identity — is unambiguous and directly verifiable in `libstackerdb/src/libstackerdb.rs`.

### Recommendation
Bind the signature to the target StackerDB contract by including the `QualifiedContractIdentifier` (or a stable hash of it) in `SlotMetadata::auth_digest()`, and thread the contract id through `sign()`/`verify()` so that a chunk signed for contract `A` cannot verify against contract `B`'s slot ownership, even when the signer address and slot_id coincide. This mirrors the Ajna fix of folding the omitted field (`endBlock_`) into the hash that is actually signed/checked.

### Proof of Concept
Conceptual PoC (mirroring the coded PoC style of the report), to be validated against the concrete signer-slot layout:
1. Identify two StackerDB contracts, `A` and `B`, where signer address `S` owns `slot_id = 3` in both (per their respective `StackerDBConfig.signers` lists).
2. `S` legitimately signs and pushes chunk `(slot_id=3, slot_version=5, data=D)` to contract `A`. This is broadcast over p2p StackerDBChunk push / observable via the `GET`/`POST .../stackerdb/A/chunks/3` RPC.
3. Attacker (no private key for `S`) captures `(slot_id=3, slot_version=5, sig, data=D)` and submits it, unmodified, to contract `B` (e.g. via `POST /v2/stackerdb/{B}/chunks` or by crafting a `StackerDBPushChunkData{contract_id: B, chunk_data: <captured chunk>}` p2p message).
4. `validate_received_chunk`/`try_replace_chunk` for contract `B` looks up `slot_validation.signer` for `(B, 3)`, finds it is `S`, calls `slot_desc.verify(&S)` — which succeeds because `auth_digest()` never included `A` or `B`. If `5 > current version at (B,3)`, the write is accepted and replicated as authentic data for `B`.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Sign this slot metadata, committing to slot_id, slot_version, and
    /// data_hash.  Sets self.signature to the signature.
    /// Fails if the underlying crypto library fails
    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
