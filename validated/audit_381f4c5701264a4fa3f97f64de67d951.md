### Title
Unbounded growth of `DelegatedResourceAccountIndex` prefix-scanned by `getDelegatedResourceAccountIndexV2` enables low-cost API/query DoS - ([File: chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java])

### Summary
An unprivileged account can broadcast an unlimited number of `DelegateResourceContract` transactions (minimum 1 TRX each) to distinct receiver addresses, each of which writes a new key into the `DelegatedResourceAccountIndex` store keyed by `V2_FROM_PREFIX/owner/receiver` and `V2_TO_PREFIX/receiver/owner`. This is directly analogous to the reported Carapace bug: an unbounded, attacker-growable set that is later iterated in full by a function reachable through a normal API/user call, creating a DDoS/resource-exhaustion vector.

### Finding Description
`DelegateResourceActuator.delegateResource()` unconditionally calls `delegatedResourceAccountIndexStore.delegateV2(ownerAddress, receiverAddress, now)` for every delegation, with no cap on the number of distinct receiver addresses a single owner can delegate to: [1](#0-0) 

`delegateV2` simply appends a new key/value pair per unique `(from, to)` pair to the store, with no limit: [2](#0-1) 

Only a 1 TRX minimum delegate balance is enforced in `DelegateResourceActuator.validate()`, so an attacker can cheaply create thousands of tiny delegations to many distinct (self-controlled) receiver accounts: [3](#0-2) 

Later, any client (unauthenticated, via HTTP/gRPC) can call `getDelegatedResourceAccountIndexV2`, which invokes `DelegatedResourceAccountIndexStore.getV2Index()` → `getWithPrefix()`. This method performs a `prefixQuery` over *all* keys under the `V2_FROM_PREFIX`/`V2_TO_PREFIX` + address prefix, materializes every matching entry into an `ArrayList`, sorts the entire collection by timestamp, and builds the response — an O(n) operation with no pagination or upper bound, where n is fully controlled by the attacker: [4](#0-3) 

`prefixQuery` at the `TronStoreWithRevoking` layer streams and deserializes every matching key/value pair into memory with no size limit: [5](#0-4) 

This query is exposed on every node interface without any owner-specific throttling beyond a generic rate limiter servlet: [6](#0-5) [7](#0-6) [8](#0-7) 

### Impact Explanation
Once an attacker has grown the `DelegatedResourceAccountIndex` set for their address to a large size (cheaply, at ~1 TRX per entry plus minimal fees, with only self-created throwaway receiver accounts needed), every subsequent call to `getdelegatedresourceaccountindexv2` / `GetDelegatedResourceAccountIndexV2` for that address forces the node to scan, deserialize, and sort the full unbounded key set in memory. Because this endpoint is reachable via HTTP, gRPC, and the PBFT/Solidity node variants with no owner-specific limit, repeated invocation degrades node responsiveness and consumes CPU/memory disproportionate to the cost paid by the attacker — a query-serving DoS vector satisfying the "API the node can no longer serve" impact criterion. This does not directly cause fund loss but can render the affected query path (and, under load, the serving node generally) unusable.

### Likelihood Explanation
Likelihood is moderate-to-high: the attack requires only broadcasting many low-value `DelegateResourceContract` transactions (1 TRX minimum, reusable across cheap throwaway receiver accounts) — an action fully available to any unprivileged account holder, with no special permissions or contract deployment needed. The growth is entirely attacker-controlled and persists on-chain (there is no automatic pruning of `DelegatedResourceAccountIndex` entries beyond the corresponding un-delegate action, which the attacker has no incentive to perform).

### Recommendation
- Add pagination or a hard cap to `getWithPrefix`/`prefixQuery`-based reads in `DelegatedResourceAccountIndexStore`, and/or limit the maximum number of distinct delegation targets stored per owner.
- Consider indexing delegation counts separately (e.g., a bounded count field) rather than requiring a full prefix scan to answer index queries.
- Apply per-owner or per-IP request cost/limits proportional to the number of stored index entries for that address.

### Proof of Concept
1. Attacker account A creates N (e.g., 50,000) throwaway receiver accounts (or reuses a small set of pre-funded receiver accounts).
2. A broadcasts N `DelegateResourceContract` transactions, each delegating the minimum 1 TRX of frozen `BANDWIDTH`/`ENERGY` from A to a distinct receiver, each success adding one `V2_FROM_PREFIX+A+receiver` and one `V2_TO_PREFIX+receiver+A` key via `delegateV2` (actuator/src/main/java/org/tron/core/actuator/DelegateResourceActuator.java:313-315, chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java:77-89).
3. Any client repeatedly calls `/wallet/getdelegatedresourceaccountindexv2` (or the gRPC `GetDelegatedResourceAccountIndexV2`) with address A.
4. Each call triggers `getV2Index(A)` → `getWithPrefix` → `prefixQuery` over all N entries, deserializing and sorting the full set in memory (chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java:114-138), consuming CPU/memory proportional to N on every request — degrading the serving node under repeated calls.

  public DelegatedResourceAccountIndexCapsule getV2Index(byte[] address) {
    return getWithPrefix(V2_FROM_PREFIX, V2_TO_PREFIX, address);
  }

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }
