### Title
DoS via unbounded per-account delegation index growth queried through `getDelegatedResourceAccountIndex`/`getV2Index` RPC/HTTP paths - ([File: chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java])

### Summary
`DelegateResourceActuator`/`DelegateResourceProcessor` and `FreezeBalanceActuator` place no cap on the number of distinct receiver (or sender) addresses a single account can delegate resources to. Each new relationship is stored as a separate DB key (`V2_FROM_PREFIX`/`V2_TO_PREFIX`, or legacy `FROM_PREFIX`/`TO_PREFIX`) via `DelegatedResourceAccountIndexStore.delegateV2`/`delegate`. The query paths (`getIndex`/`getV2Index` → `getWithPrefix`) perform a `prefixQuery` that materializes and sorts **every** relationship for that address into in-memory lists, similar in structure to the `activeProtectionIndexes` unbounded array in the reported ProtectionPool issue.

### Finding Description
`DelegateResourceProcessor.delegateResource` (`actuator/src/main/java/org/tron/core/vm/nativecontract/DelegateResourceProcessor.java:146-192`) and `FreezeBalanceActuator.delegateResource` (`actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java:289-370`) allow any account to repeatedly delegate small amounts of frozen balance to an unbounded number of distinct receiver addresses (e.g., attacker-controlled throwaway accounts), each call inserting a new key into `DelegatedResourceAccountIndexStore` via `delegateV2`/`delegate` (`chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java:63-89`). There is no validation limiting the count of unique receivers per owner address in `DelegateResourceActuator.validate()` or `FreezeBalanceActuator.validate()`.

When the index is later read — via `getIndex()`/`getV2Index()` → `getWithPrefix()` (`chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java:106-138`) — the code performs `this.prefixQuery(key).values()`, builds a full in-memory `ArrayList`, sorts it by timestamp, and streams/maps it into a `List<ByteString>` twice (once for "to" and once for "from"). If an attacker inflates one address's relationship count to a very large number, every subsequent query for that account's delegated index (surfaced through HTTP/gRPC/JSON endpoints such as `GetDelegatedResourceAccountIndexServlet`/`GetDelegatedResourceAccountIndexV2Servlet` and their PBFT/Solidity counterparts, per the grep hits) becomes increasingly expensive, and the legacy `convert()` path (`DelegatedResourceAccountIndexStore.java:42-61`) that migrates old-format lists to the V2 format also iterates the entire `toAccountsList`/`fromAccountsList` inside a state-changing actuator call.

This mirrors the reported bug class: an attacker-controlled, unbounded collection populated one small transaction at a time, later iterated in full by a function that services other users' calls (query API) or their own subsequent transaction (`convert`), with no upper bound or pagination.

### Impact Explanation
Because this is reachable via the query/API layer (`Wallet`-backed HTTP/gRPC servlets that serve `GetDelegatedResourceAccountIndex(V2)`), a sufficiently inflated index can make responses to legitimate queries for that address slow or resource-intensive, degrading the node's ability to serve that API for the affected account. This matches the allowed "API the node can no longer serve" impact category. It does not directly cause consensus-level fund loss, and the severity depends on how large the attacker can practically grow the list and how expensive the `prefixQuery`+sort actually is at scale, both of which I could not fully quantify from static analysis alone (I was unable to confirm exact per-call gas/bandwidth costs to inflate the list, or hard caps enforced elsewhere in delegate validation, before running out of investigation budget).

### Likelihood Explanation
Likelihood is moderate: any account can call `DelegateResourceContract` repeatedly with the current minimum frozen balance to a large number of self-controlled receiver addresses, each delegation being a normal, low-cost, permissionless transaction. There's no explicit code found capping the number of unique delegation relationships per address in the actuators reviewed, but I could not confirm within the available tool budget whether `validate()` methods (not fully read) impose an indirect limit (e.g., via minimum freeze amount economics) that would make large-scale list inflation economically impractical.

### Recommendation
- Enforce an upper bound on the number of distinct delegation relationships (`toAccounts`/`fromAccounts`) an account can maintain, or require unbounded lists to be paginated at read time instead of loaded/sorted in full.
- Avoid iterating full legacy lists synchronously inside `convert()`; migrate incrementally or cap conversion batch size.
- Add pagination parameters to the `GetDelegatedResourceAccountIndex(V2)` query APIs so `prefixQuery` results are limited rather than fully materialized per call.

### Proof of Concept
1. Attacker freezes/obtains the minimum TRX required to call `DelegateResourceContract`.
2. Attacker repeatedly submits `DelegateResourceContract` transactions from a single owner address to N distinct newly generated receiver addresses (each transaction independently valid and low-cost), each one adding an entry via `DelegatedResourceAccountIndexStore.delegateV2` (`chainbase/.../DelegatedResourceAccountIndexStore.java:77-89`).
3. Any client (including the attacker) then calls `GetDelegatedResourceAccountIndexV2` for the owner address; the servlet resolves to `getV2Index()` → `getWithPrefix()`, which performs `prefixQuery` over all N entries, builds and sorts an `ArrayList` of size N, and returns it — the cost of this call grows linearly (or worse, with sorting) in N, with no cap observed in the reviewed code.

Note: I could not fully verify actuator-level validation limits or exact query-servlet code (`GetDelegatedResourceAccountIndexV2Servlet.java` contents were not retrievable within the available tool calls), so confirm there is no size cap enforced elsewhere before treating this as conclusively exploitable at scale.
