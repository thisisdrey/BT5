### Title
Stale `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` trie entries survive `DeleteAccount`, allowing a former account owner to replay a privileged self-call against a later account recreated under the same `AccountId` - (File: `core/store/src/utils/mod.rs`, `runtime/runtime/src/lib.rs`, `runtime/runtime/src/actions.rs`)

### Summary
`remove_account` (`core/store/src/utils/mod.rs:505`) removes the `Account`, `ContractCode`, access keys/gas-key nonces, and `ContractData`, but never removes `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, or `TrieKey::PostponedReceiptId` entries keyed by the deleted `account_id`. Because `check_actor_permissions` (`runtime/runtime/src/actions.rs:739`) only compares `actor_id == account_id` (raw strings, no notion of account "incarnation"), a self-call ActionReceipt (`predecessor_id == receiver_id == A`) postponed before deletion can be resumed and executed against a brand-new account created later under the identical `AccountId`, authorizing `AddKey`/`DeployContract`/`Stake` as if the new owner had signed it.

### Finding Description
1. Account `A`'s owner submits a self-targeted `ActionReceipt` (e.g. via a promise `.then()` callback to itself) containing privileged actions (`AddKey`, `DeployContract`, `Stake`) with `predecessor_id == receiver_id == A` and an `input_data_ids` entry that has not yet arrived. `process_action_receipt` (`runtime/runtime/src/lib.rs:1593`) finds `pending_data_count > 0`, stores `PendingDataCount` and calls `set_postponed_receipt` (`runtime/runtime/src/lib.rs:1654`, `core/store/src/utils/mod.rs:120`), keyed by `(receiver_id = A, receipt_id = R)`, plus a `PostponedReceiptId` link keyed by `(A, data_id)`.
2. Before the missing `DataReceipt` arrives, the owner submits `DeleteAccountAction` on `A` (with `account_storage_usage <= Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE` so `action_delete_account`, `runtime/runtime/src/actions.rs:314`, does not reject it). `action_delete_account` calls `remove_account` (`core/store/src/utils/mod.rs:505-575`), which deletes the `Account`, keys, code and contract data — but does **not** touch `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, or `TrieKey::PostponedReceiptId` for `A`. Those entries remain in the trie.
3. `A` no longer exists. Some other authority later recreates an account with the exact same `AccountId` `A` (e.g. a parent recreating a sub-account, or a top-level registrar reissuing the name), with fresh keys unrelated to the original owner.
4. The original owner (or anyone able to trigger delivery of the pending `DataReceipt`, since they control the promise chain that produces it) causes the missing `DataReceipt` with the matching `data_id` to be delivered to `A`. `process_receipt`'s `Data` branch (`runtime/runtime/src/lib.rs:1367-1455`) performs no account-existence check: it looks up `PostponedReceiptId`/`PendingDataCount` (still present from the deleted account) and, once `pending_data_count` reaches 0, fetches the stale `PostponedReceipt` via `get_postponed_receipt` and executes it via `apply_action_receipt` against the *new* incarnation of `A`.
5. Inside `apply_action` (`runtime/runtime/src/lib.rs:523`), `actor_id` is derived from `receipt.predecessor_id()` which is `A` itself, and `check_actor_permissions` (`runtime/runtime/src/actions.rs:739-784`) only checks `actor_id != account_id` for `AddKey`/`DeployContract`/`Stake`/`DeleteKey`. Since both are the string `A`, the check passes trivially even though the account object, its keys, and its actual owner have all changed. The stale receipt's privileged actions execute as if authorized by the new account's owner.

This is a genuine gap between the account-lifecycle cleanup (`remove_account`) and the deferred-receipt bookkeeping (`set_postponed_receipt`/`PendingDataCount`/`PostponedReceiptId`), combined with an authorization check (`check_actor_permissions`) that is purely string-based and unaware of account recreation ("incarnation").

### Impact Explanation
This allows a former account owner to plant a "time bomb" that later injects unauthorized `AddKey`, `DeployContract`, or `Stake` actions into an account now controlled by a different party, once that party recreates an account under the same name. This is an authorization escalation across accounts/promises: the new owner never signed or approved these actions, yet they execute with full permission-check success. Concretely this can be used to add an access key to (steal control of) a resurrected account, deploy attacker-chosen contract code onto it, or stake funds without owner consent.

### Likelihood Explanation
The attacker needs only ordinary account/contract capabilities (no privileged role): create a self-call promise chain, delete their own account within storage limits, and later trigger the pending `DataReceipt`. The harder precondition is that some other party must recreate an account with the exact same `AccountId` — this is realistic for sub-accounts (a parent account may recreate a previously deleted sub-account, e.g., re-provisioning `child.parent.near`) without any awareness that stale postponed-receipt state exists for that name. The attacker fully controls the timing of when the trap is armed and (via their own promise chain) roughly controls delivery of the completing `DataReceipt`, making the attack repeatable and low-cost (bounded by minimal gas/storage fees).

### Recommendation
`action_delete_account`/`remove_account` should purge all `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, and `TrieKey::PostponedReceiptId` entries scoped to the account being deleted before completing deletion. Additionally, `process_receipt`'s `Data` branch and/or `apply_action_receipt` should verify the target account still exists (or track an account "incarnation"/creation nonce) before resuming a postponed receipt, so that receipts postponed under one incarnation of an `AccountId` cannot be resumed against a later, unrelated incarnation.

### Proof of Concept
Runtime/integration test plan (test-loop or `runtime/runtime/src/tests/apply.rs`-style):
1. Create account `A` (as sub-account of `parent`) and deploy a trivial contract.
2. Submit a receipt to `A` from `A` itself (`predecessor_id == receiver_id == A`) containing `Action::AddKey` with an unmet `input_data_ids` entry, forcing it into `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` state (assert these `TrieKey`s exist in the trie after this step).
3. Submit `Action::DeleteAccount` on `A` with `beneficiary_id = parent`, keeping `account_storage_usage <= MAX_ACCOUNT_DELETION_STORAGE_USAGE`. Assert `TrieKey::Account { account_id: A }` is gone, but assert (bug reproduction) that `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, and `TrieKey::PostponedReceiptId` for `A` still exist.
4. Have `parent` submit `Action::CreateAccount` + `Action::AddKey(new_key)` to recreate `A` with a fresh key unrelated to the original owner.
5. Deliver the missing `DataReceipt` (matching the original `data_id`) targeting `A`.
6. Assert that the postponed `AddKey` action executes and the attacker's original key (from step 2) is now present on the *new* `A`'s account — demonstrating unauthorized escalation into an account the attacker no longer controls.
7. Expected fixed behavior: after the fix, either the trie assertion in step 3 shows no residual `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` keys for `A` (cleanup at deletion), or the resumed receipt in step 6 is rejected/dropped because the account's incarnation no longer matches.
