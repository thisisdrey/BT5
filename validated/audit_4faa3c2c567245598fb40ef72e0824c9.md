### Title
`SSHReceivePack` has no negotiation/idle timeout, letting a client hold the handler and a spawned `git-receive-pack` process open indefinitely - ([File: internal/gitaly/service/ssh/receive_pack.go])

### Summary
`sshReceivePack` in `internal/gitaly/service/ssh/receive_pack.go` copies the client's stdin stream into a pipe consumed by `git-receive-pack(1)` and then calls `cmd.Wait()`, with no timeout mechanism at all. Unlike the sibling upload-pack/upload-archive code paths, which explicitly guard against a stalled negotiation with `pktline.NewReadMonitor` and a configurable `timeoutTicker`, `sshReceivePack` has no equivalent protection, so a client that sends the initial request and then never sends more data (no flush, no EOF) can keep the RPC handler, its goroutine, its OS pipe, and the spawned `git-receive-pack` process blocked forever.

### Finding Description
`sshReceivePack` builds a `streamio.Reader` over `stream.Recv()` and copies it into an `os.Pipe()` in a background goroutine: [1](#0-0) 

The pipe's read end is passed as stdin to the spawned `git-receive-pack` process, and the RPC then blocks on `cmd.Wait()`: [2](#0-1) 

There is no read monitor, no negotiation deadline, and no context timeout applied anywhere in this path. Compare this to `runUploadCommand`, used by `sshUploadPack`/upload-archive, which explicitly wraps stdin with `pktline.NewReadMonitor` and cancels the local context via a configurable `timeoutTicker` if a boundary packet (flush/"done") is not observed in time: [3](#0-2) 

The `ReadMonitor` doc comment explicitly frames this as a security mitigation against "use-after-check"-style attacks where an unbounded stdin wait lets a client hold a checked-out resource indefinitely: [4](#0-3) 

No such mechanism exists for `SSHReceivePack`. The attacker (an unprivileged user who can push to their own repository) sends the mandatory first `SSHReceivePackRequest` (repository, `GlId`, etc.) which passes `validateFirstReceivePackRequest`, then simply stops sending any further `Stdin` chunks and never closes the stream. `stream.Recv()` blocks, the io.Copy goroutine blocks, `pw` is never closed, `git-receive-pack`'s stdin never reaches EOF or a flush packet, and `cmd.Wait()` blocks indefinitely. The gRPC server's `KeepaliveParams` (`Time: 5 * time.Minute`) only pings to detect a dead *transport*; HTTP/2 PING/PONG is handled automatically by the peer's gRPC transport layer regardless of application-level progress, so it does not terminate an idle-but-connected stream: [5](#0-4) 

The existing regression test only exercises the case where the client eventually calls `CloseSend()` (producing "remote end hung up unexpectedly" / `Canceled`), not the case of an indefinitely open, silent stream: [6](#0-5) 

### Impact Explanation
Each such connection pins a real OS process (`git-receive-pack`), an `os.Pipe()`, a goroutine, and a gRPC stream/handler slot for as long as the attacker keeps the SSH/gRPC connection alive without sending data. Repeating this from a single unprivileged account (subject only to whatever per-repo/per-user concurrency limiter is configured, which is not a hard bound by default) can exhaust worker/process/file-descriptor capacity on the Gitaly node, denying service to other users of the same node — matching the GitLab HackerOne "DoS / resource exhaustion" impact class for a Gitaly RPC handler.

### Likelihood Explanation
This requires only the ability to push over SSH to a repository the attacker owns — the baseline capability assumed in this audit. No special role, secret, or non-default config is needed; the SSH transport and `git-receive-pack` invocation are the default code path for every push. The attack is trivial and fully repeatable: open an `SSHReceivePack` stream, send the valid first message, and withhold further data indefinitely.

### Recommendation
Apply the same negotiation/idle-stdin timeout mechanism used for upload-pack/upload-archive (`pktline.NewReadMonitor` + a configurable `timeoutTicker`, or a `context.WithTimeout` wrapping the whole RPC/`cmd.Wait()`) to `sshReceivePack`, so that stdin that neither reaches EOF nor sends a boundary packet within a bounded time causes the spawned `git-receive-pack` process and RPC handler to be torn down. Apply an analogous guard to the smarthttp `PostReceivePack` handler in `internal/gitaly/service/smarthttp/receive_pack.go`, which has the identical unbounded `cmd.Wait()` pattern.

### Proof of Concept
```go
func TestReceivePack_stalledStdinNeverTimesOut(t *testing.T) {
    ctx := testhelper.Context(t)
    cfg := testcfg.Build(t)
    cfg.SocketPath = runSSHServer(t, cfg)

    repoProto, _ := gittest.CreateRepository(t, ctx, cfg)
    stream, err := newSSHClient(t, cfg.SocketPath).SSHReceivePack(ctx)
    require.NoError(t, err)

    require.NoError(t, stream.Send(&gitalypb.SSHReceivePackRequest{
        Repository: repoProto, GlId: "user-123",
    }))
    // Deliberately send nothing further, and do NOT call CloseSend().
    // The handler's goroutine + spawned git-receive-pack process should
    // remain blocked forever with no configured timeout to reclaim them.

    done := make(chan error, 1)
    go func() {
        _, err := stream.Recv()
        done <- err
    }()

    select {
    case <-done:
        t.Fatal("expected handler to remain blocked indefinitely (no timeout exists)")
    case <-time.After(30 * time.Second):
        // Demonstrates the handler is still hung after 30s with no deadline
        // exceeded / cancellation, unlike sshUploadPack's negotiation timeout.
    }
}
```
Expected today: the test observes no `DeadlineExceeded`/cancellation and the RPC never completes on its own, in contrast to `TestUploadPackWithSidechannel_timeout`, which demonstrates the equivalent upload-pack path *does* enforce a bound.

// ReadMonitor monitors an io.Reader, waiting for a specified packet. If the
// packet doesn't come within a timeout, a cancel function is called. This can
// be used to place a timeout on the *negotiation* phase of some git commands,
// aborting them if it is exceeded.
//
// This timeout prevents a class of "use-after-check" security issue when the
// access check for a git command is run before the command itself. The user
// has control of stdin for the git command, and if they can delay input for
// an arbitrarily long time, they can gain access days or weeks after the
// access check has completed.
//

// short timeout, and allowing long-lived git operations to complete. The
// negotiation phase is a small proportion of the time taken for a large git
// fetch, for instance, so tighter limits can be placed on it, leading to a
// better mitigation.
