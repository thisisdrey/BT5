### Title
Repository/Object-Pool Creation Permanently Blocked via Pre-Created Target Directory (Existence-Check DoS) - ([File: internal/gitaly/repoutil/create.go])

### Summary
`repoutil.Create` guards against overwriting an existing repository by calling `os.Stat` on the target path and failing if the path already exists. An unprivileged client that can predict or choose a repository's storage-relative path can pre-create an empty directory (or any file) at that path before the legitimate creation RPC runs. This makes the existence check succeed and the RPC permanently fails with `AlreadyExists`/`FailedPrecondition`, blocking legitimate repository or object-pool creation — the same "empty state that isn't really empty" class of bug as the reported ExecutionEnvironment issue, where pre-seeding the target location before the real deployment/creation call causes the guard to (mis)treat the location as already occupied and the operation to be silently/permanently skipped.

### Finding Description
`repoutil.Create` is the shared code path used by `CreateRepository`, `CreateFork`, `CreateRepositoryFromBundle`, `CreateRepositoryFromURL`, `CreateRepositoryFromSnapshot`, and (via `objectpool.Create`) `CreateObjectPool`. Before creating a repository it checks: [1](#0-0) 

and again after acquiring the lock: [2](#0-1) 

Both checks are plain `os.Stat` calls: if the path exists at all — even as an empty directory with no `.git` contents — the function returns `structerr.NewAlreadyExists("repository exists already")` and never creates the repository. This mirrors the reported bug's root cause: the guard tests for "does this location have any content" (`codehash == 0` in the Solidity analog, `os.Stat` success/failure here) rather than testing for "is a valid entity already present here," so an attacker can satisfy the "occupied" condition without actually providing the expected artifact.

`objectpool.Create` has an equivalent, explicitly-confirmed-as-buggy version of the same check: [3](#0-2) 

The test suite for this exact code documents the behavior as intentional-but-acknowledged-buggy: [4](#0-3) 

and `repoutil.Create`'s own test suite documents the same outcome for ordinary repository creation — pre-creating an empty directory at the target path causes creation to permanently fail with no recovery path other than manual intervention: [5](#0-4) 

The `CreateRepository` RPC handler passes the client-supplied `Repository.RelativePath` straight into `repoutil.Create` with no requirement that the path be "reserved" beforehand: [6](#0-5) 

### Impact Explanation
Any client capable of invoking `CreateRepository`/`CreateFork`/`CreateObjectPool` (an "ordinary user" from Gitaly's perspective, since it validates only that the path is a well-formed relative path, not that it's otherwise unclaimed) can permanently deny creation of a repository or object pool at a specific relative path by first creating an empty directory there (e.g. via any RPC or filesystem-adjacent primitive that lets them materialize a directory entry under a storage root, such as a partial/aborted repository operation, or via known/predictable relative-path schemes used by callers like fork/pool creation). This is a denial-of-service against a core RPC handler (repository provisioning), matching the "DoS of a handler" acceptance criterion, and is directly reachable from ordinary gRPC calls without any privileged access, leaked token, or MITM position.

### Likelihood Explanation
Likelihood is moderate-to-high in environments where relative paths for repositories/pools are deterministic or otherwise learnable/racy (this is exactly the scenario the `objectpool` and `repoutil` test suites both already acknowledge and test for — "target exists"/"preexisting directory" — indicating the maintainers were aware of the check's weakness but treated it as acceptable/expected behavior rather than fully closing the race). No privileged actor, token leakage, or MITM is required; only the ability to place a directory entry at the target relative path ahead of the legitimate create call.

### Recommendation
Do not treat "path exists" as equivalent to "repository already exists." Distinguish an empty/incomplete directory from a valid repository, e.g. by checking for expected repository markers (`HEAD`, `objects/`, `refs/`) or content presence (analogous to checking `code.length` rather than `codehash != 0` in the referenced report), and/or reclaim and remove empty directories left behind by failed/incomplete operations before failing the creation attempt, provided ownership/tenancy is verified. At minimum, ensure the existence check cannot be satisfied by a bare empty directory created outside of a legitimate creation attempt.

### Proof of Concept
1. As an ordinary Gitaly client, determine or predict a target `RelativePath` intended for a future `CreateRepository`/`CreateFork`/`CreateObjectPool` call for a given storage.
2. Cause an empty directory to exist at that relative path under the storage root before the legitimate creation call arrives (e.g., by triggering an operation that creates the directory as a side effect, as reproduced deterministically in the existing test `internal/git/objectpool/create_test.go` "target exists" case and `internal/gitaly/repoutil/create_test.go` "preexisting directory" case).
3. Invoke the legitimate `CreateRepository`/`CreateObjectPool` RPC for that path.
4. Observe that `repoutil.Create`/`objectpool.Create` returns `AlreadyExists`/`FailedPrecondition: "target path exists already"` and the repository/object pool is never created, permanently denying provisioning at that path.

func (s *server) CreateRepository(ctx context.Context, req *gitalypb.CreateRepositoryRequest) (*gitalypb.CreateRepositoryResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository, storage.WithSkipRepositoryExistenceCheck()); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	hash, err := git.ObjectHashByProto(req.GetObjectFormat())
	if err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	// When the MVCC backend is requested for new repositories, carry the MVCC reference
	// backend in the context. This selects the MVCC-enabled Git binary for every command
	// run while creating the repository (git-init as well as the subsequent for-each-ref,
	// config and repack commands) and makes git-init use the MVCC ref-format.
	if featureflag.NewRepoMVCCBackend.IsEnabled(ctx) {
		ctx = gitcmd.ContextWithReferenceBackend(ctx, git.ReferenceBackendMVCC)
	}

	if err := repoutil.Create(
		ctx,
		s.logger,
		s.locator,
		s.gitCmdFactory,
		s.catfileCache,
		s.txManager,
		s.repositoryCounter,
		repository,
		func(repo *gitalypb.Repository) error {
			// We do not want to seed the repository with any contents, so we just
			// return directly.
			return nil
		},
		repoutil.WithBranchName(string(req.GetDefaultBranch())),
		repoutil.WithObjectHash(hash),
	); err != nil {
		return nil, structerr.NewInternal("creating repository: %w", err)
	}
