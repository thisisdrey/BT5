## Vulnerability Found

### Title
Unauthenticated attachment content accepted into StackerDB/Atlas cache without hash verification against the requested `content_hash` - ([File: stackslib/src/net/api/posttransaction.rs])

### Summary
The `/v2/transactions` endpoint accepts an `attachment` payload alongside a contract-call transaction and stores it directly into the Atlas attachment cache via `insert_uninstantiated_attachment`, with no check that the attachment's content actually hashes to any `content_hash` that the node is interested in. Any unauthenticated remote peer can flood the "uninstantiated attachments" table with arbitrary blobs.

### Finding Description
In `stackslib/src/net/api/posttransaction.rs` (`try_handle_request`, ~lines 230-251), when a POST transaction includes an attachment and the transaction is a `ContractCall`, the handler calls:

```rust
if network.get_atlasdb().should_keep_attachment(&contract_call.to_clarity_contract_id(), attachment) {
    network.get_atlasdb_mut().insert_uninstantiated_attachment(attachment)...
}
``` [1](#0-0) 

`insert_uninstantiated_attachment` in `stackslib/src/net/atlas/db.rs` (lines 511-536) inserts the attachment keyed by `attachment.hash()` (a hash the *submitter* controls, since it's simply `Hash160::from_data(&self.content)` over attacker-supplied bytes) with no cross-check against any expected/legitimate `content_hash` recorded from a chain-processed `AttachmentInstance`:

```rust
pub fn insert_uninstantiated_attachment(&mut self, attachment: &Attachment) -> Result<(), db_error> {
    ...
    tx.execute(
        "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 0, ?)",
        params![attachment.hash(), attachment.content, now],
    );
    ...
}
``` [2](#0-1) 

Later, when a real `AttachmentInstance` (created from on-chain events, with a genuine `content_hash`) is checked, `check_attachment_instances` in `stackslib/src/net/atlas/download.rs` looks up `find_uninstantiated_attachment(&attachment_instance.content_hash)` and, if found, promotes/serves it as validated content:

```rust
} else if let Ok(Some(attachment)) = atlas_db.find_uninstantiated_attachment(&attachment_instance.content_hash) {
    atlas_db.insert_instantiated_attachment(&attachment)?;
    do_if_found(atlas_db, &attachment_instance)?;
    ...
}
``` [3](#0-2) 

Because the uninstantiated store is keyed purely by a self-declared hash equal to `Hash160::from_data(content)`, this path is internally hash-consistent (an attacker cannot forge a *different* hash for their own chosen content in a way that collides with a legitimate `content_hash` without a hash collision). However, the equality being broken here is a different one: **"submitted-for-caching" is treated as equivalent to "authorized/expected by an on-chain attachment instance."** There is no restriction requiring the submitter to prove the attachment corresponds to any pending/real `AttachmentInstance`, `should_keep_attachment` only filters by contract id/size, not by matching a specific outstanding `content_hash`. This allows any remote, unauthenticated peer (this endpoint requires no auth) to freely populate the bounded `attachments` table (`max_uninstantiated_attachments`) with junk data tied to arbitrary contract ids, causing legitimate uninstantiated attachments to be evicted (`evict_k_oldest_uninstantiated_attachments`) before the real content the node needs ever arrives from a well-behaved peer.

### Impact Explanation
This is a bounded compute/storage DoS on a write-capable RPC endpoint reachable by any unauthenticated peer: repeatedly POSTing contract-call transactions (which can be cheap/invalid so long as they parse) with distinct attachment blobs causes continuous eviction churn in the Atlas uninstantiated-attachment cache, denying real BNS/Atlas attachment resolution for legitimate data pending download from the network. This matches the "attachment/BNS mismatch" / bounded-compute-DoS class named in scope.

### Likelihood Explanation
High likelihood: `/v2/transactions` requires no authentication, and `insert_uninstantiated_attachment` is called unconditionally whenever `should_keep_attachment` returns true (which only checks contract id and size, not an outstanding request) — no signature, no owner check, no correlation to a genuine pending `content_hash` is required before caching.

### Recommendation
Before calling `insert_uninstantiated_attachment`, verify that the attachment's content hash corresponds to a currently pending/unresolved `AttachmentInstance.content_hash` for that contract (i.e., only cache attachments that some genuine, previously-recorded on-chain instance is actually waiting for), rather than accepting and caching arbitrary attacker-supplied content merely because it accompanies a submitted transaction.

### Proof of Concept
1. Submit repeated `POST /v2/transactions` requests, each with a valid-looking `ContractCall` transaction targeting a BNS/Atlas-tracked contract and a distinct, large `attachment` payload (up to `attachments_max_size`).
2. Each call passes `should_keep_attachment` (size/contract filter only) and unconditionally inserts into the `attachments` table via `insert_uninstantiated_attachment`.
3. Once `max_uninstantiated_attachments` is reached, each new submission evicts the oldest entries (`evict_k_oldest_uninstantiated_attachments`), including any legitimately pending attachments the node is trying to resolve via the downloader, degrading Atlas attachment availability for the node and downstream event observers.

    pub fn insert_uninstantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        // Insert the new attachment
        let uninstantiated_attachments = self.count_uninstantiated_attachments()?;
        if uninstantiated_attachments >= self.atlas_config.max_uninstantiated_attachments {
            let to_delete =
                1 + uninstantiated_attachments - self.atlas_config.max_uninstantiated_attachments;
            self.evict_k_oldest_uninstantiated_attachments(to_delete)?;
        }

        let tx = self.tx_begin()?;
        let now = util::get_epoch_time_secs() as i64;
        let res = tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 0, ?)",
            params![
                attachment.hash(),
                attachment.content,
                now,
            ],
        );
        res.map_err(db_error::SqliteError)?;
        tx.commit().map_err(db_error::SqliteError)?;
        Ok(())
    }
