### Title
Client-controlled `remote_ip` gRPC metadata lets an authenticated Gitaly client evade or partition the pack-objects concurrency limiter - (File: internal/gitaly/service/hook/pack_objects.go)

### Summary
The pack-objects concurrency limiter keys its per-caller quota off a `remote_ip` value that is passed as ordinary request/metadata data rather than derived from an authenticated transport-level source, allowing a caller to manipulate the limiting key and defeat the intended cap on concurrent `git-pack-objects` invocations.

### Finding Description
`PackObjectsHookWithSidechannelRequest.RemoteIp` is explicitly documented as "the key for concurrency limiting before we trigger git-pack-objects command" [1](#0-0) , and is used directly to select the `packObjectsLimiter`'s bucket in `runPackObjectsLimited` [2](#0-1) . The value originates from `payload.UserDetails.RemoteIP`, which `gitaly-hooks` simply forwards as an outgoing gRPC metadata field (`remote_ip`) without any cryptographic binding to the real peer address [3](#0-2) [4](#0-3) . That metadata is picked up later and copied verbatim into `UserDetails.RemoteIP` when building the hook environment for both upload-pack and receive-pack flows [5](#0-4) [6](#0-5) .

In `packObjectsHook`, this attacker-influenced string is used to decide the limiting key, and it is explicitly special-cased to fully bypass the limiter when parsed as a loopback address: [7](#0-6) 

This mirrors the structural pattern of the referenced report: an entity that is expected to be gated by a fixed cap (there, `mintCeiling`; here, `packObjectsLimiter`'s per-key concurrency slot) is instead controlled through a value the caller supplies and can manipulate to reset/evade the accounting used for the cap (there, calling `lowerHasMinted()`; here, supplying/varying the `remote_ip` field). Because the limiter bucket is chosen purely by string equality on this field, a caller can:
1. Send a `remote_ip` value that parses to a loopback address (e.g. `"127.0.0.1"`), which the code explicitly treats as "ignore loop-back IPs" and routes to the unlimited `runPackObjects` path instead of `runPackObjectsLimited` [8](#0-7) , or
2. Send a distinct/rotating `remote_ip` (or leave it empty/invalid, which is also excluded from limiting per the same check) for each concurrent hook invocation so each one lands in its own keyed semaphore bucket in `keyedConcurrencyLimiter`/`ConcurrencyLimiter.Limit`, never sharing the same bucket and thus never being queued or rejected [9](#0-8) .

The tests demonstrate the server's own expectation that limiting is keyed purely on this string, and that varying it (or using loopback/invalid values) intentionally disables limiting: [10](#0-9) .

### Impact Explanation
`git-pack-objects` invocations are CPU/memory/disk-I/O intensive. The `packObjectsLimiter` exists specifically to bound the number of concurrent pack-objects processes per remote-IP/user/repo key so that a single client cannot exhaust Gitaly node resources. By manipulating the value used purely as an identity key for that limiter (spoofing loopback, sending malformed IPs, or rotating fake IPs per request), a single client authorized to fetch/clone can force each of its concurrent fetch requests into a distinct, unlimited bucket, defeating the resource-exhaustion protection and creating a denial-of-service vector against the Gitaly node (and any co-located repositories/tenants). This is analogous in severity to the referenced Medium-severity finding: no cryptographic breach occurs, but a party that is expected to be capped by an internal ceiling is able to reset/evade that ceiling via a value they control.

### Likelihood Explanation
Reachability depends on whether external, less-trusted callers (rather than only the internal `gitaly-hooks` binary talking over the authenticated internal socket) can influence the `remote_ip` gRPC metadata/field that ultimately reaches `packObjectsHook`. Based on the code reviewed, `remote_ip` metadata is propagated end-to-end as plain string data (via `metadata.AppendToOutgoingContext`/`GetValue`, and copied into the protobuf `RemoteIp` field) without a check that ties it to the actual peer address recorded by gRPC/TCP; the only validation present is IP-format parsing for the loopback-bypass decision [11](#0-10) . I could not, within the available index, fully trace the very first hop where `remote_ip` metadata is populated for externally initiated SSH/HTTP fetches (i.e., whether it comes from a trusted transport-derived source at the edge, such as Praefect/Workhorse/gitlab-shell, or is accepted as client-supplied header data such as `X-Forwarded-For`). This is a genuine gap in what I could verify from the indexed code, so likelihood should be treated as **uncertain/moderate** pending confirmation of that upstream trust boundary.

### Recommendation
- Derive the pack-objects concurrency-limiting key from a value gRPC/Gitaly can independently verify (e.g., the actual peer address from the transport layer, or a value cryptographically bound to the authenticated caller/session), rather than trusting the `remote_ip` string forwarded through metadata/protobuf fields end-to-end.
- If `remote_ip` must remain client/metadata-supplied for logging purposes, do not use it as the sole/primary concurrency-limiting key; combine it with a value the server can independently attest (e.g., authenticated user ID from the actual auth token, not just `GlId`/`GlUsername` strings passed alongside it) and remove the loopback special-case bypass (or restrict it strictly to Gitaly-server-to-Gitaly-server internal socket traffic authenticated by `InternalSocketToken`, verified server-side rather than inferred from the IP string).
- Add an explicit test that verifies clients cannot bypass or partition the pack-objects limiter merely by varying the `remote_ip` field value across requests originating from the same authenticated identity/connection.

### Proof of Concept
Conceptual PoC based on the reachable code path and existing test harness in `pack_objects_test.go`:
1. A client performs `git fetch`/`clone`, causing `SSHUploadPackWithSidechannel`/`PostUploadPackWithSidechannel` to run `git-upload-pack`, which invokes the configured `gitaly-hooks` `pack-objects` hook, forwarding `remote_ip` from the client's `UserDetails.RemoteIP` [12](#0-11) .
2. If the pipeline populating `UserDetails.RemoteIP`/`remote_ip` metadata is influenceable by the requesting party (e.g., via forwarded-header handling upstream), the client issues N concurrent fetches each carrying either a loopback-formatted `remote_ip` (e.g. `"127.0.0.1"`) or a distinct fake IP per request.
3. Per `packObjectsHook`'s branch on `ipAddr.IsLoopback()` [13](#0-12) , loopback-tagged requests skip `runPackObjectsLimited` entirely; distinct-IP-tagged requests each land in a separate `keyedConcurrencyLimiter` bucket [14](#0-13) , so the configured `Initial`/`Max` concurrency setting (as demonstrated with `Initial: 1` in `TestPackObjects_concurrencyLimit`) is never enforced across the N concurrent calls [15](#0-14) .
4. This produces unbounded concurrent `git-pack-objects` subprocesses from a single client, contrary to the limiter's intended protection.

**Caveat:** I was not able to fully confirm, from the indexed portion of the codebase, the exact point where `remote_ip` metadata is first set for externally-originated SSH/HTTP requests (i.e., whether it's derived strictly from a trusted transport source at the edge or accepted from client-influenceable data). This should be verified in a live Devin session with full repository access before treating this as a confirmed exploit rather than an analog-pattern hypothesis.

```go
// WithPackObjectsHookEnv provides metadata for gitaly-hooks so it can act as a pack-objects hook.
func WithPackObjectsHookEnv(objectHash git.ObjectHash, repo *gitalypb.Repository, protocol string) CmdOpt {
	return func(ctx context.Context, cfg config.Cfg, gitCmdFactory CommandFactory, cc *cmdCfg) error {
		if !cfg.PackObjectsCache.Enabled {
			return nil
		}

		if repo == nil {
			return fmt.Errorf("missing repo: %w", ErrInvalidArg)
		}

		userDetails := &UserDetails{
			Protocol: protocol,
			UserID:   metadata.GetValue(ctx, "user_id"),
			Username: metadata.GetValue(ctx, "username"),
			RemoteIP: metadata.GetValue(ctx, "remote_ip"),
		}

		if err := cc.configureHooks(
			ctx,
			cfg,
			objectHash,
			repo,
			gitCmdFactory,
			userDetails,
			PackObjectsHook,
		); err != nil {
			return fmt.Errorf("pack-objects hook configuration: %w", err)
		}

		cc.globals = append(cc.globals, ConfigPair{
			Key:   "uploadpack.packObjectsHook",
			Value: cfg.BinaryPath("gitaly-hooks"),
		})

		return nil
	}
}
```

```go
func (c *ConcurrencyLimiter) Limit(ctx context.Context, limitingKey string, f LimitedFunc) (interface{}, error) {
	span, ctx := tracing.StartSpanIfHasParent(
		ctx,
		"limiter.ConcurrencyLimiter.Limit",
		[]attribute.KeyValue{
			attribute.String("key", limitingKey),
		},
	)
	defer span.End()

	if c.currentLimit() <= 0 {
		return f()
	}

	sem := c.getConcurrencyLimit(limitingKey)
	defer c.putConcurrencyLimit(limitingKey)

	start := time.Now()

	if err := sem.acquire(ctx, limitingKey); err != nil {
		queueTime := time.Since(start)
		switch {
		case errors.Is(err, ErrMaxQueueSize):
			c.monitor.Dropped(ctx, limitingKey, sem.queueLength(), sem.inProgress(), queueTime, "max_size")
			return nil, structerr.NewResourceExhausted("%w", ErrMaxQueueSize).WithDetail(&gitalypb.LimitError{
				ErrorMessage: err.Error(),
				RetryAfter:   durationpb.New(0),
			})
		case errors.Is(err, ErrMaxQueueTime):
			c.monitor.Dropped(ctx, limitingKey, sem.queueLength(), sem.inProgress(), queueTime, "max_time")
			return nil, structerr.NewResourceExhausted("%w", ErrMaxQueueTime).WithDetail(&gitalypb.LimitError{
				ErrorMessage: err.Error(),
				RetryAfter:   durationpb.New(0),
			})
		default:
			c.monitor.Dropped(ctx, limitingKey, sem.queueLength(), sem.inProgress(), queueTime, "other")
			return nil, fmt.Errorf("unexpected error when dequeueing request: %w", err)
		}
	}
	defer sem.release()

	c.monitor.Enter(ctx, sem.inProgress(), time.Since(start))
	defer c.monitor.Exit(ctx)
	return f()
}
```
