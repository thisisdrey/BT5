### Title
Missing zero-guard on `totalEnergyWeight`/`totalNetWeight` in `RepositoryImpl.calculateGlobalEnergyLimit`/`calculateGlobalNetLimit` causes divide-by-zero crash or unbounded energy/bandwidth limit — (File: `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java`)

### Summary
The external report describes a class of bug where a rate-calculation formula fails to guard against a denominator-affecting value (`reserves`) that can grow or shrink to a degenerate state, causing the rate to diverge or the calculation to revert, bricking the system. The same bug class exists in java-tron's `RepositoryImpl.calculateGlobalEnergyLimit`/`calculateGlobalNetLimit`, which divide by `totalEnergyWeight`/`totalNetWeight` without the zero-guard that the parallel, non-TVM implementation (`EnergyProcessor`/`BandwidthProcessor`) explicitly has.

### Finding Description
`chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java` guards the division: [1](#0-0) 
against `totalEnergyWeight <= 0` when `allowNewReward()` is active, returning `0` instead of dividing.

However, the TVM-facing `RepositoryImpl.calculateGlobalEnergyLimit`, which is used by native contract processors reachable from ordinary transactions (e.g. `FreezeV2Util.queryDelegatableResource`, `UnDelegateResourceProcessor`), has no such runtime guard: [2](#0-1) 

The only protection is `assert totalEnergyWeight > 0;`, but Java assertions are disabled by default in production JVMs (no `-ea` flag), so this check is a no-op in a running node. If `totalEnergyWeight` (or the analogous `totalNetWeight` in `calculateGlobalNetLimit`, lines 257–266 same file) is ever `0`:
- With `hardenResourceCalculation()` enabled, `BigInteger.divide(BigInteger.ZERO)` throws `ArithmeticException`, an unhandled exception in a code path reachable from resource-delegation queries and native contract execution triggered by ordinary signed transactions.
- With the legacy (non-hardened) path, `(double) totalEnergyLimit / totalEnergyWeight` evaluates to `Infinity`, and `energyWeight * Infinity` cast back to `long` yields `Long.MAX_VALUE`, silently granting an effectively unlimited/unbacked energy or bandwidth limit to the caller.

This mirrors the report's two failure modes exactly: (1) the rate/limit formula "approaches infinity" as the denominator degenerates, and (2) the calculation "reverts, bricking" the affected functionality.

### Impact Explanation
- The `Infinity`/`Long.MAX_VALUE` branch produces an unbacked resource limit: an account could be granted an absurdly large `calculateGlobalEnergyLimit`/`calculateGlobalNetLimit`, letting it bypass the intended proportional resource allocation and consume/generate more energy or bandwidth than it should be entitled to — a form of unbacked resource issuance analogous to unbacked balance.
- The `ArithmeticException` branch, since it is unhandled at this call depth, can propagate out of native-contract/TVM execution paths invoked during ordinary transaction processing, potentially crashing transaction/block execution for any node that reaches `totalEnergyWeight == 0`/`totalNetWeight == 0`, i.e. a node crash/halt condition triggered by a specific but reachable network state.

### Likelihood Explanation
`totalEnergyWeight`/`totalNetWeight` are network-wide aggregates decremented by every account's unfreeze operations (`UnfreezeBalanceV2Processor.updateTotalResourceWeight`, `UnfreezeBalanceActuator`). While driving the global aggregate to exactly zero across an entire mainnet is unlikely under normal operation, it is a realistic condition on smaller/private/permissioned networks (or transient states after a burst of unfreezes) and is entirely reachable without any privileged role — any account performing freeze/unfreeze V2 operations (broadcastable, unprivileged transactions) contributes to this shared counter. The complete absence of the guard that exists in the parallel `EnergyProcessor`/`BandwidthProcessor` implementations indicates an inconsistency introduced when the TVM-native-contract path (`RepositoryImpl`) was added, strongly suggesting this is an overlooked edge case rather than an intentionally accepted risk.

### Recommendation
Add the same `totalEnergyWeight <= 0` / `totalNetWeight <= 0` early-return guard used in `EnergyProcessor`/`BandwidthProcessor` to `RepositoryImpl.calculateGlobalEnergyLimit` and `calculateGlobalNetLimit`, returning `0` (or another safe defined value) instead of relying on a disabled `assert` statement, for both the hardened (`BigInteger`) and legacy (`double`) code paths.

### Proof of Concept
1. On a network (e.g., private/test network) drive `DynamicPropertiesStore.getTotalEnergyWeight()` to `0` by having all accounts fully unfreeze their energy-frozen balances via `UnfreezeBalanceV2Actuator`/native `unfreezeBalanceV2`.
2. Trigger any code path that calls `RepositoryImpl.calculateGlobalEnergyLimit` (e.g., a TVM contract calling the freeze/delegate-resource native contract via `FreezeV2Util.queryDelegatableResource`, or `UnDelegateResourceProcessor`), which is reachable from an ordinary signed smart-contract-invoking transaction.
3. Observe:
   - With `ALLOW_HARDEN_RESOURCE_CALCULATION` (`hardenResourceCalculation()`) enabled: `BigInteger.divide(BigInteger.ZERO)` throws an uncaught `ArithmeticException` during transaction/native-contract execution.
   - With it disabled: the returned energy limit becomes `Long.MAX_VALUE` (via double `Infinity` cast), granting the calling account an unbacked, effectively unlimited energy allocation.

Note: full confirmation that no upstream guard exists between the transaction dispatch layer and `RepositoryImpl` (i.e., that `ArithmeticException` is truly unhandled all the way to block application) requires additional tracing of every native-contract processor's exception handling, which the indexed code snippets available here do not fully cover; a Devin session with complete repository access could verify the exact exception-propagation boundary before treating the crash scenario as fully proven.

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
