### Title
Unbounded `GetAssetIssueList` REST/gRPC endpoints allow attacker-inflatable, unlimited-size responses causing node OOM/unavailability - (File: `framework/src/main/java/org/tron/core/Wallet.java`)

### Summary
`Wallet.getAssetIssueList()` (no-arg) dumps **every** TRC10 asset issue in the database into a single in-memory `AssetIssueList` protobuf with no cap on the number of entries, and this method backs several always-enabled, unauthenticated HTTP/gRPC endpoints (`/wallet/getassetissuelist`, `/walletsolidity/getassetissuelist`, `/walletpbft/getassetissuelist`, and the gRPC `Wallet/WalletSolidity.GetAssetIssueList` RPCs). Unlike the sibling paginated API, this path enforces no `offset`/`limit`/max-item cap, mirroring the XWiki advisory pattern where an unauthenticated REST resource returns the full unbounded item collection.

### Finding Description
`Wallet.getAssetIssueList()` iterates `getAllAssetIssues()` from `AssetIssueStore`, which streams the entire underlying LevelDB/RocksDB column for asset issues and materializes it as a `List<AssetIssueCapsule>`, then builds a full `AssetIssueList` protobuf response with every entry: [1](#0-0) [2](#0-1) 

This unbounded method is directly exposed via multiple always-on network-facing entry points that any anonymous client can call:
- HTTP: `GetAssetIssueListServlet.doGet/doPost` on `/wallet/getassetissuelist`, calling `wallet.getAssetIssueList()` with no limit parameter accepted. [3](#0-2) 
- gRPC: `WalletApi`/`WalletSolidityApi.getAssetIssueList(EmptyMessage, ...)` on both the FullNode and Solidity/PBFT gRPC services, which take no size-limiting parameter at all (`EmptyMessage`). [4](#0-3) 

By contrast, the *paginated* sibling API (`getAssetIssueList(offset, limit)`/`/wallet/getpaginatedassetissuelist`) does cap results at `ASSET_ISSUE_COUNT_LIMIT_MAX` via `AssetIssueStore.getAssetIssuesPaginated`: [5](#0-4) 
but the unbounded default endpoint remains reachable and unguarded, exactly the class of defect described in the XWiki advisory (`/rest/wikis/xwiki/spaces` returning all pages by default with no configurable limit).

Critically, the size of this dataset is **not fixed or small** — it grows with every TRC10 token ever issued on the chain, and issuing a new asset is a normal, permissionless, broadcastable transaction (`AssetIssueContract`) available to any funded account. This gives an unprivileged actor a way to actively grow the unbounded dataset over time (by issuing many low-cost/1-TRX-fee asset issues) and then have any client trigger full materialization and full JSON/protobuf serialization of the entire list on every call to the unbounded endpoint, unlike a naturally-bounded, small list.

Only a global QPS-based `RateLimiterServlet` throttles call *frequency*, not response *size*, so this offers no protection against a single large/expensive request: [6](#0-5) 

### Impact Explanation
Each call to the unbounded `getassetissuelist` HTTP endpoint or `GetAssetIssueList` gRPC method forces the node to: (1) fully iterate the asset-issue store, (2) load every `AssetIssueCapsule` into memory, (3) run bandwidth-usage accounting (`BandwidthProcessor.updateUsage`) per item, and (4) build and serialize a single large protobuf/JSON response. As the number of issued TRC10 assets grows (attacker-controllable), the memory and CPU cost of a single request grows unbounded, which can exhaust heap/GC headroom or block servlet/gRPC threads long enough to degrade or crash the FullNode/SolidityNode/PBFT node process — a denial-of-service against a live node that any anonymous API client can reach with zero privileges, matching the High severity of the XWiki analog (uncontrolled resource consumption, CWE-770).

### Likelihood Explanation
The endpoint requires no authentication, no special permissions, and no crafted transaction — a single GET/POST or gRPC call suffices. The dataset it returns can be inflated over time by any account broadcasting ordinary `AssetIssueContract` transactions (a normal, cheap, permissionless operation), meaning the attack surface is entirely within reach of an "unprivileged transaction broadcaster" as scoped. Likelihood is high given the low cost of triggering the call repeatedly and the ease of growing the underlying dataset.

### Recommendation
Enforce a maximum item cap (mirroring `ASSET_ISSUE_COUNT_LIMIT_MAX` already used by `getAssetIssuesPaginated`) inside the unbounded `Wallet.getAssetIssueList()` path itself (and any HTTP/gRPC surface that calls it), or deprecate/limit the non-paginated endpoints in favor of the paginated variant with a mandatory, server-enforced upper bound on `limit`, consistent with the XWiki fix pattern of returning an error instead of an oversized response.

### Proof of Concept
1. From any account, repeatedly broadcast `AssetIssueContract` transactions to create a large number of TRC10 tokens (this is a standard, permissionless operation).
2. As an anonymous client, call `GET http://<node>:8090/wallet/getassetissuelist` (or the gRPC `Wallet.GetAssetIssueList(EmptyMessage)` / `WalletSolidity.GetAssetIssueList`).
3. Observe that the node serializes the entire asset-issue set into a single response with no `limit`/`offset` restriction, unlike `/wallet/getpaginatedassetissuelist`, which is capped; repeated concurrent calls against a sufficiently large asset-issue set degrade node responsiveness/memory.

  private List<AssetIssueCapsule> getAssetIssuesPaginated(List<AssetIssueCapsule> assetIssueList,
      long offset, long limit) {
    if (limit < 0 || offset < 0) {
      return null;
    }

    if (assetIssueList.size() <= offset) {
      return null;
    }
    assetIssueList.sort((o1, o2) -> {
      if (o1.getName() != o2.getName()) {
        return o1.getName().toStringUtf8().compareTo(o2.getName().toStringUtf8());
      }
      return Long.compare(o1.getOrder(), o2.getOrder());
    });
    limit = limit > ASSET_ISSUE_COUNT_LIMIT_MAX ? ASSET_ISSUE_COUNT_LIMIT_MAX : limit;
    long end = offset + limit;
    end = end > assetIssueList.size() ? assetIssueList.size() : end;
    return assetIssueList.subList((int) offset, (int) end);
  }
