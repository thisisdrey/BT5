### Title
Relay address ownership is never verified against the sender's certificate identity, allowing peer-address spoofing in `CreateRelayRequest`/`CreateRelayResponse` - (File: relay_manager.go)

### Summary
`relayManager.handleCreateRelayRequest` and `handleCreateRelayResponse` trust the `RelayFromAddr`/`RelayToAddr` fields embedded in an attacker-controlled `NebulaControl` message as the true identity of the relay participant, without ever checking that the claimed address (`from`) actually belongs to the authenticated peer `h` that sent the message. This is the direct analog of the Tapioca Magnetar bug: an operation is executed on behalf of an entity (`from`) that the caller (`h`) was never proven to own or represent.

### Finding Description
Any already-connected peer `h` (a `*HostInfo` whose tunnel is up, so its own real identity is `h.vpnAddrs`, taken from its certificate) can send a `NebulaControl` message of type `NebulaControl_CreateRelayRequest` with an arbitrary `RelayFromAddr` value that has nothing to do with `h`'s own certificate-bound VPN address: [1](#0-0) 

The only checks performed are that `from` is not one of my own addresses and that `target` (`RelayToAddr`) resolves to something meaningful — there is no check that `from` corresponds to `h.vpnAddrs` (i.e., that `h` actually owns/represents that address): [2](#0-1) 

When the message's target is the local node, the code immediately calls `AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)`, which installs relay routing state keyed on `h`'s HostInfo for the attacker-chosen `from` address, and marks it `Established` without any confirmation that the real owner of `from` requested or consented to this relay: [3](#0-2) 

Similarly, in the forwarding branch, `AddRelay(rm.l, peer, f.hostMap, from, nil, ForwardingType, Requested)` installs relay state on a third-party `peer` HostInfo keyed on the spoofed `from` address: [4](#0-3) 

`EstablishRelay`/`handleCreateRelayResponse` follow the same pattern — they act purely on the `RelayFromAddr`/`RelayToAddr` values carried in the message body, never cross-checking them against the sending `HostInfo`'s certificate-verified `vpnAddrs`: [5](#0-4) 

In short, the wire-level `RelayFromAddr` claim is treated as authoritative identity, exactly like Magnetar trusted the NFT id in `_actionCalldata` without checking that `msg.sender` owned it.

### Impact Explanation
A connected peer can register itself in another node's relay tables as the relay-of-record for a third party's VPN address it does not own, poisoning `HostMap.Relays` / `relayState` with a spoofed `Established` relay entry for that victim address. This can:
- Cause the responder to believe a relay to/for the victim's `vpnIp` is already `Established` through the attacker's hostinfo, redirecting future relay-assisted handshake/data traffic destined for that victim through the attacker-controlled path.
- Create index/state collisions when the genuine victim later attempts to establish its own relay (`existingRelay.RemoteIndex != m.InitiatorRelayIndex` mismatch errors), degrading or blocking legitimate relay use for that victim (denial of service).
- Enable a form of remote hostmap/relay state poisoning purely from a control-plane message field, without any proof of address ownership.

### Likelihood Explanation
Any node that has completed a normal Nebula handshake (i.e., holds a HostInfo entry) can send this control message at will; no additional privileges, admin access, or special network position are required beyond being a mesh participant capable of reaching the target over an existing tunnel. The vulnerable code path (`HandleControlMsg` → `handleCreateRelayRequest`) is reached on every relay-capable node whenever relay usage is enabled (`relay.use_relays`/`relay.am_relay`), which is a common deployment configuration.

### Recommendation
Before acting on `RelayFromAddr` (and `RelayToAddr` where it names the sender in `CreateRelayResponse`), verify it matches one of the sending `HostInfo`'s certificate-verified `vpnAddrs` (`h.vpnAddrs`). Reject and drop the control message if the claimed relay-from address does not belong to the authenticated sender, mirroring how Magnetar should check NFT ownership before acting on `_actionCalldata` targeting another user's token.

### Proof of Concept
1. Attacker `A` establishes a normal, valid tunnel to node `B` (so `B` has a `HostInfo` for `A` with `A`'s real `vpnAddrs`).
2. `A` sends `B` a `NebulaControl{Type: CreateRelayRequest, RelayFromAddr: <victim V's vpnIp>, RelayToAddr: <B's vpnIp>, InitiatorRelayIndex: idx}` over the existing tunnel.
3. In `handleCreateRelayRequest`, `f.myVpnAddrsTable.Contains(target)` is true (target is `B`), and since no existing relay state exists for `V`, `B` calls `AddRelay(rm.l, h, f.hostMap, V, &idx, TerminalType, Established)` — where `h` is `A`'s HostInfo, not `V`'s.
4. `B` now believes it has an `Established` relay to `V` via `A`, despite `V` never participating, demonstrating the missing ownership check on `RelayFromAddr`.
