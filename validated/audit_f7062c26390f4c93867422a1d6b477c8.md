### Title
Active (non-owner) multi-sig permission can be granted the `AccountPermissionUpdateContract` capability, allowing a limited key to overwrite the account's Owner permission and seize full control - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
TRON's multi-sig permission model lets an account owner define scoped "Active" permissions whose allowed operations are restricted by a 256-bit `operations` bitmap tied to `ContractType`. `AccountPermissionUpdateContract` (the contract type used to *rewrite the account's own Owner/Witness/Active permissions*) is not excluded from the set of contract types that can be enabled in that bitmap. Consequently, any Active-permission key that is granted this single bit can broadcast an `AccountPermissionUpdateContract` transaction and unilaterally overwrite the account's Owner permission, without ever needing Owner-level signature weight. This mirrors the Cassandra advisory's root cause: a permission meant to be scoped/limited (MODIFY on ALL KEYSPACES / an "Active" TRON permission) is allowed to perform an "unsafe" administrative/system action (writing to `system_auth` / rewriting the account's permission tree), letting the holder escalate to the equivalent of superuser (Owner) control.

### Finding Description
The permission-check path for any signed transaction is generic and type-agnostic:
- `TransactionCapsule.checkPermission()` only validates that (a) the permission type is `Active` when `permissionId != 0`, and (b) the specific `ContractType` bit is set in that permission's `operations` bitmap — it applies uniformly to every `ContractType`, including `AccountPermissionUpdateContract`. [1](#0-0) 

- `AccountPermissionUpdateActuator.checkPermission()` (the *validator for setting up permissions*) explicitly allows any `ContractType` present in `dynamicStore.getAvailableContractType()` to be included in an Active permission's operations bitmap, with no special exclusion for `AccountPermissionUpdateContract` itself (unlike `ClearABIContract` and `UpdateBrokerageContract`, which are excluded from the "available" set per the test at line 936-937 of `AccountPermissionUpdateActuatorTest.java`). [2](#0-1) [3](#0-2) 

- `AccountPermissionUpdateActuator.execute()` then unconditionally applies the incoming `owner`/`witness`/`actives` permissions to the account and persists them — the only prior authorization performed is the generic signature-weight check above; there is no additional rule such as "a signer using a non-zero (Active) `permissionId` cannot modify the Owner permission." [4](#0-3) 

- `AccountCapsule.updatePermissions()` fully replaces the Owner permission (`builder.setOwnerPermission(owner)`), so a single successful call from an Active key with this bit set can hand Owner control (or lock it) to an attacker-chosen key set, with no threshold-of-Owner-keys requirement. [5](#0-4) 

Root cause: the permission-scoping mechanism (the `operations` bitmap) treats `AccountPermissionUpdateContract` as an ordinary, delegable capability rather than a privileged, Owner-only action, so an Active key — intended to be scoped to specific low-risk transaction types — can be misused (via an operator/owner misconfiguration, or a malicious/compromised co-signer on a threshold Active key) to unilaterally rewrite the account's entire permission hierarchy including Owner.

### Impact Explanation
If an account owner grants an Active permission that includes the `AccountPermissionUpdateContract` bit (a valid, non-excluded bit per the actuator's own validation), any key holder meeting that Active permission's threshold can:
1. Overwrite the account's Owner permission entirely, replacing original owner keys with attacker-controlled keys, permanently locking the legitimate owner out of the account (irreversible loss of account control/funds).
2. Escalate from a narrowly scoped Active role to full account (Owner-equivalent) authority, bypassing the very threshold/weight protections the multi-sig model is designed to enforce.

This is a concrete unauthorized-account-takeover / permanent-loss-of-funds-control scenario, directly analogous to Cassandra's MODIFY-to-superuser escalation.

### Likelihood Explanation
Exploitation requires the account owner (or a threshold-satisfying co-signer set) to have configured an Active permission with the `AccountPermissionUpdateContract` bit enabled — analogous to the Cassandra precondition of granting MODIFY on ALL KEYSPACES. This is a realistic misconfiguration for exchanges/custodians who set up broad "operational" Active keys without realizing this specific bit grants full account-permission rewrite capability, since the system does not warn about or block it, and the bit is a normal, "available" (non-excluded) contract type in the validation logic.

### Recommendation
Exclude `AccountPermissionUpdateContract` from the set of contract types (`getAvailableContractType()`) that can be granted to non-Owner (Active) permissions, or explicitly reject `AccountPermissionUpdateContract` transactions signed with a non-zero `permissionId` in `TransactionCapsule.checkPermission()` / `AccountPermissionUpdateActuator.validate()`, requiring Owner-permission signature for any transaction that modifies the account's permission structure.

### Proof of Concept
1. Account owner creates an Active permission (id=2, threshold=1) whose `operations` bitmap has the bit for `AccountPermissionUpdateContract` set (this passes `AccountPermissionUpdateActuator.checkPermission()` validation since it's not excluded).
2. The Active-permission key signs and broadcasts an `AccountPermissionUpdateContract` transaction with `permission_id = 2`, setting a new `Owner` permission whose keys are entirely attacker-controlled.
3. `TransactionCapsule.checkPermission()` passes because the operations bit for `AccountPermissionUpdateContract` is set for permission id 2 [1](#0-0) .
4. `AccountPermissionUpdateActuator.execute()` calls `account.updatePermissions(...)`, replacing the account's Owner permission with the attacker's keys [4](#0-3) .
5. The original account owner is now permanently locked out; the attacker holds full Owner-level control of the account and its funds.

  public void updatePermissions(Permission owner, Permission witness, List<Permission> actives) {
    Builder builder = this.account.toBuilder();

    owner = owner.toBuilder().setId(0).build();
    builder.setOwnerPermission(owner);
    if (witness != null && builder.getIsWitness()) {
      witness = witness.toBuilder().setId(1).build();
      builder.setWitnessPermission(witness);
    }

    builder.clearActivePermission();
    if (actives != null) {
      for (int i = 0; i < actives.size(); i++) {
        Permission permission = actives.get(i).toBuilder().setId(i + 2).build();
        builder.addActivePermission(permission);
      }
    }

    this.account = builder.build();
  }
