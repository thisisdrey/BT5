### Title
Out-of-bounds/exception-inducing array read when parsing attacker-controlled ABI offsets in `ValidateMultiSign`/`BatchValidateSign` precompiles - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The DNS-parsing analog (CVE-2026-24028) is a bug class where attacker-supplied, length/offset-prefixed binary data is walked with manual pointer arithmetic that is not fully bounds-checked against the buffer size, causing an out-of-bounds read. The same bug class exists in java-tron's `ValidateMultiSign` and `BatchValidateSign` precompiled contracts, which parse a raw calldata byte array into a `DataWord[]` and then use attacker-controlled offset/length words taken from that array to index further into the same array and into the raw byte buffer, without validating that the derived offsets/lengths stay within bounds.

### Finding Description
`ValidateMultiSign.execute` and `BatchValidateSign.doExecute` decode the raw call data into 32-byte words with `DataWord.parseArray(rawData)`, then read attacker-controlled words (`words[3]`, `words[1]`, `words[2]`) and use their `intValueSafe()` values, divided by `WORD_SIZE`, as fresh indices into the same `words` array: [1](#0-0) 

Those indices are handed to `extractBytesArray` / `extractSigArray`, which read `words[offset].intValueSafe()` as an array length and then loop, reading `words[offset + i + 1]` for each element and computing yet another offset (`bytesOffset`) used to slice the *original byte buffer* via `extractBytes`: [2](#0-1) 

`extractBytes` performs `Arrays.copyOfRange(data, offset, offset + len)` with no upper bound check against `data.length`, and `extractBytesArray`/`extractSigArray` index `words[...]` with values derived purely from attacker-supplied 32-byte words, with only a partial guard (`offset > words.length - 1`) that does not protect the `words[offset + i + 1]` accesses inside the loop, nor the `bytesOffset`/`bytesLen` derived offsets passed into `extractBytes`. A crafted `bytesOffset`/`bytesLen`/array-length combination can push `offset` beyond `words.length` or `offset+len` beyond `data.length`, triggering `ArrayIndexOutOfBoundsException` / `NegativeArraySizeException` inside `Arrays.copyOfRange` or the `words[...]` array access — the direct structural analog of the DNS-overlay OOB read: attacker-controlled length/offset fields walked over a fixed buffer without full bounds validation.

The code base itself documents this exact issue: a newer guard `isValidAbiEncoding(data, headerWords, itemWords)` was added, but it is only invoked when `VMConfig.allowTvmOsaka()` is true (the TIP-854 hard-fork flag): [3](#0-2) [4](#0-3) 

When `allowTvmOsaka()` is not yet activated on a given network (or before the corresponding hard fork proposal is enabled), the legacy, unguarded decode path is reachable, and the project's own tests document that pre-activation malformed calldata is expected to throw a `RuntimeException` out of the precompile: [5](#0-4) 

### Impact Explanation
`ValidateMultiSign` and `BatchValidateSign` are reachable from any Solidity/TVM contract via a `CALL`/`STATICCALL` to their fixed precompile addresses, i.e. from any unprivileged transaction broadcaster or contract deployer. If the resulting `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` propagates uncaught out of the precompile invocation path (which the existing tests show can happen pre-TIP-854 activation), it can abort/crash the EVM execution unexpectedly, produce inconsistent gas/energy accounting, or — depending on how the surrounding `Program`/`VMActuator` call stack handles the runtime exception — potentially crash the node process handling that transaction (denial of service), matching the "node crash or halt" acceptance criterion. Because affected data (`words[]`/raw ABI bytes) is fully attacker-supplied contract call data, no privileged role is required.

### Likelihood Explanation
Likelihood is network/hard-fork-state dependent: it requires `VMConfig.allowTvmOsaka()` to be false (i.e., the TIP-854 committee proposal not yet activated) for the vulnerable legacy code path to be reached; once TIP-854 is activated network-wide the `isValidAbiEncoding` guard rejects malformed calldata before it reaches `extractBytesArray`/`extractSigArray`/`extractBytes`. On any chain/testnet/private network where this proposal has not been activated, the path is trivially reachable by any account able to send a transaction that calls a contract invoking these two fixed precompile addresses with crafted calldata.

### Recommendation
Apply the same `isValidAbiEncoding`-style structural validation (or equivalent explicit bounds checks on every derived `offset`/`length` against both `words.length` and the raw `data.length`) unconditionally, not gated behind `VMConfig.allowTvmOsaka()`, so that malformed/attacker-crafted calldata is rejected via the normal `Pair.of(false, EMPTY_BYTE_ARRAY)` return path on all networks regardless of hard-fork activation state. Additionally, harden `extractBytes`, `extractBytesArray`, and `extractSigArray` themselves to bounds-check every offset/length combination before indexing `words[]` or slicing `data`, rather than relying solely on the caller-side `isValidAbiEncoding` pre-check.

### Proof of Concept
1. On a network/instance where `VMConfig.allowTvmOsaka()` is not activated, deploy a contract that performs a low-level `call`/`staticcall` to the `ValidateMultiSign` precompile address.
2. Craft `rawData` such that `words[3]` (the offset word) encodes a value that, divided by `WORD_SIZE`, produces an index near/at `words.length - 1`, and such that the length word at that index (`words[offset].intValueSafe()`) combined with a large `bytesOffset` derived from `words[offset + i + 1]` causes `extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE, bytesLen)` to compute `offset` or `offset+len` beyond `data.length`.
3. Submit the transaction; observe `Arrays.copyOfRange` in `extractBytes` (`actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java:428-430`) or the `words[offset + i + 1]` access in `extractBytesArray`/`extractSigArray` (lines 390-426) throw `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException`, matching the failure mode already reproduced by `ValidateMultiSignContractTest.testTip854PreActivationNoOp` [6](#0-5) .

**Note on certainty**: I was unable to fully trace how `Program.callToPrecompiledAddress` (which I could not fully retrieve due to index size limits) handles a `RuntimeException`/`ArrayIndexOutOfBoundsException` thrown by a precompile's `execute()` on the legacy (pre-TIP-854) path — i.e., whether it is always caught and converted into a normal revert, or whether it can escape to crash the node/thread. The `OperationsTest.testTip854OuterFrameContainment` test suggests containment was specifically added for the *post-activation* guarded path, which implies the *pre-activation* path may not have had the same containment guarantee. A Devin session with full repo/build access would be needed to confirm the exact exception-propagation behavior of `Program.callToPrecompiledAddress` on unguarded/pre-hard-fork networks and thus confirm real-world crash impact versus a contained revert.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,

    }
    return bytesArray;
  }
