### Title
Unbounded array-length allocation in `PrecompiledContracts` multi-sig precompiles allows memory-exhaustion DoS - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
`ValidateMultiSign` and `BatchValidateSign` decode a "bytes[]"/"address[]" array length directly from attacker-controlled call data words and then allocate a Java array sized by that value, before any bound is enforced against the actual call-data length. This mirrors the CVE-2017-9039 pattern (a length/count field parsed from untrusted input drives an allocation loop with no sanity check against the real payload size), but here the trigger is a TVM `CALL` to a precompiled address instead of a crafted ELF header count.

### Finding Description
`extractBytes32Array`, `extractBytesArray`, and `extractSigArray` read the array length as `words[offset].intValueSafe()` and immediately allocate `new byte[len][]` (and further per-item byte arrays), with `len` fully attacker-controlled and unconstrained by `data.length`: [1](#0-0) 

`extractBytes32Array` in particular performs no offset/length sanity check at all before allocating: [2](#0-1) 

These helpers are invoked from `ValidateMultiSign.execute` and `BatchValidateSign.doExecute`. A `MAX_SIZE` bound (16 for `BatchValidateSign`, 5 for `ValidateMultiSign`) on the declared array-size word is enforced only when `VMConfig.allowTvmSelfdestructRestriction()` is active: [3](#0-2) [4](#0-3) 

When that gated feature is not active (e.g., on chains/networks/test environments that have not yet activated this hard-fork-style flag), the extract helpers are called with the raw, attacker-declared length straight from call data, with no upper bound — allowing a value up to `Integer.MAX_VALUE` (as clamped by `DataWord.intValueSafe()`), which drives a multi-gigabyte array allocation attempt inside `new byte[len][]`.

I was unable to fully confirm the default/activation status of `VMConfig.allowTvmSelfdestructRestriction()` across supported networks within the available indexed content — this determines whether the unguarded path is reachable on a fully up-to-date mainnet deployment versus only on networks that have not enabled this specific chain parameter. This uncertainty affects the severity assessment and should be verified against the live chain parameter state before triage.

### Impact Explanation
A successful trigger causes an attempted allocation on the order of gigabytes for a single call inside the TVM interpreter thread, which can:
- Throw `OutOfMemoryError` inside the node's transaction-execution path, and if repeated concurrently (multiple transactions/threads triggering the same precompile), cause sustained memory pressure severe enough to degrade or crash the witness/full node process (denial of service), matching the "memory consumption" impact class of CVE-2017-9039.
- This is reachable by any account that can send a transaction invoking a smart contract that performs a `CALL` to the `validateMultiSign` (`0x66`) or `batchValidateSign` precompiled address with crafted call data — no special privilege required.

### Likelihood Explanation
Likelihood depends heavily on whether `allowTvmSelfdestructRestriction()` is active on the target network. If active (the guarded path), the `MAX_SIZE` check bounds the length before allocation occurs, effectively closing this specific issue on such networks. If not yet activated, the vulnerable path is trivially reachable by any unprivileged account crafting a single transaction with an oversized bytes[]/address[] length word.

### Recommendation
- Enforce an upper bound on the declared array length (`len`) inside `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` themselves, independent of the `allowTvmSelfdestructRestriction()` feature flag, so the check cannot be bypassed by chain configuration state.
- Validate `len` against the remaining actual `data.length` (as is already done via `verifyLength`-style checks in `RLP.java`) before allocating, rejecting any declared length that cannot possibly be backed by the supplied call data.
- Consider making the previously "restriction" MAX_SIZE bound unconditional rather than gated behind a togglable VM config flag.

### Proof of Concept
1. Deploy or reuse any contract, or interact directly via `TriggerSmartContract`, calling the `validateMultiSign(address,uint256,bytes32,bytes[])` precompile at address `0x0000...0066` (or `batchValidateSign` at its address).
2. Craft the ABI-encoded call data so that the word representing the `bytes[]` array's length (the word at the offset pointed to by the array's offset word) is set to a very large value (e.g., `0x7FFFFFFF`) instead of a small legitimate count, while keeping the actual call data short.
3. On a node where `VMConfig.allowTvmSelfdestructRestriction()` is not active, this reaches `extractBytesArray`/`extractSigArray`/`extractBytes32Array`, which execute `new byte[0x7FFFFFFF][]`, attempting a multi-gigabyte allocation and throwing `OutOfMemoryError`/causing severe GC pressure inside the node process handling the transaction.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
