## Title
ETH-implicit account creation binds to an unverified global wallet-contract hash, permanently freezing funds if the global contract is never deployed - (File: `runtime/runtime/src/actions.rs`)

### Summary
The ITS bug allows a transfer to be processed against a destination balance that was never properly initialized by the corresponding "deploy" step, because the transfer path does not check that the deploy step already happened. The closest reachable analog in nearcore is in ETH-implicit account creation: any unprivileged signer can create (fund) an ETH-implicit account via a plain `Transfer`, and the runtime unconditionally sets that account's `AccountContract` to `Global(eth_wallet_global_contract_hash(chain_id))` [1](#0-0)  without ever verifying that a global contract with that hash has actually been deployed to the trie (`TrieKey::GlobalContractCode`).

### Finding Description
`action_implicit_account_creation_transfer` is invoked from the generic `Transfer` action handler whenever the receiver account does not yet exist and is implicit [2](#0-1) . For the `EthImplicitAccount` branch it computes `global_contract_hash = eth_wallet_global_contract_hash(&chain_id)` and immediately constructs the account with `AccountContract::Global(global_contract_hash)`, without any existence check against the trie: [1](#0-0) 

Compare this with `use_global_contract`, the *other* code path that assigns a global-contract pointer to an account: it explicitly checks `state_update.contains_key(&key, ...)` for `TrieKey::GlobalContractCode` and fails with `ActionErrorKind::GlobalContractDoesNotExist` if the contract has not been deployed [3](#0-2) . The implicit-account-creation path has no equivalent guard — it is the "transfer" side of the deploy/transfer pair that trusts a deploy has already (or will) happen, exactly as in the ITS bug where `update_token_balance`'s `InterchainTransfer` message did not check that the corresponding `DeployInterchainToken` balance record existed.

`eth_wallet_global_contract_hash` returns a **hardcoded constant hash** for `mainnet`/`testnet`/`mocknet` [4](#0-3) , which is only meaningful once someone actually deploys a global contract whose code hashes to that value (via a `DeployGlobalContract` action). If a `Transfer` to a not-yet-existing `0x...` account is processed on the network *before* that specific global contract blob has been deployed (e.g. immediately after the `EthImplicitGlobalContract` protocol feature activates but before the rollout deploys the matching global contract, or on any custom/forked chain id whose genesis migration is missing/misconfigured), the account is created and funded, but points at a global contract that does not exist in state.

Once such an account exists, `RuntimeContractIdentifier::resolve` for a `FunctionCall` on it will attempt `gci.clone().hash(state_update, access)?` for the missing global identifier [5](#0-4) , and ETH-implicit accounts are architecturally locked out of every other recovery path:
- They cannot be deleted (no full-access key, `DeleteAccount` requires an authorized signer/access key which ETH-implicit accounts never get).
- They cannot have a full access key added.
- The *only* way to move funds out is by calling the (missing) wallet contract's `rlp_execute` method, which cannot succeed if the global contract code is absent.

This matches the ITS root cause precisely: an action that debits/creates state on the assumption that a companion "deployment" step has already completed, with no on-chain check enforcing that ordering.

### Impact Explanation
If exploitable (i.e., if there is any window where transfers to ETH-implicit accounts are processed before the corresponding global wallet contract is deployed on a given chain_id), any NEAR deposited to such an account becomes **permanently frozen** — unspendable and undeletable, since the account has no access key and its only method-call surface depends on contract code that doesn't exist in state. This is a direct "permanent freezing of funds" outcome, which is within the accepted impact set.

### Likelihood Explanation
Triggering this requires only an ordinary, unprivileged `Transfer` transaction to a `0x...`-formatted account ID — no special permissions, cross-shard timing games, or malicious validators needed. The risk window is bounded to periods/networks where `EthImplicitGlobalContract` is active but the specific global contract matching `eth_wallet_global_contract_hash(chain_id)` has not yet been deployed to that chain's state (e.g., a new fork/testnet using the mainnet/testnet branch of `eth_wallet_global_contract_hash` without performing the corresponding `DeployGlobalContract`, or a deployment-ordering mistake during the mainnet/testnet rollout itself). I could not verify from the indexed code/tests whether nearcore's genesis or migration tooling guarantees the global wallet contract is deployed atomically with the protocol-version activation of `EthImplicitGlobalContract`; that guarantee (if present) would live in genesis-config/migration code not surfaced by these searches, so likelihood is uncertain without further investigation of that rollout mechanism.

### Recommendation
Before creating an ETH-implicit account with `AccountContract::Global(global_contract_hash)`, check that `TrieKey::GlobalContractCode { identifier: GlobalContractIdentifier::CodeHash(global_contract_hash) }` exists in the trie, mirroring the check already performed in `use_global_contract`. If the global contract is missing, either reject the transfer (mirroring the ITS-recommended fix of only allowing the "transfer" side once the "deploy" side is confirmed) or fall back to the legacy embedded-magic-bytes local-code path so the account remains usable.

### Proof of Concept
1. On a chain where `EthImplicitGlobalContract` is active but the global contract whose code hash equals `eth_wallet_global_contract_hash(chain_id)` has not yet been deployed via `DeployGlobalContract`.
2. Any account sends a plain `Transfer` to a fresh `0x...` (ETH-implicit) account id, e.g. as done in `test_eth_implicit_account_creation` [6](#0-5)  but skipping the preceding `deploy_global_contract` step.
3. `action_implicit_account_creation_transfer` creates the account with `AccountContract::Global(global_contract_hash)` and the deposited balance, with no check that the global contract exists [1](#0-0) .
4. Any subsequent attempt to call the wallet contract (`rlp_execute`) fails to resolve the contract code because `TrieKey::GlobalContractCode` is absent, and the account can never be deleted or have keys added — the deposited balance is permanently frozen.

fn action_transfer_or_implicit_account_creation(
    account: &mut Option<Account>,
    deposit: Balance,
    is_refund: bool,
    action_receipt: &VersionedActionReceipt,
    receipt: &Receipt,
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    actor_id: &mut AccountId,
    epoch_info_provider: &dyn EpochInfoProvider,
) -> Result<(), RuntimeError> {
    Ok(if let Some(account) = account.as_mut() {
        let is_gas_refund = is_refund && action_receipt.signer_id() == receipt.receiver_id();
        // For gas refunds, try to refund to the gas key first. If the signer key is a gas key,
        // the refund goes to the gas key balance and we skip crediting the account balance.
        if is_gas_refund
            && try_refund_gas_key_balance(
                state_update,
                receipt.receiver_id(),
                &action_receipt.signer_public_key(),
                deposit,
            )?
        {
            return Ok(());
        }
        action_transfer(account, deposit)?;
        if is_gas_refund {
            try_refund_allowance(
                state_update,
                receipt.receiver_id(),
                &action_receipt.signer_public_key(),
                deposit,
            )?;
        }
    } else {
        debug_assert!(!is_refund);
        action_implicit_account_creation_transfer(
            state_update,
            &apply_state,
            &apply_state.config.fees,
            account,
            actor_id,
            receipt.receiver_id(),
            deposit,
            apply_state.block_height,
            epoch_info_provider,
        );
    })

pub(crate) fn use_global_contract(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
    account: &mut Account,
    contract_identifier: &GlobalContractIdentifier,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let key = TrieKey::GlobalContractCode { identifier: contract_identifier.clone().into() };
    if !state_update.contains_key(&key, AccessOptions::DEFAULT)? {
        result.result = Err(ActionErrorKind::GlobalContractDoesNotExist {
            identifier: contract_identifier.clone(),
        }
        .into());
        return Ok(());
    }

/// Tests that ETH-implicit account is created correctly, with Wallet Contract hash.
#[test]
fn test_eth_implicit_account_creation() {
    let genesis = Genesis::test(vec!["test0".parse().unwrap(), "test1".parse().unwrap()], 1);
    let mut env = TestEnv::builder(&genesis.config).nightshade_runtimes(&genesis).build();
    let genesis_block = env.clients[0].chain.get_block_by_height(0).unwrap();
    let chain_id = &genesis.config.chain_id;

    let signer = InMemorySigner::test_signer(&"test0".parse().unwrap());
    let eth_implicit_account_id = eth_implicit_test_account();

    // Make zero-transfer to ETH-implicit account, invoking its creation.
    let transfer_tx = SignedTransaction::send_money(
        1,
        signer.get_account_id(),
        eth_implicit_account_id.clone(),
        &signer,
        Balance::ZERO,
        *genesis_block.hash(),
    );
    assert_eq!(
        env.rpc_handlers[0].process_tx(transfer_tx, false, false),
        ProcessTxResponse::ValidTx
    );
    for i in 1..5 {
        env.produce_block(0, i);
    }

    // Verify the ETH-implicit account has zero balance and appropriate code hash.
    // Check that the account storage fits within zero balance account limit.
    let request = QueryRequest::ViewAccount { account_id: eth_implicit_account_id };
    match view_request(&env, request).kind {
        QueryResponseKind::ViewAccount(view) => {
            assert!(view.amount.is_zero());
            assert_eq!(view.global_contract_hash, Some(eth_wallet_global_contract_hash(chain_id)));
            assert!(view.storage_usage <= ZERO_BALANCE_ACCOUNT_STORAGE_LIMIT)
        }
        _ => panic!("wrong query response"),
    }
}
