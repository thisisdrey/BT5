### Title
Fuzzy `tmp_objdir` prefix match in `ObjectDirectoryPath` allows cross-repository quarantine object directory access - (File: internal/git/localrepo/paths.go)

### Summary
`Repo.ObjectDirectoryPath` accepts an attacker-influenced `GitObjectDirectory` field from an RPC `Repository` message and treats *any* path within the storage whose basename starts with `tmp_objdir` and whose parent directory is literally named `quarantine` as a legitimate "transaction quarantine" directory, skipping the repository-scoped ownership check that is otherwise enforced via a per-repository SHA1-derived prefix.

### Finding Description
`ObjectDirectoryPath` first bounds the object directory to the storage root via `storage.ValidateRelativePath(storagePath, ...)` [1](#0-0) , but that check only guarantees the path is *somewhere* inside the storage — not that it belongs to the requesting repository.

It then classifies the path as an internal transaction quarantine directory using a loose, non-exact match:
```go
parentDir := filepath.Base(filepath.Dir(relativeObjectDirectoryPath))
baseDir := filepath.Base(relativeObjectDirectoryPath)
isTransactionQuarantineDir := (baseDir == "quarantine") || ((parentDir == "quarantine") && strings.HasPrefix(baseDir, "tmp_objdir"))
``` [2](#0-1) 

When `isTransactionQuarantineDir` is true, the function **skips entirely** the ownership-scoped validation that otherwise applies to manual quarantine directories — the branch that computes a repository-specific prefix (`quarantine-<sha1(relativePath)[:8]>-`) and requires `strings.HasPrefix(absoluteObjectDirectoryPath, expectedQuarantinePrefix)` [3](#0-2) . That per-repo hash check is the *only* mechanism that ties a manual quarantine directory back to the calling repository; the `tmp_objdir*` fast-path bypasses it completely and relies solely on the loose pattern `parentDir == "quarantine" && strings.HasPrefix(baseDir, "tmp_objdir")`, which says nothing about which repository the quarantine directory was created for.

This mirrors the CVE-2024-38365 bug class: two logically-parallel validation paths (`FindAndDelete` exact match vs. `removeOpcodeByData` substring match) diverge in strictness, and the weaker one is reachable and produces a different, exploitable outcome. Here, the exact, repo-bound hash-prefix check exists for one code path but a much weaker structural/prefix check silently substitutes for it on another, equally reachable, code path.

Any storage location that happens to contain a `.../quarantine/tmp_objdir-*` directory tree — e.g., another repository's active `git-receive-pack` quarantine directory created during a concurrent push, or Gitaly's own transaction-manager quarantine staging directories under `+gitaly/tmp/...` — satisfies `isTransactionQuarantineDir` regardless of which repository it actually belongs to, as long as the final joined path is still inside the storage root.

### Impact Explanation
An ordinary authenticated Gitaly client can set `Repository.git_object_directory` to a crafted relative path (e.g. `../victim-repo.git/quarantine/tmp_objdir-incoming-XXXXXX`) on requests such as `GetObjectDirectorySize`, which calls `repo.ObjectDirectoryPath(ctx)` directly [4](#0-3) , or on any other RPC/hook path that consults `ObjectDirectoryPath`/quarantine object directories (e.g. LFS pointer listing, `ListAllCommits`, `cat-file` based lookups performed with the client-supplied object directory). If such a path exists on disk and matches the loose pattern, Gitaly will treat it as this caller's valid object directory, walking/reading objects that belong to a different repository's in-flight push quarantine. This is a cross-repository object-directory access / repository isolation bypass, not merely a DoS — it can leak object sizes/contents of another tenant's not-yet-accepted push data.

### Likelihood Explanation
Exploitability depends on the attacker being able to (a) guess or discover a currently-existing `quarantine/tmp_objdir-*` directory name under some accessible storage path (these are ephemeral, randomly-suffixed directories created by `git-receive-pack`/transaction quarantines during concurrent pushes) and (b) have any repository/relative-path context that Gitaly will accept as their own `RelativePath` while pointing `GitObjectDirectory` elsewhere in the storage. The Repository message's `git_object_directory` field is attacker-supplied in normal client/Rails-originated requests (it is explicitly designed to be settable to reflect quarantine state), so the field is reachable; the main constraint is knowledge of a live, matching directory name, which reduces but does not eliminate practical likelihood — this is best characterized as Medium rather than High without confirming whether directory names are guessable/enumerable in the deployment.

### Recommendation
Remove the loose `tmp_objdir` fast-path or make it perform the same repository-scoped ownership check as the manual-quarantine branch (verify the path is nested under a temp directory prefixed by this specific repository's `QuarantineDirectoryPrefix`, not just that the basename pattern looks like `tmp_objdir*`). At minimum, require that the `quarantine`/`tmp_objdir*` directory sit under the same repo-derived quarantine prefix used elsewhere in the function before accepting it as valid.

### Proof of Concept
Not independently verified end-to-end (would require live confirmation that another repository's `quarantine/tmp_objdir-*` directory is discoverable/accessible at request time); the code-level bypass is demonstrated by the divergent validation logic cited above: a request to `GetObjectDirectorySize` with `Repository{StorageName: <own storage>, RelativePath: <own repo>, GitObjectDirectory: "../other-repo.git/quarantine/tmp_objdir-incoming-XXXX"}` satisfies `isTransactionQuarantineDir` and skips the per-repository hash-prefix ownership check entirely, returning the size of another repository's quarantine object directory.
