### Title
Unprotected `TotalNetWeight`/`TotalEnergyWeight`/`TotalTronPowerWeight` accumulation in TVM-triggered freeze/unfreeze processors can drift/underflow, unlike the actuator path - (File: `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java`)

### Summary
The Panoptic finding is about an accumulator (`removedLiquidity`) that is incremented in an `unchecked` block based on the assumption "we can't remove more liquidity than we add in the first place, so this can't overflow" — an assumption that breaks down under a specific repeated mint/burn sequence, corrupting downstream accounting. java-tron has a structurally analogous accumulator pattern: the network-wide resource weight counters (`TOTAL_NET_WEIGHT`, `TOTAL_ENERGY_WEIGHT`, `TOTAL_TRON_POWER_WEIGHT`) are updated by two independent, non-equivalent code paths that are supposed to keep the same invariant but don't.

### Finding Description
`DynamicPropertiesStore.addTotalNetWeight/addTotalEnergyWeight/addTotalTronPowerWeight` (used by the normal actuators `FreezeBalanceActuator`, `UnfreezeBalanceActuator`, `UnfreezeBalanceV2Actuator`) explicitly guard the accumulator against going negative when `allowNewReward()` is active: [1](#0-0) 

However, the exact same conceptual accumulators are also mutated through a second, independent implementation in `RepositoryImpl`, which is the `Repository` used by the TVM native-contract processors (`FreezeBalanceProcessor`, `FreezeBalanceV2Processor`, `UnfreezeBalanceProcessor`, `UnfreezeBalanceV2Processor`, `CancelAllUnfreezeV2Processor`) that are reachable from an ordinary account by triggering a smart contract that issues the corresponding native-contract call: [2](#0-1) 

This `RepositoryImpl` version performs the plain `+=` with **no lower-bound clamp at all** ("we can't remove more than we add" style assumption baked into the design, since the callers only ever pass deltas derived from that account's own freeze/unfreeze deltas), and it also writes directly to the dynamic-property key rather than reusing the clamped `DynamicPropertiesStore` method: [3](#0-2) 

The freeze/unfreeze processors invoked from the TVM (e.g. `FreezeBalanceV2Processor.execute`, `UnfreezeBalanceV2Processor.updateTotalResourceWeight`) call `repo.addTotalNetWeight(...)`/`repo.addTotalEnergyWeight(...)` directly, taking the unguarded `RepositoryImpl` path instead of the guarded `DynamicPropertiesStore` path used by the plain actuators: [4](#0-3) [5](#0-4) 

Because two independently-maintained implementations of the *same* global counter exist — one clamped, one not — and both are live entry points into the same dynamic-property slot, the "can't go wrong" assumption embedded in the unguarded `RepositoryImpl` path (mirroring the Panoptic developers' "can't overflow" comment) is not actually guaranteed once transactions interleave between the actuator path and the TVM/native-contract path for the same account across many freeze/unfreeze/delegate cycles. A test already demonstrates that the related `calculateGlobalEnergyLimit` hardening path treats overflow/negative weight as a real, previously-unguarded risk area: [6](#0-5) 

### Impact Explanation
`TOTAL_NET_WEIGHT`/`TOTAL_ENERGY_WEIGHT` are consensus-critical, network-wide values used to compute every account's bandwidth/energy limit (`BandwidthProcessor`/`EnergyProcessor` divide the total pool by this weight). If the unguarded `RepositoryImpl` accumulation path drives the counter to an incorrect (too-low, negative, or divergent) value relative to the true sum of frozen balances, every account's bandwidth/energy allowance computed off that global weight becomes wrong network-wide — this can manifest as free/duplicated resource allocation (equivalent to "unbacked" resource issuance) or as an `ArithmeticException`/crash on nodes that apply the hardened calculation path once the divergence becomes extreme, i.e. a chain-halt risk.

### Likelihood Explanation
Reaching the vulnerable path requires only ordinary, unprivileged transactions: any account can trigger a smart contract that calls the freeze/unfreeze/delegate native contracts (`FreezeBalanceV2Processor`, `UnfreezeBalanceV2Processor`, etc.), and mix this with regular (non-contract) `FreezeBalanceContract`/`UnfreezeBalanceContract` transactions that go through the actuator/`DynamicPropertiesStore` path. No special privilege, validator collusion, or network position is needed — only repeated, ordinary freeze/unfreeze/delegate activity, similar in spirit to the repeated short/long mint/burn loop used in the Panoptic PoC.

### Recommendation
Consolidate `TotalNetWeight`/`TotalEnergyWeight`/`TotalTronPowerWeight` mutation into a single implementation shared by both the plain actuators and the TVM native-contract processors, applying the same `max(0, ..., disableJavaLangMath())` clamp (and the same `allowNewReward()`-gated semantics) in `RepositoryImpl` as in `DynamicPropertiesStore`, so there is exactly one source of truth and one invariant-preserving code path for these accumulators.

### Proof of Concept
Not independently reproduced (index-only analysis); the analog is established by exact-line comparison of `RepositoryImpl.addTotalNetWeight`/`addTotalEnergyWeight`/`addTotalTronPowerWeight` (no clamp) versus `DynamicPropertiesStore.addTotalNetWeight`/`addTotalEnergyWeight`/`addTotalTronPowerWeight` (clamped), and by tracing that the TVM native-contract freeze/unfreeze processors exclusively use the unclamped `RepositoryImpl` path while ordinary transaction actuators use the clamped path, both writing to the same underlying dynamic-property keys.     switch (freezeType) {
      case BANDWIDTH:
        long oldNetWeight = accountCapsule.getFrozenV2BalanceWithDelegated(BANDWIDTH) / TRX_PRECISION;
        accountCapsule.addFrozenBalanceForBandwidthV2(-unfreezeBalance);
        long newNetWeight = accountCapsule.getFrozenV2BalanceWithDelegated(BANDWIDTH) / TRX_PRECISION;
        repo.addTotalNetWeight(newNetWeight - oldNetWeight);
        break;

        long oldEnergyWeight = accountCapsule.getFrozenV2BalanceWithDelegated(ENERGY) / TRX_PRECISION;
