### Title
Dust transfers of `DepositToken` fill victim's `depositTokensOfAccount` list, permanently reverting all new-collateral deposits and new synth issuance - ([File: contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
`DepositToken.transfer`/`transferFrom` are permissionless ERC-20 transfers. Every transfer that gives a recipient a nonzero balance calls `Pool.addToDepositTokensOfAccount(recipient)`, which reverts once `debtTokensOfAccount + depositTokensOfAccount == MAX_TOKENS_PER_USER (30)`. An attacker can deposit dust amounts of every supported collateral and transfer 1 wei of each `msdTOKEN` to a victim, filling their per-account list. Afterwards, any `deposit` (or `leverage`, or first-time `issue` of a new synthetic, since the cap is shared) for a token the victim doesn't already hold reverts with `UserReachedMaxTokens`, because `_mint`/`DebtToken.issue` unconditionally calls `addTo*TokensOfAccount`.

### Finding Description
- `DepositToken._transfer` adds the token to the recipient's list on any nonzero receipt: `if (_recipientBalanceBefore == 0 && amount_ > 0) { pool.addToDepositTokensOfAccount(recipient_); }` (`contracts/DepositToken.sol:518-520`).
- `Pool.addToDepositTokensOfAccount` enforces `onlyIfAdditionWillNotReachMaxTokens`, reverting with `UserReachedMaxTokens` at 30 combined entries (`contracts/Pool.sol:143-148`, `216-220`).
- The recipient never consented: `transfer`/`transferFrom` only check the *sender's* unlocked balance (`_revertIfLocked(sender_, amount_)`), nothing on the recipient side (`contracts/DepositToken.sol:348-376`).
- Consequently the whole transfer reverts once the victim is at cap — but only for tokens the victim does not yet hold; more importantly, the victim's *own* subsequent `deposit` of any new collateral reverts inside `_mint` → `addToDepositTokensOfAccount` (`contracts/DepositToken.sol:486-488`), and issuing a synthetic whose debt token isn't already in their list reverts in `addToDebtTokensOfAccount` (`contracts/Pool.sol:204-208`). This propagates through `SmartFarmingManager.leverage` as well.

### Impact Explanation
Denial of service / liveness break: the victim cannot deposit any new collateral type, cannot take on debt in any new synthetic, and cannot open leveraged positions in new assets — all public entry points revert. The invariant broken is that a holder's ability to open positions must not depend on actions of uninvolved third parties. Cleanup requires the victim to fully withdraw each unsolicited dust position (one `withdraw` per token, paying gas each time), which is only possible if the dust isn't locked by debt — and the attacker can re-fill slots as soon as they are cleared. Note the attack requires the pool to list enough `DepositToken`s (victim's existing deposit+debt tokens plus attacker-sent dust must reach 30); on pools with many registered collaterals this is cheap since each fill costs only a dust deposit.

### Likelihood Explanation
Medium. Requires only an unprivileged EOA, public `DepositToken.deposit`/`transfer`, and dust amounts of the pool's registered collaterals. No privileged role, oracle manipulation, or timing is needed. Feasibility scales with the number of deposit tokens registered in the pool; the cap is a hardcoded constant of 30 shared across deposits and debts.

### Recommendation
Either exempt unsolicited receipts (only add to `depositTokensOfAccount` on `deposit`/`_mint`, not on `transfer`), or make `addTo*TokensOfAccount` failure non-blocking for transfers (skip the add instead of reverting), or remove the 30-token cap by iterating over the pool's global token list in `debtOf`/`depositOf` and checking balances.

### Proof of Concept
```solidity
// Foundry fork-style test (Hardhat equivalent in test/Pool.test.ts fixtures)
function testDustFillVictimList() public {
    address victim = makeAddr("victim");
    address attacker = makeAddr("attacker");

    // victim already holds N positions (deposits + debts)
    // attacker fills remaining (30 - N) slots:
    IDepositToken[] memory dts = getAllDepositTokens(pool); // pool's registered deposit tokens
    for (uint i; i < dts.length && victimTokenCount(pool, victim) < 30; i++) {
        IERC20 underlying = dts[i].underlying();
        deal(address(underlying), attacker, 2);
        vm.startPrank(attacker);
        underlying.approve(address(dts[i]), 2);
        dts[i].deposit(1, attacker);          // mint dust to attacker
        dts[i].transfer(victim, 1);           // adds token to victim's list
        vm.stopPrank();
    }
    assertEq(pool.getDepositTokensOfAccount(victim).length
             + pool.getDebtTokensOfAccount(victim).length, 30);

    // victim deposits a collateral type they don't hold yet -> reverts
    IDepositToken newDt = dts[dts.length - 1];
    IERC20 under = newDt.underlying();
    deal(address(under), victim, 100e18);
    vm.startPrank(victim);
    under.approve(address(newDt), 100e18);
    vm.expectRevert(Pool.UserReachedMaxTokens.selector);
    newDt.deposit(100e18, victim);            // reverts inside _mint -> addToDepositTokensOfAccount
}
