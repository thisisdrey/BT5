### Title
Attacker-served `Attachment` content is stored via `insert_instantiated_attachment` even when no `AttachmentInstance` references its hash - ([File: stackslib/src/net/atlas/download.rs])

### Summary
When the Atlas downloader's `AttachmentsBatchStateMachine` reaches its `Done` state, it iterates every downloaded `Attachment` and unconditionally calls `network.atlasdb.insert_instantiated_attachment(&attachment)` regardless of whether `find_all_attachment_instances(&attachment.hash())` returned any matching rows. Because `extend_with_attachments` (same file) also never checks that the server-returned attachment's actual hash equals the `content_hash` that was requested, a malicious peer can serve arbitrary content for a request and have it permanently persisted (`was_instantiated = 1`) in the local `attachments` table.

### Finding Description
The equality that should hold is: for every row persisted into `attachments`, its `hash` column should equal the `content_hash` of at least one on-chain-derived `AttachmentInstance` (i.e., a real name-operation commitment). In the `Done` branch:

```
for attachment in context.attachments.drain() {
    let attachments_instances = network.atlasdb.find_all_attachment_instances(&attachment.hash())?;
    network.atlasdb.insert_instantiated_attachment(&attachment)?;   // unconditional
    for attachment_instance in attachments_instances.into_iter() { ... }
    context.attachments_batch.resolve_attachment(&attachment.hash())
}
``` [1](#0-0) 

`attachments_instances` is only used to build `resolved_attachments`; its emptiness does not gate the call to `insert_instantiated_attachment`. Additionally, `context.attachments` is populated in `extend_with_attachments` purely from the HTTP response's decoded payload, with no check that `response.attachment.hash()` matches the `content_hash` that was actually requested for that `AttachmentRequest`:

```
if let Ok(response) = response.decode_atlas_get_attachment() {
    self.attachments.insert(response.attachment);
    report.bump_successful_requests();
}
``` [2](#0-1) 

`insert_instantiated_attachment` itself blindly stores whatever content it is given, keyed by the hash it computes from that content, and marks it `was_instantiated = 1`:

```
tx.execute(
    "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)",
    params![attachment.hash(), attachment.content, now],
)?;
``` [3](#0-2) 

Because the row is marked `was_instantiated = 1`, it is exempt from `evict_expired_uninstantiated_attachments`, which only deletes rows where `was_instantiated = 0`. [4](#0-3) 

An unprivileged peer that (a) advertises (via `GetAttachmentsInvResponse`) that it holds an attachment for some page/index the node is soliciting, and (b) responds to the subsequent attachment-content request with arbitrary bytes unrelated to the originally requested `content_hash`, causes the node to compute a fresh hash over the attacker content and unconditionally persist it as an "instantiated" row — with no `AttachmentInstance` ever pointing at that hash.

### Impact Explanation
This lets any peer that the node syncs with cause permanent, non-evictable storage of attacker-chosen blobs in the node's `attachments` SQLite table, unconnected to any on-chain name-operation commitment. Because these rows are marked instantiated, the normal uninstantiated-attachment eviction logic never removes them, so repeated requests/responses (one per queued `AttachmentInstance` the node is trying to resolve) accumulate persistent junk data. This matches the "High" impact category of attachment/BNS mismatch and storage-based DoS via data no canonical commitment references, since the stored-hash == committed-hash invariant is broken.

### Likelihood Explanation
No privileged role is needed — the attacker only needs to be one of the node's outbound sync peers serving Atlas HTTP endpoints (`get_data_url`), a normal unauthenticated node capability. The attacker must be selected as a data source for at least one pending `AttachmentRequest`, which simply requires advertising the relevant bit in its inventory response; it then controls the actual bytes returned for the attachment-fetch request. This is repeatable per name-operation-driven attachment fetch cycle the victim node performs, at low attacker cost (run one node, answer requests with junk).

### Recommendation
In the `Done` branch of `AttachmentsBatchStateMachine::run`/`try_proceed` (or earlier, in `extend_with_attachments`), verify that `attachment.hash()` equals the `content_hash` of the `AttachmentRequest` that produced the response before adding it to `context.attachments`; discard and penalize peers (bump failed requests / mark faulty) when the hash does not match. Only call `insert_instantiated_attachment` when at least one matching `AttachmentInstance` exists (i.e., when `find_all_attachment_instances` returns a non-empty result), otherwise drop the attachment.

### Proof of Concept
Rust test in `stackslib::net::atlas`:
1. Instantiate a fresh `AtlasDB` with zero `AttachmentInstance` rows (no `insert_initial_attachment_instance` calls).
2. Construct an arbitrary `Attachment` with attacker-chosen `content` (e.g., `Attachment::new(vec![0xAA; 1024])`).
3. Call `atlas_db.find_all_attachment_instances(&attachment.hash())` and assert it returns an empty vector.
4. Call `atlas_db.insert_instantiated_attachment(&attachment)`.
5. Query `SELECT COUNT(*) FROM attachments WHERE hash = ?` with `attachment.hash()` and assert the count is `1`, and that `was_instantiated = 1`, proving the row persists with no corresponding on-chain-derived `AttachmentInstance`, and will survive `evict_expired_uninstantiated_attachments`.

    pub fn evict_expired_uninstantiated_attachments(&mut self) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let cut_off = now - self.atlas_config.uninstantiated_attachments_expire_after as i64;
        let tx = self.tx_begin()?;
        let res = tx.execute(
            "DELETE FROM attachments WHERE was_instantiated = 0 AND created_at < ?",
            params![cut_off],
        );
        res.map_err(db_error::SqliteError)?;
        tx.commit().map_err(db_error::SqliteError)?;
        Ok(())
    }
