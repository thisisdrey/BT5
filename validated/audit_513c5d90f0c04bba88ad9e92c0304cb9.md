### Title
Unbounded number of reference updates in a single push causes per-ref custom-hook process spawning, enabling a DoS of the receive-pack RPC handler - (File: internal/gitaly/hook/receivepack/receive_pack.go)

### Summary
Gitaly's proc-receive handling for `git-receive-pack` iterates over every reference update contained in a single push and, for each one, synchronously spawns a full custom-hook subprocess execution via `hookManager.UpdateHook`. There is no cap on how many reference updates a single authenticated pusher can include in one request, so a user with ordinary write access can submit a single push containing an arbitrarily large number of cheap ref updates (e.g. thousands of new lightweight branches pointing at the same, already-known object, requiring no new pack data) and force the Gitaly node to spawn one hook process per reference sequentially inside the RPC call, exhausting CPU/process/goroutine resources on the node. This is the analog of the Sherlock M-5 pattern: an attacker-controlled, unbounded list is fully iterated with a fixed per-item cost that the server cannot skip or amortize, and there is no upper bound or chunked/parallel processing to keep resource consumption bounded.

### Finding Description
The non-atomic branch of `procReceiveHook` in `internal/gitaly/hook/receivepack/receive_pack.go` loops over `handler.ReferenceUpdates()` — the full, client-supplied list of ref updates from a single push — and calls `receivePackReferenceUpdates` once per update: [1](#0-0) 

Inside `receivePackReferenceUpdates`, for **every** update in the (attacker-sized) slice, Gitaly invokes `hookManager.UpdateHook`, which runs a full custom-hook executor (subprocess spawn, environment construction, hook script execution) before queuing the ref change: [2](#0-1) 

`UpdateHook` itself launches a custom-hooks executor process per call when the node is primary: [3](#0-2) [4](#0-3) 

There is no configuration or code-level limit found on the number of reference updates that can be carried in a single `git-receive-pack`/proc-receive session (searches for size/count limits on push commands turned up none; the only related artifact is a *statistics* prefix cap in `internal/git/stats/receive_pack.go`, which only affects telemetry accuracy, not processing). The atomic path avoids the per-update hook loop (it commits updates in bulk with the hook run once via `receivePackReferenceUpdates` called with the whole slice), but the update hook is still invoked per-update inside that same function regardless of atomicity, since the loop at lines 228–244 executes unconditionally for however many updates are passed in.

An attacker who has push access to any repository can build a single push whose command list contains a very large number of ref updates (e.g., `refs/heads/attacker-<i>` for `i` in the tens of thousands), all pointing at the same, already-present commit so no meaningful pack data is needed. Because Git's push protocol places no server-independent bound on the number of `<old> <new> <ref>` command lines, and Gitaly does not reject overly large command lists before processing, the server will sequentially execute tens of thousands of hook subprocess launches for a single RPC call.

### Impact Explanation
Each additional reference update in the push forces Gitaly to spawn and wait on a subprocess (the custom-hooks executor for the `update` hook) synchronously within the RPC goroutine handling the push. With no upper bound, a single crafted push can consume disproportionate CPU, process-table entries, and wall-clock time on the Gitaly node, which can starve other concurrent RPCs on the same node/repository and effectively perform a denial-of-service against the receive-pack handler (`PostReceivePack`/`SSHReceivePack`/`ProcReceiveHook`), directly mirroring the "relayer forced to process a huge, attacker-inflated, unbounded list every round" pattern from the Sherlock report, except here the cost is paid immediately by the serving Gitaly node/RPC instead of a delayed relayer.

### Likelihood Explanation
Any user with push (write) access to a single branch-creatable repository can trigger this; no privileged role, leaked token, or malicious peer/MITM condition is required — this is exactly the "ordinary user's push" trigger path called out in the validation criteria. The attack requires no unusual permissions beyond normal write access and no large payload (creating many refs pointing to the same, already-existing object keeps the pack transfer itself small), making it low-cost and repeatable.

### Recommendation
Enforce an upper bound on the number of reference-update commands accepted per `git-receive-pack`/proc-receive session (rejecting or chunk-limiting oversized command lists before entering the per-update hook loop), and/or batch the `update` hook invocation instead of spawning one subprocess per reference so that processing cost no longer scales linearly (with subprocess overhead) in the number of refs a single unauthenticated-size push can specify.

### Proof of Concept
1. As a user with push access, prepare a `git-receive-pack` request whose command list contains N (e.g., 50,000) lines of the form `<oldOID=zero> <newOID=existingCommit> refs/heads/attacker-<i>`, followed by a minimal (or empty, since objects already exist) packfile.
2. Send this push via `PostReceivePack`/`SSHReceivePack` to a Gitaly node configured with a custom `update` hook script (as GitLab always installs) and proc-receive enabled.
3. Observe that `procReceiveHook` → `receivePackReferenceUpdates` (`internal/gitaly/hook/receivepack/receive_pack.go:228-244`) executes `hookManager.UpdateHook` (`internal/gitaly/hook/update.go:15-40`) N times sequentially, each spawning a hook subprocess, causing the RPC to take proportionally longer and consume proportionally more resources with no server-side cap, degrading availability for concurrent requests on the same Gitaly instance.
