Audit Report

## Title
Permanent Fund Lock in `pallet-asset-rewards` from Uncapped `last_update_block` After Pool Expiry - (File: `substrate/frame/asset-rewards/src/lib.rs`)

## Summary
`update_pool_rewards()` stamps `PoolInfo.last_update_block` to the actual current block number instead of capping it at `expiry_block`, while `reward_per_token()` computes `last_block_reward_applicable(expiry_block).ensure_sub(last_update_block)`. Once any staker calls `unstake` on their own position after `expiry_block` (permitted unconditionally via the `caller == staker` bypass), `last_update_block` becomes greater than `expiry_block`, and all subsequent calls to `reward_per_token()` underflow and error out, permanently bricking the pool.

## Finding Description
`PoolInfo` tracks `reward_per_token_stored` and `last_update_block` [6](#0-5) . `reward_per_token()` caps the elapsed-block window using `last_block_reward_applicable`, which returns `min(now, expiry_block)` [7](#0-6) , then subtracts `pool_info.last_update_block` via `ensure_sub` [8](#0-7) . However `update_pool_rewards()` sets `new_pool_info.last_update_block = T::BlockNumberProvider::current_block_number()` unconditionally, with no cap to `expiry_block` [1](#0-0) .

`unstake` allows the staker to act on their own account regardless of expiry: `ensure!(now > pool_info.expiry_block || caller == staker, BadOrigin);` [3](#0-2) , then persists the pool state unconditionally via `Pools::<T>::insert(pool_id, pool_info);` after `update_pool_and_staker_rewards` runs `update_pool_rewards` internally [4](#0-3) . `stake` behaves identically, persisting unconditionally [9](#0-8) .

Once any such call executes past `expiry_block`, `last_update_block` exceeds `expiry_block`. Every future call to `reward_per_token()` (from `stake`, `unstake`, `harvest_rewards`, `set_pool_reward_rate_per_block`, `set_pool_expiry_block`) then computes `expiry_block.ensure_sub(last_update_block)`, which underflows on the unsigned `BlockNumberFor<T>` and returns `Err`, causing the enclosing extrinsic to fail deterministically. Crucially, `set_pool_expiry_block` — the apparent admin remedy — itself calls `reward_per_token(&pool_info)` on the already-corrupted state before setting the new expiry [10](#0-9) , so it fails the same way and cannot repair the pool.

## Impact Explanation
This is a permanent user-fund lock: `total_tokens_staked` can never again be reduced via `unstake`, `harvest_rewards` always fails, and `cleanup_pool` requires an empty staker set that can never be reached. Staked asset balances and unclaimed reward-asset balances held in the pool's sub-account become permanently unreachable through any available extrinsic, satisfying the "permanent user-fund or bridge-state lock" impact category in the Polkadot SDK impact gate.

## Likelihood Explanation
No privileged actor or malicious behavior is required — the trigger is a routine, permitted action: any staker calling `unstake` on their own stake (`caller == staker` bypasses the expiry gate) after `expiry_block` has passed while other stakers remain in the pool. Any deployed pool with a bounded lifetime and multiple stakers is exposed to this under ordinary usage, making the likelihood high.

## Recommendation
In `update_pool_rewards()`, cap `last_update_block` to `Self::last_block_reward_applicable(pool_info.expiry_block)` instead of the raw current block number, mirroring the cap already applied inside `reward_per_token()`. This guarantees `last_update_block` never exceeds `expiry_block`, eliminating the underflow in the subsequent `ensure_sub` call.

## Proof of Concept
1. Create a pool with `expiry_block = 25` and two stakers, `staker1` and `staker2`, both staking non-zero amounts before expiry (mirrors the existing `integration` test setup) [11](#0-10) .
2. Advance the block number past `expiry_block` (e.g., to block 30) without calling `set_pool_expiry_block`.
3. `staker1` calls `unstake` for their own stake (`caller == staker` is allowed regardless of expiry): this persists `pool_info.last_update_block = 30` while `expiry_block` remains `25` via `Pools::<T>::insert` in `unstake`.
4. `staker2`, still holding a stake, calls `unstake` or `harvest_rewards`. `reward_per_token()` computes `last_block_reward_applicable(25).ensure_sub(30)` = `25 - 30`, underflows, and returns `Err`, causing the call to fail.
5. The admin attempts `set_pool_expiry_block` to remediate; it also fails because it calls `reward_per_token(&pool_info)` on the same corrupted `pool_info` before updating `expiry_block`.
6. `staker2`'s stake and any pending rewards remain permanently locked in the pool's sub-account with no available extrinsic path to recovery.

		/// Derives the current reward per token for this pool.
		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}
