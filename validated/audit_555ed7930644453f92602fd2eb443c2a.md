### Title
Truncation across the U256→FixedU128→u128→decimal-conversion chain in `calculate_fee` lets an unprivileged sender push the Ethereum-side relayer fee to zero, causing underpriced/unrelayed Snowbridge messages - ([File: bridges/snowbridge/pallets/outbound-queue/src/lib.rs])

### Summary
`Pallet::<T>::calculate_fee` computes the DOT-denominated fee a parachain sender must pay to cover the reward/gas cost of delivering a message to Ethereum. The value bounces through four different fixed-point/integer representations (`U256` wei → `u128` → `FixedU128` "mantissa" → decimal-rescaled `Balance`) without a single canonical scaled type, mirroring the "Excessive Indirection" pattern: each conversion silently truncates, and the pallet's own test suite documents a case where a fully valid, non-zero `PricingParameters` set yields a `remote` fee of exactly `0`, explicitly flagged in-repo as something "which should be avoided." [1](#0-0) 

### Finding Description
`calculate_fee` performs the following chain of representation changes:

1. `calculate_remote_fee` computes cost in wei as `U256` (`fee_per_gas * gas_used_at_most + reward`). [2](#0-1) 
2. The `U256` result is downcast to `u128` via `defensive_unwrap_or(u128::MAX)`. [3](#0-2) 
3. That raw `u128` is reinterpreted as the *inner* value of a `FixedU128` (`FixedU128::from_inner(fee)`), i.e. it is implicitly treated as already scaled by `10^18`, then multiplied by `multiplier` and divided by `exchange_rate`. [4](#0-3) 
4. The inner value is extracted again and passed through `convert_from_ether_decimals`, which does an integer `checked_div` by `10^(18 - Decimals)` to rescale from Ethereum's 18-decimal wei units to the local chain's `Decimals` (10 for DOT, 12 for KSM). [5](#0-4) 

Each of steps 2–4 is a place where a small, non-zero wei fee can be truncated to `0` once rescaled to a 10/12-decimal `Balance` — the "smallest non-zero value" invariant that the `Mantissa`/scaled-value convention is supposed to protect is not enforced anywhere in this chain; the code just passes raw integers back and forth between "wei," "FixedU128 mantissa," and "Balance" domains. The pallet's own test `test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero` demonstrates exactly this: with `exchange_rate = FixedU128::from_rational(1,1)`, `fee_per_gas = 1`, `reward.remote = 1`, `gas_used_at_most = 250000`, the remote fee that the sender is asked to pay collapses to `0` even though every individual pricing parameter passed `PricingParameters::validate()` (which only checks each field individually against zero, not the composed result). [6](#0-5) 

This value flows directly into `SendMessage::validate`, which is invoked for every outbound XCM/governance message routed to Ethereum via `EthereumBlobExporter`/`snowbridge_pallet_system::Pallet::send`, and is what an unprivileged parachain-originating XCM program is charged before the message is enqueued and later committed with a nonce. [7](#0-6)  There is no floor/minimum-fee check in `validate` or `calculate_fee` guarding against the composed result rounding to zero — the guard exists only informally in a test comment, not in the pallet logic.

### Impact Explanation
Because `remote` fee funds the reward paid out to the off-chain relayer that delivers the message to the Ethereum Gateway contract, driving it to zero (or near-zero) via ordinary, permitted parameter combinations lets any unprivileged sender enqueue and commit messages to the outbound queue nonce sequence while paying negligible or no compensation for the real ETH gas the relayer must spend. This is "public underpriced work that ... stalls bridge processing": relayers have no economic incentive to deliver these messages, so they pile up (nonces keep advancing in storage, but the messages are practically un-relayed), degrading the liveness of the bridge queue without requiring a malicious relayer, validator, or governance actor — purely a consequence of the unguarded multi-representation fee-scaling chain.

### Likelihood Explanation
The vulnerable computation path is exercised on every call to `SendMessage::validate` for Ethereum-bound traffic, i.e. on every ordinary user-triggered bridge send, not on a rare edge case. The exact zero-fee scenario is reproducible with realistic, validator-accepted `PricingParameters` (as shown by the existing unit test), and gas usage/exchange-rate/decimals combinations that produce small nonzero-but-truncating results are plausible in production once decimals differ (DOT=10, KSM=12) from Ethereum's 18. The main uncertainty is that `PricingParameters` is normally set by governance to realistic real-world values, which in practice keeps the computed fee well above the truncation floor — so exploiting this requires either an edge governance parameter set or specific low-gas commands; this reduces the immediate practical likelihood but does not remove the missing-invariant root cause.

### Recommendation
Enforce a validated invariant that `calculate_fee`'s composed remote fee is non-zero whenever `PricingParameters` passes `validate()`, either by adding a floor derived from the same rounding data (`checked_div` remainder promotion / round-up instead of round-down in `convert_from_ether_decimals`) or by rejecting the transaction (returning `SendError`) when the computed post-conversion fee is `0`. More structurally, apply the report's underlying recommendation: pick one canonical scaled representation (e.g. always keep the value as `U256` wei until the very last conversion, or always keep it as `FixedU128` and never re-inject a raw `u128` as an "inner" value) so intermediate unit identity is enforced by the type system rather than by convention, eliminating the repeated truncation points in this call chain.

### Proof of Concept
The existing repository test already demonstrates the bug deterministically: [1](#0-0) 
```rust
#[test]
fn test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero() {
    new_tester().execute_with(|| {
        let gas_used: u64 = 250000;
        let price_params: PricingParameters<<Test as Config>::Balance> = PricingParameters {
            exchange_rate: FixedU128::from_rational(1, 1),
            fee_per_gas: 1_u32.into(),
            rewards: Rewards { local: 1_u32.into(), remote: 1_u32.into() },
            multiplier: FixedU128::from_rational(1, 1),
        };
        let fee = OutboundQueue::calculate_fee(gas_used, price_params.clone());
        assert_eq!(fee.local, 698000000);
        // Though none zero pricing params the remote fee calculated here is invalid
        // which should be avoided
        assert_eq!(fee.remote, 0);
    });
}
```
All of `exchange_rate`, `fee_per_gas`, `rewards.remote`, and `multiplier` are non-zero and individually pass `PricingParameters::validate()`, yet the composed `fee.remote` charged to the sender via `SendMessage::validate` is `0`, confirming the truncation occurs in production code, not just in a contrived test.

	fn validate(
		message: &Message,
	) -> Result<(Self::Ticket, Fee<<Self as SendMessageFeeProvider>::Balance>), SendError> {
		// The inner payload should not be too large
		let payload = message.command.abi_encode();
		ensure!(
			payload.len() < T::MaxMessagePayloadSize::get() as usize,
			SendError::MessageTooLarge
		);

		// Ensure there is a registered channel we can transmit this message on
		ensure!(T::Channels::contains(&message.channel_id), SendError::InvalidChannel);

		// Generate a unique message id unless one is provided
		let message_id: H256 = message
			.id
			.unwrap_or_else(|| unique((message.channel_id, &message.command)).into());

		let gas_used_at_most = T::GasMeter::maximum_gas_used_at_most(&message.command);
		let fee = Self::calculate_fee(gas_used_at_most, T::PricingParameters::get());

		let queued_message: VersionedQueuedMessage = QueuedMessage {
			id: message_id,
			channel_id: message.channel_id,
			command: message.command.clone(),
		}
		.into();
		// The whole message should not be too large
		let encoded = queued_message.encode().try_into().map_err(|_| SendError::MessageTooLarge)?;

		let ticket = Ticket { message_id, channel_id: message.channel_id, message: encoded };

		Ok((ticket, fee))
	}
