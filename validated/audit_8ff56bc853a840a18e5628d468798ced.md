Based on my investigation, I found a concrete analog: `ConnectionState.Decrypt`/`VerifyRelay` in `connection_state.go` implement the anti-replay "checkpoint" (the `Bits` sliding window) using a **check-then-act pattern split across two separately acquired locks**, with the expensive decrypt operation happening *between* the check and the commit — exactly the same class of bug as the report (a window/checkpoint state is read, mutated later, and the gap between read and mutation is exploitable to corrupt/duplicate the tracked state).

### Title
Time-of-check/time-of-use gap in replay-window checkpointing allows duplicate processing of the same message counter - (File: `connection_state.go`)

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` protect against replay by consulting the `Bits` sliding-window "checkpoint" (`cs.window`) via `Check()`, then performing the (comparatively expensive) AEAD decryption *outside* any lock, and only afterward calling `Update()` to actually record the counter as seen. `Check()` and `Update()` are each individually locked with `decryptLock`, but the lock is released between them, so the read of the checkpoint state and the commit of the checkpoint state are not atomic as a pair.

### Finding Description
Both authenticated data-plane paths use the same three-step pattern: [1](#0-0) [2](#0-1) 

1. `cs.decryptLock.Lock(); result := cs.window.Check(l, messageCounter); cs.decryptLock.Unlock()`
2. Decrypt/verify the AEAD payload (no lock held)
3. `cs.decryptLock.Lock(); result = cs.window.Update(l, messageCounter); cs.decryptLock.Unlock()`

This mirrors the reported bug class exactly: a "checkpoint" data structure (here, the replay-window `Bits`, analogous to `s_checkpoints`) is read to decide whether a value has already been recorded, but the actual recording of that value into the checkpoint happens later and separately. If a duplicate/replayed packet for the same `messageCounter` is delivered to the interface a second time before step 3 completes for the first delivery (e.g. via a second `listenOut` reader goroutine when `routines > 1`, since multiple readers call `readOutsidePackets` concurrently — see `interface.go` lines 273-286 launching `f.routines` reader goroutines), both deliveries can pass `Check()` (since `Update()` for the first hasn't happened yet), both can successfully decrypt, and only one `Update()` call will ultimately register the counter — the other will report `ErrAlreadySeen` too late, **after** the plaintext has already been produced and (depending on caller behavior) potentially delivered to the tun device. This nullifies the intended one-shot guarantee of the anti-replay checkpoint in exactly the way the report's `_findCheckpoint`/`s_checkpointsNumberByAccount` increment nullified vote-weight state: the checkpoint bookkeeping and the checkpoint-consuming operation are split, and a well-timed duplicate slips through the gap.

### Impact Explanation
An attacker capturing a single legitimate encrypted packet from an established tunnel (no CA-signed certificate of their own required — they only need to observe/duplicate ciphertext on the wire, e.g., a MITM or a malicious relay position) can replay it in quick succession. On a multi-routine (`routines > 1`) listener, this creates a race where the replay window fails to reject the duplicate before decryption completes, defeating the nonce/replay protection that is supposed to guarantee each `messageCounter` is processed exactly once. This is the same "duplicate the checkpoint update" impact pattern the report describes for votes, translated to traffic replay/decryption integrity.

### Likelihood Explanation
Requires `routines > 1` (multi-queue UDP listener, a supported and documented configuration) and precise timing to land two deliveries of the same counter within the `Check`→`Update` window. This is a race condition, not deterministic, but is a genuine widening of the anti-replay guarantee's atomicity that the checkpoint pattern in the report calls out as the root cause class.

### Recommendation
Hold `decryptLock` across the entire `Check` → decrypt → `Update` sequence (or use a compare-and-commit primitive) so that no second caller can observe a "not yet seen" `Check()` result for a counter whose corresponding `Update()` is still pending. Equivalently, reserve/mark the counter as "in-flight" at `Check()` time so a concurrent duplicate is rejected immediately rather than being allowed to proceed to decryption.

### Proof of Concept
Not independently verified with a running exploit — this requires constructing a `routines: 2`+ configuration, establishing a tunnel, capturing one data-plane packet, and re-injecting it via two sockets nearly simultaneously to win the race between `Check` and `Update` in `connection_state.go`. I was not able to execute this in the current environment; the analysis is based on static review of the locking pattern in `connection_state.go` lines 61-108 and the multi-reader dispatch in `interface.go` lines 273-286.

**Uncertainty note:** I could not fully confirm whether an upstream caller of `Decrypt` performs any additional counter-level deduplication before writing to the tun device, which would mitigate real-world impact even if the race is won. This would need to be checked in `inside.go`/the packet-write path before treating this as fully exploitable in production.

func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}
