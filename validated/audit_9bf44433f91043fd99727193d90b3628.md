### Title
Shielded Transaction HTTP/gRPC APIs Transmit Raw Spending-Key Secret Material (`ask`/`nsk`/`ovk`), Leaking Full Spend Authority to Any Node the Wallet Talks To - (File: `framework/src/main/java/org/tron/core/services/http/GetExpandedSpendingKeyServlet.java`)

### Summary
Multiple java-tron HTTP and gRPC endpoints require the caller to send or receive the raw components of a shielded spending key — `ask` (spend authorizing key), `nsk` (nullifier deriving key) and `ovk` (outgoing viewing key) — as plaintext transaction parameters, rather than performing the sensitive signing/derivation operation with a scoped, single-purpose credential. Any node (including a remote or third-party FullNode) that a wallet/client uses to build a shielded transaction receives full spend authority over the shielded account, not just the narrow capability needed (e.g., deriving a public value or assembling an unsigned transaction). This mirrors the Magnum bug class: a credential intended for a narrow purpose is handed over in a channel that grants full, unscoped power to whoever receives it.

### Finding Description
`node.allowShieldedTransactionApi`/legacy `fullNodeAllowShieldedTransaction` config exists specifically because these APIs "require sending private keys as parameters," and the maintainers' own warning states that "Calling these APIs on untrusted or remote nodes may leak your private keys" [1](#0-0) .

Concretely, the following servlets accept or return raw `ask`/`nsk`/`ovk` material over plain HTTP as request/response bodies:
- `GetSpendingKeyServlet` returns a brand-new full spending key (`ask`, `nsk`, `ovk`) to any caller [2](#0-1) .
- `GetExpandedSpendingKeyServlet` takes a raw spending key as a hex/byte parameter and expands it into `ask`, `nsk`, `ovk`, echoing the full secret triple back in the response [3](#0-2) .
- `getAkFromAsk` / `getNkFromNsk` take the raw `ask`/`nsk` secret values directly as request parameters over HTTP/gRPC [4](#0-3) .
- The protobuf messages `PrivateParameters`, `PrivateParametersWithoutAsk`, `SpendAuthSigParameters`, and `ExpandedSpendingKeyMessage` are all defined to carry `ask`, `nsk`, `ovk` in cleartext across the wire [5](#0-4) .
- `CreateShieldedTransactionServlet` and the RPC equivalent `createShieldedTransactionWithoutSpendAuthSig` require the client to submit these secret values so the *node itself* builds and signs the transaction on the client's behalf [6](#0-5) [7](#0-6) .

Exactly like the Magnum flaw — where a credential scoped only for retrieving instance SSL certificates instead carried full OpenStack API authority when handed to Heat — here a value that a shielded-transaction protocol conceptually treats as "spend authority for one operation" is transmitted whole, in the clear, to whichever node processes the API call. Any full node operator, a man-in-the-middle on an unencrypted HTTP/gRPC channel, or a misconfigured public-facing node (`walletExtensionApi`/`http.fullNodeEnable` = true by default per `reference.conf`) can capture `ask`/`nsk`/`ovk` and gain permanent, unlimited spend authority over the shielded account — not merely the ability to complete the single requested operation.

### Impact Explanation
Capture of `ask`+`nsk`+`ovk` grants an attacker full and repeatable spend authority over a shielded TRON account: they can spend all present and future shielded balances at will, indefinitely, without needing further interaction from the victim. This is a concrete "theft of funds / key disclosure" outcome as required by the validation criteria, reachable by any unprivileged client that calls a remotely-hosted or MITM'd node for shielded-transaction assistance — a normal, expected usage pattern for wallets that don't run their own full node.

### Likelihood Explanation
The reference configuration comment itself documents that this leak occurs whenever these APIs are invoked against "untrusted or remote nodes," and explicitly recommends only invoking them locally [1](#0-0) . Given that FullNode HTTP/gRPC/PBFT/Solidity interfaces are enabled by default (`fullNodeEnable = true`, `rpc.enable = true`) [8](#0-7) , and shielded wallets commonly rely on third-party or public FullNodes for convenience, the exposure path is realistic and requires no special privilege — any client capable of sending a normal HTTP/gRPC request can trigger it, and any node operator or network-path observer can passively harvest the secrets.

### Recommendation
- Never transmit `ask`/`nsk` in cleartext to a remote node; all shielded transaction construction and key derivation that requires spend-authority material should happen exclusively client-side (as the codebase already partially supports via `PrivateParametersWithoutAsk`/`createShieldedTransactionWithoutSpendAuthSig`), and the `ask`-requiring variants should be removed or hard-disabled by default rather than gated by an easily-overlooked config flag.
- Enforce `allowShieldedTransactionApi=false` by default and make all `ask`/`nsk`/`ovk`-carrying endpoints (`GetExpandedSpendingKeyServlet`, `GetAkFromAskServlet`, `GetNkFromNskServlet`, `GetSpendingKeyServlet`, `CreateShieldedTransactionServlet`) explicitly refuse to run unless bound to `localhost`, independent of the general HTTP/RPC enable flags.
- Require TLS for any endpoint capable of carrying spend-authority secrets, and strip these fields from access/debug logs.

### Proof of Concept
1. Configure or use any publicly reachable java-tron FullNode with default settings (`node.http.fullNodeEnable=true`).
2. As an unprivileged client, call `POST /wallet/getexpandedspendingkey` with a `value` parameter containing a shielded account's raw spending key, or call the gRPC `createShieldedTransactionWithoutSpendAuthSig` with `ak`/`nsk`/`ovk` populated in `PrivateParametersWithoutAsk`.
3. The node operator (or anyone intercepting the unencrypted HTTP/gRPC channel) now possesses the account's `ask`/`nsk`/`ovk`, granting full, permanent spend authority over that shielded account — usable to drain funds at any later time without further victim interaction.

  protected void doPost(HttpServletRequest request, HttpServletResponse response) {
    try {
      PostParams params = PostParams.getPostParams(request);
      BytesMessage.Builder build = BytesMessage.newBuilder();
      JsonFormat.merge(params.getParams(), build);
      fillResponse(params.isVisible(), build.getValue(), response);
    } catch (Exception e) {
      Util.processError(e, response);
    }
  }

  private void fillResponse(boolean visible, ByteString spendingKey, HttpServletResponse response)
      throws Exception {
    ExpandedSpendingKeyMessage reply = wallet.getExpandedSpendingKey(spendingKey);
    if (reply != null) {
      response.getWriter().println(JsonFormat.printToString(reply, visible));
    } else {
      response.getWriter().println("{}");
    }
  }

    @Override
    public void createShieldedTransactionWithoutSpendAuthSig(PrivateParametersWithoutAsk request,
        StreamObserver<TransactionExtention> responseObserver) {

      TransactionExtention.Builder trxExtBuilder = TransactionExtention.newBuilder();
      Return.Builder retBuilder = Return.newBuilder();

      try {
        TransactionCapsule trx = wallet.createShieldedTransactionWithoutSpendAuthSig(request);
        trxExtBuilder.setTransaction(trx.getInstance());
        trxExtBuilder.setTxid(trx.getTransactionId().getByteString());
        retBuilder.setResult(true).setCode(response_code.SUCCESS);
      } catch (ContractValidateException | ZksnarkException e) {
        retBuilder.setResult(false).setCode(response_code.CONTRACT_VALIDATE_ERROR)
            .setMessage(ByteString
                .copyFromUtf8(Wallet.CONTRACT_VALIDATE_ERROR + e.getMessage()));
        logger.debug(CONTRACT_VALIDATE_EXCEPTION, e.getMessage());
      } catch (Exception e) {
        retBuilder.setResult(false).setCode(response_code.OTHER_ERROR)
            .setMessage(ByteString.copyFromUtf8(e.getClass() + " : " + e.getMessage()));
        logger.info(
            "createShieldedTransactionWithoutSpendAuthSig exception caught: " + e.getMessage());
      }

      trxExtBuilder.setResult(retBuilder);
      responseObserver.onNext(trxExtBuilder.build());
      responseObserver.onCompleted();

    }
