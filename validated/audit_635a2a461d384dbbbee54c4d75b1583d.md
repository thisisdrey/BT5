### Title
Heap-buffer-overread when reading Zip64 extra-field attributes without validating declared attribute count - ([File: src/tools/singlejar/zip_headers.h](path))

### Summary
Bazel's `singlejar` tool (used to build deploy jars and interface jars, including from jars that originate from third‑party/external dependencies fetched via `http_archive`/`http_jar`/Maven-style repository rules) parses ZIP Central Directory Headers (`CDH`) and Local Headers (`LH`) that carry a Zip64 "extra field" extension analogous in structure to an X.509 certificate extension (a tag + length-prefixed payload). Just like GnuTLS's SCT extension parser (CVE-2025-32989) trusted a sub-structure's presence without validating that the declared extension actually contains enough bytes for the fields it reads, `Zip64ExtraField::attr64(int index)` reads a fixed 8-byte slot at `attr_[index]` purely from pointer arithmetic, without checking that `index < attr_count()` (i.e., without checking that the field's own `payload_size()` actually covers that slot).

### Finding Description
The Zip64 extra field is defined in `src/tools/singlejar/zip_headers.h`: [1](#0-0) 

`ExtraField::find` (used by `Zip64ExtraField::find`) only validates that the *whole* extra field (`sizeof(ExtraField) + payload_size()`) fits inside the `extra_fields` region of the CDH/LH — it never validates that the number of 8‑byte attributes implied by the surrounding 32-bit size fields actually matches the field's own `payload_size()`: [2](#0-1) 

The size accessors on `CDH`/`LH` decide, from the *separate* 32-bit `compressed_file_size32_`/`uncompressed_file_size32_`/`local_header_offset32_` fields (sentinel `0xFFFFFFFF`), which index into the Zip64 field's `attr_[]` array to read — but they never check that the field's declared `attr_count()` actually contains that many slots: [3](#0-2) [4](#0-3) 

So an attacker who controls a `.jar`/`.zip` file consumed by singlejar (e.g., a malicious dependency archive fetched by `http_archive`/`http_jar`, or any jar merged via `java_library`'s deploy-jar assembly) can:
1. Set `compressed_file_size32` and/or `uncompressed_file_size32` to `0xFFFFFFFF` to signal "value is in Zip64 extra field", which forces the code down the `attr64(index)` path.
2. Attach a Zip64 extra field whose declared `payload_size` only covers fewer 8-byte attributes than the sentinel flags imply (e.g., `payload_size = 8`, one attribute) while the 32-bit sentinels imply two or three attributes are needed.
3. `Zip64ExtraField::find` accepts the field because it is internally consistent with its own (undersized) `payload_size` and fits within the CDH's `extra_fields_length()`.
4. `attr64(1)` or `attr64(2)` is then called, reading 8 bytes starting past the field's actual payload — bytes that were never validated to belong to this extension, exactly mirroring GnuTLS reading fixed SCT sub-fields without checking the SCT extension's actual declared length.

This read happens against the input jar's memory-mapped buffer (`InputJar`/`MappedFile`, see `src/tools/singlejar/input_jar.h`), so depending on where the malformed field sits relative to the CDH buffer boundary, the read can run past the mapped file into adjacent memory content, an out-of-bounds/heap-buffer-overread.

### Impact Explanation
The garbage 64-bit value read out-of-bounds is returned as `compressed_file_size()`/`uncompressed_file_size()`/`local_header_offset()`, which then feeds directly into `num_bytes` in `OutputJar::AddJar` (`src/tools/singlejar/output_jar.cc`, lines 590–671) used for `WriteBytes(input_jar.mapped_start() + copy_from, num_bytes)`. An inflated, attacker-influenced size derived from out-of-bounds memory can cause singlejar to copy adjacent memory content (not belonging to the entry) into the output deploy/interface jar — analogous to CVE-2025-32989's "exposure of confidential information," here potentially leaking bytes adjacent to the mapped input jar into a build artifact, plus a crash/overread condition detectable by ASan.

### Likelihood Explanation
This is reachable purely by supplying a crafted jar file as a build input (e.g., a malicious `http_archive`/`http_jar` dependency or any third-party `.jar` merged into a `java_binary`'s deploy jar) — no special privileges are required beyond controlling content the victim's build fetches or references. The existing `MalformedExtraField` regression test in `src/tools/singlejar/output_jar_simple_test.cc` (`CreateZipWithMalformedExtraField`, `TEST_F(OutputJarSimpleTest, MalformedExtraField)`) only exercises the "extra field size exceeds extra-fields buffer" case, which is caught by `ExtraField::find`'s / `AppendToDirectoryBuffer`'s explicit bounds checks — it does **not** cover the distinct case of a Zip64 field whose own declared `payload_size`/`attr_count()` is smaller than what the sentinel 32-bit size fields imply, which is not checked anywhere in `attr64()`.

### Recommendation
In `Zip64ExtraField::attr64()` (or at each call site in `CDH`/`LH` size/offset accessors), validate `index < attr_count()` before dereferencing `attr_[index]`, and treat a Zip64 field with insufficient attributes for the flags set in the 32-bit sentinel fields as malformed input (fail fast, as is already done for other malformed-extra-field cases), rather than performing raw pointer arithmetic based on unchecked sentinel-derived indices.

### Proof of Concept
Extend the existing `CreateZipWithMalformedExtraField`-style harness in `src/tools/singlejar/output_jar_simple_test.cc`:
1. Build a CDH with `compressed_file_size32 = 0xFFFFFFFF` and `uncompressed_file_size32 = 0xFFFFFFFF` (both sentinel, implying 2 Zip64 attributes needed).
2. Attach a Zip64 extra field (`tag = 1`) with `payload_size = 8` (only one 8-byte attribute present) instead of the required 16.
3. Run `OutputJar::Doit()` on this crafted jar under AddressSanitizer.
4. Observe a heap-buffer-overread when `CDH::compressed_file_size()`/`uncompressed_file_size()` calls `Zip64ExtraField::attr64(1)`, reading 8 bytes past the field's actual declared payload.

**Uncertainty/limitations**: I could not fully trace whether every call site clamps `num_bytes` against the actual mapped-file length elsewhere before the `WriteBytes` copy (which would reduce impact to an internal overread rather than data leaking into the output artifact), nor could I confirm from the index whether an existing ASan/fuzz test already exercises this exact `attr_count()` mismatch (only the "extra field length exceeds buffer" variant was found). A background Devin session with full repository access and the ability to build/run singlejar under ASan would be needed to confirm the exact overread magnitude and whether it reaches the output artifact versus merely crashing.

class ExtraField {
 public:
  static const ExtraField* find(uint16_t tag, const uint8_t* start,
                                const uint8_t* end) {
    while (start < end) {
      if (ziph::byte_ptr(start) + sizeof(ExtraField) > ziph::byte_ptr(end)) {
        break;
      }
      auto extra_field = reinterpret_cast<const ExtraField*>(start);
      if (ziph::byte_ptr(start) + extra_field->size() > ziph::byte_ptr(end)) {
        break;
      }
      if (extra_field->is(tag)) {
        return extra_field;
      }
      start = ziph::byte_ptr(start) + extra_field->size();
    }
    return nullptr;
  }

class Zip64ExtraField : public ExtraField {
 public:
  static const Zip64ExtraField* find(const uint8_t* start, const uint8_t* end) {
    return reinterpret_cast<const Zip64ExtraField*>(
        ExtraField::find(1, start, end));
  }

  bool is() const { return is_zip64(); }
  void signature() { ExtraField::signature(1); }

  // The value of i-th attribute
  uint64_t attr64(int index) const { return le64toh(attr_[index]); }
  void attr64(int index, uint64_t v) { attr_[index] = htole64(v); }

  // Attribute count
  int attr_count() const { return payload_size() / sizeof(attr_[0]); }
  void attr_count(int n) { payload_size(n * sizeof(attr_[0])); }

  // Space needed for this field to accommodate n_attr attributes
  static uint16_t space_needed(int n_attrs) {
    return n_attrs > 0 ? sizeof(Zip64ExtraField) + n_attrs * sizeof(uint64_t)
                       : 0;
  }

 private:
  uint64_t attr_[];
} attr_packed;
