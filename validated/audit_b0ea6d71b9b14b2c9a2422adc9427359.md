### Title
False inventory advertisement + un-validated "success" scoring in Atlas attachment download lets a lying peer starve resolution of a name's real attachment - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentsBatchStateContext::get_prioritized_attachments_requests` trusts a peer's self-reported `GetAttachmentsInvResponse` inventory bit as proof of possession and adds that peer to `sources` with no verification. Worse, when the attachment is actually fetched, `extend_with_attachments` marks the peer's request "successful" (bumping its `ReliabilityReport`) purely because the HTTP body decoded, without checking that the returned content's hash equals the requested `content_hash`. A malicious peer can therefore falsely claim inventory, get selected as the (or preferred) source, and repeatedly return garbage that "succeeds" at decoding while never resolving the real attachment, ultimately causing the batch to be dropped after `max_attachment_retry_count` retries.

### Finding Description
In `get_prioritized_attachments_requests` (`stackslib/src/net/atlas/download.rs:434-459`), `has_attachment` is derived solely from the peer-supplied `response.pages[...].inventory[position_in_page] == 1` [1](#0-0)  — there is no cross-check that the peer can actually serve that content. If `has_attachment` is true, the peer is unconditionally inserted into `sources` for the `AttachmentRequest` [2](#0-1) .

`AttachmentRequest::get_most_reliable_source` / `get_url` picks the source with the highest `ReliabilityReport::score()` [3](#0-2) . When the actual `/v2/attachments/{hash}` request is issued and answered, `extend_with_attachments` only checks that `decode_atlas_get_attachment()` succeeds (i.e., the body is valid hex/JSON) before calling `report.bump_successful_requests()` — it never compares the decoded `Attachment::hash()` to the `AttachmentRequest.content_hash` that was actually requested [4](#0-3) .

The hash check only happens later and indirectly, in `AttachmentsDownloader::run`, which looks up `find_all_attachment_instances(&attachment.hash())` using the hash of whatever bytes were returned, not the requested `content_hash` [5](#0-4) . If the peer returned unrelated/garbage bytes, `attachment.hash()` won't match any tracked instance, so the real instance stays unresolved in `attachments_batch`, and the batch is re-queued and eventually dropped once `retry_count >= max_attachment_retry_count` [6](#0-5) .

Because the content-addressed hash check prevents outright data corruption/spoofing (garbage content is never stored under the victim's `content_hash`), the real exploitable consequence is a denial-of-availability: the lying peer's `ReliabilityReport` is inflated by "successful" (but content-mismatched) responses, biasing `get_most_reliable_source` toward it on subsequent retries, while genuine peers that actually hold the data are starved of selection. After exhausting `max_attachment_retry_count` retries, the batch (and the name's real attachment resolution) is permanently dropped.

### Impact Explanation
A remote, unprivileged peer (an outbound sync peer the victim node has chosen, requiring only running one's own peer and completing a normal handshake — no secret/admin role) can repeatedly:
1. Advertise `inventory[position]==1` for attachments it does not hold, via `/v2/attachments/inv` responses.
2. Get added to `sources` for the corresponding `AttachmentRequest`.
3. Respond to `/v2/attachments/{hash}` with valid-but-wrong-content bytes, which "succeeds" at decode and boosts its reliability score.

This biases future source selection toward the lying peer and away from honest peers holding the real data, and after retry-count exhaustion the batch is dropped, denying resolution of that name's real committed attachment (BNS data availability denial). This matches the "attachment/BNS mismatch" / availability-denial category. It does not corrupt stored data (hash binding protects against actual forged content being accepted), so the severity is bounded to denial-of-resolution rather than data corruption.

### Likelihood Explanation
Requires the attacker's node to be selected as one of the node's `outbound_sync_peers` (achievable by any peer that completes a normal P2P handshake — not privileged), and it must respond to `/v2/attachments/inv` and `/v2/attachments/{hash}` requests, both public unauthenticated RPC endpoints. The cost is trivial (a few HTTP responses per retry cycle), and the effect is repeatable across retries until `max_attachment_retry_count` is hit. Full denial of resolution additionally depends on the node's other selected peers not overriding the biased selection (e.g., ties or reliability inflation favoring the attacker), so likelihood is contingent on peer set composition but not on any privileged precondition.

### Recommendation
- In `extend_with_attachments`, verify `response.attachment.hash() == request.content_hash` before calling `bump_successful_requests()`; treat a hash mismatch as a failed/faulty response (`bump_failed_requests()`, and consider blacklisting/deregistering the peer for lying).
- Optionally, do not trust the `GetAttachmentsInvResponse` inventory bit without some corroboration, or penalize `ReliabilityReport` scores when a peer's advertised inventory doesn't match delivered content.

### Proof of Concept
Rust test plan (in `stackslib/src/net/atlas/tests.rs` style):
1. Build an `AttachmentsBatch` tracking one `AttachmentInstance` with a known `content_hash`.
2. Construct an `AttachmentsBatchStateContext` with two peers: `honest_peer` and `malicious_peer`.
3. Populate `context.inventories` with a `GetAttachmentsInvResponse` for `malicious_peer` that sets `inventory[position_in_page] = 1` for the target index even though it holds no matching data.
4. Call `context.get_prioritized_attachments_requests()` and assert `malicious_peer` appears in the resulting `AttachmentRequest.sources` (proving the false-advertisement is trusted).
5. Simulate `extend_with_attachments` with a `BatchedRequestsResult` where `malicious_peer`'s response decodes successfully (`decode_atlas_get_attachment` returns `Ok`) but `Attachment::hash() != content_hash`; assert `report.bump_successful_requests()` is invoked (score increases) despite the mismatch — this is the exact assertion showing the missing hash-equality guard.
6. Confirm in `AttachmentsDownloader::run`'s `Done` branch that `context.attachments_batch.resolve_attachment` is never called for the true `content_hash` (since `attachment.hash()` differs), leaving the instance unresolved, and that after `max_attachment_retry_count` iterations the batch is dropped without ever fetching the real attachment.

impl AttachmentRequest {
    pub fn get_most_reliable_source(&self) -> (&UrlString, &ReliabilityReport) {
        self.sources
            .iter()
            .max_by_key(|(_, v)| v.score())
            .expect("Atlas: trying to select an Url out of an empty set")
    }
}

impl Hash for AttachmentRequest {
    fn hash<H: Hasher>(&self, state: &mut H) {
        self.content_hash.hash(state)
    }
}

impl Ord for AttachmentRequest {
    fn cmp(&self, other: &AttachmentRequest) -> Ordering {
        other.sources.len().cmp(&self.sources.len()).then_with(|| {
            let (_, report) = self.get_most_reliable_source();
            let (_, other_report) = other.get_most_reliable_source();
            report.cmp(other_report)
        })
    }
}

impl PartialOrd for AttachmentRequest {
    fn partial_cmp(&self, other: &AttachmentRequest) -> Option<Ordering> {
        Some(self.cmp(other))
    }
}

impl Requestable for AttachmentRequest {
    fn get_url(&self) -> &UrlString {
        let (url, _) = self.get_most_reliable_source();
        url
    }
