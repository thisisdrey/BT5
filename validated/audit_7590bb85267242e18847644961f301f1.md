### Title
FetchRemote's `timeout` field has no upper (or meaningful lower) bound, allowing indefinite mutator RPC execution - (File: internal/gitaly/service/repository/fetch_remote.go)

### Summary
The `FetchRemoteRequest.timeout` field is a caller-supplied `int32` that gates whether `FetchRemote` ever applies a context deadline to the underlying `git-fetch` operation. There is no validation of this value's range, and a value of `0` or negative disables timeout enforcement entirely, letting the mutator RPC — and the repository-wide state it holds (quarantine directory, reference-transaction locks) — run unbounded.

### Finding Description
`FetchRemote` only applies a timeout when the client-supplied value is strictly positive: [1](#0-0) 

`validateFetchRemoteRequest` performs no check on `req.GetTimeout()` at all — it only validates the repository and remote URL: [2](#0-1) 

This is directly analogous to the reported bug class: a caller-influenced numeric setting (`timeout`, in seconds, `int32`) has no sane minimum/maximum enforced at the point it is consumed. Just as the Nouns Builder report showed that `duration`/`timeBuffer` with no upper bound could keep an auction open indefinitely, an omitted or non-positive `timeout` here means `FetchRemote` never applies a deadline, and `git-fetch` (invoked via `quarantineRepo.FetchRemote`) can run for an unbounded duration while holding the quarantine directory and reference-transaction locks open: [3](#0-2) [4](#0-3) 

Unlike the general concurrency/queue limiter subsystem in Gitaly, which does implement explicit range validation via `cfgerror.Comparable(...).GreaterThan(0)`-style checks in `ConcurrencyLimits.Validate()` and `PackObjectsLimiting.Validate()`: [5](#0-4) [6](#0-5) 

...the per-RPC `timeout` field on `FetchRemoteRequest` (a value directly controllable by the RPC caller, not an admin-configured `.toml` setting) has no equivalent bound check at the point of use.

### Impact Explanation
A caller that omits `timeout` or sets it to `0`/a negative value causes `FetchRemote` to run with no deadline. Combined with a slow, hanging, or maliciously stalling remote (the RPC accepts arbitrary `RemoteParams.Url`, including `resolved_address` overrides), the fetch can be held open indefinitely. Because `fetchRemoteAtomic` holds a quarantine directory and starts two `updateref.Updater` reference transactions for the target repository before completing, an unbounded fetch effectively occupies that repository's mutator/lock state for as long as the attacker-controlled remote keeps the connection open, denying other operations on that repository. This is a DoS of a specific RPC handler bounded to a repository, consistent with the "DoS of a handler" acceptance criterion.

### Likelihood Explanation
Likelihood is low-to-moderate: `FetchRemote` is a mutator RPC typically invoked in the context of pull-mirroring configured by a repository owner/maintainer, so the caller already has some level of trust, but the RPC itself does not require any elevated Gitaly-internal privilege beyond normal repository write access, and none of the request-shaping fields (`timeout`, `remote_params.url`) are range- or scheme-restricted at this layer. This mirrors the original report's judged severity: low likelihood of intentional misuse, but real impact once it occurs because there's no compensating server-side bound.

### Recommendation
- In `validateFetchRemoteRequest`, reject non-positive `timeout` values or apply a sane server-side default and maximum (e.g., clamp to a bounded range analogous to `UploadPackNegotiation`/`UploadArchiveNegotiation` timeouts already defined in `TimeoutConfig`).
- Always apply a context deadline in `FetchRemote`, even when the caller supplies `0` or a negative value, by falling back to a Gitaly-side maximum timeout instead of skipping deadline enforcement entirely.
- Consider adding an explicit upper bound validation similar to the pattern already used for concurrency/queue settings in `ConcurrencyLimits.Validate()`.

### Proof of Concept
1. An operator with mirror/fetch permissions issues `FetchRemote` with `RemoteParams.Url` pointing to a remote/server the attacker controls (or a slow-responding proxy) and `Timeout` unset (`0`).
2. Because `req.GetTimeout() > 0` is false, no `context.WithTimeout` is applied at `internal/gitaly/service/repository/fetch_remote.go:35-39`.
3. The attacker-controlled remote holds the TCP/HTTP connection open (never completing the fetch negotiation) indefinitely.
4. `quarantineRepo.FetchRemote(ctx, "inmemory", opts)` at `internal/gitaly/service/repository/fetch_remote.go:104` blocks indefinitely, keeping the quarantine directory and reference-transaction updaters open for the target repository, preventing other mutator operations on that repository from completing.

func (s *server) validateFetchRemoteRequest(ctx context.Context, req *gitalypb.FetchRemoteRequest) error {
	if err := s.locator.ValidateRepository(ctx, req.GetRepository()); err != nil {
		return structerr.NewInvalidArgument("%w", err)
	}

	if req.GetRemoteParams() == nil {
		return structerr.NewInvalidArgument("missing remote params")
	}

	if req.GetRemoteParams().GetUrl() == "" {
		return structerr.NewInvalidArgument("blank or empty remote URL")
	}

	return nil
}

// Validate runs validation on all fields and compose all found errors.
func (pol PackObjectsLimiting) Validate() error {
	// Validate the embedded ConcurrencyLimits fields manually to handle both MaxQueueSize and MaxQueueLength
	errs := cfgerror.New().
		Append(cfgerror.Comparable(pol.MaxConcurrency).GreaterOrEqual(0), "max_concurrency").
		Append(cfgerror.Comparable(pol.MaxPerRepo).GreaterOrEqual(0), "max_per_repo").
		Append(cfgerror.Comparable(pol.MaxQueueWait.Duration()).GreaterOrEqual(0), "max_queue_wait")

	// Validate queue size fields
	hasMaxQueueSize := pol.MaxQueueSize != 0
	hasMaxQueueLength := pol.MaxQueueLength != 0

	if hasMaxQueueSize {
		errs = errs.Append(cfgerror.Comparable(pol.MaxQueueSize).GreaterThan(0), "max_queue_size")
	}
	if hasMaxQueueLength {
		errs = errs.Append(cfgerror.Comparable(pol.MaxQueueLength).GreaterThan(0), "max_queue_length")
	}

	// If neither is set, that's an error
	if !hasMaxQueueSize && !hasMaxQueueLength {
		errs = errs.Append(
			fmt.Errorf("at least one of max_queue_size or max_queue_length must be set"),
			"max_queue_size",
		)
	}

	if pol.Adaptive {
		errs = errs.
			Append(cfgerror.Comparable(pol.MinLimit).GreaterThan(0), "min_limit").
			Append(cfgerror.Comparable(pol.MaxLimit).GreaterOrEqual(pol.InitialLimit), "max_limit").
			Append(cfgerror.Comparable(pol.InitialLimit).GreaterOrEqual(pol.MinLimit), "initial_limit")
	}

	if pol.Unauthenticated.IsSet() {
		errs = errs.Append(pol.Unauthenticated.Validate(), "unauthenticated")
	}

	return errs.AsError()
}
