### Title
Unbounded `strchr` scan over an un-terminated JAR MANIFEST buffer leaks adjacent heap bytes into rewritten manifest output - ([File: third_party/ijar/ijar.cc])

### Summary
`ijar` (`third_party/ijar/ijar.cc`) reads the `META-INF/MANIFEST.MF` entry of an attacker-supplied JAR into an exactly-sized `malloc()` buffer with no trailing NUL/newline guarantee, then scans it with `strchr(line_start, '\n')` to find line boundaries. If the manifest content does not end with `\n` at the declared uncompressed size, `strchr` continues scanning past the end of the heap allocation into adjacent memory. In `AppendTargetLabelToManifest` that out-of-bounds "line" length is then `memcpy`'d directly into the freshly written manifest of the output jar, exposing adjacent heap bytes to any consumer of the rewritten jar — the same bug class as the reported Imager `strlen()`-over-read (a size-derived scan run past a buffer, with the over-read bytes copied into a caller-visible field).

### Finding Description
`ManifestLocator::Process` allocates the manifest buffer with exactly the entry's declared size and copies the entry bytes with no added terminator: [1](#0-0) 

Both `IsMultiRelease` and `AppendTargetLabelToManifest` treat this buffer as if it were a normal C string terminated by `\n`, calling `strchr(line_start, '\n')` with no upper bound check against `data_end`: [2](#0-1) [3](#0-2) 

If the attacker crafts a JAR whose `MANIFEST.MF` entry content does not contain a trailing `\n` before the entry's declared uncompressed-size boundary, the last iteration's `strchr(line_start, '\n')` will run past `data_end` into whatever heap memory follows the `malloc(size)` allocation, until it happens to find a `\n` byte somewhere else on the heap. The resulting `line_end` (and thus `len = line_end - line_start`) extends beyond the legitimate manifest bytes. In `AppendTargetLabelToManifest`, this over-long `len` is used directly in:
```
memcpy(buf, line_start, len);
```
copying the out-of-bounds heap bytes into `buf`, which is the newly written `META-INF/MANIFEST.MF` entry of the *output* interface/copied jar produced by `ijar`. Any consumer that later reads that output jar (e.g. downstream build/consumption of the manifest) can observe adjacent heap memory contents that were never intended to be exposed — directly analogous to the CVE's `copy_string_tags`/`i_tags_add` pattern where a `-1`-turned-`strlen()` scan copies unintended adjacent heap bytes into an attacker-observable tag value.

This is reachable purely from the contents of a JAR file that `ijar` processes (a dependency, srcjar, or any zip fed to the `ijar` binary), i.e., attacker-controlled content consumed by the build, not a local/trusted-root-BUILD-file issue.

### Impact Explanation
A crafted JAR (served as a fetched dependency/archive, or produced by a malicious build step whose output is consumed by `ijar`) can cause `ijar` to leak adjacent process heap bytes into the manifest of its output jar. Since jar contents are typically included/propagated further into the build graph and can end up in distributed artifacts, this is a High-severity confidentiality/information-disclosure issue for the machine running the build (process heap contents, potentially containing sensitive data such as fragments of other in-memory build state) can leak into build outputs. It can also cause an actual out-of-bounds read/segfault (crash / DoS) if `strchr` walks off a mapped page before finding a `\n`, though the more novel and higher-value impact here — matching the CVE's classification — is the confidentiality leak of adjacent heap bytes into consumer-visible output.

### Likelihood Explanation
Likelihood is moderate: it requires (1) the target to build using `ijar` with `--nostrip_jar` and a `--target_label` argument against a jar whose manifest is attacker-influenced (e.g. a fetched Maven jar, generated srcjar, or third-party archive used as a Java dependency), and (2) the manifest to be crafted so its last line has no trailing newline at exactly the declared entry size. Both conditions are fully controllable by whoever publishes the JAR (dependency author/malicious mirror/registry), and a sha256/lockfile pin on the archive as a whole does not prevent this — the pinned hash only guarantees the bytes are exactly what the attacker chose, and the attacker chooses precisely this byte layout.

### Recommendation
Bound all manifest line-scanning to `data_end`: replace `strchr(line_start, '\n')` (unbounded) with a bounded search, e.g. `static_cast<const char*>(memchr(line_start, '\n', data_end - line_start))`, in both `IsMultiRelease` and `AppendTargetLabelToManifest`, and clamp any computed `line_end`/`len` to never exceed `data_end`. Additionally, explicitly reject/handle the case where a manifest entry's uncompressed data does not end with a newline, rather than relying on scanning into unallocated memory.

### Proof of Concept
1. Build a JAR whose `META-INF/MANIFEST.MF` entry's uncompressed data is exactly `N` bytes and its last line has no trailing `\n` character within those `N` bytes (e.g. `"Manifest-Version: 1.0"` with no terminating newline, sized so the entry ends mid-content).
2. Invoke `ijar --nostrip_jar --target_label //some:label input.jar output.jar` (the `JarCopierProcessor::WriteManifest` path exercising `AppendTargetLabelToManifest`, at [4](#0-3) ).
3. Under ASan/Valgrind, observe a heap-buffer-overflow read reported at the `strchr` call in `AppendTargetLabelToManifest` ( [5](#0-4) ) and inspect `output.jar`'s `META-INF/MANIFEST.MF` to confirm it contains bytes beyond the original manifest content (i.e., leaked adjacent heap bytes) instead of terminating cleanly at the intended manifest boundary.

static bool IsMultiRelease(u1* manifest_data, size_t manifest_size) {
  static const char* enabled_line = "Multi-Release: true";
  static const size_t enabled_length = strlen(enabled_line);
  const char* line_start = (const char*)manifest_data;
  const char* data_end = (const char*)manifest_data + manifest_size;
  while (line_start < data_end) {
    const char* line_end = strchr(line_start, '\n');
    line_end = line_end != nullptr ? line_end + 1 : data_end;
    size_t line_length = line_end - line_start;

    if (line_length >= enabled_length &&
        strncmp(line_start, enabled_line, enabled_length) == 0 &&
        (line_length == enabled_length || line_start[enabled_length] == '\r' ||
         line_start[enabled_length] == '\n')) {
      return true;
    }
    line_start = line_end;
  }
  return false;
}

u1 *JarCopierProcessor::AppendTargetLabelToManifest(
    u1 *buf, const u1 *manifest_data, const size_t size,
    const char *target_label, const char *injecting_rule_kind) {
  const char *line_start = (const char *)manifest_data;
  const char *data_end = (const char *)manifest_data + size;

  // Write main attributes part
  while (line_start < data_end && line_start[0] != '\r' &&
         line_start[0] != '\n') {
    const char *line_end = strchr(line_start, '\n');
    // Go past return char to point to next line, or to end of data buffer
    line_end = line_end != nullptr ? line_end + 1 : data_end;

    // Copy line unless it's Target-Label/Injecting-Rule-Kind and we're writing
    // that ourselves
    if (strncmp(line_start, TARGET_LABEL_KEY, TARGET_LABEL_KEY_LENGTH) != 0 &&
        strncmp(line_start, INJECTING_RULE_KIND_KEY,
                INJECTING_RULE_KIND_KEY_LENGTH) != 0) {
      size_t len = line_end - line_start;
      memcpy(buf, line_start, len);
      buf += len;
    }
    line_start = line_end;
  }
