Audit Report

## Title
`claim_swap` deletes `PendingSwaps` entry even when the underlying transfer fails, permanently freezing the source's reserved funds - (File: substrate/frame/atomic-swap/src/lib.rs)

## Summary
`claim_swap` calls `swap.action.claim(&swap.source, &target)`, which for `BalanceSwapAction` invokes `C::repatriate_reserved(...)` and discards the `DispatchResult` into a `bool` (`succeeded`) [1](#0-0) . Regardless of that outcome, `claim_swap` unconditionally removes the `PendingSwaps` entry and returns `Ok(())` [2](#0-1) , and since `cancel_swap` requires that same entry to still exist [3](#0-2) , a failed claim permanently strands the source's reserved balance with no on-chain path to unreserve it.

## Finding Description
`repatriate_reserved` is documented as: "beneficiary must exist for this to succeed. If it does not, `Err` will be returned" [4](#0-3) . Note that a *partial* shortfall on the `slashed` (source) side is explicitly documented to still return `Ok(non_zero)` rather than `Err` ("As much funds up to `value` will be deducted as possible... If this is less than `value`, then `Ok(non_zero)` will be returned") [5](#0-4) , so the "source reserve balance reduced by unrelated slashing" scenario in the claim's PoC would likely still return `Ok`, not `Err`. However, the beneficiary-non-existence failure mode is real and directly reachable: if `target`'s account does not exist (e.g., has never received a deposit meeting the existential deposit, or was reaped), `repatriate_reserved` returns `Err`, `claim` returns `false`, yet `claim_swap` still unconditionally deletes `PendingSwaps::<T>` and emits `SwapClaimed { success: false }` without reverting or preserving the entry [2](#0-1) . After this point, `cancel_swap` can never succeed because it requires `PendingSwaps::<T>::get(&target, hashed_proof)` to return `Some`, failing with `Error::NotExist` otherwise [3](#0-2) . The source's originally-reserved balance (locked via `action.reserve(&source)` in `create_swap`) [6](#0-5)  is never unreserved by any other code path in this pallet, since `unreserve` is only invoked from `cancel_swap`'s `swap.action.cancel(&swap.source)` [7](#0-6) .

## Impact Explanation
This is a genuine permanent user-fund lock reachable via the unprivileged `target` calling the public `claim_swap` extrinsic (or simply by the `target` account never being funded before the claim attempt). The `source`'s reserved balance becomes permanently stuck with no cancellation path once `PendingSwaps` is deleted on a failed claim, matching the "permanent user-fund lock" impact category.

## Likelihood Explanation
The most reliable trigger — `target` account non-existence causing `repatriate_reserved` to fail — is fully within an unprivileged attacker's control: a malicious or simply careless `target` can create a swap request and then call `claim_swap` before ever funding their own account to the existential deposit, or the target account could be reaped between `create_swap` and `claim_swap`. This requires no privileged access, no relayer/prover trust assumption, and is straightforward to reproduce deterministically (unlike the "reserved balance shortfall" scenario in the original claim's PoC, which the `Ok(non_zero)` partial-transfer semantics likely rule out).

## Recommendation
`claim_swap` should not unconditionally remove `PendingSwaps` on a failed claim. Either: (a) only remove the entry and emit `success: true` when `swap.action.claim(...)` actually succeeds, leaving the entry intact on failure so `source` can later call `cancel_swap` after `end_block`; or (b) change `SwapAction::claim` to return `DispatchResult` and propagate the error with `?`, aborting the extrinsic without mutating storage. This preserves the source's ability to recover reserved funds via the existing `cancel_swap` path.

## Proof of Concept
1. `source` calls `create_swap(target, hashed_proof, BalanceSwapAction::new(value), duration)`, reserving `value` from `source` via `action.reserve(&source)`.
2. `target`'s account is not funded (below existential deposit / does not exist in `frame_system::Account`), or is otherwise reaped before claiming.
3. `target` calls `claim_swap(proof, action)` with the correct proof/action; `swap.action.claim(...)` invokes `repatriate_reserved(source, target, value, BalanceStatus::Free)`, which returns `Err` because the beneficiary does not exist, so `claim` returns `false`.
4. Despite `succeeded == false`, `claim_swap` still calls `PendingSwaps::<T>::remove(target.clone(), hashed_proof)` and returns `Ok(())`, emitting `SwapClaimed { success: false }`.
5. `source` calls `cancel_swap(target, hashed_proof)`; it returns `Error::NotExist` because the entry no longer exists, leaving `source`'s reserved `value` permanently locked with no further on-chain recovery mechanism in this pallet.
