### Title
Unbounded Reference Updates in `UpdateReferences` RPC Causes Resource Exhaustion (DoS) - ([File: internal/gitaly/service/ref/update_references.go])

### Summary
The `UpdateReferences` RPC is a bidirectional-streaming handler that queues an unbounded number of reference updates from client-controlled input before ever calling `Commit()`. There is no limit on the number of `Updates` per message nor on the total number of streamed messages/updates accumulated in a single transaction, analogous to the reported "iterate over an unbounded number of user positions" gas-limit issue: a caller who submits an extremely large number of ref updates can force the handler (and the underlying `git-update-ref --stdin` process it drives) to do unbounded work within one request/transaction.

### Finding Description
`UpdateReferences` receives an initial request, validates the repository once, and then loops over `server.Recv()` for subsequent messages [1](#0-0) . For every message it iterates `request.GetUpdates()` with no upper bound check on `len(request.GetUpdates())`, validating each reference/OID and immediately queueing it into the `updateref.Updater` via `updater.Update(...)` [2](#0-1) . The loop `for { ... request, err = server.Recv() ...}` [3](#0-2)  continues to accept additional streamed messages and queue more updates with no cap on the cumulative count, and only calls `updater.Commit()` after `io.EOF` is received (outside the shown snippet's loop body), meaning the server-side `git update-ref --stdin` process accumulates the entire (attacker-controlled) command stream in memory/pipe before finishing.

The `updateref.Updater` itself enforces no maximum queue size either: `Update()` simply writes another `update ...\x00` command to the underlying git process's stdin pipe every time it's called [4](#0-3) , and `New()` sets up the wrapped `git-update-ref` process without any resource/entry-count limiting option [5](#0-4) . A grep across the codebase for a maximum-update-count guard (`MaxUpdates`, "too many updates", etc.) found no such enforcement in the ref service or transaction manager path that would bound this specific RPC.

This mirrors the reported bug class: like `mergePositions`/`harvestAllPositions` iterating over unbounded user-supplied position counts until hitting the gas limit, `UpdateReferences` iterates over an unbounded, client-controlled stream of ref updates within a single gRPC call/transaction, with no batching or count limit imposed by the server.

### Impact Explanation
Any authenticated caller able to invoke `UpdateReferences` (used internally for git push / ref update flows) can submit a very large number of update entries — either many entries per message (bounded only by gRPC max message size) repeated across many streamed messages, or simply a very long stream of small messages — forcing Gitaly to hold the reference transaction open, write an ever-growing command stream to `git-update-ref`, and consume server memory/CPU/time proportional to the number of updates before it ever commits or aborts. This can degrade or exhaust resources on the Gitaly node handling the RPC (goroutine/pipe buffering, command buffer growth, transaction lock hold time), which is a denial-of-service risk against the reference-update handler; it does not require any escalated privileges beyond normal push/write access.

### Likelihood Explanation
Likelihood is limited by the fact that a client must be authorized to call the write RPC (this is not a MITM/unauthenticated pathway) and by the practical throughput of legitimate write/push clients, so this is a lower-severity, DoS-class issue rather than an escape/bypass. However, no explicit server-side guard exists to reject an unreasonably large batch, so exploitation only requires crafting a large streamed request, which is straightforward for any client with call access to `RefService`.

### Recommendation
Add an explicit maximum on the number of updates accepted per `UpdateReferences` transaction (counting across all streamed messages, not just per-message), rejecting the RPC with `InvalidArgument`/`ResourceExhausted` once the limit is exceeded, similar to limits already present elsewhere (e.g., `FindRefsByOIDRequest.limit`, `ListBlobsRequest.limit`). Consider also bounding total transaction duration/queue size in `updateref.Updater` itself so any caller of the updater package benefits from the guard rail, not only this one RPC.

### Proof of Concept
Not exploitable via static analysis alone without a running Gitaly instance to time/measure resource consumption; conceptually: a client opens the bidirectional `UpdateReferences` stream, sends the initial `Repository`-bearing request, then sends a very large number of subsequent messages each containing many `UpdateReferencesRequest.Updates` entries (each with a distinct valid/near-valid reference name and object IDs) without ever completing the stream promptly, causing the server-side loop and the spawned `git-update-ref --stdin` process to accumulate an unbounded backlog of pending updates before `Commit()`/`EOF` is processed. Direct confirmation of resource-exhaustion magnitude would require running Devin against the live repo to instrument and measure the actual RPC handler under load.

func (s *server) UpdateReferences(server gitalypb.RefService_UpdateReferencesServer) error {
	ctx := server.Context()

	request, err := server.Recv()
	if err != nil {
		return fmt.Errorf("receiving initial request: %w", err)
	}

	if err := s.locator.ValidateRepository(ctx, request.GetRepository()); err != nil {
		return err
	}
	repo := s.localRepoFactory.Build(request.GetRepository())

	objectHash, err := repo.ObjectHash(ctx)
	if err != nil {
		return fmt.Errorf("detecting object hash: %w", err)
	}

	// Unset the repository so that we can more easily verify inside of the loop that all incoming requests
	// ain't got a repository set anymore.
	request.Repository = nil

	updater, err := updateref.New(ctx, repo)
	if err != nil {
		return fmt.Errorf("creating updater: %w", err)
	}

	if err := updater.Start(); err != nil {
		return fmt.Errorf("starting updater: %w", err)
	}

	for {
		// Only the first request may have its repository set.
		if request.GetRepository() != nil {
			return structerr.NewInvalidArgument("repository set in subsequent request")
		}

		if len(request.GetUpdates()) == 0 {
			return structerr.NewInvalidArgument("no updates specified")
		}

		for _, update := range request.GetUpdates() {
			reference := string(update.GetReference())
			if err := git.ValidateReference(reference); err != nil {
				return structerr.NewInvalidArgument("validating reference: %w", err).
					WithMetadata("reference", reference).
					WithDetail(&gitalypb.UpdateReferencesError{
						Error: &gitalypb.UpdateReferencesError_InvalidFormat{
							InvalidFormat: &gitalypb.InvalidRefFormatError{
								Refs: [][]byte{[]byte(reference)},
							},
						},
					})
			}

			// The old object ID may be empty, in which case we don't care about the current value of the
			// reference but instead do a force update of it.
			oldObjectID := string(update.GetOldObjectId())
			if len(oldObjectID) > 0 {
				if err := objectHash.ValidateHex(oldObjectID); err != nil {
					return structerr.NewInvalidArgument("validating old object ID: %w", err).WithMetadata("old_object_id", oldObjectID)
				}
			}

			newObjectID := string(update.GetNewObjectId())
			if err := objectHash.ValidateHex(newObjectID); err != nil {
				return structerr.NewInvalidArgument("validating new object ID: %w", err).WithMetadata("new_object_id", newObjectID)
			}

			if err := updater.Update(git.ReferenceName(reference), git.ObjectID(newObjectID), git.ObjectID(oldObjectID)); err != nil {
				return structerr.NewInvalidArgument("queueing update: %w", err)
			}
		}

		if request, err = server.Recv(); err != nil {
			if errors.Is(err, io.EOF) {
				break
			}

			return fmt.Errorf("receiving subsequent request: %w", err)
		}
	}

func New(ctx context.Context, repo gitcmd.RepositoryExecutor, opts ...UpdaterOpt) (*Updater, error) {
	var cfg updaterConfig
	for _, opt := range opts {
		opt(&cfg)
	}

	objectHash, err := repo.ObjectHash(ctx)
	if err != nil {
		return nil, fmt.Errorf("detecting object hash: %w", err)
	}

	txOption := gitcmd.WithRefTxHook(objectHash, repo)
	if cfg.disableTransactions {
		txOption = gitcmd.WithDisabledHooks()
	}

	cmdFlags := []gitcmd.Option{gitcmd.Flag{Name: "-z"}, gitcmd.Flag{Name: "--stdin"}}
	if cfg.noDeref {
		cmdFlags = append(cmdFlags, gitcmd.Flag{Name: "--no-deref"})
	}

	var stderr bytes.Buffer
	cmd, err := repo.Exec(ctx,
		gitcmd.Command{
			Name:  "update-ref",
			Flags: cmdFlags,
		},
		txOption,
		gitcmd.WithSetupStdin(),
		gitcmd.WithSetupStdout(),
		gitcmd.WithStderr(&stderr),
	)
	if err != nil {
		return nil, err
	}

	referenceBackend, err := repo.ReferenceBackend(ctx)
	if err != nil {
		return nil, fmt.Errorf("detecting reference backend: %w", err)
	}

	return &Updater{
		repo:             repo,
		cmd:              cmd,
		stderr:           &stderr,
		stdout:           bufio.NewReader(cmd),
		objectHash:       objectHash,
		referenceBackend: referenceBackend,
		state:            stateIdle,
		ctx:              ctx,
	}, nil
}

func (u *Updater) Update(reference git.ReferenceName, newOID, oldOID git.ObjectID) error {
	if err := u.expectState(stateStarted); err != nil {
		return err
	}

	return u.write("update %s\x00%s\x00%s\x00", reference.String(), newOID, oldOID)
}
