### Title
Argument Injection via Unvalidated Registry-Supplied `remote` URL in `git_repository`'s `git remote add` Invocation - ([File: tools/build_defs/repo/git_worker.bzl])

### Summary
### Finding Description
The `source.json` schema for a Bazel module registry allows a module version to declare `"type": "git_repository"`, in which case the `remote` field is "directly forwarded to the underlying `git_repository` repo rule" [1](#0-0) . This value flows unmodified into `git_repo.remote = str(ctx.attr.remote)` [2](#0-1)  and is then spliced directly into a `git` invocation:

```
def add_origin(ctx, git_repo, remote):
    _git(ctx, git_repo, "remote", "add", "origin", remote)
``` [3](#0-2) 

`_git` executes this as an argv list (`ctx.execute(["git", "remote", "add", "origin", remote])`) with no validation that `remote` is a well-formed URL and, critically, no check that it does not begin with `-` [4](#0-3) . Because Bazel passes `remote` as its own argv element (not through a shell), a value such as `--upload-pack=/bin/sh -c ...` or an `ext::`/`-oProxyCommand=` style value that `git`/`ssh` treat specially would be interpreted by `git remote add` (and subsequently by `git fetch origin`, which reuses the configured remote URL) as an option rather than as opaque data — the classic "argument/option injection via unvalidated URL passed to an external program" bug class exemplified by CVE-2017-17526 (`BROWSER` env var launched with unsanitized URL) and by well-known git URL-argument-injection CVEs (e.g., CVE-2017-1000117).

### Impact Explanation
A registry entry is attacker-controllable content in the threat model given: an untrusted or compromised third-party/mirror registry (added via `--registry`) or a compromised BCR mirror could serve a `source.json` with `type: git_repository` and a hostile `remote` value. Unlike the `archive` source type, which is protected by a declared `integrity` hash on the downloaded artifact, the `git_repository` source type has **no integrity/hash binding on the `remote` string itself** — only `commit` pins content once cloned, and there is no check that `remote` cannot start with `-`. This means the invariant "untrusted content stays data, never becomes command syntax" is broken specifically for the `remote` field of `git_repository`-typed registry sources.

### Likelihood Explanation
Exploitation requires a victim to configure a `--registry` pointing at, or fall back to, a registry controlled or compromised by the attacker, and for a resolved module to use `type: git_repository`. This is a narrower attack surface than the default archive/BCR path (which is checksum protected), but it is fully reachable through documented, supported registry configuration, without any trusted root-repo code changes and without requiring MITM or local machine access — the registry response itself is the "hostile origin server" scenario explicitly permitted by the analysis rules.

### Recommendation
Reject `remote` values for `git_repository`/module-registry `git_repository` sources that begin with `-` (or otherwise look like flags) before passing them to `git`, and/or insert a `--` separator immediately before positional URL/remote arguments in every `git` invocation built in `tools/build_defs/repo/git_worker.bzl` (`add_origin`, and any other place a registry- or attribute-supplied string is passed as a positional git argument) to guarantee it can never be parsed as an option by the `git` CLI.

### Proof of Concept
A concrete reproduction cannot be fully certified from the indexed code alone: I was able to confirm the data flow (registry `source.json` → `git_repository.remote` attribute → `git_worker.bzl`'s `add_origin`/`_git` → raw `ctx.execute` argv) [5](#0-4) , but I could not verify from the available index whether any later validation (e.g., in `RegistryFunction`, `ArchiveRepoSpecBuilder`, or Java-side module resolution code) rejects flag-like `remote` values before they reach Starlark, since no Java source matching `"git_repository"` was found in the index (the module/registry-parsing Java classes were not resolvable via search, likely due to indexing coverage limits). A test harness for constructing a git-repo-backed registry module already exists at `src/test/py/bazel/bzlmod/test_utils.py:createGitRepoModule` [6](#0-5) , which could be adapted (setting `remote` to a string beginning with `-`) to build a reproducible `BuildIntegrationTestCase`/shell test that asserts whether Bazel rejects the value or passes it straight into `git remote add`.

**Caveat**: Given the index size limits noted in these instructions, I was unable to confirm whether Java-side module/registry validation (outside the `.bzl` files) already sanitizes the `remote` field before it reaches `git_worker.bzl`. I recommend starting a full Devin session with complete repository access to trace `RegistryFunction`/`ArchiveRepoSpecBuilder`/`ModuleFileFunction` (Java sources) end-to-end and to write and run the JUnit/shell proof-of-concept confirming or refuting exploitability before treating this as a confirmed, unmitigated vulnerability.

def init(ctx, git_repo):
    cl = ["git", "init", str(git_repo.directory)]
    st = ctx.execute(cl, environment = ctx.os.environ | _GIT_LOCAL_ENV_VARS)
    if st.return_code != 0:
        _error(ctx.name, cl, st.stderr)

def add_origin(ctx, git_repo, remote):
    _git(ctx, git_repo, "remote", "add", "origin", remote)

def fetch(ctx, git_repo):
    args = ["fetch", "origin"]

    sparse_checkout_patterns_or_file = \
        getattr(ctx.attr, "sparse_checkout_patterns", None) or \
        getattr(ctx.attr, "sparse_checkout_file", None)
    if sparse_checkout_patterns_or_file:
        if _git_sparse_checkout_config(ctx, git_repo):
            # Use filter to disable downloading file contents until we set the `sparse-checkout` patterns.
            args.append("--filter=blob:none")
        else:
            print("WARNING: Sparse checkout is not supported. Doing a full checkout.")
            sparse_checkout_patterns_or_file = None

    args.extend(["--", git_repo.fetch_ref])
    st = _git_maybe_shallow(ctx, git_repo, *args)

    if sparse_checkout_patterns_or_file:
        _git_sparse_checkout(ctx, git_repo, sparse_checkout_patterns_or_file)

    if st.return_code == 0:
        return
    if ctx.attr.commit:
        # Perhaps uploadpack.allowReachableSHA1InWant or similar is not enabled on the server;
        # fall back to fetching all branches, tags, and history.
        # The semantics of --tags flag of git-fetch have changed in Git 1.9, from 1.9 it means
        # "everything that is already specified and all tags"; before 1.9, it used to mean
        # "ignore what is specified and fetch all tags".
        # The arguments below work correctly for both before 1.9 and after 1.9,
        # as we directly specify the list of references to fetch.
        _report_progress(ctx, git_repo, shallow_failed = True)
        _git(
            ctx,
            git_repo,
            "fetch",
            "origin",
            "--",
            "refs/heads/*:refs/remotes/origin/*",
            "refs/tags/*:refs/tags/*",
        )
    else:
        _error(ctx.name, ["git"] + args, st.stderr)

def reset(ctx, git_repo):
    _git(ctx, git_repo, "reset", "--hard", git_repo.reset_ref)

def clean(ctx, git_repo):
    _git(ctx, git_repo, "clean", "-xdf")

def update_submodules(ctx, git_repo, recursive = False):
    if recursive:
        # "protocol.file.allow=always" allows the submodule command clone from a local directory.
        # It's necessary for Git 2.38.1 and assoicated backport versions.
        # See https://github.com/bazelbuild/bazel/issues/17040
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--recursive", "--checkout", "--force")
    else:
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--checkout", "--force")

def _get_head_commit(ctx, git_repo):
    return _git(ctx, git_repo, "log", "-n", "1", "--pretty=format:%H")

def _get_head_date(ctx, git_repo):
    return _git(ctx, git_repo, "log", "-n", "1", "--pretty=format:%cd", "--date=raw")

def _git(ctx, git_repo, command, *args):
    start = [command]
    st = _execute(ctx, git_repo, start + list(args))
    if st.return_code != 0:
        _error(ctx.name, ["git"] + start + list(args), st.stderr)
