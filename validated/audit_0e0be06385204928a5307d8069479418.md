## Title
Double-Precision Truncation in Legacy Vote-Reward Calculation Causes Miscalculated Reward Payouts - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

## Summary
The legacy (pre-`newRewardAlgorithmEffectiveCycle`) vote-reward computation path in `MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)` uses `double` arithmetic (`voteRate = (double) userVote / totalVote; reward += voteRate * totalReward;`) instead of exact integer/BigInteger math, mirroring the same class of precision-loss bug flagged in the external report (division causing truncated/miscalculated distributed amounts).

## Finding Description
`MortgageService.computeReward` for the "old" reward algorithm computes each voter's share of a witness's cycle reward with double-precision floating point: [1](#0-0) 

Specifically:
```
double voteRate = (double) userVote / totalVote;
reward += voteRate * totalReward;
```
This is functionally analogous to the reported `computeCvgExpected` bug: an integer quantity (`userVote`/`totalVote` ratio) is coerced through a lossy floating-point division before being multiplied by another integer (`totalReward`), truncating precision and producing results that differ from the mathematically exact `userVote * totalReward / totalVote` computation that BigInteger-based paths elsewhere in the codebase use (e.g. `computeReward(long beginCycle, long endCycle, ...)` for the new algorithm uses exact `BigInteger` multiply/divide with `DECIMAL_OF_VI_REWARD`): [2](#0-1) 

This legacy path is reached whenever `beginCycle < newRewardCalStartCycle`, via `getOldReward`, which is called from the exact-math `computeReward(beginCycle, endCycle, accountCapsule)` used during `withdrawReward`/`queryReward`: [3](#0-2) 

`withdrawReward` is directly invoked by any unprivileged account via a signed `WithdrawBalanceContract` transaction, processed by `WithdrawBalanceActuator.execute`: [4](#0-3) 

Because `voteRate` is a `double` with only ~15-17 significant decimal digits, for large `totalVote`/`totalReward` values (TRX vote counts and rewards can be in the trillions of sun) the multiplication `voteRate * totalReward` loses precision compared to the exact integer computation `userVote * totalReward / totalVote`. This affects every legacy-cycle reward computed before the new reward algorithm cutoff, both for `queryReward` (read path) and `withdrawReward` (state-mutating path that credits the miscalculated amount to `accountCapsule.setAllowance`/balance via `adjustAllowance`).

## Impact Explanation
Because the double-based computation can round differently from the exact value, an attacker who controls or influences `userVote`/`totalVote`/`totalReward` ratios (e.g. by structuring vote amounts) could cause a witness/voter to be credited a slightly different (potentially larger) reward amount than the protocol-exact entitlement across the sum of many cycles/witnesses, resulting in an unbacked-balance discrepancy credited to `accountCapsule.getAllowance()` and ultimately paid out as TRX balance through `WithdrawBalanceActuator.execute`. This is a fund-accounting integrity issue: aggregate rewards paid across all voters for a witness's cycle may not sum exactly to the reward pool, allowing systematic account of over/under crediting of TRX (an unbacked-balance/fund-integrity violation) each time old-cycle rewards are withdrawn.

## Likelihood Explanation
The vulnerable code path (`getOldReward` → `computeReward(cycle, votes)`) is only exercised for cycles prior to `newRewardAlgorithmEffectiveCycle`, so it applies to historical cycles rather than newly-created ones on chains where the new algorithm has already taken effect network-wide. However, any account with outstanding unwithdrawn rewards from old cycles remains able to trigger this path today by calling `withdrawReward`/`queryReward`, which is reachable from a simple signed `WithdrawBalanceContract` transaction — no special privilege required. The magnitude of the discrepancy per call is small (bounded by double rounding error, generally negligible for typical vote/reward magnitudes) but is deterministic and reachable at will.

## Recommendation
Replace the double-based ratio computation in `MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)` with exact `BigInteger` arithmetic, consistent with the pattern already used in the new-algorithm path (`BigInteger.valueOf(userVote).multiply(BigInteger.valueOf(totalReward)).divide(BigInteger.valueOf(totalVote))`), eliminating the floating-point round-trip entirely.

## Proof of Concept
Not independently reproduced in this analysis (no execution environment available); the precision-loss pattern is demonstrated purely by static comparison against the exact BigInteger computation used in the sibling (new-algorithm) code path in the same file: for large `userVote`/`totalVote`/`totalReward` values that exceed the ~2^53 safe-integer range for doubles, `(double) userVote / totalVote * totalReward` diverges from `BigInteger.valueOf(userVote).multiply(BigInteger.valueOf(totalReward)).divide(BigInteger.valueOf(totalVote))`, analogous to the PoC pattern in the original report showing `computeCvgExpectedUInt` returning identical results for differing inputs due to truncating division.

      }

      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
