Based on my investigation, I found a directly analogous bug pattern to the CVE: an internal "unset/sentinel" value is returned from a getter without being validated by the caller, and is then used in reward arithmetic — but `MortgageService.computeReward(cycle, votes)` correctly checks the sentinel while `RewardViCalService.accumulateWitnessVi` does not, in the vote-reward/delegation path reachable from any voter's `withdrawReward()`/`queryReward()` calls.

### Title
Missing REMARK sentinel check in RewardViCalService.accumulateWitnessVi causes reward miscalculation - (File: chainbase/src/main/java/org/tron/core/service/RewardViCalService.java)

### Summary
`DelegationStore` uses `REMARK = -1L` as a sentinel meaning "no vote count recorded for this witness/cycle" [1](#0-0) . Every consumer of `getWitnessVote()` is expected to special-case this sentinel before doing arithmetic with it, exactly like `DelegationStore.accumulateWitnessVi()` and `MortgageService.computeReward()` do (`if (totalVote == DelegationStore.REMARK || totalVote == 0) continue;`) [2](#0-1) [3](#0-2) . However, `RewardViCalService` — the batch "vote income" (VI) pre-computation service that seeds the `reward-vi` merkle-rooted store used by the new reward algorithm — has its own private duplicate `getWitnessVote()` that returns the same `REMARK` sentinel but the caller `accumulateWitnessVi()` only checks for `voteCount == 0`, not `voteCount == REMARK (-1)` [4](#0-3) [5](#0-4) .

### Finding Description
This mirrors the CVE-2023-52832 bug class: a getter returns an internal "unset" sentinel value, and a downstream consumer performs arithmetic on it without validating for that sentinel first, producing corrupted results.

In `RewardViCalService.accumulateWitnessVi(cycle, address)`:
```
long voteCount = getWitnessVote(cycle, address);   // may be -1 (REMARK, "no data")
long reward = getReward(cycle, address);
if (reward == 0 || voteCount == 0) { ... }
else {
  BigInteger deltaVi = BigInteger.valueOf(reward)
      .multiply(DECIMAL_OF_VI_REWARD)
      .divide(BigInteger.valueOf(voteCount));   // divide by -1 when voteCount == REMARK
  setWitnessVi(cycle, address, preVi.add(deltaVi));
}
``` [4](#0-3) 

If a witness earned a nonzero block/transaction-fee reward in a cycle (`getReward` > 0, sourced from `DelegationStore.addReward`) but no `setWitnessVote` was ever recorded for that specific cycle/address pair (`getWitnessVote` falls through to `REMARK = -1`), the division uses `-1` as the denominator instead of skipping the cycle. This produces `deltaVi = -(reward * 10^18)`, a large **negative** delta that is added into the cumulative per-witness "vote income" (`Vi`) value stored in `rewardViStore` and included in the merkle root `reward-vi` [6](#0-5) . This `Vi` accumulator is later used in `getNewRewardAlgorithmReward()` for all voters of that witness: `reward += deltaVi.multiply(userVote).divide(DECIMAL_OF_VI_REWARD)` [7](#0-6) , so a single corrupted negative `Vi` entry permanently poisons reward computation for every account that voted for that witness across the entire pre-computed reward-VI table (a one-time batch computed at `newRewardCalStartCycle` and never recomputed, gated by `isDone()`/`IS_DONE_KEY`) [8](#0-7) .

### Impact Explanation
Any account that voted for the affected super representative and later calls `withdrawReward()`/`queryReward()` (reachable via the standard `WithdrawBalanceContract`/wallet reward APIs, ultimately through `MortgageService` -> `RewardViCalService.getNewRewardAlgorithmReward`) can receive an incorrectly negative or drastically reduced reward delta, causing either permanent loss of legitimately earned rewards for affected voters, or (depending on sign propagation across cycles once accumulated into `preVi.add(deltaVi)`) an incorrect balance credited on withdrawal. Because the corrupted `Vi` value is baked into a merkle-rooted store checked against a hardcoded `MAIN_NET_ROOT_HEX` at startup, any divergence would also produce a "Merkle root mismatch" warning, indicating consensus-relevant data corruption in reward state that every full node computes deterministically at startup [9](#0-8) .

### Likelihood Explanation
This is not attacker-controlled in an obvious way (it depends on whether a "reward without recorded vote" state combination can arise for a given cycle/witness under the old reward algorithm's data layout), and I could not fully verify from the available code whether the `reward` key and `vote` key are always written together for the same cycle/address in the pre-`newRewardCalStartCycle` history, or whether there is a legitimate historical scenario (e.g. algorithm/version migrations, brokerage-only cycles) where `reward > 0` while `vote` was never set for that witness in that specific cycle. This uncertainty affects the confidence in real-world reachability of the missing-check path; the code inconsistency itself (this getter and its sibling in `DelegationStore`/`MortgageService` guarding the sentinel identically except here) is confirmed and reproducible in isolation.

### Recommendation
In `RewardViCalService.accumulateWitnessVi()`, mirror the sentinel check already used in `DelegationStore.accumulateWitnessVi()` and `MortgageService.computeReward()`: treat `voteCount == REMARK` (or `<= 0`) the same as `voteCount == 0` before performing the `BigInteger` division, forwarding `preVi` unchanged instead of computing a division by `-1`.

### Proof of Concept
1. In a test/simulation harness for `RewardViCalService`, seed `delegationStore` with a `reward` key for `(cycle, witnessAddress)` set to a positive value (e.g. via `DelegationStore.addReward`), but do not call `setWitnessVote` for that same `(cycle, witnessAddress)`.
2. Invoke the private `accumulateWitnessVi(cycle, witnessAddress)` (via reflection or by driving `startRewardCal()`/`accumulateWitnessReward()`).
3. Observe that `getWitnessVote()` returns `-1` (`REMARK`) [10](#0-9) , which is not caught by the `voteCount == 0` check, so `deltaVi = reward * 10^18 / -1` is computed and stored as a negative `Vi` for that cycle.
4. Call `getNewRewardAlgorithmReward()` for a voter of that witness across a cycle range spanning the corrupted cycle and confirm the returned reward is negative/incorrect compared to the expected non-negative reward.

    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi

          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }
