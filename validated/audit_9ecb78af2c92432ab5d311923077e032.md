### Title
Unsolicited dust `DepositToken` transfers/deposits fill `depositTokensOfAccount` to `MAX_TOKENS_PER_USER`, DoSing deposits and collateral seizures - (File: contracts/Pool.sol)

### Summary
`Pool.addToDepositTokensOfAccount` reverts once an account's combined deposit + debt token list reaches `MAX_TOKENS_PER_USER = 30`. Any `DepositToken` receipt — via `transfer`, `transferFrom`, `deposit(amount_, onBehalfOf_)`, `seize`, or `_mint` — unconditionally calls `pool.addToDepositTokensOfAccount(recipient)` when the recipient's prior balance was zero, with no opt-in or minimum-amount validation. An attacker can force-fill a victim's list with dust positions in every registered deposit token, causing all subsequent additions (new collateral deposits, seized collateral payouts) to revert with `UserReachedMaxTokens`. ### Finding Description
- `DepositToken._transfer` adds the token to the recipient's per-account set whenever `_recipientBalanceBefore == 0 && amount_ > 0` (`contracts/DepositToken.sol:517-520`). There is no minimum amount, no recipient consent, and no way to reject the transfer.
- `deposit(uint256 amount_, address onBehalfOf_)` lets anyone mint deposit tokens to an arbitrary `onBehalfOf_` address (`contracts/DepositToken.sol:211-236`), which also triggers `pool.addToDepositTokensOfAccount` via `_mint` (`contracts/DepositToken.sol:485-488`).
- `Pool.onlyIfAdditionWillNotReachMaxTokens` enforces `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30 → revert UserReachedMaxTokens` (`contracts/Pool.sol:143-148`). The same modifier guards `addToDebtTokensOfAccount`, so a fully-stuffed account also cannot take on a *new* debt token — i.e., cannot open a borrowing position in a synthetic asset it hasn't already borrowed.
- Concretely: attacker deposits a dust amount (e.g., 1 wei) of each underlying via `deposit(1, victim)` — or obtains dust of each msdTOKEN and `transfer`s it to `victim`. After ~30 calls, `victim` cannot deposit into any new collateral token and cannot receive seized collateral in tokens they don't already hold.
- A second-order DoS: if `victim` is a liquidator whose list is stuffed, `Pool.liquidate` → `DepositToken.seize` → `_transfer` → `addToDepositTokensOfAccount` reverts whenever the seized collateral token isn't already in the liquidator's set, blocking that liquidation path (`contracts/DepositToken.sol:343-345`).

### Impact Explanation
- An unprivileged attacker can, for the cost of dust amounts of each underlying, prevent a targeted account from adding any new collateral type or issuing debt in any new synthetic asset. For a victim that needs to add a *different* collateral to restore health (e.g., existing collateral devalued), remediation requires first freeing slots.
- Freeing slots is not always trivially possible: if the victim's position is unhealthy, `unlockedBalanceOf` returns 0 (issuable is 0), so `_revertIfLocked` blocks `transfer`/`withdraw` of the dust positions too — the victim must first repay enough debt to become healthy before it can eject the dust tokens (`contracts/DepositToken.sol:180-182, 383-398`). This constitutes temporary freezing/blocking of position-management operations driven entirely by attacker-pushed state the victim never requested.

### Likelihood Explanation
- Attack cost is low: `MAX_TOKENS_PER_USER` is 30 and the number of registered deposit tokens per pool is well under that, so depositing 1 wei of each underlying (or transferring dust msdTOKENs) fills the list in a handful of transactions on a cheap L2 (Base/Optimism deployments exist).
- No privileged role, oracle manipulation, or timing is needed; `deposit(onBehalfOf_)` and `transfer` are permissionless. The victim cannot prevent receipt.
- Limitation (stated for completeness): a healthy victim can clear the dust by transferring each token out, so the impact is a griefing/temporary DoS rather than permanent freezing; the DoS is most material against unhealthy victims who cannot move the dust while locked.

### Recommendation
- Require a minimum mint/transfer amount before calling `addToDepositTokensOfAccount` (e.g., only register the token when the recipient's resulting balance exceeds a dust threshold), or
- Decouple the per-account accounting set from token receipt — e.g., lazily track collaterals for health checks via the pool's global deposit token list, or cap iteration differently than membership, or
- Allow the account to opt out / forcibly remove entries (a `removeDepositToken` callable by the account holder that sweeps the dust balance to the pool or burns it), or
- Reject `transfer`/`deposit onBehalfOf` when it would exceed the recipient's remaining slot capacity before mutating balances, and let `seize` bypass the cap by auto-evicting zero/dust entries.

```solidity
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {Pool} from "../contracts/Pool.sol";
import {IDepositToken} from "../contracts/interfaces/IDepositToken.sol";
import {IERC20} from "../contracts/dependencies/openzeppelin/token/ERC20/IERC20.sol";

contract MaxTokensGriefingTest is Test {
    // mainnet fork: POOL = deployed Pool proxy; registry of deposit tokens from getDepositTokens()
    Pool pool = Pool(POOL_ADDR);
    address victim = address(0xBEEF);
    address attacker = address(0xA77AC);

    function testDustFillsAccountList() public {
        address[] memory dts = pool.getDepositTokens();
        uint256 max = pool.MAX_TOKENS_PER_USER(); // 30

        // Attacker pushes 1 wei of each deposit token to victim
        for (uint256 i; i < dts.length && i < max; ++i) {
            IDepositToken dt = IDepositToken(dts[i]);
            IERC20 underlying = dt.underlying();
            deal(address(underlying), attacker, 1);
            vm.startPrank(attacker);
            underlying.approve(address(dt), 1);
            dt.deposit(1, victim); // mints dust to victim, adds to depositTokensOfAccount
            vm.stopPrank();
        }
        // Fill remaining slots by self-deposit + transfer of any token
        // ...

        // Victim now cannot deposit into a deposit token it doesn't already hold
        vm.startPrank(victim);
        IERC20 someUnderlying = IDepositToken(dts[0]).underlying();
        // pick a token not in victim's set:
        vm.expectRevert(Pool.UserReachedMaxTokens.selector);
        IDepositToken(newDt).deposit(1e18, victim);
        vm.stopPrank();

        // If victim is unhealthy (debtInUsd > issuableLimit), dust is locked:
        // dt.transfer(attacker, dust) reverts NotEnoughFreeBalance -> cannot clear slots.
    }
}
```

Reproduction steps on a Hardhat mainnet/Base fork:
1. `pool.getDepositTokens()` → list registered collateral tokens.
2. Attacker calls `depositToken.deposit(1, victim)` (or `transfer(victim, 1)`) for each token until `pool.getDepositTokensOfAccount(victim).length == 30`.
3. Any `deposit(..., victim)` into a token not yet in the list, or `liquidate` seizing a new token to a maxed-out liquidator, reverts with `UserReachedMaxTokens`.
4. To show lock-in: give victim an unhealthy debt position (`debtPositionOf` → `_isHealthy == false`), then `depositToken.transfer(out, dust)` from victim reverts with `NotEnoughFreeBalance`, proving the dust cannot be removed until debt is repaid.
