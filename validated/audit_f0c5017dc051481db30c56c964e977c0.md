## Analog Found

### Title
Unbounded `DelegatedResourceAccountIndexCapsule` account lists cause O(n) list scans and O(n) migration writes per flat-fee transaction, mirroring the nonces-array DoS pattern - (File: chainbase/src/main/java/org/tron/core/capsule/DelegatedResourceAccountIndexCapsule.java, chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java, actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java)

### Summary
The reported bug class is an unbounded loop over an attacker-growable array performed inside on-chain transaction validation/execution, whose cost is not covered by a corresponding fee, enabling a gas/DoS attack. The same pattern exists in java-tron's resource-delegation bookkeeping: `DelegatedResourceAccountIndexCapsule.getToAccountsList()`/`getFromAccountsList()` are unbounded lists that grow by one entry per distinct delegatee/delegator address a single account has ever interacted with, and multiple **flat-fee** actuators (`FreezeBalanceActuator`, `UnfreezeBalanceActuator`, `DelegatedResourceAccountIndexStore.convert()`) perform `O(n)` `List.contains()` scans or `O(n)` two-way DB writes over these lists on every invocation.

### Finding Description
`DelegatedResourceAccountIndexCapsule.addToAccount`/`addFromAccount` simply append to a protobuf-backed list with no size cap: [1](#0-0) 

`FreezeBalanceActuator.delegateResource()` (reachable from a plain `FreezeBalanceContract` broadcast by any account) reads the owner's `toAccountsList`, does a linear `contains()` check against it, and appends if absent - each call is `O(n)` in the number of distinct receivers the owner has ever delegated to, and this list has no upper bound: [2](#0-1) 

The actuator's fee is fixed at zero regardless of list size: [3](#0-2) 

Separately, `DelegatedResourceAccountIndexStore.convert(address)` — invoked unconditionally from the same `delegateResource()` path when the "optimization" flag is on — iterates the *entire* legacy `toAccountsList`/`fromAccountsList` and performs two `put()` DB writes per entry: [4](#0-3) 

And `getWithPrefix()` (used by `getIndex()`/`getV2Index()`, reachable via `Wallet`/HTTP-gRPC query paths) performs a full prefix scan plus an `O(n log n)` sort over every entry associated with an address, with no size limit: [5](#0-4) 

Unlike the vote-count (`MAX_VOTE_NUMBER`), signature-count (`getTotalSignNum()`/`keysCount`), and freeze-slot (`frozenCount` 0/1) checks elsewhere in the codebase that explicitly bound similar loops, no equivalent cap was found on the number of distinct delegation counterpart addresses a single account can accumulate in `DelegatedResourceAccountIndexCapsule`.

### Impact Explanation
An attacker can build up an arbitrarily large `toAccountsList`/`fromAccountsList` for their own account by issuing many small `FreezeBalanceContract`/`DelegateResourceContract` transactions to distinct newly-generated receiver addresses (paying only the flat, size-independent actuator fee each time). Once the list is large:
- Every subsequent `FreezeBalanceContract`/`UnfreezeBalanceContract`/delegate/undelegate transaction involving that account triggers an `O(n)` `contains()` scan (and, via `convert()`, an `O(n)` migration doing `2n` synchronous DB writes) that is executed inline during block application (`Manager.processBlock` → `processTransaction` → actuator `execute()`), for the same flat fee.
- Query paths (`getIndex`/`getV2Index`, exposed through Wallet/HTTP/gRPC) pay an `O(n log n)` cost per request with no fee at all.

This raises node CPU/DB-write cost disproportionately to the fee charged, and because the costly work happens inside consensus-critical block application, a sufficiently large list can materially slow down or stall block processing for all nodes that must re-execute the same transaction, which is the same "gas efficiency / DoS from unbounded growth" class as the original report.

### Likelihood Explanation
Building the list costs the attacker only the (low, flat) `FreezeBalanceContract`/`DelegateResourceContract` fee per new address — no privileged role is required, and any unprivileged account can accumulate thousands of entries over time. The `convert()` migration cost is realized once per account (on first post-hardfork delegation), and the query-path cost (`getIndex`) is unbounded and repeatable by any external API caller without a matching fee, making the read-path degradation moderately likely and cheap to trigger, though the exact severity depends on chain size limits (e.g., `TotalNetWeight`/DB IOPS) I could not fully quantify from the indexed code alone.

### Recommendation
- Cap the number of distinct delegatee/delegator addresses tracked per account in `DelegatedResourceAccountIndexCapsule`, similar to `MAX_VOTE_NUMBER`/`UNFREEZE_MAX_TIMES` limits used elsewhere, and reject `FreezeBalanceContract`/`DelegateResourceContract` transactions in `validate()` once the cap is reached.
- Charge a fee proportional to the current list size (or to the migration cost in `convert()`) instead of a flat fee, or move the list scan to a hashed/indexed lookup (e.g., a `Set`-backed key scheme) to make `contains()` checks O(1) instead of O(n).
- Bound or paginate `getWithPrefix()`/`getIndex()` results returned via query APIs to avoid unbounded server-side sort/scan cost per request.

### Proof of Concept
Not independently executed; based on static code review only. A conceptual PoC:
1. From one funded account, broadcast N `FreezeBalanceContract` (with distinct `receiver_address`) or `DelegateResourceContract` transactions, each delegating a minimal amount to a freshly generated address — this appends N entries to the account's `DelegatedResourceAccountIndexCapsule.toAccountsList` for the flat per-tx fee (see `FreezeBalanceActuatorTest.testMultiFreezeDelegatedBalanceForBandwidth`, which demonstrates the same unbounded list growth pattern for `RECEIVE_COUNT` receivers, without exercising a cap): [6](#0-5) 
2. Repeat until N is large (no validate()-side rejection was found for list size).
3. Issue one more `FreezeBalanceContract`/`DelegateResourceContract` from the same account, or call `getIndex`/`getV2Index` via the Wallet/HTTP/gRPC layer, and observe processing time scale with N due to the `contains()`/`convert()`/sort operations shown above.

I was unable to verify from the index whether `supportAllowDelegateOptimization()`/the new delegate-resource model has already fully replaced the legacy list-based path on the live mainnet (which would reduce, but not eliminate, exposure via `convert()`'s one-time migration cost and the `getWithPrefix()` query path). A Devin session with full repo/runtime access would be needed to confirm current activation state and any size caps that may exist outside the indexed files.

  public void convert(byte[] address) {
    DelegatedResourceAccountIndexCapsule indexCapsule = this.get(address);
    if (indexCapsule == null) {
      // convert complete or have no delegate
      return;
    }
    // convert old data
    List<ByteString> toList = indexCapsule.getToAccountsList();
    for (int i = 0; i < toList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(address, toList.get(i).toByteArray(), i + 1L);
    }

    List<ByteString> fromList = indexCapsule.getFromAccountsList();
    for (int i = 0; i < fromList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(fromList.get(i).toByteArray(), address, i + 1L);
    }
    this.delete(address);
  }

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }
