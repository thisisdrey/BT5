### Title
Accumulate-and-Forward pallet burns funds on XCM *send* success rather than on confirmed remote mint, permanently destroying value if delivery/execution fails - ([File: substrate/frame/accumulate-and-forward/src/lib.rs])

### Summary
This is a structural analog of the reported "hooks may break invariants" bug: `pallet_accumulate_and_forward`'s `on_idle` hook treats a successful call to the pluggable `Forwarder::forward` trait as proof that funds will be minted at the destination, and burns them locally on that basis. The pallet documents the intended invariant as "burnt here == minted there," but the actual guarantee provided by `Forwarder::forward` returning `Ok(())` is only that an XCM message was *sent*, not that it will be *decoded, dispatched, and executed* successfully at the destination. This breaks the cross-chain conservation invariant analogous to `redeemed + total_debt >= minted` in the original report.

### Finding Description
The pallet's own doc comment states the intended invariant explicitly: [1](#0-0) 

The `Forwarder` trait is a pluggable hook whose implementation is opaque to this pallet — exactly like the MainController hooks in the original report: [2](#0-1) 

In `on_idle`, the pallet computes `available_funds` from the accumulation account and calls `T::Forwarder::forward(accumulation_account, available_funds)`. If it returns `Ok(())`, the pallet fires `ForwardSucceeded` and moves on — it never re-checks or re-credits the accumulation account afterward: [3](#0-2) 

The weight budget reserved before calling the forwarder only covers `send_native()` — i.e., constructing and enqueuing the outbound XCM message — not any confirmation of remote execution: [4](#0-3) 

Because `Ok(())` from `forward()` only certifies that the XCM message was successfully handed to the transport layer (e.g. `XcmpQueue`/`DmpQueue`/HRMP channel), and the actual burn of the accumulation account's balance is expected to happen as part of that same `forward()` implementation (per the module doc: "burnt upon forwarding"), there is a window where:
- Funds are burned on the source chain (reducing local `total_issuance`), and
- The corresponding mint at the destination depends on downstream message queue processing that can fail independently: decode failure, execution trap, insufficient weight at destination, barrier/filter rejection, or channel suspension.

This is structurally identical to the reported class of bug: an opaque "hook" (`Forwarder::forward`) is trusted to keep two accounting legs in lockstep (`burn_here == mint_there`), but its `Ok`/`Err` return only reflects the local half of the operation (successful *send*), not the atomic completion of both halves. The pallet has no settlement confirmation, receipt, or reconciliation mechanism to detect and reverse the local burn if the remote mint never happens.

### Impact Explanation
If the destination-side execution of the forwarded XCM message fails after the message was successfully sent (message queue congestion, execution trap, barrier rejection, decode failure, or channel suspension - none of which require a malicious relayer, validator, or collator, just adverse but permissible network/queue conditions), the accumulated funds are burned on the source parachain with no corresponding mint anywhere. This is a permanent, unrecoverable loss of value from the system's aggregate token supply, breaking the "burn here == mint there" conservation invariant that the pallet itself documents as required. This aligns with the "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically" pivot.

### Likelihood Explanation
This runs unconditionally on every system chain that uses `pallet_accumulate_and_forward` (referenced in Asset Hub-style runtimes, Bridge Hub Westend, Coretime, Collectives, People, and the relay chain fee-handling wiring shown in the runtime configs), on every `on_idle` cycle where `available_funds >= MinTransferAmount`. It requires no attacker action — only that a normal, permitted network condition (queue congestion, weight exhaustion at destination, or a transient decode/dispatch failure) causes the forwarded message to not fully execute after having been sent. Because the actual `Forwarder` implementation (which performs the burn-and-send) is not visible/verifiable from this pallet's code, there is no local mechanism enforcing atomicity between "burn" and "confirmed remote mint."

### Recommendation
- Require `Forwarder::forward` (or the pallet itself) to defer the local burn until delivery/execution is confirmed, or
- Implement a receipt/acknowledgment mechanism so that a failed remote execution triggers restoration of the burned amount to the accumulation account (mirroring the `redeemed + total_debt >= minted` style safety check recommended in the source report), and
- Add explicit bounds/verification on what `Forwarder::forward` is allowed to assume as "success," rather than trusting an opaque `Result<(), ()>` from a pluggable hook to imply eventual atomic settlement.

### Proof of Concept
1. Configure a chain with `pallet_accumulate_and_forward` where `Forwarder::forward` burns `amount` from `source` locally and sends an XCM `TransferReserveAsset`/`DepositAsset` (or teleport) message to a destination chain, returning `Ok(())` once the message is successfully enqueued via `send_xcm`.
2. Accumulate fees/dust/coretime revenue in the accumulation account until `available_funds >= MinTransferAmount` (see `on_idle` logic at lines 166-177).
3. At the `TransferPeriod` boundary, `on_idle` calls `forward()`; the implementation burns `available_funds` from the accumulation account and sends the XCM message, returning `Ok(())` — the pallet emits `ForwardSucceeded` at lines 184-188.
4. On the destination side, the message fails to execute (e.g., destination XCMP/DMP queue is congested and drops/traps the message, or the destination-side weight limit is insufficient, or the destination barrier rejects it) — no mint occurs.
5. Result: `total_issuance` decreased on the source chain by `available_funds`, with no compensating mint anywhere in the system — a permanent, unrecoverable value loss, breaking the pallet's own documented "burnt here == minted there" invariant, with no on-chain mechanism to detect or reverse this state.
