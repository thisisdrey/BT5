### No vulnerability found for this question.

**Binding validated:** `TokenId::to_string() ⟺ (variant tag, contract_id, token_id-substring)` is a bijection that the code preserves both for serde (`FromStr`/`Display`) and Borsh paths.

**Why the claimed collision cannot occur:**

1. **Cross-type collision is blocked by the fixed discriminant tag.** `TokenId::from_str` first does `s.split_once(':')` to get `(typ, data)`, and `typ` must parse via `strum::EnumString` into one of the fixed literals `"nep141" | "nep171" | "nep245" | "imt"`. An attacker cannot forge `typ` to be simultaneously `nep141` and `nep245` — the leading tag is a hard-coded, non-attacker-controllable string, so a `Nep141` token string can never equal a `Nep245` token string. [1](#0-0) 

2. **Within-type collision (`Nep245`/`Imt`) is blocked because `AccountId` cannot contain `:`.** `Nep245TokenId::from_str` does `data.split_once(':')`, giving `(contract_id, mt_token_id)` where `contract_id` is parsed via `near_account_id::AccountId`'s validated `FromStr`, which enforces NEAR's account-id charset (lowercase alphanumerics, `-`, `_`, `.` — no colon). Since `contract_id` structurally cannot embed a `:`, the first-colon split always uniquely recovers the same `(contract_id, mt_token_id)` pair used at construction — no two distinct `(contract_id, mt_token_id)` pairs can produce the same string. [2](#0-1) 

3. **`Nep141TokenId` has no delimiter ambiguity at all** — it wraps a single `AccountId` with no secondary string field to inject a delimiter into. [3](#0-2) 

4. **Borsh serialization is even more strongly disjoint** than the string form: it encodes an explicit `#[repr(u8)]` discriminant (`Nep141=0, Nep171=1, Nep245=2, Imt=3`) followed by length-prefixed fields, not concatenated strings, so there is no encoding-level ambiguity whatsoever. The repo's own fixed-vector test confirms distinct discriminant bytes and distinct encodings per type/value. [4](#0-3) 

5. `TokenDiff::diff` deserializes via `Amounts<BTreeMap<_, DisplayFromStr>>`, which calls exactly this `TokenId::FromStr` for each map key before `internal_apply_deltas` is invoked — so any attacker-supplied JSON key must round-trip through the same collision-free parser before it ever reaches balance mutation. [5](#0-4) 

Since the two sides of the claimed equality (the crafted `TokenId` string vs. a distinct real `TokenId`) can never actually be equal under this parser/encoder, the described exploit path (worthless asset's `TokenId` colliding with a valuable asset's `TokenId` to hijack `internal_apply_deltas` balance) is not reachable. `auth_by_predecessor_id` status is irrelevant here since the collision itself is impossible regardless of authorization mode.

    fn from_str(s: &str) -> Result<Self, Self::Err> {
