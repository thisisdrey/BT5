### Title
Unguarded division by `totalEnergyWeight` in `RepositoryImpl.calculateGlobalEnergyLimit()` can throw `ArithmeticException` and halt TVM-dependent operations - ([File: actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java])

### Summary
`RepositoryImpl.calculateGlobalEnergyLimit()`, the TVM-execution-path variant of the energy-limit calculation that a contract account's available energy depends on, relies on the unchecked assumption that `totalEnergyWeight` (a global dynamic property) is always greater than zero. Unlike its sibling implementation in `chainbase/.../EnergyProcessor.calculateGlobalEnergyLimit()`, which explicitly guards this case and returns `0`, the `RepositoryImpl` version only has a Java `assert` (disabled in production by default) before dividing by `totalEnergyWeight`. If that invariant is ever violated, the subsequent `BigInteger` division by zero throws an unhandled `ArithmeticException`, aborting any transaction/TVM execution path that reaches this calculation for the affected account.

### Finding Description
`RepositoryImpl.calculateGlobalEnergyLimit()`: [1](#0-0) 

computes the energy weight and then does:
```java
assert totalEnergyWeight > 0;
if (hardenResourceCalculation()) {
  return BigInteger.valueOf(energyWeight)
      .multiply(BigInteger.valueOf(totalEnergyLimit))
      .divide(BigInteger.valueOf(totalEnergyWeight))
      .longValueExact();
}
return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
```
`assert` statements are stripped/disabled by default in a standard JVM (no `-ea` flag), so this "guard" provides no real protection at runtime. If `totalEnergyWeight` is ever `0`, the `BigInteger.divide(BigInteger.ZERO)` call throws `ArithmeticException: / by zero` (and the legacy double path silently produces `Infinity`/`NaN`, which then breaks the `longValueExact()`/cast semantics differently but is still unsound).

This is the exact analog of the Sherlock report's root cause: an unchecked, hard assumption ("exit balance/weight will never be zero") baked into a value/limit-computation function that other critical operations depend on. Compare with the properly-guarded chainbase equivalent, which explicitly checks and short-circuits to avoid the divide-by-zero: [2](#0-1) 

The vulnerable `RepositoryImpl` method is reachable from the TVM execution path via `ContractState.calculateGlobalEnergyLimit()`: [3](#0-2) 

which in turn is invoked from `Program` opcode processing during a normal, unprivileged smart-contract call (e.g. computing how much energy a contract account can spend/receive). Because `totalEnergyWeight` is a network-wide dynamic property (`DynamicPropertiesStore.getTotalEnergyWeight()`), and there is no protocol-level minimum amount of frozen-for-energy TRX enforced network-wide, it is conceivable — particularly on low-adoption or private/side chains, or transient windows after mass-unfreezing — for this weight to legitimately reach `0`.

### Impact Explanation
If `totalEnergyWeight` becomes `0` while the "harden" resource-calculation code path is active, every TVM call that reaches `RepositoryImpl.calculateGlobalEnergyLimit()` for that computation throws an unhandled `ArithmeticException`, aborting the contract execution/transaction. Since this routine is used to determine energy availability during contract execution (an operation reachable by any account triggering a smart contract), a persistent zero `totalEnergyWeight` state would deny service to all TVM calls relying on this calculation, effectively freezing normal contract interactions network-wide until the invariant is restored (which may not be straightforward once triggered). This matches the "critical view function that other operations depend on can revert due to an unchecked zero-value assumption" bug class from the report, escalated to a node-level denial-of-service on contract execution rather than a single account.

### Likelihood Explanation
Likelihood is moderate-to-low on Mainnet (where `totalEnergyWeight` is large and diversified across many SRs/accounts), but non-trivial on smaller or newly-launched chains, private/consortium deployments, or in edge-case testing/maintenance windows where energy-freezing could transiently reach zero, since no minimum system-wide freeze invariant is enforced at the protocol level (mirroring the report's point about "no minimum position size" enforcement). The disabled-by-default `assert` gives a false sense of protection and does not prevent the divide-by-zero at runtime.

### Recommendation
Add an explicit `totalEnergyWeight <= 0` guard in `RepositoryImpl.calculateGlobalEnergyLimit()` (mirroring the guard already present in `chainbase/.../EnergyProcessor.calculateGlobalEnergyLimit()`) that returns `0` instead of relying on `assert`, and audit other `RepositoryImpl`/VM-repository calculations (e.g. `usageToBalance`, `divideCeilExact`) for the same unguarded-denominator pattern before performing `BigInteger` division.

### Proof of Concept
Not executable in this review context (index-only analysis); the codebase's own test suite already demonstrates the divide-by-zero-adjacent overflow behavior of these hardened calculations (e.g. `CalculateGlobalLimitHardenTest.testGlobalEnergyLimitOverflowDetectedWithHardening` / `RepositoryImplHardenTest.testCalculateGlobalEnergyLimitHardenedOverflowDetected`), confirming that `ArithmeticException` is thrown when the divisor/denominator invariant is violated in this calculation family: [4](#0-3)

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalEnergyLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }

    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
    long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
      return 0;
    } else {
      assert totalEnergyWeight > 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
