### Title
Gas-key nonce reset on delete+re-add at the same block height enables transaction replay - ([File: runtime/runtime/src/access_keys.rs])

### Summary
`add_gas_key` unconditionally reseeds every nonce-index row to `initial_nonce_value(block_height) = (block_height - 1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` with no comparison to previously consumed nonces. When a gas key is deleted and re-added under the *same public key* within the *same block height* (both `action_delete_key`/`action_add_key` use the single shared `apply_state.block_height` for that chunk), the new floor can be far below nonces that were already consumed earlier in that same block's `[block_height-1, block_height) * 1e6` window, making previously-executed gas-key transactions replayable.

### Finding Description
`initial_nonce_value` (`runtime/runtime/src/access_keys.rs:46-50`) computes the seed nonce purely from `block_height`, and `add_gas_key` (`runtime/runtime/src/access_keys.rs:194-228`) writes this seed to every `nonce_index` unconditionally: [1](#0-0) 

`delete_gas_key` (`:93-134`) removes all nonce rows and the access key with no floor tracking preserved. `verify_nonce` (`runtime/runtime/src/verifier.rs:210-237`) only checks `tx_nonce > current_nonce` (Monotonic) and an upper bound `tx_nonce < block_height * ACCESS_KEY_NONCE_RANGE_MULTIPLIER`. The "current_nonce" comes straight from `get_gas_key_nonce` state (`runtime/runtime/src/lib.rs:1937-2153`, `runtime/runtime/src/verifier.rs:912-962`) — there is no mechanism preventing the stored nonce from decreasing.

Because every action in one chunk/block shares a single `apply_state.block_height`, a sequence like: (1) several gas-key transactions at `nonce_index=0` raising the stored nonce close to the block's own ceiling `block_height * 1e6`, followed within the same block by (2) `DeleteKey` then `AddKey` re-adding the same public key as a gas key, causes the nonce to reset to `(block_height-1) * 1e6` — i.e., far *below* nonces already consumed in step (1), since the entire per-block nonce window is only `1e6` wide. Any previously signed and already-executed gas-key transaction whose nonce falls in `[(block_height-1)*1e6, consumed_nonce)` becomes valid again, because `current_nonce` after re-add is lower than it.

This is a regression of the exact protection `ACCESS_KEY_NONCE_RANGE_MULTIPLIER` was introduced for (near/nearcore#3779): that fix relies on the re-creation happening at a *later* block height than any prior consumption, so the new floor is guaranteed above old usage. That invariant silently breaks when delete+re-add of a gas key happens at the *same* block height as the key's own high-water-mark usage, which `add_gas_key`/`delete_gas_key` do nothing to prevent (no check against a previously-recorded high-nonce or a "last used" nonce, no cross-check between delete and add).

### Impact Explanation
This breaks NEAR's protocol-level nonce-based replay protection for gas keys. Any previously executed gas-key transaction (a `Transfer`, a `FunctionCall` invoking a contract action like a one-time claim/mint/vote, etc.) can be re-submitted and re-executed after the delete+re-add sequence, as long as its old nonce still exceeds the freshly reset floor. This is a double-spend/replay of value: gas cost is re-charged against the refunded gas-key balance, and any deposit/effects of the replayed action are re-applied a second time. It matches the "double-spend / replay" bounty category — a chunk/state divergence is not required; the impact is direct double execution of an already-settled transaction.

### Likelihood Explanation
- Preconditions are fully within an ordinary account owner's control: create a `GasKeyFullAccess` key with `num_nonces > 1`, drive `nonce_index=0`'s nonce up near the block's ceiling via several own gas-key transactions, then (in the same block/chunk or via a single receipt's promise batch, which the attacker fully controls and which is guaranteed to share one `apply_state.block_height`) issue `DeleteKey` + `AddKey` for the same public key.
- No validator, node-operator, or privileged access is required — this is achievable purely as a funded account owner submitting normal transactions/receipts, including via a self-deployed contract's promise batch to guarantee same-block/same-receipt ordering.
- Repeatable: the attacker can retry across blocks until timing lines up, or engineer it deterministically via a contract-driven promise batch (`add_key`/`delete_key` actions chained in one receipt execute under one `apply_state.block_height` deterministically).

### Recommendation
When re-adding a gas key (or a regular key) under a public key that previously existed as a gas key with recorded nonces, ensure the new floor is never lower than any nonce that could have been valid/consumed for that key at the current block height. Options: track and persist a monotonic "last-seen nonce ceiling" per `(account_id, public_key)` independent of key deletion (e.g., retain a tombstone value used as `max(initial_nonce_value(block_height), previous_max_nonce)`), or disallow re-adding a public key that was deleted within the same block height/transaction-processing window until a full window has elapsed.

### Proof of Concept
Unit test in `runtime/runtime/src/access_keys.rs`, extending the existing `add_gas_key_to_account`/`test_delete_gas_key` helpers:
1. Call `add_gas_key` at `block_height = H` to create a gas key with `num_nonces >= 1`; record `floor = initial_nonce_value(H) = (H-1)*MULTIPLIER`.
2. Directly call `set_gas_key_nonce` (simulating consumption from several gas-key transactions within block `H`) to set `nonce_index=0`'s nonce to `consumed = H*MULTIPLIER - 10` (near the block's own ceiling, still `< H*MULTIPLIER`).
3. Call `delete_gas_key` for the same public key (balance under `MAX_BALANCE_TO_BURN`).
4. Call `add_gas_key` again for the *same* public key at the *same* `block_height = H`.
5. Read back `get_gas_key_nonce(..., 0)` and assert it equals `floor` again — strictly less than `consumed`.
6. Assert that a nonce value such as `consumed - 1` (which was already validly used/valid before deletion) is still `> floor`, i.e., `verify_nonce` would accept it again as "current_nonce < tx_nonce", demonstrating the previously-consumed nonce range is now replayable.
