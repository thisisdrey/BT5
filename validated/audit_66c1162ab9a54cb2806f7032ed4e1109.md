### Title
Cross-contract StackerDB chunk-signature replay: `SlotMetadata::auth_digest` omits the smart-contract identifier - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` computes the message a signer authorizes over `slot_id`, `slot_version`, and `data_hash` only — it never binds the signature to the specific StackerDB smart-contract (`QualifiedContractIdentifier`) the write is destined for. This mirrors the reported bug class: a role/authorization value that should be scoped to one specific resource is instead shared/reused across a different resource due to a missing distinguishing component, allowing authorization intended for context A to be valid in context B.

### Finding Description
`SlotMetadata::auth_digest()` hashes only `slot_id`, `slot_version`, and `data_hash`: [1](#0-0) 

`SlotMetadata::verify()` recovers the signer's public key from this digest and checks it against the expected `StacksAddress` — again with no notion of *which* StackerDB contract the chunk belongs to: [2](#0-1) 

The actual per-contract binding only happens later, when the local database looks up which address is allowed to write a given `slot_id` *for that specific contract* and checks the signature against it: [3](#0-2) 
and similarly in the network-received-chunk validation path: [4](#0-3) 

Because the signed digest itself carries no contract identifier, a signature that a signer produced to authorize a chunk write into StackerDB contract A is equally valid for a write into StackerDB contract B, provided:
- the same `StacksAddress` is registered as the writer of the same `slot_id` in contract B (per `StackerDBConfig.signers`, populated from `stackerdb-get-signer-slots`), and
- the replayed `slot_version` is higher than B's currently stored version for that slot (or B's slot was just reset to `NO_VERSION`/0, e.g. after reconfiguration, per `reconfigure_stackerdb`): [5](#0-4) 

This is a direct analog of the original report: the "role"/authorization scope (`UPGRADER_ROLE` value tied to the wrong contract) is missing a distinguishing identifier, so an authorization meant for one target is honored for a different target. Here, the missing identifier is the StackerDB contract ID inside the signed digest, so a signer's authorization for slot X of contract A is silently honored for slot X of contract B.

This scenario is realistic in the Stacks network: signer sets for adjacent/related reward cycles (`.signers-0-xxx`, `.signers-1-xxx`) are populated from `stacker-set` data that frequently repeats the same `StacksAddress`-to-`slot_id` assignment across cycles (the same signers often stack repeatedly and are laid out deterministically), so slot `X` in cycle N and slot `X` in cycle N+2 (same parity contract family) can easily map to the same address. An attacker does not need any private key — they only need to observe a legitimately-signed, already-broadcast chunk (via `StackerDBGetChunkData`/push) for one contract, and replay the exact same `(slot_id, slot_version, sig, data)` tuple against a different StackerDB contract that happens to have the same signer/slot mapping.

### Impact Explanation
This allows an unprivileged network peer to author an "unauthorized write" of attacker-chosen replay data into a StackerDB contract slot that the same signer legitimately owns elsewhere, without possessing the signer's private key — satisfying the "unauthenticated/unauthorized write to state or StackerDB" impact bucket. It can also enable propagation of stale/forged-context data (data legitimately signed for cycle/contract A) into contract B's replica, where downstream consumers (e.g., signer message readers) may treat it as fresh, valid state for B.

### Likelihood Explanation
Exploitation requires no secret key and no privileged role — only observation of a previously broadcast, validly-signed chunk (StackerDB traffic is gossiped to all replicating peers) and re-submission of that identical payload against a different StackerDB contract where the signer/slot coincidence holds. Because Stacks reuses the same signer sets and slot layouts across adjacent reward cycles/contract families, such coincidences are not rare, making this more than a theoretical concern, though it depends on a specific signer/slot alignment between two contracts rather than being universally exploitable against arbitrary DBs.

### Recommendation
Bind the signed digest to the target StackerDB contract identifier, e.g. include the smart contract's serialized `QualifiedContractIdentifier` bytes in `SlotMetadata::auth_digest()`:
```rust
fn auth_digest(&self, contract_id: &QualifiedContractIdentifier) -> Sha512Trunc256Sum {
    let mut hasher = Sha512_256::new();
    hasher.update(contract_id.serialize_to_vec()); // or similar canonical bytes
    hasher.update(self.slot_id.to_be_bytes());
    hasher.update(self.slot_version.to_be_bytes());
    hasher.update(self.data_hash.0);
    Sha512Trunc256Sum::from_hasher(hasher)
}
```
and thread `contract_id` through `sign()`/`verify()` and all call sites (`try_replace_chunk`, `validate_received_chunk`, etc.) so a chunk's signature is only valid for the specific contract it targets.

### Proof of Concept
1. Signer `S` (address `addr`) legitimately signs and posts chunk `C = (slot_id=0, slot_version=1, sig, data)` to StackerDB contract `A` (e.g. `.signers-0-1`), where the local config maps `addr` to `slot_id=0`.
2. A remote peer observes `C` on the network (via `StackerDBGetChunkData` response or `StackerDBPushChunk`).
3. That peer, without any of `S`'s keys, submits `C` unchanged to StackerDB contract `B` (e.g. `.signers-0-3`) which, per its own `stackerdb-get-signer-slots` evaluation, also assigns `addr` to `slot_id=0` and currently stores a version `< 1` for that slot.
4. `try_replace_chunk`/`validate_received_chunk` for `B` calls `slot_desc.verify(&slot_validation.signer)`, i.e. `SlotMetadata::verify(addr)`, which succeeds because `auth_digest()` only covers `(slot_id, slot_version, data_hash)` and never references contract `B` — the chunk is accepted and stored into `B`'s slot 0, even though `S` never signed anything for contract `B`.     /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Sign this slot metadata, committing to slot_id, slot_version, and
    /// data_hash.  Sets self.signature to the signature.
    /// Fails if the underlying crypto library fails
    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }

    pub fn reconfigure_stackerdb(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slots: &[(StacksAddress, u32)],
    ) -> Result<(), net_error> {
        let stackerdb_id = self.get_stackerdb_id(smart_contract)?;
        let mut total_slots_read = 0u32;
        for (principal, slot_count) in slots.iter() {
            total_slots_read =
                total_slots_read
                    .checked_add(*slot_count)
                    .ok_or(net_error::OverflowError(
                        "Slot count exceeeds u32::MAX".to_string(),
                    ))?;
            let slots_before_principal = total_slots_read - slot_count;
            for cur_principal_slot in 0..*slot_count {
                let slot_id = slots_before_principal + cur_principal_slot;
                if let Some(existing_validation) =
                    self.get_slot_validation(smart_contract, slot_id)?
                {
                    // this slot already exists.
                    if existing_validation.signer == *principal {
                        // no change
                        continue;
                    }
                }

                debug!("Reset slot {} of {}", slot_id, smart_contract);

                // new slot, or existing slot with a different signer
                let qry = "INSERT OR REPLACE INTO chunks (stackerdb_id,signer,slot_id,version,write_time,data,data_hash,signature) VALUES (?1,?2,?3,?4,?5,?6,?7,?8)";
                let mut stmt = self.sql_tx.prepare(qry)?;
                let args = params![
                    stackerdb_id,
                    principal.to_string(),
                    slot_id,
                    NO_VERSION,
                    0,
                    vec![],
                    Sha512Trunc256Sum([0u8; 32]),
                    MessageSignature::empty(),
                ];

                stmt.execute(args)?;
            }
        }
        debug!("Shrink {} to {} slots", smart_contract, total_slots_read);
        self.shrink_stackerdb(stackerdb_id, total_slots_read)?;
        Ok(())
    }
