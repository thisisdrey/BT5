### Title
Unbounded hex-payload allocation in `GetAttachmentResponse::deserialize` — no size check against `AtlasConfig.attachments_max_size` before `hex_bytes` allocation - (File: stackslib/src/net/atlas/mod.rs)

### Summary
`GetAttachmentResponse::deserialize` (mod.rs:69-77) takes the JSON string `payload` from an untrusted peer's HTTP response and calls `hex_bytes(&hex_encoded)` directly, allocating a `Vec<u8>` sized to the attacker-controlled hex string with no comparison to `AtlasConfig.attachments_max_size` or `ATTACHMENTS_MAX_SIZE_MIN`. This is reached via `StacksHttpResponse::decode_atlas_get_attachment` (getattachment.rs:159-165) when a node requests `GET /v2/attachments/:hash` from a peer it is downloading attachments from.

### Finding Description
`RPCGetAttachmentRequestHandler`'s response-decoding path (`getattachment.rs:158-165`) reads the whole HTTP body, converts it to JSON, and deserializes into `GetAttachmentResponse` via `serde_json::from_value`. The `Deserialize` impl for `GetAttachmentResponse` at `stackslib/src/net/atlas/mod.rs:69-77` does:
```rust
let payload = String::deserialize(d)?;
let hex_encoded = payload.parse::<String>().map_err(de_Error::custom)?;
let bytes = hex_bytes(&hex_encoded).map_err(de_Error::custom)?;
let attachment = Attachment::new(bytes);
```
There is no check of `payload.len()` (or the resulting `bytes.len()`) against `AtlasConfig.attachments_max_size` (mod.rs:94) or the floor `ATTACHMENTS_MAX_SIZE_MIN` (mod.rs:52) at this decode site. `hex_bytes` allocates a `Vec<u8>` roughly half the size of the input hex string, so the allocation size is fully attacker-controlled up to whatever the HTTP layer permits for the response body.

The mitigating factor is the HTTP response framing: `HttpResponsePreamble.content_length` is typed `Option<u32>` (`stackslib/src/net/http/response.rs:53`), which caps the body the connection layer will read to at most `u32::MAX` (~4 GiB) bytes per response — this is a general HTTP-layer constraint, not an Atlas-specific size check. I was not able to fully confirm within this pass whether the streaming reader in `net/http`/`net/httpcore.rs` enforces a materially smaller cap (e.g. `HTTP_PREAMBLE_MAX_ENCODED_SIZE`-style limit) before buffering the whole body into memory prior to JSON parsing; the code I inspected shows no Atlas-specific `attachments_max_size` gate at all in the deserialize path, meaning a malicious/compromised peer serving a crafted `/v2/attachments/:hash` response can force allocation of a hex-decoded buffer far larger than the configured `attachments_max_size` (default 1 MiB), up to whatever the generic HTTP content-length ceiling allows.

### Impact Explanation
A remote peer that a node is downloading attachments from (reachable without any secret/privileged role, since attachment fetching is a normal peer-to-peer RPC flow) can respond to a single `GET /v2/attachments/:hash` request with a payload containing many megabytes-to-gigabytes of hex characters. This forces the requesting node to allocate a correspondingly large `Vec<u8>` with no reference to the configured `attachments_max_size` limit, well before any content-hash/size validation against the expected attachment can occur. Repeated across the attachment-download retry loop, this yields repeatable, unauthenticated memory pressure/DoS on the requesting node — matching the "remote crash/unauthenticated DoS from few messages" Critical category, bounded in practice only by the generic HTTP content-length type (`u32`, ~4 GiB ceiling).

### Likelihood Explanation
No privileged role, secret, or special peer relationship is required — any peer serving attachment responses to a node performing routine Atlas attachment sync can trigger this by returning an oversized hex payload for a legitimate-looking hash. Attacker cost is a single crafted HTTP response; the flow is part of ordinary attachment-download operation (`AttachmentsDownloader`, `net/atlas/download.rs`), so it is remotely reachable and repeatable.

### Recommendation
In `GetAttachmentResponse::deserialize` (or at the call site `decode_atlas_get_attachment`), reject the payload early: check `payload.len()` (hex length, i.e. roughly `2 * attachments_max_size`) against the caller-supplied `AtlasConfig.attachments_max_size` (or `ATTACHMENTS_MAX_SIZE_MIN` as a hard cap) before calling `hex_bytes`, returning a deserialization error for oversized payloads instead of allocating first and validating later.

### Proof of Concept
Rust test in `stackslib/src/net/api/tests/getattachment.rs` style:
1. Construct an `HttpResponsePreamble` with `content_type: application/json` and a body that is a JSON string of, e.g., 200 MB of hex characters (`"0".repeat(200_000_000)` wrapped in quotes).
2. Call `StacksHttpResponse::decode_atlas_get_attachment` (or directly `serde_json::from_value::<GetAttachmentResponse>`) on this body.
3. Assert that the call either allocates the full ~100 MB `Vec<u8>` with no error (demonstrating unbounded allocation), or — if a fix is applied — that it returns `Err` before the `hex_bytes` allocation once `payload.len() > 2 * attachments_max_size`.
Note: exact confirmation of an outer HTTP body-size ceiling in `net/httpcore.rs`/connection read loop was not completed in this pass; the PoC should also probe that boundary (e.g. try payload sizes near `u32::MAX/2`) to determine the true practical ceiling of the allocation.
