### Title
`validate_high_txn_limits` uses governance-context `get_voting_power` (inflated by `pending_active` stake) instead of current-epoch stake for transaction-limit authorization — (`aptos-move/framework/aptos-framework/sources/transaction_limits.move`)

---

### Summary

`transaction_limits::validate_high_txn_limits` is called in the transaction prologue to verify that a fee payer controls enough committed stake to unlock higher execution/IO gas multipliers. For the `StakePoolOwner` and `DelegatedVoter` variants it calls `aptos_governance::get_voting_power(pool_address)`, a function designed for governance proposals that, on mainnet, returns `active + pending_active + pending_inactive`. The `pending_active` bucket holds stake that has been deposited but is not yet live in the current epoch. The `DelegationPoolDelegator` variant in the same function correctly uses `delegation_pool::get_stake` and sums only `active + pending_inactive`. The mismatch means a stake-pool owner can temporarily inflate the measured stake by depositing into `pending_active`, pass a tier threshold they would otherwise fail, and execute transactions at a multiplier (up to 100×) that their real current-epoch stake does not justify.

---

### Finding Description

`aptos_governance::get_voting_power` is documented as returning voting power **for governance proposals**. On mainnet (`allow_validator_set_change == true`) it reads all three non-inactive buckets:

```move
// aptos_governance.move L703-L714
public fun get_voting_power(pool_address: address): u64 {
    let allow_validator_set_change =
        staking_config::get_allow_validator_set_change(&staking_config::get());
    if (allow_validator_set_change) {
        let (active, _, pending_active, pending_inactive) = stake::get_stake(pool_address);
        active + pending_active + pending_inactive   // <-- includes pending_active
    } else {
        stake::get_current_epoch_voting_power(pool_address)
    }
}
```

`stake::get_current_epoch_voting_power` — the function that reflects what the validator actually contributes to consensus **this epoch** — returns only `active + pending_inactive` for active/pending-inactive validators and 0 otherwise:

```move
// stake.move L453-L466
public fun get_current_epoch_voting_power(pool_address: address): u64 {
    ...
    if (validator_state == VALIDATOR_STATUS_ACTIVE
        || validator_state == VALIDATOR_STATUS_PENDING_INACTIVE) {
        active_stake + pending_inactive_stake   // no pending_active
    } else { 0 }
}
```

`validate_high_txn_limits` uses the governance function for two of its three variants:

```move
// transaction_limits.move L268-L295
StakePoolOwner { multipliers } => {
    ...
    let stake_amount = aptos_governance::get_voting_power(pool_address); // wrong context
    validate_enough_stake(stake_amount, multipliers);
},
DelegatedVoter { pool_address, multipliers } => {
    ...
    let stake_amount = aptos_governance::get_voting_power(pool_address); // wrong context
    validate_enough_stake(stake_amount, multipliers);
},
```

But the third variant uses the correct, per-delegator current-epoch stake:

```move
// transaction_limits.move L306-L309
let (active, _, pending_inactive) = delegation_pool::get_stake(pool_address, fee_payer);
validate_enough_stake(active + pending_inactive, multipliers);
```

The inconsistency is the root cause. `pending_active` stake is deposited via `stake::add_stake`; when the pool is already an active validator the coins land in `pending_active` and are not moved to `active` until `on_new_epoch`. They do not contribute to the validator's current-epoch consensus weight. A pool owner can therefore:

1. Call `stake::add_stake` to deposit a large amount into `pending_active` (within the governance-set `maximum_stake` cap).
2. Immediately submit a transaction carrying a `UserTxnLimitsRequest::StakePoolOwner` with a high multiplier.
3. The prologue calls `validate_high_txn_limits` → `get_voting_power` → `active + pending_active + pending_inactive`, which now exceeds the tier threshold.
4. The transaction executes at the elevated multiplier (e.g. 8× or 100× execution/IO gas).
5. The `pending_active` stake cannot be directly withdrawn; it activates next epoch. But the attacker has already obtained the elevated limits.

---

### Impact Explanation

An unprivileged stake-pool owner can bypass the stake-tier gate for higher transaction limits. The system is designed so that only validators with substantial committed stake can access multipliers up to 100× the base execution/IO gas limit. By inflating the measured stake with uncommitted `pending_active` coins, an attacker can reach a tier whose threshold their real active stake does not meet. Transactions executing at 100× gas limits can perform far more computation or storage I/O per block than the base limit allows, creating a vector for targeted validator slowdown or block-gas exhaustion that the tier system was specifically designed to prevent.

---

### Likelihood Explanation

Any account that holds an `OwnerCapability` for a stake pool currently in the active validator set can trigger this. No privileged access or governance action is required. The attacker needs only enough APT to push `get_voting_power` past the desired tier threshold, and those coins remain locked for one epoch (not permanently lost). The attack is repeatable each epoch.

---

### Recommendation

Replace `aptos_governance::get_voting_power` with `stake::get_current_epoch_voting_power` in both the `StakePoolOwner` and `DelegatedVoter` branches of `validate_high_txn_limits`. This aligns those branches with the `DelegationPoolDelegator` branch, which already uses only the stake that is live in the current epoch:

```move
// StakePoolOwner
let stake_amount = stake::get_current_epoch_voting_power(pool_address);

// DelegatedVoter
let stake_amount = stake::get_current_epoch_voting_power(pool_address);
```

`get_current_epoch_voting_power` returns `active + pending_inactive` for active/pending-inactive validators and 0 otherwise, which correctly measures the stake that actually backs the validator's consensus participation this epoch.

### Proof of Concept

```
Preconditions (mainnet rules):
  - allow_validator_set_change = true  (mainnet default)
  - TxnLimitsConfig tier: 8× execution requires min_stake = T APT
  - Attacker owns a stake pool P in the active validator set
  - P.active = A APT  (A < T, so attacker cannot reach 8× tier legitimately)
  - P.pending_active = 0

Step 1 – Inflate pending_active:
  attacker calls stake::add_stake(owner_cap, T - A + 1 APT)
  → P.pending_active = T - A + 1 APT  (pool is active, so coins go to pending_active)
  → P.active unchanged = A APT

Step 2 – Submit high-limit transaction:
  attacker submits tx with:
    UserTxnLimitsRequest::StakePoolOwner {
        multipliers: RequestedMultipliers::V1 {
            execution_multiplier_percent: 800,  // 8×
            io_multiplier_percent: 200,
        }
    }

Step 3 – Prologue evaluation (transaction_limits.move L278):
  stake_amount = aptos_governance::get_voting_power(P)
               = A + (T - A + 1) + 0          // active + pending_active + pending_inactive
               = T + 1  ≥ T                   // passes threshold

Step 4 – validate_enough_stake passes; tx executes at 8× gas limits.

Correct behavior (using get_current_epoch_voting_power):
  stake_amount = A + 0 = A  < T  → EINSUFFICIENT_STAKE abort
```

        let allow_validator_set_change = staking_config::get_allow_validator_set_change(&staking_config::get());
        if (allow_validator_set_change) {

            // stake would still count in their voting power for governance proposals.

        } else {
            stake::get_current_epoch_voting_power(pool_address)
        }
    }

    public fun get_current_epoch_voting_power(
        pool_address: address
    ): u64 acquires StakePool, ValidatorSet {
        assert_stake_pool_exists(pool_address);
        let validator_state = get_validator_state(pool_address);
        // Both active and pending inactive validators can still vote in the current epoch.
        if (validator_state == VALIDATOR_STATUS_ACTIVE
            || validator_state == VALIDATOR_STATUS_PENDING_INACTIVE) {
            let active_stake =
                coin::value(&borrow_global<StakePool>(pool_address).active);
            let pending_inactive_stake =
                coin::value(&borrow_global<StakePool>(pool_address).pending_inactive);
            active_stake + pending_inactive_stake
        } else { 0 }
    }
