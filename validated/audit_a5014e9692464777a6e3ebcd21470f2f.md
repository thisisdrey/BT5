### Title
`OutboundQueue::calculate_fee` can round the Ethereum relayer reward/gas-refund component to exactly zero, leaving relayers uncompensated for real Ethereum execution cost - ([File: bridges/snowbridge/pallets/outbound-queue/src/lib.rs])

### Summary
The Sherlock/MultiInvoker bug is a keeper-fee model where one component of the fee formula (`_calldataFee`) is structurally computed as zero in the base contract, so the "keeper" (relayer) is systematically underpaid relative to the real cost of the work it performs and is not incentivized to execute it. `snowbridge-pallet-outbound-queue`'s public fee-computation path, `Pallet::<T>::calculate_fee`, has an analogous structural defect: due to integer-truncating decimal conversion, the "remote" fee component — which is precisely the pool that reimburses Ethereum relayers for gas plus reward — can be computed as exactly `0` even though all governance-set pricing parameters (`fee_per_gas`, `rewards.remote`, `multiplier`, `exchange_rate`) are non-zero and the requested Ethereum gas usage is non-zero.

### Finding Description
`calculate_fee` in `bridges/snowbridge/pallets/outbound-queue/src/lib.rs` computes the remote (Ethereum-side) portion of the delivery fee as: [1](#0-0) 

The remote fee, expressed in wei (Ether has 18 decimals, see `ETHER_DECIMALS`), is first computed by `calculate_remote_fee` as `fee_per_gas * gas_used_at_most + reward`, then scaled by `multiplier`/`exchange_rate` via `FixedU128`, and finally divided down to the local chain's decimal precision by `convert_from_ether_decimals`: [2](#0-1) 

`convert_from_ether_decimals` performs an integer division by `10^(ETHER_DECIMALS - T::Decimals)` (e.g. `10^8` for a 10-decimal chain). Any wei-denominated remote fee smaller than this divisor is truncated to `0` by integer division — this is not a hypothetical edge case, it is demonstrated directly in the pallet's own test suite: [3](#0-2) 

The test uses fully non-zero, "valid" pricing parameters (`fee_per_gas=1`, `rewards.remote=1`, `multiplier=1`, `exchange_rate=1`) and a real `gas_used=250000`, yet `fee.remote` resolves to `0`, with the test comment itself noting "though none zero pricing params the remote fee calculated here is invalid ... which should be avoided." This fee is computed inside the public `SendMessage::validate` path (`bridges/snowbridge/pallets/outbound-queue/src/send_message_impl.rs`), which is invoked whenever any user sends an XCM message that is routed to Ethereum — an entirely unprivileged, public entrypoint. There is no floor/minimum enforced on the remote fee component before it is charged to the sender and used downstream to fund/reflect the relayer gas-refund and reward pool on the Ethereum gateway side.

### Impact Explanation
This underpriced-work defect degrades bridge relaying incentives without needing any privileged actor, malicious relayer, or governance abuse: any sender submitting a low-gas message (or a chain configured with a coarse decimal precision relative to `ETHER_DECIMALS`) can have the entire remote/reward fee component silently truncated to zero while still being permitted to enqueue and commit the message for Ethereum delivery. Relayers who execute these messages on Ethereum (paying real gas) receive no compensating reward/gas-refund credit for that batch, discouraging honest relay activity and potentially stalling processing of low-value messages — matching the "public underpriced work that degrades block production or stalls bridge processing" impact category.

### Likelihood Explanation
Likelihood is high in relative terms because the trigger condition is purely arithmetic (small `gas_used_at_most * fee_per_gas + reward` relative to the chain's decimal-scaling divisor) and reachable by any ordinary user constructing a low-gas Ethereum-bound message; the codebase's own regression test already documents that "valid" non-zero pricing parameters can produce this exact zero-fee outcome, so no adversarial parameter manipulation or privileged access is required — only ordinary message parameters within the range already exercised by the pallet's test suite.

### Recommendation
Enforce a non-zero minimum bound on the computed remote fee (e.g., saturate to `1` unit, or round up rather than truncate down) whenever the pre-truncation wei-denominated fee is non-zero, and add a defensive check/ensure! in `calculate_fee` (and its `v2` analogs) that rejects or clamps a message when `fee.remote == 0` while `gas_used_at_most > 0`, so relayers are never asked to service Ethereum-bound messages carrying zero compensation.

### Proof of Concept
Using the pallet's own mock runtime and the exact scenario already present in the codebase: [3](#0-2) 
1. Configure `PricingParameters` with `exchange_rate = 1/1`, `fee_per_gas = 1`, `rewards = { local: 1, remote: 1 }`, `multiplier = 1/1` (all non-zero, plausible governance values).
2. Call `OutboundQueue::calculate_fee(gas_used = 250_000, price_params)`.
3. Observe `fee.remote == 0` (confirmed by the existing assertion `assert_eq!(fee.remote, 0)`), even though `fee_per_gas`, `reward`, and `gas_used` are all non-zero — i.e., the sender pays only `fee.local` and the Ethereum relayer reward/gas-refund pool for that message receives nothing.

		/// Calculate total fee in native currency to cover all costs of delivering a message to the
		/// remote destination. See module-level documentation for more details.
		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

		/// Calculate fee in remote currency for dispatching a message on Ethereum
		pub(crate) fn calculate_remote_fee(
			gas_used_at_most: u64,
			fee_per_gas: U256,
			reward: U256,
		) -> U256 {
			fee_per_gas.saturating_mul(gas_used_at_most.into()).saturating_add(reward)
		}

		/// The local component of the message processing fees in native currency
		pub(crate) fn calculate_local_fee() -> T::Balance {
			T::WeightToFee::weight_to_fee(
				&T::WeightInfo::do_process_message().saturating_add(T::WeightInfo::commit_single()),
			)
		}

		// 1 DOT has 10 digits of precision
		// 1 KSM has 12 digits of precision
		// 1 ETH has 18 digits of precision
		pub(crate) fn convert_from_ether_decimals(value: u128) -> T::Balance {
			let decimals = ETHER_DECIMALS.saturating_sub(T::Decimals::get()) as u32;
			let denom = 10u128.saturating_pow(decimals);
			value.checked_div(denom).expect("divisor is non-zero; qed").into()
		}

#[test]
fn test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero() {
	new_tester().execute_with(|| {
		let gas_used: u64 = 250000;
		let price_params: PricingParameters<<Test as Config>::Balance> = PricingParameters {
			exchange_rate: FixedU128::from_rational(1, 1),
			fee_per_gas: 1_u32.into(),
			rewards: Rewards { local: 1_u32.into(), remote: 1_u32.into() },
			multiplier: FixedU128::from_rational(1, 1),
		};
		let fee = OutboundQueue::calculate_fee(gas_used, price_params.clone());
		assert_eq!(fee.local, 698000000);
		// Though none zero pricing params the remote fee calculated here is invalid
		// which should be avoided
		assert_eq!(fee.remote, 0);
	});
}
