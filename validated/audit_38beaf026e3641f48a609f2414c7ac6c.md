### Title
Missing contract-id binding in StackerDB chunk signatures enables cross-contract signature replay - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` computes the signed digest from only `slot_id`, `slot_version`, and `data_hash` [1](#0-0) . It never incorporates the target `QualifiedContractIdentifier` (the specific StackerDB replica/contract) into what is signed. Both the chunk-verification path used for unsolicited/synced chunks (`PeerNetwork::validate_received_chunk`) and the storage-layer path (`StackerDBTx::try_replace_chunk`, via `get_slot_signer`) authenticate a chunk purely by recovering the signer address from this contract-agnostic digest and checking it against the *slot owner of the target contract* [2](#0-1) . Because the contract identity is never part of what was signed, a single signature is valid for *any* StackerDB contract instance in which that signer address happens to own the same `slot_id`, not just the contract it was originally produced for.

### Finding Description
The signature/authentication scheme is exactly the class of bug described in the external report: authorization data lacking a binding value (there it was a missing nonce; here it is a missing "domain"/context identifier — the contract this authorization is meant to apply to). The signed payload is:

```
hasher.update(self.slot_id.to_be_bytes());
hasher.update(self.slot_version.to_be_bytes());
hasher.update(self.data_hash.0);
``` [3](#0-2) 

`verify()` only recovers the public key from this digest and compares the resulting `Hash160` to the expected principal — it has no notion of *which* StackerDB contract the chunk is destined for [4](#0-3) .

The consumers of this primitive look up slot ownership per target contract and then rely solely on `SlotMetadata::verify` to authenticate:
- `StackerDBs::validate_received_chunk` calls `self.stackerdbs.get_slot_signer(smart_contract_id, data.slot_id)` and then `slot_metadata.verify(&addr)` — `smart_contract_id` only selects *which* address is expected to own the slot; it never enters the signed digest itself [2](#0-1) .
- The write-path `try_replace_chunk`/`BadSlotSigner` check (exercised in `stackslib/src/net/stackerdb/tests/db.rs:429-443`) performs the identical address-recovery check with no per-DB domain separation.
- The RPC write endpoint `poststackerdbchunk.rs` and the P2P push/gossip handlers (`handle_unsolicited_StackerDBPushChunk` in `stackslib/src/net/tests/relay/nakamoto.rs` shows the call site) both ultimately funnel into this same signature check.

Any StacksAddress that is configured as the owner of `slot_id = N` in more than one StackerDB contract (which is the normal deployment pattern: the same signer set repeatedly owns the same slot indices across successive reward-cycle StackerDB instances, and signer/miner-facing StackerDBs are commonly (re)configured with overlapping address→slot assignments) can have a signature obtained from one context (contract A, slot N, version V, data D) replayed verbatim — same `(slot_id, slot_version, sig, data)` tuple — against a different contract B where that address also owns slot N. If B's current slot-N version is `< V`, the replayed chunk passes every check (`BadSigner`, `NoSuchSlot`, staleness, `TooManySlotWrites`) even though the actual key-holder never authorized *that* write for contract B.

### Impact Explanation
This is an unauthorized/forged write into StackerDB state: data that was only ever authorized (signed) for one replica/contract context can be injected into a different replica's slot without any fresh signature from the key holder for that context, because the signature format provides no domain separation between StackerDB instances. This matches "unauthenticated/unauthorized write to state or StackerDB" and "network-wide propagation of forged data" — since StackerDB chunks are broadcast/gossiped and stored by relay nodes (`handle_unsolicited_StackerDBPushChunk`), a replayed chunk can also be propagated to other peers, having them accept and store data into the wrong contract/slot context believing it is validly authorized.

### Likelihood Explanation
StackerDB chunks are not confidential — they are gossiped over the P2P network and served over RPC (`poststackerdbchunk.rs`), so any legitimately published chunk's `(slot_id, slot_version, sig, data)` is observable by any peer. The only condition needed for exploitation is that the target contract's slot allocation (`signers` list passed to `create_stackerdb`) assigns the same address to the same `slot_id` as some other contract that address participates in — a configuration that recurs naturally across reward-cycle-rotated signer StackerDBs.

### Recommendation
Bind the specific StackerDB contract to the signed payload, analogous to adding the missing nonce in the referenced report. Include the `QualifiedContractIdentifier` (or a stable numeric/hash identifier for it) in `SlotMetadata::auth_digest()`:

```rust
fn auth_digest(&self, contract_id: &QualifiedContractIdentifier) -> Sha512Trunc256Sum {
    let mut hasher = Sha512_256::new();
    hasher.update(contract_id.serialize_to_vec()); // new: domain separation
    hasher.update(self.slot_id.to_be_bytes());
    hasher.update(self.slot_version.to_be_bytes());
    hasher.update(self.data_hash.0);
    Sha512Trunc256Sum::from_hasher(hasher)
}
```
and update `sign`/`verify` and every call site (`validate_received_chunk`, `try_replace_chunk`/`get_slot_signer` path, RPC handler) to pass the contract id through, so a chunk signature is only valid for the specific contract it was created for.

### Proof of Concept
1. Configure two StackerDB contracts, `A` and `B`, each created via `create_stackerdb` such that address `S` owns `slot_id = 0` in both (a normal cross-cycle signer-set configuration) [5](#0-4) .
2. Signer `S` legitimately signs and publishes a `StackerDBChunkData { slot_id: 0, slot_version: 5, data: D }` for contract `A` — this is broadcast on the P2P network and observable by anyone.
3. An attacker takes the exact same `(slot_id, slot_version, sig, data)` tuple and POSTs it to contract `B`'s endpoint (`/v2/stackerdb/{B-principal}/{B-contract}/chunks`) or replays it via the P2P push path.
4. `validate_received_chunk`/`try_replace_chunk` for contract `B` looks up `get_slot_signer(B, 0) == S`, then calls `slot_metadata.verify(&S)` — which succeeds because the digest never referenced contract `A` — and, provided `B`'s stored version for slot 0 is `< 5`, the chunk is accepted and stored into `B`'s slot 0, even though `S` never authorized that write for `B` [6](#0-5) .

    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
