### Title
Fresh accounts accrue `balance × 1e18` reward delta when reward index still equals `INITIAL_INDEX` — (File: contracts/RewardsDistributor.sol)

### Summary
When a reward speed is enabled for a token, `tokenStates[token].index` is initialized to `INITIAL_INDEX` (1e18) while `accountIndexOf` for all existing holders stays 0. The fallback in `_calculateTokenDelta` only normalizes a zero account index when `_tokenIndex > INITIAL_INDEX`. If a holder's index is updated in the same block the speed is set (before any time delta grows the index), `_deltaIndex = INITIAL_INDEX - 0 = 1e18`, so the account accrues `balanceOf(account)` reward units instantly.

### Finding Description
In `contracts/RewardsDistributor.sol`, `_updateTokenSpeed` sets `tokenStates[token_] = TokenState({index: INITIAL_INDEX, timestamp: block.timestamp})` when a token is first given a speed (line ~298). `_calculateTokenDelta` (lines 217–231) computes:

```solidity
uint256 _accountIndex = accountIndexOf[token_][account_];
if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}
uint256 _deltaIndex = _tokenIndex - _accountIndex;
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
```

Within the same block as the `updateTokenSpeed` transaction, `_deltaTimestamps == 0`, so `_updateTokenIndex` leaves `index == INITIAL_INDEX`. The strict `>` comparison means the `INITIAL_INDEX` fallback is skipped: `accountIndex` remains 0 and `_deltaIndex == 1e18`. Any holder can permissionlessly call `updateBeforeMintOrBurn(token_, account_)` (the NatSpec says it "may be called by anyone") or `claimRewards(account_, tokens_)` and receive `tokensAccruedOf[account] += balanceOf(account) * 1e18 / 1e18 = balanceOf(account)`.

The same flaw also lets the `MappedEnumerableSet` "freed" account state (`accountIndexOf` left at 0 for an account that never indexed) be consumed with a dangling index — the closest analog to use-after-free in this codebase: a zeroed/uninitialized index is reinterpreted as a valid accumulator baseline of 0 instead of `INITIAL_INDEX`.

### Impact Explanation
Theft of unclaimed yield / drainage of the rewards contract. An attacker holding a large msdTOKEN balance before a new reward speed is enabled can claim approximately `balance` reward tokens (e.g., holding 1M msdMET yields ~1M reward tokens accrued). `_transferRewardIfEnoughTokens` pays out whatever the distributor holds, so the attacker drains the reward pool that was meant for pro-rata distribution over time.

### Likelihood Explanation
Requires a same-block interaction with a governor's `updateTokenSpeed`/`syncTokenSpeed` transaction. The attacker only needs to (a) hold a token balance before the speed is enabled and (b) front-run or bundle after the governor tx — both standard unprivileged attacker actions. The bug is deterministic whenever the timing condition is met; no malicious privileged actor is needed, only a routine reward configuration event. Each new token added to a distributor is a fresh window.

### Recommendation
Use `>=` in the fallback, i.e., treat a zero `accountIndexOf` as `INITIAL_INDEX` whenever the account has never been indexed:

```solidity
if (_accountIndex == 0) {
    _accountIndex = _tokenIndex > INITIAL_INDEX ? INITIAL_INDEX : _tokenIndex;
}
```

or, more simply, always initialize `accountIndexOf` to the current token index on first interaction (set `_accountIndex = _tokenIndex` when `_accountIndex == 0`), so no delta is ever computed against a zero baseline.

### Proof of Concept
Hardhat (fork or local deploy) sketch:

```ts
// 1. Setup: alice holds msdMET before rewards are configured
await met.connect(alice).approve(metDepositToken.address, MaxUint256)
await metDepositToken.connect(alice).deposit(parseEther('1000'), alice.address)
// fund distributor
await rewardToken.mint(rewardDistributor.address, parseEther('10000'))

// 2. Governor enables speed for msdMET (attacker bundles in same block)
await network.provider.send('evm_setAutomine', [false])
await rewardDistributor.updateTokenSpeed(metDepositToken.address, parseEther('1'))

// 3. Same block: alice permissionlessly updates her index
await rewardDistributor.updateBeforeMintOrBurn(metDepositToken.address, alice.address)
await network.provider.send('evm_mine')
await network.provider.send('evm_setAutomine', [true])

// 4. tokensAccruedOf[alice] == 1000e18 instead of ~0
expect(await rewardDistributor.tokensAccruedOf(alice.address)).to.eq(parseEther('1000'))

// 5. Claim drains the distributor
await rewardDistributor.claimRewards(alice.address, [metDepositToken.address])
// alice receives ~1000 reward tokens for zero elapsed time
```

The key assertion: `accountIndexOf(msdMET, alice)` is 0, `tokenStates(msdMET).index == INITIAL_INDEX`, so `_deltaIndex == 1e18` and `_tokensDelta == balanceOf(alice)`.
