### Title
Unauthenticated `RecvError` can force tunnel teardown when the peer's remote address is not yet fixed - ([File: outside.go])

### Summary
The external report's root issue is a check/act mismatch: a verification step (caveat enforcement, `redeemDelegation`) is treated as if it guarantees the intended downstream action, but a code path exists where the actual action never happens (or happens without the assumed guarantee) while state is still committed as if it had. The closest reachable analog in this Nebula fork is `Interface.handleRecvError` in `outside.go`: it processes an unauthenticated, unencrypted `header.RecvError` control message and executes a destructive state change (`closeTunnel`) whenever it *cannot* verify the sender, rather than only when it *can* verify and reject.

### Finding Description
`RecvError` packets are handled before any certificate or session-key verification occurs — they are dispatched straight out of the header-parsing switch in `readOutsidePackets`, alongside `Handshake`, with no `ConnectionState`/AEAD check: [1](#0-0) 

`handleRecvError` then looks up the hostinfo purely by the numeric `RemoteIndex` carried in the plaintext header, and the only anti-spoofing protection is a conditional check that is skipped whenever `hr` (the hostinfo's currently known remote) is not yet a valid address: [2](#0-1) 

```go
hr := hostinfo.GetRemote()
if hr.IsValid() && hr != addr {
    f.l.Info("Someone spoofing recv_errors?", ...)
    return
}
f.closeTunnel(hostinfo)
```

This mirrors the report's structure exactly: the code assumes that "we can verify the caller, so let's act" is always achievable, but for a legitimate state of the system (e.g., a pending/relayed tunnel, or any hostinfo whose remote UDP address is not yet set — see `GetRemote()`/`SetRemote()` usage throughout `handshake_manager.go` and `hostinfo.remotes`), the verification is a no-op and the action (`closeTunnel`, which deletes the `HostInfo` from the hostmap and clears lighthouse state) executes unconditionally based on nothing but an attacker-guessable/observable 32-bit index. Just as the report's delegation manager cannot guarantee `executeDelegatedAction` actually ran before trusting caveat-enforcer state, `handleRecvError` cannot guarantee the `RecvError` came from the genuine peer before trusting it enough to tear down live tunnel/hostmap state.

### Impact Explanation
An attacker with no CA-signed certificate can send a bare `RecvError` header (no handshake, no AEAD) to a target and, if the target has any hostinfo whose `GetRemote()` is not yet valid (freshly established via relay, still roaming, or otherwise not pinned), unconditionally force `closeTunnel` — deleting the `HostInfo` and clearing lighthouse-cached addresses for that peer. This is a remote state-poisoning / denial-of-service primitive against the hostmap and lighthouse cache, triggerable purely from packet/header content with no cryptographic authentication, matching the accepted impact class (remote state poisoning).

### Likelihood Explanation
Exploitation requires the attacker to know or guess a valid `RemoteIndex` (32-bit, allocated by `generateIndex`) for a tunnel whose `hr` is not yet pinned to a fixed remote address, and to reach the victim's UDP listener. Indexes are not encrypted in the header and are visible on any handshake/message packet on the wire, so an on-path or partially-observing attacker (e.g., anyone who can see a single packet, or a malicious relay peer forwarding traffic) can trivially obtain a valid index; a fully blind off-path attacker would need to brute-force it, which is the existing mitigation (`acceptRecvErrorConfig`/rate limiting referenced in the CHANGELOG, e.g. #1459) that this fork already partially addresses. The condition "`hr` invalid" is common during the window right after a handshake completes via relay or before the first data packet fixes the remote, so the bypass window is real but transient.

### Recommendation
Do not special-case "unknown remote" as "allow." Require an additional binding (e.g., only accept `RecvError` for hostinfos whose remote is unset if `via` itself is validated some other way, or require a minimum number of confirmations/rate-limit independent of whether `hr` is valid) before calling `closeTunnel`. At minimum, treat `!hr.IsValid()` the same as a spoofing attempt (log and drop, or require the request to have arrived at least N times / from a lighthouse-confirmed address) rather than always honoring it.

### Proof of Concept
1. Attacker (no valid nebula certificate) observes or guesses the `RemoteIndex` of a victim's just-established relayed/roaming tunnel whose `GetRemote()` has not yet been fixed to a concrete UDP address (`hr.IsValid() == false`).
2. Attacker crafts a raw UDP packet with `header.H{Type: header.RecvError, RemoteIndex: <guessed index>}` (per `header.Encode` used in `sendRecvError`) and sends it to the victim's listening UDP port from any source address.
3. In `readOutsidePackets`, the packet is routed straight to `f.handleRecvError(via.UdpAddr, h)` with no decryption/authentication.
4. In `handleRecvError`, `hostinfo.GetRemote()` returns an invalid `netip.AddrPort`, so the `hr.IsValid() && hr != addr` guard short-circuits to false, and `f.closeTunnel(hostinfo)` executes unconditionally, deleting the hostmap entry and clearing lighthouse state for that peer — without ever having presented a certificate or completing a handshake.

**Note on confidence:** I could not fully verify how easy it is in practice for an attacker to learn a valid `RemoteIndex` for a tunnel in the "`hr` not yet valid" state (this depends on relay/roaming timing and the exact behavior of `generateIndex`, `acceptRecvErrorConfig.ShouldRecvError`, and rate-limiting internals in `interface.go`, which I did not have iterations left to fully inspect). Given the size limits on the code index, if you need the exact implementation of `generateIndex`, `ShouldRecvError`, and the full `RecvErrorConfig` rate-limiting logic to confirm exploitability bounds, a Devin session with full repository access would be needed to review `interface.go` in full.
