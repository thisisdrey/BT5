### Title
Per-account token-list exhaustion via dust `DepositToken` transfers blocks victim deposits and collateral top-ups - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
The Xen bug class is a tracking structure that is allocated but never freed, letting an attacker repeatedly consume a bounded resource until service is denied. The Metronome analog is the per-account `depositTokensOfAccount`/`debtTokensOfAccount` sets in `Pool`: `DepositToken._transfer` (and `_mint` on deposit) unconditionally pushes the token into the *recipient's* list via `pool.addToDepositTokensOfAccount(account_)`, and `Pool` enforces a hard cap `MAX_TOKENS_PER_USER = 30` across deposit + debt tokens. An unprivileged attacker can dust-transfer their own `msdTOKEN` balances of every listed collateral to a victim, filling the victim's list so that any subsequent deposit or receipt of a *new* collateral type reverts with `UserReachedMaxTokens`.

### Finding Description
- `DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance goes `0 → >0`, for any positive `amount_` including 1 wei of the share token. [1](#0-0) 
- `Pool.addToDepositTokensOfAccount` is gated by `onlyIfAdditionWillNotReachMaxTokens`, which reverts when `debtTokensOfAccount + depositTokensOfAccount >= MAX_TOKENS_PER_USER (30)`. [2](#0-1) 
- The same modifier is applied on the deposit/mint path (`DepositToken._mint` → `pool.addToDepositTokensOfAccount(account_)`), so once the victim's list is full, *every* deposit into a collateral type the victim doesn't already hold reverts — including deposits the victim makes themselves to restore health before liquidation. [3](#0-2) 
- Removal only happens when the victim actively transfers the dust out (`balanceOf[sender_] == 0` → `removeFromDepositTokensOfAccount`), so the attacker forces the victim to spend gas cleaning N entries before they can use the protocol again. [4](#0-3) 
- `debtTokensOfAccount` entries can only be added for the minter themselves, so the attacker can only fill slots with dusted *deposit* tokens — the attack requires the pool to list enough collateral types (combined with whatever debt tokens the victim already holds) to approach the 30-slot cap.

### Impact Explanation
Temporary freezing of victim funds / forced liquidation: a victim with an unhealthy position who is dusted to the cap cannot deposit a new collateral type to restore health, so `Pool.liquidate` proceeds against them and their collateral is seized with fees. More generally, all deposits into not-yet-held collaterals revert until the victim manually sweeps out every dust balance (one transfer per token, paying gas each time). Funds are not stolen by the attacker directly, but the denial of the deposit function is a liveness break on a core entry point and can translate into liquidation losses.

### Likelihood Explanation
- Requires no privileged role: `DepositToken.transfer`/`transferFrom` are permissionless and accept attacker-chosen recipients and amounts.
- Cost: attacker must acquire a nonzero balance of each deposit token used for dusting (deposit fees apply on first acquisition, but a single deposit can then be split into dust for many victims since `_balanceBefore == 0` is checked per-recipient, not per-sender).
- Main constraint: the victim's combined deposit+debt token list must be pushable to 30 entries, which depends on how many deposit tokens the pool lists and how many debt positions the victim holds. On pools with few collateral types this may not be reachable; on pools with many listed collaterals it is a single-attacker, low-capital operation.
- Not a gas/unbounded-loop DoS — the revert is a hard revert from an explicit cap, which is the analogous "resource never freed → resource exhausted" mechanism of the Xen bug.

### Recommendation
- Allow the recipient (or anyone) to remove tokens from their own list, or make the cap per-list rather than shared so dust deposits cannot crowd out debt positions.
- Alternatively, skip `addToDepositTokensOfAccount` for transfers below a dust threshold, or let `onlyIfAdditionWillNotReachMaxTokens` be bypassed when the addition comes from a transfer (accounting for the spam vector differently, e.g. cleaning on behalf of the recipient).

### Proof of Concept
Hardhat (fork or unit) outline:

```ts
// Setup: pool with N listed DepositTokens (deployed config), victim holds 0 of them.
// 1. Attacker deposits a small amount of each collateral to get msdTOKEN_i balances.
for (const dt of depositTokens) {
  await underlying.connect(attacker).approve(dt.address, DUST);
  await dt.connect(attacker).deposit(DUST, attacker.address); // mint msdTOKEN
}
// 2. Dust the victim: each transfer triggers addToDepositTokensOfAccount(victim)
//    until depositTokensOfAccount.length(victim) + debtTokensOfAccount.length(victim) == 30.
for (const dt of depositTokens) {
  await dt.connect(attacker).transfer(victim.address, 1);
}
// Attacker can also top-up: after victim's cleanup they re-dust in the same block
// (recipientBalanceBefore == 0 again) to keep the list full.
// 3. Victim attempts to deposit a collateral type not yet in their list.
await expect(
  newDepositToken.connect(victim).deposit(amount, victim.address)
).to.be.revertedWithCustomError(pool, "UserReachedMaxTokens");
// 4. If victim's position is unhealthy, liquidate() succeeds while the
//    only remediation path (depositing new collateral) reverts.
```

Note: the PoC's reachability depends on the target pool listing enough deposit tokens to reach the cap; it should be run against the specific deployed pool being assessed (e.g. mainnet `Pool` from `deployments/mainnet/Pool.json`) to confirm the count.
