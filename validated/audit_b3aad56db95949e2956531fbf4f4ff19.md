### Title
Unscoped raw MARF value disclosure via `/v2/clarity/marf/:marf_key_hash` bypasses per-contract/map authorization - ([File: stackslib/src/net/api/getclaritymarfvalue.rs])

### Summary
`RPCGetClarityMarfRequestHandler::try_handle_request` accepts an arbitrary attacker-supplied 32-byte `TrieHash` and passes it directly to `ClarityDatabase::get_data_by_hash` / `get_data_with_proof_by_hash`, which read raw serialized values straight from the content-addressed MARF store with no check that the caller is entitled to read the specific contract/map/var that hash happens to resolve to. Any remote, unauthenticated client can retrieve arbitrary internal Clarity-committed state at any queryable tip (including unconfirmed tips) merely by supplying a hex-encoded hash.

### Finding Description
The handler decodes the path capture into a `TrieHash` with only syntactic validation (`TrieHash::from_hex`), resolves a tip via `load_stacks_chain_tip` (which per `TipRequest` can point at an unconfirmed microblock/tenure tip), opens a read-only Clarity transaction at that tip, and calls `clarity_db.get_data_by_hash(&marf_key_hash)` (or `get_data_with_proof_by_hash` when `?proof=1`) [1](#0-0) . These functions perform a raw, key-less lookup against the underlying MARF trie by hash and deserialize whatever bytes are stored there, with the source comment explicitly stating "Load data directly from the underlying store, given its trie hash. The lookup map will not be used... only meant to be used by the RPC system" [2](#0-1) . There is no verification tying the hash back to a specific, caller-authorized `(contract, map/var, key)` tuple — unlike `getmapentry`/`getdatavar`, which require the caller to name the exact contract and map/var and derive the MARF key from that authenticated tuple, this endpoint accepts the hash directly and serves whatever value is content-addressed by it. Since the MARF is a Merkle trie where leaf/node keys are deterministic hashes of `(contract, var-or-map-name, ...)` tuples, an attacker who can compute or brute-force these hashes offline (they are not secret, and the key derivation scheme is part of the public source) can retrieve values for any contract deployed at that tip, not just contracts/keys the request is scoped to.

### Impact Explanation
An unauthenticated remote attacker can disclose the raw serialized value of any Clarity-committed key in the queried tip's MARF trie, including data belonging to contracts/maps/vars the attacker has no defined right to read directly via authenticated endpoints, by guessing or precomputing the corresponding `TrieHash`. This is a state/memory-disclosure primitive against the node's committed Clarity storage, reachable over the public RPC port with no secret, and is repeatable for every hash the attacker computes. This matches the "memory disclosure" Critical impact category, assuming the endpoint requires no privileged token to reach (standard unauthenticated `/v2/*` GET semantics in this codebase).

### Likelihood Explanation
No preconditions beyond a running node with the RPC port reachable and at least one contract state committed to the trie at the queried tip. The attacker only needs to compute the MARF key hash for the target `(contract, map/var)` pair — this derivation is deterministic and public (documented in the Clarity DB key-derivation code), so no privileged access, secret, or social engineering is required. The attacker cost is a single GET request per key of interest; the endpoint permits querying against unconfirmed tips via `TipRequest`, increasing exposure to newly-materialized, not-yet-canonical state as well.

### Recommendation
Restrict `/v2/clarity/marf/:marf_key_hash` (or remove the raw-hash lookup capability entirely) so that it cannot be used to bypass per-contract/map authorization: either require the caller to supply the same `(contract, map/var, key)` tuple used by `getmapentry`/`getdatavar` and derive the hash server-side (never trusting a client-supplied raw hash), or gate this debug/introspection endpoint behind the node's RPC secret / admin-only interface, and disable it by default in production configurations. At minimum, document and restrict it as an operator-only diagnostic tool, not a publicly reachable endpoint.

### Proof of Concept
Rust test plan for `stackslib::net::api::tests::getclaritymarfvalue`:
1. Deploy a contract with a private data-var/map containing a sentinel value not exposed via `getmapentry`/`getdatavar` for that key shape.
2. Independently derive the MARF key string for that var/map entry using the same key-derivation logic as `clarity/src/vm/database/clarity_store.rs`/`key_value_wrapper.rs`, hash it to obtain the `TrieHash` offline (simulating attacker precomputation), without going through any authenticated API call.
3. Issue `GET /v2/clarity/marf/<hex_trie_hash>` against the test node's RPC handler (`RPCGetClarityMarfRequestHandler::try_handle_request`).
4. Assert the response returns `200 OK` with `ClarityMarfResponse.data` equal to the sentinel value's serialized hex — proving the value was retrieved without ever calling `getmapentry`/`getdatavar` or supplying the contract identifier/map name in the request, confirming unauthenticated disclosure of internal Clarity state.

    /// DO NOT USE IN CONSENSUS CODE.
    ///
    /// Load data directly from the underlying store, given its trie hash.  The lookup map will not
    /// be used.
    ///
    /// This should never be called from within the Clarity VM, or via block-processing.  It's only
    /// meant to be used by the RPC system.
    pub fn get_data_by_hash<T>(&mut self, hash: &TrieHash) -> Result<Option<T>, VmExecutionError>
    where
        T: ClarityDeserializable<T>,
    {
        self.store
            .get_data_from_path(hash)?
            .map(|x| T::deserialize(&x))
            .transpose()
    }
