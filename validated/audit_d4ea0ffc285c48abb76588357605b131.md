### Title
Unbounded array-length allocation in TVM multisig precompile helpers causes attacker-triggered OutOfMemory crash - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`extractBytes32Array`, `extractBytesArray`, and `extractSigArray` in `PrecompiledContracts.java` read an array-length word directly out of attacker-supplied precompile call data and immediately use it to allocate a `byte[][]` of that length, with no upper bound check before the allocation. ### Finding Description
In each of these three helpers, `len` is taken from `words[offset].intValueSafe()`, i.e. a 256-bit `DataWord` value taken from the raw precompile input, and passed straight into `new byte[len][]` before the code ever validates it against the actual size of the encoded input (`data.length`/`words.length`):
```java
int len = words[offset].intValueSafe();
byte[][] bytesArray = new byte[len][];
```
`intValueSafe()` only prevents a Java integer-overflow when converting the 256-bit `DataWord` to an `int` (typically by clamping to `Integer.MAX_VALUE`), but it does not cap the value to any value that is sane relative to the amount of data actually supplied. As a result, a caller can supply a calldata word whose value is on the order of `Integer.MAX_VALUE` and force the JVM to attempt to allocate an object array with over two billion `byte[]` slots (each slot itself an 8-byte reference on typical JVMs — tens of gigabytes just for the reference array, before any element is even populated). This mirrors the CVE-2016-9427 bug class: a length value derived from external, unvalidated input is used directly to size a memory allocation, without checking that the allocation is bounded by the actual data available, leading to a huge/garbage allocation attempt and an out-of-memory crash.

These helper functions are used by the multi-signature verification precompiled contracts (`ValidateMultiSign`/`BatchValidateSign` family) that parse ABI-encoded signature and address arrays out of TVM call data; any unprivileged account can trigger this path simply by calling a smart contract that invokes the corresponding precompile address with crafted calldata.

### Impact Explanation
A successful trigger causes the executing full node to attempt a multi-gigabyte (up to ~16GB+) array allocation while processing a single transaction inside the TVM. This throws an `OutOfMemoryError`, which — depending on where it propagates in the execution/block-application pipeline — can crash the node process or corrupt in-flight state, denying service to that node. If triggered during block application in `Manager`, it can stall or crash all full nodes that attempt to replay/validate the same block, which is a critical, network-wide denial-of-service condition.

### Likelihood Explanation
The `len` value is read directly from transaction calldata that is fully attacker-controlled, and it is not bounds-checked against `words.length`/`data.length` before the array allocation. No special privileges are required — an unprivileged contract deployer/caller can construct the calldata and submit an ordinary transaction/contract call to the precompile. The only cost to the attacker is normal energy(gas) for the call, since the OOM occurs before any energy-heavy operations run.

### Recommendation
Before allocating `bytesArray`/`bytes32Array` in `extractBytesArray`, `extractBytes32Array`, and `extractSigArray`, validate that `len` is consistent with the available `words.length` (and, for `extractBytesArray`/`extractSigArray`, with the size of `data`) — e.g., reject if `len < 0` or `offset + len + 1 > words.length` — before performing the allocation, mirroring the bounds checks already present in `isValidAbiEncoding`.

### Proof of Concept
Craft calldata for a call to one of the precompiled multisig contracts (e.g., the address backing `ValidateMultiSign`) where the ABI-encoded array-length word at the expected offset is set to a very large value (close to `Integer.MAX_VALUE`) while the remaining calldata is small/empty. When the precompile's `execute` method calls `extractBytesArray`/`extractBytes32Array`/`extractSigArray`, `words[offset].intValueSafe()` returns the huge length, and `new byte[len][]` is executed immediately, causing the JVM to throw `OutOfMemoryError` during transaction execution on the node processing it.

Note: I was unable to fully trace, within the available tool budget, which specific precompile method (`ValidateMultiSign`/`BatchValidateSign`) directly invokes each helper and confirm there is no earlier length-vs-data-size check performed by the caller before invoking these helpers; this should be re-verified against the full call sites before treating the PoC as final.
