### Title
ExchangeInjectActuator.execute() recomputes the swap output with overflow‑prone primitive `long` math after `doValidate()` already verified it safely with `BigInteger`, letting valid transactions revert unexpectedly - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java)

### Summary
`ExchangeInjectActuator` computes the counter-token amount for a bancor-pool token injection twice, using two different arithmetic strategies. `doValidate()` computes `anotherTokenQuant` with `BigInteger.multiply()/.divide()` (unbounded precision, cannot overflow), so it accepts any transaction whose *final* result fits in a `long` and stays under `dynamicStore.getExchangeBalanceLimit()`. `execute()`, however, recomputes the same value using `floorDiv(multiplyExact(secondTokenBalance, tokenQuant), firstTokenBalance)` — plain 64-bit checked `long` arithmetic. If the *intermediate* product `secondTokenBalance * tokenQuant` (or `firstTokenBalance * tokenQuant`) exceeds `Long.MAX_VALUE`, even though the true, final quotient is small and well within bounds, `multiplyExact` throws `ArithmeticException` and the transaction that just passed validation fails at execution. This is exactly the `BigDiv` bug class: "`(a*b)/d` can fail if the numerators are large … despite the result being far below `MAX_UINT256`."

### Finding Description
- Validation path (safe, BigInteger, never overflows): [1](#0-0) 

- Execution path (unsafe, checked primitive `long` multiply then divide): [2](#0-1) 

`multiplyExact`/`floorDiv` are the checked-overflow primitives from `org.tron.common.math.Maths`, imported and used directly here instead of the `BigInteger` path that `doValidate()` uses for the very same computation. Because `firstTokenBalance`, `secondTokenBalance`, and `tokenQuant` are each bounded only by `dynamicStore.getExchangeBalanceLimit()` (checked against the *result*, not the intermediate product) in validation, an attacker can front-run a legitimate `ExchangeInjectContract`/`ExchangeWithdrawContract` (both actuators share this exchange-pool state) with their own `ExchangeInjectActuator`/`ExchangeWithdrawActuator` transaction to push `firstTokenBalance` or `secondTokenBalance` to a value that, combined with the victim's `tokenQuant`, makes `secondTokenBalance * tokenQuant` (or the symmetric case) overflow 64 bits — while the true division result (`secondTokenBalance * tokenQuant / firstTokenBalance`) remains small and well under `exchangeBalanceLimit`. The victim's transaction then passes `doValidate()` (computed via `BigInteger`, no overflow) but throws `ArithmeticException` inside `execute()`, which is caught and turned into a `ContractExeException`, forcing the transaction to fail on-chain.

### Impact Explanation
This is a griefing/DoS vector reachable by any unprivileged account issuing standard `ExchangeInjectContract`/`ExchangeWithdrawContract`/`ExchangeTransactionContract` transactions against a public bancor-style exchange pool — no special privilege required. An attacker can deliberately manipulate pool reserves right before a targeted victim's transaction is packed into a block so the victim's otherwise-valid transaction fails at `execute()` after having already consumed bandwidth/energy fees for validation and inclusion, and after `AbstractExchangeActuator`/actuator-level state changes tied to a failed status are recorded. This matches the report's core impact: "an attacker could conceivably front run transactions ... in a way that causes targeted transactions to fail."

### Likelihood Explanation
Requires an attacker to control the timing/values of an injected or withdrawn quantity relative to an existing pool's reserves and to predict/target a specific victim transaction — feasible for exchange pools with large reserves (`exchangeBalanceLimit` can be configured to allow very large per-token balances), and only needs standard, permissionless `ExchangeInject`/`ExchangeWithdraw`/`ExchangeTransaction` contract calls to reach.

### Recommendation
Make `execute()` use the same overflow-free `BigInteger` computation that `doValidate()` already performs (or store/reuse the value computed during validation) instead of recomputing with checked-but-overflow-prone `multiplyExact`/`floorDiv` on raw `long`s. Apply the same audit to any other actuator or `capsule` code path that mixes a `BigInteger`-based validate step with a primitive-`long`-based execute step for the same multiply-then-divide computation, and add regression tests with large, similarly-scaled `firstTokenBalance`/`secondTokenBalance`/`tokenQuant` values (product overflowing 64 bits, quotient safely small) to ensure `execute()` never reverts when `doValidate()` accepted the transaction.

### Proof of Concept
1. Attacker creates or targets an existing `Exchange` (bancor pool) where `firstTokenBalance`/`secondTokenBalance` are large (near limits allowed by `exchangeBalanceLimit`).
2. Attacker front-runs an honest user's pending `ExchangeInjectContract` (or `ExchangeWithdrawContract`) with quantity `tokenQuant`, submitting their own inject/withdraw transaction that changes `secondTokenBalance` (or `firstTokenBalance`) just enough that `secondTokenBalance * tokenQuant > Long.MAX_VALUE` for the honest user's already-signed `tokenQuant`, while `secondTokenBalance * tokenQuant / firstTokenBalance` (the real answer) is still small and would pass the `exchangeBalanceLimit` check.
3. The victim's transaction still passes `doValidate()` since that method computes `anotherTokenQuant` via `BigInteger` and never overflows.
4. When the victim's transaction executes, `ExchangeInjectActuator.execute()` calls `floorDiv(multiplyExact(secondTokenBalance, tokenQuant), firstTokenBalance)`; `multiplyExact` throws `ArithmeticException` because the intermediate product overflows a signed 64-bit `long`, even though the final quotient would have been small.
5. The exception is caught, `ret.setStatus(fee, code.FAILED)` is set, and `ContractExeException` is thrown — the victim's transaction fails on-chain despite having passed validation, consuming their fee and disrupting their intended pool interaction. [3](#0-2)
