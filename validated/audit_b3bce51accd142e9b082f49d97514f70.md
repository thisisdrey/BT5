### Title
Unvalidated identity substitution in `handle_handshake_accept` allows a peer authenticated with key K1 to inject arbitrary identity metadata for key K2 - (File: stackslib/src/net/chat.rs)

### Summary
`handle_handshake_accept` is invoked from both `handle_authenticated_control_message` and `handle_unauthenticated_control_message` whenever a `HandshakeAccept`/`StackerDBHandshakeAccept` payload arrives on a conversation whose `Preamble` signature has already been verified against a specific, previously-registered public key. [1](#0-0)  Neither the authenticated nor unauthenticated dispatch path re-checks that `data.handshake.node_public_key` embedded in the payload equals the public key that actually signed the enclosing message (`self.connection.get_public_key()`), so the handler trusts and stores peer metadata for whatever key the payload claims. [2](#0-1) 

### Finding Description
The broken equality is: `signer_of(Preamble) == data.handshake.node_public_key` — the key that cryptographically produced the message's signature must equal the key whose identity fields (`addrbytes`, `port`, `services`, `expire_block_height`) are subsequently trusted. The preamble/session-level signature check (`is_preamble_valid`, called from `validate_inbound_message`) only proves the message came from the peer already bound to this `ConversationP2P` (key K1); it says nothing about the *payload's* self-declared `node_public_key` field. The dispatch sites at `handle_authenticated_control_message` (lines 2548-2562) and `handle_unauthenticated_control_message` (lines 2625-2652) pass the payload straight into `handle_handshake_accept` without an equality check against `self.connection.get_public_key()`. An attacker who legitimately completed a handshake with key K1 can subsequently send a `StacksMessage` whose `Preamble` is validly signed by K1 (the registered key of this session) but whose `HandshakeAcceptData.handshake.node_public_key` field is set to an arbitrary K2, causing the node to process and persist K2-attributed peer metadata under a session that was only ever proven to be controlled by K1.

### Impact Explanation
Downstream consumers of `handle_handshake_accept` (neighbor walk logic in `stackslib/src/net/neighbors/walk.rs`, which also calls `handle_handshake_accept`) use the returned/stored handshake data to update the `PeerDB` and neighbor state (public key, services, expiry, address). If the node persists K2 as the neighbor's public key/identity while the network address and TCP session were only proven to be controlled by K1, this is an unauthenticated write of forged identity metadata into peer state — the node's own PeerDB entry no longer reflects a real, provably-owned key, corrupting the peer graph. This matches the "unauthenticated/unauthorized write to state" and "network propagation of forged data" Critical categories, since corrupted PeerDB entries can be gossiped further to other peers via neighbor-exchange (Neighbors) messages.

### Likelihood Explanation
Precondition is minimal: the attacker only needs to be a normal, unprivileged remote peer capable of completing one legitimate handshake (trivial, no secret required) and then sending a single crafted, self-consistent `HandshakeAccept`/`StackerDBHandshakeAccept` message whose `Preamble` is signed with the same session key K1 but whose embedded `HandshakeData.node_public_key` is set to an arbitrary K2. This is repeatable per-connection and costs nothing beyond one additional handshake-accept message, satisfying the "few messages" / low-cost criteria for Critical severity.

### Recommendation
In `handle_handshake_accept`, before consuming any field of `data.handshake` (or `stackerdb_accept`), assert that `data.handshake.node_public_key` matches `self.connection.get_public_key()` (the key that authenticated the current session/preamble). If they differ, treat the message as invalid (`net_error::InvalidHandshake` or similar) and drop the connection rather than updating peer state.

### Proof of Concept
1. In `stackslib/src/net/chat.rs` test module (or a new test), establish two `ConversationP2P` instances the way existing handshake tests do (e.g., mirroring `test_handshake_accept`/`test_send_recv_message` helpers), completing a full outbound `Handshake` -> `HandshakeAccept` cycle so `self.connection`'s registered key becomes K1.
2. Construct a second `StacksMessage` whose `Preamble` is signed with K1's private key (`StacksMessage::sign(...)` using K1) but whose payload is `StacksMessageType::HandshakeAccept(HandshakeAcceptData { handshake: HandshakeData { node_public_key: K2, .. }, .. })`, with K2 an unrelated keypair the attacker generated locally (no proof of ownership needed by the target).
3. Feed this message through `ConversationP2P::validate_inbound_message` followed by `handle_authenticated_control_message`/`handle_handshake_accept`.
4. Assert that after processing, the conversation's or neighbor's stored public key/metadata reflects K2 (e.g., inspect fields updated by `handle_handshake_accept`, or the resulting `PeerDB`/neighbor entry via the neighbor-walk path), even though the message was signed and the session authenticated with K1 — demonstrating the missing `data.handshake.node_public_key == self.connection.get_public_key()` check.
