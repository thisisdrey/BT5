### Title
Attacker can permanently brick a victim's ability to add collateral by dust-filling `depositTokensOfAccount` up to `MAX_TOKENS_PER_USER` - (File: contracts/DepositToken.sol, contracts/Pool.sol)

### Summary
Analogous to the Mattermost missing-validation DoS (an unvalidated request crashes a component), Metronome fails to validate that the *recipient* of a `DepositToken` transfer consents to being added to the per-account token list. `DepositToken._transfer` unconditionally calls `Pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's prior balance is zero, and `Pool` reverts with `UserReachedMaxTokens` once `debtTokensOfAccount + depositTokensOfAccount` reaches `MAX_TOKENS_PER_USER`. An unprivileged attacker can therefore dust-transfer every listed `msdTOKEN` to a victim, fill the victim's list, and cause all subsequent first-time deposits, mints, and transfers of *new* collateral types to that account to revert.

### Finding Description
- `DepositToken.transfer`/`transferFrom` call `_transfer`, which after updating balances calls `pool.addToDepositTokensOfAccount(recipient_)` when `recipient_`'s balance was zero and `amount_ > 0` (`contracts/DepositToken.sol` lines 498-520).
- `Pool.addToDepositTokensOfAccount` is gated by `onlyIfAdditionWillNotReachMaxTokens(account_)`, which reverts `UserReachedMaxTokens` when the combined deposit+debt token count hits `MAX_TOKENS_PER_USER` (`contracts/Pool.sol` lines 143-148, 216-220).
- The revert happens *after* the balances were already updated in `_transfer`, so the entire transfer reverts — meaning any transfer/mint of a deposit token the victim doesn't already hold fails.
- The same `addToDepositTokensOfAccount` path is used by `_mint` during `deposit(amount_, onBehalfOf_)`, so anyone depositing a new collateral type on behalf of the victim also reverts (`contracts/DepositToken.sol` lines 469-489, 211-237).
- Attack cost: the attacker deposits a minimal amount of each listed deposit token (or obtains dust via `Pool.swap`/transfers) and calls `transfer(victim, 1 wei)` once per token. No privileged role, no oracle manipulation, no governance — pure public entry points.

### Impact Explanation
- The victim cannot receive any new `msdTOKEN` type, cannot have anyone deposit a new collateral type `onBehalfOf_` them, and cannot mint a new collateral via `SmartFarmingManager.leverage` paths that mint a fresh deposit token.
- Most critically, if the victim's position becomes unhealthy, they cannot top up with a *new* collateral type to restore health — the deposit reverts — turning the griefing into forced liquidations (loss of the liquidation fee / collateral discount) that would otherwise have been avoidable.
- The freeze is effectively permanent for new token types: the victim can only shed list entries by fully zeroing a balance (`withdraw`/`transfer` of the full balance), and the attacker can re-dust the slot at any time. There is no mechanism for the victim to refuse or remove dust entries without giving up the dust balance.

### Likelihood Explanation
- Requires only dust amounts of each listed deposit token and standard ERC20 transfers; cost scales linearly with the number of listed deposit tokens (bounded by `MAX_TOKENS_PER_USER`, a small constant defined in `PoolStorage.sol`).
- No modifier stops it: `transfer` is not pausable-gated for this path beyond `whenNotPaused` on deposit, `nonReentrant` doesn't apply to `transfer`, and there is no opt-in/whitelist for being added to `depositTokensOfAccount`.
- Profitable when the victim has a position near the liquidation threshold and holds few collateral types, so blocking new collateral deposits guarantees the liquidation bonus instead of letting the victim recover.

### Recommendation
- Do not add recipients to `depositTokensOfAccount` on permissionless `transfer`/`transferFrom`; instead track recipient deposit membership only on `deposit`/`_mint` (and `seize`), or
- Make `addToDepositTokensOfAccount` failure non-fatal inside `_transfer` for tokens the recipient never opted into (e.g., require an explicit `recipient_` opt-in flag, or catch the `UserReachedMaxTokens` revert and skip list insertion for transfer-in tokens), and
- Allow victims to remove themselves from the list (`removeFromDepositTokensOfAccount` initiated by the account holder) so dust entries can be cleared without surrendering balances.

### Proof of Concept
```solidity
// Hardhat/Foundry fork sketch (mainnet Pool + listed DepositTokens)
// assumption: pool has N listed deposit tokens and MAX_TOKENS_PER_USER = M
function test_dustFillVictimTokenList() public {
    address victim = makeAddr("victim");
    IPool pool = IPool(POOL);

    // victim holds one collateral type with an open position
    // (setup: victim deposits msdA and mints msUSD)

    address[] memory tokens = pool.getDepositTokens(); // listed msdTOKENs
    for (uint i; i < tokens.length; ++i) {
        IDepositToken dt = IDepositToken(tokens[i]);
        if (dt.balanceOf(attacker) == 0) {
            // attacker deposits 1 wei underlying and receives dust msdTOKEN
            deal(address(dt.underlying()), attacker, 1);
            IERC20(dt.underlying()).approve(address(dt), 1);
            dt.deposit(1, attacker);
        }
        // fills a slot in victim's depositTokensOfAccount
        dt.transfer(victim, 1);
    }

    // victim's list is now at MAX_TOKENS_PER_USER

    // victim tries to deposit a collateral type they don't already hold -> reverts
    IDepositToken newDt = IDepositToken(tokens[0]); // any token victim zeroed out
    deal(address(newDt.underlying()), victim, 100e18);
    vm.startPrank(victim);
    IERC20(newDt.underlying()).approve(address(newDt), 100e18);
    vm.expectRevert(IPool.UserReachedMaxTokens.selector);
    newDt.deposit(100e18, victim);
    vm.stopPrank();

    // third-party deposit on behalf of victim also reverts
    vm.expectRevert(IPool.UserReachedMaxTokens.selector);
    newDt.deposit(100e18, victim);

    // while victim is underwater, liquidate() succeeds (seize targets liquidator's
    // list, not victim's), so the attacker collects the liquidation bonus that the
    // victim could have avoided by depositing new collateral
}
```

Note on uncertainty: I confirmed the `transfer → _transfer → addToDepositTokensOfAccount → UserReachedMaxTokens` revert chain and that `deposit`/`_mint` share the same path. I did not verify the exact `MAX_TOKENS_PER_USER` constant value in `PoolStorage.sol` nor whether `deposit` is pausable-gated per token (`onlyIfDepositTokenIsActive` on `_mint` would only narrow, not eliminate, the vector). The revert-during-`_transfer` ordering (balance updates before the pool call) means the whole transfer reverts atomically, which is what makes the DoS airtight.
