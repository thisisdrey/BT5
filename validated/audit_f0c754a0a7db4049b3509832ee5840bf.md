Audit Report

## Title
Missing slippage protection (`amount_out_min = None`) in `swap_and_burn` allows spot-price manipulation of the AssetConversion pool to mint an inflated Snowbridge relayer reward/tip credit - (File: `bridges/snowbridge/pallets/system-frontend/src/lib.rs`)

## Summary
`Pallet::swap_and_burn` in `pallet-snowbridge-system-frontend` invokes `T::Swap::swap_exact_tokens_for_tokens` with the minimum-output parameter hard-coded to `None`, meaning the AMM swap that converts a user-supplied tip/fee asset into ether is priced entirely off the pool's instantaneous spot reserves with zero slippage protection. Because this function is reachable from the fully public, unprivileged `add_tip` extrinsic (and `register_token`), an attacker can atomically manipulate the relevant `pallet-asset-conversion` pool reserves and then execute the swap to extract an inflated `ether_gained`, which is subsequently burned and forwarded to BridgeHub/`EthereumSystem` as the authoritative relayer reward/tip amount.

## Finding Description
`add_tip` (call index 2) requires only `ensure_signed(origin)` — fully public and unprivileged. [1](#0-0) 
It calls `swap_fee_asset_and_burn`, which for any non-ether fee asset calls `swap_and_burn`: [2](#0-1) 

The critical line hard-codes `amount_out_min` to `None`: [3](#0-2) 

The `Swap` trait's documented semantics confirm that `amount_out_min` is the only guard against unfavorable execution price, and passing `None` disables it entirely; the swap withdraws the input asset from `sender` and deposits the output asset to `send_to` purely based on the pool's reserves at execution time: [4](#0-3) [5](#0-4) 

Both the `asset` (including its `AssetId` location) and the tip amount in `add_tip` are fully attacker-controlled, so an attacker can choose a thinly-liquidated pool, sandwich the `add_tip` call within a single atomic `pallet_utility::batch_all` (manipulating swap → `add_tip` → reversing swap), and receive an `ether_gained` far above the asset's true economic value. That inflated value is burned via `burn_for_teleport` and forwarded as the authoritative reward amount in the `AddTip` Transact call to `EthereumSystem` on BridgeHub: [6](#0-5) 

No existing check (e.g., TWAP, delta-bound, or caller-supplied minimum) exists anywhere in this path to catch the manipulated price before it is treated as ground truth for bridge reward accounting.

## Impact Explanation
This breaks the invariant that bridge rewards and AMM settlements must conserve value and settle exactly once at the correct amount. An unprivileged attacker can drain value from `pallet-asset-conversion` liquidity providers via unprotected spot-price manipulation and use the extracted ether to inflate the relayer reward/tip amount (`ether_gained`) reported to `EthereumSystem` on BridgeHub — a wrong-amount settlement of bridge reward funded by manipulated AMM extraction, matching the "public underpriced work" / "duplicate settlement or payout" impact class in the gate.

## Likelihood Explanation
The attack requires no privileged role, validator/collator power, or off-chain infrastructure — only a signed account and the ability to batch a manipulating swap immediately before/after `add_tip` in the same block via `pallet_utility::batch_all`, which is a standard, always-available tool. The exact vulnerable line (`None, // No minimum amount required`) is present in the current code, confirming the path is live and unguarded.

## Recommendation
Never hard-code `None` for `amount_out_min` in `swap_and_burn` when the swap output feeds into bridge reward/settlement accounting. Compute a bound using `quote_price_exact_tokens_for_tokens` and enforce an acceptable maximum deviation, or require the caller to supply an explicit `min_ether_out` parameter that is validated against pool state, consistent with how ordinary AMM swap extrinsics require `amount_out_min`/`amount_in_max`.

## Proof of Concept
1. Attacker identifies or creates a `pallet-asset-conversion` pool `(fee_asset, ether_location)` with shallow relative liquidity.
2. Attacker submits `pallet_utility::batch_all` containing: (a) a large swap skewing the pool reserves to inflate `fee_asset → ether` output, (b) `snowbridge_pallet_system_frontend::add_tip(message_id, fee_asset_amount)`, (c) a reversing swap restoring the pool.
3. Inside `add_tip` → `swap_and_burn`, the exact-input swap executes with `None` minimum output against the skewed reserves, yielding an inflated `ether_gained`.
4. `ether_gained` is burned and forwarded via the `AddTip` Transact call to `EthereumSystem`, crediting a reward disproportionate to the real value contributed, while the attacker's net cost (after step (c)) is near zero aside from AMM fees.
