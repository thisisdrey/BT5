Based on my research, I found a directly analogous bug class in java-tron's TVM precompiled contracts: parsing attacker-controlled ABI word arrays without validating declared lengths/offsets against the actual buffer size, leading to out-of-bounds reads — the same root cause as the GPAC `urn_Read` heap over-read (an unchecked length field driving an out-of-bounds memory access).

### Title
Unbounded array-length and offset fields in TVM precompiled-contract ABI decoding cause out-of-bounds heap reads / node crash - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
`PrecompiledContracts.extractBytes32Array` and `extractBytesArray` decode ABI-encoded dynamic array/bytes parameters supplied as raw `DataWord[]` input to precompiled contracts (e.g. batch signature validation and other multi-arg precompiles reachable by any contract call). Both functions take a declared length or offset directly from attacker-controlled call data via `intValueSafe()` and use it to size/allocate arrays and index into the `words`/`data` buffers without validating that the resulting indices stay within the actual array bounds.

### Finding Description
`extractBytes32Array` reads `len = words[offset].intValueSafe()` and then loops `i < len`, reading `words[offset + i + 1]` for every `i` [1](#0-0) . There is no check that `offset + len + 1 <= words.length`, so a crafted `len` (up to `Integer.MAX_VALUE`, since `intValueSafe()` only guards against negative/overflow to return `Integer.MAX_VALUE`, not against arbitrary large but positive values) will run past the end of the `words` array and throw `ArrayIndexOutOfBoundsException`, or attempt to allocate a `byte[Integer.MAX_VALUE][]` causing `OutOfMemoryError`.

`extractBytesArray` behaves similarly: it reads `len = words[offset].intValueSafe()`, then for each `i` reads `words[offset + i + 1]` to get a `bytesOffset`, and `words[offset + bytesOffset + 1]` to get `bytesLen`, and calls `extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE, bytesLen)` [2](#0-1) . Only the `offset > words.length - 1` case is guarded; none of `len`, `bytesOffset`, or `bytesLen` are bounds-checked against `words.length` or `data.length` before being used to index arrays or size allocations. A crafted call can drive `bytesOffset` or `(bytesOffset + offset + 2) * WORD_SIZE` far outside `data.length`, or make `bytesLen` huge, causing `extractBytes` to over-read or throw.

This mirrors the GPAC `urn_Read` pattern: an attacker-supplied length/offset field read from untrusted input is used directly to index/copy from a buffer without validating it against the buffer's actual size.

### Impact Explanation
Any account can invoke a contract call that reaches these precompile-input decoding routines with crafted `DataWord[]` payloads. Triggering `ArrayIndexOutOfBoundsException` or `OutOfMemoryError` inside VM execution can crash the node process or the execution thread depending on how exceptions from precompile invocation are caught in the TVM dispatch path; if uncaught at a level that isn't wrapped in the standard `Program.Exception`/`ContractExeException` handling, this can produce a denial-of-service against block/transaction processing on any node executing the transaction — a reachable crash triggered by an unprivileged transaction sender.

### Likelihood Explanation
High likelihood of reachability: precompiled contracts are invoked through ordinary `STATICCALL`/`CALL` from any deployed smart contract, meaning any address that can deploy or call a contract using these precompile-consuming ABI helpers can supply the malformed word array. No special privilege (SR/witness/committee) is required — only a signed transaction invoking a contract that calls into the affected precompile function.

### Recommendation
Add explicit bounds validation in `extractBytes32Array` and `extractBytesArray` before using `len`, `offset`, `bytesOffset`, and `bytesLen` to index or size arrays: verify `offset + len + 1 <= words.length` before the loop in `extractBytes32Array`, and verify `bytesOffset`, `bytesLen`, and the computed byte index against `words.length` and `data.length` in `extractBytesArray`, throwing a well-defined execution-revert exception (consistent with other VM bounds checks, e.g. `Program.Exception`) rather than allowing an unchecked `ArrayIndexOutOfBoundsException` or unbounded allocation to propagate.

### Proof of Concept
Construct a contract call whose input data, when decoded into `DataWord[] words` for a precompile that uses `extractBytesArray`/`extractBytes32Array`, places a very large value (e.g. `0xFFFFFFFF`) at the `len` or `offset` word position. When the precompile's execute path calls `extractBytes32Array(words, offset)` or `extractBytesArray(words, offset, data)`, the loop indexes `words[offset + i + 1]` beyond `words.length`, throwing an unhandled `ArrayIndexOutOfBoundsException` (or attempting a huge `byte[][]` allocation), which is not concretely proven here to escape TVM's own exception wrapping without deeper tracing into the specific precompile's caller and the top-level transaction-execution exception handler — this is the primary uncertainty in the analog, since I could not fully confirm within index limits whether all call sites (in `PrecompiledContracts.getContractForAddress` consumers) catch generic `RuntimeException`/`Error` before it escapes to `Manager`'s block-application path.

    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];

    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {

      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();

          bytesLen);
    }
    return bytesArray;
  }
