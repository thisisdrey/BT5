Audit Report

## Title
`do_drop_history` silently discards the `charge` error while still emitting `HistoryDropped` and consuming the payout record - ([File: substrate/frame/broker/src/dispatchable_impls.rs])

## Summary
`Pallet::<T>::do_drop_history` unconditionally removes the `InstaPoolHistory` record via `take(when)` and then attempts to forward the recorded payout to `T::OnRevenue` through `Self::charge`, but discards the fallible result with `let _ = ...`. Regardless of whether the underlying `T::Currency::withdraw` call inside `charge` succeeds or fails, the function proceeds to emit `Event::HistoryDropped { when, revenue }` with the full `maybe_payout` amount and returns `Ok(())`, breaking the "state advances only after settlement succeeds" invariant.

## Finding Description
The code path is: [1](#0-0) 

`InstaPoolHistory::<T>::take(when)` removes the record from storage first, destructively and irreversibly, before any payout attempt is made. If `record.maybe_payout` is `Some(payout)`, `Self::charge(&Self::account_id(), payout)` is called but its `DispatchResult` is thrown away by `let _ = ...`. `charge` itself is fallible: [2](#0-1) 

`T::Currency::withdraw(&who, amount, Exact, Expendable, Polite)` can fail (e.g., insufficient free/withdrawable balance in the pallet account, existential-deposit constraints, or frozen/locked balance), and when it does, `charge` returns `Err`, which is discarded. The function then computes `revenue` from the same `maybe_payout` value irrespective of whether the charge succeeded, emits `Event::HistoryDropped { when, revenue }` asserting the payout occurred, and returns `Ok(())`. There is no atomicity between the destructive `take` and the fallible `charge`, and no error propagation, so the emitted event and the returned success can misrepresent the true settlement outcome.

## Impact Explanation
This matches the "payout state must only advance after settlement succeeds atomically" pivot: the `InstaPoolHistory` record (custody of the revenue-tracking data) is destroyed and a `HistoryDropped` event with a specific `revenue` amount is emitted even when the actual value transfer to `T::OnRevenue` never happened. Because the source record is removed via `take` before the failure can be observed, the payout is unrecoverable and the accounting believed on-chain (via the event) diverges from actual token movement — the intended beneficiary of `T::OnRevenue` receives less than the chain's event log claims. This is a duplicate/incorrect settlement bug rather than a fund-theft bug: it does not mint funds or misdirect them to an attacker, it simply causes silent loss/under-crediting of the specific `payout` amount for that timeslice.

## Likelihood Explanation
`do_drop_history` is reachable once `status.last_timeslice > when + config.contribution_timeout`, which is normal, expected pallet operation and not gated by a privileged origin (per the `ensure!(status.last_timeslice > ..., Error::<T>::StillValid)` check in the same function). However, triggering the actual failure path requires the broker pallet's own account (`Self::account_id()`) to have insufficient free/withdrawable balance relative to `payout` at withdrawal time — a specific internal-accounting condition that is plausible but not certain under any adversarial-only input; it depends on emergent pallet-internal balance conditions rather than a directly attacker-controlled parameter.

## Recommendation
Propagate the error from `Self::charge` instead of discarding it, and avoid destructively taking the `InstaPoolHistory` record until the charge has succeeded (or restore/re-insert the record on failure), e.g.:
```rust
if let Some(payout) = record.maybe_payout {
    Self::charge(&Self::account_id(), payout)?;
}
```

## Proof of Concept
1. Arrange for the broker pallet's account (`Self::account_id()`) to hold less free/withdrawable balance than a scheduled `payout` for some timeslice `when` (e.g., via prior sales/purchases that drew down the account).
2. Wait until `status.last_timeslice > when + config.contribution_timeout` so `StillValid` no longer blocks the call.
3. Call `drop_history(when)`. `InstaPoolHistory::<T>::take(when)` removes the record; `Self::charge` fails inside `T::Currency::withdraw` due to insufficient balance, but the error is discarded by `let _ = ...`.
4. `Event::HistoryDropped { when, revenue: payout }` is emitted and the call returns `Ok(())` even though `T::OnRevenue::on_unbalanced` was never invoked — the payout is lost and unrecoverable since the source record no longer exists.

```rust
	pub(crate) fn do_drop_history(when: Timeslice) -> DispatchResult {
		let config = Configuration::<T>::get().ok_or(Error::<T>::Uninitialized)?;
		let status = Status::<T>::get().ok_or(Error::<T>::Uninitialized)?;
		ensure!(
			status.last_timeslice > when.saturating_add(config.contribution_timeout),
			Error::<T>::StillValid
		);
		let record = InstaPoolHistory::<T>::take(when).ok_or(Error::<T>::NoHistory)?;
		if let Some(payout) = record.maybe_payout {
			let _ = Self::charge(&Self::account_id(), payout);
		}
		let revenue = record.maybe_payout.unwrap_or_default();
		Self::deposit_event(Event::HistoryDropped { when, revenue });
		Ok(())
	}
```

```rust
	pub(crate) fn charge(who: &T::AccountId, amount: BalanceOf<T>) -> DispatchResult {
		let credit = T::Currency::withdraw(&who, amount, Exact, Expendable, Polite)?;
		T::OnRevenue::on_unbalanced(credit);
		Ok(())
	}
```
