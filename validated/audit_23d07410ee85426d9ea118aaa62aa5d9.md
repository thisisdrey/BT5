The Gogs vulnerability class (unsanitized git options accepted from user/attacker-influenced input, enabling unintended git behavior that leaks files outside the intended scope) has a concrete analog in Bazel's git repository-rule submodule handling.

### Title
Git submodule update re-enables `protocol.file.allow=always`, permitting an attacker-controlled `.gitmodules` to read files outside the checkout directory - (File: `tools/build_defs/repo/git_worker.bzl`)

### Summary
`git_repository`/`new_git_repository` with `init_submodules` or `recursive_init_submodules` set invoke `git submodule update --init [--recursive] --checkout --force` with the config override `-c protocol.file.allow=always` explicitly passed on every invocation.

### Finding Description
`update_submodules` in [1](#0-0)  unconditionally sets `protocol.file.allow=always` before running `git submodule update --init [--recursive] --checkout --force`. This config was deliberately reintroduced to work around Git 2.38.1's default restriction (`protocol.file.allow=user`) which upstream Git added specifically to stop local/file-protocol submodule URLs from being used to clone content from arbitrary local paths outside the intended repository (tracked by Bazel as https://github.com/bazelbuild/bazel/issues/17040).

The `.gitmodules` file that drives this command is not trusted, root-repo Starlark - it is content fetched from the remote Git server named in `git_repository(remote = ...)`, i.e. attacker-published repository/branch content that an unprivileged party can serve (a fork, a compromised mirror, or an "untrusted branch CI builds" scenario). The test fixture at [2](#0-1)  shows `.gitmodules` legitimately containing an attacker-influenceable `url = ` field for a submodule, confirming submodule URLs (including relative paths that can escape the checkout, or `file://` absolute paths) come from the fetched repository content itself, not from the `git_repository` rule's Starlark attributes.

Because `protocol.file.allow=always` is force-set on every submodule update, an attacker who controls the content of a git remote that a victim's `git_repository(... init_submodules = True)` or `recursive_init_submodules = True` fetches can declare a submodule pointing at an absolute local path (e.g. `file:///etc` or another sensitive directory on the build machine) in `.gitmodules`. Git will honor this and clone/checkout the pointed-to local directory's contents into the submodule path inside the repository tree, which Bazel then exposes as ordinary repository files consumable by `BUILD` targets - a read outside the intended repository directory driven entirely by attacker-supplied, unsanitized git configuration content.

### Impact Explanation
This allows exfiltration of files from outside the fetched repository into the build's dependency graph (e.g. via a `filegroup`/`genrule` reading the submodule path), matching the Gogs advisory's impact class of "unintended git options" leading to disclosure of files that should not be reachable from git operations on untrusted content. Any secrets, credentials files, or other filesystem content on the machine performing the fetch (typically CI) that is reachable via a local path could be pulled into the build output and observed by whoever controls the malicious remote/branch.

### Likelihood Explanation
Requires only that a build declares `git_repository`/`new_git_repository` with `init_submodules`/`recursive_init_submodules = True` against a remote the attacker can influence (fork, branch, or compromised/hostile git server) - a realistic scenario for CI systems that build from external contributions or third-party git dependencies. No local machine access, credentials, or trusted-root-repo BUILD changes are needed; the attacker only needs to control the content served by the git remote.

### Recommendation
Do not blanket-override `protocol.file.allow` to `always`. Restrict the override to the case that motivated it (local submodules within the same physical filesystem/cache) or scope it more narrowly (e.g. `protocol.file.allow=user` matching upstream Git's safer default, or validate that resolved submodule paths stay within the checkout directory before allowing `file://`/local-path submodules, similar to the `strip_prefix` containment checks already present in `git.bzl`).

### Proof of Concept
1. Attacker hosts (or gets a victim to build from) a git repository containing a `.gitmodules` entry such as:
   ```
   [submodule "leak"]
       path = leak
       url = file:///etc
   ```
2. Victim's `MODULE.bazel`/`WORKSPACE` uses:
   ```
   git_repository(
       name = "dep",
       remote = "<attacker-controlled-remote>",
       branch = "main",
       recursive_init_submodules = True,
   )
   ```
3. On `bazel fetch`/`bazel build`, `update_submodules` runs `git -c protocol.file.allow=always submodule update --init --recursive --checkout --force` [1](#0-0) , which clones `/etc` into `dep/leak`, making its contents available to any `BUILD` target depending on `@dep//leak/...`, extractable via the reproducible `src/test/shell/bazel/starlark_git_repository_test.sh` submodule test harness pattern shown at [3](#0-2)  adapted to point the submodule URL at a local path outside the repository.

def update_submodules(ctx, git_repo, recursive = False):
    if recursive:
        # "protocol.file.allow=always" allows the submodule command clone from a local directory.
        # It's necessary for Git 2.38.1 and assoicated backport versions.
        # See https://github.com/bazelbuild/bazel/issues/17040
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--recursive", "--checkout", "--force")
    else:
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--checkout", "--force")
