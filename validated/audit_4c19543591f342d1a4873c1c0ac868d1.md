Audit Report

## Title
Snowbridge `register_token`/`add_tip` burns the fee/tip on AssetHub before the corresponding BridgeHub message send can fail, permanently losing user funds - (File: `bridges/snowbridge/pallets/system-frontend/src/lib.rs`)

## Summary
`Pallet::register_token` and `Pallet::add_tip` on AssetHub unconditionally burn the user's fee/tip asset via `swap_fee_asset_and_burn` → `burn_for_teleport` before the corresponding `Transact` XCM reaches BridgeHub, where `snowbridge-pallet-system-v2::Self::send` independently calls `OutboundQueue::validate`/`deliver`. Because the AssetHub extrinsic finalizes (and the burn commits) before BridgeHub processes the Transact in a separate, later block, any failure on the BridgeHub side leaves the burned asset permanently and unrecoverably lost with no refund mechanism.

## Finding Description
In `register_token` (call index 1), the fee/tip asset is burned via `Self::swap_fee_asset_and_burn(origin_location.clone(), fee_asset)?` [1](#0-0)  before `Self::send_transact_call` builds and sends the `Transact` XCM to BridgeHub [2](#0-1) . `swap_fee_asset_and_burn` performs the actual withdrawal/burn via `burn_for_teleport::<T::AssetTransactor>` [3](#0-2) . The same pattern applies to `add_tip` (call index 2) [4](#0-3) .

The `Transact` is built with `UnpaidExecution`/no `fallback_max_weight` and no `ReportTransactStatus`, i.e., fire-and-forget with no status reported back to AssetHub [5](#0-4) . On BridgeHub, `EthereumSystem::register_token`/`add_tip` independently calls `Self::send`, which calls `OutboundQueue::validate` and `deliver`, either of which can return `Error::<T>::Send(err)` [6](#0-5) . This happens in BridgeHub's own, later block, entirely disconnected from AssetHub's already-finalized burn — there is no atomicity or rollback path between the two chains.

I verified the actual `OutboundQueue::validate` implementation used by `system-v2` (the v2 outbound queue) only checks message payload size (`SendError::MessageTooLarge`); it does not check halted/operating-mode or channel rate-limits at `validate`/`deliver` time [7](#0-6) . This narrows the realistic failure trigger for `system-v2`'s `Self::send` specifically to `MessageTooLarge`, rather than the broader set of conditions (halted gateway, per-channel rate limiting) suggested in the original report — those checks either don't exist in this v2 pipeline's `validate`/`deliver` path, or apply only at later async processing stages that postpone rather than reject messages (e.g., `process_message_yields_on_max_messages_per_block`). Regardless of the exact trigger, the architectural flaw is real: whatever check ultimately gates successful remote delivery is not verified on AssetHub before the burn commits.

The pallet's own `LostTips` storage on `system-v2` explicitly acknowledges this class of loss for `add_tip`'s second-order accounting failure ("captured here supports implementing a recovery method in the future") [8](#0-7) , but this only tracks failures in applying the tip to a reward after the nonce is already consumed — it does not, and structurally cannot, undo the AssetHub-side burn, and no equivalent tracking exists at all for `register_token`'s `Self::send` failure path.

## Impact Explanation
A user calling `register_token` or `add_tip` on AssetHub permanently loses the swapped/burned ether whenever the corresponding remote command fails on BridgeHub's `Self::send` (e.g., `SendError::MessageTooLarge` from the v2 `OutboundQueue::validate`), with no refund path for `register_token` and only passive, non-recoverable bookkeeping (`LostTips`) for `add_tip`. This is a permanent user-fund loss triggered through ordinary use of an unprivileged public extrinsic, matching the "permanent user-fund... lock" impact class in the Polkadot SDK impact gate.

## Likelihood Explanation
No malicious actor or privileged access is required — any signed account calling `register_token`/`add_tip` can trigger the loss if the BridgeHub-side `Self::send` rejects the message for any reason not checked on AssetHub beforehand. The verified concrete trigger in this codebase is message-size overflow in the v2 `OutboundQueue::validate`; other conditions asserted in the original report (halted operating mode, rate limiting) are not enforced at the `validate`/`deliver` layer for `system-v2` specifically, which somewhat narrows — but does not eliminate — the practical likelihood versus the original claim.

## Recommendation
Validate deliverability (e.g., message-size bounds and any other BridgeHub-side acceptance checks that could plausibly fail) on AssetHub *before* calling `swap_fee_asset_and_burn`, or defer the burn until confirmation of successful remote execution is received (e.g., via `ReportTransactStatus`/query-based confirmation). Alternatively, extend the `LostTips`-style tracking with an actual recovery/refund mechanism that also covers `register_token` and the underlying AssetHub-side burn itself, not just the BridgeHub-side reward-application failure.

## Proof of Concept
1. On AssetHub, call `snowbridge-pallet-system-frontend::register_token` with `metadata` (name/symbol) sized such that the encoded `Message` (including `Command::RegisterForeignToken`) on BridgeHub exceeds `T::MaxMessagePayloadSize` in the v2 outbound queue.
2. Observe `swap_fee_asset_and_burn`/`burn_for_teleport` executes and commits on AssetHub, burning the user's ether-denominated fee [3](#0-2) .
3. The `Transact` XCM reaches BridgeHub; `snowbridge-pallet-system-v2::register_token`'s `Self::send` returns `Error::<T>::Send(SendError::MessageTooLarge)` because `OutboundQueue::validate` rejects the oversized message [9](#0-8) .
4. The registration never lands on Ethereum, and the user's burned fee on AssetHub is not, and cannot be, refunded, since the burn was already finalized in a prior, separate extrinsic on a different chain.

		/// Send `command` to the Gateway from a specific origin/agent
		fn send(origin: H256, command: Command, fee: u128) -> DispatchResult {
			let message = Message {
				origin,
				id: frame_system::unique((origin, &command, fee)).into(),
				fee,
				commands: BoundedVec::try_from(vec![command]).unwrap(),
			};

			let ticket = <T as pallet::Config>::OutboundQueue::validate(&message)
				.map_err(|err| Error::<T>::Send(err))?;

			<T as pallet::Config>::OutboundQueue::deliver(ticket)
				.map_err(|err| Error::<T>::Send(err))?;
			Ok(())
		}

	fn validate(message: &Message) -> Result<Self::Ticket, SendError> {
		// The inner payload should not be too large
		let payload = message.encode();
		ensure!(
			payload.len() < T::MaxMessagePayloadSize::get() as usize,
			SendError::MessageTooLarge
		);

		Ok(message.clone())
	}

	fn deliver(ticket: Self::Ticket) -> Result<H256, SendError> {
		let origin = ticket.origin.into();

		let message =
			BoundedVec::try_from(ticket.encode()).map_err(|_| SendError::MessageTooLarge)?;

		T::MessageQueue::enqueue_message(message.as_bounded_slice(), origin);
		Self::deposit_event(Event::MessageQueued { message: ticket.clone() });
		Ok(ticket.id)
	}
