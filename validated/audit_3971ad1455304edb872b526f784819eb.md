### Title
Uninitialized `accountIndexOf` rewarded as full balance when token index equals `INITIAL_INDEX` - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
`RewardsDistributor._calculateTokenDelta` treats an unset account index as `INITIAL_INDEX` only when the global token index is *strictly greater* than `INITIAL_INDEX`. During the window where a token's index is still exactly `INITIAL_INDEX` (speed just activated, no accrual yet), an account with `accountIndexOf == 0` computes a delta index of `1e18`, crediting them rewards equal to their entire DepositToken/DebtToken balance.

### Finding Description
In `contracts/RewardsDistributor.sol:222-231`:

```solidity
_tokenIndex = _tokenState.index;
uint256 _accountIndex = accountIndexOf[token_][account_];

if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}

uint256 _deltaIndex = _tokenIndex - _accountIndex;
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
```

When `_updateTokenSpeed` first activates a token it stores `TokenState({index: INITIAL_INDEX, timestamp: block.timestamp})` (line 298). The token index only moves above `INITIAL_INDEX` once `_calculateTokenIndex` runs in a *later* block with `speed > 0` and `totalSupply > 0` (lines 202-208). In the same block as activation — or any block where delta timestamp accrues zero — `_tokenIndex == INITIAL_INDEX` and the strict `>` comparison fails, so `_accountIndex` remains `0` and `_deltaIndex = 1e18`. `wadMul(balance, 1e18) = balance`, so `_updateTokensAccruedOf` credits the full token balance as rewards (lines 261-265). `claimRewards` then pays out `tokensAccruedOf` via `_transferRewardIfEnoughTokens` (lines 248-256).

The reference bug is an uninitialized field (skb->mac_header) consumed by a downstream subsystem; analogously here an uninitialized `accountIndexOf` entry (0, the default) is consumed by the reward-delta computation and produces a catastrophic delta instead of being normalized to the initial index.

### Impact Explanation
An attacker who holds (or flash-acquires in the same transaction) a DepositToken or DebtToken balance and calls `claimRewards` before the index first moves above `INITIAL_INDEX` is credited `balance * 1` reward tokens — effectively stealing the distributor's reward-token balance up to their position size, i.e. theft of unclaimed yield belonging to all other users. `claimRewards` is permissionless (line 150, `nonReentrant` only) and iterates `tokens` directly.

### Likelihood Explanation
The window opens every time `_updateTokenSpeed` initializes a token (`index == 0` → set to `INITIAL_INDEX`) and persists for every block in which no successful index update occurs. Speed activation happens through `updateTokenSpeed(s)` (governor) or `syncTokenSpeed` (keeper); both are public mempool transactions an attacker can sandwich in the same block — deposit before, claim after — so `_deltaTimestamps == 0` and the index stays at `INITIAL_INDEX`. No privileged role, oracle manipulation, or malformed arguments are required. The check `tokenStates[_token].index > 0` in `claimRewards`/`updateBeforeMintOrBurn` passes because `INITIAL_INDEX > 0`.

### Recommendation
Use `>=` instead of `>` when normalizing the unset account index, matching the canonical Compound pattern:

```solidity
if (_accountIndex == 0 && _tokenIndex >= INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}
```

Alternatively, explicitly initialize `accountIndexOf[token_][account_] = INITIAL_INDEX` the first time an account interacts with a newly activated token.

### Proof of Concept
Hardhat sketch (real deployments exist on mainnet/base/optimism per `deployments/*`):

```typescript
// given: pool, depositToken (msdMET), rewardsDistributor deployed & registered
// attacker deposits before speed activation
await met.mint(attacker.address, parseEther('1000'));
await met.connect(attacker).approve(depositToken.address, MaxUint256);
await depositToken.connect(attacker).deposit(parseEther('1000'), attacker.address);

// rewards funded
await rewardToken.mint(rewardsDistributor.address, parseEther('10000'));

// when: governor activates speed and attacker claims in the same block
await setAutomine(false);
await rewardsDistributor.connect(governor).updateTokenSpeed(depositToken.address, parseEther('1'));
await rewardsDistributor.connect(attacker).claimRewards(attacker.address, [depositToken.address]);
await mineBlock();

// then: attacker was credited balance * INITIAL_INDEX delta = full deposit balance
expect(await rewardToken.balanceOf(attacker.address)).to.eq(parseEther('1000'));
expect(tokensAccruedOf(attacker)).to.eq(0); // paid out up to distributor balance
```

Root cause is the strict inequality at `contracts/RewardsDistributor.sol:225`; flipping it to `>=` makes the same claim yield zero tokens.
