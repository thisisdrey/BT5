### Title
SetCustomHooks tar extraction accepts a symlink named `custom_hooks`, causing the repository's `custom_hooks` path to be replaced by an attacker-controlled symlink - ([File: internal/gitaly/repoutil/custom_hooks.go])

### Summary
`SetCustomHooks` extracts an attacker-supplied tar via the external `tar` binary [1](#0-0)  without validating the type of the top-level `custom_hooks` entry. If the entry is a `TypeSymlink` pointing to an arbitrary path, the subsequent `os.Mkdir` call tolerates the pre-existing path (via `fs.ErrExist`), and the final `os.Rename(tempHooksPath, repoHooksPath)` moves the symlink itself into the repository, replacing what should be a plain directory with an attacker-chosen symlink target.

### Finding Description
In `SetCustomHooks`, hooks are extracted into a fresh temp directory using the `tar` CLI with `--strip-components 0` and the `custom_hooks` member name [2](#0-1) . Nothing filters tar entry types (regular file, dir, symlink) before or after extraction. If the attacker's tar stream contains a single `TypeSymlink` header named `custom_hooks` pointing at an arbitrary path (e.g. `/dev/null`, or any other host path), GNU/BSD `tar` will create that symlink at `tempHooksPath` inside the fresh temp directory.

Next, `os.Mkdir(tempHooksPath, mode.Directory)` fails because a filesystem entry (the symlink) already exists at that path, but the error is silently swallowed because it satisfies `errors.Is(err, fs.ErrExist)` [3](#0-2) . The code proceeds as if `tempHooksPath` were a normal (possibly pre-existing empty) directory.

`newDirectoryVote(tempHooksPath)` then walks `tempHooksPath` with `filepath.WalkDir`, which uses `Lstat` semantics for the root entry, so the symlink is treated as a non-directory entry; the code calls `os.Open(path)` on it, which *does* follow the symlink [4](#0-3) . As long as the symlink target exists and is readable (trivially satisfied by pointing at `/dev/null` or any world-readable file), this succeeds and voting proceeds normally — no error is raised here to block the attack.

Finally, `os.Rename(tempHooksPath, repoHooksPath)` is executed [5](#0-4) . Per POSIX `rename(2)` semantics, when the source path is itself a symlink, the *link* is renamed, not its target's contents — no dereference occurs. Consequently, `repoHooksPath` (the repository's real `custom_hooks` directory) is replaced by a symlink pointing to whatever string the attacker's tar header specified, rather than the confined, plain directory the code assumes. No check anywhere in `SetCustomHooks` verifies that `tempHooksPath`/`repoHooksPath` is a plain directory (not a symlink) before or after these operations, so the intended invariant ("hook directory writes are confined and atomic; no symlink following during the final rename step") is violated at the type-check level, even though the specific `os.Rename` call does not itself dereference the symlink.

### Impact Explanation
This corrupts the repository's `custom_hooks` on-disk representation: it becomes a symlink instead of a directory, and its target string is entirely attacker-controlled. Concretely:
- `GetCustomHooks`/backup flows that `Lstat`/tar up `CustomHooksDir` will archive a dangling/foreign symlink entry instead of the expected directory, corrupting hook state and future `SetCustomHooks` idempotency assumptions.
- If the attacker can arrange (through any other means) for the symlink target to be a directory that resolves to files literally named `pre-receive`, `update`, `post-receive`, etc. (following the hook lookup logic in `newCustomHooksExecutor`, which does follow symlinks per `TestCustomHooksWithSymlinks` [6](#0-5) ), this could lead to execution of hooks from outside the repository's intended, tar-verified location — a hook/quarantine-confinement bypass. I could not find, however, a concrete secondary primitive in this codebase that lets an unprivileged user place arbitrary executable files at a self-chosen absolute path on the Gitaly host, so full remote code execution is not proven here; the confirmed, reproducible impact is directory-confinement corruption/escape of the `custom_hooks` path away from the repository, which matches the "hook or quarantine bypass" / storage-confinement class at a moderate severity.

### Likelihood Explanation
Any unprivileged user who can invoke `SetCustomHooks`/`RestoreCustomHooks` on a repository they control (a normal, documented capability, e.g. via project import/restore flows) can supply this crafted tar; no special role or host access is required [7](#0-6) . The exploit is deterministic and repeatable — it does not depend on winning a race against the `hooksLock`, since the symlink is created inside a freshly-allocated temp directory that only `SetCustomHooks` itself touches before the final rename.

### Recommendation
After extraction, explicitly verify that `tempHooksPath` is a real directory (e.g. `os.Lstat` and check `info.Mode()&os.ModeSymlink == 0` and `info.IsDir()`) and reject the request (returning an error) if it is a symlink or any non-directory type, instead of only checking `errors.Is(err, fs.ErrExist)` on `os.Mkdir`. Additionally, `ExtractHooks` should reject or strip symlink (and other special) entries from the tar stream before/while extracting (e.g., using GNU tar's member filtering or switching to Go's `archive/tar` reader with explicit type checks) so that no symlink can ever be written into the temp hooks directory in the first place.

```go
func TestSetCustomHooks_SymlinkEntry(t *testing.T) {
    ctx := testhelper.Context(t)
    cfg := testcfg.Build(t)
    repo, repoPath := gittest.CreateRepository(t, ctx, cfg, gittest.CreateRepositoryConfig{
        SkipCreationViaService: true,
    })

    var tarBuf bytes.Buffer
    tw := tar.NewWriter(&tarBuf)
    require.NoError(t, tw.WriteHeader(&tar.Header{
        Name:     "custom_hooks",
        Typeflag: tar.TypeSymlink,
        Linkname: "/dev/null",
        Mode:     0777,
    }))
    require.NoError(t, tw.Close())

    locator := config.NewLocator(cfg)
    err := repoutil.SetCustomHooks(ctx, testhelper.NewLogger(t), locator, txManagerStub, &tarBuf, repo)
    require.NoError(t, err) // currently succeeds

    fi, lerr := os.Lstat(filepath.Join(repoPath, "custom_hooks"))
    require.NoError(t, lerr)
    // Demonstrates the invariant break: custom_hooks is now a symlink, not a directory.
    require.NotZero(t, fi.Mode()&os.ModeSymlink, "custom_hooks should not be a symlink")
}
```
Expected (fixed) behavior: `SetCustomHooks` should return an error and `custom_hooks` should remain a genuine directory. Currently, the call succeeds and `custom_hooks` becomes a symlink to the attacker-specified path.

func (s *server) SetCustomHooks(stream gitalypb.RepositoryService_SetCustomHooksServer) error {
	ctx := stream.Context()

	firstRequest, err := stream.Recv()
	if err != nil {
		return structerr.NewInternal("getting first request: %w", err)
	}

	repo := firstRequest.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repo); err != nil {
		return structerr.NewInvalidArgument("%w", err)
	}

	reader := streamio.NewReader(func() ([]byte, error) {
		if firstRequest != nil {
			data := firstRequest.GetData()
			firstRequest = nil
			return data, nil
		}

		request, err := stream.Recv()
		return request.GetData(), err
	})

	if err := repoutil.SetCustomHooks(ctx, s.logger, s.locator, s.txManager, reader, repo); err != nil {
		return structerr.NewInternal("setting custom hooks: %w", err)
	}

	return stream.SendAndClose(&gitalypb.SetCustomHooksResponse{})
