### Title
`mt_resolve_withdraw` treats a malformed-length `mt_batch_transfer_call` response as "zero delivered" and issues a full refund, even when the underlying transfer actually succeeded - `contracts/defuse/src/contract/tokens/nep245/withdraw.rs`

### Summary
`mt_resolve_withdraw` distinguishes three outcomes of the callback promise: a well-formed `used` array (trusted), a promise `Err` (treated as full refund, documented as intentional for gas-exhaustion safety), and any other `Ok` result — including a *malformed-length* JSON array — which is silently collapsed to `vec![U128(0); amounts.len()]`, i.e. "nothing was delivered." Because the attacker fully controls the external `token` contract passed to `mt_withdraw`, they can make `mt_batch_transfer_call` actually move the real, previously-deposited tokens to `receiver_id` while returning an array of the wrong length, causing the resolver to refund the full amount back into the sender's ledger balance without any real backing left on the token contract.

### Finding Description
The broken binding is:
`real_tokens_moved_out_of_Defuse_on(token, token_ids)` (by the executed `mt_batch_transfer_call`) **should equal** `amounts_used_returned_to_caller` (which drives how much is *not* refunded into `token_balances`/`total_supplies`).

Code path:
- `internal_mt_withdraw` debits the sender's ledger via `self.withdraw(...)` [1](#0-0) , then schedules `do_mt_withdraw` → `mt_batch_transfer_call` on the attacker-supplied `token` contract [2](#0-1) , followed by `mt_resolve_withdraw` as the callback.
- In `mt_resolve_withdraw`, the callback result is parsed with `promise_result_checked_json_with_len::<Vec<U128>>(0, amounts.len())`. Only the exact-length success path is trusted; any other `Ok(_)` — including a parsed array whose length differs from `amounts.len()` — falls into `vec![U128(0); amounts.len()]`, meaning the resolver assumes **zero tokens were delivered**: [3](#0-2) .
- `used` (all zero) then drives `self.deposit(sender_id, ..., refund = amount - used = amount ...)`, refunding the **entire withdrawn amount** back into the sender's `token_balances` / `total_supplies` via `REFUND_MEMO`: [4](#0-3) .

The flaw is that this fallback conflates "the response was malformed" with "nothing was transferred." Since `mt_batch_transfer_call` is an ordinary cross-contract call to an arbitrary, attacker-supplied `token` account, the actual state-changing side effect (moving Defuse's real NEP-245 balance to `receiver_id`) is entirely independent of what JSON the callee chooses to return. An attacker deploying `ATTACKER_MT` can implement `mt_batch_transfer_call` to genuinely execute the transfer (moving Defuse's real custodied balance to `ATTACKER_RECEIVER`) while returning a `used` array of the wrong length (e.g. 1 element instead of 2, or any shape that fails the `used.len() == amounts.len()` check). The resolver then refunds the ledger in full, so `total_supplies`/`token_balances` for `Nep245TokenId(ATTACKER_MT, t1/t2)` end up unchanged from before the withdraw, while the real backing tokens on `ATTACKER_MT` have already left Defuse's custodied account. This exactly matches the rule's Critical category: "a batch whose balance changes do not net to zero so the Verifier owes more than it custodies" / "a refund or resolver credit that does not match what failed to settle."

Existing guards do not stop this: `require!(token_ids.len() == amounts.len() && !amounts.is_empty())` only validates the callback's *own arguments*, not the returned `used` array shape [5](#0-4) ; the `Err(_)` branch's documented rationale (avoid punishing sender for gas-starved `mt_on_transfer`) does not apply to the malformed-`Ok` branch, which has no such safety justification and instead assumes the least trustworthy outcome (zero delivered) purely based on JSON shape, not on-chain effect.

### Impact Explanation
The internal ledger ends up crediting the sender for tokens that were already, in reality, transferred out of Defuse's custody to `receiver_id` on the attacker's own token contract. This produces an unbacked (fake) `token_balances`/`total_supplies` entry for `Nep245TokenId(ATTACKER_MT, t1/t2)` inside the Verifier. That fabricated ledger credit is fungible within the intents system (transferable, tradeable via `TransferMatcher`/swap intents), so it can later be exchanged with other, unrelated Defuse users for real assets, extracting genuine value from the Verifier/counterparties while the underlying claim can never actually be redeemed for real tokens (a subsequent real withdraw attempt will fail on-chain since Defuse no longer custodies the real balance, and will itself loop into another full refund via the `Err(_)` branch). This is a genuine conservation violation ("Verifier owes more than it custodies") — Critical severity — repeatable for any attacker-deployed NEP-245 token and any amount the attacker chooses to first legitimately deposit and then "re-mint" via this bug.

### Likelihood Explanation
Preconditions: the attacker must (1) deploy their own NEP-245 contract (`ATTACKER_MT`), (2) perform a real, legitimate deposit of `t1`/`t2` tokens into Defuse so that `token_balances` for `Nep245TokenId(ATTACKER_MT, t1/t2)` are genuinely backed, then (3) call `mt_withdraw` with `msg = Some(...)` to trigger the `mt_batch_transfer_call` (call) path, with `ATTACKER_MT`'s `mt_batch_transfer_call` implemented to actually deliver the tokens to `ATTACKER_RECEIVER` while returning a `used` array of the wrong length. All of this is achievable by an unprivileged account with no special roles, no relayer key, and no victim key — it only requires deploying and controlling a contract, which is explicitly within the described attacker capability. The attack is fully deterministic and repeatable across tokens/amounts/batches.

### Recommendation
Do not default an `Ok` result with a malformed/mismatched-length payload to "zero delivered." Either: (a) treat any malformed `Ok` response the same as the documented `Err(_)` case (assume the transfer *may have* succeeded and do not refund), or (b) require the resolver to independently verify custody (e.g., via a follow-up balance check on the token contract) before crediting any refund, or (c) at minimum, make the malformed-length case panic/abort the refund credit rather than silently assuming zero-used, forcing manual reconciliation instead of an automatic full refund that can diverge from real on-chain custody.

### Proof of Concept
`cargo test` plan (near-workspaces sandbox):
1. Deploy the Defuse contract and a custom `AttackerMt` NEP-245 contract whose `mt_batch_transfer_call` implementation:
   - performs a real `mt_transfer`-equivalent internal state update crediting `receiver_id` (`ATTACKER_RECEIVER`) with the full `amounts`,
   - returns a JSON array of length `amounts.len() - 1` (or any length `!= amounts.len()`) instead of the expected `used` array.
2. Have the attacker deposit `(AttackerMt, t1)=100` and `(AttackerMt, t2)=200` into Defuse via a legitimate `mt_transfer_call`, asserting `token_balances(sender, Nep245TokenId(AttackerMt,t1))==100` and `...t2)==200` post-deposit.
3. Call `mt_withdraw(token=AttackerMt, receiver_id=ATTACKER_RECEIVER, token_ids=[t1,t2], amounts=[100,200], msg=Some("..."))`.
4. Assert both sides of the binding after resolution:
   - LHS (`real_tokens_moved_out_of_Defuse_on(AttackerMt, [t1,t2])`): query `AttackerMt`'s internal balance record showing `receiver_id` actually received 100/200 (i.e., Defuse's real custodied balance on `AttackerMt` decreased by 100/200).
   - RHS (`token_balances(sender, Nep245TokenId(AttackerMt,t1/t2))` after `mt_resolve_withdraw`): assert it is fully restored to 100/200 (full refund), i.e. unchanged from step 2, and `total_supplies` for those `TokenId`s is likewise unchanged from before the withdraw.
   - Assert LHS != 0 while RHS == pre-withdraw value, demonstrating the sender's ledger claim is no longer backed by Defuse's actual custody on `AttackerMt`, violating the conservation invariant.
