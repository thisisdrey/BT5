### Title
Missing binding between `CreateRelayRequest`'s claimed `RelayFromAddr` and the authenticated sender allows relay-state spoofing/poisoning - (File: `relay_manager.go`)

### Summary
The external report describes a bug class where a contract trusts signed/self-declared data (a permit) without verifying that the entity submitting the transaction is actually the party the data claims to represent. The Nebula analog is in `relayManager.handleCreateRelayRequest`: the `NebulaControl_CreateRelayRequest` message body carries a self-declared `RelayFromAddr` field, but the handler never verifies that this claimed VPN address matches the VPN address of `h`, the actually-authenticated `HostInfo` that delivered the message over its own end-to-end Noise session.

### Finding Description
`relayManager.HandleControlMsg` dispatches an inbound `Control` message to `handleCreateRelayRequest(v, h, f, msg)`, where `h` is the `HostInfo` whose `ConnectionState` successfully decrypted/authenticated the packet (i.e., `h.vpnAddrs[0]` is the cryptographically-verified identity of the sender) [1](#0-0) .

Inside `handleCreateRelayRequest`, the code reads `from := protoAddrToNetAddr(m.RelayFromAddr)` directly out of the attacker-controlled message payload and uses it as the claimed originating VPN address of the relay, without ever checking `from == h.vpnAddrs[0]`: [2](#0-1) 

When the local node is the relay target, it immediately builds and establishes relay state keyed by this unverified `from` address, using the attacker-supplied `m.InitiatorRelayIndex` as the remote index, with state `Established` right away — no handshake or additional proof that `from` is who the sender claims: [3](#0-2) 

The same unverified `from` value is also propagated when the node is acting as an intermediate relay, seeding `peer.relayState` for an arbitrary claimed victim address and forwarding a new `CreateRelayRequest` on that victim's behalf: [4](#0-3) 

This mirrors the reported pattern exactly: a cryptographically authenticated channel (`h`, analogous to `msg.sender`) carries a payload that separately claims an identity (`RelayFromAddr`, analogous to the permit's signed "owner"), and the code never checks that the two match.

### Impact Explanation
Any peer that has completed a normal handshake with a node (i.e., any authenticated `h`) can claim an arbitrary `RelayFromAddr` belonging to a victim VPN address that has no relationship with the attacker at all. This causes the victim's relay bookkeeping (`h.relayState` / `peer.relayState`, keyed by VPN address) to be created and marked `Established` on the local and/or intermediate node without the victim's participation. This is remote relay/hostmap state poisoning: it can pre-empt or collide with the victim's legitimate relay establishment, misdirect relay routing decisions (`QueryRelayForByIp`/`QueryVpnAddrsRelayFor`), and be used to exhaust relay index slots tied to arbitrary victim addresses — all triggerable by any already-connected peer with no further authorization check.

### Likelihood Explanation
High reachability: any peer that can complete a normal handshake with a relay-capable node (`am_relay: true`) can send this `Control` message at will; the vulnerable code path is reached on every `NebulaControl_CreateRelayRequest`, and the only validations performed are nil-checks on `RelayFromAddr`/`RelayToAddr` and whether `from`/`target` equal the local node's own addresses — never whether `from` equals the sender's authenticated identity.

### Recommendation
In `handleCreateRelayRequest` (and correspondingly in `handleCreateRelayResponse`), reject the message unless the claimed `RelayFromAddr` equals `h.vpnAddrs[0]` (the sender's own cryptographically verified VPN address) for the case where the message is a fresh, non-forwarded request the sender is originating. For genuinely multi-hop forwarded requests, track and verify the actual originator/relay chain instead of trusting a self-declared field, so relay state can never be created or marked `Established` for a VPN address that isn't provably tied to the authenticated identity that sent the control message.

### Proof of Concept
1. Attacker `H` establishes a normal, legitimate Nebula tunnel/handshake with target node `T` (so `T` has a `HostInfo h` for `H` with `h.vpnAddrs[0] = H`).
2. `H` sends `T` a `Control` message of type `NebulaControl_CreateRelayRequest` with `RelayFromAddr = V` (an arbitrary victim VPN address unrelated to `H`) and `RelayToAddr = T`'s own VPN address, and an attacker-chosen `InitiatorRelayIndex`.
3. `T`'s `handleCreateRelayRequest` sees `target == T` (itself), never checks `from (V) == h.vpnAddrs[0] (H)`, and calls `AddRelay(..., h, f.hostMap, V, &m.InitiatorRelayIndex, TerminalType, Established)` — creating an `Established` relay entry on `h` claiming to relay for `V`, keyed by `H`'s connection [5](#0-4) .
4. `T` replies with a `CreateRelayResponse` believing a legitimate relay for `V` now exists through `H`, even though `V` never requested or consented to this relay, poisoning `T`'s relay/hostmap state for `V`.
