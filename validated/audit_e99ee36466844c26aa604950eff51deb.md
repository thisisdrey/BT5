### Title
GET /v2/attachments/{hash} serves content without re-verifying Hash160(content) == requested hash - ([File: stackslib/src/net/api/getattachment.rs])

### Summary
`RPCGetAttachmentRequestHandler::try_handle_request` fetches an attachment solely by trusting the SQL `hash` column returned by `AtlasDB::find_attachment`, and never recomputes `Hash160::from_data(&attachment.content)` to compare against the requested `attachment_hash` path parameter before wrapping it in `GetAttachmentResponse`. If any prior write ever stored a `(hash, content)` pair where `hash != Hash160::from_data(content)`, this endpoint will serve mismatched content under the requested hash with no detection.

### Finding Description
The handler decodes `attachment_hash` from the URL, calls `network.get_atlasdb().find_attachment(&attachment_hash)`, and on `Ok(Some(attachment))` immediately returns `GetAttachmentResponse { attachment }` with no equality check against `attachment_hash`: [1](#0-0) 

There is no call to `Hash160::from_data` anywhere in this handler - the only trust anchor is whatever the SQL row returns for the `hash` column keyed on the lookup. The outbound wire format further compounds this: `GetAttachmentResponse`'s `Serialize` impl only emits the hex-encoded `content` field - the `hash` is not even part of the payload sent to the client: [2](#0-1) 

and on the client side, `Deserialize` reconstructs an `Attachment` purely from the received bytes via `Attachment::new(bytes)`, with no verification against the hash used to build the original request: [3](#0-2) 

So neither the server (before responding) nor the client (after receiving) validates that the returned content actually hashes to the requested/expected `Hash160`. If a poisoned row (hash, content) with `hash != Hash160::from_data(content)` exists in the `attachments` table (established via the referenced download.rs Done-branch write path), this handler will happily serve that mismatched content as if it were canonical data for the requested hash.

### Impact Explanation
Any legitimate follower node querying `GET /v2/attachments/{hash}` for a BNS zonefile hash can be served attacker-influenced content that does not actually hash to the value it claims to represent. Since Atlas attachments back BNS zonefile resolution, this is a "serving non-canonical state as canonical" / "attachment/BNS mismatch" issue, matching the High severity category. This is repeatable for every subsequent GET request against the poisoned hash, and affects any node/client trusting this RPC response.

### Likelihood Explanation
This finding is entirely dependent on the precondition that a poisoning write into the `attachments` table has already occurred (documented separately for the `download.rs` Done-branch). Given that precondition, exploitation of this specific endpoint requires zero additional privilege: any remote party who can reach the node's RPC port and issue a plain `GET /v2/attachments/{hash}` will receive the mismatched content, since the handler performs no verification step and the response format doesn't carry the hash for client-side cross-checking either.

### Recommendation
In `RPCGetAttachmentRequestHandler::try_handle_request`, after `find_attachment` returns `Some(attachment)`, recompute `Hash160::from_data(&attachment.content)` and compare it to `attachment_hash`; if they differ, treat it as "not found"/log a data-integrity error instead of returning `GetAttachmentResponse`. Additionally, harden `AtlasDB` insert paths to enforce `hash == Hash160::from_data(content)` at write time (defense in depth) rather than relying solely on read-time re-verification.

### Proof of Concept
1. In a Rust net test, construct an `AtlasDB` (e.g., via `AtlasDB::connect_memory` or equivalent test helper used in `stackslib/src/net/atlas/tests.rs`).
2. Directly execute an `INSERT INTO attachments (content, hash, ...) VALUES (?1, ?2, ...)` with a `content` blob and a `hash` value that is NOT `Hash160::from_data(&content)`.
3. Build a `StacksNodeState`/mock network wrapping this AtlasDB, and invoke `RPCGetAttachmentRequestHandler::try_handle_request` with `StacksHttpRequest::new_getattachment(host, mismatched_hash)`.
4. Decode the response via `StacksHttpResponse::decode_atlas_get_attachment`, then assert `Hash160::from_data(&resp.attachment.content) != mismatched_hash` — demonstrating the handler served content that does not match the requested hash, with no error raised.
