### Title
Unbounded array-length field from transaction calldata drives unguarded `new byte[len][]` allocation in TVM precompile signature extraction, enabling attacker-triggered `OutOfMemoryError`/`NegativeArraySizeException` denial of service - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `ValidateMultiSign` precompiled contract (address `0x100...100e`-style TVM precompile invoked via `CALL`/`STATICCALL` from any smart contract) extracts a signature-count field directly from attacker-supplied calldata and uses it, without any upper-bound validation, to allocate a Java object array (`new byte[len][]`) *before* entering the method's only `try { … } catch (Throwable t)` block. This mirrors the CVE-2016-9844 bug class: a length/type field taken from untrusted input is used to size a buffer/array without a sanity check, causing a crash.

### Finding Description
`extractBytesArray` and `extractSigArray` in `PrecompiledContracts.java` read a length word directly from the parsed `DataWord[]` array and allocate accordingly: [1](#0-0) [2](#0-1) 

`ValidateMultiSign.execute()` calls `extractBytesArray` (legacy path, taken whenever `VMConfig.allowTvmSelfdestructRestriction()` is disabled) with an offset/length taken straight from `words[3]`, and only performs a `sigArraySize > MAX_SIZE` bound check when the `allowTvmSelfdestructRestriction` feature switch is *on*. When it is off, `extractBytesArray` runs with a fully attacker-controlled `len` (up to `Integer.MAX_VALUE` via `intValueSafe()`), and this call sits **outside** the method's only exception guard, which starts several lines later at the `account.getPermissionById` block: [3](#0-2) 

Because `new byte[len][]` with a large `len` allocates an object-reference array (8 bytes/entry on a 64-bit JVM, i.e. up to ~17 GB for `len` near `Integer.MAX_VALUE`), this either throws `NegativeArraySizeException` (for negative `len`) or `OutOfMemoryError` (for a large positive `len`). Both are uncaught at this call site — `NegativeArraySizeException` is a `RuntimeException` not wrapped by any guard here, and `OutOfMemoryError` is a JVM `Error` that even a generic `catch (Throwable t)` further down would not help with since it is thrown *before* that block is reached.

### Impact Explanation
An uncaught `OutOfMemoryError`/`NegativeArraySizeException` thrown mid-way through TVM precompile execution, triggered by a smart-contract call that any unprivileged account can construct and broadcast, risks: (a) transaction-processing thread crash with unpredictable propagation through the actuator/VM call stack and `Manager` block application, and (b) genuine heap exhaustion from repeated large-array allocation attempts, degrading or halting the node's ability to process further transactions/blocks — a denial-of-service outcome directly analogous to "buffer overflow ... allows remote attackers to cause a denial of service (crash)" in the reference CVE. This qualifies under the "node crash or halt" acceptance criterion.

### Likelihood Explanation
Reachability requires only that `VMConfig.allowTvmSelfdestructRestriction()` be disabled (i.e., the corresponding TIP has not been activated on the target network/chain parameters) — a realistic condition on chains that haven't rolled out that particular hard fork flag, or during any historical window before it was enabled. Given that flag state, exploitation requires nothing more than a single `CALL` to the `validatemultisign` precompile address with crafted calldata encoding a huge `bytes[]` length word at the signatures-array head, well within reach of any contract deployer/caller. I was not able to fully confirm, within the available tool budget, whether `Program.callToPrecompiledAddress` (the caller of `contract.execute()`) wraps the call in a catch-all that could contain an `Error`/`RuntimeException` thrown at this point; this is the main remaining uncertainty affecting exact blast radius, though `OutOfMemoryError` in particular is not interceptable by ordinary `Exception` handlers even if such a guard exists.

### Recommendation
In `extractBytesArray`/`extractSigArray`/`extractBytes32Array`, validate `len` against a small sane maximum (e.g., the same `MAX_SIZE` constants already used by `ValidateMultiSign`/`BatchValidateSign`) and against remaining `words.length` *before* allocating, regardless of the `allowTvmSelfdestructRestriction` feature flag state, so the bound check is unconditional rather than gated behind a hard-fork switch. Additionally, wrap the extraction calls themselves inside the existing `try/catch(Throwable)` guard in `ValidateMultiSign.execute()` (and equivalent call sites) so that any legacy/unguarded path still fails safely by returning `DATA_FALSE` instead of propagating an `Error`/`RuntimeException`.

### Proof of Concept
1. Ensure the target node/chain has `allowTvmSelfdestructRestriction` disabled (default/legacy state, or pre-activation window of that TIP).
2. Deploy or use any contract, or send a raw `CALL`/`STATICCALL` transaction targeting the `validatemultisign(address,uint256,bytes32,bytes[])` precompile address.
3. Encode calldata per that ABI, but instead of a normal `bytes[]` array, set the length word for the `bytes[]` array (the word at the offset pointed to by the 4th head word) to a very large value (e.g., `0x7FFFFFFF`), while otherwise keeping the head words self-consistent enough to pass `DataWord.parseArray` / `isValidAbiEncoding` (when `allowTvmOsaka` is disabled, this second check is skipped entirely).
4. Broadcast the transaction (or invoke as a constant call from any API/RPC client). During `ValidateMultiSign.execute()`, `extractBytesArray(words, offset, rawData)` executes `new byte[0x7FFFFFFF][]`, throwing `OutOfMemoryError` (or `NegativeArraySizeException` for a crafted negative offset word) before the method's `try/catch(Throwable)` block is reached, propagating out of `execute()` uncaught by that method.
