## Title
Out-of-bounds read parsing ZIP central-directory extra fields with no bounds/overflow check against the buffer end — (File: third_party/ijar/zip.cc)

### Summary
`InputZipFile::ProcessCentralDirEntry` in ijar's zip reader parses per-entry "extra field" records (attacker-controlled bytes from a downloaded/extracted `.jar`/`.zip`/`http_archive`) using a manual pointer loop with no validation that each record's declared `data_size` stays within the extra-field region or the mapped file, mirroring the HAProxy CVE-2018-20102 pattern of trusting a length field from untrusted, attacker-served data without a bounds check before reading past it.

### Finding Description
`ProcessCentralDirEntry` reads `file_name_length`, `extra_field_length`, and `file_comment_length` directly from the central directory header bytes, computes `extra_p`/`p` pointers from them, and then walks the "extra field" list: [1](#0-0) 

```
p += 16;
*compressed_size = get_u4le(p);
...
u2 extra_field_length = get_u2le(p);
...
const u1 *extra_p = p;
p += extra_field_length;
while (extra_p != p) {
  const u2 header_id = get_u2le(extra_p);
  const u2 data_size = get_u2le(extra_p);
  const u1 *extra = extra_p;
  extra_p += data_size;
  ...
}
```

Unlike the equivalent bounds-checked parser in `src/tools/singlejar/zip_headers.h`'s `ExtraField::find` (which explicitly checks `start + size() > end` before dereferencing) [2](#0-1) , this ijar loop has **no check** that `extra_p + 4 + data_size <= p` (the declared end of the extra-field region) nor that it stays within the mapped file bounds. Because `data_size` is a raw `uint16_t` taken from attacker-controlled bytes, a hostile ZIP entry can set `data_size` to a value that makes `extra_p` overshoot `p`:
- The loop condition `extra_p != p` can then never become true again (the pointers "skip past" each other), causing the loop to keep reading `header_id`/`data_size` from memory beyond the declared extra-field region and potentially beyond the mapped file (the analog to HAProxy's OOB read into "the non-initialized part of the buffer... or even past the end of the buffer").
- If `header_id == ZIP64_EXTRA_FIELD_TAG`, `get_u8le(extra)` reads 8 bytes from `extra`, again with no verification that 8 bytes remain within the extra-field record or file, directly paralleling the AAAA-record fixed-size read in the HAProxy bug.

This code path is reached whenever Bazel extracts a `.jar`/`.aar`/`.zip` via `ijar`/singlejar tooling on content fetched from an untrusted URL (e.g., `http_archive`, `http_jar`, `download_and_extract`), i.e., content from a hostile origin server or a malicious file on an untrusted branch, which is within the stated threat model.

### Impact Explanation
A successful overshoot causes reads beyond the intended extra-field buffer, and potentially beyond the memory-mapped file region backing the ZIP, which can crash the build (SIGSEGV) or leak adjacent process memory content into derived output (e.g., if such data influences copied fields like `uncompressed_size`/`compressed_size`/`offset` for Zip64, corrupting downstream artifact metadata). This is a memory-safety/out-of-bounds-read class issue analogous to CVE-2018-20102, reachable purely from attacker-supplied archive bytes.

### Likelihood Explanation
Likelihood is limited by the fact that the checksum (`sha256`/`integrity`) verification in `http_archive`/`download_and_extract` happens on the raw downloaded bytes before extraction, but does not validate ZIP structural fields — a malicious mirror/attacker publishing content and providing a matching checksum in the corresponding lockfile/attributes (or simply an attacker who controls both the archive and the hash the victim pins, e.g., a first-time `http_archive` add with attacker-supplied `sha256`) can still trigger this on extraction, since integrity checks bind file bytes, not internal structural well-formedness.

### Recommendation
Add explicit bounds checks in the extra-field parsing loop in `third_party/ijar/zip.cc::ProcessCentralDirEntry`, analogous to `ExtraField::find` in `zip_headers.h`: before reading `header_id`/`data_size`, verify `extra_p + 4 <= p`; after computing `data_size`, verify `extra_p + data_size <= p` (and that `p` overall stays within the mapped file) before advancing or dereferencing `extra`. Reject/error out the archive on violation rather than continuing to parse.

### Proof of Concept
I could not construct and verify a compilable, reproducible JUnit/shell test within the available tool budget confirming an actual crash/OOB read at runtime (this would require building and running `ijar`'s zip.cc against a crafted `.jar` with a central directory extra field whose `data_size` exceeds the remaining `extra_field_length`, similar in spirit to the existing regression test `CreateZipWithMalformedExtraField` in `output_jar_simple_test.cc` for singlejar's parser, but targeting `third_party/ijar/zip.cc` instead — that existing test only exercises the already-bounds-checked singlejar path [3](#0-2) ). This should be verified experimentally with a Devin session that can build and run `third_party/ijar` tests to confirm exploitability before treating this as fully confirmed.

  static const ExtraField* find(uint16_t tag, const uint8_t* start,
                                const uint8_t* end) {
    while (start < end) {
      if (ziph::byte_ptr(start) + sizeof(ExtraField) > ziph::byte_ptr(end)) {
        break;
      }
      auto extra_field = reinterpret_cast<const ExtraField*>(start);
      if (ziph::byte_ptr(start) + extra_field->size() > ziph::byte_ptr(end)) {
        break;
      }
      if (extra_field->is(tag)) {
        return extra_field;
      }
      start = ziph::byte_ptr(start) + extra_field->size();
    }
    return nullptr;
  }
