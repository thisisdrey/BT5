### Title
Stale `PROMISE_YIELD_STATUS`/`YIELD_ID_TO_DATA_ID`/`DATA_ID_TO_YIELD_ID` trie entries survive `action_delete_account`, allowing griefing of a re-created account's `promise_yield_create_with_id` calls - ([File: core/store/src/utils/mod.rs])

### Summary
`remove_account` (invoked from `action_delete_account` in `runtime/runtime/src/actions.rs:314`) only removes the `Account`, `ContractCode`, access keys, gas-key nonces, and `ContractData` entries for a deleted account, but never enumerates or clears `TrieKey::PromiseYieldStatus`, `TrieKey::YieldIdToDataId`, or `TrieKey::DataIdToYieldId` entries created via `promise_yield_create`/`promise_yield_create_with_id`. Because these keys are scoped only by `receiver_id` (the account name) and an attacker-chosen `yield_id`/generated `data_id`, a deleted-and-recreated account with the same name inherits stale yield mappings that can cause `has_yield_id_mapping` to spuriously report a "duplicate" for a `yield_id` the new owner never created.

### Finding Description
`promise_yield_create_with_id` in `runtime/runtime/src/ext.rs:371-400` checks `has_yield_id_mapping(self.trie_update, &receiver_id, user_yield_id)` (`core/store/src/utils/mod.rs:315-324`), which looks up `TrieKey::YieldIdToDataId{receiver_id, yield_id}`. `user_yield_id` is fully attacker-controlled contract call data. If found, the call is silently rejected with `Ok(None)`, treated by the caller as "duplicate yield_id".

`remove_account` (`core/store/src/utils/mod.rs:505-575`), called by `action_delete_account` (`runtime/runtime/src/actions.rs:314`) via `DeleteAccountAction`, removes:
- `TrieKey::Account`
- `TrieKey::ContractCode`
- Access keys and gas-key nonces (via prefix iteration)
- `TrieKey::ContractData` entries (via prefix iteration)

It does **not** enumerate or remove `TrieKey::PromiseYieldStatus`, `TrieKey::YieldIdToDataId`, or `TrieKey::DataIdToYieldId` rows for the account, unlike the explicit cleanup helpers `remove_yield_id_mappings` and `remove_promise_yield_status` that exist elsewhere in `core/store/src/utils/mod.rs:273-334` (used on resume/timeout in `runtime/runtime/src/lib.rs`).

Exploit flow:
1. `evil.near` (funded, deploys a near_sdk contract) calls `promise_yield_create_with_id` with a chosen `user_yield_id`, writing `YieldIdToDataId{evil.near, yield_id}`, `DataIdToYieldId{evil.near, data_id}`, and `PromiseYieldStatus::Yielded{evil.near, data_id}`.
2. `evil.near` self-deletes via `DeleteAccountAction` with an arbitrary beneficiary. `action_delete_account` → `remove_account` clears account/code/keys/contract-data but leaves the yield-related trie rows intact.
3. A different, unrelated user later creates a new account named `evil.near` (account names are globally unique but can be re-registered once deleted/freed, subject to normal account-creation rules) and deploys their own contract.
4. That new owner calls `promise_yield_create_with_id` with the same `yield_id` value (a value they picked independently, or by coincidence/enumeration since `YieldId` space, while large, is not guaranteed to be attacker-avoidable if the new owner's app logic happens to reuse deterministic IDs, e.g., sequential or hash-of-arguments IDs). `has_yield_id_mapping` finds the stale entry from the deleted account and returns `true`, so `create_promise_yield_receipt_with_id` returns `Ok(None)`, silently rejecting the legitimate new owner's call as a "duplicate."

### Impact Explanation
This is a liveness/griefing defect: a new, legitimate owner of a re-registered account name can have specific `yield_id` values permanently blocked from use due to orphaned state left by the account's previous (unrelated) owner. It does not cause fund loss, inflation, double-spend, or consensus divergence — it only causes a `promise_yield_create_with_id` call to return `None` (a documented "duplicate" signal) for specific `yield_id` values chosen by the new owner. The practical exploitability is limited by the fact that `yield_id` is normally attacker/application chosen and there's no guarantee an unrelated new owner would choose the exact same `yield_id` as the deleted account did unless yield_id derivation is predictable/colliding (e.g., sequential counters starting from 0, or ids derived from public inputs). This bounds the impact to a narrow griefing/state-hygiene issue rather than a general denial-of-service, and does not affect funds or shard consensus.

### Likelihood Explanation
Preconditions: attacker needs to fund an account, deploy a contract calling `promise_yield_create_with_id`, and self-delete via `DeleteAccountAction`, all of which are ordinary unprivileged operations reachable via public RPC. However, exploiting it against a *specific future victim* requires the victim to reuse the exact same account name and the exact same `yield_id` value, which the attacker does not control unless the new owner's yield_id generation is predictable (e.g., sequential integers, which is a common near_sdk yield/resume implementation pattern). Repeatability is straightforward for the attacker's own account, but weaponizing it against an arbitrary future account owner is speculative and depends on the victim's yield_id choice.

### Recommendation
Extend `remove_account` in `core/store/src/utils/mod.rs` to also enumerate and remove `TrieKey::PromiseYieldStatus`, `TrieKey::YieldIdToDataId`, and `TrieKey::DataIdToYieldId` entries prefixed by the account, mirroring the existing access-key/contract-data cleanup logic, or add dedicated prefix-based cleanup calls (analogous to `remove_yield_id_mappings`/`remove_promise_yield_status`) invoked from `action_delete_account`.

### Proof of Concept
Unit test in `core/store/src/utils` or `runtime/runtime/src/actions.rs` test module:
1. Set up a `TrieUpdate`, call `set_yield_id_mapping(&mut su, &account_id, yield_id, data_id)` and `set_promise_yield_status(&mut su, &account_id, data_id, PromiseYieldStatus::Yielded)`.
2. Call `remove_account(&mut su, &account_id)`.
3. Assert `has_yield_id_mapping(&su, &account_id, yield_id)` still returns `Ok(true)` (demonstrating the stale entry survives deletion) — expected/correct behavior would be `Ok(false)`.
4. Simulate account re-creation (no new trie key changes needed since `Account` record itself was removed but yield keys were not) and directly call the `ext.rs` `create_promise_yield_receipt_with_id` equivalent logic (`has_yield_id_mapping` check) with the same `yield_id`; assert it incorrectly returns `Ok(None)`/`true`-duplicate instead of allowing creation. /// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}

    fn create_promise_yield_receipt_with_id(
        &mut self,
        receiver_id: AccountId,
        user_yield_id: YieldId,
    ) -> Result<Option<(ReceiptIndex, CryptoHash)>, VMLogicError> {
        // Check for duplicate yield_id in trie. TrieUpdate also reflects writes from earlier
        // calls within the same function call, so this also catches in-transaction duplicates.
        if has_yield_id_mapping(self.trie_update, &receiver_id, user_yield_id)
            .map_err(wrap_storage_error)?
        {
            return Ok(None);
        }

        let input_data_id = self.generate_data_id();

        // Store bidirectional yield_id <-> data_id mappings
        set_yield_id_mapping(&mut self.trie_update, &receiver_id, user_yield_id, input_data_id);

        let receipt_index =
            self.receipt_manager.create_promise_yield_receipt(input_data_id, receiver_id.clone());

        set_promise_yield_status(
            &mut self.trie_update,
            &receiver_id,
            input_data_id,
            PromiseYieldStatus::Yielded,
        );

        Ok(Some((receipt_index, input_data_id)))
    }
