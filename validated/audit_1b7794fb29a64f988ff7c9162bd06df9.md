### Title
Out-of-bounds read in ijar ZIP central-directory parsing due to missing bounds checks - (`third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` in `third_party/ijar/zip.cc` walks a memory-mapped `.jar`/`.zip` file's Central Directory and, unlike the sibling local-file-header parser, never validates that the fields it reads (and the extra-field loop it walks) stay within the bounds of the mapped input buffer. This mirrors the GTKWave CVE-2023-37442 bug class: a structured record parser trusts length fields taken directly from attacker-controlled input and advances a raw pointer/cursor without a "remaining bytes" check, producing an out-of-bounds read that a victim triggers simply by having their build process a malicious archive.

### Finding Description
`ProcessLocalFileEntry` calls `EnsureRemaining()` before consuming `file_name_length_` and `extra_field_length_` bytes: [1](#0-0) 

By contrast, `ProcessCentralDirEntry`, which is the entry point used to iterate every record in the Central Directory (`InputZipFile::ProcessNext` calls it per-entry), performs no equivalent check anywhere in its body: [2](#0-1) 

It reads `signature`, `compressed_size`, `uncompressed_size`, `file_name_length`, `extra_field_length`, `file_comment_length`, `attr`, and `offset` purely by advancing `p` via `get_u4le`/`get_u2le` (which themselves do unchecked pointer dereferences, see `get_u2le`/`get_u4le` in `third_party/ijar/common.h`): [3](#0-2) 

It then advances `p` by attacker-controlled `file_name_length`, `extra_field_length`, and `file_comment_length` with no check against the end of the mapped file, and separately walks an inner loop over "extra fields" using an attacker-controlled `data_size` per sub-record, again with no bound against `extra_p`'s containing buffer: [4](#0-3) 

If a crafted archive declares a Central Directory entry near the end of the mapped file with an oversized `file_name_length`/`extra_field_length`/`comment_length`, or an extra-field `data_size` that runs past the buffer, subsequent `get_u2le`/`get_u4le`/`memcpy` calls (e.g. the `memcpy` into `filename` at line 520) read past the end of the mmap'd region. This is the same bug class as CVE-2023-37442: a "var/entry definition" section is parsed with length fields trusted at face value, with no equivalent of GTKWave's missing bounds check before dereferencing.

### Impact Explanation
An out-of-bounds read against a memory-mapped file can crash the ijar/singlejar process (denial of service) or, depending on what lies adjacent to the mapping, leak adjacent heap/mapped memory into derived artifacts (e.g. bytes copied into `filename`) or into error messages, and in the worst case corrupt control flow via the unbounded `extra_p` walk. ijar/singlejar are invoked by Bazel's Java toolchain to produce interface jars and merged jars from prebuilt/downloaded `.jar` files, so this triggers whenever a build processes an attacker-supplied jar.

### Likelihood Explanation
Any dependency resolved via `http_jar`, `http_archive` unpacking a `.jar`, a Maven/registry artifact, or a jar checked into an untrusted branch that CI builds will be fed into ijar (for `java_import`/interface-jar generation) or singlejar. The attacker only needs to control the bytes of that jar — no MITM, no credentials, no access to the victim's machine — consistent with the required unprivileged-attacker model. No sha256/checksum verification is present in `ProcessCentralDirEntry` to stop malformed length fields; checksum verification at the `http_archive`/`http_jar` layer authenticates the archive's overall bytes but does not prevent internal ZIP structure fields from being crafted to be inconsistent, since a valid checksum can still wrap a maliciously-crafted (but hash-matching) ZIP structure.

### Recommendation
Add `EnsureRemaining`-style bounds checks to `ProcessCentralDirEntry` before reading `file_name_length`, `extra_field_length`, `file_comment_length` bytes and before/while walking the extra-field sub-records, mirroring the checks already present in `ProcessLocalFileEntry`. Validate `extra_p + data_size <= p` (extra-field end) and `p <= central_dir_end` for the whole record before dereferencing.

### Proof of Concept
A `BuildIntegrationTestCase`/`src/test/shell` style proof would construct a minimal ZIP file whose Central Directory Header declares a `file_name_length` (or `extra_field_length`) value that extends past the actual mapped-file length, invoke ijar (`third_party/ijar/ijar.cc` main path) or the `singlejar` binary on it, and confirm the process reads/crashes (e.g. under ASan reporting a heap-buffer-overflow READ) rather than failing cleanly with a "premature end of file" error, contrasting with the same test performed against `ProcessLocalFileEntry`'s equivalent (oversized) fields, which does fail cleanly due to its `EnsureRemaining` check.

---
**Caveat:** I could not fully trace `InputZipFile::Open()` / `CalculateOutputLength()` (where `central_dir_` is first computed and any file-level End-of-Central-Directory bounds validation might occur) within the available tool budget, so I cannot rule out that an earlier, coarser validation step (e.g., checking that the declared Central Directory size fits within the file before the per-entry loop begins) partially mitigates this. The per-entry field-level checks that do exist elsewhere in the file (`ProcessLocalFileEntry`) are absent from `ProcessCentralDirEntry`, which is the concrete gap identified here; confirming the full picture would require reading `InputZipFile::Open`/`CalculateOutputLength` in `third_party/ijar/zip.cc`, which was not completed before the iteration limit.

bool InputZipFile::ProcessCentralDirEntry(const u1 *&p, u8 *compressed_size,
                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
  const u1 *extra_p = p;
  p += extra_field_length;
  while (extra_p != p) {
    const u2 header_id = get_u2le(extra_p);
    const u2 data_size = get_u2le(extra_p);
    const u1 *extra = extra_p;
    extra_p += data_size;
    if (header_id == ZIP64_EXTRA_FIELD_TAG) {
      if (*uncompressed_size == U4_MAX) {
        *uncompressed_size = get_u8le(extra);
      }
      if (*compressed_size == U4_MAX) {
        *compressed_size = get_u8le(extra);
      }
      if (*offset == U4_MAX) {
        *offset = get_u8le(extra);
      }
    }
  }
  p += file_comment_length;
  return true;
}

inline u2 get_u2be(const u1 *&p) {
    u4 x = (p[0] << 8) | p[1];
    p += 2;
    return x;
}

inline u2 get_u2le(const u1 *&p) {
    u4 x = (p[1] << 8) | p[0];
    p += 2;
    return x;
}

inline u4 get_u4be(const u1 *&p) {
    u4 x = (p[0] << 24) | (p[1] << 16) | (p[2] << 8) | p[3];
    p += 4;
    return x;
}

inline u4 get_u4le(const u1 *&p) {
