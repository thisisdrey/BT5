### Title
Path Traversal via Attacker-Controlled Remote Patch URL Filename in `_download_patch` - (File: tools/build_defs/repo/utils.bzl)

### Summary
The `curling` RCE stemmed from failing to validate/sanitize an attacker-influenced string (a URL) before using it verbatim in a way that let attacker data escape its intended, restricted context (an option string interpreted by `curl`). The closest reachable analog in Bazel is in the repository-patching helper `_download_patch`, which derives a *local filename* directly from a remote, potentially attacker-served or attacker-influenced `patch_url` without validating that the resulting path stays inside the intended `_REMOTE_PATCH_DIR` sandbox directory.

### Finding Description
`patch()` in `tools/build_defs/repo/utils.bzl` applies `remote_patches` — a dict of `{patch_url: integrity}` — by calling `_download_patch`: [1](#0-0) 

```
def _download_patch(ctx, patch_url, integrity, auth = None):
    name = patch_url.split("/")[-1]
    patch_path = ctx.path(_REMOTE_PATCH_DIR).get_child(name)
    download_info = ctx.download(
        patch_url,
        patch_path,
        canonical_id = ctx.attr.canonical_id,
        auth = get_auth(ctx, [patch_url]) if auth == None else auth,
        integrity = integrity,
    )
    return patch_path, download_info
```

`name` is taken as the last `/`-delimited path segment of `patch_url` — a string that, for Bzlmod module extensions and `archive_override`/registry-provided patches, ultimately originates from data served by a (possibly untrusted or compromised) module registry/mirror, not from the trusted root repository's own Starlark. The `integrity` field only binds the downloaded *content* to a checksum; it does not constrain or validate the `name` (filename) portion at all. `ctx.path(...).get_child(name)` then joins this attacker-influenced segment onto the fetch working directory: [2](#0-1) 

```
    remote_patches_download_info = {}
    for patch_url in remote_patches:
        integrity = remote_patches[patch_url]
        patchfile, download_info = _download_patch(ctx, patch_url, integrity, auth)
        remote_patches_download_info[patch_url] = download_info
        ctx.patch(patchfile, remote_patch_strip)
        ctx.delete(patchfile)
    ctx.delete(ctx.path(_REMOTE_PATCH_DIR))
```

`patch_path`/`patchfile` is used both as the download destination and later as the source patch applied via `ctx.patch`. No check exists anywhere in this flow that the resolved `name` (and therefore `patch_path`) stays inside `_REMOTE_PATCH_DIR`. This is unlike other fetch/extraction code paths in the same codebase (e.g., archive extraction, which explicitly guards against Zip-Slip style escapes via `StripPrefixedPath`), which shows Bazel developers are otherwise aware that raw, attacker-derived path segments must be validated before being joined onto a filesystem path — that discipline is absent here.

### Impact Explanation
If a hostile registry, mirror, or otherwise attacker-controlled source for `remote_patches` supplies a `patch_url` whose final path segment contains `..` sequences (e.g. `https://evil.example/x/../../../../home/user/.bashrc`), `name` will carry those `..` segments straight into `get_child`, and the download can be written outside the intended `_REMOTE_PATCH_DIR` scratch directory within the external repository — a write outside the repository's own extraction sandbox. Because the checksum only validates the bytes of the downloaded content, not the destination path, `integrity` does not stop this: the attacker fully controls the bytes written to an arbitrary file, subject only to matching a checksum they also control (the attacker supplies both, since they are also the source of the registry/patch entry). This is a genuine containment break: untrusted content escaping the confines of the fetch/patch working directory.

### Likelihood Explanation
This requires the attacker to control (or a hostile mirror to substitute) a `patch_url` entry consumed by `remote_patches` for a module extension or archive-override style patch application — i.e., an outsider publishing/serving content a victim's build consumes, consistent with the threat model of the referenced report. No access to the victim's machine, credentials, or trusted root-repo BUILD/.bzl files is required; only that the resolved registry/mirror JSON pointing at patch archives is attacker-influenced.

### Recommendation
In `_download_patch`, reject/normalize `name` derived from `patch_url` so it cannot contain path-separator or parent-directory (`..`) components, and explicitly verify the resolved `patch_path` remains a strict descendant of `_REMOTE_PATCH_DIR` before calling `ctx.download`, mirroring the containment checks already applied elsewhere in Bazel's extraction code (e.g. `StripPrefixedPath`).

### Proof of Concept
A `src/test/shell/bazel/external_patching_test.sh`-style reproduction:
1. Stand up a fake HTTP registry/mirror serving a module with a `remote_patches` entry whose URL is crafted as `http://<attacker>/patches/..%2f..%2f..%2fpoc_marker` (or, since the code performs a raw string `split("/")`, simply `http://<attacker>/patches/../../../poc_marker`), with a matching `integrity` value for attacker-chosen bytes.
2. Configure a Bzlmod module extension / `http_archive` invocation with `remote_patches = {"<crafted-url>": "<attacker-computed-integrity>"}`.
3. Run `bazel fetch` / `bazel build` for that repository.
4. Verify that `poc_marker` is written outside the intended `.tmp_remote_patches` directory (e.g., in an ancestor of the external repository directory or the output base), demonstrating the write escaped the intended sandbox despite integrity validation passing.

Note: I was unable to directly inspect the native (Java) implementation of `StarlarkPath.getChild`/`PathFragment` resolution in this session to conclusively confirm whether `..` segments are normalized/escaped or rejected at that layer; this should be verified in the Devin session executing the PoC, since it determines whether the traversal actually materializes on disk versus being neutralized by lower-level path normalization.
