### Title
`debtFloorInUsd` combined with `maxLiquidable < 100%` makes positions in `(floor, 2*floor)` permanently unliquidatable — an attacker can deliberately open bad debt that no liquidator can clear - (contracts/Pool.sol)

### Summary
`Pool.liquidate` enforces two independent constraints: (1) `amountToRepay_ / debt <= maxLiquidable` (initialized to 50%), and (2) the post-liquidation remaining debt must be `0` or `>= debtFloorInUsd`. When a position's debt `D` falls in the range `debtFloorInUsd < D < 2 * debtFloorInUsd`, both constraints become unsatisfiable simultaneously, permanently bricking liquidation for that position. The same check exists in `DebtToken.repay`, so the dust debt also cannot be fully repaid to zero by a third party without the repayer covering the whole balance themselves — but the critical breakage is in the liquidation path. [1](#0-0) [2](#0-1) 

### Finding Description
`maxLiquidable` is initialized to `0.5e18` (50%) in `Pool.initialize`. [3](#0-2) 

In `Pool.liquidate`:

```solidity
if (amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable) {
    revert AmountGreaterThanMaxLiquidable();
}
if (debtFloorInUsd > 0) {
    uint256 _newDebtInUsd = masterOracle().quoteTokenToUsd(..., _debtTokenBalance - amountToRepay_);
    if (_newDebtInUsd > 0 && _newDebtInUsd < debtFloorInUsd) {
        revert RemainingDebtIsLowerThanTheFloor();
    }
}
``` [1](#0-0) 

For a position with debt `D` where `floor < D < 2*floor` (with `maxLiquidable = 50%`):

- Repaying the full `D` reverts with `AmountGreaterThanMaxLiquidable` (100% > 50%).
- Repaying any allowed amount `<= 0.5*D` leaves a remainder `>= D - 0.5*D = 0.5*D`, which is `< floor` whenever `D < 2*floor`, so it reverts with `RemainingDebtIsLowerThanTheFloor`. The only non-reverting remainder is `0`, which requires a 100% repay — already blocked.

So every call to `liquidate` on such a position reverts. The position can never be liquidated, by anyone, ever — regardless of how underwater it becomes.

An attacker can deliberately manufacture this state: open a position with debt sized in `(floor, 2*floor)` (e.g., floor = $3,000, debt = $4,000 — exactly the scenario exercised in the existing test where a half-repay reverts and only a full repay succeeds). The `DebtToken._mint` floor check only rejects debt `< floor`, so debt at `1.5 * floor` mints fine. [4](#0-3) 

### Impact Explanation
When the attacker's position turns unhealthy (collateral price drop or interest accrual), it is permanently unliquidatable. The debt keeps accruing interest while the collateral value decays, and the protocol is forced to absorb the resulting bad debt — a direct solvency/liveness break of the liquidation invariant. The attacker only needs to over-collateralize modestly up front and wait; alternatively, positions can organically drift into this band, meaning the attacker can also *frontrun/grief* — no privileged role, oracle manipulation, or governance action is required. This matches the bug class (complete denial of a critical service) — the liquidation service hangs for any position in the band.

### Likelihood Explanation
Requires `debtFloorInUsd > 0` (it is a configured parameter used precisely to keep liquidations profitable) and `maxLiquidable < 1e18` (50% default). Both hold in deployed configurations. The attacker's cost is locking collateral and intentionally letting the position go underwater, and they may even recover part of it via other collateral withdrawal before health fails. Any position — attacker's or a normal user's whose debt decays into the band via interest — becomes frozen against liquidation permanently.

### Recommendation
In `Pool.liquidate` (and equivalently in the `maxLiquidable` check), skip or relax the cap when the remaining debt would fall below the floor: e.g., allow a full repay whenever `D <= floor` is unreachable — concretely, permit `amountToRepay_ == _debtTokenBalance` (closing the position entirely) regardless of `maxLiquidable`, or auto-round `amountToRepay_` up to the full balance when `D - maxLiquidable*D < floor`. Alternatively enforce at mint time that new debt is either `0` or `>= floor / maxLiquidable` so the unliquidatable band can never be entered.

### Proof of Concept
Hardhat/foundry fork outline:

1. Deploy/attach to `Pool` with `maxLiquidable = 0.5e18` and `updateDebtFloor($3,000)`.
2. Attacker deposits collateral and calls `DebtToken.issue(amount = $4,000 worth, attacker)` — succeeds since $4,000 > floor.
3. Drop collateral price (fork: move oracle time / manipulate the AMM-priced collateral same-tx, or just accrue interest via `accrueInterest` + time warp) until `debtPositionOf(attacker)._isHealthy == false`.
4. Liquidator calls `pool.liquidate(synth, attacker, D, depositToken)` → reverts `AmountGreaterThanMaxLiquidable` (test confirms: `test/Pool.test.ts:439-450`).
5. Liquidator calls `pool.liquidate(synth, attacker, D/2, depositToken)` → reverts `RemainingDebtIsLowerThanTheFloor` (test confirms: `test/Pool.test.ts:409-421`).
6. Any intermediate `amountToRepay_` reverts for one of the two reasons — the unhealthy position is unliquidatable, and its debt accrues as bad debt permanently.
