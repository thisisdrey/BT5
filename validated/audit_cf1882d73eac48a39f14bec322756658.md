## Analysis

The Biconomy report describes a **signature-replay** bug class: a component (`VerifyingSingletonPaymaster`) validates a signature over a hash that is *not* intrinsically bound to single-use semantics — replay protection is delegated to another component (the smart-account's nonce), and once that enforcement layer is bypassed, the same signature can be reused indefinitely to drain the paymaster's funds.

The closest analog reachable in java-tron by an unprivileged contract deployer/caller is the `ValidateMultiSign` TVM precompiled contract.

### Title
Signature replay via `ValidateMultiSign` precompile due to unbound signed hash - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`ValidateMultiSign` is a TVM precompile (address `0x0...66`/documented as TIP-88) that any deployed smart contract can call to verify off-chain multisig approvals against an on-chain `Permission`. It computes the signed hash purely from `(address, permissionId, data)` with `Sha256Hash.hash(...)` and returns whether the recovered signer weights exceed the permission threshold. There is no protocol-level nonce, expiration, or "hash consumed" bookkeeping in the precompile itself — exactly the missing ingredient identified in the paymaster report. [1](#0-0) 

### Finding Description
`execute()` builds the hash to verify as `sha256(address || permissionId || data)` and checks recovered signer weight against `permission.getThreshold()` [2](#0-1) . All replay/freshness protection is left entirely to whatever value the calling contract chooses to embed inside `data`. If a calling contract's own logic for tracking "this approval was already consumed" can be bypassed — e.g. via reentrancy during the callback, an upgrade/delegatecall path that swaps in different accounting state, or simply forgetting to bind a nonce into `data` — the exact same signature (and therefore the exact same off-chain approval) can be replayed against the precompile over and over, since the precompile has no `usedHash` mapping analogous to what the paymaster report recommends. This mirrors the root cause of the H-05 finding: a signature-verification surface where "was this authorization already spent" is not enforced by the verifier, only assumed to be enforced upstream.

### Impact Explanation
Any TVM contract built on top of `ValidateMultiSign` to gate value-moving operations (e.g. a custodial/multisig wallet, bridge, or vault contract) can have a single valid multisig approval replayed to repeatedly authorize withdrawals/transfers, draining the contract's held TRX/TRC10/TRC20 balances — a direct unauthorized-account-operation / theft-of-funds outcome, reachable from an ordinary triggered-contract call with no privileged role required.

### Likelihood Explanation
Exploitation depends on a calling contract's own replay-protection logic being bypassable (missing nonce embedding, reentrancy, or a state-reset path). This is a common integration mistake for exactly the reason cited in the external report — the underlying primitive offers no intrinsic single-use guarantee — so any contract author who assumes the precompile itself prevents replay (as the paymaster author assumed the smart-account layer would) reproduces the same class of drain.

### Recommendation
Document explicitly (and consider enforcing) that callers of `ValidateMultiSign` must embed a monotonically-increasing/unique nonce or transaction-scoped value inside `data`; alternatively, provide an opt-in precompile variant that maintains an on-chain `usedHash` set per calling contract/account, analogous to the mitigation the Biconomy team was asked to add, so single-use approvals cannot be replayed even if the calling contract's own bookkeeping is defeated.

### Proof of Concept
1. Deploy a vault-like contract `V` that accepts a `(data, signatures[])` pair, calls `ValidateMultiSign(ownerAddr, permissionId, data, signatures)`, and on success transfers `amount` (encoded inside `data`) to `msg.sender`, while trying to track "used" hashes in its own storage.
2. Obtain one valid multisig-approved `data`/`signatures` pair for a withdrawal of `amount`.
3. Find or induce a path in `V` where its own replay-guard is skipped (e.g., a reentrant call back into the withdrawal function before its internal "used" flag is persisted, or a delegatecall-based upgrade that swaps in logic without the guard) — analogous to the `Upgrader.sol`/`MaliciousAccount.sol` swap in the original report.
4. Re-submit the identical `signatures` to `ValidateMultiSign` repeatedly through the bypass path; since the precompile itself performs no hash-consumption bookkeeping [2](#0-1) , each call returns success and `V`'s funds are drained.
