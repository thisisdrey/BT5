### Title
Unbounded reference-update loop in `UpdateReferences` allows resource-exhaustion DoS - (File: internal/gitaly/service/ref/update_references.go)

### Summary
The `UpdateReferences` RPC accepts a client-streamed, unbounded number of `Update` messages and, for each streamed request, an unbounded `repeated Update updates` field. The handler loops over every update in every request with no cap on the total number of reference updates that can be queued before `Commit()` is called, mirroring the reported "gas overflow during iteration" class of bug: a per-iteration cost (validation + write to the `git update-ref --stdin` pipe) accumulates without bound until the entire operation fails or exhausts resources.

### Finding Description
`UpdateReferences` receives a stream of `UpdateReferencesRequest` messages, each carrying `repeated Update updates = 2` [1](#0-0) . The server-side handler loops indefinitely over `server.Recv()` and, for every request, iterates `request.GetUpdates()` without any bound on the number of updates per request or across the whole stream, validating and staging each one into a single `updateref.Updater` before finally calling `updater.Commit()` once at the very end: [2](#0-1) 

Each iteration performs reference-name and object-ID validation and then calls `updater.Update(...)`, which writes an `update` command line to the stdin of a long-running `git update-ref --stdin` subprocess [3](#0-2) . All staged updates are buffered in this single subprocess pipe and only flushed/applied when `Commit()` writes the final `commit` command and waits for Git to process the whole transaction [4](#0-3) .

Unlike comparable RPCs in the same service that explicitly cap unbounded work — e.g. `for-each-ref`/pagination enforces a `Limit` via `paginationOpts` [5](#0-4) , or `ListPoolUpstreams` explicitly batches client input at `listPoolUpstreamsBatchSize = 10_000` [6](#0-5)  — `UpdateReferences` has no such cap. The only enforced limit at that point is the underlying gRPC message-size limit (which bounds a single message but not the number of streamed messages), so a client can send an effectively unlimited number of streamed requests/updates.

Because all updates are staged in one Git subprocess and applied as a single atomic transaction, exceeding the RPC's context deadline or Git's ability to process the accumulated `update-ref` command stream causes the entire, potentially very large, transaction to fail as a unit — directly analogous to the reported bug where "more gas is required than allocated" causes "all iterations of the loop [to] fail."

### Impact Explanation
Any ordinary, authenticated client permitted to call `UpdateReferences` (a MUTATOR RPC reachable from ordinary write/push-adjacent operations) can submit an arbitrarily large number of reference updates in a single logical transaction. This can consume excessive CPU (validating and generating commands for each update), memory (buffering commands and internal reference-update state), and Git subprocess time, potentially exhausting the RPC timeout or Gitaly worker resources and causing the whole update to fail — a handler-level DoS vector with no built-in resource limit, unlike sibling RPCs in the same package.

### Likelihood Explanation
High for a client that already has the ability to invoke this RPC: no additional privilege, injection, or crafted payload complexity is required beyond sending very many `Update` entries across the gRPC stream, which is a straightforward client-side operation.

### Recommendation
Add an explicit maximum on the number of reference updates accepted per `UpdateReferences` call (per message and cumulatively across the stream), similar to the `Limit`/pagination pattern used elsewhere in `internal/gitaly/service/ref`, and return `structerr.NewInvalidArgument` (or `ResourceExhausted`) once the cap is exceeded instead of allowing unbounded accumulation before `Commit()`.

### Proof of Concept
A client opens the bidirectional `UpdateReferences` stream, sends an initial request with a valid `Repository`, then streams a very large number of subsequent requests each containing many `Update` entries (e.g., millions of valid-looking but distinct `reference`/`old_object_id`/`new_object_id` triples). The server loop at `internal/gitaly/service/ref/update_references.go:47-97` accepts and stages all of them with no limit check before invoking a single `Commit()`, causing excessive resource consumption and/or a failed, wasted transaction on timeout.

message UpdateReferencesRequest {
  // Update represents a reference update.
  message Update {
    // reference is the fully-qualified reference name that should be updated.
    bytes reference = 1;

    // old_object_id is the object ID the reference should be pointing to in order to be updated.
    // This has the intent to avoid time-of-check-time-of-use-style races when the object ID
    // has changed.
    //
    // If empty, the reference will be force-updated without any such checks. If set to the
    // all-zeroes object ID, this will verify that the branch did not exist previously.
    bytes old_object_id = 2;

    // new_object_id is the object ID the reference should be updated to. If set to the all-zeroes
    // object ID the branch will be deleted.
    bytes new_object_id = 3;
  };

  // repository is the repository where references shall be updated in.
  Repository repository = 1 [(target_repository)=true];
  // updates is the set of reference updates that shall be performed.
  repeated Update updates = 2;
}

// Commit applies the commands specified in other calls to the Updater. Commit finishes the
// reference transaction and another one must be started before further changes can be staged.
func (u *Updater) Commit() error {
	// Commit can be called without preparing the transactions.
	if err := u.checkState(statePrepared); err != nil {
		if err := u.expectState(stateStarted); err != nil {
			return err
		}
	}

	u.state = stateIdle

	if err := u.setState("commit"); err != nil {
		return err
	}

	return nil
}
