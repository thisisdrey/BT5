### Title
Unprivileged pusher can perpetually grief `OptimizeRepository` housekeeping via concurrent-conflict abort in `TransactionManager.verifyHousekeeping` - (File: `internal/gitaly/storage/storagemgr/partition/transaction_manager_housekeeping.go`)

### Summary
Gitaly's WAL-based `TransactionManager` verifies housekeeping tasks (`pack-refs`, repacking) at commit time by scanning every log entry committed between the housekeeping transaction's snapshot LSN and the current tip. If *any* concurrent transaction touched conflicting state (a ref update/deletion racing pack-refs, or another housekeeping entry), the housekeeping transaction is aborted with a fixed, non-retried error. Because ordinary push/ref-update RPCs are cheap and can be issued rapidly by any user with write access to a repository, an attacker can keep the repository's HEAD moving fast enough that a housekeeping transaction almost never lands between two of the attacker's writes, permanently starving `OptimizeRepository`. This mirrors the reported Uniswap bug class: a permissionless, unprivileged action (`sync()` / here, a ref push) that updates a piece of shared timing/version state right before the victim operation's finalization check, causing that check to fail every single time it is retried, without ever needing privileged access.

### Finding Description
`verifyHousekeeping` walks all log entries committed since the transaction's snapshot and fails the transaction outright if it observes a conflicting concurrent housekeeping entry, a repository deletion, or (via `verifyPackRefsFiles`) any concurrent reference deletion: [1](#0-0) 

`verifyPackRefsFiles` similarly aborts pack-refs with `errPackRefsConflictRefDeletion` whenever a reference the pack-refs task intended to compact was concurrently deleted by any other transaction: [2](#0-1) 

The accompanying test suite explicitly documents this as an always-abort condition — any ref update/deletion landing between the pack-refs snapshot and its commit causes the pack-refs (or repacking) transaction to fail, e.g. `errPackRefsConflictRefDeletion`, `errRepackConflictPrunedObject`, or `errHousekeepingConflictConcurrent`: [3](#0-2) [4](#0-3) 

`OptimizeRepository` (the entry point that schedules and runs these housekeeping transactions) has no retry loop: it takes a single-shot lock via `tryRunningHousekeeping`, runs one optimization pass, and returns — if the pass fails on a concurrency conflict, the caller (usually the async housekeeping middleware after a normal RPC) just logs/records the failure and returns: [5](#0-4) 

Because any user with ordinary push access to a repository can produce a steady stream of small reference updates (trivial commits, branch churn, tag churn — all normal, unprivileged Git operations), they can ensure that a conflicting ref-update log entry is *always* committed within the (typically sub-second) window between a housekeeping transaction's read snapshot and its own commit attempt. Each housekeeping attempt then aborts with a conflict error identical in kind to every previous attempt, exactly like the Uniswap oracle where an attacker's permissionless `sync()` deterministically re-triggers the same-block failure condition on every retry.

### Impact Explanation
This is a resource-exhaustion / DoS vector on the storage layer of a specific repository (and transitively on shared object pools, since fork/pool repositories go through the same `verifyHousekeeping`/repack conflict logic). If housekeeping (`pack-refs`, full/geometric repack, pruning) can be indefinitely starved by an attacker who merely keeps pushing to their own repository, then:
- Loose objects and unpacked references accumulate without bound, degrading read/write performance (`git-pack-objects(1)`, ref enumeration, `git-fetch-pack(1)` all get slower).
- Grace-period based cleanups (`FindStaleReferenceLocks`, `FindTemporaryObjects`, pruning) never run to completion for the housekeeping-critical operations gated by the transaction manager, worsening storage bloat over time.
- Because commit-graph, cruft-pack eviction and multi-pack-index maintenance are folded into the same `optimizeRepository` cycle, denying it also denies unreachable-object eviction, which has quota/pruning implications for GitLab-side product features that depend on Gitaly housekeeping cadence.

This does not grant unauthorized data access or corrupt state (the conflict checks are functioning as designed to preserve correctness), so it is a griefing/DoS finding rather than a confidentiality/integrity break, but it is unprivileged, cheaply repeatable, and requires no more capability than normal push access.

### Likelihood Explanation
Likelihood is high for any attacker who already has push access to a repository (a very common, unprivileged capability in Git hosting): the "attack" is simply pushing/creating/deleting references at a rate faster than housekeeping transactions can complete their prepare→verify→commit cycle, which the tests show takes essentially one intervening commit to trigger. No race-condition timing precision, network position, or privileged role is required — an automated script issuing rapid low-cost ref updates (analogous to front-running `sync()` every block) is sufficient to keep starving the check indefinitely.

### Recommendation
- Avoid unconditionally aborting a housekeeping transaction just because *some* ref activity occurred concurrently; instead, attempt to rebase/replay the housekeeping outcome (e.g., recompute which refs are safe to prune/pack) against the newly committed changes, similar to how ordinary ref-update conflicts are resolved at a finer grain elsewhere in the codebase.
- Add bounded retry with jitter/backoff plus a maximum number of consecutive-conflict housekeeping attempts before falling back to a smaller-scoped or forced/exclusive optimization pass (e.g., briefly pausing acceptance of new ref updates for that repository) so a single repository cannot indefinitely deny itself housekeeping via ordinary write traffic.
- Track and alert on repositories that show many consecutive verification aborts for `pack-refs`/repack so operators can detect starvation-by-churn before storage bloat becomes severe.

### Proof of Concept
Conceptual reproduction, following the pattern already validated by the codebase's own test scaffolding:
1. Repository `R` under normal push access; snapshot LSN `N` for the housekeeping transaction is taken when `RunPackRefs`/`RunRepack` begins (see harness usage in `transaction_manager_housekeeping_test.go`, `Begin{ExpectedSnapshotLSN: N}` + `RunPackRefs{...}`).
2. Attacker script continuously issues small `Commit{ReferenceUpdates: ...}` (or ref deletions) against `R`, one per housekeeping attempt window (as reproduced in the `"concurrent ref deletion before pack-refs is committed"` test case at lines 936-978).
3. Each time housekeeping tries to commit, `verifyHousekeeping`/`verifyPackRefsFiles` detects the attacker's intervening ref change and aborts with `errPackRefsConflictRefDeletion` / `errHousekeepingConflictConcurrent` (lines 936-989, 1613-1633).
4. Because `OptimizeRepository` does not retry within the same call (`internal/git/housekeeping/manager/optimize_repository.go` lines 57-99) and is only re-invoked by the async middleware on the next qualifying RPC, the attacker simply repeats step 2 on every subsequent invocation, so housekeeping for `R` never successfully completes while the attacker keeps pushing.

func (mgr *TransactionManager) verifyPackRefsFiles(ctx context.Context, transaction *Transaction, zeroOID git.ObjectID) (*gitalypb.LogEntry_Housekeeping_PackRefs, error) {
	packRefs := transaction.runHousekeeping.packRefs

	// Check for any concurrent ref deletion between this transaction's snapshot LSN to the end.
	if err := mgr.walkCommittedEntries(transaction, func(entry *gitalypb.LogEntry, objectDependencies map[git.ObjectID]struct{}) error {
		for _, refTransaction := range entry.GetReferenceTransactions() {
			for _, change := range refTransaction.GetChanges() {
				// We handle HEAD updates through the git-update-ref, but since
				// it is not part of the packed-refs file, we don't need to worry about it.
				if bytes.Equal(change.GetReferenceName(), []byte("HEAD")) {
					continue
				}

				if git.ObjectID(change.GetNewOid()) == zeroOID {
					// Oops, there is a reference deletion. Bail out.
					return errPackRefsConflictRefDeletion
				}
				// Ref update. Remove the updated ref from the list of pruned refs so that the
				// new OID in loose reference shadows the outdated OID in packed-refs.
				delete(packRefs.PrunedRefs, git.ReferenceName(change.GetReferenceName()))
			}
		}
		return nil
	}); err != nil {
		return nil, fmt.Errorf("walking committed entries: %w", err)
	}

// OptimizeRepository performs optimizations on the repository. Whether optimizations are performed
// or not depends on a set of heuristics.
func (m *RepositoryManager) OptimizeRepository(
	ctx context.Context,
	repo *localrepo.Repo,
	opts ...OptimizeRepositoryOption,
) error {
	var cfg OptimizeRepositoryConfig
	for _, opt := range opts {
		opt(&cfg)
	}

	span, ctx := tracing.StartSpanIfHasParent(ctx, "housekeeping.OptimizeRepository", nil)
	defer span.End()

	if err := m.maybeStartTransaction(ctx, repo, func(ctx context.Context, tx storage.Transaction, repo *localrepo.Repo) error {
		originalRepo := &gitalypb.Repository{
			StorageName:  repo.GetStorageName(),
			RelativePath: repo.GetRelativePath(),
		}
		if tx != nil {
			originalRepo = tx.OriginalRepository(originalRepo)
		}

		// tryRunningHousekeeping acquires a lock on the repository to prevent other concurrent housekeeping calls on the repository.
		// As we may be in a transaction, the repository's relative path may have been rewritten. We use the original unrewritten relative
		// path here to ensure we hit the same key regardless if we run in different transactions where the snapshot prefixes in the
		// relative paths may differ.
		ok, cleanup := m.repositoryStates.tryRunningHousekeeping(originalRepo)
		// If we didn't succeed to set the state to "running" because of a concurrent housekeeping run
		// we exit early.
		if !ok {
			return nil
		}
		defer cleanup()

		if m.optimizeFunc != nil {
			strategy, err := m.validate(ctx, repo, cfg)
			if err != nil {
				return err
			}
			return m.optimizeFunc(ctx, repo, strategy)
		}
