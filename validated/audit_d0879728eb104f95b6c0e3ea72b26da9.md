### Title
Certificate Malleability via Unvalidated Trailing Bytes Enables Fingerprint-Based Blocklist Bypass - (File: cert/cert_v2.go)

### Summary
`unmarshalCertificateV2` decodes the outer ASN.1 `SEQUENCE` by reassigning the same `cryptobyte.String` variable and never re-checks that the original byte slice was fully consumed by that `SEQUENCE` element, so an attacker can append arbitrary extra bytes after a valid certificate encoding and still have it parse and validate successfully, while the sha256-based `Fingerprint()` of the raw bytes changes.

### Finding Description
In `unmarshalCertificateV2`, the raw input `b` is wrapped in `input := cryptobyte.String(b)`, then `input.ReadASN1(&input, asn1.SEQUENCE)` reads the SEQUENCE's tag/length and reassigns `input` to only the *contents* of that SEQUENCE, silently dropping whatever bytes of `b` followed the closing of the outer SEQUENCE element [2](#0-1) . There is no subsequent check (e.g., verifying that the consumed length equals `len(b)`) that rejects trailing garbage appended after the outer SEQUENCE. The function proceeds to parse `TagCertDetails`, curve, public key, and signature strictly from the (correctly-bounded) sequence contents, then calls `c.validate()` [3](#0-2) , which never inspects or rejects any bytes beyond the parsed SEQUENCE. As a result, two byte strings — the canonical certificate and the same certificate with arbitrary trailing padding — both decode to an identical `certificateV2{details, curve, publicKey, signature}` and both pass `CheckSignature`, since the signature is computed only over `rawDetails + curve + publicKey` (`marshalForSigning`), not over the full raw wire bytes [4](#0-3) . This is the same bug class as the zkSync report: data that has no effect on decoded semantics but is nonetheless accepted as "valid" input, changing an externally-visible derived value (there: gas cost from message length; here: the sha256 `Fingerprint()` hash of the raw certificate bytes) [1](#0-0) .

### Impact Explanation
`Fingerprint()` is explicitly documented as usable "to blocklist certificates" [1](#0-0) , and the CA pool machinery (`cert/ca_pool.go`) exposes fingerprint-based lookups used for revocation/allow-blocklist decisions. Because the parser accepts semantically-identical certificates with different trailing bytes, and the fingerprint is a hash of the raw bytes, an attacker or malicious CA/operator can mint an unbounded number of byte-distinct encodings of the same logical (and validly-signed) certificate. Any fingerprint-based revocation or blocklist check keyed on the raw-byte hash can be bypassed: a revoked certificate's fingerprint is blocklisted, but appending a single trailing byte produces a certificate that still validates against the correct issuer's signature yet has a fresh, non-blocklisted fingerprint. This is a remote authentication/verification-bypass condition — a revoked or blocklisted peer certificate can be re-admitted into handshakes by trivially padding it, undermining certificate/CA-pool based trust enforcement.

### Likelihood Explanation
Exploitation requires only appending arbitrary bytes to an otherwise valid, correctly-signed certificate — trivial for any holder of a certificate (including ones later revoked) since it does not require breaking the signature. The likelihood of triggering the bypass in a real deployment depends on whether fingerprint/blocklist checks are performed against raw wire bytes (as `Fingerprint()`'s doc comment implies) versus solely against decoded semantic fields; either way, the parser accepting non-canonical, padded encodings as "valid" is a concrete, reachable bug via the handshake/certificate-parsing path with no CA-signed certificate required from the attacker beyond one they already legitimately (or formerly) held.

### Recommendation
After `input.ReadASN1(&input, asn1.SEQUENCE)` in `unmarshalCertificateV2`, verify that the outer SEQUENCE consumed the entirety of `b` (i.e., that no trailing bytes remain outside the parsed SEQUENCE element), returning `ErrBadFormat` otherwise. Additionally, consider deriving `Fingerprint()` from the canonical re-marshaled form of the certificate (or from `rawDetails + curve + publicKey + signature` fields, as used for signing) rather than from raw, potentially non-canonical wire bytes, to make fingerprint-based blocklisting robust against encoding malleability regardless of parser strictness.

### Proof of Concept
1. Take a validly-signed `certificateV2` and marshal it to bytes `b` via `Marshal()`.
2. Construct `b' = append(b, 0xAA)` (or any extra trailing byte(s)).
3. Call `unmarshalCertificateV2(b', publicKey, curve)`: the outer `input.ReadASN1(&input, asn1.SEQUENCE)` call reads only the original SEQUENCE length from `b'`, discards the appended `0xAA` silently, and decoding proceeds identically to step 1's certificate — parsing succeeds, `validate()` succeeds, and `CheckSignature` succeeds because the signed payload (`rawDetails+curve+publicKey`) is unchanged.
4. Compute `sha256(b)` vs `sha256(b')` — they differ, demonstrating that `Fingerprint()` (documented as the blocklisting key) produces two different values for what the certificate-parsing/validation logic treats as the same valid, correctly-signed certificate.

func (c *certificateV2) marshalForSigning() ([]byte, error) {
	d, err := c.details.Marshal()
	if err != nil {
		return nil, fmt.Errorf("marshalling certificate details failed: %w", err)
	}
	c.rawDetails = d

	b := make([]byte, len(c.rawDetails)+1+len(c.publicKey))
	copy(b, c.rawDetails)
	b[len(c.rawDetails)] = byte(c.curve)
	copy(b[len(c.rawDetails)+1:], c.publicKey)
	return b, nil
}
