### Title
Unbounded, attacker-controlled allocation/copy in `BatchValidateSign` precompile ABI decoding leads to node OutOfMemoryError DoS - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `BatchValidateSign` precompiled contract decodes its calldata into an array of `DataWord`s and then reads array-size and byte-length fields directly from that attacker-supplied data without validating them against the actual size of the input buffer before using them to size and populate new arrays / copy ranges. This is the same bug class as CVE-2019-14192 (U-Boot `net_process_received_packet`): an unvalidated/unbounded length taken from untrusted input is used directly to drive an allocation and a `memcpy`-equivalent copy, with no bounds check tying the length back to the amount of data actually available.

### Finding Description
`extractBytesArray` and `extractBytes` in `PrecompiledContracts.java` read a `len`/`bytesLen` value straight from `words[...].intValueSafe()` (attacker calldata) and use it to allocate arrays and to slice the raw byte buffer: [1](#0-0) 

The inner copy helper: [2](#0-1) 

`Arrays.copyOfRange(data, offset, offset + len)` does not verify `offset + len` against `data.length`; when `to` exceeds the source length, Java's semantics zero-pad the result rather than throwing, meaning an attacker-chosen `len` up to `Integer.MAX_VALUE` (since `intValueSafe()` returns `Integer.MAX_VALUE` on overflow) is honored, producing a request to allocate a multi-gigabyte array.

This code path is only guarded by a size check (`MAX_SIZE = 16`) when `VMConfig.allowTvmSelfdestructRestriction()` is enabled; when that feature switch is off, `extractBytesArray` is called with **no upper bound at all** on `len`: [3](#0-2) 

Even `extractBytes32Array`, used for the address array regardless of the flag, allocates `new byte[len][]` directly from an unchecked attacker value: [4](#0-3) 

The energy metering for this call is computed from the *raw calldata length*, not from the attacker-controlled `len` fields actually used to size allocations: [5](#0-4) 

This means a small, cheap transaction (short calldata, low energy cost) can still cause the extraction logic to attempt to allocate arrays sized by a fabricated 32-byte length word (up to `Integer.MAX_VALUE`), exactly mirroring the U-Boot bug class: length taken from untrusted input drives an unbounded copy/allocation with no correlation check against real buffer size.

### Impact Explanation
`Arrays.copyOfRange`/`new byte[len][]` with attacker-supplied multi-gigabyte sizes throws `OutOfMemoryError`. While the `execute()` wrapper catches `Throwable`, the `OutOfMemoryError` is thrown only *after* the JVM has attempted (and partially performed) the large allocation, which can exhaust heap and destabilize or crash the node process for all callers, not just the attacker's transaction — a shared-resource denial-of-service against a live TVM-executing node. Because `BatchValidateSign` can be invoked by any account via a plain CALL from a smart contract, this is reachable from a single unprivileged transaction.

### Likelihood Explanation
High: no special privilege is required — any account can deploy or call a contract that invokes the `BatchValidateSign` precompile address with crafted ABI-encoded input. The vulnerable code path (`extractBytesArray`/`extractBytes32Array` without the `MAX_SIZE` guard) is active whenever `allowTvmSelfdestructRestriction()` is not enabled for the running chain configuration, which is a plausible state for a non-upgraded or differently configured production network.

### Recommendation
- In `extractBytesArray`, `extractBytes32Array`, `extractSigArray`, and `extractBytes`, validate every length/offset field against the actual remaining size of `data`/`words` before allocating or copying (mirroring the RLP decoder's `verifyLength` pattern already used elsewhere in the codebase, e.g. `framework/src/main/java/org/tron/core/capsule/utils/RLP.java`).
- Always enforce the `MAX_SIZE` bound on `len` regardless of `allowTvmSelfdestructRestriction()`, rather than gating the check behind a feature flag.
- Compute energy cost from the attacker-declared array/byte lengths (not just raw calldata length) prior to performing any allocation, so oversized requests are rejected by energy limits before allocation is attempted.

### Proof of Concept
1. Deploy a contract that performs a low-level `CALL` (or `STATICCALL`) to the `BatchValidateSign` precompile address, passing hand-crafted calldata:
   - `hash` word (32 bytes, any value).
   - offset word for signatures array pointing to a controlled offset.
   - offset word for addresses array pointing to a controlled offset.
   - At the signatures-array offset, place a length word with value `0x7FFFFFFF` (or any very large number) instead of a legitimate small array count.
2. Send this as a normal transaction on a network where `allowTvmSelfdestructRestriction()` is not enabled (default/older configuration state).
3. Execution reaches `doExecute` → `extractBytesArray(words, ..., data)` → `new byte[len][]` with `len = 0x7FFFFFFF`, attempting a huge allocation and causing `OutOfMemoryError` in the executing node process. Repeat with multiple large-length calls in a loop or concurrently to sustain heap pressure and increase the chance of a node crash.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
