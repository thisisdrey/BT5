### Title
Hard-coded Noise cipher-state ordering breaks non-IX handshake patterns, risking encrypt/decrypt key swap - ([File: handshake/machine.go])

### Summary
`handshake/machine.go` derives the traffic encryption/decryption keys (`eKey`/`dKey`) from the Noise library's `ReadMessage`/`WriteMessage` return values using a fixed, hard-coded tuple ordering, rather than deriving the ordering from the actual message pattern/role that completed the handshake. This is the same bug class as the reported issue: a function assumes a fixed correspondence between two returned values (Uniswap's `_r0`/`_r1` reserves vs. `_t0`/`_t1` tokens) instead of verifying the actual, pattern-dependent order, which can lead to values being applied to the wrong side of the exchange.

### Finding Description
In `ProcessPacket`, the responder or initiator completing the handshake takes the two `*noise.CipherState` values from `m.hs.ReadMessage` and assigns them directly to `EKey`/`DKey`: [1](#0-0) 

The comment explicitly documents the assumption and its fragility:

> "The (eKey, dKey) ordering here is correct for IX, where the initiator completes the handshake by reading the responder's stage-2 message. noise returns (cs1, cs2) where cs1 is the initiator->responder cipher. For 3-message patterns where a responder finishes by reading the final message, this ordering would be wrong; revisit when XX/pqIX lands."

The symmetric case in `buildResponse` has the identical hard-coded assumption for the write side: [2](#0-1) 

> "The (dKey, eKey) ordering here is correct for IX, where the responder completes the handshake by writing the stage-2 message... For 3-message patterns where an initiator finishes by writing the final message, this ordering would be wrong; revisit when XX/pqIX lands."

The root cause mirrors the reported bug class precisely: `noise.HandshakeState.ReadMessage`/`WriteMessage` return `(cs1, cs2)` in a fixed order determined by the underlying Noise pattern semantics (which side is initiator vs. responder, and which message index completes the handshake), not by which local variable the caller intends to receive it. The `Machine` code assumes `cs1`/`cs2` always map to `eKey`/`dKey` (or `dKey`/`eKey`) in the same way regardless of which handshake pattern (`IX`, `XX`, `pqIX`, etc.) or which role (initiator/responder) actually completed the exchange — exactly analogous to assuming `_r0` always corresponds to `_t0` regardless of the tokens' sorted order.

Both `Initiate`/`ProcessPacket` (read path) and `buildResponse` (write path) contain this same unconditional mapping, and both are gated only by a code comment, not by any runtime check against the actual pattern in use (`m.subtype` selects the pattern via `subtypeInfoFor`, but the resulting `(eKey,dKey)`/`(dKey,eKey)` ordering is never cross-checked against which pattern/role is active).

### Impact Explanation
If a new handshake subtype/pattern is added (as the comments anticipate for `XX`/`pqIX`) where the *responder* — instead of the initiator — completes the handshake by reading the final message, or where the *initiator* finishes by writing it, the current code will silently swap encryption and decryption keys between the two peers. This would cause one side to encrypt outgoing traffic with the key the peer expected to use for decrypting its own traffic and vice versa, i.e., a traffic-key mismatch that can result in either handshake/data-plane failure or, in an asymmetric misuse scenario, using the peer's decrypt key to encrypt data — a session-key confusion bug that directly threatens the confidentiality/integrity guarantees Noise provides. This is the reachable "remote state poisoning" / "traffic decryption or forgery" class of impact called for in the validation criteria: it corrupts the derived session keys for a handshake accepted from a remote, unauthenticated peer during the Noise exchange itself (i.e., before any certificate trust has been established), reachable by any attacker who can send handshake packets.

### Likelihood Explanation
Currently `NewMachine`/`subtypeInfoFor` appear to gate available subtypes/patterns (see `handshake/patterns.go`), and the only pattern exercised in this codebase's tests is `IX`, for which the hard-coded ordering is stated to be correct. I was not able to fully confirm from the available index whether any `XX`/`pqIX`/other 3-message pattern is already wired up and reachable via `header.MessageSubType`/`subtypeInfoFor` (the search results show `handshake/patterns.go` and `header/header.go` reference multiple subtypes/patterns, but I could not read their full contents before running out of tool budget). If any additional pattern beyond `IX` is already selectable today (even experimentally) through `m.subtype`, the vulnerable code path is immediately reachable by a remote peer during a normal handshake exchange, with no valid CA-signed certificate required, since key derivation happens before certificate verification completes. If only `IX` is currently wired up, the bug is latent but explicitly flagged by the developers as certain to be hit "when XX/pqIX lands."

### Recommendation
Do not hard-code the `(eKey, dKey)`/`(dKey, eKey)` mapping from Noise's `(cs1, cs2)` return values. Instead, derive the correct mapping from the actual pattern metadata associated with `m.subtype` (e.g., a per-pattern flag indicating "cs1 is my encrypt key" vs. "cs1 is my decrypt key" based on role and which message completes the handshake), and add an explicit runtime assertion/test that fails fast if a pattern's completion side doesn't match the currently hard-coded assumption. This should be verified with a dedicated unit test per supported pattern (`IX`, and any `XX`/`pqIX` pattern before it is enabled) that confirms each peer ends up with matching encrypt/decrypt key pairs.
