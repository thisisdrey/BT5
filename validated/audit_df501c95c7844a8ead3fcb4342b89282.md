Audit Report

## Title
`process_delivery_receipt` ignores the `DeliveryReceipt.success` flag, paying relayer rewards and settling orders even on failed Ethereum dispatch - (File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs)

## Summary
`DeliveryReceipt` decodes the `InboundMessageDispatched` Ethereum event, which carries an explicit `success: bool` field documented as "Delivery status" [4](#0-3) . `Pallet::process_delivery_receipt` never reads or branches on `receipt.success`; it unconditionally pays the relayer reward for `order.fee > 0` and removes the `PendingOrder` from storage regardless of dispatch outcome [5](#0-4) .

## Finding Description
The extrinsic `submit_delivery_receipt` is callable by any signed account, verifies the merkle/beacon proof via `T::Verifier::verify`, decodes the log into `DeliveryReceipt`, and forwards to `process_delivery_receipt` [6](#0-5) . Inside `process_delivery_receipt`, the only checks performed are gateway address match and existence of a `PendingOrder` for `receipt.nonce`; there is no check on `receipt.success` before paying the reward and removing the order and emitting `Event::MessageDelivered` [7](#0-6) . The `success` field is faithfully decoded from the real Ethereum event data (`event.success`) [8](#0-7)  but is discarded by the pallet logic — confirmed by the fact that `receipt.success`/`.success` has no other reference anywhere in the `bridges/snowbridge` codebase outside its own struct definition.

## Impact Explanation
This breaks the intended invariant (implied by the field name "Delivery status") that reward payout and order settlement should only occur when the message dispatch actually succeeded on Ethereum. A relayer submitting a receipt for a *failed* dispatch still collects the fee and the `PendingOrder` is permanently removed from storage, closing off any retry/re-settlement path for that nonce — a fund-flow correctness bug in a public, unprivileged extrinsic governing bridge reward payout, matching the "duplicate settlement or payout" / "permanent bridge-state lock" impact class.

## Likelihood Explanation
Any relayer observing a genuine Gateway `InboundMessageDispatched` event with `success = false` can submit it through `submit_delivery_receipt` with no privileged origin or governance required — only a valid proof of an actual on-chain Ethereum log, which is the normal relayer workflow. Existing tests (`submit_delivery_receipt_succeeds_after_unhalt`, etc.) construct receipts only with `success: true` [9](#0-8) , so the `success = false` path is entirely untested and unguarded.

## Recommendation
Branch on `receipt.success` in `process_delivery_receipt`: only invoke `T::RewardPayment::register_reward` when `success == true`; for `success == false`, avoid paying the reward and implement explicit failure-path semantics (e.g., retain the order for a bounded retry window or transition to a distinct terminal "failed" state/event) instead of unconditionally removing the order via `<PendingOrders<T>>::remove(nonce)`.

## Proof of Concept
1. A message is queued via `do_process_message`, creating `PendingOrders[nonce]` with `fee > 0` [10](#0-9) .
2. The message is relayed to Ethereum and dispatch on the Gateway fails, so the emitted `InboundMessageDispatched` event has `success = false`.
3. Any signed relayer submits this real event log + proof via `submit_delivery_receipt`; `T::Verifier::verify` succeeds since the proof is genuine, and `DeliveryReceipt::try_from` decodes `success: false` faithfully.
4. `process_delivery_receipt` runs its gateway check and nonce lookup, finds `order.fee > 0`, calls `T::RewardPayment::register_reward` and removes the order — identical to the success path — despite `receipt.success == false` never being inspected.
