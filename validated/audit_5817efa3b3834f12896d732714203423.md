Based on my analysis of `pallet-nfts`' atomic swap feature, I found a structurally identical bug pattern to the Particle lien issue: a claim/right is bound to a **resource identifier** (item ID) instead of being bound to a specific **state/ownership snapshot**, so ownership changes after the claim is created let the claim be exercised against a different, unconsenting owner's asset.

### Title
`claim_swap()` can transfer away an NFT from a new owner who never agreed to the stale swap offer - (File: `substrate/frame/nfts/src/features/atomic_swap.rs`)

### Summary
`do_create_swap` stores a `PendingSwap` keyed only by `(offered_collection_id, offered_item_id)` [1](#0-0)  . `do_claim_swap` later looks the swap up purely by that same item-id key and executes the transfer using whoever is the *current* owner of that item at claim time, without verifying that the account is still the original swap creator [2](#0-1) [3](#0-2)  . This is the same broken invariant as the `withdrawNftWithInterest()` bug: a stale claim record is treated as still valid because the check is "does the resource exist/is transferable," not "is the specific claim relationship (lien/swap) still bound to its original counterparty."

### Finding Description
1. `do_create_swap` only checks that `caller` owns `offered_item_id` **at creation time**, then persists the offer keyed by `(offered_collection_id, offered_item_id)` with no linkage to the creator's identity [4](#0-3) .
2. Nothing in the ordinary `transfer` path invalidates a `PendingSwapOf` entry when the underlying item changes hands outside of `claim_swap`/`cancel_swap` — the storage map is only touched by `do_create_swap`, `do_cancel_swap`, and `do_claim_swap` itself (confirmed by the single reference to `PendingSwapOf` found in `transfer.rs`, which is only the doc comment for `do_claim_swap`'s own internal transfer, not a general invalidation hook).
3. `do_claim_swap` re-reads the item at claim time: `receive_item = Item::<T, I>::get(&receive_collection_id, &receive_item_id)` and later moves `receive_item.owner` (the **current** owner) to the caller [5](#0-4) [3](#0-2) . There is no check that this current owner is the same account that created the swap.
4. Consequence: if the original swap creator disposes of the offered item (plain `transfer`, `buy_item`, or another swap) after creating the offer but before it is cancelled or expires, the dangling `PendingSwapOf` entry remains claimable. The counterparty can later call `claim_swap`, and the pallet will yank the item away from its new, unrelated owner and hand it to the counterparty — exactly mirroring "Jack's NFT is lost" in the source report, where a stale claim on a resource id outlives the transaction that should have invalidated it.

### Impact Explanation
This breaks the "settle exactly once to the rightful beneficiary" invariant for NFTs: an unrelated third party who legitimately acquired an item can have it involuntarily transferred out from under them, with no signed consent for that specific swap. If a price was attached (`maybe_price`), the new owner would also be forced into a currency transfer they never agreed to, causing direct fund/asset loss. This is a live-scope theft/unauthorized-execution class issue inside a core FRAME pallet used by Asset Hub collections.

### Likelihood Explanation
No malicious validator, collator, relayer, or governance action is required — only two ordinary signed accounts: the swap creator and the counterparty who later calls `claim_swap` against a stale offer. The only prerequisite is that the creator moves the offered item away without remembering (or bothering) to call `cancel_swap`, which is a very plausible unprivileged sequence in normal marketplace usage (list for swap, then sell/transfer outright via another route).

### Recommendation
Bind the `PendingSwap` to the specific owner at creation time (store `offerer: T::AccountId` in `PendingSwap`) and check `item.owner == swap.offerer` in `do_claim_swap` before performing the transfer; alternatively, have every ownership-changing path (`do_transfer`, `buy_item`, `claim_swap` itself for the *other* leg) purge any `PendingSwapOf` entry for the item whose owner is changing, similar to how the report's fix required checking `loanStartTime == 0` before allowing withdrawal — i.e., verify the claim's binding is still intact, not just that the resource exists.

### Proof of Concept
1. Account A owns NFT `(collection, item_1)` and calls `create_swap(collection, item_1, collection, Some(item_2), price, duration)` — `PendingSwapOf[(collection, item_1)]` is stored.
2. Before B claims, A calls the ordinary `transfer(collection, item_1, C)`. Ownership moves to C; `PendingSwapOf[(collection, item_1)]` is untouched.
3. C is unaware of the pending swap.
4. B, who owns `item_2`, calls `claim_swap(item_2, collection, item_1, price)`. `do_claim_swap` reads `receive_item = Item::get(collection, item_1)` → owner is now C, and transfers it to B, while B's `item_2` goes to C and any attached price is charged against C — none of which C consented to. This reproduces the pattern demonstrated in `Nfts::claim_swap_should_work` tests [6](#0-5) , except substituting a mid-flight ownership change of the offered item for the original owner, showing the missing "is this claim still bound to the current owner" check.

	pub(crate) fn do_create_swap(
		caller: T::AccountId,
		offered_collection_id: T::CollectionId,
		offered_item_id: T::ItemId,
		desired_collection_id: T::CollectionId,
		maybe_desired_item_id: Option<T::ItemId>,
		maybe_price: Option<PriceWithDirection<ItemPrice<T, I>>>,
		duration: BlockNumberFor<T, I>,
	) -> DispatchResult {
		ensure!(
			Self::is_pallet_feature_enabled(PalletFeature::Swaps),
			Error::<T, I>::MethodDisabled
		);
		ensure!(duration <= T::MaxDeadlineDuration::get(), Error::<T, I>::WrongDuration);

		let item = Item::<T, I>::get(&offered_collection_id, &offered_item_id)
			.ok_or(Error::<T, I>::UnknownItem)?;
		ensure!(item.owner == caller, Error::<T, I>::NoPermission);

		match maybe_desired_item_id {
			Some(desired_item_id) => ensure!(
				Item::<T, I>::contains_key(&desired_collection_id, &desired_item_id),
				Error::<T, I>::UnknownItem
			),
			None => ensure!(
				Collection::<T, I>::contains_key(&desired_collection_id),
				Error::<T, I>::UnknownCollection
			),
		};

		let now = T::BlockNumberProvider::current_block_number();
		let deadline = duration.saturating_add(now);

		PendingSwapOf::<T, I>::insert(
			&offered_collection_id,
			&offered_item_id,
			PendingSwap {
				desired_collection: desired_collection_id,
				desired_item: maybe_desired_item_id,
				price: maybe_price.clone(),
				deadline,
			},
		);
