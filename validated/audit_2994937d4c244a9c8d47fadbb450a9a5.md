### Title
Endowment (TRX/TRC10) charged to precompiled-contract call is not refunded on early "insufficient energy" failure path - ([File: actuator/src/main/java/org/tron/core/vm/program/Program.java])

### Summary
`Program.callToPrecompiledAddress()` unconditionally debits the caller and credits the callee for the `CALL`'s endowment (TRX or TRC10 token) *before* it verifies that enough energy was supplied to actually run the precompiled contract. When the supplied energy turns out to be insufficient, the method takes an early-return-style failure path (`stackPushZero()`) without ever executing the precompiled logic and, critically, without reversing the endowment transfer that was already applied to the child `Repository`. This mirrors the `RewardsDistributor.claim()` bug: value attached to a call is consumed by an early failure branch that neither performs the intended action nor gives the value back.

### Finding Description
In `callToPrecompiledAddress`, the endowment transfer happens directly against the child repository `deposit` via `MUtil.transfer(deposit, senderAddress, contextAddress, endowment)` (TRX) or `deposit.addTokenBalance(...)` (TRC10), guarded only by a sender-balance check, well before the energy check: [1](#0-0) 

The code comment explicitly documents that this transfer is **not reversible by rollback**: [2](#0-1) 

Immediately afterward, the required energy for running the target precompiled contract is computed and compared against the energy actually supplied in the `CALL`. If the supplied energy is insufficient, the method treats the whole call as consumed/failed and pushes `0` onto the stack — an early-return path that never invokes `contract.execute(data)`: [3](#0-2) 

Only in the success branch is `deposit.commit()` called to persist changes into the parent state; in the failure branch there is no explicit call to discard `deposit`'s changes, and the comment on line 1712 indicates the endowment transfer is intentionally treated as already final/irreversible regardless of the outcome of the call. Contrast this with the analogous `RewardsDistributor.claim()` bug: an early return (`if (alcxAmount == 0) return alcxAmount;`) occurs after the caller has already attached ETH, and the contract neither performs the intended action with that ETH nor refunds it, permanently trapping the funds.

### Impact Explanation
If a smart contract issues a `CALL`/`CALLCODE`/`STATICCALL`-type instruction with a non-zero endowment to a precompiled-contract address but under-provisions the energy (e.g., due to a bug in the caller's gas estimation, or an attacker deliberately crafting the call), the endowment (TRX or a TRC10 token) is moved from the sender to the target `contextAddress` even though the "call" is reported as failed (stack value `0`) and the precompiled contract's logic never runs. Because the precompiled address is not a normal externally-usable account and no follow-up logic executes to route or refund the value, the transferred TRX/token becomes permanently unreachable/stuck, a permanent freezing-of-funds condition triggered by a single ordinary transaction from an unprivileged caller (any contract deployer/caller who invokes `CALL` to a precompiled address with value and insufficient energy).

### Likelihood Explanation
Likelihood is low-to-medium: it requires a contract author or a caller to attach a non-zero endowment to a `CALL` targeting a precompiled-contract address while under-supplying energy relative to `contract.getEnergyForData(data)`. This is an atypical but entirely reachable pattern (e.g. mis-estimated gas forwarding in a proxy/wrapper contract, or accidental double-invocation analogous to the original report's "stuck transaction, retry" scenario), and does not require any special privilege, matching the "medium severity, low likelihood" classification of the original report.

### Recommendation
Move the endowment transfer to occur only after the energy check succeeds and immediately before `contract.execute(data)` is invoked, or perform the transfer on the child `deposit` and only merge/commit it into the parent state if `contract.execute()` succeeds (mirroring the pattern already used for `out.getLeft()==true`). Alternatively, explicitly refund the endowment back to `senderAddress` in the `requiredEnergy > msg.getEnergy()` branch before pushing zero, analogous to the report's suggested fix of checking/returning `msg.value` when the "no-op" branch is taken.

### Proof of Concept
Conceptual reproduction (would require a Devin session with the actual TVM test harness to execute):
1. Deploy a contract `Caller` that performs a low-level `call{value: X}(precompiledAddress, dataWithHighEnergyCost)` but forwards only enough gas to pass the `senderBalance < endowment` check yet less than `contract.getEnergyForData(data)`.
2. Observe that the endowment `X` is deducted from `Caller`'s TRX/TRC10 balance and credited to `precompiledAddress`'s balance in the child `deposit` state per [1](#0-0) , while the `CALL` returns `0` (failure) per [3](#0-2) .
3. Confirm the value is unrecoverable at `precompiledAddress`, matching the "swallowed" fund pattern from the original report.

Note: full confirmation of whether `deposit`'s un-committed changes are discarded elsewhere in `RepositoryImpl`/`TransactionTrace` could not be completed within the available tool budget; the explicit source comment "Charge for endowment - is not reversible by rollback" is the strongest evidence supporting this finding, but a Devin session with full build/test access should verify end-to-end behavior before treating this as fully confirmed.
