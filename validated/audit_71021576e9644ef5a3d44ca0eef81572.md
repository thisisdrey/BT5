### Title
Attacker can fill a victim's per-account token list via dust `deposit(..., onBehalfOf_=victim)`, blocking new collateral deposits and forcing liquidation - ([File: contracts/DepositToken.sol])

### Summary
`Pool` enforces `MAX_TOKENS_PER_USER = 30` across an account's `depositTokensOfAccount` + `debtTokensOfAccount` sets via `onlyIfAdditionWillNotReachMaxTokens`. `DepositToken._mint` calls `pool.addToDepositTokensOfAccount(account_)` on behalf of `onBehalfOf_`, and `deposit(amount_, onBehalfOf_)` is permissionless with an arbitrary beneficiary. An unprivileged attacker can therefore mint dust deposit tokens of every registered collateral type directly into a victim's list, permanently occupying slots the victim never asked for. When the victim later needs to deposit a new collateral type (e.g. to save an unhealthy position), `_mint` reverts with `UserReachedMaxTokens`. This is the direct analog of CVE-2020-1700: an attacker repeatedly exercises a cheap public path to accumulate state (socket slots / token-list slots) until a shared resource limit rejects legitimate use.

### Finding Description
- `Pool.onlyIfAdditionWillNotReachMaxTokens` reverts once `debtTokensOfAccount + depositTokensOfAccount >= 30` (contracts/Pool.sol:143-148).
- `Pool.addToDepositTokensOfAccount` is callable only by a registered deposit token, and it applies that modifier (contracts/Pool.sol:216-220).
- `DepositToken.deposit` is `external whenNotPaused` and takes a free `onBehalfOf_` argument; `_mint(onBehalfOf_, _deposited)` adds the token to the beneficiary's list whenever their balance was zero (contracts/DepositToken.sol:211-237, 486-488).
- `DepositToken._transfer` does the same for recipients (contracts/DepositToken.sol:517-520), so the attacker can also spam `transfer` of dust to the victim after minting to themselves — no victim action required at all.
- A pool can register up to `MAX_TOKENS_PER_USER` deposit tokens (contracts/Pool.sol:703), so filling all 30 slots requires only dust deposits/transfers across existing collaterals; if fewer deposit tokens exist, debt-token balances count too, but even a partially filled list reduces the collateral types a victim can use.

The victim can clear a slot only by transferring/withdrawing the dust to zero (which calls `removeFromDepositTokensOfAccount`, contracts/DepositToken.sol:460-462, 523-525), but any unlocked dust sent back is also a public, repeatable operation: the attacker can re-dust the freed slot atomically or by front-running, so the clearing attempt can be contested indefinitely at dust cost. There is no opt-out, no minimum-amount check, and no per-account consent for list insertion.

### Impact Explanation
- A leveraged victim whose position turns unhealthy cannot deposit a new collateral type to restore health (`deposit` → `_mint` → `addToDepositTokensOfAccount` → `UserReachedMaxTokens`), making them liquidatable while their only remediation paths (transfer dust out + re-deposit, or repay debt) can be front-run/re-filled.
- New users can be pre-griefed: attacker fills an account's list before its first real deposit, capping its usable collateral set.
- The invariant broken is liveness of the deposit path — legitimate users are denied the ability to add collateral positions due to attacker-accumulated list entries, mirroring the CLOSE_WAIT pile-up that denies legitimate connections.

### Likelihood Explanation
- Fully unprivileged: `deposit`/`transfer` are public, `onBehalfOf_`/`to_` are attacker-chosen, and no pause, lock, health check, or SynthContext restriction applies.
- Cost is bounded by dust-sized deposits across the pool's registered deposit tokens (plus deposit fee, if any); each insertion is a one-slot-per-tokens repeat, exactly like the CVE's repeated disconnect attempts.
- The defense-in-depth gap is that removal requires balance to hit exactly zero, and `_revertIfLocked`/`unlockedBalanceOf` can make some dust non-withdrawable for accounts with debt, making the attacker-occupied slots partially sticky for precisely the victims who most need new collateral.

### Recommendation
- Only add a token to `depositTokensOfAccount` when the recipient initiated the action (e.g. require `onBehalfOf_ == _msgSender()` for list insertion, or add a lazy "claim" step for unsolicited balances), or exempt `transfer`-received balances from the account list.
- Alternatively, track collateral contribution in `depositOf`/`debtPositionOf` via the global `depositTokens` set scanning balances, or let `addToDepositTokensOfAccount` silently skip instead of reverting so a full list never blocks `_mint`.
- At minimum, allow any account to purge zero/dust entries (permissionless `removeFromDepositTokensOfAccount` for a token the account no longer holds) so griefed slots are cheap to clear and cannot be refilled within the same transaction ordering without cost.

### Proof of Concept
Hardhat fork sketch (reproducible against a deployed pool on Base/Optimism):

```ts
// attacker fills victim's account list to MAX_TOKENS_PER_USER
const pool = await ethers.getContractAt('Pool', POOL);
const max = await pool.MAX_TOKENS_PER_USER();
const depositTokens = await pool.getDepositTokens(); // up to 30

for (const dt of depositTokens.slice(0, max.toNumber())) {
  const depositToken = await ethers.getContractAt('DepositToken', dt);
  const underlying = await ethers.getContractAt('IERC20', await depositToken.underlying());
  // attacker acquires dust of underlying (or mints own deposit token then transfers)
  await underlying.connect(attacker).approve(dt, dust);
  await depositToken.connect(attacker).deposit(dust, victim.address); // adds to victim's list
}

expect(await pool.getDepositTokensOfAccount(victim.address)).to.have.lengthOf(max);

// victim cannot deposit a collateral type not already in their list
const newDt = await ethers.getContractAt('DepositToken', depositTokens[0] /* any token victim lacks */);
await newDt.connect(victim).deposit(amount, victim.address); // reverts UserReachedMaxTokens

// if victim clears a slot by transferring dust out, attacker re-dusts it:
await depositToken.connect(attacker).transfer(victim.address, 1); // refills the slot
```

Modifiers that do not stop it: `whenNotPaused`/`nonReentrant`/`onlyIfDepositTokenExists` all pass; the `onlyIfAdditionWillNotReachMaxTokens` check is exactly the resource limit being exhausted, and `SynthContext._msgSender` only re-labels the caller.
