### Title
`submit_delivery_receipt` pays relayer reward without checking `DeliveryReceipt.success` - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

### Summary
The Snowbridge outbound-queue-v2 pallet decodes an `InboundMessageDispatched` Ethereum event that explicitly carries a `success` boolean indicating whether the relayed message actually executed successfully on the Ethereum Gateway contract. `process_delivery_receipt` never reads or checks that field before paying out the relayer's fee, effectively disabling the one guard meant to gate payout on successful delivery — directly analogous to the external report's "deadline check is not effective" pattern where a value that exists specifically to gate execution is set/ignored so the gate never fires.

### Finding Description
`DeliveryReceipt` is decoded from the `InboundMessageDispatched` Solidity event and explicitly carries a `success: bool` field: [1](#0-0) 

The pallet's public, unprivileged extrinsic `submit_delivery_receipt` verifies the proof, decodes the receipt, and forwards straight to `process_delivery_receipt`: [2](#0-1) 

`process_delivery_receipt` checks the gateway address, resolves the reward account, looks up the `PendingOrder` by nonce, and pays the relayer's fee — but the `receipt.success` field is never referenced anywhere in this function or the rest of the pallet: [3](#0-2) 

A grep across the pallet's source confirms `success` is decoded but never consumed anywhere in the pallet logic. The only guards enforced are: gateway address match, and existence of a `PendingOrder` for the nonce (i.e., replay/duplicate-claim protection). There is no branch on `receipt.success`, so a message whose execution reverted or otherwise failed on the Ethereum Gateway is paid exactly the same as one that succeeded. The module doc explicitly states the intended contract is "When the message has been verified and executed, the relayer will call `submit_delivery_receipt`... Fetch the pending order by nonce... pay reward" — i.e., reward is documented as conditioned on successful execution, but the code drops that condition (comment at lib.rs:36-41 vs. actual code at 445-480).

### Impact Explanation
Reward funds are an economic incentive meant to compensate relayers only for successfully delivering and executing a message on Ethereum. Because `success` is ignored, any relayer (unprivileged, only needs a valid Merkle/verifier proof of an event log that decodes to a `PendingOrder` nonce) can submit a `DeliveryReceipt` for a message whose `success` field is `false` and still receive the full fee stored in `order.fee`. This is an unbacked/incorrect payout: the relayer is paid for work that the chain of custody (the Ethereum event itself) says did not complete, and the `PendingOrder` is removed from storage regardless, permanently closing out accounting for that nonce as if delivery succeeded. This falls under "theft or unbacked... payout" / "duplicate settlement or payout" impact — fee funds leave the reward pool without the corresponding successful delivery guarantee the protocol design promises.

### Likelihood Explanation
High. No governance, admin, or malicious-peer assumption is needed — an ordinary relayer only needs a legitimately verifiable proof of *any* `InboundMessageDispatched` log (success or not) for a nonce with a `PendingOrder` still pending. Failed executions on Ethereum (reverts due to gas limits estimated by `GasMeter`, bad payload handling on the Gateway, etc.) are a normal occurrence, not an attacker-crafted edge case, making this trivially and repeatedly triggerable by any relayer submitting receipts for messages that fail on-chain on Ethereum.

### Recommendation
Check `receipt.success` in `process_delivery_receipt` before paying the reward. If `success` is `false`, either withhold/reduce the reward, or route to a different reward path (e.g., paying only a base/verification reward instead of the full fee), and only remove the `PendingOrder` after applying the correct outcome-dependent payout logic.

### Proof of Concept
1. A message is queued via `do_process_message`, creating `PendingOrder { nonce: N, fee: F, block_number }`. [4](#0-3) 
2. The relayer submits it to Ethereum; the Gateway contract's execution of the commands fails (e.g., a command reverts), so `InboundMessageDispatched` is emitted with `success = false` (but nonce and topic still match).
3. Relayer obtains a valid proof for this event log and calls `submit_delivery_receipt(origin, event)`.
4. `T::Verifier::verify` succeeds (proof is valid — it's a real event, just `success=false`), `DeliveryReceipt::try_from` decodes `success: false` successfully. [5](#0-4) 
5. `process_delivery_receipt` proceeds to pay `order.fee` to `reward_account` and removes the order — identical to the success path, because `receipt.success` is never checked. [6](#0-5) 

This can be confirmed against the existing test `submit_delivery_receipt_succeeds_after_unhalt`, which never varies `success` and still results in full reward payment; no test in the module exercises `success == false` to show it is rejected or reward-reduced. [7](#0-6)

```rust
		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
```

```rust
#[test]
fn submit_delivery_receipt_succeeds_after_unhalt() {
	new_tester().execute_with(|| {
		let nonce = 0;
		let fee: u128 = 1_000_000;
		let order = PendingOrder { nonce, fee, block_number: System::block_number() };
		PendingOrders::<Test>::insert(nonce, order);

		let relayer: AccountId32 = [7u8; 32].into();
		let origin = RuntimeOrigin::signed(relayer);
		let event = Box::new(mock_valid_event_proof());

		// Bridge halted — receipt rejected, order untouched.
		set_verifier_halted(true);
		assert_noop!(
			OutboundQueue::submit_delivery_receipt(origin.clone(), event.clone()),
			Error::<Test>::Verification(VerificationError::Halted)
		);
		assert!(PendingOrders::<Test>::get(nonce).is_some());

		// Bridge resumed — same receipt succeeds and the order is settled.
		set_verifier_halted(false);
		assert_ok!(OutboundQueue::submit_delivery_receipt(origin, event));
		assert!(PendingOrders::<Test>::get(nonce).is_none());

		System::assert_has_event(mock::RuntimeEvent::OutboundQueue(Event::MessageDelivered {
			nonce,
		}));
	});
}
```
