### Title
Unauthenticated remote shutdown of signer's event receiver via `/shutdown` HTTP endpoint - (File: `libsigner/src/events.rs`)

### Summary
The `SignerEventReceiver::next_event` handler treats any POST to `/shutdown` as authoritative, unconditionally setting `stop_signal` and returning `EventError::Terminated`, which causes `main_loop` to exit. This endpoint performs no authentication, so any TCP peer that can reach the signer's bound `event_server` address can terminate the signer's event processing with a single crafted HTTP request.

### Finding Description
The intended equality is `shutdown_authorized == request came from the node process itself`. In practice, `next_event` at [1](#0-0)  implements this as: any POST whose URL is `/shutdown` sets `event_receiver.stop_signal.store(true, Ordering::SeqCst)` and returns `Err(EventError::Terminated)`, with no signature, secret, token, or peer-identity check of any kind. `main_loop` treats `EventError::Terminated` as a normal exit condition and breaks out of its loop at [2](#0-1) , permanently halting event processing until the process is externally restarted.

The legitimate caller, `SignerStopSignaler::send`, is only supposed to be invoked by the signer's own runloop (obtained via `get_stop_signaler()`), and it works by opening a plaintext TCP connection to its own `local_addr` and sending a raw `POST /shutdown HTTP/1.1` request with an arbitrary body [3](#0-2) . Nothing in this wire format (path, headers, body) is secret or derived from any credential — it is trivially reproducible by any third party who can reach the port. The `event_server` this binds via `SignerEventReceiver::bind` (using `tiny_http::Server::http(listener)`) is a plain HTTP listener with no TLS/auth layer [4](#0-3) .

Whether this is remotely reachable by an "unprivileged attacker" per the threat model depends on the configured bind address for the signer's event server. I was unable to fully confirm within the available context whether this endpoint is, by default/documentation, bound to a loopback-only address (e.g., `127.0.0.1`) or can be configured to listen on a non-loopback interface reachable from the network. If it is loopback-only by default and by deployment convention (matching the "node process itself" framing in the question, i.e., the node's event-dispatcher POSTs to this address over localhost), then a genuinely remote unprivileged attacker without any local network access cannot reach it, and the fault—while real in the code—would not be remotely exploitable under this threat model's preconditions (attacker must reach the port; loopback-bound sockets are not reachable by a "remote party" as defined).

### Impact Explanation
If the event server is reachable (bound to a non-loopback address, e.g. `0.0.0.0` or a LAN/public interface), any party able to open a TCP connection to that address can send one crafted `POST /shutdown` request and permanently stop the signer's event-receiver main loop, halting all subsequent StackerDB chunk/block-proposal/burn-block event processing until manual restart. This matches the "Critical: unauthenticated DoS from a single message" category if remotely reachable.

### Likelihood Explanation
The precondition is entirely about network reachability of the signer's event-receiver bind address (the `local_addr` set in `bind()`). This is a signer/node configuration detail (`stacks-signer/src/config.rs` defines an `endpoint`/event-server bind address) that I was not able to fully verify from the code excerpts retrieved — specifically whether operators are expected/instructed to bind it to loopback only, and whether the default configuration enforces that. Given the code explicitly performs no authentication check on `/shutdown` regardless of bind address, if any deployment binds this endpoint to a non-loopback interface (intentionally or by misconfiguration), the vulnerability is trivially and repeatably exploitable by anyone who can reach that port, at negligible attacker cost (one raw TCP write).

### Recommendation
Require some form of authentication/authorization for the `/shutdown` path — e.g., derive a per-process shared secret (already available since `SignerStopSignaler` is only constructed from `get_stop_signaler()` within the same process) and require it in a header or the request body, verified in `next_event` before honoring the stop signal. Alternatively/additionally, enforce and document that this endpoint must only ever be bound to loopback, and have `bind()` reject non-loopback addresses for the event server, or verify `request.remote_addr()` is loopback before honoring `/shutdown`.

### Proof of Concept
```rust
// libsigner test: open a raw TcpStream to a running SignerEventReceiver's bound
// address and send a crafted POST /shutdown with no auth header.
use std::io::Write;
use std::net::TcpStream;

let mut receiver = SignerEventReceiver::<SomeMessageType>::new(false);
let addr = receiver.bind("127.0.0.1:0".parse().unwrap()).unwrap();
let (tx, _rx) = std::sync::mpsc::channel();
receiver.add_consumer(tx);

let handle = std::thread::spawn(move || receiver.main_loop());

let mut stream = TcpStream::connect(addr).unwrap();
let body = "attacker-controlled";
let req = format!(
    "POST /shutdown HTTP/1.1\r\nHost: {addr}\r\nConnection: close\r\nContent-Length: {}\r\n\r\n{}",
    body.len(), body
);
stream.write_all(req.as_bytes()).unwrap();

handle.join().unwrap(); // main_loop exits via EventError::Terminated with no auth check
```
This demonstrates that `next_event`'s `/shutdown` branch (`libsigner/src/events.rs:443-445`) accepts the request unconditionally and stops `main_loop`, but exploitability hinges entirely on whether the bound address is reachable by the attacker under the stated threat model — a fact I could not fully confirm from the retrieved configuration code.
