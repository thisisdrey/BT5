### Title
Node-wide adaptive concurrency limit is manipulatable by an unprivileged client via short-burst resource spikes - (File: internal/limiter/adaptive_calculator.go)

### Summary
`AdaptiveCalculator.calibrateLimits` adjusts the shared, node-wide concurrency limit for a given RPC using an additive-increase/multiplicative-decrease (AIMD) algorithm driven purely by the *current* calibration-interval's resource readings (CPU throttle ratio, memory ratio, PSI), exactly the bug class described in the external report: a control variable is recalculated from instantaneous/short-window state rather than a value resistant to short, attacker-induced spikes, letting a single unprivileged actor manipulate it to the detriment of other repositories/tenants sharing the node.

### Finding Description
`newCPUThrottlingCondition` (and its memory/PSI equivalents) evaluate `true`/`false` strictly by comparing the two most recent cgroup polls: `throttledDuration := cur.CPUThrottledDuration - prev.CPUThrottledDuration` over one `pollInterval`. [1](#0-0) 

`AdaptiveCalculator.calibrateLimits` runs on a fixed `CalibrationInterval` (default 30s) and, for every RPC-level `AdaptiveLimit` registered on the node, applies:
- `limit += 1` if no backoff event happened since the last calibration,
- `limit = floor(limit * BackoffFactor)` (default 0.5) if any backoff event happened. [2](#0-1) 

This decision is global per RPC (not per-repository, not per-client) — the limit object is shared by every request hitting that RPC on the node. [3](#0-2) 

An ordinary, unprivileged user can drive up CPU throttling, memory pressure, or PSI stall metrics on the node for the duration of a single calibration window (e.g., by issuing resource-heavy but otherwise legitimate Git operations such as large clone/push/repack requests, or many parallel operations against their own repository) and thereby force a `BackoffEvent`. Because the multiplicative decrease is applied to the *shared* per-RPC limit for the whole node, this single burst instantly halves the concurrency budget available to *all other users'* requests for that RPC — a cross-tenant denial-of-service primitive triggered purely from a normal RPC path, no privileged access or malicious peer needed. This is the direct analog of the reported Solidity bug: a rate-control mechanism reacts to attacker-influenced "current" state within one measurement window, instead of a value immune to single-window manipulation, allowing the actor to skew the control variable in a direction that benefits or harms other participants.

### Impact Explanation
Any client capable of issuing normal Gitaly RPCs (push, clone, fetch, or any RPC guarded by an `[[concurrency]] adaptive = true` limit) can deliberately spike CPU/memory/PSI pressure during a narrow window to trigger the multiplicative-decrease branch, cutting the node-wide concurrency limit for that RPC by half instantly. Repeating this before the additive-increase (`+1` per 30s by default) can recover the limit keeps the limit pinned near `MinLimit`, denying service to unrelated repositories/tenants sharing the Gitaly node for the affected RPC. This is a legitimate, reachable RPC-handler resource-limit DoS vector.

### Likelihood Explanation
Likelihood is moderate to high in multi-tenant Gitaly deployments where adaptive concurrency limiting is enabled (`Adaptive = true` in `[[concurrency]]` config). No special privileges, tokens, or malicious peers are required — only the ability to send normal, resource-intensive RPCs, which is inherent to Gitaly's purpose (clone/push/fetch of large repos). The attack requires timing bursts to coincide with the `CalibrationInterval` window, which is a fixed, discoverable default.

### Recommendation
Base the backoff/recovery decision on a smoothed or historically-resistant signal (e.g., an exponentially weighted moving average or a longer sliding window of multiple polls) rather than the delta between only the two most-recent polls, so a short burst from one client cannot single-handedly flip the shared node-level limit. Additionally, consider scoping adaptive limit decisions (or at least applying a per-key floor/backpressure) so that one tenant's induced resource spike cannot degrade throughput for all other repositories sharing the same RPC limiter.

### Proof of Concept
1. Enable adaptive concurrency limiting for an RPC (e.g., `PostUploadPackWithSidechannel`) with `adaptive = true`.
2. As an unprivileged client, issue a burst of resource-intensive operations (e.g., concurrent large clones/pushes or repository operations known to spike CPU/PSI) timed to fall within one `CalibrationInterval` (default 30s).
3. Observe via `gitaly_concurrency_limiting_current_limit` and `gitaly_concurrency_limiting_backoff_events_total` metrics that the shared per-RPC limit is halved node-wide after the calibration tick. [4](#0-3) 
4. Concurrently, a second, unrelated tenant's requests to a different repository for the same RPC now queue/reject sooner due to the reduced shared limit, demonstrating cross-tenant impact caused entirely by the first client's normal-looking traffic burst.

// newCPUThrottlingCondition returns a Condition that evaluates to true when CPU throttling occurred for more than 50% of the
// time between the last 2 polls.
func newCPUThrottlingCondition(threshold float64) loadmonitor.Condition {
	if threshold <= 0.0 {
		threshold = defaultCPUThrottlingThreshold
	}

	return loadmonitor.Condition{
		Name: conditionCgroupCPU,
		Fn: func(ctx context.Context, previous, current loadmonitor.Stats, pollInterval time.Duration) (bool, string) {
			cur, prev := current.CGroup.ParentStats, previous.CGroup.ParentStats

			// Somehow, cgroup stats are reset. It's usually the consequence of cgroup limits being changed.
			// Alternatively, they can be overridden by another program.
			// Either way, the watcher should update the stats accordingly.
			if cur.CPUThrottledCount < prev.CPUThrottledCount || cur.CPUThrottledDuration < prev.CPUThrottledDuration {
				return false, ""
			}

			throttledDuration := cur.CPUThrottledDuration - prev.CPUThrottledDuration

			// If the total throttled duration since the last poll exceeds 50%.
			if pollInterval > 0 && throttledDuration/pollInterval.Seconds() > threshold {
				return true, eventCPUThrottling
			}
			return false, ""
		},
