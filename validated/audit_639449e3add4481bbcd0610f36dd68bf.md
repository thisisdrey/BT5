Audit Report

## Title
Missing bound between `ContractCall::V1.value` and message-transferred assets in Snowbridge V2 outbound `Transact` converter — (File: `bridges/snowbridge/primitives/outbound-queue/src/v2/converter/convert.rs`)

## Summary
The V2 XCM→command converter decodes an XCM `Transact` payload as `ContractCall::V1 { target, calldata, value, gas }` and forwards it verbatim into `Command::CallContract` with no validation that `target` is restricted or that `value` is bounded by assets actually withdrawn/reserved in the same XCM message. [1](#0-0)  An unused error variant `CallContractValueInsufficient` in the same file confirms that a value-bound check was intended but never implemented. [2](#0-1)  This is a real gap, but the claim's severity characterization overstates the reachable impact: the resulting `Command::CallContract` executes on Ethereum "dispatched by the agent contract acting as a proxy for the XCM origin" [3](#0-2)  — i.e., through the agent uniquely derived from the *same* `AliasOrigin` location the attacker supplied, not an arbitrary or shared victim agent.

## Finding Description
`convert()` requires an `AliasOrigin(origin_location)` instruction, checks it against the configured `AllowedAliasOrigin` filter, and derives the message's `origin` (the agent that will execute the resulting commands) from that same location via `AgentIdOf::convert_location(origin_location)`. [4](#0-3)  The `Transact` block then decodes `ContractCall::V1` and pushes `Command::CallContract{target, calldata, gas, value}` with no check that `value` is backed by assets withdrawn in the message and no allow-list on `target`. [1](#0-0) 

The production runtime configuration for this exporter is `AllowedAliasOrigin = EverythingBut<Equals<AssetHubLocation>>`, per `bridge_to_ethereum_config.rs`, which specifically blocks only the AssetHub-level shared/root location (protecting the shared bridge agent holding all AssetHub users' aggregate ERC20 assets) — this is documented as a defense-in-depth fix (`pr_12159.prdoc`) against an origin-spoofing bug where a signed user could previously forge the AssetHub-level `AliasOrigin`, letting them command `CallContract` via the shared AssetHub agent holding other users' funds. That specific "shared agent" theft vector has already been patched. [5](#0-4) 

Critically, the XCM executor's own `AliasOrigin` instruction enforces its own `Aliasers` authorization check independent of `AllowedAliasOrigin` — an ordinary signed account cannot make the executor accept an arbitrary `AliasOrigin(victim_location)` unless the runtime's `Aliasers` config explicitly permits that aliasing (typically self-aliasing only). This means, in the normal/expected configuration, an attacker can only cause the exporter to see an `AliasOrigin` value equal to their own account's location, so the derived agent (and its held ether) is the attacker's own dedicated agent, not an arbitrary third party's. The claim's assertion that "any XCM sender... can move/spend the agent's held ether... under the agent's identity" targeting arbitrary victims is not substantiated by the code reviewed — I was unable to locate the `Aliasers` implementation for AssetHub Westend specifically within available context to fully confirm this restricts self-aliasing only, but no code path was found that lets an unprivileged account forge another party's `AliasOrigin` (aside from the previously-patched AssetHub-root spoofing bug covered by `pr_12159.prdoc`).

Given this, the residual bug is narrower than claimed: a user can, via their own agent, issue a `CallContract` to an arbitrary `target` with arbitrary `calldata` and a `value` up to their own agent's currently-held ether balance (which could exceed what was reserved/withdrawn in the specific triggering message, e.g. dust/unclaimed refunds previously accumulated in that same agent). This is a design/validation gap (missing enforcement of the documented but unused `CallContractValueInsufficient` check and no `target` allow-list) rather than a cross-user theft primitive, because the origin-to-agent binding ties the call's authority and funds source to the same origin that must independently be authorized to alias in the first place.

## Impact Explanation
The demonstrated impact is that a user's own agent can be driven to make arbitrary Ethereum calls with a `value` unconstrained by the specific triggering message's transferred amount — i.e., a cost/accounting gap and an unrestricted arbitrary-call primitive scoped to the caller's own agent, not unauthorized access to other users' custody or a duplicate-settlement/theft-of-others'-funds condition as characterized in the claim. Without evidence that an unprivileged account can forge `AliasOrigin` for a location it does not control (the one documented spoofing bug for the AssetHub-root location has already been fixed per `pr_12159.prdoc`), the "theft of other users' agent-held ether" impact is not established from the code reviewed.

## Likelihood Explanation
The missing `value`-bound check itself is definitely present and trivially reachable by any account permitted to alias to its own location and submit a `Transact`, as shown in the repository's own integration test `transact_with_agent_from_asset_hub`. [6](#0-5)  However, exploiting it to affect funds beyond the caller's own agent requires either (a) a still-unpatched way to forge `AliasOrigin` to another party's location (not found; the known instance was fixed), or (b) reliance on funds incidentally sitting in the caller's own agent that were not intended to be spendable this way (a real but lower-severity issue).

## Recommendation
- Implement the intended check (use the existing `CallContractValueInsufficient` error) to bound `ContractCall::V1.value` by the ether amount actually withdrawn/reserved within the same XCM message, rather than allowing draws against the agent's total held balance.
- Consider constraining or documenting the semantics of `target`/`value` in `ContractCall::V1` explicitly as "spends only the calling origin's own agent balance" to avoid ambiguity, and add regression tests confirming that `AliasOrigin` cannot be forged to any location the origin does not control, beyond the already-covered AssetHub-root case.

## Proof of Concept
Using the existing integration test `transact_with_agent_from_asset_hub`, an AssetHub signed account submits `WithdrawAsset`/`PayFees`/`InitiateTransfer` → `AliasOrigin(self)`/`DepositAsset`/`Transact{ContractCall::V1{target, calldata, value: <agent's balance, unconstrained by message amount>, gas}}`; the converter accepts this without checking `value` against the message's transferred amount and emits `Command::CallContract` accordingly. [6](#0-5)  This confirms the missing value-bound check but only within the caller's own agent's authority/funds, not an arbitrary victim's, absent a separate `AliasOrigin` forgery vulnerability that was not found to exist in current code.
