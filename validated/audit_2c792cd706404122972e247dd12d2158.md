### Title
Deterministic integer-overflow panic in `Runtime::apply` causes an unrecoverable shard halt with no automatic recovery path - (File: chain/chain/src/runtime/mod.rs)

### Summary
`Runtime::apply` is the mandatory, deterministic state-transition function invoked by every validator for every chunk of every shard. When any of its many internal `checked_add`/`checked_mul`/`checked_sub` accounting operations overflow, they return an `IntegerOverflowError`, which propagates up as `RuntimeError::UnexpectedIntegerOverflow`. Unlike ordinary invalid-transaction errors (which are handled gracefully and simply reject the offending transaction), the caller of `apply` in `chain/chain/src/runtime/mod.rs` converts this specific error class into a hard `panic!`, with the code itself acknowledging this is a known gap: [1](#0-0) 

This mirrors the dForce pattern precisely: a step that runs unconditionally before/ during ordinary state processing (`Base._updateInterest` in dForce, `Runtime::apply`'s accounting in nearcore) can hit a failure condition that halts the entire system, and — because chunk application is deterministic — every honest validator hits the identical panic on the identical chunk, with no path to "just skip and continue" since the panic occurs deep inside consensus-critical, non-recoverable code.

### Finding Description
Overflow-guarded arithmetic (`.checked_add(...).ok_or(IntegerOverflowError)?` and similar) is scattered throughout the receipt/action execution pipeline in `runtime/runtime/src/lib.rs` and `runtime/runtime/src/global_contracts.rs`, e.g. accumulating `tokens_burnt`, `gas_burnt`, and congestion counters across all actions inside a receipt: [2](#0-1) 

Similar `IntegerOverflowError` sources exist for congestion accounting (`add_buffered_receipt_gas`, `remove_buffered_receipt_gas`) and gas/fee computation (`tx_cost`, `total_prepaid_gas`, `pay_action_base`, `pay_action_per_byte`), which are correctly guarded with `checked_*` at each individual call site: [3](#0-2) [4](#0-3) 

However, once any of these `IntegerOverflowError`s escapes all the way out of `Runtime::apply` as `RuntimeError::UnexpectedIntegerOverflow`, the top-level caller does not treat it as a rejectable/invalid input — it panics the node process: [1](#0-0) 

Because `apply` is the deterministic state-transition function that every validator must execute identically to agree on the resulting state root, any receipt/action sequence that triggers this overflow will cause **every** honest validator applying that chunk to panic in the same way — exactly the "entire system may halt and be unrecoverable" scenario described in the dForce report, except here the trigger is a Rust panic rather than a Solidity `require` revert, and the "system" is the whole shard's block production rather than a single lending market.

### Impact Explanation
A shard-halting panic in consensus-critical, deterministic chunk-application code satisfies the accepted impact category for this analysis (shard-halting panic). If reachable, it would stop chunk production for the affected shard entirely, requiring a coordinated software patch/restart across validators to recover — there is no in-protocol self-healing path, matching the "unrecoverable" characteristic of the original report.

### Likelihood Explanation
Likelihood is **low but structurally present**, similar to the original dForce finding itself, which the auditors flagged as "unlikely to be reached" under sane parameters yet still worth hardening. NEAR's balances/gas are 128-bit/64-bit values with large economic headroom, so reaching an actual overflow via a single transaction is hard; however, the failure mode is unguarded by design at the top level (`panic!` instead of graceful rejection) and is explicitly marked in code as a known outstanding gap (`TODO(#2152): process gracefully`), meaning any future accounting path that is added (e.g., a new congestion or fee accumulator that forgets a bound check) inherits a shard-halting panic instead of a safe error, with no defense-in-depth backstop at the point where it matters most.

### Recommendation
Complete the acknowledged `TODO(#2152)` by converting `RuntimeError::UnexpectedIntegerOverflow` (and the neighboring `RuntimeError::ReceiptValidationError` panic) handling in `chain/chain/src/runtime/mod.rs` into a recoverable outcome — e.g., reject/mark the specific transaction or receipt as invalid and continue processing the rest of the chunk, consistent with how other `InvalidTxError`/`ReceiptValidationError` cases are already handled gracefully elsewhere in the same match arm. This removes the single top-level panic as the last line of defense for what should be input-validation-style failures, analogous to the recommended dForce fix of not letting the interest-rate check become the single unrecoverable choke point.

### Proof of Concept
I could not construct a concrete numeric PoC (specific action/receipt sequence and byte-for-byte accounting values) that overflows one of the `u128`/`Gas` counters within the reachable economic bounds of NEAR, given the scope of information available through code search alone. This mirrors the original report's own caveat that the trigger condition, while code-provably present, depends on specific numeric parameters that require deeper economic/unit modeling to confirm feasibility. A background engineering session with full repository/test access would be needed to attempt to construct or rule out a concrete overflow-triggering transaction sequence.
