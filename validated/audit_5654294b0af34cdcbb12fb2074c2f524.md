### Title
`SetCustomHooks` allows tar symlink entry to make `<repo>/custom_hooks` an arbitrary-path symlink via `os.Rename` - ([File: internal/gitaly/repoutil/custom_hooks.go])

### Summary
`ExtractHooks` (`internal/gitaly/repoutil/custom_hooks.go:55-95`) invokes the external `tar` binary to extract only the `custom_hooks` member into a temporary directory. If the attacker crafts the top-level `custom_hooks` archive entry as a symlink (e.g. pointing to `/` or any absolute path), GNU tar creates it as a real symlink object rather than a directory, and `SetCustomHooks` later does `os.Rename(tempHooksPath, repoHooksPath)` [1](#0-0) , which renames the symlink *itself* (rename never dereferences the source) into the repository, turning `<repo>/custom_hooks` into a symlink to an attacker-chosen absolute path.

### Finding Description
`SetCustomHooks` extracts the tar payload into `tmpDir.Path()` via `ExtractHooks`, which shells out to `tar -xf - -C <tmpDir> --strip-components 0 custom_hooks` [2](#0-1) . GNU `tar` does not dereference symlink entries on extraction — it recreates them verbatim via `symlink(2)`. A crafted tar containing a single entry named exactly `custom_hooks` with `Typeflag: tar.TypeSymlink` and an arbitrary `Linkname` (absolute, e.g. `/`) will therefore be created as `tmpDir/custom_hooks -> /`.

Back in `SetCustomHooks`:
- `os.Mkdir(tempHooksPath, mode.Directory)` fails with `fs.ErrExist` (ignored) since the path already exists as a symlink [3](#0-2) .
- `newDirectoryVote(tempHooksPath)` uses `filepath.WalkDir`, which `lstat`s the root; since the root is a symlink (not a directory), `WalkDir` treats it as a single non-directory entry and invokes the callback once without descending [4](#0-3) . Inside the callback, `os.Open(path)` follows the symlink (Go's `os.Open`/`open(2)` dereferences symlinks by default), so if the link target is a regular file the vote hash is computed over that file's contents — an unintended dereference, though this only affects an internal hash, not a direct data leak.
- Critically, `os.Rename(tempHooksPath, repoHooksPath)` at line 221 operates on `rename(2)`, which does not dereference the source path if it is a symlink — it moves the symlink object itself. This makes `repoHooksPath` (`<repo>/custom_hooks`) become a symlink pointing to whatever absolute or relative target the attacker specified in the tar entry [5](#0-4) .

No validation exists in `ExtractHooks` or `SetCustomHooks` to reject symlink entries in the tar stream, and there is no `--strip-components`/type filtering to prevent `tar` from materializing a symlink at the `custom_hooks` path. There is no `storage.ValidateRelativePath`-style containment check applied to the extracted tar member types.

### Impact Explanation
This breaks storage-path/hooks isolation: an unprivileged repository owner can turn their own repository's `custom_hooks` directory entry into a symlink pointing anywhere on the Gitaly host filesystem that the process user can traverse. Subsequent hook-lookup logic (`<repo>/custom_hooks/pre-receive`, etc., executed on push) would resolve through this symlink. On its own this does not grant the attacker the ability to write arbitrary file content at the target (since the tar only supplies a symlink, not file content there), so it is a containment/isolation violation (cross-directory symlink planting) rather than an immediate remote-code-execution primitive — full impact depends on whether an attacker-influenced writable path elsewhere on disk (e.g., predictable `/tmp` locations) can be paired with this to plant an executable hook. This matches the GitLab bounty class of "storage/hooks isolation bypass via crafted archive" (symlink-based path confusion), with restricted/uncertain severity absent a second write primitive.

### Likelihood Explanation
The precondition is minimal: any user able to invoke the `SetCustomHooksRequest` gRPC (an unprivileged repository owner or a GitLab feature invoking it, e.g. via import/mirror hooks-setting flows) can supply arbitrary tar bytes as `Data`. Crafting the tar with a single symlink entry named `custom_hooks` is trivial and repeatable, and no server-side validation rejects it before or during `os.Rename`.

### Recommendation
- Reject non-regular/non-directory tar entries (symlinks, hardlinks, devices, fifos) when extracting hooks — pass `--exclude-caches`/explicit type filtering, or post-process the extracted tree with `os.Lstat` to verify `custom_hooks` and every descendant are regular files/directories before proceeding.
- After extraction, verify with `os.Lstat(tempHooksPath)` that the result is a real directory (`mode&fs.ModeSymlink == 0`) and abort if not, before calling `os.Rename`.
- Consider extracting with Go's `archive/tar` package directly (as already done in `internal/gitaly/service/repository/replicate.go`'s `extractTarToDirectory`, which validates and rejects absolute/escaping symlinks) instead of shelling out to the system `tar` binary without symlink policy control.

func TestSetCustomHooks_symlinkEscape(t *testing.T) {
    ctx := testhelper.Context(t)
    cfg := testcfg.Build(t)
    locator := config.NewLocator(cfg)
    txManager := transaction.NewTrackingManager()
    logger := testhelper.NewLogger(t)

    repo, repoPath := gittest.CreateRepository(t, ctx, cfg, gittest.CreateRepositoryConfig{
        SkipCreationViaService: true,
    })

    var buf bytes.Buffer
    tw := tar.NewWriter(&buf)
    require.NoError(t, tw.WriteHeader(&tar.Header{
        Name:     "custom_hooks",
        Typeflag: tar.TypeSymlink,
        Linkname: "/tmp/attacker-target", // or "/" to demonstrate arbitrary target
    }))
    require.NoError(t, tw.Close())

    err := SetCustomHooks(ctx, logger, locator, txManager, &buf, repo)
    // Depending on vote-hash walk behavior for the symlink target, this may
    // error out (e.g. "is a directory") or succeed.
    // If it succeeds:
    fi, lerr := os.Lstat(filepath.Join(repoPath, "custom_hooks"))
    require.NoError(t, lerr)
    require.True(t, fi.Mode()&fs.ModeSymlink != 0, "custom_hooks should not be a symlink")
    target, _ := os.Readlink(filepath.Join(repoPath, "custom_hooks"))
    require.Equal(t, "/tmp/attacker-target", target)
}

func ExtractHooks(ctx context.Context, logger log.Logger, reader io.Reader, path string, stripPrefix bool) error {
	// GNU tar does not accept an empty file as a valid tar archive and produces
	// an error. Since an empty hooks tar is symbolic of a repository having no
	// hooks, the reader is peeked to check if there is any data present.
	buf := bufio.NewReader(reader)
	if _, err := buf.Peek(1); errors.Is(err, io.EOF) {
		return nil
	}

	stripComponents := "0"
	if stripPrefix {
		stripComponents = "1"
	}

	cmdArgs := []string{"-xf", "-", "-C", path, "--strip-components", stripComponents, CustomHooksDir}

	var stderrBuilder strings.Builder
	cmd, err := command.New(ctx, logger, append([]string{"tar"}, cmdArgs...),
		command.WithStdin(buf),
		command.WithStderr(&stderrBuilder))
	if err != nil {
		return fmt.Errorf("executing tar command: %w", err)
	}

	if err := cmd.Wait(); err != nil {
		stderr := stderrBuilder.String()

		// GNU and BSD tar versions have differing errors when attempting to
		// extract specified members from a valid tar archive. If the tar
		// archive is valid the errors for GNU and BSD tar should have the
		// same prefix, which can be checked to validate whether the expected
		// content is present in the archive for extraction.
		if strings.HasPrefix(stderr, "tar: custom_hooks: Not found in archive") {
			return nil
		}

		return structerr.New("waiting for tar command completion: %w", err).WithMetadata("stderr", stderr)
	}

	return nil
}
