### Title
Unhardened Bancor-style Exchange math (`ExchangeProcessor`) uses double-precision floating point, allowing precision-loss extraction of pool funds - (File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java)

### Summary
The reported Soda incident stems from a liquidation/pricing loophole allowing an attacker to extract far more value than deposited. In java-tron's on-chain Bancor-style token exchange module, the default (non-hardened) trade/inject/withdraw math path is computed with `double` floating-point arithmetic in `ExchangeProcessor`, rather than the exact `BigDecimal` math used by `SafeExchangeProcessor`. Any unprivileged account can reach this path directly via `ExchangeTransactionContract`, `ExchangeInjectContract`, and `ExchangeWithdrawContract` broadcast transactions.

### Finding Description
`ExchangeCapsule.transaction()` selects between `ExchangeProcessor` (floating point) and `SafeExchangeProcessor` (BigDecimal, "hardened") based on the `allowHardenExchangeCalculation` dynamic property, controlled only via committee proposal: [1](#0-0) 

`AbstractExchangeActuator.allowHarden()` simply reads this store flag, and `subtractExact`/`addExact` in the same class fall back to plain (non-checked) `long` arithmetic when hardening is disabled: [2](#0-1) 

When hardening is not enabled, `ExchangeProcessor.exchange()` computes the Bancor formula (`exchangeToSupply` / `exchangeFromSupply`) using `double` and `Maths.pow(...)` instead of exact decimal math: [3](#0-2) 

This is reachable directly by any signed `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` transaction through `ExchangeTransactionActuator.execute()`, which calls `exchangeCapsule.transaction(tokenID, tokenQuant, dynamicStore.allowStrictMath(), allowHarden())` and then credits the caller's account with the (possibly favorably-rounded) `anotherTokenQuant`: [4](#0-3) 

The only guard on the trade output is `anotherTokenQuant < tokenExpected` in `doValidate()`, i.e. a caller-supplied minimum, which does nothing to prevent the attacker from *choosing* trade sizes/timing that exploit floating-point rounding to their favor (e.g. slicing large trades into many small ones or picking balances near representation boundaries) since `expected` is attacker-controlled and only enforces a floor, not correctness of the AMM invariant: [5](#0-4) 

This mirrors the Soda root cause: a pricing/settlement computation with insufficient numerical rigor let a participant repeatedly extract more value than the pool's true collateralization supported, and the loophole was only exploitable/exploited before an emergency fix. Here, the "fix" already exists in the codebase in the form of `SafeExchangeProcessor`/`allowHardenExchangeCalculation`, but it is a governance-gated, opt-in flag — meaning any deployment or historical period where the flag is `false` (including the default state before the proposal is passed) leaves the floating-point path live and reachable by ordinary users.

### Impact Explanation
If `allowHardenExchangeCalculation` is not enabled, an attacker can use crafted sequences of `ExchangeTransactionContract` (and `ExchangeInjectContract`/`ExchangeWithdrawContract`) with carefully chosen `quant` values to accumulate rounding gains from the `double`-based Bancor formula, incrementally draining an Exchange pool's `firstTokenBalance`/`secondTokenBalance` beyond what is economically justified — a fund-theft/pool-insolvency condition matching the "unbacked balance" / "theft of funds" impact class, analogous to Soda's mortgage-pool drain.

### Likelihood Explanation
The floating-point path is the actual default/legacy behavior of this feature and is reachable by any unprivileged account holding TRX/tokens and knowledge of an existing exchange pair — no special privilege is required, only ordinary signed transactions. Exploitability depends on whether `allowHardenExchangeCalculation` has been enabled on a given network (mainnet history/config would need to be checked, which is outside what the index can confirm), so likelihood is Medium: it is a real, reachable numerical-integrity weakness in the unhardened code path, but the codebase already contains a hardening flag intended to close it, and the practical impact size depends on floating point drift magnitude per trade, which typically requires many repeated transactions to accumulate materially.

### Recommendation
- Make `SafeExchangeProcessor` (BigDecimal-exact math) the sole/default computation path for `ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator`, removing the floating-point `ExchangeProcessor` fallback, or force `allowHardenExchangeCalculation` to `true` unconditionally rather than leaving it a togglable proposal.
- Add pool-invariant checks after every trade/inject/withdraw (e.g., verify `firstTokenBalance * secondTokenBalance` does not decrease disproportionately) to detect and reject rounding-based value extraction regardless of which processor is active.

### Proof of Concept
Conceptual (cannot be executed without live proposal state):
1. On a network/period where `allowHardenExchangeCalculation` is `0` (unhardened), create/find an `Exchange` pair via `ExchangeCreateContract`.
2. Repeatedly broadcast small `ExchangeTransactionContract` trades against the pool, choosing `quant`/`tokenID` values that push `exchangeToSupply`/`exchangeFromSupply` double-precision rounding in the attacker's favor (per `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply`, both cast final `double` results to `long` via truncation, which can be biased by choice of inputs): [6](#0-5) 
3. Each trade only needs to satisfy `anotherTokenQuant >= tokenExpected`, which the attacker sets to their own computed minimum, so validation does not block the exploit: [5](#0-4) 
4. Over many iterations, accumulated rounding gains drain `firstTokenBalance`/`secondTokenBalance` from the pool disproportionately to what was deposited, mirroring the Soda incident's fund drain via unaddressed pricing/settlement precision loopholes.

Note: I could not verify from the index whether `allowHardenExchangeCalculation` is enabled on the current live network or by default in genesis config — this would need to be confirmed in a full repo checkout/deployment config before treating this as confirmed-exploitable in production, since the code contains a purpose-built hardened mode.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
