### Title
Exchange liquidity injection is permanently bricked when token balance ratios are skewed - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java])

### Summary
`ExchangeCreateActuator` allows any unprivileged account to create a bancor-style exchange pair with an arbitrary token-balance ratio, with no upper bound on how skewed that ratio can be (only a per-token `getExchangeBalanceLimit()` ceiling and a `> 0` floor). Because `ExchangeInjectActuator` computes the counter-token amount using integer (floor) division and then strictly rejects any result that rounds to `0`, a legitimately created exchange with a sufficiently skewed ratio permanently and irrecoverably blocks the `ExchangeInjectContract` operation for the minority-value token, exactly mirroring the Sherlock report's pattern: an allowed configuration (0% Honorarium Rate there, an extreme token ratio here) collides with a downstream strict inequality check, causing a documented/expected feature to be permanently unusable once the configuration is chosen.

### Finding Description
`ExchangeCreateActuator.doValidate()` only checks: [1](#0-0) 
i.e. both balances must be `> 0` and `<= balanceLimit`. There is no check relating the two balances to each other, so a ratio such as `firstTokenBalance = 1` and `secondTokenBalance = balanceLimit` (or any similarly extreme ratio) is a fully valid, protocol-permitted configuration — just like a 0% Honorarium Rate was a fully valid, documented configuration in the original report.

`ExchangeInjectActuator.doValidate()` then computes the counter-token quantity using `BigInteger` floor division: [2](#0-1) 
If `tokenQuant * otherBalance / thisBalance` floors to `0` (which happens whenever the injected token is the "cheap" side of a highly skewed pair and the injected quantity isn't large enough to produce at least 1 unit of the other side), the actuator throws `"the calculated token quant must be greater than 0"` — permanently rejecting the transaction, exactly analogous to `totalCollateralAmount > bidAmount` failing when `feeAmount == 0` in the original report.

Because the ratio is fixed at exchange-creation time and there is no actuator to rebalance or recreate an existing `ExchangeCapsule`'s ratio, once the ratio is skewed enough, `ExchangeInjectActuator` becomes permanently unusable for injecting the minority-value token in any economically reasonable (small) amount — the only way to "fix" it is to inject enormous amounts of the minority token to bump the floor-division result above zero, which may not be economically feasible for the creator, mirroring the "redeploy with 1 wei" workaround discussed for the original report.

### Impact Explanation
This breaks core, advertised functionality (adding liquidity to an on-chain Bancor exchange) for a configuration the protocol explicitly allows and does not forbid or warn against in validation. The exchange creator can be permanently denied the ability to inject additional liquidity into their own exchange, effectively freezing the exchange's growth/rebalancing capability once created with a skewed ratio — a Medium-severity, protocol-functionality-breaking bug reachable by any unprivileged account issuing an `ExchangeCreateContract` followed by `ExchangeInjectContract`, with no code path to remediate the already-created exchange.

### Likelihood Explanation
Likelihood is moderate: no malicious intent or privileged access is required — a normal user simply creating an exchange between a very cheap token and a very valuable one (or between a token and TRX where quantities differ by many orders of magnitude, which is common for typical TRC10 economics) can trivially trigger the skewed ratio, then discover that further injection is impossible. Both `ExchangeCreateContract` and `ExchangeInjectContract` are reachable via ordinary signed transactions with no special permissions.

### Recommendation
Change the strict floor check in `ExchangeInjectActuator.doValidate()` (and mirror any equivalent check in exchange trading paths) to avoid outright rejecting valid injections, e.g., round up (`ceil`) instead of floor for the computed counter-token amount, or require the caller to inject at least the minimum amount needed for a non-zero counter-quantity and surface that minimum in the error, rather than an unconditional revert. Additionally, consider bounding the allowed initial/injected balance ratio in `ExchangeCreateActuator`/`ExchangeInjectActuator` to prevent effectively unusable pools from being created in the first place.

### Proof of Concept
1. Attacker/creator calls `ExchangeCreateContract` with `firstTokenId = TRX`, `firstTokenBalance = 1`, `secondTokenId = X`, `secondTokenBalance = <exchangeBalanceLimit>` — this passes `ExchangeCreateActuator.doValidate()` since both balances are `> 0` and `<= balanceLimit`. [1](#0-0) 
2. Creator (or any account, subject to the `is creator` check) later calls `ExchangeInjectContract` to inject a small/reasonable amount of `TRX` (`tokenQuant`), expecting to receive a proportional amount of `X`.
3. `anotherTokenQuant = secondTokenBalance * tokenQuant / firstTokenBalance` computed via floor division; if `tokenQuant` is not large enough relative to the `1 : balanceLimit` ratio, `anotherTokenQuant` rounds to `0`. [3](#0-2) 
4. The actuator throws `"the calculated token quant must be greater than 0"`, unconditionally rejecting the transaction. [4](#0-3) 
5. There is no on-chain remedy for the already-created exchange's ratio, so liquidity injection for the minority-value token is permanently blocked for any economically reasonable amount.
