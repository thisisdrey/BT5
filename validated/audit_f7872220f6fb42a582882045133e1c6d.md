### Title
Recovery pallet's `control_inherited_account` may forward privileged calls with insufficiently checked origin filters, allowing filter bypass via nested dispatch wrappers - (File: `substrate/frame/recovery/src/lib.rs`)

### Summary
The custom `pallet-recovery` in this repo introduces an `inheritor` concept: after a recovery attempt completes, the `inheritor` account can call `control_inherited_account` to dispatch an arbitrary `RuntimeCall` "as" the lost/recovered account [1](#0-0) . The pallet apparently applies a filter to prevent the inheritor from executing certain sensitive calls (e.g. `slash_attempt`, `set_friend_groups`) on behalf of the lost account, but the existing regression tests explicitly document that this filter "only checks the outer call" [2](#0-1) , meaning a disallowed call can potentially be smuggled inside a public dispatch wrapper like `pallet_utility::Call::batch`, mirroring the report's core issue: insufficiently validated intermediate/forwarded call data allows an untrusted party to spoof or escalate an action that should have been rejected.

### Finding Description
The external report's broken invariant is "an intermediary value passed through a forwarding call (`remaining_accounts` in the Solana OFT CPI) is not independently validated against the expected identity/authority before being trusted, allowing the invoker to smuggle unauthorized state into a privileged operation." The closest verified local analog is the `inheritor`-controlled dispatch path in `pallet-recovery`:

- `control_inherited_account` lets the `inheritor` account dispatch an arbitrary boxed `RuntimeCall` acting as the recovered/lost account [1](#0-0) .
- Two regression tests were added specifically to check that this dispatch path cannot be abused to slash higher-priority recovery attempts or wipe friend groups belonging to other inheritors, and that wrapping the disallowed inner call inside `pallet_utility::Call::batch` does not bypass the filter [3](#0-2) .
- The test comment explicitly states: "The batch dispatched as ALICE, but the inner slash should have still executed since our filter only checks the outer call" [4](#0-3) , indicating the filter mechanism inspects the outer `RuntimeCall` variant rather than recursively inspecting nested calls dispatched by wrapper pallets such as `pallet-utility`'s `batch`/`batch_all`/`dispatch_as` or `pallet-proxy`.

This is structurally the same bug class as the report: a privileged forwarding entry point trusts a nested/intermediate payload (the inner call inside a wrapper) without re-validating it against the same authorization rule applied to the top-level call, letting the attacker (the `inheritor`, an otherwise unprivileged actor with respect to *other* friend groups/attempts on the same lost account) escalate to actions they should not be permitted to perform.

I was not able to retrieve the actual filter implementation (e.g. `add_filter` closure or `is_sub_type` checks) inside `control_inherited_account` in `substrate/frame/recovery/src/lib.rs` before the iteration budget was exhausted, so I cannot confirm with certainty whether the bypass is currently live or has already been closed by matching logic (the tests could be asserting the fix is *effective*, i.e. currently passing, rather than documenting an open bug).

### Impact Explanation
If the filter genuinely only inspects the outer call type and does not recurse into `pallet_utility::batch`/`batch_all`/`dispatch_as` (or any other call-forwarding pallet reachable from the `control_inherited_account` call), an `inheritor` of one friend group could use the lost account's authority to slash a competing, higher-priority recovery attempt's security deposit or clear another group's friend-group configuration — theft of a security deposit and unauthorized state manipulation, matching "unauthorized execution or origin escalation" and "theft ... or unbacked mint" style impacts in the pivot list.

### Likelihood Explanation
The attacker only needs to be the `inheritor` of any (even lowest-priority) friend group on the account, i.e. an otherwise legitimate but privilege-bounded actor — no validator, relayer, governance, or leaked-key assumption is required, which matches the "unprivileged attacker" bar required by the task. However, since I could not confirm the current filter implementation, I cannot assert this is presently exploitable rather than already mitigated.

### Recommendation
Ensure the filter applied inside `control_inherited_account` recursively validates every nested call reachable through wrapper pallets (`pallet-utility`'s `batch`, `batch_all`, `force_batch`, `dispatch_as`, `if_else`, `pallet-proxy`, etc.), analogous to how the external report recommends validating every account in `remaining_accounts` against the expected signer rather than trusting the outer call/context alone. Use `GetDispatchInfo`/`IsSubType`-based recursive call inspection (similar to how `pallet-recovery`'s own tests exercise this) instead of a single top-level match.

### Proof of Concept
See the existing repository test that reproduces the exact attack path (wrap `RecoveryCall::slash_attempt` inside `pallet_utility::Call::batch`, then invoke it via `Recovery::control_inherited_account`) [3](#0-2) . /// Verify that wrapping a recovery call inside Utility::batch does not bypass the filter.
#[test]
fn inheritor_cannot_bypass_filter_via_utility_batch() {
	new_test_ext().execute_with(|| {
		let family = FriendGroupOf::<T> {
			friends: friends([BOB, CHARLIE]),
			friends_needed: 1,
			inheritor: DAVE,
			inheritance_delay: 10,
			inheritance_priority: 0,
			cancel_delay: 5,
		};
		let friends_group = FriendGroupOf::<T> {
			friends: friends([CHARLIE, EVE]),
			friends_needed: 1,
			inheritor: FERDIE,
			inheritance_delay: 1,
			inheritance_priority: 1,
			cancel_delay: 5,
		};
		assert_ok!(Recovery::set_friend_groups(signed(ALICE), vec![family, friends_group]));

		// Friends group recovers first (CHARLIE's auto-approval reaches the threshold).
		assert_ok!(Recovery::initiate_attempt(signed(CHARLIE), ALICE, 1));
		inc_block_number(2);
		assert_ok!(Recovery::finish_attempt(signed(EVE), ALICE, 1));
		assert_eq!(Recovery::inheritor(ALICE), Some(FERDIE));

		// Family initiates higher-priority attempt
		assert_ok!(Recovery::initiate_attempt(signed(BOB), ALICE, 0));
		let bob_balance_before = <Test as Config>::Currency::total_balance(&BOB);

		// FERDIE wraps the slash inside a utility::batch call to try to bypass the filter
		let slash_call: RuntimeCall = RecoveryCall::slash_attempt { friend_group_index: 0 }.into();
		let batch_call: RuntimeCall =
			pallet_utility::Call::batch { calls: vec![slash_call] }.into();
		assert_ok!(Recovery::control_inherited_account(
			signed(FERDIE),
			ALICE,
			Box::new(batch_call),
		));

		// The batch dispatched as ALICE, but the inner slash should have still executed
		// since our filter only checks the outer call. Check if BOB was slashed:
		let bob_balance_after = <Test as Config>::Currency::total_balance(&BOB);
		let was_slashed = bob_balance_after < bob_balance_before;

		if was_slashed {
			panic!(
				"BYPASS: recovery call filter was circumvented via utility::batch! \
				 BOB lost {} from security deposit slash.",
				bob_balance_before - bob_balance_after
			);
		}
