Audit Report

## Title
Stale `ChildrenCuratorFees` accumulation via curator reassignment causes parent bounty curator fee under-payment / fund lock - ([File: substrate/frame/child-bounties/src/lib.rs])

## Summary
`pallet-child-bounties` stores a single monotonic accumulator, `ChildrenCuratorFees<T>`, per parent bounty, which is incremented every time `propose_curator` is called on a child bounty and is later subtracted from the parent bounty's curator fee in `pallet-bounties::claim_bounty`. Because `unassign_curator` returns a child bounty to the `Added` state without decrementing this accumulator, and `propose_curator` can then legitimately be called again on that same child bounty index, the accumulator double-counts abandoned curator-fee commitments that are never actually paid out, causing the parent curator's `final_fee` to be under-computed.

## Finding Description
`propose_curator` unconditionally adds the newly proposed fee to the shared accumulator on every call: [1](#0-0) 

`unassign_curator` is reachable by any signed account (including a non-curator, non-privileged account) once a child bounty's `update_due` has elapsed while `Active`, and it resets `child_bounty.status` back to `ChildBountyStatus::Added` without ever touching `ChildrenCuratorFees`: [2](#0-1) 

Because the child bounty is `Added` again, the parent curator can call `propose_curator` a second time on the same `child_bounty_id`, which again adds the new fee to `ChildrenCuratorFees` at line 389-391, without any subtraction of the first (abandoned) fee. `claim_child_bounty`, the only extrinsic that pays out a child bounty's `fee`, also never adjusts `ChildrenCuratorFees`: [3](#0-2) 

Finally, `pallet-bounties::claim_bounty` reads this inflated accumulator via `T::ChildBountyManager::children_curator_fees(bounty_id)` and subtracts it from the parent curator's fee: [4](#0-3) 

There is only a `debug_assert!(children_fee <= fee)` guard, which is a no-op in release builds and does not prevent or correct the under-payment — it only panics in debug builds, and even then does not fix accounting. The corrupted value is `ChildrenCuratorFees<T>` (per parent bounty), which flows into `final_fee` in `claim_bounty`, silently reducing (potentially to zero via `saturating_sub`) the amount paid to the rightful parent bounty curator.

## Impact Explanation
This violates the "conserve value and settle exactly once to the rightful beneficiary" invariant for treasury-derived bounty funds. The parent curator's rightful fee can be reduced or entirely zeroed out by phantom fee commitments that were never disbursed to anyone, and the corresponding balance remains stranded in the bounty's sub-account with no extrinsic path to reclaim it for the correct beneficiary — a permanent partial fund lock / misallocation matching the "permanent user-fund lock" and "duplicate settlement or payout" impact categories in the gate.

## Likelihood Explanation
The unassign path used to trigger the bug does not require privileged governance: any signed account can call `unassign_curator` on an `Active` child bounty once `update_due` has passed (curator inactivity), which is a normal, expected part of the documented bounty lifecycle. Repeating `propose_curator` → `unassign_curator` cycles on the same child-bounty index is not exotic, and the parent curator's subsequent re-proposal of a curator (a routine, expected governance workflow) is sufficient to trigger the double count — no leaked keys, malicious validators, or off-repo infrastructure control are needed.

## Recommendation
Track curator fee commitments per child-bounty (e.g., only add the current live fee once and remove/replace it on reassignment) instead of an append-only accumulator, or explicitly subtract the previous fee from `ChildrenCuratorFees` inside `unassign_curator` before the status is reset to `Added`. Alternatively, compute `children_fee` at parent-claim time by summing the `fee` field of only the currently-live (`ChildBounties` map) child bounties for that parent, removing reliance on the never-reconciled accumulator.

## Proof of Concept
1. Create and fund parent bounty `B`; parent curator accepted, `Active`.
2. Parent curator calls `add_child_bounty` to create child bounty `C0`, then `propose_curator(B, C0, curator_A, fee=100)`; `curator_A` accepts → `ChildrenCuratorFees[B] = 100`.
3. Let `BountyUpdatePeriod` elapse without an update from `curator_A` so `update_due` is in the past while `C0` is `Active`.
4. Any unprivileged signed account calls `unassign_curator(B, C0)`; because `update_due < now`, this succeeds via the non-curator branch, slashing `curator_A`'s deposit and moving `C0` back to `Added`. `ChildrenCuratorFees[B]` remains `100`.
5. Parent curator calls `propose_curator(B, C0, curator_B, fee=100)` again; `curator_B` accepts, is awarded, and calls `claim_child_bounty`, receiving fee `100`. `ChildrenCuratorFees[B]` is now `200` (never decremented for the abandoned `curator_A` commitment, nor at claim time).
6. Only `100` was ever paid to any child curator, but `ChildrenCuratorFees[B] = 200`.
7. Parent curator calls `claim_bounty(B)`; with parent curator fee `F_parent = 150`, `final_fee = 150.saturating_sub(200) = 0`, permanently under-paying the parent curator by `150`, which remains stranded in the bounty sub-account.

		#[pallet::call_index(5)]
		#[pallet::weight(<T as Config>::WeightInfo::claim_child_bounty())]
		pub fn claim_child_bounty(
			origin: OriginFor<T>,
			#[pallet::compact] parent_bounty_id: BountyIndex,
			#[pallet::compact] child_bounty_id: BountyIndex,
		) -> DispatchResult {
			ensure_signed(origin)?;

			// Ensure child-bounty is in expected state.
			ChildBounties::<T>::try_mutate_exists(
				parent_bounty_id,
				child_bounty_id,
				|maybe_child_bounty| -> DispatchResult {
					let child_bounty =
						maybe_child_bounty.as_mut().ok_or(BountiesError::<T>::InvalidIndex)?;

					if let ChildBountyStatus::PendingPayout {
						ref curator,
						ref beneficiary,
						ref unlock_at,
					} = child_bounty.status
					{
						// Ensure block number is elapsed for processing the
						// claim.
						ensure!(
							Self::treasury_block_number() >= *unlock_at,
							BountiesError::<T>::Premature,
						);

						// Make curator fee payment.
						let child_bounty_account =
							Self::child_bounty_account_id(parent_bounty_id, child_bounty_id);
						let balance = T::Currency::free_balance(&child_bounty_account);
						let curator_fee = child_bounty.fee.min(balance);
						let payout = balance.saturating_sub(curator_fee);

						// Unreserve the curator deposit. Should not fail
						// because the deposit is always reserved when curator is
						// assigned.
						let _ = T::Currency::unreserve(curator, child_bounty.curator_deposit);

						// Make payout to child-bounty curator.
						// Should not fail because curator fee is always less than bounty value.
						let fee_transfer_result = T::Currency::transfer(
							&child_bounty_account,
							curator,
							curator_fee,
							AllowDeath,
						);
						debug_assert!(fee_transfer_result.is_ok());

						// Make payout to beneficiary.
						// Should not fail.
						let payout_transfer_result = T::Currency::transfer(
							&child_bounty_account,
							beneficiary,
							payout,
							AllowDeath,
						);
						debug_assert!(payout_transfer_result.is_ok());

						// Trigger the Claimed event.
						Self::deposit_event(Event::<T>::Claimed {
							index: parent_bounty_id,
							child_index: child_bounty_id,
							payout,
							beneficiary: beneficiary.clone(),
						});

						// Update the active child-bounty tracking count.
						ParentChildBounties::<T>::mutate(parent_bounty_id, |count| {
							count.saturating_dec()
						});

						// Remove the child-bounty description.
						ChildBountyDescriptionsV1::<T>::remove(parent_bounty_id, child_bounty_id);

						// Remove the child-bounty instance from the state.
						*maybe_child_bounty = None;

						Ok(())
					} else {
						Err(BountiesError::<T>::UnexpectedStatus.into())
					}
				},
			)
		}
