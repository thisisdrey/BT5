### Title
Data race on shared mutable `JumpTable` in `OperationRegistry` corrupts TVM opcode dispatch table under concurrent execution - (File: `actuator/src/main/java/org/tron/core/vm/OperationRegistry.java`)

### Summary
`OperationRegistry` exposes singleton, mutable `JumpTable` instances (`tableMap.get(LATEST_VERSION)` for on-chain execution and `CONSTANT_CALL_TABLE` for read-only calls) that are returned to every caller via `getTable`/`prepareAndGetTable` and then mutated in place by `adjustTable()` on every single invocation, with no synchronization whatsoever [1](#0-0) . The backing `Operation[]` array in `JumpTable` is written via a plain, unsynchronized `set()` and read via a plain `get()` [2](#0-1) . This mirrors the reported bug class exactly: an object that "looks" safe to share and use concurrently (the code comment even calls `CONSTANT_CALL_TABLE` "a dedicated instance… isolated from the shared consensus table," implying a safety guarantee) is in fact a mutable, non-thread-safe structure that is unconditionally handed out to and mutated by every caller — the same illusion-of-safety root cause as `SyncRef<T>` unconditionally implementing `Sync` for non-`Sync` `T`.

### Finding Description
Every VM invocation calls `OperationRegistry.prepareAndGetTable(isConstantCall)`, which fetches the single shared `JumpTable` instance and then calls `adjustTable(table)` [3](#0-2) . `adjustTable` performs multiple non-atomic in-place mutations of the shared array (`adjustMemOperations`, `adjustVoteWitness`, `adjustSelfdestruct`), each of which replaces one or more entries in the `Operation[] table` depending on live `VMConfig`/dynamic-property flags such as `allowHigherLimitForMaxCpuTimeOfOneTx`, `allowTvmOsaka`, `allowEnergyAdjustment`, and `allowTvmSelfdestructRestriction` [4](#0-3) .

Both the "shared consensus table" (`tableMap.get(LATEST_VERSION)`) and `CONSTANT_CALL_TABLE` are `static` singletons returned by reference to every caller [5](#0-4) , and `getTable`/`prepareAndGetTable` provide no locking around the read-modify-mutate sequence [6](#0-5) . The `CONSTANT_CALL_TABLE` path is reachable by any anonymous API client through `TriggerConstantContract` (Wallet) and the JSON-RPC `eth_call` equivalent in `TronJsonRpcImpl`, both of which are served on a multithreaded request pool with no execution-serializing lock (constant calls don't touch the revoking-store commit path, so there is no reason for them to be serialized). Consequently, two or more concurrent constant-call requests each invoke `prepareAndGetTable(true)`, and each independently executes `table.set(...)` on the very same array while other threads concurrently call `table.get(op)` from inside `VM.play()` to fetch cost function/action for the opcode currently being executed. A test explicitly documents that non-constant calls "must receive the shared consensus table itself" (i.e., the same instance, not a copy) [7](#0-6) , confirming the sharing is intentional/by-design rather than accidental aliasing.

Because `adjustTable()` performs several independent, non-atomic `set()` calls, a reader thread can observe an inconsistent, "torn" combination of table entries mid-transition — e.g., an `Operation` for `MLOAD` reflecting the pre-flag-flip cost function alongside a `SUICIDE`/`SELFDESTRUCT` entry reflecting the post-flip (restricted or unrestricted) semantics, depending on exactly which `set()` calls have completed when the reader samples the array. This can happen at any moment two threads execute the registry concurrently, but is most consequential exactly around a maintenance-cycle/hard-fork activation, when `VMConfig` flags (driven by on-chain `DynamicPropertiesStore` proposals) flip and multiple `adjustTable()` calls race across threads mutating and reading the same array without any happens-before relationship.

### Impact Explanation
For the `CONSTANT_CALL_TABLE`, a race window during a feature-flag flip can cause different, unprivileged API clients issuing concurrent read-only `TriggerConstantContract`/`eth_call` requests to observe inconsistent, non-deterministic opcode costs or opcode-enablement (e.g., a call that should be rejected because an opcode is not yet activated could instead be evaluated with a torn table that momentarily reports it as active, or vice versa), silently corrupting the results served by the node's query API — this is an "API can no longer reliably serve correct results" class of impact for a fully unauthenticated, remotely reachable surface.

If the same shared, non-constant `LATEST_VERSION` table is ever accessed by more than one execution thread at the same instant (e.g. concurrent transaction pre-validation/execution paths reachable from `Manager.pushTransaction` when transactions are broadcast concurrently by many senders), the same torn-table condition could cause the executing node to apply energy costs or opcode legality that differs from what other, non-racing full nodes compute for the identical transaction and identical `VMConfig` state — a consensus-critical non-determinism that risks a chain split between nodes that happen to race at that instant and nodes that do not.

### Likelihood Explanation
The window for a materially different Operation to be substituted only opens during the (rare, governance-triggered) moments a relevant `VMConfig`/dynamic-property flag changes value, which happens at fixed hard-fork/maintenance boundaries rather than continuously — this bounds likelihood to Medium rather than High. However, the concurrent invocation itself (multiple simultaneous `TriggerConstantContract`/`eth_call` requests) requires no special privilege and is trivially triggerable by any anonymous client at any time, so the "hazard" (shared mutable state, no synchronization) is always present; only the "observable divergence" requires the flag-flip timing coincidence. I was not able to fully verify from the indexed code whether `Manager.pushTransaction()` (broadcast path) is serialized by `transactionLock`/`pushTransactionQueue` in a way that prevents true concurrent VM execution on the non-constant shared table — this affects whether the consensus-split scenario (vs. the constant-call query-corruption scenario, which is unambiguously concurrent and unsynchronized) is reachable in practice.

### Recommendation
- Make `JumpTable` effectively immutable after construction (no post-publish `set()` calls), and instead have `adjustTable()` build and return a new, independent `JumpTable` copy per call (or per unique combination of active flags, cached under a lock/`ConcurrentHashMap`) rather than mutating the shared singleton in place.
- If a cache of pre-built tables per flag-combination is desired for performance, guard construction/lookup with proper synchronization (e.g., `computeIfAbsent` on a `ConcurrentHashMap<FlagsKey, JumpTable>`) so no thread ever observes a partially-mutated table.
- Add a regression test that concurrently invokes `prepareAndGetTable(true)`/`prepareAndGetTable(false)` from many threads while flipping the underlying `VMConfig` flags, and asserts that every `get(op)` result is internally consistent (i.e., either entirely pre-flip or entirely post-flip, never mixed).

### Proof of Concept
1. Start many concurrent threads (simulating concurrent `TriggerConstantContract`/`eth_call` clients), each repeatedly calling `OperationRegistry.prepareAndGetTable(true)` followed by fetching `table.get(Op.MLOAD)`, `table.get(Op.SUICIDE)` in a loop.
2. From a separate thread, toggle `VMConfig` flags that feed `adjustMemOperations`/`adjustSelfdestruct` (e.g. flip `allowTvmSelfdestructRestriction`/`allowEnergyAdjustment` repeatedly), which triggers `table.set(...)` calls into the same shared `CONSTANT_CALL_TABLE` instance concurrently with the reader threads.
3. Observe that reader threads intermittently retrieve a mix of pre-flip and post-flip `Operation` objects for different opcodes within what should be a single logically-consistent view of the table (e.g., `MLOAD` reflecting the old cost while `SUICIDE` already reflects the new restricted variant), demonstrating the unsynchronized read/write race on the shared array in `JumpTable.get`/`JumpTable.set` [8](#0-7) .

  public static JumpTable prepareAndGetTable(boolean isConstantCall) {
    JumpTable table = getTable(isConstantCall);
    // Apply configuration-dependent changes once at the top level.
    adjustTable(table);
    return table;
  }

  public static JumpTable getTable(boolean isConstantCall) {
    return isConstantCall ? CONSTANT_CALL_TABLE : tableMap.get(LATEST_VERSION);
  }

  private static void adjustTable(JumpTable table) {
    // Make the corresponding changes, excluding opcode activation.
    adjustMemOperations(table);
    adjustVoteWitness(table);
    adjustSelfdestruct(table);
  }

  public static void adjustMemOperations(JumpTable table) {
    boolean adjusted = VMConfig.allowHigherLimitForMaxCpuTimeOfOneTx();
    table.set(adjusted ? ADJUSTED_MLOAD : DEFAULT_MLOAD);
    table.set(adjusted ? ADJUSTED_MSTORE : DEFAULT_MSTORE);
    table.set(adjusted ? ADJUSTED_MSTORE8 : DEFAULT_MSTORE8);
  }

  public static void adjustVoteWitness(JumpTable table) {
    if (VMConfig.allowTvmOsaka()) {
      table.set(OSAKA_VOTEWITNESS);
    } else if (VMConfig.allowEnergyAdjustment()) {
      table.set(ADJUSTED_VOTEWITNESS);
    } else {
      table.set(DEFAULT_VOTEWITNESS);
    }
  }

  public static void adjustSelfdestruct(JumpTable table) {
    if (VMConfig.allowTvmSelfdestructRestriction()) {
      table.set(RESTRICTED_SUICIDE);
    } else if (VMConfig.allowEnergyAdjustment()) {
      table.set(ADJUSTED_SUICIDE);
    } else {
      table.set(DEFAULT_SUICIDE);
    }
  }
