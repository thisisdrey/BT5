### Title
Anti-replay window TOCTOU allows duplicate decryption of the same message counter - (File: connection_state.go)

### Summary

### Finding Description
`ConnectionState.Decrypt` implements the anti-replay check with a lock that is released between the `Check` and `Update` calls on the sliding-window replay tracker: [1](#0-0) 

The sequence is: acquire `decryptLock`, call `window.Check(messageCounter)`, release the lock, perform the actual AEAD decrypt (`DecryptDanger`), then re-acquire the lock to call `window.Update(messageCounter)`. Because the lock is dropped for the entire duration of the decrypt operation, two concurrent invocations of `Decrypt` for the *same* `messageCounter` (e.g., two threads processing two copies of the same UDP datagram, which an off-path/on-path attacker fully controls since it is just replayed ciphertext requiring no valid certificate) can both pass `Check` before either calls `Update`. Both then proceed to decrypt and hand the plaintext up to the packet-processing pipeline, and only the loser of the race on `Update` is rejected — after the duplicate has already been decrypted and processed once. `Interface.activate` shows the data path is explicitly built for concurrent multi-routine packet processing (`f.routines`, per-routine readers/writers), so multiple goroutines can call `Decrypt` on the same `ConnectionState` concurrently: [2](#0-1) 

`VerifyRelay` has the identical Check/Unlock/Decrypt/Lock/Update pattern for relayed frames: [3](#0-2) 

This is structurally the same bug class as the reported `StEthHyperdrive` issue: a state-consistency check is performed, then a slow/attacker-influenced operation runs while the "commit" of that check is deferred, allowing the same input to be processed twice against reserves/state that haven't yet reflected the first use. Here it's the anti-replay window's "reserve" (`Check`) and "commit" (`Update`) being split by an unlocked decrypt operation instead of an unlocked external call, but the reachable effect is the same: the same protocol input can be legitimately admitted twice.

### Impact Explanation
An attacker who can duplicate/replay a captured UDP packet to a target Nebula node's outside socket (no valid certificate or trusted peer status required — this is exactly the "packet on the wire" threat model) can, on a multi-routine (`routines > 1`) configuration, cause the same encrypted message counter to be decrypted and delivered to the TUN device (or forwarded, in the relay case) more than once. This is a violation of the anti-replay guarantee the `Bits` window (`bits.go`) is specifically designed to provide, and for the relay path it directly undermines the "advance the replay window on relayed packets" fix noted in the CHANGELOG (#1751) — i.e. it reopens a replay class the project has explicitly fixed once already at the `handleOutsideRelayPacket` level, but here at the `ConnectionState` primitive itself. Depending on payload content this can cause duplicate application-layer delivery, and for relay nodes, duplicate forwarding — both are concrete "traffic replay" impacts within the CA-less/no-trust reachable surface.

### Likelihood Explanation
Requires `routines > 1` (multi-queue mode), which is a commonly used performance configuration on Linux, and requires the attacker to get two copies of the same packet into different reader routines close enough in time to win the race — achievable by an on-path attacker or by duplicating a captured UDP datagram at the network layer. It does not require any certificate, valid credential, or lighthouse/peer trust.

### Recommendation
Hold `decryptLock` across the entire `Check` → `DecryptDanger` → `Update` sequence (or otherwise make the check-and-commit atomic with respect to the decrypt), matching the pattern the report recommends for `StEthHyperdrive`: don't let unrelated work happen between a state check and its corresponding commit. If holding the lock across decryption is a performance concern, use a per-counter claim (e.g., speculatively mark the counter as "in-flight" while unlocked, then finalize/rollback under lock) so a second concurrent decrypt of the same counter is rejected immediately rather than after doing the AEAD work.

### Proof of Concept
Not executed against the live codebase (no test harness run in this session); reasoning is based on static analysis of `connection_state.go` lines 61–82 and 85–108, and the confirmed multi-routine concurrent read path in `interface.go`. A confirming test would run two goroutines calling `cs.Decrypt` with an identical ciphertext/counter and assert that only one returns a plaintext result — the current code, due to the unlock/relock gap, allows both to succeed in the race window before `Update` serializes them.

func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {

	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}
