### Title
Unbounded `GetBlobsRequest.revision_paths` array enables per-RPC-handler resource-exhaustion DoS - ([File: internal/gitaly/service/blob/get_blobs.go])

### Summary
`BlobService.GetBlobs` accepts a single, non-streamed request containing a `repeated RevisionPath revision_paths` field with no upper bound on its length, and the handler synchronously loops over every entry performing one or more `git cat-file` object reads per entry before returning. This mirrors the `setPrices` gas-DoS pattern in the report: an unbounded input array drives a serial, per-element expensive operation with no cap.

### Finding Description
`validateGetBlobsRequest` only checks that the repository is set, that `revision_paths` is non-empty, and that each revision string is syntactically valid — it never bounds the number of entries in `revision_paths`: [1](#0-0) 

`GetBlobs` then calls `sendGetBlobsResponse`, which iterates every `revisionPath` in the request in a single `for` loop and, for each one, invokes `tef.FindByRevisionAndPath`, which performs an object read (`git cat-file`) and potentially a subsequent blob read: [2](#0-1) 

`FindByRevisionAndPath` caches by `(revision, dir)`, but a cache hit only avoids re-running `TreeEntries`; it still walks the cached entry slice, and any distinct `(revision, path)` pair — trivial for an attacker to vary — causes a fresh `TreeEntries` call, which itself spawns an object read through `objectReader.Object` and parses the raw tree object byte-by-byte: [3](#0-2) [4](#0-3) 

Unlike sibling RPCs in the same service — `ListBlobs`/`ListLFSPointers`/`ListAllLFSPointers`, which all expose a `limit` field to cap streamed results — `GetBlobsRequest` only has a byte `limit` for per-blob content size, not a limit on the count of `revision_paths` entries: [5](#0-4) 

Because `GetBlobs` is a unary-request/server-streaming-response RPC, the entire `revision_paths` array arrives in one gRPC message and is processed synchronously in a single goroutine before the first response chunk streaming even begins to throttle work; the only implicit cap is the gRPC max receive message size, which is not explicitly configured/reduced for this RPC in the repo (no `MaxRecvMsgSize` override was found), so an attacker can pack many thousands of small `(revision, path)` pairs into one request.

### Impact Explanation
A single caller with ordinary repository read access can submit one `GetBlobs` request with a very large `revision_paths` array (e.g., many distinct short paths under distinct/duplicated revisions) to force the Gitaly process to perform a correspondingly large number of serial `git cat-file`-backed object reads and tree parses on that RPC-handling goroutine. This consumes CPU, catfile-cache/pack-read I/O, and holds the gRPC stream open for an extended period, degrading service for other RPCs sharing the same repository's catfile cache/process, i.e., a handler-level DoS analogous to the unbounded-array gas-DoS pattern described in the source report.

### Likelihood Explanation
Likelihood is moderate: `GetBlobs` is a documented, reachable RPC requiring only standard repository-read access (no special privilege), and the proto explicitly acknowledges `revision_paths` is unbounded with no documented maximum, unlike neighboring RPCs that provide a `limit`. Exploitability depends on how large a `revision_paths` array can be packed into a single gRPC message and on Gitaly's default gRPC size/timeout/concurrency limits, which were not found to specifically bound this field.

### Recommendation
Add an explicit maximum count for `revision_paths` (and reject oversized requests with `InvalidArgument`), similar to how `ListBlobs`/`ListLFSPointers` expose `limit`; alternatively, convert `GetBlobsRequest` to a `stream` request so that per-chunk validation and concurrency/timeout limits from the transport layer apply progressively, consistent with the project's own guidance to "stream unbounded or oversized payloads" for repeated fields that can grow without limit as documented in the RPC development skill guide: [6](#0-5) 

### Proof of Concept
1. Create a repository with a commit containing at least one file.
2. Construct a `GetBlobsRequest` whose `revision_paths` contains a very large number (e.g., tens of thousands) of entries, each pointing at a distinct nonexistent path (e.g., `does-not-exist-<N>`) under the same commit ID, keeping total message size under the gRPC max message size.
3. Send the request to `BlobService/GetBlobs` and observe that the server performs one `TreeEntries`/`git cat-file` invocation per unique parent-directory cache miss and iterates the full entry list per lookup in `sendGetBlobsResponse`/`FindByRevisionAndPath`, consuming CPU/I/O proportional to the array size with no server-side cap rejecting the request up front — confirmed by the validation logic only checking non-emptiness and revision syntax, not array length: [1](#0-0) 

**Uncertainty note:** I could not verify what default gRPC `MaxRecvMsgSize` or per-RPC concurrency/timeout limits Gitaly applies in production configuration (no `MaxRecvMsgSize` references were found in the indexed portion of the repo), which would materially affect how large an array an attacker could actually submit in one request. Confirming actual exploitability (i.e., how large `revision_paths` can practically get before message-size/config limits reject the request) would require inspecting the gRPC server setup and default config, which I could not locate in this pass.

func validateGetBlobsRequest(ctx context.Context, locator storage.Locator, req *gitalypb.GetBlobsRequest) error {
	if err := locator.ValidateRepository(ctx, req.GetRepository()); err != nil {
		return err
	}

	if len(req.GetRevisionPaths()) == 0 {
		return errors.New("empty RevisionPaths")
	}

	for _, rp := range req.GetRevisionPaths() {
		if err := git.ValidateRevision([]byte(rp.GetRevision())); err != nil {
			return err
		}
	}

	return nil
}

func (tef *TreeEntryFinder) FindByRevisionAndPath(ctx context.Context, revision, path string) (*gitalypb.TreeEntry, error) {
	span, ctx := tracing.StartSpanIfHasParent(
		ctx,
		"catfile.FindByRevisionAndPatch",
		[]attribute.KeyValue{
			attribute.String("revision", revision),
			attribute.String("path", path),
		},
	)
	defer span.End()

	dir := pathPkg.Dir(path)
	cacheKey := revisionPath{revision: revision, path: dir}
	entries, ok := tef.treeCache[cacheKey]

	if !ok {
		var err error
		entries, err = TreeEntries(ctx, tef.objectReader, revision, dir)
		if err != nil {
			return nil, err
		}

		tef.treeCache[cacheKey] = entries
	}

	for _, entry := range entries {
		if string(entry.GetPath()) == path {
			return entry, nil
		}
	}

	return nil, nil
}

// TreeEntries returns the entries of a tree in given revision and path.
func TreeEntries(
	ctx context.Context,
	objectReader ObjectContentReader,
	revision, path string,
) (_ []*gitalypb.TreeEntry, returnedErr error) {
	span, ctx := tracing.StartSpanIfHasParent(
		ctx,
		"catfile.TreeEntries",
		[]attribute.KeyValue{
			attribute.String("revision", revision),
			attribute.String("path", path),
		},
	)
	defer span.End()

	if path == "." {
		path = ""
	}

	// If we ask 'git cat-file' for a path outside the repository tree it
	// blows up with a fatal error. So, we avoid asking for this.
	if strings.HasPrefix(filepath.Clean(path), "../") {
		return nil, nil
	}

	treeObj, err := objectReader.Object(ctx, git.Revision(fmt.Sprintf("%s:%s", revision, path)))
	if err != nil {
		if errors.As(err, &NotFoundError{}) {
			return nil, nil
		}
		return nil, err
	}

	objectHash, err := git.ObjectHashByFormat(treeObj.Format)
	if err != nil {
		return nil, fmt.Errorf("looking up object hash: %w", err)
	}

	// The tree entry may not refer to a subtree, but instead to a blob. Historically, we have
	// simply ignored such objects altogether and didn't return an error, so we keep the same
	// behaviour.
	if treeObj.Type != "tree" {
		if _, err := io.Copy(io.Discard, treeObj); err != nil && returnedErr == nil {
			return nil, fmt.Errorf("discarding object: %w", err)
		}

		return nil, nil
	}

	entries, err := extractEntryInfoFromTreeData(objectHash, treeObj, revision, path, treeObj.Oid.String())
	if err != nil {
		return nil, err
	}

	return entries, nil
}

// GetBlobsRequest is a request for the GetBlobs RPC.
message GetBlobsRequest {
  // RevisionPath is a combination of revision and path. All objects reachable in the subdirectory of the treeish
  // will be returned.
  message RevisionPath {
    // revision is the revision that identifies the tree-ish. Must not be empty.
    string revision = 1;
    // path is the path relative to the treeish revision that shall be searched for a blob. If the path is empty the
    // root directory of the tree-ish will be searched.
    bytes path = 2;
  }

  // repository is the repository that shall be searched.
  Repository repository = 1[(target_repository)=true];
  // revision_paths identifies the set of revision/path pairs that shall be searched for blobs.
  repeated RevisionPath revision_paths = 2;
  // limit is the maximum number of bytes we want to receive. Use '-1' to get the full blobs no matter how big.
  int64 limit = 3;
