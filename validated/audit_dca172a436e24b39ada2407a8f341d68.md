### Title
Stale-chunk equality mismatch lets `handle_unsolicited_StackerDBPushChunk` ACK a chunk version it never actually commits, serving non-canonical StackerDB inventory as canonical - ([File: stackslib/src/net/stackerdb/mod.rs])

### Summary
The external report describes a class of bug where a queued/pending mutation is validated with one equality rule, but a *different, stricter* equality rule is applied when the mutation is actually committed — allowing the system to acknowledge an action that is never actually applied, and leaving stale/mismatched state attributed to the wrong owner. The equivalent fault in `stackslib/src/net/stackerdb` is a mismatched `<` vs `<=` staleness check between the code path that decides whether to **announce** a pushed StackerDB chunk as accepted, and the code path that actually **persists** it.

### Finding Description
When a peer sends an unsolicited `StackerDBPushChunk`, `PeerNetwork::handle_unsolicited_StackerDBPushChunk` first builds a reply inventory from the *live* stored slot versions, then calls `validate_received_chunk` to decide whether the chunk is acceptable: [1](#0-0) 

This check only rejects the chunk if `data.slot_version < *expected_version` — i.e. a chunk whose `slot_version` is **equal** to what is already stored is treated as valid (not stale).

If validation succeeds, the handler immediately patches its own reply `StackerDBChunkInv` to advertise the new version and sends that reply to the peer, *before* the chunk is ever written to disk: [2](#0-1) 

The message is then forwarded to the relayer, which is the code path that actually performs the write, via `Relayer::process_stacker_db_chunks` → `StackerDBTx::try_replace_chunk`: [3](#0-2) 

But `try_replace_chunk`'s staleness check uses a *different, stricter* equality: [4](#0-3) 

`slot_desc.slot_version <= slot_validation.version` returns `StaleChunk` — i.e. a chunk whose version is equal to what is already stored is **rejected** and silently dropped (logged at `debug!` and `continue`d): [5](#0-4) 

So the exact same slot_version-equal case is accepted by the announce-path check (`<`) but rejected by the commit-path check (`<=`). This is only reachable when the same signer (or someone with a signature of theirs for that exact `(slot_id, slot_version)` pair) supplies two different `data` payloads under the same slot version — an equivocation. Because `validate_received_chunk` never compares `data_hash` against what's already stored, both payloads pass validation and get ACKed with the same `slot_version`, but only one payload ever becomes the actually-committed chunk. A remote peer that legitimately, or through delayed/duplicated network delivery, resends a chunk at the currently-stored version will be told by us (via the patched `StackerDBChunkInv`) that we now hold *their* bytes at that version, when in fact our committed chunk for that slot/version may hold different bytes (whichever write landed first). This breaks the "served vs. committed" equality StackerDB replication depends on for consistency.

### Impact Explanation
This is a High-impact issue under the "serving non-canonical state as canonical" category: an unprivileged remote peer causes the node to advertise (via `StackerDBChunkInv`) that it has stored the peer's most recently pushed chunk contents at a given slot/version, while the actual database contents for that slot/version differ. Downstream neighbors who rely on this replica's advertised inventory to decide chunk requests, and the signer/miner StackerDB protocols (`.miners`, `.signers-*`) that depend on StackerDB chunk consistency, can be misled about what is canonically stored on this replica.

### Likelihood Explanation
Triggering it requires only that a remote, unprivileged peer send an unsolicited `StackerDBPushChunk` whose `slot_version` equals the currently-stored version for that slot (a duplicate or replay), which is trivially reachable over the wire and requires no special role or secret beyond a valid signature for that slot's already-established owner key (which is required to write to any slot in the first place, same as legitimate writers). No consensus or signer decision logic is touched.

### Recommendation
Make the announce-path (`validate_received_chunk`) and commit-path (`try_replace_chunk`) staleness checks use the identical equality (`<=`), so a chunk whose version equals the currently stored version is uniformly rejected in both places, and never causes an optimistic ACK for data that will not actually be persisted.

### Proof of Concept
1. Node N stores slot `S` at version `V` with data `D1` (legitimately signed by owner key `K`).
2. Attacker (or a delayed/duplicated legitimate sender) sends `StackerDBPushChunk{slot_id: S, slot_version: V, data: D2, sig: sign_K(S,V,D2)}` to N (any signature valid for `K` over that exact `(slot_id, slot_version, hash(D2))` suffices — e.g., simply replaying/duplicating an old push carries this risk if the key ever double-signed at version V).
3. `handle_unsolicited_StackerDBPushChunk` calls `validate_received_chunk`, which passes because `V < V` is false.
4. N patches its reply `StackerDBChunkInv` to advertise slot `S` at version `V`, and sends this reply immediately to the sender, then forwards the message to the relayer for storage.
5. The relayer calls `try_replace_chunk`, which rejects the write with `StaleChunk` because `V <= V`.
6. Result: N has told the peer it holds `D2` at `(S, V)`, but its committed data remains `D1`. Any peer that trusts N's chunk inventory and skips re-downloading slot `S` version `V` will diverge from N's actual committed bytes. [1](#0-0) [4](#0-3)
