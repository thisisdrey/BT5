### Title
Floating-point precision loss in the default (non-hardened) TRC10 Exchange bancor formula allows systematic value extraction from AMM pools - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
The Tectonic incident exploited a spot-price AMM/oracle that could be moved in a single atomic sequence of transactions, letting the attacker extract far more value than deposited. The java-tron `Exchange` (TRC10 bancor-relay AMM) reachable from any signed `ExchangeTransactionContract`, `ExchangeInjectContract`, and `ExchangeWithdrawContract` has an analogous weakness: its default pricing engine, `ExchangeProcessor`, computes conversion rates with IEEE-754 `double` arithmetic instead of exact/rounded decimal math, and truncates results with a raw `(long)` cast. This is functionally equivalent to a manipulable, non-TWAP price function that an unprivileged trader can repeatedly hit with a sequence of trades to skew pool state and siphon value, mirroring the "loop and manipulate price" pattern in the report.

### Finding Description
`ExchangeCapsule.transaction()` picks between two `Processor` implementations depending on the `allowHardenExchangeCalculation` dynamic property: [1](#0-0) 

The legacy/default path, `ExchangeProcessor`, computes the bancor relay conversion entirely in `double` precision and truncates with a cast: [2](#0-1) 

This method is invoked directly from `ExchangeTransactionActuator.execute()` for every trade a user submits against a TRC10↔TRC10 or TRX↔TRC10 pool, with the resulting quantities immediately applied to both the pool balances and the trader's account balance: [3](#0-2) 

Because `Math.pow` on `double` is not exact and the intermediate `issuedSupply`/`exchangeBalance` values are truncated toward the attacker-favorable direction depending on trade size and direction, an attacker who repeatedly trades back and forth through the same pool (buy then sell, or many small trades) can accumulate rounding bias in their favor across a sequence of transactions within the same block — effectively "looping" against the AMM's price function the same way the Tectonic attacker looped borrow/re-supply against TONIC's manipulable price. `ExchangeInjectActuator` and `ExchangeWithdrawActuator` compound the risk because they also read the current (attacker-influenced) pool ratio to compute injected/withdrawn "another token" amounts using `firstTokenBalance`/`secondTokenBalance` that the attacker just moved via `ExchangeTransactionActuator` in a prior transaction of the same block: [4](#0-3) [5](#0-4) 

A hardened, `BigDecimal`-based processor (`SafeExchangeProcessor`) with exact overflow checks exists as a fix, but it is gated behind the `allowHardenExchangeCalculation` dynamic property and only used when `allowHarden()` returns true: [6](#0-5) [7](#0-6) 

I was unable to conclusively verify, within the available index, whether `allowHardenExchangeCalculation` defaults to enabled on current production configurations or must still be turned on via a committee proposal (`ProposalUtil`/`ProposalService` reference this property). If it is not universally enabled on mainnet, the floating-point path described above is the live, reachable behavior for `ExchangeTransactionContract`.

### Impact Explanation
If the legacy `ExchangeProcessor` path is active, an unprivileged account can submit ordinary `ExchangeTransactionContract` transactions to repeatedly exploit floating-point truncation bias, extracting TRX/TRC10 balances from a pool at the expense of the pool creator/other traders — a permanent, unbacked-balance-style loss for exchange participants, analogous in kind (price/exchange-rate manipulation causing fund drain) to the Tectonic incident, though smaller in blast radius since java-tron has no lending/borrowing market to amplify it further.

### Likelihood Explanation
Exploitation only requires normal signed transactions from any account with TRX/TRC10 balance and no special privileges; no consensus, witness, or node compromise is needed. The magnitude of extractable value per trade is small (rounding-level), so this is a Medium-severity, incrementally-exploitable issue rather than an instant multi-million-dollar drain, and its real-world severity depends on the still-unverified default state of `allowHardenExchangeCalculation`.

### Recommendation
Make `SafeExchangeProcessor` (or an equivalent exact/rounded-decimal engine with strict overflow and monotonicity checks) the unconditional default for all exchange math, removing the double-precision `ExchangeProcessor` code path entirely (or restricting it to historical replay only), and add pool-ratio-deviation limits (e.g., max price impact per transaction, or a TWAP-based sanity check) in `ExchangeTransactionActuator`/`ExchangeInjectActuator`/`ExchangeWithdrawActuator` validation to bound single-transaction price movement.

### Proof of Concept
1. Create a TRC10↔TRC10 (or TRX↔TRC10) exchange pool via `ExchangeCreateContract`.
2. On a node/network where `allowHardenExchangeCalculation` is not enabled, repeatedly submit small `ExchangeTransactionContract` trades alternating direction (sell token A → token B, then sell token B → token A) using the attacker's own account.
3. Because `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` use `double` math and truncate with `(long) issuedSupply`/`(long) exchangeBalance`, observe that after many round-trip trades the attacker's combined token+TRX balance increases relative to the pool's total reserves, while the pool's `firstTokenBalance`/`secondTokenBalance` invariant (`ExchangeCapsule.transaction`) is not re-validated against an external decimal-precision oracle, confirming exploitable rounding-based value leakage from the pool.

package org.tron.core.capsule;

import java.math.BigDecimal;
import java.math.RoundingMode;
import lombok.extern.slf4j.Slf4j;
import org.tron.common.math.StrictMathWrapper;

@Slf4j(topic = "capsule")
public class SafeExchangeProcessor implements ExchangeCapsule.Processor {

  private static final BigDecimal SUPPLY = BigDecimal.valueOf(1_000_000_000_000_000_000L);

  public static final SafeExchangeProcessor INSTANCE = new SafeExchangeProcessor();

  private SafeExchangeProcessor() {

  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
}
