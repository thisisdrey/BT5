**Reasoning:**

`Sep53::prehash` in `crates/signatures/sep53/src/lib.rs` builds `"Stellar Signed Message:\n" || msg` and hashes it with `defuse_digest::sha2::Sha256`, which is a `digest_cfg!`-generated type selecting between `near_sdk_env::sha256_array` (when compiled `cfg(near)`, i.e. on-chain/wasm) and the pure-Rust `::sha2::Sha256` crate otherwise. [1](#0-0) [2](#0-1) [3](#0-2) 

Crucially, the two backends are wrapped by `DigestFn`, which buffers all `Update::update` calls into a single `Vec<u8>` and only computes the digest once at `finalize_into`, calling `F::digest(&self.data)` a single time. This means `chain_update` (used twice by `prehash` for the prefix and the message) is functionally equivalent to a single-shot digest call over the concatenated bytes on both backends — there is no incremental/streaming divergence between the two code paths. [4](#0-3) 

The remaining question is whether the NEAR host function `sha256` (wrapped by `near_sdk_env::sha256_array`) computes a digest that differs from the standard `sha2` crate's SHA-256 for the same bytes, including at boundary lengths (empty input, 55/56/64-byte block boundaries, etc.). SHA-256 is a fully specified, deterministic algorithm (FIPS 180-4), and NEAR's `sha256` host function is a well-established, widely used primitive across the NEAR ecosystem that computes standard SHA-256 — there is no known or demonstrable divergence between it and the `sha2` crate for any input length, including empty input or block-boundary lengths. The repository's own test suite even asserts this equivalence for the empty-input case and other values against fixed known-correct SHA-256 outputs. [5](#0-4) 

Without a concrete, reproducible input on which `near_sdk_env::sha256_array` and `::sha2::Sha256::digest` disagree, the claimed invariant break (`digest(input)` on-chain ≠ `digest(input)` off-chain) is not demonstrated. This is a theoretical concern about third-party/host-function correctness with no shown defect path through this repository's code, which is out of scope per the audit rules ("third-party crate defects with no path through this repository," "theoretical findings with no demonstration").
