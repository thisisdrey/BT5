## Title
Aggregation of Stale Price Components in `resolve-ztoken`/`resolve-ststx` — Only the Pyth/DIA Feed Timestamp Is Freshness-Checked, Masking Staleness of the stSTX Ratio and Liquidity Index Multiplicands - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`price-resolve` in the mainnet market contract computes a final collateral/debt price as a **product of multiple independently-sourced values** (base Pyth/DIA price × stSTX ratio × vault liquidity index), but only validates freshness against the timestamp of the *base* oracle feed. The stSTX ratio, fetched from the external `block-info-nakamoto-ststx-ratio-v2` contract, is combined into the final price without any timestamp or staleness check of its own — structurally the same defect described in the external report for `ProductApi3ReaderProxyV1`, where a wrapper that returns the product of multiple feeds masks the staleness of the individual components behind a single "fresh-looking" timestamp.

### Finding Description
`price-resolve` computes `final-price` by calling `resolve-callcode`, which for stSTX/zstSTX-flavored assets chains `resolve-ststx` (multiply by external ratio) and/or `resolve-ztoken` (multiply by cached liquidity index) on top of the base oracle price:

<cite repo="ThankGodontt/zest-v2-contracts--024" path="mainnet/contracts/market/v0-4-market.clar" start="339="347" end="358" /> [1](#0-0) 

The only freshness check performed is `oracle-timestamp-fresh`, applied to `timestamp` — which comes exclusively from `resolution` (the base Pyth/DIA `resolve-price-feed` call), not from any timestamp associated with the stSTX ratio: [2](#0-1) 

`call-ststx-ratio` forwards directly to the external ratio provider and returns only the ratio value — there is no timestamp field returned or checked anywhere in the call chain: [3](#0-2) 

Because the base Pyth STX feed is updated virtually every block, `oracle-timestamp-fresh` will almost always report "fresh" even if the stSTX ratio input has not been refreshed for an extended period (e.g., the upstream `block-info-nakamoto-ststx-ratio-v2` contract stalls, or a negative-rebase/slashing event has occurred but not yet propagated). The final composite price for zstSTX/stSTX therefore can be accepted as "fresh" by the market even though one of its two multiplicative components is stale, exactly analogous to `ProductApi3ReaderProxyV1.read()` returning `block.timestamp` for a product of two feeds whose true ages may differ — masking the age of the underlying (ratio) data feed from any consumer that relies on the reported freshness.

### Impact Explanation
If the stSTX ratio component is stale and overstates the true STX-backing of stSTX (e.g., a slashing/negative-rebase event has reduced the real ratio but the cached/lagging value used by `call-ststx-ratio` has not yet updated), a user can supply stSTX/zstSTX collateral valued via the stale, inflated ratio and borrow against it via `collateral-add`/borrow flows in `v0-4-market.clar`, extracting more debt-asset value than the true collateral backs. This is direct theft of protocol funds (other users' deposited assets) and can also push the protocol into insolvency once the true ratio is reflected and bad debt must be socialized — meeting the Critical impact bar (direct theft of user funds / protocol insolvency).

### Likelihood Explanation
The likelihood depends on how the external stSTX ratio provider can lag/stall relative to real staking state, which the market contract has no ability to detect since it never sees the ratio's own timestamp. Any principal capable of noticing the ratio-provider lag (a public, observable condition) can time a collateral-add/borrow to exploit the mispriced collateral before the ratio catches up — no privileged access required, matching the "unprivileged principal call" scope.

### Recommendation
Track and validate a staleness bound for the stSTX ratio (and any other externally-sourced multiplicative price component) independently of the base Pyth/DIA feed's timestamp, e.g., have `call-ststx-ratio`/the ratio provider expose an update timestamp and require `oracle-timestamp-fresh`-style validation on it before it is multiplied into `final-price` in `resolve-ststx`/`resolve-ztoken`, rather than relying solely on the base feed's timestamp to gate the entire composite price.

### Proof of Concept
1. Monitor `block-info-nakamoto-ststx-ratio-v2`'s `get-ststx-ratio-v3` value versus the actual stSTX/STX backing ratio; identify a window where the on-chain ratio value is stale/lagging (higher than true value).
2. During that window, call `collateral-add` supplying stSTX or zstSTX as collateral; `price-resolve`'s `oracle-timestamp-fresh` check passes because it only checks the fresh Pyth STX timestamp (`mainnet/contracts/market/v0-4-market.clar:387-393`), while `resolve-ststx`/`resolve-ztoken` (`mainnet/contracts/market/v0-4-market.clar:339-347`) apply the stale, inflated ratio.
3. Borrow debt assets up to the (overstated) collateral value computed from the stale ratio.
4. Once the ratio updates to its true (lower) value, the position is under-collateralized, and the attacker's extracted debt exceeds the real value of their collateral, resulting in bad debt for the protocol.

(define-private (oracle-price-legal (p uint))
  (> p u0))

(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
