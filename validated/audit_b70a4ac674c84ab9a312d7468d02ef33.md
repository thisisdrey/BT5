Found the analog: an unbounded `contains()` scan inside `DelegateResourceActuator.delegateResource()` when the legacy (pre-optimization) index path is active.

### Title
Unbounded per-delegation linear scan of `toAccountsList`/`fromAccountsList` causes DoS-prone gas/CPU growth in resource delegation - (File: `actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java` / `actuator/src/main/java/org/tron/core/actuator/DelegateResourceActuator.java`)

### Summary
When `supportAllowDelegateOptimization()` is not enabled, every call to `FreezeBalanceActuator.delegateResource()` (and equivalently `DelegateResourceActuator`) loads the owner's and receiver's `DelegatedResourceAccountIndexCapsule`, then does `toAccountsList.contains(...)` / `fromAccountsList.contains(...)` over the full in-memory list before appending a new entry, exactly the same anti-pattern as NFTX's unbounded `feeReceivers` loop growing per-transaction and being re-scanned every time.

### Finding Description
`FreezeBalanceActuator.delegateResource()` retrieves `ownerIndexCapsule` and `receiverIndexCapsule` from `DelegatedResourceAccountIndexStore`, then performs:
```java
List<ByteString> toAccountsList = ownerIndexCapsule.getToAccountsList();
if (!toAccountsList.contains(ByteString.copyFrom(receiverAddress))) {
  ownerIndexCapsule.addToAccount(ByteString.copyFrom(receiverAddress));
}
``` [1](#0-0) 
and the symmetric check for `fromAccountsList`. Every account that has ever delegated bandwidth/energy to a given receiver (or received delegations from a given owner) is stored as a single protobuf-backed list inside one `DelegatedResourceAccountIndexCapsule` value, keyed by the address. Because there is no cap on the number of distinct counterpart addresses a single account can delegate to or receive from in this legacy pre-optimization code path, `toAccountsList`/`fromAccountsList` can grow without bound as more unique delegation relationships are created by any unprivileged account issuing `FreezeBalanceContract` transactions with distinct receiver addresses. Each subsequent delegation to/from a popular address (e.g., a large staking/exchange address) re-executes a full `O(n)` `contains()` scan over this growing list — a cost incurred inside ordinary user transaction execution, i.e., inside `Manager.processTransaction`/`processBlock`'s actuator execution loop [2](#0-1) , not in an off-chain admin-only function.

This mirrors the structural weakness described in the report: an attacker-influenced, monotonically growing list is scanned/appended to inside a function that any user's transaction can trigger, so the cost of the operation depends on prior unrelated user activity and is not capped.

### Impact Explanation
As more distinct accounts delegate resources to (or receive delegations from) a specific popular address, every new `FreezeBalanceContract` delegation touching that address becomes progressively more expensive to execute inside block/transaction processing, since the list is deserialized, linearly scanned twice (`contains()` on both directions), and re-serialized on every delegation. If the address accumulates a very large number of counterpart relationships, the per-transaction validate/execute cost for anyone delegating to/from that address grows, degrading throughput for transactions touching that popular address and increasing block-processing time for producing/validating nodes. This is a resource-growth/performance-degradation issue rather than a direct fund-theft or account-takeover bug.

### Likelihood Explanation
`FreezeBalanceContract` (legacy freeze with optional delegation) is a normal, unprivileged, freely broadcastable transaction type; any address can create it with an arbitrary new receiver address, and this legacy code path is only reachable while `supportAllowDelegateOptimization()` is disabled (the flag introduced specifically to replace this per-account index list with the prefix-based `V2` storage seen in `DelegatedResourceAccountIndexStore.getWithPrefix`/`delegate`/`delegateV2` [3](#0-2) ). On networks/configurations where this optimization has not yet been activated, the growth is fully attacker-controllable and requires no privileged access — only ordinary freeze transactions.

### Recommendation
Confirm whether `supportAllowDelegateOptimization()` is enabled by default/on mainnet; if the legacy path is still reachable, backport the `V2` prefix-indexed storage model (already used by `DelegateResourceActuator`/`DelegateResourceProcessor`, which avoid loading/scanning the full list) to fully replace the `getToAccountsList()`/`getFromAccountsList()` `contains()` pattern in `FreezeBalanceActuator`, or cap/deprecate the legacy path entirely so no code executes an unbounded linear scan of user-controlled index lists during ordinary transaction execution.

### Proof of Concept
1. On a network/config where `dynamicStore.supportAllowDelegateOptimization()` is false, use N distinct funded accounts.
2. Each account submits a `FreezeBalanceContract` with `resource=BANDWIDTH` (or `ENERGY`) and `receiver_address` set to the same target address T, with sufficient `frozen_balance`.
3. Each successful transaction appends T (or the sender) to the respective `DelegatedResourceAccountIndexCapsule.toAccountsList`/`fromAccountsList` after doing a full `contains()` scan over the current list, as shown in `FreezeBalanceActuator.delegateResource()` [4](#0-3) .
4. As N grows, the per-transaction `contains()` cost for any new delegation touching address T grows linearly, increasing execution time inside `processBlock`/`processTransaction` for every subsequent delegation involving T.

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }
