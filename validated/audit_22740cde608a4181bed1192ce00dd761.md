### Title
Housekeeping stats cache permanently disables stat-threshold triggering after first accessor RPC, allowing unbounded loose-object growth via ordinary pushes - (File: `internal/grpc/middleware/housekeeping/middleware.go`)

### Summary
`scheduleHousekeepingIfNeeded` in the housekeeping gRPC middleware computes a repository's file/directory statistics exactly once per Gitaly process lifetime and caches only the fact that the check was *performed* (a sentinel `struct{}{}`), not the actual stat value. Once this sentinel is stored in `m.statsCache`, the repository is permanently excluded from stat-threshold-based housekeeping scheduling for the remainder of the process's lifetime, no matter how much the repository grows afterward through ordinary accessor traffic.

### Finding Description
`scheduleHousekeepingIfNeeded` (`internal/grpc/middleware/housekeeping/middleware.go` lines 409-441) is called on every `OpAccessor` RPC [1](#0-0) . It checks `m.statsCache.Load(key)`; if the key was never checked before, it walks the filesystem to compute directory/file counts, then unconditionally stores the sentinel and evaluates the threshold once: [2](#0-1) 

The cache key is the `repoKey{storage, relativePath}` pair, with no expiration, no TTL, and no invalidation hook tied to mutator RPCs (unlike `repoActivity`, which is updated on every `OpMutator` via `scheduleHousekeeping`). This is analogous to the SukukFi issue: a value (the "is this repo big enough to need housekeeping" determination) is computed once at a point in time and then treated as permanently valid ("locked at fulfillment") even though the underlying state (file/object count) continues to change via subsequent activity.

In practice, stat-threshold-based scheduling is the *only* path meant to catch repositories that grow primarily through direct/synced writes or unusual access patterns rather than through the RPC-mutator counting path (the doc comment explicitly says this targets "low-activity repos" for which "a single stats check per restart is sufficient" — but that assumption doesn't hold if the repository becomes high-activity later within the same process lifetime). If an ordinary user performs any accessor RPC (e.g., `RepositoryExists`, a `git fetch`) shortly after the repository is created (while small), the sentinel gets stored. All subsequent growth of loose objects or the object directory driven by further accessor-triggered activity, or any growth on repositories that receive few enough writes to avoid `RPCInterval`-based triggering but individually large payloads pushed once, will never re-trigger the stat-based check for that key again until Gitaly restarts.

### Impact Explanation
This can lead to unbounded accumulation of loose objects, un-repacked packfiles, or oversized ref/commit-graph state in long-running Gitaly processes, since the safety-net stat-threshold check (`operationsExceedingStatThreshold`) — the mechanism specifically designed to catch repositories whose size grows outside of the write-count-based `RPCInterval` tracking — becomes permanently disabled for a given repository as soon as it is first observed via an accessor RPC. This degrades repository read/write performance over time and increases resource consumption (disk, memory for git subprocesses reading many loose objects) for a repository that never gets scheduled for full/prune housekeeping through this code path, functioning as a soft denial-of-service against later requests that must walk an increasingly bloated object store. It does not corrupt data but does undermine the correctness of a limit-enforcement design.

### Likelihood Explanation
Likelihood is moderate. Any ordinary user interacting with a repository via read-only RPCs early in its lifetime (which is essentially guaranteed on any actively used Gitaly node) will trip this cache and disable the check for that repository's key for the life of the process. Gitaly processes commonly run for extended periods, and the mutator-count-based `RPCInterval` path is a separate, independent trigger that may not fire for repositories with few, large mutating operations interspersed with many accessor calls, leaving the stat-check as the only backstop — one that is silently disabled after the first hit.

### Recommendation
Do not use a one-shot "checked" sentinel that never expires. Instead, either (a) store the actual computed stat count with a timestamp and re-evaluate/expire it periodically (similar to the `staleAge`/lease mechanism already used by `internal/cache/keyer.go`), or (b) invalidate/refresh the `statsCache` entry whenever a mutator RPC updates `repoActivity` for the same key, so the stat threshold is periodically reconsidered as the repository evolves rather than being fixed at first observation.

### Proof of Concept
1. Start Gitaly with default `MiddlewareConfig` thresholds enabled.
2. Create a small repository and perform a single accessor RPC (e.g., `RepositoryExists`) against it — `scheduleHousekeepingIfNeeded` walks the repo, finds it under threshold, and stores the sentinel in `statsCache` per [3](#0-2) .
3. As an ordinary user, repeatedly write loose objects into the repository through a pattern of pushes/writes that stays under the `RPCInterval` mutator-count trigger (`writesSinceLastRun > thresholds.RPCInterval`) for every operation type in `allOperations`, e.g., by spacing writes out or keeping each push small enough to avoid triggering `OpMutator`-driven scheduling thresholds, while occasionally issuing accessor RPCs.
4. Because the `statsCache` entry for this repository's key already exists, `scheduleHousekeepingIfNeeded` (`internal/grpc/middleware/housekeeping/middleware.go` line 410) will always short-circuit on `statsChecked == true` and never re-walk the filesystem or re-evaluate `operationsExceedingStatThreshold`, even though the true file/directory count has since exceeded `StatThreshold` (default 1000, or 500 for `OpRepackRefs`, per `DefaultMiddlewareConfig` at lines 44-56).
5. The repository accumulates loose objects/files indefinitely without stat-triggered housekeeping until the Gitaly process is restarted, confirming that the cache — not the actual on-disk state — determines eligibility for this safety-net trigger. [4](#0-3)

func (m *Middleware) scheduleHousekeepingIfNeeded(ctx context.Context, key repoKey, targetRepo *gitalypb.Repository) {
	if _, statsChecked := m.statsCache.Load(key); !statsChecked {
		localRepo := m.localRepoFactory.Build(targetRepo)
		repositoryPath, err := localRepo.Path(ctx)
		if err != nil {
			if errors.Is(err, storage.ErrRepositoryNotFound) {
				return
			}
			m.logger.WithError(err).ErrorContext(ctx, "housekeeping: find repo path")
			return
		}

		repoStats := snapshot.RepositoryStatistics{}
		if err := snapshot.WalkPathForStats(ctx, repositoryPath, &repoStats); err != nil {
			m.logger.WithError(err).ErrorContext(ctx, "calculate repository statistics")
			return
		}

		m.logger.WithFields(log.Fields{
			"repository_stats": map[string]any{
				"directory_count": repoStats.DirectoryCount,
				"file_count":      repoStats.FileCount,
			},
		}).InfoContext(ctx, "collected repository statistics")

		m.statsCache.Store(key, struct{}{})
		totalCount := repoStats.DirectoryCount + repoStats.FileCount
		ops := m.operationsExceedingStatThreshold(totalCount)
		if len(ops) > 0 {
			m.scheduleHousekeeping(ctx, targetRepo, true)
		}
	}
