### Title
Access-key nonce reseed on delete+re-add can roll back below already-admitted nonces, breaking replay protection - ([File: runtime/runtime/src/access_keys.rs])

### Finding Description
The nonce-admission upper bound used by the verifier for a transaction executed at block height `H` is `H * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` (exclusive), enforced in `verify_nonce`: [1](#0-0) 

This means a transaction executed while the chain is at height `H` can legally carry a nonce as large as `H*MULTIPLIER - 1`. This check is performed with the *current* apply-time block height (not `H-1`), both in the normal `process_transactions` path: [2](#0-1) 
and in the `DelegateAction` (meta-transaction) path, using the same multiplier: [3](#0-2) 

However, when an access key is deleted and re-added, its nonce is reseeded via `initial_nonce_value`, which uses `block_height - 1`: [4](#0-3) 

`action_add_key` passes `apply_state.block_height` — the height of the block currently being applied, i.e. the *same* height `H` used by `verify_nonce` for admission of the just-executed transaction: [5](#0-4) 

Consequently, the reseed value `(H-1)*MULTIPLIER` can be, and always is, strictly smaller than the maximum nonce admissible at that same height, `H*MULTIPLIER - 1` (difference up to `MULTIPLIER - 1 ≈ 999,999`).

An unprivileged attacker with two full-access keys `K` and `K2` on their own account can exploit this deterministically in a single block `H`:
1. Submit `tx1`, signed by `K`, with `nonce = N` close to `H*MULTIPLIER - 1` (any legitimate action, e.g. a `Transfer`). This is processed in the "process transactions" phase of `apply()`, immediately setting `access_key(K).nonce = N`.
2. Submit `tx2`, signed by `K2`, with `receiver_id == signer_id` (their own account) and actions `[DeleteKey(K), AddKey(K)]`. Because `signer_id == receiver_id`, this becomes a *local receipt*, which per the documented apply order is executed in the "process local receipts" phase — guaranteed to run strictly after all transactions (including `tx1`) have updated nonces in phase 1: [6](#0-5) 
   The `AddKey(K)` action calls `initial_nonce_value(apply_state.block_height)` = `(H-1)*MULTIPLIER`, overwriting `access_key(K).nonce` down from `N` to `(H-1)*MULTIPLIER < N`.

After block `H`, the on-chain nonce for key `K` is `(H-1)*MULTIPLIER`, strictly less than the previously-admitted `N`. In any subsequent block `H' > H`, since `H'*MULTIPLIER > N` always holds, the attacker can sign and submit a brand-new transaction with any nonce `M` in the range `((H-1)*MULTIPLIER, N]` — a range of size up to `MULTIPLIER - 1` — and it will pass both the `Monotonic` (`tx_nonce > current_nonce`) and upper-bound checks in `verify_nonce`, even though nonce values in that range were already validly usable/consumed before the reset. This is a self-inflicted but fully deterministic and reproducible break of the "nonce is used at most once" replay-protection invariant on the attacker's own key, with no validator, RPC operator, or other privileged party involved — only two `AddKey`/`DeleteKey`/`Transfer` transactions from the account owner in the same chunk.

### Impact Explanation
This breaks "replay protection determinism" for the affected access key: nonce values that should never be reusable become valid again after a self-triggered delete+re-add within the same block as a high-nonce transaction. Any system (exchange, meta-transaction relayer, custodial wallet, payment channel) that treats a NEAR transaction nonce as a single-use idempotency/ordering token for a given `(account, public_key)` can be fooled into accepting a "new" transaction using a nonce value that logically should already be spent, opening a double-spend/replay window whose size (up to `MULTIPLIER-1 ≈ 10^6`) and duration (open until the natural nonce catches up, which the attacker fully controls) are chosen by the attacker. The same reseed/upper-bound mismatch also affects `DelegateAction` (meta-transaction) nonce checks in `actions.rs`, extending the exposure to relayed meta-transactions.

### Likelihood Explanation
Fully attacker-controlled and reproducible: requires only an ordinary funded account with two full-access keys, and the ability to submit ordinary `SignedTransaction`s (`Transfer`, `DeleteKey`, `AddKey`) to a public RPC endpoint in the same chunk — no validator/node privilege, no contract exploit, no race condition. The only precondition is choosing a nonce close to the current upper bound, which is trivially computable from the current chain tip height (attacker just queries the RPC for current block height).

### Recommendation
Make the reseed formula consistent with (at least as large as) the maximum nonce ever admissible at the block height where the key is (re)created — e.g., seed with `block_height * MULTIPLIER` minus 1 is still not enough; instead seed using the *same* upper bound formula used by `verify_nonce`/`DelegateAction` (`block_height * MULTIPLIER`, not `(block_height - 1) * MULTIPLIER`), or track and preserve the previous highest nonce ever used by a public key across delete/re-create cycles (e.g., persist a per-account-public_key high-water-mark independent of the access key's lifecycle) so re-adding a key can never yield a nonce lower than one already admitted for that key in the same or an earlier block.

### Proof of Concept
Unit/integration test plan (in `runtime/runtime/src/tests/apply.rs` style, using `TestEnv`/`runtime.apply`):
1. Set up an account `alice` with two full-access keys `K` and `K2`.
2. At block height `H`, submit in the same chunk:
   - `tx1`: signed by `K`, nonce `N = H*MULTIPLIER - 1`, `Transfer` action to `bob`.
   - `tx2`: signed by `K2`, receiver = `alice` (local receipt), actions `[DeleteKey(K), AddKey(K, FullAccess)]`.
3. Apply the chunk; assert both succeed.
4. Read `access_key(K).nonce` from resulting state; assert it equals `(H-1)*MULTIPLIER`, which is `< N`.
5. At block height `H' = H+1` (or any later height), construct `tx3` signed by `K` with nonce `M` such that `(H-1)*MULTIPLIER < M <= N` (e.g., `M = N`), any valid action; submit and apply.
6. Assert `tx3` is accepted (`ProcessTxResponse::ValidTx` / successful execution), proving that a nonce already at or below a previously-admitted value for key `K` is accepted again — violating the invariant that reseeded nonces must always exceed the highest previously admitted nonce for that key.
7. Table-test variant: enumerate `(chosen_nonce, block_height_at_add, block_height_at_readd)` triples with `chosen_nonce` near `block_height_at_add * MULTIPLIER` and `block_height_at_readd == block_height_at_add`, asserting the reseeded nonce (`(block_height_at_readd - 1) * MULTIPLIER`) is always less than `chosen_nonce`.

pub(crate) fn initial_nonce_value(block_height: BlockHeight) -> Nonce {
    // Set default nonce for newly created access key to avoid transaction hash collision.
    // See <https://github.com/near/nearcore/issues/3779>.
    (block_height - 1) * near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER
}

pub(crate) fn action_add_key(
    apply_state: &ApplyState,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    result: &mut ActionResult,
    account_id: &AccountId,
    add_key: &AddKeyAction,
) -> Result<(), StorageError> {
    if get_access_key(state_update, account_id, &add_key.public_key)?.is_some() {
        result.result = Err(ActionErrorKind::AddKeyAlreadyExists {
            account_id: account_id.to_owned(),
            public_key: add_key.public_key.clone().into(),
        }
        .into());
        return Ok(());
    }

    let fee_config = &apply_state.config.fees;

    if let Some(gas_key_info) = add_key.access_key.gas_key_info() {
        add_gas_key(
            fee_config,
            state_update,
            account,
            account_id,
            &add_key.public_key,
            &add_key.access_key,
            gas_key_info,
            apply_state.block_height,
        )?;
    } else {
        add_regular_key(
            fee_config,
            state_update,
            account,
            account_id,
            &add_key.public_key,
            &add_key.access_key,
            apply_state.block_height,
        )?;
    }

    Ok(())
}
