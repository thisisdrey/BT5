### Title
Protocol fees on Nep245/Imt multi-tokens can be fully bypassed by splitting a `TokenDiff` transfer into unit-sized (`delta = ±1`) intents - (File: `contracts/defuse/core/src/intents/token_diff.rs`)

### Summary
`TokenDiff::token_fee()` waives the protocol fee whenever the absolute delta on a `Nep245` or `Imt` token is `<= 1`. Because this check is applied per individual `TokenDiff` intent rather than per net token movement across a batch, an attacker can move an arbitrarily large amount of a `Nep245`/`Imt`-typed asset (which, as used throughout this protocol, wraps fungible balances — e.g. `nep245:intents.near:nep141:<ft>`) at zero protocol fee by decomposing the transfer into many `delta = ±1` `TokenDiff` intents executed together in one `execute_intents` call.

### Finding Description
`TokenDiff::execute_intent` computes the fee to collect per token independently for each `TokenDiff` instance in the batch: [1](#0-0) 

The fee amount is derived from `token_fee()`: [2](#0-1) 

For `Nep245`/`Imt` token types, if `amount <= 1` the returned fee-rate is `Pips::ZERO`, i.e. no fee is collected for that delta at all, regardless of the token's semantic value per unit. This exemption appears intended for genuinely non-fungible items (where "1" is the entire, indivisible position), but `Nep245`/`Imt` token ids in this protocol are also used to represent fungible, divisible balances (as shown by the wrapped-FT `Nep245` token ids referenced elsewhere in the intents ecosystem, e.g. `nep245:intents.near:nep141:usdt.tether-token.near`). There is no aggregation of an account's total delta on a given token across the intents present in the same `execute_intents`/`MultiPayload` batch — each `TokenDiff`'s fee is computed solely from its own local `delta`.

Because `execute_signed_intents` simply iterates and executes every signed `MultiPayload` in the batch: [3](#0-2) 

a user (as the outgoing `delta < 0` party) and a cooperating counterparty (as the `delta > 0` party, which incurs no fee at all since fees are only taken on negative deltas) can submit `N` separate `TokenDiff` intents, each moving exactly `1` unit of the same `Nep245`/`Imt` token, to transfer `N` units in total while every individual fee computation is `token_fee(..., amount=1, ...) = Pips::ZERO`. A single `TokenDiff` moving the same `N` units in one delta would instead pay `fee.fee_ceil(N)`.

This is the same class of bug as the referenced report: a cap/charge that is correctly enforced on a single large operation is bypassed by decomposing it into many small operations that each individually fall under an exemption threshold, because the exemption is evaluated per-operation instead of per aggregate economic effect.

### Impact Explanation
This crosses the "fees owed versus fees collected" boundary explicitly called out as Critical: protocol fees that should be proportional to the value moved can be entirely bypassed for any amount of a `Nep245`/`Imt` token, as long as the mover is willing to sign/submit `N` unit-sized intents instead of one. This causes the fee collector to permanently lose fee revenue that would otherwise be owed on legitimate large transfers/swaps routed through `TokenDiff`.

### Likelihood Explanation
Any unprivileged pair of accounts (the user and a cooperating counterparty/solver, which can be the same actor's second key) can construct and sign the requisite `TokenDiff` intents without any special role, relayer key, or DAO permission — only ordinary account key(s) and the ability to submit a batch of signed payloads to `execute_intents`. The number of intents required scales with the amount to move (gas cost is the only friction), which is the same tradeoff accepted by the original margin-looping report.

### Recommendation
Compute and enforce the fee based on the aggregate signed delta per `(token_id, direction)` across the whole batch/account within a single `execute_intents` call (or otherwise anchor the "no-fee" exemption to genuinely non-fungible use, e.g. gate it on `TokenIdType::Nep171`/true NFT semantics only), rather than exempting fees per-intent whenever an individual delta happens to be `<= 1`.

### Proof of Concept
1. Attacker controls account `A` (or cooperates with account `B`) and wants to move `1000` units of a fungible `Nep245` token (e.g. a wrapped FT sub-token) from `A` to `B` with zero protocol fee.
2. Instead of signing one `TokenDiff` with `diff = {token: -1000}` (which would call `token_fee(token, 1000, fee).fee_ceil(1000) > 0` since `amount > 1`), the attacker/counterparty sign `1000` separate `TokenDiff` intents:
   - `A` signs 1000 payloads, each with `diff = {token: -1}`.
   - `B` signs 1000 payloads, each with `diff = {token: +1}`.
3. All 2000 signed `MultiPayload`s are submitted together in a single `execute_intents(signed)` call.
4. For each of the 1000 `A`-side intents, `TokenDiff::execute_intent` computes `amount = 1`, so `Self::token_fee(token_id, 1, protocol_fee)` returns `Pips::ZERO` per `token_fee`'s `Nep245 | Imt if amount > 1` branch not matching, and the `Nep245`/`Imt` fallthrough returning `Pips::ZERO`; hence `fee_ceil(1) == 0` for every intent.
5. Net result: `1000` units moved from `A` to `B`, `fees_collected` for the fee collector totals `0`, versus the non-zero fee that a single `-1000` delta `TokenDiff` would have incurred.
