### Title
`remove_account` fails to delete 8 of the 12 account-keyed trie columns, leaving stale receipt/promise-yield state that outlives account deletion and can be inherited by a newly created account with the same name - ([File: core/store/src/utils/mod.rs])

### Summary
`TrieKey::col::COLUMNS_WITH_ACCOUNT_ID_IN_KEY` enumerates 12 trie-key kinds that are keyed by `account_id` [1](#0-0) , but `remove_account` only issues `state_update.remove(...)` for 4 of them (`Account`, `ContractCode`, `AccessKey`/`GasKeyNonce`, `ContractData`) [2](#0-1) . The other 8 (`ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, `DataIdToYieldId`) are never cleaned up when an account is deleted via `DeleteAccount`.

### Finding Description
`action_delete_account` calls `remove_account` to purge an account's state [3](#0-2) . Its only gate against deleting an account that still has "large state" is `account_storage_usage > Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE` [4](#0-3) , computed from `Account::storage_usage()` minus local contract-code size. `PostponedReceipt`, `PendingDataCount`, `PostponedReceiptId`, `ReceivedData`, and the `PromiseYield*`/`YieldId*` rows are protocol bookkeeping written directly during receipt processing (`process_action_receipt`, `set_postponed_receipt`, `set_promise_yield_receipt`) [5](#0-4) [6](#0-5) ; they are not part of the account's storage-staked `storage_usage`, so this check does not prevent deletion while such rows exist.

An attacker (as an ordinary account owner) can construct: (1) a contract at `sub.attacker.near` that issues a cross-contract call with a callback on itself, creating a receipt with `input_data_ids` that is not yet satisfied when it arrives at the shard — this is persisted as `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` keyed on `sub.attacker.near`; (2) before the awaited `Data` receipt resolves, submit a `DeleteAccount` action against `sub.attacker.near` from a full-access key it controls. Because `remove_account` does not touch these 8 columns and the storage-usage guard doesn't count them, the delete succeeds, yet the postponed-receipt bookkeeping under the now-deleted account name remains live in the trie. The attacker can subsequently re-create an account with the identical name (`sub.attacker.near` is a sub-account it fully controls) and populate it with new state/contract; when the originally-pending `Data`/`PromiseResume` receipt eventually arrives, the runtime looks it up by the same `account_id` key and will resume/execute the stale postponed action receipt against whatever now occupies that name.

### Impact Explanation
This violates the "authorization exactness" invariant that state keyed by an account name must not survive that account's deletion. Concretely it produces cross-account state contamination: bookkeeping/receipt data belonging to a deleted account becomes attributable to and can affect a subsequently created account of the same name, i.e., an authorization/isolation escalation across the account-name boundary. Depending on the exact receiver-side handling of a resumed postponed receipt against a since-recreated account, this can also lead to unexpected trie mutations or execution paths that were never audited for the post-recreation account context — a real correctness/authorization defect, distinct from and root-cause to the broader family of issues referenced in the sibling questions of this batch.

### Likelihood Explanation
The attacker only needs control of a sub-account (trivial and free beyond gas/storage deposit), the ability to script a two-hop cross-contract call with a callback, and the ability to send a `DeleteAccount` action before the callback's dependent data receipt is delivered — all standard, permissionless operations reachable from a public RPC endpoint with no special privileges, and fully repeatable.

### Recommendation
Extend `remove_account` (`core/store/src/utils/mod.rs:505-575`) to iterate and remove all 12 `COLUMNS_WITH_ACCOUNT_ID_IN_KEY` entries for the account, or block `DeleteAccount` when any of `ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, `DataIdToYieldId` rows exist for that account_id (analogous to the existing `MAX_ACCOUNT_DELETION_STORAGE_USAGE` guard), gated behind a protocol feature.

### Proof of Concept
Unit test in `core/store/src/utils/mod.rs` (or a new test module): populate a `TrieUpdate` with one row of each of the 12 `TrieKey` kinds in `COLUMNS_WITH_ACCOUNT_ID_IN_KEY` under the same `account_id`, call `remove_account(&mut state_update, &account_id)`, then for each of the 12 keys assert `state_update.get(&key)?.is_none()`. Expected: assertions pass for `Account`, `ContractCode`, `AccessKey`, `ContractData` and fail for the remaining 8 (`ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, `DataIdToYieldId`), confirming the gap. A follow-on runtime/test-loop integration test can then drive the full exploit chain (create sub-account → issue cross-contract call with pending callback → delete sub-account → recreate sub-account → deliver the pending `Data`/`PromiseResume` receipt) to observe the stale postponed receipt executing against the recreated account's state, which I was not able to fully trace to a concrete fund-loss/panic outcome within this investigation and would need further confirmation via such an integration test.
