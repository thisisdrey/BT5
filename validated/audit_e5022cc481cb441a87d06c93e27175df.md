Audit Report

## Title
`process_delivery_receipt` in Snowbridge `outbound-queue-v2` never checks the decoded `success` flag before paying the relayer reward - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
`DeliveryReceipt::try_from` decodes the Ethereum `InboundMessageDispatched(uint64 indexed nonce, bytes32 topic, bool success, bytes32 reward_address)` event, including a `success: bool` field that signals whether the message actually executed successfully on the Gateway contract, into the `DeliveryReceipt` struct. `Pallet::process_delivery_receipt` only checks `receipt.gateway` against `T::GatewayAddress::get()` and that a `PendingOrder` exists for `receipt.nonce`, then unconditionally pays the relayer reward and removes the `PendingOrder` — `receipt.success` is never read anywhere in the function.

## Finding Description
`DeliveryReceipt` is decoded with the `success` field populated directly from the Ethereum event: [1](#0-0) [2](#0-1) 

The public extrinsic `submit_delivery_receipt` verifies the proof, decodes the receipt, and forwards it to settlement logic without any success gating: [3](#0-2) 

`process_delivery_receipt` performs only two guards — gateway match and pending-nonce existence — then unconditionally pays the reward and removes the order, never referencing `receipt.success`: [4](#0-3) 

A repository-wide search confirms there is no occurrence of `success` anywhere in `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`, and no dedicated error variant (e.g., `MessageDispatchFailed`) exists for a failed dispatch — only `InvalidGateway` and `InvalidPendingNonce` are used as guards. This confirms the decoded `success` flag is fully dead data at the settlement point: it is parsed off-chain proof data but never influences control flow.

## Impact Explanation
`PendingOrders` and its associated reward payout are the on-chain representation of "message delivered and dispatched on Ethereum." Since `success` is silently ignored, a receipt proving `InboundMessageDispatched(nonce, topic, success=false, reward_address)` (i.e., the Gateway contract reverted or failed to execute the command) still results in: (1) full relayer reward payout via `T::RewardPayment::register_reward`, and (2) unconditional removal of `PendingOrders::<T>` for that nonce, permanently closing settlement state with no retry/compensation path visible in this pallet. This is public underpriced/incorrect settlement — payout and queue-marker state advance without execution actually succeeding, violating the "receipts and payout state must only advance after dispatch and execution succeed" invariant.

## Likelihood Explanation
High. `submit_delivery_receipt` is a public extrinsic requiring only `ensure_signed` plus a genuine Merkle/receipt proof verified by `T::Verifier::verify`. No malicious relayer or forged proof is required — any relayer submitting an authentic receipt for a message that failed to execute on Ethereum (a normal, expected occurrence in cross-chain messaging, not an attack precondition) triggers this incorrect unconditional payout and order removal.

## Recommendation
Add `ensure!(receipt.success, Error::<T>::MessageDispatchFailed);` (or equivalent) in `process_delivery_receipt` before paying the reward and removing the `PendingOrder`. If failed dispatches should still be acknowledged/cleared without rewarding, that design must be explicit and auditable — e.g., emit a distinct `MessageDispatchFailed` event and skip `register_reward`, rather than treating success and failure identically.

## Proof of Concept
1. A message is queued via `do_process_message`, inserting `PendingOrder { nonce, fee, .. }` into `PendingOrders`.
2. On Ethereum, the Gateway contract fails to execute the dispatched command, emitting `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer builds a valid proof for this genuine event and calls `submit_delivery_receipt(origin, event)`.
4. `T::Verifier::verify` succeeds; `DeliveryReceipt::try_from` decodes `success: false` correctly.
5. `process_delivery_receipt` checks only `receipt.gateway` and `PendingOrders::get(nonce)` — both pass — then calls `T::RewardPayment::register_reward` with `order.fee` and removes `PendingOrders::<T>` for `nonce`, despite `receipt.success == false`. A unit test constructing `DeliveryReceipt { success: false, .. }` and asserting `register_reward` is *not* called would fail against current code.

			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
