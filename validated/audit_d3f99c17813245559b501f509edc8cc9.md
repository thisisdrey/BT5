### Title
GCD-normalized market price key collision causes distinct sell orders to be silently merged/orphaned in the on-chain order book - (File: `chainbase/src/main/java/org/tron/core/capsule/utils/MarketUtils.java`)

### Summary
`MarketUtils.createPairPriceKey` normalizes `sellTokenQuantity`/`buyTokenQuantity` by their GCD before deriving the DB key used to index the `MarketPairPriceToOrderStore` order book. Any two orders whose price ratios reduce to the same fraction (e.g. `sell=10,buy=21` and `sell=30,buy=63`) collapse to the **same** storage key, even though they represent economically different, independently-placed orders. This is directly analogous to the reported Node.js bug class: an object/array used as a cache/index key collides for logically distinct entities, causing state belonging to one identity/request to be silently reused or overwritten for another.

### Finding Description
`createPairPriceKey` computes `gcd = findGCD(sellTokenQuantity, buyTokenQuantity)` and stores the reduced ratio in the key: [1](#0-0) 

The key is built from `sellTokenId + buyTokenId + reduced(sellQty) + reduced(buyQty)`: [2](#0-1) 

This key is used by `MarketSellAssetActuator.saveRemainOrder` — reachable directly from an unprivileged `MarketSellAssetContract` transaction broadcast by anyone — to fetch-or-create the order-id list at that price, append the new order id, and write it back: [3](#0-2) 

Because the fetch-modify-write is keyed on the *reduced* price, two independent orders with different absolute quantities but equal reduced ratios land in the exact same `MarketOrderIdListCapsule` bucket. The project's own test explicitly documents this collision and its consequence — that a later `put` for a colliding key overwrites/merges the data of the earlier one and that reads for either "key" resolve to the same underlying value: [4](#0-3) 

The severity of the resulting corruption depends on ordering/race of the get→modify→put sequence across multiple `MarketSellAssetActuator` executions inside the same block (multiple transactions with colliding price ratios), since `saveRemainOrder`'s "get, mutate in memory, put" pattern is not atomic across the whole batch of contracts touching the same reduced-price bucket within one block's transaction processing.

### Impact Explanation
If two orders' quantities reduce to the same GCD ratio and are processed in the same block, the second actuator's `getUnchecked(pairPriceKey)` / `put(pairPriceKey, orderIdListCapsule)` sequence can race with the first, causing one order's presence in the order-id list to be lost when the in-memory capsules are written back non-atomically. A lost order-id entry means the order can never be matched or delivered to the taker while the maker's token has already been debited by `transferBalanceOrToken`, resulting in a **permanent freeze of the maker's funds** (sold asset debited, order unreachable in the book, and — since `MarketCancelOrderActuator` looks orders up by owner/order-id, not by walking the price-key list — the order capsule itself may still exist yet never surface for matching, effectively locking user funds in the exchange with no ability to trade or reliably cancel through the intended price-indexed flow).

### Likelihood Explanation
Reaching this path requires only broadcasting ordinary `MarketSellAssetContract` transactions (an unprivileged, publicly reachable actuator) with sell/buy quantities chosen so their ratios share a common GCD (trivial to engineer, e.g. any multiple of an existing pair). No special privileges, witness/SR status, or network position are needed — this is purely an attacker-controlled input to a standard actuator.

### Recommendation
Include the *unreduced* (or a collision-resistant hash of the full, non-normalized) quantities in the `pairPriceToOrderStore` key, or otherwise disambiguate colliding reduced-price buckets (e.g., key by price ratio only for ordering/matching purposes but store distinct sub-buckets per unique raw quantity pair), and make the get-modify-put sequence in `saveRemainOrder`/`matchOrder` atomic with respect to concurrent orders that map to the same reduced price key within a block.

### Proof of Concept
1. Attacker A broadcasts `MarketSellAssetContract{sellTokenId=X, buyTokenId=Y, sellTokenQuantity=10, buyTokenQuantity=21}` — no matching maker exists, so it becomes a resting order; `saveRemainOrder` computes `pairPriceKey = createPairPriceKey(X, Y, 10, 21)` (GCD=1, key encodes 10/21) and stores order id O1 there.
2. Attacker A (or B) broadcasts a second sell with `sellTokenQuantity=30, buyTokenQuantity=63` (GCD=3, reduces to 10/21) in the same block. `createPairPriceKey` produces the **identical** key as step 1.
3. `saveRemainOrder` calls `pairPriceToOrderStore.getUnchecked(pairPriceKey)`, obtaining the capsule already containing O1, appends O2, and writes it back — this matches the documented behavior in `MarketPairPriceToOrderStoreTest.testPriceSeqWithSamePair` where `put(pairPriceKey1, capsule1)` after `put(pairPriceKey2, capsule2)` for colliding keys causes `get(pairPriceKey2)` to return `capsule1`'s data instead of the original, demonstrating that the value at one logical price slot is fully replaced/overwritten by another (lines 536-551 above).
4. Depending on execution/interleaving in `MarketSellAssetActuator.execute`, the earlier in-memory order-id list mutation can be lost when a later write for the same physical key overwrites it, leaving one maker's order permanently absent from the order book while the corresponding sell-side asset has already been debited from the maker's account balance — an unbacked/frozen fund state reachable purely from unprivileged transaction broadcasts.

  public static byte[] createPairPriceKey(byte[] sellTokenId, byte[] buyTokenId,
      long sellTokenQuantity, long buyTokenQuantity) {

    byte[] sellTokenQuantityBytes;
    byte[] buyTokenQuantityBytes;

    // cal the GCD
    long gcd = findGCD(sellTokenQuantity, buyTokenQuantity);
    if (gcd == 0) {
      sellTokenQuantityBytes = ByteArray.fromLong(sellTokenQuantity);
      buyTokenQuantityBytes = ByteArray.fromLong(buyTokenQuantity);
    } else {
      sellTokenQuantityBytes = ByteArray.fromLong(sellTokenQuantity / gcd);
      buyTokenQuantityBytes = ByteArray.fromLong(buyTokenQuantity / gcd);
    }

    return doCreatePairPriceKey(sellTokenId, buyTokenId,
        sellTokenQuantityBytes, buyTokenQuantityBytes);
  }

  private static byte[] doCreatePairPriceKey(byte[] sellTokenId, byte[] buyTokenId,
      byte[] sellTokenQuantity, byte[] buyTokenQuantity) {
    byte[] result = new byte[TOKEN_ID_LENGTH + TOKEN_ID_LENGTH
        + sellTokenQuantity.length + buyTokenQuantity.length];

    System.arraycopy(sellTokenId, 0, result, 0, sellTokenId.length);
    System.arraycopy(buyTokenId, 0, result, TOKEN_ID_LENGTH, buyTokenId.length);
    System.arraycopy(sellTokenQuantity, 0, result,
        TOKEN_ID_LENGTH + TOKEN_ID_LENGTH,
        sellTokenQuantity.length);
    System.arraycopy(buyTokenQuantity, 0, result,
        TOKEN_ID_LENGTH + TOKEN_ID_LENGTH + buyTokenQuantity.length,
        buyTokenQuantity.length);

    return result;
  }
