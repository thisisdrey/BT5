### Title
Unbounded, unauthenticated write to permanent Atlas storage via unverified attachment content - ([File: stackslib/src/net/atlas/download.rs])

### Summary
The `Done()` arm of `AttachmentsBatchStateMachine::run` unconditionally calls `insert_instantiated_attachment` on every downloaded `Attachment`, regardless of whether `find_all_attachment_instances(&attachment.hash())` found any matching on-chain-committed `AttachmentInstance`. Because `extend_with_attachments` never verifies that the received bytes hash to the content_hash that was actually requested, a malicious peer can return arbitrary garbage content that gets permanently marked `was_instantiated = 1` — a state the eviction routines never touch.

### Finding Description
The equality the Atlas subsystem is supposed to maintain is: *every row in `attachments` with `was_instantiated = 1` corresponds to content whose hash was referenced by some on-chain `AttachmentInstance`.* This equality is broken.

The exploit path:
1. A node's Atlas downloader issues `AttachmentRequest`s for content hashes taken from legitimate on-chain `AttachmentInstance` rows (queued via `queue_attachment_instance` from block processing). The concrete HTTP request is `GET /v2/attachments/{content_hash}` [1](#0-0) .
2. An attacker's own peer, selected as a download source (because it previously claimed — with no validation — to have the attachment via a `GetAttachmentsInv` response), replies to this GET with **any bytes it wants**. `extend_with_attachments` decodes the response and inserts `response.attachment` directly into `self.attachments`, with **no check that `attachment.hash()` equals the `content_hash` that was requested**: [2](#0-1) .
3. In the `Done()` arm, for each such garbage attachment, `find_all_attachment_instances(&attachment.hash())` is queried using the *garbage's own hash* — which will not match any real on-chain `content_hash`, so it returns an empty vec. `insert_instantiated_attachment(&attachment)` is called anyway, unconditionally: [3](#0-2) .
4. `insert_instantiated_attachment` does `INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)` unconditionally: [4](#0-3) .
5. Right after, in the same `Done()` arm, `evict_expired_uninstantiated_attachments` and `evict_expired_unresolved_attachment_instances` run, but their `DELETE` statements are scoped to `WHERE was_instantiated = 0` and `WHERE is_available = 0` respectively: [5](#0-4) [6](#0-5) . The garbage row, already `was_instantiated = 1`, is invisible to both.

Unlike uninstantiated attachments, which are bounded by `max_uninstantiated_attachments` and evicted via `evict_k_oldest_uninstantiated_attachments`, there is **no analogous cap or eviction routine for `was_instantiated = 1` rows** anywhere in `db.rs`. Once a row is instantiated it is permanent, by design (it should represent validated on-chain-referenced content), but this design assumption is violated by the fact that instantiation is not conditioned on `attachments_instances` being non-empty.

### Impact Explanation
Any remote peer that can serve inbound Atlas attachment requests (a normal, unprivileged capability for any P2P peer) can cause the victim node to permanently persist arbitrary attacker-chosen byte blobs (up to `attachments_max_size` each) in its `attachments` SQLite table, tagged as `was_instantiated = 1`. These rows are excluded from both eviction routines and have no size cap, enabling repeated, unbounded storage growth on the victim's Atlas DB — an unauthenticated write to persistent node state that defeats the storage-bounding mechanism the eviction functions are meant to enforce.

### Likelihood Explanation
- The attacker only needs to run an ordinary P2P peer and be selected as a download source for at least one legitimate `AttachmentRequest` (achieved by responding to the corresponding `AttachmentsInventoryRequest` claiming to have the content — unauthenticated and easy to spoof).
- No node secret, StackerDB slot ownership, or special role is required.
- The attack is trivially repeatable: each malicious response with distinct garbage content produces a new permanent row (since the resulting hash differs each time), so storage growth is bounded only by the rate of outstanding attachment requests the victim issues and the attacker's ability to be selected as a reliable-looking source.
- Preconditions (real on-chain `AttachmentInstance` entries needing resolution, e.g. from BNS activity) are common in normal operation, so the attack surface is continuously present, not a one-off edge case.

### Recommendation
In the `Done()` arm of `download.rs`, only call `insert_instantiated_attachment` when `find_all_attachment_instances(&attachment.hash())` returns a non-empty result (i.e., the content actually matches a real on-chain-referenced `content_hash`). Additionally/alternatively, verify in `extend_with_attachments` that the returned `Attachment`'s hash matches the `content_hash` of the corresponding `AttachmentRequest` before inserting it into `context.attachments`, discarding/penalizing responses that don't match. As defense in depth, consider adding a cap/LRU eviction policy for `was_instantiated = 1` rows as well.

### Proof of Concept
Rust test plan (net test in `stackslib/src/net/atlas/`):
1. Construct an `AttachmentsBatchStateContext` in state `Done` with `context.attachments` containing a single crafted `Attachment` whose content does **not** correspond to any hash in the `attachment_instances` table (simulate the outcome of `extend_with_attachments` receiving unverified garbage bytes from a malicious peer).
2. Ensure the `attachment_instances` table has zero rows with `content_hash == attachment.hash()` (mirrors `find_all_attachment_instances` returning an empty vec).
3. Drive `AttachmentsBatchStateMachine::try_proceed` (or directly exercise the `Done()` processing code in `AttachmentsDownloader::run`) so that `insert_instantiated_attachment(&attachment)` executes.
4. Call `atlas_db.evict_expired_uninstantiated_attachments()` and `atlas_db.evict_expired_unresolved_attachment_instances()`.
5. Assert: `atlas_db.find_attachment(&attachment.hash())` still returns `Some(attachment)` (i.e., `SELECT ... FROM attachments WHERE hash = ? AND was_instantiated = 1` still matches), proving the garbage row survived both eviction passes and is permanently stored despite having zero matching committed `AttachmentInstance`.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }

    pub fn evict_expired_uninstantiated_attachments(&mut self) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let cut_off = now - self.atlas_config.uninstantiated_attachments_expire_after as i64;
        let tx = self.tx_begin()?;
        let res = tx.execute(
            "DELETE FROM attachments WHERE was_instantiated = 0 AND created_at < ?",
            params![cut_off],
        );
        res.map_err(db_error::SqliteError)?;
        tx.commit().map_err(db_error::SqliteError)?;
        Ok(())
    }

    pub fn insert_instantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let tx = self.tx_begin()?;
        tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)",
            params![attachment.hash(), attachment.content, now],
        )?;
        tx.execute(
            "UPDATE attachment_instances SET is_available = 1 WHERE content_hash = ?1 AND status = ?2",
            params![attachment.hash(), AttachmentInstanceStatus::Checked],
        )?;
        tx.commit()?;
        Ok(())
    }
