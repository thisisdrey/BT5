### Title
Missing slippage protection in ExchangeInject/ExchangeWithdraw allows sandwich theft against Bancor-style Exchange pools - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java, actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java)

### Summary
The on-chain Bancor-style AMM pools implemented via `ExchangeCreateContract`/`ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` let any account trade against a pool's reserves. `ExchangeTransactionActuator` correctly enforces a caller-supplied minimum-output (`expected`) to prevent price manipulation between signing and execution. [2](#0-1) 
However, `ExchangeInjectActuator` and `ExchangeWithdrawActuator` compute the required/returned amount of the paired token purely from the pool's *current* reserve ratio at execution time, with no equivalent bound supplied by the caller. [3](#0-2) [4](#0-3) 

### Finding Description
This is the java-tron analog of the reported class of bug: an actor whose transaction's economic outcome depends on a shared/pooled state (the Exchange reserves) signs a transaction assuming a certain price, but an attacker can insert a trade immediately before it (front-run/sandwich, e.g. via block-producer collusion or simple mempool ordering) to move the reserve ratio, and there is no on-chain minimum/maximum bound to reject the manipulated outcome.

Specifically:
- `ExchangeInjectActuator.execute` reads `firstTokenBalance`/`secondTokenBalance` from the `ExchangeCapsule` at execution time and derives `anotherTokenQuant` via `floorDiv(multiplyExact(secondTokenBalance, tokenQuant), firstTokenBalance)` (or the symmetric branch), then unconditionally debits both `tokenQuant` and the derived `anotherTokenQuant` from the caller's account. [5](#0-4) 
The corresponding `ExchangeInjectContract` protobuf has no expected/min/max field the caller can use to cap the second-token cost. [6](#0-5) 
- `ExchangeWithdrawActuator.execute` similarly derives `anotherTokenQuant` from the live ratio and credits it to the caller, with `ExchangeWithdrawContract` likewise lacking any minimum-received bound. [7](#0-6) [8](#0-7) 

Attack: an attacker observes a pending `ExchangeInject` or `ExchangeWithdraw` transaction (any account can create these, and their exchangeId/tokenId/quant are public), then submits an `ExchangeTransactionContract` trade immediately before it that skews the pool ratio in their favor, letting the victim's inject overpay the second token (extracted by the attacker via a follow-up trade reverting the price) or the victim's withdraw receive far less of the second token than expected. This mirrors the report's core issue — a party relying on pooled reserve state has no execution-time guard against reserve manipulation inserted by a third party in the same block.

### Impact Explanation
A victim calling `ExchangeInject` or `ExchangeWithdraw` on any Exchange pool can be made to transfer more value than intended (inject) or receive less value than expected (withdraw), extractable in full by the attacker via classic sandwich mechanics, since the actuators enforce no minimum-output/maximum-input constraint. This is a concrete, unauthorized-value-extraction bug reachable by any unprivileged transaction broadcaster (both the victim's inject/withdraw call and the attacker's exchange trade are ordinary, permissionless transactions), fitting the "theft of funds" acceptance criteria.

### Likelihood Explanation
Exploitation requires only transaction ordering control (mempool front-running or same-block bundling by whoever produces the block), which is a realistic capability on any chain without private mempools, and does not require any privileged role — any Exchange pool with liquidity and any user issuing inject/withdraw is exposed. The `ExchangeTransactionContract` already demonstrates the project is aware of this class of risk (it added an `expected` field), making the omission in Inject/Withdraw a clear regression/oversight rather than a fundamental design choice.

### Recommendation
Add a caller-specified bound to both contracts — e.g., `expected` (minimum `anotherTokenQuant` to accept) for `ExchangeWithdrawContract`, and a maximum-`anotherTokenQuant` (or minimum LP-share) cap for `ExchangeInjectContract` — and validate them in `ExchangeInjectActuator`/`ExchangeWithdrawActuator` the same way `tokenExpected` is validated in `ExchangeTransactionActuator`. [2](#0-1) 

### Proof of Concept
1. Pool P has reserves `firstTokenBalance = A`, `secondTokenBalance = B`.
2. Victim broadcasts `ExchangeInjectContract{exchangeId=P, tokenId=first, quant=Q}`, expecting to pay `~B*Q/A` of the second token based on the ratio they observed.
3. Attacker, seeing this pending transaction, submits an `ExchangeTransactionContract` trade against pool P just before it (or bundles it in the same block ahead of it) that sells the second token into the pool, driving up `secondTokenBalance` relative to `firstTokenBalance`.
4. Victim's `ExchangeInjectActuator.execute` now computes `anotherTokenQuant = floorDiv(multiplyExact(secondTokenBalance, tokenQuant), firstTokenBalance)` using the manipulated, inflated `secondTokenBalance`, causing the victim to be debited far more of the second token than intended. [9](#0-8) 
5. Attacker submits a reverse trade after the victim's transaction to restore the ratio and pocket the extracted second-token value. The symmetric attack applies to `ExchangeWithdrawActuator`, causing the victim to receive an artificially low `anotherTokenQuant`. [10](#0-9)
