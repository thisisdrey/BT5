### Title
Out-of-bounds read parsing corrupted ZIP central directory extra fields - (File: third_party/ijar/zip.cc)

### Summary
`InputZipFile::ProcessCentralDirEntry` in `third_party/ijar/zip.cc` reads a jar/zip's central directory record and, unlike its local-file-header counterpart, never validates that attacker-controlled length fields (`file_name_length`, `extra_field_length`, `file_comment_length`) stay within the bounds of the memory-mapped input file before advancing pointers and dereferencing memory.

### Finding Description
`ProcessCentralDirEntry` reads `file_name_length`, `extra_field_length`, and `file_comment_length` directly from the on-disk central directory header bytes and immediately uses them to advance `p`, `extra_p`, and to `memcpy` from `p` into `filename`, with no check that these fields lie within the mapped file’s length: [1](#0-0) 
The zip64 extra-field walk then reads `header_id`/`data_size` and advances `extra_p` by `data_size`, again without checking that `extra_p`/`extra` stay inside the file: [2](#0-1) 

By contrast, `ProcessLocalFileEntry` (used for local file headers) explicitly calls `EnsureRemaining()` before consuming `file_name_length` and `extra_field_length` bytes: [3](#0-2) 
No equivalent `EnsureRemaining`-style check exists in `ProcessCentralDirEntry`.

The input buffer itself is a raw `mmap`'d view of the file with no guaranteed trailing padding: [4](#0-3) 

The comment above the function claims safety ("the central directory is always followed by another data structure that has a signature, so parsing it this way is safe"), but this reasoning does not bound `extra_field_length`/`file_name_length`/`file_comment_length` themselves — a corrupted or hostile central directory header can declare any 16-bit length value, causing `p`, `extra_p`, and the `memcpy` source to walk past the end of the mapped region before any subsequent signature is ever checked. [5](#0-4) 

This code is reached whenever Bazel's `ijar`/`zipper` tooling opens a zip/jar via `ZipExtractor::Create` → `InputZipFile::Open` → `FindZipCentralDirectory`/`ProcessCentralDirEntry`, e.g. when processing a downloaded or externally supplied jar (such as via `http_jar`/`http_archive` producing a jar consumed by `ijar` to build an interface jar, or by `singlejar`/`zipper` binaries operating on build inputs). An externally hosted, corrupted jar is exactly the kind of untrusted content this class of tool is expected to parse.

### Impact Explanation
A maliciously crafted or corrupted jar/zip file with an oversized `extra_field_length`, `file_name_length`, or zip64 extra-field `data_size` can cause `ijar`/`zipper` to read past the end of the memory-mapped file buffer. This is a memory-safety violation (out-of-bounds read) directly analogous to the `packet_hexdump` OOB read in BlueZ's `btmon`: processing an attacker-supplied corrupted "dump" (here, a zip/jar) crashes the tool (SIGSEGV) or, depending on heap/mmap layout, could leak adjacent memory contents into the copied `filename` buffer or the derived compressed/uncompressed size values. It does not directly compromise integrity of a checksum-pinned artifact, but it is a crash / info-leak surface reachable purely from untrusted archive bytes, with no attacker access to the victim machine, credentials, or trusted BUILD/.bzl files required.

### Likelihood Explanation
Any Bazel build target that runs `ijar` or `zipper`/`singlejar` over a jar sourced from an external, attacker-controlled location (mirror, dependency, or a branch's CI-fetched artifact) can trigger this path automatically as part of normal build processing, with no special build flags required. Because there is no `EnsureRemaining`-style bound in `ProcessCentralDirEntry`, exploitation requires only crafting a corrupted central directory entry with an inflated length field — a low-complexity change to an otherwise valid jar structure.

### Recommendation
Add explicit bounds checks in `ProcessCentralDirEntry` (mirroring `EnsureRemaining` in `ProcessLocalFileEntry`) before consuming `file_name_length`, `extra_field_length`, and `file_comment_length`, and before advancing `extra_p` in the zip64 extra-field loop, validating each advance against the mapped file's total length (`input_file_->Length()`), returning an error instead of continuing to read/copy when the declared lengths would exceed the buffer.

### Proof of Concept
A concrete PoC would construct a minimal valid zip whose End-of-Central-Directory record correctly points to a central directory, but whose single `CDH` entry declares `extra_field_length` (or `file_comment_length`) larger than the number of bytes actually remaining in the file, then invoke `ZipExtractor::Create`/`ProcessAll` (as done in `third_party/ijar/zip_main.cc` or via `PartialZipExtractor::UnzipUntil` in `src/main/cpp/archive_utils.cc`) against this file under ASan; the out-of-bounds read in the `extra_p` walk of `ProcessCentralDirEntry` (lines 526-542) would be flagged. I could not fully verify within the available context whether an existing `src/test/shell/bazel` or `output_jar_simple_test.cc`-style harness already exercises this exact central-directory path (as opposed to the local-header `MalformedExtraField` test I found at `src/tools/singlejar/output_jar_simple_test.cc:1227-1236`, which covers a different code path in `singlejar`, not `ijar`'s `zip.cc`), so a new JUnit/shell-test proof targeting `ProcessCentralDirEntry` specifically would need to be authored to fully confirm reproducibility.
