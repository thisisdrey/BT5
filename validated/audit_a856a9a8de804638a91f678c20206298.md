### Title
Unchecked `long` multiplication in float-ratio energy split can overflow and corrupt caller/creator energy allocation - (File: `actuator/src/main/java/org/tron/core/actuator/VMActuator.java`)

### Summary
`getTotalEnergyLimitWithFloatRatio` computes the split of TVM energy between a contract caller and the contract's creator using raw `long` arithmetic that is not overflow-checked, unlike almost every other resource/energy calculation in the codebase, which has been deliberately hardened with `BigInteger` and `addExact`/`multiplyExact` wrappers gated behind `allowHardenResourceCalculation`.

### Finding Description
The Ghostscript CVE is a classic "arithmetic performed on attacker-influenced values without an overflow check" bug. Java-tron has systematically hardened this exact bug class across its resource-accounting code — `RepositoryImpl.calculateGlobalEnergyLimit`, `ResourceProcessor.increaseV2`/`getNewWindowSize`, and `VMActuator.getAccountEnergyLimitWithFixRatio`/`getTotalEnergyLimitWithFixRatio` all switch to `BigInteger` math or `addExact`/`multiplyExact` (see `RepositoryImpl.java:1003-1009` [1](#0-0) , and `VMActuator.java:770-797` [2](#0-1) ).

However, the sibling "float ratio" path, `getTotalEnergyLimitWithFloatRatio`, still performs raw `long` multiplication with no overflow protection: [3](#0-2) 
```java
private long getTotalEnergyLimitWithFloatRatio(AccountCapsule creator, AccountCapsule caller,
    TriggerSmartContract contract, long feeLimit, long callValue) {
  long callerEnergyLimit = getAccountEnergyLimitWithFloatRatio(caller, feeLimit, callValue);
  ...
  long creatorEnergyLimit = rootRepository.getAccountLeftEnergyFromFreeze(creator);
  ...
  long consumeUserResourcePercent = contractCapsule.getConsumeUserResourcePercent(...);

  if (creatorEnergyLimit * consumeUserResourcePercent
      > (VMConstant.ONE_HUNDRED - consumeUserResourcePercent) * callerEnergyLimit) {
    return floorDiv(
        callerEnergyLimit * VMConstant.ONE_HUNDRED, consumeUserResourcePercent,
        VMConfig.disableJavaLangMath());
  } else {
    return addExact(callerEnergyLimit, creatorEnergyLimit, VMConfig.disableJavaLangMath());
  }
}
```
`creatorEnergyLimit` comes from `rootRepository.getAccountLeftEnergyFromFreeze(creator)`, which is derived from the creator's frozen-TRX-based energy weight — a value that can be pushed close to `Long.MAX_VALUE` under crafted stake/frozen-balance conditions, and `callerEnergyLimit` is influenced by the caller's balance/feeLimit. Both `creatorEnergyLimit * consumeUserResourcePercent` and `callerEnergyLimit * VMConstant.ONE_HUNDRED` are unguarded `long*long` multiplications that silently wrap on overflow in Java, unlike the fix-ratio counterpart which uses `BigInteger` explicitly for the same shape of computation (compare with `VMActuator.java:770-775`) [4](#0-3) .

### Impact Explanation
If the comparison or the `floorDiv` branch wraps due to overflow, the total energy limit computed for the smart-contract call can be silently corrupted — resulting in either far more or far less energy being granted than the account's actual entitlement. Depending on which direction the wraparound goes, this could grant an attacker-controlled contract call more energy than it is entitled to (energy theft from the creator's frozen allocation without corresponding accounting) or crash processing paths downstream that assume non-negative/bounded energy values, both of which affect block-processing consistency across nodes if any node computes differently than others (potential chain-state divergence for VM execution).

### Likelihood Explanation
This function is reached whenever `allowTvmFreeze()`/`allowTvmFreezeV2()` are disabled (float-ratio legacy path) and a `TriggerSmartContract` is executed against a contract with `consumeUserResourcePercent` between 0 and 100 — a call path directly reachable by any transaction broadcaster invoking an existing smart contract, no special privilege required. The likelihood of actually triggering the overflow depends on reaching extreme frozen-balance/energy values, which requires the network's `allowTvmFreeze`/`allowTvmFreezeV2` flags to be off (this is a legacy code path retained for chains/parameters that have not activated freeze v2); I could not confirm from the index which mainnet parameter state currently uses this branch, so likelihood is uncertain without further chain-config verification.

### Recommendation
Apply the same hardening already used in `getTotalEnergyLimitWithFixRatio` and `RepositoryImpl`: replace the raw `long` multiplications in `getTotalEnergyLimitWithFloatRatio` with `BigInteger`-based arithmetic (or `Math.multiplyExact`/`StrictMathWrapper.multiplyExact`) for both the comparison and the `floorDiv` computation, consistent with `VMConfig.disableJavaLangMath()`/hardening gating used elsewhere in the file.

### Proof of Concept
Conceptual: craft an account with an enormous `getAllFrozenBalanceForEnergy()` (via extreme stake/freeze operations) so that `getAccountLeftEnergyFromFreeze(creator)` approaches `Long.MAX_VALUE / 100`; deploy/call a contract with `consumeUserResourcePercent` set such that `creatorEnergyLimit * consumeUserResourcePercent` or `callerEnergyLimit * VMConstant.ONE_HUNDRED` exceeds `Long.MAX_VALUE`, causing silent wraparound in the branch condition or in the `floorDiv` numerator, producing an incorrect (and possibly negative or drastically reduced/increased) total energy limit for the call. I was not able to fully verify the exact numeric preconditions (whether current network parameters allow `getAllFrozenBalanceForEnergy` to reach the needed magnitude) within the scope of the index search, so this PoC is a code-path description rather than a confirmed, executed exploit.
