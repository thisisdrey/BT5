Audit Report

## Title
`claim_rewards_to` is permanently uncallable for Snowbridge rewards on Bridge Hub Rococo due to `Weight::MAX` benchmark weight — accrued relayer rewards get permanently locked - ([File: cumulus/parachains/runtimes/bridge-hubs/bridge-hub-rococo/src/lib.rs])

## Summary
`pallet_bridge_relayers::claim_rewards_to` is the only extrinsic that can pay out `BridgeReward::Snowbridge` rewards (since `LocalAccount` beneficiaries are explicitly rejected for Snowbridge rewards, ruling out the plain `claim_rewards` call). On bridge-hub-rococo, both `BridgeRelayersConfig` implementations' `prepare_rewards_account` hooks unconditionally return `None`, which the pallet's benchmarking harness interprets as "disable this benchmark, assign `Weight::MAX`" — and that `Weight::MAX` value is baked into the shipped, generated weight tables for `claim_rewards_to()`. Because that declared weight exceeds any block's weight limit, the extrinsic can never be dispatched, permanently locking any relayer's accrued Snowbridge rewards on Rococo's Bridge Hub.

## Finding Description
The dispatchable `claim_rewards_to` charges `T::WeightInfo::claim_rewards_to()` and has no other privileged gating besides `ensure_signed`. [4](#0-3) 

The pallet's benchmark helper trait method `prepare_rewards_account` is documented to disable the `claim_rewards_to` benchmark (assigning `Weight::MAX`) when it returns `None`: [7](#0-6) 

On bridge-hub-rococo, both configured instances (`RelayersForLegacyLaneIdsMessagesInstance` and `RelayersForPermissionlessLanesInstance`) return `None` unconditionally from `prepare_rewards_account`: [1](#0-0) [2](#0-1) 

This is reflected in the generated production weight file, where `claim_rewards_to()` is hard-coded to `Weight::from_parts(18_446_744_073_709_551_000, 0)` (≈`u64::MAX`), while the neighboring `claim_rewards()` and `register()` functions in the same file have ordinary, small weights: [8](#0-7) 

By contrast, bridge-hub-westend's equivalent implementation returns a real `Some((BridgeReward::Snowbridge, BridgeRewardBeneficiaries::AssetHubLocation(..)))` tuple and funds/opens the HRMP channel needed for the benchmark to succeed, resulting in a bounded, realistic weight: [5](#0-4) 

The prdoc for the corresponding fix confirms the bug class exactly: "The `prepare_rewards_account` benchmark helper was returning `None`, causing `claim_rewards_to` to be assigned `Weight::MAX` and effectively disabling the extrinsic," and that fix updated `bridge-hub-westend-runtime` (and associated crates) — but the actual `prepare_rewards_account` body in bridge-hub-rococo's runtime, as read directly from the file, still returns `None` unconditionally and its weight file still bakes in `Weight::MAX`. [9](#0-8) 

Since `Weight::MAX` cannot fit within any block's `max_block` weight limit, standard frame weight validation will always reject any extrinsic call declaring this weight before it can be dispatched — this is not a runtime logic bug in the sense of incorrect payout math, but a structural, protocol-level block on ever calling the function at all, corrupting the "callability gate" of `claim_rewards_to` for Snowbridge rewards specifically on bridge-hub-rococo.

## Impact Explanation
`BridgeReward::Snowbridge` payouts are only routable via `claim_rewards_to` with an `AssetHubLocation` beneficiary (the `LocalAccount` path used by plain `claim_rewards` is explicitly rejected for this reward kind in the Snowbridge payment procedure). With `claim_rewards_to` unreachable on bridge-hub-rococo due to its `Weight::MAX` declared weight, any relayer that accrues `BridgeReward::Snowbridge` in `RelayerRewards` storage (e.g., via processing Snowbridge V2 inbound messages) has no functioning path to withdraw those funds. This is a permanent lock of relayer-owed value and directly disincentivizes/degrades Snowbridge relay processing on Rococo's Bridge Hub, matching the accepted impact category of permanent user-fund lock / degraded bridge processing incentive.

## Likelihood Explanation
No privileged actor or malicious behavior is required — any ordinary relayer account with accrued `BridgeReward::Snowbridge` rewards that calls the standard, public, signed extrinsic `claim_rewards_to` will be deterministically rejected by weight validation on every attempt, on bridge-hub-rococo specifically. The condition is guaranteed by the currently shipped code and weight tables, not by any race condition or special setup.

## Recommendation
Update both `BridgeRelayersConfig::prepare_rewards_account` implementations in `cumulus/parachains/runtimes/bridge-hubs/bridge-hub-rococo/src/lib.rs` to mirror the bridge-hub-westend fix: return `Some((BridgeReward::Snowbridge, BridgeRewardBeneficiaries::AssetHubLocation(..)))`, fund the relayer for XCM delivery fees, and open the outbound HRMP channel to AssetHub needed for the benchmark. Then regenerate the `pallet_bridge_relayers` weight files for bridge-hub-rococo so `claim_rewards_to()` receives a bounded, realistic weight instead of `Weight::MAX`.

## Proof of Concept
1. On bridge-hub-rococo, have a relayer accrue a `BridgeReward::Snowbridge` reward in `RelayerRewards` storage (e.g., through Snowbridge V2 inbound message processing calling `register_reward`).
2. Call `pallet_bridge_relayers::claim_rewards_to(origin=signed(relayer), reward_kind=BridgeReward::Snowbridge, beneficiary=AssetHubLocation(..))`.
3. Because `WeightInfo::claim_rewards_to()` for both bridge-hub-rococo weight files returns `Weight::from_parts(18_446_744_073_709_551_000, 0)`, the extrinsic's declared weight exceeds `BlockWeights::max_block`, causing standard frame weight validation to reject the extrinsic before dispatch regardless of relayer balance or permissions.
4. Observe that the reward remains permanently in `RelayerRewards` storage with no viable extrinsic path to withdrawal, since `claim_rewards` (the local-account variant) is also rejected for `BridgeReward::Snowbridge`.
