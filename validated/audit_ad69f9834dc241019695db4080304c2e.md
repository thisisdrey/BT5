## Title
StackerDB chunk signatures omit the StackerDB contract identity, permitting cross-database replay of validly-signed chunks - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` computes the digest that a StackerDB signer signs over as `hash(slot_id || slot_version || data_hash)` only. It never includes the target StackerDB's `contract_id` (or any network/session identifier). Consequently, a legitimately signed `StackerDBChunkData` produced for one StackerDB replica can be replayed — verbatim, with no forgery needed — into a *different* StackerDB replica that happens to assign the same signer address to the same `slot_id`, as long as the target's expected version accepts it. This is structurally the same flaw as the reported EIP-155 issue: the signature commits to the payload but not to the "domain" (chain/contract) it is meant for, so it validates in unintended contexts.

### Finding Description
The signed digest is built here: [1](#0-0) 

Note it hashes only `slot_id`, `slot_version`, and `data_hash` — the `contract_id` of the StackerDB the chunk belongs to is never part of what is signed.

Verification (`SlotMetadata::verify`) simply recovers the pubkey from this same digest and checks it hashes to the expected `principal`: [2](#0-1) 

The node-side acceptance path, `StackerDBs::validate_received_chunk`, looks up the *expected signer address for the given `smart_contract_id`+`slot_id`* and then calls `slot_metadata.verify(&addr)` — but since the signature itself never bound the `contract_id`, this only checks "was this signed by an address that happens to be assigned this slot in this contract", not "was this signed *for* this contract": [3](#0-2) 

The wire message that carries a chunk push, `StackerDBPushChunkData`, carries `contract_id` as a plain field, separate from the inner signed `StackerDBChunkData`: [4](#0-3) 

Any peer relaying an unsolicited push can therefore take a previously-observed, validly-signed `StackerDBChunkData` (slot_id, slot_version, sig, data) — which is public gossip data, not secret — and wrap it inside a new `StackerDBPushChunkData` whose `contract_id` names a *different* StackerDB instance that this node also replicates. `handle_unsolicited_StackerDBPushChunk` dispatches purely on the attacker-supplied `chunk_data.contract_id` field and then calls the same `validate_received_chunk` above: [5](#0-4) 

If the same signer address happens to be assigned the same `slot_id` in the second StackerDB (which is common — reward-cycle StackerDB contracts, e.g. `.signers-X-N`, are configured from the same active stacking/signer set and frequently assign the same address to identical slot indices across sibling contracts and across reward cycles), and the second contract's currently expected version for that slot is `<=` the replayed `slot_version`, the chunk passes all checks and is written via `try_replace_chunk`, exactly as if it had been freshly signed for that contract.

### Impact Explanation
This breaks the equality "a chunk accepted into StackerDB X was authorized by its signer for X" — the signature only proves "signed by this address for this (slot_id, slot_version, data_hash) tuple", with no domain separation across StackerDB contracts/instances. An unprivileged, remote peer can cause the network to accept and propagate genuine-looking but out-of-context data into a StackerDB replica the original signer never intended it for (e.g. re-injecting a stale `BlockResponse`/message payload from one reward cycle's signer set into another reward cycle's or another message-type's StackerDB slot). This is an unauthorized write of signer-authenticated-looking data into unintended state and gets rebroadcast network-wide via `process_stacker_db_chunks`'s `p2p.broadcast_message`, matching the Critical/High class of "unauthenticated/unauthorized write to state or StackerDB" / "network-wide propagation of forged[-context] data".

### Likelihood Explanation
No secret key or privileged role is required — the attacker only needs to observe a publicly gossiped, validly signed chunk (StackerDB chunks are broadcast p2p data by design) and re-relay it with a different `contract_id` in the `StackerDBPushChunkData` wrapper. Practical exploitability depends on finding a target contract/slot pair where the signer address and expected version line up, which is realistic given how StackerDB replicas are provisioned from overlapping signer sets across reward cycles/message types, but is not guaranteed for arbitrary contract pairs.

### Recommendation
Include the target `contract_id` (and ideally `rc_consensus_hash`/network identifier) in `SlotMetadata::auth_digest()` so the signature binds to the specific StackerDB instance it is intended for, mirroring how EIP-155 binds a transaction signature to `chain_id`. This requires a StackerDB protocol/version bump since it changes what is signed.

### Proof of Concept
1. Configure a node to replicate two StackerDB contracts, A and B, where the same signer address `S` is assigned `slot_id = k` in both (realistic across sibling `.signers-*` contracts or across reward cycles).
2. Observe (via normal p2p gossip) a validly signed `StackerDBChunkData { slot_id: k, slot_version: v, sig, data }` broadcast for contract A, as shown being signed/verified in the existing test: [6](#0-5) 
3. Craft `StackerDBPushChunkData { contract_id: B, rc_consensus_hash: <current for B>, chunk_data: <same chunk as above> }` and send it as an unsolicited push to a victim node.
4. If B's expected version for slot `k` is `<= v`, `handle_unsolicited_StackerDBPushChunk` → `validate_received_chunk` accepts it (since `slot_metadata.verify(&addr)` only checks the unchanged digest, addr resolved from B's own slot table) and the chunk is stored/rebroadcast for contract B, even though it was never signed with contract B in mind.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }

        chainstate: &mut StacksChainState,

        send_reply: bool,
    ) -> Result<(bool, bool), net_error> {

            .get_p2p_convo(event_id)
            .map(|convo| convo.to_neighbor_address())
        else {
            debug!(
                "Drop unsolicited StackerDBPushChunk: event ID {} is not connected",
                event_id
            );
            return Ok((false, false));
        };

        let mut payload = self.make_StackerDBChunksInv_or_Nack(
            naddr,
            chainstate,
            &chunk_data.contract_id,
            &chunk_data.rc_consensus_hash,

        match payload {
            StacksMessageType::StackerDBChunkInv(ref mut data) => {
                // this message corresponds to an existing DB, and comes from the same view of the
                // stacks chain tip
                let stackerdb_config = if let Some(config) =
                    self.get_stacker_db_configs().get(&chunk_data.contract_id)
                {
                    config
                } else {
                    // not for this DB
                    info!(
                        "StackerDBChunk for {} ID {} is not available locally",
                        &chunk_data.contract_id, chunk_data.chunk_data.slot_id

                    return Ok((false, false));
                };

                // sanity check
                if !self.validate_received_chunk(
                    &chunk_data.contract_id,
                    stackerdb_config,
                    &chunk_data.chunk_data,
                    &data.slot_versions,
