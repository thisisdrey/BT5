### Title
Unbounded Array Allocation from Attacker-Controlled Length Field in TVM Precompiled Contract ABI Decoding - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The FreeRDP CVE describes an integer-overflow/unvalidated-length class of bug: a length field supplied by an untrusted peer (`FramesPerPacket`) is used directly to size a memory allocation without validating it against a sane bound, causing a heap overflow/DoS. The same bug class exists in java-tron's TVM precompiled-contract ABI decoding helpers, where a 32-byte calldata word supplied by any contract caller is converted to an `int` and used directly as the size of a Java object array, with no upper-bound check against the actual calldata length before the array is allocated.

### Finding Description
`PrecompiledContracts.extractBytesArray` and `PrecompiledContracts.extractSigArray` read the "array length" header word directly from calldata: [1](#0-0) [2](#0-1) 

In both methods, `int len = words[offset].intValueSafe();` is taken straight from attacker-supplied calldata. `DataWord.intValueSafe()` only guards against negative/overflowing values by clamping to `Integer.MAX_VALUE` — it does not validate the value against the amount of data actually present: [3](#0-2) 

The resulting `len` (up to `Integer.MAX_VALUE`) is then used immediately to allocate `new byte[len][]` (an array of object references) before any bound-checking loop runs and before an `ArrayIndexOutOfBoundsException` could ever be thrown for out-of-range access. An array of `Integer.MAX_VALUE` references requires on the order of ~17 GB of heap, which will exhaust the JVM heap and throw `OutOfMemoryError` inside the node process executing the transaction.

Unlike the general-purpose VM memory subsystem (`Memory.extend`, `EnergyCost.calcMemEnergy`), which enforces a hard 3 MB `MEM_LIMIT` before any opcode like `CODECOPY`/`CALLDATACOPY` is allowed to allocate memory: [4](#0-3) [5](#0-4) 

these precompiled-contract ABI-decoding helper functions have no equivalent bound check on `len` before allocation, and are invoked from `execute(byte[] data)` of the precompile, which is charged energy via `getEnergyForData(data)` computed from the **input** data length, not from the attacker-controlled `len` header field extracted from within that data.

### Impact Explanation
Any account (no special permission required) can construct a smart-contract call that reaches a precompiled contract using these helpers with a crafted calldata word encoding a huge "array length." Because the array allocation happens before any bound validation against the true payload size, this triggers a large/failed heap allocation and `OutOfMemoryError` inside the node's transaction-execution thread. Depending on JVM behavior this can crash the node process or destabilize the FullNode/SolidityNode servicing that transaction — a Denial-of-Service against the node, consistent with the "node crash or halt" impact bar required by this report.

### Likelihood Explanation
Reaching this code path only requires broadcasting a normal transaction that calls a contract (or contract constructor) invoking the affected precompiled contract with malicious calldata — no privileged role, signer, or SR/witness status is needed. The precondition is simply crafting the ABI-encoded length word to an extreme value, which is trivial for any transaction sender/contract deployer.

### Recommendation
Add an explicit upper-bound check on `len` in `extractBytesArray` and `extractSigArray` before allocating `bytesArray`, e.g., reject if `len` is negative, exceeds a small sane maximum, or if `len` combined with the fixed per-item word size would exceed `data.length`/`words.length`, mirroring the bound check already performed via `isValidAbiEncoding`. Alternatively, validate that the declared array length is consistent with the actual ABI-encoded data size before performing the allocation.

### Proof of Concept
Not independently executed; based on static code inspection. Conceptually:
1. Deploy or call a contract that invokes the TVM precompiled contract relying on `extractBytesArray`/`extractSigArray` for its ABI decoding (e.g., a batch-signature-validation precompile).
2. Craft the calldata so the length header word at `words[offset]` decodes (via `intValueSafe()`) to a very large value (e.g., `0x7FFFFFFF`).
3. Submit the transaction; `execute(data)` calls the helper, which executes `byte[][] bytesArray = new byte[len][];` before any bounds validation, causing a multi-gigabyte allocation attempt and `OutOfMemoryError` in the node's TVM execution thread.

Note: I was unable to fully trace which specific precompiled-contract address(es) invoke `extractBytesArray`/`extractSigArray` at runtime (the grep found 20 references within `PrecompiledContracts.java`, but I did not confirm the exact `execute()` entry point and its energy-cost gating in this session). This should be verified before treating the analog as fully confirmed exploitable end-to-end.

   * In case of int overflow returns Integer.MAX_VALUE otherwise works as #intValue()

  public int intValueSafe() {
    int bytesOccupied = bytesOccupied();
    int intValue = intValue();
