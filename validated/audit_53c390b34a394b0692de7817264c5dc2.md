### Title
Unprivileged users can force entries into a victim's per-account token list via dust `DepositToken.transfer`, permanently blocking the victim's deposits, inbound transfers and new debt positions - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
Analogous to CVE-2022-4662 (incorrect access control on an attach/registration path allowing a local unprivileged user to crash the system), `Pool.addToDepositTokensOfAccount` lets any registered `DepositToken` push an entry into an arbitrary account's `depositTokensOfAccount` set. Because `DepositToken.transfer`/`transferFrom` are permissionless ERC20-style entry points, an attacker can dust-transfer small amounts of every registered deposit token to a victim until the victim reaches `MAX_TOKENS_PER_USER = 30`. From then on, any action that would add a new token to the victim's account reverts with `UserReachedMaxTokens`, DoS-ing the victim's ability to deposit into new collateral types, receive deposit tokens, or open debt in a new `DebtToken`.

### Finding Description
`DepositToken._transfer` unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's prior balance is zero (`contracts/DepositToken.sol:517-520`). On the Pool side, `addToDepositTokensOfAccount` is gated only by `onlyIfDepositToken` (caller must be a registered deposit token) plus `onlyIfAdditionWillNotReachMaxTokens`, which reverts `UserReachedMaxTokens` once `debtTokensOfAccount.length(account) + depositTokensOfAccount.length(account) >= MAX_TOKENS_PER_USER` (`contracts/Pool.sol:79,143-148`). There is no consent check: the *recipient* never authorizes being added, and the only balance check (`_revertIfLocked`/`unlockedBalanceOf`) applies to the *sender's* free balance, so dust amounts pass.

The same pattern exists on mint: `_mint` calls `pool.addToDepositTokensOfAccount(account_)` when the balance was zero (`contracts/DepositToken.sol:485-488`), so `deposit(amount_, onBehalfOf_ = victim)` also reverts once the victim is at the cap, and `DebtToken` issuance that would add a new entry via `addToDebtTokensOfAccount` reverts identically.

Attack trace (all public entry points, unprivileged EOA):
1. For each registered deposit token `d_i`, attacker calls `d_i depositToken.underlying` faucet/own funds, then `d_i.deposit(x_i, attacker)` to obtain msdTOKENs.
2. Attacker calls `d_i.transfer(victim, dust)` for each `d_i`. Each call hits `_transfer` → `addToDepositTokensOfAccount(victim)` → pushes `d_i` into the victim's set.
3. After ~30 tokens (deposit + debt entries combined), the victim's set is full.
4. Any subsequent `deposit(..., onBehalfOf_=victim)` into a token the victim doesn't hold, any `transfer(victim, ...)` of a new token, or `DebtToken.issue` that would register a new debt token reverts with `UserReachedMaxTokens`.

Modifiers do not stop this: `whenNotPaused`/`whenNotShutdown` are irrelevant in normal operation, `nonReentrant` doesn't help, `onlyIfDepositToken` only checks the *caller token* is registered — exactly what the attacker legitimately uses — and there is no opt-in/allowlist for recipients. The pool-test suite itself confirms the revert path (`test/Pool.test.ts:1386-1415`).

### Impact Explanation
Permanent-freeze-adjacent liveness break for the targeted account: the victim cannot (a) deposit into any deposit token they don't already hold, (b) receive any new deposit token via `transfer`/`transferFrom` (which also breaks `NativeTokenGateway`/`VesperGateway`-assisted deposits into new tokens), and (c) mint debt in a new `DebtToken` via `issue`, since debt-token minting registers the debt token into `debtTokensOfAccount` and shares the same 30-entry budget. Existing collateral remains withdrawable (withdraw removes entries), so this is a persistent denial of the victim's core protocol functionality — deposits, leverage entry, and receipt of position tokens — rather than loss of existing funds. Cleaning the list requires the victim to fully zero out balances token-by-token, during which the attacker can cheaply re-fill freed slots at dust cost.

### Likelihood Explanation
High feasibility: requires only ordinary deposits and transfers at dust cost (bounded by deposit fees on dust, essentially the underlying's smallest units plus gas). No privileged role, oracle manipulation, or governance action is needed. The attack is repeatable and can be front-run-maintained by a bot re-dusting any slot the victim clears. Cost scales linearly with the number of registered deposit tokens but the attacker needs to fill only the slots the victim doesn't already occupy.

### Recommendation
Make per-account token-list membership consent-based: e.g., add an opt-in mapping set by the recipient before `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` will register a token, or only register tokens on actions initiated by the account owner (deposit/mint for self) while keeping unsolicited inbound transfers out of the tracked set and bounding their health-factor contribution separately. Alternatively, revert-free accounting: skip tracking tokens received via unsolicited `transfer` and compute `debtPositionOf` over all registered tokens weighted by actual balances.

### Proof of Concept
Hardhat sketch (fork or local deployment with a `Pool` having ≥2 registered `DepositToken`s; repeat for all listed tokens):

```ts
// attacker = unprivileged EOA; victim = target
const tokens = await pool.getDepositTokens(); // registered DepositToken addresses
for (const addr of tokens) {
  const dt = await ethers.getContractAt('DepositToken', addr);
  const underlying = await ethers.getContractAt('IERC20', await dt.underlying());
  // attacker acquires dust of underlying, then:
  await underlying.connect(attacker).approve(dt.address, DUST);
  await dt.connect(attacker).deposit(DUST, attacker.address);   // mint msdTOKEN to attacker
  await dt.connect(attacker).transfer(victim.address, 1);       // 1 wei dust
}
// After ~30 distinct tokens (deposit+debt entries combined):
// victim's set length == MAX_TOKENS_PER_USER
await expect(
  newDepositToken.connect(attacker).transfer(victim.address, 1)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
await expect(
  newDepositToken.connect(victim).deposit(AMOUNT, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens'); // _mint -> addToDepositTokensOfAccount
```

Uncertainty note: the debt-token leg (`addToDebtTokensOfAccount` call site inside `DebtToken._mint`/`issue`) was inferred from the shared `onlyIfAdditionWillNotReachMaxTokens` modifier and the deployment ABI; the exact DebtToken call site was not directly read in this session, but the deposit-token path and the revert behavior are confirmed by `contracts/DepositToken.sol:517-520` and `test/Pool.test.ts:1386-1415`.
