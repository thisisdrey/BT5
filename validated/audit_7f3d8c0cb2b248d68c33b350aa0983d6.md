### Title
Unauthenticated relay-target address in `NebulaControl_CreateRelayRequest` allows a peer to poison the terminal node's relay state for arbitrary third-party vpnIPs - ([File: relay_manager.go])

### Summary
`relayManager.handleCreateRelayRequest` accepts `m.RelayFromAddr` from the sending peer `h` with no check that `h` actually has any relationship with that address, and when `f.myVpnAddrsTable.Contains(target)` is true it immediately calls `AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)`, installing `Established` relay routing state for `from` keyed to `h`'s own already-authenticated session. An unprivileged peer `h` with a real tunnel to `f` can set `RelayFromAddr` to a victim vpnIp `V` it does not control and has never handshaked with.

### Finding Description
`h` in this function is only authenticated as the entity that owns the decrypted control-message tunnel to `f`; the payload field `m.RelayFromAddr` is attacker-supplied and unchecked against `h.vpnAddrs`: [1](#0-0) 

When the target is `f` itself, the code either updates or creates relay state keyed by the claimed `from` address without any verification that `h` is a legitimate relay for that address, and for the "no existing relay" branch it goes straight to `Established`: [2](#0-1) 

Unlike the "target is not me" branch, which gates relay creation on `rm.GetAmRelay()`: [3](#0-2) 

there is no equivalent authorization/consent check in the "target is me" branch for accepting an arbitrary third-party `from` claim. The `AddRelay` call stores this into `h.relayState` under key `vpnIp = from`: [4](#0-3) 

Because this state is `Established` immediately and `RemoteIndex` is fixed to the attacker-chosen `m.InitiatorRelayIndex`, if the real owner `V` later legitimately attempts to establish a relay to `f` through `h`, the completion logic will find the pre-existing (attacker-planted) entry and reject it due to an index mismatch: [5](#0-4) 

This lets an unprivileged, authenticated peer plant bogus, non-consensual routing state for arbitrary vpnIPs on any peer it has a tunnel to, and to pre-empt/deny a real victim's future legitimate relay establishment for that path.

### Impact Explanation
This is a remote-state-poisoning / denial-of-service issue: an authenticated but otherwise unprivileged peer can cause a target node to record fabricated relay routing state (`Established`) for arbitrary third-party vpnIPs it does not own, and can subsequently block/deny the real owner's legitimate relay setup through the same intermediary by index mismatch. It does not by itself decrypt or forge the victim's end-to-end Noise traffic (that still requires a legitimate cert/session with the target), so this does not rise to full session hijack, but it is a genuine unauthenticated write into hostmap/relay state reachable purely from attacker-controlled UDP/control-message content.

### Likelihood Explanation
Preconditions are minimal: attacker only needs one legitimate (unprivileged, self-certified) authenticated tunnel to the victim node `f`, which is the normal baseline for any Nebula peer. No CA control, no config access, no spoofed handshake keys are required — only a crafted `NebulaControl_CreateRelayRequest` with `RelayFromAddr` set to an arbitrary vpnIp. This is easily repeatable and deterministic.

### Recommendation
In `handleCreateRelayRequest`, before creating/updating relay state for `from`, verify that the claimed `from` address is consistent with a value the sending peer `h` is entitled to assert (e.g., require it to match a relay candidate list already known via the lighthouse for that `vpnIp`/`h` pair, or otherwise require some proof that `h` is authorized to relay on behalf of `from`), and do not transition new relay entries directly to `Established` without a completion step confirming the real owner of `from` participated in the exchange.

### Proof of Concept
Integration test outline:
1. Start two real Nebula controls: attacker `A` and target `F`, complete a real mutual handshake so `A` has a genuine `HostInfo` (`h`) on `F`.
2. Also start victim `V`'s cert/keys but do not let `V` handshake with `F` or `A`.
3. From `A`, construct and send a `NebulaControl` message of type `CreateRelayRequest` with `RelayFromAddr = V`'s vpnIp and `RelayToAddr = F`'s own vpnIp, over `A`'s authenticated tunnel to `F` (mirroring `newRelayControl` helper used in `control_test.go`).
4. On `F`, call `relayManager.HandleControlMsg(h, d, f)` (as in existing tests) and assert:
   - `h.relayState.QueryRelayForByIp(V)` returns a relay with `State == Established` even though `V` never sent or received any packet.
   - Simulate `V` performing the legitimate relay handshake with `A` afterward (sending the real `CreateRelayRequest`/`CreateRelayResponse` sequence) and assert it is rejected/logged as "Existing relay mismatch" due to the pre-planted `RemoteIndex`, demonstrating denial of the real relay path.

		_, inRelays := hm.Relays[index]
		if !inRelays {
			// Avoid standing up a relay that can't be used since only the primary hostinfo
			// will be pointed to by the relay logic

			if !hm.unlockedMakePrimary(relayHostInfo) {
				// The tunnel was torn down after the caller grabbed relayHostInfo. A relay standing
				// on an unlinked hostinfo would never carry traffic, and its Relays entry could
				// never be reclaimed since the delete-time cleanup has already run.
				return 0, errors.New("relay hostinfo is no longer in the hostmap")

				newRelay.RemoteIndex = *remoteIdx
			}
			relayHostInfo.relayState.InsertRelay(vpnIp, index, &newRelay)

		}
