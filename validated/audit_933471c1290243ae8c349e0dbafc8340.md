### Title
Unhardened double-precision usage/weight formula in `DelegateResourceActuator.validate()` can incorrectly reject or under-restrict legitimate resource delegations - ([File: actuator/src/main/java/org/tron/core/actuator/DelegateResourceActuator.java])

### Summary
`DelegateResourceActuator.validate()` computes the amount of frozen-v2 resource already "used" (and therefore unavailable for delegation) with raw `double` arithmetic:

```java
long netUsage = (long) (accountNetUsage * TRX_PRECISION * ((double)
    (dynamicStore.getTotalNetWeight()) / dynamicStore.getTotalNetLimit()));
```
and the analogous energy branch
```java
long energyUsage = (long) (ownerCapsule.getEnergyUsage() * TRX_PRECISION * ((double)
    (dynamicStore.getTotalEnergyWeight()) / dynamicStore.getTotalEnergyCurrentLimit()));
``` [1](#0-0) 

The result is then fed into `getV2NetUsage`/`getV2EnergyUsage` to decide whether `ownerCapsule.getFrozenV2BalanceForBandwidth()/Energy() - v2Usage < delegateBalance`, which gates whether a user-submitted `DelegateResourceContract` (an ordinary signed transaction any account can broadcast) succeeds or is rejected with `ContractValidateException`. [2](#0-1) 

### Finding Description
This is the exact bug class from the Astaria report: a "maximum potential debt / available resource" bound is computed with an arithmetic formula that loses precision (there, integer truncation from multiplying rate*duration; here, `double` truncation from `accountNetUsage * TRX_PRECISION * (weight/limit)`), and that miscalculated bound is used directly as a hard gate in transaction validation.

The codebase itself acknowledges this exact formula is unsafe: the equivalent computations in `EnergyProcessor.calculateGlobalEnergyLimit`/`calculateGlobalEnergyLimitV2`, `ResourceProcessor.calculateGlobalLimitV2`, and `RepositoryImpl.calculateGlobalEnergyLimit`/`usageToBalance` were rewritten to use `BigInteger` under a `hardenCalculation()`/`disableJavaLangMath()` flag specifically because the `double`-based version produces incorrect results for realistic magnitudes (see `calculateGlobalLimitV2`'s doc comment and the dedicated regression tests asserting the old formula is "buggy"): [3](#0-2) [4](#0-3) 

However, `DelegateResourceActuator.validate()` (and its query-path twin `Wallet.calcCanDelegatedBandWidthMaxSize`/`calcCanDelegatedEnergyMaxSize`) was never migrated to the hardened path — it still performs the raw `double` multiplication/division inline: [5](#0-4) 

For accounts with realistic large frozen balances/usage (bandwidth/energy usage in the tens/hundreds of billions, weights in the billions), `accountNetUsage * TRX_PRECISION` alone can already exceed `2^53` (double's exact-integer boundary), and multiplying further by a non-terminating fractional ratio `totalNetWeight/totalNetLimit` compounds rounding error. Depending on rounding direction this can:
1. Overestimate `netUsage`/`energyUsage`, causing `v2NetUsage`/`v2EnergyUsage` to be computed too high, so `frozenV2BalanceForBandwidth() - v2NetUsage < delegateBalance` becomes true even when the owner has genuinely sufficient available resource — the transaction is rejected with `ContractValidateException("delegateBalance must be less than or equal to available ...")` even though it is a valid request (denial of service on a legitimate action), or
2. Underestimate it, letting `delegateResource()` proceed and then subtract more from `FrozenV2Balance` than is truly free (`ownerCapsule.addFrozenBalanceForBandwidthV2(-delegateBalance)` in `execute()`), corrupting the owner's frozen-balance accounting. [6](#0-5) 

### Impact Explanation
Any account can be denied the ability to delegate bandwidth/energy they legitimately have available, purely due to floating-point rounding in a check that gates a consensus-level actuator — this mirrors the reported "denial of service" class exactly (legitimate operation blocked by an incorrect debt/usage bound). In the opposite rounding direction it risks corrupting `FrozenV2Balance` bookkeeping (owner's accounted-for frozen balance becoming inconsistent with actual state), which is an accounting-integrity issue on resource/stake balances. Both are Medium-severity: the DoS path denies a normal user operation reliably and deterministically for certain balance/weight ratios; the accounting path degrades correctness of `AccountCapsule` state used for un-delegate/unfreeze bookkeeping.

### Likelihood Explanation
`DelegateResourceContract` is broadcastable by any account holding frozen v2 balance — no privileged role is required. The precision-loss trigger condition (`usage * TRX_PRECISION * weight/limit` exceeding double's 2^53 exact range, or accumulating rounding error near the `delegateBalance` boundary) is realistically reachable on mainnet given actual TRX_PRECISION (1_000_000) and network-wide `totalNetWeight`/`totalNetLimit` magnitudes already observed in the codebase's own hardening tests (values in the 1e9–1e11 range trigger divergence). The bug is deterministic given specific account/global state, so it is reliably reproducible, not a rare edge case.

### Recommendation
Apply the same hardening already used elsewhere in the codebase (`ResourceProcessor.calculateGlobalLimitV2`, `RepositoryImpl.calculateGlobalEnergyLimit`) to `DelegateResourceActuator.validate()` and `Wallet.calcCanDelegatedBandWidthMaxSize`/`calcCanDelegatedEnergyMaxSize`: replace the inline `double` computation of `netUsage`/`energyUsage` with the `BigInteger`-based exact formula guarded by `hardenCalculation()`/`disableJavaLangMath()`, consistent with the rest of the resource-accounting code paths.

### Proof of Concept
Conceptual reproduction (mirrors the existing `CalculateGlobalLimitHardenTest`/`RepositoryImplHardenTest` methodology already in the repo):
1. Set `totalNetWeight` and `totalNetLimit` to values whose ratio is non-terminating in binary and whose product with a large `accountNetUsage * TRX_PRECISION` exceeds `2^53` (e.g. `totalNetWeight = 1_234_567`, `totalNetLimit = 43_200_000_000`, `accountNetUsage` in the billions range — values of the same order used in `testGlobalNetLimitV2ExactPrecision`).
2. Freeze a large `FrozenV2BalanceForBandwidth` for an owner account and drive `accountNetUsage` so that the exact (`BigInteger`) `v2NetUsage` is strictly less than `frozenV2BalanceForBandwidth() - delegateBalance`, i.e. the delegation should be valid.
3. Submit a `DelegateResourceContract` with that `delegateBalance`; because `DelegateResourceActuator.validate()` uses the `double` formula instead of the exact `BigInteger` one, the computed `v2NetUsage` differs from the exact value by enough to flip the `<` comparison, causing `ContractValidateException("delegateBalance must be less than or equal to available FreezeBandwidthV2 balance")` to be thrown for a request that is actually valid.

  /**
   * Hardened replacement of legacy V2 formula
   * {@code (long)(((double) frozeBalance / TRX_PRECISION)
   *               * ((double) totalLimit / totalWeight))}.
   *
   * <p>Preserves V2 semantics: equivalent to
   * {@code (frozeBalance * totalLimit) / (TRX_PRECISION * totalWeight)} with
   * a single integer truncation at the end. Critically, fractional weight
   * (i.e. {@code frozeBalance < TRX_PRECISION}) is preserved through the
   * multiplication and only truncated at the final divide, so small balances
   * yield the same proportional result as the double-arithmetic path.
   */
  protected long calculateGlobalLimitV2(long frozeBalance,
      long totalLimit, long totalWeight) {
    return BigInteger.valueOf(frozeBalance)
        .multiply(BigInteger.valueOf(totalLimit))
        .divide(BigInteger.valueOf(TRX_PRECISION)
            .multiply(BigInteger.valueOf(totalWeight)))
        .longValueExact();
  }

    VMConfig.initAllowHardenResourceCalculation(0);

        .multiply(java.math.BigInteger.valueOf(totalEnergyLimit))
        .divide(java.math.BigInteger.valueOf(totalEnergyWeight))
