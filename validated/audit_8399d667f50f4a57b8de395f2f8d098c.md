Audit Report

## Title
Underpriced `submit` in `snowbridge-pallet-inbound-queue-v2` allows unbounded-size Ethereum messages to consume excessive weight/PoV during XCM conversion - (File: `bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs`)

## Summary
The `submit` extrinsic in `snowbridge-pallet-inbound-queue-v2` is charged the fixed constant weight `T::WeightInfo::submit()` at [3](#0-2) , regardless of the decoded message's size. The decoded `Message` contains attacker-controlled unbounded fields `assets: Vec<EthereumAsset>` and `payload: Payload::Raw(Vec<u8>)` at [4](#0-3) , which are iterated/expanded without bound during XCM conversion in `MessageToXcm::prepare`/`convert` at [5](#0-4)  and [6](#0-5) .

## Finding Description
`submit()` verifies the proof, then decodes the event log into a `Message` via `Message::try_from`, which populates `assets` and `payload` from Solidity-encoded, attacker-controlled arrays (`EthereumAsset[] assets`, `bytes data`) sourced from the permissionless Ethereum-side `OutboundMessageAccepted` event at [7](#0-6) . `Message::extract_assets` loops over the entire `payload.assets` slice with no cap at [8](#0-7) . During `process_message` → `MessageProcessor::process_message` → `MessageToXcm::convert` → `prepare()`, the code iterates `message.assets` unbounded (pushing `AssetTransfer` per entry) and decodes/appends the raw XCM payload with `decode_raw_xcm`/`instructions.extend(message.remote_xcm.0)`, all proportional in cost to the attacker-chosen size [9](#0-8) . None of this scales `T::WeightInfo::submit()`, which is a single fixed-fixture benchmark result with no linear component, as shown in `benchmarking.rs` and `weights.rs` [10](#0-9) [11](#0-10) . Notably, the sibling v1 `inbound-queue` pallet's `Config` explicitly defines `type MaxMessageSize: Get<u32>` and a `LengthToFee` for delivery cost [1](#0-0) , while the v2 `Config` at [2](#0-1)  has no equivalent bound or length-based fee mechanism whatsoever — confirming this is a regression/gap relative to the existing v1 design pattern rather than a deliberate simplification with an equivalent safeguard elsewhere in the pallet.

## Impact Explanation
This matches the "public underpriced work that degrades block production or stalls bridge processing" impact class. A caller can submit a valid, verified Ethereum event containing a large `assets` array and/or large `payload.Raw` bytes blob, causing CPU/PoV cost in the conversion path proportional to the attacker-chosen size, while `submit()` is charged the same fixed weight as a minimal message. Repeated cheap submissions with maximal payloads can amplify actual execution time beyond the weight declared for the extrinsic, disrupting BridgeHub block production time budgets.

## Likelihood Explanation
No privileged or colluding-peer capability is needed: any ordinary Ethereum-side user can call the permissionless Gateway `sendMessage` entrypoint with a large `assets` array / large XCM payload bytes (bounded only by Ethereum's own gas/calldata limits, which are unrelated to and much larger than what BridgeHub weight-meters), then relay it via `submit`. The vulnerable `prepare()`/`convert()` path executes on every successfully verified message, so the trigger is simply "large event payload," fully within attacker control.

## Recommendation
- Add a `MaxMessageSize`/`MaxAssetsPerMessage` bound to `snowbridge-pallet-inbound-queue-v2::Config`, mirroring the v1 `inbound-queue` pattern.
- Enforce these bounds in `Message::try_from`/`prepare()` before conversion, rejecting oversized messages rather than relying on Ethereum-side gas limits as an implicit, off-protocol assumption.
- Make `WeightInfo::submit()` a function of decoded message size (number of assets, payload byte length) and benchmark/charge accordingly.

## Proof of Concept
1. On Ethereum, emit `OutboundMessageAccepted` via the Gateway with `Payload.assets` populated with a large number of entries and/or a large `xcm.data` byte blob, within Ethereum's own gas/calldata limits.
2. Obtain the finalized event/receipt proof.
3. Call `EthereumInboundQueueV2::submit(event_proof)` on BridgeHub; note it is charged only the fixed `WeightInfo::submit()` weight regardless of payload size, per [3](#0-2) .
4. Observe that `process_message` → `MessageToXcm::convert` iterates the full `assets` vector at [5](#0-4)  and appends the full raw XCM payload at [6](#0-5) , consuming CPU/PoV proportional to size, unaccounted for in step 3's charged weight.
5. Repeating with maximal-size messages at the fixed fee demonstrates size-unbounded, underpriced work performed on each block that processes such a message.

impl TryFrom<&Log> for Message {
	type Error = MessageDecodeError;

	fn try_from(log: &Log) -> Result<Self, Self::Error> {
		// Convert to B256 for Alloy decoding
		let topics: Vec<B256> = log.topics.iter().map(|x| B256::from_slice(x.as_ref())).collect();

		// Decode the Solidity event from raw logs
		let event = IGatewayV2::OutboundMessageAccepted::decode_raw_log_validate(topics, &log.data)
			.map_err(|_| MessageDecodeError)?;

		let event_payload = event.payload;

		let substrate_assets = Self::extract_assets(&event_payload)?;

		let message_payload = Payload::try_from(&event_payload)?;

		let mut claimer = None;
		if event_payload.claimer.len() > 0 {
			claimer = Some(event_payload.claimer.to_vec());
		}

		let message = Message {
			gateway: log.address,
			nonce: event.nonce,
			origin: H160::from(event_payload.origin.as_ref()),
			assets: substrate_assets,
			payload: message_payload,
			claimer,
			value: event_payload.value,
			execution_fee: event_payload.executionFee,
			relayer_fee: event_payload.relayerFee,
		};

		Ok(message)
	}
}

impl Message {
	fn extract_assets(
		payload: &IGatewayV2::Payload,

		let mut substrate_assets = vec![];
		for asset in &payload.assets {
			substrate_assets.push(EthereumAsset::try_from(asset)?);
		}
		Ok(substrate_assets)
	}
}
