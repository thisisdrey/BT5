### Title
Missing Non-Zero/Reachable Address Validation in `AccountPermissionUpdateActuator` Permission Keys - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
`AccountPermissionUpdateActuator.checkPermission()` validates that each permission key's address is a well-formed TRON address (correct length and prefix byte) via `DecodeUtil.addressValid()`, but never checks that the address is a real, controllable account (e.g., not the all-zero/degenerate address) or that the account itself exists. This mirrors the reported bug class: a critical control field (here, the account's `Owner`/`Active`/`Witness` permission signer addresses) can be set to a value nobody can ever sign for, permanently bricking control of the account.

### Finding Description
`checkPermission()` only validates key addresses using: [1](#0-0) 

and `DecodeUtil.addressValid()` itself only checks the byte length and the fixed prefix byte — it never rejects the degenerate address whose 20 payload bytes are all zero, nor does it check the key address maps to any actually existing/controllable account: [2](#0-1) 

The permission `execute()` path then directly commits whatever keys passed `checkPermission()` as the account's new owner/active/witness permission, with no additional sanity check on the resulting signer set: [3](#0-2) [4](#0-3) 

Because `updatePermissions()` simply overwrites the `OwnerPermission` (and Active/Witness permissions) with whatever `Key` entries were supplied, a transaction signer can set their `Owner` permission's sole key (or all keys, up to the configured threshold) to an address such as `41 0000000000000000000000000000000000000000` — which passes the format check but for which no private key exists (it is the placeholder/"blackhole"-style zero address). Notably, java-tron's own initialization code treats an all-zero address as a valid `Owner`-permission key for the black-hole account, confirming that the format check alone permits this value: [5](#0-4) 

### Impact Explanation
If an account's `Owner` permission (and, since actives derive authorization for asset transfers/voting/etc., its `Active` permissions) is set to a key/threshold combination that includes only unreachable (zero or otherwise uncontrollable) addresses, the account becomes permanently unable to authorize any further `AccountPermissionUpdateContract`, transfers, votes, freezes, or withdrawals gated by that permission. This is a permanent, irreversible loss of control over the account and any TRX/TRC-10/frozen balances or voting rights held by it — matching the "permanent freezing of funds/control" impact class. Because this can be triggered by the account owner's own single signed transaction (or induced via social engineering/tooling bug), any account using `AccountPermissionUpdateContract` is exposed.

### Likelihood Explanation
The path is reachable directly by any account owner submitting a normal `AccountPermissionUpdateContract` transaction (gated only by `AllowMultiSign` being enabled), which is a standard, unprivileged wallet operation. No special privileges are required, and the validation logic that should prevent this (format-only address check) is provably insufficient to prevent selecting a permanently unusable signer address.

### Recommendation
In `AccountPermissionUpdateActuator.checkPermission()`, in addition to `DecodeUtil.addressValid()`, reject degenerate/reserved addresses (e.g., the all-zero payload address, and other known unspendable/reserved addresses) as permission-key addresses, similar to the `require(rewardsDistribution_ != address(0))` fix recommended in the original report. Consider also warning/rejecting when the resulting permission's reachable key set could never satisfy `threshold` (e.g., verifying each key address is distinct from known-burn/black-hole addresses).

### Proof of Concept
1. Attacker/account owner (with `AllowMultiSign` enabled) constructs an `AccountPermissionUpdateContract` with `ownerAddress` = their own account.
2. Sets the `Owner` permission with a single key: `address = 0x41 || 20×0x00` (format-valid, prefix-valid, but unspendable), `weight = 1`, `threshold = 1`.
3. Calls `AccountPermissionUpdateActuator.validate()` — passes because `checkPermission()` only calls `DecodeUtil.addressValid()`, which accepts this address as shown in: [2](#0-1) 
4. `execute()` commits the update via `AccountCapsule.updatePermissions()`: [4](#0-3) 
5. The account's `Owner` permission (and any future permission changes or high-authority operations gated on Owner) can never be satisfied again, since no private key exists for the zero address — permanently freezing control of the account.

  public static boolean addressValid(byte[] address) {
    if (ArrayUtils.isEmpty(address)) {
      logger.warn("Warning: Address is empty !!");
      return false;
    }
    if (address.length != ADDRESS_SIZE / 2) {
      logger.warn(
          "Warning: Address length need " + ADDRESS_SIZE + " but " + address.length
              + " !!");
      return false;
    }

    if (address[0] != addressPreFixByte) {
      logger.warn("Warning: Address need prefix with " + addressPreFixByte + " but "
          + address[0] + " !!");
      return false;
    }
    return true;
  }

  public void updatePermissions(Permission owner, Permission witness, List<Permission> actives) {
    Builder builder = this.account.toBuilder();

    owner = owner.toBuilder().setId(0).build();
    builder.setOwnerPermission(owner);
    if (witness != null && builder.getIsWitness()) {
      witness = witness.toBuilder().setId(1).build();
      builder.setWitnessPermission(witness);
    }

    builder.clearActivePermission();
    if (actives != null) {
      for (int i = 0; i < actives.size(); i++) {
        Permission permission = actives.get(i).toBuilder().setId(i + 2).build();
        builder.addActivePermission(permission);
      }
    }

    this.account = builder.build();
  }
