### Title
NUL byte in commit metadata breaks `for-each-ref` `\x00`-delimited parsing, permanently DoS-ing branch/ref listing RPCs - (File: internal/gitaly/service/ref/util.go)

### Summary
`FindLocalBranches`, `FindAllBranches`, `FindAllRemoteBranches` (and the commit-log iterator used by `ListRefs`-adjacent branch listing) parse `git for-each-ref` output by splitting each record on the `\x00` field separator and asserting a fixed field count. An ordinary user can push a commit whose message/author/committer fields legitimately contain a literal NUL byte (git's object model does not forbid this in the free-text body), which desynchronizes the field count and makes every subsequent listing call for the whole repository fail — not just for the offending ref — mirroring the `stashRewards()` pattern where a single externally-supplied list entry (an ERC20 token that reverts on zero transfers) that is not sanity-checked blocks processing of the entire batch.

### Finding Description
`buildBranch` requires an exact field count: [1](#0-0) 

and `parseRef` similarly hard-fails on any mismatch: [2](#0-1) 

The fields are populated straight from `for-each-ref --format=...%00...%00`, using free-text fields such as `%(subject)` and `%(contents)`: [3](#0-2) 

The commit-message body is attacker-controlled content pushed by an ordinary user via `git push`; it is not restricted from containing embedded NUL bytes at the git object-storage layer. If such a byte lands inside `%(subject)` or `%(contents)`, the record produced by `for-each-ref` will contain one extra `\x00`-delimited element. This causes `bytes.Split(record, []byte("\x00"))` in `commitIterator.Next()` to overflow the expected slot count, and `buildBranch` returns an error: [4](#0-3) 

That error is propagated and terminates the RPC handler entirely: [5](#0-4) 

Because the malformed ref/commit is a *persistent, externally-controlled* piece of repository state (the analog of `IGauge(gauge).reward_tokens` in the original report — a list the system does not control), every future invocation of the affected RPC against that repository will hit the same record and fail, exactly as `stashRewards()` becomes permanently blocked once a non-zero-transfer-tolerant token enters the external reward-token list.

### Impact Explanation
Any user able to push a branch can render `FindLocalBranches`/`FindAllBranches`/`FindAllRemoteBranches` (and any other caller of `buildBranch`/`parseRef` against affected format strings) permanently broken for that repository until the offending commit/ref is manually removed by an operator. This is a base-functionality availability issue (branch listing) analogous in class and severity to the original medium-severity finding: a single externally supplied, unsanitized list element blocks a whole batch operation indefinitely, and the fix (which is not directly controllable by the system, mirroring "pool reward token list is external") requires manual intervention rather than being self-healing.

### Likelihood Explanation
Likelihood is moderate-to-high in principle (any ordinary contributor with push access can craft a commit message containing arbitrary bytes), but I could not fully verify within available tools whether Gitaly's/Git's default `receive-pack` fsck configuration (`fsck.<msg>=...`) or object validation rejects NUL bytes in commit message bodies before they are persisted; the existing presence of "null byte" test cases in `find_local_branches_test.go` and `list_refs_test.go` suggests this edge case is already partially exercised in tests, but I was not able to confirm whether those tests assert correct rejection/handling or merely document existing behavior, given no further tool calls were available to inspect their contents.

### Recommendation
- Do not hard-fail the entire iterator/RPC on a single malformed record; skip or sanitize the offending ref/commit and continue processing the remainder of the list, similar to the reward-token-amount check recommended in the original report (guard against the malformed input rather than letting it abort the whole batch).
- Alternatively/additionally, enforce (or verify enforcement of) `fsck` rejection of NUL bytes in commit message content at `receive-pack` time so such objects cannot enter the repository in the first place.
- Add regression tests that push a commit with an embedded NUL byte in the subject/body and assert that `FindLocalBranches`/`FindAllBranches`/`FindAllRemoteBranches` continue to function for the remaining, well-formed refs.

### Proof of Concept
1. As an ordinary user with push access, create a commit whose message contains a literal `\x00` byte (e.g., via `git commit-tree` with a hand-crafted commit object, bypassing porcelain restrictions) and push a branch pointing at it.
2. Call `FindAllBranches` (or `FindLocalBranches`) against the repository.
3. `for-each-ref --format=...%00...%00` emits a record with an extra field due to the embedded NUL, `bytes.Split` in `commitIterator.Next()` produces a field count mismatch, `buildBranch` returns `"invalid field count"`, and the RPC returns an internal error for the entire repository.
4. Repeat the call: it fails every time, since the malformed commit/ref persists in repository state, causing a lasting denial of service for branch-listing RPCs on that repository.

	}

}
