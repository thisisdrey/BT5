### Title
Unbounded memory allocation via `sock.read_to_end` in `run_http_request` - ([File: libsigner/src/http.rs])

### Summary
`run_http_request` reads an entire HTTP response into memory with `sock.read_to_end(&mut buf)` before any header parsing or size validation occurs. Unlike the chunked-body decode path in `decode_http_body`, which bounds decoded bytes via `MAX_MESSAGE_LEN`, the raw response read has no size cap at all, so a StackerDB peer that streams data indefinitely (or very slowly) can force the connecting signer to buffer unbounded bytes in memory.

### Finding Description
`StackerDBSession::rpc_request` (`libsigner/src/session.rs:162-172`) opens a `TcpStream` to a configured StackerDB host, applies only a read/write *timeout* via `sock.set_read_timeout`/`set_write_timeout` (`libsigner/src/session.rs:132-133`), and delegates the actual request/response cycle to `run_http_request` (`libsigner/src/http.rs:221-262`).

Inside `run_http_request`, after writing the request, the code does:
```rust
let mut buf = vec![];
sock.read_to_end(&mut buf)?;
let (headers, body_offset) = decode_http_response(&buf)?;
```
`read_to_end` loops calling `read()` until the peer closes the connection or an error/timeout occurs; it has no upper bound on total bytes accumulated in `buf`. `set_read_timeout` only bounds the time waited for *each individual read syscall to make progress* — it does not bound the total number of reads or total bytes transferred. A malicious peer can send a small amount of data periodically (faster than the per-call timeout) indefinitely, or simply stream continuously without ever closing the socket, and `buf` will grow without bound until the process runs out of memory. Parsing/validation (`decode_http_response`, then bounded `decode_http_body` via `MAX_MESSAGE_LEN`) only happens *after* the entire response has already been buffered, so those checks provide no protection against this attack. ### Impact Explanation
A malicious or compromised StackerDB replica endpoint that a signer's `StackerDBSession` connects to can cause unbounded memory growth in the signer process on a single RPC call (`list_chunks`, `get_chunks`, `get_latest_chunks`, or `put_chunk`, all of which route through `rpc_request` → `run_http_request`). Repeated or sustained connections can exhaust available memory, crashing the signer process — an unauthenticated, remotely triggerable DoS requiring no privileged role, matching the "Critical - remote crash/unauthenticated DoS from few messages" category.

### Likelihood Explanation
Exploitability requires that the host in `StackerDBSession` (set via `StackerDBSession::new`/`connect`) resolves to an attacker-controlled or attacker-influenced endpoint the signer will connect to as a StackerDB replica. Given that precondition (as posited by the question), the attack is trivial and cheap: a bare `TcpListener` that answers valid HTTP status/headers and then streams data continuously without closing the connection, sending at least a trickle of bytes more frequently than `socket_timeout` to keep the per-read timeout from firing. No secrets, signatures, or elevated privileges are needed, and the attack is fully repeatable per connection attempt.

### Recommendation
Bound the total number of bytes read in `run_http_request` before parsing, e.g. replace the single `sock.read_to_end(&mut buf)` call with a loop that reads in fixed-size chunks and aborts with an error once accumulated size exceeds `MAX_MESSAGE_LEN` (or a suitably small max HTTP response size), mirroring the cap already used in `decode_http_body`'s chunked-transfer path.

### Proof of Concept
```rust
// libsigner/src/http.rs or session.rs test module
use std::io::Write;
use std::net::TcpListener;
use std::thread;
use std::time::Duration;

#[test]
fn unbounded_read_dos() {
    let listener = TcpListener::bind("127.0.0.1:0").unwrap();
    let addr = listener.local_addr().unwrap();

    thread::spawn(move || {
        if let Ok((mut stream, _)) = listener.accept() {
            stream.write_all(b"HTTP/1.1 200 OK\r\n\r\n").unwrap();
            // Never close; keep streaming small bursts faster than the
            // client's read timeout so read_to_end never returns.
            loop {
                if stream.write_all(&vec![0u8; 1 << 20]).is_err() {
                    break;
                }
                thread::sleep(Duration::from_millis(10));
            }
        }
    });

    let mut sock = std::net::TcpStream::connect(addr).unwrap();
    sock.set_read_timeout(Some(Duration::from_millis(500))).unwrap();

    // This call should never return / should exhaust memory instead of
    // failing fast with a bounded-size error.
    let _ = libsigner::http::run_http_request(&mut sock, "test", "GET", "/", None, &[]);
}
```
The assertion of the fault is the absence of any error or bound before memory exhaustion: the process's resident memory grows unbounded while `sock.read_to_end(&mut buf)` at `libsigner/src/http.rs:251` continues looping, in contrast to the bounded loop expected (comparable to `HttpChunkedTransferReader`'s `MAX_MESSAGE_LEN` enforcement at `libsigner/src/http.rs:207`).

pub fn decode_http_body(headers: &HashMap<String, String>, mut buf: &[u8]) -> io::Result<Vec<u8>> {
    let chunked = if let Some(val) = headers.get("transfer-encoding") {
        val == "chunked"
    } else {
        false
    };

    let body = if chunked {
        // chunked encoding
        let ptr = &mut buf;
        let mut fd = HttpChunkedTransferReader::from_reader(ptr, MAX_MESSAGE_LEN.into());
        let mut decoded_body = vec![];
        fd.read_to_end(&mut decoded_body)?;
        decoded_body
    } else {
        // body is just as-is
        buf.to_vec()
    };

    Ok(body)
}
