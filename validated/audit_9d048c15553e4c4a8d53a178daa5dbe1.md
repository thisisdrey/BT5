Based on my investigation, I found a genuine equality-boundary mismatch in the StackerDB chunk-freshness logic that is directly analogous to the reported bug class (a `>`/`>=` boundary discrepancy between two checkpoints that are supposed to agree).

### Title
Inconsistent freshness boundary between network-level chunk validation and storage-level chunk validation for StackerDB - (File: `stackslib/src/net/stackerdb/mod.rs` and `stackslib/src/net/stackerdb/db.rs`)

### Summary
`PeerNetwork::validate_received_chunk`, which gates whether a pushed/downloaded StackerDB chunk is treated as fresh at the network layer, uses `data.slot_version < *expected_version` to reject staleness [1](#0-0) , meaning a chunk whose version **equals** the currently known version is accepted as valid ("current or newer"). But the actual persistence gate, `StackerDBTx::try_replace_chunk`, uses the strict inequality `slot_desc.slot_version <= slot_validation.version` to reject as stale [2](#0-1) , meaning a same-version chunk is always rejected on write.

### Finding Description
These two functions are meant to enforce the same "freshness" invariant at two different points in the pipeline (network intake vs. disk commit), but they disagree exactly at the boundary `slot_version == expected_version`:
- `validate_received_chunk` (network gate, used both by the download-sync path via `StackerDBSync::validate_downloaded_chunk` and the unsolicited push path via `handle_unsolicited_StackerDBPushChunk`) treats `==` as **valid** [3](#0-2) .
- `try_replace_chunk` (the actual DB write path) treats `==` as **stale/rejected** [4](#0-3) .

Because a slot's owner can re-sign different content at the *same* version number (the signature only binds `slot_id`, `slot_version`, and `data_hash`, not monotonic freshness beyond version [5](#0-4) ), an attacker who controls a slot's private key can craft a same-version chunk with different data and have it pass the network-level "is this fresh enough to act on" check even though the storage layer would reject it as stale. In `handle_unsolicited_StackerDBPushChunk`, a chunk that passes `validate_received_chunk` immediately causes the peer's in-memory inventory bookkeeping to be patched to reflect that version as "have it" (`*slot_version = chunk_data.chunk_data.slot_version;`) [6](#0-5) , and the message is marked to be forwarded to the relayer for processing [7](#0-6)  — before the downstream `try_replace_chunk` call (reached via `relay.rs`) would actually reject it as `StaleChunk`.

### Impact Explanation
This breaks the equality that "network-accepted implies storable," producing served-vs-committed data confusion: a node can be made to believe (via its own inventory bookkeeping and relayed acknowledgements) that it holds a given version of a chunk, and can relay/acknowledge that fact to peers, while its actual persisted data for that version never changes (or, depending on race/ordering with concurrent legitimate writes, diverges from what other replicas store for the same version number). This falls into the "non-canonical state served as canonical" class called out as a valid analog in scope, since the inventory advertised to the network does not correctly reflect what's actually committed to the local StackerDB replica.

### Likelihood Explanation
This is remotely triggerable by any unprivileged party who owns (or has compromised) a single StackerDB slot signing key — no special node privileges are required, and it can be exercised via a single unsolicited `StackerDBPushChunk` message at the exact version already known to the target node.

### Recommendation
Align the two freshness checks. The `expected_versions` values passed into `validate_received_chunk` are populated with the *next* version to accept (the sync/download code already treats `local_version >= remote_version` as "nothing needed" [8](#0-7) ), so `validate_received_chunk` should reject `data.slot_version <= *expected_version` (i.e., require strictly newer), matching `try_replace_chunk`'s `<=` rejection, rather than only rejecting `<`.

### Proof of Concept
1. Attacker controls slot `S` with private key `K`, currently stored at version `N` with data `D1` on victim node `V`.
2. Attacker constructs `StackerDBChunkData { slot_id: S, slot_version: N, data: D2 }` and signs it with `K` (valid signature, since signing only commits to `slot_id`/`slot_version`/`data_hash`) [9](#0-8) .
3. Attacker sends this as an unsolicited `StackerDBPushChunk` to `V`.
4. `handle_unsolicited_StackerDBPushChunk` calls `validate_received_chunk`, which computes `expected_version = N` and checks only `data.slot_version < *expected_version` — `N < N` is false, so the chunk passes as "current or newer" [1](#0-0) .
5. `V` patches its local chunk-inventory bookkeeping to record version `N` as received/acknowledged and marks the chunk for relaying [6](#0-5) , while the actual `try_replace_chunk` persistence step will reject `D2` as `StaleChunk` since `N <= N` [2](#0-1) , leaving `V`'s on-disk data at `D1` — a mismatch between what `V`'s network-facing state machine/acks claim and what is actually stored.

Note: I could not fully trace the exact downstream call path in `stackslib/src/net/relay.rs` from "forward to relayer" to the final `try_replace_chunk` invocation within the available tool-call budget, so the precise wire-level propagation-to-other-peers consequence (vs. purely local inventory/state inconsistency) is not 100% confirmed and should be verified directly in `relay.rs` before treating this as fully proven at Critical/High severity.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Sign this slot metadata, committing to slot_id, slot_version, and
    /// data_hash.  Sets self.signature to the signature.
    /// Fails if the underlying crypto library fails
    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
