### Title
Cross-repository bundle-URI disclosure via spoofable `virtual_storage` gRPC metadata (metadata-append ordering bug) - ([File: internal/bundleuri/manager.go])

### Finding Description
`storageNameForBundle` blindly trusts client-controlled gRPC metadata to decide which storage namespace a bundle's signed URL is generated for: [1](#0-0) 

It reads `VirtualStorageKey` ("`virtual_storage`") from the incoming metadata and, if present, uses `vs[0]` as the storage name to compose `bundleRelativePath` — which feeds directly into `SignedURL` / `UploadPackGitConfig`: [2](#0-1) 

The intended, trusted source of this metadata is Praefect's coordinator, which injects the *real* virtual storage name after routing decisions are made: [3](#0-2) 

Critically, `injectVirtualStorageInMetadata` uses `md.Append(VirtualStorageKey, vs)` on a copy of the *existing* incoming metadata rather than `md.Set(...)`. If the client (an unprivileged, authenticated GitLab user issuing the upload-pack RPC through Praefect) has already placed a `virtual_storage` entry in their own request metadata, that attacker-supplied value remains at index 0 of the resulting `[]string`, and Praefect's legitimate value is appended at index 1. Since `gitaly--008/internal/bundleuri/manager.go`'s `storageNameForBundle` unconditionally takes `vs[0]`, the attacker's forged value silently overrides the value Praefect intended to set, without any validation that the requested storage matches the repository the attacker is authorized to access. The repository's relative path portion (`repo.GetRelativePath()`) is still constrained to the attacker's own authorized repository, but GitLab's hashed-storage relative paths are deterministically derivable from the (often publicly enumerable) numeric project ID, so an attacker who knows or guesses a target project's ID and the victim virtual-storage's name can construct the exact `bundleRelativePath` string that corresponds to the victim's bundle object in the object-storage sink, and cause the server to compute and return a signed URL for that path.

None of the existing safety checks intervene: there is no authorization check tying the `virtual_storage` metadata value to the actual project/repository being served, and `storage.ValidateRelativePath`-style checks are not applied to the composed sink object key here — the bundle sink path is a bucket key, not a filesystem path guarded by locator validation.

### Impact Explanation
An unprivileged, authenticated user can obtain a Gitaly-issued signed URL (via git bundle-uri advertisement during their own authorized `upload-pack`) that resolves to another repository's stored bundle object under a storage namespace they do not own, provided they can predict/guess the victim's relative path and virtual storage name. This is a cross-tenant secret/credential (time-limited signed URL) leak, matching GitLab's "sensitive data disclosure / cross-repository object access" bounty class — the leaked signed URL grants at least read access to a bundle (compressed git history/objects) of a repository the attacker is not authorized to read.

### Likelihood Explanation
The attacker only needs standard authenticated push/fetch capability on any project (to be able to invoke `git-upload-pack` with `command=bundle-uri`) and the ability to set arbitrary gRPC metadata on their own outgoing request (trivial via a raw gRPC/HTTP smart-protocol client, bypassing the normal git client). It additionally requires knowledge/guessing of a victim's virtual storage name (usually from a small, low-entropy, often-public config set) and the victim's hashed relative path (deterministically derivable from project ID, which is frequently public or easily enumerable). This makes the attack feasible but not trivial for an arbitrary unknown target — it is most exploitable when the attacker already knows or targets a specific victim project ID.

### Recommendation
- In `internal/praefect/coordinator.go`, replace `md.Append(VirtualStorageKey, vs)` with logic that first deletes any pre-existing client-supplied `VirtualStorageKey` entries (`md.Delete(VirtualStorageKey)`) before setting the authoritative value, so a spoofed client value can never coexist with/precede the legitimate one.
- In `internal/bundleuri/manager.go`'s `storageNameForBundle`, do not trust arbitrary incoming metadata directly; instead, only accept this value if it was injected via a Praefect-internal, cryptographically-verifiable channel (e.g., server-to-server auth context) or strip/reject client-set `virtual_storage` metadata at the Gitaly/Praefect ingress boundary.
- Bind the bundle's storage/relative-path key to the resolved repository/storage assignment already established by request routing and authorization, rather than re-reading mutable request metadata deep in the RPC handler.

### Proof of Concept
```go
// internal/bundleuri/manager_test.go (conceptual addition)
func TestStorageNameForBundle_SpoofedMetadataPrecedence(t *testing.T) {
    ctx := testhelper.Context(t)

    // Simulate client-supplied metadata with attacker's forged value already present
    md := metadata.New(map[string]string{VirtualStorageKey: "victim-virtual-storage"})
    ctx = metadata.NewIncomingContext(ctx, md)

    // Simulate Praefect's coordinator "injecting" the legitimate value via Append
    // (mirrors internal/praefect/coordinator.go:injectVirtualStorageInMetadata)
    existingMD, _ := metadata.FromIncomingContext(ctx)
    existingMD = existingMD.Copy()
    existingMD.Append(VirtualStorageKey, "attacker-real-virtual-storage")
    ctx = metadata.NewIncomingContext(ctx, existingMD)

    repo := &gitalypb.Repository{StorageName: "attacker-real-virtual-storage", RelativePath: "@hashed/xx/yy/attacker-project.git"}

    // BUG: resolves to victim's storage, not the attacker's real/assigned storage
    got := storageNameForBundle(ctx, repo)
    require.Equal(t, "victim-virtual-storage", got) // demonstrates spoofed value wins
}
```
Expected (buggy) result: `storageNameForBundle` returns `"victim-virtual-storage"` — the attacker-forged value — because `md.Get(VirtualStorageKey)[0]` returns the first-appended (attacker's) entry, confirming that `SignedURL`/`UploadPackGitConfig` would compose and return a bundle URL rooted at the victim's storage namespace if the attacker can additionally guess the corresponding hashed relative path for a target project ID.

// SignedURL returns a public URL to give anyone access to download the bundle from.
func (g *GenerationManager) SignedURL(ctx context.Context, repo storage.Repository) (string, error) {
	relativePath := bundleRelativePath(ctx, repo, defaultBundle)

	repoProto, ok := repo.(*gitalypb.Repository)
	if !ok {
		return "", fmt.Errorf("unexpected repository type %t", repo)
	}

	if tx := storage.ExtractTransaction(ctx); tx != nil {
		origRepo := tx.OriginalRepository(repoProto)
		relativePath = bundleRelativePath(ctx, origRepo, defaultBundle)
	}

	return g.sink.signedURL(ctx, relativePath)
}

// UploadPackGitConfig is a helper function to provide all required, and computed, configurations
// to inject into the `git-upload-pack` command in order to advertise `bundle-uri` and provide
// the URI for the bundle for the given repository.
func (g *GenerationManager) UploadPackGitConfig(ctx context.Context, repo storage.Repository) []gitcmd.ConfigPair {
	uri, err := g.SignedURL(ctx, repo)
	if err != nil {
		if st, ok := status.FromError(err); !ok || st.Code() != codes.NotFound {
			g.logger.WithField("bundle_uri_error", err)
		}
		return CapabilitiesGitConfig(ctx, false)
	}
	return UploadPackGitConfig(ctx, uri)
}

// bundleRelativePath returns a relative path of the bundle-URI bundle inside the bucket.
func bundleRelativePath(ctx context.Context, repo storage.Repository, name string) string {
	repoPath := filepath.Join(storageNameForBundle(ctx, repo), repo.GetRelativePath())
	return filepath.Join(repoPath, "uri", name+".bundle")
}

func storageNameForBundle(ctx context.Context, repo storage.Repository) string {
	storageName := repo.GetStorageName()
	md, _ := metadata.FromIncomingContext(ctx)
	vs := md.Get(VirtualStorageKey)
	if len(vs) > 0 {
		storageName = vs[0]
	}
	return storageName
}

func injectVirtualStorageInMetadata(ctx context.Context, vs string) context.Context {
	md, ok := grpc_metadata.FromIncomingContext(ctx)
	if !ok {
		md = grpc_metadata.New(nil)
	}
	// Make a copy so we don't modify the original
	md = md.Copy()
	md.Append(VirtualStorageKey, vs)
	return grpc_metadata.NewIncomingContext(ctx, md)
}
