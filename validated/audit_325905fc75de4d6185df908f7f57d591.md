### Title
Missing content-hash verification in `extend_with_attachments` allows peer reliability score inflation via mismatched attachments - (File: stackslib/src/net/atlas/download.rs)

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` calls `report.bump_successful_requests()` as soon as `response.decode_atlas_get_attachment()` succeeds, without ever comparing the decoded attachment's actual hash to the `AttachmentRequest.content_hash` that was requested. A remote peer can therefore return any syntactically well-formed but content-mismatched attachment and still be credited with a "successful" download.

### Finding Description
In `extend_with_attachments` (stackslib/src/net/atlas/download.rs:530-558), for each request/response pair:
```
if let Ok(response) = response.decode_atlas_get_attachment() {
    self.attachments.insert(response.attachment);
    report.bump_successful_requests();
} else {
    report.bump_failed_requests();
}
``` [1](#0-0) 

The only gate is whether the HTTP payload can be *decoded* into an `Attachment` struct — there is no check that `response.attachment.hash() == request.content_hash`. The requested hash is available on the `AttachmentRequest` object (`content_hash` field) at the point the request was queued, per `AttachmentRequest { sources, content_hash: content_hash.clone(), ... }` [2](#0-1) , but it is not consulted here.

The mismatch is only implicitly discovered much later: in `AttachmentsDownloader::run`, when the batch reaches `Done`, the code looks up `find_all_attachment_instances(&attachment.hash())` using the *actual* hash of whatever was received, not the originally requested hash [3](#0-2) . If the attacker's attachment hash does not match any pending instance, it simply resolves nothing and the requested attachment instance stays unresolved — but by then `bump_successful_requests()` has already inflated the peer's `ReliabilityReport` for that URL, and that inflated report persists in `self.reliability_reports` for use in future batches (rebuilt at stackslib/src/net/atlas/download.rs:115-124, and consulted when building `sources` for peer selection at lines 454-458).

This breaks the intended equality "successful_request_count == requests that returned the actually-committed hash," letting an attacker cheaply and repeatedly inflate its own reliability score by returning garbage/mismatched attachments on every request, causing the Atlas downloader to preferentially route future attachment-fetch attempts through that peer instead of genuinely reliable ones — resulting in repeated failed/incorrect attachment resolutions (attachment mismatch/DoS on the sync process).

### Impact Explanation
A malicious peer can manipulate the Atlas subsystem's internal peer-selection/reliability bookkeeping so that it appears more reliable than it is, biasing which peer is preferred as a data source for subsequent attachment downloads (`sources` map built from `self.peers` reports, stackslib/src/net/atlas/download.rs:454-458). Because the mismatch is never validated at credit time, this is trivially and repeatedly exploitable by any peer with an outbound-reachable P2P/data URL, degrading Atlas attachment sync reliability/availability (attachment-serving mismatch) — matching the "High: attachment/BNS mismatch" impact category.

### Likelihood Explanation
No privileged access is required — any remote peer that is selected as an outbound sync peer and advertises the attachment in its inventory can respond to `GET /attachments/{hash}` requests with any well-formed but wrong-content attachment payload. This requires only running a normal peer and answering attachment requests, which is inexpensive and fully repeatable across every attachment batch cycle.

### Recommendation
In `extend_with_attachments`, after `decode_atlas_get_attachment()` succeeds, verify `response.attachment.hash() == request.content_hash` before calling `report.bump_successful_requests()`; treat a hash mismatch the same as a failed request (`report.bump_failed_requests()`) and discard the attachment instead of inserting it into `self.attachments`.

### Proof of Concept
Add a Rust unit test in `stackslib/src/net/atlas/download.rs` (or `tests.rs`) that:
1. Constructs an `AttachmentsBatchStateContext` with one peer and a `ReliabilityReport::empty()`.
2. Builds a `BatchedRequestsResult<AttachmentRequest>` whose single `succeeded` entry pairs an `AttachmentRequest{ content_hash: H1, .. }` with a mocked `StacksHttpResponse` that decodes successfully via `decode_atlas_get_attachment()` into an `Attachment` whose content hashes to `H2 != H1`.
3. Calls `context.extend_with_attachments(&mut results)`.
4. Asserts `context.peers[&peer_url].successful_requests == 1` (or the returned score reflects a successful request) despite the served attachment's hash never matching the requested `content_hash`, demonstrating the reliability inflation described above.
