### Title
Missing bounds check on ELF symbol name offset causes slice-bounds panic in Go linker's `.o` reader - ([File: src/cmd/link/internal/loadelf/ldelf.go])

### Summary
`readelfsym` in the Go linker's ELF object-file loader reads a symbol's name offset (`b.Name`, a `uint32` taken directly from the untrusted `.o`/`.syso` file's symbol table) and slices the string table with it without validating that the offset is within `elfobj.symstr.base`. This mirrors the Pico `Elf::new()` bug class: an attacker-controlled offset field taken from a binary file is used to index into file-derived memory without a bounds/overflow check, and it is reachable purely by `go build`/`go link` processing a crafted host object file supplied as part of an ordinary build (e.g. a vendored `.syso` file or a cgo-produced `.o`).

### Finding Description
Attacker input: a crafted ELF relocatable object (`.o`/`.syso`) file included in a Go package (e.g. cgo `_ldflags`/`.syso` files are read directly by the linker without invoking a C compiler) is loaded by `Load()` in `cmd/link/internal/loadelf/ldelf.go`. During symbol resolution, `readelfsym` reads each `elf.Sym32`/`elf.Sym64` entry and immediately does: [1](#0-0) 
`elfsym.name = cstring(elfobj.symstr.base[b.Name:])` — `b.Name` is a raw `uint32` field taken from the symbol table entry and used directly as a slice start index into `elfobj.symstr.base` (the mapped `.strtab` section bytes). There is no check that `b.Name < len(elfobj.symstr.base)` before this slice expression is evaluated, unlike the index-bound check present a few lines earlier for `i` (`if i >= elfobj.nsymtab || i < 0 { ... }`) at [2](#0-1) . If `b.Name` exceeds the length of the mapped string-table slice, Go's runtime slice-bounds check will panic (`slice bounds out of range`), crashing the linker (and thus `go build`) mid-process. This is the same root cause pattern as the Pico bug: an attacker-supplied offset field, read straight from an untrusted binary structure, is used unchecked to index into file-derived data.

### Impact Explanation
A crafted `.syso`/host object file embedded in an otherwise ordinary Go module can cause `go build`/`go link` to panic when linking any package that includes it, denying a normal build for the victim developer. This does not achieve code execution or data disclosure — it is a reliable parser-crash (DoS at build time), which under Go's security policy for "plausible malicious-input parser panic" is a legitimate, if lower-severity, PUBLIC-track finding. It does not violate the "go build must not run malicious source" boundary since no code execution occurs — this is a memory-safety/availability bug in the linker's own parsing of untrusted binary input.

### Likelihood Explanation
The victim workflow is: a developer runs `go build`/`go install` on a package that bundles a host object file (`.syso`) or links against attacker-supplied `.o` files via cgo, as commonly done for prebuilt asset embedding on Windows (`.syso` autoloading) or vendored static objects. No special privileges are needed by the attacker beyond publishing such a file in a module the victim builds — matching the "ordinary user data / published module consumed by a normal victim workflow" premise.

### Recommendation
Add an explicit bounds check on `b.Name` before slicing, mirroring the existing index check for `i`:
```go
if uint64(b.Name) >= uint64(len(elfobj.symstr.base)) {
    return errorf("invalid symbol name offset")
}
elfsym.name = cstring(elfobj.symstr.base[b.Name:])
```
Apply the same guard to both the 64-bit and 32-bit branches.

### Proof of Concept
Because this bug lives in `cmd/link/internal/loadelf`, an internal, unexported package, a runnable `_test.go` PoC cannot be written from outside `cmd/link`; reproduction requires a background Devin agent with the full checkout and build tooling to construct a minimal `.o` file whose symbol table entry has `Name` set beyond the `.strtab` section length, then invoke `loadelf.Load` (or run `go build` on a package embedding such a crafted `.syso`) and assert that the process panics with `slice bounds out of range` rather than returning a clean "malformed elf file" error. I was unable to execute or verify this PoC within the current read-only environment — a full build/test environment is needed to confirm the panic reproduces exactly as analyzed.
