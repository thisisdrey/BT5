### Title
Missing size and hash validation of downloaded attachments allows unbounded storage growth via `insert_instantiated_attachment` - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` inserts a peer-supplied `Attachment` from a `GetAttachmentResponse` into `self.attachments` without checking its size against `atlas_config.attachments_max_size` or verifying its hash matches the requested `content_hash`. `AttachmentsDownloader::run` then calls `AtlasDB::insert_instantiated_attachment` directly on every drained attachment, never invoking `AtlasDB::should_keep_attachment`, so an oversized attachment gets written straight into the `attachments` SQLite BLOB column.

### Finding Description
The size bound is defined only in `AtlasDB::should_keep_attachment` (`content.len() as u32 > self.atlas_config.attachments_max_size` at [1](#0-0)  ), but that function is only used for locally-posted attachments (e.g., via the transaction/posttransaction path), not for attachments fetched from remote peers.

The remote-fetch path is: `AttachmentsBatchStateMachine::try_proceed` in the `DownloadingAttachment` state calls `context.extend_with_attachments(results)` [2](#0-1) , which for every successful HTTP response decodes it via `response.decode_atlas_get_attachment()` and does `self.attachments.insert(response.attachment)` [3](#0-2)  with no size check and no comparison of `attachment.hash()` against the `content_hash` that was actually requested.

`AttachmentsDownloader::run` then drains this set and, for each attachment, calls `network.atlasdb.insert_instantiated_attachment(&attachment)` directly [4](#0-3) , which unconditionally inserts `attachment.content` into the `attachments` table with no length check [5](#0-4) . `should_keep_attachment` is never called anywhere on this path.

The response format itself imposes no size limit: `GetAttachmentResponse` deserializes an arbitrary hex string into `Attachment::new(bytes)` with no length bound [6](#0-5) , and `decode_atlas_get_attachment` simply parses whatever JSON payload came back [7](#0-6) . I could not find a body-size cap specific to this endpoint's response body in the code explored (only generic HTTP/`MAX_PAYLOAD_LEN` framing in `stackslib/src/net/http/response.rs`, which was not fully inspected for its exact byte-length limit).

### Impact Explanation
A malicious peer (any outbound sync peer selected in `run`, reachable via P2P/RPC with no privileged role) that responds to an `AttachmentRequest` for a small `content_hash` with a `GetAttachmentResponse` containing an arbitrarily large `content` field can force the victim's `AtlasDB` to store that oversized blob in its SQLite `attachments` table, bypassing the intended `attachments_max_size` cap entirely. This is repeatable per `AttachmentInstance`/content hash the node is trying to resolve, allowing an attacker to inflate the target's `AtlasDB` storage far beyond the configured bound. This matches "unauthenticated/unauthorized write to state" - a remote, unauthenticated peer is able to write attacker-controlled, oversized data into persistent node state that the configured `attachments_max_size` was specifically meant to bound.

### Likelihood Explanation
The attacker only needs to run/control a node acting as an outbound sync peer for the target (no special role, secret, or StackerDB ownership required) and respond to legitimate `GetAttachment` requests issued by the target's `AttachmentsDownloader`. This is triggered whenever the target is resolving any `AttachmentInstance` (a routine, ongoing background process), so the precondition (target requesting an attachment) is common and attacker cost is a single crafted HTTP response.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments` (or in `AttachmentsDownloader::run` before calling `insert_instantiated_attachment`), validate that `response.attachment.content.len() as u32 <= atlas_config.attachments_max_size` and that `response.attachment.hash()` equals the `content_hash` of the corresponding `AttachmentRequest`/`AttachmentInstance`; discard and treat as a failed/faulty peer response otherwise. Alternatively, call `AtlasDB::should_keep_attachment` (extended to also check the hash) before invoking `insert_instantiated_attachment` on the download path.

### Proof of Concept
1. Set up two `PeerNetwork`/`AtlasDB` test instances similar to existing tests in `stackslib/src/net/atlas/tests.rs`, with `atlas_config.attachments_max_size` set to a small value (e.g., 1024 bytes).
2. Have the "server" peer respond to `/v2/attachments/<hash>` with a `GetAttachmentResponse` whose `attachment.content` is larger than `attachments_max_size` (e.g., 10 MB) and whose hash does NOT need to match the requested `content_hash`.
3. Drive `AttachmentsBatchStateContext::extend_with_attachments` with a `BatchedRequestsResult` containing this crafted response, then call `AttachmentsDownloader::run`.
4. Assert that `network.atlasdb.insert_instantiated_attachment` succeeds and that querying the `attachments` table for the given hash returns content whose length exceeds `atlas_config.attachments_max_size`, proving `should_keep_attachment`'s bound was never enforced on this path.

    pub fn insert_instantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let tx = self.tx_begin()?;
        tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)",
            params![attachment.hash(), attachment.content, now],
        )?;
        tx.execute(
            "UPDATE attachment_instances SET is_available = 1 WHERE content_hash = ?1 AND status = ?2",
            params![attachment.hash(), AttachmentInstanceStatus::Checked],
        )?;
        tx.commit()?;
        Ok(())
    }

    fn deserialize<D: serde::Deserializer<'de>>(d: D) -> Result<GetAttachmentResponse, D::Error> {
        let payload = String::deserialize(d)?;
        let hex_encoded = payload.parse::<String>().map_err(de_Error::custom)?;
