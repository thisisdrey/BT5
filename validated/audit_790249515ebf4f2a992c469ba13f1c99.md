## Analysis

The reported bug class—dividing before multiplying causes truncation/precision loss in a per-unit rate calculation—has a direct analog in `MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)`, which is on the reachable path of the unprivileged `WithdrawBalanceContract` transaction.

### Title
Division-before-multiplication in legacy vote reward calculation causes reward truncation - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Summary
`MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)` computes a voter's share of a Super Representative's per-cycle reward by first dividing `userVote` by `totalVote` into a `double`, then multiplying by `totalReward`, instead of multiplying first and dividing last. [1](#0-0) 

### Finding Description
```java
private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
  long reward = 0;
  for (Pair<byte[], Long> vote : votes) {
    ...
    long userVote = vote.getValue();
    double voteRate = (double) userVote / totalVote;
    reward += voteRate * totalReward;
  }
  return reward;
}
``` [2](#0-1) 

This is the exact division-before-multiplication pattern flagged in the external report: computing `userVote / totalVote` first (introducing a `double` rounding step) and only afterward multiplying by `totalReward`, instead of computing `userVote * totalReward / totalVote`. Because `voteRate` is a `double` with finite mantissa precision, the intermediate `userVote / totalVote` ratio is rounded before being scaled by `totalReward`, which for large `totalReward`/`totalVote` values amplifies the rounding error compared to performing the multiplication first.

This routine is invoked for every cycle in the legacy reward window via `getOldReward`: [3](#0-2) , which is itself called from `computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule)` for any cycle before `newAlgorithmCycle`: [4](#0-3) .

That method backs both `withdrawReward` and `queryReward`, which are called directly from the unprivileged, broadcastable `WithdrawBalanceContract` actuator: `mortgageService.withdrawReward(...)` in `execute()` and `mortgageService.queryReward(...)` in `validate()`. [5](#0-4) [6](#0-5) 

Any account holder with votes can broadcast a `WithdrawBalanceContract` transaction to trigger this calculation path for any past cycle prior to the new reward algorithm's effective cycle.

### Impact Explanation
Because the reward per voter is truncated via `double` division-then-multiplication instead of exact multiplication-then-division, users can receive a systematically lower reward than their proportional entitlement (`userVote/totalVote * totalReward`), especially when `totalVote` is large and `userVote` is comparatively small, causing the ratio to lose precision before scaling. Since the shortfall is not tracked or redistributed anywhere (it is simply not added to `reward`, and `delegationStore.addReward`/vote/account state do not retain the remainder), the truncated portion of the reward becomes permanently unclaimable — a permanent, low-magnitude loss of funds owed to legitimate voters, executed purely through a standard user-broadcast `WithdrawBalanceContract` transaction.

### Likelihood Explanation
This code path executes on every `WithdrawBalanceContract` transaction that includes at least one still-pending cycle prior to `NEW_REWARD_ALGORITHM_EFFECTIVE_CYCLE`, which is a legacy but still reachable state for withdrawals covering old cycles. It requires no special privileges — any account address holding votes and a pending cycle within the "old reward" window and calling `withdrawReward`/`queryReward` triggers it.

### Recommendation
Reorder the arithmetic in `computeReward(long cycle, List<Pair<byte[], Long>> votes)` to multiply before dividing, and use integer/`BigInteger` math rather than `double`, mirroring the exact/BigInteger approach already used for the new-algorithm reward calculation in the same class (`deltaVi.multiply(BigInteger.valueOf(userVote)).divide(DECIMAL_OF_VI_REWARD)`): [7](#0-6) . For example:
```java
long userVote = vote.getValue();
reward += BigInteger.valueOf(userVote).multiply(BigInteger.valueOf(totalReward))
    .divide(BigInteger.valueOf(totalVote)).longValue();
```

### Proof of Concept
Given `totalVote = 1_000_000_007` (large, non-power-of-2) and `totalReward = 999_999_999`, and a voter with `userVote = 3`:
- Correct value: `userVote * totalReward / totalVote` = `2999999997 / 1000000007` = `2` (floor).
- Current buggy path: `voteRate = (double)3 / 1000000007` ≈ `2.9999999790000002E-9`; `voteRate * 999999999` ≈ `2.9999999760000...` which truncates to `2` in this particular case, but for other ratios near integer boundaries the double rounding of the division step shifts the result by ±1 unit compared to the exact integer computation—repeated across many cycles and voters this compounds into a measurable, permanent underpayment of voter rewards, matching the precision-loss class in the referenced Sherlock finding.
