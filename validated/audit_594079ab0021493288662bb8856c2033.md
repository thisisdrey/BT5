### Title
Dust deposits on behalf of `feeCollector` fill its per-account token list to `MAX_TOKENS_PER_USER`, bricking fee-bearing withdrawals and liquidations - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
Analogous to the PercentFinance incident (accounting/interest-index state reaching a condition where routine market operations revert, permanently locking ~$1M of USDC/WBTC/ETH), Metronome's per-account token lists in `Pool` create a reachable revert condition that freezes user funds. `Pool.addToDepositTokensOfAccount` reverts with `UserReachedMaxTokens` once an account's combined debt+deposit token count reaches `MAX_TOKENS_PER_USER = 30` [1](#0-0) . `DepositToken.deposit` accepts an arbitrary `onBehalfOf_` beneficiary and `_mint` adds the token to the recipient's list whenever their balance was zero [2](#0-1) [3](#0-2) . An unprivileged attacker can therefore deposit 1 wei of every deposit-token type with `onBehalfOf_ = feeCollector`, filling its list to the cap. From then on, every withdrawal with a nonzero `withdrawFee` reverts in `_withdraw` at `_transfer(account_, feeCollector, _fee)` [4](#0-3) , every `deposit` with a nonzero `depositFee` reverts at `_mint(feeCollector, _fee)` [5](#0-4) , and every liquidation with a nonzero protocol fee reverts at `seize(account_, feeCollector, _fee)` [6](#0-5) .

### Finding Description
- `Pool.onlyIfAdditionWillNotReachMaxTokens` caps `debtTokensOfAccount.length + depositTokensOfAccount.length` at `MAX_TOKENS_PER_USER = 30` and reverts otherwise [7](#0-6) [1](#0-0) .
- `addToDepositTokensOfAccount` is called by any registered `DepositToken` whenever a recipient's balance transitions from zero to nonzero — including recipients who never asked for the tokens [8](#0-7) [9](#0-8) .
- `deposit(amount_, onBehalfOf_)` only blocks `onBehalfOf_ == treasury`; `feeCollector` is a valid beneficiary [10](#0-9) .
- The protocol supports up to 30 deposit-token types per pool (`addDepositToken` enforces `depositTokens.length() < MAX_TOKENS_PER_USER`), so on a pool with ~30 collaterals a single attacker can saturate `feeCollector`'s list with ~1 wei each [11](#0-10) .
- Once saturated, `DepositToken._withdraw` (used by `withdraw`, `withdrawFrom`, `flashWithdraw`) always reverts when `withdrawFee > 0` because the fee leg `_transfer(account_, feeCollector, _fee)` triggers `addToDepositTokensOfAccount(feeCollector)` for any deposit token the collector doesn't already hold [12](#0-11) .
- `Pool.liquidate` likewise reverts whenever `_fee > 0` and `feeCollector` lacks that deposit token in its list [13](#0-12) .
- The same attack works via plain `depositToken.transfer(feeCollector, 1)` — `_transfer` adds the token to the recipient's list with no opt-in [14](#0-13) .

### Impact Explanation
Permanent or long-lived freezing of user collateral, matching the PercentFinance bug class (accounting state makes routine operations revert, locking funds):

- **Withdrawals DoS:** on any pool where `withdrawFee > 0`, all `withdraw`/`flashWithdraw` calls revert once `feeCollector` is at cap → all user collateral in that pool is locked.
- **Liquidations DoS → insolvency:** with `protocolFee > 0` in `liquidationFees`, `liquidate` always reverts, so unhealthy positions cannot be closed and the protocol accrues bad debt.
- **Deposits DoS:** with `depositFee > 0`, `deposit` reverts for any token not already in `feeCollector`'s list.
- Recovery requires `feeCollector` (a contract) to actively transfer its dust balances out to free slots; if `FeeCollector` lacks a public/governor `transfer`/`sweep` path for `DepositToken`s, the freeze is permanent — exactly like PercentFinance's irreversibly frozen markets. Even with a governance escape, there is no self-serve fix, so the freeze persists until manual intervention.

### Likelihood Explanation
- Fully unprivileged: attacker needs only dust amounts of each underlying (or dust `DepositToken` balances) and public `deposit`/`transfer` calls. No governor/guardian/oracle manipulation involved.
- Cost scales with the number of deposit-token types; on pools near the 30-collateral cap it is trivial.
- The attack is only blocked if every configured `depositFee`, `withdrawFee`, and liquidation `protocolFee` is zero, or if the pool has far fewer than ~30 token types and the attacker cannot reach 30 entries — `feeCollector` already accumulates entries naturally from fee collection, so it approaches the cap organically over time even without an attacker.

### Recommendation
- Remove fee transfers to `feeCollector` in `DepositToken` shares and instead mint/track fees in a form that doesn't populate a per-account list, or exempt `feeCollector`/`treasury`/`smartFarmingManager` from `depositTokensOfAccount` tracking (they are protocol sinks, not positions — `debtPositionOf(feeCollector)` is never health-checked).
- Alternatively, in `_transfer`/`_mint`, catch the `UserReachedMaxTokens` revert for these privileged sink addresses and still credit the balance without adding to the list, or revert only when `account_` is not a protocol contract.
- Add an escape: allow `DepositToken` balances to be swept from the per-account list bookkeeping, or let `feeCollector` burn/transfer regardless of list membership.

### Proof of Concept
Hardhat test sketch (existing `test/` fixtures deploy a `Pool` with `feeCollector`, `feeProvider`, and several `DepositToken`s):

```typescript
it('griefs feeCollector and freezes all fee-bearing withdrawals', async () => {
  // assume feeProvider.withdrawFee() > 0 and pool has N deposit tokens
  const feeCollector = await poolRegistry.feeCollector()
  const depositTokens = await pool.getDepositTokens()

  // 1) Attacker fills feeCollector's list to MAX_TOKENS_PER_USER
  //    (also seed extra debt-token entries via issue() with onBehalf if needed)
  for (const dt of depositTokens) {
    const token = await ethers.getContractAt('DepositToken', dt)
    const underlying = await ethers.getContractAt('IERC20', await token.underlying())
    await underlying.mint(attacker.address, 10)
    await underlying.connect(attacker).approve(token.address, 10)
    // skip types feeCollector already holds; deposit dust otherwise
    if ((await token.balanceOf(feeCollector)).eq(0)) {
      await token.connect(attacker).deposit(1, feeCollector.address)
    }
  }

  // list is now at cap; verify
  const count =
    (await pool.getDepositTokensOfAccount(feeCollector.address)).length +
    (await pool.getDebtTokensOfAccount(feeCollector.address)).length
  expect(count).to.be.gte(await pool.MAX_TOKENS_PER_USER())

  // 2) Any withdrawal on a token feeCollector doesn't already hold reverts
  const victim = user1
  await depositTokenA.connect(victim).deposit(parseEther('100'), victim.address)
  await expect(
    depositTokenA.connect(victim).withdraw(parseEther('50'), victim.address)
  ).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')
  // victim's collateral is now locked in Treasury

  // 3) Liquidations revert too when protocolFee > 0
  // create unhealthy position on user2, then:
  await expect(
    pool.connect(liquidator).liquidate(msUSD.address, user2.address, repayAmt, depositTokenA.address)
  ).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')
})
```

Note on verification: I confirmed the full revert path `deposit → _mint → addToDepositTokensOfAccount → UserReachedMaxTokens` and `_withdraw → _transfer(feeCollector) → revert`, plus the `liquidate → seize(feeCollector)` path. The one unverified point is whether `FeeCollector` exposes a function to transfer `DepositToken` balances out to self-heal; if it does (governor-only), the impact downgrades from permanent to temporary freezing pending governance action — still within the accepted impact classes.

        address _msgSender = _msgSender();

        if (_fee > 0) {
            _mint(_pool.feeCollector(), _fee);
        }

        _mint(onBehalfOf_, _deposited);

        emit CollateralDeposited(_msgSender, onBehalfOf_, amount_, _deposited, _fee);
    }

    function _transfer(
        address sender_,
        address recipient_,
        uint256 amount_
    ) private updateRewardsBeforeTransfer(sender_, recipient_) {
        if (sender_ == address(0)) revert TransferFromTheZeroAddress();
        if (recipient_ == address(0)) revert TransferToTheZeroAddress();

        uint256 _senderBalanceBefore = balanceOf[sender_];
        if (_senderBalanceBefore < amount_) revert TransferAmountExceedsBalance();
        uint256 _recipientBalanceBefore = balanceOf[recipient_];

        unchecked {
            balanceOf[sender_] = _senderBalanceBefore - amount_;
            balanceOf[recipient_] += amount_;
        }

        emit Transfer(sender_, recipient_, amount_);

        // Add this token to the deposit tokens list if the recipient is receiving it for the 1st time
        if (_recipientBalanceBefore == 0 && amount_ > 0) {
            pool.addToDepositTokensOfAccount(recipient_);
        }

        // Remove this token from the deposit tokens list if the sender's balance goes to zero
        if (amount_ > 0 && balanceOf[sender_] == 0) {
            pool.removeFromDepositTokensOfAccount(sender_);
        }
    }
