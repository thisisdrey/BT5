## Title
Exchange (Bancor-style pool) inject and withdraw actuators lack slippage/minimum-output protection, unlike `ExchangeTransactionContract` - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`ExchangeInjectContract` and `ExchangeWithdrawContract` let an exchange creator add or remove liquidity from a TRX/TRC10 Bancor-style pool by specifying only the quantity of one token (`quant`). The counterpart amount of the other token (`anotherTokenQuant`) is derived purely from the pool's *current* balance ratio at execution time, and the transaction has no field allowing the signer to bound that counterpart amount. This is the exact analog of the reported Particle bug, where `amount0Min`/`amount1Min` were hardcoded to `0` in Uniswap `mint`/`increaseLiquidity`/`decreaseLiquidity` calls, exposing the caller to price-impact/frontrunning.

### Finding Description
`ExchangeInjectActuator.execute`/`doValidate` compute `anotherTokenQuant` strictly from the live pool ratio at execution time: [1](#0-0) 

There is no user-supplied minimum/maximum bound on `anotherTokenQuant` anywhere in `ExchangeInjectContract`; the protobuf only carries `exchange_id`, `token_id`, and `quant`. Similarly, `ExchangeWithdrawActuator.doValidate` computes the counterpart amount to be paid out purely from the pool ratio at execution: [2](#0-1) 

Compare this to `ExchangeTransactionContract`, which explicitly carries an `expected` field and is enforced by the actuator with a slippage check: [3](#0-2) 

The `expected` slippage-protection field exists at the protocol level for trades but is absent from `ExchangeInjectContract`/`ExchangeWithdrawContract`:


Because any unprivileged account can submit an `ExchangeTransactionContract` (a normal swap on the same pool) that shifts `firstTokenBalance`/`secondTokenBalance` right before the exchange creator's `ExchangeInject`/`ExchangeWithdraw` transaction lands in the same block, the pool ratio used to compute `anotherTokenQuant` can be manipulated between when the creator signs the transaction and when it executes — with no bound the creator can enforce on-chain.

### Impact Explanation
- On inject: the creator can be forced to deposit a much larger (or receive a much smaller effective share for) `anotherTokenQuant` than intended when they signed the transaction, since the ratio moved due to an interleaved swap.
- On withdraw: the creator can receive a significantly smaller `anotherTokenQuant` than expected for the same reason, directly losing value.
This matches the theft/permanent value-loss impact bar: an LP's committed funds can be extracted at an unfavorable, manipulated price with no on-chain guard, analogous to the Uniswap `amount0Min`/`amount1Min = 0` issue.

### Likelihood Explanation
Any account can submit a competing `ExchangeTransactionContract` against the same `exchange_id` to move the pool ratio, and same-block/adjacent ordering within a block (or simply natural trading activity racing the creator's pending tx) can achieve the same effect as MEV frontrunning of a Uniswap `mint`/`decreaseLiquidity` call. No special privilege is needed to submit the manipulating transaction; only the victim needs to be an exchange creator performing inject/withdraw, which is a normal, expected workflow for that role.

### Recommendation
Add an explicit min/max bound field to `ExchangeInjectContract` and `ExchangeWithdrawContract` protobuf messages (mirroring `ExchangeTransactionContract.expected`), and enforce it in `ExchangeInjectActuator`/`ExchangeWithdrawActuator` validate methods by comparing the computed `anotherTokenQuant` against the user-supplied bound, rejecting the transaction if outside tolerance — consistent with the pattern already used in `ExchangeTransactionActuator`.

### Proof of Concept
1. Attacker/any account observes a pending `ExchangeInjectContract` (or `ExchangeWithdrawContract`) from the exchange creator for `exchange_id` X with `token_id` = A, `quant` = Q.
2. Attacker submits an `ExchangeTransactionContract` on the same `exchange_id` X to swap a large amount, shifting `firstTokenBalance`/`secondTokenBalance` significantly.
3. If the attacker's transaction is included/executed before the creator's inject/withdraw (same block ordering or prior block), `ExchangeInjectActuator.execute`/`ExchangeWithdrawActuator.execute` computes `anotherTokenQuant` from the now-skewed ratio: [4](#0-3) 
4. The creator's inject deposits/receives a materially different `anotherTokenQuant` than intended when signing, with no on-chain field to have rejected the unfavorable outcome — unlike `ExchangeTransactionContract`, which would revert via `tokenExpected` check at: [3](#0-2)
