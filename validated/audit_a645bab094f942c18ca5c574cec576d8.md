### Title
Per-source QUIC stream throttle bypass via connection churn resets `ConnectionStreamCounter` - ([File: streamer/src/nonblocking/stream_throttle.rs], [File: streamer/src/nonblocking/quic.rs])

### Summary
The unstaked/staked stream throttle budget is tracked in a `ConnectionStreamCounter` that lives inside a `ConnectionTable` entry keyed by `(IP, pubkey)`; the counter is only reused across *concurrently open* connections from the same key, but is destroyed and recreated with `stream_count = 0` whenever all connections for that key are removed from the table. An attacker who closes and immediately reopens a QUIC connection therefore gets a fresh counter and resets the interval-based `throttle_stream` budget, allowing them to exceed the intended per-source stream rate as long as they can reconnect faster than throttling would otherwise allow.

### Finding Description
`throttle_stream` in `streamer/src/nonblocking/stream_throttle.rs` (lines 233-271) enforces a per-source cap by comparing `stream_counter.stream_count` against `max_streams_per_throttling_interval`, resetting the counter to 0 only when `STREAM_THROTTLING_INTERVAL` (100 ms) has elapsed, via `ConnectionStreamCounter::reset_throttling_params_if_needed` [1](#0-0) .

The `stream_counter` object itself, however, is not a durable per-IP structure independent of connection lifecycle. It is stored inside `ConnectionTable`'s per-key `connection_entry`, and `ConnectionTable::try_add_connection` decides whether to reuse the existing counter or manufacture a new one purely based on whether any connection for that key is still present in the entry list: [2](#0-1) 
If `connection_entry.first()` is `None` (i.e., the previous connection(s) for that IP/pubkey were fully removed via `remove_connection`), `stream_counter_factory` — `|| Arc::new(ConnectionStreamCounter::new())` in `SwQos::cache_new_connection` — is invoked, producing a brand-new counter with `stream_count = 0` [3](#0-2) .

Exploit flow:
1. Attacker opens a QUIC connection; `setup_connection` → `qos.try_add_connection` allocates a fresh `ConnectionStreamCounter` for that IP key [4](#0-3) .
2. Attacker opens streams up to just under `max_streams_per_throttling_interval - 1`, each going through `SwQos::on_new_stream` → `throttle_stream`, which does not yet trigger a sleep since the count is below cap [5](#0-4) .
3. Attacker closes the connection. `remove_connection` removes the entry for that key from the table, and once the last connection for that key is gone, the table no longer holds a reference keeping the counter "alive" for reuse.
4. Attacker reconnects (same IP) before `STREAM_THROTTLING_INTERVAL` elapses. `try_add_connection` sees an empty `connection_entry` for the key and calls the factory, producing a new `ConnectionStreamCounter` with `stream_count = 0`, regardless of wall-clock time since the previous window's reset.
5. Repeat — the per-100ms budget is reset by churn rather than by time, letting cumulative streams-per-second exceed the configured cap.

This bypasses the intended time-based enforcement because the enforcement state is coupled to connection-table membership rather than to IP identity with a lifecycle independent of connection open/close.

### Impact Explanation
This falls under QoS evasion: an unstaked source can extract more than its intended share of `QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS`/stream-throttling capacity by churning connections, at the expense of other unstaked peers sharing the aggregate unstaked stream budget (`available_load_capacity_in_throttling_duration` for `ConnectionPeerType::Unstaked` in `stream_throttle.rs`) [6](#0-5) . It does not cause a crash, panic, or consensus-affecting bug; the impact is scoped to unfair/above-budget resource consumption among unstaked senders on the QUIC ingress path.

### Likelihood Explanation
Feasibility depends entirely on the granted precondition that `ConnectionRateLimiter` (a per-IP token bucket in `connection_rate_limiter.rs`, consulted in `setup_connection`) allows the reconnect cadence [7](#0-6) . That limiter is the only real-world backstop against this churn, and it is deliberately excluded from consideration per the question's preconditions. Additionally, `max_connections_per_unstaked_peer` (often 1 by default) forces exactly this close/reopen pattern rather than preventing it, since only one open connection per unstaked IP is permitted at a time. Given the granted preconditions, the bypass is repeatable indefinitely without any additional privilege.

### Recommendation
Decouple the stream-throttle accounting from `ConnectionTable` connection-entry lifecycle. Track `ConnectionStreamCounter` (or equivalent token-bucket state) in a persistent per-IP (or per-pubkey) map with its own eviction/expiry policy independent of whether a live `Connection` currently exists for that key, similar to how `ConnectionRateLimiter` persists IP-keyed rate state via `KeyedRateLimiter` regardless of connection churn.

```rust
async fn test_stream_throttle_bypass_via_reconnect() {
    // start server with SwQosConfig::default_for_tests() (max_connections_per_unstaked_peer = 1)
    let max_streams = /* max_streams_per_throttling_interval for unstaked, from load_ema */;
    let mut total_streams_delivered = 0usize;
    let start = tokio::time::Instant::now();

    while start.elapsed() < STREAM_THROTTLING_INTERVAL {
        let client_connection = make_client_endpoint(&server_address, None).await;
        for i in 0..(max_streams - 1) {
            let mut s = client_connection.open_uni().await.unwrap();
            s.write_all(format!("{i}").as_bytes()).await.unwrap();
            s.finish().unwrap();
            total_streams_delivered += 1;
        }
        client_connection.close(0u32.into(), b"bye"); // triggers remove_connection
    }

    // Assert: total_streams_delivered within STREAM_THROTTLING_INTERVAL
    // exceeds max_streams (the intended per-window cap), demonstrating
    // the reset-via-reconnect bypass.
    assert!(total_streams_delivered > max_streams as usize);
}
```
Expected result on current code: assertion passes (streams delivered exceed the single-window cap), confirming the throttle is evadable via connection churn faster than `STREAM_THROTTLING_INTERVAL`.

```rust
        total_stake: u64,

        match peer_type {
            ConnectionPeerType::Unstaked => self.max_unstaked_load_in_throttling_window,

                } else {
                    self.max_staked_load_in_throttling_window
```
