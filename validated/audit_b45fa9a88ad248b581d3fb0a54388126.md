### Title
Unprivileged attacker can fill a victim's `depositTokensOfAccount` list via `deposit(..., onBehalfOf_)`, bricking the victim's ability to add collateral or take on debt - (File: contracts/DepositToken.sol)

### Summary
The GlusterFS CVE-2018-10914 class is "unprivileged request reaches an internal handler that aborts/bricks the service" — a remote denial of service. The Metronome analog: `DepositToken.deposit(amount_, onBehalfOf_)` lets any caller mint deposit-token balance to an arbitrary `onBehalfOf_` address. On a first mint, `DepositToken._mint` calls `Pool.addToDepositTokensOfAccount(account_)`, which reverts with `UserReachedMaxTokens` once the account holds `MAX_TOKENS_PER_USER = 30` distinct deposit/debt tokens. An attacker can cheaply deposit dust of every supported collateral `onBehalfOf` a victim until their list is full; afterwards every code path that would add a *new* token to the victim's list reverts.

### Finding Description
- `DepositToken.deposit` accepts any `onBehalfOf_` and calls `_mint(onBehalfOf_, _deposited)` — there is no opt-in by the beneficiary (`contracts/DepositToken.sol:211-237`).
- `_mint` calls `pool.addToDepositTokensOfAccount(account_)` whenever the recipient's balance goes 0 → >0 (`contracts/DepositToken.sol:486-488`). `_transfer` does the same for recipients (`contracts/DepositToken.sol:518-520`).
- `Pool.addToDepositTokensOfAccount` is guarded by `onlyIfAdditionWillNotReachMaxTokens`, which reverts once `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` (`contracts/Pool.sol:143-148`, `:216-220`). The same guard protects `addToDebtTokensOfAccount` (`contracts/Pool.sol:204-208`), called by `DebtToken` on first mint.

Attack trace (all unprivileged EOA calls):
1. For each deposit token listed in the pool (up to 30, `ReachedMaxDepositTokens` uses the same constant), attacker calls `depositToken.deposit(dustAmount, victim)`. Each call adds that token to `victim`'s `depositTokensOfAccount`.
2. Once the combined list length hits 30, the victim cannot: deposit into a collateral they don't already hold (`deposit` on behalf of themselves reverts inside `_mint`), receive any new deposit token by `transfer`/`transferFrom`/`seize` (reverts inside `_transfer`), or mint a debt token they don't already hold (`issue`/`mint` → first-mint `addToDebtTokensOfAccount` reverts).

### Impact Explanation
Temporary freezing of funds / liveness break: a victim whose position is approaching liquidation cannot top-up with a new collateral type — every deposit of a not-yet-held token reverts — so their position is force-liquidated and collateral is seized by liquidators, i.e. the DoS converts into loss of user funds (liquidation fee + seizure). It also blocks minting new debt tokens and receiving deposit tokens (e.g. seized collateral paid to a liquidator whose list is full reverts the whole `Pool.liquidate`). Recovery is only possible by fully withdrawing/repaying an existing position to free a slot, which is impossible for a victim whose unlocked balance is zero and who cannot add collateral. The invariant broken is liveness of deposit/borrow/liquidate paths for the griefed account.

### Likelihood Explanation
- Fully unprivileged: `deposit` is `whenNotPaused nonReentrant` with no beneficiary consent.
- Cost is only dust amounts of each underlying (lost to the treasury pull) plus gas; no tokens can be clawed back, but amounts can be minimal (`amount_ > 0` only).
- Attack is front-runnable at any time; the only mitigation is the victim already holding ≥1 of each needed token or freeing a slot first.
- Caveat: it is only exploitable while the pool has enough distinct deposit/debt tokens for the victim to reach 30, and the victim must not already be at the cap.

### Recommendation
- Do not add a token to `depositTokensOfAccount` when minting to `onBehalfOf_` differs from `_msgSender()` without beneficiary opt-in; alternatively make `deposit` mint only to `_msgSender()` and let users transfer explicitly.
- Alternatively, decouple the cap: track list membership lazily (derive from balances) or make `addToDepositTokensOfAccount` a no-op (skip, not revert) when the cap is reached so a forced dust deposit can't brick subsequent operations.
- If the list is needed for solvency loops (`depositOf`, `unlockedBalanceOf`), consider capping only self-initiated additions and documenting that forced entries are ignored for health computation.

### Proof of Concept
Hardhat sketch (fork or local fixtures as in `test/Pool.test.ts`):

```ts
// victim starts with an open position using 1 collateral (e.g. depositTokenA)
await depositTokenA.connect(victim).deposit(vAmount, victim.address);
// attacker fills remaining slots
const tokens = await pool.getDepositTokens(); // up to 30 entries
for (const t of tokens) {
  const dt = await ethers.getContractAt('DepositToken', t);
  const underlying = await ethers.getContractAt('ERC20', await dt.underlying());
  await underlying.connect(attacker).approve(dt.address, DUST);
  await dt.connect(attacker).deposit(DUST, victim.address); // onBehalfOf = victim
}
// list now == MAX_TOKENS_PER_USER
// victim tries to deposit a collateral they don't yet hold -> reverts
await expect(
  newDepositToken.connect(victim).deposit(vAmount, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
// victim also cannot mint a new debt token
await expect(
  newDebtToken.connect(victim).mint(...)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

This reproduces the remote-DoS invariant break end-to-end with only EOA calls.
