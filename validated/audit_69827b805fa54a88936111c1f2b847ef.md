### Title
Griefing attack can fill a victim's `MAX_TOKENS_PER_USER` slot list with dust deposit-token deposits, blocking the victim from adding new collateral or debt positions - (File: contracts/Pool.sol)

### Summary
`Pool.addToDepositTokensOfAccount` enforces a hard cap of `MAX_TOKENS_PER_USER = 30` combined deposit+debt tokens per account and reverts with `UserReachedMaxTokens`. Because `DepositToken.deposit(amount_, onBehalfOf_)` is permissionless and mints shares to an arbitrary `onBehalfOf_`, any unprivileged attacker can deposit dust of every deposit token in the pool on behalf of a victim, filling the victim's slot list and causing all future first-time deposits and new debt issuance for that account to revert. This mirrors the OpenQ report: an unprivileged caller weaponizes a token-address list limit via a permissionless funding path.

### Finding Description
- `Pool.sol` defines `MAX_TOKENS_PER_USER = 30` and the modifier `onlyIfAdditionWillNotReachMaxTokens`, which reverts when `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= 30` [1](#0-0) [2](#0-1) .
- `addToDepositTokensOfAccount(account_)` is guarded by that modifier and is callable only from a registered deposit token [3](#0-2) .
- `DepositToken.deposit` has no restriction on `onBehalfOf_` — anyone can deposit any nonzero amount and mint `msdTOKEN` to any address [4](#0-3) . `_mint` then calls `pool.addToDepositTokensOfAccount(account_)` when the recipient's balance was zero [5](#0-4) . `transfer`/`_transfer` achieves the same effect for an attacker who already holds shares [6](#0-5) .
- Once the list is full: `DepositToken._mint` reverts → victim cannot deposit any *new* collateral type; `DebtToken._mint` → `pool.addToDebtTokensOfAccount` reverts → victim cannot `issue` a *new* synthetic asset [7](#0-6) .
- Debt tokens cannot be pushed to the victim (`transfer`/`transferFrom` revert with `TransferNotSupported`, and `issue` mints debt only to `_msgSender`), so the attacker can only fill deposit-token slots [8](#0-7) . Feasibility therefore depends on the pool having enough registered deposit tokens (`ReachedMaxDepositTokens` caps the pool-level count; on deployments with many collaterals, e.g. mainnet msUSD pool, ≥30 minus the victim's existing entries is reachable).

### Impact Explanation
Temporary freezing of functionality/funds: the victim is blocked from opening positions in any collateral or synthetic asset not already in their list — including deposits urgently needed to avoid liquidation if their healthy collateral type differs from what they hold, and new debt issuance. Existing balances, withdrawals, repayments, and transfers still work, and the victim can self-recover by transferring/withdrawing the dust entries (balance → 0 triggers `removeFromDepositTokensOfAccount` [9](#0-8) ), so the freeze is temporary but costs the victim gas and can be re-applied by the attacker at dust cost.

### Likelihood Explanation
Attack cost is low: dust `deposit(1 wei-equivalent, victim)` per deposit token, permissionless, no privileged role, no flash loan needed. Limiting factor: the attacker can only occupy as many slots as there are registered deposit tokens in the pool, so on pools with few collaterals the victim's own existing entries must make up the remainder.

### Recommendation
Make `deposit` mint only to `msg.sender` (or remove `onBehalfOf_`), or exempt the slot-limit check when the deposit/mint is initiated by the account itself. Alternatively, allow entries to be force-removed or not count unsolicited dust balances below a threshold.

### Proof of Concept
Hardhat sketch (pool fixture with ≥ `MAX_TOKENS_PER_USER` registered deposit tokens):

```ts
// attacker fills victim's slot list with dust deposits
for (const depositToken of poolDepositTokens) {
  await underlying.mint(attacker.address, 1);
  await underlying.connect(attacker).approve(depositToken.address, 1);
  await depositToken.connect(attacker).deposit(1, victim.address); // adds token to victim's list
}
// victim's list is now full
expect(await pool.getDepositTokensOfAccount(victim.address)).to.have.length(30);
// victim can no longer deposit a new collateral type
await expect(newDepositToken.connect(victim).deposit(amount, victim.address))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens');
// nor mint a new synthetic asset
await expect(newDebtToken.connect(victim).issue(amount, victim.address))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

Uncertainty: the pool-level `ReachedMaxDepositTokens` cap value was not fully verified in this pass; if a given deployment registers fewer deposit tokens than `MAX_TOKENS_PER_USER`, the attacker can only partially fill the list and the attack requires the victim to already occupy the remaining slots.
