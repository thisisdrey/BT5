## Finding

`ActuatorFactory.getActuatorByContract` in `actuator/src/main/java/org/tron/core/actuator/ActuatorFactory.java` performs an unchecked `TransactionFactory.getActuator(contract.getType())` lookup and immediately calls `.newInstance()` on the result without a null check, unlike its sibling dispatcher `ActuatorCreator.getActuatorByContract` which explicitly guards against `clazz == null`. [1](#0-0) 

Compare this to the safe pattern used elsewhere in the same dispatch role: [2](#0-1) 

`TransactionFactory.getActuator` is a simple map lookup that returns `null` for any `ContractType` that has no registered `Actuator` subclass: [3](#0-2) 

Registration only happens for `ContractType` values that have a corresponding concrete `AbstractActuator` subclass discovered by reflection at startup: [4](#0-3) 

Because `Transaction.Contract.getType()` is a protobuf enum field controlled entirely by the caller-supplied bytes, an attacker can submit a transaction whose `Contract.type` field is set to any `ContractType` enum value that exists in `Tron.proto` but has no actuator implemented in this build (e.g., a reserved/legacy/not-yet-implemented contract type). `TransactionFactory.getActuator()` then returns `null`, and `ActuatorFactory.getActuatorByContract` dereferences it with `clazz.newInstance()`, throwing an unguarded `NullPointerException`. The surrounding `forEach` in `createActuator` only catches `IllegalAccessException | InstantiationException`, so the `NullPointerException` propagates uncaught out of `ActuatorFactory.createActuator`: [5](#0-4) 

This mirrors the CVE-2026-48139 bug class exactly: a dispatch/moniker-style service maps an attacker-controlled discriminator value to a handler, and an "unknown" (unmapped) value causes a null pointer dereference instead of a graceful error, because a null-check present elsewhere in the codebase's equivalent dispatcher was omitted here.

**Caveat / uncertainty:** I could not conclusively confirm, within the available tool budget, that `ActuatorFactory.createActuator` (the unsafe path) is actually invoked from a live, unauthenticated-reachable call site in `Wallet.java` (as opposed to `ActuatorCreator`/`RuntimeImpl`, which are the confirmed live dispatch paths for transaction execution and which correctly null-check). `grep` confirmed 3 references to `ActuatorFactory` in `framework/src/main/java/org/tron/core/Wallet.java`, but I was not able to retrieve those exact call sites before running out of iterations. If `ActuatorFactory.createActuator` turns out to be dead/unused code in `Wallet.java`, this finding would not be reachable from an unprivileged transaction and should be discounted. A Devin session with file access would be needed to confirm the exact call site and the enclosing exception handling (or lack thereof) at that site.

### Title
Unguarded null-pointer dereference in `ActuatorFactory.getActuatorByContract` on unmapped `ContractType` - (File: `actuator/src/main/java/org/tron/core/actuator/ActuatorFactory.java`)

### Summary
`ActuatorFactory.getActuatorByContract` looks up an `Actuator` class for a transaction's `ContractType` via `TransactionFactory.getActuator()`, which can return `null` for any enum value lacking a registered actuator, then calls `.newInstance()` on the null result without checking, unlike the equivalent `ActuatorCreator` dispatcher which explicitly guards this case.

### Finding Description
`Transaction.Contract.getType()` is fully attacker-controlled (any valid `ContractType` protobuf enum value can be placed in a signed/unsigned transaction submitted to the node). `TransactionFactory.getActuator(type)` is a bare `Map.get()` that returns `null` when no actuator has registered for that `ContractType` [3](#0-2) . `ActuatorFactory.getActuatorByContract` immediately dereferences this potentially-null `Class` object via `clazz.newInstance()` with no null check [1](#0-0) , whereas the parallel `ActuatorCreator.getActuatorByContract` throws a handled `ContractValidateException` instead [2](#0-1) . The enclosing `forEach` in `ActuatorFactory.createActuator` only catches `IllegalAccessException | InstantiationException`, letting the resulting `NullPointerException` propagate uncaught [5](#0-4) .

### Impact Explanation
If this dispatcher is reachable from an externally-submitted transaction (broadcast or query path), an uncaught `NullPointerException` would abort the transaction-processing call on whichever thread invokes it. Depending on the calling context this could cause a query/API worker thread to fail unhandled, or, if invoked on a block-processing/critical path, could destabilize transaction validation, matching the "node crash / API the node can no longer serve" bar for a Medium-severity DoS analog of CVE-2026-48139.

### Likelihood Explanation
Exploitation only requires constructing a `Transaction.Contract` with a `ContractType` enum value that has no corresponding registered `AbstractActuator` subclass in this build (e.g., an enum value defined in `Tron.proto` but not yet implemented) and routing it through the `ActuatorFactory` dispatch path — no special privileges are required, matching "an attacker provides an unknown value to trigger a NULL pointer dereference" from the source report.

### Recommendation
Add the same null-guard used in `ActuatorCreator.getActuatorByContract` to `ActuatorFactory.getActuatorByContract`: check `clazz == null` before calling `newInstance()` and raise a handled exception (e.g., `ContractValidateException`) instead of allowing an `NullPointerException` to propagate; also broaden the `catch` in `createActuator`'s `forEach` to handle unexpected `RuntimeException`s defensively.

### Proof of Concept
1. Identify (or add for a test) a `ContractType` enum value in `Tron.proto` with no corresponding concrete `AbstractActuator` subclass registered via `TransactionRegister.registerActuator()`.
2. Construct a `Transaction` whose `Contract.type` is set to that unmapped value and route it to whichever call site in `Wallet.java` invokes `ActuatorFactory.createActuator(...)` (call site not fully confirmed — requires direct code inspection).
3. Observe an uncaught `NullPointerException` thrown from `ActuatorFactory.getActuatorByContract`'s `clazz.newInstance()` call, since `clazz` is `null` and only `IllegalAccessException | InstantiationException` are caught upstream.

  public static void registerActuator() {
    if (REGISTERED.get()) {
      logger.debug("Actuator already registered.");
      return;
    }

    synchronized (TransactionRegister.class) {
      if (REGISTERED.get()) {
        logger.debug("Actuator already registered.");
        return;
      }
      logger.debug("Register actuator start.");
      Reflections reflections = new Reflections(PACKAGE_NAME);
      Set<Class<? extends AbstractActuator>> subTypes = reflections
          .getSubTypesOf(AbstractActuator.class).stream()
          .filter(c -> !Modifier.isAbstract(c.getModifiers()))
          .collect(Collectors.toSet());

      for (Class<? extends AbstractActuator>  clazz : subTypes) {
        try {
          logger.debug("Registering actuator: {} start", clazz.getName());
          clazz.getDeclaredConstructor().newInstance();
          logger.debug("Registering actuator: {} done", clazz.getName());
        } catch (Exception e) {
          Throwable cause = e.getCause() != null ? e.getCause() : e;
          String detail = cause.getMessage() != null ? cause.getMessage() : cause.toString();
          throw new TronError(clazz.getName() + ": " + detail,
              e, TronError.ErrCode.ACTUATOR_REGISTER);
        }
      }

      REGISTERED.set(true);
      logger.debug("Register actuator done, total {}.", subTypes.size());
    }
  }
