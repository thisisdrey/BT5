### Title
Stale postponed receipts / received-data survive `DeleteAccount`, letting a dangling self-callback execute with self-authority against a freshly re-created account of the same name - ([File: runtime/runtime/src/actions.rs] / [File: core/store/src/utils/mod.rs] / [File: runtime/runtime/src/lib.rs])

### Summary
`remove_account` only deletes the `Account`, `ContractCode`, `AccessKey`/`GasKeyNonce`, and `ContractData` trie rows for a deleted account; it never touches the `ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, or `PostponedReceipt` rows, which are keyed purely by the account-id string. Because `process_action_receipt`/`process_receipt` in `runtime/runtime/src/lib.rs` also key strictly on the account-id string with no incarnation/versioning, a self-callback `ActionReceipt` postponed before an account deletes itself can still be triggered later by a matching `Data` receipt, and will then execute against whatever account currently occupies that name.

### Finding Description
`remove_account` (`core/store/src/utils/mod.rs:504-575`) removes `TrieKey::Account`, `TrieKey::ContractCode`, all `AccessKey`/`GasKeyNonce` entries, and `ContractData` for `account_id`, but has no logic touching `TrieKey::ReceivedData`, `TrieKey::PostponedReceiptId`, `TrieKey::PendingDataCount`, or `TrieKey::PostponedReceipt` [1](#0-0) . These four namespaces are keyed only by `receiver_id`/`account_id` strings and a `receipt_id`/`data_id` hash [2](#0-1) , i.e. by the account *name*, not by any incarnation counter.

`action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) checks storage-usage size and gas-key-balance limits, refunds the balance, and calls `remove_account`, but performs no check for outstanding `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` entries still awaiting data for that account [3](#0-2) .

When a self-callback `ActionReceipt` (created earlier by the account itself, e.g. as the continuation of a cross-contract promise chain, so `predecessor_id == receiver_id == B`) has unmet `input_data_ids`, `process_action_receipt` stores it as a `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` keyed by `B` regardless of whether `B` will still exist when the data arrives [4](#0-3) . Later, when the corresponding `Data` receipt (whose sender/content is fully controlled by an attacker-owned account C) arrives, `process_receipt` looks up `PostponedReceiptId`/`PendingDataCount`/`PostponedReceipt` purely by the account-id string `B`, and once the counter reaches zero it fetches and executes the stored `ready_receipt` via `apply_action_receipt` [5](#0-4) . `apply_action_receipt` only checks *current* account existence for each action (`check_account_existence`), not whether the account is the same incarnation that existed when the receipt was created [6](#0-5) . Because the receipt's `predecessor_id` was fixed at creation time to `B`, and `receiver_id` is again `B` (the same name, now owned by someone else), the action set (which can include `AddKey`, `DeployContract`, `Transfer`, `DeleteKey`, `Stake`, etc.) runs with the same-account/self trust model that action receipts rely on, without any access-key signature from the new owner of `B`.

The repository's own test `test_function_call_after_same_chunk_delete_recreate_resolves_fresh_code` demonstrates that the maintainers are aware that delete+recreate within the same name can interact badly with in-flight receipts (there it's about `ReceiptPreparationPipeline` code resolution, fixed by blocking pipelining for accounts touched by `CreateAccount`/`DeleteAccount` in the same chunk) [7](#0-6) [8](#0-7) , but that mitigation is scoped to same-chunk pipelining and does not address the cross-chunk/cross-shard postponed-receipt and received-data leakage described here, since those trie namespaces are never purged by `remove_account`.

### Impact Explanation
This is an authorization-escalation primitive: actions authored by the *old* owner of an account name execute with self-account authority against the account currently held by a *different, unaware* owner who simply re-registered a previously-used name, with no signature check tying the execution to the new owner's keys. Depending on the queued actions, this can be used to add an attacker-controlled access key, redeploy a malicious contract, or move balance out of the new account — i.e. authorization escalation across accounts, matching the "Authorization escalation across accounts or promises" bounty category.

### Likelihood Explanation
Preconditions are attacker-reachable with only ordinary transaction capabilities: the attacker needs to (1) own account `B` (or a subaccount they control) and construct a self-callback `ActionReceipt` with unmet `input_data_ids` sourced from a second attacker-controlled account `C`, (2) satisfy `DeleteAccount`'s own constraints (zero locked stake, `storage_usage <= MAX_ACCOUNT_DELETION_STORAGE_USAGE`, gas-key balance under threshold) to delete `B` while the postponed receipt is still pending, and (3) get a third party (or itself) to re-create account `B` before releasing the pending `Data` receipt from `C`. Steps (1)-(2) are fully within an unprivileged attacker's control; step (3) depends on someone else re-registering the exact abandoned name (feasible for short/desirable top-level names or attacker-controlled subaccounts the attacker later hands off), and on the attacker being able to delay/time the release of the `Data` receipt from `C`, which it fully controls as sender. The attack is repeatable and does not require validator, node, or protocol-level privileges.

### Recommendation
Purge `ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, and `PostponedReceipt` (and `PromiseYieldReceipt`/`PromiseYieldStatus`/yield-id mappings) for `account_id` inside `remove_account` (or in `action_delete_account` before calling it), or alternatively reject `DeleteAccount` while any such pending entries exist for the account, so a deleted account cannot leave dangling receipt-matching state that a subsequently re-created account of the same name can inherit.

### Proof of Concept
TestLoop / integration test plan:
1. Deploy a contract to account `B` (attacker-controlled) that, on call, issues a promise to account `C` (attacker-controlled) and schedules a self-callback (`then`) on `B` with a malicious action list (e.g. `AddKey(attacker_pubkey, FullAccess)`), producing a postponed `ActionReceipt` with `predecessor_id == receiver_id == B` stored under `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId`.
2. Before `C` responds, submit a `DeleteAccount` transaction from `B` to a beneficiary, deleting `B` (ensure zero locked stake / storage usage under the cap).
3. In a following chunk, have a different signer create account `B` again (`CreateAccount` + `AddFullAccessKey` with the new owner's key), simulating an unrelated party reclaiming the name.
4. Deliver the delayed `Data` receipt from `C` targeting `B`.
5. Assert that the callback executes (`AddKey` action succeeds) against the newly created `B`, and that this key was never authorized by the new owner — i.e., assert no `PostponedReceipt`/`ReceivedData`/`PendingDataCount` rows survive account deletion, and that cross-incarnation execution does not occur.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
