Looking at the two key functions and the authorization check:

The code path is fully traceable. Here is the complete analysis:

**Tracing the authorization gap:**

`create_fixed_collection_as_owner` sets `Collection.creator = signer::address_of(creator)` at construction time and never updates it on transfer. [1](#0-0) 

After `object::transfer(creator, collection, trader_address)`, `collection.owner() == trader` but `Collection.creator` is permanently frozen at the original creator's address. [2](#0-1) 

`create_token` / `create_named_token_object` / `create_numbered_token_object` all route through `create_common_with_collection`, whose sole guard is:

```move
assert!(collection::creator(collection) == signer::address_of(creator), error::unauthenticated(ENOT_CREATOR));
``` [3](#0-2) 

Because `Collection.creator` is never mutated, this assertion passes for the original creator forever, regardless of who currently owns the collection object.

The owner-based guard (`collection.owner() == signer::address_of(owner)`) only exists in `create_common_with_collection_as_owner`, which is a completely separate code path used only by `create_token_as_collection_owner` and its siblings. [4](#0-3) 

**What the existing tests cover vs. what they miss:**

The test `test_create_token_after_transferring_collection` correctly verifies that `create_token_as_collection_owner` aborts after transfer. But there is no test verifying that the legacy `create_token` / `create_named_token_object` path also aborts after transfer — because it does not abort. [5](#0-4) 

**Stated invariant that is broken:**

The `create_fixed_collection_as_owner` / `create_unlimited_collection_as_owner` docstrings explicitly state: *"This transfers ownership and minting permissions to the new address."* [6](#0-5) [7](#0-6) 

The code does not enforce this. The original creator retains minting capability via the creator-based path indefinitely.

### Title
Original collection creator retains unauthorized minting capability after transferring a collection via `create_fixed_collection_as_owner` — (`aptos-move/framework/aptos-token-objects/sources/token.move`)

### Summary
When a collection is created with `create_fixed_collection_as_owner` and transferred to a new owner, the original creator can still successfully call `create_token`, `create_named_token_object`, `create_numbered_token_object`, and their `_from_seed` variants. The `Collection.creator` field is set at construction and never updated on object transfer, so the creator-based authorization check at `token.move:161` permanently passes for the original creator. This contradicts the documented invariant that transfer moves minting permissions to the new owner.

### Finding Description
`create_fixed_collection_as_owner` (and `create_unlimited_collection_as_owner`) enable ungated transfer of the collection object so that ownership — and per the documented contract, minting rights — can be sold or delegated. After transfer, the new owner uses `create_token_as_collection_owner` (which checks `collection.owner()`), while the original creator is supposed to lose minting access.

However, the legacy public entry points `create_token`, `create_named_token_object`, `create_numbered_token_object`, and `create_named_token_from_seed` all call `create_common_with_collection`, which checks only `collection::creator(collection) == signer::address_of(creator)`. This reads `Collection.creator`, a field that is written once at construction and has no setter. No code path in `collection.move` or `token.move` updates `Collection.creator` on `object::transfer`. Therefore the original creator passes this check forever.

The result is that two independent signers can simultaneously mint into the same collection: the new owner via `create_token_as_collection_owner`, and the original creator via `create_token`. For a `FixedSupply` / `ConcurrentSupply` collection the original creator can exhaust the entire remaining supply without the new owner's knowledge or consent.

### Impact Explanation
- **Unauthorized minting of token objects**: The original creator mints tokens into a collection they no longer own, incrementing the collection's supply counter and consuming supply slots.
- **Supply exhaustion**: For a fixed-supply collection the original creator can fill all remaining supply slots, permanently preventing the new owner from minting any further tokens.
- **Invariant violation**: The documented guarantee that `create_fixed_collection_as_owner` transfers minting permissions is broken; buyers of such collections receive an asset whose minting rights are not exclusively theirs.

### Likelihood Explanation
Any user who purchases or receives a collection created via `create_fixed_collection_as_owner` is affected. The original creator needs only to call the standard public `create_token` function with the collection object — no privileged access, no governance power, no validator control required. The attack is a single unprivileged transaction.

### Recommendation
In `create_common_with_collection`, add a branch: if the collection was created with the owner model (i.e., ungated transfer is enabled / `collection_owner` feature is active for this collection), reject the creator-based path and require the caller to use `create_common_with_collection_as_owner` instead. Alternatively, when `create_fixed_collection_as_owner` is called, store a flag in the collection resource indicating that only owner-based minting is permitted, and assert that flag is absent inside `create_common_with_collection`.

fun poc_original_creator_mints_after_transfer(
    creator: &signer,

    aptos_framework: &signer,

    features::change_feature_flags_for_testing(
        aptos_framework,
        vector[features::get_collection_owner_feature()],
        vector[],
    );

    // 1. Creator creates a transferable fixed collection (max 5 tokens).
    let constructor_ref = collection::create_fixed_collection_as_owner(

        string::utf8(b"desc"),
        5,
        string::utf8(b"MyCollection"),
        option::none(),
        string::utf8(b"uri"),
    );
    let collection = object::object_from_constructor_ref<collection::Collection>(&constructor_ref);

    // 2. Creator transfers the collection to trader.

        creator,
        collection,
        string::utf8(b"token desc"),
        string::utf8(b"token name"),
        option::none(),
        string::utf8(b"uri"),
    );
    // Reaches here — unauthorized mint succeeded.
}
