## Finding

### Title
`eth_getTransactionReceipt` always reports `cumulativeGasUsed` as zero instead of the actual accumulated gas - (File: `substrate/frame/revive/rpc/src/receipt_extractor.rs`)

### Summary
This is the direct local analog of the reported Artela bug ("`gasUsed` field of a transaction receipt is populated with the wrong value instead of the actually consumed amount"). In `pallet-revive`'s Ethereum-compatibility RPC layer, `ReceiptExtractor::decode_transaction_and_build_receipt` correctly sets `gas_used` from the on-chain `ReceiptGasInfoV1` (this exact bug was already fixed for the per-tx `gas_used` field in `prdoc/stable2512/pr_10148.prdoc`), but the sibling field `cumulative_gas_used` — required by the Ethereum JSON-RPC spec to equal "the sum of gas used by this transaction and all preceding transactions in the same block" — is never populated and is silently left at its `Default::default()` value of `0` for every transaction in every block.

### Finding Description
`ReceiptInfo` declares `cumulative_gas_used: U256` with doc comment describing the expected semantics: [1](#0-0) 

`ReceiptInfo::new` — the only constructor used when building receipts from decoded extrinsics — does not take a `cumulative_gas_used` argument at all, and relies on `..Default::default()` to fill in the remaining fields, which sets `cumulative_gas_used` to zero: [2](#0-1) 

`ReceiptExtractor::decode_transaction_and_build_receipt` builds the receipt purely from the single transaction's `receipt_gas_info.gas_used` and never threads in any running total across the transactions decoded for the same block in `extract_from_block_with_eth_hash`: [3](#0-2) 

The block-level extraction function iterates every extrinsic in the block (`eth_tx_by_index`) but only forwards `receipt_gas_info` per-transaction, with no accumulator maintained across the loop that could be used to compute `cumulative_gas_used`: [4](#0-3) 

By contrast, the runtime-side canonical Ethereum block builder (`EthereumBlockBuilder::process_transaction`) does correctly accumulate gas across transactions for the block header's `gas_used` field via `self.gas_used = self.gas_used.saturating_add(receipt_gas_info.gas_used)`: [5](#0-4) 

That accumulated value is only exposed at the *block* level (`Block::gas_used` in `header_hash`), not surfaced back into the per-transaction `ReceiptInfo.cumulative_gas_used` field returned by the RPC layer's `eth_getTransactionReceipt`/`eth_getTransactionByBlock*` handlers.

### Impact Explanation
Every `ReceiptInfo` served by `pallet-revive`'s Ethereum RPC (`eth_getTransactionReceipt`, `eth_getBlockReceipts`, etc.) reports `cumulativeGasUsed: "0x0"` regardless of position in the block or actual accumulated gas. This is a real deviation from the documented Ethereum JSON-RPC contract and corrupts a field that downstream tooling (block explorers, bridge/oracle relayers computing block gas utilization, gas-refund/fee-history logic, and any contract-verification or reimbursement tooling that trusts `cumulativeGasUsed`) may depend on for correctness. It does not directly enable fund theft or double-settlement on its own, but it is squarely the same bug class as the seed report: an RPC-served receipt field silently populated with an incorrect (here, always-zero) value instead of the true derived amount, undermining "intended behavior" guarantees of the transaction-receipt interface.

### Likelihood Explanation
This triggers on every single Ethereum-compatible transaction processed through `pallet-revive`'s RPC layer — no privileged actor, malicious peer, or special condition is required. Any unprivileged user who queries a receipt for a transaction that is not the first in its block will observe an incorrect `cumulativeGasUsed`.

### Recommendation
Maintain a running gas accumulator while iterating `eth_tx_by_index` in `extract_from_block_with_eth_hash` (mirroring the runtime's `EthereumBlockBuilder::process_transaction` accumulation logic), pass the accumulated value into `decode_transaction_and_build_receipt`, and set `ReceiptInfo.cumulative_gas_used` accordingly instead of relying on `ReceiptInfo::new`'s `Default::default()` fallback.

### Proof of Concept
1. Submit two or more Ethereum-encoded transactions (`eth_call`/`eth_instantiate_with_code`) into the same block.
2. Call `eth_getTransactionReceipt` for the second (or later) transaction.
3. Observe `cumulativeGasUsed` is `"0x0"` in the JSON response, even though the transaction's `gasUsed` and any preceding transaction's `gasUsed` in the same block are non-zero — confirmed by tracing through `ReceiptInfo::new` (no `cumulative_gas_used` param, defaults to zero) and `decode_transaction_and_build_receipt`/`extract_from_block_with_eth_hash` (no per-block gas accumulator ever computed or passed in).
