### Title
Unbounded `Vec::with_capacity` allocation from attacker-controlled `u32` length in `CheckedData::consensus_decode` reachable via `recv_message` - (File: stacks-common/src/deps_common/bitcoin/network/encodable.rs)

### Summary
`CheckedData::consensus_decode` reads a `u32` length prefix straight off the wire and calls `Vec::with_capacity(len as usize)` before reading any payload bytes, with no cap comparable to `MAX_VEC_SIZE` used elsewhere in the same file. Since `BitcoinIndexer::recv_message` (`stackslib/src/burnchains/bitcoin/network.rs`) decodes `RawNetworkMessage` — whose payload field is exactly a `CheckedData` — a malicious Bitcoin peer can send a message with a length field up to `0xFFFFFFFF` (~4 GiB) and force the node's Bitcoin-indexer thread to attempt a multi-gigabyte allocation before any checksum or content is validated.

### Finding Description
The equality the question asks about — "bytes read for the payload field == a bounded, sane length" — is broken specifically at the allocation step, not merely the read loop. `CheckedData::consensus_decode` does:
```
let len: u32 = ConsensusDecodable::consensus_decode(d)?;
let checksum: [u8; 4] = ConsensusDecodable::consensus_decode(d)?;
let mut ret = Vec::with_capacity(len as usize);
for _ in 0..len { ret.push(ConsensusDecodable::consensus_decode(d)?); }
``` [1](#0-0) 
There is no `MAX_VEC_SIZE` check here, unlike the sibling `Vec<T>` and `Box<[T]>` decoders in the very same file which explicitly bound allocation to 64 MiB before allocating: [4](#0-3) 

`RawNetworkMessage::consensus_decode` (the type decoded by `recv_message`) reads `magic`, `CommandString`, then this unbounded `CheckedData` before ever inspecting the command or byte content: [2](#0-1) 

`recv_message` performs no independent length check before or after this call — the check for magic bytes happens only after the full decode returns: [5](#0-4) 

The attacker's exact message: 4 bytes magic (must match network — public value, e.g. mainnet `0xd9b4bef9`/testnet magic which is not secret), a 12-byte `CommandString`, then a `u32` length field set to `0xFFFFFFFF`, a 4-byte checksum, and then as many bytes as the attacker cares to actually send (the allocation happens before all those bytes are received). `Vec::with_capacity(0xFFFFFFFF)` (~4 GiB) is attempted immediately, independent of whether the peer ever sends that much data.

Note: the magic-bytes check happens only after the whole `RawNetworkMessage` is decoded, so it cannot prevent the oversized allocation attempt — decoding, including the vulnerable allocation, occurs before the magic is checked.

### Impact Explanation
This is remotely triggerable by any peer that can complete (or is mid-way through) a TCP connection to the node's Bitcoin peer connection used by `BitcoinIndexer` — no handshake, authentication, or secret is required since this code path is used during `peer_handshake`/`recv_message` itself (called from `connect_handshake_backoff` → `peer_handshake` → `recv_message`, see `stackslib/src/burnchains/bitcoin/network.rs` lines 149-166), i.e., it fires on the very first messages exchanged with the burnchain peer. A single crafted message forces a multi-gigabyte allocation attempt on the indexer's sync thread, which can exhaust memory or effectively hang the process (allocator stalls or OOM), denying burnchain sync to the node — a Critical, remotely reachable, unauthenticated DoS from a single/few messages, repeatable on every reconnect attempt.

### Likelihood Explanation
No special peer/config/tip state is required beyond the node connecting outbound to (or accepting inbound from, depending on deployment) a Bitcoin-protocol peer that the attacker controls. The magic value is public/well-known per network, not secret. Attacker cost is a handful of bytes; the vulnerability is trivially repeatable on every connection attempt, matching a low-cost, high-impact Critical DoS.

### Recommendation
In `stacks-common/src/deps_common/bitcoin/network/encodable.rs`, add the same `MAX_VEC_SIZE` (or a smaller Bitcoin-message-appropriate bound, e.g. 32 MiB matching Bitcoin Core's `MAX_SIZE`) check to `CheckedData::consensus_decode` before calling `Vec::with_capacity(len as usize)`, mirroring the existing check in `Vec<T>::consensus_decode`/`Box<[T]>::consensus_decode` in the same file.

    #[inline]
    fn consensus_decode(d: &mut D) -> Result<CheckedData, serialize::Error> {
        let len: u32 = ConsensusDecodable::consensus_decode(d)?;
        let checksum: [u8; 4] = ConsensusDecodable::consensus_decode(d)?;
        let mut ret = Vec::with_capacity(len as usize);

            Err(serialize::Error::InvalidChecksum {
                expected: expected_checksum,
                actual: checksum,
            })
        } else {
            Ok(CheckedData(ret))
        }
