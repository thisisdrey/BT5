### Title
`simulate_intents` omits the refund-log-size check that `execute_intents` enforces, so a batch reported as succeeding can panic on real execution - (File: `contracts/defuse/src/contract/intents/mod.rs`)

### Summary
The bug class from the external report is that ERC-4626 "preview"/"max" view functions returned values that did not match what the real state-mutating functions would actually allow, causing the real call to revert even though the view function said it would succeed. The direct analog in this NEAR intents system is the relationship between the view method `simulate_intents` and the state-mutating method `execute_intents`: the rules for this scan explicitly call out "`simulate_intents` diverging from `execute_intents`" as a valid High-impact finding, and that divergence is concretely present here through the NEP-245 refund-log-size check.

### Finding Description
`execute_intents` runs the engine against the real `Contract` state and, after execution, calls `check_refund()` on the resulting `MtEvent` before emitting it, panicking with `ErrorLogTooLong` if the log (including possible refund overhead) would exceed `TOTAL_LOG_LENGTH_LIMIT`: [1](#0-0) 

The same enforcement happens inside the real state-mutation helpers used by withdrawals and deposits, which build `MtBurnEvent`/`MtMintEvent` and validate them with `check_refund()` (deposits directly, withdrawals via the postponed-burn flush on `Drop`): [2](#0-1) [3](#0-2) [4](#0-3) 

`simulate_intents`, however, runs the exact same engine logic against the *cached* state (`self.cached()`) with `SimulateInspector`, whose `on_event` implementation simply serializes the event to JSON for the report — it never computes an NEP-297 log string, never adds refund overhead, and never calls `check_refund()`: [5](#0-4) [6](#0-5) 

In addition, the `State` implementation used for simulation (`Cached`/`Deltas` state, reached via `cached()`) performs withdrawals through `internal_sub_balance` directly, bypassing the `MtBurnEvent` construction and `check_refund()` gate that the real `Contract::withdraw` applies: [7](#0-6) 

The binding that should hold is: *"a call to `simulate_intents(signed)` returning `Ok`/no error" ⇔ "a call to `execute_intents(signed)` with the identical payload also succeeds."* Because `simulate_intents` never reproduces the refund-log-length constraint that `execute_intents` enforces, this equality can be broken: a batch whose resulting NEP-297 event (with worst-case refund memo overhead) would exceed `TOTAL_LOG_LENGTH_LIMIT` is reported as successful by `simulate_intents`, but panics/reverts under `execute_intents`.

### Impact Explanation
This is the exact scenario the scope explicitly recognizes as High severity: `simulate_intents` diverging from `execute_intents`. Relayers, wallets, or integrators that rely on `simulate_intents` (a documented view method used to preview a batch before submission — see `tests/src/tests/defuse/intents/mod.rs::simulate_is_view_method`) to decide whether a batch of signed `MultiPayload`s is safe to submit will be misled: they will submit a transaction that `execute_intents` panics on. Because the whole transaction is atomic, all intents in the batch fail together on-chain, even though the simulation indicated success, breaking the safety guarantee integrators (and the relayer intent-execution flow itself) depend on `simulate_intents` for.

### Likelihood Explanation
The refund-log-size limit is a concrete, already-tested failure mode of the contract (`tests/src/tests/defuse/tokens/nep245/mt_transfer_resolve_gas.rs` contains tests specifically constructing payloads at/over `TOTAL_LOG_LENGTH_LIMIT`, e.g. `mt_batch_transfer_call_rejects_transfer_when_refund_log_exceeds_limit` and `mt_batch_transfer_call_rejects_at_refund_log_limit_boundary`), showing that batch withdrawals/transfers with many or long `TokenId`s realistically approach or exceed this limit. Any relayer submitting a `MultiPayload` containing an `FtWithdraw`, `MtWithdraw`, or `Transfer` intent with enough token entries (or long token ids/memos) to cross this boundary will trigger the divergence without any special privilege — this is fully reachable by an ordinary signer/relayer constructing an intent batch, no admin/DAO/relayer-key/upgrade action required.

### Recommendation
Make `simulate_intents`/`SimulateInspector` compute the same NEP-297 event log and apply the same `check_refund()` size check that `execute_intents` performs (or otherwise surface the same `ErrorLogTooLong` failure as part of the simulation result), and route the simulated state (`Cached`/`Deltas` in `contracts/defuse/core/src/engine/state/cached.rs`) through logic equivalent to `Contract::withdraw`/`Contract::deposit` so the log-length constraint is evaluated identically in both paths.

### Proof of Concept
1. Construct a `MultiPayload` containing a single signed `MtWithdraw` (or `Transfer`) intent whose `token_ids`/`amounts` are large enough (e.g., ~66 long token ids, similar to `REPRO_TOKEN_COUNT`/`REPRO_FIRST_TOKEN_ID_LEN` in `tests/src/tests/defuse/tokens/nep245/mt_transfer_resolve_gas.rs`) that the resulting `MtEvent::MtBurn`/`MtEvent::MtTransfer` NEP-297 log, including the worst-case `"refund"` memo overhead computed by `check_refund()` in `crates/near/nep245/src/checked.rs`, would exceed `defuse_near_utils::TOTAL_LOG_LENGTH_LIMIT`.
2. Call `simulate_intents([payload])` on the `Defuse` contract. Because `SimulateInspector::on_event` (`contracts/defuse/src/contract/intents/simulate.rs:56-58`) only serializes the event to JSON and the underlying `Cached` state's `mt_withdraw`/`ft_withdraw` (`contracts/defuse/core/src/engine/state/cached.rs:257-309`) never builds/validates an `MtBurnEvent`, the call returns `SimulationOutput` with `invariant_violated: None` — i.e., reported success.
3. Call `execute_intents([payload])` with the identical payload. The real `Contract::withdraw` (`contracts/defuse/src/contract/tokens/mod.rs:76-128`) constructs the `MtBurnEvent`, and either the postponed-burn flush (`contracts/defuse/src/contract/events.rs:14-21`) or the direct `check_refund()` call in `execute_intents` (`contracts/defuse/src/contract/intents/mod.rs:37-39`) panics with `ErrorLogTooLong`, reverting the entire batch.
4. The divergence is observable: step 2 reports success while step 3 panics for the exact same signed payload, confirming `simulate_intents` does not faithfully predict `execute_intents`.

```rust
    fn simulate_intents(&self, signed: Vec<MultiPayload>) -> SimulationOutput {
        let mut inspector = SimulateInspector::default();
        let engine = Engine::new(self.cached(), &mut inspector);

        let invariant_violated = match engine.execute_signed_intents(signed) {
            // do not log transfers
            Ok(_) => None,
            Err(DefuseError::InvariantViolated(v)) => Some(v),
            Err(err) => err.panic(),
        };

        SimulationOutput {
            report: inspector.into_report(),
            invariant_violated,
            state: StateOutput {
                fee: self.fee(),
                current_salt: self.salts.current(),
            },
        }
    }
```

```rust
    pub(crate) fn withdraw(
        &mut self,
        owner_id: &AccountIdRef,
        token_amounts: impl IntoIterator<Item = (TokenId, u128)>,
        memo: Option<impl Into<String>>,
        force: bool,
    ) -> Result<()> {
        let owner = self
            .storage
            .accounts
            .get_mut(owner_id)
            .ok_or_else(|| DefuseError::AccountNotFound(owner_id.to_owned()))?
            .get_mut_maybe_forced(force)
            .ok_or_else(|| DefuseError::AccountLocked(owner_id.to_owned()))?;

        let mut burn_event = MtBurnEvent {
            owner_id: Cow::Owned(owner_id.to_owned()),
            authorized_id: None,
            token_ids: Vec::new().into(),
            amounts: Vec::new().into(),
            memo: memo.map(Into::into).map(Into::into),
        };

        for (token_id, amount) in token_amounts {
            if amount == 0 {
                return Err(DefuseError::InvalidIntent);
            }

            burn_event.token_ids.to_mut().push(token_id.to_string());
            burn_event.amounts.to_mut().push(amount);

            owner
                .token_balances
                .sub(token_id.clone(), amount)
                .ok_or(DefuseError::BalanceOverflow)?;

            self.storage
                .state
                .total_supplies
                .sub(token_id, amount)
                .ok_or(DefuseError::BalanceOverflow)?;
        }

        // Schedule to emit `mt_burn` events only in the end of tx
        // to avoid confusion when `mt_burn` occurs before relevant
        // `mt_transfer` arrives. This can happen due to postponed
        // delta-matching during intents execution.
        if !burn_event.amounts.is_empty() {
            self.runtime.postponed_burns.mt_burn(burn_event);
        }

        Ok(())
    }
```

```rust
impl PostponedMtBurnEvents {
    pub fn mt_burn(&mut self, event: MtBurnEvent<'static>) {
        self.0.push(event);
    }

    pub fn flush(&mut self) -> Result<(), ErrorLogTooLong> {
        let events = mem::take(&mut self.0);
        if events.is_empty() {
            return Ok(());
        }
        MtEvent::MtBurn(events.into()).check_refund()?.emit();
        Ok(())
    }
}

impl Drop for PostponedMtBurnEvents {
    fn drop(&mut self) {
        // NOTE: `check_refund()` fails only when the refund event would exceed
        // maximum log size. Checking here prevents panics during withdrawal resolution.
        self.flush().unwrap_or_else(|err| err.panic());
    }
}
```

```rust
impl MtEvent<'_> {
    /// Validates that the event log (including potential refund overhead) fits within limits.
    /// Returns a [`CheckedMtEvent`] that can be emitted.
    pub fn check_refund(self) -> Result<CheckedMtEvent, ErrorLogTooLong> {
        let log = self.to_nep297_event().to_event_log();
        let delta = self.compute_refund_delta();
        let refund_len = log
            .len()
            .saturating_add(delta.overhead())
            .saturating_sub(delta.savings());

        if refund_len > defuse_near_utils::TOTAL_LOG_LENGTH_LIMIT {
            return Err(ErrorLogTooLong);
        }
        Ok(CheckedMtEvent(log))
    }
```
