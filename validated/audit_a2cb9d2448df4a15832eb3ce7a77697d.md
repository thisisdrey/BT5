### Title
Missing precision-symmetry check on TRC10 exchange pair creation allows Bancor-style pool drain via mixed-precision assets - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeCreateActuator.java`)

### Summary
`ExchangeCreateActuator` allows any account to create a TRC10-to-TRC10 (or TRC10/TRX) Bancor-relay exchange pool with arbitrary initial balances for two assets that may have wildly different `AssetIssueContract` precision (decimal) settings, with no check that the two initial balances are proportionate to the assets' precision. This is directly analogous to the reported `GSPVault.sol` issue, where a pool initialized with a low-precision base asset and a high-precision quote asset produced a broken internal target (`_QUOTE_TARGET_` collapsed to 0), letting an attacker drain the pool for the cost of a single unit of the quote token.

### Finding Description
`ExchangeCreateActuator.doValidate()` only checks that `firstTokenBalance` and `secondTokenBalance` are `> 0` and below `dynamicStore.getExchangeBalanceLimit()`; it never validates the ratio against the tokens' declared precision: [1](#0-0) 

TRC10 assets carry an arbitrary `precision`/`num` scale set independently by each issuer at `AssetIssueContract` creation, exactly like ERC20 `decimals()` in the report. The exchange model (`ExchangeCapsule.transaction`) treats both balances as raw integer units feeding a Bancor "relay to constant supply" curve with a fixed `supply = 1_000_000_000_000_000_000L`: [2](#0-1) 

The actual curve math is implemented in `SafeExchangeProcessor`/`ExchangeProcessor`, which perform two chained `BigDecimal` power operations (`exchangeToSupply` then `exchangeFromSupply`) using `RoundingMode.HALF_UP`/`DOWN` at fixed scale: [3](#0-2) 

If a pool is created with one side funded at a tiny raw quantity (because its issuer chose low precision, e.g. `num`/`precision` such that "1 unit" represents a large real value) and the other side funded at a huge raw quantity (high precision token), the ratio between `firstTokenBalance` and `secondTokenBalance` becomes extreme — exactly the scenario the report demonstrates with `10**6` base units vs `10**18` quote units. Because nothing in `ExchangeCreateActuator` normalizes for precision, the resulting Bancor curve parameters become skewed the same way the CFMM target became skewed in `GSPVault`, and subsequent tiny trades through `ExchangeTransactionActuator` (`exchangeCapsule.transaction(...)`) can extract disproportionate amounts of the poorly-funded side due to compounding rounding in the fixed-point power calculations.

`ExchangeWithdrawActuator` has an explicit "Not precise enough" guard comparing BigDecimal-computed ratios against actual longs to reject imprecise withdrawals: [4](#0-3) 
but no equivalent precision-consistency check exists at pool creation (`ExchangeCreateActuator`) or at swap time (`ExchangeTransactionActuator`), meaning the root-cause condition — mismatched effective precision between the two pooled assets — is never rejected up front, only partially mitigated downstream for withdrawals.

### Impact Explanation
If exploitable, this could allow an attacker to drain one side of a public liquidity pool created by any user (Exchange pools are permissionless, unprivileged accounts can call `ExchangeCreateContract`/`ExchangeInjectContract`/`ExchangeTransactionContract`), resulting in theft of pooled TRC10/TRX liquidity from other participants who injected balance into the same exchange. This matches the "unbacked balance / theft of provisioned liquidity" impact class in the rules.

### Likelihood Explanation
Likelihood is only **speculative/moderate** — I could not fully trace the exact numeric conditions (via `ExchangeProcessor`/`SafeExchangeProcessor`) that would reproduce a total-drain scenario equivalent to the GSP PoC, because I was unable to load `ExchangeProcessor.java`'s full contents within the available iterations (only its test file `ExchangeProcessorTest.java` and `SafeExchangeProcessor.java` were retrieved). The Bancor-curve math differs materially from PMM linear-target math in `GSPVault`, so the severity/exploitability of extreme balance ratios is unconfirmed without further analysis of `ExchangeProcessor.exchange()`'s rounding behavior under `useStrictMath=false` (legacy `double`-based path) versus the hardened `SafeExchangeProcessor` path.

### Recommendation
- Enforce that `ExchangeCreateActuator.doValidate()` rejects pools where `firstTokenBalance`/`secondTokenBalance` implies a ratio inconsistent with the assets' declared TRC10 `precision`, or require callers to supply amounts normalized to a common precision before pool creation.
- Extend the existing `ExchangeWithdrawActuator` "Not precise enough" style BigDecimal-ratio check to `ExchangeCreateActuator` and `ExchangeTransactionActuator` so extreme/imprecise ratios are rejected consistently across all Exchange actuators, not just withdrawal.
- Audit `ExchangeProcessor`/`SafeExchangeProcessor` for minimum-balance/minimum-ratio guards analogous to `dynamicStore.getExchangeBalanceLimit()` but bounding the *lower* end of balances relative to the counterpart token, to prevent a near-zero-balance side from being trivially drained.

### Proof of Concept
Not independently reproduced against `ExchangeProcessor`'s Bancor curve within this analysis — the concrete drain path (equivalent to the report's `sellQuote`/`sellBase` PoC) would need to be validated by: (1) creating an Exchange pool with `firstTokenBalance = 1` (asset A, low precision) and `secondTokenBalance = <exchange balance limit>` (asset B, high precision) via `ExchangeCreateContract`, then (2) issuing a minimal `ExchangeTransactionContract` sell of asset B and observing whether `ExchangeCapsule.transaction`/`ExchangeProcessor.exchange` returns a disproportionate amount of asset A, followed by repeated small trades to fully drain the pool. This step was not completed because the relevant `ExchangeProcessor.java` full source could not be retrieved before the iteration budget was exhausted; a Devin session with full repo access should confirm the exact rounding formula and whether the "Not precise enough" guard present in `ExchangeWithdrawActuator` is genuinely absent from the swap/inject/create paths before treating this as confirmed exploitable.

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
