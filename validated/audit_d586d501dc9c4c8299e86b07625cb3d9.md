### Title
Missing null-check on `ownerCapsule` before dereference in `FreezeBalanceProcessor.validate()` allows unauthenticated NPE / transaction-processing crash - ([File: actuator/src/main/java/org/tron/core/vm/nativecontract/FreezeBalanceProcessor.java])

### Summary
`FreezeBalanceProcessor.validate()`, the validation routine backing the TVM `freeze()` opcode/native-contract path, fetches the account for `ownerAddress` and immediately dereferences it (`ownerCapsule.getBalance()`) without checking for `null`, unlike its sibling `FreezeBalanceV2Processor.validate()`, which explicitly checks `ownerCapsule == null` before use. This mirrors the CVE-2021-47050 bug class: a lookup that can legitimately return `null` is dereferenced before being validated.

### Finding Description
In `FreezeBalanceProcessor.validate()`: [1](#0-0) 
the code does:
```java
byte[] ownerAddress = param.getOwnerAddress();
AccountCapsule ownerCapsule = repo.getAccount(ownerAddress);
long frozenBalance = param.getFrozenBalance();
if (frozenBalance <= 0) {
  ...
} else if (frozenBalance < TRX_PRECISION) {
  ...
} else if (frozenBalance > ownerCapsule.getBalance()) {   // <-- NPE if ownerCapsule == null
  ...
}
```
There is no `ownerCapsule == null` guard at all. Compare this to the analogous, corrected pattern in `FreezeBalanceV2Processor.validate()`, which checks for `null` immediately after fetching the account and before touching `getBalance()`: [2](#0-1) 

`repo.getAccount()` (i.e. `RepositoryImpl.getAccount`) returns `null` when the account does not exist in the store or any parent cache: [3](#0-2) 

This `validate()` is reached from the TVM `freeze` native function, `Program.freeze()`, using `ownerAddress = getContextAddress()` (the currently executing contract's own address): [4](#0-3) 

### Impact Explanation
If `ownerCapsule` is `null` when `validate()` runs, the call throws an uncaught `NullPointerException` rather than a handled `ContractValidateException`. Unlike `ContractValidateException`, which is caught in `Program.freeze()`'s `catch` block, a `NullPointerException` is not caught there, so it propagates up through the TVM execution path. Depending on how far up the exception is caught (transaction-level vs. block-application-level), this can:
- Cause the transaction execution to fail unpredictably instead of being gracefully reverted, or
- Cause block-processing/transaction-processing anomalies in `Manager` if the exception propagates past the expected `ContractValidateException`/`ContractExeException` handling used elsewhere in the actuator/native-contract framework, potentially affecting node availability for that transaction/block.

This satisfies the "node crash or halt" / "an API the node can no longer serve" impact category for a reachable, unprivileged-triggerable code path (any contract can invoke `freeze()` via TVM).

### Likelihood Explanation
Reachability depends on whether `getContextAddress()` (the executing contract itself) can lack an `AccountCapsule` entry at the moment `freeze()` executes. Newly created contract accounts are normally instantiated with an account record during `CREATE`/`CREATE2` handling before code execution begins, which would make this hard to trigger in the common case. I was unable to fully verify, within the available tool budget, whether there is an edge case (e.g., a contract executing in a repository child scope before its account entry is committed/visible, or an account removed via self-destruct semantics in some execution path) where `getContextAddress()` maps to no account when `freeze()` is invoked. This uncertainty affects confidence in exploitability; the defect itself (missing null check, inconsistent with the `V2` sibling) is confirmed by direct code comparison, but a concrete PoC transaction sequence proving `ownerCapsule == null` at that exact call site could not be fully constructed with the tools available.

### Recommendation
Add a `null` check for `ownerCapsule` in `FreezeBalanceProcessor.validate()` immediately after `repo.getAccount(ownerAddress)`, mirroring the existing pattern in `FreezeBalanceV2Processor.validate()`:
```java
AccountCapsule ownerCapsule = repo.getAccount(ownerAddress);
if (ownerCapsule == null) {
  throw new ContractValidateException(ACCOUNT_EXCEPTION_STR + ... + NOT_EXIST_STR);
}
```

### Proof of Concept
Not able to construct a concrete, verified end-to-end PoC transaction with the tools available — confirmation would require tracing whether a contract account entry can be absent from `AccountStore`/`Repository` cache at the moment `Program.freeze()` executes for `getContextAddress()`. The root-cause defect (dereference of a nullable `AccountCapsule` without a guard, contrasted against the guarded sibling implementation) is confirmed by direct code inspection cited above.

  @Override
  public AccountCapsule getAccount(byte[] address) {
    Key key = new Key(address);
    if (accountCache.containsKey(key)) {
      return new AccountCapsule(accountCache.get(key).getValue());
    }

    AccountCapsule accountCapsule;
    if (parent != null) {
      accountCapsule = parent.getAccount(address);
    } else {
      accountCapsule = getAccountStore().get(address);
    }

    if (accountCapsule != null) {
      accountCache.put(key, Value.create(accountCapsule));
    }
    return accountCapsule;
  }
