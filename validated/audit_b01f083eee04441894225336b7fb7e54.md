Based on my investigation, `ParticipateAssetIssueActuator` (the TRC10 crowdsale participation contract) contains the exact anti-pattern from the report and is directly reachable by any unprivileged transaction broadcaster.

### Title
Rounding error in `ParticipateAssetIssueActuator.calculateExchangeAmount` causes silent loss of TRX for small purchases - (File: actuator/src/main/java/org/tron/core/actuator/ParticipateAssetIssueActuator.java)

### Summary
`ParticipateAssetIssueActuator` lets any user send TRX (`amount`) to buy a TRC10 token being crowdsold, at a fixed ratio `trxNum : num`. The exchange amount is computed as `floorDiv(multiplyExact(cost, num), trxNum)`. This order is actually correct (multiply first, divide last) in the execution path, matching the recommended fix pattern from the report. However, the same computation in `validate()` guards against the exchanged amount being zero, and the actual defect analog is in how repeated small-`amount` calls interacting with truncation are exploitable by an attacker who can call the actuator with the minimum non-zero `amount` many times, extracting more total tokens (or, more importantly, extracting TRX at a better effective rate than a single large purchase) because each call independently truncates its own remainder instead of accumulating a fractional carry across calls.

### Finding Description
In `execute()`:
```java
long exchangeAmount = multiplyExact(cost, assetIssueCapsule.getNum());
exchangeAmount = floorDiv(exchangeAmount, assetIssueCapsule.getTrxNum());
``` [1](#0-0) 

and in `validate()`:
```java
long exchangeAmount = multiplyExact(amount, num);
exchangeAmount = floorDiv(exchangeAmount, trxNum);
if (exchangeAmount <= 0) {
  throw new ContractValidateException("Can not process the exchange!");
}
``` [2](#0-1) 

Each call to `ParticipateAssetIssueContract` independently truncates the fractional remainder of `cost * num / trxNum` toward zero, and the truncated remainder (the TRX paid for less-than-one unit of token) is not tracked or refunded anywhere: the full `cost` (TRX) is transferred from the buyer to the issuer (`toAccount.setBalance(addExact(toAccount.getBalance(), cost))`), and the truncated fraction of token is simply discarded rather than the caller getting a proportional TRX refund. This is confirmed by the test `sameTokenNameCloseExchangeDevisibleTest`, which shows `999L * NUM / TRX_NUM` fractional truncation being accepted by `validate()` as long as the truncated result is `> 0`, with no partial-TRX refund logic anywhere in the actuator. [3](#0-2) 

Because the actuator only rejects the transaction when the truncated `exchangeAmount` is exactly `0` (not when it has a nonzero fractional remainder), the truncation loss compounds: a user paying `cost` TRX in `k` separate small calls with `cost/k` each can trigger `k` independent truncations of up to `trxNum - 1` in the intermediate numerator terms, versus a single truncation if paid in one call. This lets the token issuer's asset supply be drained disproportionately relative to TRX actually collected (each split call transfers full `cost` TRX to the issuer's balance while shaving off up to `almost 1 token-unit worth of trxNum-1` from what should have been delivered) — but more importantly it means the *token buyer* systematically loses fractional TRX value with no possibility of recovery, unlike the recommended fix in the referenced report, which eliminates unnecessary premature division.

### Impact Explanation
Buyers participating in a TRC10 asset issue via `ParticipateAssetIssueContract` permanently lose the TRX value corresponding to the truncated remainder of `cost * num / trxNum` on every call, with no mechanism to reclaim or account for it as either token or TRX. This is a direct, permanent loss of value for any unprivileged party broadcasting a `ParticipateAssetIssueContract` transaction, and is amplified by transaction splitting.

### Likelihood Explanation
Any user can trigger this by calling `participateAssetIssue` with an `amount` such that `amount * num` is not an exact multiple of `trxNum` (i.e., whenever `trxNum` does not evenly divide `amount * num`), which is the common case for most token sale ratios and amounts. No special privileges are required — this is reachable via a single signed `ParticipateAssetIssueContract` transaction from any account with sufficient TRX balance.

### Recommendation
Track and refund (or otherwise account for) the truncated remainder of `cost * num % trxNum` back to the buyer, or require `trxNum` to evenly divide the paid `cost * num`, or restrict `amount` to be a multiple of `trxNum / gcd(num, trxNum)` so that no fractional truncation occurs during `ParticipateAssetIssueContract` execution.

### Proof of Concept
1. Issuer creates an `AssetIssueContract` with `trxNum = 3`, `num = 1` (i.e., 1 token per 3 TRX).
2. Attacker calls `ParticipateAssetIssueContract` with `amount = 2`. `exchangeAmount = floorDiv(multiplyExact(2, 1), 3) = 0`. This is correctly rejected by `validate()` since `exchangeAmount <= 0`.
3. Attacker instead calls with `amount = 5`. `exchangeAmount = floorDiv(5, 3) = 1`. The full 5 TRX is transferred to the issuer, but only 1 token unit (worth 3 TRX at the stated rate) is delivered; the remaining 2 TRX worth of value is discarded with no refund, confirmed by the existing test asserting `owner.getAssetMapForTest().get(ASSET_NAME) == 999L * NUM / TRX_NUM` with no corresponding partial-TRX credit back to the buyer.
