### Title
Attacker-controlled `tokenIn_` in `SmartFarmingManager.leverage` lets any EOA impersonate `SmartFarmingManager` and burn victims' `DepositToken` collateral into a stuck contract (File: contracts/SmartFarmingManager.sol)

### Summary
`SmartFarmingManager.leverage` accepts an arbitrary `IERC20 tokenIn_` argument and calls `tokenIn_.safeTransferFrom(_msgSender, address(this), amountIn_)` — an external call into a fully attacker-controlled contract while `msg.sender == SmartFarmingManager`. Several `DepositToken` functions (`flashWithdraw`, `withdrawFrom`) are gated only by `onlyIfSmartFarmingManager` (i.e. `_msgSender() == pool.smartFarmingManager()`). From inside the malicious token's `transferFrom`, the attacker calls `depositToken.flashWithdraw(victim, victimBalance)`, which burns the victim's `msdTOKEN` and pulls the underlying out of `Treasury` into the `SmartFarmingManager` contract, where it is permanently stranded. This drains backing from the pool while leaving other depositors' `msdTOKEN` unbacked — protocol insolvency / permanent freezing of user funds — the same bug class as the Inverter `executeTxFromModule` → `transferOrchestratorToken` drain (a privileged-context function reached via an intermediary `msg.sender`).

### Finding Description
`leverage` performs an arbitrary external call with attacker-chosen target before any other state change:

```solidity
// contracts/SmartFarmingManager.sol
IERC20 _collateral = _collateralOf(depositToken_);
if (address(tokenIn_) == address(0)) tokenIn_ = _collateral;
amountIn_ = _safeTransferFrom(tokenIn_, _msgSender, amountIn_);   // attacker callback, msg.sender = SFM
``` [1](#0-0) 

Inside the callback, `msg.sender` on any downstream call is the `SmartFarmingManager` contract. `DepositToken` guards two collateral-moving functions solely on that identity:

```solidity
// contracts/DepositToken.sol
modifier onlyIfSmartFarmingManager() {
    if (_msgSender() != address(pool.smartFarmingManager())) revert SenderIsNotSmartFarmingManager();
    _;
}
``` [2](#0-1) 

```solidity
function flashWithdraw(address account_, uint256 amount_)
    external override onlyIfSmartFarmingManager returns (uint256, uint256) {
    return _withdraw({account_: account_, amount_: amount_, to_: _msgSender()});
}
``` [3](#0-2) 

Critically, `flashWithdraw` routes straight into `_withdraw` **without** the `_revertIfLocked` check applied in `withdraw`/`withdrawFrom`, so even collateral backing an open debt position can be seized:

```solidity
function _withdraw(address account_, uint256 amount_, address to_)
    private whenNotShutdown nonReentrant onlyIfDepositTokenExists returns (uint256 _withdrawn, uint256 _fee) {
    ...
    _burn(account_, _withdrawn);
    _pool.treasury().pull(to_, _withdrawn);   // underlying leaves Treasury to SFM
}
``` [4](#0-3) 

`Treasury.pull` passes because its caller is the whitelisted `DepositToken`:

```solidity
function pull(address to_, uint256 amount_) external override nonReentrant {
    address _msgSender = _msgSender();
    if (!pool.doesDepositTokenExist(IDepositToken(_msgSender))) revert SenderIsNotDepositToken();
    ...
    IDepositToken(_msgSender).underlying().safeTransfer(to_, amount_);
}
``` [5](#0-4) 

The `nonReentrant` guards do not stop this: `leverage`'s guard lives on `SmartFarmingManager`, while `flashWithdraw`/`_withdraw` enter `DepositToken` and `Treasury` — different contracts with independent transient reentrancy slots (`ReentrancyGuardTransient` is per-contract). The stolen underlying lands in `SmartFarmingManager`, which has no user-facing sweep function (`TokenHolder` sweep is `onlyGovernor` where present; `SmartFarmingManager` exposes none), so the collateral is stranded. The rest of `leverage` can be driven to succeed trivially (`amountIn_` measured as 0 → `debtAmount` 0 → `depositAmountMin_ = 0` → attacker health check passes), so the malicious callback is not reverted.

Invariant broken: solvency — `DepositToken.totalSupply` is reduced and the corresponding underlying leaves `Treasury`, but the assets sit in an unspendable contract, leaving remaining `msdTOKEN` holders unbacked (later `withdraw`s will underflow/pull nothing).

### Impact Explanation
Any unprivileged attacker can, for every `DepositToken` of every pool, burn arbitrary victims' entire `msdTOKEN` balances (including debt-locked balances via `flashWithdraw`) and move the underlying collateral out of `Treasury` into `SmartFarmingManager`, where it is permanently locked absent governor intervention. Direct consequences:

- Permanent freezing/loss of victims' collateral (their deposit tokens are burned; underlying is stranded in SFM).
- Protocol insolvency: `Treasury` backing < `DepositToken.totalSupply` for remaining users, so honest withdrawals eventually revert on `pull`.
- Repeatable across all deposit tokens and all pools in a single transaction via `Operator.execute` batching.

### Likelihood Explanation
Likelihood is high:

- `tokenIn_` is a raw user-supplied `IERC20`; there is no allowlist check — only `address(0)` is special-cased to the collateral.
- No privileged role is needed; `leverage` is a public function gated only by `whenNotShutdown` and token-existence modifiers.
- `SynthContext._msgSender()` resolves to the real EOA for the outer call, but the impersonation happens through raw `msg.sender` propagation during the token callback — the `Operator`/transient-sender machinery is not involved and cannot help.
- Pause does not help victims: `flashWithdraw`/`_withdraw` are `whenNotShutdown` (still callable while merely paused).

One caveat I could not fully verify within this review: whether `DebtToken.flashIssue`/`mint` (also callable by SFM) can be abused in the same callback for direct profit rather than insolvency — e.g. `debtToken.mint(attacker, X)` inside the callback would mint debt to the attacker, which is then constrained by the final `PositionIsNotHealthy` check. The stranded-collateral insolvency path stands regardless.

### Recommendation
- Do not trust `msg.sender == SmartFarmingManager` as authorization when SFM makes calls into untrusted contracts. Resolve victims' state changes off the *outer* `_msgSender()` instead of the callback context — e.g. have `flashWithdraw`/`withdrawFrom` accept the beneficiary only from a pull pattern, or pass the user explicitly and verify the call was initiated in the same top-level frame (e.g. store the legit caller in a transient slot set only inside SFM's `leverage`/`flashRepay` entrypoints, cleared on exit, and have `DepositToken` require that slot).
- Alternatively, perform the `tokenIn_.safeTransferFrom` pull *last* (after all privileged calls), or require `tokenIn_ == _collateral` / an allowlist of `tokenIn_`.
- Short term, add the same protection Inverter was advised to add: bind privileged flows to a checksummed execution context rather than a contract identity that can be spoofed via arbitrary external calls.

### Proof of Concept
Foundry-style test against the pool's contracts (assumes `pool`, `depositToken`, `syntheticToken`, `treasury`, `sfm` deployed; `victim` holds `msdTOKEN`):

```solidity
contract EvilToken {
    IDepositToken dt; address victim; uint256 amt;
    constructor(IDepositToken _dt, address _victim, uint256 _amt) { dt = _dt; victim = _victim; amt = _amt; }
    function transferFrom(address, address, uint256) external returns (bool) {
        // msg.sender == SmartFarmingManager here -> bypasses onlyIfSmartFarmingManager
        dt.flashWithdraw(victim, amt); // burns victim's msdTOKEN, pulls underlying to SFM
        return true;                   // transfers nothing -> amountIn_ measured as 0
    }
    function balanceOf(address) external view returns (uint256) { return 0; }
    function allowance(address, address) external view returns (uint256) { return type(uint256).max; }
    // other ERC20 fns can no-op
}

function testDrainViaSFMImpersonation() public {
    uint256 victimBal = depositToken.balanceOf(victim);
    uint256 treasuryBefore = underlying.balanceOf(address(treasury));

    EvilToken evil = new EvilToken(depositToken, victim, victimBal);

    vm.prank(attacker);
    sfm.leverage(
        IERC20(address(evil)),   // tokenIn_ — malicious
        depositToken,
        syntheticToken,
        1,                       // amountIn_ (delta will be 0)
        1.1e18,                  // leverage_ > 1e18
        0                        // depositAmountMin_
    );

    assertEq(depositToken.balanceOf(victim), 0);
    assertEq(underlying.balanceOf(address(treasury)), treasuryBefore - victimBalWithdrawn);
    assertGt(underlying.balanceOf(address(sfm)), 0); // stranded in SFM
}
```

Call chain: `attacker → SFM.leverage(evilToken,…)` → `evilToken.transferFrom` (msg.sender = SFM) → `DepositToken.flashWithdraw(victim, bal)` → `_withdraw` → `Treasury.pull(SFM, bal)` → underlying irrevocably stranded; `DepositToken.totalSupply` reduced with no corresponding recoverable backing → insolvency for remaining depositors.
