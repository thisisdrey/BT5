### Title
Unvalidated attacker-controlled length fields in `PrecompiledContracts` byte-array extraction can trigger `OutOfMemoryError`/uncaught runtime exceptions from a single crafted contract call - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
This is the closest reachable analog to CVE-2019-13217. The CVE is a heap buffer overflow in `stb_vorbis`'s `start_decoder`, caused by trusting an attacker-supplied length/size field from a file header when allocating and copying a buffer. In java-tron, the precompiled-contract input decoders `extractBytesArray` and `extractSigArray` in `PrecompiledContracts.java` exhibit the same root-cause pattern: a length value is read directly out of attacker-controlled `DataWord[]` call data and used, unchecked, to size and copy a buffer.

### Finding Description
`extractBytesArray` and `extractSigArray` decode ABI-style byte-array parameters passed to precompiled contracts (e.g. batch signature validation contracts) reachable from ordinary smart-contract calls: [1](#0-0) 

`len`, `bytesOffset`, and `bytesLen` are all derived from `words[...].intValueSafe()`, i.e. directly from caller-supplied `DataWord` values with no validation against the actual size of `data` or against negative/huge values before being handed to: [2](#0-1) 

`extractBytes` simply calls `Arrays.copyOfRange(data, offset, offset + len)`. Because `offset` and `len` are attacker-influenced ints derived from a full 256-bit word truncated via `intValueSafe()`, this call can be reached with:
- `len` at or near `Integer.MAX_VALUE`, causing `copyOfRange` to attempt to allocate a byte array of that size, throwing `OutOfMemoryError`.
- `offset` larger than `data.length`, or negative, causing an unhandled `IndexOutOfBoundsException`/`NegativeArraySizeException` deep in `System.arraycopy`.

This mirrors the stb_vorbis bug class exactly: an untrusted size/offset field from the "file" (here, the ABI-encoded call data) is trusted to allocate and copy a buffer without bounds validation against the actual backing buffer.

### Impact Explanation
If such an exception (particularly `OutOfMemoryError`) is not caught cleanly by the VM's per-transaction exception handling and instead propagates or destabilizes the JVM heap, it can crash or degrade the node process handling the transaction — a denial-of-service against any node that executes the transaction (including all validating full nodes/SRs during block application). Because this decode path runs during ordinary contract execution triggered by a broadcast transaction, it is reachable by any unprivileged transaction sender who can invoke the corresponding precompiled contract (e.g. `BatchValidateSign`/`ValidateMultiSign`).

### Likelihood Explanation
Reachability is straightforward: an attacker only needs to construct a transaction/contract call whose ABI-encoded input, once parsed into `DataWord[]`, produces a decoded `len`/`bytesOffset` far outside the bounds of the actual `data` buffer. No special privileges, keys, or SR/witness status are required — this is directly triggerable by any transaction broadcaster. However, I was not able to fully confirm within the available context (i) the exact upstream code path that populates `words`/`data` before calling `extractBytesArray`/`extractSigArray`, (ii) whether the surrounding precompiled-contract `execute()` method or `Program`/VM transaction-execution wrapper wraps this with a broad `catch (Throwable)` that safely reverts on `OutOfMemoryError` (JVM `Error`s are often not caught by `catch (Exception)` clauses), and (iii) whether `intValueSafe()` already clamps values to a smaller safe range before reaching this code, which would reduce or eliminate the practical impact. These are the key uncertainties limiting a full "proven root cause" determination.

### Recommendation
- In `extractBytesArray`/`extractSigArray`/`extractBytes`, validate that `bytesOffset`, `bytesLen`/`len`, and the resulting `offset + len` are non-negative and within `data.length` before calling `Arrays.copyOfRange`, returning an empty array or throwing a caught/handled exception (consistent with how `RLP.decode`'s `verifyLength` bounds-checks lengths against the actual payload) instead of allowing unchecked huge or negative sizes to reach array allocation/copy.
- Ensure the precompiled-contract execution path uses a `catch (Throwable)` (not just `Exception`) around per-contract-call decoding so that `OutOfMemoryError`/`Error` from a single malicious call cannot destabilize the node process or the block-application flow in `Manager`.

### Proof of Concept
Conceptual (not independently executed against a running node due to tool limitations):
1. Craft a transaction calling the `BatchValidateSign`/`ValidateMultiSign` precompiled contract address with ABI-encoded input where the array-length word (`words[offset]`) is set to a small count, but the per-element offset word (`words[offset + i + 1]`) is set to a very large value (e.g., `0xFFFFFFFF`/near `Integer.MAX_VALUE / WORD_SIZE`), and/or the length word (`words[offset + bytesOffset + 1]`) is set to a value near `Integer.MAX_VALUE`.
2. Broadcast the transaction to a full node executing the TVM.
3. `extractBytesArray` computes `bytesLen` from the crafted word and calls `extractBytes(data, hugeOffset, hugeLen)` → `Arrays.copyOfRange(data, hugeOffset, hugeOffset + hugeLen)`, attempting to allocate an oversized array or throwing an unbounded-index exception during transaction execution.

Given the incomplete verification of the surrounding exception-handling and input-population code noted above, this should be validated further (e.g., via a Devin session with full file/test access) before treating it as a confirmed exploitable DoS.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
