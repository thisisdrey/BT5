### Title
Unauthenticated peer-controlled `data_url` enables SSRF-style outbound connections to arbitrary/internal addresses - (File: stackslib/src/net/chat.rs)

### Summary
A remote, unauthenticated peer can set an arbitrary `data_url` (including `127.0.0.1`, RFC1918/private, or link-local addresses) in its `Handshake` message. The receiving node resolves this URL and, unlike the mempool-sync code path, does **not** filter out private/loopback/link-local addresses before using the resolved address to open outbound HTTP connections back to that peer's claimed "data server," mirroring the `Resource#find` SSRF pattern in the Recurly advisory: an attacker supplies a "location" value that the victim uses to make an outbound request without validating that the destination is safe/expected.

### Finding Description
When a `Handshake` message arrives, the P2P `ConversationP2P` records the sender-supplied `data_url` string. The routine `try_resolve_data_url_host` in [1](#0-0)  either decodes a literal IP from that URL via `try_decode_data_url_ipaddr` [2](#0-1)  or resolves a domain name via DNS [3](#0-2) , storing the result in `self.data_ip` **without any check that the resulting address is not loopback/private/link-local**.

This resolved `data_ip` is later used directly to open a real outbound TCP/HTTP connection to the attacker-chosen address, e.g. in the neighbor-RPC HTTP client used for StackerDB/RPC fetches: [4](#0-3) 
which calls `HttpPeer::connect_http` [5](#0-4)  — there is no private/loopback filtering in this path either.

Contrast this with the **mempool sync** code, which explicitly guards against exactly this problem: [6](#0-5) 
Here, before issuing an HTTP query to a resolved data-URL address, the code checks `PeerAddress::from_socketaddr(addr).is_in_private_range()` and aborts the sync unless `connection_opts.private_neighbors` is explicitly enabled. This proves the private-range check is a known, deliberate mitigation for this exact SSRF class elsewhere in the same file/module — but it is missing from the general `ConversationP2P`/`NeighborRPC` HTTP-connect path that all other data-URL-driven outbound requests (StackerDB chunk fetch, generic neighbor RPC) rely on.

### Impact Explanation
Any already-connected, unauthenticated remote peer (handshake requires no privileged credential) can set its advertised `data_url` to point at an internal-only address (loopback, RFC1918, link-local/metadata service, or an unrelated third-party host) and force the victim Stacks node to originate outbound HTTP connections to that destination whenever the node later performs a neighbor-RPC/HTTP fetch against that peer (e.g., StackerDB chunk downloads via `NeighborRPC::send_request`). This lets a remote attacker use the victim node as a network proxy to reach internal services/ports that are not otherwise externally reachable — the classic SSRF impact described in the Recurly `Resource#find` advisory, remotely triggerable with no special privileges.

### Likelihood Explanation
High: `data_url` is attacker-supplied plaintext in the `Handshake` message and is trivially set to any string that parses as a URL; no authentication beyond a normal p2p handshake is required, and the vulnerable resolve/connect path (`try_resolve_data_url_host` → `NeighborRPC::send_request` → `HttpPeer::connect_http`) is exercised by ordinary node operation whenever this peer's data URL needs to be contacted (e.g., StackerDB sync).

### Recommendation
Apply the same private/loopback/link-local filtering used in `mempool_sync_send_query` (`PeerAddress::is_in_private_range()` gated by `connection_opts.private_neighbors`) uniformly in `ConversationP2P::try_resolve_data_url_host` and in `HttpPeer::connect_http`/`NeighborRPC::send_request`, so that no outbound HTTP connection is made to a resolved `data_url` address that falls in a private/loopback/link-local range unless the operator has explicitly opted in via `private_neighbors`.

### Proof of Concept
1. Attacker node completes a normal `Handshake` with the victim, setting `HandshakeData.data_url` to `http://127.0.0.1:<internal-port>/` (or an RFC1918 address of an internal service reachable from the victim's network).
2. Victim's `ConversationP2P::try_resolve_data_url_host` decodes the literal IP with no private-range check and stores it as `data_ip` [2](#0-1) .
3. When the victim later needs to fetch a StackerDB chunk (or any neighbor-RPC HTTP request) from this peer, `NeighborRPC::send_request` uses `convo.data_ip` directly to call `connect_http` [4](#0-3) , causing the victim node to open an outbound HTTP connection to the attacker-chosen internal address.
