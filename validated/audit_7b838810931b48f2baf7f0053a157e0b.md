### Title
Unbonded pool-member DoS: shared staking `unlocking` chunk queue can be exhausted, blocking legitimate `withdraw_unbonded`/`unbond` calls - (File: `substrate/frame/nomination-pools/src/lib.rs`)

### Summary
`pallet-nomination-pools`'s `unbond()` extrinsic lets any pool member unbond, but every member's unbond writes into the *same* underlying staking `StakingLedger.unlocking` chunk vector for the pool's single bonded stash account, which is bounded by `Config::MaxUnlockingChunks` in `pallet-staking`. Because the bound is shared across all members of a pool rather than per-member, a low-value member can repeatedly submit minimal unbonds (one per era) to fill all available chunk slots, causing legitimate members' subsequent `unbond` calls to fail with `NoMoreChunks` until the attacker's chunks expire. This mirrors the reported Pontis bug class: a bounded, shared, first-come-first-served resource pool intended to serve many honest users can be monopolized by a cheap adversarial user, producing a temporary denial of service of a core user-facing function.

### Finding Description
`Pallet::unbond` in `substrate/frame/nomination-pools/src/lib.rs` (around lines 2255-2337) is a permissioned public extrinsic. After validating the caller via `bonded_pool.ok_to_unbond_with`, it calls: [1](#0-0) 

`T::StakeAdapter::unbond(...)` ultimately appends an `UnlockChunk` to the pool's bonded account `StakingLedger.unlocking`, a `BoundedVec<UnlockChunk, T::MaxUnlockingChunks>` in `pallet-staking`. This bonded account is **one shared stash for the entire pool** — every member of the pool who calls `unbond` competes for the same fixed number of chunk slots (`MaxUnlockingChunks`, typically 32 in production runtimes). Unbonds in different eras each consume a new chunk; unbonds within the same era merge into the existing chunk for that era.

Once the shared `unlocking` vec is full, `pallet-staking` rejects the unbond attempt with `Error::NoMoreChunks`, which propagates up through `nomination-pools::unbond`. This is directly exercised by the existing test `automatic_unbonding_pools` in `substrate/frame/election-provider-multi-phase/test-staking-e2e/src/lib.rs` (lines 356-362), where member `3`'s `unbond` fails with `pallet_staking::Error::<Runtime>::NoMoreChunks` purely because member `2`'s prior unbond filled the shared chunk: [2](#0-1) 

Nothing in `unbond` or `ok_to_unbond_with` limits how often, or how cheaply, a single member can consume a chunk slot relative to the number of *other* members waiting to unbond. An attacker can:
1. Join the pool with the minimum bond (`Pools::join` at minimal value, subject only to `MinJoinBond`).
2. Once per era, call `unbond` for a tiny `unbonding_points` amount, consuming one of the finite chunk slots each time — this is cheap (bounded by dust amounts and normal transaction fees) and requires no privileged role.
3. Repeat until `MaxUnlockingChunks` slots are exhausted.

While `pool_withdraw_unbonded` exists as a permissionless helper to clear *expired* chunks (only after `bonding_duration` eras have elapsed), it provides no relief while the attacker's chunks are still within the bonding window — the attacker can keep re-filling freed slots at the start of each new era, sustaining the block indefinitely at negligible cost, exactly like the Pontis `PegOutKeyUtxo` attacker repeatedly consuming cheap slots to starve the shared pool.

### Impact Explanation
This directly blocks the core "exit" functionality of nomination pools (`unbond` / `withdraw_unbonded`) for all *other* members of the affected pool: legitimate members cannot unbond their stake while the shared chunk queue is saturated, causing a persistent denial of service on fund withdrawal for as long as the attacker sustains the pattern. This is a fund-lock/availability impact on staking accounting matching the "public underpriced work that degrades... stalls processing" and "permanent user-fund... lock" categories in the impact gate, achievable entirely by an unprivileged, non-validator, non-collator account acting as an ordinary pool member — no malicious relayer, validator, or admin is required.

### Likelihood Explanation
Likelihood is moderate: the attack requires the attacker to be (or become) a member of the target pool, and to sustain one unbond transaction per era over multiple eras (bounded by `MaxUnlockingChunks`, e.g. 32 eras/~8 days in a typical runtime) to fully saturate the queue, then keep re-filling it. This is exactly analogous to the Pontis report's own mitigating factor ("attacker must pay fees repeatedly") — here the attacker pays transaction fees and locks a small, refundable bond amount, but no large capital is required, and the attack is fully repeatable at will against any pool, making it a realistic low-cost griefing vector against any nomination pool a victim wishes to exit.

### Recommendation
Consider one or more of:
- Tracking and enforcing a per-member share/reservation of unbonding chunk capacity so that a single member cannot consume slots needed by others.
- Allowing `unbond`/`withdraw_unbonded` to proactively call `pool_withdraw_unbonded` internally to free any already-expired chunks before failing with `NoMoreChunks`, reducing the window in which the attack is effective.
- Introducing a minimum bonded-value or cooldown per member for chunk consumption so that dust-value unbonds cannot cheaply monopolize the shared slot pool.

### Proof of Concept
Using the existing pool test harness in `substrate/frame/election-provider-multi-phase/test-staking-e2e/src/lib.rs` (see `automatic_unbonding_pools`, lines 301-406) as a base:
1. Configure `MaxUnlockingChunks = 1` (or any small N) and `BondingDuration = D` on `pallet-staking`, and create a pool with members `A` (attacker) and `B` (victim).
2. Attacker `A` calls `Pools::unbond(A, A, small_amount)` in era `E`, filling the pool's single/only remaining shared `unlocking` chunk.
3. Victim `B` calls `Pools::unbond(B, B, amount)` in the same era before the chunk expires — this fails with `pallet_staking::Error::<Runtime>::NoMoreChunks`, exactly as demonstrated for member `3` in the existing `automatic_unbonding_pools` test: [3](#0-2) 
4. Repeat step 2 by `A` at the start of each subsequent era (re-filling the slot as soon as it frees) to keep `B` perpetually unable to unbond.
