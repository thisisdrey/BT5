### Title
Stale `base_time` inherited via `TokenBucket::clone()` causes new per-key rate-limit buckets to instantly reach full burst capacity, bypassing the intended initial connection-rate limit - (File: net-utils/src/token_bucket.rs)

### Summary
`KeyedRateLimiter` creates a fresh `TokenBucket` for every new key (e.g. every new source IP hitting the QUIC connection rate limiter) by calling `TokenBucket::clone()` on a long-lived `prototype_bucket`. `Clone` copies the prototype's `base_time` (an `Instant` fixed at validator/limiter startup) verbatim instead of resetting it to "now," while `last_update` is copied as `0` (its never-modified initial value on the untouched prototype). This is the same class of bug as the Gondi finding: a timestamp that should represent "now" is instead hardcoded/inherited as a stale/zero value, which inflates a rate/time-delta calculation. Here it inflates the "elapsed time" used to mint tokens on the very first use of a brand-new bucket, saturating it to `max_tokens` (the burst cap) instead of the intended smaller `initial_tokens`, defeating the purpose of the initial rate limit for every first-seen peer.

### Finding Description
`TokenBucket::new()` sets: [1](#0-0) 
`base_time` to `Instant::now()` at construction time, and `tokens` to `initial_tokens` (which is deliberately smaller than `max_tokens` for `ConnectionRateLimiter`, see below). `last_update` starts at `0` (meaning "0 microseconds after `base_time`").

`KeyedRateLimiter` keeps one long-lived `prototype_bucket` created once, at limiter construction: [2](#0-1) 
The prototype itself is never consumed from directly — only clones of it are stored per key. So the prototype's `last_update` never advances past its initial value of `0`, and its `base_time` remains fixed at limiter-creation time (essentially validator startup, since `ConnectionRateLimiter::new` is called once when the QUIC server is spawned).

When a new key (new source IP) is first seen, `KeyedRateLimiter::consume_tokens` clones the prototype: [3](#0-2) 
`Clone` for `TokenBucket` copies `base_time` and `last_update` straight from the prototype instead of re-anchoring them to the current instant: [4](#0-3) 

`time_us()` computes elapsed time as `Instant::now() - self.base_time`: [5](#0-4) 
Because `base_time` is the *original* prototype creation time (long in the past once the validator has been running), the very first call to `update_state()` on a freshly-cloned bucket computes `elapsed = now.saturating_sub(last=0)` as a huge value (the validator's entire uptime so far, in microseconds), not the intended "0 elapsed since bucket creation": [6](#0-5) 
`new_tokens_f64 = elapsed * new_tokens_per_us` is therefore enormous and `add_tokens()` saturates the bucket to `max_tokens` immediately, even though the bucket is brand-new.

This is directly analogous to the Gondi bug: a constructor/derivation path initializes a "last update timestamp" incorrectly (stale/zero instead of "now"), and the subsequent rate math (`elapsed = now - last_ts`) is computed against the wrong baseline, producing a grossly inflated rate value that is then used to pass/exceed an intended threshold check (there: APR validation check; here: token-bucket capacity check).

### Impact Explanation
This is reachable via the unprivileged QUIC/UDP streamer connection path. `ConnectionRateLimiter` (built on `KeyedRateLimiter<IpAddr>`/`TokenBucket`) is used to throttle new incoming QUIC connections per source IP: [7](#0-6) 
and is consulted/updated on every new connection in the QUIC accept loop: [8](#0-7) [9](#0-8) 

The prototype is constructed with `initial_tokens = max_connections_per_ipaddr_per_min` and `max_tokens = 10 * max_connections_per_ipaddr_per_min` (intentional 10x burst allowance for legitimate multi-pod/NAT scenarios), refilling at `limit_per_minute/60` tokens/sec: [8](#0-7) 

Once the validator has been running long enough for `elapsed_since_prototype_creation * new_tokens_per_us` to exceed `max_tokens` (with the default rate this is on the order of minutes), *every subsequent first-seen source IP* gets its bucket saturated to the full 10x burst cap on the very first connection attempt, instead of the intended, smaller `initial_tokens` allowance. This effectively multiplies the allowed initial connection burst per new/spoofable-looking source IP by up to 10x for the remaining lifetime of the validator process, weakening the QUIC connection-flood/DoS mitigation this rate limiter exists to enforce. This is a QoS-evasion class issue: a resource-consumption gate that is supposed to ramp up gradually per new peer instead grants full capacity immediately.

### Likelihood Explanation
High likelihood of occurring in production and low likelihood of being caught by tests: any validator that has been up for more than a short warm-up period will exhibit this behavior for every newly-seen IP for the rest of its uptime. It requires no privileged access — any unprivileged client opening a new QUIC connection from a new source IP triggers the vulnerable code path. Existing unit tests (`test_keyed_rate_limiter`, `test_connection_rate_limiter`) don't catch it because they create the prototype and immediately exercise clones within the same test, so `elapsed_since_prototype_creation` is negligible and the bug doesn't manifest in that timeframe.

### Recommendation
In `TokenBucket::clone()`, reset `base_time` to `Instant::now()` and `last_update` to `0` for the new instance (i.e., re-anchor the clock at clone time) rather than copying the prototype's original `base_time`/`last_update`. Equivalently, have `KeyedRateLimiter` construct a fresh bucket from the prototype's *parameters* (`new_tokens_per_us`, `max_tokens`, `tokens` initial value) via a dedicated "new_from_prototype" constructor that calls `Instant::now()` itself, instead of relying on `Clone` to copy time-anchoring fields verbatim.

### Proof of Concept
1. Start a QUIC streamer with `ConnectionRateLimiter::new(limit_per_minute=8, max_burst=80, num_shards=...)` (matching production defaults' ratio in `streamer/src/nonblocking/quic.rs`).
2. Let the process run/idle for ~10+ minutes (no traffic needed) so that `elapsed_since_prototype_creation (µs) * (limit_per_minute/60/1e6)` exceeds `max_burst` (80 tokens ⇒ ~600 seconds at rate 8/60 tokens/sec).
3. From a brand-new source IP never seen before, call `rate_limiter.register_connection(&new_ip)` repeatedly.
4. Observe that the very first bucket created for `new_ip` already contains `max_tokens` (80) rather than `initial_tokens` (8): the caller can immediately register ~80 connections from that single new IP before being throttled, instead of the intended ~8, confirming the 10x burst-capacity bypass caused by the stale `base_time`/`last_update` inherited through `Clone`.

    fn update_state(&self, now: u64) {
        // fetch last update time
        let last = self.last_update.load(Ordering::SeqCst);

        // If time has not advanced, nothing to do.
        if now <= last {
            return;
        }

        // Try to claim the interval [last, now].
        // If we can not claim it, someone else will claim [last..some other time] when they
        // touch the bucket.
        // If we can claim interval [last, now], no other thread can credit tokens for it anymore.
        // If [last, now] is too short to mint any tokens, spare time will be preserved in credit_time_us.
        match self.last_update.compare_exchange(
            last,
            now,
            Ordering::AcqRel,  // winner publishes new timestamp
            Ordering::Acquire, // loser observes updates
        ) {
            Ok(_) => {
                // This thread won the race and is responsible for minting tokens
                let elapsed = now.saturating_sub(last);

                // also add leftovers from previous conversion attempts.
                // we do not care about who uses the spare_time_us, so relaxed is ok here.
                let elapsed =
                    elapsed.saturating_add(self.credit_time_us.swap(0, Ordering::Relaxed));

                let new_tokens_f64 = elapsed as f64 * self.new_tokens_per_us;

                // amount of full tokens to be minted
                let new_tokens = new_tokens_f64.floor() as u64;

                let time_to_return = if new_tokens >= 1 {
                    // Credit tokens, saturating at max_tokens
                    self.add_tokens(new_tokens);
                    // Fractional remainder of elapsed time (not enough to mint a whole token)
                    // that will be credited to other minters
                    (new_tokens_f64.fract() / self.new_tokens_per_us) as u64
                } else {
                    // No whole tokens minted → return whole interval
                    elapsed
                };
                // Save unused elapsed time for other threads
                self.credit_time_us
                    .fetch_add(time_to_return, Ordering::Relaxed);
            }
            Err(_) => {
                // Another thread advanced last_update first → nothing we can do now.
            }
        }
    }

    /// Clones the TokenBucket with approximate state
