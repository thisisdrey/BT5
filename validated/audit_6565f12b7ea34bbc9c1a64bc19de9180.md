### Title
Missing Origin/Auth Validation on Signer Event-Receiver HTTP Server Allows Remote Injection of Forged StackerDB/Block/Burn Events - (File: libsigner/src/events.rs)

### Summary
The `stacks-signer` binary runs an embedded HTTP server (`SignerEventReceiver`) that listens on a network-reachable socket (`endpoint`, e.g. `0.0.0.0:30000` per `sample/conf/signer/mainnet-signer-conf.toml`) to receive `/stackerdb_chunks`, `/proposal_response`, `/new_burn_block`, and `/new_block` POST events from what is assumed to be its paired `stacks-node`. This server accepts and processes any POST request on these paths from any TCP peer that can reach the port — it performs no authentication, no `Authorization`/token check, and no origin/source validation of the caller, unlike the `browserify-hmr` HMR websocket, which likewise failed to validate the origin of incoming connections before trusting their payloads.

### Finding Description
`SignerEventReceiver::next_event` in [1](#0-0)  dispatches based solely on HTTP method and URL path — `/stackerdb_chunks`, `/proposal_response`, `/new_burn_block`, `/new_block`, `/status`, `/shutdown` — and calls `process_event` to deserialize the JSON body directly into signer events, with no check of any credential, token, or peer identity. The `bind()` implementation, [2](#0-1) , simply opens a plain `HttpServer::http(listener)` with no TLS/auth wrapper.

The `auth_token`/`auth_password` mechanism that exists in this codebase (`stacks-signer/src/config.rs`, `stacks-signer/src/client/stacks_client.rs`, and `stackslib/src/net/api/postblock_proposal.rs`) is used only in the opposite direction: it authenticates the *signer's outbound* requests to the *node's* `/v3/block_proposal` RPC endpoint via an `Authorization` header the node checks. It provides no protection for the *signer's own inbound* event-listener socket described above — this is confirmed by the absence of any `auth_token`/`Authorization` reference in `libsigner/src/events.rs` or anywhere in the `SignerEventReceiver`/`EventReceiver` trait implementation.

Because `event_dispatcher_blocking` HTTP POSTs from the node are just plain HTTP over TCP/IP with no mutual authentication and the signer's listening endpoint is commonly bound to `0.0.0.0` (see `sample/conf/signer/mainnet-signer-conf.toml:39`, `endpoint = "0.0.0.0:30000"`), any network-adjacent or WAN-reachable attacker who can reach that port can POST directly to it, bypassing the real `stacks-node` entirely.

The chunk data inside the `StackerDBChunksEvent` payload does carry a `SlotMetadata`/`sig` field that is independently verified downstream against the on-chain-registered signer key (e.g. in `stackslib/src/net/stackerdb/mod.rs:649` `validate_received_chunk`), so an attacker cannot forge *StackerDB chunk contents* accepted as authentic signer messages. However, `/new_burn_block`, `/new_block`, and `/proposal_response` events carry **no signature or provenance check at all** at the transport layer — the equality that should hold ("message originated from my configured, trusted stacks-node") is never verified; only "the JSON parses into the expected type" is checked.

### Impact Explanation
An attacker who can reach the signer's listening endpoint can inject spoofed `/new_burn_block`, `/new_block`, or `/proposal_response` events into the signer's runloop channel (via `forward_event` / `SignerRunLoop::run_one_pass`), potentially confusing the signer's view of burnchain/chain tip state or block-validation outcomes, since these payload types have no cryptographic binding to the real node. This can steer signer decision timing/state off the legitimate chain view, which is a documented out-of-scope area for full analysis (signer decision logic itself), but the *root cause* — the event-receiver's total lack of origin validation — sits squarely in `libsigner/src/events.rs`, which is in-scope. The severity is bounded because slot-owner-signed StackerDB chunk data is separately signature-verified elsewhere, limiting the worst-case impact to non-chunk event types and to information/DoS-style confusion rather than a full forged-chunk propagation.

### Likelihood Explanation
Exploitability depends entirely on network exposure of the signer's listening port. Since sample configs bind to `0.0.0.0` and the transport is plain, unauthenticated HTTP, any operator who follows the sample configuration verbatim (or fails to firewall the signer port) is exposed to any host that can route to that port — no privileged access or node secret is required.

### Recommendation
Add origin/authentication enforcement to `SignerEventReceiver::next_event` in `libsigner/src/events.rs`: require and verify a shared-secret `Authorization` header (mirroring the existing `auth_token`/`auth_password` mechanism already used for the node→signer direction is documented but not enforced on ingestion), and/or bind the listener to a loopback/private interface by default, rejecting requests from any source that doesn't present the configured credential before deserializing untrusted event bodies.

### Proof of Concept
1. Deploy a `stacks-signer` with the sample config (`endpoint = "0.0.0.0:30000"`).
2. From any remote host able to reach TCP port 30000, send:
```
POST /new_burn_block HTTP/1.1
Host: <signer-ip>:30000
Content-Type: application/json
Content-Length: <n>

{"burn_block_hash":"...", "burn_block_height":..., "consensus_hash":"...", ...}
```
3. `SignerEventReceiver::next_event` (`libsigner/src/events.rs:413-458`) accepts this request without any credential check, deserializes it via `process_event::<T, BurnBlockEvent>`, and forwards a `SignerEvent::NewBurnBlock` into the signer's runloop exactly as if it came from the legitimate `stacks-node`, confirming the missing origin/auth validation.

```rust
    fn next_event(&mut self) -> Result<SignerEvent<T>, EventError> {
        self.with_server(|event_receiver, http_server, _is_mainnet| {
            // were we asked to terminate?
            if event_receiver.is_stopped() {
                return Err(EventError::Terminated);
            }
            debug!("Request handling");
            let request = http_server.recv()?;
            debug!("Got request"; "method" => %request.method(), "path" => request.url());

            if request.url() == "/status" {
                request
                .respond(HttpResponse::from_string("OK"))
                .expect("response failed");
                return Ok(SignerEvent::StatusCheck);
            }

            if request.method() != &HttpMethod::Post {
                return Err(EventError::MalformedRequest(format!(
                    "Unrecognized method '{}'",
                    request.method(),
                )));
            }
            debug!("Processing {} event", request.url());
            if request.url() == "/stackerdb_chunks" {
                process_event::<T, StackerDBChunksEvent>(request)
            } else if request.url() == "/proposal_response" {
                process_event::<T, BlockValidateResponse>(request)
            } else if request.url() == "/new_burn_block" {
                process_event::<T, BurnBlockEvent>(request)
            } else if request.url() == "/shutdown" {
                event_receiver.stop_signal.store(true, Ordering::SeqCst);
                Err(EventError::Terminated)
            } else if request.url() == "/new_block" {
                process_event::<T, StacksBlockEvent>(request)
            } else {
                let url = request.url().to_string();
                debug!(
                    "[{:?}] next_event got request with unexpected url {}, return OK so other side doesn't keep sending this",
                    event_receiver.local_addr,
                    url
                );
                ack_dispatcher(request);
                Err(EventError::UnrecognizedEvent(url))
            }
        })?
```
