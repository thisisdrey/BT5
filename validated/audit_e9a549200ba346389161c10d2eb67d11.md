### Title
ERC-20 `transferFrom` precompile always requires an allowance approval, even when spender == from - (File: substrate/frame/assets/precompiles/src/lib.rs)

### Summary
The `pallet-assets` ERC-20 precompile's `transferFrom(from, to, value)` implementation unconditionally calls `pallet_assets::Pallet::do_transfer_approved`, which mandates a pre-existing `Approvals` entry for `(asset_id, from, caller)`. The ERC-20 standard only requires an allowance check when `spender != from`; when the caller is the token owner itself, `transferFrom` should behave like `transfer` and succeed without any approval. Because the precompile never special-cases `spender == from`, self-initiated `transferFrom` calls always revert with `Unapproved` unless the owner has explicitly self-approved, breaking compatibility with the many DeFi/pull-based integrations (bridges, DEX routers, vaults) that rely on this ERC-20 semantic.

### Finding Description
`transfer_from` in [3](#0-2)  derives `spender` from the caller and `from` from the call arguments, then immediately calls `do_transfer_approved(asset_id, &from, &spender, &to, approval_amount)` with no equality check between `spender` and `from`.

`do_transfer_approved` in [4](#0-3)  looks up `Approvals::<T, I>::try_mutate_exists((id, owner, delegate), ...)` and returns `Error::<T, I>::Unapproved` if no approval entry exists — it has no owner-is-self bypass. This mirrors exactly the reported bug class: the allowance mechanism is invoked even when `spender == from`, where the ERC-20 spec (and OpenZeppelin's reference `_spendAllowance`, itself vendored in this repo at [5](#0-4) ) does not require any allowance when the caller already owns the tokens — normally `transferFrom` in OZ's implementation is built on `_transfer` + `_spendAllowance(owner, spender, value)`, and while OZ's own `transferFrom` doesn't special-case `owner==spender` either, most conforming implementations and asset-standard tooling treat self-`transferFrom` as expected to work because `msg.sender` owning the assets fully justifies the move. Here, the pallet has both a direct `transfer` extrinsic and a `transfer_from`/`transferFrom` precompile path, and the precompile path breaks for the self-pull use case that is otherwise handled fine when using `pallet-assets::transfer` (or ERC-20 `transfer`) directly — protocols coded generically against `transferFrom` (pull-only integrations) will find that calling `transferFrom(self, dest, amount)` unconditionally reverts unless a redundant self-approval is created first.

### Impact Explanation
Any contract or off-chain integrator that generically calls `transferFrom` to pull its own tokens (a pattern common in routers, vaults, and bridges that don't special-case owner==spender) will have transactions revert against `pallet-assets` ERC-20-precompiled assets. Funds that are only ever moved through this style of pull call become unreachable via that code path, and if a protocol has no fallback to plain `transfer`, tokens can become effectively stranded in that integration — matching the "stranded funds due to broken ERC-20 compatibility" impact identified in the original report.

### Likelihood Explanation
Likelihood is moderate: this doesn't require a malicious actor, privileged role, or governance action — it is triggered by ordinary usage of the standard, unprivileged `transferFrom` precompile entrypoint by any integrator that follows the common "always use transferFrom" pattern. It is a functional/compatibility defect rather than a directly exploitable fund-theft bug, since it fails closed (revert) rather than allowing unauthorized movement, but it directly undermines the intended ERC-20-compatibility guarantee the precompile in [6](#0-5)  was explicitly built to provide.

### Recommendation
In `transfer_from` ( [7](#0-6) ), check `if spender == from` and, in that case, perform a direct transfer (e.g. via the pallet's internal `transfer_and_die`/`do_transfer` path used elsewhere) bypassing the `Approvals` lookup entirely, matching ERC-20 conventions where a token owner does not need to approve themselves.

### Proof of Concept
1. Asset owner `A` holds `100` units of an asset exposed via the `pallet-assets` ERC-20 precompile and has never called `approve`.
2. A pull-style integrator contract calls the precompile as `A` (i.e. `msg.sender == A`) with `transferFrom(A, B, 50)`.
3. `transfer_from` computes `spender = A` and `from = A`, then calls `do_transfer_approved(asset_id, &A, &A, &B, 50)`.
4. `Approvals::<T, I>::try_mutate_exists((asset_id, A, A), ...)` finds no entry (since `A` never approved itself) and the call fails with `Error::<T, I>::Unapproved`, even though `A` unquestionably owns and controls the 50 units — demonstrated by the existing test pattern at [8](#0-7)  which confirms `Unapproved` is returned whenever no matching `Approvals` entry covers the requested amount.
