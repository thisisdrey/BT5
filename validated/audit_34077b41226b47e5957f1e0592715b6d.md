### Title
Unbounded growth of a delegator's/receiver's delegate-index list allows an attacker to permanently DOS the `GetDelegatedResourceAccountIndexV2` query API - ([File: chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java])

### Summary
`DelegateResourceContract` (and the legacy `FreezeBalanceContract` delegate path) let any account create a new `DelegatedResourceAccountIndex` entry per distinct `(from, to)` pair with essentially no cap on the number of distinct counterparties. Reading that index — via `getV2Index`/`getIndex`, which is directly exposed through the HTTP/gRPC `GetDelegatedResourceAccountIndexV2` API — performs a full prefix scan and in-memory sort over every entry ever created for that address, with cost growing linearly (and with sorting, super-linearly) in the number of entries. This mirrors the Crab Netting bug class: an attacker can cheaply create an unbounded number of list entries (analogous to the deposit/withdraw queue entries) that must all be read back whenever the "queue" (delegate index) is processed, eventually making that read operation impractically expensive or timing out request handling.

### Finding Description
`DelegateResourceActuator.delegateResource()` calls `DelegatedResourceAccountIndexStore.delegateV2(ownerAddress, receiverAddress, now)` on every successful delegate call: [1](#0-0) 

`delegateV2` writes two new keys — one under `V2_FROM_PREFIX+from+to` and one under `V2_TO_PREFIX+to+from`: [2](#0-1) 

Nothing in `DelegateResourceActuator.validate()` limits how many distinct `receiverAddress` values a single owner can delegate to (only a minimum 1 TRX balance and available-frozen-balance checks are enforced): [3](#0-2) 

This is unlike the sibling `UnfreezeBalanceV2Actuator`, which explicitly caps the number of queue-like entries at `UNFREEZE_MAX_TIMES = 32` to prevent exactly this kind of unbounded list growth: [4](#0-3) [5](#0-4) 

Because a single TRX (`TRX_PRECISION`) is enough per delegate call, and freeze/unfreeze cycles (`FreezeBalanceV2`/`UnDelegateResource`) let the same TRX be re-delegated to a fresh address repeatedly, an attacker can accumulate an arbitrarily large number of distinct `(from,to)` index rows over time for one address, cheaply and without bound.

When any client queries that address's delegate index (`GetDelegatedResourceAccountIndexV2`), the store performs a full prefix scan and sort over *all* entries created for that address: [6](#0-5) 

This is precisely the "blank/skip entries must all be read" pattern described in the Crab Netting report — here every historical delegate relationship (even ones later un-delegated only partially, or accumulated over months) must be scanned and sorted on every query, and the number of entries is attacker-controlled and unbounded.

### Impact Explanation
Because `getWithPrefix` is invoked directly from the externally reachable `GetDelegatedResourceAccountIndexV2` HTTP/gRPC endpoints (`GetDelegatedResourceAccountIndexV2Servlet`, `RpcApiService`, and the PBFT/Solidity variants), an attacker who inflates their own delegate-index entry count can make every future query against that address (which may be queried by wallets, explorers, or other users interacting with that address) arbitrarily expensive in CPU/DB read time. Because the list is a full DB prefix scan plus a `Comparator.comparing` sort done synchronously in the API-serving thread, a sufficiently large number of entries can degrade or effectively "freeze" that query path for the given address, which is a node-availability/API-serving impact rather than a fund-theft impact. This is lower severity than the original Crab Netting finding (which could brick core contract accounting), since here it does not corrupt on-chain state or block consensus/block-application — it only degrades a specific read-only API path for addresses the attacker controls. I could not fully verify the real-world magnitude (e.g., typical scan/sort cost at extreme entry counts, whether other rate limits such as bandwidth/energy consumption for repeated `DelegateResourceContract`+`UnDelegateResourceContract` cycles meaningfully throttle the attack in practice) within the available tooling.

### Likelihood Explanation
Reachable purely from ordinary signed transactions (`DelegateResourceContract`) that only require 1 TRX of frozen balance per new receiver and no special privilege, making the growth path easy to trigger repeatedly over time. The attack is however rate-limited by the cost/friction of issuing many separate transactions (bandwidth/energy consumption, and the fact that the frozen TRX must be re-obtained after `UnDelegateResourceContract`/unfreeze cycles), so the practical likelihood of reaching a truly "DOS-level" number of entries is uncertain without further data on per-tx cost versus scan cost growth.

### Recommendation
Add an explicit cap (analogous to `UNFREEZE_MAX_TIMES`) on the number of distinct outstanding delegate relationships (`toAccounts`/`fromAccounts` entries) a single address can accumulate in `DelegatedResourceAccountIndexStore`, or change `getWithPrefix` to support pagination/limits so that a single query cannot be forced to scan and sort an attacker-controlled, unbounded number of rows. Alternatively, prune/garbage-collect index entries whose underlying `DelegatedResourceCapsule` balances have gone to zero, so stale entries do not persist indefinitely.

### Proof of Concept
1. Attacker account `A` freezes the minimum 1 TRX via `FreezeBalanceV2Contract`.
2. Attacker repeatedly issues `DelegateResourceContract(from=A, to=R_i, balance=1 TRX)` to a large number of distinct freshly generated receiver addresses `R_1..R_n`, and optionally `UnDelegateResourceContract` + re-delegate to reuse the same 1 TRX for new targets over time — each call appends new `V2_FROM_PREFIX`/`V2_TO_PREFIX` rows via `delegateV2` [2](#0-1) , unconstrained by any cap in `DelegateResourceActuator.validate()`.
3. Any client calls `GetDelegatedResourceAccountIndexV2` for address `A`, which triggers `getV2Index` → `getWithPrefix`, doing a full prefix scan and sort over all `n` accumulated rows [7](#0-6) .
4. As `n` grows without bound, this query becomes increasingly slow, degrading that API path for address `A`.

  public DelegatedResourceAccountIndexCapsule getV2Index(byte[] address) {
    return getWithPrefix(V2_FROM_PREFIX, V2_TO_PREFIX, address);
  }

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }
