### Title
Unbounded attacker-controlled array length causes OOM/DoS in BatchValidateSign precompile - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `BatchValidateSign` precompiled contract parses calldata-supplied "array length" words and uses them directly to size Java arrays before any bound is enforced, mirroring the TensorFlow Lite `segment_sum` bug where a value taken from input data is used verbatim to size an output allocation, letting an attacker trigger an out-of-memory condition.

### Finding Description
`extractBytes32Array` reads a length word straight out of attacker-controlled calldata and immediately allocates an array of that size, with no validation on the value at the point of allocation: [1](#0-0) 

`extractBytesArray` has the identical pattern: [2](#0-1) 

These helpers are invoked from `BatchValidateSign.doExecute`, which is reached by any TVM contract call to the precompile address. The size cap (`MAX_SIZE`) that would prevent an oversized allocation is only enforced when the `allowTvmSelfdestructRestriction()` hard-fork flag is active; when that flag is off, `extractBytesArray`/`extractSigArray` are called with no upper bound at all, and `extractBytes32Array` is likewise called unconditionally using the same unchecked `words[2]`-derived offset/length: [3](#0-2) 

Because `intValueSafe()` clamps a `DataWord` to an `int` rather than rejecting out-of-range values, an attacker can set the length word to a huge value (e.g., near `Integer.MAX_VALUE`), causing `new byte[len][]` to attempt to allocate billions of array-header slots, which throws `OutOfMemoryError` inside the node's TVM execution path — the same "length field taken from data directly drives allocation size" root cause as the TensorFlow `segment_sum` CVE.

### Impact Explanation
An `OutOfMemoryError` thrown mid-transaction execution inside the TVM can destabilize or crash the node process handling the block/transaction, since Java `OutOfMemoryError`s are not reliably recoverable and can corrupt shared JVM state (thread pools, GC state) used by concurrent block processing. This matches the "node crash or halt" impact bucket for a Medium/High DoS finding, reachable from a single, unprivileged, signed transaction that calls the `BatchValidateSign` precompile.

### Likelihood Explanation
Reachability is high in principle — any address can deploy or call a contract that invokes the precompile with attacker-chosen calldata — but the actual exploitability is gated by the `allowTvmSelfdestructRestriction()` committee-controlled hard-fork switch. If this switch is active on the target network, the `MAX_SIZE` check upstream neutralizes the issue for `signatures`/`addresses`; if it is inactive (e.g., prior to that fork activation, or on a private/test chain that never enables it), both `extractBytesArray` and `extractBytes32Array` remain reachable with fully unbounded lengths. I could not fully verify from the indexed code whether `allowTvmSelfdestructRestriction()` is unconditionally enabled on current mainnet configurations, which affects present-day exploitability.

### Recommendation
Move the `MAX_SIZE` (or equivalent) length validation inside `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` themselves — unconditionally, not gated behind `allowTvmSelfdestructRestriction()` — so that any caller of these helpers is protected regardless of hard-fork activation state. Reject or clamp with an exception path returning `DATA_FALSE`/energy-out before allocating, instead of relying on an external pre-check that can be bypassed when the feature flag is disabled.

### Proof of Concept
1. Deploy a contract that performs a low-level `staticcall`/`call` to the `BatchValidateSign` precompile address with hand-crafted calldata.
2. Set the word at the offset used for the signature-array length (`words[words[1].intValueSafe()/WORD_SIZE]`) to a large value such as `0x7FFFFFFF`.
3. On a network/state where `allowTvmSelfdestructRestriction()` is not active, `doExecute` skips the `MAX_SIZE` pre-check [4](#0-3)  and calls `extractBytesArray`/`extractBytes32Array` with the attacker-supplied length, triggering `new byte[len][]` and an `OutOfMemoryError` during transaction execution [5](#0-4) .

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
