### Title
False StackerDB chunk inventory advertised before the chunk is actually committed, causing a served-vs-stored mismatch - (File: `stackslib/src/net/stackerdb/mod.rs`)

### Summary
`PeerNetwork::handle_unsolicited_StackerDBPushChunk` validates an incoming `StackerDBPushChunk` message's signature/version and, on success, immediately mutates and replies with a `StackerDBChunkInv` that advertises the new, higher `slot_version` as already held by this node [1](#0-0) . The actual write to the on-disk StackerDB (`try_replace_chunk`) does not happen at this point — the message is instead forwarded to the relayer, which performs the write later in `process_stacker_db_chunks`/`process_pushed_stacker_db_chunks` [2](#0-1) . This decouples what the node *tells its neighbors it has* from what it *actually stores*, analogous to the report's core issue of a state-changing operation racing with a concurrent update so that the observed/advertised result no longer matches the true underlying state.

### Finding Description
The StackerDB replication protocol relies on a strict Lamport-clock ordering per slot: `try_replace_chunk` only accepts a chunk if `slot_version > current_stored_version`, otherwise it returns `StaleChunk` [3](#0-2) .

When an unsolicited `StackerDBPushChunk` arrives, `validate_received_chunk` checks the chunk's signature, size, and that its version is `>=` the locally-known `expected_version` (read from the in-memory/DB inventory, not from a lock held across the eventual write) [4](#0-3) . If this check passes, `handle_unsolicited_StackerDBPushChunk` immediately patches the reply inventory's `slot_versions[slot_id]` to the *new* version and sends this `StackerDBChunkInv` back to the sender as an acknowledgment that the chunk is now held [5](#0-4) , before any database write occurs.

The actual persistence happens asynchronously, only when the relayer thread later calls `process_stacker_db_chunks`, which calls `try_replace_chunk` per chunk and silently drops it (continuing the loop) if it now returns `StaleChunk` or another error, e.g., because a competing push for the same slot from a different peer/thread was stored first [6](#0-5) .

Because the pre-write inventory patch and the deferred, possibly-failing write are not atomic with respect to each other, two (or more) validly-signed pushes for the same slot arriving close together can each pass `validate_received_chunk` against the same stale `expected_version`, causing both senders to receive a "success" `StackerDBChunkInv` claiming the new version is stored, while only one of the underlying writes actually succeeds. Any node relying on the acknowledgment (e.g., a neighbor that skips re-requesting the slot because this node's inventory says it already has the newest version) will find that the node does not actually serve that version when queried via `StackerDBGetChunk`.

This is documented as a related, already-observed failure mode in this repository's changelog: `changelog.d/stackerdb-uploaded-chunk-event-loss.fixed` notes that "a StackerDB chunk uploaded over HTTP being stored and acknowledged but never announced to the node's event observers... whenever the relayer fell behind and a peer echoed the same chunk back" , confirming the acknowledge/relayer decoupling is a genuine, previously-hit race window in this exact code path.

### Impact Explanation
StackerDB chunks are used by the Nakamoto signer set to propagate block-signing coordination data (`SignerMessageV0`, `StateMachineUpdate`) which `StackerDBListener` consumes to build its `GlobalStateEvaluator` [7](#0-6) . A false "I already have this version" acknowledgment can cause peers to skip re-fetching a slot's true latest content, stalling propagation of that content across the gossip network — a non-canonical/served-vs-committed inconsistency of the kind called out as High-severity in scope ("steering a node off the tip via false inventory"), here applied to StackerDB inventory rather than the block-inventory case explicitly named.

### Likelihood Explanation
Triggering this only requires sending unsolicited, validly-signed `StackerDBPushChunk` messages (which any two neighbors that legitimately hold or relay a signer's chunk can do, including simply replaying an already-seen valid chunk to race the target node's own relayer), and no additional privileges, secret keys, or admin roles are required to cause the advertise/commit divergence to manifest under ordinary network timing and relayer backpressure — as evidenced by the already-fixed related event-loss bug in the same code path.

### Recommendation
Only construct/send the `StackerDBChunkInv` reply's patched slot version after the chunk has been durably stored (i.e., have the relayer's storage step and the neighbor-facing acknowledgment share the same success/failure result), or otherwise make the inventory read used for both the validation and the reply-generation transactionally consistent with the eventual write outcome, so an inventory advertisement is never sent for a version that failed to persist.

### Proof of Concept
1. Node N is replicating a StackerDB contract with slot 0 currently at version `V`.
2. Two peers, A and B, each independently obtain (via legitimate gossip) a validly-signed chunk for slot 0 at version `V+1` (e.g., because the true owner briefly double-published, or one replays a chunk seen from the other).
3. A and B both push this chunk to N as unsolicited `StackerDBPushChunk` messages in close succession, before N's relayer processes either.
4. `handle_unsolicited_StackerDBPushChunk` runs `validate_received_chunk` for both, and both see `expected_version == V` (since neither write has landed yet), so both pass, and N replies to both A and B with a `StackerDBChunkInv` claiming slot 0 is now at version `V+1` [1](#0-0) .
5. Later, the relayer processes both pushes via `process_stacker_db_chunks`; the first `try_replace_chunk` call succeeds and commits `V+1`, but the second returns `StaleChunk` (since `V+1 <= V+1`) and is silently dropped [6](#0-5) , [8](#0-7) .
6. Both A and B nonetheless already received a "success" acknowledgment from N implying their specific push was accepted and stored — the actual content of N's slot 0 is now whichever chunk won the race, not necessarily the one either A or B believe they confirmed, and downstream neighbors of N that trust N's up-to-date `StackerDBChunkInv` will not re-request slot 0, even though the specific push they made was silently dropped.
