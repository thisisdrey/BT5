### Title
`ExchangeInjectActuator` lacks slippage protection, allowing sandwich attacks on exchange liquidity injection - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java])

### Summary
`ExchangeInjectActuator.execute`/`doValidate` computes the counterpart token amount (`anotherTokenQuant`) required to inject liquidity purely from the exchange pool's current reserve ratio, with no user-supplied minimum/maximum bound. This mirrors the reported `TrufPartner.pay` issue, where liquidity is added to a pool with `lpTokenMinOut`/`amountMin` effectively unenforced, letting a party sandwich the transaction and force an unfavorable liquidity ratio on the injector.

### Finding Description
`ExchangeInjectContract` only carries `owner_address`, `exchange_id`, `token_id`, and `quant` — there is no minimum/maximum bound field for the paired token amount: [1](#0-0) 

In `doValidate`, `anotherTokenQuant` is derived solely from the pool's current `firstTokenBalance`/`secondTokenBalance` at the moment the transaction is processed, using the proportional (Bancor-ratio) formula: [2](#0-1) 

`execute` then repeats the same reserve-ratio computation and deducts `anotherTokenQuant` from the caller's balance/asset: [3](#0-2) 

Contrast this with `ExchangeTransactionActuator`, the swap actuator, which does accept a caller-supplied `expected` bound and enforces it (`anotherTokenQuant < tokenExpected` reverts): [4](#0-3) 

`ExchangeInjectActuator` has no equivalent protection. Any account can be the exchange creator (created via `ExchangeCreateContract`, itself reachable by any signed transaction), and only the creator may call inject: [5](#0-4) 

Because the TRC10 exchange is a public AMM-like pool reachable by any account via `ExchangeTransactionContract` (buy/sell), an attacker can:
1. Front-run the creator's pending `ExchangeInjectContract` transaction with a large `ExchangeTransactionContract` trade that skews the pool's `firstTokenBalance`/`secondTokenBalance` ratio.
2. Let the creator's inject execute at the skewed ratio, forcing them to contribute a distorted amount of the "another" token relative to what they intended (either much more, causing balance-insufficiency revert / wasted attempt, or much less, causing the pool's new liquidity ratio to be unfavorable and extractable).
3. Back-run with an opposite trade to restore the ratio and realize a profit, extracted from the value the creator just injected.

This is functionally identical to the `TrufPartner.pay`→Uniswap `addLiquidity` scenario: liquidity is added to a two-asset AMM pool at whatever ratio exists at execution time, with no caller-enforced bound on the counterpart amount, letting anyone with the ability to place ordinary swap transactions before/after the injection sandwich it.

### Impact Explanation
A successful sandwich lets the attacker extract value from the exchange creator's newly injected liquidity, and/or force the creator's transaction to revert wastefully, without any privileged access — only ordinary signed `ExchangeTransactionContract` transactions are needed. This is a concrete unauthorized value transfer from one account (the injector) to another (the sandwicher) via a core, permissionless on-chain financial primitive (the TRC10 Bancor-style exchange), matching the Medium-severity classification of the original finding.

### Likelihood Explanation
The Bancor-exchange feature (`ExchangeCreateContract`/`ExchangeInjectContract`/`ExchangeTransactionContract`) is public, permissionless, and exposed to any account; the p2p mempool ordering (as with the original Uniswap report) allows an attacker to observe a pending inject transaction and place bracketing trades. No special privileges, malicious-SR/witness behavior, or protocol bugs are required — only mempool visibility and normal transaction issuance, which is realistic on any public chain, including java-tron.

### Recommendation
Add a caller-supplied slippage bound to `ExchangeInjectContract` (e.g., `anotherTokenQuantMin`/`Max`, similar to `expected` in `ExchangeTransactionContract`) and enforce it in `ExchangeInjectActuator.doValidate`/`execute`, reverting if the ratio-derived `anotherTokenQuant` falls outside the caller's acceptable bound at execution time.

### Proof of Concept
1. Account A creates an exchange pool via `ExchangeCreateContract` and becomes its creator.
2. A submits `ExchangeInjectContract(tokenId=X, quant=Q)` intending to add liquidity at the pool's current ratio, expecting to also spend `anotherTokenQuant` of token Y as computed at submission time (per `ExchangeInjectActuator` lines 215-227 in `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`).
3. Before A's transaction is processed, attacker B submits a large `ExchangeTransactionContract` swap (X→Y or Y→X) that shifts `firstTokenBalance`/`secondTokenBalance`, changing the ratio.
4. A's inject transaction executes against the new skewed ratio, causing `anotherTokenQuant` to differ substantially from what A expected — either reverting (insufficient balance) or committing A to an unfavorable ratio.
5. B submits a reverse `ExchangeTransactionContract` swap to restore the ratio, realizing arbitrage profit from A's injected liquidity, exactly as demonstrated in the original report's `test_pay_sandwichAttack` pattern applied to Uniswap `addLiquidity`.
