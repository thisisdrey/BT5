Audit Report

## Title
Dry-run/RPC predicted `CREATE1` contract address diverges from the actual on-chain address due to unconditional nonce adjustment - (File: `substrate/frame/revive/src/exec.rs`)

## Summary
In `pallet-revive`'s `new_frame` instantiate address derivation, the `create1` nonce adjustment (`account_nonce - 1`) is applied whenever `origin_is_caller` is true, without checking whether execution is a real transaction (where the nonce was pre-incremented) or a dry-run/Runtime-API call (where it was not). The repository's own `prdoc/stable2506/pr_8504.prdoc` documents this exact bug and a fix using an `ExecContext` check, but no `ExecContext` type or usage exists anywhere in `exec.rs` — the fix was drafted in documentation but never implemented in code.

## Finding Description
The instantiate address for CREATE1 (`salt = None`) is computed as:
```rust
address::create1(
    &deployer,
    if origin_is_caller {
        account_nonce.saturating_sub(1u32.into()).saturated_into()
    } else {
        account_nonce.saturated_into()
    },
)
``` [1](#0-0) 

The `-1` adjustment is only correct when the nonce has already been incremented pre-dispatch by the real extrinsic pipeline. The `prdoc` explicitly states the intended fix is to gate this on `matches!(exec_context, ExecContext::Transaction)`, distinguishing real dispatch from RPC dry-run: [6](#0-5)  A repository-wide search confirms `ExecContext` exists only in this prdoc text and is absent from the actual `exec.rs` source, meaning the described fix was never merged into the code that executes.

The existing unit test `create1_address_from_extrinsic` exercises `bare_instantiate` only after manually pre-incrementing the nonce via `System::inc_account_nonce`, which does not distinguish a genuine dry-run (no nonce increment) from a real dispatch — so it does not catch the cross-context mismatch. [4](#0-3) 

## Impact Explanation
If reachable as described, any wallet or tool using the Runtime API `instantiate` dry-run to predict a CREATE1 address before submission would get an address one nonce lower than what is actually assigned on real dispatch. Funds or state pre-associated with the predicted address would become permanently stranded relative to the actually-deployed contract, matching the "permanent user-fund lock" impact category.

## Likelihood Explanation
The trigger conditions (`salt = None`, dry-run via Runtime API, `origin_is_caller = true`) are all part of normal, unprivileged, publicly-documented usage patterns (dry-run before submit), requiring no privileged access or malicious behavior — assuming the underlying `origin_is_caller`/nonce-increment discrepancy between the RPC dry-run path and the real dispatch path is confirmed to exist as described, which I was not able to fully verify within available tool calls.

## Recommendation
Introduce an explicit execution-context flag (e.g., `ExecContext::Transaction` vs. dry-run) and gate the nonce subtraction on it, as outlined in `prdoc/stable2506/pr_8504.prdoc`:
```rust
if origin_is_caller && matches!(exec_context, ExecContext::Transaction) {
    account_nonce.saturating_sub(1u32.into()).saturated_into()
} else {
    account_nonce.saturated_into()
}
```
Add a regression test (e.g., `nonce_not_incremented_in_dry_run`) that dry-runs an instantiate call without incrementing the nonce and compares the predicted address against the address produced by an actual signed extrinsic dispatch (which does increment the nonce pre-dispatch), ensuring they match.

## Proof of Concept
1. Query `ReviveApi::instantiate` (Runtime API dry-run) for `ALICE` with `salt = None`, without any prior extrinsic dispatch that would increment `ALICE`'s nonce.
2. Record predicted address `create1(ALICE_H160, N-1)` per the code at `exec.rs:1148-1157`, if `origin_is_caller` is true in this dry-run context and `account_nonce` is still `N` (un-incremented).
3. Submit the real `instantiate_with_code` extrinsic from `ALICE`, which increments the nonce pre-dispatch to `N+1`, yielding actual address `create1(ALICE_H160, N)`.
4. Compare: if the two addresses differ, the divergence is confirmed and any value sent to the predicted address is stranded. This should be codified as a unit test analogous to `create1_address_from_extrinsic` in `substrate/frame/revive/src/tests/pvm.rs`, but explicitly comparing a true dry-run (no nonce pre-increment) call against a subsequent real dispatch, rather than a bare call after manual nonce increment.
