### Title
Unaligned/malformed calldata triggers an uncaught runtime exception in the `ValidateMultiSign` precompile's legacy ABI decoder - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`CVE-2016-1249` describes DBD::mysql crashing with an out-of-bounds read when the number of prepared-statement placeholders is unaligned with the number of output fields. The structural analog in java-tron is the `ValidateMultiSign` TVM precompile, which decodes a raw, attacker-controlled byte array into a variable-length signature array by trusting length/offset words embedded in the calldata itself, without validating that they are internally consistent before the pre-TIP-854 (`allowTvmOsaka`) code path.

### Finding Description
`ValidateMultiSign.execute()` only runs the new bounds check (`isValidAbiEncoding`) when `VMConfig.allowTvmOsaka()` is enabled: [1](#0-0) 

Before that feature flag, calldata is parsed directly via `DataWord.parseArray(rawData)` and fed into `extractSigArray`/`extractBytesArray`, which compute array lengths and offsets purely from words embedded in `rawData` (`words[offset].intValueSafe()`, `words[offset + i + 1].intValueSafe() / WORD_SIZE`) and then call `extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE, len)`: [2](#0-1) 

Because `extractBytes` performs `Arrays.copyOfRange(data, offset, offset + len)` with no bound check against `data.length`, a caller can craft an "unaligned" combination of the declared array length word and the per-item offset/length words (analogous to mismatched placeholder/output-field counts in the CVE) so that the computed `offset`/`offset+len` falls outside `rawData`. This throws an uncaught `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` from inside the decoder, which is not wrapped in a try/catch in the pre-`allowTvmOsaka` path.

The project's own regression test explicitly documents this as expected, unmitigated legacy behavior: [3](#0-2) 

### Impact Explanation
`ValidateMultiSign` is invoked from Solidity via a normal `staticcall`/`call` from any smart contract, i.e. it is reachable by any unprivileged contract deployer/caller through a signed transaction (`TriggerSmartContract`). If the resulting `RuntimeException` is not caught somewhere up the TVM call stack (in `Program`/`VM` operation dispatch) during block application, it can crash the node executing the block or abort transaction processing in a way inconsistent between full nodes, risking a node crash/halt or non-deterministic execution divergence — matching the "node crash or halt" acceptance bar. Because the precompile has "no outer catch" (per the test's own comment), this is a real reachability gap rather than a benign, caught error path.

### Likelihood Explanation
Likelihood is constrained by the `allowTvmOsaka` (TIP-854) feature switch: on networks/forks where this flag is already active, the new `isValidAbiEncoding` guard closes the gap entirely for canonical ABI-shaped calldata. The vulnerability is only live on chains/versions where TIP-854 has not yet activated, and requires crafting calldata that passes the initial `execute()` word extraction but produces internally inconsistent offset/length values deep in `extractSigArray`/`extractBytesArray`. This is a narrow, version-gated condition, so likelihood is limited to specific active-fork configurations rather than universally exploitable on the latest chain state.

### Recommendation
Apply the same `isValidAbiEncoding`/bounds validation unconditionally (not gated behind `allowTvmOsaka`), and add explicit bounds checks inside `extractBytesArray`/`extractSigArray`/`extractBytes` so that any offset/length values derived from calldata are validated against `data.length` before use, returning `Pair.of(false, EMPTY_BYTE_ARRAY)` instead of throwing. Additionally, wrap precompiled-contract `execute()` invocations in `Program`/`OperationActions` with a catch-all that converts any `RuntimeException` into a normal TVM revert rather than letting it propagate.

### Proof of Concept
Construct calldata for `ValidateMultiSign` (via the `validateMultiSign(address,uint256,bytes32,bytes[])` precompile call path) where the header words are well-formed enough to pass the initial parse, but the embedded "signature array length" word combined with a crafted per-item offset word yields a byte range whose `offset + SIG_LENGTH` (or `bytesOffset + bytesLen`) exceeds `rawData.length`, e.g. setting the array-length word to a large positive value while making `rawData` only the minimal 5-word header. This reaches `extractBytes(data, offset, len)` → `Arrays.copyOfRange` with `offset+len > data.length`, throwing `ArrayIndexOutOfBoundsException` before `VMConfig.allowTvmOsaka()` is active — exactly the scenario documented by `testTip854PreActivationNoOp` in `ValidateMultiSignContractTest.java`.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }

  private static byte[][] extractSigArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          SIG_LENGTH);
    }
    return bytesArray;
  }

  private static byte[] extractBytes(byte[] data, int offset, int len) {
    return Arrays.copyOfRange(data, offset, offset + len);
  }
