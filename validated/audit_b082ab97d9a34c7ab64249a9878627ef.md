### Title
Unbounded repository write-lock renewal lets an ordinary pusher perpetually block writes to the same repository - ([File: internal/praefect/datastore/lock_manager.go])

### Summary
The reported QuickSwap/StellaSwap bug works because a cooldown-style timer (`lastLiquidityAddTimestamp`) can be refreshed indefinitely by anyone acting "on behalf of" a target, permanently gating a legitimate action (withdrawal) for that target. Gitaly's `RepoReferenceWriteLockManager` implements an analogous per-repository timer: a PostgreSQL-backed lock keyed only by `(virtualStorage, relativePath)` whose expiry is renewed on demand by whichever transaction currently holds it, with no cap on the number of renewals or on total hold duration.

### Finding Description
`RepoReferenceWriteLockManager.tryLock` acquires an exclusive lock row per repository (`lock_id = virtualStorage|relativePath`) with an `expired_at` set to `NOW() + renewInterval` (20s), and `renew` simply extends `expired_at` by another `renewInterval` on request: [1](#0-0) 

Per `doc/serialized_writes.md`, the lock lifecycle is driven purely by the client-visible reference-transaction phases: `PREPARING_PHASE` acquires the lock, `PREPARED_PHASE` renews it, and only `COMMITTED_PHASE` releases it: [2](#0-1) 

There is no maximum lock hold duration or renewal count enforced anywhere in `tryLock`/`renew`/`Lock` — the lock is only reclaimed by another transaction once `expired_at < NOW()`, i.e., once the holder stops renewing: [3](#0-2) 

Because renewal is gated solely on the caller re-supplying the same `txnID` it was granted at acquisition time (`WHERE locks.lock_id = $1 AND holder_txn_id = $2`), any client that can reach the `PREPARING_PHASE`/`PREPARED_PHASE` voting path for an ordinary push — i.e., any user with normal write access to a repository — can keep voting `Prepared` (or otherwise triggering renewal) indefinitely without ever advancing to `COMMITTED_PHASE`, thereby holding the repository-wide lock forever and starving every other legitimate write transaction for that same repository, which must block in `Lock()` waiting for the row to expire or be released: [4](#0-3) 

This mirrors the AlgebraPool root cause precisely: a caller-controlled action refreshes a timer gating a shared resource, and nothing ties the number/duration of refreshes to a bound tied to actually completing the underlying operation, so the timer can be kept alive forever by an ordinary, otherwise-legitimate actor.

### Impact Explanation
If exploitable, this is a denial of service against a specific repository: once one client's transaction is parked in `PREPARED_PHASE` and keeps renewing, no other client (including legitimate pushes from other users or automated jobs) can ever acquire the write lock for that repository, so all future write RPCs to it stall indefinitely. Because the lock is keyed at the repository level and shared across all Praefect instances via PostgreSQL, this affects the whole cluster's ability to write to the targeted repository, not just one node.

### Likelihood Explanation
Likelihood depends on details this analysis could not fully verify from the indexed code: whether Gitaly/Praefect enforces an outer request or hook-execution deadline that would force the reference-transaction hook process (and thus the client's ability to keep voting `Prepared`) to terminate before it can renew past a bounded number of cycles, and whether `internal/praefect/transactions/manager.go` (not fully reviewed here) imposes any such cap when calling `lock.Renew`. If such a deadline exists and is short/bounded, the practical exploitability is much lower; if it does not exist or can be circumvented (e.g., a client that keeps the underlying git process alive/slow on purpose), the attack is straightforward for any user with ordinary push access.

### Recommendation
Bound the total time (or number of renewals) a single `txnID` may hold the write lock regardless of how frequently it calls `renew`, and/or enforce a hard timeout on the reference-transaction hook / voting round-trip in Praefect so a stalled or malicious client cannot indefinitely keep a transaction in `PREPARED_PHASE`. Track lock-acquisition time (already recorded in `lockAcquiredAt`) and refuse further renewals past an absolute maximum hold duration, forcibly expiring and reclaiming the lock.

### Proof of Concept
Not independently verified end-to-end due to index/tooling constraints (this requires exercising the full Praefect transaction manager and hook path, which needs a running cluster). Conceptually:
1. As an ordinary user with push access, initiate a write transaction against a repository so that Praefect calls `WriteLockManager.Lock` at `PREPARING_PHASE`, acquiring the row in `repository_reference_write_locks`.
2. Keep the client/hook process alive and issue `VoteTransaction` calls carrying `PREPARED_PHASE` (invoking `lock.Renew`) at an interval shorter than 20 seconds, without ever sending `COMMITTED_PHASE`.
3. Observe that any other client attempting to push to the same repository blocks forever in `RepoReferenceWriteLockManager.Lock`, since `expired_at` is continually pushed forward and the row is never deleted.

Given the uncertainty about upstream timeout enforcement noted above, this should be validated against the actual `internal/praefect/transactions/manager.go` control flow and any gRPC/hook deadlines before treating it as confirmed exploitable.

// Lock acquires the write lock for a given virtualStorage, relativePath and txnID,
// blocking until the lock is acquired or ctx is cancelled.
func (r *RepoReferenceWriteLockManager) Lock(ctx context.Context, virtualStorage, relativePath string, txnID uint64,
) (RepoLock, error) {
	for {
		res := r.tryLock(ctx, virtualStorage, relativePath, txnID)
		if res.Err != nil {
			return RepoLock{}, res.Err
		}
		if res.Acquired {
			return RepoLock{Unlock: res.Unlock, Renew: res.Renew}, nil
		}

		select {
		case <-ctx.Done():
			res.Deregister()
			return RepoLock{}, fmt.Errorf("wait for lock: %w", ctx.Err())
		case <-res.NotificationCh:
			// wait for the lock to release
		}
	}
}

// renew extends the expiry of the write lock held by txnID by another renewInterval.
// It returns an error if the lock is not currently held by txnID.
func (r *RepoReferenceWriteLockManager) renew(ctx context.Context, virtualStorage string, relativePath string, txnID uint64) error {
	query := `
UPDATE repository_reference_write_locks as locks
SET  expired_at = (NOW() + $3::interval)
WHERE locks.lock_id = $1 AND holder_txn_id = $2
RETURNING expired_at;
`
	lockID := repoLockID(virtualStorage, relativePath)
	start := time.Now()
	rows, err := r.qc.QueryContext(ctx, query, lockID, txnID, r.renewInterval)
	r.operationDuration.WithLabelValues(virtualStorage, "renew").Observe(time.Since(start).Seconds())
	if err != nil {
		return fmt.Errorf("renew repo reference write lock (executing query): %s, %w", lockID, err)
	}
	defer func() {
		if err := rows.Close(); err != nil {
			r.logger.WithError(err).Error("close rows")
		}
	}()
	if rows.Next() {
		return nil
	}
	if err := rows.Err(); err != nil {
		return fmt.Errorf("renew repo reference write lock (iterating rows): %s, %w", lockID, err)
	}
	return fmt.Errorf("renew repo reference write lock (no rows): %s", lockID)

```markdown
`internal/praefect/transactions/manager.go` owns the lock lifecycle. A
repository-scoped write lock backed by PostgreSQL is acquired, renewed, and
released according to the phase of each `VoteTransaction` call:

| Phase            | Action                                                  |
|------------------|---------------------------------------------------------|
| `PREPARING_PHASE`| `WriteLockManager.Lock` — block until exclusive access  |
| `PREPARED_PHASE` | `lock.Renew` — keep the lock alive across phases        |
| `COMMITTED_PHASE`| `lock.Unlock` — release once the write is durable       |

If any phase fails before commit, the deferred
`unlockRepoForTransaction` releases the lock so the next transaction can
proceed. Transactions that are explicitly stopped or canceled
(`StopTransaction`, `cancelTransaction`) also release the lock to avoid
stranding it in PostgreSQL.
```
