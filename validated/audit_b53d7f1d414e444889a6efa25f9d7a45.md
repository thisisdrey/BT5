Audit Report

## Title
Outbound Queue V2 settles and rewards delivery regardless of on-chain execution `success` flag - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
`Pallet::process_delivery_receipt` decodes a `DeliveryReceipt` containing a `success: bool` field (sourced directly from the Ethereum `InboundMessageDispatched` event) but never inspects it before finalizing settlement. It unconditionally pays the relayer's fee reward and removes the `PendingOrder`, emitting `MessageDelivered`, whether the corresponding commands actually executed successfully on Ethereum or reverted.

## Finding Description
The Ethereum Gateway contract emits `InboundMessageDispatched(nonce, topic, success, reward_address)` to allow settlement logic to distinguish successful vs. failed command execution, and this is decoded into `DeliveryReceipt.success` [2](#0-1) . However, `process_delivery_receipt` only checks `T::GatewayAddress::get() == receipt.gateway` and that a `PendingOrder` exists for `receipt.nonce`; it never reads `receipt.success` before paying `order.fee` to the reward account, removing `PendingOrders::<T>::remove(nonce)`, and emitting `Event::MessageDelivered` [1](#0-0) . The module documentation describing the delivery-receipt flow ("verify... fetch pending order... pay reward... remove the order") likewise makes no mention of branching on execution outcome [3](#0-2) , confirming the success/failure distinction is absent from the implementation rather than deliberately handled elsewhere. Existing guards (`GatewayAddress` equality, `PendingOrders` existence) validate provenance and nonce uniqueness only — neither prevents a receipt reporting `success == false` from settling identically to a successful one.

## Impact Explanation
Because `PendingOrders::<T>::remove(nonce)` is irreversible and `MessageDelivered` fires unconditionally, any consumer of that event or of `PendingOrders` absence will treat the message as fully executed on Ethereum even when the underlying commands reverted. There is no retry, reconciliation, or distinct failure-settlement path, so this produces a permanent bridge-state mismatch — the message is marked "delivered" on Substrate while the intended cross-chain effect (e.g., asset unlock/mint) never happened on Ethereum — falling squarely under "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically."

## Likelihood Explanation
This requires no malicious actor — only an ordinary command execution failure on Ethereum (e.g., insufficient gas, reverting downstream call) combined with an honest relayer submitting the resulting valid receipt exactly per the documented flow. `T::Verifier::verify` and `DeliveryReceipt::try_from` succeed regardless of the `success` value, since they only validate proof authenticity, not the semantic outcome. No test in `outbound-queue-v2/src/test.rs` exercises the `success == false` case.

## Recommendation
In `process_delivery_receipt`, branch on `receipt.success`: only pay the reward and finalize/remove the `PendingOrder` when `true`; on `false`, emit a distinct event (e.g., `MessageDeliveryFailed`) and route to explicit failure handling (retain for reconciliation/refund) instead of silently treating it as success.

## Proof of Concept
1. A message is queued via `do_process_message`, creating `PendingOrder { nonce, fee, block_number }` in storage.
2. On Ethereum, the Gateway's forwarded commands revert (e.g., insufficient gas from `GasMeter::maximum_dispatch_gas_used_at_most`), but the Gateway still emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer obtains a valid proof for this event and calls `submit_delivery_receipt`.
4. Verification succeeds (the proof legitimately proves a failed execution); `DeliveryReceipt::try_from` decodes `success: false`.
5. `process_delivery_receipt` ignores `success`, pays `order.fee`, calls `<PendingOrders<T>>::remove(nonce)`, and emits `MessageDelivered { nonce }` — identical to the successful path, despite the Ethereum-side effect never occurring.
