### Title
Nonce reuse via TOCTOU race between `window.Check` and `window.Update` in `ConnectionState.Decrypt` - (File: `connection_state.go`)

### Summary
`ConnectionState.Decrypt` performs the replay-window admission check (`window.Check`) and the replay-window commit (`window.Update`) as two separate critical sections under `decryptLock`, with `DecryptDanger` (the AEAD open call) executed in between while the lock is released. When Nebula's multiple UDP read routines concurrently deliver two packets bearing the same `header.RemoteIndex` and the same `header.MessageCounter` for the same live `HostInfo`/`ConnectionState`, both goroutines can pass `Check` before either calls `Update`, allowing `DecryptDanger` to run twice for the same nonce.

### Finding Description
An unprivileged attacker sends UDP packets whose header sets `RemoteIndex` to a value matching a currently-live `hostinfo.remoteIndexId` (this is an unauthenticated 32-bit index looked up via `f.hostMap.QueryIndex(h.RemoteIndex)` in `outside.go`, with no cryptographic binding at this stage) and sets `MessageCounter` to an arbitrary/duplicated value. `readOutsidePackets` (outside.go:93,126) looks up the `HostInfo` purely by this attacker-controlled index and calls `hostinfo.ConnectionState.Decrypt(f.l, h.MessageCounter, out, packet, nb)` without any additional serialization per hostinfo.

Inside `Decrypt` (connection_state.go:61-82):
```go
cs.decryptLock.Lock()
result := cs.window.Check(l, messageCounter)
cs.decryptLock.Unlock()
...
out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
...
cs.decryptLock.Lock()
result = cs.window.Update(l, messageCounter)
cs.decryptLock.Unlock()
```
The lock is released between `Check` and `Update`, so two concurrent invocations of `Decrypt` with the identical `messageCounter` value against the same `ConnectionState` can both observe `Check` returning `true` (neither has marked the counter as seen yet), then both proceed to call `DecryptDanger` with that same `messageCounter` (used as the AEAD nonce) — one with the attacker's crafted first ciphertext and one with a second, different ciphertext delivered concurrently (e.g., a genuine retransmitted/duplicated legitimate packet, or two attacker-forged packets riding the spoofed index). Only after decryption does either goroutine call `Update`, by which point the AEAD `Open` call has already executed twice under the same key/nonce pair.

Concurrent execution of `readOutsidePackets` for the same `ConnectionState` is architecturally possible because Nebula's UDP reader routines are per-queue/per-core (multiple `listenOut`/reader goroutines share the same `f.hostMap` and dispatch to `readOutsidePackets` independently), and nothing in the packet-lookup path (`QueryIndex`, the length check, or `Decrypt` itself) serializes processing per `HostInfo`. The replay-window `Check`/`Update` split is the only guard against duplicate counters, and it is not atomic.

### Impact Explanation
Reusing an AEAD nonce (the `messageCounter`) with two different plaintexts under the same key is a classic keystream-collision scenario: for AEAD ciphers like AES-GCM/ChaCha20-Poly1305, encrypting/decrypting two different messages under the same (key, nonce) leaks the XOR of the two plaintexts and can allow forgery of subsequent ciphertexts (authentication break) once the keystream is recovered. Here the primitive is used in "decrypt" direction (`DecryptDanger`), so the attacker cannot directly choose the AEAD keystream, but running `Open` twice on the same nonce with two attacker-influenced ciphertexts is a session-crypto invariant violation that undermines the confidentiality/integrity guarantees Nebula relies on for that tunnel (`ConnectionState.dKey`), matching a "traffic decryption/replay/session crypto integrity" impact class.

### Likelihood Explanation
Preconditions: (1) attacker can send arbitrary UDP packets to the victim (standard unprivileged network attacker capability — no cert/keys/CA needed since `RemoteIndex` is an unauthenticated lookup key), (2) the victim process has more than one concurrent UDP-read execution path for the same `HostInfo` (true for Nebula's multi-queue design), (3) the attacker can cause two `Decrypt` calls with the same `messageCounter` to race — achievable by flooding duplicate packets with the same counter value in a tight burst, exploiting normal network jitter/duplication or multiple sockets. This is a genuine, repeatable concurrency bug rather than a one-shot exploit, and is amplified under load (more queues, higher packet rates).

### Recommendation
Make the replay-window check-and-commit atomic with respect to `DecryptDanger`: hold `decryptLock` across `Check`, `DecryptDanger`, and `Update` as a single critical section (or use a CAS-style `Bits.CheckAndUpdate` that atomically reserves the counter before returning success), so that only one goroutine can ever proceed to `DecryptDanger` for a given `messageCounter`. Equivalently, reserve the slot in `window` (mark-as-in-progress) inside the same locked section as `Check`, and roll back on `DecryptDanger` failure.

### Proof of Concept
Add a concurrency/invariant test in `connection_state_test.go`:
1. Construct a `ConnectionState` with a real `dKey`/`eKey` pair (as in existing tests) and a fresh `Bits` window.
2. Wrap/instrument `cs.dKey` (or use a counting shim satisfying `noiseutil.CipherState`) so `DecryptDanger` records every `(nonce, invocationID)` pair it is called with into a shared, mutex-protected slice.
3. Prepare two distinct valid ciphertexts (e.g., two different plaintexts encrypted with `eKey`/matching `dKey` setup) but craft both packets to carry the identical `messageCounter` value `N`.
4. Launch many goroutines (e.g., 100) calling `cs.Decrypt(l, N, ...)` concurrently, split between the two ciphertext variants, using a `sync.WaitGroup`/barrier to maximize the race window between `Check` and `Update`.
5. Assert: across all goroutines, `DecryptDanger` is recorded as invoked with nonce `N` **at most once** (`len(recordedCalls[N]) <= 1`). Run under `go test -race` and repeat (e.g., loop the test body) to reliably surface the failure; with the current split-lock implementation, `DecryptDanger` will be observed invoked more than once for nonce `N`, violating the invariant and failing the assertion — demonstrating the nonce-reuse race.
