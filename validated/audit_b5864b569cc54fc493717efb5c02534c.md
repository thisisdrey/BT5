Based on the code, this attack path is already mitigated by several layered defenses in the QUIC ingress path, so I'm rejecting this finding.

#No Vulnerability found for this question.

**Why the described attack doesn't hold up:**

1. **Concurrent uni-stream limit is enforced at the QUIC protocol layer, not just application-level accounting.** When a connection is admitted, `SwQos::cache_new_connection` calls `connection.set_max_concurrent_uni_streams(max_uni_streams)` where `max_uni_streams` comes directly from `compute_max_allowed_uni_streams_with_rtt`, before any streams are accepted. [1](#0-0)  This is a `quinn`/QUIC transport-level `MAX_STREAMS` limit — the peer's QUIC stack is physically prevented from opening more concurrent uni streams than this bound, regardless of how many the attacker "requests" at the application layer. The bound is capped even under RTT scaling: `QUIC_MAX_STAKED_CONCURRENT_STREAMS` (512) or `QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS` (128), scaled by at most `MAX_RTT_MS/REFERENCE_RTT_MS = 350/50 = 7x`. [2](#0-1) [3](#0-2)  This directly answers the "PoC idea" in the question: `active_streams` is already provably bounded by the value computed in `compute_max_allowed_uni_streams_with_rtt`, since quinn refuses additional stream opens beyond that limit.

2. **Per-stream data is bounded regardless of trickle rate.** `handle_chunks` accumulates `accum.meta.size` across chunks and immediately closes the entire connection with `CONNECTION_CLOSE_CODE_INVALID_STREAM` if it exceeds `max_stream_data_bytes`, so a stream cannot accumulate unbounded bytes no matter how slowly they trickle in. [4](#0-3) 

3. **Idle/slow streams are killed by a timeout.** Each `read_chunks` call is wrapped in `tokio::time::timeout(wait_for_chunk_timeout, ...)`; if a stream doesn't yield any chunk within that window it's torn down and `active_streams` decremented. [5](#0-4)  This is directly validated by the existing test `test_quic_stream_timeout`. [6](#0-5) 

4. **New-stream opening rate is separately throttled** via `throttle_stream`/`ConnectionStreamCounter` token-bucket in `on_new_stream`, independent of the concurrent-stream cap. [7](#0-6) 

Given (1) a hard, protocol-enforced ceiling on concurrent uni streams per connection, (2) a per-stream byte cap, and (3) an idle-stream timeout, per-connection memory from `PacketAccumulator`s is bounded by `max_concurrent_uni_streams * max_stream_data_bytes`, which is a small, fixed multiple (low single-digit MB), not unbounded growth. The scenario described (thousands of concurrent streams per connection bypassing these bounds) is not reachable given the existing `set_max_concurrent_uni_streams` call made before any streams can be accepted.

fn compute_max_allowed_uni_streams_with_rtt(
    rtt_millis: u32,
    peer_type: ConnectionPeerType,
    total_stake: u64,
) -> u32 {
    let streams = match peer_type {
        ConnectionPeerType::Staked(peer_stake) => {
            // No checked math for f64 type. So let's explicitly check for 0 here
            if total_stake == 0 || peer_stake > total_stake {
                warn!(
                    "Invalid stake values: peer_stake: {peer_stake:?}, total_stake: \
                     {total_stake:?}"
                );

                QUIC_MIN_STAKED_CONCURRENT_STREAMS
            } else {
                let delta = (QUIC_TOTAL_STAKED_CONCURRENT_STREAMS
                    - QUIC_MIN_STAKED_CONCURRENT_STREAMS) as f64;

                (((peer_stake as f64 / total_stake as f64) * delta) as u32
                    + QUIC_MIN_STAKED_CONCURRENT_STREAMS)
                    .clamp(
                        QUIC_MIN_STAKED_CONCURRENT_STREAMS,
                        QUIC_MAX_STAKED_CONCURRENT_STREAMS,
                    )
            }
        }
        ConnectionPeerType::Unstaked => QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS,
    };
    // scale amount of streams based on RTT if RTT is larger than REFERENCE_RTT_MS
    // multiply first then divide to avoid rounding errors.
    (streams.saturating_mul(rtt_millis.clamp(REFERENCE_RTT_MS, MAX_RTT_MS))) / REFERENCE_RTT_MS
}
