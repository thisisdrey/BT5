### Title
Unauthenticated `RecvError` packets let a spoofing attacker repeatedly tear down established tunnels - (File: outside.go)

### Summary
`RecvError` is one of the two packet types nebula processes before any decryption or certificate/handshake verification. `readOutsidePackets` dispatches it directly to `f.handleRecvError` from the "Unencrypted packets" switch, with no cryptographic authentication of the sender at all. [1](#0-0) 

### Finding Description
`handleRecvError` only gates on a local config toggle (`ShouldRecvError`, which just checks whether the address is private/always/never) and then looks up the target `HostInfo` purely by the cleartext `h.RemoteIndex` field carried in the (unauthenticated, unencrypted) packet header: [2](#0-1) 

The only "authentication" performed is comparing the spoofable UDP source address of the incoming packet against the hostinfo's currently known remote address: [3](#0-2) 

Both values used for this check are attacker-controllable or observable without holding any CA-signed certificate:
- `h.RemoteIndex` is a 32-bit index transmitted in cleartext in the header of every packet on the wire (see `header.H` handling in `readOutsidePackets`), so any on-path/off-path observer who can see even one packet exchanged between two peers (or who brute-forces the 32-bit space) obtains a valid index.
- The UDP source address comparison (`hr != addr`) provides no protection against basic UDP source spoofing, since UDP has no source-address integrity.

Once index+address are supplied, `handleRecvError` unconditionally calls `f.closeTunnel(hostinfo)` and `f.handshakeManager.DeleteHostInfo(hostinfo)` — mutating live tunnel state (deleting the `HostInfo` from both the main hostmap and the pending handshake map) with no signature, MAC, or handshake-derived key check whatsoever: [4](#0-3) 

This mirrors the reported bug class: a state-mutating function reachable without proper access control, callable repeatedly by an unauthenticated party to drive victim state to an attacker-chosen value (here: forcibly tearing down/reset established tunnels), analogous to repeatedly zeroing `withdrawReserve` in the original report. The CHANGELOG shows the project has already had to patch adjacent `recv_error` abuse ("Disable sending `recv_error` messages when a packet is received outside the allowable counter window", #1459), indicating this attack surface has a known history of soft-authentication issues. [5](#0-4) 

### Impact Explanation
An attacker with no valid certificate, who can merely observe or guess a live tunnel's `RemoteIndex` and spoof the peer's UDP source address, can repeatedly send crafted `RecvError` packets to force `closeTunnel`/`DeleteHostInfo` on either endpoint. This is a remote, unauthenticated denial-of-service against established Nebula tunnels: it can be triggered repeatedly (no rate limit, no proof-of-possession of any key material), continuously disrupting connectivity between legitimate peers — analogous to the H-26 report's "keep calling the function... to keep decrementing state to zero," except here the "state" being repeatedly zeroed is the victim's live tunnel/hostmap entry.

### Likelihood Explanation
Likelihood is moderate: the attacker must know (or guess) a live `RemoteIndex`, but this value travels in cleartext in every packet header, so any attacker positioned to observe even a single packet between the two peers (e.g., a network intermediary, or anyone who can capture UDP traffic to/from the target) obtains it directly. UDP source-address spoofing is a well-established, low-cost attack primitive. No cryptographic secret is required.

### Recommendation
Do not allow `RecvError` (or any unauthenticated packet type) to directly mutate authoritative tunnel state such as `closeTunnel`/`DeleteHostInfo`. Options:
- Require the `RecvError` to be authenticated against the tunnel's derived symmetric keys (e.g., AEAD-tag it like relay/message packets) before acting on it, rather than trusting a bare index + best-effort address match.
- Rate-limit/backoff `RecvError` processing per remote index/address.
- Treat `RecvError` as a hint to attempt re-handshake rather than an unconditional command to destroy the existing session, avoiding destructive action from an unauthenticated signal alone.

### Proof of Concept
1. Establish a legitimate tunnel between hosts A and B; observe (via a capture point, or a brute-force loop) any packet exchanged between them to learn its cleartext `RemoteIndex` (present in every packet header).
2. From attacker-controlled infrastructure, craft a UDP packet with `Type = header.RecvError` and `RemoteIndex` set to the observed index, and spoof the UDP source address to match B's known remote address (`hostinfo.GetRemote()`), sending it to A.
3. `readOutsidePackets` dispatches this straight to `f.handleRecvError` (no decrypt/auth step for `RecvError`), and since the spoofed `addr` matches `hr`, the code proceeds to `f.closeTunnel(hostinfo)` and `f.handshakeManager.DeleteHostInfo(hostinfo)`, destroying A's session with B. [6](#0-5) 
4. Repeat at will — there's no cryptographic gate preventing the attacker from issuing this again for any newly re-established tunnel, causing sustained denial-of-service.

Note: I could not fully verify the entropy/predictability of `generateIndex()` (its implementation is generated via a random source per the standard nebula design, presumably `crypto/rand` in `handshake_manager.go`, but I did not get to inspect its exact source before running out of iterations) — this affects how easily an attacker can *guess* an index versus needing to *observe* one on the wire. The core finding (unauthenticated destructive state mutation via `RecvError`) stands regardless, since observation of cleartext headers alone is sufficient.

```go
func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
```
