### Title
Irrevocable single-step `AccountPermissionUpdateContract` can permanently freeze an account's funds and lock out its owner role - (File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java)

### Summary
`AccountPermissionUpdateContract` lets an account replace its `owner`, `witness`, and `active` permissions (including the keys and threshold used to authorize all future transactions) in a single atomic transaction with no confirmation/acceptance step by the new key holders, exactly the "missing two-step transfer" bug class described in the referenced report for the `dao` role.

### Finding Description
`AccountPermissionUpdateActuator.execute` unconditionally overwrites the account's owner/witness/active permissions supplied in the contract, with no verification that the newly designated keys can actually produce a valid signature for the account, and no pending/staged state requiring the new keys to "accept" the change: [1](#0-0) 

`validate()` only checks structural constraints (key count, threshold vs. weight sum, distinct addresses, valid address format, permitted contract-type bitmap for `active` permission) — it never checks that the caller (or anyone) actually controls the private keys being installed as the new `owner`/`active` permission: [2](#0-1) 

Because the `owner` permission is the only permission capable of calling `AccountPermissionUpdateContract` again, and the `active` permission is required to authorize ordinary operations (transfers, contract calls, resource delegation, etc.), a single mistaken or malicious transaction that sets the `owner` permission's keys to addresses the account does not control makes the permission structure unrecoverable — there is no rollback, no second signature/acceptance step from the new key holder(s), and no way to reclaim the `owner` role, mirroring the `setDao`-style single-step role transfer flaw in the referenced report.

### Impact Explanation
If the `owner` permission is set to keys not controlled by the account holder (typo, phishing, or a compromised active key with restricted-but-sufficient operation bitmap), the account permanently loses the ability to ever change permissions again. If the `active` permission is similarly bricked, the account can no longer sign any ordinary transaction, permanently freezing all TRX/TRC10/resources held by that account — satisfying the "permanent freezing of funds" impact bar, since java-tron provides no recovery mechanism (no two-step confirm/claim) for this contract type.

### Likelihood Explanation
`AccountPermissionUpdateContract` is a normal broadcastable transaction type reachable by any account through the public HTTP/gRPC API (`AccountPermissionUpdateServlet` / `wallet.createTransactionCapsule`) and requires only that the transaction be signed by keys currently satisfying the account's own `owner` permission threshold — i.e., any account holder (or anyone who compromises/coerces the necessary signing keys) can trigger it in one step: [3](#0-2) 
This is an entirely ordinary, frequently-used feature (multi-sig setup/rotation), increasing the chance of an unrecoverable mistake, and there is no dynamic property or check gating it beyond `AllowMultiSign`: [4](#0-3) 

### Recommendation
Introduce a two-step process for `AccountPermissionUpdateContract` changes to the `owner` (and ideally `active`) permission: stage the proposed new permission set and require a follow-up transaction signed by the new keys (meeting the new threshold) to "accept"/activate it before it takes effect, analogous to OpenZeppelin's `Ownable2Step` pattern recommended in the source report. At minimum, add a proof-of-possession/acceptance signature requirement for any new `owner` permission keys before committing the change in `AccountCapsule.updatePermissions`.

### Proof of Concept
1. Account `A` (using default single-key owner permission) broadcasts an `AccountPermissionUpdateContract` transaction signed with its current owner key, setting the new `owner` permission's key list to an address `B` that nobody controls (e.g., a typo'd address), and/or setting the `active` permission similarly.
2. `AccountPermissionUpdateActuator.validate()` passes all structural checks (valid address format, weight sum ≥ threshold) since these do not verify key custody.
3. `AccountPermissionUpdateActuator.execute()` commits `updatePermissions` unconditionally.
4. Account `A` can no longer produce a transaction meeting the new `owner`/`active` permission threshold, permanently losing the ability to change permissions or move funds — with no recovery path in the protocol.
