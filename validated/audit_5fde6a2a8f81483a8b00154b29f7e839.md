### Title
`LinkRepositoryToObjectPool` links any repository to any attacker-reachable object pool without verifying they belong to the same repository/fork network - ([File: internal/gitaly/service/objectpool/link.go])

### Summary
The `LinkRepositoryToObjectPool` RPC accepts an arbitrary `Repository` and an arbitrary `ObjectPool`, and — provided the two happen to reside in the same partition — links them via the repository's Git alternates without ever verifying that the `ObjectPool` was actually created from, or is otherwise legitimately associated with, that specific `Repository`. This is structurally the same defect as the reported `VoterProxy.deposit` bug: a mutating RPC accepts two caller-supplied identifiers (`_token`/`_gauge` there, `Repository`/`ObjectPool` here) and performs a privileged linking operation on them without validating that the pair is a legitimate/compatible combination.

### Finding Description
`LinkRepositoryToObjectPool` only validates that the target repository is a valid git repository and that the referenced object pool directory is a valid pool repository: [1](#0-0) 

`poolForRequest` resolves the pool purely from the request's `ObjectPool.Repository` path and checks only that it is a syntactically/structurally valid pool directory (`ErrInvalidPoolDir` / `ErrInvalidPoolRepository`) — it never checks that this pool is the one that was created from, or is otherwise associated with, the caller's target `Repository`: [2](#0-1) 

`Link()` itself only checks whether the repository already has an alternates file pointing somewhere else; if not, it happily writes the caller-supplied pool's path into the repository's `objects/info/alternates` file and triggers deduplication: [3](#0-2) 

The only structural constraint that limits which pools can be linked is that the target repository and the object pool repository must reside in the **same partition** on the same storage (`ErrRepositoriesInDifferentStorages`, `ErrRepositoriesAreInDifferentPartitions`): [4](#0-3) 

This partition co-location, however, is not an authorization mechanism — it is only meant to make WAL transactions atomic. Nothing in `LinkRepositoryToObjectPool` cross-checks project/fork-network identity, ownership, or that the object pool's `origin` corresponds to the linked repository. The RPC comment itself documents that the caller is trusted to pass a coherent pool/repository pair, i.e., there is no server-side compatibility check analogous to the recommended `ICurveGauge(_gauge).withdraw(_amount)` returns the correct `_token` check in the report: [5](#0-4) 

### Impact Explanation
If a caller (e.g. GitLab Rails acting on behalf of a project owner, or any actor able to reach this RPC with a repository/pool pair placed in the same partition) can get their own repository and someone else's pool — or an unrelated pool — into the same partition (for example via `CreateFork`'s partitioning hint mechanism, or simply by naming an already-known object pool relative path that happens to share a partition), they can link their repository to that foreign pool. Once linked:
- The repository gains read access to every object contained in the foreign pool via the Git alternates mechanism — a cross-repository/cross-tenant object disclosure.
- Because `Link()` performs deduplication (`removeMemberBitmaps`) and future repacks will physically dedupe against the pool, this can also corrupt or destabilize the target repository's storage layout, and interacting RPCs like `DisconnectGitAlternates`/`FetchIntoObjectPool` assume a legitimate pool relationship exists.
- Combined with `DeleteObjectPool`'s explicit lack of safety checks (per its own doc comment), a malicious link could make later pool deletion corrupt an unrelated repository.

This matches the "cross-repository object access" acceptance criterion in the validation rules.

### Likelihood Explanation
Exploitation requires the attacker-controlled repository and the target object pool to be placed in the same Gitaly partition. In the normal flow this only happens for actual fork/pool relationships (via `CreateFork`'s implicit partitioning hint or explicit partitioning hint metadata), constraining ordinary exploitation. However, the RPC handler itself performs **no compatibility check** between the two objects at all — the security boundary rests entirely on the partition-assignment side effect rather than an explicit authorization/compatibility check in `LinkRepositoryToObjectPool`, which is the exact structural weakness flagged in the external report (missing whitelisting/compatibility validation between two attacker-suppliable IDs performing a privileged action). Any change to partitioning behavior, or any caller with the ability to supply a partitioning hint pointing at a foreign repository's relative path, would directly enable the described impact.

### Recommendation
In `LinkRepositoryToObjectPool` (and `poolForRequest`), explicitly validate that the supplied `ObjectPool` is actually the pool associated with the given `Repository`'s fork network/origin — e.g., by checking a persisted mapping created by `CreateObjectPool`/`CreateFork`, or by requiring the caller to prove origin membership — rather than relying solely on partition co-location as an implicit authorization signal. This mirrors the report's recommendation to check that `_token`/`_gauge` are a compatible, whitelisted pair before performing the privileged operation.

### Proof of Concept
Conceptual PoC (cannot be executed in ask-only mode, described for a Devin session to verify):
1. Create repository A and object pool P as an established origin/member pair using `CreateObjectPool`.
2. As a different, unrelated caller, create repository B such that it is placed in the same partition as P (e.g., via `CreateFork`'s partitioning hint mechanism referencing P's relative path, or another partitioning-hint-capable RPC).
3. Call `LinkRepositoryToObjectPool` with `Repository = B`, `ObjectPool = P`.
4. Observe that the call succeeds without any error even though B has no legitimate relationship to P, and that objects exclusive to P become readable from B via `objects/info/alternates`, as demonstrated by the existing test `TestMiddleware_partitioning_hint`, which links an artificially-partitioned fork to an unrelated pool successfully: [6](#0-5)

```go
func (s *server) LinkRepositoryToObjectPool(ctx context.Context, req *gitalypb.LinkRepositoryToObjectPoolRequest) (*gitalypb.LinkRepositoryToObjectPoolResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	pool, err := s.poolForRequest(ctx, req)
	if err != nil {
		return nil, err
	}

	repo := s.localRepoFactory.Build(repository)

	if err := pool.Link(ctx, repo); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	return &gitalypb.LinkRepositoryToObjectPoolResponse{}, nil
```

```go
func (s *server) poolForRequest(ctx context.Context, req PoolRequest) (*objectpool.ObjectPool, error) {
	pool, err := objectpool.FromProto(ctx, s.logger, s.locator, s.gitCmdFactory, s.catfileCache, s.txManager, s.housekeepingManager, req.GetObjectPool())
	if err != nil {
		if errors.Is(err, objectpool.ErrInvalidPoolDir) {
			return nil, errInvalidPoolDir
		}

		if errors.Is(err, objectpool.ErrInvalidPoolRepository) {
			return nil, structerr.NewFailedPrecondition("%w", err)
		}

		return nil, structerr.NewInternal("%w", err)
	}

	return pool, nil
```

```go
// Link will link the given repository to the object pool. This is done by writing the object pool's
// path relative to the repository into the repository's "alternates" file. This does not trigger
// deduplication, which is the responsibility of the caller.
func Link(ctx context.Context, pool, repo *localrepo.Repo, txManager transaction.Manager) (returnedErr error) {
	altPath, err := repo.InfoAlternatesPath(ctx)
	if err != nil {
		return err
	}

	expectedRelPath, err := getRelativeObjectPath(ctx, pool, repo)
	if err != nil {
		return err
	}

	linked, err := linkedToRepository(ctx, pool, repo)
	if err != nil {
		return err
	}

	if linked {
		// When the repository is already linked to the repository, cast a vote to ensure the
		// repository is consistent with the other replicas.
		if err := transaction.VoteOnContext(ctx, txManager, voting.VoteFromData([]byte("repository linked")), voting.Synchronized); err != nil {
			return fmt.Errorf("vote on linked repository: %w", err)
		}

		return nil
	}
```
