### Title
Arbitrary `unlocker` address in `LoansNFT.lock()` lets a narrowly-approved address hijack investor cashflow routing - ([File: tare-io__tare-contracts/contracts/LoansNFT.sol])

### Summary
`LoansNFT.lock(address unlocker, uint256 id)` accepts any non-zero `unlocker` address from any account that is "authorized" per ERC721 semantics — which includes not just the token owner but also a **per-token `approve()`d address** — with no allowlist or scope restriction on what `unlocker` may be. Once set, `Loans.investorWithdraw()` treats `unlocker` as fully trusted: it routes *all* principal and interest cashflows for the locked loan to `msg.sender == unlocker` and blocks both the investor and admin from withdrawing. This mirrors the reported pattern exactly — an unprivileged caller supplies an arbitrary address that the protocol then blindly trusts to control a critical operation (here, fund routing) without validating that the address is the one the investor actually intended to receive that capability.

### Finding Description
`lock()` in `LoansNFT.sol` is guarded only by `_isAuthorized(tokenOwner, msg.sender, id)`: [1](#0-0) 

The code comment explicitly acknowledges the authorization surface is broader than the ERC-5753 reference: "owner or operator... per-token approved addresses may also lock" [2](#0-1) . This is demonstrated by the test showing a plain `approve()`d address (not `setApprovalForAll`) can call `lock()` directly and choose any unlocker: [3](#0-2) 

Once locked, `Loans.investorWithdraw()` routes cash exclusively to the stored `unlocker`, and the investor/admin are explicitly rejected: [4](#0-3) 

This is confirmed by test assertions that only the unlocker (not the investor or admin) can withdraw once a loan is locked: [5](#0-4) 

An ERC721 `approve()` grant is conventionally understood by users/integrators to authorize **transfer** of a single token to a designated marketplace/counterparty (e.g., to interact with `LoansExchange`, which internally locks to itself via a hardcoded address: `LOANS_NFT.lock(address(this), uint256(loanId))`). However, because `lock()` accepts any caller with per-token approval and does not restrict which `unlocker` value that caller may choose, the approved address can bypass the intended flow (e.g., listing through the exchange) and instead call `LoansNFT.lock()` directly with an attacker-chosen `unlocker`, redirecting all future investor withdrawals for that loan to itself or a colluding address — without ever transferring the NFT and without the investor's knowledge, until the investor notices withdrawals are blocked.

### Impact Explanation
This diverts investor loan cashflows (principal and interest) to an unintended address, which the audit scope explicitly recognizes as an allowed impact ("Theft, diversion, or unauthorized reassignment of ... loan cashflows ... from honest users"). It also permanently blocks the investor (and admin) from withdrawing legitimate proceeds until the malicious unlocker calls `unlock()`, which they have no incentive to do — a practical, unprivileged-path lock of claimable cashflows.

### Likelihood Explanation
Any investor who grants a narrow, per-token `approve()` to a counterparty for a specific integration (e.g., listing on a marketplace, or a bilateral escrow arrangement outside `LoansExchange`) is exposed, since the approved party can call `lock()` on `LoansNFT` directly rather than going through the intended integration contract. This requires no privileged role and no cooperation from the investor beyond a standard, seemingly-benign `approve()` call.

### Recommendation
Restrict `lock()` so that plain per-token `approve()`s cannot invoke it with an arbitrary `unlocker`. Options: (1) require `msg.sender == tokenOwner || isApprovedForAll(tokenOwner, msg.sender)` (drop bare per-token approval as sufficient authorization for locking), or (2) require the caller to *be* the `unlocker` (i.e., `msg.sender == unlocker`), which matches the documented intent of "integrators lock listed loans with narrow per-token approvals" (the integrator locks to itself, not to an arbitrary third party) and closes the ability for an approved party to redirect cashflow to a different address than itself.

### Proof of Concept
1. Investor calls `loansNFT.approve(marketplaceX, loanId)` intending `marketplaceX` to use the standard listing flow.
2. Instead, `marketplaceX` (or anyone it delegates to) calls `loansNFT.lock(attackerAddress, loanId)` directly — this succeeds because `_isAuthorized` accepts the per-token approval, and `lock()` places no restriction on the `unlocker` parameter (see `test_Lock_SucceedsWhenCalledByApprovedOperator`, `tare-io__tare-contracts/test/LoansNFT/unit/LoansNFT_Lockable.t.sol:72-82`).
3. Servicer processes payments normally into the loan's ledger.
4. `attackerAddress` calls `loans.investorWithdraw([loanId], ...)`; per `Loans.sol:864-877`, the recipient is `msg.sender` (the unlocker), not the investor. The investor's principal/interest is now paid to `attackerAddress`, and the investor/admin cannot withdraw it (per `Loans_UnlockerWithdraw.t.sol:92-118`, `test_unlockerWithdraw_revertsWhenCallerIsNotUnlocker`).

```text
  /**
   * @inheritdoc ILockable
   * @dev Authorization is intentionally broader than the ERC-5753 reference
   *      implementation (owner or operator): per-token approved addresses may also
   *      lock. This lets integrators such as `LoansExchange` lock listed loans with
   *      narrow per-token approvals instead of requiring `setApprovalForAll`.
   */
  function lock(address unlocker, uint256 id) external {
    address tokenOwner = ownerOf(id);

    require(unlocker != address(0), InvalidUnlocker());
    require(_unlockers[id] == address(0), AlreadyLocked());
    require(_isAuthorized(tokenOwner, msg.sender, id), Unauthorized());

    // Clear approval
    _approve(address(0), id, address(0), false);
    _unlockers[id] = unlocker;

    emit Lock(unlocker, id);
  }
```
