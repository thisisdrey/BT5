### Title
Missing content-hash verification of `Attachment` payload against requested `content_hash` allows AtlasDB poisoning and permanent unresolved `AttachmentInstance` - (stackslib/src/net/atlas/download.rs, stackslib/src/net/api/getattachment.rs)

### Summary
`AttachmentsDownloader` never checks that the `Attachment` bytes returned by a peer actually hash to the `content_hash` that was requested. `extend_with_attachments` blindly inserts whatever `Attachment` a peer returns, and `insert_instantiated_attachment` stores it in the AtlasDB keyed by the attachment's own (self-reported) hash rather than the hash that was demanded. A malicious peer can therefore make the node permanently store useless/garbage data and leave the real, requested `content_hash` unresolved.

### Finding Description
`AttachmentRequest::get_most_reliable_source` / `Requestable::get_url` for `AttachmentRequest` selects a single "most reliable" peer URL to send the `GET /v2/attachments/{content_hash}` request to [1](#0-0) . The HTTP response is decoded by `decode_atlas_get_attachment`, which only parses JSON into a `GetAttachmentResponse { attachment }` — there is no comparison of `Hash160::from_data(&attachment.content)` against the request's `content_hash` [2](#0-1) .

`extend_with_attachments` then unconditionally inserts the returned `Attachment` into `self.attachments` on success, with no equality check against `request.content_hash`: [3](#0-2) 

In the FSM completion handler, each drained attachment is looked up and persisted using **its own** hash, not the hash that triggered the request: [4](#0-3) 

`insert_instantiated_attachment` unconditionally writes the attacker-supplied bytes to the `attachments` table keyed by `attachment.hash()` and only updates `attachment_instances.is_available` for rows whose `content_hash` equals that same (attacker-controlled) hash: [5](#0-4) 

Since the legitimate, confirmed `AttachmentInstance` was recorded with `content_hash = H1` (from on-chain event data, via `queue_attachment_instance`/`check_attachment_instances`), and the attacker's bogus payload hashes to H2 (H2 != H1), the `UPDATE ... WHERE content_hash = ?1` never touches the row for H1. `AttachmentsBatch::resolve_attachment` is also called with `attachment.hash()` (H2), so the batch's tracked missing entry for H1 is never removed — it is left in `attachments_batch.attachments_instances` and gets bumped/retried until `max_attachment_retry_count` is exhausted, after which the batch is dropped entirely: [6](#0-5) .

Because `AttachmentRequest` only queries one peer at a time (`get_most_reliable_source`), the exact "two simultaneous fake peers on one HTTP response" scenario in the prompt does not occur within a single round — but the same effective outcome is achieved across retries: on retry N the most-reliable peer may be attacker A (answers with H2), on retry N+1 a different attacker B may become most-reliable (answers with H3). Each retry poisons the DB with an unrelated attachment row and never resolves H1, until retries are exhausted and H1's instance is permanently left with `is_available = 0`.

### Impact Explanation
- Any single unprivileged peer that a node queries for an attachment can return arbitrary bytes; the node will accept them as "instantiated" attachment content and store them under the attacker-chosen hash of that content, regardless of what was actually requested — a form of unauthenticated write to node storage (`attachments` table) with attacker-controlled hash/content.
- The requested `content_hash` (backed by a real, confirmed `AttachmentInstance` from on-chain BNS data) is never marked available, so legitimate zonefile/BNS data can never be served for that instance — "attachment/BNS mismatch" and permanently missing legitimate data.
- Repeatable per retry/round for as many distinct content hashes as the attacker wants to serve (up to `connection_options.max_attachment_retry_count` retries per batch, but new batches for new content hashes are unbounded), causing unbounded growth of the `attachments` table with junk data (`insert_instantiated_attachment` has no dedup/size accounting comparable to `insert_uninstantiated_attachment`'s eviction path).
- Matches "High" — attachment/BNS mismatch (serving/failing to serve canonical BNS-referenced data) plus storage growth from unauthenticated writes.

### Likelihood Explanation
- Requires only that the node treats the attacker as an "outbound sync peer" with a data URL, i.e. attacker just needs to be a peer the node queries for `/v2/attachments/inv` and `/v2/attachments/{hash}` — no secret, no privileged role, no StackerDB slot, purely public P2P/RPC surface.
- No signature, MAC, or size validation ties the HTTP attachment response to the requested hash; the request itself is a public unauthenticated GET.
- The attack is cheap: a single crafted HTTP JSON response per attempt; repeatable across retries/batches, and multiple colluding malicious peers increase the chance of being selected as "most reliable" over time (reliability scoring is based on request counts, not correctness of content).

### Recommendation
In `extend_with_attachments` (or immediately after `decode_atlas_get_attachment`), verify `Hash160::from_data(&response.attachment.content) == request.content_hash` before inserting into `self.attachments`; discard and mark the peer's report as a failed request otherwise. Additionally, in the `AttachmentsBatchStateMachine::Done` handler, use the originally requested hash (not `attachment.hash()`) to resolve entries in `attachments_batch` and to look up `find_all_attachment_instances`, and reject persisting any `Attachment` whose computed hash does not match the hash that was requested for that download slot.

### Proof of Concept
```rust
// stackslib/src/net/atlas/tests.rs (illustrative)
#[test]
fn test_bogus_attachment_hash_mismatch_leaves_instance_unresolved() {
    // H1: legitimate, on-chain-confirmed AttachmentInstance content_hash
    let real_attachment = new_attachment_from("facade01");
    let h1 = real_attachment.hash();
    let instance = new_attachment_instance_from(&real_attachment, 0, 1); // content_hash = h1

    let attachments_batch = new_attachments_batch_from(vec![instance.clone()], 0);
    let peers = new_peers(vec![
        ("http://attacker-a:20443", 1, 1),
        ("http://attacker-b:30443", 1, 1),
    ]);
    let context =
        AttachmentsBatchStateContext::new(attachments_batch, peers, &ConnectionOptions::default());

    // Build the single AttachmentRequest for h1 (as get_prioritized_attachments_requests would)
    let request = new_attachment_request(
        vec![("http://attacker-a:20443", 1, 1)],
        &h1,
        1,
    );

    // Attacker A responds with bogus content hashing to H2 (H2 != H1)
    let bogus = new_attachment_from("deadbeef");
    assert_ne!(bogus.hash(), h1);

    let mut results = BatchedRequestsResult::new(HashMap::new());
    results.succeeded.insert(
        request.clone(),
        Some(fake_get_attachment_response(bogus.clone())), // constructs 200 OK w/ GetAttachmentResponse{attachment: bogus}
    );

    let context = context.extend_with_attachments(&mut results);

    // BUG: bogus attachment (hash H2) is accepted despite request.content_hash == H1
    assert!(context.attachments.contains(&bogus));

    // Simulate DB persistence path as in AttachmentsDownloader::run
    let mut atlasdb = AtlasDB::connect_memory(AtlasConfig::new(false)).unwrap();
    atlasdb.queue_attachment_instance(&instance).unwrap();
    // mark instance checked, as check_queued_attachment_instances would for "not found"
    atlasdb.mark_attachment_instance_checked(&instance, false).unwrap();

    for attachment in context.attachments.iter() {
        // uses attachment.hash() (H2), NOT h1
        atlasdb.insert_instantiated_attachment(attachment).unwrap();
    }

    // Assert: legitimate instance for H1 is still unresolved
    let unresolved = atlasdb.count_unresolved_attachment_instances().unwrap();
    assert_eq!(unresolved, 1, "H1 instance must remain is_available=0 despite a stored bogus attachment for H2");

    // Assert: DB now contains a junk row for H2 that has nothing to do with H1
    assert!(atlasdb.find_attachment(&bogus.hash()).unwrap().is_some());
    assert!(atlasdb.find_all_attachment_instances(&h1).unwrap().iter().all(|i| !i_is_available(i)));
}
```
This demonstrates the broken equality (`served attachment hash == requested content_hash` is never checked), the poisoned DB row at the attacker-chosen hash, and the permanently unresolved legitimate `AttachmentInstance` at `content_hash = H1`.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }

    pub fn insert_instantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let tx = self.tx_begin()?;
        tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)",
            params![attachment.hash(), attachment.content, now],
        )?;
        tx.execute(
            "UPDATE attachment_instances SET is_available = 1 WHERE content_hash = ?1 AND status = ?2",
            params![attachment.hash(), AttachmentInstanceStatus::Checked],
        )?;
        tx.commit()?;
        Ok(())
    }
