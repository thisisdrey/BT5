### Title
Unchecked zero-value divisor (`TotalNetWeight`/`TotalEnergyWeight`) in `UnDelegateResourceActuator.execute()` and `UnDelegateResourceProcessor.execute()` may yield NaN/Infinity-derived resource usage values - (File: `actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java`, `actuator/src/main/java/org/tron/core/vm/nativecontract/UnDelegateResourceProcessor.java`)

### Summary
Both the `UnDelegateResourceContract` actuator (reachable by any signed transaction) and its TVM-precompile counterpart `UnDelegateResourceProcessor` (reachable via the `unDelegateResource` native contract call from any deployed smart contract) compute a resource "transfer usage" by dividing by `dynamicStore.getTotalNetWeight()` / `dynamicStore.getTotalEnergyWeight()` (or `repo.getTotalNetWeight()` / `repo.getTotalEnergyWeight()`) without validating that these divisors are non-zero, unlike the analogous, hardened calculation in `EnergyProcessor.calculateGlobalEnergyLimitV2()` which explicitly guards `if (totalEnergyWeight == 0) return 0;`.

### Finding Description
`UnDelegateResourceActuator.execute()` computes: [1](#0-0) [2](#0-1) 

These lines take `dynamicStore.getTotalNetWeight()` / `dynamicStore.getTotalEnergyWeight()` as the divisor of a `double` expression (`(double)(...) / dynamicStore.getTotalNetWeight()`), with no prior check that the divisor is non-zero. The identical unguarded pattern also exists in the TVM-precompile version of this logic, `UnDelegateResourceProcessor.execute()`: [3](#0-2) [4](#0-3) 

This directly mirrors the reported bug class: an external/mutable numeric value used as a divisor in a downstream calculation without validating it is non-zero. The codebase itself proves this is a recognized risk that must be handled — `EnergyProcessor.calculateGlobalEnergyLimitV2()` explicitly checks for the zero case before dividing: [5](#0-4) 

and `RepositoryImpl.calculateGlobalEnergyLimit()` uses an `assert totalEnergyWeight > 0` guard (plus a `<= 0` short-circuit) before performing the same kind of division: [6](#0-5) 

However, `UnDelegateResourceActuator`/`UnDelegateResourceProcessor` skip this validation entirely. Because the divisor is used inside a `double` division (`(double) x / weight`), a zero divisor does not throw an `ArithmeticException` (as integer division would); instead it silently produces `Infinity` (if numerator ≠ 0) or `NaN` (if numerator is 0). When such a value is subsequently cast to `long` via `(long) (...)`, Java's numeric-conversion rules turn `Infinity` into `Long.MAX_VALUE` and `NaN` into `0`. This value is used to compute `unDelegateMaxUsage`, which is combined via `min(...)` with `transferUsage` and then written into the receiver account's `NetUsage`/`EnergyUsage` fields, which back further bandwidth/energy accounting for that account.

### Impact Explanation
If `TotalNetWeight`/`TotalEnergyWeight` were ever to reach zero (or an unexpected inconsistency temporarily drove it to zero) while delegated resources still exist, the unchecked division produces `Long.MAX_VALUE`/`0` derived garbage values that get written into account bandwidth/energy usage state via `receiverCapsule.setNetUsage(...)` / `receiverCapsule.setEnergyUsage(...)` — an on-chain accounting/resource-state corruption reachable from an ordinary `UnDelegateResourceContract` transaction or a TVM `unDelegateResource` precompile call. This falls into "unbacked resource accounting" / state corruption territory consistent with the audit report's underlying bug class (unchecked divisor causing wrong/undefined calculation results in a value that flows into user-facing state).

### Likelihood Explanation
Likelihood is lower than the original oracle-price finding because `TotalNetWeight`/`TotalEnergyWeight` are chain-wide aggregates that are hard for a single unprivileged account to drive to exactly zero under normal network conditions (they track network-wide frozen TRX). However, the code path itself is reachable by any account holding delegated resources issuing an ordinary transaction (`UnDelegateResourceContract`) or by any smart contract invoking the `unDelegateResource` native precompile, and the missing guard is a genuine deviation from the pattern the codebase otherwise enforces elsewhere for the same computation (`EnergyProcessor`, `RepositoryImpl`).

### Recommendation
Add the same defensive check used elsewhere in the codebase (e.g., `EnergyProcessor.calculateGlobalEnergyLimitV2()`) before dividing by `dynamicStore.getTotalNetWeight()` / `dynamicStore.getTotalEnergyWeight()` (and the `repo.getTotalNetWeight()` / `repo.getTotalEnergyWeight()` equivalents in `UnDelegateResourceProcessor`), short-circuiting to a safe value (e.g., `0`) when the divisor is `<= 0`, instead of relying on `double` division semantics to silently produce `Infinity`/`NaN`.

### Proof of Concept
1. An account has delegated bandwidth/energy resources to a receiver (`UnDelegateResourceActuator`/`UnDelegateResourceProcessor` code paths at [7](#0-6)  are reached).
2. If `dynamicStore.getTotalNetWeight()` (or `getTotalEnergyWeight()`) is `0` at execution time, the expression `(double)(dynamicStore.getTotalNetLimit()) / dynamicStore.getTotalNetWeight()` evaluates to `Infinity`.
3. `unDelegateMaxUsage = (long) ((double) unDelegateBalance / TRX_PRECISION * Infinity)` evaluates to `Long.MAX_VALUE`.
4. This flows through `min(unDelegateMaxUsage, transferUsage)` and is subtracted into `receiverCapsule.setNetUsage(newNetUsage)`, corrupting the receiver's recorded bandwidth/energy usage state without any exception being raised or validated against.

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
