### Title
Out-of-bounds read in `InputZipFile::ProcessCentralDirEntry` from unvalidated central-directory length fields - (File: `third_party/ijar/zip.cc`)

### Summary
`third_party/ijar/zip.cc` implements the ZIP/JAR parser used by ijar/`zipper` to read attacker-suppliable ZIP central directory records without validating that declared length fields stay inside the mapped input file, unlike the sibling local-file-header parser in the same file.

### Finding Description
`InputZipFile::ProcessLocalFileEntry` calls `EnsureRemaining()` before consuming `file_name_length_` and `extra_field_length_` bytes: [1](#0-0) . `EnsureRemaining` compares the requested length against `input_file_->Length() - (p - zipdata_in_)` and errors out if the read would run past the end of the mmap'd buffer: [2](#0-1) .

`InputZipFile::ProcessCentralDirEntry`, however, reads `file_name_length`, `extra_field_length`, and `file_comment_length` directly from the untrusted central directory bytes and never calls `EnsureRemaining` before advancing `p` by these attacker-controlled 16-bit lengths, nor before the `memcpy` that copies `file_name_length` bytes from `p` into the fixed `filename` buffer: [3](#0-2) . The `while (extra_p != p)` loop that parses the "extra field" TLV entries is similarly unchecked — it reads a 2-byte `header_id` and `data_size` from `extra_p` via `get_u2le`, which itself performs no bounds checking (`get_u2le`/`get_u4le`/`get_u8le` just dereference `p[0]`, `p[1]`, ... with no length check): [4](#0-3) . If `data_size` is crafted so `extra_p` never lands exactly on `p`, the loop can walk past the mapped file boundary reading attacker-uncontrolled/unmapped memory.

`FindZipCentralDirectory` only validates that `central_dir_offset + central_dir_size <= in_length` for the central directory *as a whole* [5](#0-4) ; it does not validate that any individual entry's `file_name_length`/`extra_field_length`/`file_comment_length` keeps `p` within that region. A single entry near the end of the central directory (or of the file) with an inflated length field can therefore push `p`/`extra_p` past the end of the `mmap`-ed input file, producing an out-of-bounds read (and potential `SIGSEGV`/crash, or leakage of adjacent heap/mmap memory into the copied `filename` buffer, which is subsequently used in `processor->Accept`/`processor->Process` callbacks).

This is directly analogous to the reported CGAL `SM_io_parser::read_vertex()`/`set_first_out_edge()` bug class: a length-prefixed record format is parsed with fields trusted from the file without validating them against the buffer bounds, causing OOB reads that feed into subsequent processing.

### Impact Explanation
The affected code is compiled into the `ijar`/`zipper` tool that Bazel uses to build interface jars and to extract/pack zip archives as part of normal build actions (`ijar`, `singlejar`/`zipper` binaries under `third_party/ijar`). A jar or zip file supplied by an unprivileged party (e.g., a maliciously crafted artifact fetched as a build dependency) can be parsed by this code as part of a build. The bug reads memory outside of the intended buffer — a memory-safety violation in native C++ code, potentially crashing the build tool (worker-side denial of impact aside) or, depending on heap layout, disclosing adjacent memory contents through the extracted `filename`/emitted entries.

### Likelihood Explanation
The parsed bytes are entirely attacker-controlled (arbitrary ZIP/JAR content), and the vulnerable function is reached on every entry of every central directory processed by `ijar`/`zipper` — no exotic conditions are required beyond crafting one entry with a length field larger than the remaining buffer. No authentication or special privilege is required; the attacker only needs to get such a file consumed as an input to a build (an unprivileged/external content-supply scenario matching the required threat model).

### Recommendation
Add explicit bounds checks in `InputZipFile::ProcessCentralDirEntry` (and in the `get_u*le` extra-field parsing loop) analogous to `EnsureRemaining()` in `ProcessLocalFileEntry`: validate `file_name_length`, `extra_field_length`, and `file_comment_length` against the number of bytes actually remaining in the mapped file (or within the known central-directory region) before advancing `p`/`extra_p` or performing the `memcpy`, and bound the extra-field TLV loop so `data_size` cannot walk `extra_p` past `p`/the buffer end.

    size_t in_offset = p - zipdata_in_;
    size_t remaining = input_file_->Length() - in_offset;
    if (n > remaining) {
      return error("Premature end of file (at offset %zd, state=%s); "

                   in_offset, state, n, remaining);
    }
    return 0;
