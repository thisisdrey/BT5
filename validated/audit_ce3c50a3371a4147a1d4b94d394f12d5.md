### Title
`LinkRepositoryToObjectPool` links arbitrary repositories to any object pool without verifying fork/origin relationship - ([File: internal/gitaly/service/objectpool/link.go])

### Summary
`ObjectPoolService.LinkRepositoryToObjectPool` accepts any `Repository` and any `ObjectPool` and links them together, performing only existence/format validation. There is no check that the target repository is actually part of the object pool's fork network or was ever associated with the pool's `origin` at `CreateObjectPool` time. This mirrors the reported bug class: a lower-level "factory"-like operation (`Link`) can be invoked directly to bypass the implicit ownership/registry relationship that the higher-level workflow (`CreateObjectPool` from a specific `origin`, followed by intentional linking of only fork-network members) is supposed to enforce.

### Finding Description
`CreateObjectPool` creates a pool repository tied to a specific `origin` repository [1](#0-0) . The pool is meant to be linked only to repositories that are part of the same fork network as that origin, per the documented lifecycle in the proto: "One or more repositories are linked to the object pool via LinkRepositoryToObjectPool" [2](#0-1) .

However, `LinkRepositoryToObjectPool`'s handler performs no verification that the repository being linked has any relationship to the pool's `origin` or fork network — it only validates that the repository exists and that the pool resolves to a valid Git repository: [3](#0-2) 

The pool lookup helper `poolForRequest` simply resolves the object pool by its `ObjectPool.Repository` path via `objectpool.FromProto`, with no binding back to the repository that originally created it: [4](#0-3) 

The underlying `Link` function then unconditionally writes the pool's path into the caller-specified repository's `objects/info/alternates` file, making all pool objects visible to that repository: [5](#0-4) 

This is structurally identical to the reported bug class: `MIMOProxyFactory.deployFor()` could be called directly, bypassing the `MIMOProxyRegistry` that was supposed to gate proxy creation/registration. Here, `LinkRepositoryToObjectPool` (the "factory-adjacent" operation) can be called directly against any pool/repository pair, bypassing the implicit registry/ownership relationship that `CreateObjectPool`'s `origin` field and the fork-network model are supposed to establish.

### Impact Explanation
Linking an unrelated repository to an object pool grants that repository read access (via Git alternates) to every object contained in the pool, including objects belonging to the pool's original (possibly private) origin repository and any other repository already linked to it. Since the RPC does no ownership check, any caller able to invoke this Gitaly RPC with knowledge of (or ability to guess/enumerate) a pool's storage name and relative path can cause cross-repository object disclosure — objects from a private/unrelated project become fetchable through the linked repository (e.g., via `GetObjectPool`/`CommitService` reads against the now-linked repo, as demonstrated by the existing test asserting pool objects become visible after `Link`) [6](#0-5) .

### Likelihood Explanation
Gitaly is the trust boundary here: whether this is exploitable by an "ordinary" actor depends entirely on whether the caller of `ObjectPoolService.LinkRepositoryToObjectPool` (normally GitLab Rails, orchestrating the fork-creation flow) itself enforces that the linked repository is part of the correct fork network before issuing the RPC. Gitaly's own service layer performs zero such enforcement, so any defect or omission in that upstream authorization — or any direct/crafted RPC invocation carrying a `target_repository`/`additional_repository` pair — is sufficient to trigger the cross-repository linkage described above. The complete lack of a same-fork-network or origin-relationship check inside Gitaly itself is the root cause and mirrors exactly the "factory can circumvent registry" pattern from the source report.

### Recommendation
Add a check inside `LinkRepositoryToObjectPool` (or in `objectpool.Link`) that verifies the repository being linked is a legitimate member of the object pool's fork network — e.g., by recording and checking the object pool's `origin`/allowed-members relationship (the existing `relational.ObjectPoolStateManager`/`PoolStore` membership tracking could be leveraged for this) before writing to the alternates file, rather than relying solely on the caller (Rails) to have performed this authorization check.

### Proof of Concept
1. Repository A (private, sensitive objects) is used to create object pool P via `CreateObjectPool{ObjectPool: P, Origin: A}` [7](#0-6) .
2. An attacker-controlled/unrelated repository B (no fork relationship to A) issues `LinkRepositoryToObjectPool{ObjectPool: P, Repository: B}`.
3. The handler only checks that B exists and P resolves to a valid repository, then calls `pool.Link(ctx, B)` [8](#0-7) , writing P's object directory into B's `objects/info/alternates` [9](#0-8) .
4. Any object present in pool P (originating from private repository A) is now readable through repository B via any object-reading RPC (e.g., `CommitService`), as shown by the existing `TestLink` test which confirms pool commits become visible to the linked repository after the call [10](#0-9) .

func (s *server) CreateObjectPool(ctx context.Context, in *gitalypb.CreateObjectPoolRequest) (*gitalypb.CreateObjectPoolResponse, error) {
	if in.GetOrigin() == nil {
		return nil, errMissingOriginRepository
	}

	poolRepo := in.GetObjectPool().GetRepository()
	if poolRepo == nil {
		return nil, errMissingPool
	}

	if !storage.IsPoolRepository(poolRepo) {
		return nil, errInvalidPoolDir
	}

	// repoutil.Create creates the repositories in a temporary directory. This means the repository is not created in the location
	// expected by the transaction manager. This makes sense without transactions, but with transactions, there's no real point in
	// doing so given a failed transaction's state is anyway removed. Creating the repository in a temporary directory is problematic
	// as the reference transaction hook is invoked for the repository from unexpected location, causing the transaction to fail to
	// associate the reference updates with the repository.
	//
	// Run the repository creation without the transaction in the context. The transactions reads the created repository's state from
	// the disk when committing it, so it's not necessary to capture the updates from the reference-transaction hook. This avoids the
	// problem for now, and later with transactions enabled by default we can stop creating repositories in unexpected locations.
	ctxWithoutTransaction := storage.ContextWithTransactionID(ctx, 0)
	if err := repoutil.Create(ctxWithoutTransaction, s.logger, s.locator, s.gitCmdFactory, s.catfileCache, s.txManager, s.repositoryCounter, poolRepo, func(poolRepo *gitalypb.Repository) error {
		if _, err := objectpool.Create(
			ctxWithoutTransaction,
			s.logger,
			s.locator,
			s.gitCmdFactory,
			s.catfileCache,
			s.txManager,
			s.housekeepingManager,
			&gitalypb.ObjectPool{
				Repository: poolRepo,
			},
			s.localRepoFactory.Build(in.GetOrigin()),
		); err != nil {
			return err
		}

		return nil
	}, repoutil.WithSkipInit()); err != nil {
		return nil, structerr.New("creating object pool: %w", err)
	}

//
// 1. An object pool is created via CreateObjectPool from its primary pool member. Typically this
//    would be the repository that gets forked.
// 2. One or more repositories are linked to the object pool via LinkRepositoryToObjectPool. Each
//    object pool member linked to the repository will have its objects deduplicated when its

//    reason to do this for any repositories except for the primary object pool member in case it
//    for example becomes private.
// 5. When the object pool does not have any members anymore it gets deleted via DeleteObjectPool.
//    It is the responsibility of the caller to ensure that it really has no members left, else

func (s *server) LinkRepositoryToObjectPool(ctx context.Context, req *gitalypb.LinkRepositoryToObjectPoolRequest) (*gitalypb.LinkRepositoryToObjectPoolResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	pool, err := s.poolForRequest(ctx, req)
	if err != nil {
		return nil, err
	}

	repo := s.localRepoFactory.Build(repository)

	if err := pool.Link(ctx, repo); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	return &gitalypb.LinkRepositoryToObjectPoolResponse{}, nil
}

func (s *server) poolForRequest(ctx context.Context, req PoolRequest) (*objectpool.ObjectPool, error) {
	pool, err := objectpool.FromProto(ctx, s.logger, s.locator, s.gitCmdFactory, s.catfileCache, s.txManager, s.housekeepingManager, req.GetObjectPool())
	if err != nil {
		if errors.Is(err, objectpool.ErrInvalidPoolDir) {
			return nil, errInvalidPoolDir
		}

		if errors.Is(err, objectpool.ErrInvalidPoolRepository) {
			return nil, structerr.NewFailedPrecondition("%w", err)
		}

		return nil, structerr.NewInternal("%w", err)
	}

	return pool, nil
}

// Link will link the given repository to the object pool. This is done by writing the object pool's
// path relative to the repository into the repository's "alternates" file. This does not trigger
// deduplication, which is the responsibility of the caller.
func Link(ctx context.Context, pool, repo *localrepo.Repo, txManager transaction.Manager) (returnedErr error) {
	altPath, err := repo.InfoAlternatesPath(ctx)
	if err != nil {
		return err
	}

	expectedRelPath, err := getRelativeObjectPath(ctx, pool, repo)
	if err != nil {
		return err
	}

	linked, err := linkedToRepository(ctx, pool, repo)
	if err != nil {
		return err
	}

	if linked {
		// When the repository is already linked to the repository, cast a vote to ensure the
		// repository is consistent with the other replicas.
		if err := transaction.VoteOnContext(ctx, txManager, voting.VoteFromData([]byte("repository linked")), voting.Synchronized); err != nil {
			return fmt.Errorf("vote on linked repository: %w", err)
		}

		return nil
	}

func TestLink(t *testing.T) {
	t.Parallel()

	ctx := testhelper.Context(t)

	cfg, repo, _, _, client := setup(t, ctx, testserver.WithDisablePraefect())

	localRepo := localrepo.NewTestRepo(t, cfg, repo)
	poolProto, _, poolPath := createObjectPool(t, ctx, cfg, repo)

	// Mock object in the pool, which should be available to the pool members
	// after linking
	poolCommitID := gittest.WriteCommit(t, cfg, poolPath,
		gittest.WithBranch("pool-test-branch"))

	for _, tc := range []struct {
		desc        string
		request     *gitalypb.LinkRepositoryToObjectPoolRequest
		expectedErr error
	}{
		{
			desc: "unset repository",
			request: &gitalypb.LinkRepositoryToObjectPoolRequest{
				Repository: nil,
				ObjectPool: poolProto,
			},
			expectedErr: structerr.NewInvalidArgument("%w", storage.ErrRepositoryNotSet),
		},
		{
			desc: "unset object pool",
			request: &gitalypb.LinkRepositoryToObjectPoolRequest{
				Repository: repo,
				ObjectPool: nil,
			},
			expectedErr: structerr.NewInvalidArgument("%w", storage.ErrRepositoryNotSet),
		},
		{
			desc: "successful",
			request: &gitalypb.LinkRepositoryToObjectPoolRequest{
				Repository: repo,
				ObjectPool: poolProto,
			},
		},
	} {
		t.Run(tc.desc, func(t *testing.T) {
			_, err := client.LinkRepositoryToObjectPool(ctx, tc.request)
			testhelper.RequireGrpcError(t, tc.expectedErr, err)
			if tc.expectedErr != nil {
				return
			}

			// verify that the commit is present in the pool
			commitClient := gitalypb.NewCommitServiceClient(gittest.DialService(t, ctx, cfg))
			gittest.RequireObjectExistsAPI(t, ctx, commitClient, repo, poolCommitID)

			commit, err := localRepo.ReadCommit(ctx, git.Revision(poolCommitID))
			require.NoError(t, err)
			require.NotNil(t, commit)
			require.Equal(t, poolCommitID.String(), commit.GetId())
		})
	}
