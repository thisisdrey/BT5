### Title
`ValidateMultiSign` precompile signs only `(account, permissionId, data)` without binding the calling contract, enabling cross-contract signature replay/front-running - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` TVM precompile (address `0x...0a`) is a generic on-chain signature-verification oracle that any smart contract can call via `TriggerSmartContract`/`CreateSmartContract`. The message it hashes and verifies signatures against is built solely from `account address || permissionId || data` supplied as call arguments, with no binding to the *calling contract's* identity, no nonce, and no consumption/marking of the signature as used. This mirrors exactly the root cause of the reported `LiquidityPool::requestRedeemWithPermit` bug: a signature that authorizes an action is not scoped to the specific consumer contract, so a signature broadcast (or observable in the mempool as calldata to one contract) that is valid for `(account, permissionId, data)` is equally valid when replayed against any other contract that calls the same precompile with the same three values, regardless of what that second contract does with the authorization.

### Finding Description
`ValidateMultiSign.execute` computes:
```
combine = address || permissionId || data
hash = sha256(combine)
```
and then verifies the supplied ECDSA signatures against `hash`, checking recovered addresses against the account's `Permission` weight/threshold. [1](#0-0) 

Nothing in this hash construction, and nothing in the precompile's execution, ties the verification to:
- the address of the smart contract that invoked the precompile (no `msg.sender`/calling-contract binding equivalent to the LiquidityPool's own address in the fixed permit scheme), or
- a nonce/used-signature bookkeeping (the precompile is stateless/pure and never marks a signature as consumed). [2](#0-1) 

Because the precompile is reachable from any deployed TVM contract (`VMConfig.allowTvmSolidity059()` gate only, no privilege requirement), and Solidity contract developers on TRON are expected to use `ValidateMultiSign` as their generic multi-sig authorization primitive (as documented in the accompanying tests), a `data` payload signed by a user with intent to authorize action in Contract A can be observed in the mempool (as part of the `TriggerSmartContract` calldata) and replayed by a malicious contract B that calls `ValidateMultiSign` with the identical `(address, permissionId, data)` triple, obtaining the same "authorized" result even though contract B's operation is unrelated to (or more damaging than) what the user intended for contract A. This is structurally identical to the Centrifuge finding: the permit signature bound only to (owner, spender, amount, nonce, deadline) — not to the specific liquidity pool — so any pool sharing those fields could consume it first.

### Impact Explanation
Any TRON smart contract ecosystem that relies on `ValidateMultiSign` as an authorization mechanism for value-moving operations (e.g., custom vaults, bridges, multi-sig wallets, or DeFi primitives built on TVM that reuse it analogous to EIP-2612 permits) inherits this cross-contract replay hazard. An attacker monitoring pending transactions can front-run with a different, malicious contract call using the intercepted `(address, permissionId, data, signatures)` tuple to redirect authorized funds/actions to itself or to a more damaging counterpart contract, resulting in unauthorized account operations or theft of funds routed through the victim's own valid signature.

### Likelihood Explanation
Exploitation only requires: (1) a contract ecosystem that uses `ValidateMultiSign` without independently embedding contract-identity/domain-separation into `data` (which the precompile does nothing to encourage or enforce), and (2) an attacker able to observe pending `TriggerSmartContract` transactions in the mempool and submit a competing transaction with higher fee/priority — the same "front-run the permit tx" mechanics as the original finding. No special privilege, SR/witness role, or protocol-level access is needed; any account able to broadcast a transaction and deploy a contract can carry out the attack.

### Recommendation
Document and, where feasible, enforce that `data` passed to `ValidateMultiSign` include the calling/consuming contract's address (and a nonce) so the resulting hash is scoped to a specific consumer and cannot be replayed across unrelated contracts — analogous to the recommended EIP-712-style domain separation adopted by Centrifuge. Consider extending the precompile hash to also fold in the calling contract's own address (`the contract that invoked this precompile`, obtainable from the current execution context) by default, removing the burden from downstream Solidity developers to remember domain separation.

### Proof of Concept
1. Contract `A` (e.g. a vault) expects users to sign `data = keccak256(abi.encode(amount, recipient))` and calls `ValidateMultiSign(user, permissionId, data, sig)` before releasing funds to `recipient`.
2. User submits a `TriggerSmartContract` transaction calling `A.withdraw(amount, recipient, sig)`; this transaction (and thus `sig`, `amount`, `recipient`) is visible in the mempool.
3. Attacker deploys/uses contract `B`, which also calls the same precompile: `ValidateMultiSign(user, permissionId, data, sig)` with the identical `data` (since `data`'s only inputs — `amount`/`recipient` — match, or the attacker crafts B to accept the exact same `data` blob), then executes a different, attacker-controlled effect (e.g., redirecting funds to the attacker) once the precompile call returns success.
4. Attacker's transaction is submitted with a higher fee and is mined before the user's original transaction; the precompile has no per-signature-use tracking, so it happily approves both calls, and the user's follow-up transaction to `A` may now be replay-safe from `A`'s perspective but the attacker has already extracted value via `B` using the intercepted signature — exactly mirroring the `newLPool.requestRedeemWithPermit(...)` front-run in the source report.
