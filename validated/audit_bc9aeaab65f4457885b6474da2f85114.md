### Title
`AccountPermissionUpdateActuator` accepts an all-zero address as an Owner/Active/Witness permission key, permanently bricking account permission management - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
`AccountPermissionUpdateActuator.validate()` verifies each `Key` in every submitted `Permission` (Owner, Witness, Active) using `DecodeUtil.addressValid()` [1](#0-0) , but that helper only checks address length and the `0x41` TRON prefix byte, never rejecting the "null"/zero address (prefix + 20 zero bytes) [2](#0-1) . This is the same bug class as the reported `SwapperFactory.createSwapper()` issue: a permission/ownership field that should never be set to the zero address is accepted without an explicit zero-check.

### Finding Description
Any account holder can broadcast a signed `AccountPermissionUpdateContract` transaction to update their own account's Owner, Witness, and Active permissions. The validation path `checkPermission()` enforces key count, weight, threshold, and distinctness constraints, and calls `DecodeUtil.addressValid(key.getAddress())` to ensure "key is not a validate address" [1](#0-0) . `addressValid()` only checks that the array is non-empty, exactly 21 bytes, and starts with the mainnet prefix byte `0x41` [2](#0-1)  — it does not reject an address consisting of the prefix followed by 20 zero bytes. Consequently, a user can submit an Owner permission whose sole key (with sufficient weight to meet the threshold) is the zero address, and `execute()` will persist this via `AccountCapsule.updatePermissions()` [3](#0-2) , overwriting the account's real owner permission.

### Impact Explanation
Because nobody controls the private key for the zero address, once the Owner permission (and potentially Active permissions) are set to the zero address as the sole/controlling key, the account can never again produce a valid signature meeting the Owner permission threshold. This permanently locks the account out of further permission updates (`AccountPermissionUpdateContract` itself requires satisfying the Owner permission) and, if Active permissions controlling asset transfers are similarly zeroed, can permanently freeze the account's ability to transfer TRX/TRC10 tokens or otherwise operate — a permanent freezing-of-funds/control condition, matching the impact class of the original finding.

### Likelihood Explanation
This is reachable by any single unprivileged, signed transaction from the account owner (accidentally or via a malicious dApp/tool tricking a user into submitting such a permission update), with no special privileges required beyond owning the account being (mis)configured. The validation logic never special-cases the zero address, so the condition is trivially triggerable.

### Recommendation
In `AccountPermissionUpdateActuator.checkPermission()` (or centrally in `DecodeUtil.addressValid()`), explicitly reject addresses that are all-zero after the prefix byte (i.e., disallow the canonical "black hole"/zero address as a permission key), in addition to the existing length/prefix checks.

### Proof of Concept
1. Attacker (or the account owner themselves, tricked by a malicious wallet UI) constructs an `AccountPermissionUpdateContract` for `ownerAddress = A`.
2. Sets the `Owner` permission with a single `Key` whose address is `0x41` followed by 20 zero bytes, with `weight >= threshold`.
3. Sets valid `Active` permission(s) (required by validation) as needed to pass other checks.
4. Signs and broadcasts the transaction using the account's current valid Owner key.
5. `validate()` passes because `DecodeUtil.addressValid()` accepts the zero address [1](#0-0) .
6. `execute()` persists the new Owner permission via `account.updatePermissions(...)` [4](#0-3) .
7. From this point forward, no valid signature can satisfy the Owner permission threshold, permanently preventing further `AccountPermissionUpdateContract` transactions for account `A`.

  public static boolean addressValid(byte[] address) {
    if (ArrayUtils.isEmpty(address)) {
      logger.warn("Warning: Address is empty !!");
      return false;
    }
    if (address.length != ADDRESS_SIZE / 2) {
      logger.warn(
          "Warning: Address length need " + ADDRESS_SIZE + " but " + address.length
              + " !!");
      return false;
    }

    if (address[0] != addressPreFixByte) {
      logger.warn("Warning: Address need prefix with " + addressPreFixByte + " but "
          + address[0] + " !!");
      return false;
    }
    return true;
  }
