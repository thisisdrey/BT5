### Analysis

**The binding claimed to be broken:** `token_id.to_string()` used as the credited key during `mt_on_transfer` deposit == `token_id.to_string()` used as the debited key when a signed `TokenDiff`/withdraw is parsed from a `MultiPayload`.

Tracing this:
- In `mt_on_transfer`, the byte-length check `token_id.len() > MAX_TOKEN_ID_LEN` operates on `String::len()`, which returns UTF-8 byte length in Rust — the same value that is later used to construct `Nep245TokenId::new(token.clone(), token_id)` ( [3](#0-2) ). The `mt_token_id: String` field is stored byte-for-byte, untouched.
- `Nep245TokenId`'s `Display`/`Debug` writes the raw string with no escaping or normalization ( [4](#0-3) ), and `FromStr` splits on the first `:` and takes the raw remainder as `mt_token_id`, again with no normalization ( [5](#0-4) ).
- `TokenId`'s `PartialEq`/`Eq`/`PartialOrd`/`Ord` used as the `BTreeMap<TokenId, i128>` key in `TokenDeltas` ( [6](#0-5)  and the enum derive at [7](#0-6) ) are **derived**, meaning they recurse into `Nep245TokenId`'s derived `PartialEq`/`Ord` on its `String` field — which is exact byte-sequence comparison, not any form of Unicode-aware or normalized comparison.
- There is no `.chars().count()`, `.nfc()`, `.nfkc()`, or any normalization/truncation call anywhere in this path (verified via repo-wide grep — the only matches were unrelated to token IDs, e.g. in `crates/crypto/*` and decimal/time crates).
- There is also an explicit test in this repo asserting exact round-trip equality for arbitrary `Nep245TokenId` values, including any Unicode content the `arbitrary` crate generates: [8](#0-7) .

Since the byte length reported by `token_id.len()` is the same quantity carried through unmodified into the `String` field used for equality/ordering, there is no point in the pipeline where two *different* byte sequences could be treated as the same key, nor where the same byte sequence could be split into two different keys. The premise that "Unicode normalization or byte-length truncation applied inconsistently" exists in this codebase is not supported by the code — no such logic exists at all in the deposit, `FromStr`, `Display`, or `BTreeMap` key path.
