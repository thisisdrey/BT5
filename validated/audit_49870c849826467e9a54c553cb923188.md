### Title
Protocol fee bypass on NEP-245 `TokenDiff` swaps via unit-leg splitting (`token_fee` returns `Pips::ZERO` for `amount <= 1`) - ([File: contracts/defuse/core/src/intents/token_diff.rs])

### Summary
`TokenDiff::execute_intent` computes and collects the protocol fee independently for every `TokenDiff` intent in a batch, and `TokenDiff::token_fee` hard-codes `Pips::ZERO` for NEP-245/NEP-171/IMT legs whenever `|delta| <= 1`. An unprivileged signer can split what would economically be one large NEP-245 swap into N unit-magnitude `TokenDiff` intents (each `delta == ±1`) inside the same `MultiPayload` batch, so the sum of `fee_ceil` over the N unit legs is `0`, whereas a single `TokenDiff` with `delta == ∓N` on the same token would have collected `protocol_fee.fee_ceil(N) > 0`.

### Finding Description
The binding that should hold is:
`fees_credited_to(fee_collector, T) == Σ_{negative deltas d on T} Pips::fee_ceil(protocol_fee, |d|)`

In [1](#0-0) , this sum is computed **per `TokenDiff` intent**, not per batch: for each negative `delta`, `fee = Self::token_fee(token_id, amount, protocol_fee).fee_ceil(amount)` is added to `fees_collected`, which is later credited to `fee_collector` via `internal_add_balance`.

The root cause is in `TokenDiff::token_fee`:
```
TokenIdType::Nep245 | TokenIdType::Imt if amount > 1 => {}
TokenIdType::Nep171 | TokenIdType::Nep245 | TokenIdType::Imt => return Pips::ZERO,
``` [2](#0-1) 

This exempts NEP-245/IMT legs from fees whenever the magnitude of that single leg's delta is `<= 1`, regardless of how many such unit legs the signer submits in aggregate. Since `DefuseIntents::intents` is a `Vec<Intent>` (`contracts/defuse/core/src/intents/mod.rs:30-37`) and a single signed `DefusePayload`/`MultiPayload` consumes only one nonce for the whole vector (`Engine::execute_signed_intent`, `contracts/defuse/core/src/engine/mod.rs:42-83`), an attacker can pack N `TokenDiff` intents, each with `diff = {token_id: -1, other_token_id: +k}` (or matched with a counterparty's reciprocal unit legs), into one signed payload (or one batch of payloads). Each intent is executed via the per-intent loop in `execute_intent`, and `finalize()` only verifies that all deltas across the whole batch net to zero (`Deltas::finalize`/`TransferMatcher`) — it does not re-aggregate or re-check fees.

Exploit flow: attacker (optionally using a second self-controlled account as counterparty) constructs one `MultiPayload` containing N `TokenDiff` intents on the same NEP-245 `token_id`, each leg `delta == -1` (matched by corresponding `+1` legs elsewhere in the batch to satisfy the zero-sum invariant). Because `token_fee` returns `Pips::ZERO` for `amount == 1` Nep245 legs, `fees_collected` accumulates to `0` across all N legs, whereas submitting the economically identical single `TokenDiff` with `delta == -N` would have charged `protocol_fee.fee_ceil(N)`.

No existing guard prevents this: `MultiPayload::verify`, nonce checks, and `Deltas::finalize`'s conservation check only ensure balances net to zero and the signature/nonce are valid — none of them aggregate per-token-id fee-eligible amounts across intents in a batch.

### Impact Explanation
Protocol fees can be systematically avoided on NEP-245 (and IMT) swaps by unit-leg splitting, directly matching the listed Critical category "protocol fees bypassed." The `fee_collector` account under-receives fees it is otherwise entitled to on every NEP-245 swap the attacker chooses to structure this way; repeatable indefinitely and across any NEP-245 token id, any account, and any batch size N, with no protocol-side rate limiting on this pattern.

### Likelihood Explanation
Preconditions are fully within an unprivileged attacker's control: an existing signer account with sufficient NEP-245 balance and a nonzero `protocol_fee` configured on the Verifier (a normal, expected operating configuration). The attacker only needs to construct a batch with many small legs on the same token id (paired with legitimate/self-controlled counter-legs to satisfy the zero-sum invariant), all in one or a few signed payloads — no special role, relayer key, or upgrade access required. Feasibility is high; the only cost is slightly larger transaction/gas size for N intents (out of scope per rules, but not prohibitive).

### Recommendation
Aggregate the total magnitude of same-token negative deltas per signer across the whole `DefuseIntents`/batch before applying the unit-fee exemption, or compute the exemption based on the token's unit-transferability (e.g., truly non-fungible balances) rather than a raw per-intent `amount <= 1` threshold that can be defeated by splitting. Alternatively, remove/restrict the unit-fee exemption specifically for `TokenIdType::Nep245` (which can represent fungible-like MT balances, unlike NEP-171 NFTs) and only keep it for genuinely non-divisible NFT semantics.

### Proof of Concept
`cargo test` plan (near-workspaces sandbox), analogous to existing `tests/src/tests/defuse/intents/token_diff.rs::swap_p2p`:
1. Set up `Env` with `protocol_fee = Pips::ONE_PERCENT` and a fee_collector.
2. Deploy an NEP-245 (MT) contract; create user accounts A and B each with a Defuse balance of the same MT token id `X` and a second MT token id `Y` (100 units each, sufficient to net-zero the batch).
3. **Baseline**: Sign and execute one `MultiPayload` where A submits a single `TokenDiff{X: -100, Y: +100*k}` and B submits the matching `TokenDiff{X: +100, Y: -100*k}`. Assert `fee_collector`'s MT balance for `X` equals `Pips::ONE_PERCENT.fee_ceil(100)` (nonzero).
4. **Exploit**: Reset balances; sign and execute one `MultiPayload` where A submits 100 separate `TokenDiff{X: -1, Y: +k}` intents (or 100 signed payloads) and B submits 100 matching `TokenDiff{X: +1, Y: -k}` intents, net-summing to the same total transfer as step 3.
5. Assert `fee_collector`'s MT balance for `X` is `0` after the exploit batch, versus `Pips::ONE_PERCENT.fee_ceil(100)` expected — demonstrating the binding `fees_credited_to(fee_collector, X) == Σ fee_ceil(delta)` fails to hold.

    pub fn token_fee(token_id: impl Into<TokenIdType>, amount: u128, fee: Pips) -> Pips {
        let token_id = token_id.into();
        match token_id {

            TokenIdType::Nep245 | TokenIdType::Imt if amount > 1 => {}
