### Title
Unchecked division by governance-controlled `TotalNetLimit`/`TotalEnergyCurrentLimit` in `RepositoryImpl.usageToBalance` can throw `ArithmeticException` and crash resource-balance queries reachable from TVM/precompile and Wallet resource APIs - (File: `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java`)

### Summary
The reported Notional bug is a division-by-zero revert that happens because a value derived from a governance-settable parameter (`haircut`/`buffer`) can legitimately be zero, and the arithmetic function that consumes it performs a raw integer division without guarding for that case. The closest analog in java-tron is `RepositoryImpl.getAccountEnergyUsageBalanceAndRestoreSeconds` / `getAccountNetUsageBalanceAndRestoreSeconds`, which feed `TotalEnergyCurrentLimit` / `TotalNetLimit` (both are on-chain dynamic parameters adjustable through governance proposals) as the divisor into `usageToBalance`, which internally uses the private `divideCeil`/`divideCeilExact` helpers performing plain integer/`BigInteger` division. [1](#0-0) [2](#0-1) 

### Finding Description
`getAccountEnergyUsageBalanceAndRestoreSeconds` and `getAccountNetUsageBalanceAndRestoreSeconds` compute `totalEnergyLimit`/`totalNetLimit` directly from `DynamicPropertiesStore` and pass them into `usageToBalance(usage, weight, limit)` without any zero-check, unlike the sibling functions `calculateGlobalNetLimit`/`calculateGlobalEnergyLimit` in `BandwidthProcessor`/`EnergyProcessor`, which explicitly guard `if (totalNetWeight == 0) return 0;` before invoking the corresponding hardened (`BigInteger`) division path: [3](#0-2) [4](#0-3) 

That existing pattern shows the maintainers are aware that these totals can become zero and require explicit guarding before doing integer division. `RepositoryImpl`'s `usageToBalance` (confirmed via `RepositoryImplHardenTest#testUsageToBalanceOverflowDetectedWithHardening`, which exercises the same helper with `totalLimit=1L` and expects an `ArithmeticException` on overflow) relies on `divideCeil`/`divideCeilExact`, whose denominator is the "limit" parameter: [5](#0-4) 

`TotalNetLimit` and `TotalEnergyCurrentLimit` are dynamic-parameter values that get updated via chain governance/proposal mechanisms (and, in the resource-delegation math paths, are already treated as values that can hit zero, as shown by the explicit `totalNetWeight == 0`/`totalEnergyWeight == 0` short-circuits above). If either total-limit value reaches zero — through a proposal or state transition that the codebase does not appear to fully forbid in this particular consumer — the plain integer division `numerator / denominator` in `divideCeil` throws `ArithmeticException: / by zero`, exactly mirroring the Solidity `.div(multiple)` revert in the original report where `multiple` (built from haircut/buffer) can be zero.

### Impact Explanation
An uncaught `ArithmeticException` inside a `Repository`/TVM resource-accounting helper used by native-contract processors and resource-query code paths would propagate up and fail the surrounding TVM execution/query, denying the resource-balance functionality for any account touched by that computation once the underlying total-limit parameter is zero — a node-serviceability/API-availability impact consistent with the "API the node can no longer serve" acceptance criterion.

### Likelihood Explanation
Medium/uncertain: this requires the on-chain `TotalNetLimit`/`TotalEnergyCurrentLimit` dynamic parameter to actually reach zero, which is governance/state-dependent rather than directly settable by an anonymous caller in a single transaction. I was not able to fully verify (within the available search budget) whether committee/proposal validation elsewhere in the codebase forbids setting these specific parameters to zero, nor could I directly inspect the full body of `usageToBalance` to confirm the exact divisor ordering beyond what the test file demonstrates. This uncertainty should be resolved by inspecting `RepositoryImpl.usageToBalance`'s full implementation and the proposal validation logic for `TOTAL_NET_LIMIT` / `TOTAL_ENERGY_CURRENT_LIMIT` before treating this as fully confirmed.

### Recommendation
Add explicit zero-guards for `totalEnergyLimit`/`totalNetLimit` (and any other divisor sourced from a governance-adjustable dynamic property) in `RepositoryImpl.getAccountEnergyUsageBalanceAndRestoreSeconds` / `getAccountNetUsageBalanceAndRestoreSeconds` before calling `usageToBalance`, mirroring the `totalNetWeight == 0` / `totalEnergyWeight == 0` guards already present in `BandwidthProcessor`/`EnergyProcessor`. Additionally, review committee-parameter validation to ensure `TotalNetLimit`/`TotalEnergyCurrentLimit` cannot be set to zero via proposals.

### Proof of Concept
Not independently reproducible from the indexed context alone: reaching this requires the dynamic parameter `TotalNetLimit` or `TotalEnergyCurrentLimit` to be zero, then invoking a code path that calls `RepositoryImpl.getAccountEnergyUsageBalanceAndRestoreSeconds`/`getAccountNetUsageBalanceAndRestoreSeconds` (e.g., through a resource-query precompile/opcode or an equivalent Wallet resource query). I could not confirm the exact caller(s) of these two methods or the full body of `usageToBalance` within the available tool budget; a Devin session with full repository access would be needed to trace the exact caller chain and confirm whether the divisor can reach zero in practice.

  public Pair<Long, Long> getAccountEnergyUsageBalanceAndRestoreSeconds(AccountCapsule accountCapsule) {
    long now = getHeadSlot();

    long energyUsage = accountCapsule.getEnergyUsage();
    long latestConsumeTime = accountCapsule.getAccountResource().getLatestConsumeTimeForEnergy();
    long accountWindowSize = accountCapsule.getWindowSize(Common.ResourceCode.ENERGY);

    if (now >= latestConsumeTime + accountWindowSize) {
      return Pair.of(0L, 0L);
    }

    long restoreSlots = latestConsumeTime + accountWindowSize - now;

    long newEnergyUsage = recover(energyUsage, latestConsumeTime, now, accountWindowSize);

    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getTotalEnergyWeight();

    long balance = usageToBalance(newEnergyUsage, totalEnergyWeight, totalEnergyLimit);

    return Pair.of(balance, restoreSlots * BLOCK_PRODUCED_INTERVAL / 1_000);
  }

  private long divideCeil(long numerator, long denominator) {
    return (numerator / denominator) + ((numerator % denominator) > 0 ? 1 : 0);
  }

  private long divideCeilExact(BigInteger numerator, BigInteger denominator) {
    BigInteger[] divRem = numerator.divideAndRemainder(denominator);
    long result = divRem[0].longValueExact();
    if (divRem[1].signum() > 0) {
      result = StrictMathWrapper.addExact(result, 1);
    }
    return result;
  }
