### Title
DoS via HTTP/2 zero flow-control window against java-tron's gRPC API (`Server`, port 50051) — `maxConnectionIdle`/`maxConnectionAge` do not reclaim connections with permanently-stalled streams - (File: `framework/src/main/java/org/tron/common/application/RpcService.java`)

### Summary
The gRPC transport (`NettyServerBuilder`) backing `RpcApiService`, `RpcApiServiceOnSolidity`, and `RpcApiServiceOnPBFT` is configured only with connection-level idle/age timeouts and a `maxRstFramesPerWindow` guard against Rapid-Reset-style attacks. There is no mechanism (server-side call deadline, per-stream flow-control timeout, or global connection cap) that reclaims a connection that keeps at least one HTTP/2 stream nominally "active" while advertising (or draining to) a zero flow-control window, exactly the bug class described in CVE-2023-43622 for Apache httpd's HTTP/2 module.

### Finding Description
`RpcService.initServerBuilder()` builds the gRPC server with: [1](#0-0) 
Only `maxConnectionIdle` and `maxConnectionAge` bound connection lifetime; both are keyed off whether the connection currently has *any* active RPC. A stream that has been accepted by the server (headers received, `maxConcurrentCallsPerConnection` slot consumed) but whose response can never be flushed because the client advertised an HTTP/2 `INITIAL_WINDOW_SIZE` of 0 (or drains the window to 0 and never sends `WINDOW_UPDATE`) is not "idle" from grpc-java/Netty's point of view — the stream is open and has pending work, so `maxConnectionIdle` never fires. There is no server-side per-call deadline enforced anywhere in the RPC path (only a client-side `TimeoutInterceptor` used in tests), so a stalled stream can persist indefinitely.

`NodeConfig.postProcess()` even converts an explicit `0` (documented as "no limit") for `maxConnectionIdleInMillis`/`maxConnectionAgeInMillis` into `Long.MAX_VALUE`: [2](#0-1) 
so operators who rely on the documented "0 = no limit" reference default get an effectively permanent connection lifetime, and even with the shipped `config.conf` default of 60s idle timeout, that timeout is defined over "no active call," which a deliberately stalled stream defeats.

Each connection can hold up to `maxConcurrentCallsPerConnection` (default 100) concurrently open streams, each of which may be servicing a data-heavy unary RPC (e.g. `getBlockByLimitNext`, block/transaction list APIs) whose serialized response can be multiple MB. The gRPC/Netty write path buffers the produced response frames in the channel's outbound queue while waiting for window credit; if the credit never arrives, that memory (and the executor thread if the handler blocks on a synchronous write/backpressure path) remains pinned. There is no cap on the number of gRPC connections a single unprivileged client (or a small botnet) can open to the public port (50051/50061/50071), so this can be trivially multiplied.

### Impact Explanation
An unauthenticated, unprivileged network client can hold arbitrarily many connections and streams open indefinitely against the node's public gRPC endpoints by manipulating HTTP/2 flow-control windows, without ever completing valid RPC work. This ties up the fixed-size gRPC executor pool (`rpc.thread`) and/or accumulates unflushed response buffers in Netty, degrading or halting the node's ability to serve legitimate wallet/API/block-sync queries — a node-level Denial of Service consistent with the "node crash or halt" / "API the node can no longer serve" acceptance criteria.

### Likelihood Explanation
The attack requires only a raw TCP/HTTP2 client capable of completing the client preface/SETTINGS handshake and sending a zero (or drained) `INITIAL_WINDOW_SIZE`, then issuing calls to any data-returning RPC. No authentication, signed transaction, or special privilege is needed — the gRPC ports are commonly exposed to the public in FullNode/SolidityNode/PBFT-node deployments. The existing `RpcServiceHttp2SecurityTest` demonstrates the project already tests low-level HTTP/2 frame manipulation against this exact server, confirming the attack surface is reachable and testable with raw sockets.

### Recommendation
- Enforce a per-call server-side deadline (e.g., via a `ServerInterceptor` that calls `Context.current().withDeadlineAfter(...)`) so that any RPC — including ones blocked purely on transport-level flow control — is forcibly cancelled after a bounded time.
- Consider adding an explicit cap on total concurrent gRPC connections (analogous to `ConnectionLimit` already used for the Jetty `HttpService` in `framework/src/main/java/org/tron/common/application/HttpService.java`) so a small number of clients cannot multiply stalled-stream memory usage without bound.
- Re-evaluate whether `0` should truly mean "no limit" for `maxConnectionIdleInMillis`/`maxConnectionAgeInMillis`, or whether a bounded maximum should be enforced regardless, to avoid silently disabling connection reclamation.

### Proof of Concept
1. Connect via raw TCP to the gRPC port (e.g. 50051), complete the HTTP/2 client preface.
2. Send a `SETTINGS` frame advertising `SETTINGS_INITIAL_WINDOW_SIZE = 0` (or a very small window that is never replenished).
3. Send `HEADERS`+`DATA` to invoke a data-heavy RPC such as `WalletGrpc/GetBlockByLimitNext` requesting a large block range.
4. The server accepts the stream (consuming a `maxConcurrentCallsPerConnection` slot) and attempts to write the response, which is queued indefinitely at the Netty/HTTP2 layer awaiting window credit that is never sent.
5. Never send a `WINDOW_UPDATE` or `RST_STREAM`; repeat steps 1-4 from many connections/streams up to `maxConcurrentCallsPerConnection` per connection.
6. Because the stream is still "active," `maxConnectionIdle`/`maxConnectionAge` (`RpcService.java:107-108`) never terminate the connection, and no per-call deadline exists server-side, so buffered memory and occupied stream slots accumulate without bound until the node's resources are exhausted.
