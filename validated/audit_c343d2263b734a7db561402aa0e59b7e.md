## Analysis

The Curve `stored_balances` bug is a specific instance of a broader bug class: **an internal "amount credited" ledger is set to the requested transfer amount instead of the actual balance delta observed on the token contract**, so if the token's real balance transfer differs from the requested amount (rebase, fee-on-transfer, etc.), the internal accounting becomes permanently decoupled from the real balance, and later attempts to move funds out revert, locking value.

The closest local analog in this repository is `ERC20Transactor` in `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`, used to bridge arbitrary ERC20 contracts (deployed via `pallet-revive`) into XCM's asset-holding model.

### Title
Unbacked XCM asset credit from ERC20 transfers with non-standard token semantics (fee-on-transfer/rebasing) - (File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs)

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` credits an XCM `AssetsInHolding` with the *requested* transfer `amount` based solely on whether the ERC20 `transfer()` call succeeded, never verifying the actual balance delta received by the checking account. [1](#0-0) 

### Finding Description
`withdraw_asset_with_surplus` calls the ERC20 contract's `transfer(checking_address, amount)` and only inspects the boolean return value (`is_success`) to decide whether the operation succeeded; it never checks the checking account's `balanceOf` before/after the call. [2](#0-1) 

If `is_success` is true, the code unconditionally mints an `Erc20Credit(amount)` into the XCM holding register — i.e. it assumes exactly `amount` tokens landed in the `TransfersCheckingAccount`: [3](#0-2) 

`Erc20Credit` itself is documented as performing no runtime-level balance enforcement — it is a bookkeeping value only, trusting the ERC20 contract to be a standard, non-deflationary/non-rebasing implementation: [4](#0-3) 

For any ERC20 contract that is fee-on-transfer, deflationary, or rebasing (i.e. real balance delta ≠ transferred `amount`, exactly the class of token the Curve report is about), the checking account's real token balance ends up lower than the sum of `Erc20Credit` amounts registered on its behalf across all XCM operations. This is precisely the "stored balance vs actual/rebased balance" divergence described in the report: an internal accounting value assumes a 1:1, non-rebasing relationship with the underlying token, but nothing enforces or verifies that assumption.

Later, when a legitimately-credited holder attempts `deposit_asset_with_surplus` to redeem their share (transfer `amount` out of the checking account to a beneficiary), if the checking account's real balance is insufficient because of prior fee-on-transfer/rebase shortfalls, the underlying ERC20 `transfer()` will fail/return `false`/revert, and the code returns the asset back into holding with `FailedToTransactAsset`: [5](#0-4) 

No mechanism exists anywhere in this file to reconcile the accumulated `Erc20Credit` bookkeeping against the checking account's true on-chain balance, so once the shortfall exists it is permanent — subsequent legitimate holders cannot redeem their full entitled balance through this transactor, exactly mirroring "tokens with accrued/rebased balance changes cannot be removed" in the original report.

### Impact Explanation
This breaks the fungible-asset conservation-of-value invariant for any ERC20 asset registered with this transactor whose real transfer semantics diverge from the requested `amount` (fee-on-transfer or rebasing tokens). The result is:
- An unbacked increase in XCM-tracked asset supply relative to what the checking account actually holds (equivalent to an unbacked mint).
- A subsequent, unrelated (honest) user's redemption of their legitimately-credited asset can permanently fail, locking their funds — the transactor has no recovery path, matching the "permanent user-fund lock" impact class.

### Likelihood Explanation
Exploitability depends on whether the deployment's `Matcher`/asset registry allows non-standard ERC20 contracts (fee-on-transfer or rebasing tokens) to be matched by `MatchesFungibles`. Any unprivileged user holding such a token can trigger `withdraw_asset_with_surplus` via a normal XCM reserve-transfer/teleport-style message routed through this transactor — no privileged, governance, or validator/relayer assumption is required, only that the asset in question is permitted by the runtime's asset filter for this transactor.

### Recommendation
Verify actual balance delta rather than trusting the boolean return value: read `balanceOf(checking_address)` before and after the `transfer` call (and similarly for `deposit_asset_with_surplus`), and credit/debit `AssetsInHolding` with the observed delta instead of the requested `amount`. Alternatively, restrict this transactor's asset matcher to a documented allow-list of standard, non-rebasing, non-fee-on-transfer ERC20 contracts, and add a defensive check that reverts the whole operation if the observed delta does not equal the requested amount.

### Proof of Concept
1. Deploy (or configure the matcher to accept) a fee-on-transfer ERC20 contract `T` where `transfer(to, amount)` actually delivers `amount - fee` to `to` but still returns `true`.
2. User A initiates an XCM operation causing `withdraw_asset_with_surplus` to call `T.transfer(checking_account, 1000)`. The checking account actually receives `950` (5% fee), but `Erc20Credit(1000)` is minted into the XCM holding.
3. User A's XCM message completes, crediting 1000 units of `T` to some beneficiary/holding elsewhere in the system, backed by only 950 real tokens at the checking account.
4. A different, honest holder B who was legitimately credited an equivalent amount of `T` earlier attempts to redeem via `deposit_asset_with_surplus`, calling `T.transfer(beneficiary, amount)` from the checking account. Because the checking account is now short by the accumulated fee shortfall, the transfer fails/reverts, and B's asset is returned to holding with `FailedToTransactAsset` — B cannot retrieve their funds, reproducing the "tokens become stuck" scenario from the original report.

/// A minimal imbalance tracking type that holds an ERC20 token amount.
///
/// This type implements the necessary imbalance accounting traits but does not perform
/// runtime-level balance enforcement. It's used to track ERC20 token amounts within XCM
/// asset holdings, where the actual balance constraints are enforced by the ERC20 smart
/// contract itself rather than the runtime.
struct Erc20Credit(u128);
impl UnsafeConstructorDestructor<u128> for Erc20Credit {
	fn unsafe_clone(&self) -> Box<dyn ImbalanceAccounting<u128>> {
		Box::new(Erc20Credit(self.0))
	}
	fn forget_imbalance(&mut self) -> u128 {
		let amount = self.0;
		self.0 = 0;
		amount
	}
}
