### Title
`disabledApi` list restricting `getaccount`/other sensitive APIs is not enforced on the JSON-RPC endpoint, allowing anonymous access via a different query path - (File: `framework/src/main/java/org/tron/core/services/jsonrpc/TronJsonRpcImpl.java`)

### Summary
The XWiki advisory describes a class of bug where data that an administrator restricted to a limited audience (a closed subwiki) remains reachable to unrestricted anonymous users through a *different* query path (the farm-wide Dashboard) that does not enforce the same access-scoping. The `disabledApi` mechanism in java-tron exhibits the same structural flaw: an operator disables sensitive HTTP/gRPC endpoints (e.g. `getaccount`, account/resource lookups) via `node.disabledApi`, but this restriction is explicitly documented and implemented to *not* apply to the JSON-RPC interface, so the same underlying data is still servable to any anonymous JSON-RPC client.

### Finding Description
`HttpApiAccessFilter` and `RpcApiAccessInterceptor` both consult `CommonParameter.getInstance().getDisabledApiList()` to block specific HTTP servlet paths and gRPC methods when an operator lists them in `node.disabledApi`: [1](#0-0) [2](#0-1) 

The configuration itself explicitly documents that this list only covers HTTP, RPC (gRPC) and PBFT — not JSON-RPC: [3](#0-2) 

However, `TronJsonRpcImpl` (mounted via `FullNodeJsonRpcHttpService`, `JsonRpcServiceOnSolidity`, `JsonRpcServiceOnPBFT`) exposes equivalent read APIs (e.g. balance/account/transaction lookups) directly against `Wallet`, with no interceptor equivalent to `HttpApiAccessFilter`/`RpcApiAccessInterceptor` applied to it. The `addServlet`/`addFilter` wiring for JSON-RPC servlets (`JsonRpcServlet`, `JsonRpcOnSolidityServlet`, `JsonRpcOnPBFTServlet`) does not reference `httpApiAccessFilter` anywhere in the codebase (confirmed by the absence of any match for `HttpApiAccessFilter` usage inside those JSON-RPC service classes), unlike `FullNodeHttpApiService`, `HttpApiOnSolidityService`, and `HttpApiOnPBFTService`, which all explicitly register it: [4](#0-3) [5](#0-4) [6](#0-5) 

Consequently, an operator who runs `node.disabledApi = ["getaccount"]` intending to prevent public disclosure of account balances/resources/permissions still leaves that exact data reachable by an anonymous client through the equivalent JSON-RPC method (e.g. `eth_getBalance`, `eth_getTransactionCount`, or `eth_getTransactionByHash`), because the enforcement point (`HttpApiAccessFilter`/`RpcApiAccessInterceptor`) is never invoked for the JSON-RPC transport. This mirrors the XWiki advisory's root cause exactly: a scoping/visibility control implemented at one interface boundary is silently bypassed by an alternate interface that surfaces the same underlying data.

### Impact Explanation
Any anonymous, unauthenticated JSON-RPC client can retrieve account balances, transaction history, and other data an operator has explicitly and intentionally disabled on the primary HTTP/gRPC surface for privacy, DoS-mitigation, or compliance reasons. This is an information-disclosure bypass of a documented access control (CWE-668, Exposure of Resource to Wrong Sphere), matching the classification and severity class of the reference CVE. It does not directly enable theft of funds or node crash, but it defeats an operator-configured confidentiality/availability control on a production RPC surface reachable by any anonymous API client — within the explicitly allowed scope of "an API the node can no longer serve [as configured]" in reverse (an API operators believed was disabled remains served).

### Likelihood Explanation
High reachability: any anonymous JSON-RPC client can trigger this with a single unauthenticated request once `node.jsonrpc.httpFullNodeEnable` (or Solidity/PBFT variants) is turned on, which is common for dApp/wallet integration nodes. No special privileges, transactions, or signatures are required — only knowledge that the JSON-RPC port is open, which is default discoverable behavior for public RPC endpoints.

### Recommendation
Apply the same `disabledApiList` enforcement (or an equivalent JSON-RPC-specific filter) to `TronJsonRpcImpl` methods, mapping JSON-RPC method names (or the underlying Wallet operations they proxy) to the existing disabled-API config keys, and reject calls to disabled endpoints there just as `HttpApiAccessFilter`/`RpcApiAccessInterceptor` do for HTTP/gRPC. At minimum, update documentation/config validation to fail startup or warn loudly when `disabledApi` is configured but JSON-RPC remains enabled with overlapping unrestricted methods.

### Proof of Concept
1. Configure a node with `node.disabledApi = ["getaccount"]` and `node.jsonrpc.httpFullNodeEnable = true`.
2. Confirm `POST /wallet/getaccount` now returns `{"Error":"this API is unavailable due to config"}` per `HttpApiAccessFilter` behavior (as verified in `HttpApiAccessFilterTest`) [7](#0-6) .
3. As an anonymous client, call the JSON-RPC endpoint (`POST /jsonrpc`) with `eth_getBalance` for the same target address — this is serviced directly by `TronJsonRpcImpl` without any `disabledApiList` check, returning the same balance/account data the operator intended to block.

      if (!disabledApiList.isEmpty()) {

      logger.warn("check isDisabled except, endpoint={}, {}", endpoint, e.getMessage());

          httpPort = Args.getInstance().getPBFTHttpPort();
        } else {
          httpPort = Args.getInstance().getFullNodeHttpPort();
        }

        String url = String.format("http://%s:%d%s", ip, httpPort, urlPath);

        Args.getInstance().setDisabledApiList(disabledApiList);
        String response = sendGetRequest(url);
        Assert.assertEquals("{\"Error\":\"this API is unavailable due to config\"}",
            response);

        Args.getInstance().setDisabledApiList(emptyList);
        int statusCode = getRequestCode(url);
        Assert.assertEquals(HttpStatus.SC_OK, statusCode);
