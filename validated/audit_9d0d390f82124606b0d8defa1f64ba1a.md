### Title
Unstaked attacker can evade per-IP QUIC connection rate limiting and exhaust the global connection-slot pool via abandoned handshakes - ([File: streamer/src/nonblocking/quic.rs])

### Summary
The QUIC connection-rate limiter (`ConnectionRateLimiter`) only records/penalizes an IP after a completed handshake, but the resource that actually bounds concurrent connection attempts (`ClientConnectionTracker` / `stats.open_connections`, capped by `qos.max_concurrent_connections()`) is reserved *before* the handshake completes. An unstaked remote client can therefore repeatedly initiate QUIC connections and abandon them before the handshake finishes, permanently evading per-IP rate limiting while still occupying the shared global connection-slot pool for up to `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` (2s) per attempt, starving legitimate peers.

### Finding Description
In `run_server`, for every incoming connection the server does, in order: a peek-only global rate check (`overall_connection_rate_limiter.current_tokens() == 0`), a per-IP peek check (`rate_limiter.is_allowed(&ip)`), then reserves a global connection slot via `ClientConnectionTracker::new(stats.clone(), qos.max_concurrent_connections())`, and finally spawns `setup_connection`, which calls `timeout(QUIC_CONNECTION_HANDSHAKE_TIMEOUT, connecting).await`. [1](#0-0) 

The per-IP limiter's actual state mutation — `rate_limiter.register_connection(&from.ip())`, which is what makes `is_allowed()` start returning `false` — only happens inside `setup_connection` *after* the handshake future resolves `Ok`: [2](#0-1) 

`ConnectionRateLimiter::is_allowed` explicitly treats an IP with no recorded tokens as always allowed: [3](#0-2) 

Since `register_connection` is never called for an aborted/never-completing handshake, `is_allowed` for that IP is never falsified — the attacker's source IP is never penalized regardless of how many connection attempts it makes, as long as none of them complete.

Meanwhile, the *global* concurrency cap enforced by `ClientConnectionTracker::new` is not scoped per IP — it only compares against `stats.open_connections` versus `qos.max_concurrent_connections()`: [4](#0-3) 

This slot is acquired at accept time (before the handshake) and is only released when `client_connection_tracker` is dropped — either on success (once folded into `ConnectionEntry`) or, for a hung/failed handshake, implicitly at the end of `setup_connection` after the 2-second `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` elapses: [5](#0-4) [6](#0-5) 

Because a single unstaked, never-penalized IP can keep initiating new connections continuously (each held for up to 2s before being reaped), it can occupy up to `qos.max_concurrent_connections()` slots indefinitely by refreshing attempts faster than they expire. New incoming connections from legitimate peers are then refused via the `refused_connections_too_many_open_connections` path: [7](#0-6) 

No other check in this path is scoped per source IP before the connection slot is reserved — the only per-IP gate (`rate_limiter.is_allowed`) is exactly the one that never fires for abandoned handshakes.

### Impact Explanation
This is a QoS-evasion / DoS in the TPU QUIC ingress path: an unprivileged, unstaked attacker at a single source IP can consume the entire global concurrent-connection budget (`qos.max_concurrent_connections()`, e.g. `(max_staked_connections + max_unstaked_connections) * 5 / 4` for `SwQos`) reserved for connection setup, causing legitimate staked and unstaked peers' connection attempts to be refused (`refused_connections_too_many_open_connections`), effectively starving them of TPU capacity — matching the "unfairly capture connection/stream/per-IP QoS limits" bounty category referenced in the question.

### Likelihood Explanation
Fully reachable by any unstaked remote client with only network access to the leader's public TPU QUIC port; no stake, keys, or special config are required. The attack is simply: open a QUIC connection (send an Initial packet) and never complete the TLS handshake (or reset immediately), repeated fast enough that the number of concurrently pending (never-completing) connections from the attacker approaches `qos.max_concurrent_connections()`. This is trivially automatable and repeatable, bounded only by the attacker's own network throughput and the 2-second handshake timeout window.

### Recommendation
Track and cap outstanding (pre-handshake) connection attempts per source IP independently of the post-handshake `ConnectionRateLimiter`, e.g. reserve `ClientConnectionTracker`/slot capacity against a per-IP counter (or reuse `rate_limiter` state) rather than only a global counter, and/or consume from the per-IP rate limiter's token bucket at accept time (optimistically) and refund it if the handshake fails, so that abandoned handshakes from one IP cannot indefinitely occupy the shared `open_connections` budget without being throttled.

### Proof of Concept
Integration test plan (in `streamer/src/nonblocking/quic.rs` test module, using existing `setup_quic_server` helpers):
1. Configure a small `qos.max_concurrent_connections()` (e.g. `SwQosConfig { max_unstaked_connections: 2, max_staked_connections: 0, .. }`).
2. From a single client IP/socket, repeatedly call `endpoint.connect(server_addr, "localhost")` but never drive the resulting future to completion (drop it immediately after sending the Initial, e.g. spawn the connect future and abort/drop the task before it resolves), doing this in a tight loop faster than `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` (2s).
3. Concurrently, from a second, distinct client IP, attempt a normal `make_client_endpoint(&server_address, None).await` connection.
4. Assert:
   - `stats.connection_rate_limited_per_ipaddr.load(Ordering::Relaxed) == 0` for the whole test duration (per-IP limiter never triggers for the attacker).
   - The second IP's connection attempt fails or is delayed, and `stats.refused_connections_too_many_open_connections.load(Ordering::Relaxed) > 0`.
   - `stats.connection_setup_timeout` increases for the attacker's abandoned attempts, confirming they occupied `ClientConnectionTracker` slots until timeout rather than being rejected immediately by any IP-scoped guard.

impl ClientConnectionTracker {
    /// Check the max_concurrent_connections limit and if it is within the limit
    /// create ClientConnectionTracker and increment open connection count. Otherwise returns Err
    fn new(stats: Arc<StreamerStats>, max_concurrent_connections: usize) -> Result<Self, ()> {
        let open_connections = stats.open_connections.fetch_add(1, Ordering::Relaxed);
        if open_connections >= max_concurrent_connections {
            stats.open_connections.fetch_sub(1, Ordering::Relaxed);
            debug!(
                "There are too many concurrent connections opened already: open: \
                 {open_connections}, max: {max_concurrent_connections}"
            );
            return Err(());
        }

        Ok(Self { stats })
    }

    /// Check if the connection from the said `ip` is allowed.
    /// Here we assume that only IPs with actual confirmed connections are stored in it,
    /// since we should only modify server state once source IP is verified
    pub fn is_allowed(&self, ip: &IpAddr) -> bool {
        // Check if we have records in the rate limiter for the given IP address
        match self.limiter.current_tokens(ip) {
            Some(r) => r > 0, // we have a record, and rate is not exceeded
            None => true,     // if we have not seen IP, allow connection request
