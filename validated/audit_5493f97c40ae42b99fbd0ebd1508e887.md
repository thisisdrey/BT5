### Title
Front-runnable allowance reduction lets a delegate double-spend the old and new caps in `TrustedSpender` - ([File: tare-io__tare-contracts/contracts/TrustedSpender.sol])

### Summary
`TrustedSpender.setAllowance` fully overwrites the `(token, from, to)` allowance in a single write, exactly mirroring the classic ERC20 `approve` race condition described in the external report. When a Safe (or guardian) tries to *reduce* an already-consumable allowance for a delegate/recipient route, a delegate who observes the pending reduction in the mempool can front-run it by calling `executeTransfer` for the full old amount, and then, once the reduction lands, spend the newly-set amount on top of that — extracting `old + new` instead of the intended `max(old, new)`. [1](#0-0) 

### Finding Description
`setAllowance` is `safeOrGuardian`-gated but always does a full overwrite of the stored `Allowance` struct instead of an incremental/decrease-only adjustment: [2](#0-1) 

`executeTransfer` checks and decrements the currently stored allowance and then moves funds via `safeTransferFrom`: [3](#0-2) 

This is structurally identical to ERC20 `approve`/`transferFrom`: the "spender" role here is the registered `delegate` for a Safe, and the "owner" is the Safe (or a guardian acting on its behalf). Just as in the reported bug class, a two-step "approve again to change value" flow (`setAllowance(1000)` → later `setAllowance(500)`) is vulnerable: if the delegate calls `executeTransfer(..., 1000)` before the second `setAllowance` transaction lands, it drains the full original 1000, and once the reduction to 500 is mined, the delegate is granted a completely fresh 500 allowance regardless of what was already spent — because `setAllowance` blindly overwrites rather than reconciling against the current outstanding amount.

The `TrustedSpender` contract is specifically designed to bound the blast radius of a compromised or malicious delegate (e.g., the `hotProxy` role wired up in `buildCommonSteps`/`SmartAccountFactory.configureSmartAccount`) by capping per-route spend. The overwrite semantics of `setAllowance` undermine that exact security guarantee: a Safe/guardian attempting to *tighten* a delegate's spending limit in response to suspicious activity can be defeated by a delegate racing the reduction transaction, resulting in the delegate extracting more USDC (or other approved currency) from the Safe than either the old or the new limit alone would have permitted. [4](#0-3) [5](#0-4) 

### Impact Explanation
This causes unauthorized diversion of USDC (or other trusted-currency) funds from a Safe smart account to a delegate-controlled recipient route beyond what either the pre- or post-change allowance was intended to permit — directly matching the "Theft, diversion, or unauthorized reassignment of USDC ... from ... shared protocol state" allowed-impact category. Because `TrustedSpender` is the exact mechanism relied upon to contain the damage from a compromised/malicious delegate key, defeating its cap via this race breaks the core invariant the contract exists to enforce.

### Likelihood Explanation
Exploitation requires only that (a) a delegate is registered for the Safe/route (a normal, expected configuration, not a privileged admin role) and (b) the Safe or guardian issues a `setAllowance` call that *decreases* an existing non-max allowance while a delegate is actively watching the mempool. This is a realistic operational scenario — reducing a compromised or overly generous allowance is precisely the kind of defensive action a Safe/guardian would take in response to suspected delegate misuse, which is the moment the delegate has the strongest incentive to race the transaction. The window is bounded by one block/transaction confirmation, consistent with the original ERC20 report's likelihood profile.

### Recommendation
Change `setAllowance` to support safe, race-resistant adjustment: e.g., add explicit `increaseAllowance`/`decreaseAllowance` (delta-based) semantics, or require a decrease to first bring the allowance to zero/observed value (compare-and-set with expected current amount), analogous to the recommended ERC20 fix. Alternatively, pair every allowance-reducing `setAllowance` call with `removeDelegate` (which is a boolean revocation not subject to this overwrite race) when the Safe needs to reliably cut off a delegate rather than merely resize its cap.

### Proof of Concept
1. Safe `S` grants delegate `D` a route allowance: `TrustedSpender.setAllowance(USDC, S, R, 1000e6, validUntil)` (via `safeOrGuardian`).
2. `D` observes a pending Safe/guardian transaction `setAllowance(USDC, S, R, 500e6, validUntil)` intended to lower the cap.
3. `D` front-runs it with `executeTransfer(USDC, S, R, 1000e6)`, draining the full original 1000 USDC allowance (`allowance.amount` becomes 0, `safeTransferFrom(S, R, 1000e6)` succeeds since `S` has approved `TrustedSpender` for `type(uint256).max` at deploy time, per `configureSmartAccount`). [6](#0-5) 

4. The Safe/guardian's `setAllowance(USDC, S, R, 500e6, validUntil)` is then mined, fully overwriting `_allowances[USDC][S][R]` to `{amount: 500e6, ...}` — with no knowledge of the 1000e6 already spent.
5. `D` calls `executeTransfer(USDC, S, R, 500e6)` again, extracting another 500 USDC.
6. Total extracted: 1500 USDC, exceeding both the original (1000) and reduced (500) intended caps — the exact `1500` outcome described in the external ERC20 report, reproduced natively in `TrustedSpender`.

  function executeTransfer(address token, address from, address to, uint256 amount) external whenNotPaused {
    // Verify sender is a delegate
    require(delegates[from][msg.sender], NotADelegate());

    // Check allowance exists, is sufficient, and has not expired
    Allowance storage allowance = _allowances[token][from][to];
    require(allowance.amount >= amount, InsufficientAllowance());
    require(block.timestamp <= allowance.validUntil, AllowanceExpired());

    // Update allowance if not infinite
    if (allowance.amount != type(uint208).max) {
      allowance.amount -= uint208(amount);
    }

    IERC20(token).safeTransferFrom(from, to, amount);
  }
