No BMP decoder exists in this repository (only `image/gif`, `image/png`, and `image/jpeg` codecs are present under `src/image/`), and the standard library's `image` package explicitly documents its allocation model as an accepted risk rather than a vulnerability: `DecodeConfig` lets callers inspect `Config.Width`/`Height` before calling `Decode`, and a large-but-honestly-reported image is "not considered a security issue, regardless of whether the image is itself malformed or not" per the package's own Security Considerations section. [1](#0-0) 

The closest analogous decoders in scope, `image/png` and `image/gif`, already guard against the CImg-style failure mode (dimension/allocation issues from a malformed header) with explicit overflow and bounds checks rather than blindly trusting header-declared dimensions: `parseIHDR` rejects non-positive dimensions and detects `int64`/`int` pixel-count overflow before any allocation, and the GIF decoder's `newImageFromDescriptor` rejects frames whose bounds exceed the logical screen before allocating a `Paletted` image. [2](#0-1) [3](#0-2) 

There's also an existing regression test, `TestDimensionOverflow`, that specifically exercises crafted headers designed to trigger allocation-size overflow (the CImg bug class), confirming this failure mode is already a known, tested, and mitigated concern in this codebase rather than an unaddressed one. [4](#0-3) 

Given there is no BMP loader in scope to map the CVE onto, and the closest analogous decoders (PNG, GIF) already have explicit checks and regression tests for the exact allocation-failure/overflow bug class described in CVE-2018-7587, no unmitigated analog exists.
