### Title
Missing floor-at-zero clamp on `RepositoryImpl.addTotalNetWeight`/`addTotalEnergyWeight`/`addTotalTronPowerWeight` allows a TVM contract to corrupt the global resource-weight accounting used by all accounts - ([File: actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java])

### Summary
The Rio report describes a shared global accounting counter (`unverifiedValidatorETHBalance`) that is decremented on one code path assuming a matching increment happened on another path, and lacks a floor/consistency check — letting one operator's out-of-band action underflow the counter and break verification for unrelated operators. The closest reachable analog in java-tron is the pair of global weight counters `TotalNetWeight`/`TotalEnergyWeight`/`TotalTronPowerWeight`, which are read by every account's bandwidth/energy limit calculation, but are mutated through two different code paths with **inconsistent protections**:

- `chainbase/src/main/java/org/tron/core/store/DynamicPropertiesStore.java` (used by the plain actuators, e.g. `UnfreezeBalanceActuator`, `FreezeBalanceActuator`) clamps the result with `max(0, totalWeight, ...)` when `allowNewReward()` is active: [1](#0-0) 

- `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java`, which is the `Repository` implementation used by TVM **native contract processors** (`FreezeBalanceV2Processor`, `UnfreezeBalanceV2Processor`, `UnDelegateResourceProcessor`, `CancelAllUnfreezeV2Processor`, and `Program.suicide`/`transferDelegatedResourceToInheritor`), has **no such clamp** — it blindly adds the delta and persists it: [2](#0-1) 

### Finding Description
`TotalNetWeight`/`TotalEnergyWeight` are global, chain-wide counters that every account's resource limit is computed from: [3](#0-2) [4](#0-3) 

These counters are updated on the increment side by `FreezeBalanceProcessor`/`FreezeBalanceV2Processor` and on the decrement side by `UnfreezeBalanceProcessor`/`UnfreezeBalanceV2Processor`, `UnDelegateResourceProcessor`, and by `Program.suicide` → `transferDelegatedResourceToInheritor`, all of which call `repo.addTotalNetWeight(...)`/`repo.addTotalEnergyWeight(...)` on the `RepositoryImpl` instance: [5](#0-4) 

Unlike the equivalent method in `DynamicPropertiesStore` (used by the plain, non-TVM actuators) which floors the result at 0 whenever `allowNewReward()` is enabled, `RepositoryImpl.addTotalNetWeight`/`addTotalEnergyWeight`/`addTotalTronPowerWeight` apply the delta unconditionally with no floor check: [2](#0-1) 

This mirrors the Rio pattern exactly: the "spend" side of a shared global counter (here, the TVM/native-contract path) does not enforce the same invariant that the "mint" side (the ordinary actuator path) enforces, so an actor who reaches the counter exclusively through the unprotected path (deploying and interacting with a smart contract that freezes/unfreezes/delegates/self-destructs) can drive the counter into a state — e.g. negative, or lower than the true aggregate of legitimately frozen TRX — that the protected path never allows. Any later account performing a `calculateGlobalNetLimit`/`calculateGlobalEnergyLimit` computation (i.e. any account trying to use bandwidth/energy) reads this corrupted global weight, exactly analogous to how a legitimate operator's `verifyWithdrawalCredentials` call reads a corrupted `unverifiedValidatorETHBalance`.

### Impact Explanation
If `TotalNetWeight`/`TotalEnergyWeight` can be driven inconsistent (negative, or too low relative to actually-frozen TRX) via the TVM-only code path that lacks the floor protection present in the actuator path, every other account's bandwidth/energy limit calculation is affected network-wide, because `calculateGlobalNetLimit`/`calculateGlobalEnergyLimit` divide by this shared denominator: [6](#0-5) 
A corrupted weight could zero out or distort every account's available bandwidth/energy (denial of resource use for the whole network), which is the type of "node can no longer serve" / unbacked-accounting impact called for by the validation criteria.

### Likelihood Explanation
Reaching this code path only requires deploying and calling a smart contract that performs freeze/unfreeze/delegate/self-destruct sequences — no special privilege is required, matching the "unprivileged contract deployer" threat model. However, I was **not able to fully verify within the available tool budget** that a concrete sequence of TVM operations (e.g., repeated `FreezeBalanceV2`/`UnfreezeBalanceV2`/`UnDelegateResource`/`suicide` combinations) actually drives the underlying weight negative in practice — the deltas applied at each call site (`newWeight - oldWeight`) are generally derived from consistent before/after account state, so most single-call sequences are self-balancing. The residual risk is specifically in edge cases such as contract self-destruct interacting with delegated/frozen balances across accounts (as hinted by the "TVM contract suicide, re-create will produce this situation" comments in `UnDelegateResourceProcessor`/`UnfreezeBalanceProcessor`), where balances can be forcibly zeroed on one side without the corresponding total-weight adjustment being applied symmetrically. Without being able to trace a complete, concrete underflow sequence end-to-end, I can confirm the **structural asymmetry** (missing clamp) as a genuine code inconsistency, but cannot fully confirm exploitability to the level of certainty required — this should be validated further with a live/test-net level of investigation (e.g., a Devin session that can build and run a PoC contract), since the index has limits on how deeply nested execution paths can be traced.

### Recommendation
Apply the same floor-at-zero (or exact consistency) invariant to `RepositoryImpl.addTotalNetWeight`, `addTotalEnergyWeight`, and `addTotalTronPowerWeight` that already exists in `DynamicPropertiesStore`'s equivalents, and audit all TVM native-contract callers (`FreezeBalanceV2Processor`, `UnfreezeBalanceV2Processor`, `UnDelegateResourceProcessor`, `CancelAllUnfreezeV2Processor`, `Program.suicide`/`transferDelegatedResourceToInheritor`) to ensure the weight delta always exactly matches the corresponding frozen-balance delta, including all self-destruct/re-create edge cases.

### Proof of Concept
Not fully constructed — the structural gap (missing clamp in `RepositoryImpl` vs. `DynamicPropertiesStore`) is demonstrated by the cited code, but a concrete transaction sequence proving the counter goes negative/inconsistent via TVM calls (freeze → delegate → self-destruct → re-create → unfreeze, etc.) would require deeper tracing/execution than available in this indexed-code review. A background Devin session with build/test access could construct and run such a PoC against the freeze/unfreeze/delegate/suicide native contract tests already present in `framework/src/test/java/org/tron/common/runtime/vm/FreezeV2Test.java` and `FreezeTest.java` to confirm or refute exploitability.

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }

    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();

      return 0;
    } else {
      assert totalEnergyWeight > 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }

    // delegated resource from sender to owner, just abandon
    // in order to making that sender can unfreeze their balance in future
    // nothing will be deleted

    // there cannot be any resource when suicide

    AccountCapsule ownerCapsule = repo.getAccount(ownerAddr);

    // transfer owner`s frozen balance for bandwidth to inheritor
    long frozenBalanceForBandwidthOfOwner = 0;
    // check if frozen for bandwidth exists
    if (ownerCapsule.getFrozenCount() != 0) {
      frozenBalanceForBandwidthOfOwner = ownerCapsule.getFrozenList().get(0).getFrozenBalance();
    }
    repo.addTotalNetWeight(-frozenBalanceForBandwidthOfOwner / TRX_PRECISION);

    long frozenBalanceForEnergyOfOwner =

    repo.addBalance(inheritorAddr, frozenBalanceForBandwidthOfOwner + frozenBalanceForEnergyOfOwner);

      clearOwnerFreeze(ownerCapsule);
