### Title
Unbounded array pre-allocation in `BatchValidateSign` precompile from attacker-controlled length words - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The TVM precompile `BatchValidateSign` (address `0x66`) parses ABI-encoded calldata and extracts dynamic byte arrays using helper methods `extractBytesArray` and `extractBytes32Array`. Both helpers read a "length" word directly from attacker-supplied calldata and immediately use it to allocate a Java array (`new byte[len][]`) **before** any bound is enforced. A size cap (`MAX_SIZE = 16`) is only applied conditionally — guarded by the `VMConfig.allowTvmSelfdestructRestriction()` hard-fork flag — and only for the code path that calls `extractSigArray`/`extractBytes32Array` for the "restricted" branch. When that flag is not active, `extractBytesArray` is invoked with **no upper bound check at all**, so a small calldata payload can declare an enormous element count and trigger a huge/OOM-inducing pre-allocation, exactly mirroring the Netty `RedisArrayAggregator` bug class: "length declared on the wire is used to size a collection before the corresponding elements are validated or even present."

### Finding Description
`extractBytesArray` and `extractBytes32Array` read the count directly from the DataWord array parsed from calldata and allocate immediately: [1](#0-0) 

In `BatchValidateSign.doExecute`, the length-vs-`MAX_SIZE` check is only performed inside an `if (VMConfig.allowTvmSelfdestructRestriction())` block, and even then only gates the `addrArraySize`/`sigArraySize` values that are subsequently re-read inside the extraction helpers — it does not change the fact that when the flag is false, the extraction helpers are called with the raw, unchecked length: [2](#0-1) 

The only post-hoc guard (`cnt > MAX_SIZE`) executes **after** `signatures`/`addresses` arrays have already been allocated: [3](#0-2) 

The energy charged for the precompile call is computed purely from `data.length` (the actual calldata size), not from the declared element count: [4](#0-3) 

This means a caller can submit a small, cheap calldata blob that encodes a header word with a very large integer value at the position read as `len` inside `extractBytesArray`/`extractBytes32Array`, causing the node to attempt allocating an array sized to that attacker-chosen value — with negligible energy cost, before the code has verified enough calldata bytes exist to back that many elements. This is the same root-cause pattern as the reported Netty CVE: pre-allocation sized from an untrusted length field taken "off the wire" (here, from EVM calldata) prior to validating that the declared count is reasonable or backed by real data.

### Impact Explanation
Any account that can send a `TriggerSmartContract` transaction (or make a `TriggerConstantContract`/API call) invoking address `0x66` can attempt this. If the resulting array size is large enough, the resulting `OutOfMemoryError`/excessive allocation is uncaught by any resource-metering mechanism (since it happens before the `cnt > MAX_SIZE` check and is independent of energy charged), which can degrade or crash the executing node process. Because this happens during block/transaction execution in `Manager`/TVM, it affects every full node processing the same block, which is a network-wide availability impact (not merely peer-local), matching the "no impact analog" exclusion boundary — this is a genuine node crash/halt risk, which the rules explicitly accept.

### Likelihood Explanation
Reachable from a single, unprivileged, signed transaction invoking a smart contract that calls the `BatchValidateSign` precompile — no special permissions, no need to be a witness/SR, no p2p or network-level access required. The vulnerable code path is unconditionally present in the current build and is only closed off by a hard-fork gate (`allowTvmSelfdestructRestriction`); on any network/chain state where that flag is not yet active (older synced chains, private/test networks, or a node processing historical blocks before the fork), the unbounded path is live. This satisfies "unprivileged transaction broadcaster ... contract deployer" reachability required by the scan rules.

### Recommendation
Enforce the `MAX_SIZE` (or a similarly small, energy-consistent) bound check unconditionally, before calling `extractBytesArray`/`extractBytes32Array`/`extractSigArray`, regardless of the `allowTvmSelfdestructRestriction()` flag. Additionally, validate that the declared element count is consistent with the actual `data.length` (i.e., that enough bytes exist to back the claimed count) prior to allocating `new byte[len][]`, similar to how `isValidAbiEncoding` is already used elsewhere in this file. Consider charging energy proportional to the declared count rather than only to raw calldata length so pre-validation costs cannot be trivially bypassed.

### Proof of Concept
1. Construct a `TriggerSmartContract` transaction whose EVM code performs a `CALL` (or `STATICCALL`) to precompiled address `0x66` (`BatchValidateSign`).
2. Craft calldata such that:
   - `words[0]` = arbitrary hash (32 bytes).
   - `words[1]` = offset pointing to a "signatures array" header.
   - `words[2]` = offset pointing to an "addresses array" header.
   - At the offset referenced by `words[1]`/`words[2]`, place a length word with an extremely large value (e.g., close to `Integer.MAX_VALUE`), while keeping total calldata small (a handful of 32-byte words) — well under what would be required to actually back that many elements.
3. Ensure the chain configuration has `allowTvmSelfdestructRestriction` **not yet active** (e.g., a private devnet or a chain state prior to that hard fork) so the `extractBytesArray`/`extractBytes32Array` path is taken without the `MAX_SIZE` pre-check.
4. Submit/broadcast the transaction. `BatchValidateSign.doExecute` will call `extractBytesArray`/`extractBytes32Array`, which reads the crafted large `len` and immediately executes `new byte[len][]`, attempting a huge allocation for very little committed energy — leading to excessive memory pressure/`OutOfMemoryError` on every node that executes the transaction.

Note: I was unable to directly inspect the implementation of `DataWord.intValueSafe()` (its exact clamping behavior for out-of-range values) within the indexed content, so the precise numeric ceiling an attacker can reach (e.g., whether it clamps to `Integer.MAX_VALUE` or throws for negative results) could not be fully confirmed from the available index; a Devin session with full repository access would be needed to pin down that exact bound and construct a fully working exploit payload.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
