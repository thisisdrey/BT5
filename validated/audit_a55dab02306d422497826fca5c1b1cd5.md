Confirmed: `TransferActuator.execute` at [1](#0-0)  auto-creates a brand-new account at `toAddress` and credits it with the transferred amount whenever no account currently exists there, and the only validation performed on `toAddress` is `DecodeUtil.addressValid`, which merely checks length/prefix and never rejects the reserved all-zero address value.

### Title
Missing zero/black-hole-style address validation in `TransferActuator`/`TransferAssetActuator` allows permanent freezing of TRX/TRC10 funds - (File: `actuator/src/main/java/org/tron/core/actuator/TransferActuator.java`, `actuator/src/main/java/org/tron/core/actuator/TransferAssetActuator.java`)

### Summary
`TransferContract` and `TransferAssetContract` — the two primary fund-movement actuators reachable directly from a signed transaction — validate the `to_address` field only with `DecodeUtil.addressValid`, which checks byte length (21) and the network prefix byte (`0x41`) but never inspects the remaining 20 payload bytes. [2](#0-1)  This means a fully "zero" address (`0x41` followed by 20 zero bytes) passes validation identically to any legitimate address, exactly mirroring the reported bug class where `to == address(0)` is never rejected.

### Finding Description
In `TransferActuator.validate`, the only checks performed on `toAddress` are format validity and inequality to the sender's own address: [3](#0-2)  There is no denylist/blacklist check preventing `toAddress` from being the reserved zero-value address.

In `TransferActuator.execute`, if no account exists yet at `toAddress` (which will be the case for the zero address, since it is never pre-allocated in genesis and no one can derive a private key that hashes to it), a brand-new `AccountCapsule` is silently created there and the funds are credited to it: [1](#0-0)  and then `adjustBalance(accountStore, toAddress, amount)` moves the value in. [4](#0-3) 

`TransferAssetActuator.validate` has the identical pattern for TRC10 asset transfers — `DecodeUtil.addressValid(toAddress)` plus a self-transfer check, with no zero-address denylist: [5](#0-4) 

This is the direct java-tron analog of the reported bug class: a caller-supplied recipient address is accepted and used for an unconditional fund transfer, with no check excluding the well-known "null"/zero address. As the external report's exploit scenario describes (a withdrawal/transfer script bug leaving the `to` field defaulted/zeroed), any wallet, exchange, or automated payout script on TRON that fails to properly populate the 21-byte `to_address` (e.g., a bug that zero-fills the byte buffer but leaves the network prefix byte set, or that otherwise nulls out the payload while keeping the 21-byte structure) will have its funds accepted by the chain and irrecoverably locked in an account nobody controls.

### Impact Explanation
Funds (TRX and TRC10 tokens) sent via `TransferContract`/`TransferAssetContract` to the zero-format address are permanently and irrecoverably frozen: no private key can produce a public key whose hash160 equals the all-zero value, so the resulting account can never be spent from. This is a permanent freezing-of-funds condition, matching the accepted impact categories for this analysis.

### Likelihood Explanation
Likelihood is driven entirely by external tooling/script correctness rather than by any privileged or malicious actor — precisely the scenario the original report calls out (an automated process with an uninitialized/zeroed `to` argument). Since `DecodeUtil.addressValid` only enforces length and network-prefix byte, any 21-byte buffer with the correct prefix and zeroed payload is accepted by the node, so a single logic bug in any wallet, exchange withdrawal batcher, or bridge relayer submitting TRON transfers is sufficient to trigger irreversible loss, with no additional conditions required on-chain.

### Recommendation
Add an explicit check in `TransferActuator.validate` and `TransferAssetActuator.validate` (and any other actuator that accepts a caller-supplied recipient address for value transfer, e.g. `DelegateResourceActuator`) rejecting `toAddress` values equal to the all-zero payload (`0x41` followed by 20 zero bytes), in addition to the existing length/prefix and self-transfer checks. Consider extending `DecodeUtil.addressValid` itself to reject this reserved value so the protection is applied uniformly across all actuators that reuse this utility.

### Proof of Concept
1. Construct a `TransferContract` (or `TransferAssetContract`) protobuf message with `owner_address` set to a valid funded account and `to_address` set to 21 bytes: `0x41` followed by 20 `0x00` bytes.
2. Sign and broadcast the transaction as an ordinary unprivileged user.
3. `TransferActuator.validate` passes because `DecodeUtil.addressValid` only checks length (21) and prefix (`0x41`), and the zero address differs from `owner_address`. [3](#0-2) 
4. `TransferActuator.execute` finds no existing account at the zero address, creates a new `AccountCapsule` there, and credits it with the transferred amount. [6](#0-5) 
5. The funds are now held by an account with no corresponding private key and are permanently unspendable.
