### Title
`simulate_intents` reports success for `AuthCall`/`NotifyOnTransfer`/`StorageDeposit` intents whose real callee-side callback would revert - (File: contracts/defuse/core/src/engine/state/cached.rs)

### Summary
`simulate_intents` runs the exact same `Engine`/intent logic as `execute_intents`, but against a `CachedState<Contract>` wrapper instead of the real `Contract`. For intents that in real execution schedule a cross-contract `Promise` and depend on its outcome (`AuthCall`, `NotifyOnTransfer`, `StorageDeposit`, `NativeWithdraw`), `CachedState`'s `State` implementation just mutates the in-memory balances optimistically and never invokes the external callee, since (per its own comment) "Simulation that uses a cached state cannot create promises, as it is a view call."

### Finding Description
`simulate_intents` is documented/expected (per the in-scope rules) to reflect what `execute_intents` will do. The engine dispatch is identical for both paths — `Engine::execute_signed_intents` — the only difference is the `State`/`StateView` implementation injected: [1](#0-0) 

For real execution, `Contract::auth_call` (in `contracts/defuse/src/contract/intents/state.rs`) withdraws the signer's wNEAR (if any attached deposit) and dispatches a `Promise` to an arbitrary `contract_id` calling `on_auth`, whose success is entirely determined by the callee contract (an arbitrary, attacker- or third-party-controlled receiver): [2](#0-1) [3](#0-2) 

For simulation, `CachedState::auth_call` just debits the balance and returns `Ok(())` without ever invoking the target contract or checking any success/failure condition of `on_auth`: [4](#0-3) 

Similarly, `notify_on_transfer` (used for `Transfer`/`Deposit`'s notification, `mt_on_transfer` hooks) is a complete no-op under `CachedState`, explicitly noted: [5](#0-4) 

while the real implementation actually dispatches the notify promise and later resolves/refunds based on the receiver's response: [6](#0-5) [7](#0-6) 

`storage_deposit` behaves the same way — cached state just debits the wNEAR balance, whereas real execution unwraps wNEAR and calls `do_storage_deposit` via a promise chain that can fail: [8](#0-7) [9](#0-8) 

This class of bug maps directly to the `BunniQuoter` report: a "quoter"/simulation function skips invoking receiver-side hook logic that can gate or alter the real outcome (e.g., an arbitrary `on_auth` receiver that reverts based on caller identity, deposit amount, or state — analogous to a KYC-gated `hookletBeforeDeposit`). `simulate_intents` will therefore report `Ok`/success for a batch of `MultiPayload`s containing an `AuthCall`/`NotifyOnTransfer`/`StorageDeposit` intent even when the real `execute_intents` call would later fail at the promise-resolution stage (e.g., attached deposit permanently withdrawn from the signer with no automatic refund path for `AuthCall`, since there is no `do_auth_call` result check that credits money back on `on_auth` failure) or diverge in balance effects from what was reported by the simulation.

### Impact Explanation
This is explicitly called out as a valid High-impact class in this analysis: "`simulate_intents` diverging from `execute_intents`." Relayers/solvers that rely on `simulate_intents` to decide whether to submit a bundle of signed intents on-chain can be misled into executing (and paying gas for) batches that revert or, worse, that succeed on-chain but leave the signer's wNEAR spent on an `auth_call` whose external callback fails with no compensating refund logic, producing a mismatch between the previewed and actual value delivered to/deducted from the signer.

### Likelihood Explanation
Likelihood is medium: any account can freely construct a `MultiPayload` containing an `AuthCall` (or `Transfer`/`Deposit` with `NotifyOnTransfer`, or `StorageDeposit`) intent targeting an arbitrary or malicious contract, sign it, and probe `simulate_intents` (a view call, cheap and unrestricted) to see it "succeed," then have a relayer submit the identical payload to `execute_intents`, where the real cross-contract call diverges based on the callee's actual logic.

### Recommendation
Either make `simulate_intents` conservative for intents whose outcome depends on an external cross-contract call it cannot execute (e.g., mark such intents' outcome as "unknown"/best-effort in the `SimulationOutput`, rather than reporting unconditional success), or document explicitly (and enforce at the relayer layer) that `simulate_intents` success is not a guarantee for `AuthCall`, `NotifyOnTransfer`, and `StorageDeposit` intents. At minimum, ensure `execute_intents` never leaves signer funds unrecoverable when `AuthCall`'s downstream `on_auth` promise fails (currently `do_auth_call` in `contracts/defuse/src/contract/intents/auth_call.rs` has no failure branch that refunds the withdrawn attached deposit back to the signer).

### Proof of Concept
1. Attacker deploys `MaliciousReceiver`, whose `on_auth` implementation always panics (or accepts unconditionally regardless of state, unlike what it will do at real-execution time e.g. based on caller reputation checked via storage that is populated between simulate and execute).
2. Attacker signs a `MultiPayload` with an `AuthCall { contract_id: MaliciousReceiver, attached_deposit: X, msg }`.
3. Attacker (or an unsuspecting relayer) calls `simulate_intents([payload])`; because `CachedState::auth_call` (`contracts/defuse/core/src/engine/state/cached.rs:362-374`) never invokes `MaliciousReceiver::on_auth`, the simulation returns success with no `invariant_violated` and debits the wNEAR balance only in the ephemeral cached state.
4. Relayer submits the same payload via `execute_intents`. The real `Contract::auth_call` withdraws wNEAR from the signer's real balance and fires the promise to `MaliciousReceiver::on_auth`, which panics. `do_auth_call` (`contracts/defuse/src/contract/intents/auth_call.rs:17-37`) has no failure handling to refund the withdrawn deposit, so the signer's wNEAR is permanently lost even though the simulated preview showed a clean success with no funds-loss warning.

    fn simulate_intents(&self, signed: Vec<MultiPayload>) -> SimulationOutput {
        let mut inspector = SimulateInspector::default();
        let engine = Engine::new(self.cached(), &mut inspector);

        let invariant_violated = match engine.execute_signed_intents(signed) {
            // do not log transfers
            Ok(_) => None,
            Err(DefuseError::InvariantViolated(v)) => Some(v),
            Err(err) => err.panic(),
        };

        SimulationOutput {
            report: inspector.into_report(),
            invariant_violated,
            state: StateOutput {
                fee: self.fee(),
                current_salt: self.salts.current(),
            },
        }
    }

    #[private]
    pub fn do_auth_call(signer_id: AccountId, auth_call: AuthCall) -> Promise {
        if !auth_call.attached_deposit.is_zero() {
            require!(
                promise_result_checked_void(0).is_ok(),
                "near_withdraw failed",
            );
        }

        let min_gas = auth_call.min_gas();
        let mut p = Promise::new(auth_call.contract_id);

        if let Some(state_init) = auth_call.state_init {
            p = p.state_init(state_init, NearToken::ZERO);
        }

        ext_auth_callee::ext_on(p)
            .with_attached_deposit(auth_call.attached_deposit)
            .with_static_gas(min_gas)
            .on_auth(signer_id, auth_call.msg)
    }

    fn mt_resolve_transfer(
        &mut self,
        previous_owner_ids: Vec<AccountId>,
        receiver_id: AccountId,
        token_ids: Vec<TokenId>,
        #[allow(unused_mut)] mut amounts: Vec<U128>,
        approvals: Option<Vec<Option<Vec<ClearedApproval>>>>,
    ) -> Vec<U128> {
        require!(approvals.is_none(), "approvals are not supported");
        require!(
            !token_ids.is_empty()
                && previous_owner_ids.len() == token_ids.len()
                && amounts.len() == token_ids.len(),
            "invalid args"
        );

        let mut refunds = promise_result_checked_json_with_len::<Vec<U128>>(0, amounts.len())
            .ok()
            .and_then(Result::ok)
            .filter(|refund| refund.len() == amounts.len())
            .unwrap_or_else(|| amounts.clone());

        let sender_id = previous_owner_ids.first().cloned().unwrap();

        for ((token_id, previous_owner_id), (amount, refund)) in token_ids
            .iter()
            .map(|token_id| token_id.parse().unwrap_or_else(|e| panic!("{e}")))
            .zip(previous_owner_ids)
            .zip(amounts.iter_mut().zip(&mut refunds))
        {
            require!(
                sender_id == previous_owner_id,
                "approvals are not supported"
            );

            refund.0 = refund.0.min(amount.0);
            let Some(receiver) = self
                .accounts
                .get_mut(&receiver_id)
                // NOTE: refunds from locked accounts are allowed to prevent
                // senders from loss of funds.
                //
                // Receiver's account might have been locked between
                // `mt_transfer_call()` and `mt_resolve_transfer()`, so that
                // outgoing transfers are no longer allowed for this account.
                // But here we distinguish between regular transfers and
                // refunds, despite it would lead to `mt_transfer` event
                // emitted with `old_owner_id` being the locked account.
                //
                // Locked receivers still won't be able to transfer funds in
                // `<receiver_id>::on_mt_transfer()` implementation.
                .map(Lock::as_inner_unchecked_mut)
            else {
                // receiver doesn't have an account, so nowhere to refund from
                return amounts;
            };
            let receiver_balance = receiver.token_balances.amount_for(&token_id);
            // refund maximum what we can
            refund.0 = refund.0.min(receiver_balance);
            if refund.0 == 0 {
                // noting to refund
                continue;
            }

            // withdraw refund
            receiver
                .token_balances
                .sub(token_id.clone(), refund.0)
                .unwrap();
            // deposit refund
            self.accounts
                .get_or_create(previous_owner_id)
                // refunds are allowed for locked accounts
                .as_inner_unchecked_mut()
                .token_balances
                .add(token_id, refund.0)
                .unwrap();

            // update as used amount in-place
            amount.0 -= refund.0;
        }
