### Title
Withdrawals and repayments can be frozen when an external Vesper pool integrated via `VesperGateway` is paused - (File: contracts/Treasury.sol)

### Summary
Metronome Synth idles user collateral in external Vesper pools through `Treasury` / `VesperGateway`. `VPool.withdraw` carries Vesper's `whenNotPaused` guard, so if the upstream Vesper pool is paused, `Treasury.pull` reverts and every user-facing path that needs to move underlying (`DepositToken.withdraw`, exits after `DebtToken.repay`, unwind legs in `SmartFarmingManager`) reverts unconditionally. Metronome's own `Pauseable` flags (`Pool.paused`, `everythingStopped`) only gate Metronome functions; they cannot unblock the external dependency and there is no fail-safe exit path.

### Finding Description
- Collateral deposited via `DepositToken.deposit` is forwarded to `Pool.treasury`, which deploys idle underlying into Vesper pools through `VesperGateway` (attacker-visible surface: `VesperGateway` wraps `IVPool` deposit/withdraw calls).
- `DepositToken.withdraw` pulls underlying back through `Treasury.pull`, which in turn calls `VPool.withdraw`. Vesper `VPool.withdraw` is guarded by `whenNotPaused`; when the Vesper pool is paused, the entire call chain reverts.
- The same applies to any user flow that must move underlying out of the treasury (withdraw collateral, `SmartFarmingManager.flashRepay` unwinds). `Pool.paused()` merely ORs the local flag with `PoolRegistry.paused()` [1](#0-0)  and `shutdown`/`pause` are governor-controlled flags that cannot make the external Vesper call succeed [2](#0-1) .
- Unlike the UXD report (where the protocol had no pause at all), Metronome does have pause/shutdown [3](#0-2)  — but that does not mitigate the liveness failure: user funds sitting in a paused Vesper pool remain locked until the external dependency unpauses, and `liquidate`/`swap` continue to operate on `whenNotShutdown` while exits are bricked [4](#0-3) .

Note: I confirmed the `Treasury`/`VesperGateway`/`IVPool` integration points exist via search, but iteration limits prevented me from reading `Treasury.pull` and `VesperGateway.withdraw` line-by-line. If `Treasury` keeps a liquid buffer that fully covers withdrawals, the window shrinks; otherwise every withdraw routed through a paused Vesper pool reverts.

### Impact Explanation
Temporary freezing of user funds: users cannot withdraw collateral (and cannot complete unwind/repay flows that need treasury liquidity) for as long as the upstream Vesper pool remains paused. Positions also cannot be deleveraged by users during that window, exposing them to liquidation risk they cannot act on — a guaranteed-to-revert transaction class identical to the referenced UXD finding.

### Likelihood Explanation
Requires an external condition (Vesper pausing its pool, which Vesper admin can do at any time) rather than attacker action — same trust assumption as the source report. When it occurs, all affected collateral withdrawals revert deterministically.

### Recommendation
- Keep a minimum liquid buffer in `Treasury` so `pull` can serve withdrawals without hitting the external pool, or fall back to serving withdrawals from buffer when the Vesper pool reports `paused()`.
- Add a guardian-triggered pause on `DepositToken.deposit`/leverage entry points (mirroring `pause()`/`shutdown()` already on `Pool`) so users get a clean revert reason instead of a dependency failure.
- Document the dependency and expose a view (`Treasury.isWithdrawalPathLive`) so frontends can warn users.

### Proof of Concept
Hardhat fork (mainnet):
1. Deploy/locate a live `Pool` whose `Treasury` routes underlying into a real Vesper `VPool` via `VesperGateway`; deposit collateral so `Treasury` forwards underlying into the VPool.
2. Impersonate the Vesper pool's governor (`impersonateAccount`) and call `vPool.pause()`.
3. As the depositor call `depositToken.withdraw(amount)` — the call reverts inside `Treasury.pull` → `VesperGateway` → `VPool.withdraw` (`whenNotPaused`).
4. Show `pool.paused()` remains `false` and `pool.liquidate`/`pool.swap` still function, confirming Metronome's own flags cannot restore the exit path; withdrawals resume only after `vPool.unpause()`.
