### Title
Cross-contract StackerDB chunk-signature replay allows unauthorized write/smuggling of forged data into unrelated signer message channels - ([File: libstackerdb/src/libstackerdb.rs])

### Summary
`SlotMetadata::auth_digest()` binds a signature only to `slot_id`, `slot_version`, and `data_hash` — it never binds to the target smart contract (StackerDB) that the chunk is being posted to. Because the `.signers-{set}-{message_id}` StackerDB contracts all derive their slot assignment from the same per-signer-set slot list (`stackerdb-get-signer-slots-page`), the same signer address occupies the *same* `slot_id` across every message-type contract (`signers-0-1`, `signers-0-2`, `signers-0-3`, etc.). Any unprivileged remote peer that observes one validly-signed chunk (chunks are broadcast/public) can replay it verbatim to a different message-type contract, and it will pass every check in `StackerDBTx::try_replace_chunk` / `PeerNetwork::validate_received_chunk`, since none of those checks are contract-scoped.

### Finding Description
`SlotMetadata::auth_digest()` ( [1](#0-0) ) computes:
```
hash(slot_id || slot_version || data_hash)
```
with no `smart_contract`/`QualifiedContractIdentifier` component. `verify()` ( [2](#0-1) ) simply recovers the public key from this digest and checks it against the *slot's* expected signer address — again with no dependency on which contract is being validated.

The actual write/validation path, `StackerDBTx::try_replace_chunk`, only checks chunk size, slot signer (via the contract-agnostic digest), staleness, and max-writes — never the contract identity itself as part of the authenticated payload: [3](#0-2) 

The P2P unsolicited-push validation path has the identical gap: [4](#0-3) 

Signer-message contracts are provisioned with **identical slot layouts across message types** for a given signer set, since every `signers-{set}-{message_id}` contract calls the same `stackerdb-get-signer-slots-page` for that set: [5](#0-4) [6](#0-5) 
So signer address `A` at `slot_id = k` in `signers-0-1` (BlockResponse) is the same `A` at `slot_id = k` in `signers-0-3` (BlockPreCommit), `signers-0-2` (StateMachineUpdate), etc. ( [7](#0-6) , [8](#0-7) ).

The HTTP write endpoint that stores a chunk performs no additional binding of the signature to the target contract path parameter — it just forwards the caller-controlled `contract_identifier` to `try_replace_chunk`, and requires no authentication: [9](#0-8) 

**Attack**: An attacker (any unprivileged network participant, node operator, or even a passive observer of gossip) obtains a validly-signed chunk that signer `A` posted to contract `signers-0-1` slot `k` (BlockResponse). The attacker POSTs (or P2P-pushes) the exact same `(slot_id, slot_version, sig, data)` tuple to `signers-0-3` (BlockPreCommit) or `signers-0-2` (StateMachineUpdate) at the same slot. Since `A` is also the registered signer for slot `k` in that other contract, and the auth digest/signature check is contract-agnostic, the write succeeds and overwrites/advances slot `k`'s version in the *unrelated* contract with forged content that signer `A` never intended to publish there. The store also triggers rebroadcast to the network: [10](#0-9) 

This breaks the "authenticated vs. stored" equality: the node treats a signature valid for context A as valid for context B, storing and propagating attacker-chosen, cross-context data as if it were authentically posted to that specific message channel.

### Impact Explanation
This is a remote, unauthenticated write of forged data into a signer's message-type-specific StackerDB slot and network-wide propagation of that forged/smuggled data via `process_stacker_db_chunks`/`handle_unsolicited_StackerDBPushChunk` broadcast. It can be used to: pollute/overwrite BlockPreCommit or StateMachineUpdate slots with stale/irrelevant BlockResponse payloads, consume a signer's `max_writes` budget in a channel the signer never intended to write to, and disrupt downstream signer-to-signer coordination (since receivers must now defensively detect and drop cross-type payloads, if they even do). It does not require the signer's private key, only public observation of one legitimately-signed chunk from any contract that shares the same slot assignment. This matches "unauthenticated/unauthorized write to state or StackerDB" and "network-wide propagation of forged data."

### Likelihood Explanation
High. Chunks are gossiped and openly queryable (`GET /v2/stackerdb/...` and P2P `StackerDBGetChunk`), so obtaining a valid signed chunk from one contract is trivial. Re-posting it to a sibling contract requires only knowing the target `contract_identifier` and slot ID, both public/derivable from `make_signers_db_contract_id`. No cryptographic material or privileged role is needed.

### Recommendation
Include the smart contract identifier (or a fixed protocol-specific message-type tag derived from it) as part of `SlotMetadata::auth_digest()`, so a signature computed for one StackerDB contract cannot be replayed against another. This requires threading the `QualifiedContractIdentifier` (or equivalent binding) into `sign()`/`verify()` in `libstackerdb/src/libstackerdb.rs`, and updating all callers (`StackerDBTx::try_replace_chunk`, `PeerNetwork::validate_received_chunk`, `poststackerdbchunk.rs`, and signer client `stackerdb.rs`) to pass and check it.

### Proof of Concept
1. Signer `A` legitimately posts a `BlockResponse` chunk to `signers-0-1` at `slot_id = k`, `slot_version = v`, producing `(data, sig)` where `sig` verifies via `SlotMetadata::auth_digest()` = `hash(k || v || sha512_256(data))`.
2. Attacker fetches this chunk (`GET /v2/stackerdb/<addr>/signers-0-1/<k>` or via P2P `StackerDBGetChunkData`).
3. Attacker determines that `A` also occupies `slot_id = k` in `signers-0-3` (BlockPreCommit) — true by construction, since both contracts share the same signer-slot list for signer set 0 ( [5](#0-4) ).
4. Attacker POSTs the identical `(slot_id=k, slot_version=v, sig, data)` to `/v2/stackerdb/<addr>/signers-0-3/chunks`.
5. `try_replace_chunk` ( [11](#0-10) ) calls `slot_desc.verify(&slot_validation.signer)`, which succeeds because the digest never referenced `signers-0-3` vs `signers-0-1`. The chunk is accepted, stored under `signers-0-3`'s slot `k` (overwriting whatever legitimate BlockPreCommit content existed there), and rebroadcast to peers via `process_stacker_db_chunks`.

This confirms attacker-controlled cross-contract chunk smuggling with no signer cooperation and no privileged access required.

    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
