Confirmed: `Middleware.repoActivity` (`internal/grpc/middleware/housekeeping/middleware.go`) is a plain Go map keyed by `repoKey{storage, relativePath}` that is populated on essentially every mutator/accessor RPC via `scheduleHousekeeping`/`markHousekeepingActive`/`markHousekeepingInactive`, and there is no eviction, cap, or cleanup logic anywhere in the file — I searched for `delete(m.repoActivity`, size caps, and eviction and found none.

### Title
Unbounded growth of the housekeeping middleware's `repoActivity` map via low-cost mutator RPCs to distinct repository paths - (File: internal/grpc/middleware/housekeeping/middleware.go)

### Summary
The Gitaly housekeeping gRPC middleware maintains an in-memory map, `Middleware.repoActivity`, that tracks per-repository write counters used to decide when to schedule background `OptimizeRepository` work. An entry is added to this map on nearly every mutator RPC handled through the interceptor, but the map is never pruned or bounded, so a client that issues many mutator RPCs against a large number of distinct (including nonexistent) repository paths can grow this map without bound, analogous to the referenced report where cheap, unchecked calls (`share == 0` withdrawals) inflate an unbounded on-chain queue that a privileged actor later has to process at high cost.

### Finding Description
`UnaryServerInterceptor` and `StreamServerInterceptor` call `scheduleHousekeeping` for every `OpMutator` RPC after the underlying handler runs: [1](#0-0) 

`scheduleHousekeeping` only skips adding/incrementing an entry for a small set of gRPC error codes (`FailedPrecondition`, `ResourceExhausted`, `PermissionDenied`) and for the `RemoveRepository` RPC specifically: [2](#0-1) 

Every other outcome — including common failures such as "repository not found" (`NotFound`), `InvalidArgument`, or `Internal` — falls through to `scheduleHousekeeping`, which unconditionally creates a new `*activity` (with its own nested `writeCountAtLastRun` map) keyed by `repoKey{storage, relativePath}` if one doesn't already exist: [3](#0-2) 

`markHousekeepingActive`/`markHousekeepingInactive` and `isActive`, used for `OpMaintenance` RPCs, likewise lazily create map entries keyed by the target repository without any size limit: [4](#0-3) 

The `Middleware` struct declares `repoActivity map[repoKey]*activity` with no maximum size, TTL, or LRU eviction mechanism: [5](#0-4) 

Because `repoKey` is derived from the RPC's `Repository` field (`storage`, `relative_path`), which is attacker-controlled in the RPC payload, and the map entry is created regardless of whether the target repository actually exists on disk, an ordinary authenticated client can trigger unbounded map growth simply by sending cheap mutator RPCs (e.g. `WriteRef`) against a large number of distinct, possibly bogus, `relative_path` values. Each such call is inexpensive for the client (the handler quickly returns a `NotFound`-class error) but permanently grows server memory, since nothing ever removes stale `repoKey` entries.

### Impact Explanation
Unbounded growth of an in-process map keyed by attacker-supplied values is a memory-exhaustion vector: each `repoKey` plus its `*activity` (with a `map[config.OperationType]int` nested inside) consumes real heap memory that is never reclaimed for the process lifetime. A sustained stream of mutator RPCs against unique bogus repository paths can drive Gitaly's memory usage up until the process is OOM-killed, causing denial of service for the entire Gitaly node (affecting all repositories and tenants served by that node, not just the attacker's own repository) — the same DoS pattern described in the reference report where an unbounded internal structure grows from cheap calls until it burdens/starves the system.

### Likelihood Explanation
Any client with routine access to invoke a mutator RPC (a normal, non-privileged GitLab/Gitaly client performing a push or similar mutating operation) can reach this path — reaching `scheduleHousekeeping` does not require the target repository to exist, only that the handler return an error code outside the small exclusion list. This makes the issue reachable from ordinary, unprivileged RPC traffic with no special timing or race conditions required, though it does require sustained traffic across many distinct relative paths to accumulate a memory-significant number of entries.

### Recommendation
Bound the size of `repoActivity` (e.g., LRU eviction with a maximum entry count or TTL-based expiry of inactive entries), and/or validate that the target repository actually exists (or that the mutator RPC succeeded) before creating a housekeeping-tracking entry for it, mirroring how the concurrency limiter bounds its per-key queue via `maxQueueLength`/`max_queue_size`.

### Proof of Concept
1. As an ordinary authenticated Gitaly client, repeatedly call a cheap `OpMutator` RPC (e.g. `RepositoryService/WriteRef`) with a `Repository{StorageName: "default", RelativePath: <unique-random-string>}` for a large number of unique `RelativePath` values that do not correspond to real repositories.
2. Each call's handler quickly fails with a non-excluded error code (e.g., `NotFound`), so `scheduleHousekeeping` is invoked and inserts a new `repoActivity[repoKey{...}]` entry `internal/grpc/middleware/housekeeping/middleware.go:337-368`.
3. Because there is no eviction path, `repoActivity` grows by one entry (plus its nested map) per unique `RelativePath` sent, indefinitely, consuming heap memory proportional to the number of distinct fake paths submitted, with no cost to the caller beyond issuing lightweight RPCs.

func (m *Middleware) markHousekeepingActive(key repoKey) {
	a, ok := m.repoActivity[key]
	if !ok {
		a = newActivity()
		m.repoActivity[key] = a
	}

}

func (m *Middleware) markHousekeepingInactive(key repoKey) {
	m.mu.Lock()
	defer m.mu.Unlock()

	a, ok := m.repoActivity[key]
	if !ok {
		a = newActivity()
		m.repoActivity[key] = a
	}

	a.active = false
}

func (m *Middleware) isActive(key repoKey) bool {
	a, ok := m.repoActivity[key]
	if !ok {
		return false
	}

	return a.active
}

func (m *Middleware) scheduleHousekeeping(ctx context.Context, repo *gitalypb.Repository, force bool) {
	m.mu.Lock()
	defer m.mu.Unlock()

	key := m.getRepoKey(repo)

	a, ok := m.repoActivity[key]
	if !ok {
		a = newActivity()
		m.repoActivity[key] = a
	}
	a.writeCount++

	if a.active {
		return
	}

	pendingOps := m.pendingOperations(a, force)
	if len(pendingOps) == 0 {
		return
	}

	m.logger.WithFields(log.Fields{
		"forced":     force,
		"operations": pendingOps,
	}).InfoContext(ctx, "beginning scheduled housekeeping")

	// Mark that these operations are running at the current write count
	for _, op := range pendingOps {
		a.writeCountAtLastRun[op] = a.writeCount
	}
