## Analysis

The Moodle CVE describes a bug class where **removing an authorization grant doesn't revoke the associated capability** — the runtime keeps enforcing a stale permission after the underlying entitlement is gone. I traced this class through the StackerDB write-authorization path in this repo and found a reachable analog.

### Title
StackerDB reconfiguration skips revocation when a signer set legitimately shrinks to zero, letting an unauthorized (removed) signer keep writing chunks - (File: `stackslib/src/net/stackerdb/mod.rs`)

### Summary
When a StackerDB-backing contract legitimately reports zero signers for a reward cycle (e.g. insufficient stacking participation), `create_or_reconfigure_stackerdbs` skips calling `reconfigure_stackerdb`, so the previous cycle's per-slot signer bindings are never cleared from the on-disk `chunks` table. Because the write-path (`try_replace_chunk`) authorizes purely from that persisted per-slot binding — not from the in-memory `StackerDBConfig` — a signer who was removed from the signer set can continue submitting validly-signed chunks to the stale slot indefinitely.

### Finding Description
`StackerDBs::create_or_reconfigure_stackerdbs` only calls `reconfigure_stackerdb` for an existing replica when:
```
(new_config != stackerdb_config && !new_config.signers.is_empty())
    || (new_config == stackerdb_config && new_config.signers.len() != self.get_slot_versions(...)?.len())
``` [1](#0-0) 

The `!new_config.signers.is_empty()` guard was added to protect against a `noop()` fallback (used only on a *failed* contract-call) transiently wiping a good config, as documented at `StackerDBConfig::noop()` [2](#0-1) . However, this same guard also fires on a *legitimate* empty signer set: the `.signers` boot contract explicitly returns an empty `stackerdb_list` when `has_participation` is false for a reward cycle:
```
let stackerdb_list = if !has_participation { vec![] } else { ... }
``` [3](#0-2) [4](#0-3) 

So the config-comparison guard cannot distinguish "config load failed, keep old state as a safety net" from "signer set was legitimately revoked to empty." In the latter case `reconfigure_stackerdb` — which is what actually resets the per-slot `signer` column in the `chunks` table when ownership changes [5](#0-4)  — is never invoked, so stale slot bindings from the prior (now-revoked) signer set remain in the database.

Critically, the actual write-authorization check does not consult the in-memory `StackerDBConfig.signers` at all. `try_replace_chunk` authorizes a submitted chunk purely against the persisted `slot_validation.signer` for that slot:
```
let slot_validation = self.get_slot_validation(smart_contract, slot_desc.slot_id)?...
if !slot_desc.verify(&slot_validation.signer)? { return Err(net_error::BadSlotSigner(...)); }
``` [6](#0-5) 
and the HTTP POST handler calls this directly with no separate cross-check against the "current" config: [7](#0-6) 

Consequently, a previously-valid signer whose entitlement was revoked (signer set now legitimately empty) is never actually revoked at the DB layer — their key still recovers correctly against the stale `slot_validation.signer` row, and they can keep incrementing the slot version and pushing chunks (as long as `max_writes`/`write_freq` from the stale config still permit it, since the in-memory config also isn't refreshed).

This is the same equality break as the Moodle bug: **authenticated-as-current-signer vs. actually-still-authorized** — the code checks "is this signature valid for the *stored* owner of this slot" rather than "is this signer currently in the *authoritative* signer set."

### Impact Explanation
This is an unauthorized write to StackerDB state by a party whose write capability was supposed to have been revoked. Depending on which StackerDB is affected (e.g. a signer-message StackerDB), a removed/rotated-out signer could continue injecting messages into the replicated DB that other nodes and signers may still treat as coming from a validly-configured slot, which is a network-relevant integrity issue for the corresponding protocol (e.g., signer coordination messages).

### Likelihood Explanation
This triggers under a legitimate, attacker-uninvolved condition (reward cycle with `has_participation == false`, or a reward cycle's derived signer set becoming empty) that requires no privileged access — it is purely a consequence of state transitions the node processes automatically. Any account previously holding a slot in that StackerDB can exploit it by simply continuing to sign with their existing key.

### Recommendation
Distinguish "config load failure -> fall back to `noop()`" from "legitimately empty signer set" in `create_or_reconfigure_stackerdbs`, and in the latter case still call `reconfigure_stackerdb` (or an explicit clear) so that stale slot-to-signer bindings are wiped whenever the authoritative signer set no longer contains them, rather than gating reconfiguration solely on `!new_config.signers.is_empty()`.

### Proof of Concept
1. Node replicates a StackerDB contract with signers `[A]` for reward cycle `N` (slot 0 bound to `A`).
2. At reward cycle `N+1`, participation drops (`has_participation = false`), so the boot contract returns an empty `stackerdb_list`/signer list.
3. `StackerDBConfig::from_smart_contract` returns `signers: vec![]` for cycle `N+1`.
4. In `create_or_reconfigure_stackerdbs`, the guard `!new_config.signers.is_empty()` is false, so `reconfigure_stackerdb` is skipped; slot 0's DB row still lists `A` as `signer`.
5. `A` continues to POST `/v2/stackerdb/.../chunks` with a validly-signed, version-incremented chunk; `try_replace_chunk` validates it against the stale `slot_validation.signer == A` and accepts it, despite `A` no longer being part of the authoritative signer set for cycle `N+1`.

    pub fn reconfigure_stackerdb(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slots: &[(StacksAddress, u32)],
    ) -> Result<(), net_error> {
        let stackerdb_id = self.get_stackerdb_id(smart_contract)?;
        let mut total_slots_read = 0u32;
        for (principal, slot_count) in slots.iter() {
            total_slots_read =
                total_slots_read
                    .checked_add(*slot_count)
                    .ok_or(net_error::OverflowError(
                        "Slot count exceeeds u32::MAX".to_string(),
                    ))?;
            let slots_before_principal = total_slots_read - slot_count;
            for cur_principal_slot in 0..*slot_count {
                let slot_id = slots_before_principal + cur_principal_slot;
                if let Some(existing_validation) =
                    self.get_slot_validation(smart_contract, slot_id)?
                {
                    // this slot already exists.
                    if existing_validation.signer == *principal {
                        // no change
                        continue;
                    }
                }

                debug!("Reset slot {} of {}", slot_id, smart_contract);

                // new slot, or existing slot with a different signer
                let qry = "INSERT OR REPLACE INTO chunks (stackerdb_id,signer,slot_id,version,write_time,data,data_hash,signature) VALUES (?1,?2,?3,?4,?5,?6,?7,?8)";
                let mut stmt = self.sql_tx.prepare(qry)?;
                let args = params![
                    stackerdb_id,
                    principal.to_string(),
                    slot_id,
                    NO_VERSION,
                    0,
                    vec![],
                    Sha512Trunc256Sum([0u8; 32]),
                    MessageSignature::empty(),
                ];

                stmt.execute(args)?;
            }
        }
        debug!("Shrink {} to {} slots", smart_contract, total_slots_read);
        self.shrink_stackerdb(stackerdb_id, total_slots_read)?;
        Ok(())
    }
