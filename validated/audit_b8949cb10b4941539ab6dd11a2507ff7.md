### Title
Cross-repository object disclosure via unvalidated `git_object_directory`/`git_alternate_object_directories` on accessor RPCs - ([File: internal/git/gitcmd/command_factory.go], [File: internal/git/alternates/alternates.go], [File: internal/gitaly/storage/storagemgr/middleware.go])

### Summary
Gitaly's git command execution path (`ExecCommandFactory.newCommand` → `alternates.Env`) blindly joins the attacker-controlled `Repository.git_object_directory` / `git_alternate_object_directories` fields onto the target repository's path and injects them as `GIT_OBJECT_DIRECTORY`/`GIT_ALTERNATE_OBJECT_DIRECTORIES` env vars, with **no** call to `storage.ValidateRelativePath` or any repository-ownership check. The only gate that exists is in `storagemgr/middleware.go`'s `beginTransactionForRepository`, which rejects quarantine fields on mutators but, for accessor RPCs, simply requires a client-supplied gRPC metadata header (`relative-path-bin`) to be present — a value the attacker fully controls — before letting the request through untransacted with the crafted fields intact.

### Finding Description
`gitalypb.Repository` exposes `GitObjectDirectory` and `GitAlternateObjectDirectories` as free-form client-settable fields [1](#0-0) . These fields are consumed in two different places with very different levels of validation:

1. `localrepo.Repo.ObjectDirectoryPath` (used e.g. by `GetObjectDirectorySize`) validates the path with `storage.ValidateRelativePath` against the storage root and additionally requires that, if the path isn't a sub-path of the repo itself, it match a repository-specific quarantine-directory prefix [2](#0-1) .
2. `ExecCommandFactory.newCommand`, which is the path used by essentially every git-invoking RPC (`GetBlob`, `FindCommit`, `TreeEntry`, `IsAncestor`, etc.), does **not** use `ObjectDirectoryPath` at all. It calls `alternates.Env(repoPath, repo.GetGitObjectDirectory(), repo.GetGitAlternateObjectDirectories())` directly [3](#0-2) , and `alternates.Env` performs a bare `filepath.Join(repoPath, dir)` for every configured directory with **no bounds checking whatsoever** [4](#0-3) .

The only defense against an attacker directly setting these fields on an ordinary (non-hook) RPC is in the transaction middleware. `beginTransactionForRepository` detects a non-empty `GitObjectDirectory`/`GitAlternateObjectDirectories` and, for **mutator** RPCs, unconditionally rejects the request (`ErrQuarantineConfiguredOnMutator`) [5](#0-4) . For **accessor** RPCs, however, it does not reject — it instead calls `restoreSnapshotRelativePath` and returns the request as a `nonTransactionalRequest`, i.e. no transaction/snapshot verification is performed [6](#0-5) . `restoreSnapshotRelativePath` requires only that the gRPC metadata key `relative-path-bin` (`MetadataKeySnapshotRelativePath`) be present, failing with `ErrQuarantineWithoutSnapshotRelativePath` if it's missing [7](#0-6) ; test cases confirm the value from this header is copied verbatim into `Repository.RelativePath` with no verification that it corresponds to a real transaction snapshot the caller is authorized to use [8](#0-7) . Since this is an ordinary client-settable gRPC metadata header, an unprivileged attacker can set it to any value, including the relative path of their own repository A.

Combining these facts: an attacker who owns repo A can send an accessor RPC (e.g. `GetBlob`) with `Repository{relative_path: A, git_alternate_object_directories: ["../<repoB-hash>/objects"]}` plus an arbitrary `relative-path-bin` metadata header. The middleware lets the request through unmodified (since it is an accessor, not a mutator), and the RPC handler then executes a git command through `ExecCommandFactory.newCommand`, which computes `GIT_ALTERNATE_OBJECT_DIRECTORIES=<storageRoot>/A/../<repoB-hash>/objects` via `alternates.Env` with zero path validation. Git will then happily search repo B's object store for the requested object, disclosing its content to the attacker even though they have no access rights to repo B.

### Impact Explanation
This breaks the fundamental repository isolation invariant: an unprivileged user who owns any repository on a shared storage can read blobs, commits, and trees belonging to any other repository on the same storage, provided they can guess or determine that repository's relative path (e.g. via predictable hashed-storage naming or sequential project IDs). This corresponds to a "cross-repository object access" / "unauthorized information disclosure" bounty class — significant on multi-tenant GitLab.com-style deployments where storage-relative paths are largely derived from project IDs.

### Likelihood Explanation
The attacker only needs: (1) an account able to push/fetch to a repository they legitimately own, (2) the ability to issue arbitrary gRPC accessor requests with attacker-chosen `Repository` message fields and metadata (which any GitLab client/API caller effectively controls at the Gitaly protocol level once authenticated for their own repo), and (3) knowledge or a reasonable guess of the target repository's storage-relative path. No admin privileges, no secrets, and no race conditions are required, and the attack is fully repeatable.

### Recommendation
Apply the same validation used in `localrepo.Repo.ObjectDirectoryPath` (storage-root containment plus per-repository quarantine-prefix check) inside `alternates.Env`/`ExecCommandFactory.newCommand` before ever converting `GitObjectDirectory`/`GitAlternateObjectDirectories` into environment variables for the spawned git process. Additionally, harden `beginTransactionForRepository` so that accessor RPCs with these quarantine fields set are only permitted when the transaction/snapshot referenced by `relative-path-bin` can be cryptographically or structurally tied to a transaction actually opened by Gitaly for that request (not an arbitrary client-supplied string), rather than trusting client-supplied metadata.

func TestCrossRepoAlternateObjectDirectoryLeak(t *testing.T) {
    ctx := testhelper.Context(t)
    cfg, client := setupRepositoryService(t) // or blob/commit service client

    // Repo B: private repo containing a secret blob.
    repoB, repoBPath := gittest.CreateRepository(t, ctx, cfg)
    secretOID := gittest.WriteBlob(t, cfg, repoBPath, []byte("super-secret-content"))

    // Repo A: attacker-owned repo.
    repoA, _ := gittest.CreateRepository(t, ctx, cfg)

    // Compute the relative path from repoA to repoB's objects dir.
    relToB, err := filepath.Rel(
        filepath.Join(cfg.Storages[0].Path, repoA.GetRelativePath()),
        filepath.Join(repoBPath, "objects"),
    )
    require.NoError(t, err)

    craftedRepo := proto.Clone(repoA).(*gitalypb.Repository)
    craftedRepo.GitAlternateObjectDirectories = []string{relToB}

    // Satisfy the middleware's requirement of a snapshot-relative-path header
    // with an attacker-controlled arbitrary value (their own repo A's path).
    ctx = metadata.AppendToOutgoingContext(ctx, storagemgr.MetadataKeySnapshotRelativePath, repoA.GetRelativePath())

    resp, err := client.GetBlob(ctx, &gitalypb.GetBlobRequest{
        Repository: craftedRepo,
        Oid:        secretOID.String(),
        Limit:      -1,
    })

    // Expected (buggy) behavior: request succeeds and leaks repo B's blob content
    // even though the caller only had legitimate access to repo A.
    require.NoError(t, err)
    require.Contains(t, string(resp.GetData()), "super-secret-content")
}

// Env returns the alternate object directory environment variables.
func Env(repoPath, objectDirectory string, alternateObjectDirectories []string) []string {
	var env []string
	if objectDirectory != "" {
		env = append(env, fmt.Sprintf("GIT_OBJECT_DIRECTORY=%s", filepath.Join(repoPath, objectDirectory)))
	}

	if len(alternateObjectDirectories) > 0 {
		var dirsList []string

		for _, dir := range alternateObjectDirectories {
			dirsList = append(dirsList, filepath.Join(repoPath, dir))
		}

		env = append(env, fmt.Sprintf("GIT_ALTERNATE_OBJECT_DIRECTORIES=%s", strings.Join(dirsList, ":")))
	}

	return env
}
