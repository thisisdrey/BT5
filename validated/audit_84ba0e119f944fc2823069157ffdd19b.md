### Title
DoS on `unfreezeBalanceV2`/`withdrawExpireUnfreeze` via shared per-contract `UNFREEZE_MAX_TIMES` queue - (File: `actuator/src/main/java/org/tron/core/vm/nativecontract/UnfreezeBalanceV2Processor.java`)

### Summary
Java-tron exposes the `unfreezeBalanceV2(uint256,uint256)` TVM native opcode, which lets any smart contract call TVM's freeze/unfreeze mechanism on its **own account** (`getContextAddress()`), exactly the pattern used by wrapping/pooling contracts such as liquid-staking bridges that act on behalf of many end users pooled into one contract-level stake position — structurally analogous to `BridgeReth` acting on behalf of many DittoETH users against RocketPool. Each unfreeze request appends an entry to the calling contract's own `unfrozenV2List`, which is capped at `UNFREEZE_MAX_TIMES = 32` pending entries per account, and unlocked only after `unfreezeDelayDays` has elapsed.

`Program.unfreezeBalanceV2()` always operates on `getContextAddress()` — i.e. the calling contract's own account, not the individual end user's address: [2](#0-1) 

Each successful call adds one entry to `accountCapsule.getUnfrozenV2List()`/`addUnfrozenV2List`, and these entries remain pending until `calcUnfreezeExpireTime` (based on `unfreezeDelayDays`) is reached: [3](#0-2) [4](#0-3) 

The cap constant is defined once, globally, per account: [5](#0-4) 

This is confirmed by the unit/integration test, which shows that once 32 pending unfreeze entries exist on an account, any further `unfreezeBalanceV2` call on that same account reverts: [6](#0-5) 

For a pooling/wrapping smart contract that lets many unrelated end users each trigger an unfreeze on the contract's shared stake position (the exact analog of `BridgeReth::depositEth`/`withdraw` fanning many users' actions through one on-chain principal), the 32-slot queue is a shared, contract-wide resource. Because the check is keyed to the calling contract's own account rather than per end-user, **any** of the pool's users triggering enough unfreeze operations (or a malicious/careless subset of them) can fill the queue to 32 pending entries, after which all other users of that same pooling contract are blocked from unfreezing/unstaking their own funds until the earliest queued entry expires (governed by `unfreezeDelayDays`, settable by committee proposal via `ProposalService`): [7](#0-6) 

### Impact Explanation
Any smart contract built on top of java-tron's Stake 2.0 TVM opcodes that pools resources/stake for multiple third-party users (a common DeFi/staking-wrapper pattern, mirroring `BridgeReth`) inherits a shared, per-account cap of 32 pending unfreeze slots. A relatively small number of unfreeze calls issued by unrelated users of the pool (or a griefing subset of them) permanently occupies all 32 slots for as long as `unfreezeDelayDays` dictates, preventing every other user of that same contract from unfreezing/withdrawing their own staked TRX. Funds remain locked (frozen) in the contract and are practically unstakeable by their rightful owners for the duration of the delay, which is a temporary but real freezing-of-funds condition scoped to any pooling contract built on this feature.

### Likelihood Explanation
Reaching this path requires only ordinary, permissionless transactions: deploying a pooling contract that internally calls `unfreezeBalanceV2`/`freezeBalanceV2` on behalf of depositors, and having any set of unprivileged callers invoke it enough times to fill the 32-slot queue. No special privilege, witness/committee role, or protocol bug is needed — it is an inherent design property of the shared per-account queue combined with the fact that TVM natively attributes all such operations to `getContextAddress()` rather than per end-user. The likelihood of a DApp author unintentionally building this exposure (as `BridgeReth`'s authors did for RocketPool) is realistic, and a malicious pool participant could deliberately trigger it.

### Recommendation
For contracts that pool multiple users' stake through a single java-tron account, consider that `unfreezeBalanceV2`'s 32-slot limit and shared expire-queue is a global, per-account resource, not per end user. Documentation/guidance for TVM Stake 2.0 integrators should call out this shared-state DoS risk explicitly (similar to the recommendation given for `BridgeReth`), and/or contract authors should track per-user allotments internally and throttle/batch unfreeze calls so that no single depositor's actions can starve the shared 32-entry queue for all other depositors of the pooling contract.

### Proof of Concept
1. Deploy a pooling contract `Pool` that, on behalf of depositors, calls TVM opcode `unfreezeBalanceV2(uint256,uint256)` (which internally always targets `Pool`'s own account via `getContextAddress()`).
2. Have 32 different unrelated callers (or one caller acting 32 times) each trigger `Pool`'s public unfreeze-on-behalf-of-caller function for small amounts, until `Pool`'s `unfrozenV2List` reaches `UNFREEZE_MAX_TIMES` (32) pending entries, as validated in `UnfreezeBalanceV2Processor.validate()` (lines 51-55).
3. A 33rd, legitimate user of `Pool` calls the same unfreeze function to retrieve their own staked funds; the call reverts with `"Invalid unfreeze operation, unfreezing times is over limit"`.
4. That user's funds remain frozen and unwithdrawable until at least one of the 32 queued entries reaches its `unfreezeExpireTime` (`now + unfreezeDelayDays * FROZEN_PERIOD`), which can be many days depending on the live `unfreezeDelayDays` chain parameter.

    VoteRewardUtil.withdrawReward(ownerAddress, repo);

    long unfreezeExpireBalance = this.unfreezeExpire(accountCapsule, now);

    if (repo.getDynamicPropertiesStore().supportAllowNewResourceModel()
        && accountCapsule.oldTronPowerIsNotInitialized()) {
      accountCapsule.initializeOldTronPower();
    }

    long expireTime = this.calcUnfreezeExpireTime(now, repo);
    accountCapsule.addUnfrozenV2List(param.getResourceType(), unfreezeBalance, expireTime);

    this.updateTotalResourceWeight(accountCapsule, param.getResourceType(), unfreezeBalance, repo);
    this.updateVote(accountCapsule, param.getResourceType(), ownerAddress, repo);

    if (repo.getDynamicPropertiesStore().supportAllowNewResourceModel()
        && !accountCapsule.oldTronPowerIsInvalid()) {
      accountCapsule.invalidateOldTronPower();
    }

    repo.updateAccount(accountCapsule.createDbKey(), accountCapsule);

  }
