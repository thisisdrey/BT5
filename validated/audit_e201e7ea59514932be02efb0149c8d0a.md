Found it: the `deposit` function lacks a zero-shares check, unlike `redeem` which asserts `(> inkind u0) ERR-OUTPUT-ZERO`. This is the direct analog to the reported rounding-to-zero bug — `convert-to-shares-preview` can round down to zero shares for a nonzero deposit `amount`, permanently donating the deposited underlying to existing depositors while the depositor receives zero `zft` shares.

### Title
Deposit lacks minimum-shares check, allowing rounding-to-zero share minting that silently steals depositor funds - (File: `mainnet/contracts/vault/v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`)

### Summary
Every vault's `deposit` function computes shares to mint via `convert-to-shares-preview` and only checks that the *input* `amount` is nonzero and that `inkind >= min-out` — but never checks that the computed `inkind` (shares to mint) is itself nonzero. `redeem` in the same contracts, by contrast, explicitly guards against this with `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)`. This asymmetry mirrors the reported `RewardsTracker` bug class where a `mul-div-down`-style computation rounds down to zero for legitimate nonzero inputs, causing the underlying value to be silently absorbed by the pool instead of credited to the caller.

### Finding Description
`convert-to-shares-preview` performs `(mul-div-down amount ts ta)` [1](#0-0) . When total supply `ts` grows large relative to total assets `ta` (e.g., after significant interest accrual/treasury-LP minting inflates `ts` relative to `ta`, or simply after the vault has operated for a long period with many decimals of scale), a small but nonzero `amount` can produce `inkind = 0` due to integer division truncation.

In `deposit`, the only assertions are:
```
(asserts! (> amount u0) ERR-AMOUNT-ZERO)
(asserts! (>= inkind min-out) ERR-SLIPPAGE)
``` [2](#0-1) 

If a caller passes `min-out = 0` (a valid, common choice for a simple deposit with no explicit minimum), `inkind = 0` satisfies `(>= inkind min-out)` trivially. The function then proceeds to:
```
(try! (receive-underlying amount account))
(try! (ft-mint? zft inkind recipient))   ;; mints 0 shares
(var-set assets (+ current-assets amount))
``` [3](#0-2) 

The depositor's underlying tokens are pulled into the vault (`assets` increases by `amount`) but they receive `0` `zft` shares — i.e., their principal is fully and permanently donated to all other existing shareholders pro-rata. This is the same root cause as the `RewardsTracker` finding: a value-transferring computation that can legitimately round to zero is not guarded, so the depositor's funds are irrecoverably lost while accounting silently proceeds as if nothing went wrong.

Note `redeem` explicitly protects against the symmetric case with `ERR-OUTPUT-ZERO` [4](#0-3) , confirming this is a known failure mode in this codebase that was mitigated on the withdrawal side but not on the deposit side.

### Impact Explanation
This is a permanent freezing/theft of the depositing user's principal (their deposited funds become unclaimed/unattributed and are absorbed into the shared pool for other shareholders to eventually redeem) — this falls under the in-scope Critical impact category of "permanent freezing of funds" / direct loss of user funds at rest, since the specific depositor who triggers the zero-mint receives nothing in exchange for their transferred underlying asset.

### Likelihood Explanation
Likelihood scales with how large `ts/ta` grows and how small a legitimate deposit `amount` is. Vaults using low-decimal underlying tokens (USDC, USDH — 6/8 decimals) combined with a large accumulated `total-supply` (from long-running interest accrual and treasury-LP minting) make a rounding-to-zero deposit increasingly plausible for small deposit amounts. Any ordinary user who passes `min-out = 0` (a very natural default for scripts/UI when the exact conversion rate isn't pre-computed) is exposed without any special privilege or crafted conditions.

### Recommendation
Add an explicit check in `deposit` mirroring the one already present in `redeem`:
```
(asserts! (> inkind u0) ERR-OUTPUT-ZERO)
```
placed alongside the existing asserts in each vault's `deposit` function, so that a deposit which would mint zero shares reverts instead of silently consuming the user's funds.

### Proof of Concept
1. Let a vault reach a state where `total-supply-preview` `ts` is large relative to `total-assets-preview` `ta` (e.g., ratio `ts/ta > 1e6` for a 6-decimal token), which is achievable over the vault's normal operating lifetime as interest compounds and treasury-LP shares accumulate.
2. A user calls `deposit(amount, min-out=0, recipient)` with a small nonzero `amount` such that `mul-div-down(amount, ts, ta) == 0`.
3. `deposit` passes both assertions (`amount > 0` and `0 >= 0`), pulls in `amount` of the underlying token via `receive-underlying`, increments `assets` by `amount`, and mints `0` `zft` shares to `recipient` via `ft-mint? zft 0 recipient`.
4. The user has permanently lost `amount` of the underlying token with zero shares to redeem it; the value is absorbed proportionally by all other existing `zft` holders.
