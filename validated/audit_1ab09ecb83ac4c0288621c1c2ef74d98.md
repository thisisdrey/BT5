## Title
DelegateResourceActuator/DelegateResourceProcessor decrease TronPower without settling reward or adjusting votes, allowing unbacked vote rewards - (File: `actuator/src/main/java/org/tron/core/actuator/DelegateResourceActuator.java`)

### Summary
`DelegateResourceActuator.execute()` and its TVM counterpart `DelegateResourceProcessor.execute()` reduce the owner's `FrozenV2Balance` (and therefore TronPower) when resources are delegated to another account, but unlike every other TronPower-reducing action (`UnfreezeBalanceActuator`, `UnfreezeBalanceV2Actuator`/`UnfreezeBalanceV2Processor`, `VoteWitnessActuator`/`VoteWitnessProcessor`), they never call `mortgageService.withdrawReward()` / `VoteRewardUtil.withdrawReward()` and never call the corresponding `updateVote()` routine that proportionally shrinks an account's cast votes when TronPower drops below the total vote count.

### Finding Description
Every path that reduces an account's TronPower elsewhere in the codebase settles pending vote rewards first and then reconciles the votes list against the new (lower) TronPower:
- `UnfreezeBalanceActuator.execute()` calls `mortgageService.withdrawReward(ownerAddress)` before clearing/adjusting votes: [1](#0-0) 
- `UnfreezeBalanceV2Actuator.execute()` calls `mortgageService.withdrawReward(ownerAddress)` then `updateVote(...)`: [2](#0-1) 
- The TVM-side `UnfreezeBalanceV2Processor.execute()` does the same via `VoteRewardUtil.withdrawReward` and `updateVote`, which proportionally rescales cast votes to the new TronPower: [3](#0-2)  and [4](#0-3) 

In contrast, `DelegateResourceActuator.execute()` only mutates the owner's frozen/delegated balances directly — it never calls `withdrawReward` or any vote-reconciliation logic: [5](#0-4) 

The same omission exists in the equivalent TVM native contract path, `DelegateResourceProcessor.execute()`, which also directly reduces `FrozenV2Balance` without touching votes or rewards: [6](#0-5) 

`validate()` in both `DelegateResourceActuator` and `DelegateResourceProcessor` only checks that the delegated amount does not exceed the owner's available `FrozenV2Balance` after subtracting bandwidth/energy usage; it does not check or care about the account's outstanding `VotesList`: [7](#0-6) 

This is the same bug class as the reported `Vault.blacklistProtocol` issue: an operation that permanently alters the underlying stake/allocation (here TronPower, backing votes and reward computation) without first settling/reconciling the reward-relevant state (here: withdrawing pending reward and shrinking the votes list), leaving stale state that misrepresents the true backing of the reward calculation.

### Impact Explanation
Vote rewards in java-tron are computed purely from the `VotesList` stored on the account (via `VoteRewardUtil.computeReward`/`MortgageService.computeReward`), not from the account's live TronPower, except at the moment `withdrawReward`/`updateVote` are invoked to reconcile the two. By delegating out frozen balance without triggering that reconciliation, a normal, unprivileged account holder can vote for witnesses using their full TronPower and then delegate that same underlying frozen balance to another address. Their `VotesList` remains unchanged even though their real TronPower backing those votes is now reduced (or entirely delegated away), so they continue to accrue and later withdraw witness-vote rewards for votes that are no longer backed by real stake. This is an "unbacked reward"/unbacked balance condition, distributing witness rewards funded by the network to votes not backed by real, non-delegated TronPower.

### Likelihood Explanation
This is reachable directly by any account owner via a plain `DelegateResourceContract` transaction (`DelegateResourceActuator`) or via the `delegateResource` TVM opcode (`Program.delegateResource` → `DelegateResourceProcessor`), requiring no special privileges — only that the account has previously voted and has sufficient `FrozenV2Balance` to delegate. It is a straightforward two-step user action (vote, then delegate) with no additional preconditions.

### Recommendation
Mirror the pattern used in `UnfreezeBalanceV2Actuator`/`UnfreezeBalanceV2Processor`: before mutating `FrozenBalanceForBandwidthV2`/`FrozenBalanceForEnergyV2` in `DelegateResourceActuator.execute()` and `DelegateResourceProcessor.execute()`, call `mortgageService.withdrawReward(ownerAddress)` (or `VoteRewardUtil.withdrawReward`) to settle pending rewards, then invoke the equivalent of `updateVote()` to proportionally shrink the owner's `VotesList` when the post-delegation TronPower falls below the currently cast vote total.

### Proof of Concept
1. Account A freezes X TRX for bandwidth, obtaining TronPower = X.
2. Account A casts votes for witness W using the full TronPower X (`VoteWitnessContract`), which internally calls `withdrawReward` and records `VotesList = [W: X]` via `VoteWitnessActuator.countVoteAccount`: [8](#0-7) 
3. Account A sends a `DelegateResourceContract` delegating the same X TRX worth of bandwidth to Account B. `DelegateResourceActuator.execute()` reduces A's `FrozenBalanceForBandwidthV2` by X (dropping A's TronPower to ~0) but does not touch A's `VotesList` or call `withdrawReward`: [9](#0-8) 
4. On subsequent maintenance cycles, `MortgageService`/`VoteRewardUtil` compute reward for A based on the unchanged `VotesList = [W: X]`, even though A no longer holds the TronPower backing those votes (it was delegated to B who may also be voting/using it independently), letting A accrue rewards not backed by actual retained stake.

  private void countVoteAccount(VoteWitnessContract voteContract) {
    AccountStore accountStore = chainBaseManager.getAccountStore();
    VotesStore votesStore = chainBaseManager.getVotesStore();
    MortgageService mortgageService = chainBaseManager.getMortgageService();
    byte[] ownerAddress = voteContract.getOwnerAddress().toByteArray();

    VotesCapsule votesCapsule;

    //
    mortgageService.withdrawReward(ownerAddress);

    AccountCapsule accountCapsule = accountStore.get(ownerAddress);

    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    if (dynamicStore.supportAllowNewResourceModel()
        && accountCapsule.oldTronPowerIsNotInitialized()) {
      accountCapsule.initializeOldTronPower();
    }

    if (!votesStore.has(ownerAddress)) {
      votesCapsule = new VotesCapsule(voteContract.getOwnerAddress(),
          accountCapsule.getVotesList());
    } else {
      votesCapsule = votesStore.get(ownerAddress);
    }

    accountCapsule.clearVotes();
    votesCapsule.clearNewVotes();

    voteContract.getVotesList().forEach(vote -> {
      logger.debug("countVoteAccount, address[{}]",
          ByteArray.toHexString(vote.getVoteAddress().toByteArray()));

      votesCapsule.addNewVotes(vote.getVoteAddress(), vote.getVoteCount());
      accountCapsule.addVotes(vote.getVoteAddress(), vote.getVoteCount());
    });

    accountStore.put(accountCapsule.createDbKey(), accountCapsule);
    votesStore.put(ownerAddress, votesCapsule);
  }
