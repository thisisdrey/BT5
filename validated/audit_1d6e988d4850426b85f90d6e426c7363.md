## Analysis

The DODO bug's core broken invariant is: **a scaling/normalization value derived from a tiny initial input can round down to zero via fixed-point multiplication, and that zero then permanently corrupts all subsequent economic accounting because later operations multiply against it.**

The closest verifiable analog in this repository is in the Snowbridge outbound-queue fee calculation, `Pallet::calculate_fee` [1](#0-0) , which converts a remote (Ethereum) fee into native currency using `FixedU128` fixed-point math with an `exchange_rate` and a decimals-adjustment division, exactly analogous to DODO's `mulFloor`/`divFloor` scaling-factor rounding.

### Title
Public message-fee calculation can round the relayer reward to zero, allowing free/underpriced Snowbridge message submission that stalls relayer processing - (File: `bridges/snowbridge/pallets/outbound-queue/src/lib.rs`)

### Summary
`Pallet::calculate_fee` computes the fee charged to a user for sending a message to Ethereum via the public `send_message` entrypoint. The remote component is computed with `FixedU128` fixed-point division by `exchange_rate`, then rescaled from 18-decimal "ether" units to the chain's native decimals (10 or 12) via `convert_from_ether_decimals`, which performs integer division by `10^(18-decimals)` [2](#0-1) . Because `PricingParameters::validate()` only checks that each individual field (`exchange_rate`, `fee_per_gas`, `rewards.local`, `rewards.remote`, `multiplier`) is nonzero [3](#0-2) , it does not guard against the *composed* result rounding to zero. The pallet's own test confirms this: with fully valid, non-zero parameters, `fee.remote` still computes to exactly `0` [4](#0-3) .

### Finding Description
`calculate_fee` is invoked from the public message-send path (`SendMessage::validate`, used both by XCM-triggered exports and `snowbridge_pallet_system::Pallet::send`) to determine what a user must pay to have a message delivered to Ethereum. The remote fee (the relayer's gas refund + reward, denominated in ETH/wei) is converted to native currency by:

```
fee = FixedU128::from_inner(fee).saturating_mul(multiplier).checked_div(&exchange_rate).into_inner();
fee = convert_from_ether_decimals(fee); // divides by 10^(18 - Decimals), e.g. 10^8 for a 10-decimal chain
``` [5](#0-4) 

`convert_from_ether_decimals` performs a floor integer division by up to `10^8` [2](#0-1) . This is structurally identical to DODO's `mulFloor`/`divFloor` truncation against a `1e18` scalar: any intermediate fee value smaller than the decimal scaling factor collapses to `0` regardless of the nominal (validated, non-zero) `PricingParameters`. This is demonstrated directly in-repo by `test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero`, where `exchange_rate = 1/1`, `fee_per_gas = 1`, `rewards.remote = 1` — all individually valid per `PricingParameters::validate` — yet `fee.remote == 0` [4](#0-3) .

Unlike the DODO case, this zero is not a *persisted* multiplicative state (there is no on-chain "target" that stays corrupted); rather it is recomputed per-message. But because `PricingParameters` is governance-set (not attacker-controlled) and applies globally to every message, once such a degenerate parameter combination is in effect (e.g. from a legitimate governance update that under-specifies `fee_per_gas`/`exchange_rate` in low-decimal-precision terms), **every subsequent public message submitted through this path is charged zero relayer reward**, i.e., a systemic zero-fee state that persists until parameters are manually corrected — mirroring the "quote target stuck at zero, corrupting all subsequent operations" pattern from the DODO report, but at the protocol-fee layer instead of an AMM reserve-target layer.

### Impact Explanation
If the computed relayer reward component of the fee rounds to zero, users can submit messages to be committed and relayed to Ethereum via `snowbridge_pallet_outbound_queue::Pallet::process_message` / `commit` while paying no relayer incentive fee, i.e. public underpriced work: the local fee still covers weight, but the remote reward that motivates off-chain relayers to actually deliver messages to Ethereum is zero. This matches the explicitly permitted impact class "public underpriced work that degrades block production or stalls bridge processing," since relayers have no incentive to pick up such messages, causing them to pile up undelivered in the merkle-committed message set, stalling the bridge's outbound delivery pipeline.

### Likelihood Explanation
This requires no malicious peer, relayer, validator, or leaked key — it is a pure computation/rounding defect triggerable any time `PricingParameters` (a normal governance-configured, non-privileged-attacker-controlled value from the perspective of ordinary users interacting with the fixed parameters) produces a small enough remote-fee numerator relative to the `10^(18-Decimals)` divisor and `exchange_rate`. Because `PricingParameters::validate()` checks only individual field non-zero-ness and not the composed rounding outcome, misconfiguration (which is realistic given decimals differ between chains, e.g., 10 vs 12) silently produces a systemic zero-fee condition affecting every message, not just an edge-case single transaction. The in-repo test already documents this exact scenario occurring with parameters that pass validation.

### Recommendation
Add an explicit post-computation check in `calculate_fee` (or in `PricingParameters::validate`) ensuring the final `fee.remote` (and ideally `fee.local`) is non-zero, returning an error/defensive fallback rather than silently proceeding with a free-delivery message. Alternatively, perform the decimal rescaling before/inside the `FixedU128` division rather than as a final floor-division pass, so sub-divisor amounts are preserved rather than truncated to zero, analogous to using a properly scaled decimal representation instead of DODO's flat `1e18` `mulFloor` truncation.

### Proof of Concept
The existing pallet test is a direct proof of concept:
```rust
// bridges/snowbridge/pallets/outbound-queue/src/test.rs:303-318
let price_params: PricingParameters<<Test as Config>::Balance> = PricingParameters {
    exchange_rate: FixedU128::from_rational(1, 1),
    fee_per_gas: 1_u32.into(),
    rewards: Rewards { local: 1_u32.into(), remote: 1_u32.into() },
    multiplier: FixedU128::from_rational(1, 1),
};
let fee = OutboundQueue::calculate_fee(gas_used, price_params.clone());
assert_eq!(fee.local, 698000000);
assert_eq!(fee.remote, 0); // relayer reward silently rounds to zero despite all-nonzero, valid params
``` [4](#0-3) 

**Uncertainty note:** I was not able to fully trace whether downstream code (e.g. `snowbridge_pallet_system` when setting `PricingParameters`) applies any additional sanity check beyond `PricingParameters::validate()` to reject parameter sets that produce a zero composed fee before they take effect network-wide; this would need to be confirmed by inspecting `snowbridge_pallet_system`'s `set_pricing_parameters` extrinsic and any related governance tooling, which was outside what I could verify with the available search results.

		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

		pub(crate) fn convert_from_ether_decimals(value: u128) -> T::Balance {
			let decimals = ETHER_DECIMALS.saturating_sub(T::Decimals::get()) as u32;
			let denom = 10u128.saturating_pow(decimals);
			value.checked_div(denom).expect("divisor is non-zero; qed").into()
		}
