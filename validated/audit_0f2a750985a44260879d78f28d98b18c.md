## Finding

The Unlock report's broken invariant is: **a system charges a user at price P1, but computes the refund of the unused portion using a freshly re-derived price P2 instead of the rate actually paid**, letting the refunded amount diverge from what was actually collected. The direct analog in `polkadot-sdk` is `SwapFirstAssetTrader` in `cumulus/primitives/utility/src/lib.rs`, which is a `WeightTrader` used by the XCM executor to pay/refund execution fees by swapping through `pallet-asset-conversion`.

### Title
XCM fee refund re-quotes the AMM swap rate instead of reusing the rate actually paid, enabling value extraction from the liquidity pool - (File: cumulus/primitives/utility/src/lib.rs)

### Summary
`SwapFirstAssetTrader::buy_weight` swaps the user's asset into `Target` at whatever the pool's current price is, and only records the resulting `total_fee` (in `Target`) and which asset was used (`last_fee_asset`) — it never records the exchange rate that was actually paid. `refund_weight` later swaps the unused portion of `total_fee` (in `Target`) back into the original asset via a brand-new `SwapCredit::swap_exact_tokens_for_tokens` call, which is priced against the pool's state *at that later moment*, not the rate from `buy_weight`. [1](#0-0) [2](#0-1) 

### Finding Description
- `buy_weight` performs `SwapCredit::swap_tokens_for_exact_tokens(vec![swap_asset, Target::get()], credit_in, fee)`, converting the user's asset into `Target` at the pool's price P1, and stores only `total_fee` (the `Target`-denominated amount) and `last_fee_asset` — no record of P1 or of how much of the original asset was actually consumed per unit of `Target`. [3](#0-2) 
- `refund_weight` computes `refund_amount = WeightToFee::weight_to_fee(&weight)` in `Target` terms (correct — weight is priced statically), extracts that from `total_fee`, then calls `SwapCredit::swap_exact_tokens_for_tokens(vec![Target::get(), refund_swap_asset], refund, None)` to convert back to the user's original asset. This swap uses whatever price P2 the pool has *at the time `refund_weight` runs*, with no minimum-output enforcement (`None`) and no reference to the P1 rate paid at `buy_weight` time. [4](#0-3) 
- Because `buy_weight` and `refund_weight` are both called during execution of the *same* XCM program (via `BuyExecution` and `RefundSurplus`), and the same message can also contain other instructions (e.g. `ExchangeAsset`) that trade against the identical `pallet-asset-conversion` pool, a single unprivileged sender fully controls both the fee-swap and any intervening trade. By first swapping into the pool in the direction that makes the refund-asset cheap relative to `Target`, then triggering a large `BuyExecution` (locking in `total_fee` in `Target`) followed by `RefundSurplus` for most of that weight, the sender causes `refund_weight` to reconvert `Target` back into the original asset at the now-favorable P2, extracting more of the original asset from the pool's reserves than was ever paid in by that same sender at P1.
- This is structurally identical to the Unlock bug: the amount refunded is derived from a "current price" read at refund time rather than the price actually paid at purchase time, and there is no snapshot of the rate used in `buy_weight` to bound or reconcile the refund.

### Impact Explanation
The pool (`pallet-asset-conversion`) holds funds contributed by liquidity providers and other users' assets in flight (e.g., Asset Hub fee-payment pools). A discrepancy between the swap-in rate and swap-out rate for the *same* fee-trader instance lets an attacker drain value from that shared pool without needing any privileged role — only the ability to submit a self-contained XCM program with a swap instruction plus `BuyExecution`/`RefundSurplus`. This falls under "theft or unbacked mint/unlock" and "public underpriced work" in the impact gate: value is settled to the sender at an amount inconsistent with what was actually paid, at the expense of the pool/other participants.

### Likelihood Explanation
Exploitability depends on pool depth, fee tiers (LP fee), and how much the sender can move the price within one atomic message before triggering the refund — the attacker must self-fund the price-moving trade and pay its LP fee, so profitability is bounded by pool depth/fees, but no external actor, admin, or relayer/validator collusion is required; a normal user constructing a crafted XCM program is sufficient, which fits the "unprivileged attacker" requirement of the impact gate. It is more exploitable against shallow pools or artificially large weight/fee amounts.

### Recommendation
Do not re-quote the swap rate at refund time. Either:
- Record the effective per-`Target`-unit rate (or the amount of the original asset consumed) at `buy_weight` time in `SwapFirstAssetTrader`, and compute `refund_weight`'s output using that stored rate (pro-rata of the original conversion) instead of a fresh `swap_exact_tokens_for_tokens` call; or
- Enforce a minimum-output / maximum-slippage bound tied to the original buy-time rate when calling `SwapCredit::swap_exact_tokens_for_tokens` in `refund_weight`, rejecting refunds where the reconverted amount deviates materially from the pro-rata share of what was originally paid.

### Proof of Concept
1. Attacker constructs an XCM program sent to a chain using `SwapFirstAssetTrader` as its `WeightTrader` (e.g., Asset Hub-style fee-swap configuration), paying fees in asset `X`, with `Target` as the pool's other asset.
2. Program instructions:
   a. `ExchangeAsset` (or equivalent) swapping a chosen amount of `X` for `Target` in the same `pallet-asset-conversion` pool used by the fee trader, shifting reserves so that a subsequent `Target -> X` swap yields more `X` per `Target` than the rate at step (c).
   b. `BuyExecution` with a large `weight_limit`, causing `buy_weight` to swap a chunk of `X` into `Target` at the pool's current (now-shifted) rate P1, recorded only as `total_fee` in `Target` and `last_fee_asset = X`.
   c. Program consumes little actual weight, then `RefundSurplus`, causing `refund_weight` to convert most of `total_fee` back into `X` via `swap_exact_tokens_for_tokens(vec![Target, X], refund, None)` at the pool's rate P2.
3. Because P2 was engineered in step (a) to favor `Target -> X` conversions, the attacker receives back more `X` than the amount consumed in step (b), net of the LP fee paid in step (a) — extracting value from the pool's reserves via the buy/refund rate mismatch rather than a legitimate arbitrage against external markets.

	fn refund_weight(&mut self, weight: Weight, _context: &XcmContext) -> Option<AssetsInHolding> {
		log::trace!(
			target: "xcm::weight",
			"SwapFirstAssetTrader::refund_weight weight: {:?}, self.total_fee: {:?}",
			weight,
			self.total_fee,
		);
		if weight.is_zero() || self.total_fee.peek().is_zero() {
			// noting to refund.
			return None;
		}
		let refund_asset = if let Some(asset) = &self.last_fee_asset {
			// create an initial zero refund in the asset used in the last `buy_weight`.
			(asset.clone(), Fungible(0)).into()
		} else {
			return None;
		};
		let refund_amount = WeightToFee::weight_to_fee(&weight);
		if refund_amount >= self.total_fee.peek() {
			// not enough was paid to refund the `weight`.
			return None;
		}

		let refund_swap_asset = FungiblesAssetMatcher::matches_fungibles(&refund_asset)
			.map(|(a, _)| a.into())
			.ok()?;

		let refund = self.total_fee.extract(refund_amount);
		let refund = match SwapCredit::swap_exact_tokens_for_tokens(
			vec![Target::get(), refund_swap_asset],
			refund,
			None,
		) {
			Ok(refund_in_target) => refund_in_target,
			Err((refund, _)) => {
				// return an attempted refund back to the `total_fee`.
				let _ = self.total_fee.subsume(refund).map_err(|refund| {
					// error may occur if `total_fee.asset` differs from `refund.asset`, which does
					// not apply in this context.
					defensive!(
						"`total_fee.asset` must be equal to `refund.asset`",
						(self.total_fee.asset(), refund.asset())
					);
				});
				return None;
			},
		};

		let refund = AssetsInHolding::new_from_fungible_credit(refund_asset.id, Box::new(refund));
		Some(refund)
	}
