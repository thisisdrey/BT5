Based on my investigation, `routines` config (multiple `readOutsidePackets` worker goroutines processing UDP packets concurrently per interface, seen in `InterfaceConfig.routines`/`Interface.routines` in `interface.go`) combined with the split Check/Update pattern in `ConnectionState.Decrypt` gives a concrete, provable TOCTOU race in the anti-replay window.

### Title
Anti-replay window Check/Update race allows a captured packet to be decrypted twice - (File: connection_state.go)

### Summary
`ConnectionState.Decrypt` (and `VerifyRelay`) validate a packet's replay-window status and then commit that status as two *separate* locked critical sections, with the AEAD decryption running in between while the lock is released. This mirrors the External Report's root cause: a security-relevant state transition (there, the "already accounted for" collateral value; here, "already seen" counter) is checked once but not atomically reserved/committed, so an attacker can race the window between check and update to make the system act on stale state twice.

### Finding Description
`Decrypt` does:
```go
cs.decryptLock.Lock()
result := cs.window.Check(l, messageCounter)
cs.decryptLock.Unlock()
...
out, err = cs.dKey.DecryptDanger(...)
...
cs.decryptLock.Lock()
result = cs.window.Update(l, messageCounter)
cs.decryptLock.Unlock()
``` [1](#0-0) 

`Bits.Check` only reads whether a counter has been marked seen; `Bits.Update` is what actually marks it [2](#0-1) . Because the lock is released between `Check` and `Update`, and nebula runs multiple `readOutsidePackets` worker routines per interface (`Interface.routines` / `InterfaceConfig.routines`) [3](#0-2) [4](#0-3) , two workers can concurrently receive the exact same replayed UDP datagram (an attacker simply duplicates a captured packet on the wire, or the packet is naturally duplicated by a NAT/switch), both pass `Check` before either calls `Update`, and both proceed to `DecryptDanger` and hand the plaintext to the tun device / relay-forward path. The `VerifyRelay` path for relayed frames has the identical Check-then-decrypt-then-Update structure [5](#0-4) , so a relay node is equally exposed. This is the same shape of bug the report describes — the code determines "not yet counted" state once, performs the side-effecting operation, and only afterward commits the "now counted" state, leaving a window where an attacker-controlled duplicate can be processed as if it were the same never-before-seen input.

Historical CHANGELOG entries confirm the project has already fixed adjacent instances of this exact class ("Advance the replay window on relayed packets..." #1751, "Lock replay window updates so concurrent readers can't corrupt it" #1802) [6](#0-5) , indicating replay-window atomicity is a known trouble spot in this codebase, but the fix in #1802 addresses *corruption* of the window under concurrency, not the semantic TOCTOU gap between the read (`Check`) and the commit (`Update`) that straddles the AEAD decrypt call.

### Impact Explanation
An attacker who can observe/duplicate ciphertext on the wire (a passive on-path observer, or simply by re-sending a captured UDP datagram before it is processed) can cause a single legitimate encrypted packet to be decrypted and delivered to the tun device (or forwarded through a relay) more than once. This breaks the confidentiality/integrity guarantee that each message counter is processed exactly once, and for relay nodes it re-introduces double-forwarding of relayed traffic, undermining the anti-replay protection the `Bits` window is specifically designed to provide.

### Likelihood Explanation
Exploitability depends on winning a race: the attacker needs two copies of the same encrypted packet to be picked up by two different reader goroutines before the first `Update` call lands. This is more likely on multi-`routines` configurations (which increase the number of concurrent UDP reader goroutines) and is trivially triggerable by a network-level attacker who can duplicate a UDP datagram (common on lossy/duplicating links or via targeted duplicate injection), requiring no valid certificate.

### Recommendation
Make the replay-window check-and-mark a single atomic operation under one lock acquisition that spans the full decision, e.g. call `Update` (or an atomic reserve step) before releasing the lock and before invoking `DecryptDanger`, only proceeding to decrypt if the reservation succeeded; if decryption subsequently fails, do not "unmark" the counter (a decrypt failure should not resurrect the slot for a legitimate future duplicate). Apply the same fix to both `Decrypt` and `VerifyRelay`.

### Proof of Concept
Conceptual reproduction (not runnable without the full harness):
1. Establish a tunnel between two nebula nodes with `listen.routines` > 1 so multiple UDP reader goroutines exist.
2. Capture one legitimate encrypted data-plane packet with message counter N.
3. Inject two copies of that exact packet into the UDP socket back-to-back (e.g., via `SO_REUSEPORT`/raw socket duplicate send, or simply by re-sending the captured bytes twice in quick succession) so they land on two different reader goroutines.
4. Observe (via tun output or relay-forward output) that the plaintext is delivered/forwarded twice, confirming that `cs.window.Check` returned `true` for both copies before `cs.window.Update` recorded counter N as seen — matching the e2e replay test in `e2e/tunnels_test.go` (`TestRelayReplayProtection`) but on the direct (non-relay) `Decrypt` path with concurrent readers rather than a single-threaded sequential replay [7](#0-6) .

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}

// Update has three branches:
//   - i == b.current+1: fast path; advance the cursor by one and lose-count
//     the slot we just stomped (only past warmup; see the i > b.length guard
//     below).
//   - i  >  b.current+1: jump path; clear all slots between current and i
//     (or up to a full window's worth, whichever is smaller) via clearRange,
//     then mark i. Two arms here: a warmup arm that handles the very first
//     window before the cursor has slid, and a steady-state arm that treats
//     every cleared empty slot as a lost packet.
//   - i  <= b.current: in-window check for duplicates; out-of-window otherwise.
//
// NewBits seeds bits[0]=1 so counter 0 looks "received" — Update never
// clears that marker during warmup (clearRange skips position 0 when
// startPos=1), and once b.current >= b.length the marker is no longer
// consulted. The marker prevents a fictitious "lost" hit on the first real
// counter.
func (b *Bits) Update(l *slog.Logger, i uint64) bool {
	// Fast path: i is the next expected counter. Split out so the function
	// stays small and avoids paying for the slow paths' slog argument-build
	// stack frame on every call. The bit read/test/write is inlined to
	// touch the backing word once.
	if i == b.current+1 {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if i > b.length && w&mask == 0 {
			b.lostCounter.Inc(1)
		}
		b.bits[word] = w | mask
		b.current = i
		return true
	}
	return b.updateSlow(l, i)
}
