## Title
Dynamic-energy penalty calculation rounds down, letting contract callers pay less than the correct congestion-pricing surcharge - (File: `actuator/src/main/java/org/tron/core/vm/VM.java`, `actuator/src/main/java/org/tron/core/vm/EnergyCost.java`)

### Summary
When TVM dynamic energy pricing is enabled (`VMConfig.allowDynamicEnergy()`), every opcode's energy cost is multiplied by a per-contract congestion `factor` and the "penalty" (extra energy the caller must pay above the base cost) is computed with plain integer division, which truncates toward zero. This is the same rounding-class flaw as the Notional `convertFromStorage()` bug: a value that should be rounded up in favor of the protocol is instead rounded down in favor of the transaction sender, systematically under-charging energy on every opcode of every call while the factor is active.

### Finding Description
In `VM.play()`, for every opcode executed once `factor > DYNAMIC_ENERGY_FACTOR_DECIMAL`: [1](#0-0) 

```java
if (factor > DYNAMIC_ENERGY_FACTOR_DECIMAL) {
  long penalty;
  if (CALL_OPS.contains(op.getOpcode())) {
    penalty = program.getCallPenaltyEnergy();
  } else {
    penalty = energy * factor / DYNAMIC_ENERGY_FACTOR_DECIMAL - energy;
    ...
  }
  program.spendEnergyWithPenalty(energy, penalty, opName);
}
```

`energy * factor / DYNAMIC_ENERGY_FACTOR_DECIMAL` is a `long / long` division that truncates any fractional remainder. The correct amount owed (`energy * factor / DECIMAL`) is fractional whenever `factor` is not an exact multiple of `DYNAMIC_ENERGY_FACTOR_DECIMAL`, and the truncation always discards the remainder rather than rounding up, so the computed `penalty` is always `<=` the true value the protocol's congestion-pricing mechanism intends to charge.

The identical rounding-down pattern also appears in the CALL-cost penalty computation used to size the sub-call's energy budget: [2](#0-1) 

```java
if (VMConfig.allowDynamicEnergy()) {
  long factor = program.getContextContractFactor();
  if (factor > DYNAMIC_ENERGY_FACTOR_DECIMAL) {
    long penalty = energyCost * factor / DYNAMIC_ENERGY_FACTOR_DECIMAL - energyCost;
    if (penalty < 0) {
      penalty = 0;
    }
    program.setCallPenaltyEnergy(penalty);
    energyCost += penalty;
  }
}
```

Both sites compute `x * factor / DECIMAL - x` using truncating integer division rather than a ceiling division (e.g. the correct pattern is already implemented elsewhere in the codebase as `divideCeil`/`divideCeilExact` in `RepositoryImpl.java`, lines 965-976, but is not applied here).

### Impact Explanation
Any account that broadcasts a transaction invoking a contract (or any contract making further calls) while dynamic energy pricing is active systematically underpays the congestion surcharge that the mechanism is designed to collect. This directly parallels the Notional finding: the rounding favors the paying party (the caller) instead of the protocol, causing a persistent, accumulative shortfall in energy fees actually burned/collected versus what the dynamic-energy design intends. Because it triggers on essentially every non-CALL opcode of every transaction once the factor is engaged, the dust loss compounds across the network rather than being a one-off rounding artifact, and it is fully reachable from an ordinary, unprivileged `TriggerSmartContract` transaction — no special privilege is required.

### Likelihood Explanation
This code path executes on every opcode of every TVM execution whenever `allowDynamicEnergy()` is enabled and a contract's congestion factor exceeds the baseline (`factor > DYNAMIC_ENERGY_FACTOR_DECIMAL`), which is the intended steady-state behavior of the dynamic energy feature during periods of contract congestion — not an edge case. Any user calling a "hot" contract triggers it.

### Recommendation
Replace the truncating division with a ceiling division so the protocol never under-collects the penalty, mirroring the `divideCeil` helper already present in `RepositoryImpl.java`:

```java
long scaled = energy * factor;
long penalty = (scaled + DYNAMIC_ENERGY_FACTOR_DECIMAL - 1) / DYNAMIC_ENERGY_FACTOR_DECIMAL - energy;
```//(or use `RepositoryImpl`'s `divideCeil`/`divideCeilExact` equivalents, guarding against overflow since `energy * factor` is currently computed with plain `long` multiplication).

Apply the same fix to the analogous computation in `EnergyCost.getCalculateCallCost`.

### Proof of Concept
1. Enable dynamic energy pricing (`allowDynamicEnergy()` true) and drive a contract's congestion factor above `DYNAMIC_ENERGY_FACTOR_DECIMAL` (e.g., `DYNAMIC_ENERGY_FACTOR_DECIMAL + 1`) by repeated invocation, as intended by the feature.
2. Trigger the contract with an opcode of base `energy` such that `energy * factor` is not evenly divisible by `DYNAMIC_ENERGY_FACTOR_DECIMAL` (e.g., `energy = 3`, `factor = DYNAMIC_ENERGY_FACTOR_DECIMAL + 1`).
3. Compute expected penalty with ceiling division vs. the actual truncated result from `energy * factor / DYNAMIC_ENERGY_FACTOR_DECIMAL - energy`; observe the actual charged penalty is 1 unit lower than the mathematically correct surcharge, repeatable on every subsequent opcode for the duration the factor remains above baseline.
