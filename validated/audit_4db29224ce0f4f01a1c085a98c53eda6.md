## Title
Unchecked `long` multiplication overflow in bandwidth/energy resource accounting when the hardening flag is disabled - (File: `chainbase/src/main/java/org/tron/core/db/ResourceProcessor.java`)

### Summary
The reported bug class is an unguarded `long`/numeric multiplication (`totalCredits * 1e18`) with no bounds/overflow check, causing a revert (denial of service). The same pattern exists in `ResourceProcessor`, which is used on every transaction to update bandwidth/energy usage windows. The safe, overflow-checked path (using `BigInteger`) is only exercised when a runtime flag `hardenCalculation()` is enabled; the legacy fallback branch still performs raw `long * long` multiplication/addition with no overflow protection.

### Finding Description
`ResourceProcessor.increase`, `increaseV2`, `getUsage`, and `getNewWindowSize` each branch on `hardenCalculation()` (`dynamicPropertiesStore.allowHardenResourceCalculation()`). When hardening is off, they fall back to plain `long` arithmetic without any `Math.multiplyExact`/`BigInteger` protection: [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) 

These raw multiplications (`lastUsage * this.precision`, `usage * this.windowSize`, `lastUsage * lastWindowSize + usage * windowSize`, `usage * windowSize / precision`) can silently wrap around (Java `long` overflow does not throw) rather than throw an exception, which is actually the *inverse* symptom of the reported vulnerability (silent wraparound instead of revert), but is the same root cause class: multiplication performed on attacker/consensus-influenceable inputs (`usage`, accumulated resource window values reachable via `DelegateResourceActuator`/`UnDelegateResourceActuator`/freeze-v2 delegation flows) without overflow checking in the default/legacy code path.

Notably, the project's own test suite explicitly demonstrates this exact overflow class being caught only under hardening: [6](#0-5) 

This confirms the java-tron team is aware that `usage * windowSize`-style computations can overflow, and introduced `BigInteger`-based hardened variants guarded by a governance-controlled flag (`allowHardenResourceCalculation`), rather than always enforcing the safe path.

### Impact Explanation
If `allowHardenResourceCalculation` is not active on a given chain/network (it is a proposable/governance-controlled parameter, not hardcoded on), every bandwidth/energy consuming transaction (i.e., essentially all transactions) runs through the unguarded arithmetic in `ResourceProcessor`. A crafted large resource-delegation/window scenario (via freeze-v2 delegate/undelegate flows that manipulate `usage` and `windowSize` fields on accounts) could overflow these `long` computations, producing corrupted (wrapped, potentially negative) usage/window values. This can corrupt resource accounting state used for bandwidth/energy limit enforcement, potentially permitting resource-limit bypass or inconsistent account state — a resource-accounting integrity issue, not merely a revert-based DoS.

### Likelihood Explanation
Reaching this code requires only a signed transaction consuming resources or invoking delegate/undelegate resource contracts, i.e., trivially reachable by any broadcaster. However, triggering an actual overflow requires driving `usage`/`windowSize`-derived products near `Long.MAX_VALUE`, which in practice requires extreme, likely infeasible-in-practice values under normal resource accounting bounds (usage is generally bounded by realistic freeze/delegate amounts and window sizes measured in blocks). This bounds the practical likelihood, similar to how the original QVBaseStrategy bug required an implausibly large `totalCredits`. The likelihood is Medium, contingent on whether `allowHardenResourceCalculation` is active on the target network — I could not verify from the indexed code whether this flag defaults to enabled on mainnet.

### Recommendation
Remove the `hardenCalculation()` conditional fallback in `ResourceProcessor` and unconditionally use the `BigInteger`-based (or `Math.*Exact`-based) arithmetic for all `usage`/`windowSize`/`precision` multiplications, matching the approach already used in the hardened branch and in `RepositoryImpl`'s equivalent resource-limit calculations (`calculateGlobalLimitV2`).

### Proof of Concept
Not independently reproduced against a live node; based on static analysis of `ResourceProcessor.increase`/`increaseV2`/`getUsage`/`getNewWindowSize` and the project's own `RepositoryImplHardenTest` overflow tests, which demonstrate that disabling hardening (`VMConfig.initAllowHardenResourceCalculation(0)`) allows overflow to occur silently in the analogous `usage * windowSize` computation: [7](#0-6) 

**Note on other candidate paths investigated:** vote/reward math (`VoteWitnessActuator`, `VoteWitnessProcessor`, `VoteRewardUtil`, `MortgageService`), exchange math (`ExchangeInjectActuator`, `ExchangeWithdrawActuator`, `ExchangeTransactionActuator`, `SafeExchangeProcessor`), and asset-issue math (`ParticipateAssetIssueActuator`, `TransferAssetActuator`) were all reviewed and found to already use `LongMath.checkedAdd/checkedMultiply`, `Math.addExact/multiplyExact`, or `BigInteger` arithmetic, with dedicated tests (`sameTokenNameCloseMultiplyOverflowTest`, etc.) confirming overflow is caught and rejected — these are not valid analogs.

  private long getNewWindowSize(long lastUsage, long lastWindowSize, long usage,
      long windowSize, long newUsage) {
    if (hardenCalculation()) {
      BigInteger bi = BigInteger.valueOf(lastUsage).multiply(BigInteger.valueOf(lastWindowSize))
          .add(BigInteger.valueOf(usage).multiply(BigInteger.valueOf(windowSize)));
      return bi.divide(BigInteger.valueOf(newUsage)).longValueExact();
    }
    return (lastUsage * lastWindowSize + usage * windowSize) / newUsage;
  }
