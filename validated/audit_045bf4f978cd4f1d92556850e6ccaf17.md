### Title
Unauthenticated `HandshakeAccept`/`StackerDBHandshakeAccept` type-confusion via seq-only `is_solicited()` match lets a peer inject unverified identity data by racing any pending request - (File: `stackslib/src/net/chat.rs`, `stackslib/src/net/connection.rs`)

### Summary
`NetworkConnection::is_solicited()`/`fulfill_request()` mark an inbound message as "solicited" purely by matching `preamble.seq` against any outstanding request's `expected_seq`, with no check that the reply's message type corresponds to the request that was sent. Combined with the fact that `handle_handshake_accept()`/`update_from_handshake_data()` never verify that the `HandshakeAccept` payload is signed by (or otherwise bound to) the claimed `node_public_key`, a remote peer can reply to *any* outstanding request (e.g. a `Ping`) with a crafted `HandshakeAccept` bearing the same `seq`, causing the local node to accept unverified identity/public-key/address/data_url data into `ConversationP2P` state.

### Finding Description
`is_solicited()` and `fulfill_request()` in `stackslib/src/net/connection.rs:1394-1431` compute solicitation solely from:
```rust
if inflight.expected_seq == msg.request_id() {
    solicited = true;
}
``` [1](#0-0) 
There is no binding between the `expected_seq` and the *type* of message that was originally sent under that sequence number; `MessageSequence::request_id()` for `StacksMessage` is just `self.preamble.seq` [2](#0-1) , a value fully controlled by whoever crafts the reply's preamble.

In `ConversationP2P::chat()` (`stackslib/src/net/chat.rs:2946-2958`), when the connection has no public key yet, `update_stats = self.connection.is_solicited(&msg)` is computed and `handle_unauthenticated_control_message` is invoked [3](#0-2) . Inside `handle_unauthenticated_control_message` (`stackslib/src/net/chat.rs:2605-2663`), the *same* `solicited` boolean (computed once, type-agnostically) gates whether an unauthenticated `HandshakeAccept`/`StackerDBHandshakeAccept` is processed via `handle_handshake_accept`:
```rust
let solicited = self.connection.is_solicited(msg);
...
StacksMessageType::HandshakeAccept(ref data) => {
    if solicited {
        self.handle_handshake_accept(...)  // mutates peer state
``` [4](#0-3) 

`handle_handshake_accept` then calls `update_from_handshake_data` (`stackslib/src/net/chat.rs:1338-1345`), which sets `peer_version`, `peer_network_id`, `peer_services`, `peer_expire_block_height`, `handshake_addrbytes`, `handshake_port`, `data_url`, and installs the attacker-claimed public key via `self.connection.set_public_key(...)` [5](#0-4) . Critically, neither `handle_handshake_accept` nor `update_from_handshake_data` calls `verify_secp256k1`/`Preamble::verify` to confirm the message was actually signed by the claimed `node_public_key` or by any previously-known key — `verify_secp256k1` is only invoked from `validate_handshake` for the `Handshake` message type (`stackslib/src/net/chat.rs:1058-1070`), not for `HandshakeAccept`.

Because the attacker is the direct TCP peer on that connection, it trivially observes the exact `seq` of any request the local node sends it (e.g. a keep-alive `Ping`, or a `GetNeighbors`) and can immediately answer with a forged `HandshakeAccept`/`StackerDBHandshakeAccept` carrying that same `seq` — no brute-forcing of the 32-bit random `seq` (`next_seq()` at `stackslib/src/net/chat.rs:879-882`) is required. This satisfies `is_solicited()` even though the local node never issued a `Handshake` on that seq, and lets the attacker's forged identity/address/data_url data overwrite conversation state, and — since `set_public_key` is now populated — subsequent messages on that connection will be routed through `handle_authenticated_control_message` instead of the more suspicious unauthenticated path, effectively letting the attacker "authenticate" without ever proving possession of the claimed private key.

### Impact Explanation
A remote, unprivileged peer can, for any conversation where the local node has an outstanding request of any kind, inject an unverified public key, IP/port (`handshake_addrbytes`/`handshake_port`), and `data_url` into that conversation's state, and flip the connection into the "authenticated" code path without ever demonstrating ownership of the claimed key. This is an authentication-bypass / unauthenticated write to in-memory peer state. If this state subsequently feeds neighbor-walk bookkeeping (`stackslib/src/net/neighbors/walk.rs` `handle_handshake_accept`) it can propagate forged peer/address records into the `PeerDB` and onward via `GetNeighbors` gossip to other nodes. This is repeatable on every conversation/reconnect and requires only a handful of crafted messages, matching the Critical category (unauthenticated write to state / auth bypass / potential network-wide propagation of forged data).

### Likelihood Explanation
Preconditions are minimal and commonly met: the target connection must not yet have a known public key for the remote (true for every freshly-opened p2p connection until handshake completes) and the local node must have at least one outstanding request on that connection (Handshake, Ping, GetNeighbors, etc., all of which are issued as part of normal peer lifecycle). The attacker only needs to run a normal P2P client that connects to the node's p2p port, observe the `seq` on any inbound request (plaintext, unencrypted on the wire), and reply with a crafted message — no secrets, no privileged role, and full remote reachability. Cost per exploitation attempt is a single crafted message.

### Recommendation
Bind solicitation matching to message type, not just `seq`: `ReceiverNotify`/`is_solicited`/`fulfill_request` should record and check the expected reply type (e.g., `Handshake→{HandshakeAccept,HandshakeReject,Nack}`, `Ping→Pong`, etc.) alongside `expected_seq`. Independently, `handle_handshake_accept` should require and verify a signature over the `HandshakeAcceptData`/`StackerDBHandshakeData` payload against the embedded `node_public_key` (mirroring `validate_handshake`'s `verify_secp256k1` check for `Handshake`), so identity claims in `HandshakeAccept` cannot be accepted without cryptographic proof of key ownership.

### Proof of Concept
Rust test in `stackslib/src/net/chat.rs` test module (`mod test`), modeled on existing tests such as the one at `stackslib/src/net/chat.rs:4083+`:
1. Create `convo_1` (local, no public key known for peer) and a raw attacker-controlled `StacksMessage` builder (not going through `convo_2`'s normal handshake flow).
2. Have `convo_1` issue `send_signed_request` with a `Ping` payload (`ttl` large), capturing the `ReplyHandleP2P`'s request `seq = msg.request_id()`.
3. Before delivering any real `Pong`, craft a `HandshakeAccept` (or `StackerDBHandshakeAccept`) `StacksMessage` with `preamble.seq` set to the captured `seq`, arbitrary `HandshakeAcceptData` (attacker-chosen `node_public_key`, `addrbytes`, `data_url`), sign it with an arbitrary/unrelated key (or leave unsigned/garbage signature) — do NOT go through the legitimate handshake protocol.
4. Feed this crafted message into `convo_1`'s inbox (as done via `convo_send_recv` helpers) and call `convo_1.chat(...)`.
5. Assert that `self.connection.is_solicited(&msg)` returned `true` for the mismatched type, that `convo_1.connection.get_public_key()` now equals the attacker's forged key, and that `convo_1.data_url`/`handshake_addrbytes` reflect the attacker-supplied values — demonstrating state mutation from an unauthenticated, unverified, type-mismatched reply.
