### Title
DisconnectGitAlternates allows unauthenticated-effort repeated triggering of expensive hard-link migration and full connectivity check, enabling self-service DoS - ([File: internal/gitaly/service/objectpool/alternates.go])

### Summary
`DisconnectGitAlternates` invokes `objectpool.Disconnect`, which performs a full `findObjectFiles` walk and hard-link migration of every object in the linked object pool, followed by a `git rev-list --objects --all --quiet` connectivity check, both scaling with the size of the alternate object store. An attacker who owns a repository linked to a large object pool can repeatedly call Link/Disconnect to force this expensive work on every invocation.

### Finding Description
The RPC handler in `internal/gitaly/service/objectpool/alternates.go` (`server.DisconnectGitAlternates`, lines 19-42) validates only that the repository is well-formed, then delegates directly to `objectpool.Disconnect` [1](#0-0) . `Disconnect`, in `internal/git/objectpool/disconnect.go`, walks the entire alternate object directory via `findObjectFiles` and hard-links every object file into the requesting repository [2](#0-1) , then temporarily removes `objects/info/alternates` and performs a `git rev-list --objects --all --quiet` connectivity check over the now-standalone repository before either committing or rolling back [3](#0-2) . Both operations are proportional to the size of the object pool/repository, not the request payload, so a client can force disproportionate server-side work with a trivially small RPC. Re-linking the repository to the pool (`LinkRepositoryToObjectPool`) and calling `Disconnect` again repeats the full cost each time, since `Disconnect` only exits early when `altInfo.Exists` is false or there are no alternate object directories [4](#0-3) . Concurrency limiting in Gitaly is per-RPC, and is only enforced when a corresponding entry exists in `cfg.Concurrency`, which is a server-operator-configured, non-default control rather than an inherent protection of this handler — the middleware itself simply passes requests straight to the handler when no limiter is configured for a given method [5](#0-4) . There is no per-repo, per-user or global rate limiting hardcoded specifically for `DisconnectGitAlternates`, and no cost accounting based on object pool size before the expensive work is performed.

### Impact Explanation
This causes disk I/O (hard-link creation across potentially very large pool contents) and CPU load (`git rev-list --objects --all` traversal) proportional to object pool size, on a shared Gitaly storage node. Because storage nodes host multiple tenants' repositories, sustained repeated invocation can degrade latency/throughput for unrelated, co-located repositories sharing the same disk and CPU resources — this matches a DoS/resource-exhaustion impact class scoped to a single Gitaly node's storage, with blast radius affecting other tenants sharing that storage shard.

### Likelihood Explanation
The precondition (owning a repository linked to a large object pool) is achievable by an ordinary user through legitimate self-service actions — creating/forking a large repository and using object pool linking (`CreateObjectPool` + `LinkRepositoryToObjectPool`), which are standard fork-network features, not privileged operations. The attack itself is a simple scripted loop of standard, exposed RPCs (Link → Disconnect → Link → Disconnect) requiring no injected content, malformed input, or bypass of any validation — it uses the RPC exactly as designed. Repeatability is limited only by how often the Link/Disconnect sequence can be re-issued, and by any operator-configured concurrency limits for this specific RPC (which are not enabled by default based on the code reviewed).

### Recommendation
- Add a default per-RPC (and preferably per-repository) concurrency/rate limit for `DisconnectGitAlternates` and `LinkRepositoryToObjectPool` so repeated invocation cannot be used to keep saturating I/O/CPU.
- Consider tracking/caching the "already disconnected" state so redundant `Disconnect` calls on an unchanged repository short-circuit without re-walking and re-linking the whole object store.
- Consider bounding the cost of `findObjectFiles`/hard-link migration and the connectivity check per invocation (e.g., additional queueing, cgroup-based resource isolation per repository, or requiring administrator/elevated privilege for this RPC as its own docstring already flags it as "slightly dangerous").

```go
func (s *server) DisconnectGitAlternates(ctx context.Context, req *gitalypb.DisconnectGitAlternatesRequest) (*gitalypb.DisconnectGitAlternatesResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	repo := s.localRepoFactory.Build(repository)

	storageRoot, err := s.locator.GetStorageByName(ctx, repo.GetStorageName())
	if err != nil {
		return nil, fmt.Errorf("storage by name: %w", err)
	}

	f := storage.NewNoopFS(storageRoot)
	if tx := storage.ExtractTransaction(ctx); tx != nil {
		f = tx.FS()
	}

	if err := objectpool.Disconnect(ctx, f, repo, s.logger, s.txManager); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	return &gitalypb.DisconnectGitAlternatesResponse{}, nil
```
