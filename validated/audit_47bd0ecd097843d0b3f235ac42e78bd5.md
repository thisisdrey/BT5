## Title
Out-of-bounds read past mapped JAR data in `InputZipFile::ProcessCentralDirEntry` due to missing bounds checks - (File: `third_party/ijar/zip.cc`)

### Summary
`ijar` (Bazel's interface-jar stripping tool, invoked as a build action on every `.jar` dependency that's used for Java compilation) parses ZIP central-directory records with `InputZipFile::ProcessCentralDirEntry`. Unlike `ProcessLocalFileEntry`, which calls `EnsureRemaining()` before reading variable-length fields, `ProcessCentralDirEntry` reads `file_name_length`, `extra_field_length`, `file_comment_length` and then advances `p`/`extra_p` with `get_u2le`/`get_u4le`/`get_u8le` (defined in `third_party/ijar/common.h`) without ever validating that these fields' declared lengths remain inside the mapped input file. [1](#0-0) [2](#0-1) 

### Finding Description
`FindZipCentralDirectory` computes the central directory bounds from the End-Of-Central-Directory record and validates `cd.central_dir_offset + cd.central_dir_size <= in_length` [3](#0-2) , but that check only bounds the *aggregate* central-directory region — it does not validate any individual entry's `file_name_length`/`extra_field_length`/`file_comment_length` fields against the remaining bytes in that region or against the whole mapped file.

Inside `ProcessCentralDirEntry`:
- `file_name_length`, `extra_field_length`, `file_comment_length` are read directly from attacker-controlled bytes [4](#0-3) .
- `memcpy(filename, p, len)` copies from `p` for up to `file_name_length` bytes with no check that `p + len` is still inside the mapped buffer [5](#0-4) .
- The extra-field loop reads `header_id`/`data_size` via `get_u2le` and advances `extra_p` by `data_size` without ever checking `extra_p + 4 <= p` before dereferencing, and without checking `extra_p` stays within the mapped input [6](#0-5) .

This is structurally the same bug class as CVE-2018-11697 in LibSass's `Prelexer::exactly()`: a length-driven scan/copy over attacker-supplied bytes that omits a bounds check against the end of the buffer, letting a crafted length field walk the read pointer past the end of the mapped region into unmapped memory.

`get_u2le`/`get_u4le`/`get_u8le` themselves perform no bounds checking either — they are raw pointer dereferences [7](#0-6) , so every call site is responsible for ensuring the read stays in-bounds. `ProcessLocalFileEntry` does this correctly via `EnsureRemaining()` [8](#0-7) , but `ProcessCentralDirEntry`, which drives both `ProcessNext()` (used by `AddJar`/interface-jar generation) and `CalculateOutputLength()`, does not.

### Impact Explanation
`ijar` runs as a genai/build action on jars supplied as dependencies (e.g., fetched via `http_jar`/`http_archive`/Maven-style external repositories, or checked into an untrusted branch that CI builds). An attacker who controls the content of such a jar — a hostile origin server or a malicious commit on a branch that is later built — can craft a ZIP central-directory entry with a `file_name_length`/`extra_field_length`/`file_comment_length` value that is inconsistent with the file's actual size but still passes the coarse "`central_dir_offset + central_dir_size <= in_length`" check (e.g., a length that is large only for the *last* entry in the CD, so the aggregate check on the *whole* central directory still holds while the individual entry read runs past the mapped file). This causes `ijar` to read unmapped memory, matching the "out-of-bounds read...disclose information or...cause a denial of service" characterization from the reference CVE. Because `mmap`-based access to unmapped pages typically triggers SIGSEGV/SIGBUS, the primary practical impact is a crash of the `ijar` build tool (denial of service against the build), with the memcpy path additionally capable of copying adjacent-heap bytes into the recovered `filename` buffer if the OOB read lands on a still-mapped page beyond the intended data (information disclosure into diagnostic output/derived symlink names).

### Likelihood Explanation
Reaching this code only requires the ability to publish or serve a crafted `.jar`/interface-jar input that Bazel's build consumes as a Java dependency — exactly the "unprivileged attacker publishing content a victim's build fetches" threat model. No credentials, no access to the victim's machine, and no interaction with a trusted root-repo `BUILD`/`.bzl` file are needed; only a malformed ZIP central directory entry inside an otherwise plausible jar is required.

### Recommendation
Add explicit bounds checks (analogous to `EnsureRemaining()` in `ProcessLocalFileEntry`) in `ProcessCentralDirEntry` before reading/copying `file_name_length`, `extra_field_length`, and `file_comment_length` bytes, verifying `p + <declared length> <= end_of_mapped_region` (and similarly bound the extra-field sub-loop against the parent entry's `extra_field_length` and the mapped region) before any `memcpy`/`get_u*le` call.

### Proof of Concept
Note: I was not able to fully verify with a build/execution environment (no filesystem/terminal access in this session) that a specific byte-for-byte crafted jar reliably triggers a SIGSEGV versus being caught by some earlier, unexamined guard (e.g., `MappedFile` page-fault handling or OS-level accessible-but-unmapped-page behavior). The following is the intended reproduction outline for a `src/test/...` C++ unit test against `third_party/ijar/zip.cc`, but it has not been executed:

1. Construct a minimal ZIP byte buffer containing: a valid EOCD record whose `central_dir_offset`/`central_dir_size` satisfy the `FindZipCentralDirectory` aggregate check.
2. Place a single central-directory entry near the very end of the mapped buffer, with `file_name_length` (or `extra_field_length`) set to a value that would require reading bytes past `bytes + in_length`.
3. Call `ZipExtractor::Create()`/`ProcessAll()` (or directly `InputZipFile::ProcessCentralDirEntry`) on this buffer and observe an out-of-bounds read (e.g., via ASan `heap-buffer-overflow`/`SEGV on unknown address`) when `memcpy(filename, p, len)` or the extra-field loop dereferences past the mapped region.

This should be added as a `third_party/ijar/zip_test.cc`-style test built with AddressSanitizer to make the OOB read observable deterministically, since a plain (non-ASan) build may not crash if the adjacent memory happens to be mapped.

bool InputZipFile::ProcessCentralDirEntry(const u1 *&p, u8 *compressed_size,
                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
  const u1 *extra_p = p;
  p += extra_field_length;
  while (extra_p != p) {
    const u2 header_id = get_u2le(extra_p);
    const u2 data_size = get_u2le(extra_p);
    const u1 *extra = extra_p;
    extra_p += data_size;
    if (header_id == ZIP64_EXTRA_FIELD_TAG) {
      if (*uncompressed_size == U4_MAX) {
        *uncompressed_size = get_u8le(extra);
      }
      if (*compressed_size == U4_MAX) {
        *compressed_size = get_u8le(extra);
      }
      if (*offset == U4_MAX) {
        *offset = get_u8le(extra);
      }
    }
  }
  p += file_comment_length;
  return true;
}

inline u1 get_u1(const u1 *&p) {
    return *p++;

inline u2 get_u2be(const u1 *&p) {
    u4 x = (p[0] << 8) | p[1];
    p += 2;
    return x;
}

inline u2 get_u2le(const u1 *&p) {
    u4 x = (p[1] << 8) | p[0];
    p += 2;
    return x;
}

inline u4 get_u4be(const u1 *&p) {

inline u8 get_u8le(const u1 *&p) {
