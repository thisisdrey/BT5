### Title
`remove_account` fails to purge PromiseYield/YieldId state, letting resumed promises from a deleted account act against a recreated account of the same name - ([File: core/store/src/utils/mod.rs])

### Summary
`remove_account` in `core/store/src/utils/mod.rs` deletes `Account`, `ContractCode`, `AccessKey`/`GasKeyNonce`, and `ContractData` entries for a deleted account, but never removes `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, or `DataIdToYieldId` trie rows scoped to that `account_id`. Because these trie keys are addressed only by the account-id string (not by any per-incarnation identifier), a pending yield created by the old owner of an account can survive deletion and later be resolved against a newly re-created account of the same name.

### Finding Description
`TrieKey::YieldIdToDataId`, `TrieKey::DataIdToYieldId`, `TrieKey::PromiseYieldStatus`, and `TrieKey::PromiseYieldReceipt` are all keyed purely by `receiver_id: AccountId` (a string) plus a `yield_id`/`data_id`. [1](#0-0) 

`remove_account` is the function invoked by `action_delete_account` to purge state when `DeleteAccountAction` executes: [2](#0-1) [3](#0-2) 

It only enumerates and deletes `Account`, `ContractCode`, `AccessKey`/`GasKeyNonce` (by iterating the access-key prefix) and `ContractData` (by iterating the contract-data prefix). It does not iterate or remove `YieldIdToDataId`, `DataIdToYieldId`, `PromiseYieldStatus`, or `PromiseYieldReceipt` rows under that account's namespace. Nothing else in the delete-account code path (or account-creation validation) performs this cleanup either.

Exploit flow:
1. Account A (a subaccount, e.g. `sub.parent.near`) has a deployed contract that calls `promise_yield_create_with_id`. This stores `YieldIdToDataId{receiver_id: A, yield_id}` / `DataIdToYieldId{receiver_id: A, data_id}` and a `PromiseYieldReceipt{receiver_id: A, data_id}` scheduled to resume A's own callback. [4](#0-3)  This can be triggered indirectly through a `DelegateAction` signed by A and relayed by any unprivileged relayer.
2. A is deleted via `DeleteAccountAction`. `remove_account` clears the account and its keys/code/data but leaves the `YieldIdToDataId`/`DataIdToYieldId`/`PromiseYieldStatus`/`PromiseYieldReceipt` rows for `receiver_id = A` in the trie. [5](#0-4) 
3. Because top-level uniqueness is only enforced at creation time (not by scrubbing all historical namespaces), a different owner can later recreate an account with the identical name A (e.g. `sub.parent.near` created again by `parent.near`).
4. Anyone (the original relayer, or new-A's own contract) can call `promise_yield_resume_with_yield_id`/`submit_promise_resume_data_with_yield_id` using the old `yield_id`. This function only checks `get_data_id_for_yield_id(trie_update, &self.account_id, user_yield_id)` — i.e. it purely does a trie lookup keyed by the account-id string, with no notion of "this account was deleted and recreated." [6](#0-5) 
5. The stale mapping resolves, and the runtime finds and executes the old `PromiseYieldReceipt{receiver_id: A, data_id}` still stored under new-A's namespace, delivering a `PromiseResume` and executing the yielded action receipt against new-A's live account/contract state: [7](#0-6) 

This breaks authorization exactness: the resumed callback (created under authority of old-A's DelegateAction/signer) fires against new-A's contract without new-A's owner ever having signed anything, and can invoke privileged self-call-gated logic on new-A because these yielded receipts execute as the account calling itself.

### Impact Explanation
This is an authorization escalation across account re-creation: state and pending "self callback" execution created under one owner's key persists into and can be triggered against a subsequent, unrelated owner of the same account name. Depending on what the new contract deployed at that account does with self-calls (a common trust pattern is "only callable by `predecessor_id == current_account_id`"), an attacker relayer holding a stale `yield_id` can invoke privileged internal callback logic on the new owner's contract that was never authorized by the new owner. This matches the "authorization escalation across accounts or promises" bounty category.

### Likelihood Explanation
Preconditions: an account name must be deleted and re-created (permitted by protocol for subaccounts / any account whose owner chooses to delete it), a relayer/attacker must have observed or been party to the earlier `yield_create_with_id` call and know the `yield_id` (which is user-chosen and can be attacker-supplied via a meta-transaction the attacker itself relays), and the resume must occur after re-creation. This requires no validator/node privilege — an ordinary funded account can sign the DelegateAction, delete the account, and (as relayer or via any account) submit the resume. The main friction is the specific choreography (delete+recreate before resume, and a contract at the new account whose logic is meaningfully triggerable via the leftover callback), which is feasible but requires deliberate setup by the attacker rather than being automatic for arbitrary victims.

### Recommendation
`remove_account` should also enumerate and delete all `YieldIdToDataId`, `DataIdToYieldId`, `PromiseYieldStatus`, and `PromiseYieldReceipt` rows scoped to `account_id` (via prefix iteration similar to the existing access-key/contract-data cleanup), so that no dangling promise-yield state survives across a `DeleteAccountAction`. Additionally, consider binding yield resumption to an account "incarnation" (e.g. include a per-account creation nonce/hash in the trie key or in `PromiseYieldStatus`) so that even leftover rows cannot be misattributed to a re-created account.

### Proof of Concept
Integration/test-loop plan:
1. Deploy a test contract on account A with a method that calls `promise_yield_create_with_id` with a fixed `yield_id`, and a callback method gated on `predecessor_account_id() == current_account_id()` (self-call only) that performs a sensitive state mutation.
2. Have A sign this call inside a `SignedDelegateAction`; relay it via `check_meta_tx_execution` (see `integration-tests/src/tests/features/delegate_action.rs`) so the yield is created and `YieldIdToDataId{receiver_id: A, yield_id}` is stored.
3. Submit `DeleteAccountAction` for A (see `test_delete_account` helpers in `runtime/runtime/src/actions_test_utils.rs`), and assert with `env.view_account` that A no longer exists.
4. Re-create account A (same account id) with a different owner key and a benign or unrelated contract.
5. Submit `promise_yield_resume_with_yield_id` (or the underlying `submit_promise_resume_data_with_yield_id`) against new-A using the original `yield_id`.
6. Assert: (a) the lookup in `TrieKey::YieldIdToDataId{receiver_id: A, yield_id}` still succeeds after step 3/4 (proving the leak), and (b) the resumed callback executes against new-A's state (the sensitive mutation from step 1 occurs) despite new-A's owner never having signed any `DelegateAction`/authorizing transaction — demonstrating authorization escalation across the account re-creation boundary.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}

    fn create_promise_yield_receipt_with_id(
        &mut self,
        receiver_id: AccountId,
        user_yield_id: YieldId,
    ) -> Result<Option<(ReceiptIndex, CryptoHash)>, VMLogicError> {
        // Check for duplicate yield_id in trie. TrieUpdate also reflects writes from earlier
        // calls within the same function call, so this also catches in-transaction duplicates.
        if has_yield_id_mapping(self.trie_update, &receiver_id, user_yield_id)
            .map_err(wrap_storage_error)?
        {
            return Ok(None);
        }

        let input_data_id = self.generate_data_id();

        // Store bidirectional yield_id <-> data_id mappings
        set_yield_id_mapping(&mut self.trie_update, &receiver_id, user_yield_id, input_data_id);

        let receipt_index =
            self.receipt_manager.create_promise_yield_receipt(input_data_id, receiver_id.clone());

        set_promise_yield_status(
            &mut self.trie_update,
            &receiver_id,
            input_data_id,
            PromiseYieldStatus::Yielded,
        );

        Ok(Some((receipt_index, input_data_id)))
    }
