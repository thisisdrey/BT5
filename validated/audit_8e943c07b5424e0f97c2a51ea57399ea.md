### Title
Tokens mistakenly sent to `Treasury` are permanently locked since only registered underlyings can ever leave - (File: contracts/Treasury.sol)

### Summary
`Treasury` holds collateral for every `DepositToken` in a `Pool`, but provides no generic token-recovery path. Unlike `DepositToken`, `DebtToken`, `NativeTokenGateway`, `VesperGateway`, and `AMO` — which all inherit `TokenHolder.sweep` — `Treasury` inherits only `Initializable`, `ReentrancyGuard*`, `Manageable`, and `TreasuryStorageV1` and defines exactly three token-moving functions, each restricted to a narrow token set. Any ERC20 (or excess of a registered underlying) transferred to the `Treasury` address that is not a Vesper reward token can never be withdrawn, by anyone, including the governor. This is the same bug class as the OpenQ `TieredFixedBountyV1.receiveFunds` issue (contract can be funded with tokens that the payout path cannot release), but in Metronome there is not even an expiry/refund fallback — the freeze is permanent.

### Finding Description
`Treasury.pull()` reverts unless `msg.sender` is a registered `DepositToken`, and only ever transfers that caller's own `underlying()` [1](#0-0) . `Treasury.migrateTo()` iterates `pool.getDepositTokens()` and transfers only each deposit token's `underlying()` [2](#0-1) . `Treasury.claimFromVesper()` transfers only tokens returned by `vPool.poolRewards().getRewardTokens()`, and for reward tokens that are also collateral it keeps `depositToken.totalSupply()` behind [3](#0-2) .

Therefore:

1. An ERC20 sent to the `Treasury` that is not any deposit token's underlying and not listed in some `IPoolRewards.getRewardTokens()` has zero exit paths — permanently frozen.
2. Even a registered underlying sent directly (donation/mistake) beyond `depositToken.totalSupply()` is permanently frozen: cumulative `pull` amounts are bounded by burned msdTOKEN supply, and `claimFromVesper` explicitly subtracts `totalSupply()` from the transferable surplus [4](#0-3) .

There is no `sweep`, no `rescue`, and `receive`/`fallback` do not exist to block plain ERC20 transfers (which don't trigger them anyway).

### Impact Explanation
Permanent freezing of funds: any token mistakenly transferred to the `Treasury` address (EOAs frequently send funds to contracts by mistake; integrators depositing via `transfer` instead of `DepositToken.deposit`) is unrecoverable. For registered collaterals, surplus donations inflate `Treasury`'s balance but, since withdrawal requires burning msdTOKEN, the excess can never leave — it also silently distorts surplus accounting in `claimFromVesper`. Unlike the referenced bounty issue where funds could be refunded after expiration, here there is no recovery mechanism at all.

### Likelihood Explanation
Requires user error (accidental transfer to the Treasury contract), which is exactly the accidental-funding scenario the analogous report was accepted for. The Treasury is a widely known, long-lived address receiving constant token flows, so mistaken direct transfers are a realistic occurrence. No privileged action is needed to trigger the lock; the absence of a recovery function (present in sibling contracts via `TokenHolder`) makes the outcome deterministic.

### Recommendation
Have `Treasury` inherit `TokenHolder` (or add a governor-only `sweep`) that permits recovering non-underlying tokens, while reverting for any token that is a registered deposit token's `underlying()` so collateral backing cannot be drained. Alternatively, allow `sweep` of underlying only for `balance - depositToken.totalSupply()` surplus.

### Proof of Concept
Foundry fork test sketch:

```solidity
// Fork e.g. mainnet; resolve a live Pool -> treasury via pool.treasury()
IPool pool = IPool(<live pool>);
Treasury treasury = Treasury(address(pool.treasury()));

// Attacker/victim: any EOA mistakenly sends a random ERC20 to Treasury
ERC20Mock stray = new ERC20Mock("STRAY", "STRAY", 18);
stray.mint(alice, 1000e18);
vm.prank(alice);
stray.transfer(address(treasury), 1000e18);

// 1. pull() cannot take it: caller isn't a DepositToken, and even a
//    DepositToken can only pull its own underlying()
vm.expectRevert(SenderIsNotDepositToken.selector);
treasury.pull(alice, 1000e18);

// 2. migrateTo() only moves registered underlyings -> stray stays
//    (callable only by Pool, but even when invoked it skips `stray`)

// 3. claimFromVesper() only moves tokens in vPool.poolRewards().getRewardTokens()
//    -> `stray` is not a reward token -> stays

// No sweep/other function exists on Treasury's ABI.
assertEq(stray.balanceOf(address(treasury)), 1000e18); // permanently locked
```

The same holds for donating extra of a registered collateral: `underlying.transfer(treasury, x)` raises the balance, but total withdrawable via `pull` remains capped by `depositToken.totalSupply()`, and `claimFromVesper` subtracts `totalSupply()` before transferring surplus.
