### Title
OS Command Injection via unsafe shell quoting of `patch_tool`/`patch_args`/`patch_cmds` in Bazel's repository `patch()` utility - (File: `tools/build_defs/repo/utils.bzl`)

### Summary
Bazel's canonical repository-rule patching helper `patch()` builds a shell command line by naively wrapping each `patch_args` element in single quotes and concatenating `patch_tool` unquoted, then executes it via `bash -c` / `powershell /c`. Any embedded shell metacharacter (in particular a single quote) in these attacker-influenced strings breaks out of the quoting and injects arbitrary shell commands that run on the machine performing the `bazel build`/`bazel sync`, exactly analogous to the reported Jison `exec("jison " + process.argv[2])` bug where unsanitized external input was concatenated into a shell command string.

### Finding Description
`patch()` in [1](#0-0)  is the implementation used by Bazel's built-in `http_archive`, `git_repository`, and `new_git_repository` repository rules (and by any module extension that calls this shared helper) to apply patches to a freshly fetched, external, attacker-influenced repository.

Key problems:
- `patch_tool` is interpolated into the command string with **no quoting at all**.
- Each element of `patch_args` is wrapped only with `"'%s'" % arg` — a single embedded `'` character in any `patch_args` entry breaks out of the quoting and lets the attacker append arbitrary shell syntax (`; `, `&&`, backticks, etc.).
- The resulting string is passed to `ctx.execute([bash_exe, "-c", command], ...)`, i.e. it is executed by a real shell, not as a literal argv vector.

The same shell-construction pattern is repeated for `patch_cmds`/`patch_cmds_win`, but those are documented as raw shell/PowerShell snippets so their execution is "by design"; the vulnerability specifically affects `patch_tool` and `patch_args`, which are meant to be a *tool path* and a *list of flags*, not shell code, yet are treated unsafely.

`patch_tool`/`patch_args`/`patch_cmds` are ordinary string/string_list attributes on `http_archive`/`git_repository` (see `tools/build_defs/repo/git.bzl` attrs, e.g. [3](#0-2) ), and the same `patch()` helper (with the same attributes) is exposed publicly via `@bazel_tools//tools/build_defs/repo:utils.bzl` for use by module-extension implementations (`module_ctx`) that construct repository specs programmatically from data the extension itself downloaded or parsed (manifests, lockfiles, source.json-derived metadata, etc. fetched from third-party origins). Any such value that is influenced by content from a hostile origin — and is not restricted to `-p<N>` syntax or free of `'`/shell metacharacters — flows unmodified into the shell string above.

### Impact Explanation
If an attacker (e.g. a malicious/compromised package/module maintainer, or a hostile mirror serving a manifest/config file that a repository rule or module extension consumes to compute `patch_tool`/`patch_args`) can get a single quote or other shell metacharacter into one of these values, they achieve arbitrary command execution in the context of the Bazel client process that is fetching/patching the dependency — i.e. on the developer's or CI machine performing the build, with no additional access needed beyond publishing/serving that content. This is a full OS command injection, matching the severity of the referenced Jison CVE-2020-8178.

### Likelihood Explanation
`patch()` is invoked by default for every `http_archive`/`git_repository` with `patches`/`remote_patches` set and a non-default `patch_tool`/`patch_args`, and by any module extension using the shared `@bazel_tools` patch helper. Triggering the bug only requires the string reaching `patch_args`/`patch_tool` to contain an unescaped `'`; no privileged access to the build machine, output base, or trusted root MODULE.bazel/BUILD files is required — only the ability to influence the *content* consumed when computing those attribute values (e.g. via a malicious dependency's data files). No sha256/integrity mechanism protects the *content* of `patch_args`/`patch_tool` strings themselves (they aren't hashed/pinned data — they are Starlark string values), so existing checksum verification does not stop this.

### Recommendation
Replace the manual `"'%s'" % arg` quoting with a proper shell-quoting function (e.g. an equivalent of Python's `shlex.quote`, correctly escaping embedded `'`), and quote `patch_tool` as well. Alternatively, avoid constructing a shell string altogether: invoke the patch tool directly via `ctx.execute([patch_tool] + patch_args + ["<", patchfile])`-style argv construction (a shell is only needed for the `<` redirection, which can be handled by reading the file content and passing it via `stdin`/temp files) so that `patch_args` elements are passed as discrete argv entries rather than interpolated into shell syntax.

### Proof of Concept
A `BuildIntegrationTestCase`/`src/test/shell/bazel` proof can reuse the existing patching test scaffolding (see `tools/build_defs/repo/utils.bzl` `patch()` call sites in `starlark_repository_test.sh`) with:
```python
http_archive(
    name = "pwned",
    url = "...",
    sha256 = "...",
    patch_tool = "patch",
    patch_args = ["-p1", "'; touch /tmp/pwned; '"],
)
```
Running `bazel build @pwned//...` results in `ctx.execute([bash_exe, "-c", "patch -p1 '; touch /tmp/pwned; ' < <patchfile>"])`, and the shell executes `touch /tmp/pwned` as an independent command, demonstrating injection through the naive quoting in [4](#0-3) .
