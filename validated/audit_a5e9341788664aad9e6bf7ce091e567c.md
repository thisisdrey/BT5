### Title
Bypassed `max_receipt_size` check via promise-return / large value-return allows oversized receipts that `BandwidthRequest::make_from_receipt_sizes` cannot request bandwidth for, permanently freezing the receipt in the outgoing buffer - (File: core/primitives/src/bandwidth_scheduler.rs)

### Summary
The receipt size validation intended to enforce `max_receipt_size` (~4 MiB) can be bypassed via `promise_return`/large value-return patterns, as explicitly documented in the codebase's own regression tests referencing a known bug. `BandwidthRequest::make_from_receipt_sizes` assumes no receipt exceeds `max_single_grant`/`max_receipt_size` and simply `break`s out of its loop when `cur_value_idx` reaches `values.len()` without setting a bit for the oversized receipt, meaning bandwidth is never requested to cover it.

### Finding Description
`BandwidthRequest::make_from_receipt_sizes` iterates receipt sizes in the outgoing buffer, accumulates `total_size`, and searches the `values` array (40 entries, up to `max_single_grant`) for a bucket at least as large as `total_size`: [1](#0-0) 
If `total_size` (which includes the oversized receipt) exceeds every entry in `values` (whose max is `params.max_single_grant`, designed to correspond to `max_receipt_size`), the loop `break`s and no bit is ever set for that receipt/the receipts after it, so no bandwidth request is ever generated to cover it - the entry is never eligible for a bandwidth grant and remains permanently stuck in the outgoing buffer.

This scenario is normally prevented because `verifier.rs`/receipt validation is supposed to reject any receipt whose borsh-serialized size exceeds `max_receipt_size`, via `ReceiptValidationError::ReceiptSizeExceeded` [2](#0-1) . However, the repository's own tests document that this check can be bypassed: a function call receipt is validated at exactly `max_receipt_size` when the promise DAG is created, but `output_data_receivers` is mutated afterward (in the `promise_return` case) or a large returned value is wrapped into a data receipt after size validation (in the value-return case), pushing the final receipt size above `max_receipt_size` without re-validation: [3](#0-2) [4](#0-3) 

Both `test_max_receipt_size_promise_return` and `test_max_receipt_size_value_return` explicitly construct this attacker-reachable scenario using ordinary `FunctionCall` transactions against a deployed contract, and assert (via `assert_oversized_receipt_occurred`) that a receipt above `max_receipt_size` does in fact occur on-chain, confirming the bypass is real and already tracked as a known issue (referenced as near/nearcore#12606) rather than a hypothetical: [5](#0-4) [6](#0-5) 

Once such an oversized receipt is buffered for cross-shard delivery, `make_from_receipt_sizes` (invoked per shard to build `BandwidthRequests` for the scheduler) can never generate a sufficient request for it, since `values` tops out at `max_single_grant` which is calibrated to `max_receipt_size`, not to arbitrarily larger sizes produced by the bypass.

### Impact Explanation
This matches the "permanent freezing of user funds / liveness violation" category: the oversized receipt (and any attached NEAR deposit or contract state changes it represents) can never be granted outgoing bandwidth and is stuck forever in the shard's outgoing buffer, violating the invariant that every receipt eventually resolves. Because the growth is unbounded by contract logic (returned value size, chained promises), the attacker can create receipts far above `max_receipt_size`, guaranteeing the loop in `make_from_receipt_sizes` always `break`s early for that entry.

### Likelihood Explanation
The precondition is a funded account deploying an ordinary wasm contract using standard host functions (`promise_then`, `promise_return`, value return) - fully within reach of an unprivileged attacker, no special access needed. This is corroborated by the existing test-loop tests in the repo that already reproduce the oversized-receipt condition using exactly this transaction pattern, so the exploit is not speculative. Repeatability is limited only by gas/storage costs of deploying and calling the contract, which are ordinary transaction costs.

### Recommendation
Fix the underlying `max_receipt_size` bypass (near/nearcore#12606) by re-validating the final serialized receipt size *after* all mutations (e.g., after `output_data_receivers` are appended, or after wrapping a returned value into a data receipt) rather than only at creation time. As defense-in-depth, `BandwidthRequest::make_from_receipt_sizes` should not silently drop bandwidth requests for receipts exceeding the largest bucket; it should either clamp to the maximum request value (so the receipt is still eventually granted, even if slowly) or treat such a receipt as a protocol invariant violation.

### Proof of Concept
Use the existing `test_max_receipt_size_promise_return` and `test_max_receipt_size_value_return` tests in `test-loop-tests/src/tests/max_receipt_size.rs` as the base PoC (they already show oversized receipts occurring on-chain via `assert_oversized_receipt_occurred`). Extend the integration test to:
1. Deploy the contract on a 2+ shard test-loop setup so the oversized receipt must cross shards and land in an outgoing buffer.
2. Run the bandwidth scheduler for many heights (as in `test-loop-tests/src/tests/bandwidth_scheduler.rs` patterns).
3. Assert that the outgoing buffer entry for the oversized receipt is never drained/granted bandwidth (e.g., by inspecting `BandwidthSchedulerState`/outgoing buffer metadata across many applied heights), demonstrating the permanent freeze predicted by the loop `break` in `make_from_receipt_sizes`.
