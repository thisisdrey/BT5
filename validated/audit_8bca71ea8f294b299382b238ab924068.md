### Title
Unbounded length field from precompiled-contract call data drives unchecked array allocation, enabling attempted excessive memory allocation (DoS) - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
CVE-2018-10971 describes FLIF's `Plane` function allocating memory sized by an attacker-controlled value taken directly from a crafted file, without validating it against a sane bound, letting a single malicious input trigger an out-of-memory condition. The same bug class — trusting an attacker-supplied length field to size an array allocation before validating it is consistent with the actual payload — is present in java-tron's TVM precompiled-contract argument decoders.

### Finding Description
`PrecompiledContracts.extractBytes32Array`, `extractBytesArray`, and `extractSigArray` decode ABI-encoded arguments passed to precompiled contracts reachable from ordinary contract calls: [1](#0-0) [2](#0-1) 

In each of these, `int len = words[offset].intValueSafe();` reads a length directly out of attacker-controlled `DataWord[] words` (the raw call-data words handed to the precompile), and immediately allocates `byte[len][]` (or `byte[len][32]`/`byte[len][192]` in similarly-structured `byte[][]` allocations elsewhere in the file, e.g. `extractBytes32Array`) with no upper bound check relative to the actual size of `data`/`words` before the allocation happens. `intValueSafe()` clamps to `Integer.MAX_VALUE`, so a crafted call can set `len` to a value near `Integer.MAX_VALUE`; `new byte[len][]` alone (an array of `Integer.MAX_VALUE` references) attempts to allocate on the order of gigabytes before any bounds validation of the remaining array elements takes place. This mirrors the FLIF `Plane` bug: the size used for allocation is taken from untrusted input and used before the code validates that the input actually contains that much data.

This differs from the explicitly-checked `EnergyCost.calcMemEnergy`/`checkMemorySize` path that gates general TVM memory (`MEM_LIMIT` = 3MB) used for opcodes like `CODECOPY`/`CALLDATACOPY`/`EXTCODECOPY` before their `OperationActions` execute: [3](#0-2) 

That energy-metering gate bounds ordinary VM memory expansion, but the array-length values consumed inside `PrecompiledContracts`'s ABI-array extraction helpers are not passed through this (or any comparable) size check — they are used directly as allocation sizes.

### Impact Explanation
A crafted call to a precompiled contract whose argument decoding goes through `extractBytesArray`/`extractBytes32Array`/`extractSigArray` can supply a length word disconnected from the real size of the supplied call data. This causes the node executing the transaction to attempt a very large heap allocation, which can throw `OutOfMemoryError` mid-execution. Depending on where this is caught (or not) in the precompile/TVM execution stack, this can crash the executing node process or degrade node availability, which is a node-crash/halt-class impact reachable by any account that can submit a contract call (no special privilege required).

### Likelihood Explanation
Reaching this code path requires only crafting `TriggerSmartContract` call data targeting the specific precompiled contract address(es) that route through these helpers, with a length word set to a very large value — an operation any unprivileged account with enough energy/bandwidth to submit a transaction can perform. No special permission, staking, or witness/validator role is needed.

### Recommendation
Before allocating `new byte[len][...]`, validate `len` against the actual remaining size of `words`/`data` (e.g. `len <= (words.length - offset - 1)` or the equivalent byte-length check derivable from `data.length`), and reject the call (return `false`/zero result) if the declared length is inconsistent with the available payload, mirroring the existing `isValidAbiEncoding` bound checks used elsewhere in the same file.

### Proof of Concept
1. Identify a precompiled-contract address whose `execute(byte[] data)` implementation calls `extractBytesArray`, `extractBytes32Array`, or `extractSigArray` on the raw `data` converted to `DataWord[] words`.
2. Craft `data` such that the `DataWord` at the offset consumed as `len` encodes a value close to `Integer.MAX_VALUE`, while the remainder of `data` is minimal/short.
3. Submit a `TriggerSmartContract` transaction invoking that precompile with this crafted `data`.
4. Observe the node attempt `new byte[len][...]`, triggering excessive memory allocation / `OutOfMemoryError` during precompile execution.

Note: I was not able to fully enumerate, within the available search iterations, every specific precompiled-contract `execute` method that calls these three helper functions (the tool only surfaced their definitions, not every call site with full context). This should be verified against the actual call sites before treating the PoC as final, but the core vulnerable pattern — allocation sized by an unchecked, attacker-controlled length word — is clearly present in the cited code.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }

  private static long calcMemEnergy(long oldMemSize, BigInteger newMemSize,
                             long copySize, int op) {
    long energyCost = 0;

    checkMemorySize(op, newMemSize);

    // memory SUN consume calc
    long memoryUsage = (newMemSize.longValueExact() + 31) / 32 * 32;
    if (memoryUsage > oldMemSize) {
      long memWords = (memoryUsage / 32);
      long memWordsOld = (oldMemSize / 32);
      long memEnergy = (MEMORY * memWords + memWords * memWords / 512)
          - (MEMORY * memWordsOld + memWordsOld * memWordsOld / 512);
      energyCost += memEnergy;
    }

    if (copySize > 0) {
      long copyEnergy = COPY_ENERGY * ((copySize + 31) / 32);
      energyCost += copyEnergy;
    }
    return energyCost;
  }

  private static void checkMemorySize(int op, BigInteger newMemSize) {
