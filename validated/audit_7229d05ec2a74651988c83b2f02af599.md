### Title
Attacker can fill a victim's per-account token list with dust deposits, blocking the victim from depositing collateral or issuing new debt — (File: contracts/Pool.sol)

### Summary
`Pool` enforces `MAX_TOKENS_PER_USER = 30` across `depositTokensOfAccount + debtTokensOfAccount` in `onlyIfAdditionWillNotReachMaxTokens` [1](#0-0) . `DepositToken` mints/transfers add a token to the recipient's list whenever the recipient's prior balance is `0` [2](#0-1) . Since deposits accept an arbitrary `onBehalfOf`/`account_` and transfers are permissionless ERC-20-like transfers, an unprivileged attacker can push dust balances of every deposit token in the pool to a victim, permanently filling the victim's list until the victim manually cleans it.

### Finding Description
`DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever `_recipientBalanceBefore == 0` [2](#0-1) . `addToDepositTokensOfAccount` reverts with `UserReachedMaxTokens` once the combined deposit+debt list reaches 30 [3](#0-2) . Because `DepositToken` is an externally transferable token and `deposit` allows crediting an arbitrary account, an attacker can, for each of the pool's deposit tokens, acquire a tiny amount and `transfer`/`deposit` 1 wei to the victim. Each new token consumes a slot.

Once the list is full:
- Any subsequent deposit into a collateral the victim does not already hold reverts (`UserReachedMaxTokens`), because `_mint` → `addToDepositTokensOfAccount` reverts.
- `DebtToken.issue/mint` into a synthetic the victim does not already hold reverts via `addToDebtTokensOfAccount` [4](#0-3) , blocking leverage/borrowing for vault-relevant synthetics.
- For a fresh account with open debt but no usable collateral slot, this can prevent the victim from topping up collateral to avoid liquidation (deposit into an unheld collateral token reverts; the victim must first detect and clear dust).

There is no pause, `onlyPool`, or health check that stops this: `addTo*` calls are driven by the token contracts themselves, and the attacker only uses public `transfer`/`deposit` entry points.

### Impact Explanation
Temporary freezing of funds / griefing: the victim is prevented from depositing new collateral types and from issuing debt in new synthetics until they manually transfer out or consolidate the dust entries (`_transfer` removes a token when balance reaches 0 [5](#0-4) ). For a victim approaching the liquidation threshold who needs a *new* collateral to restore health, the forced delay can directly result in liquidation loss.

### Likelihood Explanation
The attack requires only standard token transfers/deposits and gas cost proportional to the number of enabled deposit tokens (≤30). No privileged role, oracle manipulation, or flash loan is needed. Mitigating factor: the victim can self-recover by clearing dust, and existing tokens already in the list remain usable, so the window of denial depends on the victim's portfolio composition.

### Recommendation
Whitelist only user-initiated additions: e.g., only add a deposit token to `depositTokensOfAccount` when it is added via `deposit`/`_mint` for the sender themselves, or add a per-token minimum balance threshold; alternatively allow `Pool.withdraw`/repay paths to ignore the cap and let removal be batched by anyone (`sweepDust`) so victims can free slots cheaply.

### Proof of Concept
```solidity
// Foundry-style PoC (fork or unit env with deployed Pool, DepositTokens d0..d29)
function testFillVictimTokenList() public {
    address victim = address(0xBEEF);

    // Precondition: victim holds no deposit tokens and no debt tokens.
    assertEq(pool.getDepositTokensOfAccount(victim).length, 0);

    // Attacker deposits dust of each collateral and transfers 1 wei of each
    // DepositToken to the victim (or calls deposit(1, victim)).
    for (uint i; i < 30; ++i) {
        IDepositToken dt = IDepositToken(pool.getDepositTokens()[i]);
        IERC20 underlying = dt.underlying();
        deal(address(underlying), attacker, 1);
        vm.startPrank(attacker);
        underlying.approve(address(dt), 1);
        dt.deposit(1, attacker);            // attacker mints 1 wei msdToken
        dt.transfer(victim, 1);             // _transfer -> addToDepositTokensOfAccount(victim)
        vm.stopPrank();
    }
    assertEq(pool.getDepositTokensOfAccount(victim).length, 30);

    // Victim can no longer deposit a collateral type it does not hold:
    vm.prank(victim);
    vm.expectRevert(Pool.UserReachedMaxTokens.selector);
    someOtherDepositToken.deposit(1e18, victim);

    // Victim can no longer issue debt in a synthetic it does not hold:
    vm.prank(victim);
    vm.expectRevert(Pool.UserReachedMaxTokens.selector);
    someDebtToken.issue(1e18); // mint -> addToDebtTokensOfAccount reverts
}
```
Note: if the pool has fewer than 30 deposit tokens, the remaining slots can be filled by first creating dust debt positions in distinct synthetics (each `issue` adds a `DebtToken` to `debtTokensOfAccount`).
