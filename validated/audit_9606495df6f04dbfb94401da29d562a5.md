### Title
UnfreezeBalanceContract can zero out an unrelated new receiver's `AcquiredDelegatedFrozenBalance`, causing permanent loss of resource weight for a legitimate, unrelated delegation - (File: `actuator/src/main/java/org/tron/core/actuator/UnfreezeBalanceActuator.java`)

### Summary
`UnfreezeBalanceActuator#execute` resolves the delegated-resource record purely from the deterministic `(ownerAddress, receiverAddress)` key produced by `DelegatedResourceCapsule.createDbKey`, but then mutates whatever `AccountCapsule` currently lives at `receiverAddress` in `AccountStore`. If the account that originally received the delegation is deleted (e.g. via `AccountStore.delete`, contract suicide, or a CREATE2 collision as covered by the project's own `FreezeTest`/`Create2Test` suite) and a different, unrelated account is later created/recreated at that same address with its own, independently-acquired `acquiredDelegatedFrozenBalanceForBandwidth/Energy`, the old delegator's `UnfreezeBalanceContract` will still succeed and will overwrite/zero the new occupant's legitimately-acquired delegated balance — exactly mirroring the JPEG'd bug class of "existing user's locked position overwritten/zeroed by state tied to a shared key that is reused across unrelated parties."

### Finding Description
`UnfreezeBalanceActuator.execute` (and the mirrored `UnfreezeBalanceProcessor.execute` for TVM native calls) computes the `DelegatedResourceCapsule` key from `(ownerAddress, receiverAddress)` [1](#0-0) , reads the *current* `AccountCapsule` at `receiverAddress` [2](#0-1) , and then reduces (or, in the "insufficient" branch, force-zeroes) that account's `AcquiredDelegatedFrozenBalanceForBandwidth`/`ForEnergy` field based purely on the stale `DelegatedResourceCapsule.frozenBalance` value: 

```
if (dynamicStore.getAllowTvmSolidity059() == 1
    && receiverCapsule.getAcquiredDelegatedFrozenBalanceForBandwidth() < unfreezeBalance) {
  oldNetWeight = unfreezeBalance / TRX_PRECISION;
  receiverCapsule.setAcquiredDelegatedFrozenBalanceForBandwidth(0);
}
``` [3](#0-2) 

There is no check that the `AccountCapsule` currently at `receiverAddress` is the *same* logical account that originally received the delegation (e.g. via a creation-time nonce, an account epoch counter, or a link back from the `DelegatedResourceCapsule` verifying continuity). The `DelegatedResourceStore` entry for `(owner, receiver)` is address-keyed only and is never invalidated when the receiver account is deleted (this happens on contract `SUICIDE`/`selfdestruct` and is directly exercised in `FreezeTest.testContractSuicideToExistNormalAccount`/`testCreate2SuicideToAccount`, and in `UnfreezeBalanceActuatorTest.testUnfreezeDelegatedBalanceForBandwidthWithRecreatedReceiver`, which the project's own test suite proves the existing behavior for) [4](#0-3) . When a brand-new, unrelated account is subsequently created at that address and independently receives its own delegated resource (a totally different `(newOwner, receiverAddress)` `DelegatedResourceCapsule`, giving it its own `AcquiredDelegatedFrozenBalance`), the original delegator can still submit `UnfreezeBalanceContract` referencing the stale `(oldOwner, receiverAddress)` pair. `validate()` only checks that the `DelegatedResourceCapsule` for that key still exists and has expired [5](#0-4)  — it does not verify the receiver's identity continuity. `execute()` then zeroes the *current* receiver's `AcquiredDelegatedFrozenBalance`, which now backs the *new* owner's still-active, unrelated delegation, as demonstrated by the test's own assertion that the new receiver's `AcquiredDelegatedFrozenBalanceForBandwidth` drops from `10` to `0` [6](#0-5)  after the stale unfreeze from the old owner runs.

This is the same bug class as the JPEG'd report: a shared, reusable key (there: NFT index; here: TRON address) is used to look up and mutate per-participant accounting state, and a later, unrelated participant's legitimate position is silently destroyed by an action tied to a stale prior occupant of that key.

### Impact Explanation
The victim here is whichever party currently delegated resource to the reused address (the *new* delegator, whose `DelegatedResourceCapsule` and receiver-side `AcquiredDelegatedFrozenBalance` still show the balance as valid/undelegated, since that record was never touched). After the stale unfreeze fires:
- The receiver's `AcquiredDelegatedFrozenBalanceForBandwidth/Energy` on `AccountStore` is silently zeroed, decoupling it from the still-existing, still-locked `DelegatedResourceCapsule` for `(newOwner, receiver)`.
- The new delegator's TRX remains frozen/locked (their own `DelegatedResourceCapsule` and `AccountCapsule.DelegatedFrozenBalance` are untouched), but the resource weight/bandwidth-or-energy backing it on the receiver side has vanished, and `TotalNetWeight`/`TotalEnergyWeight` accounting is decremented inconsistently with the real outstanding delegation.
- When the new delegator eventually tries to unfreeze their own genuine delegation, the receiver-side `AcquiredDelegatedFrozenBalance` is already 0, which can again trigger the "insufficient" branch and can produce further inconsistent/negative-clamped weight adjustments, and the resource benefit they paid TRX for is unrecoverable even though their principal is eventually returned — the network-wide resource accounting (`TotalNetWeight`/`TotalEnergyWeight`) becomes permanently desynchronized from actual locked TRX. This satisfies the "permanent freezing of funds / unbacked resource accounting" impact bar.

### Likelihood Explanation
Reaching this state requires an account to be deleted (achievable today via contract `SUICIDE`/`selfdestruct` to a receiver address that has outstanding delegated-resource-as-receiver bookkeeping, as already exercised by `FreezeTest.testContractSuicideToExistNormalAccount`/`testCreate2SuicideToAccount`) and then recreated (e.g. re-deploying a CREATE2 contract to the same address, or the address later receiving a new normal-account creation via transfer). Both delegators — the stale one and the new one — are ordinary, unprivileged transaction senders (`FreezeBalanceContract`/`DelegateResourceContract`/`UnfreezeBalanceContract` submitters); no special privilege, SR/witness role, or off-chain compromise is required. The precondition (address reuse after deletion) is uncommon but is not merely theoretical — it is precisely the scenario the project's own `Create2Test`/`FreezeTest` suite was written to explore, indicating the authors were aware address reuse at a receiver can occur and is reachable purely through normal contract deployment/freeze/unfreeze transactions.

### Recommendation
1. In `UnfreezeBalanceActuator#validate` and `#execute` (and the mirrored `UnfreezeBalanceProcessor`), do not blindly trust the `AccountCapsule` currently found at `receiverAddress`. Bind continuity between the `DelegatedResourceCapsule` and the receiver account, e.g. by recording a creation-epoch/account-generation marker on `AccountCapsule` at creation/deletion time and rejecting unfreeze operations whose `DelegatedResourceCapsule` predates the receiver's current generation.
2. Alternatively, proactively clear or migrate all `DelegatedResourceCapsule` entries that reference an address as `to` whenever that address's `AccountCapsule` is deleted (contract suicide) or re-typed, mirroring the existing `existingAccount.clearDelegatedResource()` call in `Program.createContractImpl`, but also purging the cross-referenced `DelegatedResourceStore`/`DelegatedResourceAccountIndexStore` entries rather than only the account's own aggregate fields.
3. Add a regression test that deletes/recreates a receiver with its own independent delegation (as in `testUnfreezeDelegatedBalanceForBandwidthWithRecreatedReceiver`), then issues a stale unfreeze from the original delegator, and asserts the new receiver's `AcquiredDelegatedFrozenBalance` and `TotalNetWeight`/`TotalEnergyWeight` remain consistent with the still-active new delegation.

### Proof of Concept
1. `owner` delegates `frozenBalance` bandwidth to `receiver` (creating `DelegatedResourceCapsule(owner, receiver)` and setting `receiver.AcquiredDelegatedFrozenBalanceForBandwidth = frozenBalance`).
2. `receiver`'s account is deleted (e.g. via contract `SUICIDE` to that address, as in `FreezeTest.suicideToAccount`, or directly via `AccountStore.delete` as in the test).
3. A new, unrelated account is created at the same `receiver` address and independently acquires its own delegated resource, e.g. `receiver.AcquiredDelegatedFrozenBalanceForBandwidth = 10` from a different delegator (`newOwner`), with its own separate `DelegatedResourceCapsule(newOwner, receiver)` still outstanding.
4. `owner` (the original, stale delegator) submits `UnfreezeBalanceContract(ownerAddress=owner, receiverAddress=receiver, resource=BANDWIDTH)`. `validate()` succeeds because `DelegatedResourceCapsule(owner, receiver)` still exists and is expired.
5. `execute()` runs: since `receiver.AcquiredDelegatedFrozenBalanceForBandwidth (10) < unfreezeBalance (frozenBalance)`, the code sets `receiver.AcquiredDelegatedFrozenBalanceForBandwidth = 0`, destroying the unrelated, still-valid delegation belonging to `newOwner`, as verified directly by `UnfreezeBalanceActuatorTest.testUnfreezeDelegatedBalanceForBandwidthWithRecreatedReceiver` [7](#0-6) .
