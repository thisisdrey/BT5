## Title
Permanently unrecoverable user funds in `LostTips` storage with no redemption/withdrawal extrinsic - (File: bridges/snowbridge/pallets/system-v2/src/lib.rs)

## Summary
`pallet_system_frontend::add_tip` on AssetHub unconditionally swaps/burns a user's asset into Ether via `swap_fee_asset_and_burn` (`bridges/snowbridge/pallets/system-frontend/src/lib.rs:261-273, 372-404`) before the corresponding `add_tip` call on BridgeHub (`bridges/snowbridge/pallets/system-v2/src/lib.rs:253-281`) attempts to attribute that value to a relayer reward via `InboundQueue::add_tip`/`OutboundQueue::add_tip`. If that attribution fails (stale/consumed nonce, missing order), the burned value is recorded only in `LostTips::<T>` (lib.rs:140-142, 268-270), a `StorageMap` that is never read anywhere else in the codebase.

## Finding Description
The `LostTips` storage item's own doc comment states it exists to "support implementing a recovery method in the future" (lib.rs:136-139), confirming the recovery/redeem path is intentionally deferred and not present. Inspection of `snowbridge_pallet_system_v2`'s complete extrinsic set — `upgrade` (call_index 0), `set_operating_mode` (1), `register_token` (2), and `add_tip` (3) — shows no fifth extrinsic exists to read, zero, or pay out `LostTips`, and a repository-wide search for `withdraw`, `reclaim`, `redeem`, `recover`, or direct `LostTips::<T>::take`/`remove` usage returns no matches in this pallet or any caller. The exploit path is real and attacker-triggerable without privilege: an ordinary signed user calls `add_tip` on the frontend pallet (system-frontend/src/lib.rs:261-273), which burns/swaps the asset for Ether unconditionally via `swap_fee_asset_and_burn` (lines 372-404) *before* any validation that the target nonce/order is valid, then dispatches a Transact call to BridgeHub's `add_tip`. If the nonce was already consumed or the order not found, `InboundQueue::add_tip`/`OutboundQueue::add_tip` returns `Err`, and the amount is credited into `LostTips::<T>` instead of refunded (lib.rs:266-271). This is confirmed reproducible by the existing test `add_tip_inbound_fails_when_nonce_is_consumed` (system-v2/src/tests.rs:197-219) and the emulated integration test `tip_to_invalid_nonce_is_added_to_lost_tips` (cumulus/.../snowbridge_v2_outbound.rs:277-319), both of which assert value lands in `LostTips` with no subsequent payout path exercised or existing.

## Impact Explanation
This matches the "permanent user-fund or bridge-state lock" category in the impact gate: real value is destroyed on the local chain (burned for teleport) in exchange for a credit that can never be settled back to the user, since no extrinsic, governance call, or migration reads `LostTips` to compensate the account. The loss is monotonically increasing in aggregate across the bridge's lifetime and constitutes a genuine value-conservation violation — the burned asset is neither delivered as a reward nor refunded.

## Likelihood Explanation
High and unprivileged. Any signed AssetHub account can trigger this by calling the public `add_tip` extrinsic with a stale, already-processed, or invalid `message_id`/nonce — no relayer collusion, governance action, or compromised key is required. Ordinary timing races (tipping a message that finishes processing just before the tip lands) make this reachable even without malicious intent, as acknowledged by the pallet's own test suite covering exactly this failure mode.

## Recommendation
Either (a) validate nonce/order existence on BridgeHub before the AssetHub frontend burns the tip asset, with an atomic refund path if validation fails, or (b) implement the documented "recovery method": a permissioned extrinsic (restricted to the original `sender`, or an automatic XCM-based refund back to the originating account) that reads and zeroes `LostTips::<T>::get(&sender)` and settles the equivalent value back to the user, closing the write-only nature of this storage map.

## Proof of Concept
1. On AssetHub, a user calls `EthereumSystemFrontend::add_tip(origin=signed(Alice), message_id=Inbound(N)/Outbound(N), asset)` for a nonce `N` that is already fully processed or invalid.
2. `swap_fee_asset_and_burn` (system-frontend/src/lib.rs:372-404) burns/swaps Alice's asset for Ether and teleports it cross-chain regardless of nonce validity.
3. On BridgeHub, `EthereumSystemV2::add_tip` (system-v2/src/lib.rs:253-281) calls `InboundQueue::add_tip(N, amount)` / `OutboundQueue::add_tip(N, amount)`, which returns `Err` for the consumed/invalid nonce.
4. `LostTips::<T>::mutate(&sender, ...)` credits the amount into storage and emits `TipProcessed { success: false }`, exactly as exercised by `add_tip_inbound_fails_when_nonce_is_consumed` (system-v2/src/tests.rs:197-219) and `tip_to_invalid_nonce_is_added_to_lost_tips` (cumulus/parachains/integration-tests/.../snowbridge_v2_outbound.rs:277-319).

		fn swap_fee_asset_and_burn(
			origin: Location,
			fee_asset: Asset,
		) -> Result<u128, DispatchError> {
			let ether_location = T::EthereumLocation::get();
			let (fee_asset_location, fee_amount) = match fee_asset {
				Asset { id: AssetId(ref loc), fun: Fungible(amount) } => (loc, amount),
				_ => {
					tracing::debug!(target: LOG_TARGET, ?fee_asset, "error matching fee asset");
					return Err(Error::<T>::UnsupportedAsset.into());
				},
			};
			if fee_amount == 0 {
				return Ok(0);
			}

			let ether_gained = if *fee_asset_location != ether_location {
				Self::swap_and_burn(
					origin.clone(),
					fee_asset_location.clone(),
					ether_location,
					fee_amount,
				)
				.inspect_err(|&e| {
					tracing::debug!(target: LOG_TARGET, ?e, "error swapping asset");
				})?
			} else {
				burn_for_teleport::<T::AssetTransactor>(&origin, &fee_asset)
					.map_err(|_| Error::<T>::BurnError)?;
				fee_amount
			};
			Ok(ether_gained)
		}
