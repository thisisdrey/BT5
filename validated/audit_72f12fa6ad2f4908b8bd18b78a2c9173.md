## Analysis

The external report is about a **wrong-decimal/precision handling bug in a value-transfer calculation** (`vault.deposit` using an 18-decimal amount that should have been scaled), causing funds to be mis-credited. The closest reachable analog in java-tron is in the **TRX/TRC10 Bancor-relay Exchange subsystem** (`ExchangeTransactionContract`), which is explicitly in-scope ("exchange and market order handling").

The `ExchangeCapsule.transaction()` method selects between two calculation engines depending on the `allowHardenExchangeCalculation` dynamic property: [1](#0-0) 

- **Legacy (default) path** — `ExchangeProcessor`, which implements the Bancor relay formula entirely in IEEE-754 `double` arithmetic and truncates the result to `long` via a naked cast: [2](#0-1) 

- **Hardened path** — `SafeExchangeProcessor`, which performs the same math with `BigDecimal` at 18-digit scale: [3](#0-2) 

A test explicitly confirms the legacy path is the default, unprivileged-reachable behavior: [4](#0-3) 

### Title
Floating-point precision loss (double-based Bancor math) in default `ExchangeProcessor` allows value extraction from TRX/TRC10 Exchange pools - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
`ExchangeCapsule.transaction()`, invoked by any account via a signed `ExchangeTransactionContract` (`ExchangeTransactionActuator`), computes swap outputs using `ExchangeProcessor` unless the committee has activated `allowHardenExchangeCalculation`. `ExchangeProcessor` performs the entire Bancor relay-token calculation in 64-bit `double` precision and truncates the intermediate/final results with a bare `(long)` cast, rather than using exact fixed-point/BigDecimal arithmetic. This is directly analogous to the reported bug class: incorrect handling of value precision/scale in a fund-moving calculation causes systematic mis-crediting of amounts.

### Finding Description
`exchangeToSupply`/`exchangeFromSupply` compute:
```
double issuedSupply = -supply * (1.0 - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, useStrictMath));
long out = (long) issuedSupply;
``` [5](#0-4) 

and
```
double exchangeBalance = balance * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, useStrictMath) - 1.0);
return (long) exchangeBalance;
``` [6](#0-5) 

`double` has only ~15-17 significant decimal digits, but pool balances can range up to `Long.MAX_VALUE` (~9.2×10^18) and the fixed internal `supply` constant is 10^18. The result is that (a) the ratio `quant/newBalance` loses precision for large balances, and (b) the truncating `(long)` cast (round-toward-zero, not consistent floor/ceiling) accumulates rounding error differently depending on how a trade is split. This is functionally the same bug class as the report: an amount computed at the wrong precision/scale is credited into account balances (`accountCapsule.addAssetAmountV2` / `setBalance`) in `ExchangeTransactionActuator.execute()`: [7](#0-6) 

The codebase itself demonstrates awareness of the precision defect: a parallel `SafeExchangeProcessor` was added using `BigDecimal` at scale 18 with `RoundingMode.HALF_UP`/`DOWN`, but it is only used when the `allowHardenExchangeCalculation` committee proposal flag is enabled — which is **off by default**, as confirmed by the test asserting the legacy (double) processor is used when the flag is 0: [8](#0-7) 

`AbstractExchangeActuator.allowHarden()` simply reads this same dynamic property to decide whether add/subtract overflow checks are strict, confirming the two code paths (legacy double vs hardened BigDecimal) coexist and the legacy one is default: [9](#0-8) 

### Impact Explanation
Any anonymous account can submit `ExchangeTransactionContract` transactions to swap TRX/TRC10 tokens against an Exchange pool. Because the default engine performs Bancor pricing in floating point instead of exact fixed-point math, a sequence of small trades against the same pool can be crafted so that cumulative truncation/rounding systematically favors the trader over the pool (or vice versa), extracting or destroying value in the pool balances stored on-chain (`firstTokenBalance`/`secondTokenBalance`), and correspondingly crediting/debiting account TRX or TRC10 balances incorrectly. This constitutes theft/unbacked-balance risk within the Exchange pools, matching the "unbacked balance"/"theft of funds" acceptance criteria.

### Likelihood Explanation
High likelihood of reachability: no special privilege is required — a single signed `ExchangeTransactionContract` from any account triggers `ExchangeCapsule.transaction()` via `ExchangeTransactionActuator.execute()`, which defaults to `ExchangeProcessor` unless `allowHardenExchangeCalculation` has been separately enabled by the committee. Repeated small trades are trivially scriptable by any order-placing account.

### Recommendation
Make `SafeExchangeProcessor` (BigDecimal-based, fixed-scale) the unconditional/default implementation for `ExchangeCapsule.transaction()`, removing the double-precision `ExchangeProcessor` code path entirely (or force `allowHardenExchangeCalculation` to be permanently enabled network-wide), so that Exchange swap accounting is never computed with floating-point arithmetic.

### Proof of Concept
1. Create/observe an existing Exchange pool (`ExchangeCreateContract`) with large token balances (near the scale where `double` precision loss becomes significant relative to the smallest tradable unit).
2. Submit many small `ExchangeTransactionContract` trades (quantities near the rounding boundary of `Maths.pow`/`(long)` truncation) instead of one large trade, exploiting `AbstractExchangeActuator.allowHarden()`’s default-off `SafeExchangeProcessor` gate documented in `framework/src/test/java/org/tron/core/db/ManagerTest.java` (`isExchangeTransactionBypassedWhenHardenedEnabled`), to accumulate a materially different — and favorable to the attacker — total received amount than a single trade of the same aggregate size would yield under `SafeExchangeProcessor`.
3. Repeat across blocks to drain economic value from the pool over time, all via ordinary unprivileged transactions.

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
