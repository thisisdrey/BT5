### Title
Contract owner can arbitrarily and instantly change `consumeUserResourcePercent` via `UpdateSettingContract`, shifting energy fees onto callers without limit or delay - (File: `actuator/src/main/java/org/tron/core/actuator/UpdateSettingContractActuator.java`)

### Summary
The `UpdateSettingContractActuator` lets the origin owner of any deployed smart contract change the `consumeUserResourcePercent` value at any time, for any already-deployed contract, with no timelock and no protection against front-running pending caller transactions. This mirrors the BribeVault `setFee` finding: a privileged-but-reachable-by-normal-user actor (the contract's origin address, which any asset issuer/contract deployer can be) can retroactively and instantly alter a fee-like parameter that determines how transaction costs are split between itself and unrelated third-party callers.

### Finding Description
`consumeUserResourcePercent` determines the split of TVM energy cost between the contract's origin account and the calling account. The actuator only bounds the value to `[0, 100]` and enforces that the caller is the contract's `originAddress`: [1](#0-0) 

There is no cooldown, no minimum time between changes, and no restriction preventing the owner from changing this value in the very same block as (or immediately before) a victim's `TriggerSmartContract` transaction. The value is read live at execution time to compute how much energy the origin pays versus the caller: [2](#0-1) 

And the actual bill split at settlement time is likewise driven directly by the current `consumeUserResourcePercent` stored on the contract, with no snapshot taken from the time the caller's transaction was signed/broadcast: [3](#0-2) 

This is analogous to the reported BribeVault issue: a fee-controlling party can change the fee (a) for a "deposit" (contract interaction) already made/pending, and (b) can front-run the counterparty's transaction, since the setting takes effect for the next block regardless of when the victim's call was broadcast.

### Impact Explanation
A contract owner can advertise a contract with `consumeUserResourcePercent = 0` (owner sponsors all energy) to attract callers, then submit an `UpdateSettingContract` transaction raising it to `100` and have it included in the same or an earlier block than pending caller transactions. Callers who signed transactions expecting the owner to cover energy costs will instead have their own account (via frozen energy or burned TRX) pay the full cost, resulting in unexpected fund loss/griefing for the unprivileged transaction broadcaster interacting with the contract, with no on-chain notice or delay to react.

### Likelihood Explanation
This requires no special network privilege — only a normal account that is a contract's `originAddress` (any asset/contract deployer) — and the state change takes effect immediately at the next block via a single signed `UpdateSettingContract` transaction, making front-running trivial for the contract owner against any caller of their own contract.

### Recommendation
Add a minimum time delay (timelock) between successive `UpdateSettingContract` calls for the same contract (e.g., enforce a cooldown via a stored "last updated" block/timestamp in `ContractCapsule`), and/or bound the maximum change per update, and/or snapshot `consumeUserResourcePercent` at the time a caller's transaction enters the mempool/executes within the same block window so front-running cannot retroactively alter the fee split for transactions already broadcast.

### Proof of Concept
1. Deploy a contract with `consumeUserResourcePercent = 0` and enough `originEnergyLimit`/frozen energy, so callers reasonably expect the owner covers all energy costs.
2. Wait for a victim to sign and broadcast a `TriggerSmartContract` transaction calling this contract.
3. As the contract owner, broadcast an `UpdateSettingContract` transaction (via `UpdateSettingContractActuator`, reachable through `UpdateSettingServlet`/gRPC) setting `consumeUserResourcePercent = 100`, timed to land in the same or an earlier block.
4. When the victim's call executes, `VMActuator.getTotalEnergyLimitWithFixRatio` and `TransactionTrace.pay` read the now-updated `consumeUserResourcePercent`, causing the victim to be billed the full energy cost rather than the value assumed when they signed their transaction. [4](#0-3)

  public boolean execute(Object object) throws ContractExeException {
    TransactionResultCapsule ret = (TransactionResultCapsule) object;
    if (Objects.isNull(ret)) {
      throw new RuntimeException(ActuatorConstant.TX_RESULT_NULL);
    }

    long fee = calcFee();
    ContractStore contractStore = chainBaseManager.getContractStore();
    try {
      UpdateSettingContract usContract = any.unpack(UpdateSettingContract.class);
      long newPercent = usContract.getConsumeUserResourcePercent();
      byte[] contractAddress = usContract.getContractAddress().toByteArray();
      ContractCapsule deployedContract = contractStore.get(contractAddress);

      contractStore.put(contractAddress, new ContractCapsule(
          deployedContract.getInstance().toBuilder().setConsumeUserResourcePercent(newPercent)
              .build()));
      RepositoryImpl.removeLruCache(contractAddress);

      ret.setStatus(fee, code.SUCESS);
    } catch (InvalidProtocolBufferException e) {
      logger.debug(e.getMessage(), e);
      ret.setStatus(fee, code.FAILED);
      throw new ContractExeException(e.getMessage());
    }
    return true;
  }
