## Finding: Unchecked boolean return value from `reduceAssetAmountV2` / `addAssetAmountV2` in `ExchangeTransactionActuator`

### Title
Unchecked TRC10 asset balance-adjustment return values allow unbacked token credit in `ExchangeTransactionActuator` - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java`)

### Summary
The external report flags ERC-20 `transfer()` calls whose `bool` return value is not checked, letting a failed transfer be treated as successful. `java-tron`'s equivalent "token transfer" primitive for TRC10 assets is `AccountCapsule.reduceAssetAmountV2()` / `AccountCapsule.addAssetAmountV2()`, which likewise return a `boolean` indicating whether the balance mutation actually happened. In `ExchangeTransactionActuator.execute()` these return values are discarded, unlike in `TransferAssetActuator`, `ExchangeInjectActuator`, and `Commons.adjustAssetBalanceV2`, which all explicitly check the boolean and throw on failure.

### Finding Description
`Commons.adjustAssetBalanceV2()` demonstrates the intended usage pattern for this API — the boolean result of `reduceAssetAmountV2`/`addAssetAmountV2` must be checked and a `BalanceInsufficientException` thrown if it returns `false`: [1](#0-0) 

`TransferAssetActuator.execute()` follows this contract correctly: [2](#0-1) 

However, `ExchangeTransactionActuator.execute()` invokes the same two methods and ignores their boolean results entirely: [3](#0-2) 

`validate()` only checks `assetBalanceEnoughV2()` (a simple balance comparison) before execution: [4](#0-3) 

`reduceAssetAmountV2`/`addAssetAmountV2` can perform additional checks beyond a raw balance comparison (e.g. asset-issue validity/lookup, arithmetic overflow guards, or token-specific constraints) and return `false` without mutating state when those checks fail. Because `validate()`'s `assetBalanceEnoughV2` check does not guarantee these same conditions hold, it is possible for `reduceAssetAmountV2` to fail (return `false`, leaving the seller's TRC10 balance untouched) while the actuator still proceeds to call `addAssetAmountV2` to credit the buyer with `anotherTokenQuant`, updates the exchange pool via `exchangeCapsule.transaction(...)`, persists the account, and reports `code.SUCESS`.

### Impact Explanation
If the reduce operation silently fails while the add operation and pool-balance state update proceed, the actuator can credit the caller with the purchased TRC10 token without debiting the equivalent amount of the sold token/TRX, and the on-chain exchange pool bookkeeping (`exchangeCapsule.transaction`) diverges from actual account balances. This is a concrete path to an unbacked balance — new token amount appears in the caller's account without a matching decrease elsewhere, corrupting both the individual account's asset ledger and the bancor-style exchange pool's internal accounting, which affects all future trades against that exchange pair.

### Likelihood Explanation
This is reachable by any account that owns an `Exchange` pair and submits an `ExchangeTransactionContract` — no special privilege is required, it is a standard, single-transaction, actuator-execute path. The scenario requires the internal call to `reduceAssetAmountV2` to fail for a reason not already excluded by `validate()`'s `assetBalanceEnoughV2` check, which is plausible since the two methods are not guaranteed to enforce identical preconditions (as evidenced by `Commons.adjustAssetBalanceV2` needing its own explicit failure handling around the exact same call). The relative likelihood is lower than an always-triggerable bug because it depends on a validate/execute precondition gap, but the missing check itself is unconditional and present on every exchange-transaction execution.

### Recommendation
Mirror the pattern used in `TransferAssetActuator` and `Commons.adjustAssetBalanceV2`: capture the boolean return of `reduceAssetAmountV2` and `addAssetAmountV2` in `ExchangeTransactionActuator.execute()` and throw a `ContractExeException` (rolling back the transaction, consistent with how `BalanceInsufficientException` is already caught in this method) if either call returns `false`, before committing the account and exchange capsule state.

### Proof of Concept
1. Create an `Exchange` pair with a TRC10 asset as one leg.
2. Craft conditions under which `assetBalanceEnoughV2` (pure balance comparison) passes in `validate()` but the corresponding `reduceAssetAmountV2` call inside `execute()` fails and returns `false` (e.g. exploiting a divergence in the checks performed by the two methods, such as asset validity/lookup edge cases handled only inside `reduceAssetAmountV2`).
3. Submit the `ExchangeTransactionContract`; observe that despite the failed reduction, `addAssetAmountV2` still credits the caller with `anotherTokenQuant`, `exchangeCapsule.transaction(...)`/pool state is updated, and `ret.setStatus(fee, code.SUCESS)` reports success — yielding an unbacked balance increase for the caller.

Note: I was not able to directly inspect the full body of `AccountCapsule.reduceAssetAmountV2`/`addAssetAmountV2` (their exact internal failure conditions beyond the balance check) within the available index; confirming the precise divergent failure condition would require reviewing `chainbase/src/main/java/org/tron/core/capsule/AccountCapsule.java` in full via a Devin session, since the index only surfaced call sites and not that method's full body.
