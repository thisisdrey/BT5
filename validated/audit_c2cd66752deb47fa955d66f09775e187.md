### Title
Unauthenticated `RecvError` packet with spoofed source + guessed `RemoteIndex` can force tunnel teardown - (File: outside.go)

### Summary
`Interface.handleRecvError` in `outside.go` tears down an established tunnel (`f.closeTunnel(hostinfo)` and `f.handshakeManager.DeleteHostInfo(hostinfo)`) based solely on an unauthenticated `header.RecvError` packet whose `RemoteIndex` matches an existing session and whose UDP source address matches `hostinfo.GetRemote()`. Neither of these values is cryptographically verified, so an attacker who can spoof the victim's peer's UDP source address and who knows/observes the victim's `RemoteIndex` can trigger session teardown without ever completing a handshake.

### Finding Description
In `readOutsidePackets`, `header.RecvError` packets are dispatched before any AEAD/handshake verification: [1](#0-0) 

`handleRecvError` then:
1. Rate/allow-checks via `f.acceptRecvErrorConfig.ShouldRecvError(addr)`.
2. Looks up the local `HostInfo` purely by `h.RemoteIndex` via `f.hostMap.QueryReverseIndex(h.RemoteIndex)` — a value carried in cleartext in the packet header, and also observable in plaintext in any packet header exchanged with that host, since Nebula header fields (`LocalIndex`/`RemoteIndex`) are never encrypted.
3. Performs only a source-address equality check: `hr := hostinfo.GetRemote(); if hr.IsValid() && hr != addr { ... return }`.
4. If the address matches, calls `f.closeTunnel(hostinfo)` and `f.handshakeManager.DeleteHostInfo(hostinfo)` with no cryptographic proof that the sender possesses the tunnel's key material or is the actual remote peer. [2](#0-1) 

`closeTunnel` unconditionally removes the hostmap entry: [3](#0-2) 

Because `RemoteIndex` is transmitted in cleartext in every packet's header (not just handshake packets), an attacker positioned to passively observe even a single packet between the victim and its peer (e.g., on a shared network segment, public Wi-Fi, or via an intermediate network operator) can learn the exact `RemoteIndex` without needing to guess a 32-bit random value. The only remaining requirement is spoofing the UDP source `IP:port` to match the current legitimate remote endpoint of that tunnel, which is a standard IP-spoofing capability rather than a Nebula-specific bypass. The developers were clearly aware address equality alone is weak evidence, as shown by the log message `"Someone spoofing recv_errors?"`, but the code proceeds to act on it regardless of that suspicion (it only logs when it *rejects*, and takes no extra caution when it accepts).

The comparable per-packet safety check for authenticated packets (`handleHostRoaming`) is bypassed entirely here because `RecvError` handling never reaches the AEAD decryption / roaming code path — it acts before any authentication step.

### Impact Explanation
This causes state poisoning/teardown of a legitimate, already-authenticated tunnel using a completely unauthenticated packet: `HostInfo` is deleted from both the main hostmap and the handshake-manager's pending map, forcing the two legitimate peers into a new handshake. During the resulting re-handshake window there is a firewall/connection-state gap and possible traffic disruption; repeated injection can be used as a persistent low-effort DoS/tunnel-flapping primitive against a specific victim tunnel. This does not break encryption, authentication of data-plane packets, or certificate verification — it is confined to unauthenticated remote hostmap/session-state teardown, matching Nebula's "remote state poisoning" impact category rather than a full auth or crypto bypass.

### Likelihood Explanation
Feasibility depends on two preconditions: (1) the attacker must observe a genuine packet's header to learn the target `RemoteIndex` (trivial cleartext field, achievable by any on-path observer or by anyone able to see even a single packet, e.g., via a shared LAN, compromised switch/AP, or upstream link) — no header guessing/brute force of the full 32-bit space is actually required; (2) the attacker must be able to spoof the victim's peer UDP source `IP:port`, which requires either being on-path or being on a network without egress/anti-spoofing filtering. This is a standard off-path IP-spoofing precondition, not something specific to Nebula's design, and is repeatable at will since nothing rate-limits per-`RemoteIndex` beyond the (address-based) `acceptRecvErrorConfig.ShouldRecvError` check.

### Recommendation
Do not let unauthenticated `RecvError` packets alone tear down a hostmap entry. At minimum:
- Require some proof of remote authenticity before honoring `RecvError` (e.g., only accept it as a hint to send a probe/challenge over the existing encrypted tunnel rather than immediately deleting state), or
- Bind `RecvError` handling to a value that isn't visible in cleartext and isn't just the routable source address (e.g., require it to be accompanied by a MAC over recent traffic, or ignore `RecvError` unless a subsequent number of real data packets also fail, adding a confirmation step through the authenticated channel), or
- At minimum, rate-limit/backoff so a single spoofed packet cannot immediately force teardown, and treat address-equality-based "someone spoofing recv_errors?" detection as a reason to distrust rather than to still act on the received `RecvError`.

### Proof of Concept
Unit/integration test outline (extending existing tests around `handleRecvError` in `outside.go`/`interface.go`):
1. Establish two `Interface` test instances (A and B) and complete a real handshake so `A`'s hostmap has a `HostInfo` for B with `hostinfo.remote == B_addr` and a known `RemoteIndex` (`h.RemoteIndex`) that would be attached to packets exchanged with B (assert this value is visible in plaintext header of a captured data packet).
2. Do **not** perform any additional handshake or send any key material as the "attacker".
3. Craft a raw `header.RecvError` packet with `RemoteIndex` set to the value learned from step 1, and call `A.handleRecvError(B_addr, h)` directly (or feed it through `readOutsidePackets`) with the source `netip.AddrPort` spoofed to equal `B_addr`.
4. Assert that, prior to the fix, `A.hostMap.QueryIndex`/`QueryReverseIndex` for that `HostInfo` returns `nil` afterward (i.e., `closeTunnel`/`DeleteHostInfo` executed) even though no AEAD-authenticated packet or handshake message was ever presented by the "attacker".
5. After remediation, assert that the same spoofed, unauthenticated `RecvError` packet does **not** remove the hostmap entry unless accompanied by additional authenticated confirmation.

```go
func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
```
