### Title
Bzlmod registries can smuggle arbitrary `git(1)` remote-helper/argument-injection payloads through `git_repository`-typed `source.json`, causing command execution during dependency resolution - ([File: tools/build_defs/repo/git_worker.bzl])

### Summary
When a Bazel module's `source.json` declares `"type": "git_repository"`, the registry-controlled `remote`, `commit`, `tag`, and `branch` fields are forwarded verbatim into the `git_repository` repo rule and from there into `tools/build_defs/repo/git_worker.bzl`, which shells out to the system `git` binary. Unlike the `archive` source type (which is bound by a mandatory `integrity` checksum), the `git_repository` source type has **no integrity/checksum field at all** to bind trust to the registry-supplied values. [1](#0-0) [2](#0-1) 

`git_repo()` builds the git commands from these raw values, and several of the resulting invocations pass the attacker-controlled string directly to `git` without any transport/protocol restriction (no `GIT_ALLOW_PROTOCOL` is set) and without an `--` argument-terminator in some cases: [3](#0-2) [4](#0-3) 

### Finding Description
A `--registry` (any registry configured for the build, including a custom or compromised third-party registry, or a compromised/hostile mirror of an otherwise-trusted registry) can publish a module version whose `source.json` sets `"type": "git_repository"` together with attacker-chosen `remote`, `commit`, `tag`, or `branch` values. Bazel's `git.bzl`/`git_worker.bzl` forwards these fields unmodified into:

- `add_origin(ctx, git_repo, remote)` → `git remote add origin <remote>` [5](#0-4) 
- `fetch(ctx, git_repo)` → `git fetch origin ... -- <fetch_ref>` [6](#0-5) 
- `reset(ctx, git_repo)` → `git reset --hard <reset_ref>` [7](#0-6) 

`_execute()` invokes the real `git` binary with the caller's full environment plus a small denylist of `GIT_*` variables; it does **not** set `GIT_ALLOW_PROTOCOL` or otherwise restrict which git transports are usable: [4](#0-3) 

Because `remote` is passed straight into `git remote add origin <remote>` and subsequently `git fetch origin`, an attacker-controlled `remote` value using git's built-in `ext::` (or `fd::`) remote-helper transport (e.g. `ext::sh -c "touch$IFS/tmp/pwned"`) causes `git` itself to execute an attacker-chosen shell command during the fetch — this is exactly the class of "git ref/URL misinterpreted, leading to command execution in the context of the user executing the build" described in CVE-2019-13139, just triggered through Bazel's own git-based repository fetcher instead of `docker build`'s remote-git-URL handling.

Additionally, when `commit` is used (as opposed to `tag`/`branch`, whose values are always prefixed with `"tags/"` or `"origin/"` before being used, incidentally preventing a leading `-`), the raw attacker-controlled `commit` string is used unprefixed as `git_repo.reset_ref` and passed to `git reset --hard <reset_ref>` with no `--` terminator, so a `commit` value starting with `-` is parsed as a flag rather than a treeish, matching the literal "ref misinterpreted as a flag" bug class named in the CVE. [8](#0-7) [7](#0-6) 

The `git_repository` repo rule itself performs no validation on `remote`'s scheme (it is a plain `attr.string`) and no validation preventing a leading `-` in `commit`/`tag`/`branch`: [9](#0-8) 

### Impact Explanation
A build that resolves a `bazel_dep` backed by a `git_repository`-typed registry source will invoke `git` with attacker-supplied values during `MODULE.bazel` resolution (e.g. on `bazel build`, `bazel sync`, or CI dependency fetch), potentially before any build actions run and with no digest/integrity gate to stop it (unlike `http_archive`, which has a mandatory `integrity` field). This can lead to arbitrary command execution in the context of the user/CI running Bazel, i.e. full compromise of the build host — the same severity class as the original Docker CVE (CVSS 8.4, local/user-context command execution via a manipulated build source).

### Likelihood Explanation
Exploitability requires the victim to configure or be defaulted to a hostile/compromised registry (via `--registry`, a compromised mirror of a configured registry, or a supply-chain-compromised BCR-like registry) that serves a `git_repository`-typed `source.json` for a module version the victim depends on (directly or transitively). This is a plausible, low-privilege "malicious dependency/registry" scenario explicitly in scope of the analog rules ("registry module version" as an attacker vector), and does not require MITM, a malicious peer, or local machine access — only that the victim's build resolves a module whose source is controlled by the attacker's registry entry.

### Recommendation
- Add a `GIT_ALLOW_PROTOCOL` (or equivalent) allowlist to `_execute()` in `git_worker.bzl` restricting git transports to safe schemes (`https`, `git`, `ssh`, `file` if locally intended) and explicitly disabling `ext`/`fd`.
- Validate the `remote` attribute in `git.bzl`/`git_worker.bzl` to reject `ext::`/`fd::` and other command-execution transports.
- Reject `commit`/`tag`/`branch` values beginning with `-` (or always prefix/terminate with `--` before passing to `git` subcommands) to eliminate argument-injection into `git reset`, `git remote add`, etc.
- Require (or at minimum support) an integrity/pinning mechanism for `git_repository`-typed registry sources analogous to `integrity` for `archive` sources, so a compromised registry/mirror cannot silently swap in a hostile `remote`/`commit` for a previously-locked module version.

### Proof of Concept
1. Stand up a registry (or compromise a mirror of one already configured via `--registry`) serving a module version with `source.json`:
```json
{
  "type": "git_repository",
  "remote": "ext::sh -c \"touch $TMPDIR/pwned\""
}
```
as shown to be forwarded verbatim to `git_repository` by the registry format and test helper `createGitRepoModule`: [2](#0-1) 
2. Have the victim's `MODULE.bazel` declare `bazel_dep(name = "<module>", version = "<version>")` for that module.
3. Run `bazel build //...` (or any command triggering module resolution). Bazel synthesizes a `git_repository(remote = "ext::sh -c \"touch $TMPDIR/pwned\"", ...)` invocation, which calls `add_origin` → `git remote add origin ext::sh -c ...` and then `fetch` → `git fetch origin`, causing `git` to execute the attacker's shell command via its `ext::` remote helper. [10](#0-9) 
4. Verify `pwned` file exists after the build/fetch step, confirming command execution in the context of the user running `bazel`.

A JUnit/shell-integration reproduction (e.g. under `src/test/py/bazel/bzlmod/`, extending the existing `createGitRepoModule` test harness) can drive this end-to-end by pointing `remote` at an `ext::` payload instead of a `file://` path and asserting a side-effect file is created after `bazel build` resolves the dependency.

**Note on uncertainty:** I was not able to locate the Java-side `RegistryFunction`/`IndexRegistry`/`ArchiveRepoSpecBuilder`-equivalent code in this index that converts `source.json`'s `git_repository` type into the final `git_repository` rule invocation (searches for `IndexRegistry.java` and related class names returned no matches, likely due to index coverage limits), so I could not directly confirm from Java source whether any additional server-side validation exists there beyond what the documentation and Starlark-level test harness (`createGitRepoModule`) describe. The documentation and test fixtures consistently show `remote`/`commit`/`tag`/etc. being forwarded without an integrity check, which is the basis for this finding, but a Devin session with full repository access would be needed to double check the Java-side registry-to-repo-rule translation for any bypassed sanitation.

def _update(ctx, git_repo):
    ctx.delete(git_repo.directory)

    init(ctx, git_repo)
    add_origin(ctx, git_repo, ctx.attr.remote)
    fetch(ctx, git_repo)
    reset(ctx, git_repo)
    clean(ctx, git_repo)

    if git_repo.recursive_init_submodules:
        ctx.report_progress("Updating submodules recursively")
        update_submodules(ctx, git_repo, recursive = True)
    elif git_repo.init_submodules:
        ctx.report_progress("Updating submodules")
        update_submodules(ctx, git_repo)

def init(ctx, git_repo):
    cl = ["git", "init", str(git_repo.directory)]
    st = ctx.execute(cl, environment = ctx.os.environ | _GIT_LOCAL_ENV_VARS)
    if st.return_code != 0:
        _error(ctx.name, cl, st.stderr)

def add_origin(ctx, git_repo, remote):
    _git(ctx, git_repo, "remote", "add", "origin", remote)

def fetch(ctx, git_repo):
    args = ["fetch", "origin"]

    sparse_checkout_patterns_or_file = \
        getattr(ctx.attr, "sparse_checkout_patterns", None) or \
        getattr(ctx.attr, "sparse_checkout_file", None)
    if sparse_checkout_patterns_or_file:
        if _git_sparse_checkout_config(ctx, git_repo):
            # Use filter to disable downloading file contents until we set the `sparse-checkout` patterns.
            args.append("--filter=blob:none")
        else:
            print("WARNING: Sparse checkout is not supported. Doing a full checkout.")
            sparse_checkout_patterns_or_file = None

    args.extend(["--", git_repo.fetch_ref])
    st = _git_maybe_shallow(ctx, git_repo, *args)

    if sparse_checkout_patterns_or_file:
        _git_sparse_checkout(ctx, git_repo, sparse_checkout_patterns_or_file)

    if st.return_code == 0:
        return
    if ctx.attr.commit:
        # Perhaps uploadpack.allowReachableSHA1InWant or similar is not enabled on the server;
        # fall back to fetching all branches, tags, and history.
        # The semantics of --tags flag of git-fetch have changed in Git 1.9, from 1.9 it means
        # "everything that is already specified and all tags"; before 1.9, it used to mean
        # "ignore what is specified and fetch all tags".
        # The arguments below work correctly for both before 1.9 and after 1.9,
        # as we directly specify the list of references to fetch.
        _report_progress(ctx, git_repo, shallow_failed = True)
        _git(
            ctx,
            git_repo,
            "fetch",
            "origin",
            "--",
            "refs/heads/*:refs/remotes/origin/*",
            "refs/tags/*:refs/tags/*",
        )
    else:
        _error(ctx.name, ["git"] + args, st.stderr)

def reset(ctx, git_repo):
    _git(ctx, git_repo, "reset", "--hard", git_repo.reset_ref)
