### Title
Single-step, unchecked replacement of an account's Owner/Active/Witness permission keys can permanently brick the account — (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
`AccountPermissionUpdateContract` lets any account holder replace their Owner permission (and Active/Witness permissions) in a single atomic step, analogous to the reported `updateConfigMaster` pattern (single-step critical role change, no zero-address / unreachable-address protection). `checkPermission()` only validates address format via `DecodeUtil.addressValid`, which merely checks length and network-prefix byte, never that the address is non-zero or otherwise controllable.

### Finding Description
`AccountPermissionUpdateActuator.validate()` calls `checkPermission(owner)` for the new Owner permission [1](#0-0) . Inside `checkPermission`, the only per-key validation is: [2](#0-1) 
`DecodeUtil.addressValid` itself only checks the byte length and the chain's address prefix byte, with no rejection of the zero address or any other address nobody holds keys for: [3](#0-2) 
`execute()` then applies the change unconditionally in one step via `AccountCapsule.updatePermissions`, replacing the Owner permission entirely with no staging/confirmation mechanism: [4](#0-3)  and [5](#0-4) . There is no "propose then accept" flow (unlike e.g. `Ownable2Step`) — the new Owner keys take effect immediately, and if the submitted keys are the zero address, the chain's designated black-hole address, or simply an address for which the sender does not actually control a private key, the account's Owner (and, correspondingly, all Active permissions if similarly misconfigured) becomes permanently unusable. Indeed, java-tron's own `Manager.resetBlackholeAccountPermission()` deliberately sets the black-hole account's owner permission to the all-zero address specifically to disable it [6](#0-5) , confirming that an all-zero-keyed Owner permission is recognized internally as "unusable/locked," yet nothing in the actuator prevents a normal user from inadvertently (or via a crafted wallet/dApp) creating this exact state for their own account.

### Impact Explanation
Once an account's Owner permission (and/or all Active permissions) is set to an address with no accessible private key, the account can no longer authorize any further `AccountPermissionUpdateContract`, transfers requiring owner-permission signatures, or other privileged operations gated by that permission — the account's TRX/TRC10/TRC20 balances become permanently frozen since no further signature can satisfy the (still valid-format) key. This matches "permanent freezing of funds," reachable purely from a single unprivileged, self-signed transaction.

### Likelihood Explanation
Likelihood is driven by user/wallet error or malicious front-end/dApp: because there is no address(0) check and no staged confirmation, a single malformed or maliciously crafted `AccountPermissionUpdateContract` (e.g., via a compromised or buggy wallet integration, or a phishing dApp instructing the user to sign) can silently transfer control to an unreachable address with irreversible effect on the very next block, with no window to detect and cancel the change.

### Recommendation
Add explicit checks in `AccountPermissionUpdateActuator.checkPermission`/`validate` rejecting the all-zero address and the black-hole address as permission keys, and consider introducing a two-step confirmation process for changes to the Owner permission specifically (e.g., requiring a follow-up transaction signed by the new owner key(s) to "accept" the permission before it takes effect), mirroring `Ownable2Step`-style patterns.

### Proof of Concept
1. Attacker-controlled or buggy wallet builds an `AccountPermissionUpdateContract` for victim's account with `owner.keys = [{address: 0x41000000000000000000000000000000000000 (chain-prefix + 20 zero bytes), weight: 1}]`, `threshold = 1`.
2. Victim signs and broadcasts the transaction with their currently valid (soon-to-be-replaced) owner/active key.
3. `AccountPermissionUpdateActuator.validate()` passes: `DecodeUtil.addressValid` accepts the zero-filled 21-byte address because it only checks length/prefix [3](#0-2) .
4. `execute()` applies `account.updatePermissions(...)`, overwriting the account's Owner permission with the unreachable key [4](#0-3) .
5. The victim's account can no longer produce a valid owner-permission signature; any subsequent operation requiring owner permission is permanently blocked, freezing the account's assets.

  public static boolean addressValid(byte[] address) {
    if (ArrayUtils.isEmpty(address)) {
      logger.warn("Warning: Address is empty !!");
      return false;
    }
    if (address.length != ADDRESS_SIZE / 2) {
      logger.warn(
          "Warning: Address length need " + ADDRESS_SIZE + " but " + address.length
              + " !!");
      return false;
    }

    if (address[0] != addressPreFixByte) {
      logger.warn("Warning: Address need prefix with " + addressPreFixByte + " but "
          + address[0] + " !!");
      return false;
    }
    return true;
  }

  public void updatePermissions(Permission owner, Permission witness, List<Permission> actives) {
    Builder builder = this.account.toBuilder();

    owner = owner.toBuilder().setId(0).build();
    builder.setOwnerPermission(owner);
    if (witness != null && builder.getIsWitness()) {
      witness = witness.toBuilder().setId(1).build();
      builder.setWitnessPermission(witness);
    }

    builder.clearActivePermission();
    if (actives != null) {
      for (int i = 0; i < actives.size(); i++) {
        Permission permission = actives.get(i).toBuilder().setId(i + 2).build();
        builder.addActivePermission(permission);
      }
    }

    this.account = builder.build();
  }
