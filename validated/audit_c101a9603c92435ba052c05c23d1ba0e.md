### Title
Out-of-bounds read from unvalidated ZIP central-directory extra-field lengths in `ijar` - ([File: third_party/ijar/zip.cc])

### Summary
`InputZipFile::ProcessCentralDirEntry` in `third_party/ijar/zip.cc` parses the central directory of a ZIP/JAR file supplied to `ijar` (used by Bazel to build interface jars from `java_library`/`java_import` dependencies). While walking the per-entry "extra fields" sub-records, the code trusts the attacker-controlled `data_size` field to advance a raw pointer without checking it against the bounds of the extra-field block or the mapped file, mirroring the class of bug in CVE-2020-11098 (an out-of-bound read caused by an unchecked, attacker-influenced index/size value used to access a cache/record structure).

### Finding Description
`ProcessCentralDirEntry` reads the central directory header fields, including `file_name_length`, `extra_field_length`, and `file_comment_length`, directly from the mmap'd input file with no cross-validation against the actual remaining size of the central directory or the file itself [1](#0-0) . It then iterates over the extra-field records:

```
const u1 *extra_p = p;
p += extra_field_length;
while (extra_p != p) {
  const u2 header_id = get_u2le(extra_p);
  const u2 data_size = get_u2le(extra_p);
  const u1 *extra = extra_p;
  extra_p += data_size;
  if (header_id == ZIP64_EXTRA_FIELD_TAG) {
    if (*uncompressed_size == U4_MAX) *uncompressed_size = get_u8le(extra);
    ...
  }
}
``` [2](#0-1) 

The loop condition `extra_p != p` assumes the attacker-supplied `data_size` values sum exactly to `extra_field_length`. If a malicious ZIP encodes a `data_size` that overshoots (or undershoots and wraps) the declared `extra_field_length`, `extra_p` can advance past `p` without the loop terminating correctly, or `get_u8le(extra)` can read 8 bytes starting at `extra` even when the declared `payload_size` for the ZIP64 tag is smaller than 8 bytes — i.e., the code never verifies that the ZIP64 extra field is at least large enough (`data_size >= 8` per requested 64-bit field) before calling `get_u8le`. There is no check that `extra_p + data_size` stays within `[p_start, p_end)` of the extra-field block, nor a check against the mmap'd file's actual bounds. This is the direct analog of `glyph_cache_put`'s missing bound check on an attacker-influenced index into a fixed-size structure: here the attacker-controlled `data_size`/`header_id` pair from a ZIP's central directory extra field is used to compute a memory offset and then dereferenced (`get_u2le`, `get_u8le`) without a bounds check, versus the `zip_headers.h` `ExtraField::find` helper used elsewhere in the codebase (`output_jar.cc`/`zip_headers.h`), which *does* perform explicit bounds checks (`ziph::byte_ptr(ef) + ef->size() > byte_ptr(end)`) before dereferencing [3](#0-2) . `third_party/ijar/zip.cc` lacks this equivalent guard.

### Impact Explanation
A crafted JAR/ZIP consumed by `ijar` (e.g., a `java_import`'d jar, a jar produced by an external dependency, or any archive that flows into the ijar toolchain) can trigger an out-of-bounds heap/mmap read when Bazel processes its central directory. Because the mapped file backing this pointer arithmetic is a memory-mapped region (`MappedInputFile`), an out-of-bounds read can leak adjacent process memory into the derived interface jar's recorded sizes/offsets, or crash the process (SIGSEGV) if the read strays past the mapped page — consistent in severity with the reference CVE's medium-severity OOB read.

### Likelihood Explanation
`ijar` runs unconditionally as part of normal Java compilation actions on any input jar, including jars originating from external, attacker-influenced sources (an unprivileged party publishing a malicious jar dependency or an untrusted CI branch). No special build flags or privileges are required to reach this code path; it triggers on ordinary `java_library`/`java_import` builds.

### Recommendation
Add explicit bounds checks in `ProcessCentralDirEntry`'s extra-field loop, mirroring `singlejar`'s `ExtraField::find`: verify `extra_p + 4 <= p` before reading the 2-byte header/size fields, verify `extra_p + data_size <= p` before advancing, and verify `data_size >= 8` before calling `get_u8le` for the ZIP64 tag. Additionally bound `p` (and the overall central-directory cursor) against the actual mapped-file end.

### Proof of Concept
I could not fully verify a concrete, buildable JUnit/shell reproduction within the available exploration (the `get_u2le`/`get_u8le`/`get_u4le` helper definitions in `third_party/ijar/common.h` and the full bounds context of `ProcessNext`/`CalculateOutputLength`, which determine whether an even earlier guard exists against total mmap size, were not fully inspected due to tool budget). A reproducible PoC would construct a minimal ZIP (as already partially modeled by the existing `CreateZipWithMalformedExtraField` test helper in `src/tools/singlejar/output_jar_simple_test.cc`, which is for the sibling `singlejar` tool, not `ijar`) with a central directory entry whose extra field declares an oversized `data_size` and feed it through `ijar`'s `ZipExtractor`/`InputZipFile::ProcessNext` path, then run under ASan to confirm an out-of-bounds read. This gap in verification should be flagged: confirm whether `ProcessNext`/`CalculateOutputLength` already enforce a hard cap on central-directory traversal that would prevent `extra_p`/`p` from exceeding the mmap'd region before treating this as conclusively exploitable.
