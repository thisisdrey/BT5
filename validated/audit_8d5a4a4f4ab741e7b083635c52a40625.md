### Title
Unbounded growth of `PostReceiveRegistry.signaled` map causes memory-exhaustion DoS - ([File: internal/gitaly/hook/postreceive_registry.go])

### Summary
### Finding Description
`PostReceiveRegistry.Signal` buffers a result under `r.signaled[txID]` whenever `Signal` is called before a corresponding `RegisterWaiter` call for the same transaction ID exists [1](#0-0) . This entry is only ever removed in two places: when `RegisterWaiter` is subsequently called for that same `txID` (which pops and consumes it) [2](#0-1) , or when the registered waiter's `cleanup` closure runs (which only fires after a waiter was registered) [3](#0-2) . There is no expiry, size cap, or background reaper for the `signaled` map.

If `Signal` is invoked for a `txID` for which `RegisterWaiter` is never subsequently called, the entry is never cleaned up and remains in `r.signaled` for the lifetime of the process. This is directly analogous to the reported ERC1155 bug: a value is "deposited" (buffered) by one path expecting a later "claim" (`RegisterWaiter`) that may never come, and the deposited state is never reclaimed — leading to unbounded resource accumulation instead of an unbounded token loss.

The intended flow is: Praefect signals `SignalPostReceiveReady` after committed-phase concludes, and the primary Gitaly's `PostReceiveHook` handler calls `RegisterWaiter` for the same `txID` shortly after [4](#0-3) . However, the two paths are decoupled and can diverge for legitimate reasons reachable by an ordinary push:
- If `pre-receive` rejects the push (a routine, user-triggered outcome of an ordinary push), `PostReceiveHook` and its `postReceiveHook`/wait logic may never run for that transaction, so `RegisterWaiter` is never called — yet Praefect's async monitor may still fire `Signal` for the `txID` if the committed-phase concluded per Praefect's view.
- If the primary Gitaly RPC times out or the connection is dropped before reaching the post-receive wait step, `RegisterWaiter` is likewise skipped while `Signal` can still arrive via the backchannel RPC `SignalPostReceiveReady` [5](#0-4) .

Each ordinary push allocates a new transaction ID, so an attacker (or even normal usage patterns involving hook rejections/timeouts) that repeatedly triggers pushes whose post-receive `RegisterWaiter` path is skipped will cause `r.signaled` to grow monotonically, entry by entry, forever.

### Impact Explanation
This is an in-process, unbounded memory leak inside a long-lived `PostReceiveRegistry` singleton held by `GitLabHookManager` [6](#0-5) . Because ordinary, unprivileged git pushes are sufficient to reach the code paths that add entries to `signaled` without ever consuming them, an attacker with ordinary push access (or even normal traffic combined with routine pre-receive rejections/timeouts) can cause continuous growth of gitaly's heap, eventually leading to increased GC pressure, memory exhaustion, and process-level denial of service affecting all repositories served by that gitaly node — not just the attacker's own repository.

### Likelihood Explanation
The feature is currently gated behind the `PraefectPostReceiveSignal` feature flag, which defaults to `false` [7](#0-6) , so the leak only manifests once this flag is enabled. When enabled, no privileged access is required to trigger it — any pushing user can cause pre-receive rejections or RPC timeouts, both of which are routine occurrences in normal operation, making the leak likely to accumulate over time in a Praefect-fronted deployment with this flag on.

### Recommendation
Add a bound/expiry mechanism to `PostReceiveRegistry.signaled`: e.g., store a timestamp with each buffered signal and run a periodic sweep (similar to `tempdir`'s `clean` walker) to evict stale entries after a short grace period, or cap the map's size and evict oldest entries. Alternatively, require `Signal` to no-op (and log/drop) if no waiter is registered within a bounded time window rather than buffering indefinitely, so a `RegisterWaiter` that never arrives cannot cause unbounded growth.

### Proof of Concept
Conceptual reproduction (not run against a live cluster, inferred from code paths):
1. Enable feature flag `praefect_post_receive_signal`.
2. Repeatedly push changes to a repository configured so that the custom `pre-receive` hook rejects the push (a normal, user-controllable outcome) — this prevents `PostReceiveHook`/`postReceiveHook` from reaching the point where `RegisterWaiter` is called [8](#0-7) .
3. If Praefect's async monitor still observes the committed phase concluding for the transaction and calls `SignalPostReceiveReady` (backchannel RPC, unauthenticated by tenant identity, only checked for Praefect origin) [5](#0-4) , `PostReceiveRegistry.Signal` buffers the result in `r.signaled[txID]` with no consumer ever arriving to remove it [1](#0-0) .
4. Repeating this across many pushes over time accumulates entries in `signaled` indefinitely, since nothing purges stale, unclaimed entries.

Note: I could not fully trace the exact call site inside `manager.go`/`postreceive.go` that wires `RegisterWaiter` into the post-receive flow (it is not present in `internal/gitaly/hook/manager.go`, and I was unable to locate the calling code within the remaining exploration budget) to confirm every scenario under which `RegisterWaiter` is skipped after a `Signal`. This should be verified against the actual wiring code before treating the PoC as conclusively validated.

```go
// same event — the transaction's committed phase concluding — but then run on
// independent paths:
//
//   - Praefect (async monitor): CommittedConcluded -> DB generation write -> backchannel
//     SignalPostReceiveReady RPC -> Signal.
//   - Primary Gitaly (the push): committed-phase vote returns -> git finishes the ref
//     update -> post-receive hook runs -> waitForPraefectSignal -> RegisterWaiter.
//
// The committed phase concludes at essentially the same instant on both sides, so if the
// signal path (which includes a DB round-trip and a network RPC) happens to complete
// before the primary reaches its post-receive hook — e.g. fast/local Postgres or
// single-node quorum — Signal is called before RegisterWaiter. To handle this, Signal
// buffers the result in `signaled` and RegisterWaiter returns a pre-populated channel if
// a signal is already waiting. This buffering is required for correctness: without it the
// hook would block until timeout whenever the signal wins the race.
```

```go
func (r *PostReceiveRegistry) Signal(txID uint64, err error) {
	r.mu.Lock()
	defer r.mu.Unlock()

	ch, ok := r.waiters[txID]
	if !ok {
		r.signaled[txID] = err
		return
	}
```

```go
func (s *server) SignalPostReceiveReady(
	ctx context.Context,
	req *gitalypb.SignalPostReceiveReadyRequest,
) (*gitalypb.SignalPostReceiveReadyResponse, error) {
	// Validate that the request is coming via Praefect's backchannel.
	// This prevents external callers from unblocking arbitrary transactions.
	if _, err := backchannel.GetPeerID(ctx); err != nil {
		return nil, structerr.NewPermissionDenied("SignalPostReceiveReady can only be called via Praefect backchannel")
	}

	// Validate transaction ID is non-zero to prevent abuse.
	if req.GetTransactionId() == 0 {
		return nil, structerr.NewInvalidArgument("transaction_id must be non-zero")
	}

	if s.postReceiveRegistry == nil {
		return &gitalypb.SignalPostReceiveReadyResponse{}, nil
	}

	var signalErr error
	if req.GetPostTransactionFailed() {
		signalErr = errors.New("Praefect post-transaction work failed")
	}
	s.postReceiveRegistry.Signal(req.GetTransactionId(), signalErr)

	return &gitalypb.SignalPostReceiveReadyResponse{}, nil
}
```
