### Title
`leverage()` and `flashRepay()` lack a deadline parameter, allowing stale pending transactions to execute with outdated slippage bounds — (File: contracts/SmartFarmingManager.sol)

### Summary
`SmartFarmingManager.leverage()` and `SmartFarmingManager.flashRepay()` route user funds through an external AMM via `ISwapper.swapExactInput()` with only a minimum-amount-out slippage check and no deadline/expiry parameter. The `ISwapper` interface itself (`contracts/interfaces/external/ISwapper.sol`) does not support a deadline, so the staleness protection cannot even be passed through. A transaction that sits pending in the mempool (e.g., due to a low gas fee during congestion on mainnet/Base) can be mined much later when market prices have moved, executing at a stale `depositAmountMin_`/`swapAmountOutMin_` and delivering a worse trade than the user intended — the exact bug class of the reference report.

### Finding Description
- `leverage()` performs up to two AMM swaps (`tokenIn_ -> collateral` at line 184 and `syntheticToken -> collateral` at line 197) and only validates the final deposited amount against `depositAmountMin_` at line 198. There is no deadline check anywhere.
- `flashRepay()` swaps withdrawn collateral for the synthetic token at line 125 with `amountOutMin_ = 0` and checks `swapAmountOutMin_` afterward at line 126. Again, no expiry is enforced.
- `_swap()` (lines 293–311) calls `swapper_.swapExactInput(tokenIn, tokenOut, amountIn, amountOutMin, to)`; the interface signature at `contracts/interfaces/external/ISwapper.sol:6-12` accepts no deadline argument.
- `Pool.swap()` is oracle-priced and therefore does not suffer from mempool-staleness in the same way, making `SmartFarmingManager` the strongest reachable surface for this class.

### Impact Explanation
A user's pending `leverage`/`flashRepay` transaction mined after prices moved can produce two harms: (1) the user unknowingly completes a bad trade that still satisfies a stale `min` bound, losing value versus current market prices (direct loss of user funds); (2) on chains with public mempools, a stale/loose slippage bound widens the sandwich surface for MEV bots, extracting user funds. On the deployment set (mainnet, Base, Optimism, etc.), mempool-visible transactions on mainnet are sandwichable; on L2 sequencers the first scenario still applies during congestion where inclusion is delayed.

### Likelihood Explanation
Likelihood is conditional: it requires the user's transaction to remain pending while prices move, or an outdated slippage bound attractive to a sandwich. The sponsor of the original report argued this is network-level/out of scope, and the judge rated it medium as a user-conditional error — the same assessment applies here since the code identically omits any expiry mechanism.

### Recommendation
Add a `deadline_` parameter to `leverage()`, `flashRepay()`, the cross-chain variants (`CrossChainDispatcher.triggerLeverageSwap`/`triggerFlashRepaySwap` and retry paths), and to `ISwapper.swapExactInput()`, reverting if `block.timestamp > deadline_` before executing any swap, consistent with standard DEX-aggregator practice.

### Proof of Concept
1. Alice calls `SmartFarmingManager.flashRepay(msUSD, vaETHDeposit, withdrawAmount, swapAmountOutMin)` with a gas price too low for immediate inclusion.
2. The tx stays pending; hours later the collateral/msUSD price moves adversely.
3. When finally mined, `_swap` executes at current (worse) market prices and the stale `swapAmountOutMin_` still passes, repaying less debt than Alice expected — or on a public mempool a bot sandwiches the loose bound.
4. A Foundry test reproducing this: warp `vm.warp(block.timestamp + N)`, move the mock swapper's exchange rate, then execute the pre-signed `flashRepay` call and assert the output is worse than at signing time yet still above the stale min. Since there is no timestamp check, nothing prevents execution.

Note: this is a user-conditional, medium-severity analog matching the judged severity of the reference finding; whether it is in scope depends on the program's stance on mempool-timing issues.
