### Title
Unguarded BigInteger division by `totalEnergyWeight`/`totalNetWeight` in `RepositoryImpl` can throw `ArithmeticException` and abort TVM resource-limit calculations - (File: `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java`)

### Summary
`RepositoryImpl.calculateGlobalEnergyLimit()` (and the analogous net-limit computation reachable through `getUsage`/`usageToBalance`) divides by `totalEnergyWeight` using `BigInteger.divide()` when hardened resource calculation is enabled, but only protects against the zero-denominator case with a Java `assert` statement, which is a no-op unless the JVM is started with `-ea`. This is the same bug class as the reported Beta Finance issue: a denominator that legitimately represents a "total shares/weight" value and can be `0` (before anyone has frozen TRX for ENERGY, or after all ENERGY-frozen balance has been unfrozen) is not defensively checked before being used as a divisor, so the call throws an uncaught `ArithmeticException` instead of degrading gracefully to `0`.

`RepositoryImpl.calculateGlobalEnergyLimit` reimplements this same math directly (rather than delegating to the guarded `ResourceProcessor`/`EnergyProcessor` helpers) and omits the `totalEnergyWeight <= 0 → return 0` short-circuit that its sibling implementation has, relying solely on a disabled `assert`. Because `totalEnergyWeight`/`totalNetWeight` are chain-wide aggregate counters that decrease every time TRX is unfrozen (`RepositoryImpl.addTotalEnergyWeight`/`addTotalNetWeight` with negative deltas, driven by `FreezeBalanceV2Actuator`, `UnfreezeBalanceV2Actuator`, `CancelAllUnfreezeV2Actuator`), it is possible for this aggregate to reach `0` (e.g., on a freshly bootstrapped/private chain before any account has frozen TRX for ENERGY, or transiently after mass unfreezing), exactly mirroring the "new pool / zero total supply" precondition in the original Beta Finance report. [6](#0-5) [7](#0-6) 

### Impact Explanation
When `hardenResourceCalculation()` is enabled and `totalEnergyWeight` (or `totalNetWeight` via the equivalent net-limit path) is `0`, `BigInteger.divide(BigInteger.ZERO)` throws `ArithmeticException`. Unlike the double-arithmetic fallback (which silently produces `Infinity`/`NaN` and truncates to a wrong-but-non-throwing long), the hardened/BigInteger path throws. If this exception propagates uncaught out of a TVM resource-limit computation invoked as part of processing a broadcast transaction or contract call, it can abort that unit of work; if it is not properly caught at a higher layer in block application, this can freeze the affected resource-limit computation path for every account until `totalEnergyWeight`/`totalNetWeight` becomes non-zero again — a denial-of-service on ENERGY/BANDWIDTH resource accounting analogous to the "rebalancing frozen" impact in the original report.

### Likelihood Explanation
Likelihood is contingent on: (1) `hardenResourceCalculation()`/`allowHardenResourceCalculation` being enabled (a hard-fork-gated feature flag), and (2) `totalEnergyWeight` or `totalNetWeight` reaching `0`, which is realistic on any newly-deployed chain (testnet, private chain, or right after genesis before the resource pool is populated) or transiently if unfreezing outpaces freezing. I was not able to fully confirm, within the available search budget, the exact caller chain that invokes `RepositoryImpl.calculateGlobalEnergyLimit` (it is declared on the `Repository` interface and referenced from `FreezeV2Util.java`/`Program.java`-adjacent VM utility code, but I could not trace the precise precompile/opcode entry point in this pass). This uncertainty should be resolved by a deeper trace of `Repository.calculateGlobalEnergyLimit` callers before treating this as fully confirmed exploitable from an unprivileged transaction.

### Recommendation
Add the same zero/negative guard used by `EnergyProcessor`/`BandwidthProcessor`/`calculateGlobalLimitV2` to `RepositoryImpl.calculateGlobalEnergyLimit` (and the corresponding net-limit logic), returning `0` when `totalEnergyWeight <= 0` (or `totalNetWeight <= 0`) before performing the `BigInteger` division, rather than relying on a JVM `assert` that is disabled in production.

### Proof of Concept
1. Deploy/initialize a chain (or reach a state) where no account has frozen TRX for ENERGY, so `DynamicPropertiesStore.TOTAL_ENERGY_WEIGHT == 0`.
2. Enable `allowHardenResourceCalculation` (hardened resource calculation flag).
3. Trigger a TVM-level call path that invokes `Repository.calculateGlobalEnergyLimit(accountCapsule)` with `accountCapsule.getAllFrozenBalanceForEnergy() >= TRX_PRECISION` (e.g., an account that has legacy V1 frozen ENERGY balance but the network-wide `totalEnergyWeight` counter is otherwise zero due to accounting reset/migration).
4. `BigInteger.valueOf(totalEnergyLimit).divide(BigInteger.valueOf(0))` throws `ArithmeticException: BigInteger divide by zero`, matching `RepositoryImplHardenTest`/`CalculateGlobalLimitHardenTest`-style overflow/zero tests already present in the test suite for the sibling `calculateGlobalEnergyLimit` methods but not exercised for this zero-weight case: [8](#0-7)
