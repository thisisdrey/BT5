### Title
Per-`TokenId` NEP-245/IMT fee exemption for `|delta|==1` allows fee-free transfer of arbitrary value split across many `token_id`s - (File: contracts/defuse/core/src/intents/token_diff.rs)

### Summary
`TokenDiff::token_fee` waives the protocol fee whenever a NEP-245 (or IMT) leg's absolute delta is `1`, on the theory that such legs represent an indivisible NFT-like unit. Because the exemption is evaluated per distinct `TokenId` (contract + `token_id` string), a signer can move an arbitrary aggregate quantity of value by spreading it across `N` distinct `token_id`s, each traded with `delta.unsigned_abs() == 1`, paying `Pips::ZERO` fee on every leg instead of the fee that a single `N`-unit delta on one `token_id` would incur.

### Finding Description
The broken binding is:

`fees_collected(single N-unit leg on token_id T) == fees_collected(N legs of 1 unit each on distinct token_id T_1..T_N)` for equal aggregate value moved.

In `TokenDiff::execute_intent` (`contracts/defuse/core/src/intents/token_diff.rs:59-78`), for every negative-delta entry in `self.diff` the fee is computed independently per `TokenId`:
```
let fee = Self::token_fee(token_id, amount, protocol_fee).fee_ceil(amount);
```
`TokenDiff::token_fee` (lines 206-216) explicitly zeroes the fee for `Nep245`/`Imt` when `amount <= 1`:
```
TokenIdType::Nep245 | TokenIdType::Imt if amount > 1 => {}
TokenIdType::Nep171 | TokenIdType::Nep245 | TokenIdType::Imt => return Pips::ZERO,
```
Because `self.diff` is a `BTreeMap<TokenId, i128>` keyed by the full `TokenId` (which for NEP-245 embeds both the MT contract id and the sub-`token_id` string), an attacker with `N` distinct NEP-245 `token_id`s already deposited (each balance `>= 1`) can submit one `TokenDiff` intent with `N` separate legs, each `delta == -1` on a different `token_id`. Every leg independently satisfies `amount <= 1`, so `token_fee` returns `Pips::ZERO` for all `N` legs and `fees_collected` never gains an entry for them, regardless of how large `N` is or how much aggregate notional value the counterparty (solver) pays for those `N` legs in NEP-141 or other tokens. The exact same aggregate quantity moved as a single `token_id` with `delta == -N` would instead pay `fee.fee_ceil(N) > 0`.

No existing guard prevents this: `MultiPayload::verify`, nonce/salt checks, and `TransferMatcher::finalize` only validate signatures, replay-protection and that deltas net to zero across the batch — none of them recompute or cap the fee based on aggregate value across distinct `TokenId`s. The per-`TokenId` fee exemption is coded as a deliberate design choice for genuine single NFT transfers, but it does not distinguish "one truly indivisible NFT" from "many distinct MT `token_id`s that together represent a divisible/fungible notional value" (e.g., an MT contract minting many `token_id`s each representing a fixed unit of value, which the attacker can deploy and control per the stated preconditions).

### Impact Explanation
The `fee_collector` under-collects protocol fees on the entire value transferred through legs structured this way, up to 100% of the fee that would otherwise apply — this matches the explicitly listed Critical category "protocol fees bypassed." No accounting invariant is broken (the Verifier remains solvent, and the counterparty must still genuinely provide value), but every batch structured this way permanently denies the protocol its fee on that leg. This is repeatable indefinitely across accounts/tokens/batches as long as the attacker (or any MT-contract-controlling party) can mint/hold many distinct `token_id`s of unit amount.

### Likelihood Explanation
Requires only that the attacker's chosen NEP-245 contract (which per the attacker profile they can deploy and control) issues many distinct `token_id`s and that a counterparty is willing to trade against them for real value in the same batch — no privileged role, relayer key, or victim key is needed. Cost is minimal (deploying an MT contract and depositing `N` balances of 1 unit each), and it is trivially repeatable.

### Recommendation
Compute the NEP-245/IMT fee exemption based on aggregate notional value across all legs of the same underlying MT contract (or require callers to consolidate same-contract legs into one `token_id`/amount before fee assessment), or restrict the `amount <= 1` exemption to intents containing exactly one NEP-245/IMT leg per contract, so that fee assessment cannot be defeated by fragmenting a transfer across many `token_id`s.

### Proof of Concept
Unit test in `contracts/defuse/core/src/intents/token_diff.rs` (or a new test module) comparing `TokenDiff::token_fee` totals:
```rust
let fee = Pips::ONE_PERCENT;
let mt_contract: AccountId = "mt.near".parse().unwrap();

// Single leg: 100 units of one token_id
let single_id = TokenId::from(Nep245TokenId::new(mt_contract.clone(), "shareA".into()));
let single_fee = TokenDiff::token_fee(&single_id, 100, fee).fee_ceil(100);
assert!(single_fee > 0);

// Split leg: 100 distinct token_ids, each amount 1
let split_fee_total: u128 = (0..100)
    .map(|i| {
        let id = TokenId::from(Nep245TokenId::new(mt_contract.clone(), format!("share{i}")));
        TokenDiff::token_fee(&id, 1, fee).fee_ceil(1)
    })
    .sum();

assert_eq!(split_fee_total, 0);
assert_ne!(split_fee_total, single_fee); // fee bypassed despite equal aggregate value
```
This can be extended to a full `near-workspaces` sandbox test executing two `TokenDiff` intents (one aggregated leg vs. `N` unit legs on a deployed MT contract) against `execute_intents` and asserting the `fee_collector`'s resulting balance differs despite identical aggregate value transferred.
