### Title
Unbounded attachment size in `GetAttachmentResponse::deserialize` allows a malicious peer to smuggle oversized attachment payloads past the `attachments_max_size` bound - (File: stackslib/src/net/atlas/mod.rs)

### Summary
`GetAttachmentResponse::deserialize` decodes an arbitrary-length hex string from a peer's HTTP response and constructs an `Attachment` directly, with no comparison against `AtlasConfig.attachments_max_size` at the point of decode. [1](#0-0)  Because this is the deserialization routine used by `StacksHttpResponse::decode_atlas_get_attachment` when parsing the response to a `GET /v2/attachments/{hash}` request sent to a peer during attachment sync, an attacker-controlled peer can respond with a hex-encoded blob far larger than the configured `attachments_max_size` (default 1 MiB, via `ATTACHMENTS_MAX_SIZE_MIN`). [2](#0-1) [3](#0-2) 

### Finding Description
The invariant the codebase intends is `Attachment.content.len() <= AtlasConfig.attachments_max_size`, enforced at config-validation time via `AtlasConfig::validate` (which only checks the *configured minimum*, not incoming data) [4](#0-3) , but nothing in the `Deserialize` implementation for `GetAttachmentResponse` re-checks this bound against the bytes actually received from the wire: it calls `hex_bytes(&hex_encoded)` and directly wraps the result in `Attachment::new(bytes)` regardless of size. [1](#0-0) 

The attacker's exact message is a normal JSON HTTP response body to `GET /v2/attachments/{hash}` containing a hex string many times larger than `attachments_max_size` (e.g. hundreds of MB). This response is parsed by `RPCGetAttachmentRequestHandler::try_parse_response` → `parse_json` → `GetAttachmentResponse::deserialize`, and then surfaced through `StacksHttpResponse::decode_atlas_get_attachment`. [5](#0-4)  A grep of the codebase confirms `attachments_max_size` is referenced only in `mod.rs` (struct/validate), `config/mod.rs`, `Stacks.toml`, `db.rs`, and `tests.rs` — it is not referenced anywhere in `stackslib/src/net/atlas/download.rs`, the module that consumes `GetAttachmentResponse` and stores attachments via the `extend_with_attachments`-style insertion path. This means the size check performed at config-load time is never re-applied to attacker-supplied response bytes on the client/download side.

### Impact Explanation
A malicious peer that the node's Atlas downloader contacts for an attachment (because the peer advertised having it in its attachment inventory) can force the victim node to allocate and hex-decode an arbitrarily large buffer from a single HTTP response, and this oversized `Attachment.content` can then flow into the node's attachment processing/storage path without the intended `attachments_max_size` bound being enforced at the point of decode. This is a single-message (or few-message), unauthenticated resource-consumption issue against any node performing Atlas attachment sync, repeatable on demand by any peer the downloader queries.

### Likelihood Explanation
Precondition: the victim node's Atlas subsystem must be attempting to fetch an attachment (this requires that an attachment instance be known via on-chain BNS/registration and that the attacker's peer be selected as a download source, which an attacker can arrange by running their own peer and advertising the relevant inventory bit). No secrets, admin roles, or privileged keys are required — only that the attacker run an ordinary P2P/RPC-reachable peer, which matches the "unprivileged remote party" threat model. The attack costs the attacker only building one oversized HTTP response.

### Recommendation
Enforce `attachments_max_size` inside `GetAttachmentResponse::deserialize` (or immediately after hex-decoding, before constructing `Attachment`), rejecting/erroring out any payload whose decoded byte length exceeds the configured maximum, and additionally re-validate `attachment.content.len()` against `AtlasConfig.attachments_max_size` in the `download.rs` ingestion path before any DB insertion, so the bound is enforced independent of where the value later flows.

### Proof of Concept
Rust test in `stackslib/src/net/atlas/tests.rs` (or a new test module) that: (1) constructs a JSON string of the form `"<hex string of length > 2 * ATTACHMENTS_MAX_SIZE_MIN>"`; (2) calls `serde_json::from_str::<GetAttachmentResponse>(...)` directly, or builds a `StacksHttpResponse` with that body and calls `decode_atlas_get_attachment()`; (3) asserts that decoding succeeds and `resp.attachment.content.len()` exceeds `ATTACHMENTS_MAX_SIZE_MIN`, demonstrating the missing bound at the deserialization boundary identified in `stackslib/src/net/atlas/mod.rs:69-77`.

Note: I was unable to fully read `stackslib/src/net/atlas/download.rs` in this session due to tool-call budget limits, so I could not directly confirm or rule out a downstream size check performed after `extend_with_attachments`/DB insertion. The grep-based evidence (absence of the `attachments_max_size` identifier anywhere in `download.rs`) supports the claim that no such check exists on that path, but this should be independently verified by reading `download.rs` in full before treating this as fully confirmed.

impl<'de> Deserialize<'de> for GetAttachmentResponse {
    fn deserialize<D: serde::Deserializer<'de>>(d: D) -> Result<GetAttachmentResponse, D::Error> {
        let payload = String::deserialize(d)?;
        let hex_encoded = payload.parse::<String>().map_err(de_Error::custom)?;
        let bytes = hex_bytes(&hex_encoded).map_err(de_Error::custom)?;
        let attachment = Attachment::new(bytes);
        Ok(GetAttachmentResponse { attachment })
    }
}
