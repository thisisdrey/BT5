Based on my investigation, java-tron's `ExchangeCreateActuator`/`ExchangeCapsule` pool mechanism is structurally analogous to the SoftVault first-depositor issue: an unprivileged account creates the pool with attacker-chosen (arbitrarily small) initial token balances, which are then used as the ratio basis for all future `ExchangeInject` and `ExchangeTransaction` operations, with no minimum-liquidity floor and no protection against extreme skew.

### Title
First TRC10 Exchange creator can set an arbitrarily skewed initial reserve ratio to later drain counterparties via rounding - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeCreateActuator.java])

### Summary
`ExchangeCreateActuator` lets any account create a TRC10 Bancor-style trading pool (`Exchange`) by freely choosing `firstTokenBalance`/`secondTokenBalance`, the only constraint being `> 0` and below `exchangeBalanceLimit`. This mirrors the `SoftVault` "first depositor sets share price" bug class: whoever creates the pool fully controls the initial price ratio with no minimum-liquidity safeguard, and subsequent `ExchangeInject`/`ExchangeTransaction` calls compute amounts from that ratio using integer/floor division that can be made to favor the creator at the counterparty's expense.

### Finding Description
`ExchangeCreateActuator.doValidate()` only checks `firstTokenBalance <= 0 || secondTokenBalance <= 0` and an upper `exchangeBalanceLimit`, with no minimum-size or ratio-sanity requirement: [1](#0-0) 

This lets the creator set balances such as `firstTokenBalance = 1, secondTokenBalance = 1_000_000_000_000` (or any other extreme ratio), fully determining the exchange rate that the pool starts with, exactly like the first depositor minting 1 share in `SoftVault.deposit`.

Two downstream actuators consume this attacker-chosen ratio:

1. `ExchangeInjectActuator` computes the "another token" amount to require from an injector using integer division (`floorDiv`) of the pool's current (attacker-set) balances: [2](#0-1) 
When the pool ratio is extreme (e.g., `firstTokenBalance = 1`), `anotherTokenQuant = floorDiv(secondTokenBalance * tokenQuant, firstTokenBalance)` can be trivially forced to round in the creator's favor, or make it effectively free/near-free to inject one side while requiring a huge/rounded amount of the other, corrupting the pool's economic backing.

2. `ExchangeTransactionActuator`/`ExchangeCapsule.transaction()` feeds the same attacker-set `firstTokenBalance`/`secondTokenBalance` directly into the Bancor pricing formula: [3](#0-2) [4](#0-3) 
With one reserve set to a minimal value (e.g., `1`), the `pow`-based formula becomes numerically unstable/extremely sensitive to the first trade, letting the creator (or a colluding first trader) extract a disproportionate amount of the other token for a negligible amount of the skewed token, before any other liquidity/trust assumption holds.

### Impact Explanation
An attacker who creates the exchange (`ExchangeCreateContract`, reachable by any signed transaction from any account) can set the initial reserve ratio to an extreme value at negligible cost (limited only by `firstTokenBalance/secondTokenBalance > 0` and the `exchangeBalanceLimit` upper bound), then induce a victim to `ExchangeInject` or `ExchangeTransaction` against the corrupted ratio, extracting value from the victim due to rounding/extreme-ratio effects — a direct value-extraction path against any counterparty interacting with the pool, analogous to the reported "first depositor manipulates share price" impact.

### Likelihood Explanation
Creating an Exchange with skewed balances requires only enough of one token (which can be `1` unit) and the fixed `calcFee()` TRX fee — no special privilege is needed. The attack requires a second party (victim) to interact with that specific exchange (inject or trade), which is a normal, expected interaction pattern for TRC10 exchanges, making exploitation plausible whenever victims trust exchange IDs without inspecting reserve ratios.

### Recommendation
- Enforce a sane minimum initial balance and/or minimum ratio bound in `ExchangeCreateActuator.doValidate()` (e.g., require both `firstTokenBalance` and `secondTokenBalance` to exceed a protocol-defined minimum, not just `> 0`).
- Consider requiring symmetric/minimum liquidity locks for pool creation similar to Uniswap-style minimum-liquidity burns, or exposing the current ratio prominently so integrators/clients can reject exchanges with extreme skew before injecting/trading.
- Review `ExchangeInjectActuator`'s `floorDiv` usage for rounding direction that could always favor one side over the other at extreme ratios.

### Proof of Concept
1. Attacker calls `ExchangeCreateContract` with `firstTokenId = TRX`, `firstTokenBalance = 1`, `secondTokenId = <ownTRC10>`, `secondTokenBalance = 1_000_000_000_000` — validated/executed per [5](#0-4) .
2. Victim, trusting the exchange ID, calls `ExchangeInjectContract` to add liquidity in TRX; `ExchangeInjectActuator.execute()` computes the paired TRC10 amount via `floorDiv(secondTokenBalance * tokenQuant, firstTokenBalance)` off the skewed `1` reserve, per [2](#0-1) , producing a distorted required amount.
3. Alternatively, victim calls `ExchangeTransactionContract` to trade against the pool; `ExchangeCapsule.transaction()` uses the same skewed reserves in the Bancor formula in `ExchangeProcessor.exchange()`, extracting disproportionate value from the victim's trade. [6](#0-5) [7](#0-6) [8](#0-7)

    if (dynamicStore.getAllowSameTokenName() == 1) {

            firstTokenBalance, tokenQuant), secondTokenBalance);

            addExact(secondTokenBalance, tokenQuant));
      }

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
