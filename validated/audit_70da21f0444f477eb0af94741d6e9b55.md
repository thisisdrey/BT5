## Analysis

The external GMX report's core broken invariant: **a swap-through-conversion path skips slippage/minimum-output enforcement while a comparable path in the same subsystem enforces it**, letting the party on the other side of the swap capture unbounded value from adverse price movement.

The Polkadot SDK analog to this exact pattern exists in the `SwapFirstAssetTrader` weight-trader used to pay/refund XCM execution fees by swapping a user-supplied asset into/out-of a `Target` fee asset through `pallet_asset_conversion`'s `SwapCredit` interface.

- `buy_weight` correctly protects the *purchase* leg: it calls `SwapCredit::swap_tokens_for_exact_tokens(..., fee)`, i.e. it demands *exactly* `fee` of `Target` and lets the input amount float — the user's asset spend is capped by whatever the AMM needs, and any unfavorable price only makes the user spend more of *their own* asset, never lose more than intended of the `Target` fee itself. [1](#0-0) 

- `refund_weight`, however, calls `SwapCredit::swap_exact_tokens_for_tokens(vec![Target::get(), refund_swap_asset], refund, None)` — passing `None` for `amount_out_min`, the exact analog of GMX's missing `minLongTokenAmount`/`minShortTokenAmount` check when no swap-path/min is supplied. [2](#0-1) 

- The `SwapCredit` mock used in this module's own test-suite makes the semantics explicit: `amount_out_min.unwrap_or(Self::Balance::zero())` — passing `None` is treated as "accept any output down to zero." [3](#0-2) 

### Title
Unprotected refund swap accepts any output amount (no slippage floor) in `SwapFirstAssetTrader::refund_weight` - (File: `cumulus/primitives/utility/src/lib.rs`)

### Summary
`SwapFirstAssetTrader` is a `WeightTrader` used by parachain runtimes to let users pay XCM execution fees in a non-native asset by auto-swapping it into the `Target` fee asset via `pallet_asset_conversion`'s `SwapCredit`. When execution weight is refunded (partial/unused `BuyExecution`/`PayFees`), `refund_weight` swaps `Target` back into the asset the user originally supplied so the refund can be returned in kind. This swap-back is invoked with `amount_out_min = None`, meaning the AMM's `do_swap_exact_credit_tokens_for_tokens` performs the swap without any lower bound on the amount received — exactly the missing check identified in the GMX report (withdrawal/refund path with no swap-path minimum enforced).

### Finding Description
`SwapFirstAssetTrader::refund_weight` extracts `refund_amount` of `Target` from accumulated fees and swaps it for the user's original asset:
```rust
let refund = self.total_fee.extract(refund_amount);
let refund = match SwapCredit::swap_exact_tokens_for_tokens(
    vec![Target::get(), refund_swap_asset],
    refund,
    None,
) { ... };
``` [4](#0-3) 

Because `amount_out_min` is `None`, `pallet_asset_conversion::Pallet::do_swap_exact_credit_tokens_for_tokens` only checks `amount_out_min.map_or(true, |a| amount_out >= a)`, which is vacuously true, so no floor is enforced on `amount_out` — the swap succeeds regardless of how little `refund_swap_asset` the pool returns for the `Target` fed in. [5](#0-4) 

This is the asymmetric-protection pattern from the GMX report: the "buy" (deposit) leg of the trade is protected by demanding an exact output (`swap_tokens_for_exact_tokens`), but the "give-back"/refund leg accepts an unconstrained output, so any adverse pool state at the moment of the refund (temporary imbalance, low liquidity in the relevant pair, or another XCM message's swap processed earlier in the same block against the same pool) silently reduces the value returned to the user with no on-chain recourse or failure — the trader always reports success (`Some(refund)`) as long as the swap call itself doesn't error.

### Impact Explanation
This directly violates the invariant that fee/refund payout state must settle the exact rightful amount to the beneficiary. A user who is entitled to a refund of unused XCM execution fees can receive a refund credit worth substantially less than the `Target`-asset value extracted from `total_fee`, with the shortfall absorbed by the AMM pool/LPs rather than returned to the user. Because this runs inside the XCM executor for every parachain configuring `SwapFirstAssetTrader` (e.g. Asset Hub runtimes, per `prdoc/stable2506/pr_8376.prdoc` which documents its adoption to replace `TakeFirstAssetTrader`), the value loss is systemic to any refund path using this trader whenever the relevant pool is thin or has moved since `buy_weight` executed. [6](#0-5) 

### Likelihood Explanation
This does not require a malicious validator, collator, relayer, or governance actor — any unprivileged account that can submit XCM messages incurring `BuyExecution`/`PayFees` followed by unused weight can trigger `refund_weight` under adverse pool conditions (thin liquidity, or a preceding message in the same block that moves the pool via `ExchangeAsset`/swap fee payment against the same asset pair). No `amount_out_min` guard exists to reject the resulting undervalued refund.

### Recommendation
`refund_weight` should compute a minimum acceptable refund (e.g. via `QuotePrice::quote_price_exact_tokens_for_tokens` before swapping, mirroring how `buy_weight`/`quote_weight` already use `QuotePrice`) and pass `Some(min_amount)` to `SwapCredit::swap_exact_tokens_for_tokens` instead of `None`, treating a below-floor result as a failed refund (fall back to returning the un-swapped `Target` credit to `total_fee`, as is already done on hard swap errors) rather than silently accepting an under-valued swap.

### Proof of Concept
1. Configure a runtime with `SwapFirstAssetTrader<Target=Native, SwapCredit=AssetConversion, ...>` and a thinly-liquidated `(Native, AssetX)` pool.
2. Submit XCM `WithdrawAsset(AssetX) -> BuyExecution{fees: AssetX, weight_limit} -> <cheap program>` so that `buy_weight` swaps part of `AssetX` into `Native` for `total_fee`, leaving significant unused weight.
3. Before/at the same block, submit another XCM message that swaps a large amount against the same `(Native, AssetX)` pool (a legitimate, unprivileged action, e.g. another user's `ExchangeAsset`), moving the pool price so that `Native -> AssetX` now returns far less `AssetX` than fair value.
4. Let `refund_weight` run for the first message: it calls `swap_exact_tokens_for_tokens(vec![Native, AssetX], refund_credit_in_native, None)`, accepting whatever (possibly near-zero) `AssetX` the degraded pool state yields, and returns that as the "refund" — observably less than `WeightToFee::weight_to_fee(unused_weight)` worth of `AssetX`, with no error raised. [7](#0-6)

			// noting to refund.
			return None;
		}

			// create an initial zero refund in the asset used in the last `buy_weight`.

			return None;
