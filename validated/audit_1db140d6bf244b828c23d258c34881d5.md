### Title
Users with debt permanently frozen out of withdrawing disabled collateral when the asset's oracle price cannot be resolved - ([File: contracts/market/market.clar])

### Summary
When a collateral asset is disabled by the DAO registry (`assets.clar` `disable`) but a user still holds that asset as collateral, `market.clar`'s `collateral-remove` forces the withdrawal path for disabled collateral to depend on a live oracle price for that asset. If the oracle for a disabled asset can no longer be resolved (feed retired/never refreshed since the asset is no longer part of active egroups/price-update flows), any user who has ANY debt elsewhere in the protocol is permanently unable to withdraw their own disabled-collateral holdings, mirroring the SKALE analog where delegators are stuck with a non-functioning validator because an unrelated on-chain precondition (MSR / here, a valid oracle price) blocks their exit.

### Finding Description
`collateral-remove` branches on whether the collateral asset is still "enabled" (`is-collateral-enabled (get collateral asset)`): [1](#0-0) 

For the disabled-collateral branch, the code unconditionally requires a successful oracle resolution before it will even evaluate whether the withdrawal is safe:
```
(price (unwrap! (price-resolve oracle-data) ERR-DISABLED-COLLATERAL-PRICE-FAILED))
``` [2](#0-1) 

This is reached only when the caller has debt elsewhere (`has-debt` true) — see the top-level dispatch: [3](#0-2) 

The asset registry allows the DAO to disable an asset's collateral flag via `assets.clar`'s `disable`, which simply flips the bitmap and does not guarantee the oracle feed for that asset continues to be maintained/updated: [4](#0-3) 

Because the disabled asset is no longer part of any live egroup or actively-priced position, once its Pyth/DIA feed goes stale (no participant has economic incentive to keep pushing updates for a delisted asset, and `write-feeds` only accepts feeds the caller supplies — if the feed itself is retired/unavailable there is nothing valid to supply), `price-resolve` will keep failing, and `ERR-DISABLED-COLLATERAL-PRICE-FAILED` will be returned indefinitely. The user cannot bypass this: there is no path in `collateral-remove` that lets a user withdraw disabled collateral while holding debt without going through the oracle-price branch, and the only "no debt" bypass requires the user to have zero debt on every other asset, which they may not control (e.g., they may need to keep borrowing for operational reasons, or repaying may itself be blocked by the same market being paused/other issue).

This is structurally analogous to the SKALE report: an unrelated precondition enforced at the protocol level (there: MSR being met by the validator; here: oracle price being resolvable for a delisted asset) that the token holder/user does not control, blocks the user from exiting/withdrawing their own funds indefinitely.

### Impact Explanation
This results in **temporary to permanent freezing of funds** — the user's own disabled-collateral balance becomes unwithdrawable for as long as (a) they carry any debt elsewhere and (b) the oracle for the disabled asset cannot be resolved. If the asset was disabled precisely because its oracle feed is broken/retired (a very plausible disable-trigger), the condition can persist indefinitely, i.e., permanent freezing of the collateral, which lands squarely in the "permanent freezing of funds" / "temporary freezing of funds" impact classes.

### Likelihood Explanation
Likelihood is tied to an asset being disabled while still held as collateral by users with open debt positions elsewhere — a realistic post-disable state, since disabling an asset does not force-liquidate or force-withdraw existing holders. Any scenario where an asset is disabled due to oracle/feed problems (a common real-world disable trigger) directly produces the stuck state for every affected user simultaneously.

### Recommendation
Decouple the ability to withdraw a user's own disabled collateral from a live-price requirement when the withdrawal cannot increase risk to the protocol (e.g., allow using the last cached/known price, or allow full withdrawal of the disabled asset without valuation if the user's remaining collateral/debt (excluding the disabled asset) is separately confirmed healthy). Alternatively, provide a DAO/permissionless "force-withdraw disabled collateral" path that does not require re-resolving oracle prices for an asset that is no longer counted toward collateral value.

### Proof of Concept
1. DAO disables asset `X` as collateral via `assets.disable` (e.g., because its oracle feed is being retired) while some users still hold `X` as collateral: [4](#0-3) .
2. Alice holds `X` as collateral and has any outstanding debt on another asset (e.g., USDC).
3. No participant continues to push price updates for the now-delisted `X` feed; `write-feeds` cannot supply a valid update since the feed publisher has stopped publishing.
4. Alice calls `market.collateral-remove` to withdraw her `X` collateral. Because `has-debt` is true and `is-collateral-enabled` is false, the code executes `(price (unwrap! (price-resolve oracle-data) ERR-DISABLED-COLLATERAL-PRICE-FAILED))` at [2](#0-1) , which fails and reverts the whole call with `ERR-DISABLED-COLLATERAL-PRICE-FAILED`.
5. Alice's only way out is to fully repay all debt everywhere in the protocol first (not always feasible/desirable), after which the "no debt" branch skips price resolution entirely: [5](#0-4) . Until then, her disabled collateral remains permanently locked, exactly mirroring token holders unable to exit delegation to a non-functioning validator.
