### Title
Unbounded attacker-controlled offsets in `VerifyTransferProof` allow out-of-bounds read of heap-adjacent EVM data - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The Sapling shielded-transfer precompile parses `spendOffset`, `spendAuthSigOffset` and `receiveOffset` directly from attacker-supplied `data` and then uses them, unchecked, to index further into `data` for reading proof/signature/commitment fields. This mirrors the CVE-2019-2180 bug class: a length/offset value taken from untrusted input is used without validating it against the buffer bounds, causing an out-of-bounds read.

### Finding Description
`VerifyTransferProof.execute()` only checks that `data.length` matches one of four fixed sizes (`{2080, 2368, 2464, 2752}`), then reads three 32-byte-aligned offset fields directly from the buffer: [1](#0-0) 

`spendOffset`, `spendAuthSigOffset`, and `receiveOffset` come straight from `parseInt(data, 0/32/64)` with no upper- or lower-bound validation against `data.length`. These raw values are then used as base offsets for `parseInt(data, spendOffset)` / `parseInt(data, spendAuthSigOffset)` / `parseInt(data, receiveOffset)`, and afterward for computing per-item byte offsets in `System.arraycopy` calls that read `nullifier`, `anchor`, `spendCv`, `rk`, `spendProof`, `spendAuthSig`, `receiveCm`, `receiveCv`, `receiveEpk`, and `receiveProof`: [2](#0-1) 

Because `spendOffset`/`spendAuthSigOffset`/`receiveOffset` are arbitrary 32-bit integers chosen entirely by the transaction/contract caller (this precompile is reachable from any TVM contract call, e.g. via `TriggerSmartContract`, since precompiles are invoked at fixed addresses from TVM opcode dispatch), an attacker can set them to values that make `parseInt(data, spendOffset)` or the subsequent `System.arraycopy` source offsets land far outside the `data` array — including negative offsets (via integer overflow of `spendOffset + 320*i + 128` etc.) or offsets beyond `data.length`. This is directly analogous to `ippSetValueTag`'s failure to validate an offset/length derived from untrusted input before using it to index a buffer.

### Impact Explanation
Unlike a typical parsing bug that just throws, here the entire block is wrapped in a broad `catch (Throwable any)` that swallows `ArrayIndexOutOfBoundsException` and returns a benign `false` result, so a naive OOB read is silently converted into "proof verification failed" rather than crashing the node. However, the underlying out-of-bounds *read* (via `System.arraycopy`/`parseInt`) still executes against JVM heap memory belonging to the `data` array's backing buffer/pool before the exception is thrown, which is the same "read before validation" defect class as the CVE. Given that TRON's execution model treats any exception during precompile execution as a failed call (energy still consumed, no crash), the most concrete, provable impact within this codebase is a determinism/DoS-adjacent condition: crafted offsets can trigger heavy/needless allocations (`byte[Integer.MAX_VALUE]`-scale via `spendCount`/`receiveCount` before those are bounds-checked) and repeated `ArrayIndexOutOfBoundsException` handling, but not a direct memory-disclosure primitive to the caller since no data is echoed back on the exception path.

### Likelihood Explanation
Reachable directly by any account triggering a smart contract call to this precompiled contract address with the fixed-size but adversarially-crafted `data` payload — no special privileges are required, matching the CVE's "no additional execution privileges needed" characteristic.

### Recommendation
Validate `spendOffset`, `spendAuthSigOffset`, and `receiveOffset` (and all derived per-item offsets) against `0` and `data.length` before any `parseInt`/`System.arraycopy` call in `VerifyTransferProof.execute()`, mirroring the `verifyLength` bounds check already used in `RLP.decode`/`RLP.decodeList` ( [3](#0-2) ), so malformed offsets are rejected deterministically instead of relying on catching `Throwable`.

### Proof of Concept
Craft calldata of exactly 2080 bytes (the smallest valid `SIZE`) for a `TriggerSmartContract` invocation of the shielded verify-transfer precompile, setting the first 32-byte word (`spendOffset`) to a large value such as `0x000007D0` (2000) or to `0xFFFFFFFF` (interpreted as negative via `parseInt`). This causes `parseInt(data, spendOffset)` at line 1492, or the subsequent `System.arraycopy(data, spendOffset + 320*i + ..., ...)` calls at lines 1514–1518, to read outside the 2080-byte buffer bounds before the surrounding `catch (Throwable any)` intercepts the resulting `ArrayIndexOutOfBoundsException`.
