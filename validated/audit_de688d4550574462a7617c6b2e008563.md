Based on the investigation, the closest concrete gitaly analog to the Arrakis "aggregate check bypassed by fragmenting across multiple independent buckets" bug class is the pack-objects concurrency limiter, which enforces its DoS protection *per remote IP* rather than in aggregate.

### Title
Pack-objects concurrency/resource limiting is bypassable by DoS because it is scoped per remote IP instead of being enforced in aggregate - ([File: internal/gitaly/service/hook/pack_objects.go])

### Summary
Gitaly limits concurrent `git-pack-objects` invocations (spawned to serve fetches/clones) using a `ConcurrencyLimiter` keyed by the client's `remote_ip`, exactly analogous to the Arrakis bug where a protection (slippage/limit check) was applied per independent unit (fee tier) instead of being aggregated across all units that share the same underlying resource. Here, the shared resource is the Gitaly node's CPU/memory used by `git-pack-objects`, but the limit is partitioned per-IP key, so it never bounds the *total* number of concurrently running pack-objects processes on the node.

### Finding Description
`packObjectsHook` computes a cache key and then dispatches to `runPackObjectsLimited`, which calls the concurrency limiter using the caller's IP address string as the limiting key: [1](#0-0) 

`runPackObjectsLimited` passes this `limitkey` straight to `s.packObjectsLimiter.Limit(ctx, limitkey, ...)`: [2](#0-1) 

The `ConcurrencyLimiter.getConcurrencyLimit` lazily creates one independent semaphore per unique key, and each key gets its own full concurrency budget: [3](#0-2) 

The configuration documentation for this feature explicitly states the scoping is per-IP and that this bounds only a *single* IP's concurrency, not the aggregate load on the node: [4](#0-3) 

This is structurally identical to the Arrakis M-3 issue: a protective check (slippage bound / concurrency bound) is correctly enforced *within* one partition (one fee tier / one IP) but is never enforced *across* partitions in aggregate. Just as Alice could split her manipulation across fee tiers to defeat Bob's per-pool slippage check while the aggregate price impact was unconstrained, an attacker can split fetch/clone traffic across many distinct source IPs (trivial with IPv6 address rotation, botnets, or open proxies) so that each individual IP bucket never breaches its limit, while the aggregate number of concurrently running `git-pack-objects` processes on the Gitaly node is effectively unbounded.

### Impact Explanation
`git-pack-objects` is CPU- and memory-intensive. The per-IP semaphore was introduced specifically as a backpressure/DoS-protection mechanism (see `doc/backpressure.md` context and the `PackObjectsLimiting` config), but because there is no complementary aggregate/global cap, an unprivileged remote user who can vary their apparent source IP (e.g., IPv6 prefix rotation, botnet, proxy pool) can spawn effectively unlimited concurrent `git-pack-objects` processes, exhausting CPU/memory on the Gitaly node and causing a denial of service for all repositories and tenants hosted on that node — the same class of impact ("RPC-handler resource limits" bypass) called out as acceptable in the validation criteria.

### Likelihood Explanation
The likelihood is high for an attacker who can present many distinct IPs. `git-upload-pack`/clone/fetch traffic is triggered by ordinary, unprivileged users (no special privilege needed to initiate a fetch), and the limiting key is derived directly from the request's `remote_ip` field with only basic sanity checks (loopback exclusion, best-effort parsing), as shown by the test cases covering malformed/empty/loopback IPs: [5](#0-4) 
No additional aggregate ceiling (e.g., total node-wide in-flight pack-objects count) exists in the reviewed code to catch the case where many distinct keys are used simultaneously.

### Recommendation
In addition to the existing per-IP `ConcurrencyLimiter`, enforce a global/aggregate ceiling on the total number of concurrently running `git-pack-objects` processes (or on aggregate CPU/memory consumed by them) across all keys, similar to how the Arrakis recommendation was to check deposited amounts "in aggregate but grouped by fee tiers." Concretely, wrap `s.packObjectsLimiter.Limit` with (or precede it by) a node-wide semaphore/token bucket that is independent of the per-IP key, so that fragmenting requests across many IPs cannot defeat the overall resource bound.

### Proof of Concept
1. An unprivileged user (or a small botnet / IPv6-rotating client) issues N concurrent `git fetch`/clone requests against a public or authenticated Gitaly-backed repository, each request presenting a distinct `remote_ip` (trivial over IPv6, or via a pool of proxies/NAT egress IPs).
2. Each request lands in `packObjectsHook` → `runPackObjectsLimited`, which computes a limiting key equal to that unique IP (`internal/gitaly/service/hook/pack_objects.go:65-87,176-212`).
3. Because `ConcurrencyLimiter.getConcurrencyLimit` creates an independent semaphore per key (`internal/limiter/concurrency_limiter.go:243-270`), none of the N requests are throttled against each other even though the configured `MaxPerRepo`/concurrency limit (e.g., 200) is meant to bound resource usage.
4. All N `git-pack-objects` invocations run concurrently, consuming node CPU/memory well beyond the intended aggregate ceiling, degrading or crashing the Gitaly node for all hosted repositories.

Note: I was unable to fully trace, within the available tool budget, the exact upstream code path that populates `RemoteIp` on `PackObjectsHookWithSidechannelRequest` (i.e., whether it is derived strictly from a verified TLS/SSH peer address or can be influenced by client-supplied proxy headers in some deployment topologies). This affects how easily an attacker can present many *distinct* apparent IPs versus needing genuinely different network paths. This detail should be confirmed before treating the likelihood as fully "trivial," though the aggregate-vs-per-key structural weakness itself is confirmed directly in the code and configuration comments cited above.

					stdin,

// getConcurrencyLimit retrieves the concurrency limit for the given key. If no such limiter exists
// it will be lazily constructed.
func (c *ConcurrencyLimiter) getConcurrencyLimit(limitingKey string) *keyedConcurrencyLimiter {
	c.m.Lock()
	defer c.m.Unlock()

	if c.limitsByKey[limitingKey] == nil {
		// Set up the queue tokens in case a maximum queue length was requested. As the
		// queue tokens are kept during the whole lifetime of the concurrency-limited
		// function we add the concurrency tokens to the number of available token.
		var queueTokens semaphorer
		if c.maxQueueLength > 0 {
			queueTokens = c.createSemaphore(uint(c.currentLimit() + c.maxQueueLength))
		}

		c.limitsByKey[limitingKey] = &keyedConcurrencyLimiter{
			monitor:               c.monitor,
			maxQueueWait:          c.maxQueueWait,
			setWaitTimeoutContext: c.SetWaitTimeoutContext,
			concurrencyTokens:     c.createSemaphore(uint(c.currentLimit())),
			queueTokens:           queueTokens,
		}
	}

	c.limitsByKey[limitingKey].refcount++

	return c.limitsByKey[limitingKey]
}
