### Title
Unrestricted tar extraction in `untar`/`CreateRepositoryFromSnapshot` allows path traversal / arbitrary file write - (File: internal/gitaly/service/repository/create_repository_from_snapshot.go)

### Summary
`CreateRepositoryFromSnapshot` downloads an archive from an attacker-controllable `HttpUrl` (with optional `HttpAuth` header) and extracts it via `tar -C <path> -xvf -` with no member allowlist, path validation, or `--no-same-owner`/`-P`-style hardening. Unlike `repoutil.ExtractHooks`, which restricts extraction to the single `custom_hooks` member, `untar` passes the archive through unrestricted, so any entry containing `../` segments or an absolute path can write outside the newly created repository directory.

### Finding Description
`s.untar` in `internal/gitaly/service/repository/create_repository_from_snapshot.go:87-121` performs an HTTP GET to `in.GetHttpUrl()` and streams the response body directly into `command.New(ctx, s.logger, []string{"tar", "-C", path, "-xvf", "-"}, command.WithStdin(rsp.Body))`. There is no argument limiting which members are extracted (contrast with `ExtractHooks` in `internal/gitaly/repoutil/custom_hooks.go:55-95`, which passes an explicit `custom_hooks` member name to `tar -xf` so only that top-level directory can be touched). The code comment at lines 140-141 explicitly acknowledges: "the received archive is trusted *a lot*... it should undergo a lot of hardening" before being pointed at endpoints not under Gitaly's control.

`CreateRepositoryFromSnapshot` (lines 123-160) accepts a `CreateRepositoryFromSnapshotRequest` containing `HttpUrl`/`HttpAuth`/`ResolvedAddress` fields directly from the RPC caller, resolves a fresh repo path via `s.locator.GetRepoPath`, and calls `s.untar(ctx, path, in)` with no additional validation of the tar content once it enters `repoutil.Create`. GNU `tar` by default extracts absolute paths and `../` sequences relative to `-C path` unless invoked with restrictive flags, so a crafted archive can write files anywhere the Gitaly process can reach on that filesystem, including into other repositories' `custom_hooks` directories (hook planting) or arbitrary system paths.

### Impact Explanation
This is a full filesystem write primitive scoped to the privileges of the Gitaly process. Concrete impact includes planting `custom_hooks/pre-receive` (or similar) scripts in unrelated repositories to achieve remote code execution on subsequent git operations, overwriting other repositories' Git objects/config, or writing files outside the storage root entirely. This matches the "archive extraction escape" / storage-path escape impact class called out in the audit rules.

### Likelihood Explanation
The precondition is that an unprivileged user can trigger `CreateRepositoryFromSnapshot` with attacker-controlled `HttpUrl`/`HttpAuth`, e.g., through a fork/import/snapshot flow in GitLab Rails that surfaces this field to user input. Whether that precondition holds depends on how GitLab Rails gates and populates this RPC's arguments — this is outside the Gitaly codebase and could not be verified from the repository index alone. If Rails only invokes this RPC for admin-controlled/internal snapshot sources (e.g., trusted internal mirrors), the attack surface described would not be reachable by an unprivileged user, and the code comment itself indicates the intended threat model is "not attacker-controlled" endpoints. Within Gitaly itself, there is no verification, member filtering, or storage-relative path checking (e.g., no `storage.ValidateRelativePath` on extracted entries), so if the precondition holds the exploit is straightforward and deterministic.

### Recommendation
Harden `untar` by extracting to a temporary staging directory first and validating every resulting file path is confined under the target repo path before moving it into place, or invoke tar with restrictive flags/allowlisting (similar to `ExtractHooks`'s member-name restriction) and reject archives containing `../` or absolute-path entries. Alternatively, parse the tar stream in Go and validate each header's `Name` via `filepath.Clean`/`storage.ValidateRelativePath` before writing, rejecting any that escape `path`. Additionally, confirm with GitLab Rails whether unprivileged users can control `HttpUrl` for this RPC, and if so, restrict the RPC to trusted/internal snapshot sources only.
