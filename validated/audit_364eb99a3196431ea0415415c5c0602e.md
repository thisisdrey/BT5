Confirmed: `try_replace_chunk` accepts the `contract_identifier` from the URL path purely to route to the right DB/table, but the signature verification path (`SlotMetadata::verify` / `auth_digest`) only ever covers `slot_id`, `slot_version`, `data_hash` — never the StackerDB contract identifier. This is a direct structural analog of the reported bug.

### Title
StackerDB chunk signatures omit the contract identifier, enabling cross-StackerDB replay of authenticated chunks - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` computes the signed digest as `hash(slot_id || slot_version || data_hash)` and never binds it to the specific StackerDB `QualifiedContractIdentifier` being written to. Any node's StackerDB write path (`try_replace_chunk`) verifies a chunk's signature only against `(slot_id, slot_version, data_hash)` and separately, out-of-band, checks whether the recovered signer address owns that slot *in this particular contract's* config. Since the identity of the target contract is not part of what is actually signed, a chunk validly signed by a signer for one StackerDB replica can be replayed verbatim into any other StackerDB replica where that same signer address happens to own the same `slot_id`, as long as the `slot_version`/freshness gates are also satisfiable there.

### Finding Description
`SlotMetadata::auth_digest()` at [1](#0-0)  builds the digest solely from `slot_id`, `slot_version`, and `data_hash`. `SlotMetadata::verify()` recovers the public key from this digest and only checks it against the caller-supplied `principal` [2](#0-1) .

The write path, `StackerDBTx::try_replace_chunk`, receives the `smart_contract` identifier as a parameter and uses it only to look up the *locally configured* slot owner for that contract, then verifies the signature against that owner — the contract identifier itself never enters the signed digest: [3](#0-2) .

The same absence of contract binding is repeated on the P2P-relay validation path in `StackerDBs::validate_received_chunk`, which resolves the slot owner via `get_slot_signer(smart_contract_id, ...)` and then calls `slot_metadata.verify(&addr)` — again the digest that is checked is contract-agnostic: [4](#0-3) .

The unauthenticated HTTP write endpoint `POST /v2/stackerdb/:address/:contract/chunks` takes the target contract purely from the URL path and forwards the client-supplied `StackerDBChunkData` (whose `sig` field commits to nothing about the contract) straight into `try_replace_chunk`: [5](#0-4) .

As a result, the equality that should hold — "this signature authenticates a chunk write to *this specific StackerDB instance*" — is not actually enforced. It only enforces "this signature authenticates `(slot_id, slot_version, data_hash)` by an address that happens to be configured as owner of `slot_id` in whichever contract the request happens to target." If the same signer key/address is registered as a slot owner in two or more different StackerDB replicas (which is a normal and expected configuration — the same signer's key participates across multiple `.signers-*`-style contracts, `.miners`, and any third-party StackerDB smart contracts that list the same principal as a writer, per `StackerDBConfig::eval_signer_slots`/`parse_slot_entry`: [6](#0-5) ), then a chunk gossiped or fetched from replica A (which any unprivileged network participant can observe, since StackerDB chunks are broadcast/servable to anyone) can be resubmitted byte-for-byte against replica B's `POST .../chunks` endpoint or replayed on the P2P `StackerDBPushChunk` path. If B's slot for that signer is at the same or lower `slot_version`, the write succeeds, causing replica B to store data that was never actually signed with B's context in mind — an unauthorized cross-context write of "foreign" data into a different StackerDB and, if `StackerDBPushChunk` relay is used, propagation of this cross-context forged/misattributed chunk network-wide via `handle_unsolicited_StackerDBPushChunk` and `log_stored_stackerdb_chunk`/relay logic (see the FutureView buffering path that accepts and forwards validly-signed-but-context-independent chunks): [7](#0-6) .

### Impact Explanation
This is an unauthenticated-write/forged-data-propagation class issue: an attacker who observes a legitimately-signed chunk for StackerDB contract A can inject it as authentic content into a different StackerDB contract B, as long as the signer participates in both (a common deployment pattern, since StackerDB slot ownership is driven purely by which principal a Clarity contract's `stackerdb-get-signer-slots` lists — nothing prevents the same address from being listed in multiple contracts). The result is a write that appears validly signed to a consumer of contract B's data, even though the signer never intended nor produced a signature scoped to B. This can propagate over P2P and corrupt/replace state for downstream applications built on the mis-targeted StackerDB, matching the "unauthenticated/unauthorized write to state or StackerDB" / "network-wide propagation of forged data" impact tier.

### Likelihood Explanation
Exploitability requires only: (1) observing a chunk gossiped on a StackerDB the attacker can already read (any StackerDB chunk is servable to any peer/HTTP client), and (2) a target StackerDB contract where the same signer's principal is also registered for the same `slot_id`. This is a realistic scenario in the Stacks ecosystem because the same signer/miner keys are commonly reused across several boot and application StackerDB instances. No secret keys, admin roles, or the node's own signing key are needed — an unprivileged network observer/HTTP client can perform the replay.

### Recommendation
Bind the StackerDB contract identifier (the `QualifiedContractIdentifier`, i.e., the StackerDB's "instance address") into the signed digest, analogous to including `safeAddress`/`address(this)` in the reported PayrollManager fix. Concretely, extend `SlotMetadata::auth_digest()` (and correspondingly `sign()`/`verify()`) to also hash the contract's issuer address and name (or a chain/network ID plus contract identifier) before hashing `slot_id`, `slot_version`, and `data_hash`, and thread the contract identifier through `try_replace_chunk` and `validate_received_chunk` so verification is performed against the digest that includes it.

### Proof of Concept
1. Deploy (or use existing) StackerDB contracts A and B whose `stackerdb-get-signer-slots` both list the same signer address `S` for `slot_id = 0`.
2. Signer `S` legitimately signs `StackerDBChunkData{slot_id:0, slot_version:1, data:D}` for contract A and it is stored/gossiped, as in `try_replace_chunk` [8](#0-7) .
3. An observer captures this chunk (e.g., via `GET` chunk endpoint or P2P gossip) and resubmits the identical `(slot_id=0, slot_version=1, sig, data=D)` tuple via `POST /v2/stackerdb/<B-address>/<B-contract>/chunks`.
4. Because `try_replace_chunk`'s signature check only verifies `slot_metadata.verify(&slot_validation.signer)` against B's locally-configured owner of slot 0 — and never checks that the signature was produced with contract B (rather than A) in mind — the write succeeds against contract B if B's slot 0 version requirement is met, as shown by the passing `try_replace_chunk`/`BadSlotSigner` test flow that only fails when the *address*, not the *contract*, mismatches: [9](#0-8) .

    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);

    fn parse_slot_entry(
        entry: ClarityValue,
        contract_id: &QualifiedContractIdentifier,
    ) -> Result<(StacksAddress, u32), String> {
        let ClarityValue::Tuple(slot_data) = entry else {
            let reason = format!(
                "StackerDB fn `{contract_id}.{STACKERDB_SLOTS_FUNCTION}` returned non-tuple slot entry",
            );
            return Err(reason);
        };

        let Ok(ClarityValue::Principal(signer_principal)) = slot_data.get("signer") else {
            let reason = format!(
                "StackerDB fn `{contract_id}.{STACKERDB_SLOTS_FUNCTION}` returned tuple without `signer` entry of type `principal`",
            );
            return Err(reason);
        };

        let Ok(ClarityValue::UInt(num_slots)) = slot_data.get("num-slots") else {
            let reason = format!(
                "StackerDB fn `{contract_id}.{STACKERDB_SLOTS_FUNCTION}` returned tuple without `num-slots` entry of type `uint`",
            );
            return Err(reason);
        };

        let num_slots = u32::try_from(*num_slots)
            .map_err(|_| format!("Contract `{contract_id}` set too many slots for one signer (max = {STACKERDB_INV_MAX})"))?;
        if num_slots > STACKERDB_INV_MAX {
            return Err(format!("Contract `{contract_id}` set too many slots for one signer (max = {STACKERDB_INV_MAX})"));
        }

        let PrincipalData::Standard(standard_principal) = signer_principal else {
            return Err(format!(
                "StackerDB contract `{contract_id}` set a contract principal as a writer, which is not supported"
            ));
        };
        let addr = StacksAddress::from(standard_principal.clone());
        Ok((addr, num_slots))
    }
