### Title
Unbounded array allocation from unvalidated length field in TVM precompiled-contract array extraction helpers - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The precompiled-contract helper methods `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` in `PrecompiledContracts.java` read a 32-byte word from attacker-supplied TVM call data and use it directly as an array length to allocate `byte[][]` without validating it against the actual size of the input buffer, mirroring the HDF5 `H5O__chunk_deserialize()` pattern of trusting a crafted length field to drive an allocation.

### Finding Description
`extractBytes32Array` reads `len = words[offset].intValueSafe()` and immediately allocates `new byte[len][]` with no upper bound check against `words.length` or `data.length`: [1](#0-0) 

The same unvalidated pattern repeats in `extractBytesArray`: [2](#0-1) 

and in `extractSigArray`, which is used to build the signature list for a multi-signature verification precompile: [3](#0-2) 

In all three cases, `len` comes from `DataWord.intValueSafe()`, which only bounds the value to the `int` range (up to `Integer.MAX_VALUE`) but performs no comparison against the actual remaining `data`/`words` length before the `new byte[len][]` allocation is attempted. This is functionally analogous to the HDF5 bug: a length taken from crafted/untrusted input is used to size a buffer allocation before the input is validated to actually contain that much data, leading to attacker-controlled, effectively unbounded memory allocation.

### Impact Explanation
A crafted TVM call into the precompiled contract that uses these helpers (multi-signature/batch-validate-sign style precompile, as referenced by `BatchValidateSignContractTest`/`ValidateMultiSignContractTest`) can supply a 32-byte word whose integer value is very large (up to `Integer.MAX_VALUE`). This forces the JVM to attempt allocating a `byte[][]` with billions of reference slots, which will throw `OutOfMemoryError` or consume large amounts of heap/GC pressure on the node executing the transaction. If this exception is not caught precisely at the allocation site (I was not able to fully trace and confirm the outer catch blocks around every call site within the remaining tool budget), it can propagate and disrupt block/transaction processing, resulting in a denial-of-service condition consistent with the "memory consumption" impact class of CVE-2018-17234.

### Likelihood Explanation
Any unprivileged account can construct and broadcast/execute a smart-contract call whose input data reaches this precompiled contract address with an attacker-chosen length word, requiring no special privileges, staking, or SR/witness status — only the ability to send a transaction that triggers a `CALL` to the precompile.

### Recommendation
Add explicit bounds checks in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` so that `len` (and any subsequently derived offsets/lengths such as `bytesOffset`, `bytesLen`) is validated against `words.length` / `data.length` before any array is allocated, returning an empty/invalid result (as already done for the `offset > words.length - 1` case) instead of allocating based on unchecked attacker-controlled values.

### Proof of Concept
1. Construct a transaction that performs a TVM `CALL`/`STATICCALL` to the batch-signature-validation precompiled contract address.
2. Craft the call data so that the word at the expected `len` offset (consumed by `extractBytes32Array`/`extractBytesArray`/`extractSigArray`) decodes to a large positive integer (e.g., close to `Integer.MAX_VALUE`), while the rest of the call data is minimal/short.
3. Broadcast the transaction; the precompiled contract's `execute()` path calls the vulnerable helper, which executes `new byte[len][]` with the attacker-supplied `len`, triggering excessive memory allocation/`OutOfMemoryError` on the executing node.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
