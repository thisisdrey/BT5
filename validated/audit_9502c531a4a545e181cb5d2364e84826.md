#No vulnerability found for this question.

The concern is not applicable to the current code. `AccessKeyPermission` is a plain Rust enum with exactly four variants (`FunctionCall`, `FullAccess`, `GasKeyFunctionCall`, `GasKeyFullAccess`), and `gas_key_info()`/`gas_key_info_mut()` match on it exhaustively — the Rust compiler enforces exhaustiveness at compile time, so there is no code path where an unmatched/ambiguous variant could fall through [1](#0-0) . Borsh deserialization of this enum uses discriminant-tagged variants; an unrecognized discriminant byte causes a hard deserialization error rather than being coerced into an existing variant, so there is no "borderline/edge permission encoding" that a wallet or the runtime could parse differently [2](#0-1) . The premise requires a "future/forked protocol enum discriminant not yet exhaustively matched," which is speculative and not a defect reachable in the current codebase — any such change would itself require a protocol/schema change reviewed independently, not something an unprivileged attacker can trigger via a crafted `AddKeyAction`. `action_add_key` and `add_gas_key` correctly route only the two gas-key variants through the nonce-zeroing path, and `add_regular_key` handles the two non-gas variants with `initial_nonce_value` [3](#0-2) [4](#0-3) [5](#0-4) .

    pub fn gas_key_info(&self) -> Option<&GasKeyInfo> {
        match &self.permission {
