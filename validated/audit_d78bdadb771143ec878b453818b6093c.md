Audit Report

## Title
Reward accounting assumes full requested amount is minted on destination without verifying actual XCM-execution outcome - ([File: bridges/snowbridge/primitives/core/src/reward.rs])

## Summary
`pallet_bridge_relayers::do_claim_rewards` (`bridges/modules/relayers/src/lib.rs`, called via the public `claim_rewards_to` extrinsic) removes the relayer's `RelayerRewards` entry and emits `RewardPaid` for the full `reward_balance` as soon as `T::PaymentProcedure::pay_reward` returns `Ok(())`. For Snowbridge, `pay_reward` is `PayAccountOnLocation::pay_reward`, which returns `Ok(())` once `XcmSender::deliver(ticket)` succeeds, without any confirmation that the `DepositAsset` instruction actually executed successfully on AssetHub for the full requested amount.

## Finding Description
`do_claim_rewards` at [1](#0-0)  takes the stored `reward_balance` via `try_mutate_exists` (which deletes the entry once the closure returns `Ok`), invokes `PaymentProcedure::pay_reward`, and on success emits `RewardPaid { reward_balance, .. }` for the full amount — this bookkeeping is irreversible and is reached from the public, signed extrinsic `claim_rewards_to` at [2](#0-1) , callable by any registered relayer with an accumulated reward.

For Snowbridge rewards, `PayAccountOnLocation::pay_reward` at [3](#0-2)  builds an `UnpaidExecution` XCM containing `ReserveAssetDeposited`/`DepositAsset` for the full `reward` amount to `beneficiary`, charges only the delivery fee from the relayer, and calls `XcmSender::deliver(ticket)`. The function returns `Ok(())` purely based on successful message *delivery* — it does not wait for or verify execution success on AssetHub (e.g., via a receipt/ack). If `DepositAsset` fails at the destination (beneficiary account can't be created due to existential deposit requirements, the foreign asset isn't registered/sufficient, weight limits are exceeded, or the message is otherwise dropped/fails to execute), BridgeHub has already deleted `RelayerRewards` and emitted `RewardPaid`, permanently erasing any on-chain record that the relayer is owed that amount.

## Impact Explanation
This matches the "permanent user-fund lock" / "settle exactly once to the rightful beneficiary and amount" impact category: `RelayerRewards` storage is cleared and `RewardPaid` is emitted claiming full settlement, yet the actual reward asset may never be deposited to the beneficiary on AssetHub, and there is no state left from which to retry or reclaim it. The exact corrupted value is the `RelayerRewards<T,I>` double-map entry for `(relayer, reward_kind)` — it is deleted based on XCM send success rather than confirmed execution/deposit success.

## Likelihood Explanation
The failure path requires only ordinary, non-malicious conditions at the destination chain (AssetHub) — e.g. a beneficiary account/location that cannot satisfy existential deposit, an unregistered/insufficient foreign asset, or transient execution/weight issues — none of which require a compromised relayer, validator, or off-chain infrastructure. The relayer's own call to the public `claim_rewards_to` extrinsic with an ordinary AssetHub beneficiary is sufficient to trigger it; this is a legitimate, unprivileged, reachable code path rather than a "malicious peer/relayer" scenario, satisfying the rule that "existing guards reviewed and shown insufficient" (there is no receipt/confirmation mechanism at all in `pay_reward`).

## Recommendation
Do not treat `XcmSender::deliver` success as final settlement of the reward. Options: (1) use a receipted/acknowledged delivery mechanism (e.g., XCM query/report, or a callback message from AssetHub back to BridgeHub) and only clear `RelayerRewards` once destination-side execution success is confirmed; or (2) move the entry to a "pending confirmation" state instead of deleting it outright in `do_claim_rewards`, allowing retry/reclaim on execution failure rather than eagerly finalizing based solely on `pay_reward` returning `Ok(())` for what is effectively a fire-and-forget XCM send.

## Proof of Concept
1. Relayer accumulates `reward_balance = X` under a Snowbridge `T::Reward` kind in `RelayerRewards` via prior message-delivery confirmations (`register_reward`/equivalent).
2. Relayer calls the public `claim_rewards_to` extrinsic with a `beneficiary` location on AssetHub corresponding to a fresh account with no existing balance sufficient to satisfy existential deposit for the reward's foreign asset (or where that foreign asset is not yet registered/sufficient on AssetHub).
3. `do_claim_rewards` invokes `PayAccountOnLocation::pay_reward`; `validate_send` succeeds, `XcmExecutor::charge_fees` charges only the delivery fee from the relayer, and `XcmSender::deliver(ticket)` succeeds, so `pay_reward` returns `Ok(())` — see [4](#0-3) .
4. Back on BridgeHub, `do_claim_rewards` sees `Ok(())`, so `try_mutate_exists` permanently deletes the `RelayerRewards` entry and emits `RewardPaid { reward_balance: X, .. }` — see [5](#0-4) .
5. On AssetHub, the `DepositAsset` instruction fails (e.g., account cannot be created due to ED, or asset deposit fails); the relayer never receives `X`, yet BridgeHub records it as fully paid with no remaining state to retry or recover the reward.

		fn do_claim_rewards(
			relayer: T::AccountId,
			reward_kind: T::Reward,
			beneficiary: BeneficiaryOf<T, I>,
		) -> DispatchResult {
			RelayerRewards::<T, I>::try_mutate_exists(
				&relayer,
				reward_kind,
				|maybe_reward| -> DispatchResult {
					let reward_balance =
						maybe_reward.take().ok_or(Error::<T, I>::NoRewardForRelayer)?;
					T::PaymentProcedure::pay_reward(
						&relayer,
						reward_kind,
						reward_balance,
						beneficiary.clone(),
					)
					.map_err(|e| {
						tracing::error!(
							target: LOG_TARGET,
							error=?e,
							?relayer,
							?reward_kind,
							?reward_balance,
							?beneficiary,
							"Failed to pay rewards"
						);
						Error::<T, I>::FailedToPayReward
					})?;

					Self::deposit_event(Event::<T, I>::RewardPaid {
						relayer: relayer.clone(),
						reward_kind,
						reward_balance,
						beneficiary,
					});
					Ok(())
				},
			)

	fn pay_reward(
		relayer: &Relayer,
		_: (),
		reward: RewardBalance,
		beneficiary: Self::Beneficiary,
	) -> Result<(), Self::Error> {
		let ethereum_location = Location::new(2, [GlobalConsensus(EthereumNetwork::get())]);
		let assets: Asset = (ethereum_location.clone(), reward.into()).into();

		let xcm: Xcm<()> = alloc::vec![
			UnpaidExecution { weight_limit: Unlimited, check_origin: None },
			DescendOrigin(InboundQueueLocation::get().into()),
			UniversalOrigin(GlobalConsensus(EthereumNetwork::get())),
			ReserveAssetDeposited(assets.into()),
			DepositAsset { assets: AllCounted(1).into(), beneficiary },
		]
		.into();

		let (ticket, fee) =
			validate_send::<XcmSender>(AssetHubLocation::get(), xcm).map_err(|_| XcmSendFailure)?;
		XcmExecutor::charge_fees(relayer.clone(), fee).map_err(|_| ChargeFeesFailure)?;
		XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;

		Ok(())
	}
