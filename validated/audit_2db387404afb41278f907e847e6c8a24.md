### Title
Unstaked attacker can starve TPU connection admission by repeatedly opening QUIC connections that never complete the handshake, since rate limiters are only charged after handshake completion - ([File: streamer/src/nonblocking/quic.rs])

### Summary
`ClientConnectionTracker::new` admits a connection into the global `open_connections` slot pool (`qos.max_concurrent_connections()`) as soon as a QUIC `Incoming` is accepted, before any handshake has completed. The per-IP (`ConnectionRateLimiter`) and global (`overall_connection_rate_limiter`) rate limiters are only *consumed* in `setup_connection` after a handshake succeeds, so an attacker who never completes the handshake never gets rate-limited and can cycle through `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` (2s) windows indefinitely, repeatedly occupying the bounded connection-admission slots.

### Finding Description
In the accept loop [1](#0-0) , the overall rate limiter is only checked via `current_tokens() == 0` (a non-mutating peek) and the per-IP limiter is checked via `rate_limiter.is_allowed(...)`, which also does not consume a token — it only returns `true`/`false` based on tokens already consumed elsewhere. `ClientConnectionTracker::new(stats.clone(), qos.max_concurrent_connections())` [2](#0-1)  is then called and, if the global `open_connections` count is under the max, a slot is reserved and `incoming.accept()` is invoked, spawning `setup_connection`.

Only inside `setup_connection`, **after** the QUIC handshake actually succeeds, do the rate limiters get mutated: `rate_limiter.register_connection(&from.ip())` and `overall_connection_rate_limiter.consume_tokens(1)` [3](#0-2) . This is explained by the comment that address ownership can't be trusted until the handshake completes (anti IP-spoofing measure) [4](#0-3) .

The consequence: an attacker who deliberately never completes the handshake (or delays it) never triggers `register_connection`/`consume_tokens`, so neither the per-IP nor the global rate limiter is ever decremented for their attempts. They can repeatedly send fresh QUIC `Initial` packets, each of which is accepted into a `ClientConnectionTracker` slot (bounded only by `qos.max_concurrent_connections()`, with no per-IP cap at this stage), held for the full `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` = 2 seconds [5](#0-4) , then freed via the `timeout(...)` branch in `setup_connection` and the `ClientConnectionTracker`'s `Drop` impl [6](#0-5) [7](#0-6) . The attacker can immediately reopen a similar number of connections in the next 2-second window, keeping most/all of `qos.max_concurrent_connections()` slots perpetually occupied by non-completing handshakes.

Legitimate clients attempting to connect during this window will fail `ClientConnectionTracker::new` and hit the refusal path, incrementing `refused_connections_too_many_open_connections` and calling `incoming.refuse()` [8](#0-7) .

### Impact Explanation
This is a QoS-evasion / TPU admission-starvation DoS: an unstaked, unprivileged remote client can deny `refused_connections_too_many_open_connections` headroom to legitimate handshakers, preventing staked/legitimate senders from establishing QUIC connections to submit transactions to the leader's TPU. This matches the "unfairly capture connection/stream/QoS limits and starve legitimate senders of TPU capacity" bounty category, since the admission-control mechanism (`ClientConnectionTracker` + rate limiters) is bypassed specifically because rate-limiter accounting is deferred until after handshake success.

### Likelihood Explanation
Feasible with a single unstaked attacker machine: no valid keypair, stake, or leader control is required — only the ability to open QUIC/UDP `Initial` packets to the public TPU port and refuse to progress the handshake (or intentionally stall it, e.g., not responding to the server's Handshake flight). The attack is fully repeatable every `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` (2s) cycle, and because rate limiters aren't charged for incomplete handshakes, this can be sustained indefinitely without the attacker's own request rate ever being throttled by `ConnectionRateLimiter` or `overall_connection_rate_limiter`.

### Recommendation
Reserve a portion of `qos.max_concurrent_connections()` slot admission behind a lightweight, pre-handshake resource accounting mechanism that is charged on *acceptance* (not just on handshake success) — e.g., consume from the per-IP/global token buckets at the same time the `ClientConnectionTracker` slot is reserved, and refund the token only when it's later confirmed the peer needed protection against spoofing (or use a separate, coarser pre-handshake attempt limiter keyed by IP or 24 subnet, decoupled from the post-handshake anti-spoofing limiter). Alternatively, reduce `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` further for the specific admission-slot hold, or require QUIC Retry (address validation) for all connections above a configurable pending-handshake threshold so that pre-handshake slot consumption inherently requires proof of address ownership.

```rust
#[tokio::test(flavor = "multi_thread")]
async fn test_incomplete_handshake_starves_legit_clients() {
    let SpawnTestServerResult {
        join_handle, server_address, stats, cancel, ..
    } = setup_quic_server(
        None,
        QuicStreamerConfig::default_for_tests(), // small max_concurrent_connections via SwQosConfig
        SwQosConfig {
            max_staked_connections: 2,
            max_unstaked_connections: 2, // => max_concurrent_connections = 5 (2+2)*5/4
            ..Default::default()
        },
    );

    // Attacker: repeatedly open raw UDP sockets sending QUIC Initial packets
    // to server_address but never respond to the server's Handshake flight,
    // looping every QUIC_CONNECTION_HANDSHAKE_TIMEOUT - epsilon.
    let attacker = tokio::spawn(async move {
        loop {
            for _ in 0..5 {
                // send_incomplete_quic_initial(server_address) - crafted Initial packet,
                // never completes handshake
                send_incomplete_quic_initial(server_address).await;
            }
            tokio::time::sleep(Duration::from_millis(1900)).await; // just under 2s timeout
        }
    });

    // Legitimate client attempts a real handshake during the attack window.
    let legit_result = tokio::time::timeout(
        Duration::from_secs(5),
        make_client_endpoint(&server_address, None),
    ).await;

    attacker.abort();
    cancel.cancel();
    join_handle.await.unwrap();

    // Expect this assertion to FAIL under the vulnerability: legitimate client
    // should succeed promptly, but refused_connections_too_many_open_connections
    // stays elevated while attacker cycles slots.
    assert!(legit_result.is_ok(), "legitimate client starved of connection slots");
    assert_eq!(
        stats.refused_connections_too_many_open_connections.load(Ordering::Relaxed),
        0,
        "legitimate handshakers should not be refused due to incomplete-handshake slot squatting"
    );
}
```
Expected result on the vulnerable code: `refused_connections_too_many_open_connections` increases and the legitimate client's connection attempt times out or is delayed well past normal latency, demonstrating that non-completing handshakes evade rate-limiting and monopolize `ClientConnectionTracker` slots.
