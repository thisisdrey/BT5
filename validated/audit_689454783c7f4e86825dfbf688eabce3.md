### Title
`VerifyTransferProof` precompile ignores CPU-time-limit wait result, bypassing OutOfTime enforcement for shielded-transfer proof verification - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The Sapling `VerifyTransferProof` precompile (invoked from TVM `STATICCALL`/`CALL` by any smart-contract transaction using the shielded-transfer verify precompile address) submits multiple zk-proof/signature verification tasks to a thread pool and waits on a `CountDownLatch` bounded by the remaining CPU-time budget for the transaction. The boolean result of that bounded wait (`withNoTimeout`) is computed but never checked, unlike the sibling `BatchValidateSign` precompile which correctly throws `Program.Exception.notEnoughTime(...)` when the wait times out.

### Finding Description
`getCPUTimeLeftInNanoSecond()` [1](#0-0)  returns the CPU-time budget remaining for the current VM execution and throws if it is already exhausted. `BatchValidateSign` uses the result of `countDownLatch.await(...)` correctly: if the wait times out, it explicitly throws `notEnoughTime` to enforce the CPU budget [2](#0-1) .

In contrast, `VerifyTransferProof.execute()` computes the identical `withNoTimeout` value from `countDownLatch.await(getCPUTimeLeftInNanoSecond(), TimeUnit.NANOSECONDS)` but discards it — the code immediately proceeds to iterate `futures` and call the blocking, no-timeout `future.get()` regardless of whether the CPU budget had already elapsed [3](#0-2) . This mirrors the CVE-2026-64148 bug class: a wait/poll result signaling that the operation did not complete/succeed in time is computed and then silently ignored, letting execution continue as if nothing were wrong (analogous to `pdsc_devcmd_wait` ignoring `!running`/timeout and returning stale success).

Because `future.get()` has no timeout, the call will block until every `SaplingCheckSpendTask`/`SaplingCheckOutputTask`/`SaplingCheckBingdingSig` task actually finishes on the shared `workersInConstantCall`/`workersInNonConstantCall` pools [4](#0-3) , completely bypassing the transaction's CPU-time budget (`vmShouldEndInUs`) that `checkCPUTimeLimit`/`notEnoughTime` are designed to enforce elsewhere in the VM interpreter loop [5](#0-4) . The precompile itself has no opcode-level time check once it enters this code path.

### Impact Explanation
A contract caller can invoke this precompile with a small number of expensive zk-proof verification tasks that saturate the fixed-size thread pools (5 workers each for constant/non-constant calls) and take longer than the transaction's normal CPU budget, or can craft calls that queue behind other in-flight verifications. Because the timeout is never enforced, execution of this single precompile call can run far past the intended per-transaction CPU deadline that every other opcode/precompile respects. Repeated or concurrent abuse can starve the fixed thread pools and extend per-transaction/per-block execution well beyond the CPU-time budget designed to bound block-production latency, risking degraded block production or a denial-of-service condition on validating nodes (a "node crash or halt"-class impact per the accepted categories), since the shared executor and CPU accounting invariant relied upon elsewhere in the VM is violated only in this precompile.

### Likelihood Explanation
The precompile is reachable from any signed transaction that triggers a smart contract calling the Sapling `VerifyTransferProof` precompile address with attacker-controlled shielded-transfer proof data — no special privilege is required. Exploitation only requires crafting/submitting proof data sized to pass the length checks; the actual cryptographic validity of individual proofs is irrelevant to triggering the unchecked-timeout path since the wait/ignore code runs before any correctness check is evaluated. This makes the trigger straightforward for any transaction broadcaster/contract deployer.

### Recommendation
After computing `withNoTimeout = countDownLatch.await(getCPUTimeLeftInNanoSecond(), TimeUnit.NANOSECONDS)` in `VerifyTransferProof.execute()`, check the result and throw `Program.Exception.notEnoughTime("call VerifyTransferProof precompile method")` when `false`, mirroring the existing `BatchValidateSign` handling, before calling `future.get()` on the submitted tasks. Additionally consider cancelling outstanding futures on timeout to release thread-pool capacity promptly.

### Proof of Concept
1. Deploy/trigger a smart contract that calls the Sapling `VerifyTransferProof` precompile with a maximal-size well-formed shielded-transfer payload (`spendCount`/`receiveCount` = 2, valid structural offsets) inside a transaction whose remaining CPU budget (`vmShouldEndInUs`) is nearly exhausted by prior opcodes/precompile calls in the same call frame.
2. Because `countDownLatch.await(getCPUTimeLeftInNanoSecond(), ...)` will return `false` (timeout) but the return value is discarded, execution proceeds to `future.get()` for each of the `spendCount + receiveCount + 1` submitted tasks, blocking until the librustzcash native verification calls complete — well past the CPU deadline that should have raised `OutOfTimeException`.
3. Submit several such transactions concurrently to saturate the shared `workersInNonConstantCall` (5-thread) pool, further amplifying execution latency for all pending shielded-transfer verifications and exceeding the intended per-block CPU-time enforcement. [3](#0-2)
