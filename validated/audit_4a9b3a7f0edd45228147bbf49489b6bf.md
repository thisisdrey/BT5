### Title
Unauthenticated `RecvError` packets allow remote tunnel teardown without any CA-signed certificate - (File: `outside.go`)

### Summary
Nebula's `RecvError` message type is processed before any certificate/handshake authentication occurs, and it directly mutates connection state (tearing down an active tunnel) based only on an unauthenticated UDP packet and a source-address comparison. This mirrors the reported Earning.sol bug class: a state-mutating operation (`update()` / here, `closeTunnel()` + `DeleteHostInfo()`) that is reachable without the access-control guarantee the protocol relies on elsewhere (an `onlyAdmin` modifier / a verified certificate), letting an attacker manipulate protocol state that is supposed to be trust-gated.

### Finding Description
In `readOutsidePackets`, packet types are dispatched before decryption or peer-certificate verification. `header.Handshake` and `header.RecvError` are both handled as "Unencrypted packets" prior to any lookup requiring `hostinfo.ConnectionState`: [1](#0-0) 

The `RecvError` path leads to `handleRecvError`, which looks up the hostinfo purely from `h.RemoteIndex` (a 32-bit value that travels in cleartext on the wire during handshakes) and only checks that the packet's source address matches the currently known remote address before tearing the tunnel down: [2](#0-1) 

No cryptographic authentication (no CA-pool verification, no cert, no MAC/AEAD tag) is required to trigger this — only knowledge of a `RemoteIndex` and the ability to source a UDP packet from (or spoof) the peer's `addr:port`. This is analogous to the Earning.sol `update()` bug: a function that should only be reachable by a trusted/verified party (there, `onlyAdmin`; here, a cryptographically authenticated peer) is instead reachable by anyone who can construct the right wire-format packet, allowing them to directly manipulate protocol state (tunnel/hostmap state) that the rest of the system treats as trustworthy.

### Impact Explanation
An attacker who can observe or guess a live `RemoteIndex` (these are exchanged in cleartext handshake headers and are only 32 bits) and who can spoof or send from the peer's UDP source address can force `closeTunnel()` and `handshakeManager.DeleteHostInfo()` on a victim, tearing down an established, authenticated tunnel. This is a remote state-poisoning / denial-of-service primitive that requires no valid certificate at all, unlike the rest of Nebula's control-plane messages (handshake continuation, lighthouse updates, relay control) which all require a verified peer certificate before they can influence state.

### Likelihood Explanation
The likelihood is gated by `acceptRecvErrorConfig.ShouldRecvError(addr)` (an allow/rate-limit config in `interface.go`) and by the source-address equality check, so this is not trivially exploitable by an arbitrary off-path attacker without also being able to spoof the peer's source UDP address or being rate-limit-exempt. This significantly reduces exploitability compared to the Earning.sol case where `update()` had zero access control. Given the additional config-gating and the address-match requirement, this analog is weaker/partial and should be treated as a design-level unauthenticated-DoS surface rather than a full authentication bypass.

### Recommendation
Require the `RecvError` message to be tied to a nonce/MAC bound to the actual tunnel session (e.g., authenticate it under the existing session key, similar to `VerifyRelay`) rather than accepting an unauthenticated, address-matched signal to tear down state. At minimum, ensure `acceptRecvErrorConfig` defaults are conservative and rate-limited, and consider requiring the packet to also prove knowledge of the current handshake/session key before honoring the teardown.

### Proof of Concept
1. Observe (or be told, via a spoofed replay of) a handshake between `me` and `them`, learning `them`'s current `RemoteIndex` value used by `me`, which is sent in cleartext in handshake/message headers.
2. From an attacker-controlled host that can spoof `them`'s UDP source `addr:port` (or is otherwise unfiltered on the path), send a crafted `header.RecvError` packet to `me` with `RemoteIndex` set to the observed index, as built by `sendRecvError`: [3](#0-2) 
3. `me` calls `handleRecvError`, finds the hostinfo via `QueryReverseIndex`, sees the spoofed address matches the expected remote, and calls `f.closeTunnel(hostinfo)` plus `f.handshakeManager.DeleteHostInfo(hostinfo)`, tearing down the tunnel without any certificate or handshake authentication from the attacker: [4](#0-3)

func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
