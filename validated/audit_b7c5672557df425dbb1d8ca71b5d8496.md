Confirmed root-cause finding.

### Title
Deposit function permits minting 0 shares while accepting underlying deposit, permanently freezing depositor funds - ([File: mainnet/contracts/vault/v0-vault-stx.clar])

### Summary
The `deposit` function in each Zest vault contract (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`) computes shares to mint via `convert-to-shares-preview`, which performs `amount * total-supply / total-assets` with truncating (floor) division and no minimum-output check like the one present in `redeem`. This mirrors the C4 `IdleYieldSource` H-05 bug class: rounding-down share math without a zero-output guard can zero out shares owed to a depositor while their underlying assets are still pulled into the vault.

### Finding Description
`convert-to-shares-preview` is defined identically across all vaults: [1](#0-0) 
This uses `mul-div-down amount ts ta` (i.e. `amount * total_supply / total_assets`), truncating toward zero. When `total-assets` (`ta`) has grown large relative to `total-supply` (`ts`) — the expected steady state for an interest-accruing vault where the liquidity index rises above 1.0 — a sufficiently small `amount` deposit can compute to `0` shares.

The `deposit` function then only validates against `min-out`, which defaults to caller-supplied value (commonly `0` for a naive integrator or a script that doesn't anticipate rounding): [2](#0-1) 
Specifically: [3](#0-2) 
There is no `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)` check in `deposit`, unlike `redeem`, which explicitly guards against a zero output: [4](#0-3) 
Because `deposit` calls `receive-underlying` and `ft-mint?` unconditionally once the `min-out` check passes, a deposit that rounds down to `inkind = 0` will still: (1) pull the user's underlying tokens into the vault (`receive-underlying amount account`), (2) mint `0` zTokens to the recipient (`ft-mint? zft 0 recipient` — a no-op mint), and (3) increase `assets` by the full deposited `amount`. The depositor's underlying tokens are absorbed into the vault's `assets` accounting and become instantly redistributable to all existing shareholders (their share price effectively increases at the depositor's expense), while the depositor receives literally nothing in return — no zTokens to redeem later.

This is directly analogous to the IdleYieldSource bug class: rounding-down share math without an output floor, letting depositors get zero shares for a nonzero deposit.

### Impact Explanation
This lands squarely in the in-scope **High** impact category: temporary/permanent freezing of funds — here it is effectively **permanent loss** of the depositor's principal (not merely yield), because the depositor receives 0 shares and thus has no claim to redeem back their contributed underlying; the deposited amount is absorbed into the vault and effectively donated to existing shareholders. This can occur unintentionally for any depositor who does not manually compute a nonzero `min-out`, particularly on vaults where the liquidity index (`total-assets/total-supply` ratio) has grown large after prolonged interest accrual (e.g. `sbtc` with 8 decimals, or any vault long after launch).

### Likelihood Explanation
Likelihood is proportional to how far the liquidity index has drifted from 1.0 and how small a deposit is attempted. Because vaults accrue interest indefinitely and reserve funds are minted continuously to `dao-treasury`, `total-assets` can grow substantially relative to `total-supply` over time. A user (or an integrating contract) that submits a small deposit amount with `min-out = 0` (the common default for a "no slippage protection needed for exact-in deposit" mental model) is exposed. This does not require any privileged action or DAO misconfiguration — it is triggerable by any ordinary depositor's own transaction under natural vault-aging conditions.

### Recommendation
Add an explicit zero-output guard in every vault's `deposit` function, mirroring the pattern already used in `redeem`:
```clarity
(asserts! (> inkind u0) ERR-OUTPUT-ZERO)
```
placed alongside the existing `min-out` slippage check in `deposit`, for all six vaults (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`).

### Proof of Concept
1. Let a vault reach a state where `total-assets = 2_000_000` (underlying units) and `total-supply = 1_000_000` (shares), i.e. share price = 2.0.
2. A user calls `deposit(1, 0, recipient)` (deposits `1` unit of underlying, `min-out = 0`).
3. `convert-to-shares-preview(1)` computes `mul-div-down(1, 1_000_000, 2_000_000)` = `1 * 1_000_000 / 2_000_000` = `0` (integer division floors to `0`).
4. `deposit` asserts `(>= inkind min-out)` → `(>= 0 0)` → passes.
5. `receive-underlying(1, account)` transfers the user's `1` unit of underlying into the vault.
6. `ft-mint? zft 0 recipient` mints `0` shares to the recipient.
7. `assets` is incremented by `1`.
8. Result: the user's `1` unit of underlying is now part of vault `assets` and benefits all existing shareholders' redemption value, but the depositor holds `0` zTokens and cannot redeem any of it back. [5](#0-4) [2](#0-1)
