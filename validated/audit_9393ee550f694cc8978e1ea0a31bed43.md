### Title
Unauthenticated RecvError packet allows one-step, unconfirmed remote tunnel teardown - (File: `outside.go`)

### Summary
Nebula's `RecvError` packet type is processed before any cryptographic authentication (before handshake completion checks or AEAD decryption), and a single such packet causes the receiver to immediately and irrevocably tear down an active tunnel (`closeTunnel` + `handshakeManager.DeleteHostInfo`). This mirrors the "lack of a two-step process" bug class from the external report: a single unauthenticated message triggers a privileged, irreversible state change with no confirmation step, opening the door to a remote, unauthenticated denial-of-service/state-poisoning primitive.

### Finding Description
In `readOutsidePackets`, `header.RecvError` is dispatched immediately after basic header parsing/version checks, in the same branch as `header.Handshake` — i.e., before the code path that requires an existing authenticated `ConnectionState` and successful AEAD decryption: [1](#0-0) 

```go
switch h.Type {
case header.Handshake:
    f.handshakeManager.HandleIncoming(via, packet, h)
    return

case header.RecvError:
    f.handleRecvError(via.UdpAddr, h)
    return
}
```

`handleRecvError` then performs the actual "ownership transfer"-style irreversible action in one step: [2](#0-1) 

```go
func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		...
		return
	}
	...
	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		...
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?", ...)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
```

The only gate protecting this action is:
1. `acceptRecvErrorConfig` — defaults to `recvErrorAlways` (accept from anywhere) unless explicitly configured otherwise [3](#0-2) .
2. A comparison of the UDP source address (`via.UdpAddr`) against the hostinfo's currently known remote address (`hr`) — this is a plaintext, unauthenticated UDP header field, not a cryptographic proof. UDP source addresses are attacker-controllable via spoofing on many networks, and even without spoofing, an on-path or off-path attacker who can observe/guess the peer's known remote `ip:port` (learnable via lighthouse traffic, which is often visible to a passive network observer) can forge this packet.

Unlike the analogous `CloseTunnel` message type, which is only processed *after* decryption succeeds (i.e., it requires possession of the negotiated symmetric key derived from a CA-signed certificate handshake) — see the authenticated path at [4](#0-3)  and the corresponding test `TestCloseTunnelAuthenticated` confirming a forged, unauthenticated `CloseTunnel` packet is correctly rejected [5](#0-4)  — the `RecvError` path performs the equivalent teardown action *without* any such requirement. There is no second confirmation step, no requirement to hold a CA-signed certificate, and no cryptographic binding to the tunnel being destroyed; only a guessable 32-bit index (`h.RemoteIndex`, generated by `generateIndex`) and a spoofable source-address comparison stand between an attacker and forcibly and permanently destroying a live tunnel in a single packet.

This is directly analogous to the Beanstalk `transferOwnership()` finding: a single, unauthenticated call performs an irreversible, privileged state change with no two-step confirmation, and a mistaken/malicious single message can "permanently misconfigure" (here: sever) the established secure channel.

### Impact Explanation
An attacker without a CA-signed certificate can force termination of an active, established Nebula tunnel between two legitimate peers by sending a single forged `RecvError` packet, provided they can guess/observe the 32-bit `RemoteIndex` and spoof (or know) the peer's current UDP source address. This is a remote state-poisoning/denial-of-service primitive: it forces both the local hostinfo and the pending hostmap entry to be deleted, disrupting connectivity and forcing costly re-handshakes, without ever needing to complete a Noise handshake or possess a valid certificate.

### Likelihood Explanation
Exploitation is low-to-moderate difficulty: it requires knowledge of `h.RemoteIndex` (a 32-bit value assigned via `generateIndex`, not secret but not broadcast either) and either UDP source-IP spoofing capability or knowledge of the peer's currently-visible remote endpoint (obtainable by observing lighthouse traffic or existing UDP flows on the path). `acceptRecvErrorConfig` defaults to accepting these packets from any address (`recvErrorAlways`), which maximizes the attack surface unless operators have explicitly hardened this setting.

### Recommendation
- Short term: Require `RecvError` handling to be tied to a second, authenticated confirmation step rather than immediately tearing down state on a single unauthenticated packet — e.g., only mark the tunnel for probing/re-verification, and require the tunnel to fail a subsequent authenticated liveness check (already-existing `header.Test`/connection-manager dead-tunnel detection) before actually deleting the hostinfo. Alternatively, harden the default `accept_recv_error` policy to `never` or `private` and document the risk of `always`.
- Long term: Audit and document every code path that can mutate hostmap/tunnel state in a single step in response to an unauthenticated packet (as is already partially done for `CloseTunnel`, which correctly requires decryption first), and ensure they all require the same authenticated-channel guarantee before making irreversible changes.

### Proof of Concept
1. Establish a tunnel between "me" and "them" as in `TestCloseTunnelAuthenticated`, and observe/derive `them`'s `RemoteIndex` value as seen by "me" (or vice versa) and the currently-active `CurrentRemote` UDP address.
2. Craft a raw UDP packet with `header.H{Type: header.RecvError, RemoteIndex: <known/guessed index>}`, source address spoofed to (or actually originating from) the peer's currently known `CurrentRemote`.
3. Send this single unencrypted packet to the victim's listening UDP port.
4. Observe that `handleRecvError` immediately calls `f.closeTunnel(hostinfo)` and `f.handshakeManager.DeleteHostInfo(hostinfo)`, tearing down the tunnel in one step with no cryptographic proof of authorization — contrast with the equivalent `CloseTunnel` packet type, which the existing `TestCloseTunnelAuthenticated` test proves is correctly rejected without authentication [6](#0-5) .

```go
func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
```
