### Title
Missing zero-check in `MarketSellAssetActuator.matchSingleOrder` "taker == maker" branch allows a taker to drain a maker's price-3 sell order for free due to rounding - (File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java)

### Summary
`MarketSellAssetActuator` (java-tron's TRC10 order-book DEX) computes fill amounts with integer floor division via `MarketUtils.multiplyAndDivide`. Two of the three branches in `matchSingleOrder` explicitly guard against the computed "amount to receive" rounding down to zero and return the tokens to their rightful owner instead of consuming the order. The third branch — the exact-match ("taker == maker") case — has no such guard, so with an adversarially chosen low-value/odd-ratio maker price, `makerBuyTokenQuantityReceive` can round down to `0` while the maker's order is still fully consumed and the taker still receives the maker's full sell-token balance, effectively for free.

### Finding Description
In `matchSingleOrder`, the "taker == maker" branch is: [1](#0-0) 

Unlike the "taker < maker" branch (no receive computation needed) and the "taker > maker" branch, which explicitly checks: [2](#0-1) 

for `makerBuyTokenQuantityReceive == 0` and returns the maker's remaining sell tokens instead of zeroing them out, the "taker == maker" branch performs no such check. It unconditionally sets `makerOrderCapsule.setSellTokenQuantityRemain(0)` (fully consuming/removing the maker's order) and credits the taker with `takerBuyTokenQuantityReceive = makerOrderCapsule.getSellTokenQuantityRemain()` (the maker's full remaining balance), while only debiting the taker by `makerBuyTokenQuantityReceive`, which can be `0` due to `MarketUtils.multiplyAndDivide`'s floor-division rounding: [3](#0-2) 

Because the taker order's own sell-side reduction is `takerOrderCapsule.getSellTokenQuantityRemain() - makerBuyTokenQuantityReceive`, when `makerBuyTokenQuantityReceive == 0` the taker's own balance/order is unaffected while the maker's order is deleted and its tokens are transferred out via `addTrxOrToken`: [4](#0-3) 

This is precisely the rounding-to-zero class described in the external report ("if the resulting withdrawable/received amount falls between zero and one, it will be rounded down to zero"), except here it is not merely a fund-freezing issue for the order placer — it is exploitable by an unprivileged taker to seize a maker's tokens for zero payment, because the equal-fill branch omits the zero-guard present in its sibling branch.

### Impact Explanation
Any account can place `MarketSellAssetContract` orders (once the committee-controlled Market Transaction feature is enabled, which is standard functionality, not a privileged action per transaction). An attacker who can craft an order whose implied price and remaining maker quantity trigger the exact-match branch with a rounded-to-zero receive amount can obtain the maker's remaining sell tokens without paying the corresponding buy token, directly stealing another user's funds. This is a concrete unauthorized asset transfer / theft of funds bug reachable purely through the `MarketSellAssetContract` transaction path.

### Likelihood Explanation
Exploitation requires the attacker to control both the taker order parameters and knowledge of an existing maker order's exact remaining quantity/price (both are readable from on-chain order-book state via `MarketOrderStore`/`MarketPairPriceToOrderStore`), and to choose a sell/buy quantity ratio such that integer rounding produces a zero result in the specific branch. This is fully computable off-chain by an attacker before submitting the transaction (or the attacker can place their own low-value maker order first and then match it with a crafted taker order from a second account they control, guaranteeing exact conditions), making exploitation practical and deterministic rather than probabilistic.

### Recommendation
Add the same zero-amount guard used in the "taker > maker" branch to the "taker == maker" branch: if `makerBuyTokenQuantityReceive == 0`, return the maker's `sellTokenQuantityRemain` to the maker (via `MarketUtils.returnSellTokenRemain`) instead of transferring it to the taker, and do not treat the exchange as a valid full fill of the maker's order in that case. More generally, enforce a minimum-fill/minimum-price constraint at order validation time (as recommended in the referenced audit) so that any leg of a match that would round to zero received tokens is disallowed for both maker and taker.

### Proof of Concept
1. Account A creates a `MarketSellAssetContract` maker order selling token `TOKEN_ID_ONE` for `TOKEN_ID_TWO` with `sellTokenQuantity = 3`, `buyTokenQuantity = 2` (price ratio 3:2), letting it rest on the book (partially filled elsewhere first, or created directly with a small remaining quantity of `1` unit of `TOKEN_ID_ONE`, achievable via a prior partial fill leaving `makerSellRemainQuantity = 1`).
2. Account B (attacker, taker) submits a `MarketSellAssetContract` selling `TOKEN_ID_TWO` for `TOKEN_ID_ONE` with a `sellTokenQuantity` chosen so that `MarketUtils.multiplyAndDivide(takerSellRemainQuantity, 3, 2, ...)` equals exactly `1` (e.g., `takerSellRemainQuantity = 1`, giving `floor(1*3/2) = 1`), matching `makerOrderCapsule.getSellTokenQuantityRemain() = 1` and hitting the "taker == maker" branch in `matchSingleOrder`.
3. Inside that branch, `makerBuyTokenQuantityReceive = multiplyAndDivide(1, 2, 3, ...) = floor(2/3) = 0`.
4. `takerBuyTokenQuantityReceive = 1` is credited to B via `addTrxOrToken(takerOrderCapsule, 1, ...)`, while B's own sell order is reduced by `0` (`takerSellTokenLeft = takerOrderCapsule.getSellTokenQuantityRemain() - 0`).
5. A's maker order is marked `INACTIVE`/removed with `sellTokenQuantityRemain` set to `0`, and `addTrxOrToken(makerOrderCapsule, 0)` credits A with zero `TOKEN_ID_TWO`.
6. Net result: Account B receives 1 unit of `TOKEN_ID_ONE` from Account A's order while paying nothing, and Account A's order is fully consumed with zero proceeds — a direct theft of A's remaining order balance.

  public static long multiplyAndDivide(long a, long b, long c, boolean disableMath) {
    try {
      long tmp = multiplyExact(a, b, disableMath);
      return floorDiv(tmp, c, disableMath);
    } catch (ArithmeticException ex) {
      // do nothing here, because we will use BigInteger to compute again
    }

    BigInteger aBig = BigInteger.valueOf(a);
    BigInteger bBig = BigInteger.valueOf(b);
    BigInteger cBig = BigInteger.valueOf(c);

    return aBig.multiply(bBig).divide(cBig).longValue();
  }
