### Title
Unbounded Delegated Resource Index Growth Causes DoS in `GetDelegatedResourceAccountIndexV2` Query Path - (File: `chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java`)

### Summary
An unprivileged account can call `DelegateResourceContract` repeatedly toward many distinct receiver addresses. Each delegation writes a new key-value entry keyed by `V2_FROM_PREFIX + owner + receiver` (and the mirrored `V2_TO_PREFIX` entry), with no limit on the number of distinct receivers/senders an address can accumulate. Any later attempt to read that account's index via `getV2Index()` (exposed through the `GetDelegatedResourceAccountIndexV2` HTTP/gRPC API) performs an unbounded `prefixQuery` over all entries for that address, deserializes every entry, and sorts the whole result set in memory — mirroring the reported bug class (unbounded attacker-controlled array later iterated, causing DoS for a legitimate reader).

### Finding Description
`DelegateResourceActuator.delegateResource()` writes new, independent DB keys for every `(owner, receiver)` pair via `DelegatedResourceAccountIndexStore.delegateV2` [1](#0-0) , with each key built from a fixed prefix concatenated with the owner and receiver addresses [2](#0-1) . The only guardrails in `DelegateResourceActuator.validate()` limit the amount delegated per call (minimum 1 TRX, and bounded by the owner's frozen balance) [3](#0-2)  — there is no limit on the number of distinct receiver addresses a single owner can delegate to over many transactions, and no existence/reputation check on receivers beyond `AccountType != Contract` [4](#0-3) .

When any client later queries the delegation index for that address (`getDelegatedResourceAccountIndexV2` on the Wallet API, backed by `GetDelegatedResourceAccountIndexV2Servlet`) [5](#0-4) , the store performs `getWithPrefix`, which runs `prefixQuery` over both the `FROM` and `TO` prefixes for the address, builds an `ArrayList` of every returned capsule, and sorts by timestamp before returning [6](#0-5) . `prefixQuery` itself deserializes every matching entry into an in-memory map [7](#0-6) . There is no cap on the number of entries this scan/sort/deserialize can touch — an attacker who fans out delegations to (or receives delegations from) an arbitrarily large number of distinct addresses can make this single query arbitrarily expensive.

### Impact Explanation
This is a resource-exhaustion / DoS vector against a JSON-RPC/HTTP query path served by the node (`GetDelegatedResourceAccountIndexV2`, and the analogous non-V2 `getIndex`/`GetDelegatedResourceAccountIndexServlet`). A single crafted address with many fan-out delegations can force full-node/solidity-node API instances to perform large unbounded DB scans, deserialization, and sorting on every query for that address, degrading or denying node API service for legitimate callers. Unlike the original report (which achieves DoS with a single transaction), this variant requires the attacker to send multiple transactions to build up entries, but each transaction is cheap (delegating the 1 TRX minimum to throwaway/self-controlled receiver addresses), and the resulting query cost is unbounded and attacker-controlled, satisfying the "API the node can no longer serve" criterion.

### Likelihood Explanation
Medium-High. Any account can call `DelegateResourceContract` without special privilege; the only cost is the minimum 1 TRX per receiver and the frozen balance backing it (which can be recycled via `UnDelegateResourceContract`/`UnfreezeBalanceV2Contract`), and normal TRX transfer fees. There is no consensus-level check preventing an address from being the source or destination of an unbounded number of delegation relationships.

### Recommendation
- Cap the number of distinct delegation index entries (`fromAccounts`/`toAccounts`) tracked per address, or restructure the query API to support pagination instead of returning/sorting the full unbounded set in one call.
- Add rate limiting or minimum-delegation-amount scaling (e.g., require larger deposits for large numbers of distinct receivers) to make fan-out economically costly.
- Bound `prefixQuery` result processing in `DelegatedResourceAccountIndexStore.getWithPrefix` (and its non-V2 counterpart) with a maximum entry count, returning a truncated/paginated result rather than scanning and sorting an unbounded set.

### Proof of Concept
1. Attacker account `A` freezes balance for `BANDWIDTH`/`ENERGY` via `FreezeBalanceV2Contract`.
2. Attacker sends `N` (e.g., tens of thousands) `DelegateResourceContract` transactions from `A`, each to a distinct freshly-created receiver address, delegating the 1 TRX minimum each time [3](#0-2) . Each call stores a new key under `V2_FROM_PREFIX + A + receiver_i` and `V2_TO_PREFIX + receiver_i + A` via `delegateResourceAccountIndexStore.delegateV2` [1](#0-0) .
3. Any client calls the `GetDelegatedResourceAccountIndexV2` HTTP endpoint with `value = A` [8](#0-7) , triggering `getV2Index(A)` → `getWithPrefix` → `prefixQuery` over `N` entries, deserializing and sorting all of them in memory [9](#0-8) .
4. As `N` grows, this single API call consumes increasing CPU/memory on the serving node, degrading service for other API clients on that node.

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
