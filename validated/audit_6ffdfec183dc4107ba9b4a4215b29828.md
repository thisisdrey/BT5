### Title
Fixed-window stream throttling in `ConnectionStreamCounter` allows ~2x `max_streams_per_throttling_interval` streams within any 100ms window via boundary timing - ([File: streamer/src/nonblocking/stream_throttle.rs])

### Summary
`throttle_stream` and `ConnectionStreamCounter::reset_throttling_params_if_needed` implement a fixed (tumbling) window rate limiter keyed off `last_throttling_instant`, not a sliding window. An attacker who times stream opens to land a full burst of `max_streams_per_throttling_interval` streams right before the window resets, then immediately sends another full burst right after the reset, can get ~2x the configured stream budget accepted within a much shorter wall-clock span than `STREAM_THROTTLING_INTERVAL_MS`.

### Finding Description
`reset_throttling_params_if_needed` only zeroes `stream_count` and moves `last_throttling_instant` forward when `Instant::now().duration_since(last_throttling_instant) > STREAM_THROTTLING_INTERVAL` [1](#0-0) . Between resets, `throttle_stream` just compares the current `stream_count` against `max_streams_per_throttling_interval` and sleeps only if it is already at/over the cap [2](#0-1) .

Because the window boundary is defined purely by `last_throttling_instant + STREAM_THROTTLING_INTERVAL` (a fixed, non-overlapping window per connection), an attacker controlling stream timing can:
1. Open the connection and immediately send `max_streams_per_throttling_interval` streams just before the current window's `STREAM_THROTTLING_INTERVAL_MS` (100ms) boundary elapses — all pass unthrottled since `stream_count` is below the cap.
2. Immediately after the boundary passes (even 1ms later), `reset_throttling_params_if_needed` resets `stream_count` to 0 and moves `last_throttling_instant` forward, opening a brand new window.
3. The attacker immediately sends another full burst of `max_streams_per_throttling_interval` streams, which is again accepted unthrottled.

The result is up to `2 * max_streams_per_throttling_interval` streams accepted within a wall-clock span far shorter than `STREAM_THROTTLING_INTERVAL_MS` (in the worst case, back-to-back around the boundary), effectively doubling the configured per-connection stream ingress rate for that short period. This directly matches the stated invariant that stream limits must not be evadable via interval-boundary gaming, and no other mechanism (EMA-based staked throttling operates on aggregate load, not per-connection boundaries, and doesn't prevent this per-connection burst) closes this gap.

### Impact Explanation
This is a per-connection stream-rate-limit (QoS) evasion reachable by any unstaked remote client opening a QUIC connection to the TPU: it lets an attacker push transaction/stream ingress at up to ~2x the configured `max_streams_per_throttling_interval` for short bursts, increasing packet/stream processing load beyond the intended cap without needing privileges. This falls under QoS evasion / rate-limit bypass for unstaked connections.

### Likelihood Explanation
Fully reachable by an unprivileged, unstaked remote attacker: it only requires precise (but easily achievable, since attacker controls timing) scheduling of stream opens relative to `STREAM_THROTTLING_INTERVAL_MS` (100ms), which is coarse-grained and trivial to straddle from a network client. It is deterministic and repeatable per connection/window.

### Recommendation
Replace the fixed/tumbling window in `ConnectionStreamCounter` with a sliding-window or token-bucket algorithm (e.g., track timestamps of individual stream opens and only count those within the trailing `STREAM_THROTTLING_INTERVAL_MS`, or use a leaky-bucket token refill model) so that no rolling `STREAM_THROTTLING_INTERVAL_MS` window can ever see more than `max_streams_per_throttling_interval` accepted streams, regardless of alignment with the reset boundary.

### Proof of Concept
```rust
// streamer/src/nonblocking/stream_throttle.rs (test mod)
#[tokio::test(start_paused = true)]
async fn test_boundary_gaming_doubles_accepted_streams() {
    let stats = StreamerStats::default();
    let counter = Arc::new(ConnectionStreamCounter::new());
    let max_streams = 10u64;
    let peer_type = ConnectionPeerType::Unstaked;
    let addr = "127.0.0.1:0".parse().unwrap();

    // Burst 1: fill window just under the boundary.
    for _ in 0..max_streams {
        throttle_stream(&stats, peer_type, addr, &counter, max_streams).await;
        counter.stream_count.fetch_add(1, Ordering::Relaxed);
    }
    // Advance time to just past STREAM_THROTTLING_INTERVAL_MS to trigger reset.
    tokio::time::advance(STREAM_THROTTLING_INTERVAL + Duration::from_millis(1)).await;

    // Burst 2: immediately after reset, another full burst is accepted unthrottled.
    let start = tokio::time::Instant::now();
    for _ in 0..max_streams {
        throttle_stream(&stats, peer_type, addr, &counter, max_streams).await;
        counter.stream_count.fetch_add(1, Ordering::Relaxed);
    }
    let elapsed = start.elapsed();

    // Assert violation: 2*max_streams accepted within ~STREAM_THROTTLING_INTERVAL_MS wall time
    // (elapsed for burst 2 alone is near-zero, meaning total 20 streams landed within
    // a rolling 100ms window centered on the boundary), exceeding max_streams_per_throttling_interval.
    assert!(elapsed < STREAM_THROTTLING_INTERVAL);
    assert_eq!(counter.stream_count.load(Ordering::Relaxed), max_streams); // window-local count resets, hiding the true 2x total
}
```
Expected: the test demonstrates that 2x `max_streams_per_throttling_interval` streams are processed without any `sleep` throttling being triggered, within a combined wall-clock window on the order of `STREAM_THROTTLING_INTERVAL_MS`, confirming the sliding-window invariant is violated.

    pub(crate) fn reset_throttling_params_if_needed(&self) -> tokio::time::Instant {
        let last_throttling_instant = *self.last_throttling_instant.read().unwrap();
        if tokio::time::Instant::now().duration_since(last_throttling_instant)
            > STREAM_THROTTLING_INTERVAL
        {
            let mut last_throttling_instant = self.last_throttling_instant.write().unwrap();
            // Recheck as some other thread might have done throttling since this thread tried to acquire the write lock.
            if tokio::time::Instant::now().duration_since(*last_throttling_instant)
                > STREAM_THROTTLING_INTERVAL
            {
                *last_throttling_instant = tokio::time::Instant::now();
                self.stream_count.store(0, Ordering::Relaxed);
            }
            *last_throttling_instant
        } else {
            last_throttling_instant
        }
    }
