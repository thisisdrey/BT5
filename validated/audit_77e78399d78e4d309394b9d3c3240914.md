### Title
DebtToken interest accrual changes holder balances without checkpointing RewardsDistributor, causing misaccrued rewards - (File: contracts/DebtToken.sol)

### Summary
The reference bug class is "rewarder is not called on every balance change, so reward accrual is wrong." In Metronome, `RewardsDistributor` must be notified via `updateBeforeMintOrBurn`/`updateBeforeTransfer` before any `DepositToken` or `DebtToken` balance changes. All explicit mint/burn/transfer paths are covered (`DepositToken._mint`, `_burn`, `_transfer` at `contracts/DepositToken.sol:444,469,498`; `DebtToken._mint`, `_burn` at `contracts/DebtToken.sol:525,572`). However, `DebtToken.accrueInterest()` mutates `totalSupply_` and `debtIndex`, which changes every holder's effective `balanceOf` (`principalOf[account] * debtIndex / debtIndexOf[account]`) without any rewards-distributor update, and without per-account index bookkeeping (`debtIndexOf`/`principalOf` are only reset on the next `_mint`/`_burn`). Reward deltas in `RewardsDistributor._calculateTokenDelta` are computed as `deltaIndex * token_.balanceOf(account)` evaluated at update time, so the interest-inflated debt balance is applied retroactively over the whole accrual window.

### Finding Description
- `accrueInterest()` (`contracts/DebtToken.sol:156`) increases `totalSupply_` and `debtIndex` with no call to any rewards distributor.
- `balanceOf()` (`contracts/DebtToken.sol:196`) therefore returns a growing balance between checkpoints even though no `updateBeforeMintOrBurn` ever ran for the holder.
- When `updateBeforeMintOrBurn`/`updateBeforeTransfer`/`claimRewards` eventually run, `_updateTokensAccruedOf` → `_calculateTokenDelta` (`contracts/RewardsDistributor.sol:217-231`) multiplies the index delta by the *current* (interest-grown) `balanceOf`, crediting the holder rewards on debt they did not have during most of the accrual period.
- Symmetrically, the global index `_calculateTokenIndex` divides emitted rewards by `token_.totalSupply()` (`contracts/RewardsDistributor.sol:204-206`), which for `DebtToken` already includes pending unminted interest, so per-unit distribution is diluted while individual deltas are inflated — accounting diverges in both directions.

### Impact Explanation
If a `DebtToken` is registered for rewards (`updateTokenSpeed` allows `doesDebtTokenExist` tokens per `contracts/RewardsDistributor.sol:91-97`), borrowers whose debt compounds via interest systematically over-accrue rewards relative to their time-weighted balance, paid from the same reward pool other users claim from — theft/dilution of unclaimed yield. On deployed configs where debt-token rewards are disabled, the impact is nil; the issue then reduces to inconsistent reward accounting, which the rewarder-miss bug class still covers but with low realized loss.

### Likelihood Explanation
Reachable by any unprivileged borrower via `DebtToken.issue` followed by simply not repaying — `accrueInterest` is invoked on every `issue`, `repay`, `repayAll`, `mint`, `flashIssue` and grows `balanceOf` continuously. No privileged role needed. However, exploitation requires a rewards speed configured on a debt token (governance-dependent), and the over-accrual magnitude is bounded by the interest rate, so realized theft is modest rather than full drainage.

### Recommendation
Checkpoint the rewards distributor when interest accrual changes effective balances. Concretely, when `accrueInterest()` increases `debtIndex`, iterate the pool's rewards distributors and update the token index (at minimum call `IRewardsDistributor(d).updateBeforeMintOrBurn(this, account)` for the interacting account *before* `accrueInterest()` alters `debtIndex`, or track reward shares on `principalOf` instead of live `balanceOf`). Alternatively, exclude `DebtToken` from rewardable tokens in `onlyIfTokenExists` so reward math is never applied to a balance that changes outside the mint/burn hooks.
