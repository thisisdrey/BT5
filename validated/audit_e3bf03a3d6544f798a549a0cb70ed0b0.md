### Title
Deflationary/fee-on-transfer NEP-141 deposits mint uncollateralized internal balance - (File: contracts/defuse/src/contract/tokens/nep141/deposit.rs)

### Summary
`ft_on_transfer` credits the depositor with the full nominal `amount` argument reported by the external token's `ft_transfer_call`, without checking that Defuse's real token balance increased by that same amount.

### Finding Description
`ft_on_transfer` (`contracts/defuse/src/contract/tokens/nep141/deposit.rs:19-43`) calls `self.deposit(receiver_id, [(token_id, amount.0)], ...)` where `amount` is simply the value the NEP-141 sender claims to transfer and the standard requires be reported. `Contract::deposit` (`contracts/defuse/src/contract/tokens/mod.rs:18-74`) then unconditionally increases `total_supplies` and the receiver's `token_balances` by that full `amount`, with no cross-check against Defuse's actual NEP-141 balance on the underlying token contract.

For a deflationary/fee-on-transfer token (as in the referenced BGLD exploit, where transfers burn a percentage of the transferred amount), the sender's `ft_transfer_call(defuse, amount, msg)` reduces the sender's balance by `amount`, but Defuse's real balance at the token contract only increases by `amount * (1 - fee)`. Defuse nevertheless mints the full `amount` internally. This breaks the binding "value debited (real backing received) versus value delivered (internal credit) plus refunded": internal claims on that `TokenId` now exceed the actual custodied backing.

Because all depositors of a given `TokenId::Nep141` share the same underlying real-token balance pool (`total_supplies` is a single ledger, `token_balances` is a per-account share of that shared pool), this creates a shortfall that is invisible until withdrawals are attempted. `internal_ft_withdraw` (`contracts/defuse/src/contract/tokens/nep141/withdraw.rs:53-106`) subtracts the requested amount from the internal ledger and then attempts to `ft_transfer`/`ft_transfer_call` that same amount out, refunding only if the transfer promise itself fails (`ft_resolve_withdraw`, lines 154-195) — it does not detect or protect against insufficient real backing caused by earlier deflationary deposits.

### Impact Explanation
This is a Critical-class issue under the stated impact categories ("funds permanently frozen" / mismatched custody backing): the internal ledger can represent more of a `TokenId::Nep141` than Defuse actually custodies. Any user (attacker or otherwise) who deposits a deflationary token is unknowingly minting excess internal claims, and whichever depositor of that same token withdraws first drains the genuinely available balance, leaving later depositors with internal balances that cannot be redeemed — a shared-pool insolvency. This can also be leveraged intentionally by an attacker: deposit a small nominal amount into a fee-on-transfer token to create excess unbacked internal credit, then trade/settle it against other assets via `TokenDiff`/`Transfer` intents before the shortfall is discovered, extracting real value from other users' backing of that same token.

### Likelihood Explanation
Reachable by any unprivileged user calling standard `ft_transfer_call` into Defuse with an attacker-deployed or attacker-chosen deflationary NEP-141 token; no privileged role, relayer key, or victim key needed. The precondition is that Defuse accepts deposits of an arbitrary NEP-141 contract identified only by `predecessor_account_id()`, which is the documented general design of the contract (any `AccountId` can be a `TokenId::Nep141`).

### Recommendation
Before crediting `amount` in `Contract::deposit` for NEP-141 tokens, verify actual balance received (e.g., by comparing `ft_balance_of(current_account_id())` before and after the transfer, similar to how many vault protocols handle fee-on-transfer tokens), or credit only `min(amount, promise_result-verified received amount)`. Alternatively, explicitly document and enforce (via governance/allow-list) that only tokens with exact-transfer semantics (no transfer fee) are accepted, and reject deposits from tokens that do not conserve `amount` end-to-end.

### Proof of Concept
1. Deploy (or use) a NEP-141 token contract that implements a transfer fee/burn such that `ft_transfer_call(defuse, X, msg)` results in Defuse's real balance increasing by `X * (1-fee)` while the standard `ft_on_transfer(sender, amount=X, msg)` callback still reports `amount = X` (this is permitted by the NEP-141 interface, which does not mandate that `amount` reflect the receiver's actual delta).
2. Call `ft_transfer_call` from an attacker account into Defuse for amount `X`.
3. Observe: Defuse's internal `mt_balance_of` for that `TokenId::Nep141` shows `X` credited to the attacker's account (per `Contract::deposit`/`ft_on_transfer` logic cited above), while Defuse's real balance on the token contract only increased by `X*(1-fee)`.
4. Attacker (or any other holder of that `TokenId`) withdraws via `FtWithdraw`; `internal_ft_withdraw` (`contracts/defuse/src/contract/tokens/nep141/withdraw.rs`) subtracts the full requested amount from the internal ledger and issues `ft_transfer`, which succeeds using the actually-available (deficient) real balance, draining backing that other legitimate depositors of the same `TokenId` are relying on — later withdrawers of the same token find the real balance insufficient.     pub(crate) fn deposit(
        &mut self,
        owner_id: AccountId,
        tokens: impl IntoIterator<Item = (TokenId, u128)>,
        memo: Option<&str>,
    ) -> Result<()> {
        let owner = self
            .storage
            .accounts
            .get_or_create(owner_id.clone())
            // deposits are allowed for locked accounts
            .as_inner_unchecked_mut();

        let mut mint_event = MtMintEvent {
            owner_id: owner_id.into(),
            token_ids: Vec::new().into(),
            amounts: Vec::new().into(),
            memo: memo.map(Into::into),
        };

        for (token_id, amount) in tokens {
            if amount == 0 {
                return Err(DefuseError::InvalidIntent);
            }

            mint_event.token_ids.to_mut().push(token_id.to_string());
            mint_event.amounts.to_mut().push(amount);

            let total_supply = self
                .storage
                .state
                .total_supplies
                .add(token_id.clone(), amount)
                .ok_or(DefuseError::BalanceOverflow)?;
            match token_id {
                TokenId::Nep171(ref tid) => {
                    if total_supply > 1 {
                        return Err(DefuseError::NftAlreadyDeposited(tid.clone()));
                    }
                }
                TokenId::Nep141(_) | TokenId::Nep245(_) | TokenId::Imt(_) => {}
            }

            owner
                .token_balances
                .add(token_id, amount)
                .ok_or(DefuseError::BalanceOverflow)?;
        }

        if !mint_event.amounts.is_empty() {
            MtEvent::MtMint([mint_event].as_slice().into())
                .check_refund()?
                .emit();
        }

        Ok(())
    }

#[near]
impl FungibleTokenWithdrawResolver for Contract {
    #[private]
    fn ft_resolve_withdraw(
        &mut self,
        token: AccountId,
        sender_id: AccountId,
        amount: U128,
        is_call: bool,
    ) -> U128 {
        let used = if is_call {
            // `ft_transfer_call` returns successfully transferred amount
            match promise_result_checked_json::<U128>(0) {
                Ok(Ok(used)) => used.0.min(amount.0),
                Ok(Err(_deserialize_err)) => 0,
                // do not refund on failed `ft_transfer_call` due to
                // NEP-141 vulnerability: `ft_resolve_transfer` fails to
                // read result of `ft_on_transfer` due to insufficient gas
                Err(_) => amount.0,
            }
        } else {
            // `ft_transfer` returns empty result on success
            if promise_result_checked_void(0).is_ok() {
                amount.0
            } else {
                0
            }
        };

        let refund = amount.0.saturating_sub(used);
        if refund > 0 {
            self.deposit(
                sender_id,
                [(Nep141TokenId::new(token).into(), refund)],
                Some(REFUND_MEMO),
            )
            .unwrap_or_else(|err| err.panic());
        }

        U128(used)
    }
}
