### Title
Unbounded array allocation from attacker-controlled length in TVM precompiled-contract ABI array parsing causes memory-exhaustion DoS - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The private helpers `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` in `PrecompiledContracts.java` read an array-length word directly from calldata and immediately allocate a `byte[len][]` array before validating that `len` is consistent with the actual size of the supplied calldata.

### Finding Description
`extractBytes32Array` reads `len = words[offset].intValueSafe()` and immediately does `new byte[len][]` with no upper bound check at all: [1](#0-0) 

`extractBytesArray` only validates that `offset` is within the `words` array, but the derived `len` used for allocation is never checked against the remaining calldata size before the allocation happens: [2](#0-1) 

`extractSigArray` has the same pattern — `len` comes straight from attacker-supplied calldata (`words[offset].intValueSafe()`) and is used to size a new two-dimensional array before any sanity check on the actual data length: [3](#0-2) 

This mirrors the CVE-2016-6308 bug class: memory is allocated based on an attacker-supplied length field before the length is checked against the real size of the input, which can force a huge (up to `Integer.MAX_VALUE`) allocation immediately upon parsing, i.e., before any subsequent bounds validation of the array contents can reject the malformed input.

By contrast, the codebase elsewhere in the same file demonstrates the correct pattern of validating length before allocating, e.g. `VerifyTransferProof.execute` explicitly bounds `spendCount`/`receiveCount` to the range `[1,2]` before allocating any arrays sized by them: [4](#0-3) 
No equivalent bound exists for the `len` values consumed by `extractBytes32Array`, `extractBytesArray`, and `extractSigArray`.

### Impact Explanation
Any TVM precompiled contract that uses these helpers to parse variable-length array parameters from calldata (e.g. batch-signature-style precompiles that accept arrays of 32-byte words or signatures) can be driven to allocate an oversized array directly from a single crafted `CALL`/`STATICCALL` to that precompile address. Because `DataWord.intValueSafe()` clamps to `Integer.MAX_VALUE` rather than rejecting the value, an attacker can supply a length word of `0xFFFFFFFF...` and force allocation of an array with up to `2^31-1` elements, which throws `OutOfMemoryError` or consumes excessive heap, degrading or crashing the node process that executes the transaction (validator/full node), i.e., a denial-of-service condition reachable by any unprivileged contract caller.

### Likelihood Explanation
Any account that can broadcast a transaction invoking the affected precompiled contract with crafted calldata can trigger this: no special privilege, stake, or witness/committee role is required — an ordinary TVM contract call reaches these decoding helpers as part of executing the precompile.

### Recommendation
Add explicit upper-bound checks on `len` in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` before allocating memory — validate `len` against a reasonable maximum and against the actual remaining `words`/`data` length (as is already done in `VerifyTransferProof`), rejecting the call (returning a failure result) instead of allocating when the declared length is inconsistent with the supplied calldata size.

### Proof of Concept
1. Identify (or add, for a fresh Devin session with full file access) a precompiled-contract implementation in `PrecompiledContracts.java` whose `execute(byte[] data)` calls `extractBytesArray`/`extractBytes32Array`/`extractSigArray` on attacker-controlled `data`.
2. Craft an ABI-encoded calldata blob where the length word at the expected `offset` is set to a large value (e.g. `0x7FFFFFFF`).
3. Deploy a trivial contract that performs a `CALL`/`STATICCALL` to that precompile address with the crafted calldata, or invoke it directly via a `TriggerSmartContract` transaction.
4. Broadcast the transaction from any unprivileged account; observe the executing node attempt a multi-gigabyte array allocation, resulting in `OutOfMemoryError` or severe GC pressure/service degradation on the node processing the transaction.

Note: due to index size limits, I was unable to fully enumerate which specific precompiled-contract `execute()` method(s) invoke `extractBytesArray`/`extractBytes32Array`/`extractSigArray` in this build — the callers exist within the same file but the caller line numbers could not be located via search. A Devin session with full file access to `PrecompiledContracts.java` would be needed to confirm the exact reachable precompile address and finalize the PoC calldata layout.

    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
