## Title
Reentrant `instantiate` with the same address is not rejected in legacy `pallet-contracts`, unlike the equivalent fixed guard in `pallet-revive` - (File: `substrate/frame/contracts/src/exec.rs`, `substrate/frame/contracts/src/storage.rs`)

## Summary
The external report's core broken invariant is: a callee invoked mid-construction can re-enter the constructing contract's own `initialize`/instantiate path before the "is initialized" collision guard is durably recorded, letting the attacker win a race against the guard and hijack the freshly-created contract's identity. `pallet-revive` had exactly this bug class (documented and fixed in `prdoc/pr_12645.prdoc`): `ContractInfo` is only written to `AccountInfoOf` when the constructor frame pops, so the `is_contract` collision check in `ContractInfo::new` cannot see an address that is still under construction, letting a re-entrant `CREATE2` with the same salt+code resolve to the same address and run a second constructor frame on one account. The fix added an explicit in-stack check in `push_frame`.

## Finding Description
`pallet-revive`'s `Stack::push_frame` was patched to check the live frame stack (not just committed storage) for a colliding in-construction address: [1](#0-0) 

The prdoc explicitly documents why the pre-existing storage-based check (`ContractInfo::new`'s `is_contract`/`contains_key` guard) was insufficient: `ContractInfo` is not persisted until the constructor frame pops, so a nested/re-entrant instantiate at the same address (same salt, same code, nonce-independent per EIP-684) sails past the guard: [2](#0-1) 

The legacy `pallet-contracts` (still present and shipped in this repo) uses the exact same architecture: `ContractInfo::new` only guards against collision via a storage lookup on `ContractInfoOf`: [3](#0-2) 

And `ContractInfoOf` is only written back to storage when a frame is popped/persisted (in `absorb`/frame-teardown), not while the frame is still open on the stack: [4](#0-3) 

Unlike `pallet-revive`'s `push_frame`, `pallet-contracts`'s `push_frame` has no equivalent check against the live `self.frames()` stack for an in-construction `Constructor` frame at the same target account before pushing a new constructor frame. The only reentrancy protections present in `pallet-contracts::exec.rs` are `allows_reentry`/`is_recursive`, which govern `call` reentrancy for already-materialized contracts, not the constructor-collision path that `pallet-revive` had to specifically patch: [5](#0-4) 

This mirrors the Rubicon `BathToken.initialize()` bug precisely: the "initialized" state (there, a boolean flag; here, the `ContractInfoOf` storage entry) is only durably committed *after* an external call/sub-execution completes, so a re-entrant call that occurs *during* that window bypasses the guard and can create a colliding/duplicate object bound to the same identity (there, the same pool address; here, the same contract account).

## Impact Explanation
An attacker-controlled constructor in `pallet-contracts` can re-enter an instantiate call for the same `code_hash` + `salt` (deriving the same account address deterministically), and since `ContractInfoOf` is not yet populated for that address, the collision guard in `ContractInfo::new` does not fire. This permits two constructor frames to run against a single account, one of which is orphaned when the outer frame's changes are eventually persisted/overwritten. Depending on the order of writes at frame-pop, this can leak the code reference count (module never getting a matching decrement), permanently orphan a child trie's storage deposit (funds locked, matching the "permanent user-fund lock" impact criterion), or leave conflicting/duplicate contract metadata for the address that downstream logic (deposits, code hash lookups) relies on.

## Likelihood Explanation
This requires no privileged, governance, admin, validator, collator, or off-chain actor — only an unprivileged user deploying a contract whose constructor calls back into `pallet_contracts::instantiate` with matching `code_hash`/`salt`, which is exactly the primitive `pallet-revive` had to defend against with a dedicated patch. Since `pallet-contracts` is still compiled and available in this repository and received no equivalent fix, the same attacker-controlled contract code pattern applies directly.

## Recommendation
Port the `pallet-revive` fix to `pallet-contracts::exec.rs`: before pushing a new `Constructor` frame in `push_frame`, check the live `self.frames()` stack for an existing `Constructor` frame with the same `account_id` and reject with `Error::<T>::DuplicateContract` if found, exactly as done in `substrate/frame/revive/src/exec.rs` lines 1238-1246.

## Proof of Concept
1. Deploy contract `A` with `code_hash = H` and `salt = S`, deriving deterministic address `X` (as in `pallet-contracts`'s CREATE2-style address derivation).
2. In `A`'s constructor, before returning, call back into `pallet_contracts::Pallet::instantiate` (or the `Ext::instantiate` host function) with the same `code_hash = H` and `salt = S`.
3. Because `ContractInfoOf::<T>::contains_key(&X)` is still `false` (the outer frame's `ContractInfo` has not yet been persisted — see `absorb`/`persist` logic in `exec.rs`), `ContractInfo::new` in `storage.rs` does not return `DuplicateContract`, and a second constructor frame for account `X` is pushed and executed.
4. Compare against `pallet-revive`'s regression test `reentrant_instantiate_at_same_address_is_rejected`, which demonstrates the identical re-entrant instantiate primitive and asserts it is rejected with `DuplicateContract`: [6](#0-5) 

No equivalent test or guard exists for `pallet-contracts`, confirming the analog gap.

impl<T: Config> ContractInfo<T> {
	/// Constructs a new contract info **without** writing it to storage.
	///
	/// This returns an `Err` if an contract with the supplied `account` already exists
	/// in storage.
	pub fn new(
		account: &AccountIdOf<T>,
		nonce: u64,
		code_hash: CodeHash<T>,
	) -> Result<Self, DispatchError> {
		if <ContractInfoOf<T>>::contains_key(account) {
			return Err(Error::<T>::DuplicateContract.into());
		}

		let trie_id = {
			let buf = (account, nonce).using_encoded(T::Hashing::hash);
			buf.as_ref()
				.to_vec()
				.try_into()
				.expect("Runtime uses a reasonable hash size. Hence sizeof(T::Hash) <= 128; qed")
		};

		let contract = Self {
			trie_id,
			code_hash,
			storage_bytes: 0,
			storage_items: 0,
			storage_byte_deposit: Zero::zero(),
			storage_item_deposit: Zero::zero(),
			storage_base_deposit: Zero::zero(),
			delegate_dependencies: Default::default(),
		};

		Ok(contract)
	}

#[test]
fn reentrant_instantiate_at_same_address_is_rejected() {
	// EIP-684: while `B1` constructs at address `X`, its constructor re-enters the deployer to
	// instantiate the same code+salt. That resolves to `X` again and must be rejected rather
	// than run a second constructor for one account.
	let salt = [42u8; 32];

	let constructor_ch = MockLoader::insert(Constructor, |ctx, _| {
		// Re-enter the deployer (BOB) while we are still being constructed.
		ctx.ext
			.call(
				&CallResources::NoLimits,
				&BOB_ADDR,
				U256::zero(),
				vec![],
				ReentrancyProtection::AllowReentry,
				false,
			)
			.unwrap();
		exec_success()
	});

	let invocations = Rc::new(RefCell::new(0u32));
	let second_instantiate_error = Rc::new(RefCell::new(None::<DispatchError>));
	let factory_ch = MockLoader::insert(Call, {
		let invocations = Rc::clone(&invocations);
		let second_instantiate_error = Rc::clone(&second_instantiate_error);
		move |ctx, _| {
			*invocations.borrow_mut() += 1;
			let n = *invocations.borrow();
			// Bound the recursion in case the guard fails to reject the collision.
			if n <= 2 {
				let min_balance = <Test as Config>::Currency::minimum_balance();
				let value = Pallet::<Test>::convert_native_to_evm(min_balance);
				let result = ctx.ext.instantiate(
					&CallResources::NoLimits,
					Code::Existing(constructor_ch),
					value,
					vec![],
					Some(&salt),
				);
				if n == 2 {
					if let Err(err) = &result {
						*second_instantiate_error.borrow_mut() = Some(err.error);
					}
				}
			}
			exec_success()
		}
	});

	ExtBuilder::default()
		.with_code_hashes(MockLoader::code_hashes())
		.existential_deposit(15)
		.build()
		.execute_with(|| {
			let min_balance = <Test as Config>::Currency::minimum_balance();
			set_balance(&ALICE, min_balance * 1000);
			place_contract(&BOB, factory_ch);
			let origin = Origin::from_account_id(ALICE);
			let mut meter =
				TransactionMeter::<Test>::new_from_limits(WEIGHT_LIMIT, min_balance * 100).unwrap();

			// `B1` still constructs; only the colliding re-entrant instantiate fails.
			assert_ok!(MockStack::run_call(
				origin,
				BOB_ADDR,
				&mut meter,
				Pallet::<Test>::convert_native_to_evm(min_balance * 100),
				vec![],
				&ExecConfig::new_substrate_tx(),
			));

			// Initial call plus one re-entry; without the guard it would recurse further.
			assert_eq!(*invocations.borrow(), 2);
			assert_eq!(
				*second_instantiate_error.borrow(),
				Some(<Error<Test>>::DuplicateContract.into())
			);
		});
}
