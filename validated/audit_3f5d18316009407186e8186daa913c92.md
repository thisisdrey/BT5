### Title
Incomplete reference-name validation in `RefExists` allows extended-revision syntax to reach `git-show-ref`/`ResolveRevision` - (File: internal/gitaly/service/ref/refexists.go)

### Summary
Gitaly already implements a strict, git-compatible reference-name validator, `git.ValidateReference`, which rejects control characters, embedded `..`, `@{`, colons, and other constructs that have special meaning to Git's revision-parsing machinery [1](#0-0) . However, the `RefExists` RPC does not use this validator. It instead relies on a much weaker, ad-hoc `isValidRefName` helper that only checks that the value starts with `"refs/"` [2](#0-1) . This is the same class of bug described in the external report: a correct validation routine exists in the codebase but is never invoked at the actual point where the untrusted value is used.

### Finding Description
`RefExistsRequest.Ref` is a `bytes` field, so a caller can supply any byte sequence as long as it begins with `refs/`. The handler only calls `isValidRefName`, which is a bare prefix check, before using the value: [3](#0-2) 

The unvalidated string is then passed as a positional `Args` element (not the safer `PostSepArgs`, whose doc comment explicitly warns it is unsafe for "directly user-controlled" input) to `git show-ref --verify --quiet <ref>`: [4](#0-3) [5](#0-4) 

If `show-ref` exits with code 128 (fatal error), the same unvalidated string is fed into `repo.ResolveRevision(ctx, git.Revision(ref))`, which implements Git's *extended SHA-1* syntax — supporting `:path` (blob-at-path lookups), `@{...}` (reflog/upstream expressions), and other revision operators: [6](#0-5) 

Because `isValidRefName` does not reject `:`, `@{`, `..`, or control/NUL characters — all of which `git.ValidateReference` explicitly forbids — a value like `refs/heads/main:some/internal/path` or `refs/heads/main@{upstream}` passes the "is this a reference name" gate and is then interpreted by Git with entirely different semantics (tree/blob path lookup, upstream-branch resolution) instead of being treated as a literal, fully-qualified reference name as the RPC's own comment promises ("The ref must start with the string `ref/`"). This is precisely the report's pattern: existing, correct validation logic (`git.ValidateReference`, analogous to the unused checksum-verification code in the report) is bypassed in favor of an incomplete substitute (`isValidRefName`, analogous to the report's prefix-only address check).

### Impact Explanation
An authenticated, otherwise-authorized RPC caller (someone who can already call `RefExists` against a repository they have access to) can smuggle Git extended-revision syntax into a field that is documented and expected to be a literal reference name. Depending on the resolved object, `danglingReference` returns an error detail that includes the OID and the caller-supplied "reference" string, which can act as an oracle for the existence of specific paths/blobs inside commits of the same repository, outside of the reference namespace the RPC's contract implies. It also demonstrates that Gitaly's own service layer inconsistently applies its hardened reference-name validator, undermining defense-in-depth for other, more sensitive git-argument constructions that assume `isValidRefName`-style checks are sufficient.

### Likelihood Explanation
High for reachability — `RefExists` is a standard-tier RPC reachable from any client with repository access, requires no special privileges beyond normal repo access, and the malformed value needs only to start with `refs/` to bypass the check. However, the exploitable *impact* is bounded to information disclosure of path/OID existence within the same repository the caller already can query, so it does not constitute a cross-repository or storage escape by itself.

### Recommendation
Replace `isValidRefName` in `internal/gitaly/service/ref/refexists.go` with `git.ValidateReference`, which is already implemented, tested, and used elsewhere in the codebase. Additionally, pass the reference through `PostSepArgs` rather than `Args` when invoking `git show-ref`, consistent with the `gitcmd.Command` documentation's guidance for user-controlled values [5](#0-4) .

### Proof of Concept
1. Create/have access to a repository containing a commit on `refs/heads/main` with a known file at `secret/path`.
2. Call `RefExists` with `Ref = []byte("refs/heads/main:secret/path")`.
3. `isValidRefName` accepts the value (starts with `refs/`) [7](#0-6) .
4. `git show-ref --verify --quiet refs/heads/main:secret/path` fails with exit 128 (not a valid ref format), triggering `danglingReference`, which calls `ResolveRevision` with the same string, now interpreted as *tree-ish:path* syntax and resolving to the blob for `secret/path` [8](#0-7) .
5. The response/error metadata differs depending on whether `secret/path` exists in the commit, letting the caller enumerate paths/objects using a field the API documents as a plain reference name.

Note: I could not fully verify the exact `command_description.go` entry for `show-ref` (whether it independently rejects the `:`/`@{` characters at the `gitcmd` layer) due to index truncation of that file; if `show-ref`'s command description already blocks such characters, the practical exploitability of step 4 may be reduced, though the underlying validation-layering defect (using the weak `isValidRefName` instead of `git.ValidateReference`) remains a real code-quality/security gap that should be fixed regardless.

// ValidateReference checks whether a reference looks valid. It aims to be a faithful implementation of Git's own
// `check_or_sanitize_refname()` function and all divergent behaviour is considered to be a bug. Please also refer to
// https://git-scm.com/docs/git-check-ref-format#_description for further information on the actual rules.
func ValidateReference(name string) error {
	if name == "HEAD" {
		return fmt.Errorf("HEAD reference not allowed")
	}

	// TODO: this can eventually be converted to use `strings.CutPrefix()`.
	if !strings.HasPrefix(name, "refs/") {
		return fmt.Errorf("reference is not fully qualified")
	}
	name = name[len("refs/"):]

	if len(name) == 0 {
		return fmt.Errorf("refs/ is not a valid reference")
	}

	if strings.HasSuffix(name, "/") {
		return fmt.Errorf("reference must not end with slash")
	}

	if strings.HasSuffix(name, ".") {
		return fmt.Errorf("reference must not end with dot")
	}

	if strings.Contains(name, "@{") {
		return fmt.Errorf("reference must not contain @{")
	}

	if strings.Contains(name, "..") {
		return fmt.Errorf("reference must not contain double dots")
	}

	for _, c := range name {
		switch c {
		case ' ', '\t', '\n':
			return fmt.Errorf("reference must not contain space characters")
		case ':', '?', '[', '\\', '^', '~', '*', '\177':
			return fmt.Errorf("reference must not contain special characters")
		}

		// Note that we treat some of the characters below 32 specially in the switch above so
		// that we can report back more precise error messages.
		if c < 32 {
			return fmt.Errorf("reference must not contain control characters")
		}
	}

// danglingReference reports whether the reference resolves to an object ID whose object is missing.
// Anything that doesn't conclusively confirm this returns false so the caller surfaces the original
// error as INTERNAL instead of misclassifying it.
func danglingReference(ctx context.Context, repo *localrepo.Repo, ref string) (danglingReferenceError, bool) {
	oid, err := repo.ResolveRevision(ctx, git.Revision(ref))
	if err != nil {
		return danglingReferenceError{}, false
	}

	// The reference resolves to an object ID; read the object to confirm it exists.
	// A missing object means the reference is dangling.
	var invalidObjectErr localrepo.InvalidObjectError
	if _, err := repo.ReadObjectInfo(ctx, oid.Revision()); errors.As(err, &invalidObjectErr) {
		return danglingReferenceError{reference: ref, oid: oid.String()}, true
	}

	return danglingReferenceError{}, false
}
