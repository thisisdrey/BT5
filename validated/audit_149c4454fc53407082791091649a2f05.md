Audit Report

## Title
Reentrancy stipend guard is bypassed for real value-transferring calls (`.transfer()`/`.send()`) - (File: `substrate/frame/revive/src/vm/evm/instructions/contract.rs`)

## Summary
The `run_call` heuristic in `substrate/frame/revive/src/vm/evm/instructions/contract.rs` selects `ReentrancyProtection` via a tuple match that checks `value.is_zero()` before `gas_limit == CALL_STIPEND`, causing any non-zero-value call — including calls made via Solidity's `.transfer()`/`.send()`, which pass `value != 0` together with `gas_limit = 2300` — to always resolve to `ReentrancyProtection::AllowReentry` instead of the intended `AllowNext`. This defeats the explicit stipend-based reentrancy guard that `pallet-revive` relies on because the classic Ethereum 2300-gas guarantee does not hold on revive's gas scale.

## Finding Description
In `run_call` [1](#0-0) , the match arms are evaluated top-down: `(false, _)` matches whenever `value.is_zero()` is `false`, regardless of the gas limit, so it catches the `(value != 0, gas_limit == 2300)` case before the second arm `(_, true)` — which is the one that actually applies `AllowNext` — ever gets a chance to match. Since Solidity's `.transfer(amount)`/`.send(amount)` are defined by passing a non-zero `value` together with `gas_limit = 2300` (the entire stipend mechanism), this exact call shape is captured by the first arm and always resolves to `AllowReentry`.

The `ReentrancyProtection::AllowNext` variant and its accompanying doc comment in `exec.rs` [2](#0-1)  explicitly states this guard exists because "due to gas scale differences that guarantee does not automatically hold in revive and we enforce it explicitly here" — confirming the codebase's own acknowledgment that the 2300-gas stipend alone is insufficient on revive without this explicit mechanism. The downstream enforcement (`allows_reentry`, `push_frame`) correctly denies reentry when `AllowNext`/`Strict` is set, meaning the bug is isolated entirely to the branch-selection logic in `run_call`, not the enforcement machinery itself.

## Impact Explanation
This is a runtime bug that compromises intended execution-model behavior of `pallet-revive`'s EVM-compatibility layer, matching the impact gate's "runtime bugs that compromise intended behavior." Solidity contracts deployed on revive that rely on the `.transfer()`/`.send()` stipend pattern for reentrancy safety — a widely used and historically-recommended idiom, especially for withdrawal patterns — silently lose that protection, allowing an attacker-controlled recipient contract to reenter the caller via `receive()`/`fallback()` during a value transfer.

## Likelihood Explanation
High. Every value-carrying `.transfer()`/`.send()` call, not just adversarial edge cases, triggers the vulnerable branch, since that is the default calling convention solc emits for these functions. No privileged access is required — a malicious contract only needs to be the recipient of a value transfer from any contract that assumes stipend-based reentrancy safety.

## Recommendation
Reorder the heuristic so `gas_limit == CALL_STIPEND` is checked independently of `value.is_zero()`, e.g. check `gas_limit == CALL_STIPEND` first and apply `AllowNext` whenever it matches, regardless of value being zero or non-zero. Add regression tests (extending the existing `Stipends.sol`/`ReentrancyAttacker` fixture [3](#0-2) ) asserting that a reentrant call attempted from a `receive()` triggered by a non-zero-value `.transfer()`/`.send()` is rejected with `ReentranceDenied`.

## Proof of Concept
1. Deploy a `Victim` contract that performs `payable(recipient).transfer(amount)` as part of a withdrawal function.
2. Deploy the repo's own `ReentrancyAttacker` fixture [3](#0-2)  as the recipient, whose `receive()` calls back into `msg.sender`.
3. Call `Victim.withdraw()`, triggering `.transfer()` with `value != 0` and `gas_limit = 2300`.
4. Observe that `run_call` [1](#0-0)  selects `(true, ReentrancyProtection::AllowReentry)` instead of `AllowNext`, so the nested reentrant call from `ReentrancyAttacker.receive()` back into `Victim` is not denied, unlike native Ethereum where the 2300-gas stipend alone would prevent this.

/// Level of reentrancy protection.
///
/// This needs to be specifed when a contract makes a message call. This way the calling contract
/// can specify the level of re-entrancy protection while the callee (and it's recursive callees) is
/// executing.
#[derive(Copy, Clone, PartialEq, Debug)]
pub enum ReentrancyProtection {

	/// Activate strict reentrancy protection. The direct callee and none of its own recursive

	/// However, due to gas scale differences that guarantee does not automatically hold in revive
	/// and we enforce it explicitly here.
	AllowNext,
}
