## Title
Relay control messages allow a peer to spoof another node's VPN address as the relay "from" identity, enabling relay-state poisoning and traffic redirection - (File: relay_manager.go)

## Summary
`relayManager.handleCreateRelayRequest` and `handleCreateRelayResponse` derive the "who is being relayed" identity (`RelayFromAddr`/`RelayToAddr`) entirely from attacker-controlled fields inside the `NebulaControl` message, without ever checking that the claimed `from` address matches the actual, certificate-verified VPN address of the peer (`h`) that sent the message. This is the same bug class as the WETH `approve(owner, spender)` issue: a caller-supplied identity parameter is trusted in place of the cryptographically authenticated identity of the caller.

## Finding Description
When a relay receives a `NebulaControl_CreateRelayRequest`, it extracts the claimed source address purely from the message body: [1](#0-0) 

`from` here comes from `m.RelayFromAddr` (or the legacy `OldRelayFromAddr`), fields fully controlled by the sending peer inside the encrypted Control payload. `h` is the `HostInfo` for the tunnel the message physically arrived on, and `h.vpnAddrs` is the address that was actually verified via the peer's certificate during the handshake (the "msg.sender" equivalent in this analogy). Nowhere in `handleCreateRelayRequest` (nor `handleCreateRelayResponse`) is `from` checked against `h.vpnAddrs`: [2](#0-1) [3](#0-2) 

The relay then installs state — `AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)` — keyed on the attacker-supplied `from` value, and later routes/forwards traffic addressed to that claimed VPN address through `h`'s tunnel: [4](#0-3) 

This mirrors the WETH vulnerability pattern exactly: `approve(address owner, address spender)` trusted an explicit `owner` argument instead of `msg.sender`; here, `handleCreateRelayRequest`/`handleCreateRelayResponse` trust an explicit `RelayFromAddr`/`RelayToAddr` argument instead of the handshake-verified `h.vpnAddrs`. The only checks performed are that the claimed addresses aren't the relay's own address: [5](#0-4) 

but no check ties the claimed "from" identity back to the actual sender's certificate-derived address.

## Impact Explanation
Any node holding a valid (CA-signed) certificate and an established tunnel to a relay node can claim to be relaying traffic "from" an arbitrary victim VPN address it does not own. The relay will then create `Established` relay state for that victim address pointed at the attacker's `HostInfo`/tunnel, and subsequently forward packets addressed to/from that victim address through the attacker's session (`outside.go`'s `handleOutsideRelayPacket` uses this relay-state lookup to route traffic). This enables:
- Relay-state poisoning: hijacking traffic intended for another mesh member.
- Man-in-the-middle / traffic redirection for the spoofed VPN address via the relay, since the relay believes the attacker's tunnel represents the victim's tunnel.

This is a legitimate authenticated-mesh member abusing protocol-level identity trust (no CA cert required beyond the attacker's own legitimate one), fitting "remote state poisoning" and traffic redirection impact categories.

## Likelihood Explanation
Exploitation only requires that the attacker be a normal (but malicious or compromised) member of the mesh capable of establishing a tunnel to a relay node (`relay.am_relay: true`) and sending a `CreateRelayRequest`/`CreateRelayResponse` Control message with a forged `RelayFromAddr`/`RelayToAddr`. No additional certificate forgery or handshake bypass is needed, making this straightforward to trigger by anyone who can reach a relay.

## Recommendation
Do not trust `RelayFromAddr` (or `RelayToAddr` where it identifies the requester) from the wire. Instead, derive the "from" identity of a `CreateRelayRequest`/`CreateRelayResponse` from `h.vpnAddrs` (the certificate-verified identity established during the handshake for the tunnel the Control message arrived on), and reject the message if the claimed address does not match one of `h.vpnAddrs`. This closes the gap between the claimed identity and the cryptographically authenticated one, analogous to removing the untrusted `owner` parameter and using the caller's own verified identity.

## Proof of Concept
1. Attacker `A` establishes a legitimate (CA-signed cert) tunnel to relay `R` (`relay.am_relay: true`).
2. `A` sends `NebulaControl_CreateRelayRequest` to `R` with `RelayFromAddr` set to victim `V`'s VPN address (an address `A` does not own) and `RelayToAddr` set to some other target `T`.
3. `handleCreateRelayRequest` on `R` checks only that `from` (`V`) and `target` (`T`) are not `R`'s own address, then calls `AddRelay(..., h=A's HostInfo, from=V, ...)`, installing relay state that maps `V` to `A`'s tunnel.
4. `R` now believes traffic to/from `V` should be relayed via `A`'s session, without ever validating that `A`'s certificate-verified VPN address is `V`. [6](#0-5)

func (rm *relayManager) HandleControlMsg(h *HostInfo, d []byte, f *Interface) {
	msg := &NebulaControl{}
	err := msg.Unmarshal(d)
	if err != nil {
		h.logger(f.l).Error("Failed to unmarshal control message", "error", err)
		return
	}

	var v cert.Version
	if msg.OldRelayFromAddr > 0 || msg.OldRelayToAddr > 0 {
		v = cert.Version1

		b := [4]byte{}
		binary.BigEndian.PutUint32(b[:], msg.OldRelayFromAddr)
		msg.RelayFromAddr = netAddrToProtoAddr(netip.AddrFrom4(b))

		binary.BigEndian.PutUint32(b[:], msg.OldRelayToAddr)
		msg.RelayToAddr = netAddrToProtoAddr(netip.AddrFrom4(b))
	} else {
		v = cert.Version2
	}

	// validate:
	switch msg.Type {
	case NebulaControl_CreateRelayRequest, NebulaControl_CreateRelayResponse:
		if msg.RelayFromAddr == nil {
			if f.l.Enabled(context.Background(), slog.LevelDebug) {
				h.logger(f.l).Debug("Control message received with nil RelayFromAddr", "type", msg.Type)
			}
			return
		} else if msg.RelayToAddr == nil {
			if f.l.Enabled(context.Background(), slog.LevelDebug) {
				h.logger(f.l).Debug("Control message received with nil RelayToAddr", "type", msg.Type)
			}
			return
		}
	}

	switch msg.Type {
	case NebulaControl_CreateRelayRequest:
		rm.handleCreateRelayRequest(v, h, f, msg)
	case NebulaControl_CreateRelayResponse:
		rm.handleCreateRelayResponse(v, h, f, msg)
	}
}

func (rm *relayManager) handleCreateRelayRequest(v cert.Version, h *HostInfo, f *Interface, m *NebulaControl) {
	//nil-checks for protoAddrToNetAddr handled by caller
	from := protoAddrToNetAddr(m.RelayFromAddr)
	target := protoAddrToNetAddr(m.RelayToAddr)

	logMsg := rm.l.With(
		"relayFrom", from,
		"relayTo", target,
		"initiatorRelayIndex", m.InitiatorRelayIndex,
		"vpnAddrs", h.vpnAddrs,
	)

	logMsg.Info("handleCreateRelayRequest")
	// Is the source of the relay me? This should never happen, but did happen due to
	// an issue migrating relays over to newly re-handshaked host info objects.
	if f.myVpnAddrsTable.Contains(from) {
		logMsg.Error("Discarding relay request from myself", "myIP", from)
		return
	}

	// Is the target of the relay me?
	if f.myVpnAddrsTable.Contains(target) {
		existingRelay, ok := h.relayState.QueryRelayForByIp(from)
		if ok {
			switch existingRelay.State {
			case Requested:
				ok = h.relayState.CompleteRelayByIP(from, m.InitiatorRelayIndex)
				if !ok {
					logMsg.Error("Relay State not found")
					return
				}
			case Established:
				if existingRelay.RemoteIndex != m.InitiatorRelayIndex {
					// We got a brand new Relay request, because its index is different than what we saw before.
					// This should never happen. The peer should never change an index, once created.
					logMsg.Error("Existing relay mismatch with CreateRelayRequest",
						"existingRemoteIndex", existingRelay.RemoteIndex)
					return
				}
			case Disestablished:
				if existingRelay.RemoteIndex != m.InitiatorRelayIndex {
					// We got a brand new Relay request, because its index is different than what we saw before.
					// This should never happen. The peer should never change an index, once created.
					logMsg.Error("Existing relay mismatch with CreateRelayRequest",
						"existingRemoteIndex", existingRelay.RemoteIndex)
					return
				}
				// Mark the relay as 'Established' because it's safe to use again
				h.relayState.UpdateRelayForByIpState(from, Established)
			case PeerRequested:
				// I should never be in this state, because I am terminal, not forwarding.
				logMsg.Error("Unexpected Relay State found",
					"existingRemoteIndex", existingRelay.RemoteIndex,
					"state", existingRelay.State)
			}
		} else {
			_, err := AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)
			if err != nil {
				logMsg.Error("Failed to add relay", "error", err)
				return
			}
		}

		relay, ok := h.relayState.QueryRelayForByIp(from)
		if !ok {
			logMsg.Error("Relay State not found", "from", from)
			return
