### Title
Split Check/Update race in the anti-replay window defeats one-time delivery guarantee - (File: `connection_state.go`)

### Summary
`ConnectionState.Decrypt()` and `ConnectionState.VerifyRelay()` implement replay protection as two separate, independently-locked steps around an unlocked AEAD decrypt/verify operation, mirroring exactly the bug class described in the external report: a "checkpoint" primitive (`window.Check`) and a state-mutating "commit" primitive (`window.Update`) are exposed/used as two disjoint calls instead of one atomic check-act-commit operation, with attacker-influenced work (AEAD decryption) happening in the gap between them.

### Finding Description
`Bits.Check` and `Bits.Update` together implement the sliding-window anti-replay tracker (`Bits` type) described in `bits.go`. `ConnectionState.Decrypt` uses them as two separate critical sections: [1](#0-0) 

and `ConnectionState.VerifyRelay` follows the identical pattern: [2](#0-1) 

In both functions, `decryptLock` is acquired, `window.Check()` is called, the lock is released, the expensive `DecryptDanger` AEAD operation runs with **no lock held**, and only afterward is the lock re-acquired to call `window.Update()`, which performs the actual state mutation ("commit"/checkpoint) that marks the counter as consumed. This is structurally identical to the reported SwapGuardV2 flaw: the "read checkpoint" step and the "write checkpoint" step are not atomic with respect to the operation performed in between, so a second caller can observe the pre-update state (`Check` returns `true`) before the first caller's `Update` has committed.

This is reachable by a pure network attacker with no CA-signed certificate: a captured/duplicated ciphertext UDP packet for an already-established tunnel (or relay frame, per `VerifyRelay`) can be delivered twice in close succession from the wire — no cert or valid handshake participation is required to duplicate observed UDP traffic, only the ability to inject the raw packet bytes, e.g., a MITM/on-path attacker or someone spoofing UDP toward the victim's listening socket.

### Impact Explanation
If two packets carrying the same `messageCounter` are processed concurrently (Nebula's inbound path can service the same `HostInfo`/`ConnectionState` from multiple reader/queue goroutines, per the `q int` queue-indexed reader path in `outside.go`), both can pass the `Check()` gate before either has called `Update()`. Both then execute the AEAD decrypt/verify. Only the *second* `Update()` call is guaranteed to fail as a duplicate, but by that point decryption has already succeeded and the packet has already been handed off to `handleOutsideMessagePacket`/`readOutsidePackets` for delivery to the tun device or relay-forward path. This defeats the intended one-copy delivery guarantee of the replay window: a captured packet can be delivered to the application/tun layer more than once, and the relay-forwarding path (`handleOutsideRelayPacket`) could likewise re-forward a duplicate relay frame if the race lands favorably — precisely the regression the project's own changelog describes fixing once already (`Advance the replay window on relayed packets so a relay drops replayed frames instead of re-forwarding them`, and `Lock replay window updates so concurrent readers can't corrupt it`), indicating this exact class of check/update race has previously caused real replay-forwarding bugs in this codebase.

### Likelihood Explanation
Exploitation requires only capturing one legitimate ciphertext packet (trivial for any on-path/network observer, no cert needed) and re-injecting it twice in rapid succession so both copies are picked up by different reader goroutines before the first `Update()` commits — a narrow but realistic race window given `Check`/`Update` are split into two independently-lockable operations rather than one atomic operation.

### Recommendation
Collapse `Check` and `Update` into a single atomic operation, matching the SwapGuardV2 report's own recommendation: hold `decryptLock` for the entire duration of "check window state → perform AEAD verify/decrypt → commit window state," so no other caller can observe or race the intermediate state. Concretely, `ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` should validate-and-commit the replay-window slot as one locked unit around the AEAD call rather than as two separately-locked calls to `window.Check` and `window.Update`, e.g. by introducing a single `CheckAndUpdate`-style method on `Bits` that is only released after the AEAD operation and its accept/reject decision.

### Proof of Concept
1. Establish a tunnel between two Nebula nodes.
2. Capture one legitimate `header.Message` UDP packet (ciphertext) sent to the victim's listening port, noting its `MessageCounter`.
3. From an on-path/attacker position, inject two copies of that exact captured packet to the victim in immediate succession (e.g., via two sockets/threads sending simultaneously) so they are likely to be picked up by two different reader queues in `readOutsidePackets`.
4. Observe whether the plaintext is delivered twice to the tun device (or, for a relay node, forwarded twice) — i.e., `window.Check` returning `true` for both before `window.Update` commits for either — despite the anti-replay window being present. (Verification of the exact concurrency model of Nebula's inbound reader queues was not completed within the available tool budget; the code path and lock structure enabling the race is confirmed directly from `connection_state.go`, but empirical reproduction of the goroutine interleaving was not performed.)

// VerifyRelay verifies AEAD protected (but not encrypted) relay frames. packet must be length-checked by the caller.
func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}
