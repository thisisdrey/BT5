## Title
Floating-point precision loss in the TRC10 Bancor-style exchange pricing formula allows value extraction from `Exchange` pools - (`chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
The WLEO incident involved an attacker exploiting flawed token-minting/accounting logic in an ERC-20 wrapper contract to extract real ETH from a Uniswap liquidity pool without providing equivalent backing value. The closest reachable analog in java-tron is the built-in TRC10 `Exchange` (a Bancor-style AMM), where the legacy, non-hardened pricing math is computed using Java `double` floating point arithmetic in `ExchangeProcessor`, rather than exact fixed-point/BigDecimal arithmetic.

### Finding Description
Any account can call `ExchangeTransactionActuator` (reachable via a signed `ExchangeTransactionContract` broadcast by any user) to swap `tokenID` for `anotherTokenID` inside an on-chain `Exchange` pool. The actual swap math is delegated to `ExchangeCapsule.transaction()`, which selects a `Processor`: [1](#0-0) 

When the hardened path is not used, `ExchangeProcessor` performs the constant-relay-supply computation using `double` math and `Maths.pow`, casting the result down to `long`: [2](#0-1) 

By contrast, the "hardened" `SafeExchangeProcessor` uses `BigDecimal` with explicit rounding to avoid these issues: [3](#0-2) 

The existing test suite explicitly documents that the legacy (double) and hardened (BigDecimal) processors produce **different** results for the same input, and that the legacy path is not merely a rounding variant but structurally imprecise: [4](#0-3) 

`ExchangeTransactionActuator.execute()` and its `doValidate()` both invoke `exchangeCapsule.transaction(...)`, which mutates the pool's `firstTokenBalance`/`secondTokenBalance` internal supply based on this same double-precision result and directly credits/debits the caller's real TRX/TRC10 balances: [5](#0-4) 

Repeated small swaps that exploit `double` truncation/rounding behavior in `exchangeToSupply`/`exchangeFromSupply` (analogous to how the WLEO wrapper let an attacker mint tokens disproportionate to real backing) could allow a caller to extract more real asset value (TRX or TRC10 tokens) from the pool than they contributed, draining liquidity providers—mirroring how the WLEO attacker drained real ETH from the Uniswap pool by exploiting a flawed value-accounting path.

### Impact Explanation
If exploitable, an attacker could repeatedly execute low-cost `ExchangeTransactionContract` swaps to slowly (or, depending on precision drift, non-trivially) extract TRX/TRC10 asset value from a pool in excess of what they deposited, draining funds from other pool participants/liquidity — a direct unauthorized value-extraction / theft-of-funds scenario, matching the WLEO incident's "cast token, drain real asset" pattern. This is Medium severity because it requires the legacy (non-hardened) math path to be active and requires many repeated transactions to accumulate meaningful value.

### Likelihood Explanation
Reachability is confirmed: this is directly triggerable by any account via a normal signed `ExchangeTransactionContract`, `ExchangeInjectContract`, or `ExchangeWithdrawContract` broadcast — no special privilege required. However, I could **not** confirm whether the network currently runs with the hardened `SafeExchangeProcessor` path always active (in which case this is already mitigated) or whether the legacy `ExchangeProcessor` double-math path remains reachable in production depending on the `allowHarden()`/`AllowHardenExchangeCalculation` dynamic property's default and rollout status. This materially affects likelihood and I was unable to verify it within the available searches.

### Recommendation
Confirm whether `AllowHardenExchangeCalculation` is enabled by default in current mainnet chain parameters; if not, prioritize enabling/enforcing `SafeExchangeProcessor` (BigDecimal, rounding-controlled) for all exchange calculations and deprecate the legacy `double`-based `ExchangeProcessor` path entirely, since it is a known source of precision loss in AMM-style constant-relay-supply formulas.

### Proof of Concept
Not independently reproduced beyond static analysis; the existing repository test `ExchangeProcessorTest.testStrictMath` (lines 218–280) already demonstrates that legacy `ExchangeProcessor.exchange(...)` yields results systematically different from `SafeExchangeProcessor.INSTANCE.exchange(...)` for identical inputs, corroborating the precision-loss root cause. Full weaponization (repeated-swap value extraction) would require chain-parameter confirmation not available in this analysis. [6](#0-5)

    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
