### Title
Classic liquidation always reverts when it would fully repay the liquidatee's last remaining debt in the targeted bank - ([File: programs/marginfi/src/state/marginfi_account.rs])

### Summary
`lending_account_liquidate` calls `liquidatee_liab_bank_account.repay(liab_amount_final)` [1](#0-0)  and then unconditionally validates the post-liquidation state via `check_post_liquidation_condition_and_get_account_health`, which requires the targeted liability balance to still be non-empty: `check!(!liability_balance.is_empty(BalanceSide::Liabilities), MarginfiError::ExhaustedLiability);` [2](#0-1) . If a liquidator's repayment (`liab_amount_final`) happens to fully clear the liquidatee's remaining debt in `liab_bank`, this check reverts the entire instruction, mirroring the Fluid DEX bug class where full clearance of debt is structurally impossible through the primary liquidation path.

### Finding Description
`check_post_liquidation_condition_and_get_account_health` is invoked at the end of `lending_account_liquidate` and hard-requires that the liability balance for `liab_bank` is *not* empty post-repayment [3](#0-2) . There is no branch or exemption for the case where the repayment exactly (or by rounding, effectively) exhausts the debt. Since the liquidator supplies `asset_amount` (collateral to seize) as the primary input, and the corresponding `liab_amount_final` (debt reduction) is a derived, price-dependent quantity [4](#0-3) , a liquidator attempting to seize all remaining collateral to close out a small/final debt position will trigger `repay()` to zero out the liability balance, and the subsequent `ExhaustedLiability` check will always fail, reverting the whole transaction (withdraw, repay, and fee transfers all undone).

This differs functionally from Fluid's `hf = type(uint256).max` mechanism (marginfi computes health as a signed difference `assets - liabs`, not a ratio, so there is no infinite-HF artifact), but the *effect* is the analog described in the report: the protocol structurally forbids a liquidation transaction from fully closing out the last debt in a bank via the classic liquidation path, because the post-condition explicitly requires a residual non-zero liability.

By contrast, the newer receivership liquidation path (`start_liquidation`/`end_liquidation`) explicitly supports and tests full closure of positions, including full repay and full withdraw, and the liquidatee account can end with **zero active balances** [5](#0-4) . This confirms the classic path's `ExhaustedLiability` invariant is a real functional restriction (not a shared invariant across all liquidation flows), and it is not documented in `SECURITY.md` as a known accepted limitation.

### Impact Explanation
When a liquidatee's position has debt in `liab_bank` that is small enough (or is the only remaining liability) such that a liquidator's natural attempt to close it out entirely would zero it, the classic `lending_account_liquidate` instruction reverts every time. This is a partial-liquidation-only DoS: a liquidator cannot use classic liquidation to fully clear a specific bank's debt when the repayment happens to exhaust it, forcing liquidators to either (a) leave residual dust debt behind, or (b) fail. Combined with tight minimum-payback/precision constraints on small remaining balances, this can leave residual bad debt un-liquidatable through classic liquidation, exposing the protocol/depositors to lingering risk on that residual debt (interest accrual, price risk) until it's handled via a different mechanism (e.g., receivership liquidation or bankruptcy). This does not cause outright loss of funds by itself since the tx simply reverts (no state corruption or theft), but it degrades the core liquidation safety mechanism for the classic path.

### Likelihood Explanation
Likely to occur naturally whenever a liquidator computes `asset_amount` intending to close out the last debt exactly, or when small residual debts remain after prior partial liquidations — no attacker-controlled exploit is required, just organic liquidation activity against small/final debt balances. However, the protocol provides the receivership liquidation path as an alternative that explicitly supports full closeout, which mitigates the overall severity since liquidators/keepers can route full-closure liquidations through that instruction instead.

### Recommendation
In `check_post_liquidation_condition_and_get_account_health` (`programs/marginfi/src/state/marginfi_account.rs`), allow the liquidatee's liability balance for the targeted bank to become fully empty as a valid terminal state (mirroring how `repay_all`/`close_balance` normally handle full closure elsewhere in the codebase, e.g. `programs/marginfi/src/state/marginfi_account.rs:1681-1735`), rather than unconditionally reverting with `ExhaustedLiability`. This should only require that the account health did not worsen, not that the specific bank retains a residual liability.

### Proof of Concept
Not executed; behavior is derived directly from the `check!(!liability_balance.is_empty(BalanceSide::Liabilities), MarginfiError::ExhaustedLiability)` invariant in `check_post_liquidation_condition_and_get_account_health` [2](#0-1)  combined with the unconditional call site in `lending_account_liquidate` [6](#0-5) . A concrete on-chain reproduction (constructing a position with a single small debt, then liquidating asset_amount sized to exactly clear it) would need to be run in the bankrun test harness to confirm exact revert behavior and rounding edge cases, which was not verified within the scope of this analysis.

```rust
pub fn check_post_liquidation_condition_and_get_account_health<'info>(
    marginfi_account: &MarginfiAccount,
    remaining_ais: &'info [AccountInfo<'info>],
    bank_pk: &Pubkey,
    pre_liquidation_health: I80F48,
) -> MarginfiResult<I80F48> {
    check!(
        !marginfi_account.get_flag(ACCOUNT_IN_FLASHLOAN),
        MarginfiError::AccountInFlashloan
    );

    let liability_balance = marginfi_account
        .lending_account
        .balances
        .iter()
        .find(|b| b.is_active() && b.bank_pk == *bank_pk)
        .ok_or(MarginfiError::LendingAccountBalanceNotFound)?;

    check!(
        !liability_balance.is_empty(BalanceSide::Liabilities),
        MarginfiError::ExhaustedLiability
    );

    check!(
        liability_balance.is_empty(BalanceSide::Assets),
        MarginfiError::TooSeverePayoff
    );
```
