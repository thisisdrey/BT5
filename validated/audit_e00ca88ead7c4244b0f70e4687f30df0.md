I investigated whether java-tron has an analog to the Rizin GDB-profile stack buffer overflow (fixed-size buffer overflow from parsing untrusted external data without bounds checks). Since java-tron is pure Java, classic C-style stack buffer overflows are not directly possible, so the meaningful analog would be unchecked-length copies from attacker-controlled transaction data into fixed-size arrays — which in Java manifests as unhandled `ArrayIndexOutOfBoundsException`s rather than memory corruption.

The most relevant candidate is `PrecompiledContracts.VerifyTransferProof.execute()`, which parses a Sapling shielded-transfer proof-verification precompile input: [1](#0-0) 

Here `spendOffset`, `spendAuthSigOffset`, and `receiveOffset` are read directly from attacker-supplied `data` via `parseInt(data, 0/32/64)` and then used, unchecked against `data.length`, as offsets into further `parseInt`/`System.arraycopy` calls at lines 1492–1531 (e.g. `System.arraycopy(data, spendOffset + 320 * i, nullifier[i], 0, 32)`): [2](#0-1)
