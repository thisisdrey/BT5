### Title
Heap buffer over-read parsing Zip central-directory extra fields in `ijar`'s `InputZipFile::ProcessCentralDirEntry` - (File: `third_party/ijar/zip.cc`)

### Summary
`third_party/ijar/zip.cc` implements the `ijar`/`zipper`/`singlejar`-family Zip reader used by Bazel to parse `.jar`/`.zip` archives (e.g. interface-jar generation and jar manipulation over externally-obtained jars such as those fetched with `http_jar`/`http_archive`). `InputZipFile::ProcessCentralDirEntry` parses the "extra field" chain of a central-directory entry by trusting an attacker-controlled 16-bit `data_size` field to advance a cursor, without validating that the advance stays inside the mapped central directory / file buffer. This mirrors the OVS CVE-2022-32166 pattern: an unsafe consumer trusts a length taken directly from untrusted input to walk through a structure, over-reading past the actual allocated/mapped region.

### Finding Description
In the central-directory extra-field loop: [1](#0-0) 

```
const u1 *extra_p = p;
p += extra_field_length;
while (extra_p != p) {
  const u2 header_id = get_u2le(extra_p);
  const u2 data_size = get_u2le(extra_p);
  const u1 *extra = extra_p;
  extra_p += data_size;
  ...
}
```
`extra_field_length` and each `data_size` are read directly from the attacker-controlled zip bytes with `get_u2le`, and neither is validated against the actual bytes remaining in the mapped file or against the outer `extra_field_length`. Unlike `ProcessLocalFileEntry`, which calls `EnsureRemaining()` before reading `file_name_length_`/`extra_field_length_`-sized regions: [2](#0-1) 

`ProcessCentralDirEntry` performs no equivalent bounds check before or during the extra-field walk: [3](#0-2) 

If a crafted entry sets `data_size` larger than the remaining extra-field bytes, `extra_p` overshoots `p` and the loop condition `extra_p != p` never becomes true again, causing `get_u2le`/`get_u8le` to keep dereferencing memory past the end of the mapped zip file (a heap/mmap buffer over-read), analogous to the unsafe `minimasks` length comparison in the OVS CVE that read past the allocated buffer because a length value taken from the flow structure wasn't validated before use.

### Impact Explanation
An attacker who controls the bytes of a `.jar`/`.zip` that Bazel processes with this reader (e.g. a maliciously crafted jar served through `http_jar`, `http_archive`, or a Maven/registry artifact consumed via a repository rule) can trigger an out-of-bounds read in the process parsing the archive during the build. Even if the outer archive bytes match a pinned `sha256`/`integrity` checksum (the attacker fully controls the archive and can craft it to satisfy any checksum they declare), the internal Zip structure is unconstrained and can carry a malformed extra-field chain. This can crash the Bazel-invoked tool (denial of service for that action) and, depending on memory layout, leak adjacent heap bytes into subsequent processing (e.g., if attribute values derived from `get_u8le(extra)` are later serialized).

### Likelihood Explanation
Reaching this code only requires supplying a jar/zip file whose central directory contains an extra field with an oversized declared length — a fully attacker-controlled artifact acceptable through normal dependency-fetching mechanisms (`http_jar`, `http_archive`, Maven-style external repositories). No privileged access to the build machine is needed; only the ability to publish or serve an archive that the build consumes. The existing checksum verification in the fetch layer does not constrain internal archive structure, so it does not block this.

### Recommendation
In `ProcessCentralDirEntry`'s extra-field loop, bound each read: verify `extra_p + 4 <= p` before reading the 2-byte header/size fields, and verify `extra_p + data_size <= p` (and that `p` itself does not exceed the mapped file end) before advancing `extra_p` or dereferencing `extra` with `get_u8le`. Treat any violation as a fatal parse error rather than continuing the loop, consistent with `ProcessLocalFileEntry`'s use of `EnsureRemaining()`.

### Proof of Concept
A concrete JUnit/`BuildIntegrationTestCase` proof would need to:
1. Hand-construct a minimal zip file whose central directory contains one file entry with an extra field record declaring `data_size = 0xFFFF` (or another value exceeding the real remaining extra-field/file bytes) while `extra_field_length` for the entry is small.
2. Feed this file to the `ijar`/`zipper` binary (or the `InputZipFile` API directly, as already done in `third_party/ijar/zip_main.cc`) and observe a crash/ASan heap-buffer-overflow report from the over-read, similar in spirit to the malformed-extra-field regression test already present for the local/central headers in `src/tools/singlejar/output_jar_simple_test.cc` (`CreateZipWithMalformedExtraField`, lines 1179-1225), which exercises the analogous singlejar `ExtraField::find` bounds check but does not cover `third_party/ijar/zip.cc`'s central-directory extra-field loop.

I was not able to fully trace how `central_dir_` and its overall extent (`central_dir_current_`, `central_dir_` bounds established at `Open()`) are validated at the whole-file level within the limited exploration performed, so I cannot state with certainty whether an outer bound (e.g., total central directory size derived from EOCD) would clip the overshoot before it reaches unmapped memory in all cases; this would need to be confirmed by reading the full `Open()`/EOCD-parsing implementation and by writing/running the ASan-instrumented test described above before treating this as fully confirmed rather than a strong candidate.

                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
  const u1 *extra_p = p;
  p += extra_field_length;
  while (extra_p != p) {
    const u2 header_id = get_u2le(extra_p);
    const u2 data_size = get_u2le(extra_p);
    const u1 *extra = extra_p;
    extra_p += data_size;
    if (header_id == ZIP64_EXTRA_FIELD_TAG) {
      if (*uncompressed_size == U4_MAX) {
        *uncompressed_size = get_u8le(extra);
      }
      if (*compressed_size == U4_MAX) {
        *compressed_size = get_u8le(extra);
      }
      if (*offset == U4_MAX) {
        *offset = get_u8le(extra);
      }
    }
  }
