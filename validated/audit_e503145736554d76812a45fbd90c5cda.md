### Title
Unauthenticated Account Permission/Multisig Disclosure Oracle via `getTransactionSignWeight` (`/wallet/getsignweight`, gRPC `GetTransactionSignWeight`) - (File: `actuator/src/main/java/org/tron/core/utils/TransactionUtil.java`)

### Summary
The unauthenticated read-only RPC/HTTP endpoint `GetTransactionSignWeight` (exposed via gRPC in `Wallet` service and via HTTP `POST /wallet/getsignweight`) accepts an arbitrary, unsigned or partially-signed `Transaction` whose only requirement is that the embedded contract carries a valid `owner_address`. It then looks up that address in the `AccountStore`, resolves the account's `Permission` object (owner/active permission, keys, weights, threshold, operations bitmap), and returns it in full, without verifying that the caller possesses any signing key for that account.

### Finding Description
`TransactionUtil.getTransactionSignWeight` extracts the `owner` from the first contract of the supplied transaction, fetches the corresponding `AccountCapsule` from the `AccountStore`, resolves the `Permission` by `permissionId`, and attaches it to the response via `tswBuilder.setPermission(permission)`: [1](#0-0) 

This lookup happens before any signature-weight check is meaningful — a caller can submit zero signatures (or garbage `owner_address`-only data) and still receive the full `Permission` structure for any existing account, since `permission` is set on the builder regardless of whether enough weight was ever reached: [2](#0-1) 

The HTTP servlet backing this call performs no authentication or ownership check; it simply parses the POST body into a `Transaction` and forwards it: [3](#0-2) 

The gRPC handler is likewise unauthenticated and directly forwards the raw request: [4](#0-3) 

The sibling endpoint `GetTransactionApprovedList` (`wallet.getTransactionApprovedList`, `/wallet/getapprovedlist`) exhibits the same pattern — it resolves and returns the `Permission` of any `owner_address` supplied in an unsigned transaction: [5](#0-4) 

This is structurally analogous to the Capgo `get_identity_apikey_only` bug class: an unauthenticated query endpoint takes a caller-supplied identifier (there: an API key; here: an `owner_address` embedded in an arbitrary/self-crafted transaction) and returns sensitive account-identity/security metadata (there: the owning `user_id`; here: the account's full multisig permission configuration — signer addresses, individual weights, and the approval threshold) without requiring the caller to prove any relationship to that account.

### Impact Explanation
An anonymous API client can enumerate any TRON account address and, by crafting a transaction with that address as `owner_address` (no valid signature required), retrieve:
- The full list of active/owner permission `Key` entries (addresses authorized to sign for the account) and their individual weights.
- The signing threshold required to authorize transactions.
- Which permission (`permissionId`) governs which contract-type operations (via the `operations` bitmap check flow).

This discloses the internal governance/multisig structure of any account — information that account owners may consider private (e.g., corporate/custodial multisig setups, cold/hot key separation, threshold policy) — and lets an attacker map out weak points in an account's signer set (e.g., which keys carry the most weight) to prioritize social-engineering or key-compromise targeting. It does not by itself allow fund theft, matching the Medium severity classification of the analogous Capgo finding (information/identity disclosure oracle, not direct fund loss).

### Likelihood Explanation
High likelihood of exploitation: the endpoint is unauthenticated, requires only a well-formed protobuf `Transaction` with an `owner_address` set (any valid TRON address, including addresses that never signed anything), and can be queried at will over both HTTP and gRPC. No rate limiting beyond the generic `RateLimiterServlet` is evident, and no ownership/ACL check gates the `Permission` disclosure.

### Recommendation
Restrict the amount of sensitive permission detail returned by `getTransactionSignWeight`/`getTransactionApprovedList` to callers who cannot prove control of the queried account, or require at least one valid signature over the transaction hash from a key that could plausibly belong to the account before returning full `Permission` contents (keys, weights, threshold). Alternatively, provide only the minimal information needed by legitimate wallet clients (e.g., current weight vs. required threshold) without echoing back the full signer-key list and per-key weights for accounts the caller has not authenticated against.

### Proof of Concept
1. Pick any known TRON account address `A` (e.g., from a public exchange deposit address or on-chain history).
2. Construct an unsigned `Transaction` containing a single contract (e.g., `TransferContract`) with `owner_address = A` and no valid signature, or with `permissionId` left at default.
3. POST it to `http://<node>/wallet/getsignweight` (or call gRPC `GetTransactionSignWeight`), e.g.:
```
POST /wallet/getsignweight
{
  "transaction": { "raw_data": { "contract": [ { "type": "TransferContract",
        "parameter": { "value": { "owner_address": "<A_hex>", "to_address": "<any_hex>", "amount": 1 } } } ] } }
}
```
4. The response includes `result.code = PERMISSION_ERROR`/`NOT_ENOUGH_PERMISSION` but also a `permission` object populated from `tswBuilder.setPermission(permission)` in `TransactionUtil.getTransactionSignWeight`, disclosing the full key list, weights, and threshold for account `A`, even though the requester supplied zero valid signatures for that account.
