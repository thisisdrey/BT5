## Title
Floating-point division-before-multiplication precision loss in `UnfreezeBalanceV2Processor.updateVote` causes incorrect vote recalculation — (File: actuator/src/main/java/org/tron/core/vm/nativecontract/UnfreezeBalanceV2Processor.java)

### Summary
The bug class described in the report (dividing before multiplying, causing precision loss versus the mathematically-safer "multiply then divide" order) has a direct analog in java-tron's vote-recalculation logic executed whenever an account calls `UnfreezeBalanceV2`. The affected computation determines each vote's new weight after part of a stake is unfrozen.

### Finding Description
When an account owner unfreezes part of their staked TRX via `UnfreezeBalanceV2Contract`/`UnfreezeBalanceV2Actuator`, execution flows into `UnfreezeBalanceV2Processor.execute` → `updateVote`. There, when the account's remaining TRON Power is less than its total existing vote count, each vote is rescaled: [1](#0-0) 

The expression `(double) vote.getVoteCount() / totalVote * ownedTronPower / TRX_PRECISION` performs division (`voteCount / totalVote`) before multiplying by `ownedTronPower`, exactly the anti-pattern flagged in the report (`amountWithDec18 / (10 ** fixDec)` computed before any compensating multiplication). Because this is done in floating-point `double` arithmetic rather than integer/BigInteger math with multiply-first ordering (as the codebase itself does correctly elsewhere, e.g. `MarketUtils.multiplyAndDivide` at [2](#0-1)  and the hardened resource-weight calculations in `RepositoryImpl.usageToBalance`/`calculateGlobalEnergyLimit` at [3](#0-2) ), the intermediate division truncates precision early, and subsequent double-to-long casting (`(long)`) can systematically round the recomputed vote weight up or down relative to the mathematically exact `voteCount * ownedTronPower / (totalVote * TRX_PRECISION)`.

### Impact Explanation
`newVoteCount` values feed directly into `VotesCapsule`/`accountCapsule.addAllVotes`, which are later used by `VoteRewardUtil.computeReward` to calculate SR voting rewards proportional to recorded vote counts: [4](#0-3) . If the division-before-multiplication ordering causes vote counts to be rounded inconsistently (e.g., systematically favorable roundings across many unfreeze operations on many accounts/votes), an account can end up with recorded vote weight that does not correspond to its actual backing TRON Power, letting it accrue disproportionate voting rewards relative to real stake — an unbacked-reward / fund-drain vector reachable by any account holder issuing ordinary `UnfreezeBalanceV2` transactions.

### Likelihood Explanation
This code path executes on every `UnfreezeBalanceV2` transaction where the account has existing votes and remaining TRON Power below total votes — a very common, fully permissionless scenario requiring no special privileges, just staking, voting, then partially unfreezing. The magnitude of the precision error per call is small, but it is deterministic and repeatable, so it can be amplified via many small unfreeze operations across many vote entries.

### Recommendation
Replace the floating-point division-then-multiply with an exact multiply-then-divide computation using `BigInteger`/`Math.multiplyExact`, mirroring the pattern already used in `MarketUtils.multiplyAndDivide` and the hardened resource calculations in `RepositoryImpl`/`ResourceProcessor`:
```java
long newVoteCount = BigInteger.valueOf(vote.getVoteCount())
    .multiply(BigInteger.valueOf(ownedTronPower))
    .divide(BigInteger.valueOf(totalVote).multiply(BigInteger.valueOf(TRX_PRECISION)))
    .longValueExact();
```
This avoids the early-division precision loss and keeps recorded vote weight consistent with actual backing power.

### Proof of Concept
1. Freeze TRX and vote for multiple SRs so `accountCapsule.getVotesList()` has several entries with varying `voteCount`.
2. Call `UnfreezeBalanceV2` for a portion of the stake such that `ownedTronPower < totalVote * TRX_PRECISION`, triggering the rescale branch in `updateVote` ( [5](#0-4) ).
3. Compare the resulting `newVoteCount` per vote against the exact integer computation `voteCount * ownedTronPower / (totalVote * TRX_PRECISION)`; repeated small unfreeze operations show accumulated rounding drift from double-precision division-before-multiplication, analogous to `testGlobalEnergyLimitV2CorrectVsDoublePrecisionLoss` which the codebase itself uses to demonstrate this exact class of bug elsewhere: [6](#0-5) .
4. Over many cycles, the drifted vote counts feed into `VoteRewardUtil.computeReward`, producing rewards inconsistent with actual staked TRON Power.

```java
  private static long computeReward(long beginCycle, long endCycle,
                                    AccountCapsule accountCapsule, Repository repository) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    for (Protocol.Vote vote : accountCapsule.getVotesList()) {
      byte[] srAddress = vote.getVoteAddress().toByteArray();
      BigInteger beginVi = repository.getDelegationStore().getWitnessVi(beginCycle - 1, srAddress);
      BigInteger endVi = repository.getDelegationStore().getWitnessVi(endCycle - 1, srAddress);
      BigInteger deltaVi = endVi.subtract(beginVi);
      if (deltaVi.signum() <= 0) {
        continue;
      }
      long userVote = vote.getVoteCount();
      reward += deltaVi.multiply(BigInteger.valueOf(userVote))
          .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
    }
    return reward;
```
