## Title
`pallet-lottery` picks the winner using randomness whose freshness is never validated against the ticket-purchase window - ([File: substrate/frame/lottery/src/lib.rs])

## Summary
`Pallet::generate_random_number` in `substrate/frame/lottery/src/lib.rs` calls `T::Randomness::random(...)` and discards the returned `known_since` block number via `let (random_seed, _) = ...`, so the pallet never confirms the randomness postdates the ticket-buying deadline. `on_initialize` triggers payout purely based on `payout_block <= n`, with no comparison against `config.start.saturating_add(config.length)`, unlike `polkadot/runtime/common/src/auctions/mod.rs::check_auction_end`, which explicitly checks `late_end <= known_since` before trusting the seed.

## Finding Description
`choose_ticket`/`generate_random_number` compute the winning ticket as:
```rust

    let (random_seed, _) = T::Randomness::random(&(T::PalletId::get(), seed).encode());
    ...
}
``` [1](#0-0) 

The `Randomness` trait documentation explicitly requires callers to check the returned block number against the last commitment time before trusting the seed: [2](#0-1) 

The pallet's `on_initialize` triggers payout solely from `payout_block <= n`, without checking that the randomness `known_since` postdates `config.start + config.length`: [3](#0-2) 

The pallet's own source acknowledges this gap via an open TODO: [4](#0-3) 

By contrast, `auctions.rs` faces the identical problem and correctly checks `late_end <= known_since` before consuming the seed, deferring otherwise: [5](#0-4) 

`pallet-lottery` implements no equivalent guard, so if the configured `Randomness` type's seed for the payout block is knowable/predictable before the ticket-buying window (`start + length`) closes, an unprivileged caller can predict or observe the seed and time their `buy_ticket` calls (controlling `TicketsCount`/ticket index) so that `random_number % total` resolves to their own ticket.

## Impact Explanation
This allows an unprivileged participant to bias which account is selected as `winner` and receives `lottery_balance` from the pot account, a wrong-beneficiary payout achieved entirely through the public `buy_ticket` extrinsic, provided the runtime's `Config::Randomness` does not itself guarantee freshness relative to the ticket-buying deadline. This is a real structural gap in the pallet's own logic — it is present in `substrate/frame/lottery/src/lib.rs` regardless of runtime, though the degree of exploitability is influenced by which `Randomness` implementation a runtime chooses.

## Likelihood Explanation
Any signed account able to call `buy_ticket` can exploit this deterministically whenever the runtime's `Randomness` provider doesn't independently guarantee freshness past the ticket-buying deadline. The lottery pallet's `delay` field exists precisely to allow fresh randomness to accumulate, but the code never actually verifies this occurred, making the check-then-use pattern from `auctions.rs` a proven, directly comparable in-repo precedent that lottery lacks.

## Recommendation
Capture the `known_since` value returned by `T::Randomness::random` in `generate_random_number`/`choose_ticket`, and only finalize payout in `on_initialize` if `known_since >= config.start.saturating_add(config.length)`; otherwise defer to a later block, mirroring `auctions::check_auction_end`'s deferral pattern.

## Proof of Concept
1. Configure a runtime with `pallet_lottery::Config::Randomness` set to a source (e.g. `RandomnessFromOneEpochAgo`) whose seed for the payout block is already fixed/knowable before `config.start + config.length`.
2. Call `start_lottery` with `length`/`delay` chosen such that the payout-block seed is determinable before the ticket window closes.
3. Read the pre-committed randomness value from public storage and compute the expected `generate_random_number(0)` output.
4. Time the final `buy_ticket` call to control `TicketsCount` so `random_number % total` maps to the attacker's ticket index.
5. At `payout_block`, `on_initialize` (`substrate/frame/lottery/src/lib.rs` lines 243-263) calls `choose_account`/`choose_ticket` and transfers `lottery_balance` to the attacker without ever validating `known_since` against the ticket-buying deadline.
