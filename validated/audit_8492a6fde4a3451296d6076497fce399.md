### Title
Deposit crediting trusts the declared `ft_on_transfer`/`mt_on_transfer` amount instead of verified balance received, allowing fee-on-transfer/deflationary tokens to mint uncollateralized internal balance - (File: `contracts/defuse/src/contract/tokens/mod.rs`)

### Summary
`Contract::deposit` in the intents contract credits a depositor's internal multi-token ledger (`token_balances` / `total_supplies`) with exactly the `amount` value it is told about by the `ft_on_transfer`/`mt_on_transfer` callback, without ever comparing that value to the actual balance the contract holds of the underlying token. Any NEP-141 (or NEP-245) token contract is accepted as a valid `TokenId::Nep141`/`TokenId::Nep245` — there is no whitelist. [1](#0-0)  A token whose implementation reports a full `amount` to `ft_on_transfer` while internally delivering less (a deflationary/fee-on-transfer style NEP-141) causes the defuse contract to mint internal balance that is not backed by an equivalent increase in the tokens it actually custodies.

### Finding Description
The deposit entrypoints (`ft_on_transfer`, `mt_on_transfer`) unconditionally forward the caller-declared `amount`/`amounts` into `Contract::deposit`: [2](#0-1) [3](#0-2) 

`deposit()` then increments both the depositor's `token_balances` and the global `total_supplies` entry for that `token_id` by exactly this declared `amount`, with no verification against the contract's actual on-chain NEP-141/NEP-245 balance for that token: [4](#0-3) 

This is the same root-cause pattern as the referenced Knox `Queue.sol` finding: the receiving contract trusts a caller-supplied `amount` parameter as proof of value received instead of measuring the actual balance delta. Because the `TokenId::Nep141`/`Nep245` type is derived purely from `env::predecessor_account_id()` with no permission or whitelist check, any account can deploy a custom NEP-141 contract whose `ft_transfer_call` internally transfers `amount - fee` to the defuse contract's real token balance while still invoking `ft_on_transfer(sender_id, amount, msg)` with the undiminished `amount`. The defuse contract has no way to detect the discrepancy and mints internal shares corresponding to the inflated `amount`.

The invariant that should hold is: `sum(token_balances[token_id])` (`total_supplies[token_id]`) must always equal the real balance of `token_id` custodied by the defuse contract. This deposit path breaks that equality by minting balance that is not backed by any real asset increase.

### Impact Explanation
Once the attacker's account is credited with unbacked internal balance for the fee-on-transfer token, this "phantom" balance is fully fungible within the intents system — it can be used in `TokenDiff` swaps or `Transfer` intents to extract real, fully-backed tokens from counterparties/solvers, or withdrawn later (subject to the withdraw resolver, which only limits refunds by the actual promise result of the outbound transfer, not by whether the deposit was ever fully collateralized). The result is a broken custody invariant (`total_supplies` no longer equal to true underlying token holdings), which can ultimately leave legitimate depositors of other tokens unable to fully withdraw once the shortfall is realized — i.e., funds effectively taken from the shared, undifferentiated custody without a matching deposit ever having occurred. This matches the Critical impact bucket: value credited without valid, backed authorisation, ultimately threatening frozen/undercollateralized withdrawals for other users.

### Likelihood Explanation
Exploitation only requires deploying an ordinary custom NEP-141 (or NEP-245) contract that skims a fee on transfer and reports the pre-fee amount to `ft_on_transfer`, then calling `ft_transfer_call` to the defuse contract with `msg` addressed to oneself. No privileged role, DAO action, relayer key, or victim key is required — it is entirely triggerable by an ordinary unprivileged user acting as their own "attacker token" deployer, matching the deposit path used by every legitimate token today.

### Recommendation
In `Contract::deposit` (or in the `ft_on_transfer`/`mt_on_transfer` handlers before calling `deposit`), measure the actual increase in the contract's on-chain balance of the token (e.g., via `ft_balance_of`/`mt_balance_of` self-query before and after, or by tracking per-token reserve accounting) and credit the depositor with the verified delta rather than the caller-declared `amount`. Alternatively, restrict deposits to a vetted allow-list of NEP-141/NEP-245 contracts known not to implement fee-on-transfer semantics.

### Proof of Concept
1. Deploy a custom NEP-141 contract `EvilToken` whose `ft_transfer_call` implementation: debits `amount` from the sender, credits only `amount - fee` to the receiver's (defuse's) balance internally, but calls `receiver_id.ft_on_transfer(sender_id, amount, msg)` with the full, undiminished `amount`.
2. Attacker calls `EvilToken.ft_transfer_call(defuse, amount, msg="")`.
3. `ft_on_transfer` in `contracts/defuse/src/contract/tokens/nep141/deposit.rs` receives `amount` (full) and calls `self.deposit(attacker, [(TokenId::Nep141(EvilToken), amount)], ...)`. [5](#0-4) 
4. `Contract::deposit` credits the attacker's `token_balances` and `total_supplies` by the full `amount`, even though defuse's real `EvilToken` balance only increased by `amount - fee`. [4](#0-3) 
5. Attacker signs a `TokenDiff` intent trading the inflated `EvilToken` balance for a solver's real, fully-backed token, realizing `fee` worth of value that was never actually deposited into defuse's custody.

    pub(crate) fn deposit(
        &mut self,
        owner_id: AccountId,
        tokens: impl IntoIterator<Item = (TokenId, u128)>,
        memo: Option<&str>,
    ) -> Result<()> {
        let owner = self
            .storage
            .accounts
            .get_or_create(owner_id.clone())
            // deposits are allowed for locked accounts
            .as_inner_unchecked_mut();

        let mut mint_event = MtMintEvent {
            owner_id: owner_id.into(),
            token_ids: Vec::new().into(),
            amounts: Vec::new().into(),
            memo: memo.map(Into::into),
        };

        for (token_id, amount) in tokens {
            if amount == 0 {
                return Err(DefuseError::InvalidIntent);
            }

            mint_event.token_ids.to_mut().push(token_id.to_string());
            mint_event.amounts.to_mut().push(amount);

            let total_supply = self
                .storage
                .state
                .total_supplies
                .add(token_id.clone(), amount)
                .ok_or(DefuseError::BalanceOverflow)?;
            match token_id {
                TokenId::Nep171(ref tid) => {
                    if total_supply > 1 {
                        return Err(DefuseError::NftAlreadyDeposited(tid.clone()));
                    }
                }
                TokenId::Nep141(_) | TokenId::Nep245(_) | TokenId::Imt(_) => {}
            }

            owner
                .token_balances
                .add(token_id, amount)
                .ok_or(DefuseError::BalanceOverflow)?;

    fn ft_on_transfer(
        &mut self,
        sender_id: AccountId,
        amount: U128,
        msg: String,
    ) -> PromiseOrValue<U128> {
        require!(amount.0 > 0, "zero amount");

        let token_id = TokenId::Nep141(Nep141TokenId::new(env::predecessor_account_id()));

        let DepositMessage {
            receiver_id,
            action,
        } = if msg.is_empty() {
            DepositMessage::new(sender_id.clone())
        } else {
            msg.parse().unwrap_or_else(|e| panic!("{e}"))
        };

        self.deposit(
            receiver_id.clone(),
            [(token_id.clone(), amount.0)],
            Some("deposit"),
        )
        .unwrap_or_else(|err| err.panic());

    fn mt_on_transfer(
        &mut self,
        sender_id: AccountId,
        previous_owner_ids: Vec<AccountId>,
        token_ids: Vec<defuse_nep245::TokenId>,
        amounts: Vec<U128>,
        msg: String,
    ) -> PromiseOrValue<Vec<U128>> {
        let token = env::predecessor_account_id();

        require!(!amounts.is_empty(), "invalid args");

        require!(
            token_ids.len() == amounts.len(),
            "NEP-245: Contract MUST panic if `token_ids` length does not equals `amounts` length"
        );

        require!(
            previous_owner_ids.len() == token_ids.len(),
            "NEP-245: Contract MUST panic if `previous_owner_ids` length does not equals `token_ids` length"
        );

        require!(
            token != env::current_account_id(),
            "self-wrapping is not allowed"
        );

        let core_token_ids = token_ids
            .iter()
            .inspect(|token_id| {
                if token_id.len() > MAX_TOKEN_ID_LEN {
                    DefuseError::TokenIdTooLarge(token_id.len()).panic();
                }
            })
            .cloned()
            .map(|token_id| Nep245TokenId::new(token.clone(), token_id))
            .map(Into::into);

        let DepositMessage {
            receiver_id,
            action,
        } = if msg.is_empty() {
            DepositMessage::new(sender_id.clone())
        } else {
            msg.parse().unwrap_or_else(|e| panic!("{e}"))
        };

        self.deposit(
            receiver_id.clone(),
            core_token_ids
                .clone()
                .zip(amounts.iter().map(|amount| amount.0)),
            Some("deposit"),
        )
        .unwrap_or_else(|err| err.panic());
