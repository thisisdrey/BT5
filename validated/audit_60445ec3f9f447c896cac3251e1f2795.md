### Title
Wallet Contract pays the relayer fee unconditionally, then also fully refunds the caller's attached deposit on failure, allowing repeated draining of the ETH-implicit account's balance - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The eth-implicit Wallet Contract's `rlp_execute` entry point can be invoked by any unprivileged NEAR account (it is a plain `#[payable]` public method reachable via a normal `FunctionCall`, exactly like Li.Fi's broadly-permissioned `SWAP_CALLER_ROLE` executor in the original report). When such a caller both (a) attaches a NEAR deposit to the call and (b) supplies a signed Ethereum transaction that is an emulated base-token/ERC-20 transfer with a non-zero relayer `fee`, the contract pays the `fee` out of its own balance immediately and unconditionally, but later refunds the caller's *entire* attached deposit if the underlying action fails - without netting the fee already paid against that refund. A caller can deliberately make the underlying action fail (e.g. target a non-existent receiver/method) to collect the fee "for free" while getting their deposit back in full, repeatedly draining the wallet's balance.

### Finding Description
`inner_rlp_execute` (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:330-410`) computes `caller_deposit` from the raw `attached_deposit` of the call [1](#0-0) , then, independently, if the parsed transaction is an `EOABaseTokenTransfer`/`ERC20Transfer` with non-zero `fee` and the predecessor differs from the current account, it immediately fires a transfer promise paying `fee` to the predecessor from the wallet's own balance, with no dependency on whether the requested action later succeeds: [2](#0-1) 

Later, in `rlp_execute_callback`, if the spawned promise for the actual action fails, the contract refunds the caller the *full* originally tracked `yocto_near` from `caller_deposit`, with no adjustment for any fee that was already disbursed to that same account earlier in the same call: [3](#0-2) 

`CallerDeposit::new` only tracks whether the caller is external (`predecessor_account_id != current_account_id`) and the raw `attached_deposit`; it has no notion of `fee` having already been paid to that very account: [4](#0-3) 

Because the `fee` payment and the deposit-refund-on-failure are two independent, unconditional code paths that both pay the same external account, an attacker acting as their own "relayer" (submitting the signed Ethereum tx to their own `rlp_execute` call and attaching a NEAR deposit) can:
1. Set a large `fee` (bounded by `VALUE_MAX`) in the signed Ethereum transaction, which is paid out of the wallet's own balance as soon as parsing succeeds.
2. Target an invalid/non-existent receiver or method so the spawned action promise fails.
3. Receive the full deposit refund in `rlp_execute_callback`'s failure branch on top of the already-collected fee.

This mirrors the original report's root cause: a value-disbursing path reachable by an unprivileged caller (`handleReallocation`/`rlp_execute`) combined with a "cancellation"/failure-refund path (`invalidateParticipations`/failed-promise refund) that does not net out funds already paid out, letting the caller repeatedly extract more value than they put in.

### Impact Explanation
This lets any account with access to the ETH-implicit wallet (which, per the model, must be reachable by ordinary relayers/callers per NEP-518's design) repeatedly extract `fee` amounts from the wallet's own NEAR balance at negligible cost (only the gas for the failing call), each time also recovering their attached deposit intact. Repeating this drains the ETH-implicit account's balance - a concrete theft of user funds from an ordinary account reachable purely through normal transaction/contract-call flow, satisfying the "concrete theft of funds" impact bar.

### Likelihood Explanation
The path requires no privileged access: any account (including the wallet owner emulating a self-relayed transaction, or a malicious relayer of the wallet owner's transactions) can attach a NEAR deposit and submit a crafted Ethereum transaction with an attacker-chosen `fee` and a target guaranteed to fail. All of the necessary primitives (fee computation, immediate fee payment, and unconditional deposit refund-on-failure) are present in the shipped Wallet Contract logic, so the only requirement is crafting one transaction with both a non-zero attached NEAR deposit and a nonzero-fee, failure-guaranteed emulated transfer, then repeating it.

### Recommendation
Net the already-disbursed relayer `fee` against the caller's tracked deposit before issuing the failure-path refund in `rlp_execute_callback`, e.g. by reducing `CallerDeposit.yocto_near` by any `fee` amount already paid to the same `account_id` in `inner_rlp_execute`, or by deferring the fee payment until after the action's success/failure is known and only paying it net of any refund obligation to that same account.

### Proof of Concept
1. Attacker deploys/owns an ETH-implicit account with the Wallet Contract and funds it with NEAR.
2. Attacker (as their own relayer) calls `rlp_execute` on their own eth-implicit account, attaching a NEAR deposit `D > 0`, with a signed Ethereum transaction that:
   - Encodes an `EOABaseTokenTransfer`/`ERC20Transfer` with `max_fee_per_gas * gas_limit` set to yield a large `fee`.
   - Targets a non-existent receiver/method to guarantee the spawned promise fails.
3. `inner_rlp_execute` immediately sends `fee` from the wallet's balance to the attacker (predecessor) via `env::promise_batch_action_transfer` [5](#0-4) .
4. The target action promise fails; `rlp_execute_callback`'s `PromiseResult::Failed` branch refunds the attacker's full deposit `D` [6](#0-5) .
5. Net result: attacker keeps `D` (refunded) plus gains `fee` extracted from the wallet's balance. Repeating steps 2-4 drains the wallet.

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),

        })
