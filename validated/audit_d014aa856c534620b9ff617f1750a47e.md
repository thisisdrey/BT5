### Title
Stale cache resurrects deleted contract/account/code data after `RepositoryImpl.deleteContract` (cache-store desync causing use-after-free-like state corruption) - (File: actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java)

### Summary
`RepositoryImpl.deleteContract` writes deletions straight to the persistent stores while leaving the in-memory per-transaction caches (`accountCache`, `codeCache`, `contractCache`) untouched. Any subsequent `getAccount`/`getContract`/`getCode` call in the same execution context checks the cache first, so a "deleted" contract's account/code/state can be resurrected from the stale cache — the same underlying bug class as the ImageMagick CVE (freed/invalidated object state read back and reused, causing corrupted/incorrect behavior instead of a normal null/missing result).

### Finding Description
`RepositoryImpl` maintains layered, per-repository HashMaps that shadow the underlying stores: `accountCache`, `codeCache`, `contractCache`, `contractStateCache`, etc. [1](#0-0) . Reads such as `getContract` and `getCode` consult these caches before falling back to the persistent stores, and populate the cache on first read [2](#0-1) [3](#0-2) .

However, `deleteContract` bypasses all of these caches and deletes directly from `codeStore`, `accountStore`, and `contractStore`: [4](#0-3) 

It never calls `accountCache.remove(...)`, `codeCache.remove(...)`, or `contractCache.remove(...)` (confirmed no such calls exist anywhere in the codebase). `Repository.deleteContract` is exposed through `ContractState.deleteContract` [5](#0-4) , reachable from TVM execution paths (e.g., `TransactionTrace.deleteContract` performs the equivalent multi-store delete pattern independently) [6](#0-5) .

Because `RepositoryImpl` is instantiated per-transaction/per-call-frame (root and nested children via `newRepositoryChild`), if any code path in a single execution first reads a contract's account/code/contract entry (populating the cache), then deletes it via `deleteContract`, and then reads it again (e.g., a nested internal call, retry logic, or a subsequent opcode in the same call frame), the second read will return the pre-deletion cached object instead of `null`/absent, since the cache lookup at the top of `getAccount`/`getContract`/`getCode` short-circuits before checking `accountStore.get/contractStore.get` again. This is a direct analog of the CVE's core defect: state that has been logically freed/invalidated is not properly invalidated in the object graph, and a later access reuses/re-serves the stale object, producing incorrect state (resurrected balance, code, and contract metadata) rather than the "does not exist" contract that has actually been deleted from the backing store.

### Impact Explanation
If an attacker can arrange, within one transaction/call context, to have a contract's account/code/contract entry cached, then deleted, then re-read (via nested CALL/CREATE opcodes, revert-and-retry ordering, or subsequent read within the same repository instance before `commit()`), the TVM would operate on inconsistent/resurrected state: energy/balance/code that should be gone continues to be visible and usable in-memory for the remainder of the transaction. Depending on how these stale reads are used downstream (balance transfers, contract call dispatch, `getCode`/`isContractExist` checks used for CREATE2 collision guards, etc.), this can lead to unauthorized/incorrect account operations, resurrection of a "destroyed" contract's balance/state within the same execution, or bypass of `contractAlreadyExists` checks used during CREATE2 redeployment (`Program.createContractImpl` relies on `getAccount`/contract existence checks that traverse the same caches) [7](#0-6) . This has the potential to result in unbacked balances or incorrect contract-existence decisions — a High-severity impact class matching the funds-safety/state-corruption criteria.

### Likelihood Explanation
Reaching this requires a specific sequence (cache-populating read → delete → re-read) inside a single transaction/call context, which is plausible via nested internal calls, revert-and-retry logic within `Program`/`VMActuator`, or a contract calling patterns that force a read-then-suicide-then-read of the same address in one root transaction. This is reachable by any unprivileged party who can submit a `TriggerSmartContract`/`CreateSmartContract` transaction executing crafted bytecode, i.e., an anonymous contract deployer/caller — no special privilege is required. However, I could not fully trace every internal call path that would definitively trigger the cache-populate-then-delete-then-reread sequence within the available search scope; the specific victim opcode/method sequence that exploits this window needs deeper code tracing (e.g., stepping through `suicide`/`suicide2` in `Program.java` combined with `createContractImpl`'s CREATE2 collision checks) than I was able to confirm here.

### Recommendation
In `RepositoryImpl.deleteContract`, explicitly evict the corresponding entries from `accountCache`, `codeCache`, and `contractCache` (and `contractStateCache` if applicable) in addition to deleting from the backing stores, or mark them with a `Type.DELETE` sentinel that all `get*` methods honor (returning `null` for cache entries marked deleted rather than skipping the cache lookup). Add tests that read-then-delete-then-read a contract's account/code/state within a single `RepositoryImpl` instance (and within nested `newRepositoryChild()` contexts) to verify the second read consistently reflects deletion.

### Proof of Concept
Conceptual reproduction (not fully executed due to tool constraints):
1. Within one `RepositoryImpl` root instance (single transaction execution), call `getAccount(addr)` / `getContract(addr)` / `getCode(addr)` to populate `accountCache`/`contractCache`/`codeCache` for a contract address.
2. Call `deleteContract(addr)` on the same repository instance (or root, if commit propagates to root while caches remain populated from step 1 prior to commit).
3. Call `getAccount(addr)` / `getContract(addr)` / `getCode(addr)` again in the same instance before any new repository is constructed.
4. Observe that the pre-deletion cached `AccountCapsule`/`ContractCapsule`/code bytes are returned instead of `null`, even though `accountStore`/`contractStore`/`codeStore` no longer contain the entry — demonstrating stale/"freed" object reuse.
