### Title
Duplicate `input_data_ids` in an `ActionReceipt` permanently stalls the receipt and freezes its attached deposit - (File: `runtime/runtime/src/lib.rs`)

### Summary
`process_action_receipt` computes `pending_data_count` by counting every entry of `action_receipt.input_data_ids()`, without checking that the ids are distinct. Since the "arrival" bookkeeping (`TrieKey::PostponedReceiptId`) is keyed only by `(receiver_id, data_id)`, a receipt whose `input_data_ids` contains the same `data_id` more than once will register only one wait slot but count more than one pending dependency. When the single corresponding `DataReceipt` finally arrives, the counter can only ever be decremented once, so the receipt can be left permanently "postponed" in state and never executes — silently freezing any value carried by it (e.g. an attached deposit that would otherwise be refunded on execution failure/success).

### Finding Description
In `process_action_receipt` (`runtime/runtime/src/lib.rs`), the pending-dependency counter is derived purely from the length of `input_data_ids`, with a per-id increment loop: [1](#0-0) 

Each iteration writes a `TrieKey::PostponedReceiptId { receiver_id, data_id }` entry keyed by `data_id` alone — so if the same `data_id` appears twice in `input_data_ids`, the second write is just an overwrite of the same key, not a second wait slot: [2](#0-1) 

The counter is persisted as `TrieKey::PendingDataCount` and the receipt is stored as postponed: [3](#0-2) 

On the consumer side, when a `DataReceipt` for that `data_id` arrives, the runtime looks up the single `PostponedReceiptId` entry, removes it, and decrements `pending_data_count` by exactly one before deciding whether the receipt is ready to run: [4](#0-3) 

Because a given `data_id` is produced by exactly one upstream promise/callback and delivered as exactly one `DataReceipt`, only a single "arrival" event exists per distinct `data_id`, regardless of how many times that `data_id` was listed in `input_data_ids`. If the id is listed N>1 times, `pending_data_count` is initialized to (distinct_ids + (N-1)) but can only be decremented (distinct_ids) times total, leaving a residual positive count forever, so the branch that finalizes and executes the receipt (`pending_data_count == 1`) is never reached: [5](#0-4) 

`validate_action_receipt`, which is the gate applied to newly generated receipts, only checks the *count* of `input_data_ids` against a limit — it performs no uniqueness/deduplication check on the ids themselves: [6](#0-5) 

This mirrors the structure of the reported `EscrowManager.createLock()` bug: an attacker-controlled input array (`vestingWallets_` / here `input_data_ids`) is trusted to represent N independent entities and is used to accumulate/track a quantity (locked NEAR balance / pending dependency count) without validating that the array elements are distinct, letting the same entry be "double counted" and desynchronizing the accounting from the real, singular resource it references.

### Impact Explanation
A postponed `ActionReceipt` that never becomes eligible for execution is never rolled back, never refunded, and never retried by protocol logic — the `apply_action_receipt` refund path (`refund_unspent_gas_and_deposits`, `Receipt::new_balance_refund`/`new_gas_refund`) only runs once a receipt is actually executed. A receipt stuck in `PostponedReceipt`/`PendingDataCount` state permanently holds:
- any attached deposit inside its actions (the deposit is neither delivered to the receiver nor refunded to the sender),
- the storage cost of the postponed receipt itself,

and never emits an execution outcome, effectively making these funds permanently unspendable/frozen. This matches the "permanent freezing of funds" impact category. It also represents a self-inflicted but permanent state-liveness bug for the affected receiver account and receipt.

### Likelihood Explanation
The construction is reachable from an ordinary account/contract without any special privilege: a contract can create a receipt whose `input_data_ids` deliberately lists a promise/callback dependency more than once (e.g., by depending on the same async-call result twice via a crafted low-level receipt/host-function usage), or by depending on the same `data_id` through two different promise combinators that resolve to the same result. Since `validate_action_receipt`/`validate_receipt` never rejects duplicate `input_data_ids`, and no other layer performs deduplication, an attacker fully controls this outcome from the transaction/contract layer. I was not able to fully verify, within tool-call limits, that the higher-level VM host functions (`promise_and`/`receipt_manager.rs`) forward promise indices/data ids to `input_data_ids` completely unfiltered/without automatic dedup — this should be independently confirmed by exercising `promise_and` with a repeated promise index (or constructing a receipt with a duplicate `data_id` directly) to demonstrate the runtime-level stall end-to-end.

### Recommendation
- Deduplicate `input_data_ids` before computing `pending_data_count` in `process_action_receipt`, or reject receipts whose `input_data_ids` contain duplicates in `validate_action_receipt`.
- Alternatively, make `PendingDataCount` track the number of *distinct* pending ids rather than the raw vector length, and make the arrival path decrement per distinct id consumed rather than assume a 1:1 mapping between vector length and arrival events.
- Add a regression test that submits/creates a receipt with a duplicated `data_id` in `input_data_ids` and asserts the receipt eventually executes/finalizes after the single corresponding `DataReceipt` arrives, and that no balance/gas is permanently stranded.

### Proof of Concept
Conceptual reproduction (needs to be validated in a running node/test-loop environment):
1. Craft (or have a contract emit) an `ActionReceipt` whose `input_data_ids` is `[data_id_X, data_id_X]` (same hash twice) and which carries a non-zero deposit in its `actions`.
2. Submit the receipt so it goes through `process_action_receipt`; observe `pending_data_count` is set to `2` while only one `PostponedReceiptId{receiver_id, data_id_X}` entry exists (see `runtime/runtime/src/lib.rs:1608-1655`).
3. Deliver the single `DataReceipt` for `data_id_X`. Observe in `process_receipt` (`runtime/runtime/src/lib.rs:1396-1465`) that `pending_data_count` decrements from `2` to `1` and is persisted again instead of triggering execution (the `== 1` finalize branch is never reached because it started at `2` from the duplicate).
4. Confirm no further `DataReceipt` for `data_id_X` will ever be produced (it was already consumed/removed), so the postponed receipt — and any deposit inside it — remains in state indefinitely, unreachable and unrefunded.

fn validate_action_receipt(
    limit_config: &LimitConfig,
    receipt: VersionedActionReceipt,
    receiver: &AccountId,
    current_protocol_version: ProtocolVersion,
    mode: ValidateReceiptMode,
) -> Result<(), ReceiptValidationError> {
    if receipt.input_data_ids().len() as u64 > limit_config.max_number_input_data_dependencies {
        return Err(ReceiptValidationError::NumberInputDataDependenciesExceeded {
            number_of_input_data_dependencies: receipt.input_data_ids().len() as u64,
            limit: limit_config.max_number_input_data_dependencies,
        });
    }

    if let Some(account_id) = receipt.refund_to() {
        AccountId::validate(account_id.as_ref()).map_err(|_| {
            ReceiptValidationError::InvalidRefundTo { account_id: account_id.to_string() }
        })?;
    }

    validate_actions_with_mode(
        limit_config,
        receipt.actions(),
        receiver,
        current_protocol_version,
        mode,
    )
    .map_err(ReceiptValidationError::ActionsValidation)
}
