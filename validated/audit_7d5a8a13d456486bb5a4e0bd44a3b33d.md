### Title
Per-file `remote_file_integrity` map silently downgrades to unpinned download when an entry is empty or missing - (File: tools/build_defs/repo/utils.bzl)

### Summary
`http_archive`'s `remote_file_urls`/`remote_file_integrity` feature lets a rule author overlay extra files (e.g. `BUILD.bazel`, `REPO.bazel`) fetched over HTTP(S) on top of an archive, with an integrity value pinned per path. The helper that performs these downloads reads the pinned value with a dict `.get(path, "")` fallback, so a missing key or an explicitly empty string silently becomes "no integrity constraint" rather than a hard error, exactly mirroring the reported bug class: a security-relevant per-item parameter that defaults/degrades to zero/empty is treated as "verification disabled" instead of "verification required," and the surrounding machinery keeps functioning normally instead of failing loudly.

### Finding Description
`download_remote_files` builds the `integrity` argument for each overlay file like this: [1](#0-0) 

Note `integrity = ctx.attr.remote_file_integrity.get(path, "")`. If the rule author's `remote_file_integrity` dict simply omits a path that is present in `remote_file_urls` (a very easy authoring mistake, since these are two independently maintained dicts), or if the value recorded for that path is `""`, the resulting `ctx.download()` call for that specific file receives `integrity=""`, which Bazel treats identically to "no integrity requested" — i.e., an unpinned download.

The test suite documents this exact behavior for the `""` case: `test_overlay_remote_file_with_empty_integrity` sets `"BUILD.bazel": ""` in `remote_file_integrity` and the build still succeeds, only printing a "canonical reproducible form" suggestion, not failing: [2](#0-1) 

Compare this with `test_overlay_remote_file_without_integrity`, which shows the same no-op-warning-only behavior when the key is entirely absent: [3](#0-2) 

This is the same failure pattern as the Teller report: a market/config parameter (`paymentDefaultDuration = 0`) that is supposed to gate a safety-critical check instead silently disables it, and the rest of the pipeline (bid creation, fee collection / here: archive fetch, extraction, BUILD file generation) proceeds as if everything were fine. Here, `remote_file_integrity` is meant to pin every overlay file's content, but an incomplete/empty entry for one path degrades only that path to unpinned HTTP fetch while the rest of the `http_archive` (main archive `integrity`/`sha256`) may still be correctly pinned, giving a false sense that "the repo declares checksums" when one specific overlaid file (frequently `BUILD.bazel` or `REPO.bazel`, i.e. build-relevant files) is not actually integrity-checked.

### Impact Explanation
An attacker who controls the HTTP(S) origin/mirror serving an overlay file referenced via `remote_file_urls` (a realistic "hostile origin server" scenario per the rules of engagement) can serve arbitrary content for that path whenever its corresponding `remote_file_integrity` entry is missing or empty, without triggering a checksum mismatch error. Since these overlay files are commonly `BUILD.bazel`/`REPO.bazel` — files that directly define build targets, `load()` statements, and even repository-wide `.bzl` loads — a mismatch here can lead to attacker-controlled build definitions being materialized into the repository, undermining the very reproducibility/integrity guarantee that `remote_file_integrity` exists to provide. It also silently breaks the "declared digest should stop it" invariant that governs `.get(path, "")` at line 108 versus a design that should `fail()` when a path present in `remote_file_urls` has no (or an empty) integrity entry.

### Likelihood Explanation
Likely to occur by ordinary authoring mistakes (two independently-maintained dicts, `remote_file_urls` and `remote_file_integrity`, must stay in sync) or by a rule/macro generator that populates `remote_file_integrity` incompletely. It requires no special build flags — it happens with default `http_archive` usage of `remote_file_urls`. The bar for silent exploitation is a hostile/compromised origin controlling the overlay URL(s) and a repo definition lacking (or zeroing out) the corresponding integrity entry.

### Recommendation
In `download_remote_files` (tools/build_defs/repo/utils.bzl), fail fast instead of defaulting to `""` when a path in `remote_file_urls` has no corresponding non-empty entry in `remote_file_integrity` (mirroring the existing check already present for `remote_module_file_urls`/`remote_module_file_integrity` at lines 240-241 of the same file). At minimum, require callers to explicitly pass an unpinned override sentinel rather than allowing an implicit dict `.get(..., "")` fallback to silently disable verification per-file.

### Proof of Concept
The existing shell test already demonstrates the unpinned/no-op behavior for both the missing-key and empty-string cases without any build failure: [2](#0-1) 
A reproducible PoC: stand up an `http_archive` with `remote_file_urls={"BUILD.bazel": [attacker_url]}` and `remote_file_integrity={}` (or `{"BUILD.bazel": ""}`); serve a malicious `BUILD.bazel` from `attacker_url`; observe `bazel build` succeeds and materializes the attacker-provided `BUILD.bazel` with no integrity error, in contrast to the main archive `sha256`/`integrity` mismatch case which does hard-fail (as shown by `test_integrity_incorrect`): [4](#0-3)

test_overlay_remote_file_without_integrity() {
  EXTREPODIR=`pwd`
  EXTREPOURL="$(get_extrepourl ${EXTREPODIR})"

  archive_integrity="sha256-$(cat hello_world.zip | openssl dgst -sha256 -binary | openssl base64 -A)"

  # Generate the remote files to overlay
  cat > BUILD.bazel <<'EOF'
load("@rules_cc//cc:defs.bzl", "cc_binary")

cc_binary(
    name = "hello_world",
    srcs = ["hello_world.c"],
)
EOF
  touch REPO.bazel

  mkdir main
  cd main
  cat >> $(setup_module_dot_bazel) <<EOF
http_archive = use_repo_rule("@bazel_tools//tools/build_defs/repo:http.bzl", "http_archive")
http_archive(
  name="hello_world",
  strip_prefix="hello_world-0.1.2",
  urls=["${EXTREPOURL}/hello_world.zip"],
  integrity="${archive_integrity}",
  remote_file_urls={
    "REPO.bazel": ["${EXTREPOURL}/REPO.bazel"],
    "BUILD.bazel": ["${EXTREPOURL}/BUILD.bazel"],
  },
)
EOF
  add_rules_cc "MODULE.bazel"

  bazel build @hello_world//:hello_world > "${TEST_log}" 2>&1
  expect_log "canonical reproducible form can be obtained by modifying arguments \
remote_file_integrity = {\"REPO\.bazel\": \"[^\"]*\", \"BUILD\.bazel\": \"[^\"]*\"}\$"
