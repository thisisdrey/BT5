### Title
Divide-by-zero DoS in `EnergyProcessor.calculateGlobalEnergyLimit()` when `totalEnergyWeight` is zero and `allowNewReward` is disabled - (File: `chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java`)

### Summary
This is the same root-cause pattern as the Curves `FeeSplitter.addFees()` bug: a legitimate, unprivileged operation reverts because a divisor derived from aggregated network state (`totalSupply` in Curves, `totalEnergyWeight` in java-tron) can become `0` on a valid, reachable path, and the zero-guard that exists is incomplete — it only covers one code branch.

### Finding Description
`EnergyProcessor.calculateGlobalEnergyLimit()` computes an account's energy limit by dividing by `totalEnergyWeight`, the sum of all frozen-for-energy balances network-wide: [1](#0-0) 

The zero-guard is conditioned on `dynamicPropertiesStore.allowNewReward()`:
```java
if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
  return 0;
} else {
  assert totalEnergyWeight > 0;
}
if (hardenCalculation()) {
  return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
}
```
If `allowNewReward()` is `false` (this flag is a maintenance-cycle-gated feature switch, not guaranteed to be enabled on all networks/heights) and `totalEnergyWeight` is `0`, the `assert` statement is a no-op in production (Java assertions are disabled by default at runtime — there is no `-ea` flag set for the node process), so execution falls straight through to the division: [2](#0-1) 
```java
protected long calculateGlobalLimitV1(long frozeBalance, long totalLimit, long totalWeight) {
  long weight = frozeBalance / TRX_PRECISION;
  return BigInteger.valueOf(weight)
      .multiply(BigInteger.valueOf(totalLimit))
      .divide(BigInteger.valueOf(totalWeight))   // ArithmeticException: / by zero
      .longValueExact();
}
```
`BigInteger.divide(BigInteger.ZERO)` throws `ArithmeticException`. The non-hardened path (`hardenCalculation() == false`) performs `(double) totalEnergyLimit / totalEnergyWeight`, which for a `double` produces `Infinity`/`NaN` rather than throwing — but the hardened path (`allowHardenResourceCalculation()` on, which is the newer, "safer" code path meant to eliminate silent overflow/precision bugs) throws an uncaught `ArithmeticException`.

`calculateGlobalEnergyLimit()` is invoked from `useEnergy()`, which is called on essentially every TVM contract-triggering transaction (`TriggerSmartContract`) to determine the caller's free energy limit: [3](#0-2) 

`totalEnergyWeight` is maintained in `DynamicPropertiesStore` and is decremented whenever accounts unfreeze frozen-for-energy balance (`UnfreezeBalanceActuator`/`UnfreezeBalanceV2Actuator`). On a network/testnet with low participation, or one where the new reward algorithm has not yet been activated (`allowNewReward() == false`), it is possible for all frozen-for-energy stake to be unfrozen, driving `totalEnergyWeight` to `0`.

### Impact Explanation
Once `totalEnergyWeight` reaches `0` while `allowNewReward()` is disabled and `allowHardenResourceCalculation()` is enabled, every subsequent smart-contract-triggering transaction that reaches `useEnergy()`/`calculateGlobalEnergyLimit()` throws an unhandled `ArithmeticException`. This is a broad denial-of-service: any unprivileged user submitting a `TriggerSmartContractContract` transaction can no longer have their energy limit computed, bricking smart contract execution on the affected chain until an operator manually restores non-zero `totalEnergyWeight` (e.g., via a hard fork/emergency freeze) — directly analogous to how Bob's legitimate sell in the Curves report is permanently blocked once the divisor collapses to zero.

### Likelihood Explanation
This requires `totalEnergyWeight` to hit exactly `0` while the two feature flags are in the specific combination (`allowNewReward` off, hardened calculation on). Both flags are controlled by committee proposals / maintenance-cycle activation, and mainnet has had `allowNewReward` active for a long time, which somewhat limits practical likelihood on TRON mainnet today. However, for any chain deployment (private/enterprise chains, testnets, or forks) where these flags are toggled independently — which java-tron explicitly supports via `ProposalUtil`/committee parameters — the zero-weight state is a normal, reachable configuration, and no signed transaction or privileged action is needed to trigger the resulting crash; a plain `TriggerSmartContract` call suffices.

### Recommendation
Make the zero-weight guard unconditional, independent of `allowNewReward()`:
```java
if (totalEnergyWeight <= 0) {
  return 0;
}
```
Remove the `assert` (which offers no protection in production) and apply the same unconditional check in `calculateGlobalEnergyLimitV2` as already exists there, ensuring `calculateGlobalLimitV1`/`calculateGlobalLimitV2` are never invoked with a zero divisor regardless of feature-flag state.

### Proof of Concept
1. Deploy/operate a java-tron network where `allowNewReward()` is `0` (not yet enabled via committee proposal) and `allowHardenResourceCalculation()` (`hardenCalculation()`) is `1`.
2. Drive `totalEnergyWeight` to `0` by having all accounts fully unfreeze their energy-frozen balance via `UnfreezeBalanceActuator`/`UnfreezeBalanceV2Actuator` (`chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java` lines 154-165 read this value from `DynamicPropertiesStore`).
3. Any account submits a normal `TriggerSmartContractContract` transaction; `EnergyProcessor.useEnergy()` calls `calculateGlobalEnergyLimit()`, which falls through the disabled `assert` and calls `calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, 0)` in `ResourceProcessor.java` line 355, throwing `ArithmeticException: / by zero` and failing the transaction/contract-execution path for all callers until `totalEnergyWeight` is restored above zero.

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalEnergyLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }

    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
    long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
      return 0;
    } else {
      assert totalEnergyWeight > 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
