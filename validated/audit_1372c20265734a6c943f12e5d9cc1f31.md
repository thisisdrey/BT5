### Title
Wallet Contract's ERC-20 `transfer` emulation forwards to the zero address without validation, permanently freezing NEP-141 tokens - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/eth_emulation.rs)

### Summary
The ETH-implicit Wallet Contract's ERC-20 emulation layer maps an Ethereum-encoded `transfer(address to, uint256 value)` call directly onto a NEP-141 `ft_transfer` call, deriving the NEAR `receiver_id` from the raw 20-byte `to` address without ever checking that `to` is non-zero. This mirrors the reported ERC-20 `mint`-to-zero-address bug class: the contract performs an unchecked balance-moving operation to an address that (practically) nobody controls, resulting in permanent, irrecoverable loss of the transferred tokens.

### Finding Description
`try_emulation` in [1](#0-0)  handles the `ERC20_TRANSFER_SELECTOR` case: it ABI-decodes `(to, value)` and builds `receiver_id` as `format!("0x{}{}", hex::encode(to), suffix)` with no check that `to` is the zero address (`0x0000000000000000000000000000000000000000`). This receiver id is then wired into a NEP-141 `ft_transfer` `FunctionCall` action (`Action::FunctionCall { receiver_id, method_name: "ft_transfer", ... }`).

Downstream, `rlp_execute` in [2](#0-1)  automatically handles the case where the receiver is not yet registered for storage (per NEP-145): it calls `storage_balance_of` and, if absent, performs `storage_deposit` before `ft_transfer`. This means the wallet contract will transparently create storage for, and then transfer NEP-141 tokens to, the account `0x000...0000<suffix>` even though no real Secp256k1 key can ever hash to the all-zero address (the ETH zero address is a conventional "no owner" sentinel, not a spendable key). Once tokens land there, they are permanently unreachable — nobody holds a private key that authorizes `rlp_execute` calls against that ETH-implicit account (compare the address-derivation logic in [3](#0-2)  and the target-address check in [4](#0-3) , none of which reject a zero `to` in the transfer path).

This is directly analogous to the reported `LibERC20.mint` bug: an unchecked "recipient == zero address" condition allows value to be moved to an address that cannot practically be controlled, causing token loss while the sender's balance is correctly debited (i.e., accounting proceeds as if the transfer succeeded, but the funds are unrecoverable).

### Impact Explanation
Any ordinary user (or a buggy/malicious dApp interacting with the Wallet Contract via an Ethereum-style `transfer(0x0, amount)` call — a call pattern that is normally rejected by compliant ERC-20 implementations such as OpenZeppelin's, which is exactly why the external report flags the missing check) can cause an eth-implicit account's NEP-141 balance to be permanently and irrecoverably locked. This is a "permanent freezing of funds" impact: the tokens still exist in the FT contract's ledger under an account no key controls, so they are removed from usable circulation without being burned through any accounted mechanism.

### Likelihood Explanation
Likelihood is driven by user/tooling error rather than attacker intent: many Ethereum wallets/dApps assume ERC-20 contracts reject `transfer(address(0), ...)`, so a relayed transaction encoding `to = 0x000...0` (e.g., from a misconfigured integration, or a user attempting what they believe is a "burn") would silently succeed here instead of reverting, unlike a spec-compliant ERC-20. Because the flow requires only a normal signed Ethereum transaction executed through `rlp_execute`, no privileged access is needed — this is a fully unprivileged-signer path.

### Recommendation
In `try_emulation`'s `ERC20_TRANSFER_SELECTOR` branch ( [1](#0-0) ), reject `to == Address::zero()` (return `Err(Error::User(UserError::...))`, mirroring the OpenZeppelin `require(_to != address(0))` pattern) before constructing the `ft_transfer` action, so the emulation layer matches standard ERC-20 semantics and prevents accidental token loss.

### Proof of Concept
1. Deploy the Wallet Contract as a global contract and create an ETH-implicit account (as in `test_erc20_emulation`, [5](#0-4) ).
2. Mint NEP-141 tokens to the wallet contract's account via `Nep141::mint` ( [6](#0-5) ).
3. Construct an EIP-2930 transaction with `data = ERC20_TRANSFER_SELECTOR || abi_encode(Address::zero(), amount)` targeting the token contract, sign it with the wallet's key, and submit via `rlp_execute_with_receipts` (analogous to the existing test at [7](#0-6)  but with `other_address` replaced by the zero address).
4. Observe that the call succeeds: `storage_deposit` + `ft_transfer` execute against receiver `0x0000000000000000000000000000000000000000<suffix>`, debiting the sender's balance with no way to ever recover the funds, since no valid Secp256k1 key maps to the zero address.

/// Coverts any Near account ID into a 20-byte address by taking the last 20 bytes
/// of the keccak256 hash.
pub fn account_id_to_address(account_id: &AccountId) -> Address {
    let hash = keccak256(account_id.as_bytes());
    let mut result = [0u8; 20];
    result.copy_from_slice(&hash[12..32]);
    result.into()
}

/// Validates the transaction is following the Wallet Contract protocol.
/// This includes checks for:
/// - from address matches current account address
/// - to address is present and matches the target address (or hash of target account ID)
/// - nonce matches expected nonce
/// If this validation fails then the relayer that sent it is faulty and should be banned.
fn validate_tx_relayer_data<'a>(
    tx: &NormalizedEthTransaction,
    target: &'a AccountId,
    context: &ExecutionContext,
    expected_nonce: u64,
) -> Result<TargetKind<'a>, Error> {
    if tx.address.raw() != context.current_address {
        return Err(Error::Relayer(RelayerError::InvalidSender));
    }

    if tx.chain_id != Some(CHAIN_ID) {
        return Err(Error::Relayer(RelayerError::InvalidChainId));
    }

    let to = tx.to.ok_or(Error::User(UserError::EvmDeployDisallowed))?.raw();

    let target_kind = parse_target(target, context.current_address);

    // valid targets satisfy `to == target` or `to == hash(target)`
    let is_valid_target = match target_kind {
        TargetKind::CurrentAccount if to == context.current_address => {
            target == &context.current_account_id
        }
        TargetKind::EthImplicit(address) if to == address => {
            target.as_str()
                == format!("0x{}{}", hex::encode(address), context.current_account_suffix())
        }
        _ => to == account_id_to_address(target),
    };

    if !is_valid_target {
        return Err(Error::Relayer(RelayerError::InvalidTarget));
    }
