### Title
Unvalidated attachment content accepted from peer responses permanently pollutes `attachments` table - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` accepts and stores whatever `Attachment` content a peer returns for a `GET /v2/attachments/<hash>` request without ever checking that the returned content's `Hash160` matches the `content_hash` that was actually requested. Any outbound peer serving attachment responses can therefore return arbitrary garbage bytes, which get permanently written to `attachments` with `was_instantiated=1`, a state that `evict_expired_uninstantiated_attachments` never touches.

### Finding Description
The equality that should hold is: every row in `attachments` with `was_instantiated=1` corresponds to some `AttachmentInstance.content_hash` that was queued from an on-chain Atlas event. This equality is broken because the download response is never checked against the request:

- `AttachmentRequest::make_request_type` builds a `GET /v2/attachments/{content_hash}` request [1](#0-0) .
- When the response comes back, `extend_with_attachments` decodes it and inserts `response.attachment` into `self.attachments` with **no comparison** between `response.attachment.hash()` and `request.content_hash` [2](#0-1) .
- In `AttachmentsDownloader::run`'s `Done` branch, every attachment drained from that set is unconditionally passed to `insert_instantiated_attachment`, keyed by `attachment.hash()` (the hash of whatever bytes the peer sent), regardless of whether any `AttachmentInstance` ever referenced that hash [3](#0-2) .
- `insert_instantiated_attachment` does `INSERT OR REPLACE INTO attachments (... was_instantiated ...) VALUES (?, ?, 1, ?)` [4](#0-3) .
- `evict_expired_uninstantiated_attachments` only deletes `WHERE was_instantiated = 0`, so rows inserted this way are never cleaned up [5](#0-4) .
- Unlike the atlas-event ingestion path, which enforces a size cap via `should_keep_attachment` (checks `attachments_max_size`) [6](#0-5) , the downloader's `extend_with_attachments` performs no size or hash validation at all.

Exploit flow: a remote peer that is one of the victim's outbound sync peers (or is selected as a data source because it claims, via inventory response, to have an attachment) responds to `GET /v2/attachments/<hash>` with a 200 JSON body containing arbitrary hex content unrelated to `<hash>`. Since the attacker controls their own peer's HTTP server implementation, they are not bound by the honest handler logic in `getattachment.rs` (which normally enforces hash-to-content correctness only for a compliant server) and can freely return distinct garbage payloads. Each distinct payload yields a new `Hash160` key, so repeated responses produce unbounded distinct rows.

### Impact Explanation
A malicious peer can permanently fill the victim's `attachments` SQLite table with garbage rows tagged `was_instantiated=1`, which are excluded from any existing eviction routine. This is unbounded disk growth tied to zero consensus commitment, matching the "High" impact category (state stored/served that no canonical block ever committed to). It does not corrupt consensus-critical state but does degrade a full node's storage over time and pollutes data that `find_attachment`/`/v2/attachments/<hash>` RPC could later serve for coincidentally matching hashes.

### Likelihood Explanation
Preconditions: the victim node must have Atlas enabled with an active `AttachmentsDownloader` and at least one outbound sync peer (default configuration for any node running Atlas/BNS sync) [7](#0-6) . The attacker only needs to be a normal, unprivileged P2P peer capable of responding to attachment inventory/content requests — no secret, signature, or admin role is required. The attack is trivially repeatable: each processed batch (`run()` cycle) that resolves against the malicious peer yields more garbage rows, and the attacker fully controls the response content and thus the resulting hash, guaranteeing new distinct keys per message.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments`, verify `response.attachment.hash() == request.content_hash` before inserting into `self.attachments`; drop/penalize (`report.bump_failed_requests()`) any response that fails this check. Additionally, enforce `attachments_max_size` (via `should_keep_attachment` or equivalent) on downloaded attachments before calling `insert_instantiated_attachment`, mirroring the validation already done for posted attachments.

### Proof of Concept
Rust net test plan (in `stackslib/src/net/atlas/download.rs` or `tests.rs`):
1. Build an `AttachmentsBatchStateContext` with one `AttachmentRequest` for a legitimate `content_hash` `H` (as in `test_downloader_context_attachment_requests`).
2. Construct a `BatchedRequestsResult` where `succeeded` maps that request to a `StacksHttpResponse` whose JSON body encodes an unrelated `Attachment` (garbage bytes whose hash `G != H`).
3. Call `context.extend_with_attachments(&mut results)` and assert `context.attachments` contains the garbage attachment (hash `G`), not `H`.
4. Feed this context through the `Done` branch logic (or call `atlasdb.insert_instantiated_attachment(&garbage)` directly, then `atlasdb.evict_expired_uninstantiated_attachments()`), and assert that `atlasdb.find_attachment(&G)` still returns `Some(garbage)` afterward — proving the garbage row is never evicted despite corresponding to no `AttachmentInstance.content_hash`.

    pub fn evict_expired_uninstantiated_attachments(&mut self) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let cut_off = now - self.atlas_config.uninstantiated_attachments_expire_after as i64;
        let tx = self.tx_begin()?;
        let res = tx.execute(
            "DELETE FROM attachments WHERE was_instantiated = 0 AND created_at < ?",
            params![cut_off],
        );
        res.map_err(db_error::SqliteError)?;
        tx.commit().map_err(db_error::SqliteError)?;
        Ok(())
    }

    pub fn insert_instantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let tx = self.tx_begin()?;
        tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)",
            params![attachment.hash(), attachment.content, now],
        )?;
        tx.execute(
            "UPDATE attachment_instances SET is_available = 1 WHERE content_hash = ?1 AND status = ?2",
            params![attachment.hash(), AttachmentInstanceStatus::Checked],
        )?;
        tx.commit()?;
        Ok(())
    }
