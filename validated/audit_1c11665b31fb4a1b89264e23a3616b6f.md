### Title
Nil pointer dereference in `calcExcessBlobGas` when `parent.BaseFee` is nil during post-Osaka blob gas calculation - (File: `consensus/misc/eip4844/eip4844.go`)

### Summary
`calcExcessBlobGas` in `consensus/misc/eip4844/eip4844.go` dereferences `parent.BaseFee` without a nil check when computing the EIP-7918 reserve price for Osaka-era blocks, mirroring the CVE-2021-3443 bug class (a decoder/consumer trusting a referenced field without validating its presence before dereferencing it).

### Finding Description
`calcExcessBlobGas` computes the reserve price introduced by EIP-7918 whenever `isOsaka` is true and the accumulated excess/target gas condition is met: [1](#0-0) 

At line 158, `baseCost.Mul(baseCost, parent.BaseFee)` calls `(*big.Int).Mul` with `parent.BaseFee` as the `y` argument. If `parent.BaseFee` is `nil`, this dereferences a nil `*big.Int` internally, causing a panic. There is no nil guard on `parent.BaseFee` anywhere in this function or in its caller `CalcExcessBlobGas`: [2](#0-1) 

The repository itself documents this exact bug class as a known regression, with a dedicated t8n test case: [3](#0-2) 

In the primary consensus header-verification path (`consensus/beacon/consensus.go`), `eip1559.VerifyEIP1559Header` (which rejects a London-active parent with nil `BaseFee`) is invoked before `eip4844.VerifyEIP4844Header` is reached, which does provide protection for that specific call chain: [4](#0-3) [5](#0-4) 

However, `CalcExcessBlobGas` has multiple other call sites that do not necessarily go through this same header-validation gate first — e.g. `core/chain_makers.go`, `miner/worker.go`, `eth/gasprice/feehistory.go`, `internal/ethapi/simulate.go`, and `cmd/evm/internal/t8ntool/execution.go`. Any of these paths that construct or supply a synthetic/derived parent header without a `BaseFee` set (for example a locally assembled header used during block building or simulation) could reach the vulnerable line and panic.

### Impact Explanation
If reachable with an attacker- or caller-supplied header lacking `BaseFee` on the Osaka-active path, this results in a deterministic panic. Per the scoping rules, "a deterministic panic or halt from one valid transaction or block is IN scope" and could constitute a Critical/High severity issue (chain halt / block-production failure) if reachable from a path processing a block or building a block without prior EIP-1559 validation of the parent.

### Likelihood Explanation
I was **not able to fully confirm** an unguarded, attacker-reachable call path in the time available. The main chain-import/consensus verification path (`consensus/beacon/consensus.go`) is protected because `VerifyEIP1559Header` runs first and guarantees `parent.BaseFee != nil` for any London-active parent, and canonical parent headers retrieved from the persisted chain should already have passed that validation when they were originally inserted. The remaining call sites in `miner/worker.go`, `core/chain_makers.go`, `eth/gasprice/feehistory.go`, and `internal/ethapi/simulate.go` operate on headers derived from the canonical chain or from test/simulation code, which likely also carry non-nil `BaseFee` in practice — I could not verify with certainty whether any of them can supply a nil-`BaseFee` parent header on a live/mainnet Osaka-era chain. The presence of a specific regression test (`cmd/evm/testdata/34`) strongly suggests this exact nil-dereference was previously observed and is being actively guarded against by external correctness of callers rather than a defensive check inside `calcExcessBlobGas` itself, which represents fragile, assumption-based safety rather than a structurally guaranteed invariant.

### Recommendation
Add an explicit nil check for `parent.BaseFee` inside `calcExcessBlobGas` (or `CalcExcessBlobGas`) before use in the EIP-7918 reserve-price branch, returning/panicking with a clear error instead of relying on every caller to have already validated the parent header via `VerifyEIP1559Header`. This removes the implicit cross-package invariant and hardens the function against any future or currently-unverified call path that supplies an incompletely-populated parent header.

### Proof of Concept
Not conclusively demonstrated end-to-end from an attacker-controlled input in the time available. The mechanical trigger is calling `eip4844.CalcExcessBlobGas(config, parent, headTimestamp)` (or any function that transitively calls it, e.g. `NewEVMBlockContext`, `miner` block assembly, `eth_simulateV1`, `eth_feeHistory`) with `config.IsOsaka(...)` true, `parent.ExcessBlobGas != nil`, the excess/target condition satisfied, and `parent.BaseFee == nil` — which is exactly the scenario the repository's own `cmd/evm/testdata/34` regression test was written to cover, indicating the underlying flaw is real but its exploitability depends on finding a caller that does not itself guarantee `parent.BaseFee` is set, which I was unable to fully verify within the available searches.

// CalcExcessBlobGas calculates the excess blob gas after applying the set of
// blobs on top of the excess blob gas.
func CalcExcessBlobGas(config *params.ChainConfig, parent *types.Header, headTimestamp uint64) uint64 {
	isOsaka := config.IsOsaka(config.LondonBlock, headTimestamp)
	bcfg, err := latestBlobConfig(config, headTimestamp)
	if err != nil {
		panic("calculating excess blob gas on nil blob config")
	}
	return calcExcessBlobGas(isOsaka, bcfg, parent)
}
