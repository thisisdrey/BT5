### Title
Per-IP QUIC connection rate limit can be reset early via LRU cache eviction churn - (File: streamer/src/nonblocking/connection_rate_limiter.rs)

### Summary
`ConnectionRateLimiter` wraps a `KeyedRateLimiter<IpAddr>` whose LazyLRU eviction (`maybe_shrink` in `net-utils/src/token_bucket.rs`) removes the *oldest* entries once a DashMap shard grows past `target_shard_size * 3/2`, purely based on `last_update` recency, with no regard for whether the bucket is currently depleted (actively rate-limiting an abusive IP). An attacker who legitimately controls a large address block (trivial with a single IPv6 /64 or /56 allocation, no spoofing required) can flush many distinct never-before-seen IPs through the connection path to force premature eviction of its own previously-throttled IP's bucket entry, causing that entry to reappear as "unseen" (`is_allowed` returns `true` again) with a brand-new, fully-refilled bucket on reinsertion.

### Finding Description
- `ConnectionRateLimiter::new` builds a `KeyedRateLimiter` with `target_capacity = CONNECTION_RATE_LIMITER_CLEANUP_SIZE_THRESHOLD = 100_000`. [1](#0-0) 
- Every new key insertion via `consume_tokens` decrements `countdown_to_shrink`; once `shrink_interval = target_capacity / 4` new keys have been inserted, `maybe_shrink()` runs. [2](#0-1) 
- `maybe_shrink` iterates each DashMap shard; if a shard's length exceeds `target_shard_size * 3 / 2`, it keeps only the `target_shard_size` most-recently-updated entries (by `TokenBucket.last_update`) and drops the rest — regardless of whether the dropped bucket is empty (actively enforcing a limit) or full. [3](#0-2) 
- Once an IP's `TokenBucket` entry is evicted from the map, `ConnectionRateLimiter::is_allowed` treats that IP as unseen (`None => true`), and `register_connection`'s next `consume_tokens` call allocates a fresh bucket cloned from `prototype_bucket` with full initial tokens. [4](#0-3) 
- This is invoked from the QUIC ingress path in `run_server`/`setup_connection`: `rate_limiter.is_allowed(...)` gates acceptance and `rate_limiter.register_connection(...)` consumes a token after handshake completes. [5](#0-4) [6](#0-5) 
- Exploit flow: attacker exhausts the per-IP quota for IP `A` (using `max_connections_per_ipaddr_per_min` connections), then, without touching `A` again, opens/aborts enough handshakes from a large number of distinct, genuinely-owned IPs (feasible cheaply from an IPv6 /64+ block) to push the relevant DashMap shard(s) past the `3/2` eviction threshold. Because `A`'s entry is now the *oldest* touched entry, it gets pruned. The attacker then reconnects from `A`, and since the map has no record, `is_allowed` returns `true` and a brand-new full-token bucket is created — before the token bucket's natural per-minute refill would have restored capacity. This is a rate-limit reset via cache-size-driven eviction rather than time-based token replenishment.
- Additionally, all the churn connections used to trigger eviction themselves consume tokens from the shared `overall_connection_rate_limiter` (a global `TokenBucket` sized by `MAX_CONNECTION_BURST`/`TOTAL_CONNECTIONS_PER_SECOND`), so the same burst simultaneously threatens to starve legitimate connection attempts hitting the global limiter at `run_server`. [7](#0-6) [8](#0-7) [9](#0-8) 

Existing guards do not prevent this: `is_allowed`/`register_connection` only check the per-IP token count, and the LazyLRU cleanup has no awareness of "in-cooldown" (empty) buckets vs. idle ones — it evicts strictly by `last_update` recency, so a deliberately-idle depleted bucket is exactly the kind of entry that gets pruned first.

### Impact Explanation
This is a QoS/rate-limit evasion: the per-IP connection throttle (`DEFAULT_MAX_CONNECTIONS_PER_IPADDR_PER_MINUTE`) intended to bound per-source QUIC connection churn to the leader's TPU can be circumvented by an attacker who owns (not spoofs) a sufficiently large contiguous address range, letting it sustain a higher effective per-address connection rate than configured, and/or contend with the shared `overall_connection_rate_limiter` to degrade availability for legitimate unstaked/staked peers connecting during the burst. This falls in the QoS-evasion / rate-limiting-bypass bounty category rather than a full sigverify/sanitization bypass.

### Likelihood Explanation
Feasibility hinges entirely on the attacker legitimately owning enough distinct source addresses to exceed a shard's `target_shard_size * 3/2` threshold (with default 100_000 target capacity split across `num_shards` — e.g., tens of thousands of new keys concentrated in one shard). A single machine with a routed IPv6 /64 (a common, cheap ISP allocation) can trivially generate hundreds of thousands of legitimately-routable, non-spoofed source addresses, making this realistically reachable by a single unprivileged attacker without requiring a botnet, staked status, or protocol-level spoofing. It is repeatable indefinitely, bounded only by the attacker's ability to generate handshake attempts fast enough to trigger `maybe_shrink` before natural token refill.

### Recommendation
Change the eviction policy in `KeyedRateLimiter::maybe_shrink` (or add a dedicated policy for `ConnectionRateLimiter`) to avoid evicting buckets that are currently depleted (i.e., actively enforcing a limit, `current_tokens() == 0`) in preference to idle/full buckets, or track and preserve "recently rate-limited" keys separately from the LRU cache so that eviction cannot be used to reset the limit before the token bucket's own time-based refill. At minimum, bound target_shard_size sizing/shrink triggers such that the shrink threshold cannot be reached faster than the rate-limit window by a single reachable address range, and audit whether `is_allowed`/`register_connection` should treat "evicted-while-still-limited" as a boundary condition to be avoided by design (e.g., by re-touching `last_update` whenever `is_allowed` is checked, not only on `register_connection`, so that repeatedly-probed IPs are not the first pruned).

### Proof of Concept
Rust unit test sketch for `net-utils/src/token_bucket.rs` demonstrating premature eviction of an actively-limited key:
```rust
#[test]
fn test_eviction_can_reset_depleted_bucket_early() {
    // small capacity/shards to make the scenario reproducible quickly
    let prototype = TokenBucket::new(1, 1, 1.0 / 3600.0); // 1 token/hour refill, effectively no natural refill within test
    let rl = KeyedRateLimiter::new(8, prototype, 2); // target_capacity=8, shrink_interval=2

    let victim = IpAddr::V4(Ipv4Addr::from_bits(1));
    // deplete victim's single token
    rl.consume_tokens(victim, 1).unwrap();
    assert!(rl.consume_tokens(victim, 1).is_err(), "victim should now be rate-limited");

    // churn many distinct new keys through the same shard to trigger maybe_shrink
    // and evict victim (oldest last_update) before natural refill
    for i in 2..200u32 {
        let ip = IpAddr::V4(Ipv4Addr::from_bits(i));
        let _ = rl.consume_tokens(ip, 1);
    }

    // Assert victim's rate-limit state was wiped early: current_tokens() is None
    // (evicted) instead of remaining "0/limited" as it should be until natural refill.
    assert_eq!(
        rl.current_tokens(victim),
        None,
        "victim's depleted bucket was evicted by churn, not by token refill"
    );
    // Reconnecting now succeeds with a fresh full bucket, bypassing the intended limit:
    assert!(rl.consume_tokens(victim, 1).is_ok());
}
```
Expected result: the assertions pass, demonstrating that a churn burst of distinct, legitimately-owned keys evicts an actively rate-limited entry from the map before its token bucket would naturally refill, allowing the corresponding IP to reconnect as if freshly seen.

    pub fn consume_tokens(&self, key: K, request_size: u64) -> Result<u64, u64> {
        let (entry_added, res) = {
            let bucket = self.data.entry(key);
            match bucket {
                Entry::Occupied(entry) => (false, entry.get().consume_tokens(request_size)),
                Entry::Vacant(entry) => {
                    // if the key is not in the LRU, we need to allocate a new bucket
                    let bucket = self.prototype_bucket.clone();
                    let res = bucket.consume_tokens(request_size);
                    entry.insert(bucket);
                    (true, res)
                }
            }
        };

        if entry_added {
            if let Ok(count) =
                self.countdown_to_shrink
                    .fetch_update(Ordering::Relaxed, Ordering::Relaxed, |v| {
                        if v == 0 {
                            // reset the countup to starting position
                            // thus preventing other threads from racing for locks
                            None
                        } else {
                            Some(v.saturating_sub(1))
                        }
                    })
            {
                if count == 1 {
                    // the last "previous" value we will see before counter reaches zero
                    self.maybe_shrink();
                    self.countdown_to_shrink
                        .store(self.shrink_interval, Ordering::Relaxed);
                }
            } else {
                self.approx_len.fetch_add(1, Ordering::Relaxed);
            }
        }
        res
    }

    #[allow(clippy::arithmetic_side_effects)]
    fn maybe_shrink(&self) {
        let mut actual_len = 0;
        let target_shard_size = self.target_capacity / self.data.shards().len();
        if target_shard_size == 0 {
            return;
        }
        let mut entries = Vec::with_capacity(target_shard_size * 2);
        for shardlock in self.data.shards() {
            let mut shard = shardlock.write();

            if shard.len() <= target_shard_size * 3 / 2 {
                actual_len += shard.len();
                continue;
            }
            entries.clear();
            entries.extend(
                shard.drain().map(|(key, value)| {
                    (key, value.get().last_update.load(Ordering::SeqCst), value)
                }),
            );

            entries.select_nth_unstable_by_key(target_shard_size, |(_, last_update, _)| {
                Reverse(*last_update)
            });

            shard.extend(
                entries
                    .drain(..)
                    .take(target_shard_size)
                    .map(|(key, _last_update, value)| (key, value)),
            );
            debug_assert!(shard.len() <= target_shard_size);
            actual_len += shard.len();
        }
        self.approx_len.store(actual_len, Ordering::Relaxed);
    }
