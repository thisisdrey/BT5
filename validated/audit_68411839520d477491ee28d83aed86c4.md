### Title
Gas-key nonce double-spend via stale prefetch cache read in `verify_and_charge_gas_key_tx_ephemeral` - (File: runtime/runtime/src/lib.rs, runtime/runtime/src/verifier.rs)

### Finding Description
The gas-key transaction verification path reads the current nonce for a `(signer_id, pubkey, nonce_index)` tuple from the `gas_key_nonces` prefetch cache via an immutable `.get()` call [1](#0-0) , then passes that snapshot value as `current_nonce` into `verify_and_charge_gas_key_tx_ephemeral` [2](#0-1) . That function is explicitly documented to perform no mutation of `account` or `access_key`, and the caller is responsible for applying nonce/balance updates afterward via `VerificationResult::apply` [3](#0-2) .

Unlike `accounts` and `access_keys`, which are looked up with `.get_mut()` on each iteration (allowing direct in-place mutation of the same referenced object across the loop) [4](#0-3) , `gas_key_nonces` is only read with `.get()`, and the corresponding write path is not visible in this per-transaction loop segment. If the nonce write-back for a successful gas-key transaction is not immediately reflected into the same `gas_key_nonces` prefetch structure queried at line 2113 (e.g., if it's instead written only to the trie/`state_update` and not to the in-memory prefetch snapshot used for lookups), then a second transaction in the same chunk using the same `(signer_id, pubkey, nonce_index)` and nonce value would still observe the stale `current_nonce`, pass `verify_nonce`'s monotonicity check, and be accepted a second time.

### Impact Explanation
If confirmed, this would allow duplicate acceptance of two gas-key transactions with the same nonce within one chunk, resulting in double balance charging and duplicate receipt creation — a replay/double-spend of gas-key-funded actions, falling under NEAR's "double-spend/replay" and "loss of user funds" bounty categories.

### Likelihood Explanation
I was unable to fully trace the write-back mechanism for `gas_key_nonces` (the code applying `VerificationResult` for the `Success`/`DepositFailed` branches was not visible in the sections read), so I cannot conclusively confirm whether the in-memory prefetch cache is updated in place before the next loop iteration's read at line 2113, or whether it lags behind (only written to `state_update`/trie). The asymmetry between `.get_mut()` for accounts/access_keys and `.get()` for `gas_key_nonces`, combined with `verify_and_charge_gas_key_tx_ephemeral`'s explicit "performs no mutation" contract, is circumstantial evidence supporting the described staleness issue, but is not itself conclusive proof of the exploit without seeing the actual apply/write-back code path.

### Recommendation
Confirm (via reading the apply/write-back logic that follows this snippet, and/or the `PrefetchStagedMap`/cache implementation backing `gas_key_nonces`) whether nonce updates from an earlier transaction in the same chunk are reflected before the next transaction's lookup. If not, update the in-memory `gas_key_nonces` entry immediately after a successful (or deposit-failed-but-nonce-consuming) gas-key transaction is verified, before processing the next transaction in the same batch, mirroring the `get_mut`-based in-place update pattern used for `accounts` and `access_keys`.

### Proof of Concept
Integration test plan (runtime/runtime/src/tests/apply.rs):
1. Create an account with a `GasKeyFullAccess` key with `num_nonces >= 1`, and sufficient balance for two transactions.
2. Build `tx_a` and `tx_b`, both with `nonce = N+1` and `nonce_index = 0`, signed by the same gas key.
3. Include both in the same chunk's transaction list passed to a single `Runtime::apply` call.
4. Assert only one `ExecutionOutcome`/`TxVerdict::Success` is produced (the other must fail with `InvalidNonce`), and that the gas-key balance is charged exactly once and only one receipt is created.
5. If both transactions succeed and two receipts/charges occur, the vulnerability is confirmed.

Note: due to inability to fully inspect the write-back/apply code path for `gas_key_nonces` within the tool budget for this audit, this finding should be validated further by tracing `VerificationResult::apply` and the `gas_key_nonces` prefetch map implementation before treating it as fully confirmed.
