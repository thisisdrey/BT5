## Title
Same-block `DeleteKey`+`AddKey` re-seeds an access key's nonce *below* an already-consumed nonce, enabling replay of a prior `SignedTransaction` (works with plain `TransactionV0`, no GasKeys/V1 needed) - (`runtime/runtime/src/access_keys.rs`)

## Summary
`initial_nonce_value(block_height)` reseeds a re-created access key's nonce purely as a function of the *current* block height, with no memory of the nonce the same key already reached. Because self-targeted `DeleteKey`+`AddKey` actions execute as a *local receipt in the same block* as the transaction that spent a higher nonce, the reseed can overwrite the access key's nonce with a value lower than one already consumed in that same block, letting a stale `SignedTransaction` (any nonce mode, including plain V0/`Monotonic`) be legally resubmitted and re-executed later.

## Finding Description
`initial_nonce_value` computes the seed for a (re-)created regular key strictly from `block_height`, independent of any prior nonce history for that key: `(block_height - 1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` [1](#0-0) . `add_regular_key` unconditionally overwrites `access_key.nonce` with this seed whenever a key is (re-)added, and `action_add_key` only refuses to add if a key by that public key currently exists — a `DeleteKey` earlier in the same action list clears that check [2](#0-1) [3](#0-2) .

Nonce validation (`verify_nonce`) for `NonceMode::Monotonic` — the *only* mode `TransactionV0` can ever have, since `Transaction::nonce_mode()` forces V0 to `Monotonic` [4](#0-3)  — simply requires `tx_nonce > current_nonce` [5](#0-4) . There is no independent, hash-based, global replay-protection: the nonce comparison is the sole defense.

The exploitable sequence, all within one block (self-targeted `DeleteKey`/`AddKey` produce local receipts executed in the same chunk as the originating transaction, per `docs/architecture/how/tx_receipts.md` and `docs/RuntimeSpec/ApplyingChunk.md` [6](#0-5) ):

1. Access key `K` (FullAccess, plain V0-compatible) is at nonce `N` in block `H` (e.g. seeded at `H` itself, or close to it, so `S=(H-1)*1e6` is still below `N+1`).
2. `TxA` (nonce `N+1`): ordinary `send_money` (V0) using `K`, e.g. a transfer of value. Verification bumps `access_key.nonce` to `N+1` immediately as the transaction is processed [7](#0-6) .
3. `TxB` (nonce `N+2`, self-targeted, signed by `K`): actions `[DeleteKey(K), AddKey(K, FullAccess)]`. Verification again bumps the nonce (to `N+2`) using the *pre-action* key state, then the resulting local receipt executes in the *same block*: `DeleteKey` removes the record, `AddKey` recreates it and resets `access_key.nonce = initial_nonce_value(H) = S`. Since `S` was computed from the same block height as `TxA`/`TxB`, `S <= N < N+1`.
4. End of block `H`: `access_key(K).nonce == S`, which is *lower* than the nonce already spent by `TxA` (`N+1`).
5. In any later block, anyone who has observed `TxA` on-chain (transactions are public) resubmits the exact same `SignedTransaction` bytes. `verify_nonce` sees `tx_nonce (N+1) > current_nonce (S)` and **accepts** it — `TxA` executes a second time.

This is not gated by `GasKeys`, `StrictNonce`, `TransactionV1`, or any newer feature; it only requires `AddKey`/`DeleteKey` actions and the `Monotonic` nonce check, both of which are the default/only behavior for legacy `TransactionV0`.

## Impact Explanation
Any action from the replayed transaction re-executes with full authorization it never received a second time — a `Transfer` moves funds again, a `FunctionCall` re-executes with its original deposit, etc. Because the replay can be submitted by *any observer* of the public chain (not just the original signer), this is a genuine unauthorized double-spend/replay of a previously-executed, presumably one-time-authorized transaction — matching the "double-spend/replay" and "theft ... of user funds" bounty categories. It is universal to the entire existing account base using plain V0 FullAccess keys, since the vulnerable path (`add_regular_key`/`initial_nonce_value`, `verify_nonce` Monotonic) is exercised identically for V0 transactions.

## Likelihood Explanation
Preconditions: the account owner (or an attacker who compromises timing of their own submissions — no elevated privilege needed) must get a nonce-incrementing transaction and a self-targeted `DeleteKey`+`AddKey` (same public key) transaction both processed in the *same block height*. This is attacker-controllable by submitting several own transactions back-to-back via a public RPC when the network isn't congested; it is deterministically reproducible in a runtime/integration test where multiple transactions are supplied to one `apply()` call (as already done for ordering tests such as `test_transaction_multiple_access_keys_with_apply` in `runtime/runtime/src/tests/apply.rs`). No signature forgery, no validator/node access, and no leaked keys are required — only ordinary transaction crafting and public knowledge of a previously broadcast signed transaction.

## Recommendation
Do not reset a re-created regular access key's nonce to a value that can fall below a nonce most recently observed for that (account, public_key) pair within the same or an earlier block. Either (a) track and persist the highest nonce ever used by a given public key even across delete/re-add cycles and seed with `max(initial_nonce_value(block_height), previous_highest_nonce + 1)`, or (b) forbid `AddKey` from reusing a public key that was deleted earlier in the same receipt/transaction batch, or (c) require the reseed value to strictly exceed any nonce already committed for that signer/pubkey pair during the current chunk's `TrieUpdate`.

## Proof of Concept
Runtime integration test plan (mirrors existing `runtime/runtime/src/tests/apply.rs` patterns using a single `Runtime::apply` call to guarantee same-block-height execution):
1. Set up account `alice` with FullAccess key `K` at some nonce `N` (e.g. via `setup_runtime_with_keys`).
2. Build `tx_a = SignedTransaction::send_money(N+1, alice, bob, K, deposit, block_hash)` (plain V0).
3. Build `tx_b = SignedTransaction::from_actions(N+2, alice, alice, K, vec![DeleteKey(K), AddKey(K, FullAccess)], block_hash)` (V0, self-targeted so it becomes a local receipt).
4. Call `runtime.apply(..., transactions=[tx_a, tx_b], ...)` at height `H`, commit the result.
5. Assert: `access_key(alice, K).nonce == (H-1)*ACCESS_KEY_NONCE_RANGE_MULTIPLIER`, and this value is `< N+1`.
6. In a second `apply()` call at height `H+1`, resubmit `tx_a` unchanged.
7. Assert `tx_a` is accepted (no `InvalidNonce` error) and Bob's balance reflects the transfer amount twice — proving the same signed transaction executed twice from a single authorization.

pub(crate) fn initial_nonce_value(block_height: BlockHeight) -> Nonce {
    // Set default nonce for newly created access key to avoid transaction hash collision.
    // See <https://github.com/near/nearcore/issues/3779>.
    (block_height - 1) * near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER
}

    account: &mut Account,

    account_id: &AccountId,

    if get_access_key(state_update, account_id, &add_key.public_key)?.is_some() {
        result.result = Err(ActionErrorKind::AddKeyAlreadyExists {
            account_id: account_id.to_owned(),
            public_key: add_key.public_key.clone().into(),
        }

        return Ok(());
    }

    let fee_config = &apply_state.config.fees;

    if let Some(gas_key_info) = add_key.access_key.gas_key_info() {

            account,
            account_id,
            &add_key.public_key,
            &add_key.access_key,
            gas_key_info,
            apply_state.block_height,
        )?;

        add_regular_key(
            fee_config,
            state_update,
            account,
            account_id,
            &add_key.public_key,
            &add_key.access_key,
            apply_state.block_height,
        )?;
    }

    Ok(())
}

fn add_regular_key(
    fee_config: &RuntimeFeesConfig,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    public_key: &PublicKey,
    access_key: &AccessKey,
    block_height: BlockHeight,
) -> Result<(), StorageError> {
    let mut access_key = access_key.clone();
    access_key.nonce = initial_nonce_value(block_height);
    set_access_key(state_update, account_id.clone(), public_key.clone(), &access_key);

    account.set_storage_usage(
        account
            .storage_usage()
            .checked_add(access_key_storage_usage(fee_config, public_key, &access_key))
            .ok_or_else(|| {
                StorageError::StorageInconsistentState(format!(
                    "Storage usage integer overflow for account {}",
                    account_id
                ))
            })?,
    );
    Ok(())
}
