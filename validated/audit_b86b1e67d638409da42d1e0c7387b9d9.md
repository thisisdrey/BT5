### Title
Global Fee State Can Be Front-Run and Initialized By Any Unprivileged Account - (File: `programs/marginfi/src/instructions/marginfi_group/init_global_fee_state.rs`)

### Summary
The `initialize_fee_state` instruction handler creates the program-wide `FeeState` singleton PDA and assigns the caller-supplied `admin_key` as `global_fee_admin` and an arbitrary `fee_wallet`, without any access-control check restricting who may call it. This mirrors the `CSFeeOracle.initialize()` bug class: a privileged, one-time initializer is exposed with no `onlyOwner`/allow-list equivalent, so whoever lands the transaction first becomes the privileged party.

### Finding Description
`InitFeeState` only requires `payer: Signer<'info>` and a `system_program`; there is no constraint tying the caller to a known deployer key, upgrade authority, or any pre-existing privileged account: [1](#0-0) [2](#0-1) 

The handler blindly writes the attacker-controlled `admin_key` and `fee_wallet` parameters into the newly created PDA: [3](#0-2) 

Because `fee_state` is a PDA derived purely from the constant `FEE_STATE_SEED` (no signer-derived seed component) and uses Anchor's `init` constraint, it can only be created once program-wide; the first successful caller permanently owns the `global_fee_admin` role. This is structurally identical to the reported Lido issue: an external, unauthenticated caller can front-run the legitimate deployer's initialization transaction and seize a privileged role.

This `FeeState` singleton is not a peripheral or mock component — its `global_fee_wallet`, `program_fee_fixed`, and `program_fee_rate` fields are read into every newly created `MarginfiGroup`'s fee cache at group-initialization time: [4](#0-3) 

so control over `FeeState` translates directly into control over where protocol-wide program fees are routed for every group created afterward.

### Impact Explanation
If an attacker front-runs the legitimate `initialize_fee_state` call, they become `global_fee_admin` and control `global_fee_wallet`/`program_fee_fixed`/`program_fee_rate` for the entire deployed program. Downstream admin-gated instructions such as `edit_global_fee`/`config_group_fee` (which authorize via `has_one = global_fee_admin`) would then only be callable by the attacker, letting them redirect protocol fee revenue to an attacker-controlled wallet and set/alter fee parameters for every group on the program. This is a concrete unauthorized-state-change / fee-misdirection impact within the fee-accounting path, not a theoretical or admin-only concern (the vulnerability is precisely the absence of the privileged check).

### Likelihood Explanation
Exploitation requires the attacker to submit the `InitFeeState`-based instruction and have it processed before the legitimate deployer's own initialization transaction lands — a single-shot race at program deployment time. This is a narrower window than a routinely-callable instruction, but the vulnerability is a genuine code-level omission (no privileged signer/allow-list check), matching the acknowledged-but-unfixed root cause pattern in the external report. Likelihood depends entirely on operational timing/deployment practices rather than any code-level mitigation.

### Recommendation
Add an access-control check to `InitFeeState`/`initialize_fee_state`, e.g. require `payer` to match a hardcoded/expected deployer key or the program's upgrade authority (via `bpf_loader_upgradeable` program-data account check), or bootstrap `global_fee_admin` in the same transaction as program deployment/upgrade so no independent front-runnable transaction window exists.

### Proof of Concept
1. Monitor for program deployment of the marginfi program (or for the `FeeState` PDA, derived from `FEE_STATE_SEED`, to not yet exist).
2. Before the legitimate deployer submits their `initialize_fee_state` transaction, submit a transaction with:
   - `payer`: attacker's own signer keypair,
   - `fee_state`: the PDA at `[FEE_STATE_SEED]`,
   - `admin_key`: attacker's own pubkey,
   - `fee_wallet`: attacker's own wallet,
   - other fee parameters of the attacker's choosing.
3. Because `InitFeeState` has no privileged-signer constraint (only `payer: Signer`), this transaction succeeds and creates the singleton `FeeState` with the attacker as `global_fee_admin`.
4. The legitimate deployer's subsequent `initialize_fee_state` call fails (`init` constraint — account already exists), permanently leaving the attacker in control of `global_fee_admin`, and thus of `edit_global_fee`/`config_group_fee` and the `global_fee_wallet` used by all future `MarginfiGroup`s created via `marginfi_group_initialize`.
