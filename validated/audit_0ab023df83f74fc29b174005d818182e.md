### Title
Division-before-multiplication in `UnDelegateResourceActuator` causes bandwidth/energy transfer-usage truncation on unstake - (File: actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java)

### Summary
`UnDelegateResourceActuator.execute()`, invoked directly by any account holder who submits an `UnDelegateResourceContract` transaction to reclaim delegated TRX stake, computes the resource `transferUsage` that must be carried over to the receiver's usage window using floating-point division performed *before* multiplication, rather than multiplying first and dividing last as recommended to avoid truncation/rounding loss.

### Finding Description
In the BANDWIDTH and ENERGY branches of `execute()`: [1](#0-0) 

```java
long unDelegateMaxUsage = (long) ((double) unDelegateBalance / TRX_PRECISION
    * ((double) (dynamicStore.getTotalNetLimit()) / dynamicStore.getTotalNetWeight()));
transferUsage = (long) (receiverCapsule.getNetUsage()
    * ((double) (unDelegateBalance) / receiverCapsule.getAllFrozenBalanceForBandwidth()));
transferUsage = min(unDelegateMaxUsage, transferUsage);
```
and the equivalent ENERGY branch: [2](#0-1) 

Both `unDelegateMaxUsage` and `transferUsage` compute a ratio (`getTotalNetLimit()/getTotalNetWeight()`, or `unDelegateBalance/getAllFrozenBalanceForBandwidth()`) as an intermediate `double` division *before* multiplying it by another operand, instead of performing `a * b / c` in one combined expression. This is exactly the bug class described in the external report: dividing first discards precision that a subsequent multiplication can never recover, whereas multiplying first preserves the full numerator before the single final division/truncation.

This is notable because elsewhere in the same codebase (`RepositoryImpl.calculateGlobalEnergyLimit`, `ResourceProcessor.calculateGlobalLimitV1/V2`, `ResourceProcessor.increase`/`getUsage`) the exact same class of division-order bug has been identified and is being actively remediated behind an `allowHardenResourceCalculation` feature flag that switches the calculation to `BigInteger`-based "multiply first, divide once at the end" arithmetic: [3](#0-2) [4](#0-3) 

`UnDelegateResourceActuator`, however, is not covered by this hardening effort at all — it still performs the unguarded, unhardened double-division-then-multiply pattern unconditionally, with no `hardenCalculation`/`allowHardenResourceCalculation` gate.

### Impact Explanation
Because `transferUsage`/`unDelegateMaxUsage` are computed via double division before multiplication, the resulting bandwidth/energy usage transferred to the receiver upon undelegation can be truncated or rounded incorrectly relative to the mathematically exact `a*b/c` value. Depending on rounding direction, this can either:
- Under-transfer usage to the receiver, permanently losing legitimate accounted resource usage tracking (resource-accounting drift), or
- Over/under compute `unDelegateMaxUsage` used as a cap via `min(...)`, letting `transferUsage` diverge from the exact proportional value it is meant to represent.

This affects bandwidth/energy accounting integrity for delegated resources touched by every `UnDelegateResourceContract` transaction — a broadly reachable, unprivileged, single-transaction path (any TRX holder with delegated resources can trigger it). It does not directly move TRX balances, but resource usage window state is part of the chain's resource-accounting/anti-spam ledger, so incorrect values can cause persistent inconsistency between an account's tracked resource usage and its true entitlement.

### Likelihood Explanation
High reachability: `UnDelegateResourceActuator` is executed by a normal `UnDelegateResourceContract` transaction, requiring only a delegated-resource relationship and no special privilege. The precision-loss condition triggers whenever the intermediate ratios are not exact integers, which is the common case for arbitrary `unDelegateBalance`, `totalNetWeight`, and `getAllFrozenBalanceForBandwidth()` values chosen by ordinary network activity/state — no adversarial setup beyond crafting the unstake amount is required.

### Recommendation
Restructure the two computations to multiply before dividing, mirroring the pattern already adopted (behind `allowHardenResourceCalculation`) in `ResourceProcessor`/`RepositoryImpl`:
```java
long unDelegateMaxUsage = MarketUtils.multiplyAndDivide(
    unDelegateBalance, dynamicStore.getTotalNetLimit(),
    TRX_PRECISION * dynamicStore.getTotalNetWeight(), disableJavaLangMath());
long transferUsage = MarketUtils.multiplyAndDivide(
    receiverCapsule.getNetUsage(), unDelegateBalance,
    receiverCapsule.getAllFrozenBalanceForBandwidth(), disableJavaLangMath());
```
using `BigInteger`/overflow-safe multiply-then-divide helpers (as already used elsewhere in the codebase, e.g. `MarketUtils.multiplyAndDivide`, `ResourceProcessor.calculateGlobalLimitV2`) instead of `(double) a/b * c`.

### Proof of Concept
Given `unDelegateBalance = 3_000_000L` (3 TRX), `TRX_PRECISION = 1_000_000L`, `getTotalNetLimit() = 43_200_000_000L`, `getTotalNetWeight() = 7L` (a weight value not evenly dividing the limit, plausible in a live network):

- Correct multiply-first result: `(3_000_000 * 43_200_000_000) / (1_000_000 * 7) = 129,600,000,000,000,000 / 7,000,000 = 18,514,285,714` (floor).
- Buggy divide-first-as-double result: `(double)3_000_000/1_000_000 = 3.0`; `(double)43_200_000_000/7 = 6,171,428,571.428571...`; product `= 18,514,285,714.285713...` truncated to `long` → `18,514,285,714`.

While this particular example is close due to double's 52-bit mantissa keeping ~15-17 significant digits, the discrepancy grows and becomes observable once `unDelegateBalance`/`getAllFrozenBalanceForBandwidth()` or `getTotalNetLimit()`/`getTotalNetWeight()` values exceed double's exact-integer representable range (~2^53) or when the intermediate ratio requires many fractional digits that get rounded before the second multiplication — exactly the scenario the project's own `CalculateGlobalLimitHardenTest` suite was written to catch for the sibling `ResourceProcessor`/`RepositoryImpl` calculations: [5](#0-4) 
That test demonstrates the double-precision-loss class is real and already fixed for other call sites; `UnDelegateResourceActuator` remains unpatched and reachable by any user's unstake transaction.

```java
  /**
   * Hardened replacement of legacy V2 formula
   * {@code (long)(((double) frozeBalance / TRX_PRECISION)
   *               * ((double) totalLimit / totalWeight))}.
   *
   * <p>Preserves V2 semantics: equivalent to
   * {@code (frozeBalance * totalLimit) / (TRX_PRECISION * totalWeight)} with
   * a single integer truncation at the end. Critically, fractional weight
   * (i.e. {@code frozeBalance < TRX_PRECISION}) is preserved through the
   * multiplication and only truncated at the final divide, so small balances
   * yield the same proportional result as the double-arithmetic path.
   */
  protected long calculateGlobalLimitV2(long frozeBalance,
      long totalLimit, long totalWeight) {
    return BigInteger.valueOf(frozeBalance)
        .multiply(BigInteger.valueOf(totalLimit))
        .divide(BigInteger.valueOf(TRX_PRECISION)
            .multiply(BigInteger.valueOf(totalWeight)))
        .longValueExact();
  }
```
