Found a strong analog: `MortgageService.getOldReward` (and its `VoteRewardUtil`/`RewardViCalService` counterparts) computes historical voting rewards with a loop whose iteration count is `endCycle - beginCycle` (the number of maintenance cycles since the account last withdrew/claimed reward), with **no upper bound** on how large that gap can grow.

### Title
Unbounded per-cycle reward computation loop can make reward withdrawal/settlement fail or force costly recomputation - ([File: chainbase/src/main/java/org/tron/core/service/MortgageService.java])

### Summary
`MortgageService.withdrawReward`/`queryReward` and the TVM-reachable `VoteRewardUtil.withdrawReward`/`queryReward` call `computeReward(beginCycle, endCycle, ...)`, which for pre-"new reward algorithm" cycles falls back to `getOldReward`, iterating once per cycle between the account's `beginCycle` and `endCycle`: [1](#0-0) 
This is directly analogous to EMPAM's settlement loop iterating over every unsettled bid: the loop bound (`endCycle - beginCycle`, i.e., "how long since the user last interacted") is fully attacker/user controlled by simply not calling `WithdrawBalanceContract`/`withdrawreward` for a long time, exactly like letting bids accumulate before settlement.

### Finding Description
`beginCycle`/`endCycle` are per-account cursors persisted in `DelegationStore` and only advance when the account calls withdraw (`WithdrawBalanceActuator` → `MortgageService.withdrawReward`, reachable by any signed transaction) or the TVM-native `withdrawReward`/`WithdrawRewardProcessor` (reachable by any contract call, per the allowed "actuator validate/execute" and "stake/delegation/reward math" categories): [2](#0-1) [3](#0-2) 

Each `payReward`/maintenance cycle advances `currentCycle` (roughly every 6 hours), and `withdrawReward` is O(1) *only if called every cycle*. If a voting account never calls withdraw, `beginCycle` stays fixed while `currentCycle` keeps advancing indefinitely, so `endCycle - beginCycle` grows without bound over months/years. When the account finally does call `withdrawReward` (or any other transaction that internally triggers it, e.g. `VoteWitnessActuator.countVoteAccount` also calls `mortgageService.withdrawReward(ownerAddress)` before any vote can be counted): [4](#0-3) 
the single transaction must synchronously execute `getOldReward`'s per-cycle loop: [1](#0-0) 
with each iteration performing further `DelegationStore` reads (`getReward`, `getWitnessVote`) inside `computeReward(cycle, votes)`: [5](#0-4) 
For the TVM path, `VoteRewardUtil.computeReward` similarly loops per vote per delta, and is invoked on every `freezeBalanceV2`, `unfreezeBalanceV2`, `voteWitness`, and `withdrawReward` TVM opcode/native-contract call, all metered under the transaction's finite energy limit: [6](#0-5) 

Because a single account (or a large number of accounts that all coordinate to withhold withdrawal for a long time, or simply forget) can build up an arbitrarily large `endCycle - beginCycle` gap, the reward-settlement transaction becomes arbitrarily expensive to process, mirroring the reported bug class of "gas-intensive iteration whose bound is attacker/organically controlled and unlimited."

### Impact Explanation
- For the account-model path (`MortgageService.withdrawReward`), there is no VM energy metering — the loop simply runs synchronously as part of block processing. An account that accumulates enough unclaimed cycles could make its own withdraw (or any vote transaction, since `countVoteAccount` unconditionally calls `withdrawReward`) take arbitrarily long, causing that transaction (and thus the containing block) to take excessive CPU time to process, which can affect block production timing.
- For the TVM path (`VoteRewardUtil`), the same unbounded loop is gas-metered, so the practical effect is the transaction/contract call permanently reverts with out-of-energy once the accumulated cycle gap is large enough — permanently trapping the pending reward for that account (denial of service / freezing of funds), the same "funds permanently stuck due to unresolvable gas-exhausting settlement" impact described in the source report.
- This also affects the reward computation triggered as a side effect of ordinary voting (`VoteWitnessActuator`/`VoteWitnessProcessor`), meaning an account that has been dormant for a long period can find that voting itself becomes impossible.

### Likelihood Explanation
Likelihood is moderate-to-high in practice: any account that freezes/votes once and never interacts again for a sufficiently long period (governed only by wall-clock time / number of maintenance cycles, not by any protocol-enforced cap) will accumulate this backlog. No special privilege or coordination is required — a single ordinary user's own inactivity is sufficient to trigger the worst case for their own account, and the number of cycles is unbounded because there is no `MAX_CYCLE_GAP`-style cap analogous to the `UNFREEZE_MAX_TIMES` (32) protection that was added for the unfreeze-list, or the `MAX_MATCH_NUM` cap added to `MarketSellAssetActuator` for exactly this class of unbounded-iteration issue.

### Recommendation
Introduce a bound on `endCycle - beginCycle` analogous to `UNFREEZE_MAX_TIMES`/`MAX_MATCH_NUM`: either (a) force periodic/forced settlement (e.g., auto-checkpoint reward accrual every N cycles during maintenance so `beginCycle` cannot drift arbitrarily far from `currentCycle`), or (b) allow/require partial incremental withdrawal (settle a capped number of cycles per call, similar to processing bids/order matches in batches) so a single transaction's cost is bounded regardless of how long the account has been dormant. Apply the same fix to both `MortgageService.getOldReward`/`computeReward` and `VoteRewardUtil.computeReward`.

### Proof of Concept
1. Freeze balance and vote for a witness from account A (via `VoteWitnessContract` or TVM `voteWitness`), setting `beginCycle` to the current cycle.
2. Do not call `WithdrawBalanceContract` / `withdrawReward` for a very large number of maintenance cycles (each ~6 hours; e.g., let `currentCycle - beginCycle` grow to a very large N over an extended period, or in a private/test network shorten `maintenanceTimeInterval` to accelerate cycle advancement).
3. Call `WithdrawBalanceContract` (or trigger any vote transaction, since `VoteWitnessActuator.countVoteAccount` calls `mortgageService.withdrawReward` first) for account A.
4. Observe that `getOldReward`/`computeReward` executes an O(N) loop over `DelegationStore` reads before completing; for the TVM-native `VoteRewardUtil` path, show that once N is large enough the call consistently exceeds any feasible `feeLimit`/energy limit, causing `OutOfEnergyException` and permanently preventing that account's reward withdrawal and, incidentally, its ability to vote (since `countVoteAccount` also calls `withdrawReward`).

*Note: I was unable to independently confirm production-scale timing/energy-cost figures (i.e., the exact number of cycles required to exceed typical `feeLimit`/block-time budgets) using the indexed code alone; a Devin session with access to full test tooling would be needed to benchmark `getOldReward`/`computeReward` cost per cycle and derive the precise N threshold.*

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }

  public static void withdrawReward(byte[] address, Repository repository) {
    if (!VMConfig.allowTvmVote()) {
      return;
    }
    AccountCapsule accountCapsule = repository.getAccount(address);
    long beginCycle = repository.getBeginCycle(address);
    long endCycle = repository.getEndCycle(address);
    long currentCycle = repository.getDynamicPropertiesStore().getCurrentCycleNumber();
    long reward = 0;
    if (beginCycle > currentCycle || accountCapsule == null) {
      return;
    }
    if (beginCycle == currentCycle) {
      AccountCapsule account = repository.getAccountVote(beginCycle, address);
      if (account != null) {
        return;
      }
    }
    if (beginCycle + 1 == endCycle && beginCycle < currentCycle) {
      AccountCapsule account = repository.getAccountVote(beginCycle, address);
      if (account != null) {
        reward = computeReward(beginCycle, endCycle, account, repository);
        adjustAllowance(address, reward, repository);
        reward = 0;
      }
      beginCycle += 1;
    }
    endCycle = currentCycle;
    if (CollectionUtils.isEmpty(accountCapsule.getVotesList())) {
      repository.updateBeginCycle(address, endCycle + 1);
      return;
    }
    if (beginCycle < endCycle) {
      reward += computeReward(beginCycle, endCycle, accountCapsule, repository);
      adjustAllowance(address, reward, repository);
    }
    repository.updateBeginCycle(address, endCycle);
    repository.updateEndCycle(address, endCycle + 1);
    repository.updateAccountVote(address, endCycle, accountCapsule);
  }
