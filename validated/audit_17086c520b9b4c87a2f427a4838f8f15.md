### Title
Dust-transfer griefing fills `depositTokensOfAccount` up to `MAX_TOKENS_PER_USER`, permanently blocking collateral deposits and enabling forced liquidations - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
Analogous to a memory leak (attacker-driven, unbounded resource consumption that is never released on the victim's side), an attacker can permanently grow a victim's per-account token list `depositTokensOfAccount` by dust-transferring each `DepositToken` to them. Once the combined debt+deposit token count reaches `MAX_TOKENS_PER_USER = 30`, every `_mint`/`_transfer`/`deposit` of any token the victim does not already hold reverts in `addToDepositTokensOfAccount`, so the victim cannot add new collateral types — freezing their ability to restore health and exposing them to liquidation.

### Finding Description
`DepositToken._transfer` and `_mint` add the token to the recipient's list whenever the recipient's balance goes from `0` to non-zero, with no minimum amount and no opt-in from the recipient:

- `DepositToken.sol` lines 517–520: `if (_recipientBalanceBefore == 0 && amount_ > 0) { pool.addToDepositTokensOfAccount(recipient_); }`
- `DepositToken.sol` line 348–353: `transfer` calls `_transfer` with only a `_revertIfLocked` check on the *sender* — the recipient has no say.

On the `Pool` side, `addToDepositTokensOfAccount` is gated by `onlyIfAdditionWillNotReachMaxTokens`:

- `Pool.sol` lines 143–148: reverts with `UserReachedMaxTokens` once `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30`.
- `Pool.sol` lines 216–220: the revert propagates, so the entire `transfer`/`deposit`/`seize` transaction fails.

Because a `DepositToken` is only removed from the victim's list when their balance hits exactly zero (`Pool.sol` 630–634, `DepositToken.sol` 522–525), each dust "allocation" is only freed by the victim actively withdrawing/transferring the dust — mirroring the memory-leak pattern of resources consumed but never automatically released.

Attack path:
1. Attacker deposits a dust amount into each of the pool's `DepositToken`s (cost ≈ dust per token, up to `MAX_TOKENS_PER_USER` tokens since `addDepositToken` also caps `depositTokens` at 30).
2. Attacker calls `transfer(victim, 1)` on each `DepositToken`. Each transfer adds that token to `depositTokensOfAccount[victim]`.
3. Once `victim`'s list reaches 30 entries, any `deposit(onBehalfOf_ = victim)`, `transfer(victim, ...)` of a not-yet-held token, or `seize(..., to_ = victim, ...)` reverts.

### Impact Explanation
- **Temporary/permanent freezing of funds flows**: The victim cannot receive or deposit any new collateral token. If the victim holds debt in one of the not-yet-held tokens, they also cannot acquire it via `Pool.swap` + repay paths that would require receiving a new `DepositToken`.
- **Forced liquidation → direct loss**: A victim with an unhealthy position who does not already hold a needed collateral token cannot top up to restore health (`deposit` reverts). They become stuck and are liquidated, paying liquidator incentive + protocol fee — a direct monetary loss induced by the attacker.
- **Liquidation blocking**: `liquidate` calls `depositToken_.seize(account_, msgSender, ...)` which internally hits `addToDepositTokensOfAccount(liquidator)` — griefing specific liquidator EOAs is possible too, though liquidators can rotate addresses, so the primary impact is on the victim.

### Likelihood Explanation
Requires only the attacker to spend dust amounts of each underlying collateral; no privileged role, no oracle manipulation, no governance action. The attack is fully reachable through the public `DepositToken.transfer` entry point. Constraints: the pool must have several deposit tokens registered (cap is 30, `Pool.sol` 703), and meaningful impact requires the victim to have an open debt position — but the griefing is cheap and can be done preemptively on any account.

### Recommendation
- Let recipients opt out: only add to `depositTokensOfAccount` on `deposit`/`_mint`, not on plain `_transfer`/`seize`; or
- Remove `MAX_TOKENS_PER_USER` accounting for dust (e.g., require a minimum `amount_` or a minimum USD value before adding to the per-account list); or
- Make `addToDepositTokensOfAccount` non-reverting when the cap is reached and account for the token lazily in `depositOf`/`debtPositionOf`.

### Proof of Concept
Foundry/Hardhat fork sketch:

```solidity
// Pool has >= 2 registered DepositTokens: dA (e.g., msETH-WETH deposit token), dB
// victim holds position in dA and has debt.
address attacker = makeAddr("attacker");
address victim   = makeAddr("victim");

// setup: victim deposits collateral in dA and issues debt
vm.startPrank(victim);
underlyingA.approve(address(dA), DEPOSIT);
dA.deposit(DEPOSIT, victim);
dA_debtToken.mint(...); // via issue/synthetic mint
vm.stopPrank();

// attacker fills victim's list: deposit dust into dB..dZ and transfer 1 wei each
vm.startPrank(attacker);
for (uint i; i < depositTokens.length; ++i) {
    IDepositToken dt = IDepositToken(depositTokens[i]);
    dt.underlying().approve(address(dt), 10);
    dt.deposit(10, attacker);          // mint dust to attacker
    dt.transfer(victim, 1);            // pushes dt into depositTokensOfAccount[victim]
}
vm.stopPrank();

assertEq(pool.getDepositTokensOfAccount(victim).length + debtCount, 30);

// victim can no longer deposit a collateral type it doesn't already hold
vm.startPrank(victim);
underlyingNew.approve(address(dNew), 1000);
vm.expectRevert(UserReachedMaxTokens.selector);
dNew.deposit(1000, victim);

// anyone trying to transfer a not-yet-held deposit token to victim also reverts
vm.expectRevert(UserReachedMaxTokens.selector);
dA.transfer(victim, 1); // if dA were not already in victim's list
vm.stopPrank();
```

The revert originates in `Pool.sol` line 144 (`onlyIfAdditionWillNotReachMaxTokens`) reached from `DepositToken._transfer`/`_mint` (`DepositToken.sol` 487, 519), confirming the victim's token-list resource is leaked by unsolicited dust and never freed without victim action.
