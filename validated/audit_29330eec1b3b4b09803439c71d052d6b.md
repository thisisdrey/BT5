### Title
Unprivileged attacker can indefinitely starve the delayed-receipt queue via local storage-proof exhaustion, freezing a victim's pending receipt - (File: `runtime/runtime/src/lib.rs`, `runtime/runtime/src/congestion_control.rs`)

### Summary
The chunk receipt-processing order is fixed as local → delayed → incoming, and both phases share a single proof-size budget (`main_storage_proof_size_soft_limit`) tracked on the same `TrieRecorder` for the whole chunk. An attacker who submits their own cheap local `FunctionCall` receipts that read enough large trie values can drive `check_proof_size_limit_exceed()` to true before `process_delayed_receipts` runs, causing `DelayedReceiptQueueWrapper::pop` to break immediately every chunk and leave any victim's already-queued delayed receipt un-popped.

### Finding Description
`Runtime::process_receipts` (`runtime/runtime/src/lib.rs:2681-2736`) processes local receipts first, then delayed, then incoming, all sharing the same `processing_state.state_update.trie` and therefore the same `TrieRecorder` created fresh per chunk in `apply_chunk` (`chain/chain/src/runtime/mod.rs:1268-1269`).

In `process_local_receipts` (`runtime/runtime/src/lib.rs:2380-2455`), each local receipt is checked against `compute_limit` and `check_proof_size_limit_exceed()` (`:2408-2410`) *before* being executed; receipts that fit are executed and their trie reads accumulate into `upper_bound_size` via `TrieRecorder::record`/`record_with` (`core/store/src/trie/trie_recording.rs:109-131`, `161-163`). Only once the limit is exceeded do subsequent local receipts get deferred to the delayed queue.

`process_delayed_receipts` (`runtime/runtime/src/lib.rs:2464-2545`) then loops, but its very first check is `processing_state.state_update.trie.check_proof_size_limit_exceed()` (`:2487`), and `DelayedReceiptQueueWrapper::pop` (`runtime/runtime/src/congestion_control.rs:880-910`) repeats the same pre-check at `:889` before popping. If the local phase already pushed `upper_bound_size` above `main_storage_proof_size_soft_limit`, both checks immediately break, and **zero** delayed receipts are popped that chunk — including any victim's pending refund/transfer sitting at the front of the FIFO queue.

Because a fresh `TrieRecorder` (and thus a reset `upper_bound_size`) is created every chunk (`chain/chain/src/runtime/mod.rs:1269`), the attacker can repeat this every single chunk: submit local `FunctionCall` transactions from their own account (`signer_id == receiver_id`, so they land in `local_receipts`, not incoming/buffered) that read large trie values, sized so the cumulative recorded proof reaches the soft limit before the local loop finishes. This requires no bypass of any signature/nonce/access-key/gas check — it is ordinary transaction submission with attached gas to fund reads (as validated by `test_storage_proof_size_limit`/`test_main_storage_proof_size_soft_limit` in `integration-tests/src/tests/features/storage_proof_size_limit.rs`, which already demonstrates the soft-limit deferral mechanic, just not the indefinite-starvation angle).

No existing mechanism gives the delayed queue priority or a reserved share of the per-chunk proof budget; the ordering local→delayed→incoming is fixed and unconditional, and the deferral logic in `process_local_receipts` only pushes *excess* local receipts to the delayed queue — it does not yield any of the budget already consumed back to the delayed queue.

### Impact Explanation
This is a liveness/DoS finding, not a fund-theft or supply-inflation bug: it can indefinitely delay (freeze) processing of a victim's delayed receipt (e.g., a pending refund or cross-contract transfer) for as long as the attacker keeps repeating the local-receipt flood every chunk on the shard holding the victim's queue entry. Funds are not stolen or destroyed, but they become inaccessible/unresolved to the victim while the attack is sustained — a scoped "freezing of user funds" liveness violation as long as the attack is maintained, rather than a permanent one, since it requires continuous attacker funding and stops the moment the attacker stops or runs out of gas budget/NEAR.

### Likelihood Explanation
- Preconditions: attacker needs an account with balance to cover gas/fees each chunk, a deployed contract with a method that reads N distinct/large state values (patterned exactly like `read_n_megabytes` in the existing test contract), and a victim receipt already resident in the shard's delayed queue.
- Cost: non-trivial but bounded — the attacker pays gas for storage reads every chunk (real NEAR cost scales with the configured storage-read gas costs), so this is a sustained-cost griefing attack rather than a free/zero-cost one.
- Repeatability: fully repeatable every chunk since the recorder resets each chunk and the local phase always runs before the delayed phase, with no anti-starvation fairness mechanism between the two queues.
- Feasibility is directly supported by the existing test infrastructure (`test_storage_proof_size_limit`) demonstrating that a small number of ~3MB reads can already hit `main_storage_proof_size_soft_limit`, i.e., the budget is attacker-reachable with a modest number of transactions per chunk.

### Recommendation
Introduce fairness between local and delayed receipt processing sharing the per-chunk proof-size (and/or compute) budget — e.g., reserve a minimum share of `main_storage_proof_size_soft_limit` for delayed-queue draining before local receipts are allowed to consume the remainder, or interleave local/delayed processing instead of a strict local-then-delayed ordering, so that a burst of self-submitted local receipts cannot categorically prevent any delayed-receipt progress in a chunk.

    fn process_receipts(
        &self,
        processing_state: &mut ApplyProcessingReceiptState,
        receipt_sink: &mut ReceiptSink,
    ) -> Result<ProcessReceiptsResult, RuntimeError> {
        let mut validator_proposals = vec![];
        let apply_state = &processing_state.apply_state;

        // TODO(#8859): Introduce a dedicated `compute_limit` for the chunk.
        // For now compute limit always matches the gas limit.
        let compute_limit = apply_state.gas_limit.map(|g| g.as_gas()).unwrap_or(u64::MAX);

        // We first process local receipts. They contain staking, local contract calls, etc.
        self.process_local_receipts(
            processing_state,
            receipt_sink,
            compute_limit,
            &mut validator_proposals,
        )?;

        // Then we process the delayed receipts. It's a backlog of receipts from the past blocks.
        self.process_delayed_receipts(
            processing_state,
            receipt_sink,
            compute_limit,
            &mut validator_proposals,
        )?;

    pub(crate) fn pop(
        &mut self,
        trie_update: &mut TrieUpdate,
        config: &RuntimeConfig,
    ) -> Result<Option<ReceiptOrStateStoredReceipt<'_>>, RuntimeError> {
        // While processing receipts, we need to keep track of the gas and bytes
        // even for receipts that may be filtered out due to a resharding event
        loop {
            // Check proof size limit before each receipt is popped.
            if trie_update.trie.check_proof_size_limit_exceed() {
                break;
            }
            let Some(receipt) = self.queue.pop_front(trie_update)? else {
                break;
            };
            let delayed_gas = receipt_congestion_gas(&receipt, &config)?;
            let delayed_bytes = receipt_size(&receipt)? as u64;
            self.removed_delayed_gas =
                self.removed_delayed_gas.checked_add(delayed_gas).ok_or(IntegerOverflowError)?;
            self.removed_delayed_bytes = self
                .removed_delayed_bytes
                .checked_add(delayed_bytes)
                .ok_or(IntegerOverflowError)?;

            // Track gas and bytes for receipt above and return only receipt that belong to the shard.
            if self.receipt_filter_fn(&receipt) {
                return Ok(Some(receipt));
            }
        }
        Ok(None)
    }

    /// Just like "record", but takes a function which returns the serialized node.
    /// Allows to avoid re-serializing the node when it has already been recorded.
    pub fn record_with(&self, hash: &CryptoHash, get_serialized_node: impl FnOnce() -> Arc<[u8]>) {
        let mut size_from_first_insert: Option<usize> = None;
        self.recorded
            .entry(*hash)
            .or_insert_with(|| {
                let serialized = get_serialized_node();
                size_from_first_insert = Some(serialized.len());
                serialized.into()
            })
            .increment();

        // Only do size accounting if this is the first time we see this value.
        if let Some(size) = size_from_first_insert {
            self.upper_bound_size.fetch_add(size, Ordering::Release).checked_add(size).unwrap();
            self.size.fetch_add(size, Ordering::Release);
        }
    }

    /// Convenience function to record memtrie nodes
    pub fn record_memtrie_node<M: ArenaMemory>(&self, node_view: &MemTrieNodeView<'_, M>) {
        self.record_with(&node_view.node_hash(), || {
            borsh::to_vec(&node_view.to_raw_trie_node_with_size()).unwrap().into()
        });
    }

    pub fn record_key_removal(&self) {
        // Charge 2000 bytes for every removal
        self.upper_bound_size.fetch_add(2000, Ordering::Release).checked_add(2000).unwrap();
        // No need to check for overflows here as the `upper_bound_size` would overflow sooner than
        // this if there was an overflow.
        self.removal_counter.fetch_add(1, Ordering::Relaxed);
    }

    pub fn record_code_len(&self, code_len: usize) {
        // NB: this isn't necessarily super well-formed as it is possible for reads of
        // `code_len_counter` to observe and act on overflow-wrapped `code_len` before this
        // `checked_add` gets an opportunity to notice the overflow and panic.
        //
        // We hope that this is is small enough window to make it a non-concern, esp. given that
        // this overflow shouldn't be occurring in any practical situation anyway.
        self.upper_bound_size.fetch_add(code_len, Ordering::Release).checked_add(code_len).unwrap();
        // No need to check for overflows here as the `upper_bound_size` would overflow sooner than
        // this.
        self.code_len_counter.fetch_add(code_len, Ordering::Relaxed);
    }
