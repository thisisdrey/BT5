### Title
Unbounded `sock.read_to_end` in `run_http_request` allows a malicious StackerDB node to exhaust signer memory - (File: libsigner/src/http.rs)

### Summary
`run_http_request` reads an entire HTTP response into memory with `sock.read_to_end(&mut buf)` before any header/`Content-Length`/`MAX_MESSAGE_LEN` check is applied, and `decode_http_body`'s non-chunked branch (`buf.to_vec()`) performs no size cap either. A node that a `StackerDBSession` client connects to can therefore stream an unbounded body with no `Content-Length` and no `Transfer-Encoding: chunked` marker, forcing the signer process to allocate memory without bound on a single connection.

### Finding Description
`run_http_request` in `libsigner/src/http.rs` writes the request, then does: [1](#0-0) 
`sock.read_to_end(&mut buf)` loops calling `read()` until EOF, appending every byte to `buf` with **no upper bound at all** — this happens before `decode_http_response`/`decode_http_body` ever run, so `MAX_MESSAGE_LEN` is irrelevant to this call site. Only after all bytes are already buffered does `decode_http_body` run, and its non-chunked branch is simply: [2](#0-1) 
i.e. it just copies whatever was already read — no cap is applied here either. Only the chunked branch enforces `MAX_MESSAGE_LEN` via `HttpChunkedTransferReader`: [3](#0-2) 

The only mitigating factor is `socket_timeout` set via `set_read_timeout` in `StackerDBSession::connect_or_reconnect`: [4](#0-3) 
but this only bounds the time between individual `read()` calls, not the total bytes received. As long as the malicious node keeps sending data at any rate faster than the timeout, `read_to_end` keeps growing `buf` indefinitely without closing the connection, and there is no per-response size limit anywhere in this path (`decode_http_response`/`decode_http_body` execute only after the full body has already been buffered).

`StackerDBSession::rpc_request` is the caller used by `list_chunks`, `get_chunks`, `get_latest_chunks`, and `put_chunk` — all of which reach `run_http_request`: [5](#0-4) 

### Impact Explanation
A single malicious/compromised Stacks node that a signer is configured to query via `StackerDBSession` can respond to any GET/POST (e.g. `GET /v2/stackerdb/.../chunks`) with a valid status line/headers and then stream gigabytes of body data with no `Content-Length` and no chunked marker. The signer process will attempt to buffer the entire stream in `Vec<u8>` on a single connection, leading to unbounded memory growth and process OOM/crash — a Critical, unauthenticated, single-connection memory-exhaustion DoS against the signer's session client, repeatable on every request the signer issues to that node.

### Likelihood Explanation
No privileged access, secret, or signature is required — the attacker only needs to be the endpoint the signer's `StackerDBSession` connects to (or otherwise able to respond on that TCP connection) and to withhold `Content-Length`/`chunked` while streaming data. `read_to_end` has no size guard, and the only defense (`socket_timeout`) only limits idle-time-per-read, not total bytes, so the attacker can trivially defeat it by trickling data. The attack is trivially repeatable on every RPC call the signer makes to the malicious node.

### Recommendation
Bound the total number of bytes read in `run_http_request` (e.g., use a `Read::take(MAX_MESSAGE_LEN)` adaptor or a manual loop that reads incrementally into `buf` and aborts once `buf.len()` exceeds `MAX_MESSAGE_LEN`, regardless of `Content-Length`/chunked framing), and additionally validate any declared `Content-Length` header against `MAX_MESSAGE_LEN` before reading the body, applying the same cap uniformly to both chunked and non-chunked responses in `decode_http_body`.

### Proof of Concept
```rust
// libsigner/src/session.rs or http.rs test module
#[test]
fn unbounded_read_to_end_dos() {
    use std::io::Write;
    use std::net::TcpListener;
    use std::thread;

    let listener = TcpListener::bind("127.0.0.1:0").unwrap();
    let addr = listener.local_addr().unwrap();

    thread::spawn(move || {
        if let Ok((mut stream, _)) = listener.accept() {
            // consume request, then send headers with NO Content-Length,
            // NO Transfer-Encoding: chunked, and stream forever
            let _ = stream.write_all(b"HTTP/1.1 200 OK\r\n\r\n");
            let chunk = vec![0u8; 1 << 20]; // 1MB
            loop {
                if stream.write_all(&chunk).is_err() {
                    break;
                }
            }
        }
    });

    let contract_id = clarity::vm::types::QualifiedContractIdentifier::transient();
    let mut session = StackerDBSession::new(
        &addr.to_string(),
        contract_id,
        std::time::Duration::from_secs(5),
    );
    session.connect_or_reconnect().unwrap();

    // Expectation: this call should either error or cap the body size.
    // Actual: run_http_request's `sock.read_to_end(&mut buf)` grows `buf`
    // without bound until the process runs out of memory or the test is killed.
    let _ = session.rpc_request("GET", "/", None, &[]);
}
```
Assertion/crash site: `sock.read_to_end(&mut buf)` in `run_http_request` at `libsigner/src/http.rs:251` — `buf` grows without any cap because no `MAX_MESSAGE_LEN` check exists before or during this read, and the subsequent `decode_http_body` non-chunked branch (`buf.to_vec()` at line 213) performs no cap either.
