Audit Report

## Title
Reward payout on delivery receipt ignores dispatch `success` flag, causing incorrect settlement regardless of actual message execution outcome - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
`Pallet::process_delivery_receipt` in the Snowbridge outbound-queue-v2 pallet pays the relayer reward and removes the `PendingOrder` for a nonce based solely on `order.fee > 0`, without ever checking `receipt.success`, which is decoded from the real Ethereum `InboundMessageDispatched(nonce, topic, success, reward_address)` event log. This allows a relayer to be rewarded, and the order irreversibly settled, even when the destination-side dispatch actually failed (`success == false`).

## Finding Description
The `DeliveryReceipt` struct explicitly carries a `success: bool` field populated directly from the verified Ethereum event log during decoding via `TryFrom<&Log>`: [1](#0-0) [2](#0-1) 

`submit_delivery_receipt` is a public, unprivileged, signed extrinsic that verifies the proof via `T::Verifier::verify`, decodes the `DeliveryReceipt`, and passes it straight to `process_delivery_receipt`: [3](#0-2) 

Inside `process_delivery_receipt`, the code checks `receipt.gateway`, resolves `reward_account` from `receipt.reward_address`, looks up `PendingOrders` by `receipt.nonce`, and — if `order.fee > 0` — unconditionally calls `T::RewardPayment::register_reward`, then removes the order and emits `MessageDelivered`, all without any branch on `receipt.success`: [4](#0-3) 

A repository-wide search for `.success` usage within the `outbound-queue-v2` pallet confirms it is decoded but never consumed anywhere else in that crate, so there is no alternate code path that gates the reward or order settlement on the actual dispatch outcome. The module documentation itself describes the intended flow as "When the message has been verified **and executed**... pay reward with fee attached in the order," but the implementation does not check for successful execution, only for successful proof verification of *some* dispatch outcome: [5](#0-4) 

## Impact Explanation
This falls under the "duplicate settlement or payout" / "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically" impact gate. The `PendingOrder` for a nonce is removed and the fee reward is paid out to `reward_account` regardless of whether the corresponding message dispatch on Ethereum succeeded or reverted, meaning the settlement state advances on proof-of-dispatch-attempt rather than proof-of-successful-execution as intended by design.

## Likelihood Explanation
Likelihood is bounded by the requirement that `receipt.success = false` still needs a genuine, Beefy/Merkle-proof-verified `InboundMessageDispatched` event from the real Gateway contract — an attacker cannot forge this. However, no malicious behavior is required at all: any ordinary relayer who relays a message whose destination-side dispatch legitimately fails (e.g., insufficient gas budget, a reverting command) and then calls the unprivileged `submit_delivery_receipt` extrinsic will trigger the full reward payout and order removal, since the check is entirely absent rather than merely bypassable under adversarial conditions.

## Recommendation
In `process_delivery_receipt`, branch on `receipt.success`: only call `T::RewardPayment::register_reward` when `receipt.success == true`; when `false`, still remove/settle the `PendingOrder` to avoid a permanent lock of that nonce slot, but skip the reward payment (or route to a distinct refund/failure-handling flow) and emit a distinguishing event (e.g., `MessageDispatchFailed`) instead of unconditionally emitting `MessageDelivered`.

## Proof of Concept
1. A message is queued via `do_process_message`, creating `PendingOrders[nonce]` with `fee > 0`.
2. The message is relayed to Ethereum but the destination command reverts/fails during execution, causing the Gateway contract to emit `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer calls `submit_delivery_receipt` with a valid Merkle/Beefy proof of this real event log.
4. `T::Verifier::verify` succeeds (the log is authentic) and `DeliveryReceipt::try_from` correctly decodes `success = false`.
5. `process_delivery_receipt` ignores `receipt.success`, sees `order.fee > 0`, calls `T::RewardPayment::register_reward` to pay the relayer, removes the `PendingOrder`, and emits `MessageDelivered` — identical behavior to a genuinely successful dispatch.

		pub fn process_delivery_receipt(

			receipt: DeliveryReceipt,

		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,

			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
