### Title
NullPointerException in `TransactionTrace.checkIsConstant()` from unchecked `TriggerSmartContract` unpack failure - (File: `chainbase/src/main/java/org/tron/core/db/TransactionTrace.java`)

### Summary
`TransactionTrace.checkIsConstant()` calls `ContractCapsule.getTriggerContractFromTransaction(...)`, which can return `null` when the transaction's contract parameter fails to unpack as `TriggerSmartContract`, but the caller dereferences the result immediately without a null check, mirroring the `adev == NULL` dereference pattern fixed upstream in the Linux `int3472` driver.

### Finding Description
`ContractCapsule.getTriggerContractFromTransaction` unpacks the `Any` parameter of the first contract in a transaction as a `TriggerSmartContract`. If unpacking throws `InvalidProtocolBufferException`, the method silently returns `null`: [1](#0-0) 

`TransactionTrace.checkIsConstant()` calls this helper and, when the transaction type is `TRX_CONTRACT_CALL_TYPE`, immediately calls `.getContractAddress()` on the result without checking for `null`: [2](#0-1) 

The `trxType` field is determined purely from the `ContractType` enum tag on the raw transaction contract (`Transaction.Contract.ContractType.TriggerSmartContract_VALUE`), which is independent of whether the embedded `Any` payload actually parses as a valid `TriggerSmartContract` message: [3](#0-2) 

Because the contract-type tag and the `Any` payload bytes are set independently by the transaction sender, an attacker can craft a transaction whose contract type is `TriggerSmartContract` but whose `parameter` bytes do not deserialize into a valid `TriggerSmartContract` protobuf message. `getTriggerContractFromTransaction` then returns `null`, and `checkIsConstant()` dereferences it, throwing an unguarded `NullPointerException`, exactly the class of bug the CVE-2024-58011 fix addresses (missing null check on an optional/failed-lookup object before dereference).

### Impact Explanation
`checkIsConstant()` is invoked from `Manager` during the transaction validate/apply path for smart-contract-call transactions (confirmed by two call sites in `framework/src/main/java/org/tron/core/db/Manager.java`), which is on the path every broadcast transaction with a `TriggerSmartContract` type goes through. An unguarded NPE thrown from deep inside block/transaction processing can propagate as an unexpected `RuntimeException` instead of the expected `ContractValidateException`/`VMIllegalException`, which is not handled the same way by callers, risking inconsistent transaction rejection behavior or, depending on where in the pipeline it surfaces (e.g., during block application), a node processing fault. This is reachable by any unprivileged party who can broadcast a crafted transaction, satisfying the "node crash/halt" impact bar.

### Likelihood Explanation
Exploitation only requires constructing a transaction whose `Transaction.Contract.type` is set to `TriggerSmartContract` while the `parameter` `Any` bytes are invalid/mismatched — something fully controllable by any transaction broadcaster without needing special permissions, signatures beyond a normal valid transaction signature, or any privileged role.

### Recommendation
Add a null check on the result of `ContractCapsule.getTriggerContractFromTransaction(...)` in `TransactionTrace.checkIsConstant()` before calling `.getContractAddress()`, throwing a `ContractValidateException` (consistent with the rest of the validation logic) instead of allowing an NPE to propagate, analogous to the upstream kernel fix that added an `adev == NULL` check before dereferencing in `skl_int3472_get_acpi_buffer()`.

### Proof of Concept
1. Construct a `Transaction` whose `raw_data.contract[0].type` is set to `TriggerSmartContract` but whose `parameter` field contains bytes that are valid protobuf for some other/garbage structure (so `Any.unpack(TriggerSmartContract.class)` throws `InvalidProtocolBufferException`).
2. Broadcast the transaction to a node.
3. During processing, `TransactionTrace` is constructed with `trxType = TRX_CONTRACT_CALL_TYPE` (based on the `type` tag alone).
4. When `checkIsConstant()` runs (invoked from `Manager`'s transaction processing), `ContractCapsule.getTriggerContractFromTransaction` returns `null`, and the subsequent `triggerContractFromTransaction.getContractAddress()` call throws `NullPointerException`, an unhandled exception type in this code path.

  public static TriggerSmartContract getTriggerContractFromTransaction(Transaction trx) {
    try {
      Any any = trx.getRawData().getContract(0).getParameter();
      TriggerSmartContract contractTriggerContract = any.unpack(TriggerSmartContract.class);
      return contractTriggerContract;
    } catch (InvalidProtocolBufferException e) {
      return null;
    }
  }
