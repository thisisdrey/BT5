## Analysis Result

### Title
Unbounded array-length field from ABI-encoded precompile input used to allocate/copy buffers without bounds validation — Heap/OOM DoS analog of CVE-2016-10192 - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ffserver` bug in the CVE report is a classic "trust an attacker-supplied length field, then allocate/copy without checking it" bug. java-tron's TVM precompiled-contract input decoders (`extractSigArray`, `extractBytesArray`, `extractBytes32Array` in `PrecompiledContracts.java`) contain the same pattern: they read a 32-byte "array length" word straight out of the calldata and use it to size a Java array, without validating it against the actual size of the `words`/`data` buffers being indexed.

### Finding Description
`extractSigArray`, `extractBytesArray`, and `extractBytes32Array` decode ABI-encoded dynamic arrays from precompile call data: [1](#0-0) 

`len` is taken directly from `words[offset].intValueSafe()` — fully attacker controlled via the calldata passed to the `BatchValidateSign` precompile (address `0x66...` reachable from any TVM `CALL`/`STATICCALL`). There is no upper bound check on `len` before `new byte[len][]` is allocated, and the subsequent loop indexes `words[offset + i + 1]` with no check that `offset + i + 1 < words.length`. The same unchecked pattern exists in the sibling helpers: [2](#0-1) 

The only bounds guard present, `isValidAbiEncoding`, only checks that the total `data.length` is a multiple of 32 and internally consistent with a `headerWords`/`itemWords` formula — it never validates that the length word read out of the data is itself sane relative to `words.length`: [3](#0-2) 

Because `intValueSafe()` can return values up to `Integer.MAX_VALUE`, `new byte[len][]` can trigger a multi-gigabyte allocation attempt, throwing `OutOfMemoryError`/`NegativeArraySizeException`. `OutOfMemoryError` is a `java.lang.Error`, not an `Exception`; TVM's per-opcode/precompile exception handling in `Program`/actuators is written around `Exception`/`Throwable` catches at various layers, so depending on where the error surfaces it can escape the intended VM sandboxing and take down the node process executing the block, unlike a normal reverted transaction.

### Impact Explanation
An attacker can craft a contract call to the `BatchValidateSign` precompile with a malicious length word to force allocation of an oversized array or an out-of-bounds `ArrayIndexOutOfBoundsException`/`OutOfMemoryError` during block/transaction execution. If this propagates as an uncaught `Error` rather than a normal VM revert, it can crash the executing node (denial of service), and because block execution must be deterministic across all full nodes/SRs, a crash during block validation could also cause a chain halt for nodes processing that block.

### Likelihood Explanation
This is reachable by any unprivileged account: constructing and sending a transaction that calls the `BatchValidateSign` precompiled contract (address `0x66...`, exposed to any contract deployer) with crafted calldata is a low-effort, permissionless attack requiring only a signed transaction and no special privileges.

### Recommendation
Add explicit bounds checks in `extractSigArray`, `extractBytesArray`, and `extractBytes32Array` before allocating: verify `len >= 0` and `offset + len + 1 <= words.length` (and that computed byte offsets stay within `data.length`) before performing any allocation or array indexing; reject with a normal VM revert (not an uncaught `Error`) if the encoded length is inconsistent with the actual data size.

### Proof of Concept
Because this requires crafting raw ABI-encoded calldata to `BatchValidateSign` with a length word (e.g., `0xFFFFFFFF`) at the array-length slot and observing the resulting `OutOfMemoryError`/`ArrayIndexOutOfBoundsException` during `PrecompiledContracts.BatchValidateSign.execute()`, a full runtime reproduction requires executing the TVM against a live/test node — I could not execute code in this environment to confirm whether the resulting `Error` is actually caught and converted into a normal revert somewhere higher in the call stack (e.g., in `Program` or the actuator invoking precompiles) versus propagating uncaught. This should be verified with a live Devin session that can run the TVM test suite (e.g., extending `BatchValidateSignContractTest`) to confirm the crash/DoS is not otherwise mitigated.
