However, this finding is explicitly out of scope per the audit rules and does not meet the required threat model.### Title
Unauthenticated remote injection of `SignerEvent::BlockValidationResponse` (and other signer events) via `SignerEventReceiver` HTTP listener - (File: libsigner/src/events.rs)

### Summary
`SignerEventReceiver::next_event` in `libsigner/src/events.rs` dispatches any POST to `/stackerdb_chunks`, `/proposal_response`, `/new_burn_block`, `/new_block` straight into `process_event::<T, E>` with no authentication, shared secret, or peer-address check of any kind. Anyone who can open a TCP connection to the signer's configured `endpoint` can forge a `BlockValidateResponse` JSON body and have it delivered to the signer runloop as `SignerEvent::BlockValidationResponse`, indistinguishable from a response produced by the locally configured node's validation engine.

### Finding Description
The broken equality is: *what the signer runloop treats as "my node's validation result" == whatever bytes the TCP client POSTed to `/proposal_response`*.

`SignerEventReceiver::bind` at [1](#0-0)  simply opens a `tiny_http::HttpServer` on the configured socket with no allow-list, TLS client-cert check, or shared-secret middleware. `next_event` at [2](#0-1)  reads any request and, for `/proposal_response`, calls `process_event::<T, BlockValidateResponse>(request)`. `process_event` at [3](#0-2)  only reads the raw body, `serde_json::from_slice`-decodes it into `BlockValidateResponse`, and calls `.try_into()`, which for `BlockValidateResponse` is a bare pass-through into `SignerEvent::BlockValidationResponse` with no additional validation, at [4](#0-3) . The event is then forwarded verbatim to the runloop via `forward_event` at [5](#0-4) , with no way for the runloop to tell it apart from a genuine node-originated response.

Unlike the node's own RPC/event-dispatcher push path, which is gated by `auth_token`/`auth_password` matching between the node's `[connection_options]` and the signer's `auth_password` (documented in `docs/signing.md` and the sample configs), that shared secret is only used for the signer's *outbound* calls to the node's block-proposal RPC endpoint — it is never checked on the *inbound* HTTP listener that the signer itself binds to receive event-dispatcher pushes. There is no equivalent secret/header check anywhere in `libsigner/src/events.rs`.

### Impact Explanation
An attacker who can reach the signer's bound `endpoint` (default sample configs bind it to `0.0.0.0:30000`, see `sample/conf/signer/mainnet-signer-conf.toml`) can inject a forged `BlockValidateResponse` (Valid/Invalid/Rejected) that the signer runloop consumes as if it came from its paired node's validation engine. Depending on how the runloop's decision logic consumes `SignerEvent::BlockValidationResponse`, this could cause the signer to sign, reject, or stall on a block proposal based on attacker-controlled input rather than actual local chainstate validation — i.e., unauthenticated write into the signer's internal validation-response channel. This is repeatable per message and requires no special access beyond network reachability to the port.

### Likelihood Explanation
Preconditions: the signer's `endpoint` (event-receiver bind address) must be reachable from the attacker's network position. Per the sample/reference configs (`sample/conf/signer/mainnet-signer-conf.toml`, line `endpoint = "0.0.0.0:30000"`), and the explicit runtime warning logged in `stacks-signer/src/lib.rs` ("Reminder: The signer is primarily designed for use with a local or subnet network stacks node... exercise caution if you are communicating with an external node..."), this is a known, documented operational risk rather than a code defect distinct from design — operators are expected to firewall this port themselves; the code provides no in-band authentication as a defense-in-depth measure. Attacker cost is trivial (a single crafted HTTP POST), and the action is fully repeatable.

### Recommendation
Add an authentication gate to `SignerEventReceiver`/`process_event` (e.g., require the same shared secret/`auth_password` header used elsewhere, or an HMAC over the body) and verify it before deserializing/forwarding any event, for all four POST endpoints (`/stackerdb_chunks`, `/proposal_response`, `/new_burn_block`, `/new_block`). Additionally consider binding the receiver to loopback by default and requiring explicit opt-in plus authentication for non-loopback binds.

```rust
                return false;

                    return false;
                }
            }
            true
        }
```

```rust
fn process_event<T, E>(mut request: HttpRequest) -> Result<SignerEvent<T>, EventError>
where
    T: SignerEventTrait,
    E: serde::de::DeserializeOwned + TryInto<SignerEvent<T>, Error = EventError>,
{
    let mut body = String::new();

    if let Err(e) = request.as_reader().read_to_string(&mut body) {
        error!("Failed to read body: {:?}", &e);
        ack_dispatcher(request);
        return Err(EventError::MalformedRequest(format!(
            "Failed to read body: {:?}",
            e
        )));
    }
    // Regardless of whether we successfully deserialize, we should ack the dispatcher so they don't keep resending it
    ack_dispatcher(request);
    let json_event: E = serde_json::from_slice(body.as_bytes())
        .map_err(|e| EventError::Deserialize(format!("Could not decode body to JSON: {:?}", e)))?;

    let signer_event: SignerEvent<T> = json_event.try_into()?;

    Ok(signer_event)
}
```
