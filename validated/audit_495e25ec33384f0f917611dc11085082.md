### Title
Attachment content is stored and served under a content hash without verifying `Hash160::from_data(&content) == requested content_hash` - ([File: stackslib/src/net/atlas/download.rs])

### Summary
In `AttachmentsDownloader::run`'s handling of `AttachmentsBatchStateMachine::Done`, attachments received from a peer's HTTP response are inserted into `AtlasDB` via `insert_instantiated_attachment` and matched against `find_all_attachment_instances`/`resolve_attachment` using `attachment.hash()` — the hash computed from the *received bytes* — rather than being checked against the `content_hash` that was originally requested in the corresponding `AttachmentRequest`. This allows a malicious peer serving `GET /v2/attachments/{content_hash}` to substitute different bytes and have them accepted as if they matched the requested hash's binding, as long as the swap only needs to fool code that indexes purely on `attachment.hash()` computed from the returned bytes.

### Finding Description
The `Done` branch of `AttachmentsDownloader::run` iterates `context.attachments.drain()` (populated in `AttachmentsBatchStateContext::extend_with_attachments` from `response.decode_atlas_get_attachment()`), and for each attachment does: [1](#0-0) 
It looks up `find_all_attachment_instances(&attachment.hash())`, calls `insert_instantiated_attachment(&attachment)`, and resolves the batch's `content_hash` entry via `attachment.hash()` — but never separately validates `attachment.hash()` against the `AttachmentRequest.content_hash` that was actually sent in the URL to the peer (`/v2/attachments/{content_hash}`, built via `Requestable::make_request_type` on `AttachmentRequest`, `content_hash` field defined at [2](#0-1) ). Because the downstream lookups (`find_all_attachment_instances`, `resolve_attachment`, and DB storage) are all keyed by `attachment.hash()` derived from the response body itself, an attacker peer that responds with different attachment bytes still gets those bytes indexed consistently by their own (different) hash — so the direct proof-of-concept described (returning content whose hash differs from the requested hash) would simply cause `attachment.hash()` to not match the outstanding attachment instance's `content_hash`, meaning `find_all_attachment_instances(&attachment.hash())` would return no matching instances (since instances are keyed by the on-chain-committed `content_hash`, not by whatever hash the returned bytes produce). In that case the forged attachment gets stored in `AtlasDB` as an "instantiated attachment" under its own (attacker-chosen) hash, but it is never linked to the `content_hash` that the BNS name operation actually committed to, and `find_attachment(&requested_content_hash)` would not return the forged bytes for that specific hash — it would only be resolvable under the *attacker's* hash, not the originally committed one.

I was unable to fully verify the internals of `insert_instantiated_attachment`, `find_attachment`, and `decode_atlas_get_attachment` (in `stackslib/src/net/atlas/db.rs` and `stackslib/src/net/atlas/mod.rs`) within the available tool budget, so I cannot confirm with certainty whether there is any secondary path where content is stored/indexed under the *requested* hash rather than the hash of the actual bytes. If such a path existed (e.g., if some code stored content directly under the requested `content_hash` without recomputing/validating it), the vulnerability as described would be real. But based on the code actually traced, `AtlasDB` and `Attachment` handling in this file consistently key attachments by `attachment.hash()` (computed from the bytes themselves via `Hash160::from_data`), not by attacker-supplied or requested hash. That means the specific equality break claimed in the prompt — “content is served for `content_hash` despite having a different actual hash” — does not hold as traced, since content is always indexed by its own computed hash, not by the request's `content_hash` label.

### Impact Explanation
Not established with confidence given the incomplete trace of `AtlasDB::find_attachment` / `insert_instantiated_attachment`. Based on available evidence, forged bytes would end up indexed under their own hash, not under the victim's `content_hash`, so `RPCGetAttachmentRequestHandler::try_handle_request` -> `find_attachment(&requested_content_hash)` would not serve the forged bytes for that hash.

### Likelihood Explanation
Uncertain / not confirmed as exploitable as described. Requires further inspection of `stackslib/src/net/atlas/db.rs` (`insert_instantiated_attachment`, `find_attachment`) to definitively rule in or out.

### Recommendation
Regardless of the above uncertainty, as defense-in-depth the `Done` branch in `AttachmentsDownloader::run` (stackslib/src/net/atlas/download.rs, lines ~153-169) should explicitly re-verify, for each downloaded `Attachment`, that `attachment.hash()` equals the `content_hash` of the `AttachmentRequest` that produced it (available via the `BatchedRequestsResult<AttachmentRequest>::succeeded` map keys before they're discarded in `extend_with_attachments`), and drop/penalize the peer on mismatch instead of silently storing content under whatever hash it happens to have.

### Proof of Concept
Not constructed — given the uncertainty in the trace (unable to inspect `AtlasDB::insert_instantiated_attachment`/`find_attachment` internals), a proof-of-concept confirming or refuting cross-hash storage/service could not be completed within the available tool budget. This would require a `net` test in `stackslib/src/net/atlas/db.rs` or `stackslib/src/net/atlas/download.rs` tests constructing an `AtlasDB`, requesting attachment for `content_hash_A`, feeding a forged `Attachment{content}` with `Hash160::from_data(&content) = hash_B != hash_A` through `extend_with_attachments`/`Done` handling, then asserting whether `find_attachment(&hash_A)` returns the forged bytes (would confirm the bug) or returns `None`/original data (would refute it).
