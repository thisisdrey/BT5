### Summary
The Story Protocol bug divided a fixed pool by the *length* of a caller-influenced array and then paid out per array element without ever checking for duplicate entries, so repeating an ID in the array let one beneficiary collect multiple shares of a fixed pot. The exact same pattern exists in Substrate's slashing-reward-to-reporters logic: `pay_reporters` computes `per_reporter = reward_payout / reporters.len()` and then iterates the `reporters` slice, paying `per_reporter` to every element with no uniqueness check.

### Impact Explanation
`reward_payout` is capped by `slashed_imbalance`/`unapplied_slash.payout`, so this does not mint unbacked funds, but it does cause **duplicate settlement / wrong-beneficiary payout** within the fixed reward-for-reporting-an-offence pot: a reporter listed twice can claim double (or N×) the intended per-reporter share, corrupting the fair split among all reporters of an offence and diverting funds away from honest co-reporters. This falls under "duplicate settlement or payout" and "value not conserved / not settled exactly once to the rightful beneficiary" impact classes.

### Likelihood Explanation
The reachability of this bug depends entirely on whether `unapplied_slash.reporters` can end up containing a duplicate `AccountId` through a legitimate, unprivileged, non-malicious-validator path (e.g., the same account submitting two distinct valid equivocation/dispute-slashing reports against the same offender within the same slashing span, if `pallet-offences`'s merge-on-report logic appends to a combined reporters list rather than deduplicating). I was not able to fully trace, within the remaining budget, whether `pallet-offences`'s report-merging path (`substrate/frame/offences/src/lib.rs`) enforces uniqueness on the `reporters` vector when combining multiple reports of the same offence, or whether individual `report_equivocation` calls always produce single-element reporters vectors that get concatenated unchecked. This is the key open question that determines exploitability and should be verified before treating this as production-critical; I flag it explicitly rather than asserting certainty.

### Recommendation
In `pay_reporters` (both `substrate/frame/staking/src/slashing.rs` and `substrate/frame/staking-async/src/slashing.rs`), deduplicate the `reporters` slice (e.g., via `BTreeSet`) before computing `per_reporter = reward_payout / unique_reporters.len()`, and/or enforce uniqueness at the point where `UnappliedSlash.reporters` is constructed/merged in `pallet-offences`, so no single account can occupy more than one slot in the divisor or payout loop.

/// Apply a previously-unapplied slash.
pub(crate) fn apply_slash<T: Config>(
	unapplied_slash: UnappliedSlash<T::AccountId, BalanceOf<T>>,
	slash_era: EraIndex,
) {
	let mut slashed_imbalance = NegativeImbalanceOf::<T>::zero();
	let mut reward_payout = unapplied_slash.payout;

	do_slash::<T>(
		&unapplied_slash.validator,
		unapplied_slash.own,
		&mut reward_payout,
		&mut slashed_imbalance,
		slash_era,
	);

	for &(ref nominator, nominator_slash) in &unapplied_slash.others {
		do_slash::<T>(
			nominator,
			nominator_slash,
			&mut reward_payout,
			&mut slashed_imbalance,
			slash_era,
		);
	}

	pay_reporters::<T>(reward_payout, slashed_imbalance, &unapplied_slash.reporters);
}

/// Apply a reward payout to some reporters, paying the rewards out of the slashed imbalance.
fn pay_reporters<T: Config>(
	reward_payout: BalanceOf<T>,
	slashed_imbalance: NegativeImbalanceOf<T>,
	reporters: &[T::AccountId],
) {
	if reward_payout.is_zero() || reporters.is_empty() {
		// nobody to pay out to or nothing to pay;
		// just treat the whole value as slashed.
		T::Slash::on_unbalanced(slashed_imbalance);
		return;
	}

	// take rewards out of the slashed imbalance.
	let reward_payout = reward_payout.min(slashed_imbalance.peek());
	let (mut reward_payout, mut value_slashed) = slashed_imbalance.split(reward_payout);

	let per_reporter = reward_payout.peek() / (reporters.len() as u32).into();
	for reporter in reporters {
		let (reporter_reward, rest) = reward_payout.split(per_reporter);
		reward_payout = rest;

		// this cancels out the reporter reward imbalance internally, leading
		// to no change in total issuance.
		asset::deposit_slashed::<T>(reporter, reporter_reward);
	}

	// the rest goes to the on-slash imbalance handler (e.g. treasury)
	value_slashed.subsume(reward_payout); // remainder of reward division remains.
	T::Slash::on_unbalanced(value_slashed);
}

#[test]
fn subsequent_reports_in_same_span_pay_out_less() {
	// This test verifies that the reporters of the offence receive their slice from the slashed
	// amount, but less and less if they submit multiple reports in one span.
	ExtBuilder::default().build_and_execute(|| {
		// The reporters' reward is calculated from the total exposure.
		let initial_balance = 1125;

		assert_eq!(Staking::eras_stakers(active_era(), &11).total, initial_balance);

		on_offence_now(&[offence_from(11, Some(vec![1]))], &[Perbill::from_percent(20)]);

		// F1 * (reward_proportion * slash - 0)
		// 50% * (10% * initial_balance * 20%)
		let reward = (initial_balance / 5) / 20;
		assert_eq!(asset::total_balance::<Test>(&1), 10 + reward);

		on_offence_now(&[offence_from(11, Some(vec![1]))], &[Perbill::from_percent(50)]);

		let prior_payout = reward;

		// F1 * (reward_proportion * slash - prior_payout)
		// 50% * (10% * (initial_balance / 2) - prior_payout)
		let reward = ((initial_balance / 20) - prior_payout) / 2;
		assert_eq!(asset::total_balance::<Test>(&1), 10 + prior_payout + reward);
	});
}
