### Title
`AccountPermissionUpdateActuator` allows setting owner/active/witness permission keys to the unspendable zero address, permanently locking account control - ([File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java])

### Summary
The audited report describes `SolidStateDiamond`/`AuctionInternal`/`QueueInternal`'s `_transferOwnership` accepting `address(0)` because only `OwnableInternal.setOwner()` is called with no zero-address check, permanently bricking privileged control. The same bug class exists in java-tron's `AccountPermissionUpdateActuator`, whose `checkPermission()` only validates permission-key addresses with `DecodeUtil.addressValid()`, which checks length and the chain prefix byte but never rejects an all-zero payload. A user can therefore set their account's `Owner`/`Active`/`Witness` permission key(s) to the "zero" TRON address, which corresponds to no known private key, permanently and irrecoverably losing the ability to authorize any future active-permission transaction (including a corrective `AccountPermissionUpdateContract`).

### Finding Description
`AccountPermissionUpdateContract` is processed by `AccountPermissionUpdateActuator.validate()` and `execute()`. Key addresses in each permission are checked only via: [1](#0-0) 

which calls: [2](#0-1) 

`addressValid` only enforces address length (21 bytes) and the correct network prefix byte (`0x41` on mainnet); it never checks that the remaining 20 bytes aren't all-zero. Consequently a permission `Key` whose address is `0x41` followed by 20 zero bytes passes validation and is written directly into the account's owner/active/witness permission via: [3](#0-2) 

No known private key can produce a signature that recovers to this zero-payload address, so once it becomes the sole/threshold-controlling key of a permission, that permission (and by extension the account's active-permission-gated operations, including any future `AccountPermissionUpdate` to fix it) becomes permanently unusable — directly analogous to the reported diamond/auction/queue ownership-to-zero-address issue, where a critical control field is set to an address nobody can act from.

### Impact Explanation
Any account holder issuing a normal, signed `AccountPermissionUpdateContract` transaction (paying the associated fee) can, whether by mistake or via a crafted wallet/dApp, permanently freeze their own account's active-permission-gated capabilities (transfers requiring active permission, multisig operations, resource delegation actions, etc., depending on which permission is bricked) because the resulting key configuration is unrecoverable. This matches the "permanent freezing of funds" impact class called out in the validation criteria — funds/assets controlled under that permission's threshold can no longer be moved because no valid signature can ever satisfy it.

### Likelihood Explanation
Reachable directly by any unprivileged transaction broadcaster once multisig is enabled (`AllowMultiSign`), with no special privilege beyond controlling the account being updated: `validate()` only requires `DecodeUtil.addressValid()` to pass, `dynamicStore.getAllowMultiSign() == 1`, and threshold/weight-sum constraints, none of which reject the zero-payload address. A malicious dApp, phishing UI, or misconfigured multisig tooling could trivially construct such a contract for a victim who is convinced to sign it.

### Recommendation
In `AccountPermissionUpdateActuator.checkPermission()` (and ideally in `DecodeUtil.addressValid()` used more broadly for permission keys), explicitly reject the zero address, e.g. verify that the 20 bytes following the prefix are not all zero, in addition to the existing length/prefix checks, before allowing a `Key` to be included in `Owner`, `Active`, or `Witness` permissions.

### Proof of Concept
1. Enable multisig (`AllowMultiSign = 1`).
2. Submit an `AccountPermissionUpdateContract` for an owned account where the `Owner` permission's single key address is `0x41` + 20 zero bytes, with `threshold = 1`, `weight = 1` (satisfies `checkPermission`'s weight/threshold/key-count checks).
3. `AccountPermissionUpdateActuator.validate()` passes because `DecodeUtil.addressValid()` only checks length/prefix; `execute()` commits the permission via `AccountCapsule.updatePermissions()`.
4. The account's owner permission is now bound to an address with no corresponding private key — no transaction can ever satisfy that permission again, permanently freezing any operation gated by it.

  public static boolean addressValid(byte[] address) {
    if (ArrayUtils.isEmpty(address)) {
      logger.warn("Warning: Address is empty !!");
      return false;
    }
    if (address.length != ADDRESS_SIZE / 2) {
      logger.warn(
          "Warning: Address length need " + ADDRESS_SIZE + " but " + address.length
              + " !!");
      return false;
    }

    if (address[0] != addressPreFixByte) {
      logger.warn("Warning: Address need prefix with " + addressPreFixByte + " but "
          + address[0] + " !!");
      return false;
    }
    return true;
  }

  public void updatePermissions(Permission owner, Permission witness, List<Permission> actives) {
    Builder builder = this.account.toBuilder();

    owner = owner.toBuilder().setId(0).build();
    builder.setOwnerPermission(owner);
    if (witness != null && builder.getIsWitness()) {
      witness = witness.toBuilder().setId(1).build();
      builder.setWitnessPermission(witness);
    }

    builder.clearActivePermission();
    if (actives != null) {
      for (int i = 0; i < actives.size(); i++) {
        Permission permission = actives.get(i).toBuilder().setId(i + 2).build();
        builder.addActivePermission(permission);
      }
    }

    this.account = builder.build();
  }
