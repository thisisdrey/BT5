### Title
Unauthenticated dust-transfer stuffing of `depositTokensOfAccount` blocks victim deposits — `Pool.addToDepositTokensOfAccount` / `DepositToken._transfer` - ([File: contracts/DepositToken.sol](contracts/DepositToken.sol), [contracts/Pool.sol](contracts/Pool.sol))

### Summary
The Gogs report describes a permissionless endpoint that lets any unauthenticated user consume a shared resource (server storage) at the victim's expense. The Metronome analog: `DepositToken._transfer` is a fully public entry point that calls `pool.addToDepositTokensOfAccount(recipient_)` whenever a recipient's balance goes from 0 to >0. `Pool.addToDepositTokensOfAccount` enforces `onlyIfAdditionWillNotReachMaxTokens`, so once a victim's combined `depositTokensOfAccount + debtTokensOfAccount` reaches `MAX_TOKENS_PER_USER = 30`, every further mint or transfer of a *new* deposit token to that account reverts — a permissionless stuffing attack that requires no authentication, no victim interaction, and only dust amounts of collateral.

### Finding Description
- `DepositToken._transfer` (and `_mint` via `deposit`) unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` on a 0→positive balance transition [1](#0-0) .
- `Pool.addToDepositTokensOfAccount` is gated only by `onlyIfAdditionWillNotReachMaxTokens`, which reverts with `UserReachedMaxTokens` once the list reaches 30 entries [2](#0-1) [3](#0-2) .
- `transfer`/`transferFrom` only check `_revertIfLocked` (unlocked balance); an attacker with no debt has fully unlocked balances and can transfer 1 wei of each deposit token to the victim [4](#0-3) .
- `DebtToken` is non-transferable (`TransferNotSupported`), so the attacker can only fill slots with deposit tokens [5](#0-4) .

Attack path: attacker deposits dust underlying into each `DepositToken` of a pool (or uses `deposit(amount, onBehalfOf_ = victim)` directly, which mints to an arbitrary beneficiary [6](#0-5) ). Each new token occupies one slot in the victim's `depositTokensOfAccount`. After 30 distinct deposit tokens are pushed, any subsequent `deposit`, `transfer`, or `seize`-into-new-token for the victim reverts inside `addToDepositTokensOfAccount`.

### Impact Explanation
- **Temporary freezing of funds/positions**: the victim cannot deposit into any new collateral type, cannot open new positions via `SmartFarmingManager.leverage` (which deposits on their behalf), and cannot receive any deposit token they don't already hold — including liquidation seizes or rewards paid in a new token — until they manually transfer each dust token out to zero-balance it (which itself costs gas and requires the dust to be unlocked; if the attacker topped the victim's list while the victim has debt, the dust may be locked by `_revertIfLocked`, prolonging the freeze).
- The attack is griefing-costly only in dust collateral plus gas; no authentication or privileged role is needed.

### Likelihood Explanation
Feasible only on pools with enough listed deposit tokens to reach the cap: since `DebtToken`s cannot be transferred, the attacker needs `30 - victimDebtTokens - victimDepositTokens` distinct deposit tokens available in the pool. On mainnet, Metronome pools list many collaterals (native, stablecoins, Vesper/vaTokens, etc.); I could not fully verify the exact deployed count per pool from the index, so reachability depends on the deployed pool having enough deposit tokens (likely on the largest pools, not guaranteed on small ones). Modifiers don't help: `addToDepositTokensOfAccount` legitimately accepts calls from any registered `DepositToken`, and `transfer`/`deposit` are intentionally public. Mitigating factor: the victim can self-recover by sweeping dust tokens out, so impact is temporary freezing rather than theft.

### Recommendation
- Make token-list updates on the *recipient* side opt-in or permissioned: e.g., only add to `depositTokensOfAccount` when the recipient initiates the deposit themselves (`deposit` with `onBehalfOf_ == _msgSender()` or an explicit `claim`), or have `transfer`/`deposit`-on-behalf emit tokens without registering the slot and require `account_` to call a `registerDepositToken()` after their first receipt.
- Alternatively, raise/remove the fixed cap by iterating differently, or allow the account itself (or anyone) to call `removeFromDepositTokensOfAccount` for zero-balance entries so dust entries can be purged without transferring value.

### Proof of Concept
Foundry fork test sketch (against a deployed Pool with ≥30 deposit tokens):

```solidity
function testDustStuffingBlocksVictimDeposits() public {
    address victim = makeAddr("victim");
    address[] memory dts = pool.getDepositTokens(); // assume length >= 30
    for (uint i; i < 30; ++i) {
        IDepositToken dt = IDepositToken(dts[i]);
        IERC20 underlying = dt.underlying();
        deal(address(underlying), attacker, 1e6);
        underlying.approve(address(dt), 1e6);
        // mints dust to victim and registers the token in their list
        dt.deposit(1, victim);
    }
    assertEq(pool.depositTokensOfAccountLength(victim), 30);

    // victim cannot deposit into any deposit token they don't already hold,
    // nor receive a new deposit token via transfer:
    vm.startPrank(victim);
    vm.expectRevert(Pool.UserReachedMaxTokens.selector);
    IDepositToken(someNewToken).transfer(victim, 1); // or deposit(1, victim)
}
```

Caveat: requires the target pool to actually expose ~30 deposit tokens; if the pool has fewer, the cap cannot be reached via deposit tokens alone and the attack fails.
