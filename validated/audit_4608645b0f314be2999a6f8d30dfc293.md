### Title
Anti-replay window check-then-update race in `ConnectionState.Decrypt`/`VerifyRelay` allows duplicate packet delivery on replayed ciphertext - (File: `connection_state.go`)

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` implement anti-replay protection using a sliding-bitmap window (`Bits`), guarded by `decryptLock`. However, the lock is released between the replay **Check** and the replay **Update**, with the actual AEAD decryption performed *outside* the lock. This mirrors the Blend bug class exactly: a piece of shared state used to gate a calculation/decision (`non_queued_tokens` in Blend, the replay window in Nebula) is read, then a side-effecting operation is performed, and only afterward is the state updated — leaving a window where the read-side check can be satisfied twice for the same input before the corresponding write-side update has occurred.

### Finding Description
In `connection_state.go`: [1](#0-0) 

`Decrypt` does:
1. Lock `decryptLock`, call `cs.window.Check(l, messageCounter)`, unlock.
2. (unlocked) `cs.dKey.DecryptDanger(...)`.
3. Lock `decryptLock`, call `cs.window.Update(l, messageCounter)`, unlock.

`VerifyRelay` follows the identical pattern (lines 85-108) for relay frames.

The anti-replay window itself (`Bits`) is documented as a "sliding-window anti-replay tracker" whose `Update` records a counter as seen and its `Check`/`Update` split is meant to reject duplicates: [2](#0-1) 

Because `Check` and `Update` are two separate, independently-locked operations with the (comparatively expensive) AEAD decryption sandwiched in between *unlocked*, if two goroutines invoke `Decrypt` concurrently with the same `messageCounter` for the same `ConnectionState` (e.g., because a network attacker duplicates/replays a captured ciphertext UDP packet), both calls can observe `Check` returning `true` before either has called `Update`. Both then proceed to successfully decrypt the same ciphertext (a legitimate previously-observed nonce/ciphertext pair decrypts successfully every time) and both deliver the resulting plaintext into the packet-processing pipeline (`outside.go`): [3](#0-2) 

This is reachable by an on-path/off-path network attacker who does not hold any CA-signed certificate — they merely need to capture and re-inject (duplicate) an already-observed UDP packet belonging to an established tunnel, which is a classic replay primitive that the `Bits` anti-replay window exists specifically to defeat.

Concurrency is plausible because Nebula supports multiple reader/writer routines (`tun.routines`, `listen.batch`/`recvmmsg`) as referenced in the changelog and `Interface.routines`/`readers`/`writers` fields: [4](#0-3) [5](#0-4) 

I was not able to fully verify, from the indexed code, the exact dispatch logic that assigns an incoming UDP datagram to a specific reader/queue index `q` (i.e., whether duplicate packets for the same `HostInfo` can land on two different goroutines calling `readOutsidePackets`/`Decrypt` truly concurrently, or whether some upstream serialization per remote address prevents this). This should be confirmed by inspecting the UDP listen loop dispatch (`udp/udp_linux.go`, `main.go`) which I could not fully trace within the available search budget.

### Impact Explanation
If the race is reachable, a network attacker who can duplicate/replay previously observed ciphertext (no valid certificate required) can cause the same plaintext packet to be delivered twice into the tun device / firewall pipeline, defeating the anti-replay protection the `Bits` window is designed to provide. Depending on the payload, this can lead to duplicate processing of application-layer traffic (e.g., duplicate transactions, DNS responses, or other idempotency-sensitive traffic) — a traffic-replay class impact.

### Likelihood Explanation
Requires (a) the attacker being able to capture and duplicate an already-transmitted encrypted UDP packet between two Nebula peers (feasible for any on-path or off-path attacker with the ability to send spoofed/replayed UDP datagrams, common for UDP-based protocols), and (b) the two decrypt attempts landing on different goroutines with a tight enough race window before `Update` is called. The exact scheduling likelihood is uncertain without confirming Nebula's queue-dispatch design, so likelihood should be treated as **uncertain/moderate** pending further code review of the UDP read-loop dispatch.

### Recommendation
Hold `decryptLock` for the full duration of `Check` → `Decrypt` → `Update` (or otherwise make the check-decrypt-update sequence atomic per `messageCounter`), so that a second concurrent attempt with the same counter is rejected by `Check` before any decryption work is repeated, matching the Blend fix's approach of ensuring the state used to gate the operation is updated before the operation's effects can be observed elsewhere.

### Proof of Concept
Conceptual PoC (not executed, based on code review):
1. Establish a tunnel between two Nebula nodes with `tun.routines`/`listen.batch` > 1 (multi-reader mode).
2. Capture one legitimate encrypted data-plane packet (`header.Message`) sent by node A to node B.
3. Immediately re-inject two copies of the exact same UDP packet toward node B such that they are picked up by two different reader goroutines at (near) the same time.
4. If both `Decrypt` calls read `window.Check` before either has executed `window.Update`, both decrypt successfully and both payloads are forwarded to `f.readers[q].Write(out)`, resulting in duplicate delivery of the same plaintext packet despite the anti-replay window.

Note: I could not execute or fully trace the UDP reader-dispatch code within the available tool budget to conclusively prove that two goroutines can process the identical `(hostinfo, messageCounter)` pair concurrently; this should be verified against `udp/udp_linux.go` and the routine-spawning code in `main.go`/`interface.go` in a follow-up session with fuller code access.

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}
