### Title
Unchecked `new_authority` in `transfer_to_new_account`/`transfer_to_new_account_pda` permits permanent lock of all account funds via zero-address authority transfer - (File: `programs/marginfi/src/instructions/marginfi_account/transfer_account.rs`)

### Summary
The account-authority-signed instructions `transfer_to_new_account` and `transfer_to_new_account_pda` accept an arbitrary `new_authority` account with no validation that it is not `Pubkey::default()` (the zero pubkey). This mirrors the referenced `CryptoPunksHelper` finding, where privileged/owner-only functions permitted transferring an asset to the zero address, permanently destroying it. Here, the "asset" is the entire marginfi account — all deposits, borrows, and emissions — which becomes permanently inaccessible if migrated to a zero/unattainable authority, since no keypair exists that can sign as `Pubkey::default()`.

### Finding Description
`TransferToNewAccount` and `TransferToNewAccountPda` accept `new_authority` as a completely unchecked account: [2](#0-1) . The handler `transfer_to_new_account_pda` (and its sibling `transfer_to_new_account`) calls `initialize_migrated_account`, which sets `new_account.authority = new_authority` unconditionally: [1](#0-0) . Immediately afterward, the old account is disabled and its lending balances zeroed out via `finalize_migrated_old_account`, which sets `ACCOUNT_DISABLED` and clears `lending_account`: [4](#0-3) . There is no on-chain check equivalent to the CLI's `if new_authority == Pubkey::default() { bail!(...) }` guard found only in the off-chain client tooling: [3](#0-2) . Since the old account is disabled/emptied in the same instruction that creates the new account with the bad authority, all positions move irreversibly into an account no one can ever sign for.

### Impact Explanation
If `new_authority` is set to `Pubkey::default()` (whether by user/integrator error, malicious frontend, or a buggy/malicious third-party integrator invoking the instruction via CPI), the resulting `new_marginfi_account` holds all the user's deposits and liabilities but can never be signed for — `Signer<'info>` constraints on `authority` can never be satisfied for the zero pubkey. This permanently freezes/locks all collateral and outstanding positions in that account, a permanent loss of user funds with no recovery path (the source account is simultaneously emptied and disabled, so there's no rollback).

### Likelihood Explanation
The instruction is reachable by any account authority (unprivileged user) and by third-party integrators, matching the "unprivileged-user" scope. The bug is only masked by voluntary client-side (CLI) validation that is not enforced by the program itself, so any direct RPC/CPI caller, custom frontend, or a compromised/malicious dApp integration can trigger the zero-address transfer without any additional program-level protection. The account-level comment `WARN: New authority is completely unchecked` in the source itself acknowledges the gap.

### Recommendation
Add an on-chain constraint rejecting `new_authority.key() == Pubkey::default()` (and potentially other unattainable/system-owned addresses) in both `TransferToNewAccount` and `TransferToNewAccountPda` account validation structs or at the top of their handler functions, mirroring the check already present client-side in `p0-cli/src/processor/account.rs`.

### Proof of Concept
1. User (or integrator) calls `transfer_to_new_account` with `new_authority = Pubkey::default()`.
2. `initialize_migrated_account` sets `new_account.authority = Pubkey::default()`.
3. `finalize_migrated_old_account` disables the old account and zeroes its `lending_account`, moving all balances to the new account.
4. The new account's `authority` is the zero pubkey; no valid `Signer` can ever satisfy `has_one = authority` on subsequent instructions (deposit/withdraw/borrow/repay/close), permanently locking all funds in that account.

}
