Based on my research, I found a strong analog to the reported bug class in java-tron's resource-energy accounting code, where a denominator (`totalEnergyWeight`/`totalNetWeight`) that can legitimately reach zero is guarded only by a Java `assert` statement — which is a no-op in production (assertions are disabled by default unless the JVM is started with `-ea`).

### Title
Unguarded division by `totalEnergyWeight`/`totalNetWeight` in resource-limit calculation causes overflow to `Long.MAX_VALUE`, bypassing energy/bandwidth metering - ([File: chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java])

### Summary
`EnergyProcessor.calculateGlobalEnergyLimit()` and its `RepositoryImpl` counterpart compute an account's energy limit as a ratio of its frozen weight to the network's `totalEnergyWeight`. When `totalEnergyWeight` is 0, the code relies on a Java `assert` to prevent the division, but `assert` statements are compiled out / disabled by default in production JVMs, so the division still executes.

### Finding Description
In `EnergyProcessor.calculateGlobalEnergyLimit()`: [1](#0-0) 

the legacy (non-hardened) branch performs:
```java
long energyWeight = frozeBalance / TRX_PRECISION;
return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
```
If `totalEnergyWeight == 0` and `allowNewReward()` is not active, the only protection is `assert totalEnergyWeight > 0;`, which does nothing at runtime in a standard deployment. `(double) totalEnergyLimit / 0` evaluates to `Double.POSITIVE_INFINITY`, and `energyWeight * Infinity` is `Infinity`; casting that to `long` in Java yields `Long.MAX_VALUE` rather than throwing.

The identical pattern exists in the TVM-facing `RepositoryImpl.calculateGlobalEnergyLimit()`, which is used from native contract processors (freeze/unfreeze/delegate resource) reachable from ordinary transactions and contract calls: [2](#0-1) 

Here there isn't even the `allowNewReward()` short-circuit — only the bare `assert totalEnergyWeight > 0;` guards the division, and the hardened (`BigInteger`) branch would instead throw `ArithmeticException` (division by zero), while the legacy double-precision branch silently overflows to `Long.MAX_VALUE`.

The analogous bandwidth code path (`totalNetWeight`) follows the same structure, confirmed by the parity/overflow test suite exercising both `calculateGlobalEnergyLimit`/`calculateGlobalNetLimit` and their V2 variants: [3](#0-2) 

`totalEnergyWeight`/`totalNetWeight` are network-wide aggregates decremented whenever accounts unfreeze energy/bandwidth stake (via `UnfreezeBalanceProcessor`, `UnfreezeBalanceV2Processor`, etc.), so it is a value that depends on aggregate account behavior across the whole chain, not something a caller directly controls, but it is also not intrinsically prevented from reaching zero by any explicit runtime check outside the disabled `assert`.

### Impact Explanation
If `totalEnergyWeight` (or `totalNetWeight`) reaches 0 while any account still has `frozeBalance >= TRX_PRECISION` for energy/bandwidth (a state reachable on smaller/private/test networks, freshly bootstrapped chains, or theoretically after mass unfreeze events on mainnet), calls into `calculateGlobalEnergyLimit`/`calculateGlobalNetLimit` from ordinary contract execution and resource checks will either:
- silently overflow to `Long.MAX_VALUE`, effectively granting that account unlimited free energy/bandwidth (breaking energy metering, a form of unbacked resource "balance"), or
- throw an uncaught `ArithmeticException` in the hardened `BigInteger` path, aborting transaction/contract execution unexpectedly.

Both outcomes are more severe than the disclosed StableModule analog because they affect the chain's core resource-accounting invariant rather than an isolated LP-share calculation.

### Likelihood Explanation
Likelihood depends on the network's total frozen-for-energy/bandwidth stake reaching exactly zero while an account with nonzero frozen balance still queries its limit — unlikely on a mature mainnet with many participants, but realistic on smaller/private chains, immediately post-genesis before freezes accumulate, or after protocol events causing widespread unfreezing (e.g. governance-driven resource-model migrations). The guard being an `assert` (a no-op in production) means the code offers no actual protection regardless of how the zero state is reached.

### Recommendation
Replace the `assert totalEnergyWeight > 0;` / equivalent `totalNetWeight` checks with explicit runtime `if (totalEnergyWeight <= 0) return 0;` (or throw a proper checked exception) in both `EnergyProcessor.calculateGlobalEnergyLimit()` and `RepositoryImpl.calculateGlobalEnergyLimit()` (and their bandwidth analogs), independent of the `allowNewReward()` proposal flag, so the safety check is always active in production regardless of JVM assertion settings.

### Proof of Concept
1. On a network (e.g., private/test chain) where `totalEnergyWeight` is reduced to 0 via mass `UnfreezeBalance`/`UnfreezeBalanceV2` transactions while at least one account still shows `frozeBalance >= TRX_PRECISION` for energy (a stale/latent state, or via a resource-model transition edge case).
2. Trigger any transaction that calls `EnergyProcessor.useEnergy()` → `calculateGlobalEnergyLimit()`, or a TVM call that hits `RepositoryImpl.calculateGlobalEnergyLimit()` (e.g. via delegate/undelegate resource precompiles as exercised in `PrecompiledContractsTest`).
3. Observe that the legacy branch returns `Long.MAX_VALUE` (double-division-by-zero overflow) instead of `0`, or that the hardened branch throws `ArithmeticException`, since the `assert totalEnergyWeight > 0;` never fires in a production JVM run without `-ea`. [4](#0-3) [5](#0-4)

```java
  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
```
