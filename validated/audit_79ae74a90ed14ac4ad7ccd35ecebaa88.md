### Title
Account-scoped PromiseYield state (PromiseYieldReceipt/PromiseYieldStatus/YieldIdToDataId/DataIdToYieldId) survives `remove_account` and is inherited by a re-created account of the same name, enabling authorization escalation via delayed `PromiseResume` - ([File: core/store/src/utils/mod.rs])

### Finding Description
`remove_account` (core/store/src/utils/mod.rs:505-570) only clears `TrieKey::Account`, `TrieKey::ContractCode`, `TrieKey::AccessKey`/`GasKeyNonce`, and `TrieKey::ContractData` rows for the deleted account. It never iterates or removes rows under the `PROMISE_YIELD_RECEIPT`, `PROMISE_YIELD_STATUS`, `YIELD_ID_TO_DATA_ID`, or `DATA_ID_TO_YIELD_ID` columns.

Critically, `core/primitives/src/trie_key.rs` explicitly documents these four columns as account-id-keyed: `COLUMNS_WITH_ACCOUNT_ID_IN_KEY` (trie_key.rs:89-102) lists `PROMISE_YIELD_RECEIPT`, `PROMISE_YIELD_STATUS`, `YIELD_ID_TO_DATA_ID`, and `DATA_ID_TO_YIELD_ID` alongside `ACCOUNT`, `CONTRACT_CODE`, `ACCESS_KEY`, and `CONTRACT_DATA` as columns whose trie key embeds the `account_id`. Only the delayed-receipts queue, the yielded-promise timeout queue, and the outgoing-receipt buffer are called out in the surrounding comment as shard-global (not account-scoped) — the yield receipt/status/id-mapping rows are not in that exclusion list, confirming they are per-account state that a full "delete this account's state" routine should clear but does not.

Attack flow: an attacker deploys a contract on `a.attacker.near`, calls `promise_yield_create` targeting itself (`receiver_id == current_account_id`) with a batch action list containing `AddKey(FullAccess)` attached to the yielded promise, and never resolves the corresponding data. The postponed `ActionReceipt` (predecessor_id == receiver_id == `a.attacker.near`, actions = `[AddKey(FullAccess)]`) is persisted under `TrieKey::PromiseYieldReceipt`/`PromiseYieldStatus`/`YieldIdToDataId`/`DataIdToYieldId` for that account. The attacker then submits `DeleteAccount` (contract not locked) with the parent as beneficiary. `remove_account` clears the account row, code, keys, and contract data, but the four yield-related rows above remain in the trie under the now-nonexistent account's key prefix.

If the parent later re-creates `a.attacker.near` for a new tenant, that account's trie prefix is reused. Because the surviving `PromiseYieldStatus`/receipt state was never cleared, a subsequent data delivery (from the original attacker-controlled `data_id`, or the automatic `PromiseYieldTimeout` mechanism, since the timeout queue entry is shard-global and was never tied to account existence) causes the runtime to look up the postponed yield receipt by `data_id` and execute its stored actions against whatever account currently occupies that name. Runtime authorization (`apply_action_receipt` / `check_actor_permissions` in `runtime/runtime/src/lib.rs` and `runtime/runtime/src/actions.rs`) derives `actor_id` from `receipt.predecessor_id()`; since the stored receipt's `predecessor_id == receiver_id == account_id` (self-call, baked in at creation time), the permission check treats it as full/owner permission and admits the `AddKey(FullAccess)` action — even though the actor executing it is the new tenant's fresh account, not the original key holder.

### Impact Explanation
This is authorization escalation / account takeover: an attacker who never held keys on the newly (re)created account can gain a `FullAccess` key on it by exploiting stale, account-scoped yield state that `remove_account` fails to purge. This matches NEAR's "authorization escalation across accounts or promises" bounty category and can lead to theft of funds held by the new tenant account.

### Likelihood Explanation
Preconditions: attacker must control the account being deleted (trivial, self-owned subaccount), must convince/arrange for the same account name to be re-created (plausible in marketplaces, factory-pattern subaccount reuse, or accidental re-registration by the parent/registrar), and relies on either themselves later delivering the pending data or on the automatic timeout firing. Cost is minimal (standard transaction fees); the mechanism is fully attacker-controlled up to the point of re-creation, which depends on external behavior (parent account or registrar choosing to reuse the exact name). This reduces real-world likelihood compared to a fully self-contained exploit, but the underlying storage-cleanup bug is unconditionally present and reproducible.

### Recommendation
Extend `remove_account` in core/store/src/utils/mod.rs to also enumerate and remove all `TrieKey::PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, and `DataIdToYieldId` rows scoped to the deleted `account_id` (mirroring the existing access-key/contract-data iteration-and-delete pattern), or block `DeleteAccount` while any such pending yield state exists for the account, analogous to existing checks for locked contracts/pending state.

### Proof of Concept
Integration test in `runtime/runtime/src/tests/apply.rs` (or `test-loop-tests/src/tests/yield_resume.rs`):
1. Deploy a contract on `a.attacker.near`; call `promise_yield_create` with `receiver_id = "a.attacker.near"` and an attached `AddKey(FullAccess, attacker_pubkey)` action, capturing `data_id`.
2. Submit `DeleteAccount` for `a.attacker.near` (beneficiary = parent) in one applied chunk; assert `TrieKey::Account` is gone but assert (via direct trie read) that `TrieKey::PromiseYieldReceipt`/`YieldIdToDataId` rows for `a.attacker.near` still exist.
3. In a subsequent chunk, have the parent `CreateAccount` for `a.attacker.near` again (new tenant, no attacker keys).
4. Deliver `PromiseResume` for the captured `data_id` (or let `PromiseYieldTimeout` fire).
5. Assert the new tenant's access-key set on `a.attacker.near` now contains the attacker's `FullAccess` key — demonstrating unauthorized key injection into a freshly created account.
