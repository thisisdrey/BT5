## Analysis

The external report's core issue: a contract's on-chain address is trusted as a stable identity, but its executing bytecode can later change while the address stays the same ("metamorphic" contract), letting an attacker get approvals/trust while benign, then switch to malicious code and drain approved assets — all without any privileged/admin action, purely from the deploying party's own contract-level capability.

The direct local analog is `pallet_contracts`'s `seal0::set_code_hash` host function, exposed to any deployed Wasm contract, which lets **a contract change its own `code_hash` in place while its address remains identical**: [1](#0-0) 

The runtime dispatch for this host call requires no special origin — any contract calling into itself can invoke it during a normal `call`: [2](#0-1) 

The API doc itself acknowledges the exact metamorphic-contract risk pattern from the report: after this call, the address no longer deterministically identifies a fixed code hash, and even reentrant self-calls can pick up new code mid-flight: [3](#0-2) 

The existing test fixture demonstrates the primitive concretely: a contract can be called once, behave one way (return `1`), then swap its own code so that a second call to the *same address* returns a completely different result (`2`), i.e., a live A→B identity swap behind one stable address: [4](#0-3) [5](#0-4) 

Notably, `pallet-revive` (the newer EVM-compatible contracts pallet) already removed this exact capability along with `terminate`, explicitly because of this class of issue: [6](#0-5) 

But the legacy `pallet-contracts` (still shipped/used, e.g. by parachains on Substrate) retains `set_code_hash` fully enabled with no restriction beyond a determinism check on the new code — no guard prevents a contract from re-pointing itself to arbitrary different logic after other parties have already interacted with/approved it (e.g., an XCM-approved asset transactor, an NFT `approve_for_all` analog, or a staking/pool contract that users trusted after auditing its deployed bytecode).

### Why existing guards don't stop this
- The only check is `is_deterministic()` on the new code — it says nothing about behavioral equivalence to the previously audited code: [7](#0-6) 
- No caller/owner restriction exists — the contract's own logic decides when/whether to call `set_code_hash`, so a malicious contract author can gate this behind a hidden trigger to flip identity only after achieving trust/approvals, exactly mirroring the OZ Clones metamorphic scenario in the report.
- Because the account/address is unchanged, any external approval, allowance, or reliance placed on "this address's audited code" (approvals to move NFTs/tokens, delegate-dependency locks, treasury payout targets, etc.) silently carries over to the new, potentially malicious code.

### Title
Self-modifying contract identity via `set_code_hash` enables metamorphic-contract exploit in pallet-contracts — (File: `substrate/frame/contracts/src/exec.rs`)

### Summary
`pallet-contracts` exposes an unrestricted `set_code_hash` host function that lets any deployed contract rewrite its own `code_hash` in place, keeping the same on-chain address. This reproduces the exact "metamorphic contract" primitive from the external report: a contract can behave benignly to gain trust/approvals, then swap to malicious logic under the same trusted address to divert or steal already-approved funds.

### Finding Description
`Ext::set_code_hash` in `exec.rs` performs the swap with only a determinism check on the target code; it does not restrict who/what can trigger it beyond normal contract execution, and it explicitly warns (in its own doc comment) that after calling it the address no longer identifies a fixed code hash. Any counterparty that granted the contract's address an approval, allowance, delegate-dependency, or held it as a trusted integration point has no on-chain mechanism to detect or prevent the subsequent code swap.

### Impact Explanation
An attacker who deploys and controls a contract can present it for audit/trust (e.g., a pool/gauge-style contract that legitimately requests approvals from users or other contracts), then later call `set_code_hash` to swap in code that abuses those already-granted approvals to move funds to attacker-controlled accounts — a direct theft/fund-loss path with no runtime-privileged actor required.

### Likelihood Explanation
Likelihood is moderate: it requires only that some other contract or user grants an approval/trust relationship to the address before the swap, which is a normal integration pattern (approvals, delegate dependencies, staking authorizations). No validator, governance, or leaked-key assumption is needed — the deploying account of the vulnerable contract is the sole actor, matching the report's "malicious party controlling the deploy pipeline" framing.

### Recommendation
Restrict or remove `set_code_hash` in `pallet-contracts` consistent with the mitigation already applied in `pallet-revive` (see `prdoc/stable2603/pr_10517.prdoc`), or require that address-identity-changing operations be gated by an explicit, auditable mechanism (e.g., disallow self-`set_code_hash` for contracts holding outstanding approvals/locks, or require a time-locked announcement before the swap takes effect) so downstream trust relationships cannot be silently invalidated.

### Proof of Concept
Using the existing test harness pattern in `substrate/frame/contracts/src/tests.rs::set_code_hash`:
1. Deploy contract `A` with benign code; have a victim grant `A`'s address an approval/allowance or add it as a trusted delegate/integration.
2. `A`'s owner calls `A`, which internally invokes `api::set_code_hash(new_hash)` to switch to malicious code (as shown in `set_code_hash.rs` fixture).
3. Subsequent calls to the same address `A` now execute the malicious logic, which uses the still-valid approval/allowance to redirect funds to attacker-controlled accounts — with no new deployment, no address change, and no privileged action.

	fn set_code_hash(&mut self, hash: CodeHash<Self::T>) -> DispatchResult {
		let frame = top_frame_mut!(self);
		if !E::from_storage(hash, &mut frame.nested_gas)?.is_deterministic() {
			return Err(<Error<T>>::Indeterministic.into());
		}

		let info = frame.contract_info();

		let prev_hash = info.code_hash;
		info.code_hash = hash;

		let code_info = CodeInfoOf::<T>::get(hash).ok_or(Error::<T>::CodeNotFound)?;

		let old_base_deposit = info.storage_base_deposit();
		let new_base_deposit = info.update_base_deposit(&code_info);
		let deposit = StorageDeposit::Charge(new_base_deposit)
			.saturating_sub(&StorageDeposit::Charge(old_base_deposit));

		frame.nested_storage.charge_deposit(frame.account_id.clone(), deposit);

		Self::increment_refcount(hash)?;
		Self::decrement_refcount(prev_hash);
		Contracts::<Self::T>::deposit_event(Event::ContractCodeUpdated {
			contract: frame.account_id.clone(),
			new_code_hash: hash,
			old_code_hash: prev_hash,
		});
		Ok(())
	}

	#[prefixed_alias]
	#[mutating]
	fn set_code_hash(ctx: _, memory: _, code_hash_ptr: u32) -> Result<ReturnErrorCode, TrapReason> {
		ctx.charge_gas(RuntimeCosts::SetCodeHash)?;
		let code_hash: CodeHash<<E as Ext>::T> =
			ctx.read_sandbox_memory_as(memory, code_hash_ptr)?;
		match ctx.ext.set_code_hash(code_hash) {
			Err(err) => {
				let code = Runtime::<E>::err_into_return_code(err)?;
				Ok(code)
			},
			Ok(()) => Ok(ReturnErrorCode::Success),
		}
	}
