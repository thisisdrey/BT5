Audit Report

## Title
`submit_delivery_receipt` pays the full relayer fee regardless of message delivery outcome - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
The Snowbridge V2 outbound queue's `process_delivery_receipt` function decodes a `DeliveryReceipt` containing a `success: bool` field from a verified Ethereum event log, but never inspects this field before crediting the relayer reward and removing the `PendingOrder`. This allows a relayer to be paid the full fee for a message that failed to execute on Ethereum, as long as a genuine `InboundMessageDispatched` event with `success = false` can be produced.

## Finding Description
The `DeliveryReceipt` struct decoded from the `InboundMessageDispatched` Ethereum event explicitly carries a `success` field [1](#0-0) . The `submit_delivery_receipt` extrinsic verifies only that the raw event log is genuinely included in a valid Ethereum receipt via `T::Verifier::verify`, decodes it into a `DeliveryReceipt`, and forwards it straight to `process_delivery_receipt` without any success check: [2](#0-1) .

In `process_delivery_receipt`, the function verifies the gateway address, resolves the reward account, fetches the `PendingOrder` by `receipt.nonce`, and — if `order.fee > 0` — unconditionally calls `T::RewardPayment::register_reward` for the full fee, then removes the order from `PendingOrders`. The `receipt.success` field is decoded upstream but is never read in this function: [3](#0-2) .

The module-level documentation states the intended flow is that reward payment happens "When the message has been verified **and executed**," implying the reward should be contingent on successful execution, not merely on the event's existence: [4](#0-3) . Since `success` is decoded but discarded, any signed account (no relayer allowlist — `ensure_signed` only) that can present proof of a real `success = false` event still collects the full `order.fee`, and the `PendingOrder` is deleted, foreclosing retry or reconciliation.

## Impact Explanation
This is a duplicate/incorrect-settlement class issue: value that should only be paid out for successful message delivery/execution on Ethereum is instead paid unconditionally whenever a verifiable delivery-attempt event exists, regardless of the `success` outcome. This drains the reward pot funded by user message fees for work that was not completed, and permanently removes the `PendingOrder`, eliminating any path to retry or correct the failed delivery. This matches the "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically" pivot and the "duplicate settlement or payout" impact gate.

## Likelihood Explanation
`submit_delivery_receipt` is fully public and unprivileged (`ensure_signed` only, no relayer allowlist). The only requirement is a genuine, provable `InboundMessageDispatched` event with `success = false`, which is a normal, expected outcome of Ethereum execution failures (e.g., insufficient gas, reverting commands) that any relayer can naturally encounter or potentially induce, without collusion with governance, validators, or the bridge operator.

## Recommendation
In `process_delivery_receipt`, check `receipt.success` before crediting `T::RewardPayment::register_reward`. On `success == false`, either withhold or reduce the reward, or route the order into a distinct failure/retry path instead of unconditionally removing the `PendingOrder` and paying the full fee as if delivery had succeeded.

## Proof of Concept
1. A message is enqueued via `do_process_message`, creating `PendingOrders[nonce] = { fee, block_number }` [5](#0-4) .
2. On Ethereum, the corresponding command execution reverts/fails, so the Gateway contract emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. Any signed account submits `submit_delivery_receipt` with a valid proof for this real `success=false` event; `T::Verifier::verify` succeeds and `DeliveryReceipt::try_from` decodes `success = false`.
4. `process_delivery_receipt` never reads `receipt.success`, so `order.fee > 0` triggers `register_reward` for the full fee, and `PendingOrders::remove(nonce)` deletes the order — the relayer is fully paid despite the failed delivery [6](#0-5) .

```rust
		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
```
