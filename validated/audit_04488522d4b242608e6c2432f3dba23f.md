### Title
Ignored `CountDownLatch.await()` timeout result in `VerifyTransferProof` precompile allows unbounded blocking on TVM execution thread - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `verifyTransferProof` TVM precompile (mapped to a fixed precompile address and reachable from any smart-contract call that invokes the shielded-transfer precompile) submits parallel sapling proof-check tasks and computes a `withNoTimeout` flag from `countDownLatch.await(getCPUTimeLeftInNanoSecond(), TimeUnit.NANOSECONDS)`, but never checks that flag before unconditionally blocking on every `Future.get()`. This mirrors the CVE-2021-47457 bug class: the result of an interruptible/timed wait is computed but discarded, so execution proceeds as if the wait had always succeeded, defeating the intended time budget enforcement.

### Finding Description
In `VerifyTransferProof.doExecute` [1](#0-0) , `countDownLatch.await(getCPUTimeLeftInNanoSecond(), TimeUnit.NANOSECONDS)` is invoked and its boolean result is stored in `withNoTimeout`, but that variable is never inspected — the code falls straight into a loop calling `future.get()` on every submitted task regardless of whether the CPU-time budget already expired.

This is inconsistent with the sibling precompile `BatchValidateSign.doExecute`, which performs the identical pattern but correctly checks the result and aborts with `Program.Exception.notEnoughTime(...)` when the latch does not complete in time [2](#0-1) . `VerifyMintProof` performs its zk-check synchronously and is unaffected, but `VerifyTransferProof` (and its `VerifyProof` subclass structure at lines 1559-1611) shares the same `SaplingCheckSpendTask` / `SaplingCheckOutputTask` / `SaplingCheckBingdingSig` submission-and-latch pattern as the vulnerable snippet [3](#0-2) .

Because `future.get()` (no-arg, unbounded) is called unconditionally after the ignored timeout check, once the CPU-time-left budget for the transaction has already elapsed, the VM-executing thread no longer bails out — it keeps blocking on the worker pool (`workersInConstantCall` / `workersInNonConstantCall`, each a fixed pool of 5 threads) until the native `librustzcash` proof verification actually finishes, however long that takes.

### Impact Explanation
An unprivileged caller can invoke a smart contract that calls the `verifyTransferProof` precompile with a syntactically valid but computationally expensive proof-verification workload (the precompile only validates array sizes/duplicate nullifiers before dispatching to the thread pool). Since the CPU-time-limit check result is discarded, the transaction-processing/VM thread can be blocked past the intended per-transaction time budget while holding a slot in the shared, size-5 worker pool. Because the pool is static and shared across all transactions processed by that JVM (constant calls and non-constant calls each share one pool), repeated invocation can exhaust the available worker threads and stall subsequent shielded-transfer proof verifications, and it removes the CPU-time enforcement that is supposed to bound transaction execution during block application in `Manager`. This weakens the node's ability to enforce transaction execution time limits, a resource/availability concern on the block-application path.

### Likelihood Explanation
The precompile is reachable by any account that can deploy or call a contract invoking the `verifyTransferProof` address with attacker-controlled (but format-valid) `spendCount`/`receiveCount` proof data — no special privilege is required. The missing check is a simple, always-present code path (not conditional on rare timing), so it triggers on every call where the underlying native verification runs long, making exploitation straightforward and repeatable.

### Recommendation
Check the result of `countDownLatch.await(...)` in `VerifyTransferProof.doExecute` exactly as `BatchValidateSign.doExecute` does: if `withNoTimeout` is `false`, immediately throw `Program.Exception.notEnoughTime(...)` (or otherwise abort/cancel outstanding futures) instead of proceeding to call `future.get()` on every submitted task.

### Proof of Concept
Not independently executable from static analysis alone — the observed defect is the unconditional fallthrough to `future.get()` in `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java` lines 1589-1595, contrasted with the correctly-guarded equivalent in `BatchValidateSign.doExecute` (lines 1201-1207). Confirming the practical DoS magnitude (exact time to exhaust the 5-thread pools, or the wall-clock overrun achievable via crafted proof data) would require running the node and timing `verifyTransferProof` invocations under `getCPUTimeLeftInNanoSecond()` pressure, which requires runtime access beyond static code review.
