### Title
Half-open QUIC handshakes bypass both per-IP and global connection rate limiters and starve `ClientConnectionTracker` slots - ([File: streamer/src/nonblocking/quic.rs])

### Summary
An unstaked/unauthenticated attacker can repeatedly open QUIC connections that stall before completing the TLS handshake. Because the per-IP and global connection rate limiters only consume tokens *after* a handshake successfully completes, incomplete handshakes never get rate-limited, letting the attacker cycle through `ClientConnectionTracker` slots up to `qos.max_concurrent_connections()` indefinitely and starve legitimate senders.

### Finding Description
In `run_server`, before a connection is accepted, two rate-limit checks are performed but they are **read-only / non-consuming**:
- `overall_connection_rate_limiter.current_tokens() == 0` [1](#0-0) 
- `rate_limiter.is_allowed(&incoming.remote_address().ip())`, which explicitly does not mutate state and returns `true` for any IP it hasn't seen registered yet [2](#0-1) [3](#0-2) 

After these checks pass, `ClientConnectionTracker::new` is granted, `outstanding_incoming_connection_attempts` is bumped, and `setup_connection` is spawned to await the handshake with a 2-second timeout (`QUIC_CONNECTION_HANDSHAKE_TIMEOUT`, not 60s as in the question — that 60s constant lives in the unrelated client-side `quic-client/src/nonblocking/quic_client.rs`) [4](#0-3) [5](#0-4) .

Crucially, the actual token-consuming calls — `rate_limiter.register_connection(&from.ip())` and `overall_connection_rate_limiter.consume_tokens(1)` — only execute **after** the handshake completes successfully, inside the `Ok(new_connection)` branch of `setup_connection` [6](#0-5) . If the peer never completes the handshake, execution falls into the timeout branch that only increments `connection_setup_timeout` and never touches either rate limiter [7](#0-6) .

Because of this, an attacker who deliberately never finishes the TLS handshake (e.g., sends a valid Initial packet and stops) is never registered by either limiter, so `is_allowed`/`current_tokens` checks continue to pass for repeated attempts from the same IP indefinitely. The only backstop is `ClientConnectionTracker::new`'s cap at `qos.max_concurrent_connections()` [8](#0-7) , and the 2-second timeout that eventually frees the slot via `Drop for ClientConnectionTracker` [9](#0-8) . By sustaining a churn of stalled handshakes faster than the 2s expiry, the attacker can keep `open_connections` pinned near `max_concurrent_connections()`, causing legitimate connections to be refused via `refused_connections_too_many_open_connections` [10](#0-9) .

### Impact Explanation
This is a QoS-evasion / availability issue: legitimate staked and unstaked senders are continuously refused new TPU connections while the attacker sustains the half-open handshake flood, because the connection-admission gate (`ClientConnectionTracker`) exhausts before either rate limiter ever engages. Unlike the intended design (bounded degradation of at most `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` ≈ 2s per burst, per the code comment's stated threat model at lines 332-340), the rate limiters that are supposed to bound repeat abuse from a single IP or in aggregate never trigger against this specific pattern, so the attacker can sustain the denial indefinitely rather than only for a single 2-second window.

### Likelihood Explanation
Fully feasible with only unprivileged UDP access to the public TPU QUIC port: the attacker just needs to send Initial packets and withhold the rest of the handshake, requiring no stake, no spoofing, and no cooperation from other peers. It is trivially repeatable since generating new stalled connection attempts is cheap for the attacker (no cryptographic completion required) while occupying a server-side tracker slot for up to 2 seconds each.

### Recommendation
Move (or duplicate) rate-limiter token consumption to the point of *connection attempt* (before/at `incoming.accept()`), rather than only on successful handshake completion, so that repeated failed/stalled handshake attempts from an IP are counted against that IP's and the global budget. Alternatively, track and rate-limit failed/timed-out handshake attempts per IP explicitly (e.g., increment a penalty counter in the `connection_setup_timeout` path) so that non-completing peers are throttled at least as aggressively as completing ones.

### Proof of Concept
Integration test plan (streamer crate, using existing `setup_quic_server` test harness in `streamer/src/nonblocking/quic.rs` tests):
1. Spawn a QUIC server via `spawn_server`/`setup_quic_server` with a small `max_staked_connections`/`max_unstaked_connections` (so `max_concurrent_connections()` is easy to saturate, e.g. 10).
2. From a single attacker source IP (loopback with distinct ephemeral ports is fine for the per-connection tracker but same IP for rate-limiter purposes), repeatedly create raw `quinn::Endpoint::connect` calls but drop the `Connecting` future immediately after sending the Initial (or use a custom UDP socket sending just an Initial packet) so handshake never completes, cycling faster than `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` (2s).
3. Assert that `stats.refused_connections_too_many_open_connections` increments while a concurrently-attempted legitimate client (with a proper full handshake) fails to connect or connects with elevated latency approaching the 2s bound, repeatedly, for as long as the flood continues (i.e., it doesn't recover once — it keeps failing).
4. Assert that `stats.connection_rate_limited_per_ipaddr` and `stats.connection_rate_limited_across_all` remain at 0 (or far below the flood volume) throughout, proving the rate limiters never engaged against the attacker's repeated incomplete attempts.

impl ClientConnectionTracker {
    /// Check the max_concurrent_connections limit and if it is within the limit
    /// create ClientConnectionTracker and increment open connection count. Otherwise returns Err
    fn new(stats: Arc<StreamerStats>, max_concurrent_connections: usize) -> Result<Self, ()> {
        let open_connections = stats.open_connections.fetch_add(1, Ordering::Relaxed);
        if open_connections >= max_concurrent_connections {
            stats.open_connections.fetch_sub(1, Ordering::Relaxed);
            debug!(
                "There are too many concurrent connections opened already: open: \
                 {open_connections}, max: {max_concurrent_connections}"
            );
            return Err(());
        }

        Ok(Self { stats })
    }

    /// Check if the connection from the said `ip` is allowed.
    /// Here we assume that only IPs with actual confirmed connections are stored in it,
    /// since we should only modify server state once source IP is verified
    pub fn is_allowed(&self, ip: &IpAddr) -> bool {
        // Check if we have records in the rate limiter for the given IP address
        match self.limiter.current_tokens(ip) {
            Some(r) => r > 0, // we have a record, and rate is not exceeded
            None => true,     // if we have not seen IP, allow connection request
