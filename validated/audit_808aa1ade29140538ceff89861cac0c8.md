## Analysis

The Gondi bug is a "shortcut-hash divergence" class: two code paths derive an authorization/accounting-relevant value from the same logical object, one path's derivation omits a field the other includes, and the mismatch lets an attacker's on-chain object escape a fee/QoS check that the canonical path would have enforced.

The closest reachable analog in the allowed surface (banking stage / QoS) is the **sigverify-side priority-floor pre-filter**, which computes transaction priority from **raw, unverified packet bytes** via a lightweight parse (`SanitizedTransactionView`), separate from and *prior to* the canonical priority computed by the scheduler from the fully-resolved, signature-verified transaction. The code explicitly documents that these two computations "must agree," and both currently share the same downstream formula — but they operate on structurally different inputs (unverified bytes vs. fully sanitized/resolved transaction), which is exactly the shape of bug that produced the Gondi finding: a cheap check derived from a subset/different view of the same data used to gate an economic filter.

### Title
Sigverify Priority-Floor Computed From Unverified/Partially-Sanitized Bytes Can Diverge From Canonical Scheduler Priority, Enabling QoS-Floor Evasion - (File: core/src/transaction_priority.rs)

### Summary
`apply_priority_floor_to_batch` in [1](#0-0)  drops packets whose priority is at-or-below the scheduler-published `SchedulerPriorityFloor` **before signature verification**, using `calculate_priority_from_bytes` [2](#0-1) . That function parses the packet with the lightweight, unverified `SanitizedTransactionView::try_new_sanitized` and computes priority from a partially-resolved view (no address-lookup-table resolution, no full account-lock/duplicate validation, `MessageHash::Compute` on unverified bytes). The scheduler's authoritative priority, used to actually admit/evict transactions and set the floor itself, is computed later from a fully resolved, signature-verified `RuntimeTransaction<ResolvedTransactionView>` in `receive_and_buffer.rs` [3](#0-2) . The codebase's own test explicitly documents this as an invariant that "must agree" rather than something structurally guaranteed: [4](#0-3) .

### Finding Description
Two independent code paths compute the "priority" value used to gate the same QoS mechanism:

1. **Cheap/unverified path** (`calculate_priority_from_bytes`): runs in the sigverify worker on raw packet bytes, before Ed25519 signature verification, using `SanitizedTransactionView` (a partial/streaming parse) and `RuntimeTransaction<SanitizedTransactionView<_>>::try_new` with `MessageHash::Compute`. It resolves `transaction_configuration()` from whatever compute-budget instructions can be parsed from the static (unresolved) message — it does *not* resolve address-lookup-table (ALT) accounts, does not perform full account-lock/duplicate-key validation, and does not require a valid signature. [5](#0-4) 

2. **Canonical/authoritative path**: runs later in the scheduler's `receive_and_buffer.rs`, after ALT resolution (`load_addresses_for_view`) and `RuntimeTransaction<ResolvedTransactionView<_>>::try_new`, and is what actually determines admission/eviction from the bounded scheduler container and thus what value gets published as the floor itself (`get_min_max_priority()` in `scheduler_controller.rs`). [6](#0-5) [7](#0-6) 

Because path (1) operates on a *different, unverified, and less-resolved* representation of the transaction than path (2), the two priority computations are not derived from the same canonical set of "signed" inputs. This mirrors the Gondi root cause precisely: a fast/partial derivation (the loan hash omitting `protocolFee`; here, the bytes-path priority omitting full ALT/account resolution and running on unauthenticated bytes) is trusted to gate a check whose real enforcement point uses a fuller derivation — and nothing in the type system prevents the two from diverging as new transaction-configuration fields, versions, or ALT-dependent behavior are added.

### Impact Explanation
If an attacker crafts a packet where the bytes-path (`SanitizedTransactionView`) computes a priority *above* the current floor — e.g., by exploiting any parsing/resolution difference between the unresolved static message and the ALT-resolved message (compute-budget-relevant instructions, `is_writable`/account-count-dependent cost inputs, or version-specific `TransactionConfig` parsing differences) — while the transaction's *true*, fully-resolved priority would fall at-or-below the floor, the packet bypasses the cheap pre-signature-verification drop that is specifically meant to shed such low-value work under saturation. This lets underpriced/low-value work consume signature-verification CPU and banking-stage channel capacity that the priority-floor mechanism exists to protect, i.e. a QoS-evasion / "grossly underpriced pre-fee work" outcome under saturation — the exact category the validation rules list as acceptable impact. Conversely, a legitimate high-priority transaction whose bytes-path priority is computed lower than its true priority (e.g., because ALT-resolved writable-account cost differs from unresolved cost) could be spuriously dropped before it even reaches sigverify, a false-negative admission-control failure.

### Likelihood Explanation
The floor check only activates once the scheduler's buffer is saturated (`SATURATION_BUFFER_PCT`), so exploitation requires the attacker to first drive the node into a saturated state (achievable by flooding with a burst of transactions) and then send crafted packets timed to that window — realistic during normal high-load/ spam conditions and does not require validator/operator privileges, matching the "packet dedup and sigverify / banking stage and scheduler" unprivileged-user scope. The exact divergence vector (which specific ALT/account-resolution/version field causes bytes-path vs. typed-path priority to differ) was not fully proven within the available tooling — this requires dynamic testing (e.g., crafting a v0 transaction with an ALT-resolved writable account that changes the cost/priority formula, or exploiting a parse difference in `SanitizedTransactionView` vs. full resolution) to confirm a concrete diverging payload, which I was not able to construct and verify from static reading alone.

### Recommendation
Ensure `calculate_priority_from_bytes` (the pre-sigverify floor check) is provably bound to the same inputs as the scheduler's authoritative priority computation, e.g., by resolving ALT/account state consistently before priority computation in both paths, or by explicitly documenting/enforcing (via a shared typed conversion, not merely a unit test asserting equality on a single example) that the floor pre-check can only ever produce a value less-than-or-equal to the true post-resolution priority (so it is safe to use as a monotone lower bound rather than an exact predictor), and adding fuzz/property tests across ALT-resolved and v1-config transactions (not just the single legacy-transfer case in `floor_priority_from_bytes_matches_typed_path`) to catch divergence classes analogous to the Gondi `protocolFee` omission.

### Proof of Concept
A precise byte-level PoC transaction that provably diverges the two priority computations could not be constructed with the available read-only tooling; this would require building and comparing a v0 transaction using address-lookup-table-resolved writable accounts (or another compute-budget/version edge case) through both `calculate_priority_from_bytes` and the `receive_and_buffer.rs::try_handle_packet` path, and observing a priority difference that straddles a saturation-triggered floor value, mirroring the existing but single-case `floor_priority_from_bytes_matches_typed_path` test at [4](#0-3) .

fn apply_priority_floor_to_batch(
    batch: &mut PacketBatch,
    floor: u64,
    bank: &Bank,
) -> (usize, bool) {
    let mut dropped: usize = 0;
    let mut any_kept = false;
    for mut packet in batch.iter_mut() {
        if packet.meta().discard() {
            continue;
        }
        let Some(data) = packet.data(..) else {
            // Zero-length or otherwise unreadable: leave to downstream
            // stages to reject.
            any_kept = true;
            continue;
        };
        // Unparseable packets are kept and left for downstream rejection.
        match calculate_priority_from_bytes(bank, data) {
            Some(priority) if priority <= floor => {
                packet.meta_mut().set_discard(true);
                dropped = dropped.saturating_add(1);
            }
            _ => any_kept = true,
        }
    }
    (dropped, !any_kept)
}

/// Evaluate raw packet bytes against the pf-floor, returning the computed
/// priority.
///
/// Returns `None` if the bytes don't parse as a valid transaction, in which
/// case the caller should leave the packet to downstream stages to reject.
pub(crate) fn calculate_priority_from_bytes(bank: &Bank, data: &[u8]) -> Option<u64> {
    let view = SanitizedTransactionView::try_new_sanitized(data, &sanitize_config()).ok()?;
    let runtime_tx = RuntimeTransaction::<SanitizedTransactionView<_>>::try_new(
        view,
        MessageHash::Compute,
        None,
    )
    .ok()?;
    let transaction_configuration = runtime_tx
        .transaction_configuration(&bank.feature_set)
        .ok()?;
    let (priority, _cost) =
        calculate_priority_and_cost(bank, &runtime_tx, &transaction_configuration);

    Some(priority)
}
