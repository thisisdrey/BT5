### Title
Missing G2 subgroup check in `alt_bn128_pairing_check` host function allows pairing forgery - (File: `runtime/near-vm-runner/src/logic/alt_bn128.rs`)

### Summary
The `alt_bn128_pairing_check` WASM host function, reachable by any deployed contract, decodes G2 points via `decode_g2` which only checks that `(x, y)` lies on the BN254 twist curve (`bn::AffineG2::new`) but never verifies the point belongs to the correct order-`r` prime-order subgroup used by pairings. [1](#0-0) 

### Finding Description
`pairing_check` in `alt_bn128.rs` decodes each element as `(bn::G1, bn::G2)` and calls `bn::pairing_batch`, but `decode_g2` performs no subgroup check — it only rejects points not on the twist curve, or accepts the identity when both coordinates are zero. [2](#0-1) 

The docstring on `VMLogic::alt_bn128_pairing_check` explicitly assumes the G2 input is an "Fr-ordered subgroup point," documenting the required precondition, but the implementation never enforces it in code. [3](#0-2) 

For comparison, NEAR's own BLS12-381 pairing implementation does perform explicit subgroup checks (`blst_p1_affine_in_g1`, `blst_p2_affine_in_g2`) before running the pairing, confirming the team recognizes subgroup validation as a necessary security property for on-chain pairing host functions — but this check is absent from the BN254/alt_bn128 path. [4](#0-3) 

This host function is directly exposed to any unprivileged contract via the WASM import table. [5](#0-4) 

Because BN254's G2 subgroup has cofactor > 1 relative to the full twist group order, points on the curve but outside the r-order subgroup exist. Feeding such points into `pairing_batch` can produce results inconsistent with what a correct SNARK/Groth16 verifier expects, since the security proofs and pairing bilinearity guarantees for e(P,Q) rely on both P and Q belonging to their respective prime-order subgroups.

### Impact Explanation
Any NEAR contract that implements a Groth16/pairing-based zk-SNARK verifier (e.g., bridges, mixers, rollup verifiers) using `alt_bn128_pairing_check` inherits this gap. An attacker able to supply an arbitrary proof (including the G2 element, typical in Groth16 proofs where `π_B ∈ G2`) could attempt to construct a proof containing an off-subgroup G2 point that satisfies the pairing equation without corresponding to a valid witness, potentially forging proof verification. If such a verifier gates fund transfers (e.g., a bridge withdrawal, private-pool withdrawal), this could lead to theft or improper minting of funds — a concrete violation of contract-level authorization guarantees. The severity for any specific contract depends on whether that contract's own circuit additionally constrains subgroup membership, but the NEAR host function itself provides no such guarantee, unlike its BLS12-381 counterpart.

### Likelihood Explanation
Exploitability requires an attacker to actually find G2 points outside the correct subgroup that also satisfy a target pairing equation for a specific circuit/verifying key — this is not trivial in general and depends on the specific verifier logic built on top. However, the host function itself is unconditionally reachable by any contract with no gas-cost or protocol barrier, and the lack of subgroup enforcement is a well-known precondition failure class for pairing-based proof systems (matching the class flagged in the analogous zksync-crypto report). The likelihood of practical exploitation is contract-dependent (moderate) rather than universal, since it requires an on-chain consumer of `alt_bn128_pairing_check` for security-critical verification.

### Recommendation
Add an explicit subgroup check in `decode_g2` (and consider `decode_g1`, since BN254 G1 also technically requires it, though G1's cofactor is 1 so it's automatically satisfied) by verifying `[r]P == O` for the decoded G2 point before it is used in `bn::pairing_batch`, mirroring the `blst_p2_affine_in_g2` check already used in the BLS12-381 implementation. If the underlying `bn` crate does not expose subgroup-check functionality, the check should be implemented manually (e.g., using the endomorphism-based faster subgroup test referenced in the original report) inside `runtime/near-vm-runner/src/logic/alt_bn128.rs`.

### Proof of Concept
Not concretely constructed here — a full PoC requires deriving a specific BN254 G2 point outside the r-order subgroup that satisfies a target pairing equation for a chosen victim contract's verifying key, which is circuit/contract-specific. The structural gap is demonstrable directly: `decode_g2` (`runtime/near-vm-runner/src/logic/alt_bn128.rs`, lines 131-142) performs only `bn::AffineG2::new(x, y)` (on-curve check), with no call analogous to `blst_p2_affine_in_g2` found anywhere in the alt_bn128 module, confirmed via `grep_search` for `is_in_correct_subgroup|subgroup` across the repo showing zero matches in `alt_bn128.rs`.

fn decode_g2(raw: &[u8; 2 * POINT_SIZE]) -> Result<bn::G2, InvalidInput> {
    let (x, y) = stdx::split_array(raw);
