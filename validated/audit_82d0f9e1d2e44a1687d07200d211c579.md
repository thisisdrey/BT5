### Title
Unsynchronized lazy-singleton in `ActuatorCreator.getINSTANCE()` can publish a partially-constructed instance to concurrent transaction-execution threads - (File: `actuator/src/main/java/org/tron/core/actuator/ActuatorCreator.java`)

### Summary
`ActuatorCreator` uses a classic unsynchronized "check-then-act" lazy singleton (no `volatile`, no `synchronized`, no read/write barrier) to publish its instance across threads. This is the same bug class as CVE-2024-58084: a globally shared reference is written on one thread without a proper memory barrier and read on another without a pairing barrier, risking observation of a stale or partially-initialized value.

### Finding Description
`ActuatorCreator.getINSTANCE()` performs:
```java
public static ActuatorCreator getINSTANCE() {
    if (ActuatorCreatorInner.instance == null) {
      ActuatorCreatorInner.instance = new ActuatorCreator(StoreFactory.getInstance());
    }
    return ActuatorCreatorInner.instance;
}
``` [1](#0-0) 
The backing field is a plain, non-`volatile` static field:
```java
private static class ActuatorCreatorInner {
    private static ActuatorCreator instance;
}
``` [2](#0-1) 

This is exactly the pattern the CVE describes: a write to a shared pointer/reference (`instance = new ActuatorCreator(...)`) is not paired with a happens-before/read barrier on the reader side. Without `volatile` or `synchronized`, the JVM memory model does not guarantee that:
1. a concurrently-running thread observes the updated (non-null) reference promptly (it may keep reading a stale `null`, similar to the kernel bug re-dereferencing a stale NULL `__scm`), or
2. even if the reference is observed as non-null, that all of the object's non-final fields (`chainBaseManager`, `forkController`) are fully visible/initialized to that thread (reordering/partial-publication hazard) — this is analogous to the kernel driver dereferencing a `__scm` object whose internal state wasn't yet consistently visible.

`getINSTANCE()` is called directly from the hot, unprivileged transaction-execution path in `RuntimeImpl.execute()`, which handles every non-TVM contract type dispatched from a broadcast transaction:
```java
default:
    actuatorList = ActuatorCreator.getINSTANCE().createActuator(context.getTrxCap());
``` [3](#0-2) 
`RuntimeImpl` is invoked for every transaction actuator execution, meaning this code runs concurrently on multiple worker threads that process/validate/execute broadcast transactions in java-tron's block/transaction pipeline, contrasted with `ActuatorCreator.init()`, which performs an unsynchronized plain write of the same field, callable at any time (e.g., during node re-init) with no barrier pairing to readers:
```java
public static void init() {
    ActuatorCreatorInner.instance = new ActuatorCreator(StoreFactory.getInstance());
}
``` [4](#0-3) 

### Impact Explanation
If a race causes `getINSTANCE()` on one thread to observe a stale `null` after another thread has already assigned it (as in the CVE), or to observe a non-null reference to an object whose `chainBaseManager`/`forkController` fields aren't yet visibly initialized, a concurrent transaction-execution thread could:
- throw an NPE while processing a legitimate, unprivileged transaction (denial-of-service to the actuator/execution pipeline — "an API/path the node can no longer serve" for that transaction type), or
- construct an `AbstractActuator` bound to a stale/incorrect `chainBaseManager` or `forkController`, potentially causing an actuator to validate/execute against the wrong chain state or fork-activation view, which in the worst case affects state consistency for a broadcast transaction.

This is a concurrency correctness issue, not a directly exploitable one-shot RCE; its practical blast radius depends on how many `ActuatorCreator` instances get created/re-initialized during a node's lifetime (in the running system `init()`/`getINSTANCE()` are set up largely at startup), which limits realistic exploitability compared to the kernel case (where a NULL SCM pointer deref crashes the kernel on every request path).

### Likelihood Explanation
Low-to-moderate. `ActuatorCreator.init()` and first calls to `getINSTANCE()` typically occur during startup/initialization before the transaction-execution thread pool is fully active, so the race window in a stock deployment is narrow. However, the unsynchronized field is a genuine JMM (Java Memory Model) violation reachable from the unprivileged transaction-execution path (`RuntimeImpl.execute()`), and any future code path or test harness that calls `init()`/`getINSTANCE()` concurrently with in-flight transaction processing (e.g. dynamic reconfiguration, hot-reload, or multiple `ChainBaseManager`/`StoreFactory` initializations in a single process) would hit this race.

### Recommendation
Make the singleton field `volatile` and use standard double-checked locking (or an initialization-on-demand holder / `AtomicReference`) so that writes to `ActuatorCreatorInner.instance` are properly paired with read barriers on `getINSTANCE()`:
```java
private static class ActuatorCreatorInner {
    private static volatile ActuatorCreator instance;
}

public static ActuatorCreator getINSTANCE() {
    ActuatorCreator result = ActuatorCreatorInner.instance;
    if (result == null) {
      synchronized (ActuatorCreator.class) {
        result = ActuatorCreatorInner.instance;
        if (result == null) {
          ActuatorCreatorInner.instance = result = new ActuatorCreator(StoreFactory.getInstance());
        }
      }
    }
    return result;
}
```
Also make `init()` write through the same synchronized/volatile path so re-initialization is safely published to concurrently-running actuator-creation threads.

### Proof of Concept
Concurrency races of this kind are timing-dependent and not deterministically reproducible via a single crafted transaction; a stress test spawning multiple threads that call `ActuatorCreator.init()`/`ActuatorCreator.getINSTANCE()` concurrently with `RuntimeImpl.execute()` invocations (mirroring the existing `TransactionRegisterTest.testConcurrentAccessThreadSafe` pattern used elsewhere in this codebase) can be used to demonstrate visibility/staleness under a memory-model-aware JVM (e.g. via JCStress) or on weakly-ordered architectures, but a guaranteed reproduction cannot be shown without such tooling.
