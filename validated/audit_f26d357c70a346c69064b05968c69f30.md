### Title
Single-signer weight amplification bypasses multisig threshold in `ValidateMultiSign` precompile - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` TVM precompiled contract, exposed to any smart contract via the `validatemultisign(address,uint256,bytes32,bytes[])` call, is intended to verify that the combined weight of *distinct* signers listed in an on-chain `Permission` meets `permission.getThreshold()`. Its duplicate-signature detection is weaker than the equivalent logic in `TransactionCapsule.checkWeight`, and can be bypassed by a single key holder supplying multiple distinct-but-valid signatures over the same hash.

### Finding Description
In `PrecompiledContracts.ValidateMultiSign.execute()` [1](#0-0) , the loop that accumulates weight for each supplied signature does the following for de-duplication:

```
byte[] recoveredAddr = recoverAddrBySign(sign, hash);
sign = merge(recoveredAddr, sign);
if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
  if (ByteArray.matrixContains(executedSignList, sign)) {
    continue;
  }
  MUtil.checkCPUTime();
}
long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
...
totalWeight += weight;
executedSignList.add(sign);
executedSignList.add(recoveredAddr);
```

The `continue` (skip) only happens when the *exact same raw signature bytes* were already seen for that address. If the address was already used but the signature bytes differ — which trivially happens because ECDSA signing normally uses a fresh random nonce each time `sign()` is invoked (or via signature malleability, flipping `s`/`v`) — the code does **not** skip; it merely calls `MUtil.checkCPUTime()` (a CPU-budget check, not a security control) and then falls through to add the recovered signer's weight to `totalWeight` again.

This means one private key can be signed over the same `hash` multiple times, each producing a distinct 65-byte signature that all recover to the same address, and each one will add `weight` again into `totalWeight`. This directly parallels the reported oracle bug pattern (missing canonical/unique-signer check in a threshold-weighted signature aggregation), except here the correct fix (compare by recovered *address*, not raw signature bytes) is already known to be used correctly elsewhere in the codebase — `TransactionCapsule.checkWeight` de-dupes by the recovered address (via `encode58Check(address)`/`addMap`) and throws `PermissionException` on a second signature from the same address [2](#0-1)  — but `ValidateMultiSign` uses a different, weaker dedup keyed on signature bytes plus address.

### Impact Explanation
`ValidateMultiSign` is a general-purpose precompile any deployed smart contract can call to implement on-chain multisig access control (e.g. custody/vault contracts, bridges, DAOs gating a critical operation behind `permission.getThreshold()`). If the threshold is set to require N ≥ 2 independent signers, a single compromised or malicious signer who controls just one key in the permission's key list can synthesize multiple distinct valid signatures over the same message hash (simply by calling `sign()` again, or flipping `s` to `n-s` and `v` accordingly) and pass them all into the `bytes[]` signature array. The precompile will double/triple count that one signer's weight, satisfying `totalWeight >= permission.getThreshold()` and returning `dataOne()` (true) even though no independent second signer actually approved. Any contract relying on this precompile's boolean result to gate fund transfers, ownership changes, or other privileged actions can be unilaterally unlocked by one key — an unauthorized operation / potential theft or loss of funds scenario.

### Likelihood Explanation
Reachable by any unprivileged account: deploy or call a smart contract that invokes the `validatemultisign` precompile with a single signer's multiple distinct signatures over the same hash. No special privileges, node access, or timing conditions are needed — only knowledge of one private key from the target permission's key list and the ability to produce more than one signature over the same digest (a normal capability of any ECDSA signer).

### Recommendation
Change the duplicate-check in `ValidateMultiSign.execute()` to de-duplicate strictly by the **recovered address**, not by the combination of address+raw-signature bytes — mirroring `TransactionCapsule.checkWeight`'s approach of keying on the recovered signer's address and rejecting (or simply skipping without adding weight) any subsequent signature that recovers to an address already counted, regardless of the raw signature bytes.

### Proof of Concept
1. Create an on-chain account with an `Active` permission of `threshold = 2`, containing two keys: `key1` (weight 1) and `key2` (weight 1) — i.e. it should require both signers.
2. As the holder of only `key1`, compute `hash = sha256(address || permissionId || data)`.
3. Sign `hash` twice with `key1` using two independent signing calls (fresh random nonce each time, e.g. `key1.sign(toSign)` invoked twice) to obtain `sig_a` and `sig_b` — two different 65-byte signatures that both `ecrecover` to `key1`'s address.
4. Call the `validatemultisign` precompile (via a TriggerSmartContract call) with `signatures = [sig_a, sig_b]`.
5. Observe: `recoverAddrBySign(sig_a, hash)` and `recoverAddrBySign(sig_b, hash)` both equal `key1`'s address. On the second iteration, `matrixContains(executedSignList, recoveredAddr)` is true but `matrixContains(executedSignList, merge(recoveredAddr, sig_b))` is false (different raw bytes), so the loop does **not** `continue`; it adds `key1`'s weight again. `totalWeight` becomes `1 + 1 = 2 >= threshold(2)`, and the precompile returns `dataOne()` (true) despite only `key1` ever having signed — confirming the single-signer threshold bypass. (This scenario is distinguishable from the existing regression test `ValidateMultiSignContractTest.testDifferentCase`, which only exercises *byte-identical* repeated signatures — `signs.add(Hex.toHexString(key1.sign(toSign).toByteArray())); signs.add(Hex.toHexString(key1.sign(toSign).toByteArray()));` [3](#0-2)  — that test happens to pass with the current signing scheme when it produces byte-identical output, but does not cover the case of two *distinct* valid signatures from the same key, which is the actual exploitable gap.)
