### Title
Missing negative-length validation before array allocation in `ValidateMultiSign` precompile — unhandled `NegativeArraySizeException` on attacker-controlled calldata - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The `ValidateMultiSign` precompiled contract (address `0x...0a`, TVM opcode reachable via any `CALL`/`STATICCALL` from a deployed contract once `allowTvmSolidity059()` is enabled) parses an attacker-controlled signature-array length word from calldata and only bounds-checks it from above, never checking for negativity, before using it to size a Java array. This mirrors the CVE-2017-15931 bug class: an untrusted length/count field is validated against an upper bound but not against being negative, and is then fed directly into an allocation, producing an invalid-size exception.

### Finding Description
`ValidateMultiSign.execute()` reads the byte length from calldata via `DataWord.intValueSafe()` twice: [1](#0-0) 

```java
if (VMConfig.allowTvmSelfdestructRestriction()) {
  int sigArraySize = words[words[3].intValueSafe() / WORD_SIZE].intValueSafe();
  if (sigArraySize > MAX_SIZE) {
    return Pair.of(true, DATA_FALSE);
  }
}
byte[][] signatures = VMConfig.allowTvmSelfdestructRestriction() ?
    extractSigArray(words, words[3].intValueSafe() / WORD_SIZE, rawData) :
    extractBytesArray(words, words[3].intValueSafe() / WORD_SIZE, rawData);
```

The guard `sigArraySize > MAX_SIZE` (`MAX_SIZE = 5`) rejects arrays that are too large, but a negative `sigArraySize` (e.g. `-1`) trivially satisfies `sigArraySize > MAX_SIZE == false` and passes the check. The same unchecked value is then re-read inside `extractSigArray`/`extractBytesArray` and used directly as an array dimension: [2](#0-1) 

```java
private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
  if (offset > words.length - 1) {
    return new byte[0][];
  }
  int len = words[offset].intValueSafe();
  byte[][] bytesArray = new byte[len][];
  ...
}

private static byte[][] extractSigArray(DataWord[] words, int offset, byte[] data) {
  if (offset > words.length - 1) {
    return new byte[0][];
  }
  int len = words[offset].intValueSafe();
  byte[][] bytesArray = new byte[len][];
  ...
}
```

Because `new byte[len][]` with a negative `len` throws `NegativeArraySizeException` (Java's analog of the "negative number leading to invalid memory access" behavior described for the native/ELF case in the CVE), and this call site sits **outside** the `try { ... } catch (Throwable t) { ... }` block that only wraps the later permission-checking logic (`lines 1082-1117`), the exception is not caught inside `ValidateMultiSign.execute()` and propagates to the caller.

By contrast, the sibling precompile `BatchValidateSign` has the exact same unchecked-negative-length pattern but wraps its whole `doExecute(data)` call in a `try { ... } catch (Throwable t)` at the `execute()` level: [3](#0-2) 

so it degrades gracefully to `Pair.of(true, new byte[WORD_SIZE])`. `ValidateMultiSign` lacks this protection.

### Impact Explanation
Any account that can deploy a contract and issue a `CALL`/`STATICCALL` to the `ValidateMultiSign` precompile address with crafted calldata (specifically making `words[3]` reference a word whose low 32 bits form a negative signed `int`, e.g. `0xFFFFFFFF`) triggers an uncaught `NegativeArraySizeException` inside the precompile execution path. Whether this fully escalates to a node crash/halt depends on exception handling further up the TVM/Program call chain (e.g., in `Program`'s precompile invocation or the transaction executor), which was not fully confirmed within this investigation — this is the main residual uncertainty. At minimum, it is a concrete, unhandled-exception defect diverging from the intended "reject and return false" behavior that the upper-bound check was clearly meant to provide, and if any code path in block/transaction application does not generically catch `RuntimeException`/`Throwable` around this precompile call, it would result in transaction processing failure or worse.

### Likelihood Explanation
High reachability: the precompile is invocable by any unprivileged contract deployer once `allowTvmSolidity059()` (already enabled in mainnet history) is active, requiring only a single crafted transaction calling the precompile with a manipulated offset/length word — no special privileges needed.

### Recommendation
Add an explicit negative check alongside the existing upper-bound check in `ValidateMultiSign.execute()` (and defensively in `extractSigArray`/`extractBytesArray`/`extractBytes32Array`), e.g. `if (sigArraySize > MAX_SIZE || sigArraySize < 0) return Pair.of(true, DATA_FALSE);`, and wrap the extraction calls at lines 1072-1074 in the same try/catch that already exists for the permission logic (matching `BatchValidateSign`'s defensive pattern).

### Proof of Concept
Craft calldata for `validatemultisign(address,uint256,bytes32,bytes[])` where the `bytes[]` offset/head word at `words[3]` is manipulated so that the pointed-to length word decodes (via `intValueSafe()`) to a negative 32-bit value (e.g., word value ending in `...FFFFFFFF`). Submitting a transaction that `CALL`s the `ValidateMultiSign` precompile (`0x000...00a`) with this data causes `extractSigArray`/`extractBytesArray` to execute `new byte[-1][]`, throwing `NegativeArraySizeException` outside of any local catch block in `ValidateMultiSign.execute()`.
