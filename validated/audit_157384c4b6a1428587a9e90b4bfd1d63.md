### Title
NAV Computation DoS via Curated Loan List Inflation - ([File: tare-io__tare-contracts/contracts/PortfolioVault.sol])

### Summary
The `PortfolioVault` contract calculates its Net Asset Value (NAV) by iterating over a curated list of loan IDs (`_navLoanIds`). This computation is paginated but must complete within a specific time window defined by `maxNavComputationTime`. If the number of loans in the curated list grows sufficiently large, the time required to complete the multi-batch computation may exceed `maxNavComputationTime`, causing the process to restart indefinitely. Since critical vault operations like `approveDeposit` and `approveRedemption` require a recently finalized (fresh) NAV, the vault can be placed into a permanent DoS state where no deposits or redemptions can be processed. [1](#0-0) [2](#0-1) 

### Finding Description
The `PortfolioVault` uses an asynchronous, multi-transaction process to update its NAV via the `updateNav` function. [3](#0-2) 

The system implements several "restart" conditions for this computation:
1. If the vault's NFT holdings change (detected via `ownershipNonce`). [4](#0-3) 
2. If the NAV calculator configuration changes. [5](#0-4) 
3. If the time elapsed since the start of the computation exceeds `maxNavComputationTime`. [6](#0-5) 

If any of these occur, `navCursor` and `pendingNav` are reset to 0. [7](#0-6) 

The vulnerability arises because the `PORTFOLIO_MANAGER` can add an unlimited number of loans to the `_navLoanIds` list via `addLoansToNav`. [8](#0-7)  If the list grows to a point where the total gas or number of transactions required to iterate through the entire list cannot be completed before `block.timestamp - navStart > maxNavComputationTime`, the NAV will never finalize. Furthermore, any operation that bumps the `ownershipNonce` (like acquiring a single new loan) will also trigger a full restart. [9](#0-8) 

### Impact Explanation
This is a **Material production DoS**. A finalized NAV is a strict prerequisite for `approveDeposit` and `approveRedemption`. [10](#0-9) [11](#0-10)  If NAV cannot be finalized, investor capital becomes trapped in the `pendingDepositAssets` state (unless they cancel), and shareholders cannot have their redemption requests approved, effectively locking their funds in the vault. [12](#0-11) [13](#0-12) 

### Likelihood Explanation
The likelihood is medium. While it requires a large number of loans, the protocol is designed for "institutional-grade private credit" and explicitly mentions "thousands of loans". [14](#0-13)  As the portfolio scales, the window for successful NAV finalization narrows. If the `maxNavComputationTime` is set too low relative to the portfolio size and network congestion/latency, the system will naturally halt.

### Recommendation
1. Implement a `maxLoansInNav` cap to ensure the curated list cannot exceed a size that is computationally feasible within the timeout.
2. Modify the restart logic to be more granular; for example, allow the computation to continue if a loan is added, only re-valuing the newly added loan rather than restarting the entire set.
3. Ensure `maxNavComputationTime` is dynamically or carefully calibrated against the actual number of loans in the `_navLoanIds` list.

### Proof of Concept
1. A `PORTFOLIO_MANAGER` populates the vault with 5,000 loans and adds them all to the NAV list via `addLoansToNav`.
2. The `maxNavComputationTime` is configured to 1 hour (3600 seconds).
3. Due to the gas limits per block and the need for multiple transactions to process 5,000 loans (calling `updateNav` repeatedly), the total time taken to reach the end of the list exceeds 3600 seconds.
4. On the final batch call to `updateNav`, the condition `block.timestamp - navStart > maxNavComputationTime` evaluates to true. [6](#0-5) 
5. The vault resets `navCursor = 0`, discarding all progress. [15](#0-14) 
6. The vault is now unable to finalize NAV, blocking all deposits and redemptions.

The Portfolio Vault enables funds to gain exposure to a portfolio of loans originated on Tare's platform through a single ERC20 share token. Shareholders deposit USDC into the vault, which uses those funds to purchase loans from Tare SPV (initial investor for all loans created). The vault becomes the `investor` for each acquired loan by owning the loan NFT, and receives principal and interest distributions as borrowers make payments.

## Design Goals

- **Simplicity**: While more complex, feature-rich solutions exist we want to keep this vault as simple as possible. That means no epoch calculation, cross-chain capabilities or management/performance fees charged by the vault
- **Liquidity Management**: Fully asynchronous deposit and redemption flows enable a fund to easily own thousands of loans via a simple ERC20 token
