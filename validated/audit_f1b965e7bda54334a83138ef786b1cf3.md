### Title
Unrecoverable Underflow Panic in `accrue()` Bricks Vault and All Market Operations for an Asset - ([File: mainnet/contracts/vault/v0-vault-stx.clar])

### Summary
Every state-mutating vault function (`deposit`, `redeem`, `transfer`, `system-borrow`, `system-repay`, etc.) unconditionally calls `accrue()` before doing anything else, exactly like `Safe.execTransaction()` unconditionally calling the `guard`. `accrue()` computes a treasury‑share mint using an unchecked subtraction `(- (total-assets-preview) reserve-inc)`. If `reserve-inc` (the reserve‑factor cut of newly accrued interest) ever equals or exceeds `total-assets-preview`, this subtraction underflows and Clarity aborts the transaction with a runtime panic. Because `accrue()` is re-executed identically on every future call using the same persisted state, this failure is permanent — the vault (and every `market.clar` operation that touches that asset, via `accrue-and-cache`/`vault-accrue`) is bricked forever, with no way for anyone — including the DAO — to recover it, because the only mitigation path (`set-pause-states` pausing `accrue`) itself calls `(try! (accrue))` first when transitioning into the paused state.

### Finding Description
`accrue()` in the vault contracts performs, unconditionally, on every call: [1](#0-0) 

```
(reserve-inc (mul-div-down debt-delta (var-get fee-reserve) BPS))
(treasury-lp (if (> reserve-inc u0) (mul-div-down reserve-inc (total-supply) (- (total-assets-preview) reserve-inc)) u0))
```

`total-assets-preview` is bounded below by outstanding `total-debt` (available liquidity can be redeemed down to zero, but the borrowed/outstanding principal cannot, since `redeem` is gated by `available-assets`): [2](#0-1) 

`debt-delta` is the newly accrued interest since the last `accrue()` call, which compounds via `next-index`/`next-liquidity-index` based on elapsed time and the configured borrow rate. If `accrue()` is not invoked for a sufficiently long interval (e.g. low activity on an asset, or simply an attacker driving utilization high and then waiting), the compounding multiplier can grow large enough that `debt-delta`, and hence `reserve-inc = debt-delta * fee-reserve / BPS`, exceeds `total-assets-preview`. At that point `(- (total-assets-preview) reserve-inc)` underflows and the transaction panics.

Because this computation is deterministic and depends only on already-persisted state (`principal-scaled`, `index`, `lindex`, `last-update`, `assets`), **every subsequent call to `accrue()` will re-derive the same (or a worse) underflow** — the vault is permanently bricked. This function is invoked as the first step of `deposit`, `redeem`, `transfer`, `system-borrow`, `system-repay` and via `market.clar`'s `accrue-and-cache`/`vault-accrue` for oracle price resolution, health checks, and liquidations: [3](#0-2) [4](#0-3) 

Critically, the only designed "escape hatch" — the DAO pausing `accrue` via `set-pause-states` — itself calls `accrue()` first when transitioning from unpaused to paused, so it also panics and cannot be used to recover the vault: [5](#0-4) 

This directly mirrors the referenced report's bug class: a mandatory pre-check/hook executed on every privileged and unprivileged path (the Safe `guard`) that, once broken, reverts all transactions including the very transaction meant to disable/fix it (disabling modules before setting a broken guard), permanently freezing funds with no recovery route.

### Impact Explanation
Once triggered, every user's collateral and liquidity supplied to that vault becomes permanently inaccessible: deposits, redemptions, borrows, repayments, liquidations, and price resolution for that asset in `market.clar` all revert forever, since they all route through `accrue()`. This is a permanent freezing of funds for all users of that vault/asset, not merely temporary, and DAO governance has no working remediation path since even the pause transition itself calls the panicking function. This lands squarely in the Critical impact class ("permanent freezing of funds").

### Likelihood Explanation
Reaching this state does not require any privileged action or DAO compromise — it only requires normal usage: an ordinary borrower/lender driving utilization on an asset high, and then either the natural passage of time (staleness of `accrue`) or a period of low interaction, causing accrued interest (and thus `reserve-inc`) to overtake the shrinking `total-assets-preview` floor set by outstanding debt. An attacker can accelerate this deliberately by maximizing borrow utilization on a vault (borrowing up to `cap-debt`) and then simply waiting or minimizing calls to `accrue` before triggering it with a normal `deposit`/`redeem`/`borrow` call from an unprivileged EOA or their own contract — no leaked keys or DAO action needed.

### Recommendation
Replace the unchecked subtraction in the `treasury-lp` calculation with a saturating/bounded computation (e.g., clamp `reserve-inc` to `total-assets-preview`, or use `(if (>= total-assets-preview reserve-inc) (mul-div-down reserve-inc (total-supply) (- total-assets-preview reserve-inc)) u0)`), so that pathological interest-accrual states cannot cause an unrecoverable panic. Additionally, ensure the pause-transition logic (`set-pause-states`) does not depend on a successful call to `accrue()`, so the DAO retains a guaranteed recovery path independent of vault-internal accounting invariants.

### Proof of Concept
1. Attacker (or any user) borrows up to `cap-debt` on a vault (e.g. `vault-stx`), driving `total-borrowed`/`principal-scaled` high relative to `assets`.
2. Attacker/other suppliers redeem all currently available (non-borrowed) liquidity, driving `assets` down toward the outstanding debt floor.
3. Time passes without any transaction touching this vault (or attacker repeatedly forces the interest rate curve to a high value at high utilization) so that `next-index`/`next-liquidity-index` compound significantly, producing a large `debt-delta` on the next `accrue()` call.
4. Any subsequent call to `deposit`, `redeem`, `system-borrow`, `system-repay`, or `market.clar`'s health-check/price-resolution path that calls `accrue()`/`vault-accrue` computes `reserve-inc >= total-assets-preview`, causing `(- (total-assets-preview) reserve-inc)` to underflow and the transaction to panic.
5. Every future call to any of these functions re-derives the identical underflow from persisted state, permanently bricking the vault. The DAO's only mitigation, `set-pause-states` pausing `accrue`, itself calls `accrue()` first and also panics, leaving no recovery path.
