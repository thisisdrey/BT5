### Title
Unauthenticated durable-nonce dedup eviction allows unbounded griefing of victim's legitimate nonce transaction - (File: core/src/banking_stage/transaction_scheduler/receive_and_buffer.rs, core/src/banking_stage/transaction_scheduler/transaction_state_container.rs)

### Summary
The scheduler's nonce-dedup logic in `handle_packet_batch_message` keeps only one buffered transaction per durable-nonce address, evicting the lower-priority one via `TransactionStateContainer::remove_by_id` whenever a new transaction references the same nonce address with higher priority. Because the nonce-address extraction used to key this dedup (`validated_nonce_address`) is purely structural (derived from the `AdvanceNonceAccount` instruction's account list) and is not checked against the real on-chain nonce authority, an attacker can forge a self-signed, sigverify-passing "nonce-shaped" transaction that names the victim's nonce account but uses the attacker's own key as the (bogus) nonce authority — a transaction guaranteed to fail at execution — yet still wins the dedup priority race and permanently evicts the victim's genuine, executable nonce transaction from the buffer.

### Finding Description
`TransactionStateContainer` tracks one active priority id per nonce address in `nonces_in_use: HashMap<Pubkey, TransactionPriorityId, ..>` and exposes `get_nonce_transaction_priority_id` / `set_nonce_transaction_priority_id` for consumers to update/query it [1](#0-0) . `remove_by_id` unconditionally deletes both the map entry and the queue entry for a given `TransactionId`, and the cleanup in `remove_state` only touches `nonces_in_use` when the currently tracked priority id for the address matches the one being removed [2](#0-1) [3](#0-2) .

`handle_packet_batch_message` in `receive_and_buffer.rs` uses these primitives together with a `num_evicted_on_nonce_dedup` metric and `existing_nonce_priority_id` lookups to implement "only keep the highest-priority transaction per nonce address" semantics — when a new nonce-referencing transaction arrives with higher priority than the one currently registered for that address, the previously-registered (lower priority) transaction is evicted via `container.remove_by_id(...)` [4](#0-3) .

The root problem is that this dedup keying is computed purely from the *shape* of the instruction (which account is being advanced) rather than from verified on-chain state (who the real nonce authority is). The `AdvanceNonceAccount` instruction only requires that whichever pubkey is designated as "nonce authority" in the account-meta list be a signer of the transaction — it does not require that pubkey to be the actual authority recorded in the nonce account's on-chain state; that check only happens later, at bank execution time. Consequently, an attacker who does not hold the victim's nonce authority key can still:
1. Construct an `AdvanceNonceAccount` instruction whose "nonce account" field is the victim's real (public) nonce pubkey, and whose "nonce authority" field is the attacker's own pubkey.
2. Sign the transaction entirely with their own keypair — this satisfies Ed25519 sigverify since every required signer key is one they control.
3. Attach a higher priority fee than the victim's genuine nonce transaction.

This transaction passes sigverify (no invalid signatures) and reaches `handle_packet_batch_message`, which extracts the nonce address from the instruction, finds `existing_nonce_priority_id` already registered for the victim's transaction, and evicts it via `container.remove_by_id`, incrementing `num_evicted_on_nonce_dedup`. The attacker's transaction is certain to fail at bank execution (invalid nonce authority signer check), but that failure occurs long after the victim's transaction has already been discarded from the buffer. The attacker can repeat this indefinitely with monotonically increasing priority against every retry of the victim's transaction.

### Impact Explanation
This falls under the stated "buffer eviction correctness" / fee-paying-transaction stranding category. A completely unprivileged, unstaked attacker who merely knows the victim's public nonce account address (on-chain, public data) can permanently and repeatedly prevent the victim's valid, fee-paying durable-nonce transaction from ever being scheduled, without needing the nonce authority key, stake, or any privileged access — a targeted denial-of-service against a specific user's nonce-based transactions.

### Likelihood Explanation
Feasibility is high: the attacker only needs (a) the victim's nonce account pubkey, which is public, and (b) the ability to sign an arbitrary transaction with their own key that structurally references that account in an `AdvanceNonceAccount` instruction — no special privilege or authority is required. The attack is trivially repeatable each scheduling pass, since the attacker can always outbid the victim's priority and resubmit after eviction.

### Recommendation
Do not use unauthenticated, purely structural nonce-address extraction as the dedup key for evicting buffered transactions. Before evicting an existing nonce-tracked transaction, verify (or at minimum weight the decision by) whether the newly-arriving transaction's declared nonce authority actually matches the currently known on-chain nonce authority for that account (a cheap bank/account read), or defer eviction until execution confirms the new transaction's nonce validity. Alternatively, only allow dedup-eviction among transactions from the account that also holds write-lock priority under standard account-lock contention rules, rather than unconditionally deleting the buffer entry outright.

### Proof of Concept
Integration test outline (extending `test_receive_and_buffer_nonce_capacity_eviction`-style tests in `receive_and_buffer.rs`):
1. Create a real durable nonce account `N` with authority `victim_authority`.
2. Submit `victim_tx`: valid `AdvanceNonceAccount(N, victim_authority)` transaction signed by `victim_authority`, priority = `P0`. Assert it is buffered and `set_nonce_transaction_priority_id(N, victim_id)` is set.
3. Craft `attacker_tx`: `AdvanceNonceAccount(N, attacker_authority)` where `attacker_authority` is a keypair fully controlled by the attacker (not the real nonce authority), signed entirely by the attacker, priority = `P1 > P0`.
4. Feed `attacker_tx` through `handle_packet_batch_message`. Assert `container.remove_by_id` is invoked for `victim_id`, `victim_tx` is no longer retrievable via `container.get_transaction(victim_id)`, and `num_evicted_on_nonce_dedup` incremented.
5. Repeat steps 2–4 in a loop with increasing attacker priorities, confirming the victim's freshly resubmitted transaction is evicted every cycle and never reaches scheduling/consumption, while the attacker's transactions would each fail at bank execution (invalid nonce authority) if actually processed.

    fn remove_state(&mut self, id: TransactionId) -> TransactionPriorityId {
        let state = self.id_to_transaction_state.remove(id);
        let priority_id = TransactionPriorityId::new(state.priority(), id);

        if let Some(nonce_address) = state.nonce_address()
            && let Entry::Occupied(entry) = self.nonces_in_use.entry(*nonce_address)
            && *entry.get() == priority_id
        {
            entry.remove();
        }

        priority_id
    }
