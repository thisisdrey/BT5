### Title
On-chain Bancor-formula Exchange (`ExchangeTransactionContract`) is vulnerable to sandwich attacks via mempool-visible order/price-impact monitoring - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java`)

### Summary
java-tron implements a fully on-chain, deterministic Bancor-formula AMM (`ExchangeCreateContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract`/`ExchangeTransactionContract`) reachable by any unprivileged account through the wallet HTTP/gRPC API. Because trade execution price is a pure deterministic function of the current pool balances at execution time, and pending transactions (including their `token_id`/`quant`/`expected` parameters) are publicly visible in the mempool/pending pool before block inclusion, any account can front-run and back-run a victim's `ExchangeTransactionContract` to extract value from the victim's price impact — the same "monitor pending order, sandwich, profit from slippage" bug class described in the Dinari `OrderProcessor` report.

### Finding Description
`ExchangeTransactionActuator.execute` calls `exchangeCapsule.transaction(tokenID, tokenQuant, ...)`, which mutates the pool's `firstTokenBalance`/`secondTokenBalance` using the constant-formula processor in `ExchangeProcessor`/`SafeExchangeProcessor.exchange` [1](#0-0) . The only user protection against price movement is the `expected` field, and `doValidate()` only requires `tokenExpected > 0` — i.e., users can supply a trivially low `expected` value, and even users who set a "reasonable" slippage bound remain exposed to value extraction up to that bound [2](#0-1) . The `ExchangeTransactionContract` is submitted like any ordinary transaction through the wallet HTTP servlet (`/wallet/exchangetransaction`) or gRPC `Wallet.ExchangeTransaction`, so it sits in the node's pending-transaction pool prior to block inclusion, exactly like the Dinari `OrderRequested` event exposure [3](#0-2) [4](#0-3) . A malicious block producer or a well-connected node operator (an ordinary order-placer/broadcaster, not a validator role) can observe a pending large `ExchangeTransactionContract`, submit a front-run trade on the same exchange pair with higher priority, let the victim's trade execute against the now-skewed pool, then submit a back-run trade to capture the price differential — analogous to steps 1–3 in the report.

### Impact Explanation
A successful sandwich yields concrete, unbacked-fund-style value transfer: the attacker's TRX/TRC10 balance increases while the victim receives strictly less output than the unperturbed pool price would have given, up to their `expected` slippage tolerance. This is a direct, unauthorized-account-operation-adjacent financial loss for arbitrary order placers using the exchange feature, reachable purely by broadcasting ordinary signed transactions — matching the rule's requirement of "concrete... theft... of funds" reachable by an unprivileged transaction broadcaster/order placer.

### Likelihood Explanation
Likelihood is constrained by real-world usage: the TRX/TRC10 Bancor exchange is a legacy feature largely superseded by the `MarketSellAsset` order-book contracts, so liquidity/usage may be low, reducing profitable sandwich opportunities. However, the mechanism itself is unconditionally exploitable whenever an exchange pool has any liquidity and a victim submits a non-trivial trade, requiring no special privilege beyond normal transaction broadcasting.

### Recommendation
Apply the same mitigations proposed in the source report, adapted to java-tron's exchange: enforce tighter/more meaningful slippage bounds (e.g., require `expected` to reflect a bounded percentage rather than merely `>0`), consider batching or delaying settlement of `ExchangeTransactionContract` within a block, or migrate remaining exchange liquidity/usage to the order-book-based `MarketSellAssetContract` mechanism which is less susceptible to instantaneous price-impact sandwiching. Tightening the `doValidate` check in `ExchangeTransactionActuator` to reject trivial `expected` values would reduce (but not eliminate) exposure.

### Proof of Concept
1. Attacker monitors the pending transaction pool for a large `ExchangeTransactionContract` against exchange `exchangeId` (visible via node's pending-pool or gRPC broadcast).
2. Attacker submits their own `ExchangeTransactionContract` selling `tokenID` for `anotherTokenID` with high fee/priority so it lands in the same or an earlier block, shifting `firstTokenBalance`/`secondTokenBalance` in `ExchangeCapsule.transaction` [5](#0-4)  unfavorably against the victim.
3. Victim's original `ExchangeTransactionContract` executes at the worsened price, still passing validation as long as `anotherTokenQuant >= tokenExpected` [6](#0-5) .
4. Attacker immediately submits a reverse `ExchangeTransactionContract` to sell back into the pool at the now-improved price, realizing profit equal to the victim's price impact.

    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;

      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
