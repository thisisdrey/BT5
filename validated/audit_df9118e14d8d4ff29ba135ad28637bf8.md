Confirmed root cause. In `ValidateMultiSign.execute()` (and similarly `BatchValidateSign.doExecute()`), the `isValidAbiEncoding` guard only validates that the calldata's total length is a legal multiple of the ABI shape — it never validates that the *dynamic offset fields themselves* (`words[3]` for `ValidateMultiSign`, `words[1]`/`words[2]` for `BatchValidateSign`) point to an index within the `words[]` array. An attacker who calls the precompile at address `0x...0a` (or `0x...09`) with crafted calldata can set `words[3]` (the ABI offset to the `bytes[]` signatures array) to an arbitrary large value. `words[3].intValueSafe() / WORD_SIZE` is then used directly as an index into `words[]` at:

```java
int sigArraySize = words[words[3].intValueSafe() / WORD_SIZE].intValueSafe();
```

This line sits **outside** the `try { ... } catch (Throwable t)` block that wraps the rest of the method, so an out-of-range offset throws an uncaught `ArrayIndexOutOfBoundsException` from `execute()`.

### Title
Unchecked ABI offset field causes uncaught ArrayIndexOutOfBoundsException in ValidateMultiSign precompile - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`ValidateMultiSign.execute()` (`PrecompiledContracts.java:1052-1120`) trusts an attacker-supplied ABI offset word (`words[3]`) as a direct array index into `words[]` without bounds-checking it, exactly mirroring the batman-adv `eth_hdr` bug class: a field is read from untrusted, variable-length input under the assumption that the caller already validated accessibility, but no caller in this path actually does so before the read.

### Finding Description
`isValidAbiEncoding(rawData, ABI_HEADER_WORDS, ABI_ITEM_WORDS)` [1](#0-0)  only checks that `data.length` is 32-byte aligned and that the tail is a nonzero multiple of `itemWords*32`. It never inspects the *value* of any ABI offset word.

`ValidateMultiSign.execute()` then computes an index directly from attacker data and dereferences `words[]` with it before entering the method's only `try/catch`: [2](#0-1) 

`words[3].intValueSafe()` can be any value the caller places in calldata (up to `Integer.MAX_VALUE`); dividing by `WORD_SIZE` still yields an arbitrary index that is very likely to exceed `words.length - 1`. Unlike `extractBytesArray`/`extractSigArray`, which explicitly guard with `if (offset > words.length - 1) return new byte[0][];` [3](#0-2)  and [4](#0-3) , the inline read at line 1067 has no such guard, and `BatchValidateSign`'s analogous inline reads at lines 1166-1167 have the same gap (guarded only when `VMConfig.allowTvmSelfdestructRestriction()` is enabled, and even then the guard itself performs the same unchecked index).

The `ArrayIndexOutOfBoundsException` thrown at line 1067 propagates out of `execute()` uncaught by anything inside `PrecompiledContracts.java`.

### Impact Explanation
Whether this constitutes real, node-affecting impact depends entirely on how `Program.callToPrecompiledAddress` handles exceptions thrown by a precompile's `execute()`. The repository's own test suite (`OperationsTest.testTip854OuterFrameContainment`) explicitly exercises this exact scenario for both `ValidateMultiSign` and `BatchValidateSign` and asserts the outer CALL frame is unaffected and no exception is inherited by `program.getResult()` [5](#0-4) . This strongly indicates that a general containment mechanism already exists at the `Program`/opcode dispatch layer (TIP-854) that converts such runtime exceptions from a precompiled CALL into a normal "push 0" failure result rather than a VM/node crash. I was not able to fully trace `Program.callToPrecompiledAddress`'s exception-handling implementation within the available context to confirm this containment covers the *inline pre-try-catch* read path (line 1067) specifically versus only the guarded/tested calldata-length rejection path (`isValidAbiEncoding` returning false). If containment does apply uniformly to any exception thrown during a precompiled CALL, then this is at most a contract-execution revert/false-result with no node crash or fund impact — i.e., not exploitable beyond normal EVM-call failure semantics. If it does not apply to this specific uncaught AIOOBE (as opposed to the guarded rejection paths the tests target), it could propagate further up the transaction-execution stack and cause a per-transaction/node processing exception.

### Likelihood Explanation
Triggering the vulnerable code path only requires an unprivileged, unsigned-permission smart-contract call (constant or state-changing) to precompile address `0x...0a` with `VMConfig.allowTvmSelfdestructRestriction()` enabled and a crafted `words[3]` offset — trivially reachable by any contract deployer or caller once the TIP is active. However, given the demonstrated existing TIP-854 hardening and dedicated regression tests around malformed calldata for this exact contract, likelihood of this being an *unpatched, impactful* issue is low to moderate; it may already be fully contained by the outer-frame exception handling.

### Recommendation
Add an explicit bounds check before dereferencing `words[]` with an ABI-derived offset at `PrecompiledContracts.java:1067` and the equivalent lines in `BatchValidateSign` (1166-1167), mirroring the existing `if (offset > words.length - 1)` guard used in `extractBytesArray`/`extractSigArray`, so that out-of-range offsets are rejected via `Pair.of(true, DATA_FALSE)` instead of relying on exception propagation and containment elsewhere. This closes the gap even if the outer-frame containment already mitigates crash risk, removing dependence on exception-based control flow for a security boundary.

### Proof of Concept
1. Enable `VMConfig.allowTvmSelfdestructRestriction()`.
2. Craft `rawData` for `validatemultisign(address,uint256,bytes32,bytes[])` such that:
   - Total length passes `isValidAbiEncoding` (32-byte aligned, tail = `5 * 32` for one dummy item), and
   - `words[3]` (the tuple's "offset to bytes[]" field) is set to a large value, e.g. `0xFFFFFFF0`, so `words[3].intValueSafe() / WORD_SIZE` exceeds `words.length - 1`.
3. Deploy a contract that performs `staticcall`/`call` to precompile address `0x...0a` with this payload.
4. Observe that `PrecompiledContracts.java:1067` throws `ArrayIndexOutOfBoundsException` before reaching the method's `try/catch`, and determine (via node logs / actual behavior, not verifiable from this index alone) whether the exception is safely converted to a call failure by the outer TIP-854 containment or propagates further.
