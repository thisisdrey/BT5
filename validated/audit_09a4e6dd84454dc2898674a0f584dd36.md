Audit Report

## Title
Unbounded-slippage AMM swap in `SwapFirstAssetTrader::refund_weight` (missing `amount_out_min`) - (File: `cumulus/primitives/utility/src/lib.rs`)

## Summary
`SwapFirstAssetTrader::refund_weight` converts the leftover `Target` fee credit back into the original fee-payment asset by calling `SwapCredit::swap_exact_tokens_for_tokens(vec![Target::get(), refund_swap_asset], refund, None)` with `amount_out_min` hardcoded to `None`, disabling the slippage-bound check the underlying pallet otherwise enforces. This lets a pool-price shift between `buy_weight` and `refund_weight` silently reduce the amount refunded to the fee payer, with no error raised.

## Finding Description
`buy_weight` swaps a user's non-`Target` fee asset into `Target` via `swap_tokens_for_exact_tokens`, holding any surplus in `self.total_fee` [1](#0-0) . When unused weight is later refunded, `refund_weight` swaps a portion of that `Target` credit back to the original asset:
```
SwapCredit::swap_exact_tokens_for_tokens(vec![Target::get(), refund_swap_asset], refund, None)
``` [2](#0-1) 

The `Swap`/`SwapCredit` trait's `amount_out_min` parameter exists precisely to enforce a slippage floor, and the pallet implementation (`do_swap_exact_credit_tokens_for_tokens`, reached via `SwapCredit::swap_exact_tokens_for_tokens`) checks `amount_out >= amount_out_min` only `if amount_out_min.is Some(..)` [3](#0-2) . The trait itself documents this: "If `amount_out_min` is provided and the swap can't achieve at least this amount, an error is returned" [4](#0-3) . Passing `None` disables that guard entirely for this specific refund leg — any pool output, however small, is accepted as valid.

`SwapFirstAssetTrader` is not test-only scaffolding; it is wired as the `WeightTrader` in production runtime configs, confirmed present in `cumulus/parachains/runtimes/assets/asset-hub-rococo/src/xcm_config.rs`, `cumulus/parachains/runtimes/assets/asset-hub-westend/src/xcm_config.rs`, and `cumulus/parachains/runtimes/testing/penpal/src/xcm_config.rs`.

## Impact Explanation
If the `(Target, refund_swap_asset)` pool price moves unfavorably between `buy_weight` and `refund_weight` for the same XCM message (e.g., another public swap extrinsic against the same pool executes in between), the refund conversion accepts an arbitrarily bad rate with no failure. This is an underpriced-settlement bug: value that should be returned to the fee payer is captured by whoever moved the price, and the wrong (understated) refund `amount_out` is settled to the beneficiary. This matches the required invariant that asset conservation and settlement amount/beneficiary correctness must hold for fee-refund credit flows.

## Likelihood Explanation
`SwapFirstAssetTrader::buy_weight`/`refund_weight` execute automatically and unprivileged for any XCM message paying fees in a non-`Target` asset — no admin, governance, or validator privilege is required. The attacker only needs to submit an ordinary, public `swap_exact_tokens_for_tokens`/`swap_tokens_for_exact_tokens` extrinsic against the same `(Target, refund_swap_asset)` pool in temporal proximity to skew the price. Every other swap call site in this same file and in the pallet threads a `Some(..)` bound (`buy_weight`'s own `swap_tokens_for_exact_tokens` call uses `fee` as an exact-output target with implicit bound via `amount_in_max` semantics, and the public extrinsics/precompiles require explicit `amount_out_min`); only this refund leg hardcodes `None`.

## Recommendation
Compute a bounded `amount_out_min` for the refund swap using `QuotePrice::quote_price_exact_tokens_for_tokens` (which `SwapFirstAssetTrader` already depends on) with an acceptable tolerance, and treat a resulting `ProvidedMinimumNotSufficientForSwap` error as a failed partial refund (skip/return `None`) rather than accepting whatever amount the pool yields.

## Proof of Concept
1. Configure a runtime with `SwapFirstAssetTrader<Target, SwapCredit = pallet_asset_conversion::Pallet<T>, ...>` as `WeightTrader` (as in `asset-hub-westend`/`asset-hub-rococo`/`penpal` xcm_config).
2. Create an `AssetConversion` pool for `(Target, ClientAsset)`.
3. Submit an XCM message paying fees in `ClientAsset`; `buy_weight` swaps into `Target` via `swap_tokens_for_exact_tokens`, leaving excess `total_fee` credit to be refunded.
4. Before `refund_weight` executes for that message, submit a public `swap_exact_tokens_for_tokens`/`swap_tokens_for_exact_tokens` extrinsic that skews the `(Target, ClientAsset)` pool ratio.
5. `refund_weight` calls `SwapCredit::swap_exact_tokens_for_tokens(vec![Target, ClientAsset], refund, None)` and accepts the skewed rate — the refunded `ClientAsset` amount is below fair value and `Error::ProvidedMinimumNotSufficientForSwap` is never triggered because `amount_out_min` is `None`.
