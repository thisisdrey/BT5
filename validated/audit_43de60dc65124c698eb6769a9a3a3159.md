### Title
Accrued debt can exceed mintable synthetic supply and permanently block full repayment - ([File: contracts/DebtToken.sol](https://github.com/Kohvert/metronome-synth-public--001/blob/main/contracts/DebtToken.sol))

### Summary
`DebtToken.accrueInterest()` increases `totalSupply_` and `debtIndex` before attempting to mint the corresponding synthetic tokens to the fee collector. [1](#0-0) 

If that mint fails, the debt remains accrued and is only recorded as `pendingInterestFee`. [2](#0-1) 

`SyntheticToken._mint()` rejects any mint that would make `totalSupply` exceed `maxTotalSupply`. [3](#0-2) 

Therefore, once synthetic supply reaches its cap, any subsequent interest accrual creates user debt for which no repayment asset exists. [4](#0-3) [3](#0-2) 

The mainnet msBTC configuration sets both the synthetic token cap and debt token cap to `16e18`, while the debt token has a nonzero 1% interest rate. [5](#0-4) [6](#0-5) 

### Finding Description
`DebtToken.issue()` is publicly reachable and records the requested gross amount as debt before minting the same gross synthetic amount, split between the borrower and fee collector. [7](#0-6) [8](#0-7) 

An unprivileged user with sufficient collateral can therefore issue enough debt-backed synths to consume the entire synthetic-token supply cap. [9](#0-8) 

After the cap is reached, anyone can call the unauthenticated `accrueInterest()` function once the timestamp advances. [10](#0-9) 

The function adds the accrued interest to debt supply and the account debt index, but the matching fee-collector mint reverts inside `SyntheticToken._mint()` because the supply cap is exhausted. [11](#0-10) [3](#0-2) 

The catch block preserves the higher debt instead of reverting the accrual, so `debtToken.totalSupply()` becomes greater than `syntheticToken.totalSupply()`. [2](#0-1) [12](#0-11) 

`repayAll()` first accrues this unminted interest, then requires the payer to burn synthetic tokens equal to the full updated debt balance. [13](#0-12) 

Even if all outstanding synthetic tokens are consolidated and burned, the aggregate debt remains equal to the unminted `pendingInterestFee`, leaving the last portion of debt mathematically unpayable. [14](#0-13) [15](#0-14) 

The problem is not prevented by `DebtToken.maxTotalSupply`, because that cap is checked only when minting new principal and is bypassed by interest accrual. [16](#0-15) 

### Impact Explanation
This breaks the repayment-supply invariant that every unit of debt must be backed by a mintable synthetic token that can be burned. [17](#0-16) [15](#0-14) 

At full synthetic supply, debtors collectively owe more tokens than can ever exist, so some collateral backing the residual debt cannot be recovered through repayment. [11](#0-10) [3](#0-2) 

For the equal-cap msBTC configuration, a borrower that issues the full `16e18` supply will owe `16e18 + interest` after accrual while only `16e18` msBTC exists. [5](#0-4) [6](#0-5) 

`collectPendingInterestFee()` cannot immediately resolve the state because it also calls the cap-enforcing `SyntheticToken.mint()`. [18](#0-17) [19](#0-18) [3](#0-2) 

Until enough existing supply is burned to create cap headroom and the fee collector subsequently makes the newly minted tokens available, the residual debt keeps collateral locked; if that supply is never distributed or the cap is not changed, the freeze is indefinite. [18](#0-17) 

### Likelihood Explanation
The trigger requires synthetic supply to reach `maxTotalSupply`, which is a normal protocol bound rather than a privileged or malformed state. [20](#0-19) [3](#0-2) 

An unprivileged actor can reach that bound through ordinary collateralized issuance because `issue()` is externally callable and subject only to the account's issuable limit, token existence, shutdown, and reentrancy checks. [7](#0-6) [21](#0-20) 

The configured mainnet msBTC debt cap equals the synthetic cap, so maximum permitted borrowing can exhaust the entire mintable repayment asset. [5](#0-4) [22](#0-21) 

Because the configured interest rate is nonzero, the next accrual after cap saturation necessarily attempts to add positive debt and mint positive synthetic supply. [23](#0-22) [22](#0-21) 

The likelihood is bounded by the need for sufficient collateral and actual cap utilization, but no governor, keeper, malicious oracle, malicious bridge endpoint, or other privileged attacker is required. [24](#0-23) 

### Recommendation
Do not allow user debt to increase when the corresponding synthetic repayment token cannot be minted. [11](#0-10) 

Prefer separating the public synthetic-supply cap from protocol accounting mints by adding a dedicated interest-fee mint path that is not constrained by the user-facing `maxTotalSupply`, while retaining other authorization checks. [19](#0-18) [3](#0-2) 

Alternatively, enforce a combined invariant such as `debtToken.totalSupply() <= syntheticToken.maxTotalSupply()` before accrual and design debt accrual so the debt cap explicitly includes all future interest. [1](#0-0) [16](#0-15) 

If `pendingInterestFee` is retained, it should not be included in borrower debt or `debtIndex` until the matching synthetic mint succeeds. [2](#0-1) [14](#0-13) 

### Proof of Concept
The following Foundry-style fork test demonstrates the equal-cap msBTC case; it assumes a fork block at which the deployed msBTC debt token is registered and the attacker can obtain enough supported collateral to issue the remaining synthetic supply. [24](#0-23) 

```solidity
function test_cappedInterestMakesDebtUnrepayable() public {
    vm.createSelectFork(vm.envString("MAINNET_RPC_URL"), forkBlock);

    SyntheticToken msBTC = SyntheticToken(msBTCAddress);
    DebtToken msBTCDebt = DebtToken(msBTCDebtAddress);
    DepositToken collateralToken = DepositToken(collateralTokenAddress);
    IERC20 collateral = IERC20(collateralToken.underlying());

    address attacker = address(0xA11CE);

    uint256 collateralAmount = enoughCollateralForFullIssuance;
    deal(address(collateral), attacker, collateralAmount);

    vm.startPrank(attacker);
    collateral.approve(address(collateralToken), collateralAmount);
    collateralToken.deposit(collateralAmount, attacker);

    uint256 headroom = msBTC.maxTotalSupply() - msBTC.totalSupply();
    msBTCDebt.issue(headroom, attacker);
    vm.stopPrank();

    assertEq(msBTC.totalSupply(), msBTC.maxTotalSupply());

    vm.warp(block.timestamp + 1);
    msBTCDebt.accrueInterest();

    assertGt(msBTCDebt.totalSupply(), msBTC.totalSupply());
    assertGt(msBTCDebt.getPendingInterestFee(), 0);

    // With a single-debtor/fresh-market fork, attacker owns all msBTC here.
    // Even burning the entire capped supply cannot cover debt + pending interest.
    vm.prank(attacker);
    vm.expectRevert();
    msBTCDebt.repayAll(attacker);
}
```

In the single-debtor case, `issue(16e18)` mints `16e18` synthetic tokens and creates `16e18` debt; after the next timestamp, `accrueInterest()` increases debt to `16e18 + interest`, while `SyntheticToken._mint()` cannot mint the extra interest because the cap is already reached. [8](#0-7) [11](#0-10) [3](#0-2) 

`repayAll()` then attempts to burn `16e18 + interest` from a maximum possible circulating balance of `16e18`, so full repayment reverts and the collateral backing the residual debt remains locked. [13](#0-12)
