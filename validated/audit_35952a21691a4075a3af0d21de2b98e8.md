### Title
Irreversible `DeleteAccountAction.beneficiary_id` with no existence check permanently burns account funds sent to a mistyped/non-existent beneficiary - (File: runtime/runtime/src/actions.rs)

### Summary
The external report flags CPort's `transferOwnership()` for performing a single-step, unchecked write of a critical destination address (`newOwner`), with only a non-zero-address check, allowing funds/control to be irrevocably sent to an unreachable address. The closest reachable analog in nearcore is `DeleteAccountAction`: its `beneficiary_id` is validated only for account-ID *syntax*, never for *existence*, and the action is executed atomically and irreversibly in a single transaction with no two-step confirmation.

### Finding Description
`DeleteAccountAction` carries a `beneficiary_id: AccountId` that receives the deleted account's entire remaining balance [1](#0-0) . Validation of this action only checks that `beneficiary_id` is a syntactically valid account id via `validate_action_account_id` — there is no check that the account actually exists on chain [2](#0-1) .

In `action_delete_account`, the runtime unconditionally pushes a refund receipt carrying the full account balance to `delete_account.beneficiary_id`, then immediately removes the account (`*account = None`) — a single, atomic, irreversible operation with no owner confirmation step analogous to `Ownable2Step` [3](#0-2) .

Critically, the comment in `check_transfer_to_nonexisting_account` explicitly documents that refund receipts do **not** create the destination account even if it doesn't exist: "Refunds don't automatically create accounts, because refunds are free and we don't want some type of abuse. Account deletion with beneficiary creates a refund, so it'll not create a new account." [4](#0-3) . This means if the signer supplies a `beneficiary_id` that does not exist (e.g. a typo, a never-created sub-account, or an account that gets deleted between signing and inclusion), the balance-refund receipt is dropped with no failure surfaced back to the deleting account, because the account has already been removed from state by the time the refund receipt executes.

### Impact Explanation
Unlike the `transferOwnership()` case where the admin merely loses control of privileges, here the entire remaining native-token balance of the deleted account is unrecoverably lost/burned if the beneficiary address is wrong, since: (1) no existence check happens at signing/validation time, (2) the delete and the refund are irreversible and atomic, and (3) refund receipts to non-existent accounts are silently dropped rather than creating the account or bouncing back to the sender. This is a permanent loss-of-funds condition triggered purely by an ordinary user's own transaction, with no additional confirmation step to catch a mistake — the direct analog of the reported bug class.

### Likelihood Explanation
Likelihood is realistic for ordinary usage: users/relayers routinely need to type or generate a `beneficiary_id` (e.g., via `delete_account_with_beneficiary_set` in the client SDK or `meta_tx_delete_account` in meta-transactions) [5](#0-4) [6](#0-5) , and any account-ID typo that happens to be syntactically valid but not yet created will pass validation and result in silent fund loss with no error reported to the user, since the deleting account no longer exists to receive a failure receipt.

### Recommendation
Add an existence check for `beneficiary_id` before executing `DeleteAccountAction` (reject with an explicit error, e.g., `BeneficiaryAccountDoesNotExist`, analogous to how `Transfer` to a non-existent, non-implicit account is rejected in `check_transfer_to_nonexisting_account`) or require an explicit acknowledgment/two-step account-deletion flow so an unreachable beneficiary cannot silently absorb the balance loss.

### Proof of Concept
1. Create account `alice.near` with a nonzero balance.
2. Sign a `DeleteAccountAction { beneficiary_id: "typonotexist.near" }` from `alice.near`, where `typonotexist.near` has never been created on chain.
3. `validate_delete_action` only checks the ID's syntax and passes [2](#0-1) .
4. `action_delete_account` executes: it enqueues a `Receipt::new_balance_refund(beneficiary_id, account_balance)` and deletes `alice.near` from state in the same step [3](#0-2) .
5. The refund receipt is a `Transfer` to `typonotexist.near`, which does not exist; per the documented behavior, refunds do not create accounts [4](#0-3) , so the balance is effectively lost, with no path to recover it since `alice.near` has already been deleted.

Note: I was not able to fully trace the exact code path that processes the resulting `Transfer` refund receipt against a nonexistent receiver to confirm 100% whether the tokens are explicitly burned/counted in `tokens_burnt` versus simply vanishing from the total supply invariant (this would need to be verified against `runtime/runtime/src/lib.rs`'s receipt-processing/refund logic, which I could not fully inspect before running out of iterations). This affects only the precise bookkeeping/labeling of the loss, not the core finding that funds sent to a non-existent beneficiary via `DeleteAccountAction` are unrecoverable.

    config: &RuntimeConfig,
    account_id: &AccountId,
    implicit_account_creation_eligible: bool,

    if implicit_account_creation_eligible
        && account_is_implicit(account_id, config.wasm_config.eth_implicit_accounts)
    {
        // OK. It's implicit account creation.
        // Notes:
        // - Transfer action has to be the only action in the transaction to avoid
        // abuse by hijacking this account with other public keys or contracts.
        // - Refunds don't automatically create accounts, because refunds are free and
        // we don't want some type of abuse.
        // - Account deletion with beneficiary creates a refund, so it'll not create a
        // new account.
        Ok(())

        Err(ActionErrorKind::AccountDoesNotExist { account_id: account_id.clone() }.into())
