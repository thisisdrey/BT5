### Title
Unprivileged attacker can fill a victim's per-account token list to `MAX_TOKENS_PER_USER` via forced dust deposits/transfers, permanently blocking the victim from opening new collateral or debt positions - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool.addToDepositTokensOfAccount` and `Pool.addToDebtTokensOfAccount` enforce a shared cap of 30 entries per account through `onlyIfAdditionWillNotReachMaxTokens`. Because `DepositToken._transfer` and `DepositToken._mint` add the token to the *recipient's* list, and `deposit()` accepts an arbitrary `onBehalfOf_`, any unprivileged user can force entries onto a victim's list until the cap is hit. Once the combined `debtTokensOfAccount + depositTokensOfAccount` length reaches `MAX_TOKENS_PER_USER`, every code path that would add a new token to the victim's account reverts with `UserReachedMaxTokens`, DoS-ing new deposits, new borrows, and leverage flows for that account — analogous to CVE-2020-8295's wrong-check user-targeted DoS.

### Finding Description
The cap check lives in `Pool`: [1](#0-0) [2](#0-1) 

Entries are added to a recipient's list from two externally reachable paths with no opt-in:

1. `DepositToken.deposit(amount_, onBehalfOf_)` — `onBehalfOf_` is attacker-chosen, so `deposit(1 wei, victim)` mints dust to the victim and calls `pool.addToDepositTokensOfAccount(victim)`: [3](#0-2) [4](#0-3) 

2. `DepositToken.transfer(victim, dust)` / `transferFrom` — `_transfer` adds the token to `recipient_`'s list when their prior balance is 0, and the lock check (`_revertIfLocked`) only applies to the *sender's* unlocked balance, not the recipient's consent: [5](#0-4) 

Once `debtTokensOfAccount.length(victim) + depositTokensOfAccount.length(victim) == 30`, the following all revert for the victim:
- `DepositToken.deposit` for any collateral type the victim doesn't already hold (`_mint` → `addToDepositTokensOfAccount` → `UserReachedMaxTokens`), so a user with an unhealthy position cannot add a *new* collateral type to save it.
- `DebtToken.issue` for any synthetic the victim hasn't borrowed before (`_mint` → `addToDebtTokensOfAccount`), blocking new debt positions.
- `SmartFarmingManager.leverage`/`flashRepay` flows that mint a new deposit or debt token for the victim.
- Liquidation seizes where `seize` transfers a deposit token to a liquidator whose list is full (secondary effect).

The victim cannot remove the forced entries themselves — removal requires balance → 0 (`removeFromDepositTokensOfAccount`), and withdrawing/transferring dusted tokens only frees one slot at a time while the attacker can refill them for near-zero cost.

### Impact Explanation
Temporary freezing of funds / reachable DoS of core protocol operations against a targeted user. The victim loses the ability to deposit new collateral types or issue new synthetics until they manually empty token slots, and the attacker can keep the list saturated. If the victim's position goes unhealthy during the attack, they cannot top up with a different collateral and may be liquidated — converting the freeze into loss of funds via forced liquidation. Attack cost is the dust value transferred plus gas for ~30 transactions; no privileged role needed.

### Likelihood Explanation
Fully reachable by any EOA through the public `deposit`/`transfer` entry points. Constraints: the pool only supports up to `MAX_TOKENS_PER_USER` deposit tokens globally, so the attacker can fill at most the number of registered deposit tokens (deployments typically have a handful) — filling the list requires depositing/transferring each listed `DepositToken`, which is cheap dust. Debt-token entries can't be forced directly (only `issue`/`mint` add them), so the attacker must fill slots with deposit tokens. No modifier blocks it: `deposit` is `whenNotPaused`, `transfer` is unguarded except the sender-side lock check, and `addToDepositTokensOfAccount` accepts any registered deposit token as caller.

### Recommendation
- Don't let unsolicited inbound transfers consume a recipient's slots: skip `addToDepositTokensOfAccount` for recipients in `_transfer`, or derive the account list lazily instead of on receive.
- Alternatively, only count toward the cap tokens the user has *deposited* themselves, or make `deposit(..., onBehalfOf_)` not register tokens for accounts other than the payer.
- If the list is only needed for `debtPositionOf`/`depositOf` iteration, consider enumerating a user's deposit tokens by scanning `pool.getDepositTokens()` balances instead of a mutable per-account list.

### Proof of Concept
Foundry test sketch (fork or local deploy with a `Pool` exposing ≥2 deposit tokens):

```solidity
// contracts: Pool, DepositToken(msdA, msdB, ...), DebtToken(msUSD)
// Attacker = EOA with dust of each underlying collateral
function test_grief_MaxTokensPerUser() public {
    address victim = makeAddr("victim");
    // victim already holds positions: e.g. 1 deposit token + 1 debt token
    vm.startPrank(victim);
    msdA.deposit(1000e18, victim);
    msUSDDebt.issue(100e18, victim);
    vm.stopPrank();

    // attacker fills remaining slots by force-depositing dust of every other deposit token
    address[] memory dts = pool.getDepositTokens();
    for (uint i; i < dts.length; ++i) {
        IDepositToken dt = IDepositToken(dts[i]);
        if (dt.balanceOf(victim) == 0) {
            uint256 dust = 1;
            deal(address(dt.underlying()), attacker, dust);
            vm.startPrank(attacker);
            dt.underlying().approve(address(dt), dust);
            dt.deposit(dust, victim); // or dt.transfer(victim, dust)
            vm.stopPrank();
        }
    }

    assertEq(
        pool.getDepositTokensOfAccount(victim).length +
        pool.getDebtTokensOfAccount(victim).length,
        pool.MAX_TOKENS_PER_USER()
    );

    // victim can no longer deposit a new collateral type nor issue a new synth
    vm.startPrank(victim);
    vm.expectRevert(UserReachedMaxTokens.selector);
    msdNewCollateral.deposit(100e18, victim);        // _mint -> addToDepositTokensOfAccount reverts

    vm.expectRevert(UserReachedMaxTokens.selector);
    msETHDebt.issue(1e18, victim);                   // _mint -> addToDebtTokensOfAccount reverts
    vm.stopPrank();
}
```

Note on scope: severity is bounded by how many distinct `DepositToken`s are registered (the attacker needs one dust deposit per slot) and the victim retains the ability to withdraw existing collateral and repay debt, so the impact is temporary freezing of position management — potentially escalating to forced liquidation losses when the victim needs a new collateral type to restore health.
