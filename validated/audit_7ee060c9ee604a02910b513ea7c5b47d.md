Audit Report

## Title
ERC20 asset transactor credits/debits XCM holding by nominal `amount` instead of measured `balanceOf()` delta, allowing fee-on-transfer/rebasing tokens to desync the shared checking account and lock user funds - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `ERC20Transactor::deposit_asset_with_surplus` call the target contract's `transfer()` and, on a `true` boolean return, unconditionally credit/debit the XCM holding register with the requested `amount` instead of the amount actually moved into/out of the shared `TransfersCheckingAccount`. Because `ERC20Matcher` accepts any location of the form `{parents:0, AccountKey20{key}}` with no allowlist, any permissionlessly-deployable `pallet-revive` contract implementing a `transfer()` that returns `true` — including fee-on-transfer or rebasing tokens — can be transacted through this path, letting the recorded XCM balance diverge from the real on-chain balance of the shared checking account.

## Finding Description
`withdraw_asset_with_surplus` matches the asset via `Matcher::matches_fungibles(what)?` [1](#0-0) , then transfers `amount` to `TransfersCheckingAccount` and, if `transferCall` decodes to `true`, credits `AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount)))` with the full nominal `amount`, never reading `balanceOf(checking_address)` before/after the call [2](#0-1) . Symmetrically, `deposit_asset_with_surplus` transfers `amount` from `TransfersCheckingAccount` to the beneficiary and treats `Ok(true)` as full success without verifying the beneficiary's actual received balance [3](#0-2) .

Critically, the `Matcher` used in production (`ERC20Matcher`) is defined as `MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>`, where `IsLocalAccountKey20` accepts *any* `Location` of the shape `(0, [AccountKey20 { .. }])` [4](#0-3) . There is no allowlist restricting which contract addresses can be transacted — any 20-byte contract address is matched. Since `pallet-revive` contract instantiation is permissionless, any unprivileged user can deploy a custom ERC20-like contract whose `transfer()` deducts a fee or rebases balances while still returning `true`, and immediately use it in XCM `WithdrawAsset`/`DepositAsset` operations through `ERC20Transactor`, which is wired into `AssetTransactors` on Asset Hub Westof [5](#0-4) .

## Impact Explanation
The shared `TransfersCheckingAccount` — a single `Get<AccountId>` used across all withdraw/deposit operations for every asset matched by `ERC20Transactor` — can accumulate an on-chain balance smaller than what the XCM holding register believes it has credited, for any fee-on-transfer/rebasing/non-standard ERC20 contract matched by the unrestricted `ERC20Matcher`. Once desynced, a subsequent, unrelated deposit for a different holder of the same token can fail (`transfer` returns `false` or reverts) because the checking account's real balance is insufficient, causing `XcmError::FailedToTransactAsset` and trapping/losing that user's assets — a "permanent user-fund … lock" per the impact gate.

## Likelihood Explanation
No privileged action is required: contract deployment via `pallet-revive` is permissionless, and `ERC20Matcher`/`IsLocalAccountKey20` imposes no allowlist on which contract addresses may be transacted, matching any `AccountKey20` location [6](#0-5) . Any user can deploy a fee-on-transfer contract and route it through ordinary, permissionless XCM `WithdrawAsset`/`DepositAsset` instructions handled by this transactor.

## Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, read `balanceOf` of the relevant account (checking account or beneficiary) immediately before and after the `transfer()` call and use the measured delta — not the requested `amount` — for both the `Erc20Credit`/`AssetsInHolding` value and for judging success. If the delta is less than `amount`, fail the operation atomically rather than crediting/debiting the nominal amount.

## Proof of Concept
1. Deploy via `pallet-revive` an ERC20-like contract whose `transfer(to, amount)` moves `amount * 99 / 100` to `to` but still returns `true`.
2. Configure/observe that `ERC20Matcher` (`IsLocalAccountKey20`) matches this contract's address with no allowlist check [6](#0-5) .
3. Submit an XCM `WithdrawAsset` for `amount=1000` of this token; `withdraw_asset_with_surplus` calls `transfer(checking_account, 1000)`, delivering only `990` to `TransfersCheckingAccount`, yet credits `Erc20Credit(1000)` into holding [7](#0-6) .
4. Submit an unrelated XCM `DepositAsset` for `1000` of the same token to a different beneficiary; `deposit_asset_with_surplus` calls `transfer(beneficiary, 1000)` from `TransfersCheckingAccount`, which now has insufficient real balance, causing failure/revert and asset trapping [8](#0-7) .

/// `Contains<Location>` implementation that matches locations with no parents,
/// a `PalletInstance` and an `AccountKey20` junction.
pub struct IsLocalAccountKey20;
impl Contains<Location> for IsLocalAccountKey20 {
	fn contains(location: &Location) -> bool {
		matches!(location.unpack(), (0, [AccountKey20 { .. }]))
	}
}

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {
		Some(Location::new(0, [AccountKey20 { key: (*key).into(), network: None }]))
	}
}

/// [`xcm_executor::traits::MatchesFungibles`] implementation that matches
/// ERC20 tokens.
pub type ERC20Matcher =
	MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>;
