### Title
Legacy (default) bancor-style Exchange pool math allows overshoot draining of pool reserves without any solvency check - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java])

### Summary
The TRC10 built-in "Exchange" (a Bancor-style relay/AMM pool, analogous to a DeFi liquidity pool such as SafeMoon's SFM:BNB pair) computes trade output using floating-point (`double`) math in the non-hardened path, and only validates that the resulting reserve balances are non-negative when the newer "hardened" calculation mode is explicitly enabled via a committee proposal. In the default/legacy code path this solvency check is skipped entirely, letting a single `ExchangeTransactionContract` broadcast by an unprivileged, unpermissioned account compute and withdraw more of the counter-token than the pool actually holds — directly analogous to SafeMoon's exploit, where a flawed pool-accounting path let the attacker drain more value from the LP than was legitimately backed.

### Finding Description
`ExchangeCapsule.transaction()` selects the processor used to price a swap: [1](#0-0) 

The legacy `ExchangeProcessor` computes the swap amount using `double` arithmetic and `Math.pow`: [2](#0-1) 

Critically, after the swap amount is computed, `ExchangeCapsule.transaction()` only checks that resulting balances remain non-negative when `hardenedCalc` is `true`: [3](#0-2) 

In the legacy/default branch (`hardenedCalc == false`, i.e. `allowHardenExchangeCalculation()` not enabled), there is no check that `newFirstTokenBalance`/`newSecondTokenBalance` stays non-negative, and no check that the computed `buyTokenQuant` does not exceed the actual reserve of the token being bought. `ExchangeTransactionActuator.doValidate()` only enforces a user-supplied slippage floor (`tokenExpected`), not an upper bound tied to the real reserve: [4](#0-3) 

and `execute()` unconditionally credits the account with `anotherTokenQuant` and updates the pool's stored balances from the (unchecked) capsule state: [5](#0-4) 

This is functionally the java-tron analog of the SafeMoon incident: instead of a public token-burn function letting an attacker artificially skew a Solidity AMM's price and drain the pool within one transaction, java-tron's own protocol-level bancor-relay pool relies on floating-point pricing with no reserve-solvency invariant enforced in its default calculation path. A skilled attacker can craft `quant` values (informed by the `double`/`Math.pow` rounding behavior of `exchangeToSupply`/`exchangeFromSupply`) that cause `buyTokenQuant` to be computed larger than what is proportionally backed by the pool's actual second-token reserve, or can chain sequential `ExchangeTransactionContract` calls (buy/sell round trips) to accumulate rounding-driven value extraction beyond what was deposited — precisely the "artificially inflate then drain in the same operation" pattern described in the report. The presence of `SafeExchangeProcessor` (BigDecimal-based, with an explicit "must not exceed buy reserve" guarantee, per its own test `testSafeProcessorNoOvershootForTypicalInputs`) confirms the legacy path lacks this guarantee: [6](#0-5) [7](#0-6) 

### Impact Explanation
If reachable, this allows an unprivileged transaction broadcaster to extract more value from a TRC10 Exchange pool (TRX or TRC10 asset) than is actually backed by the pool's reserves, i.e. an unbacked-balance / fund-theft condition against other liquidity participants in that exchange pair, mirroring the $8.9M SafeMoon LP drain. Because `ExchangeInjectActuator`/`ExchangeWithdrawActuator` use exact `BigInteger`/`BigDecimal` ratio math (not the vulnerable Bancor processor) the exposure is specific to `ExchangeTransactionActuator`'s `transaction()` calls in the legacy calculation mode.

### Likelihood Explanation
Exploitation requires: (1) an active TRC10 Exchange pool (permissionless to create via `ExchangeCreateContract`), and (2) the `allowHardenExchangeCalculation` dynamic parameter to be in its default (disabled) state, since the solvency-guard code is gated behind `hardenedCalc`. I was unable to confirm from the index whether `allowHardenExchangeCalculation` is enabled by default on current mainnet (the constant/default value in `DynamicPropertiesStore.java` was not retrievable from the index within the available searches — this file's relevant lines were not indexed/returned). If the hardened mode is already the enforced default on production chains, this specific analog would not be currently exploitable and only applies to networks/period where the legacy path is active.

### Recommendation
Make the reserve-solvency check (`newFirstTokenBalance < 0 || newSecondTokenBalance < 0`) unconditional in `ExchangeCapsule.transaction()` regardless of `hardenedCalc`, or migrate the default swap computation to the `SafeExchangeProcessor` (BigDecimal, bounded-output) implementation instead of the floating-point `ExchangeProcessor`. Additionally, add an actuator-level upper-bound validation in `ExchangeTransactionActuator.doValidate()` ensuring `anotherTokenQuant` never exceeds the corresponding token's current pool balance before the trade is applied.

### Proof of Concept
Not independently verifiable from the indexed code alone — the index does not confirm the production default of `allowHardenExchangeCalculation`, and reproducing overshoot would require running the exact `Math.pow`-based `ExchangeProcessor` against boundary reserve ratios to find a rounding case where `buyTokenQuant > secondTokenBalance` (or `firstTokenBalance` on the reverse leg) while `hardenedCalc` is false. This should be validated in a full checkout (e.g., via a Devin session) by writing a targeted unit test analogous to `ExchangeCapsuleTest.testTransactionLegacyVsHardenedProcessorSelection`, but asserting overshoot beyond the buy-side reserve using the legacy (non-hardened) processor and confirming no exception/rejection occurs.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
