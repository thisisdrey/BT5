### Title
Non-constant-time comparison of the `authorization` header against the configured RPC auth token enables remote timing side-channel token recovery - (File: `stackslib/src/net/api/postblock_v3.rs`)

### Summary
Six privileged HTTP RPC endpoints authenticate callers by comparing the raw `authorization` header value to the node's configured shared secret (`connection_options.auth_token`) using Rust's built-in `!=` string/`&str` comparison. `std::str`/`String` equality is implemented as a length check followed by a byte-by-byte `memcmp`-style comparison that returns as soon as a mismatch is found, so the comparison time leaks the number of leading bytes that match the secret. Because these endpoints are reachable pre-authentication over the network, this is the same bug class as CVE-2015-10004 (timing side-channel during shared-secret comparison), applied to the node's HTTP auth token instead of an HMAC.

### Finding Description
The following handlers all gate a privileged action behind a shared secret and perform the check the same (variable-time) way: [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) 

In each of these, the pattern is:
```rust
let Some(auth_header) = preamble.headers.get("authorization") else {
    return Err(Error::Http(401, "Unauthorized".into()));
};
if auth_header != password {
    return Err(Error::Http(401, "Unauthorized".into()));
}
```
`auth_header` and `password` are `String`/`&str`. Rust's derived `PartialEq` for strings ultimately calls the slice comparison, which first compares lengths, then walks bytes and short-circuits on the first differing byte. This is explicitly *not* constant-time — the same property flagged in the external advisory for HMAC-comparison code in `robbert229/jwt` (CWE-668, CVSS AV:N/AC:L). Here the "MAC" is simply the operator-configured `auth_token` string (`stackslib/src/config/mod.rs`, documented at lines 3802-3816 as the shared secret used for `/v3/block_proposal` and communication with `stacks-signer`).

The equality being broken is: *attacker-supplied header bytes* vs *node-configured secret bytes*. Because the check exits early on mismatch, response latency for a request whose header matches the secret's first `k` bytes is measurably larger than one that mismatches at byte `0`. Repeating this over many requests per candidate byte (256 candidates × secret length) lets a remote, unauthenticated attacker recover the `auth_token` value byte-by-byte, exactly as described for HMAC-comparison timing attacks in the report.

### Impact Explanation
Recovering `auth_token` grants an unauthenticated remote attacker the ability to:
- POST to `/v3/block_proposal` (`postblock_proposal.rs`) and `/v3/blocks/simulate/...` / `/v3/transactions/simulate` (which are meant to be restricted to the trusted `stacks-signer`), and
- broadcast blocks via `/v2/blocks?broadcast=1` (`postblock_v3.rs`), and
- invoke `/v3/contracts/fast-call-read/...` (`fastcallreadonly.rs`) and the block-replay debug endpoint (`blockreplay.rs`).

This is an authentication-bypass primitive against endpoints that are explicitly gated because they influence block proposal/broadcast flows and signer-node trust boundaries. Per the scope rubric, "auth bypass" achieved remotely without needing the node's own secret or another party's key qualifies as Critical/High impact — the attacker derives the secret purely from response timing, no prior credential needed.

### Likelihood Explanation
Exploitation requires only unauthenticated HTTP access to the node's RPC port and the ability to send a large number of low-latency requests, which matches the CVE-2015-10004 attack model (leverages a low-latency connection and volume of requests, but is not "flooding/DDoS" — it targets a specific comparison operation to extract secret bytes, one byte at a time, rather than needing raw bandwidth). Local-network or same-datacenter attackers (e.g., against a stacks-signer's paired node) have realistic timing precision to exploit byte-at-a-time comparisons. The check is duplicated identically across 6 handlers, indicating a systemic (not isolated) pattern.

### Recommendation
Replace all `auth_header != password` comparisons with a constant-time comparison, e.g. using the `subtle` crate's `ConstantTimeEq` on the byte representations (after first normalizing length, e.g. by hashing both sides with a fixed-size MAC/hash before comparing, or padding to a fixed length prior to a constant-time compare) in each of:
- `stackslib/src/net/api/postblock_v3.rs`
- `stackslib/src/net/api/postblock_proposal.rs`
- `stackslib/src/net/api/blockreplay.rs`
- `stackslib/src/net/api/blocksimulate.rs`
- `stackslib/src/net/api/txsimulate.rs`
- `stackslib/src/net/api/fastcallreadonly.rs`

Ideally, factor this into a single shared `check_auth(preamble, password)` helper used by all handlers to avoid future re-introduction of variable-time comparisons.

### Proof of Concept
Conceptual timing attack (mirrors the referenced advisory's methodology):
1. For a target node with `auth_token` configured, send repeated POST requests to `/v2/blocks?broadcast=1` (or any of the other 5 endpoints) with an `authorization` header guess `G`.
2. Measure round-trip latency of the 401 response for each candidate first byte `G[0] ∈ 0..255`, holding the rest of `G` constant/empty. The candidate producing a statistically higher latency (comparison proceeded past byte 0) is likely the correct first byte of `auth_token`.
3. Fix `G[0]` to the discovered value and repeat for `G[1]`, `G[2]`, ... until the full token is recovered or a match returns 400/other-than-401 (indicating full match).
4. Use the recovered token to submit forged/broadcast requests to `/v2/blocks?broadcast=1`, `/v3/block_proposal`, `/v3/blocks/simulate/...` etc. without legitimate credentials.

Note: I was not able to execute this PoC (no live node/timing environment available); this is derived purely from static code review of the comparison logic cited above.
