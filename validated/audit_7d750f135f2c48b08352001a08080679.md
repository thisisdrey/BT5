### Title
`Contract::storage_deposit` permanently destroys signer's wNEAR when `ext_storage_management::storage_deposit` fails, with no resolver refund - (File: contracts/defuse/src/contract/tokens/nep141/storage_deposit.rs)

### Summary
`Contract::storage_deposit` withdraws wNEAR from the signer's ledger balance and unwraps it to real NEAR before calling `do_storage_deposit`, which fires the `ext_storage_management::storage_deposit` cross-contract call with no `.then()` resolver to check success or refund on failure. If the named `contract_id` rejects or has no `storage_management` implementation, the attached NEAR is refunded by the NEAR runtime to the Verifier contract's own account (outside the ledger), while the signer's ledger balance has already been permanently decremented, breaking the conservation invariant between debited wNEAR and delivered value.

### Finding Description
The binding that must hold is: `wnear_debited_from_signer(amount) == storage_credited_on(contract_id, deposit_for_account_id, amount) OR wnear_credited_back_to_signer(amount)`.

The call path is `StorageDeposit::execute_intent -> Contract::storage_deposit` [1](#0-0) , which:
1. Calls `self.withdraw(...)` with the signer's wNEAR `Nep141TokenId`, permanently decrementing the signer's ledger balance via `internal_sub_balance` [2](#0-1) [3](#0-2) .
2. Fires `ext_wnear::near_withdraw` (unwrapping wNEAR into real NEAR held by the Verifier contract) chained to `do_storage_deposit` with `with_unused_gas_weight(0)` [4](#0-3) .
3. `do_storage_deposit` only checks that `near_withdraw` itself succeeded, then issues `ext_storage_management::ext(storage_deposit.contract_id).storage_deposit(...)` as a bare `Promise` with **no further `.then()` resolver** [5](#0-4) .

This is structurally different from every other withdrawal path in the codebase: `ft_withdraw` chains `ft_resolve_withdraw`, which explicitly checks the promise result and calls `self.deposit(...)` to refund the unused/failed amount back to the sender's ledger [6](#0-5) . `storage_deposit` has no equivalent resolver, so there is no code path that credits the signer back if `ext_storage_management::storage_deposit` panics (e.g., method not found because `contract_id` doesn't implement `storage_management`) or explicitly rejects the deposit.

Exploit: an attacker signs (as themselves, using their own wNEAR balance and their own key — no victim signature needed) a `StorageDeposit{contract_id: <attacker-controlled contract with no storage_management>, deposit_for_account_id: <any>, amount}` intent and calls `execute_intents`. The signer's own wNEAR is debited and unwrapped to NEAR; the `storage_deposit` cross-call to `contract_id` fails; the runtime refunds the attached NEAR back to the Verifier's own account balance (not to the ledger), and the signer's Defuse-ledger wNEAR balance is never restored.

Existing guards (`MultiPayload::verify`, nonce/lock checks, `assert_one_yocto`, `#[private]`) do not address this because the debit itself is fully authorized by the signer's own signature — the vulnerability is not unauthorized debit, but the missing refund-on-failure resolver after an authorized debit.

### Impact Explanation
The signer's own wNEAR ledger balance is permanently destroyed with no benefit delivered — the unwrapped NEAR is stranded in the Verifier contract's raw account balance, untracked by the ledger, and not owed to or recoverable by the signer through any code path in this contract. This is a "user funds permanently frozen" condition (Critical per the rubric), self-inflicted per attempt but exploitable at will and repeatable across accounts naming different `contract_id`s (or accidentally triggered by any legitimate user whose target contract is misconfigured/paused), each time destroying that user's wNEAR.

### Likelihood Explanation
Preconditions are trivial for the attacker to satisfy against themselves: hold wNEAR balance ≥ amount (an unprivileged action), deploy a stub contract with no `storage_management` implementation (unprivileged, standard NEAR deployment), and sign+submit a `StorageDeposit` intent naming it via `execute_intents`/`simulate_intents`. No role, relayer key, or victim key is required. The bug is deterministic given the call structure at `contracts/defuse/src/contract/tokens/nep141/storage_deposit.rs:14-26` — the missing resolver.

### Recommendation
Add a `#[private]` resolver method chained via `.then()` after the `ext_storage_management::storage_deposit` call (analogous to `ft_resolve_withdraw`) that checks `promise_result_checked_*` on the `storage_deposit` result and, on failure, calls `self.deposit(...)` to credit the wNEAR `TokenId` amount back to the original signer's ledger balance.

    fn internal_sub_balance(
        &mut self,
        owner_id: &AccountIdRef,
        tokens: impl IntoIterator<Item = (TokenId, u128)>,
    ) -> Result<()> {
        let owner = self
            .accounts
            .get_mut(owner_id)
            .ok_or_else(|| DefuseError::AccountNotFound(owner_id.to_owned()))?
            .get_mut()
            .ok_or_else(|| DefuseError::AccountLocked(owner_id.to_owned()))?;

        for (token_id, amount) in tokens {
            if amount == 0 {
                return Err(DefuseError::InvalidIntent);
            }

            owner
                .token_balances
                .sub(token_id.clone(), amount)
                .ok_or(DefuseError::BalanceOverflow)?;
        }

        Ok(())
    }

            Some("withdraw"),

            .with_static_gas(NEAR_WITHDRAW_GAS)

                    .do_storage_deposit(storage_deposit),
            )

impl FungibleTokenWithdrawResolver for Contract {
    #[private]
    fn ft_resolve_withdraw(
        &mut self,
        token: AccountId,
        sender_id: AccountId,
        amount: U128,
        is_call: bool,
    ) -> U128 {
        let used = if is_call {
            // `ft_transfer_call` returns successfully transferred amount
            match promise_result_checked_json::<U128>(0) {
                Ok(Ok(used)) => used.0.min(amount.0),
                Ok(Err(_deserialize_err)) => 0,
                // do not refund on failed `ft_transfer_call` due to
                // NEP-141 vulnerability: `ft_resolve_transfer` fails to
                // read result of `ft_on_transfer` due to insufficient gas
                Err(_) => amount.0,
            }
        } else {
            // `ft_transfer` returns empty result on success
            if promise_result_checked_void(0).is_ok() {
                amount.0
            } else {
                0
            }
        };

        let refund = amount.0.saturating_sub(used);
        if refund > 0 {
            self.deposit(
                sender_id,
                [(Nep141TokenId::new(token).into(), refund)],
                Some(REFUND_MEMO),
            )
            .unwrap_or_else(|err| err.panic());
        }

        U128(used)
    }
