### Title
Dust-transfer griefing fills the per-account token list to `MAX_TOKENS_PER_USER`, DoS-ing deposits, liquidations and borrows for the victim (or the fee collector) - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
The MongoDB advisory is a "consumer buffer fills → watermark never updated → process crash" bug class: a bounded per-consumer buffer that permanently wedges once saturated. The Metronome analog is the per-account bounded token list (`debtTokensOfAccount` + `depositTokensOfAccount`, hard cap `MAX_TOKENS_PER_USER = 30`). Any unprivileged user can force arbitrary entries into *someone else's* buffer by sending dust `DepositToken` transfers; once the combined list reaches 30, every code path that tries to add a new token type for that account reverts with `UserReachedMaxTokens`, blocking deposits on their behalf, transfers to them, new borrows, and — if the victim is the fee collector — all fee-bearing deposits and liquidations protocol-wide.

### Finding Description
`Pool.onlyIfAdditionWillNotReachMaxTokens` reverts when `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= 30` (`Pool.sol:143-148`). Entries are added *for the recipient* inside `DepositToken._transfer`/`_mint` — not initiated by the recipient:

```solidity
// DepositToken.sol:517-520
if (_recipientBalanceBefore == 0 && amount_ > 0) {
    pool.addToDepositTokensOfAccount(recipient_);
}
```

`DepositToken.transfer` is permissionless and only checks the *sender's* unlocked balance (`DepositToken.sol:348-354`). An attacker deposits a dust amount of collateral via `deposit(amount, attacker)`, then calls `msdToken.transfer(victim, 1 wei)` for each distinct deposit token. Each call pushes a new element into `depositTokensOfAccount[victim]` via `Pool.addToDepositTokensOfAccount` (`Pool.sol:216-220`). The victim cannot prevent incoming transfers; entries are only removed when the holder's balance reaches exactly zero (`DepositToken.sol:523-525`), i.e. the victim must actively burn/transfer each dust amount out.

After saturation:
- `deposit(amount_, victim)` for any deposit token the victim doesn't already hold reverts, because `_mint` → `addToDepositTokensOfAccount` hits the cap (`DepositToken.sol:486-488`).
- `DebtToken` issuance of a new synth for the victim reverts via `addToDebtTokensOfAccount` (`Pool.sol:204-208`), blocking new borrows.
- Liquidation fee seizure `depositToken_.seize(account_, feeCollector, _fee)` (`Pool.sol:592`) calls `_transfer`, which adds the token to `feeCollector`'s list — so saturating the *fee collector's* list bricks every liquidation that charges a protocol fee and every deposit that charges a deposit fee (`_mint(feeCollector, _fee)` at `DepositToken.sol:231`), protocol-wide, until the fee-collector operator manually empties dust entries.

The invariant broken is liveness: a bounded per-account "buffer" that external parties can fill to capacity, after which the protocol crashes (reverts) on the exact paths the capacity check protects.

### Impact Explanation
- Targeted DoS: a chosen victim cannot open positions in any new collateral/debt type, and cannot receive transfers of new msd tokens.
- Protocol-wide DoS: by filling `feeCollector`'s combined list to 30, all deposits that mint a fee and all liquidations that seize a fee revert. Blocked liquidations allow unhealthy positions to persist, risking bad-debt accrual — direct impact on solvency guarantees.
- Recovery is possible (victim/fee collector transfers the dust out so the entry is removed), making this temporary freezing of funds/functionality rather than permanent loss.

### Likelihood Explanation
Cost scales with the number of distinct deposit/debt tokens the victim doesn't already hold (up to 30); each requires a dust deposit the attacker can fully withdraw afterward, so the attack is nearly free on pools with several listed collaterals. Attack paths that don't already self-block:
- `transfer`/`transferFrom` have no recipient-consent check and no cap check on the recipient side beyond the revert itself.
- `nonReentrant`, `whenNotPaused`, `SynthContext` checks don't prevent a plain EOA transfer.
- `MAX_TOKENS_PER_USER` is a hard-coded constant, not governor-tunable.

The main limitation is impact severity: no funds are stolen, and a user (or fee-collector operator) can self-recover by zeroing out dust balances. It is a genuine, reachable liveness/griefing bug rather than theft or permanent freeze.

### Recommendation
- On add, allow eviction instead of reverting: if the recipient's list is full, the recipient-initiated removal should still be possible — alternatively, don't revert in `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` when the cap is hit; instead skip tracking dust positions below a USD threshold (`debtFloorInUsd`-style minimum), or
- Make token-list membership opt-in (only add on `deposit`/`issue` initiated by the account, not on inbound `transfer`), or
- Exempt `seize`/fee-mint paths from the cap so liquidation and fee collection can never be bricked by a filled fee-collector list.
