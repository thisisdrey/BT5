### Title
Stale postponed `DeleteAccount` receipt survives account deletion and drains a subsequently re-created account of the same name to an attacker-chosen beneficiary - ([File: core/store/src/utils/mod.rs])

### Summary
`remove_account` (core/store/src/utils/mod.rs:505-575) deletes an account's `Account`, `ContractCode`, access/gas keys, and `ContractData`, but never touches `TrieKey::PostponedReceipt`, `PendingDataCount`, or `PostponedReceiptId` entries indexed under that `receiver_id`. Because a postponed `ActionReceipt` can contain a self-targeted `DeleteAccount{beneficiary_id}` action that is authorized purely by string equality of `predecessor_id == receiver_id` (`check_actor_permissions`, runtime/runtime/src/actions.rs:761-776), an attacker who owned account `A` can leave a dormant, unresolved postponed `DeleteAccount` behind after deleting `A`, and later trigger its execution (by resolving the data dependency at a time of their choosing) once someone else has re-created `A` and funded it — silently transferring the new balance to the attacker's `beneficiary_id`.

### Finding Description
1. Account `A` (attacker-controlled) issues a self-receipt (`predecessor_id == receiver_id == A`) with `input_data_ids = [d1]` and `actions = [DeleteAccount{beneficiary_id: attacker_beneficiary}]`. Because `d1` is unmet, `process_action_receipt` (runtime/runtime/src/lib.rs:1593-1658) stores this receipt via `set_postponed_receipt` under `TrieKey::PostponedReceipt{receiver_id: A, receipt_id}` plus a `PendingDataCount` and `PostponedReceiptId{receiver_id: A, data_id: d1}` link — all keyed only by `A`'s account name, with no linkage to "this specific incarnation of `A`."
2. `A` then executes a second receipt, `DeleteAccount{beneficiary: A}` (or anything), which passes `check_actor_permissions` (`actor_id == account_id == A`) and calls `remove_account(state_update, A)` (runtime/runtime/src/actions.rs:371, core/store/src/utils/mod.rs:505). This clears `TrieKey::Account`, `ContractCode`, access keys, gas keys and `ContractData` for `A` — but leaves the `PostponedReceipt`, `PendingDataCount`, and `PostponedReceiptId` entries for `A` completely intact in the trie.
3. The data dependency `d1` need not resolve automatically or soon: the attacker fully controls when it resolves, because `d1` is only produced when some other `ActionReceipt`'s `output_data_receivers` fires (`lib.rs:1034-1073`). The attacker can chain this off another account they control (or even a further postponed hop) and submit the triggering transaction at an arbitrary later time — there is no timeout on the ordinary postponed-receipt path (unlike yield/resume). The postponed entry persists indefinitely in state.
4. Later, `B` (who must be `A`'s namespace parent for sub-account names, per `CreateAccountNotAllowed`/naming rules in `check_account_existence`, actions.rs:787-855) submits `CreateAccount` + `Transfer` for the same account id `A`, funding it with `N` NEAR. Since `A`'s name was fully freed by `remove_account`, this succeeds and creates a brand-new `Account` state under key `A`, with a fresh, unrelated owner/keys.
5. The attacker now submits the triggering transaction that resolves `d1`. `process_receipt`/data handling (`lib.rs:1415-1474`) reads `PendingDataCount`, decrements it to 0, fetches the still-present `PostponedReceipt{receiver_id: A, receipt_id}`, removes it, and calls `apply_action_receipt` on it.
6. Inside `apply_action`, `check_actor_permissions` for the `DeleteAccount` action again only checks `actor_id (= A, from stale predecessor_id) == account_id (= A)` (actions.rs:761-776) — it has no notion of "generation" of the account and cannot distinguish the old `A` from the freshly re-created `A`. The check passes.
7. `action_delete_account` (actions.rs:364-389) pays out the account's *current* balance (`account_ref.amount()` — i.e., `B`'s freshly deposited `N` NEAR) via `Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance)` to the attacker's `beneficiary_id`, then calls `remove_account` again, deleting `B`'s newly created account.

The root cause is that `remove_account` is not exhaustive over all state keyed by `account_id` (it misses the postponed-receipt/pending-data-count/postponed-receipt-id columns, and similarly the promise-yield columns), and the authorization model for `DeleteAccount` in `check_actor_permissions` binds purely to the account-id string rather than to any identity/generation of the specific account instance that issued the postponed request. ### Impact Explanation
Theft of funds: the beneficiary of a stale, attacker-authored `DeleteAccount` action receives the balance of an account it no longer has any relationship with, at the expense of whoever re-created and funded that account name. This is a direct violation of value conservation/authorization exactness and matches NEAR's "theft of user funds" / "authorization escalation across accounts" bounty category.

### Likelihood Explanation
- The attacker needs no privileged access: only an ordinary account, its own contract, and standard transactions (`CreateAccount`... no, `DeleteAccount`, `FunctionCall`/promise chaining) — all reachable via a public RPC endpoint.
- Because plain postponed receipts (not yield/resume) have no timeout, the attacker can hold the dangling `DeleteAccount` open indefinitely and choose the exact moment to trigger it, maximizing the chance of catching a victim's deposit.
- The main constraint is naming rules: sub-account creation requires the predecessor to be the direct parent namespace (`alice.near` creating `eve.alice.near`), so the "victim" `B` who re-creates the deleted account is typically the parent account that once controlled/delegated `A`. This is a realistic pattern for platforms/apps that programmatically create, delete, and later reuse subaccount names for different tenants/sessions.
- The attack is fully reproducible and deterministic in an integration test/apply-loop environment (as described in the prompt's proof idea), since the test can script exact ordering without depending on real-world timing coincidences.

### Recommendation
- Make `remove_account` exhaustive: when deleting an account, also purge any `PostponedReceipt`, `PendingDataCount`, `PostponedReceiptId` (and `PromiseYieldReceipt`/`PromiseYieldStatus`/`YieldIdToDataId`/`PromiseYieldTimeout`) entries keyed by that `receiver_id`, failing/refunding those receipts rather than silently letting them execute against the account name's future occupant.
- Alternatively (or additionally), bind postponed receipts to the account's identity/generation (e.g., store and check a monotonically increasing "account nonce"/incarnation counter that is bumped on `CreateAccount`, and reject execution of a postponed action receipt whose captured incarnation no longer matches current state) so that even if cleanup is incomplete, stale receipts fail safely with `AccountDoesNotExist`/analogous error instead of inheriting permission on the new account.

### Proof of Concept
Integration/apply-loop test plan (mirrors `runtime/runtime/src/tests/apply.rs` style, e.g. `test_function_call_after_same_chunk_delete_recreate_resolves_fresh_code`):
1. Set up account `A` = `eve.alice.near`, parent `B` = `alice.near`, attacker beneficiary `E`.
2. Submit a receipt to `A` with `input_data_ids = [d1]` and `actions = [DeleteAccount{beneficiary_id: E}]`; assert it is stored as a postponed receipt (`PostponedReceipt`/`PendingDataCount` present in trie, `get_postponed_receipt` returns it).
3. Submit a self `DeleteAccount{beneficiary_id: A}` receipt for `A` (actor_id == account_id passes); assert `A`'s `Account` record is gone (`get_account` returns `None`) while the `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` entries for `A` still exist in state.
4. Submit `B`'s `CreateAccount` + `Transfer(N)` receipt targeting `A`; assert `A` exists again with balance `N`.
5. Submit/produce the `Data` receipt satisfying `d1` (e.g., via a chained `FunctionCall` output whose `output_data_receivers` targets `(A, d1)`).
6. After processing, assert: `A`'s account no longer exists (deleted again), and `E`'s balance increased by exactly `N` (`attacker_balance_after == attacker_balance_before + N`), demonstrating theft of `B`'s deposit via the stale, privilege-inheriting `DeleteAccount`.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}

    fn process_action_receipt(
        &self,
        receipt: &Receipt,
        receipt_sink: &mut ReceiptSink,
        instant_receipts: &mut VecDeque<Receipt>,
        validator_proposals: &mut Vec<ValidatorStake>,
        state_update: &mut TrieUpdate,
        apply_state: &ApplyState,
        epoch_info_provider: &dyn EpochInfoProvider,
        pipeline_manager: &ReceiptPreparationPipeline,
        stats: &mut ChunkApplyStatsV1,
        account_id: &AccountId,
        action_receipt: VersionedActionReceipt<'_>,
        receipt_to_tx: &mut Vec<(CryptoHash, ReceiptToTxInfo)>,
    ) -> Result<Option<ExecutionOutcomeWithId>, RuntimeError> {
        let mut pending_data_count: u32 = 0;
        for data_id in action_receipt.input_data_ids() {
            if !has_received_data(state_update, account_id, *data_id)? {
                pending_data_count += 1;
                // The data for a given data_id is not available, so we save a link to this
                // receipt_id for the pending data_id into the state.
                set(
                    state_update,
                    TrieKey::PostponedReceiptId {
                        receiver_id: account_id.clone(),
                        data_id: *data_id,
                    },
                    receipt.receipt_id(),
                )
            }
        }

        if pending_data_count == 0 {
            // All input data is available. Executing the receipt. It will cleanup
            // input data from the state.
            return self
                .apply_action_receipt(
                    state_update,
                    apply_state,
                    pipeline_manager,
                    receipt,
                    receipt_sink,
                    instant_receipts,
                    validator_proposals,
                    stats,
                    epoch_info_provider,
                    receipt_to_tx,
                )
                .map(Some);
        } else {
            // Not all input data is available now.
            // Save the counter for the number of pending input data items into the state.
            set(
                state_update,
                TrieKey::PendingDataCount {
                    receiver_id: account_id.clone(),
                    receipt_id: *receipt.receipt_id(),
                },
                &pending_data_count,
            );
            // Save the receipt itself into the state.
            set_postponed_receipt(state_update, receipt);
        }

        Ok(None)
    }
