### Title
StackerDB chunk signatures omit the contract/message binding, allowing cross-contract chunk replay between sibling `signers-{cycle%2}-{msg_id}` StackerDBs - (File: libstackerdb/src/libstackerdb.rs)

### Summary
The reported DAO issue is a case where an identity/authorization decision (the deployed contract address) is derived from data that does not uniquely bind to the target chain, letting a validly-produced artifact from one context be replayed to override state in a different context that shares the same identity. The direct analog in this repo is `StackerDB` chunk authentication: a slot's signature commits only to `(slot_id, slot_version, data_hash)` and never to the StackerDB contract it was written for. Because Nakamoto creates several sibling StackerDB contracts per reward cycle (`signers-{cycle%2}-1`, `-2`, `-3`, one per `MessageSlotID`) that all share an identical signer→slot assignment, a chunk validly signed for one contract passes signature verification unchanged when replayed into a sibling contract for the same cycle, since the verification function is never told "this signature was only valid for contract X."

### Finding Description
`SlotMetadata::auth_digest()` hashes only the slot id, slot version, and data hash: [1](#0-0) 
`SlotMetadata::verify()`/`StackerDBChunkData::verify()` recover a pubkey from that digest and compare its hash to the expected `principal` — again with no notion of *which contract* the signature was scoped to: [2](#0-1) 

Both storage paths use exactly this same-scope-agnostic check:
- The write path `StackerDBTx::try_replace_chunk` looks up the slot's expected signer *for the given `smart_contract`* and calls `slot_desc.verify(&slot_validation.signer)`; nothing about the accepted signature ties it back to that specific `smart_contract`: [3](#0-2) 
- The p2p ingestion path `PeerNetwork::validate_received_chunk` does the same lookup/verify pattern against `smart_contract_id`, with the same gap: [4](#0-3) 

The reason this is exploitable rather than theoretical is that in Nakamoto, a single reward cycle produces multiple StackerDB contracts sharing the *same* signer set and *same* slot-id assignment, differentiated only by `message_id`: [5](#0-4) [6](#0-5) 
and the shared `.signers` contract explicitly serves the identical `signer-slots` page to every sibling `signers-{parity}-{msg_id}` contract for that parity: [7](#0-6) [8](#0-7) 

Consequently, signer `S` occupying `slot_id = k` in `signers-0-1` (BlockResponse) also occupies `slot_id = k` in `signers-0-2` (StateMachineUpdate) and `signers-0-3` (BlockPreCommit). A `StackerDBChunkData` that `S` legitimately signed and published to `signers-0-1` — captured off the wire by any unprivileged network observer — verifies successfully if resubmitted (via the p2p `StackerDBPushChunk` unsolicited-message path or the public `POST /stackerdb/chunks` HTTP endpoint) against `signers-0-2` or `signers-0-3`, because `verify()` only checks "was this signed by `S`'s key over this `(slot_id, slot_version, data_hash)`" — it never checks "was this signed *for this contract*."

### Impact Explanation
This breaks the equality "signed-for-contract-A" vs "accepted-as-valid-for-contract-B": an unprivileged relayer, without possessing any signer's private key, can inject a byte-for-byte replay of one signer's legitimate message into an unrelated StackerDB slot meant to carry a different, structurally distinct message type (e.g. planting `BlockResponse` payload bytes into the `StateMachineUpdate` or `BlockPreCommit` slot for the same signer). Any consumer of that slot (miner block-response coordinator, signer state-machine monitor) that deserializes the slot content expecting a specific `SignerMessage` variant will either fail to parse or, worse, silently misinterpret stale/foreign data as the canonical latest state for that message type — this is a "non-canonical data served as canonical" condition matching the High-severity bucket (steering consumers off the correct state via a forged/misdirected but validly-signed artifact). It requires no compromise of any key and only network relay capability.

### Likelihood Explanation
Medium-to-High: exploitation only requires observing one broadcasted/queryable chunk (StackerDB chunks are, by design, openly served to any replicating peer) and re-POSTing/re-pushing it to a sibling contract that shares the same signer-slot layout for the same reward-cycle parity — no cryptographic work and no privileged access are needed. The main constraint is that the replayed slot_version must clear the target contract's freshness (`slot_version <= stored version`) and `max_writes` checks, which is a matter of timing rather than a real barrier.

### Recommendation
Bind the StackerDB contract identity into the signed digest. `SlotMetadata::auth_digest()` should include the `QualifiedContractIdentifier` (or at minimum the `message_id`) it is scoped to, so a signature produced for `signers-0-1` cannot be verified as valid against `signers-0-2`/`signers-0-3`. This requires a coordinated protocol/version change (new signing scheme) since existing clients only sign over `(slot_id, slot_version, data_hash)`.

### Proof of Concept
1. During reward cycle `N`, signer `S` (private key `sk`) legitimately signs and publishes chunk `C = (slot_id=k, slot_version=v, sig, data)` to `signers-{N%2}-1` (BlockResponse), verified via `StackerDBChunkData::verify` at [9](#0-8) .
2. An unprivileged network observer captures `C` off the wire (StackerDB chunks are openly queryable/broadcast).
3. The observer, without any of `S`'s key material, re-submits the identical `(slot_id=k, slot_version=v, sig, data)` to the sibling contract `signers-{N%2}-2` (StateMachineUpdate) — either via the p2p unsolicited `StackerDBPushChunk` handler or the `POST /v2/stackerdb/{contract}/chunks` endpoint.
4. `validate_received_chunk`/`try_replace_chunk` look up the expected signer for `signers-{N%2}-2`, find it is the same `S` at the same `slot_id=k` (per the shared `stackerdb-get-signer-slots-page` logic), call `slot_desc.verify(&S)`, which succeeds because the digest never encoded which contract it was for.
5. The replayed BlockResponse bytes are now accepted and stored as the "latest" StateMachineUpdate chunk for signer `S`, even though `S` never signed anything intended for that message type/contract.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
