### Title
Oversized DataReceipt from `value_return` bypasses `NewReceipt` size check and persists via `ExistingReceipt` mode - (File: `runtime/runtime/src/lib.rs`, `runtime/runtime/src/verifier.rs`)

### Summary
An unprivileged attacker can deploy a contract that calls `value_return` with data close to `max_length_returned_data`/`max_receipt_size` and have the runtime wrap that value into an output `DataReceipt` without ever passing it through `validate_receipt(..., ValidateReceiptMode::NewReceipt)`. The oversized receipt is only checked later with the looser `ValidateReceiptMode::ExistingReceipt`, which explicitly skips the size check (documented as the known bug tracked in near/nearcore#12606), letting the oversized receipt be forwarded/persisted and repeatedly reprocessed.

### Finding Description
`validate_receipt` in `runtime/runtime/src/verifier.rs` only enforces `ReceiptSizeExceeded` when `mode == ValidateReceiptMode::NewReceipt`; `ExistingReceipt` mode intentionally tolerates oversized receipts [1](#0-0)  and the enum documents this as the known, still-open bug from issue #12606 [2](#0-1) .

Newly created *action* receipts from a contract call are validated with `NewReceipt` mode right after action execution (per `apply_action_receipt`/`function_call.rs` flow). However, the output `DataReceipt`s generated from a contract's `value_return` result (the "Value Result" path, used when the receipt has `output_data_receivers`) are constructed later, directly inside `apply_action_receipt`, and pushed straight to `receipt_sink.forward_or_buffer_receipt` without any subsequent `validate_receipt(..., NewReceipt)` call [3](#0-2) . The only size check performed on the return value is `value_return`'s comparison against `max_length_returned_data` inside the VM host function [4](#0-3) , which is a per-value bound, not a bound on the full serialized `DataReceipt` (which also carries `receipt_id`, `predecessor_id`, `receiver_id`, `data_id`, and enum tags). A return value sized close to `max_receipt_size` therefore produces a serialized `DataReceipt` that exceeds `max_receipt_size` while still passing `value_return`'s own check.

Once such an oversized `DataReceipt` is forwarded/buffered as an outgoing receipt, it is later re-validated only via `ValidateReceiptMode::ExistingReceipt` — both when consumed as an incoming receipt (`process_incoming_receipts`, `runtime/runtime/src/lib.rs:2591-2597`) and when popped from the delayed-receipts queue (`process_delayed_receipts`, `runtime/runtime/src/lib.rs:2522-2534`) [5](#0-4) [6](#0-5) . In both cases `ReceiptSizeExceeded` is never raised, so the oversized receipt is accepted, can be pushed to the delayed queue when the chunk's compute/gas or proof-size limit is hit, and re-enters `process_delayed_receipts` in later chunks.

This exact scenario is already reproduced in the repository's own integration test, `test_max_receipt_size_value_return`, which deploys a contract, triggers `max_receipt_size_value_return_method` to return a value sized at `max_receipt_size` (4,194,304 bytes), and then asserts via `assert_oversized_receipt_occurred` that a receipt above `max_receipt_size` actually appears in the incoming-receipts/receipt-proofs of a subsequent block [7](#0-6) [8](#0-7) .

### Impact Explanation
Once persisted, an oversized `DataReceipt` sitting in the delayed-receipts queue or awaiting cross-shard delivery must be included in state/trie proofs (chunk witnesses) any time the shard is applied and the queue is touched, inflating chunk witness size every time that shard produces a chunk while the receipt is queued. Since the runtime never rejects it for size at the `ExistingReceipt` re-validation points, it can be repeatedly re-queued (e.g., pushed back to the delayed queue whenever compute/proof-size limits are hit) before it is finally applied, causing avoidable, attacker-triggered growth of witness/proof size on the affected shard across chunks. This is a resource-exhaustion/liveness-degradation issue scoped to the shard handling the receipt, not a fund-theft or consensus-divergence bug — it falls under NEAR's DoS/liveness bounty category rather than fund loss or chain split.

### Likelihood Explanation
The precondition is trivial for an unprivileged account: deploy any wasm contract, call a method that invokes `value_return` with a payload close to `max_receipt_size` while the receipt has `output_data_receivers` set (i.e., is `.then()`-chained), pay the attached gas/deposit for that single function call, and submit via a public RPC endpoint. No validator, protocol, or special permission is required, and the cost is a single transaction's gas. It is repeatable per chunk/shard the attacker targets.

### Recommendation
Route the `DataReceipt`s created from `value_return` output data (in `apply_action_receipt`, `runtime/runtime/src/lib.rs` around lines 1117-1136) through `validate_receipt(..., ValidateReceiptMode::NewReceipt)` before they are handed to `receipt_sink.forward_or_buffer_receipt`, exactly as is done for action receipts created via the promise API, so an oversized value-return receipt fails at creation time (charged to the failing receipt) instead of being silently forwarded and only caught by the intentionally lax `ExistingReceipt` path.

### Proof of Concept
Use/extend the existing integration test `test_max_receipt_size_value_return` in `test-loop-tests/src/tests/max_receipt_size.rs`:
1. Deploy `near_test_contracts::rs_contract()` under an attacker-controlled account.
2. Call `max_receipt_size_value_return_method` with `value_size` set to `max_receipt_size` (4,194,304) so the resulting `DataReceipt` (value + envelope) exceeds `max_receipt_size`.
3. Assert the transaction/receipt chain completes successfully (i.e., no `ReceiptSizeExceeded` `ActionError` is raised, unlike the `FunctionCall`-argument or `yield` cases which are correctly rejected in `test_max_receipt_size`/`test_max_receipt_size_yield_resume`).
4. Call `assert_test_completed` to confirm the downstream promise (`mark_test_completed`) still ran, proving the oversized data receipt was delivered/processed.
5. Use `assert_oversized_receipt_occurred` to scan incoming-receipt proofs across blocks and confirm a receipt with `borsh::object_length > max_receipt_size` was present in the shard's receipt flow, then extend the test to run several additional chunks and record the receipt's presence in the delayed-receipts trie / witness size to show repeated inclusion across chunks before final consumption.

/// Validates a given receipt. Checks validity of the Action or Data receipt.
pub(crate) fn validate_receipt(
    limit_config: &LimitConfig,
    receipt: &Receipt,
    current_protocol_version: ProtocolVersion,
    mode: ValidateReceiptMode,
) -> Result<(), ReceiptValidationError> {
    if mode == ValidateReceiptMode::NewReceipt {
        let receipt_size: u64 =
            borsh::object_length(receipt).unwrap().try_into().expect("Can't convert usize to u64");
        if receipt_size > limit_config.max_receipt_size {
            return Err(ReceiptValidationError::ReceiptSizeExceeded {
                size: receipt_size,
                limit: limit_config.max_receipt_size,
            });
        }
    }

pub enum ValidateReceiptMode {
    /// Used for validating new receipts that were just created.
    /// More strict than `OldReceipt` mode, which has to handle older receipts.
    NewReceipt,
    /// Used for validating older receipts that were saved in the state/received. Less strict than
    /// NewReceipt validation. Tolerates some receipts that wouldn't pass new validation. It has to
    /// be less strict because:
    /// 1) Older receipts might have been created before new validation rules.

    ///    to handle them gracefully until the receipt size limit bug is fixed.
    ///    See https://github.com/near/nearcore/issues/12606 for details.
    ExistingReceipt,
}

/// Assert that there was an incoming receipt with size above max_receipt_size
fn assert_oversized_receipt_occurred(node: &TestLoopNode<'_>) {
    let client = node.client();
    let chain = &client.chain;
    let epoch_manager = &*client.epoch_manager;

    let tip = chain.head().unwrap();
    let epoch_id = epoch_manager.get_epoch_id(&tip.last_block_hash).unwrap();
    let protocol_version = epoch_manager.get_epoch_protocol_version(&epoch_id).unwrap();
    let runtime_config = client.runtime_adapter.get_runtime_config(protocol_version);
    let max_receipt_size = runtime_config.wasm_config.limit_config.max_receipt_size;

    let mut block = chain.get_block(&tip.last_block_hash).unwrap();

    // Go over all blocks down to genesis looking for a receipt above max_receipt_size.
    loop {
        if block.header().is_genesis() {
            panic!("Didn't find receipt with size above max_receipt_size!");
        }
        let prev_block = chain.get_block(block.header().prev_hash()).unwrap();

        let shard_layout = epoch_manager
            .get_shard_layout(&epoch_manager.get_epoch_id(block.hash()).unwrap())
            .unwrap();

        let oversized = if ProtocolFeature::Spice.enabled(protocol_version) {
            // With spice chunks are executed asynchronously and their produced receipts are
            // persisted as receipt proofs keyed by the block in which the chunk was applied,
            // rather than as incoming receipts on the following block.
            shard_layout.shard_ids().any(|shard_id| {
                chain
                    .chain_store()
                    .iter_receipt_proofs_for_shard(block.hash(), shard_id)
                    .iter()
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        } else {
            block.chunks().iter_new().any(|new_chunk| {
                let shard_id = new_chunk.shard_id();
                let prev_shard_index = epoch_manager
                    .get_prev_shard_id_from_prev_hash(block.header().prev_hash(), shard_id)
                    .unwrap()
                    .2;
                let prev_height_included =
                    prev_block.chunks().get(prev_shard_index).unwrap().height_included();
                let incoming_receipts_proofs = get_incoming_receipts_for_shard(
                    &chain.chain_store,
                    epoch_manager,
                    shard_id,
                    &shard_layout,
                    *block.hash(),
                    prev_height_included,
                    ReceiptFilter::TargetShard,
                )
                .unwrap();
                incoming_receipts_proofs
                    .iter()
                    .flat_map(|response| response.1.iter())
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        };

        if oversized {
            return;
        }

        block = prev_block;
    }
}

fn receipt_is_oversized(receipt: &Receipt, max_receipt_size: u64) -> bool {
    let receipt_size: u64 = borsh::object_length(receipt).unwrap().try_into().unwrap();
    if receipt_size > max_receipt_size {
        tracing::info!(%receipt_size, %max_receipt_size, "found receipt above max size");
        return true;
    }
    false
}
