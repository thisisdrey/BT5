### No vulnerability found for this question.

**Analysis:**

The claimed binding — that `verify_intent_nonce` never checks nonce expiry while `is_nonce_cleanable` does, creating desync — does not hold. Both checks use the identical condition `deadline < Timestamp::now()`:

- `verify_intent_nonce` explicitly checks `deadline < Timestamp::now()` and returns `DefuseError::NonceExpired` if the nonce's own deadline has passed, in addition to enforcing `intent_deadline > deadline` (the payload's deadline may not exceed the nonce's deadline). [1](#0-0) 

- `is_nonce_cleanable` in the garbage collector uses the exact same condition on the same `deadline` field. [2](#0-1) 

These are the same check expressed inline rather than through `ExpirableNonce::has_expired()`, which itself is defined as `self.deadline < Timestamp::now()`. [3](#0-2) 

Not calling the named method is a style difference, not a logic divergence — there is no window where a nonce is considered "not cleanable" by one check but "not expired" by the other.

Critically, the payload's own `deadline` is checked *before* nonce commitment, independent of the nonce's deadline: [4](#0-3) 

Because `verify_intent_nonce` enforces `intent_deadline <= nonce.deadline`, the signed payload's own `deadline` can never be later than `nonce.deadline`. Consequently, by the time `nonce.deadline < Timestamp::now()` becomes true (making the nonce eligible for garbage collection), the payload's own `intent_deadline` has already necessarily expired (since it is `<= nonce.deadline`). Any attempt to resubmit the original signed payload after GC clears the nonce will be rejected at line 66 (`DeadlineExpired`) before nonce logic is even reached — exactly the outcome the question's own "Proof idea" anticipates as the expected (non-exploitable) result.

The described attack requires "a hypothetical still-live off-chain signature" reused after its own signed deadline expired, which is not a real code path: the deadline is part of the NEP-413 signed message and is independently enforced. There is no mechanism in this codebase that allows resubmission of a payload whose signed `deadline` has already elapsed. Therefore there is no replay, no double-settlement, and no fund movement without authorization — no Critical/High impact as scoped.
