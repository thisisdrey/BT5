## Title
Snowbridge outbound-queue-v2 settles pending orders and pays relayer rewards without checking delivery `success` - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

## Summary
`process_delivery_receipt` in `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs` decodes an `InboundMessageDispatched` event from Ethereum into a `DeliveryReceipt` struct that carries a `success: bool` flag reflecting whether the dispatched command actually executed on the Gateway contract, but the pallet logic never reads or branches on `receipt.success` before paying the relayer reward and removing the `PendingOrder`. [1](#0-0)  This allows the relayer reward to be paid and the pending order to be permanently cleared even when the underlying command execution on Ethereum failed.

## Finding Description
The `DeliveryReceipt` struct decoded via `TryFrom<&Log>` includes a `success` field taken directly from the Ethereum `InboundMessageDispatched(nonce, topic, success, reward_address)` event. [2](#0-1)  The public extrinsic `submit_delivery_receipt` verifies the proof, decodes the receipt, and forwards it to `process_delivery_receipt` without any success-based gating. [3](#0-2) 

`process_delivery_receipt` only checks the gateway address matches and that a `PendingOrder` exists for the nonce; if `order.fee > 0` it unconditionally registers the reward and then unconditionally removes the `PendingOrder`, emitting `MessageDelivered`: [4](#0-3)  The `success` field of `receipt` is decoded but never inspected anywhere in this function. A `grep` across the pallets directory confirms no other logic in `outbound-queue-v2` or downstream `system-v2` pallet reconciles a failed dispatch via this `success` flag — the matches found in `system-v2/src/lib.rs` are unrelated occurrences of the word "success" in that file, not consumers of `DeliveryReceipt::success`.

The commands dispatched by this pipeline (e.g. `Command::CallContract { gas, .. }`) allow the sender to supply an on-chain-committed maximum gas value that becomes the actual gas passed to the target contract call via `ConstantGasMeter::maximum_dispatch_gas_used_at_most`. [5](#0-4)  If this gas is insufficient, the command reverts on Ethereum and the Gateway emits `success=false`, yet the settlement path described above pays out and clears state as though the message was delivered successfully.

All integration tests for this extrinsic construct `DeliveryReceipt { success: true, .. }` exclusively; none exercise `success: false`, confirming the failure path is untested and unhandled by the pallet. [6](#0-5) 

## Impact Explanation
This violates the invariant that message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically. A relayer is paid `order.fee` and the `PendingOrder` is destroyed for a message whose on-chain command execution on Ethereum actually failed, resulting in incorrect/duplicate-style settlement (payout without corresponding successful effect) and permanent loss of the ability to retry or reconcile the failed command, since `PendingOrders::remove(nonce)` is unconditional. This matches the "duplicate settlement or payout" and "public underpriced work" impact categories for the Snowbridge/Polkadot SDK program.

## Likelihood Explanation
No privileged or malicious actor is required. Any user can construct a v2 XCM message containing `Command::CallContract` with an insufficient `gas` value (or otherwise cause execution to revert on Ethereum for other commands), and any honest relayer submitting the resulting `InboundMessageDispatched(success=false, ...)` event via the public `submit_delivery_receipt` extrinsic will trigger reward payment and order removal regardless of the `success` value. The only gates present — `GatewayAddress` match and nonce lookup — do not validate `success`.

## Recommendation
`process_delivery_receipt` should branch on `receipt.success`. On `success == true`, proceed with the existing reward payment and `PendingOrders::remove`. On `success == false`, avoid paying the reward and either retain the order for retry/reprocessing or transition to an explicit failure-handling path (e.g., refund fee to sender, emit a distinct `MessageDeliveryFailed` event) instead of silently discarding the failure signal.

## Proof of Concept
1. A user submits a v2 XCM message with `Command::CallContract { target, calldata, gas: <too_low>, value }` via the `Transact`/`ContractCall::V1` conversion path in `XcmConverter::convert`. [7](#0-6) 
2. `do_process_message` commits the command's gas verbatim and stores a `PendingOrder { nonce, fee, .. }`. [8](#0-7) 
3. On Ethereum, the Gateway executes the command with insufficient gas, the call reverts, and the Gateway emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
4. An honest relayer submits this event via `submit_delivery_receipt`; verification succeeds and `DeliveryReceipt::try_from` correctly decodes `success=false`.
5. `process_delivery_receipt` ignores `success`, pays `order.fee` to `reward_account`, and removes the `PendingOrder`, emitting `Event::MessageDelivered` despite the underlying command never having taken effect — reproducible as a unit test asserting `EthereumOutboundQueueV2::process_delivery_receipt` succeeds and pays a reward when `success: false` is supplied, analogous to the existing `success: true` test at `cumulus/parachains/integration-tests/emulated/tests/bridges/bridge-hub-westend/src/tests/snowbridge_v2_outbound.rs:409-418`.

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
