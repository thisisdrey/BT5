## Title
Missing zero-address validation for `new_authority` in `transfer_to_new_account`/`transfer_to_new_account_pda` permanently locks migrated positions - (File: `programs/marginfi/src/instructions/marginfi_account/transfer_account.rs`)

### Summary
Analogous to the BullvBear finding where `transferPosition()` to `address(0)` was left completely unchecked and used to defeat a "matched-once" invariant, marginfi's account-migration instructions (`transfer_to_new_account` and `transfer_to_new_account_pda`) accept an arbitrary, completely unchecked `new_authority` account, including `Pubkey::default()`. The `TransferToNewAccount`/`TransferToNewAccountPda` account structs explicitly document this as unchecked, and there is no on-chain guard preventing `new_authority == Pubkey::default()`. [1](#0-0) [2](#0-1) 

### Finding Description
`transfer_to_new_account` and `transfer_to_new_account_pda` migrate all of an account's positions (`lending_account`) from `old_marginfi_account` into a fresh `new_marginfi_account` whose `authority` is set to whatever `new_authority` pubkey is supplied, with the comment `/// CHECK: WARN: New authority is completely unchecked`. [3](#0-2) [4](#0-3) 

The only protections present are:
- `old_account.migrated_to == Pubkey::default()` (prevents double-migrating the *old* account).
- `old_account.active_orders == 0` and various flag checks (flashloan/receivership/order-execution). [5](#0-4) 

None of these checks validate `new_authority` itself. A `MarginfiAccount` whose `authority` field equals `Pubkey::default()` can never be controlled again on-chain, because `Pubkey::default()` has no corresponding private key and thus can never satisfy a `Signer<'info>` constraint used everywhere else in the program (deposit/withdraw/borrow/repay/close, etc., all gate on `has_one = authority @ MarginfiError::Unauthorized`). This mirrors the root cause of the referenced report: an instruction that transfers "ownership" of a position/order to an attacker- or user-controlled destination, including the zero address, without any validation, undermining an invariant the rest of the protocol relies on (here: "every account has a controllable authority" rather than "every order is matched at most once").

Notably, the CLI (`p0-cli`) *does* add this check client-side: [6](#0-5) 
but this is not enforced by the on-chain program, meaning any direct caller (a different frontend, an integrator building the instruction manually, or a CPI caller per the doc comment `"or create the account manually and use transfer_to_new_account to gift it to the owner you wish"`) can bypass it entirely. [7](#0-6) 

### Impact Explanation
If `new_authority` is passed as `Pubkey::default()` (accidentally by a buggy integrator/CPI caller, or via a crafted transaction), all of the old account's lending positions (deposits and borrows) are moved into a brand-new `MarginfiAccount` whose `authority` is the zero pubkey. Because `Signer<'info>` can never be satisfied by the zero pubkey, no instruction gated by `has_one = authority` can ever operate on the new account again: deposits, withdrawals, borrows, repays, order placement, and account close all become permanently inaccessible. The old account is simultaneously disabled (`ACCOUNT_DISABLED`) and zeroed. The net effect is a **permanent lock/freeze** of the user's collateral and debt positions with no recovery path (an admin freeze/liquidation could still act on it, but the rightful owner permanently loses direct control).

### Likelihood Explanation
Likelihood is limited primarily by the fact that the "happy path" CLI blocks this. However, the check is purely client-side and not enforced by the Anchor account constraints, so any alternate client, SDK, or third-party/CPI integration invoking `transfer_to_new_account`/`transfer_to_new_account_pda` directly (which the doc-comment for `marginfi_account_initialize` explicitly encourages third parties to do) can trigger it, whether through a bug in argument construction or a malicious relayer substituting the destination authority. This is a realistic "missing zero-address check" class of bug on a high-impact, irreversible state transition.

### Recommendation
Add an on-chain check in `transfer_to_new_account` and `transfer_to_new_account_pda` (mirroring the existing `check_eq!` pattern used for `migrated_to`) that rejects `new_authority == Pubkey::default()`, e.g.:
```rust
check!(
    ctx.accounts.new_authority.key() != Pubkey::default(),
    MarginfiError::IllegalAction,
    "Cannot transfer to the zero pubkey"
);
```
placed in both `transfer_to_new_account` (`programs/marginfi/src/instructions/marginfi_account/transfer_account.rs:51`) and `transfer_to_new_account_pda` (same file, `:182`), so the invariant is enforced by the program itself rather than relying on a client-side guard.

### Proof of Concept
1. Create a `MarginfiAccount` with authority `A` and deposit collateral / open borrow positions.
2. Directly build and send a `TransferToNewAccount` instruction (bypassing the `p0-cli` helper that would reject it) with `new_authority = Pubkey::default()`.
3. The instruction succeeds: `old_account` is disabled and zeroed, `new_account.authority = Pubkey::default()` now holds all migrated balances. [4](#0-3) 
4. Attempt any subsequent operation on `new_account` (deposit/withdraw/borrow/repay/close) signed by any keypair — all fail `has_one = authority @ MarginfiError::Unauthorized` since no signer can ever equal `Pubkey::default()`. The migrated funds are permanently inaccessible to any user-controlled key.
