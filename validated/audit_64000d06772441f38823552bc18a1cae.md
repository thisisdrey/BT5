### Title
Attached deposit is permanently lost when the wallet contract's registrar/storage-balance sub-call fails before the refund-aware callback runs - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
The near-wallet-contract (eth-implicit account wallet) tracks an external caller's attached NEAR deposit via `CallerDeposit` so it can be refunded if the outer promise chain ultimately fails [1](#0-0) . That refund logic is only implemented in `rlp_execute_callback`, on the `PromiseResult::Failed` branch [2](#0-1) . However, two intermediate callbacks (`address_check_callback` and `nep_141_storage_balance_callback`) have early-return error paths that never forward execution to `rlp_execute_callback`, and therefore never invoke the refund. In those paths the `caller_deposit` value is simply dropped.

### Finding Description
`inner_rlp_execute` creates a `CallerDeposit` from the attached deposit whenever the predecessor differs from the current account [3](#0-2) , and threads it through the multi-step promise chains for `EOABaseTokenTransfer` (via the address registrar) and `ERC20Transfer` (via NEP-141 storage checks) so the deposit can eventually be returned if the whole chain fails [4](#0-3) .

The only code that actually performs the refund is inside `rlp_execute_callback`:
```
PromiseResult::Failed => {
    if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
        let refund_promise = env::promise_batch_create(&account_id);
        env::promise_batch_action_transfer(refund_promise, NearToken::from_yoctonear(yocto_near.into()));
    }
    ...
}
``` [2](#0-1) 

But `address_check_callback` has two branches that return `PromiseOrValue::Value(...)` directly, bypassing `rlp_execute_callback` entirely, while still holding a `caller_deposit` that is discarded without any refund:
- when the registrar lookup call itself fails: `PromiseResult::Failed => return PromiseOrValue::Value(ExecuteResponse { ... error: "Call to Address Registrar contract failed" })` [5](#0-4) 
- when the registrar response cannot be deserialized: `Err(_) => return PromiseOrValue::Value(ExecuteResponse { ... error: "Unexpected response from account registrar" })` [6](#0-5) 
- when the target resolves to an existing named account and the caller is not the wallet itself: `return PromiseOrValue::Value(ExecuteResponse { ... error: "Invalid target..." })` [7](#0-6) 

Similarly, `nep_141_storage_balance_callback` has matching early-return branches that drop `caller_deposit` without refunding:
- when the `storage_balance_of` call fails [8](#0-7) 
- when the response cannot be deserialized [9](#0-8) 
- when the stored action is unexpectedly not a `FunctionCall` [10](#0-9) 

In every one of these paths the attached deposit (already transferred to the wallet contract's balance when the original `rlp_execute` transaction was sent, since `rlp_execute` is `#[payable]` [11](#0-10) ) stays on the wallet contract's balance with no code path left to reclaim it: the `CallerDeposit` value that carried the recipient/amount information is simply discarded when the function returns. Unlike the Swivel/Illuminate report, the wallet contract has no `withdraw`/admin-rescue function at all (confirmed by search), so there is no way — administrative or otherwise — to recover the funds afterward.

### Impact Explanation
This is a genuine, ordinary-user-reachable fund freeze: any relayer or external caller who attaches a deposit while acting on behalf of a different `current_account_id` (`CallerDeposit::new` requires `current_account_id != predecessor_account_id` [3](#0-2) ) loses that deposit permanently whenever the address-registrar lookup or the NEP-141 `storage_balance_of` call fails or returns unparsable data — both are realistic failure modes (e.g., target registrar/token contract temporarily out of gas, panicking, or returning a malformed/incompatible response), not adversarial-node behavior. There is no recovery mechanism in the contract, so this is a permanent loss of funds for the depositor, matching the "permanent freezing/loss of funds" bar.

### Likelihood Explanation
Likelihood is meaningfully non-trivial: the `EOABaseTokenTransfer` path with `address_check` and the `ERC20Transfer` path are core, commonly used features of the eth-implicit wallet emulation (Ethereum-style base-token transfers to unregistered accounts and ERC-20 style transfers). Any external-caller cross-contract call failure against the address registrar or the target NEP-141 token (rate limiting, temporary panic, incompatible non-standard token contract, insufficient gas) triggers the loss — this does not require a malicious actor, only an unlucky failed sub-call, which is an intended, non-privileged usage path of the contract.

### Recommendation
Thread `caller_deposit` refund logic into every early-return branch of `address_check_callback` and `nep_141_storage_balance_callback` (or route all of them uniformly through the existing refund logic in `rlp_execute_callback`) so that whenever a `CallerDeposit` exists and the chain terminates in failure, a `promise_batch_action_transfer` is issued back to `account_id` for `yocto_near`, mirroring the handling already present in `rlp_execute_callback`.

### Proof of Concept
1. A relayer account `R` (different from the eth-implicit account `E`) submits `rlp_execute` on `E`'s wallet contract with an Ethereum transaction that is an `EOABaseTokenTransfer` to an address requiring an `address_check` (target is another eth-implicit account), attaching a deposit `d` (e.g., to cover a `storage_deposit`). This constructs `CallerDeposit { account_id: R, yocto_near: d }` and calls the address registrar, then `address_check_callback` [12](#0-11) .
2. The address-registrar contract's `lookup` call fails (e.g., registrar temporarily out of gas or panics).
3. `address_check_callback` hits `PromiseResult::Failed` and returns `ExecuteResponse { success: false, ... }` directly, without ever constructing a refund promise for `R` [5](#0-4) .
4. `d` yoctoNEAR, already transferred to `E`'s wallet contract balance as part of step 1's attached deposit, remains stuck there permanently; there is no withdraw/rescue entry point in the contract to return it to `R`.

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}
