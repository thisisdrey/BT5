### Title
Interest accrual bypasses the `maxTotalSupply` debt cap and permanently reverts `issue`/`mint`/`leverage` until debt is repaid - (File: contracts/DebtToken.sol)

### Summary
The Allora M-9 bug class is "a cumulative counter is incremented past a cap because the cap check is missing on one path, and a later, periodic/recurring operation then breaks (revert/liveness)." Metronome's `DebtToken` has the same shape: `accrueInterest()` grows `totalSupply_` by the accrued interest without checking `maxTotalSupply`, while `_mint()` enforces the cap on the stored value. Once interest pushes `totalSupply_` over the cap, every `issue()`/`mint()` (and therefore SmartFarmingManager `leverage`) call reverts with `SurpassMaxDebtSupply`, and the breach is self-reinforcing because interest keeps accruing on the over-cap supply.

### Finding Description
- `DebtToken.accrueInterest()` adds `_interestAmountAccrued` to `totalSupply_` unconditionally — there is no `maxTotalSupply` check on this path (`contracts/DebtToken.sol:169-179`). The only failure mode it anticipates is the *synthetic* token fee mint, which is wrapped in `try/catch` into `pendingInterestFee`; the debt counter itself is never cap-checked.
- `DebtToken._mint()` then enforces `totalSupply_ + amount_ > maxTotalSupply → revert SurpassMaxDebtSupply` (`contracts/DebtToken.sol:590-591`).
- `issue()` is the public entry point: any user calls `DebtToken.issue(amount_, to_)` (via `Pool.issue`), which first calls `accrueInterest()` (`contracts/DebtToken.sol:248`) and then `_mint()` (`contracts/DebtToken.sol:262`).
- `mint()` (`contracts/DebtToken.sol:328-345`) is called by `SmartFarmingManager` during `leverage`; it also calls `accrueInterest()` then `_mint()`.
- Concretely: set `maxTotalSupply = S`. Over time `accrueInterest()` sets `totalSupply_ = S + i` (interest `i` > 0, no revert — the counter silently crosses the cap, exactly like `AddEcosystemTokensMinted` crossing the Allora treasury cap). From that block onward, every subsequent `accrueInterest()` only grows `totalSupply_` further (`_interestAmountAccrued` is proportional to `totalSupply_`, `contracts/DebtToken.sol:562`), so `issue()`/`mint()`/`leverage()` deterministically revert. The cap invariant (`totalSupply_ <= maxTotalSupply`) is permanently violated and the minting surface is bricked until someone voluntarily repays enough debt (`repay`/`repayAll`/`liquidate` via `_burn` still work) or the governor raises the cap.
- No guard prevents this: `whenNotShutdown`, `nonReentrant`, `onlyIfDebtTokenIsActive`, and `onlyIfSyntheticTokenIsActive` are all satisfied in the deployed configuration, and `accrueInterest()` is permissionless (`public`).

### Impact Explanation
- Broken invariant: the protocol's stated debt supply cap (`maxTotalSupply`, documented in `docs/emergency-flags.md:47` as capping `issue` and `leverage`) does not hold — debt supply exceeds it with no transaction ever reverting at the moment of breach.
- Temporary freezing/liveness: all new debt issuance (`issue`, leverage via `SmartFarmingManager.mint`/`flashIssue` flows that call `mint()`) reverts deterministically once the cap is crossed. Users cannot open or lever positions; the freeze persists as long as stored `totalSupply_` stays above the cap, and repaying enough debt to unfreeze requires a third party's voluntary action. This mirrors the Allora impact (cap not holding + recurring function compromised), classified Medium.

### Likelihood Explanation
- Requires no attacker privileges or even an attacker: `accrueInterest()` is permissionless and interest accrues automatically with `block.timestamp`. In any deployment where a DebtToken's `interestRate > 0` and outstanding debt approaches its configured `maxTotalSupply`, the cap is crossed inevitably — the same "once a month emissions hit the cap" dynamic as the original report.
- `flashIssue()` additionally bypasses the debt cap entirely by design (it mints synth without minting debt), but the liveness compromise via `accrueInterest` + `_mint` stands on its own.

### Recommendation
Apply the cap check inside `accrueInterest()` symmetrically with `_mint`, e.g.:

```diff
 if (_interestAmountAccrued > 0) {
     totalSupply_ += _interestAmountAccrued;
+    if (totalSupply_ > maxTotalSupply) {
+        // clamp accrued supply to the cap so issuance is not permanently bricked
+        totalSupply_ = maxTotalSupply;
+        _interestAmountAccrued = maxTotalSupply - (totalSupply_ - _interestAmountAccrued);
+    }
     debtIndex = _debtIndex;
     ...
 }
```

Alternatively, cap `_interestAmountAccrued` itself (adjusting `debtIndex` consistently) so the stored supply can never exceed `maxTotalSupply`, matching the "cap `tokensToMint` at the remaining mintable amount" fix recommended in the original report.

### Proof of Concept
Hardhat fork-style reproduction:

```ts
// setup: pool with a DebtToken (interestRate > 0), user with collateral
await debtToken.connect(governor).updateMaxTotalSupply(parseEther('100'))
await pool.connect(alice).deposit(collateral.address, parseEther('1000'))
// mint debt up to just under the cap
await debtToken.connect(alice).issue(parseEther('99'), alice.address)   // totalSupply_ = 99

// time passes; anyone (or any protocol call) triggers accrual
await time.increase(30 * DAY)
await debtToken.accrueInterest()                                        // succeeds; totalSupply_ = 99 + interest > 100  <-- cap silently crossed

// from now on, all issuance reverts permanently
await expect(
  debtToken.connect(bob).issue(parseEther('1'), bob.address)
).revertedWithCustomError(debtToken, 'SurpassMaxDebtSupply')

// accrueInterest keeps succeeding and widening the breach
await time.increase(30 * DAY)
await debtToken.accrueInterest()                                        // still no revert; totalSupply_ grows further
await expect(
  debtToken.connect(bob).issue(parseEther('1'), bob.address)
).revertedWithCustomError(debtToken, 'SurpassMaxDebtSupply')
// leverage via SmartFarmingManager -> debtToken.mint() reverts identically

        IMasterOracle masterOracle_,
        address account_,
        uint256 amount_
    ) private onlyIfDebtTokenIsActive updateRewardsBeforeMintOrBurn(account_) {
        if (account_ == address(0)) revert MintToNullAddress();

        uint256 _debtFloorInUsd = pool_.debtFloorInUsd();
        uint256 _balanceBefore = balanceOf(account_);

        if (
            _debtFloorInUsd > 0 &&
            masterOracle_.quoteTokenToUsd(address(syntheticToken), _balanceBefore + amount_) < _debtFloorInUsd

            revert DebtLowerThanTheFloor();
