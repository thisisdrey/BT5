## Finding

### Title
Stale `YieldIdToDataId`/`DataIdToYieldId`/`PromiseYieldReceipt`/`PromiseYieldStatus` rows survive `DeleteAccountAction`, enabling authorization bypass on a recreated account - ([File: core/store/src/utils/mod.rs])

### Summary
`remove_account` in `core/store/src/utils/mod.rs` deletes an account's `Account`, `ContractCode`, access/gas keys, and `ContractData`, but never calls `remove_yield_id_mappings` or clears `PromiseYieldReceipt`/`PromiseYieldStatus` rows for that account. Because these rows are keyed only by `account_id` (not by any incarnation/version of the account), they persist across account deletion and re-creation, letting a stale, attacker-authored yielded callback (with an attacker-chosen `method_name`/`arguments`) later execute as a self-call against whatever contract is subsequently deployed under the same account name.

### Finding Description
`promise_yield_create_with_id` (`runtime/near-vm-runner/src/logic/logic.rs:3727`) stores its duplicate-detection state via `set_yield_id_mapping` (`core/store/src/utils/mod.rs:281`), writing both `TrieKey::YieldIdToDataId{receiver_id, yield_id}` and `TrieKey::DataIdToYieldId{receiver_id, data_id}` [1](#0-0) . The corresponding `PromiseYield` receipt (containing the attacker-chosen `method_name`/`arguments`/`deposit`, with `receiver_id == predecessor_id == current_account_id`) is persisted via `set_promise_yield_receipt` [2](#0-1) , and a `PromiseYieldTimeout{account_id, data_id, expires_at}` entry is enqueued in the global timeout queue.

When `DeleteAccountAction` is processed, `action_delete_account` (`runtime/runtime/src/actions.rs:314`) calls `remove_account` [3](#0-2) . `remove_account` only removes `Account`, `ContractCode`, access/gas keys, and `ContractData` rows [4](#0-3) . It never invokes `remove_yield_id_mappings`, nor deletes `PromiseYieldReceipt`/`PromiseYieldStatus` rows for the account being deleted.

Consequently, after deletion:
- `has_yield_id_mapping` (checked by `create_promise_yield_receipt_with_id`, `runtime/runtime/src/ext.rs:378`) still returns `true` for the old `yield_id`, since the `YieldIdToDataId` row is untouched [5](#0-4) .
- `resolve_promise_yield_timeouts` (`runtime/runtime/src/lib.rs:3009`) only checks `state_update.contains_key(&promise_yield_key)` (i.e. whether the `PromiseYieldReceipt` row still exists) — not whether the account itself still exists — before synthesizing a `PromiseResume` receipt destined for `account_id` [6](#0-5) .
- When that `PromiseResume` (or an explicit resume) is later processed, `apply_action_receipt` looks up `get_promise_yield_receipt(state_update, account_id, data_id)` and, finding the stale row, executes it as an action receipt against whatever now lives at `account_id` [7](#0-6) .

If `account_id` is later recreated by a different party (e.g. a factory/platform pattern that deploys identical, open-source contract code to reused sub-account names such as `user.platform.near`), the leftover receipt executes as a `receiver_id == predecessor_id == current_account_id` self-call carrying the *original* attacker's `method_name`/`arguments`. Many NEAR contracts guard privileged internal callbacks (exactly the kind of method used as a yield-resume callback, e.g. withdrawal finalization) with a `predecessor_id == current_account_id` check. Because the stale receipt satisfies that check on the new account, the attacker can pre-plant a call to a known-public privileged method with attacker-chosen arguments (e.g. redirecting a withdrawal to an attacker-controlled destination), which fires once the new account's contract is deployed and the timeout/resume executes.

### Impact Explanation
This is an authorization-escalation vector: an unprivileged attacker plants a stale, privilege-satisfying (`predecessor_id == current_account_id`) callback receipt under an account name, deletes that account, and the receipt survives to be executed against a subsequently (re)deployed contract at the same name. Where such contracts gate sensitive operations (fund transfers, withdrawals) on self-call checks, this enables theft of the new occupant's funds — matching the "authorization escalation across accounts or promises" / "theft of user funds" bounty categories. The bug is rooted precisely in `remove_account` (`core/store/src/utils/mod.rs`) never calling `remove_yield_id_mappings` or clearing `PromiseYieldReceipt`/`PromiseYieldStatus`.

### Likelihood Explanation
Precondition: the same account name must be deleted and later recreated with a different, but predictable (often open-source/shared factory-deployed), contract. This is realistic in dapp patterns that provision/reclaim named sub-accounts (staking-pool factories, linkdrop-style onboarding, account-abstraction relayers). Cost to the attacker is minimal (one `promise_yield_create_with_id` call plus one `DeleteAccountAction`), and the leftover state persists indefinitely (bounded only by the yield timeout window for the eventual auto-resume, or forever if explicitly resumed by someone acting on the new account). Exploitation requires no privileged access, keys, or social engineering — only normal transaction submission.

### Recommendation
In `remove_account` (`core/store/src/utils/mod.rs`), also enumerate and remove all `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, and `DataIdToYieldId` rows scoped to the account being deleted (mirroring the existing access-key/gas-key/contract-data iteration-and-removal pattern), and ensure any outstanding `PromiseYieldTimeout` queue entries referencing the deleted account are treated as no-ops (e.g. by re-checking account existence, not just `PromiseYieldReceipt` existence, in `resolve_promise_yield_timeouts`).

### Proof of Concept
Integration test plan (analogous to `integration-tests/src/tests/runtime/test_yield_resume.rs`):
1. Deploy a contract on `victim.near`; call `promise_yield_create_with_id` with a chosen `yield_id` X, letting the receipt execute so `YieldIdToDataId{victim.near, X}`, `DataIdToYieldId{victim.near, D1}`, and `PromiseYieldReceipt{victim.near, D1}` are written.
2. Submit `DeleteAccountAction` for `victim.near`.
3. Directly query state (or use `get_data_id_for_yield_id`) and assert `YieldIdToDataId{victim.near, X}` still resolves to `D1` — proving the mapping survived deletion.
4. Recreate `victim.near` (`CreateAccountAction` + `DeployContractAction`) with a different contract exposing a self-call-guarded privileged method matching the attacker's originally chosen `method_name`.
5. Advance blocks past the yield timeout (or submit an explicit resume) and assert the `PromiseResume` executes the stale `PromiseYieldReceipt`, invoking the privileged method on the new contract with `predecessor_id == current_account_id == victim.near`, despite no legitimate self-call having been made by the new contract's own logic.

pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
