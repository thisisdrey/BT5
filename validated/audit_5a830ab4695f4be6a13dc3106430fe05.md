## Finding: Floating-point precision divergence in `ExchangeProcessor`'s Bancor-formula AMM enables value extraction from Exchange pools

### Title
Floating-point precision divergence in the legacy Bancor-formula AMM math allows draining `Exchange`/`ExchangeV2` pools via crafted trade sequences - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
The KyberSwap exploit exploited a sub-`0.00000000001%` precision error in tick/liquidity math to drain concentrated-liquidity pools via carefully engineered swap sizes. The closest reachable analog in java-tron is the TRX/TRC10 `Exchange` AMM (Bancor-style relay-token formula), whose legacy calculation path (`ExchangeProcessor`) performs the core swap math in IEEE-754 `double` arithmetic rather than exact decimal math, and this path remains reachable by any unprivileged account issuing `ExchangeTransactionContract` transactions.

### Finding Description
`ExchangeCapsule.transaction()` selects between two swap-math implementations based on the `allowHardenExchangeCalculation` dynamic parameter: [1](#0-0) 

When hardened calc is not enabled, it uses `ExchangeProcessor`, whose `exchangeToSupply`/`exchangeFromSupply` compute the Bancor formula entirely with `double` primitives and `Maths.pow`: [2](#0-1) 

The project's own test suite (`ExchangeProcessorTest.testStrictMath`) explicitly demonstrates and asserts that the legacy double-based path and the exact `SafeExchangeProcessor` (BigDecimal-based) path produce **different, non-equal results** for the same swap inputs: [3](#0-2) 

This is architecturally the same bug class as KyberSwap: a floating point / fixed-point precision approximation is used to compute a bonding-curve trade output, and the discrepancy between the "true" (exact) value and the approximated value can be systematically exploited by choosing specific `sellTokenQuant` inputs (analogous to Kyber's "extremely precise swaps" that pushed the tick math past its rounding boundary). Repeated `ExchangeTransactionContract` calls with quantities chosen to maximize the `double`-vs-exact divergence let an attacker consistently extract more of the counter-asset than the exact invariant would allow, each time draining a small amount from the pool's other token balance — the effect compounds over many transactions, exactly mirroring how KyberSwap's attacker used many "extremely precise swaps" to accumulate the drained value.

The bug is reachable from a single unprivileged, signed transaction (`ExchangeTransactionContract`) processed by `ExchangeTransactionActuator`, which calls `exchangeCapsule.transaction(tokenID, tokenQuant, dynamicStore.allowStrictMath(), allowHarden())`: [4](#0-3) 

Whether the exploitable legacy path is used depends entirely on the `allowHardenExchangeCalculation` committee parameter — on any network/chain state where this hardening has not been activated (which is the historical default, since `SafeExchangeProcessor` was added as a later mitigation), the double-precision path remains live and exploitable.

### Impact Explanation
Exploiting the `double`-based Bancor formula divergence lets an attacker who repeatedly issues `ExchangeTransactionContract` transactions extract more value from an `Exchange`/`ExchangeV2` pool than the exact invariant permits, draining the counter-token balance held by the pool — a direct theft-of-funds / unbacked-balance impact matching the "concrete unauthorized account operation, theft ... of funds" bar. Because AMM pools of this type are funded by third-party liquidity providers via `ExchangeInjectActuator`, the loss is borne by LPs, similar to how KyberSwap LPs lost funds.

### Likelihood Explanation
Likelihood is Medium: exploitation requires the attacker to have (or acquire) knowledge of the exact rounding behavior of `Maths.pow`/`double` division at specific balance/quantity combinations, and requires the target Exchange pool to still be running with `allowHardenExchangeCalculation` disabled (the legacy default). The precision differential is provably real (confirmed by the project's own regression test), but requires precise crafting of trade sizes, similar in spirit to the "carefully engineered" KyberSwap exploit, and each individual trade's edge is small, requiring iteration to accumulate meaningful drain.

### Recommendation
- Force `allowHardenExchangeCalculation` (and the `SafeExchangeProcessor` BigDecimal-based path) to be the only path, deprecating and removing the double-based `ExchangeProcessor` entirely rather than gating it behind a committee-toggled parameter.
- Add invariant checks after every `Exchange`/`ExchangeV2` swap (e.g., constant-product/Bancor invariant should never decrease beyond a documented, minimal fee-derived tolerance) and reject transactions that violate it, regardless of which processor is active.
- Add exhaustive property-based/fuzz tests comparing `ExchangeProcessor` output against `SafeExchangeProcessor` across the full range of realistic balances/quantities to detect any further exploitable divergence before hardening is universally enabled.

### Proof of Concept
1. Deploy/observe a live `Exchange` (TRX/TRC10) pool where `allowHardenExchangeCalculation == 0` (legacy default).
2. Compute, offline, the balances/quantities for which `ExchangeProcessor.exchange()` (double math) yields a materially larger `buyTokenQuant` than `SafeExchangeProcessor.exchange()` (exact BigDecimal math) would for the same inputs — as already demonstrated systematically by `ExchangeProcessorTest.testStrictMath`, which shows non-equal results for dozens of realistic balance/quantity triples: [5](#0-4) 
3. Submit repeated `ExchangeTransactionContract` transactions with `tokenId`/`quant` chosen from step 2 via `ExchangeTransactionActuator.execute()`, each time receiving more of the counter-token than the exact bonding curve would allow.
4. Repeat across many blocks to accumulate a meaningful drain of the pool's counter-token balance, mirroring KyberSwap's strategy of executing "extremely precise swaps" repeatedly to exploit a sub-percent precision failure.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }
