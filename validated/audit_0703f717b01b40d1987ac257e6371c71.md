Audit Report

## Title
Relayer reward paid and order settled regardless of on-chain message execution outcome (`success` field ignored) - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
The Ethereum Gateway's `InboundMessageDispatched` event includes a `success: bool` field indicating whether the dispatched command actually succeeded on Ethereum, and `DeliveryReceipt::try_from` correctly decodes it, but `Pallet::process_delivery_receipt` never reads `receipt.success` before paying the relayer reward and removing the `PendingOrder`. This causes reward payout and permanent order settlement even when the Ethereum-side command execution failed.

## Finding Description
`submit_delivery_receipt` [5](#0-4)  is callable by any signed account and only requires a Merkle-proved Ethereum event log verified by `T::Verifier` matching the configured `GatewayAddress`. `process_delivery_receipt` [1](#0-0)  checks `receipt.gateway` and looks up `PendingOrders` by `receipt.nonce`, but unconditionally calls `T::RewardPayment::register_reward` and `<PendingOrders<T>>::remove(nonce)` without ever inspecting `receipt.success`, which was decoded from the genuine Gateway event log per [3](#0-2) . This breaks the invariant that queue/order settlement should only advance after execution succeeds — the receipt only proves the Gateway processed/attempted the command, not that its effects took hold.

## Impact Explanation
Once `PendingOrders::remove(nonce)` runs, the pallet exposes no retry mechanism for that nonce, so a failed command's tracking state is permanently lost while the relayer is still paid from `order.fee`. This is a runtime logic bug that compromises intended settlement behavior: reward funds are misallocated to relayers for deliveries whose on-chain effects failed, and the bridge loses the ability to retry or refund the failed nonce.

## Likelihood Explanation
This requires a genuine `success=false` event emitted by the real Gateway contract (a real command execution failure on Ethereum), which is not attacker-forged data — the proof must pass `T::Verifier`. However, no privileged access, malicious relayer, or compromised prover assumption is needed; any ordinary relayer submitting a legitimate failure receipt via the public `submit_delivery_receipt` extrinsic triggers the flawed unconditional payout/removal path during normal operation.

## Recommendation
Branch on `receipt.success` in `process_delivery_receipt`: only pay the reward and remove the `PendingOrder` when `success == true`; on `false`, emit a distinct event (e.g., `MessageDeliveryFailed`) and implement a defined retry or refund policy instead of unconditionally rewarding and dropping the order.

## Proof of Concept
1. `do_process_message` queues a message, inserting `PendingOrders[nonce] = { fee, block_number }` [6](#0-5) .
2. The relayer delivers the message to the Ethereum Gateway; the dispatched command fails there, and the Gateway emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. The relayer builds a Merkle proof for this genuine log and calls `submit_delivery_receipt(event)`.
4. `T::Verifier::verify` succeeds and `DeliveryReceipt::try_from` decodes `success=false` correctly, but `process_delivery_receipt` never reads `receipt.success`.
5. `T::RewardPayment::register_reward` pays the relayer and `<PendingOrders<T>>::remove(nonce)` deletes the order despite the failed command, confirmed by the absence of any `success`-branching logic in [4](#0-3) .
