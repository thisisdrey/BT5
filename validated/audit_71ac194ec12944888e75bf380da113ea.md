### Title
Truncating Integer Arithmetic in `vest()` Permanently Freezes Shareholder Vested Tokens When `total_grant × vesting_fraction < 1` — (`File: aptos-move/framework/aptos-framework/sources/vesting.move`)

---

### Summary

`vest()` in `vesting.move` computes the per-period vested amount using `fixed_point32::multiply_u64(total_grant, vesting_fraction)`, which **truncates** (floors) the result. When `total_grant × vesting_fraction.value < 2^32`, the result is `0`. Critically, `last_vested_period` still advances even when `vested_amount = 0`, consuming vesting schedule entries without distributing any tokens. Because `total_grant` is fixed (it is `grant_pool.total_coins()`, which never changes), every subsequent `vest()` call also produces `0`, and `remaining_grant` never reaches zero. Shareholders permanently lose their entitled vested tokens; the only recovery path is admin termination, which routes funds to the `withdrawal_address` rather than to shareholders.

---

### Finding Description

In `vest()`:

```move
let total_grant = vesting_contract.grant_pool.total_coins();
let vested_amount = fixed_point32::multiply_u64(total_grant, vesting_fraction);
vested_amount = min(vested_amount, vesting_contract.remaining_grant);
vesting_contract.remaining_grant -= vested_amount;
vesting_schedule.last_vested_period = next_period_to_vest;   // always advances
unlock_stake(vesting_contract, vested_amount);
``` [1](#0-0) 

`fixed_point32::multiply_u64` is documented to **truncate** the fractional part:

```move
let unscaled_product = (val as u128) * (multiplier.value as u128);
let product = unscaled_product >> 32;   // floor, not round
``` [2](#0-1) 

The condition for `vested_amount = 0` is:

```
total_grant × vesting_fraction.value < 2^32
```

`total_grant` is `grant_pool.total_coins()`, which is the **original** grant amount and never changes — it is not reduced as vesting progresses. Therefore `vested_amount` is a **constant** per period. If that constant is `0`, every `vest()` call:

1. Computes `vested_amount = 0`
2. Leaves `remaining_grant` unchanged
3. **Advances `last_vested_period`** unconditionally [3](#0-2) 

The last schedule fraction repeats indefinitely:

```move
let vesting_fraction = if (schedule_index < schedule.length()) {
    schedule[schedule_index]
} else {
    schedule[schedule.length() - 1]   // repeats forever
};
``` [4](#0-3) 

So the contract loops forever: `vest()` succeeds (no abort), `last_vested_period` grows, but `remaining_grant` is permanently non-zero. Shareholders can never receive their vested tokens through the normal `vest()` → `distribute()` path.

The `grant_pool` struct is a `pool_u64::Pool` used only for proportional share tracking; it is never modified by `unlock_stake`, `vest`, or `distribute`. [5](#0-4) 

---

### Impact Explanation

Shareholders permanently lose their entitled vested tokens. The only recovery is admin calling `terminate_vesting_contract`, which sets `remaining_grant = 0` and routes all active stake to `withdrawal_address` — not to shareholders. [6](#0-5) 

This is a **permanent freezing / unauthorized reassignment of user-controlled on-chain assets**: tokens that shareholders are contractually entitled to are redirected to the admin's withdrawal address.

---

### Likelihood Explanation

The condition `total_grant × vesting_fraction.value < 2^32` is reachable with valid, on-chain inputs:

- **Minimum representable fraction** (`vesting_fraction.value = 1`, i.e., `1/2^32`): any grant under `2^32` octas (~43 APT) produces `vested_amount = 0`.
- **Fraction `1/48`** (`vesting_fraction.value ≈ 89,478,485`): any grant under 48 octas triggers the bug.
- **Fraction `1/1,000,000`** (`vesting_fraction.value ≈ 4,294`): any grant under ~1,000,000 octas (0.01 APT) triggers the bug.

The minimum grant enforced by the contract is 1 octa:

```move
assert!(grant_amount > 0, error::invalid_argument(EZERO_GRANT));
``` [7](#0-6) 

`vest()` is a public entry function callable by anyone, so no privileged access is needed to trigger the stuck state. [8](#0-7) 

---

### Recommendation

**Short term:** In `vest()`, after computing `vested_amount`, check whether it is `0` while `remaining_grant > 0`. If so, either:
- Distribute `remaining_grant` directly (treat it as the final period), or
- Abort with a descriptive error so callers know the contract parameters are incompatible.

Do **not** advance `last_vested_period` when `vested_amount == 0` and `remaining_grant > 0`.

**Long term:** Add a validation in `create_vesting_schedule` (or `create_vesting_contract`) that asserts `floor(total_grant × vesting_fraction) >= 1` for every fraction in the schedule, so the stuck state is impossible to create. Alternatively, use ceiling division for the final period to guarantee `remaining_grant` reaches zero.

---

### Proof of Concept

**Parameters:**
- `total_grant = 10` octas (valid: > 0)
- `vesting_fraction = 1/2^32` → `vesting_fraction.value = 1`

**Calculation:**
```
vested_amount = (10 × 1) >> 32 = 10 / 4,294,967,296 = 0  (truncated)
```

**Sequence:**
1. Admin creates vesting contract with `grant_amount = 10`, schedule `[1/2^32]`.
2. Time passes; shareholder calls `vest()` — `vested_amount = 0`, `remaining_grant = 10`, `last_vested_period = 1`.
3. Shareholder calls `vest()` again — same result, `last_vested_period = 2`.
4. This repeats indefinitely. `remaining_grant` never reaches 0.
5. `distribute()` always distributes 0 coins to shareholders.
6. Admin calls `terminate_vesting_contract` → 10 octas go to `withdrawal_address`, not to shareholders.

**Larger realistic example:**
- `total_grant = 1,000,000` octas (0.01 APT), `vesting_fraction = 1/1,000,001`
- `vesting_fraction.value = floor(2^32 / 1,000,001) = 4,294`
- `vested_amount = floor(1,000,000 × 4,294 / 2^32) = floor(4,294,000,000 / 4,294,967,296) = 0`
- All 0.01 APT is permanently frozen from shareholders. [1](#0-0) [2](#0-1)

    public fun multiply_u64(val: u64, multiplier: FixedPoint32): u64 {
        // The product of two 64 bit values has 128 bits, so perform the
        // multiplication with u128 types and keep the full 128 bit product
        // to avoid losing accuracy.
        let unscaled_product = (val as u128) * (multiplier.value as u128);
        // The unscaled product has 32 fractional bits (from the multiplier)
        // so rescale it by shifting away the low bits.
        let product = unscaled_product >> 32;
        // Check whether the value is too large.
        assert!(product <= MAX_U64, EMULTIPLICATION);
        product as u64
    }
