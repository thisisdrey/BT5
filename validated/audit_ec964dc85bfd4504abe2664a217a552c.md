### Title
Refund redirection to a non-existent account permanently burns balance and gas refunds - ([File: runtime/runtime/src/lib.rs])

### Summary
NEAR exposes a host function that lets an unprivileged contract redirect where its own balance/gas refunds are sent (`refund_to`). The protocol only validates that this account id is *syntactically* well-formed — it never checks that the account exists or can receive an implicit-account-creation transfer. Because refund receipts are treated specially (they are not implicit-account-creation eligible and any refund that fails to execute is burned by design), a caller who sets `refund_to` to a syntactically valid but non-existent/non-implicit account id causes its own refund to be silently destroyed instead of returned, which is the direct analog of the reported "fees sent to an unusable recipient are burned" bug class.

### Finding Description
A contract can attach a redirect target for its refunds using the `set_refund_to` / `promise_set_refund_to` host function, which is stored as `ActionReceiptMetadata::refund_to` [1](#0-0)  and surfaced through the `dependencies::set_refund_to` external trait [2](#0-1) .

When a receipt executes, the actual recipient of a balance refund is computed as `refund_to().unwrap_or(predecessor_id())` [3](#0-2) , and refund receipts themselves are built with `predecessor_id = "system"` [4](#0-3) .

The only validation performed on `refund_to` at receipt-creation time is a format check via `AccountId::validate`; there is no check that the account exists or is reachable by implicit-account creation: [5](#0-4) 

When the refund receipt is later executed, `apply_action` computes `is_refund = predecessor_id().is_system()` and explicitly disables implicit-account-creation eligibility for any refund (`implicit_account_creation_eligible = is_the_only_action && !is_refund`): [6](#0-5) 

If the target account named by `refund_to` does not exist (e.g. a random/never-created named account, or one that is deleted between redirection and refund delivery), `check_account_existence` will not allow the transfer to create the account (this path is reserved for implicit accounts only), and `action_implicit_account_creation_transfer` itself asserts `AccountType::NamedAccount => panic!("must be implicit")` for any code path that erroneously reaches it with a non-implicit id [7](#0-6) .

The protocol's documented behavior for this exact situation is explicit: refund receipts are free/gasless, and **if execution of a refund fails, the refund amount is burnt**: [8](#0-7) 

This mirrors the reported bug class precisely: a normal, unprivileged account (the "creator"/predecessor here) is allowed to specify a fund destination that the system will happily accept as syntactically valid, but that destination causes the transferred value to be irrecoverably destroyed rather than delivered, even though the protocol still computes and attempts to send the funds.

### Impact Explanation
Refunds represent real user value — unspent prepaid gas (converted back to NEAR) and unspent attached deposits. Redirecting them to a non-existent account causes that value to be permanently burned instead of returned to the rightful signer/predecessor, i.e., permanent loss of funds for the party who should have received the refund. Because `set_refund_to` is settable per-receipt by whichever account creates that receipt (e.g. a relayer in a meta-transaction, or any contract issuing promises on behalf of a callee), a relayer or intermediary contract could cause a victim's legitimately-earned refund to be destroyed, or a misbehaving/buggy contract could unintentionally destroy funds that would otherwise have been recovered.

### Likelihood Explanation
`set_refund_to` is a normal, unprivileged host function reachable from any deployed contract in the course of ordinary promise/receipt construction — no special permissions, validator status, or protocol-level access is required, matching the "ordinary client/contract" reachability bar. The failure condition (target does not exist, or ceases to exist before the refund is delivered — accounts can be deleted via `DeleteAccountAction` at any time) is easy to trigger, whether intentionally or as an implementation mistake in a relayer/aggregator contract.

### Recommendation
- Validate at receipt-creation time (in `validate_receipt`/`validate_action_receipt`) not just the format of `refund_to`, but forbid redirecting refunds to accounts that are provably unusable as implicit-creation targets when they don't already exist, or
- Change the failure-refund semantics so a refund whose target account does not exist and cannot be implicitly created falls back to the original predecessor/signer instead of being burned, analogous to disallowing/rerouting `address(0)`-style unusable recipients in the reported report.

### Proof of Concept
1. Contract A creates a promise/receipt to Contract B with an attached deposit and/or generous prepaid gas.
2. Before sending, Contract A calls `promise_set_refund_to(promise_index, "never-created-account.testnet")` — an account id that is syntactically valid (passes `AccountId::validate`) but has never been created and is not in implicit-account format.
3. The receiver receipt is validated successfully (`InvalidRefundTo` is only raised for malformed ids), and dispatched.
4. Suppose B's call fails (e.g., insufficient gas/method missing) or B leaves unused gas — the runtime generates a deposit-refund and/or gas-refund receipt targeting `receipt.balance_refund_receiver()` = "never-created-account.testnet" with `predecessor_id = "system"`.
5. When this refund receipt executes, `is_refund=true` forces `implicit_account_creation_eligible=false`; the target account cannot be created via the implicit path, the refund receipt's Transfer action fails, and per `docs/RuntimeSpec/Refunds.md:12` the refund amount is burnt rather than returned to Contract A.

(Note: exact confirmation of whether `check_account_existence` returns an explicit error before reaching `action_implicit_account_creation_transfer`, versus reaching the `panic!("must be implicit")` branch, could not be fully traced within the available tool budget — the `check_account_existence` function body itself was not retrieved before the session ended. Either outcome (a clean action failure that is then burned per the documented refund-failure rule, or a runtime panic) supports the "funds destroyed / correctness violated" classification, but I was not able to view the function body to state with certainty which of the two occurs.)

```rust
/// Can only be used for implicit accounts.
pub(crate) fn action_implicit_account_creation_transfer(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    fee_config: &RuntimeFeesConfig,
    account: &mut Option<Account>,
    actor_id: &mut AccountId,
    account_id: &AccountId,
    deposit: Balance,
    block_height: BlockHeight,
    epoch_info_provider: &dyn EpochInfoProvider,
) {
    *actor_id = account_id.clone();
    match account_id.get_account_type() {
        AccountType::NearImplicitAccount => {
            let mut access_key = AccessKey::full_access();
            access_key.nonce = initial_nonce_value(block_height);

            // unwrap: here it's safe because the `account_id` has already been determined to be implicit by `get_account_type`
            let public_key = PublicKey::from_near_implicit_account(account_id).unwrap();

            *account = Some(Account::new(
                deposit,
                Balance::ZERO,
                AccountContract::None,
                fee_config.storage_usage_config.num_bytes_account
                    + public_key.trie_id_len() as u64
                    + borsh::object_length(&access_key).unwrap() as u64
                    + fee_config.storage_usage_config.num_extra_bytes_record,
            ));

            set_access_key(state_update, account_id.clone(), public_key, &access_key);
        }
        // Invariant: The `account_id` is implicit.
        // It holds because in the only calling site, we've checked the permissions before.
        AccountType::EthImplicitAccount => {
            let chain_id = epoch_info_provider.chain_id();

            // Use a deployed global contract for ETH implicit accounts.
            let global_contract_hash = eth_wallet_global_contract_hash(&chain_id);
            let storage_usage = fee_config.storage_usage_config.num_bytes_account
                + global_contract_hash.as_bytes().len() as u64;

            *account = Some(Account::new(
                deposit,
                Balance::ZERO,
                AccountContract::Global(global_contract_hash),
                storage_usage,
            ));
        }
        AccountType::NearDeterministicAccount => {
            *account = Some(create_deterministic_account(
                deposit,
                &apply_state.config.fees.storage_usage_config,
            ));
        }
        // This panic is unreachable as this is an implicit account creation transfer.
        // `check_account_existence` would fail because `account_is_implicit` would return false for a Named account.
        AccountType::NamedAccount => panic!("must be implicit"),
    }
}
```

**File:** docs/RuntimeSpec/Refunds.md (L9-13)
```markdown

Refund receipts are identified by having `predecessor_id == "system"`. They are also special because they don't cost any gas to generate or execute. As a result, they also do not contribute to the block gas limit.

If the execution of a refund fails, the refund amount is burnt.
The refund receipt is an `ActionReceipt` that consists of a single action `Transfer` with the `deposit` amount of the refund.
```
