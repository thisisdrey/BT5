## Analysis

I found a concrete local analog in `substrate/frame/asset-rewards` (the FRAME Staking Rewards / `RewardsPool` pallet). The bug class is the same as the external report: a routine "update" helper unconditionally stamps a block-number field with the *current* block instead of the value that should actually cap the reward window, and that stale/inconsistent stamp later breaks an invariant check that every subsequent operation depends on — permanently locking user funds instead of merely mis-triggering a TP/SL.

### Title
Unbounded `last_update_block` stamping after pool expiry causes permanent arithmetic-underflow lock of staked funds and rewards - (File: `substrate/frame/asset-rewards/src/lib.rs`)

### Summary
`Pallet::update_pool_rewards` always sets `PoolInfo::last_update_block` to the *actual* current block number, with no cap at `expiry_block` [1](#0-0) . But `reward_per_token` computes elapsed blocks as `last_block_reward_applicable(expiry_block) - last_update_block`, where `last_block_reward_applicable` is capped at `expiry_block` [2](#0-1)  and the subtraction uses `ensure_sub` [3](#0-2) . Once any post-expiry interaction sets `last_update_block` past `expiry_block` while `total_tokens_staked` is still non-zero, every future call computes `expiry_block.ensure_sub(last_update_block)` on a negative delta, which errors out and reverts the whole extrinsic — permanently, since there is no path to reset `last_update_block` without going through the same broken function.

### Finding Description
`update_pool_rewards` is the single point that advances `last_update_block`, and it is invoked unconditionally before every pool-mutating action (`stake`, `unstake`, `harvest_rewards`, `set_pool_reward_rate_per_block`, `set_pool_expiry_block`) via `update_pool_and_staker_rewards` or directly [4](#0-3) :

```rust
pub fn update_pool_rewards(...) -> Result<PoolInfoFor<T>, DispatchError> {
    let mut new_pool_info = pool_info.clone();
    new_pool_info.last_update_block = T::BlockNumberProvider::current_block_number();
    new_pool_info.reward_per_token_stored = reward_per_token;
    Ok(new_pool_info)
}
```

This mirrors the audited pattern exactly: a generic "update" helper that stamps a tracked block number to "now" as a side effect of an operation, without regard for whether "now" is semantically valid for that field (in the external report, TP/SL block; here, a reward-accrual cutoff that must never exceed `expiry_block`).

`reward_per_token` then relies on `last_update_block` always being `<= last_block_reward_applicable(expiry_block)`:

```rust
let rewardable_blocks_elapsed: u32 =
    match Self::last_block_reward_applicable(pool_info.expiry_block)
        .ensure_sub(pool_info.last_update_block)?
        ...
``` [3](#0-2) 

`last_block_reward_applicable` caps at `expiry_block` once the pool has expired [2](#0-1) , but `update_pool_rewards` does not apply the same cap when writing `last_update_block`. So the very first post-expiry interaction (which is explicitly permitted — `unstake`/`harvest_rewards` allow "any account" once `now > pool_info.expiry_block`, see the `ensure!` guards [5](#0-4)  and [6](#0-5) ) leaves `last_update_block > expiry_block` while `total_tokens_staked` may still be non-zero (not everyone has unstaked). Any subsequent call to `reward_per_token` for that pool then computes `expiry_block.ensure_sub(last_update_block)`, which underflows and returns `Err`, aborting the extrinsic.

### Impact Explanation
Once `last_update_block` overshoots `expiry_block` for a pool that still has staked tokens:
- Further `unstake` calls fail (they call `update_pool_and_staker_rewards` → `reward_per_token` first) [5](#0-4) , so remaining stakers can never withdraw their frozen tokens.
- `harvest_rewards` likewise fails [6](#0-5) , so unclaimed rewards become unclaimable.
- `set_pool_reward_rate_per_block` and `set_pool_expiry_block` also call `reward_per_token` first and would fail too [7](#0-6) [8](#0-7) , so the admin cannot recover the pool by extending expiry either.
- `cleanup_pool` requires `PoolStakers` to be empty [9](#0-8) , which can never be reached since stakers can't unstake.

This is a permanent, unprivileged, no-governance-needed lock of staked assets (frozen via `AssetsFreezer`) and reward assets for that pool — matching the "permanent user-fund lock" acceptance criterion.

### Likelihood Explanation
No malicious actor, privileged role, or governance action is required. It only takes normal usage: a pool naturally passes its `expiry_block` while tokens are still staked (the common case, since `unstake`/`harvest_rewards` are explicitly designed to be callable by anyone after expiry, implying stakers are not expected to exit before expiry), and one ordinary post-expiry `unstake`/`harvest_rewards`/`stake` call by any user is enough to poison `last_update_block` for the remaining stakers.

### Recommendation
In `update_pool_rewards`, cap the new `last_update_block` at `expiry_block` (i.e. store `last_block_reward_applicable(pool_info.expiry_block)` instead of raw `T::BlockNumberProvider::current_block_number()`), consistent with how `reward_per_token` treats the reward window. This ensures `last_update_block` never exceeds the value used in future `ensure_sub` calls, eliminating the underflow.

### Proof of Concept
1. Create a pool with `expiry_block = E`.
2. Stake `amount > 0` at block `< E` (pool stays active, `total_tokens_staked > 0`).
3. Advance chain to block `now1 > E`. Call `unstake` (partial) or `harvest_rewards` as any account — succeeds, but `update_pool_rewards` sets `last_update_block = now1` (not capped at `E`), while `total_tokens_staked` remains `> 0`.
4. Advance chain further to `now2 > now1`. Call `unstake`/`harvest_rewards`/`stake`/`set_pool_reward_rate_per_block`/`set_pool_expiry_block` on the same pool.
5. `reward_per_token` computes `last_block_reward_applicable(E) = E` and then `E.ensure_sub(last_update_block = now1)`, where `now1 > E`, causing an arithmetic underflow error and reverting the call.
6. All further operations on the pool fail identically forever; remaining staked tokens and unharvested rewards are permanently locked, and `cleanup_pool` can never succeed because `PoolStakers` for that pool can never be emptied.
