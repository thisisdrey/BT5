### Title
TOCTOU race between `ConnectionRateLimiter::is_allowed` and `register_connection` allows per-IP connection rate-limit bypass - ([File: streamer/src/nonblocking/connection_rate_limiter.rs])

### Finding Description
`ConnectionRateLimiter::is_allowed` is a read-only, non-mutating check that inspects `current_tokens(ip)` without reserving or consuming any token: `Some(r) => r > 0` [1](#0-0) . Only `register_connection` actually mutates state via `self.limiter.consume_tokens(*ip, 1)` [2](#0-1) . Because these are two distinct, non-atomic calls invoked at different phases of the connection lifecycle in `streamer/src/nonblocking/quic.rs` (pre-handshake `is_allowed` check, post-handshake `register_connection`), an attacker opening many concurrent QUIC connections from a single IP can drive N parallel handshakes that all observe `is_allowed() == true` (since none of them have yet decremented the bucket) before any of them calls `register_connection`. Each subsequent `register_connection` call is individually serialized by the dashmap shard lock inside `KeyedRateLimiter::consume_tokens`, but that only guarantees consistency of the token count after the fact — it does not retroactively reject the already-completed handshakes that were let through by the non-authoritative `is_allowed` pre-check. This is a classic check-then-act (TOCTOU) race intrinsic to splitting the "may I connect" check from the "consume my quota" mutation into two separate function calls with observable state between them, as documented directly by the module's own comment: "we should only modify server state once source IP is verified" [3](#0-2) , which is precisely why the check happens before the connection completes and the mutation after — creating the window being exploited.

### Impact Explanation
An attacker can burst well beyond the configured `limit_per_minute`/`max_burst` for `ConnectionRateLimiter` by completing many QUIC handshakes concurrently within the race window, each of which independently observed a non-decremented token count. This lets a single IP exceed the intended per-source connection admission rate, contributing extra load toward exhausting `ClientConnectionTracker` slots / `max_concurrent_connections()`, which is a QoS/rate-limit evasion issue under the Agave bounty's DoS/resource-exhaustion category.

### Likelihood Explanation
Exploitability requires only an unstaked/unprivileged attacker capable of opening many concurrent QUIC connections from one IP address — no validator, staked, or gossip control needed, matching the allowed threat model. The race window is bounded by TLS/QUIC handshake completion latency, so the achievable burst multiplier is limited by how many handshakes the attacker can drive to near-simultaneous completion (network/CPU-bound), not unbounded — this constrains the severity somewhat, but the bypass is real and repeatable per burst window (attacker can repeat the attack every rate-limiter window).

### Recommendation
Make the admission check and quota consumption atomic: reserve a token in `register_connection`-equivalent logic *before* or during handshake acceptance (e.g., a single `try_consume` call up front), and release/refund it only if the handshake later fails verification, rather than using a separate non-mutating `is_allowed` peek followed by a later `register_connection` mutation. Alternatively, move the authoritative rate check to occur atomically at the same point the decision to proceed with the handshake is made, eliminating the window in which multiple concurrent callers can all observe a stale non-zero token count.

### Proof of Concept
```rust
// streamer/src/nonblocking/connection_rate_limiter.rs (test augmentation)
#[tokio::test]
async fn test_race_toctou_bypass() {
    use std::sync::Arc;
    let limiter = Arc::new(ConnectionRateLimiter::new(1, 1, 4)); // burst=1
    let ip = IpAddr::V4(Ipv4Addr::new(10, 0, 0, 1));

    // Simulate N concurrent handshakes all doing is_allowed() pre-check
    // before any of them calls register_connection().
    let n = 20;
    let mut checks = Vec::new();
    for _ in 0..n {
        checks.push(limiter.is_allowed(&ip)); // all read stale token count
    }
    // At this point, more than `max_burst` checks returned true.
    let allowed_precheck = checks.iter().filter(|&&b| b).count();

    // Now all "handshakes" complete and call register_connection concurrently.
    let mut handles = Vec::new();
    for _ in 0..n {
        let l = limiter.clone();
        handles.push(tokio::spawn(async move { l.register_connection(&ip) }));
    }
    let mut accepted = 0;
    for h in handles {
        if h.await.unwrap() {
            accepted += 1;
        }
    }

    // Expected (correct) behavior: accepted <= max_burst (1).
    // Bug: allowed_precheck > max_burst demonstrates the TOCTOU window,
    // showing more callers observed is_allowed()==true than the bucket capacity,
    // even though register_connection ultimately serializes actual admission.
    assert!(allowed_precheck > 1, "TOCTOU window observed: {allowed_precheck} callers saw is_allowed()==true with burst=1");
}
```
This demonstrates that the non-atomic `is_allowed`/`register_connection` split allows more callers to pass the pre-check than the configured burst capacity, confirming the race window exists at the `ConnectionRateLimiter` API level that `setup_connection` relies on in `streamer/src/nonblocking/quic.rs`.
