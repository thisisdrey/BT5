### Title
Front-runnable contract-creation address check allows permanent Denial of Service against `CreateSmartContract` deployments - (File: `actuator/src/main/java/org/tron/core/actuator/VMActuator.java`)

### Summary
The Solana report describes a class of bug where a deterministic account address is created with an `init`-style "must not already exist" constraint, allowing an attacker to pre-create that account and permanently block the legitimate owner from ever using it — a denial-of-service via address squatting. The java-tron analog is the top-level smart-contract deployment path in `VMActuator.create()`, which derives a deterministic contract address from the transaction and unconditionally rejects deployment if *any* account already occupies that address, with no distinction between "empty account funded by an attacker" and "real conflicting contract."

### Finding Description
When a `CreateSmartContract` transaction is processed, the target contract address is computed deterministically as `sha3omit12(txRawDataHash || ownerAddress)`: [1](#0-0) 

`VMActuator.create()` then performs a naive existence check before allowing the deployment: [2](#0-1) 

This check simply asks "does *any* account (`rootRepository.getAccount(contractAddress)`) already exist at this address?" — it does not distinguish between an address that already holds a real conflicting smart contract and an address that merely received a plain TRX transfer or `AccountCreateContract`. If any account object exists there at all, the deployment is rejected with `ContractValidateException`.

Contrast this with the internal `CREATE`/`CREATE2` opcode path in `Program.createContractImpl`, which was specifically hardened against this exact griefing scenario: when `allowTvmConstantinople` is active, `contractAlreadyExists` is only true if the existing account is *actually a contract* (`isContractExist`), not merely funded: [3](#0-2) 

This shows the team already recognized and fixed this exact class of bug for the in-VM `CREATE2` opcode (allowing counterfactual/pre-funded deployment addresses to still be deployed to), but the top-level, transaction-level `CreateSmartContract` deployment path in `VMActuator.create()` was never given the same treatment — it still uses the blunt "account exists → reject" check.

Because the deployment address is fully determined by data visible in the signed-but-unconfirmed transaction (`txRawDataHash` and `ownerAddress`), any observer of the pending transaction (e.g., in the P2P transaction pool) can immediately compute the exact future contract address and race a simple, cheap `TransferContract` or `AccountCreateContract` to that address before the victim's `CreateSmartContract` transaction is packed into a block. Once any account record exists at that address, the victim's contract-creation transaction is guaranteed to fail validation, permanently, for that specific signed transaction (since the address is bound to that unique transaction hash).

### Impact Explanation
This is a griefing/Denial-of-Service primitive reachable by any unprivileged party broadcasting ordinary transactions: it costs the attacker only a minimal TRX transfer or account-creation fee, while it guarantees the legitimate contract deployer's transaction fails, wasting their bandwidth/energy and blocking that specific deployment attempt entirely. This is especially damaging for any application, exchange, or factory pattern that relies on predictable/deterministic deployment addresses (a common pattern for wallets, escrow, and counterfactual contract instantiation) — such flows can be systematically and repeatedly frustrated by a bot watching the mempool for `CreateSmartContract` transactions and squatting the resulting address. This matches the "no impact" exclusion boundary at the low end but rises to the level of node-serviceable-attack (a concrete, repeatable disruption of a core network capability — deploying contracts to intended/predictable addresses) rather than being purely resource-only, since it produces deterministic, permanent, unrecoverable failure of the specific targeted transaction and can be weaponized against any observable pending deployment.

### Likelihood Explanation
Likelihood is high for any environment where pending transactions are observable prior to confirmation (standard behavior of any blockchain's transaction relay/mempool) and where the target's deployment address can be computed in advance from the raw transaction fields, both of which hold unconditionally in java-tron's design. The attack requires no special privileges, and the fix for the equivalent CREATE2 case already exists elsewhere in the codebase, underscoring that the vulnerable top-level path was simply missed rather than being an intentional restriction.

### Recommendation
Apply the same fix pattern used in `Program.createContractImpl`'s constantinople-aware `isContractExist` check to `VMActuator.create()`: only reject a `CreateSmartContract` deployment if the existing account at the target address is already a real deployed contract (i.e., check `ContractStore`/`AccountType.Contract` and code presence), not merely because an `AccountCapsule` record exists. If the pre-existing account is a plain/funded account, allow the deployment to proceed and convert/attach the contract to that address (mirroring the internal CREATE2 semantics), preserving balance the same way the constantinople CREATE2 path does.

### Proof of Concept
1. Attacker monitors the P2P transaction pool for pending `CreateSmartContract` transactions.
2. Upon observing a victim's unconfirmed `CreateSmartContract` transaction, the attacker computes `contractAddress = sha3omit12(victimTxRawDataHash || victimOwnerAddress)` exactly as `WalletUtil.generateContractAddress` does [1](#0-0) .
3. Attacker immediately broadcasts a cheap `TransferContract` (or `AccountCreateContract`) sending TRX to `contractAddress`, prioritizing inclusion ahead of the victim's transaction.
4. When the victim's `CreateSmartContract` transaction is later processed, `VMActuator.create()`'s existence check finds the attacker-created `AccountCapsule` and throws `ContractValidateException("Trying to create a contract with existing contract address: ...")` [2](#0-1) , permanently failing the victim's deployment for that transaction while the victim still pays bandwidth/energy fees.
