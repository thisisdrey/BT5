### Title
`close_account` omits `ACCOUNT_IN_ORDER_EXECUTION` guard, allowing account closure mid order-execution - (File: programs/marginfi/src/instructions/marginfi_account/close.rs)

### Summary
`close_account` checks `ACCOUNT_FROZEN`, `liquidation_record`, `active_orders`, and calls `can_be_closed()`, but neither `close_account` nor `can_be_closed()` checks the `ACCOUNT_IN_ORDER_EXECUTION` flag, unlike the parallel permissionless path `admin_close_account`, which explicitly checks it.

### Finding Description
`close_account` at [1](#0-0)  performs these checks: frozen flag, `liquidation_record == default`, `active_orders == 0`, and `can_be_closed()`. `can_be_closed()` is defined as [2](#0-1) , which checks `ACCOUNT_DISABLED`, empty balances, `ACCOUNT_IN_FLASHLOAN`, `ACCOUNT_IN_RECEIVERSHIP`, and `ACCOUNT_FROZEN` — but never `ACCOUNT_IN_ORDER_EXECUTION`.

By contrast, `admin_close_account` (the intended permissionless-close analog) explicitly re-adds the missing check: [3](#0-2) . This strongly implies the omission in `close_account` is a genuine gap rather than an intentional design choice — the flag is clearly considered relevant to closing eligibility elsewhere in the codebase.

`ACCOUNT_IN_ORDER_EXECUTION` is set by `start_execute_order` [4](#0-3)  and is only meant to be cleared by `end_execute_order` in the same atomic transaction (`validate_instructions` enforces `start`...`end` bracketing in the same tx via instruction-sysvar introspection, line 335-340). Other instructions that mutate balances (deposit, borrow, repay, withdraw) explicitly guard against `ACCOUNT_IN_ORDER_EXECUTION` via the `PlaceOrder`-style constraint block shown in `order.rs:519-533`, and `EndLiquidation`/`EndDeleverage` account constraints also explicitly check `!acc.get_flag(ACCOUNT_IN_ORDER_EXECUTION)`. `close_account`, however, has no such constraint or check.

Exploit flow: because `close_account` is a normal user-authority instruction requiring `has_one = authority`, and `start_execute_order`/`end_execute_order` are meant to be Keeper-driven and bracketed atomically within one transaction (enforced via `validate_instructions`), the theoretical attack is: place a transaction containing `StartExecuteOrder` (sets the flag) followed by an account-draining action that brings all balances to zero (satisfying `only_has_empty_balances`), then insert `close_account` before `EndExecuteOrder` executes/clears the flag and closes the order — all within the same atomic transaction, since Solana transactions execute instructions sequentially and `close_account`'s account-closing side effect (returning lamports, zeroing data) takes place immediately upon that instruction's execution, not at the end of the transaction.

However, this requires: (1) the attacker to control or coordinate with the entity constructing the `StartExecuteOrder`/`EndExecuteOrder` transaction (normally a Keeper), and (2) `validate_instructions` enforces that `EndExecuteOrder` must be the last instruction of the transaction and matches discriminators for start/end — if `close_account` is inserted between them, the account gets closed via Anchor's `close = fee_payer` constraint, and the subsequent `EndExecuteOrder` instruction in the same transaction would then fail because the account is closed (it would no longer deserialize as a valid `MarginfiAccount`), causing the whole transaction to abort atomically. This self-defeats the naive "insert close in the middle" approach, because Solana transactions are all-or-nothing — a failure in `EndExecuteOrder` after account closure reverts the entire transaction, undoing the `close_account` effect as well.

The only way this bug becomes exploitable is if there's a legitimate reachable path where `ACCOUNT_IN_ORDER_EXECUTION` remains set on-chain *after* a completed transaction (i.e., a bug causes `end_execute_order` to not always clear the flag, or a transaction can be constructed and confirmed without `EndExecuteOrder` ever executing successfully but with the flag having been persisted). Given Solana's atomicity, if the transaction fails at any single instruction, all state changes are rolled back — the `set_flag` call in `start_execute_order` would also be reverted. I could not find, within the code reachable, any code path where `ACCOUNT_IN_ORDER_EXECUTION` is set and persisted across transaction boundaries without `end_execute_order` (or a failure causing full-transaction rollback).

### Impact Explanation
If a persisted state existed where `ACCOUNT_IN_ORDER_EXECUTION` is set and balances are empty, `close_account` would succeed in closing the account without clearing the flag or the pending order execution record, effectively closing the container while an order execution was still notionally "in-flight," corresponding to the described impact ("permanent lock or hidden exposure"). However, I was unable to establish a concrete reachable path where this flag persists across transactions without also being cleared by a full-transaction rollback, given Solana's atomicity guarantees and the fact that `validate_instructions` requires `EndExecuteOrder` to be the last instruction in the same transaction. This significantly reduces confidence that this is independently and repeatably exploitable by an unprivileged attacker in a single, isolated transaction, as required by the bounty program's "reproducible PoC" bar.

### Likelihood Explanation
Low/uncertain — while the missing check is a genuine gap (confirmed present in `admin_close_account` but absent in `close_account`), no PoC could be constructed within the explored code that persists `ACCOUNT_IN_ORDER_EXECUTION` past a single atomic transaction boundary without also undoing the `close_account` side effect through transaction rollback. This may indicate the finding is only a defense-in-depth gap rather than an exploitable vulnerability, but it cannot be fully ruled out without directly testing on-chain behavior of Anchor's `close = fee_payer` constraint interacting with a subsequent failing instruction in the same transaction (i.e., whether closure is truly rolled back on later instruction failure).

### Recommendation
Add an explicit `!marginfi_account.get_flag(ACCOUNT_IN_ORDER_EXECUTION)` check to `close_account` (and to `can_be_closed()`, to keep the invariant centralized and consistent with `admin_close_account`), matching the belt-and-suspenders check already present in the admin/permissionless close path and in `EndLiquidation`/`EndDeleverage` account constraints.

### Proof of Concept
Not confirmed exploitable with existing tools/knowledge. Suggested test to validate defensively (even without confirmed exploitability):
1. Add a Rust integration test in `programs/marginfi/tests/user_actions/order.rs` that calls `try_place_order`, `start_execute_order` (do not call `end_execute_order`), and within the *same transaction*, insert `close_account` before `EndExecuteOrder`.
2. Assert whether the transaction reverts entirely (expected under Solana atomicity) or whether `close_account` succeeds while `ACCOUNT_IN_ORDER_EXECUTION` remains set — if the latter is observed, this confirms exploitability and the fix above should be applied immediately.
3. Additionally, add a unit test directly against `can_be_closed()`/`close_account`'s logic that manually sets `ACCOUNT_IN_ORDER_EXECUTION = true` on an account with empty balances and asserts `close_account` (or `can_be_closed()`) returns an error, to enforce the invariant defensively regardless of current reachability.
