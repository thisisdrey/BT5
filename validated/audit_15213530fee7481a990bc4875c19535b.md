### Title
Falsely-acknowledged StackerDB chunk inventory before durable commit ("served vs committed" mismatch) - (File: stackslib/src/net/stackerdb/mod.rs)

### Summary
`PeerNetwork::handle_unsolicited_StackerDBPushChunk` builds and immediately transmits a `StackerDBChunkInv` acknowledgment claiming a pushed chunk's slot version has been accepted, before that chunk has actually been durably written to the local `StackerDBs` store. The acknowledgment is derived from an in-memory patch of the inventory vector, not from a post-commit read of the database, so the value the network is told ("we have version V") can diverge from what actually ends up persisted.

### Finding Description
In `make_StackerDBChunksInv_or_Nack` / `handle_unsolicited_StackerDBPushChunk`, the flow is:
1. Read current on-disk slot versions via `self.stackerdbs.get_slot_versions(...)` [1](#0-0) .
2. Validate the pushed chunk's signature/version/size against that snapshot with `validate_received_chunk` [2](#0-1) .
3. On success, *patch the in-memory reply* (`data.slot_versions`) to reflect the new version — "patch inventory -- we'll accept this chunk" — without touching the database [3](#0-2) .
4. If `send_reply` is set, immediately sign and transmit this patched inventory back to the sending peer via `send_p2p_message`, and separately return `(false, true)` so the chunk is *also* forwarded to the relayer for actual storage [4](#0-3) .

The actual durable write happens later and independently, in the relay path: `Relayer::process_pushed_stacker_db_chunks` → `process_stacker_db_chunks`, which calls `StackerDBTx::try_replace_chunk` inside a fresh SQL transaction [5](#0-4) . That call can still fail after the ack was already sent — e.g. with `StaleChunk` if a different, higher-versioned chunk for the same slot was committed first (a legitimate race between the read used for the ack in step 1 and the actual commit-time comparison in `try_replace_chunk`, per `stackslib/src/net/stackerdb/db.rs` lines 411-429), or with any other `net_error`, in which case the code simply logs a warning and `continue`s without storing anything [6](#0-5) .

This breaks the "served vs committed" equality: the `StackerDBChunkInv` message a remote peer receives is not proof that the chunk is actually present in the node's replica. This is architecturally the same class of defect as read-only reentrancy in the reference report — a caller-visible state summary is computed and emitted using pre-commit assumptions, and can be inconsistent with the real post-commit state if a conflicting write intervenes.

### Impact Explanation
A remote, unauthenticated peer can push chunks that other peers' inventories will optimistically believe are stored, even though the actual store may reject them (stale version, DB error) afterward. Peers that rely on `StackerDBChunkInv` for scheduling downloads (rarest-first/newest-first, per the module-level docs in `stackslib/src/net/stackerdb/mod.rs`) may believe the announcing node already has the newest chunk and skip fetching it from elsewhere, when in fact the node never actually stored it — a form of false/non-canonical inventory being served as canonical, which the rules explicitly call out as an acceptable High-impact analog ("steering a node off the tip via false inventory"). This can degrade StackerDB replication reliability and delay propagation of legitimate signer/data messages, without requiring any privileged access — only the ability to send `StackerDBPushChunk` messages, which is unauthenticated/unprivileged at the P2P layer.

### Likelihood Explanation
Triggering requires only sending a `StackerDBPushChunk` message that passes `validate_received_chunk` (correct signature, size, and non-stale version relative to the version snapshot at read time) from any P2P-connected peer. No secret keys, other users' credentials, or elevated roles are needed — the attacker only needs a properly signed chunk from any legitimate slot owner (or a colluding pair of peers pushing to the same slot in the same processing window) to create the race between the immediate ack and the later, independent commit attempt.

### Recommendation
Do not send the `StackerDBChunkInv` acknowledgment reflecting an "accepted" version bump until after the chunk has been durably committed via `try_replace_chunk`. Either (a) perform the storage synchronously before constructing/sending the reply and report the version that was actually committed (re-reading `get_slot_versions` post-commit), or (b) explicitly decouple "will attempt to store" acks from "did store" acks so remote peers never learn of a version that is not yet guaranteed to be on disk.

### Proof of Concept
Not independently executable from the index alone (would require a running two/three-node testnet), but the fault is reachable purely from remote, unauthenticated input:
1. Two peers `B` and `C` are configured to replicate the same StackerDB with a shared slot `S` owned by signer key `k`.
2. Attacker in control of `k` sends `StackerDBPushChunk(S, version=5)` to victim node `A` via `B`, and near-simultaneously another `StackerDBPushChunk(S, version=6)` via `C`.
3. `A` processes both `StackerDBPushChunk` messages in `handle_unsolicited_StackerDBPushChunk`; both read the pre-update slot version (say 4) via `get_slot_versions`, both pass `validate_received_chunk` (5 > 4 and 6 > 4), both patch their own in-memory inventories and are immediately ack'd back to `B` and `C` respectively, claiming versions 5 and 6 are now held by `A`.
4. Later, in the relay thread, `process_stacker_db_chunks` calls `try_replace_chunk` for each — only one (say version 6) succeeds; the version-5 write returns `StaleChunk` (since version 6 already committed) and is silently dropped (log + `continue`).
5. `B` now believes `A` holds slot `S` at version 5, but `A` never actually stored that chunk — `B`'s local view of `A`'s inventory is false, matching the "served vs committed" fault class from the report.

    pub fn validate_received_chunk(
        &self,
        smart_contract_id: &QualifiedContractIdentifier,
        config: &StackerDBConfig,
        data: &StackerDBChunkData,
        expected_versions: &[u32],
    ) -> Result<bool, net_error> {
        // validate -- must not exceed this replica's configured chunk size.
        if (data.data.len() as u64) > config.chunk_size {
            info!(
                "Received StackerDBChunk for {} ID {}, which is oversized: {} bytes (max {} bytes)",
                smart_contract_id,
                data.slot_id,
                data.data.len(),
                config.chunk_size
            );
            return Ok(false);
        }

        // validate -- must be a valid chunk
        let Some(expected_version) = expected_versions.get(data.slot_id as usize) else {
            info!(
                "Received StackerDBChunk for {} ID {}, which is too big ({})",
                smart_contract_id,
                data.slot_id,
                expected_versions.len()
            );
            return Ok(false);
        };

        // validate -- must be signed by the expected author
        let addr = match self
            .stackerdbs
            .get_slot_signer(smart_contract_id, data.slot_id)?
        {
            Some(addr) => addr,
            None => {
                return Ok(false);
            }
        };

        let slot_metadata = data.get_slot_metadata();
        if !slot_metadata.verify(&addr)? {
            info!(
                "StackerDBChunk for {} ID {} is not signed by {}",
                smart_contract_id, data.slot_id, &addr
            );
            return Ok(false);
        }

        // validate -- must be the current or newer version
        if data.slot_version < *expected_version {
            info!(
                "Received StackerDBChunk for {} ID {} version {}, which is stale (expected {})",
                smart_contract_id, data.slot_id, data.slot_version, *expected_version
            );
            return Ok(false);
        }

        // validate -- must not exceed max writes
        if data.slot_version > config.max_writes {
            info!(
                "Write count exceeded for StackerDBChunk for {} ID {} version {} (max is {})",
                smart_contract_id, data.slot_id, data.slot_version, config.max_writes
            );
            return Ok(false);
        }

        Ok(true)
    }
