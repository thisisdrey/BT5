### Title
Priority-floor DoS-shedding check compares values computed under different bank fee/cost parameters, letting the shared floor and live packet priorities drift out of sync - (File: `core/src/banking_stage/transaction_scheduler/scheduler_controller.rs`, `core/src/sigverify.rs`, `core/src/transaction_priority.rs`)

### Summary
The scheduler publishes a `SchedulerPriorityFloor` derived from the *cached* priority of the lowest-priority transaction already buffered in its container. Sigverify workers use that shared floor to drop incoming packets whose priority is *recomputed fresh* against whatever bank happens to be the current `sharable_banks.working()` at verification time. Because transaction priority is `reward / (1 + cost)` and `reward` depends on `bank.fee_structure().lamports_per_signature` (a value the fee-rate governor adjusts every slot based on how congested the prior block was), the "last computed" priority stored in the container and the "currently computed" priority checked at sigverify can be derived from two different bank states, exactly like the Balancer bug where the invariant used the amplification factor from `getLastInvariant()` instead of the value from `_getAmplificationParameter()` at time of use.

### Finding Description
- Container-buffered transactions get a fixed `priority: u64` field set once, at receive time, via `TransactionState::new` (`core/src/banking_stage/transaction_scheduler/transaction_state.rs:11-37`), computed by `calculate_priority_and_cost` against whatever bank was current at that moment (`core/src/transaction_priority.rs:32-66`).
- When the scheduler's retained buffer saturates, `SaturationState::publish_floor` (`core/src/banking_stage/transaction_scheduler/scheduler_controller.rs:102-105`) publishes the queue-min transaction's *already-computed, aged* priority into the shared `SchedulerPriorityFloor` (`banking-stage-ingress-types/src/lib.rs:71-95`).
- Independently, `sigverify.rs::run_transaction_task` reads that floor and applies it to newly-arriving packets by recomputing their priority *fresh*, against the sigverify thread's own view of the bank: `let working_bank = sharable_banks.working();` then `apply_priority_floor_to_batch(&mut batch, floor, &working_bank)` (`core/src/sigverify.rs:300-323`, `370-441`), which calls `calculate_priority_from_bytes(bank, data)` → `calculate_priority_and_cost` (`core/src/transaction_priority.rs:73-88`, `32-66`).
- `calculate_priority_and_cost` derives `reward` from `bank.fee_structure().lamports_per_signature` (`core/src/transaction_priority.rs:44-52`), a per-bank value that the fee-rate governor updates every slot in response to congestion. It also depends on `bank.feature_set` for cost calculation.
- No mechanism ties the bank used to compute the *stored* container priority (basis of the floor) to the bank used to compute the *live* sigverify priority against that floor. As slots roll forward and `lamports_per_signature`/feature activations change, the floor value and the live comparison values are silently computed from two different fee/cost parameter states — mirroring the Balancer issue of comparing an invariant computed with a stale amplification factor against a pool state that has since moved on.

### Impact Explanation
The priority floor exists specifically as the DoS-shedding mechanism: when the banking-stage buffer saturates, low-value/low-fee packets are meant to be dropped *before* costly sigverify work, protecting the validator under load. If the fee-rate governor lowers `lamports_per_signature` between when the floor was computed (from an older, buffered transaction) and when a new packet's priority is recomputed at sigverify, the same nominal transaction will score a different priority than the one used to set the floor. This can let higher volumes of transactions clear the (now comparatively looser) floor than intended, or conversely spuriously drop legitimate transactions that would have cleared it under the current bank — i.e., the exact protection the floor exists to provide loses its correctness guarantee, weakening QoS enforcement under saturation. This is unprivileged-user reachable: any TPU client submitting transactions during a saturated leader slot is affected by whichever bank/fee state sigverify happens to be using at that instant.

### Likelihood Explanation
This requires only the ordinary operating condition already anticipated by the code (`SATURATION_BUFFER_PCT`/`DESATURATION_BUFFER_PCT` in `scheduler_controller.rs:41-46`) plus normal fee-rate-governor adjustment across slots, which happens continuously as block fullness varies. No privileged access or crafted malicious input is needed — it is a natural consequence of the floor's producer (scheduler, using aged/cached priorities) and consumer (sigverify, using freshly computed priorities against a possibly newer bank) not sharing a consistent parameter basis.

### Recommendation
Tie the floor comparison to a consistent basis: either (a) recompute/republish the floor using the same live bank sigverify will use for comparison (i.e., have the scheduler continuously re-derive the floor from the current working bank rather than from the aged container priority value), or (b) have sigverify's `apply_priority_floor_to_batch` normalize/re-scale the floor using the delta between the bank in effect when the floor was published and the bank in effect at check time, or (c) invalidate/clear the floor whenever the underlying bank's `fee_structure()`/feature set changes, analogous to fetching the current amplification parameter (`getAmplificationParameter`) instead of relying on the last-cached value (`getLastInvariant`).

### Proof of Concept
Conceptual reproduction (would need to be validated with an actual running scheduler/sigverify pipeline, which I could not execute in this environment):
1. Drive the banking-stage container into saturation under bank `B0` with `lamports_per_signature = X`; the scheduler publishes `floor = f(B0, X)` from the queue-min transaction (`scheduler_controller.rs::publish_floor`).
2. Advance to bank `B1` (new slot) where the fee-rate governor has adjusted `lamports_per_signature` downward due to reduced congestion (`bank.fee_structure().lamports_per_signature` changes).
3. Submit a transaction whose priority under `B0`'s fee parameters would have been below `floor`, but whose priority under `B1` (as recomputed live in `sigverify.rs::run_transaction_task` via `sharable_banks.working()`) is at or above `floor`.
4. Because sigverify recomputes against `B1` but the floor was set from `B0`-derived data, the transaction is admitted rather than shed, contrary to the saturation-mitigation intent (or the reverse: a transaction that should clear is dropped because `B1` lowered relative reward vs. cost for that shape of transaction).

Confidence/uncertainty: I was unable to trace the exact call site of `update_scheduler_priority_floor` (only found its call site, not its full body) or confirm empirically how often/rapidly `fee_structure().lamports_per_signature` actually changes slot-to-slot in this fork, due to running out of tool iterations. The core divergence (aged container-priority floor vs. live-bank-recomputed sigverify priority, with priority formula dependent on a per-bank, governor-adjusted fee parameter) is confirmed by the cited code, but the magnitude of real-world impact (how large the fee_rate delta typically is per slot) was not independently verified and should be checked before treating this as more than a low/medium-severity QoS-consistency issue.
