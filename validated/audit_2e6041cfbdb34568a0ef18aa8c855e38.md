Audit Report

## Title
Unauthorized permanent saturation of a victim's `Vesting` schedule slots via `pallet_vesting::vested_transfer` - (`substrate/frame/vesting/src/lib.rs`)

## Summary
`pallet-vesting`'s `vested_transfer` extrinsic is permissionless with respect to the `target` account and only validates `schedule.locked() >= MinVestedTransfer` and `schedule.is_valid()` (non-zero `locked`/`per_block`), never constraining schedule duration. Because `VestingInfo::per_block()` floors at `1` and `ending_block_as_balance` computes `locked / per_block()`, an attacker can create schedules that last for an arbitrarily large number of blocks at the minimum cost (`MinVestedTransfer`), and repeat this `MAX_VESTING_SCHEDULES` times against any target to fill its `Vesting` `BoundedVec`, causing all subsequent `vested_transfer`/`force_vested_transfer` calls to that account to fail with `AtMaxVestingSchedules`.

## Finding Description
`do_vested_transfer` at [1](#0-0)  only checks `schedule.locked() >= T::MinVestedTransfer::get()` and `schedule.is_valid()`, then delegates to `can_add_vesting_schedule`/`add_vesting_schedule`, which enforce only the `MAX_VESTING_SCHEDULES` slot-count bound via `Vesting::<T>::decode_len` [2](#0-1)  and the `BoundedVec::try_push` capacity check [3](#0-2) .

Neither check bounds schedule *duration*. `per_block()` is floored at `One::one()` [4](#0-3) , and `ending_block_as_balance` computes `locked / per_block()` (plus rounding) [5](#0-4) . Setting `per_block = 1` and `locked = MinVestedTransfer` produces a schedule lasting `MinVestedTransfer` blocks — potentially millions — at the minimum permitted cost per slot.

The `vested_transfer` extrinsic is dispatchable by any signed account against any `target` it does not control, gated only by `ensure_signed` and the lookup of `target` [6](#0-5) . `Vesting<T>` is a per-account `BoundedVec` capped at `MaxVestingSchedulesGet<T>` [7](#0-6) . Repeating the call `MAX_VESTING_SCHEDULES` times (28 in the reference node runtime [8](#0-7) ) fills the target's slots with near-maximal-duration schedules. Any subsequent `vested_transfer`/`force_vested_transfer` to that target then reverts with `Error::AtMaxVestingSchedules` [9](#0-8)  until the victim's own `vest`/`vest_other` prunes fully-vested entries via `exec_action`/`write_vesting` [10](#0-9) [11](#0-10)  — timing the attacker controls by choosing schedule length. Existing guards (`MAX_VESTING_SCHEDULES` count bound, `MinVestedTransfer` floor) do not stop this because neither limits duration, and there is no target-consent mechanism.

## Impact Explanation
This is a repeatable, target-specific denial of vesting-based transfers: a victim account can be locked out of receiving `vested_transfer`/`force_vested_transfer` funds (blocking exchanges, payroll, crowdloan/parachain reward distribution, or genesis allocations relying on this pallet) for an attacker-chosen duration bounded only by `BlockNumber`'s max value, at a fixed, minimal one-time cost (`MAX_VESTING_SCHEDULES × MinVestedTransfer`, ultimately transferred to the victim). It requires no privileged role, governance action, or infrastructure — only a public, permissionless dispatchable present in production runtimes (Polkadot, Westend, Rococo, node template).

## Likelihood Explanation
High feasibility and repeatability: the attacker needs only a signed account with balance ≥ `MAX_VESTING_SCHEDULES × MinVestedTransfer` and can execute the attack against any account at any time without timing constraints, front-running, or special access.

## Recommendation
- Enforce a maximum vesting schedule duration (e.g., a configurable cap on `ending_block_as_balance - starting_block`) so a single schedule cannot occupy a slot indefinitely.
- Require target consent or an opt-in/allow-list for unsolicited `vested_transfer`s.
- Allow the account owner to evict or merge the least useful schedules once at capacity instead of hard-failing new legitimate transfers.

## Proof of Concept
1. Attacker `A` holds balance ≥ `MAX_VESTING_SCHEDULES × MinVestedTransfer`.
2. For `i in 0..MAX_VESTING_SCHEDULES`, `A` calls `Vesting::vested_transfer(target, VestingInfo::new(MinVestedTransfer, 1, current_block))`; each succeeds since `Vesting<T>::get(target).len() < MAX_VESTING_SCHEDULES` and `schedule.is_valid()` holds with `per_block=1`.
3. After `MAX_VESTING_SCHEDULES` calls, `target`'s `Vesting` `BoundedVec` is full with schedules ending far in the future (`starting_block + MinVestedTransfer` blocks).
4. Any subsequent `Vesting::vested_transfer(_, target, _)` or `Vesting::force_vested_transfer(_, _, target, _)` reverts with `Error::AtMaxVestingSchedules`, confirming the target is denied vesting-based transfers until the attacker-chosen schedules fully elapse or `target` calls `vest`/`vest_other`.

```rust
	// Execute a vested transfer from `source` to `target` with the given `schedule`.
	fn do_vested_transfer(
		source: &T::AccountId,
		target: &T::AccountId,
		schedule: VestingInfo<BalanceOf<T>, BlockNumberFor<T>>,
	) -> DispatchResult {
		// Validate user inputs.
		ensure!(schedule.locked() >= T::MinVestedTransfer::get(), Error::<T>::AmountLow);
		if !schedule.is_valid() {
			return Err(Error::<T>::InvalidScheduleParams.into());
		};

		// Check we can add to this account prior to any storage writes.
		Self::can_add_vesting_schedule(
			target,
			schedule.locked(),
			schedule.per_block(),
			schedule.starting_block(),
		)?;

		T::Currency::transfer(source, target, schedule.locked(), ExistenceRequirement::AllowDeath)?;

		// We can't let this fail because the currency transfer has already happened.
		// Must be successful as it has been checked before.
		// Better to return error on failure anyway.
		let res = Self::add_vesting_schedule(
			target,
			schedule.locked(),
			schedule.per_block(),
			schedule.starting_block(),
		);
		debug_assert!(res.is_ok(), "Failed to add a schedule when we had to succeed.");

		Ok(())
	}
```

```rust
	fn write_vesting(

		let schedules: BoundedVec<

		} else {
			Vesting::<T>::insert(who, schedules)
		}

		Ok(())
	}
```

```rust
	/// Ensure we can call `add_vesting_schedule` without error. This should always
	/// be called prior to `add_vesting_schedule`.
	fn can_add_vesting_schedule(
		who: &T::AccountId,
		locked: BalanceOf<T>,
		per_block: BalanceOf<T>,
		starting_block: BlockNumberFor<T>,
	) -> DispatchResult {
		// Check for `per_block` or `locked` of 0.
		if !VestingInfo::new(locked, per_block, starting_block).is_valid() {
			return Err(Error::<T>::InvalidScheduleParams.into());
		}

		ensure!(
			(Vesting::<T>::decode_len(who).unwrap_or_default() as u32) < T::MAX_VESTING_SCHEDULES,
			Error::<T>::AtMaxVestingSchedules
		);

		Ok(())
	}
```

```rust
	/// Block number at which the schedule ends (as type `Balance`).
	pub fn ending_block_as_balance<BlockNumberToBalance: Convert<BlockNumber, Balance>>(
		&self,
	) -> Balance {
		let starting_block = BlockNumberToBalance::convert(self.starting_block);
		let duration = if self.per_block() >= self.locked {
			// If `per_block` is bigger than `locked`, the schedule will end
			// the block after starting.
			One::one()
		} else {
			self.locked / self.per_block() +
				if (self.locked % self.per_block()).is_zero() {
					Zero::zero()
				} else {
					// `per_block` does not perfectly divide `locked`, so we need an extra block to
					// unlock some amount less than `per_block`.
					One::one()
				}
		};

		starting_block.saturating_add(duration)
	}
```
