### Title
Unauthenticated `RecvError` packets let an off-path attacker tear down active tunnels by spoofing only a UDP source address and a plaintext index - ([File: outside.go])

### Summary
Nebula accepts `header.RecvError` packets before any decryption or certificate check and, by default (`listen.accept_recv_error: always`), tears down the referenced tunnel if the packet's source address matches the tunnel's currently known remote endpoint. Because `RemoteIndex` travels in the cleartext packet header on every packet and UDP allows source-address spoofing, an attacker with no CA-signed certificate can forge this single unauthenticated field/address pair to destroy a legitimate tunnel — the same trust-without-verification bug class as the reported M-05 finding, where an unauthenticated/unverified signal is blindly trusted to drive a destructive state change.

### Finding Description
`readOutsidePackets` dispatches `header.RecvError` packets straight to `f.handleRecvError` before any decryption, replay-window check, or certificate validation is performed: [1](#0-0) 

`handleRecvError` looks up the hostinfo purely by the plaintext `h.RemoteIndex` field, and its only anti-spoofing check is a comparison against the currently known remote UDP address: [2](#0-1) 

If `hr.IsValid() && hr != addr` fails to trigger (i.e., the packet's source address happens to equal the tunnel's current remote endpoint), the code calls `f.closeTunnel(hostinfo)` and deletes the pending hostinfo — with no cryptographic proof that the sender actually holds the peer's private key or certificate. `RemoteIndex` is not a secret: it is encoded in cleartext in every packet's header (used for hostinfo lookup before decryption is possible), so any passive observer of a single packet on the path (or a party who previously handshook and later loses the tunnel) can read/replay it.

The severity is controlled only by a config flag whose default trusts the signal unconditionally: [3](#0-2) 

This mirrors the M-05 root cause: a value that should be independently verified (fund-moving `nominals` in the DeFi report; here, the authenticity of a `RecvError` signal that triggers tunnel teardown) is instead trusted based on a single unauthenticated/spoofable check, and misuse of that trust directly destroys legitimate state.

### Impact Explanation
An attacker who can spoof a UDP source address (trivial on many network paths, and the CHANGELOG for 1.10.x itself documents multiple `remote_allow_list` / address-trust regressions in this exact area) can force teardown of any active Nebula tunnel whose `RemoteIndex` they can observe from a single packet, without ever possessing a valid Nebula certificate. This is a remote state-poisoning / denial-of-service impact: it repeatedly severs tunnels between legitimate, mutually-authenticated hosts, and forces "fast reconnect" deletion from the pending hostmap, amplifying disruption. This qualifies as a concrete remote-state-poisoning impact under the strict output rules.

### Likelihood Explanation
Likelihood is high for the default configuration (`accept_recv_error: always`): no certificate, no successful handshake, and no possession of any cryptographic secret is required — only knowledge of the target's current index/address and the ability to send a UDP packet with a spoofed source. `RemoteIndex` is observable from a single sniffed packet on-path, and UDP source-address spoofing (or being on-path / behind shared NAT) is a well-known, practically-executable attack primitive, especially since the project's own changelog documents the security consideration around `recv_error` disclosure/behavior in this exact code path.

### Recommendation
Do not let an unauthenticated, cleartext-triggered message directly destroy tunnel state. At minimum:
- Require `RecvError` handling to also validate a value derived from the session's authenticated key material (e.g., a MAC/nonce bound to the connection) rather than relying solely on `RemoteIndex` + source-address equality.
- Default `listen.accept_recv_error` to `never` or `private`, requiring explicit opt-in for this unauthenticated fast-teardown path, consistent with the more restrictive posture already offered but not defaulted.
- Consider gating teardown behind additional corroborating signals (e.g., only accept when correlated with an actual decrypt failure count/timeout on that same session) rather than a single unauthenticated packet.

### Proof of Concept
1. Establish a legitimate Nebula tunnel between hosts A and B; observe (via passive capture, or by being the peer at any earlier point) a single packet from B to A and extract the plaintext `RemoteIndex` field from its header, and A's known remote `UdpAddr`.
2. From attacker-controlled infrastructure capable of spoofing B's UDP source address (or from an on-path/NAT-shared vantage point matching `hr`), craft a `header.RecvError` packet with that `RemoteIndex`, per `header.Encode(make([]byte, header.Len), header.Version, header.RecvError, 0, index, 0)` as done in `sendRecvError`.
3. Send the forged packet to A's listening UDP port.
4. Observe `handleRecvError` on A: since the spoofed source address matches `hostinfo.GetRemote()`, `f.closeTunnel(hostinfo)` executes and the hostinfo is deleted from the pending map — the legitimate tunnel is torn down with no certificate or handshake ever presented by the attacker. [4](#0-3)

```go
func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
```

```go
func (f *Interface) reloadAcceptRecvError(c *config.C) {
	if c.InitialLoad() || c.HasChanged("listen.accept_recv_error") {
		stringValue := c.GetString("listen.accept_recv_error", "always")

		switch stringValue {
		case "always":
			f.acceptRecvErrorConfig = recvErrorAlways
		case "never":
			f.acceptRecvErrorConfig = recvErrorNever
		case "private":
			f.acceptRecvErrorConfig = recvErrorPrivate
		default:
			if c.GetBool("listen.accept_recv_error", true) {
				f.acceptRecvErrorConfig = recvErrorAlways
			} else {
				f.acceptRecvErrorConfig = recvErrorNever
			}
		}

		f.l.Info("Loaded accept_recv_error config", "acceptRecvError", f.acceptRecvErrorConfig.String())
	}
}
```
