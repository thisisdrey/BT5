### Title
Unbounded `DelegatedResourceAccountIndexCapsule.toAccountsList` / `fromAccountsList` growth via `FreezeBalanceContract` delegation lets an attacker bloat an account's resource-delegation index, causing every future freeze/delegate/unfreeze on that account to become progressively more expensive — [File: actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java]

### Summary
`FreezeBalanceActuator#delegateResource` maintains, for the legacy (pre-`AllowDelegateOptimization`) resource-delegation model, a single `DelegatedResourceAccountIndexCapsule` per address holding `to_accounts` / `from_accounts` repeated-bytes lists. Before appending a new counterpart address, the code performs a full linear scan (`List.contains`) over the existing list, then rewrites the *entire* capsule (whole array) back to the store. There is no cap on how many distinct receiver/giver addresses can be added to this list, mirroring the `PP_Streaming_v1.activePaymentReceivers` bug class: an unbounded per-account array that is both linearly scanned and fully re-serialized on every mutating call.

### Finding Description [1](#0-0) 

When `!dynamicPropertiesStore.supportAllowDelegateOptimization()`, every call to `FreezeBalanceContract` with `resource_receiver` delegation:
1. Loads the owner's `DelegatedResourceAccountIndexCapsule` (`toAccountsList`), does `toAccountsList.contains(receiverAddress)` — O(n) — and if absent, appends via `addToAccount`, then `put`s the whole capsule back (full re-serialize of the growing list).
2. Symmetrically loads/mutates/re-serializes the receiver's `fromAccountsList`. [2](#0-1) 
The capsule wraps the whole protobuf-encoded `repeated bytes` list; every `addToAccount`/`addFromAccount`/`removeToAccount`/`removeFromAccount` call rebuilds the full protobuf message, and `getIndex()` in the store deserializes the entire array on every read. [3](#0-2) 
Unfreeze similarly copies the *entire* list into a new `ArrayList`, removes one element, and rewrites the whole array — cost scales with list length, not with the number of entries actually being removed.

An attacker who repeatedly issues cheap `FreezeBalanceContract` transactions delegating bandwidth/energy to (or from) many distinct throwaway addresses can grow a target account's `toAccountsList`/`fromAccountsList` without bound, since:
- Each delegation only requires a minimal frozen balance (fixed by `TRX_PRECISION`, i.e. as little as 1 TRX per new counterpart address), which is cheap relative to growing an array indefinitely.
- There is no `MAX_*` size check analogous to `MaxFrozenSupplyNumber` (which the codebase does enforce elsewhere, e.g. `AssetIssueActuator`'s frozen-supply-list bound) or to the array size caps already added for `TransactionApprovedList`, JSON-RPC log filters, etc. (see the various `*OverLimit*` tests already present in this repo, which shows the maintainers have proactively hardened *other* unbounded-list code paths but this one remains unguarded).

This is functionally identical to the reported `PP_Streaming_v1._findAddressInActiveStreams` bug: an unbounded per-account array, checked with a linear `contains()` scan before insertion, growing without limit as a side effect of ordinary, cheap, unprivileged calls, and fully reloaded/rewritten on every subsequent mutation of that account's state.

### Impact Explanation
As the array grows, every subsequent `FreezeBalanceContract` (with delegation) or `UnfreezeBalanceContract` touching that account pays increasing CPU/energy cost to deserialize, scan, and re-serialize the whole list. Read-side API queries (`getDelegatedResourceAccountIndex` via `Wallet`, gRPC/HTTP) that return the full list also become increasingly expensive to serve, potentially degrading node responsiveness for that query. In the worst case this can make it costly-to-impossible for the legitimate owner (or victim who becomes the target of unsolicited delegations) to continue freezing/unfreezing/delegating resources on their own account, effectively freezing their ability to manage their staked TRX resource state — a resource-DoS on a specific account rather than a full node halt.

### Likelihood Explanation
Exploitability depends on `DynamicPropertiesStore.allowDelegateOptimization` being disabled — if this committee proposal has already been activated on the target network, the legacy array path is bypassed in favor of per-pair keyed storage (`delegate`/`delegateV2`/`unDelegate` in `DelegatedResourceAccountIndexStore`, which do not suffer unbounded single-key growth). I was unable to determine from the available index whether `AllowDelegateOptimization` defaults to enabled or disabled on the current production TRON mainnet/testnets, or whether this is a one-way, already-activated proposal — this is a genuine gap in what I could verify from the indexed code (the reference.conf / ProposalUtil bounds for this parameter were not fully retrievable). If the optimization is not yet enabled on some network, or the actuator path remains reachable via legacy transaction types, the attack requires only unprivileged, minimally-funded `FreezeBalanceContract` transactions and is straightforward to script.

### Recommendation
- Add an explicit cap (e.g., `MAX_DELEGATE_INDEX_SIZE`) on `toAccountsList`/`fromAccountsList` length in `FreezeBalanceActuator#delegateResource`, rejecting new delegations to previously-unseen addresses once the cap is hit, analogous to the existing `MaxFrozenSupplyNumber` check in `AssetIssueActuator`.
- Regardless of `supportAllowDelegateOptimization` status, migrate/deprecate the legacy array-based `DelegatedResourceAccountIndexCapsule` storage entirely in favor of the already-implemented per-pair prefixed-key scheme (`FROM_PREFIX`/`TO_PREFIX`) used by `DelegatedResourceAccountIndexStore.delegate()`, removing the unbounded single-key array code path.
- Confirm and, if needed, force-enable `AllowDelegateOptimization` network-wide so the vulnerable legacy path can never be exercised again.

### Proof of Concept
Not independently reproduced against a running node (index-only investigation); the following steps describe the attack path supported by the cited code:
1. Ensure `dynamicPropertiesStore.supportAllowDelegateOptimization()` returns `false` (legacy path active).
2. From attacker-controlled address `A0`, freeze 1,000,000 sun and issue `FreezeBalanceContract` with `resource_receiver = victim`, repeated with `N` distinct freshly generated attacker addresses `A0..AN` each delegating to `victim`.
3. Each call appends `victim`'s `fromAccountsList` with a new attacker address (`FreezeBalanceActuator.java:334-345`), with `contains()` cost growing O(n) per call and full-list re-serialization on every `put`.
4. After sufficient iterations, `victim`'s subsequent `FreezeBalanceContract`/`UnfreezeBalanceContract` calls, and any `getDelegatedResourceAccountIndex` API query for `victim`, incur processing cost proportional to the bloated list size.
