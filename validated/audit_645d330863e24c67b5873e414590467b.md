### Title
Missing bounds check on `Zip64ExtraField::attr64()` index causes OOB read when merging attacker-supplied JAR/ZIP entries - (File: `src/tools/singlejar/zip_headers.h`)

### Summary
`singlejar` (Bazel's internal JAR-merging tool used by `java_library`/`java_binary` and any build that consumes third-party `.jar` dependencies) parses ZIP64 "extra field" records to recover 64-bit compressed/uncompressed sizes when the corresponding 32-bit ZIP header fields are `0xFFFFFFFF`. The accessor `Zip64ExtraField::attr64(int index)` indexes directly into a flexible array member with no check that `index < attr_count()`, even though callers (`CDH::compressed_file_size()`/`uncompressed_file_size()`, `LH::compressed_file_size()`) compute or hardcode that index based only on the *32-bit size fields*, not on the actual declared payload size of the Zip64 extra field that was found.

### Finding Description
The Zip64 extra field is documented as variable-length: only the 64-bit values that are actually needed (because their 32-bit counterpart is `0xFFFFFFFF`) are present, in a fixed order (uncompressed size, compressed size, offset). `attr_count()` derives the number of present 64-bit values from `payload_size()`: [1](#0-0) 

`CDH::compressed_file_size()` decides which slot holds the compressed size purely from whether the *uncompressed* 32-bit field also needs extension, and then calls `attr64()` with that computed index — without ever consulting `attr_count()` to confirm the field actually contains that many 64-bit values: [2](#0-1) 

The same unchecked-index pattern appears in `LH::compressed_file_size()`/`uncompressed_file_size()`, which unconditionally read `attr64(0)`/`attr64(1)`: [3](#0-2) 

`ExtraField::find()` only validates that the *ExtraField header itself* (`tag`/`payload_size`) and its declared `size()` fit within the surrounding `extra_fields` buffer; it performs no semantic validation that `payload_size` is consistent with what the ZIP64-size-decoding logic expects to read: [4](#0-3) 

An attacker who controls a JAR/ZIP file consumed by `singlejar` (e.g. a `java_import`/`http_jar`/`http_archive`-provided dependency, or any zip processed during a build) can craft an entry whose Central Directory Header sets `compressed_file_size32 = uncompressed_file_size32 = 0xFFFFFFFF` (both need "ext64"), but whose accompanying Zip64 extra field declares `payload_size = 8` (i.e. `attr_count() == 1`, only one 64-bit slot actually present). `CDH::compressed_file_size()` will then compute `index = ziph::zfield_has_ext64(uncompressed_file_size32()) == 1` and call `attr64(1)`, reading 8 bytes past the single 64-bit value the archive author declared — this read lands beyond the intended field, inside (or, if the record sits at the tail of the memory-mapped input file, beyond) the ZIP entry's declared byte range. Because `InputJar` memory-maps the file directly (`MappedFile`, see `input_jar.cc` `LocateCentralDirectory`), this out-of-bounds slot is read straight out of the process's mapped memory with no further validation.

This precisely mirrors the CVE-2024-21640 bug class: a producer-controlled discriminant field (`pixel_format` in CEF; here, the 32-bit size fields that indicate "value is stored in extra data") is trusted to select how much/what data to read from a buffer, without validating that the buffer (the Zip64 extra field payload) actually contains enough declared elements for that selection.

### Impact Explanation
The out-of-bounds 8-byte read can leak adjacent memory content (bytes from other, unrelated parts of the memory-mapped input file, or the tail of the mapping) into a size value. This size value is subsequently used by `singlejar` to determine how many bytes of the entry's data to copy/decompress/merge into the combined output jar (`OutputJar::AddJar`/`WriteEntry`, `TransientBytes::DecompressEntryContents`). A corrupted/leaked size value can cause `singlejar` to copy an attacker-influenced but unintended byte range from the mapped file into the produced jar, or to over/under-read while merging entries — an information-disclosure/data-corruption primitive within the build's output artifact, consistent with the CVSS 5.4 "confidentiality/integrity low, no availability impact" profile of the analog.

### Likelihood Explanation
`singlejar` runs by default whenever `java_library`/`java_binary`/`java_import` targets are merged, and it processes any JAR supplied via external dependencies (which can originate from an untrusted mirror, registry, or repository as covered by the threat model). Triggering the bug requires no privileged access — only the ability to supply a malformed ZIP64 extra field inside a `.jar`/`.zip` that ends up as a build input, which is squarely within the "attacker publishes an archive that a victim's build consumes" scenario.

### Recommendation
- In `Zip64ExtraField::attr64()`, validate `index < attr_count()` before dereferencing `attr_[index]`, or have callers check `attr_count()` against the number of 64-bit values their computed index requires before calling `attr64()`.
- In `CDH::compressed_file_size()`/`uncompressed_file_size()` and `LH::compressed_file_size()`/`uncompressed_file_size()`, verify that the found `Zip64ExtraField`'s `attr_count()` is sufficient for the derived index; treat a mismatch as a corrupt/malformed archive error (as is already done elsewhere in `zip_headers.h`/`output_jar.cc` for malformed extra fields, e.g. the `diag_errx(1, "malformed extra field ...")` checks in `output_jar.cc`).

### Proof of Concept
A `BuildIntegrationTestCase`/`src/test/shell` reproduction would:
1. Hand-craft a minimal ZIP file with one entry whose Local/Central Directory Header sets `compressed_file_size32 = 0xFFFFFFFF` and `uncompressed_file_size32 = 0xFFFFFFFF`.
2. Attach a Zip64 extra field to the Central Directory Header with `payload_size = 8` (declaring only one 64-bit attribute, e.g., only the uncompressed size), immediately followed in the file by attacker-chosen bytes (simulating adjacent unrelated data).
3. Feed this archive to `singlejar` (e.g., via a `java_import`/`AddJar` call in a unit test analogous to `src/tools/singlejar/zip_headers_test.cc` or `output_jar_test.cc`), and observe that `CDH::compressed_file_size()` returns the attacker-planted adjacent 8 bytes reinterpreted as a `uint64_t` instead of failing with a "malformed extra field" diagnostic, and that this value is subsequently used to size a copy/read operation in `OutputJar::AddJar`.

*Note: this analysis is based on static reasoning over the indexed source; I was not able to execute `singlejar` to empirically confirm the resulting read lands outside the mapped file region in all cases (this depends on file layout and page alignment), so the crash/leak severity in practice should be confirmed with the described PoC before treating this as fully validated.*

  static const ExtraField* find(uint16_t tag, const uint8_t* start,
                                const uint8_t* end) {
    while (start < end) {
      if (ziph::byte_ptr(start) + sizeof(ExtraField) > ziph::byte_ptr(end)) {
        break;
      }
      auto extra_field = reinterpret_cast<const ExtraField*>(start);
      if (ziph::byte_ptr(start) + extra_field->size() > ziph::byte_ptr(end)) {
        break;
      }
      if (extra_field->is(tag)) {
        return extra_field;
      }
      start = ziph::byte_ptr(start) + extra_field->size();
    }
    return nullptr;
  }
