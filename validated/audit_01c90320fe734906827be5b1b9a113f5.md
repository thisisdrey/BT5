### Title
Unprivileged users can force-mint deposit positions into a victim's account, filling their per-account token list up to `MAX_TOKENS_PER_USER` and freezing the victim's ability to open new positions — ([File: contracts/DepositToken.sol])

### Summary
`DepositToken.deposit(uint256 amount_, address onBehalfOf_)` is a public, unprivileged function that mints `msdTOKEN` deposit-position tokens to an arbitrary `onBehalfOf_` account, paid for by the caller (`contracts/DepositToken.sol:211-237`). There is no opt-in and no way for the beneficiary to refuse the position. The Pool tracks which deposit tokens each account holds in a bounded enumerable set (`MappedEnumerableSet`, `contracts/lib/MappedEnumerableSet.sol`) capped by `MAX_TOKENS_PER_USER` (`contracts/Pool.sol`). An attacker can grief a victim by depositing dust amounts of every listed deposit token on the victim's behalf (or dust-transferring the tokens to them), pushing the victim's account token list to the cap so subsequent position-opening operations revert.

### Finding Description
The bug class is "acting on another user's behalf in a way the victim cannot refuse, forcing an unfavorable account state." In the external report, `claimMultiple` fragmented a victim's voting power; here, `deposit` (and plain `transfer`/`transferFrom` of `msdTOKEN`) registers a new deposit-token entry in the victim's account list each time they receive a balance of a token they did not previously hold. Because the list is capped (`MAX_TOKENS_PER_USER` enforced in `Pool.sol`), the attacker can fill every slot with dust positions, paid for with their own funds at dust cost.

### Impact Explanation
Once the victim's deposit-token set is at the cap, any operation that would add a new deposit token to their account reverts — they cannot deposit a different collateral, cannot receive `msdTOKEN` transfers, and leverage/zap flows through `SmartFarmingManager` that mint new deposit positions to them will revert. Since Metronome lists many collaterals (msUSD/msETH pools across deployments), the victim's ability to manage their position can be temporarily frozen; mitigating factors (the victim can burn/withdraw a dust position to free a slot) make this a temporary rather than permanent freeze.

### Likelihood Explanation
The attack requires only an EOA calling `deposit(dustAmount, victim)` repeatedly across the deposit tokens of a pool. Cost is proportional to the number of collaterals needed to reach the cap and the dust amounts, which the attacker can partially recover by withdrawing afterwards (fees may apply). No privileged role, oracle manipulation, or flash loan is required.

### Recommendation
Require consent for third-party deposits (e.g., only mint to `_msgSender()`, or route through an allowance/signature), mirroring the recommended fix in the external report: when `msg.sender != onBehalfOf_`, restrict or disallow the operation. Alternatively, do not register a deposit token in the account's enumerable set for transfers/deposits the account did not initiate, or make adding to the set permissionless-tolerant by not reverting at the cap on receive paths.

### Proof of Concept
```solidity
// Attacker fills victim's deposit-token set with dust positions
address victim = ...;
IDepositToken[] memory dts = pool.depositTokens(); // all listed collaterals
for (uint256 i; i < dts.length; ++i) {
    IERC20 underlying = dts[i].underlying();
    underlying.approve(address(dts[i]), 1);
    dts[i].deposit(1, victim); // registers dts[i] in victim's account set
}
// victim's account deposit-token list is now at MAX_TOKENS_PER_USER;
// victim.deposit(newToken) and any mint of a not-yet-held deposit token to
// victim reverts until the victim manually withdraws a dust position.
```
Note: the exact revert site in `Pool.sol` where `MAX_TOKENS_PER_USER` is enforced on set insertion could not be fully read within tool limits, so the precise revert condition (on mint vs. on first non-zero balance) should be confirmed against `Pool.sol` / `DepositToken` transfer hooks before finalizing a PoC.     function deposit(
        uint256 amount_,
        address onBehalfOf_
    ) external override whenNotPaused nonReentrant onlyIfDepositTokenExists returns (uint256 _deposited, uint256 _fee) {
        if (amount_ == 0) revert AmountIsZero();
        if (onBehalfOf_ == address(0)) revert BeneficiaryIsNull();

        IPool _pool = pool;
        IERC20 _underlying = underlying;
        address _msgSender = _msgSender();
        address _treasury = address(_pool.treasury());

        if (_msgSender == _treasury) revert TreasuryCanNotDeposit();

        uint256 _balanceBefore = _underlying.balanceOf(_treasury);
        _underlying.safeTransferFrom(_msgSender, _treasury, amount_);
        amount_ = _underlying.balanceOf(_treasury) - _balanceBefore;

        (_deposited, _fee) = quoteDepositOut(amount_);
        if (_fee > 0) {
            _mint(_pool.feeCollector(), _fee);
        }

        _mint(onBehalfOf_, _deposited);

        emit CollateralDeposited(_msgSender, onBehalfOf_, amount_, _deposited, _fee);
    }
