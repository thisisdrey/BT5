### Title
Out-of-bounds heap read parsing untrusted ZIP/JAR central-directory extra fields - (File: third_party/ijar/zip.cc)

### Summary
`InputZipFile::ProcessCentralDirEntry` in ijar reads central-directory-header fields (`file_name_length`, `extra_field_length`, and the Zip64 extra-field payload) directly from an attacker-supplied, memory-mapped ZIP/JAR without any bounds validation against the mapped file length, unlike the analogous local-file-header parser which explicitly calls `EnsureRemaining()` before every variable-length read.

### Finding Description
`ProcessLocalFileEntry` validates every variable-length read against the remaining mapped-file size via `EnsureRemaining()` before advancing the cursor [1](#0-0) . `ProcessCentralDirEntry`, which walks the central directory used by both `ijar` (`InputZipFile::CalculateOutputLength`, `ProcessNext`) and singlejar's jar-merging path, has no equivalent check: it reads `file_name_length`, `extra_field_length`, `file_comment_length` straight from attacker-controlled header bytes and then unconditionally advances `p`/`extra_p` and dereferences memory using them [2](#0-1) . Inside the extra-field loop, `header_id` and `data_size` are read from the extra-field bytes and, when `header_id == ZIP64_EXTRA_FIELD_TAG`, `get_u8le(extra)` is called to read 8-byte little-endian values directly from `extra` with no check that `data_size` is at least 8 bytes or that `extra + 8` (or `extra_p + data_size`) stays within the mapped file/central-directory region [3](#0-2) . A crafted CDH can declare an oversized `extra_field_length`/`data_size` that runs past the actual mmap'd bytes, causing `get_u8le`/`memcpy` to read past the end of the mapping — analogous to the extended-content-descriptor parsing in `gst_asf_demux_process_ext_content_desc` (CVE-2017-5847), where a length field taken from untrusted media metadata is trusted without validating it against the buffer's real extent, producing an out-of-bounds heap read.

By contrast, `src/tools/singlejar/zip_headers.h`'s `ExtraField::find()` and the call sites in `output_jar.cc` do perform explicit bound checks (`byte_ptr(ef) + ef->size() > byte_ptr(end)`) before trusting extra-field sizes [4](#0-3) [5](#0-4) , confirming that the ijar central-directory path (`third_party/ijar/zip.cc`) is missing this same protection that exists elsewhere in the same codebase, and is the weaker of the two ZIP-parsing implementations.

### Impact Explanation
`ijar` and singlejar process JAR/ZIP files that can originate from external, attacker-influenced sources reachable during a build — e.g. `http_jar`/`http_file` downloads, Maven/registry artifacts fetched via `rules_jvm_external`, or precompiled third-party jars checked into an untrusted branch that CI later builds. Feeding such a file with a malformed central-directory extra field into `ijar` (used to produce interface jars for `java_library`) or singlejar triggers an out-of-bounds heap read, which can crash the build process (worker) or potentially leak adjacent heap memory contents into derived output depending on how the read bytes are subsequently used (e.g., as a 64-bit size/offset value echoed into computed sizes).

### Likelihood Explanation
Any build that ingests a jar produced or served by an untrusted party (mirror, registry, or hostile CI branch) and runs it through `ijar`/singlejar will parse the central directory unconditionally; the missing bounds check is unconditionally reachable and requires no special build flags, and unlike the local-file-header path, no `EnsureRemaining` guard exists to stop a malformed extra field from being trusted.

### Recommendation
Add explicit bounds validation in `ProcessCentralDirEntry` (and `MaybeReadZip64CentralDirectory`/`FindZip64CentralDirectory`) mirroring `EnsureRemaining()`/`ExtraField::find()`: verify `file_name_length`, `extra_field_length`, `file_comment_length`, and each extra-field's `data_size` (including the Zip64 tag's 8/16/24-byte payload) fit within the mapped file bounds before reading or advancing pointers, and reject the entry with an error instead of reading past the mapping.

### Proof of Concept
A JUnit/`src/test/shell/bazel` proof would construct a minimal ZIP/JAR whose central directory header declares `extra_field_length` (or a Zip64 extra-field `data_size`) larger than the bytes actually present before EOF/mmap end, then invoke `ijar`'s `InputZipFile::CalculateOutputLength()`/`ProcessNext()` (or singlejar's `--sources` merge path) on it under ASan, expecting a heap-buffer-overflow (read) report instead of a graceful parse error — analogous to the existing `CreateZipWithMalformedExtraField` test helper already present for singlejar's CDH parsing [6](#0-5) , but targeting `third_party/ijar/zip.cc`'s unguarded `ProcessCentralDirEntry`.

  size_t lh_size = sizeof(LH) + filename.size();
