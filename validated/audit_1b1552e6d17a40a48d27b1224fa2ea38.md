## Title
Vault `deposit` mints zero shares while still pulling underlying tokens when total-assets is fully written down to zero via `socialize-debt` - ([File: mainnet/contracts/vault/v0-vault-stx.clar])

### Summary
The Aura finding describes tokens being pulled from a user without the corresponding action (locking) being performed, because a branch that should convert the pulled funds into a benefit for the user is skipped, leaving them "stuck." The Zest vaults have a structurally identical gap in `convert-to-shares-preview`, used by `deposit`: when `total-supply-preview() != 0` but `total-assets-preview() == 0`, the function returns `u0` shares, yet `deposit` still unconditionally pulls the full underlying `amount` from the depositor via `receive-underlying`.

### Finding Description
`convert-to-shares-preview` in the vault contracts (e.g. `v0-vault-stx.clar`) is: [1](#0-0) 

This returns `u0` shares whenever `ts != u0` and `ta == u0`. `ta` (`total-assets-preview`) can reach `u0` after `socialize-debt` is invoked enough times/amounts by the market to fully write off the vault's tracked `assets` and `total-borrowed` while `zft` (`total-supply`) remains non-zero, since `socialize-debt` only reduces `principal-scaled`, `total-borrowed`, and `assets`, and never touches or burns the `zft` share supply: [2](#0-1) 

In `deposit`, the computed `inkind` share count is only checked via the caller-supplied `min-out` slippage bound - there is no protection against `inkind == u0` on its own (no `ERR-OUTPUT-ZERO` style check exists here, unlike `redeem`, which does assert `(> inkind u0)`): [3](#0-2) 

If a caller supplies `min-out = u0` (a common default for a first deposit into a pool believed to be healthy, or via any integrator/aggregator that doesn't know the pool state), the `asserts! (>= inkind min-out) ERR-SLIPPAGE)` check trivially passes with `inkind = u0`. The function proceeds to call `receive-underlying amount account`, pulling the user's full underlying token amount into the vault, and mints `zft inkind recipient` i.e. mints zero shares: [4](#0-3) 

The user's underlying tokens are transferred into the vault but the user receives no shares representing any claim on them - functionally identical to the Aura bug where CVX is pulled from the user but the corresponding beneficial action (locking) is skipped because of a missing/insufficient guard, leaving the user's funds stuck (here, effectively donated to the vault / to other zft holders, with the depositor receiving nothing in return).

### Impact Explanation
This is a direct loss of principal for the depositing user: their underlying tokens (STX/sBTC/USDC/etc.) are pulled into the vault with zero economic claim minted back. It falls under "theft of unclaimed yield... or temporary/permanent freezing of funds" / direct loss of user funds at rest, since the deposited principal becomes indistinguishable from vault assets with no corresponding share claim - the depositor cannot redeem it. The same `convert-to-shares-preview` pattern and analogous `deposit`/`min-out` guard exist in all vault contracts (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`), so the exposure is systemic to the vault design, not a single-file issue.

### Likelihood Explanation
Reaching `ta == u0` with `ts != u0` requires the vault to have been driven to a state where `socialize-debt` has written off all tracked assets/borrowed value for that vault (i.e., a market has already suffered bad debt severe enough to socialize 100% of the vault's assets) while zft shares remain outstanding for existing depositors who haven't redeemed. This is a legitimate, reachable end-state of the protocol's own designed socialize-debt mechanism (not a DAO misconfiguration), and once reached, any depositor calling `deposit` with `min-out = u0` (the natural default when a user/integrator does not know shares will be zero) immediately loses their principal. It is not guaranteed to trigger on every call (a nonzero `min-out` protects the caller), which is why likelihood is not "high," but the underlying state is protocol-reachable without any privileged action.

### Recommendation
Add an explicit output check in `deposit` analogous to the one already present in `redeem`, e.g. `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)`, so that a deposit reverts outright when the computed shares would be zero, rather than relying solely on the caller-supplied `min-out` slippage parameter to catch this degenerate state.

### Proof of Concept
1. A market experiences enough bad debt on a given vault that the DAO/market authorizes `socialize-debt` calls summing to a `scaled-amount` that drives `assets` and `total-borrowed` for the vault down to `u0`, while `zft` total supply (existing depositors' shares) remains greater than zero.
2. `total-assets()`/`total-assets-preview()` now return `u0` (per `total-assets-preview` at [5](#0-4) ), while `total-supply-preview()` remains `> u0`.
3. A new (or existing) depositor calls `deposit(amount, min-out: u0, recipient)`.
4. `convert-to-shares-preview(amount)` evaluates `ts != u0` and `ta == u0`, returning `inkind = u0`.
5. `asserts! (>= inkind min-out) ERR-SLIPPAGE)` passes trivially since `u0 >= u0`.
6. `receive-underlying amount account` executes, transferring the full `amount` of underlying tokens from the depositor into the vault.
7. `ft-mint? zft inkind recipient` mints `u0` shares to the depositor.
8. The depositor has lost `amount` of underlying tokens with no corresponding zft claim to redeem them back.

(define-public (socialize-debt (scaled-amount uint))
  (let ((scaled-principal (var-get principal-scaled))
        (borrowed (var-get total-borrowed))
        (idx (var-get index))
        (current-assets (var-get assets))
        (current-lindex (var-get lindex))
        (old-total-assets (total-assets))
        (debt-reduction (mul-div-down scaled-amount idx INDEX-PRECISION))
        (principal-reduction (if (> scaled-principal u0)
                                (mul-div-down scaled-amount borrowed scaled-principal)
                                u0))
        ;; Write down lindex proportionally to loss in total-assets
        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
                       (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
                       u0)))

    (try! (check-caller-auth))
    (asserts! (> scaled-amount u0) ERR-AMOUNT-ZERO)

    (var-set lindex new-lindex)
    (var-set principal-scaled (if (> scaled-principal scaled-amount) (- scaled-principal scaled-amount) u0))
    (var-set total-borrowed (if (> borrowed principal-reduction) (- borrowed principal-reduction) u0))
    (var-set assets (if (> current-assets principal-reduction) (- current-assets principal-reduction) u0))

    (print {
      action: "socialize-debt",
      caller: contract-caller,
      data: {
        scaled-amount: scaled-amount,
        debt-reduction: debt-reduction,
        principal-reduction: principal-reduction,
        old-lindex: current-lindex,
        new-lindex: new-lindex,
        old-total-assets: old-total-assets,
        principal-scaled: (if (> scaled-principal scaled-amount) (- scaled-principal scaled-amount) u0),
        total-borrowed: (if (> borrowed principal-reduction) (- borrowed principal-reduction) u0),
        index: idx
      }
    })

    (ok true)))
