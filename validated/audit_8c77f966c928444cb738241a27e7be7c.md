### Title
Attacker can fill a victim's per-account token list to `MAX_TOKENS_PER_USER` with dust `DepositToken` transfers, DoSing deposits, new borrows, and inbound transfers - (File: contracts/Pool.sol)

### Summary
CVE-2018-11084 is a "crafted state prevents removal/creation → denial of service" class bug: a user creates artifacts whose attributes block the platform from deleting/allocating environments. The Metronome analog is the per-account token registry (`depositTokensOfAccount` / `debtTokensOfAccount`) in `Pool`, capped at `MAX_TOKENS_PER_USER = 30`. An unprivileged attacker can send 1-wei `DepositToken.transfer()` calls to a victim; each first-time transfer permanently appends an entry to the victim's set via `DepositToken._transfer → pool.addToDepositTokensOfAccount`. Once the combined set length reaches 30, `onlyIfAdditionWillNotReachMaxTokens` reverts every subsequent addition - `Pool.deposit` for a new collateral, `DebtToken.issue`/`mint` for a new debt position, `DepositToken.seize`, and even ordinary inbound `transfer`/`transferFrom` - with `UserReachedMaxTokens`. ### Finding Description
- `Pool` tracks each account's held tokens in `MappedEnumerableSet.AddressSet` structures (`depositTokensOfAccount`, `debtTokensOfAccount`) and enforces `MAX_TOKENS_PER_USER = 30` through the `onlyIfAdditionWillNotReachMaxTokens(account_)` modifier on `addToDepositTokensOfAccount` / `addToDebtTokensOfAccount`. [2](#0-1) 
- `DepositToken._transfer` is public-facing via `transfer`/`transferFrom` and unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance was zero and `amount_ > 0`. There is no opt-in, no minimum amount, and no way for the recipient to refuse the entry. A 1-wei transfer therefore consumes one of the victim's 30 slots. [5](#0-4) 
- `DepositToken._mint` (used by `deposit`/`seize`) applies the same add path for `account_`/`to_`, so every *new* collateral deposit or new debt token the victim tries to open also goes through the cap check and reverts once the list is full. [6](#0-5) 
- Debt tokens are non-transferable (`TransferNotSupported`), so the attacker can only inflate the `depositTokensOfAccount` side; the cap counts `debtTokensOfAccount.length + depositTokensOfAccount.length` together. [7](#0-6) 
- The victim can only remove entries by spending gas to transfer each dust balance out (`removeFromDepositTokensOfAccount` fires when balance hits zero), which is the same transaction class the attacker can re-front-run with new dust.

### Impact Explanation
Temporary denial of service / freezing of the victim's position-management functions: while the list is at cap, the victim cannot deposit any collateral type they don't already hold, cannot mint/issue any synthetic they don't already owe, cannot receive `DepositToken` transfers (including `seize` proceeds sent to an address they control or liquidator-chosen recipients that are also at cap), and SmartFarmingManager leverage flows that mint new token types to their account revert. Existing deposits of already-held tokens can still be added to (balance > 0 → no add call) and withdrawals still work, so this is a liveness break on new allocations - directly mirroring the CVE's "denial of service for new app instances/scaling".

### Likelihood Explanation
- Fully unprivileged: only requires the attacker to hold dust amounts of registered `DepositToken`s (cheap - deposits are open to anyone) and call `transfer`.
- Constraint: the attack can only fill slots equal to the number of distinct registered deposit tokens (plus what the victim already holds). On pools with few listed collaterals the attacker may only be able to add a handful of entries, so the attack is most effective against accounts that already hold several deposit/debt tokens. Because the cap is shared across deposit + debt tokens, a victim with ~20 positions can be permanently pushed to the cap with a few dust transfers.
- Recovery requires the victim to transfer out each dusted token (and repay debt tokens), costing gas and being re-griefable; the block is temporary, not permanent, which bounds severity to Medium.

### Recommendation
- Don't register tokens for zero/insignificant balances: require a minimum amount (e.g. `amount_` above a dust threshold or USD floor) before calling `addToDepositTokensOfAccount`.
- Alternatively, gate `addToDepositTokensOfAccount` additions on `transfer`/`transferFrom` behind an opt-in flag, or exempt inbound transfers from the cap (only enforce the cap on `deposit`/`issue`), since forced dust was never consented to.
- Allow permissionless cleanup: a `removeIfDust(account, token)` path or automatically skipping the cap check when the recipient had no ability to refuse.

### Proof of Concept
Hardhat-style fork sketch (run against the repo's existing `test/Pool.test.ts` fixture setup):

```ts
// victim already holds (30 - N) deposit/debt token entries
// attacker deposits dust of N distinct collaterals, then:
for (const dt of attackerDepositTokens) {
  await dt.connect(attacker).transfer(victim.address, 1); // each adds entry via addToDepositTokensOfAccount
}
// victim's depositTokensOfAccount + debtTokensOfAccount length == 30

// 1) victim cannot deposit a collateral they don't yet hold
await expect(
  pool.connect(victim).deposit(newCollateral.address, amount)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// 2) victim cannot issue a synthetic they don't yet owe
await expect(
  debtToken.connect(victim).issue(amount, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// 3) even a plain inbound transfer to victim reverts
await expect(
  someDepositToken.connect(attacker).transfer(victim.address, 1)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

The revert chain: `DepositToken._transfer`/`_mint` → `pool.addToDepositTokensOfAccount(recipient)` → `onlyIfAdditionWillNotReachMaxTokens` → `length >= 30` → `UserReachedMaxTokens`. No privileged role, oracle manipulation, or governance action is required.

Caveat: feasibility in a concrete deployment depends on the number of listed deposit tokens per pool versus the victim's existing list length; where the attacker can add fewer entries than needed to reach 30, the attack degrades to increasing the victim's gas/recovery cost rather than a hard block.
