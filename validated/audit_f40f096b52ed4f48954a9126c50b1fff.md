### Title
Permissionless `lending_pool_emissions_deposit` enables first-depositor share-price inflation (donation) attack on a bank - (File: `programs/marginfi/src/instructions/marginfi_group/configure_bank.rs`)

### Summary
The reported CLMM bug lets an attacker artificially inflate the price of a single "bin's" shares via flash-loan-funded donations, monopolizing that bin and blocking/harming later liquidity providers. Marginfi has a structurally analogous primitive: each `Bank` tracks a single global `asset_share_value` [1](#0-0) , and the permissionless instruction `lending_pool_emissions_deposit` lets *any* signer directly inflate that value by transferring tokens straight into the liquidity vault, independent of `total_asset_shares` [2](#0-1) . This is the same "donate to spike the share price" mechanic used in the CLMM bin-manipulation report, applied to marginfi's global share accounting instead of a per-bin price.

### Finding Description
`lending_pool_emissions_deposit` is documented as permissionless ("Permissionlessly deposit same-mint emissions directly into the bank liquidity vault, increasing depositor value through asset share value") [3](#0-2) . It only requires `total_asset_shares > 0` [4](#0-3) , then directly recomputes:

```
bank.asset_share_value = (total_assets + amount) / total_asset_shares
``` [5](#0-4) 

If an attacker is the sole (or dominant) holder of `total_asset_shares` for a bank (trivially achievable on a freshly created bank by being the first depositor), they can call this instruction with an arbitrarily large `amount` to drive `asset_share_value` to an extreme value while `total_asset_shares` stays unchanged. Because `get_asset_shares` computes `value / asset_share_value` when crediting new depositors [6](#0-5) , any subsequent depositor whose deposit value is small relative to the inflated `asset_share_value` receives a disproportionately tiny (and, at extreme enough inflation, a fixed-point-rounded-to-zero) amount of `asset_shares`, while their tokens are pulled into the vault and become part of the pool now dominated by the attacker's shares — the direct analog of the CLMM bin's inflated share price making it "financially impractical" for others to add liquidity and giving the attacker a liquidity-provider monopoly in that bin/bank.

### Impact Explanation
- New depositors into the targeted bank can be economically blocked (their deposit is diluted at a manipulated exchange rate) or, in the extreme, lose value to fixed-point rounding, while the attacker who controls the share pool captures the benefit on withdrawal.
- Because the deposit-vault transfer happens for real tokens (not merely bookkeeping), an attacker can use borrowed/flash-loaned liquidity of the same mint (e.g., borrowed from a different bank) to fund the inflation and later reclaim it by redeeming their shares, similar to the PoC flow in the report (add minimal liquidity, inflate price via a large payment, then reap/burn the position).
- This directly targets the core accounting invariant (`asset_share_value` used everywhere: interest accrual, socialize_loss, withdraw calculations) [7](#0-6) , making it an unauthorized state change to core accounting with potential fund-loss consequences for victims and a monopolization/DoS effect on the bank, matching the "permanent lock/freeze" and "unauthorized state change" impact classes.

### Likelihood Explanation
Medium. The instruction is explicitly permissionless and only gated by `total_asset_shares > 0`, which the attacker fully controls by creating/being first depositor into a bank [8](#0-7) . The attack requires the attacker to control (or be a large fraction of) `total_asset_shares` and to have or borrow enough of the underlying token to move `asset_share_value` meaningfully — this is capital-intensive but not permission-restricted, and flash loans of the same mint from other banks are a supported primitive in this codebase [9](#0-8) . I was not able to fully verify, within the available tool budget, whether marginfi enforces a minimum-deposit/anti-dust check elsewhere in `lending_account_deposit` that would prevent the exact "shares round to zero" outcome; this should be confirmed by directly reviewing `programs/marginfi/src/instructions/marginfi_account/deposit.rs` and `BankAccountWrapper`'s deposit path before treating the zero-share rounding scenario as proven, though the price-manipulation/dilution effect itself is proven directly from the code cited above.

### Recommendation
- Restrict `lending_pool_emissions_deposit` (or add a rate-limit / maximum-per-call cap relative to `total_assets`) so a single permissionless call cannot move `asset_share_value` by an arbitrary multiple in one transaction.
- Require a minimum number of outstanding `total_asset_shares` (or a minimum bank TVL) before permitting emissions deposits, so the instruction can't be used to inflate a near-empty/first-depositor bank.
- Enforce a minimum-shares-minted check on deposit (reject deposits that would mint zero or dust shares) to eliminate the dilution/loss vector for the victim side of this attack, mirroring the "safeguards against artificial inflation" remediation from the original report.

### Proof of Concept
1. Attacker creates or is first depositor into `Bank` B (mint X), depositing `1` unit → `total_asset_shares = 1`, `asset_share_value = 1` [10](#0-9) .
2. Attacker flash-loans a large amount `M` of mint X (e.g., from another bank of the same mint, per `lending_account_start_flashloan` / `lending_account_borrow`) [9](#0-8) .
3. Attacker calls `lending_pool_emissions_deposit(bank=B, amount=M)`, which is permissionless, transferring `M` into B's liquidity vault and setting `asset_share_value = (1 + M) / 1 = 1 + M` [11](#0-10) .
4. Any victim depositing a normal-sized amount `V` (where `V << M`) into B now receives `V / (1+M)` asset_shares — negligible or (if below I80F48's precision floor) zero — via `get_asset_shares` [6](#0-5) , while their tokens land in the vault that is now overwhelmingly owned (in share terms) by the attacker.
5. Attacker withdraws their 1 share (now worth `1 + M + V`-ish minus rounding) and repays the flash loan, retaining the diluted victim value as profit, mirroring the original report's "burn the last share and profit" step.

/// Permissionlessly deposit same-mint emissions directly into the bank liquidity vault,
/// increasing depositor value through asset share value.
pub fn lending_pool_emissions_deposit(
    ctx: Context<LendingPoolEmissionsDeposit>,
    amount: u64,
) -> MarginfiResult {
    if amount == 0 {
        return Ok(());
    }

    let clock = Clock::get()?;
    let mut bank = ctx.accounts.bank.load_mut()?;
    let group = ctx.accounts.group.load()?;

    utils::validate_bank_state(&bank, utils::InstructionKind::FailsIfPausedOrReduceState)?;

    // Reject mints with non-zero transfer fees or active transfer hooks.
    let mint_ai = ctx.accounts.mint.to_account_info();
    check!(
        !utils::nonzero_fee(mint_ai.clone(), clock.epoch)?,
        MarginfiError::InvalidTransfer
    );
    check!(
        !utils::has_transfer_hook(mint_ai)?,
        MarginfiError::InvalidTransfer
    );

    let total_asset_shares = I80F48::from(bank.total_asset_shares);
    check!(
        total_asset_shares > I80F48::ZERO,
        MarginfiError::EmissionsUpdateError
    );

    bank.accrue_interest(
        clock.unix_timestamp,
        &group,
        #[cfg(not(feature = "client"))]
        ctx.accounts.bank.key(),
    )?;

    transfer_checked(
        CpiContext::new(
            ctx.accounts.token_program.key(),
            TransferChecked {
                from: ctx.accounts.emissions_funding_account.to_account_info(),
                to: ctx.accounts.liquidity_vault.to_account_info(),
                authority: ctx.accounts.depositor.to_account_info(),
                mint: ctx.accounts.mint.to_account_info(),
            },
        ),
        amount,
        ctx.accounts.mint.decimals,
    )?;

    let total_assets = bank.get_asset_amount(total_asset_shares)?;
    let updated_total_assets = total_assets
        .checked_add(I80F48::from_num(amount))
        .ok_or_else(math_error!())?;

    bank.asset_share_value = updated_total_assets
        .checked_div(total_asset_shares)
        .ok_or_else(math_error!())?
        .into();
```
