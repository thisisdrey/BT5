### Title
Stale `PromiseYieldReceipt`/`PromiseYieldTimeout` state survives `DeleteAccount` and is delivered against a re-created account, bypassing `check_actor_permissions` - ([File: core/store/src/utils/mod.rs])

### Summary
`remove_account` (called by `action_delete_account`) purges `Account`, `ContractCode`, `AccessKey`/`GasKeyNonce`, and `ContractData` entries for a deleted account, but never removes any `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`/`DataIdToYieldId`, or the global `PromiseYieldTimeout` queue entry that reference that account id. If the account id is later re-created (e.g. as a subaccount by its parent), the orphaned yield receipt — including whatever privileged actions were originally queued on it (`AddKey`, `DeleteKey`, `Stake`, etc.) — is still resolvable by timeout or resume and executes against the new account, because `check_actor_permissions` only compares the receipt's embedded `predecessor_id`/`actor_id` string to the current `account_id` string, not to any notion of account identity/generation.

### Finding Description
`remove_account` in `core/store/src/utils/mod.rs:505-575` explicitly enumerates and removes `Account`, `ContractCode`, access keys/gas-key nonces, and contract data for the account being deleted [1](#0-0) , but it never touches `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, `TrieKey::YieldIdToDataId`, `TrieKey::DataIdToYieldId`, or `TrieKey::PromiseYieldTimeout`. `action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) calls only this function before clearing the `Account` and it is the sole account-cleanup routine for `DeleteAccount` [2](#0-1) .

When account `A` calls `promise_yield_create` targeting itself (`predecessor_id == receiver_id == A`) with an attacker-chosen action list (e.g. `AddKey`) attached to the yield callback, the runtime stores the whole `ActionReceipt` under `TrieKey::PromiseYieldReceipt{receiver_id: A, data_id}` as soon as the `PromiseYield` receipt is processed, well before resolution: [3](#0-2) . Because self-targeted yields pass `check_actor_permissions` trivially (`actor_id == account_id` by construction), no authorization is re-checked at creation time for the deferred actions — authorization is deferred entirely to execution time.

If `A` subsequently sends `DeleteAccount(beneficiary=A)`, the `Account`/keys are wiped but the `PromiseYieldReceipt`, its `PromiseYieldStatus`, and its entry in the global `PromiseYieldTimeout` queue survive untouched. Because `TrieKey::PromiseYieldReceipt`/`PromiseYieldTimeout` key by the raw account-id string, if account id `A` is later re-created (an ordinary, unprivileged `CreateAccount` action — e.g. by the parent account of a subaccount `A`, which only checks `get_account` for `AccountAlreadyExists` and finds `None` since the `Account` row was removed), the orphaned queue entry now silently applies to the *new* occupant of that account id.

At resolution time — either an explicit resume or `resolve_promise_yield_timeouts` (`runtime/runtime/src/lib.rs:3009-3116`) — the code only checks `state_update.contains_key(&promise_yield_key)` [4](#0-3)  and, if present, synthesizes/forwards a `PromiseResume` and ultimately calls `apply_action_receipt` on the stored yield receipt [5](#0-4) . The actions in that stored receipt (e.g. `AddKey`) are checked via `check_actor_permissions(action, account, actor_id, account_id)` (`runtime/runtime/src/actions.rs:739-785`) which requires only `actor_id == account_id` — both are the same string ("A") regardless of which real owner now controls that account id [6](#0-5) . There is no check that the account occupying `A` today is the same logical account that existed when the yield was created (no generation counter, no re-validation against `A`'s current key set). This lets the attacker's originally-queued privileged action (e.g. `AddKey`) execute against the new account.

### Impact Explanation
This is an authorization-escalation / account-hijack primitive: an attacker can plant a time-delayed privileged action (`AddKey` with an attacker-controlled public key, `DeleteKey`, `Stake`, etc.) that survives account deletion and fires against whatever account subsequently occupies that account id, bypassing the intended `predecessor_id == receiver_id` self-authorization invariant. In deployments where account ids are re-provisioned to new tenants/users after deletion (a common multi-tenant/subaccount pattern), this allows the attacker to add a full-access key to, or otherwise take control of, a completely unrelated party's account — matching NEAR's "authorization escalation across accounts" bounty category.

### Likelihood Explanation
The preconditions are fully within an unprivileged attacker's control: create a subaccount they own, call `promise_yield_create` on themselves with an attached `AddKey` action, then send `DeleteAccount` for that subaccount. The only external dependency is that the same account id gets re-created later (which requires either the attacker's own parent account to re-provision the name, or a victim/service that reuses deleted subaccount names — a realistic pattern for escrow/session-style subaccount factories). The bug is deterministically reproducible and does not depend on validator/node privilege, timing races beyond the normal yield-timeout window, or any signature/nonce bypass — it is a pure state-cleanup omission in `remove_account`.

### Recommendation
`remove_account` (and/or `action_delete_account`) should also remove any `PromiseYieldReceipt`/`PromiseYieldStatus`/`YieldIdToDataId`/`DataIdToYieldId` entries and dequeue/invalidate the corresponding `PromiseYieldTimeout` entries for the account being deleted, so no privileged action list outlives the account that authorized it. Alternatively/additionally, `check_actor_permissions` (or the resume/timeout resolution path) should bind the stored yield receipt to some identity/generation of the account fixed at creation time (e.g. verify the account existed continuously, or tag yields with a creation nonce/height compared against the account's own creation) so a re-created account cannot inherit a predecessor's queued actions.

### Proof of Concept
Runtime integration test outline (in `runtime/runtime/src/tests/apply.rs` style, similar to `test_function_call_after_same_chunk_delete_recreate_resolves_fresh_code`):
1. Set up parent account `parent.near` and subaccount `sub.parent.near`.
2. Have `sub.parent.near` call a contract method that invokes `promise_yield_create` targeting itself and, on the yielded promise, batches `Action::AddKey(attacker_public_key)`.
3. Assert `TrieKey::PromiseYieldReceipt{receiver_id: sub.parent.near, data_id}` and a `PromiseYieldTimeout` entry exist in state.
4. Send a receipt with `Action::DeleteAccount(beneficiary=parent.near)` from `sub.parent.near`; commit.
5. Assert `get_account(sub.parent.near)` is `None`, but the `PromiseYieldReceipt`/`PromiseYieldTimeout` trie entries for `sub.parent.near` still exist (this demonstrates the `remove_account` gap).
6. From `parent.near`, send `Action::CreateAccount` + `Action::AddKey(victim_public_key)` targeting `sub.parent.near`, simulating re-provisioning to a new owner; commit.
7. Advance block height past `yield_timeout_length_in_blocks` and run `resolve_promise_yield_timeouts` (or explicitly invoke resume with the leaked `data_id`).
8. Assert that `attacker_public_key` is now a full-access key on `sub.parent.near`, alongside `victim_public_key` — demonstrating the attacker gained unauthorized key access on the re-created account despite `check_actor_permissions` passing.
