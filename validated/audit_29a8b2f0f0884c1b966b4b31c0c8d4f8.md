### Title
Active-permission holders can be granted the right to fully overwrite an account's Owner/Witness/Active permission set, enabling permanent lockout of the original Owner - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
The Mahara CVE (CVE-2017-1000134) allowed a group member to unilaterally change access permissions in a way that caused another member to permanently lose access to resources they created. The analogous class of bug — a *lower-trust key being able to rewrite the entire permission structure and strip access from the higher-trust key* — exists in java-tron's account multisig permission system, because `AccountPermissionUpdateContract` can be assigned as an allowed operation of an `Active` permission, and the actuator's execution path performs an unrestricted full overwrite of the account's Owner/Witness/Active permission set with no validation that the resulting configuration still preserves any particular key's access.

### Finding Description
`AccountPermissionUpdateActuator.execute()` unconditionally replaces the account's entire permission set via `account.updatePermissions(...)` with whatever `Owner`, `Witness`, and `Actives` permissions are supplied in the transaction: [1](#0-0) 

`validate()` only checks structural correctness of each `Permission` (key count, threshold, distinct addresses, valid operation bits) — it never checks that the transaction's signer (i.e., the permission actually used to authorize the call) is being preserved in the new permission configuration, nor does it require Owner-level authority to modify Owner permission: [2](#0-1) 

Authorization to invoke `AccountPermissionUpdateContract` is controlled purely by whether the `Active` permission used to sign has the corresponding bit set in its `operations` bitmap, checked generically for any contract type via `checkPermissionOperations`: [3](#0-2) [4](#0-3) 

Critically, `AccountPermissionUpdateContract` IS present in `getAvailableContractType()` (the set of operations that CAN be granted to an `Active` permission), and is only excluded from the *default* active operations bitmap generated at account creation — confirmed by the actuator's own test cases showing the "AvailableContractType" bitmap includes it while "ActiveDefaultOperations" excludes it: [5](#0-4) 

This means an account owner can (intentionally or via a poorly-understood wallet configuration) grant a low-threshold `Active` permission (e.g., a single key with weight 1) the ability to call `AccountPermissionUpdateContract`. Because the actuator performs a full, unchecked overwrite of Owner/Witness/Active permissions on execution, that single low-trust `Active` key can then submit one transaction that replaces the `Owner` permission entirely — removing the original Owner's key(s) — and rewrites all `Active` permissions, permanently locking out the legitimate account controller. There is no requirement that the new Owner permission include the previous Owner's key, no requirement that the operation be co-signed by the current Owner permission, and no minimum-threshold/weight relationship enforced between the granting Active permission and the resulting Owner permission it is allowed to replace.

This mirrors the Mahara bug-class exactly: a member with a narrower/lower level of trust (analogous to a "group member") is able to perform a permission-altering operation that permanently and unilaterally revokes the access of another party (the true account Owner), with no safeguard requiring the affected party's consent or a higher-trust signature to prevent it.

### Impact Explanation
Successful exploitation is unauthorized/permanent account takeover or lockout: the original account Owner permanently loses all administrative control of the account (cannot ever author a new `AccountPermissionUpdateContract` from Owner authority again since that Owner permission itself was replaced), and TRX/asset custody tied to that account's Owner permission becomes effectively frozen or transferable only by the attacker's new permission set. This satisfies "permanent freezing of funds" / "unauthorized account operation" impact criteria.

### Likelihood Explanation
Exploitation requires the account Owner to have granted an `Active` permission the `AccountPermissionUpdateContract` operation bit at some point (this is not the default, but it is a supported and reachable configuration via the same actuator, and is exposed through normal wallet/API usage, e.g. `UpdateAssetServlet`/`Wallet` APIs `createTransactionCapsule` + `AccountPermissionUpdateContract`). Once granted, the holder of that `Active` key — which can be a completely different, lower-trust individual (analogous to a "group member") — can unilaterally and irreversibly rewrite the whole permission structure with a single signed transaction, without requiring any interaction from the Owner. No additional privileged access is needed beyond possessing that one Active key.

### Recommendation
In `AccountPermissionUpdateActuator.validate()`/`execute()`, restrict which contract types may legitimately be included in the `AccountPermissionUpdateContract` operation bitmap for `Active` permissions (i.e., disallow granting `Active` permissions the ability to invoke `AccountPermissionUpdateContract` itself), or alternatively require that any permission update signed via a non-Owner (`permissionId != 0`) `Active` permission cannot modify the `Owner` permission's key set, only the `Active` permission set that the signer itself belongs to. At minimum, document/enforce that the resulting Owner permission after an update signed by a non-zero permission ID must still satisfy the previous Owner permission's threshold (i.e., require Owner-level co-signature to change Owner permission), preventing a low-trust Active key from unilaterally displacing the account's Owner authority.

### Proof of Concept
1. Account Owner creates an `Active` permission `P_active` with `threshold=1`, one key `K_attacker` with `weight=1`, and sets the `operations` bitmap bit for `AccountPermissionUpdateContract` (this is permitted since `AccountPermissionUpdateContract` is part of `getAvailableContractType()`), via a legitimate `AccountPermissionUpdateActuator` transaction signed by the current Owner.
2. `K_attacker` (holder of `P_active`) constructs a new `AccountPermissionUpdateContract` with `permissionId` set to `P_active`'s id, specifying:
   - a new `Owner` permission containing only `K_attacker`'s key,
   - a new `Actives` list containing only permissions controlled by `K_attacker`.
3. `K_attacker` signs the transaction with just their own key (satisfying `P_active`'s threshold of 1) and broadcasts it via `Wallet.broadcastTransaction`.
4. `TransactionCapsule.validateSignature`/`checkPermission` accepts the transaction because `permissionId != 0`, permission type is `Active`, and `checkPermissionOperations` confirms the `AccountPermissionUpdateContract` bit is set — no Owner-level signature is required.
5. `AccountPermissionUpdateActuator.execute()` overwrites the account's Owner/Active permissions per step 2, permanently removing the original Owner's access.

  @Override
  public boolean validate() throws ContractValidateException {

    if (chainBaseManager == null) {
      throw new ContractValidateException(ActuatorConstant.STORE_NOT_EXIST);
    }

    if (this.any == null) {
      throw new ContractValidateException(ActuatorConstant.CONTRACT_NOT_EXIST);
    }

    AccountStore accountStore = chainBaseManager.getAccountStore();
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();

    if (dynamicStore.getAllowMultiSign() != 1) {
      throw new ContractValidateException("multi sign is not allowed, "
          + "need to be opened by the committee");
    }
    if (!this.any.is(AccountPermissionUpdateContract.class)) {
      throw new ContractValidateException(
          "contract type error,expected type [AccountPermissionUpdateContract],real type["
              + any.getClass() + "]");
    }
    final AccountPermissionUpdateContract accountPermissionUpdateContract;
    try {
      accountPermissionUpdateContract = any.unpack(AccountPermissionUpdateContract.class);
    } catch (InvalidProtocolBufferException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractValidateException(e.getMessage());
    }
    byte[] ownerAddress = accountPermissionUpdateContract.getOwnerAddress().toByteArray();
    if (!DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("invalidate ownerAddress");
    }
    AccountCapsule accountCapsule = accountStore.get(ownerAddress);
    if (accountCapsule == null) {
      throw new ContractValidateException("ownerAddress account does not exist");
    }

    if (!accountPermissionUpdateContract.hasOwner()) {
      throw new ContractValidateException("owner permission is missed");
    }

    if (accountCapsule.getIsWitness()) {
      if (!accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("witness permission is missed");
      }
    } else {
      if (accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("account isn't witness can't set witness permission");
      }
    }

    if (accountPermissionUpdateContract.getActivesCount() == 0) {
      throw new ContractValidateException("active permission is missed");
    }
    if (accountPermissionUpdateContract.getActivesCount() > 8) {
      throw new ContractValidateException("active permission is too many");
    }

    Permission owner = accountPermissionUpdateContract.getOwner();
    Permission witness = accountPermissionUpdateContract.getWitness();
    List<Permission> actives = accountPermissionUpdateContract.getActivesList();

    if (owner.getType() != PermissionType.Owner) {
      throw new ContractValidateException("owner permission type is error");
    }
    checkPermission(owner);
    if (accountCapsule.getIsWitness()) {
      if (witness.getType() != PermissionType.Witness) {
        throw new ContractValidateException("witness permission type is error");
      }
      checkPermission(witness);
    }
    for (Permission permission : actives) {
      if (permission.getType() != PermissionType.Active) {
        throw new ContractValidateException("active permission type is error");
      }
      checkPermission(permission);
    }
    return true;

  public static boolean checkPermissionOperations(Permission permission, Contract contract)
      throws PermissionException {
    ByteString operations = permission.getOperations();
    if (operations.size() != 32) {
      throw new PermissionException(String.format("operations size must 32, actual: %d",
          operations.size()));
    }
    int contractType = contract.getTypeValue();
    boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
    return b;
  }
