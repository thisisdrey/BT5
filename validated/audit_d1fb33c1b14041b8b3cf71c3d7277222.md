### Title
Unbounded array allocation from attacker-controlled length field in precompiled contract calldata decoding causes memory-exhaustion DoS - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
`PrecompiledContracts.extractBytesArray`, `extractBytes32Array`, and `extractSigArray` allocate arrays sized directly by a length word taken from attacker-supplied ABI-encoded calldata, without validating that the declared length is consistent with the actual size of the input buffer. This is the same bug class as CVE-2017-5835 (libplist): a size/offset value parsed from untrusted input is used to drive a memory allocation before it is validated against the real amount of available data, allowing a crafted, small input to trigger an oversized allocation attempt.

### Finding Description
`ValidateMultiSign.execute` and `BatchValidateSign.doExecute` parse calldata into 32-byte words with `DataWord.parseArray(data)` and then call helper decoders: [1](#0-0) [2](#0-1) 

`extractBytesArray` only checks `offset > words.length - 1`; it never checks that `len` (`words[offset].intValueSafe()`) is bounded by the amount of data actually supplied before doing `new byte[len][]`. `extractBytes32Array` performs no bounds check at all on `offset` or `len` before allocating `new byte[len][]`.

In `ValidateMultiSign.execute`, when `VMConfig.allowTvmSelfdestructRestriction()` is disabled, `extractBytesArray` is invoked directly with no prior sanity check on `len` relative to `MAX_SIZE`: [3](#0-2) 

Critically, the array-extraction call happens *before* the `try { ... } catch (Throwable t) { ... }` block later in the method (which only wraps the signature-recovery loop), so an `OutOfMemoryError` thrown while allocating `new byte[len][]` is not contained inside `ValidateMultiSign.execute` itself.

The energy charged for the call is computed only from `data.length`, not from the attacker-controlled length field embedded in the ABI encoding: [4](#0-3) 

This means a caller can submit a small `data` buffer (cheap in energy) that encodes a huge length word (e.g., close to `Integer.MAX_VALUE`) at the position read by `words[3].intValueSafe()`, driving `extractBytesArray`/`extractBytes32Array` to attempt to allocate an extremely large `byte[][]` — mirroring libplist's "offset size of zero"/unchecked-size class of bug where a size field from the input stream is trusted to allocate memory before validating it against the real payload size.

This precompile is reached whenever the TVM executes a `CALL`/`STATICCALL`/`DELEGATECALL` to the `ValidateMultiSign`/`BatchValidateSign` precompile addresses via `Program.callToPrecompiledAddress`: [5](#0-4) 

Propagation path if an `Error` (e.g. `OutOfMemoryError`) escapes: `VM.play` only special-cases `RuntimeException` and `StackOverflowError`, so a plain `OutOfMemoryError` is not caught there: [6](#0-5) 

It is only caught much higher up in `VMActuator.execute`'s generic `catch (Throwable e)`: [7](#0-6) 

Even though this outer `catch (Throwable e)` ultimately prevents the transaction thread itself from dying, the JVM has already attempted the oversized allocation by the time the `OutOfMemoryError` is thrown, which can trigger GC storms / heap pressure across the whole node process shared by all concurrently executing transactions and services (this matches the CVE's "large memory allocation and crash" description, though whether it escalates to a full process crash depends on heap sizing and JVM flags, which I could not fully determine — `start.sh`/`java-tron.vmoptions` do reference `OnOutOfMemoryError`, suggesting a configured action on OOM, but I was not able to read the exact handler content to confirm whether it kills the process).

### Impact Explanation
If triggerable with cheap energy cost, an unprivileged transaction broadcaster/contract deployer can repeatedly call `TriggerSmartContract` invoking a contract that `CALL`s the `ValidateMultiSign`/`BatchValidateSign` precompile with crafted calldata, forcing the node to repeatedly attempt huge array allocations. This is a resource-exhaustion / denial-of-service vector against block-producing and API-serving nodes, potentially degrading or halting normal transaction processing across the node, which aligns with "node crash or halt" in the accepted impact list.

### Likelihood Explanation
The precompile addresses for `validatemultisign`/`batchvalidatesign` are reachable from any deployed contract via ordinary `CALL` opcodes, and the vulnerable code path (`extractBytesArray`, unguarded when `allowTvmSelfdestructRestriction` is not active, and `extractBytes32Array`, which has no size guard regardless of that flag) requires only crafting the ABI-encoded length word — no special privileges, keys, or SR/witness status are needed. The likelihood is High assuming the guard flag (`VMConfig.allowTvmSelfdestructRestriction`) is not universally active for all execution paths that reach these helpers (I was unable to fully confirm the current hard-fork activation status of this flag in this codebase from the available context; that should be verified before treating this as fully exploitable in production).

### Recommendation
- Before allocating in `extractBytesArray`, `extractBytes32Array`, and `extractSigArray`, validate that the decoded `len` (and the derived per-item offsets) is consistent with `words.length`/`data.length` (i.e., that enough data actually exists to satisfy the declared length) and is bounded by a small constant (e.g., `MAX_SIZE`) unconditionally, not only when `allowTvmSelfdestructRestriction()` is enabled.
- Move the `MAX_SIZE` bound checks so they always execute prior to any `new byte[len][]` allocation, independent of feature-flag state.
- Ensure `ValidateMultiSign.execute` wraps the array-extraction calls in the same `try`/`catch` used for the rest of the method so that any residual failure is handled gracefully rather than propagating an `Error` out of the precompile.
- Tie `getEnergyForData` to the actual claimed array sizes (or cap them) so an attacker cannot decouple a cheap energy charge from an expensive/large decode.

### Proof of Concept
1. Deploy a contract that performs a low-level `call` to the `ValidateMultiSign` precompile address (`0x0000...66` per TRON precompile numbering) with calldata shaped as:
   - word0: signer address (32 bytes)
   - word1: permissionId
   - word2: offset/word for `data` (irrelevant filler)
   - word3: offset pointing to the "signatures" array position
   - at that array position, set the length word to a very large value (e.g., `0x000000000000000000000000000000000000000000000000000000FFFFFFF0`) while keeping the rest of `data` short.
2. Ensure `VMConfig.allowTvmSelfdestructRestriction()` is not active for the call path being exercised (pre-activation behavior), so the `sigArraySize > MAX_SIZE` guard is skipped and `extractBytesArray(words, offset, rawData)` is invoked directly.
3. Submit the `TriggerSmartContract` transaction; `extractBytesArray` executes `byte[][] bytesArray = new byte[len][];` with `len` at or near `Integer.MAX_VALUE`, attempting a huge allocation immediately, before the encapsulating `try`/`catch` in `ValidateMultiSign.execute` is entered — producing an `OutOfMemoryError`/large-allocation event on the node executing/verifying the transaction.

    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
