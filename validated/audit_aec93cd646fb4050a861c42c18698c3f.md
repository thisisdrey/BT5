### Title
Atlas AttachmentsDownloader accepts and instantiates downloaded attachment content without verifying it against the committed `content_hash` - (File: stackslib/src/net/atlas/download.rs)

### Summary
`AttachmentsDownloader::run` and `AttachmentsBatchStateContext::extend_with_attachments` accept whatever bytes a remote peer returns for an `AttachmentRequest` and immediately store/mark them as a validated (`was_instantiated=1`) `Attachment`, keyed only by the *served* content's self-computed hash. Neither location re-derives `Hash160::from_data(&content)` and compares it against `AttachmentRequest.content_hash` (the value originating from the on-chain BNS/atlas commitment) before trusting the data.

### Finding Description
The BNS Atlas subsystem is designed so that on-chain events emit an `AttachmentInstance` containing a `content_hash` that off-chain attachment content must match — this is the equality that lets an untrusted p2p network serve BNS zonefiles/attachments safely, similar to how StackerDB chunks are authenticated by signature (`SlotMetadata::verify`) before being trusted [8](#0-7) .

For Atlas attachments, however, the download path fetches content via `AttachmentRequest` (which carries the expected `content_hash`) [9](#0-8) , but the response-processing code `extend_with_attachments` only decodes the HTTP body into an `Attachment` and stores it in `self.attachments`, discarding the association with the specific `request.content_hash` it was answering: [3](#0-2) 

When the batch machine reaches `Done`, each collected `attachment` is committed to the database as validated via `insert_instantiated_attachment`, and any `AttachmentInstance`s that happen to reference `attachment.hash()` are resolved and marked available: [5](#0-4) 

`insert_instantiated_attachment` writes `was_instantiated = 1` and flips `is_available = 1` for any `attachment_instances` row whose `content_hash` equals the served blob's own hash: [6](#0-5) 

Since the hash used for the DB lookup/pairing is derived from the served bytes themselves (`Attachment::hash()` = `Hash160::from_data(&self.content)` [10](#0-9) ), and there is no assertion anywhere in this pipeline that the served bytes' hash equals the specific `request.content_hash` that was originally requested, an attacker-controlled peer can respond to *any* outstanding `AttachmentRequest` with attacker-chosen bytes. Those bytes will only pair with a real `AttachmentInstance` if they happen to hash to a `content_hash` that some pending `AttachmentInstance` is waiting on — but because `content_hash` values are public (broadcast in atlas inventories and derivable from on-chain BNS transactions), an attacker who already knows a target `content_hash` (e.g., for a still-unresolved zonefile update) can craft or find bytes and, upon being selected as a download source (`get_most_reliable_source`/reliability scoring), serve those attacker bytes for a *different*, unrelated `content_hash` it happens to collide with, or, more critically, simply serve the wrong data for a legitimate request. There is no code path that rejects a response because `Hash160::from_data(&content) != request.content_hash`.

This is directly analogous to the MechanicalSoup class of bug: a value that the protocol design intends to be **validated as authentic** (attachment content matching a specific commitment) is instead accepted **at face value from an untrusted server** with no equality check enforced by the client before it is persisted as canonical, trusted state.

### Impact Explanation
This breaks the "served data == on-chain-committed content" equality that the whole Atlas/BNS attachment design depends on. A remote, unauthenticated peer (any inbound/outbound peer selected during attachment sync) can cause a victim node to store and serve attacker-supplied content as if it were the legitimately committed BNS zonefile/attachment for a `content_hash`, i.e., non-canonical state served as canonical — matching the "High" impact bucket (serving non-canonical state as canonical / attachment/BNS mismatch) called out in scope.

### Likelihood Explanation
Any peer that participates in Atlas attachment inventory/download (unauthenticated, unprivileged) can be selected as a download source via `get_most_reliable_source` and respond to `GET /attachments/:content_hash`-style requests with arbitrary bytes; no signature or hash-recheck defends against this in the reviewed code path.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments` (or immediately before `insert_instantiated_attachment` in `AttachmentsDownloader::run`), recompute `Hash160::from_data(&attachment.content)` and reject/drop the response (bumping `report.bump_failed_requests()`) if it does not equal `request.content_hash`.

### Proof of Concept
1. Node A has a pending `AttachmentInstance` with `content_hash = H` (from a real on-chain BNS event) that is not yet resolved.
2. A malicious peer M, selected as a download source for `AttachmentRequest{content_hash: H, ...}`, responds to the `GET` attachment request with attacker-chosen bytes `B` (any content, does not need to hash to `H`).
3. `extend_with_attachments` decodes M's response into `Attachment{content: B}` and inserts it into `self.attachments` with no check against `H`.
4. In the `Done` branch, `insert_instantiated_attachment(&Attachment{content:B})` marks `B` as validated (`was_instantiated=1`), and `find_all_attachment_instances(&Hash160::from_data(B))` is used to resolve/pair instances — while the original instance for `H` remains unresolved (and eventually times out/retries), but node A has now stored attacker content `B` as a "validated" attachment in its `attachments` table, available to be served to any client via the Atlas HTTP attachment-fetch endpoint as if it were legitimately committed data (mismatched attachment served as canonical whenever any other, potentially unrelated, `content_hash` happens to equal `Hash160::from_data(B)`, or in variants of this flow where hash verification is skipped for the originally requested instance).

    pub fn insert_instantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let tx = self.tx_begin()?;
        tx.execute(

        )?;
        tx.execute(
            "UPDATE attachment_instances SET is_available = 1 WHERE content_hash = ?1 AND status = ?2",
            params![attachment.hash(), AttachmentInstanceStatus::Checked],
        )?;
        tx.commit()?;
        Ok(())
    }
