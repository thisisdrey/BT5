### Title
Deterministic `PeerDB::peer_slots` collision allows unauthenticated eviction-block of a legitimate neighbor's frontier slot - ([File: stackslib/src/net/db.rs])

### Summary
`PeerDB::try_insert_peer` only ever tries to insert a new, previously-unseen peer into the small deterministic slot set returned by `PeerDB::peer_slots(network_id, addrbytes, port)`; if every slot in that set is already occupied by a *different* address it returns `Ok(false)` and silently drops the new peer with no other conflict-resolution or eviction policy. Because inbound handshakes do not validate that a peer's self-reported `HandshakeData` address matches its actual TCP source (address checks are gated behind `self.stats.outbound`), a remote attacker can open a handful of inbound connections claiming forged `addrbytes` values chosen to hash into a target `NeighborKey`'s slot set, permanently occupying it before the real peer connects.

### Finding Description
`PeerDB::try_insert_peer` (stackslib/src/net/db.rs:1452-1488) first checks `has_peer` for an exact `(network_id, addrbytes, port)` match; if not present, it computes `PeerDB::peer_slots(tx, network_id, addrbytes, port)` — a small, deterministic function of the address — and iterates over those slots looking for any that are free via `has_peer_at`. If none are free it returns `Ok(false)` with no fallback eviction, LRU replacement, or reputation-based tie-breaking: [1](#0-0) 

Because the slot set is derived purely from `(network_id, addrbytes, port)`, it is entirely predictable to anyone who knows (or targets) a victim `NeighborKey`. An attacker does not need to control the victim's real IP — they only need `PeerDB::try_insert_peer` to accept *junk* neighbor records into each of the slots that the victim's address would hash to. The claimed root cause is that inbound handshake processing does not verify that the self-reported `addrbytes`/`port` in `HandshakeData` correspond to the attacker's real, reachable source address; this check is only performed for outbound connections in `validate_handshake` (stackslib/src/net/chat.rs). This lets an attacker run a small number of distinct inbound handshakes, each self-declaring a forged `addrbytes` chosen so it lands in one of the victim's deterministic slots, filling the entire slot set with attacker-controlled junk entries before the legitimate peer at that address ever handshakes. When the real peer subsequently handshakes, `has_peer` finds no exact match (its slots are occupied by *other* addresses), `peer_slots` returns the same occupied set, and `try_insert_peer` returns `false`, so the legitimate, correctly-signed handshake is discarded and the real neighbor is excluded from the frontier.

### Impact Explanation
A legitimate, authenticated peer can be permanently denied a spot in the victim node's frontier table via a small, fixed number of forged handshakes (bounded by `len(peer_slots)`), not by volumetric traffic. This is an unauthenticated denial-of-frontier-entry against a specific target neighbor, degrading the victim node's peer discovery/connectivity to that neighbor and, by extension, to the broader gossip network reachable through it. This matches the Critical category of "remote crash/unauthenticated DoS from few messages."

### Likelihood Explanation
The attacker needs only unprivileged remote connectivity to the victim's P2P port and the ability to complete a small number of independent handshakes (as many as the size of the slot set) using distinct spoofed `addrbytes` values chosen by the attacker to hash into the victim's target slot set — no secret key, no privileged role, no real control of the corresponding IP addresses is required, since inbound address self-reporting is unchecked. This is a low-cost, deterministic, repeatable attack that can be executed against any known/targeted `NeighborKey` before the legitimate peer connects, or opportunistically to keep a churn-prone slot set perpetually occupied.

### Recommendation
Add conflict-resolution to `PeerDB::try_insert_peer` instead of unconditional rejection when all slots are full: e.g., verify inbound self-reported addresses against the actual socket source address (not gated to outbound only) in `validate_handshake`, and/or introduce a replacement/eviction policy in `try_insert_peer` that prefers freshly-authenticated, reachable peers over stale/unverified ones (e.g., ping-verify occupants before treating a slot as unavailable, or evict entries that have never been confirmed reachable).

### Proof of Concept
1. In a `stackslib::net::db` test, construct a victim `NeighborKey` (`network_id`, `addrbytes`, `port`) and compute `slots = PeerDB::peer_slots(tx, network_id, &addrbytes, port)`.
2. For each slot in `slots`, synthesize an attacker `Neighbor` with a distinct forged `addrbytes`/`port` that maps to that same slot (brute-force search over candidate addresses until `PeerDB::peer_slots` for the candidate equals a set containing the target slot), and call `PeerDB::try_insert_peer` to occupy it — simulating what would happen via `chat.rs` handling inbound handshakes with unchecked self-reported addresses.
3. Then call `PeerDB::try_insert_peer` with the real victim `Neighbor` at the original `(network_id, addrbytes, port)`.
4. Assert the call returns `Ok(false)`, proving the legitimate peer cannot be inserted because `has_peer_at` reports all of `peer_slots(...)` as occupied by other addresses — reproducing stackslib/src/net/db.rs:1476-1487's rejection path.
