### Title
Unvalidated self-reported address in neighbor-of-neighbor `HandshakeAccept` allows PeerDB frontier poisoning with attacker-chosen victim IP:port - (File: stackslib/src/net/neighbors/db.rs, stackslib/src/net/neighbors/walk.rs)

### Summary
`add_or_schedule_replace_neighbor` in `stackslib/src/net/neighbors/db.rs` blindly persists whatever `addrbytes`/`port` the *payload* of a `HandshakeAccept` claims via `Neighbor::load_and_update(&tx, ..., handshake)` and then `save`/`save_update`, using that self-reported address as the PeerDB primary key. When this is reached via the neighbor-of-neighbor walk (`handle_neighbor_handshake_accept` in `stackslib/src/net/neighbors/walk.rs:1092-1124`) or the pingback flow (`pingback_handshakes_try_finish`, `walk.rs:1683-1725`), there is no check that the claimed `handshake.addrbytes`/`handshake.port` equals the address (`na`/`naddr`) that was actually dialed to obtain the reply.

### Finding Description
The equality that should hold is: *the PeerDB key (address) stored for a neighbor == the address the local node actually connected to / verified as reachable for that peer's signing key*. That equality is enforced in the primary handshake path (`handle_handshake_accept`, `walk.rs:676-737`), which explicitly compares `neighbor_from_handshake.addr` against `self.cur_neighbor.addr` and rejects on mismatch (`walk.rs:705-715`), and softly self-corrects private/any-net claims to the dialed address (`walk.rs:693-703`).

That guard is **absent** in two other call sites of `add_or_schedule_replace_neighbor`:
- `handle_neighbor_handshake_accept` (`walk.rs:1092-1124`), invoked from `neighbor_handshakes_try_finish` for handshakes sent to `cur_neighbor`'s *neighbors-of-neighbors* (addresses `na` obtained from an untrusted `GetNeighbors` reply). The local node dials `na.addrbytes:na.port` [1](#0-0) , but the returned `HandshakeAccept`'s `data.handshake` (self-reported by the answering server) is passed straight into `add_or_schedule_replace_neighbor` with no comparison to `na` [2](#0-1) .
- `pingback_handshakes_try_finish` (`walk.rs:1683-1725`), which only validates the public-key hash via `check_handshake_pubkey_hash` [3](#0-2)  but never checks that `data.handshake.addrbytes/port` matches the pingback's advertised `naddr`.

Inside `add_or_schedule_replace_neighbor` (`stackslib/src/net/neighbors/db.rs:368-426`), the handshake data is turned into a `Neighbor` via `Neighbor::load_and_update(&tx, preamble.peer_version, preamble.network_id, handshake)` [4](#0-3)  and then persisted with `.save(...)` / `.save_update(...)` [5](#0-4) , keyed on `neighbor_from_handshake.addr`, which is derived from the handshake payload's `addrbytes`/`port`, not from the socket address that was actually dialed.

Root cause: `ConversationP2P::validate_handshake` (`stackslib/src/net/chat.rs:1047-1127`) verifies `message.verify_secp256k1(&handshake_data.node_public_key)` — i.e., that the *sender* holds the private key for `node_public_key` — and, for outbound connections with an already-known key, verifies `addrbytes`/`port` against the real socket only in that specific case (`chat.rs:1079-1091`). It does not, and cannot by itself, guarantee that the `addrbytes`/`port` *field inside the signed payload* corresponds to the address that was dialed in the neighbor-of-neighbor/pingback flows, because the attacker signs the entire message themselves and can put any address they want into `handshake.addrbytes`/`handshake.port`. The signature is valid over attacker-chosen data — it authenticates "attacker's key said this", not "this data describes the socket we're talking to."

Attack: attacker runs a real, reachable server (own IP) and gets it discovered as a neighbor (either directly gossiped, or as a "neighbor of a neighbor" reported by any node, including itself). When a victim node's `NeighborWalk` dials the attacker's real address and asks for a handshake, attacker replies with a validly self-signed `HandshakeAccept`/`StackerDBHandshakeAccept` whose `HandshakeData.addrbytes`/`port` claim an arbitrary third-party (victim) IP:port. This flows unchecked into `add_or_schedule_replace_neighbor` → `PeerDB::try_insert_peer`/`update_peer`, inserting/updating a PeerDB record keyed at the victim's address but bound to the attacker's public key.

### Impact Explanation
This corrupts the local node's PeerDB frontier: entries keyed by a third-party's real IP:port are populated with an attacker-controlled public key and treated as legitimate peers. Because PeerDB is gossiped onward (via `GetNeighbors`/`Neighbors` replies) and drives further outbound connection attempts (`neighbor_handshakes_begin`, `ping_existing_neighbors_begin`), this can propagate a forged address/identity record network-wide and cause repeated unsolicited connection attempts toward the victim's IP:port from many nodes in the network — an unauthenticated write to a peer's persistent state (PeerDB) driven entirely by attacker-crafted signed payload content, satisfying "network-wide propagation of forged data / unauthenticated write to state."

### Likelihood Explanation
No privileged access is required: an attacker only needs to run one reachable peer and be discoverable via normal gossip (either by directly connecting inbound so it's reported as a neighbor, or being reported by any node running `GetNeighbors`). The attacker fully controls the contents of their own `HandshakeAccept`/`StackerDBHandshakeAccept` payload, and the signature check only proves they hold the private key for the claimed `node_public_key` — it does not bind the payload's `addrbytes`/`port` to the dialed socket in the neighbor-of-neighbor or pingback code paths. This is remotely triggerable, repeatable on every walk cycle, and costs the attacker nothing beyond running one ordinary peer.

### Recommendation
In `handle_neighbor_handshake_accept` (`walk.rs:1092`) and `pingback_handshakes_try_finish` (`walk.rs:1683`), before calling `add_or_schedule_replace_neighbor`, enforce the same equality check already used in `handle_handshake_accept`: compare `data.handshake.addrbytes`/`data.handshake.port` (after the private/any-net override logic) against the address actually dialed (`na`/`naddr`), and reject/drop the reply (or force-override to the dialed address) on mismatch, exactly as `walk.rs:693-715` already does for the primary handshake path.

### Proof of Concept
Rust test in `stackslib::net::tests::neighbors` (or `net::neighbors::db` unit test):
1. Stand up two `TestPeer`s: `attacker` (with its own real bind address) and `victim_node` (the node under test performing a walk).
2. Have `victim_node` discover `attacker` as a neighbor-of-neighbor (e.g., seed a `GetNeighborsReply`/`Neighbors` payload naming `attacker`'s real address, or drive it through `neighbor_handshakes_begin`).
3. On the `attacker` side, construct a `HandshakeAcceptData` whose inner `HandshakeData.addrbytes`/`port` are set to an arbitrary third-party ("victim") IP:port unrelated to `attacker`'s real bind address, sign the message with `attacker`'s real key, and return it as the handshake reply.
4. Drive `victim_node`'s walk state machine through `neighbor_handshakes_try_finish` → `handle_neighbor_handshake_accept` → `add_or_schedule_replace_neighbor`.
5. Assert: `PeerDB::get_peer(victim_node.peerdb_conn(), network_id, &third_party_addrbytes, third_party_port)` returns `Some(peer)` whose `public_key` equals `attacker`'s public key — proving a PeerDB record was created/updated for an address `victim_node` never actually connected to, keyed under the attacker's identity.
