### Title
`ExchangeCapsule.transaction()` mutates exchange reserves as a side effect of validation, letting `validate()` alone permanently corrupt AMM pool balances - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java`)

### Summary
`ExchangeCapsule.transaction()` both computes the swap output **and** mutates `firstTokenBalance`/`secondTokenBalance` on the in-memory `ExchangeCapsule` in the same call. [1](#0-0) 
`ExchangeTransactionActuator.doValidate()` calls this mutating method purely to obtain `anotherTokenQuant` for the slippage check (`anotherTokenQuant < tokenExpected`), before `execute()` is even invoked. [2](#0-1) 
`execute()` then calls `exchangeCapsule.transaction(...)` again on the *already-mutated* capsule and persists the result. [3](#0-2) 

### Finding Description
This mirrors the report's root cause: a critical protective computation (bonding-curve pricing / balance update, analogous to Vader's IL-protection math) is embedded inside a "helper" routine (`ExchangeCapsule.transaction`) that both computes and *commits* the reserve update, and is invoked from two different code paths (`validate()` and `execute()`) that are supposed to be independent, side-effect-free-then-effectful stages of the actuator lifecycle. Because `transaction()` is not idempotent/pure, calling it during `validate()` silently pre-applies the swap to the in-memory `Exchange` capsule's reserves. If `execute()` subsequently runs on that same capsule instance, the reserves get double-applied for one `ExchangeTransactionContract`, and even where callers re-fetch the object, the pattern of "validate mutates state" is unsafe: any exception path, retry, or additional actuator that shares the loaded `ExchangeCapsule` object (e.g. batched/multi-contract transaction processing in `TransactionCapsule`/`Manager` where multiple contracts in one transaction reuse loaded capsules) can persist reserves that were shifted purely by a rejected/validate-only invocation, corrupting the AMM's `firstTokenBalance`/`secondTokenBalance` bookkeeping without a corresponding real asset transfer having occurred for the failed leg. This is the same class of bug: a safety/pricing computation meant to be an internal step of a protected sequence is exposed via a "shared" function that produces state changes as a side effect, defeating the intended protection when the sequence is entered from other call paths than the sole intended one.

### Impact Explanation
Reserve balances (`firstTokenBalance`/`secondTokenBalance`) in `Exchange`/`ExchangeV2` back all subsequent AMM price computations and payouts in `ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator`. If reserves drift from the true backing balances due to the double-mutation described above, this yields an unbacked/incorrect bonding-curve state: future trades will compute wrong `anotherTokenQuant`, effectively creating value from nothing or permanently freezing/mis-pricing tokens in the pool — a permanent-freezing/unbacked-balance class impact reachable by any account issuing an `ExchangeTransactionContract`.

### Likelihood Explanation
The double-call itself is normally protected because `validate()` and `execute()` operate on separately re-fetched `ExchangeCapsule` objects. However, the structural flaw — a validation-only path being permitted to mutate persistent-state-bearing objects — is fragile: it is not enforced by any interface contract, is not marked read-only, and is directly reachable by any user submitting a standard `ExchangeTransactionContract` transaction. Any future or existing code path in `Manager`/actuator dispatch that shares/reuses a capsule instance across the validate→execute boundary (e.g., speculative validation, mempool re-validation, or batched contract execution reusing cached capsules) would trigger real reserve corruption. This makes the likelihood conditional on internal reuse patterns rather than a pure crypto-economic flaw, but it is a genuine violation of the "validate must not mutate state" invariant that the actuator framework otherwise relies on everywhere else.

### Recommendation
Split `ExchangeCapsule.transaction()` into a pure/read-only pricing function (e.g. `previewTransaction()` that only computes `buyTokenQuant` without mutating `this.exchange`) used by `doValidate()`, and a separate mutating `applyTransaction()` used only by `execute()`. This guarantees `validate()` never persists or mutates reserve state, restoring the intended validate/execute separation and eliminating any path where a rejected or re-validated transaction could corrupt AMM reserves.

### Proof of Concept
1. Call `ExchangeTransactionActuator.validate()` for a given `ExchangeTransactionContract`; internally this invokes `exchangeCapsule.transaction(tokenID, tokenQuant, ..., allowHarden())` at [4](#0-3) , which mutates `this.exchange`'s `firstTokenBalance`/`secondTokenBalance` inside `ExchangeCapsule.transaction()` at [5](#0-4) .
2. If the same in-memory `exchangeCapsule` object reference (not a fresh reload) is reused when `execute()` runs (e.g. via any code path caching/reusing capsule objects across validate/execute, or a retried validate call before execute), `execute()` calls `transaction()` a second time on already-mutated balances at [6](#0-5) , applying the swap twice to reserves while only debiting/crediting the account balance once.
3. The persisted `ExchangeCapsule` via `Commons.putExchangeCapsule(...)` at [7](#0-6)  now reflects reserves inconsistent with actual token transfers, corrupting the AMM's bonding-curve state for all future trades on that exchange pair.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
