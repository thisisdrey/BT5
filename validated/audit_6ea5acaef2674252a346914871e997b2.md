Based on my investigation, I found the strongest analog in ijar's zip central directory parsing.

### Title
Out-of-bounds read in ZIP central directory extra-field parsing when data_size overruns entry bounds - (File: third_party/ijar/zip.cc)

### Summary
Like CVE-2019-9038's `ReadNextCell()` in matio's `mat5.c`, which trusts an attacker-controlled size field to walk a structured record and reads past the buffer, ijar's `InputZipFile::ProcessCentralDirEntry` trusts attacker-controlled `data_size` fields inside a ZIP central directory extra-field record to advance a cursor, with no check that the advance stays within the declared extra-field region or the mmap'd file buffer.

### Finding Description
`ProcessCentralDirEntry` reads `file_name_length`, `extra_field_length`, and `file_comment_length` directly from the central directory header, then parses the extra-field region with a loop keyed on an equality check rather than a bounds check: [1](#0-0) 

The loop condition is `while (extra_p != p)`, where `p` is `extra_p + extra_field_length` computed earlier. Each iteration reads a 2-byte `header_id` and 2-byte `data_size` from `extra_p` via `get_u2le`, then does `extra_p += data_size`. Nothing constrains `data_size` to remain within the extra field, and nothing re-checks that `extra_p` (before dereferencing `get_u2le(extra_p)` on the next iteration) is still inside the mmap'd input buffer bounds. If a hostile ZIP author crafts a `data_size` value that causes `extra_p` to skip past `p` (the intended end) instead of landing exactly on it — e.g., an odd overshoot — the `while (extra_p != p)` loop no longer terminates at the expected boundary; it continues reading 4-byte header/size pairs and advancing by attacker-chosen `data_size` values indefinitely forward through memory past the legitimate central directory buffer, since there is no `p_end`/file-length bound check inside this loop (unlike `InputZipFile::EnsureRemaining`, which is used elsewhere in local file header parsing but is not applied here). This mirrors the matio bug class: parsing continues past the intended record extent driven purely by an attacker-supplied size field, ending in reads past the mapped buffer (SEGV/OOB read), and is a class already tracked for JAR/ZIP-like extra-field parsers.

The `singlejar` output tool has an explicit regression test acknowledging exactly this bug class exists for extra fields with oversized payload sizes: [2](#0-1) 

This shows the project is aware that malformed/oversized extra-field `payload_size` values are a known hazard in the codebase's zip-parsing surface, but the fix demonstrated for that test is in the singlejar output-jar consumer path, not in `ijar/zip.cc`'s `ProcessCentralDirEntry`, which lacks any equivalent guard.

### Impact Explanation
`ijar/zip.cc`'s `ProcessCentralDirEntry` is reachable whenever Bazel or a build extracts/reads a `.jar`/`.zip` via ijar's `ZipExtractor` (e.g., interface jar generation and other jar-processing tool invocations that consume attacker-influenced jars, such as third-party jar dependencies fetched from an untrusted URL/registry). An attacker who controls the bytes of a jar/zip that gets processed by ijar (a hostile origin serving a "dependency" jar) can trigger reads beyond the mapped input file, causing a crash (SEGV) or, in principle, disclosure of adjacent mapped memory content depending on how the read bytes are used downstream (e.g., in the ZIP64 extra-field handling within the same loop, which reads `u8` values used to overwrite `*uncompressed_size`, `*compressed_size`, `*offset`).

### Likelihood Explanation
This requires only a hostile jar file to be fed into ijar's `ZipExtractor` (or, more broadly, any code path exercising `ProcessCentralDirEntry`), with no checksum protecting internal structural integrity of the file content beyond a whole-file `sha256`/`integrity` in `http_archive` — but a jar built to satisfy a specific checksum is trivially achievable by the attacker since it's their own published artifact. The bug class is directly comparable to the CVE's structural parser without size validation, and there is a project-internal precedent test acknowledging "Malformed size exceeding extra field buffer" as an issue, but that guard exists only for the `output_jar` writer path, not for ijar's central-directory reader.

### Recommendation
In `InputZipFile::ProcessCentralDirEntry`, bound the extra-field parsing loop so that `extra_p + 4 <= p` before reading `header_id`/`data_size`, and that `extra_p + data_size <= p` before advancing, terminating (with an error) rather than looping past `p ` on mismatch, mirroring the `EnsureRemaining` bounds discipline already used in `ProcessLocalFileEntry`.

### Proof of Concept
A JUnit/`src/test/shell/bazel` reproduction was not verified end-to-end within tool budget; the concrete crafted-bytes PoC (central directory entry with extra field whose declared `data_size` does not evenly divide into `extra_field_length`, causing `extra_p` to overshoot `p`) would need to be validated experimentally against a live `ZipExtractor::Create`/`ProcessAll` invocation to confirm the loop's non-termination and resulting SEGV/OOB read, ideally as a `third_party/ijar` unit test analogous to the existing `output_jar_simple_test.cc` malformed-extra-field test shown above.
