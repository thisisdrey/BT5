### Title
Non-Constant-Time Authorization Token Comparison Enables Timing-Based Auth Bypass on Privileged RPC Endpoints - (File: stackslib/src/net/api/postblock_proposal.rs, blockreplay.rs, blocksimulate.rs, postblock_v3.rs, txsimulate.rs, fastcallreadonly.rs)

### Summary
Multiple privileged HTTP RPC endpoints in `stackslib/src/net/api/**` authenticate callers by comparing the `authorization` header against the node's configured secret using Rust's standard string equality operator (`!=`), which is not constant-time.

### Finding Description
The `auth_token` (also called `password`) is a shared secret configured via `connection_options.auth_token` and is meant to gate write/administrative RPC endpoints such as `/v3/block_proposal`, `/v3/blocks/replay/:id`, `/v3/blocks/simulate/:id`, `/v3/transactions/simulate`, and the authenticated-broadcast path of `POST /v3/block` (`postblock_v3.rs`). Each of these handlers implements the same pattern in `try_parse_request`: [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

In each case, `auth_header != password` is a `String`/`&str` comparison (`PartialEq` on `String`), which under the hood uses byte-by-byte comparison that short-circuits at the first mismatching byte (or on differing length). This is directly analogous to the reported Mojic CWE-208 issue: the time to reject an incorrect secret is proportional to the number of correct leading bytes supplied by the attacker, allowing incremental extraction of the secret via repeated timing measurements — exactly the bug class described in the external report (`footerHex !== calcDigest`).

The OpenAPI spec confirms this is a plain-text shared-secret compared for exact equality: [5](#0-4) 

### Impact Explanation
An unauthenticated, unprivileged network client that can reach these HTTP endpoints (`/v3/block_proposal`, `/v3/blocks/replay/*`, `/v3/blocks/simulate/*`, `/v3/transactions/simulate`, `/v3/blocks?broadcast=1`) can attempt to recover the `auth_token`/`auth_password` byte-by-byte using response-timing side channels, since the comparison exits early on the first byte mismatch. Full or partial recovery of this token would grant an outside attacker the ability to invoke privileged operations that are supposed to be reserved for the trusted miner/signer relationship (e.g., forcing block validation calls, or self-broadcasting attacker-controlled blocks/transactions authenticated as the miner). This matches the "auth bypass" impact category called out in scope. Local network jitter/noise on production TCP/HTTP stacks reduces reliability, and successful exploitation would require many repeated requests and statistical analysis, which affects likelihood but not the underlying root-cause classification.

### Likelihood Explanation
Medium-low. The attack requires: (1) network access to the RPC endpoint, (2) the operator to have configured a non-empty `auth_token` (otherwise these endpoints reject with 400, effectively disabled), and (3) enough measurement precision/repetition to overcome real-world network jitter to defeat a short-circuiting `!=` comparison over what is typically a short secret. This mirrors the CVE analog's own caveat that the byte-by-byte forgery is "theoretical" given noise, but the code pattern itself is a textbook non-constant-time secret comparison and is reproducible across at least six independent RPC handlers.

### Recommendation
Replace all `auth_header != password` string comparisons in `stackslib/src/net/api/{blockreplay,blocksimulate,postblock_proposal,postblock_v3,txsimulate,fastcallreadonly}.rs` with a constant-time comparison, e.g. via `subtle::ConstantTimeEq` or a manual constant-time byte comparison that always compares the full length of the longer string (or a fixed-size HMAC of both) instead of returning as soon as a difference is found. Centralize this check into a single shared helper function used by all RPC handlers with an `auth_token` to avoid re-introducing the same defect in future endpoints.

### Proof of Concept
1. Configure a node with `connection_options.auth_token = "S3cr3tTokenValue"`.
2. From a remote unauthenticated client, repeatedly send `GET /v3/blocks/replay/<64-hex>` (or any of the affected endpoints) with an `authorization` header value that varies one byte position at a time, e.g. try all 256 values for byte 0 while keeping the rest as a fixed guess, and measure response latency for the `401 Unauthorized` rejection.
2. Because `auth_header != password` (as in `blockreplay.rs:581`, `blocksimulate.rs:159`, `postblock_v3.rs:106`, `txsimulate.rs:358`) short-circuits at the first mismatching byte, correct-byte guesses will show a measurable (if small) latency increase versus incorrect guesses, since the comparison advances further before returning `false`.
3. Repeating this per byte position with sufficient samples (to average out jitter) allows incrementally recovering `auth_token` without ever knowing it, bypassing the authentication check that gates these RPC endpoints.

Note: I was not able to fully verify the exact byte-level timing sensitivity of the compiled/optimized `PartialEq for str` implementation (LLVM may vectorize short comparisons), which affects real-world exploitability/likelihood; this uncertainty is inherent to the timing-side-channel class of finding and mirrors the same caveat in the original Mojic report.
