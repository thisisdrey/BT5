### Title
Single-key threshold bypass in `ValidateMultiSign` precompile via ECDSA signature malleability - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The TVM precompiled contract `ValidateMultiSign` is designed to let smart contracts verify that a set of signatures collectively meets an account's `Permission` weight threshold — i.e., that a required number of *distinct* authorized keys have signed. Its de-duplication logic only rejects a signature entry if the exact same signature bytes were already counted for a recovered address; it does not deduplicate per signer/authority. Because ECDSA signatures over secp256k1/secp256r1 are malleable (the same key can produce multiple distinct but valid `(r, s, v)` triples for the same hash), an attacker controlling a single authorized key can submit two different signatures from that one key and have the weight of that key counted twice, satisfying a multi-key threshold with only one real authorization — the same "count per verified entry instead of per authority" flaw described in the sigstore-go advisory.

### Finding Description
`PrecompiledContracts.ValidateMultiSign.execute` accumulates weight per signature array entry: [1](#0-0) 

For each signature it recovers `recoveredAddr`, then checks `executedSignList` for duplicates. The skip (`continue`) only triggers when both the recovered address **and** the exact merged `sign` bytes were seen before: [2](#0-1) 

If the recovered address is already present but the signature bytes differ (which happens with a malleable variant of the same key's signature over the same `hash`), the code merely calls `MUtil.checkCPUTime()` and then falls through to compute `weight = TransactionCapsule.getWeight(permission, recoveredAddr)` and add it to `totalWeight` again — counting the same authorized key's weight a second (or, up to `MAX_SIZE=5`, additional) time.

This differs from the transaction-level multisig check `TransactionCapsule.checkWeight`, which deduplicates strictly by recovered **address** (`addMap.containsKey(base64)` keyed by the address after `VERSION_4_7_1`), correctly rejecting "has signed twice": [3](#0-2) 

The TVM precompile's per-signature-bytes dedup is the analog of the sigstore-go bug: threshold counting is keyed to the verified *entry* (raw signature bytes) rather than the verified *authority* (recovered address/key), so a single authority that can produce multiple valid entries defeats the multi-authority threshold policy.

No canonical/low-S enforcement was found anywhere in the crypto or precompile code paths (`ECKey`, signature recovery utilities) that would prevent an attacker from generating a second valid signature for the same key and hash, so the malleable variant is not rejected upstream.

The existing unit test only exercises *identical* repeated signature bytes from the same key and correctly shows they are counted once: [4](#0-3) 

It does not cover the case of two *different* valid signatures from the same key, which is exactly the gap the flawed `executedSignList` check leaves open.

### Impact Explanation
`ValidateMultiSign` is a public TVM precompiled contract reachable by any smart contract or externally-owned account triggering a contract call — no special privilege is required. Smart contracts (custodial wallets, exchange withdrawal gates, DAO-style multisig treasuries) that rely on `ValidateMultiSign` to enforce an N-of-M `Permission` threshold before releasing funds or executing privileged operations can be tricked into approving an operation with only a single compromised or attacker-controlled key, by supplying that key's signature twice in malleable form. This defeats the defense-in-depth guarantee of multi-signature authorization and can lead to unauthorized account operations or theft of funds gated by on-chain multisig logic built on this precompile.

### Likelihood Explanation
Exploitation only requires: (1) knowledge of one legitimate signer's private key or possession of one authorized key with weight below the permission threshold, and (2) the ability to derive a second valid (r,s,v) signature for the same message hash from that key — a standard, well-known ECDSA malleability transform requiring no cryptographic breakthrough. The attacker calls the `ValidateMultiSign` precompile directly from a contract they deploy/call, with no cooperation from other signers, node operators, or witnesses needed. This is reachable by any unprivileged contract deployer/caller.

### Recommendation
Change the deduplication key in `ValidateMultiSign.execute` from `(recoveredAddr, signatureBytes)` to `recoveredAddr` alone, matching the semantics already used in `TransactionCapsule.checkWeight`: once an address's weight has been counted, any further signature recovering to that same address must be skipped entirely (not merely rate-limited via `checkCPUTime`), regardless of whether the raw signature bytes differ.

### Proof of Concept
1. Create an account with an `Active` permission requiring `threshold = 2`, with two keys `key1` (weight 1) and `key2` (weight 1) — a standard 2-of-2 multisig gate exposed to a contract via `ValidateMultiSign`.
2. Attacker controls only `key1`.
3. Attacker signs the message hash with `key1` to get signature `sig_a = (r, s, v)`.
4. Attacker derives the malleable counterpart `sig_b = (r, n-s, 1-v)` (standard secp256k1 transform), which recovers to the same address as `sig_a` but has different byte content.
5. Attacker calls `ValidateMultiSign(address, permissionId, data, [sig_a, sig_b])`.
6. In `execute()`, first iteration: `recoveredAddr` = key1's address, not in `executedSignList` → `totalWeight += 1`. Second iteration: `recoveredAddr` already in `executedSignList`, but merged `sign` bytes differ from `sig_a` → skip check fails to trigger `continue`; code falls through and does `totalWeight += 1` again.
7. `totalWeight` = 2 ≥ `threshold` (2) → precompile returns `true`/`DataWord.ONE()`, even though only `key1` ever authorized the operation and `key2` never signed. [5](#0-4)
