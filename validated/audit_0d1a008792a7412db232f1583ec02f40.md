### Title
Unbounded iteration over client-supplied `ref_names` in `ListCommitsByRefName` enables RPC handler resource exhaustion - ([File: internal/gitaly/service/commit/list_commits_by_ref_name.go])

### Summary
The reported bug class is a Solidity function (`withdrawReward`) that loops over an attacker/caller-influenced range with no upper bound (`lastUpdatedDay` never initialized, `allTranches` unbounded), causing the call to run out of gas and become permanently unusable. The Gitaly analog is a gRPC RPC handler that iterates over a `repeated` request field supplied directly by the caller with no size limit and no pagination, performing one Git object lookup per entry — allowing a client to force the server to do unbounded, serial work per RPC call.

### Finding Description
`ListCommitsByRefName` iterates directly over the client-supplied `RefNames` field of the request, calling `catfile.GetCommit` once per entry with no cap on the number of iterations: [1](#0-0) 

Unlike sibling RPCs in the same service family — e.g. `ListBlobsRequest` (has `limit`/`bytes_limit`), `FindRefsByOIDRequest` (has `limit`), `ListLFSPointersRequest` (has `limit`) — `ListCommitsByRefNameRequest` has no `limit` field constraining `ref_names`, so the number of catfile lookups performed by the handler is entirely determined by how many ref names the caller decides to send in a single request: [2](#0-1) [3](#0-2) 

The design guidance in the codebase itself calls out that repeated fields which can grow without bound should be streamed and capped, which was not applied here for the request side: [4](#0-3) 

Each iteration invokes `catfile.GetCommit`, which spawns/uses the catfile process to look up an object — a non-trivial cost multiplied by however many ref names the request contains, all serially and synchronously within a single gRPC call, with no `context` cancellation between lookups other than what the outer RPC deadline provides.

### Impact Explanation
Because a single unary-style request field (`ref_names`) can contain up to the gRPC max message size worth of ref name strings (each short strings can be packed densely), a caller can submit a very large list of `ref_names` in one `ListCommitsByRefName` request, causing the handler to perform a correspondingly large number of sequential catfile object lookups within one RPC invocation. This ties up a Gitaly worker goroutine and catfile session for the full duration of the loop, which — unlike the Marginswap gas-exhaustion bug that simply reverts — degrades or exhausts Gitaly server-side resources (CPU / catfile session pool) per request, and can be repeated across many concurrent requests to amplify the effect into a broader denial-of-service against the Gitaly node, similar in class to the concerns addressed by explicit `limit` fields and concurrency limiters elsewhere in the codebase (e.g. `packObjectsLimiter`, `maxDivergentRefs`) that this RPC lacks: [5](#0-4) 

### Likelihood Explanation
This RPC is reachable by any client authorized to call Gitaly's `CommitService` (an ordinary, authenticated but otherwise unprivileged caller of the gRPC API, analogous to GitLab Rails/Workhorse forwarding user-controlled ref lists), and the request field is fully attacker-controlled with no server-side clamp, making the likelihood high for anyone able to issue this specific RPC with a large `ref_names` array.

### Recommendation
Add a `limit` field to `ListCommitsByRefNameRequest` (consistent with `FindRefsByOIDRequest`/`ListLFSPointersRequest`) and enforce it in the handler before iterating, or otherwise cap the maximum number of `ref_names` entries processed per call and reject/truncate requests that exceed it. Consider applying the same concurrency/queueing protections used for other expensive RPCs (e.g. the `packObjectsLimiter` pattern) if per-call cost cannot be bounded up front.

### Proof of Concept
Not independently reproduced against a running Gitaly instance in this analysis (no execution environment available); the finding is based on static review of the handler and its request-side lack of a size/limit guard: [1](#0-0) 
A conceptual PoC would be a `ListCommitsByRefName` gRPC call whose `ref_names` field is populated with the maximum number of short ref-name strings that fit under the gRPC message-size limit, then measuring per-call CPU/catfile time versus a small `ref_names` list, and repeating the call concurrently to observe server-side resource degradation.

func (s *server) ListCommitsByRefName(in *gitalypb.ListCommitsByRefNameRequest, stream gitalypb.CommitService_ListCommitsByRefNameServer) error {
	ctx := stream.Context()
	repository := in.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return structerr.NewInvalidArgument("%w", err)
	}
	repo := s.localRepoFactory.Build(repository)

	objectReader, cancel, err := s.catfileCache.ObjectReader(ctx, repo)
	if err != nil {
		return structerr.NewInternal("%w", err)
	}
	defer cancel()

	sender := chunk.New(&commitsByRefNameSender{stream: stream})

	for _, refName := range in.GetRefNames() {
		commit, err := catfile.GetCommit(ctx, objectReader, git.Revision(refName))
		if errors.As(err, &catfile.NotFoundError{}) {
			continue
		}
		if err != nil {
			return structerr.NewInternal("%w", err)
		}

		commitByRef := &gitalypb.ListCommitsByRefNameResponse_CommitForRef{
			Commit: commit.GitCommit, RefName: refName,
		}

		if err := sender.Send(commitByRef); err != nil {
			return structerr.NewInternal("%w", err)
		}
	}
