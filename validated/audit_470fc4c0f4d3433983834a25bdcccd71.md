## Verdict

Based on the available evidence, this describes a real, exploitable mechanism, but it is a known and bounded design characteristic of the greedy scheduler rather than a novel unmitigated bug — however, the specific claim that a **single fee payer can be reused across all 100,000 decoy transactions to make the attack cheap** (bypassing the need for many funded accounts) is a legitimate low-cost path worth flagging, since `check_fee_payer_unlocked` only validates that the fee payer can cover *one* fee against the current bank state, not that funds are reserved across all in-flight buffered transactions from that payer.

### Title
Scan-budget exhaustion via cheap same-account conflicting transactions causes indefinite starvation of lower-priority victim transactions - (File: core/src/banking_stage/transaction_scheduler/greedy_scheduler.rs)

### Summary
`GreedyScheduler::schedule` bounds each pass by `num_scanned < config.max_scanned_transactions_per_scheduling_pass` (100,000) [1](#0-0) , and any transaction that fails `try_lock_accounts` due to a write-lock conflict is pushed to `unschedulables` and re-queued at the same priority for the next pass [2](#0-1) [3](#0-2) . An attacker can flood the container with many high-priority transactions that all write-lock the same "decoy" account (e.g., reuse one funded fee payer, whose account is implicitly writable), so after the first one locks the account for a thread, every subsequent one hits `TryLockError::MultipleConflicts`/`ThreadNotAllowed` and consumes scan budget without being scheduled, potentially exhausting the pass before a lower-priority, conflict-free victim transaction is even popped.

### Finding Description
`schedule()` pops transactions strictly in priority order via `container.pop()` [4](#0-3) , and stops scanning once `num_scanned` reaches `max_scanned_transactions_per_scheduling_pass` (100,000 by default) [5](#0-4) . For each popped id, `try_schedule_transaction` calls `ThreadAwareAccountLocks::try_lock_accounts`, which returns `Err(TryLockError::MultipleConflicts)` or `Err(TryLockError::ThreadNotAllowed)` if the account is already write-locked on another/all threads [6](#0-5) . On failure the id goes into `unschedulables` [7](#0-6)  and is re-inserted into the priority queue at the end of the pass at the *same* priority [3](#0-2) , so it will again be popped ahead of the victim's lower-priority transaction on the next pass.

Locks are only released when the in-flight batch completes and `SchedulingCommon::complete_batch`/`try_receive_completed` calls `unlock_accounts` [8](#0-7) . Thus at most one decoy transaction per thread is actually "in flight" and holding the lock at any time, while the remaining decoy transactions in the container all fail the lock check and consume scan budget every pass.

To get many cheap conflicting transactions into the container, an attacker only needs to pass sig verification, sanitization, and `Consumer::check_fee_payer_unlocked`, which is invoked in `handle_packet_batch_message` prior to insertion [9](#0-8) . This check validates against the current bank state (does the fee payer currently have enough balance to cover the fee), not against a reservation that accounts for the fact that thousands of buffered sibling transactions from the same payer will never all land. This means a single funded keypair, reused as fee payer (which is implicitly writable in every transaction) across many distinct transactions (varying an instruction/compute-budget field for unique signatures/message hashes), is sufficient to generate the mutually-conflicting decoy set cheaply — the attacker doesn't need thousands of funded accounts.

### Impact Explanation
The scoped impact is a scheduling-fairness violation: a specific victim transaction (paying real, possibly high, priority fees) can be repeatedly excluded from every `ConsumeWork` batch on the leader for the duration of the attack, because 100,000 scan slots per pass are consumed by unschedulable decoy transactions ahead of it in priority. This matches the "scheduling correctness/fairness" category described in the prompt — indefinite delay/effective drop of a targeted transaction without the attacker needing to pay real fees for the vast majority of decoys (only one decoy actually gets scheduled/executed per thread per pass; the rest never consume fees since they never execute).

### Likelihood Explanation
Feasibility requires: (1) one funded fee-payer keypair with lamports to cover a single priority fee (this passes `check_fee_payer_unlocked` for each distinct transaction submitted, since the balance check is stateless per submission and does not decrement for queued-but-unexecuted transactions); (2) ability to construct many distinct, validly-signed transactions from that keypair with a compute-unit-price higher than the victim's; (3) knowledge or guessability of victim's account so the decoy set only needs to write-lock a shared account among itself (does not even need to target the victim's specific account — locking any account causes conflicts among *itself*, consuming scan budget ahead of any lower-priority transaction, victim included). This is reachable purely through the unstaked public TPU/QUIC ingress path with no validator/staked control required, and is repeatable every scheduling pass as long as the attacker keeps refilling the container (bounded only by container capacity and re-submission rate).

### Recommendation
- Track per-conflict-group or per-payer scan consumption and cap it (e.g., limit the number of scan slots consumable by transactions sharing a write-locked account within one pass) so a single hot account cannot dominate the scan budget.
- Alternatively, only re-count `unschedulables` toward the *next* pass's scan budget once, or apply exponential/priority backoff to repeatedly-unschedulable ids so they don't perpetually occupy the head of the priority queue.
- Consider deprioritizing (not just re-queuing at same priority) transactions that fail `try_lock_accounts` for consecutive passes, so the scanner naturally reaches lower-priority, conflict-free transactions sooner.

    pub fn try_lock_accounts<'a>(
        &mut self,
        write_account_locks: impl Iterator<Item = &'a Pubkey> + Clone,
        read_account_locks: impl Iterator<Item = &'a Pubkey> + Clone,
        allowed_threads: ThreadSet,
        thread_selector: impl FnOnce(ThreadSet) -> ThreadId,
    ) -> Result<ThreadId, TryLockError> {
        let schedulable_threads = self
            .accounts_schedulable_threads(write_account_locks.clone(), read_account_locks.clone())
            .ok_or(TryLockError::MultipleConflicts)?;
        let schedulable_threads = schedulable_threads & allowed_threads;
        if schedulable_threads.is_empty() {
            return Err(TryLockError::ThreadNotAllowed);
        }

        let thread_id = thread_selector(schedulable_threads);
        self.lock_accounts(write_account_locks, read_account_locks, thread_id);
        Ok(thread_id)
    }

    /// Mark a given `TransactionBatchId` as completed.
    /// This will update the internal tracking, including account locks.
    fn complete_batch(&mut self, batch_id: TransactionBatchId, transactions: &[Tx]) {
        let thread_id = self.in_flight_tracker.complete_batch(batch_id);
        for transaction in transactions {
            let account_keys = transaction.account_keys();
            let write_account_locks = account_keys
                .iter()
                .enumerate()
                .filter_map(|(index, key)| transaction.is_writable(index).then_some(key));
            let read_account_locks = account_keys
                .iter()
                .enumerate()
                .filter_map(|(index, key)| (!transaction.is_writable(index)).then_some(key));
            self.account_locks
                .unlock_accounts(write_account_locks, read_account_locks, thread_id);
        }
    }
