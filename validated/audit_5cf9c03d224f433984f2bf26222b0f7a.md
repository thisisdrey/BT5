### Title
Rx ring slot is re-armed for a new UDP receive before the completed packet's data is copied out, creating a TOCTOU window that lets a UDP flood overwrite `packet.data` before `copy()` reads it - (File: udp/udp_rio_windows.go)

### Summary
In `RIOConn.receive`, after a completion is dequeued the code calls `u.rx.Return(1)` and `u.insertReceiveRequest()` — which re-arms the ring slot with a brand-new `ReceiveEx` — *before* it dereferences `results[0].RequestContext` and executes `copy(buf, packet.data[:results[0].BytesTransferred])`. This ordering leaves a window in which the kernel can DMA a newly-arrived datagram's bytes into the exact same registered-memory slot that is about to be read into `buf`.

### Finding Description
The relevant sequence in `RIOConn.receive` is: [1](#0-0) 

1. `winrio.DequeueCompletion` returns a completed request whose `RequestContext` is the address of a `ringPacket` inside the pre-registered `rx.packets` memory region.
2. `u.rx.Return(1)` bumps `ring.head` — pure bookkeeping.
3. `u.insertReceiveRequest()` immediately calls `ring.Push()` and posts a **new** `winrio.ReceiveEx` pointed at `packets + (tail%packetsPerRing)*sizeof(ringPacket)`. Because the ring is normally kept full (1024 requests always outstanding, filled in `NewRIOListener`, see [2](#0-1) ), `Push()`'s slot for the new request is the very slot that was just freed by `Return()` — i.e. the same memory that backs the packet whose data is about to be read.
4. Only *after* that new receive is armed does the code compute `packet := (*ringPacket)(unsafe.Pointer(uintptr(results[0].RequestContext)))` and run `copy(buf, packet.data[:results[0].BytesTransferred])` ( [3](#0-2) ).

Between steps 3 and 4 the kernel/NIC can complete the freshly-submitted `ReceiveEx` for a new inbound datagram and write its bytes into that same buffer, because RIO buffers are just raw registered memory with no synchronization other than the completion-queue protocol Nebula itself drives. An attacker who floods the listener with UDP packets fast enough increases the probability that a second datagram's bytes land in the slot during this window, so the `copy()` can pull a mixture of the "old" (already-completed) bytes and the "new" (racing) bytes, or entirely different bytes than what `BytesTransferred` was computed for.

The reported `BytesTransferred` value itself is still bounded by the buffer length that was registered for that request (`bytesPerPacket`), so this is not a buffer-overflow / memory-safety bug — the `copy()` never runs off the end of `packet.data` or `buf`. The corruption is purely a content-integrity race: the bytes copied into `buf` can belong to a different datagram than the one the completion metadata (`RequestContext`/`BytesTransferred`) was generated for.

### Impact Explanation
The resulting `buf[:n]` is handed to the registered `EncReader` (`ListenOut` → `r(...)`) and flows into header parsing, hostmap/relay lookup by `RemoteIndex`, and eventually AEAD decryption. However, Nebula's packet header fields are never trusted pre-authentication: any lookup driven by a torn/garbled `RemoteIndex` or `MessageCounter` only selects a hostmap entry, and the packet is still required to pass AEAD open (which authenticates the full ciphertext including the header) before any state is mutated. A torn buffer combining bytes from two different datagrams will, in the overwhelming majority of cases, simply fail the AEAD tag check and be dropped — so this race does not provide a path to authentication bypass, decryption/forgery, or firewall/hostmap state poisoning.

The practical impact is limited to reliability/integrity: an unprivileged flooder co-resident on the network path to a Windows Nebula node using the RIO path (`NewRIOListener`, selected by default in `NewListener` unless it fails to initialize, see [4](#0-3) ) can increase spurious packet drops/authentication failures for legitimate sessions by corrupting their own or coincidentally overlapping datagrams before they are copied out. This is an availability/integrity defect in the Windows-specific RIO receive path, not a cryptographic or authentication bypass.

### Likelihood Explanation
No certificate or privileged access is required — only the ability to send a sustained, high-rate stream of UDP packets to the listener, which any unprivileged network peer can do. The likelihood of the race actually being hit scales with attacker send rate and how close to the completion/re-arm boundary the timing lands; it is a genuine, reproducible race given the ordering of operations in `receive`, since the ring is intentionally kept at full occupancy (1024 always-outstanding receives) so slot reuse is immediate and continuous.

### Recommendation
Reorder the operations in `RIOConn.receive` so the completed packet's data is copied into `buf` (and any address/metadata extracted) *before* the slot is returned to the ring and re-armed with `insertReceiveRequest()`. Concretely, extract `packet`, `ep`, and perform the `copy()` immediately after validating `results[0].Status`, and only call `u.rx.Return(1)` / `u.insertReceiveRequest()` afterward, so the buffer is never re-submitted for a new receive while its previous contents are still being read out.

### Proof of Concept
Integration/race test plan (Windows-only, requires RIO):
1. Stand up a `RIOConn` via `NewRIOListener` on loopback.
2. From a separate goroutine/process, flood the listener with UDP datagrams where each datagram's payload is a unique, easily-recognizable byte pattern encoding a monotonically increasing sequence number (e.g., 8-byte counter repeated to fill the datagram).
3. In the receiving loop (mirroring `ListenOut`), for each `buf[:n]` delivered, assert that all bytes in `buf[:n]` are consistent with a single sequence number (i.e., `buf` is byte-identical to exactly one transmitted datagram of that size). Fail the test if any `buf[:n]` contains bytes belonging to two different sequence numbers.
4. Run under high concurrency/rate (multiple flooding goroutines) to maximize the chance of hitting the re-arm window between `insertReceiveRequest()` and the subsequent `copy()`.
5. Expected result before fix: intermittent assertion failures showing mixed sequence-number bytes in a single delivered buffer, confirming the torn read; after reordering the copy before re-arming, the test should pass consistently under the same flood conditions.
