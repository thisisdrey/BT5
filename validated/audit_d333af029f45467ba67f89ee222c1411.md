### Title
Unescaped exception message concatenated into JSON error response breaks output structure - (File: framework/src/main/java/org/tron/core/services/http/JsonFormat.java)

### Summary
The Go advisory (CVE-2024-24785) is a bug class where an error string derived from `MarshalJSON` — which may embed user-controlled data — is inserted into output without being safely re-escaped for the target format, letting attacker data break the encoding contract of the consumer. The same bug class exists in java-tron's HTTP JSON error path: `JsonFormat.printErrorMsg` builds a JSON object by raw string concatenation of `ex.getMessage()` without any JSON-string escaping.

### Finding Description
`JsonFormat.printErrorMsg` constructs the error body manually: [1](#0-0) 

It appends `ex.getMessage()` verbatim between quotes with no call to `escapeText`/`escapeNameStringText` (the very escaping routines the codebase uses elsewhere to prevent exactly this class of bug, as evidenced by the extensive `JsonFormatEscapeTest` suite guarding `escapeBytesSelfType`) [2](#0-1) . This method is reached via `Util.processError`, which every unauthenticated HTTP servlet (e.g. `GetBlockServlet`, `GetContractServlet`, `GetContractInfoServlet`, `GetNkFromNskServlet`, etc.) calls on any thrown `Exception` to build the HTTP response body: [3](#0-2)  and directly in `GetNodeInfoServlet`: [4](#0-3) .

Many of these servlets throw exceptions whose message text embeds attacker-supplied request parameters verbatim, e.g. `InvalidParameterException(Util.OWNER_ADDRESS + " isn't set.")` in `TriggerSmartContractServlet.validateParameter` [5](#0-4) , or `JSONException`/`ParseException` messages that embed the caller's raw JSON/hex input during `JsonFormat.merge` parsing [6](#0-5) . If any such user-controlled substring contains a `"` or `\` (or a raw control character), it is emitted unescaped into `printErrorMsg`'s `{"Error":"..."}` payload, letting the caller inject additional bogus JSON keys or break the string boundary of the response.

Note `TriggerSmartContractServlet`'s own generic-exception handler mitigates this locally by doing `e.getMessage().replaceAll("[\"]", "\'")` before embedding the message [7](#0-6)  — this ad-hoc, per-servlet patch is itself evidence that the underlying shared helper (`JsonFormat.printErrorMsg`) is not safe by default and other callers using `Util.processError` do not apply any equivalent sanitization.

### Impact Explanation
This breaks the structural/escaping contract of an HTTP JSON API response (the analog of "breaking contextual auto-escaping" in the reported advisory) rather than the strict routines the codebase already hardened for on-chain byte fields (`escapeBytesSelfType`/`escapeText`). Depending on how the resulting malformed JSON is consumed downstream (permissive JSON parsers, log aggregation, or any client eval'ing the field), this can allow response content injection or downstream parsing corruption for any anonymous API caller hitting a servlet that funnels exceptions through `Util.processError`/`printErrorMsg`. It does not directly cause fund loss or consensus impact, but it is a genuine API-response integrity/injection bug reachable by any unauthenticated HTTP client.

### Likelihood Explanation
High reachability: `Util.processError` is the default catch-all error responder wired into essentially every full-node HTTP servlet, and multiple exception sites embed raw user input in their message text (parameter names/values, malformed request bodies). No privileged access is required — a single crafted HTTP GET/POST with a quote or backslash in a parameter that ends up quoted inside an exception message is sufficient to trigger the unescaped concatenation.

### Recommendation
Route `JsonFormat.printErrorMsg` (and any other manual `"{\"Error\":\"" + msg + "\"}"` construction) through the same escaping utility already used for name-string byte fields (`JsonFormat.escapeText`), or build the error object via the Jackson-backed `org.tron.json.JSONObject`/`JsonUtil.obj2Json` instead of manual string concatenation, so exception messages are always properly JSON-escaped regardless of their content.

### Proof of Concept
1. Send a POST to `TriggerSmartContractServlet` (or any endpoint that reaches `Util.processError`) with a parameter value crafted to appear inside a thrown exception's message, e.g. an owner-address value containing `","injected":true` such that the resulting `InvalidParameterException` message is `... "injected":true isn't set.`.
2. Observe that `printErrorMsg`/`processError` emits this text unescaped inside the `{"Error":"..."}` body, producing structurally invalid/attacker-influenced JSON in the HTTP response — the java-tron analog of the reported "errors ... may break template escaping" bug class.

  private static String escapeNameStringText(String input) {
    int index = input.indexOf(Character.MAX_VALUE);
    if (index < 0) {
      return escapeText(input);
    }

    StringBuilder result = new StringBuilder(input.length());
    int start = 0;
    while (index >= 0) {
      result.append(escapeText(input.substring(start, index)));
      result.append(Character.MAX_VALUE);
      start = index + 1;
      index = input.indexOf(Character.MAX_VALUE, start);
    }
    result.append(escapeText(input.substring(start)));
    return result.toString();
  }
