Based on the code I traced through, this proposed vulnerability does not hold up.

**Mechanism analysis:**

The finite-wasm instrumentation in `instrument_v3.rs` inserts a `GAS_GLOBAL` charge at the *start* of each metered basic block, before any of that block's instructions (including any `call` to a host import) execute [1](#0-0) . The charge subtracts the full estimated cost of the upcoming block from `GAS_GLOBAL` and, only on underflow, calls back into the host via `GAS_INSTRUMENTATION_FN` [2](#0-1) . Since `call` instructions to host imports are emitted verbatim within the already-charged block [3](#0-2) , by the time control reaches such a `call`, `GAS_GLOBAL` already reflects the full cost of every wasm op executed so far in that block, including the call itself.

The wasmtime `call_hook` fires exactly at this `CallHook::CallingHost` boundary, reading the (already-decremented) `GAS_GLOBAL` and burning the delta into `GasCounter` via `burn_gas` *before* the host function body executes [4](#0-3) . Only after this sync does the host function's own logic run and charge its own `pay_base`/`pay_per` costs on top [5](#0-4) . On return, `CallHook::ReturningFromHost` re-publishes the updated `remaining_gas()` back into `GAS_GLOBAL` [6](#0-5) .

There is no window where a host function observes a stale (higher) gas value than what the wasm has already consumed — the sync is strictly ordered before host logic execution on every boundary crossing. This exact test scenario (`gas_export_clash`) confirms consistent burnt/used gas accounting across such boundaries [7](#0-6) , and `GasCounter::burn_gas`/`process_gas_limit` enforce hard caps regardless [8](#0-7) .

    k: Option<InstrumentationKind>,
    gas: Fee,
    globals: u32,
    local_idx: u32,
) -> Result<(), Error> {
    if matches!(gas, Fee::ZERO) {
        return Ok(());
    } else if gas.linear == 0 {
