## Analysis

The Frax bug reduces to one broken invariant: **a value used to gate protocol payouts is read as an instantaneous on-chain AMM spot price, with no TWAP/oracle protection, and the attacker fully controls both the manipulating trade and the payout-triggering call.**

The closest local analog in `paritytech/polkadot-sdk` is `pallet-asset-conversion-tx-payment`'s `SwapAssetAdapter`, which prices transaction fees paid in a non-native asset using the *live* reserves of a `pallet-asset-conversion` pool, with no time-weighting.

### Title
Transaction fees paid via `SwapAssetAdapter` can be underpaid by self-manipulating the `pallet-asset-conversion` spot price in the same block - (File: `substrate/frame/transaction-payment/asset-conversion-tx-payment/src/payment.rs`)

### Summary
`SwapAssetAdapter::withdraw_fee` and `can_withdraw_fee` price a transaction's native-fee obligation in an arbitrary user-chosen asset by calling `QuotePrice::quote_price_tokens_for_exact_tokens`, which in turn reads the *current* reserve balances of the `pallet-asset-conversion` pool via `Pallet::get_reserves` [1](#0-0) . There is no TWAP, no minimum-liquidity check tied to manipulation resistance, and no protection against the payer's own prior extrinsic having just skewed the pool in the same block, exactly mirroring the Frax `spotPriceOHM` pattern.

### Finding Description
`Pallet::get_reserves` returns the raw, instantaneous asset balances held by the pool account [2](#0-1) , and `quote_price_tokens_for_exact_tokens`/`quote` derive the exchange rate directly from those balances with no averaging window [3](#0-2) [4](#0-3) .

`SwapAssetAdapter::withdraw_fee`, used by `ChargeAssetTxPayment` to charge transaction fees in a non-native asset, uses exactly this instantaneous quote to decide how much of the payer's asset to withdraw for a fixed native `fee`, then performs the swap for that quoted amount: [5](#0-4) 

Because `ChargeAssetTxPayment` is a `TransactionExtension`, its `prepare` step (which calls `withdraw_fee`) runs immediately before the wrapped call is dispatched, in the same block, using whatever pool state exists at that point [6](#0-5) . An attacker fully controls their own extrinsic ordering (e.g. via `pallet-utility::batch_all`, which is explicitly a public wrapper this program flags): they can first submit a large `AssetConversion::swap_exact_tokens_for_tokens` that pushes the pool's price of `asset_id` relative to the native fee asset up, then, atomically or in the very next extrinsic in the same block, pay their transaction fee in `asset_id` while the price is still skewed, and finally swap back. No malicious collator, relayer, validator, or governance action is required — the entire sequence is composed of the attacker's own ordinary transactions.

### Impact Explanation
This is "public underpriced work that degrades block production": the attacker pays less real economic value than the fee schedule intends for the weight/length they consume, at the direct expense of the liquidity pool (and thus its LPs) and the fairness of the fee market that funds block production. Because `SwapAssetAdapter` is the reference/most commonly cited `OnChargeAssetTransaction` implementation shipped in the SDK for asset-fee payment, any runtime wiring it in production inherits this exposure whenever a manipulable (i.e., not deeply liquid) `AssetConversion` pool is used for fee payment.

### Likelihood Explanation
Likelihood depends on pool depth: shallow pools (the same condition the original report calls out — "if a TWAP is used, ensure the underlying pool is highly liquid") make the round-trip manipulation cheap relative to the fee savings. The code's own doc comment acknowledges price can move "by the time the transaction is executed" but only frames this as a UX/slippage concern for `quote_price_*`, not as an adversarial-manipulation concern for fee charging, so no mitigation (TWAP, minimum pool depth requirement, or price staleness bound) exists today [7](#0-6) .

### Recommendation
Do not derive the fee-asset conversion rate purely from the instantaneous reserves of a single pool at execution time. Either (a) bound the allowed price deviation between the `validate`-time quote and the `prepare`-time quote and reject if it exceeds a threshold, (b) require a minimum pool liquidity/depth for a pool to be eligible as a fee-payment route, or (c) compute the rate from a moving-average of reserves over multiple blocks rather than the single current block's balances.

### Proof of Concept
1. Attacker funds account with `asset_id` and enough native currency for one manipulating swap.
2. Extrinsic A (attacker): `AssetConversion::swap_exact_tokens_for_tokens(path=[Native, asset_id], amount_in=large, ...)` — pushes the pool reserves so that `asset_id` is priced richly relative to native.
3. Extrinsic B (attacker, same block, next nonce): any call with `ChargeAssetTxPayment { asset_id: Some(asset_id), .. }`. `withdraw_fee` calls `quote_price_tokens_for_exact_tokens(asset_id, Native, fee, true)` against the now-skewed reserves [1](#0-0) , returning a smaller-than-fair `asset_fee`, which is withdrawn and swapped for the exact native `fee` [8](#0-7) .
4. Extrinsic C (attacker): swap back `asset_id` → native to close the position, net cost = pool's swap fee (e.g. 0.3%) twice plus price impact, versus the fee-payment discount realized in step 3.
5. Repeating over many blocks against a shallow pool nets the attacker a persistent discount on all their transaction fees at LP expense. [9](#0-8)

				Err(Error::<T>::PoolEmpty)?;
			}

		pub fn quote_price_tokens_for_exact_tokens(
			asset1: T::AssetKind,
			asset2: T::AssetKind,
			amount: T::Balance,
			include_fee: bool,
		) -> Option<T::Balance> {
			// Swaps reject zero amounts, match that behavior.
			if amount.is_zero() {
				return None;
			}
			let pool_account = T::PoolLocator::pool_address(&asset1, &asset2).ok()?;

			let (balance1, balance2) = Self::get_reserves(asset1.clone(), asset2.clone()).ok()?;

			if balance1.is_zero() {
				return None;
			}

			// Swap withdrawals from pools use `keep_alive=true` (Preserve). Use the same
			// preservation level to determine the actual withdrawable amount.
			let max_output =
				T::Assets::reducible_balance(asset2.clone(), &pool_account, Preserve, Polite);
			if amount > max_output {
				return None;
			}

			if include_fee {
				let fee = Self::pool_fee_for(&asset1, &asset2).ok()?;
				Self::get_amount_in(fee, &amount, &balance1, &balance2).ok()
			} else {
				Self::quote(&amount, &balance2, &balance1).ok()
			}
		}
