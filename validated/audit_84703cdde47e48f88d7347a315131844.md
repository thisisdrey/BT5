### Title
Malicious peer can supply arbitrary attachment bytes for a requested content hash, causing the real hash to never resolve (BNS denial-of-resolution) - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentsDownloader::run` resolves and indexes downloaded attachments using `attachment.hash()` — the hash computed from the bytes actually returned by the queried peer — instead of the `content_hash` (`H`) that was originally requested. Nothing in the download path checks that the returned bytes actually hash to `H`, so a malicious peer that is selected as a download source for an `AttachmentRequest` can return arbitrary bytes `B` and the node will never resolve the legitimately committed attachment `H`.

### Finding Description
`get_prioritized_attachments_requests` builds one `AttachmentRequest` per real, on-chain-committed `content_hash` (`H`), and issues the HTTP request to `/v2/attachments/{H}` against the "most reliable" peer in `sources` [1](#0-0) [2](#0-1) . `sources` is populated from peer-controlled inventory bitmaps (`AttachmentsInventoryRequest`/`GetAttachmentsInvResponse`), so an unprivileged peer can freely claim to have `H` in its inventory and become a candidate source for it [3](#0-2) .

When the HTTP response comes back, `decode_atlas_get_attachment` simply JSON-decodes the body into `GetAttachmentResponse { attachment }` with no check that `attachment.hash() == H` [4](#0-3) . `extend_with_attachments` then unconditionally inserts this attacker-controlled `Attachment` into `self.attachments: HashSet<Attachment>` — again with no hash validation against the request that produced it [5](#0-4) .

Finally, in the `Done` branch of `AttachmentsDownloader::run`, the code does:
```
let attachments_instances = network.atlasdb.find_all_attachment_instances(&attachment.hash())...
network.atlasdb.insert_instantiated_attachment(&attachment)...
...
context.attachments_batch.resolve_attachment(&attachment.hash())
``` [6](#0-5) 

`attachment.hash()` is `Hash160::from_data(&attachment.content)` [7](#0-6)  — i.e., the hash of whatever bytes the peer actually sent (`B`), not the `H` that was requested. Since `resolve_attachment` and `find_all_attachment_instances` are both keyed on `attachment.hash()` (= hash of `B`), and `attachments_batch.attachments_instances`/AtlasDB entries are keyed on `H`, the entry for `H` is never touched: it is not removed from `attachments_batch.attachments_instances`, `find_all_attachment_instances` returns an empty/unrelated set (since no tracked instance has `content_hash == hash(B)`), and no `(AttachmentInstance, Attachment)` pair is produced for `H`.

Because `H` was never resolved, `context.attachments_batch.has_fully_succeed()` remains false, so the batch is re-enqueued via `bump_retry_count()` and retried up to `connection_options.max_attachment_retry_count`, after which it is dropped entirely [8](#0-7) . A single malicious peer chosen as the source for that `content_hash` can therefore indefinitely (until the retry budget is exhausted) prevent resolution of a real, on-chain-committed attachment, even when an honest peer holds the correct data — because only one peer is queried per `AttachmentRequest` (`get_most_reliable_source()`), and no cross-check against `H` ever happens regardless of which peer answers.

### Impact Explanation
This is a High-severity "attachment/BNS mismatch"/denial-of-resolution bug. A remote, unprivileged peer that a node considers a sync peer (no secret or admin role required — any P2P peer offering the atlas HTTP service) can:
1. Claim (via its self-reported attachment inventory bitmap) to have any attachment `H` it likes.
2. When selected as the download source for that `AttachmentRequest`, return arbitrary bytes `B ≠ preimage(H)`.
3. Cause the node to permanently fail to resolve `H` (its zonefile/BNS attachment), even though the data is legitimately committed on-chain and available from honest peers, because the resolution/removal logic operates on `hash(B)` instead of `H`.

This is repeatable per attachment/content hash and per retry cycle, and results in a node treating a legitimately committed BNS attachment as permanently unavailable — the exact "attachment/BNS mismatch" impact category called out in the rules.

### Likelihood Explanation
- Preconditions: attacker only needs to run an ordinary Stacks peer that the victim treats as an outbound sync peer with a reachable data URL (`network.get_outbound_sync_peers()` / `get_data_url`), and to be selected as the "most reliable" source for the targeted attachment request (achievable by responding successfully/quickly to build up a favorable `ReliabilityReport`, or simply by being the only/first source claiming the attachment).
- Attacker cost: minimal — one crafted inventory response plus one crafted attachment response per targeted `content_hash`; no cryptographic material, secrets, or privileged roles needed.
- Remote reachability: standard P2P/RPC attachment endpoints (`/v2/attachments/inv`, `/v2/attachments/{hash}`), which are unauthenticated by design.
- Repeatable indefinitely against any newly committed attachment the attacker wants to censor, bounded only by `max_attachment_retry_count` per batch (after which the batch is simply dropped, making the denial permanent for that instance).

### Recommendation
In `AttachmentsDownloader::run` (and/or in `extend_with_attachments`/`decode_atlas_get_attachment`), verify `attachment.hash() == request.content_hash` (the `H` that was actually requested) before accepting, storing, or using the response. Reject/penalize (bump `report.bump_failed_requests()`, and blacklist the peer) any response whose content hash does not match the requested hash, and retry the same `content_hash` against a different peer within the same batch pass rather than silently treating the mismatched attachment as if it were unrelated data.

### Proof of Concept
Rust test plan (in `stackslib/src/net/atlas` test module or a new integration test):
1. Set up an `AttachmentsBatchStateContext`/`AttachmentsDownloader` with two peers: one "honest" peer that will genuinely serve `Attachment{content: preimage_of(H)}` for `/v2/attachments/{H}`, and one "malicious" peer.
2. Have both peers respond to the `AttachmentsInventoryRequest` claiming to have `H` available (set the inventory bit for `H`'s page/position in `GetAttachmentsInvResponse`).
3. Ensure ordering/reliability causes the malicious peer to be selected as `get_most_reliable_source()` for the `AttachmentRequest` for `H` (e.g., give it a strictly better initial `ReliabilityReport`, or process its `succeeded` HTTP response first in `BatchedRequestsState::PollRequests`).
4. Have the malicious peer's HTTP handler return a `GetAttachmentResponse { attachment: Attachment::new(b"attacker bytes".to_vec()) }` (hash `B ≠ H`) for the request meant for `H`.
5. Call `AttachmentsDownloader::run(...)` to completion (drive the state machine through `Done`).
6. Assert:
   - `network.atlasdb.find_all_attachment_instances(&H)` still returns the original `AttachmentInstance` for `H` (i.e., it was never resolved/removed) — showing `attachments_batch.attachments_instances` still contains `H` after `run()`.
   - The `resolved_attachments` vector returned by `run()` does not contain an entry keyed on `H`.
   - `context.attachments_batch.retry_count` was incremented (via `bump_retry_count()`), and the batch is either re-queued or eventually dropped after `max_attachment_retry_count` retries, at which point `H` is permanently unresolved even though the honest peer had the correct attachment content the whole time.

    pub fn get_prioritized_attachments_requests(&self) -> BinaryHeap<AttachmentRequest> {
        let mut queue = BinaryHeap::new();
        let mut enqueued = HashSet::new();
        for ((contract_id, pages, _), peers_responses) in self.inventories.iter() {
            let missing_attachments = match self
                .attachments_batch
                .attachments_instances
                .get(contract_id)
            {
                None => continue,
                Some(missing_attachments) => missing_attachments,
            };
            // Note: we're getting missing_attachments (attachment_id: content_hash)
            for (attachment_index, content_hash) in missing_attachments.iter() {
                let page_index = attachment_index / AttachmentInstance::ATTACHMENTS_INV_PAGE_SIZE;
                // Since there's a limit in the number of pages that a node can request,
                // we can potentially have multiple inventory request at once.
                if !pages.contains(&page_index) {
                    continue;
                }

                if enqueued.contains(content_hash) {
                    debug!("Atlas: {} already enqueued", content_hash);
                    continue;
                }

                let mut sources = HashMap::new();
                let position_in_page =
                    attachment_index % AttachmentInstance::ATTACHMENTS_INV_PAGE_SIZE;

                for (peer_url, response) in peers_responses.iter() {
                    // Considering the response, look for the page with the index
                    // we're looking for.
                    let search_page = response.pages.iter().find(|page| page.index == page_index);

                    let has_attachment = search_page
                        .and_then(|search_page| {
                            search_page.inventory.get(position_in_page as usize)
                        })
                        .map(|result| *result == 1)
                        .unwrap_or(false);

                    if !has_attachment {
                        debug!(
                            "Atlas: peer does not have attachment ({}, {}) in its inventory {:?}",
                            page_index, position_in_page, response.pages
                        );
                        continue;
                    }

                    let report = self
                        .peers
                        .get(peer_url)
                        .expect("Atlas: unable to retrieve reliability report for peer");
                    sources.insert(peer_url.clone(), report.clone());
                }

                if sources.is_empty() {
                    warn!("Atlas: could not find a peer including attachment in its inventory");
                    continue;
                }

                // Success, we found at least one inventory including the attachment we're looking for.
                let request = AttachmentRequest {
                    sources,
                    content_hash: content_hash.clone(),
                    stacks_block_height: self.attachments_batch.stacks_block_height,
                    canonical_stacks_tip_height: self.attachments_batch.canonical_stacks_tip_height,
                };
                enqueued.insert(content_hash);
                queue.push(request);
            }
        }
        queue
    }

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }
