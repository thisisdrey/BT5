### Title
RewardsDistributor `uint32` timestamp truncation permanently DoSes all reward-tracking token operations - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
The external bug class is a crash caused by incorrect bounds checking on a timestamp field (Wireshark `vwr.c` signature-timestamp bounds). The Metronome analog is `RewardsDistributor._calculateTokenIndex`/`_updateTokenIndex`, which store `block.timestamp` into a `uint32` `TokenState.timestamp` via `SafeCast.toUint32()`. Once `block.timestamp` exceeds `type(uint32).max` (2106-02-07), every code path that touches a tracked deposit/debt token reverts inside `_updateTokenIndex`, permanently freezing deposits, withdrawals, transfers, borrows, repays, and reward claims for any token registered with a non-zero speed.

### Finding Description
`TokenState.timestamp` is declared `uint32` and is written with `block.timestamp.toUint32()` in `_calculateTokenIndex` (lines 208, 210) and `_updateTokenSpeed` (lines 298, 302). `SafeCast.toUint32` reverts on values above `2^32 - 1`, so the bounds check is performed on the wrong width for a real-world timestamp: the protocol has no mechanism to migrate the field or bypass the cast once the wall-clock exceeds the bound. The revert propagates through `_updateTokenIndex` into every public entry point that touches reward state:

- `RewardsDistributor.updateBeforeMintOrBurn` / `updateBeforeTransfer` (lines 175–192), which are invoked by the `updateRewardsBeforeMintOrBurn` modifier on `DebtToken` (contracts/DebtToken.sol:114-121) and the analogous hook on `DepositToken` before every mint, burn, and transfer.
- `RewardsDistributor.claimRewards` (lines 141–168).
- `syncTokenSpeed` (line 333) — the only recovery-adjacent path — also reverts, since it calls `_updateTokenSpeed` → `_updateTokenIndex` when `_currentSpeed > 0`.

Because the failing check is inside a modifier wrapped around state-changing token operations, there is no privileged or unprivileged escape: a governor cannot even set the speed back to 0, because `_updateTokenSpeed` calls `_updateTokenIndex` first while `_currentSpeed > 0` (line 293).

### Impact Explanation
Permanent freezing of funds. Once `block.timestamp` crosses `2^32`, any deposit token or debt token that has a nonzero `tokenSpeeds` entry can no longer be minted, burned, or transferred — `DepositToken.withdraw`, `DebtToken.issue`/`repay`, `Pool.liquidate`, and `claimRewards` all revert. All collateral and debt positions tracked by such tokens are permanently locked in the protocol. This is the same failure shape as the reference bug: an inadequately-bounded timestamp check turns into a hard crash (revert) on a code path that cannot be skipped.

### Likelihood Explanation
Certain to trigger eventually on any pool that registers reward speeds, but only after the `uint32` boundary (~year 2106). No attacker action, privileged role, or external condition is required — the failure is purely a function of wall-clock time. Likelihood is therefore low in practical terms but nonzero and unconditional, which is why severity is bounded.

### Recommendation
Widen `TokenState.timestamp` to `uint64` (or `uint256`) in `RewardsDistributorStorage` and drop the `toUint32()` casts, matching how `DebtToken.lastTimestampAccrued` stores `block.timestamp` un-truncated. If the storage layout must be preserved, replace the `SafeCast` casts with `uint32(block.timestamp)`-style wrapping plus modulo-`2^32` delta math (`uint32(uint256(block.timestamp) - _supplyState.timestamp)`), which stays correct across the boundary — the exact class of fix applied in the upstream advisory.

### Proof of Concept
Hardhat, fork or local deploy:

```ts
// Setup: pool, depositToken, rewardsDistributor initialized;
// governor calls rewardsDistributor.updateTokenSpeed(depositToken, 1e18)
// so tokenStates[depositToken] = {index: 1e18, timestamp: now32}.

// Warp past the uint32 bound
await network.provider.send("evm_setNextBlockTimestamp", [2 ** 32]);
await network.provider.send("evm_mine");

// Any operation that touches reward accounting reverts inside
// _calculateTokenIndex at `block.timestamp.toUint32()`
await expect(
  depositToken.transfer(alice.address, 1) // calls updateBeforeTransfer
).to.be.reverted; // SafeCast: value doesn't fit in 32 bits

await expect(
  rewardsDistributor.claimRewards(user.address)
).to.be.reverted;

// Recovery is also blocked: speed can't be set to 0 because
// _updateTokenSpeed -> _updateTokenIndex reverts first
await expect(
  rewardsDistributor.connect(governor).updateTokenSpeed(depositToken, 0)
).to.be.reverted;
```

The revert originates at `contracts/RewardsDistributor.sol:208`/`210` (`block.timestamp.toUint32()`), reachable via `updateBeforeMintOrBurn`/`updateBeforeTransfer` invoked from `DebtToken`/`DepositToken` token movements — no privileged attacker action required.
