### Title
Cross-StackerDB signature replay due to missing contract-id binding in `SlotMetadata::auth_digest` - ([File: libstackerdb/src/libstackerdb.rs])

### Summary
`SlotMetadata::auth_digest` only hashes `slot_id || slot_version || data_hash` and never binds the target `smart_contract_id`/replica identity. `StackerDBs::validate_received_chunk` then calls `slot_metadata.verify(&addr)` using an address resolved solely from the target contract's own `signers` config, so a signature legitimately produced for slot `N` in contract A is equally valid for slot `N` in contract B whenever the same signer address occupies that slot in both configs.

### Finding Description
The signed digest is constructed in `SlotMetadata::auth_digest` (libstackerdb/src/libstackerdb.rs:160-166):
```
hasher.update(self.slot_id.to_be_bytes());
hasher.update(self.slot_version.to_be_bytes());
hasher.update(self.data_hash.0);
```
No contract identifier, replica identity, or chain-view value is included. `StackerDBs::validate_received_chunk` (stackslib/src/net/stackerdb/mod.rs:649-717) resolves the expected signer independently, purely from the *target* contract's config: `self.stackerdbs.get_slot_signer(smart_contract_id, data.slot_id)` (mod.rs:680-682), then calls `slot_metadata.verify(&addr)` (mod.rs:691), which only checks that the recovered pubkey hash matches `addr` — it has no notion of which contract the signature was originally produced for.

`handle_unsolicited_StackerDBPushChunk` (mod.rs:742-807) calls `validate_received_chunk` with `chunk_data.contract_id` taken directly from the attacker-supplied `StackerDBPushChunkData`, and the `expected_versions`/config are also looked up per that same wire-supplied `contract_id`. Thus if an attacker's key is registered as the slot-`N` signer in both contract A and contract B (a plausible configuration, e.g. reward-cycle StackerDB configs derived from the same signer set), a `StackerDBChunkData` legitimately signed and pushed for contract A's slot `N` is accepted verbatim when relabeled with `contract_id = B` in the `StackerDBPushChunkData` envelope, because the signature check only asks "did this address sign (slot_id, slot_version, data_hash)?" and never "was this signed *for contract B*?".

### Impact Explanation
An attacker who legitimately owns the same slot index in two StackerDB replicas can inject a chunk into contract B's replica using a signature/content pair that was only ever authorized for contract A. Successful validation leads to storage via `try_replace_chunk` and network-wide re-broadcast through `PeerNetwork::process_stacker_db_chunks` (stackslib/src/net/relay.rs:2385-2412) and `broadcast_message`, propagating the cross-replica forged chunk to all peers replicating contract B. This is an unauthenticated write of attacker-controlled data into a StackerDB the attacker was never authorized to write that specific content to for that slot in that DB context (data crafted/authorized under a different trust boundary), repeated on every push.

### Likelihood Explanation
Requires the attacker to genuinely hold a private key that is a slot signer for the same slot index in two distinct `StackerDBConfig`s (contracts A and B) simultaneously — a precondition dependent on config/signer-set overlap, which is realistic for related StackerDB contracts (e.g. multiple StackerDB instances tied to the same signer set/reward cycle). No privileged role, RPC secret, or other peer's key is needed; the attacker only needs P2P connectivity to send a crafted `StackerDBPushChunk` message, matching a remote-unprivileged threat model. The exploit is fully repeatable per push.

### Recommendation
Bind the target StackerDB identity into the signed digest, e.g. include `smart_contract_id` (and ideally the contract's expected reward-cycle/config epoch) in `SlotMetadata::auth_digest`, or otherwise scope signature verification so that a signature is only valid for the specific contract/replica it was produced for.

### Proof of Concept

1. Construct two `QualifiedContractIdentifier`s (A, B) and two `StackerDBConfig`s whose `signers` list both map slot 3 to the same `StacksAddress` derived from a single `StacksPrivateKey`.
2. Build a `StackerDBChunkData { slot_id: 3, slot_version: 1, data: b"evil".to_vec(), .. }`, compute `get_slot_metadata()`, call `.sign(&privkey)` — this signs the chunk intending contract A.
3. Call `StackerDBs::validate_received_chunk(&contract_b_id, &config_b, &chunk_data, &expected_versions_b)`.
