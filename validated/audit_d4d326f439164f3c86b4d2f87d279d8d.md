Confirmed: `execute_intents` calls `.unwrap_or_else(|e| e.panic())` on the `Result` from `execute_signed_intents`, so any `Err` returned (including `DefuseError::InvalidIntent` from the zero-delta check) causes a host-level panic, which reverts all state changes made in that NEAR contract call, including any `internal_apply_deltas` and fee-collection side effects that already ran for earlier entries in the same `TokenDiff` loop. [1](#0-0) 

The runtime check `if *delta == 0 { return Err(DefuseError::InvalidIntent); }` is evaluated per entry, as the very first statement of the loop body, *before* `internal_apply_deltas` or fee accounting for that entry. [2](#0-1) 

This check operates directly on the deserialized `self.diff: TokenDeltas` (a `BTreeMap<TokenId, i128>`), independent of whether the map was produced via `with_apply_deltas` or via raw hand-crafted JSON — the check does not rely on any invariant established at construction time. Standard `serde_json`/BTreeMap deserialization of an object cannot represent two different values for the same key simultaneously; a literal duplicate JSON key is resolved by the parser (last-value-wins) before the map is even built, so there is no way for both a "cancelling" pair and a surviving zero entry to coexist for the same `TokenId` in the deserialized `BTreeMap`. Any zero entry that does end up in the map — however it was crafted — is caught by this exact runtime guard.

Given the panic-on-error semantics of `execute_intents`, the binding the question worries about — "unauthorized zero-value entries mask fee/accounting side effects" — cannot occur: the guard fires before any balance or fee mutation for that entry, and hitting it aborts and reverts the whole transaction via `.panic()`, undoing any partial mutations from earlier entries in the same diff or earlier intents in the batch. There is no code path where a zero-delta entry in `TokenDiff::diff` results in a state change, fee collection, or masked accounting effect — it always results in a full revert.

I could not find any way to bypass this per-entry check via nested/duplicate JSON keys, since serde's map deserialization structurally prevents duplicate-key coexistence, and I found no alternate deserialization path for `TokenDiff::diff` other than the one shown at `contracts/defuse/core/src/intents/token_diff.rs:31-32` guarded by the same loop check.
