### Title
Gas-key transactions bypass NEP-611 deploy exclusivity checks in `PendingTxSession::check_pending` - (chain/client/src/pending_transaction_queue.rs)

### Summary
`PendingTxSession::check_pending` wraps its entire deploy-exclusivity enforcement (`total_deploy_count > 0` and `tx_has_deploy && total_access_key_count > 0`) inside an `if !is_gas_key_tx { ... }` block, so a transaction submitted with `nonce_index = Some(_)` (a gas-key transaction) is never checked against these invariants regardless of what is already pending for the same account. [1](#0-0) 

### Finding Description
`check_pending` computes `tx_has_deploy = has_deploy_action(tx.transaction.actions())` and `total_access_key_count`/`total_deploy_count` unconditionally, but only enforces exclusivity for non-gas-key transactions: [2](#0-1) 

This means that if a gas-key transaction (`nonce_index.is_some()`) contains a `DeployContract` action, it skips both:
1. The check that a deploy cannot be admitted while `total_deploy_count > 0` (another deploy already pending).
2. The check that a deploy cannot be admitted while `total_access_key_count > 0` (a normal access-key tx is already pending for the same account).

Contrast this with the reverse direction, which *is* enforced: a normal access-key tx checks `total_deploy_count > 0`, and `total_deploy_count` is fed both by `PendingAccount.deploy_tx_count` (incremented unconditionally in `add_chunk_transactions`, not gated on `is_gas_key_tx`) and by `session_deploy_tx_counts` (also incremented unconditionally later in `check_pending`, at the `if tx_has_deploy { ... }` block). [3](#0-2) [4](#0-3) 

So the asymmetry is specifically: an *incoming* gas-key deploy transaction is never blocked by a pre-existing pending non-gas-key access-key tx (or a pre-existing pending deploy), even though the reverse case (a pending gas-key deploy blocking a *new* access-key tx) is correctly enforced — as demonstrated by the existing unit test `test_deploy_exclusivity_gas_key_deploy_blocks_access_key_tx`, which has no symmetric counterpart testing a gas-key deploy against a pre-existing access-key tx. [5](#0-4) 

Note: the specific mechanistic detail in the question that "`has_deploy_action(tx)` on the gas-key path never increments `session_deploy_tx_counts`" is not accurate — that increment (`if tx_has_deploy { ... }`) is unconditional and does apply to gas-key deploys. The actual root cause is narrower: the *admission check itself* (comparing against `total_access_key_count`/`total_deploy_count`) is skipped for the gas-key path, not the bookkeeping.

An important unresolved precondition: whether the runtime's transaction/action validation layer (`runtime/runtime/src/verifier.rs`, `runtime/runtime/src/access_keys.rs`, `runtime/runtime/src/action_validation.rs`) permits a `DeployContract` action to appear in a gas-key transaction at all, prior to or independent of `check_pending`. I was not able to fully confirm within the available tool budget whether gas-key transactions are restricted to `FunctionCall`-only actions elsewhere in the pipeline (which would make this specific attack path unreachable in practice even though `check_pending`'s logic is asymmetric). The existence of `make_gas_key_deploy_tx` as a first-class helper in the pending-transaction-queue test suite suggests such a transaction is at least constructible and accepted by `check_pending`, but end-to-end reachability through `verify_and_charge_gas_key_tx_ephemeral` and full runtime action validation was not verified.

### Impact Explanation
If gas-key `DeployContract` transactions are indeed permitted by the rest of the validation pipeline, this bypass allows an attacker's own account to have a deploy and a normal `FunctionCall` transaction admitted into the *same* chunk-production session simultaneously, violating the P_MAX/NEP-611 deploy-exclusivity guarantee that the pending transaction queue is designed to enforce (per the module doc comment describing "P_MAX / deploy exclusivity counts (per account)" as the invariant the session tracks). This risks: uncertified chunks containing a deploy and a call against pre-deploy code concurrently, and potential divergence in behavior if uncertified chunks are reordered/replayed across nodes, which the question characterizes as at minimum a P_MAX/NEP-611 guarantee bypass. [6](#0-5) 

Given the unresolved precondition above, I cannot confirm concrete fund loss, token inflation, or state-root divergence — the impact is scoped to a guarantee bypass in the pending-transaction-queue's exclusivity invariant, contingent on gas-key deploy transactions being otherwise valid.

### Likelihood Explanation
The attacker only needs an account with a full-access key and a provisioned gas key (both attainable by an ordinary user via normal account/gas-key provisioning flows), and to submit two transactions in the same chunk-production window: a gas-key `DeployContract` tx and a normal-access-key `FunctionCall` tx. This requires no validator/node privileges. The main uncertainty affecting real-world likelihood is whether `DeployContract` is a permitted action for gas-key transactions elsewhere in the codebase — this was not confirmed.

### Recommendation
Remove the `!is_gas_key_tx` gate around the deploy-exclusivity checks in `check_pending` (or perform an equivalent check for gas-key deploy transactions), so that any transaction containing a `DeployContract` action — gas-key or not — is checked against `total_deploy_count` and `total_access_key_count` before being admitted. Additionally, verify at the action-validation layer whether `DeployContract` should be a permitted action inside a gas-key transaction at all.

### Proof of Concept
Add a unit test in `chain/client/src/pending_transaction_queue.rs` mirroring `test_deploy_exclusivity_pending_access_key_tx_blocks_deploy`, but using a gas-key deploy tx as the incoming transaction:
1. `add_chunk_txs` with a normal (non-gas-key) `transfer_tx` from `signer` pending.
2. Call `session.check_pending(&make_gas_key_deploy_tx(&signer, nonce, 0), HasContract::No)`.
3. Expected (per invariant): `PendingTxCheckResult::Skip`.
4. Actual (current code): `PendingTxCheckResult::Admit(_)`, demonstrating the asymmetric bypass.

    fn test_deploy_exclusivity_gas_key_deploy_blocks_access_key_tx() {

        // A gas key tx with a deploy action is pending.
        add_chunk_txs(

        let mut session = make_session(&sharded);
        let transfer_tx = make_transfer_tx(&signer, "bob.near", 2, TEST_DEPOSIT);

            PendingTxCheckResult::Skip

        // But another gas key tx should still be admitted.
