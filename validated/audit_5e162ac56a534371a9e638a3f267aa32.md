## Title
Old-algorithm reward computation divides before multiplying, causing systematic reward under-payment and unaccounted dust — (File: chainbase/src/main/java/org/tron/core/service/MortgageService.java)

### Summary
The legacy ("old algorithm") per-cycle reward computation in `MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)` divides `userVote` by `totalVote` **before** multiplying by `totalReward`, exactly the divide-then-multiply pattern flagged in the reported Olympus finding. This truncates precision on every voter/cycle pair, so a delegator receives less than their exact proportional share and the difference is left unaccounted in the reward pool.

### Finding Description
`computeReward` computes each voter's share of a super representative's cycle reward as: [1](#0-0) 

```java
private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
  long reward = 0;
  for (Pair<byte[], Long> vote : votes) {
    ...
    long userVote = vote.getValue();
    double voteRate = (double) userVote / totalVote;   // divide first
    reward += voteRate * totalReward;                  // multiply second
  }
  return reward;
}
```

This is the same divide-before-multiply anti-pattern as the reported `internalRewardsForToken` bug: `voteRate` is computed and truncated to a `double` before being multiplied by `totalReward`, instead of computing `userVote * totalReward / totalVote` in one higher-precision step. Note that java-tron's *newer* VI-based algorithm (`VoteRewardUtil.computeReward`, `RewardViCalService.getNewRewardAlgorithmReward`, and the second `MortgageService.computeReward(beginCycle, endCycle, ...)` overload) correctly multiplies with `BigInteger` before dividing: [2](#0-1) 

— but the *old* per-cycle path at lines 171-188 was never fixed to follow the same multiply-then-divide order, and remains reachable through `getOldReward`: [3](#0-2) 

```java
private long getOldReward(long begin, long end, List<Pair<byte[], Long>> votes) {
  if (dynamicPropertiesStore.allowOldRewardOpt()) {
    return rewardViCalService.getNewRewardAlgorithmReward(begin, end, votes);
  }
  long reward = 0;
  for (long cycle = begin; cycle < end; cycle++) {
    reward += computeReward(cycle, votes);   // legacy divide-then-multiply path
  }
  return reward;
}
```

This legacy path is invoked whenever a beginCycle predates `getNewRewardAlgorithmEffectiveCycle()` and `allowOldRewardOpt` is not enabled, via `computeReward(beginCycle, endCycle, accountCapsule)`: [4](#0-3) 

It is reachable from unprivileged, transaction/API surfaces:
- `WithdrawBalanceActuator.execute`, triggered by a broadcast `WithdrawBalanceContract` transaction: [5](#0-4) 
- `queryReward`/`withdrawReward` exposed over HTTP via `GetRewardServlet` and over gRPC via `RpcApiService` (both call `mortgageService.queryReward`).
- The TVM `withdrawReward` opcode path (`VoteRewardUtil`/`Program.withdrawReward`), for contract-initiated calls.

### Impact Explanation
For every vote/cycle combination processed through the legacy `double` path, the computed `voteRate * totalReward` truncates fractional sun that would otherwise be owed to the voter. Because `double` has only ~15-17 significant decimal digits and TRX amounts routinely reach into the 10^14-10^17 sun range for large SRs/pools, the truncation is not just a 1-2 wei rounding artifact (as in the Solidity report) — it can systematically under-pay many voters across many cycles, and the truncated remainder is never credited to anyone, permanently freezing/losing a portion of reward funds inside the delegation reward pool. This matches the "loss of precision for user rewards" / "protocol accounted for less" impact class from the referenced report, translated to java-tron's staking reward accounting.

### Likelihood Explanation
Reachable by any account voting for witnesses and withdrawing rewards for cycles that pre-date `getNewRewardAlgorithmEffectiveCycle` while `allowOldRewardOpt` is disabled — no special privilege is required, just a standard `WithdrawBalanceContract` transaction or a `queryReward` API call. The condition is deterministic (chain-parameter controlled) rather than requiring any attacker-crafted input, so any node/chain configuration where the old algorithm path is still active for historical cycles will exhibit the loss on every affected withdrawal.

### Recommendation
In `MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)`, replace the `double`-based `voteRate` computation with an integer-only multiply-then-divide (ideally via `BigInteger`, mirroring the pattern already used in the VI-based reward paths), e.g. `BigInteger.valueOf(totalReward).multiply(BigInteger.valueOf(userVote)).divide(BigInteger.valueOf(totalVote))`, so multiplication happens before division and precision is preserved consistently with the newer reward algorithm.

### Proof of Concept
Given `totalReward = 100000026`, `totalVote = 2700000729` (sum of 27 SR's votes as in `DelegationServiceTest.testPay`), and a voter with `userVote = 100000000`:
- Old (buggy) order: `voteRate = (double)100000000 / 2700000729 ≈ 0.037037...` (already truncated to double precision) then `reward = (long)(voteRate * 100000026)` — the fractional information lost in the intermediate `double` division is never recovered.
- Correct order: `reward = (100000000L * 100000026L) / 2700000729L` computed as a single integer/BigInteger operation, preserving maximal precision until the single final truncation.

Across the 27 SR / multi-cycle scenario exercised in `DelegationServiceTest.testPay`/`testWithdraw` [6](#0-5) , repeated double-based `voteRate` computations accumulate rounding loss identical in nature to the referenced Sherlock finding.
