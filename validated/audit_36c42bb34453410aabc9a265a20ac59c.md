### Title
Malicious `tokenIn_` executes arbitrary calls as `SmartFarmingManager`, enabling unbacked `flashIssue` minting - ([File: contracts/SmartFarmingManager.sol](contracts/SmartFarmingManager.sol))

### Summary
`SmartFarmingManager.leverage()` accepts an arbitrary `IERC20 tokenIn_` argument and calls `tokenIn_.safeTransferFrom(_msgSender, address(this), amountIn_)`. A malicious token's `transferFrom` therefore executes a callback where `msg.sender == SmartFarmingManager`. Because `SmartFarmingManager` is a privileged actor (`onlyIfSmartFarmingManager` on `DebtToken.flashIssue`, `DebtToken.mint`, `DepositToken.flashWithdraw`, etc.), the attacker's token code can call `DebtToken.flashIssue(attacker, amount)` to mint synthetic tokens with zero debt, swap them through `Pool.swap` for real collateral, and still pass the final health check. This is the direct analog of the SpEL-injection bug class: attacker-supplied input (the token address) reaches a trusted identity's privileged call surface.

### Finding Description
- `leverage()` validates `depositToken_` and `syntheticToken_` but performs no validation on `tokenIn_` (only the `address(0)` → collateral defaulting at line 180). [SmartFarmingManager.sol:155-181](contracts/SmartFarmingManager.sol)
- `_safeTransferFrom` calls `token_.safeTransferFrom(from_, address(this), amount_)`, which executes attacker-controlled code while `msg.sender` is the `SmartFarmingManager` contract itself (lines 257-260).
- During that callback the attacker can call `IDebtToken(pool.debtTokenOf(synth)).flashIssue(attacker, X)`, which is gated to the SFM and mints `X` synthetic tokens to `attacker` **without recording any debt** (that's the design: `leverage` pairs `flashIssue` with `mint` for debt separately, lines 191-192).
- The attacker then calls `pool.swap(synth → collateral)` inside the same callback, converting unbacked synth into real collateral held in the Pool.
- `nonReentrant` on `leverage` only blocks reentry into `SmartFarmingManager`; `ReentrancyGuardTransient`/`ReentrancyGuardDeprecated` locks are per-contract, so calls into `DebtToken` and `Pool` succeed.
- The final `pool.debtPositionOf(_msgSender)` health check (line 207) measures only the attacker's own debt/deposit. The flash-minted synth never registered as attacker debt, so the check passes trivially (the attacker can even pass a tiny `amountIn_` with `leverage_` just above `1e18`).

### Impact Explanation
Direct protocol insolvency / theft of user funds: synthetic supply is inflated without corresponding debt, and the proceeds are swapped out as real collateral backing other users' deposits. Profit is bounded only by `maxTotalSupply` caps and pool liquidity. No governor, keeper, oracle manipulation, or privileged role is required — only a deployed malicious ERC20 passed as `tokenIn_`.

### Likelihood Explanation
High: `leverage` is a public, unprivileged entry point deployed on mainnet/optimism/base/hemi. `tokenIn_` is explicitly user-chosen and the tests confirm arbitrary tokens are accepted (defaulting only when `address(0)`). The only precondition is deploying a malicious token and satisfying `amountIn_ > 0`, `leverage_ > 1e18`.

### Recommendation
- Reject arbitrary `tokenIn_` values; whitelist tokens to the deposit token's `underlying()` or a registry-approved list.
- Alternatively, perform the `transferFrom` via a non-privileged intermediary, or add a transient reentrancy lock shared across privileged callbacks (`DebtToken.flashIssue`/`mint` should revert when called inside an untrusted external call window).
- Disallow `flashIssue`/`mint` from being called when the SFM is executing inside an external token callback (e.g., a reentrancy guard covering the whole SFM call frame exposed to tokens).

### Proof of Concept (Hardhat, fork)
```solidity
// Attacker deploys:
contract EvilToken is ERC20 {
    ISmartFarmingManager sfm; IPool pool; ISyntheticToken synth;
    function transferFrom(address, address, uint256) external override returns (bool) {
        // msg.sender == SmartFarmingManager
        IDebtToken debt = pool.debtTokenOf(synth);
        (uint256 minted,) = debt.flashIssue(address(this), CAP); // unbacked mint
        synth.approve(address(pool), minted);
        pool.swap(synth, COLLATERAL, minted, 0); // drains real collateral
        return true;
    }
}

// Then:
sfm.leverage(IERC20(evil), depositToken, synth, 1 ether, 1.01 ether, 0);
// Assert: attacker holds collateral, attacker debt == ~0, synth supply inflated.
```
`flashRepay` is not exploitable the same way (tokens are registry-validated), but `leverage`'s unconstrained `tokenIn_` is the reachable surface. Confidence is high on the call path; the exact `flashIssue`/`mint` modifier names (`onlyIfSmartFarmingManager` / `onlyIfCanMint`) are confirmed present in `DebtToken.sol`/`SyntheticToken.sol` via grep, though final line-level reading of those modifiers was not completed in this pass.
