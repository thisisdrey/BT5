### Title
Account-level permission escalation via `AccountPermissionUpdateContract` allows a limited Active-permission key to rewrite the Owner permission and seize full account control - (File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java)

### Summary
`AccountPermissionUpdateActuator` lets any signature that satisfies a valid permission on an account (Owner, Witness, or an Active permission whose operation bitmap includes `AccountPermissionUpdateContract`) completely replace the account's Owner permission, Witness permission, and all Active permissions in a single transaction. The actuator's `validate()`/`checkPermission()` only sanity-checks the *new* permission structure (key count, threshold, distinct addresses, valid operation bits) but never compares the newly-proposed permission set against the authority of the permission that authorized the change. This mirrors the CVE-2017-0883 class of bug: a principal holding a narrower, delegated permission (analogous to a "read-only" share) can use the very operation that was delegated to them (re-share/update) to grant themselves (or any other key) a strictly larger permission set (analogous to "edit" or full ownership), because the sharing/update primitive does not clamp new permissions to be no greater than the grantor's own authority.

### Finding Description
Java-tron's multi-sig model allows the true account Owner to grant an Active permission to a secondary key and restrict what that key may do via a 256-bit operation bitmap (`Permission.operations`), checked bit-by-bit against `ContractType` ordinals [1](#0-0) . If the Owner ever grants that Active permission the single bit corresponding to `AccountPermissionUpdateContract` (e.g., to let a hot-wallet/operations key rotate its own signing key), the signature-authority check in `TransactionCapsule.checkPermission()`/`addSign()` only verifies that this specific contract type is enabled for that permission id — it performs no further restriction on the contents of the resulting `AccountPermissionUpdateContract` [2](#0-1) .

Once that gate is passed, `AccountPermissionUpdateActuator.validate()` performs only structural checks on the submitted `owner`, `witness`, and `actives` permissions (key distinctness, weight/threshold sanity, valid operation bits) [3](#0-2) , and `execute()` unconditionally overwrites the account's entire permission set with whatever was submitted, with no comparison to the previous Owner permission, no requirement that the signer's own keys/weights be preserved, and no check that the new Owner/Active permission's `keys`/`threshold`/`operations` are bounded by the authority of the permission that signed the transaction [4](#0-3) [5](#0-4) .

Consequently, a holder of a narrowly-scoped Active permission — who was only ever intended to be able to trigger permission rotations for their own key — can instead submit a completely new Owner permission (e.g., set threshold to 1, add their own key with dominant weight, and remove the legitimate co-signers), and can likewise rewrite every Active permission, including granting themselves an operations bitmap covering `TransferContract`, `TransferAssetContract`, `WithdrawBalanceContract`, `TriggerSmartContract`, etc. This directly parallels CVE-2017-0883, where a party holding only a limited (read) permission used the re-share/update API to grant itself an unrestricted (write) permission — the shared root cause is that the "update permission" operation does not clamp the requested permission set to the acting principal's own authority.

### Impact Explanation
Exploitation converts a deliberately narrow delegation (e.g., an automated key permitted only to co-sign key-rotation transactions) into full, unilateral control of the target account, including its Owner permission. This enables the attacker to permanently lock out the legitimate account owner/co-signers by rewriting the Owner and Active permission threshold/keys, and then to authorize arbitrary transfers, asset operations, staking/voting, and contract calls, resulting in theft or permanent freezing of the account's funds. Because `AccountPermissionUpdateContract` is a normal broadcastable contract reachable by any signed transaction that satisfies an existing permission on the account, this is directly reachable by an unprivileged signer that has been granted even a minimal slice of authority — no committee/witness/node compromise is required.

### Likelihood Explanation
Exploitation requires that the true account owner has, at some point, granted an Active permission the `AccountPermissionUpdateContract` operation bit — a plausible and even encouraged configuration (used for self-service key rotation, hot-wallet key refresh, delegated administration) under TRON's documented multi-sig model. Once that grant exists, exploitation is a single, unprivileged, fully deterministic transaction (`AccountPermissionUpdateContract`) with no additional preconditions (no timing windows, no race conditions, no on-chain governance approval). This is analogous to the "medium/authenticated, low complexity" characterization of CVE-2017-0883 (CVSS AV:N/AC:L/PR:L).

### Recommendation
In `AccountPermissionUpdateActuator.validate()` (and/or in `TransactionCapsule.checkPermission()`), when the signing permission id is not the account's Owner permission (`permissionId != 0`), enforce that the resulting Owner permission, Witness permission, and every Active permission cannot grant broader authority than the signing Active permission itself possesses — e.g., disallow a non-Owner-signed `AccountPermissionUpdateContract` from modifying the Owner permission at all, or require that any new/edited permission's operation bitmap be a subset of the signing permission's bitmap and that the signer's own key/weight in the resulting permission not be reduced/removed by a permission with lesser authority. At minimum, restrict the `AccountPermissionUpdateContract` operation bit so it can only be effectively exercised via the Owner permission, consistent with least-privilege for delegated Active permissions.

### Proof of Concept
1. Account `A` (Owner key `K_owner`) creates an Active permission `P1` with `threshold=1`, containing only key `K_ops` with weight 1, and sets `P1.operations` to allow only `AccountPermissionUpdateContract` (bit set) and no other contract type.
2. `A` submits `AccountPermissionUpdateContract` (signed by `K_owner`, permission id 0) to install this configuration via `AccountPermissionUpdateActuator.execute()` [6](#0-5) .
3. The holder of `K_ops` (an "unprivileged" delegate) now crafts a new `AccountPermissionUpdateContract` for account `A`, setting: `owner = {threshold:1, keys:[{address:K_ops, weight:1}]}` (dropping `K_owner` entirely), and an Active permission with an operations bitmap that enables `TransferContract`/`TransferAssetContract`/etc.
4. The delegate signs this transaction with `K_ops` using `permission_id = P1.id`. `TransactionCapsule.addSign()`/`checkPermission()` accept the signature because `P1.operations` includes `AccountPermissionUpdateContract` [7](#0-6) .
5. `AccountPermissionUpdateActuator.validate()` passes because all structural checks (`checkPermission` on the new Owner/Active permissions) only validate the new permission's internal consistency, not its relationship to `P1`'s authority [8](#0-7) .
6. `execute()` overwrites account `A`'s Owner and Active permissions via `AccountCapsule.updatePermissions()` [5](#0-4) , giving `K_ops` sole Owner control and unrestricted transaction authority over account `A`, permanently excluding the original owner `K_owner`.

      logger.debug(e.getMessage(), e);
      result.setStatus(fee, code.FAILED);
      throw new ContractExeException(e.getMessage());

  @Override
  public boolean validate() throws ContractValidateException {

    if (chainBaseManager == null) {
      throw new ContractValidateException(ActuatorConstant.STORE_NOT_EXIST);
    }

    if (this.any == null) {
      throw new ContractValidateException(ActuatorConstant.CONTRACT_NOT_EXIST);
    }

    AccountStore accountStore = chainBaseManager.getAccountStore();
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();

    if (dynamicStore.getAllowMultiSign() != 1) {
      throw new ContractValidateException("multi sign is not allowed, "
          + "need to be opened by the committee");
    }
    if (!this.any.is(AccountPermissionUpdateContract.class)) {
      throw new ContractValidateException(
          "contract type error,expected type [AccountPermissionUpdateContract],real type["
              + any.getClass() + "]");
    }
    final AccountPermissionUpdateContract accountPermissionUpdateContract;
    try {
      accountPermissionUpdateContract = any.unpack(AccountPermissionUpdateContract.class);
    } catch (InvalidProtocolBufferException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractValidateException(e.getMessage());
    }
    byte[] ownerAddress = accountPermissionUpdateContract.getOwnerAddress().toByteArray();
    if (!DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("invalidate ownerAddress");
    }
    AccountCapsule accountCapsule = accountStore.get(ownerAddress);
    if (accountCapsule == null) {
      throw new ContractValidateException("ownerAddress account does not exist");
    }

    if (!accountPermissionUpdateContract.hasOwner()) {
      throw new ContractValidateException("owner permission is missed");
    }

    if (accountCapsule.getIsWitness()) {
      if (!accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("witness permission is missed");
      }
    } else {
      if (accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("account isn't witness can't set witness permission");
      }
    }

    if (accountPermissionUpdateContract.getActivesCount() == 0) {
      throw new ContractValidateException("active permission is missed");
    }
    if (accountPermissionUpdateContract.getActivesCount() > 8) {
      throw new ContractValidateException("active permission is too many");
    }

    Permission owner = accountPermissionUpdateContract.getOwner();
    Permission witness = accountPermissionUpdateContract.getWitness();
    List<Permission> actives = accountPermissionUpdateContract.getActivesList();

    if (owner.getType() != PermissionType.Owner) {
      throw new ContractValidateException("owner permission type is error");
    }
    checkPermission(owner);
    if (accountCapsule.getIsWitness()) {
      if (witness.getType() != PermissionType.Witness) {
        throw new ContractValidateException("witness permission type is error");
      }
      checkPermission(witness);
    }
    for (Permission permission : actives) {
      if (permission.getType() != PermissionType.Active) {
        throw new ContractValidateException("active permission type is error");
      }
      checkPermission(permission);
    }
    return true;

  public void addSign(byte[] privateKey, AccountStore accountStore)
      throws PermissionException, SignatureException, SignatureFormatException {
    Transaction.Contract contract = this.transaction.getRawData().getContract(0);
    int permissionId = contract.getPermissionId();
    byte[] owner = getOwnerAddress();
    AccountCapsule account = accountStore.get(owner);
    if (account == null) {
      throw new PermissionException("Account is not exist!");
    }
    Permission permission = account.getPermissionById(permissionId);
    if (permission == null) {
      throw new PermissionException("permission isn't exit");
    }
    checkPermission(permissionId, permission, contract);
    List<ByteString> approveList = new ArrayList<>();
    SignInterface cryptoEngine = SignUtils
        .fromPrivate(privateKey, CommonParameter.getInstance().isECKeyCryptoEngine());
    byte[] address = cryptoEngine.getAddress();
    if (this.transaction.getSignatureCount() > 0) {
      checkWeight(permission, this.transaction.getSignatureList(),
          this.getTransactionId().getBytes(),
          approveList);
      if (approveList.contains(ByteString.copyFrom(address))) {
        throw new PermissionException(encode58Check(address) + " had signed!");
      }
    }

    long weight = getWeight(permission, address);
    if (weight == 0) {
      throw new PermissionException(
          ByteArray.toHexString(privateKey) + "'s address is " + encode58Check(address)
              + " but it is not contained of permission.");
    }
    ByteString sig = ByteString.copyFrom(cryptoEngine.Base64toBytes(cryptoEngine
        .signHash(getTransactionId().getBytes())));
    this.transaction = this.transaction.toBuilder().addSignature(sig).build();
  }

  private static void checkPermission(int permissionId, Permission permission, Transaction.Contract contract) throws PermissionException {

      }

      }
    }
  }

  public void updatePermissions(Permission owner, Permission witness, List<Permission> actives) {
    Builder builder = this.account.toBuilder();

    owner = owner.toBuilder().setId(0).build();
    builder.setOwnerPermission(owner);
    if (witness != null && builder.getIsWitness()) {
      witness = witness.toBuilder().setId(1).build();
      builder.setWitnessPermission(witness);
    }

    builder.clearActivePermission();
    if (actives != null) {
      for (int i = 0; i < actives.size(); i++) {
        Permission permission = actives.get(i).toBuilder().setId(i + 2).build();
        builder.addActivePermission(permission);
      }
    }

    this.account = builder.build();
  }
