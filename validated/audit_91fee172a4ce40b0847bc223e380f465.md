### Title
Dust deposit/issue front-runs and permanently blocks `Pool.removeDepositToken`/`removeDebtToken` delisting - ([File: contracts/Pool.sol])

### Summary
`Pool.removeDepositToken` and `Pool.removeDebtToken` revert with `TotalSupplyIsNotZero` whenever the token's `totalSupply() > 0` at execution time (`contracts/Pool.sol:725-744`). This is the same bug class as the Arrakis report: removal is gated on a live, externally-manipulable quantity (here total token supply, there UniV3 position liquidity) read at the moment the removal transaction executes. Any unprivileged user can front-run the governor's removal transaction by minting 1 wei of the token — via `DepositToken.deposit` / `NativeTokenGateway` / `VesperGateway` for collaterals, or a borrow/`DebtToken.issue` path for debt tokens — making `totalSupply() > 0` and reverting the removal. The attacker can repeat this indefinitely at near-zero cost (dust capital, reclaimable), so a collateral/debt token can be prevented from ever being delisted, and its `depositTokenOf[underlying]` / `debtTokenOf[syntheticToken]` mapping can never be cleared. Since `addDepositToken` reverts with `UnderlyingAssetInUse` when the mapping is occupied, the underlying can never be re-registered under a fixed token contract either.

### Finding Description
In `Pool.sol`:

```solidity
function removeDebtToken(IDebtToken debtToken_) external onlyGovernor {
    if (debtToken_.totalSupply() > 0) revert TotalSupplyIsNotZero();
    ...
}
function removeDepositToken(IDepositToken depositToken_) external onlyGovernor {
    if (depositToken_.totalSupply() > 0) revert TotalSupplyIsNotZero();
    ...
}
```

`totalSupply()` reflects positions created through permissionless entry points (`DepositToken.deposit(amount_)`, gateway deposits, `DebtToken.issue`/borrow). An attacker watching the mempool can mint dust in the same block ahead of the removal tx. Unlike Arrakis's fix (`type(uint256).max` burns), there is no "force remove regardless of outstanding supply" path — the governor has no alternative entry point to delist a token while any holder exists.

### Impact Explanation
Delisting is a security-relevant governance operation: it is the mechanism to disable a collateral that has become dangerous (oracle manipulation risk, deprecated/ compromised vault-share collateral, a synthetic that must be sunset). A single griefer holding an indefinitely-renewable dust position can permanently veto delisting, keeping the risky token active for deposits, collateralization, swaps and `depositTokenOf` lookups. Because `UnderlyingAssetInUse` blocks re-adding the same underlying, a broken DepositToken cannot be replaced either. This is a permanent liveness denial of a governance function achieved purely through unprivileged front-running.

### Likelihood Explanation
Cost per grief is one dust deposit (~gas + 1 wei underlying). The attacker can use a contract that re-mints dust whenever its balance approaches withdrawal, or simply hold the dust permanently — the governor can never distinguish "real last holder" from the griefer, and there is no force-removal path. Any user with the underlying asset can execute it; no privileged role required.

### Recommendation
Do not gate removal on `totalSupply() == 0` read at execution time. Options mirroring the Arrakis fix: allow the governor to force-remove a token while disabling new deposits/mints (a `paused`/`delisted` flag that blocks `deposit`/`issue` but lets existing holders withdraw/repay), or require a two-step `delist → remove` where `delist` first halts all new supply so `totalSupply` can only decrease, making the dust front-run impossible.

### Proof of Concept
Hardhat-style sketch (against deployed `Pool` + `DepositToken` on a fork):

```ts
// given: depositToken with totalSupply == 0, governor tx pending
await underlying.mint(attacker.address, 1);
await underlying.connect(attacker).approve(depositToken.address, 1);

// attacker front-runs governor's removeDepositToken tx
await depositToken.connect(attacker).deposit(1); // mints 1 wei of depositToken

// governor tx now reverts
await expect(
  pool.connect(governor).removeDepositToken(depositToken.address)
).to.be.revertedWithCustomError(pool, 'TotalSupplyIsNotZero');

// repeat: attacker withdraws/re-deposits dust each time; delisting never succeeds
```

Note the residual uncertainty: whether "permanently blocking a governance delisting" meets your impact bar depends on treating delisting as a security function (no user funds are directly frozen). If the judges require direct fund impact, the weaker variant — dust transfers filling a victim's `depositTokensOfAccount`/`debtTokensOfAccount` up to `MAX_TOKENS_PER_USER` and reverting their subsequent deposits of new token types — exists but is self-mitigatable by the victim transferring the dust out, so it likely falls under "no impact".
