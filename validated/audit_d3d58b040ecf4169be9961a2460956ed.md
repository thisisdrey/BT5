### Title
Stale, previously-superseded StackerDB chunks can be replayed and accepted as canonical after slot reassignment resets the Lamport clock - ([File: stackslib/src/net/stackerdb/db.rs])

### Summary
`StackerDBTx::reconfigure_stackerdb` resets a slot's Lamport clock (`version`) to `NO_VERSION` (0) whenever the smart-contract-configured signer for that slot changes, but the signature that authenticates a chunk (`SlotMetadata::auth_digest`) never binds the chunk to a reward cycle/contract epoch — it only covers `slot_id`, `slot_version`, and `data_hash`. Because the `.signers-{0,1}-{message_id}` StackerDB contracts are reused across alternating reward cycles (`reward_cycle % 2`), a slot can be reassigned away from and later back to the same signer address, at which point the version counter is reset to 0. Anyone who recorded that signer's old, previously-superseded, but validly-signed chunk (all StackerDB writes are broadcast/servable over public HTTP/P2P) can resubmit it and have it accepted as the "latest" chunk for that slot, since its embedded `slot_version` will be greater than the freshly reset counter of 0 (or any lower current version).

### Finding Description
`try_replace_chunk` in `stackslib/src/net/stackerdb/db.rs` (lines 400-438) only enforces that `slot_desc.slot_version > slot_validation.version` (the value currently stored for that slot) and that the signature recovers to the recorded slot owner: [1](#0-0) 

The same monotonic-version-only check is duplicated for gossiped/pushed chunks in `validate_received_chunk`: [2](#0-1) 

Neither check ties the accepted `slot_version` to any global, non-replayable context (e.g., reward cycle, contract epoch, or a monotonically-increasing global nonce). The only state that prevents replay is the last-seen `slot_validation.version` stored per `(stackerdb_id, slot_id)`.

`reconfigure_stackerdb` resets that stored version back to `NO_VERSION = 0` whenever the *principal* assigned to a slot differs from what's currently recorded, and otherwise leaves the version untouched (treating it as "no change"): [3](#0-2) 

The `.signers` boot contract cycles slot assignments between two "pages" that are re-used every other reward cycle (`signers-0-*` for even cycles, `signers-1-*` for odd cycles): [4](#0-3) [5](#0-4) 

The signature that authenticates a chunk only covers `slot_id`, `slot_version`, and `data_hash` — nothing that scopes it to a particular contract deployment epoch or reward cycle: [6](#0-5) 

Putting this together: if signer address `A` occupies slot `X` in reward cycle `N` and writes several versions (e.g., up to version 50), then a different signer `B` occupies slot `X` in cycle `N+1` (reset to version 0 by `reconfigure_stackerdb`), and then `A` is reassigned back to slot `X` in a later cycle that reuses the same contract (e.g., `N+2` on the same `signers-0-*`/`signers-1-*` page), the stored version for slot `X` is reset to 0 again because `existing_validation.signer` (which was `B`) no longer equals `A`. At that point, anyone who has a copy of `A`'s old, validly-signed chunk from cycle `N` (public chunks are relayed and stored on all StackerDB replicas, and can also be fetched by any peer) can POST or gossip that stale chunk to nodes; it will be accepted because its `slot_version` (up to 50) is greater than the freshly-reset stored version (0), and the signature still recovers to `A`, who is once again the recorded slot owner.

### Impact Explanation
This breaks the "authenticated ⇒ current/fresh" equality that StackerDB nodes and downstream consumers rely on. Concretely:
- A stale chunk is served as canonical/latest state for a signer slot, matching the rubric's High-impact category of "serving non-canonical state as canonical."
- Downstream consumers that read "the latest chunk" for a slot — e.g. `InitialChunksLoader::load_chunks` in the Nakamoto miner's `stackerdb_listener.rs`, which loads the latest per-slot chunk to seed signer-state-machine views — could be fed stale/attacker-replayed signer messages (e.g., an old `BlockResponse` or `StateMachineUpdate`) instead of the signer's actual current state: [7](#0-6) 
- The replayed chunk is also propagated network-wide via normal StackerDB sync/gossip once accepted locally, since acceptance triggers relaying to peers (see `handle_unsolicited_StackerDBPushChunk`/inventory update path), amplifying the effect beyond the attacker's own node.

### Likelihood Explanation
Likelihood depends on whether the same signer address is ever reassigned to the same `slot_id` after being displaced by another signer — plausible in a system with rotating reward-cycle signer sets sorted deterministically (e.g., by public key or stake weight), especially over many reward cycles as the same node operators repeatedly qualify as top-N stackers. No attacker key material or admin privilege is required; the attacker only needs a previously-observed, publicly-broadcast chunk and the ability to send an unauthenticated `POST /v2/stackerdb/.../chunks` request or a gossip message — squarely a remote, unprivileged action.

### Recommendation
Bind the signed digest (`SlotMetadata::auth_digest`) to a value that cannot be replayed across a slot's reassignment history — e.g., include a per-assignment epoch/generation counter (bumped whenever `reconfigure_stackerdb` changes a slot's owner) or the StackerDB contract's `reward_cycle`/consensus hash in the signed payload. Alternatively, never reset the on-disk version counter to a value lower than any version previously seen for that `(stackerdb_id, slot_id)` pair, tracking a monotonically increasing "high-water mark" independent of ownership changes.

### Proof of Concept
1. Reward cycle `N`: Signer `A` is assigned slot `X` in `.signers-0-<msg>`. `A` broadcasts several chunks, ending at `slot_version = 50`, all publicly relayed/gossiped and thus observable/storable by any peer/attacker.
2. Reward cycle `N+1`: Signer `B` is assigned slot `X` (different address than `A`). `reconfigure_stackerdb` resets slot `X`'s stored version to `NO_VERSION = 0` per `stackslib/src/net/stackerdb/db.rs:319-346`.
3. Reward cycle `N+2` (reuses `signers-0-<msg>` again): Signer `A` is reassigned to slot `X`. Since the previously recorded signer (`B`) differs from `A`, `reconfigure_stackerdb` again resets slot `X`'s version to 0.
4. Attacker replays `A`'s old chunk (with `slot_version = 50`, still validly signed by `A`) via `POST /v2/stackerdb/<signers-0-msg>/chunks` (handled by `stackslib/src/net/api/poststackerdbchunk.rs`) or via unsolicited push. `try_replace_chunk` sees `50 > 0` and `A`'s signature verifies against the current slot owner `A`, so the stale chunk is accepted and stored as the current/latest chunk for slot `X`, then relayed to peers.

    pub fn reconfigure_stackerdb(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slots: &[(StacksAddress, u32)],
    ) -> Result<(), net_error> {
        let stackerdb_id = self.get_stackerdb_id(smart_contract)?;
        let mut total_slots_read = 0u32;
        for (principal, slot_count) in slots.iter() {
            total_slots_read =
                total_slots_read
                    .checked_add(*slot_count)
                    .ok_or(net_error::OverflowError(
                        "Slot count exceeeds u32::MAX".to_string(),
                    ))?;
            let slots_before_principal = total_slots_read - slot_count;
            for cur_principal_slot in 0..*slot_count {
                let slot_id = slots_before_principal + cur_principal_slot;
                if let Some(existing_validation) =
                    self.get_slot_validation(smart_contract, slot_id)?
                {
                    // this slot already exists.
                    if existing_validation.signer == *principal {
                        // no change
                        continue;
                    }
                }

                debug!("Reset slot {} of {}", slot_id, smart_contract);

                // new slot, or existing slot with a different signer
                let qry = "INSERT OR REPLACE INTO chunks (stackerdb_id,signer,slot_id,version,write_time,data,data_hash,signature) VALUES (?1,?2,?3,?4,?5,?6,?7,?8)";
                let mut stmt = self.sql_tx.prepare(qry)?;
                let args = params![
                    stackerdb_id,
                    principal.to_string(),
                    slot_id,
                    NO_VERSION,
                    0,
                    vec![],
                    Sha512Trunc256Sum([0u8; 32]),
                    MessageSignature::empty(),
                ];

                stmt.execute(args)?;
            }

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }
