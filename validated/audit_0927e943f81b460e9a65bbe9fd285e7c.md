### Title
Replay of a captured `broadcast=1` POST to `/v3/blocks/upload/` causes unbounded re-relay of an already-canonical block - ([File: stackslib/src/net/api/postblock_v3.rs])

### Summary
The `RPCPostBlockRequestHandler::try_handle_request` in `stackslib/src/net/api/postblock_v3.rs` calls `node.set_relay_message` unconditionally whenever `Relayer::process_new_nakamoto_block_ext` returns `BlockAcceptResponse::Accepted`, with no deduplication keyed on `block.block_id()`. Because `process_new_nakamoto_block_ext` is invoked with `force_broadcast = self.broadcast` (true when the request has `broadcast=1`), the "already-have-this-block" branch in `stackslib/src/net/relay.rs` explicitly returns `Accepted` (not `AlreadyStored`) every single time the same block is re-submitted with `broadcast=1`, so a single captured request replayed N times triggers N relay-message emissions for the same block.

### Finding Description
- Handler flow: `try_parse_request` (`stackslib/src/net/api/postblock_v3.rs:80-136`) validates the `authorization` header against the static configured secret and sets `broadcast=true` only if authenticated. This validation is purely a byte-equality check against a static header value (`stackslib/src/net/api/postblock_v3.rs:104-111`) — there is no nonce, timestamp, or per-request freshness token, so an identical wire-captured request (same headers, same body) remains valid forever and can be replayed verbatim by anyone who intercepts it (e.g., from a relay/log), without needing to know the secret itself.
- `try_handle_request` (`stackslib/src/net/api/postblock_v3.rs:147-207`) calls `Relayer::process_new_nakamoto_block_ext(..., self.broadcast.unwrap_or(false))`, then unconditionally does:
```rust
if data_resp.accepted {
    node.set_relay_message(StacksMessageType::NakamotoBlocks(NakamotoBlocksData { blocks: vec![block] }));
}
```
There is no check of whether this specific `block.block_id()` was already relayed by a prior identical request.
- In `stackslib/src/net/relay.rs:936-958` (`process_new_nakamoto_block_ext`), the "we already have this block" branch is:
```rust
if force_broadcast {
    // it's possible that the signer sent this block to us, in which case, we should broadcast it
    return Ok(BlockAcceptResponse::Accepted);
} else {
    return Ok(BlockAcceptResponse::AlreadyStored);
}
```
When `broadcast=1` (i.e. `force_broadcast = true`), this branch always returns `Accepted`, regardless of how many times the exact same already-canonical block has been submitted before. This is by design to let a signer force one legitimate re-broadcast, but it has no bound: `data_resp.accepted` will be `true` on every replay, so `set_relay_message` fires every time.
- Existing guards that would normally prevent amplification (dedup by block hash in the staging DB, `has_nakamoto_block_with_index_hash` check) only gate storage/consensus acceptance — they do not gate the relay-message emission when `force_broadcast` is set. The auth check gates *whether broadcast is requested at all*, not *how many times* an identical already-processed request may re-trigger relay.

### Impact Explanation
Each replay of the exact same captured authenticated request causes the node to enqueue a fresh `NakamotoBlocksData` relay message via `node.set_relay_message`, which is subsequently gossiped to the node's peers. A single captured authenticated broadcast message can therefore be used to make one node repeatedly re-inject the same block into network-wide gossip an unbounded number of times, amplifying traffic across all connected peers from one captured message — matching the "single-captured-message amplification of network-wide gossip" impact category described in the prompt. No new state is forged (the block is genuinely canonical), but the relay/gossip subsystem's per-message cost is not bounded per unique block.

### Likelihood Explanation
- The attacker needs no privileged role and no knowledge of the RPC secret; they only need to have observed one legitimate `broadcast=1` request (e.g., on a public/semi-public relay, from network capture, or from being a StackerDB/peer participant that saw the message in transit).
- The endpoint is reachable by any peer that can reach the node's RPC port with a POST to `/v3/blocks/upload/?broadcast=1`.
- The attack is trivially repeatable: replaying identical bytes N times produces N relay-message emissions, since there is no session/nonce binding and the "already stored" dedup is bypassed specifically for the `broadcast=1` path.
- Preconditions: the target block must already be known/canonical to the node (true after the first legitimate send), and the node's operator must have configured an RPC auth secret (which is standard when using authenticated broadcast).

### Recommendation
Deduplicate relay-message emission by `block.block_id()` (e.g., an in-memory recently-broadcast set with TTL, similar to `Relayer::recently_sent_nakamoto_blocks`) before calling `node.set_relay_message`, regardless of the `force_broadcast`/`broadcast=1` path. Additionally, consider requiring a per-request nonce or timestamp bound to the auth header/body so identical captured requests cannot be replayed indefinitely.

### Proof of Concept
Rust net test plan (in `stackslib/src/net/api/tests/postblock_v3.rs` or similar):
1. Construct a `RPCPostBlockRequestHandler` with a configured `auth` secret and a `StacksNodeState` wired to a test peer/chainstate that already has one Nakamoto block accepted (canonical).
2. Build a `StacksHttpRequest::new_post_block_v3_broadcast(host, &block, secret)` for that already-canonical block, serialize it once to raw bytes (headers + body) to simulate "captured off the wire."
3. Feed the identical serialized bytes into `try_parse_request` + `try_handle_request` N times (e.g., N = 5), each time using a fresh handler/preamble but with the *same* captured request bytes (no modification).
4. Instrument/mock `node.set_relay_message` (or inspect `network_result`/mpsc channel `StacksMessageType::NakamotoBlocks`) to count emissions keyed by `block.block_id()`.
5. Assert: `emission_count == 1` (expected/fixed behavior) fails — actual observed count is `N`, demonstrating unbounded re-relay of a single already-canonical block from replaying one captured authenticated request.
