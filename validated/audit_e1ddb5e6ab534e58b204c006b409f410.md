### Title
Unprivileged attacker can permanently fill a victim's `depositTokensOfAccount` list with dust deposit tokens, blocking all future deposits of new collateral types and rescue of unhealthy positions - ([File: contracts/DepositToken.sol])

### Summary
`DepositToken._transfer` and `_mint` call `Pool.addToDepositTokensOfAccount(recipient)` whenever the recipient's balance of that token is zero (DepositToken.sol:486-488, 518-520). `Pool` caps each account's collateral token list at `MAX_TOKENS_PER_USER = 30` (Pool.sol:79) and reverts with `UserReachedMaxTokens` once the list is full. Any user can deposit dust `onBehalfOf` a victim (`deposit(amount_, onBehalfOf_)`, DepositToken.sol:211-237) or `transfer` dust directly (DepositToken.sol:348-354), with no opt-in required. Once the victim's list is full, every subsequent `_mint`/`_transfer` of a deposit token the victim does not already hold reverts inside `addToDepositTokensOfAccount`, permanently denying them new collateral types.

### Finding Description
1. Attacker deposits dust amounts of every listed `DepositToken` via `deposit(1, victim)` (or transfers 1 wei of each msd token to the victim). Each call hits `_balanceBefore == 0 && amount_ > 0` and appends the token to `depositTokensOfAccount[victim]` until it reaches 30 entries.
2. Afterwards, `victim.deposit(x, victim)` for any collateral they do not already hold reverts, because `_mint` → `addToDepositTokensOfAccount` → `UserReachedMaxTokens`. The same applies to receiving any new deposit token via `transfer`/`transferFrom` and to liquidation `seize` proceeds directed to the victim.
3. Crucially, the victim cannot self-clean the list while they carry debt: `_transfer`/`withdraw` require `unlockedBalanceOf` (DepositToken.sol:180-182, 383-398), and while `_debtInUsd > 0` the dust tokens count toward locked collateral proportionally, so `removeFromDepositTokensOfAccount` cannot be reached for tokens whose entire balance is locked. The DoS therefore persists for the life of the debt position: the victim can never add the new collateral type that would restore health, and is forced into liquidation.

This mirrors CVE-2018-2775's bug class (unprivileged attacker induces a repeatable availability failure / hang of a core function) applied to Metronome: a repeatable, attacker-triggerable liveness break of `deposit`/`transfer`/rescue paths for a chosen account.

### Impact Explanation
Liveness: an unprivileged attacker can permanently (for the duration of any outstanding debt) prevent a victim from depositing additional collateral of new types, transferring out dust, or receiving new deposit tokens. For a victim sliding toward liquidation, this blocks the primary self-rescue action (topping up collateral), causing forced loss via liquidation that would otherwise have been avoided — a temporary freezing of the victim's position-management capability with direct monetary impact through the liquidation discount.

### Likelihood Explanation
Fully permissionless: `deposit(amount_, onBehalfOf_)` has no beneficiary consent check (DepositToken.sol:211-216) and `transfer` only checks the *sender's* unlocked balance (DepositToken.sol:350-352), not the recipient's list size. Cost is ~30 dust deposits across the pool's listed deposit tokens. No privileged role, oracle manipulation, or governance parameter change is required. Partial mitigation: the victim can repay all debt to unlock and transfer dust out, or use already-listed collateral — so the attack is strongest against accounts already holding debt and near the health threshold, or executed front-running a rescue deposit.

### Recommendation
- Enforce the per-account cap inside `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` only for tokens received via user-initiated deposits (`deposit()` mint path), or allow the recipient list to exceed the cap while gating deposits of *new* tokens separately from transfers/seizes.
- Alternatively, add an opt-in/allowlist for `onBehalfOf_` deposits, or make `addToDepositTokensOfAccount` a no-op (rather than revert) past the cap and account for extra tokens in `debtPositionOf` via an explicit user opt-in.
- Add a permissionless `removeMyDustToken` path that lets an account force-remove a token with negligible balance regardless of lock status.

### Proof of Concept
Hardhat fork sketch (repo uses Hardhat + ethers, see `test/Pool.test.ts`):

```ts
// setup: pool with >=1 deposit token listed (msdMET, ...); victim holds an open debt position
const tokens = await pool.getDepositTokens() // all listed DepositToken addresses

for (const dt of tokens) {
  const depositToken = await ethers.getContractAt('DepositToken', dt)
  const underlying = await depositToken.underlying()
  const erc20 = await ethers.getContractAt('IERC20', underlying)
  await erc20.connect(attacker).approve(depositToken.address, 1)
  // deposit dust directly to victim — no consent needed
  await depositToken.connect(attacker).deposit(1, victim.address)
}

// victim's list is now at MAX_TOKENS_PER_USER (30)
// victim tries to deposit a collateral type they don't hold yet:
await underlying2.connect(victim).approve(newDepositToken.address, amount)
await expect(
  newDepositToken.connect(victim).deposit(amount, victim.address)
).revertedWithCustomError(pool, 'UserReachedMaxTokens')

// victim cannot clean up: dust is locked while debtInUsd > 0
await expect(
  msdMET.connect(victim).transfer(attacker.address, 1)
).revertedWithCustomError(msdMET, 'NotEnoughFreeBalance') // or list stays full
```
