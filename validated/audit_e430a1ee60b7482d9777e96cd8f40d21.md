### Title
Missing zero-check on `totalEnergyWeight`/`totalNetWeight` before division in `RepositoryImpl.calculateGlobalEnergyLimit` allows divide-by-zero/precision corruption in TVM native resource contracts - ([File: actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java])

### Summary
`RepositoryImpl.calculateGlobalEnergyLimit` divides by `totalEnergyWeight` (the chain-wide sum of all frozen-for-energy TRX) after only a Java `assert` statement, which is compiled out and disabled by default at runtime (Java `assert` requires the JVM `-ea` flag). This mirrors the reported bug class exactly: a precision/ratio helper function performs division without a real (non-assert) guard against a zero denominator, so a caller that reaches it while the denominator is zero either throws an uncaught `ArithmeticException` (hardened/BigInteger path) or silently produces `NaN`/`Infinity`-derived garbage (legacy double path), rather than failing gracefully.

### Finding Description [1](#0-0) 

```java
public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
  long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
  if (frozeBalance < TRX_PRECISION) {
    return 0;
  }
  long energyWeight = frozeBalance / TRX_PRECISION;
  long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
  long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

  assert totalEnergyWeight > 0;   // <-- disabled in production, no real guard

  if (hardenResourceCalculation()) {
    return BigInteger.valueOf(energyWeight)
        .multiply(BigInteger.valueOf(totalEnergyLimit))
        .divide(BigInteger.valueOf(totalEnergyWeight))   // ArithmeticException if 0
        .longValueExact();
  }
  return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));  // NaN/Infinity if 0
}
```

Contrast this with the equivalent, correctly-guarded implementations elsewhere in the codebase, which explicitly `return 0` when the weight is zero instead of relying on `assert`: [2](#0-1) [3](#0-2) 

Both `EnergyProcessor.calculateGlobalEnergyLimit` and `BandwidthProcessor.calculateGlobalNetLimit` check `totalEnergyWeight <= 0` / `totalNetWeight == 0` and return 0 safely. `RepositoryImpl.calculateGlobalEnergyLimit`, used from the TVM native-contract execution path (`RepositoryImpl` is the `Repository` implementation used by `VMActuator`/native contract processors such as `DelegateResourceProcessor`/`UnDelegateResourceProcessor`), lacks this same protection and only has a no-op `assert`.

`totalEnergyWeight` is a chain-wide accumulator (`DynamicPropertiesStore.getTotalEnergyWeight()`) that is decremented whenever any account unfreezes its energy-frozen balance. While reaching an exact global zero requires essentially every frozen-for-energy TRX on the network to be unfrozen simultaneously, it is a state fully reachable through normal `UnfreezeBalanceV2`/`UnDelegateResource` operations from unprivileged accounts, not a privileged/malicious-node action — matching the "unbacked/incorrect accounting caused by unauthorized/normal user operation" category.

### Impact Explanation
- If `hardenResourceCalculation()` is enabled, division by zero throws `ArithmeticException` from inside TVM native-contract execution, propagating as an uncaught exception in a smart-contract call/transaction execution path rather than being converted into a graceful `ContractValidateException`/`ContractExeException`, which is inconsistent with how other resource-processor code paths handle the same computation.
- If hardening is disabled, `(double) totalEnergyLimit / totalEnergyWeight` with `totalEnergyWeight == 0` yields `Infinity`, and the subsequent multiplication/cast to `long` yields `Long.MAX_VALUE` — silently giving the caller an incorrect (unbounded) global energy limit value instead of failing safely, an unbacked-value class of bug.
- Both outcomes stem from the same root cause identified in the original report: relying on an `assert` instead of an actual runtime zero-check before a ratio/percentage-style division used by account resource accounting.

### Likelihood Explanation
Likelihood is lower than the original Sherlock finding because `totalEnergyWeight` reaching exactly zero requires essentially all delegated/frozen-for-energy balance on the chain to be unfrozen at once, which is an extreme, low-probability network state rather than a per-account condition an attacker can trivially force in isolation. It is nonetheless reachable purely through normal `UnfreezeBalanceV2` transactions from unprivileged accounts, with no special/malicious-actor privilege required, and no compile-time or runtime protection exists in `RepositoryImpl` (the `assert` provides none in production).

### Recommendation
Replace the `assert totalEnergyWeight > 0;` in `RepositoryImpl.calculateGlobalEnergyLimit` with an explicit runtime check mirroring `EnergyProcessor.calculateGlobalEnergyLimit`/`BandwidthProcessor.calculateGlobalNetLimit`, e.g. `if (totalEnergyWeight <= 0) { return 0; }`, before performing either the BigInteger or double division, to guarantee identical safe behavior regardless of JVM assertion settings.

### Proof of Concept
Not independently reproducible from the index alone: verifying the exact call chain that invokes `RepositoryImpl.calculateGlobalEnergyLimit` from a TVM native-contract execution (e.g., through `VMActuator`/native `DelegateResource`/`UnfreezeBalanceV2` opcode handling) and confirming whether `-ea` is ever enabled in production builds requires reading the full `RepositoryImpl`/`VMActuator` wiring and build configuration, which was not fully available within the indexed context. I recommend a full-repository review (e.g., a Devin session with complete file access) to trace all call sites of `calculateGlobalEnergyLimit`/`calculateGlobalNetLimit` in `RepositoryImpl` and confirm whether `totalEnergyWeight`/`totalNetWeight` can reach zero in a way callable purely through unprivileged transactions before treating this as fully confirmed exploitable.
