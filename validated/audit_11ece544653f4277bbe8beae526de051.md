### Title
Zero-value `TransactionID` sentinel is inconsistently validated across the proc-receive hook path, enabling waiter/handler cross-registration - (File: internal/gitaly/hook/procreceive_registry.go)

### Summary
This is analogous to the reported bug class ("a zero/default identifier is treated as a legitimate registered value, letting an unauthorized caller be matched against a sensitive handler") but in Gitaly's `storage.TransactionID` handling for the proc-receive hook path, rather than in the smart-contract `adapterId`.

### Finding Description
`storage.TransactionID` is a `uint64` whose zero value is explicitly documented and used as the "no transaction" sentinel: `ExtractTransactionID` returns `0` when no transaction is present in the context. [1](#0-0) 

The `ProcReceiveRegistry` used to correlate `ReceivePack`'s waiter with the `proc-receive` hook's handler keys its internal `waiters` map directly by this same `storage.TransactionID`, with **no rejection of the zero value** at the registry layer: [2](#0-1) 

Some call sites do defend against the zero sentinel — e.g. `NewProcReceiveHandler` (invoked from the `gitaly-hooks` binary side) explicitly rejects `payload.TransactionID == 0`: [3](#0-2) 
and `SignalPostReceiveReady` explicitly guards `req.GetTransactionId() == 0`: [4](#0-3) 

However, `RegisterWaiter`/`Transmit` in `ProcReceiveRegistry` itself perform no equivalent zero-ID rejection — they will happily register a waiter for ID `0` and transmit a handler whose `TransactionID()` is `0` to it: [5](#0-4) 

This mirrors the reported pattern precisely: the identifier space treats "unset/default" (`0`) the same as a normal, valid identifier, and the guard against it exists only in some call paths (`procreceive_handler.go`, `signal_post_receive.go`) but not centrally in the shared registry data structure that actually performs the security-sensitive matching (routing a live receive-pack handler to whichever caller registered as its waiter). I was unable to confirm (due to tool-call limits) whether the gRPC `ProcReceiveHook` RPC handler in `internal/gitaly/service/hook/proc_receive.go` independently re-validates the transaction ID extracted from the request's hooks-payload environment before calling `Transmit`, which is the exact point analogous to `BridgeRouterHub::receiveMessage()` accepting an uninitialized/default index as valid.

### Impact Explanation
If any code path can reach `RegisterWaiter`/`Transmit` with a transaction ID of `0` (e.g., a hooks payload crafted or replayed without a valid transaction, or a race where `ExtractTransactionID` legitimately defaults to `0` in one flow while another flow explicitly passes `0`), two independent, unrelated operations could be paired through the shared "zero" key in the `waiters` map — the same defective-mitigation pattern as the reported contract bug, where a supposedly-restricted gateway function accepts the default/uninitialized identifier as if it were a validated one. This could let a caller improperly receive or inject reference-update handling instructions.

### Likelihood Explanation
This is a defense-in-depth concern rather than a confirmed unauthenticated bypass: existing guards in `procreceive_handler.go` and `signal_post_receive.go` reduce the practical likelihood of reaching the registry with ID `0` through the documented client paths. However, its likelihood is uncertain because I could not verify (within tool-call limits) whether `internal/gitaly/service/hook/proc_receive.go`'s RPC handler performs the same `== 0` check before calling `registry.Transmit`, or relies solely on the map lookup succeeding/failing naturally. Given `RegisterWaiter` already contains an explicit test case documenting "`transactionID: 0`, ... `A transaction ID with a value of zero is invalid`" as an expected-failure scenario, the codebase authors are aware zero is a meaningful invalid sentinel, but the check is not enforced at the shared registry boundary itself.

### Recommendation
Add an explicit `id == 0` rejection directly inside `ProcReceiveRegistry.RegisterWaiter` and `ProcReceiveRegistry.Transmit` (analogous to the reported contract's suggested `adapterId == 0` revert), rather than relying on it being separately checked in each calling code path. This centralizes the invariant "0 is never a valid transaction ID" at the data structure that performs the actual security-sensitive pairing, closing the gap regardless of which caller (gitaly-hooks binary, gRPC service handler, or future code) reaches the registry.

### Proof of Concept
Not independently reproduced here due to tool-call limits; the existing test `TestHooksProcReceive` in `cmd/gitaly-hooks/hooks_test.go` already documents the expected-invalid behavior for `transactionID: 0` at the `gitaly-hooks` binary boundary via `RegisterWaiter(tc.transactionID)`: [6](#0-5) 
demonstrating that `0` is treated as a meaningful sentinel value application-wide, but the enforcement of this invariant is not present at the `ProcReceiveRegistry` level itself.

```go
type ProcReceiveRegistry struct {
	waiters map[storage.TransactionID]chan<- ProcReceiveHandler
	m       sync.Mutex
}

// NewProcReceiveRegistry creates a new registry by allocating the required
// variables.
func NewProcReceiveRegistry() *ProcReceiveRegistry {
	return &ProcReceiveRegistry{
		waiters: make(map[storage.TransactionID]chan<- ProcReceiveHandler),
	}
}

// RegisterWaiter registers a waiter against the provided transactionID.
// The function returns a channel to obtain the handler, a cleanup function
// which must be called and an error if any.
func (r *ProcReceiveRegistry) RegisterWaiter(id storage.TransactionID) (<-chan ProcReceiveHandler, func(), error) {
	r.m.Lock()
	defer r.m.Unlock()

	if _, ok := r.waiters[id]; ok {
		return nil, nil, fmt.Errorf("cannot register id: %d again", id)
	}

	ch := make(chan ProcReceiveHandler)
	r.waiters[id] = ch

	cleanup := func() {
		r.m.Lock()
		defer r.m.Unlock()

		delete(r.waiters, id)
	}

	return ch, cleanup, nil
}

// Transmit transmits a handler to its waiter.
func (r *ProcReceiveRegistry) Transmit(ctx context.Context, handler ProcReceiveHandler) error {
	r.m.Lock()
	ch, ok := r.waiters[handler.TransactionID()]
	r.m.Unlock()

	if !ok {
		return fmt.Errorf("no waiters for id: %d", handler.TransactionID())
	}

	// It is possible that the RPC (waiter) returned because receive-pack
	// returned an error. In such scenarios, we don't want to block indefinitely.
	select {
	case <-ctx.Done():
		return ctx.Err()
	case ch <- handler:
	}

	return nil
}
```
