## Analysis

The external report's core broken invariant: a single self-controlled trade at an attacker-chosen price is stored as *the* reference price used to compute a critical derived value (funding rate / liquidation price) for a subsequent period, with no volume-weighting or manipulation resistance.

The closest local analog in this repository is in `pallet-broker` (the Coretime sale pallet), where the price of a *single* permissionless core purchase becomes the sole input that sets the price for the *entire next sale period*, including renewal prices for parachains.

### Title
Single-purchase price capture in Coretime sale pricing lets an attacker set the next sale's `end_price`/`target_price` and renewal prices - (File: `substrate/frame/broker/src/utility_impls.rs`, `substrate/frame/broker/src/adapt_price.rs`)

### Summary
`Pallet::purchase_core` records `SaleInfoRecord::sellout_price` from whichever single `Call::purchase` transaction happens to push `cores_sold` up to `ideal_cores_sold` [1](#0-0) . That one recorded price is later fed, unweighted and unaveraged, into `CenterTargetPrice::adapt_price` at `rotate_sale`, which derives `end_price` and `target_price` for the *entire* next sale period [2](#0-1) [3](#0-2) . `target_price` is also directly written into `PotentialRenewalRecord.price` for any lease expiring in that region, becoming the fixed renewal price parachains will pay [4](#0-3) . This is structurally the same "single/self-controlled trade sets the reference price for a whole subsequent period" pattern described in the external report, just without the need for a counterparty.

### Finding Description
`do_purchase` is a permissionless, signed extrinsic: it checks only that a sale is active, `now > sale.sale_start`, and that the buyer's `price_limit` covers the current deterministic `sale_price(sale, now)` [5](#0-4) . `sale_price` is a pure function of block number and the sale's public `leadin_length`/`end_price`, so any actor can predict exactly what price will be charged at any future block [6](#0-5) .

`purchase_core` updates `sale.sellout_price` on every purchase for which `cores_sold <= ideal_cores_sold` [1](#0-0) , meaning the *last* such qualifying purchase — the one that brings `cores_sold` to exactly `ideal_cores_sold` — is what survives into `SaleInfoRecord::sellout_price` used by `rotate_sale`. Because `sale_price` decays monotonically over the leadin period, an attacker who can time/control which of their own purchase transactions lands at the `ideal_cores_sold`-th slot fully controls the recorded `sellout_price` (e.g., by waiting until the leadin has decayed close to the floor and then being the buyer who fills the ideal quota, or by front-loading purchases to control the exact slot).

`CenterTargetPrice::adapt_price` (the pallet's current, "fixed" adapter per PR #4521 / issue #4360) then computes: `target_price = sellout_price`, `end_price = sellout_price / 10` [2](#0-1) . These two numbers become, respectively, the ceiling price for the *entire next sale's leadin curve* and the renewal price locked into `PotentialRenewalRecord` for every lease/parachain renewing in that period [7](#0-6) . There is no aggregation across multiple purchases, no volume weighting, and no protection against the attacker being the party that fills the `ideal_cores_sold` slot — the prior fix (PR #4521) changed the metric from "cores sold count" to "price achieved," but that price is still captured from a single transaction rather than a TWAP over the sale.

### Impact Explanation
An attacker with sufficient balance can depress (or, depending on timing control, inflate) the coretime price for an entire multi-week sale period and the renewal price for any parachain lease expiring in that window, by controlling the single purchase that sets `sellout_price`. This directly affects protocol revenue (`OnRevenue`) and parachain blockspace-cost fairness on Coretime chains (Rococo/Westend, and by extension the "fellowship production runtime" noted in the prdoc) — a public, underpriced-work-style economic manipulation of a chain-critical pricing parameter, achievable by an unprivileged, ordinary signed account.

### Likelihood Explanation
Moderate-to-high: no privileged role, relayer, validator, or governance action is required — only a signed account with enough currency to buy coretime and the ability to observe/predict `sale_price(sale, now)`, which is a fully public deterministic function of block number. The main cost to the attacker is the price of the manipulating purchase itself, but that cost can be offset by the value gained from favorable pricing on subsequent purchases/renewals they or colluding parties make.

### Recommendation
Compute `sellout_price`/`target_price` as a volume- or time-weighted average over multiple qualifying purchases within the sale (or over the whole sale duration) rather than capturing the price of a single purchase transaction. Alternatively, require a minimum number of independent purchasers/blocks before a price sample is allowed to update `sellout_price`, and bound the maximum period-over-period price movement more strictly than the current `1/10` and `10x` linear factors in `CenterTargetPrice`.

### Proof of Concept
1. Observe the public `sale_price(sale, now)` curve for the ongoing sale (deterministic function of `leadin_length`, `end_price`, block number) via `current_price()` [8](#0-7) .
2. Wait until `cores_sold == ideal_cores_sold - 1` (achievable either passively or by buying preceding cores yourself).
3. Submit `Call::purchase` at the moment the leadin price has decayed near its floor, becoming the purchase that sets `cores_sold == ideal_cores_sold`, which stores this depressed price into `sale.sellout_price` [1](#0-0) .
4. At `rotate_sale`, `CenterTargetPrice::adapt_price` derives the next sale's `end_price`/`target_price` from this manipulated `sellout_price` [2](#0-1) , and any parachain renewing in that period is locked into the attacker-influenced `target_price` [4](#0-3) .

	fn adapt_price(performance: SalePerformance<Balance>) -> AdaptedPrices<Balance> {
		let Some(sellout_price) = performance.sellout_price else {
			return AdaptedPrices {
				end_price: performance.end_price,
				target_price: FixedU64::from(10).saturating_mul_int(performance.end_price),
			};
		};

		let price = FixedU64::from_rational(1, 10).saturating_mul_int(sellout_price);
		let price = if price == Balance::zero() {
			// We could not recover from a price equal 0 ever.
			sellout_price
		} else {
			price
		};

		AdaptedPrices { end_price: price, target_price: sellout_price }
	}

	pub(crate) fn do_purchase(
		who: T::AccountId,
		price_limit: BalanceOf<T>,
	) -> Result<RegionId, DispatchError> {
		let status = Status::<T>::get().ok_or(Error::<T>::Uninitialized)?;
		let mut sale = SaleInfo::<T>::get().ok_or(Error::<T>::NoSales)?;
		Self::ensure_cores_for_sale(&status, &sale)?;

		let now = RCBlockNumberProviderOf::<T::Coretime>::current_block_number();
		ensure!(now > sale.sale_start, Error::<T>::TooEarly);
		let price = Self::sale_price(&sale, now);
		ensure!(price_limit >= price, Error::<T>::Overpriced);

		let core = Self::purchase_core(&who, price, &mut sale)?;

		SaleInfo::<T>::put(&sale);
		let id = Self::issue(
			core,
			sale.region_begin,
			CoreMask::complete(),
			sale.region_end,
			Some(who.clone()),
			Some(price),
		);
		let duration = sale.region_end.saturating_sub(sale.region_begin);
		Self::deposit_event(Event::Purchased { who, region_id: id, price, duration });
		Ok(id)
	}
