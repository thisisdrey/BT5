### Title
Mandatory unconditional CPI to third-party lending protocols (Drift, JupLend) in withdraw path can permanently lock user funds if the external protocol reverts - ([File: programs/marginfi/src/instructions/drift/withdraw.rs], [File: programs/marginfi/src/instructions/juplend/withdraw.rs])

### Summary
`drift_withdraw` and `juplend_withdraw` both begin execution with an unconditional, un-catchable CPI into the external protocol (`update_spot_market_cumulative_interest` for Drift, `update_rate` for JupLend) before any marginfi-side accounting is finalized. This mirrors the reported `OgvStaking`/`RewardsSource` coupling issue: a core user-facing operation (there, `stake`/`unstake`; here, `withdraw`) is strongly coupled to an external contract's internal call (`RewardsSource.collectRewards` there, `update_rate`/`update_spot_market_cumulative_interest` here), and if that external call reverts for any reason outside marginfi's control, the core operation is unconditionally blocked, with no fallback path.

### Finding Description
In `drift_withdraw`, the very first program action is: [1](#0-0) 
which calls `cpi_update_spot_market_cumulative_interest()` unconditionally via `?`, propagating any Drift-side revert directly and aborting the entire marginfi withdraw instruction: [2](#0-1) 

Similarly, `juplend_withdraw` starts with: [3](#0-2) 
which calls `ctx.accounts.cpi_update_rate()?` into the JupLend program before any of marginfi's own share/balance accounting runs: [4](#0-3) 

In both cases there is no try/catch equivalent, no fallback withdrawal path bypassing the external refresh call, and no way for marginfi (or the user) to withdraw the underlying collateral if the external protocol's rate/interest-update instruction becomes permanently unreachable (e.g., the third-party market is paused, deprecated/delisted, or otherwise made to always revert on that specific CPI by the external protocol's own administration — an action entirely outside marginfi's control, just as `RewardsSource.setRewardsTarget(0)` was outside `OgvStaking`'s control). The actual `withdraw`/`cpi_juplend_withdraw` CPI later in each function also has no error-handling wrapper.

This is architecturally the same root cause as the reported bug: a strongly-coupled core-path function (`stake`/`unstake`/`extend` there, `drift_withdraw`/`juplend_withdraw` here) unconditionally depends on a call into a separate, independently-administered contract, and any failure in that separate contract's function permanently disables the core user action.

### Impact Explanation
If the mandatory upstream CPI (`update_spot_market_cumulative_interest` on Drift or `update_rate` on JupLend) becomes permanently unable to succeed for a given market/pool — for example, the third-party protocol pauses or delists that spot market/lending pool, or otherwise blocks that specific instruction — every marginfi user with a position in the corresponding wrapped bank loses the ability to withdraw their underlying collateral through `drift_withdraw`/`juplend_withdraw`. Because these wrapped banks have no alternate/emergency withdrawal instruction that bypasses the mandatory rate/interest refresh, user funds held in these Drift- or JupLend-backed banks become permanently locked, matching the "permanent lock/freeze" impact category the rules require.

### Likelihood Explanation
This requires no privileged access on marginfi's own admin/governance keys — the trigger condition is state change on the third-party integrated protocol (Drift or JupLend), which marginfi does not control, exactly analogous to how `RewardsSource`'s admin (a separate contract's owner) could brick `OgvStaking` by zeroing `rewardTarget`. Given marginfi integrates multiple actively-changing third-party lending venues, and those venues can pause, deprecate, or otherwise restrict specific markets/pools at their own discretion, this is a realistic, externally-triggerable condition rather than a purely theoretical one. However, I was not able to fully verify from the indexed code/docs whether Drift or JupLend's admin-side pause/delist mechanisms actually cause `update_spot_market_cumulative_interest`/`update_rate` (as opposed to only the withdraw/deposit CPIs) to revert, since those third-party programs are only referenced as `drift_mocks`/`juplend_mocks` dependencies in this repo and their full source was not available to inspect.

### Recommendation
Introduce a bypass/fallback withdrawal path for wrapped venue banks (Drift/JupLend/Kamino/Solend) that does not depend on the external protocol's rate/interest-refresh CPI succeeding — e.g., allow withdrawal using the last-cached exchange rate/interest data when the refresh CPI fails, guarded by a staleness check, or provide an admin/permissionless "emergency withdraw" instruction that skips the refresh CPI and relies on the bank's last known state. At minimum, wrap the refresh CPIs in an explicit error-handling path that surfaces a distinct, catchable error (rather than only relying on Anchor's default `?` propagation) so integrators/keepers can detect and react to the otherwise-opaque failure, similar to the recommendation in the referenced report to catch and emit the error reason as an event.

### Proof of Concept
Conceptual reproduction (not independently executed against live Drift/JupLend state due to sandboxed `_mocks` programs in this repo):
1. A marginfi group admin creates a Drift-wrapped bank (or JupLend-wrapped bank) and users deposit funds via `drift_deposit`/`juplend_deposit`.
2. The external protocol's own administration pauses/delists the relevant spot market or lending pool such that `update_spot_market_cumulative_interest` (Drift) or `update_rate` (JupLend) always reverts for that market/pool going forward.
3. Any user calls `drift_withdraw`/`juplend_withdraw`. Execution reaches [5](#0-4)  or [6](#0-5) , the CPI reverts, and the whole instruction fails via `?` propagation.
4. Because there is no alternate withdrawal path in the wrapped-bank instruction set that skips this refresh CPI, the user's underlying collateral remains permanently locked in the bank's fToken/spot-market position with no on-chain recovery mechanism, exactly mirroring the `OgvStaking`/`RewardsSource` "zero rewardTarget bricks staking" scenario.

    pub fn cpi_update_spot_market_cumulative_interest(&self) -> MarginfiResult {
        let accounts = UpdateSpotMarketCumulativeInterest {
            state: self.drift_state.to_account_info(),
            spot_market: self.integration_acc_1.to_account_info(),
            oracle: self
                .drift_oracle
                .as_ref()
                .map(|o| o.to_account_info())
                .unwrap_or(self.system_program.to_account_info()),
            spot_market_vault: self.drift_spot_market_vault.to_account_info(),
        };

        let program = self.drift_program.to_account_info();
        let cpi_ctx = CpiContext::new(program.key(), accounts);

        update_spot_market_cumulative_interest(cpi_ctx)?;
        Ok(())
    }
