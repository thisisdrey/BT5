Audit Report

## Title
Snowbridge v1 outbound queue locks user funds/messages permanently when adverse gas-price/exchange-rate conditions make delivery unprofitable, with no way to top up the reward - ([File: bridges/snowbridge/pallets/outbound-queue/src/lib.rs])

## Summary
The v1 `snowbridge-pallet-outbound-queue` fixes a relayer `reward` and `max_fee_per_gas` into a `CommittedMessage` at commit time based on `PricingParameters`, which per the pallet's own documentation are only manually refreshed by governance "every few weeks." [1](#0-0)  If Ethereum gas price or the ETH/DOT exchange rate move adversely after commit, the baked-in reward can become unprofitable to deliver, and unlike the newer v2 pipeline, there is no permissionless tip/topup entrypoint in v1 to rescue the message.

## Finding Description
`do_process_message` computes `reward` and `max_fee_per_gas` from `T::PricingParameters::get()` at the moment the message is processed and locks them into the `CommittedMessage` structure permanently, with no later re-adjustment path. [2](#0-1)  On the Ethereum side, the relayer is refunded `Min(GasPrice, Message.MaxFeePerGas) * GasUsed() + Message.Reward`, so any gas price above `MaxFeePerGas` is borne entirely by the relayer with no compensation beyond what was fixed at commit time. [3](#0-2) 

The pallet's own module documentation explicitly frames this pricing scheme as an "interim measure" pending liquidity-pool-based pricing, and states governance updates parameters only "every few weeks" via `set_pricing_parameters`. [4](#0-3)  The message submission/enqueue path (`validate`/`deliver`) is a simple queue with no expiry or refund logic. [5](#0-4) 

A grep across the v1 outbound-queue pallet source confirms there is no tip/topup code path anywhere in it, whereas the string "tip"/"topup" appears extensively in `outbound-queue-v2`, `inbound-queue-v2`, `system-v2`, and `system-frontend` pallets — confirming the tip mechanism exists exclusively for the newer v2 pipeline. The v1 pallet remains compiled into and exposed by the live Bridge Hub Westend and Rococo runtimes via `impl snowbridge_outbound_queue_runtime_api::OutboundQueueApi<Block, Balance> for Runtime`.

## Impact Explanation
This matches the impact gate's "public underpriced work that degrades block production or stalls bridge processing" and potentially "permanent user-fund or bridge-state lock" categories: once a message's baked-in reward becomes economically unattractive to relayers due to ordinary market movement, no permissionless actor can raise the fee/reward, and the message (and any Ethereum-side state transition or locked asset contingent on it) can remain undelivered indefinitely absent a privileged governance re-pricing action.

## Likelihood Explanation
This condition is triggered by ordinary, externally-observable market movement (Ethereum gas price spikes, ETH/DOT FX volatility) rather than by a malicious relayer, validator, or governance actor — it is an unprivileged, externally-triggerable degradation of bridge processing that requires no special access, consistent with the impact gate's exclusion of "malicious peer/relayer/governance actor" as the root cause.

## Recommendation
Backport a permissionless tip/topup mechanism (as implemented for `snowbridge-pallet-outbound-queue-v2`/`inbound-queue-v2`/`system-v2`/`system-frontend`) to the v1 `snowbridge-pallet-outbound-queue`, allowing any account to top up the `reward`/`max_fee_per_gas` of an already-committed, undelivered message, or add automatic on-chain re-pricing tied to elapsed blocks since commit.

## Proof of Concept
1. Governance sets `PricingParameters` at time T0 via `set_pricing_parameters`.
2. A user submits a message via `SendMessage::validate`/`deliver`, which enqueues it through `T::MessageQueue::enqueue_message`. [6](#0-5) 
3. `do_process_message` commits the message with `max_fee_per_gas`/`reward` fixed from T0 parameters. [7](#0-6) 
4. Before any relayer delivers it on Ethereum, gas price spikes or ETH/DOT rate moves against relayers beyond the locked `fee_per_gas`/reward.
5. No relayer profitably delivers `Min(GasPrice, MaxFeePerGas) * GasUsed() + Reward`; since governance updates parameters only "every few weeks" and v1 lacks any topup extrinsic, the message remains stuck until governance intervenes.

	fn validate(
		message: &Message,
	) -> Result<(Self::Ticket, Fee<<Self as SendMessageFeeProvider>::Balance>), SendError> {
		// The inner payload should not be too large
		let payload = message.command.abi_encode();
		ensure!(
			payload.len() < T::MaxMessagePayloadSize::get() as usize,
			SendError::MessageTooLarge
		);

		// Ensure there is a registered channel we can transmit this message on
		ensure!(T::Channels::contains(&message.channel_id), SendError::InvalidChannel);

		// Generate a unique message id unless one is provided
		let message_id: H256 = message
			.id
			.unwrap_or_else(|| unique((message.channel_id, &message.command)).into());

		let gas_used_at_most = T::GasMeter::maximum_gas_used_at_most(&message.command);
		let fee = Self::calculate_fee(gas_used_at_most, T::PricingParameters::get());

		let queued_message: VersionedQueuedMessage = QueuedMessage {
			id: message_id,
			channel_id: message.channel_id,
			command: message.command.clone(),
		}
		.into();
		// The whole message should not be too large
		let encoded = queued_message.encode().try_into().map_err(|_| SendError::MessageTooLarge)?;

		let ticket = Ticket { message_id, channel_id: message.channel_id, message: encoded };

		Ok((ticket, fee))
	}

	fn deliver(ticket: Self::Ticket) -> Result<H256, SendError> {
		let origin = AggregateMessageOrigin::Snowbridge(ticket.channel_id);

		if ticket.channel_id != PRIMARY_GOVERNANCE_CHANNEL {
			ensure!(!Self::operating_mode().is_halted(), SendError::Halted);
		}

		let message = ticket.message.as_bounded_slice();

		T::MessageQueue::enqueue_message(message, origin);
		Self::deposit_event(Event::MessageQueued { id: ticket.message_id });
		Ok(ticket.message_id)
	}
