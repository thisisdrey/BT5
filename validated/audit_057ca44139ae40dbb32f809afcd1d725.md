### Title
Fee-tier splitting bypasses protocol fee on NEP-245/IMT transfers via per-leg `amount <= 1` exemption in `TokenDiff::token_fee` - ([File: contracts/defuse/core/src/intents/token_diff.rs])

### Summary
`TokenDiff::execute_intent` computes the fee independently for each `TokenDiff` intent's own `delta`, and `TokenDiff::token_fee` exempts any `Nep245`/`Imt` leg whose `amount <= 1` from fees regardless of `protocol_fee`. Because an unprivileged signer can submit an arbitrary number of `TokenDiff` intents inside one `MultiPayload` (or across payloads in one `execute_intents` call), a transfer of any size can be decomposed into N single-unit legs, each independently exempted, so the aggregate transferred amount pays zero fee.

### Finding Description
The claimed invariant is:
`fee_collector_balance_after − fee_collector_balance_before == Pips::fee_ceil(protocol_fee, total_negative_delta_moved_for_token)`

Trace:
- `TokenDiff::execute_intent` (`contracts/defuse/core/src/intents/token_diff.rs:41-104`) loops over `self.diff` (the deltas of a *single* `TokenDiff` intent) and for each negative delta computes:
```
let fee = Self::token_fee(token_id, amount, protocol_fee).fee_ceil(amount);
``` [1](#0-0) 
- `TokenDiff::token_fee` (`contracts/defuse/core/src/intents/token_diff.rs:206-217`) returns `Pips::ZERO` for `Nep245`/`Imt`/`Nep171` whenever `amount <= 1`, and only applies `fee` (the real `protocol_fee`) when `amount > 1`: [2](#0-1) 
- This check is scoped to the `amount` of the single intent leg, not to any aggregate over the batch. `DefuseIntents::execute_intent` simply iterates `for intent in self.intents { intent.execute_intent(...) }` (`contracts/defuse/core/src/intents/mod.rs:97-113`), and `Engine::execute_signed_intents` loops over every `MultiPayload` in the caller-supplied `Vec<MultiPayload>` (`contracts/defuse/core/src/engine/mod.rs:32-40`), with no cap or aggregation of `TokenDiff` legs across intents/payloads for fee purposes.
- The only cross-intent aggregation that exists is `TransferMatcher` (`contracts/defuse/core/src/engine/state/deltas.rs:241-392`), which matches net deposits/withdrawals per token to produce `Transfers`; it enforces that the *sum of balance deltas* nets to zero (no free minting), but it has no notion of fees and does not re-derive or check the fee that should have applied to the aggregate amount transferred.

Attacker's exact flow: attacker controls two of their own accounts, A (holder of 1,000,000 units of an `Nep245` token) and B (a second attacker-controlled account). Attacker signs N=1,000,000 separate `TokenDiff` intents (or many small `TokenDiff` intents packed into fewer `MultiPayload`s) each moving exactly `-1`/`+1` unit of the same `TokenId` between A and B, and submits them together in one `execute_intents(signed)` call. Each leg has `amount == 1`, so `token_fee` returns `Pips::ZERO` for every leg, `fee_ceil` on zero rate returns 0, and `fees_collected` stays empty for every intent (`contracts/defuse/core/src/intents/token_diff.rs:96-101`: `if !fees_collected.is_empty() { ... }` never fires). The `TransferMatcher` finalizes the whole batch (all deltas net to zero across A/B), so `execute_intents` succeeds and 1,000,000 units move from A to B with `fee_collector`'s balance unchanged, whereas the same aggregate value moved as a single `Nep141` transfer/`TokenDiff` of amount 1,000,000 would incur `protocol_fee = Pips::ONE_PERCENT` (`fee_ceil(1_000_000)` nonzero).

None of the existing guards (`MultiPayload::verify`, nonce/salt checks, `TransferMatcher::finalize`, `assert_one_yocto`, pause/role guards) address this because they operate on signature validity, replay protection, and balance-conservation — not on fee-tier aggregation across a batch. The exemption itself (`amount <= 1`) is a per-leg, stateless check with no memory of prior legs in the same signer/batch/session.

### Impact Explanation
The `fee_collector` (`contracts/defuse/src/contract/fees.rs:49-51`) never receives its due protocol fee on arbitrarily large `Nep245`/`Imt` transfers, as long as the attacker is willing to split the transfer into unit-sized legs. This matches the Critical category "protocol fees bypassed" — no funds are stolen from other users, but the protocol systematically under-collects revenue on all MT/IMT volume, and the bypass is fully repeatable across any token, any account pair, and any batch size, at the sole cost of extra intents/signatures (no monetary cost per leg beyond gas, and gas/DoS concerns are explicitly out of scope for this analysis but do not block the fee bypass logically — the point is that fee amount is fully attacker-controlled to zero for any transfer size on this token class).

### Likelihood Explanation
Preconditions are trivial for any unprivileged actor: own two accounts, hold or acquire the `Nep245`/`Imt` token balance to move, and sign N `TokenDiff` intents with `delta = ±1` for the same `TokenId`, submitted in one or more `MultiPayload`s to `execute_intents`. No special role, relayer key, or victim signature is needed. The only friction is generating/signing N legs (cost scales with N, but this is not a security control — it is simply the attacker's own transaction-construction overhead), which is fully within reach for scripted attacks and does not require unbounded gas in a single call since it can be split across multiple `execute_intents` calls.

### Recommendation
Compute the `Nep245`/`Imt` fee exemption based on the amount actually represented by the token's semantics (e.g., treat it as NFT-like only when the underlying MT token genuinely has `total_supply == 1` / is non-fungible), not on the `abs(delta)` of a single intent leg; alternatively, track and aggregate transferred amounts per `(signer_id, token_id)` across all `TokenDiff` intents within the same `execute_intents` call (and ideally within a bounded recent window) before applying the `amount <= 1` exemption, so fee computation is based on the true aggregate value moved rather than an attacker-chosen leg size.

### Proof of Concept
```
// contracts/defuse/core/src/intents/token_diff.rs (or a new tests/src/tests/defuse/intents/token_diff.rs test)
#[tokio::test]
async fn fee_bypass_via_unit_split_nep245() {
    // setup: env with protocol_fee = Pips::ONE_PERCENT, an Nep245 token contract,
    // attacker-controlled accounts A (balance 1_000_000 of token X) and B (balance 0)

    // Baseline: single TokenDiff moving -1_000_000/+1_000_000 in one intent (or Nep141 equivalent)
    // asserts fee_collector balance == Pips::ONE_PERCENT.fee_ceil(1_000_000) > 0

    // Exploit: N = 1_000_000 (or representative smaller N, e.g. 1000, scaled) TokenDiff intents,
    // each with diff = {token_id_X: -1} signed by A and {token_id_X: +1} signed by B,
    // batched into one Vec<MultiPayload> passed to execute_intents.

    // assertions:
    // - mt_balance_of(A, token_id_X) == 1_000_000 - N  (or 0 if N == 1_000_000)
    // - mt_balance_of(B, token_id_X) == N
    // - mt_balance_of(fee_collector, token_id_X) == 0   // FEES invariant broken: expected nonzero
    assert_eq!(fee_collector_balance, 0);
}
```
This demonstrates the equality `fee_collector_credited (0) == Pips::fee_ceil(protocol_fee, total_moved=1_000_000)` fails to hold (RHS is nonzero, LHS is zero), confirming the fee bypass.
