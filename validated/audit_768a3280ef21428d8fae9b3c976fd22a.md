### Title
Operator Can Permanently Freeze Staker Funds via Malicious `beneficiary_for_operator` in `staking_contract.move` — (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

---

### Summary

`staking_contract::set_beneficiary_for_operator()` accepts any arbitrary address as the new beneficiary with no validation that the address can receive APT. When `distribute_internal()` later calls `aptos_account::deposit_coins()` to pay the operator's commission to that beneficiary, the call aborts if the beneficiary account exists but has opted out of direct coin transfers (`allow_arbitrary_coin_transfers = false`) and is not registered for `AptosCoin`. Because `distribute_internal()` is called atomically inside `distribute()`, `unlock_stake()`, and `switch_operator()`, a single malicious operator can permanently prevent the staker from ever withdrawing their staked APT or rewards.

---

### Finding Description

**Root cause — missing beneficiary validation in `set_beneficiary_for_operator`**

`staking_contract::set_beneficiary_for_operator()` stores any caller-supplied address without checking whether it can receive APT: [1](#0-0) 

Compare this to `vesting::set_beneficiary()`, which explicitly guards against exactly this scenario: [2](#0-1) 

The guard `assert_account_is_registered_for_apt(new_beneficiary)` is present in the vesting module but entirely absent in `staking_contract`.

**Propagation — `distribute_internal()` calls `deposit_coins()` on the operator's beneficiary**

Inside `distribute_internal()`, when the current distribution recipient is the operator, the code redirects payment to `beneficiary_for_operator(operator)` and immediately calls `aptos_account::deposit_coins()`: [3](#0-2) 

**Abort condition — `deposit_coins` aborts on opted-out, unregistered accounts**

`aptos_account::deposit_coins()` aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` when the recipient account exists, is **not** registered for `AptosCoin`, and has explicitly set `allow_arbitrary_coin_transfers = false`: [4](#0-3) 

Any account can reach this state by calling `aptos_account::set_allow_direct_coin_transfers(false)` without ever registering for `AptosCoin`: [5](#0-4) 

**Blast radius — all staker exit paths call `distribute_internal()`**

`distribute_internal()` is called unconditionally by `distribute()`, `unlock_stake()`, and `switch_operator()`: [6](#0-5) 

If `distribute_internal()` always aborts, the staker has no remaining path to recover their principal or rewards.

---

### Impact Explanation

A malicious operator permanently freezes the staker's APT principal and all accumulated staking rewards. The staker cannot call `distribute()`, `unlock_stake()`, or `switch_operator()` — every path aborts at the `deposit_coins` call for the operator's commission. This constitutes **permanent freezing of user-controlled staking balances**, which is within the Aptos bounty's allowed impact scope.

---

### Likelihood Explanation

The attack is fully unprivileged. Any operator can:
1. Create a fresh account, call `set_allow_direct_coin_transfers(false)`, and never register for `AptosCoin`.
2. Call `set_beneficiary_for_operator(malicious_address)` — no framework permission required, only the `operator_beneficiary_change_enabled` feature flag, which is a live mainnet feature.
3. Wait for any non-zero commission to accumulate (guaranteed whenever the stake pool earns rewards and `commission_percentage > 0`).

After step 3, every call to `distribute_internal()` for that staking contract aborts, permanently locking the staker's funds.

---

### Recommendation

Add the same guard that `vesting::set_beneficiary()` already uses:

```move
public entry fun set_beneficiary_for_operator(
    operator: &signer, new_beneficiary: address
) acquires BeneficiaryForOperator {
    assert!(
        features::operator_beneficiary_change_enabled(),
        std::error::invalid_state(EOPERATOR_BENEFICIARY_CHANGE_NOT_SUPPORTED)
    );
+   // Ensure the beneficiary can receive APT, mirroring vesting::set_beneficiary().
+   aptos_account::assert_account_is_registered_for_apt(new_beneficiary);
    ...
}
```

Additionally, consider restructuring `distribute_internal()` to skip or defer a recipient that cannot receive funds rather than aborting the entire distribution, so that one bad recipient cannot block all others.

---

### Proof of Concept

```
1. Alice (staker) creates a staking contract with Bob (operator), commission_percentage = 10.
2. Bob creates address EVIL:
     - calls account::create_account(EVIL)
     - signs as EVIL: aptos_account::set_allow_direct_coin_transfers(false)
     - never calls coin::register<AptosCoin> for EVIL
3. Bob calls staking_contract::set_beneficiary_for_operator(EVIL).
   → No validation; BeneficiaryForOperator { beneficiary_for_operator: EVIL } is stored.
4. Stake pool earns rewards over one epoch.
5. Alice calls staking_contract::unlock_stake(alice, bob, amount).
   → unlock_stake calls distribute_internal(alice, bob, staking_contract).
   → distribute_internal calls update_distribution_pool, which transfers commission shares to Bob.
   → Loop: recipient = bob → recipient = beneficiary_for_operator(bob) = EVIL.
   → aptos_account::deposit_coins(EVIL, commission_coins):
       - account::exists_at(EVIL) == true  (account was created)
       - coin::is_account_registered<AptosCoin>(EVIL) == false
       - can_receive_direct_coin_transfers(EVIL) == false  (opted out)
       → ABORT: EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS
6. Transaction reverts. Alice's principal and rewards are permanently locked.
   Every subsequent call to distribute(), unlock_stake(), or switch_operator() also aborts.
```
