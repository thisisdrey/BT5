### Title
Protocol fee bypass on `Nep245`/`Imt` `TokenId`s via unit-delta leg-splitting across a `TokenDiff` batch - (`contracts/defuse/core/src/intents/token_diff.rs`)

### Summary
`TokenDiff::execute_intent` computes the protocol fee independently for each `TokenDiff` intent, based solely on that intent's own per-`TokenId` delta magnitude, rather than on the true net amount of that `TokenId` moved across the whole batch. Because `Self::token_fee` returns `Pips::ZERO` whenever `amount <= 1` for `Nep245`/`Imt` token types, an attacker can split a large trade into many unit-magnitude `TokenDiff` legs and pay zero fee on the entire trade, whereas an equivalent single-intent trade with the same aggregate magnitude would be charged the normal fee.

### Finding Description
The broken binding: `total fees credited to fee_collector across the batch == fee owed on the true aggregate delta magnitude for that TokenId`. This does not hold.

In `TokenDiff::execute_intent` [1](#0-0) , for each `(token_id, delta)` pair inside a single `TokenDiff.diff`, if `delta < 0` the fee is computed as `Self::token_fee(token_id, amount, protocol_fee).fee_ceil(amount)` where `amount = delta.unsigned_abs()` — strictly local to that one intent's delta.

`Self::token_fee` exempts `Nep245`/`Imt` from fees whenever `amount <= 1`: [2](#0-1) . This threshold check has no knowledge of how many other `TokenDiff` intents in the same batch move the same `TokenId`.

Because `internal_add_balance`/`internal_sub_balance` route through `Deltas::deltas` (the `TransferMatcher`) which accumulates deposits/withdrawals per `TokenId` across the *entire* batch and requires them to net to exactly zero via `TransferMatcher::finalize` [3](#0-2) [4](#0-3) , the fee-collector credit (`fees_collected`) is itself deposited through this matcher [5](#0-4) . When the fee is zero for every leg (because each leg's `amount == 1`), no extra deposit needs to be matched by an extra withdrawal, so the batch settles cleanly with zero fee collected overall — even though the same aggregate token movement done as one `TokenDiff` with `delta` magnitude `> 1` would trigger the non-exempt branch (`amount > 1`) and charge the normal `protocol_fee`.

Exploit: an attacker (as solver or via two accounts they control) constructs `N` `TokenDiff` intents that together move `N` units of a `Nep245`/`Imt` `TokenId` (e.g., `N` legs of `delta = -1`/`+1` matched pairwise across two signers, or against themselves in aggregate), signs them, and submits them all in one `execute_intents`/`MultiPayload` batch. Each leg independently hits the `amount <= 1` branch of `token_fee`, so `fees_collected` stays empty on every intent; the aggregated real transfer of `N` units incurs zero protocol fee, versus the non-zero fee an equivalent single `-N` delta intent would incur.

None of the existing guards catch this: `MultiPayload::verify`/nonce checks only ensure authenticity/replay-protection of each signed intent, not aggregation of fee-relevant amounts; `TransferMatcher::finalize`'s invariant only checks that deltas (including whatever fee deposits actually occurred) net to zero — it does not independently recompute what the fee *should* have been on the netted amount.

### Impact Explanation
This is a direct protocol fee bypass: fees that should be credited to `fee_collector` for genuine, larger-magnitude MT/IMT token trades can be entirely avoided by structuring the trade as many unit-delta `TokenDiff` intents in a single batch. This matches the explicitly listed critical category "protocol fees bypassed." The blast radius covers all `Nep245`/`Imt`-typed tokens integrated with the Defuse Verifier; it is repeatable indefinitely by any solver/user pair (or self-pair) for any batch, at the cost of needing to sign and submit more individual intents.

### Likelihood Explanation
No privileged role is required — any two unprivileged accounts (or one attacker controlling both legs) with `Nep245`/`Imt` balances deposited in the Verifier can perform this. The only cost is generating and signing more payloads (linear in the number of unit legs), which is a routine operation available to any external caller of `execute_intents`. The threshold that must be respected is simply keeping every per-intent per-token delta at magnitude `<= 1`, which is trivial for an attacker to construct deliberately.

### Recommendation
Compute (or validate) the `Nep245`/`Imt` fee exemption based on the net aggregate magnitude of each `TokenId` across the whole batch (e.g., at the `Deltas`/`TransferMatcher` finalization stage, or by tracking cumulative per-`TokenId` negative-delta magnitude across all intents in `execute_signed_intents` before applying `token_fee`), rather than per single `TokenDiff` intent's isolated delta.

### Proof of Concept
`cargo test` (or `near-workspaces` sandbox) plan:
1. Deposit an MT (`Nep245`) or IMT balance of `N` units (e.g., 100) for a signer/solver-pair.
2. Scenario A: execute a single `TokenDiff` batch where the paying account's diff has `delta = -N` for that `TokenId` (matched by a counterparty's `+N`), with `protocol_fee > 0`. Assert `fee_collector`'s balance for that `TokenId` increases by `token_fee(..., N, fee).fee_ceil(N) > 0`.
3. Scenario B: execute a batch of `N` separate `TokenDiff` intents, each with `delta = -1`/`+1` for the same `TokenId` and same pair of accounts, submitted together via `execute_intents`. Assert `fee_collector`'s balance for that `TokenId` is unchanged (`0`).
4. Assert the two scenarios produce different `fee_collector` balances despite moving the same aggregate `N` units of the same `TokenId`, demonstrating the fee bypass via leg-splitting granularity.

        &mut self,
        owner_id: AccountId,
        tokens: impl IntoIterator<Item = (TokenId, u128)>,
    ) -> Result<()> {
        for (token_id, amount) in tokens {
            self.state
                .internal_add_balance(owner_id.clone(), [(token_id.clone(), amount)])?;
            if !self.deltas.deposit(owner_id.clone(), token_id, amount) {
