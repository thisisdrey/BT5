### Title
Missing Slippage Protection in `ExchangeInjectActuator` / `ExchangeWithdrawActuator` Allows Front-Run Manipulation of Bancor Exchange Rate - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
TRON's TRC10 Bancor-style `Exchange` supports four user-facing operations: create, inject, withdraw, and transaction (swap). `ExchangeTransactionActuator` explicitly implements slippage protection via an `expected` field that is validated against the computed `anotherTokenQuant` [1](#0-0) . However, `ExchangeInjectActuator` and `ExchangeWithdrawActuator`, which also compute a counter-token amount from the live pool ratio (`firstTokenBalance`/`secondTokenBalance`) at execution time, have no equivalent bound — the `ExchangeInjectContract`/`ExchangeWithdrawContract` protobuf messages carry no `expected`/`min`/`max` field at all. This is the exact bug class described in the external report: a rate/index used to compute a minted or returned amount can be shifted between transaction submission and execution, with no way for the caller to bound the resulting output.

### Finding Description
Any account can become the `creator` of an exchange pool by calling `ExchangeCreateActuator`, and any account can call `ExchangeTransactionActuator` to swap against that pool, which directly mutates `firstTokenBalance`/`secondTokenBalance` via `exchangeCapsule.transaction(...)` and `Commons.putExchangeCapsule(...)` [2](#0-1) .

When the pool creator later calls `ExchangeInjectActuator.execute`, the amount of the paired token that must be deducted from the creator's balance (`anotherTokenQuant`) is computed purely from the pool balances observed at execution time: [3](#0-2) 
There is no user-supplied bound on `anotherTokenQuant`; validation only checks that the creator's balance is sufficient for whatever amount is computed [4](#0-3) .

Similarly, `ExchangeWithdrawActuator.execute` computes the counter-token amount returned to the creator from the live ratio, with no minimum-output guarantee for the creator [5](#0-4) .

Because any unprivileged account can submit `ExchangeTransactionContract` swaps that move `firstTokenBalance`/`secondTokenBalance` immediately before the creator's `ExchangeInjectContract`/`ExchangeWithdrawContract` is packed into a block, an attacker can sandwich the creator's transaction:
1. Attacker observes a pending `ExchangeInject`/`ExchangeWithdraw` from the creator in the mempool.
2. Attacker front-runs with a large `ExchangeTransaction` swap that skews the `firstTokenBalance:secondTokenBalance` ratio.
3. The creator's inject executes against the skewed ratio, forcing them to deposit far more of the paired token than intended (value extraction via inflated required contribution), or the creator's withdraw executes against the skewed ratio, returning far less of the paired token than intended (value extraction via reduced payout).
4. Attacker can then reverse the swap (back-run) to restore the ratio and pocket the difference, or the ratio just organically stays skewed while the creator has already lost value.

This mirrors the reported class exactly: a mintable/returnable amount derived from a manipulable running rate, with no way for the caller to specify a minimum acceptable output or maximum acceptable input, unlike the sibling `ExchangeTransactionActuator`, which already carries this protection.

### Impact Explanation
An attacker who can broadcast ordinary signed transactions (any account, no special privileges, SR/witness role, or elevated permission required) can extract value from a pool creator's TRC10 liquidity by sandwiching `ExchangeInjectContract`/`ExchangeWithdrawContract` transactions, causing the creator to lose funds (either by overpaying on inject or under-receiving on withdraw). This is a concrete theft-of-funds impact reachable purely through the normal, unprivileged `Exchange*Actuator` transaction path.

### Likelihood Explanation
Exploitation requires only the ability to submit ordinary TRC10 exchange transactions and observe pending transactions (mempool visibility), both of which are available to any network participant. No malicious SR/witness/peer behavior, no leaked keys, and no protocol-level fork are needed — the actuators as implemented already lack the bound.

### Recommendation
Add an `expected` (minimum-received) field to `ExchangeInjectContract` and a `max`/`expected` (maximum-required or minimum-received) field to `ExchangeWithdrawContract`, mirroring the existing pattern in `ExchangeTransactionContract`/`ExchangeTransactionActuator`, and validate the computed `anotherTokenQuant` against it in `doValidate()` before allowing execution, reverting with a `ContractValidateException` if the bound is not met.

### Proof of Concept
1. Attacker or any account calls `ExchangeCreateActuator` to establish a TRX/TRC10 pool, or targets an existing pool.
2. Pool creator broadcasts `ExchangeInjectContract` (or `ExchangeWithdrawContract`) intending to inject/withdraw at the currently observed ratio.
3. Before this transaction is packed, attacker broadcasts an `ExchangeTransactionContract` swap large enough to shift `firstTokenBalance`/`secondTokenBalance` significantly, as computed in `ExchangeCapsule.transaction(...)` and applied in `ExchangeTransactionActuator.execute` [6](#0-5) .
4. The creator's `ExchangeInjectActuator`/`ExchangeWithdrawActuator` executes against the now-skewed ratio, computing an `anotherTokenQuant` far different from what the creator expected when signing, with no revert path since no minimum/maximum bound exists [3](#0-2) .
5. Attacker optionally reverses the swap in a following transaction, realizing the extracted value while the creator has permanently lost funds from the mismatch.
