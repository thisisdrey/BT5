### Title
Unbounded synchronous VotesStore scan in block-application path enables maintenance-cycle stall (soft-lockup analog) - (File: consensus/src/main/java/org/tron/consensus/dpos/MaintenanceManager.java)

### Summary
The Linux CVE fixes an unbounded, uninterruptible processing loop (CEQEs) running in a latency-critical context (interrupt handler) with no per-call cap, causing soft lockups. The structural analog in java-tron is `MaintenanceManager.countVote()`, which does a full linear scan-and-mutate over the entire `VotesStore` with no upper bound, executed synchronously inside the single-threaded block-application call chain (`Manager.processBlock` → `consensus.applyBlock` → `DposService.applyBlock` → `MaintenanceManager.applyBlock` → `doMaintenance`) every time a maintenance-cycle boundary is crossed.

### Finding Description
`VoteWitnessActuator`/`VoteWitnessProcessor` only bound the number of votes *per transaction* (`MAX_VOTE_NUMBER`) [4](#0-3) , and each vote is persisted keyed by the voter's own address in `VotesStore` via `countVoteAccount()` [5](#0-4) . There is no global limit on the number of distinct voter addresses (i.e., number of `VotesStore` entries) that can exist across an epoch — any number of accounts, each holding minimal frozen TRON Power, can each cast a `VoteWitnessContract`, and each becomes a separate row in `VotesStore`.

At every maintenance-time boundary (an interval reached deterministically by block timestamp, not gated by any per-call budget), `MaintenanceManager.doMaintenance()` invokes `countVote(votesStore)`, which iterates the *entire* `VotesStore` with a `while (dbIterator.hasNext())` loop, doing per-entry `forEach` over old/new votes and a synchronous `votesStore.delete(next.getKey())` DB write for every entry [3](#0-2) . This entire operation runs on the same thread that is applying/producing blocks — there is no chunking, no yielding, no upper bound on iteration count comparable to the kernel's fix ("set an upper limit for the number of CEQE handled by a single call"), and no offloading to a background worker.

Because vote casting is reachable by any unprivileged transaction broadcaster (only cost: enough TRX frozen for TRON Power on many funded accounts), an attacker can inflate `VotesStore` to a very large number of entries before a maintenance boundary is crossed, causing `doMaintenance()`/`countVote()` to take arbitrarily long on the block-processing thread of every full node in the network simultaneously (since maintenance time is a chain-wide, deterministic value, not per-node).

### Impact Explanation
`doMaintenance()` runs inside `processBlock()`, which is the same call path used both to validate/apply blocks received from peers and to generate blocks as a witness. A sufficiently large `VotesStore` at the maintenance boundary stalls block processing/production network-wide for the duration of the scan, degrading or halting liveness across the chain until the maintenance pass completes — a network-wide DoS analogous to the soft lockup described in the CVE, reachable purely from unprivileged, self-funded transactions (no special privileges required).

### Likelihood Explanation
Moderate-to-high: an attacker needs capital to fund many accounts with minimal TRON Power to vote, but no privileged access, code execution, or protocol bypass is required — just ordinary `VoteWitnessContract` broadcasts from many addresses ahead of a maintenance boundary (maintenance boundaries recur periodically and deterministically). The larger the attacker's capital/account fan-out, the larger the resulting stall.

### Recommendation
Bound the amount of work `doMaintenance()`/`countVote()` can perform per maintenance cycle: cap or paginate the number of `VotesStore` entries processed per call (mirroring the kernel fix's "upper limit for the number of CEQE handled by a single call"), and/or move the scan off the block-application critical thread into a background task with a hard iteration budget so that block validation/production cannot be blocked by an unbounded vote count.

### Proof of Concept
1. Fund N accounts (N large, e.g. tens of thousands) with the minimum TRX needed to freeze for TRON Power.
2. From each account, broadcast a `VoteWitnessContract` transaction before the next maintenance-time boundary, so each address gets its own entry in `VotesStore` via `VoteWitnessActuator.countVoteAccount()`.
3. When `consensusDelegate.getNextMaintenanceTime() <= blockTime` becomes true on the next block, every node's `processBlock()` synchronously invokes `MaintenanceManager.doMaintenance()` → `countVote(votesStore)`, which must scan and delete all N entries in a single, unbounded loop on the block-application thread, stalling block validation/production for the duration proportional to N.

  private Map<ByteString, Long> countVote(VotesStore votesStore) {
    final Map<ByteString, Long> countWitness = Maps.newHashMap();
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();
    long sizeCount = 0;
    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) - voteCount);
        } else {
          countWitness.put(voteAddress, -voteCount);
        }
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) + voteCount);
        } else {
          countWitness.put(voteAddress, voteCount);
        }
      });
      sizeCount++;
      votesStore.delete(next.getKey());
    }
    logger.info("There is {} new votes in this epoch", sizeCount);
    return countWitness;
  }

  private void countVoteAccount(VoteWitnessContract voteContract) {
    AccountStore accountStore = chainBaseManager.getAccountStore();
    VotesStore votesStore = chainBaseManager.getVotesStore();
    MortgageService mortgageService = chainBaseManager.getMortgageService();
    byte[] ownerAddress = voteContract.getOwnerAddress().toByteArray();

    VotesCapsule votesCapsule;

    //
    mortgageService.withdrawReward(ownerAddress);

    AccountCapsule accountCapsule = accountStore.get(ownerAddress);

    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    if (dynamicStore.supportAllowNewResourceModel()
        && accountCapsule.oldTronPowerIsNotInitialized()) {
      accountCapsule.initializeOldTronPower();
    }

    if (!votesStore.has(ownerAddress)) {
      votesCapsule = new VotesCapsule(voteContract.getOwnerAddress(),
          accountCapsule.getVotesList());
    } else {
      votesCapsule = votesStore.get(ownerAddress);
    }

    accountCapsule.clearVotes();
    votesCapsule.clearNewVotes();

    voteContract.getVotesList().forEach(vote -> {
      logger.debug("countVoteAccount, address[{}]",
          ByteArray.toHexString(vote.getVoteAddress().toByteArray()));

      votesCapsule.addNewVotes(vote.getVoteAddress(), vote.getVoteCount());
      accountCapsule.addVotes(vote.getVoteAddress(), vote.getVoteCount());
    });

    accountStore.put(accountCapsule.createDbKey(), accountCapsule);
    votesStore.put(ownerAddress, votesCapsule);
  }
