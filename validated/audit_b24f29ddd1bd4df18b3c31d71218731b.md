### Title
Unguarded Division by `totalEnergyWeight` in `RepositoryImpl.calculateGlobalEnergyLimit` Relies on a No-Op Java `assert` - (File: `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java`)

### Summary
`RepositoryImpl.calculateGlobalEnergyLimit` divides `energyWeight * totalEnergyLimit` by `totalEnergyWeight` without a real runtime guard, protecting the divisor only with a Java `assert` statement, which is compiled out / disabled at runtime unless the JVM is started with `-ea`. This is the same bug class as the reported `L2ECOBridge.finalizeDeposit` issue: a divisor sourced from mutable chain/contract state is used in a division without an enforced non-zero check.

### Finding Description [1](#0-0) 

```java
public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
  long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
  if (frozeBalance < TRX_PRECISION) {
    return 0;
  }
  long energyWeight = frozeBalance / TRX_PRECISION;
  long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
  long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

  assert totalEnergyWeight > 0;

  if (hardenResourceCalculation()) {
    return BigInteger.valueOf(energyWeight)
        .multiply(BigInteger.valueOf(totalEnergyLimit))
        .divide(BigInteger.valueOf(totalEnergyWeight))
        .longValueExact();
  }
  return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
}
```

`assert` statements in Java are disabled by default unless the JVM flag `-ea` is passed; java-tron nodes are not run with assertions enabled in production. This means the `assert totalEnergyWeight > 0;` line provides no actual protection — if `totalEnergyWeight` (`DynamicPropertiesStore.getTotalEnergyWeight()`) is `0`, execution falls through directly into the division, throwing an uncaught `ArithmeticException` (integer division) or, in the `hardenResourceCalculation()` path, a `BigInteger` division-by-zero `ArithmeticException`.

This is directly analogous to the reported class of bug: `_amount / inflationMultiplier` in `L2ECOBridge.finalizeDeposit` divides by a mutable global-state value without validating it is non-zero. Here, `totalEnergyWeight` is likewise a mutable, chain-wide dynamic property that this actuator-adjacent VM code assumes (via an unenforced `assert`) is always positive, rather than validating it.

By contrast, the sibling implementation `EnergyProcessor.calculateGlobalEnergyLimit` in `chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java` (lines 145-166) demonstrates the fix was already applied there for one code path: it explicitly checks `if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) { return 0; }` before falling back to the same ineffective `assert`. This confirms the project is aware `totalEnergyWeight` can reach zero and requires guarding, but the `RepositoryImpl` copy used by the TVM/VMActuator execution path was never given this real guard. [2](#0-1) 

This vulnerable method is reachable from any unprivileged smart-contract call: `VMActuator.getAccountEnergyLimitWithFloatRatio` calls `rootRepository.calculateGlobalEnergyLimit(account)` whenever the calling/creator account has `totalBalanceForEnergyFreeze != 0`, which happens on every `TriggerSmartContract` transaction from an account that has frozen TRX for energy. [3](#0-2) 

### Impact Explanation
If `totalEnergyWeight` (the network-wide total frozen-for-energy weight) is ever `0` — which is architecturally possible since it is decremented as accounts unfreeze energy stakes and is not floor-protected anywhere in `DynamicPropertiesStore` — any subsequent contract-triggering transaction from an account with a nonzero frozen-for-energy balance will trigger an uncaught `ArithmeticException` inside `RepositoryImpl.calculateGlobalEnergyLimit`, called from `VMActuator` while calculating the account's TVM energy limit. `VMActuator.execute()`/`call()` does not wrap this computation in an exception handler for `ArithmeticException`, so the exception propagates out of the actuator during transaction execution. This is invoked during normal block application for every smart-contract transaction, so it directly threatens the availability of the transaction-processing / block-application path — potentially causing repeated transaction execution failures or crashing block processing (matching the "node crash or halt" bar) rather than a graceful revert.

### Likelihood Explanation
This requires the specific network state where `totalEnergyWeight == 0`. This can occur if all frozen-for-energy balances are unfrozen across the network (a realistic scenario for private/test networks, freshly bootstrapped networks, or in edge cases after mass migration/unfreeze events under `FreezeV2`/`allowNewReward` transitions), combined with an account that still shows `getAllFrozenBalanceForEnergy() >= TRX_PRECISION` (e.g., through a state-transition edge case, or simply on a fresh chain where energy weight tracking hasn't been initialized). The reachability trigger — a normal `TriggerSmartContract` transaction from any account with frozen energy — requires no special privileges, matching the "unprivileged transaction broadcaster" criterion. However, achieving `totalEnergyWeight == 0` on a live mainnet with many stakers is unlikely in practice; this is a genuine but conditionally-reachable defect, primarily elevated by the fact that the intended safeguard (`assert`) is a no-op in production builds.

### Recommendation
Replace the `assert totalEnergyWeight > 0;` with an explicit runtime check consistent with `EnergyProcessor.calculateGlobalEnergyLimit`, e.g.:
```java
if (totalEnergyWeight <= 0) {
  return 0;
}
```
before performing either the `BigInteger` division or the double-based division, so the method never falls through to a division whose divisor may be zero.

### Proof of Concept
1. Drive `DynamicPropertiesStore.getTotalEnergyWeight()` to `0` (e.g., via a test harness directly calling `saveTotalEnergyWeight(0)`, or through a sequence of `UnfreezeBalanceActuator`/`UnfreezeBalanceV2Actuator` calls that bring total network energy weight to zero on a low-stake private/test network).
2. Have any account with `getAllFrozenBalanceForEnergy() >= TRX_PRECISION` issue a `TriggerSmartContract` transaction (calling any deployed contract).
3. `VMActuator.getAccountEnergyLimitWithFloatRatio` invokes `rootRepository.calculateGlobalEnergyLimit(account)` [4](#0-3) , which executes the unguarded division in `RepositoryImpl.calculateGlobalEnergyLimit` [5](#0-4) , throwing `ArithmeticException` (division by zero, either from `long` integer division or `BigInteger.divide`) uncaught within transaction processing.

This mirrors the existing project test `CalculateGlobalLimitHardenTest` which already demonstrates `ArithmeticException` being thrown from the sibling hardened-division code paths under degenerate inputs [6](#0-5) , confirming these divisions are not exception-safe when the divisor collapses to zero.
