### Title
Unbounded `estimated_len` from `/v2/fees/transaction` request body causes integer overflow in fee floor computation - (File: stackslib/src/net/api/postfeerate.rs)

### Summary
`RPCPostFeeRateRequestHandler::try_parse_request` accepts an attacker-controlled `estimated_len` field from the JSON body with no upper bound check, and forwards it unmodified to `estimate_tx_fee_from_cost_and_length`, where it is multiplied by `MINIMUM_TX_FEE_RATE_PER_BYTE` with the plain `*` operator. A remote, unauthenticated caller can set `estimated_len` to `u64::MAX` while supplying a trivially small real `transaction_payload`, producing a `u64` multiplication overflow and/or a fee value with no relation to the actual transaction size.

### Finding Description
The claimed equality — "`estimated_len` used for the fee floor == the length the caller-declared transaction will actually occupy on the wire" — is not enforced anywhere in this code path. `try_parse_request` computes: [1](#0-0) 

`body.estimated_len` is an `Option<u64>` deserialized directly from client JSON with no range/consistency check against `payload_data.len()` other than taking the `max`, i.e. any value ≥ real payload length (including `u64::MAX`) passes through unmodified. The only prior validation is on `content_length` of the whole HTTP body (must be `< MAX_PAYLOAD_LEN`), which bounds the size of the JSON text, not the numeric value of an integer field inside it: [2](#0-1) 

This `estimated_len` is later used, unguarded, in a plain multiplication: [3](#0-2) 

`MINIMUM_TX_FEE_RATE_PER_BYTE` is a nonzero constant defined in `stackslib/src/chainstate/stacks/db/blocks.rs`; multiplying it by `u64::MAX` (or any sufficiently large attacker-chosen value) overflows `u64`. In debug builds (overflow checks enabled) this panics inside the request-handling thread; in release builds (Rust's default overflow behavior for release profiles) it silently wraps, producing an internally inconsistent `RPCFeeEstimate.fee` value the endpoint returns as if it were a valid minimum-fee floor. Neither `will_admit_mempool_tx` nor any mempool/consensus check is invoked on this endpoint — it is a pure read/estimate endpoint reachable without the node's RPC secret.

### Impact Explanation
Per attacker-controlled HTTP POST message to `/v2/fees/transaction`, the caller can (a) crash the node's HTTP handler thread on debug/overflow-checked builds via an arithmetic-overflow panic, satisfying a Critical single-message-crash class, or (b) on release builds, receive/force emission of `RPCFeeEstimate.fee` values that are wrapped/nonsensical and disconnected from the real transaction size, which is a bounded compute/logic distortion of a read endpoint (High). The request is trivially repeatable and requires no state, peer registration, or secret.

### Likelihood Explanation
The endpoint is public JSON-RPC (`/v2/fees/transaction`), requires only a well-formed JSON body with a valid hex `transaction_payload` and one large integer `estimated_len` field, and no authentication/secret. Attacker cost is a single small HTTP POST; the flaw is deterministically reachable every time cost/fee estimators are configured on the node (`rpc_args.get_estimators_ref()` returning `Some`).

### Recommendation
Bound `estimated_len` to a sane maximum (e.g., `MAX_PAYLOAD_LEN` or a small multiple of `payload_data.len()`), reject values above that threshold with a 400 in `try_parse_request`, and replace the raw `*` in `estimate_tx_fee_from_cost_and_length` with `checked_mul`/`saturating_mul`, returning a `HttpBadRequest` on overflow instead of allowing an unchecked panic or silent wraparound.

### Proof of Concept
Add a test in `stackslib/src/net/api/tests/postfeerate.rs` that constructs an HTTP POST to `/v2/fees/transaction` with body `{"estimated_len": 18446744073709551615, "transaction_payload": "<hex of a minimal valid TransactionPayload, e.g. a short token-transfer payload>"}`, drive it through `RPCPostFeeRateRequestHandler::try_parse_request` and `try_handle_request` (or the full HTTP handling harness used by existing `postfeerate` tests), and assert that either: the handler returns a clean 400 (expected if a fix bounding `estimated_len` is applied) — currently it does not — or, on an overflow-checked (debug) build, the thread panics at `estimated_len * MINIMUM_TX_FEE_RATE_PER_BYTE` in `estimate_tx_fee_from_cost_and_length` (`stackslib/src/net/api/postfeerate.rs:112`), demonstrating the unguarded multiplication.
