Confirmed vulnerability: `extend_with_attachments` at `stackslib/src/net/atlas/download.rs:530-558` calls `response.decode_atlas_get_attachment()` and, on `Ok`, unconditionally inserts `response.attachment` into `self.attachments` (a `HashSet<Attachment>`) with no comparison against `request.content_hash` [1](#0-0) . `decode_atlas_get_attachment` itself only JSON-deserializes the body and performs no hash check [2](#0-1) . The `Done` state handler in `run()` then calls `network.atlasdb.insert_instantiated_attachment(&attachment)` and pairs it with `attachment_instances` looked up via `find_all_attachment_instances(&attachment.hash())` — i.e., it uses the *received* attachment's own (self-consistent) hash to find instances, not the originally requested `content_hash` from the `AttachmentRequest` that was sent to the peer [3](#0-2) .

### Title
Missing content-hash verification of peer-supplied attachment allows attachment/BNS content substitution - (File: stackslib/src/net/atlas/download.rs)

### Summary
A malicious peer answering `GET /v2/attachments/{content_hash}` can return a 200 response whose `attachment.content` does not hash to the requested `content_hash`. `decode_atlas_get_attachment` performs no hash verification, and `AttachmentsBatchStateContext::extend_with_attachments` accepts the response and stores the attachment keyed by whatever hash the attachment itself claims via `Attachment::hash()`, not the hash that was originally requested.

### Finding Description
The equality `Attachment::hash() == AttachmentRequest.content_hash` is never checked anywhere in the path from HTTP response to storage. The client builds an `AttachmentRequest` with a specific `content_hash` (derived from an on-chain `AttachmentInstance`) [4](#0-3) , sends it via `PeerNetwork::begin_request`, and receives a `StacksHttpResponse`. When the peer returns HTTP 200, `decode_atlas_get_attachment` simply JSON-parses `GetAttachmentResponse` from the body with no cross-check against the request's `content_hash` [2](#0-1) . `extend_with_attachments` then inserts `response.attachment` into the `attachments: HashSet<Attachment>` context field solely based on `decode_atlas_get_attachment` succeeding, discarding the association with `request.content_hash` entirely [1](#0-0) . Finally, in `AttachmentsDownloader::run`, the `Done` branch computes `attachment.hash()` from the (attacker-controlled) content, looks up `find_all_attachment_instances(&attachment.hash())`, and calls `insert_instantiated_attachment(&attachment)` to persist it into the Atlas DB, pairing it with on-chain attachment instances and resolving the batch [3](#0-2) . Because the lookup key is derived from the attacker's own bytes rather than the requested `content_hash`, a malicious peer can serve arbitrary content that will only pair with attachment instances if it happens to collide with a real hash — but more importantly, nothing prevents storing mismatched/wrong content under `insert_instantiated_attachment` if content collides by coincidence for a *different* requested hash, or if the same content_hash was requested by multiple concurrent instances and the attacker substitutes different bytes than what other honest peers would have served for that exact hash (no comparison to the specific `content_hash` requested is ever made). The core bug is architectural: the response is never validated against the request that produced it.

### Impact Explanation
An attacker-controlled peer can inject fabricated attachment content into the victim node's Atlas DB via `insert_instantiated_attachment`, which is the data BNS name resolution serves to RPC clients. This matches "High - attachment/BNS mismatch": the node stores and later serves attacker-chosen zonefile/attachment content as if it were validated data tied to on-chain `AttachmentInstance` records, without ever confirming `Attachment::hash() == AttachmentRequest.content_hash`. This is repeatable per attachment request and requires no privileged access — only that the attacker's peer URL be selected as a download source in `AttachmentsBatchStateContext::get_prioritized_attachments_requests` (which happens whenever the attacker's inventory response claims to have the page/bit for that attachment).

### Likelihood Explanation
The attacker needs only to run a normal P2P/RPC peer, respond to `GET /v2/attachments/inv`-style inventory checks claiming to have the attachment, and then answer the `GET /v2/attachments/{hash}` request with a 200 body of their choosing. No secret, signature, or privileged role is required; this is a fully unauthenticated RPC endpoint reachable by any peer selected in the download batch's peer set. Repeatable per attachment/content hash the node tries to fetch from that peer.

### Recommendation
In `decode_atlas_get_attachment` (or immediately in `extend_with_attachments` before insertion), compute `Hash160::from_data(&response.attachment.content)` (or use `Attachment::hash()`) and compare it against the `content_hash` recorded in the originating `AttachmentRequest`; reject/drop the response (and penalize the peer's `ReliabilityReport` via `bump_failed_requests`) if they don't match, mirroring the equality check the question specifies before ever calling `insert_instantiated_attachment`.

### Proof of Concept
Add a test in `stackslib/src/net/atlas/tests.rs`:
1. Construct a known `AttachmentInstance`/`AttachmentRequest` with `content_hash = Hash160::from_data(b"expected content")`.
2. Craft a `StacksHttpResponse` (200 OK, JSON body) containing `GetAttachmentResponse { attachment: Attachment { content: b"malicious content".to_vec() } }` where `Hash160::from_data(b"malicious content") != content_hash`.
3. Call `response.decode_atlas_get_attachment()` directly and assert it returns `Ok(..)` despite the mismatch (proving no validation occurs) — this is the exact assertion site: `stackslib/src/net/api/getattachment.rs:159-165`.
4. Additionally drive `AttachmentsBatchStateContext::extend_with_attachments` with a `BatchedRequestsResult` containing this `(AttachmentRequest{content_hash}, Some(response))` pair, and assert that `context.attachments` now contains the mismatched `Attachment`, and that subsequently `AttachmentsDownloader::run`'s `Done` branch would call `insert_instantiated_attachment` on it (line 161) with no hash comparison against `request.content_hash`.
