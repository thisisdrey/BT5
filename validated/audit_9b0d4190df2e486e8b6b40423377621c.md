## Title
Unbounded, size-independent `receipt_proof` in Snowbridge `submit` extrinsic allows underpriced computational DoS - (File: `bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs`)

### Summary
The Snowbridge inbound-queue-v2 `submit` extrinsic accepts an `EventProof` whose `Proof.receipt_proof` field is an unbounded `Vec<Vec<u8>>` of Merkle-Patricia trie nodes, but the dispatch weight charged for `submit()` is a **fixed constant** (`Weight::from_parts(60_000_000, 0)`) that does not scale with the number or size of proof nodes supplied. This mirrors the external report's core flaw: a fixed/oversized resource-consumption allowance that is decoupled from the actual cost incurred by processing attacker-supplied input, letting a caller pay a cheap, fixed fee while forcing the node to do unbounded work.

### Finding Description
The `submit` extrinsic is a public, unprivileged entry point: [1](#0-0) 

It calls `T::Verifier::verify(&event.event_log, &event.proof)`, which (for the Ethereum beacon-client verifier) eventually calls `verify_receipt_inclusion`, passing `receipt_proof: &[Vec<u8>]` straight into `verify_receipt_proof`: [2](#0-1) [3](#0-2) 

`receipt_proof` is a plain `Vec<Vec<u8>>` with no `MaxEncodedLen`/`BoundedVec` restriction visible in the primitives crate, and `verify_proof` iterates and RLP-decodes every supplied node. Nothing in `submit()` bounds the number of nodes or the size of each node before invoking the trie-verification routine.

Crucially, the weight assigned to `submit()` is a **constant**, independent of the size of `event: Box<EventProof>`: [4](#0-3) 

The benchmark that generates this constant only ever exercises a single fixed-size fixture (`T::Helper::initialize_storage()`), never scaling the number/size of `receipt_proof` entries: [5](#0-4) 

Because `pallet::weight(T::WeightInfo::submit())` is fixed, the runtime's weight-based fee/block-inclusion accounting does not increase with the actual size of the caller-supplied `receipt_proof` Vec. An attacker can therefore submit a `submit()` call whose `EventProof.proof.receipt_proof` contains a very large number of large `Vec<u8>` nodes (bounded only by the max extrinsic/block length limit, not by the pallet's declared weight), causing the node to perform disproportionately expensive Merkle-proof verification (RLP decoding and hash-based traversal over every node) while only being charged the fixed, cheap weight — exactly the "big requests for a small declared cost" pattern in the external gRPC report.

### Impact Explanation
This is public underpriced work that can degrade block production / stall bridge processing: since the weight recorded for `submit()` does not reflect the true computational cost of verifying a maliciously bloated `receipt_proof`, a relayer (an unprivileged, signed account — no special permission is required to call `submit`) can craft calls that consume far more CPU time than their charged weight implies. Submitted within a block's weight budget (which is computed from the fixed `submit()` weight, not actual proof size), such calls can push actual execution time well past the block's time budget, causing block-production slowdowns or missed slots on BridgeHub chains that run this pallet — a live-scope impact for "public underpriced work that degrades block production or stalls bridge processing."

### Likelihood Explanation
Likelihood is high for the following reasons:
- `submit` is callable by any signed account (no governance/admin/validator/relayer allow-list is enforced beyond `ensure_signed`), satisfying the "unprivileged attacker" requirement.
- The proof fields (`receipt_proof: Vec<Vec<u8>>`) have no explicit length or item-count bound found in the primitives crate, so oversized submissions are not rejected at decode time.
- The transaction length limit (extrinsic/block byte size) is the only practical ceiling, but that ceiling is much larger than what the pallet's fixed weight accounts for, so the disconnect between declared/charged weight and actual work is real and exploitable at the byte-limit boundary.

### Recommendation
- **Short term:** Make `submit()`'s weight formula scale with the size of the supplied proof (e.g., `T::WeightInfo::submit(receipt_proof.len(), total_proof_bytes)` similar to how `pallet-message-queue`/`xcmp-queue` already scale weight by message size), and/or introduce an explicit hard cap (`BoundedVec<BoundedVec<u8, MaxNodeSize>, MaxProofNodes>`) on `Proof.receipt_proof` so the worst case is bounded and benchmarkable.
- **Long term:** Audit all Snowbridge proof-carrying extrinsics (`inbound-queue`, `inbound-queue-v2`, `ethereum-client`) for similar fixed-weight-vs-variable-input mismatches, and add benchmarks that vary proof size/node count to ensure declared weights are conservative upper bounds, consistent with how `MaxXcmpMessageLenOf`/`MaxMessageSize` are enforced elsewhere in XCMP/message-queue code.

### Proof of Concept
Conceptual PoC (not run, since we cannot execute code in ask-only mode):
1. Construct a syntactically-valid `EventProof` whose `event_log`/`execution_proof` pass verification for a legitimate, previously-stored finalized header (as done in existing test fixtures, e.g. `make_inbound_fixture()` used in `bridges/snowbridge/pallets/inbound-queue-v2/src/test.rs`).
2. Replace `proof.receipt_proof` with a very large `Vec<Vec<u8>>` — e.g., thousands of large filler byte arrays — up to the max extrinsic size limit, without needing them to form a cryptographically valid Merkle path (verification will simply fail after doing the work, or can be crafted as intermediate valid-looking trie nodes to maximize traversal cost).
3. Call `InboundQueue::submit(origin, Box::new(forged_event))` repeatedly from a single signed account.
4. Compare actual wall-clock execution time of `verify_receipt_proof`/`verify_proof` against the weight charged by `T::WeightInfo::submit()` (a constant ~60ms weight regardless of proof size) to demonstrate the mismatch.

Note: I was not able to fully verify whether `Proof`/`EventProof`'s SCALE encoding independently caps `Vec<Vec<u8>>` length via a transaction-pool-level extrinsic size limit that might mitigate the worst case — this would require checking runtime-specific `BlockLength`/`TransactionByteFee` configuration in the specific BridgeHub runtime, which was outside what I could confirm from the indexed code alone.

```rust
pub fn verify_receipt_proof(
	receipts_root: H256,
	tx_index: u64,
	proof: &[Vec<u8>],
) -> Option<ReceiptEnvelope> {
	let key = receipt_trie_key(tx_index);
	let root = B256::from_slice(receipts_root.as_bytes());
	let proof_nodes: Vec<Bytes> = proof.iter().map(|node| Bytes::copy_from_slice(node)).collect();

	// Call verify_proof with None to extract the value from an inclusion proof. For inclusion
	// proofs, alloy_trie returns ValueMismatch with the extracted value in `got`. The proof is
	// already cryptographically verified during this traversal.
	let value = match verify_proof(root, key, None, proof_nodes.iter()) {
		Ok(()) => return None, // Exclusion proof - key does not exist
		Err(ProofVerificationError::ValueMismatch { path, got: Some(v), expected: None })
			if path == key =>
		{
			v.to_vec()
		},
		Err(_) => return None,
	};

	ReceiptEnvelope::decode(&mut value.as_slice()).ok()
}
```
