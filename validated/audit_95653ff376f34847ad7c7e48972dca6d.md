### Title
Anti-replay window `Check`/`Update` split with an unlocked interval allows a genuine packet replay to bypass duplicate detection - (File: connection_state.go)

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` implement the same "check, then act, then update" pattern flagged in the external report: a bookkeeping predicate is evaluated, a comparatively expensive/blocking operation is executed *without holding the lock that protects the bookkeeping state*, and only afterward is the bookkeeping state advanced. Exactly like `beforeRatio`/`afterRatio` being taken on either side of an interest accrual that the check is supposed to be atomic with, the replay-window `Check()`/`Update()` pair here is not atomic with the intervening `DecryptDanger` call, so two concurrent invocations for the identical message counter can both pass `Check()` before either calls `Update()`.

### Finding Description
`Decrypt` takes `decryptLock`, calls `cs.window.Check(l, messageCounter)` to test whether the counter has already been seen, releases the lock, performs the AEAD decryption (`cs.dKey.DecryptDanger(...)`, which does not touch `window` or the lock at all), and only afterward re-acquires the lock to call `cs.window.Update(l, messageCounter)`, which is what actually marks the counter as consumed in the `Bits` sliding-window bitmap: [1](#0-0) 

`VerifyRelay` follows the identical shape for relay frames: [2](#0-1) 

The `Bits.Check`/`Bits.Update` primitives themselves are correct and mutually consistent when invoked back-to-back under a single held lock — `Check` is read-only and `Update` is what actually flips the bit for `i`: [3](#0-2) [4](#0-3) 

The vulnerability is that `decryptLock` is dropped between the `Check` and the `Update` calls, and the state-mutating decrypt work happens in that unlocked gap — the same structural flaw as the liquidation bug: a validity check is taken, a state-affecting operation runs outside the scope of that check, and a second check is performed afterward assuming nothing changed. Nebula's UDP receive path is deliberately multi-threaded (multiple reader routines process inbound packets for the same tunnel/`ConnectionState` concurrently, e.g. via the `q` reader-index parameter threaded through `readOutsidePackets`/`handleOutsideMessagePacket`), so it is architecturally possible for two goroutines to call `Decrypt` for the exact same `messageCounter` at close to the same time: [5](#0-4) [6](#0-5) 

When that happens:
1. Goroutine A calls `Check(l, N)` under the lock → bit for `N` unset → returns `true` → lock released.
2. Goroutine B (processing a replayed/duplicated copy of the same UDP datagram) calls `Check(l, N)` under the lock before A calls `Update` → bit for `N` is still unset → also returns `true` → lock released.
3. Both A and B independently run `DecryptDanger` for counter `N` (this succeeds for both, since AEAD decryption with the same key/nonce/ciphertext is deterministic and idempotent — it is not itself replay-protected).
4. Both A and B then call `Update(l, N)`. Only one of them will observe the bit as already set and get rejected; the other will have already delivered the *first* copy to the TUN device and the attacker's replayed copy is also written to the TUN device by whichever call raced first.

The net effect: the same ciphertext, delivered twice on the wire, can be decrypted and injected into the overlay network twice, defeating the entire purpose of the nonce/replay window (`ReplayWindow`, `Bits`) that `ConnectionState` exists to enforce.

### Impact Explanation
This breaks Nebula's replay-protection guarantee described by `ReplayWindow`/`Bits` and enforced at `connection_state.go`. Successful exploitation lets a network-level attacker (who can duplicate/replay UDP datagrams — which is trivial for any attacker positioned on the path, since Nebula runs over unauthenticated UDP) get a legitimate encrypted message accepted and delivered to the TUN device twice instead of once. Depending on the payload this enables replay of application-layer traffic (e.g., duplicate command execution, duplicate transactions, replayed control messages) inside the overlay — a genuine traffic-replay/nonce-bypass impact, which is one of the explicitly in-scope impact categories (replay bypass). It does not require possession of any valid CA-signed certificate; the attacker only needs to be able to capture and duplicate an already-observed on-wire UDP packet belonging to an established tunnel.

### Likelihood Explanation
The race window is narrow (it requires the decrypt operation of the original packet to still be in flight when the duplicate arrives on another reader routine), but it is entirely attacker-controlled: an attacker who has recorded a single legitimate encrypted packet can retransmit it any number of times, immediately, to maximize the chance of hitting the window between `Check` and `Update` on a system that services inbound UDP with multiple concurrent reader routines. This is a plausible, low-cost, and repeatable attack (just resend the packet many times / send many duplicates in a tight burst) rather than a purely theoretical race, making likelihood moderate rather than merely theoretical.

### Recommendation
Make the "is this counter unseen" check and "mark this counter seen" update atomic with respect to each other, and move the check-and-mark to *before* the expensive decrypt, not around it:
- Perform `window.Update` (or a combined check-and-mark primitive) under a single lock acquisition immediately, and only proceed to `DecryptDanger` if that atomic check-and-mark succeeds. If decryption then fails (e.g., corrupted/forged packet), it's acceptable to have consumed the counter slot, since a genuine legitimate packet using that same counter cannot exist.
- Alternatively, hold `decryptLock` across the entire `Check → Decrypt → Update` sequence so no other goroutine can observe the pre-update window state for the same counter.
- Apply the same fix to `VerifyRelay`.

### Proof of Concept
1. Establish a Nebula tunnel between two peers (no attacker certificate required).
2. Capture a single legitimate outside UDP packet destined to the victim (its ciphertext, header, and message counter `N`).
3. From an attacker vantage point on the path (or by flooding via UDP spoofing), rapidly re-send multiple exact copies of that captured packet to the victim's UDP listener within the same instant, so they land on different internal reader routines processing the socket concurrently.
4. Observe that `Decrypt` is invoked concurrently for counter `N` on more than one goroutine because `Check(l, N)` was evaluated by both before either called `Update(l, N)` — both succeed, and the duplicate payload is written to the TUN device a second time, confirming that the anti-replay window failed to reject a duplicate of an already-processed packet.

func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]

	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}

func (b *Bits) Update(l *slog.Logger, i uint64) bool {
	// Fast path: i is the next expected counter. Split out so the function
	// stays small and avoids paying for the slow paths' slog argument-build
	// stack frame on every call. The bit read/test/write is inlined to
	// touch the backing word once.
	if i == b.current+1 {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if i > b.length && w&mask == 0 {
			b.lostCounter.Inc(1)
		}
		b.bits[word] = w | mask
		b.current = i
		return true
	}
	return b.updateSlow(l, i)
}

func (f *Interface) handleOutsideMessagePacket(hostinfo *HostInfo, out []byte, packet []byte, fwPacket *firewall.Packet, nb []byte, q int, localCache firewall.ConntrackCache) {
	err := newPacket(out, true, fwPacket)
	if err != nil {
		hostinfo.logger(f.l).Warn("Error while validating inbound packet",
			"error", err,
			"packet", out,
		)
		return
	}

	dropReason := f.firewall.Drop(*fwPacket, true, hostinfo, f.pki.GetCAPool(), localCache)

		// NOTE: We give `packet` as the `out` here since we already decrypted from it and we don't need it anymore

	}
