#No Vulnerability found for this question.

**Analysis supporting this conclusion:**

The clamp behavior in `ReceiptSinkV2::try_forward` is intentional and documented, not an exploitable flaw:

1. The admission check uses `admission_gas = gas.min(allowed_shard_outgoing_gas)` while the actual deduction uses the real `gas` via `forward_limit.gas.saturating_sub(gas)` — this is the explicit purpose of `ClampOutgoingGasAdmission` (PV 85): "so a single very-expensive receipt cannot be blocked forever by the gas limit" [1](#0-0) . It is a deliberate design tradeoff to prevent oversized receipts from permanently stalling the buffer, not an accounting bug.

2. Zero-congestion-gas receipts (Data, PromiseYield, PromiseResume, GlobalContractDistribution) always satisfy `forward_limit.gas >= admission_gas` (since `admission_gas = 0`) by design — this predates and is independent of the `ClampOutgoingGasAdmission` feature, as these kinds are defined to carry zero congestion gas in `compute_receipt_congestion_gas` [2](#0-1) .

3. Critically, admission into `outgoing_receipts` only determines *when* a receipt is delivered to the receiver shard's incoming queue — it does not cause double execution. Each receipt is forwarded exactly once and executed exactly once by `Runtime::process_incoming_receipts`; there is no code path in `try_forward`, `buffer_receipt`, or the congestion accounting that duplicates a receipt or re-queues it after successful forwarding [3](#0-2) . The claimed "double-execute high-gas receipts across chunks" outcome has no supporting mechanism in this code.

4. The gas/size accounting is self-consistent: `own_congestion_info.remove_buffered_receipt_gas(gas)` uses the same real `gas` value subtracted from `forward_limit.gas`, so there is no divergence between the sender's local bookkeeping and what is actually forwarded [4](#0-3) . This computation is deterministic and identical across all validators applying the same chunk under the same protocol version, so it cannot cause state-root or consensus divergence — every node computes the same `forward_limit` state and the same `outgoing_receipts` set.

5. At most, this allows a sender shard to forward somewhat more cumulative real gas to a receiver in one chunk than the nominal `allowed_shard_outgoing_gas`/`outgoing_gas_limit` would naively suggest — a resource-hygiene/congestion-precision characteristic explicitly acknowledged in the code comments, not a reachable path to theft, fund freezing, double-spend, authorization escalation, consensus divergence, or a shard-halting panic. Per the audit rules, such congestion-control-precision claims without a concrete fund-loss/consensus/halt impact are out of scope.

pub(crate) fn compute_receipt_congestion_gas(
    receipt: &Receipt,
    config: &RuntimeConfig,
) -> Result<Gas, IntegerOverflowError> {
    match receipt.versioned_receipt() {
        VersionedReceiptEnum::Action(action_receipt) => {
            // account for gas guaranteed to be used for executing the receipts
            action_receipt_congestion_gas(receipt, config, action_receipt.into())
        }
        VersionedReceiptEnum::Data(_data_receipt) => {
            // Data receipts themselves don't cost gas to execute, their cost is
            // burnt at creation. What we should count, is the gas of the
            // postponed action receipt. But looking that up would require
            // reading the postponed receipt from the trie.
            // Thus, the congestion control MVP does not account for data
            // receipts or postponed receipts.
            Ok(Gas::ZERO)
        }
        VersionedReceiptEnum::PromiseYield(_) => {
            // The congestion control MVP does not account for yielding a
            // promise. Yielded promises are confined to a single account, hence
            // they never cross the shard boundaries. This makes it irrelevant
            // for the congestion MVP, which only counts gas in the outgoing
            // buffers and delayed receipts queue.
            Ok(Gas::ZERO)
        }
        VersionedReceiptEnum::PromiseResume(_) => {
            // The congestion control MVP does not account for resuming a promise.
            // Unlike `PromiseYield`, it is possible that a promise-resume ends
            // up in the delayed receipts queue.
            // But similar to a data receipt, it would be difficult to find the cost
            // of it without expensive state lookups.
            Ok(Gas::ZERO)
        }
        VersionedReceiptEnum::GlobalContractDistribution(_) => Ok(Gas::ZERO),
    }
}
