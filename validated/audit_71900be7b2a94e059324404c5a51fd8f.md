### Title
Restore RestoreRepository leaks cross-tenant backups because `VanityRepository.RelativePath` bypasses path-traversal validation before being joined into the backup sink path - ([File: internal/gitaly/service/repository/restore_repository.go], [File: internal/backup/backup.go], [File: internal/backup/locator.go])

### Summary
`RestoreRepository` validates the `VanityRepository` field with `storage.WithSkipStorageExistenceCheck()`, which causes `configLocator.ValidateRepository` to return success before it ever reaches the `storage.ValidateRelativePath` traversal check. The unsanitized `VanityRepository.RelativePath` is then joined via `filepath.Join` into the backup sink's storage/manifest paths in `internal/backup/locator.go` and `internal/backup/manifest.go`, letting an attacker point the restore lookup at another repository's backup artifacts on the shared backup sink and have that content (bundle, refs, custom hooks) written into their own, legitimately-owned target repository.

### Finding Description
`s.validateRestoreRepositoryRequest` in `internal/gitaly/service/repository/restore_repository.go:54-72` validates two different repositories with two different strictness levels: [1](#0-0) 

- `in.GetRepository()` (the actual on-disk target) is validated with `storage.WithSkipRepositoryExistenceCheck()`, which still runs the full `ValidateRepository` path including `storage.ValidateRelativePath(storagePath, relativePath)`.
- `in.GetVanityRepository()` (used purely to compute the backup path) is validated with `storage.WithSkipStorageExistenceCheck()`.

In `configLocator.ValidateRepository` (`internal/gitaly/config/locator.go:47-118`), the `SkipStorageExistenceCheck` branch returns `nil` immediately after only checking that storage name/relative path aren't both empty and that relative path isn't empty: [2](#0-1) 
The `storage.ValidateRelativePath` call that would reject `../`-escaping paths is never reached for this branch — it only executes later in the function (line 81), which is skipped entirely.

`Manager.Restore` (`internal/backup/backup.go:388-417`) then passes `req.VanityRepository` straight to `mgr.locator.Find`/`FindLatest`: [3](#0-2) 

Those calls resolve into `ManifestLocator.Find`/`FindLatest` → `ManifestLoader.ReadManifest`/`ReadLatestManifest` (`internal/backup/manifest.go:28-47`, `74-80`), which build the manifest/backup path via `manifestPath`/`manifestDirectory` using the repo's raw `RelativePath`, and `BeginFull`/`BeginIncremental` (`internal/backup/locator.go:30-118`) build bundle/ref/custom-hooks paths the same way: [4](#0-3) 

All of these use unguarded `filepath.Join(cfg.pathPrefix, storageName, relativePath, backupID, ...)`. Because `relativePath` (from `VanityRepository`) was never checked against `../` traversal, an attacker can set it to something like `../../<victim-storage>/<victim-relative-path>` to make the locator resolve to another repository's backup manifest/bundle/refs/custom_hooks tarball on the shared backup sink. `Manager.Restore` will then load that foreign manifest, and `restoreFromBundle`/`restoreCustomHooks` write the referenced bundle, refs, and custom hooks tarball content into `req.Repository` — the attacker's own, properly validated repository. The separately-checked `backup.ValidatePathPrefix(in.GetPathPrefix())` only sanitizes the `PathPrefix` field and does not cover `VanityRepository.RelativePath` at all.

### Impact Explanation
An unprivileged owner of a repository can trigger `RestoreRepository` (directly, or indirectly if this manager is invoked by backend restore tooling) with a crafted `VanityRepository.RelativePath` to read another tenant's backup bundle, refs, and `custom_hooks` archive from the shared backup sink, and inject that foreign content — including custom hooks, which execute code during git operations — into their own repository. This is cross-repository/cross-tenant information disclosure combined with a hook-injection primitive, matching GitLab's "unauthorized access to another user's private repository content" / "arbitrary code execution via custom hooks" bounty impact classes.

### Likelihood Explanation
Exploitation requires only that the attacker control the `RestoreRepositoryRequest.VanityRepository.RelativePath` field of a request they can send to a Gitaly node with server-side backups configured, and knowledge/guessability of a target storage name and relative path (which, for hashed repository storage, is a deterministic function of the project ID and not a secret). No admin privileges, credentials, or infrastructure compromise are needed — only the ability to issue (or have issued on their behalf) a `RestoreRepository` call for a repository they own, which is realistic in disaster-recovery/self-service restore flows. The bug is fully repeatable since the flawed validation path is deterministic.

### Recommendation
Validate `VanityRepository.RelativePath` with the same rigor as `Repository`, i.e. do not use `WithSkipStorageExistenceCheck()` to bypass `storage.ValidateRelativePath`. At minimum, always run `storage.ValidateRelativePath` (or an equivalent traversal check) against `VanityRepository.GetRelativePath()` before it is used to build any backup sink key, independent of whether storage/repository existence is skipped.

```go
// internal/gitaly/service/repository/restore_repository_test.go (new case)
func TestRestoreRepository_vanityPathTraversal(t *testing.T) {
    // ... existing test scaffolding (backupSink, backupLocator, server, client) ...

    // Victim repo backup already exists at:
    //   manifests/<victim-storage>/<victim-relative-path>/<backupID>.toml
    //   <victim-storage>/<victim-relative-path>/<backupID>/001.bundle, 001.refs, 001.custom_hooks.tar

    attackerRepo := &gitalypb.Repository{
        StorageName:  cfg.Storages[0].Name,
        RelativePath: attackerRepoRelativePath, // real repo the attacker owns
    }

    maliciousVanity := &gitalypb.Repository{
        StorageName:  cfg.Storages[0].Name,
        // traversal payload pointing at victim's backup path
        RelativePath: "../" + victimStorageName + "/" + victimRelativePath,
    }

    _, err := client.RestoreRepository(ctx, &gitalypb.RestoreRepositoryRequest{
        Repository:       attackerRepo,
        VanityRepository: maliciousVanity,
        BackupId:         victimBackupID,
    })
    require.NoError(t, err)

    // Assertion: attacker's repo now contains the victim's custom hooks / objects
    hooksPath := filepath.Join(attackerRepoPath, "custom_hooks")
    require.DirExists(t, hooksPath)
    require.FileExists(t, filepath.Join(hooksPath, "victim-hook-marker"))
}
```
Expected result confirming the vulnerability: the restore succeeds and the attacker's own repository ends up containing objects/refs/hooks from the victim's backup, despite the attacker never having access to the victim repository directly.
