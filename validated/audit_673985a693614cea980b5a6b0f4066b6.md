### Title
Quarantine object-directory ownership check can be bypassed by any base directory literally named `quarantine` - (File: internal/git/localrepo/paths.go)

### Summary
`Repo.ObjectDirectoryPath()` is supposed to bind a repository's `GitObjectDirectory` field to a quarantine directory that was actually created for that specific repository/transaction. Instead, it grants an unconditional bypass of that ownership check whenever the base name of the supplied relative path is literally `quarantine`, without ever verifying it is *this* repository's quarantine directory.

### Finding Description
`ObjectDirectoryPath` first confines the caller-supplied `GitObjectDirectory` to the storage root via `storage.ValidateRelativePath(storagePath, ...)` [1](#0-0) . It then decides whether the path is a "transaction quarantine dir" purely from its base name:

```go
isTransactionQuarantineDir := (baseDir == "quarantine") || ((parentDir == "quarantine") && strings.HasPrefix(baseDir, "tmp_objdir"))
``` [2](#0-1) 

When `isTransactionQuarantineDir` is true, the function skips the block that otherwise verifies the path either lives inside the repository itself or has the repository-specific prefix `storage.QuarantineDirectoryPrefix(repo)` (a SHA1 hash of the repo's own relative path) [3](#0-2) . That prefix check is the only mechanism that binds a quarantine directory to the repository that "owns" it: `QuarantineDirectoryPrefix` computes `quarantine-<hash(relative_path)>-` specifically so that "we can verify that a given quarantine object directory indeed belongs to the repository at hand" [4](#0-3) .

Because the `baseDir == "quarantine"` branch short-circuits this ownership check entirely, any relative path under the storage root whose final component is exactly `quarantine` — regardless of which repository's temp/transaction directory it lives in — is accepted as a valid object directory for the requesting repository. This is directly analogous to the reported voucher bug: the "voucher" (the object-directory reference) is honored purely by matching a superficial pattern (its name), without checking that it was actually mint(ed)/created for the specific redeemer (the requesting repository). Whoever supplies the `Repository.GitObjectDirectory` field for a request (e.g. an access-check call replaying a quarantine path, as exercised in `TestGetObjectDirectorySize_quarantine`) can point it at another repository's or another transaction's quarantine directory as long as the final path component is named `quarantine` and stays within the storage root [5](#0-4) .

### Impact Explanation
This weakens the isolation the quarantine mechanism is meant to provide between concurrently-quarantined pushes/transactions on the same storage. A caller who can influence the `GitObjectDirectory` field of a `Repository` message (this field is part of the protobuf `Repository` message and is round-tripped through the access-check flow, as documented in the test helper comments about Rails sending back the quarantine object directory) can point `ObjectDirectoryPath` — and thus RPCs like `GetObjectDirectorySize` — at another transaction's quarantine content on the same storage, rather than being restricted to only its own quarantine. This is a cross-repository/cross-transaction object-directory access analog: the code path that is supposed to prove "this quarantine directory belongs to this specific repo" is unconditionally skipped for a whole class of paths.

### Likelihood Explanation
Exploiting this requires being able to control the `GitObjectDirectory` field of a `Repository` message sent in an internal-only RPC such as `GetObjectDirectorySize`, which is normally populated by Gitaly itself from `quarantine.Apply`/`quarantine.New` and only echoed back through the access-check round-trip rather than being freely chosen by external Git push/fetch clients. Within that constrained internal channel, however, the check that is bypassed is the *only* code that ties a `quarantine`-named path to a specific repository, so any caller of this internal path who can name an arbitrary `quarantine`-suffixed relative path under the storage (rather than the one that was actually issued to them) is unconditionally trusted.

### Recommendation
Remove the unconditional `baseDir == "quarantine"` bypass and always require the `QuarantineDirectoryPrefix(repo)` (or equivalent per-repository binding) check, even for paths whose base directory is exactly `quarantine`, so that a repository can only reference a quarantine directory that was actually allocated for it.

### Proof of Concept
Not independently verified end-to-end (would require constructing a second repository's `Repository` proto with `GitObjectDirectory` rewritten to point at repo A's `state-dir/quarantine` directory and confirming `ObjectDirectoryPath`/`GetObjectDirectorySize` returns repo A's quarantine content for repo B's request). The existing test `TestGetObjectDirectorySize_quarantine/repository quarantined by transaction manager` in `internal/gitaly/service/repository/size_test.go` demonstrates the exact code path (`GitObjectDirectory` set to a `.../quarantine` directory not derived from `QuarantineDirectoryPrefix`) being accepted successfully [5](#0-4) , confirming the bypass branch is reachable and functions as described.

// QuarantineDirectoryPrefix returns a prefix for use in the temporary directory. The prefix is
// based on the relative repository path and will stay stable for any given repository. This allows
// us to verify that a given quarantine object directory indeed belongs to the repository at hand.
// Ideally, this function would directly be located in the quarantine module, but this is not
// possible due to cyclic dependencies.
func QuarantineDirectoryPrefix(repo Repository) string {
	hash := [20]byte{}
	if repo != nil {
		hash = sha1.Sum([]byte(repo.GetRelativePath()))
	}
	return fmt.Sprintf("quarantine-%x-", hash[:8])
```
