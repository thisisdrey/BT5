### Title
Unauthenticated `RecvError` packets allow remote tunnel-state poisoning via spoofed index/source - ([File: outside.go])

### Summary
The `RecvError` message type is processed entirely outside of the Noise/AEAD session — it carries no signature, no nonce, and is not covered by the per-tunnel replay window (`Bits`/`ConnectionState`) that protects every other message type. `handleRecvError` accepts the packet, looks up the tunnel purely by the attacker-supplied 32-bit `h.RemoteIndex`, and tears the tunnel down if the packet's source address happens to match the host's currently recorded remote. Because UDP source addresses are trivially spoofable and nothing in the packet is cryptographically bound to the sender, this is the same class of bug as the reported "ECDSA PPS oracle" issue: a state-changing message that lacks any nonce/anti-replay/authentication binding to the party or channel that is supposed to be authorized to send it.

### Finding Description
In `outside.go`, `RecvError` is handled before any certificate/AEAD verification: [1](#0-0) 

`handleRecvError` only checks a local per-endpoint rate/accept policy and whether the source address matches the tunnel's currently known remote — it never verifies a signature, nonce, or any value that was actually produced by the legitimate peer inside its authenticated session: [2](#0-1) 

Contrast this with the data plane and relay paths, where every message carries a `MessageCounter` that is checked and updated against the peer's `Bits` sliding-window replay tracker before being trusted: [3](#0-2) 

`RecvError` has no equivalent counter/nonce and is verified only by comparing `via.UdpAddr` (the sender's claimed/observed source, easily spoofed over UDP) against `hostinfo.GetRemote()`. The in-code comment "Someone spoofing recv_errors?" shows the implementers were aware source-address matching is not real authentication, yet no stronger binding (nonce, signature, or a value derived from the live Noise session) was added — exactly the "signature schema lacks a nonce/binding to the authorized party" root cause described in the reported bug class.

### Impact Explanation
An attacker who can send UDP packets to a Nebula node — with no CA-signed certificate and no established tunnel to that node — and who can either spoof the victim's current remote address or otherwise get a matching source address, can forge a `RecvError` for a guessed/observed `RemoteIndex` and force `f.closeTunnel(hostinfo)` plus deletion from the pending handshake map. This poisons the victim's tunnel state (remote state poisoning / DoS), forcing tunnel teardown and re-handshakes, without needing any of the cryptographic material that legitimately authenticates Nebula peers.

### Likelihood Explanation
Exploitability depends on the attacker knowing (or guessing) a live `RemoteIndex` and being able to source-spoof (or genuinely originate from) the address currently recorded as the tunnel's remote. `RemoteIndex` values are otherwise visible in-transit to any on-path/network observer, and UDP allows straightforward source-address spoofing when there is no return-path/state check, matching the changelog's own acknowledgment that `recv_error` handling is security-sensitive (`listen.send_recv_error`, `#670`; `#1459` disabling `recv_error` when a packet is outside the counter window). This keeps likelihood moderate-to-high for any attacker positioned to observe or infer index values.

### Recommendation
Do not let an unauthenticated, unsigned control message unilaterally tear down an authenticated tunnel. Bind `RecvError` legitimacy to something only the real peer can produce inside the current session — e.g., require it to be sent as an authenticated `Message`/`Control` type inside the existing AEAD tunnel (covered by the `Bits` replay window and message counter) rather than as a bare, unauthenticated packet type, or otherwise incorporate a per-session nonce/counter that must match state only the legitimate peer holds before acting on it.

### Proof of Concept
1. Observe or infer an active tunnel's `RemoteIndex` (e.g., via network position) between hosts A and B.
2. From an unrelated attacker host, spoof the UDP source address to match B's currently recorded remote address (`hostinfo.GetRemote()` on A), and send a `header.RecvError` packet with `RemoteIndex` set to A's local index for that tunnel, as built in `sendRecvError`: [4](#0-3) 
3. `handleRecvError` on A passes the address-match check and calls `f.closeTunnel(hostinfo)`, tearing down the legitimate tunnel to B with no certificate, handshake, or AEAD-authenticated material presented by the attacker.

func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
