### Title
Relayer reward paid without validating delivery success flag - (File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs)

### Summary
`process_delivery_receipt` decodes an Ethereum `InboundMessageDispatched` event into a `DeliveryReceipt` that carries a `success: bool` field (and a `topic` field), but the pallet logic never inspects these fields. It validates only `gateway` address and looks up the `PendingOrder` by `nonce`, then unconditionally transfers `order.fee` to the relayer/reward account and removes the order.

### Finding Description
The `DeliveryReceipt` type is decoded from a real Ethereum log via `TryFrom<&Log>` [3](#0-2) , capturing whether the message dispatch on Ethereum actually succeeded (`success`) and which message it corresponds to (`topic`). In `process_delivery_receipt`, only `receipt.gateway` and `receipt.nonce` are used to gate the reward payment: `ensure!(T::GatewayAddress::get() == receipt.gateway, ...)` then `<PendingOrders<T>>::get(nonce)` [4](#0-3) . The code proceeds to pay `order.fee` to the reward account whenever `order.fee > 0`, with no branch conditioned on `receipt.success` [5](#0-4) . This mirrors the external report's pattern precisely: a value returned from an external/oracle-like source (the Ethereum event log) is decoded but its critical field is not validated before it drives on-chain settlement.

### Impact Explanation
Since Ethereum message execution can legitimately fail (Solidity-side revert, insufficient gas, etc.), the Gateway on Ethereum still emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)` per the event signature [6](#0-5) . A relayer can submit a valid, cryptographically-proven receipt for a message whose remote execution failed and still collect the full relayer reward, because the pallet does not distinguish `success=true` from `success=false`. This causes the protocol to pay out relayer rewards for messages that were not successfully delivered/executed, i.e., a reward-accounting invariant violation (public underpriced/incentive-misaligned work with fund-drain characteristics) without needing any malicious peer, validator, or relayer collusion — any relayer submitting a legitimately failed-execution receipt profits identically to one submitting a successful one.

### Likelihood Explanation
High: no privileged role or off-chain assumption is required. Any account can call `submit_delivery_receipt` with a legitimately obtained (real, provable) receipt for a message whose Ethereum-side execution failed, and the extrinsic will succeed and pay the fee, because `T::Verifier::verify` and `verify_receipt_proof` only attest to the authenticity of the log, not to the semantic `success` value inside it [7](#0-6) .

### Recommendation
In `process_delivery_receipt`, branch on `receipt.success` before paying `order.fee`: reject/skip reward payment (or route to a different failure-handling path) when `receipt.success == false`, only settling `PendingOrders` removal and reward transfer for confirmed-successful dispatches. Also consider validating `receipt.topic` matches the original message topic if that binding is expected to be enforced on-chain.

### Proof of Concept
1. An outbound message is queued and `PendingOrders::<T>::insert(nonce, PendingOrder { nonce, fee: F, .. })` as in `do_process_message` [8](#0-7) .
2. On Ethereum, the Gateway contract attempts to dispatch the message but the dispatch reverts/fails; the Gateway still emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer obtains a genuine receipt-inclusion proof for this failed-dispatch log and calls `submit_delivery_receipt` [7](#0-6) .
4. `T::Verifier::verify` succeeds (the log is authentic), `DeliveryReceipt::try_from` decodes `success: false`, but `process_delivery_receipt` still executes `T::RewardPayment::register_reward(&reward_account, ..., order.fee)` and removes the order, paying the relayer for a message that never executed successfully on Ethereum.

		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
