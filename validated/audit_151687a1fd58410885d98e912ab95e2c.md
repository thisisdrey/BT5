### Title
Unbounded memory allocation before energy accounting in TVM `Memory.extend()` - (File: actuator/src/main/java/org/tron/core/vm/program/Memory.java)

### Summary
`Memory.extend(int address, int size)`, which backs every TVM memory-expanding opcode (`CALLDATACOPY`, `CODECOPY`, `RETURNDATACOPY`, `MSTORE`, `MCOPY`, etc.), physically allocates JVM heap chunks for the requested memory size (`addChunks(...)`) *before* it invokes `programListener.onMemoryExtend(toAllocate)`, which is where energy is actually charged/validated. Because the size value is attacker-controlled (derived directly from opcode stack words that ultimately come from a transaction's contract-call `data`), a caller can request memory sizes up to ~`Integer.MAX_VALUE` bytes (~2 GB per opcode invocation) and force the node to allocate that memory in the JVM heap before the subsequent energy check has a chance to reject the call for insufficient energy. This mirrors the websocket-driver bug class: a length header taken from untrusted input drives an allocation whose cost is validated only *after* the allocation has already occurred.

### Finding Description
`Memory.extend()`: [1](#0-0) 

The sequence is:
1. `toAllocate = newSize - internalSize()` is computed from `address + size` (attacker-controlled).
2. `addChunks((int) ceil(toAllocate / CHUNK_SIZE))` immediately allocates `byte[1024]` chunks in the JVM heap for the full requested size.
3. Only afterward does the method recompute `toAllocate` against `softSize` and call `programListener.onMemoryExtend(toAllocate)`, which is the hook responsible for energy metering/limits.

This `extend()` is reached from `Program.memorySave`, `Program.memoryExpand`, and `Program.memoryChunk`: [2](#0-1) 

which in turn are driven directly by opcode handlers taking length/offset values straight off the EVM stack, e.g. `callDataCopyAction`: [3](#0-2) 

The length itself is decoded with `DataWord.intValueSafe()`, which simply clamps any oversized 256-bit stack value to `Integer.MAX_VALUE` rather than rejecting it outright: [4](#0-3) 

Additionally, `ProgramInvokeImpl.getDataCopy` (backing `CALLDATACOPY`) allocates a `byte[length]` array of the full requested (attacker-chosen) length up front, independent of the actual size of `msgData`: [5](#0-4) 

so even a contract call with tiny real calldata can force a large transient array allocation merely by specifying a large `length` word on the stack, before any energy check for that array's size is performed.

### Impact Explanation
Any unprivileged account can trigger this by broadcasting a transaction that calls (or deploys and calls) a smart contract executing `CALLDATACOPY`/`CODECOPY`/`MSTORE`/similar opcodes with a large offset/length operand. Each such opcode invocation can cause the node to allocate on the order of ~2 GB of JVM heap in `Memory.extend()`/`getDataCopy()` before the energy-based rejection occurs. Executed repeatedly (e.g., in a loop within one contract, or via multiple concurrently broadcast transactions from different unprivileged accounts hitting different full/witness nodes), this can exhaust node memory, triggering `OutOfMemoryError` and crashing or stalling the node process — a concrete node-crash/DoS impact within the accepted impact categories (CWE-400/CWE-770 resource exhaustion leading to node crash/halt).

### Likelihood Explanation
The path is reachable by any unprivileged transaction broadcaster or contract deployer/caller — no special privileges, SR/witness status, or peer-level access is required. The attack requires only crafting a smart contract (or reusing an existing deployed one) that executes a copy/memory opcode with a large stack-supplied length, and broadcasting a signed transaction that invokes it. The bug is a straightforward ordering flaw (allocate-then-charge) rather than a subtle timing race, making it reliably triggerable.

### Recommendation
Reorder `Memory.extend()` (and any other TVM memory-expansion code) so that the projected memory-expansion cost is computed and validated against remaining energy (or a hard maximum bound) *before* any chunk allocation (`addChunks`) occurs. Similarly, `ProgramInvokeImpl.getDataCopy` (and equivalent methods) should clamp/validate `length` against the real bounds (e.g., against `msgData.length` or a safe maximum) before allocating the destination array, rather than allocating `new byte[length]` first and truncating afterward. Consider introducing an explicit upper bound on single-opcode memory requests independent of the two-step allocate/charge sequence.

### Proof of Concept
Deploy a contract whose fallback/entry function executes TVM bytecode equivalent to:
```
PUSH32 0x7fffffff   // length ~ 2^31-1 (~2GB), passes through DataWord.intValueSafe unmodified
PUSH1 0x00          // dataOffset
PUSH1 0x00          // memOffset
CALLDATACOPY
```
Broadcasting a transaction invoking this function causes `callDataCopyAction` → `ProgramInvokeImpl.getDataCopy` to allocate a ~2 GB `byte[]`, and/or `Program.memorySave` → `Memory.extend` to call `addChunks` for the same size, before the energy check in `programListener.onMemoryExtend` can reject the operation for insufficient energy — consistent with the CWE-400/770 memory-exhaustion pattern described in the reference advisory (unbounded allocation driven by an attacker-supplied length value, validated only after the allocation is performed).

  public void extend(int address, int size) {
    if (size <= 0) {
      return;
    }
    final int newSize = addExact(address, size, VMConfig.disableJavaLangMath());
    int toAllocate = newSize - internalSize();
    if (toAllocate > 0) {
      addChunks((int) ceil((double) toAllocate / CHUNK_SIZE, VMConfig.disableJavaLangMath()));
    }

    toAllocate = newSize - softSize;
    if (toAllocate > 0) {
      toAllocate = (int) ceil((double) toAllocate / WORD_SIZE,
          VMConfig.disableJavaLangMath()) * WORD_SIZE;
      softSize = addExact(softSize, toAllocate, VMConfig.disableJavaLangMath());

      if (programListener != null) {
        programListener.onMemoryExtend(toAllocate);
      }
    }
  }

  public byte[] getDataCopy(DataWord offsetData, DataWord lengthData) {

    int offset = offsetData.intValueSafe();
    int length = lengthData.intValueSafe();

    byte[] data = new byte[length];

    if (msgData == null) {
      return data;
    }
    if (offset > msgData.length) {
      return data;
    }
    if (offset + length > msgData.length) {
      length = msgData.length - offset;
    }

    System.arraycopy(msgData, offset, data, 0, length);

    return data;
  }
