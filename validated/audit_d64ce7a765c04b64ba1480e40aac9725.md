## Finding [1](#0-0) 

The Astaria report's root cause is that a state-mutating "join the value pool" operation (`ERC4626Cloned.deposit`/`mint`) has no gate ensuring the caller is legitimately entitled to the underlying value stream — the contract simply performs the requested state change for anyone who calls it. The closest reachable analog in Gitaly is `ObjectPoolService.LinkRepositoryToObjectPool`.

### Title
Unrestricted `LinkRepositoryToObjectPool` allows attaching an arbitrary repository to any object pool, granting cross-repository object read access - (`internal/gitaly/service/objectpool/link.go`)

### Summary
`LinkRepositoryToObjectPool` writes an unconditional `objects/info/alternates` entry pointing the caller-supplied `repository` at the caller-supplied `object_pool`, without verifying any relationship (fork membership, common origin, ownership) between the two. Once linked, every object stored in the target pool becomes readable through the linked repository via standard Git operations.

### Finding Description
The RPC handler validates only that the `repository` argument is a well-formed repository and that the `object_pool` resolves to an existing pool: [1](#0-0) 

It then calls `pool.Link(ctx, repo)`, which delegates to `objectpool.Link`. That function only checks whether the repository is *already* linked to the pool; if not, it unconditionally writes the pool's relative object path into the repository's `objects/info/alternates` file and removes the repo's own bitmap files so it can transparently see the pool's objects: [2](#0-1) 

Nowhere in this path is there a check that the `repository` being linked is a genuine fork of, or otherwise entitled to, the object pool's origin (the repository from which `CreateObjectPool` cloned the pool's data, per the documented lifecycle): [3](#0-2) 

The protobuf definition likewise contains no server-side ownership/ancestry constraint between `object_pool` and `repository` — both are just arbitrary repository references tagged for the transaction/routing layer: [4](#0-3) 

This is structurally identical to the reported bug class: a function meant to be reached only through a controlled flow (pool membership established during fork creation, `LinkRepositoryToObjectPool` called by trusted callers as part of fork provisioning) can instead be invoked directly with attacker-chosen arguments, and the underlying primitive performs the sensitive state change (linking alternates / minting withdrawal shares) without validating that the caller is entitled to the resulting benefit.

### Impact Explanation
Once a repository is linked to an unrelated object pool, `git fetch`/`git clone`/`git cat-file` on the linked repository (or any Gitaly RPC that reads objects, e.g. `GetBlob`, `TreeEntry`, `CommitService` calls) can resolve any object stored in that pool via the alternates search path, because Git treats alternates transparently. If the target `object_pool` was seeded from a private/confidential repository, any actor who can call `LinkRepositoryToObjectPool` with a repository they control and an `object_pool` reference they can supply gains read access to that pool's object graph (blobs, trees, commits) — a concrete cross-repository object disclosure, analogous to the reported unauthorized capture of value that should have been reserved for legitimate participants only.

### Likelihood Explanation
Exploitability depends on the caller being able to supply an `object_pool` `Repository` value (storage name + relative path) for a pool it does not legitimately belong to. Because the RPC performs no ownership/ancestry check at the Gitaly layer, the sole barrier is whatever access control gitlab-rails enforces before issuing the RPC and the attacker's ability to guess/learn the pool's relative path (which is derived deterministically from repository/project identifiers in GitLab's object-pool provisioning, not a per-request secret). No malicious peer, leaked token, or privileged position is required beyond ordinary RPC access to `ObjectPoolService` with attacker-influenced request fields.

### Recommendation
Enforce membership/ancestry validation server-side in `LinkRepositoryToObjectPool` (and mirror it in `FetchIntoObjectPool`/`GetObjectPool` where relevant): verify that the target `repository` is a recognized member/fork of the `object_pool`'s origin (e.g., via the pool metadata store already used elsewhere, `internal/gitaly/storage/relational` `PoolStore`) before writing the alternates link, rejecting requests where no such relationship is recorded.

### Proof of Concept
1. Attacker controls repository `A` (any repository they can write to, e.g., their own project) and knows/derives the relative path of object pool `P` created from private repository `B` (pool paths are deterministically derived, not secret per-request tokens).
2. Attacker calls `ObjectPoolService.LinkRepositoryToObjectPool` with `{ repository: A, object_pool: P }`.
3. `internal/gitaly/service/objectpool/link.go` validates only that `A` is a valid repository and `P` resolves to an existing pool, then calls `objectpool.Link`, which writes `P`'s object directory into `A`'s `objects/info/alternates` unconditionally (`internal/git/objectpool/link.go` lines 28-84).
4. Attacker runs `git fetch`/`git cat-file` against `A` and can now resolve any object ID that exists in pool `P`, including objects originating from private repository `B`, without ever having been authorized to read `B` directly.

func (s *server) LinkRepositoryToObjectPool(ctx context.Context, req *gitalypb.LinkRepositoryToObjectPoolRequest) (*gitalypb.LinkRepositoryToObjectPoolResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	pool, err := s.poolForRequest(ctx, req)
	if err != nil {
		return nil, err
	}

	repo := s.localRepoFactory.Build(repository)

	if err := pool.Link(ctx, repo); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	return &gitalypb.LinkRepositoryToObjectPoolResponse{}, nil
}

func Link(ctx context.Context, pool, repo *localrepo.Repo, txManager transaction.Manager) (returnedErr error) {
	altPath, err := repo.InfoAlternatesPath(ctx)
	if err != nil {
		return err
	}

	expectedRelPath, err := getRelativeObjectPath(ctx, pool, repo)
	if err != nil {
		return err
	}

	linked, err := linkedToRepository(ctx, pool, repo)
	if err != nil {
		return err
	}

	if linked {
		// When the repository is already linked to the repository, cast a vote to ensure the
		// repository is consistent with the other replicas.
		if err := transaction.VoteOnContext(ctx, txManager, voting.VoteFromData([]byte("repository linked")), voting.Synchronized); err != nil {
			return fmt.Errorf("vote on linked repository: %w", err)
		}

		return nil
	}

	alternatesWriter, err := safe.NewLockingFileWriter(altPath)
	if err != nil {
		return fmt.Errorf("creating alternates writer: %w", err)
	}
	defer func() {
		if err := alternatesWriter.Close(); err != nil && returnedErr == nil {
			returnedErr = fmt.Errorf("closing alternates writer: %w", err)
		}
	}()

	if _, err := io.WriteString(alternatesWriter, expectedRelPath); err != nil {
		return fmt.Errorf("writing alternates: %w", err)
	}

	if err := transaction.CommitLockedFile(ctx, txManager, alternatesWriter); err != nil {
		return fmt.Errorf("committing alternates: %w", err)
	}

	if tx := storage.ExtractTransaction(ctx); tx != nil {
		alternatesRelativePath, err := filepath.Rel(tx.FS().Root(), altPath)
		if err != nil {
			return fmt.Errorf("rel alternates file: %w", err)
		}

		if err := tx.FS().RecordFile(alternatesRelativePath); err != nil {
			return fmt.Errorf("record alternates file")
		}
	}

	return removeMemberBitmaps(ctx, pool, repo)
}
