## Title
Unstaked attacker can saturate global `open_connections` slack via stalled QUIC handshakes, denying legitimate TPU connections - ([File: streamer/src/nonblocking/quic.rs])

## Summary
The pre-handshake abuse checks in `run_server` (per-IP `ConnectionRateLimiter::is_allowed` and the global `overall_connection_rate_limiter.current_tokens() == 0` check) are non-consuming peeks; the actual token consumption (`register_connection` / `consume_tokens`) only happens *after* a QUIC handshake completes in `setup_connection`. An attacker who never completes the handshake therefore never gets charged against either rate limiter and can repeatedly pass both checks, incrementing the single global `stats.open_connections` counter via `ClientConnectionTracker::new` on every accepted `Incoming` until it reaches `qos.max_concurrent_connections()`, at which point legitimate clients are refused via `refused_connections_too_many_open_connections`.

## Finding Description
In `run_server` (`streamer/src/nonblocking/quic.rs:304-411`), each incoming QUIC `Incoming` is gated by:
1. `overall_connection_rate_limiter.current_tokens() == 0` — a peek at `TokenBucket` state [1](#0-0) 
2. `rate_limiter.is_allowed(&incoming.remote_address().ip())` — a peek at the per-IP `ConnectionRateLimiter` [2](#0-1) 
3. `ClientConnectionTracker::new(stats.clone(), qos.max_concurrent_connections())`, which increments the single shared `AtomicUsize` `stats.open_connections` and only fails once that counter reaches `max_concurrent_connections` [3](#0-2) , refusing the connection and bumping `refused_connections_too_many_open_connections` if the cap is hit [4](#0-3) .

Crucially, `ConnectionRateLimiter::is_allowed` is documented and tested to be a non-mutating check ("just checking should not mutate state"); the actual budget is only consumed by `register_connection`, and `register_connection` is only called in `setup_connection` *after* the QUIC handshake (`connecting.await`) succeeds [5](#0-4) [6](#0-5) . Likewise, the global `overall_connection_rate_limiter` is only actually decremented via `consume_tokens(1)` post-handshake in `setup_connection` [7](#0-6) , while the pre-accept gate only reads `current_tokens()` without consuming.

Since neither rate limiter is charged unless the handshake completes, an attacker can hold arbitrarily many `Incoming` connections in a stalled/slow-handshake state (satisfying "Preconditions: unstaked attacker can hold TCP/UDP flows open ... without finishing `connecting.await`"). Each such connection increments `stats.open_connections` via `ClientConnectionTracker::new` before the handshake resolves, and is only decremented when the `ClientConnectionTracker` is dropped — which happens either when `setup_connection`'s `timeout(QUIC_CONNECTION_HANDSHAKE_TIMEOUT, connecting)` expires, or when the handshake completes/fails. Per-peer/per-IP caps in `ConnectionTable` (`SwQos::try_add_connection`, `SimpleQos::try_add_connection`) are enforced only *after* a successful handshake via `qos.try_add_connection`, so a never-completing handshake never touches those per-peer bounds at all — it is counted only in the shared `open_connections` gate that `ClientConnectionTracker::new` enforces. This matches the described exploit exactly: attacker connections bypass per-peer `ConnectionTable` limits entirely while still consuming the shared `max_concurrent_connections` slack.

`max_concurrent_connections()` for `SwQos` is `(max_staked_connections + max_unstaked_connections) * 5 / 4` [8](#0-7) , a bounded, finite value known/derivable from default or configured parameters, making the target count for saturation static and achievable.

## Impact Explanation
This is a Denial-of-Service against the TPU QUIC endpoint: once `open_connections` reaches `max_concurrent_connections`, every subsequent `Incoming` — including from legitimate staked and unstaked clients — is refused at `ClientConnectionTracker::new` and counted under `refused_connections_too_many_open_connections`, before any per-peer/stake-based admission logic runs. This denies all clients (including staked/high-priority ones) the ability to even attempt a TPU connection, which is a scoped ingress-availability impact consistent with a QoS/rate-limit bypass leading to unstaked-attacker-triggered denial of service on validator ingress.

## Likelihood Explanation
Feasible and repeatable with only unprivileged network access to the leader's public TPU QUIC port. The attacker does not need stake, gossip presence, or any privileged capability — only the ability to open TCP/UDP-level flows and stall the QUIC handshake (e.g., send the initial packet and then withhold further handshake packets, or open connections against a socket and never complete `ClientHello`/`ServerHello` exchange) for up to `QUIC_CONNECTION_HANDSHAKE_TIMEOUT`. Because the pre-accept peeks never consume budget for incomplete handshakes, the attack is bounded only by `max_concurrent_connections` (a fixed, computable value) and by however many source IPs/ports the attacker can use to keep `is_allowed` returning true (which, per the non-mutating semantics, is essentially always true for IPs that have not yet completed a handshake, regardless of attempt volume). This is a low-cost, single-node, off-path attack.

## Recommendation
Charge (consume) the per-IP and overall connection-rate-limiter budgets, or otherwise bound in-flight (non-handshake-complete) connection attempts, at accept time rather than only after a successful handshake — e.g., consume a token from `overall_connection_rate_limiter` and register the IP in `rate_limiter` before/at the point `ClientConnectionTracker::new` is called, refunding on handshake failure/timeout. Additionally, consider a dedicated, smaller cap on in-flight (pre-handshake) `Incoming`/`Connecting` distinct from `max_concurrent_connections`, so that stalled handshakes cannot consume the entire post-handshake connection budget that legitimate, quickly-handshaking peers rely on.

## Proof of Concept
Integration test plan (using existing test harness in `streamer/src/nonblocking/quic.rs` / `testing_utilities.rs`):
1. Spawn a test QUIC server via `spawn_stake_weighted_qos_server` with a small `SwQosConfig { max_staked_connections: N, max_unstaked_connections: M, .. }` so `max_concurrent_connections = (N+M)*5/4` is a small, known number.
2. From a single attacker task, open `max_concurrent_connections` raw UDP sockets/QUIC `Connecting` attempts to the server's TPU address, sending only the initial QUIC packet and then withholding all further handshake packets (or use a custom client `Endpoint` that never advances past `Connecting`), so `connecting.await` inside `setup_connection` never resolves before `QUIC_CONNECTION_HANDSHAKE_TIMEOUT`.
3. Assert `stats.open_connections.load(Ordering::Relaxed) == max_concurrent_connections` and `stats.outstanding_incoming_connection_attempts.load(...) == max_concurrent_connections` while attacker connections are stalled.
4. From a legitimate, well-behaved client, attempt a normal QUIC connection and assert it is refused: `stats.refused_connections_too_many_open_connections.load(Ordering::Relaxed) >= 1` and the client's `connect().await` fails/times out.
5. Wait past `QUIC_CONNECTION_HANDSHAKE_TIMEOUT`, confirm `stats.open_connections` drops back toward 0 as `ClientConnectionTracker` instances are dropped via `connection_setup_timeout`, and confirm the legitimate client can now connect successfully.

impl ClientConnectionTracker {
    /// Check the max_concurrent_connections limit and if it is within the limit
    /// create ClientConnectionTracker and increment open connection count. Otherwise returns Err
    fn new(stats: Arc<StreamerStats>, max_concurrent_connections: usize) -> Result<Self, ()> {
        let open_connections = stats.open_connections.fetch_add(1, Ordering::Relaxed);
        if open_connections >= max_concurrent_connections {
            stats.open_connections.fetch_sub(1, Ordering::Relaxed);
            debug!(
                "There are too many concurrent connections opened already: open: \
                 {open_connections}, max: {max_concurrent_connections}"
            );
            return Err(());
        }

        Ok(Self { stats })
    }

    /// Check if the connection from the said `ip` is allowed.
    /// Here we assume that only IPs with actual confirmed connections are stored in it,
    /// since we should only modify server state once source IP is verified
    pub fn is_allowed(&self, ip: &IpAddr) -> bool {
        // Check if we have records in the rate limiter for the given IP address
        match self.limiter.current_tokens(ip) {
            Some(r) => r > 0, // we have a record, and rate is not exceeded
            None => true,     // if we have not seen IP, allow connection request
        }
    }

    pub fn register_connection(&self, ip: &IpAddr) -> bool {
        if self.limiter.consume_tokens(*ip, 1).is_ok() {
            debug!("Request from IP {ip:?} allowed");
            true // Request allowed
        } else {
            debug!("Request from IP {ip:?} blocked");
            false // Request blocked
        }
    }
