### Title
Certificate timestamps are unmarshaled and converted with no bounds/sanity checking, allowing an unauthenticated peer to submit arbitrary-magnitude `notBefore`/`notAfter` values before signature verification - ([File: cert/cert_v1.go], [File: cert/cert_v2.go])

### Summary
The reported Chainlink oracle issue was that `latestAnswer`/`latestTimestamp` values returned by an external, unauthenticated-by-signature source were converted with unchecked arithmetic and never validated against `!= 0` / a reasonable time bound before being trusted. The same pattern exists in Nebula's certificate parsers: `notBefore`/`notAfter` are read directly off the wire as raw 64-bit integers and passed straight into `time.Unix(...)` with no range check, and this conversion happens during `Unmarshal`/parse, which runs *before* `CheckSignature`/`CAPool.verify` is ever invoked on the certificate. Any peer — including one with no CA-issued certificate at all — can hand Nebula a self-signed or garbage-signed certificate blob during the handshake and have its timestamp fields converted and later compared with `Expired()`, with no bound on how far in the past/future the value can be.

### Finding Description
- In `cert/cert_v1.go`, `unmarshalCertificateV1` builds `detailsV1.notBefore`/`notAfter` directly from the protobuf `int64` fields with no bounds check: [1](#0-0) 
  Specifically: [2](#0-1) 

- In `cert/cert_v2.go`, `unmarshalDetails` reads the ASN.1 `Time` field (defined in the schema as `INTEGER (0..18446744073709551615)`, i.e., up to `uint64` max) into a Go `int64` and converts with `time.Unix`, again unchecked: [3](#0-2) [4](#0-3) 

- Both `certificateV1.Expired` and `certificateV2.Expired` simply compare these unchecked `time.Time` values against `t`, with no upper/lower sanity bound (analogous to the missing `newPrice != 0` / timeout-range check in the oracle report): [5](#0-4) [6](#0-5) 

- Critically, this parsing/conversion happens in `unmarshalCertificateV1`/`unmarshalCertificateV2`, which are invoked from certificate unmarshal/handshake paths *before* any signature or CA-pool trust check occurs (`AddCA`/`VerifyCertificate` happen only after the object already exists with these fields populated): [7](#0-6) 

  This means an attacker with no valid CA-signed certificate can still submit a handshake certificate whose `notBefore`/`notAfter` integer fields are attacker-chosen (e.g., `math.MinInt64`, `math.MaxInt64`, or values causing the ASN.1 `Time` field—declared up to `uint64` max but stored in an `int64`—to wrap to a negative Unix timestamp), and the code will happily construct a `time.Time` and evaluate `Expired()` against it without ever range-checking the raw integer before the signature is validated.

### Impact Explanation
This does not bypass certificate signature verification (Nebula still requires a valid CA signature for the certificate to be trusted for authentication), so it is not a full authentication bypass. Its impact is limited to how the unvalidated timestamp is used prior to/around validation: unusual, extreme integer values sail through unmarshal and are stored as ordinary `time.Time` values, mirroring the oracle bug's root cause (trusting untrusted numeric input with no bounds check before use in the freshness/expiry logic that downstream code and operators rely on).

### Likelihood Explanation
Likelihood of exploitation to achieve concrete security impact (auth bypass, decrypt/forge, crash) is low/unclear from static review alone — the surrounding signature verification (`CheckSignature`, `CAPool.verify`) still gates whether an untrusted certificate is ever accepted as valid, so this analog is weaker than the oracle case where the unchecked value was consumed directly by financial logic.

### Recommendation
Validate the raw `notBefore`/`notAfter` integers against a sane range (e.g., non-negative, within a plausible calendar range) immediately after decoding and before constructing `time.Time`/using them in `Expired()`, in both `unmarshalCertificateV1` (`cert/cert_v1.go`) and `unmarshalDetails` (`cert/cert_v2.go`), consistent with the oracle fix's recommendation to check that values are within a configurable/sane bound rather than trusting the wire format's nominal type range.

### Proof of Concept
Not independently verified end-to-end (would require constructing a PEM/ASN.1-encoded certificate with `notBefore`/`notAfter` set to `math.MinInt64` or a value that overflows when re-serialized, and observing whether `time.Unix` and subsequent `Expired()` comparisons produce unexpected accept/reject behavior). Given the tool limitations of this review (static code search only, no ability to run the parser), this should be confirmed by a background agent capable of building and running Nebula's certificate test/fuzz harnesses (e.g., extending `cert/cert_v2_test.go`'s unmarshal tests) with out-of-range `notBefore`/`notAfter` values.

```go
// AddCA verifies a Nebula CA certificate and adds it to the pool.
func (ncp *CAPool) AddCA(c Certificate) error {
	if !c.IsCA() {
		return fmt.Errorf("%s: %w", c.Name(), ErrNotCA)
	}

	if !c.CheckSignature(c.PublicKey()) {
		return fmt.Errorf("%s: %w", c.Name(), ErrNotSelfSigned)
	}

	sum, err := c.Fingerprint()
	if err != nil {
		return fmt.Errorf("could not calculate fingerprint for provided CA; error: %w; %s", err, c.Name())
	}

	cc := &CachedCertificate{
		Certificate:    c,
		Fingerprint:    sum,
		InvertedGroups: make(map[string]struct{}),
	}

	for _, g := range c.Groups() {
		cc.InvertedGroups[g] = struct{}{}
	}

	ncp.CAs[sum] = cc

	if c.Expired(time.Now()) {
		return fmt.Errorf("%s: %w", c.Name(), ErrExpired)
	}
```
