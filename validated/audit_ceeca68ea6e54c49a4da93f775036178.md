## Analysis: Front-run of standby-witness reward distribution via last-block vote count inflation

The Carapace bug is a classic "flash accrual" pattern: a participant deposits capital right before a periodic reward-accrual event fires, and the accrual mechanism naively credits them as if they had contributed for the entire period. Java-tron has a directly analogous flaw in how the **standby witness allowance** is distributed at each maintenance (epoch) boundary.

### Root cause

Vote counting and the standby-witness payout both happen inside a single call to `MaintenanceManager.doMaintenance()`, but in the wrong order relative to vote freshness:

1. `MaintenanceManager.doMaintenance()` first tallies all votes recorded in `VotesStore` since the previous maintenance — including votes cast in the very last block of the concluding cycle — via `countVote(votesStore)`, then immediately applies the delta to each witness's persisted vote count: [1](#0-0) 

2. Right after that update, `incentiveManager.reward(newWitnessAddressList)` distributes the entire cycle's fixed standby-witness allowance (`totalPay`) pro-rata using the **just-updated** vote count: [2](#0-1) [3](#0-2) 

Because `applyBlock()` in `Manager.java` executes all transactions in the block (including any `VoteWitnessContract` transaction) before invoking `consensus.applyBlock(block)` (which triggers `doMaintenance()`), a vote cast in the final block of a cycle is fully counted for that concluding cycle's reward split: [4](#0-3) 

By contrast, the per-voter VI-based reward mechanism (`accumulateWitnessVi`/`VoteRewardUtil`/`MortgageService.withdrawReward`) is properly protected: `accumulateWitnessVi` for the concluding cycle uses the witness's **pre-existing** vote count (captured before `countVote` applies new deltas) [5](#0-4) , and `VoteWitnessActuator` always calls `mortgageService.withdrawReward()` to settle stale reward with the OLD vote list before applying new votes [6](#0-5) . New/changed votes only start earning VI-based reward from the following cycle. The standby-witness allowance path has no such lag — it is the exact "last-second deposit steals the whole period's yield" pattern from the report.

### Title
Standby witness reward pool can be front-run by voting in the last block of a maintenance cycle - (File: consensus/src/main/java/org/tron/consensus/dpos/MaintenanceManager.java)

### Summary
`MaintenanceManager.doMaintenance()` tallies fresh votes into `witnessCapsule.setVoteCount()` and then immediately calls `IncentiveManager.reward()`, which splits a fixed per-cycle standby-witness allowance pro-rata by that just-updated vote count, allowing a vote cast in the final block of a cycle to receive full credit for the entire cycle's reward.

### Finding Description
`doMaintenance()` first calls `countVote(votesStore)` to tally all vote changes recorded since the last maintenance and applies them to each witness's `voteCount` [1](#0-0) . It then immediately calls `incentiveManager.reward(newWitnessAddressList)` [7](#0-6) . Inside `IncentiveManager.reward()`, the fixed pool `totalPay = consensusDelegate.getWitnessStandbyAllowance()` is split among top-129 witnesses strictly by `getWitness(address).getVoteCount()` at that instant: `pay = voteCount * totalPay / voteSum` [8](#0-7) . Since ordinary transactions (including `VoteWitnessContract`, reachable by any signer) execute before `consensus.applyBlock()`/maintenance in `Manager.processBlock()` [4](#0-3) , a vote cast in the very last block prior to `nextMaintenanceTime` is included in `countVote()`'s tally and therefore counts at full weight for the entire concluding cycle's payout, even though it was only in effect for a single block.

### Impact Explanation
The standby witness allowance is a fixed reward pool paid out once per maintenance cycle. Diverting a disproportionate share to a witness whose vote count was inflated only moments before payout directly reduces the legitimate share owed to other witnesses who held genuine votes for the entire cycle — an unbacked reallocation of protocol reward funds, analogous to the reported theft of unearned premium in the referenced report.

### Likelihood Explanation
`getNextMaintenanceTime()` is a public, deterministic on-chain value, so any account can time a `VoteWitnessContract` transaction (requiring only frozen TRON Power, no special privilege) to land in the last block of a cycle. This requires no validator collusion, no network-level manipulation, and can be repeated every maintenance cycle.

### Recommendation
Compute the vote count used for `IncentiveManager.reward()` from the vote tally as of the *start* of the concluding cycle (i.e., before applying `countWitness` deltas accumulated during that cycle), mirroring the lagged/cycle-boundary approach already used for the VI-based per-voter reward (`accumulateWitnessVi`), so that only votes held for the full cycle are credited toward that cycle's standby allowance.

### Proof of Concept
1. Freeze TRX to obtain TRON Power under account A, without voting for any witness yet.
2. Monitor `getNextMaintenanceTime()` on-chain and wait until immediately before this timestamp.
3. Submit `VoteWitnessContract` from account A allocating full TRON Power to witness W (could be attacker-controlled) so the transaction lands in the last block before maintenance triggers.
4. `Manager.processBlock()` executes the vote transaction, updating `VotesStore`, then invokes `consensus.applyBlock()` → `MaintenanceManager.doMaintenance()`.
5. `countVote(votesStore)` picks up A's new vote and updates `witnessCapsule.setVoteCount()` for W before `incentiveManager.reward()` runs.
6. `IncentiveManager.reward()` distributes the full cycle's `totalPay` pro-rata using the now-inflated vote count for W, granting W (and by extension A's vote) full credit for a cycle-long reward despite the vote being active for one block.

  public void reward(List<ByteString> witnesses) {
    if (consensusDelegate.allowChangeDelegation()) {
      return;
    }
    if (witnesses.size() > WITNESS_STANDBY_LENGTH) {
      witnesses = witnesses.subList(0, WITNESS_STANDBY_LENGTH);
    }
    long voteSum = 0;
    for (ByteString witness : witnesses) {
      voteSum += consensusDelegate.getWitness(witness.toByteArray()).getVoteCount();
    }
    if (voteSum <= 0) {
      return;
    }
    long totalPay = consensusDelegate.getWitnessStandbyAllowance();
    for (ByteString witness : witnesses) {
      byte[] address = witness.toByteArray();
      long pay = (long) (consensusDelegate.getWitness(address).getVoteCount() * ((double) totalPay
          / voteSum));
      AccountCapsule accountCapsule = consensusDelegate.getAccount(address);
      accountCapsule.setAllowance(accountCapsule.getAllowance() + pay);
      consensusDelegate.saveAccount(accountCapsule);
    }
  }
