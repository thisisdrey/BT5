### Title
Praefect stream proxy blocks all destination writers when one secondary lags, hanging in-flight push/fetch RPCs indefinitely - ([File: internal/grpc/proxy/handler.go])

### Summary
Praefect's gRPC stream proxy (`internal/grpc/proxy/handler.go`) fans out every client-sent frame from a push/fetch RPC to the primary and all secondary Gitaly backends by writing sequentially, without any timeout, into small per-destination buffered channels. If any single destination's consumer goroutine falls behind (slow network, backpressure, an unresponsive node), the shared read loop that feeds *all* destinations blocks forever on that one channel, stalling the entire RPC for every other (healthy) destination too. This is structurally the same bug class as the reported broker issue — sequential, blocking delivery to a set of "subscribers" without per-recipient isolation — except here there isn't even a fallback timeout.

### Finding Description
`forwardClientToServers` creates one small buffered channel (`chan *frame, 16`) per destination (primary + secondaries) and spawns one `forwardFramesToServer` goroutine per destination to drain it via `dst.SendMsg(f)`: [1](#0-0) 

The single reader of the client stream, `receiveFromClientAndForward`, then loops over *all* `frameChans` and sends the same frame into each one, one at a time, with a plain blocking channel send and no `select`/timeout/context check: [2](#0-1) 

Because this send has no `select { ... case <-ctx.Done(): ...}` guard (unlike the broker's `select` with `time.After(b.timeout)`), once one destination's 16-message buffer fills — e.g. because that Gitaly node is slow to `SendMsg` over a congested or partially failed network link, or is itself overloaded — the loop blocks on `frameChan <- f` for that destination. Since this is the *same* loop instance servicing every destination, all other destinations (including a perfectly healthy primary) stop receiving new frames from the client too, even though only one backend is slow. The entire RPC (e.g. an in-progress `git push`/`SSHReceivePack` or `PostUploadPack` being replicated by Praefect to primary + secondaries) hangs until the slow node catches up or the client/context is torn down.

This mirrors the reported bug class exactly: broadcast/fan-out to multiple recipients is done through one blocking, sequential path, so one slow or stuck recipient (subscriber / secondary Gitaly node) can stall delivery to everyone else, risking non-deterministic timing and, worst case, indefinitely hung streams since there's no timeout fallback at all here.

### Impact Explanation
Praefect proxies most mutator RPCs (pushes, ref updates, etc.) to multiple physical Gitaly nodes via `HandleStream`/`forwardClientToServers`. An ordinary user's push or fetch that gets routed through Praefect to a cluster with one degraded/slow replica can have its entire streaming RPC — including delivery to the otherwise-healthy primary — stall indefinitely, because the client-frame relay loop is blocked on the slow destination's channel. This ties up the goroutines, connection, and any locks/quarantine state held for that RPC's duration, and can accumulate across concurrent requests hitting the same degraded node, producing a resource-exhaustion / availability issue (DoS) for the affected virtual storage without any malicious actor being required.

### Likelihood Explanation
This does not require a malicious actor — only one backend replica (secondary Gitaly node) being transiently slow, network-congested, or momentarily unresponsive, which is a normal operational condition (node restarts, GC pauses, disk pressure, network blips) rather than an edge case. Any ordinary streaming write RPC proxied by Praefect during such a window is affected.

### Recommendation
Make delivery to each destination independent and bounded, mirroring the recommended broker fix: send to each destination's `frameChan` in its own goroutine (or with a `select` against the per-destination stream's context/cancellation) instead of a single shared blocking loop, so a stuck destination only affects its own stream and cannot stall frame delivery to the primary or other secondaries. Additionally, ensure the send respects `ctx.Done()`/cancellation so a stalled destination can be aborted rather than hanging forever.

### Proof of Concept
1. Set up Praefect with a primary and at least one secondary Gitaly node.
2. Start a large streaming push (e.g. `SSHReceivePack`) that sends more than 16 chunked frames.
3. Introduce artificial slowness/backpressure on the secondary's connection (e.g. throttle the network or pause the secondary process) so its `forwardFramesToServer` goroutine cannot drain `dst.SendMsg` fast enough to keep its channel below the 16-frame buffer.
4. Observe that `receiveFromClientAndForward`'s loop over `frameChans` blocks on the secondary's full channel, and the primary (and the client) stop receiving/sending any further frames until the secondary recovers or the whole RPC times out/is cancelled at a higher layer — confirming the sequential/blocking fan-out stalls unrelated healthy destinations.

	ret := make(chan error, 1)

		var g errgroup.Group

		frameChans := make([]chan<- *frame, 0, len(dsts))

			frameChan := make(chan *frame, 16)
			frameChan <- &frame{payload: dst.destination.Msg} // send re-written message

func receiveFromClientAndForward(src grpc.ServerStream, frameChans []chan<- *frame) error {
	f := &frame{}

	if err := src.RecvMsg(f); err != nil {
		for _, frameChan := range frameChans {
			// signal no more data to redirect
			close(frameChan)
		}

		return err // this can be io.EOF which is happy case
	}

	for _, frameChan := range frameChans {
		frameChan <- f
	}

	return nil
}
