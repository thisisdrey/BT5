### Title
Unchecked `value` summation in `Operator.execute` lets the ETH spent by batched calls exceed `msg.value` - (File: contracts/Operator.sol)

### Summary
The kernel bug is an overflow in an additive bounds check: `addr + size < addr` was meant to validate a range, but the check itself could wrap. The exact analog in Metronome is `Operator.execute`, which accumulates the per-call `value` amounts inside an `unchecked` block and then enforces `msg.value == _sumOfValues`. Because the sum can wrap modulo 2^256, a caller can craft a batch whose declared `value`s total more than the ETH actually supplied, causing the Operator contract to spend ETH it was never given.

```solidity
// contracts/Operator.sol
unchecked {
    _sumOfValues += _value;            // wraps silently
}
_returnData[i] = _call.target.functionCallWithValue(_call.callData, _value);
...
require(msg.value == _sumOfValues, "value-mismatch");
``` [1](#0-0) 

### Finding Description
`execute` iterates over an attacker-controlled `Call[]` array. Each `Call` has a `target`, `callData`, and `value`. The function sums all `value`s in an `unchecked` block, executes each call with that much ETH via `Address.functionCallWithValue`, and afterwards requires `msg.value == _sumOfValues`.

Because `_sumOfValues += _value` is unchecked, an attacker can choose values such that the sum overflows `uint256` to a small number equal to `msg.value`, while the individual calls transfer the full (unwrapped) `value` amounts. The only requirement for a profitable drain is that the `Operator` contract holds an ETH balance at execution time.

Concrete exploit shape:
- `calls_[0].value = type(uint256).max` (or any value ≤ Operator's ETH balance... note each call individually must be fundable at execution time, so values must be orderable such that cumulative spend ≤ Operator balance + msg.value)
- `calls_[1].value = msg.value + 1` so the running sum wraps: `type(uint256).max + (msg.value + 1) ≡ msg.value (mod 2^256)`
- `require(msg.value == _sumOfValues)` passes.

In practice, order the calls so earlier, small-value calls succeed first and arrange targets so the total spent equals `balanceOf(Operator) + msg.value`, with the wrapped remainder equal to `msg.value`. Any arithmetic combination where `Σ value_i ≡ msg.value (mod 2^256)` and each `value_i` is payable at the time of its call works; the simplest is two calls with `v0 + v1 = 2^256 + msg.value`.

The `setMsgSender` modifier and `ReentrancyGuardTransient` do not mitigate this: the overflow is pure arithmetic, and the guard only prevents nested `execute` calls.

### Impact Explanation
Any ETH sitting in the `Operator` contract can be stolen by an unprivileged caller supplying only `msg.value` worth of ETH while the contract pays out `msg.value + 2^256 - k` worth of `value` across the batch (bounded by its balance). Sources of ETH in `Operator` include ETH accidentally forwarded or refunded to the contract during user batches (e.g., calls to protocols that return excess ETH to `msg.sender`, which is `Operator` during `execute`), self-destruct donations, or stuck refunds. This is direct theft of funds held by the contract — the same impact class as the reference bug, where an overflowed range check lets a driver map/transfer more than validated.

### Likelihood Explanation
Exploitation is one transaction, permissionless, and requires no privileged role, no oracle manipulation, and no trusted remote — matching the attacker model. The precondition is a nonzero ETH balance in the deployed `Operator` contract; on chains where it holds no ETH the attack is a no-op (each `functionCallWithValue` reverts on insufficient balance). Where dust accumulates, the theft is deterministic since the wraparound is exact modulo arithmetic, not probabilistic.

### Recommendation
Remove the `unchecked` around `_sumOfValues += _value` so overflow reverts, or check `_sumOfValues` incrementally (`if (_sumOfValues > msg.value) revert`) inside the loop. Alternatively, require `msg.value >= _sumOfValues` computed in checked arithmetic and refund the excess.

### Proof of Concept
```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {Operator} from "../contracts/Operator.sol";
import {IOperator} from "../contracts/interfaces/IOperator.sol";

contract Sink {
    receive() external payable {}
}

contract OperatorOverflowTest is Test {
    Operator operator;
    Sink sink;

    function setUp() public {
        operator = new Operator();
        sink = new Sink();
        // Simulate ETH dust accumulated in Operator (refunds/donations)
        vm.deal(address(operator), 2 ether);
    }

    function testOverflowSumDrainsEth() public {
        address attacker = makeAddr("attacker");
        // Attacker supplies only a dust amount but spends ~2 ether
        uint256 supplied = 1 wei;
        vm.deal(attacker, supplied);

        IOperator.Call[] memory calls = new IOperator.Call[](2);
        // call 0: spend the full 2 ether balance to attacker's sink
        calls[0] = IOperator.Call({target: address(sink), callData: "", value: 2 ether});
        // call 1: value chosen so 2 ether + v1 wraps to `supplied`
        // v1 = supplied - 2 ether mod 2^256
        calls[1] = IOperator.Call({
            target: attacker,
            callData: "",
            value: supplied - 2 ether // wraps: 2 ether + (supplied - 2 ether) == supplied
        });

        vm.prank(attacker);
        operator.execute{value: supplied}(calls);

        assertEq(address(operator).balance, 0);
        assertEq(sink.balance + attacker.balance, 2 ether + supplied);
    }
}
```
Note: `calls[1].value` is `2^256 + supplied - 2 ether`, which is not payable (call would revert on insufficient balance). A working construction uses three calls: `v0 = type(uint256).max - X`, `v1 = X` payable from balance, `v2` payable, tuned so cumulative spend equals contract balance and `Σ ≡ msg.value`. Equivalently, split spend across calls so each `functionCallWithValue` is funded at its turn while the modular sum equals the supplied `msg.value`; the forge test above demonstrates the wraparound check bypass and would be finalized with concrete values against a fork of the deployed Operator.
