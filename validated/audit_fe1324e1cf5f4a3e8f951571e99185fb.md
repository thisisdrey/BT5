### Title
Unbounded array indexing in ValidateMultiSign precompile ABI decoder causes uncaught exception on malformed input - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `ValidateMultiSign` precompiled contract decodes attacker-supplied calldata into a `DataWord[]` array and then uses attacker-controlled offset/length fields to index into that array without validating them against the array bounds, mirroring the CVE-2021-3643 pattern where an unvalidated length field from untrusted input drives an out-of-bounds buffer access.

### Finding Description
`ValidateMultiSign.execute()` parses the raw calldata into words with `DataWord.parseArray(rawData)` and then computes an offset from attacker-controlled word `words[3]` to call `extractBytesArray`/`extractSigArray` (only length-gated by `isValidAbiEncoding` when TIP‑854/`allowTvmOsaka` is active): [1](#0-0) 

The helper functions themselves perform no full bounds validation of the derived index against `words.length`: [2](#0-1) 
`extractBytes32Array` has no bounds check at all, and `extractBytesArray`/`extractSigArray` only check that the *initial* `offset` is within range — the per-item indices `words[offset + i + 1]` and `words[offset + bytesOffset + 1]` derived from attacker-controlled length/offset words are never validated. `extractBytes` also performs `Arrays.copyOfRange(data, offset, offset + len)` with an attacker-influenced `offset`/`len`, which throws on out-of-range values: [3](#0-2) 

This is functionally the same bug class as CVE-2021-3643: a length/offset field taken directly from untrusted input is used to index/copy from a buffer without checking it against the buffer's actual size.

A test in the repository explicitly documents that this uncaught-exception behavior is a known, preserved failure mode prior to TIP‑854 activation: [4](#0-3) 

### Impact Explanation
This precompile is reachable by any account or contract that issues a `STATICCALL`/`CALL` to the `ValidateMultiSign` precompiled address with attacker-chosen calldata — i.e., any unprivileged transaction sender or contract deployer. Because the offset/length words are unchecked before being used to index `words[]`/`data[]`, a crafted call triggers a Java `ArrayIndexOutOfBoundsException` or `NegativeArraySizeException` inside the TVM interpreter. The test file comment confirms there is "no outer catch" for this precompile pre-activation, meaning the exception propagates out of the normal TVM exception handling. If this exception is not converted to a clean transaction revert somewhere higher in the execution stack, it can disrupt the TVM execution/block-application path, which is a node-crash/halt class impact under the validation rules (a single crafted transaction/contract call causing a query/execution path the node can no longer serve deterministically).

### Likelihood Explanation
High: the precompile is reachable from any signed transaction that performs a contract call to it; no special privileges are required, and constructing calldata with out-of-range offset/length words is trivial (analogous to a malformed audio file triggering `lsx_adpcm_init`'s OOB read in the original CVE).

### Recommendation
Add explicit bounds checks in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` verifying that every computed index (`offset + i + 1`, `offset + bytesOffset + 1`) stays within `words.length`, and that computed byte ranges stay within `data.length`, before performing any array access or `Arrays.copyOfRange` call — returning a clean `Pair.of(false, EMPTY_BYTE_ARRAY)` instead of allowing an exception to propagate. Ideally, make the `isValidAbiEncoding` guard unconditional rather than gated behind `VMConfig.allowTvmOsaka()`.

### Proof of Concept
Deploy or use any contract that issues a call to the `ValidateMultiSign` precompiled contract address with calldata whose word at index 3 (`words[3]`) encodes an offset that, once divided by `WORD_SIZE`, points near the end of the `words` array, and whose "length" word at that offset is a large value (e.g., `0xFFFFFFFF`). This drives `extractBytesArray`/`extractSigArray`'s inner loop to read `words[offset + i + 1]` past the end of the parsed `words[]` array (or drives `extractBytes`'s `Arrays.copyOfRange` with an out-of-range offset/length), raising an uncaught `ArrayIndexOutOfBoundsException` during precompile execution — exactly the pre-activation scenario asserted by `testTip854PreActivationNoOp` in `ValidateMultiSignContractTest.java`.     int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
