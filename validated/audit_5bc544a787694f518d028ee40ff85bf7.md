## Title
Concurrent decrypt race allows double-delivery of a single replayed packet before anti-replay window update - (`File: connection_state.go`)

## Finding Description
`ConnectionState.Decrypt` performs anti-replay validation in three separate, lock-released steps: `cs.window.Check()` under `decryptLock` [1](#0-0) , then AEAD decryption *without holding the lock* [2](#0-1) , then `cs.window.Update()` under `decryptLock` again [3](#0-2) . `Bits.Check` is a pure read that does not mutate any window state — it only inspects `b.current` and the bitmap without setting any bit [4](#0-3) . Only `Bits.Update` actually marks the counter as seen [5](#0-4) .

If an attacker captures one legitimate ciphertext/counter pair and replays it so that it is processed by two concurrent goroutines (e.g., two UDP reads hitting the same `ConnectionState`, which is plausible since Nebula's outside-packet handling is not necessarily single-threaded per connection), both goroutines will call `Check` before either calls `Update`. Since `Check` never mutates state, both calls observe the counter as not-yet-seen and both return `true`. Both goroutines then proceed to call `cs.dKey.DecryptDanger` independently — AEAD decryption is stateless and deterministic, so both succeed and produce the same valid plaintext. Only afterward does each goroutine acquire `decryptLock` to call `Update`; the first to arrive marks the bit and returns `true`, the second observes the duplicate bit and returns `false`/`ErrAlreadySeen`. However, by that point **both** decryptions have already completed successfully, and depending on the caller in `outside.go`, the decrypted plaintext may already have been forwarded to the tun device before the second `Update` call fails.

This breaks the intended invariant that `Update`'s duplicate check is the sole authority preventing replay forwarding — the Check/Decrypt/Update sequence is not atomic with respect to `decryptLock`, creating a TOCTOU race window during which a single replayed ciphertext can be decrypted and potentially forwarded twice.

## Impact Explanation
This is a replay-protection bypass: a single attacker-captured, unmodified ciphertext for a legitimate counter can result in double-delivery of that packet's plaintext to the receiving side's tun device under concurrent processing, violating Nebula's "replayed packets are dropped" guarantee. This does not grant decryption of arbitrary new content or key compromise — the attacker only replays authentic previously-observed traffic — but duplicate delivery of application-layer traffic (e.g., duplicate commands, duplicate transactions forwarded upstream) is a real, scoped correctness/integrity impact consistent with a traffic-replay class bug in Nebula's bounty scope.

## Likelihood Explanation
This requires: (1) capturing one legitimate ciphertext (passive on-path attacker, no privileged access needed — this matches "unprivileged attacker" per the rules), and (2) causing two decrypt calls for the same `ConnectionState`/counter to run concurrently. Whether nebula's actual outside-packet reader dispatches concurrently per connection/counter (allowing two goroutines to race on `Decrypt` for the same tunnel) determines real-world feasibility; I was not able to fully confirm from `outside.go`'s call site whether such concurrency is architecturally possible for a single UDP conn in this build (the tool budget ran out before I could inspect `outside.go`'s goroutine model in full). If receive processing for a given remote/tunnel is guaranteed single-threaded (e.g., single reader goroutine per `LightHouse`/`Interface` UDP socket, serialized before calling `Decrypt`), this race would not be reachable in practice despite the code-level TOCTOU gap. This uncertainty should be resolved before treating this as a confirmed exploitable bug.

## Recommendation
Make the Check-Decrypt-Update sequence atomic with respect to a single lock: hold `decryptLock` across the entire `Check → Decrypt → Update` sequence in `ConnectionState.Decrypt` (and `VerifyRelay`), or fold the "check" step into `Update` itself (i.e., have a single locked call that checks-and-marks atomically, decrypting only after the mark succeeds, and rolling back the mark if decryption fails).

## Proof of Concept
Integration test in `connection_state_test.go`:
1. Build two `ConnectionState` objects sharing the same keys/counter such that both represent the receiver side (or reuse one `ConnectionState`).
2. Capture one valid encrypted packet + `messageCounter`.
3. Spawn two goroutines that both call `cs.Decrypt(logger, messageCounter, out, packet, nb)` concurrently on the *same* `ConnectionState`.
4. Assert that only one of the two calls returns success (`err == nil`), and the other returns `ErrAlreadySeen` — this alone would currently pass. To actually prove double-delivery, add a hook/counter incremented every time `DecryptDanger` succeeds (before `Update` is called) and assert it should be 1 but observe it can be 2 under `-race -count=100` with deliberate scheduling (e.g., inserting a small sleep between `Check` and `Decrypt`, or using `runtime.Gosched()`), demonstrating both decrypts completed despite only one being a legitimate first-seen packet.

func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {

}

func (b *Bits) Update(l *slog.Logger, i uint64) bool {
	// Fast path: i is the next expected counter. Split out so the function
	// stays small and avoids paying for the slow paths' slog argument-build
	// stack frame on every call. The bit read/test/write is inlined to
	// touch the backing word once.
	if i == b.current+1 {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if i > b.length && w&mask == 0 {
			b.lostCounter.Inc(1)
		}
		b.bits[word] = w | mask
		b.current = i
		return true
	}
	return b.updateSlow(l, i)
}
