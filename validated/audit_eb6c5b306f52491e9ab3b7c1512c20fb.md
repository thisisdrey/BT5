### Title
Sensitive `git credential fill` output (including plaintext password) written to `go` command's diagnostic log via `GOAUTH=git` error path - ([File: src/cmd/go/internal/auth/gitauth.go])

### Summary
When `GOAUTH=git <dir>` is configured and `git credential fill` exits with a non-zero status after having already written credential data (protocol/host/username/password lines) to stdout, `runGitAuth` wraps the raw combined output verbatim into the returned error. This error is cached and, if `-x` (`cfg.BuildX`) is set and no other GOAUTH source ultimately supplies a working credential for the URL, it is written unredacted to the build log via `log.Printf` in `runGoAuth`.

### Finding Description
Untrusted/attacker-influenced input is the response of `git credential fill`, invoked from `runGitAuth`: [1](#0-0) 
`cmd.CombinedOutput()` captures both stdout and stderr regardless of exit status. If the credential helper (which git itself may consult, e.g. via `credential.helper`) writes `username=...`/`password=...` lines to stdout and then fails (non-zero exit, e.g. a helper that validates and rejects after printing the cached credential), the entire raw byte content `out` — including the plaintext password line — is embedded directly into the returned `error` string via `fmt.Errorf("... %w\n%s", url, err, out)`.

That error propagates to `runGoAuth` in `src/cmd/go/internal/auth/auth.go`: [2](#0-1) 
It is stored in `cmdErrs` without redaction. If `cfg.BuildX` (the `-x` flag) is set and no credential could ultimately be loaded for the URL, the accumulated errors — including the embedded password — are printed unredacted: [3](#0-2) 

This differs from the sibling path in the same file, `parseGitAuth`, which deliberately avoids logging `username`/`password` fields and only logs the (non-sensitive) malformed-URL value: [4](#0-3) 
That existing redaction intent shows the raw-output-in-error path at line 50 was overlooked as a leak vector.

### Impact Explanation
An attacker who can influence or observe the git credential helper's behavior/output for a given host (e.g. a compromised or misconfigured helper, or a helper that echoes cached credentials before failing) can cause a real, valid password/token to be written in plaintext to the `go` command's stderr/log output when a developer or CI job runs `go build -x`/`go mod download -x`/etc. against a module proxy or VCS URL requiring GOAUTH=git. Since `-x` output is very commonly captured into CI logs or artifact stores, this matches the CVE's core primitive: authentication material improperly reaching a log destination. This would be a Go **PUBLIC** track candidate (documentation/behavior fix — add redaction before logging git-credential-fill output) rather than a memory-safety/URGENT issue, since the impact is credential disclosure through diagnostic logs, not a memory corruption.

### Likelihood Explanation
Requires: (1) `GOAUTH` set to use the `git` method (an opt-in but documented/supported configuration), (2) an unprivileged actor who can affect the credential helper's decision to print-then-fail for a given URL (helper misconfiguration, or malicious/compromised helper as commonly cited in the CVE's own threat model of "credentials written to diagnostic logs"), and (3) `-x` (verbose) mode with logs retained/aggregated. This is not attacker-controlled-server or attacker-controlled-network-input in the strict sense; it depends on a legitimate victim workflow (running `go` with `GOAUTH=git` and `-x`) combined with a credential helper that yields partial output before failing.

### Recommendation
In `runGitAuth` (`src/cmd/go/internal/auth/gitauth.go:48-51`), do not embed the raw `out` bytes from `git credential fill` into the returned error. Redact or omit credential-bearing fields (parse and strip `password=`/`username=` lines) before including any diagnostic text in the error, consistent with the redaction already applied in `parseGitAuth` for the `url=` field.

### Proof of Concept
```go
package auth

import (
	"strings"
	"testing"
)

// Demonstrates that raw 'git credential fill' output (including password)
// would be embedded verbatim in the error message construction used by
// runGitAuth, which is later logged unredacted when cfg.BuildX is set.
func TestGitCredentialOutputLeaksPasswordIntoError(t *testing.T) {
	// Simulated CombinedOutput() from a credential helper that printed
	// the cached credential before exiting non-zero (e.g. rejected/expired).
	out := []byte("protocol=https\nhost=example.com\nusername=bob\npassword=secr3t\n")

	err := formatGitAuthFailureError("https://example.com/repo", out)

	if !strings.Contains(err.Error(), "secr3t") {
		t.Fatalf("expected password to be present in error text (demonstrating leak), got: %v", err)
	}
}

// formatGitAuthFailureError mirrors the vulnerable construction at
// src/cmd/go/internal/auth/gitauth.go:50:
//   fmt.Errorf("'git credential fill' failed (url=%s): %w\n%s", url, err, out)
func formatGitAuthFailureError(url string, out []byte) error {
	return &wrappedErr{msg: "'git credential fill' failed (url=" + url + "): dummy err\n" + string(out)}
}

type wrappedErr struct{ msg string }

func (e *wrappedErr) Error() string { return e.msg }
```
Expected assertion: the constructed error string contains the plaintext password `secr3t`, confirming that credential material from `git credential fill` output flows unredacted into an error that, per `runGoAuth`'s `cfg.BuildX` branch (`src/cmd/go/internal/auth/auth.go:130-139`), can be written to the `go` command's diagnostic log.
