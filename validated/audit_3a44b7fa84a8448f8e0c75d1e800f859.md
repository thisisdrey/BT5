Audit Report

## Title
Unvalidated caller-supplied token metadata lets any asset owner mint an impersonating wrapped ERC20 on Ethereum - (File: bridges/snowbridge/pallets/system-frontend/src/lib.rs)

## Summary
`register_token` in `bridges/snowbridge/pallets/system-frontend/src/lib.rs` accepts an arbitrary, caller-supplied `AssetMetadata` parameter and forwards it verbatim through `build_register_token_call` to BridgeHub's `snowbridge-pallet-system-v2::register_token`, which embeds it unmodified into `Command::RegisterForeignToken`. The only origin check performed—via `LocalAssetOwner`/`ForeignAssetOwner` in `bridges/snowbridge/runtime/runtime-common/src/v2/register_token.rs`—verifies asset *ownership* through `AssetInspect::owner`, never validating that the supplied `name`/`symbol`/`decimals` correspond to the real on-chain `pallet_assets::Metadata` of that asset.

## Finding Description
In `register_token` [1](#0-0) , the `metadata: AssetMetadata` argument is taken directly from the caller and passed into `build_register_token_call` [2](#0-1)  with no cross-check against the asset's actual on-chain metadata.

Origin validation is delegated to `T::RegisterTokenOrigin`, whose `LocalAssetOwner::try_origin` and `ForeignAssetOwner::try_origin` implementations only fetch `AssetInspect::owner(asset_location)` and compare it to the caller's converted account — they never read or compare `pallet_assets::Metadata` fields. [3](#0-2) [4](#0-3) 

The message is relayed to BridgeHub's `EthereumSystem::register_token`, which again forwards `metadata.name`/`metadata.symbol`/`metadata.decimals` unmodified into `Command::RegisterForeignToken`. [5](#0-4)  This command is later ABI-encoded for the Ethereum Gateway, which uses that exact name/symbol to instantiate the wrapped ERC-20 contract representing the registered `token_id`.

Because ownership is proven only over `asset_location` (which is trivially attacker-created and owned via permissionless `pallet_assets::create`), any user can supply metadata claiming to be a well-known token (e.g., "USD Coin"/"USDC") for a throwaway/worthless asset. The `token_id` is derived deterministically from the asset's `Location`, so this does not let an attacker hijack an *existing* registered token's identity, but it does let them register a brand-new wrapped ERC-20 whose displayed `name()`/`symbol()` impersonate a legitimate asset.

## Impact Explanation
This is a genuine runtime logic gap: the pallet's stated purpose is to let asset owners register their *Polkadot-native token* as a wrapped ERC-20 with metadata reflecting that token, but no code path enforces that the supplied metadata is actually derived from the asset's `pallet_assets::Metadata`. This compromises intended behavior of the registration pipeline and could deceive end users/integrators relying on ERC-20 `name()`/`symbol()` to identify a legitimate bridged token, since a worthless attacker-owned asset can be registered under a spoofed, recognizable brand name. It does not itself enable fund theft, unauthorized mint of an *existing* token's supply, or duplicate settlement, since each registration produces a distinct `token_id` tied to the specific source asset location.

## Likelihood Explanation
High feasibility: creating a new `pallet_assets` asset on Asset Hub is permissionless, and `register_token` is a public, non-privileged extrinsic. Nothing in `LocalAssetOwner`/`ForeignAssetOwner` or the downstream `register_token` handlers reads or validates the caller-supplied metadata against the actual asset metadata. The existing test suite (`register_usdt_from_owner_on_asset_hub`, `register_usdt_not_from_owner_on_asset_hub_will_fail`) exercises only origin/ownership checks, never metadata authenticity, confirming the path is unguarded and untested.

## Recommendation
- In `register_token`, fetch the asset's canonical `pallet_assets::Metadata` (name/symbol/decimals) via `AssetInspect`/`fungibles::metadata::Inspect` and require the supplied `metadata` to match, or remove the free-form parameter and derive metadata on-chain directly.
- Alternatively, reject registration if the supplied `name`/`symbol` collides with metadata of an already-known/well-known bridged asset, to prevent impersonation.

## Proof of Concept
1. On Asset Hub, permissionlessly create a new local asset (e.g. `id=999`) via `pallet_assets::create`, becoming its `owner`, leaving its real on-chain `Metadata` blank/innocuous.
2. Call `snowbridge_pallet_system_frontend::register_token(origin=signed(attacker), asset_id=Location::for(999), metadata=AssetMetadata{name:"USD Coin", symbol:"USDC", decimals:6}, fee_asset)`.
3. `LocalAssetOwner::try_origin` succeeds because the attacker is the registered `owner` of asset `999` — no check compares `metadata` to the asset's actual `pallet_assets::Metadata`.
4. The call proceeds to BridgeHub's `EthereumSystem::register_token`, producing `Command::RegisterForeignToken{name:"USD Coin", symbol:"USDC", decimals:6, token_id: <derived from asset 999>}`, which is relayed to the Ethereum Gateway, instantiating a wrapped ERC-20 contract advertising itself as "USD Coin (USDC)" backed only by the attacker's worthless asset `999`.

				metadata,

	fn try_origin(
		origin: RuntimeOrigin,
		asset_location: &L,
	) -> Result<Self::Success, RuntimeOrigin> {
		let origin_location = EnsureXcm::<Everything, L>::try_origin(origin.clone())?;
		if !IsForeign::contains(asset_location, &origin_location) {
			return Err(origin);
		}
		let asset_location: Location = asset_location.clone().into();
		let owner = AssetInspect::owner(asset_location.into()).ok_or_else(|| origin.clone())?;
		let location: Location = origin_location.clone().into();
		let from =
			LocationToAccountId::convert_location(&location).ok_or_else(|| origin.clone())?;
		if from != owner {
			return Err(origin);
		}
		Ok(location.into())
	}
