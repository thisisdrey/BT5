### Title
Unvalidated empty-contract transaction triggers `IndexOutOfBoundsException` in `TransactionCapsule.validateSignature` before contract-count validation - (File: `chainbase/src/main/java/org/tron/core/capsule/TransactionCapsule.java`)

### Summary
`TransactionCapsule.validateSignature()` unconditionally calls `transaction.getRawData().getContractList().get(0)` to obtain the transaction's contract before any check on whether the raw transaction actually contains a contract. `Manager.pushTransaction()` — the entry point reached by any unprivileged transaction broadcaster — invokes this method before the contract-count validation that normally happens later in `processTransaction()`. A transaction crafted with zero `Contract` entries in its `raw` data therefore causes an unguarded `List.get(0)` on an empty list, throwing an unchecked `IndexOutOfBoundsException` that is not declared/caught anywhere along the call chain.

### Finding Description
`TransactionCapsule.getOwnerAddress()` and the static `validateSignature()` both assume `getContract(0)` / `getContractList().get(0)` is safe: [1](#0-0) [2](#0-1) 

The contract-count guard (`getContractList().size() != 1`) only exists later, inside `Manager.processTransaction()`: [3](#0-2) 

However, `Manager.pushTransaction()` — the actual entry point for an unprivileged transaction broadcaster (via gRPC/HTTP `broadcastTransaction`) — calls `trx.validateSignature(...)` *before* `processTransaction()` is ever invoked, so the size check has not yet run: [4](#0-3) 

If `trx` is a `TransactionCapsule` built from a raw `Transaction` whose `raw.contract` repeated field is empty (this is trivially constructible — protobuf does not require at least one `Contract` entry, and there is no check on this before `validateSignature` is called), `getContractList().get(0)` throws `IndexOutOfBoundsException`. This exception type is not part of `pushTransaction`'s declared `throws` clause (`ValidateSignatureException, ContractValidateException, ContractExeException, AccountResourceInsufficientException, DupTransactionException, TaposException, TooBigTransactionException, TransactionExpirationException, ReceiptCheckErrException, VMIllegalException, TooBigTransactionResultException`), so it propagates as an unchecked `RuntimeException` out of `pushTransaction`.

This mirrors the CVE-2022-2719 bug class: an operation (`WriteImages`/`validateSignature`) is invoked on a list (image list / contract list) that can be empty/NULL, and the code performs an unguarded "first element" access, producing an unhandled failure instead of a graceful validation error.

### Impact Explanation
Any anonymous transaction broadcaster can submit a `Transaction` with an empty contract list to `broadcastTransaction`. This causes `Manager.pushTransaction()` to throw an unchecked `IndexOutOfBoundsException` instead of the expected `ContractValidateException`/`ValidateSignatureException`. Depending on how far up the call stack (gRPC/HTTP service layer) this propagates before being caught generically, this can manifest as unhandled-exception noise, inconsistent error responses, or, if any calling code assumes only the declared checked exceptions can occur (e.g. certain internal callers of `pushTransaction` such as re-push/retry logic), an uncaught runtime exception that disrupts transaction processing for that thread. This is a denial-of-service-class defect analogous to the ImageMagick assertion failure — malformed but easily crafted input reaches deep processing logic that assumes a non-empty list.

### Likelihood Explanation
High likelihood of reachability: constructing a `Transaction` with zero `Contract` entries requires no special privileges — it is a normal protobuf message any client can build and submit through `broadcastTransaction`. No signature or contract data is needed to reach the vulnerable `getContractList().get(0)` call, since that call happens as part of signature *validation* itself.

### Recommendation
Add an explicit `getContractList().isEmpty()` (or `getContractCount() != 1`) check at the very start of `Manager.pushTransaction()`, before `validateSignature()` is invoked, throwing a proper `ContractValidateException` for malformed transactions. Additionally, harden `TransactionCapsule.getOwnerAddress()` and `validateSignature()` themselves to check for an empty contract list and throw a checked/expected exception rather than relying on callers to pre-validate.

### Proof of Concept
1. Construct a `Transaction` whose `raw` field has `.build()` called without any `addContract(...)` call (i.e., `Transaction.raw.newBuilder().setExpiration(...)...build()`), producing `getContractList().size() == 0`.
2. Wrap it as `new TransactionCapsule(transaction)`.
3. Submit it via the node's `broadcastTransaction` RPC/HTTP endpoint, which internally calls `Manager.pushTransaction(trx)`.
4. Observe that `trx.validateSignature(...)` at [5](#0-4)  invokes `TransactionCapsule.validateSignature` → `transaction.getRawData().getContractList().get(0)` [6](#0-5) , throwing an undeclared `IndexOutOfBoundsException` instead of a controlled validation error.
