### Title
Active permission holder can escalate to full account takeover via `AccountPermissionUpdateContract` - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
`AccountPermissionUpdateActuator` allows any transaction whose signer satisfies an account's **Active** permission (which can have an arbitrarily low threshold, e.g. 1-of-N) to overwrite the account's **Owner** permission, all **Active** permissions, and the **Witness** permission in one call, with no check that the authorizing permission's weight/threshold is commensurate with the scope of the change being made.

### Finding Description
`execute()` unpacks the contract and unconditionally calls `account.updatePermissions(...)` with the new Owner, Witness, and Active permission sets supplied by the caller: [1](#0-0) 

`validate()` only checks the structural validity of the new permissions (key counts, weights, threshold, operations bitmap) — it never inspects which permission (`permissionId`) was used to *authorize* the incoming transaction, nor does it require that authorization come from the Owner permission: [2](#0-1) 

Whether an Active permission is allowed to sign an `AccountPermissionUpdateContract` transaction is governed only by the per-account `operations` bitmap of that Active permission, checked generically for any contract type in `TransactionCapsule.checkPermission()` / `WalletUtil.checkPermissionOperations()`: [3](#0-2) [4](#0-3) 

Crucially, `checkPermission()` inside the actuator validates the operations bitmap against `dynamicStore.getAvailableContractType()`, which **includes** `AccountPermissionUpdateContract` as a settable bit (it is only excluded from the *default* active-permission template, not from what a user can explicitly enable): [5](#0-4) 

This is confirmed by the test suite, which shows `AccountPermissionUpdateContract` is excluded only from the "active default operations" bitmap, not from the "available contract type" bitmap that governs what can be validly configured: [6](#0-5) [7](#0-6) 

Consequently, once an account owner grants any Active permission the `AccountPermissionUpdateContract` operation bit (e.g. for legitimate delegated key-management convenience, or by copy-pasting/misconfiguring an operations mask), a signer meeting only that Active permission's threshold — which can be as low as a single key with weight 1 — can submit an `AccountPermissionUpdateContract` transaction that replaces the Owner permission entirely (dropping all other Owner keys), rewrites all Active permissions, and rewrites the Witness permission. This mirrors the HOPR finding's bug class: a component that is supposed to be protected by a higher-threshold, multi-party control (`Safe`'s intended M-of-N owners / the account's Owner permission) can be unilaterally disabled/overridden by a single lower-privilege signer, because the enforcement of "who may change the top-level security configuration" is delegated to a bitmap flag rather than being hard-restricted to the Owner permission itself.

### Impact Explanation
A single Active-permission key holder (threshold as low as 1) can seize full administrative control of the account: remove all legitimate Owner keys, install their own key as sole Owner, and neutralize any multi-signature protection the account holders believed was in place. Because Owner permission controls all subsequent fund transfers, resource delegation, and future permission changes, this results in unauthorized account takeover and consequent theft/freezing of the account's funds — satisfying the "unauthorized account operation / theft of funds" impact bar.

### Likelihood Explanation
Exploitation requires that some Active permission on the target account has the `AccountPermissionUpdateContract` operation bit set. This is not the default template, so it requires either: (a) the account owner deliberately or mistakenly enabling that bit for a delegated/low-threshold active permission, or (b) prior use of `AccountPermissionUpdateActuator` itself (which is not restricted to Owner-authorized transactions) to add such a bit through a permission that already carries it. Given the actuator provides no structural guardrail against granting or leveraging this capability at low threshold, any workflow (custodial service, exchange hot wallet, DAO-style shared account) that grants an Active permission broad operation rights for convenience is directly exposed.

### Recommendation
Restrict `AccountPermissionUpdateActuator` so that a transaction authorized under a non-Owner (`permissionId != 0`) Active permission cannot modify the Owner permission, and/or unconditionally disallow the `AccountPermissionUpdateContract` type from ever being enabled in an Active permission's operations bitmap (remove it from `getAvailableContractType()`'s allowed set, not just the default), forcing all permission-scheme changes to always require the account's Owner threshold.

### Proof of Concept
1. Owner account `A` initializes permissions with `AccountPermissionUpdateContract` (Owner threshold 3, 3 keys) and an Active permission `P2` with threshold 1 and an operations bitmap that (intentionally or by misconfiguration) includes the `AccountPermissionUpdateContract` bit, via `AccountPermissionUpdateActuator.execute()`: [8](#0-7) 
2. Any single key in `P2` signs a new `AccountPermissionUpdateContract` transaction using `permissionId = 2`, satisfying `P2`'s threshold of 1, and setting the new Owner permission to only their own key.
3. `TransactionCapsule.checkPermission()` accepts the transaction because `P2`'s operations bitmap has the `AccountPermissionUpdateContract` bit set: [3](#0-2) 
4. `AccountPermissionUpdateActuator.execute()` applies the new Owner/Active/Witness permissions unconditionally, giving the single Active-key holder sole Owner control of account `A`.

  @Override
  public boolean validate() throws ContractValidateException {

    if (chainBaseManager == null) {
      throw new ContractValidateException(ActuatorConstant.STORE_NOT_EXIST);
    }

    if (this.any == null) {
      throw new ContractValidateException(ActuatorConstant.CONTRACT_NOT_EXIST);
    }

    AccountStore accountStore = chainBaseManager.getAccountStore();
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();

    if (dynamicStore.getAllowMultiSign() != 1) {
      throw new ContractValidateException("multi sign is not allowed, "
          + "need to be opened by the committee");
    }
    if (!this.any.is(AccountPermissionUpdateContract.class)) {
      throw new ContractValidateException(
          "contract type error,expected type [AccountPermissionUpdateContract],real type["
              + any.getClass() + "]");
    }
    final AccountPermissionUpdateContract accountPermissionUpdateContract;
    try {
      accountPermissionUpdateContract = any.unpack(AccountPermissionUpdateContract.class);
    } catch (InvalidProtocolBufferException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractValidateException(e.getMessage());
    }
    byte[] ownerAddress = accountPermissionUpdateContract.getOwnerAddress().toByteArray();
    if (!DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("invalidate ownerAddress");
    }
    AccountCapsule accountCapsule = accountStore.get(ownerAddress);
    if (accountCapsule == null) {
      throw new ContractValidateException("ownerAddress account does not exist");
    }

    if (!accountPermissionUpdateContract.hasOwner()) {
      throw new ContractValidateException("owner permission is missed");
    }

    if (accountCapsule.getIsWitness()) {
      if (!accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("witness permission is missed");
      }
    } else {
      if (accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("account isn't witness can't set witness permission");
      }
    }

    if (accountPermissionUpdateContract.getActivesCount() == 0) {
      throw new ContractValidateException("active permission is missed");
    }
    if (accountPermissionUpdateContract.getActivesCount() > 8) {
      throw new ContractValidateException("active permission is too many");
    }

    Permission owner = accountPermissionUpdateContract.getOwner();
    Permission witness = accountPermissionUpdateContract.getWitness();
    List<Permission> actives = accountPermissionUpdateContract.getActivesList();

    if (owner.getType() != PermissionType.Owner) {
      throw new ContractValidateException("owner permission type is error");
    }
    checkPermission(owner);
    if (accountCapsule.getIsWitness()) {
      if (witness.getType() != PermissionType.Witness) {
        throw new ContractValidateException("witness permission type is error");
      }
      checkPermission(witness);
    }
    for (Permission permission : actives) {
      if (permission.getType() != PermissionType.Active) {
        throw new ContractValidateException("active permission type is error");
      }
      checkPermission(permission);
    }
    return true;
  }
