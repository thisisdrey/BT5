### Title
Reference-counter "push in progress" state is set only after external interactions complete, allowing repository moves/deletion to race an in-flight push - ([File: internal/gitaly/hook/prereceive.go])

### Summary
The Solidity finding is a classic checks-effects-interactions violation: `withdrawETHForKnot` performs an external call (sending ETH) before recording the effect (`bannedBLSPublicKeys[...] = ...`), letting the recipient reenter and observe stale state. Gitaly's pre-receive hook path exhibits the same structural flaw: the "reference counter" that marks a push as in-progress for a repository (`gl_repository`) is the *effect* meant to prevent the repository from being concurrently moved/renamed/deleted while a push is underway, but it is only recorded after two externally-observable interactions (an HTTP round-trip to Rails and execution of arbitrary custom hook scripts) have already executed.

### Finding Description
`GitLabHookManager.preReceiveHook` in `internal/gitaly/hook/prereceive.go` executes, in order:
1. `m.gitlabClient.Allowed(ctx, params)` — an HTTP call out to Rails' `/internal/allowed` endpoint, during which Rails is documented to call back into Gitaly RPCs to inspect the quarantined push objects (see `doc/object_quarantine.md`: "During the POST, the internal GitLab API makes Gitaly calls back into the repo to examine the objects being pushed").
2. Execution of admin-installed custom `pre-receive` hook scripts via `executor(...)`, which are arbitrary external processes that can take an unbounded amount of time and can themselves invoke other Gitaly RPCs.
3. Only after both of the above complete does it call `m.gitlabClient.PreReceive(ctx, repo.GetGlRepository())` (lines 197-198) to increment the reference counter. [1](#0-0) 

According to `doc/hooks.md`, this reference counter's entire purpose is: "The reference is per repository so GitLab knows when a certain repository can be moved. If the reference counter is not at 0, there are active pushes happening." [2](#0-1) 

The documentation itself describes the intended (safe) order as incrementing the counter *first*, then calling `/internal/allowed`: [3](#0-2) 

But the shipped implementation performs it last. This means for the entire duration of the `Allowed` HTTP round-trip (including any Gitaly-side reentrant RPCs Rails issues against the same repository/quarantine) plus the entire duration of arbitrary custom hook execution, the "push in progress" state that other logic and Rails-side repository-move/deletion code depends on is not yet set. Any ordinary user push (reachable simply by an authenticated `git push`, i.e., `PostReceivePack`/`SSHReceivePack`, or any `OperationService` RPC that goes through `UpdaterWithHooks.UpdateReference`, e.g., `UserCommitFiles`, `UserCreateTag`, `UserCherryPick`) drives this code path.

### Impact Explanation
If a repository move, rename, or deletion is gated (on the Rails/GitLab side) by checking this reference counter to decide it is safe to relocate storage, the window between the start of `Allowed`/custom-hook execution and the actual counter increment allows a concurrent operation to conclude "no push is active" and proceed to relocate or delete the repository while a push is mid-flight. Because quarantined objects and the eventual `git-update-ref` transaction depend on the repository remaining in place and the quarantine directory being valid (see `internal/git/quarantine/quarantine.go` `Migrate`), a repository relocation racing with an unrecorded in-flight push can leave the push in an inconsistent state — for example, the quarantine migration or subsequent reference update in `UpdaterWithHooks.UpdateReference` (`internal/gitaly/hook/updateref/update_with_hooks.go`) failing after the repository has moved, or objects/reflog state landing in the wrong location. This is directly analogous to the reported impact class: state meant to gate concurrent repository lifecycle operations is set only after externally-observable interactions, enabling those operations to act on stale/incorrect state and potentially corrupt or strand in-flight repository data. [4](#0-3) 

### Likelihood Explanation
This path executes on every push through Gitaly's primary hook-execution flow and requires no special privilege beyond the ability to push (an ordinary authenticated Git user). The window is proportional to the latency of the Rails `/internal/allowed` HTTP call plus the runtime of any admin-installed custom `pre-receive` hooks, both of which can be made arbitrarily large by a user triggering slow access checks or by hook scripts installed on the instance, widening the race window that any concurrent repository-lifecycle operation could exploit.

### Recommendation
Increment the reference counter (`gitlabClient.PreReceive`) as the very first effect in `preReceiveHook`, immediately after basic request validation, and only decrement it in `PostReceiveHook`/on error — matching the checks-effects-interactions pattern and the behavior already described in `doc/hooks.md`. This ensures the "push in progress" state is durably recorded before any external HTTP call or custom hook execution can be observed or raced by concurrent repository-lifecycle logic.

### Proof of Concept
1. Configure a custom `pre-receive` hook on a test repository that sleeps for several seconds (simulating slow custom hook execution or a slow Rails `/internal/allowed` response).
2. Start a `git push` against the repository; observe via logging/tracing that `m.gitlabClient.PreReceive` (the reference-counter increment) in `internal/gitaly/hook/prereceive.go` is not called until after `Allowed` and the custom hook complete.
3. During that window, issue a concurrent repository move/rename/delete RPC (e.g. via `RepositoryService`) that relies on Rails' view of the reference counter to decide the repository is idle; confirm it proceeds because the counter has not yet been incremented, then confirm the racing push fails or corrupts state when quarantine migration/reference update subsequently executes against the relocated/removed repository path.
