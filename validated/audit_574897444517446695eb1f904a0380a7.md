### Title
Permissionless `lending_pool_emissions_deposit` lets a malicious first depositor inflate `asset_share_value`, enabling a donation-style share-price manipulation attack analogous to the XDEFI `_pointsPerUnit` exploit - ([File: programs/marginfi/src/instructions/marginfi_group/configure_bank.rs])

### Summary
The XDEFI report describes a class of bug where a permissionless "distribute rewards" call recomputes a global per-unit accounting value (`_pointsPerUnit`) as `newAmount * CONSTANT / totalUnits`. Because `totalUnits` can be driven arbitrarily low by a first user locking a dust amount, an attacker can inflate the per-unit value to the point that later users' legitimate operations revert (overflow) or lose funds.

marginfi-v2 has a structurally analogous, permissionless instruction: `lending_pool_emissions_deposit`. It recomputes the bank's `asset_share_value` as `(current_total_assets + attacker_supplied_amount) / total_asset_shares` with essentially no floor on `total_asset_shares`, and no cap on how large `asset_share_value` can become in one call. Since the very first depositor into a bank mints shares 1:1 (as confirmed by test comments/asserts), an attacker can make `total_asset_shares` extremely small and then call this permissionless instruction with a large `amount` to blow up `asset_share_value` by an arbitrary factor, in a single transaction, using only their own funds.

### Finding Description
`lending_pool_emissions_deposit` is explicitly documented as callable by anyone ("Permissionlessly deposit same-mint emissions directly into the bank liquidity vault, increasing depositor value through asset share value"): [1](#0-0) 

The only guard against a degenerate/attacker-controlled denominator is that `total_asset_shares` must be strictly greater than zero — there is no minimum-shares floor (unlike Uniswap V2's `MINIMUM_LIQUIDITY` burn-to-zero-address pattern, which is exactly the fix WatchPug recommended for XDEFI): [2](#0-1) 

The new share value is then derived directly from the attacker-chosen `amount` divided by the (attacker-shrinkable) `total_asset_shares`: [3](#0-2) 

A brand-new bank's first depositor mints shares 1:1 with their deposited amount, so an attacker can trivially make `total_asset_shares` as small as a single native unit: [4](#0-3) 

Once `asset_share_value` is inflated, every downstream calculation that multiplies shares by `asset_share_value` is affected. `get_asset_shares` performs `value / asset_share_value` (floor division for I80F48), so subsequent depositors' legitimate deposits can floor to 0 shares while their tokens are absorbed into the vault increasing the attacker's own share value — a classic donation/inflation attack: [5](#0-4) 

Deposit-limit computation (`get_remaining_deposit_capacity`) also multiplies `total_asset_shares * asset_share_value`, so an inflated share value can push this computation toward overflow, permanently bricking deposits on limited banks: [6](#0-5) 

The project's own fuzz harness independently flags this exact multiplication (`asset_shares * asset_share_value`) as an overflow risk serious enough to `panic!` rather than silently return 0, specifically to avoid feeding a corrupted value into liquidation/bankruptcy logic — confirming this arithmetic path is a recognized fragility point in the codebase: [7](#0-6) 

### Impact Explanation
If exploited, this allows:
1. **Loss of user funds (donation/inflation attack)**: An attacker seeds a fresh bank with a dust deposit, then permissionlessly pumps `asset_share_value` via `lending_pool_emissions_deposit`, causing subsequent legitimate depositors to receive zero (or near-zero) shares for real token transfers into the vault, effectively donating their principal to the attacker's existing share position.
2. **Denial of service / fund freeze**: If `asset_share_value` grows large enough, `shares * asset_share_value` computations used in deposit-limit checks, health checks, and withdrawal/redemption paths can overflow I80F48's bounded range, causing transactions (deposits, withdrawals, liquidations) on that bank to revert or panic — matching the "freeze users' funds" impact described in the XDEFI report.

This maps to the required impact categories: unauthorized state change (share value manipulation) leading to theft of deposited funds and/or permanent lock/freeze of legitimate user operations on the affected bank.

### Likelihood Explanation
The attack requires only: (a) being the first (or an early) depositor of a target bank — trivial for any new bank, permissionless pools, or banks an attacker can front-run at creation — and (b) calling a permissionless instruction (`lending_pool_emissions_deposit`) with attacker-supplied funds. No admin privilege or special access is required, and the instruction's only safety check (`total_asset_shares > 0`) does not meaningfully bound the achievable inflation factor. Likelihood is elevated for any newly-created bank before organic liquidity accumulates.

### Recommendation
- Enforce a minimum `total_asset_shares` floor (analogous to Uniswap V2's `MINIMUM_LIQUIDITY`) before allowing `lending_pool_emissions_deposit`/share-value-affecting operations to proceed, e.g., require `total_asset_shares >= MINIMUM_ASSET_SHARES` rather than merely `> 0`.
- Cap the maximum per-call increase to `asset_share_value` (e.g., a percentage-based cap similar to the `share_value_after <= 0.8` sausage-finger check already used in `super_admin_withdraw`) to prevent single-transaction share-value blowups.
- Alternatively/additionally, seed new banks with a small amount of shares owned by the protocol (burned/unspendable), so `total_asset_shares` can never be attacker-driven to a value low enough to make the multiplier attack profitable.
- Add `checked_mul`/`checked_div` overflow-safe bounds checks specifically around `get_remaining_deposit_capacity` and any other `shares * share_value` computation to fail closed rather than silently or catastrophically.

### Proof of Concept
1. Attacker creates (or is first depositor into) a fresh bank and deposits the smallest possible amount (e.g. 1 native unit), receiving `total_asset_shares = 1` per the 1:1 first-deposit behavior confirmed in `tests/specs/basic/07_deposit.spec.ts:151-153`.
2. Attacker calls the permissionless `lending_pool_emissions_deposit` instruction (`configure_bank.rs:86-156`) with a large `amount` of the same mint funded from their own wallet.
3. `bank.asset_share_value` is recomputed as `(assets_before + amount) / total_asset_shares` (`configure_bank.rs:138-146`), which — with `total_asset_shares = 1` — becomes approximately equal to `amount`, i.e., inflated by whatever factor the attacker can afford.
4. A subsequent legitimate depositor deposits a reasonable amount; `get_asset_shares` (`bank.rs:249-256`) computes `value / asset_share_value`, which floors to 0 shares if `value < asset_share_value`, so the victim's tokens enter the vault while they receive no claim on it.
5. With sufficiently large inflation, any code path multiplying `shares * asset_share_value` (deposit-limit checks in `bank.rs:263`, or the multiplication in `trident-tests/fuzz_0/methods/core.rs:104-107`) can overflow I80F48's range, causing transaction failures/panics on that bank going forward.

```rust
    fn get_remaining_deposit_capacity(&self) -> MarginfiResult<u64> {
        if !self.config.is_deposit_limit_active() {
            return Ok(u64::MAX);
        }

        let current_assets = self.get_asset_amount(self.total_asset_shares.into())?;

        let limit = if self.config.asset_tag == ASSET_TAG_DRIFT {
            scale_drift_deposit_limit(self.config.deposit_limit, self.mint_decimals)?
        } else {
            I80F48::from_num(self.config.deposit_limit)
        };

        if current_assets >= limit {
            return Ok(0);
        }

        let remaining = limit
            .checked_sub(current_assets)
            .ok_or_else(math_error!())?
            .checked_sub(I80F48::ONE) // Subtract 1 to ensure we stay under limit
            .ok_or_else(math_error!())?
            .checked_floor()
            .ok_or_else(math_error!())?
            .checked_to_num::<u64>()
            .ok_or_else(math_error!())?;
```
