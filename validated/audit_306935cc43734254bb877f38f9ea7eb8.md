### Title
StackerDB chunk signatures omit the smart-contract/domain identifier, enabling cross-database replay - (`libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` computes the message a stacker signs to authorize a StackerDB chunk write from only `slot_id`, `slot_version`, and `data_hash` — it never binds the signature to the specific `QualifiedContractIdentifier` (StackerDB instance/"domain") the chunk is destined for. [1](#0-0)  Every write path (`StackerDBTx::try_replace_chunk`, `PeerNetwork::validate_received_chunk`, the unsolicited push handler, and the HTTP POST-chunk RPC) authenticates the chunk purely via `slot_desc.verify(&signer_addr)`/`slot_metadata.verify(&addr)`, which internally re-derives that same domain-less digest. [2](#0-1) [3](#0-2)  This is structurally the same class of bug as the reported EIP-712 issue: a signature that is supposed to be scoped to one "domain" (there: chain ID; here: the target StackerDB contract) is computed without incorporating that domain, so a signature valid in one context is also valid — and replayable — in another.

### Finding Description
A StackerDB chunk write is authorized solely by recovering the signer's public key from `auth_digest = SHA512/256(slot_id || slot_version || data_hash)` and checking that the recovered address matches the slot's configured owner for *that* database. [4](#0-3)  The contract identifier (`smart_contract`/`contract_id`) that scopes which StackerDB the write applies to is passed in as a plain function argument and is never part of the signed material:

- `StackerDBTx::try_replace_chunk(smart_contract, slot_desc, chunk)` looks up `slot_validation` for `smart_contract`, but the signature check `slot_desc.verify(&slot_validation.signer)` only covers `(slot_id, slot_version, data_hash)`. [5](#0-4) 
- `PeerNetwork::validate_received_chunk(smart_contract_id, ...)` (used both for downloaded chunks and for `handle_unsolicited_StackerDBPushChunk`) likewise fetches the expected signer for `smart_contract_id` and calls `slot_metadata.verify(&addr)`, again over the domain-less digest. [6](#0-5) 

Because the digest never commits to the StackerDB's contract identity (nor to a network/consensus identifier), a `StackerDBChunkData` message that is validly signed for one StackerDB replica is *also* a valid signature for any other StackerDB replica in which the same signer address owns the same `slot_id`, provided the replayed `slot_version` is newer than that replica's stored version. StackerDB chunks are gossiped in the clear over the p2p network and served by the `GET /v2/stackerdb/...` RPC endpoints, so any unprivileged peer can observe and re-transmit a legitimately-signed chunk.

This scenario is realistic in this codebase: signer-set StackerDBs are instantiated per reward cycle (`signers-0-<cycle>`/`signers-1-<cycle>`), and slot assignment is derived deterministically from `stackerdb-set-signer-slots`, sorted by `signing_key`, over the reward-cycle's signer set. [7](#0-6)  When the signer set is unchanged (or only partially changed) between consecutive cycles — a common real-world condition — the same signer address is assigned the same `slot_id` in multiple, distinct StackerDB contracts. An attacker can then take a chunk legitimately signed for cycle N's contract and replay it into cycle N+1's (or any other same-slot-owner) contract instance, causing that node to accept and store data the signer never authorized for that specific destination.

### Impact Explanation
This breaks the intended equality "signature authenticates (signer, *this* StackerDB slot)" into "signature authenticates (signer, this slot_id/version/hash, in any StackerDB where the same signer owns that slot_id)". The result is an unauthenticated/unauthorized write of attacker-replayed data into a StackerDB instance the original signer did not intend to write to, and that data can subsequently be gossiped network-wide to other replicas via the normal StackerDB sync/broadcast logic (`handle_unsolicited_StackerDBPushChunk` forwards accepted/bufferable chunks to the relayer). [8](#0-7)  Since signer StackerDBs carry consensus-relevant signer messages, cross-cycle/cross-context replay of stale-but-validly-signed content can pollute a node's view of current signer state for the wrong reward cycle/context — matching the Critical/High categories of "unauthenticated/unauthorized write to StackerDB" and "network-wide propagation of forged data."

### Likelihood Explanation
Exploitability requires no privileges beyond normal network access: StackerDB chunks are broadcast unencrypted and are also readable via public RPC (`GET /v2/stackerdb/{contract}/chunk/{slot}`), so an attacker only needs to capture one validly-signed chunk and replay it into a different, structurally-similar StackerDB where the same signer owns the same slot and the target slot's stored version is behind the replayed one. Given that signer sets frequently persist with high overlap across consecutive reward cycles, the "same signer owns same slot_id in a different contract" precondition is not rare.

### Recommendation
Bind the signed digest to the StackerDB's domain: include the `QualifiedContractIdentifier` of the target StackerDB (and ideally a network/consensus identifier, e.g. `rc_consensus_hash` or mainnet/testnet chain id) inside `SlotMetadata::auth_digest()`, analogous to including `chainId`/`verifyingContract` in an EIP-712 domain separator. This ensures a signature over `(contract_id, slot_id, slot_version, data_hash[, network_id])` cannot be replayed into any other StackerDB context.

### Proof of Concept
1. Node/operator A signs and pushes `StackerDBChunkData { slot_id: 3, slot_version: 5, data }` for contract `signers-0-15`, where signer key `K` owns slot 3 there. `auth_digest` = `H(3 || 5 || hash(data))`, signed by `K`.
2. Attacker observes this chunk (via p2p gossip or `GET /v2/stackerdb/...`).
3. In `signers-0-16` (or `signers-1-15`, or any other configured StackerDB), signer key `K` also owns slot 3 (common when the signer set is stable across cycles), and its stored version for slot 3 is `< 5`.
4. Attacker submits the *same* `StackerDBChunkData` (unchanged `sig`, `slot_id`, `slot_version`, `data`) to that other contract's StackerDB endpoint (`POST /v2/stackerdb/{other_contract}/chunks` or via an unsolicited P2P push referencing `other_contract`'s `contract_id`).
5. `validate_received_chunk`/`try_replace_chunk` recompute the same domain-less digest, recover `K`, confirm `K` owns slot 3 in the *other* contract, and accept the write — even though `K` never signed anything for that contract. [2](#0-1)

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Sign this slot metadata, committing to slot_id, slot_version, and
    /// data_hash.  Sets self.signature to the signature.
    /// Fails if the underlying crypto library fails
    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
