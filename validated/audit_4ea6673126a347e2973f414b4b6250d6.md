I have sufficient evidence to identify the strongest analog: the Gitaly partition-wide WAL apply loop, which serializes all repositories sharing a partition (object pool + all its fork members) behind a single sequential log-application goroutine, where a failure applying any single log entry halts the entire partition for every member repository.

### Title
Single repository's failed WAL log-entry application permanently halts all fork/pool members sharing the same partition - ([File: internal/gitaly/storage/storagemgr/partition/transaction_manager.go])

### Summary
Gitaly groups an object pool and every repository connected (or about-to-be-connected) to it into a single storage "partition," which is served by exactly one `TransactionManager` goroutine that applies the write-ahead log (WAL) sequentially. `TransactionManager.run` calls `applyLogEntry` for each pending LSN in order; if applying any single log entry returns an error, `run` returns and the whole partition's `TransactionManager.Run()` goroutine terminates, causing `storage.ErrTransactionProcessingStopped` to be returned to every in-flight and future transaction targeting the partition, not just the repository whose entry failed to apply.

### Finding Description
Object pools and every repository linked (or being linked, e.g. new forks) to them are deliberately co-located in one partition to preserve ordering guarantees between pool and fork writes, as documented in [1](#0-0) . That partition is driven by a single `TransactionManager` instance per [2](#0-1) , whose `run` loop applies queued log entries one at a time and aborts entirely on the first `applyLogEntry` error: `if err := mgr.applyLogEntry(ctx, lsn); err != nil { return fmt.Errorf("apply log entry: %w", err) }` [3](#0-2) .

`applyLogEntry` itself can fail for a variety of repository-specific reasons — e.g. `applyOperations` failing to perform a hard link/rename/remove for one member's manifest, or `storeAppliedLSN` failing — and any such failure propagates straight out of `run`, tearing down the manager for the *whole partition*: `if err := applyOperations(...); err != nil { return fmt.Errorf("apply operations: %w", err) } ... if err := mgr.storeAppliedLSN(lsn); err != nil { return fmt.Errorf("set applied LSN: %w", err) }` [4](#0-3) .

`StorageManager.startPartition` observes the goroutine returning an error, logs "partition failed," tears down the `Partition` handle, and only creates a fresh `TransactionManager` instance lazily the next time some repository in that partition is accessed [5](#0-4) . Crucially, on restart the manager resumes from `appliedLSN`, so it will retry applying the very same failing log entry at the front of the queue (`for { if mgr.appliedLSN < mgr.logManager.AppendedLSN() { ... mgr.applyLogEntry ...} }`), and will fail again identically — this is corroborated by the recovery-replay tooling, which explicitly documents that once a log entry cannot be applied "that partition is always in a broken state ... the partition is broken completely" [6](#0-5) .

This means: a fork/pool member whose committed WAL entry cannot be applied (e.g. due to a transient filesystem error, a manifest referencing a file that failed to sync, disk pressure, or any bug triggering `applyOperations` failure for that one repository) will not just corrupt that repository — it stalls log application for the entire partition, which by design also contains the shared object pool and every other fork connected to it. All of those other, otherwise-healthy repositories become unable to begin or commit any WAL transaction (`ErrTransactionProcessingStopped`) until the specific faulty entry is fixed or worked around, exactly mirroring the reported bug class where a single member's failure ("paused market") bricked a shared resource ("KeeperOracle") used by unrelated members.

### Impact Explanation
Because object pools intentionally place many independent fork repositories into the same partition to preserve consistency ordering [1](#0-0) , a single problematic commit against any one fork (or the pool itself) can deny service (reads and writes via transactions) to every other fork sharing that pool. This is a partition-wide denial of service reachable from an ordinary user's push/fetch workflow that creates forks and triggers `FetchIntoObjectPool`/`LinkRepositoryToObjectPool` housekeeping, without requiring any privileged actor.

### Likelihood Explanation
Triggering `applyLogEntry` failure requires an underlying fault (I/O error, corrupted manifest state, a bug in one of the housekeeping/reference-update code paths for one specific repository), so it is not trivially triggerable by a single crafted RPC field alone, but any repository-specific bug or transient storage fault occurring during WAL application is sufficient, and there's no isolation preventing that fault from blocking co-located repositories that have nothing to do with the fault.

### Recommendation
Consider isolating failures at the granularity of the failing log entry/repository rather than aborting the whole partition's transaction manager: e.g., surface the failure to only the transaction(s) whose repository is implicated, quarantine or skip clearly-corrupt entries with an explicit operator-controlled recovery path, or shard partitions more finely so a pool's fork count doesn't unnecessarily couple unrelated forks into a single point of failure. At minimum, ensure `run`'s retry-on-restart behavior does not deterministically re-fail the same entry forever without an alerting/backoff/skip mechanism distinguishing transient vs. permanent failures, similar to the recommendation in the referenced report to avoid a single member's failure bricking the shared resource for all others.

### Proof of Concept
1. Set up an object pool with two independent fork members `member-A` and `member-B`, all assigned to the same partition per the pool-colocation rule [1](#0-0) .
2. Commit a transaction for `member-A` whose WAL manifest cannot be applied on disk (this is directly demonstrated by the test harness's `BeforeApplyLogEntry`/`BeforeStoreAppliedLSN` crash-simulation hooks used throughout `transaction_manager_*_test.go`, e.g. [7](#0-6) , or in production by an I/O failure inside `applyOperations`).
3. Observe `TransactionManager.run` returns an error from `applyLogEntry`, `Run()` exits, and `StorageManager.startPartition`'s goroutine logs "partition failed" and tears down the manager [5](#0-4) .
4. Attempt any transaction (read or write) for `member-B`, the unrelated pool member — it fails with `storage.ErrTransactionProcessingStopped` even though `member-B` is unaffected by the original fault, because a fresh `TransactionManager` for the partition will immediately retry and re-fail applying the same stuck LSN for `member-A` before any other repository in the partition can proceed, consistent with the recovery tooling's documented behavior that the partition becomes "broken completely" [6](#0-5) .

Gitaly automatically assigns repositories to partitions when they are first accessed:

- Object pools and all repositories connected to the object pool are placed in the same partition. Repositories that are about to be connected to an object pool, such as newly created forks, are also placed in the same partition with the object pool they are about to be connected.

- Repositories that are not connected (nor about to be connected) to an object pool are placed in their own partitions.
