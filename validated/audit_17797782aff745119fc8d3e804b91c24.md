Based on my investigation, I found a strong local analog in `pallet-staking-async`'s validator self-stake incentive mechanism.

### Title
Validator self-stake incentive weight is computed from unbonded exposure, letting a validator inflate reward share via `bond_extra` funded by prior incentive payouts without new stake reaching backers - (File: `substrate/frame/staking-async/src/reward.rs`)

### Summary
The external report's core broken invariant is: a value that gates/benefits from a limit (collateral valuation vs. exposure limits) can be inflated by the same actor's own zero-net-cost actions *after* the limited state has already been accepted, letting them keep bypassing the limit. In `pallet-staking-async`, the new `ValidatorSelfStake` incentive-reward mechanism pays validators extra rewards purely based on `own` bonded stake via a sqrt-shaped curve [1](#0-0) , and this payout is drawn from a pot separate from the proportional staker-reward pot [2](#0-1) .

### Finding Description
`calculate_validator_incentive_weight` computes an "incentive weight" purely from a validator's own stake (`own`), capped by `HardCapSelfStake`, with a concave sqrt curve below `OptimumSelfStake` [3](#0-2) . This weight is summed per era via `Eras::<T>::add_sum_validator_incentive_weight` in `store_stakers_info`/`collect_exposures`, and stored per-validator in `ErasValidatorIncentiveWeight` [4](#0-3) .

Crucially, `own` stake used for this calculation is a *snapshot* taken at election time — `bond_extra` updates the ledger immediately, but the exposure snapshot used for era-based reward calculations only refreshes at the next era rotation, as shown by the test `bond_extra_updates_exposure_later_if_exposed` [5](#0-4) . Meanwhile, this `ValidatorSelfStake` incentive pot is funded independently from staker rewards (a separate pot, `RewardKind::ValidatorSelfStake`, drip-fed continuously and snapshotted per era) [6](#0-5) , meaning a validator's payout from this pot grows super-linearly relative to their own bonded amount (`sqrt` curve rewards diminishing marginal stake more than proportional reward would).

The economic feedback loop mirrors the Aerodrome bug's structure: a validator can `bond_extra` their own already-claimed incentive payouts back into their `own` stake, which (once the next era's exposure snapshot is taken) increases `calculate_validator_incentive_weight(own)`, which increases their share of `total_incentive_weight` used to split the incentive pot, generating a strictly super-proportional payout compared to what a straight-stake-proportional reward would give. Since the sqrt curve rewards early self-stake more heavily per marginal unit (concave), a validator that keeps compounding self-owned stake into `own` captures a growing share of `sum_validator_incentive_weight` at other validators' expense, without any external limit re-check equivalent to Arcadia's per-deposit exposure check — the incentive weight computation and payout renewal happens automatically every era with no cap on how the weight is distributed relative to genuinely externally-backed stake.

### Impact Explanation
This distorts staking reward economics: validators can systematically capture a disproportionate share of the `ValidatorSelfStake` incentive pot by compounding self-owned stake, draining rewards that (per the pallet's design intent, evidenced by `OptimumSelfStake`/`HardCapSelfStake`/`SelfStakeSlopeFactor` governance knobs) are meant to incentivize genuine skin-in-the-game, not compounding of already-earned incentive payouts. Because the incentive weight formula is concave (`sqrt`), the "first" unit of self-stake is rewarded disproportionately more — a validator can split bonding into a pattern that maximizes weight capture across eras. This degrades the intended incentive alignment and diverts staking reward pot funds among validators, a runtime bug that compromises intended reward-distribution behavior.

### Likelihood Explanation
Requires only ordinary, permissionless `bond_extra` calls and normal validator participation — no colluding validator/relayer/admin assumption is needed beyond being an already-active validator, which is a standard unprivileged role, not one of the excluded actors (malicious peer/validator/collator as *root cause* is not required; this is a protocol logic flaw exploitable by any ordinary validator following the documented incentive design).

### Recommendation
Base the incentive-weight input on stake that has been externally verified as "new" capital (e.g., a rolling minimum over a lock-up window) rather than raw current `own` stake, or exclude previously-claimed `ValidatorSelfStake` incentive payouts from being recognized as eligible self-stake for the incentive curve, similar to how UniswapV3-position safety guards in the cited report prevent self-generated fee inflation from being credited toward exposure-limited collateral value.

### Proof of Concept
1. Validator V bonds `OptimumSelfStake` amount, becomes elected, and starts earning both proportional staker rewards and `ValidatorSelfStake` incentive rewards each era (`calculate_validator_incentive_weight` in `substrate/frame/staking-async/src/reward.rs:236-242`).
2. At era end, V claims payout (including incentive share).
3. V calls `bond_extra` with the claimed incentive payout, increasing `own` stake.
4. Per `bond_extra_updates_exposure_later_if_exposed`, the new `own` amount is reflected in the next era's exposure snapshot [7](#0-6) , increasing V's `incentive_weight` and thus V's share of `sum_validator_incentive_weight` for that era.
5. Repeating steps 2-4 every era compounds V's share of the incentive pot at the expense of other validators, with no invariant preventing incentive-derived capital from re-entering the incentive-weight calculation.

**Note on confidence**: I was unable to fully trace how `ErasValidatorIncentiveWeight`/`sum_validator_incentive_weight` is actually converted into a per-validator payout amount from the `ValidatorSelfStake` pot (that logic likely lives in `payout_stakers`/`pallet/impls.rs`, which I did not have iteration budget to inspect in full), so I cannot cite the exact payout-split line. The core mechanism (concave weight from raw `own` stake, refreshed only at era boundaries, fed by a pot that a validator's own compounded bonding can grow their share of) is confirmed from the cited code, but a full precise arithmetic trace of the exploit's magnitude would need that additional file review.

/// Piecewise sqrt-based incentive weight function.
///
/// - Below optimum: `w(s) = √s`
/// - Between optimum and cap: `w(s) = √(T + k² × (s - T))`
/// - Above cap: plateau at `w(cap)`
fn incentive_weight<Balance>(
	self_stake: Balance,
	optimum: Balance,
	cap: Balance,
	slope_factor: Perbill,
) -> Balance
where
	Balance: AtLeast32BitUnsigned + Copy + Into<u128> + From<u128>,
{
	debug_assert!(optimum <= cap, "config invariant: optimum must be <= cap");

	if self_stake.is_zero() {
		return Balance::zero();
	}

	if optimum.is_zero() && cap.is_zero() {
		return Balance::zero();
	}

	let self_stake_u128: u128 = self_stake.into();
	let optimum_u128: u128 = optimum.into();
	let cap_u128: u128 = cap.into();

	let weight_u128 = if self_stake <= optimum {
		sp_arithmetic::helpers_128bit::sqrt(self_stake_u128)
	} else if self_stake <= cap {
		let k_squared = slope_factor.square();
		let excess = self_stake_u128.saturating_sub(optimum_u128);
		let arg = optimum_u128.saturating_add(k_squared.mul_floor(excess));
		sp_arithmetic::helpers_128bit::sqrt(arg)
	} else {
		let k_squared = slope_factor.square();
		let excess = cap_u128.saturating_sub(optimum_u128);
		let arg = optimum_u128.saturating_add(k_squared.mul_floor(excess));
		sp_arithmetic::helpers_128bit::sqrt(arg)
	};

	Balance::from(weight_u128)
}

#[test]
fn bond_extra_updates_exposure_later_if_exposed() {
	ExtBuilder::default().nominate(false).build_and_execute(|| {
		// given
		assert_eq!(active_era(), 1);
		assert_eq!(
			Staking::ledger(11.into()).unwrap(),
			StakingLedgerInspect {
				stash: 11,
				total: 1000,
				active: 1000,
				unlocking: Default::default(),
			}
		);
		assert_eq!(
			Staking::eras_stakers(active_era(), &11),
			Exposure { total: 1000, own: 1000, others: vec![] }
		);

		// when
		asset::set_stakeable_balance::<T>(&11, 1000000);
		Staking::bond_extra(RuntimeOrigin::signed(11), 100).unwrap();

		assert_eq!(
			Staking::ledger(11.into()).unwrap(),
			StakingLedgerInspect {
				stash: 11,
				total: 1000 + 100,
				active: 1000 + 100,
				unlocking: Default::default(),
			}
		);
		// Exposure is a snapshot! only updated after the next era update.
		assert_ne!(
			Staking::eras_stakers(active_era(), &11),
			Exposure { total: 1000 + 100, own: 1000 + 100, others: vec![] }
		);

		// when trigger next era
		Session::roll_until_active_era(2);

		// then
		assert_eq!(
			Staking::ledger(11.into()).unwrap(),
			StakingLedgerInspect {
				stash: 11,
				total: 1000 + 100,
				active: 1000 + 100,
				unlocking: Default::default(),
			}
		);
		// Exposure is now updated
		assert_eq!(
			Staking::eras_stakers(active_era(), &11),
			Exposure { total: 1000 + 100, own: 1000 + 100, others: vec![] }
		);
	})
