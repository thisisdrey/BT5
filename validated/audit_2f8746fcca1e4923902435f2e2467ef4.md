### Title
Active-permission operations bitmask can be granted the `AccountPermissionUpdateContract` bit, letting a delegated key rewrite Owner/Witness permissions and take over the account - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
The reported ENS bug is a case of over-extended approval: giving approval scoped to one purpose (managing wrapped domains) is silently interpreted by the code as authorization for a much broader action (wrapping/controlling any unwrapped domain), because the permission check doesn't restrict the scope of what the approval actually implies. java-tron's multi-sig `Active` permission model exhibits the same class of issue: an account's `Active` permission is granted with an arbitrary 256-bit `operations` bitmap that can include *any* contract type the network supports — including `AccountPermissionUpdateContract` itself, the contract that rewrites the account's `Owner`, `Witness`, and `Active` permissions. There is no special-case restriction preventing a non-`Owner` (`permissionId != 0`) key from using this bit to gain full control of the account.

### Finding Description
`AccountPermissionUpdateActuator.checkPermission()` validates an `Active` permission's `operations` field only by checking that every set bit corresponds to a valid `ContractType` known to the network (via `dynamicStore.getAvailableContractType()`), with no exclusion for `AccountPermissionUpdateContract`: [1](#0-0) 

At signature/authorization time, `TransactionCapsule.checkPermission()`/`validateSignature()` only verifies that (a) the signer's `permissionId` maps to an `Active` permission, and (b) the target contract's type-bit is set in that permission's `operations` bitmap — via `WalletUtil.checkPermissionOperations()`: [2](#0-1) [3](#0-2) [4](#0-3) 

There is no special-case logic anywhere in this path that says "the `AccountPermissionUpdateContract` type may only be authorized by the `Owner` permission (`permissionId == 0`)." Once an `Active` key's operations bitmap contains that bit, `AccountPermissionUpdateActuator.execute()` will happily replace the account's entire `Owner`, `Witness`, and `Active` permission set with attacker-controlled keys: [5](#0-4) 

This is structurally identical to the ENS `wrapETH2LD` issue: a permission check that treats "approved for operation X" as sufficient authorization for an action whose real-world effect (here, total account takeover) is far broader than the scope the granter likely intended when configuring that specific `Active` key (e.g., for routine resource delegation or transfers).

### Impact Explanation
If any `Active` permission on an account is configured (by the account owner, a business partner, an exchange's hot-wallet co-signer setup, or a smart-contract-based multisig integration) with the `AccountPermissionUpdateContract` bit set — even if it was intended to also cover routine operations like `TransferContract`, `DelegateResourceContract`, etc. — a holder of that `Active` key (once its threshold is met, which can be a single key if the permission's threshold equals a single key's weight) can submit an `AccountPermissionUpdateContract` transaction and overwrite the `Owner` permission entirely, evicting the legitimate owner's keys and asserting exclusive future control. This is a concrete unauthorized-account-takeover / permanent-freezing-of-funds primitive: the true owner loses all ability to move funds, vote, withdraw rewards, or otherwise interact with the account, and the attacker (now sole "owner") can drain balances via subsequent `TransferContract`/`WithdrawBalanceContract` transactions.

### Likelihood Explanation
Exploitation requires that some `Active` permission on the target account has the `AccountPermissionUpdateContract` operation bit enabled. This is plausible in real usage: multisig/custody setups often grant broad operation bitmaps to delegate keys for convenience (e.g., a co-signer service, exchange hot-wallet infra, or a smart contract acting as a delegated signer) without realizing that this specific bit grants full re-keying power — exactly the "user unaware of the implications of a broad approval" scenario the ENS judge described when downgrading severity to Medium. I was not able to fully confirm from the available index whether `AccountCapsule.createDefaultActivePermission(...)` (used as an implicit default `Active` permission, id 2) includes this bit by default; that would raise likelihood further if true, but I could not verify it within the tool budget available and note this as an open question requiring direct inspection of `chainbase/src/main/java/org/tron/core/capsule/AccountCapsule.java`.

### Recommendation
Explicitly forbid the `AccountPermissionUpdateContract` type bit from being set in any `Active` permission's `operations` bitmap (reject it in `AccountPermissionUpdateActuator.checkPermission()`), and/or hard-code in `TransactionCapsule.checkPermission()` / `WalletUtil.checkPermissionOperations()` that `AccountPermissionUpdateContract` may only be authorized via `permissionId == 0` (the `Owner` permission), regardless of any bit set in an `Active` permission's operations.

### Proof of Concept
1. Account owner O creates an `Active` permission P (id 2) with a delegate key K, intending K to only sign `DelegateResourceContract`/`TransferContract` transactions, but sets a broad `operations` bitmap that also happens to include the bit for `AccountPermissionUpdateContract` (this bit passes validation in `AccountPermissionUpdateActuator.checkPermission()` since it is simply "a valid ContractType").
2. K crafts and signs an `AccountPermissionUpdateContract` transaction with `permissionId = 2` (P), setting `Owner` permission keys to addresses K controls.
3. `TransactionCapsule.validateSignature()` accepts the transaction because `checkPermissionOperations()` finds the `AccountPermissionUpdateContract` bit set in P's operations.
4. `AccountPermissionUpdateActuator.execute()` overwrites O's `Owner`/`Active` permissions, permanently locking O out and giving K sole control of the account and its funds. [6](#0-5)

  public static boolean checkPermissionOperations(Permission permission, Contract contract)
      throws PermissionException {
    ByteString operations = permission.getOperations();
    if (operations.size() != 32) {
      throw new PermissionException(String.format("operations size must 32, actual: %d",
          operations.size()));
    }
    int contractType = contract.getTypeValue();
    boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
    return b;
  }

  public static boolean validateSignature(Transaction transaction,
      byte[] hash, AccountStore accountStore, DynamicPropertiesStore dynamicPropertiesStore)
      throws PermissionException, SignatureException, SignatureFormatException {
    Transaction.Contract contract = transaction.getRawData().getContractList().get(0);
    int permissionId = contract.getPermissionId();
    byte[] owner = getOwner(contract);
    AccountCapsule account = accountStore.get(owner);
    Permission permission = null;
    if (account == null) {
      if (permissionId == 0) {
        permission = AccountCapsule.getDefaultPermission(ByteString.copyFrom(owner));
      }
      if (permissionId == 2) {
        permission = AccountCapsule
            .createDefaultActivePermission(ByteString.copyFrom(owner), dynamicPropertiesStore);
      }
    } else {
      permission = account.getPermissionById(permissionId);
    }
    if (permission == null) {
      throw new PermissionException("permission isn't exit");
    }
    checkPermission(permissionId, permission, contract);
    long weight = checkWeight(permission, transaction.getSignatureList(), hash, null);
    if (weight >= permission.getThreshold()) {
      return true;
    }
    return false;
  }
