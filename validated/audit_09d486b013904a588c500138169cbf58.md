### Title
Unbounded attacker-controlled array-length field in TVM precompile input parsing causes uncaught `OutOfMemoryError`/`ArrayIndexOutOfBoundsException` (DoS) - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The CVE describes a crash caused by trusting an attacker-controlled length/size field from a crafted file (`useratoms.c`) without bounds validation before allocating/copying a buffer. The same bug class exists in java-tron's ABI-array parsing helpers used by the `ValidateMultiSign` precompiled contract, which is directly reachable from any TVM contract call (`STATICCALL`/`CALL` to the precompile address) issued by an unprivileged transaction sender.

### Finding Description
`extractBytesArray` and `extractSigArray` read an attacker-supplied 32-byte word as an array length and immediately allocate an array of that size before any sanity check against a maximum, and only bound-check the *offset*, not the derived length: [1](#0-0) [2](#0-1) 

`ValidateMultiSign.execute` calls these helpers. The `MAX_SIZE` (5) bound is only enforced *before* the call when `VMConfig.allowTvmSelfdestructRestriction()` is enabled, and even then only guards the `extractSigArray` branch; when that hard-fork flag is disabled, `extractBytesArray` is invoked with a completely attacker-controlled `len` derived from `words[offset].intValueSafe()`, and this call sits **outside** the surrounding `try { ... } catch (Throwable t)` block that wraps the rest of the method: [3](#0-2) 

`intValueSafe()` lets an attacker craft a length up to `Integer.MAX_VALUE`: [4](#0-3) 

`new byte[len][]` with `len` near `Integer.MAX_VALUE` triggers an immediate `OutOfMemoryError` (an `Error`, not an `Exception`), which is not caught by the method's `catch (Throwable t)` because that catch block only wraps the account/permission logic that follows the array-extraction call, not the extraction call itself.

### Impact Explanation
An `OutOfMemoryError` thrown mid-transaction-execution during block application is an `Error`, and many upstream call sites (transaction trace execution, `Manager` block application) are structured to catch `Exception`/specific checked exceptions rather than `Throwable`/`Error`. If uncaught, this can terminate the block-processing thread or destabilize the JVM heap for the whole node process, i.e., a remote, unauthenticated-by-privilege denial-of-service against any node that executes the crafted transaction — directly analogous to the "crafted file causes crash" impact of CVE-2017-9127.

### Likelihood Explanation
Reaching `ValidateMultiSign` only requires deploying/calling a contract that issues a `CALL`/`STATICCALL` to the precompile address with crafted calldata — no special privilege, signature authority, or SR/witness status is needed, matching the "unprivileged contract deployer/caller" reachability requirement. The only precondition is that `allowTvmSelfdestructRestriction()` is not active for the `extractBytesArray` path (or, even when active, the `words[3].intValueSafe()/WORD_SIZE` index used at line 1067 can itself be crafted to index out of `words[]`, causing an uncaught `ArrayIndexOutOfBoundsException` before the try block, for a lower-severity but still-uncaught failure).

### Recommendation
- In `extractBytesArray`/`extractSigArray`/`extractBytes32Array`, validate `len` against `MAX_SIZE` (or a sane upper bound derived from `words.length`) before allocating the array, not after.
- Move the array-extraction calls inside the existing `try { ... } catch (Throwable t)` block in `ValidateMultiSign.execute`, or wrap them independently, so any parsing failure (including `Error` subclasses from malicious length fields) safely reverts the call instead of propagating.

### Proof of Concept
1. Deploy a contract that performs a `STATICCALL` to the `ValidateMultiSign` precompiled contract address with input where `words[3]` points to an offset whose word value (`len`) is set to a very large 32-byte integer (e.g., `0x7fffffff`).
2. On nodes where `allowTvmSelfdestructRestriction()` is not enabled, `extractBytesArray` executes `new byte[len][]` with `len ≈ Integer.MAX_VALUE`, triggering an uncaught `OutOfMemoryError` outside the method's `catch (Throwable t)` guard.
3. Observe abnormal termination/instability of the transaction-processing thread on the executing node.

Note: I could not fully trace every upstream exception handler (e.g., inside `TransactionTrace`/`Runtime`/`Manager`) within the available index to confirm with certainty whether some outer layer ultimately catches `Throwable`/`Error` for all TVM execution paths; a Devin session with full repo access would be needed to verify the complete call chain and confirm whether `OutOfMemoryError` truly escapes uncaught to the point of node instability.
