### Title
Hardcoded Pyth/DIA oracle contract addresses in `market.clar` price resolution have no update path if the upstream oracle contract is migrated - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`v0-4-market.clar` resolves all collateral/debt prices by calling fully-qualified, literal principal addresses for the Pyth storage contract and the DIA oracle contract, embedded directly inside `contract-call?` expressions rather than through an upgradeable reference. This mirrors the reported Aave "hardcoded pool address" bug class: an external DeFi infrastructure address that its own operator can and does migrate is baked into the consuming contract with no mechanism to redirect calls, so if the upstream address changes, price resolution — and therefore every operation that depends on it — breaks.

### Finding Description
In `v0-4-market.clar`, the two oracle price sources are called through hardcoded literal principals: [1](#0-0) [2](#0-1) 

```clarity
(define-private (call-pyth (ident (buff 32)))
  (let ((res (unwrap! (contract-call? 'SP1CGXWEAMG6P6FT04W66NVGJ7PQWMDAC19R7PJ0Y.pyth-storage-v4 get-price ident) ERR-ORACLE-PYTH)))
    (ok res)))
...
(define-private (call-dia (key (string-ascii 32)))
  (let ((res (unwrap! (contract-call? 'SP1G48FZ4Y7JY8G2Z0N51QTCYGBQ6F4J43J77BQC0.dia-oracle get-value key) ERR-ORACLE-DIA)))
    (ok res)))
```

These functions are invoked from `resolve-price-feed`, which is the entry point for all price resolution in the market: [3](#0-2) 

Notably, Pyth's own infrastructure is designed with an explicit, upgradeable "execution plan" that lets the storage/decoder/oracle contract addresses be migrated via governance (`pyth-governance-v3.clar`'s `current-execution-plan` var, updatable through `update-pyth-storage-contract`, etc.), which is exactly the scenario the external report warns about — the canonical Pyth storage contract address is not meant to be treated as permanent. Zest's `v0-4-market.clar`, however, references a single specific `pyth-storage-v4` deployment as a Clarity literal principal with no `data-var`, no indirection through a registry, and no update function. If Pyth (or DIA) redeploys/migrates their storage/oracle contract — as Pyth has already done multiple times (v1 → v2 → v3 → v4, visible in the naming convention itself) — `call-pyth`/`call-dia` will call a stale, possibly decommissioned contract. Since these addresses are compiled directly into `contract-call?` statements rather than stored state, there is no way to redirect them without shipping and migrating to an entirely new market contract, which is the same structural flaw as `OrigamiAaveV3FlashLoanProvider.POOL` being immutable.

### Impact Explanation
Price resolution via `call-pyth`/`call-dia` is required for essentially every value-bearing operation in the market: borrow, withdraw, health checks, and liquidation all resolve collateral/debt notional values through `price-resolve` → `resolve-price-feed`. If the referenced Pyth/DIA contract address becomes stale (deprecated, paused, or replaced), `contract-call?` to that address will error out (`ERR-ORACLE-PYTH`/`ERR-ORACLE-DIA`), causing `price-resolve` to fail for any asset using that feed. This freezes all borrow, withdraw, and liquidation operations relying on that asset's price — funds already deposited become unwithdrawable and positions become unliquidatable until the market contract itself is redeployed and all state/positions migrated. This lands squarely on the in-scope "temporary freezing of funds" impact class.

### Likelihood Explanation
This does not require any attacker action, DAO compromise, or malicious behavior — it is triggered purely by the normal, expected lifecycle of the upstream oracle provider redeploying its storage/oracle contract, which Pyth's own governance module is explicitly built to support and has exercised historically (version-numbered contract names `pyth-storage-v1/v2/v3/v4`). The likelihood of Pyth or DIA migrating their contract address again over the protocol's lifetime is non-trivial, and Zest has no mitigation for that event beyond a full contract redeploy.

### Recommendation
Do not hardcode the Pyth/DIA contract principals as literals inside `contract-call?`. Instead:
- Store the Pyth storage contract principal and DIA oracle principal in `data-var`s that can be updated by DAO-authorized governance calls, or
- Route calls through Pyth's own `pyth-oracle-v4`/execution-plan proxy contract (which already tracks the live storage contract) rather than calling `pyth-storage-v4` directly, so address migrations on Pyth's side are transparently absorbed.

### Proof of Concept
1. Pyth (or DIA) deprecates the currently-referenced storage/oracle contract and migrates state to a new contract address (as has happened across `pyth-storage-v1` → `v4`), leaving the old contract non-functional or removed.
2. Any user calls a market function (e.g., `borrow`, `withdraw`, `liquidate`) that requires price resolution for an asset using the Pyth or DIA feed.
3. `call-pyth`/`call-dia` in `v0-4-market.clar` still targets the old, now-stale hardcoded principal; the `contract-call?` fails, `resolve-price-feed` returns `ERR-ORACLE-PYTH`/`ERR-ORACLE-DIA`, and the entire transaction reverts.
4. Every subsequent user of the affected market path is now blocked from borrowing, withdrawing collateral, or being properly liquidated involving that asset, until a new market contract is deployed and positions migrated — a temporary freeze of funds with no on-chain remediation path in the current contract.
