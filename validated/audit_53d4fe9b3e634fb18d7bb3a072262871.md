## Title
Heap out-of-bounds read via unchecked Zip64 extra-field attribute index in `CDH::local_header_offset()`/`compressed_file_size()` when parsing attacker-supplied JARs - (File: `src/tools/singlejar/zip_headers.h`)

### Summary
`singlejar` (the `_deploy.jar` builder used by `java_binary`/`java_import` and invoked whenever Bazel merges JARs, including ones fetched from attacker-controlled URLs via `http_jar`/`http_archive`/Maven coordinates) memory-maps and parses Central Directory Headers (CDH) from input JARs. When a 32-bit size/offset field in a CDH equals `0xFFFFFFFF`, the code looks up the corresponding 64-bit value in the entry's Zip64 extra field by computing a dynamic array index from *other* sentinel flags, and passes that index straight into `Zip64ExtraField::attr64()` without ever checking that the extra field's declared `payload_size()`/`attr_count()` actually contains that many 8-byte slots.

### Finding Description
`Zip64ExtraField::attr64(int index)` blindly dereferences `attr_[index]`: [1](#0-0) 

The callers compute `index` from *unrelated* sentinel checks instead of validating it against the actual number of attributes present in the field: [2](#0-1) [3](#0-2) 

This is structurally the same bug class as the Unbound CVE: the parser computes the location of an "optional" sub-field (here, the Nth 8-byte attribute inside the Zip64 extra field) based on flags in a *different* part of the record (whether `compressed_file_size32`/`uncompressed_file_size32` also need Zip64 extension), then reads from that computed location without confirming the sub-field is actually present in the record's declared length — exactly like `dname_valid()`'s address being computed and handed to `query_dname_tolower()` without checking a second name exists in the RDATA.

Only `ExtraField::find()` bounds-checks that the *entire* extra field (header + `payload_size()`) fits within `[start, end)` of the CDH's extra-fields region: [4](#0-3) 
It does **not** check that `payload_size()` is large enough to hold the specific attribute index a caller intends to use. A malicious JAR can declare `local_header_offset32 == 0xFFFFFFFF` (forcing 64-bit lookup) while also setting `compressed_file_size32`/`uncompressed_file_size32` to `0xFFFFFFFF`, causing `attr_no` to become 2, while shipping a Zip64 extra field whose `payload_size` is small (e.g., only 0 or 8 bytes, i.e., `attr_count() < 3`). `z64->attr64(2)` then reads 8 bytes at `attr_[2]`, past the end of the declared payload. Because the CDH is only bounds-checked against the truncated declared `extra_fields_length()`/`size()` in `InputJar::NextEntry`, not against per-attribute counts, this read can walk past the mapped region for the last CDH entry in the memory-mapped input file: [5](#0-4) 

The corrupted 64-bit value is then used directly as a byte offset into the mapped input file to locate the local file header: [6](#0-5) 

### Impact Explanation
`singlejar` is invoked by the build to merge a set of dependency JARs (including third-party jars fetched via `http_jar`, Maven/`rules_jvm_external`, or any externally-hosted `.jar`) into the final deploy jar. A hostile origin server or mirror serving a malformed JAR could trigger an out-of-bounds heap read in the `singlejar` process during a normal build, corrupting the computed local-header offset with attacker-influenced adjacent heap bytes and subsequently reading/copying data from an unintended (but attacker-steerable) file offset into the output jar, or crashing the build tool. This is a memory-safety bug in a native tool that directly consumes untrusted dependency bytes, analogous in class to the Unbound RRSIG-parsing overread.

### Likelihood Explanation
Exploitability depends on whether the input JAR is checksum-verified before this parsing occurs. `http_jar`/`http_archive` support `sha256`/`integrity` pins, but these are optional attributes; if a project's WORKSPACE/MODULE dependency declaration omits them (a documented but common anti-pattern flagged elsewhere in Bazel's own docs), an attacker controlling the URL/mirror can serve a crafted JAR that reaches `singlejar` unverified. I was not able to fully trace whether all `singlejar` invocation paths (e.g., from `java_binary`, `java_import`, or `rules_jvm_external`-managed jars) always occur after a mandatory hash check in every configuration — this is a real gap in my verification given no more tool calls are available.

### Recommendation
In `Zip64ExtraField`, add a bounds check in `attr64()` (or at each call site) verifying `index < attr_count()` before reading, and treat a failed/insufficient attribute count in `compressed_file_size()`, `uncompressed_file_size()`, and `local_header_offset()` as a corrupt-archive error (matching the existing `diag_errx`/malformed-field handling already used elsewhere in `output_jar.cc` for extra fields) rather than silently reading arbitrary adjacent memory.

### Proof of Concept
I could not construct and run a concrete JUnit/shell reproduction within this session (no further tool calls available to build/execute a crafted `.jar` against `singlejar` and confirm an ASan-detected heap-buffer-overflow). A reproduction would need to:
1. Hand-craft a Central Directory Header with `compressed_file_size32 = uncompressed_file_size32 = local_header_offset32 = 0xFFFFFFFF`.
2. Attach a Zip64 extra field with `payload_size` covering fewer than 3 `uint64_t` attributes (e.g., 8 bytes = 1 attribute).
3. Place this CDH as the last entry in the mapped input so that `attr64(2)` reads past the end of the mapped file, then run it through `singlejar --sources <crafted.jar> --output out.jar` under ASan/Valgrind and observe the heap-buffer-overflow report in `zip_headers.h`'s `attr64()`.

This aligns with the existing test infrastructure in `src/tools/singlejar/zip_headers_test.cc`, which already exercises `Zip64ExtraField`/`CDH` attribute parsing and would be the natural home for such a regression test, though I was unable to author and execute it in this session.
