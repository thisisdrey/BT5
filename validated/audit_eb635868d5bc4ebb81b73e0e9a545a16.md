### Title
Unbounded attachment content decode in `RPCGetAttachmentRequestHandler::try_parse_response` before any `attachments_max_size` check - ([File: stackslib/src/net/api/getattachment.rs])

### Summary
`RPCGetAttachmentRequestHandler::try_parse_response` calls `parse_json` to deserialize the HTTP response body into a `GetAttachmentResponse`, whose custom `Deserialize` implementation hex-decodes the entire `content` string into memory with `hex_bytes` before any comparison against `AtlasConfig::attachments_max_size` or the requested attachment hash occurs. A malicious peer answering an attachment-fetch request can supply an oversized hex payload, forcing the requesting node to allocate and decode the full buffer before any validation runs.

### Finding Description
The response handler is: [1](#0-0) 

`parse_json` deserializes into `GetAttachmentResponse`, whose `Deserialize` impl is: [2](#0-1) 

This reads the whole JSON string field, then unconditionally calls `hex_bytes(&hex_encoded)` to materialize the decoded byte buffer and wraps it in `Attachment::new(bytes)` — there is no check of the decoded length against `attachments_max_size` at this point. The only place `ATTACHMENTS_MAX_SIZE_MIN` (1,048,576 bytes) is referenced is in `AtlasConfig::validate`, which only bounds the *configured* value, not the size of an incoming response: [3](#0-2) [4](#0-3) 

Since `attachments_max_size` defaults to and is only bounded below by `ATTACHMENTS_MAX_SIZE_MIN`, a node operator can configure it larger, but regardless, this handler's decode path performs the full hex-decode allocation for any content the remote peer chooses to send, independent of the configured limit. Any per-attachment size/hash validation that exists is a downstream concern applied only after `try_parse_response` returns a fully-materialized `Attachment`; it does not prevent the decode itself from running against attacker-supplied length.

### Impact Explanation
A remote peer that receives a legitimate `/v2/attachments/<hash>` GET request from a victim node (attachment fetch requests are issued automatically by `AttachmentsDownloader` based on gossiped BNS/attachment inventories) can respond with a body containing a very large hex-encoded string. The victim's HTTP client-side response parser (`try_parse_response`) will allocate and decode that entire buffer before it ever checks the resulting content's hash or length against the request. This is a bounded compute/memory DoS on the requesting node's attachment-fetch code path — matching the "bounded compute DoS on a read endpoint" High-severity category. It is repeatable per fetch attempt as long as the attacker peer keeps being selected to serve attachment responses.

### Likelihood Explanation
The attacker needs no privileged role: any peer that can be selected as a source for an attachment (via gossiped attachment inventories) and that answers a normal `/v2/attachments/:hash` request can trigger this. The cost to the attacker is minimal (craft one oversized HTTP response); the cost to the victim is a proportionally large one-time allocation/hex-decode per response, repeatable for every attachment-fetch attempt that lands on the malicious peer.

### Recommendation
Enforce a maximum content-length / decoded-size check in `RPCGetAttachmentRequestHandler::try_parse_response` (or in `GetAttachmentResponse::deserialize`) prior to hex-decoding — reject bodies whose declared/hex-encoded length would exceed `attachments_max_size` (passed into the handler/deserializer context) before calling `hex_bytes`, and validate the decoded length again immediately after decode as a defense-in-depth measure.

### Proof of Concept
Rust test in `stackslib/src/net/api/tests/getattachment.rs`-style harness:
1. Construct an `HttpResponsePreamble` with `Content-Type: application/json` and a body consisting of a JSON string whose hex payload decodes to, e.g., 50 MB (`"..."` repeated hex chars far exceeding `ATTACHMENTS_MAX_SIZE_MIN = 1_048_576`).
2. Call `RPCGetAttachmentRequestHandler::new().try_parse_response(&preamble, &body)`.
3. Assert that the call succeeds (returns `Ok`) and that `hex_bytes` is invoked/allocates the full buffer with no error raised for exceeding `attachments_max_size`, demonstrating the decode proceeds without a prior size guard.

impl<'de> Deserialize<'de> for GetAttachmentResponse {
    fn deserialize<D: serde::Deserializer<'de>>(d: D) -> Result<GetAttachmentResponse, D::Error> {
        let payload = String::deserialize(d)?;
        let hex_encoded = payload.parse::<String>().map_err(de_Error::custom)?;
        let bytes = hex_bytes(&hex_encoded).map_err(de_Error::custom)?;
        let attachment = Attachment::new(bytes);
        Ok(GetAttachmentResponse { attachment })
    }
}
