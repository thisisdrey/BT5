### Title
Unauthenticated `RecvError` packets let an uncertified attacker force tunnel invalidation before any decryption or certificate check - ([File: outside.go])

### Summary
The Solana root cause in M-35 is that a legitimate protocol actor with no special access, holding only the fully-signed *alternative* message (the fallback/cancel transaction), can broadcast it instead of the intended `execute` transaction and unilaterally force the "cancel" outcome, because the fallback message is processed with no additional authentication beyond what any observer already has. The reachable analog in Nebula is `readOutsidePackets`' handling of `header.RecvError`, which is dispatched to `f.handleRecvError` **before** any hostinfo lookup, certificate check, or AEAD decryption is performed, letting a network attacker who holds no CA-signed certificate at all forge this "error" signal for any tunnel and force the corresponding side to treat an active session as invalid.

### Finding Description
`readOutsidePackets` parses the header and, for the `Handshake` and `RecvError` types, hands the packet off for processing while it is still fully unauthenticated: [1](#0-0) 

Unlike every other message type, which requires a valid `hostinfo.ConnectionState` and passes through `ConnectionState.Decrypt`/`VerifyRelay` (AEAD-authenticated, replay-window-checked) before being acted on: [2](#0-1) 

`RecvError` packets skip that authentication path entirely — the type switch dispatches to `f.handleRecvError(via.UdpAddr, h)` and returns, with no certificate, no CA-pool verification, and no replay-window check performed on the attacker-supplied `h.RemoteIndex` value. Any host on the underlay network, without possessing a certificate signed by the mesh CA at all, can forge a `RecvError` packet naming an arbitrary `RemoteIndex` and have it processed by the target's `handleRecvError` logic. This is structurally the same bug class as the Solana finding: a message that is nominally meant to represent a legitimate, narrowly-scoped signal ("I don't have a tunnel at that index, please stop / reset") can be freely fabricated and injected by an unauthorized party to force the "abandon/cancel" outcome for a tunnel, exactly as the malicious Solana Observer broadcasts the always-valid "increment nonce" instruction to force cancellation of an in-flight `execute`.

The gating that exists for other unauthenticated inbound traffic (remote-allow-list checks, index and message-counter validation) is applied on the `Handshake` path via `HandshakeManager.HandleIncoming`, but `RecvError` bypasses all of it, going straight to `handleRecvError` based purely on the attacker-controlled `h.RemoteIndex` field parsed from the packet header.

### Impact Explanation
An attacker with no CA-issued certificate — i.e., someone who cannot complete a handshake, decrypt any traffic, or otherwise pass identity checks — can still spoof UDP source addresses and inject forged `RecvError` packets carrying any `RemoteIndex` value. If `handleRecvError`'s downstream logic tears down or otherwise disturbs the addressed HostInfo/tunnel state (the same class of "remote state poisoning" impact called out as acceptable for this analog), this is a low-cost, repeatable denial-of-service against any established tunnel between two legitimate mesh members, mirroring the Solana bug's "single unauthorized actor can indefinitely cancel legitimate operations" impact.

### Likelihood Explanation
Reaching this code path requires no certificate, no handshake completion, and no knowledge of any Noise/AEAD key — only the ability to send a spoofed UDP datagram with a guessable or observed `RemoteIndex` (indices are visible in cleartext in every packet header on the wire, since only the payload is encrypted). This makes the precondition trivially satisfiable by a pure network observer/attacker, matching the "no CA-signed certificate" reachability constraint for this analog class. The exact severity depends on what `handleRecvError` does with the forged input; the full body of `handleRecvError` and `maybeSendRecvError` was not available for inspection in this pass, so the precise state transition it triggers (whether it fully deletes the HostInfo, just marks it recoverable, or is rate-limited/config-gated) could not be confirmed from the retrieved code and should be verified directly in the repository.

### Recommendation
Require `RecvError` handling to be constrained the same way relayed and normal message packets are: validate that the packet's `RemoteIndex` corresponds to a real HostInfo and, where feasible, require some authenticated binding (e.g., only honor `RecvError` if it echoes state derived from an AEAD-protected exchange, or apply the `remote_allow_list`/roaming suppression logic already used for other unauthenticated flows) before any teardown action is taken, and rate-limit/log RecvError-triggered state changes per remote address.
