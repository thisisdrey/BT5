### Title
Uninitialized `accountIndexOf` treated as index `0` instead of `INITIAL_INDEX` lets an attacker steal accrued rewards equal to their full balance - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
The analog of CVE-2021-30027's "use of uninitialized memory → invalid state processing" is a read of a default (zero) storage slot where a sentinel value was required. In `RewardsDistributor._calculateTokenDelta`, a missing `accountIndexOf[token][account]` entry (uninitialized storage) is only normalized to `INITIAL_INDEX` when the global index is *strictly greater* than `INITIAL_INDEX`. While the token's supply index still equals `INITIAL_INDEX` — which holds for the whole block in which the governor/keeper sets a positive speed for a newly registered token, and whenever `_deltaTimestamps == 0` — the uninitialized account index is treated as `0`, producing a delta index of `1e18` and crediting the account rewards equal to its entire token balance.

### Finding Description
When a reward speed is first set for a token, `_updateTokenSpeed` registers it with `tokenStates[token_] = TokenState({index: INITIAL_INDEX, timestamp: block.timestamp})` at `contracts/RewardsDistributor.sol:296-299`. [1](#0-0) 

`_calculateTokenDelta` then handles an account that has never interacted (uninitialized `accountIndexOf`) like this at `contracts/RewardsDistributor.sol:222-230`:

```solidity
_tokenIndex = _tokenState.index;                       // = INITIAL_INDEX
uint256 _accountIndex = accountIndexOf[token_][account_]; // uninitialized = 0

if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}

uint256 _deltaIndex = _tokenIndex - _accountIndex;     // = INITIAL_INDEX - 0
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex); // = balance * 1e18
``` [2](#0-1) 

When `tokenStates[token].index == INITIAL_INDEX` (i.e. the index has not yet advanced past its initial value), the `> INITIAL_INDEX` normalization is skipped, `_deltaIndex = 1e18`, and the account is credited `_tokensDelta = balanceOf(account)` — as if the account had accrued the entire index since index 0. The normalizing comparison should be `>= INITIAL_INDEX` (or the default should apply whenever the account index is unset).

`updateBeforeMintOrBurn` is explicitly callable by anyone (`@dev Called by DepositToken and DebtToken contracts ... also may be called by anyone`) at `contracts/RewardsDistributor.sol:171-180`, and is also invoked automatically on deposit/mint hooks. [3](#0-2)  The credited amount lands in `tokensAccruedOf[account]` at `contracts/RewardsDistributor.sol:261-266` and is paid out in `rewardToken` by `claimRewards` → `_transferRewardIfEnoughTokens` at `contracts/RewardsDistributor.sol:248-256`. [4](#0-3) 

Reachability of the vulnerable state:

- `_calculateTokenIndex` returns `(0, 0)` when `block.timestamp == supplyState.timestamp`, leaving the stored index at `INITIAL_INDEX` (`contracts/RewardsDistributor.sol:201-212`). So any `updateBeforeMintOrBurn`/`updateBeforeTransfer`/`claimRewards` executed in the **same block** as the governor's `updateTokenSpeed`/`updateTokenSpeeds` (or the keeper's `syncTokenSpeed`, which is permissioned to `tokenSpeedKeeper` only — the governor path is the relevant one) hits the bug. [5](#0-4) 
- An attacker can back-run the governor transaction in the same block (standard MEV bundle/ordering), or simply call `updateBeforeMintOrBurn(vulnerableToken, attacker)` in that block.

No modifier prevents this: `updateBeforeMintOrBurn` has no access control, `claimRewards` is public and only gated by `nonReentrant`, and the attacker needs nothing more than an existing balance of the target DepositToken/DebtToken obtained via a normal deposit.

### Impact Explanation
Theft of unclaimed yield / direct theft of reward funds. The attacker is credited `tokensAccruedOf[attacker] += depositToken.balanceOf(attacker)` (in raw units) with zero actual accrual time. By sizing their deposit position to at least the distributor's `rewardToken` balance, `claimRewards(attacker)` drains the entire reward reserve in one call. These rewards are funded for all legitimate depositors/borrowers, so this is a direct loss of protocol/user yield, not a self-DoS.

### Likelihood Explanation
Requires the `tokenStates[token].index == INITIAL_INDEX` window — i.e. the same block in which a positive speed is first assigned to a token (or any same-block window where no time has elapsed since index initialization). This is a narrow but realistic window: reward speed updates are discrete, observable on-chain events, and same-block back-running is a standard capability for an unprivileged actor. On L2 deployments the attacker can pre-position a deposit in advance, making the only remaining requirement ordering two transactions in one block — feasible via MEV relays/bundles. No privileged role, oracle manipulation, or governance compromise is needed for the exploit itself.

### Recommendation
Fix the default-index normalization in `_calculateTokenDelta` so an unset account index is always seeded at `INITIAL_INDEX`, not only when the token index has already advanced:

```solidity
// contracts/RewardsDistributor.sol
if (_accountIndex == 0 && _tokenIndex >= INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}
```

or equivalently `if (_accountIndex == 0) { _accountIndex = _tokenIndex < INITIAL_INDEX ? _tokenIndex : INITIAL_INDEX; }`. Additionally, consider seeding `accountIndexOf` lazily to the current stored index on any first touch, which removes the need for the sentinel comparison entirely.

### Proof of Concept
Foundry-style reproduction (run against deployed pool fixtures; `rd` = RewardsDistributor, `dt` = DepositToken, `reward` = rewardToken funded to the distributor):

```solidity
// test/foundry/poc/UninitializedAccountIndex.t.sol
function test_firstTouchAtInitialIndex_stealsRewards() external {
    address alice = address(0xA11CE);

    // 1. Attacker deposits underlying -> DepositToken balance BEFORE rewards exist
    uint256 deposit = IERC20(reward).balanceOf(address(rd)); // sized to drain the reserve
    underlying.mint(alice, depositAmount);
    vm.startPrank(alice);
    underlying.approve(address(dt), depositAmount);
    dt.deposit(depositAmount, alice); // accountIndexOf[dt][alice] stays 0 (token not yet registered)
    vm.stopPrank();

    // 2. Governor registers speed for dt -> tokenStates[dt] = (INITIAL_INDEX, now)
    vm.prank(governor);
    rd.updateTokenSpeed(dt, 1e18);

    // 3. SAME BLOCK: anyone can poke the accrual; deltaIndex = INITIAL_INDEX - 0 = 1e18
    rd.updateBeforeMintOrBurn(dt, alice);
    // tokensAccruedOf[alice] == dt.balanceOf(alice) == deposit

    // 4. Claim drains the distributor's reward tokens
    uint256 balBefore = reward.balanceOf(alice);
    rd.claimRewards(alice);
    assertEq(reward.balanceOf(alice) - balBefore, deposit); // alice stole the full reserve
    assertEq(rd.tokensAccruedOf(alice), 0);
}
```

Step 3 must execute in the same block as step 2 (use `vm.roll` unchanged / same timestamp, or bundle ordering on a fork). The assertion that `tokensAccruedOf[alice] == deposit` demonstrates the uninitialized-index misinterpretation: `INITIAL_INDEX - 0 = 1e18`, and `balance.wadMul(1e18) == balance`.

Uncertainty note: I verified the accounting path directly in `RewardsDistributor.sol` but did not fully read `DepositToken._mint`/hook call sites; this does not affect the finding because `updateBeforeMintOrBurn` and `claimRewards` are both permissionlessly callable, so the attacker triggers the vulnerable read themselves.
