### No vulnerability found for this question.

This exact behavior — an enabled extension disabling the signer's signature while remaining the sole enabled extension, then acting on behalf of the wallet in the same request — is documented, intended design, and is exercised by an existing test, not an attacker escalation.

The wallet README explicitly states that extensions "have the same full power over the wallet-contract instance as the original signer does" and that lockout protection only requires "at least one extension must remain enabled" when signature is disabled — it does not require the *signer* to remain in control. [1](#0-0) 

`check_lockout` correctly implements this documented invariant: it only fails when both `signature_enabled == false` AND `extensions.is_empty()`. With `extensions = {attacker_ext}`, disabling the signature is exactly the allowed "key rotation" path. [2](#0-1) 

Crucially, the "attacker" in this scenario is not an unprivileged party — per the audit's own attacker model, they must reach this state via `execute_op`/`check_lockout` starting from `extensions set = {attacker_ext}`, meaning the wallet owner already added this account as an enabled extension via `AddExtension`, granting it "full power" per design. Becoming an enabled extension requires either the signer's own signed request or an already-enabled extension acting through `w_execute_extension` — an unprivileged attacker cannot add itself as an extension without first being authorized by the owner. [3](#0-2) [4](#0-3) 

This exact flow — signer adds extension, extension disables signature and continues acting on behalf of the wallet — is validated as expected behavior (a "key rotation") in the existing SDK test suite, not as an exploit: [5](#0-4) 

Since the "binding" the question claims is violated (owner's exclusive control) is never actually promised by the contract — the documented invariant is only "no total lockout," not "signer retains ultimate authority over extensions it already granted power to" — there is no divergence between intended and actual behavior. The scenario requires the owner to have already granted the attacker's account extension privileges, which is out of the unprivileged attacker's reach and is explicitly a supported wallet feature (2FA/social recovery/session-key patterns), not a vulnerability.

    fn set_signature_mode(&mut self, enable: bool, actor: Actor<'_>) -> Result<()> {
        if self.0.signature_enabled == enable {
            return Err(Error::ThisSignatureModeAlreadySet);
        }
        self.0.signature_enabled = enable;
        self.check_lockout()?;

        WalletEvent::SignatureModeSet {
            enabled: enable,
            by: actor,
        }
        .emit();

        Ok(())
    }

    fn add_extension(&mut self, account_id: AccountId, actor: Actor<'_>) -> Result<()> {
        if !self.0.extensions.insert(account_id.clone()) {
            return Err(Error::ExtensionEnabled(account_id));
        }

        WalletEvent::ExtensionAdded {
            account_id: account_id.into(),
            by: actor,
        }
        .emit();

        Ok(())
    }

    fn remove_extension(&mut self, account_id: &AccountIdRef, actor: Actor<'_>) -> Result<()> {
        if !self.0.extensions.remove(account_id) {
            return Err(Error::ExtensionNotEnabled(account_id.to_owned()));
        }
        self.check_lockout()?;

        WalletEvent::ExtensionRemoved {
            account_id: account_id.into(),
            by: actor,
        }
        .emit();

        Ok(())
    }

    #[inline]
    fn check_extension_enabled(&self, account_id: &AccountIdRef) -> Result<()> {
        if !self.0.has_extension(account_id) {
            return Err(Error::ExtensionNotEnabled(account_id.to_owned()));
        }
        Ok(())
    }

    #[inline]
    fn check_lockout(&self) -> Result<()> {
        if !self.0.signature_enabled && self.0.extensions.is_empty() {
            return Err(Error::Lockout);
        }
        Ok(())
    }
