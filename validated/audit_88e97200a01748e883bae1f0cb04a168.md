## Title
Unvalidated `call_value`/`call_token_value` transferred to code-less (e.g. self-destructed) contract addresses in `VMActuator.call()` - permanent loss of funds ([File: actuator/src/main/java/org/tron/core/actuator/VMActuator.java])

### Summary
The original report describes `InsurancePool.depositCollateral()` accepting an arbitrary `msg.value` alongside an ERC20 deposit without validating/refunding it, so any excess value sent by the caller is permanently stranded in the contract. The analogous root cause in java-tron is in `VMActuator.call()`, which handles `TriggerSmartContractContract` transactions: it unconditionally transfers the caller-supplied `call_value` (TRX) and `call_token_value` (TRC10) to the destination contract address even when that address has no executable bytecode to receive/process/refund them, permanently locking the funds.

### Finding Description
`VMActuator.call()` validates that a `ContractCapsule` exists for the target address [1](#0-0) , but the actual bytecode is fetched separately and may be empty: [2](#0-1) 

If `code` is empty, the entire block that sets up a `Program`/VM invocation (energy limit checks, `ProgramInvoke` creation, `Program` construction) is skipped: [3](#0-2) .

Regardless of whether that code branch ran, the method falls through and unconditionally transfers `callValue` and `tokenValue` to `contractAddress`: [4](#0-3) 

There is no check that the destination actually has bytecode capable of handling, forwarding, or refunding the received value before the transfer is performed. This mirrors the reported pattern of "msg.value not validated" — a caller-provided value amount is accepted and moved into a contract's balance without any guarantee that the value can ever be retrieved or is meaningfully consumed by that contract's logic (because there is no logic to run).

A concrete way this manifests: a smart contract that self-destructs (`SELFDESTRUCT`/`suicide`) has its bytecode removed via `Program`/`MUtil` suicide handling [5](#0-4) , but its `ContractCapsule` entry in the `ContractStore` can remain resolvable by `rootRepository.getContract(contractAddress)`. Any subsequent `TriggerSmartContract` transaction that targets this dead contract address with a nonzero `call_value`/`call_token_value` will pass the `deployedContract == null` check, skip VM execution because `code` is empty, and still execute the unconditional `MUtil.transfer` / `MUtil.transferToken` calls at lines 573-579, moving TRX/TRC10 into a contract address that can never execute code again to move it back out.

### Impact Explanation
Value sent to a destroyed/code-less contract address via this path becomes permanently unrecoverable, since no bytecode exists at that address to ever move it out (no receive/fallback/any function can execute). This is a permanent freezing of user funds, triggered by an ordinary, unprivileged `TriggerSmartContract` transaction targeting a self-destructed contract, matching the "permanent freezing of funds" acceptance criterion.

### Likelihood Explanation
Any transaction broadcaster can trigger this by sending a `TriggerSmartContractContract` transaction with `call_value` or `call_token_value` set, targeting a contract address that has previously self-destructed (a routine, unprivileged, publicly-known blockchain state). No special privileges, malicious validators, or network conditions are required — only knowledge of a self-destructed contract's address, which is public information.

### Recommendation
Before performing the unconditional value transfers at [4](#0-3) , verify that the destination `code` is non-empty (i.e., there is an actual executable contract to receive/process the value), and reject the transaction (or route the value back to the caller) when the target contract has no bytecode, consistent with the `isNotEmpty(code)` check already used to gate VM execution setup.

### Proof of Concept
1. Deploy contract `C` with a `selfdestruct` function; call it to destroy `C`'s bytecode (its `ContractCapsule` may remain retrievable via `getContract`).
2. Broadcast a `TriggerSmartContractContract` transaction from an unprivileged account with `contract_address = C`, `call_value = X` (or `call_token_value = Y`, `token_id = Z`).
3. `VMActuator.call()` finds `deployedContract != null` (passes validation), reads `code = rootRepository.getCode(C)` which is empty, skips the VM-execution setup block, and then unconditionally executes `MUtil.transfer(rootRepository, callerAddress, C, X)` / `MUtil.transferToken(...)`.
4. `X` TRX (or `Y` of token `Z`) is now held by dead contract `C`'s balance with no way to ever execute code at `C` again, permanently locking the funds.
