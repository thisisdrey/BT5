### Title
Legacy (non-hardened) Bancor exchange calculation allows a trading pair's pool balances to go negative without being rejected - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java])

### Summary
`ExchangeCapsule.transaction()` computes new pool balances proportionally (Bancor-style AMM math) from a user-supplied trade quantity, exactly the same class of operation as the reported `updateCompartmentsReduceLiq` bug: a percentage/ratio-derived balance mutation that can push a balance below the valid threshold (here, below zero) without the invariant being re-checked and enforced by default.

### Finding Description
`ExchangeCapsule.transaction()` mutates `firstTokenBalance`/`secondTokenBalance` based on the processor's computed `buyTokenQuant`: [1](#0-0) 

The post-mutation validity check (`newFirstTokenBalance < 0 || newSecondTokenBalance < 0` → revert) is only performed when `hardenedCalc` is `true`: [2](#0-1) 

`hardenedCalc` is gated by the dynamic parameter `allowHardenExchangeCalculation`, which is off by default and only turned on for tests in this codebase (`saveAllowHardenExchangeCalculation(1)`), meaning the legacy/default path performs the balance mutation via `ExchangeProcessor`/legacy Bancor math (which uses `double`/floating point and truncating division) and never validates that the resulting pool balances are non-negative or otherwise consistent — this is invoked by both `ExchangeTransactionActuator` (which even calls `transaction()` twice — once in `doValidate()` and again in `execute()` — mutating a re-fetched capsule each time) and by `ExchangeInjectActuator`/`ExchangeWithdrawActuator`, which use similarly unguarded `floorDiv`/`divide` arithmetic on user-controlled `tokenQuant`: [3](#0-2) [4](#0-3) 

This is directly analogous to the reported bug: a percentage-derived balance update (`compartment.balance -= liquidityPerAsset`) is applied without re-validating/enforcing the invariant that the resulting balance must remain within the valid range, and the codebase already demonstrates awareness of the fix (the `hardenedCalc` branch), but it is not applied unconditionally — exactly mirroring "the recommendation is to call compartmentalize()... but it currently is not [called in all paths]".

### Impact Explanation
If the legacy exchange balance calculation can be driven to a state where `firstTokenBalance` or `secondTokenBalance` becomes zero or negative (e.g., via repeated small trades exploiting floating-point rounding/truncation in the legacy `ExchangeProcessor`, or via sequences of inject/withdraw/transaction calls that are individually validated against stale balances but not re-validated post-mutation), it corrupts the AMM invariant for that trading pair. This can result in a permanently broken exchange (denial of service for that market, since further validate() calls key off `firstTokenBalance == 0 || secondTokenBalance == 0`) or, depending on downstream arithmetic sign handling, produce miscalculated `anotherTokenQuant` in future trades. This falls in the requested "unbacked balance"/permanent freezing/state-corruption impact category for an in-scope actuator.

### Likelihood Explanation
Reachable by any unprivileged account broadcasting `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` transactions — no special privilege required. However, the default hardened flag being off is deliberate legacy behavior, and exploiting rounding to actually drive a balance negative under the legacy Bancor math requires careful crafting of quant values across possibly many transactions; I could not confirm from the available code that the legacy `ExchangeProcessor` math (using `double`, not `BigDecimal`) can actually be forced to produce a negative outcome without hitting an earlier "exchange balance is not enough" guard, since `ExchangeWithdrawActuator`/`ExchangeInjectActuator` do have their own `subtractExact`/`multiply/divide` sufficiency checks in `doValidate()`. This significantly limits confidence that a full negative-balance state is currently reachable through the exposed actuators today; it should be treated as a class-of-bug/defense-in-depth gap rather than a confirmed exploitable finding.

### Recommendation
Apply the same non-negative/invariant post-condition check that the hardened path already performs (`newFirstTokenBalance < 0 || newSecondTokenBalance < 0`) unconditionally in `ExchangeCapsule.transaction()`, regardless of the `allowHardenExchangeCalculation` flag, and revert/throw `ContractValidateException` if violated — analogous to calling `compartmentalize()` after every balance-affecting operation in the reported bug's recommendation.

### Proof of Concept
Not confirmed as directly exploitable with concrete transaction inputs; I was unable to fully trace whether the legacy `ExchangeProcessor`'s double-based math combined with existing `doValidate()` sufficiency checks in `ExchangeTransactionActuator`/`ExchangeInjectActuator`/`ExchangeWithdrawActuator` can actually be driven to produce a negative pool balance without first tripping "exchange balance is not enough" or "Token balance in exchange is equal with 0" guards. This would require deeper analysis of `ExchangeProcessor`'s arithmetic (`chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`) which was not retrievable within the available context — recommend a Devin session with full repository access to trace `ExchangeProcessor.exchange()`'s formula and attempt to construct a sequence of `ExchangeTransactionContract` calls (or Inject/Withdraw combinations) that drives `firstTokenBalance`/`secondTokenBalance` negative under `allowHardenExchangeCalculation = 0`.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
