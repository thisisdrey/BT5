Audit Report

## Title
Unbounded, un-prunable growth of `PendingOrders` in Snowbridge outbound queue v2 - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
`do_process_message` unconditionally inserts a permanent `PendingOrder` entry into the `PendingOrders` storage map for every message processed from the message queue, keyed by `nonce`, with no cap on the number of entries and no expiry mechanism. The only removal path is `process_delivery_receipt`, which depends entirely on an off-chain relayer voluntarily submitting a verified Ethereum delivery receipt for that exact nonce — something not guaranteed to happen for every message (e.g., zero-fee messages, dropped Ethereum execution, or verifier downtime).

## Finding Description
Every message accepted by the pallet — whether it originates from a sibling parachain's XCM export or from `snowbridge-pallet-system-v2` — is inserted into `PendingOrders` unconditionally in `do_process_message`: [1](#0-0) 

The pallet's `on_initialize`/`on_finalize` hooks only clear the transient `Messages`/`MessageLeaves` storage values and commit the merkle root; they never touch `PendingOrders`: [2](#0-1) 

Removal of a `PendingOrders` entry only happens in `process_delivery_receipt`, gated behind `T::Verifier::verify` and a call to the signed extrinsic `submit_delivery_receipt`: [3](#0-2) [4](#0-3) 

There is no other code path in the pallet — no `on_idle` reaper, no admin extrinsic, no migration — that prunes or expires stale entries, despite the `PendingOrder` struct already carrying a `block_number` field that could support expiry logic. The message-entry path itself (`send_message_impl::deliver`) has no fee floor or storage-deposit requirement beyond the ordinary message weight fee: [5](#0-4) 

`MaxMessagesPerBlock` only bounds the number of messages processed *per block* (to cap `on_finalize` weight), not the cumulative size of `PendingOrders` over the chain's lifetime: [6](#0-5) 

Any message whose corresponding Ethereum-side delivery receipt is never submitted — because the fee is zero/unprofitable, the relayer never observes/relays it, or Ethereum-side execution reverts — leaves a permanent, un-removable entry in `PendingOrders`. Since message entry is triggered by ordinary XCM traffic (asset transfers/exports to Ethereum from any sibling parachain, or the system pallet), this is reachable by unprivileged usage, not just governance or malicious relayers.

## Impact Explanation
This matches the accepted impact category "public underpriced work that degrades block production or stalls bridge processing." A message sender pays only the ordinary message-processing fee; there is no additional cost proportional to the permanent state increment created in `PendingOrders`. Because BridgeHub is a system parachain with strict PoV/state-size constraints, indefinite unbounded growth of this map increases per-block state overhead and long-term chain storage costs with no offsetting mechanism.

## Likelihood Explanation
High. No malicious relayer, prover, or governance action is required. A single message with `fee == 0` (or one whose Ethereum-side receipt is never produced/relayed) is sufficient to create a permanently orphaned `PendingOrders` entry. Given that delivery-receipt submission depends entirely on independent, unincentivized off-chain relayer behavior, some fraction of entries accumulating without removal over the bridge's lifetime is a near-certainty.

## Recommendation
Introduce a bounded/expiring mechanism for `PendingOrders`:
- Use the existing `block_number` field on `PendingOrder` to implement a bounded, weight-metered reaping mechanism in `on_initialize`/`on_idle` that removes orders older than a configurable threshold.
- Alternatively/additionally, charge a per-entry storage deposit at insertion time (refunded on `submit_delivery_receipt`), so abandoned entries carry an explicit, priced cost.
- Cap the total number of outstanding `PendingOrders` entries and apply backpressure (e.g., reject/yield new message processing) once the cap is reached, similar in spirit to `MAX_UNREWARDED_RELAYERS_IN_CONFIRMATION_TX` in `pallet-bridge-messages`.

## Proof of Concept
1. From any sibling parachain (or via `snowbridge-pallet-system-v2`), submit an outbound message with `fee = 0` through the normal XCM export/`SendMessage::deliver` path.
2. The message queue invokes `Pallet::do_process_message`, which unconditionally inserts a `PendingOrder` keyed by the assigned `nonce` into `PendingOrders` — `<PendingOrders<T>>::insert(nonce, order);` (`bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs:436`).
3. Because `fee == 0`, no relayer has an economic incentive to call `submit_delivery_receipt` for this nonce, so `process_delivery_receipt` (the only removal path) is never invoked for it.
4. Repeat step 1 across many blocks: `PendingOrders` accumulates permanently, with no `on_initialize`/`on_idle` hook or other code path in the pallet ever expiring or pruning stale entries.

		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}

impl<T> SendMessage for Pallet<T>
where
	T: Config,
{
	type Ticket = Message;

	fn validate(message: &Message) -> Result<Self::Ticket, SendError> {
		// The inner payload should not be too large
		let payload = message.encode();
		ensure!(
			payload.len() < T::MaxMessagePayloadSize::get() as usize,
			SendError::MessageTooLarge
		);

		Ok(message.clone())
	}

	fn deliver(ticket: Self::Ticket) -> Result<H256, SendError> {
		let origin = ticket.origin.into();

		let message =
			BoundedVec::try_from(ticket.encode()).map_err(|_| SendError::MessageTooLarge)?;

		T::MessageQueue::enqueue_message(message.as_bounded_slice(), origin);
		Self::deposit_event(Event::MessageQueued { message: ticket.clone() });
		Ok(ticket.id)
	}
