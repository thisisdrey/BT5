Audit Report

## Title
`process_delivery_receipt` in Snowbridge outbound-queue-v2 ignores the on-chain `success` flag, rewarding relayers and clearing pending orders even when the Ethereum-side execution failed - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
The Snowbridge V2 outbound pipeline commits messages to Ethereum after assets have already been withdrawn/reserved on Asset Hub via `InitiateTransfer`/`ReserveWithdraw` XCM instructions, tracking per-message state in `PendingOrder`. Settlement is driven by `submit_delivery_receipt` → `process_delivery_receipt`, which decodes a `DeliveryReceipt` including a `success: bool` field from the Ethereum `InboundMessageDispatched` event, but never inspects that flag before paying the relayer and removing the order.

## Finding Description
`DeliveryReceipt` carries a `success` field decoded straight from the Ethereum event log [4](#0-3) . In `process_delivery_receipt`, the pallet checks `receipt.gateway`, resolves `reward_account`, fetches the `PendingOrder` by `nonce`, pays the relayer if `order.fee > 0`, then unconditionally calls `<PendingOrders<T>>::remove(nonce)` and emits `MessageDelivered` — `receipt.success` is decoded but never read [2](#0-1) . The extrinsic `submit_delivery_receipt` only validates the proof/log and forwards the decoded receipt as-is [3](#0-2) . By the time this runs, the pallet's own documentation confirms assets were already committed for delivery via `InitiateTransfer` at message-processing time [5](#0-4) , and `do_process_message` creates the `PendingOrder` entry when the message is queued for export, well before any Ethereum-side outcome is known [6](#0-5) . There is no branch anywhere in this pallet that distinguishes `success: true` from `success: false`, and no other storage or call in the module re-examines the flag to trigger a refund.

## Impact Explanation
This matches the "duplicate settlement or payout" / "permanent bridge-state lock" impact category: a relayer is rewarded and the `PendingOrder` bookkeeping is permanently destroyed regardless of whether the Ethereum dispatch actually succeeded, since the receipt proof only attests to what the event log says (`success: false` is exactly as provable as `success: true`). Once removed, no code path in the pallet can recover or reroute the assets that were already committed for the cross-chain transfer.

## Likelihood Explanation
This is reachable via the ordinary, unprivileged `submit_delivery_receipt` extrinsic by any relayer who obtains a valid proof for a legitimate Ethereum event log — no malicious relayer, validator, or governance action is required. A message whose Ethereum-side dispatch fails for any reason (revert, insufficient gas, dispatch error) deterministically produces a `success: false` event that is processed identically to a success case.

## Recommendation
Branch on `receipt.success` in `process_delivery_receipt`: on `true`, keep current behavior; on `false`, avoid treating the delivery as completed for reward purposes and emit a distinct event (e.g., `MessageDispatchFailed`) while retaining or transitioning the `PendingOrder` state so a refund path back to the original sender can be driven, instead of unconditionally removing the order and paying the reward.

## Proof of Concept
1. Send an XCM with `WithdrawAsset`/`InitiateTransfer`/`ReserveWithdraw` targeting Ethereum on Asset Hub, producing a message with nonce `n` and inserting `PendingOrder { nonce: n, fee, .. }` via `do_process_message`.
2. Assume the Ethereum Gateway contract execution for nonce `n` fails, emitting `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer calls `submit_delivery_receipt` with a valid proof of that log; `T::Verifier::verify` succeeds and `DeliveryReceipt::try_from` decodes `success: false` correctly.
4. `process_delivery_receipt` ignores `success`, still calling `T::RewardPayment::register_reward` for the relayer and `<PendingOrders<T>>::remove(nonce)`, emitting `MessageDelivered`.
5. The relayer is paid as if delivery succeeded, and the pending-order state for nonce `n` is destroyed with no refund path triggered.

			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward

					&reward_account,

					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
