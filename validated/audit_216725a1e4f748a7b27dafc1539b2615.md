### Title
Incorrect exponentiation logic in graduated liquidation curve produces wrong `liq-pct-scaled` and excessive liquidation seizure - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`calc-liq-factor-exp` is meant to raise the linear liquidation factor to a configurable curve exponent (`factor^alpha`, where `alpha = curve-exponent / BPS`). Like the reported ELO `Elo.sol` bug, the implementation decomposes the exponent incorrectly using integer-only math, so for the vast majority of possible `curve-exponent` values the function returns a mathematically wrong result instead of `factor^alpha`.

### Finding Description
```
(define-private (calc-liq-factor-exp (factor uint) (exp uint))
  (if (is-eq exp BPS) 
    factor
    (if (> exp BPS) 
        (/ (pow factor (/ exp BPS)) (pow BPS (- (/ exp BPS) u1)))
        (sqrti (* factor BPS))))) ;; assume factor^0.5
``` [1](#0-0) 

Two independent errors mirror the ELO exponent-decomposition bug:

1. **`exp > BPS` branch (alpha > 1):** `(/ exp BPS)` is integer division. Any `exp` that is not an exact multiple of `BPS` (10000) is truncated, so a configured exponent like `alpha = 1.5` (`exp = 15000`) collapses to `(/ exp BPS) = 1`, and the whole expression degenerates to `(/ (pow factor 1) (pow BPS 0)) = factor`, i.e. the code silently computes `factor^1` instead of `factor^1.5`. Because `factor <= BPS` (a fraction ≤ 1), `factor^1.5 < factor^1`, so the code **returns a larger `liq-pct-scaled` than the curve intends** for any non-integer-multiple exponent above `BPS`.
2. **`exp < BPS` branch (alpha < 1):** the code does not use `exp` at all — it is hard-coded to `sqrti(factor * BPS)`, i.e. always computes `factor^0.5`, exactly as the comment admits ("assume factor^0.5"). Any configured `curve-exponent` other than exactly `5000` (alpha = 0.5) is silently ignored and replaced by the wrong hard-coded square-root formula.

This is directly analogous to the referenced Elo.sol finding: an exponent is supposed to be applied precisely, but an integer-based decomposition/offset scheme (`/ exp BPS`, hard-coded `sqrti`) discards the fractional/actual exponent and yields a value far from the mathematically correct one.

`calc-liq-factor-exp` feeds directly into `calc-liquidation-params`, which computes `liq-pct-scaled` used both for the liquidation penalty (`calc-liq-factor-bound`) and the maximum liquidatable debt (`calc-liq-debt-repay`):
```
(let ((liq-pct-linear (calc-liq-factor current-ltv ltv-liq-partial ltv-liq-full))
      (liq-pct-scaled (calc-liq-factor-exp liq-pct-linear curve-exponent))
      (liq-penalty (calc-liq-factor-bound liq-pct-scaled liq-penalty-min liq-penalty-max))
      (max-debt-usd (calc-liq-debt-repay total-debt-usd liq-pct-scaled)))
``` [2](#0-1) 

`calc-liquidation-params` is used by the liquidation entry point that any unprivileged principal (liquidator) can call, so the wrong `liq-pct-scaled` is reachable without any privileged action.

### Impact Explanation
When `liq-pct-scaled` is inflated by the truncation/hard-coding bug, both `liq-penalty` (via `calc-liq-factor-bound`) and `max-debt-usd` (via `calc-liq-debt-repay`) are computed larger than the graduated curve intends. A larger `max-debt-usd` allows a liquidator to repay more debt than the curve should permit at the current LTV, and a larger `liq-penalty` increases the bonus collateral seized per unit of debt repaid (`calc-liq-collateral-repay`). This lets a liquidator extract more collateral from a borrower's position than the intended graduated-liquidation design allows — a direct theft of user (borrower) collateral beyond the mathematically correct amount, which lands on the Critical impact class (direct theft of user funds at rest).

### Likelihood Explanation
The bug fires for essentially any `curve-exponent` value other than exactly `BPS` (alpha=1) or exactly `5000` (alpha=0.5), so unless the DAO happens to configure the curve exponent to one of those two exact values, every partial/graduated liquidation computes the wrong scaled factor. Since liquidation is a normal, permissionless, frequently-triggered operation, the incorrect math is exercised continuously rather than needing a rare edge case.

### Recommendation
Replace the integer-truncated exponent decomposition with a fixed-point power function that can represent fractional exponents precisely (e.g., a `pow-fixed(base, exponent, precision)` helper using binary exponentiation over a fixed-point representation), and remove the hard-coded `sqrti`/`factor^0.5` shortcut so the actual configured `curve-exponent` is always honored.

### Proof of Concept
1. DAO configures `curve-exponent = 15000` (intending `alpha = 1.5`, a common graduated-liquidation curve shape).
2. A borrower's position reaches `liq-pct-linear = 0.8 * BPS` (8000).
3. Correct result: `factor^1.5 = 0.8^1.5 ≈ 0.7155 * BPS ≈ 7155`.
4. Actual contract result: `(/ exp BPS) = (/ 15000 10000) = 1` → `(/ (pow 8000 1) (pow 10000 0)) = 8000`.
5. `liq-pct-scaled = 8000` instead of the correct `~7155`, inflating `max-debt-usd` and `liq-penalty`, allowing the liquidator to seize more collateral than the curve should permit at that LTV.
