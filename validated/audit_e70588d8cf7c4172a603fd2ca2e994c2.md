### Title
Unbounded `sock.read_to_end` in `run_http_request` allows a malicious/impersonated node to exhaust `stacks-signer` memory before the `STACKERDB_MAX_CHUNK_SIZE`/`SIGNERS_STACKERDB_CHUNK_SIZE` check ever runs - (File: `libsigner/src/http.rs`, `libsigner/src/session.rs`)

### Summary
`StackerDBSession::get_latest_chunks` only rejects an oversized chunk body *after* the entire HTTP response has already been buffered in memory. The underlying transport function `run_http_request` calls `sock.read_to_end(&mut buf)` with no length cap and no chunked-transfer bound check on non-chunked bodies, so a malicious HTTP peer can send an arbitrarily large `Content-Length`-less or raw body that gets fully allocated into `buf`/`body_bytes` before `body_bytes.len() > limit` is ever evaluated.

### Finding Description
In `libsigner/src/http.rs`, `run_http_request` does: [1](#0-0) 
`sock.read_to_end(&mut buf)` reads from the socket until EOF with no size bound whatsoever, allocating and growing `buf` to hold however many bytes the peer chooses to send. Only after this full read completes does the code call `decode_http_response` and then `decode_http_body`. For a non-chunked body, `decode_http_body` does `buf.to_vec()` verbatim with no cap: [2](#0-1) 
(The `MAX_MESSAGE_LEN` bound only applies to the chunked-transfer-encoding branch via `HttpChunkedTransferReader`, not to the plain body path.)

Only in `StackerDBSession::get_latest_chunks` (and similarly `get_chunks`) is a size check performed, and it happens strictly *after* `rpc_request` → `run_http_request` has returned the fully-materialized `body_bytes`: [3](#0-2) 

So the equality the question poses is confirmed broken: the `len() > limit` guard is a post-allocation sanity check, not a bounded-read mechanism. A peer that the `stacks-signer` process connects to for a `GET stackerdb_get_chunk_path` request (i.e., the node configured in the signer's config, or any host reachable at that configured address/port) can respond with a 200 status, headers, and then stream an arbitrarily large body (megabytes to gigabytes) without `Transfer-Encoding: chunked`. `run_http_request` will keep growing `buf` via `read_to_end` until the connection is closed or the process runs out of memory, well before `get_latest_chunks` gets a chance to compare `body_bytes.len()` against `SIGNERS_STACKERDB_CHUNK_SIZE`/`STACKERDB_MAX_CHUNK_SIZE`.

### Impact Explanation
This is a memory-exhaustion DoS against the `stacks-signer` process itself: the peer at the other end of a `StackerDBSession` connection (the configured node's RPC endpoint, or an attacker able to stand at that reachable TCP endpoint) can force the signer to allocate an unbounded amount of memory per request/response cycle, and this is repeatable on every `get_latest_chunks`/`get_chunks`/`list_chunks`/`put_chunk` call since all of them funnel through the same unbounded `run_http_request`. Repeated or large-enough responses can crash or OOM the signer process, which matches the "Critical - remote crash/unauthenticated DoS from few messages" category, since a single oversized response is sufficient.

### Likelihood Explanation
The `StackerDBSession` connects out to `self.host`, which is the node RPC address configured for the signer; ordinarily this is the operator's own trusted node. However, per the question's stated threat model, any party able to be reached at that configured TCP endpoint (e.g., due to network-level redirection, a compromised/misbehaving upstream node the signer is pointed at, or a peer standing in for that endpoint) can serve the oversized response with no authentication, secret, or privileged role needed — the client performs a plain unauthenticated `GET`. Attacker cost is a single crafted HTTP response; the flaw is triggerable on every StackerDB read RPC the signer performs, making it trivially repeatable.

### Recommendation
Bound the read in `run_http_request` (e.g., wrap `sock` with a `Take` reader capped at `MAX_MESSAGE_LEN` or the caller-supplied chunk-size limit) so the socket read itself is capped, and enforce a body-size limit inside `decode_http_body`'s non-chunked branch (mirroring the `HttpChunkedTransferReader` cap already used for chunked bodies), rather than checking `body_bytes.len()` only after the full buffer has been allocated in `get_latest_chunks`/`get_chunks`.

### Proof of Concept
Rust test in `libsigner/src/session.rs` (or `http.rs`) tests module:
1. Spin up a `TcpListener` on `127.0.0.1:0`.
2. In a spawned thread, accept the connection, read the request line, then write `"HTTP/1.1 200 OK\r\n\r\n"` followed by `STACKERDB_MAX_CHUNK_SIZE * 10` bytes of arbitrary payload (no `Content-Length`, no chunked encoding), then close the socket.
3. Call `StackerDBSession::get_latest_chunks(&[0])` (or directly `run_http_request`) against this listener.
4. Assert/observe that the process's `buf` in `run_http_request` grows to `STACKERDB_MAX_CHUNK_SIZE * 10` bytes (e.g., by instrumenting/measuring allocation, or by using a very large multiplier to demonstrate uncontrolled memory growth) — i.e., the full oversized body is read via `sock.read_to_end(&mut buf)` in `libsigner/src/http.rs:251` before `body_bytes.len() > limit` is evaluated in `libsigner/src/session.rs:243`, at which point the check merely converts the result to `None` instead of preventing the allocation.

/// Decode an HTTP body, given the headers.
pub fn decode_http_body(headers: &HashMap<String, String>, mut buf: &[u8]) -> io::Result<Vec<u8>> {
    let chunked = if let Some(val) = headers.get("transfer-encoding") {
        val == "chunked"
    } else {
        false
    };

    let body = if chunked {
        // chunked encoding
        let ptr = &mut buf;
        let mut fd = HttpChunkedTransferReader::from_reader(ptr, MAX_MESSAGE_LEN.into());
        let mut decoded_body = vec![];
        fd.read_to_end(&mut decoded_body)?;
        decoded_body
    } else {
        // body is just as-is
        buf.to_vec()
    };

    Ok(body)
}
