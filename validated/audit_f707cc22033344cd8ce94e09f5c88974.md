### Title
Dust deposits permanently occupy a victim's per-account token slots (`MAX_TOKENS_PER_USER`), blocking collateral top-ups, new borrows, and rescue of underwater positions - ([File: contracts/DepositToken.sol])

### Summary
The `Pool` tracks each account's collateral/debt tokens in a per-account enumerable set capped at `MAX_TOKENS_PER_USER = 30` (Pool.sol:79). Both `DepositToken._transfer` and `DepositToken._mint` unconditionally call `pool.addToDepositTokensOfAccount(recipient)` whenever the recipient's balance transitions from 0, and `addToDepositTokensOfAccount` reverts with `UserReachedMaxTokens` once the combined list is full (Pool.sol:143-148, 216-220). There is no minimum transfer amount. An unprivileged attacker can deposit a few wei of every supported collateral, receive `msdTOKEN`, and `transfer` 1 wei of each deposit token to a victim, permanently filling all 30 slots. Analogous to CVE-2022-23328 (attacker occupying a bounded resource to deny service to a victim), this is a contract-level mempool-filling equivalent: a dust-funded, one-way occupancy of the victim's token slots.

### Finding Description
- `DepositToken._transfer` adds the token to the recipient's account list on any non-zero transfer to a zero-balance account, with no dust threshold or opt-in (DepositToken.sol:517-520).
- `Pool.addToDepositTokensOfAccount` enforces `debtTokensOfAccount.length + depositTokensOfAccount.length < 30` and reverts otherwise (Pool.sol:143-148).
- Once slots are full:
  - `DepositToken.deposit(..., onBehalfOf_ = victim)` reverts inside `_mint` → `addToDepositTokensOfAccount` (DepositToken.sol:486-488). The victim cannot deposit *new* collateral types.
  - `DebtToken.issue` reverts inside `_mint` → `addToDebtTokensOfAccount` for any synthetic the victim doesn't already hold (DebtToken.sol:598-600).
  - `Pool.liquidate` → `DepositToken.seize` reverts if the liquidator's own list is full, but more importantly the victim cannot add collateral to restore health.
- Escape is unreliable: to free a slot the victim must zero the dust balance via `transfer`, which requires `unlockedBalanceOf(victim) >= 1 wei`. `unlockedBalanceOf` returns `min(balance, quoteUsdToToken(issuableInUsd / CF))` when debt exists (DepositToken.sol:383-398). For a victim at or above their collateralization limit (`issuableInUsd == 0`), `unlockedBalanceOf == 0`, so every dusted slot — including pre-existing collateral the attacker dusted to re-register? no, re-registration isn't needed — the dust tokens are locked and cannot be removed, making the freeze permanent for leveraged accounts.

### Impact Explanation
An underwater or near-underwater victim is permanently prevented from topping up with any collateral token they don't already hold (the most common rescue action — depositing a new asset). If the victim has debt and zero free balance, the dust cannot be sent back, so all 30 slots are bricked: no new deposits, no new debt types, and `swap`/`issue` paths that mint new debt tokens revert. This is temporary-to-permanent freezing of the victim's ability to manage their position, directly causing liquidation losses that could have been avoided.

### Likelihood Explanation
Cost to the attacker is near zero: deposit minimal amounts of each listed underlying (no minimum in `deposit`), keep enough dust per `msdTOKEN`, and send 1 wei of each to the victim. It is fully permissionless via public `deposit`/`transfer`. The attack is most damaging against already-leveraged accounts (where `unlockedBalanceOf == 0` prevents cleanup) and can be timed before expected volatility. Front-running a victim's first-ever deposit is also possible but less severe.

### Recommendation
Enforce a minimum balance/transfer for first-time registration (e.g., only call `addToDepositTokensOfAccount` when the resulting balance or its USD value exceeds a dust threshold), or allow recipients to unregister dust entries — e.g., a `Pool`-level function letting an account remove a deposit/debt token whose balance is below a dust floor. Alternatively, remove the `MAX_TOKENS_PER_USER` guard by bounding iteration via oracle-priced aggregation limits rather than per-account set size.

### Proof of Concept
Hardhat/fork sketch against a deployed `Pool`:

```solidity
// Assume `pool` has >= 30 usable collateral/debt offerings (depositTokens list).
// 1. For each DepositToken dt_i in pool's deposit list:
//    underlying_i.approve(dt_i, 2);
//    dt_i.deposit(2, attacker);            // attacker gets >=1 wei msdToken_i
// 2. For each dt_i:
//    dt_i.transfer(victim, 1);             // fills victim's depositTokensOfAccount
// Now depositTokensOfAccount.length(victim) == 30.
// 3. victim attempts to deposit a NEW collateral dt_new:
//    dt_new.deposit(amount, victim)        // reverts: UserReachedMaxTokens
// 4. victim attempts to issue a new synthetic:
//    debtToken_new.issue(x, victim)        // reverts: UserReachedMaxTokens
// 5. If victim has debt with issuableInUsd == 0:
//    dt_i_from_victim.transfer(dust)       // reverts: NotEnoughFreeBalance
//    -> slots cannot be freed; freeze is permanent.
```

Reproduction on a fork only requires the victim to hold some debt and the pool to list enough deposit tokens for the attacker to cover remaining slots.
