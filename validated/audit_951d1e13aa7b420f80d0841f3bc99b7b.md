### Title
`ProxyOFT.sendFrom` accepts a zero/invalid destination address, causing bridged tokens to be permanently burned on the source chain with an unconsumable message on the destination - (File: contracts/ProxyOFT.sol)

### Summary
`ProxyOFT.sendFrom` (and the base `OFTCoreUpgradeable.sendFrom`) perform no validation of the destination `to_`/`_toAddress` argument. A user can specify `address(0)` (or the `SyntheticToken`/`ProxyOFT` contract itself) as the recipient. The source-side `_debitFrom` succeeds and burns the user's `SyntheticToken` [1](#0-0) , but on the destination chain `_sendAck` → `ProxyOFT._creditTo` calls `syntheticToken.mint(toAddress_, amount_)` [2](#0-1) , which reverts with `MintToTheZeroAddress` when `to_ == address(0)` [3](#0-2) . Because `retryMessage` replays the identical immutable payload [4](#0-3) , the message can never be consumed.

### Finding Description
`sendFrom` encodes the user-supplied `to_` directly into the LayerZero payload without any sanity check [5](#0-4) . There is no `to_ != address(0)` check anywhere along the send path, and no check that the recipient is not the `SyntheticToken` or `ProxyOFT` contract itself (tokens minted to a contract that cannot move them are equally unrecoverable). On the receiving side, `OFTCoreUpgradeable._sendAck` decodes `toAddress` and calls `_creditTo` [6](#0-5) , which calls `SyntheticToken.mint`, which hard-reverts on `account_ == address(0)` [3](#0-2) . This mirrors the reported `L1DAIBridge.deposit` issue exactly: the source-side call succeeds while the destination-side handler can never succeed.

### Impact Explanation
Bridge conservation is broken: tokens are burned on the source chain (`totalSupply` decreased, `totalBridgedOut` increased) but the corresponding mint on the destination permanently fails. `NonblockingLzAppUpgradeable._blockingLzReceive` catches the revert and stores the payload hash in `failedMessages` [7](#0-6) , yet `retryMessage` requires the identical `keccak256(_payload)` and reverts again on every retry — there is no path to redirect or refund the funds. The result is permanent loss of the bridged amount.

### Likelihood Explanation
Requires a user (or a front-end/integration bug) to pass `address(0)` — or an address that can never custody tokens, such as the `SyntheticToken`/`ProxyOFT` contract on the destination chain — as `to_`. This is a self-inflicted/input-error class issue rather than an externally exploitable theft vector, matching the Medium severity of the reference finding. No modifier (`isBridgingActive`, `isDestinationChainSupported`, `SenderIsNotTheOwner`) prevents it [1](#0-0) .

### Recommendation
Add destination-address sanity checks in `ProxyOFT.sendFrom`/`_debitFrom` (and/or in `_creditTo` with a recoverable path):
- `if (to_ == address(0)) revert RecipientIsNull();`
- Reject `to_ == address(syntheticToken)` and `to_ == address(this)` to avoid minting to contracts that cannot move the tokens.
- Alternatively, implement a fallback so failed `_creditTo` messages can be claimed by a corrected recipient rather than being permanently bricked.

### Proof of Concept
Foundry fork test (two forks, e.g. Base → Plasma as in `test/foundry/CrossChainsPlasmaBase.sol`):

```solidity
function test_sendFrom_zeroRecipient_bricksFunds() public {
    vm.selectFork(baseFork);
    uint256 amount = 1e18;
    deal(msUSD_base, alice, amount);
    uint256 fee = msUSD_proxyOFT_base.estimateSendFee(LZ_PLASMA_CHAIN_ID, address(0), amount);
    deal(alice, fee);

    vm.prank(alice);
    // No zero-recipient check: succeeds and burns alice's msUSD on Base
    msUSD_proxyOFT_base.sendFrom{value: fee}(alice, LZ_PLASMA_CHAIN_ID, address(0), amount);
    assertEq(IERC20(msUSD_base).balanceOf(alice), 0);

    // Deliver on destination
    vm.selectFork(plasmaFork);
    bytes memory toAddress = abi.encodePacked(address(0));
    vm.prank(lzEndpoint_plasma.defaultReceiveLibraryAddress());
    lzEndpoint_plasma.receivePayload(
        LZ_BASE_CHAIN_ID,
        abi.encodePacked(address(msUSD_proxyOFT_base), address(msUSD_proxyOFT_plasma)),
        address(msUSD_proxyOFT_plasma),
        lzEndpoint_plasma.getInboundNonce(LZ_BASE_CHAIN_ID, abi.encode(address(msUSD_proxyOFT_base))) + 1,
        SIMPLE_TRANSFER_GAS,
        abi.encode(PT_SEND, toAddress, amount)
    );

    // Mint reverted with MintToTheZeroAddress -> message stored as failed
    bytes32 stored = msUSD_proxyOFT_plasma.failedMessages(
        LZ_BASE_CHAIN_ID, abi.encodePacked(msUSD_proxyOFT_base), nonce);
    assertTrue(stored != bytes32(0));
    assertEq(IERC20(msUSD_plasma).balanceOf(address(0)), 0);

    // Retry replays the same payload and reverts forever -> funds permanently lost
    vm.expectRevert();
    msUSD_proxyOFT_plasma.retryMessage(
        LZ_BASE_CHAIN_ID, abi.encodePacked(msUSD_proxyOFT_base), nonce,
        abi.encode(PT_SEND, toAddress, amount));
}
```

    function retryMessage(uint16 _srcChainId, bytes calldata _srcAddress, uint64 _nonce, bytes calldata _payload) public payable virtual {
        // assert there is message to retry
        bytes32 payloadHash = failedMessages[_srcChainId][_srcAddress][_nonce];
        require(payloadHash != bytes32(0), "NonblockingLzApp: no stored message");
        require(keccak256(_payload) == payloadHash, "NonblockingLzApp: invalid payload");
        // clear the stored message
        failedMessages[_srcChainId][_srcAddress][_nonce] = bytes32(0);
        // execute the message. revert if it fails again
        _nonblockingLzReceive(_srcChainId, _srcAddress, _nonce, _payload);
        emit RetryMessageSuccess(_srcChainId, _srcAddress, _nonce, payloadHash);
    }
