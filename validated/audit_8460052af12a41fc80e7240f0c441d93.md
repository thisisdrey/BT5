### Title
Uncontrolled Resource Consumption via Unbounded Array Allocation in `ValidateMultiSign`/`BatchValidateSign` TVM Precompiles - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` and `BatchValidateSign` TVM precompiled contracts extract attacker-controlled array-length fields from calldata and use them directly to allocate Java arrays (`new byte[len][]`) before any upper-bound validation is performed, whenever the `allowTvmSelfdestructRestriction` fork/feature flag is not active. Any contract call (reachable from an unprivileged `TriggerSmartContract` transaction) can supply a crafted length word to force a huge memory allocation attempt, analogous to CVE-2022-29864's "attacker supplies a size field that drives unbounded allocation before validation."

### Finding Description
`extractBytesArray` and `extractBytes32Array` read a length directly from the caller-supplied `data` and allocate an array of that size without any bound check: [1](#0-0) 

These are invoked from `ValidateMultiSign.execute` and `BatchValidateSign.doExecute`. The size guard (`sigArraySize > MAX_SIZE` / `addrArraySize > MAX_SIZE`) is only applied when `VMConfig.allowTvmSelfdestructRestriction()` is true — otherwise `extractBytesArray`/`extractBytes32Array` are called unconditionally with the attacker-controlled length, and the `cnt > MAX_SIZE` check only happens **after** the array has already been allocated: [2](#0-1) [3](#0-2) 

The energy charged for calling these precompiles is computed purely from `data.length` (the actual calldata size), not from the value encoded inside the length word: [4](#0-3) [5](#0-4) 

This means a caller can submit small, cheap calldata (a handful of 32-byte words) that pays minimal energy, but embed an arbitrarily large integer (e.g., close to `Integer.MAX_VALUE`) in the position read as the array length. `words[offset].intValueSafe()` converts the 256-bit word to an `int`; when that huge value is used as `new byte[len][]`/`new byte[len][]`, the JVM attempts to allocate an array of up to ~2^31 element references before the guard at line 1179/1076 is ever reached, since the guard executes only after the array has already been constructed in the un-gated (feature flag off) code path.

### Impact Explanation
A single, unprivileged, low-cost smart-contract call (`CALL` to the precompiled address for `validatemultisign`/`batchvalidatesign`, reachable via any `TriggerSmartContract` transaction or `TransferAssetContract`-adjacent contract invocation) can force the node's TVM execution thread to attempt an outsized heap allocation. Repeated invocation (each transaction independently cheap in energy relative to the attempted allocation) can exhaust JVM heap, triggering `OutOfMemoryError` in the block/transaction-processing thread. Because this executes inside `Manager`'s transaction/block application path, an uncaught `OutOfMemoryError` during contract execution (or repeated allocation pressure across many transactions in a block) can crash or stall the node — a node crash/halt (CWE-400), which is explicitly an accepted impact category (node crash or halt).

### Likelihood Explanation
Likelihood is conditional: the vulnerable, un-gated path is exercised only while `allowTvmSelfdestructRestriction` is not yet active on a given network/fork height. On networks/testnets or historical states where this specific TIP/fork has not been activated (it is a committee-governed feature switch, gated the same way as other TVM upgrade proposals in `ProposalUtil.java`/`DynamicPropertiesStore`), any address can trigger the bug with a single crafted transaction, at very low cost since the energy formula is decoupled from the attacker-chosen length field. On networks/heights where the flag is active, the bound check happens before extraction and this specific path is closed for the signature/address arrays it guards, though the general design pattern (deriving allocation size from an unchecked embedded word before verifying it) remains fragile.

### Recommendation
- In `extractBytesArray` and `extractBytes32Array`, validate the extracted `len` against a hard upper bound (e.g., `MAX_SIZE` for the respective precompile) and against `words.length` before allocating any array, regardless of `allowTvmSelfdestructRestriction`.
- Move the `sigArraySize`/`addrArraySize` bound checks so they execute unconditionally (not gated behind the fork flag) prior to calling `extractBytesArray`/`extractSigArray`/`extractBytes32Array`.
- Ensure `getEnergyForData` energy costs (or a dedicated pre-check) account for the value encoded in the length word itself, not merely `data.length`, so that mismatches between claimed array size and actual calldata size are rejected cheaply before allocation.

### Proof of Concept
1. Craft calldata for `batchvalidatesign(bytes32,bytes[],address[])` with the minimal 5-word ABI header (satisfying `isValidAbiEncoding`) but set the word at the offset read as the `addresses` array length (`words[2]`-derived offset) to a very large value (e.g., `0x7FFFFFFF`).
2. Ensure `VMConfig.allowTvmSelfdestructRestriction()` is false (i.e., target a network/height where this TIP has not been activated).
3. Deploy a trivial contract that performs a `CALL` (or `STATICCALL`) to the `BatchValidateSign` precompiled address with this calldata, and submit it via `TriggerSmartContract`.
4. Observe that `extractBytes32Array` executes `new byte[0x7FFFFFFF][]` before the `addrArraySize > MAX_SIZE` guard is reached (the guard is skipped entirely in this code path), causing an attempted multi-gigabyte allocation and `OutOfMemoryError` in the executing node, for the cost of only a few dozen bytes of calldata and minimal energy per `getEnergyForData`.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
