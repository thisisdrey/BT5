### Title
Unauthenticated `RecvError` Packet Causes Immediate, Unauthenticated Tunnel Teardown - ([File: outside.go])

### Summary
The external report describes a bug class where a privileged actor's single, immediately-effective action (`set_maintenance_margin_required()`) can force a negative state transition (liquidation) on an existing session with no grace period and only a shallow safety check. The reachable analog in this repository is Nebula's `RecvError` handling: an attacker who has *no* valid CA-signed certificate can send a single crafted, unencrypted UDP packet that causes `Interface.handleRecvError` to immediately tear down an established, authenticated tunnel between two legitimate peers, gated only by a plaintext source-address comparison rather than any cryptographic authentication.

### Finding Description
`readOutsidePackets` dispatches `header.RecvError` packets before any certificate or AEAD authentication is performed: [1](#0-0) 

The handler, `handleRecvError`, looks up the target `HostInfo` purely by the numeric `RemoteIndex` embedded in the unauthenticated packet, and then performs only a comparison of the packet's UDP source address against the currently known remote address of that tunnel: [2](#0-1) 

If that address check passes (or the recorded remote address happens to be unset/matches, e.g. via UDP source spoofing, an on-path position, or shortly after a roam), `f.closeTunnel(hostinfo)` is called immediately — tearing down a fully established, cryptographically authenticated tunnel with a single unauthenticated packet. There is no signature, no HMAC, no replay/nonce protection, and no grace period: one packet forces an immediate, irreversible state change on a victim tunnel, exactly mirroring the reported bug class where a single privileged update immediately and irreversibly changes a user's risk state (safe → liquidatable) with no timelock or corroborating check.

By default, `acceptRecvErrorConfig` is `"always"`, meaning this path is reachable from any address unless the operator has hardened `listen.accept_recv_error` to `"private"` or `"never"`: [3](#0-2) 

This is also acknowledged as a known-sensitive area in the project history — a previous release note explicitly changed defaults here due to spoofing concerns — confirming the reachability and sensitivity of this code path to attackers without a valid certificate: [4](#0-3) 

### Impact Explanation
An attacker with no CA-signed certificate (i.e., someone who is not a member of the Nebula mesh) can force teardown of live tunnels between legitimate, mutually-authenticated peers by spoofing a UDP source address and guessing/observing a `RemoteIndex` value. This is a remote state-poisoning / denial-of-service primitive against the tunnel/session state (`HostMap`), directly analogous to the "immediate liquidation" impact in the original report: a victim's previously-safe state (an established, authenticated tunnel) is forcibly and immediately converted to a bad state (torn-down tunnel, forcing re-handshake, connection loss, and potential downstream disruption of the overlay network) via a single unauthenticated signal, with no timelock, no corroboration from the cryptographic session state, and no recourse for the victim.

### Likelihood Explanation
The `RecvError` message type is deliberately unencrypted/unauthenticated by design (it must be sendable before any session exists), and by default acceptance is not restricted (`accept_recv_error: always`). An attacker only needs to know/guess a `RemoteIndex` (a 32-bit value transmitted in cleartext on every packet, thus observable to any network-path attacker) and be able to spoof (or legitimately control, in an on-path position) the expected source `netip.AddrPort`. This is a comparably low bar relative to full MITM or certificate compromise, making the analog readily reachable by a certificateless attacker.

### Recommendation
- Do not allow `RecvError` (or any other unauthenticated control packet) to trigger an immediate, unconditional `closeTunnel()`. At minimum, require some additional corroborating signal (e.g., MAC over the encrypted session material, or requiring several corroborating error signals within a scoring window) before tearing down an established, authenticated tunnel.
- Tighten the default `listen.accept_recv_error` value from `"always"` to `"private"` (only accept from private/local addresses) or add stricter default rate limiting per remote index/address.
- Consider only accepting `RecvError` while a hostinfo is `pendingDeletion` or already known transiently invalid, rather than fully authenticated/established tunnels, closing the gap between "reachable by anyone" and "acted upon with full trust."

### Proof of Concept
1. Attacker learns (or brute-forces/observes on path) the `RemoteIndex` a victim (`them`) has assigned to a tunnel with peer `me`, and the current UDP `AddrPort` `me` believes `them` is reachable at (both values travel in cleartext on every Nebula packet header).
2. Attacker crafts a UDP packet with `header.RecvError` type and the victim's `RemoteIndex`, spoofing the source address to match `me`'s known remote address for that tunnel (or positions on-path to send from that address).
3. Attacker sends this single packet to `them`'s listening UDP port.
4. `readOutsidePackets` routes it directly to `f.handleRecvError` (outside.go:81-84) without any authentication.
5. `handleRecvError` matches the spoofed source address against `hostinfo.GetRemote()` and, on match, immediately calls `f.closeTunnel(hostinfo)` and deletes pending handshake state — destroying the fully-established, legitimate, authenticated tunnel between `me` and `them` with a single forged, unauthenticated packet (outside.go:563-575).

Note that repository tests (e.g. `TestCloseTunnelAuthenticated` in `e2e/tunnels_test.go`) explicitly verify that a bogus, unauthenticated `CloseTunnel` message is correctly rejected by the encrypted-message path — but no equivalent test exists validating that `RecvError` cannot be similarly spoofed to force the same teardown outcome, underscoring that this specific unauthenticated path was not hardened to the same standard. [5](#0-4)

func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}

func (f *Interface) reloadAcceptRecvError(c *config.C) {
	if c.InitialLoad() || c.HasChanged("listen.accept_recv_error") {
		stringValue := c.GetString("listen.accept_recv_error", "always")

		switch stringValue {
		case "always":
			f.acceptRecvErrorConfig = recvErrorAlways
		case "never":
			f.acceptRecvErrorConfig = recvErrorNever
		case "private":
			f.acceptRecvErrorConfig = recvErrorPrivate
		default:
			if c.GetBool("listen.accept_recv_error", true) {
				f.acceptRecvErrorConfig = recvErrorAlways
			} else {
				f.acceptRecvErrorConfig = recvErrorNever
			}
		}

		f.l.Info("Loaded accept_recv_error config", "acceptRecvError", f.acceptRecvErrorConfig.String())
	}
}
