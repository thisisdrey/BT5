### Title
P2P-pushed transactions bypass `Relayer::static_check_problematic_relayed_tx`, unlike HTTP-uploaded ones - ([File: stackslib/src/net/p2p.rs])

### Summary
`PeerNetwork::store_transaction` (called from `store_transactions` for both `network_result.pushed_transactions` and `network_result.synced_transactions`) never calls `Relayer::static_check_problematic_relayed_tx` before submitting a transaction to the mempool, while `posttransaction.rs`'s HTTP handler explicitly performs this static check before calling `mempool.submit`. This means a remote peer can push a known-problematic transaction (e.g. an over-depth pre-Epoch-3.4 AST) over the p2p wire and have it stored and relayed, bypassing the guard that exists on the HTTP ingestion path.

### Finding Description
In `stackslib/src/net/api/posttransaction.rs`, `try_handle_request` explicitly calls: [1](#0-0) 
before invoking `mempool.submit`.

In `stackslib/src/net/p2p.rs`, `PeerNetwork::store_transaction` (used by `store_transactions` for both p2p-pushed and mempool-synced transactions) goes straight from `mempool.has_tx` / epoch lookup to `mempool.submit`, with no corresponding call to `Relayer::static_check_problematic_relayed_tx`: [2](#0-1) 

`store_transactions` calls this function for every transaction in `network_result.pushed_transactions` (transactions pushed to this node by a remote peer over p2p) and stores it into the `ret` map for re-relay if `store_transaction` returns `true`: [3](#0-2) 

Since the only content check performed is `mempool.submit(...)` (which internally applies `will_admit_mempool_tx`-type checks, but not the static problematic-tx heuristic that `Relayer::static_check_problematic_relayed_tx` implements), a transaction that would be statically rejected on the HTTP path (e.g., due to AST depth / problematic clarity constructs relative to the epoch) is not rejected on the p2p push path. If `mempool.submit` otherwise accepts it (nonce/fee/signature valid), `store_transaction` returns `true`, the tx is added to `ret[nk]`, and `store_transactions` re-inserts it into `network_result.pushed_transactions`, from which it will subsequently be relayed to other peers — achieving network-wide propagation of the problematic transaction that the static check was designed to prevent.

### Impact Explanation
This allows an unprivileged remote peer to inject a known-problematic transaction into a target node's mempool and have the node re-relay it to its other peers, defeating the epoch-based static problematic-tx defense (e.g., over-depth AST parsing/processing issues) across the p2p gossip network. This matches the "network-wide propagation of forged/problematic data" Critical impact category, since the static check exists specifically to prevent such transactions from being stored/relayed and it is skipped entirely on this path.

### Likelihood Explanation
The attacker only needs to be an ordinary p2p peer able to push a transaction message to a node (`pushed_transactions`), which is a standard, unauthenticated (beyond normal peer handshake) capability of any connected peer. No secret, no privileged role, no special node state is needed. The bug is deterministic and repeatable for every problematic transaction pushed.

### Recommendation
Add a call to `Relayer::static_check_problematic_relayed_tx(chainstate.mainnet, stacks_epoch.epoch_id, &tx)` inside `PeerNetwork::store_transaction` (guarded by `Relayer::do_static_problematic_checks()`), immediately after the epoch lookup and before `mempool.submit`, mirroring the check in `posttransaction.rs`, so both p2p-pushed and synced transactions are subject to the same static problematic-tx rejection as HTTP-uploaded ones.

### Proof of Concept
In `stackslib/src/net/p2p.rs` tests (or `net/tests/relay`), construct a `StacksTransaction` known to be flagged by `Relayer::static_check_problematic_relayed_tx` for the target epoch (e.g., an over-depth AST tx that is problematic pre-Epoch-3.4). Populate `network_result.pushed_transactions` with `(NeighborKey, vec![(vec![], problematic_tx)])`, call `PeerNetwork::store_transactions(...)`, and assert:
1. Directly calling `Relayer::static_check_problematic_relayed_tx(mainnet, epoch_id, &tx)` returns `Err(...)`.
2. After `store_transactions`, the mempool (`mempool.has_tx(&txid)`) contains the transaction and/or `network_result.pushed_transactions` still contains it for re-relay — demonstrating it was NOT rejected, unlike the equivalent flow through `posttransaction.rs::try_handle_request`, which would return `Ok(false)` at line 208 for the same transaction/epoch.

    fn store_transaction(
        mempool: &mut MemPoolDB,
        sortdb: &SortitionDB,
        chainstate: &mut StacksChainState,
        burnchain_tip: &BlockSnapshot,
        consensus_hash: &ConsensusHash,
        block_hash: &BlockHeaderHash,
        tx: StacksTransaction,
        event_observer: Option<&dyn MemPoolEventDispatcher>,
    ) -> bool {
        let txid = tx.txid();
        if mempool.has_tx(&txid) {
            debug!("Already have tx {}", txid);
            return false;
        }
        let stacks_epoch = match SortitionDB::get_stacks_epoch(
            sortdb.conn(),
            burnchain_tip.block_height,
        )
        .ok()
        .flatten()
        {
            Some(epoch) => epoch,
            None => {
                warn!("Failed to store transaction because could not load Stacks epoch for canonical burn height = {}",
                      burnchain_tip.block_height);
                return false;
            }
        };

        if let Err(e) = mempool.submit(
            chainstate,
            sortdb,
            consensus_hash,
            block_hash,
            &tx,
            event_observer,
            &stacks_epoch.block_limit,
            &stacks_epoch.epoch_id,
        ) {
            debug!("Transaction rejected from mempool, {}", &e.into_json(&txid));
            return false;
        }

        debug!("Stored tx {}", txid);
        return true;
    }
