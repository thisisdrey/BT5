This confirms the premise of the question is not achievable in the codebase.

`BlockBandwidthRequests.shards_bandwidth_requests` is a `BTreeMap<ShardId, BandwidthRequests>` keyed by `ShardId`, so by construction it is impossible to have "duplicate shard entries" — a `BTreeMap` cannot hold two entries for the same key; a second insert overwrites the first. [1](#0-0) 

This map is also not attacker-influenced content at all. It is built once per shard by `Runtime`/`generate_bandwidth_requests`, which iterates `shard_layout.shard_ids()` and produces at most one `BandwidthRequest` per `to_shard` from the runtime's own outgoing-receipt-buffer sizes (via `get_receipt_group_sizes_for_buffer_to_shard`), not from arbitrary receipt fields an attacker controls. [2](#0-1) [3](#0-2) 

Each chunk's `BandwidthRequests::V1(BandwidthRequestsV1{ requests })` therefore contains at most one request per receiver shard (loop is over `shard_layout.shard_ids()`), and `block_bandwidth_requests`/`build_block_bandwidth_requests` insert one entry per producing shard ID into the outer `BTreeMap`, again keyed uniquely. [4](#0-3) [5](#0-4) 

An unprivileged attacker submitting transactions/receipts (even with conflicting `to_shard`/receiver fields) cannot inject entries into this structure directly — it is derived deterministically from the runtime's own trie-backed outgoing buffers and metadata after chunk apply, not parsed from a serialized attacker-supplied `BandwidthRequests` blob. There is no code path where an ActionReceipt's contents let the attacker create two entries for the same `ShardId` key or otherwise produce a non-canonical `BlockBandwidthRequests`; the "buggy upstream builder" scenario in the question is hypothetical and not reachable via any transaction the attacker can submit.

Separately, even the internal `BandwidthScheduler::run` algorithm re-sorts/re-buckets all `SchedulerBandwidthRequest`s by `link` and by `allowance` into fresh `BTreeMap`s (`requests_by_allowance`) before processing, and only shuffles requests within a tie bucket using a `ChaCha20Rng` seeded by `prev_block_hash` (itself agreed upon by consensus, not attacker-influenced) — so the input iteration order of `shards_bandwidth_requests` has no bearing on determinism; every shard reconstructs the same canonical ordering from the same map contents. [6](#0-5) [7](#0-6)
