### Title
Emergency Pause Blocks User Withdrawals, Permanently Freezing Confidential Asset Balances — (File: `aptos-move/framework/aptos-framework/sources/confidential_asset/confidential_asset.move`)

### Summary

The `withdraw_to` function and `rollover_pending_balance` function in `confidential_asset.move` both assert `!is_emergency_paused()` before executing. When governance triggers an emergency pause, users are completely unable to withdraw their fungible assets from the confidential pool or roll over their pending balances. Their on-chain assets are permanently frozen for the duration of the pause, with no escape hatch.

### Finding Description

The `confidential_asset` module implements a global emergency pause controlled by governance via `set_emergency_paused`. When `emergency_paused == true`, the following user-facing functions all abort with `E_EMERGENCY_PAUSED`:

- `register` (line 423)
- `deposit` (line 458)
- `withdraw_to` / `withdraw_to_raw` (line 522)
- `confidential_transfer` (line 623)
- `rotate_encryption_key` (line 700)
- `rollover_pending_balance` (line 772)
- `set_incoming_transfers_paused` (line 817)

The critical flaw is that **`withdraw_to`** — the only function that moves fungible assets from the confidential pool back to a user's primary store — is blocked by the same emergency pause that is supposed to protect users. This means that during an emergency pause, users cannot recover their own assets.

The developers themselves recognized the asymmetry between "disabled" and "paused" states for withdrawals. The comment at line 525–526 explicitly states:

```move
// WARNING: We do not assert `is_confidentiality_enabled_for_asset_type` because we want to give users a way to
// withdraw from the confidential into their public balance after an asset type is disabled.
```

This shows the intent: withdrawals should be allowed even in restricted states so users can always recover their funds. However, this same exemption was not applied to `is_emergency_paused()`, creating an inconsistency where an asset-type disable allows withdrawal but a global emergency pause does not.

The full withdrawal path is blocked at two levels:
1. `rollover_pending_balance` (line 772) — required to move pending balance to available before withdrawal — checks `is_emergency_paused()`.
2. `withdraw_to` (line 522) — the actual withdrawal — also checks `is_emergency_paused()`.

A user with funds only in their pending balance (not yet rolled over) cannot even reach the withdrawal step.

### Impact Explanation

When governance triggers an emergency pause (e.g., in response to a discovered vulnerability), all users with confidential asset balances lose access to their fungible assets for the entire duration of the pause. The assets remain locked in the confidential pool's `FungibleStore` at the protocol-controlled address. There is no user-callable escape hatch. This constitutes **permanent freezing of user-controlled on-chain fungible assets** for the pause duration, matching the allowed impact category of "permanent freezing … of fungible assets … or other user-controlled on-chain assets."

The emergency pause governance proposal already exists in the repository (`emergency-pause-confidential-assets.yaml`), confirming this is a real, deployable governance action on mainnet.

### Likelihood Explanation

The emergency pause mechanism exists precisely because the protocol anticipates scenarios requiring it. Any governance-triggered pause — whether due to a cryptographic vulnerability, a discovered exploit, or a protocol upgrade — will simultaneously freeze all user withdrawals. The longer the pause, the more severe the impact. Users have no recourse.

### Recommendation

Exempt `withdraw_to` (and by extension `rollover_pending_balance`, since it is a prerequisite for withdrawal) from the emergency pause check, mirroring the existing exemption for `is_confidentiality_enabled_for_asset_type`. The fix is:

```move
// In withdraw_to: remove or conditionalize the emergency pause check
// assert!(!is_emergency_paused(), error::invalid_state(E_EMERGENCY_PAUSED));  // REMOVE

// In rollover_pending_balance: same
// assert!(!is_emergency_paused(), error::invalid_state(E_EMERGENCY_PAUSED));  // REMOVE
```

Withdrawals should always be permitted so users can recover their assets regardless of protocol state, consistent with the existing design intent documented in the code comment at line 525–526.

### Proof of Concept

1. User calls `deposit(...)` and accumulates a confidential balance (pending or available).
2. Governance executes the `emergency_pause_confidential_assets` proposal, setting `GlobalConfig::V2 { emergency_paused: true }`.
3. User calls `rollover_pending_balance(...)` → aborts at line 772: `assert!(!is_emergency_paused(), ...)`.
4. User calls `withdraw_to_raw(...)` → aborts at line 522: `assert!(!is_emergency_paused(), ...)`.
5. User's fungible assets remain locked in the confidential pool's `FungibleStore` with no callable exit path.
