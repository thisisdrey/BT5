### Title
StackerDB chunk signatures omit contract binding, enabling cross-StackerDB replay of authenticated chunks - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` — the digest that a Stacker signs to authenticate a `StackerDBChunkData` write — is computed only from `slot_id`, `slot_version`, and `data_hash`. It does not include the target StackerDB's smart-contract identifier (`QualifiedContractIdentifier`) or any reward-cycle/consensus-hash context. Any node that accepts the chunk (via P2P push, sync, or the `POST /v2/stackerdb/.../chunks` HTTP RPC) only re-derives the signer address from its own local, per-contract slot-owner table and checks that this signature verifies against that address — it never checks that the signature was produced *for this contract*.

Because the same private key is very commonly authorized as the signer for the *same slot index* across multiple StackerDB instances (e.g. signer-set / signer-signature StackerDBs re-deployed per reward cycle, where the same signer set is re-assigned to the same slot ordering), a `StackerDBChunkData` object that is validly signed for contract A's slot 3 also validly verifies for contract B's slot 3, as long as the destination contract has that same address configured for that slot and the destination slot's Lamport clock is lower than the replayed chunk's `slot_version`. Nothing in the signed payload (`auth_digest`) or in `try_replace_chunk`/`validate_received_chunk`/`process_stacker_db_chunks` binds the signature to the specific `smart_contract_id` (`QualifiedContractIdentifier`) that produced it. The `rc_consensus_hash` field carried in `StackerDBPushChunkData`/`StackerDBGetChunkData` is likewise not part of the signed digest — it is only used to gate whether a message is processed "now" vs. buffered as `FutureView`, not to authenticate the chunk to a particular reward cycle.

This is the CWE-502-class analog requested: data that is "authenticated" is accepted and stored without verifying that the authentication actually corresponds to *this* destination object (the specific StackerDB/contract instance) — the same class of bug as accepting a deserialized object without checking that it is of the expected/intended type or origin.

### Impact Explanation
An attacker (any peer, no special privilege) who has observed one validly-signed chunk broadcast for reward-cycle N's StackerDB contract can replay that exact `StackerDBChunkData` (unmodified — replay does not even require forging anything) to a *different* StackerDB contract (e.g. reward-cycle N+1's instance) if that contract configures the same signer address at the same `slot_id`, and if the target slot's local Lamport clock is currently lower than the replayed `slot_version`. Since `try_replace_chunk` performs no cross-contract binding check, the replayed chunk is accepted as authentic and stored, and the local node then rebroadcasts it via `process_stacker_db_chunks`/`broadcast_message`, propagating stale/foreign data as if it were freshly authenticated content for the new context. This is an unauthorized write to StackerDB state and network-wide propagation of data outside its intended authenticated context — falling under "unauthenticated/unauthorized write to state or StackerDB" / "network-wide propagation of forged data".

### Likelihood Explanation
Exploitability depends entirely on operational fact patterns outside this code's control: whether the same signer address is assigned to the same `slot_id` across two live StackerDB instances at the same time. This is a plausible and even likely configuration for Nakamoto signer-set StackerDBs, which are re-provisioned each reward cycle typically preserving relative signer ordering, but I could not fully confirm from the indexed code whether slot assignment is guaranteed/likely to preserve index-to-signer mapping across cycles (this would require reviewing the StackerDB config-derivation logic driven by the signers smart contract, which was outside what I could examine in the time available). The remaining checks (`slot_version` must exceed the destination's stored version, and the chunk must fit `chunk_size`) reduce — but do not eliminate — the practical replay window.

### Recommendation
Include the target `smart_contract_id` (and ideally the applicable reward-cycle identifier / `rc_consensus_hash`) in `SlotMetadata::auth_digest()` so that a chunk signature is cryptographically bound to the specific StackerDB instance it was written to, preventing any cross-contract or cross-cycle replay of otherwise-valid signed chunks.

### Proof of Concept
Conceptual (not fully verified against slot-assignment behavior, see Likelihood):
1. Signer `S` is configured as the owner of `slot_id = 3` in StackerDB contract `A` (reward cycle N) and also of `slot_id = 3` in StackerDB contract `B` (reward cycle N+1).
2. `S` signs and pushes `StackerDBChunkData { slot_id: 3, slot_version: 5, sig, data }` to contract `A`; the network stores and gossips it as usual.
3. An attacker observes this chunk on the wire and re-submits the identical `StackerDBChunkData` (same `sig`, same `data`) as a `StackerDBPushChunk`/`POST /v2/stackerdb/.../chunks` targeting contract `B`, as long as `B`'s slot 3 currently has `slot_version < 5`.
4. `validate_received_chunk`/`try_replace_chunk` for contract `B` verify the signature against `B`'s configured slot-3 signer address (`S`), which succeeds because the digest never referenced contract `A`, and the chunk is accepted, stored, and rebroadcast under contract `B`'s identity.     /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Sign this slot metadata, committing to slot_id, slot_version, and
    /// data_hash.  Sets self.signature to the signature.
    /// Fails if the underlying crypto library fails
    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
