## Analog Found

### Title
Graduated liquidation curve exponent math silently truncates fractional exponents in `calc-liq-factor-exp`, causing incorrect (inflated) liquidation penalty/percentage - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
The external report's root cause — a power function that only correctly supports integer exponents, silently breaking any fractional-exponent use case (e.g., `0.5^0.5`) — has a direct analog in Zest's graduated liquidation curve implementation, `calc-liq-factor-exp`.

### Finding Description
`calc-liq-factor-exp` is meant to compute `liq-factor^alpha`, where `alpha` (the `LIQ-CURVE-EXP` egroup parameter, expressed in bps) is explicitly documented to support fractional multipliers such as `<10000` for "gentle curve (e.g., square root)" and `>10000` for "aggressive curve" scaling [1](#0-0) .

The implementation, however, only uses Clarity's native integer `pow`, combined with integer division `(/ exp BPS)` to derive the exponent:

```
(define-private (calc-liq-factor-exp (factor uint) (exp uint))
  (if (is-eq exp BPS) 
    factor
    (if (> exp BPS) 
        (/ (pow factor (/ exp BPS)) (pow BPS (- (/ exp BPS) u1)))
        (sqrti (* factor BPS))))) ;; assume factor^0.5
``` [2](#0-1) 

For any `exp` strictly between `BPS` and `2*BPS` (i.e., a curve exponent between 1.0 and 2.0, exclusive of 1.0), integer division `(/ exp BPS)` truncates to `1`, so the function returns `factor` unchanged (i.e., computes `factor^1`) instead of `factor^alpha`. For any `exp < BPS` other than exactly `5000` (0.5), the code unconditionally assumes the exponent is `0.5` and returns `sqrti(factor * BPS)`, silently miscomputing any other "gentle curve" value (e.g., `0.3`). This is the exact "pow math allows only integers" defect described in the report — the function only produces correct results at exact integer multiples of `BPS` (or the hardcoded `0.5` special case), not for the fractional exponents the egroup parameter is documented to support.

### Impact Explanation
`calc-liq-factor-exp` feeds directly into `calc-liquidation-params`, which computes `liq-pct-scaled` (used for both `max-debt-usd` and `liq-penalty`) inside the standard liquidation flow reachable by any liquidator [3](#0-2) . When an egroup is configured with a fractional `LIQ-CURVE-EXP` (a supported, documented configuration, not a misconfiguration or DAO compromise), the truncated exponent causes `liq-pct-scaled` to be computed larger than the intended curve value for `factor < BPS`, since `factor^1 > factor^alpha` for any `alpha > 1` and `factor < 1`. This inflated `liq-pct-scaled` increases both `max-debt-usd` (via `calc-liq-debt-repay`) and `liq-penalty` (via `calc-liq-factor-bound`), letting a liquidator seize a larger share of the borrower's collateral and repay more debt than the intended graduated curve allows — a direct theft of the borrower's principal collateral (funds at rest), not merely yield.

### Likelihood Explanation
Any egroup deployed with a non-integer, non-`0.5` `LIQ-CURVE-EXP` (explicitly part of the documented parameter space) triggers this on every liquidation of an under-water position in that egroup — a routine, unprivileged liquidator call, with no special conditions required beyond a normal graduated-curve configuration.

### Recommendation
Replace the integer-only `pow`/`(/ exp BPS)` truncation in `calc-liq-factor-exp` with a fixed-point exponentiation routine (e.g., a fixed-point `ln`/`exp` based power function) that correctly handles arbitrary fractional exponents expressed in bps, matching the documented behavior of `LIQ-CURVE-EXP`.

### Proof of Concept
1. DAO configures an egroup with `LIQ-CURVE-EXP = 15000` (1.5x, "aggressive curve" per docs).
2. A borrower's position reaches `current-ltv` such that `calc-liq-factor` yields `liq-pct-linear = 5000` (50%).
3. `calc-liq-factor-exp(5000, 15000)`: expected `(0.5)^1.5 * 10000 ≈ 3535`; actual code computes `(/ 15000 10000) = 1` → `pow(5000,1)/pow(10000,0) = 5000`.
4. This inflated `5000` (vs. correct `3535`) propagates through `calc-liq-factor-bound` and `calc-liq-debt-repay`, producing a higher `liq-penalty` and `max-debt-usd` than the intended curve specifies, letting the liquidator extract excess collateral value from the borrower's position beyond what the configured graduated-liquidation design intends.
