### Title
Unbounded array allocation from unchecked attacker-controlled length in precompiled-contract calldata decoding (`extractBytesArray` / `extractSigArray`) - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
`PrecompiledContracts.extractBytesArray` and `PrecompiledContracts.extractSigArray` read a "count" field directly from attacker-supplied calldata and immediately allocate a two-dimensional `byte[][]` array of that size *before* validating it against the actual size of the calldata buffer, mirroring the CVE-2019-17351 bug class of unrestricted resource consumption driven by a user-controlled size value used for memory allocation/mapping.

### Finding Description
Both helper methods take the array length straight from a `DataWord` decoded out of the raw precompile input and use it to size a heap allocation with no upper bound check relative to `data.length`: [1](#0-0) [2](#0-1) 

`words[offset].intValueSafe()` can return values up to `Integer.MAX_VALUE`; that value is used unchecked to size `new byte[len][]`. Because this happens during calldata *decoding*, it executes before the loop body ever touches `data`, so the allocation attempt (and its cost) is paid up front regardless of whether the rest of the array bounds are even valid. There is no size cap tying `len` to `data.length / itemSize`, unlike other precompiles in the same file (e.g. `ModExp`, which explicitly bounds `baseLen`/`expLen`/`modLen` to `UPPER_BOUND` after `allowTvmOsaka`): [3](#0-2) 

This is directly analogous to the Xen balloon-driver bug: a size value taken from an unprivileged caller is used to drive a resource-mapping/allocation operation with no restriction on how large that resource can be, before any accounting/limit check runs.

### Impact Explanation
An allocation of `new byte[len][]` with `len` near `Integer.MAX_VALUE` requires many gigabytes of heap purely for array-of-array references, which will throw `OutOfMemoryError`. `OutOfMemoryError` is an `Error`, not a checked/normal `RuntimeException` path that the VM interpreter loop is designed to catch and convert into a reverted transaction — large-array OOM conditions in a shared JVM process risk destabilizing or crashing the node process serving all other transactions, which is a node-crash/halt class of impact under the report's acceptance criteria.

### Likelihood Explanation
This code is reached from any signed transaction or contract call that triggers a `CALL`/`STATICCALL`/`DELEGATECALL` to the precompiled address backed by the multisig-signature-validation precompile that uses these decoders (`ValidateMultiSign`/`BatchValidateSign` family), i.e. any unprivileged contract caller can craft calldata with a large declared count field. No special privileges, SR/witness status, or malicious peer/network position are required — it is reachable purely through the TVM precompile-call path.

### Recommendation
Bound the decoded `len` against the actual remaining size of `data` (e.g., `len <= (data.length - headerBytes) / itemSize`) before allocating `bytesArray`/`bytes32Array`, and reject with `Pair.of(false, ...)` when the declared count cannot be backed by the supplied calldata, mirroring the explicit `UPPER_BOUND` check already used in `ModExp.execute`.

### Proof of Concept
Craft a transaction that calls the precompiled address backed by `extractBytesArray`/`extractSigArray` (multisig validation precompile) with calldata whose "count" word (`words[offset]`) is set to a very large value (e.g., `0x7fffffff`) while the remaining calldata buffer is only a few words long. The decoder allocates `new byte[len][]` before any bounds check against the real buffer size, causing excessive heap consumption / `OutOfMemoryError` for a single call, independent of the small amount of energy the caller pays for the call itself.

*Note: exact certainty on the precise clamp behavior of `DataWord.intValueSafe()` and which specific precompile class(es) invoke `extractBytesArray`/`extractSigArray` (only partially confirmed as multisig-validation precompiles) could not be fully verified within available tool calls — a Devin session with full file access would be needed to confirm the exact caller wiring and `intValueSafe()` clamp bounds before treating this as fully proven.*

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
