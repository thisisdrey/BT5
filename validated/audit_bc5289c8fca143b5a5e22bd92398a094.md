### Title
Shielded-key HTTP endpoints omit no-store/no-cache directives, allowing browser/proxy caching of spending and viewing keys - (File: framework/src/main/java/org/tron/core/services/http/RateLimiterServlet.java)

### Summary
The FullNode HTTP API servlets that handle Sapling/shielded key material — `GetSpendingKeyServlet`, `GetExpandedSpendingKeyServlet`, and `GetIncomingViewingKeyServlet` — accept and return sensitive cryptographic secrets (spending keys, expanded spending keys, viewing keys) over plain HTTP `GET`/`POST` without ever setting `Cache-Control: no-store`, `Pragma: no-cache`, or `Expires: 0` headers, exactly the CWE-525 class described in the Flask-AppBuilder advisory (browser/intermediary caching of sensitive response data due to missing cache directives).

### Finding Description
All FullNode HTTP servlets extend `RateLimiterServlet`, whose `service()` override is the single place response headers are set before dispatch: it sets only `Content-Type: application/json; charset=utf-8` and never touches `Cache-Control`/`Pragma`/`Expires`. [1](#0-0) 

Several endpoints reachable by any anonymous HTTP client return or accept highly sensitive shielded-pool key material through this same code path with no caching protection:
- `GetSpendingKeyServlet.doGet`/`doPost` returns a freshly generated Sapling spending key in the JSON body. [2](#0-1) 
- `GetExpandedSpendingKeyServlet.doGet` takes the spending key as a `GET` query parameter (`request.getParameter("value")`) and echoes derived key material back. [3](#0-2) 
- `GetIncomingViewingKeyServlet.doGet` similarly accepts `ak`/`nk` viewing-key material via `GET` query parameters. [4](#0-3) 

Because these are `GET`-able endpoints with query parameters and no explicit no-cache headers, the HTTP responses (and the request URLs containing the secret parameters) are subject to default HTTP caching semantics: they can be stored by browser disk/history cache when accessed interactively, retained by intermediate forward/reverse proxies, or logged verbatim in access logs and browser history on shared or multi-user hosts — the same failure mode as the referenced Flask-AppBuilder login-form advisory.

### Impact Explanation
Any process, browser session, or proxy with access to a node's HTTP API port that fetches these endpoints causes the shielded spending key, expanded spending key, or incoming viewing key to be persisted outside of the caller's control (disk cache, shared-computer browser cache, corporate/ISP proxy cache, or access logs). Recovery of a cached spending key by a second party on a shared machine or through a caching proxy directly yields the ability to spend shielded funds tied to that key — i.e., key disclosure leading to theft of shielded balances, which the report scope explicitly accepts as valid impact.

### Likelihood Explanation
Exploitation requires local/shared access to a browser or intercepting proxy that observed a legitimate call to one of these endpoints (e.g., an operator or wallet tool calling `/wallet/getspendingkey`, `/wallet/getexpandedspendingkey`, or `/wallet/getincomingviewingkey` from a shared workstation, or traffic passing through a caching HTTP proxy). This mirrors the original advisory's own likelihood profile (CVSS AC:L/PR:N/UI:R, "shared computer resources"), i.e., moderate likelihood limited to specific deployment/browsing patterns rather than a remote, unauthenticated network attack.

### Recommendation
In `RateLimiterServlet.service()` (or a dedicated filter applied to key-handling servlets), explicitly set `Cache-Control: no-store, no-cache, must-revalidate, max-age=0`, `Pragma: no-cache`, and `Expires: 0` on all responses — at minimum for `GetSpendingKeyServlet`, `GetExpandedSpendingKeyServlet`, and `GetIncomingViewingKeyServlet`. Additionally, consider rejecting `GET` requests that accept secret key material as query parameters (spending key, `ak`/`nk`) and requiring `POST` with a body, since query strings are more prone to being logged/cached by intermediaries independent of response caching headers.

### Proof of Concept
1. Start a FullNode with the JSON-RPC/HTTP API enabled (default `HttpService`/`RateLimiterServlet` stack, no auth required).
2. From a browser or via a caching HTTP proxy, issue `GET http://<node>:8090/wallet/getspendingkey`.
3. Inspect the response headers: only `Content-Type: application/json; charset=utf-8` is present (confirmed in `RateLimiterServlet.service()`), no `Cache-Control`/`Pragma`/`Expires`.
4. Because caching is not disabled, the browser or an intermediate proxy may store the returned spending key in its cache/history; a second user of the same browser profile or a peer sharing the caching proxy can retrieve the cached response and recover the spending key, or `GET http://<node>:8090/wallet/getexpandedspendingkey?value=<sk>` leaks the input `sk` itself into proxy/access logs and browser history.
