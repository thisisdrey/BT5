### Title
Single-step, unchecked overwrite of account Owner/Active/Witness permissions with no two-step confirmation - (File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java)

### Summary
The reported bug class is a one-step `transferOwnership()` that lets an admin overwrite the privileged `owner` storage slot with a single validated call and no way to undo an incorrect transfer. The closest reachable analog in java-tron is `AccountPermissionUpdateActuator`, which lets any account holder replace their account's `Owner` permission (and `Active`/`Witness` permissions) in a single atomic transaction, directly overwriting the existing permission structure with no staged/two-step confirmation mechanism.

### Finding Description
`AccountPermissionUpdateActuator.execute()` unpacks the `AccountPermissionUpdateContract`, looks up the target `AccountCapsule` by `ownerAddress`, and immediately calls `account.updatePermissions(...)` with the new `Owner`, `Witness`, and `Active` permissions taken directly from the transaction, then persists the account: [1](#0-0) 

`validate()` performs structural checks (`checkPermission`) on key counts, address validity, weight thresholds, and operation bitmaps, but never verifies that the new `Owner` permission's keys are actually controllable by any known/reachable signer other than syntactic well-formedness checks: [2](#0-1) 

Because the new permission set (including the `Owner` permission, which controls the ability to issue further `AccountPermissionUpdateContract` transactions) is written directly into the `AccountStore` in one step with no pending/staged state and no confirmation step from the new key holders, an account owner who submits a transaction with a malformed, unreachable, or attacker-controlled `Owner` permission (e.g., wrong key address, or a permission whose combined key weights are technically valid but whose keys are not held by anyone the owner controls) permanently and irreversibly loses the ability to manage that account, exactly mirroring the `transferOwnership()` root cause described in the report (a privileged pointer overwritten in a single step with no recovery path).

### Impact Explanation
This matches the report's permanent-freezing pattern: once the account's `Owner` permission is overwritten with keys the legitimate operator does not control (mistake, phishing, or compromised second party providing an address), there is no mechanism to reclaim ownership. For witness/committee-relevant accounts, or any account holding TRC10/TRX balances and multi-sig authority, this results in loss of the ability to spend/manage those balances or governance operations, i.e., an unbacked/frozen fund state (funds remain but become permanently unmanageable by the original owner).

### Likelihood Explanation
Any unprivileged transaction broadcaster who owns an account can trigger this by submitting a signed `AccountPermissionUpdateContract`. The validation logic (`checkPermission`) only checks the structural correctness of key lists (distinct addresses, valid TRON address format, weight math, and, for `Active` permissions, the 32-byte operation bitmap), not the real-world reachability of the new keys. A single mistaken transaction is sufficient — this is a normal operator error path, not one requiring privileged access, so likelihood is Medium (user error) rather than a directly exploitable third-party attack, but the impact is severe once triggered.

### Recommendation
Introduce a two-step or timelocked confirmation process for `Owner` permission changes, e.g.:
- Require the transaction to be counter-signed by a threshold of the *proposed* new `Owner` permission's keys before it takes effect (an on-chain "accept" step, analogous to Ownable2Step's `acceptOwnership()`), or
- Stage the new permission set and only activate it after an explicit confirmation transaction signed under the new permission, with a cancellation window in which the current owner can revoke the pending change.

### Proof of Concept
1. Attacker/careless owner crafts an `AccountPermissionUpdateContract` for `ownerAddress = victimAccount`, setting `owner.keys = [wrongOrUncontrolledAddress]` with a valid threshold/weight structure that passes `checkPermission`.
2. Submit the signed transaction; `AccountPermissionUpdateActuator.validate()` passes (all structural checks satisfied) and `execute()` calls `account.updatePermissions(...)` and persists it via `accountStore.put(ownerAddress, account)`, overwriting the account's `Owner` permission in one step. [3](#0-2) 
3. The account's owner permission is now controlled by keys the original operator cannot sign with, and there is no on-chain path to revert or re-claim it — permanently freezing the account's ability to authorize further owner/active-level operations.

Note: I was unable to fully inspect `AccountCapsule.updatePermissions()` itself within the indexed content (the method body was not returned by search), so the exact internal storage mechanics of the permission overwrite could not be independently verified beyond the actuator call site shown above; this should be confirmed directly in `chainbase/src/main/java/org/tron/core/capsule/AccountCapsule.java` in a full checkout.

  private boolean checkPermission(Permission permission) throws ContractValidateException {
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    if (permission.getKeysCount() > dynamicStore.getTotalSignNum()) {
      throw new ContractValidateException("number of keys in permission should not be greater "
          + "than " + dynamicStore.getTotalSignNum());
    }
    if (permission.getKeysCount() == 0) {
      throw new ContractValidateException("key's count should be greater than 0");
    }
    if (permission.getType() == PermissionType.Witness && permission.getKeysCount() != 1) {
      throw new ContractValidateException("Witness permission's key count should be 1");
    }
    if (permission.getThreshold() <= 0) {
      throw new ContractValidateException("permission's threshold should be greater than 0");
    }
    String name = permission.getPermissionName();
    if (!StringUtils.isEmpty(name) && name.length() > 32) {
      throw new ContractValidateException("permission's name is too long");
    }
    //check owner name ?
    if (permission.getParentId() != 0) {
      throw new ContractValidateException("permission's parent should be owner");
    }

    long weightSum = 0;
    List<ByteString> addressList = permission.getKeysList()
        .stream()
        .map(x -> x.getAddress())
        .distinct()
        .collect(toList());
    if (addressList.size() != permission.getKeysList().size()) {
      throw new ContractValidateException(
          "address should be distinct in permission " + permission.getType());
    }
    for (Key key : permission.getKeysList()) {
      if (!DecodeUtil.addressValid(key.getAddress().toByteArray())) {
        throw new ContractValidateException("key is not a validate address");
      }
      if (key.getWeight() <= 0) {
        throw new ContractValidateException("key's weight should be greater than 0");
      }
      try {
        weightSum = addExact(weightSum, key.getWeight());
      } catch (ArithmeticException e) {
        throw new ContractValidateException(e.getMessage());
      }
    }
    if (weightSum < permission.getThreshold()) {
      throw new ContractValidateException(
          "sum of all key's weight should not be less than threshold in permission " + permission
              .getType());
    }
