## Title
Missing slippage/minimum-output protection in `ExchangeInjectContract` and `ExchangeWithdrawContract` enables sandwich attacks on TRC10 exchange liquidity providers - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`ExchangeInjectContract` and `ExchangeWithdrawContract` let any account add or remove liquidity from a TRC10 token-pair exchange pool by specifying only the amount of *one* token (`quant`). The required/received amount of the *other* token is computed at execution time from the pool's live reserve ratio, with no user-supplied bound on that computed amount. This is the exact bug class described in the report (deposit/withdraw without `minAmountOut`/slippage protection), and it is directly reachable by any unprivileged transaction broadcaster.

### Finding Description
In `ExchangeInjectActuator.execute()`, the amount of the "other" token required from the injecting account is derived purely from the current pool balances at execution time: [1](#0-0) 

The corresponding validation performs the same ratio-based computation, again with no caller-supplied minimum/maximum bound on `anotherTokenQuant`: [2](#0-1) 

Likewise, `ExchangeWithdrawActuator.execute()` computes the amount of the other token the withdrawer receives purely from the live pool ratio, with no `expected`/minimum field in the contract or checked in code: [3](#0-2) 

Both `ExchangeInjectContract` and `ExchangeWithdrawContract` only carry `owner_address`, `exchange_id`, `token_id`, and `quant` — no `expected`/minimum-output field: [4](#0-3) 

By contrast, the same-purpose swap contract, `ExchangeTransactionContract`, does have an `expected` minimum field and enforces it in `ExchangeTransactionActuator`, confirming the framework designers were aware of this risk for swaps but omitted it for inject/withdraw: [5](#0-4) 

Because the exchange pool's reserve ratio is a live, on-chain value shared by all callers, and `ExchangeTransactionContract` swaps can move that ratio arbitrarily within a block, an attacker who observes a pending `ExchangeInjectContract`/`ExchangeWithdrawContract` transaction in the mempool can:
1. Front-run it with an `ExchangeTransactionContract` swap that skews `firstTokenBalance`/`secondTokenBalance`.
2. Let the victim's inject/withdraw execute against the skewed ratio — the actuator will compute a manipulated `anotherTokenQuant` value that the victim implicitly accepts because there is no floor/ceiling check.
3. Back-run with an opposite swap to restore the ratio and capture the loss inflicted on the victim (paying more assets to inject, or receiving fewer assets on withdrawal, than at the true market ratio).

### Impact Explanation
A liquidity provider using `ExchangeInjectContract` can be forced to contribute a disproportionately large amount of the "other" token relative to fair value, and a provider using `ExchangeWithdrawContract` can be forced to receive a disproportionately small amount of the "other" token — both are direct, unauthorized value extraction from a victim account executed purely through public transaction ordering, matching the "theft of funds" criterion.

### Likelihood Explanation
Any address can create the token pair or observe an existing pool, broadcast `ExchangeTransactionContract` swaps before and after a victim's pending `ExchangeInjectContract`/`ExchangeWithdrawContract` transaction (visible in the mempool), and profit from the ratio manipulation. No special privilege (SR/witness/committee) is required — only a normal signed transaction from any account holding the relevant TRC10 tokens/TRX, making this Medium-to-High likelihood on any exchange pool with reasonable liquidity depth for the attacker to move.

### Recommendation
Add an `expected`/`min_receive` (for withdraw) or `max_another_token` (for inject) field to `ExchangeInjectContract` and `ExchangeWithdrawContract`, and enforce it in `ExchangeInjectActuator`/`ExchangeWithdrawActuator` the same way `ExchangeTransactionActuator` enforces its `expected` field, rejecting the transaction if the computed `anotherTokenQuant` falls outside the caller's specified bound.

### Proof of Concept
1. Attacker observes a pending `ExchangeInjectContract` from victim V for exchange pool `(A, B)` specifying `tokenId=A`, `quant=Q`.
2. Attacker front-runs with an `ExchangeTransactionContract` selling a large amount of `B` for `A`, sharply increasing `firstTokenBalance`(A)/`secondTokenBalance`(B) skew (subject only to the `expected` check on the attacker's own swap, which the attacker sets to 0).
3. V's `ExchangeInjectContract` executes: `anotherTokenQuant = secondTokenBalance * Q / firstTokenBalance` per `ExchangeInjectActuator.execute()` (lines 71-83) is now computed against the skewed reserves, so V is debited a much larger amount of token B than they would have been at the pre-attack ratio.
4. Attacker back-runs with the reverse `ExchangeTransactionContract` trade, restoring the ratio and pocketing the extra token B extracted from V, minus fees/slippage from their own two trades.
