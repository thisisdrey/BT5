### Title
Slow-loris drip-feed on QUIC uni-streams bypasses `total_stream_read_timeouts` and holds streams open indefinitely - ([File: streamer/src/nonblocking/quic.rs])

### Summary
`handle_connection` re-arms a fresh `wait_for_chunk_timeout` timer on every call to `stream.read_chunks`, rather than enforcing a bound on total wall-clock time to complete a stream. An attacker who writes 1 byte every `wait_for_chunk_timeout - ε` never trips the per-read timeout, so the stream stays "active" and occupies the connection's stream slot for as long as the attacker wishes (bounded only by `max_stream_data_bytes`), without ever incrementing `total_stream_read_timeouts`.

### Finding Description
In `handle_connection` (streamer/src/nonblocking/quic.rs), the read loop is: [1](#0-0) 
Each iteration calls `tokio::time::timeout(wait_for_chunk_timeout, stream.read_chunks(&mut chunks))`. This timeout only measures the gap between two chunk arrivals — it is reset on every successful read. There is no cap on the cumulative time from `PacketAccumulator::new` (`accum.start_time`) to stream completion.

`handle_chunks` only rejects a stream when accumulated `accum.meta.size` exceeds `max_stream_data_bytes`: [2](#0-1) 
Nothing here checks elapsed time. The only elapsed-time check exists after the *entire* stream is finished (`n_chunks == 0`), and it is purely a statistics/telemetry counter, not an enforcement mechanism: [3](#0-2) 
It increments `reassembly_delayed_streams` and `reassembly_delayed_streams_cumulative_delay_us` but takes no corrective action (no early termination, no connection penalty beyond a stat).

Consequently, an attacker can:
1. Open a uni-directional stream on an established (even unstaked) QUIC connection.
2. Write 1 byte, sleep for `wait_for_chunk_timeout - ε` (default `DEFAULT_WAIT_FOR_CHUNK_TIMEOUT` = 2s, per `streamer/src/nonblocking/quic.rs` line 54), and repeat.
3. Each `read_chunks` call succeeds just inside the timeout window, so `stats.total_stream_read_timeouts` is never incremented and the loop never breaks via the `Err(_)` timeout branch.
4. The stream (and the `stats.active_streams` slot it holds, per line 626/709) stays open for as long as the attacker wants, well past `LATE_REASSEMBLY_THRESHOLD` (1.5×RTT), until `max_stream_data_bytes` is reached — at attacker-chosen pacing, not proportional to legitimate transaction transmission time.

The existing `test_quic_stream_timeout` test (streamer/src/nonblocking/quic.rs lines 1332-1370) only validates the trivial case of zero further writes causing a timeout; it does not cover the drip-feed case where periodic sub-timeout writes indefinitely postpone the timeout.

Existing mitigations do not stop this:
- `throttle_stream` / `ConnectionStreamCounter` (streamer/src/nonblocking/stream_throttle.rs) rate-limit how many *new* streams can be opened per interval, but do not bound how long an already-accepted stream may remain open.
- `max_stream_data_bytes` bounds the *amount* of data, not the *time* it can take to deliver that data.
- QUIC's `max_concurrent_uni_streams` transport parameter bounds concurrent streams per connection, but a slow-loris stream still consumes one of those slots for the attacker's chosen duration.

### Impact Explanation
This ties up one entry in the connection's concurrent-uni-stream budget (and the shared `stats.active_streams` counter) for an attacker-controlled duration far exceeding the time needed to actually transmit a transaction. If an attacker repeats this across multiple streams within their per-connection `max_concurrent_uni_streams` limit and across multiple connections up to the unstaked connection limit, they can occupy a meaningful fraction of the unstaked ingress budget with negligible bandwidth cost, degrading legitimate unstaked transaction ingestion — a resource-exhaustion/DoS class issue on the TPU QUIC ingress path.

### Likelihood Explanation
Preconditions are minimal: any unstaked remote client that can open a QUIC connection to the TPU port and open a uni-stream can perform this attack (no stake, no special config, no privileged access required). The attack requires only accurately-timed, tiny writes (1 byte every ~2s), which is trivial to script with any QUIC client library. It is fully repeatable and does not depend on race conditions or luck.

### Recommendation
Enforce an absolute deadline on total stream reassembly time, not just an inter-chunk timeout. For example, wrap the entire per-stream read loop in `tokio::time::timeout(max_total_stream_duration, ...)` measured from `accum.start_time`, where `max_total_stream_duration` is derived from RTT and `LATE_REASSEMBLY_THRESHOLD` (or a fixed generous ceiling), and terminate/close the stream (incrementing a dedicated stat) if exceeded — independent of whether individual chunk reads keep arriving just inside `wait_for_chunk_timeout`.

### Proof of Concept
```rust
// streamer/src/nonblocking/quic.rs (test module)
#[tokio::test(flavor = "multi_thread")]
async fn test_quic_stream_drip_feed_never_times_out() {
    agave_logger::setup();
    let SpawnTestServerResult { join_handle, receiver, server_address, stats, cancel } =
        setup_quic_server(None, QuicStreamerConfig::default_for_tests(), SwQosConfig::default());

    let conn1 = make_client_endpoint(&server_address, None).await;
    let mut s1 = conn1.open_uni().await.unwrap();

    // Drip 1 byte just under the timeout window, repeatedly, well past
    // LATE_REASSEMBLY_THRESHOLD * rtt and past several multiples of
    // DEFAULT_WAIT_FOR_CHUNK_TIMEOUT.
    let drip_interval = DEFAULT_WAIT_FOR_CHUNK_TIMEOUT - Duration::from_millis(200);
    for _ in 0..20 {
        s1.write_all(&[0u8]).await.unwrap();
        sleep(drip_interval).await;
        // Assert the stream was never counted as timed out and is still active.
        assert_eq!(stats.total_stream_read_timeouts.load(Ordering::Relaxed), 0);
        assert_eq!(stats.active_streams.load(Ordering::Relaxed), 1);
    }
    // Total elapsed wall-clock time here is ~20 * 1.8s ≈ 36s, far exceeding
    // rtt * LATE_REASSEMBLY_THRESHOLD, yet the stream/slot is still held open,
    // demonstrating unbounded occupancy driven purely by attacker pacing.

    cancel.cancel();
    drop(receiver);
    join_handle.await.unwrap();
}
```
Expected (buggy) result: the loop completes with `total_stream_read_timeouts == 0` and `active_streams == 1` throughout, proving the stream/slot occupancy is unbounded in wall-clock time and controlled entirely by the attacker's drip cadence rather than legitimate transaction-size-proportional duration.
