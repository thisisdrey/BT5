Based on the investigation, the strongest analog to the M-15 "zero-value edge case causes an unconditional revert on core value flow" bug class is found in the `accrue()` function of Zest's tokenized vault contracts (e.g. `v0-vault-usdc.clar`, `v0-vault-sbtc.clar`, `v0-vault-stx.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdh.clar`), where the `treasury-lp` calculation performs an unguarded subtraction/division that can abort the transaction, and `accrue()` is an unconditional dependency of essentially every user-facing vault entrypoint.

### Title
`accrue()` treasury-lp calculation can underflow/divide-by-zero, permanently bricking all vault operations - (File: `mainnet/contracts/vault/v0-vault-usdc.clar` and sibling vaults)

### Summary
Every state-changing vault function (`deposit`, `redeem`, `transfer`, `system-borrow`, `system-repay`, `socialize-debt`) begins by calling `accrue()`. Inside `accrue()`, the treasury LP-minting share is computed with `(mul-div-down reserve-inc (total-supply) (- (total-assets-preview) reserve-inc))`. Clarity aborts a transaction on unsigned-integer subtraction underflow and on division by zero. If `reserve-inc` (the fee-reserve cut of newly accrued interest) is ever equal to or greater than `total-assets-preview`, this line panics — and because `accrue()` gates literally every subsequent operation, the entire vault becomes permanently unusable.

### Finding Description [1](#0-0) 

The relevant logic (identical across all six vault contracts) is: [2](#0-1) 

`reserve-inc` is computed as `(mul-div-down debt-delta (var-get fee-reserve) BPS)`, i.e. a configurable percentage (`fee-reserve`, settable by DAO governance) of the interest accrued this block. `treasury-lp` is only computed when `reserve-inc > 0`, at which point Clarity evaluates `(- (total-assets-preview) reserve-inc)` as the divisor. Clarity's native `-` operator on `uint` aborts the entire transaction if the result would be negative (underflow), and `/` aborts on divide-by-zero. This is directly analogous to the `BondingTax::swapForAsset` bug: an intended, admin-configurable parameter (`buyTax`/`sellTax` there, `fee-reserve` here) combined with a normal-but-edge-case state (zero contract balance there, near-zero/near-fully-utilized vault assets here) causes a hard revert inside a function that is unconditionally invoked from the protocol's main money-movement path, instead of gracefully skipping the mint (e.g. returning early or clamping).

Every vault function that touches user funds calls `accrue()` first — `deposit`, `redeem`, `transfer`, `system-borrow`, `system-repay`, `socialize-debt` all begin with `(u (try! (accrue)))`, e.g.: [3](#0-2) [4](#0-3) 

If `accrue()` ever panics on this arithmetic edge case, none of `deposit`, `redeem`, `transfer`, borrowing, or repayment can succeed anymore for that vault — permanently freezing all principal and unclaimed yield in it (short of a contract redeploy/migration, since Clarity contracts are immutable).

### Impact Explanation
This lands squarely in the "Critical - protocol insolvency / permanent freezing of funds" category, because unlike the original finding (which only DoSed the tax-swap side-effect of buy/sell while leaving the core trade path usable in principle), here the reverting code sits inside `accrue()`, a hard dependency of every fund-moving vault function. Once triggered, depositors cannot `redeem` their principal, borrowers cannot `system-repay`, and the DAO cannot `socialize-debt` — the vault is bricked.

### Likelihood Explanation
Triggering requires `reserve-inc >= total-assets-preview` at some accrual step. `fee-reserve` is a DAO-configurable parameter (not attacker-controlled) but setting it to a high percentage is a normal, intended admin action (directly mirroring the original report's premise that setting `buyTax`/`sellTax` to an edge value like `0` is "a very valid and intuitive value to set"). Combined with a vault state where utilization is high and `assets` (idle liquidity) is at or near zero — which can arise from ordinary borrowing activity draining available liquidity — the accrued interest reserve cut can catch up to or exceed the tracked total-assets figure, especially over multiple accrual periods without a fresh deposit. This does not require a DAO compromise, oracle manipulation, or leaked keys; it only requires a plausible admin-set fee parameter plus organic vault utilization, similar in spirit to the original finding's "easily manipulated by an attacker" premise. I was not able to fully verify, within the available tool budget, the exact numeric bound on `fee-reserve`/utilization needed to reach the underflow/zero-divisor condition in this session (the precise definitions of `total-assets-preview` and `mul-div-down` were not retrieved), so this should be verified against those definitions before being treated as fully proven.

### Recommendation
Guard the treasury-lp computation so it cannot revert on this edge case, e.g.:
```clarity
(treasury-lp (if (and (> reserve-inc u0) (> (total-assets-preview) reserve-inc))
                (mul-div-down reserve-inc (total-supply) (- (total-assets-preview) reserve-inc))
                u0))
```
This mirrors the original report's recommended fix of returning a benign `(false, 0)`/no-op instead of reverting when the divisor would be non-positive.

### Proof of Concept
1. DAO sets `fee-reserve` to a high value (e.g. via governance proposal, a normal parameter-setting action, not a compromise) on a vault.
2. Borrowers drive `system-borrow` utilization up so `assets` (idle liquidity) trends toward zero while `total-borrowed` dominates `total-assets-preview`.
3. Over successive blocks, interest accrual increases `debt-delta`, and thus `reserve-inc = debt-delta * fee-reserve / BPS`, while `total-assets-preview` stays flat or shrinks (e.g. via redemptions draining `assets`).
4. Once `reserve-inc >= total-assets-preview` in a given `accrue()` call, the subtraction `(- (total-assets-preview) reserve-inc)` underflows (or the subsequent division divides by zero), aborting the transaction.
5. Because `accrue()` is called at the start of `deposit`, `redeem`, `transfer`, `system-borrow`, `system-repay`, and `socialize-debt`, every subsequent call to these functions on the vault reverts, permanently freezing all deposited funds.
