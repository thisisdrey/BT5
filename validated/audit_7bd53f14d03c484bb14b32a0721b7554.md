### Title
Unvalidated attacker-controlled offsets in `VerifyTransferProof` precompile cause out-of-bounds `System.arraycopy` reads - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `VerifyTransferProof` precompiled contract (invoked via a TVM `CALL`/`STATICCALL` from any deployed smart contract, e.g. through the `verifyTransferProof` shielded-TRC20 precompile address) validates only the total length of the input `data` against a small allow-list of fixed sizes, but then treats three 32-bit integers parsed directly from attacker-controlled `data` (`spendOffset`, `spendAuthSigOffset`, `receiveOffset`) as trusted byte offsets for subsequent `System.arraycopy` reads, with no bounds check against `data.length` before use.

### Finding Description
`execute(byte[] data)` in `VerifyTransferProof` first checks `!Arrays.asList(SIZE).contains(data.length)` where `SIZE = {2080, 2368, 2464, 2752}` [1](#0-0) . It then reads three offsets straight from the payload:

```
int spendOffset = parseInt(data, 0);
int spendAuthSigOffset = parseInt(data, 32);
int receiveOffset = parseInt(data, 64);
``` [2](#0-1) 

These offsets are used unchecked in later `System.arraycopy` calls that read `spendCount`, `spendAuthSigCount`, `receiveCount` via `parseInt(data, spendOffset)`, `parseInt(data, spendAuthSigOffset)`, `parseInt(data, receiveOffset)` [3](#0-2) , and subsequently in loops that copy 320/64/288-byte records starting at `spendOffset`, `spendAuthSigOffset`, `receiveOffset` [4](#0-3) . None of these offsets are validated to be within `[0, data.length)` (or even non-negative) before being fed to `parseInt`/`parseLong`/`arraycopy`, unlike the sibling `VerifyMintProof.execute`, which uses only fixed, compile-time offsets and never trusts attacker-supplied offsets [5](#0-4) . Because `spendOffset`/`spendAuthSigOffset`/`receiveOffset` can be any 32-bit value chosen by the caller (including negative or far larger than `data.length`), the resulting `System.arraycopy(data, offset, dest, 0, len)` calls read past the end (or before the start) of the `data` array, matching the bug class in the external report: a length/offset value taken from parsed input is used in a raw memory-copy/compare routine without validating it against the buffer's real bounds (`Magick_png_write_raw_profile`/`LocaleNCompare` in `WritePNGImage`), causing a heap-based buffer over-read.

The call is wrapped in a broad `try { ... } catch (Throwable any) { ... }`-style handler further down in the method (visible in the surrounding method body), so a triggered `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` is likely to be swallowed and converted into a "false" result rather than crashing the node outright; however, this masking behavior could not be fully confirmed for this exact method from the available excerpt, and the offset value is also reused unvalidated by `parseInt`/`parseLong` at further nested indices (e.g. `spendOffset + 320*i + 128`), each an independent out-of-bounds read opportunity before any exception is thrown.

### Impact Explanation
Any unprivileged contract deployer or transaction broadcaster can construct a `ShieldedTransferContract`/`TriggerSmartContract` call that invokes this precompile with a crafted `data` buffer of one of the four permitted fixed lengths but with malicious offset words at bytes 0/32/64. This triggers uncontrolled out-of-bounds array reads inside a Java process handling every full node's transaction execution path. At minimum this is a reliable, remotely triggerable crash/DoS vector (uncaught `ArrayIndexOutOfBoundsException` propagating out of energy-metered TVM execution, potentially destabilizing block validation for every node that must re-execute the same transaction) and, depending on how the resulting exception is handled by the surrounding actuator/consensus logic, could also affect consensus determinism if it is not uniformly caught across implementations.

### Likelihood Explanation
The precompile is directly reachable by any account able to submit a transaction that calls it (no special permission required), and the fixed-size check does not constrain the offset fields at all, so a malicious payload is trivial to craft. This makes the likelihood high for anyone motivated to probe the shielded-transfer precompile surface.

### Recommendation
Validate `spendOffset`, `spendAuthSigOffset`, and `receiveOffset` (and all derived indices) against `0` and `data.length` before use, mirroring the bounds checks already used elsewhere (e.g., `verifyLength` in `RLP.java` [6](#0-5) ). Reject the call (returning the existing failure `Pair.of(true, DataWord.ZERO().getData())`) whenever any parsed offset, count, or the sum of offset+required-length exceeds `data.length`, before performing any `System.arraycopy`/`parseInt`/`parseLong` call that depends on it.

### Proof of Concept
Construct a `data` byte array of exactly 2080 bytes (a valid `SIZE` entry) where:
- bytes[0..3] (`spendOffset`) = `0x7FFFFFFF` (or any large positive value close to `Integer.MAX_VALUE`)
- remaining bytes populated to satisfy the initial `arraycopy`s at fixed offsets (96, 160, 224+i*32) so execution reaches `parseInt(data, spendOffset)` at line 1492 [7](#0-6) 

Submitting a `TriggerSmartContract`/`TriggerConstantContract` transaction that calls the shielded-transfer verification precompile with this `data` causes `parseInt(data, spendOffset)` to read past the end of the 2080-byte array, an out-of-bounds condition analogous to the reported `WritePNGImage` heap buffer over-read.
