### Title
Attacker can dust-transfer deposit tokens to fill a victim's per-account token list to `MAX_TOKENS_PER_USER`, blocking the victim from depositing new collateral types, minting new debt, and receiving msdToken transfers - (File: contracts/Pool.sol)

### Summary
The referenced CVE is an availability/DoS bug (a repeatable crash/hang of the server). The closest reachable Metronome analog is the per-account token-list cap in `Pool`: `MAX_TOKENS_PER_USER = 30` is enforced by `onlyIfAdditionWillNotReachMaxTokens`, which reverts with `UserReachedMaxTokens` once `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` [1](#0-0) [2](#0-1) . Entries are added not only on deposit/mint but also on ordinary `DepositToken` transfers: `DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's prior balance of that token is zero [3](#0-2) . An unprivileged attacker can therefore deposit dust into every `DepositToken` of a pool and transfer 1 wei of each `msdToken` to a victim, filling the victim's list without their consent.

### Finding Description
`addToDepositTokensOfAccount` is only callable by a registered deposit token (`_revertIfSenderIsNotDepositToken`), but the trigger is the generic ERC20 `transfer`/`transferFrom` path, which any holder can call [4](#0-3) [5](#0-4) . Once the victim's combined list reaches 30:

- `DepositToken.deposit` → `_mint` reverts on any token the victim does not already hold, blocking all new collateral types [6](#0-5) .
- `DebtToken.issue` reverts on any synthetic the victim has not borrowed before (same `addToDebtTokensOfAccount` path at `Pool.sol:204-208`), blocking new borrows and leverage into new synths.
- Any `msdToken` `transfer`/`transferFrom` to the victim reverts, so the victim cannot receive collateral shares (e.g., OTC transfers, gateway deposits routed to their address) and cannot be paid seized collateral they don't already hold.
- During `Pool.liquidate`, `DepositToken.seize` routes collateral shares to the liquidator via the same add path; a liquidator whose list is full cannot execute the liquidation for a new collateral token (secondary effect, easily worked around by other liquidators).

There is no guard distinguishing "user-initiated" additions from forced dust additions; the set is keyed only on balance transitions `0 → >0` [7](#0-6) .

### Impact Explanation
Temporary denial of service against a targeted account: the victim cannot open positions in new collateral or debt types and cannot receive msdTokens until they free slots. The victim can recover by fully withdrawing or transferring out the dusted tokens (balance → 0 triggers `removeFromDepositTokensOfAccount` [8](#0-7) ), but each removal costs gas and oracle-priced withdrawal flow, and the attacker can re-dust the slot, so the griefing is repeatable at asymmetric cost. This maps to the "temporary freezing of funds / liveness" acceptance bucket rather than permanent loss.

### Likelihood Explanation
Cost to the attacker is bounded: one dust deposit plus one transfer per deposit token registered in the pool (must hold ≥1 wei of each underlying; no pause/active flag prevents deposits on active tokens). No privileged role, oracle manipulation, or reentrancy is needed — just public `deposit` + `transfer` calls. Likelihood of occurrence is moderate; impact is limited to feature-availability on new token types and is user-recoverable, keeping overall severity Medium-Low.

### Recommendation
Skip the account-list addition for dust/negligible amounts, or decouple balance tracking from the capped list: e.g., only add to `depositTokensOfAccount`/`debtTokensOfAccount` when the recipient explicitly deposits/issues (mint path), not on inbound `transfer`s, or add a minimum-value threshold. Alternatively, allow `seize`/`liquidate`-driven additions to bypass the cap so liquidation liveness is never list-bound.

### Proof of Concept
Reproducible in the existing Hardhat setup (pattern already exercised in `test/Pool.test.ts:1491-1520`):

```ts
// contracts: pool with N deposit tokens registered (N >= MAX_TOKENS_PER_USER)
const max = (await pool.MAX_TOKENS_PER_USER()).toNumber(); // 30

for (const dt of allDepositTokens.slice(0, max)) {
  const underlying = await ethers.getContractAt('ERC20', await dt.underlying());
  await underlying.mint(attacker.address, 1);
  await underlying.connect(attacker).approve(dt.address, 1);
  await dt.connect(attacker).deposit(1, attacker.address);   // mints 1 wei msdToken
  await dt.connect(attacker).transfer(victim.address, 1);    // adds dt to victim's list
}

// victim now has 30 entries; any new-token interaction reverts
await expect(
  newDepositToken.connect(victim).deposit(parseEther('1'), victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

await expect(
  newDebtToken.connect(victim).issue(victim.address, parseEther('1'))
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// inbound msdToken transfers to victim for tokens not yet held also revert
await expect(
  anotherDepositToken.connect(attacker).transfer(victim.address, 1)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

        address sender_,
        address recipient_,
        uint256 amount_
    ) private updateRewardsBeforeTransfer(sender_, recipient_) {
        if (sender_ == address(0)) revert TransferFromTheZeroAddress();
        if (recipient_ == address(0)) revert TransferToTheZeroAddress();

        uint256 _senderBalanceBefore = balanceOf[sender_];
        if (_senderBalanceBefore < amount_) revert TransferAmountExceedsBalance();
        uint256 _recipientBalanceBefore = balanceOf[recipient_];

        unchecked {
            balanceOf[sender_] = _senderBalanceBefore - amount_;
            balanceOf[recipient_] += amount_;
        }

        emit Transfer(sender_, recipient_, amount_);

        // Add this token to the deposit tokens list if the recipient is receiving it for the 1st time
        if (_recipientBalanceBefore == 0 && amount_ > 0) {
            pool.addToDepositTokensOfAccount(recipient_);
        }

        // Remove this token from the deposit tokens list if the sender's balance goes to zero
        if (amount_ > 0 && balanceOf[sender_] == 0) {
            pool.removeFromDepositTokensOfAccount(sender_);
        }
    }
