### Title
Weight double-counting for duplicate signer with distinct signature bytes in `ValidateMultiSign` precompile bypasses multisig threshold - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The `ValidateMultiSign` TVM precompiled contract, used by smart contracts to verify that a set of signatures meets an account's multi-signature `Permission` threshold, contains a deduplication flaw that allows the weight of a single key to be counted more than once when the same recovered address supplies two syntactically different signature byte strings for the same hash (e.g. via ECDSA signature malleability, `(r, s)` vs `(r, n-s)`). This lets a caller satisfy a `permission.getThreshold()` check without possessing the number of genuinely distinct authorized signers required — analogous to the reported issue where a claimant not actually present in the required "winners" set is still treated as eligible.

### Finding Description
`ValidateMultiSign.execute()` iterates over the supplied signature array and, for each signature, recovers the signer address and accumulates `weight`: [1](#0-0) 

The deduplication logic is:
```
if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
  if (ByteArray.matrixContains(executedSignList, sign)) {
    continue;
  }
  MUtil.checkCPUTime();
}
long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
...
totalWeight += weight;
executedSignList.add(sign);
executedSignList.add(recoveredAddr);
```
This only skips a signature (`continue`) when **both** the recovered address **and** the exact merged `sign` bytes have been seen before. If the same address is seen again but with *different* signature bytes (i.e., a second, distinct valid signature over the same hash produced by the same private key — for example a non-canonical/malleable ECDSA signature `(r, n-s)` alongside the canonical `(r, s)`), execution falls through past the `if` block (after only performing a `MUtil.checkCPUTime()` DoS guard) and re-adds `weight` for that same key to `totalWeight`. Compare this with `TransactionCapsule.checkWeight()`, the equivalent logic used for on-chain transaction signature verification, which throws a `PermissionException` ("has signed twice!") whenever the same recovered address appears more than once, regardless of the raw signature bytes: [2](#0-1) 

The precompile's weaker, byte-exact check means an attacker holding a single authorized key (with some non-zero weight below `permission.getThreshold()`) can supply the same signature twice in two malleable encodings and have their weight counted twice (or up to `MAX_SIZE = 5` times), inflating `totalWeight` past `permission.getThreshold()` even though only one real signer participated. This precompile is reachable by any TVM contract call from any transaction sender (unprivileged), since precompiled contracts are invoked via ordinary `CALL`/`STATICCALL` opcodes with attacker-controlled calldata, as exercised in the existing test suite: [3](#0-2) 

### Impact Explanation
Smart contracts on TVM (e.g. multisig wallets, custody contracts, DAOs) that rely on `ValidateMultiSign` to gate privileged operations (fund transfers, ownership changes, approvals) can be tricked into believing that a threshold-satisfying set of independent co-signers approved an action when in fact only a single authorized key (with insufficient standalone weight) produced the approval by exploiting signature malleability to be double-counted. This constitutes unauthorized execution of privileged/fund-moving operations gated by multisig — a concrete unauthorized account operation / theft-of-funds vector for contracts built on top of this precompile.

### Likelihood Explanation
Exploitation only requires: (1) an account/`Permission` configuration where a single key's weight is less than the threshold but a second, differently-encoded (malleable) signature from the same key can be produced, and (2) invoking a TVM contract that calls `ValidateMultiSign`. Generating a second valid ECDSA signature for the same message/key (`s` vs `n-s`) is trivial and can be done offline without any special access — this is standard signature malleability, not a cryptographic break. No privileged role is required to trigger this; any user who deploys or calls a contract dependent on this precompile can attempt it.

### Recommendation
In `ValidateMultiSign.execute()` (and the analogous `BatchValidateSign` precompile, which should be checked for the same pattern), deduplicate strictly by `recoveredAddr` alone — mirroring `TransactionCapsule.checkWeight()` — rather than by the combination of address and raw signature bytes. Any repeated `recoveredAddr` should cause the second occurrence to be skipped (or the whole call to fail), regardless of whether the signature bytes differ.

### Proof of Concept
1. Create an account with an `Active` `Permission` of `threshold = T` containing key `K` with `weight = w < T` (and possibly other keys never actually used).
2. Off-chain, produce two malleable ECDSA signatures for the same `hash` using `K`'s private key: canonical `(r, s)` and non-canonical `(r, n-s)` (both recover to `K`'s address under `recoverAddrBySign`).
3. Deploy/call a contract that invokes the `ValidateMultiSign` precompile, passing both signatures in the `signatures` array (as shown in `ValidateMultiSignContractTest.testDifferentCase`, which already demonstrates the harness for supplying multiple signatures at `framework/src/test/java/org/tron/common/runtime/vm/ValidateMultiSignContractTest.java:68-156`).
4. Because `recoveredAddr` is identical but merged `sign` bytes differ, the dedup `continue` is skipped and `weight` (`w`) is added twice, so `totalWeight = 2w`.
5. If `2w >= T` while `w < T`, the precompile returns `dataOne()` (success), incorrectly validating the multisig threshold with only one real signer.
