Based on my research, I found a valid analog in Bazel's own zip-parsing code (ijar), which is structurally identical to the FreeRDP `RLEDECOMPRESS` bug class: parsing attacker-controlled length fields without bounds-checking against the actual buffer before dereferencing.

### Title
Out-of-bounds heap read in ijar's ZIP central-directory extra-field parser - (File: `third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` in ijar's ZIP parser walks a "extra fields" sub-record list using an attacker-controlled `data_size` for each record, with no check that the record (or its 2-byte header + `data_size` payload) actually fits within the bounds of the mapped input file or even within `extra_field_length`. This allows a malicious jar (an ijar dependency artifact, such as a precompiled/prebuilt jar consumed via `java_import`, `run_ijar`, or a downloaded `http_archive`/`http_jar`) to make ijar read past the end of the mapped file buffer.

### Finding Description
In `third_party/ijar/zip.cc`, `ProcessCentralDirEntry` reads the central directory header fields directly from the mmapped zip bytes: [1](#0-0) 

After reading `file_name_length` and `extra_field_length`, it advances `p` past the file name and then loops over "extra field" records between `extra_p` and `p` (i.e., bounded only by the untrusted `extra_field_length` from the header, not by remaining bytes in the actual mapped file): [2](#0-1) 

Unlike `ProcessLocalFileEntry`, which explicitly calls `EnsureRemaining()` before consuming `file_name_length` and `extra_field_length` bytes (`third_party/ijar/zip.cc:360-370`), the central-directory extra-field loop performs **no equivalent bounds check**. `get_u2le(extra_p)` reads a 2-byte `header_id`/`data_size` pair unconditionally, and `extra_p += data_size` can jump `extra_p` arbitrarily far — including past the actual mapped buffer — with the loop condition `while (extra_p != p)` never terminating cleanly if `data_size` overshoots `p`, causing further out-of-bounds reads (`get_u2le`, and for a spoofed ZIP64 tag, `get_u8le(extra)`) on each iteration until it happens to hit unmapped memory or wraps.

This mirrors the FreeRDP `RLEDECOMPRESS` bug class exactly: a size/length field taken directly from untrusted input is used to advance a read cursor and dereference memory without validating it against the actual buffer bounds, in contrast to the sibling function (`ProcessLocalFileEntry`) which does perform such validation via `EnsureRemaining`.

### Impact Explanation
The attacker here is an unprivileged party who can publish/serve a malicious `.jar` file that ends up being processed by ijar — e.g., a `java_import`'s prebuilt/precompiled jar attribute, a jar fetched by `http_jar`/`http_archive` and later run through `java_common.run_ijar`, or any dependency jar Bazel strips for interface-jar generation. Since ijar operates on the raw bytes of that untrusted jar, a crafted central directory entry can drive `extra_p`/`p` outside the bounds of the file mapping, causing the process (`ijar`, invoked as a Bazel build action) to read out-of-bounds heap/mapped memory. Depending on layout, this can crash the build action (denial of service) or, more concerning per the ZIP64 branch, cause bogus (out-of-bounds-derived) `compressed_size`/`uncompressed_size`/`offset` values to be used downstream to seek and copy bytes from other regions of the mapped file into the resulting output jar — i.e., data confusion in the build's ABI-interface jar.

### Likelihood Explanation
This requires only that the attacker control the *contents* of a jar file that gets run through ijar — a very common workflow for any external/pre-built Java dependency. No control of the build machine, credentials, or trusted BUILD/.bzl files is required, and no checksum verifies the *internal structure* of an already-integrity-verified jar (a sha256/integrity check on the whole archive does not protect against malformed internal zip structure once the bytes match the pinned digest — the attacker who publishes the pinned artifact controls its internal bytes by construction).

### Recommendation
Add the same bounds validation used in `ProcessLocalFileEntry` (`EnsureRemaining`-style checks) to the central-directory extra-field walking loop in `ProcessCentralDirEntry`: before reading each `ExtraField` header, verify at least 4 bytes remain within `extra_field_length` (and within the mapped file), and after reading `data_size`, verify `extra_p + data_size` does not exceed `p` (end of the declared extra-fields region) nor the mapped file end, aborting parsing with an error otherwise — analogous to the bounds checks already present in `third_party/ijar/zip_headers.h`'s `ExtraField::find` used by singlejar.

### Proof of Concept
A reproducible JUnit/C++ test (e.g., in `third_party/ijar/test/`) can construct a minimal ZIP file with:
1. One local file header.
2. A central directory header whose `extra_field_length` declares a small extra-fields region, but whose first "extra field" record encodes a `data_size` (e.g., `0xFFFF`) that is larger than the space remaining in the file/mapped region.
3. Running `ijar` (or `InputZipFile::ProcessCentralDirEntry` directly, as `output_jar_simple_test.cc`'s `MalformedExtraField` test already does for the analogous singlejar code path) on this file under AddressSanitizer to demonstrate the heap-buffer-overflow read, comparable to the existing `CreateZipWithMalformedExtraField`/`MalformedExtraField` test pattern in `src/tools/singlejar/output_jar_simple_test.cc:1179-1236`, which shows singlejar already guards against this but ijar's `zip.cc` does not. bool InputZipFile::ProcessCentralDirEntry(const u1 *&p, u8 *compressed_size,
                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
  const u1 *extra_p = p;
  p += extra_field_length;
  while (extra_p != p) {
    const u2 header_id = get_u2le(extra_p);
    const u2 data_size = get_u2le(extra_p);
    const u1 *extra = extra_p;
    extra_p += data_size;
    if (header_id == ZIP64_EXTRA_FIELD_TAG) {
      if (*uncompressed_size == U4_MAX) {
        *uncompressed_size = get_u8le(extra);
      }
      if (*compressed_size == U4_MAX) {
        *compressed_size = get_u8le(extra);
      }
      if (*offset == U4_MAX) {
        *offset = get_u8le(extra);
      }
    }
  }
  p += file_comment_length;
  return true;
}
