### Title
Unbounded growth of `DelegatedResourceAccountIndexCapsule` to/from-account lists enables DoS on freeze/unfreeze operations - (File: `actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java`, `actuator/src/main/java/org/tron/core/actuator/UnfreezeBalanceActuator.java`, `chainbase/src/main/java/org/tron/core/capsule/DelegatedResourceAccountIndexCapsule.java`)

### Summary
When resource delegation optimization is not active (`DynamicPropertiesStore.supportAllowDelegateOptimization() == false`), `FreezeBalanceActuator` and `UnfreezeBalanceActuator` maintain a legacy `DelegatedResourceAccountIndexCapsule` per account containing plain `List<ByteString>` fields (`toAccountsList` / `fromAccountsList`). Any unprivileged account can grow these lists without bound by repeatedly delegating small amounts of bandwidth/energy to a large number of distinct freshly-generated receiver addresses. Every subsequent unfreeze/undelegate operation that touches this index performs an `ArrayList.remove(Object)` call, which is an O(n) linear scan comparing `ByteString` contents, mirroring the `ArrayLib.getItemIndex` linear-scan pattern in the external report.

### Finding Description
In `FreezeBalanceActuator.delegateResource`, whenever `!dynamicPropertiesStore.supportAllowDelegateOptimization()`, the owner's and receiver's `DelegatedResourceAccountIndexCapsule` are fetched and a new entry is appended unconditionally (as long as it isn't already present) via `addToAccount`/`addFromAccount`: [1](#0-0) 

Because a malicious owner can generate an unlimited number of fresh receiver addresses and issue many small `FreezeBalanceContract` (with delegation) transactions, both the owner's `toAccountsList` and every distinct receiver's `fromAccountsList` can be inflated arbitrarily. The `addToAccount`/`addFromAccount` helpers simply append to the protobuf repeated field with no size cap: [2](#0-1) 

When resources are later unfrozen via `UnfreezeBalanceActuator.execute` (non-optimized path), the code copies the entire list into a fresh `ArrayList`, then calls `List.remove(Object)`, which linearly scans the whole list for a matching `ByteString` before removing it and rewriting the full list back to the store: [3](#0-2) 

This directly parallels the `ArrayLib.getItemIndex`/`removeItem` pattern flagged in the external report: an attacker inflates an array reachable by third parties, and any subsequent removal operation must scan (and rewrite) the whole array, which grows the cost of that operation linearly with attacker-controlled list size. Unlike the bounded `unfrozenV2List` (capped at `UNFREEZE_MAX_TIMES = 32` in `UnfreezeBalanceV2Actuator`), no equivalent cap exists on `DelegatedResourceAccountIndexCapsule.toAccountsList`/`fromAccountsList` in this legacy code path.

### Impact Explanation
An attacker can target any receiver address (including their own or a victim's) by issuing many `FreezeBalanceContract` delegate transactions from newly created sender addresses, each delegating a minimal frozen balance to the same receiver. This inflates the victim receiver's `fromAccountsList` without the victim's consent. Every time the victim (or anyone interacting with that index, e.g., during subsequent delegate/undelegate processing) triggers a read-modify-write of that index entry, the node must deserialize, linearly scan, and re-serialize an ever-growing list, increasing CPU/storage cost for that specific account's delegation bookkeeping and increasing the size of the value stored under a single DB key. In the worst case this raises resource-metering costs disproportionately and can degrade or block further delegate/undelegate processing for the targeted account, which affects the ability to unfreeze/reclaim frozen TRX (funds temporarily immobilized).

### Likelihood Explanation
This requires the chain to still be operating with `AllowDelegateOptimization` disabled (the legacy code path is still present and reachable when that dynamic property is off), and requires the attacker to submit many freeze/delegate transactions, each incurring bandwidth/energy costs and a minimum frozen balance, so the attack has a linear cost to the attacker as well. On networks where the optimization proposal has already been activated (which appears to be the common expectation for mainnet), the vulnerable branch is not executed, reducing real-world likelihood. The finding is a valid dormant/analog issue in the legacy delegation-index code path rather than an actively exploited mainnet vector.

### Recommendation
Replace the legacy `List<ByteString>` based `DelegatedResourceAccountIndexCapsule.toAccountsList`/`fromAccountsList` membership tracking with a per-pair keyed store (as already done in the V2 delegation path in `DelegateResourceProcessor`/`UnDelegateResourceProcessor`, which use `Bytes.concat(V2_FROM_PREFIX/V2_TO_PREFIX, ...)` keys instead of in-list scans), or enforce a hard cap on the number of distinct delegation counterparties tracked per account in the legacy path, deprecating/disabling the unbounded-list code entirely once optimization is universally active.

### Proof of Concept
1. Ensure `AllowDelegateOptimization` is not yet enabled on the target network (`supportAllowDelegateOptimization() == false`).
2. From attacker-controlled address `A`, freeze a minimal balance and delegate bandwidth to victim receiver `V` via `FreezeBalanceContract` — this appends `V` into `A`'s `toAccountsList` and `A` into `V`'s `fromAccountsList` (`FreezeBalanceActuator.delegateResource`, lines 320-345).
3. Repeat step 2 from thousands of newly generated addresses `A1..An`, all delegating to the same `V`, inflating `V`'s `fromAccountsList` to size `n` with no upper bound enforced by `addFromAccount`.
4. Any subsequent unfreeze/undelegate operation touching `V`'s index (`UnfreezeBalanceActuator.execute`, lines 162-188) must copy, linearly scan, and rewrite the full `n`-sized list, causing execution cost to scale linearly with the attacker-inflated list size.

  public void addFromAccount(ByteString fromAccount) {
    this.delegatedResourceAccountIndex = this.delegatedResourceAccountIndex.toBuilder()
        .addFromAccounts(fromAccount)
        .build();
  }

  public void removeFromAccount(ByteString fromAccount) {
    if (getFromAccountsList().contains(fromAccount)) {
      List<ByteString> fromList = new ArrayList<>(getFromAccountsList());
      fromList.remove(fromAccount);
      setAllFromAccounts(fromList);
    }
  }

  public List<ByteString> getToAccountsList() {
    return this.delegatedResourceAccountIndex.getToAccountsList();
  }

  public void setAllToAccounts(List<ByteString> toAccounts) {
    this.delegatedResourceAccountIndex = this.delegatedResourceAccountIndex.toBuilder()
        .clearToAccounts()
        .addAllToAccounts(toAccounts)
        .build();
  }

  public void addToAccount(ByteString toAccount) {
    this.delegatedResourceAccountIndex = this.delegatedResourceAccountIndex.toBuilder()
        .addToAccounts(toAccount)
        .build();
  }

  public void removeToAccount(ByteString toAccount) {
