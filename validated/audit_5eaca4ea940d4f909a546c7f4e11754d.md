Based on my investigation, there is a legitimate structural analog to the Beanstalk `plenty`-loss bug in marginfi's emissions accounting.

### Title
Full withdrawal/repay permanently burns unclaimed `emissions_outstanding` without settlement - ([File: programs/marginfi/src/state/marginfi_account.rs])

### Summary
Beanstalk's bug loses a user's accrued `plenty` because an early return skips crediting the reward before the position is reset. Marginfi has a structurally identical pattern: `Balance::close()` unconditionally zeroes every field of the `Balance` struct — including `emissions_outstanding`, the unclaimed-rewards accumulator — and is invoked by `BankAccountWrapper::withdraw_all` / `repay_all` without first requiring that outstanding emissions be settled or claimed.

### Finding Description
`Balance` tracks `emissions_outstanding`, unclaimed emissions rewards accrued for a position [1](#0-0) . `Balance::close()` resets the whole struct to `empty_deactivated()`, which sets `emissions_outstanding` back to `I80F48::ZERO` unconditionally [2](#0-1) [3](#0-2) .

`BankAccountWrapper::withdraw_all` only checks that the asset amount is positive and the liability amount is zero before calling `balance.close()` — it never checks or settles `emissions_outstanding`: [4](#0-3) . `repay_all` follows the same pattern [5](#0-4) .

Notably, the error code `CannotCloseOutstandingEmissions` ("Cannot close balance because of outstanding emissions") exists in the error enum [6](#0-5) , which indicates the protocol's own design intent is that a balance should not be closable while emissions are outstanding. However, this check does not appear anywhere in `withdraw_all`, `repay_all`, or `close_balance` in `marginfi_account.rs` — a `grep` across the whole repo shows `CannotCloseOutstandingEmissions` is referenced only in `errors.rs` and a test-utility file, never actually invoked from any instruction path. This mirrors the Beanstalk root cause exactly: the safeguard that should prevent loss of the reward is absent from the code path that resets/clears the position.

Since `emissions_outstanding` is only settled (paid out) via a dedicated `lending_account_withdraw_emissions`-style claim instruction (separate from deposit/withdraw), a user who calls a full withdraw (`withdraw_all`) or full repay (`repay_all`) without first claiming pending emissions will have that unclaimed balance permanently wiped when `close()` resets the `Balance` slot.

### Impact Explanation
This causes a **loss of funds** for any user who has unclaimed emissions accrued on a bank position and executes a full withdrawal or full repay in the same or later transaction as reaching zero balance — the emissions value is destroyed with no path to recovery, since the `Balance` struct slot is fully reset and the position is deactivated. This is directly reachable by any ordinary unprivileged user through the standard withdraw/repay flow, matching the "unprivileged-user, core accounting path" scope.

### Likelihood Explanation
Likelihood is moderate-to-high in practice: any bank with active emissions configured, combined with a user who withdraws/repays their full position without first claiming, triggers the loss. This is a normal user action (full exit from a position), not an edge-case or adversarial sequence, making it easy to hit unintentionally.

### Recommendation
Before calling `balance.close()` in `withdraw_all`, `repay_all`, and `close_balance`, require that `emissions_outstanding` is zero (returning `MarginfiError::CannotCloseOutstandingEmissions` if not), or automatically settle/transfer outstanding emissions to the user as part of the close path rather than silently zeroing the accumulator.

### Proof of Concept
Conceptually:
1. User deposits into a bank that has emissions configured; emissions accrue over time into `balance.emissions_outstanding`.
2. Before calling the emissions-claim instruction, the user calls `lending_account_withdraw` with `withdraw_all = true` (or `repay_all`), which invokes `BankAccountWrapper::withdraw_all` → `balance.close()`.
3. `close()` resets `emissions_outstanding` to zero along with `asset_shares`/`liability_shares`, with no check on emissions state.
4. The user can no longer claim the previously accrued emissions — they are permanently lost, even though the position and its unclaimed rewards existed moments before.

I could not find any current instruction wiring `CannotCloseOutstandingEmissions` into the close paths, so I cannot rule out that this check exists in an emissions-claim helper that's called separately before these functions in practice — starting a Devin session with full repo access would let a background agent trace all call sites of `withdraw_all`/`repay_all`/`close_balance` to confirm no upstream settlement occurs, and verify against the current emissions-related instructions listed in `programs/marginfi/src/lib.rs`.
