This confirms `auth_password` is used only by the outbound `stacks-signer` client (`stacks-signer/src/client/stacks_client.rs`) when it POSTs *to* the node's `/v3/block_proposal` endpoint, where it's checked via the `authorization` header (see `stackslib/src/net/api/postblock_proposal.rs` tests). There is no matching check in `libsigner/src/events.rs` on the *inbound* side, where the node pushes events to the signer's HTTP listener.

### Title
Unauthenticated write into signer event stream via `SignerEventReceiver` HTTP listener - (File: `libsigner/src/events.rs`)

### Summary
The `SignerEventReceiver::next_event` handler, which is the signer's HTTP server that accepts `stackerdb_chunks`, `proposal_response`, `new_burn_block`, and `new_block` events, never validates any authentication credential on incoming requests before deserializing and forwarding them into the signer's runloop.

### Finding Description
`SignerEventReceiver::bind` opens a plain `HttpServer` listener [1](#0-0)  and `next_event` dispatches based solely on the URL path (`/stackerdb_chunks`, `/proposal_response`, `/new_burn_block`, `/new_block`, `/shutdown`, `/status`), calling `process_event` to deserialize the JSON body and convert it into a `SignerEvent`, with no header or token check anywhere in the function [2](#0-1) . `process_event` itself only reads the body, ACKs the request, and deserializes JSON [3](#0-2) . The event is then unconditionally forwarded to the signer's runloop via `forward_event` [4](#0-3) .

The documentation for this feature explicitly describes an `auth_token`/`auth_password` pairing intended to protect this channel: the node's `[connection_options] auth_token` is supposed to match the signer's `auth_password` [5](#0-4) . However, that credential is only enforced in the opposite direction — from signer to node, on `/v3/block_proposal` submissions, where the signer client attaches an `AUTHORIZATION` header [6](#0-5)  that the node RPC endpoint checks. No equivalent check exists guarding the signer's own listener that receives `StackerDBChunksEvent`, `BlockValidateResponse`, `BurnBlockEvent`, and `StacksBlockEvent` payloads.

This breaks the intended equality "only the paired/authenticated node may push events into the signer's decision pipeline" — the code fails open: any actor able to reach the bound `endpoint:port` (which per sample configs defaults to binding all interfaces, e.g. `endpoint = "0.0.0.0:30000"`) can POST arbitrary, attacker-crafted `StackerDBChunksEvent` or `BlockValidateResponse` JSON bodies and have them delivered as if they came from the legitimate node.

### Impact Explanation
This is an unauthenticated write into signer-facing network state: a remote, unprivileged party can inject forged `SignerEvent`s (e.g. fabricated StackerDB chunk events or block-validation responses) into a running signer's event channel merely by reaching its listening socket. Depending on how the signer runloop consumes these events downstream, this can influence signer decision inputs with data that never actually came from the paired node, i.e., non-authenticated data being treated as authenticated/canonical input to the signer. This matches the "unauthenticated/unauthorized write to state" and "auth-gate that fails open" impact classes.

### Likelihood Explanation
Exploitation requires only network reachability to the signer's HTTP listener port and no possession of any secret; the request is a well-formed HTTP POST with a JSON body matching the expected schema. Given documented sample configs bind to `0.0.0.0`, and there is no code path enforcing `auth_password`/`auth_token` on the receive side, this is trivially and remotely exploitable whenever the listener is reachable (e.g., not firewalled to localhost or a private network as operationally recommended).

### Recommendation
Add authentication enforcement in `SignerEventReceiver::next_event` (or in `process_event`) that validates an `Authorization`/token header against the configured `auth_password` before processing `/stackerdb_chunks`, `/proposal_response`, `/new_burn_block`, and `/new_block` requests, mirroring the check already performed on the node's `/v3/block_proposal` RPC endpoint. Requests without a valid credential should be rejected (e.g., HTTP 401) rather than deserialized and forwarded.

### Proof of Concept
1. Configure and run a `stacks-signer` with `endpoint = "0.0.0.0:30000"` (per sample config `sample/conf/testnet-signer.toml`), regardless of the configured `auth_password`.
2. From an unrelated remote host, POST a crafted `StackerDBChunksEvent` JSON body (matching the shape used in `libsigner/src/tests/mod.rs::test_simple_signer`, lines 108–116) directly to `http://<signer-host>:30000/stackerdb_chunks` with no `Authorization` header at all.
3. Observe that `SignerEventReceiver::next_event` at `libsigner/src/events.rs:437-438` routes this to `process_event::<T, StackerDBChunksEvent>(request)` and, absent any header check, the forged event is ACKed, deserialized, and pushed via `forward_event` into the signer runloop — identical to a legitimate event from the paired node.

        self.with_server(|event_receiver, http_server, _is_mainnet| {
            // were we asked to terminate?
            if event_receiver.is_stopped() {
                return Err(EventError::Terminated);
            }
            debug!("Request handling");
            let request = http_server.recv()?;
            debug!("Got request"; "method" => %request.method(), "path" => request.url());

            if request.url() == "/status" {
                request
                .respond(HttpResponse::from_string("OK"))
                .expect("response failed");
                return Ok(SignerEvent::StatusCheck);
            }

            if request.method() != &HttpMethod::Post {
                return Err(EventError::MalformedRequest(format!(
                    "Unrecognized method '{}'",
                    request.method(),
                )));
            }
            debug!("Processing {} event", request.url());
            if request.url() == "/stackerdb_chunks" {
                process_event::<T, StackerDBChunksEvent>(request)
            } else if request.url() == "/proposal_response" {

            } else if request.url() == "/new_burn_block" {
                process_event::<T, BurnBlockEvent>(request)

        if self.out_channels.is_empty() {
            // nothing to do
            error!("No channels connected to event receiver");
            false
        } else if self.out_channels.len() == 1 {
            // avoid a clone
            if let Err(e) = self.out_channels[0].send(ev) {
                error!("Failed to send to signer runloop: {:?}", &e);
                return false;
            }
            true

                if let Err(e) = out_channel.send(ev.clone()) {
                    error!("Failed to send to signer runloop #{}: {:?}", i, &e);
                    return false;
                }
            }
            true
        }
    }

fn process_event<T, E>(mut request: HttpRequest) -> Result<SignerEvent<T>, EventError>
where
    T: SignerEventTrait,
    E: serde::de::DeserializeOwned + TryInto<SignerEvent<T>, Error = EventError>,
{
    let mut body = String::new();

    if let Err(e) = request.as_reader().read_to_string(&mut body) {
        error!("Failed to read body: {:?}", &e);
        ack_dispatcher(request);
        return Err(EventError::MalformedRequest(format!(
            "Failed to read body: {:?}",
            e
        )));
    }
    // Regardless of whether we successfully deserialize, we should ack the dispatcher so they don't keep resending it
    ack_dispatcher(request);
    let json_event: E = serde_json::from_slice(body.as_bytes())
        .map_err(|e| EventError::Deserialize(format!("Could not decode body to JSON: {:?}", e)))?;

    let signer_event: SignerEvent<T> = json_event.try_into()?;

    Ok(signer_event)
}
