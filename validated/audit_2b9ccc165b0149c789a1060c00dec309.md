### Title
Missing membership/dependency check before object pool deletion allows corruption of linked repositories - (File: internal/gitaly/service/objectpool/delete.go)

### Summary
The `DeleteObjectPool` RPC permanently removes an object pool repository without first verifying that no member repository is still linked (via `objects/info/alternates`) to that pool. This mirrors the M-22 pattern: a destructive "withdraw all" operation that omits a precondition check ensuring a dependent invariant (minimum liquidity / remaining membership) is not violated, leaving the system in a corrupted state.

### Finding Description
Object pools are shared object stores for forked repositories, linked via the `objects/info/alternates` file [2](#0-1) . The lifecycle documentation and generated gRPC interface explicitly state: "DeleteObjectPool deletes the object pool. There are no safety checks in place, so if any repository is still using this object pool it will become corrupted... It is the responsibility of the caller to ensure that it really has no members left" [3](#0-2) [4](#0-3) .

The implementation confirms this: `DeleteObjectPool` simply resolves the pool and calls `repoutil.Remove`, with no check of remaining member repositories (no reference count, no alternates-back-reference scan) before removal [1](#0-0) . Compare this to `LinkRepositoryToObjectPool`, which also performs no cross-checks when adding a member [5](#0-4)  — there is no server-side bookkeeping of pool membership at all. The `poolForRequest` helper used by both RPCs only validates that the pool repository itself is well-formed, not that it is unreferenced [6](#0-5) .

This differs from `DisconnectGitAlternates`, which mitigates the analogous risk on the member side by hard-linking objects back into the member and running a connectivity check before removing the alternates link, restoring on failure [7](#0-6) . No equivalent safety mechanism exists on the pool-deletion side.

### Impact Explanation
If `DeleteObjectPool` is invoked (e.g., driven by an ordinary user action such as deleting a fork network's origin project, or via a race between fork creation/linking and pool cleanup) while one or more member repositories still rely on the pool's alternate object directory, those member repositories will lose access to shared objects and become corrupt — commits, trees, and blobs referenced only in the pool will disappear, resulting in unreadable/broken repositories for any linked fork. This is a direct storage-integrity violation analogous to draining liquidity below the protocol's required minimum, except here the "invariant" is "no repository still depends on this pool" instead of a minimum balance.

### Likelihood Explanation
Exploitation does not require any privileged access beyond what a normal caller of the `ObjectPoolService` already has (this service is invoked by GitLab's application layer on behalf of ordinary user actions like deleting the pool source project or repository, or via race conditions between concurrent fork/unlink/delete-pool operations). Since there is no membership tracking or check at all in the code path, any caller that can trigger `DeleteObjectPool` for a pool that still has linked members will corrupt those members deterministically — likelihood is high given the complete absence of the safety check that the interface's own documentation says is required but not enforced.

### Recommendation
Before removing the pool repository in `DeleteObjectPool`, add a check that verifies no repository is still linked to it — analogous to the recommended `require(balance - MINIMUM_LIQUIDITY >= amount)` check in the referenced report. Concretely: track pool membership (e.g., via a reference/link count persisted alongside the pool, or by scanning storage for `objects/info/alternates` files pointing at the pool) and fail the RPC with a `FailedPrecondition` error if any active member remains, mirroring the connectivity-check safety net already implemented in `objectpool.Disconnect`.

### Proof of Concept
1. Fork repository `A` by creating object pool `P` and linking `A` to `P` via `CreateObjectPool` + `LinkRepositoryToObjectPool` [8](#0-7) .
2. Repack `A` so duplicate objects are removed and `A` depends entirely on alternates in `P` (as done in `TestDisconnectGitAlternates` setup) [9](#0-8) .
3. Call `DeleteObjectPool` for `P` while `A` is still linked, without calling `DisconnectGitAlternates` first.
4. `P` is removed with no check for existing members [1](#0-0) .
5. Attempt to read objects from `A` (e.g., via `CommitService`) — the previously deduplicated objects are gone because `objects/info/alternates` in `A` now points to a nonexistent directory, and `git fsck` on `A` reports missing objects, confirming corruption.

func (s *server) LinkRepositoryToObjectPool(ctx context.Context, req *gitalypb.LinkRepositoryToObjectPoolRequest) (*gitalypb.LinkRepositoryToObjectPoolResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	pool, err := s.poolForRequest(ctx, req)
	if err != nil {
		return nil, err
	}

	repo := s.localRepoFactory.Build(repository)

	if err := pool.Link(ctx, repo); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	return &gitalypb.LinkRepositoryToObjectPoolResponse{}, nil
```

func (s *server) poolForRequest(ctx context.Context, req PoolRequest) (*objectpool.ObjectPool, error) {
	pool, err := objectpool.FromProto(ctx, s.logger, s.locator, s.gitCmdFactory, s.catfileCache, s.txManager, s.housekeepingManager, req.GetObjectPool())
	if err != nil {
		if errors.Is(err, objectpool.ErrInvalidPoolDir) {
			return nil, errInvalidPoolDir
		}

		if errors.Is(err, objectpool.ErrInvalidPoolRepository) {
			return nil, structerr.NewFailedPrecondition("%w", err)
		}

		return nil, structerr.NewInternal("%w", err)
	}

	return pool, nil
```
