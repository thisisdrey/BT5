### Title
Oracle reverts propagate through `Pool.liquidate`/`debtPositionOf`, freezing liquidations and withdrawals during market stress - (File: contracts/Pool.sol)

### Summary
Metronome's `Pool` prices all collateral and debt through `IMasterOracle.getPriceInUsd`, and there is no `try`/`catch` or fallback anywhere in the call chain. Any token oracle that reverts — a disabled Chainlink feed, an expired RedStone pull price, or a token priced at 0 — makes `debtPositionOf`, `depositOf`, `liquidate`, `withdraw`, `swap`, and `DebtToken` health checks revert. The repo's own E2E tests demonstrate this liveness failure: `pool.debtPositionOf(alice)` reverts with `invalid-token-price` as soon as the RedStone pull price is stale [1](#0-0)  and again at lines 133–134. The MasterOracle itself is an external contract (`MASTER_ORACLE_ADDRESS` in `helpers/address.ts:54`), but the vulnerable code — the unchecked propagation of its revert into every solvency-relevant path — lives in `contracts/Pool.sol`, `contracts/DebtToken.sol`, `contracts/FeeProvider.sol`, and `contracts/SmartFarmingManager.sol`.

### Finding Description
`Pool.debtPositionOf` iterates over all of an account's deposit tokens and debt tokens and calls `masterOracle.getPriceInUsd(token)` for each; `Pool.liquidate`, `quoteLiquidateOut`, `maxLiquidable`, `Pool.swap`, `DepositToken.seize`, and `SmartFarmingManager.leverage`/`flashRepay` all sit downstream of the same quote. There is no per-token isolation: a single reverting feed bricks the entire view. Unlike the D3Oracle finding where a price of 0 reverts, here the failure mode is identical in effect — any revert in any registered token oracle (including the governor-set RedStone pull provider on Hemi, which reverts on expired prices unless someone first submits a fresh data package) halts liquidation of *all* accounts, not just holders of the affected token, because `debtPositionOf` aggregates every deposit token the account holds and liquidators quote through the same path.

### Impact Explanation
Protocol insolvency via liquidation liveness failure, same invariant class as the reference finding. During a market crash — precisely when liquidations are most needed — a disabled or stale oracle makes `Pool.liquidate` revert for every account. Collateral values can fall below debt values with no way for liquidators to act, removing the incentive to liquidate later and leaving the pool with bad debt. Secondary impact: `withdraw`/`unlock` paths that check health also revert, temporarily freezing user funds. For pull-oracle configurations the freeze persists until a data package is submitted; for a deactivated Chainlink feed it persists until governance swaps the token oracle — i.e., recovery itself requires the privileged actor the rules exclude as an attacker but not as a recovery dependency.

### Likelihood Explanation
Medium-to-low likelihood but nonzero: Chainlink multisigs have previously disabled feeds during turbulence (UST collapse), and the deployed Hemi configuration uses a pull oracle that *routinely* reverts when stale — the E2E tests explicitly wrap price updates plus `debtPositionOf` in one `Operator.execute` batch to work around it [2](#0-1) . No unprivileged action is required to trigger it; the condition is external feed failure/staleness, which matches the reference report's threat model.

### Recommendation
Wrap per-token `getPriceInUsd` calls in `try`/`catch` inside `Pool` (or an oracle wrapper) with a defined failure policy: e.g., skip valuation of a failing collateral for liquidation purposes only in a conservative direction, or fall back to a secondary oracle per token. At minimum, isolate `liquidate` and `debtPositionOf` so that one failing feed does not DoS liquidations for unrelated collateral/debt pairs, and never let an oracle revert block `withdraw`-less exits like `liquidate` during solvency-critical conditions.

```solidity
    vm.mockCallRevert(tokenOracle, abi.encodeWithSignature("getPriceInUsd(address)", WETH), "feed-offline");
    // (equivalently: let the RedStone pull price expire, as in E2E.hemi.pullOracle.test.ts)

    // All liquidation and health-check paths now revert:
    vm.expectRevert();
    pool.debtPositionOf(victim);
    vm.expectRevert();

```

The stale-price variant is already demonstrated by the repo's own test: an expired pull price makes `pool.debtPositionOf(alice)` revert with `invalid-token-price` [1](#0-0) , and the same revert propagates into `liquidate` since it calls `debtPositionOf` internally.

Note on confidence: I confirmed the oracle call sites exist throughout `contracts/Pool.sol`, `contracts/DebtToken.sol`, and `contracts/FeeProvider.sol` and that no `try`/`catch` exists in production contracts (grep found none), but the index did not surface the exact line numbers of `liquidate`'s internal `debtPositionOf` call, so a full review of `Pool.sol`'s liquidation path is recommended to confirm no alternate non-oracle liquidation entry exists.
