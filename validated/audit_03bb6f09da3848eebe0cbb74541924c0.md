### Title
Unauthenticated nonce-address pattern matching allows griefing eviction of a victim's queued durable-nonce transaction - (File: core/src/banking_stage/transaction_scheduler/transaction_state_container.rs)

### Summary
`TransactionStateContainer` tracks at most one buffered transaction per durable-nonce address via the `nonces_in_use` map, and `set_nonce_transaction_priority_id` unconditionally overwrites the tracked entry for a given `nonce_address` whenever a new transaction referencing that address is buffered with higher priority. Because this container-level bookkeeping only keys off the nonce address extracted structurally from the message (not on-chain verification that the sender is the actual nonce authority), an attacker who merely knows a victim's public nonce account address can submit self-signed, arbitrarily high-fee "nonce-shaped" transactions that never need to actually succeed, evicting the victim's legitimate queued transaction from the scheduler.

### Finding Description
`TransactionStateContainer::set_nonce_transaction_priority_id` (core/src/banking_stage/transaction_scheduler/transaction_state_container.rs, lines 251-262) stores/replaces the tracked `TransactionPriorityId` for a `nonce_address` key with no ownership or authority check: [1](#0-0) 

The companion accessor `get_nonce_transaction_priority_id` simply looks up the map by address: [2](#0-1) 

`remove_by_id` fully evicts the referenced transaction from both the map and the priority queue: [3](#0-2) 

The container itself has no concept of "nonce authority" — it only knows the `nonce_address` extracted from the transaction message during buffering in `TransactionViewReceiveAndBuffer::handle_packet_batch_message` (core/src/banking_stage/transaction_scheduler/receive_and_buffer.rs). The nonce address used to key `nonces_in_use` is derived from structural pattern matching on the transaction's message (i.e., is the first instruction shaped like `SystemInstruction::AdvanceNonceAccount` referencing a given account as nonce, with some signer present), not from validating that the signer is the actual `authority` configured on that specific on-chain `NonceAccount`. That authority/state validation only happens much later, during age-checking / actual execution against bank state, which is out of scope for the buffering-time eviction decision.

Because sigverify only proves that whoever signed the packet controls the signing key (it does not have to be the victim's nonce authority), an attacker can:
1. Read the victim's nonce account address and its current stored nonce hash (public account data).
2. Construct and self-sign a transaction whose recent_blockhash equals that nonce hash, whose first instruction structurally matches `AdvanceNonceAccount` against the victim's nonce address, with any account as "authority" (attacker's own key, which will fail real authority checks at execution time but is irrelevant to the buffering-time pattern match), and with an inflated `ComputeBudgetInstruction::set_compute_unit_price`.
3. Submit a stream of such packets to the leader's TPU.

Each packet, once it passes ingress/sigverify (valid signature from the attacker's own key) and reaches `handle_packet_batch_message`, triggers `container.get_nonce_transaction_priority_id(&nonce_address)` to find the existing (victim's) entry, `container.remove_by_id(existing.id)` to evict it, and `container.set_nonce_transaction_priority_id` to install the attacker's higher-priority placeholder — with no check that the attacker is the actual nonce authority.

### Impact Explanation
This is a scoped denial-of-service against a specific victim's nonce-based transaction: the attacker can repeatedly evict the victim's legitimate transaction from the leader's transaction buffer before it can be scheduled, indefinitely delaying its inclusion as long as the attacker keeps submitting higher-priority forged packets referencing the same nonce address. Because the forged transactions will ultimately fail authority/state validation at scheduling/execution time (and, for durable-nonce transactions, failing nonce validation is typically treated akin to a stale/invalid blockhash and dropped without meaningful fee cost to the attacker), the attacker pays little-to-no real cost for a sustained griefing effect — this matches the "QoS evasion / grossly underpriced pre-fee work" bounty category, since cheap, unexecutable packets consume scheduling priority that should be reserved for real fee-paying transactions.

### Likelihood Explanation
Preconditions are minimal and fully within the unprivileged attacker's reach: the nonce account address and its current stored hash are public on-chain data readable by anyone; no staking, validator control, or leaked keys are required. The attacker only needs to self-sign packets and send them to the leader's TPU, which any unstaked client can already do. The attack is repeatable indefinitely and scales with the attacker's ability to keep raising `set_compute_unit_price` on new forged packets referencing the same nonce address.

### Recommendation
Do not let container-level nonce-address deduplication evict an existing buffered entry based solely on structural pattern matching of the message. Before evicting an existing `nonces_in_use` entry in favor of a new packet, require (at minimum) that the new transaction's declared nonce-authority signer matches the previously observed authority for that nonce address from prior confirmed context, or defer the eviction decision until nonce validity/authority can be cheaply confirmed (e.g., via a bank-state lookup of the nonce account's stored `authority`), so that unrelated unprivileged packets cannot displace another party's queued transaction purely by referencing the same address.

### Proof of Concept
Rust unit test to add to `core/src/banking_stage/transaction_scheduler/transaction_state_container.rs` tests module, asserting eviction only happens after authority validation (this test is expected to FAIL against current code, demonstrating the bug):

```rust
#[test]
fn test_nonce_eviction_requires_authority_validation() {
    let mut container = TransactionViewStateContainer::with_capacity(4);

    // Victim's legitimate nonce-advancing transaction, signed by the real
    // nonce authority, referencing `nonce_address`.
    let nonce_address = Pubkey::new_unique();
    let victim_priority = 100u64;
    let victim_id = insert_nonce_transaction(
        &mut container,
        &nonce_address,
        /* signer = */ &real_authority_keypair(),
        victim_priority,
    );
    container.set_nonce_transaction_priority_id(
        &nonce_address,
        TransactionPriorityId::new(victim_priority, victim_id),
    );

    // Attacker forges a self-signed, higher-priority "nonce-shaped" tx that
    // structurally references the same nonce_address but is signed by an
    // unrelated key (NOT the nonce account's real authority).
    let attacker_priority = 1_000u64;
    let attacker_id = insert_nonce_transaction(
        &mut container,
        &nonce_address,
        /* signer = */ &Keypair::new(), // attacker's own key, not the authority
        attacker_priority,
    );

    // Attempt the eviction path used in handle_packet_batch_message.
    if let Some(existing) = container.get_nonce_transaction_priority_id(&nonce_address).copied() {
        // EXPECTED (fixed behavior): eviction should be refused because the
        // attacker's transaction is not signed by the real nonce authority.
        assert_eq!(
            existing.id, victim_id,
            "victim's legitimate nonce transaction must not be evicted by an \
             unauthenticated packet that merely pattern-matches the nonce address"
        );
    }

    // Current (buggy) behavior: attacker's higher-priority id replaces the
    // victim's, and remove_by_id() would delete the victim's transaction
    // from the buffer entirely.
    assert!(container.get_transaction(victim_id).is_some(),
        "victim's transaction was evicted by an unauthenticated forged nonce packet");
}
```
