Audit Report

## Title
Unbounded, attacker-controlled `relayer_fee` in Snowbridge V2 inbound messages causes unbacked minting of ETH-denominated foreign asset on AssetHub - ([File: bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs])

## Summary
`InboundQueue::process_message` takes the `relayer_fee` field decoded verbatim from the Ethereum `OutboundMessageAccepted` event and registers it as a claimable relayer reward with no check that it is bounded by `message.value` or any real backing. When claimed via `claim_rewards_to`, the Snowbridge reward path (`PayAccountOnLocation::pay_reward`) does not debit a pre-funded, message-specific escrow — it constructs a fresh `ReserveAssetDeposited` XCM instruction that mints the ETH-denominated foreign asset directly to the beneficiary on AssetHub, in an amount equal to the attacker-chosen `relayer_fee`.

## Finding Description
`Message` is decoded directly from the Solidity `OutboundMessageAccepted` event's `Payload` struct, including `relayerFee`, with no cross-field validation: [1](#0-0) 

`process_message` only verifies the gateway address and nonce uniqueness before unconditionally registering `relayer_fee` (plus any tip) as a reward: [2](#0-1) 

There is no `Config::MaxRelayerFee`, no comparison against `message.value`, and no comparison against `execution_fee`. `register_relayer_reward` simply accumulates whatever value it's given: [3](#0-2) 

Critically, the downstream payout mechanism for `BridgeReward::Snowbridge` does not draw from funds that were actually locked for this specific message. `BridgeRewardPayer::pay_reward` routes Snowbridge rewards through `PayAccountOnLocation::pay_reward`: [4](#0-3) 

That implementation builds an XCM program using `ReserveAssetDeposited` for `(ethereum_location, reward)` and deposits it straight to the beneficiary — this is a mint-style instruction that assumes reserve backing on the Ethereum side, but no such backing is verified anywhere in this call path: [5](#0-4) 

Because `submit` is a public extrinsic (any `ensure_signed` origin, including the attacker acting as their own relayer per the pallet's README flow), and the Ethereum-side event generation is controlled by an unprivileged end user calling the Gateway's `v2_sendMessage`, an attacker can set `relayerFee` to an arbitrarily large value while setting `value` (real bridged Ether) to near zero, then submit the corresponding proof and claim the reward, causing AssetHub to mint ETH-denominated foreign asset unbacked by any real Ethereum-side lock.

## Impact Explanation
This matches the "theft or unbacked mint or unlock" impact category for Snowbridge BridgeHub code: the reward-claim path mints new supply of the Ethereum-reserve asset on AssetHub proportional to an attacker-controlled `relayer_fee`, decoupled from the actual Ether locked in the corresponding message (`message.value`). Repeated exploitation inflates the AssetHub-side ETH-denominated foreign asset supply beyond what is actually escrowed on the Ethereum Gateway contract, undermining the reserve-backing invariant relied upon by all legitimate Snowbridge ETH transfers.

## Likelihood Explanation
High likelihood: `submit` is open to any signed account, and the attacker fully controls the `relayerFee` field of the Ethereum event they themselves emit (via `v2_sendMessage`/`v2_registerToken`), then self-relays the proof. No collusion, governance action, or key compromise is required, and this is repeatable per nonce/message.

## Recommendation
Add a `Config` bound (e.g., `MaxRelayerFee` or a ratio check) in `process_message` that rejects or caps `relayer_fee` relative to `message.value`/`execution_fee` before calling `T::RewardPayment::register_reward`. Additionally, review `PayAccountOnLocation::pay_reward` to ensure Snowbridge reward payouts are backed by value actually locked for the specific message/nonce rather than unconditionally minting via `ReserveAssetDeposited`.

## Proof of Concept
1. On Ethereum, call `v2_sendMessage` with `Payload.value = 0` (or minimal) and `Payload.relayerFee` set to a very large `u128`.
2. Obtain the event log and valid receipt/execution-header proof (proves the event happened, not that the values are economically sane).
3. Call `EthereumInboundQueueV2::submit` as the attacker's own account (acting as "the relayer").
4. `process_message` (`bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs:219-239`) registers the full inflated `relayer_fee` as a reward for the attacker via `T::RewardPayment::register_reward`.
5. Call `claim_rewards_to` on `pallet-bridge-relayers` with `BridgeRewardBeneficiaries::AssetHubLocation`; this triggers `PayAccountOnLocation::pay_reward`, which mints the inflated ETH-denominated foreign asset directly to the attacker's AssetHub account via `ReserveAssetDeposited`, with no real Ethereum-side backing for that amount.

	fn pay_reward(
		relayer: &Relayer,
		_: (),
		reward: RewardBalance,
		beneficiary: Self::Beneficiary,
	) -> Result<(), Self::Error> {
		let ethereum_location = Location::new(2, [GlobalConsensus(EthereumNetwork::get())]);
		let assets: Asset = (ethereum_location.clone(), reward.into()).into();

		let xcm: Xcm<()> = alloc::vec![
			UnpaidExecution { weight_limit: Unlimited, check_origin: None },
			DescendOrigin(InboundQueueLocation::get().into()),
			UniversalOrigin(GlobalConsensus(EthereumNetwork::get())),
			ReserveAssetDeposited(assets.into()),
			DepositAsset { assets: AllCounted(1).into(), beneficiary },
		]
		.into();

		let (ticket, fee) =
			validate_send::<XcmSender>(AssetHubLocation::get(), xcm).map_err(|_| XcmSendFailure)?;
		XcmExecutor::charge_fees(relayer.clone(), fee).map_err(|_| ChargeFeesFailure)?;
		XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;

		Ok(())
	}
