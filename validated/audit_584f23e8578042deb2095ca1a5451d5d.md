### Title
Unbounded/optional `FetchRemoteRequest.Timeout` allows a mutator RPC to run — and hold its repository write lock — indefinitely - ([File: internal/gitaly/service/repository/fetch_remote.go])

### Summary
`FetchRemoteRequest.Timeout` is a client-supplied integer field that is used verbatim to construct a `context.WithTimeout` guard around the entire fetch operation, but only if the caller sets it to a strictly positive value. There is no upper bound enforced on it, and — more critically — no lower/default bound is enforced either: any caller-supplied value of `0` or less disables the timeout entirely, leaving the fetch (and everything it holds open: quarantine directory, `updateref` processes, and — under the newly introduced Praefect serialized-writes feature — the per-repository PostgreSQL write lock) to run for as long as the remote endpoint keeps the connection alive, i.e. potentially forever.

### Finding Description
`FetchRemote` reads the request-controlled `Timeout` field and applies it conditionally: [1](#0-0) 

```go
func (s *server) FetchRemote(ctx context.Context, req *gitalypb.FetchRemoteRequest) (*gitalypb.FetchRemoteResponse, error) {
	if err := s.validateFetchRemoteRequest(ctx, req); err != nil {
		return nil, err
	}

	if req.GetTimeout() > 0 {
		var cancel context.CancelFunc
		ctx, cancel = context.WithTimeout(ctx, time.Duration(req.GetTimeout())*time.Second)
		defer cancel()
	}
	...
```

There is no validation that clamps `Timeout` to a sane maximum, and there is no fallback/default timeout applied when the field is `<= 0` — the operation simply proceeds with whatever deadline (if any) the caller's gRPC context already carries. Since `FetchRemote` is invoked as part of ordinary repository-mirroring/import workflows using attacker/operator-controlled `RemoteParams` (URL, SSH key, auth header, etc. — see `Remote` message), an unprivileged caller who can trigger a mirror/import fetch fully controls this field.

`fetchRemoteAtomic`, which is executed under this (possibly non-existent) deadline, opens a Git object quarantine directory and spawns two `updateref.Updater` instances that hold on-disk ref locks for the repository during the entire fetch: [2](#0-1) 

This is the same shape as the sNOTE `coolDownTimeInSeconds` issue: a caller-chosen numeric duration parameter is passed straight into a bound-setting primitive (`context.WithTimeout` / `_safe32`) without an upper limit or a mandatory-minimum/default fallback, so a chosen value (here, "unset"/non-positive, there, `type(uint32).max`) defeats the intended bound and allows the guarded resource to remain locked/unavailable indefinitely.

Because Gitaly now supports Praefect's serialized-writes mechanism, mutator RPCs like `FetchRemote` acquire a repository-scoped write lock (`WriteLockManager.Lock`) for the duration of the transaction phases, and that lock is only released when the RPC handler returns (via the deferred unlock path) or the context is cancelled: [3](#0-2) 

If `FetchRemote` never times out because `Timeout` was left at `0` (or negative) and the remote endpoint stalls (e.g. a slow/hanging HTTP or SSH remote, entirely controllable by whoever configures `RemoteParams.Url`), the handler never returns, the deferred unlock never fires, and the repository's write lock is held for as long as the stalled connection persists — blocking every other write to that repository cluster-wide.

### Impact Explanation
An unprivileged caller who can trigger `FetchRemote` (e.g. via a mirrored/imported repository whose remote URL/SSH endpoint they control) can point it at a server that accepts the connection but never completes the negotiation. With `Timeout` left unset/zero, Gitaly applies no deadline of its own, so the fetch — and the on-disk ref locks plus (when serialized writes are enabled) the cluster-wide Postgres write lock for that repository — can be held indefinitely. This denies all other writers (pushes, other operations) to the affected repository, a direct availability impact analogous to the referenced report's "funds locked forever": here it is "repository writes locked forever."

### Likelihood Explanation
Reaching this path requires only the ability to invoke `FetchRemote` (a standard mutator RPC used for repository mirroring/import) and to control the remote endpoint being fetched from, both of which are realistic for an ordinary GitLab user setting up a pull mirror or import from an external/attacker-controlled Git host. No special privilege over Gitaly configuration is needed — the vulnerable field is a normal RPC request parameter.

### Recommendation
- Always apply a bounded context deadline to `FetchRemote`/`fetchRemoteAtomic`, regardless of whether `Timeout` is set: use a sane server-enforced default when `Timeout <= 0`, and clamp any caller-supplied value to a maximum (e.g. via `cfgerror`-style `InRange` validation, mirroring the pattern already used in `internal/gitaly/diff/diff.go`'s `enforceUpperBound`).
- Ensure lock-holding operations (quarantine directory, `updateref` updaters, and the Praefect repository write lock) are always released on a bounded worst-case timeline independent of client input.

### Proof of Concept
1. Configure a mirror/import repository whose remote URL points to an HTTP(S) or SSH server under attacker control that accepts the TCP connection and the Git protocol handshake but never sends further data (simulating a slow-loris style stall), similar to the existing test setup in `internal/gitaly/service/repository/fetch_remote_test.go` (`"http with timeout"` case) but this time omitting `Timeout` (or setting it to `0`).
2. Call `FetchRemote` with `RemoteParams.Url` pointing at that stalling server and `Timeout: 0`.
3. Observe that, unlike the existing test which sets `Timeout: 1` and expects a `DeadlineExceeded` failure, the request with `Timeout` unset applies no deadline; the RPC blocks indefinitely inside `fetchRemoteAtomic`, holding the quarantine directory and ref-updater locks (and, with serialized writes enabled, the cluster-wide repository write lock) open for as long as the attacker keeps the connection alive.

func (s *server) FetchRemote(ctx context.Context, req *gitalypb.FetchRemoteRequest) (*gitalypb.FetchRemoteResponse, error) {
	if err := s.validateFetchRemoteRequest(ctx, req); err != nil {
		return nil, err
	}

	if req.GetTimeout() > 0 {
		var cancel context.CancelFunc
		ctx, cancel = context.WithTimeout(ctx, time.Duration(req.GetTimeout())*time.Second)
		defer cancel()
	}

	tagsChanged, repoChanged, err := s.fetchRemoteAtomic(ctx, req)
	if err != nil {
		return nil, err
	}

	return &gitalypb.FetchRemoteResponse{TagsChanged: tagsChanged, RepoChanged: repoChanged}, nil
}

// Lock acquires the write lock for a given virtualStorage, relativePath and txnID,
// blocking until the lock is acquired or ctx is cancelled.
func (r *RepoReferenceWriteLockManager) Lock(ctx context.Context, virtualStorage, relativePath string, txnID uint64,
) (RepoLock, error) {
	for {
		res := r.tryLock(ctx, virtualStorage, relativePath, txnID)
		if res.Err != nil {
			return RepoLock{}, res.Err
		}
		if res.Acquired {
			return RepoLock{Unlock: res.Unlock, Renew: res.Renew}, nil
		}

		select {
		case <-ctx.Done():
			res.Deregister()
			return RepoLock{}, fmt.Errorf("wait for lock: %w", ctx.Err())
		case <-res.NotificationCh:
			// wait for the lock to release
		}
	}
}
