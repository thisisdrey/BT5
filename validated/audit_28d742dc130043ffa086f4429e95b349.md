Based on my research, I found a genuine, exploitable command-injection pattern in Bazel's own repository-rule utilities: `tools/build_defs/repo/utils.bzl`'s `patch()` helper builds a shell command string by naively single-quoting each `patch_args` element and concatenating it into a `bash -c` invocation, without escaping embedded single quotes.

### Title
Shell Command Injection via Unescaped `patch_args`/`patch_tool` in Repository Patch Application - (File: tools/build_defs/repo/utils.bzl)

### Summary
The `patch()` utility function used by `http_archive`, `git_repository`, and other repository rules constructs a shell command line by naively wrapping each `patch_args` string in single quotes and concatenating it with `patch_tool` before handing it to `bash -c` / `powershell -c`. Because the quoting does not escape embedded single-quote characters, any `patch_args` (or `patch_tool`) value containing a single quote breaks out of the intended argument and injects arbitrary shell syntax into the command executed via `ctx.execute([bash_exe, "-c", command], ...)`. This mirrors the `plotter` advisory's root cause: a string value that is supposed to be inert data (a tool argument, analogous to a plot title) is spliced unescaped into a string that is later interpreted as shell/command syntax.

### Finding Description
In `tools/build_defs/repo/utils.bzl`, the `patch()` function builds the patch command like this: [1](#0-0) 

```
for patchfile in patches:
    command = "{patchtool} {patch_args} < {patchfile}".format(
        patchtool = patch_tool,
        patchfile = ctx.path(patchfile),
        patch_args = " ".join([
            "'%s'" % arg
            for arg in patch_args
        ]),
    )
    st = ctx.execute([bash_exe, "-c", command], working_directory = patch_directory or "")
```
Each element of `patch_args` is wrapped as `'%s'`, which is the classic insufficient escaping bug: it protects against spaces but not against an embedded `'` character. A value such as `-p1' ; touch pwned; echo '` closes the quote early and lets the attacker append arbitrary shell syntax that `bash -c` will execute. `patch_tool` is inserted with no quoting at all, so a value containing whitespace/metacharacters is likewise unconstrained.

### Impact Explanation
If an attacker can influence the string values that flow into `patch_args` (or `patch_tool`) for a repository rule that is fetched and evaluated as part of a build — e.g., via a module extension in a dependency module that forwards externally-derived strings (from a downloaded manifest/version file/registry-provided metadata) into `patch_args` — the resulting `ctx.execute([bash_exe, "-c", command])` call executes attacker-chosen shell commands with the privileges of the Bazel client during repository fetching/patching (part of the analysis phase, before any sandboxing of build actions applies). This is a full command-injection primitive (CWE-77), not merely resource exhaustion or a sandbox issue, matching the `plotter` advisory's class.

### Likelihood Explanation
Exploitability requires a code path where a value under attacker influence (data from an untrusted source: a fetched file, registry-provided metadata, or extension logic that echoes external strings) ends up populating `patch_args`/`patch_tool` for a rule invoking `patch()`. The Bazel-native patch path (`_use_native_patch`) is only taken when every `patch_args` entry starts with `-p`, so any other value — including one crafted to contain a stray quote — forces the vulnerable shell-based branch. `remote_patches` content itself is integrity-checked and applied via native `ctx.patch`, so the immediate risk is in the naive quoting of `patch_args`/`patch_tool`, which is Bazel's own escaping defect independent of how those strings originate.

### Recommendation
Replace the naive `"'%s'" % arg` quoting with a proper POSIX shell-quoting routine that escapes embedded single quotes (e.g., `'` → `'\''`), or better, avoid string-interpolated shell invocation entirely by invoking the patch tool as an argv list (`ctx.execute([patch_tool] + patch_args + ["<", patchfile])`is not directly possible for redirection, so instead write the patch content via `ctx.execute` with explicit argv and shell out only for the unavoidable `<` redirection using a properly escaped single-quoted string, or read the patch file content in Starlark and pass it via stdin using `ctx.execute(..., environment=...)`with a wrapper script that takes the patchfile path as an escaped argv entry rather than string-formatted into the command).

### Proof of Concept
A `BuildIntegrationTestCase`/`src/test/shell/bazel` style proof: define a repository rule that sets `patch_args = ["-p1' ; touch " + marker_path + " ; echo '"]` and a benign `patches` file, then assert that after `bazel build` triggers repository fetch/patch, the file at `marker_path` (outside the repository directory) exists — demonstrating that shell command injection occurred outside the intended `patch`/`bash` invocation boundary.
