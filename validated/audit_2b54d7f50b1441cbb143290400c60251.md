## Analysis

The core broken invariant in the M-12 report is: **a periodic/point-in-time rate is derived from an instantaneous, attacker-influenced pool state, and the same actor who inflates the pool immediately consumes the mis-priced rate before reverting the pool state** — all inside a single atomic sequence they fully control (no relayer, validator, or governance actor needed).

The closest verifiable analog in `polkadot-sdk` is in `pallet_asset_conversion_tx_payment`'s `SwapAssetAdapter`, which prices a user's transaction fee by reading the **live spot reserves** of a `pallet-asset-conversion` AMM pool at the moment of fee withdrawal, with no TWAP, oracle, or slippage-bound protection against reserve manipulation performed by the very account paying the fee, in a preceding extrinsic of the *same block*.

### Title
Self-manipulated AMM spot price allows attacker to systematically underpay transaction fees via `SwapAssetAdapter` - (File: substrate/frame/transaction-payment/asset-conversion-tx-payment/src/payment.rs)

### Summary
`SwapAssetAdapter::withdraw_fee` prices the asset-denominated transaction fee using `QuotePrice::quote_price_tokens_for_exact_tokens`, which reads the AMM pool's live reserves (`get_reserves`) with no protection against a preceding, attacker-controlled swap in the same block that skews those reserves. An account that (temporarily) controls the pool's liquidity ratio — analogous to the flash-loan-filled insurance pool in the source report — can drive the quoted `asset_fee` down to a minimal amount, pay a near-zero fee, and then restore the pool, paying only the round-trip LP fee (which, if the attacker is also the pool's liquidity provider, is returned to themselves) instead of the correct transaction fee.

### Finding Description
`withdraw_fee` computes the amount of the user-chosen `asset_id` needed to cover the fee entirely from the pool's current reserves: [1](#0-0) 

The quote is produced by `AssetConversion::quote_price_tokens_for_exact_tokens`, which is explicitly documented as being only valid "if no other swaps are made... before the target swap": [2](#0-1) 

and is computed directly from the pool account's current on-chain balances via `get_reserves`, with no moving-average or manipulation resistance: [3](#0-2) [4](#0-3) 

Because Substrate applies extrinsics from the same sender strictly in nonce order within a block, an attacker fully controls the ordering of the following three of their own extrinsics landing in one block:
1. `swap_exact_tokens_for_tokens` — push a large amount of the fee-asset into the pool (or pull native asset out) to sharply skew `reserve(asset_id) : reserve(native)` in their favor.
2. The intended call, paying fees in `asset_id` — `ChargeAssetTxPayment`'s signed extension invokes `SwapAssetAdapter::withdraw_fee`, which quotes `asset_fee` off the now-skewed reserves, producing an artificially small `asset_fee` for the same native-denominated `fee`.
3. A reverse swap restoring the original reserve ratio.

No component in this chain enforces a maximum-deviation check, an oracle-anchored price, or a slippage bound supplied independently of the attacker (the "exact tokens for exact fee" swap in step 2 has no min/max guard beyond `change.peek().is_zero()`, which only checks that the quoted amount was fully consumed — not that the quote itself is fair): [5](#0-4) 

The only cost to the attacker is the LP fee charged on their own two swaps — which nets to zero if the attacker is (or controls) the pool's liquidity provider, exactly mirroring the flash-loan round-trip in the source report where the "insurance" cost of moving funds is negligible compared to the value extracted.

### Impact Explanation
This is a runtime-level accounting bug that lets an unprivileged, ordinary account systematically underpay (or in the extreme, near-zero-pay) protocol transaction fees that should be collected by `OnUnbalanced`/treasury (`ResolveAssetTo<TreasuryAccount, ...>` in the runtime config), degrading the intended fee-based economic security and treasury inflows of any chain using `pallet_asset_conversion_tx_payment::SwapAssetAdapter`: [6](#0-5) 
This falls under "runtime bugs that compromise intended behavior" / "theft or unbacked... underpriced work" in the impact gate, since fee payment is public underpriced work whose correctness the treasury/fee model depends on.

### Likelihood Explanation
The attack requires no validator, relayer, governance, or leaked-key assumptions — only an account with enough capital (or LP ownership) to move a pool's reserves for one block, exactly like the flash-loan actor in the original report. It is repeatable every block the attacker wishes, is fully deterministic due to nonce-ordered extrinsic execution, and scales with pool size/attacker capital rather than requiring any privileged timing window (unlike the hourly cadence in the original finding, this can be done on essentially every transaction the attacker sends).

### Recommendation
- Use a manipulation-resistant price source (time-weighted average price, or a price anchored across multiple blocks) rather than the instantaneous spot reserves for fee quoting.
- Bound `asset_fee` deviation against a reference/last-known-good price, rejecting quotes that deviate beyond a configurable tolerance.
- Alternatively, disallow same-block swap-then-fee-payment-then-swap-back sequences from the same origin, or require the fee-asset swap to route through a pool with independent (non-attacker-controlled) liquidity depth guarantees.

### Proof of Concept
1. Attacker creates/controls a `pallet-asset-conversion` pool for `(asset_id, NativeAsset)` used by `SwapAssetAdapter` as the runtime's `OnChargeAssetTransaction`, and is the pool's dominant LP.
2. In block N, extrinsic 1 (attacker, nonce k): `swap_exact_tokens_for_tokens` swapping a large amount of `asset_id` into the pool, sharply lowering `reserve(native)`/raising `reserve(asset_id)` so that `quote_price_tokens_for_exact_tokens(asset_id, native, fee, true)` returns a near-minimal `asset_fee`.
3. Extrinsic 2 (attacker, nonce k+1): the attacker's actual intended call with `ChargeAssetTxPayment` fee-asset set to `asset_id`. `withdraw_fee` (`substrate/frame/transaction-payment/asset-conversion-tx-payment/src/payment.rs:142-157`) quotes and withdraws the artificially small `asset_fee`.
4. Extrinsic 3 (attacker, nonce k+2): reverse `swap_exact_tokens_for_tokens` restoring the original reserve ratio, recovering the LP fee paid in steps 1/3 back to the attacker as LP.
5. Net result: attacker's intended call is executed while treasury/fee recipient receives a fee far below the intended native-denominated `fee`, at negligible net cost to the attacker.

		pub fn quote_price_tokens_for_exact_tokens(
			asset1: T::AssetKind,
			asset2: T::AssetKind,
			amount: T::Balance,
			include_fee: bool,
		) -> Option<T::Balance> {
			// Swaps reject zero amounts, match that behavior.
			if amount.is_zero() {
				return None;
			}
			let pool_account = T::PoolLocator::pool_address(&asset1, &asset2).ok()?;

			let (balance1, balance2) = Self::get_reserves(asset1.clone(), asset2.clone()).ok()?;

			if balance1.is_zero() {
				return None;
			}

			// Swap withdrawals from pools use `keep_alive=true` (Preserve). Use the same
			// preservation level to determine the actual withdrawable amount.
			let max_output =
				T::Assets::reducible_balance(asset2.clone(), &pool_account, Preserve, Polite);
			if amount > max_output {
				return None;
			}

			if include_fee {
				let fee = Self::pool_fee_for(&asset1, &asset2).ok()?;
				Self::get_amount_in(fee, &amount, &balance1, &balance2).ok()
			} else {
				Self::quote(&amount, &balance2, &balance1).ok()
			}
		}
