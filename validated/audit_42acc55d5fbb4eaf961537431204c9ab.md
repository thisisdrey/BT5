### Title
Unbounded/unvalidated length field in `ValidateMultiSign` precompile allocation triggers uncaught crash - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `ValidateMultiSign` precompiled contract reads an attacker-controlled length word straight out of calldata and uses it to size a `byte[][]` allocation and drive array indexing, without validating it against the actual calldata size, and — critically — this call happens **outside** any `try/catch`, unlike its sibling `BatchValidateSign` contract which wraps the equivalent logic in a catch-all. This mirrors the Wireshark DMP dissector bug: a length field taken from untrusted input is trusted and used directly to size/traverse a buffer, causing a crash.

### Finding Description
`ValidateMultiSign.execute()` parses calldata into `DataWord[] words` and then calls: [1](#0-0) 

The `sigArraySize`/`MAX_SIZE` bound check is only performed when `VMConfig.allowTvmSelfdestructRestriction()` is enabled; otherwise `extractBytesArray` is invoked directly with no bound. `extractBytesArray` reads the length word verbatim and uses it to allocate an array and iterate: [2](#0-1) 

`len` comes from `words[offset].intValueSafe()`, which can be any value the caller places in calldata (up to `Integer.MAX_VALUE`), and is never checked against `words.length` or `data.length` before being used in `new byte[len][]` or in the subsequent loop that indexes `words[offset + i + 1]` and calls `extractBytes(data, ..., bytesLen)` (an unchecked `Arrays.copyOfRange`): [3](#0-2) 

Crucially, in `ValidateMultiSign.execute()` this call at line 1074 sits **before** the method's only `try` block (which starts at line 1082 and only wraps the permission/weight logic): [4](#0-3) 

By contrast, `BatchValidateSign.execute()` wraps its entire `doExecute` (which performs the identical `extractBytesArray`/`extractSigArray` calls) in `catch (Throwable t)`: [5](#0-4) 

`ValidateMultiSign` has no equivalent outer safety net, so an out-of-bounds/oversized `len` derived from calldata can raise `NegativeArraySizeException`, `ArrayIndexOutOfBoundsException`, or `OutOfMemoryError` (from attempting to allocate a huge `byte[][]`) that propagates unhandled out of the precompile.

### Impact Explanation
`ValidateMultiSign` is a TVM precompiled contract reachable by any smart-contract `CALL`/`STATICCALL` originating from a normal, signed transaction — no special privileges are required. A crafted calldata length word can force an oversized/negative array allocation. If the resulting `OutOfMemoryError`/`ArrayIndexOutOfBoundsException` is not caught by a higher-level generic handler in the VM call stack (the only local catch does not cover this code path), it can propagate up through block/transaction execution, aborting the executing thread or, for `OutOfMemoryError`, destabilizing the whole JVM (since `Error` is frequently not caught by ordinary `catch(Exception)` blocks used elsewhere in the runtime). This is the same class of "unvalidated declared length used to size/traverse a buffer causes a crash" as the Wireshark DMP CVE, but here reachable from any contract call, potentially producing a node crash / halted block processing during normal transaction execution — matching the "node crash or halt" acceptance criteria.

### Likelihood Explanation
Likelihood is limited by whatever generic exception handling exists further up the TVM invocation stack (e.g. around `Program`'s call-to-precompile dispatch), which was not directly inspected in this pass; if a broad `catch(Throwable)`/`catch(Exception)` exists there, the practical effect is degraded to a reverted call/OOM spike rather than a full crash. The precompile is reachable trivially (any deployed contract can `CALL` it with fully attacker-controlled calldata), and the missing bound check is a straightforward code-inspection finding, not merely inferred from the external report.

### Recommendation
- Mirror the `BatchValidateSign` protection: wrap the entirety of `ValidateMultiSign.execute()` (including the `words` parsing, `extractSigArray`/`extractBytesArray` calls, and `signatures` derivation) in a `catch (Throwable t)` that returns `Pair.of(true, DATA_FALSE)` on any error.
- Independently, harden `extractBytesArray`/`extractSigArray` to validate `len` against `words.length`/`data.length` (and reject negative/oversized values) before allocating, regardless of the `allowTvmSelfdestructRestriction()` feature flag, so the bound check is not gated behind an optional flag.

### Proof of Concept
1. Deploy any contract that performs a low-level `call` (or `staticcall`) to the `ValidateMultiSign` precompiled contract address.
2. Construct calldata where `words[3]` (the signature-array offset word) points to an offset whose corresponding length word (`words[offset]`) is set to a very large value (e.g. `0x7FFFFFFF`), with `VMConfig.allowTvmSelfdestructRestriction()` not yet activated so the `MAX_SIZE` guard at line 1066–1071 is skipped.
3. Broadcast the transaction; `extractBytesArray(words, offset, rawData)` at line 1074 executes `new byte[0x7FFFFFFF][]`, attempting a multi-gigabyte allocation, or indexes `words[]`/`data[]` out of bounds, throwing an exception that is not caught anywhere within `ValidateMultiSign.execute()`.
4. Observe whether the exception (in particular `OutOfMemoryError`) escapes the transaction-execution call stack and destabilizes/crashes the node process, versus being silently swallowed elsewhere in the caller chain (unverified in this pass).
