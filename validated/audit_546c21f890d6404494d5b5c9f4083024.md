### Title
Unbounded prefix scan in DelegatedResourceAccountIndexStore lets an attacker DoS delegation-index queries - ([File: chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java])

### Summary
`DelegateResourceActuator` lets any account delegate as little as 1 TRX of bandwidth/energy to an arbitrary receiver address, and each such delegation writes a brand-new key under `V2_FROM_PREFIX + owner + receiver` (and the mirrored `V2_TO_PREFIX` key for the receiver) in `DelegatedResourceAccountIndexStore` [1](#0-0) [2](#0-1) . There is no cap on the number of distinct receiver (or sender) addresses one account can accumulate this way, and the minimum delegate amount is just `TRX_PRECISION` (1 TRX) [3](#0-2) .

Reading the index back (`getIndex`/`getV2Index`) performs an unbounded `prefixQuery` over the whole key range for that address and then sorts/streams every entry it finds [4](#0-3) . This query path is directly reachable by any unauthenticated caller via the HTTP servlets `GetDelegatedResourceAccountIndexServlet` / `GetDelegatedResourceAccountIndexV2Servlet` and the corresponding gRPC methods exposed through `Wallet`/`RpcApiService` [5](#0-4) .

### Finding Description
1. An attacker with a modest amount of TRX (e.g., a few thousand TRX, or even less split over many transactions/blocks) can send many low-cost `DelegateResourceContract` transactions from the same owner address, each to a freshly generated receiver address, each moving only the 1-TRX minimum.
2. Each such transaction is cheap for the attacker (fee is `0`, `calcFee()` returns `0` in `DelegateResourceActuator`), yet it permanently adds a new key to the `DelegatedResourceAccountIndexStore` under the attacker's address prefix.
3. Because there is no maximum on the number of distinct delegation relationships an address can have, this key set can be grown arbitrarily large by the attacker alone, entirely through ordinary, permission-less transactions.
4. Any subsequent read of this attacker's delegation index — via `getIndex`/`getV2Index`, exposed by the public "get delegated resource account index" HTTP/gRPC APIs — must execute `prefixQuery` over the full accumulated key range, then sort and map every result [6](#0-5) . This is unbounded work driven directly by attacker-controlled state size, matching the reported bug class ("unbounded loop … if [attacker-controlled data] gets sufficiently large, calls will fail/degrade").
5. Additionally, `FreezeBalanceActuator`'s legacy delegation path also reads/converts this same index (`getIndex`, `convert`) during freeze/unfreeze operations, so the unbounded work can also be triggered as a side effect of ordinary account operations by or against the attacker's account, not only by the read-only query API.

### Impact Explanation
A single low-value account can grow its own delegation index without bound and force any external node serving the delegated-resource-account-index HTTP/gRPC API (or a peer processing a freeze/unfreeze/delegate transaction that touches the poisoned index) to perform O(n) LevelDB/RocksDB prefix scans and sorting, where n is fully attacker-controlled. Because these APIs are commonly exposed for wallet/exchange integrations, this can degrade or effectively stall query-serving nodes (denial of service against the query path), and can slow down block processing when other actuators (`FreezeBalanceActuator`, `UnDelegateResourceActuator`) touch the same bloated index for that address.

### Likelihood Explanation
High reachability: any account holder can trigger this purely with signed `DelegateResourceContract` transactions costing 1 TRX increments and zero actuator fee; no special privilege, contract deployment, or witness/SR role is required. The read side is a standard, publicly documented HTTP/gRPC query endpoint, so any anonymous API client can be the trigger for the resulting performance degradation.

### Recommendation
Impose a hard cap on the number of distinct delegate/receiver relationships tracked per account in `DelegatedResourceAccountIndexStore` (similar to the existing `UNFREEZE_MAX_TIMES` cap on `UnfreezeBalanceV2Actuator`), enforced in `DelegateResourceActuator.validate()`, and/or paginate the `prefixQuery` results returned by `getIndex`/`getV2Index` so a single request cannot force unbounded I/O and CPU work.

### Proof of Concept
Not independently executed; reasoning is based on static code inspection of `DelegateResourceActuator.delegateResource()` [7](#0-6)  and `DelegatedResourceAccountIndexStore.getWithPrefix()` [8](#0-7) . Conceptually:
1. From account A, freeze at least `N` TRX for bandwidth/energy (V2 freeze).
2. Send `N` separate `DelegateResourceContract` transactions from A, each delegating the 1-TRX minimum to a distinct freshly-generated receiver address `R_1..R_N` (no self-delegation allowed, but arbitrary numbers of unique receivers are).
3. Call the `getDelegatedResourceAccountIndex`/`GetDelegatedResourceAccountIndexV2` HTTP or gRPC endpoint for address A.
4. Observe query latency and I/O scale linearly with `N`; for a sufficiently large `N` chosen by the attacker, the query (and any actuator, such as `UnDelegateResourceActuator`/`FreezeBalanceActuator`, that reads the same index) becomes prohibitively slow, denying service to that lookup path.

I was not able to execute this against a running node to measure concrete latency/resource numbers; this assessment is based on code-level analysis of the unbounded prefix scan and lack of any per-account cap on distinct delegation relationships.

  private void delegateResource(byte[] ownerAddress, byte[] receiverAddress, boolean isBandwidth,
                                long balance, boolean lock, long lockPeriod) {
    AccountStore accountStore = chainBaseManager.getAccountStore();
    DynamicPropertiesStore dynamicPropertiesStore = chainBaseManager.getDynamicPropertiesStore();
    DelegatedResourceStore delegatedResourceStore = chainBaseManager.getDelegatedResourceStore();
    DelegatedResourceAccountIndexStore delegatedResourceAccountIndexStore = chainBaseManager
        .getDelegatedResourceAccountIndexStore();

    // 1. unlock the expired delegate resource
    long now = chainBaseManager.getDynamicPropertiesStore().getLatestBlockHeaderTimestamp();
    delegatedResourceStore.unLockExpireResource(ownerAddress, receiverAddress, now);

    //modify DelegatedResourceStore
    long expireTime = 0;
    if (lock) {
      expireTime = now + lockPeriod * BLOCK_PRODUCED_INTERVAL;
    }
    byte[] key = DelegatedResourceCapsule.createDbKeyV2(ownerAddress, receiverAddress, lock);
    DelegatedResourceCapsule delegatedResourceCapsule = delegatedResourceStore.get(key);
    if (delegatedResourceCapsule == null) {
      delegatedResourceCapsule = new DelegatedResourceCapsule(ByteString.copyFrom(ownerAddress),
          ByteString.copyFrom(receiverAddress));
    }

    if (isBandwidth) {
      delegatedResourceCapsule.addFrozenBalanceForBandwidth(balance, expireTime);
    } else {
      delegatedResourceCapsule.addFrozenBalanceForEnergy(balance, expireTime);
    }
    delegatedResourceStore.put(key, delegatedResourceCapsule);

    //modify DelegatedResourceAccountIndexStore
    delegatedResourceAccountIndexStore.delegateV2(ownerAddress, receiverAddress,
        dynamicPropertiesStore.getLatestBlockHeaderTimestamp());

    //modify AccountStore for receiver
    AccountCapsule receiverCapsule = accountStore.get(receiverAddress);
    if (isBandwidth) {
      receiverCapsule.addAcquiredDelegatedFrozenV2BalanceForBandwidth(balance);
    } else {
      receiverCapsule.addAcquiredDelegatedFrozenV2BalanceForEnergy(balance);
    }
    accountStore.put(receiverCapsule.createDbKey(), receiverCapsule);
  }

  public DelegatedResourceAccountIndexCapsule getIndex(byte[] address) {
    DelegatedResourceAccountIndexCapsule indexCapsule = get(address);
    if (indexCapsule != null) {
      return indexCapsule;
    }
    return getWithPrefix(FROM_PREFIX, TO_PREFIX, address);
  }

  public DelegatedResourceAccountIndexCapsule getV2Index(byte[] address) {
    return getWithPrefix(V2_FROM_PREFIX, V2_TO_PREFIX, address);
  }

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }
