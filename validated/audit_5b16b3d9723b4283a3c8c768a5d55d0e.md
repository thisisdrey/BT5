### Title
Integer overflow in ZIP64 central-directory bounds check allows OOB pointer computation on 32-bit systems - (File: third_party/ijar/zip.cc)

### Summary
`FindZipCentralDirectory` in `third_party/ijar/zip.cc` validates that the central directory (offset + size) lies within the mapped file before computing a pointer into it, but the bounds check is vulnerable to unsigned integer overflow when the ZIP64 fields are fully attacker-controlled, mirroring the Monero `round_money_up` class of bug (overflow detection defeated by integer-width/wraparound behavior).

### Finding Description
`FindZip64CentralDirectory`/`MaybeReadZip64CentralDirectory` read `central_dir_size` and `central_dir_offset` directly from the ZIP64 End-Of-Central-Directory record as 64-bit `u8` (`unsigned long long`) values taken verbatim from attacker-supplied bytes via `get_u8le`. [1](#0-0) 
These are then used in `FindZipCentralDirectory`'s single bounds check before computing the central directory pointer: [2](#0-1) 
The check `cd.central_dir_offset + cd.central_dir_size > in_length` performs the addition in 64-bit (`u8`) arithmetic. Since both operands are attacker-controlled and can be set arbitrarily close to `UINT64_MAX`, the sum can wrap around to a small value, causing the check to incorrectly pass. The resulting `*central_dir = end_of_central_dir - cd.central_dir_size` pointer arithmetic and any subsequent central-directory-entry parsing based on `central_dir_offset`/`central_dir_size` then operates on an out-of-bounds or attacker-chosen pointer.

### Impact Explanation
This function gates whether the jar-parsing/interface-jar-generation logic (`ijar`) treats attacker-supplied byte ranges as the ZIP central directory. This code path processes zip/jar files that can originate from external, unprivileged sources (e.g., a jar fetched from a Maven/HTTP dependency URL that is then processed by `ijar` to build a header/interface jar). An integer-overflow bypass of the bounds check could let a maliciously-crafted jar drive the parser to read starting from an out-of-bounds offset (heap buffer over-read), potentially leaking adjacent memory contents into derived build artifacts or causing memory-safety issues in the native tool.

### Likelihood Explanation
The overflow only manifests when the 64-bit sum of `central_dir_offset + central_dir_size` wraps modulo 2^64 — this requires both fields to be very large (close to `UINT64_MAX`), which is achievable because both are read as raw attacker-controlled 8-byte little-endian values with no independent range validation prior to the sum. Unlike the original Monero report (which is specifically a 32-bit `size_t`/`ULONG_MAX` vs `ULLONG_MAX` mismatch), here the vulnerable arithmetic operands are already 64-bit (`u8`), so the practical trigger condition is a pure 64-bit wraparound rather than a type-width mismatch, and it requires constructing extreme edge-value ZIP64 fields. I was not able to fully trace, within the remaining investigation budget, how `central_dir_offset`/`central_dir_size` are subsequently dereferenced (e.g., whether later per-entry parsing independently re-validates offsets before reads), so I cannot confirm with certainty that a wrapped value produces an exploitable out-of-bounds read rather than being caught by a later, independent bounds check.

### Recommendation
Perform the bounds check using overflow-safe arithmetic, e.g. verify `cd.central_dir_size <= in_length` and `cd.central_dir_offset <= in_length - cd.central_dir_size` (checked in that order, or using a saturating/overflow-checked add), and reject the file if either individual field already exceeds `in_length` before summing them.

### Proof of Concept
A JUnit/`BuildIntegrationTestCase`-style reproduction was not verified in this pass; the recommended verification is to add a `src/tools/singlejar`/`third_party/ijar` unit test (analogous to `ZipFileTest`) that constructs a ZIP64 EOCD record with `central_dir_offset` and `central_dir_size` chosen so their 64-bit sum wraps to a value `<= in_length`, then asserts that `FindZipCentralDirectory` rejects the file instead of returning a central-directory pointer. bool FindZip64CentralDirectory(const u1 *bytes, size_t in_length,
                               const u1 **end_of_central_dir,
                               EndOfCentralDirectoryRecord *cd) {
  // In the absence of a zip64 extensible data sector, the zip64 EOCD is at a
  // fixed offset from the regular central directory.
  if (MaybeReadZip64CentralDirectory(
          bytes, in_length,
          *end_of_central_dir - ZIP64_EOCD_LOCATOR_SIZE - ZIP64_EOCD_FIXED_SIZE,
          end_of_central_dir, cd)) {
    return true;
  }

  // If we couldn't find a zip64 EOCD at a fixed offset, either it doesn't exist
  // or there was a zip64 extensible data sector, so try going through the
  // locator. This approach doesn't work if data was prepended to the archive
  // without updating the offset in the locator.
  const u1 *zip64_locator = *end_of_central_dir - ZIP64_EOCD_LOCATOR_SIZE;
  if (zip64_locator - ZIP64_EOCD_FIXED_SIZE < bytes) {
    return true;
  }
  u4 zip64_locator_signature = get_u4le(zip64_locator);
  if (zip64_locator_signature != ZIP64_EOCD_LOCATOR_SIGNATURE) {
    return true;
  }
  u4 disk_with_zip64_central_directory = get_u4le(zip64_locator);
  u8 zip64_end_of_central_dir_offset = get_u8le(zip64_locator);
  u4 zip64_total_disks = get_u4le(zip64_locator);
  if (MaybeReadZip64CentralDirectory(bytes, in_length,
                                     bytes + zip64_end_of_central_dir_offset,
                                     end_of_central_dir, cd)) {
    // TODO(b/228519294) Add a test for a valid zip64 file with total disks = 0
    if (disk_with_zip64_central_directory != 0 || zip64_total_disks > 1) {
      fprintf(stderr, "multi-disk JAR files are not supported\n");
      return false;
    }
    return true;
  }
  return true;
}
