### Title
Stale votes from removed-then-re-added multisig owners silently re-count toward approval threshold, enabling unauthorized transaction execution — (`aptos-move/framework/aptos-framework/sources/multisig_account.move`)

---

### Summary

`update_owner_schema` removes an owner from the `owners` vector but never clears their existing votes from pending transactions' `votes` `SimpleMap`. When that owner is later re-added, `num_approvals_and_rejections_internal` iterates the current `owners` list, finds the re-added owner's stale vote still present in the map, and counts it again — without the owner ever explicitly re-approving the transaction. This mirrors the Ethos root cause exactly: state written at removal time is not cleared at restoration time, causing the restored entity to carry forward a capability it should not have.

---

### Finding Description

Every `MultisigTransaction` stores votes in a per-transaction `SimpleMap<address, bool>`: [1](#0-0) 

`num_approvals_and_rejections_internal` counts approvals by iterating the **current** `owners` vector and checking whether each address has an entry in `votes`. This correctly excludes removed owners — as the existing test `test_validate_transaction_should_not_consider_removed_owners` confirms: [2](#0-1) 

However, `update_owner_schema` — the sole code path for removing owners — only splices the address out of the `owners` vector. It never touches the `transactions` table or the `votes` map inside any pending transaction: [3](#0-2) 

When the same address is later re-added via `add_owners` / `update_owner_schema`, it re-enters the `owners` vector: [4](#0-3) 

At that point `num_approvals_and_rejections_internal` will find the address in `owners`, find its stale `true` entry still present in `votes`, and count it as a fresh approval — without the owner ever calling `approve_transaction` again after being re-added.

---

### Impact Explanation

A pending multisig transaction can reach (or re-reach) the `num_signatures_required` threshold using a vote that was cast before the owner was removed, without that owner's explicit post-reinstatement consent. Any owner or third party can then call `execute_rejected_transaction` or submit a `MultisigTransaction` payload to execute it. Because multisig accounts routinely hold APT, fungible assets, or control over protocol upgrade keys, this constitutes unauthorized transaction execution leading to direct theft or unauthorized state mutation of user-controlled on-chain assets.

---

### Likelihood Explanation

The sequence — owner votes, owner is removed, owner is re-added while the transaction is still pending — is operationally plausible:

1. A compromised or colluding owner (A) creates a malicious transaction T1 and auto-votes yes.
2. A second owner (B) approves T1 (threshold met, but not yet executed).
3. Remaining owners remove B to invalidate T1 (T1 drops below threshold).
4. A later proposes re-adding B (claiming the compromise is resolved); the remaining owners approve.
5. B's stale approval on T1 is silently reinstated; T1 can now be executed without B ever re-approving it.

The re-addition step itself requires k-of-n approval, but the owners approving it may not realize that doing so retroactively re-enables every pending transaction B had previously voted on.

---

### Recommendation

In `update_owner_schema`, after removing an owner, iterate over all pending transactions (from `last_executed_sequence_number + 1` to `next_sequence_number - 1`) and remove the evicted owner's entry from each transaction's `votes` map:

```move
// After removing owners_removed from the owners vector:
let seq = multisig_account_ref_mut.last_executed_sequence_number + 1;
while (seq < multisig_account_ref_mut.next_sequence_number) {
    let tx = multisig_account_ref_mut.transactions.borrow_mut(seq);
    owners_removed.for_each_ref(|removed| {
        if (tx.votes.contains_key(removed)) {
            tx.votes.remove(removed);
        }
    });
    seq = seq + 1;
};
```

Alternatively, store a per-owner "added-at sequence number" and reject votes whose sequence number predates the voter's most recent addition.

### Proof of Concept

```move
#[test(owner_1 = @0x123, owner_2 = @0x124, owner_3 = @0x125)]
fun test_readded_owner_stale_vote_reenables_transaction(
    owner_1: &signer, owner_2: &signer, owner_3: &signer) {
    setup();
    let owner_1_addr = address_of(owner_1);
    let owner_2_addr = address_of(owner_2);
    create_account(owner_1_addr);
    let multisig_account = get_next_multisig_account_address(owner_1_addr);
    // 2-of-2 multisig
    create_with_owners(owner_1, vector[owner_2_addr], 2, vector[], vector[]);

    // Owner 1 creates T1 (auto-votes yes) and owner 2 approves → threshold met
    create_transaction(owner_1, multisig_account, PAYLOAD);
    approve_transaction(owner_2, multisig_account, 1);
    assert!(can_be_executed(multisig_account, 1), 0);

    // Owner 2 is removed → T1 drops below threshold
    let multisig_signer = &create_signer(multisig_account);
    remove_owners(multisig_signer, vector[owner_2_addr]);
    assert!(!can_be_executed(multisig_account, 1), 1);

    // Owner 2 is re-added → stale vote silently reinstated, threshold met again
    // without owner_2 ever calling approve_transaction a second time
    add_owners(multisig_signer, vector[owner_2_addr]);
    assert!(can_be_executed(multisig_account, 1), 2); // BUG: should still be false
}
```

The final assertion passes, demonstrating that T1 is executable again purely because of the stale vote — the re-added owner never re-approved it.

    inline fun num_approvals_and_rejections_internal(owners: &vector<address>, transaction: &MultisigTransaction): (u64, u64) {
        let num_approvals = 0;
        let num_rejections = 0;

        let votes = &transaction.votes;
        owners.for_each_ref(|owner| {
            if (simple_map::contains_key(votes, owner)) {
                if (*simple_map::borrow(votes, owner)) {
                    num_approvals += 1;
                } else {
                    num_rejections += 1;
                };
            }
        });

        (num_approvals, num_rejections)
    }
