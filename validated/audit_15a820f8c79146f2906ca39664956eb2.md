### Title
Borrower can permanently block their own liquidation by spreading dust debt across more low-activity assets than `price-feeds` can refresh in a single call - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`liquidate()` (and every other health-checking entry point) computes the borrower's notional value by calling `get-assets(mask)`, which resolves oracle prices for **every** asset the borrower currently holds as collateral or debt via `price-multi-resolve`. If the price feed for even one of those assets is stale, `price-multi-resolve` fails and the whole call `unwrap-panic`s, aborting the transaction. The only way to avoid this is for the caller to supply fresh feeds via the `price-feeds` parameter, but that parameter is capped at a fixed-size `(list 3 (buff 8192))`. A borrower who opens tiny debt positions in more than 3 distinct assets (permitted by the egroup design, which explicitly allows a single collateral asset to back multiple simultaneous debt assets) can guarantee that at any time at least one of the required oracle feeds is stale, permanently reverting `liquidate()` for that position — even though a liquidator would otherwise be able to fully cover the required capped debt.

### Finding Description
`get-assets` builds the price list for all assets implied by the user's mask and panics if any single price resolution fails: [1](#0-0) [2](#0-1) 

`price-multi-resolve` treats a single failed `price-resolve` as fatal for the entire batch: [3](#0-2) 

`price-resolve` fails with `ERR-ORACLE-INVARIANT` whenever the feed's timestamp exceeds the asset's configured `max-staleness`: [4](#0-3) 

`liquidate()` calls `get-assets(mask)` (via the accrual/notional-evaluation pipeline) for the borrower's full mask before it can perform the health check or compute liquidation amounts, so a stale feed on ANY held asset — collateral or debt, no matter how small — aborts the whole liquidation attempt: [5](#0-4) 

The only mitigation is the `price-feeds` parameter that lets the caller push fresh oracle data before evaluation, but it is bounded to at most 3 entries: [6](#0-5) 

The egroup registry deliberately allows a single collateral asset to be paired with several simultaneous debt assets (e.g. Egroup 1 permits sBTC collateral against STX + sBTC + stSTX + USDC + USDH debt — 5 debt assets plus 1 collateral asset, i.e. 6 assets requiring price resolution): [7](#0-6) 

A borrower can therefore open dust-sized debt in 4+ of the permitted debt assets. As long as more than 3 of the assets in their mask require oracle resolution, no single `liquidate()` call (limited to 3 injected feeds) can guarantee all of them are simultaneously fresh — especially for assets that see infrequent price-feed publication/low market activity, which naturally accumulate staleness. When the position becomes genuinely liquidatable (large real debt in one asset, small dust debt in the others), any attempt to liquidate the large real debt still requires resolving prices for the dust debts too, and reverts if any of those feeds happen to be stale at call time.

### Impact Explanation
This blocks liquidation of an under-collateralized position, i.e., temporary (and potentially indefinite, since the attacker fully controls how many/which dust debts to hold and can keep re-triggering staleness) freezing of lender funds that should be recoverable through liquidation — the equivalent "theft of unclaimed yield / temporary freezing of funds" impact class recognized as in-scope. It also directly threatens protocol solvency since bad debt cannot be socialized via `liquidate`'s bad-debt path if liquidation itself cannot execute.

### Likelihood Explanation
Requires an ordinary user with no special privileges: opening a normal collateral position and taking on multiple small debt positions permitted by an existing DAO-approved egroup (no DAO compromise or egroup misconfiguration needed — this is a property of the general egroup design allowing multiple debt assets against one collateral). Likelihood is proportional to how many multi-debt egroups exist and how tolerant the least-liquid asset's `max-staleness` is versus its actual feed publication cadence; both are realistic given documented per-asset staleness windows as short as 60 seconds for volatile assets.

### Recommendation
- Cap the number of distinct assets a position mask may simultaneously carry (collateral + debt) to be ≤ the number of feeds `price-feeds` can accept, or increase the `price-feeds` list size to match the maximum number of assets any egroup can require.
- Alternatively, make `liquidate()` resilient to a stale price on assets that are not the collateral/debt pair being liquidated — e.g., skip/zero-value assets whose price cannot be freshly resolved rather than reverting the whole call, or allow the liquidator to specify which oracle-resolution failures should be tolerated for irrelevant dust holdings.
- Consider enforcing a minimum debt/collateral value threshold per asset entry (anti-dust) so a borrower cannot cheaply open many trivial positions purely to grief liquidation.

### Proof of Concept
1. Attacker deposits sBTC as collateral and borrows small amounts of 4 different debt assets permitted by an egroup that allows multi-asset debt (e.g., Egroup 1: sBTC collateral + STX/sBTC/stSTX/USDC/USDH debt), so their position mask includes ≥5 assets requiring oracle resolution — see `mainnet/contracts/proposals/mainnet/v0-init.clar:195-197`.
2. Over time, price collapses on the main sBTC-backed USDC debt, making the position genuinely liquidatable (`current-ltv >= ltv-liq-partial`).
3. A liquidator calls `liquidate(borrower, sBTC, USDC, amount, ..., price-feeds)`. Internally `get-liquidation-position`/`get-full-position` → `get-assets(mask)` must resolve oracle prices for all 5+ assets in the mask (`mainnet/contracts/market/v0-4-market.clar:504-514`, `397-418`).
4. `price-feeds` accepts at most 3 buffers (`mainnet/contracts/market/v0-4-market.clar:1382-1390`), so the liquidator cannot refresh all 5+ feeds in one call.
5. If any one of the un-refreshed feeds (typically the least-traded/dust asset) is stale beyond its configured `max-staleness`, `price-resolve` returns `ERR-ORACLE-INVARIANT`, `price-multi-resolve` fails, and `get-assets` panics — aborting the entire `liquidate()` transaction with no way for the liquidator to work around it in a single call.
6. The borrower can keep the dust debts alive indefinitely (repaying/re-borrowing trivial amounts) to make it likely that at least one of their many required feeds is stale at any given liquidation attempt, effectively griefing liquidators and freezing the real, and much larger, under-collateralized debt from being liquidated.

Note: I could not find an on-chain mechanism forcing simultaneous freshness of all held assets' feeds nor a way for the liquidator to batch more than 3 feed updates in one transaction; if `price-feeds` can be widened or the contract allows multiple sequential calls to pre-warm all feeds before `liquidate()` in the same transaction via a wrapper, this would reduce (but the base entry-point-level DoS on a single call remains, and repeated calls cost the liquidator more gas/complexity than in the original design intent).

(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))

        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

        (map-set last-update key timestamp)
        false)
