### Title
Unbounded `VotesStore` growth causes DoS in mandatory `MaintenanceManager.doMaintenance()`/`countVote()` block-application logic - (File: `consensus/src/main/java/org/tron/consensus/dpos/MaintenanceManager.java`)

### Summary
`VoteWitnessContract` transactions are unbounded in number of distinct voter accounts. Each vote adds/updates one entry in `VotesStore`. This store is fully iterated, entry-by-entry, inside `MaintenanceManager.doMaintenance()`'s `countVote()` — mandatory logic that every full node executes synchronously while applying the block that crosses a maintenance-time boundary.

### Finding Description
`VoteWitnessProcessor.execute()` (and the corresponding `VoteWitnessActuator`) let any account with tron power/frozen balance cast votes for witnesses; it creates a `VotesCapsule` in `VotesStore` keyed by voter address if one does not exist yet, with only a per-account limit `MAX_VOTE_NUMBER` on the number of distinct witnesses voted for — there is no limit on the number of distinct voter accounts that can each add an entry to `VotesStore`. [6](#0-5) 

On every block whose timestamp crosses `nextMaintenanceTime`, `Manager.processBlock()` unconditionally calls `consensus.applyBlock(block)`, which calls `MaintenanceManager.applyBlock()` → `doMaintenance()`: [7](#0-6) [2](#0-1) [8](#0-7) 

`doMaintenance()` calls `countVote(votesStore)`, which uses a full DB iterator over the entire `VotesStore` and, for every entry, iterates its `getOldVotes()`/`getNewVotes()` lists, performing `HashMap` reads/writes, and finally deletes the key: [4](#0-3) 

This entire scan happens inside `processBlock()`, which is executed under the `synchronized (this)` block in `Manager.pushBlock()` (the main block-application critical section): [9](#0-8) [10](#0-9) 

Because `VotesStore` entries are only deleted as they are consumed inside this very loop (not pruned beforehand), an attacker who cheaply activates a very large number of accounts (minimum account-creation fee) and casts one `VoteWitnessContract` from each before a maintenance boundary can inflate `VotesStore` to millions of entries. The maintenance block that follows must then synchronously process the entire bloated store before the block can be committed.

### Impact Explanation
If the scan of `VotesStore` cannot complete within the allotted block-production/processing time, the node that must apply this block (every witness and every syncing/observing full node) either misses its production slot or falls behind in synchronization, since `processBlock()` must fully finish before the block is committed and the lock is released. Because this code path is mandatory and identical on every node (not opt-in or configurable), a sufficiently large `VotesStore` can delay or stall block production/consensus across the network — a liveness/availability failure of the chain, not merely a single node's resource exhaustion.

### Likelihood Explanation
Reaching this path requires no special privilege: any address can freeze a small amount of TRX for `TRON_POWER`/bandwidth and issue a `VoteWitnessContract`. Account activation and freezing cost is attacker-controlled and can be amortized across many low-value accounts. The maintenance interval is fixed and predictable (`getNextMaintenanceTime`), so an attacker can time the creation of a large `VotesStore` right before a maintenance boundary. The primary cost to the attacker is cumulative transaction/activation fees and bandwidth/energy, which scale roughly linearly with the number of entries created, while the defender's per-maintenance-cycle cost scales similarly — making this a "linear cost, linear damage" DoS whose real-world severity depends on how cheaply many accounts/votes can be created relative to the resulting scan cost and block-time budget.

### Recommendation
- Bound the total number of live entries permitted in `VotesStore` (e.g., cap concurrently active voter accounts or require minimum vote/stake thresholds before a vote is persisted), or
- Avoid a single unbounded synchronous scan in `doMaintenance()`: incrementally process/prune `VotesStore` across multiple blocks (batching) instead of a single full-store iteration in one maintenance block, and/or
- Charge/require a resource cost for casting a vote that scales with the storage impact it creates (e.g., higher minimum frozen balance) to make store-inflation economically costly.

### Proof of Concept
1. Create N (e.g., 100,000+) distinct accounts, each funded with the minimal TRX needed to activate and freeze the minimum amount for `TRON_POWER`/bandwidth.
2. From each account, submit one `VoteWitnessContract` transaction (one active witness address, vote count 1) before the next `nextMaintenanceTime` boundary — this creates N entries in `VotesStore` via `VoteWitnessProcessor.execute()`/`VoteWitnessActuator`.
3. Once the timestamp of an incoming block passes `nextMaintenanceTime`, every node applying that block calls `Manager.processBlock()` → `consensus.applyBlock()` → `MaintenanceManager.doMaintenance()` → `countVote(votesStore)`, which must synchronously iterate all N `VotesStore` entries (with per-entry sub-list iteration and map operations) while holding the block-application lock.
4. Measure the wall-clock time of that block's application versus the network's block interval; with sufficiently large N this scan can exceed the block time budget, delaying/blocking block commitment on every node that must apply it.

  private Map<ByteString, Long> countVote(VotesStore votesStore) {
    final Map<ByteString, Long> countWitness = Maps.newHashMap();
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();
    long sizeCount = 0;
    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) - voteCount);
        } else {
          countWitness.put(voteAddress, -voteCount);
        }
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) + voteCount);
        } else {
          countWitness.put(voteAddress, voteCount);
        }
      });
      sizeCount++;
      votesStore.delete(next.getKey());
    }
    logger.info("There is {} new votes in this epoch", sizeCount);
    return countWitness;
  }
