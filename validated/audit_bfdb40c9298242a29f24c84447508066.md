Based on my investigation, the `UpdateReferences` RPC accepts a client-streamed, unbounded number of reference updates per transaction with no enforced limit on count, closely mirroring the "too many stakes / unbounded per-user loop" bug class from the report — an ordinary user (anyone who can call gRPC/push through a repo they have write access to, or via GitLab-mediated calls) can supply an arbitrarily large number of `Update` entries across the stream.

### Title
Unbounded number of reference updates per `UpdateReferences` transaction enables resource-exhaustion DoS - (File: internal/gitaly/service/ref/update_references.go)

### Summary
`UpdateReferences` receives a client-side stream of `UpdateReferencesRequest` messages, each carrying an arbitrary number of `Update` entries, and queues every one of them into a single `git-update-ref --stdin` transaction with no cap on the total number of updates.

### Finding Description
The handler loop reads every incoming stream message and, for each one, iterates `request.GetUpdates()` calling `updater.Update()` for every entry without ever checking a maximum count, before finally calling `updater.Commit()` once EOF is reached: [1](#0-0) . The `updateref.Updater.Update` method has no built-in count limit either — it simply writes another `update` command into the `update-ref --stdin` process for every call: [2](#0-1) . This is structurally the same class of issue as the reported bug: an operation that iterates over an entire caller-supplied collection ("all of a user's stakes") with no upper bound, so a large collection inflates the cost of a single atomic operation. Here, a caller can stream an unbounded number of updates across multiple `UpdateReferencesRequest` messages (the only per-message constraint is that each individual message must contain at least one update: [3](#0-2) ), all of which get buffered into one huge `update-ref --stdin` transaction that must be validated and committed atomically inside the storage transaction manager.

### Impact Explanation
A large number of updates in a single call causes proportionally large CPU/memory usage in `git-update-ref`, in the reference-transaction hook parsing (`parseChanges` reads the entire stdin then builds a map per update: [4](#0-3) ), and in `TransactionManager.UpdateReferences`, which loops over every update again to merge state: [5](#0-4) . Because this all happens within one atomic transaction, an oversized request can consume disproportionate gRPC handler time, memory, and reference-lock hold duration, degrading or blocking the storage partition for other operations — a DoS of the RPC handler and potentially of the enclosing partition/transaction manager.

### Likelihood Explanation
Any ordinary user with write access to a repository (or any RPC caller with access to `RefService.UpdateReferences`) can trigger this simply by streaming a large number of update entries; there is no authentication bypass needed, only normal access to the mutator RPC.

### Recommendation
Enforce a maximum number of reference updates accepted per `UpdateReferences` transaction (either per-message or cumulative across the stream), returning `InvalidArgument`/`ResourceExhausted` once the limit is exceeded, similar to the `limit` fields already used elsewhere in `ref.proto` (e.g., `ListBlobsRequest.limit`, `FindRefsByOIDRequest.limit`): [6](#0-5) .

### Proof of Concept
A client opens the `UpdateReferences` stream and sends the first request with `Repository` set and one `Update`, then continues streaming thousands to millions of subsequent `UpdateReferencesRequest` messages each containing additional `Update` entries (e.g., creating/deleting distinct branch names) before closing the stream. The server accepts and queues all of them: [1](#0-0) , causing large-scale resource consumption in a single Commit call.

// Update commands the reference to be updated to point at the object ID specified in newOID. If
// newOID is the zero OID, then the branch will be deleted. If oldOID is a non-empty string, then
// the reference will only be updated if its current value matches the old value. If the old value
// is the zero OID, then the branch must not exist.
//
// A reference transaction must be started before calling Update.
func (u *Updater) Update(reference git.ReferenceName, newOID, oldOID git.ObjectID) error {
	if err := u.expectState(stateStarted); err != nil {
		return err
	}

	return u.write("update %s\x00%s\x00%s\x00", reference.String(), newOID, oldOID)
}

func parseChanges(objectHash git.ObjectHash, changes io.Reader) (git.ReferenceUpdates, error) {
	scanner := bufio.NewScanner(changes)

	updates := git.ReferenceUpdates{}
	for scanner.Scan() {
		line := scanner.Text()
		components := strings.Split(line, " ")
		if len(components) != 3 {
			return nil, fmt.Errorf("unexpected change line: %q", line)
		}

		reference := git.ReferenceName(components[2])

		// We only track updates made in the 'refs/' directory.
		// An exception to this is when HEAD is updated.
		if !strings.HasPrefix(reference.String(), "refs/") && reference.String() != "HEAD" {
			continue
		}

		update := git.ReferenceUpdate{}

		var err error

		if _, target, ok := strings.Cut(components[0], "ref:"); ok {
			update.OldTarget = git.ReferenceName(target)
		} else {
			update.OldOID, err = objectHash.FromHex(components[0])
			if err != nil {
				return nil, fmt.Errorf("parse old: %w", err)
			}
		}

		if _, target, ok := strings.Cut(components[1], "ref:"); ok {
			update.NewTarget = git.ReferenceName(target)
		} else {
			update.NewOID, err = objectHash.FromHex(components[1])
			if err != nil {
				return nil, fmt.Errorf("parse new: %w", err)
			}
		}

		// Only capture default branch changes and ignore all other symbolic reference updates.
		if reference.String() != "HEAD" && (update.NewTarget != "" || update.OldTarget != "") {
			continue
		}

		// If the default branch is being deleted, we ignore updating HEAD
		//
		// TODO: This can be removed once the bug in Git itself is fixed
		// https://gitlab.com/gitlab-org/git/-/issues/348
		if reference.String() == "HEAD" && update.NewTarget == "" {
			continue
		}

		updates[reference] = update
	}

	return updates, nil
}

func (txn *Transaction) UpdateReferences(ctx context.Context, updates git.ReferenceUpdates) error {
	u := git.ReferenceUpdates{}

	for reference, update := range updates {
		// Transactions should only stage references with valid names as otherwise Git would already
		// fail when they try to stage them against their snapshot. `update-ref` happily accepts references
		// outside of `refs` directory so such references could theoretically arrive here. We thus sanity
		// check that all references modified are within the refs directory.
		//
		// HEAD is a special case and refers to a default branch update.
		if !strings.HasPrefix(reference.String(), "refs/") && reference != "HEAD" {
			return InvalidReferenceFormatError{ReferenceName: reference}
		}

		oldOID := update.OldOID
		oldTarget := update.OldTarget

		if initialValue, ok := txn.initialReferenceValues[reference]; ok {
			if !initialValue.IsSymbolic {
				oldOID = git.ObjectID(initialValue.Target)
			} else {
				oldTarget = git.ReferenceName(initialValue.Target)
			}
		}

		if oldOID == update.NewOID && oldTarget == update.NewTarget {
			// This was a no-op.
			continue
		}

		for _, updates := range txn.referenceUpdates {
			if txUpdate, ok := updates[reference]; ok {
				if txUpdate.NewOID != "" {
					oldOID = txUpdate.NewOID
				}

				if txUpdate.NewTarget != "" {
					oldTarget = txUpdate.NewTarget
				}
			}
		}

		u[reference] = git.ReferenceUpdate{
			OldOID:    oldOID,
			NewOID:    update.NewOID,
			OldTarget: oldTarget,
			NewTarget: update.NewTarget,
		}
	}
