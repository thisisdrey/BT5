### Title
Protocol fees on NEP-245/IMT tokens can be fully bypassed by splitting a `TokenDiff` into unit-delta (`|delta| == 1`) legs - (`File: contracts/defuse/core/src/intents/token_diff.rs`)

### Summary
`TokenDiff::execute_intent` computes the fee for each negative delta independently, per intent, using `TokenDiff::token_fee`, which returns `Pips::ZERO` for `TokenIdType::Nep245`/`Imt` whenever the per-intent `amount <= 1`. An attacker can decompose one large NEP-245 (or IMT) `token_in` amount into many separate `TokenDiff` intents each moving exactly `1` unit, so every individual fee computation hits the zero-fee branch and the aggregate fee collected across the batch is `0`, whereas a single aggregate `TokenDiff` of the same net amount would owe `Pips::fee_ceil(protocol_fee, amount)`.

### Finding Description
The broken binding is: `fees_collected[T] == Pips::fee_ceil(protocol_fee, amount)` for the *total* `token_in` amount `T` moved by a signer in a batch. In the actual code, this is computed per intent-per-key, not per aggregate amount: [1](#0-0) 

`amount` here is `delta.unsigned_abs()` for a single `TokenId` entry inside one signed `TokenDiff.diff` (a `BTreeMap<TokenId, i128>`, so only one delta per token per intent). The fee itself is derived from `TokenDiff::token_fee`: [2](#0-1) 

For `TokenIdType::Nep245` and `TokenIdType::Imt`, if `amount > 1` the normal `fee` is used, but if `amount <= 1` it unconditionally returns `Pips::ZERO`. This branch exists to avoid fractional-fee issues on NFT-like MT items, but NEP-245 also represents fungible-like MT balances with large quantities, so the exemption is exploitable there.

Exploit flow (fully unprivileged, self-contained):
1. Attacker funds a Defuse balance of `N` units of some NEP-245 token `T` (e.g. via deposit with `msg`), and controls a second counterparty account (their own second key/account) holding `N * x` units of some token `U`.
2. Instead of signing one `TokenDiff` intent `{T: -N, U: +N*x}` matched by a counter `TokenDiff` `{T: +N, U: -N*x}` (which would incur `fee.fee_ceil(N)` on `T`), the attacker signs `N` separate `TokenDiff` intents, each `{T: -1, U: +x}`, matched by `N` separate counter-intents `{T: +1, U: -x}`.
3. Each of the `2N` intents is executed independently by `execute_intent`; for every negative delta on `T`, `amount == 1`, so `TokenDiff::token_fee` returns `Pips::ZERO`, and `fees_collected` for `T` is `0` in every single intent.
4. The whole `MultiPayload` batch still nets to zero across all tokens (`TransferMatcher::finalize` in `contracts/defuse/core/src/engine/state/deltas.rs` only checks that per-token deltas sum to zero across the batch, not fee correctness), so it settles successfully via `execute_intents`.
5. Net effect: `fee_collector`'s balance for `T` receives `0` instead of `fee.fee_ceil(N)`, while the exact same net position change (`N` units of `T` for `N*x` units of `U`) is achieved as if done in one intent.

No existing guard prevents this: `MultiPayload::verify` and nonce/signature checks only validate authenticity of each of the `N` separate signed intents (which are all validly signed), `TransferMatcher::finalize` only enforces net-zero balances across the batch, and there is no batch-level or account-level accumulation of `amount` used for fee computation — it is always the single intent's per-token delta.

### Impact Explanation
Protocol fee revenue on NEP-245/IMT-denominated swaps can be reduced to zero by any signer willing to split trades into unit legs, at the cost of extra signed intents. This falls squarely into the listed Critical category "protocol fees bypassed or over-collected" — value (the protocol fee) that should be credited to `fee_collector` never leaves the trading parties. It is repeatable indefinitely, for any NEP-245/IMT token, any amount, and any account pair the attacker controls (does not require any privileged role, relayer key, or third-party victim).

### Likelihood Explanation
Preconditions are minimal: the attacker needs a funded NEP-245/IMT balance under their own account, one counterparty account they also control (or a colluding/non-fee-sensitive counterparty), and a non-zero `protocol_fee` configured for that token type. Cost scales linearly with the number of unit legs (`N` signed intents / additional gas), which is a normal transaction cost, not resource exhaustion of the network. This is directly demonstrable in a unit test against `Engine`/`TokenDiff::execute_intent` without any sandbox dependencies.

### Recommendation
Compute the NEP-245/IMT fee-exemption threshold based on something that cannot be trivially split across the batch — e.g., only exempt genuine NFT-like MT tokens (a per-`TokenId` supply/decimals property, or a separate `TokenIdType` distinguishing NFT-like vs fungible-like NEP-245 tokens) rather than an ad hoc `amount <= 1` check on each individual intent's delta. Alternatively, track and enforce fee accounting at the account/token/batch aggregate level rather than per single `TokenDiff.diff` entry, so splitting `token_in` across multiple intents cannot reduce the total fee owed.
