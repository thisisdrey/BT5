## Title
Every incremental `borrow()` call unconditionally overwrites `last-borrow-block`, letting a borrower indefinitely refresh the same-block liquidation shield with a trivial top-up borrow - (File: `mainnet/contracts/market/v0-market-vault.clar`)

### Summary
`debt-add-scaled` in `market-vault` unconditionally overwrites the position's `last-borrow-block` field to the current `stacks-block-height` on **every** call, not just the first time debt is opened for an account. This value is later used by `market.clar`'s `liquidate` function as an "oracle frontrunning protection" that blocks liquidation if `last-borrow-block` equals the current block. Because the field is refreshed unconditionally rather than being preserved/left untouched for existing debt, any account with an open debt position can re-arm this single-block liquidation shield at will by taking on a trivial extra amount of debt, as long as the position is still under the (lower) borrow-LTV threshold at that moment.

### Finding Description
`debt-add-scaled` merges the account's position with `{ mask: update-mask, last-update: stacks-block-time, last-borrow-block: stacks-block-height }` on every invocation: [1](#0-0) 

This mirrors the `add_stake` root cause pattern from the report: a resource top-up operation (`add_stake` / incremental `borrow`) resets a protection/eligibility timestamp field to the current value on every call instead of leaving an already-set "start" marker untouched. In `add_stake`, the field controlled reward eligibility; here, `last-borrow-block` controls the liquidator-blocking "same block" check performed in `liquidate`: [2](#0-1) 

The intent (per the inline comment "prevent same-block liquidation... blocks flash-loan based attacks where user borrows + gets liquidated in same block") is to protect a *first-time* borrower from being liquidated in the same block their debt was opened, guarding against atomic flashloan/oracle-manipulation sequences. However, because the write happens on every subsequent `debt-add-scaled` call for that account (any asset, any amount), an existing borrower can re-trigger it by calling `market.clar`'s public `borrow()` with a dust amount: [3](#0-2) 

The only gate on this dust borrow is `is-healthy` measured against the **borrow** LTV threshold on the *current* mask/position, which is a separate (and normally more conservative) threshold than the **liquidation** LTV threshold checked in `liquidate`: [4](#0-3) 

Because `borrow()` may use whatever price data is currently on hand (feeds are only refreshed if the caller explicitly supplies `price-feeds`), a borrower can perform the dust top-up using stale, favorable oracle data whenever their position still evaluates as "healthy" under the borrow threshold, even if a pending price update (about to be pushed by a liquidator in the same block) would make the position liquidatable. Once the dust borrow lands first in that block, `last-borrow-block` is set to that block height, and any `liquidate` call attempted in the same block reverts with `ERR-LIQUIDATION-BORROW-SAME-BLOCK` regardless of the fresh price the liquidator supplies.

### Impact Explanation
This is a griefing/DoS vector against liquidation execution: a borrower approaching liquidation can repeatedly self-refresh the "same block" shield with negligible-cost dust borrows, delaying legitimate liquidation of an under-collateralized position. In a fast-moving market this buys the attacker additional blocks to withdraw value, avoid the liquidation penalty, or let the position accrue further into bad debt before it can finally be liquidated — increasing the amount of debt that must ultimately be socialized via `socialize-debt-asset`/bad-debt-socialization, i.e., temporary freezing of the market's ability to protect solvency and elevated risk of protocol insolvency from delayed liquidations. This lands in the in-scope "temporary freezing of funds" / insolvency-risk impact category.

### Likelihood Explanation
Likelihood is limited by the requirement that the account remain under the borrow-LTV threshold at the moment of the dust borrow, and by liquidators potentially targeting the position in a subsequent block once the shield lapses. It is a self-service, unprivileged action requiring no special permissions or external actors, and can be executed cheaply and repeatedly by any account with an open debt position, making it a low-cost, reachable griefing pattern rather than a one-off edge case.

### Recommendation
Only set `last-borrow-block` (and the related first-borrow bookkeeping) when the account is opening a *new* debt position (i.e., when the asset bit in `mask` transitions from not-set to set, analogous to `resolve-or-create` first insertion), or otherwise preserve the earliest/first borrow block rather than overwriting it on every incremental `debt-add-scaled` call — mirroring the correct fix pattern from the referenced report (use the value that reflects the true start of exposure, not `max`/overwrite-to-current on every top-up).

### Proof of Concept
1. Alice opens a debt position at block `N` via `borrow()`; `market-vault.debt-add-scaled` sets `last-borrow-block = N`.
2. Over time, collateral price declines such that Alice's position approaches the liquidation LTV threshold but still satisfies the (lower) borrow-LTV threshold using stale cached price data.
3. At block `N+k`, right before a liquidator's transaction (which supplies fresh price feeds) is expected to land, Alice calls `borrow()` for a dust amount using no/older `price-feeds`; the health check passes against the stale/favorable price, and `debt-add-scaled` resets `last-borrow-block = N+k`.
4. In the same block, the liquidator's `liquidate` call hits `same-block-check` at [5](#0-4)  and reverts with `ERR-LIQUIDATION-BORROW-SAME-BLOCK`.
5. Alice repeats step 3 in subsequent blocks as needed (while still under the borrow-LTV threshold) to keep re-arming the shield, delaying liquidation of an increasingly risky position.
