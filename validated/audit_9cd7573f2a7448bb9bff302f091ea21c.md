The claim rests on a false premise about what `ColdVacant` in the hot state delta actually means. Let me trace the full architecture to show why.

**Architecture of `get_persisted_state()`**

`CachedStateView::new` calls `reader.get_persisted_state()`, which calls `PersistedState::get_state()`, which calls `HotState::get_committed()`: [1](#0-0) [2](#0-1) 

This returns `(committed.view, committed.state)`. The `committed.state` is the latest persisted state (set via `PersistedState::set()` → `hot_state.enqueue_commit(state)`). So `base_version = committed.state.version()` is the persisted state version, and the cold DB at `base_version` is authoritative for that version. [3](#0-2) 

**What `ColdVacant` in the delta actually means**

The `LayeredHotStateView.delta` is built as `to_commit.make_delta(&merged_state)` — it covers changes from `merged_state` (what the DashMaps reflect) to `committed.state` (the persisted state): [4](#0-3) 

A `ColdVacant` slot in the delta is produced only by `slot.to_cold()` on a `HotVacant` slot during LRU eviction: [5](#0-4)
