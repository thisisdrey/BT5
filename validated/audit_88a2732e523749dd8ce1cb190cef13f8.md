### Title
Stale `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` rows survive `remove_account`, letting a self-targeted delayed action receipt execute with escalated permission against a later re-created same-named account - (File: `core/store/src/utils/mod.rs`, `runtime/runtime/src/lib.rs`, `runtime/runtime/src/actions.rs`)

### Summary
`remove_account` [1](#0-0)  only removes the `Account`, `ContractCode`, `AccessKey`/gas-key, and `ContractData` rows for a deleted account, but never touches `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, or `TrieKey::PostponedReceiptId` rows keyed under the same `receiver_id`. `action_delete_account` performs no check for outstanding postponed receipts before calling `remove_account` [2](#0-1) . When the missing `DataReceipt` later arrives, `process_receipt` looks the postponed receipt up purely by account name and executes it via `apply_action_receipt` against whatever account currently occupies that name [3](#0-2) , with `actor_id` set from the *original* `receipt.predecessor_id()` [4](#0-3) , and `check_actor_permissions` only performs a name-equality check (`actor_id == account_id`), not an identity/incarnation check [5](#0-4) .

### Finding Description
The scenario:
1. Attacker controls account `A` (which must be a name reusable by a fixed authority — either `A` is a sub-account created by a specific parent account `P` that later recreates the same sub-account name for a new, unrelated tenant, since sub-account creation is restricted to `account_id.is_sub_account_of(predecessor_id)` [6](#0-5) , or top-level names restricted to the `registrar` account).
2. From `A`, attacker submits a `FunctionCall` on itself that issues a cross-contract `promise_then` targeting itself, creating an `ActionReceipt` with `predecessor_id = A`, `receiver_id = A`, and an unmet `input_data_id`. `process_action_receipt` stores `PostponedReceiptId{receiver_id: A, data_id}`, `PendingDataCount{receiver_id: A, receipt_id}`, and `set_postponed_receipt` (`PostponedReceipt{receiver_id: A, receipt_id}`) [7](#0-6) , with the receipt's action list containing e.g. `AddKey(FullAccess, attacker_key)`.
3. Attacker delays resolution of the dependency (e.g. by chaining further cross-shard hops) and submits `DeleteAccount(beneficiary=A)` from `A`. `check_actor_permissions` allows it (`actor_id == account_id == A`, zero locked stake) [8](#0-7) , and `remove_account` wipes the `Account`/keys/code/data but leaves the three postponed-receipt rows intact [9](#0-8) .
4. The parent authority (or registrar) later re-creates `A` for a new, unrelated owner via `CreateAccountAction`, which succeeds unconditionally as long as the naming rule is satisfied — there is no check for leftover postponed-receipt state [10](#0-9) .
5. When the delayed `DataReceipt` finally arrives at `A`, `process_receipt` finds the still-present `PostponedReceiptId`/`PendingDataCount`, fetches and executes the stored `PostponedReceipt` via `apply_action_receipt` [11](#0-10) . Inside, `account = get_account(state_update, account_id)` fetches the *new* owner's account [4](#0-3) , while `actor_id` is still the stale `A` string from the old receipt. `check_actor_permissions` compares `actor_id == account_id` as plain strings — both are `"A"` — so it passes, letting the stored `AddKey`/`DeployContract`/`DeleteKey` actions mutate the new owner's account.

This is a genuine escalation because authorization here is bound to the account *name*, not to a specific account incarnation/owner; no invariant ties the postponed receipt to the account's identity (e.g. a creation nonce or storage root) at delivery time.

### Impact Explanation
This allows authorization escalation across account lifecycles — an old account controller can plant a privileged action (`AddKey(FullAccess)`, `DeployContract`, `DeleteKey`) that fires against whoever legitimately re-registers the same account name later, hijacking that new owner's keys/contract. This matches the "authorization escalation across accounts / account hijack of a re-created name" bounty category.

### Likelihood Explanation
Feasibility is real but constrained: the attacker cannot pick an arbitrary victim/timing — the account name must be one whose creation authority is a specific parent/registrar that reuses names (a realistic pattern for hosting/faucet-style subaccount issuance, e.g. `<tenant>.<platform>.near`), and the attacker only controls the width of the vulnerable window (by delaying the dependency resolution via extra cross-contract hops or congestion), not the exact moment the name gets reused. Cost to the attacker is a handful of low-value transactions (funding `A`, one `FunctionCall`, one `DeleteAccount`), fully repeatable against any subaccount-issuing authority that does not itself defend against name reuse.

### Recommendation
`remove_account` should also purge any `PostponedReceipt`, `PendingDataCount`, and `PostponedReceiptId` rows still keyed under the account being deleted (iterate/clear these prefixes the same way access keys and contract data are cleared), and/or `action_delete_account` should refuse deletion while such pending state exists for the account, mirroring the existing size/gas-key-balance deletion guards.

### Proof of Concept
Runtime integration test (extending the existing `runtime/runtime/src/tests/apply.rs` delete/recreate harness, e.g. near `test_function_call_after_same_chunk_delete_recreate_resolves_fresh_code` [12](#0-11) ):
1. Create account `child.alice.near` under `alice.near`.
2. Have `child.alice.near` create a postponed `ActionReceipt` (`receiver_id = predecessor_id = child.alice.near`) with an unmet `input_data_id` and an `AddKey(FullAccess, attacker_key)` action; assert `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` are present in state.
3. Apply a `DeleteAccount(beneficiary=alice.near)` receipt from `child.alice.near`; assert the account/keys are gone but the postponed rows remain in the trie.
4. Have `alice.near` `CreateAccount` the same `child.alice.near` name (new owner) and deploy a contract for it.
5. Deliver the resolving `DataReceipt` for the original `data_id`.
6. Assert `apply_action_receipt` executed successfully and `get_access_key(child.alice.near, attacker_key)` is `Some`, proving the old controller's `AddKey` mutated the newly re-created account.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}

    account_creation_config: &AccountCreationConfig,
    account: &mut Option<Account>,
    actor_id: &mut AccountId,
    account_id: &AccountId,
    predecessor_id: &AccountId,

    if account_id.is_top_level() {
        if account_id.len() < account_creation_config.min_allowed_top_level_account_length as usize
            && predecessor_id != &account_creation_config.registrar_account_id
        {
            // A short top-level account ID can only be created registrar account.
            result.result = Err(ActionErrorKind::CreateAccountOnlyByRegistrar {
                account_id: account_id.clone(),
                registrar_account_id: account_creation_config.registrar_account_id.clone(),
                predecessor_id: predecessor_id.clone(),
            }
            .into());
            return;
        } else {
            // OK: Valid top-level Account ID
        }
    } else if !account_id.is_sub_account_of(predecessor_id) {
        // The sub-account can only be created by its root account. E.g. `alice.near` only by `near`
        result.result = Err(ActionErrorKind::CreateAccountNotAllowed {
            account_id: account_id.clone(),
            predecessor_id: predecessor_id.clone(),
        }
        .into());
        return;
    } else {
        // OK: Valid sub-account ID by proper predecessor.
    }

    *actor_id = account_id.clone();
    *account = Some(Account::new(
        Balance::ZERO,
        Balance::ZERO,
        AccountContract::None,
        fee_config.storage_usage_config.num_bytes_account,
    ));
}
