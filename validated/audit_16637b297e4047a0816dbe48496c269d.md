Audit Report

## Title
Unbounded `nonce` accepted in `InboundQueue::add_tip` permanently locks user funds - (File: bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs)

## Summary
`InboundQueue::add_tip` accepts any caller-supplied `u64` nonce as long as `Nonce::<T>::get(nonce)` is `false`, with no check that the nonce corresponds to a legitimate, soon-to-arrive Ethereum message. A signed AssetHub user can reach this via `pallet-snowbridge-system-frontend::add_tip` → `pallet-snowbridge-system-v2::add_tip`, causing already-burned/transacted Ether value to be stored against a nonce that will never be consumed, permanently stranding it in the `Tips` storage map with no expiry or reclaim path.

## Finding Description
The dispatch chain is: `pallet-snowbridge-system-frontend::add_tip` (signed origin, AssetHub) swaps the caller's asset for Ether and burns it, then XCM-Transacts a call to BridgeHub [1](#0-0) . On BridgeHub, `pallet-snowbridge-system-v2::add_tip` dispatches to `InboundQueue::add_tip` for `MessageId::Inbound(nonce)` [2](#0-1) .

`InboundQueue::add_tip`'s only guard is that the nonce has not already been processed (`!Nonce::<T>::get(nonce)`); it performs no validation that `nonce` is within any bounded/expected window relative to the current inbound nonce counter: [3](#0-2) . The `NonceBitmap`/`Nonce` type only tracks processed nonces via `process_message`, which sets the bit and drains any accumulated `Tips` entry for real, verified messages [4](#0-3) . There is no tracking of "expected" or "pending" nonces analogous to `OutboundQueue`'s `PendingOrders`, which correctly rejects tips for unknown nonces via `AddTipError::UnknownMessage` [5](#0-4) .

Because `InboundQueue::add_tip` returns `Ok(())` for any not-yet-consumed nonce, `system-v2::add_tip` treats the call as a success and never routes the amount to `LostTips`, which only triggers on an `Err` result [2](#0-1) . If the nonce never arrives from Ethereum (e.g., a bogus or far-future `u64`), the `Tips::<T>` entry persists indefinitely since only `process_message` (triggered by an actual verified Ethereum event with that exact nonce) drains it — with no other dispatchable capable of reclaiming or expiring it.

## Impact Explanation
This matches the "permanent user-fund lock" impact category in the gate: an unprivileged, signed AssetHub account can cause real value (already swapped/burned into Ether and transacted to BridgeHub) to become permanently unrecoverable in `Tips` storage, since no message with an unbound/bogus nonce will ever be processed to release it, and the pallet provides no expiry or reclaim mechanism, unlike `OutboundQueue::add_tip`'s bounded `PendingOrders` check.

## Likelihood Explanation
High likelihood: exploitation requires only a single unprivileged signed extrinsic (`system-frontend::add_tip`) reachable by any AssetHub account, with no governance, relayer, or validator collusion needed. The missing check is a straightforward omission relative to the sibling `OutboundQueue::add_tip` implementation, which validates against `PendingOrders` before accepting a tip.

## Recommendation
Bind `InboundQueue::add_tip` to a legitimate, bounded nonce range — e.g., only accept nonces within `[current_nonce+1, current_nonce+MaxTipAheadWindow]`, or maintain a pending/expected-nonce tracking structure analogous to `OutboundQueue`'s `PendingOrders` — and reject out-of-window nonces with `AddTipError::UnknownMessage` so `system-v2::add_tip` correctly routes the amount into `LostTips` instead of silently stranding it in `Tips`.

## Proof of Concept
1. A signed AssetHub user calls `EthereumSystemFrontend::add_tip(origin, MessageId::Inbound(u64::MAX - 1), asset)` with a nonzero asset.
2. The asset is swapped to Ether and burned, then XCM-Transacted to BridgeHub via `system-frontend::add_tip`.
3. BridgeHub's `EthereumSystemV2::add_tip` dispatches to `InboundQueue::add_tip(u64::MAX - 1, amount)`.
4. `Nonce::<T>::get(u64::MAX - 1)` is `false` (and will never become `true`, since real Ethereum nonces are sequential and far from `u64::MAX`), so `Tips::<T>::mutate` inserts the tip and the call returns `Ok(())`.
5. `TipProcessed { success: true, .. }` is emitted; `LostTips` is untouched, and the tip value remains permanently unrecoverable in `Tips` storage.

			sender: AccountIdOf<T>,
			message_id: MessageId,
			amount: u128,
		) -> DispatchResult {
			T::FrontendOrigin::ensure_origin(origin)?;

			let result = match message_id {

			};

			if let Err(ref e) = result {
				tracing::debug!(target: LOG_TARGET, ?e, ?message_id, ?amount, "error adding tip");
				LostTips::<T>::mutate(&sender, |lost_tip| {
					*lost_tip = lost_tip.saturating_add(amount);
				});
			}

			Self::deposit_event(Event::<T>::TipProcessed {
				sender,
				message_id,
				amount,
				success: result.is_ok(),
			});

			Ok(())
		}

	impl<T: Config> Pallet<T> {
		pub fn process_message(relayer: T::AccountId, message: Message) -> DispatchResult {
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == message.gateway, Error::<T>::InvalidGateway);

			let (nonce, relayer_fee) = (message.nonce, message.relayer_fee);

			// Verify the message has not been processed
			ensure!(!Nonce::<T>::get(nonce), Error::<T>::InvalidNonce);

			// Mark message as received
			Nonce::<T>::set(nonce);

			let message_id = T::MessageProcessor::process_message(relayer.clone(), message)
				.map_err(|e| match e {
					MessageProcessorError::ProcessMessage(e) => e,
					MessageProcessorError::ConvertMessage(e) => Error::<T>::from(e).into(),
					MessageProcessorError::SendMessage(e) => Error::<T>::from(e).into(),
				})?;

			// Pay relayer reward
			let tip = Tips::<T>::take(nonce).unwrap_or_default();
			let total_tip = relayer_fee.saturating_add(tip);
			if total_tip > 0 {
				T::RewardPayment::register_reward(&relayer, T::DefaultRewardKind::get(), total_tip);
			}

			// Emit event with the message_id
			Self::deposit_event(Event::MessageReceived { nonce, message_id });

			Ok(())
		}

		fn add_tip(nonce: u64, amount: u128) -> Result<(), AddTipError> {
			ensure!(amount > 0, AddTipError::AmountZero);
			// If the nonce is already processed, return an error
			ensure!(!Nonce::<T>::get(nonce.into()), AddTipError::NonceConsumed);
			// Otherwise add the tip.
			Tips::<T>::mutate(nonce, |tip| {
				*tip = Some(tip.unwrap_or_default().saturating_add(amount));
			});
			return Ok(());
		}

		fn add_tip(nonce: u64, amount: u128) -> Result<(), AddTipError> {
			ensure!(amount > 0, AddTipError::AmountZero);
			PendingOrders::<T>::try_mutate_exists(nonce, |maybe_order| -> Result<(), AddTipError> {
				match maybe_order {
					Some(order) => {
						order.fee = order.fee.saturating_add(amount);
						Ok(())
					},
					None => Err(AddTipError::UnknownMessage),
				}
