### Title
Unchecked boolean return value from FT transfer allows fake-collateral crediting - ([File: mainnet/contracts/market/v0-market-vault.clar])

### Summary
### Finding Description
`market-vault`'s token-transfer helpers wrap `contract-call?` results with `try!` but never inspect the inner boolean returned by the SIP-010 `transfer` function. `try!` in Clarity only propagates/aborts on a Clarity-level error (`(err ...)`); it does **not** assert that a returned `(ok bool)` actually carries `true`. This is the direct Clarity analog of the reported "no return-value check after ERC-20 transfer" bug: a token contract that returns `(ok false)` instead of erroring will be treated as a successful transfer.

`receive-tokens` performs the inbound transfer and is called from `collateral-add`: [1](#0-0) [2](#0-1) 

`collateral-add` calls `(try! (receive-tokens ft amount account))` and then immediately calls `(insert updated-entry)` to credit the account's collateral for `asset-id`, based solely on the `try!` not erroring — the boolean success flag inside the response is discarded. If any `ft` contract passed by the caller (it is generic over the `<ft-trait>`, so it can be *any* contract implementing the trait, not necessarily the DAO-approved asset for `asset-id`) returns `(ok false)` from `transfer` without actually moving funds and without raising an error, `market-vault` will register collateral for the account that was never actually deposited.

The identical pattern (`try!` without checking the inner bool) is used for outbound transfers in `send-tokens`, and for vault-level transfers in `receive-underlying`/`send-underlying` across the vault contracts, e.g.: [3](#0-2) 

### Impact Explanation
If reachable with an asset whose transfer contract can return `(ok false)` (rather than aborting) on failure — which is exactly the class of behavior the original ERC-20 report warns about — an attacker can register phantom collateral in `market-vault` without transferring any real tokens, then borrow real assets against that phantom collateral via the market's debt operations. This is direct theft of protocol/user funds and can drive the market into insolvency, matching the Critical impact tier (direct theft of funds at rest, protocol insolvency).

### Likelihood Explanation
Exploitability is gated by whether `asset-id`/`ft` pairing is enforced against a DAO-curated allowlist elsewhere (e.g., in `v0-4-market.clar`) before `collateral-add` is invoked, and by whether `check-impl-auth` restricts callers of `market-vault` to a single trusted `impl` contract. I could not fully verify within the available context whether the calling market contract restricts the `ft` argument to only the token contract that is actually registered for `asset-id`, or whether all in-scope collateral/underlying tokens used in production (`sbtc`, `usdc`, `usdh`, `ststx`, `ststxbtc`, wrapped STX) are trusted enough to never return `(ok false)`. If such validation exists and strictly binds `ft` to the DAO-approved token contract per `asset-id`, exploitability is low since it would require a compromised/malicious approved asset contract. If that binding is missing or bypassable by an ordinary caller, likelihood is high since it only requires deploying an attacker-controlled SIP-010-compliant contract that returns `false` instead of erroring.

### Recommendation
After every `contract-call? ... transfer ...`, explicitly assert the inner boolean is `true` (e.g., `(asserts! (is-eq (try! (contract-call? asset transfer amount account current-contract none)) true) ERR-TRANSFER-FAILED)`) rather than relying on `try!` alone, in `receive-tokens`/`send-tokens` in `market-vault.clar` and in the `receive-underlying`/`send-underlying` helpers across all vault contracts. Additionally, confirm (or add, if missing) strict binding of `asset-id` to a DAO-registered token contract so that `collateral-add`/`collateral-remove` cannot be called with an arbitrary attacker-supplied `<ft-trait>` implementation.

### Proof of Concept
1. Attacker deploys a contract implementing `ft-trait` whose `transfer` function returns `(ok false)` unconditionally (no error, no actual balance change).
2. Attacker (or the market contract on the attacker's behalf, if `asset-id`/`ft` binding is not enforced) calls `market-vault.collateral-add` with this malicious contract as `ft` and an arbitrary `amount`.
3. `receive-tokens` executes `contract-call? asset transfer amount account current-contract none` → returns `(ok false)`; `try!` passes because it is `ok`, not an error.
4. `insert updated-entry` registers the account's collateral for `asset-id` as if tokens were actually deposited, with no real balance change in `market-vault`.
5. Attacker uses the phantom collateral entry to call `debt-add-scaled`/borrow real assets, extracting real funds without having deposited anything.

(define-public (collateral-add (account principal) (amount uint) (ft <ft-trait>) (asset-id uint))
  (let ((states (var-get pause-states))
        (entry (resolve-or-create account))
        (user-id (get id entry))
        (mask (get mask entry))
        (updated-mask (mask-update mask asset-id true true)) ;; collateral, insert
        (updated-entry (merge entry (refresh updated-mask)))
        (result (add-user-collateral user-id asset-id amount)))

    (try! (check-impl-auth))
    (asserts! (not (get collateral-add states)) ERR-PAUSED)
    (asserts! (> amount u0) ERR-AMOUNT-ZERO)

    (try! (receive-tokens ft amount account))
    
    (insert updated-entry)

    (print {
      action: "collateral-add",
      caller: contract-caller,
      data: {
        account: account,
        asset-id: asset-id,
        amount: amount,
        updated-collateral-amount: result,
        mask-before: mask,
        mask-after: updated-mask
      }
    })
