Based on my research, I found a strong analog to the reported ELF-parsing bug class: TVM precompiled contract input decoding that trusts attacker-controlled ABI offsets/lengths without bounds validation, leading to an unhandled exception (crash) when processing a transaction.

### Title
Unvalidated ABI array offset in `ValidateMultiSign` precompile causes uncaught `ArrayIndexOutOfBoundsException`, crashing/halting the node - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`PrecompiledContracts.extractBytes32Array` reads an attacker-supplied `DataWord[]` array (decoded from raw transaction calldata) and uses an offset and length taken directly from that data to index into the array — with no bounds check, unlike its sibling helpers `extractBytesArray` and `extractSigArray`, which both explicitly guard `if (offset > words.length - 1) return new byte[0][];` before indexing.

### Finding Description
`extractBytes32Array` reads `words[offset]` to get an element count and then loops `words[offset + i + 1]` without ever validating that `offset` or `offset + i + 1` are within the bounds of the `words` array: [1](#0-0) 

Compare this to the two neighboring helpers in the same file that parse similarly-shaped ABI-encoded dynamic arrays, both of which explicitly guard the offset before indexing: [2](#0-1) 

`words` is constructed by splitting the raw `data` byte array (the calldata a caller passes to `CALL`/`STATICCALL` against a precompile address) into 32-byte `DataWord` chunks. Because `offset` itself comes from a prior word in that same attacker-controlled `data`, and `len` is derived from `words[offset].intValueSafe()`, an attacker can craft calldata where `offset` is close to or beyond `words.length`, or where `len` is large enough that `offset + len + 1` exceeds `words.length`. The very next read, `words[offset + i + 1]`, then throws `ArrayIndexOutOfBoundsException` — this mirrors the reported bug class exactly: trusting embedded offsets/counts from untrusted binary-format input and dereferencing/indexing without validating them first (as with `fastelf`'s unchecked `Shoff`/`Shnum` and `GetCStringUnsafe` slicing).

This is the same unsafe-parsing pattern that a previous hardening pass already fixed in `extractBytesArray`/`extractSigArray` (both got the `offset > words.length - 1` guard) and in `ContractEventParser.subBytes`/`parseDataBytes` (which now reject negative/out-of-range offsets and lengths, evidenced by the regression tests in `EventParserTest.java`), but `extractBytes32Array` was missed.

### Impact Explanation
An `ArrayIndexOutOfBoundsException` raised deep inside TVM precompile execution, if not caught somewhere up the call stack before it unwinds out of block/transaction processing, causes the node to fail while executing a normal, syntactically valid transaction. Since block application processes transactions sequentially and deterministically, this can either (a) crash the node process handling the transaction (local DoS against a single node, matching the "Medium" severity of the analog CVE), or (b) if different node versions/builds handle the uncaught exception differently, cause divergent transaction execution outcomes between nodes — a chain-split risk. Any anonymous account can trigger this by sending a transaction that calls the ValidateMultiSign precompile address with crafted calldata; no special privileges are required.

### Likelihood Explanation
Reaching this code only requires constructing and broadcasting a `TriggerSmartContract` transaction (or an internal `CALL` from within a contract) targeting the fixed precompile address that resolves to the `ValidateMultiSign` contract, with calldata whose ABI-encoded array offset is out of range. This is directly reachable by any unprivileged transaction broadcaster and needs no special account permissions, matching the report's "AC:L/PR:L" reachability profile.

### Recommendation
Add the same bounds guard used in `extractBytesArray` and `extractSigArray` to `extractBytes32Array`:
```java
private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
  if (offset < 0 || offset > words.length - 1) {
    return new byte[0][];
  }
  int len = words[offset].intValueSafe();
  if (len < 0 || offset + 1L + len > words.length) {
    return new byte[0][];
  }
  byte[][] bytes32Array = new byte[len][];
  for (int i = 0; i < len; i++) {
    bytes32Array[i] = words[offset + i + 1].getData();
  }
  return bytes32Array;
}
```
More broadly, audit all `DataWord[]`/raw-`byte[]`-offset-driven decoding in `PrecompiledContracts.java` (e.g., the sapling/shielded-transfer precompiles that directly `System.arraycopy` at attacker-supplied offsets, as seen around lines 1472–1531) to ensure every offset/length derived from `data` is range-checked before use, and ensure precompile `execute()` invocations are wrapped so any unexpected runtime exception is converted into a graceful contract-execution failure rather than propagating and destabilizing block processing.

### Proof of Concept
1. Craft a `TriggerSmartContract` transaction whose target address is the precompile address resolved to `ValidateMultiSign` (guarded by `VMConfig.allowTvmFreezeV2()`/similar feature flag — confirm the currently active flag for this build).
2. Construct calldata such that, after being decoded into `DataWord[] words`, whichever call path invokes `extractBytes32Array(words, offset)` receives an `offset` value from the calldata that is large (e.g., close to `Integer.MAX_VALUE / 32`) or a `len` value such that `offset + len + 1 > words.length`.
3. Broadcast the transaction to a full node via the normal JSON-RPC/gRPC transaction submission path (`Wallet`/`TronJsonRpcImpl`).
4. During block/transaction execution, `words[offset + i + 1]` throws `ArrayIndexOutOfBoundsException`; verify whether this propagates uncaught out of contract execution and crashes/halts the node process or produces divergent execution results across nodes.

Note: I was unable to fully trace every call site of `extractBytes32Array` (e.g., which specific precompile methods use it and whether their `execute()` bodies are wrapped in a try/catch that would swallow this exception) within the available search results, so confirmation of whether the exception is caught upstream (which would reduce this from a node-crash to a mere reverted-call issue) should be verified directly in the `ValidateMultiSign`/related precompile class bodies in `PrecompiledContracts.java` before treating this as a confirmed DoS.
