## Title
Wallet Contract pays the relayer fee before validating the transaction target, allowing a malicious relayer to collect payment for a transaction it deliberately fails to execute - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The external report describes an ERC20 `transfer()` call whose boolean return value is ignored, letting code proceed as if a payment succeeded when it may not have. The NEAR Wallet Contract (the ETH-implicit account's meta-transaction relayer system) has a structurally identical flaw: it fires the relayer-fee `Transfer` promise unconditionally and without waiting for or checking the outcome of the actual user-requested action, so a relayer can be paid even when the wallet later determines the relayer supplied a faulty/invalid transaction target and the intended action never executes.

### Finding Description
In `inner_rlp_execute`, as soon as an Ethereum transaction is parsed into a Near `Action`, the wallet eagerly fires a fee payment to the calling relayer for any `EOABaseTokenTransfer` or `ERC20Transfer` with a non-zero fee: [1](#0-0) 

This `env::promise_batch_action_transfer` call creates an independent, fire-and-forget receipt to `context.predecessor_account_id` (the relayer) with no `.then()` linkage to the outcome of the actual requested action, and its result is never inspected — the exact "ignored transfer result" pattern from the report, except here it's the *payment* leg that is unconditionally dispatched regardless of whether the paid-for work later succeeds.

Crucially, this fee is dispatched *before* the wallet has verified that the relayer-supplied `target` is actually correct. For an `EOABaseTokenTransfer` whose target is another eth-implicit account, the nonce increment is deliberately deferred until after an address-registrar lookup confirms the relayer didn't send to the wrong place: [2](#0-1) 

That verification happens later, asynchronously, in `address_check_callback`, which can determine the relayer was "faulty" (the address actually belongs to a named account registered in the address registrar, not the naive eth-implicit account the relayer passed) and either bans the relayer's key or simply returns a failure response: [3](#0-2) 

Because the fee-transfer promise at lines 382-384 was already dispatched before this check runs, the relayer keeps the fee even though the callback later reports failure ("Invalid target: target is address corresponding to existing named account_id" or a ban) and the user's actual intended transfer never happens.

### Impact Explanation
This is a direct, concrete theft-of-funds vector: an untrusted relayer (unprivileged by design in this meta-transaction scheme) can collect the user-authorized relayer fee while deliberately supplying a wrong `target` for any eth-implicit-addressed transaction where the destination address is already claimed by a named account in the address registrar. The user's balance is debited the fee amount with no corresponding action executed, and no funds are recovered (the fee promise is fire-and-forget with no result check or refund-on-failure path).

### Likelihood Explanation
Relayers, by construction of this meta-tx design, see and control the `target` parameter passed into `rlp_execute`, independent of what the user's signed Ethereum transaction actually specifies. Any relayer who chooses to (or a compromised/malicious relayer service) can pass an eth-implicit-derived `target` for a `to` address that is already registered to a named account — a realistic scenario since named accounts (e.g. exchanges) are expected to register addresses in the registrar to receive such transfers. No special privilege beyond being a relaying party (which by design has no on-chain trust assumptions) is required.

### Recommendation
Do not dispatch the relayer fee transfer until the requested action's success (and target validity) has been confirmed. Either (a) defer the fee-refund promise creation until after `address_check_callback`/`nep_141_storage_balance_callback` resolve the action successfully, chaining it with `.then()` off the confirmed outcome, or (b) reclaim/cancel the fee via the ban/error paths (e.g., have `address_check_callback`'s failure branches issue a compensating refund back from the relayer, though this is not generally enforceable) — the structurally sound fix is to move fee payment to occur only after the underlying action promise reports `PromiseResult::Successful`.

### Proof of Concept
1. User `alice.eth` (an eth-implicit account) signs an Ethereum-style base-token transfer to `to = 0xVICTIM`, with a nonzero relayer fee, intending it to reach the wallet contract for `0xVICTIM`.
2. `0xVICTIM`'s address has separately been registered by a named account `exchange.near` in the address registrar (a supported, documented feature).
3. A malicious relayer receives/observes this signed transaction and calls `rlp_execute` on `alice.eth` with `target = <eth-implicit-account-id-for-0xVICTIM>` (instead of correctly resolving and using `exchange.near`).
4. `inner_rlp_execute` parses this as `EOABaseTokenTransfer{ address_check: Some(0xVICTIM), fee }`, defers the nonce increment, but immediately fires `promise_batch_action_transfer(refund_promise, fee)` to the relayer at lines 382-384.
5. `address_check_callback` later looks up the registrar, finds `exchange.near` is registered for `0xVICTIM`, and returns `ExecuteResponse{success: false, error: "Invalid target..."}` (or bans the relayer if self-signed).
6. The user's intended transfer never happens (nonce wasn't consumed, so the user can retry with an honest relayer), but the fee already paid to the malicious relayer in step 4 is unrecoverable.

    /// Callback after checking if an address is contained in the registrar.
    /// This check happens when the target is another eth implicit account to
    /// confirm that the relayer really did check for a named account with that address.
    #[private]
    pub fn address_check_callback(
        &mut self,
        target: AccountId,
        action: near_action::Action,
        caller_deposit: Option<CallerDeposit>,
    ) -> PromiseOrValue<ExecuteResponse> {
        self.has_in_flight_tx = false;
        let maybe_account_id: Option<AccountId> = match env::promise_result(0) {
            PromiseResult::Failed => {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Call to Address Registrar contract failed".into()),
                });
            }
            PromiseResult::Successful(value) => match serde_json::from_slice(&value) {
                Ok(x) => x,
                Err(_) => {
                    return PromiseOrValue::Value(ExecuteResponse {
                        success: false,
                        success_value: None,
                        error: Some("Unexpected response from account registrar".into()),
                    });
                }
            },
        };
        let current_account_id = env::current_account_id();
        let promise = if maybe_account_id.is_some() {
            // We intentionally do not increment the nonce in this case because the
            // error is caused by a faulty relayer, not the user. An honest relayer
            // may still be able to successfully send the user's intended transaction.
            if env::signer_account_id() == current_account_id {
                create_ban_relayer_promise(current_account_id)
            } else {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Invalid target: target is address corresponding to existing named account_id".into()),
                });
            }
        } else {
            // We must increment the nonce at this point to prevent replay of the transaction.
            // Recall that the nonce was not incremented in `inner_rlp_execute` in the case that
            // the registrar contract was called (i.e. in the case we end up inside this callback).
            self.nonce = self.nonce.saturating_add(1);
            let ext =
                WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
            match action_to_promise(target, action)
                .map(|p| p.then(ext.rlp_execute_callback(caller_deposit)))
            {
                Ok(p) => p,
                Err(e) => {
                    return PromiseOrValue::Value(e.into());
                }
            }
        };
        self.has_in_flight_tx = true;
        PromiseOrValue::Promise(promise)
    }
