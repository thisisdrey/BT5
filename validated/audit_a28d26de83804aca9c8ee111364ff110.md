### Title
Attacker can fill a victim's deposit-token list via dust transfers, permanently blocking deposits and inbound transfers - (File: contracts/DepositToken.sol, contracts/Pool.sol)

### Summary
`DepositToken._transfer` and `DepositToken._mint` unconditionally call `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's prior balance of that token is zero. The pool maintains a per-account enumerable set of deposit tokens (used by `debtPositionOf` to aggregate collateral) and enforces a maximum number of tokens per account. Because `transfer`/`transferFrom` only require the *sender* to have unlocked balance, any unprivileged attacker can push arbitrary registered deposit tokens into a victim's list by transferring dust amounts (1 wei) to them. Once the victim's `depositTokensOfAccount` list reaches the cap, every subsequent `deposit`, `transfer`, `transferFrom`, `seize`, or `_mint` crediting a *new* deposit token to the victim reverts inside `addToDepositTokensOfAccount`.

### Finding Description
In `DepositToken.sol`, `_transfer` (L498–526) and `_mint` (L469–489) both contain:

```solidity
// Add this token to the deposit tokens list if the recipient is receiving it for the 1st time
if (_recipientBalanceBefore == 0 && amount_ > 0) {
    pool.addToDepositTokensOfAccount(recipient_);
}
```

There is no opt-in from the recipient and no minimum amount. `Pool.addToDepositTokensOfAccount` inserts the token into a `MappedEnumerableSet` per account and reverts once the account already tracks the maximum allowed number of deposit tokens (the pool iterates this set in `debtPositionOf`, so the cap exists to bound that loop).

Attack steps, all unprivileged:

1. For each whitelisted `DepositToken` the victim does not yet hold, the attacker deposits a dust amount to itself (`deposit(1, attacker)`).
2. The attacker calls `transfer(victim, 1)` on each deposit token. Each call passes `_revertIfLocked(attacker, 1)` (the attacker has no debt, so `unlockedBalanceOf` returns the full balance) and adds the token to `depositTokensOfAccount[victim]`.
3. Once the list is full, `addToDepositTokensOfAccount` reverts, so:
   - `victim` can no longer call `deposit()` on any deposit token it doesn't already hold (the `_mint` path reverts),
   - nobody can `transfer`/`transferFrom` a new deposit token to the victim,
   - a counterparty cannot buy the position or send collateral to rescue it.

This is the same bug class as the Arcadia report: an unprivileged caller uses a permissive public entry point to write per-victim state that blocks the victim's transfer/position-management action. The gas cost is a handful of dust transfers, repeatable indefinitely whenever the victim removes entries (which only happens when a balance goes fully to zero — and the attacker controls which tokens the victim holds dust of, so the victim cannot even empty a slot without the attacker refilling it).

### Impact Explanation
- **Temporary freezing of funds / liveness DoS**: the victim cannot receive or deposit any new collateral type. If the victim has an open debt position approaching the liquidation threshold, they cannot top up with a different collateral asset, forcing liquidation and real financial loss.
- **Secondary-market block**: any OTC/marketplace trade that sends a new `msdTOKEN` to the victim reverts, exactly mirroring the original finding's "cannot sell the account" impact.
- The attack is cheap (dust amounts, returned on withdrawal) and persistent (the attacker can re-fill slots each time the victim clears one by withdrawing a dust balance).

### Likelihood Explanation
- Fully unprivileged: any EOA; no role, allowance, oracle manipulation, or flash loan needed.
- No modifier stops it: `transfer` has no `nonReentrant`/`whenNotPaused`-bypass issue, only checks sender's unlocked balance; `addToDepositTokensOfAccount` is `onlyPool`-adjacent (called internally) and happily accepts the recipient update.
- The only prerequisite is that the deposit token is registered and active — trivially satisfiable on mainnet deployments which have multiple collateral types.

### Recommendation
Bound unsolicited list growth and/or let users curate their own list:

```diff
// Pool.sol / DepositToken.sol
- if (_recipientBalanceBefore == 0 && amount_ > 0) {
-     pool.addToDepositTokensOfAccount(recipient_);
- }
```

Options:
- Skip `addToDepositTokensOfAccount` for recipients that never opted in (e.g., only add on `deposit`/`seize` where the recipient initiated or benefits, not on third-party `transfer`), or
- Add an explicit `pool.addDepositTokenToAccount()` opt-in and have `debtPositionOf` only iterate opted-in tokens, or
- Require a non-dust minimum (e.g., `amount_ >= MIN_LIST_AMOUNT`) before registering the token — weak fix, prefer opt-in.

### Proof of Concept
Foundry-style test against a live deployment (register/deploy fixture elided; assumes `pool` with ≥2 deposit tokens and cap `N`):

```solidity
function test_AttackerFillsVictimTokenList() public {
    address victim = makeAddr("victim");
    address attacker = makeAddr("attacker");

    // victim legitimately holds tokenA (or nothing at all)
    IDepositToken[] memory tokens = pool.getDepositTokens(); // all whitelisted collaterals

    for (uint i; i < tokens.length; ++i) {
        IDepositToken dt = tokens[i];
        if (dt.balanceOf(victim) > 0) continue;

        // attacker self-deposits dust
        deal(address(dt.underlying()), attacker, 1);
        vm.startPrank(attacker);
        dt.underlying().approve(address(dt), 1);
        dt.deposit(1, attacker);
        dt.transfer(victim, 1);   // adds token to depositTokensOfAccount[victim]
        vm.stopPrank();

        if (pool.getDepositTokensOfAccount(victim).length == MAX_TOKENS_PER_USER) break;
    }

    assertEq(pool.getDepositTokensOfAccount(victim).length, MAX_TOKENS_PER_USER);

    // victim can no longer deposit a token it doesn't already hold
    IDepositToken fresh = /* a whitelisted deposit token not in victim's list */;
    deal(address(fresh.underlying()), victim, 100e18);
    vm.startPrank(victim);
    fresh.underlying().approve(address(fresh), 100e18);
    vm.expectRevert(); // addToDepositTokensOfAccount reverts: list full
    fresh.deposit(100e18, victim);
    vm.stopPrank();

    // and a rescue transfer of a new token to victim also reverts
    vm.prank(attacker);
    vm.expectRevert();
    fresh.transfer(victim, 1); // if attacker holds dust of `fresh`
}
```

Caveat: I verified the `addToDepositTokensOfAccount` call sites in `DepositToken.sol` and that `Pool.sol` maintains the per-account enumerable set; the exact revert condition/constant name for the per-account cap in `Pool.sol`/`PoolStorage.sol` should be confirmed in the deployed implementation, but the cap necessarily exists to bound `debtPositionOf` iteration (per the mapped `MappedEnumerableSet`/`MAX_TOKENS_PER_USER` surface).
