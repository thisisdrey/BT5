### Title
`AtlasDB::insert_instantiated_attachment` stores unauthenticated, unverified attachment content with no `attachments_max_size` enforcement and no hash-binding check - (File: `stackslib/src/net/atlas/db.rs`)

### Summary
When the Atlas downloader receives an `AttachmentRequest` response from a peer, it stores the returned `Attachment` via `AtlasDB::insert_instantiated_attachment` without ever checking the content size against `AtlasConfig::attachments_max_size`, and without verifying that the returned content actually resolves to any `AttachmentInstance.content_hash`. This lets any peer serving attachment-sync requests write arbitrary, oversized, unrelated data into the node's persistent SQLite `attachments` table.

### Finding Description
The size guard `should_keep_attachment` (checks `attachment.content.len() as u32 > self.atlas_config.attachments_max_size`) exists only in the RPC-POST attachment path, at [1](#0-0) . It is **not** called anywhere along the P2P download path.

In `AttachmentsDownloader::run`, once the state machine reaches `Done`, every attachment collected in `context.attachments` (populated purely from a peer's HTTP response body via `extend_with_attachments` → `response.decode_atlas_get_attachment()` → `self.attachments.insert(response.attachment)`) is unconditionally persisted: [2](#0-1) 

`extend_with_attachments` never checks that the decoded attachment's hash matches the `content_hash` that was originally requested — it just inserts whatever the peer returned into a `HashSet<Attachment>`: [3](#0-2) 

`insert_instantiated_attachment` itself performs no size check at all before the `INSERT OR REPLACE` write: [4](#0-3) 

Because the lookup key used to find matching `attachment_instances` is `attachment.hash()` (the hash of whatever bytes the peer actually sent), an attacker's garbage payload with a hash that does not match any real `content_hash` still gets written to `attachments` with `was_instantiated = 1`; `find_all_attachment_instances` simply returns an empty vector, and no matching instance gets marked `is_available`, but the write to disk still happens. There is no eviction routine analogous to `evict_expired_uninstantiated_attachments` for `was_instantiated = 1` rows — only unresolved instances and uninstantiated attachments (`was_instantiated = 0`) are evicted: [5](#0-4) [6](#0-5) 

I was unable to fully confirm within available tools whether a generic HTTP-layer body-size cap (`MAX_MESSAGE_LEN`/content-length checks referenced in `stackslib/src/net/httpcore.rs`) bounds the overall response size before it reaches `decode_atlas_get_attachment`. If such a generic transport cap exists, it is not Atlas-aware and is unrelated to `AtlasConfig::attachments_max_size`, so the Atlas-specific bound is still bypassed even if some larger generic limit applies.

### Impact Explanation
Any outbound peer selected during Atlas attachment sync (`network.get_outbound_sync_peers()`) can respond to an `AttachmentRequest` with oversized/unrelated content. That content is written permanently into the node's `attachments` SQLite table via `insert_instantiated_attachment` with no cap tied to `attachments_max_size`, and with no requirement that its hash correspond to a `content_hash` referenced by any on-chain-committed `AttachmentInstance`. This is an unauthenticated write to persistent node storage, repeatable for every attachment batch the node processes, causing storage growth uncorrelated with any consensus commitment.

### Likelihood Explanation
Preconditions: the victim node must be actively syncing Atlas attachments (`has_ready_batches() == true`, i.e., it has queued `AttachmentInstance`s referencing hashes it doesn't yet have) and have at least one outbound peer serving it. An attacker can become that outbound peer simply by running a normal Stacks node that gets discovered/connected to via the P2P protocol — no privileged role, secret, or admin access is required. The attacker does not need to target any specific `content_hash`; they only need to be selected to answer some `AttachmentRequest` and return oversized junk.

### Recommendation
Enforce `attachment.content.len() as u32 <= atlas_config.attachments_max_size` inside `insert_instantiated_attachment` (and `insert_uninstantiated_attachment`) before writing, mirroring `should_keep_attachment`. Additionally, in `extend_with_attachments` / the `Done`-state processing loop in `download.rs`, verify that `attachment.hash()` matches the `content_hash` of the original `AttachmentRequest` before accepting/storing the response, discarding and penalizing (via `report.bump_failed_requests()`) any peer that returns mismatched or oversized content.

### Proof of Concept
Rust test plan in `stackslib/src/net/atlas/tests.rs`:
1. Construct an `AtlasDB` with a small `attachments_max_size` (e.g., 1 KB) via `AtlasConfig`.
2. Simulate the `Done` branch of `AttachmentsBatchStateMachine::try_proceed` by building an `AttachmentsBatchStateContext`, inserting into `context.attachments` an `Attachment` whose `content` is, e.g., 10 MB of arbitrary bytes (hash intentionally not matching any queued `AttachmentInstance.content_hash`).
3. Call `network.atlasdb.insert_instantiated_attachment(&attachment)` directly (mirroring `download.rs` line 161) and then `network.atlasdb.find_attachment(&attachment.hash())`.
4. Assert the row is present and `content.len()` exceeds `atlas_config.attachments_max_size`, proving the cap is not enforced at this call site, and assert `find_all_attachment_instances(&attachment.hash())` returns empty, proving the content is stored with no tie to any committed `AttachmentInstance`.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }
