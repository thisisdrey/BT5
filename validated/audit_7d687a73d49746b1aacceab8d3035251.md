This confirms the finding: the signer's event-receiver endpoint (e.g. `0.0.0.0:30000` in the sample config [1](#0-0)  and `mainnet-signer.toml` [2](#0-1) ) is bound with no authentication check in `next_event()` — the `/shutdown` branch stores `true` to `stop_signal` unconditionally for any request matching that URL, regardless of source. There's no auth token, secret, or peer-address check anywhere in that function, unlike the node's RPC `auth_token`/`auth_password` mechanism used elsewhere in the signer/node protocol.

### Title
Unauthenticated remote `/shutdown` HTTP request permanently terminates the signer's event receiver - (File: libsigner/src/events.rs)

### Summary
`SignerEventReceiver::next_event` handles any HTTP POST to `/shutdown` on its bound event-receiver socket by unconditionally setting `stop_signal` to `true` and returning `EventError::Terminated`, with no authentication, secret, or origin check. Since this socket is configured to listen on `0.0.0.0` (all interfaces) per the sample configs, any remote party who can open a TCP connection to that port can permanently halt the signer's event pipeline with a single crafted HTTP request.

### Finding Description
In `next_event()`, the request-dispatch logic checks `request.url()` against a fixed set of paths, and for `/shutdown` it directly does:
```rust
} else if request.url() == "/shutdown" {
    event_receiver.stop_signal.store(true, Ordering::SeqCst);
    Err(EventError::Terminated)
}
``` [3](#0-2) 

This is the same code path invoked internally by `SignerStopSignaler::send()`, which connects to `self.local_addr` and issues `POST /shutdown HTTP/1.1 ...` [4](#0-3)  — but `next_event()` has no way to distinguish that legitimate local stop-signaler connection from an arbitrary remote TCP client sending the identical bytes, because there is no token, HMAC, shared secret, or source-address restriction checked before the `stop_signal.store(true, ...)` call.

Once `stop_signal` is `true`, `is_stopped()` returns `true` [5](#0-4) , and `main_loop()` observes this on its next iteration and breaks out, ending event processing for all downstream consumers registered via `add_consumer` [6](#0-5) .

The event-receiver bind address is operator-configured and the shipped reference configs bind it to `0.0.0.0` (all interfaces), e.g. `endpoint = "0.0.0.0:30000"` in `sample/conf/signer/mainnet-signer-conf.toml` [1](#0-0) , meaning the port is remotely reachable by design in that reference deployment, unlike the node's RPC/P2P surfaces which enforce an `auth_token`/`auth_password` (as documented in `docs/signing.md` [7](#0-6) ). That auth mechanism protects the node's block-proposal endpoint but is never consulted anywhere in `SignerEventReceiver::next_event`, so it provides no protection for `/shutdown`.

### Impact Explanation
A single unauthenticated HTTP POST to `/shutdown` permanently disables the signer's `main_loop`, meaning the signer will stop receiving `StackerDBChunksEvent`, `BlockValidateResponse`, `NewBurnBlock`, and `NewBlock` events from the node indefinitely (the loop only restarts on process restart) [6](#0-5) . This is a remote, unauthenticated, single-message DoS against the signer process — matching the "Critical: remote crash/unauthenticated DoS from few messages" category, since it silently takes the signer offline from block-signing duties without crashing the OS process, but effectively renders the signer non-functional until manually restarted.

### Likelihood Explanation
No preconditions beyond TCP reachability to the configured event-receiver endpoint are required; the attacker needs no key, StackerDB slot, secret, or peer relationship. The reference/sample configs bind this endpoint to `0.0.0.0`, and the attack requires only one crafted HTTP request, is trivially repeatable (can be re-sent after any restart), and costs the attacker essentially nothing.

### Recommendation
Require an authentication token/shared secret (reusing the existing `auth_password`/HMAC infrastructure already used elsewhere) or restrict `/shutdown` to loopback/local connections only, e.g., verify the peer's `SocketAddr` is `127.0.0.1`/`::1` before honoring the stop request, or require a per-process random token known only to the in-process `SignerStopSignaler`.
