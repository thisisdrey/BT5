### Title
Missing `supportUnfreezeDelay()` committee-gate check in `WithdrawExpireUnfreezeProcessor` allows the TVM `withdrawexpireunfreeze` opcode to bypass the protection enforced by `WithdrawExpireUnfreezeActuator` - (File: `actuator/src/main/java/org/tron/core/vm/nativecontract/WithdrawExpireUnfreezeProcessor.java`)

### Summary
`WithdrawExpireUnfreezeActuator`, which handles the regular `WithdrawExpireUnfreezeContract` transaction, requires the committee-controlled feature flag `supportUnfreezeDelay()` to be enabled before it will let an account withdraw its expired (delayed) unfrozen TRX. The equivalent TVM native-contract path, `WithdrawExpireUnfreezeProcessor`, which is reached when a smart contract executes the `withdrawexpireunfreeze` opcode, performs none of this check.

### Finding Description
`WithdrawExpireUnfreezeActuator.validate()` explicitly gates the withdrawal on the chain parameter `supportUnfreezeDelay`: [1](#0-0) 

If this feature has not been activated by the committee, any account-level (transaction) attempt to withdraw expired unfrozen balances is rejected with `ContractValidateException`.

The parallel implementation used by the TVM opcode, `WithdrawExpireUnfreezeProcessor.validate()`, only checks that the repository exists, that the address is valid, that the account exists, that there is a positive amount to withdraw, and that the resulting balance addition does not overflow — it never calls or checks `dynamicStore.supportUnfreezeDelay()`: [2](#0-1) 

Both paths operate on the exact same underlying data (the account's `unfrozenV2` list and its expiry timestamps) and both ultimately move the expired unfrozen balance back into the spendable balance: [3](#0-2) [4](#0-3) 

This mirrors the reported bug class exactly: a protection mechanism enforced on one entry point (the normal actuator, analogous to `LMPVault.claimRewards()`'s `whenNotPaused`) is completely absent on a second, lower-level entry point that reaches the same state mutation (the TVM opcode, analogous to `MainRewarder.getReward()` lacking the pause check). Because Solidity contracts on TVM can invoke the `withdrawexpireunfreeze` opcode directly (via `Program.withdrawExpireUnfreeze()` and `WithdrawExpireUnfreezeProcessor`), an unprivileged contract deployer can call this native contract from a smart contract to withdraw expired unfrozen TRX even while the committee has intentionally left the `UnfreezeDelay`/expired-withdraw feature disabled network-wide.

### Impact Explanation
This allows an unauthorized bypass of a chain-governed feature gate: funds that the committee intends to keep locked/unreachable (because the `supportUnfreezeDelay` feature has not yet been turned on, e.g., during a phased hard-fork rollout) can still be unlocked and moved to spendable balance through a smart contract call. This is a violation of the intended activation-controlled behavior of the unfreeze/withdraw mechanism and can result in funds being released from the frozen/locked state before they are supposed to be, i.e., an unauthorized state-changing account operation that the protocol explicitly tries to prevent while the feature is off.

### Likelihood Explanation
Any account can deploy a trivial smart contract that calls the `withdrawexpireunfreeze` native opcode; no special privilege is required beyond having previously frozen (V2) balance with an unfreeze already requested. As long as the node has activated the underlying TVM opcode itself (a separate VM hard-fork toggle from `supportUnfreezeDelay`), the missing business-logic check in `WithdrawExpireUnfreezeProcessor` is reachable by any ordinary transaction sender.

### Recommendation
Add the same `dynamicStore.supportUnfreezeDelay()` check to `WithdrawExpireUnfreezeProcessor.validate()` that exists in `WithdrawExpireUnfreezeActuator.validate()`, throwing a `ContractValidateException` when the feature is not enabled, so the TVM native-contract path cannot bypass the committee-controlled activation gate.

### Proof of Concept
1. Committee has not yet enabled `supportUnfreezeDelay` (`ALLOW_UNFREEZE_DELAY` chain parameter = 0).
2. An account freezes TRX using `FreezeBalanceV2` and later calls `UnfreezeBalanceV2`, producing entries in `unfrozenV2` with a future `unfreeze_expire_time`.
3. Sending a normal `WithdrawExpireUnfreezeContract` transaction fails validation with "Not support WithdrawExpireUnfreeze transaction, need to be opened by the committee" as shown in [1](#0-0) .
4. Once the unfreeze expiry time passes, the same account deploys/calls a smart contract that invokes the `withdrawexpireunfreeze` TVM opcode (`Program.withdrawExpireUnfreeze()` → `WithdrawExpireUnfreezeProcessor`).
5. `WithdrawExpireUnfreezeProcessor.validate()` (see lines 26–60 above) contains no `supportUnfreezeDelay` check, so validation succeeds and `execute()` moves the expired unfrozen balance into `balance`, successfully bypassing the committee gate that blocked step 3.

Note: I was unable to fully verify, within the remaining investigation budget, whether `Program.java`/`OperationRegistry` additionally gates the `withdrawexpireunfreeze` opcode's very existence behind a separate VM hard-fork switch (e.g., an `allowTvmFreezeV2`-style flag) that might be enabled/disabled in lockstep with `supportUnfreezeDelay` in production configuration. If such a flag exists and is always toggled together with `supportUnfreezeDelay`, the practical exploitability window would be narrower than described; however, the code-level discrepancy between the two `validate()` implementations is confirmed and represents a defense-in-depth gap regardless.

  public void validate(WithdrawExpireUnfreezeParam param, Repository repo) throws ContractValidateException {
    if (repo == null) {
      throw new ContractValidateException(STORE_NOT_EXIST);
    }

    byte[] ownerAddress = param.getOwnerAddress();
    DynamicPropertiesStore dynamicStore = repo.getDynamicPropertiesStore();
    if (!DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("Invalid address");
    }
    AccountCapsule accountCapsule = repo.getAccount(ownerAddress);
    if (Objects.isNull(accountCapsule)) {
      String readableOwnerAddress = StringUtil.createReadableString(ownerAddress);
      throw new ContractValidateException(ACCOUNT_EXCEPTION_STR
          + readableOwnerAddress + NOT_EXIST_STR);
    }

    long now = dynamicStore.getLatestBlockHeaderTimestamp();
    List<Protocol.Account.UnFreezeV2> unfrozenV2List = accountCapsule.getInstance()
        .getUnfrozenV2List();
    long totalWithdrawUnfreeze = getTotalWithdrawUnfreeze(unfrozenV2List, now);
    if (totalWithdrawUnfreeze < 0) {
      throw new ContractValidateException("no unFreeze balance to withdraw ");
    }
    try {
      LongMath.checkedAdd(accountCapsule.getBalance(), totalWithdrawUnfreeze);
    } catch (ArithmeticException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractValidateException(e.getMessage());
    }

    if (accountCapsule.hasInvalidDelegatedV2()) {
      MUtil.checkCPUTimeForInvalidDelegatedV2Balance();
    }
  }

  public long execute(WithdrawExpireUnfreezeParam param, Repository repo) throws ContractExeException {
    byte[] ownerAddress = param.getOwnerAddress();
    DynamicPropertiesStore dynamicStore = repo.getDynamicPropertiesStore();
    AccountCapsule ownerCapsule = repo.getAccount(ownerAddress);
    long now = dynamicStore.getLatestBlockHeaderTimestamp();
    List<Protocol.Account.UnFreezeV2> unfrozenV2List = ownerCapsule.getInstance().getUnfrozenV2List();
    long totalWithdrawUnfreeze = getTotalWithdrawUnfreeze(unfrozenV2List, now);
    if (totalWithdrawUnfreeze <= 0) {
      return 0;
    }
    ownerCapsule.setInstance(ownerCapsule.getInstance().toBuilder()
        .setBalance(ownerCapsule.getBalance() + totalWithdrawUnfreeze)
        .build());
    List<Protocol.Account.UnFreezeV2> newUnFreezeList = getRemainWithdrawList(unfrozenV2List, now);
    ownerCapsule.clearUnfrozenV2();
    ownerCapsule.addAllUnfrozenV2(newUnFreezeList);
    repo.updateAccount(ownerCapsule.createDbKey(), ownerCapsule);
    return totalWithdrawUnfreeze;
  }
