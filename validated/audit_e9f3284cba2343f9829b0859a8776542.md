### Title
Deposits into severely impaired (near-zero share value) banks can be wiped out by a later bankruptcy socialization - (File: `programs/marginfi/src/state/bank.rs`, `programs/marginfi/src/instructions/marginfi_group/handle_bankruptcy.rs`)

### Summary

### Finding Description
The reported bug class is: a lending pool lets users deposit into a position that is already severely value-impaired (share price near zero due to prior unrealized/realized losses) without any minimum-health gate, and a subsequent insolvency event that crosses an all-or-nothing threshold wipes the *entire* pool's value to zero — destroying the new depositor's freshly-contributed, otherwise-recoverable funds along with the pre-existing bad position.

marginfi has the same structural pattern in its bank/bankruptcy accounting:

- `lending_account_deposit` only gates on operational state (`Paused`/`ReduceOnly`/`Uninitialized`/`KilledByBankruptcy`) via `validate_bank_state`, and on account-level flags — there is no check on how degraded `asset_share_value` is before allowing a deposit. [1](#0-0) [2](#0-1) 

- Shares are minted as `value / asset_share_value`, so once `asset_share_value` becomes tiny (but not yet exactly zero) from an earlier partial bankruptcy socialization, a new depositor mints a disproportionately large number of shares for their deposit — mirroring the "1 wei = 1e18 shares" mechanic in the report. [3](#0-2) 

- `socialize_loss`, invoked from `lending_pool_handle_bankruptcy`, computes `total_value = total_asset_shares * old_asset_share_value` and, if a *new, unrelated* bad-debt event's `loss_amount` is greater than or equal to that `total_value`, sets `asset_share_value` to **zero for the entire bank** and marks `kill_bank = true` — regardless of how much of that `total_value` consists of a legitimate, freshly-deposited, recoverable balance. [4](#0-3) 

- Once `kill_bank` is true, the bank's operational state is permanently set to `KilledByBankruptcy`, which is documented and enforced as irrecoverable and blocks every user operation (deposit/withdraw/borrow/repay) forever, with no path for any depositor — including the one whose funds arrived after the risk was already visible — to recover principal. [5](#0-4) [6](#0-5) 

This is the analog of the reported bug: no mechanism (comparable to MetaStreet's "impaired price" check or Cantina's `_isEmpty()`/inactive-node gate) prevents deposits into a bank whose `asset_share_value` is already critically degraded before it is formally killed. Because `lending_pool_handle_bankruptcy` is permissionless when `PERMISSIONLESS_BAD_DEBT_SETTLEMENT_FLAG` is set, and because deposits remain open in `Operational`/`ReduceOnlyWithBorrowingPower` states even with a severely degraded share value, a depositor can unknowingly deposit into a bank on the edge of insolvency and have their principal zeroed out by a subsequent, unrelated bankruptcy resolution that only marginally exceeds the pool's book value. [7](#0-6) 

### Impact Explanation
If triggered, this results in permanent loss/freeze of legitimately deposited user funds: the depositor's tokens were transferred into the bank's liquidity vault, their shares were minted correctly per the (already-degraded) share price, yet a subsequent `handle_bankruptcy` call unrelated to their own action can zero `asset_share_value` for the whole bank and permanently disable it (`KilledByBankruptcy`), with no recovery mechanism for remaining depositors. This is a real insolvency/permanent-fund-lock outcome, matching the "concrete theft, insolvency, or permanent lock/freeze" bar.

### Likelihood Explanation
This requires a bank to already be in a state where a prior (or same) bankruptcy resolution has degraded `asset_share_value` to a very small nonzero value without yet killing the bank (i.e., `total_value > loss_amount` on a first pass), followed by a new user depositing into that same bank before an admin/risk_admin notices and pauses it, followed by another bad-debt/bankruptcy event whose `loss_amount` now exceeds the new (deposit-inflated) `total_value`. This is a multi-step, low-probability sequence dependent on real economic conditions (large borrower default, illiquid collateral, delayed liquidator/admin response) — the same conditions the project's own bankruptcy guide describes as "rare." It is a genuine architectural gap (no minimum-health deposit gate) rather than a trivially-triggerable exploit, so likelihood is low but the class of bug is real and unmitigated by any explicit check in the deposit path.

### Recommendation
Add a minimum-health/minimum-share-value gate to `validate_bank_state` (or a dedicated check in `lending_account_deposit`) that rejects deposits when a bank's `asset_share_value` has fallen below a configurable safety threshold (e.g., analogous to the `super_admin_withdraw` 0.8 share-value safety rail already present for admin withdrawals). Alternatively, extend `socialize_loss` so that when a bank is killed, only the portion of `total_value` attributable to shares outstanding *before* the triggering bad debt was incurred is subject to zeroing, or require admins to move a critically-impaired bank into `ReduceOnly`/`Paused` automatically once its share value crosses a low-health threshold, blocking further deposits before a full kill can occur.

### Proof of Concept
Conceptual reproduction (mirrors the reported PoC structurally, cannot be run without a live/bankrun environment):
1. Bank X has one borrower default resolved via `lending_pool_handle_bankruptcy`; `socialize_loss` reduces `asset_share_value` to a very small positive number without killing the bank (`total_value` still exceeds this `loss_amount`). Bank remains `Operational`. [8](#0-7) 
2. A new depositor calls `lending_account_deposit` into bank X; since there is no minimum-share-value check, the deposit succeeds and mints a very large number of shares for a modest deposit, per `get_asset_shares`. [9](#0-8) 
3. A second, unrelated borrower default is resolved via `lending_pool_handle_bankruptcy`; this time `loss_amount` (bad debt minus insurance coverage) exceeds the bank's `total_value` (which now includes the new deposit), so `socialize_loss` sets `asset_share_value = 0` and `kill_bank = true`. [10](#0-9) 
4. The bank transitions to `KilledByBankruptcy`, permanently blocking all operations; the new depositor's principal (which was real, transferred tokens) is unrecoverable. [11](#0-10)

```rust
pub fn validate_bank_state(bank: &Bank, kind: InstructionKind) -> MarginfiResult {
    if bank.config.operational_state == BankOperationalState::KilledByBankruptcy {
        return err!(MarginfiError::BankKilledByBankruptcy);
    }
    // Bank exists but has not completed one-time setup (e.g. JupLend seed deposit). Block every
    // operation until init runs.
    if bank.config.operational_state == BankOperationalState::Uninitialized {
        return err!(MarginfiError::BankUninitialized);
    }

    match kind {
        InstructionKind::FailsInReduceState if bank.config.operational_state.is_reduce_only() => {
            return err!(MarginfiError::BankReduceOnly);
        }

        InstructionKind::FailsInPausedState
            if bank.config.operational_state == BankOperationalState::Paused =>
        {
            return err!(MarginfiError::BankPaused);
        }

        InstructionKind::FailsIfPausedOrReduceState
            if matches!(
                bank.config.operational_state,
                BankOperationalState::Paused
                    | BankOperationalState::ReduceOnly
                    | BankOperationalState::ReduceOnlyWithBorrowingPower
            ) =>
        {
            return match bank.config.operational_state {
                BankOperationalState::Paused => {
                    err!(MarginfiError::BankPaused)
                }
                state if state.is_reduce_only() => {
                    err!(MarginfiError::BankReduceOnly)
                }
                _ => unreachable!(),
            };
        }
        _ => {}
    }

    Ok(())
}
```

```rust
    /// Socialize a loss of `loss_amount` among depositors, the `total_deposit_shares` stays the
    /// same, but total value of deposits is reduced by `loss_amount`;
    ///
    /// In cases where assets < liabilities, the asset share value will be set to zero, but cannot
    /// go negative. Effectively, depositors forfeit their entire deposit AND all earned interest in
    /// this case.
    fn socialize_loss(&mut self, loss_amount: I80F48) -> MarginfiResult<bool> {
        let mut kill_bank = false;
        let total_asset_shares: I80F48 = self.total_asset_shares.into();
        let old_asset_share_value: I80F48 = self.asset_share_value.into();

        // Compute total "old" value of shares
        let total_value: I80F48 = total_asset_shares
            .checked_mul(old_asset_share_value)
            .ok_or_else(math_error!())?;

        // Subtract loss, clamping at zero (i.e. assets < liabilities, the bank is wiped out)
        if total_value <= loss_amount {
            self.asset_share_value = I80F48::ZERO.into();
            // This state is irrecoverable, the bank is dead.
            kill_bank = true;
        } else {
            // otherwise subtract then redistribute
            let new_share_value: I80F48 = (total_value - loss_amount)
                .checked_div(total_asset_shares)
                .ok_or_else(math_error!())?;
            self.asset_share_value = new_share_value.into();
            // Sanity check: should be unreachable.
            if new_share_value == I80F48::ZERO {
                kill_bank = true;
            }
        }

        Ok(kill_bank)
    }
```

```markdown
### KilledByBankruptcy

The bank was killed by a bankruptcy event and is irrecoverable. All operations are blocked. This
state can only be set programmatically by the `handle_bankruptcy` instruction when a bankruptcy
event wipes out all remaining assets in the bank. It **cannot** be set manually by an admin.
```
