### Title
StackerDB chunk signatures lack context binding, enabling cross-contract/cross-reward-cycle chunk replay — ([File: libstackerdb/src/libstackerdb.rs])

### Summary
The signature that authenticates a StackerDB chunk (`SlotMetadata::auth_digest`) commits only to `slot_id`, `slot_version`, and `data_hash` — it never binds the signature to the specific StackerDB smart contract (i.e., reward cycle / message lane) it was created for. Because signer slot assignments are frequently identical across multiple StackerDB replicas (e.g., the same signer holds the same `slot_id` across `signer-<rc>-<msg_id>` contracts for different reward cycles or lanes), an attacker who observes one legitimately signed, publicly-broadcast `StackerDBChunkData` can resubmit the exact same `(slot_id, slot_version, sig, data)` tuple to a *different* StackerDB replica and have it accepted as an authentic write, since nothing in the signed digest ties it to the originating contract.

### Finding Description
`SlotMetadata::auth_digest` computes the signed digest strictly from `slot_id`, `slot_version`, and `data_hash`: [1](#0-0) 

`verify()` recovers the public key from this digest and only checks it against the expected principal for that slot — it never checks which smart contract the chunk is destined for: [2](#0-1) 

The storage-layer write path, `StackerDBTx::try_replace_chunk`, re-derives the expected signer from `smart_contract` + `slot_id` and calls `slot_desc.verify(&slot_validation.signer)`, but the signature check itself is contract-agnostic — it only proves the chunk was signed by *some* address that happens to own that slot in *this* contract, not that it was signed *for* this contract: [3](#0-2) 

Slot ownership is highly likely to repeat across different StackerDB replicas: signer slot indices are derived from the reward-set/signer-set ordering, and the same address commonly retains the same `slot_id` across the various `signer-<rc>-<msg_id>` contracts (different reward cycles, same or different message lanes) as long as the signer set doesn't change. A `StackerDBChunkData` accepted into one contract is therefore, by construction of the auth digest, equally valid to submit into a different contract, whether via the public unauthenticated HTTP endpoint (`poststackerdbchunk.rs`, path `/v2/stackerdb/:address/:contract/chunks`) or via unsolicited P2P chunk-push: [4](#0-3) 

The severity is sharpest for `SignerMessage::BlockPreCommit`, which carries **no inner SIP-018 signature at all** — it is a bare `Sha512Trunc256Sum` whose only authentication is the outer StackerDB chunk-level signature: [5](#0-4) 

Unlike other signer messages (`MockProposal`, `MockSignature`, `BlockRejection`), which are additionally protected by a SIP-018 domain-separated hash (`make_structured_data_domain` with name/version/chain-id): [6](#0-5) 

`BlockPreCommit` has no such secondary binding, so replaying its raw chunk (slot_id, slot_version, sig, data) into a different contract where the sender's address owns the same slot is sufficient to have the node accept and store it as an authentic pre-commit for the wrong round/tenure. The event-classification layer only filters by payload-type-vs-lane, not by reward cycle: [7](#0-6) 

so a cross-reward-cycle replay of a same-lane message is not caught anywhere.

### Impact Explanation
This breaks the intended "chunk authenticated by owner for this replica" equality: a chunk validly signed for StackerDB replica A can be accepted as valid for StackerDB replica B whenever the sender's address happens to own the same slot in B and B's slot version has not yet advanced past the replayed version. This is an unauthenticated/unauthorized write to StackerDB state in a context the signer never intended, and for lanes lacking an inner domain-separated signature (e.g. `BlockPreCommit`), it directly forges the appearance of a signer's precommit in the wrong reward cycle/round, which can propagate network-wide as other nodes replicate the chunk.

### Likelihood Explanation
The prerequisite artifact — a validly signed `StackerDBChunkData` — is not secret; it is broadcast to and stored by every replicating peer, and is retrievable via the same GET StackerDB chunk RPC endpoints. No node secret or admin role is required; the attacker only needs (a) knowledge of one legitimately-signed chunk and (b) knowledge that the target contract assigns the same address to the same slot id, both of which are derivable from public chain state (the reward-set/signer-set is on-chain).

### Recommendation
Include the StackerDB smart contract identifier (and, where relevant, reward cycle) inside `SlotMetadata::auth_digest`, so that a signature is only valid for the specific StackerDB replica it was created for — analogous to appending a fixed, context-specific string/identifier to every signed payload as recommended in the referenced report. Additionally, add SIP-018 domain separation (or equivalent binding to `slot_id`/reward-cycle/contract) to `BlockPreCommit`, which currently relies entirely on the StackerDB chunk-level signature for authenticity.

### Proof of Concept
1. Observe a legitimately signed `StackerDBChunkData` broadcast for signer address `S` at `slot_id=k`, `slot_version=v` in contract `signer-0-3` (a `BlockPreCommit` payload), e.g. via `GET /v2/stackerdb/.../chunks/k`.
2. Confirm (from on-chain `.signers`/reward-set state, or by observing StackerDB inventories) that address `S` also owns `slot_id=k` in contract `signer-1-3` (next reward cycle, same lane) with a current slot version `< v`.
3. POST the identical bytes (`slot_id=k`, `slot_version=v`, `sig`, `data`) to `/v2/stackerdb/<addr>/signer-1-3/chunks` on any node.
4. `StackerDBTx::try_replace_chunk` ( [3](#0-2) ) calls `slot_desc.verify(&slot_validation.signer)`, which succeeds because the digest never encoded which contract it belongs to; the chunk is accepted and stored as a legitimate `BlockPreCommit` for reward cycle 1, even though `S` never signed anything for that cycle.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )

    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
