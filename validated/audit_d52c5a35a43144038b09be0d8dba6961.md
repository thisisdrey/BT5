### Title
Wallet Contract relayer fee (`tx_fee`) can round to zero via truncating integer division, causing relayers to execute Ethereum-emulated transactions for free — ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs])

### Summary
`parse_rlp_tx_to_action` computes the fee a relayer is refunded for executing an ETH-implicit account's transaction as `tx.max_fee_per_gas.saturating_mul(tx.gas_limit)` converted into yoctoNEAR, with no lower-bound / non-zero check, mirroring the `bptClaim == 0` pattern from the referenced report (a division/scaling result silently truncating to zero and the code proceeding instead of reverting).

### Finding Description
`tx_fee` is computed by multiplying `max_fee_per_gas * gas_limit`, clamping to `VALUE_MAX`, converting to `u128`, and then scaling to yoctoNEAR by `wei_amount.saturating_mul(MAX_YOCTO_NEAR)`: [1](#0-0) 
This fee value is what an honest relayer is compensated with for submitting the user's RLP-encoded transaction to the Wallet Contract, as shown in the relayer-refund test where `gas_price` is deliberately chosen as `RELAYER_REFUND / (GAS_LIMIT * MAX_YOCTO_NEAR)`: [2](#0-1) 
If the ETH-side `max_fee_per_gas` (an integer, Wei-per-gas-unit) times `gas_limit` produces a value smaller than `1` after this pipeline — or if `max_fee_per_gas` itself is `0`, which is an entirely valid field for the caller (an ordinary Wallet Contract user) to set on their signed Ethereum transaction — `tx_fee` becomes exactly `0`. There is no check anywhere in `parse_rlp_tx_to_action` that rejects or reverts a `tx_fee` of zero before proceeding to build the `EthEmulationKind` payload with `fee: tx_fee`.

Unlike the `_convertStrategyTokensToBPTClaim` example (where the caller loses funds), here it is the relayer service — an unprivileged actor who pays real NEAR gas fees to submit the transaction on behalf of the eth-implicit-account owner — who is left uncompensated: they perform work and pay gas, but the code computing their compensation silently truncates to zero instead of failing the parse/build step. This matches the reported bug class exactly: a division/scaling result that can legitimately be zero is used downstream (as a refund amount) without any zero-check or revert, silently defeating the economic assumption the mechanism was built to provide (per the file's own comment: "This is sent as a refund to the relayer... allows a user with $NEAR to use a relayer service... immediately without additional on-boarding").

### Impact Explanation
This does not directly threaten protocol consensus, cause token inflation, enable double-spend, or escalate privileges. Its concrete effect is: a relayer who agrees to front gas costs for eth-implicit-account users, expecting to be reimbursed via the emulated fee mechanism, receives zero reimbursement whenever the user sets (or a malicious wallet-contract caller deliberately sets) `max_fee_per_gas = 0` or a sufficiently small fee/gas_limit product. Because the relayer's Wallet-Contract interaction is unprivileged and permissionless (any signed Ethereum-style transaction routed through `rlp_execute`), a user could deliberately craft near-zero fees to freeload off relayer infrastructure, causing relayers to lose real NEAR (their own gas costs) with no compensation. This is a loss-of-funds/broken-incentive issue for relayer operators rather than a shard-halting or state-root-divergence bug.

### Likelihood Explanation
Likelihood is high for the "user forgets/omits `max_fee_per_gas`" case (honest mistake) and moderate for the intentional-exploitation case, since crafting an RLP transaction with `max_fee_per_gas = 0` requires no special privilege — any account holder controlling the Secp256K1 key of the eth-implicit account can do it. The path is fully reachable from an ordinary client interaction (relayer forwarding a user's Ethereum-style transaction to `rlp_execute`), with no special network or validator conditions required.

### Recommendation
Add an explicit minimum-fee or non-zero check on `tx_fee` inside `parse_rlp_tx_to_action` (or the caller in `internal.rs`) before it's embedded into `EthEmulationKind::EOABaseTokenTransfer { fee: tx_fee, .. }`/`ERC20` handling, and reject (return an error) transactions whose computed relayer fee would round to zero when a non-zero fee was economically expected, consistent with the "prefer revert over silent zero-value success" pattern recommended in the referenced report.

### Proof of Concept
1. Deploy an ETH-implicit account with the Wallet Contract and fund it, per the existing test harness pattern in `test_wallet_contract_interaction`. [3](#0-2) 
2. Construct an Ethereum-style `Transaction2930` with `gas_price: 0.into()` (i.e., `max_fee_per_gas = 0`) and any nonzero `gas_limit`, targeting a base-token-transfer or ERC-20 action, and sign it with the eth-implicit account's Secp256K1 key.
3. Have a relayer submit it via `rlp_execute`, mirroring `create_rlp_execute_tx`. [4](#0-3) 
4. Observe that `tx_fee` computed in `parse_rlp_tx_to_action` is `0` yoctoNEAR — `wei_amount = 0.saturating_mul(gas_limit).min(VALUE_MAX).low_u128() == 0`, so `NearToken::from_yoctonear(0)` — and the emulated transfer/ERC-20 action still executes successfully, refunding the relayer nothing, while the relayer still paid real NEAR gas to submit the transaction. pub fn create_rlp_execute_tx(
    target: &AccountIdRef,
    mut action: Action,
    nonce: u64,
    eth_implicit_account: &AccountIdRef,
    secret_key: &SecretKey,
    near_signer: &NearSigner<'_>,
    env: &TestEnv,
) -> SignedTransaction {
    const CHAIN_ID: u64 = 399;
    // handles 24 vs 18 decimal mismatch between $NEAR and $ETH
    const MAX_YOCTO_NEAR: u128 = 1_000_000;

    // Construct Eth transaction from user's intended action
    let value = match &mut action {
        Action::Transfer(tx) => {
            let raw_amount = tx.deposit;
            tx.deposit = Balance::from_yoctonear(raw_amount.as_yoctonear() % MAX_YOCTO_NEAR);
            Wei::new_u128(raw_amount.as_yoctonear() / MAX_YOCTO_NEAR)
        }
        Action::FunctionCall(fn_call) => {
            let raw_amount = fn_call.deposit;
            fn_call.deposit = Balance::from_yoctonear(raw_amount.as_yoctonear() % MAX_YOCTO_NEAR);
            Wei::new_u128(raw_amount.as_yoctonear() / MAX_YOCTO_NEAR)
        }
        _ => Wei::zero(),
    };
    let tx_data = abi_encode(target.to_string(), action);
    let transaction = Transaction2930 {
        chain_id: CHAIN_ID,
        nonce: nonce.into(),
        gas_price: U256::zero(),
        gas_limit: U256::zero(),
        to: Some(derive_address(target)),
        value,
        data: tx_data,
        access_list: Vec::new(),
    };
    let signed_tx = sign_eth_transaction(transaction, &secret_key);
