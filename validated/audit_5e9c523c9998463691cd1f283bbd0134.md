## Local Analog: `pallet-message-queue::execute_overweight` has no economic incentive, so permanently-overweight messages can remain stuck forever

### Title
Permanently overweight messages require a permissionless but unincentivized `execute_overweight` call, risking indefinite message-queue stalls - (File: `substrate/frame/message-queue/src/lib.rs`)

### Summary
The Aloe report's core defect is a two-step process (permissionless `warn`, then privileged `liquidate`) where the first step is mandatory but nobody is paid to perform it, so the whole liquidation flow can stall. `pallet-message-queue`, which underlies UMP/DMP/HRMP and XCM-based bridge message delivery (including Snowbridge's use of the queue infrastructure), has the same structural gap: automatic processing (`on_initialize`/`on_idle` via `service_queues_impl`) will never retry a message once it is classified as *permanently overweight*; only a manual, permissionless `execute_overweight` extrinsic can unstick it [1](#0-0) . Unlike the other permissionless "unstick" calls in the same codebase (`pallet-nomination-pools::apply_slash`, `pallet-staking-async::apply_slash`), `execute_overweight` grants the caller **no reward and no fee waiver** — it is a normal, fee-paying `DispatchResultWithPostInfo` call.

### Finding Description
The message-queue documentation itself states the failure mode plainly: [1](#0-0) 

`execute_overweight` is defined as: [2](#0-1) 

Compare this to the two structurally similar "apply-a-pending-action-permissionlessly" calls elsewhere in the same codebase, which *do* incentivize the caller:

- `pallet-nomination-pools::apply_slash` refunds the caller's fee (`Pays::No`) and can reward the caller with a slice of the slash via the stake adapter: [3](#0-2) 
- `pallet-staking-async::apply_slash` is explicitly documented as permissionless with `Pays::No` fee-waiver as its only incentive: [4](#0-3) 

`execute_overweight` has neither a fee waiver nor a reward. The dispatch weight is `T::WeightInfo::execute_overweight_page_updated().max(...).saturating_add(*weight_limit)`, meaning the caller must pay tx fees proportional to the (potentially large) weight of the overweight message they are executing, purely to unblock the chain's own queue state, for zero return. There is also no guarantee the message will still be there to execute — the same section notes the page may be reaped/culled before manual execution occurs: [5](#0-4) .

Since `pallet-message-queue` is the generic processing engine for UMP, DMP, and HRMP messages between the relay chain and parachains (and is used by bridge/XCM message pipelines), a permanently overweight message in this queue blocks the `ReadyRing` position for that origin's later messages (later messages in the same page cannot be processed until this position is resolved, and stale pages accumulate against `MaxStale` before being culled). Nobody but the affected message's ultimate beneficiary (e.g., an XCM program moving funds, or a bridge commitment) has a reason to pay gas to call `execute_overweight`, and that beneficiary may not know an overweight event even occurred (it requires monitoring `Event::OverweightEnqueued`) or may not have funds available to pay the fee for executing it.

### Impact Explanation
This matches the "public underpriced work that degrades block production or stalls bridge processing" and "permanent user-fund or bridge-state lock" impact categories: an overweight message that nobody executes remains queued indefinitely (subject only to eventual, non-guaranteed page culling under `MaxStale`), which can mean XCM-transported funds, governance-relevant messages, or bridge payloads never settle, and the associated `Pages`/`BookStateFor` storage remains occupied with no path to resolution other than an altruistic, fee-paying, unrewarded call.

### Likelihood Explanation
Overweight classification happens automatically whenever a message's processing weight exceeds the per-page/per-block weight budget available at servicing time (`Overweight`/`InsufficientWeight` branches in `process_message_payload`), which is a routine occurrence under congestion or with heavy XCM programs, not an exotic edge case. Given the total absence of an economic incentive (contrast with `apply_slash` calls elsewhere in the codebase which get `Pays::No` or a reward cut), it is realistic that a permanently overweight message sits unresolved until it is silently culled by `do_reap_page`'s staleness watermark, which itself depends on unrelated queue traffic patterns.

### Recommendation
Introduce an incentive for `execute_overweight` analogous to the existing `apply_slash` patterns in the codebase: waive the caller's transaction fee (`Pays::No`) unconditionally on success, and/or allow protocols built on top of the queue (e.g., XCM, bridge pallets) to attach a small reward payable to whoever successfully executes their overweight message, so that permanently overweight, chain-critical messages are not left to depend on altruistic, unrewarded calls.

### Proof of Concept
1. Enqueue a message whose processing weight exceeds the queue's available per-block weight limit so that `service_queues`/`on_initialize` classifies it as permanently overweight, emitting `Event::OverweightEnqueued` (see the existing test demonstrating this exact classification): [6](#0-5) 
2. Observe that automatic servicing (`on_initialize`/`on_idle`) will never retry this message per the pallet's own documentation: [1](#0-0) 
3. Confirm that resolving it requires a signed, fee-paying `execute_overweight` call with no `Pays::No` and no reward, unlike `pallet-nomination-pools::apply_slash`/`pallet-staking-async::apply_slash`: [7](#0-6) 
4. Since no account benefits economically from paying to execute someone else's stuck message, the message (and any dependent later messages/positions in the same page) can remain unresolved indefinitely, bounded only by the unrelated `MaxStale` culling heuristic in `do_reap_page`: [8](#0-7)

			// The maximum number of stale pages (i.e. of overweight messages) allowed before
			// culling can happen at all. Once there are more stale pages than this, then historical
			// pages may be dropped, even if they contain unprocessed overweight messages.
			let max_stale = T::MaxStale::get();

			// The amount beyond the maximum which are being used. If it's not beyond the maximum
			// then we exit now since no culling is needed.
			let overflow = match stale_pages.checked_sub(max_stale + 1) {
				Some(x) => x + 1,
				None => return false,
			};

			// The special formula which tells us how deep into index-history we will pages. As
			// the overflow is greater (and thus the need to drop items from storage is more urgent)
			// this is reduced, allowing a greater range of pages to be culled.
			// With a minimum `overflow` (`1`), this returns `max_stale ** 2`, indicating we only
			// cull beyond that number of indices deep into history.
			// At this overflow increases, our depth reduces down to a limit of `max_stale`. We
			// never want to reduce below this since this will certainly allow enough pages to be
			// culled in order to bring `overflow` back to zero.
			let backlog = (max_stale * max_stale / overflow).max(max_stale);

			let watermark = book_state.begin.saturating_sub(backlog);
			page_index < watermark
		};

#[test]
fn execute_overweight_works() {
	build_and_execute::<Test>(|| {
		set_weight("bump_service_head", 1.into_weight());
		set_weight("service_queue_base", 1.into_weight());
		set_weight("service_page_base_completion", 1.into_weight());

		// Enqueue a message
		let origin = MessageOrigin::Here;
		MessageQueue::enqueue_message(msg("weight=200"), origin);
		// Load the current book
		let book = BookStateFor::<Test>::get(origin);
		assert_eq!(book.message_count, 1);
		assert!(Pages::<Test>::contains_key(origin, 0));

		// Mark the message as permanently overweight.
		assert_eq!(MessageQueue::service_queues(4.into_weight()), 4.into_weight());
		assert_eq!(QueueChanges::take(), vec![(origin, 1, 10)]);
		assert_last_event::<Test>(
			Event::OverweightEnqueued {
				id: blake2_256(b"weight=200"),
				origin: MessageOrigin::Here,
				message_index: 0,
				page_index: 0,
			}
			.into(),
		);
