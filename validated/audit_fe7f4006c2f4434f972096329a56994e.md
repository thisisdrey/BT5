### Title
Unbounded disk write from attacker-controlled blob size in `createTemporaryIgnoreRevsFile` - (File: internal/gitaly/service/commit/raw_blame.go)

### Summary
`RawBlame` lets a caller supply `IgnoreRevisionsBlob`, which is resolved via `catfile.ObjectReader.Object` and then copied in full to a freshly created temp file with `blobObj.WriteTo(tmpFile)`, with no size cap on the blob being copied. Because the blob revision is fully attacker-controlled (any object reachable in the caller's own repository), an attacker can point this at an arbitrarily large blob they committed themselves, forcing Gitaly to write that entire blob to local disk (`os.CreateTemp("", ...)`, i.e. the OS temp directory) for every `RawBlame` RPC invocation.

### Finding Description
In `RawBlame` (`internal/gitaly/service/commit/raw_blame.go:45-57`), if `in.GetIgnoreRevisionsBlob()` is set, `createTemporaryIgnoreRevsFile` is called with the raw attacker-supplied bytes as a revision string. The function resolves that revision against the request's own repository via the catfile object reader (`internal/gitaly/service/commit/raw_blame.go:159`), verifies it is a blob (`:174`), and then writes the **entire** blob object to a newly created temp file with `blobObj.WriteTo(tmpFile)` (`:198`) — there is no `io.CopyN`/`io.LimitReader` bound, unlike the pattern used elsewhere in the codebase (e.g. `Repo.ReadObjectWithLimit` at `internal/git/localrepo/objects.go:91-118`, which explicitly wraps the object reader in `io.LimitReader`). The only validation performed (`validateRawBlameRequest`) checks repository existence, revision syntax, path locality, and blame range format — none of it bounds the size of the ignore-revs blob. Since the attacker controls the target repository's content (they can push/commit any blob to a repo they own), they can commit a multi-gigabyte blob and reference its OID/branch as `IgnoreRevisionsBlob`. Each `RawBlame` call with that blob then triggers a full-size copy to `os.TempDir()`, a filesystem that is typically shared across all repositories/tenants on the Gitaly node and distinct from the per-repository storage quota enforced by GitLab Rails.

### Impact Explanation
Repeated or concurrent `RawBlame` calls referencing a large blob can exhaust disk space on the Gitaly node's temp directory, which is shared storage rather than repository-specific storage subject to GitLab's per-repository storage quotas. This matches a Denial-of-Service impact class (resource exhaustion of a Gitaly RPC handler / node), potentially affecting other tenants/repositories on the same node whose operations also depend on temp-directory availability (e.g. other Gitaly RPCs that write temp files).

### Likelihood Explanation
An unprivileged authenticated user with push access to any repository they control can trivially commit a large blob and issue `RawBlame` requests referencing it as `IgnoreRevisionsBlob`; no special permissions, secrets, or non-default configuration are required. Repeatability is high, limited only by whatever git/GitLab push size limits exist upstream (which are enforced outside Gitaly and not a Gitaly-level control), and the attack can be parallelized across multiple RPC calls/streams to multiply disk pressure.

### Recommendation
Bound the amount of data copied in `createTemporaryIgnoreRevsFile`, e.g. by checking `blobObj.ObjectSize()` against a sane maximum (an ignore-revs file only needs to contain a list of hex OIDs) and rejecting oversized blobs with `InvalidArgument`, or by wrapping the copy in `io.LimitReader`/`io.CopyN` similar to `Repo.ReadObjectWithLimit`, aborting/erroring if the blob exceeds the limit rather than silently truncating.

    blobOID := gittest.WriteBlob(t, cfg, repoPath, largeContent)

    client, _ := newCommitServiceClient(t, cfg.SocketPath)
    stream, err := client.RawBlame(ctx, &gitalypb.RawBlameRequest{

        Revision:             []byte("HEAD"),
        Path:                 []byte("file.txt"),
        IgnoreRevisionsBlob:  []byte(blobOID),
    })
    require.NoError(t, err)

    // Expect: server writes the full 500MB blob to os.TempDir() before running
    // `git blame`, unbounded by any size check. Scaling blobOID content to multiple
    // GB and issuing many concurrent RawBlame calls demonstrates disk exhaustion
    // of the shared temp filesystem.
    _, err = stream.Recv()
    _ = err
}
