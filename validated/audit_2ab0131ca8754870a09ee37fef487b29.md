Audit Report

## Title
Missing slippage protection in `SystemFrontend::swap_and_burn` lets an unprivileged caller under-fund Ethereum-side execution fees and relayer tips - (File: `bridges/snowbridge/pallets/system-frontend/src/lib.rs`)

## Summary
`swap_and_burn`, called from the public `register_token` and `add_tip` extrinsics via `swap_fee_asset_and_burn`, invokes `T::Swap::swap_exact_tokens_for_tokens` with `amount_out_min` hard-coded to `None` and the comment "No minimum amount required". [1](#0-0)  The resulting `ether_gained`, fully dependent on unconstrained AMM spot price, is burned and forwarded as the `amount` field of the `RegisterToken`/`AddTip` XCM `Transact` calls to BridgeHub. [2](#0-1) [3](#0-2) 

## Finding Description
`register_token` and `add_tip` are both public, signed extrinsics. [4](#0-3) [5](#0-4)  Both call `swap_fee_asset_and_burn`, which routes to `swap_and_burn` whenever the supplied fee/tip asset is not already Ether. [6](#0-5) 

`swap_and_burn` calls the generic `pallet_asset_conversion::Swap::swap_exact_tokens_for_tokens` trait method, passing `None` for `amount_out_min` — the exact parameter designed to bound slippage. [1](#0-0)  The trait definition documents that `amount_out_min` is meant to guard against unfavorable execution when supplied, but it is `Option`, so passing `None` fully disables that protection. [7](#0-6)  The concrete pallet implementation simply forwards this optional parameter unchanged into `do_swap_exact_tokens_for_tokens`, which only enforces the `amount_out >= amount_out_min` check when `Some` is supplied. [8](#0-7)  Elsewhere in the codebase, the public `AssetConversion::swap_exact_tokens_for_tokens` extrinsic correctly requires and enforces a caller-supplied minimum. [9](#0-8) [10](#0-9) 

Because `AssetConversion` pools are constant-product AMMs, an attacker can move the pool price within the same atomic extrinsic (e.g. `Utility::batch_all`) by first swapping a large amount through the same pool, then calling `register_token`/`add_tip` in the same batch. Since `swap_and_burn` accepts any non-zero output with no floor check against the pre-manipulation price, the attacker's preceding swap determines how little Ether the second swap yields, and there is no `ensure!` anywhere in `swap_and_burn` or its callers to guard against this.

## Impact Explanation
This falls under the "public underpriced work that degrades block production or stalls bridge processing" category of the impact gate. For `register_token`, a manipulated swap can cause the Ethereum-side registration message to dispatch with near-zero backing Ether, starving the execution of gas/fee on Ethereum and stalling registration. For `add_tip`, the relayer tip amount allocated on BridgeHub (`AddTip.amount`, used "to be allocated to the reward in the Inbound/Outbound pallet" per the code comment) can be driven near zero despite the caller supplying a full-value tip asset, degrading relayer incentives for message delivery. [11](#0-10)  No privileged role is required — only an ordinary signed account submitting a batched extrinsic.

## Likelihood Explanation
Likelihood is highest for low-liquidity or newly-created `fee_asset`/Ether pools, where a single swap within the same batch can substantially move the AMM price before `swap_and_burn` executes. Nothing in the code path checks a minimum output or an oracle-derived price, and the `None` is unconditional for every non-Ether fee asset, so the attack is repeatable against any thin pool.

## Recommendation
Thread a `min_amount_out` (and optionally a slippage/deadline bound) parameter through `register_token`/`add_tip` into `swap_and_burn`, replacing the hard-coded `None` passed to `T::Swap::swap_exact_tokens_for_tokens`, and reject the call if `ether_gained` falls below the caller- or system-configured minimum, mirroring the protection in `pallet_asset_conversion::do_swap_exact_tokens_for_tokens`.

## Proof of Concept
1. Attacker identifies or creates a low-liquidity `AssetConversion` pool for `(fee_asset_location, EthereumLocation)`.
2. Attacker submits `Utility::batch_all` containing:
   a. `AssetConversion::swap_exact_tokens_for_tokens` swapping a large amount of `fee_asset` into Ether, sharply reducing the Ether reserve and moving the price against subsequent `fee_asset -> Ether` swaps.
   b. `SystemFrontend::add_tip(message_id, fee_asset_amount)` (or `register_token` with a non-root origin and `fee_asset`), internally invoking `swap_and_burn` with `amount_out_min: None`.
3. Because of the attacker's own preceding swap, `ether_gained` computed inside `swap_and_burn` is far below fair price, yet the call succeeds since there is no floor check.
4. The resulting near-zero `ether_gained` is burned and forwarded as `amount` in the `AddTip`/`RegisterToken` XCM `Transact` call to BridgeHub, under-funding the relayer reward or Ethereum-side execution fee despite the caller supplying a full-value `fee_asset` amount.

		fn swap_fee_asset_and_burn(
			origin: Location,
			fee_asset: Asset,
		) -> Result<u128, DispatchError> {
			let ether_location = T::EthereumLocation::get();
			let (fee_asset_location, fee_amount) = match fee_asset {
				Asset { id: AssetId(ref loc), fun: Fungible(amount) } => (loc, amount),
				_ => {
					tracing::debug!(target: LOG_TARGET, ?fee_asset, "error matching fee asset");
					return Err(Error::<T>::UnsupportedAsset.into());
				},
			};
			if fee_amount == 0 {
				return Ok(0);
			}

			let ether_gained = if *fee_asset_location != ether_location {
				Self::swap_and_burn(
					origin.clone(),
					fee_asset_location.clone(),
					ether_location,
					fee_amount,
				)
				.inspect_err(|&e| {
					tracing::debug!(target: LOG_TARGET, ?e, "error swapping asset");
				})?
			} else {
				burn_for_teleport::<T::AssetTransactor>(&origin, &fee_asset)
					.map_err(|_| Error::<T>::BurnError)?;
				fee_amount
			};
			Ok(ether_gained)
		}
