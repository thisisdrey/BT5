### Title
Attachment size limit bypass on download-resolution path allows unbounded attachment storage growth - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AtlasDB::should_keep_attachment` enforces `attachment.content.len() as u32 <= atlas_config.attachments_max_size` but is only invoked on the POST-attachment ingestion path. [1](#0-0)  The `AttachmentsBatchStateMachine::Done` branch in `download.rs` writes downloaded attachments straight into the AtlasDB via `insert_instantiated_attachment` without ever calling `should_keep_attachment`, since that check is only referenced from `posttransaction.rs`, `db.rs`, and its own tests — never from `download.rs`.

### Finding Description
`should_keep_attachment` is the sole enforcement point for the `attachments_max_size` cap configured in `AtlasConfig`, and it is invoked from the transaction-attached-attachment POST path (`posttransaction.rs`). [1](#0-0)  The attachment download-resolution logic in `download.rs`, however, calls `network.atlasdb.insert_instantiated_attachment(&attachment)` directly for each attachment drained out of `context.attachments` in the `Done` state, with no size gate. A remote peer that responds to a legitimate `GET /v2/attachments/{hash}` request (issued by the requesting node as part of normal Atlas attachment-instance resolution) with an oversized `Attachment.content` can have that content persisted into the `attachments` SQLite table even though it exceeds the locally configured `attachments_max_size`. The only remaining gate on this path is the attachment's content hash matching the expected `Hash160` (integrity, not size), so a peer can supply arbitrarily large content bounded only by the wire-level message/payload size limits of the P2P/RPC transport, which are typically far larger than the intended `attachments_max_size` policy value.

### Impact Explanation
This lets any peer a node fetches attachments from cause that node's local AtlasDB `attachments` table to grow beyond its configured storage policy on a per-attachment basis, repeatable for every attachment instance the victim node resolves from that peer. This directly breaks the size-based resource-exhaustion protection the `attachments_max_size` config is meant to provide, matching the "attachment/BNS mismatch" / bounded resource-exhaustion class of High-severity issues (state stored that violates the configured commitment, without any signature/consensus check catching it).

### Likelihood Explanation
No privileged role is required: the attacker only needs to run/control a peer that a Stacks node contacts for attachment resolution (or answer any `GET /v2/attachments/{hash}` request the target node issues), which is standard Atlas subsystem behavior and remotely reachable. The victim node does not need any unusual configuration beyond having Atlas attachment download enabled, which is default behavior; the attack is essentially free to repeat for every downloaded attachment.

### Recommendation
Apply the same `should_keep_attachment` (or equivalent size/contract check) inside the `AttachmentsBatchStateMachine::Done` branch in `download.rs` before calling `insert_instantiated_attachment`, discarding or rejecting attachments whose `content.len()` exceeds `atlas_config.attachments_max_size`, mirroring the POST-ingestion path's enforcement.

### Proof of Concept
Construct an `AttachmentsBatchStateContext` with one queued `AttachmentInstance`, drive the state machine with a mocked `GetAttachmentResponse` whose `attachment.content` is a `Vec<u8>` sized larger than `atlas_config.attachments_max_size` (but still matching the instance's expected content hash), call `try_proceed` until it reaches `Done`, then call `atlasdb.find_attachment(&content_hash)` and assert the returned attachment's `content.len()` exceeds `attachments_max_size` — demonstrating the size policy was bypassed relative to `AtlasDB::should_keep_attachment`'s check.     pub fn should_keep_attachment(
        &self,
        contract_id: &QualifiedContractIdentifier,
        attachment: &Attachment,
    ) -> bool {
        if !self.atlas_config.contracts.contains(contract_id) {
            info!(
                "Atlas: will discard posted attachment - {} not in supported contracts",
                contract_id
            );
            return false;
        }
        if attachment.content.len() as u32 > self.atlas_config.attachments_max_size {
            info!("Atlas: will discard posted attachment - attachment too large");
            return false;
        }
        true
    }
