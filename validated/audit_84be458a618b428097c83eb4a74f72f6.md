Based on the investigation, I found a concrete constructor bug in `ReceiveDescriptionCapsule` that is directly analogous to the CVE's core issue — an object being used/dereferenced with an uninitialized reference field caused by a wrong-variable assignment during construction.

### Title
Null-pointer crash via uninitialized `receiveDescription` field in shielded transaction parameter builder - (File: `framework/src/main/java/org/tron/core/capsule/ReceiveDescriptionCapsule.java`)

### Summary
`ReceiveDescriptionCapsule` has a constructor that takes a `ReceiveDescription outputDescription` parameter but never assigns it to the instance field — it instead self-assigns the (still-null) field to itself, silently discarding the caller-supplied data and leaving the object's `receiveDescription` field `null`.

### Finding Description
The constructor at [1](#0-0) 
is written as:
```java
public ReceiveDescriptionCapsule(final ReceiveDescription outputDescription) {
    this.receiveDescription = receiveDescription;
}
```
The right-hand side references the class field `receiveDescription` (not the constructor parameter `outputDescription`). Since this is a fresh object, `this.receiveDescription` is `null` at that point, so the assignment is effectively a no-op — the object ends up with a `null` `receiveDescription` field regardless of what `ReceiveDescription` was passed in.

Every other accessor in the class assumes `receiveDescription` is non-null and directly dereferences it, e.g.: [2](#0-1) [3](#0-2) 
Any call to `getValueCommitment()`, `getEphemeralKey()`, `getEncCiphertext()`, `getCm()`, `getZkproof()`, `getData()`, or `getInstance()` on an instance built via this constructor throws a `NullPointerException`, because it operates on an uninitialized reference rather than the caller-supplied data — the same class of bug the CVE describes (an operation performed on an uninitialized/incorrect memory reference caused by mishandling of crafted/attacker-influenced input during object construction).

This constructor is used by shield-transaction builders on the node side: [4](#0-3) [5](#0-4) 
These classes are invoked from node-side Wallet gRPC/HTTP endpoints that construct shielded transaction parameters on behalf of a caller (e.g., shielded TRC-20 parameter/transaction construction APIs), meaning an unprivileged API client can trigger this code path.

### Impact Explanation
If the buggy `(ReceiveDescription)` constructor overload is reached with a non-null intended output description, the resulting capsule silently loses that description's contents (`null` instead of the real proto), and any subsequent access (serialization via `getData()`, or field getters) throws an unhandled `NullPointerException`. Depending on whether this exception propagates uncaught, this can crash the request-handling thread of the node's Wallet/HTTP/gRPC service, denying that API to further callers — matching the CVE's "crash the analyzer/service via an uninitialized reference" impact class.

### Likelihood Explanation
I was not able to fully confirm, within the available search budget, the exact line(s) in `ZenTransactionBuilder.java` / `ShieldedTRC20ParametersBuilder.java` that invoke this specific `(ReceiveDescription)` overload versus the other, correctly-implemented overloads (byte[] or the six-`ByteString`-argument constructor) in the same file. Both alternate constructors are implemented correctly and do not have this bug. Therefore likelihood of exploitation depends on whether production call sites actually use the broken overload; this could not be verified with full confidence due to running out of investigation iterations.

### Recommendation
Fix the constructor to assign the parameter, not the field:
```java
public ReceiveDescriptionCapsule(final ReceiveDescription outputDescription) {
    this.receiveDescription = outputDescription;
}
```
Additionally, audit all call sites in `ZenTransactionBuilder` and `ShieldedTRC20ParametersBuilder` to confirm which overload is used, and add null-guards or unit tests asserting round-trip integrity (constructed capsule getters return exactly what was passed in).

### Proof of Concept
```java
ReceiveDescription rd = ReceiveDescription.newBuilder()
    .setValueCommitment(ByteString.copyFrom(new byte[32]))
    .build();
ReceiveDescriptionCapsule capsule = new ReceiveDescriptionCapsule(rd);
capsule.getValueCommitment(); // throws NullPointerException — receiveDescription is null
```

**Caveat**: I could not conclusively verify, within the remaining tool budget, that the vulnerable `(ReceiveDescription)` overload (rather than the safe overloads) is the one actually called from `ZenTransactionBuilder` / `ShieldedTRC20ParametersBuilder` at their externally reachable call sites. This should be verified in the codebase before treating this as confirmed-exploitable in production.
