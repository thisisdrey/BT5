No vulnerability found for this question.

**Rationale:** The behavior described is intentional, documented API functionality, not a bug. `HttpRequestContentsExtensions::tip_request` parses the `tip` query parameter into a `TipRequest` [1](#0-0)  and `StacksNodeState::load_stacks_chain_tip` explicitly returns the caller-supplied block ID verbatim for `TipRequest::SpecificTip(tip) => Ok(tip.clone())` [2](#0-1) . This is by design: the endpoint is meant to let a caller read historical/any-known-block state, not just the canonical tip — the public API docs state that `tip` may be any 64-hex-character block ID to "use specific block ID" [3](#0-2) .

When a caller omits `tip` (or the value is malformed), the handler defaults to `TipRequest::UseLatestAnchoredTip`, which resolves strictly through `NakamotoChainState::get_canonical_block_header` — the actual canonical tip [4](#0-3) . The vulnerability claim assumes the response is supposed to represent "state committed at the canonical tip" unconditionally, but that equality is only claimed for the default/omitted-tip case. When a caller explicitly supplies `tip=<some_block_id>`, they are opting into querying that specific block's state — including on a fork the node has processed — and the response is correctly scoped to that request, not falsely presented as canonical. `RPCGetContractSrcRequestHandler::try_handle_request` and the sibling handlers (`getaccount.rs`, `getcontractabi.rs`, `getdatavar.rs`, `getconstantval.rs`, `callreadonly.rs`, etc.) all follow this same documented pattern [5](#0-4) .

Since this is expected, documented behavior explicitly requested by the caller via the `tip` parameter (not a forged/unauthenticated write, crash, or unrequested substitution of non-canonical for canonical data), it does not meet the required impact categories (no equality violation for the default/unspecified-tip path, no forgery, no crash).
