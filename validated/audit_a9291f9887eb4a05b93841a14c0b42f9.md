### Title
Heap buffer over-read parsing ZIP/JAR central directory entries with no bounds checking - ([File: third_party/ijar/zip.cc])

### Summary
`InputZipFile::ProcessCentralDirEntry()` in `third_party/ijar/zip.cc:493-545` reads a sequence of fixed-width fields (`u4`/`u2`/`u8` — 32/16/64-bit integers, the same class of "LONG data type" the CVE describes) directly out of the mmap'd input buffer via `get_u4le`, `get_u2le`, `get_u8le`, and then walks the "extra field" chain, without ever calling the buffer-remaining check that the rest of the parser uses.

### Finding Description
The local-file-entry parser in the same file is careful: `InputZipFile::ProcessLocalFileEntry()` and `SkipFile()`/`ProcessFile()` all call `EnsureRemaining(n, "state")` (`third_party/ijar/zip.cc:161-170`) before consuming `n` bytes, and abort with an error if the read would run past `input_file_->Length()`. [1](#0-0) 

`ProcessCentralDirEntry`, however, never calls `EnsureRemaining`. It reads signature, sizes, `file_name_length`, `extra_field_length`, `file_comment_length`, attributes and offset purely by advancing the pointer `p`: [2](#0-1) 

It then walks the "extra field" records using an unchecked loop keyed only on attacker-controlled `data_size`: [3](#0-2) 

The only bound placed on the whole central directory is a check that `central_dir_offset + central_dir_size <= in_length` inside `FindZipCentralDirectory()`: [4](#0-3) 

That check validates the *aggregate* size of the central directory as declared in the End-Of-Central-Directory record, but it does not validate that any individual entry's `file_name_length` / `extra_field_length` / `file_comment_length` / extra-field `data_size` values keep the per-field reads (`get_u2le`, `get_u4le`, `get_u8le`) inside the mapped file. A crafted entry can:
- declare `file_name_length`/`extra_field_length`/`file_comment_length` values that push `p` past the true end of the mapped file (or past the validated central-directory region into adjacent heap), and/or
- declare an extra-field `data_size` that never lands `extra_p` exactly on `p`, so the `while (extra_p != p)` loop (`zip.cc:526-542`) keeps calling `get_u2le`/`get_u8le` indefinitely past the buffer end.

`get_u2le`/`get_u4le`/`get_u8le` themselves (`third_party/ijar/common.h:43-72`) are raw pointer dereferences with no bounds awareness — they trust the caller to have validated remaining length, exactly as `EnsureRemaining` does elsewhere but is *not* invoked here. This mirrors the CVE-2017-6800 pattern: fixed-width integer fields (LONG/`u4`/`u8`) read from attacker-supplied binary data without a length check, producing a heap-based buffer over-read. [5](#0-4) 

### Impact Explanation
`ijar`'s zip reader is exercised whenever Bazel processes a jar as a zip archive — for example when the `ijar`/interface-jar tool or `singlejar`-adjacent tooling opens a `.jar`/`.zip` sourced from a `java_import`, `http_jar`, or fetched Maven dependency. An unprivileged attacker who publishes a malicious jar that a victim's build fetches (e.g., a dependency artifact) can craft a central directory entry with out-of-range length fields. When Bazel's build parses this jar with `InputZipFile::ProcessCentralDirEntry`, the process reads past the end of the mmap'd buffer, an out-of-bounds heap read. The pinned `sha256`/hash on the fetched archive only guarantees the outer bytes match what was recorded — it does nothing to prevent internal, self-consistent-looking but malformed zip metadata from causing an out-of-bounds read once those exact (hash-verified) bytes are parsed.

### Likelihood Explanation
Any dependency-fetch pathway that results in Bazel/ijar tooling opening an externally-supplied `.jar`/`.zip` will reach this code with default flags — no special configuration is required and no existing check in `ProcessCentralDirEntry` stops it (unlike `ProcessLocalFileEntry`, which is guarded by `EnsureRemaining`). The bug requires only a malformed but hash-matching archive, which is straightforward for the artifact's publisher to construct since they control the archive bytes and can compute whatever hash is later pinned.

### Recommendation
Add `EnsureRemaining`-style bounds checks in `InputZipFile::ProcessCentralDirEntry()` before each fixed-size read and before advancing over `file_name_length`, `extra_field_length`, and `file_comment_length`, mirroring the guards already present in `ProcessLocalFileEntry`/`SkipFile`/`ProcessFile`. Also bound the extra-field walking loop so that `extra_p + 4 <= p` (or the true buffer end) is checked before each `get_u2le`/`get_u8le`, and terminate with an error rather than looping past `p` if `data_size` does not land exactly on `p`.

### Proof of Concept
A JUnit/`src/test/shell/bazel` proof would construct a minimal ZIP whose EOCD declares a small, in-bounds `central_dir_size`, but whose single central-directory-header entry declares `file_name_length`/`extra_field_length`/`file_comment_length` values that, when summed with the fixed 46-byte CDH size, exceed the actual remaining bytes in the mapped file (or exceed the declared `central_dir_size` while `central_dir_offset + central_dir_size <= in_length` still holds because the surrounding EOCD/comment padding makes up the difference). Feeding this file into `InputZipFile::Open()` → `ProcessNext()` → `ProcessCentralDirEntry()` and running it under AddressSanitizer would demonstrate the heap-buffer-overflow-read when `get_u2le`/`get_u4le` dereference past the mapped file's end. I was not able to fully verify the exact minimal byte layout needed within this session — a background agent with build/test tooling access would be needed to construct and run this ASan-instrumented reproduction against `third_party/ijar/zip_test.cc` or a new equivalent test target.

inline u4 get_u4le(const u1 *&p) {
    u4 x = (p[3] << 24) | (p[2] << 16) | (p[1] << 8) | p[0];
    p += 4;
    return x;
}

inline u8 get_u8le(const u1 *&p) {
  u4 lo = get_u4le(p);
  u4 hi = get_u4le(p);
  u8 x = ((u8)hi << 32) | lo;
  return x;
}
