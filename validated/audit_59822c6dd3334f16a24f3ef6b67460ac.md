## Analysis

The Solana report's core broken invariant is: **a decimal/rate value is snapshotted once at setup, but a later state-changing operation trusts that stale snapshot instead of re-validating it against live, attacker-influenceable state**, letting the asset owner make the accounting layer use one decimals scale for pricing while the actual token no longer has that scale — draining value.

The exact analog exists in `pallet-psm` (`substrate/frame/psm/src/lib.rs`), a stablecoin peg-stability module added to this repo (see `prdoc/stable2606/pr_11819.prdoc`). It snapshots each external asset's `decimals` at approval time (`add_external_asset`) into `ExternalAssetInfo.decimals`, and snapshots `internal_decimals` in `PsmInfo` at PSM creation. Both are read from `pallet-assets`' mutable `Metadata` storage, whose `decimals` field is freely changeable at any time by the asset's `owner` via `set_metadata`/`Mutate::set` — a normal, unprivileged, permissionless action unrelated to PSM governance. [1](#0-0) [2](#0-1) 

`mint()` correctly re-verifies the snapshot against live decimals before every use, via `ensure_decimals_match`: [3](#0-2) [4](#0-3) 

However, `redeem()` never calls this check. It pulls `ext_decimals`/`internal_decimals` straight from the stale snapshot and feeds them into `internal_to_external` to compute the payout, with a doc comment explicitly acknowledging it intentionally ignores live drift ("Redemptions use the decimals snapshotted when the PSM/external pair was registered, allowing existing positions to unwind even if live metadata later changes"): [5](#0-4) [6](#0-5) 

Since raw balances in `pallet-assets` never rescale when `decimals` metadata changes, an asset owner can register a token as high-decimals (e.g. 18), let the PSM accumulate real reserve funded at that (correct) rate via `mint`, then call `set_metadata` to drop the asset's decimals (e.g. to 0), and finally call `redeem`, which will still apply the old 18-decimal scaling factor via `internal_to_external`, producing a wildly inflated `external_out` and draining far more of the reserve (`psm_account`) than is economically backed — an unbacked, theft-style payout.

### Title
Stale decimals snapshot lets external asset owner drain PSM reserve via `redeem` - (`substrate/frame/psm/src/lib.rs`)

### Summary
`pallet_psm::redeem` computes the external payout using the `ExternalAssetInfo.decimals` / `PsmInfo.internal_decimals` snapshot taken at `add_external_asset`/`create_psm` time, without re-validating it against the asset's current live decimals as `mint` does via `ensure_decimals_match`. An external asset's decimals metadata is mutable at will by its `owner` (a normal, unprivileged `pallet-assets` capability, not PSM governance). By changing decimals after building up reserve, the asset owner corrupts the scaling factor used only on the redeem path, causing the PSM to release far more external tokens than were actually deposited.

### Finding Description
`add_external_asset` snapshots `T::Fungibles::decimals(external_asset)` into `ExternalAssetInfo::decimals` and `PsmInfo::internal_decimals` at PSM creation [7](#0-6) . These values are used to scale amounts between the internal stablecoin and each external asset via `external_to_internal` / `internal_to_external` [8](#0-7) .

`mint()` guards against drift: before using the snapshot, it calls `Self::ensure_decimals_match`, which re-reads `T::Fungibles::decimals(...)` live and errors with `DecimalsMismatch` if it no longer matches the stored snapshot [9](#0-8) [10](#0-9) .

`redeem()` has no equivalent guard — it reads `external.decimals` and `info.internal_decimals` directly from storage and immediately uses them in `internal_to_external` to compute `external_out`, which is then transferred out of the PSM reserve account [11](#0-10) [12](#0-11) .

Because `pallet-assets` balances are raw integers independent of the `decimals` display field, and because `decimals` is mutable post-creation by the asset's `owner` via `set_metadata`/`force_set_metadata` [13](#0-12) , the owner of an approved external asset can:
1. Get the asset approved on a PSM instance with true decimals (e.g. 18), matching `MAX_DECIMALS_DIFF` bounds.
2. Use `mint()` (which enforces the live-vs-snapshot check, so this step is legitimate) to build real reserve backing at the correct 18-decimal rate.
3. Call `set_metadata` on their own asset to change its decimals (e.g. to 0). `mint`'s next call would now revert with `DecimalsMismatch`, but this doesn't undo the already-built reserve.
4. Call `redeem()`. It skips the live-decimals check entirely and reuses the stale 18-decimal exponent in `internal_to_external`, multiplying the payout by `10^12` more than the true 0-decimal scale warrants, releasing a hugely inflated amount of the external asset from the PSM reserve to the attacker.

This is the direct analog of the `ld2sd_rate` bug: a rate cached from mutable external metadata is trusted on the value-transferring path without re-validation, while a sibling path (here `mint`, there `InitOFT`'s initial check) enforces the very check that's missing elsewhere.

### Impact Explanation
This breaks the "conserve value and settle exactly once to the rightful beneficiary and amount" invariant for PSM. The attacker can drain the reserve account (`psm_account`, holding potentially many users' deposited stablecoin collateral) far beyond what they legitimately deposited, an unbacked/theft-style fund loss directly caused by an unprivileged, permissionless action (owning and reconfiguring one's own registered asset) — not requiring any admin, governance, validator, or relayer compromise.

### Likelihood Explanation
Likelihood is Low-to-Medium: it requires the attacker's asset to first be approved by the PSM's `full_admin` via `add_external_asset`. This approval step is a normal, expected part of onboarding external stablecoins and does not require the admin to act maliciously or negligently beyond approving what appears at approval-time to be a legitimately decimaled token; the exploit condition (decimals mutation happening strictly after approval and after reserve accumulation) is entirely under the asset owner's control and needs no special timing, front-running, or privileged coordination.

### Recommendation
Add the same `Self::ensure_decimals_match(&info, &internal_asset, &external_asset, &external)?` guard (or an equivalent live re-check) to `redeem()` before computing `external_out`, mirroring `mint()`. If intentionally allowing unwind of pre-existing positions at the old rate is desired, at minimum halt further `mint`s for that pair immediately on drift (which already happens) and cap/pause `redeem` too until governance resolves the mismatch, rather than silently paying out at a rate that no longer reflects the asset's real decimals.

### Proof of Concept
1. Attacker creates asset `X` via `pallet_assets::create` (permissionless), sets `decimals = 18` via `set_metadata`.
2. PSM admin approves `X` as an external for `internal_asset` via `add_external_asset`; `ExternalAssetInfo.decimals = 18` is snapshotted.
3. Attacker (or other users) calls `mint()` with a large `external_amount` of `X`, building real reserve of `X` in `psm_account`, computed correctly at 18 decimals; `PsmDebt` increases accordingly.
4. Attacker calls `pallet_assets::set_metadata(X, decimals = 0)` (they are the asset owner, no PSM permission required).
5. Attacker calls `redeem(internal_asset, X, internal_amount, max_fee)`. `redeem` reads the stale `ext_decimals = 18` from `ExternalAssetInfo` and computes `external_out = internal_to_external(internal_net, 18, internal_decimals)`, multiplying by `10^(18 - internal_decimals)` — vastly more than the true current 0-decimal value warrants — and transfers this inflated `external_out` of `X` out of `psm_account` to the attacker, exceeding what their `internal_amount` legitimately backs.

		///
		/// Scales by `10^(ext_decimals - internal_decimals)` — multiplies up when internal has more
		/// decimals, floor-divides when it has fewer. Returns [`Error::ConversionOverflow`] if
		/// the scaling factor or the product does not fit in the balance type.
		pub(crate) fn external_to_internal(
			amount: BalanceOf<T>,
			ext_decimals: u8,
			internal_decimals: u8,
		) -> Result<BalanceOf<T>, Error<T>> {
			use core::cmp::Ordering::*;
			match ext_decimals.cmp(&internal_decimals) {
				Equal => Ok(amount),
				Less => {
					let diff = (internal_decimals - ext_decimals) as u32;
					let factor = Self::pow10(diff)?;
					amount.checked_mul(&factor).ok_or(Error::<T>::ConversionOverflow)
				},
				Greater => {
					let diff = (ext_decimals - internal_decimals) as u32;
					let factor = Self::pow10(diff)?;
					Ok(amount.checked_div(&factor).unwrap_or_else(BalanceOf::<T>::zero))
				},
			}
		}
