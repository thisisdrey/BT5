### Title
Precision Loss in Old-Algorithm Vote Reward Calculation Due to Division Before Multiplication - (File: chainbase/src/main/java/org/tron/core/service/MortgageService.java)

### Summary
`MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)` computes a voter's share of a Super Representative's block reward using floating-point division before multiplication, exactly the anti-pattern flagged in the external report (`estimatedValue = a.mul(ONE.div(b))` instead of `a.mul(b).div(ONE)`).

### Finding Description
In the legacy ("old algorithm") reward path, the per-voter reward is computed as: [1](#0-0) 

```java
double voteRate = (double) userVote / totalVote;
reward += voteRate * totalReward;
```

This divides `userVote` by `totalVote` first (producing a `double` with limited mantissa precision), then multiplies by `totalReward`. This is mathematically equivalent to `userVote * totalReward / totalVote`, but by dividing first the fractional/precision information is truncated into a floating-point approximation before the multiplication, exactly the bug class described in the external Kairos report where `loan.lent.mul(ONE.div(loan.shareLent))` loses precision versus `loan.lent.mul(loan.shareLent).div(ONE)`.

This legacy path is reached from `computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule)`, which calls `getOldReward(...)` for any cycle prior to `newAlgorithmCycle`: [2](#0-1) 

That method, in turn, is invoked from `withdrawReward(byte[] address)` and `queryReward(byte[] address)`: [3](#0-2) [4](#0-3) 

`withdrawReward` is invoked by `WithdrawBalanceActuator.execute`, which is directly reachable by any unprivileged account broadcasting a `WithdrawBalanceContract` transaction. Note the new-algorithm path (post `newAlgorithmCycle`) already uses `BigInteger` multiply-then-divide (`deltaVi.multiply(BigInteger.valueOf(userVote)).divide(DECIMAL_OF_VI_REWARD)`), consistent with hardening done elsewhere in the codebase (e.g. `RewardViCalService`, `DelegationStore.accumulateWitnessVi`), which makes the old-algorithm double-based path in this same file stand out as an un-hardened remnant.

### Impact Explanation
Because `voteRate` is computed as a `double`, `userVote/totalVote` is rounded to ~15-17 significant decimal digits before multiplying by `totalReward`. For large vote counts and rewards, this can introduce rounding error in the computed reward per voter. Summed across many voters and many cycles, this systematic truncation can cause the total rewards paid out to diverge (be slightly less or, in specific rounding edge cases, more) than the mathematically exact `userVote * totalReward / totalVote`, i.e. an unbacked/incorrect balance credited via `adjustAllowance`. This is a fund-accounting correctness issue rather than a currently demonstrated large-scale drain, since double precision (52-bit mantissa) is fairly tight and TRX vote counts / rewards are bounded `long` values, but it remains a real deviation from exact integer arithmetic that the rest of the codebase has already moved away from via `BigInteger`-based hardening.

### Likelihood Explanation
Likelihood is high in terms of code being exercised: `withdrawReward`/`queryReward` for cycles prior to `newAlgorithmCycle` are on the reward-claim path reachable by any account via `WithdrawBalanceContract`. However, the magnitude of the precision loss per call is small (bounded by double's ~2^-52 relative error), so the practical monetary impact per transaction is likely negligible; the concern is about correctness/precision drift rather than an easily exploitable large fund theft.

### Recommendation
Replace the double-based computation in `computeReward(long cycle, List<Pair<byte[], Long>> votes)` with integer arithmetic that multiplies before dividing, consistent with the pattern already used in the new-algorithm branch, e.g.:
```java
long userVote = vote.getValue();
reward += BigInteger.valueOf(userVote)
    .multiply(BigInteger.valueOf(totalReward))
    .divide(BigInteger.valueOf(totalVote))
    .longValueExact();
```
This avoids the intermediate floating-point division and preserves exact integer precision until the final truncation, matching the mitigation recommended in the referenced report.

### Proof of Concept
Given `totalVote = 3`, `userVote = 1`, `totalReward = 10`:
- Current code: `voteRate = 1.0/3.0 = 0.3333333333333333` (double, truncated), `reward += 0.3333333333333333 * 10 = 3.333333333333333` → cast to `long` accumulation truncates to `3`.
- Exact integer order: `1 * 10 / 3 = 3` (same result here, but for larger/less-friendly numerators, e.g. `totalVote = 700000001`, `userVote = 233333333`, `totalReward = 999999999999L`, the double division `userVote/totalVote` loses bits relative to computing `userVote * totalReward` first in `BigInteger`, then dividing by `totalVote`), producing a value that differs from the exact integer computation by 1 or more units depending on the specific numbers — demonstrating the same order-of-operations precision defect as the reported `AuctionFacet.price` issue.   private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
