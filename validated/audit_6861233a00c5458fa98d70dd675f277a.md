### Title
Out-of-bounds read in `Zip64ExtraField::attr64()` due to unchecked attribute index when parsing malicious ZIP/JAR entries - ([File: src/tools/singlejar/zip_headers.h])

### Summary
`singlejar`'s `output_jar.cc`/`input_jar.cc` (used by `java_binary`/`java_library`/`android_binary` deploy-jar merging, and by ijar-like archive combination) reads JAR/ZIP entries and, when a 32-bit size/offset field equals `0xFFFFFFFF`, looks up the value in the Zip64 extra field via `Zip64ExtraField::attr64(index)`. The index passed to `attr64()` is computed purely from *which* of the 32-bit fields are flagged as needing extension (`zfield_has_ext64`), never validated against the actual number of 8-byte attributes the attacker-supplied extra field claims to carry (`attr_count()`).

### Finding Description
`Zip64ExtraField::attr64(int index)` does a raw indexed read into `attr_[]` with no bounds check against `attr_count()`: [1](#0-0) 

The `ExtraField::find()` helper only validates that the *extra field header itself* fits within the extra-fields buffer before returning it — it does not know how many attributes the caller intends to read afterward: [2](#0-1) 

Callers such as `CDH::compressed_file_size()`, `CDH::uncompressed_file_size()`, `CDH::local_header_offset()`, and the equivalent `LH` methods compute the attribute index from the 32-bit "needs-extension" flags of *other, independently attacker-controlled* fields, and pass that index straight into `attr64()` without first checking `zip64_ef->attr_count()`: [3](#0-2) [4](#0-3) 

Because a malicious/hostile JAR entry can set `compressed_file_size32`/`uncompressed_file_size32`/`local_header_offset32` to `0xFFFFFFFF` (triggering the "has extension" branch) while supplying a Zip64 extra field whose `payload_size` (hence `attr_count()`) is smaller than what the flag combination implies (e.g., only 1 stored attribute but the code asks for index `1` or `2`), `attr64()` reads 8 bytes past the end of the declared/allocated extra-field payload. This mirrors the qede pattern exactly: an index derived from one untrusted field is used to access an array/element before validating that the count field governing the array bounds actually supports that index.

There is a test that specifically constructs a "malformed extra field" with an oversized `payload_size` to probe overflow behavior in extra-field iteration, showing this is a recognized-risky area of the code, but it targets `ExtraField::find`'s bound check, not the `attr64()` indexing issue described here: [5](#0-4) 

### Impact Explanation
This code runs while `singlejar` combines/repackages JAR files supplied as build inputs (deploy jars, merged JARs, etc.). An out-of-bounds read of 8 bytes adjacent to a heap/mmap-backed buffer can leak adjacent memory content into computed size/offset values, potentially causing further out-of-bounds copies (`memcpy` sizing based on corrupted `compressed_file_size`/`uncompressed_file_size`) or a crash (denial of service via SIGSEGV) when processing a hostile input JAR (e.g., a dependency archive fetched from an untrusted mirror or produced by an untrusted build step whose output becomes another build's input).

### Likelihood Explanation
An attacker only needs to control the bytes of a `.jar`/`.zip` archive that is later processed by `singlejar` (any JAR consumed by a Bazel build, e.g., a fetched dependency or third-party artifact). No credentials, MITM, or write access to the victim's machine is required — the archive itself is the vector. The bounds-check gap is real and unconditional; it triggers whenever the 32-bit "needs Zip64" flags on the CDH/LH request an attribute index that exceeds the actual `attr_count()` of the attacker-supplied Zip64 extra field.

### Recommendation
In `Zip64ExtraField::attr64()`, or at each call site in `CDH`/`LH` (`compressed_file_size`, `uncompressed_file_size`, `local_header_offset`), validate `index < attr_count()` before dereferencing `attr_[index]`, and treat a failing check the same as `z64 == nullptr` (fail parsing / treat as malformed archive) rather than reading out of bounds.

### Proof of Concept
Construct a ZIP central directory entry (`CDH`) where:
- `compressed_file_size32 = 0xFFFFFFFF` and `uncompressed_file_size32 = 0xFFFFFFFF` (both flagged as needing Zip64 extension, requiring an `attr_count()` of at least 2),
- a Zip64 extra field (`tag = 1`) with `payload_size = 8` (i.e., `attr_count() == 1`, only one 8-byte attribute present),
so that `CDH::compressed_file_size()` computes `index = zfield_has_ext64(uncompressed_file_size32()) == true → index 1`, and calls `z64->attr64(1)`, reading 8 bytes beyond the single stored attribute — analogous to the existing `CreateZipWithMalformedExtraField()` test harness pattern already present in the test suite (`src/tools/singlejar/output_jar_simple_test.cc:1179-1225`), but exercising `attr64()` indexing rather than `ExtraField::find()`. This would need to be wrapped in a `TEST_F` that feeds the crafted bytes through `OutputJar::AddJar` and observes an ASAN heap-buffer-overflow (or crafted value in the resulting size) to confirm the OOB read.
