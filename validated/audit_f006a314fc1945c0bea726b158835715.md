### Title
`process_delivery_receipt` pays relayer rewards and closes `PendingOrder` regardless of the Ethereum-side execution outcome (`success` field is decoded but never checked) - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

### Summary
`snowbridge-pallet-outbound-queue-v2::process_delivery_receipt` decodes a `DeliveryReceipt` from an Ethereum-emitted `InboundMessageDispatched` event that explicitly carries a `success: bool` field reporting whether the corresponding outbound message actually executed successfully on the Ethereum Gateway contract. The pallet decodes this field but never inspects it before paying the relayer reward and removing the `PendingOrder`. This mirrors the `MagicLpAggregator` bug pattern: a return/decoded value that downstream logic is expected to rely on for correctness is silently discarded, causing the consumer to always treat the result as valid/successful.

### Finding Description
The Solidity event and Rust decode struct both carry the `success` flag: [1](#0-0) 

But `process_delivery_receipt` — the function that actually pays out the reward and settles the order — never reads `receipt.success`: [2](#0-1) 

The only checks performed are: `receipt.gateway` matches the configured `GatewayAddress`, and a `PendingOrder` exists for `receipt.nonce`. If `order.fee > 0`, the reward is unconditionally registered via `T::RewardPayment::register_reward`, and the `PendingOrder` is unconditionally removed — irrespective of whether the Ethereum-side dispatch actually succeeded (`success == false`) or failed.

`T::Verifier::verify` (the beacon/receipt proof check invoked in `submit_delivery_receipt`) only proves that the log was genuinely emitted by the Gateway contract in a finalized Ethereum block; it says nothing about the semantic value of the `success` field inside that log. So a real `InboundMessageDispatched(nonce, topic, success=false, reward_address)` event — emitted whenever the destination-side execution reverted on Ethereum — will decode fine, pass verification, and still fully reward the relayer and close the order, exactly as if the message had been delivered successfully.

This is the direct analog of the C4 report: `MagicLpAggregator.latestRoundData()` decodes/returns a value but drops fields (`updatedAt`, etc.) that integrators are supposed to rely on for correctness, silently breaking the invariant that the returned data reflects reality. Here, `DeliveryReceipt.success` is decoded but dropped before the reward/settlement logic runs, breaking the invariant that reward payout is contingent on delivery success.

### Impact Explanation
This allows relayer rewards to be paid, and `PendingOrder`s to be closed, for messages that failed execution on Ethereum. Fee reserves intended to reward *successful* delivery are drained on the basis of "false" positives, and the pallet's committed state (`PendingOrders`) is incorrectly finalized as delivered even when it was not. This is a fund-accounting / reward-payout correctness bug in a live-scope Snowbridge BridgeHub pallet (falls under "duplicate settlement or payout" / incorrect beneficiary-or-amount settlement in the impact gate).

### Likelihood Explanation
No privileged actor, malicious relayer, or malicious validator assumption is required. The `success=false` event is a legitimate output of the real Gateway contract whenever a destination-side call reverts (e.g., insufficient gas, reentrancy guard, downstream revert) — a routine, expected occurrence, not an attack. Any relayer (or anyone) who observes such an event and submits a standard, valid receipt proof triggers the erroneous unconditional payout/settlement path.

### Recommendation
In `process_delivery_receipt`, branch on `receipt.success`:
- If `true`, proceed with reward payment and remove the order as done today.
- If `false`, do not pay the reward (or apply a different/penalized path), and either retain the order for a future correct receipt, mark it as failed, or handle refund/retry logic explicitly, but do not treat a failed delivery the same as a successful one.

### Proof of Concept
1. Ethereum Gateway contract emits `InboundMessageDispatched(nonce=N, topic, success=false, reward_address=R)` because the destination-side XCM/command execution reverted.
2. Relayer builds a valid `EventProof` for this real log (receipt inclusion + beacon finality proof — all genuinely valid).
3. Relayer calls `submit_delivery_receipt(origin, event)`.
4. `T::Verifier::verify` succeeds (log is genuinely included and finalized).
5. `DeliveryReceipt::try_from` decodes `success: false` correctly.
6. `process_delivery_receipt` ignores `success`, finds `PendingOrders::get(N)`, sees `order.fee > 0`, calls `T::RewardPayment::register_reward` and removes the order, emitting `MessageDelivered { nonce: N }` — even though the message delivery failed on Ethereum.

This can be demonstrated by modifying the existing test `submit_delivery_receipt_succeeds_after_unhalt` (`bridges/snowbridge/pallets/outbound-queue-v2/src/test.rs`) to set `success: false` in the mock event log data and observing that `RewardPayment::register_reward` still fires and `PendingOrders` is still cleared.

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
	}
