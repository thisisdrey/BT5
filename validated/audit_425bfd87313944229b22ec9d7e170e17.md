### Title
Unchecked attacker-controlled array length in `extractBytesArray`/`extractSigArray` allows node crash via calldata to a TVM precompile - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`PrecompiledContracts.extractBytesArray()` and `extractSigArray()` read an array-length field (`len`) directly from user-supplied `DataWord[] words` — i.e. from smart-contract calldata passed by any transaction sender calling a TVM precompiled contract — and immediately use it to allocate `new byte[len][]`, without verifying that `len` is consistent with the actual amount of remaining calldata.

### Finding Description
```java
private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
  if (offset > words.length - 1) {
    return new byte[0][];
  }
  int len = words[offset].intValueSafe();
  byte[][] bytesArray = new byte[len][];
  ...
}
``` [3](#0-2) 

The only bound check is `offset > words.length - 1` (which is an off-by-one-style check on the *offset*, not the *length*). The `len` value itself, taken via `intValueSafe()` from a 256-bit word supplied entirely by the caller's calldata, is never checked against `words.length`, `data.length`, or any energy-charged upper bound before it is used both for array allocation (`new byte[len][]`) and for loop bounds indexing further into `words[offset + i + 1]`. The identical unchecked pattern exists in `extractSigArray` at lines 414-426. This is directly analogous to the reported Gearbox issue where `paths[i]` length was used without a bound check, leading to unsafe indexing/allocation from an untrusted length value.

### Impact Explanation
A crafted `len` (e.g., close to `Integer.MAX_VALUE`) passed as part of calldata to any TVM precompile that calls these helpers causes the JVM to attempt allocating an oversized `byte[len][]` object-reference array, which can trigger an `OutOfMemoryError`. Because energy/CPU metering for these precompiles is typically charged based on nominal input size rather than the requested internal array length, this allows a single crafted transaction to cause disproportionate memory pressure on the executing node relative to the fee paid, potentially destabilizing or crashing the node process handling the transaction — a node crash/halt qualifies under the accepted impact criteria.

### Likelihood Explanation
Reachable via an ordinary signed transaction that calls a smart contract invoking one of the affected precompiled contracts, requiring no special privileges (broadcaster/contract deployer level access only). The exact precompile(s) wiring into `extractBytesArray`/`extractSigArray` (e.g., signature-batch verification precompiles) were not fully confirmed from the indexed snippets available to me — I could not enumerate every call site within the remaining tool budget, so likelihood should be validated by tracing all callers of these two private methods before treating this as confirmed-exploitable in production.

### Recommendation
Bound-check `len` against the number of remaining `words` (and against a sane maximum) before allocating `bytesArray`/`bytesArray[i]`, e.g. `if (len < 0 || len > words.length - offset - 1) return new byte[0][];`, mirroring the fix recommended for the Gearbox `paths[i]` length check.

### Proof of Concept
Not independently executed; conceptual PoC: deploy a contract that calls the affected precompile address with calldata whose word at the length-`offset` position encodes a very large positive integer (e.g. `0x7fffffff`) while the rest of calldata is minimal/absent, triggering `new byte[len][]` allocation inside `extractBytesArray`/`extractSigArray` during precompile execution.

**Uncertainty note:** I was not able to trace, within the remaining tool budget, the exact precompiled-contract classes that invoke `extractBytesArray`/`extractSigArray` to fully confirm which externally-triggerable opcode/address exposes this path, nor whether an upstream energy check indirectly bounds `len`. This should be verified against the full call graph in `PrecompiledContracts.java` before treating the finding as fully confirmed.
