### Title
Unauthenticated `recv_error` handler allows a spoofing attacker to force tunnel teardown before a legitimate handshake/data-plane exchange completes - (File: outside.go)

### Summary
The `header.RecvError` message type is dispatched by `readOutsidePackets` before any decryption or certificate check is performed, directly to `Interface.handleRecvError`. `handleRecvError` tears down an existing tunnel (`f.closeTunnel(hostinfo)` and `f.handshakeManager.DeleteHostInfo(hostinfo)`) based solely on an unauthenticated `RemoteIndex` value taken from the plaintext packet header and a source-address comparison against the last known remote endpoint of that hostinfo. Neither field requires possession of a CA-signed certificate or a completed handshake to be produced by an attacker.

### Finding Description
`readOutsidePackets` routes `header.RecvError` packets straight to `f.handleRecvError(via.UdpAddr, h)` prior to any cert/handshake verification: [1](#0-0) 

`handleRecvError` looks up the hostinfo purely from `h.RemoteIndex` (a 32-bit value that is transmitted in cleartext on every packet header sent by the local node, and therefore observable by anyone able to see traffic on the wire, without needing a valid certificate) and only checks that the source UDP address matches the hostinfo's currently recorded remote address before calling `closeTunnel`: [2](#0-1) 

This mirrors the SGX report's bug class: a state-mutating function (here, tunnel teardown / hostinfo deletion) that is meant to be triggered only by the legitimate remote peer detecting a real decrypt failure, but is reachable and triggerable by any third party who can (a) observe/guess the `RemoteIndex` and (b) spoof the victim's UDP source address — both of which do not require possession of a CA-signed certificate. As in the report, front-running this state transition can prevent or disrupt legitimate protocol progress (here, an active data tunnel is torn down instead of a blocked block proof).

The "someone spoofing recv_errors?" check in the code acknowledges this exact class of attack but only rejects a spoofed packet if the observed source address differs from the currently recorded remote — it does nothing to prevent spoofing when the attacker can forge the source address to match (classic UDP source-address spoofing, independent of cert possession).

### Impact Explanation
A successful spoof causes `closeTunnel` and `DeleteHostInfo` to run on a live, correctly-authenticated tunnel between two legitimate peers, tearing down a connection that neither peer intended to close. Because `RemoteIndex` is sent in the clear on every packet, an on-path or off-path (spoofing) attacker who has observed any single packet exchanged between two nebula nodes can extract the necessary index and repeatedly force teardown of that tunnel, causing denial-of-service / repeated forced re-handshakes — directly analogous to the report's "prevent proving" DoS impact, but against the data-plane tunnel state rather than a rollup proof.

### Likelihood Explanation
Exploitability depends on the attacker's ability to spoof the legitimate peer's source UDP address, which is a standard, well-known network attack primitive (especially on networks without egress/ingress filtering) and does not require any cryptographic material, certificate, or completed handshake. The `RemoteIndex` itself is not secret — it appears in every packet header in cleartext. This keeps the precondition of the report's rule ("attacker with no CA-signed certificate") intact.

### Recommendation
Do not tear down tunnels based solely on an unauthenticated `RecvError` message and address match. Consider requiring some additional binding (e.g., only accept `RecvError` for a bounded time window immediately after sending a packet whose counter maps to a specific tracked outstanding send, or rate-limit/ignore this signal from addresses that haven't completed a handshake), or removing `closeTunnel`/`DeleteHostInfo` side effects entirely on `RecvError` and relying on the existing `connectionManager` liveness/rehandshake mechanisms instead.

### Proof of Concept
1. Observe (or otherwise learn) any packet flowing from host A to host B; extract the `RemoteIndex` field from the plaintext header — no decryption needed.
2. Craft a UDP packet with `header.RecvError` type and that `RemoteIndex`, spoofing the source address to match A's current remote endpoint as known to B (`hostinfo.GetRemote()`).
3. Send it to B. `readOutsidePackets` routes it directly into `handleRecvError` without cert or decryption checks, the address check passes because the source was spoofed, and B calls `closeTunnel` + `DeleteHostInfo`, tearing down the legitimate tunnel. [1](#0-0) [2](#0-1)

func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
