### Title
Remote peer can serve an oversized `GetAttachment` response that bypasses `attachments_max_size` and gets persisted unbounded - ([File: stackslib/src/net/atlas/download.rs])

### Summary
The Atlas attachment download path deserializes a peer-supplied `GetAttachmentResponse` and stores its `content` via `AtlasDB::insert_instantiated_attachment` without ever checking it against `AtlasConfig.attachments_max_size`, unlike the sibling `should_keep_attachment`/`insert_uninstantiated_attachment` path used for locally-submitted (`posttransaction`) attachments. A malicious peer answering a `GET /v2/attachments/<hash>` request can therefore return a multi-megabyte (or larger) blob that is accepted and written to the node's SQLite attachments table.

### Finding Description
The claimed invariant is `bytes_stored <= AtlasConfig.attachments_max_size` (default `ATTACHMENTS_MAX_SIZE_MIN = 1_048_576`, defined in `stackslib/src/net/atlas/mod.rs:52`). Tracing the remote-controlled path:

1. `RPCGetAttachmentRequestHandler::try_parse_response` (`stackslib/src/net/api/getattachment.rs:135-142`) just calls `parse_json` and wraps the JSON into `HttpResponsePayload` — no size check.
2. `StacksHttpResponse::decode_atlas_get_attachment` (`stackslib/src/net/api/getattachment.rs:159-165`) deserializes the JSON body into `GetAttachmentResponse` via its custom `Deserialize` impl (`stackslib/src/net/atlas/mod.rs:69-77`), which hex-decodes the string into `Attachment { content }` with **no length check whatsoever**.
3. `AttachmentsBatchStateContext::extend_with_attachments` (`stackslib/src/net/atlas/download.rs:530-559`) takes every successful response, calls `decode_atlas_get_attachment()`, and does `self.attachments.insert(response.attachment)` — again no size or hash-vs-request-content_hash check.
4. When the state machine reaches `Done`, `AttachmentsDownloader::run` (`stackslib/src/net/atlas/download.rs:153-165`) iterates `context.attachments.drain()` and calls `network.atlasdb.insert_instantiated_attachment(&attachment)` directly.
5. `AtlasDB::insert_instantiated_attachment` (`stackslib/src/net/atlas/db.rs:576-592`) performs an unconditional `INSERT OR REPLACE INTO attachments (...) VALUES (?, ?, 1, ?)` with the full `attachment.content` blob — no call to `should_keep_attachment` (which is the only place that checks `attachment.content.len() as u32 > self.atlas_config.attachments_max_size`, see `stackslib/src/net/atlas/db.rs:249-266`) and no size comparison of any kind.

By contrast, the only code path that does enforce `attachments_max_size` is `should_keep_attachment`, which is invoked from `posttransaction.rs` for attachments a client posts directly to this node's own RPC endpoint — not from the peer-download path. This confirms the equality is broken: a served attachment can have `content.len() > attachments_max_size` and still be accepted by `insert_instantiated_attachment`.

### Impact Explanation
A single crafted `GetAttachmentResponse` from any peer the node queries (an attacker can operate their own peer and simply be selected as an outbound sync peer, or answer inbound `/v2/attachments/<hash>` polling from other nodes) causes unbounded-size content to be written into the node's persistent Atlas SQLite database, growing storage without the configured cap. Because `insert_instantiated_attachment` uses `INSERT OR REPLACE`, this can be repeated per distinct/queued attachment instance, and each accepted attachment instance in the queue can trigger one such write, allowing storage growth well past the intended 1 MiB-per-attachment bound. This matches "unauthenticated/unauthorized write to state" — data is persisted to node state without any enforcement of the configured resource bound.

### Likelihood Explanation
- The attacker only needs to be selected as a legitimate outbound Atlas sync peer (`network.get_outbound_sync_peers()`) or respond to a `/v2/attachments/<hash>` GET issued by another node — no secret, no privileged role, no local access required.
- The attacker must have a pending/queued `AttachmentInstance` whose `content_hash` the victim node is trying to resolve (these instances come from on-chain BNS-related contract events), so the victim is already asking for *some* hash; the attacker's node simply must be asked for that hash and can return oversized content for it (the response is inserted keyed on the attacker-supplied hash bytes decoded from the response, without verifying that `Attachment::hash()` equals the originally-requested `content_hash` — this is a related gap but the length bypass alone is directly reachable and repeatable).
- Cost to the attacker is trivial: one crafted HTTP response per request received.

### Recommendation
Enforce `attachments_max_size` (and verify `Attachment::hash() == request.content_hash`) at the point attachments are decoded from peer responses — either in `StacksHttpResponse::decode_atlas_get_attachment` (`stackslib/src/net/atlas/mod.rs`/`getattachment.rs`) or in `AttachmentsBatchStateContext::extend_with_attachments` (`stackslib/src/net/atlas/download.rs:530-559`), rejecting/dropping any attachment whose `content.len() as u32 > atlas_config.attachments_max_size`. Additionally, `AtlasDB::insert_instantiated_attachment` (`stackslib/src/net/atlas/db.rs:576-592`) should itself call `should_keep_attachment`-style validation before performing the `INSERT OR REPLACE`, so the DB layer enforces the bound regardless of caller.

### Proof of Concept
Rust test plan (net test, analogous to `stackslib/src/net/api/tests/getattachment.rs`):
1. Build a `StacksHttpResponse` whose JSON body is `to_hex(&content)` for a `content: Vec<u8>` of length `2 * ATTACHMENTS_MAX_SIZE_MIN` (e.g., 2 MiB of `0xAA`), matching the `GetAttachmentResponse` wire format.
2. Feed the bytes through `RPCGetAttachmentRequestHandler::try_parse_response` (or directly call `response.decode_atlas_get_attachment()`), and assert it returns `Ok(GetAttachmentResponse { attachment })` with `attachment.content.len() > AtlasConfig::new(false).attachments_max_size as usize` — this assertion passing demonstrates the missing guard.
3. Extend the test to call `AttachmentsBatchStateContext::extend_with_attachments` with a synthetic `BatchedRequestsResult` containing this oversized response, then `network.atlasdb.insert_instantiated_attachment(&attachment)`, and query `find_attachment` back from `AtlasDB` — assert the stored `content.len()` exceeds `attachments_max_size`, confirming persistence of the oversized blob with no error and no truncation.
