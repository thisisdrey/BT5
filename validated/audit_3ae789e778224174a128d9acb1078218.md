Audit Report

## Title
Missing enforcement of `MaxMessageSize`/payload-size cap in `snowbridge_pallet_inbound_queue::submit` and `snowbridge-pallet-inbound-queue-v2::submit`, allowing unbounded Ethereum-controlled payloads to be decoded and forwarded as XCM - (`bridges/snowbridge/pallets/inbound-queue/src/lib.rs`, `bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs`, `bridges/snowbridge/primitives/inbound-queue/src/v2/converter.rs`)

## Summary
`Pallet::submit` in both the v1 and v2 inbound-queue pallets decodes an Ethereum-supplied `EventProof.event_log.data` (an unbounded `Vec<u8>`) into a message and forwards it as `Xcm<()>` to AssetHub without ever checking its length against `Config::MaxMessageSize`, unlike the outbound-queue pallets which explicitly `ensure!(payload.len() < T::MaxMessagePayloadSize::get(), SendError::MessageTooLarge)` before enqueueing. This allows a permissionless relayer with a valid Ethereum event proof to push oversized/instruction-heavy XCM programs into the bridge pipeline at a fixed, non-scaling extrinsic weight cost.

## Finding Description
In `bridges/snowbridge/pallets/inbound-queue/src/lib.rs:237-311`, `submit()` verifies the event log/proof, decodes `envelope.payload` via `VersionedMessage::decode_all` (line 284) with no length check, converts it to XCM via `Self::do_convert` (line 288), and forwards it via `Self::send_xcm` (line 301). `Config::MaxMessageSize` (lines 138-139) is explicitly documented as "only used to estimate delivery cost" and is consumed solely by `calculate_delivery_cost`/the `Get<BalanceOf<T>>` impl (lines 343-384) for fee estimation — never as a guard inside `submit()`.

The same pattern holds in `bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs:185-198`: `submit()` verifies, decodes `event.event_log` into a `Message` (line 195), and calls `process_message` (lines 214-245), with no size check on `event.event_log`/decoded `Message` anywhere in the file. The underlying `Log` type (`bridges/snowbridge/primitives/verification/src/lib.rs:47-53`) contains an unbounded `data: Vec<u8>`.

In `bridges/snowbridge/primitives/inbound-queue/src/v2/converter.rs:327-342` and `375-426`, `message.remote_xcm` is decoded only with a decode-depth limit (`MAX_XCM_DECODE_DEPTH`) and then appended verbatim to the outbound instruction list (`instructions.extend(message.remote_xcm.0)`), with no bound on total size or instruction count.

By contrast, `bridges/snowbridge/pallets/outbound-queue/src/send_message_impl.rs:41-49` enforces `ensure!(payload.len() < T::MaxMessagePayloadSize::get(), SendError::MessageTooLarge)` before a message is allowed into the outbound pipeline — a guard structurally absent from both inbound pallets.

## Impact Explanation
This matches the "public underpriced work that degrades block production or stalls bridge processing" and "permanent user-fund or bridge-state lock" impact categories: a relayer can force full decode → XCM conversion → `send_xcm` processing of an oversized payload at a cost fixed to `T::WeightInfo::submit()`'s benchmark weight rather than one scaled to the actual payload processed. If the resulting XCM fails HRMP/XCMP page-size or weight limits, `validate_send`/`send_xcm` errors out, reverting the whole `submit` dispatch (including the already-executed relayer-fee transfer, since FRAME dispatch is transactional on error). If it instead succeeds in being queued but cannot be executed on AssetHub, assets referenced in the XCM (reserve/teleport instructions) can be trapped rather than delivered to the intended beneficiary. `pallet-message-queue`'s handling of `Overweight`/`Unprocessable` messages (`substrate/frame/message-queue/src/lib.rs:1589-1613`) prevents full channel deadlock, which correctly limits — but does not eliminate — the severity.

## Likelihood Explanation
Exploitation requires only a permissionless relayer submitting a legitimately-proven Ethereum event log for a message emitted from the configured Gateway address; no privileged actor, validator, or leaked key is needed. Whether the Ethereum-side Gateway contract itself constrains payload size is off-repo and cannot be confirmed here, but the Substrate-side code provides no defense-in-depth regardless of that external assumption.

## Recommendation
Add an explicit length check in `submit()` for both inbound-queue and inbound-queue-v2 pallets — e.g. `ensure!(envelope.payload.len() <= T::MaxMessageSize::get() as usize, Error::<T>::InvalidPayload)` (v1) and an analogous check on `event.event_log.data`/decoded `Message` (v2) — before decode/conversion, mirroring the outbound-queue guard. Additionally, bound the size/instruction count of `remote_xcm` in `converter.rs` independent of decode depth, and make `T::WeightInfo::submit()` scale with actual payload size rather than using a fixed benchmark constant.

## Proof of Concept
Not independently reproducible purely within this repository since triggering requires an Ethereum-side event emission with an oversized payload plus a valid consensus/receipt proof. The missing guard is directly demonstrable by reading `submit()` end-to-end in both `bridges/snowbridge/pallets/inbound-queue/src/lib.rs:237-311` and `bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs:185-245`, confirming no code path calls `T::MaxMessageSize::get()` other than the fee-estimation helper, and comparing this to the explicit size guard in `bridges/snowbridge/pallets/outbound-queue/src/send_message_impl.rs:41-49`. 	/// Parse and (non-strictly) decode `raw` XCM bytes into a `Xcm<()>`.
	/// If decoding fails, return an empty `Xcm<()>`—thus allowing the message
	/// to proceed so assets can still be trapped on AH rather than the funds being locked on
	/// Ethereum but not accessible on AH.
	fn decode_raw_xcm(raw: &[u8]) -> Xcm<()> {
		let mut data = raw;
		if let Ok(versioned_xcm) =
			VersionedXcm::<()>::decode_with_depth_limit(MAX_XCM_DECODE_DEPTH, &mut data)
		{
			if let Ok(decoded_xcm) = versioned_xcm.try_into() {
				return decoded_xcm;
			}
		}
		// Decoding failed; allow an empty XCM so the message won't fail entirely.
		Xcm::new()
	}
