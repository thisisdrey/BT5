### Title
Permanent reward loss via integer-division rounding in `reward_per_token` — attacker-inflatable stake can zero out reward accrual - (File: `substrate/frame/asset-rewards/src/lib.rs`)

### Summary
`pallet-asset-rewards` computes the pool's global `reward_per_token` increment using integer division that rounds toward zero, exactly like the reported `MultiRewards.notifyRewardAmount` bug where `reward.div(rewardsDuration)` can round the `rewardRate` to zero. Here the divisor is `total_tokens_staked`, which is fully attacker-controlled via the permissionless `stake` extrinsic and has no minimum-ratio validation against `reward_rate_per_block`, so any funded user can force the reward accrual to permanently round to zero for the whole pool.

### Finding Description
`reward_per_token` computes the per-period reward increment as: [1](#0-0) 

```rust
Ok(pool_info.reward_per_token_stored.ensure_add(
    pool_info
        .reward_rate_per_block
        .ensure_mul(rewardable_blocks_elapsed.into())?
        .ensure_mul(PRECISION_SCALING_FACTOR.into())?
        .ensure_div(pool_info.total_tokens_staked)?,
)?)
```

`PRECISION_SCALING_FACTOR` is a fixed constant of only `4096` [2](#0-1)  — far smaller than the `1e18`-style scaling normally used to guard against this exact rounding class. This is Euclidean/integer division: if `reward_rate_per_block * rewardable_blocks_elapsed * 4096 < total_tokens_staked`, the increment rounds down to `0`, exactly mirroring the external report's `reward.div(rewardsDuration)` rounding-to-zero scenario, just with `total_tokens_staked` playing the role of the "high duration" denominator.

Critically, once `update_pool_rewards` is called, `last_update_block` advances unconditionally regardless of whether any reward was actually accrued [3](#0-2) . There is no accumulated remainder carried forward — any reward that rounds to zero for a given update window is lost forever, not merely deferred, just like the GUSD example in the report where the entire distribution was permanently locked.

The denominator `total_tokens_staked` is fully attacker-controllable: `stake` is a permissionless, unprivileged call with no minimum or maximum bound on `amount`, and no validation exists anywhere (in `create_pool`, `stake`, or `set_pool_reward_rate_per_block`) enforcing a minimum `reward_rate_per_block`-to-`total_tokens_staked` ratio: [4](#0-3) 

An attacker who stakes a sufficiently large amount of the pool's `staked_asset_id` (any asset the attacker holds/controls enough of, since arbitrary `fungibles::Inspect`/`Mutate` assets can have arbitrarily large balances) can force `reward_per_token` to permanently compute `0` for every subsequent block window, freezing reward accrual for themselves and all other legitimate stakers in the pool, while the pool's already-deposited reward tokens sit stranded, unclaimable except back to the admin via `cleanup_pool` once all stakers have exited.

### Impact Explanation
This breaks the intended invariant that staking rewards deposited into a pool are conserved and eventually settle to legitimate stakers. An unprivileged, single-transaction action (calling `stake` with a large amount) can permanently zero out reward distribution for an entire pool, causing a **permanent user-fund lock** of the reward asset for legitimate stakers — directly matching the "permanent user-fund lock" impact category. It also degrades the intended incentive mechanism (denial of reward payout) without requiring any admin, governance, validator, or malicious-peer assumption — only ordinary asset ownership by a normal account.

### Likelihood Explanation
Likelihood is high: `stake` is a public, unprivileged extrinsic [5](#0-4)  with no minimum/maximum amount checks, and `PRECISION_SCALING_FACTOR` is a small fixed constant (`4096`) rather than a large fixed-point scale, making the rounding-to-zero condition (`reward_rate_per_block * blocks_elapsed * 4096 < total_tokens_staked`) easy to trigger for any pool whose staked asset has enough available supply relative to its configured reward rate. No existing guard (in `create_pool`, `stake`, or the `RewardsPool` trait impls) enforces a minimum ratio to prevent this, unlike the mitigation the external report explicitly recommends.

### Recommendation
Enforce a minimum multiple between `reward_rate_per_block * PRECISION_SCALING_FACTOR` and any plausible `total_tokens_staked`, e.g., by increasing `PRECISION_SCALING_FACTOR` to a much larger fixed-point scale (analogous to `1e18`) and/or bounding the maximum stakeable amount per pool, and/or accumulating unrounded remainders (fixed-point accounting) instead of discarding them each update, so no distribution period can silently round to zero.

### Proof of Concept
1. Admin creates a pool via `create_pool` with `reward_rate_per_block = R` and asset `staked_asset_id = X` [6](#0-5) .
2. Attacker (any signed account holding a large balance of `X`) calls `stake(pool_id, amount)` with `amount` chosen such that `R * 4096 < amount` (feasible since `PRECISION_SCALING_FACTOR` is fixed at `4096` and `amount` is unbounded) [7](#0-6) .
3. On every subsequent call to `reward_per_token` (triggered by any `stake`/`unstake`/`harvest_rewards`), the term `reward_rate_per_block * blocks_elapsed * 4096 / total_tokens_staked` evaluates to `0` due to integer division, so `reward_per_token_stored` never increases [8](#0-7) .
4. Legitimate stakers who staked before or after the attacker accrue zero rewards despite the pool holding deposited reward tokens; funds remain locked until the pool is fully drained of stakers and cleaned up by the admin.

		pub fn stake(origin: OriginFor<T>, pool_id: PoolId, amount: T::Balance) -> DispatchResult {
			let staker = ensure_signed(origin)?;

			// Always start by updating staker and pool rewards.
			let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
			let staker_info = PoolStakers::<T>::get(pool_id, &staker).unwrap_or_default();
			let (mut pool_info, mut staker_info) =
				Self::update_pool_and_staker_rewards(&pool_info, &staker_info)?;

			T::AssetsFreezer::increase_frozen(
				pool_info.staked_asset_id.clone(),
				&FreezeReason::Staked.into(),
				&staker,
				amount,
			)?;

			// Update Pools.
			pool_info.total_tokens_staked.ensure_add_assign(amount)?;

			Pools::<T>::insert(pool_id, pool_info);

			// Update PoolStakers.
			staker_info.amount.ensure_add_assign(amount)?;
			PoolStakers::<T>::insert(pool_id, &staker, staker_info);

			// Emit event.
			Self::deposit_event(Event::Staked { staker, pool_id, amount });

			Ok(())
		}

	fn create_pool(
		creator: &T::AccountId,
		staked_asset_id: T::AssetId,
		reward_asset_id: T::AssetId,
		reward_rate_per_block: T::Balance,
		expiry: DispatchTime<BlockNumberFor<T>>,
		admin: &T::AccountId,
	) -> Result<PoolId, DispatchError> {
		// Ensure the assets exist.
		ensure!(T::Assets::asset_exists(staked_asset_id.clone()), Error::<T>::NonExistentAsset);
		ensure!(T::Assets::asset_exists(reward_asset_id.clone()), Error::<T>::NonExistentAsset);

		// Check the expiry block.
		let now = T::BlockNumberProvider::current_block_number();
		let expiry_block = expiry.evaluate(now);
		ensure!(expiry_block > now, Error::<T>::ExpiryBlockMustBeInTheFuture);

		let pool_id = NextPoolId::<T>::try_mutate(|id| -> Result<PoolId, DispatchError> {
			let current_id = *id;
			*id = id.ensure_add(1)?;
			Ok(current_id)
		})?;

		let footprint = Self::pool_creation_footprint();
		let cost = T::Consideration::new(creator, footprint)?;
		PoolCost::<T>::insert(pool_id, (creator.clone(), cost));

		// Create the pool.
		let pool = PoolInfoFor::<T> {
			staked_asset_id: staked_asset_id.clone(),
			reward_asset_id: reward_asset_id.clone(),
			reward_rate_per_block,
			total_tokens_staked: 0u32.into(),
			reward_per_token_stored: 0u32.into(),
			last_update_block: 0u32.into(),
			expiry_block,
			admin: admin.clone(),
			account: Self::pool_account_id(&pool_id),
		};

		// Insert it into storage.
		Pools::<T>::insert(pool_id, pool);

		// Emit created event.
		Self::deposit_event(Event::PoolCreated {
			creator: creator.clone(),
			pool_id,
			staked_asset_id,
			reward_asset_id,
			reward_rate_per_block,
			expiry_block,
			admin: admin.clone(),
		});

		Ok(pool_id)
	}
