### Title
Maliciously crafted dust deposits permanently fill a victim's per-account token list and DoS all further deposits/transfers - (File: contracts/Pool.sol)

### Summary
`DepositToken.deposit()` accepts an arbitrary `onBehalfOf_` beneficiary and mints deposit tokens to that address. Each first-time mint for a new deposit token pushes the token into `Pool.depositTokensOfAccount[account]`, which is capped by `MAX_TOKENS_PER_USER`. An unprivileged attacker can, via a single `Operator.execute` batch, deposit 1-wei dust of every deposit token into a victim's account, filling the list. From then on, any mint of a deposit token that is not already in the victim's list reverts in `addToDepositTokensOfAccount` with `UserReachedMaxTokens` — blocking the victim's deposits and inbound `msdTOKEN` transfers for all other collateral types.

### Finding Description
`Pool.addToDepositTokensOfAccount` enforces the per-account cap:

- `contracts/Pool.sol:143-148` — `onlyIfAdditionWillNotReachMaxTokens` reverts with `UserReachedMaxTokens` once `debtTokensOfAccount.length + depositTokensOfAccount.length >= MAX_TOKENS_PER_USER`.
- `contracts/Pool.sol:216-220` — `addToDepositTokensOfAccount` adds the token under that cap.
- `contracts/DepositToken.sol:211-236` — `deposit(amount_, onBehalfOf_)` mints to any `onBehalfOf_ != address(0)`; the internal `_mint` hook registers the token on the beneficiary, not on the payer.

So `deposit(1, victim)` executed once per deposit token (batchable in one tx through `Operator.execute`, `contracts/Operator.sol:34-55`) inflates the victim's list at the cost of a few wei of underlying per token. The analogous "maliciously crafted packet causes an illegal modification that crashes the target" is a crafted batch that silently mutates victim-side accounting state, after which all subsequent legitimate operations touching the list revert.

The same applies to inbound `transfer`/`transferFrom` of `msdTOKEN` and to `seize` proceeds during liquidation routed to a fresh receiver, since all mint/transfer paths register the token on the recipient.

### Impact Explanation
- A victim holding collateral types not yet in their list cannot deposit them at all: `deposit` reverts, so their assets are effectively locked out of the protocol (temporary freezing of funds / liveness failure on deposits).
- A victim cannot receive `msdTOKEN` transfers in any not-yet-listed token; `transfer`/`transferFrom` revert on the `add` step, freezing secondary-market settlement to that account.
- Recovery requires the victim to detect the attack and `withdraw` each dust balance to remove entries, which costs one transaction per injected token and is only possible if their position has no outstanding debt locking the dust (`_revertIfLocked`, `contracts/DepositToken.sol:180-182`). With outstanding debt, `unlockedBalanceOf` may be 0 and the dust cannot be removed until the debt position changes — extending the freeze.

### Likelihood Explanation
- Fully unprivileged: only needs dust amounts of each listed underlying plus gas for ≤ `MAX_TOKENS_PER_USER` calls, compressible into one `Operator.execute` transaction.
- No privileged role, oracle manipulation, or victim interaction required; `onBehalfOf_` is unconstrained except non-zero (`DepositToken.sol:216`).
- No existing guard stops it: `whenNotPaused`, `nonReentrant`, and `onlyIfDepositTokenExists` are all satisfied for legitimate registered tokens.

### Recommendation
- Do not register tokens for `onBehalfOf_` deposits below a meaningful threshold, or require the beneficiary to "opt in" (e.g., only register on self-deposits / explicit `addDepositToken` call by the account).
- Alternatively, make mint-to-recipient paths skip list registration for `to_ != msgSender` and let recipients register lazily on their first state-changing action, or allow removing/ignoring zero-impact entries.

### Proof of Concept
Hardhat (fork or unit fixture with N registered deposit tokens `msdX[i]`, underlying `underlying[i]`):

```ts
it('DoS: dust deposits fill victim token list', async function () {
  // attacker acquires dust of each underlying
  for (let i = 0; i < tokens.length; i++) {
    await underlying[i].connect(attacker).approve(msdX[i].address, 1)
  }

  // one crafted "packet": batch of dust deposits on behalf of the victim
  const calls = msdX.map(dt => ({
    target: dt.address,
    value: 0,
    callData: dt.interface.encodeFunctionData('deposit', [1, victim.address]),
  }))
  await operator.connect(attacker).execute(calls)

  // victim's list is now at MAX_TOKENS_PER_USER
  expect(await pool.depositTokensOfAccountLength(victim.address)).to.eq(MAX)

  // victim cannot deposit a collateral type not already in their list
  const newToken = msdNew // freshly added deposit token, e.g. msdWBTC
  await wbtc.connect(victim).approve(newToken.address, parseUnits('1', 8))
  await expect(
    newToken.connect(victim).deposit(parseUnits('1', 8), victim.address)
  ).revertedWithCustomError(pool, 'UserReachedMaxTokens')

  // nor receive a transfer of any not-yet-listed msdTOKEN
  await expect(
    msdX_new.connect(holder).transfer(victim.address, 1)
  ).revertedWithCustomError(pool, 'UserReachedMaxTokens')
})
```

The broken invariant is liveness: a crafted input batch performs an unauthorized, irreversible-by-sender modification of the victim's registry state, after which all legitimate deposits/transfers-in for unregistered tokens deterministically revert.
