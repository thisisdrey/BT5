## Analog Found

### Title
Check-then-act race in the anti-replay window lets a duplicated packet bypass replay protection - (File: `connection_state.go`)

### Summary
The external report describes a classic re-entrancy pattern in `EntangleTestBridge.withdraw`: the contract performs an external call (token transfer / callback) before committing its internal balance state, letting an attacker re-enter and drain funds using stale state. The reachable analog in Nebula is structurally the same "check state → perform external/expensive operation → commit state" ordering, but in `ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` in `connection_state.go`. The replay-window check (`window.Check`) is released before the costly external operation (AEAD `DecryptDanger`), and the window is only updated (`window.Update`) afterward, under a freshly-reacquired lock. Two concurrent invocations for the same counter can both pass `Check` before either commits via `Update`, defeating the anti-replay window.

### Finding Description
`Decrypt` and `VerifyRelay` both follow this pattern: [1](#0-0) 

1. Lock, call `cs.window.Check(l, messageCounter)`, unlock.
2. If allowed, perform `cs.dKey.DecryptDanger(...)` — an expensive, lock-free cryptographic operation.
3. Lock again, call `cs.window.Update(l, messageCounter)` to commit the counter as seen, unlock.

Between steps 1 and 3 the mutex is released, so the "commit" of state (marking the counter seen) is not atomic with the "check". `Interface.run` starts multiple reader goroutines (`f.routines`), each independently calling `readOutsidePackets` → `hostinfo.ConnectionState.Decrypt`/`VerifyRelay` for packets arriving on the shared `ConnectionState`: [2](#0-1) [3](#0-2) 

If the same encrypted packet (or a captured/duplicated copy of it) is delivered twice in close succession — e.g., via network-level duplication, or an on-path/attacker-controlled relay re-injecting a copy before the first copy's `Update` call lands — both calls can observe `window.Check` returning `true` (not yet marked) prior to either call reaching `window.Update`. Both decryptions succeed and both are handed to `handleOutsideMessagePacket`/`handleOutsideRelayPacket`, i.e., the packet is processed twice despite `Bits`, the sliding-window anti-replay tracker, being designed to reject duplicates: [4](#0-3) 

The commit history shows the project is actively hardening exactly this replay-window commit ordering elsewhere (e.g., "Lock replay window updates so concurrent readers can't corrupt it" and "Advance the replay window on relayed packets so a relay drops replayed frames instead of re-forwarding them"), confirming this class of check/update-ordering bug is a recognized real risk area in this codebase: [5](#0-4) 

### Impact Explanation
This is a remote-state-poisoning / replay-bypass issue reachable by any peer that can deliver (or cause duplicate delivery of) a valid encrypted packet — no CA-signed certificate is required beyond an already-established tunnel, and the race can be triggered purely by packet duplication at the network layer or a malicious relay re-forwarding a captured frame quickly. Successful exploitation causes a data-plane packet to be delivered twice to the tun device (or relay-forwarded twice), defeating the anti-replay guarantee `Bits`/`ConnectionState` is meant to provide.

### Likelihood Explanation
Exploitability depends on winning a narrow race window (the gap between `Check` and `Update` while the lock is released) and requires the ability to deliver a duplicate of a legitimate encrypted frame quickly (e.g., normal network duplication, or a relay/attacker able to inject a copy). This is achievable but timing-sensitive, so likelihood is moderate rather than trivial — comparable to the "AC:L" (low complexity, needs precise conditions) rating used in the original BVSS score for the analogous smart-contract bug.

### Recommendation
Make the check-and-commit atomic with respect to the decrypt operation for a given counter: either hold `decryptLock` across the entire Check→Decrypt→Update sequence for a given `ConnectionState`, or use an atomic "reserve" step (mark the counter as tentatively consumed under lock before decrypting, and only roll back on decrypt failure) so no two goroutines can pass `Check` for the same counter before one of them commits via `Update`. This mirrors the report's underlying recommendation of updating internal state before/atomically with the external operation, rather than after it.

### Proof of Concept
1. Establish two encrypted UDP payloads that are byte-identical duplicates of the same legitimate data-plane packet (e.g., by capturing and replaying a frame, or by a relay path re-forwarding it), both carrying the same `MessageCounter`.
2. Deliver both copies to the target's UDP listener at effectively the same time when `f.routines > 1` (multi-queue), so they are picked up by two different reader goroutines that both call `hostinfo.ConnectionState.Decrypt` concurrently.
3. Both goroutines call `window.Check` and observe the counter as not-yet-seen because neither has reached `window.Update` yet.
4. Both goroutines successfully `DecryptDanger` and proceed to hand the plaintext to `handleOutsideMessagePacket`, resulting in double processing/delivery of the same message despite the replay window.

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}
