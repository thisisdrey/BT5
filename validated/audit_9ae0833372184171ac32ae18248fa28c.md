### Title
Unbounded array allocation from attacker-controlled length field in `ValidateMultiSign` precompile causes OOM/DoS - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` precompiled contract's legacy signature-extraction path allocates a `byte[][]` array whose size is taken directly from an attacker-supplied 32-byte word in the call data, before any bound is enforced. This mirrors the FFmpeg `asf_build_simple_index` bug class: a "count" field taken from untrusted input is used to drive allocation/iteration with no check that it is consistent with, or bounded relative to, the actual size of the backing data, and with no bound check performed before the resource is consumed.

### Finding Description
`ValidateMultiSign.execute()` chooses between two extraction helpers depending on the `ALLOW_TVM_SELFDESTRUCT_RESTRICTION` hard-fork flag: [1](#0-0) 

When `VMConfig.allowTvmSelfdestructRestriction()` is `false` (the default value stored in `DynamicPropertiesStore.getAllowTvmSelfdestructRestriction()` is `0` unless a network proposal has explicitly activated it): [2](#0-1) 

`extractBytesArray()` is invoked directly with **no prior `MAX_SIZE` check** — the `sigArraySize > MAX_SIZE` guard is only executed inside the `if (VMConfig.allowTvmSelfdestructRestriction())` branch: [3](#0-2) 

Inside `extractBytesArray`, `len` is read straight from calldata via `words[offset].intValueSafe()` and used to allocate `new byte[len][]` and drive a loop, before any relationship between `len` and the actual `data` array size is validated: [4](#0-3) 

Because a `DataWord`/32-byte word can encode any value up to `2^256-1`, and `intValueSafe()` only needs to yield a large positive `int` (e.g. close to `Integer.MAX_VALUE`), the caller can set the "declared length" word to a huge value while the actual `rawData` calldata blob passed to the contract can remain small (i.e. the "backing data" is insufficient for the declared count — exactly the CVE-2017-14223 pattern). The only downstream bound check (`signatures.length == 0 || signatures.length > MAX_SIZE`) happens **after** `extractBytesArray` has already returned/allocated, i.e. after the damage is done: [5](#0-4) 

The energy cost charged for this call is derived only from `data.length / WORD_SIZE`, not from the declared array size `len`, so the attacker pays energy proportional to a small calldata blob while the JVM must service an allocation/loop sized by the crafted `len` value: [6](#0-5) 

### Impact Explanation
A single crafted contract call (constant or non-constant, reachable by any unprivileged transaction/contract caller through the TVM's `ValidateMultiSign` precompile) can trigger allocation of a huge `byte[len][]` reference array (e.g. `len` near `Integer.MAX_VALUE`), which will throw `OutOfMemoryError` inside the node JVM. This is caught only partially — the surrounding `try { ... } catch (Throwable t) { if (t instanceof OutOfTimeException) throw t; ... }` block catches `OutOfMemoryError` as a `Throwable` and logs it, but the transient massive allocation itself (and associated GC churn immediately before the exception is thrown) can degrade or crash the node process under repeated invocation, denying service to the validator/node. This satisfies the "node crash or halt" / API-can-no-longer-serve impact bar.

### Likelihood Explanation
High for any node where `ALLOW_TVM_SELFDESTRUCT_RESTRICTION` has not been activated (default state is `0`/inactive unless a chain-wide proposal has passed). This is directly reachable by any account that can deploy or call a contract invoking the `ValidateMultiSign` precompiled address — no special privilege, staking, or witness role is required, matching the "unprivileged contract deployer/caller" reachability requirement.

### Recommendation
Enforce the `MAX_SIZE` bound check on the declared signature-array length **before** calling `extractBytesArray`, unconditionally (not gated behind `allowTvmSelfdestructRestriction`), and additionally validate inside `extractBytesArray`/`extractSigArray` that the declared `len` is consistent with the actual size of `data` before allocating any array, mirroring the approach already used for the newer `extractSigArray`/`isValidAbiEncoding` path.

### Proof of Concept
1. Deploy/call a contract that invokes the `ValidateMultiSign` precompile with calldata laid out as:
   - word[0]: target address
   - word[1]: permissionId
   - word[2]: `data` field
   - word[3]: offset pointer to signature-array header
   - at the pointed-to offset: a length word set to a large value close to `Integer.MAX_VALUE` (crafted so `words[offset].intValueSafe()` returns that large positive int)
   - the remainder of calldata kept minimal (small `data.length`), so the energy charged (`(data.length / WORD_SIZE - 5) / 5 * 1500`) remains low.
2. On a node where `ALLOW_TVM_SELFDESTRUCT_RESTRICTION` has not been activated (`getAllowTvmSelfdestructRestriction() == 0`, the default), `ValidateMultiSign.execute()` takes the `extractBytesArray` branch without the `sigArraySize > MAX_SIZE` guard.
3. `extractBytesArray` executes `new byte[len][]` with the attacker-chosen huge `len`, causing a huge memory allocation attempt / `OutOfMemoryError` inside the executing node's JVM for a call that cost only minimal energy.

Note: I was not able to fully verify the exact numeric semantics/clamping of `DataWord.intValueSafe()` (e.g., whether it clamps to `Integer.MAX_VALUE` or throws on very large `BigInteger` values) due to iteration limits — this should be confirmed by inspecting `common/src/main/java/org/tron/common/runtime/vm/DataWord.java` in a follow-up session, as it affects the exact maximum achievable `len` value for the PoC.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
