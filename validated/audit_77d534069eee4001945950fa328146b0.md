Based on my research, I found a direct structural analog to the NFTX timelock bug: `Banlist::ban()` in `net-utils/src/banlist.rs` unconditionally overwrites a ban's expiration time, exactly mirroring the vulnerable `_timelockMint` pattern (no "only extend, never shorten" guard).

### Title
Banlist::ban() unconditionally overwrites expiry, letting a shorter re-ban shrink an existing longer ban - (File: net-utils/src/banlist.rs)

### Summary
`Banlist<T>::ban()`, the shared primitive backing `SimpleQosBanlist` used both by the QUIC/QoS streamer and by the BLS certificate/vote sigverify pipeline, computes `expires_at = Instant::now() + timeout` and unconditionally inserts it into the map, regardless of any existing (possibly longer) ban already recorded for that key. [1](#0-0) 

### Finding Description
The `ban` function is:
```rust
pub fn ban(&self, id: T, timeout: Duration) -> bool {
    debug_assert!(!timeout.is_zero());
    debug_assert!(Instant::now().checked_add(timeout).is_some());
    let Some(expires_at) = Instant::now().checked_add(timeout) else {
        return false;
    };
    let prev = self.banned.write().unwrap().insert(id, expires_at);
    debug_assert!(prev < Some(expires_at));
    prev.is_some()
}
``` [1](#0-0) 

There is no check that the newly computed `expires_at` is later than any pre-existing ban expiry for `id` — it always replaces the stored value. The only "safety net" is a `debug_assert!(prev < Some(expires_at))`, which is compiled out in release builds and therefore provides no runtime protection. This is structurally identical to the reported bug: `_timelockMint` in `XTokenUpgradeable.sol` always set `timelock[account] = block.timestamp + timelockLength` with no guard against shrinking an existing, longer timelock.

`Banlist<Pubkey>` is wrapped by `SimpleQosBanlist`, which is shared and reused across multiple subsystems:
- `bls-sigverify` bans a validator's identity pubkey for `BAN_TIMEOUT = 48 hours` when it sends an invalid certificate or invalid vote signature, e.g. in `bls_cert_sigverify.rs::handle_cert_verify_error` and `bls_sigverifier.rs::keep_vote`. [2](#0-1) [3](#0-2) [4](#0-3) 
- The same `SimpleQosBanlist` instance is consumed by `SimpleQos` in the QUIC streamer, which checks `banlist.is_banned(&remote_pubkey)` when admitting new connections and evicts existing connections for a pubkey when banned. [5](#0-4) [6](#0-5) 

Because `ban()` is a public, general-purpose API on the *same* map instance and takes an arbitrary `timeout`, any code path (present or future) that re-bans an already-banned pubkey with a shorter duration will unconditionally shrink the effective ban window. In the current codebase every production call site happens to pass the same constant `BAN_TIMEOUT`, so exploitation today would require two different call sites banning the same key with different durations — e.g., `streamer/src/quic.rs` also calls `.ban(...)` and I was not able to fully confirm from the index whether it passes the same 48-hour constant or a different, shorter one, since the file content for that specific call site was not returned by my searches. This is the piece I could not fully verify with the tools available.

### Impact Explanation
If any code path bans a pubkey with a shorter duration than an existing ban (now or in a future change), the effect is a full ban-timelock bypass: a validator that was banned for 48 hours for sending an invalid vote/certificate (a severe correctness/anti-spam control) could have that ban silently shortened by triggering a lower-severity, shorter-timeout ban event afterward, re-enabling it to reconnect and resume sending votes/certs/packets well before the intended 48-hour cooldown elapses. This weakens a security control that exists specifically to throttle malicious/faulty validators.

### Likelihood Explanation
Currently low-to-medium: exploitability depends on whether any call site in the codebase (or a future one) invokes `ban()` on the same key with a different, shorter timeout than an already-recorded longer ban. I confirmed multiple independent call sites exist across `bls-sigverify` and `streamer` that share the exact same `Banlist<Pubkey>` via `SimpleQosBanlist`, and one additional call site in `streamer/src/quic.rs` that I could not fully verify the timeout value for. The underlying primitive itself is unconditionally unsafe regardless of current callers, and the `debug_assert!` intended to catch this class of bug is not enforced in release builds, which is the root defect.

### Recommendation
Change `Banlist::ban()` to only update (or extend) the ban if the new expiry is strictly later than any existing one, mirroring the C4 recommendation for `_timelockMint`:
```rust
pub fn ban(&self, id: T, timeout: Duration) -> bool {
    let Some(expires_at) = Instant::now().checked_add(timeout) else {
        return false;
    };
    let mut banned = self.banned.write().unwrap();
    match banned.entry(id) {
        Entry::Occupied(mut e) if *e.get() >= expires_at => true,
        Entry::Occupied(mut e) => { e.insert(expires_at); true }
        Entry::Vacant(e) => { e.insert(expires_at); false }
    }
}
```
This guarantees a ban can only be extended, never shortened, closing the same class of bug identified in the NFTX report.

### Proof of Concept
1. Call `banlist.ban(pubkey, Duration::from_hours(48))` (e.g., via `bls_sigverifier` after an invalid vote) — pubkey is now banned until `now + 48h`.
2. Any subsequent call `banlist.ban(pubkey, Duration::from_secs(30))` from a different call site (e.g., a lower-severity QUIC-level offense) overwrites the entry to `now + 30s`, per `net-utils/src/banlist.rs:25`. [1](#0-0) 
3. After 30 seconds, `is_banned()` returns `false` and the pubkey can reconnect and resume sending votes/certificates/packets, 48 hours ahead of the intended ban expiry. [7](#0-6)

    pub fn is_banned<Q>(&self, id: &Q) -> bool
    where
        T: Borrow<Q>,
        Q: Hash + Eq + ?Sized,
    {
        let now = Instant::now();
        let Some(expires_at) = self.banned.read().unwrap().get(id).copied() else {
            return false;
        };

        if expires_at > now {
            return true;
        }

        let mut banned = self.banned.write().unwrap();
        // Check again in case another thread modified  the banlist
        let Some(expires_at) = banned.get(id).copied() else {
            return false;
        };

        if expires_at > now {
            return true;
        }

        banned.remove(id);
        false
    }
