## Title
DeleteRefs (and UpdateReferences) processes unbounded reference arrays with no hard cap, enabling single-request DoS via unbounded git-update-ref transactions - (File: internal/gitaly/service/ref/delete_refs.go)

### Summary
`RefService.DeleteRefs` accepts a `repeated bytes refs` field of arbitrary size (bounded only by the gRPC max message size) and, like `GovernorAlpha.propose`'s unbounded `targets` array, has no hard cap on how many elements a caller may submit. The handler iterates over the full, unbounded list multiple times, feeds every entry into a single `git-update-ref --stdin` transaction, and locks all of the referenced refs at once in `Prepare()`/`Commit()`, with no chunking or limit enforced anywhere in the call path.

### Finding Description
`validateDeleteRefRequest` only rejects *empty* `Refs`/`ExceptWithPrefix` combinations; it never bounds the maximum size of the `Refs` slice: [1](#0-0) 

`DeleteRefs` then walks the (still unbounded) `refnames` slice several separate times: once to validate each reference name, once to enqueue a `Delete` into the `updateref.Updater`, and additionally writes every reference name into a rolling `voting.VoteHash`: [2](#0-1) 

Each `Delete` call is translated into an `update` command written synchronously to the stdin of a live `git update-ref --stdin` subprocess, and `Prepare`/`Commit` lock and update every one of those references as a single, indivisible transaction: [3](#0-2) [4](#0-3) 

The `.proto` documentation itself flags this exact pattern as risky: it recommends switching to streaming ("Stream unbounded or oversized payloads... Use a stream when the result is an unbounded sequence") for any `repeated` field that "can grow without limit", precisely because a single non-streaming RPC processing such a field can blow past reasonable resource/time budgets: [5](#0-4) 

`DeleteRefs` is a unary (non-streaming) RPC whose `Refs` field is exactly this kind of unbounded `repeated` field, yet it carries no cap, no pagination, and no chunking — mirroring the `GovernorAlpha.propose` issue where an unbounded `targets` array is fully iterated by `queue`/`cancel`/`execute` with no hard cap.

The companion streaming RPC `UpdateReferences` has the analogous problem at the per-message level: each streamed message's `Updates` field is fully consumed in an inner loop with no per-message or per-stream cap, so a single message can still smuggle an unbounded number of updates: [6](#0-5) 

The Gitaly concurrency-limiter middleware only throttles the *number of concurrent RPC invocations* per RPC name; it does not inspect or limit the *size* of an individual request's repeated fields, so it provides no protection against a single oversized `DeleteRefs`/`UpdateReferences` call: [7](#0-6) 

### Impact Explanation
A caller who can invoke `DeleteRefs` on a repository (e.g. via GitLab's bulk branch/tag deletion feature, which is available to any user with write access to the repository) can submit a single request whose `Refs` array contains as many entries as fit under the gRPC max message size (tens of thousands to low hundreds of thousands of ref names, depending on name length). Processing this request:
- keeps the RepositoryService's concurrency slot occupied for the RPC's entire, unbounded processing time,
- locks every referenced reference for the duration of `Prepare`→`Commit`, blocking any concurrent legitimate ref operations (pushes, branch creation, CI, etc.) on the same repository,
- writes an unbounded number of commands through the `git-update-ref` stdin pipe and computes a vote hash over the full set, consuming CPU/memory proportional to request size,
and can therefore degrade or deny service for a single Gitaly node/repository, similar in spirit to the referenced report's DoS of `queue`/`cancel`/`execute` due to unbounded iteration.

### Likelihood Explanation
The `Refs` field is directly attacker-controlled from a standard, authenticated mutator RPC that ordinary repository-write users can reach through GitLab application flows (bulk branch cleanup / stale-branch deletion). No special privilege beyond normal write access is required, and no existing validation caps the array length, making the analog straightforward to trigger.

### Recommendation
Impose an explicit hard cap on the number of entries accepted per `DeleteRefsRequest.Refs` (and per `UpdateReferencesRequest.Updates` message / cumulative stream), rejecting oversized requests with `InvalidArgument`, or convert `DeleteRefs` into a client-streaming RPC and process/commit refs in fixed-size batches (as already done defensively by internal tooling, which manually batches deletions/updates into slices of 1000–50000) so a single request cannot force unbounded work inside one RPC invocation.

### Proof of Concept
1. As a user with write access to a repository, call `RefService.DeleteRefs` with a `Refs` array populated with the maximum number of unique, syntactically valid reference names that fit under the gRPC max message size (no server-side cap exists at `validateDeleteRefRequest`, `internal/gitaly/service/ref/delete_refs.go:166-192`).
2. Observe that the handler proceeds to iterate the entire list three times (`internal/gitaly/service/ref/delete_refs.go:47-78`), feed every entry to a live `git-update-ref --stdin` process (`internal/git/updateref/updateref.go:415-421`), and lock all of them for `Prepare`/`Commit` (`internal/git/updateref/updateref.go:423-453`) — all inside a single, non-chunked RPC call, tying up the concurrency slot and reference locks for the whole processing duration.

func validateDeleteRefRequest(ctx context.Context, locator storage.Locator, req *gitalypb.DeleteRefsRequest) error {
	if err := locator.ValidateRepository(ctx, req.GetRepository()); err != nil {
		return err
	}

	if len(req.GetExceptWithPrefix()) > 0 && len(req.GetRefs()) > 0 {
		return errors.New("ExceptWithPrefix and Refs are mutually exclusive")
	}

	if len(req.GetExceptWithPrefix()) == 0 && len(req.GetRefs()) == 0 { // You can't delete all refs
		return errors.New("empty ExceptWithPrefix and Refs")
	}

	for _, prefix := range req.GetExceptWithPrefix() {
		if len(prefix) == 0 {
			return errors.New("empty prefix for exclusion")
		}
	}

	for _, ref := range req.GetRefs() {
		if len(ref) == 0 {
			return errors.New("empty ref")
		}
	}

	return nil
}

// Prepare prepares the reference transaction by locking all references and determining their
// current values. The updates are not yet committed and will be rolled back in case there is no
// call to `Commit()`. This call is optional.
func (u *Updater) Prepare() error {
	if err := u.expectState(stateStarted); err != nil {
		return err
	}

	u.state = statePrepared

	return u.setState("prepare")
}

// Commit applies the commands specified in other calls to the Updater. Commit finishes the
// reference transaction and another one must be started before further changes can be staged.
func (u *Updater) Commit() error {
	// Commit can be called without preparing the transactions.
	if err := u.checkState(statePrepared); err != nil {
		if err := u.expectState(stateStarted); err != nil {
			return err
		}
	}

	u.state = stateIdle

	if err := u.setState("commit"); err != nil {
		return err
	}

	return nil
}
