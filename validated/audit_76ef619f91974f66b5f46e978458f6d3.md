### Title
Pre-funded EOA colliding with TIP-2935 system address retains votes/frozen resources when upgraded to a contract, unlike the equivalent CREATE2 collision path - (File: `framework/src/main/java/org/tron/core/db/HistoryBlockHashUtil.java`)

### Summary
Any unprivileged account can transfer TRX (or freeze/delegate resources) to the fixed, publicly known address `HISTORY_STORAGE_ADDRESS` before TIP-2935 activation. When the `ALLOW_TVM_PRAGUE` proposal is later processed, `HistoryBlockHashUtil.deploy()` converts that pre-existing account into a contract in place, but only calls `updateAccountType` + `clearDelegatedResource`, unlike the canonical CREATE2-collision handling in `Program.createContractImpl`, which the code comments claim to mirror.

### Finding Description
`HistoryBlockHashUtil.deploy()` is invoked once from `ProposalService.process()` when the `ALLOW_TVM_PRAGUE` proposal parameter is applied: [1](#0-0) 

The deploy routine explicitly branches on whether an account already exists at the hardcoded `HISTORY_STORAGE_ADDRESS`, and for the pre-existing case only clears delegated resource, not votes/freeze/tron-power state: [2](#0-1) 

The doc-comment itself states the intent is to mirror the CREATE2 collision handling (`updateAccountType` + `clearDelegatedResource`) in `Program.createContractImpl`: [3](#0-2)  That reference implementation is: [4](#0-3) 

Because `HISTORY_STORAGE_ADDRESS` is a fixed, publicly known constant (`410000f90827f1c53a10cb7a02335b175320002935`), any unprivileged user can, prior to activation, send TRX to it, freeze balance in it, become a receiver of `DelegateResourceContract`, vote with it, etc. — all state-mutating operations available to ordinary account holders via `FreezeBalanceV2Contract`, transfer, `DelegateResourceContract`, and `VoteWitnessContract`. When the committee later activates TIP-2935 (an ordinary, non-malicious governance action once Prague support ships), `deploy()` converts this attacker-prepared account to `AccountType.Contract` while leaving any frozen balance, `FrozenV2` entries, votes, and TRON Power untouched, since only `clearDelegatedResource()` is invoked, not `clearFrozenV2`/`clearVotes`/vote weight adjustment such as `UnfreezeBalanceProcessor`/`Program.clearOwnerFreezeV2`/`withdrawRewardAndCancelVote` perform elsewhere for account-type transitions. This leaves a "contract" account able to retain governance voting power and resource state derived from before it existed as a contract, at an address whose code/storage every node treats as the shared TIP-2935 system contract.

### Impact Explanation
An unbacked/attacker-controlled voting-power and resource-accounting state ends up permanently attached to the canonical, globally-shared system contract address that every node's TVM STATICCALLs into for block-hash history. This corrupts total-weight accounting (`TotalNetWeight`/`TotalEnergyWeight`/`TotalTronPowerWeight`) invariants maintained elsewhere by symmetric clear operations, and grants an attacker-influenced vote/resource footprint tied to an address the protocol intends to be a clean, freshly-provisioned system contract — a form of unauthorized/unbacked resource-accounting corruption on a chain-wide, non-reclaimable address.

### Likelihood Explanation
Reachable by any unprivileged transaction broadcaster: sending TRX, freezing/delegating resources, or voting to a known, hardcoded address requires no special privilege. The only precondition outside attacker control is that the committee eventually activates `ALLOW_TVM_PRAGUE`, which is an ordinary planned feature activation, not a malicious act — the vulnerability is triggered by legitimate governance combined with attacker pre-positioning at a public, deterministic address.

### Recommendation
In `HistoryBlockHashUtil.deploy()`, when reusing a pre-existing account (`accountExisting == true`), fully reset resource/voting state to match a freshly created contract account — clear `FrozenV2`, legacy `Frozen`, votes (with corresponding `TotalNetWeight`/`TotalEnergyWeight`/`TotalTronPowerWeight` adjustments and `VotesCapsule` bookkeeping), and any acquired/delegated resource fields — not just delegated resource, consistent with the full set of steps `Program.createContractImpl`'s CREATE2-collision branch and associated unfreeze/vote-clearing helpers perform together.

### Proof of Concept
1. Before any committee activates `ALLOW_TVM_PRAGUE`, an unprivileged attacker sends TRX to `410000f90827f1c53a10cb7a02335b175320002935` and freezes balance there (`FreezeBalanceV2Contract`) to accrue TRON Power / votes via `VoteWitnessContract`.
2. Committee later approves the `ALLOW_TVM_PRAGUE` proposal; `ProposalService.process()` calls `HistoryBlockHashUtil.deploy(manager)`.
3. `deploy()` finds `accountExisting == true`, calls `account.updateAccountType(Contract)` and `account.clearDelegatedResource()` only, then writes the account back with its frozen balance, votes, and TRON Power intact.
4. The account at the canonical system-contract address now simultaneously behaves as the shared BlockHashHistory contract and retains attacker-derived votes/frozen weight that a freshly-created contract account would never have, deviating from the intended invariant that system contracts start with clean resource/vote state.
