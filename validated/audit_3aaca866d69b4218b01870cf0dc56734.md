### Title
Cross-StackerDB signature replay via missing `contract_id` binding in `SlotMetadata::auth_digest` - ([File: libstackerdb/src/libstackerdb.rs])

### Summary
`SlotMetadata::sign`/`verify` authenticate only `(slot_id, slot_version, data_hash)` via `auth_digest()`, never `contract_id`. `validate_received_chunk` in `stackslib/src/net/stackerdb/mod.rs` resolves the expected signer purely from `(smart_contract_id, slot_id)` and then calls `slot_metadata.verify(&addr)`, so a previously-broadcast, publicly-observable `StackerDBChunkData` for contract A's slot N is a valid signature for contract B's slot N whenever both slots' configured signer addresses coincide, with no need to possess any private key.

### Finding Description
`auth_digest()` hashes only `slot_id`, `slot_version`, and `data_hash`: [1](#0-0) . `SlotMetadata::verify` recovers the public key from this digest and the signature and compares its hash160 to the caller-supplied `principal` — the `contract_id` never enters the check: [2](#0-1) . `StackerDBChunkData::verify`/`sign` simply delegate to this same metadata (again with no contract binding): [3](#0-2) .

In `validate_received_chunk`, the expected signer is looked up per-contract (`get_slot_signer(smart_contract_id, data.slot_id)`), but the signature check itself only verifies against that address using the contract-agnostic digest: [4](#0-3) . This is invoked from `handle_unsolicited_StackerDBPushChunk`, which is reachable from any connected P2P peer sending a `StackerDBPushChunkData` message, requiring only that the local node also replicates the target `contract_id`: [5](#0-4) .

Since a valid `StackerDBChunkData` (slot_id, slot_version, sig, data) that was legitimately broadcast for contract A is fully public (every replicating node relays it), any unprivileged peer can capture it off the wire and resubmit the identical bytes tagged with a different `contract_id` (contract B). If contract B's slot with that same `slot_id` happens to be configured (by its own smart contract's signer list) to the same `StacksAddress` as contract A's slot, `get_slot_signer` returns that address for contract B, and `slot_metadata.verify(&addr)` succeeds — because the digest never included which contract it was for. No private key is needed by the replaying attacker; they only need to have observed the original broadcast, which is itself unauthenticated public gossip.

The remaining checks in `validate_received_chunk` (chunk size, version freshness, `max_writes`) do not bind to `contract_id` either and do not prevent this cross-contract replay.

### Impact Explanation
An unprivileged peer can force a node to accept and store into StackerDB contract B's slot data that was only ever authorized (signed) for contract A, without holding any signing key. This is an unauthenticated/unauthorized write into StackerDB state — data attributed to a real signer address is injected into a different smart contract's replica than the one the signer actually wrote to. Depending on how downstream consumers (e.g., signer coordination `.signers-*` StackerDBs used across different reward cycles/pages) trust per-contract StackerDB content, this could cause stale/foreign data to be served/propagated as if freshly authored for that contract, and the write propagates network-wide via the normal StackerDB replication/broadcast path. Note: the actual consumption/interpretation of signer-coordination StackerDB content by the signer decision logic is explicitly out of scope; the injection point itself (unauthenticated cross-contract StackerDB write) is what is being reported.

### Likelihood Explanation
Exploitation requires: (1) the attacker observes (via normal gossip/relay, no privilege needed) a validly-signed `StackerDBChunkData` for some slot in contract A, and (2) the node under attack also replicates contract B, whose signer-list assignment for the same numeric `slot_id` happens to resolve to the same `StacksAddress` as contract A's slot. Address-to-slot-index assignment is determined by each contract's own signer-list logic (e.g., ordering by stacked amount), so the same address landing on the same slot index across two different StackerDB contracts (e.g., different reward-cycle `.signers-*` contracts, or `.signers` vs another custom StackerDB) is a plausible, not merely theoretical, coincidence, and the attacker's cost is trivial — replay one already-public message with a different `contract_id` field, remotely, over P2P. Repeatable indefinitely and for any coinciding slot pair.

### Recommendation
Include `contract_id` (or a stable numeric contract identifier) in `SlotMetadata::auth_digest()` so signatures are cryptographically bound to the specific StackerDB contract they were authored for, e.g. hash `contract_id.issuer`, `contract_id.name`, `slot_id`, `slot_version`, and `data_hash`. This requires threading the `QualifiedContractIdentifier` into `SlotMetadata`/`sign`/`verify` (and bumping any wire/DB compatibility as needed), and updating `validate_received_chunk` and DB-write paths to pass the contract ID into the verification call.

### Proof of Concept
Rust test in `libstackerdb/src/tests` (or `stackslib/src/net/stackerdb/tests`):
1. Construct two distinct `QualifiedContractIdentifier`s, contract A and contract B.
2. Create a `StackerDBChunkData` with `slot_id = 0`, `slot_version = 1`, some `data`, sign it with `privkey` for address `addr` (note: `sign`/`verify` take no `contract_id` parameter at all, confirming the missing binding) — `chunk.sign(&privkey)`.
3. Call `chunk.verify(&addr)` — assert it returns `Ok(true)` (this is the "contract A" verification context).
4. Reuse the exact same `chunk` object unmodified, and call `chunk.verify(&addr)` again standing in for "contract B slot 0" (since the API provides no way to pass contract B's identity into `verify` at all) — assert it still returns `Ok(true)`, proving the same signed bytes validate for any contract whose slot owner matches `addr`.
5. Extend into a `stackslib` integration test: configure two `StackerDBs` replicas for contract A and contract B, each with slot 0 assigned to `addr`; call `PeerNetwork::validate_received_chunk(&contract_b_id, &config_b, &chunk_signed_for_a, &expected_versions)` and assert it returns `Ok(true)`, then confirm the chunk is written into contract B's slot 0 store despite having been authored/broadcast originally for contract A.

    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }

        let digest = self.get_slot_metadata().auth_digest();
        StacksPublicKey::recover_to_pubkey_without_validating_low_s(digest.as_bytes(), &self.sig)
            .map_err(|ve| Error::VerifyingError(ve.to_string()))
    }
