### Title
`ReliabilityReport::bump_successful_requests` credits peers for undelivered content, poisoning peer selection - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` bumps a peer's reliability score whenever `response.decode_atlas_get_attachment()` succeeds, without ever checking that the returned attachment's hash matches the requested `content_hash`. This lets a malicious peer serve arbitrary well-formed-but-wrong-hash payloads and still accumulate a perfect reliability score, biasing future peer selection in its favor.

### Finding Description
In `extend_with_attachments` [1](#0-0) , the code does:
```
if let Ok(response) = response.decode_atlas_get_attachment() {
    self.attachments.insert(response.attachment);
    report.bump_successful_requests();
} else {
    report.bump_failed_requests();
}
```
There is no comparison of `response.attachment.hash()` against `request.content_hash` at this point. Any peer that returns a syntactically valid `GetAttachmentResponse` JSON blob — regardless of whether its content hashes to the requested `content_hash` — causes `report.bump_successful_requests()` to fire. The reliability score is supposed to represent the rate at which a peer serves the *correct* requested content, but as implemented it merely reflects the rate at which a peer returns *any* parseable response.

This poisoned `ReliabilityReport` is stored back into `AttachmentsDownloader::reliability_reports` (via the `run` loop at `context.peers.drain()`, lines 182–185) and is subsequently used to construct new `AttachmentRequest`/`AttachmentsInventoryRequest` objects's `sources`/`reliability_report` fields, which drive `Ord`/`get_most_reliable_source` peer prioritization for future requests. Because scoring never depends on hash correctness, an attacker peer that always returns wrong-hash content still climbs to (and stays at) the top reliability tier, crowding out honest peers on every retry.

Separately, the actual attachment *value* stored in `self.attachments` (a `HashSet<Attachment>`) is not directly bound to `request.content_hash` either at this call site; downstream in `AttachmentsDownloader::run`, attachments are paired to instances via `atlasdb.find_all_attachment_instances(&attachment.hash())`, i.e., by the actual content hash of what was received, not the hash that was requested — so a wrong-hash attachment from the attacker does not get mis-paired to the requested instance, but it does get scored as a "success," which is the object of this finding.

### Impact Explanation
No data is corrupted or served as canonical as a direct result of this specific bug (the hash-based pairing downstream prevents wrong-content acceptance for that call). The impact is confined to reliability-score integrity: an unprivileged attacker peer can force its `ReliabilityReport` score upward indefinitely while delivering zero correct attachments, which (per the "two prior findings" referenced by this question) entrenches attacker-peer selection via `AttachmentRequest::get_most_reliable_source`/`Ord::cmp`, causing honest peers to be starved of retries and increasing overall attachment-resolution latency/failure for the syncing node. This matches "steering a node off canonical data-serving peers" in spirit but does not itself achieve state corruption; the score corruption is the mechanism that entrenches selection bias described in the linked prior findings.

### Likelihood Explanation
Preconditions are minimal and attacker cost is low: the attacker only needs to be a normal outbound sync peer (`network.get_outbound_sync_peers()`) with a data URL, and to respond to every attachment request with a well-formed but hash-mismatched `GetAttachmentResponse`. No secrets, no privileged role, no protocol violation beyond serving wrong content are required, and the behavior is fully repeatable across retries/batches. [2](#0-1) 

### Recommendation
In `extend_with_attachments`, verify `response.attachment.hash() == request.content_hash` before calling `report.bump_successful_requests()`; if it does not match, treat it as a failed request (`report.bump_failed_requests()`) and discard the attachment instead of inserting it into `self.attachments`. Apply the same corrective pattern anywhere else a decoded response is credited without a content-integrity check (e.g. `extend_with_inventories` should still be checked against its own contract for consistency of trust signal).

### Proof of Concept
Rust test in `stackslib/src/net/atlas/tests.rs` (or a new test module in `download.rs`):
1. Construct an `AttachmentsBatchStateContext` with one peer `P` and a `ReliabilityReport::empty()`.
2. Build an `AttachmentRequest` with `content_hash = H_expected`.
3. Construct a `BatchedRequestsResult` whose `succeeded` map contains `(request.clone(), Some(fake_response))`, where `fake_response` decodes via `decode_atlas_get_attachment()` to an `Attachment` whose `.hash()` is `H_attacker != H_expected`.
4. Call `context.extend_with_attachments(&mut results)` several times (simulating repeated rounds).
5. Assert: `context.peers.get(&peer_url).unwrap().score()` increased after each round despite `H_attacker != H_expected` on every round — i.e., `score_after > score_before` with zero correct deliveries, proving the equality break (score should be 0/N, but the test shows it climbing to N/N).

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }
