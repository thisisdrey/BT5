### Title
Quarantined objects are migrated into the main object directory before the transaction's final `Committed` vote succeeds, allowing rejected/failed transactions to leave permanent, unauthorized objects in the repository - ([File: internal/gitaly/service/operations/squash.go])

### Summary
Several Gitaly RPCs that use quarantine directories (`UserSquash`, `FetchRemote`, `DisconnectGitAlternates`/`LinkRepositoryToObjectPool` via `objectpool.Disconnect`/`Link`, and repository creation via `repoutil.Create`) migrate quarantined objects into the repository's real object directory *after* the `Prepared` transactional vote but *before* the final `Committed` vote is cast and confirmed. If the `Committed` vote subsequently fails (e.g. quorum is lost, a peer disagrees, or the vote errors out), the RPC returns an error to the client as if the operation failed, but the objects have already been irreversibly written to disk and become part of the repository's object database.

### Finding Description
The reported external bug class is "an operation makes state changes (share distribution) visible/permanent before the gating condition (investment period end / quorum) is actually satisfied, because validation/finalization is checked too late relative to the state-changing action." The Gitaly analog is the ordering of `quarantine.Dir.Migrate()` relative to `voting.Committed`.

In `internal/gitaly/service/operations/squash.go`, `userSquash()`: [1](#0-0) 
casts a `Preparing` and `Prepared` vote, then unconditionally calls `quarantineDir.Migrate(ctx)` to move the staged objects into the main object directory, and only afterwards casts the `Committed` vote. `Migrate()` performs a physical, non-transactional file-system move/rename of the quarantine contents into the repository's real `objects/` directory: [2](#0-1) [3](#0-2) 

The same "migrate-before-final-vote" pattern also exists in:
- `internal/gitaly/service/repository/fetch_remote.go` — objects are migrated before `refUpdater.Commit()`: [4](#0-3) 
- `internal/git/objectpool/disconnect.go` — objects are hard-linked out of the alternate before the `Committed` vote is cast: [5](#0-4) 
- `internal/gitaly/repoutil/create.go` — the new repository directory is renamed into its final place between `Prepared` and before the caller confirms full success: [6](#0-5) 

The project's own test suite documents that this produces an inconsistent result specifically when the transaction manager does **not** use the new WAL-based partition (`storagemgr` in non-WAL mode, which remains a supported/likely-more-common configuration since WAL/partitioned transactions are explicitly called "work-in-progress" and "not production ready yet" in `doc/transactions.md`): [7](#0-6) [8](#0-7) 

The test explicitly asserts `expectedExists: !testhelper.IsWALEnabled()` for the "committing vote failure" case — i.e., when the final `Committed` vote fails, the squashed commit object still exists on disk in the non-WAL execution path, even though the RPC returned an `Aborted` error to the caller. This is the direct analog of "operator distributes shares before the investment period ends": the artifact (objects) is made durably visible in the repository before the gating condition (final quorum/commit vote) that is supposed to authorize its existence has actually succeeded.

### Impact Explanation
- Objects that a Gitaly cluster's voting/quorum mechanism was supposed to reject (e.g., because a replica disagreed, hooks failed post-quorum, or the transaction was otherwise aborted) can persist in the repository's object database despite the RPC reporting failure to the caller.
- This breaks the intended replica consistency guarantee that transactional voting is meant to enforce (per `doc/transactions.md`, votes gate whether a write becomes visible across replicas). A node can end up with extra, un-referenced-but-present objects that other nodes do not have, or that were never supposed to be committed, leading to storage divergence between Gitaly nodes in a Praefect-managed cluster.
- Because the objects are moved via `os.Rename`/hard-link rather than being reverted on vote failure, there is no compensating rollback of the already-migrated data — it is treated as best-effort garbage rather than being cleaned up.
- This is reachable through unprivileged, everyday user actions (e.g., squash-before-merge triggers `UserSquash`; a fork/fetch triggers `FetchRemote`), not just administrative/operator actions.

### Likelihood Explanation
The behavior is deterministic and reproducible: it occurs whenever the `Committed` vote phase fails or is aborted after the `Prepared` phase has already succeeded, in any code path that does not use the newer WAL/partitioned transaction manager. Since the WAL-based transaction manager is explicitly documented as experimental and not yet generally available, the affected legacy path is still the default execution model for many Gitaly deployments, making this a realistically triggerable condition (e.g., a flaky/partitioned replica causing quorum loss right after the prepared phase).

### Recommendation
Reorder the finalization sequence in all affected RPC paths (`userSquash`, `fetchRemoteAtomic`, `objectpool.Disconnect`, `objectpool.Link`, `repoutil.Create`) so that any irreversible, physical migration of quarantined objects (`quarantine.Dir.Migrate`, alternates hard-linking, directory renames) only occurs *after* the `Committed` vote has been confirmed to succeed, not between `Prepared` and `Committed`. Where migration must happen earlier for technical reasons (e.g. `git-update-ref(1)` needing objects present), implement a compensating cleanup/rollback step that removes the migrated objects if the subsequent `Committed` vote fails, so that a failed transaction never leaves durable artifacts in the repository.

### Proof of Concept
The existing repository test already demonstrates the flaw: [7](#0-6) 

1. Configure the `txManager.VoteFn` to fail specifically on the `voting.Committed` phase for a `UserSquash` request.
2. Call `client.UserSquash(...)`. The RPC returns `structerr.NewAborted("committing vote on squashed commit: ...")` to the client, signaling failure.
3. Inspect the repository (`repo.HasRevision(ctx, squashedCommitID+"^{commit}")`): in the non-WAL execution path, the squashed commit object exists on disk despite the RPC having reported failure, because `quarantineDir.Migrate(ctx)` (`internal/gitaly/service/operations/squash.go:199`) already ran before the failed `Committed` vote.

// Migrate migrates all objects part of the quarantine directory into the repository and thus makes
// them generally available. This implementation follows the git.git's `tmp_objdir_migrate()`.
func (d *Dir) Migrate(ctx context.Context) error {
	repoPath, err := d.locator.GetRepoPath(ctx, d.repo, storage.WithRepositoryVerificationSkipped())
	if err != nil {
		return fmt.Errorf("migrating quarantine: %w", err)
	}

	objectDir := d.repo.GetGitObjectDirectory()
	if objectDir == "" {
		// Migrate the objects to the default object directory if the repository
		// didn't have an object directory explicitly configured.
		objectDir = "objects"
	}

	return migrate(ctx, d.dir.Path(), filepath.Join(repoPath, objectDir))
}

func migrate(ctx context.Context, sourcePath, targetPath string) error {
	entries, err := os.ReadDir(sourcePath)
	if err != nil {
		return fmt.Errorf("reading directory: %w", err)
	}
	sortEntries(entries)

	syncer := safe.NewSyncer()
	for _, entry := range entries {
		if entry.Name() == "." {
			continue
		}

		nestedTargetPath := filepath.Join(targetPath, entry.Name())
		nestedSourcePath := filepath.Join(sourcePath, entry.Name())

		if entry.IsDir() {
			if err := os.Mkdir(nestedTargetPath, mode.Directory); err != nil {
				if !errors.Is(err, os.ErrExist) {
					return fmt.Errorf("creating target directory %q: %w", nestedTargetPath, err)
				}
			}

			if err := migrate(ctx, nestedSourcePath, nestedTargetPath); err != nil {
				return fmt.Errorf("migrating directory %q: %w", nestedSourcePath, err)
			}

			if storage.NeedsSync(ctx) {
				if err := syncer.Sync(ctx, nestedTargetPath); err != nil {
					return fmt.Errorf("sync directory: %w", err)
				}
			}

			continue
		}

		if err := finalizeObjectFile(nestedSourcePath, nestedTargetPath); err != nil {
			return fmt.Errorf("migrating object file %q: %w", nestedSourcePath, err)
		}

		if storage.NeedsSync(ctx) {
			if err := syncer.Sync(ctx, nestedTargetPath); err != nil {
				return fmt.Errorf("sync object: %w", err)
			}
		}
	}

	if storage.NeedsSync(ctx) {
		if err := syncer.Sync(ctx, targetPath); err != nil {
			return fmt.Errorf("sync object directory: %w", err)
		}
	}

	if err := os.Remove(sourcePath); err != nil {
		return fmt.Errorf("removing source directory: %w", err)
	}

	return nil
}

# Transactions

Gitaly contains work-in-progress support for transactions that can be enabled by through configuration:

```toml
[transactions]
enabled = true
```

Gitaly logs the following line confirming transactions are enabled:

```json
{"level":"warning","msg":"Transactions enabled. Transactions are an experimental feature. The feature is not production ready yet and might lead to various issues including data loss.","pid":70356,"time":"2025-07-16T07:44:28.884Z"}
```

While transactions are functional and being tested in production on GitLab.com, they're not considered generally available yet. The original blueprint describing transactions in Gitaly can be found at the
[GitLab Handbook](https://handbook.gitlab.com/handbook/engineering/architecture/design-documents/gitaly_transaction_management), and it's worthwhile reading it before this document. This document focuses on the current state of the implementation.

Transactions provide [snapshot isolation](https://en.wikipedia.org/wiki/Snapshot_isolation) with [optimistic concurrency control](https://en.wikipedia.org/wiki/Optimistic_concurrency_control). Transactions read a stable snapshot of the latest committed state of a repository at the time the transaction began and remain isolated from concurrent changes of other transactions. Possible conflicts are detected at commit time, and lead to transactions being aborted.

While the logical properties are similar to other databases providing snapshot isolation, the implementation is non-conventional. Gitaly is tightly coupled to Git, and the transaction implementation works around shortcomings of Git. For example, Git only understands repositories stored on a file system in the `.git` directory, so snapshot isolation is implemented through indirection on the file system level. Some Git operations produce conflicting file modifications which the transaction implementation has to resolve at commit time. There's also a lot of existing code tightly coupled to Git in Gitaly, and the transaction implementation is designed to plug into the existing code transparently.
```
