### Title
Account deletion fails to purge PostponedReceipt/PostponedReceiptId/PendingDataCount trie entries, enabling stale-receipt execution against a recreated account - (File: core/store/src/utils/mod.rs)

### Summary
`remove_account` in `core/store/src/utils/mod.rs` only deletes the `Account`, `ContractCode`, `AccessKey`/`GasKeyNonce`, and `ContractData` trie entries for an account, but never touches `TrieKey::PostponedReceipt`, `TrieKey::PostponedReceiptId`, or `TrieKey::PendingDataCount`. Since these entries are keyed by `receiver_id` (the account name) and written whenever a receipt with unresolved `input_data_ids` targets that account (`process_action_receipt`, `runtime/runtime/src/lib.rs:1608-1655`), an account can be deleted while it still has an outstanding postponed receipt, and that receipt survives in state under the same account-name key even after `DeleteAccount`.

### Finding Description
`process_action_receipt` writes `TrieKey::PostponedReceiptId { receiver_id, data_id }` and `TrieKey::PendingDataCount { receiver_id, receipt_id }` plus the postponed receipt itself (`set_postponed_receipt`) whenever an incoming action receipt's `input_data_ids` are not yet all resolved via `has_received_data` [1](#0-0) . These keys are namespaced purely by `receiver_id`, i.e., the account name string, with no binding to the account's underlying identity/generation (e.g., no nonce or account "epoch" tied to the current occupant of that name).

`remove_account` is the routine invoked by `action_delete_account` when an account self-destructs, and it explicitly removes only `Account`, `ContractCode`, access keys/gas-key nonces, and `ContractData`: [2](#0-1) . There is no corresponding cleanup of `TrieKey::PostponedReceipt`, `TrieKey::PostponedReceiptId`, or `TrieKey::PendingDataCount` for `account_id` anywhere in this function.

Because NEAR account names can be freely recreated after deletion (deleting `temp.near` and later re-creating `temp.near` is a normal, permissionless operation available to any account holder), an attacker can:
1. Create `temp.near` with access key K1.
2. Send `temp.near` an action receipt whose actions include a privileged action (e.g., `AddFullAccessKey`) with an `input_data_ids` dependency that is never resolved (e.g., a `promise_then` callback on itself that is intentionally never fulfilled). This receipt gets stored as a postponed receipt keyed to `receiver_id = temp.near`.
3. Issue `DeleteAccount` on `temp.near`. `remove_account` clears the account/keys/code/data but leaves the postponed receipt and its bookkeeping entries in the trie under the `temp.near` key namespace.
4. Recreate `temp.near` (any account, potentially a victim or the attacker acting as a new owner with different keys).
5. Deliver the outstanding `DataReceipt` for the pending `data_id`. When the runtime processes it, `has_received_data`/postponed-receipt resolution logic in `apply_action_receipt` (`runtime/runtime/src/lib.rs:772` per the referenced flow) finds the stored postponed receipt for `temp.near` and executes its actions — now against the freshly recreated account, using whatever authority the *new* account holds, not the authority that was verified when the original receipt was created.

None of the existing checks (`action_validation.rs` signature/permission checks, nonce checks, gas metering, storage staking) address this because those checks are performed for the *original* receipt creation and for the *delete* transaction — they do not perform a liveness check of "does this account still have pending postponed receipts" before allowing deletion, and they have no way to invalidate previously-stored postponed receipts tied only to a plain account-name string when the account identity changes.

### Impact Explanation
This is an authorization-escalation-across-account-recreation bug: a receipt's actions (e.g., `AddFullAccessKey`, `DeployContract`, `Transfer`) that were only valid in the context of an account's prior existence can be replayed against a semantically different (recreated) account without the new owner's consent. Depending on which actions are queued in the stale postponed receipt, this can lead to unauthorized key injection or fund transfers, matching the "authorization escalation across account recreation" bounty category. Concretely, an attacker could plant an `AddFullAccessKey` action against their own account name, delete/recreate it (or have a victim recreate the freed name), and then trigger execution to gain a full-access key on the new occupant's account — a fund-theft primitive if the new occupant deposits funds.

### Likelihood Explanation
The attack is fully executable by an unprivileged account holder using only ordinary transactions: `FunctionCall`/`promise_then` to create an unresolved cross-receipt dependency, followed by `DeleteAccount`, then a normal `CreateAccount`, then delivering the pending `DataReceipt` (which the attacker controls the timing of, since it is the attacker's own dangling promise). No validator or node privilege is required, and the cost is limited to gas/storage fees for a handful of transactions. It is repeatable for any account name the attacker controls at time of deletion, though most impactful when a victim ends up reusing the freed account name (a scenario the protocol already discourages but does not prevent).

### Recommendation
`remove_account` (`core/store/src/utils/mod.rs:505-575`) should also iterate and remove all `TrieKey::PostponedReceipt`, `TrieKey::PostponedReceiptId`, and `TrieKey::PendingDataCount` entries for the deleted `account_id` before allowing `DeleteAccount` to complete (or `action_delete_account` should reject deletion while any postponed receipts targeting the account remain outstanding, similar to existing protections against deleting accounts with locked/staked balance).

### Proof of Concept
Integration/runtime test-loop plan:
1. Create account `temp.near` with access key K1.
2. Submit an action receipt to `temp.near` containing a `promise_then`-style dependency on a `data_id` that is never resolved by any subsequent receipt, and whose eventual actions include `AddFullAccessKey(K_attacker)`. Confirm via state query that `TrieKey::PostponedReceipt`/`PostponedReceiptId`/`PendingDataCount` exist for `temp.near`.
3. Submit `DeleteAccount` for `temp.near` signed by K1; confirm `Account`, `AccessKey` records are gone but the postponed-receipt trie keys above are still present (directly query trie state).
4. Submit `CreateAccount` recreating `temp.near` with a new key K2 (simulating a different/victim owner).
5. Deliver the missing `DataReceipt` for the previously-unresolved `data_id`.
6. Assert that the runtime executes the stale receipt (`apply_action_receipt`) and that `AddFullAccessKey(K_attacker)` is now present on the recreated `temp.near` account, despite the new owner (K2) never authorizing it.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
