### Title
Time-of-check/time-of-use race in the message-counter replay window lets a duplicated packet be decrypted twice - (File: connection_state.go)

### Summary
The external report's bug class is that a value which can legitimately change between "check" and "use" is not bound-checked atomically, so an attacker (or adverse timing) can slip through with a stale/duplicated value and cause unintended, harmful processing. The reachable analog in nebula is `ConnectionState.Decrypt` in `connection_state.go`, where the replay-window check (`window.Check`) and the replay-window commit (`window.Update`) are two separate, individually-locked operations with decryption sandwiched in between and the lock released in the gap.

### Finding Description
`ConnectionState.Decrypt` first takes `decryptLock`, calls `cs.window.Check(l, messageCounter)` to see whether `messageCounter` is a duplicate, and releases the lock: [1](#0-0) 

Only after decryption succeeds does it re-acquire the lock and call `cs.window.Update(l, messageCounter)` to actually mark the counter as seen. Between the `Check` and the `Update`, the lock is not held, so two goroutines racing on the same `ConnectionState` (e.g., processing two copies of the same wire packet delivered to two different UDP listener routines) can both pass `Check` for the same `messageCounter` before either has called `Update`. Both will then proceed to `DecryptDanger` and both will succeed, and only afterward does `Update` get called twice (the second call correctly returns `false` from `Bits.Update`, but by then the damage is already done — the packet has already been decrypted and handed to the caller a second time).

`Bits.Check`/`Bits.Update` in `bits.go` implement the actual sliding-window replay-detection algorithm and are correct in isolation: [2](#0-1) [3](#0-2) 

but their correctness depends entirely on the caller treating "check-then-mark" as one atomic step, which `Decrypt` does not — the two locked sections are separated by the unlocked, non-trivial `DecryptDanger` call. `VerifyRelay` has the identical pattern: [4](#0-3) 

The e2e replay-protection test only exercises the *sequential* replay case (a single injected duplicate packet processed one after another) and does not exercise concurrent delivery of the same counter, so it would not catch this race: [5](#0-4) 

Whether nebula's runtime actually delivers packets destined for the same `HostInfo`/`ConnectionState` concurrently from multiple goroutines (e.g., multiple UDP read routines dispatching to the same tunnel) could not be confirmed from the indexed code in this pass — the UDP listener/dispatch loop implementation was not retrievable within the available search results. This is the key uncertainty: if nebula guarantees single-threaded, serialized delivery per `ConnectionState`, this race is unreachable in practice; if any two listener goroutines can hand packets for the same tunnel to `Decrypt` concurrently (which the presence of a `decryptLock` at all strongly suggests was a real concern), the race is live.

### Impact Explanation
If reachable, this breaks the core guarantee of the replay window: an attacker who can capture a single valid ciphertext (no CA-signed certificate needed — replaying already-observed on-wire traffic requires no cryptographic material of its own) can, by re-injecting timed duplicate copies of that captured packet, cause the same plaintext to be decrypted and delivered to the application/tun-device path more than once. Depending on what is carried in that message this can mean data being reprocessed (duplicate delivery to the TUN interface), and for `VerifyRelay`, duplicate relay-frame forwarding. It undermines the anti-replay assurance nebula documents and tests for.

### Likelihood Explanation
Exploiting this requires precise packet timing to win a race between two goroutines processing the same `messageCounter`, and requires the runtime to actually deliver overlapping packets concurrently to the same `ConnectionState`, which was not confirmed. Given that uncertainty, likelihood is assessed as low-to-moderate: the code pattern is a textbook TOCTOU that the existing lock exists to prevent but doesn't fully cover, but concrete exploitation depends on nebula's dispatch concurrency model, which could not be verified with the tools available in this session.

### Recommendation
Hold `decryptLock` for the entire check-decrypt-commit sequence in `ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` (or otherwise make "check and mark as seen" a single atomic operation, e.g., have `Bits` expose a combined `CheckAndReserve`/`CheckAndUpdate` call performed under one lock acquisition that spans the decryption boundary, or reserve the slot before decrypting and roll it back on decryption failure). This closes the window during which two callers can both observe "not yet seen" for the same counter.

### Proof of Concept
Conceptual (not verified against actual dispatch code):
1. Attacker captures one legitimate encrypted packet `P` with message counter `N` sent over an established tunnel.
2. Attacker sends two copies of `P` to the receiving node's UDP socket at nearly the same instant.
3. If the receiver's socket-read path can hand the two copies to two different goroutines that both invoke `ConnectionState.Decrypt` for the same `ConnectionState` before either call reaches `window.Update`, both goroutines pass `window.Check(N)` (returns "not seen"), both successfully run `DecryptDanger`, and both return decrypted plaintext to their callers — i.e., the same message is delivered twice despite replay protection.
4. Only the second `window.Update(N)` call (whichever runs second) will return `false`, but this happens *after* decryption/delivery already occurred for both copies, so it does not prevent duplicate processing, only duplicate future acceptance.

func (b *Bits) strictlyWithinWindow(i uint64) bool {
	// Handle the case where the window hasn't slid yet. This avoids u64 underflow.
	inWarmup := b.current < b.length
	if i < b.length && inWarmup {
		return true
	}

	// Next, if the packet is in-window, see if we've seen it before
	if i > b.current-b.length {
		return true
	}
	return false //not within window!
}

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}

// updateSlow handles jumps, in-window backfill, dupes, and out-of-window.
func (b *Bits) updateSlow(l *slog.Logger, i uint64) bool {
	// If i is a jump, adjust the window, record lost, update current, and return true
	if i > b.current {
		end := i
		if end > b.current+b.length {
			end = b.current + b.length
		}
		count := end - b.current
		startPos := (b.current + 1) & b.lengthMask

		var lost int64
		if b.current >= b.length {
			// Steady state: every cleared slot is past warmup, so any unset
			// bit we evict is a lost packet from the previous cycle.
			wasSet := b.clearRange(startPos, count)
			lost = int64(count) - int64(wasSet)
		} else {
			// Warmup (the very first window). Some cleared slots represent
			// packets <= length where eviction is not "lost" in the usual
			// sense. This branch is taken at most once per connection so we
			// don't bother optimizing it.
			for n := b.current + 1; n <= end; n++ {
				if !b.get(n) && n > b.length {
					lost++
				}
			}
			b.clearRange(startPos, count)
		}

		// Anything past the new window can never be backfilled, so it's lost.
		if i > b.current+b.length {
			lost += int64(i - b.current - b.length)
		}
		b.lostCounter.Inc(lost)

		b.set(i)
		b.current = i
		return true
	}
