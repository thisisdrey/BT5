### Title
Dust deposit griefing saturates `MAX_TOKENS_PER_USER` per-account lists, freezing receipt of collateral tokens and issuance of new debt for the victim - ([File: contracts/DepositToken.sol])

### Summary
The Mintty CVE class is "an unprivileged remote party forces repeated state-changing operations at negligible cost, degrading service for the victim with no rate limiting." The reachable analog in Metronome is that `DepositToken.deposit` accepts an arbitrary `onBehalfOf_` beneficiary, and every mint of a new msdToken to an account pushes that token into the account's `depositTokensOfAccount` set in `Pool`. Once the combined `debtTokensOfAccount + depositTokensOfAccount` length reaches `MAX_TOKENS_PER_USER` (30), `Pool.addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` revert with `UserReachedMaxTokens`, so every subsequent transfer, deposit, or debt issuance that would add a new token type to the victim's account reverts.

### Finding Description
In `DepositToken.deposit`, the caller supplies `onBehalfOf_` and the minted msdTokens go to that address:

- `deposit(uint256 amount_, address onBehalfOf_)` pulls `underlying` from the caller, mints `_deposited` to `onBehalfOf_` (contracts/DepositToken.sol:211-237).
- `_mint` calls `pool.addToDepositTokensOfAccount(account_)` whenever the recipient's balance goes from 0 to non-zero (contracts/DepositToken.sol:485-488).
- The same happens on `_transfer` (contracts/DepositToken.sol:517-520).
- In `Pool`, `addToDepositTokensOfAccount` and `addToDebtTokensOfAccount` are guarded by `onlyIfAdditionWillNotReachMaxTokens`, which reverts once `debtTokensOfAccount + depositTokensOfAccount >= 30` (contracts/Pool.sol:143-148, 204-220).

An attacker can therefore call `deposit(1 wei, victim)` — or `transfer(victim, dust)` — once per registered deposit token in the pool, at a cost of only dust collateral plus gas. The attacker controls no privileged role; `deposit` is permissionless and `onBehalfOf_` is attacker-chosen. There is no opt-out, minimum amount, or rate limit on adding tokens to another account's list (exactly the "no throttling" bug class). When the victim's list reaches 30 entries, `UserReachedMaxTokens` poisons every path that would add a new token to their account.

### Impact Explanation
- The victim cannot receive any msdToken they don't already hold: direct `transfer`, `transferFrom`, and `deposit(..., victim)` all revert, so funds sent to the victim (e.g., via `Operator.execute` batches or integrator zaps that deposit on behalf of a recipient) fail — temporary freezing of funds in transit.
- The victim cannot issue a synthetic asset through a debt token they haven't used before: `DebtToken.issue`/`mint` adds the debt token via `addToDebtTokensOfAccount` and reverts, blocking new borrowing.
- The grief is cheap and repeatable: each re-add after the victim cleans up costs the attacker only dust collateral. The victim can recover by transferring the dust balances to another address (entries are removed when the balance hits zero), so the freeze is temporary rather than permanent, and existing deposit/debt positions remain withdrawable and repayable.

### Likelihood Explanation
- Attack is permissionless: any EOA with trace amounts of each underlying can execute it directly or via `Operator.execute`.
- Effectiveness depends on the number of registered deposit tokens in a pool relative to `MAX_TOKENS_PER_USER = 30`; on pools with many listed collaterals a single attacker can saturate the entire list. If the victim already holds several token types, fewer deposits are needed.
- No modifier stops it: `whenNotPaused`, `nonReentrant`, `onlyIfDepositTokenExists` all pass; `SynthContext` meta-sender only affects attribution, not authorization.
- Limitation: the attacker can only add deposit-token entries (debt-token entries require the victim to mint), so the attack requires enough distinct registered deposit tokens to push the victim to 30.

### Recommendation
- Do not mutate the victim's per-account list on unsolicited inbound transfers/deposits; instead track collateral membership lazily, or let the set be populated only by actions the account initiates (e.g., add on first `deposit` initiated by the account, not on receipt).
- Alternatively, allow list eviction (`removeFromDepositTokensOfAccount`) to be triggered by the account owner independent of balance, or raise/decouple `MAX_TOKENS_PER_USER` so dust recipients aren't constrained.

### Proof of Concept
Hardhat fork sketch (Hardhat, ethers):

```ts
// Assume `pool` (deployed Pool) and several registered `DepositToken`s d1..dN.
// Attacker holds tiny amounts of each underlying.

// 1. For each deposit token, deposit 1 wei on behalf of the victim.
for (const dt of depositTokens) {
  const underlying = await ethers.getContractAt('IERC20', await dt.underlying())
  await underlying.connect(attacker).approve(dt.address, 1)
  await dt.connect(attacker).deposit(1, victim.address) // mints dust to victim
}

// Victim's list is now saturated:
expect(await pool.getDepositTokensOfAccount(victim.address))
  .to.have.lengthOf.at.least(depositTokens.length)

// 2. Any new-token interaction with the victim now reverts.
//    a) transfer of an msdToken the victim doesn't hold:
await expect(
  otherDepositToken.connect(holder).transfer(victim.address, 1)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')

//    b) deposit on behalf of the victim:
await expect(
  otherDepositToken.connect(attacker).deposit(1, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')

//    c) issuing a new synthetic (debt token not previously used):
await expect(
  newDebtToken.connect(victim).issue(amount, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')

// 3. Recovery: victim must transfer each dust balance out to free slots.
for (const dt of depositTokens) {
  await dt.connect(victim).transfer(attacker.address, await dt.balanceOf(victim.address))
}
```

Note: the exact saturation threshold depends on the number of registered deposit/debt tokens in the target pool's deployed configuration; the PoC requires enough distinct deposit tokens (or victim-held tokens) to reach `MAX_TOKENS_PER_USER = 30`.
