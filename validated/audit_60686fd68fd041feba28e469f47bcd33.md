### Title
`account_not_frozen_for_authority` does not block pending order execution or receivership actions after `ACCOUNT_FROZEN` is set, allowing frozen-account funds to be withdrawn - (File: `programs/marginfi/src/state/marginfi_account.rs`)

### Summary
`account_not_frozen_for_authority` only blocks a transaction when the *signer equals the account authority*, so any instruction that permits a non-authority signer (a keeper executing a resting order, or a liquidator during receivership) sails through the freeze check even while `ACCOUNT_FROZEN` is set. Because `is_signer_authorized` is called with `allow_receivership=true, allow_order=true` in `lending_account_withdraw`, funds can still be withdrawn from a frozen account through these paths after freeze, contradicting the freeze's stated purpose of blocking all authority-initiated value-moving actions.

### Finding Description
`account_not_frozen_for_authority` is defined as: [1](#0-0) 
It returns `false` (blocking) only when the account is frozen **and** the signer is the account's own `authority`. It does not consider whether the account is `ACCOUNT_IN_RECEIVERSHIP` or has active orders.

`lending_account_withdraw`'s account validation calls this check together with `is_signer_authorized(&a, g.admin, authority.key(), true, true)`: [2](#0-1) 
The doc comment on the `authority` field explicitly states: *"during receivership and order execution, there are no signer checks whatsoever: any key can repay as long as the invariants checked at the end of execution are met."* This means when the account is in receivership (mid-liquidation) or is fulfilling a previously placed order, the withdraw instruction's signer need not be the account authority — it can be a liquidator or order-filling keeper.

The `set_account_freeze` instruction toggles `ACCOUNT_FROZEN` independently of these other state flags: [3](#0-2) 
Its doc comment claims freezing blocks "the account authority... from major actions (borrow/deposit/withdraw/repay/transfer/etc.)" — implying a comprehensive freeze. However, if the account was already in receivership or had an outstanding order at the moment it becomes frozen, the withdraw path is reachable with a **non-authority signer** (liquidator/keeper), so `account_not_frozen_for_authority` returns `true` (not blocked), and `is_signer_authorized`'s permissive receivership/order branch also authorizes the non-authority signer. The freeze flag therefore has no effect on funds moving out of the account through these two channels.

The `LendingAccountLiquidate` accounts struct confirms the liquidatee side has *no* freeze check at all — only a receivership check — so a frozen account under active liquidation continues to be liquidated and have its liability/collateral balances mutated: [4](#0-3) 

### Impact Explanation
An account that is placed into receivership (mid-liquidation) or has resting limit orders, and is then frozen by the group admin (e.g., for fraud/compromise remediation), does not actually have its withdrawal capability halted for these two already-in-flight mechanisms. A keeper filling the resting order, or the liquidation engine processing the receivership, can still move real value out of the account after the freeze is applied, because the frozen check `account_not_frozen_for_authority` is authority-signer-specific and `is_signer_authorized`'s receivership/order override does not re-check the frozen flag. This directly undermines the freeze's purpose as a safety mechanism (e.g., during compromise/fraud response), producing unauthorized state mutation/value movement with financial effect on a frozen account, matching "High: unauthorized state mutation or bypass of safety freeze with financial effect."

### Likelihood Explanation
Preconditions: (1) the target account must already have `ACCOUNT_IN_RECEIVERSHIP` set (i.e., mid-liquidation) or an active resting order at the time it becomes frozen, and (2) the freeze must be applied by the admin during that window. Both `ACCOUNT_IN_RECEIVERSHIP` and order placement are reachable via normal, unprivileged instructions (`lending_account_liquidate`, `place_order`), so an attacker (the account authority, or a colluding liquidator/keeper) can deliberately create this race by placing an order or triggering their own receivership right before/around an anticipated freeze, or simply rely on the timing gap between an admin's freeze action and any pending keeper/liquidator transaction already in flight. This is a timing/state-machine gap rather than a purely theoretical issue, and is reproducible deterministically in a unit test that sets flags directly.

### Recommendation
Change the frozen check so that freeze fully blocks value-moving paths regardless of which key signs: e.g., have `account_not_frozen_for_authority` (or a new stricter freeze-check) return `false` whenever `ACCOUNT_FROZEN` is set, irrespective of the signer, for instructions that move value (`lending_account_withdraw`, `lending_account_borrow`, order execution/fill, liquidation of a frozen liquidatee). If admin/remediation actions must still be able to touch a frozen account, gate that exception explicitly on `signer == group.admin` rather than on "signer != authority," and re-validate the frozen flag inside the receivership/order-execution bypass branch of `is_signer_authorized` rather than skipping it entirely.

### Proof of Concept
Rust unit test plan (in `programs/marginfi/src/state/marginfi_account.rs` or an integration test):
1. Construct a `MarginfiAccount` with `authority = user_pk`, set `ACCOUNT_IN_RECEIVERSHIP` (or simulate an active order count > 0).
2. Set `ACCOUNT_FROZEN` via `set_flag`.
3. Assert `account_not_frozen_for_authority(&account, keeper_pk)` (where `keeper_pk != user_pk`) returns `true` — i.e., the freeze check does not block a non-authority signer.
4. Integration test: place an order for an account, freeze the account via `set_account_freeze`, then execute the order-fill/withdraw path with a keeper as `authority` signer; assert the withdrawal succeeds and token balances move despite `ACCOUNT_FROZEN` being set — expected (per invariant) to fail, but currently succeeds.
5. Similarly, drive an account into `ACCOUNT_IN_RECEIVERSHIP` via `lending_account_liquidate`, freeze it mid-liquidation, and confirm a subsequent liquidation step still mutates its balances.
6. Recommended assertion after fix: both scenarios should return `MarginfiError::AccountFrozen` and leave balances/flags unchanged.

```rust
pub fn set_account_freeze(ctx: Context<SetAccountFreeze>, frozen: bool) -> MarginfiResult {
    let group = ctx.accounts.group.load()?;
    check_eq!(
        group.admin,
        ctx.accounts.admin.key(),
        MarginfiError::Unauthorized
    );
    let mut marginfi_account = ctx.accounts.marginfi_account.load_mut()?;
    if frozen {
        marginfi_account.set_flag(ACCOUNT_FROZEN, true);
    } else {
        marginfi_account.unset_flag(ACCOUNT_FROZEN, true);
    }
    marginfi_account.last_update = Clock::get()?.unix_timestamp as u64;
```
