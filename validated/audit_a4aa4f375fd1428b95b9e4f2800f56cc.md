### Title
Unvalidated Offset Fields in `VerifyTransferProof` Precompile Cause Out-of-Bounds Array Access - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`PrecompiledContracts.VerifyTransferProof.execute()` reads three offset fields (`spendOffset`, `spendAuthSigOffset`, `receiveOffset`) from the fixed-length call-data buffer and uses them directly as source offsets into `System.arraycopy`/`parseInt`/`parseLong` calls, without ever validating that `offset (+ needed length)` stays within `data.length`. This mirrors the Golioth Pouch bug class: a size is validated once up-front (the fixed `data.length` check), but internal cursor/offset arithmetic used for subsequent copies is trusted without re-validation, letting attacker-controlled values run past the allocated/available buffer.

### Finding Description
`execute(byte[] data)` first checks `data.length` is one of `{2080, 2368, 2464, 2752}` [3](#0-2) . It then parses `spendOffset`, `spendAuthSigOffset`, and `receiveOffset` as raw 32-byte integers taken straight from `data` (attacker-controlled contract call data) [4](#0-3) . These offsets are then used verbatim to index into `data` via `parseInt(data, spendOffset)`, `parseInt(data, spendAuthSigOffset)`, `parseInt(data, receiveOffset)` and later in copy loops such as `System.arraycopy(data, spendOffset + 320 * i, nullifier[i], 0, 32)` [5](#0-4) . Only `spendCount`/`receiveCount` (the values *read* from those offsets) are range-checked (`1..2`); the offsets themselves are never checked against `data.length`, so a caller can set `spendOffset`/`spendAuthSigOffset`/`receiveOffset` to arbitrary values (even negative after overflow, or beyond the buffer), producing out-of-bounds array reads that throw uncaught `ArrayIndexOutOfBoundsException` (or similar) during opcode execution inside the TVM, reachable via a plain `CALL`/`STATICCALL` to this precompiled contract address from any contract, i.e. from any unprivileged transaction.

### Impact Explanation
An uncaught runtime exception thrown from a precompile invoked mid-VM-execution can propagate as an unexpected `Program.Exception`/`BytecodeExecutionException` outside the normal "revert" handling paths that the VM expects for contract-generated failures, risking inconsistent handling across full nodes vs. SR/validator nodes if the exception type is not uniformly caught by the VM's execute wrapper. At minimum this is a reliable, unauthenticated crash/DoS vector reachable through a single crafted transaction calling the `VerifyTransferProof` precompile address with a valid-length-but-malicious-offset payload — an unprivileged transaction broadcaster can trigger it without any special privileges, satisfying "node crash or halt" impact criteria.

### Likelihood Explanation
High likelihood: any address can call the precompiled contract directly (no special TRC20/shielded-contract deployment appears strictly required to reach `execute()` at the VM dispatch level, since precompiles are addressed by fixed address and invoked like any contract call), the length check only restricts total call-data size to one of 4 values, and the offset fields are fully attacker-controlled 32-byte words within that buffer — trivial to construct.

### Recommendation
Before using `spendOffset`, `spendAuthSigOffset`, and `receiveOffset` (and the subsequent `spendCount`/`receiveCount`-derived copy loops), validate that each offset plus the maximum bytes it will be used to read/copy (e.g., `offset + 32`, `offset + 320*spendCount`, etc.) does not exceed `data.length`, returning `Pair.of(true, DataWord.ZERO().getData())` on any bounds violation, consistent with the pattern already used for `SIZE` and `leafCount`/`TREE_WIDTH` checks elsewhere in the same class.

### Proof of Concept
1. Craft call data of exactly one of the valid lengths, e.g. 2080 bytes.
2. Set the 32-byte word at offset 0 (`spendOffset`) to a large value (e.g. `0xFFFFFFF0` or a value close to `Integer.MAX_VALUE`, or a value that when added to `320*i` overflows/exceeds `data.length`).
3. Set `spendAuthSigOffset` and `receiveOffset` words such that `parseInt(data, spendOffset)` yields a `spendCount` in `[1,2]` — reachable because `spendOffset` can point back into a crafted region containing a small valid count value while remaining copy loops (`spendOffset + 320*i`) run off the end of `data`.
4. Submit a transaction that `CALL`s the `VerifyTransferProof` precompiled contract address with this payload.
5. Observe `System.arraycopy(data, spendOffset + 320 * i, ...)` throwing `ArrayIndexOutOfBoundsException` during TVM execution.

Note: I was not able to fully verify from the index whether this uncaught exception is caught generically by the VM's top-level exception handler (in which case impact reduces to a reverted transaction) or propagates further; confirming this requires tracing `Program.callToPrecompiledAddress` and the VM's outer exception-handling wrapper (`VM.play`/`Program.Exception` hierarchy) in a full session, which the index does not fully expose.
