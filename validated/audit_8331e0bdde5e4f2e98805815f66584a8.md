### Title
Unbounded, unpaginated `DelegatedResourceAccountIndex` lookup allows cheap attacker-inflated delegation lists to cause DB/CPU exhaustion on every subsequent query - (File: `chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java`)

### Summary
The `GetDelegatedResourceAccountIndex`/`GetDelegatedResourceAccountIndexV2` API (reachable via anonymous gRPC and HTTP/JSON) takes only an address and returns the *entire* list of delegation relationships for that address with no offset/limit, unlike almost every other list-style API in the codebase (`GetPaginatedAssetIssueList`, `GetPaginatedExchangeList`, `GetPaginatedProposalList`, `GetPaginatedNowWitnessList`), which all enforce pagination. An account can cheaply inflate its own delegation-index entry by issuing many small `DelegateResourceContract` transactions to many distinct receiver addresses, and any anonymous API client can then repeatedly trigger the expensive, unbounded prefix-scan-and-sort lookup against that address, analogous to the Nextcloud circles "sharee recommendation" resource-exhaustion bug class (expensive relation enumeration with no cap, triggered repeatedly by any caller).

### Finding Description
`DelegatedResourceAccountIndexStore.getWithPrefix` performs two full prefix range scans (`prefixQuery`) over the `DelegatedResourceAccountIndex` column family — one for the FROM prefix and one for the TO prefix — collects all matching capsules into `ArrayList`s, and then sorts each list by timestamp before returning: [1](#0-0) 

This method is invoked, unconditionally and without any size cap, by `Wallet.getDelegatedResourceAccountIndex`/`getDelegatedResourceAccountIndexV2`: [2](#0-1) 

which in turn is exposed directly to anonymous callers through:
- the gRPC `GetDelegatedResourceAccountIndex`/`GetDelegatedResourceAccountIndexV2` RPCs, taking only a `BytesMessage` address [3](#0-2) 
- the unauthenticated HTTP servlet `/wallet/getdelegatedresourceaccountindex`, which simply forwards the address to `wallet.getDelegatedResourceAccountIndex` and prints the full result [4](#0-3) 
- the corresponding V2 servlet, identical pattern [5](#0-4) 

Unlike `GetAssetIssueList`, `ListExchanges`, and `ListProposals` (which all also lack pagination but reflect economically-bounded resource creation), this endpoint's underlying cost is driven purely by the *number of distinct FROM/TO relationships one account has created*, and creating a delegation relationship via `DelegateResourceActuator`/`DelegateResourceProcessor` is cheap: it only requires freezing a minimal TRX amount to a receiver address, and that frozen balance is later recoverable through unstaking — it is not burned like the asset-issue/exchange-create fees. An attacker can therefore delegate tiny amounts to a large number of distinct receiver addresses (each such transaction writes both a FROM-prefixed and a TO-prefixed `DelegatedResourceAccountIndexCapsule` entry) at comparatively low, largely recoverable cost, then have any anonymous client repeatedly query `getdelegatedresourceaccountindex` for that address to force the node into repeated full prefix scans and in-memory sorts, load proportional to the number of relationships created.

### Impact Explanation
Because the query endpoint requires no authentication or fee, and can be invoked repeatedly and in parallel against the same or many pre-inflated addresses, a moderately funded attacker can force sustained CPU and RocksDB/LevelDB I/O load on any full node, solidity node, or PBFT node servicing wallet queries (`FullNodeHttpApiService`, `HttpApiOnSolidityService`, `HttpApiOnPBFTService`, `RpcApiServiceOnSolidity`, `RpcApiServiceOnPBFT` all wire this same code path). This can degrade node responsiveness for legitimate API consumers, consistent with the CVE-2022-39330 bug class (DB/CPU resource exhaustion via unbounded relation enumeration).

### Likelihood Explanation
Likely exploitable by any account holder able to fund and sign a handful of `DelegateResourceContract` transactions to build up a large relationship set, followed by unauthenticated, unlimited repeated queries from any client (no login/permission required for the read path). The attack setup cost is moderate but largely recoverable (frozen TRX can later be unfrozen), unlike the burn-fee-based asset/exchange creation paths, making this the most attacker-favorable unpaginated list endpoint in the API surface.

### Recommendation
Add pagination (offset/limit) to `GetDelegatedResourceAccountIndex`/`GetDelegatedResourceAccountIndexV2` and to `DelegatedResourceAccountIndexStore.getWithPrefix`, mirroring the pattern already used for `GetPaginatedAssetIssueList`/`GetPaginatedExchangeList`/`GetPaginatedProposalList`. Additionally consider capping the maximum number of delegation relationships (FROM/TO) a single account may hold, or rate-limiting/costing repeated full-index queries at the API layer.

### Proof of Concept
1. Attacker account A funds and freezes/delegates minimal TRX (e.g., the protocol minimum) via `DelegateResourceContract` to N distinct receiver addresses (`DelegateResourceActuator`/`DelegateResourceProcessor`), creating N `DelegatedResourceAccountIndexCapsule` FROM-prefix entries for A and N TO-prefix entries scattered across N receivers.
2. Any anonymous client repeatedly issues `POST /wallet/getdelegatedresourceaccountindex {"value": "<A's address>"}` (or the equivalent gRPC `GetDelegatedResourceAccountIndex` call).
3. Each request triggers `DelegatedResourceAccountIndexStore.getWithPrefix`, which performs full prefix scans over up to N entries and sorts them, with cost scaling linearly (or worse) with N and no upper bound enforced by the API.
4. Repeating step 2 at high request volume drives sustained CPU/I/O load on the serving node.

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;

  public DelegatedResourceAccountIndex getDelegatedResourceAccountIndex(ByteString address) {
    if (address == null || address.size() != DecodeUtil.ADDRESS_SIZE / 2) {
      return DelegatedResourceAccountIndex.getDefaultInstance();
    }
    DelegatedResourceAccountIndexCapsule accountIndexCapsule =
        chainBaseManager.getDelegatedResourceAccountIndexStore().getIndex(address.toByteArray());
    if (accountIndexCapsule != null) {
      return accountIndexCapsule.getInstance();
    } else {
      return DelegatedResourceAccountIndex.getDefaultInstance();
    }
  }

  public DelegatedResourceAccountIndex getDelegatedResourceAccountIndexV2(ByteString address) {
    if (address == null || address.size() != DecodeUtil.ADDRESS_SIZE / 2) {
      return DelegatedResourceAccountIndex.getDefaultInstance();
    }
    DelegatedResourceAccountIndexCapsule accountIndexCapsule = chainBaseManager
        .getDelegatedResourceAccountIndexStore().getV2Index(address.toByteArray());
    if (accountIndexCapsule != null) {
      return accountIndexCapsule.getInstance();
    } else {
      return DelegatedResourceAccountIndex.getDefaultInstance();
    }
  }
