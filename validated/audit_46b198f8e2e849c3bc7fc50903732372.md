### Title
Pack-objects concurrency limiter is keyed only by remote IP, not per-user/per-repository, allowing cross-tenant denial of service - ([File: internal/gitaly/service/hook/pack_objects.go])

### Summary
The external report's bug class — a shared resource-tracking key (`usedNonces`) that is not scoped per unique actor, causing unrelated actors to collide and be denied service — maps onto Gitaly's `PackObjectsHookWithSidechannel` concurrency limiter. There, the limiting key used to throttle concurrent `git pack-objects` invocations is derived solely from the client's remote IP address, not from the combination of user and repository, even though the code comment claims otherwise.

### Finding Description
When Gitaly serves `git pack-objects` on behalf of a fetch/clone (via `PackObjectsHookWithSidechannel`), it optionally applies a concurrency limiter to protect the server from being overwhelmed. In `packObjectsHook`, the limiting key passed to `runPackObjectsLimited` is derived purely from the parsed remote IP address: [1](#0-0) 

That value flows straight into `ConcurrencyLimiter.Limit` as the sole key: [2](#0-1) 

The `TypePackObjects` limiter is documented as using "RemoteIP/Repository/User" as its limiting key, but the actual implementation only forwards the IP: [3](#0-2) 

Because the `ConcurrencyLimiter` maintains a separate semaphore per key (`limitsByKey`), all requests sharing the same key compete for the same limited concurrency slots and queue capacity: [4](#0-3) [5](#0-4) 

This is functionally analogous to the reported nonce bug: a shared tracking structure (`usedNonces` / `limitsByKey`) is keyed on a value (nonce / IP) that is not unique to the actor (wallet address / user+repository), so unrelated actors sharing that value interfere with each other.

### Impact Explanation
Any users or repositories whose traffic egresses through the same remote IP — for example clients behind NAT, corporate proxies, shared CI runners, or a load balancer that does not preserve per-client addressing — are forced to share a single concurrency slot pool for `pack-objects`. If `max_per_repo`/`max_queue_size` for the pack-objects limiter is small, one heavy but entirely unrelated user's fetch traffic from repo A can exhaust the queue and cause `ErrMaxQueueSize`/`ErrMaxQueueTime` rejections for a different user fetching a different, unrelated repo B, purely because they share an IP. This is an availability (DoS) issue reachable by an ordinary authenticated user performing normal fetch/clone operations — no privilege escalation or malicious peer behavior is required.

### Likelihood Explanation
The likelihood is moderate: it does not require any malicious action — everyday deployments with NAT gateways, corporate egress proxies, or shared build infrastructure would naturally produce many distinct users/repos sharing one remote IP. The pack-objects limiter is only exercised when `PackObjectsCache`/limiter is configured on the Gitaly node with a nonzero limit (`cfg.PackObjectsLimit`), so exposure is deployment-dependent, but the mismatch between the documented per-user/per-repo intent and the actual per-IP-only implementation is a clear implementation defect.

### Recommendation
Compose the limiting key from the IP address together with the user ID (`req.GetGlId()`) and repository (`req.GetRepository().GetRelativePath()`), matching the documented `TypePackObjects` semantics, so that concurrency limits are enforced per actor/repository rather than collectively per shared network address.

### Proof of Concept
1. Configure Gitaly with the pack-objects concurrency limiter enabled (`[pack_objects_limiting]` with a small `max_concurrency`/queue size).
2. Have two distinct, unrelated GitLab users, each fetching a different, unrelated repository, originate their requests through the same egress IP (e.g., both behind the same corporate NAT/proxy, or both via the same CI runner pool).
3. Have the first user issue several concurrent large fetches, saturating the per-IP queue governed by `limitkey` in `packObjectsHook`/`runPackObjectsLimited`.
4. Observe the second, unrelated user's fetch of a completely different repository fail with `ErrMaxQueueSize`/`ErrMaxQueueTime` (`structerr.NewResourceExhausted`), despite having no relationship to the first user's traffic — demonstrating the cross-tenant DoS caused by the non-unique (per-IP-only) limiting key.

Note: I could not fully trace how `cfg.PackObjectsLimit`/limiter enablement is wired end-to-end from `serve.go` within the available iterations, so exact production-default enablement status (on by default vs. opt-in) is not fully confirmed from the index; this would benefit from further investigation in a full Devin session if precise deployment-default behavior is needed.

func (s *server) runPackObjectsLimited(
	ctx context.Context,
	w io.Writer,
	limitkey string,
	req *gitalypb.PackObjectsHookWithSidechannelRequest,
	args *packObjectsArgs,
	stdin io.ReadCloser,
	key string,
) error {
	ctx = context.WithoutCancel(ctx)

	ctx, cancel := context.WithCancel(ctx)
	defer cancel()

	defer stdin.Close()

	if _, err := s.packObjectsLimiter.Limit(
		ctx,
		limitkey,
		func() (interface{}, error) {
			return nil,
				s.runPackObjectsFn(
					ctx,
					s.gitCmdFactory,
					w,
					req,
					args,
					stdin,
					key,
				)
		},
	); err != nil {
		return err
	}

	return nil
}

// ConcurrencyLimiter contains rate limiter state.
type ConcurrencyLimiter struct {
	// limit is the adaptive maximum number of concurrent calls to the limited function. This limit is
	// calculated adaptively from an outside calculator.
	limit *AdaptiveLimit
	// maxQueueLength is the maximum number of operations allowed to wait in a queued state.
	// This limit is global and applies before the concurrency limit. Subsequent incoming
	// operations will be rejected with an error immediately.
	maxQueueLength int
	// maxQueueWait is a time duration of an operation allowed to wait in the queue.
	maxQueueWait time.Duration
	// SetWaitTimeoutContext is a function for setting up timeout context. If this is nill, context.WithTimeout is
	// used. This function is for internal testing purpose only.
	SetWaitTimeoutContext func() context.Context

	// monitor is a monitor that will get notified of the state of concurrency-limited RPC
	// calls.
	monitor ConcurrencyMonitor

	m sync.RWMutex
	// limitsByKey tracks all concurrency limits per key. Its per-key entries are lazily created
	// and will get evicted once there are no concurrency-limited calls for any such key
	// anymore.
	limitsByKey map[string]*keyedConcurrencyLimiter
}

// getConcurrencyLimit retrieves the concurrency limit for the given key. If no such limiter exists
// it will be lazily constructed.
func (c *ConcurrencyLimiter) getConcurrencyLimit(limitingKey string) *keyedConcurrencyLimiter {
	c.m.Lock()
	defer c.m.Unlock()

	if c.limitsByKey[limitingKey] == nil {
		// Set up the queue tokens in case a maximum queue length was requested. As the
		// queue tokens are kept during the whole lifetime of the concurrency-limited
		// function we add the concurrency tokens to the number of available token.
		var queueTokens semaphorer
		if c.maxQueueLength > 0 {
			queueTokens = c.createSemaphore(uint(c.currentLimit() + c.maxQueueLength))
		}

		c.limitsByKey[limitingKey] = &keyedConcurrencyLimiter{
			monitor:               c.monitor,
			maxQueueWait:          c.maxQueueWait,
			setWaitTimeoutContext: c.SetWaitTimeoutContext,
			concurrencyTokens:     c.createSemaphore(uint(c.currentLimit())),
			queueTokens:           queueTokens,
		}
	}

	c.limitsByKey[limitingKey].refcount++

	return c.limitsByKey[limitingKey]
}
