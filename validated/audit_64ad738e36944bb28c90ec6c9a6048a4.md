### Title
Unbounded growth of `DelegatedResourceAccountIndex.toAccounts`/`fromAccounts` via repeated `DelegateResourceContract`/legacy delegated `FreezeBalanceContract` calls leads to oversized capsule and API/serialization DoS - (File: chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java)

### Summary
`DelegatedResourceAccountIndexCapsule` stores, per account, an ever-growing `repeated bytes to_accounts` / `repeated bytes from_accounts` list of every distinct counterparty address it has ever delegated resources to or received a delegation from. Neither `DelegateResourceActuator`, `FreezeBalanceActuator`'s legacy delegation path, `DelegateResourceProcessor` (TVM native contract), nor `DelegatedResourceAccountIndexStore` enforce any maximum count on this list, unlike sibling structures (`AccountPermissionUpdateActuator` caps keys/actives, `VoteWitnessActuator` caps votes at `MAX_VOTE_NUMBER`, `AssetIssueActuator` caps `frozen_supply`). Any account owner can trigger unbounded growth of this list by delegating tiny amounts (as low as 1 TRX, `TRX_PRECISION`) of frozen bandwidth/energy to a large number of distinct freshly-created receiver addresses, or by receiving delegations from many distinct senders.

### Finding Description
In `DelegateResourceActuator.delegateResource()` [1](#0-0)  and the legacy path in `FreezeBalanceActuator.delegateResource()` [2](#0-1) , every call to `addToAccount`/`addFromAccount` on `DelegatedResourceAccountIndexCapsule` unconditionally appends a new distinct address, with no upper bound check anywhere in `validate()`. The `DelegateResourceProcessor` used by the TVM `delegateResource` opcode has the same property [3](#0-2) .

The only cost to grow this list is:
1. Freezing/holding at least `TRX_PRECISION` (1 TRX) worth of bandwidth or energy, checked in `DelegateResourceActuator.validate()` [4](#0-3) .
2. Creating a fresh receiver account for each entry (a `TransferContract`/`AccountCreateContract` costs bandwidth/energy but no explicit fee beyond resource consumption), or accepting resource from many distinct senders (no consent required from the receiver at all — `DelegateResourceActuator` never checks that the receiver authorized incoming delegation).

An attacker can therefore drive the `to_accounts`/`from_accounts` list of a single `DelegatedResourceAccountIndexCapsule` to an arbitrarily large size across many transactions. This capsule is read wholesale (not paginated) by:
- `DelegatedResourceAccountIndexStore.getIndex()`/`getWithPrefix()`, which materializes the *entire* list into memory and sorts it every time it's queried [5](#0-4) .
- `Wallet.getDelegatedResourceAccountIndex`/`getDelegatedResourceAccountIndexV2` gRPC/HTTP API endpoints, which any unauthenticated client can call for any address and which serialize/return the whole unbounded protobuf message, as exercised in `RpcApiServicesTest.testGetDelegatedResourceAccountIndex` [6](#0-5) .
- The convert-on-first-touch path `DelegatedResourceAccountIndexStore.convert()`, which iterates the entire legacy list on the very next delegate/undelegate/freeze call for that address [7](#0-6) , causing the cost of the attack to be paid again by every subsequent legitimate delegator interacting with the account.

This mirrors the CVE-2026-55996 bug class: no cap on a repeated/list field that legitimate unauthenticated (or low-privileged) requests keep appending to, until the resulting oversized message causes downstream consumers (TLS handshake for SAN stuffing; here, protobuf serialization/gRPC-HTTP response, `convert()` iteration cost, and DB record size) to fail or become prohibitively expensive.

### Impact Explanation
An attacker can grow a target account's delegated-resource index list to an unbounded size (bounded only by how many cheap accounts/transactions the attacker is willing to pay bandwidth/energy for). This can:
- Cause `getDelegatedResourceAccountIndex`/`V2` API calls against that address to return oversized responses or fail on protobuf/gRPC message-size limits, denying legitimate wallets/exchanges the ability to query delegation state for that account (API the node can no longer serve).
- Force a large, expensive one-time `convert()` migration cost onto the *next* victim account owner who performs any delegate/undelegate/freeze operation involving that inflated index, since `convert()` is triggered lazily and unconditionally re-plays every historical entry.
- Bloat the underlying LevelDB/RocksDB record for that key indefinitely, since there is no compaction, expiry, or cap logic removing stale entries (removal only happens when the corresponding `DelegatedResourceCapsule` balance drops to exactly zero).

### Likelihood Explanation
High reachability: `DelegateResourceContract` and legacy delegated `FreezeBalanceContract` are ordinary broadcastable transactions requiring only a funded account and a minimal (1 TRX) frozen balance per new distinct counterparty; the TVM `delegateResource` opcode provides an equivalent path from any smart contract. No committee/administrator gating exists (`supportDR()`/`supportUnfreezeDelay()` are chain-wide feature flags, not per-attacker permissions). The receiver-side `from_accounts` list can be inflated without any cooperation or consent from the victim receiver at all.

### Recommendation
Enforce a maximum count (analogous to `MAX_VOTE_NUMBER` for votes, `getTotalSignNum()` for permission keys, and `getMaxFrozenSupplyNumber()` for frozen supply) on the number of distinct entries permitted in `DelegatedResourceAccountIndexCapsule.to_accounts`/`from_accounts`, enforced in `DelegateResourceActuator.validate()`, `FreezeBalanceActuator.validate()`, and `DelegateResourceProcessor.validate()` before appending a new distinct address. Additionally, consider paginating `getDelegatedResourceAccountIndex`/`V2` API responses and bounding the work done in `DelegatedResourceAccountIndexStore.convert()`.

### Proof of Concept
1. Attacker account `A` freezes bandwidth (`FreezeBalanceContract`, legacy pre-optimization mode, or `FreezeBalanceV2Contract` + `DelegateResourceContract` in the current model) with balance ≥ 1 TRX (`TRX_PRECISION`).
2. Attacker generates N fresh receiver addresses `R1..RN` (creating minimal accounts for each, e.g. via a tiny `TransferContract`).
3. For each `Ri`, attacker broadcasts a `DelegateResourceContract{owner=A, receiver=Ri, balance=1_000_000 (1 TRX)}`. Each call appends `Ri` to `A`'s `to_accounts` list unconditionally, as in `DelegateResourceActuator.delegateResource()` [8](#0-7) ; no validate-time check limits N.
4. Repeat for large N (e.g., tens of thousands); each transaction costs only bandwidth/energy, no protocol-level cap rejects it (contrast with `VoteWitnessActuator.validate()`'s explicit `MAX_VOTE_NUMBER` check).
5. Query `getDelegatedResourceAccountIndexV2(A)` via gRPC/HTTP: the full inflated list is serialized and returned, demonstrating unbounded response growth; simultaneously, any subsequent `DelegateResourceActuator`/`FreezeBalanceActuator`/`UnDelegateResourceActuator` operation touching account `A` (in legacy mode) triggers `DelegatedResourceAccountIndexStore.convert(A)`, which now must replay all N historical entries in a single execution, inflating that transaction's real processing cost with no corresponding energy/bandwidth accounting for the replay work.

  public void convert(byte[] address) {
    DelegatedResourceAccountIndexCapsule indexCapsule = this.get(address);
    if (indexCapsule == null) {
      // convert complete or have no delegate
      return;
    }
    // convert old data
    List<ByteString> toList = indexCapsule.getToAccountsList();
    for (int i = 0; i < toList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(address, toList.get(i).toByteArray(), i + 1L);
    }

    List<ByteString> fromList = indexCapsule.getFromAccountsList();
    for (int i = 0; i < fromList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(fromList.get(i).toByteArray(), address, i + 1L);
    }
    this.delete(address);
  }

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }
