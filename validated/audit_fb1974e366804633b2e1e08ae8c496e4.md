The Fraxlend report describes an application-level (Solidity contract) design flaw: a whitelisted user can pick a `_name`/`_configData` to compute the same `CREATE2` salt as a pending "public" pair deployment and front-run it, causing the honest deployment to revert due to `deployedPairsBySalt`/`deployedPairsByName` uniqueness checks in `FraxlendPairDeployer._deployFirst`/`_deploySecond`. This is a smart-contract salt-management/anti-front-running design issue specific to the Fraxlend periphery contract, not a flaw in the EVM's `CREATE2` opcode semantics.

Checking the in-scope Geth EVM implementation of `CREATE2`/`CREATE` collision handling in `core/vm/evm.go`, the collision check correctly follows EIP-1014/EIP-684 semantics: an address is treated as colliding only if it has non-zero nonce or non-empty code, and any pre-existing collision causes the frame to halt with `ErrContractAddressCollision`, consuming the caller's gas but leaving state untouched otherwise. [1](#0-0) 
This deterministic collision-rejection behavior is intentional, spec-compliant, and identical to how every other client computes `CREATE2` addresses and detects collisions — it does not create a consensus divergence, incorrect gas charge, unauthorized ETH/code/nonce change, or a state/persistence mismatch. The "griefing via colliding salt" scenario is purely a consequence of how an application (Fraxlend) chooses its salts and defends its deployment uniqueness, not a bug in Geth's core CREATE/CREATE2 handling.
