### Title
Uninitialized `accountIndexOf` lets depositors accrue rewards equal to their entire token balance when the global index is still `INITIAL_INDEX` - (File: contracts/RewardsDistributor.sol)

### Summary
The bug class is use-after-free; the closest reachable analog in Metronome is use of an uninitialized/stale index. In `RewardsDistributor._calculateTokenDelta`, when an account has no stored `accountIndexOf[token][account]` (i.e. the index entry was never written — the "freed"/default state), the code only snaps it to `INITIAL_INDEX` if the current token index is strictly greater than `INITIAL_INDEX`. When the token index equals `INITIAL_INDEX` (the period right after a reward token is activated, before any time has elapsed), `_accountIndex` stays `0`, so `_deltaIndex = INITIAL_INDEX = 1e18` and the account accrues `balanceOf(account) * 1` reward tokens — a full-balance reward for zero elapsed time. [1](#0-0) 

### Finding Description
`tokenStates[token_]` is initialized with `index = INITIAL_INDEX` (1e18) when the governor first sets a non-zero speed via `_updateTokenSpeed`: [2](#0-1) 

While `tokenStates[token_].index == INITIAL_INDEX` (same block/tx window after activation, since `_calculateTokenIndex` only grows the index when `block.timestamp - timestamp > 0`), any call that touches `_updateTokensAccruedOf` — `updateBeforeMintOrBurn` (invoked on every DepositToken mint / DebtToken issue), `updateBeforeTransfer`, or `claimRewards` — computes:

- `_tokenIndex = INITIAL_INDEX`
- `_accountIndex = accountIndexOf[token][account] == 0`
- guard `_accountIndex == 0 && _tokenIndex > INITIAL_INDEX` is **false**, so `_accountIndex` remains `0`
- `_deltaIndex = 1e18 - 0 = 1e18`
- `_tokensDelta = balance.wadMul(1e18) = balance`

The account's `tokensAccruedOf` is credited with an amount equal to its full deposit/debt token balance, and `accountIndexOf` is then written as `INITIAL_INDEX`, so the inflated accrual persists and can be claimed in any later block. [3](#0-2) 

`claimRewards` is permissionless and pays out `tokensAccruedOf` up to the distributor's `rewardToken` balance: [4](#0-3) 

### Impact Explanation
Direct theft of unclaimed yield. An attacker who holds or acquires a DepositToken/DebtToken balance in the activation block is credited reward tokens equal to that balance without any accrual period, then calls `claimRewards` to drain the distributor's `rewardToken` holdings. The reward-accrual invariant (rewards = balance × index growth) is broken because a never-written `accountIndexOf` is treated as index `0` rather than `INITIAL_INDEX`.

### Likelihood Explanation
Requires no privileged role: the attacker is an ordinary depositor. The exploit window is the block in which `updateTokenSpeed`/`syncTokenSpeed` first activates a token's index (`index == INITIAL_INDEX`, timestamp delta `0`). Governor/keeper speed-update transactions are visible in the mempool, so an attacker can back-run them in the same block (e.g., via a bundle on mainnet or sequencing on an L2): deposit collateral to mint DepositToken (triggering `updateBeforeMintOrBurn`, which writes the inflated `tokensAccruedOf`), then claim later. A pre-existing balance at activation also works — the first `updateBeforeTransfer`/`updateBeforeMintOrBurn`/`claimRewards` touching that account inside the same timestamp window books the full-balance delta. `nonReentrant` on `claimRewards` does not help because the bad accrual is written by the token hooks, and `claimRewards` itself can be front-run-safe since the accrual is stored.

### Recommendation
In `_calculateTokenDelta`, default a missing account index to the current index (or `INITIAL_INDEX`) whenever it is `0`, not only when `_tokenIndex > INITIAL_INDEX`:

```solidity
if (_accountIndex == 0) {
    _accountIndex = _tokenIndex > INITIAL_INDEX ? INITIAL_INDEX : _tokenIndex;
}
```

Equivalently, initialize `accountIndexOf` to `INITIAL_INDEX` on first interaction. Add a regression test that mints deposit tokens in the same block the token speed is activated and asserts zero claimable rewards.

### Proof of Concept
Hardhat fork/test sketch against deployed `RewardsDistributor`:

```solidity
// Assume governor tx in block N calls updateTokenSpeed(depositToken, speed>0)
// -> tokenStates[depositToken] = {index: INITIAL_INDEX (1e18), timestamp: N}

// Attacker (same block N, back-running the governor tx):
underlying.approve(address(pool), amount);
pool.deposit(depositToken, amount);          // DepositToken.mint -> updateBeforeMintOrBurn
// _calculateTokenDelta: tokenIndex == 1e18, accountIndex == 0 -> guard fails
// tokensDelta = balance * 1e18 / 1e18 == amount  (asserted below)

assertEq(distributor.tokensAccruedOf(attacker), attackerDepositBalance);

// Any later block:
address[] memory accts = new address[](1); accts[0] = attacker;
distributor.claimRewards(accts, distributor.tokens());
// rewardToken.balanceOf(attacker) == min(tokensAccruedOf, distributor balance)
assertGt(rewardToken.balanceOf(attacker), 0); // stolen yield == full deposit balance
```

    function _calculateTokenDelta(
        TokenState memory _tokenState,
        IERC20 token_,
        address account_
    ) private view returns (uint256 _tokenIndex, uint256 _tokensDelta) {
        _tokenIndex = _tokenState.index;
        uint256 _accountIndex = accountIndexOf[token_][account_];

        if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
            _accountIndex = INITIAL_INDEX;
        }

        uint256 _deltaIndex = _tokenIndex - _accountIndex;
        _tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
    }
