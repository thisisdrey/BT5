### Title
`accountIndexOf == 0` used as "unset" sentinel lets a same-block user accrue rewards equal to their entire token balance - (File: contracts/RewardsDistributor.sol)

### Summary
`RewardsDistributor` uses `accountIndexOf[token][account] == 0` as a sentinel for "account index not yet initialized", and only substitutes `INITIAL_INDEX` (1e18) when the global token index is strictly greater than `INITIAL_INDEX`. When the global index still equals `INITIAL_INDEX` — which is true in the block in which the reward speed is first set, or while the token has zero supply — the sentinel check falls through, `_deltaIndex` is computed as `INITIAL_INDEX - 0 = 1e18`, and `wadMul` credits the account with `balance * 1` reward-token units, effectively stealing the reward pool. This is the same bug class as the WAuraPools report: overloading a stored value (here `0`, there `type(uint).max`) to mean "unset" produces incorrect reward-per-share accounting.

### Finding Description
In `_calculateTokenDelta` the unset-account sentinel is handled incorrectly at the boundary value:

```solidity
// contracts/RewardsDistributor.sol:222-231
_tokenIndex = _tokenState.index;
uint256 _accountIndex = accountIndexOf[token_][account_];

if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}

uint256 _deltaIndex = _tokenIndex - _accountIndex;
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
```

When a token is first registered for rewards, `_updateTokenSpeed` writes `TokenState({index: INITIAL_INDEX, timestamp: block.timestamp})` and pushes the token (lines 296-299). The index only advances inside `_calculateTokenIndex`/`_updateTokenIndex` when a positive `elapsed` time has passed and `totalSupply() > 0`. Consequently, for every account that already holds `token_` while `tokenStates[token_].index == INITIAL_INDEX`:

- `accountIndexOf == 0` (never accrued),
- the guard `_tokenIndex > INITIAL_INDEX` is false, so `_accountIndex` stays `0`,
- `_deltaIndex = 1e18 - 0 = 1e18`,
- `_tokensDelta = balance * 1e18 * 1e-18 = balance`.

`_updateTokensAccruedOf` then stores this full-balance delta into `tokensAccruedOf[account_]` (lines 261-265), and `claimRewards`/`_transferRewardIfEnoughTokens` pays it out from the distributor's `rewardToken` balance (lines 248-255).

### Impact Explanation
An attacker holding the reward-tracked token (DepositToken or DebtToken) can force `updateBeforeMintOrBurn`/`updateBeforeTransfer`/`claimRewards` to run while the stored index is still exactly `INITIAL_INDEX` — i.e., in the same block/timestamp as the `updateTokenSpeed` call that registers the token (front-running via bundle/sequencer ordering on L2, or when the token's supply is 0 at registration and the attacker becomes the first holder while index has not advanced). Each account so touched accrues `balance` units of `rewardToken`, draining all unclaimed yield and the distributor's reward balance — direct theft of rewards owed to other users. The payout is only capped by the contract's `rewardToken` balance.

### Likelihood Explanation
- Reachable entirely through public entry points (`claimRewards`, token `transfer`, deposit/mint paths) by an unprivileged account that legitimately holds the tracked token.
- Requires a timing edge: index must still equal `INITIAL_INDEX` when the attacker accrues. This occurs deterministically for transactions sharing the same `block.timestamp` as the `updateTokenSpeed`/`addToken` transaction (same-block inclusion on L2s such as Base/Optimism/Hemi where Metronome is deployed), and whenever a token is registered while its `totalSupply` is 0 and rewards are claimed before the index can advance.
- The deployed `RewardsDistributor` (VERSION 1.3.2) contains this exact logic; no modifier prevents it, and `_transferRewardIfEnoughTokens` silently performs the payout whenever the distributor holds enough reward tokens.
- Likelihood is moderate: it depends on the same-block/timestamp window or the zero-supply registration ordering, but it needs no privileged role and is repeatable per account.

### Recommendation
Do not overload `accountIndexOf == 0` as an unset flag. Either store an explicit per-account `initialized` boolean and always substitute `INITIAL_INDEX` for uninitialized accounts regardless of the global index value, or clamp the accrual so that `_accountIndex` defaults to `min(_tokenIndex, INITIAL_INDEX)` when it is `0` (i.e., use `INITIAL_INDEX` whenever `_tokenIndex >= INITIAL_INDEX`, and `_tokenIndex` otherwise). Additionally, when registering a new reward token, snapshot `totalSupply()`/holders' first-touch via `updateBeforeMintOrBurn` semantics so no account can accrue a `1e18` delta.

### Proof of Concept
Foundry/Hardhat test sketch (production `RewardsDistributor`, no mocks needed beyond a registered ERC20-like deposit token whose `balanceOf`/`totalSupply` the pool uses):

```solidity
// Assume: depositToken already has `attacker` balance = 1000e18, totalSupply > 0.
// governor calls updateTokenSpeed(depositToken, 1e18) in block N.
// In the SAME block N (same timestamp), attacker calls:
rewardsDistributor.claimRewards(attacker, tokens); // or depositToken.transfer(...)
// Inside _updateTokensAccruedOf:
//   _updateTokenIndex: elapsed = 0  -> index stays INITIAL_INDEX (1e18)
//   _calculateTokenDelta:
//      accountIndex = 0; tokenIndex = 1e18 (not > INITIAL_INDEX)
//      deltaIndex = 1e18; tokensDelta = 1000e18.wadMul(1e18) = 1000e18
//   tokensAccruedOf[attacker] += 1000e18
// _transferRewardIfEnoughTokens pays min(1000e18, rewardToken.balanceOf(distributor))
assertEq(rewardToken.balanceOf(attacker), 1000e18); // stolen yield
```

Note: I was unable to inspect the exact body of `_calculateTokenIndex` and the ordering inside `updateBeforeMintOrBurn` within the available context; the finding assumes the standard Compound-style ordering (index update, then account accrual) as indicated by `_updateTokenSpeed` (lines 287-300) and `_updateTokensAccruedOf` (lines 261-266). If `_calculateTokenIndex` writes an index `> INITIAL_INDEX` even at `elapsed == 0`, the exploitable window narrows to the zero-`totalSupply` registration case.
