Audit Report

## Title
Non-conforming ERC20 `transfer` return value causes silent double-credit of pooled custody balance in `ERC20Transactor` - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

## Summary
`ERC20Transactor::deposit_asset_with_surplus` and `withdraw_asset_with_surplus` execute a real, state-mutating ERC20 `transfer` via `pallet_revive::Pallet::<T>::bare_call` and then classify success solely by whether the returned bytes ABI-decode as `bool` [1](#0-0) [2](#0-1) . A contract whose `transfer` mutates real balances (e.g. via `_update`) but returns non-bool data (such as `MyTokenFake`, which returns a `uint256`) causes the runtime-side accounting to treat an on-chain-successful transfer as a failure, desynchronizing the XCM holding register from the actual ERC20 ledger.

## Finding Description
`deposit_asset_with_surplus` transfers real tokens from the pooled `TransfersCheckingAccount` to the beneficiary before checking the result [3](#0-2) . If the call does not revert but `IERC20::transferCall::abi_decode_returns_validate` fails to decode a valid `bool`, the function returns `Err((what, XcmError::FailedToTransactAsset(...)))`, i.e. it tells the caller the assets are still in `what` (the holding register) even though the on-chain `_update`/balance mutation already occurred [4](#0-3) . The fixture `MyTokenFake.transfer` demonstrates this exact behavior: it calls `_transfer`/`_update` (a real balance mutation) and returns an arbitrary `uint256` instead of `bool` [5](#0-4) , and the runtime's own test confirms the resulting XCM `execute` call fails/errors despite the underlying transfer executing [6](#0-5) .

I verified the generic XCM executor trap/claim machinery independently corroborates the exploit path described in the claim: when `deposit_asset_with_surplus` returns `Err`, the unspent `AssetsInHolding` remain in the holding register, and `XcmExecutor::post_process` traps any non-empty holding via `Config::AssetTrap::drop_assets`, emitting `AssetsTrapped` [7](#0-6) . Trapped assets are later claimable via `pallet_xcm`'s `ClaimAssets` implementation, which re-mints the asset from the trap and deposits it again by re-invoking `AssetTransactor::mint_asset`/`deposit_asset` for the claimer [8](#0-7) . This generic mechanism, combined with `deposit_asset_with_surplus`'s incorrect "not deposited" classification of an already-executed transfer, means a second real ERC20 `transfer` call from the same `TransfersCheckingAccount` is triggered for the same nominal amount — a genuine double-payout from a value perspective, at the expense of the shared checking-account balance backing all other holders of that asset id.

The same decode-driven success/failure classification exists symmetrically in `withdraw_asset_with_surplus` [9](#0-8) .

## Impact Explanation
This is a duplicate-settlement / theft-from-shared-custody issue: `TransfersCheckingAccount` is a single account used for all ERC20 XCM asset movements of a given asset id, so a decode-classification bug for one non-conforming ERC20 contract can drain value belonging to other users' balances routed through the same checking account. This matches the "theft or unbacked mint or unlock" / "duplicate settlement or payout" impact categories.

## Likelihood Explanation
The precondition — an ERC20 contract whose `transfer` mutates state but returns non-bool/undecodable data — is a known real-world non-conformance pattern, and the repository's own fixture (`MyTokenFake`) and test (`smart_contract_does_not_return_bool_fails`) demonstrate the exact "mutation succeeds, decode fails" condition is reachable purely through public XCM `execute`/reserve-transfer entry points, with no privileged actor required. Whether such a contract can actually be registered as a `Matcher`-recognized asset id (i.e., whether AssetHub's production configuration restricts this to an allowlist) was not verified in the available code; if only vetted/allowlisted ERC20 contracts can be routed through this transactor, likelihood is reduced accordingly, but no such allowlist was found in the reviewed transactor code itself.

## Recommendation
Do not rely solely on ABI-decoded boolean return values to gate `AssetsInHolding` accounting after a non-reverted call. Verify the actual ERC20 balance delta (`balanceOf` before/after) to determine whether the transfer truly happened, and only trap/refund `what` when the transfer is confirmed not to have moved funds. Consider adopting a `SafeERC20`-style tolerant-but-verified pattern, and/or restrict `TransfersCheckingAccount`-based ERC20 transacting to an allowlist of known-conforming tokens given the shared-custody design.

## Proof of Concept
1. Deploy `MyTokenFake` (or an equivalent contract) whose `transfer` performs a real balance mutation but returns non-bool data, as already present in the fixtures [5](#0-4) .
2. Register it as a `Matcher`-recognized fungible asset and fund `TransfersCheckingAccount`, mirroring the existing test setup [10](#0-9) .
3. Submit an XCM `deposit_asset` for this token; `deposit_asset_with_surplus` performs the real transfer but returns `Err((what, ...))` due to decode failure [11](#0-10) .
4. Observe `AssetsTrapped` emitted by `post_process`/`drop_assets` [7](#0-6)  and confirm the on-chain ERC20 balance already moved.
5. Call `pallet_xcm::claim_assets` for the trapped amount, triggering `ClaimAssets::claim_assets` to re-mint and re-deposit, causing a second real `transfer` from `TransfersCheckingAccount` [8](#0-7) .
6. Confirm the beneficiary received two transfers for one logical deposit while `TransfersCheckingAccount`'s real balance was debited twice.

impl<T: Config> ClaimAssets for Pallet<T> {
	fn claim_assets(
		origin: &Location,
		ticket: &Location,
		assets: &Assets,
		context: &XcmContext,
	) -> Option<AssetsInHolding> {
		let mut versioned = VersionedAssets::from(assets.clone());
		match ticket.unpack() {
			(0, [GeneralIndex(i)]) => {
				versioned = match versioned.into_version(*i as u32) {
					Ok(v) => v,
					Err(()) => return None,
				}
			},
			(0, []) => (),
			_ => return None,
		};
		let hash = BlakeTwo256::hash_of(&(origin.clone(), versioned.clone()));
		match AssetTraps::<T>::get(hash) {
			0 => return None,
			1 => AssetTraps::<T>::remove(hash),
			n => AssetTraps::<T>::insert(hash, n - 1),
		}
		let mut claimed = AssetsInHolding::new();
		for asset in assets.inner() {
			match <T::XcmExecutor as XcmAssetTransfers>::AssetTransactor::mint_asset(asset, context)
			{
				Ok(minted) => {
					// SAFETY: Any fungible imbalances are now effectively duplicated because they
					// were not resolved when the asset was trapped (so total issuance tracks
					// trapped assets too), and now a duplicate asset was just minted.
					// To balance the system and keep total issuance constant, we drop and resolve
					// one of the duplicates. As a result, total issuance doesn't change.
					//
					// Note: This may emit Burned/Minted events even though the net issuance change
					// is zero. The mint creates a +X imbalance, and dropping the clone resolves -X,
					// resulting in no net change but potentially two events. This is an acceptable
					// tradeoff for the asset trap/claim mechanism.
					minted.fungible.iter().for_each(|(_, imbalance)| {
						let to_resolve = imbalance.unsafe_clone();
						core::mem::drop(to_resolve);
					});
					claimed.subsume_assets(minted)
				},
				Err(error) => tracing::debug!(
					target: "xcm::pallet_xcm::claim_assets",
					?asset, ?error, "Asset claimed from trap but unable to mint."
				),
			}
		}
		Self::deposit_event(Event::AssetsClaimed {
			hash,
			origin: origin.clone(),
			assets: versioned,
		});
		Some(claimed)
	}
