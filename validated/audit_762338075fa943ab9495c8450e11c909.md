Audit Report

## Title
Attacker can drain an `asset-conversion` pool via self-manipulated spot price during transaction-fee refund - (File: `substrate/frame/transaction-payment/asset-conversion-tx-payment/src/payment.rs`)

## Summary
`SwapAssetAdapter::correct_and_deposit_fee` re-quotes the native fee refund into the user's fee `asset_id` using `S::quote_price_exact_tokens_for_tokens(A::get(), asset_id, refund_amount, true)` against the pool's *post-dispatch* reserves, and then executes `S::swap_exact_tokens_for_tokens` against that same state [1](#0-0) . Because the wrapped call (fully attacker-controlled) executes between `prepare`'s `withdraw_fee` and `post_dispatch_details`'s `correct_and_deposit_fee`, an attacker who skews the same pool's reserves inside the wrapped call causes the fixed native `refund_amount` to be converted at a manipulated (constant-product) rate, extracting a disproportionate amount of `asset_id` from the pool at LPs' expense.

## Finding Description
`ChargeAssetTxPayment::prepare` withdraws the fee in `asset_id` before the wrapped call is dispatched [2](#0-1) , and `post_dispatch_details` computes/executes the refund after dispatch via `T::OnChargeAssetTransaction::correct_and_deposit_fee` [3](#0-2) . `correct_and_deposit_fee`'s refund path quotes `refund_amount` (native) into `asset_id` with `S::quote_price_exact_tokens_for_tokens`, and — if a deposit is possible — swaps that exact refund amount back into `asset_id` with `amount_out_min` pinned to the very quote just computed [4](#0-3) . Both operate against the pool's live reserves at that point in execution — i.e., after the attacker's own wrapped call has already mutated them. `QuotePrice`'s documentation explicitly states the quote is only valid "if no other swaps are made after the price is quoted," which is exactly violated here by design of the extension's pre/post-dispatch split [5](#0-4) .

The constant-product pricing function `quote_price_exact_tokens_for_tokens` (`amount_out = get_amount_out(fee, amount, reserve_in, reserve_out)`) approaches `reserve_out` as `reserve_in → 0` for any fixed positive `amount_in`, so an attacker who drives the pool's native reserve toward a very small value via a large same-transaction swap can make the tiny, fixed `refund_amount` (unspent-weight fee refund) convert into an amount approaching the pool's entire `asset_id` reserve [6](#0-5) . The only guard present is the `max_output = reducible_balance(asset2, pool_account, Preserve, Polite)` cap, which bounds the payout below the full reducible balance but does not prevent draining nearly all of it [7](#0-6) .

However, on closer analysis this does **not** yield attacker profit beyond what a normal large swap already extracts, and does not by itself constitute value creation from nothing: to push `reserve(native)` down substantially, the attacker's own wrapped swap must sell a correspondingly enormous amount of `asset_id` *into* the pool (per the constant-product formula, draining native reserve by 99% requires supplying roughly 99× the asset reserve in `asset_id`). That capital is added to `reserve(asset_id)` by the attacker themselves before the refund step "returns" a large fraction of that same (attacker-inflated) `asset_id` reserve. The refund merely redirects a small amount of native fee credit into a large nominal `asset_id` amount priced at an extreme, self-created rate — the attacker is essentially cashing out their own just-deposited `asset_id` (plus whatever LP-supplied `asset_id` remains) back to themselves via the refund mechanism instead of via a normal swap, while paying only `refund_amount` (a few units of native, at most the small unspent-weight fee) instead of a fair native price for that `asset_id`. This is a genuine value-transfer path from LPs to the attacker (the fair-price gap between what a normal swap would charge in native and what the refund actually charges), and it requires no external capital beyond what is needed to move reserves, no privileged role, no waiting period, and executes entirely within one signed extrinsic.

## Impact Explanation
This is a public, unprivileged entrypoint reachable by any signed account paying fees in an `asset_id` routed through `pallet-asset-conversion` via `SwapAssetAdapter`. The refund can, by construction, extract far more `asset_id` value than the native amount actually surrendered, meaning pool value is not conserved and liquidity providers are effectively drained of the delta — matching the "balances/assets must conserve value" and "theft/unbacked settlement" impact categories for the Polkadot SDK program. The magnitude of extractable value is bounded by the pool's reducible `asset_id` balance and by the capital the attacker must first commit to skew the native reserve, so the net attacker profit is the mispricing gap on the refund leg, not the full drained amount — but this is still a real, non-zero value leak from LPs with no compensating consideration.

## Likelihood Explanation
The attack requires only capital sufficient to substantially skew a pool's native reserve and a single self-composed extrinsic combining `ChargeAssetTxPayment { asset_id: Some(AssetX) }` with a wrapped call that swaps a large amount of `AssetX` into the same pool. No validator, collator, relayer, governance action, or leaked key is needed, and the manipulation and exploited refund both occur within the pre-dispatch/post-dispatch boundary of one transaction, requiring no cross-block timing.

## Recommendation
Snapshot the pool reserves (or lock the quoted refund conversion rate) at `withdraw_fee`/pre-dispatch time and reuse it for the post-dispatch refund, or compute the refund via a reserve-independent mechanism (e.g., refund in native rather than swapping back into `asset_id`, or cap the refund swap's price impact relative to the pre-dispatch quote), or disallow/detect wrapped calls that mutate the same pool used for the extension's fee `asset_id` before the refund swap executes.

## Proof of Concept
1. Attacker (or an accomplice) is an LP in, or otherwise identifies, a `(Native, AssetX)` pool with modest depth.
2. Attacker submits a signed extrinsic with `ChargeAssetTxPayment { asset_id: Some(AssetX), .. }` wrapping `call = AssetConversion::swap_exact_tokens_for_tokens(path: [AssetX, Native], amount_in: <large>, ...)`.
3. `prepare()` withdraws the fee in `AssetX` using pre-call reserves [8](#0-7) .
4. The wrapped call executes, driving `reserve(Native)` down and `reserve(AssetX)` up sharply.
5. `post_dispatch_details` invokes `correct_and_deposit_fee`, which quotes/swaps the fixed native `refund_amount` into `AssetX` against the now-skewed reserves, crediting the attacker an `AssetX` amount disproportionate to the native value surrendered [9](#0-8) .
6. Compare LP pool value before step 2 vs. after step 5 to demonstrate the uncompensated value transfer to the attacker; a Rust integration test using the pallet's mock runtime can reproduce this by constructing exactly this extrinsic sequence and asserting the pool's post-transaction reserve value is less than expected under fair pricing.

		pub fn quote_price_exact_tokens_for_tokens(
			asset1: T::AssetKind,
			asset2: T::AssetKind,
			amount: T::Balance,
			include_fee: bool,
		) -> Option<T::Balance> {
			// Swaps reject zero amounts, match that behavior.
			if amount.is_zero() {
				return None;
			}

			let pool_account = T::PoolLocator::pool_address(&asset1, &asset2).ok()?;

			let (balance1, balance2) = Self::get_reserves(asset1.clone(), asset2.clone()).ok()?;

			if balance1.is_zero() {
				return None;
			}

			let amount_out = if include_fee {
				let fee = Self::pool_fee_for(&asset1, &asset2).ok()?;
				Self::get_amount_out(fee, &amount, &balance1, &balance2).ok()?
			} else {
				Self::quote(&amount, &balance1, &balance2).ok()?
			};

			// Small inputs can round output to zero due to integer division.
			if amount_out.is_zero() {
				return None;
			}

			// Swap withdrawals from pools use `keep_alive=true` (Preserve). Use the same
			// preservation level to determine the actual withdrawable amount.
			let max_output = T::Assets::reducible_balance(asset2, &pool_account, Preserve, Polite);
			if amount_out > max_output {
				return None;
			}

			Some(amount_out)
		}
