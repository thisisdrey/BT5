### Title
Downloaded attachments are persisted to `AtlasDB` without enforcing `AtlasConfig::attachments_max_size` - ([File: stackslib/src/net/atlas/db.rs])

### Summary
`AtlasDB::insert_instantiated_attachment` writes the raw `attachment.content` BLOB into the `attachments` SQLite table with no size check against `AtlasConfig::attachments_max_size`. The only place that check exists, `AtlasDB::should_keep_attachment`, is not invoked on the peer-download path in `stackslib/src/net/atlas/download.rs`, so content fetched from a remote peer's `GetAttachmentResponse` (served over `/v2/attachments/{hash}`) is stored unconditionally once its hash matches the requested `content_hash`.

### Finding Description
`AtlasDB::insert_instantiated_attachment` performs a direct SQL `INSERT OR REPLACE` of `attachment.content` with no length validation: [1](#0-0) 

The size bound that exists in the codebase, `should_keep_attachment`, checks `attachment.content.len() as u32 > self.atlas_config.attachments_max_size` and rejects oversized content — but this function is defined and used only for the "posted" attachment ingestion path, not for attachments resolved via peer download: [2](#0-1) 

In the download state-machine flow (`AttachmentsDownloader::run`), once a batch is `Done`, every resolved `Attachment` is drained and passed directly to `insert_instantiated_attachment` with no size gate in between: [3](#0-2) 

The same unguarded call also occurs in `check_attachment_instances` when resolving an already-inboxed/uninstantiated attachment: [4](#0-3) 

The wire format for the attacker-controlled bytes is `GetAttachmentResponse`, decoded from a peer's HTTP JSON response body with no length limit applied at deserialization time — it hex-decodes an arbitrary-length hex string into `Attachment::new(bytes)`: [5](#0-4) 

`AtlasConfig::validate()` only enforces a *minimum* value for `attachments_max_size` (>= 1MB), it never caps content on the ingest path itself: [6](#0-5) 

The download/resolution logic verifies the returned content hashes to the requested `content_hash` (this is what makes the attack require the attacker to have originally committed that hash on-chain, e.g. via a legitimate BNS-related contract call embedding a `Hash160` they control the preimage of), but nowhere in the path from `StacksHttpResponse::decode_atlas_get_attachment` through `AttachmentsBatchStateMachine::try_proceed` to `insert_instantiated_attachment` is `content.len()` compared against `atlas_config.attachments_max_size`.

### Impact Explanation
A remote peer serving a `GetAttachmentResponse` for a `content_hash` it legitimately committed on-chain (e.g., via a BNS-related contract call event that becomes an `AttachmentInstance`) can return content of arbitrary size that still hashes to the requested `content_hash`, and the requesting node will persist the full oversized BLOB into its local `attachments` SQLite table via `insert_instantiated_attachment`, with no `attachments_max_size` enforcement. This is repeatable per distinct `AttachmentInstance`/`content_hash` the attacker can register, allowing unauthenticated disk-storage exhaustion on any node that syncs Atlas attachments from that peer.

### Likelihood Explanation
The attacker needs no special privileges: they must (1) get an `AttachmentInstance` with a chosen `content_hash` tracked by the target node (via a normal on-chain contract-call event processed by any node, which is attacker-affordable since they choose the preimage/content locally before submitting the hash), and (2) run/control a peer that responds to `/v2/attachments/{hash}` HTTP requests with oversized-but-hash-matching content. Both preconditions are within reach of an unprivileged network participant and require no admin role or secret. Configuring a small `attachments_max_size` only sharpens the demonstration; the missing check exists regardless of the configured value.

### Recommendation
Enforce `attachment.content.len() as u32 <= atlas_config.attachments_max_size` (reusing `should_keep_attachment` or an equivalent check) before calling `insert_instantiated_attachment` in both call sites in `stackslib/src/net/atlas/download.rs` (the `Done` branch of `run`, and the "inboxed" resolution branch of `check_attachment_instances`), and/or add the same guard directly inside `AtlasDB::insert_instantiated_attachment` in `stackslib/src/net/atlas/db.rs` so the bound is enforced at the single point of persistence regardless of caller.

### Proof of Concept
```rust
// stackslib/src/net/atlas/tests.rs (new test)
#[test]
fn test_oversized_attachment_bypasses_max_size_on_download_path() {
    let bns_contract_id = boot_code_id("bns", false);
    let mut contracts = HashSet::new();
    contracts.insert(bns_contract_id.clone());

    let atlas_config = AtlasConfig {
        contracts,
        attachments_max_size: 16, // tiny cap
        max_uninstantiated_attachments: 10,
        uninstantiated_attachments_expire_after: 10,
        unresolved_attachment_instances_expire_after: 10,
        genesis_attachments: None,
    };
    let mut atlas_db = AtlasDB::connect_memory(atlas_config).unwrap();

    // Attacker-controlled content exceeding attachments_max_size (16 bytes), but attacker
    // knows the preimage so it hashes correctly to whatever content_hash was posted on-chain.
    let oversized_content = vec![0xAA; 1024]; // 1KB >> 16 bytes cap
    let oversized_attachment = Attachment::new(oversized_content);

    // Simulate the peer download path (as in AttachmentsDownloader::run's Done branch /
    // check_attachment_instances "inboxed" branch): it calls insert_instantiated_attachment
    // directly with no size check.
    atlas_db
        .insert_instantiated_attachment(&oversized_attachment)
        .unwrap(); // succeeds -- should have been rejected because content.len() > attachments_max_size

    let stored = atlas_db
        .find_attachment(&oversized_attachment.hash())
        .unwrap()
        .expect("oversized attachment was persisted");
    assert!(
        stored.content.len() as u32 > 16,
        "BUG: oversized attachment ({} bytes) was stored despite attachments_max_size=16",
        stored.content.len()
    );
}
```
This demonstrates that `insert_instantiated_attachment` (and thus the download path in `stackslib/src/net/atlas/download.rs` lines 153-169/255-262 that calls it) never enforces `attachments_max_size`, unlike `should_keep_attachment` which is bypassed entirely on this path.

    pub fn should_keep_attachment(
        &self,
        contract_id: &QualifiedContractIdentifier,
        attachment: &Attachment,
    ) -> bool {
        if !self.atlas_config.contracts.contains(contract_id) {
            info!(
                "Atlas: will discard posted attachment - {} not in supported contracts",
                contract_id
            );
            return false;
        }
        if attachment.content.len() as u32 > self.atlas_config.attachments_max_size {
            info!("Atlas: will discard posted attachment - attachment too large");
            return false;
        }
        true
    }

    pub fn insert_instantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let tx = self.tx_begin()?;
        tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)",
            params![attachment.hash(), attachment.content, now],
        )?;
        tx.execute(
            "UPDATE attachment_instances SET is_available = 1 WHERE content_hash = ?1 AND status = ?2",
            params![attachment.hash(), AttachmentInstanceStatus::Checked],
        )?;
        tx.commit()?;
        Ok(())
    }
