### Title
Unprivileged repayment can move an unhealthy position into an unliquidatable debt-floor band - (File: contracts/Pool.sol)

### Summary
`Pool.liquidate` combines a `maxLiquidable` close-factor cap with a requirement that any nonzero remaining debt be at least `debtFloorInUsd`. An unprivileged account can call `DebtToken.repay` for an unhealthy position and reduce its debt exactly to the floor; afterward, every repayment allowed by the close factor leaves less than the floor and reverts, while a full repayment is blocked by the close factor.

### Finding Description
`DebtToken.repay(address onBehalfOf_, uint256 amount_)` is public and burns synthetic tokens from the caller to reduce another account’s debt. It permits the resulting debt to equal `debtFloorInUsd`, reverting only when nonzero remaining debt is strictly below that floor. [1](#0-0) 

`Pool.liquidate` first limits the repayment to `debtBalance * maxLiquidable`, then rejects a partial repayment when the remaining debt is below `debtFloorInUsd`. [2](#0-1)  The deployment default for `maxLiquidable` is `0.5e18`, or 50%. [3](#0-2) 

For example, with a $1,000 debt floor and 50% close factor, an unhealthy account with $1,500 debt can repay $500 through `repay(victim, amountFor500Debt)`, leaving exactly $1,000 debt. A liquidator can then repay at most $500, which would leave $500 and trigger `RemainingDebtIsLowerThanTheFloor`; repaying the full $1,000 triggers `AmountGreaterThanMaxLiquidable`.

The attack does not require privileged access, oracle manipulation, or control of the victim. The payer can be the debtor, another EOA protecting the debtor, or a contract holding the required synthetic token because `repay` burns `_msgSender`’s synthetic tokens while reducing `onBehalfOf_`’s debt. [4](#0-3) 

### Impact Explanation
This breaks liquidation liveness for positions whose debt is intentionally moved into the interval `[debtFloor, debtFloor / (1 - maxLiquidable))`. During that interval, the protocol cannot liquidate the position even when `debtPositionOf` reports it as unhealthy and sufficient collateral exists to satisfy the liquidation accounting. [5](#0-4) 

If collateral value continues falling, the position can remain unliquidatable until interest or price movement lifts debt out of the gap, creating avoidable bad debt. Where debt does not grow fast enough, the blockage can persist indefinitely. This maps to temporary liquidation freezing and potential protocol insolvency.

### Likelihood Explanation
The attack requires a nonzero deployed `debtFloorInUsd`, a `maxLiquidable` below 100%, and an unhealthy position with enough debt for the payer to reduce it into the forbidden band. The code initializes `maxLiquidable` to 50%, and `repay` can be front-run immediately before a liquidation transaction. [3](#0-2) [6](#0-5) 

The economic cost is bounded by the amount needed to reduce the debt to the floor. For the debtor, this is a rational defensive action because it prevents the liquidator’s collateral seizure and liquidation incentive, potentially preserving the position until prices recover.

### Recommendation
Do not allow `maxLiquidable` and `debtFloorInUsd` to create a debt range where both partial and full liquidation are impossible. In `Pool.liquidate`, permit a liquidation that reduces debt to zero when `debtBalance < debtFloor / (1 - maxLiquidable)`, or cap `amountToRepay` to either `debtBalance * maxLiquidable` or the full balance when the capped result would leave sub-floor debt. Ensure the resulting collateral seizure behavior remains correctly bounded when the position is deeply underwater.

### Proof of Concept
```solidity
// Foundry fork-style test against a deployed Pool and registered tokens.
// Assumes:
// - debtFloorInUsd > 0
// - maxLiquidable == 0.5e18
// - victim is unhealthy and has debt above the floor
// - payer holds enough syntheticToken
function testRepayToDebtFloorBlocksLiquidation() public {
    IPool pool = IPool(MAINNET_POOL);
    ISyntheticToken synth = ISyntheticToken(MS_ASSET);
    IDebtToken debtToken = pool.debtTokenOf(synth);
    IDepositToken depositToken = IDepositToken(MSD_COLLATERAL);

    address victim = UNHEALTHY_ACCOUNT;
    address payer = ATTACKER_OR_VICTIM;

    uint256 debtBefore = debtToken.balanceOf(victim);

    // Target a remaining debt equal to the configured floor.
    uint256 targetDebt = pool.masterOracle().quoteUsdToToken(
        address(synth),
        pool.debtFloorInUsd()
    );

    assertLt(targetDebt, debtBefore);

    uint256 debtReduction = debtBefore - targetDebt;
    (uint256 grossRepayAmount, ) = debtToken.quoteRepayIn(debtReduction);

    vm.prank(payer);
    debtToken.repay(victim, grossRepayAmount);

    uint256 debtAfter = debtToken.balanceOf(victim);
    assertEq(debtAfter, targetDebt);

    uint256 maxRepay = debtAfter.wadMul(pool.maxLiquidable());

    // maxRepay is only 50% of debtAfter, so the remainder is below floor.
    vm.prank(LIQUIDATOR);
    vm.expectRevert(Pool.RemainingDebtIsLowerThanTheFloor.selector);
    pool.liquidate(synth, victim, maxRepay, depositToken);

    // A full repayment is also rejected by the close-factor cap.
    vm.prank(LIQUIDATOR);
    vm.expectRevert(Pool.AmountGreaterThanMaxLiquidable.selector);
    pool.liquidate(synth, victim, debtAfter, depositToken);
}
```

The first revert is caused by the floor check, while the second is caused by the 50% liquidation cap. [6](#0-5)
