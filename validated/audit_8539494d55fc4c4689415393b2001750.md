### Title
Precision loss / unchecked ratio blow-up in the legacy Bancor-style exchange rate formula can be manipulated to drain TRC10 exchange pools - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
The reported bug is a class of "unbounded ratio calculation" issue: a rate formula built from mutable pool state (`cash`, `borrows`, `reserves`) is not bounded to a sane range, and that unbounded ratio is then used to scale a payout, letting an attacker who can manipulate the underlying pool state extract more value than was deposited. The closest reachable analog in java-tron is the legacy `ExchangeProcessor` used by `ExchangeTransactionActuator`/`ExchangeCapsule.transaction`, which computes swap outputs for TRC10↔TRC10/TRX pools using a double-precision Bancor-style relay formula driven directly by the pool's `firstTokenBalance`/`secondTokenBalance` (the "reserves" of the exchange). Any account can invoke this path via a broadcast `ExchangeTransactionContract`.

### Finding Description
`ExchangeCapsule.transaction()` selects between two `Processor` implementations depending on the `hardenedCalc` flag returned by `allowHarden()`: [1](#0-0) 

When the hardening feature is not active, the legacy `ExchangeProcessor` is used, which computes the swap output using raw `double` arithmetic on the pool reserves: [2](#0-1) 

This mirrors the ERC721 report's root cause exactly: a rate (`issuedSupply`/`exchangeBalance`) is derived from a ratio of `quant` to pool `balance` ("reserves"), computed with imprecise floating-point math and with no explicit bound on the resulting supply/exchange ratio, similar to how `utilizationRate` in the reported bug had no cap at `1e18`. Because `double` has only ~15-17 significant decimal digits, extreme but validly-reachable combinations of `sellTokenBalance`/`buyTokenBalance`/`sellTokenQuant` (e.g., very small balance vs. large quant, or vice versa, both of which are attacker-chosen via the `ExchangeTransactionContract.quant` field) can push `Maths.pow(1 + quant/newBalance, ...)` into regions where the double computation loses precision or the derived `exchangeBalance` no longer reflects the true constant-product-style invariant, yielding an output amount that is not bounded correctly relative to the counter-reserve.

The repo itself already acknowledges this bug class: a `SafeExchangeProcessor` was added that performs the same relay math in `BigDecimal` with explicit `RoundingMode` and `StrictMathWrapper.addExact`/`subtractExact` and asserts the invariant `newFirstTokenBalance >= 0 && newSecondTokenBalance >= 0` after the swap: [3](#0-2) [4](#0-3) 

Existing regression tests directly demonstrate divergence between the legacy and hardened processors for the exact same inputs: [5](#0-4) 

This is analogous to the compound-fork case: the fix ("Fixed as recommended... in [commit]") was already made in a hardened path, but the vulnerable legacy formula remains reachable whenever the corresponding chain parameter/hard-fork proposal enabling `allowHarden()` is not active for a given network deployment, meaning the "reserves-driven unbounded rate" bug class is only mitigated, not eliminated, at the protocol level.

### Impact Explanation
If the hardening proposal is not enabled on a given java-tron network, any account can call `ExchangeTransactionContract` (via `ExchangeTransactionActuator`) with crafted `quant` values relative to the pool's `firstTokenBalance`/`secondTokenBalance` to trigger the double-precision formula's imprecision, potentially receiving `anotherTokenQuant` that is inconsistent with the true bonding-curve invariant. Because the actuator directly credits the computed `anotherTokenQuant` to the caller's account balance/asset amount and debits the exchange pool by the same amount, an attacker could extract more value from the pool's counter-token reserve than economically justified, draining TRC10/TRX exchange pools and causing loss of funds for other participants — a concrete unauthorized transfer of value, matching the required "theft of funds" impact bar.

### Likelihood Explanation
Reachability is high: `ExchangeTransactionContract` is a standard, permissionless broadcastable transaction type requiring only that the sender own the tokens/TRX being sold, and `ExchangeTransactionActuator.execute()`/`ExchangeCapsule.transaction()` unconditionally uses the legacy `ExchangeProcessor` whenever `allowHarden()` is false for the executing node/network. Exploitation, however, requires the hardening proposal to be inactive and requires finding/engineering pool balance and quant combinations where double-precision loss becomes economically significant, which is a nontrivial but demonstrated (by the repo's own tests) source of numeric divergence.

### Recommendation
- Make the `SafeExchangeProcessor` (BigDecimal-based) the unconditional implementation for `ExchangeCapsule.transaction`, removing the legacy double-precision `ExchangeProcessor` code path entirely rather than gating it behind a proposal flag, since it constitutes a live, reachable rate-calculation flaw whenever the flag is off.
- Add protocol-level invariant checks after every exchange (already partially done in the hardened path) enforcing that the swap never returns more than the counter-reserve and that the post-swap product of reserves does not decrease beyond the fee/precision tolerance, regardless of which processor is active.
- Confirm and, if necessary, force-enable the hardening proposal on all deployed networks so the legacy formula can no longer be reached.

### Proof of Concept
1. An attacker creates or finds an `Exchange` pool with a skewed `firstTokenBalance`/`secondTokenBalance` ratio (e.g., via repeated small trades) on a network where the hardening proposal (`allowHarden()`) is not yet activated.
2. The attacker broadcasts an `ExchangeTransactionContract` with a `quant` chosen such that `quant / (balance + quant)` in `ExchangeProcessor.exchangeToSupply` (`chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java:17-29`) falls into a range where double-precision `Math.pow` rounding diverges materially from the exact `BigDecimal` computation performed by `SafeExchangeProcessor` (as shown to diverge in `framework/src/test/java/org/tron/core/capsule/utils/ExchangeProcessorTest.java:218-281`, where `Assert.assertNotEquals(anotherTokenQuant, result)` explicitly confirms the two paths give different outputs for the same inputs).
3. `ExchangeTransactionActuator.execute()` credits the attacker with the (miscalculated, more favorable) `anotherTokenQuant` and debits the exchange pool accordingly, extracting value beyond what the exact bonding-curve invariant would allow — analogous to the reported ERC721 case where an unbounded rate calculation let an attacker "claim more interest than was paid" from the pool.

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
