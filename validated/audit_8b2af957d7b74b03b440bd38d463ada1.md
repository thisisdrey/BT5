### Title
StackerDB chunk signatures don't bind to the StackerDB's contract ID, enabling cross-database chunk replay - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` — the digest that a signer signs to authenticate a StackerDB chunk write — commits only to `(slot_id, slot_version, data_hash)`. It does not commit to the StackerDB's smart-contract identifier or to any of that database's config parameters (`chunk_size`, `max_writes`, `write_freq`). This is the same bug class as the reported Atlas issue: a signature is valid independent of the "config" context (here, which StackerDB / contract the write is destined for), so a chunk authenticated for one StackerDB replica can be replayed into a different StackerDB replica that happens to assign the same signer address to the same `slot_id`.

### Finding Description
`SlotMetadata::auth_digest()` builds the signed hash as: [1](#0-0) 

and `verify()` only checks that this digest recovers to the expected signer address: [2](#0-1) 

Crucially, the `smart_contract_id` (which StackerDB instance this chunk belongs to) is never part of the signed material. The caller-side validation (`PeerNetwork::validate_received_chunk` and `StackerDBTx::try_replace_chunk`) determines *which* address is allowed to write a given `slot_id` by looking up `get_slot_signer(smart_contract_id, slot_id)` from local per-contract state, but this lookup is external to, and disconnected from, the cryptographic digest itself: [3](#0-2) 

Because the digest is contract-agnostic, if the same signer address is assigned to the same `slot_id` in two different StackerDB contracts (a realistic scenario — e.g. the Nakamoto signer-set StackerDB contracts, which are instantiated per reward cycle and typically reuse the same signer key ordering/allocation, per `chainstate/stacks/boot/mod.rs` and `chainstate/nakamoto/signer_set.rs`), a signature produced for one contract's slot is *also a valid signature* for the other contract's identically-indexed slot with the same `slot_version`/`data`. The per-DB `StackerDBConfig` (chunk size, max writes, write frequency) that governs each replica is likewise not part of the hash, so the same signed bytes remain "valid" regardless of which config context ultimately consumes them — exactly the "hash doesn't depend on config state" pattern from the reference report, mapped from `DAppControl`/`CallConfig` onto `smart_contract_id`/`StackerDBConfig`.

`create_stackerdb`/`reconfigure_stackerdb` assign `slot_id`s purely by ordinal position within the configured signer list, with no per-contract salt: [4](#0-3) [5](#0-4) 

So nothing in the on-disk slot layout or in the signed digest prevents slot-index collisions across different `smart_contract_id`s from being cryptographically indistinguishable.

### Impact Explanation
If two active StackerDB instances (e.g. two consecutive reward-cycle `.signers-*` contracts, or any two contracts whose signer-slot layout coincidentally overlaps) assign the same signer address to the same `slot_id`, an attacker who obtains — or a signer who reuses — a validly signed `StackerDBChunkData` for one contract can replay that exact wire message to the other contract's endpoint (`POST /v2/stackerdb/.../chunks` handled by `poststackerdbchunk.rs`, or via unsolicited `StackerDBPushChunk` gossip) and have it accepted as an authentic write there, as long as the target replica's expected version for that slot is `<=` the replayed `slot_version`. This is an unauthorized cross-database write of attacker-controlled-but-authentically-signed data: state intended for one context (one config, one contract) gets injected into another, potentially confusing signer message coordination (e.g. old-cycle signer data appearing as fresh in a new cycle's DB) or bypassing a stricter DB's `max_writes`/`chunk_size` expectations by having been "freshly" signed for a laxer DB with the same slot layout.

### Likelihood Explanation
Exploitability depends entirely on whether two live StackerDB contracts actually reuse the same signer→slot_id assignment — which is plausible by design for the signer-set contracts that are re-instantiated every reward cycle using deterministic ordering. I was not able to fully verify from the indexed code whether the boot contract logic guarantees identical ordering/slot reuse across cycles for the same signer, so likelihood should be treated as **uncertain/moderate** rather than confirmed — this needs verification against `chainstate/nakamoto/signer_set.rs` and the `.signers-*.clar` contract logic beyond what was retrievable here.

### Recommendation
Include the StackerDB's `smart_contract_id` (and ideally a config/version tag) inside `SlotMetadata::auth_digest()` so that a signature is only valid for the specific StackerDB instance (and config epoch) it was produced for, mirroring the report's recommendation to bind each party's expected config value into the signed hash.

### Proof of Concept
Conceptual (not fully executable from indexed code alone, since it depends on real-world signer/slot reuse across contracts):
1. Signer key `K` owns `slot_id = 3` in StackerDB contract `A` (e.g. `.signers-0-1`) and also owns `slot_id = 3` in contract `B` (e.g. `.signers-1-1`), which occurs if slot ordering assignment is identical across the two reward-cycle contracts for a signer that stays in the active set.
2. Signer signs `StackerDBChunkData{slot_id:3, slot_version:5, data: D}` for contract `A` via `StackerDBChunkData::sign` (`libstackerdb/src/libstackerdb.rs:226`).
3. Attacker captures this message (it's broadcast over gossip / servable via HTTP) and POSTs it to contract `B`'s stackerdb endpoint instead.
4. `validate_received_chunk`/`try_replace_chunk` for contract `B` looks up `get_slot_signer(B, 3)` → returns `K`; `slot_metadata.verify(&K)` succeeds because the digest never referenced `A` vs `B` — the write is accepted into `B`'s replica even though `K` never authorized writing this specific payload into `B`.     /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
