### Title
Arbitrary local file/directory disclosure via forced `protocol.file.allow=always` in Git submodule fetch - (File: tools/build_defs/repo/git_worker.bzl)

### Summary
`git_repository`'s submodule handling unconditionally re-enables Git's `file://` transport for *all* submodule URLs — including absolute, attacker-chosen filesystem paths — not just paths relative to the fetched superproject. Any untrusted repository consumed via `git_repository(init_submodules = True)` or `recursive_init_submodules = True` can therefore smuggle a `.gitmodules` entry that makes the build host clone an arbitrary local git repository (anywhere the invoking user has read access) into the workspace, where its contents become readable to subsequent build steps/genrules.

### Finding Description
`update_submodules` in `git_worker.bzl` runs: [1](#0-0) 

i.e. `git -c protocol.file.allow=always submodule update --init [--recursive] --checkout --force`. The comment explains this was added to restore support for local-directory submodule clones (bazelbuild/bazel#17040), but Git's own security advisory for the class of bug this addresses (`file://` submodule protocol abuse, patched by making `protocol.file.allow` default to `user`/disabled for indirect fetches) exists precisely because a submodule URL controlled by an untrusted repository owner can point at absolute paths, not merely relative ones. By forcing `protocol.file.allow=always` for every submodule update, Bazel unconditionally disables that Git-side protection.

The Bazel test corpus confirms the ordinary (benign) use case is a **relative** submodule URL such as `url = ../pluto`: [2](#0-1) 

exercised by `test_git_repository_submodules`: [3](#0-2) 

Nothing in `update_submodules`, `_git_maybe_shallow`, or `_execute` restricts the resolved submodule URL to be relative to the superproject's own remote, or otherwise validates/sandboxes it: [4](#0-3) 

The only content-integrity control on `git_repository` fetches is pinning `commit`/`tag`/`branch` of the top-level repository; nothing pins or validates the content of `.gitmodules` or the paths it names, and `protocol.file.allow=always` means an absolute `file:///...` URL in that file is honored just as readily as a relative one.

### Impact Explanation
A third party who controls (or compromises, or is granted a legitimate but malicious contribution to) any Git repository that a victim's `MODULE.bazel`/`WORKSPACE` fetches with `git_repository(..., init_submodules = True)` (or `recursive_init_submodules = True`) can add a submodule entry such as:
```
[submodule "leak"]
    path = leak
    url = file:///home/victim/.ssh
```
(or any other absolute path on the build machine that is itself a git repository, e.g. another repository already checked out under the same output_base, a CI credentials checkout, etc.). When Bazel fetches this repository, it will `git submodule update --init` with `protocol.file.allow=always`, causing the local git binary to clone that arbitrary local path into the workspace's `leak/` directory. The cloned contents then live inside the external repository directory and are readable by any downstream `genrule`/build action that consumes the repository, i.e. content is exfiltrated from outside the intended repository/exec-root boundary into a location the untrusted repository's own build files (or a colluding downstream rule) can read and repackage into build outputs.

This satisfies the "read outside the repository / exec root / output base" acceptance criterion: the invariant that a fetched Git repository can only expose its own remote-hosted content is broken, and the fetch mechanism itself (a Bazel-controlled subprocess flag) is what removes the containment Git normally provides.

### Likelihood Explanation
`init_submodules`/`recursive_init_submodules` are common, documented options on `git_repository`, and any dependency maintained by a third party (a very common real-world scenario for external repositories) can add or modify `.gitmodules` at any time, including for commits already pinned by hash if the victim later updates the pin, or immediately for branch/tag-tracked dependencies. No opt-in or warning is required — the `protocol.file.allow=always` override is applied unconditionally whenever submodules are requested, on default Bazel flags, on the current release.

### Recommendation
- Do not blanket-enable `protocol.file.allow=always`; instead restrict it to only permit relative submodule URLs resolved against the already-fetched superproject (e.g., resolve and validate submodule URLs from `.gitmodules` before running `submodule update`, rejecting absolute `file://` paths or paths that escape the superproject clone).
- Alternatively, use `protocol.file.allow=user` (Git's own safer default) combined with pre-resolving/rewriting relative submodule paths to absolute ones under the already-cloned directory before invoking `submodule update`, so the `file://` allowance is scoped to a known-safe location rather than the whole filesystem.
- Add a regression test (extending `test_git_repository_submodules` in `src/test/shell/bazel/starlark_git_repository_test.sh`) that creates a submodule with an absolute `file://` URL pointing outside the test's `TEST_TMPDIR` sandbox and asserts the fetch fails or the outside content is not copied in.

### Proof of Concept
1. Create `outer` git repo with a `.gitmodules` submodule entry `url = file:///tmp/victim_secret_repo` (an absolute path to another git repository readable by the invoking user, e.g. containing sensitive files committed to it).
2. In a Bazel workspace, declare:
```
git_repository(
    name = "outer",
    remote = "<outer repo path/url>",
    commit = "<pinned commit>",
    init_submodules = True,
)
```
3. Run `bazel fetch @outer` (or any build depending on `@outer`).
4. Observe that `external/+git_repository+outer/<submodule_path>` now contains the contents of `/tmp/victim_secret_repo`, cloned purely because `git_worker.bzl`'s `update_submodules` forced `protocol.file.allow=always` — this can be confirmed by comparing against the same test with the flag removed/restricted, where Git would refuse the absolute `file://` submodule URL by default.

```text
def update_submodules(ctx, git_repo, recursive = False):
    if recursive:
        # "protocol.file.allow=always" allows the submodule command clone from a local directory.
        # It's necessary for Git 2.38.1 and assoicated backport versions.
        # See https://github.com/bazelbuild/bazel/issues/17040
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--recursive", "--checkout", "--force")
    else:
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--checkout", "--force")
```

```text
def _execute(ctx, git_repo, args):
    # "core.fsmonitor=false" disables git from spawning a file system monitor which can cause hangs when cloning a lot.

        environment = ctx.os.environ | _GIT_LOCAL_ENV_VARS,

    )
```
