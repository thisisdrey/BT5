### Title
Unbounded heap allocation from attacker-controlled CODECOPY/EXTCODECOPY length causes node OutOfMemory DoS - (File: `actuator/src/main/java/org/tron/core/vm/OperationActions.java`)

### Summary
The TVM `CODECOPY` and `EXTCODECOPY` opcode handlers allocate a byte array sized directly by an attacker-controlled stack value (clamped only to `Integer.MAX_VALUE`, i.e. up to ~2GB) before any bounds check against the actual code being copied or against the VM's memory-cost energy limit is applied to that allocation. This mirrors the Pillow `IcnsImagePlugin` bug class: a crafted "size" field taken directly from untrusted input is used to size a buffer/loop without validation, leading to a denial of service.

### Finding Description
In `codeCopyAction` and `extCodeCopyAction`: [1](#0-0) 

```java
public static void codeCopyAction(Program program) {
  byte[] fullCode = program.getCode();
  int memOffset = program.stackPop().intValueSafe();
  int codeOffset = program.stackPop().intValueSafe();
  int lengthData = program.stackPop().intValueSafe();
  ...
  byte[] codeCopy = new byte[lengthData];
  ...
}
```

and the analogous `extCodeCopyAction`: [2](#0-1) 

`lengthData` is popped straight from the EVM/TVM stack and converted with `DataWord.intValueSafe()`: [3](#0-2) 

`intValueSafe()` does not reject large values — it clamps any value that doesn't fit cleanly into 4 bytes (or is "negative" as a signed int) to `Integer.MAX_VALUE` (~2.1 billion), rather than throwing or being bounded by the VM's memory-cost model. The resulting `lengthData` (up to `Integer.MAX_VALUE`) is used directly as `new byte[lengthData]` — a raw JVM array allocation that is independent of `Memory.extend()`'s soft/hard limit checks (`MEM_LIMIT`, `checkMemorySize`) that are supposed to gate all TVM memory growth and charge/limit it via `EnergyCost.calcMemEnergy`: [4](#0-3) 

Because `codeCopy`/`extCodeCopy`'s temporary buffer is allocated ahead of, and separately from, the metered `Memory` object, a crafted `lengthData` value can force the JVM to attempt an ~2GB `byte[]` allocation regardless of the energy/fee limit paid by the caller, before any energy-based rejection for that specific allocation occurs.

### Impact Explanation
A single attacker-supplied smart contract, deployable and callable by any unprivileged account, can execute `CODECOPY` or `EXTCODECOPY` with a maximal length operand. Repeated invocation (e.g., in a loop, or via many parallel transactions/internal calls) forces the node to repeatedly allocate near-2GB temporary arrays, which can exhaust heap memory and trigger `OutOfMemoryError`, crashing or hanging the TVM/node process — a node crash/halt DoS reachable purely through normal contract execution, matching the "node crash or halt" acceptance criterion.

### Likelihood Explanation
High reachability: `CODECOPY`/`EXTCODECOPY` are ordinary, frequently used EVM/TVM opcodes available to any contract; no special privilege, witness/SR role, or network position is required — just a deployed contract and a `TriggerSmartContract` transaction that any broadcaster can submit.

### Recommendation
Bound `lengthData` (and `codeOffset`) against `fullCode.length` before allocating `codeCopy`, and/or route the allocation through the metered `Memory`/`EnergyCost` path (`checkMemorySize`/`MEM_LIMIT`) so oversized lengths are rejected with `Program.Exception.memoryOverflow` prior to any large `new byte[...]` allocation, consistent with how `Memory.extend()` already guards other memory-growing opcodes.

### Proof of Concept
Deploy any contract whose bytecode/runtime executes:
```
PUSH32 0xFFFFFFFF...FF   ; length (clamps to Integer.MAX_VALUE via intValueSafe)
PUSH1 0x00                ; codeOffset
PUSH1 0x00                ; memOffset
CODECOPY
```
Sending a `TriggerSmartContractContract` transaction invoking this path causes `codeCopyAction` to execute `new byte[Integer.MAX_VALUE]`, triggering a large/failing allocation on the node executing the transaction (also applies identically to `EXTCODECOPY` against any target address). This can be corroborated against the existing project OOM regression test that already demonstrates TVM memory-growth OOM behavior for comparison: [5](#0-4)

  public static void codeCopyAction(Program program) {
    byte[] fullCode = program.getCode();

    int memOffset = program.stackPop().intValueSafe();
    int codeOffset = program.stackPop().intValueSafe();
    int lengthData = program.stackPop().intValueSafe();

    int sizeToBeCopied = lengthData;
    if ((long) codeOffset + lengthData > fullCode.length) {
      sizeToBeCopied = fullCode.length < codeOffset ? 0 : fullCode.length - codeOffset;
    }

    byte[] codeCopy = new byte[lengthData];

    if (codeOffset < fullCode.length) {
      System.arraycopy(fullCode, codeOffset, codeCopy, 0, sizeToBeCopied);
    }

    program.memorySave(memOffset, codeCopy);
    program.step();
  }

   * In case of int overflow returns Integer.MAX_VALUE otherwise works as #intValue()

  public int intValueSafe() {
    int bytesOccupied = bytesOccupied();
    int intValue = intValue();
    if (bytesOccupied > 4 || intValue < 0) {
      return Integer.MAX_VALUE;
    }
    return intValue;
  }

  private static long calcMemEnergy(long oldMemSize, BigInteger newMemSize,
                             long copySize, int op) {
    long energyCost = 0;

    checkMemorySize(op, newMemSize);

    // memory SUN consume calc
    long memoryUsage = (newMemSize.longValueExact() + 31) / 32 * 32;
    if (memoryUsage > oldMemSize) {
      long memWords = (memoryUsage / 32);
      long memWordsOld = (oldMemSize / 32);
      long memEnergy = (MEMORY * memWords + memWords * memWords / 512)
          - (MEMORY * memWordsOld + memWordsOld * memWordsOld / 512);
      energyCost += memEnergy;
    }

    if (copySize > 0) {
      long copyEnergy = COPY_ENERGY * ((copySize + 31) / 32);
      energyCost += copyEnergy;
    }
    return energyCost;
  }

  private static void checkMemorySize(int op, BigInteger newMemSize) {
    if (newMemSize.compareTo(MEM_LIMIT) > 0) {
      throw Program.Exception.memoryOverflow(op);
    }
  }
