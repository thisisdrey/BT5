## Title
Incorrect V2 net-usage/energy-usage calculation lets `DelegateResourceContract` and TVM `delegateResource` bypass the "available FreezeV2 balance" check, enabling delegation of unbacked bandwidth/energy - (File: actuator/src/main/java/org/tron/core/vm/utils/FreezeV2Util.java)

### Summary
`FreezeV2Util.getV2NetUsage()` / `getV2EnergyUsage()` compute the portion of an account's resource usage attributable to its own FreezeBalanceV2 stake by subtracting unrelated "reserved" quantities (legacy V1 frozen balance and delegated-in balances) from a scaled usage value, then clamping the result to `>= 0`. Exactly like the Sherlock M-25 finding — where `balanceBefore/After` subtracted an unrelated `reservedFunds` that could exceed `getVaultBalance()` — here the subtracted quantities (`getFrozenBalance()`, `getAcquiredDelegatedFrozenBalanceForBandwidth()`, `getAcquiredDelegatedFrozenV2BalanceForBandwidth()`) can exceed the scaled usage value, silently flooring the result to `0` via `max(0, v2NetUsage, ...)` instead of reflecting genuine remaining usage. This corrupted value directly feeds an availability check in `DelegateResourceActuator`/`DelegateResourceProcessor` used to validate `DelegateResourceContract` transactions and the TVM `delegateResource()` opcode.

### Finding Description
`getV2NetUsage`/`getV2EnergyUsage`: [1](#0-0) 

are consumed by both the legacy actuator validate path and the TVM native contract validate path: [2](#0-1) [3](#0-2) 

as well as `Wallet.calcCanDelegatedBandWidthMaxSize`/`calcCanDelegatedEnergyMaxSize` used to advertise available delegation capacity: [4](#0-3) 

Whenever an account has non-trivial legacy V1 frozen balance (`getFrozenBalance()`) or delegated-in balances (`getAcquiredDelegatedFrozenBalanceForBandwidth()`/`getAcquiredDelegatedFrozenV2BalanceForBandwidth()`) that are large relative to its scaled net usage (`netUsage`), the subtraction goes negative and is floored to `0`. Once `v2NetUsage`/`v2EnergyUsage` reports `0`, the availability check:
```
if (ownerCapsule.getFrozenV2BalanceForBandwidth() - v2NetUsage < delegateBalance)
```
overestimates the account's truly free FreezeV2 balance by the full amount that should have been subtracted, since the intended "usage that must be reserved against the owner's own V2 stake" is silently zeroed instead of properly reflecting the real remaining margin. This is structurally the same defect as the derby `balanceBefore/After` bug: an intermediate subtraction of an unrelated reserved quantity that can exceed the base value, producing either a revert (derby case, underflow protected in Solidity) or, in java-tron's unsigned/clamped Java math, a silently wrong (inflated) result rather than a revert — arguably worse because it fails open instead of failing closed.

### Impact Explanation
An account owner can pass the "delegateBalance must be less than or equal to available FreezeBandwidthV2/EnergyV2 balance" check with a `delegateBalance` that exceeds the resource actually free after usage, because the usage subtracted from `getFrozenV2BalanceForBandwidth()`/`getFrozenV2BalanceForEnergy()` is incorrectly floored to zero. This lets a user delegate stake-weighted bandwidth/energy to other accounts that is not actually backed by free (unused) frozen TRX, inflating the effective resource issued to receivers beyond what the owner's real remaining V2 collateral supports — an unbacked resource/stake-accounting bug reachable by any account via a single signed `DelegateResourceContract` transaction or via the TVM `delegateResource` precompile from any smart contract.

### Likelihood Explanation
The bug is triggered purely by normal account state that is common on TRON: any account that still has legacy V1 frozen balance (pre-Freeze V2 migration) or has received V1/V2 delegated resource from others, combined with sufficient bandwidth/energy usage, will experience this "over-subtraction to zero" behavior. No special permissions or race conditions are required — any unprivileged holder of a TRON account with mixed V1/V2 freeze history can trigger it deterministically by calling `DelegateResourceContract` or the corresponding TVM opcode.

### Recommendation
Do not floor the usage-portion calculation at the point of subtracting unrelated V1/delegated-in quantities. Instead of `max(0, netUsage - frozenBalance - acquiredDelegatedFrozenBalance - acquiredDelegatedFrozenV2Balance)`, compute the usage attributable to the account's own FreezeV2 balance using the proper proportional/waterfall accounting (e.g., first subtract usage covered by other pools without clamping intermediate terms, and only clamp the final result), mirroring the derby fix of removing the unnecessary/incorrect intermediate subtraction so that `getFrozenV2BalanceForBandwidth() - v2NetUsage` (and the Energy equivalent) always reflects the actual free FreezeV2 balance rather than being inflated when V1/delegated-in reserves happen to exceed usage.

### Proof of Concept
1. Freeze a small amount via legacy `FreezeBalance` (V1) for BANDWIDTH so `accountCapsule.getFrozenBalance()` is large (e.g., 1,000 TRX).
2. Freeze a separate, smaller amount via `FreezeBalanceV2` for BANDWIDTH (e.g., 10 TRX) — this is `getFrozenV2BalanceForBandwidth()`.
3. Perform transactions to accumulate `netUsage` on the account such that the TRX-equivalent scaled usage (`netUsage * TRX_PRECISION * totalNetWeight/totalNetLimit`) is smaller than the V1 frozen balance (step 1) — trivially true right after freezing since usage accrues slowly relative to a large V1 stake.
4. Call `DelegateResourceActuator`/`DelegateResourceContract` with `delegateBalance` close to the full `getFrozenV2BalanceForBandwidth()` (10 TRX).
5. Because `getV2NetUsage()` returns `0` (the subtraction of V1 frozen balance underflows and is clamped), the check `getFrozenV2BalanceForBandwidth() - 0 < delegateBalance` passes even though the account's true remaining V2-specific free balance (after accounting correctly for its own usage) should be lower, allowing delegation of resource that in a correct accounting model would have been rejected.

  public long calcCanDelegatedBandWidthMaxSize(
          ByteString ownerAddress) {
    AccountStore accountStore = chainBaseManager.getAccountStore();
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    AccountCapsule ownerCapsule = accountStore.get(ownerAddress.toByteArray());
    if (ownerCapsule == null) {
      return 0L;
    }

    BandwidthProcessor processor = new BandwidthProcessor(chainBaseManager);
    processor.updateUsage(ownerCapsule);

    long accountNetUsage = ownerCapsule.getNetUsage();
    accountNetUsage += TransactionUtil.estimateConsumeBandWidthSize(dynamicStore,
            ownerCapsule.getFrozenV2BalanceForBandwidth());

    long netUsage = (long) (accountNetUsage * TRX_PRECISION * ((double)
            (dynamicStore.getTotalNetWeight()) / dynamicStore.getTotalNetLimit()));

    long v2NetUsage = getV2NetUsage(ownerCapsule, netUsage, dynamicStore.disableJavaLangMath());

    long maxSize = ownerCapsule.getFrozenV2BalanceForBandwidth() - v2NetUsage;
    return max(0, maxSize, dynamicStore.disableJavaLangMath());
