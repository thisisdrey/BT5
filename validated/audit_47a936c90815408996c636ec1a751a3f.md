### Title
GitConfigOptions Client Field Can Override Gitaly's `core.hooksPath` and Disable Hook Enforcement in `PostReceivePack` - ([File: internal/gitaly/service/smarthttp/receive_pack.go])

### Summary
`PostReceivePackRequest.git_config_options` is a client-supplied, unauthenticated-content field (any ordinary user performing a push can set it) that is converted into `-c key=value` Git global options with only syntactic validation and no key blocklist. In `postReceivePack`, these client-controlled config pairs are appended to the `git-receive-pack(1)` invocation *after* Gitaly's own hook-configuration options (`core.hooksPath`, `receive.procReceiveRefs`), so a malicious value for one of these same keys silently overrides Gitaly's setting, because later `-c` occurrences win over earlier ones for single-valued Git config keys. This is the same bug class as the `setBridge()` report: a value that is meant to be fixed/trusted for a security check (there: `REMOTE_TOKEN`/`BRIDGE`; here: `core.hooksPath`) can instead be overwritten by an untrusted party, defeating the invariant the rest of the system relies on.

### Finding Description
`PostReceivePackRequest` carries a `git_config_options` field that any client performing a push controls: [1](#0-0) 

`postReceivePack` converts these attacker-controlled strings into `ConfigPair`s with `gitcmd.ConvertConfigOptions`, whose only validation is `GitConfig.Validate()` — it checks for a dot, absence of `=`, and a regex, but never blocks specific keys such as `core.hooksPath`: [2](#0-1) [3](#0-2) 

Crucially, in the receive-pack command construction, the client-supplied `config` is appended **after** `gitcmd.WithReceivePackHooks(...)`, which is the option responsible for injecting Gitaly's own `core.hooksPath` (and, when transactions are enabled, `receive.procReceiveRefs`): [4](#0-3) 

`WithReceivePackHooks` → `configureHooks` is what sets the trusted hook path and the proc-receive routing config: [5](#0-4) [6](#0-5) 

Both the server-injected pairs and the client-supplied pairs end up in the same `cc.globals` slice, appended via `WithConfig`: [7](#0-6) 

Because Git config resolution treats a later `-c key=value` occurrence as authoritative for single-valued keys (same semantics as later lines in a config file), a client-supplied `git_config_options: ["core.hooksPath=<attacker path>"]` overrides Gitaly's own hooksPath value that was appended earlier in the argument list. The same reasoning applies to `receive.procReceiveRefs`, which Gitaly relies on to route ref updates through its write-ahead log/proc-receive hook: [8](#0-7) 

This mirrors the external report's bug class exactly: a security-relevant value (`REMOTE_TOKEN`/`BRIDGE` there, `core.hooksPath`/`receive.procReceiveRefs` here) that the system assumes is fixed and trustworthy can instead be clobbered by an untrusted party (there: privileged owner; here: an ordinary pushing client), because the "set trusted value" step and the "let caller supply value" step are not properly isolated/ordered/validated.

### Impact Explanation
If `core.hooksPath` is overridden, Git will no longer invoke Gitaly's `gitaly-hooks`-backed `pre-receive`, `update`, `post-receive`, and `reference-transaction` hooks for that push. These hooks are Gitaly's sole mechanism for injecting access checks, transaction voting, and GitLab custom hooks during a push. Losing them means: reference updates can bypass access-control/quota enforcement normally performed in hook logic, and — if `receive.procReceiveRefs` is also neutralized — ref updates can bypass the write-ahead log transaction path entirely. This is a hook/quarantine-gating bypass reachable directly from an ordinary user's authenticated push, with no privileged access required.

### Likelihood Explanation
Likelihood is high for any deployment that honors the `git_config_options` field from `PostReceivePackRequest`/`SSHReceivePackRequest` without an allowlist: any authenticated user permitted to push can attach a crafted `git_config_options` entry to their request. The RPC-level tests in the repo (`TestPostReceivePack_rejectViaGitConfigOptions`, `TestInfoRefsUploadPack_gitConfigOptions`) confirm that arbitrary keys such as `receive.MaxInputSize` and `uploadpack.hideRefs` are indeed honored end-to-end, demonstrating the field is fully functional and unfiltered: [9](#0-8) 

I could not fully verify within the available context whether `internal/gitaly/service/ssh/receive_pack.go` places `WithConfig` in the same vulnerable position relative to `WithReceivePackHooks` (the file segment I could inspect stopped before the final command-construction call), so that code path should be checked as part of remediation.

### Recommendation
- Reorder command construction so that Gitaly-injected, security-critical `ConfigPair`s (`core.hooksPath`, `receive.procReceiveRefs`, `receive.advertisePushOptions`, etc.) are always appended **last**, after any client-supplied `git_config_options`, so they cannot be overridden.
- Alternatively/additionally, add an explicit denylist/allowlist in `gitcmd.ConvertConfigOptions` (or a wrapper used specifically for client-supplied config) that rejects keys known to control hook execution, quarantine, or transaction routing (`core.hooksPath`, `receive.procReceiveRefs`, `uploadpack.packObjectsHook`, etc.) regardless of ordering.
- Add a regression test asserting that a client-supplied `git_config_options` entry for `core.hooksPath` (and `receive.procReceiveRefs`) has no effect on hook execution for `PostReceivePack` and `SSHReceivePack`.

### Proof of Concept
1. As an ordinary user with push access, open a `PostReceivePack` (smarthttp) or `SSHReceivePack` stream to a repository.
2. Send the first request with `GitConfigOptions: ["core.hooksPath=/tmp/empty-or-attacker-dir"]` alongside the normal push payload.
3. Because `WithConfig(config...)` is invoked after `WithReceivePackHooks(...)` in `postReceivePack`, the attacker's `-c core.hooksPath=...` argument appears later on the `git-receive-pack` command line than Gitaly's own `-c core.hooksPath=<real hooks dir>`, so Git resolves the client's value as authoritative. [4](#0-3) 
4. Git executes hooks (if any) from the attacker-specified directory instead of Gitaly's real hooks directory, meaning `pre-receive`/`update`/`post-receive`/`reference-transaction` hooks that Gitaly relies on for enforcement are silently skipped (if the directory is empty) or replaced with attacker-controlled behavior (if the attacker can place executables at that path).

```go
func (cfg GitConfig) Validate() error {

		return cfgerror.NewValidationError(cfgerror.ErrNotSet, "key")
	}

			fmt.Errorf(`key %q cannot contain "="`, cfg.Key),
			"key",
		)
	}

		return cfgerror.NewValidationError(
			fmt.Errorf("key %q must contain at least one section", cfg.Key),
			"key",
		)
	}
	if strings.HasPrefix(cfg.Key, ".") || strings.HasSuffix(cfg.Key, ".") {
```

```go
// ConvertConfigOptions converts `<key>=<value>` config entries into `ConfigPairs`.
func ConvertConfigOptions(options []string) ([]ConfigPair, error) {
	configPairs := make([]ConfigPair, len(options))

	for i, option := range options {
		configPair := strings.SplitN(option, "=", 2)
		if len(configPair) != 2 {
			return nil, fmt.Errorf("cannot convert invalid config key: %q", option)
		}

		configPairs[i] = ConfigPair{Key: configPair[0], Value: configPair[1]}
	}

	return configPairs, nil
}
```

```go
// WithReceivePackHooks returns an option that populates the safe command with the environment
// variables necessary to properly execute the pre-receive, update, post-receive, and proc-receive
// (if enabled) hooks for git-receive-pack(1).
func WithReceivePackHooks(objectHash git.ObjectHash, req ReceivePackRequest, protocol string, enableProcReceive bool) CmdOpt {
	return func(ctx context.Context, cfg config.Cfg, gitCmdFactory CommandFactory, cc *cmdCfg) error {
		requestedHooks := ReceivePackHooks
		if enableProcReceive {
			// When transactions are in use, Git should only invoke pre-receive and proc-receive.
			// Our proc-receive implementation handles invoking the later hooks.
			requestedHooks = PreReceiveHook | ProcReceiveHook
		}

		if err := cc.configureHooks(ctx, cfg, objectHash, req.GetRepository(), gitCmdFactory, &UserDetails{
			UserID:   req.GetGlId(),
			Username: req.GetGlUsername(),
			Protocol: protocol,
			RemoteIP: metadata.GetValue(ctx, "remote_ip"),
		}, requestedHooks); err != nil {
			return err
		}

		return nil
	}
}
```

```markdown
### Proc-receive hook

The `git-receive-pack(1)` executes the proc-receive hook for commands that have a
matching prefix with the multi-valued config variable `receive.procReceiveRefs`.
When the variable is set, the hook executes these commands instead of the internal
`execute_commands()` function. This transfers the responsibility of making
reference updates to the hook. The hook executes once for the receive operation.
The hook takes no arguments, but uses a _pkt-line format_ protocol to communicate
with `git-receive-pack(1)` to read commands and push options, and send results.

In Gitaly, we use this mechanism to intercept updates to references made directly
via Git. This hook allows us to capture any updates to references made and route
them through the write-ahead log's write queue. This ensures that we account for
every reference update and log all reference updates.

The write-ahead log eventually will go over the log and commit each transaction where
it will call `git-update-ref(1)` to do the reference update.
```
