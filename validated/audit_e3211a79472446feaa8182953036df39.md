Audit Report

## Title
`propose_curator`'s top-level-bounty branch omits the `SpendContext` aggregation guard used elsewhere in `pallet-multi-asset-bounties`, allowing a `SpendOrigin`'s per-invocation `max_amount` cap to be bypassed via batched calls - ([File: substrate/frame/multi-asset-bounties/src/lib.rs])

## Summary
`Config::SpendOrigin`'s `Success` value is documented as "the maximum amount in a native asset that this origin is allowed to spend at a time" [1](#0-0) . `fund_bounty` enforces this correctly by wrapping the check in `with_context::<SpendContext<T::Balance>, _>`, which accumulates spend per `max_amount` bucket across an entire dispatch, catching batched over-spend [2](#0-1) , but `propose_curator`'s `None` (top-level bounty) branch performs only a bare, per-call `ensure!(native_amount <= max_amount, ...)` with no such accumulator [3](#0-2) .

## Finding Description
`propose_curator`'s top-level branch re-uses the identical `SpendOrigin`/`max_amount`/`native_amount` pattern as `fund_bounty` but checks only the single call in isolation:
```rust
None => {
    ensure!(maybe_sender.is_none(), BadOrigin);
    let max_amount = T::SpendOrigin::ensure_origin(origin)?;
    let native_amount = T::BalanceConverter::from_asset_balance(value, asset_kind)
        .map_err(|_| Error::<T, I>::FailedToConvertBalance)?;
    ensure!(native_amount <= max_amount, Error::<T, I>::InsufficientPermission);
},
``` [4](#0-3) 

By contrast, `fund_bounty` wraps the identical check in the shared `SpendContext` accumulator, tracking cumulative spend per `max_amount` bucket for the lifetime of the outer dispatch (including nested `utility::batch_all` calls), and rejecting once the running total for that `max_amount` bucket would be exceeded [5](#0-4) . `propose_curator` never enters this accumulator, so multiple `propose_curator` calls for different `CuratorUnassigned` top-level bounties bundled into one `utility::batch_all` extrinsic are each checked against the full `max_amount` independently, with no visibility into sibling calls in the same batch. The existing `fund_bounty_in_batch_respects_max_total` test demonstrates the intended aggregation behavior for `fund_bounty` [6](#0-5) , confirming that the same protection is absent for `propose_curator`.

`propose_curator` transitions a bounty from `CuratorUnassigned` to `Funded`, which is a prerequisite for the subsequent `accept_curator` → `award_bounty` path that releases the bounty's already-escrowed native value to a beneficiary chosen by the curator. This is a genuine inconsistency between two functions in the same pallet file that are meant to enforce the identical "per SpendOrigin invocation" ceiling on native-asset authorization.

## Impact Explanation
An entity holding a `SpendOrigin` scoped to authorize at most `max_amount` of native value "at a time" can batch several `propose_curator` calls for distinct top-level bounties (each individually within `max_amount`) into a single `utility::batch_all` extrinsic, re-activating the payout path for multiple bounties whose combined value exceeds the intended single-invocation ceiling. This matches the impact category of origin-gated spend authorization not conserving its intended "per authorization" bound before enabling downstream payout via `accept_curator`/`award_bounty`, since the aggregate re-curated value released can exceed what a single `SpendOrigin` use was designed to permit.

## Likelihood Explanation
The bug is reachable via public, unprivileged extrinsics (`utility::batch_all` wrapping `propose_curator`) by any account holding the configured `SpendOrigin`. No malicious validator, collator, relayer, or leaked-key assumption is required; it is a pure runtime logic gap inconsistent with the pallet's own established mitigation pattern used one function away in the same file (`fund_bounty`).

## Recommendation
Wrap the `max_amount`/`native_amount` check in `propose_curator`'s `None` branch with the same `with_context::<SpendContext<T::Balance>, _>` accumulation pattern used in `fund_bounty`, so that all `SpendOrigin`-gated value approvals (funding and re-curation) share one running total per `max_amount` bucket for the lifetime of the outer dispatch/batch.

## Proof of Concept
1. Configure a runtime where `SpendOrigin` for `pallet-multi-asset-bounties` grants an account/track `max_amount = X` per authorization.
2. Create and fund two top-level bounties, each with native value just under `X`, then unassign their curators via `unassign_curator` so both sit in `CuratorUnassigned`.
3. Submit `utility::batch_all { calls: [propose_curator(bounty_1, curator), propose_curator(bounty_2, curator)] }` from the `SpendOrigin` account.
4. Both calls independently pass `ensure!(native_amount <= max_amount, ...)` at line 795 because neither call is aware of the other's amount, whereas an equivalent `fund_bounty` batch exceeding `X` in aggregate is rejected by the `SpendContext` guard, as shown by `fund_bounty_in_batch_respects_max_total` [6](#0-5) .
5. Both bounties transition to `Funded`; subsequent `accept_curator`/`award_bounty` calls can release a combined value of `~2X`, exceeding the single-invocation ceiling the `SpendOrigin`'s `max_amount` was meant to enforce.
