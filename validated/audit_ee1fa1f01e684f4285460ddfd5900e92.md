### Title
`git_repository`/`git_override` submodule fetch disables Git's `protocol.file.allow` containment, letting a malicious repo read arbitrary local files into the build - (File: `tools/build_defs/repo/git_worker.bzl`)

### Summary
When `init_submodules`/`recursive_init_submodules` is enabled on `git_repository` (WORKSPACE) or the corresponding Bzlmod git repo rule, Bazel unconditionally runs `git submodule update` with `-c protocol.file.allow=always`. This globally re-enables the `file://` transport for *all* submodule URLs discovered while walking the fetched (attacker-controlled) repository's `.gitmodules` files, overriding Git's own default hardening (`protocol.file.allow=user`) that exists specifically to stop a malicious repository from using submodule entries to make Git read arbitrary local paths.

### Finding Description
`update_submodules` in [1](#0-0)  runs:
```
_git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--recursive", "--checkout", "--force")
```
for both the recursive and non-recursive cases. The comment explains the intent is compatibility with newer Git ("necessary for Git 2.38.1 and associated backport versions... allows the submodule command clone from a local directory", referencing bazelbuild/bazel#17040), but the flag is applied unconditionally to *every* submodule reference resolved from the fetched repository's own `.gitmodules` content — content that is fully controlled by whoever authored/serves that Git repository, not by the victim.

Git added the `protocol.<type>.allow` allowlist (defaulting `file`/`ext` to `user`, i.e. disallowed for automatically-invoked operations like submodule recursion) precisely to close the class of bugs where a hostile repository's `.gitmodules` specifies `url = file:///some/local/path` (or an absolute path treated as a local clone source) so that `git submodule update --init --recursive` copies arbitrary local filesystem content that the invoking user can read into the checked-out working tree. By force-setting `protocol.file.allow=always` for the whole submodule-update invocation, Bazel disables this containment check for every nested/transitive submodule entry that the malicious repository chooses to declare, not just for the legitimate cross-directory local-clone case the fix targeted.

This is directly analogous to the CVE-2023-37154 bug class: a mechanism intended to be a hard boundary (there, SSH command-argument sanitization in `check_by_ssh`; here, Git's `protocol.*.allow` transport allowlist) is disabled/bypassed by the tool itself, letting attacker-supplied input (there, monitoring check arguments; here, `.gitmodules` submodule URLs from a fetched repo) reach a sensitive operation (arbitrary local path access via the `file://` transport) that should have been blocked.

### Impact Explanation
An attacker who merely controls the content of a Git repository that a victim's Bazel build fetches via `git_repository` (or a Bzlmod `git_override`/module extension using the same `git_worker.bzl`) with `init_submodules = True` or `recursive_init_submodules = True` can declare a `.gitmodules` submodule entry with a `file://` URL pointing at an arbitrary path on the machine performing the fetch (e.g. another checked-out repo, SSH keys, credential files, other Bazel output bases). Because Bazel forces `protocol.file.allow=always`, Git will happily treat that path as a local repository to "clone" as a submodule, copying its contents into the external repository's working tree in the victim's output base. Those files then become part of the build graph — readable by subsequent build steps, potentially embedded into build outputs, or otherwise exfiltrated. This is a concrete read of content outside the intended repository/output-base boundary, enabled only because Bazel disabled the exact safeguard Git ships to prevent this.

### Likelihood Explanation
Likelihood is limited by the fact that a `file://` submodule URL only ever resolves to files/directories readable to the OS user account running the Bazel build (no privilege escalation), and by the requirement that the victim's `MODULE.bazel`/`WORKSPACE` opts into `init_submodules`/`recursive_init_submodules` for the untrusted repo. However, that opt-in is common for real-world dependencies with submodules, and the attacker needs no control beyond the content of the (already externally-served/untrusted) Git repository — matching the "hostile origin server" premise required by the rules. No credentials, sandbox bypass, or victim-machine access is needed beyond what the build already grants to the fetch step.

### Recommendation
Do not blanket-enable `protocol.file.allow=always` for the entire submodule tree of an untrusted, attacker-served repository. Instead:
- Scope the local-clone allowance narrowly to the specific known-safe case referenced in bazelbuild/bazel#17040 (e.g., only when the submodule URL is a relative path within the already-fetched repository directory), rather than passing a global `-c protocol.file.allow=always` to the whole `git submodule update --init --recursive` invocation.
- Consider validating/rejecting `.gitmodules` submodule URLs that use `file://` (or other non-network schemes) unless the URL is confined under the checkout directory, restoring the containment Git's own `protocol.file.allow=user` default provides.

### Proof of Concept
A `src/test/shell/bazel/git_repository_test.sh`-style shell integration test can demonstrate this:
1. Create a "secret" file/directory outside any repo checkout, e.g. `echo "top-secret" > $TEST_TMPDIR/secret/data.txt`, and `git init` it as a bare local git repo (`$TEST_TMPDIR/secret_repo`).
2. Create a malicious upstream repository `outer_repo` with a `.gitmodules` file:
   ```
   [submodule "evil"]
     path = evil
     url = file:///$TEST_TMPDIR/secret_repo
   ```
   committed alongside a stub `evil` gitlink entry, and served via a local git daemon/HTTP server (`serve_file`/`git daemon` as used elsewhere in `src/test/shell/bazel/git_repository_test.sh`).
3. In a Bazel workspace, declare:
   ```
   git_repository(
       name = "outer",
       remote = "<url of outer_repo>",
       commit = "<sha>",
       recursive_init_submodules = True,
   )
   ```
4. Run `bazel build @outer//...` and assert that `bazel-outer/evil/data.txt` (or the equivalent path in the external repo directory) now exists and contains `top-secret`, proving that content from `$TEST_TMPDIR/secret_repo` — a path entirely outside the fetched repository and outside the declared checkout — was pulled into the build tree solely because of the forced `protocol.file.allow=always` in `_git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", ...)` at [1](#0-0) .
