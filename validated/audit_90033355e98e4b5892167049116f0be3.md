### Title
Missing pending-transaction-queue update allows double-spend of account balance across uncertified Spice chunks - (File: `chain/client/src/rpc_handler.rs`, `chain/client/src/chunk_producer.rs`)

### Summary
The reported BoringDAO bug is a class of "stale-snapshot" vulnerability: a value that must be refreshed immediately before use (the oracle price) is instead read from an outdated snapshot, letting a downstream computation (rewards) operate on inconsistent data. In nearcore's Spice execution model, the analogous "value that must be refreshed" is the signer's account balance/nonce as validated against the last **certified** state. Because chunks under Spice execute asynchronously and several chunks can be produced against the same certified base state before any of them is certified, the runtime relies on the `PendingTransactionQueue` (`PendingConstraints`) to account for balance/nonce already consumed by other **uncertified** chunks. When this update path is skipped or disabled, validation falls back to the stale certified-state snapshot alone.

### Finding Description
`RpcHandlerActor::process_tx_internal` in [1](#0-0)  computes `(state_root, constraints)` from the **last certified** chunk extra. The `constraints` (`PendingConstraints`, tracking balance/gas-key balance/nonce already spent by transactions in not-yet-certified chunks) are only populated `if self.config.spice_pending_transaction_queue_enabled`; otherwise `PendingConstraints::default()` (all zero) is used [2](#0-1) .

The same gating occurs on the chunk-production side: `ChunkProducer::prepare_transactions` only invokes `PendingTxSession::check_pending` (which queries the pending-transaction-queue for `paid_from_balance`/`max_nonce`) `if ptq_enabled`; otherwise it always returns `PendingConstraints::default()` regardless of what other uncertified chunks have already committed [3](#0-2) . Likewise `reinitialize_pending_transaction_queue` — which rebuilds the queue after startup/reorgs from all currently-uncertified chunks — is a no-op unless `spice_pending_transaction_queue_enabled` is true [4](#0-3) .

The verifier itself documents that `pending` constraints are the mechanism that prevents inconsistency: `verify_and_charge_tx_ephemeral` computes `available_balance = account.amount().saturating_sub(pending.paid_from_balance)` and `effective_nonce = max(access_key.nonce, pending.max_nonce)` [5](#0-4) . If `pending` is always the zero default (because the queue was never updated/consulted), two or more independently-produced, still-uncertified chunks can each validate transactions from the same signer against the identical certified `account.amount()`/nonce, each believing the full balance/nonce range is available. Both chunks can pass local admission and consensus (block/chunk validity does not re-check cross-chunk balance sufficiency beyond the ephemeral per-chunk state), and when both are eventually certified and executed against the shared prior certified state, the signer's balance is effectively spent (or its nonce reused) more than the account actually allows — a token double-spend condition rooted purely in the omitted "update-before-read" step, exactly analogous to `RewardsManager.getAccruedYield()` using a stale oracle price instead of calling `_tryUpdateOracle()` first.

### Impact Explanation
If `spice_pending_transaction_queue_enabled` is left disabled (or the queue reinitialization is skipped after a reorg/restart) while Spice's asynchronous multi-chunk-in-flight execution model is active, a single account can have its balance debited by more than it holds across two or more uncertified chunks that both validate against the same certified snapshot, resulting in token creation/loss inconsistent with the account's true balance — a direct funds-theft/inflation-class impact matching the "concrete theft or permanent freezing of funds" acceptance criterion.

### Likelihood Explanation
This requires: (1) the Spice protocol feature to be active, and (2) the `spice_pending_transaction_queue_enabled` config to be false (or the queue to have been cleared/not yet reinitialized, e.g., right after a node restart or chain reorg per `reinitialize_pending_transaction_queue`), combined with (3) more than one uncertified chunk in flight for the same shard/signer — a normal condition under Spice's asynchronous execution given `MAX_PENDING_CHUNKS` (24) allowed outstanding chunks [6](#0-5) . Since this is a config/operational toggle rather than a hard protocol invariant, exploitability depends on deployment configuration, making likelihood medium rather than certain, but the code path itself contains no independent safety net once the flag is off.

### Recommendation
Do not allow the pending-transaction-queue consultation to be bypassed while Spice is active: either make `spice_pending_transaction_queue_enabled` mandatory (non-optional) whenever `ProtocolFeature::Spice` is enabled, or add a defense-in-depth check that recomputes/verifies aggregate balance and nonce usage across all currently uncertified chunks for a shard before certifying/executing them, so that a stale/zeroed `PendingConstraints` can never be silently substituted for the real value, mirroring how `LevelMintingV2` unconditionally calls the oracle update before reading a price.

### Proof of Concept
