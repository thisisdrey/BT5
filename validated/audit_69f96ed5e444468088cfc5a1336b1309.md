### Title
Malformed/overflowing `Content-Length` on HTTP requests is silently swallowed instead of rejected, enabling request framing desync - (File: stackslib/src/net/http/request.rs)

### Summary
`HttpRequestPreamble::consensus_deserialize` parses the `Content-Length` header with `value.parse::<u32>()` and, on any parse failure (non-numeric value, or a value that overflows `u32` such as `99999999999`), silently sets `content_length = None` and continues accepting the request as valid. The symmetric response-side parser in `net/http/response.rs` treats the identical failure condition as a hard `CodecError::DeserializeError`, showing the request-side behavior is an unintentional divergence rather than a designed default.

### Finding Description
In `stackslib/src/net/http/request.rs` (lines 392-398): [1](#0-0) 
the `content-length` branch does:
```
content_length = match value.parse::<u32>() {
    Ok(len) => Some(len),
    Err(_) => None,
};
```
Any header value that fails to parse as `u32` (non-numeric text, or a numeric value exceeding `u32::MAX`, e.g. `99999999999`) results in `content_length = None` with no error raised and no rejection of the request. The request preamble is accepted as well-formed.

By contrast, `net/http/response.rs` (lines 543-549) treats the same failure as fatal: [2](#0-1) 
```
let len = value.parse::<u32>().map_err(|_e| {
    CodecError::DeserializeError("Invalid Content-Length header value".to_string())
})?;
```

This is a broken invariant: the preamble's declared "content length" field no longer faithfully reflects what the attacker's declared Content-Length header actually said (a header was present and specified an intended body size), yet the parsed preamble looks identical to a request that never sent a Content-Length header at all. Downstream code that reads the request body length from the preamble (`get_content_length()`/equivalent accessors used throughout `net/api/*.rs` handlers, e.g. `posttransaction.rs`, `postblock.rs`, `poststackerdbchunk.rs`) cannot distinguish "no Content-Length header, treat body as absent/empty" from "attacker sent an invalid/oversized Content-Length, actual body bytes are unaccounted for." If the connection body-reading logic uses this field to decide how many bytes to consume from the socket before treating subsequent bytes as the next pipelined request preamble, a request with `Content-Length: 99999999999` followed by attacker-controlled bytes could result in those bytes never being consumed as body and instead being parsed as the start of a new HTTP request on the same keep-alive connection — a request-smuggling/framing desync condition.

### Impact Explanation
If exploitable via the connection body-consumption path, this allows an unprivileged remote client connecting to the RPC HTTP listener to desynchronize a keep-alive/pipelined connection: the server's view of "where the current request body ends and next request begins" diverges from the client's, allowing attacker-controlled bytes framed as one request's "body" to instead be interpreted as an independent, seemingly legitimate follow-on request. Depending on connection reuse (e.g. via any intermediary or connection pooling on the RPC port), this is a request-smuggling primitive against the node's own RPC endpoints, which matches the Critical category ("request smuggling or auth bypass").

### Likelihood Explanation
The attacker only needs to open a TCP connection to the node's RPC port (no secret, no peer identity, no StackerDB slot needed) and send a single crafted HTTP request such as:
```
POST /v2/transactions HTTP/1.1\r\nHost: x\r\nContent-Length: 99999999999\r\n\r\n<body bytes>
```
This requires no privileged role and is trivially repeatable at zero cost per attempt. The condition triggers deterministically whenever the parser accepts an invalid `Content-Length` value.

### Recommendation
Change `HttpRequestPreamble::consensus_deserialize` in `stackslib/src/net/http/request.rs` (lines 392-398) to mirror `response.rs`: return `CodecError::DeserializeError("Invalid Content-Length header value")` when `value.parse::<u32>()` fails, instead of silently defaulting to `None`.

### Proof of Concept
Add a test in `stackslib/src/net/http` (or wherever existing preamble parse tests live) that:
1. Constructs raw bytes: `b"POST /v2/transactions HTTP/1.1\r\nHost: x\r\nContent-Length: 99999999999\r\n\r\n<attacker body>"`.
2. Calls `HttpRequestPreamble::consensus_deserialize` (or `StacksHttp::try_parse_request`) on it.
3. Assert (current buggy behavior) that it returns `Ok(preamble)` with `preamble.content_length == None` despite the header being present and malformed — demonstrating the parser accepted an invalid declaration silently, which is inconsistent with `response.rs`'s `Err(CodecError::DeserializeError(..))` on the same input via a parallel test on `HttpResponsePreamble::consensus_deserialize`.
4. (Follow-up, requires tracing the connection-level body reader, which was not fully confirmed in this investigation) feed the two-request byte stream into the full connection handling loop and assert the "second request" parsed out is actually the leftover `<attacker body>` bytes from request 1.

Note: I confirmed the exact asymmetry in the two `consensus_deserialize` implementations (request.rs silently defaults to `None`; response.rs errors), which is the root cause claimed in the question. I was not able to fully trace, within the available tool budget, the exact body-consumption/pipelining loop that reads `get_content_length()` to determine how many bytes are consumed from the socket before parsing the next request, so I cannot confirm with full certainty whether downstream code treats `None` as "0 bytes to consume" (enabling smuggling) versus "reject request for missing required Content-Length" (which would only be a DoS/robustness issue, not smuggling). The parser-level bug itself — silently accepting a malformed request field that mirror code treats as fatal — is confirmed and real.
