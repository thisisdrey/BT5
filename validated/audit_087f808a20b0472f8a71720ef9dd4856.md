### Title
Zip Extraction Path-Containment Check Uses Raw String Prefix Without Separator Boundary, Allowing Sibling-Directory Escape - (`third_party/ijar/zip_main.cc`)

### Summary
The `unzip`-equivalent extraction routine built on top of ijar's zip reader validates that an extracted entry stays inside the intended output directory by normalizing both the output root and the candidate entry path and then doing a raw prefix `compare()` on the two strings. Exactly like the `view_component` `File.realpath` + `start_with?` bug, this check does not verify that a path separator immediately follows the shared prefix, so a sibling directory whose name has the output directory's name as a string prefix (e.g. `output_root_evil`) passes the check while being outside `output_root_`.

### Finding Description
In `UnzipProcessor::Process` [1](#0-0) , for every zip entry the code builds the destination path with `concat_path(path, sizeof(path), output_root_, output_file_name)`, normalizes both the candidate path and the output root with `normalize_path`, and then checks:

```cpp
std::string normalized_root = normalize_path(output_root_);
std::string normalized = normalize_path(path);
if (normalized.compare(0, normalized_root.size(), normalized_root) != 0) {
  fprintf(stderr, "paths in the zip may not end up outside of the output directory...");
  abort();
}
``` [2](#0-1) 

This is a bare string-prefix comparison: it only checks that `normalized` begins with the exact character sequence `normalized_root`, never that a path separator (`/`) immediately follows that prefix (or that the two strings are equal). Consequently, if `output_root_` is `/tmp/extract`, a zip entry name that normalizes to `/tmp/extract_evil/payload` (e.g. an entry literally named `../extract_evil/payload` relative to a root ending in `extract`, or any entry whose `..`-resolved path lands in a directory that shares `output_root_` as a string prefix) satisfies `normalized.compare(0, normalized_root.size(), normalized_root) == 0` even though `/tmp/extract_evil` is a completely different, sibling directory outside `/tmp/extract`. The check "stops" absolute escapes and most `../../` traversal into unrelated trees, but it does not stop escapes into a sibling directory that happens to share the same name prefix as the target extraction root — the exact class of bug described in the report (CWE-22/CWE-187).

This mirrors `paths.bzl`'s own `_starts_with` helper, which *does* correctly check the separator boundary (`norm_a[len(norm_b)] == "/"`) [3](#0-2) , and `git.bzl`'s `strip_prefix`/`add_prefix` checks, which append `"/"` to the base before calling `startswith` [4](#0-3) [5](#0-4)  — showing that Bazel is aware elsewhere in the codebase that a raw prefix check is insufficient, but the ijar zip extractor's C++ implementation omits this separator check entirely.

### Impact Explanation
An attacker who controls the contents of a zip archive that Bazel (or a build extracts via this ijar-based unzip tool) processes can craft entry names that, after `concat_path` + `normalize_path`, resolve to a path in a sibling directory of the intended extraction root while still passing the containment check. This allows writing/overwriting arbitrary files outside the intended extraction directory (a write primitive outside the intended repository/extraction root), which is a real containment-check bypass matching the report's bug class. The severity in Bazel's context depends on which callers rely on `output_root_` as a security boundary rather than a mere destination hint; regardless, the check as written provides a false sense of containment.

### Likelihood Explanation
Exploitation only requires the attacker to control the byte content of a zip file consumed by this extractor (e.g. an archive fetched from an attacker-controlled/compromised mirror, or a crafted artifact in a build), i.e. an unprivileged, remote content producer — no local machine access or credentials are required. The vulnerable pattern is reached on every entry of every processed zip archive whenever `extract_` is true, so it is reachable code, not a corner case.

### Recommendation
Change the containment check in `UnzipProcessor::Process` to require a path-separator boundary (or exact equality) after the shared prefix, e.g.:
```cpp
bool contained =
    normalized.size() == normalized_root.size()
        ? normalized == normalized_root
        : normalized.compare(0, normalized_root.size(), normalized_root) == 0 &&
          normalized.size() > normalized_root.size() &&
          normalized[normalized_root.size()] == '/';
if (!contained) { ... abort(); }
```
Add regression tests (in `third_party/ijar/test/zip_test.sh`) covering: a normal entry inside the output root, an entry resolving to a sibling directory sharing the root's name as a prefix (e.g. `output_root_evil/file`), and `../`-based absolute escapes, asserting the extractor rejects the sibling-directory and traversal cases while accepting the normal case.

### Proof of Concept
Because I could not fully trace every caller of this `unzip` binary within the remaining investigation budget, I present the PoC as a targeted unit-test scenario for `third_party/ijar/test/zip_test.sh` (the existing zip test harness) rather than a full end-to-end Bazel build reproduction:

1. Create output root directory `OUT=/tmp/ijar_extract`.
2. Craft a zip archive `evil.zip` containing an entry whose relative name, when concatenated with `OUT` and normalized, resolves to `/tmp/ijar_extract_evil/pwned.txt` (this can be achieved by naming the extraction root itself, e.g. running the tool with `output_root_ = /tmp/ijar_extract` and an entry name that starts with enough `../` segments combined with `ijar_extract_evil/pwned.txt` such that `normalize_path` on the concatenated path yields `/tmp/ijar_extract_evil/pwned.txt`).
3. Run the `unzip` tool (built from `zip_main.cc`) with `-x -d /tmp/ijar_extract evil.zip`.
4. Observe: the containment check `normalized.compare(0, normalized_root.size(), normalized_root)` succeeds (both strings share the `/tmp/ijar_extract` prefix) and `pwned.txt` is written to `/tmp/ijar_extract_evil/pwned.txt`, outside the intended `/tmp/ijar_extract` tree — demonstrating the sibling-directory escape.

This scenario requires precise crafting of the zip entry name to make `normalize_path` produce a string with the vulnerable prefix relationship; I was not able to execute this end-to-end within the available tool budget, so the exact entry-name string needed should be worked out empirically against the `normalize_path`/`concat_path` implementations in `third_party/ijar/platform_utils.cc` before filing as a confirmed, reproducible finding.
