This confirms the mechanism: `action_implicit_account_creation_transfer` (`runtime/runtime/src/actions.rs:213-267`) creates a `0s...` deterministic account via a bare `Transfer` with `AccountContract::None` (calling `create_deterministic_account`), leaving it in an "uninit" state holding only a balance. Later, `action_deterministic_state_init` (`runtime/runtime/src/deterministic_account_id.rs:38-52`) deploys code/data **only if `account.contract().is_none()`**, and otherwise silently does nothing — it never re-verifies that a pre-existing contract actually matches the `state_init` supplied. The only binding check is `validate_deterministic_state_init` (`runtime/runtime/src/action_validation.rs:435-449`), which recomputes `derive_near_deterministic_account_id(state_init)` — `'0s' + keccak256(borsh(state_init))[12:32]` — and compares it to the receiver id. This is a 256-bit hash truncated to 160 bits, structurally identical to the Panoptic `validateCallback` pattern in the report: address uniqueness is assumed from a truncated hash rather than cryptographically enforced. ### Title
Deterministic account ("0s…") pre-funding is vulnerable to a truncated-hash birthday collision, permanently hijacking the account's contract - (File: runtime/runtime/src/deterministic_account_id.rs)

### Summary
`derive_near_deterministic_account_id` truncates a 256-bit Keccak256 digest of the borsh-encoded `DeterministicAccountStateInit` to 160 bits to form the `0s…` account id [4](#0-3) . `validate_deterministic_state_init` only checks that this truncated hash equals the receiver id [3](#0-2) , and `action_deterministic_state_init` deploys the supplied code/data unconditionally the first time an account with `AccountContract::None` receives a `DeterministicStateInitAction`, and is a silent no-op on every subsequent attempt [2](#0-1) . As with the reported `CallbackLib.validateCallback()` bug, the derivation is exposed to pigeonhole/birthday-style truncated-hash collisions: because `data: BTreeMap<Vec<u8>, Vec<u8>>` (and the `code` global-contract identifier) are entirely attacker-controlled with a huge input space, an attacker can search for their own `DeterministicAccountStateInit` whose derived 160-bit id collides with the address of a legitimately pre-funded but not-yet-deployed deterministic account.

### Finding Description
A `0s…` deterministic account can exist in an "uninit" state — created purely via a `Transfer` (`action_implicit_account_creation_transfer`, which calls `create_deterministic_account` giving `AccountContract::None`) — before the actual `DeterministicStateInitAction` deploying its intended code and data is ever submitted [1](#0-0) . This is an explicitly documented pattern: "A `Transfer` can also deposit a balance before the `DeterministicStateInitAction`. The account will not be usable, however, until the `DeterministicStateInitAction` is also executed" [5](#0-4) .

Because address uniqueness rests solely on the 160-bit truncation of a Keccak256 hash over attacker-controllable bytes, an attacker who knows (or predicts) the target `0s…` address of a not-yet-deployed, pre-funded deterministic account can brute-force search an arbitrary `DeterministicAccountStateInit` (their own `code` global-contract identifier plus arbitrary `data`) whose derived id collides with that address. They then submit `DeterministicStateInitAction` with their colliding `state_init` to that address. Since `account.contract().is_none()` at that point, `action_deterministic_state_init` deploys the attacker's code and data unconditionally [6](#0-5) . When the legitimate owner later submits the real `DeterministicStateInitAction`, the check at `deterministic_account_id.rs:38` (`account.contract().is_none()`) is now false, so the runtime "does nothing" and silently accepts the transaction without redeploying or validating that the existing contract matches the intended state_init — the account permanently keeps the attacker's contract, while the previously-transferred balance and the legitimate deposit refund flow to the attacker-controlled code.

Just as the original report notes for `2^160`-bit EVM addresses derived from `keccak256`, finding *any* collision between an attacker-chosen search space and a set of legitimately precomputed (but undeployed) target addresses is a birthday-style search requiring roughly `2^80` hash operations rather than a full `2^160` preimage search — the same asymmetric economics discussed in the report apply here, since the account id encoding is likewise a naive keccak256-truncated-to-160-bit scheme with no additional entropy or on-chain existence check binding the address to a single valid parameter set.

### Impact Explanation
If exploited, an attacker permanently redirects control of a deterministic account — including any balance transferred to it in anticipation of legitimate deployment — to a contract of their choosing, since the deployment check only fires once and is never re-validated against the actual `state_init` afterward. This is a concrete theft/permanent-hijack primitive on an unprivileged, ordinary-transaction code path (`Transfer` + `DeterministicStateInitAction`), matching the "concrete theft of funds" and "authorization escalation" categories.

### Likelihood Explanation
Like the original report, exploitation requires substantial (but, per the cited real-world economics, plausibly attainable for a well-resourced attacker within a multi-year horizon) compute to find a 160-bit truncated-hash collision via the birthday method. It further requires a legitimate protocol/dApp pattern of pre-funding deterministic accounts before their `DeterministicStateInitAction` is executed — a pattern the NEAR docs explicitly describe as supported [7](#0-6) , making it a realistic usage pattern rather than a hypothetical one.

### Recommendation
Do not rely solely on the truncated 160-bit id as unique proof of the parameters that produced it. Options: (1) re-validate on every `DeterministicStateInitAction` that an *already-deployed* account's code/data actually matches the given `state_init` (reject with a distinct error if it doesn't, rather than silently no-op'ing), and/or (2) widen the truncation (e.g., use the full 256-bit hash, or a longer non-EVM-compatible encoding) for the `0s…` id so that birthday-style collisions become computationally infeasible, consistent with recommending full-preimage security margins for any address that is trusted before on-chain deployment.

### Proof of Concept
1. A dApp or user precomputes `X = derive_near_deterministic_account_id(state_init_A)` for a legitimate `state_init_A` (global contract code + specific data), and funds `X` via `Transfer` before submitting the `DeterministicStateInitAction` for `A` (this is a documented supported flow).
2. An attacker performs a birthday search over attacker-chosen `state_init_B` candidates (varying `data`/`code`) against known pre-funded-but-undeployed `0s…` addresses like `X`, until `derive_near_deterministic_account_id(state_init_B) == X`.
3. Attacker submits `DeterministicStateInitAction{state_init: state_init_B, deposit: 0}` with receiver `X`. `validate_deterministic_state_init` passes because the derived id matches [8](#0-7) ; `action_deterministic_state_init` sees `account.contract().is_none()` and deploys attacker's code/data [6](#0-5) .
4. The legitimate owner later submits `DeterministicStateInitAction{state_init: state_init_A}` to `X`; the id check still passes (matches by design), but `account.contract().is_none()` is now false, so deployment is skipped entirely — `X` permanently runs the attacker's contract, controlling the pre-funded balance and any future funds sent to `X`.

/// Returns a NEP-616 compliant deterministic account id.
/// This is a NEAR-implicit account ID which is fully defined by its initial state.
pub fn derive_near_deterministic_account_id(
    state_init: &DeterministicAccountStateInit,
) -> AccountId {
    use sha3::Digest;
    let mut hasher = sha3::Keccak256::new();
    borsh::to_writer(&mut hasher, state_init).expect("borsh must not fail");
    let hash: [u8; 32] = hasher.finalize().into();
    format!("0s{}", hex::encode(&hash[12..32])).parse().unwrap()
}
