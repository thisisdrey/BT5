### Title
Users lose unclaimed airdrop rewards when `updateMerkleRoot` replaces the current root - (File: contracts/utils/RecurringAirdrop.sol)

### Summary
`RecurringAirdrop` (deployed on mainnet as `MetAirdrop`, see `deployments/mainnet/MetAirdrop.json`) keeps a single `merkleRoot` that is overwritten each distribution round by `updateMerkleRoot()`. `claim()` verifies proofs only against the current root, so once a new root is set, any user whose allocation is not carried forward into the new tree (as a cumulative amount) permanently loses their unclaimed rewards. Additionally, if a user's cumulative amount in the new tree is lower than their already-`claimed` total, `amount_ - claimed[msg.sender]` underflows and their claim reverts forever.

### Finding Description
`claim()` builds the leaf as `keccak256(abi.encodePacked(msg.sender, amount_))` and verifies it against the single mutable `merkleRoot` state variable [1](#0-0) . `updateMerkleRoot()` is called by the governor each round and simply overwrites `merkleRoot` — no history of past roots is kept [2](#0-1) .

The protocol's intended mitigation is that each leaf encodes the *cumulative* entitlement, and `claimed[msg.sender]` tracks how much was already paid out, so users can skip rounds [3](#0-2) . The test suite confirms this assumption: "should receive accumulated amount when only claiming on 2st round" only works because `rewards1[alice]` is the cumulative total [4](#0-3) .

However, this mitigation is purely a convention about off-chain tree construction, not an on-chain invariant:

1. If a user who has not yet claimed is omitted from the next tree (or included with only their *new-round* amount rather than the cumulative total), their proof from the old round is invalid against the new root and there is no fallback path — the rewards are permanently frozen in the contract.
2. If a user's cumulative amount in a new root is ever lower than `claimed[user]` (e.g., a corrected/recomputed tree), the subtraction `amount_ - claimed[msg.sender]` reverts, so even a valid proof cannot be executed — a permanent DoS on that user's remaining claim [5](#0-4) .

`MetAirdrop` inherits this exact behavior and additionally locks claimed MET into esMET positions, so stranded claims are real user funds [6](#0-5) .

### Impact Explanation
Permanent freezing of unclaimed yield: any allocation not carried into the latest merkle root becomes unclaimable. The tokens remain in the airdrop contract with no recovery path for the affected user.

### Likelihood Explanation
The contract is explicitly designed for *recurring* root updates (`updateMerkleRoot`, `updatedAt`, `proofsFileHash` rotation), so the root-replacement event is guaranteed to happen each round. The loss occurs whenever the off-chain tree generation fails to carry forward every unclaimed cumulative balance — an operational convention with no on-chain enforcement.

### Recommendation
Keep a registry of historical roots (e.g., `bytes32[] public merkleRoots` or `mapping(uint256 => bytes32)`) and let `claim()` accept a round/index parameter, verifying the proof against the corresponding root. Alternatively, require `claim()` to specify the round and keep per-round claimed accounting, so old allocations remain claimable regardless of later root updates.

### Proof of Concept

```ts
// Hardhat, based on test/MetAirdrop.test.ts fixture
it('unclaimed rewards are lost after root update when user omitted from new tree', async () => {
  // Round 0: alice has an allocation in merkleTree0
  const amount0 = rewards0[alice.address]
  const leaf0 = generateLeaf(alice.address, amount0)
  const proof0 = merkleTree0.getHexProof(leaf0)

  // Alice does NOT claim in round 0.

  // Governor publishes round 1 tree that does not carry alice's balance forward
  // (e.g., a tree built only over bob, or with a lower cumulative amount for alice)
  await airdrop.updateMerkleRoot(merkleRoot1WithoutAlice, `0x${randomBytes(32).toString('hex')}`)

  // Alice's old proof is now invalid: reverts InvalidProof()
  await expect(airdrop.connect(alice).claim(amount0, proof0)).to.be.revertedWith('InvalidProof')

  // And a user whose new cumulative amount < claimed[] also reverts on underflow:
  // amount_ - claimed[msg.sender] -> panic / revert
})
```
