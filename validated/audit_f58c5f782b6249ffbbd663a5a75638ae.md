Audit Report

## Title
Snowbridge tip funds are irrecoverably burned and lost on remote-dispatch failure with no refund/claim mechanism - (File: `bridges/snowbridge/pallets/system-v2/src/lib.rs`, `bridges/snowbridge/pallets/system-frontend/src/lib.rs`)

## Summary
`pallet-snowbridge-system-frontend::add_tip` on AssetHub swaps the user's tip asset for Ether and irreversibly burns it via `burn_for_teleport` before dispatching an XCM `Transact` to BridgeHub's `snowbridge-pallet-system-v2::add_tip`. If that remote call fails (e.g. the target nonce was already consumed, or the outbound order no longer exists), the already-burned value is only recorded into a `LostTips` storage map keyed by sender, and there is no dispatchable, hook, or trait method anywhere in the pallet that reads and pays out or clears `LostTips`.

## Finding Description
On AssetHub, `add_tip` calls `ensure_signed`, then `swap_fee_asset_and_burn`, which swaps the tip asset for ether and calls `burn_for_teleport::<T::AssetTransactor>`, destroying the asset synchronously within the same extrinsic before any XCM has been delivered or executed on BridgeHub. [1](#0-0) [2](#0-1) 

The value is only "recreated" as a reward if the remote `Transact` executes successfully on BridgeHub, where `EthereumSystemV2::add_tip` forwards the call to either `InboundQueue::add_tip` or `OutboundQueue::add_tip` depending on `message_id`. [3](#0-2) 

If the underlying queue rejects the tip (nonce already consumed / order no longer found), the error is caught and only bookkept into `LostTips`, with `TipProcessed{success: false}` emitted — the extrinsic itself still returns `Ok(())`. [4](#0-3) 

`LostTips` is declared with a comment explicitly acknowledging that no recovery mechanism is implemented ("Capturing the lost tips here supports implementing a recovery method in the future"). [5](#0-4) 

A repository-wide search for `LostTips` confirms it is written to only in `system-v2/src/lib.rs` and read only in test files (`system-v2/src/tests.rs`, `snowbridge_v2_outbound.rs` integration test) — there is no extrinsic, hook, or governance call anywhere in the codebase that reads `LostTips` and pays it back out to the `sender`. The burn on AssetHub (steps in `system-frontend::add_tip`) and the tip-registration attempt on BridgeHub (`system-v2::add_tip`) execute in entirely separate transactions/blocks on separate chains with no atomicity guarantee tying them together, so a benign timing race (relayer processing the target nonce before the delayed `Transact` executes) is sufficient to strand the burned value forever.

## Impact Explanation
This results in permanent, unrecoverable loss of real user funds (the swapped/burned tip asset value) with no path to reclaim it, matching the "permanent user-fund or bridge-state lock" category of the accepted impact gate. The corrupted/stranded value is exactly the `u128` amount recorded in `LostTips::<T>` keyed by `sender` in `bridges/snowbridge/pallets/system-v2/src/lib.rs`, which represents burned Ether that was never re-minted or refunded to its rightful owner.

## Likelihood Explanation
High and requires no privileged or malicious actor. Any ordinary signed user calling `add_tip` for a message whose nonce is consumed by normal relayer activity concurrently with, or before, their XCM `Transact` executes on BridgeHub will trigger this loss — a purely benign race condition caused by the lack of atomicity between the AssetHub burn and the BridgeHub-side registration. The affected code paths (`system-frontend::add_tip`, `system-v2::add_tip`) are both public, unprivileged, signed-origin extrinsics.

## Recommendation
Do not irreversibly burn/withdraw the tip asset on AssetHub until the remote registration success is confirmed (e.g., use an escrow/hold pattern with a settlement callback), or implement a documented recovery/refund extrinsic gated on `LostTips::<T>::take(sender)` that mints/teleports the recorded amount back to the original sender. At minimum, add a receipt/refund callback mechanism so that a failed remote registration reverses the burn atomically rather than leaving it in a write-only, unreadable ledger entry.

## Proof of Concept
1. User calls `SnowbridgeSystemFrontend::add_tip(origin, MessageId::Inbound(N), asset)` on AssetHub for inbound nonce `N` not yet fully processed.
2. `swap_fee_asset_and_burn` swaps `asset` for ether and calls `burn_for_teleport`, irreversibly destroying `amount` on AssetHub within the same extrinsic (`bridges/snowbridge/pallets/system-frontend/src/lib.rs:267,372-404`).
3. The pallet builds and sends an XCM `Transact` carrying `EthereumSystemCall::AddTip{ sender, message_id: Inbound(N), amount }` to BridgeHub (`bridges/snowbridge/pallets/system-frontend/src/lib.rs:271-272,406-423`).
4. Before or concurrently with the `Transact` executing on BridgeHub, a relayer processes message `N` via the inbound queue, consuming its nonce.
5. When the delayed `Transact` executes, `EthereumSystemV2::add_tip` calls `InboundQueue::add_tip(N, amount)`, which returns an error because the nonce was already consumed (`bridges/snowbridge/pallets/system-v2/src/lib.rs:262`).
6. `EthereumSystemV2::add_tip` catches the error and only performs `LostTips::<T>::mutate(&sender, |lost_tip| *lost_tip = lost_tip.saturating_add(amount))`, emitting `TipProcessed{success: false}` while the call still returns `Ok(())` (`bridges/snowbridge/pallets/system-v2/src/lib.rs:266-280`).
7. The user's `amount` was already burned in step 2 and is now permanently unrecoverable — grepping the repository for `LostTips` confirms no extrinsic exists anywhere to reclaim the value tracked there.

		fn swap_fee_asset_and_burn(
			origin: Location,
			fee_asset: Asset,
		) -> Result<u128, DispatchError> {
			let ether_location = T::EthereumLocation::get();
			let (fee_asset_location, fee_amount) = match fee_asset {
				Asset { id: AssetId(ref loc), fun: Fungible(amount) } => (loc, amount),
				_ => {
					tracing::debug!(target: LOG_TARGET, ?fee_asset, "error matching fee asset");
					return Err(Error::<T>::UnsupportedAsset.into());
				},
			};
			if fee_amount == 0 {
				return Ok(0);
			}

			let ether_gained = if *fee_asset_location != ether_location {
				Self::swap_and_burn(
					origin.clone(),
					fee_asset_location.clone(),
					ether_location,
					fee_amount,
				)
				.inspect_err(|&e| {
					tracing::debug!(target: LOG_TARGET, ?e, "error swapping asset");
				})?
			} else {
				burn_for_teleport::<T::AssetTransactor>(&origin, &fee_asset)
					.map_err(|_| Error::<T>::BurnError)?;
				fee_amount
			};
			Ok(ether_gained)
		}

		#[pallet::call_index(3)]
		#[pallet::weight(<T as pallet::Config>::WeightInfo::add_tip())]
		pub fn add_tip(
			origin: OriginFor<T>,
			sender: AccountIdOf<T>,
			message_id: MessageId,
			amount: u128,
		) -> DispatchResult {
			T::FrontendOrigin::ensure_origin(origin)?;

			let result = match message_id {
				Inbound(nonce) => <T as pallet::Config>::InboundQueue::add_tip(nonce, amount),
				Outbound(nonce) => <T as pallet::Config>::OutboundQueue::add_tip(nonce, amount),
			};

			if let Err(ref e) = result {
				tracing::debug!(target: LOG_TARGET, ?e, ?message_id, ?amount, "error adding tip");
				LostTips::<T>::mutate(&sender, |lost_tip| {
					*lost_tip = lost_tip.saturating_add(amount);
				});
			}

			Self::deposit_event(Event::<T>::TipProcessed {
				sender,
				message_id,
				amount,
				success: result.is_ok(),
			});

			Ok(())
		}
