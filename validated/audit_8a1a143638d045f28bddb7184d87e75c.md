### Title
Unbounded array allocation from attacker-controlled length field in TVM precompiled-contract ABI decoding causes OutOfMemoryError / node crash - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
Several helper methods used by TVM precompiled contracts (`extractBytes32Array`, `extractBytesArray`, `extractSigArray`) allocate an array whose size is taken directly from a 256-bit word in the attacker-supplied calldata, with only a value-safety cast and no check against the actual size of `data` or any hard upper bound, mirroring the "unbounded allocation from untrusted input" bug class of CVE-2018-16865.

### Finding Description
`extractBytes32Array`, `extractBytesArray`, and `extractSigArray` each read a "length" word from the decoded ABI `words` array and immediately allocate a two-dimensional `byte[][]` of that length before any bound checking against `data.length`: [1](#0-0) [2](#0-1) [3](#0-2) 

`len = words[offset].intValueSafe()` converts an attacker-controlled 256-bit calldata word into a Java `int` used directly as the array dimension. The only guard present is `offset > words.length - 1` (checking that the *offset* pointer is in range), not that `len` is consistent with the amount of data actually supplied. A caller can therefore craft calldata where the "array length" word encodes a very large value (e.g. close to `Integer.MAX_VALUE`), causing `new byte[len][]` to attempt to allocate an array of that many object references (roughly 4–8 bytes per reference), which throws `OutOfMemoryError` or otherwise exhausts significant heap before the loop that would populate/bound-check the elements ever executes.

This is directly analogous to the CVE-2018-16865 pattern: a size value taken from untrusted input is used to drive a memory allocation with no upper limit enforced prior to the allocation itself.

### Impact Explanation
`PrecompiledContracts` implementations back the fixed-address native contracts invocable from any smart contract via `CALL`/`STATICCALL` inside a normal, unprivileged transaction (any contract deployer or caller can construct calldata reaching these precompiles). Triggering `OutOfMemoryError` inside the shared TVM execution path can destabilize or crash the node process handling the transaction, since Java's `OutOfMemoryError` is frequently unrecoverable and can corrupt JVM state for the whole process, not just the calling thread — leading to a denial-of-service against the node.

### Likelihood Explanation
Reaching these code paths only requires submitting a signed transaction (or an internal contract call) whose calldata is routed to a precompiled contract that uses one of the vulnerable `extract*Array` helpers. No special privilege, node role, or previous compromise is required — this is reachable by any ordinary transaction broadcaster/contract caller, which is the exact reachability model this report requires.

### Recommendation
Before allocating `bytesArray`/`bytes32Array` in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray`, validate that `len` is consistent with the available calldata size (e.g., `len * WORD_SIZE <= data.length - offsetInBytes`) and cap `len` to a small sane maximum before performing the allocation, mirroring the `isValidAbiEncoding` bound-check pattern already used elsewhere in this file at [4](#0-3) .

### Proof of Concept
Construct calldata for the precompiled contract that invokes `extractBytesArray`/`extractSigArray`/`extractBytes32Array` such that the `DataWord` at the expected "array length" offset encodes a very large integer (e.g., `0x7FFFFFFF`) while the rest of the calldata is minimal/short. Submitting this as a `TriggerSmartContract` transaction targeting a contract that performs the corresponding native call causes the node to attempt `new byte[0x7FFFFFFF][]`, triggering `OutOfMemoryError` during precompiled-contract execution.

**Note on completeness:** I was unable to fully trace, within the remaining tool budget, the exact precompiled-contract class (`execute()` method) that calls `extractBytesArray`/`extractSigArray`/`extractBytes32Array` and confirm whether an energy/size check occurs earlier in that specific caller's `execute()` before these helpers run. The `extract*Array` methods themselves, however, contain no such guard, and the pattern is consistent with the other, verified precompile (`VerifyTransferProof.execute`) which does perform explicit size/count validation before allocating arrays [5](#0-4) , unlike the `extract*Array` helpers.
