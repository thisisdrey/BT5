### Title
`ref_time_per_fuel` can saturate to zero, making PolkaVM execution (heavy loops / EXP-like computation) free of ref_time weight - ([File: substrate/frame/revive/src/metering/weight.rs])

### Summary
`pallet-revive`'s `WeightMeter` translates the executor's internal fuel/gas units (PolkaVM `Gas`) into `Weight` (`ref_time`) via a single derived constant, `ref_time_per_fuel()`. That constant is computed as the *difference* of two independently-benchmarked weight values. If that subtraction saturates to zero, every unit of engine fuel consumed by a contract's execution (e.g. a tight loop, analogous to the `loopExp` pattern in the external report where a cheap-looking opcode drives a large amount of internal work) translates into zero charged `ref_time`, i.e. unpriced computation.

### Finding Description
`EngineMeter::ref_time_per_fuel` is defined as: [1](#0-0) 

```rust
fn ref_time_per_fuel() -> u64 {
    let loop_iteration =
        T::WeightInfo::instr(1).saturating_sub(T::WeightInfo::instr(0)).ref_time();
    let empty_loop_iteration = T::WeightInfo::instr_empty_loop(1)
        .saturating_sub(T::WeightInfo::instr_empty_loop(0))
        .ref_time();
    loop_iteration.saturating_sub(empty_loop_iteration)
}
```

This value is derived from two *independently* generated benchmark weight functions (`instr` and `instr_empty_loop`), each itself already computed via a `saturating_sub` of two benchmark data points. Because these are separately measured (and possibly separately regressed/interpolated) weight-per-step values, benchmark noise, rounding in the linear-regression weight generation, or a bad/incorrectly regenerated `weights.rs` can make `empty_loop_iteration >= loop_iteration`. In that case `saturating_sub` silently returns `0` instead of erroring.

`EngineMeter::set_fuel` then uses this constant to translate fuel consumed by the interpreter into `Weight`: [2](#0-1) 

```rust
fn set_fuel(&mut self, fuel: u64) -> Weight {
    let consumed = self.fuel.saturating_sub(fuel).saturating_mul(Self::ref_time_per_fuel());
    self.fuel = fuel;
    Weight::from_parts(consumed, 0)
}
```

If `ref_time_per_fuel()` is `0`, `consumed` is always `0` regardless of how much fuel (i.e., how many actual interpreter steps/loop iterations) were burned by the executor. `sync_from_executor`, which is the only place this "translated" weight is charged against the meter's `weight_consumed`, will then accrue nothing: [3](#0-2) 

Because the interpreter itself is only bounded by PolkaVM's own internal gas/fuel limit (derived from `sync_to_executor`, which converts *remaining ref_time* back into fuel using the same broken constant — an unbounded/very large fuel budget when `ref_time_per_fuel()` is 0), a contract executing large loop bodies (the direct analog of `VMTests/vmPerformance/loopExp` — an opcode/loop-heavy program designed to consume a disproportionate amount of internal engine work relative to its apparent gas cost) would run essentially unmetered ref_time-wise, only bounded by other unrelated resources (block time / proof size), while declaring near-zero `ref_time` weight consumption.

### Impact Explanation
This directly matches the "public underpriced work that degrades block production or stalls...processing" impact class. An attacker able to deploy/call a `pallet-revive` contract could submit calls whose declared `Weight` (ref_time) is far below their actual CPU cost, letting them pack disproportionately expensive execution into a block (or repeatedly call it) at normal transaction fees, degrading block production time or enabling a computation-based DoS, without any privileged actor, admin, or malicious infrastructure — a pure unprivileged public dispatch (`pallet_revive::call`/`eth_transact`) primitive.

### Likelihood Explanation
The likelihood depends entirely on whether `instr`/`instr_empty_loop` benchmark weights for the deployed runtime actually satisfy `loop_iteration > empty_loop_iteration` with sufficient margin. This is a benchmark-derived value regenerated per-runtime (`substrate/frame/revive/src/weights.rs`, `cumulus/.../weights/pallet_revive.rs`), so on machines/environments where PolkaVM's baseline "empty loop" overhead is close to, equal to, or noisier than a "real" instruction's cost, or if a future benchmark run/regression yields a smaller `instr(1)-instr(0)` delta than `instr_empty_loop(1)-instr_empty_loop(0)`, the constant silently becomes `0` — with no explicit assertion, invariant check, or defensive minimum guarding this value in code. Unlike the zk-evm case, this cannot be diagnosed via a "trace" — the meter simply reports low/zero weight consumed with no error, exactly mirroring the "hard to diagnose" aspect of the original report (the failure mode produces no error/trace signal, only quietly wrong accounting).

### Recommendation
- Replace the double `saturating_sub` derivation with an explicit, defensively-checked minimum: assert or return a build/config error if `ref_time_per_fuel()` resolves to `0`, rather than silently allowing zero-cost fuel.
- Consider deriving `ref_time_per_fuel` from a single dedicated benchmark of fuel-to-ref_time ratio rather than composing two independently-regressed weight functions.
- Add a runtime/genesis sanity check (similar to other schedule/config validations in `pallet-revive`/`pallet-contracts`) that fails pallet initialization if `ref_time_per_fuel() == 0`.
- Add regression tests asserting `ref_time_per_fuel() > 0` for all supported runtimes' generated `weights.rs`.

### Proof of Concept
A concrete PoC requires the benchmark weights (`instr`, `instr_empty_loop`) for a given runtime to actually collapse to `loop_iteration <= empty_loop_iteration`, which can only be confirmed by running `frame-omni-bencher` for `pallet_revive` in an environment where PolkaVM's loop overhead noise exceeds the marginal per-instruction cost, and then:
1. Deploy a `pallet-revive` EVM/PolkaVM contract with a tight, heavy loop (mirroring `loopExp`'s structure — a loop with large iteration count / heavy per-iteration work).
2. Call it with `gas_syncs_work`-style instrumentation (see existing test at [4](#0-3)  for the analogous `pallet-contracts` gas-sync test pattern) and observe that `result.gas_consumed.ref_time()` does not scale with the number of loop iterations executed, while the call still completes (not `OutOfGas`), demonstrating the fuel→weight translation charges near-zero ref_time for arbitrarily large loop work.

Note: I was not able to execute the actual benchmarks in this environment to confirm whether `loop_iteration <= empty_loop_iteration` currently holds for any shipped `weights.rs`; this would need to be verified with `frame-omni-bencher` runs across target runtimes, and is the main remaining uncertainty in this finding.

	pub fn sync_from_executor(&mut self, engine_fuel: polkavm::Gas) -> Result<(), DispatchError> {
		let weight_consumed = self
			.engine_meter
			.set_fuel(engine_fuel.try_into().map_err(|_| Error::<T>::OutOfGas)?);

		self.weight_consumed.saturating_accrue(weight_consumed);
		if self.weight_consumed.any_gt(self.effective_weight_limit) {
			self.weight_consumed = self.effective_weight_limit;
			return Err(<Error<T>>::OutOfGas.into());
		}

		Ok(())
	}

#[test]
fn gas_syncs_work() {
	let (code, _code_hash) = compile_module::<Test>("caller_is_origin_n").unwrap();
	ExtBuilder::default().existential_deposit(200).build().execute_with(|| {
		let _ = <Test as Config>::Currency::set_balance(&ALICE, 1_000_000);
		let addr = builder::bare_instantiate(Code::Upload(code)).build_and_unwrap_account_id();

		let result = builder::bare_call(addr.clone()).data(0u32.encode()).build();
		assert_ok!(result.result);
		let engine_consumed_noop = result.gas_consumed.ref_time();

		let result = builder::bare_call(addr.clone()).data(1u32.encode()).build();
		assert_ok!(result.result);
		let gas_consumed_once = result.gas_consumed.ref_time();
		let host_consumed_once = <Test as Config>::WeightInfo::seal_caller_is_origin().ref_time();
		let engine_consumed_once = gas_consumed_once - host_consumed_once - engine_consumed_noop;

		let result = builder::bare_call(addr).data(2u32.encode()).build();
		assert_ok!(result.result);
		let gas_consumed_twice = result.gas_consumed.ref_time();
		let host_consumed_twice = host_consumed_once * 2;
		let engine_consumed_twice = gas_consumed_twice - host_consumed_twice - engine_consumed_noop;

		// Second contract just repeats first contract's instructions twice.
		// If runtime syncs gas with the engine properly, this should pass.
		assert_eq!(engine_consumed_twice, engine_consumed_once * 2);
	});
}
