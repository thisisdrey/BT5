### Title
`rlp_execute` on the Wallet Contract accepts `#[payable]` deposits but silently retains them on early-return error paths instead of refunding the caller - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
`WalletContract::rlp_execute` is marked `#[payable]`, allowing any predecessor (a relayer or any other external account) to attach a NEAR deposit when calling it. That deposit is only tracked and refunded via `CallerDeposit` when the transaction is turned into a promise and that promise later fails on-chain. However, several code paths inside `rlp_execute`/`inner_rlp_execute` return an `ExecuteResponse` value synchronously (a *successful* contract execution from the protocol's point of view, just with `success: false` in the payload) without ever creating a promise or a refund transfer. On those paths the attached deposit is neither used nor refunded — exactly the same class of bug as the WormholeFacet report, where a `payable` function accepts the native asset but has a code path that fails to forward or refund it.

### Finding Description
`rlp_execute` is declared `#[payable]`: [1](#0-0) 

Inside `inner_rlp_execute`, the attached deposit is captured into `ExecutionContext`/`CallerDeposit`, which is meant to allow refunding external callers if their action fails later: [2](#0-1) [3](#0-2) 

That `CallerDeposit` is only ever consumed for a refund inside `rlp_execute_callback`, which runs **after a promise has been scheduled and has failed**: [4](#0-3) 

But several branches never reach that callback and return a value directly from the top-level `#[payable]` method:
- The in-flight-transaction guard returns immediately with `PromiseOrValue::Value(...)`, before `CallerDeposit`/`ExecutionContext` are even constructed: [5](#0-4) 
- Any RLP/ABI parsing error (`User`, `Relayer`, or `AccountId` error kinds) from `parse_rlp_tx_to_action` bubbles up as `Err(e)` from `inner_rlp_execute` and is converted straight into a value response with no promise or refund: [6](#0-5) [7](#0-6) 

In NEAR's protocol semantics, a deposit attached to a function call is only auto-refunded to the predecessor when the **receipt itself fails** (panics/reverts); if the function call *returns normally* (even encoding a "logical" failure in its return value, as `ExecuteResponse{success:false,...}` does here) the receipt succeeds and the attached deposit is permanently credited to the receiving account (`current_account_id`, i.e. the eth-implicit wallet), per the documented refund model: [8](#0-7) 

Since `rlp_execute` deliberately never panics ("that method is not meant to panic... success/failure must be communicated via the return value" — see `ExecuteResponse` docs), every one of these synchronous error branches locks in the deposit rather than refunding it: [9](#0-8) 

This is structurally identical to the WormholeFacet report: a `payable`/deposit-accepting entry point has code paths where the attached value is not forwarded to its intended destination nor refunded to the sender, so it is effectively lost from the sender's perspective (silently absorbed by the receiving contract/account).

### Impact Explanation
Any external account (a relayer, or any other unprivileged NEAR account acting as the predecessor) that calls `rlp_execute` with a nonzero attached deposit and hits the in-flight-transaction guard or any RLP/ABI/nonce/signature parsing error will have that NEAR permanently and irrecoverably transferred into the eth-implicit account's balance, with no path to reclaim it. This is a genuine, reachable loss-of-funds bug for an ordinary (non-owner) caller, matching the "permanent freezing/loss of funds" acceptance criterion.

### Likelihood Explanation
Reachability requires only: (1) an eth-implicit account with the Wallet Contract deployed (standard/default for such accounts), and (2) any account attaching a deposit to `rlp_execute` while the wallet has an in-flight transaction, or while submitting a malformed/incorrectly-signed/incorrectly-nonced RLP transaction. Relayer implementations in this codebase currently always attach `Balance::ZERO` to the outer `FunctionCall` when calling `rlp_execute` (see `create_rlp_execute_tx`/`rlp_execute_from` test helpers), so the bug is not hit by the existing reference relayer flow, but nothing in the contract enforces `attached_deposit == 0`, so any third-party integrator or relayer that does attach a deposit (e.g., to also fund the account) is exposed. Likelihood is therefore moderate: it depends on caller behavior not enforced by the protocol or the contract.

### Recommendation
Either:
1. Reject non-zero attached deposits on all early-return/synchronous-failure paths of `rlp_execute` (i.e., check `env::attached_deposit().is_zero()` before the in-flight guard, and refuse/refund immediately via an explicit transfer promise when parsing fails), or
2. Remove `#[payable]` from `rlp_execute` entirely if the attached-deposit mechanism is not needed for anything other than the already-tracked `CallerDeposit` cross-contract-call refund flow, or
3. Explicitly issue a transfer-back promise to `predecessor_account_id` for the attached deposit whenever the function is about to return a value synchronously (guard branch, and every `Err` branch in `inner_rlp_execute`) instead of relying solely on the post-promise `rlp_execute_callback` refund path.

### Proof of Concept
1. Deploy the Wallet Contract as the global contract for an eth-implicit account `A` (as in `test_wallet_contract_interaction`).
2. From an unrelated funded NEAR account `B` (predecessor ≠ `A`), call `A.rlp_execute(target, tx_bytes_b64)` twice back-to-back within the same block/without waiting for completion so the second call hits `self.has_in_flight_tx == true`, attaching e.g. 1 NEAR as deposit on the second call — see the guard at lines 96-105 of `lib.rs`.
3. Observe: the call returns `PromiseOrValue::Value(ExecuteResponse{success:false,...})` synchronously; the receipt succeeds (no panic), so per `docs/RuntimeSpec/Refunds.md` the 1 NEAR deposit is credited to account `A`'s balance and never refunded to `B`.
4. Equivalently, submit an RLP transaction with a mismatched nonce/signature or malformed ABI data alongside a nonzero deposit — `inner_rlp_execute` returns `Err(...)` before any promise/refund is created (lines 389-409), producing the same permanent-loss outcome.
