## Title
Pre-funding the canonical TIP‑2935 history-storage address permanently locks TRX/TRC10 balances when `HistoryBlockHashUtil.deploy()` upgrades the account in place - (File: `framework/src/main/java/org/tron/core/db/HistoryBlockHashUtil.java`)

### Summary
`HistoryBlockHashUtil.deploy()` installs the TIP‑2935 `BlockHashHistory` system contract at the hardcoded address `HISTORY_STORAGE_ADDRESS`. If an account already exists at that address (which anyone can create simply by sending TRX or a TRC10 asset there before the proposal activates), the code does **not** reset the account's balance/asset state - it only flips the account type to `Contract` and clears delegated resources, deliberately preserving the pre-existing balance to mirror the CREATE2-collision behavior in the TVM.

### Finding Description
The deploy routine reads any pre-existing account at the canonical address and mutates it in place instead of rejecting or clearing it: [1](#0-0) 

Because `HISTORY_STORAGE_ADDRESS` is a fixed, publicly known constant address for which no private key exists, any unprivileged user can send TRX (a plain `TransferContract`) or TRC10 tokens (a plain `TransferAssetContract`) to it at any time before the TIP‑2935 proposal is activated - no signature from that address is required for either operation, only a valid destination address. When the proposal later activates and `deploy()` runs from `ProposalService` during maintenance-time block processing, the existing account is detected (`accountExisting = true`) and is upgraded to `AccountType.Contract` with its balance preserved: [2](#0-1) 

After this point the address holds fixed `BlockHashHistory` bytecode (a passive read-only history contract that has no payable/withdraw logic) and there is no private key that can ever sign a transaction from that address to move the funds out. Any TRX or TRC10 balance parked there before activation becomes permanently inaccessible.

This is structurally analogous to the reported `MechMarketplace.create` bug: an unprivileged party can pre-position state at an identifier that is *later* consumed/finalized by privileged logic (there, `mapServiceIdMech[serviceId]`; here, the account at the canonical system address) without the finalizing code verifying that the pre-existing state is untouched/benign, letting attacker-influenced state be silently absorbed into the system's trusted object.

### Impact Explanation
Any TRX or TRC10 tokens sent to `HISTORY_STORAGE_ADDRESS` prior to TIP‑2935 activation are permanently and irrecoverably frozen once the proposal activates, since the resulting `BlockHashHistory` contract has no code path to move value out and no private key exists to authorize a withdrawal. This satisfies the "permanent freezing of funds" impact bar - a user who is tricked (or who mistakenly reuses/tests against the known canonical address) into sending value there loses it permanently, and the amount at risk is unbounded by anyone advertising/targeting that address before activation.

### Likelihood Explanation
The precondition (transferring TRX/TRC10 to a known, publicly documented address) requires only an ordinary unprivileged transfer transaction - no special privilege, no contract interaction, and no race condition beyond "before the TIP‑2935 proposal activates." Because the address is fixed and published as part of the TIP-2935 design, it is straightforward for an attacker to induce or wait for such transfers before the community-known activation block.

### Recommendation
When a pre-existing account is found at `HISTORY_STORAGE_ADDRESS` during `deploy()`, do not silently preserve its balance. Options: reject/clear the balance (burning it explicitly, consistent with a documented policy) or, more safely, fail loudly / abort activation (similar to the "foreign code/foreign contract" collision-skip branches already implemented for code/contract collisions) and require an explicit governance decision for how to handle it, rather than defaulting to preserving attacker-influenced state that becomes unspendable.

### Proof of Concept
1. Before the `AllowTvmPrague`/TIP‑2935 activation proposal takes effect, any account (attacker or victim) sends TRX (`TransferContract`) and/or a TRC10 asset (`TransferAssetContract`) to the well-known address `410000f90827f1c53a10cb7a02335b175320002935`.
2. This succeeds because standard transfers do not require the recipient's signature, only a valid target address, and the address is a normal (non-existent-code) account at this point.
3. Once the committee/proposal activates TIP‑2935, `Manager`'s proposal application invokes `HistoryBlockHashUtil.deploy(manager)`.
4. `deploy()` finds the pre-existing account (`accountExisting = true`), sets its type to `Contract`, clears only delegated resources, and writes it back with the balance untouched: [1](#0-0) 
5. The address now runs immutable `BlockHashHistory` bytecode with no transfer/withdraw entry point, and no private key exists for it, so the TRX/TRC10 balance deposited in step 1 is permanently locked and unrecoverable by anyone. This can be confirmed by asserting `getAccountStore().get(HISTORY_STORAGE_ADDRESS).getBalance()` remains non-zero post-deploy while no further transaction can move it, contrasted with the existing test `deploySkipsWhenForeignBytecodePresent`/`deploySkipsWhenForeignContractPresent` which only guard against foreign *code/contract* collisions, not foreign *balance* preservation: [3](#0-2)
