### Title
`SlotMetadata::auth_digest` omits `contract_id`, allowing a StackerDB chunk signature to be replayed from one StackerDB to another - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::sign`/`verify` compute their authentication digest only over `(slot_id, slot_version, data_hash)`, with no binding to the StackerDB's `contract_id`. `PeerNetwork::validate_received_chunk` (called from `handle_unsolicited_StackerDBPushChunk`) resolves the expected signer address purely from `get_slot_signer(smart_contract_id, data.slot_id)` and then checks `slot_metadata.verify(&addr)`, so any signature that recovers to the correct address for the *target* `contract_id` passes, regardless of which StackerDB contract it was originally produced for.

### Finding Description
The signed message is defined in `SlotMetadata::auth_digest` (`libstackerdb/src/libstackerdb.rs:160-166`):
```rust
fn auth_digest(&self) -> Sha512Trunc256Sum {
    let mut hasher = Sha512_256::new();
    hasher.update(self.slot_id.to_be_bytes());
    hasher.update(self.slot_version.to_be_bytes());
    hasher.update(self.data_hash.0);
    Sha512Trunc256Sum::from_hasher(hasher)
}
```
This is used both by `SlotMetadata::sign`/`verify` (lines 171-193) and by `StackerDBChunkData::sign`/`verify` (lines 226-244). Nowhere does the digest incorporate the `QualifiedContractIdentifier` of the StackerDB the chunk is destined for.

On the verification path, `PeerNetwork::validate_received_chunk` (`stackslib/src/net/stackerdb/mod.rs:649-717`) does:
```rust
let addr = match self.stackerdbs.get_slot_signer(smart_contract_id, data.slot_id)? { ... };
let slot_metadata = data.get_slot_metadata();
if !slot_metadata.verify(&addr)? { ... return Ok(false); }
```
`smart_contract_id` here is only used to look up which address is *expected* to own `data.slot_id` in that particular DB's config (`get_slot_signer`, `stackslib/src/net/stackerdb/db.rs`) — it is never mixed into the cryptographic check itself. `handle_unsolicited_StackerDBPushChunk` (`stackslib/src/net/stackerdb/mod.rs:742-871`) passes `chunk_data.contract_id` (attacker-controlled, taken straight off the wire in `StackerDBPushChunkData`) into `validate_received_chunk` as `smart_contract_id`, and stores the chunk keyed by that same `contract_id` if validation succeeds.

Exploit flow: an attacker who legitimately owns slot `i` in StackerDB A signs a chunk (bytes `D`) — this produces `sig` over `(i, version, sha512_256(D))`. If the attacker's `StacksAddress` also happens to be the signer of slot `i` in StackerDB B (e.g. by being registered as a signer in two related `.signers-*` contracts, or any two contracts that both list the same address at the same slot index — a state entirely controlled by contract configuration, not by any P2P-layer guard), the attacker can send a `StackerDBPushChunkData` with `contract_id = B`, `chunk_data = { slot_id: i, slot_version: version, sig, data: D }`. `get_slot_signer(B, i)` returns the attacker's address (since they are a legitimate signer there too), `slot_metadata.verify(&addr)` recomputes the digest from `(i, version, sha512_256(D))` — identical to what was signed for A — and passes. The chunk is accepted and stored into DB B's replica under `log_stored_stackerdb_chunk`/storage, and is gossiped onward via `StacksMessageType::StackerDBChunkInv` and the sync/push protocol.

None of the existing guards catch this: `validate_received_chunk` only checks chunk size, expected-version bounds, signer-address match, monotonic version, and max-writes — it never asserts that the signature is scoped to `smart_contract_id`. The `rc_consensus_hash`/view checks in `make_StackerDBChunksInv_or_Nack` guard against stale chain tips, not against cross-contract replay.

### Impact Explanation
An unprivileged remote peer who is a legitimate signer in two (or more) StackerDB contracts at the same slot index can cause a node to store and re-gossip data into StackerDB B that was only ever properly authorized for StackerDB A, without needing B's private key material to newly produce that signature for B — effectively a forged/cross-contaminated write into a StackerDB replica the attacker does not have independent write authority over for that specific bytestream/context. This is a write to StackerDB state with a signature that does not commit to the target contract, and it propagates network-wide as the chunk is relayed to other replicas. This matches the "unauthenticated/unauthorized write to state or StackerDB" / "network-wide propagation of forged data" Critical category, though it is bounded by the precondition that the attacker must hold a matching slot index/address across two related DBs.

### Likelihood Explanation
Preconditions: attacker must be a legitimate signer at slot index `i` in two StackerDB-replicating contracts. This is plausible for real deployments where signer sets are duplicated across message-topic or reward-cycle-specific `.signers-*` contracts (visible in the repo as `signers-0-xxx.clar`, `signers-1-xxx.clar`), since the same signer set/ordering is commonly reused across such contracts. No secret, admin role, or privileged access is required — just P2P connectivity and legitimate slot ownership, which is attacker-controllable/cheap. The attack is repeatable per chunk/version.

### Recommendation
Bind the StackerDB signature to the target contract identity: include `contract_id` (and ideally a network/chain identifier) in `SlotMetadata::auth_digest`, requiring a protocol version bump/migration for existing signed chunks, or otherwise domain-separate signing across contracts (e.g., hash `contract_id.to_string()` bytes into the digest before slot_id/version/data_hash). Update `sign`/`verify` call sites (`StackerDBChunkData::sign`, `PeerNetwork::validate_received_chunk`) to pass and check the target `contract_id`.

### Proof of Concept
In `stackslib/src/net/stackerdb/tests`, construct two `StackerDBConfig`s (DB A, DB B) whose `signers` list places the same `StacksAddress` (derived from one keypair) at slot index 0 in both. Sign a `StackerDBChunkData` for slot 0 under DB A's context (there is no contract-specific signing today, so this is just `chunk.sign(&privk)`). Then call `PeerNetwork::handle_unsolicited_StackerDBPushChunk` (or directly `validate_received_chunk`) with `contract_id = B` and the same chunk/sig. Assert that today `validate_received_chunk` returns `Ok(true)` (chunk accepted for B), demonstrating the missing binding; the fix should make this assertion `Ok(false)` once `contract_id` is folded into `auth_digest`.
