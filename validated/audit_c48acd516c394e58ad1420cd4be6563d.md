### Title
Pool.swap lacks user-specified minimum amountOut, exposing swappers to oracle price drift between submission and execution - ([File: contracts/Pool.sol])

### Summary
`Pool.swap` exchanges synthetic tokens purely at the `masterOracle` price at execution time and accepts no `amountOutMinimum`/`amountInMaximum` parameter. This is the direct analog of the Unitas finding: the protocol-level price check (here, the oracle itself) cannot protect a pending transaction from a legitimate price move, and the user has no way to bound worst-case output. Notably, Metronome already acknowledges this class of risk elsewhere — `SmartFarmingManager.leverage` takes `depositAmountMin_` and `flashRepay` takes `swapAmountOutMin_` — but `Pool.swap`, the primary user-facing swap entry point, has none.

### Finding Description
- `IPool.swap` is declared as `swap(ISyntheticToken syntheticTokenIn_, ISyntheticToken syntheticTokenOut_, uint256 amountIn_)` returning `(_amountOut, _fee)` — there is no slippage parameter in the interface [1](#0-0) .
- The quote functions `quoteSwapIn`/`quoteSwapOut` exist only for off-chain estimation; nothing on-chain enforces the quoted value at execution [2](#0-1) .
- The test confirms the swap output is fully determined by the oracle prices at call time (`expectedAmountOut = amountInUsd * 1e18 / dogePrice`) with no bound check [3](#0-2) .
- In contrast, the protocol's own zap paths do take slippage bounds: `leverage(..., depositAmountMin_)` reverts with `LeverageSlippageTooHigh` [4](#0-3)  and `flashRepay(..., swapAmountOutMin_)` reverts with `FlashRepaySlippageTooHigh` [5](#0-4) , and `_swap` forwards `amountOutMin_` to `swapper_.swapExactInput` [6](#0-5) . `Pool.swap` offers no equivalent.

Scenario (identical structure to the report):
1. Alice calls `quoteSwapOut(msETH, msUSD, 1e18)` and sees ~2000 msUSD out.
2. She submits `pool.swap(msETH, msUSD, 1e18)` with low gas; the tx sits pending.
3. ETH's oracle price drops 10% before inclusion.
4. The swap executes at the new price — Alice receives ~1800 msUSD. No revert is possible because no minimum was ever expressed.

### Impact Explanation
Users swapping through `Pool.swap` bear unbounded unfavorable price movement between submission and execution. The swap is zero-sum at oracle price for the protocol (burns synthIn, mints synthOut), so the loss accrues entirely to the user. On L2s with private/orderly mempools and on any chain during volatile oracle updates (e.g., a Chainlink heartbeat deviation firing between mempool and inclusion), a pending swap can execute at materially worse terms than the user would have accepted. This is a direct loss of user funds within the accepted bug class (insufficient slippage protection on an oracle-priced swap).

### Likelihood Explanation
Medium. Oracle price updates between submission and execution are routine for volatile-asset synths (msETH, msBTC, etc.). There is no attacker requirement — natural price drift suffices — and nothing in `Pool.swap` (no min-out check, only `AmountInIsInvalid`, `SwapFeatureIsInactive`, and activity checks per the tests) prevents execution at a worse price. Note the caveat that, unlike an AMM, the swap cannot be profitably sandwiched via the pool itself since quotes are symmetric oracle prices; the exposure is purely adverse drift, which is exactly the medium-severity scenario in the reference finding.

### Recommendation
Add a user-supplied bound, matching the pattern already used in `SmartFarmingManager`:

```diff
- function swap(ISyntheticToken syntheticTokenIn_, ISyntheticToken syntheticTokenOut_, uint256 amountIn_)
+ function swap(ISyntheticToken syntheticTokenIn_, ISyntheticToken syntheticTokenOut_, uint256 amountIn_, uint256 amountOutMin_)
    external returns (uint256 _amountOut, uint256 _fee)
```

and inside the function, after computing `_amountOut` via `quoteSwapOut`, `require(_amountOut >= amountOutMin_)` (or a custom `SlippageTooHigh` error) before burning/minting.

### Proof of Concept
Reproducible in the existing Hardhat suite (`test/Pool.test.ts` harness):

```ts
// 1. Alice has msETH; quote at current prices
const amountIn = parseEther('1')
const quoted = await pool.quoteSwapOut(msEth.address, msUsd.address, amountIn) // e.g. 2000e18

// 2. Oracle updates: ETH price drops 10% before Alice's tx executes
await ethOracle.updatePrice(ethPrice.mul(90).div(100))

// 3. Alice's pending tx executes — no minOut to check against
await pool.connect(alice).swap(msEth.address, msUsd.address, amountIn)
const received = await msUsd.balanceOf(alice.address)

// 4. Alice got ~10% less than quoted; the tx cannot revert
expect(received).to.be.lt(quoted.mul(91).div(100))
```

The same flow in Foundry via `PoolHandler.swap` (which already calls `pool.swap(synthIn, synthOut, amountIn)` with no bound) [7](#0-6) : bound the actor's balance, warp/mock a new oracle price between quote and call, and assert the received amount is below any reasonable user-expected minimum — demonstrating the missing check.
