### Title
Race condition allows a transaction signed with a since-revoked key to be admitted to the mempool because signature verification happens outside the pending-queue lock and its result is cached - (File: `framework/src/main/java/org/tron/core/db/Manager.java`)

### Summary
`Manager.pushTransaction()` calls `trx.validateSignature(...)` **before** acquiring `transactionLock`/entering the `synchronized (this)` block that actually applies the transaction and inserts it into `pendingTransactions`. `TransactionCapsule.validateSignature`/`validatePubSignature` verify against the *live* `AccountStore` and then cache the result in the non-volatile `isVerified` field, permanently short-circuiting all future re-checks for that `TransactionCapsule` instance. [1](#0-0) 

### Finding Description
This mirrors the Zulip class of bug: a resource's authorization state (account permission/keys) is read once, cached, and a concurrent state change (permission revocation) that happens between the check and the "commit" is not honored.

- `pushTransaction` enqueues the transaction, then validates its signature against `chainBaseManager.getAccountStore()` outside of any lock: [2](#0-1) 

- `validateSignature`/`validatePubSignature` in `TransactionCapsule` fetch the `AccountCapsule` (and thus its `Permission`/key list) at call time, check weight, and cache `isVerified = true` once successful: [3](#0-2) [4](#0-3) 

- After that, execution proceeds under `synchronized (transactionLock)` / `synchronized (this)` and calls `processTransaction`, which (per `TransactionCapsule.validateSignature`'s `if (!isVerified)` guard) will **not** re-verify the signature since `isVerified` is already `true`.

A concurrent `AccountPermissionUpdateActuator.execute` (invoked by another transaction being processed inside the lock, or in a subsequent block between mempool admission and inclusion) can rewrite the account's `owner`/`active` permissions - removing the key that signed the pending transaction - via `accountStore.put(ownerAddress, account)`: [5](#0-4) 

Because `isVerified` was already latched to `true` on the `TransactionCapsule` object before the permission change lands, the transaction using the now-revoked key is still admitted to `pendingTransactions` and later processed (e.g. via `rePush`, which only forces re-verification, `setVerified(false)`, when the *owner* is currently pending another tx - not when its permission was already changed by an already-applied/queued update): [6](#0-5) 

Additionally, `preValidateTransactionSign` runs `ValidateSignTask` in a thread pool over all transactions in an incoming block concurrently, again computing/caching `isVerified` against a fixed account snapshot at validation time, ahead of transactions in the same block that could mutate that account's permission via `AccountPermissionUpdateContract` earlier in `block.getTransactions()`: [7](#0-6) [8](#0-7) 

### Impact Explanation
If exploitable, an attacker who has been removed from an account's active/owner permission (e.g., after a multisig re-key or an emergency key rotation) could still get a transaction executed under the old permission, because verification is check-then-cache rather than check-at-commit. This is an unauthorized account operation / permission bypass, matching the "concrete unauthorized account operation" bar for a valid analog (funds theft/transfer risk if the old key still authorizes `TransferContract`/`TriggerSmartContract`, etc.).

### Likelihood Explanation
Requires a narrow timing window: the attacker (or someone else) must broadcast a transaction signed by a key that is about to be removed, and the permission-update transaction that revokes that key must be processed by the node in between the signature check and the pending-queue commit, or within the same block being parallel-validated by `preValidateTransactionSign`. This is racy and timing-dependent (medium likelihood), consistent with the CVSS 5.4 / Medium severity of the original Zulip finding, and requires no privileged node role - any broadcaster or account owner triggering their own key rotation is sufficient to create the race.

### Recommendation
Re-validate transaction signatures (or explicitly invalidate `isVerified` for all pending transactions belonging to an address) immediately before the transaction is actually included/applied, not just once at admission time. Concretely: move `trx.validateSignature(...)` inside the same lock that performs `processTransaction`/queue insertion in `Manager.pushTransaction`, and in `preValidateTransactionSign`, ensure per-account permission-changing transactions are validated/applied in strict order before later transactions from the same account are considered "verified" (or force `setVerified(false)` on all pending transactions from an address whenever an `AccountPermissionUpdateContract` for that address is processed, not only when that address currently has something already pending).

### Proof of Concept
1. Account A has active permission key K1 (threshold satisfied by K1 alone).
2. Attacker/owner broadcasts Tx1: `TransferContract` from A, signed by K1.
3. Node calls `pushTransaction(Tx1)` → `trx.validateSignature` succeeds against current `AccountStore` (K1 still valid) → `isVerified=true` is cached on the `TransactionCapsule`, *before* the `transactionLock`/`synchronized(this)` block is entered.
4. Before Tx1 reaches `processTransaction`, another transaction Tx0 (an `AccountPermissionUpdateContract` removing K1 from A's permissions) is processed by the same node (e.g., submitted concurrently and it wins the lock first, or arrives in the same upcoming block ahead of Tx1).
5. Because `TransactionCapsule.validateSignature` short-circuits on `isVerified == true`, Tx1 is still added to `pendingTransactions`/executed later using the old, now-revoked K1 authorization, producing state changes (e.g., a transfer) that should have been rejected under A's current permission set.

  private void preValidateTransactionSign(List<TransactionCapsule> txs)
      throws InterruptedException, ValidateSignatureException {
    int transSize = txs.size();
    if (transSize <= 0) {
      return;
    }
    Histogram.Timer requestTimer = Metrics.histogramStartTimer(
        MetricKeys.Histogram.VERIFY_SIGN_LATENCY, MetricLabels.TRX);
    try {
      CountDownLatch countDownLatch = new CountDownLatch(transSize);
      List<Future<Boolean>> futures = new ArrayList<>(transSize);

      for (TransactionCapsule transaction : txs) {
        Future<Boolean> future = validateSignService
            .submit(new ValidateSignTask(transaction, countDownLatch, chainBaseManager));
        futures.add(future);
      }
      countDownLatch.await();

      for (Future<Boolean> future : futures) {
        try {
          future.get();
        } catch (ExecutionException e) {
          throw new ValidateSignatureException(e.getCause().getMessage());
        }
      }
    } finally {
      Metrics.histogramObserve(requestTimer);
    }
  }

  public static boolean validateSignature(Transaction transaction,
      byte[] hash, AccountStore accountStore, DynamicPropertiesStore dynamicPropertiesStore)
      throws PermissionException, SignatureException, SignatureFormatException {
    Transaction.Contract contract = transaction.getRawData().getContractList().get(0);
    int permissionId = contract.getPermissionId();
    byte[] owner = getOwner(contract);
    AccountCapsule account = accountStore.get(owner);
    Permission permission = null;
    if (account == null) {
      if (permissionId == 0) {
        permission = AccountCapsule.getDefaultPermission(ByteString.copyFrom(owner));
      }
      if (permissionId == 2) {
        permission = AccountCapsule
            .createDefaultActivePermission(ByteString.copyFrom(owner), dynamicPropertiesStore);
      }
    } else {
      permission = account.getPermissionById(permissionId);
    }
    if (permission == null) {
      throw new PermissionException("permission isn't exit");
    }
    checkPermission(permissionId, permission, contract);
    long weight = checkWeight(permission, transaction.getSignatureList(), hash, null);
    if (weight >= permission.getThreshold()) {
      return true;
    }
    return false;
  }

  public boolean validatePubSignature(AccountStore accountStore,
      DynamicPropertiesStore dynamicPropertiesStore)
      throws ValidateSignatureException {
    if (!isVerified) {
      if (this.transaction.getSignatureCount() <= 0
              || this.transaction.getRawData().getContractCount() <= 0) {
        throw new ValidateSignatureException("miss sig or contract");
      }
      if (this.transaction.getSignatureCount() > dynamicPropertiesStore
              .getTotalSignNum()) {
        throw new ValidateSignatureException("too many signatures");
      }

      byte[] hash = getTransactionId().getBytes();

      long startNs = System.nanoTime();
      try {
        if (!validateSignature(this.transaction, hash, accountStore, dynamicPropertiesStore)) {
          isVerified = false;
          throw new ValidateSignatureException("sig error");
        }
      } catch (SignatureException | PermissionException | SignatureFormatException e) {
        isVerified = false;
        throw new ValidateSignatureException(e.getMessage());
      } finally {
        logSlowSigVerify(startNs);
      }
      isVerified = true;
    }
    return true;
  }
