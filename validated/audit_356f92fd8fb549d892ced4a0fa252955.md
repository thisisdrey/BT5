## Title
Unauthenticated/unstaked QUIC clients can exhaust the global TPU connection-rate budget even when `max_unstaked_connections` is configured to `0` - (File: `streamer/src/nonblocking/quic.rs`)

### Summary
The QUIC streamer's global connection-admission token bucket (`overall_connection_rate_limiter`) is consumed by every completed handshake **before** the connection's stake/peer-type is checked against its own quota. An attacker who owns no stake can complete many cheap QUIC handshakes to burn through this shared, validator-wide budget, causing legitimate staked connections to be rejected even though the operator has explicitly configured `max_unstaked_connections = 0` to prevent unstaked clients from consuming server resources. This mirrors the reported disperser bug: an unprivileged actor drains a *global* rate limit before the per-class (stake) check that would otherwise reject them is ever applied.

### Finding Description
`run_server` creates one shared, global `TokenBucket` for all incoming connections regardless of stake: [1](#0-0) 

In `setup_connection`, once a QUIC handshake completes, the code first registers the connection against the per-IP limiter, then unconditionally consumes a token from this shared `overall_connection_rate_limiter` — all of this happens *before* `qos.build_connection_context` determines whether the peer is staked or unstaked, and before `qos.try_add_connection` enforces the operator-configured `max_unstaked_connections` / `max_connections_per_unstaked_peer` quotas: [2](#0-1) 

Only afterward, inside `try_add_connection` (e.g. `SwQos::try_add_connection` / `prune_unstaked_connections_and_add_new_connection`), is the unstaked connection actually rejected if `max_unstaked_connections == 0`: [3](#0-2) [4](#0-3) 

By the time this stake-based rejection occurs, the token has already been irrevocably spent from the single global bucket shared by *all* connections — staked and unstaked alike. There is no separate/staked-reserved capacity in `overall_connection_rate_limiter`; it is a flat, validator-wide budget of `MAX_CONNECTION_BURST = 1000` burst and `TOTAL_CONNECTIONS_PER_SECOND = 2500` sustained. This is structurally identical to the disperser flaw: an unauthorized/zero-quota actor is able to deplete a shared global counter before the check that would otherwise refuse them is evaluated.

The only gate standing before this global consumption is the per-IP `ConnectionRateLimiter` (default `max_connections_per_ipaddr_per_min = 8`, with a 10x/`80` burst allowance): [5](#0-4) 

which is a per-IP throttle, not an aggregate cap on how much of the global budget any given class of unprivileged clients can consume — an attacker distributing handshakes across a modest number of source IPs (no stake required, just the ability to complete a QUIC handshake) can still exhaust the shared 1000-token burst / 2500-per-second sustained rate.

### Impact Explanation
This is a QoS-evasion / denial-of-service on the validator's TPU ingress path. Because a completed QUIC handshake requires no stake and no meaningful cost beyond network round trips, any unprivileged network participant can repeatedly open (and immediately have rejected) connections to burn through the shared `overall_connection_rate_limiter` budget. While their own connections are correctly denied by the stake-based `try_add_connection` logic, the depletion of the shared token bucket also blocks legitimate staked validators' new connection attempts (`connection_rate_limited_across_all` stat), preventing them from submitting transactions to the leader during the exhaustion window. This directly undermines the purpose of `max_unstaked_connections = 0` and the stake-weighted QoS design, which exists specifically to prevent unstaked/unprivileged traffic from starving staked traffic.

### Likelihood Explanation
Likely and cheap to trigger: no stake, no valid transaction, and no signature verification is required — only completion of the QUIC crypto handshake (real UDP round trips from real/rotatable source addresses, since QUIC path validation makes IP spoofing impractical, but attackers with a modest set of source addresses or cloud instances can sustain the required rate). The per-IP limiter (8/min, burst 80) does not prevent aggregate exhaustion of the shared global 1000-burst/2500-per-second budget when spread across a small number of IPs.

### Recommendation
- Do not consume the shared/global `overall_connection_rate_limiter` token until after the connection has been classified (staked vs. unstaked) and admitted by the per-class quota (`try_add_connection`), or
- Split the global connection-admission budget into stake-reserved and unstaked-reserved partitions (similar to how `StakedStreamLoadEMA` reserves stream throughput for staked vs. unstaked traffic), so that unstaked handshake churn cannot deplete capacity reserved for staked connections, or
- When `max_unstaked_connections == 0` (or the per-peer/per-class quota is already known to be exhausted), reject the connection before touching the shared `overall_connection_rate_limiter`.

### Proof of Concept
1. Configure `SwQosConfig { max_unstaked_connections: 0, .. }` (a validator that wants to accept only staked TPU connections), as in the existing test `test_quic_server_unstaked_node_connect_failure`: [6](#0-5) 
2. From an unstaked/unprivileged client, complete a burst of QUIC handshakes from a handful of distinct source addresses at a rate sufficient to consume the `MAX_CONNECTION_BURST` (1000) tokens and sustain > `TOTAL_CONNECTIONS_PER_SECOND` (2500/s) of `overall_connection_rate_limiter.consume_tokens(1)` calls in `setup_connection` — each such attempt is ultimately rejected by `try_add_connection` (as `max_unstaked_connections == 0`), but only *after* the shared token is already spent.
3. Concurrently, have a legitimate staked client attempt to connect; observe its connection rejected with `CONNECTION_CLOSE_CODE_DISALLOWED` / incremented `stats.connection_rate_limited_across_all`, despite holding valid stake, because the shared global budget was already exhausted by the unstaked attacker.
