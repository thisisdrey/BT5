Based on my research, I found a genuine analog to the reported bug class in `OperationActions.java`.

### Title
`FREEZE`/`UNFREEZE` TVM opcodes bypass the `STATICCALL` mutation guard when `ALLOW_TVM_VOTE` is not active - ([File: actuator/src/main/java/org/tron/core/vm/OperationActions.java])

### Summary
The Atlas report flags a pattern where a critical invariant check (`reconcile()` / `solverCalledBack`) is only executed under certain feature-flag combinations, so some code paths bypass the check entirely. The same pattern exists in java-tron's TVM opcode dispatch: the `STATICCALL`-mutation guard for the `FREEZE` and `UNFREEZE` opcodes is conditioned on the `VMConfig.allowTvmVote()` feature flag, while every other state-mutating opcode (`SSTORE`, `TSTORE`, `CREATE`, `SUICIDE`, `FREEZEBALANCEV2`, `UNFREEZEBALANCEV2`, `DELEGATERESOURCE`, `VOTEWITNESS`, etc.) enforces the guard unconditionally.

### Finding Description
In `actuator/src/main/java/org/tron/core/vm/OperationActions.java`, most state-mutating opcodes unconditionally reject execution inside a `STATICCALL` context: [1](#0-0) [2](#0-1) 

However, `freezeAction` and `unfreezeAction` only enforce the same guard when `VMConfig.allowTvmVote()` is true: [3](#0-2) 

If `allowTvmVote()` is not enabled (e.g. on a private/consortium java-tron network that has not yet activated the corresponding committee proposal, or during a window before the proposal is enacted), a contract executed via `STATICCALL`/inside a `view`-declared call context can still invoke the legacy `FREEZE`/`UNFREEZE` opcodes and mutate account resource-delegation/frozen-balance state — directly violating the `STATICCALL` no-state-change invariant that the TVM otherwise strictly enforces for every other opcode.

This is the same bug class as the report: an invariant-enforcing check ("reconcile() must have been called back") is gated behind a conditional (`needsPreSolver()`/`needsSolverPostCall()`), so certain configurations bypass the check entirely. Here, the invariant ("no state mutation under `STATICCALL`") is gated behind `allowTvmVote()`, so networks/blocks where that flag is `0` bypass the check for exactly these two opcodes while every sibling opcode enforces it unconditionally — an inconsistency that strongly suggests a bug rather than an intentional design choice.

### Impact Explanation
A malicious contract deployer could deploy a contract that another contract (or off-chain caller) invokes via `STATICCALL` expecting no state changes (a common pattern for reentrancy-safety and read-only aggregator/proxy patterns). On a chain/environment where `allowTvmVote` is disabled, the callee could still execute `FREEZE`/`UNFREEZE`, silently altering the frozen TRX balance / bandwidth or energy resources of an account — an unauthorized state mutation performed under a call type that callers rely on being side-effect-free. This can lead to unexpected freezing/unfreezing of funds and violates a core EVM/TVM safety guarantee that other contracts depend on for correctness and security (e.g., reentrancy guards built around `STATICCALL`).

### Likelihood Explanation
Exploitability is fully gated by the current value of the `ALLOW_TVM_VOTE` dynamic parameter, which is set via a committee proposal (`common/src/main/java/org/tron/core/vm/config/VMConfig.java`, `chainbase/.../DynamicPropertiesStore.java`). On long-running mainnet this proposal was very likely enacted long ago, making the flag permanently `1` and the vulnerable branch unreachable there. However, java-tron is also run as the base for private/consortium/test networks that start from genesis with default (disabled) proposals, and the guard's inconsistency with every other opcode indicates a latent code defect regardless of current mainnet activation state. I could not fully verify from the index whether `allowTvmVote()` is hardcoded to `true` in some later hard-fork gate (would require checking `ConfigLoader.java`/`Args.java` initialization order, which I was unable to fully inspect before running out of iterations).

### Recommendation
Remove the `VMConfig.allowTvmVote() &&` condition from the `STATICCALL` guards in `freezeAction` and `unfreezeAction` so they are enforced unconditionally, consistent with every other state-mutating opcode in `OperationActions.java`.

### Proof of Concept
1. On a java-tron network where the `ALLOW_TVM_VOTE` proposal has not been enacted (`allowTvmVote() == false`), deploy Contract B containing the `FREEZE`/`UNFREEZE` opcode (e.g. via raw bytecode using `0x9c`/`0x9d`-style TVM-specific opcodes as exposed by `freezeAction`/`unfreezeAction`).
2. Deploy Contract A that calls Contract B via `STATICCALL`.
3. Observe that instead of throwing `Program.StaticCallModificationException` (as it would for `SSTORE`, `CREATE`, `FREEZEBALANCEV2`, etc.), the call succeeds and the account's frozen balance / resource state is mutated, confirmed by querying `program.freeze()`/`program.unfreeze()` state changes via `Program.java` after execution.   public static void freezeAction(Program program) {
```java
    // after allow vote, check static
    if (VMConfig.allowTvmVote() && program.isStaticCall()) {
      throw new Program.StaticCallModificationException();
    }
    // 0 as bandwidth, 1 as energy
    DataWord resourceType = program.stackPop();
    DataWord frozenBalance = program.stackPop();
    DataWord receiverAddress = program.stackPop();

    if (VMConfig.allowTvmFreezeV2()) {
      // after v2 activated, we just push zero to stack and do nothing
      program.stackPush(DataWord.ZERO());
    } else {
      boolean result = program.freeze(receiverAddress, frozenBalance, resourceType );
      program.stackPush(result ? DataWord.ONE() : DataWord.ZERO());
    }
    program.step();
  }

  public static void unfreezeAction(Program program) {
    if (VMConfig.allowTvmVote() && program.isStaticCall()) {
      throw new Program.StaticCallModificationException();
    }

    DataWord resourceType = program.stackPop();
    DataWord receiverAddress = program.stackPop();

    boolean result = program.unfreeze(receiverAddress, resourceType);
    program.stackPush(result ? DataWord.ONE() : DataWord.ZERO());
    program.step();
  }
```
