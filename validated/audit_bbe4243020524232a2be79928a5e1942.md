### Title
Unbounded attacker-controlled disk growth via `insert_instantiated_attachment` on unverified attachment content - (File: stackslib/src/net/atlas/download.rs, stackslib/src/net/atlas/db.rs)

### Summary
The Atlas attachment-download path accepts and permanently stores (`was_instantiated = 1`) any attachment content an outbound peer returns for an `AttachmentRequest`, without ever checking that the returned bytes actually hash to the requested `content_hash`. Because eviction logic in `AtlasDB` only ever targets `was_instantiated = 0` rows, an attacker-controlled peer can cause a node to permanently store arbitrarily many uncommitted, wrong-hash attachments with no cap or eviction path.

### Finding Description
The broken equality: a row in the `attachments` table with `was_instantiated = 1` is supposed to mean "this content corresponds to some confirmed on-chain `AttachmentInstance.content_hash`." In `AttachmentsBatchStateMachine::try_proceed`'s `Done` branch (`stackslib/src/net/atlas/download.rs:153-169`), every attachment collected in `context.attachments` (a `HashSet<Attachment>` populated in `extend_with_attachments`, `download.rs:530-558`) is unconditionally passed to `network.atlasdb.insert_instantiated_attachment(&attachment)` (`download.rs:161`), regardless of whether `find_all_attachment_instances(&attachment.hash())` (`download.rs:155-158`) found any matching on-chain instance.

`extend_with_attachments` (`download.rs:530-558`) simply calls `response.decode_atlas_get_attachment()` and inserts whatever `Attachment` comes back into the `HashSet`, with **no comparison of the returned content's `Hash160` against the requested `content_hash`** that motivated the original `AttachmentRequest`. `decode_atlas_get_attachment` (`stackslib/src/net/api/getattachment.rs:159-165`) purely deserializes the JSON body into a `GetAttachmentResponse` (hex-decoded bytes) with no hash check whatsoever.

`insert_instantiated_attachment` (`stackslib/src/net/atlas/db.rs:576-592`) then does `INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ...)` keyed by `attachment.hash()` — i.e., whatever hash the attacker's bytes happen to produce. The subsequent `UPDATE attachment_instances SET is_available = 1 WHERE content_hash = ?1 ...` (`db.rs:586-589`) is a no-op when no such `content_hash` exists on-chain, but the row insertion into `attachments` with `was_instantiated=1` already succeeded unconditionally.

The attacker's exact action: run a peer that answers `GET /v2/attachments/<hash>` requests (served as `AttachmentRequest`s during the download batch state machine) with arbitrary/random bytes `Yi` rather than the content that actually hashes to the requested value. Each response is accepted as "successfully downloaded" per `extend_with_attachments`'s lack of verification, and each distinct `Yi` produces a distinct `Hash160`, so each triggers a fresh `INSERT OR REPLACE` row rather than colliding with a prior one.

Existing guards do not catch this: `evict_expired_uninstantiated_attachments` and `evict_k_oldest_uninstantiated_attachments` (`db.rs:538-560`) filter strictly on `was_instantiated = 0`; `max_uninstantiated_attachments` (`stackslib/src/net/atlas/mod.rs:95,108`) similarly only caps rows in that same state (`insert_uninstantiated_attachment`, `db.rs:511-536`). There is no `max_instantiated_attachments`, no `attachments_max_size`-based cap enforced against the raw table row count, and no code path that ever deletes a `was_instantiated = 1` row.

### Impact Explanation
An attacker who is selected as an outbound download peer for Atlas attachment batches (any remote peer that participates in the P2P/HTTP data-plane and gets picked in `network.get_outbound_sync_peers()`, requiring no privileged role or secret) can cause the victim node to permanently store an unbounded number of garbage rows in the `attachments` SQLite table, consuming disk space indefinitely with content that was never committed on-chain. This matches the "High" impact category of attachment/BNS-adjacent storage exhaustion untied to consensus. It does not corrupt canonical chain state or forge served BNS zonefiles (since `find_attachment` lookups are keyed by the actual content hash, and the attacker doesn't know a hash any real `AttachmentInstance` needs), but it is a persistent, repeatable resource-exhaustion vector.

### Likelihood Explanation
Preconditions: the node must have outstanding `AttachmentInstance`s to download (normal operation for BNS name-import/zonefile processing) and the attacker's peer must be selected among `get_outbound_sync_peers()` and win the round-robin/priority selection for at least one `AttachmentsInventoryRequest`/`AttachmentRequest` per round. This requires no secret, no privileged role, and no local access — only running a normal P2P peer that advertises attachment availability. Each successful "win" produces one stored garbage row; the attacker can repeat this indefinitely as new `AttachmentInstance`s continue to appear on-chain (each unresolved instance re-queues into `priority_queue` on failure, giving repeated opportunities), and each retry cycle can introduce a new distinct wrong-hash value.

### Recommendation
In `extend_with_attachments` (`stackslib/src/net/atlas/download.rs:530-558`), verify that the returned `Attachment`'s `hash()` matches the `content_hash` of the original `AttachmentRequest` before inserting into `self.attachments`; on mismatch, treat it as a failed request (`report.bump_failed_requests()`) rather than success. Additionally, in the `Done` branch (`download.rs:153-169`), only call `insert_instantiated_attachment` when `find_all_attachment_instances` returns a non-empty result (i.e., there is a genuine on-chain `AttachmentInstance` awaiting this content), discarding attachments that don't correspond to any known instance.

### Proof of Concept
```rust
// stackslib/src/net/atlas/tests.rs (illustrative)
#[test]
fn test_insert_instantiated_attachment_unbounded_growth() {
    let atlas_config = AtlasConfig::new(false);
    let mut db = AtlasDB::connect_memory(atlas_config).unwrap();

    // Simulate N attacker responses Y1..Yn, none of which correspond to any
    // committed AttachmentInstance.content_hash.
    let n = 10_000;
    for i in 0..n {
        let bogus_bytes = format!("attacker-garbage-{i}").into_bytes();
        let attachment = Attachment::new(bogus_bytes);
        db.insert_instantiated_attachment(&attachment).unwrap();
    }

    // No uninstantiated rows exist, so eviction logic never fires.
    assert_eq!(db.count_uninstantiated_attachments().unwrap(), 0);

    // Yet the attachments table has grown by N rows, unbounded and uncapped.
    let count: i64 = db
        .conn
        .query_row("SELECT COUNT(*) FROM attachments", [], |r| r.get(0))
        .unwrap();
    assert_eq!(count as u32, n);
    // No config field (max_uninstantiated_attachments, attachments_max_size)
    // constrains this; evict_k_oldest_uninstantiated_attachments and
    // evict_expired_uninstantiated_attachments only target was_instantiated = 0.
}
```
A full end-to-end reproduction would additionally require a mock HTTP peer answering `GET /v2/attachments/<hash>` with random hex content and driving `AttachmentsDownloader::run` through `extend_with_attachments` → `Done` to show `insert_instantiated_attachment` gets invoked from `download.rs:161` for content whose hash never matches any `AttachmentInstance.content_hash`, confirming the same growth via the full network code path rather than the DB API directly.
