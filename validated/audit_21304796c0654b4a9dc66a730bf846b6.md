## Confirmed: `AccountIdConverter::try_convert` deterministically derives the pool account from `(PalletId, PoolId)` via `blake2_256` hashing **before** the pool exists in storage [1](#0-0) , exactly like Uniswap's CREATE2-derived pair address that can be pre-funded before `createPair`.

### Title
Balance-based reserve query in `do_add_liquidity` lets an attacker pre-fund the deterministic pool account and block/skew the initial liquidity seeding - (File: `substrate/frame/asset-conversion/src/lib.rs`)

### Summary
`pallet-asset-conversion`'s liquidity math reads live account balances (`Self::get_balance(&pool_account, ...)`) as the "reserves," the same pattern Uniswap V2 uses (`IERC20(token).balanceOf(pair)`). Because the pool account address is a deterministic hash of `(PalletId, asset1, asset2)` [1](#0-0) , an attacker can transfer a small amount of one or both assets directly to that address before the legitimate first liquidity provider calls `add_liquidity`. This reproduces the external report's "1 wei donation" primitive: reserves become non-zero while the LP-token supply is still zero, forcing the router-style `quote()`/optimal-amount branch to execute against attacker-chosen reserves instead of the "fresh pool" branch, which can revert the legitimate depositor's call or skew the amounts they are forced to deposit.

### Finding Description
In `do_add_liquidity`, the reserves used to decide whether the pool is "fresh" are pulled straight from the pool account's actual balances: [2](#0-1) 

Note that the branch selection (`if reserve1.is_zero() || reserve2.is_zero()`) depends solely on the pool account's raw token balance, not on whether any LP tokens have ever been minted (`total_supply`). The pool account itself is a normal `AccountId` computed by `AccountIdConverter::try_convert`, a pure hash of the pallet ID and the (deterministic) `PoolId` [1](#0-0) , which is derivable off-chain by anyone before the pool is even created, exactly mirroring the CREATE2-predictable Uniswap pair address in the external report.

Attack sequence:
1. Attacker computes the future pool account for `(assetA, assetB)`.
2. Attacker transfers a small amount of `assetA` (and/or `assetB`) directly to that account — no special permission needed, ordinary `transfer`/`mint_into` on a sufficient/existing asset works.
3. Victim (or the pool creator) calls `create_pool` then `add_liquidity` for the first time. `get_balance` now returns the donated, non-zero reserve(s) even though `Pools::<T>::get` LP-token `total_supply` is still zero [3](#0-2) .
4. If only one side was donated, the top branch still treats it as fresh (matches Uniswap's `reserveA == 0 && reserveB == 0` check), but if **both** sides were donated (attacker sends both assets), the `else` branch runs `Self::quote(&amount1_desired, &reserve1, &reserve2)` against attacker-chosen reserve ratios even though `total_supply == 0`. The victim's desired amounts must now match the attacker's arbitrary donated ratio or the call reverts with `AssetTwoDepositDidNotMeetMinimum` / `OptimalAmountLessThanDesired` — exactly the router-level revert pattern described in the report — permanently blocking pool seeding at the amounts the victim intended.
5. Separately, the donated tokens sitting in the pool account are never backed by minted LP tokens (mint amount for the zero-supply case is computed from `amount1`/`amount2`, not from `reserve1`/`reserve2`) [4](#0-3) , so the donated value becomes permanently unrecoverable/stuck pool-owned value with no LP claim on it — a fund-lock impact distinct from, but caused by, the same broken invariant (balance ≠ tracked liquidity state).

Existing guards do not stop this: there is no check that `total_issuance(lp_token) == 0` implies `reserve1 == reserve2 == 0`; the code only checks reserves independently of LP-token supply. There is also no restriction on who may hold a balance in the pool account before `create_pool`/`add_liquidity` is called — asset pallets permit ordinary transfers to any valid account.

### Impact Explanation
This is a public, permissionless "underpriced work"/DoS-and-fund-lock primitive against `pallet-asset-conversion`, which backs the AssetHub Uniswap-style DEX used across Polkadot/Kusama Asset Hub runtimes (referenced in `create_pool`/`add_liquidity` wiring in `cumulus/parachains/runtimes/assets/*`). It can:
- Permanently block a specific asset pair from being seeded at the depositor's intended ratio (denial of service on a specific pool), and
- Cause donated attacker funds (and potentially first-depositor funds if the optimal-amount branch silently succeeds at a skewed ratio) to become value that is not represented by any LP token, i.e., value that no account can withdraw via `remove_liquidity` — a fund-lock condition.

No malicious validator, collator, governance actor, or leaked key is required — any unprivileged account with a small balance of the relevant assets can execute the attack against any not-yet-seeded pool address it can predict.

### Likelihood Explanation
High. `PoolId`/pool-account derivation is a pure deterministic function (`AccountIdConverter::try_convert`) of public inputs (`PalletId`, asset pair) [1](#0-0) , so any address can be computed off-chain before pool creation with no cost beyond a small token transfer. Asset creation on Asset Hub is frequently permissionless (sufficient assets, or any account minting its own asset class), making pre-funding trivial and cheap, similar to the low-cost 1-wei donation in the original report.

### Recommendation
Track pool reserves via internal pallet storage (or verify `T::PoolAssets::total_issuance(lp_token) == 0` as the sole condition for the "fresh pool" branch) instead of trusting the live `get_balance` of the pool account. Before minting on the zero-supply path, reconcile/absorb any pre-existing balance into the LP-token accounting (e.g., treat any balance present at first `add_liquidity` as belonging proportionally to the first minter, or reject `add_liquidity`/`create_pool` if the pool account already holds a non-zero balance of either asset that isn't reflected by any LP-token supply).

### Proof of Concept
1. Compute `pool_account = AccountIdConverter::try_convert(&(assetA, assetB))` for a not-yet-created pool.
2. From an unprivileged account, call `Assets::mint`/`transfer` to send `amountA` of `assetA` and `amountB` of `assetB` directly to `pool_account` (no `create_pool` call needed first).
3. Call `AssetConversion::create_pool(assetA, assetB)` — this only checks `Pools::<T>::contains_key`, not the account's balance, so it succeeds.
4. Victim calls `AssetConversion::add_liquidity(assetA, assetB, amount1_desired, amount2_desired, amount1_min, amount2_min, mint_to)` with amounts reflecting their intended 1:1 (or other) ratio.
5. Because `reserve1`/`reserve2` (from step 2) are both non-zero, `do_add_liquidity` takes the `quote()` branch (`substrate/frame/asset-conversion/src/lib.rs:822-843`) using the attacker's donated ratio instead of the "fresh pool" branch; if `amount2_desired`/`amount1_desired` don't match that ratio within `amount1_min`/`amount2_min`, the call reverts, blocking pool seeding — reproducing the reported bug class inside `pallet-asset-conversion`.

/// `PoolId` to `AccountId` conversion.
pub struct AccountIdConverter<Seed, PoolId>(PhantomData<(Seed, PoolId)>);
impl<Seed, PoolId, AccountId> TryConvert<&PoolId, AccountId> for AccountIdConverter<Seed, PoolId>
where
	PoolId: Encode,
	AccountId: Decode,
	Seed: Get<PalletId>,
{
	fn try_convert(id: &PoolId) -> Result<AccountId, &PoolId> {
		sp_io::hashing::blake2_256(&Encode::encode(&(Seed::get(), id))[..])
			.using_encoded(|e| Decode::decode(&mut TrailingZeroInput::new(e)).map_err(|_| id))
	}
}
