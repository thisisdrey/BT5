### Title
Relay-Chain-supplied `activation_timestamp` is trusted without bounds/monotonicity checks in `pallet-staking-async::session_rotation::Rotator::end_session`, corrupting era-duration reward accounting on Asset Hub - (File: substrate/frame/staking-async/src/session_rotation.rs)

### Summary
The external report's core broken invariant is: a timestamp value produced in one chain/domain is trusted and compared/consumed by logic on a different chain/domain without any sanity or monotonicity check, even though the two domains' clocks are not guaranteed to be consistent with one another. `pallet-staking-async` reproduces this exact pattern: Asset Hub (AH) no longer keeps its own local clock for staking purposes and instead relies entirely on an `activation_timestamp: Option<(u64, u32)>` value sent by the Relay Chain (RC) inside `SessionReport`, which is fed straight into era-start bookkeeping used to compute reward payouts.

### Finding Description
The rc-client module's own documentation states the design intent explicitly: *"pallet-staking-async no longer has a notion of timestamp locally, and only relies in [the RC-provided timestamp]"* [1](#0-0) .

The `SessionReport` struct carries `activation_timestamp: Option<(u64, u32)>`, documented as "the new validator set was activated at the given timestamp" [2](#0-1) .

This value flows unchanged from `relay_session_report` → `AHStakingInterface::on_relay_session_report` → `session_rotation::Rotator::end_session`: [3](#0-2) 

Inside `end_session`, the only check performed on the incoming `(time, id)` pair is that `id` matches the currently planned era; the `time` component itself is passed straight into `start_era` with **no check that it is greater than the previous era's start timestamp, no check that it is not implausibly far in the future, and no check against any local notion of "now"** on Asset Hub: [4](#0-3) 

This is architecturally identical to the Renzo bug: a value representing "time" is generated in one execution domain (Relay Chain) and consumed in another (Asset Hub) that has explicitly given up its own clock for this purpose, exactly as `xRenzoDeposit::_updatePrice` consumed an L1 timestamp against L2 semantics. The era duration derived from this timestamp (`current activation time - previous era start`) directly drives the reward payout amount, as shown in the era-rotation test suite where `validator_payout_for(time_per_era())` is used to compute `EraPaid { validator_payout, .. }` [5](#0-4) .

Existing tests only demonstrate protection for the `id` mismatch case (`activation_timestamp_when_no_planned_era`, which deliberately sends a *future* timestamp together with a *wrong* id and is rejected solely because of the id check, not because of the timestamp itself) [6](#0-5) . There is no test or code path that rejects a syntactically-valid `id` accompanied by a stale, replayed, or out-of-order `time` value.

### Impact Explanation
The era-duration figure computed from the RC-sourced timestamp feeds directly into the validator reward payout formula (`validator_payout_for(time_per_era())`). If the elapsed time between two consecutive `activation_timestamp` values sent by the Relay Chain does not correctly reflect the real elapsed wall-clock time as understood by Asset Hub (e.g., due to XCM message queue delay/reordering between the two chains, a stalled bridge/queue causing a backlog of session reports to be replayed in a burst, or any deviation between RC's and AH's block-time/timestamp progression), the computed era duration will be wrong. This causes wrong-amount reward settlement (over- or under-minting of staking rewards) to the staker reward pots — a direct violation of the "conserve value and settle exactly once to the rightful ... amount" invariant for staking payouts described in the impact gate.

### Likelihood Explanation
This does not require a malicious relayer, validator, or governance actor — `relay_session_report` is dispatched by the legitimate, authorized `RelayChainOrigin` [7](#0-6) . The risk arises purely from the asynchronous, cross-domain nature of the message pipeline (buffering/leftover handling, session-report bursts documented and tested in `session_report_burst`) combined with the complete absence of a timestamp sanity check on the AH side, mirroring the exact "L1/L2 timestamps are unrelated, can't be demanded to be monotonic between domains" root cause acknowledged by the external report's judge.

### Recommendation
In `session_rotation::Rotator::end_session` / `start_era`, validate the RC-supplied `time` before use: reject or clamp values that are not monotonically greater than the previous era's stored start timestamp, and bound the value against Asset Hub's own local time (e.g., via `pallet_timestamp::Now` or block-time-derived estimate) with an explicit maximum allowed drift, emitting `Event::Unexpected` and skipping era rotation/payout using that value when the check fails, analogous to the existing `id` mismatch handling.

### Proof of Concept
1. Asset Hub is at `active_era = N`, `planned_era = N+1`, with `ActiveEraInfo.start = T0` (set from a prior RC `activation_timestamp`).
2. RC's XCM message queue to AH backs up or reorders (a normal operational condition already anticipated by the `leftover`/buffering logic in `relay_session_report`, see the burst-handling test) [8](#0-7) .
3. A `SessionReport` eventually arrives with `activation_timestamp = Some((T1, N+1))` where `id = N+1` correctly matches `planned_era`, but `T1` does not correctly reflect the real elapsed time since `T0` (e.g., it is much larger due to accumulated queue delay, or smaller due to reordering).
4. `end_session` matches `Some((time, id)) if Some(id) == current_planned_era` and unconditionally calls `Self::start_era(active_era, starting, T1)` [9](#0-8) , with no plausibility check on `T1`.
5. `time_per_era() = T1 - T0` is now wrong, and the subsequent `EraPaid` payout computed from this duration mis-prices the reward distributed to the era's staker pot, as demonstrated by the payout-by-duration pattern in `era_rotation.rs` tests.

#[test]
fn session_report_burst() {
	// note: there is also an e2e `session_report_burst` test
	ExtBuilder::default().local_queue().build().execute_with(|| {
		// Initial state
		assert_eq!(CurrentEra::<T>::get(), Some(0));
		assert_eq!(Rotator::<Runtime>::active_era_start_session_index(), 0);
		assert_eq!(ActiveEra::<T>::get(), Some(ActiveEraInfo { index: 0, start: Some(0) }));
		assert_eq!(rc_client::LastSessionReportEndingIndex::<T>::get(), None);

		// then send 20 sessions all at once. This is enough to schedule multiple elections, but we
		// only schedule one.
		for s in 1..=20 {
			assert_ok!(rc_client::Pallet::<T>::relay_session_report(
				RuntimeOrigin::root(),
				rc_client::SessionReport {
					end_index: s,
					validator_points: vec![(5, 50)],
					activation_timestamp: None,
					leftover: false,
				},
			));
			// all are processed fine, in one go
			assert_eq!(
				rc_client_events_since_last_call(),
				vec![rc_client::Event::SessionReportReceived {
					end_index: s,
					activation_timestamp: None,
					validator_points_counts: 1,
					leftover: false
				}]
			);
			// and we have collected reward points.
			assert_eq!(staking_async::ErasRewardPoints::<T>::get(&0).total, 50 * s);
		}

		// crucially, election has started, but we have not done anything else.
		Rotator::<T>::assert_election_ongoing();

		assert!(matches!(
			&staking_events_since_last_call()[..],
			&[
				staking_async::Event::SessionRotated {
					starting_session: 2,
					active_era: 0,
					planned_era: 1
				},
				..,
				staking_async::Event::SessionRotated {
					starting_session: 21,
					active_era: 0,
					planned_era: 1
				}
			]
		));
	})
}
