### Title
Custom section preceding ExportSection in `PrepareContext::run` causes duplicate `MEMORY_EXPORT` export sections in Wasmtime-prepared bytecode - ([File: runtime/near-vm-runner/src/prepare/prepare_v3.rs])

### Summary
In `PrepareContext::run` (`runtime/near-vm-runner/src/prepare/prepare_v3.rs`), a `CustomSection` payload occurring before the real `ExportSection` payload invokes `ensure_export_section()` (line 279), which unconditionally appends a synthetic `ExportSection` containing `MEMORY_EXPORT` when `before_export_section` is still `true` and `vm_kind == Wasmtime`. When the real `ExportSection` payload is later encountered (lines 152-201), the handler unconditionally re-emits a second, independent `ExportSection` (also containing another `MEMORY_EXPORT` entry for Wasmtime) without first checking `self.before_export_section`. The result is a re-encoded module with two `Export` sections and duplicate `MEMORY_EXPORT` names.

### Finding Description
`ensure_export_section` (lines 364-374) guards its synthetic-export emission with `if self.before_export_section`, and is called from the `CustomSection`, `StartSection`, `ElementSection`, `DataCountSection`, `DataSection`, and `CodeSectionStart` branches to make sure a memory export exists before those sections in case the module never has an explicit `ExportSection`. However, the real `wp::Payload::ExportSection` branch (lines 152-201) does not check or call `ensure_export_section`/`self.before_export_section` before emitting its own `new_section` (which also appends `MEMORY_EXPORT` for Wasmtime at line 198) - it merely sets `self.before_export_section = false` as a side effect (line 154) after the fact.

Since custom sections are permitted by the core wasm binary format to appear before/interleaved with core sections (including before `Export`), an attacker can craft a module ordered as: Type/Function/Table/Memory/Global sections, then a `Custom` section, then the real `Export` section, then Code, etc. Parsing proceeds section-by-section in `wp::Parser::parse_all` (line 66), so the `CustomSection` payload is seen first and triggers `ensure_export_section()` → emits export section #1 with `MEMORY_EXPORT`. Then the real `ExportSection` payload is processed unconditionally and emits export section #2, also containing `MEMORY_EXPORT` for Wasmtime.

The resulting `output_code` returned by `run()` (line 305) is not re-validated against `wp::Validator` before being passed into `finite_wasm_6::Analysis::analyze` and `InstrumentContext::run` in `prepare_contract` (lines 402-461); neither of those internal passes is guaranteed to reject a structurally invalid module with duplicate `Export` sections/duplicate export names, since they are focused on gas/stack accounting and instrumentation, not full module validation. If they don't reject it, `prepare_contract` returns `Ok`, and the malformed bytecode is accepted, stored, and cached.

### Impact Explanation
If this path is reachable, `DeployContract` would succeed and cache the module. The actual defect only surfaces at `FunctionCall` time when Wasmtime compiles/instantiates the cached bytes and rejects the module for duplicate section id / duplicate export name, causing every subsequent call to that contract to fail. This matches the "Liveness and Determinism" concern raised in the question: deploy-time acceptance no longer guarantees a callable contract, and gas is burned on every failed call.

### Likelihood Explanation
I could not confirm from the available code whether this is actually exploitable, for the following unresolved reasons:
1. I was unable to fully inspect `finite_wasm_6::Analysis::analyze` and the full body of `InstrumentContext::run` (in `instrument_v3.rs`) to determine whether they perform full structural re-validation of `lightly_steamed` (the intermediate output of `PrepareContext::run`) that would catch a duplicate `Export` section before `prepare_contract` returns `Ok`. If either pass re-parses/validates with `wp::Validator` or otherwise rejects duplicate sections, this bug is caught at deploy time (as `PrepareError::Deserialization`/`Serialization`) and the described exploit path does not exist.
2. The existing fuzz test `v3_preparation_wasmtime_generates_valid_contract_fuzzer` (`prepare_v3.rs` lines 639-662) explicitly re-validates the output of `prepare_contract` (not just `PrepareContext::run`) with `wp::Validator::validate_all` and panics on failure, which suggests this exact class of bug (invalid output despite `Ok` prepare result) is a known invariant that's actively fuzzed against; if this bug were reachable, the fuzzer would very likely have caught it already, since Wasmtime's `wp::Validator` used for `validate_all` should reject duplicate Export sections/duplicate export names, unless the fuzzer's harness or corpus never generates custom sections positioned before an export section.
3. I could not verify where in the transaction execution pipeline `prepare_contract` is actually invoked at `DeployContract` time (i.e., whether deploy-time validation calls this exact function, or a different/lighter check), nor confirm the near_vm backend's behavior for comparison (the divergence claim in the question).

### Recommendation
Given the unresolved uncertainty above, I cannot confirm this rises to a validated, reproducible vulnerability with the current evidence. A background engineering session should:
1. Read the full `finite_wasm_6::Analysis::analyze` and `InstrumentContext::run` implementations to determine whether duplicate `Export` sections in `lightly_steamed` are caught.
2. If not caught, add a defensive check to `wp::Payload::ExportSection` handling in `prepare_v3.rs` to short-circuit if `!self.before_export_section` is already false (indicating another Export section already appeared, which is itself invalid and should return `PrepareError::Deserialization`), and/or run `wp::Validator::validate_all` on `lightly_steamed`/`output_code` before returning from `PrepareContext::run`/`prepare_contract`.
3. Extend `v3_preparation_wasmtime_generates_valid_contract_fuzzer`'s corpus/harness to specifically exercise custom sections positioned immediately before the export section, to confirm/deny the hypothesis with concrete fuzzing evidence.

### Proof of Concept
Cannot be fully specified without confirming point 1 above. Suggested test plan for the background engineer to execute against the actual code (not simulated here):

pub(crate) fn prepare_contract(
    original_code: &[u8],
    features: crate::features::WasmFeatures,
    config: &Config,
    kind: VMKind,
) -> Result<Vec<u8>, PrepareError> {
    let lightly_steamed = PrepareContext::new(original_code, features, config).run()?;

    let analysis = finite_wasm_6::Analysis::new()
        .with_stack(SimpleMaxStackCfg)
        .with_gas(SimpleGasCostCfg {
            regular: u64::from(config.regular_op_cost),
            linear_base: config.linear_op_base_cost,
            linear_unit: config.linear_op_unit_cost,
        })
        .analyze(&lightly_steamed)
        .map_err(|err| {
            tracing::error!(target: "vm", ?err, ?kind, "analysis failed");
            PrepareError::Deserialization
        })?;
