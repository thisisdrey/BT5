### Title
Index-out-of-range panic in Mach-O load-command parsing due to unchecked/untrusted `sz` field - ([File: src/cmd/link/internal/loadmacho/ldmacho.go])

### Summary
`cmd/link`'s internal Mach-O object loader (`loadmacho.Load`/`unpackcmd`) trusts the attacker-controlled `cmdsize` field of each Mach-O load command to slice its own header buffer, without ever validating that the underlying buffer (`cmdp`) is actually large enough for the fixed-size sub-structures it later indexes into. This is the same class of bug as the GPAC `print_udta` heap overflow: a container-format box/atom carries a declared length that is trusted for pointer/slice arithmetic instead of being validated against the real remaining buffer size, letting a crafted "box" cause an out-of-bounds access.

### Finding Description
`Load()` reads the whole load-command area into one buffer, `cmdp, _, err := f.Slice(uint64(cmdsz))` [1](#0-0) , then iterates `ncmd` times reading `ty`/`sz` from the front of `cmdp` and calling `unpackcmd(cmdp, m, &m.cmd[i], uint(ty), uint(sz))` before advancing with `cmdp = cmdp[sz:]` [2](#0-1) . Nothing checks that the attacker-supplied `sz` is `<= len(cmdp)`.

Inside `unpackcmd`, for `LdMachoCmdSegment`/`LdMachoCmdSegment64` the code only validates the declared `sz` against a minimum constant (e.g. `if sz < 72 { return -1 }` for 64-bit segments) and then unconditionally indexes the *full remaining* `p` (which is `cmdp`, not `p[:sz]`) at fixed offsets such as `p[8:24]`, `e8(p[24:])`, `p[56:]`, etc. [3](#0-2) . If the real remaining buffer (`cmdp`, bounded by the file's `cmdsz`) is shorter than the claimed `sz`, these fixed-offset slice expressions run out of the actual buffer and panic with "slice bounds out of range" — an out-of-bounds access analogous to GPAC's `print_udta` reading past its buffer due to an untrusted atom-size field.

### Impact Explanation
This is a Go-toolchain (linker) crash/DoS: a crafted or corrupted Mach-O relocatable object (`.o`/`.syso`) processed by `cmd/link` during a normal `go build`/`go test` on darwin (e.g., a native object bundled in or produced for a third-party Go module using cgo, or an attacker-supplied precompiled `.syso`) can panic the linker via an out-of-bounds slice access. It does not by itself demonstrate memory-safety corruption (Go's runtime turns this into a panic rather than a C-style heap overflow), so it would fall on Go's PUBLIC-track "parser panic on malicious input" bucket rather than a memory-corruption/RCE bucket, but the root cause (trusting an untrusted length field for buffer navigation without bounds validation) is structurally identical to the CVE's root cause.

### Likelihood Explanation
The victim workflow is an ordinary `go build`/`go test`/link of a package that embeds or links a native Mach-O object (via cgo output, `.syso`, or a prebuilt static/dynamic Mach-O supplied through a module or vendored archive) on a darwin/amd64 or darwin/arm64 target. The attacker only needs to control the bytes of that Mach-O object; no special privileges are required beyond having the victim build/link with it.

### Recommendation
Before calling `unpackcmd`, verify `sz <= uint(len(cmdp))` in the `Load` loop, and inside `unpackcmd` bound every fixed-offset access to `p[:sz]` (or otherwise ensure `len(p) >= sz` and `sz` covers the offsets used) instead of indexing the full remaining buffer.

### Proof of Concept
```go
package loadmacho

import "testing"

// TestUnpackcmdOOB demonstrates that a crafted LC_SEGMENT_64 load command
// whose declared size exceeds the actual remaining buffer causes an
// out-of-bounds slice panic instead of a graceful error.
func TestUnpackcmdOOB(t *testing.T) {
	defer func() {
		if r := recover(); r == nil {
			t.Fatal("expected panic due to out-of-bounds slice access, got none")
		}
	}()

	m := &ldMachoObj{e: littleEndian{}}
	c := &ldMachoCmd{}

	// Only 8 bytes available, but sz claims 1000000 (>=72 satisfies the
	// minimum-size check for LdMachoCmdSegment64), so unpackcmd proceeds
	// to index p[8:24], p[24:], etc. against an 8-byte slice.
	p := make([]byte, 8)
	unpackcmd(p, m, c, LdMachoCmdSegment64, 1000000)
}
```
Expected: the call panics with an index/slice-bounds-out-of-range error, confirming the buffer is indexed past its real length using the untrusted `sz` field rather than being validated first.
