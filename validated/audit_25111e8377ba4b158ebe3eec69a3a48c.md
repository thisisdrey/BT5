### Title
Legacy SUICIDE opcode (`canSuicide`) omits the account's own frozen-balance checks that `SUICIDE2`/`canSuicide2` enforces, allowing self-destruct of a contract with active self-frozen bandwidth/energy - ([File: actuator/src/main/java/org/tron/core/vm/program/Program.java])

### Summary
`OperationActions.suicideAction` (legacy `SUICIDE` opcode) guards execution with `Program.canSuicide()`, while the newer `OperationActions.suicideAction2` (`SUICIDE2`) guards with `Program.canSuicide2()`. `canSuicide2()` calls `freezeV1Check()`, which blocks self-destruct when the contract account itself has an unexpired self-frozen bandwidth (`getFrozenList()`) or self-frozen energy (`getAccountResource().getFrozenBalanceForEnergy()`) balance, in addition to checking delegated balances. `canSuicide()`, however, only checks the account's *delegated* frozen balances (`getDelegatedFrozenBalanceForBandwidth`/`getDelegatedFrozenBalanceForEnergy`) and never inspects the account's own `FrozenList`/`FrozenBalanceForEnergy`. [1](#0-0)  Both entry points funnel into the same guard pattern in `OperationActions`: [2](#0-1) 

### Finding Description
`freezeV1Check` (used only by `canSuicide2`) explicitly walks the account's own `FrozenList` and `AccountResource.getFrozenBalanceForEnergy()` to block self-destruction while V1 stake is still locked, then also checks delegated balances: [3](#0-2) 

`canSuicide` (used by the older, still-reachable `SUICIDE` opcode via `suicideAction`) skips this self-frozen check entirely and only tests delegated balances plus `freezeV2Check`: [4](#0-3) 

Because both opcodes are reachable from any `TriggerSmartContractContract`/`CreateSmartContractContract` transaction executed by `VMActuator`/`OperationRegistry` (an unprivileged contract call), a contract with TRX self-frozen for bandwidth or energy (V1 freeze, still expiring) can execute the legacy `SUICIDE` opcode and successfully self-destruct even though the equivalent `SUICIDE2` path would reject it via `freezeV1Check`. This is the same bug class as the report: a "wrapper" reachable via ordinary user calls fails to apply the same restrictive check that a sibling/parent implementation enforces.

### Impact Explanation
Self-destructing a contract while it still holds an unexpired V1 self-frozen balance for bandwidth/energy removes the account without going through the normal unfreeze/expire accounting path that credits the frozen TRX back to the owner. This creates an inconsistency between chain-level bookkeeping (total frozen supply, resource pools) and the now-deleted account, which can permanently freeze/lock or orphan the staked TRX (the frozen balance can no longer be unfrozen/withdrawn because the account no longer exists to receive it), and desynchronizes global bandwidth/energy accounting used across the network. This matches the "unauthorized... permanent freezing of funds" acceptance criterion.

### Likelihood Explanation
Low/medium difficulty, matching the source report's "Low" difficulty rating: any account can deploy a simple contract, self-freeze V1 bandwidth/energy for it, and trigger a call ending in the legacy `SUICIDE` opcode — no special privileges required, and `VMConfig.allowTvmFreeze()`/`allowTvmFreezeV2()` are standard, already-activated feature flags on production chains, not exotic toggles.

### Recommendation
Short term: make `canSuicide()` call the same `freezeV1Check()` used by `canSuicide2()` (or otherwise apply the self-frozen-balance check to the legacy `SUICIDE` opcode) so both opcodes enforce identical restrictions. Long term: consolidate `canSuicide`/`canSuicide2` and `freezeCheck`/`freezeV1Check` into a single shared guard to prevent this kind of divergence when new freeze/vote checks are added in the future, and add differential tests asserting `SUICIDE` and `SUICIDE2` reject in the same conditions.

### Proof of Concept
1. Deploy a simple contract `C` (bytecode containing a bare `SUICIDE` opcode reachable from an ABI function) from `OWNER_ADDRESS`.
2. From `OWNER_ADDRESS`, freeze V1 bandwidth (or energy) for `C`'s account with an expiration in the future (`VMConfig.allowTvmFreeze()` enabled, as in mainnet), setting `AccountCapsule.getFrozenList()`/`getAccountResource().getFrozenBalanceForEnergy()` non-zero with `expireTime > now`.
3. Trigger `C`'s function that executes the legacy `SUICIDE` opcode (not `SUICIDE2`). `OperationActions.suicideAction` calls `program.canSuicide()`, which does not inspect `getFrozenList()`/`getFrozenBalanceForEnergy()`, so the check passes and `program.suicide(address)` executes, deleting the account.
4. Repeat the same steps but using the `SUICIDE2` opcode/`suicideAction2`: `program.canSuicide2()` invokes `freezeV1Check`, which detects the unexpired self-frozen balance and returns `false`, causing `program.getResult().setRevert()` — the self-destruct is correctly blocked.
5. The divergent outcomes for functionally identical starting states demonstrate that the legacy `SUICIDE` path bypasses a restriction that the codebase itself considers necessary (as enforced by `SUICIDE2`), consistent with the report's bug class of an unrestricted function invoking privileged/state-changing logic that a sibling implementation properly guards. [2](#0-1) 

**Caveat / uncertainty**: I was not able to fully trace, within tool budget, whether a later validate/execute step elsewhere (e.g. in `Program.suicide()` itself, or `Manager`/`FreezeBalanceV2` processors) re-checks and blocks this case, which would reduce or eliminate the impact. The `StakeV2AfterSelfDestructTest` I found focuses on post-self-destruct freeze/unfreeze/cancel *processor* validation timeouts (a different, already-covered concern) rather than on the pre-suicide `canSuicide` vs `canSuicide2` divergence itself, so it does not confirm or refute this specific gap. Confirming exploitability with a full TVM integration test (deploy → self-freeze V1 → trigger legacy SUICIDE vs SUICIDE2) would require running the test suite, which is outside the scope of this read-only analysis.

  public boolean canSuicide2() {
    byte[] owner = getContextAddress();
    AccountCapsule accountCapsule = getContractState().getAccount(owner);

    return freezeV1Check(accountCapsule) && freezeV2Check(accountCapsule);
  }

  private boolean freezeV1Check(AccountCapsule accountCapsule) {
    if (!VMConfig.allowTvmFreeze()) {
      return true;
    }

    // check freeze
    long now = getContractState().getDynamicPropertiesStore().getLatestBlockHeaderTimestamp();
    // bandwidth
    if (accountCapsule.getFrozenCount() > 0
        && accountCapsule.getFrozenList().stream()
        .anyMatch(frozen -> frozen.getExpireTime() > now)) {
      return false;
    }
    // energy
    Protocol.Account.Frozen frozenEnergy =
        accountCapsule.getAccountResource().getFrozenBalanceForEnergy();
    if (frozenEnergy.getFrozenBalance() > 0 && frozenEnergy.getExpireTime() > now) {
      return false;
    }

    // check delegate
    return accountCapsule.getDelegatedFrozenBalanceForBandwidth() == 0
        && accountCapsule.getDelegatedFrozenBalanceForEnergy() == 0;
  }

  public static void suicideAction(Program program) {
    if (program.isStaticCall()) {
      throw new Program.StaticCallModificationException();
    }

    if (!program.canSuicide()) {
      program.getResult().setRevert();
    } else {
      DataWord address = program.stackPop();
      program.suicide(address);
    }

    program.stop();
  }

  public static void suicideAction2(Program program) {
    if (program.isStaticCall()) {
      throw new Program.StaticCallModificationException();
    }

    if (!program.canSuicide2()) {
      program.getResult().setRevert();
    } else {
      DataWord address = program.stackPop();
      program.suicide2(address);
    }

    program.stop();
  }
