### Title
Unprivileged dust-transfer griefing fills `MAX_TOKENS_PER_USER` and blocks victim deposits - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
Analogous to CVE-2020-8766 (an improper conditions check enabling an unauthenticated denial of service), `Pool.onlyIfAdditionWillNotReachMaxTokens` reverts whenever `debtTokensOfAccount.length + depositTokensOfAccount.length >= MAX_TOKENS_PER_USER` (30) — before checking whether the token being added is already tracked or whether the recipient consented. Because anyone can force a new `DepositToken` entry into a victim's per-account list by sending them a dust amount of a freely transferable `msdTOKEN` via `DepositToken.transfer`/`_transfer`, an unprivileged EOA can saturate a victim's token list and cause all subsequent first-time deposits to that account to revert with `UserReachedMaxTokens`.

### Finding Description
- `Pool.addToDepositTokensOfAccount` enforces `onlyIfAdditionWillNotReachMaxTokens(account_)`, reverting once the combined deposit+debt token list reaches `MAX_TOKENS_PER_USER = 30` (`contracts/Pool.sol:143-148`, `contracts/Pool.sol:216-220`). [1](#0-0) 
- `DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance transitions from 0 (`contracts/DepositToken.sol:517-520`). `transfer` only checks the *sender's* unlocked balance (`_revertIfLocked(_msgSender, amount_)`); there is no opt-in or minimum-amount check for recipients (`contracts/DepositToken.sol:348-354`). [2](#0-1) 
- `DepositToken._mint` (reached by the public `deposit(amount_, onBehalfOf_)`) calls `addToDepositTokensOfAccount` for any `onBehalfOf_` whose balance was 0 (`contracts/DepositToken.sol:486-488`, `contracts/DepositToken.sol:211-237`). [3](#0-2) 
- Attack path: attacker buys/acquires dust positions in the pool's deposit tokens (e.g., via `deposit(1 wei, attacker)` for each underlying, or cheap AMM/transfers), then calls `msdToken_i.transfer(victim, 1)` for every `DepositToken` the victim does not already hold. Each transfer appends one entry to `depositTokensOfAccount[victim]`. Once the combined list hits 30, every call path that would add a *new* token to the victim's list reverts:
  - `DepositToken.deposit(amount, victim)` → `_mint` → `addToDepositTokensOfAccount` → `UserReachedMaxTokens` for any collateral type the victim doesn't already hold.
  - Anyone transferring a new `msdTOKEN` to the victim reverts.
  - The victim cannot mint a new debt-token type either, since `DebtToken.issue` → `_mint` → `addToDebtTokensOfAccount` shares the same combined limit (`contracts/Pool.sol:204-208`).
- Removing entries requires the victim to transfer each dust token out, which itself calls `_revertIfLocked`/`unlockedBalanceOf` — dust transfers when the victim carries debt are partially locked, and every removal is an extra transaction the victim must perform.

### Impact Explanation
Temporary freezing of funds / liveness DoS: while the list is saturated, the victim cannot deposit any *new* collateral type into their position and cannot receive any new `msdTOKEN`. If the victim's health factor is deteriorating and their existing collateral types are depleted or insufficient, they are blocked from topping up with other collateral, which can force liquidation of the position. Recovery requires manually flushing dust entries one-by-one (bounded by the attacker's re-fills, which cost only 1 wei of each msdToken). This matches the CVE bug class: an improper conditions check (the combined-length `>=` cap applied on an attacker-controllable, recipient-unconsented state transition) enables an unauthenticated denial of service.

### Likelihood Explanation
- Fully unprivileged: attacker needs only EOAs and dust amounts of the pool's deposit tokens; no governor/keeper/oracle cooperation, no fake contracts required (attacker's own real deposits suffice).
- Effectiveness depends on deployed configuration: the attack can fill at most `number of pool DepositTokens` entries (debt tokens cannot be force-added since `issue` mints debt to the caller). On pools with many listed collaterals approaching 30, or against victims already holding several token types, the cap is reachable; on pools with few collaterals, the attack only reduces the victim's remaining headroom.
- The victim can clear entries by transferring dust out (unlocked portion only), so the DoS is temporary rather than permanent.

### Recommendation
- Only revert in `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` when the set insertion is actually new and the cap is reached (the current code does revert pre-`add`, which is fine), but more importantly, allow the victim to bypass the cap on cleanup: permit `removeFrom*` calls and consider not counting entries below a dust threshold.
- Alternatively, track per-account lists only for tokens the account has deposited/minted itself, or add an opt-in/allowlist for incoming `msdTOKEN` transfers so unsolicited dust cannot consume list slots.
- Optionally, exempt `seize`/liquidation transfers from the max-tokens check so the cap can never interfere with liquidations.

### Proof of Concept
Hardhat (fork or unit) sketch:

```ts
// victim starts with 0 deposit/debt tokens tracked
const victim = bob.address

// attacker holds dust of each DepositToken in the pool
for (const msd of poolDepositTokens) {
  // attacker already deposited 1 wei earlier: msd.deposit(1, attacker)
  if ((await msd.balanceOf(victim)) == 0 && (await msd.balanceOf(attacker.address)) > 0) {
    await msd.connect(attacker).transfer(victim, 1) // adds entry to victim's list
  }
}

// once depositTokensOfAccount[victim].length + debtTokens == 30:
expect(await pool.getDepositTokensOfAccount(victim)).to.have.lengthOf(30)

// any new deposit on behalf of victim reverts
await expect(
  newMsdToken.connect(alice).deposit(parseEther('1'), victim)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')

// and victim cannot issue a new debt token type
await expect(
  newDebtToken.connect(bob).issue(amount, bob.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')
```

The unit test at `test/Pool.test.ts:1386-1416` already demonstrates the `UserReachedMaxTokens` revert path; the PoC only differs in that entries are added via unsolicited `DepositToken.transfer` dust sends rather than by the account owner. [4](#0-3)
