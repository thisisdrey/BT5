### Title
Cross-StackerDB chunk replay due to signature not binding contract identifier - (File: `libstackerdb/src/libstackerdb.rs`, `stackslib/src/net/stackerdb/mod.rs`, `stackslib/src/net/stackerdb/db.rs`)

### Summary
`SlotMetadata::auth_digest()` computes the signed digest from only `slot_id`, `slot_version`, and `data_hash` [1](#0-0) . The `QualifiedContractIdentifier` (which StackerDB/contract the chunk belongs to) is never part of what is cryptographically authenticated. It is only used as a routing/lookup key to select which DB's slot-owner table to check the recovered address against, both in `validate_received_chunk` [2](#0-1)  and in `StackerDBTx::try_replace_chunk` [3](#0-2) . This is exactly the "auth token only used for the check/lookup path, not bound into what's actually verified" pattern from the referenced report: the enum/identifier is checked for routing purposes but the signature itself doesn't commit to it.

### Finding Description
A `StackerDBPushChunkData` P2P gossip message carries `contract_id`, `rc_consensus_hash`, and `chunk_data` (slot_id/slot_version/sig/data) as independent, unauthenticated fields [4](#0-3) . On receipt, `handle_unsolicited_StackerDBPushChunk` uses `chunk_data.contract_id` purely to select which local StackerDB config/table to validate and store into [5](#0-4) . The actual authenticity check, `validate_received_chunk`, recovers the signer's address from `slot_metadata.verify(&addr)` and only checks it against the owner recorded for that `smart_contract_id`+`slot_id` pair [6](#0-5) ; the signature payload (`auth_digest`) never includes `smart_contract_id` at all.

Since Stacks stacker-set/StackerDB contracts (e.g. successive PoX reward-cycle `.signers-*`/`.miners-*` contracts) frequently reuse the same address for the same `slot_id` across multiple contract instances, a chunk that was legitimately signed by a stacker/signer for one StackerDB contract's slot can be re-wrapped by *any* relaying peer (attacker does not need the signer's key at all — they just need a previously observed, validly-signed chunk) into a `StackerDBPushChunkData` naming a *different* `contract_id` that happens to assign the same address to the same `slot_id`. Both `validate_received_chunk` and `try_replace_chunk` will accept and store it, because they only check "does this address own this slot in this contract," which is satisfied, and never check "was this exact chunk signed for this contract." The same gap exists in the storage layer: `StackerDBTx::try_replace_chunk` looks up `slot_validation` scoped by `smart_contract` [7](#0-6) , but `slot_desc.verify(&slot_validation.signer)` again only checks `slot_id`/`slot_version`/`data_hash`, not which contract it was destined for.

### Impact Explanation
This breaks the "signed-for-contract-A" vs "accepted-for-contract-B" equality: forged/misrouted but validly-signed data can be propagated network-wide into a StackerDB replica other than the one it was actually authorized for, letting an attacker who is not the signer inject stale or cross-context data as canonical into any StackerDB instance whose slot-owner table happens to overlap with another instance's. This matches the "network-wide propagation of forged data" / "serving non-canonical state as canonical" impact categories, since the version/staleness check (`slot_desc.slot_version <= slot_validation.version`) is evaluated per-contract independently, so a chunk that is "fresh" relative to contract B's version counter (even though it was produced for contract A) can overwrite contract B's slot with attacker-selected (replayed) content, all via existing P2P relay without needing to compromise any key.

### Likelihood Explanation
Exploitation requires only relaying a message any peer can observe/craft (`StackerDBPushChunkData`) with a substituted `contract_id`; it needs no private key and no admin role, only that the two contracts' signer-to-slot assignment happens to intersect at the target slot — a realistic condition for the Stacks PoX signer sets, which are frequently the same address set slotted in the same order for consecutive reward-cycle StackerDB contracts.

### Recommendation
Bind the target `QualifiedContractIdentifier` (or its stable numeric `stackerdb_id`) into `SlotMetadata::auth_digest()` so a signature is only valid for the specific StackerDB contract it was produced for, mirroring the report's recommended fix of checking the identifying parameter explicitly rather than only using it for routing/lookup.

### Proof of Concept
1. Registize two StackerDB contracts, `A` and `B`, both configuring address `X` as owner of `slot_id = 0` (a realistic configuration mirroring adjacent PoX reward-cycle signer contracts).
2. Signer `X` legitimately signs and pushes chunk `(slot_id=0, slot_version=5, data=D)` into contract `A` via `StackerDBPushChunkData{ contract_id: A, chunk_data }`; this propagates to other nodes.
3. An attacker (no keys needed) observes this gossip message and re-broadcasts `StackerDBPushChunkData{ contract_id: B, chunk_data: <same chunk_data> }` to peers.
4. Because `validate_received_chunk`/`try_replace_chunk` only check that `X` (recovered from the untouched signature) owns `slot_id=0` in contract `B` — which it does — and that `slot_version=5` is fresher than B's current version, the chunk from A's context is accepted and stored into B's slot 0, and then re-broadcast by that node as B's canonical chunk, per `process_stacker_db_chunks` [8](#0-7) .
