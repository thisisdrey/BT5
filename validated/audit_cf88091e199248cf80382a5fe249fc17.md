### Title
Attacker-controlled offsets in `VerifyTransferProof.execute` cause heap-buffer-over-read / crash-inducing exception handling in the TVM shielded precompile - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `VerifyTransferProof` precompiled contract (part of the shielded TRC-20/Sapling verification precompiles reachable from any TVM contract call) parses `spendOffset`, `spendAuthSigOffset`, and `receiveOffset` directly from attacker-supplied `data` and uses them, unvalidated against the input buffer length, as indices into `System.arraycopy`/`parseInt` calls. This mirrors the CVE-2018-8101 bug class: a decoder trusts length/offset fields taken from untrusted input and performs buffer reads based on them without verifying they stay within bounds, leading to an out-of-bounds heap read (here, an `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException`) that is only caught generically, but which still represents an uncontrolled crash path deep inside VM/precompile execution triggered purely by a crafted transaction.

### Finding Description
`VerifyTransferProof.execute()` validates only that `data.length` is one of four fixed sizes `{2080, 2368, 2464, 2752}` [1](#0-0) . It then reads three offset fields directly from the caller-controlled buffer:
```
int spendOffset = parseInt(data, 0);
int spendAuthSigOffset = parseInt(data, 32);
int receiveOffset = parseInt(data, 64);
``` [2](#0-1) 

These offsets are used, without any bound validation against `data.length`, to index further into `data`:
```
int spendCount = parseInt(data, spendOffset);
int spendAuthSigCount = parseInt(data, spendAuthSigOffset);
int receiveCount = parseInt(data, receiveOffset);
```
and then in a loop:
```
for (int i = 0; i < spendCount; i++) {
  System.arraycopy(data, spendOffset + 320 * i, nullifier[i], 0, 32);
  ...
}
``` [3](#0-2) 

Only `spendCount`/`spendAuthSigCount`/`receiveCount` are range-checked (`1..2`) — the offsets themselves are never checked to be within `[0, data.length)`, nor is the arithmetic `spendOffset + 320*i` checked to remain within the buffer. Because `parseInt`/`parseLong` (as seen in the analogous RLP/`PrecompiledContracts` decode helpers such as `extractSigArray`/`extractBytes` at lines 414-430) do raw `Arrays.copyOfRange`/direct indexing without bound checks, a crafted `spendOffset` (e.g., very large, or negative-after-overflow) produces an `ArrayIndexOutOfBoundsException` or `NegativeArraySizeException` when the VM attempts the out-of-bounds heap read — directly analogous to `JPXStream::inverseTransformLevel` trusting a stream-derived index/length and reading past the allocated buffer.

Although the enclosing `try { ... } catch (Throwable any) { ... }` block [4](#0-3)  prevents an unhandled crash of the whole node process, the out-of-bounds read still occurs inside the JVM heap before the exception is thrown, and this pattern is exactly the "decode using untrusted offsets from the same buffer" defect class the CVE describes. The same unguarded-offset pattern also appears in `VerifyMintProof.execute` (fixed offsets only, safer) and in `extractSigArray`, which computes `bytesOffset` from `words[offset + i + 1]` and calls `extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE, SIG_LENGTH)` without validating the resulting offset against `data.length` [5](#0-4) .

### Impact Explanation
Because the generic `catch (Throwable any)` swallows the exception and returns a failure result, this specific instance does not crash the whole node process, but it does demonstrate an unguarded, attacker-triggerable out-of-bounds heap access deep within energy-metered TVM precompile execution reachable from any contract call carrying `data` to the shielded-transfer precompile address. This is a real robustness defect (uncontrolled exception from malformed/malicious input) in a security-sensitive privacy-preserving-transaction verification path; a similar unguarded-offset defect in `extractSigArray` (used by signature verification precompiles) is more directly reachable and could throw uncaught `ArrayIndexOutOfBoundsException` depending on the caller context, which could destabilize the node's TVM execution loop for that transaction. No funds theft or permanent balance corruption is demonstrated; the impact class is limited to per-transaction DoS/exception-path robustness, matching the "Medium" severity of the original CVE (denial-of-service crash on malformed input), not chain-halting or unauthorized value transfer.

### Likelihood Explanation
Any account can broadcast a TriggerSmartContract transaction that calls the shielded-transfer precompiled contract address with a crafted `data` payload of one of the four accepted lengths but with `spendOffset`/`spendAuthSigOffset`/`receiveOffset` values chosen to point out of bounds. This requires only knowledge of the ABI-like layout (fully documented by the code itself and by TIP specifications for shielded TRC-20), no privileged keys or special permissions — matching the CVE's "unprivileged, crafted-input" trigger profile.

### Recommendation
Add explicit bounds validation immediately after parsing `spendOffset`, `spendAuthSigOffset`, and `receiveOffset`: verify each offset is within `[0, data.length)` and that `offset + requiredBytes <= data.length` before every subsequent `parseInt`/`parseLong`/`System.arraycopy` call that uses it (including inside the `spendCount`/`receiveCount` loops, accounting for `320*i`/`288*i` strides). Apply the same offset-bounds validation to `extractSigArray`/`extractBytes` in the same file. Prefer failing fast with `Pair.of(true, DataWord.ZERO().getData())` on any out-of-range offset rather than relying on the outer `catch (Throwable)` to mask the underlying out-of-bounds read.

### Proof of Concept
1. Craft a `TriggerSmartContract` transaction whose `data` targets the `VerifyTransferProof` precompile address with `data.length == 2080` (smallest accepted size).
2. Set bytes `[0:32)` (parsed as `spendOffset`) to a large value, e.g. `0x00000000000000000000000000000000000000000000000000000000001000` (4096), which exceeds `data.length`.
3. Leave other fixed fields (`bindingSig`, `signHash`, `value`, `frontier`, `leafCount`) as any values satisfying the `leafCount < TREE_WIDTH - 1` early-return check so execution reaches `parseInt(data, spendOffset)`.
4. Broadcast the transaction; `parseInt(data, spendOffset)` attempts to read 4 bytes starting at offset 4096 in a 2080-byte array, throwing `ArrayIndexOutOfBoundsException`, demonstrating the unguarded, attacker-controlled out-of-bounds heap read inside `VerifyTransferProof.execute`.
