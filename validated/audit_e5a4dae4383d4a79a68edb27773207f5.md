### Title
Missing array-bounds check on ABI header index allows `ArrayIndexOutOfBoundsException` in `ValidateMultiSign`/`BatchValidateSign` precompiles - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
This is analogous to the reported `veml6075_read_int_time_ms` bug class: an index is computed from attacker-controlled data and used to access a fixed/derived array without validating it is within bounds. In java-tron's TVM precompiled contracts `ValidateMultiSign` and `BatchValidateSign`, offsets parsed directly from the raw call-data (`words[3]`, `words[1]`, `words[2]`) are divided by `WORD_SIZE` and used as an index into the `words` array without checking that the resulting index is `< words.length`.

### Finding Description
`ValidateMultiSign.execute()` parses `rawData` into a `DataWord[] words` array and then computes an offset directly from user-controlled call data: [1](#0-0) 

Specifically, `words[words[3].intValueSafe() / WORD_SIZE]` is read to obtain `sigArraySize` when `VMConfig.allowTvmSelfdestructRestriction()` is enabled — the divided value coming from `words[3]` is fully attacker-controlled (it is part of the TVM precompile call data supplied by a contract calling this precompile address). There is no check that `words[3].intValueSafe() / WORD_SIZE` is less than `words.length` before it is used as an array index.

The same pattern exists in `BatchValidateSign.doExecute()`: [2](#0-1) 

Here `words[words[1].intValueSafe() / WORD_SIZE]` and `words[words[2].intValueSafe() / WORD_SIZE]` are similarly unguarded reads.

Helper methods `extractBytesArray`/`extractSigArray` do check `offset > words.length - 1` before use: [3](#0-2) 

but the earlier direct index reads at lines 1067 and 1166–1167 (used to compute `sigArraySize`/`addrArraySize` for the `allowTvmSelfdestructRestriction` size check) occur *before* those bounds-checked helper calls, and are not themselves bounds-checked. A crafted `words[3]` (or `words[1]`/`words[2]`) value can make the index exceed `words.length`, causing an uncaught `ArrayIndexOutOfBoundsException`.

### Impact Explanation
An `ArrayIndexOutOfBoundsException` thrown here is a `RuntimeException`, not caught by the `Throwable` wrapper in `BatchValidateSign.execute()`'s try/catch that only special-cases `InterruptedException`: [4](#0-3) 

For `ValidateMultiSign`, there is no surrounding try/catch at all outside of the inner `AccountCapsule`-scoped `try` block — the array-index computation happens before that inner try. Depending on how the VM's top-level exception handling in `VM.play()` treats this (it generically catches `RuntimeException` and marks the transaction as reverted/failed rather than crashing the node), the most concrete, provable impact is a reliable way for any contract-calling transaction to trigger a runtime exception mid-execution of a precompiled contract, rather than a clean revert produced by the precompile's own validation logic. This is a correctness/robustness defect but I could not fully verify (due to not completing the trace into `VM.play` before the tool budget ran out) whether it can be escalated beyond a normal reverted transaction to node crash or halt — I was unable to reach `Program.java`'s exception classification code before running out of iterations.

### Likelihood Explanation
Both precompiled contracts (`ValidateMultiSign` at a fixed system address, `BatchValidateSign` similarly) are reachable by any contract deployer/caller who can construct a `CALL`/`STATICCALL` to the precompile address with attacker-chosen calldata, when `VMConfig.allowTvmSelfdestructRestriction()` is active. Since the vulnerable index is derived from directly attacker-supplied `DataWord` values without any bound check prior to indexing, triggering it requires only crafting the input word at the appropriate position, making it trivially and reliably reachable from a single transaction.

### Recommendation
Add a bounds check before dereferencing `words[...]` using attacker-derived offsets in `ValidateMultiSign.execute()` (line 1067) and `BatchValidateSign.doExecute()` (lines 1166–1167), matching the existing pattern used in `extractBytesArray`/`extractSigArray` (`if (offset > words.length - 1) { return ...failure... }`), so that any offset resolving to an out-of-range index causes a controlled failure response instead of an uncaught exception.

### Proof of Concept
Construct calldata for `ValidateMultiSign` where `words[3]` (the signature-array offset) is set to a large value such that `words[3].intValueSafe() / WORD_SIZE >= words.length` (e.g., set the raw calldata to only the minimum 5 header words plus a `words[3]` value like `0xFFFFFFFF`). When `VMConfig.allowTvmSelfdestructRestriction()` is enabled and the precompile is invoked with this data, the line:
```java
int sigArraySize = words[words[3].intValueSafe() / WORD_SIZE].intValueSafe();
```
throws `ArrayIndexOutOfBoundsException` since the computed index exceeds `words.length - 1`. The equivalent PoC applies to `BatchValidateSign` by crafting `words[1]` or `words[2]` similarly.

**Note on investigation limits**: I was not able to fully trace how `ArrayIndexOutOfBoundsException` propagates through `VM.play()`/`Program.java`'s energy/exception handling before the tool-call budget was exhausted, so I cannot confirm with certainty whether this escalates beyond a reverted/failed transaction. If deeper confirmation of node-crash/DoS-level impact is needed, a Devin session with full codebase access should trace `Program.Exception` handling and `VM.play()`'s catch blocks for uncaught `RuntimeException` types originating from precompiled contract execution.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
