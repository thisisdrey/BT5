### Title
`depositAmountMin_` is enforced before the deposit fee, so users cannot bound the final collateral credited - (File: `contracts/SmartFarmingManager.sol`)

### Summary
`SmartFarmingManager.leverage()` exposes `depositAmountMin_` as the “min final deposit amount,” but checks it against the gross collateral balance before calling `DepositToken.deposit()`. `DepositToken.deposit()` subsequently deducts `depositFee`, mints the fee to `feeCollector`, and credits only the net amount to the user. A transaction can therefore satisfy the user's minimum while crediting materially less collateral than requested.

### Finding Description
`leverage()` adds the initial collateral and external swap output into `_depositAmount`, then reverts only if that gross amount is below `depositAmountMin_` [1](#0-0) . The actual deposit happens afterward through `depositToken_.deposit(_depositAmount, _msgSender)` [2](#0-1) .

`DepositToken.deposit()` measures the collateral received by Treasury, calculates `quoteDepositOut()`, mints `_fee` deposit shares to `feeCollector`, and mints only `_deposited` shares to the user [3](#0-2) . When `depositFee` is nonzero, `_deposited = amount_ - amount_.wadMul(depositFee)` [4](#0-3) .

As a result, if `_depositAmount == depositAmountMin_` and `depositFee = 10%`, the call succeeds even though the user receives only `0.9 * depositAmountMin_` deposit tokens. The final health check validates solvency, not the user's requested minimum credited deposit [5](#0-4) .

The same post-check deduction pattern exists in `flashRepay()`: `swapAmountOutMin_` is documented as the “minimum amount to repay,” but it is compared with the gross synthetic-token swap output [6](#0-5) . `DebtToken.repay()` then seizes a repay fee and burns only the lower net `_repaid` amount against the user's debt [7](#0-6) .

### Impact Explanation
Users can receive less collateralized exposure than their explicitly supplied minimum. The difference is minted to the protocol fee collector, while the user's resulting position has a smaller collateral buffer and can be closer to liquidation than the `depositAmountMin_` bound was intended to allow.

The issue is directly reachable through the public `leverage()` function using a registered deposit token and synthetic token. AMM slippage or a same-transaction trade can make the external swap return exactly the gross amount needed to pass the check; the subsequent deposit fee still reduces the user's actual credited amount below the specified minimum.

### Likelihood Explanation
Likelihood depends on `depositFee` being nonzero and on the external swap producing an output near the user's gross minimum. None of the registered-token checks, reentrancy guards, shutdown checks, or final health checks enforce the net deposited amount.

The likelihood is lower when the deposit fee is zero, because gross and net deposit amounts are identical. However, the parameter is documented as a final-deposit bound and the code does not preserve that invariant whenever fees are enabled.

### Recommendation
Apply `depositAmountMin_` to the user's net deposit, not the gross collateral held by `SmartFarmingManager`.

For example:

```solidity
(uint256 _expectedDeposited, ) = depositToken_.quoteDepositOut(_depositAmount);
if (_expectedDeposited < depositAmountMin_) revert LeverageSlippageTooHigh();

(_deposited, ) = depositToken_.deposit(_depositAmount, _msgSender);
```

Alternatively, perform the check after depositing:

```solidity
(_deposited, ) = depositToken_.deposit(_depositAmount, _msgSender);
if (_deposited < depositAmountMin_) revert LeverageSlippageTooHigh();
```

For `flashRepay()`, compare the user's minimum against `quoteRepayOut(_swapAmountOut)._amountToRepay` or rename the parameter/documentation to make explicit that it bounds only the gross swap output.

### Proof of Concept
A Foundry/Hardhat test can reproduce the mismatch by configuring a nonzero deposit fee and forcing the external swapper to return exactly enough collateral for the gross check:

```solidity
// Existing protocol fixture/deployed fork provides:
// user, smartFarmingManager, feeProvider, depositToken,
// syntheticToken, collateral, and a controllable/mock swapper.

uint256 depositFee = 0.10e18;
vm.prank(governor);
feeProvider.updateDepositFee(depositFee);

uint256 grossDeposit = 100 ether;
uint256 userMinimum = 100 ether;

// Arrange the initial collateral transfer and external swap so that:
// amountIn_ + swappedCollateral == grossDeposit.
vm.prank(user);
smartFarmingManager.leverage(
    IERC20(address(collateral)),
    depositToken,
    syntheticToken,
    amountIn,
    leverage,
    userMinimum
);

(uint256 expectedNet, uint256 expectedFee) =
    depositToken.quoteDepositOut(grossDeposit);

// Transaction succeeds despite the user's final deposit being below
// the documented "min final deposit amount".
assertEq(depositToken.balanceOf(user), expectedNet);
assertEq(depositToken.balanceOf(feeCollector), expectedFee);
assertLt(depositToken.balanceOf(user), userMinimum);
```

With `depositFee = 10%`, `grossDeposit == userMinimum == 100 ether`, the user receives `90 ether` deposit tokens while `10 ether` shares are minted to the fee collector, yet the slippage check does not revert.
