### Title
Unbounded per-account delegation index enables O(n) / O(n log n) CPU-exhaustion DoS on every freeze/unfreeze and on the public `GetDelegatedResourceAccountIndex` query - (File: chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java)

### Summary
`DelegatedResourceAccountIndexStore` maintains, per account, an unbounded list of every address it has ever delegated resources to/from. Unlike the capped lists elsewhere in the actuator layer (e.g. `MAX_VOTE_NUMBER`, `UNFREEZE_MAX_TIMES = 32`, small `FreezeV2`/`Frozen` lists), this index has no size limit and is fully rebuilt/scanned on every delegate/undelegate/freeze/unfreeze call and on every read of the account's delegation index — directly analogous to Xen's unbounded grant-table walk (CVE-2021-28698), where an account can create arbitrarily many "entries" for itself and every subsequent operation must walk them all.

### Finding Description
Legacy resource delegation (`FreezeBalanceContract` with a `receiverAddress`, still supported when `dynamicStore.supportDR()` is true and `!supportAllowDelegateOptimization()`) stores, for an owner, the full list of receiver addresses it has delegated to via `DelegatedResourceAccountIndexCapsule.addToAccount` / `addFromAccount`: [1](#0-0) 

Each call rebuilds the whole protobuf list via `toBuilder().addToAccounts(...).build()` — an O(n) copy — and there is no maximum on how many distinct receiver addresses one owner can accumulate (unlike `MAX_VOTE_NUMBER` in `VoteWitnessActuator` or `UNFREEZE_MAX_TIMES` in `UnfreezeBalanceV2Actuator`). A single unprivileged account can call `FreezeBalanceActuator` repeatedly with distinct (even self-controlled) receiver addresses to grow this list arbitrarily: [2](#0-1) 

When later unfreezing any one entry, `UnfreezeBalanceActuator` copies the *entire* `toAccountsList`/`fromAccountsList` into a new `ArrayList`, does a linear `.remove()`, and writes the whole list back — cost proportional to the size the attacker built up, for every single unfreeze transaction: [3](#0-2) 

The newer, V2 delegation model stores individual keyed entries (`delegate`/`unDelegate`/`delegateV2`) instead of a growing list, but the read/aggregation path used by both `getIndex` (legacy) and `getV2Index` (V2) still performs an unbounded `prefixQuery` over all delegation records for the address, loads them into an `ArrayList`, and **sorts** the whole set by timestamp — O(n log n) — on every call: [4](#0-3) 

This aggregation is also invoked from `DelegatedResourceAccountIndexStore.convert`, which iterates the whole legacy list to migrate it, itself triggered from actuator execution paths (`FreezeBalanceActuator`/`UnfreezeBalanceActuator`) when `supportAllowDelegateOptimization()` flips: [5](#0-4) 

`getIndex`/`getV2Index` are also the backing implementation for the public `GetDelegatedResourceAccountIndex`/`GetDelegatedResourceAccountIndexV2` RPC/HTTP query paths exposed through `Wallet`, so any anonymous API client can trigger the full prefix-scan-and-sort simply by querying an account that has accumulated many delegation records — no transaction fee or signature required for the query itself, only for the initial population of many entries.

### Impact Explanation
An attacker who controls one funded account can:
1. Issue many cheap `FreezeBalanceContract`/`DelegateResource` transactions delegating small amounts to a large number of distinct addresses (self-controlled addresses are sufficient — "no need for multiple domains", matching the original Xen advisory's own note).
2. Each subsequent freeze/unfreeze/undelegate transaction from that account, and any `GetDelegatedResourceAccountIndex(V2)` query against that account, becomes progressively more expensive (unbounded list copy/scan/sort), consuming disproportionate node CPU relative to the bandwidth/energy paid for the triggering transaction, and disproportionate CPU for the free API query path.
3. Because the cost is paid by every node processing the block (during actuator execution) and by any node serving the read API, this is a network-wide CPU-exhaustion vector, potentially degrading block processing or the query API service — matching the "no impact" exclusion boundary only if bounded; here it is unbounded and thus qualifies as node/service degradation.

### Likelihood Explanation
Reachable by a single unprivileged account with ordinary signed transactions (`FreezeBalanceContract`) and no special permissions; the query surface (`GetDelegatedResourceAccountIndex`) requires no signature at all. The bandwidth/energy cost of issuing the many small freeze transactions is the attacker's only real cost, and it is linear while the resulting future cost imposed on the network is worse than linear (O(n) per follow-up operation, O(n log n) per API query), giving an asymmetric cost profile similar to the amplification pattern described in the Xen advisory.

### Recommendation
- Cap the number of distinct delegation targets per owner (analogous to `MAX_VOTE_NUMBER`/`UNFREEZE_MAX_TIMES`), rejecting further `FreezeBalanceContract`/`DelegateResourceContract` calls to new receivers once a limit is reached.
- Avoid full-list copy-and-rebuild on every add/remove in `DelegatedResourceAccountIndexCapsule`; use an indexed store (as V2 delegation partially does) rather than a single growing repeated field.
- In `DelegatedResourceAccountIndexStore.getWithPrefix`, avoid sorting the entire prefix-query result on every read if the entries are already naturally ordered by key, or paginate/limit the returned index size for the query APIs.
- Add a CPU-time / entry-count guard in the actuator validate steps (similar to `MUtil.checkCPUTimeForInvalidDelegatedV2Balance`) that rejects operations once a given account's delegation index exceeds a safe size.

### Proof of Concept
1. Attacker account A calls `FreezeBalanceContract` with `receiverAddress` set to N distinct addresses it controls (N in the tens of thousands), each with the minimum freezable amount, while `dynamicStore.supportDR()` is enabled and delegate optimization is off — this populates `DelegatedResourceAccountIndexCapsule` for A with N entries in `toAccountsList` via `FreezeBalanceActuator`.
2. Any subsequent `UnfreezeBalanceContract` from A against one of those receivers forces `UnfreezeBalanceActuator` to copy and linearly scan the full N-entry list.
3. Any client calls `GetDelegatedResourceAccountIndex`/`GetDelegatedResourceAccountIndexV2` for address A; `DelegatedResourceAccountIndexStore.getWithPrefix` performs a `prefixQuery` returning up to N records and sorts them by timestamp on every single call, with no pagination or cap, consuming CPU proportional to N for a free, unauthenticated query.

  public void convert(byte[] address) {
    DelegatedResourceAccountIndexCapsule indexCapsule = this.get(address);
    if (indexCapsule == null) {
      // convert complete or have no delegate
      return;
    }
    // convert old data
    List<ByteString> toList = indexCapsule.getToAccountsList();
    for (int i = 0; i < toList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(address, toList.get(i).toByteArray(), i + 1L);
    }

    List<ByteString> fromList = indexCapsule.getFromAccountsList();
    for (int i = 0; i < fromList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(fromList.get(i).toByteArray(), address, i + 1L);
    }
    this.delete(address);
  }

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }
