### Title
Unsynchronized lazy-initialization of the shared `ActuatorCreator` singleton can race during concurrent transaction processing - (File: `actuator/src/main/java/org/tron/core/actuator/ActuatorCreator.java`)

### Summary
`ActuatorCreator` holds a single static instance that wraps the `ChainBaseManager`/`ForkController` used to build the actuator for every non-VM transaction contract. The lazy accessor `getINSTANCE()` checks-and-creates this shared instance without any lock or `volatile` field, mirroring the exact bug class described in the report: a shared, statically-scoped resource is initialized "optimistically" with no synchronization guarding first-use races.

### Finding Description
```java
public static ActuatorCreator getINSTANCE() {
    if (ActuatorCreatorInner.instance == null) {
      ActuatorCreatorInner.instance = new ActuatorCreator(StoreFactory.getInstance());
    }
    return ActuatorCreatorInner.instance;
}

public static void init() {
    ActuatorCreatorInner.instance = new ActuatorCreator(StoreFactory.getInstance());
}

private static class ActuatorCreatorInner {
    private static ActuatorCreator instance;
}
``` [1](#0-0) 

The `instance` field is neither `volatile` nor guarded by a lock. `getINSTANCE()` is invoked on every transaction whose contract is not a smart-contract call, from the hot execution path in `RuntimeImpl.execute`:
```java
default:
    actuatorList = ActuatorCreator.getINSTANCE().createActuator(context.getTrxCap());
``` [2](#0-1) 

Under the Java Memory Model, a plain (non-volatile) field write is not guaranteed to be visible, nor is the constructor guaranteed to be fully published, to other threads absent a proper happens-before edge. If two threads call `getINSTANCE()` concurrently before `ActuatorCreatorInner.instance` has been set by `init()` (or if the class is re-initialized/reset in a multi-threaded validation pool), both can observe `instance == null` simultaneously and both construct a new `ActuatorCreator`, or one thread can observe a partially-constructed object (a reference published before the constructor — which itself calls `forkController.init(...)` — has finished running). This is the same class of "hope no two threads race through the unguarded init" bug as the reported seeder DNS `listenSocket` issue, just applied to `ActuatorCreator` instead of a raw file descriptor.

### Impact Explanation
If two transaction-processing threads race here, they can end up operating on two different `ActuatorCreator`/`ForkController` instances, or one thread can dereference a not-yet-fully-initialized `ForkController`/`ChainBaseManager` reference, leading to inconsistent fork-check state, `NullPointerException`, or use of a stale/incomplete `chainBaseManager`. This is reachable purely by an unprivileged party whose transactions get validated/executed concurrently, and can manifest as node crashes or inconsistent actuator validate/execute behavior under load (which is what the analog rules classify as an in-scope, reachable analog).

### Likelihood Explanation
Likelihood is limited because `ActuatorCreator.init()` is normally called once synchronously during `Manager` startup (before RPC/transaction processing threads are active), so in the standard startup sequence the race window is small. However, there is no code-level guarantee preventing concurrent first-touch (e.g., in test harnesses, alternate bootstrap orderings, or any future code path that defers/skips the explicit `init()` call and instead relies purely on `getINSTANCE()`), and the field is not `volatile`, so cross-thread visibility of the fully-constructed object is not formally guaranteed by the JMM. This makes it a genuine but narrow-window robustness/UB issue rather than a trivially triggerable exploit.

### Recommendation
Make `ActuatorCreatorInner.instance` `volatile` and add double-checked locking (synchronizing on `ActuatorCreatorInner.class`) around the create-if-null branch in `getINSTANCE()`, consistent with how `Param.getInstance()` in `consensus/src/main/java/org/tron/consensus/base/Param.java` already does it correctly:
```java
private static volatile Param param = new Param();
public static Param getInstance() {
  if (param == null) {
    synchronized (Param.class) {
      if (param == null) {
        param = new Param();
      }
    }
  }
  return param;
}
``` [3](#0-2) 

### Proof of Concept
A concrete PoC would require instrumenting concurrent calls to `ActuatorCreator.getINSTANCE()` from multiple threads before `init()` has run (e.g., a stress test spawning threads that call `RuntimeImpl.execute` for non-VM contracts concurrently at node startup), and observing either duplicate `ActuatorCreator` instances or a `NullPointerException`/inconsistent `ForkController` state. I was not able to fully verify from static analysis alone whether any current call path invokes `getINSTANCE()` concurrently before `Manager` calls `init()`, since I could not confirm the full ordering/threading guarantees in `Manager.java` within the available tool budget — this uncertainty should be resolved by tracing `Manager`'s startup sequence and the thread pool(s) used for transaction validation.
