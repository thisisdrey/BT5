### Title
Unvalidated attacker-controlled length in TVM precompile ABI-array decoding causes crash - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`PrecompiledContracts.extractBytes32Array` (and, to a lesser extent, `extractBytesArray`) decode ABI-encoded dynamic arrays from `DataWord[]` calldata words that come directly from a smart-contract call's input. The array length is taken verbatim from attacker-controlled calldata and used to size a Java array and drive a loop over the `words` array without checking that `offset + len` stays within the bounds of the actual decoded `words` array.

### Finding Description
`extractBytes32Array` reads the length from a caller-controlled word and immediately allocates `new byte[len][]`, then walks `words[offset + i + 1]` for `i` up to `len - 1` with no upper bound check against `words.length`: [1](#0-0) 

This mirrors the CVE-2017-9847 bug class in libtorrent's `bdecode`: a length/size field parsed straight from untrusted input is trusted to compute an array size and a read cursor, without validating it against the amount of data actually available, leading to an out-of-bounds read/crash. Here, if `len` is large (attacker sets the corresponding calldata word to a large value), `new byte[len][]` can trigger an `OutOfMemoryError`, and even for moderate `len`, `words[offset + i + 1]` will run past the end of the real `words` array and throw `ArrayIndexOutOfBoundsException`, since there is no check equivalent to the `offset > words.length - 1` guard present in the sibling method `extractBytesArray`: [2](#0-1) 

Even `extractBytesArray`'s guard only checks `offset` against `words.length`, not whether `len` (also attacker-controlled) keeps subsequent indexing (`words[offset + i + 1]`, `words[offset + bytesOffset + 1]`) inside bounds, so a crafted `len`/`bytesOffset` combination can still index out of range.

### Impact Explanation
These helpers are used to decode multi-value ABI arguments (e.g., signature arrays / hash arrays) inside TVM precompiled contracts invoked from ordinary smart-contract calls (`TriggerSmartContract`). An attacker who can call the affected precompiled contract can supply a crafted calldata length word to force either an `OutOfMemoryError` (an `Error`, not caught by ordinary `catch (Exception e)` handlers in the VM call path) or an unhandled `ArrayIndexOutOfBoundsException` during precompile execution. If not caught by an outer catch-all in the VM interpreter, this can crash or halt the node processing the transaction/block, which every full node must execute identically — a reachable denial-of-service analogous to the crafted-file crash described in CVE-2017-9847.

### Likelihood Explanation
Likelihood is moderate: reaching these helpers requires calling a specific precompiled-contract address with a crafted DataWord array via `TriggerSmartContract`, something any account can do. However, I was not able to fully confirm within the available search budget (a) the exact precompile(s) (`BatchValidateSign`/`ValidateMultiSign`) that invoke `extractBytes32Array`/`extractBytesArray` and the exact calldata offsets they pass, and (b) whether the TVM's outer `Program`/interpreter dispatch wraps precompile execution in a broad `catch (Throwable)` that would downgrade this to a mere reverted transaction rather than a node crash. Given the recent hardening seen elsewhere in the same PR history (e.g., `ContractEventParser.subBytes` now explicitly rejects oversized/negative ABI lengths, and `ValidateMultiSignContractTest` documents a "TIP-854" guard for malformed calldata), it is plausible similar protection has already been added around these call sites, which I could not verify due to tool budget exhaustion.

### Recommendation
Add explicit bounds validation in both `extractBytes32Array` and `extractBytesArray` before allocating or indexing: reject (return empty / throw a caught `Program` exception) whenever `len < 0` or `offset + len + 1 > words.length`, mirroring the bounds checks already used in `RLP.verifyLength` elsewhere in the codebase.

### Proof of Concept
Not able to construct a concrete end-to-end transaction PoC because the exact precompile entry points calling `extractBytes32Array`/`extractBytesArray` with attacker-supplied offsets were not located within the available tool budget; this would require confirming the `BatchValidateSign`/`ValidateMultiSign` `execute()` methods and verifying whether the TVM call dispatcher catches `Throwable`/`Error` around precompile execution.

    for (int i = 0; i < len; i++) {

      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,

    }

  }
