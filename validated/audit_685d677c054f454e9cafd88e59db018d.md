### Title
Missing minimum borrow/collateral-size enforcement allows creation of dust positions that are unprofitable to liquidate, leading to accumulated bad debt - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
The `borrow` and `collateral-add`/`collateral-remove` entry points in `v0-4-market.clar` only assert that the amount is non-zero and that the resulting position remains "healthy" per the LTV thresholds; there is no floor on the absolute USD size of a position. A user can open, and a liquidator must later close, positions whose total value is smaller than the gas/incentive cost of liquidating them, which is the exact bug class described in the WiseLending report (missing minimum borrow amount check, bypassable minimum deposit check).

### Finding Description
`borrow` in `mainnet/contracts/market/v0-4-market.clar` only checks `(> amount u0)`, that borrowing isn't disabled, and that the position stays healthy under `is-healthy-with-mask` — no minimum USD-value floor is enforced: [1](#0-0) 

Similarly, `collateral-add` and `collateral-remove` only assert `(> amount u0)` and health/capacity invariants, with no minimum position-size floor: [2](#0-1) 

Because there is no minimum deposit/borrow amount and no minimum-withdrawal restriction, a user can:
1. Deposit collateral and borrow a dust amount of debt (e.g., a few satoshis of value), satisfying the health checks trivially since both sides of the LTV ratio scale together.
2. Later, price movement or interest accrual can push this dust position underwater, making it liquidatable via `liquidate` (`mainnet/contracts/market/v0-4-market.clar:1382`).
3. Because the collateral/debt values are dust, the liquidation reward (`liq-penalty` bonus on `coll-final`) is smaller than the liquidator's transaction cost, so no rational liquidator will call `liquidate` on it.
4. The position accumulates as effectively permanent bad debt for the protocol, since `socialize-debt-asset` only runs when someone actually calls `liquidate` and collateral is exhausted: [3](#0-2) 

This is confirmed by the project's own test suite, which documents the exact scenario (minimal collateral, dust debt) succeeding without any minimum enforced, contrary to the test's own name suggesting rejection should occur: [4](#0-3) 

Unlike WiseLending's `WiseSecurity::_checkMinDepositValue`, Zest's `v0-4-market.clar` does not even attempt a minimum-deposit check that could later be bypassed by partial withdrawal — the floor is simply absent, making the analog strictly easier to exploit here (no bypass step is even required).

### Impact Explanation
This falls under "protocol insolvency": accumulation of many unliquidatable dust positions results in permanent bad debt that is never cleaned up because no economically rational liquidator will trigger `liquidate` and thus `socialize-debt-asset` on them. Over time (or via intentional spam by an attacker creating many such positions), this degrades protocol solvency and dilutes lender returns, matching the Critical impact class of protocol insolvency.

### Likelihood Explanation
Likelihood is high: any ordinary principal can call `collateral-add` then `borrow` with arbitrarily small amounts, as both only require `(> amount u0)` and a trivially satisfiable health ratio at small scale. No privileged action, DAO compromise, or flashloan trick is needed — an unprivileged user's normal call path is sufficient.

### Recommendation
Enforce a protocol-configured minimum USD-notional size (e.g., in `get-notional-evaluation` result) for both collateral and debt at `borrow`, `collateral-add`, and after `collateral-remove`, rejecting operations that would leave a non-zero position below the floor. Alternatively/also, enforce that any partial `collateral-remove`/`repay` that leaves a residual non-zero debt or collateral balance keeps it above the minimum notional threshold, closing the same bypass path noted in the original report.

### Proof of Concept
1. Attacker calls `collateral-add` with a minimal collateral amount (e.g., `1n` satoshi of sBTC), which succeeds since only `(> amount u0)` is checked (`mainnet/contracts/market/v0-4-market.clar:1116`).
2. Attacker calls `borrow` for a proportionally dust amount of USDC, which succeeds since only `(> amount u0)` and the health ratio are checked (`mainnet/contracts/market/v0-4-market.clar:1269-1287`) — confirmed reproducible per the project's own `edge-cases.test.ts` "should reject borrow that results in dust debt" test, which in fact shows the dust borrow succeeding.
3. Repeat at scale (many accounts/positions) to accumulate numerous dust positions across the protocol.
4. When any of these positions becomes underwater (price move / interest accrual), no liquidator calls `liquidate` because `liq-penalty`-scaled proceeds don't cover transaction costs; the debt remains outstanding indefinitely, representing unrecoverable bad debt on the protocol's books.

(define-private (socialize-debt-asset
                (debt-entry { aid: uint, scaled: uint })
                (acc { borrower: principal, success: bool }))
  ;; Early return if previous socialization failed
  (if (not (get success acc))
      acc
      (let ((borrower (get borrower acc))
            (failed-status { borrower: borrower, success: false })
            (asset-id (get aid debt-entry))
            (scaled-debt (get scaled debt-entry)))

            ;; Socialize in vault - pass scaled directly to avoid rounding
            (unwrap! (vault-socialize-debt asset-id scaled-debt) failed-status)
            ;; Refresh cache with new indexes post-write-down (lindex decreased)
            (map-set index-cache
                     { timestamp: stacks-block-time, aid: asset-id }
                     (unwrap! (vault-accrue asset-id) failed-status))

                                      debt-remove-scaled
                                      borrower
                                      scaled-debt
                                      asset-id) failed-status)
          acc)
        ))
