### Title
Disk cache no longer verifies content digests on cache hit, allowing a poisoned local disk-cache entry to be silently trusted - (File: CHANGELOG.md, Bazel disk-cache client)

### Summary
The `RubiconMarket` report describes a class of bug where a *missing validation step* (checking `feeTo != address(0)` before trusting/using a value) breaks an invariant the rest of the system silently relies on. The Bazel analog in this index is a documented, intentional-but-dangerous behavior change: as of a recent pre-release, **Bazel no longer verifies the digests of disk-cache entries on a cache hit**, even though the `--remote_verify_downloads` flag's description implies it should. This is recorded verbatim in the changelog: [1](#0-0) 

### Finding Description
Bazel's disk cache (`--disk_cache=<path>`) stores action outputs and CAS blobs keyed by their content digest, and is explicitly documented as a "remote cache" implemented on the local filesystem, sharable across workspaces/checkouts/branches: [2](#0-1) 

Historically the `--remote_verify_downloads` flag was supposed to make Bazel re-hash cache content and confirm it matches the requested digest before trusting it — the same integrity-gate role that `require(_offer.buy_gem.transferFrom(...))`/a `feeTo != 0` check plays in the Solidity report: a check that must run before a value from an untrusted source is consumed. The changelog documents that this verification was silently dropped for disk-cache hits: [3](#0-2) 

Because the disk cache directory is attacker-reachable content in several realistic setups (a shared CI cache directory, a directory synced from another branch/fork's build, or a cache populated by an untrusted CI job sharing the same `--disk_cache` path as documented for "sharing build artifacts when switching branches"), an attacker who can write or replace an entry under the digest-addressed disk-cache path can have Bazel accept arbitrary bytes for that digest on the next build that hits the cache — without any hash re-verification catching the substitution. This directly parallels the missing-validation root cause in the C4 report: a security-relevant check (`feeTo` non-zero / digest match) that the surrounding code implicitly assumes always holds, but which is not actually enforced at the point of use.

### Impact Explanation
If the digest check is skipped on cache hit, a disk-cache entry whose *stored bytes no longer match its digest key* (e.g., because it was overwritten, corrupted, or maliciously substituted by another user/process/CI job with write access to the shared cache directory) will be served to the build as if it were verified content, addressed as a legitimate action output or CAS blob. This is a content-integrity bypass on the disk cache — the same class of "unenforced trust invariant" as the report, though the practical blast radius depends on how broadly the disk-cache directory is shared (e.g., team-shared `.bazelrc`-configured `--disk_cache=~/path` per the docs).

### Likelihood Explanation
This is not a hypothetical bypass of an existing check — it is documented as an actual behavior change on a current pre-release baseline of this Bazel checkout, meaning it reproducibly occurs under default flag combinations once `--disk_cache` and `--remote_verify_downloads` are combined, per the changelog wording ("no longer verifies... upon a cache hit"). Any environment sharing a disk-cache directory across less-trusted branches/CI jobs — the exact scenario the docs recommend disk cache for — is exposed. [4](#0-3) 

### Recommendation
Restore digest verification on disk-cache hits when `--remote_verify_downloads` is enabled (or introduce an explicit, separately documented flag/default for disk-cache verification), so that content read back from a shared/untrusted disk-cache path is re-hashed and compared to its addressed digest before being trusted as build input, closing the same class of gap as adding the `feeTo != address(0)` check in the original report.

Important changes:

  - Bazel no longer verifies the digests of disk cache entries upon a
    cache hit. This honors the description but not the previous
    behavior of the `--remote_verify_downloads` flag, which in fact
    controlled digest verification for both remote and disk caches.
  - Bazel now has experimental support for --rewind_lost_inputs,
    which can rerun actions within a single build to recover from
    (remote or disk) cache evictions.

## Disk cache {#disk-cache}

Bazel can use a directory on the file system as a remote cache. This is
useful for sharing build artifacts when switching branches and/or working
on multiple workspaces of the same project, such as multiple checkouts.
Enable the disk cache as follows:

```posix-terminal
build --disk_cache=<var>path/to/build/cache</var>
```

You can pass a user-specific path to the `--disk_cache` flag using the `~` alias
(Bazel will substitute the current user's home directory). This comes in handy
when enabling the disk cache for all developers of a project via the project's
checked in `.bazelrc` file.
```
