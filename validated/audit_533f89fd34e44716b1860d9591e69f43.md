### Title
Custom hook environment construction fails to validate `GitObjectDirectory`/`GitAlternateObjectDirectories`, allowing path-traversal object directory injection - (File: internal/gitaly/hook/custom.go)

### Summary
`customHooksEnv` in `internal/gitaly/hook/custom.go` builds the `GIT_OBJECT_DIRECTORY` and `GIT_ALTERNATE_OBJECT_DIRECTORIES` environment variables for custom hooks directly from the `gitalypb.Repository` fields carried in the `HooksPayload`, joining them onto the repository path with `filepath.Join` and no boundary check. This mirrors the Vyper `raw_call` bug class: an attacker/caller-supplied parameter (`value` in the Vyper case, object-directory paths here) is accepted and used in a code path where it must be constrained, but the constraint check that exists elsewhere in the codebase for the very same field is missing here.

### Finding Description
Gitaly already recognizes that `GitObjectDirectory`/`GitAlternateObjectDirectories` are attacker-reachable and dangerous if unconstrained: `internal/git/localrepo/paths.go` `ObjectDirectoryPath()` explicitly calls `storage.ValidateRelativePath` to ensure the resulting path stays inside the storage root, and has dedicated tests for directory-traversal payloads (`internal/git/localrepo/paths_test.go`, e.g. `"with directory traversal"`, `"with sneaky directory traversal"`, `"with traversal outside repository"`). [1](#0-0) 

However, `customHooksEnv`, which is used to construct the environment for **custom hooks** (server-side scripts triggered on every push), performs no such validation: [2](#0-1) 

It takes `objectDirectory`/`alternateObjectDirectories` either from the raw environment (`env.ExtractValue(envs, "GIT_OBJECT_DIRECTORY")`) or from `payload.Repo.GetGitObjectDirectory()` / `payload.Repo.GetGitAlternateObjectDirectories()`, then does a plain `filepath.Join(repoPath, alternateObjectDirectory)` and injects the result unchecked into the hook’s environment.

`payload.Repo` originates from the `HooksPayload`, which is populated from a `storage.Repository` (`internal/git/gitcmd/hooks_payload.go`, `NewHooksPayload`) — this interface directly exposes the `GitObjectDirectory`/`GitAlternateObjectDirectories` fields of the `gitalypb.Repository` protobuf message, which is part of virtually every RPC request: [3](#0-2) [4](#0-3) 

For most call sites the object directory does come from a safely-computed quarantine directory (`internal/git/quarantine/quarantine.go` `Apply`, which uses `filepath.Rel` and is therefore constrained). But `updateref.UpdaterWithHooks.UpdateReference` (`internal/gitaly/hook/updateref/update_with_hooks.go`) forwards `repoProto` — the repository as it arrived on the RPC request, including whatever `GitObjectDirectory`/`GitAlternateObjectDirectories` values the caller set — straight into `gitcmd.NewHooksPayload(...)` without going through `quarantine.Apply` in the non-quarantined case, and `validatePreReceiveHookRequest`/`locator.ValidateRepository` (used by `PreReceiveHook`) only validates the relative repository path, not these auxiliary fields. [5](#0-4) [6](#0-5) 

Because these fields are unauthenticated, client-settable strings on the `Repository` message and are not restricted to a repository-relative safe subtree by `customHooksEnv`, a caller-supplied value such as `../../../../etc` (or an absolute-looking traversal sequence) is joined onto `repoPath` and exported as `GIT_OBJECT_DIRECTORY`/`GIT_ALTERNATE_OBJECT_DIRECTORIES` to every custom hook process that Gitaly spawns for that push.

### Impact Explanation
Custom hooks run arbitrary git operations (e.g. `git cat-file`, `git rev-parse`) using the object directory search path handed to them via these environment variables (this is precisely the documented purpose of quarantine object-directory propagation, see `doc/object_quarantine.md`). If the search path can be steered outside the repository's own object store by an unvalidated field, a custom hook can be tricked into reading (and, depending on the hook's own logic and subsequent git operations, potentially merging/exposing) objects from a directory outside the intended repository — a cross-repository/object-store escape analogous to the "cross-repository object access" class explicitly called out as in-scope. This directly parallels the reported bug class: a caller-supplied parameter (`value` for `raw_call`, object-directory path here) is used unconditionally in a context where the codebase's own design (see the validated counterpart in `paths.go`) shows it must be constrained, and the absence of that constraint silently produces unintended, security-relevant behavior (accounting corruption there; directory/object-store escape here).

### Likelihood Explanation
Reachability requires the specific code path where `GitObjectDirectory`/`GitAlternateObjectDirectories` are populated on the `HooksPayload` from a request-supplied `Repository` message without first going through `quarantine.Apply`'s `filepath.Rel`-derived normalization, and where `customHooksEnv` is invoked for a repo that has configured custom hooks. This is a narrower, harder-to-trigger condition than the other well-guarded call sites (e.g. `ObjectDirectoryPath`), and I could not fully trace, within the remaining investigation budget, whether every current caller of `NewHooksPayload` always supplies a quarantine-derived repository or whether an ordinary user's RPC (e.g. via `UserUpdateSubmodule`/`UpdateReference`-style flows without a quarantine dir) can inject an attacker-controlled `GitObjectDirectory` end-to-end into `customHooksEnv`. This uncertainty should be resolved by tracing all callers of `configureHooks`/`NewHooksPayload` to confirm whether an unquarantined, client-controlled `Repository.GitObjectDirectory` value can reach `customHooksEnv`.

### Recommendation
In `internal/gitaly/hook/custom.go`, before joining `objectDirectory`/`alternateObjectDirectories` onto `repoPath`, validate each path the same way `internal/git/localrepo/paths.go`'s `ObjectDirectoryPath` does — via `storage.ValidateRelativePath` (or an equivalent quarantine-prefix check) — and reject/strip any path that would resolve outside the repository or its known quarantine directories, rather than accepting arbitrary values pulled from `payload.Repo` or the raw environment.

### Proof of Concept
Not independently confirmed end-to-end due to remaining uncertainty about which RPC paths populate `HooksPayload.Repo` with an unquarantined, request-supplied `Repository` message (see Likelihood Explanation). Conceptually: an ordinary push/RPC flow that reaches `updateref.UpdaterWithHooks.UpdateReference` with `quarantineDir == nil` and a `Repository` request message whose `git_alternate_object_directories` field contains a traversal sequence (e.g. `../../../..`) would have that value carried unmodified through `gitcmd.NewHooksPayload` → `customHooksEnv` → `GIT_ALTERNATE_OBJECT_DIRECTORIES`, and any configured custom hook for that repository would then search for git objects under the escaped directory.
