Permissionless `InitLiquidationRecord` Lets Any User Permanently Block a Victim's Account From Being Closed - ([File: programs/marginfi/src/instructions/marginfi_account/init_liquid_record.rs])

### Summary
`marginfi_account_init_liq_record` (handler `initialize_liquidation_record`) is permissionless and unconditional: any signer can create a `LiquidationRecord` PDA for *any* `MarginfiAccount`, healthy or not, and this write sets `marginfi_account.liquidation_record` to a non-default value. Both of the protocol's account-closing paths — the authority-driven `marginfi_account_close` and the permissionless `admin_close_account` — explicitly refuse to close an account unless `liquidation_record == Pubkey::default()`. Because `close_liquidation_record` (the only way to clear this field) requires 60 days of inactivity on the record, an attacker can grief any account by front-running its intended closure, permanently (for 60 days, indefinitely if repeated) locking it and its rent.

### Finding Description
`InitLiquidationRecord` takes the `marginfi_account` as a plain, non-owner-checked account: [1](#0-0) 

The handler unconditionally links the record back to the account with no authority check, no health check, and no restriction on who may call it: [2](#0-1) 

This mirrors the `poke()` root cause described in the report: a state-mutating instruction reachable by any unprivileged caller against a tokenId/account they do not own, with no requirement that the action reflect the owner's intent or a legitimate economic condition (unlike `StartLiquidation`, which is also permissionless but only succeeds against an *unhealthy* account, per `check_pre_liquidation_condition_and_get_account_health`).

Both account-close paths gate on this same field being default:
- `admin_close_account` (permissionless, 60-day-inactive path) requires `marginfi_account.liquidation_record == Pubkey::default()` [3](#0-2) 
- `marginfi_account_close` (the normal authority-driven close instruction) has the equivalent check in `close.rs`, confirmed via the `liquidation_record == Pubkey::default()` guard in that file.

Once `liquidation_record` is set to non-default via `InitLiquidationRecord`, clearing it requires `close_liquidation_record`, which is only permitted once the record has been inactive for **60 days**, or was never used for an actual liquidation: [4](#0-3) 

An attacker therefore does not need the target account to be unhealthy, liquidatable, or owned by them at all — they simply call `marginfi_account_init_liq_record` against the victim's account pubkey to write a persistent, blocking value into a field the victim does not control.

### Impact Explanation
This is a permanent-lock/DoS on the account-closure and rent-reclaim path: a victim who wants to close an empty, healthy `MarginfiAccount` and recover their rent-exempt SOL is blocked for up to 60 days per attack, and an attacker can re-trigger this indefinitely by re-initializing the record again once it becomes eligible for close (each re-init resets the 60-day inactivity clock). This does not (per the code reviewed) block deposit/withdraw/borrow/repay, so it is narrower than the original `poke()` bug (which blocked mint/burn/transfer entirely), but it still constitutes an unauthorized state change and a legitimate, unprivileged-user-reachable permanent-freeze primitive against the account-closure/rent-reclaim flow, satisfying the "permanent lock/freeze" impact category.

### Likelihood Explanation
High: `marginfi_account_init_liq_record` has no signer-authority constraint on the `marginfi_account`, no health precondition, and only costs the caller a small amount of PDA rent. Any user can trivially target any known `MarginfiAccount` pubkey (all such accounts are publicly discoverable on-chain).

### Recommendation
Either (a) restrict `InitLiquidationRecord` so it can only be created by, or with consent of, the account's `authority`, or in immediate conjunction with a genuine `StartLiquidation`/`StartDeleverage` call (analogous to how those instructions require an unhealthy account), or (b) decouple the account-close eligibility checks in `close.rs` / `admin_close_account` from the mere *existence* of a `liquidation_record`, and instead gate on whether the record reflects an actual, currently-active liquidation (e.g., check `liquidation_receiver != Pubkey::default()` / an active flag) rather than presence of the PDA link itself.

### Proof of Concept
1. Attacker observes a victim's empty, healthy `MarginfiAccount` pubkey that the victim intends to close (e.g., to reclaim rent).
2. Attacker calls `marginfi_account_init_liq_record` (permissionless) with `marginfi_account = victim_account`, paying rent for the `LiquidationRecord` PDA themselves — see `InitLiquidationRecord` accounts, which impose no constraint tying the caller to the account authority: [1](#0-0) .
3. `marginfi_account.liquidation_record` is now set to the new record's pubkey (non-default).
4. Victim calls `marginfi_account_close` (authority-driven) or waits for `admin_close_account` eligibility — both fail because `liquidation_record != Pubkey::default()`, per the guard in `admin_close.rs` ( [3](#0-2) ) and the analogous check in `close.rs`.
5. Victim cannot close the account (or reclaim rent) until the record has been inactive 60 days per `close_liquidation_record`'s `INACTIVITY_PERIOD_SECS` check ( [5](#0-4) ), and the attacker can repeat step 2 to re-lock it indefinitely.

pub fn initialize_liquidation_record(ctx: Context<InitLiquidationRecord>) -> MarginfiResult {
    let mut marginfi_account = ctx.accounts.marginfi_account.load_mut()?;
    let mut liq_record = ctx.accounts.liquidation_record.load_init()?;

    liq_record.key = ctx.accounts.liquidation_record.key();
    liq_record.record_payer = ctx.accounts.fee_payer.key();
    liq_record.marginfi_account = ctx.accounts.marginfi_account.key();
    liq_record.entries = [LiquidationEntry::default(); 4];
    liq_record.cache = LiquidationCache::default();

    // Link the record back to the MarginfiAccount. This also serves to inform liquidators if the
    // record exists without performing a fetch. If this field is non-default, it exists.
    marginfi_account.liquidation_record = ctx.accounts.liquidation_record.key();

    Ok(())
}
