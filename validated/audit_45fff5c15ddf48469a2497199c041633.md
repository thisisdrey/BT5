Based on the code examined, the vulnerability is confirmed as described.

### Title
Attachment content-hash not verified against requested `content_hash` before persisting to AtlasDB - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` decodes a peer's `GetAttachmentResponse` and inserts `response.attachment` into `self.attachments` without ever comparing `response.attachment.hash()` to the `content_hash` of the `AttachmentRequest` that was sent. `AttachmentsDownloader::run` then unconditionally calls `network.atlasdb.insert_instantiated_attachment(&attachment)`, persisting arbitrary attacker-supplied bytes keyed by their own hash regardless of whether any on-chain `AttachmentInstance` requested that specific content.

### Finding Description
The request/response flow is: `AttachmentsBatchStateMachine` builds an `AttachmentRequest{content_hash: X, sources, ...}` [1](#0-0) , sends it to a selected peer, and collects the result in `BatchedRequestsResult<AttachmentRequest>`. `extend_with_attachments` then processes each `(request, response)` pair: it decodes the HTTP body via `response.decode_atlas_get_attachment()` and, on success, directly does `self.attachments.insert(response.attachment)` and `report.bump_successful_requests()` — with no check that `response.attachment.hash() == request.content_hash` [2](#0-1) .

Once the state machine reaches `AttachmentsBatchStateMachine::Done(context)`, `AttachmentsDownloader::run` iterates `context.attachments.drain()`, looks up `find_all_attachment_instances(&attachment.hash())` (keyed by the attacker's own hash, not `X`), and unconditionally calls `network.atlasdb.insert_instantiated_attachment(&attachment)` before checking whether any instances were found [3](#0-2) . This means a malicious/compromised source peer that served `Attachment{content: B}` where `Hash160::from_data(&B) != X` still gets its bytes written permanently to the node's AtlasDB, keyed by `Hash160::from_data(&B)` — content that no on-chain name operation ever committed to.

The reliability-report bump (`bump_successful_requests`) also rewards the malicious peer as if it served correct data, further undermining the reliability-tracking mechanism used to prefer peers for future requests.

### Impact Explanation
Any single remote peer acting as the sole source for a queued `AttachmentRequest` can cause the victim node to persist arbitrary attacker-chosen attachment blobs into its local `AtlasDB` under a content hash of the attacker's choosing, with no linkage to a real confirmed `AttachmentInstance`/on-chain commitment. This is an unauthenticated write to persistent node state, matches the "unauthenticated/unauthorized write to state" Critical category, and is repeatable per request/batch — enabling attachment-storage exhaustion and pollution of the AtlasDB with content that was never committed to on-chain.

### Likelihood Explanation
The attacker only needs to run an ordinary Stacks peer that other nodes select as an outbound sync peer for the Atlas attachment sync protocol (no special privileges, secrets, or roles required), and be selected as (one of) the sources for a given content hash — attainable simply by being present in the requester's peer set and reporting itself as having the attachment in its inventory. The attack is trivially repeatable for each `AttachmentRequest` cycle.

### Recommendation
In `extend_with_attachments` (stackslib/src/net/atlas/download.rs:530-558), after decoding `response.decode_atlas_get_attachment()`, verify `response.attachment.hash() == request.content_hash` before inserting into `self.attachments`; on mismatch, treat as a failed/faulty response (`bump_failed_requests`, and optionally mark the peer as faulty) instead of accepting it. As defense in depth, `AttachmentsDownloader::run` should also verify the attachment hash matches an actual expected content hash before calling `insert_instantiated_attachment`.

### Proof of Concept
Add a test in `stackslib/src/net/atlas/download.rs` tests module:
1. Construct an `AttachmentsBatchStateContext` with a single peer and a pending `AttachmentRequest{content_hash: X, ...}`.
2. Build a `BatchedRequestsResult<AttachmentRequest>` whose `succeeded` map contains `(request, Some(response))` where `response.decode_atlas_get_attachment()` returns `Attachment{content: B}` with `Hash160::from_data(&B) != X`.
3. Call `context.extend_with_attachments(&mut results)` and assert `context.attachments` contains the attacker's attachment (keyed by `Hash160::from_data(&B)`), while `X` was never validated.
4. Drive it through `AttachmentsDownloader::run` (or replicate its `Done` handling logic), then assert `atlasdb.find_attachment(&X).unwrap().is_none()` while `atlasdb.find_attachment(&Hash160::from_data(&B)).unwrap().is_some()` — proving unrequested/unverified content was persisted.
