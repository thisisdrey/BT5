### Title
Unbounded, unprunable growth of an account's TRC10 `assetV2` map lets any user permanently degrade `GetAccount` API performance for a victim address - (File: chainbase/src/main/java/org/tron/core/capsule/AccountCapsule.java)

### Summary
`TransferAssetActuator` lets any TRC10 asset holder push an asset balance into an arbitrary `toAddress`, creating a new entry in that account's `assetV2` map. `AccountCapsule.reduceAssetAmountV2` and `addAssetAmountV2` never remove an entry once created, even when the balance is reduced back to `0`, so a victim's per-address asset entry set only ever grows. This mirrors the Curves `ownedCurvesTokenSubjects` bug: an attacker (not the account owner) can unilaterally and permanently inflate a victim's per-account collection via an ordinary transfer, and there is no way for the victim to prune it.

### Finding Description
`TransferAssetActuator.execute()` calls `toAccountCapsule.addAssetAmountV2(assetName, amount, ...)` for any `toAddress`, creating the account if it doesn't exist yet: [2](#0-1) 

`addAssetAmountV2` always adds a brand-new key to `assetV2Map` (via `putAssetV2`) if the token is not already present, and `reduceAssetAmountV2` only ever writes `0` back into the map — it never calls `clearAssetV2`/removes the key: [3](#0-2) 

When `AllowAssetOptimization` is enabled, each new asset entry is additionally persisted as its own key (`address || tokenId`) in `AccountAssetStore`: [4](#0-3) 

Crucially, `Wallet.getAccount()` — the handler backing the public `GetAccount` gRPC/HTTP API — unconditionally calls `accountCapsule.importAllAsset()` on every request: [1](#0-0) 

`importAllAsset()` triggers `AssetUtil.importAllAsset()`, which performs a full LevelDB `prefixQuery` over *every* asset key ever created for that address and rebuilds the whole map from scratch: [5](#0-4) [6](#0-5) 

Since (1) issuing a TRC10 asset and sending a dust amount is a normal, unprivileged operation, (2) the victim's `assetV2` entry set can only grow and is never pruned, and (3) every `GetAccount` API call for that address re-executes an O(n) prefix scan and map rebuild, an attacker can cheaply and permanently degrade the query cost of a targeted address by issuing many distinct TRC10 tokens and transferring a small amount of each to the victim. This is directly analogous to the Curves `ownedCurvesTokenSubjects` issue: a storage collection tied to an account that (a) grows via actions of unrelated third parties, (b) is never shrunk even when the underlying balance stops being owned, and (c) is iterated in full on a hot path.

### Impact Explanation
Every `GetAccount` request (used pervasively by wallets, exchanges, explorers, and the JSON-RPC/HTTP gateway) for a targeted address becomes proportionally more expensive as the attacker keeps adding new TRC10 entries. Because entries are never removed, this is a permanent, cumulative degradation, not a one-off cost — repeated targeting of high-value addresses (exchange hot wallets, popular contracts) can make routine balance queries against them slow or resource-intensive for the serving Full/Solidity Node, affecting the node's ability to serve that query path for other users as well.

### Likelihood Explanation
Likelihood is high: no special privilege is needed — issuing an asset (`AssetIssueContract`) and sending trivial TRC10 amounts (`TransferAssetContract`) to any address are ordinary, cheap, broadcastable operations available to any account holder. Repeating this against a single victim address costs only the linear sum of asset-issuance fees while the resulting query overhead accumulates in a way the victim cannot reverse or clean up.

### Recommendation
Prune `assetV2` entries (both the in-memory map and the persisted `AccountAssetStore` key) whenever a balance is reduced to `0`, instead of leaving a zero-value entry behind. Consider also capping the number of distinct assets an account can hold at once, or moving `GetAccount`'s asset aggregation off the hot path (e.g., paginated/lazy asset listing) so a single account's asset-count cannot be weaponized to slow down every future balance query against it.

### Proof of Concept
1. Attacker issues N distinct TRC10 tokens via `AssetIssueContract` (`CreateAssetIssue`).
2. For each token, attacker broadcasts a `TransferAssetContract` sending a minimal amount (e.g., `1`) to victim address `V`. Each call runs `TransferAssetActuator.execute()` → `toAccountCapsule.addAssetAmountV2(...)`, adding a new key to `V`'s `assetV2` map/`AccountAssetStore` entries — see `TransferAssetActuator.java` lines 60-84 above.
3. Even if `V` immediately spends the received tokens back out (`reduceAssetAmountV2` reaching `0`), the map entry for that `tokenId` is never deleted (`AccountCapsule.java` lines 780-813), so `V`'s asset-entry count is monotonically non-decreasing.
4. Any client calls `GetAccount(V)` via the `Wallet`/`WalletSolidity` gRPC service; `Wallet.getAccount()` calls `accountCapsule.importAllAsset()`, forcing a `prefixQuery` over all N (and growing) asset keys for `V` on every single request (`Wallet.java` lines 335-341, `AssetUtil.java` lines 46-52, `AccountAssetStore.java` lines 97-109), with cost scaling with N indefinitely as the attacker repeats step 2 against `V` over time.

  public boolean addAssetAmountV2(byte[] key, long amount,
      DynamicPropertiesStore dynamicPropertiesStore, AssetIssueStore assetIssueStore) {
    importAsset(key);
    boolean disableJavaLangMath = dynamicPropertiesStore.disableJavaLangMath();
    //key is token name
    if (dynamicPropertiesStore.getAllowSameTokenName() == 0) {
      Map<String, Long> assetMap = this.account.getAssetMap();
      AssetIssueCapsule assetIssueCapsule = assetIssueStore.get(key);
      String tokenID = assetIssueCapsule.getId();
      String nameKey = ByteArray.toStr(key);
      Long currentAmount = assetMap.get(nameKey);
      if (currentAmount == null) {
        currentAmount = 0L;
      }
      this.account = this.account.toBuilder()
          .putAsset(nameKey, addExact(currentAmount, amount, disableJavaLangMath))
          .putAssetV2(tokenID, addExact(currentAmount, amount, disableJavaLangMath))
          .build();
    }
    //key is token id
    if (dynamicPropertiesStore.getAllowSameTokenName() == 1) {
      String tokenIDStr = ByteArray.toStr(key);
      Map<String, Long> assetMapV2 = this.account.getAssetV2Map();
      Long currentAmount = assetMapV2.get(tokenIDStr);
      if (currentAmount == null) {
        currentAmount = 0L;
      }
      this.account = this.account.toBuilder()
          .putAssetV2(tokenIDStr, addExact(currentAmount, amount, disableJavaLangMath))
          .build();
    }
    return true;
  }

  public boolean reduceAssetAmount(byte[] key, long amount, boolean disableJavaLangMath) {
    Map<String, Long> assetMap = this.account.getAssetMap();
    String nameKey = ByteArray.toStr(key);
    Long currentAmount = assetMap.get(nameKey);
    if (amount > 0 && null != currentAmount && amount <= currentAmount) {
      this.account = this.account.toBuilder()
              .putAsset(nameKey, subtractExact(currentAmount, amount, disableJavaLangMath)).build();
      return true;
    }

    return false;
  }

      map.forEach((k, v) -> {
        byte[] assetID = ByteArray.subArray(k.getBytes(),
                account.getAddress().toByteArray().length, k.getBytes().length);
        assets.put(ByteArray.toStr(assetID), Longs.fromByteArray(v));
      });
    }
    account.getAssetV2Map().forEach((k, v) -> assets.put(k, v));
    return assets;
  }
