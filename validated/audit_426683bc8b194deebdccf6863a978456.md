### Title
Near-zero `total-assets` after `socialize-debt` causes disproportionate LP share minting on `deposit` - ([File: mainnet/contracts/vault/v0-vault-usdc.clar])

### Summary
The Zest v2 tokenized vault contracts (`v0-vault-usdc.clar`, `v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdh.clar`) compute share-out on deposit as `amount * total-supply / total-assets`, exactly the same division-by-near-zero-pool-value pattern flagged in the Halborn `calcLpOut`/`getEffectivePoolValue` report. When `total-assets` is driven to a tiny (but non-zero) value relative to `total-supply`, a subsequent `deposit` mints a disproportionately large number of shares, diluting/stealing value from existing LPs; if `total-assets` hits exactly zero, the code resets to 1:1 baseline minting, exactly mirroring the two failure modes described in the report ("inflated shares" and "reset to base shares").

### Finding Description
`convert-to-shares-preview` computes shares as: [1](#0-0) 
i.e. `mul-div-down(amount, total-supply-preview, total-assets-preview)` when both are non-zero, but falls back to a raw 1:1 `amount` when `total-supply` is zero, and to `u0` when `total-assets` is zero. This is used directly to mint shares in `deposit`: [2](#0-1) 

`total-assets` is computed as `assets + max(0, debt-preview - total-borrowed)` — i.e. the vault's own bookkeeping variable `assets` plus any accrued interest not yet realized: [3](#0-2) 

The `assets` bookkeeping variable can be reduced sharply relative to `total-supply` (the outstanding `zft` shares) by `socialize-debt`, which writes down `assets` and `lindex` proportionally when bad debt is realized, without burning any `zft` shares: [4](#0-3) 

Because `socialize-debt` reduces the numerator/denominator basis (`assets`) but never touches `total-supply` (zft), it can push `total-assets` toward a tiny value while `total-supply` remains large — precisely the "pool value approaches zero" precondition from the Halborn report. Any subsequent unprivileged user calling `deposit` with even a small `amount` will receive `amount * total-supply / total-assets` shares — a wildly inflated share count relative to the value deposited, diluting/stealing value from all existing LP-share holders. If a repay or other action pushes `total-assets` to exactly zero, `convert-to-shares-preview` reverts to minting shares 1:1 with `amount` (ignoring the existing `total-supply` entirely), which is the "reset to baseline" failure mode from the report.

### Impact Explanation
An attacker (or even an ordinary user acting opportunistically right after a socialize-debt event that is a normal, expected part of protocol operation, not a DAO compromise) can deposit a small amount immediately after `total-assets` collapses relative to `total-supply` and mint a disproportionate number of `zft` shares. Because `zft` shares are fungible claims on the vault's underlying assets (redeemable via `redeem`/`convert-to-assets-preview`), this directly dilutes and steals value from existing LP-share holders — a direct theft of user funds at rest, matching the **Critical** impact class.

### Likelihood Explanation
The precondition (a large drop in `assets` relative to `total-supply`) is reachable through the protocol's own `socialize-debt` mechanism, which exists specifically to handle bad-debt write-downs — a normal operational path, not requiring DAO compromise or leaked keys. Once that state occurs, exploitation only requires calling the public, unprivileged `deposit` entrypoint, so the likelihood is not purely theoretical, though it depends on the size and timing of a socialize-debt write-down relative to outstanding share supply.

### Recommendation
Enforce a minimum floor on `total-assets-preview` (and `total-assets`) analogous to the remediation applied to `calcLpOut` (never letting the effective pool value drop below a fixed floor, e.g. equivalent to `MINIMUM-LIQUIDITY`), or reject/queue deposits and share-price-dependent operations when `total-assets` falls below a safe threshold relative to `total-supply`. Additionally, consider proportionally burning/adjusting share supply within `socialize-debt` so that the shares-to-assets ratio is not distorted for later depositors.

### Proof of Concept
1. Vault has `total-supply` (zft) = `S` from prior deposits, `assets` = `A`.
2. An authorized caller (e.g., liquidation/lending module) invokes `socialize-debt` for a large `scaled-amount` to realize bad debt, sharply reducing `assets` (per lines 942-982) while leaving `total-supply` (zft) unchanged.
3. `total-assets-preview` (line 343-348) now returns a value `A'` that is tiny relative to `S`.
4. An unprivileged user calls `deposit(amount, min-out, recipient)` (line 761); `convert-to-shares-preview(amount)` (line 306-313) computes `mul-div-down(amount, S, A')`, minting a share count disproportionate to `amount`'s real value, diluting all existing zft holders.
5. If a subsequent repay/accrue drives `total-assets-preview` to exactly `u0`, the same function instead mints shares 1:1 with `amount`, ignoring `S` entirely — the "reset to baseline" bug from the report.

(define-public (socialize-debt (scaled-amount uint))
  (let ((scaled-principal (var-get principal-scaled))
        (borrowed (var-get total-borrowed))
        (idx (var-get index))
        (current-assets (var-get assets))
        (current-lindex (var-get lindex))
        (old-total-assets (total-assets))
        (debt-reduction (mul-div-down scaled-amount idx INDEX-PRECISION))
        (principal-reduction (if (> scaled-principal u0)
                                (mul-div-down scaled-amount borrowed scaled-principal)
                                u0))
        ;; Write down lindex proportionally to loss in total-assets
        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
                       (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
                       u0)))

    (try! (check-caller-auth))
    (asserts! (> scaled-amount u0) ERR-AMOUNT-ZERO)

    (var-set lindex new-lindex)
    (var-set principal-scaled (if (> scaled-principal scaled-amount) (- scaled-principal scaled-amount) u0))
    (var-set total-borrowed (if (> borrowed principal-reduction) (- borrowed principal-reduction) u0))
    (var-set assets (if (> current-assets principal-reduction) (- current-assets principal-reduction) u0))

    (print {
      action: "socialize-debt",
      caller: contract-caller,
      data: {
        scaled-amount: scaled-amount,
        debt-reduction: debt-reduction,
        principal-reduction: principal-reduction,
        old-lindex: current-lindex,
        new-lindex: new-lindex,
        old-total-assets: old-total-assets,
        principal-scaled: (if (> scaled-principal scaled-amount) (- scaled-principal scaled-amount) u0),
        total-borrowed: (if (> borrowed principal-reduction) (- borrowed principal-reduction) u0),
        index: idx
      }
    })

    (ok true)))
