### Title
Unbounded proc-receive reference-update list allows a single push to trigger unbounded synchronous hook-process spawning — DoS of `SSHReceivePack`/`PostReceivePack` - ([File: internal/gitaly/hook/procreceive_handler.go])

### Summary
`NewProcReceiveHandler` reads an attacker-controlled, unbounded sequence of pkt-line reference-update records from `git-receive-pack`'s `proc-receive` protocol stream and accumulates them into an in-memory `updates []ReferenceUpdate` slice with no upper bound. This list is later walked multiple times, once per update spawning a Git `update` hook (with associated custom-hook executor, subprocess, and RPC round trip), directly analogous to the reported `refund()` bug where an unbounded, attacker-grown `participants` array is iterated in a single call, causing resource exhaustion / DoS.

### Finding Description
`NewProcReceiveHandler` scans pkt-lines from the client-controlled stdin stream and appends every parsed reference update to `updates` with no cap: [1](#0-0) 

This handler is registered per push via `RegisterProcReceiveHook`, which is wired into the ordinary `SSHReceivePack`/`PostReceivePack` RPC handlers when transactions are enabled: [2](#0-1) 

Once populated, `handler.ReferenceUpdates()` is iterated:
1. In the non-atomic branch of `procReceiveHook`, once per update, each iteration calling `receivePackReferenceUpdates` for a single update: [3](#0-2) 
2. Again to accept/reject every update: [4](#0-3) 
3. Inside `receivePackReferenceUpdates`, once per update, invoking `hookManager.UpdateHook`, which spawns a custom-hooks executor (an OS subprocess) for every single reference: [5](#0-4) [6](#0-5) 

No limit exists anywhere in this path on the number of reference updates a client may submit in a single proc-receive session; searches for a maximum-updates/maximum-refs guard in the codebase returned no results.

### Impact Explanation
An ordinary authenticated user with push access can submit a single push (e.g. a mirror-style push or a crafted `proc-receive` client) containing an extremely large number of reference updates (thousands to tens of thousands of refs). Because the loop is unbounded, this forces Gitaly to:
- Hold the entire update list in memory for the RPC's lifetime.
- Serially spawn one OS process (and potentially a custom hook script) per reference in the non-atomic path, and one `UpdateHook` RPC + subprocess per reference in the atomic path.

This can starve process/file-descriptor limits, exhaust CPU on the storage node, and cause the RPC to run far past client/gateway timeouts — a denial of service against the receive-pack RPC handler and potentially against the whole storage node given repeated abuse, matching the "RPC-handler resource limits" acceptance criterion.

### Likelihood Explanation
Reachable directly from an unprivileged user's `git push` (SSH or HTTP) as long as the repository has the `proc-receive` transaction path enabled; no special privileges beyond ordinary write/push access are required, and no server-side cap exists to reject an oversized reference-update batch before iterating.

### Recommendation
Enforce a configurable maximum number of reference updates accepted per proc-receive session in `NewProcReceiveHandler` (reject/abort the scan once the count exceeds the limit), and/or batch update-hook invocations instead of spawning one subprocess per reference, with bounded concurrency and a hard cap consistent with existing Gitaly `[[concurrency]]`/request-limiting patterns already used elsewhere in the service.

### Proof of Concept
1. Initiate an SSH/HTTP `git push` against a repository with `proc-receive` transactions enabled.
2. Drive a custom `proc-receive` protocol client (or a push containing an artificially large number of ref updates) that sends, e.g., 50,000 pkt-line reference-update records before the terminating flush.
3. Observe `NewProcReceiveHandler`'s scan loop accepting all 50,000 entries into `updates` unchecked.
4. Observe `procReceiveHook`/`receivePackReferenceUpdates` sequentially invoking `hookManager.UpdateHook` (and, for non-atomic mode, `receivePackReferenceUpdates`) 50,000 times, spawning a subprocess per reference, causing the RPC to run for an extended period and consume disproportionate CPU/process resources on the Gitaly node — an out-of-gas-style DoS analog of the `refund()` unbounded-loop pattern.

	cfg config.Cfg,
	req gitcmd.ReceivePackRequest,
	repo *localrepo.Repo,
	hookManager hook.Manager,
	txRegistry hook.TransactionRegistry,

	receiveDoneCh := make(chan struct{})
	handlerErrCh := make(chan error, 1)

	tx, err := txRegistry.Get(transactionID)

		return nil, fmt.Errorf("getting transaction: %w", err)
	}

	registry := hookManager.ProcReceiveRegistry()

	if err != nil {
		return nil, fmt.Errorf("registering waiter: %w", err)
	}

		case <-ctx.Done():

				handlerErrCh <- err
			}
		}
		close(handlerErrCh)
	}()

func (m *GitLabHookManager) updateHook(ctx context.Context, payload gitcmd.HooksPayload, repo *gitalypb.Repository, ref, oldValue, newValue string, env []string, stdout, stderr io.Writer) error {
	objectHash, err := git.ObjectHashByFormat(payload.ObjectFormat)
	if err != nil {
		return fmt.Errorf("looking up object hash: %w", err)
	}

	if ref == "" {
		return structerr.NewInternal("hook got no reference")
	}
	if err := objectHash.ValidateHex(oldValue); err != nil {
		return structerr.NewInternal("hook got invalid old value: %w", err)
	}
	if err := objectHash.ValidateHex(newValue); err != nil {
		return structerr.NewInternal("hook got invalid new value: %w", err)
	}
	if payload.UserDetails == nil {
		return structerr.NewInternal("payload has no receive hooks info")
	}

	executor, err := m.newCustomHooksExecutor(ctx, repo, "update")
	if err != nil {
		return structerr.NewInternal("%w", err)
	}

	customEnv, err := m.customHooksEnv(ctx, payload, nil, env)
	if err != nil {
		return structerr.NewInternal("constructing custom hook environment: %w", err)
	}

	if err = executor(
		ctx,
		[]string{ref, oldValue, newValue},
		customEnv,
		nil,
		stdout,
		stderr,
	); err != nil {
		return fmt.Errorf("executing custom hooks: %w", err)
	}
