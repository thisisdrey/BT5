### Title
Stale `PromiseYieldReceipt`/`PromiseYieldStatus` state survives `DeleteAccount`, letting attacker-planted actions execute with self-authority against an account recreated under the same name - ([File: runtime/runtime/src/ext.rs], [File: core/store/src/utils/mod.rs], [File: runtime/runtime/src/lib.rs])

### Summary
`create_promise_yield_receipt` writes `TrieKey::PromiseYieldStatus`/`PromiseYieldReceipt` keyed only by `(receiver_id, data_id)`, and `remove_account` (used by `DeleteAccount`) never deletes those keys for the account being removed. When the account name is later reused, a `PromiseResume` for the old `data_id` is looked up and executed purely by name in `process_receipt`, letting an attacker's pre-planted callback actions run with self-authority (`predecessor_id == receiver_id`) against the new occupant of the account name.

### Finding Description
`create_promise_yield_receipt` sets `PromiseYieldStatus::Yielded` for `(receiver_id, data_id)` at host-call time, and delivery of the corresponding `PromiseYield` receipt persists the full callback `Receipt` via `set_promise_yield_receipt` in `process_receipt`: [1](#0-0) [2](#0-1) 

`remove_account`, invoked when a `DeleteAccount` action executes, only clears `Account`, `ContractCode`, `AccessKey`/`GasKeyNonce`, and `ContractData` rows for the account; it never scans or removes `PromiseYieldReceipt`, `PromiseYieldStatus`, or `YieldIdToDataId`/`DataIdToYieldId` rows: [3](#0-2) 

Later, when a `PromiseResume` receipt for the stale `data_id` arrives, `process_receipt` looks the status and yield receipt up strictly by `(account_id, data_id)` — with no check that the account instance which created the yield is the same one currently occupying that name — and, if found, executes the stored `yield_receipt`'s actions via `apply_action_receipt` against whatever state/contract now exists at that account name: [4](#0-3) 

Because the yield's callback is a self-referential promise (receiver_id == predecessor_id == the account that created it), actions inside it (e.g. `AddKey`, `DeployContract`, `Stake`, `Transfer`, `FunctionCall`) are treated as self-authorized. Since the trie key namespace is name-only and survives account deletion, an attacker can preconstruct a callback bundle that will later execute with full self-authority against a completely different, unrelated account occupying the same name — an authorization escalation the new owner never granted.

### Impact Explanation
This is an authorization-escalation vulnerability: the resumed receipt's action list, chosen by the attacker at yield-creation time, executes as if the *new* account authorized it against itself, potentially allowing full compromise (adding attacker keys, redeploying contracts, transferring balance) of an account the attacker no longer controls. This maps to NEAR's "authorization escalation across accounts or promises" bounty category.

### Likelihood Explanation
Exploitability requires the attacker to control (or be, or collude with) the parent/factory account that creates the affected sub-account, as stated in the precondition — a realistic setup for common on-chain "subaccount factory" patterns (linkdrops, app-specific user account provisioning) where a name can be deleted and later reissued to a new party. The attacker's cost is limited to ordinary transaction/gas fees for `CreateAccount`, `DeployContract`, `FunctionCall(promise_yield_create)`, `DeleteAccount`, and later triggering `promise_yield_resume`/`PromiseResume` for the known `data_id`. No validator, node, or protocol-level privilege is needed, and the sequence is fully repeatable per reused account name. I was not able to fully inspect `action_delete_account`'s complete body in this session to confirm there is no additional guard rejecting deletion while a `PromiseYield` is outstanding; the `PromiseYield` reference found in `runtime/runtime/src/actions.rs` should be manually checked to rule out an existing mitigation before treating this as fully confirmed.

### Recommendation
Have `remove_account` (or the `DeleteAccount` action handler) enumerate and remove all `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, and `DataIdToYieldId` trie rows prefixed by the account being deleted (analogous to the existing access-key/contract-data cleanup loops), or block/timeout-resolve outstanding yields before allowing account deletion so no stale name-keyed promise state can survive account recreation.

### Proof of Concept
Integration test in the runtime `apply` test harness:
1. `CreateAccount(A)` by an attacker-controlled parent, `DeployContract` exposing `promise_yield_create`, then `FunctionCall` invoking it; assert `get_promise_yield_status`/`get_promise_yield_receipt` return `Some` for `(A, data_id)` immediately after this receipt commits.
2. Submit `DeleteAccount(A, beneficiary=attacker)`; commit, then assert `get_promise_yield_status`/`get_promise_yield_receipt` for `(A, data_id)` **still** return `Some` even though `get_account(A)` returns `None`.
3. Have an unrelated party issue `CreateAccount(A)` again (fresh account/contract state).
4. Deliver `PromiseResume(data_id)` (e.g., via `promise_yield_resume` from an attacker-controlled contract, or the timeout path); assert the stale yield's original action list (e.g., an `AddKey` planted by the attacker) executes against the new account A, and that the new account now contains the attacker's key/contract despite the new owner never authorizing it.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
