## Title
Unauthenticated `RecvError` packets can tear down established tunnels when the target `HostInfo` has no set remote address (relay-only peers) - (File: `outside.go`)

### Summary
Nebula's `RecvError` message type is processed entirely outside the authenticated data-plane: it is a bare, unencrypted header with no certificate, no handshake, and no AEAD tag, and is routed to `handleRecvError` before any hostinfo/connection-state validation happens [1](#0-0) . `handleRecvError` is supposed to defend against packet forgery by comparing the packet's source address to the tunnel's currently known remote address, but that check is only performed when the tunnel's remote address happens to be "valid":

```go
hr := hostinfo.GetRemote()
if hr.IsValid() && hr != addr {
    f.l.Info("Someone spoofing recv_errors?", ...)
    return
}
f.closeTunnel(hostinfo)
``` [2](#0-1) 

If `hr.IsValid()` is `false` — which is the normal, persistent state for any `HostInfo` reachable only through a relay, since `SetRemote` is only called for non-relayed peers during handshake completion [3](#0-2)  — the address-spoofing check silently evaluates to `false` and is skipped entirely. `closeTunnel` then runs unconditionally.

### Finding Description
This is the same bug class as the `arbitraryCall()`/`incentives[who]==0` finding: a security check is gated on a piece of mutable state (`incentives[who]` in the external report, `hostinfo.GetRemote().IsValid()` here) that legitimately becomes "empty"/zero during normal protocol operation, and once it does, the code silently treats the "empty" state as "nothing to protect" instead of "deny by default." In the external report, once an incentive is fully claimed the tracking map resets to zero and the `require` guard that was supposed to block `arbitraryCall` on that token becomes a no-op. Here, once a `HostInfo` is relay-only (a completely normal, supported Nebula topology, e.g. `relay.use_relays`), `GetRemote()` never becomes valid, so the anti-spoofing guard in `handleRecvError` becomes a permanent no-op for that tunnel.

Because `header.RecvError` packets require no certificate, no handshake, and no decryption to reach `handleRecvError` [4](#0-3) , any attacker on the path to the victim's UDP listener — without holding any CA-signed Nebula certificate — can forge a `RecvError` packet from an arbitrary source address, carrying the victim's `RemoteIndex` (observable on the wire in every packet header, not a secret), and the check that is meant to bind the source address to the known remote is entirely bypassed for relay-only peers.

### Impact Explanation
An unauthenticated attacker can force `f.closeTunnel(hostinfo)` and `f.handshakeManager.DeleteHostInfo(hostinfo)` [5](#0-4)  on any established tunnel to a relay-only peer, without needing to hold a valid certificate, and without needing to accurately spoof the source address (the check that would normally require that is skipped). This is a remote, unauthenticated tunnel-teardown / denial-of-service against a class of tunnels (behind-NAT / relay-connected nodes) that Nebula explicitly supports and that CHANGELOG entries show the project treats as security-relevant (e.g. the `listen.send_recv_error`/`accept_recv_error` mitigations and the 1.9.7 security fix "Nebula could incorrectly accept and process a packet from an erroneous source IP").

### Likelihood Explanation
`RemoteIndex` values are transmitted in cleartext in every packet header, so any attacker who can observe a single packet to/from the victim (or who is positioned to send spoofed UDP to the victim's listen port) learns the value needed to trigger this. No cryptographic material, certificate, or handshake completion is required to reach `handleRecvError`. The only precondition is that the target `HostInfo` is relay-connected (`GetRemote()` unset), which is a standard, commonly-used Nebula deployment pattern for NAT'd nodes.

### Recommendation
Do not treat `hr.IsValid() == false` as "no check needed." Either:
- Track the last-known relay/forwarding path (or the relay's own address) for relay-only `HostInfo`s and validate `addr` against that, or
- Refuse to act on `RecvError` for any `HostInfo` that doesn't have a validated, comparable remote address, rather than defaulting to "allow the teardown."

### Proof of Concept
1. Establish a Nebula tunnel between two nodes, `A` and `B`, where `B` is only reachable through a relay (`relay.use_relays` on `B`, `relay.am_relay` on the relay node) so `B`'s `HostInfo` on `A`'s side never calls `SetRemote`.
2. As an attacker with no Nebula certificate, capture or otherwise learn `B`'s `RemoteIndex` as seen by `A` (visible in cleartext in packet headers exchanged over the relay).
3. Send `A` a single UDP packet, header-only, `Type = header.RecvError`, `RemoteIndex` = the value learned in step 2, from any spoofed or attacker-controlled source address.
4. `A.handleRecvError` looks up the hostinfo via `QueryReverseIndex`, finds `hr.IsValid() == false` (no direct remote was ever set for `B`), skips the spoof check, and calls `closeTunnel` + `DeleteHostInfo`, tearing down `A`'s authenticated tunnel to `B` without any authentication from the attacker.

		if len(packet) > 1 {

					"error", err,
					"packet", packet,
				)
			}
		}
		return

		}
		return
	}

	// Check before processing to see if this is a expected type/subtype
	if !h.IsValidSubType() {
		f.messageMetrics.RxInvalid(1)

		}
		return

			}
			return
		}
	}

	// don't keep Rx metrics for message type, since you can see those in the tun metrics
	if h.Type != header.Message {
		f.messageMetrics.Rx(h.Type, h.Subtype, 1)

	// Unencrypted packets
	switch h.Type {
	case header.Handshake:
		f.handshakeManager.HandleIncoming(via, packet, h)
		return

	case header.RecvError:
		f.handleRecvError(via.UdpAddr, h)
		return
	}
