### Title
`ReceiveDescriptionCapsule` constructor discards its parameter and self-assigns an uninitialized field, causing a guaranteed `NullPointerException` on every shielded-output build (denial of the shielded-transaction API) - ([File: framework/src/main/java/org/tron/core/capsule/ReceiveDescriptionCapsule.java])

### Summary
`ReceiveDescriptionCapsule(final ReceiveDescription outputDescription)` never stores the constructor argument into the object's field; instead it assigns the field to itself (`this.receiveDescription = receiveDescription;`), leaving `receiveDescription` `null`. Every subsequent call on the resulting object (getters, setters that call `.toBuilder()`, or `getData()`/`getInstance()`) dereferences a `null` reference, guaranteeing a `NullPointerException`. This mirrors the CVE bug class: a copy/construction routine that erroneously preserves/overwrites the wrong reference instead of the intended source value, producing a dangling/invalid reference that is dereferenced downstream. [1](#0-0) 

### Finding Description
The constructor is supposed to initialize `this.receiveDescription` from the `outputDescription` parameter, matching the pattern used everywhere else in the class (e.g., the byte-array and multi-`ByteString` constructors both correctly populate the field): [2](#0-1) 

Instead, the buggy constructor references the field itself (`receiveDescription`) rather than the parameter `outputDescription`: [1](#0-0) 

Since Java initializes object reference fields to `null` before the constructor body runs (there is no field initializer for `receiveDescription`), this line is equivalent to `this.receiveDescription = null;`. Any use of this constructor produces an object whose internal protobuf message is `null`. All getters (`getValueCommitment`, `getEphemeralKey`, `getEncCiphertext`, `getOutCiphertext`, `getCm`, `getZkproof`) and all setters (which call `this.receiveDescription.toBuilder()...`), as well as `getData()`/`getInstance()`, will throw `NullPointerException` unconditionally when invoked on such an instance. [3](#0-2) 

This constructor is used by the shielded-transaction builders that back user-facing wallet APIs for constructing shielded outputs: `ZenTransactionBuilder` and `ShieldedTRC20ParametersBuilder` both import and instantiate `ReceiveDescriptionCapsule` with a `ReceiveDescription` argument. [4](#0-3) 

I was not able to fully trace the exact call sites inside `ZenTransactionBuilder`/`ShieldedTRC20ParametersBuilder` where this specific single-argument constructor is invoked (as opposed to the working multi-`ByteString` constructor) within the tool-call budget available, so I cannot confirm with certainty whether this exact overload is reachable from a live, non-test code path today or is effectively dead/unused code shadowed by the correct constructor. This is an important caveat for likelihood assessment.

### Impact Explanation
If this constructor overload is actually invoked from a live wallet-API code path (e.g., building a shielded transfer or a shielded TRC20 parameter set that includes a receive/output description), any anonymous API client requesting such an operation would deterministically trigger a `NullPointerException` inside the node's request-handling code. Depending on how the surrounding Wallet/gRPC/HTTP layer handles unchecked exceptions, this could:
- Break/deny the shielded transaction creation API entirely (an API the node can no longer serve for legitimate users), or
- Propagate as an unhandled exception in the request-handling thread.

This does not on its own grant unauthorized fund movement or key disclosure; the primary concrete impact is availability/denial-of-service for the shielded-transaction construction API path, which is the accepted "API the node can no longer serve" impact category.

### Likelihood Explanation
The bug is 100% deterministic once the buggy constructor is invoked — no attacker-controlled data or race condition is required, only that the vulnerable code path is reached. The uncertainty is whether it is currently reachable in production: I found the constructor exists and is not dead code (referenced via import/usage in `ZenTransactionBuilder`), but I could not verify from the retrieved snippets whether that particular one-argument overload (versus the working multi-arg overload) is the one actually called in the current output-building logic.

### Recommendation
Fix the constructor to store the parameter instead of self-assigning:
```java
public ReceiveDescriptionCapsule(final ReceiveDescription outputDescription) {
    this.receiveDescription = outputDescription;
}
```
Additionally, add a unit test constructing a `ReceiveDescriptionCapsule` via this specific overload and asserting `getInstance()` returns the passed-in `ReceiveDescription`, to prevent regression. Audit all call sites in `ZenTransactionBuilder` and `ShieldedTRC20ParametersBuilder` to confirm whether this overload is currently exercised, and add defensive null-checks/exception handling around shielded-transaction construction in the Wallet API layer regardless.

### Proof of Concept
```java
import org.tron.protos.contract.ShieldContract.ReceiveDescription;
import org.tron.core.capsule.ReceiveDescriptionCapsule;

ReceiveDescription rd = ReceiveDescription.newBuilder()
    .setValueCommitment(com.google.protobuf.ByteString.copyFromUtf8("cv"))
    .build();

ReceiveDescriptionCapsule capsule = new ReceiveDescriptionCapsule(rd);
capsule.getValueCommitment(); // throws NullPointerException — internal field is null,
                               // not the `rd` passed in.
```
Because `this.receiveDescription` is `null` after construction, any getter/setter call — and thus any code path in `ZenTransactionBuilder`/`ShieldedTRC20ParametersBuilder` that further populates or serializes this capsule for inclusion in a shielded transaction — throws `NullPointerException` instead of producing a valid shielded output.
