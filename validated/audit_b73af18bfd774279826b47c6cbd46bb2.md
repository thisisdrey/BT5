Found a concrete, unmitigated analog of this rounding-to-zero bug class in java-tron's on-chain order-book market (TRON's DEX), specifically in `MarketSellAssetActuator.matchSingleOrder`.

### Title
Rounding-to-zero in order-book match settlement lets a taker drain a maker's residual sell tokens for free - ([File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java])

### Summary
`MarketSellAssetActuator.matchSingleOrder` computes the payment a maker receives from a match using integer (floor) division via `MarketUtils.multiplyAndDivide`. When the taker precisely consumes a maker's remaining sell quantity ("taker == maker" branch), the code does not guard against the computed payment rounding down to zero, unlike the sibling "taker > maker" branch, which explicitly checks for this and refunds the maker instead of finalizing the trade.

### Finding Description
In `matchSingleOrder`, three branches handle the relative size of `takerBuyTokenQuantityRemain` vs. `makerOrderCapsule.getSellTokenQuantityRemain()`. [1](#0-0) 

In the "taker == maker" branch, `makerBuyTokenQuantityReceive` is computed as: [2](#0-1) 

This uses `MarketUtils.multiplyAndDivide`, which floors the result: [3](#0-2)

Unlike the "taker > maker" branch, which explicitly checks for this and refunds the maker's un-paid sell tokens instead of finalizing the trade: [4](#0-3) 

the "taker == maker" branch has no such check. It unconditionally sets `makerOrderCapsule.setSellTokenQuantityRemain(0)` and marks the maker order `INACTIVE`, then credits the taker with the full token amount and the maker with `0`:

`addTrxOrToken(makerOrderCapsule, makerBuyTokenQuantityReceive)` with `makerBuyTokenQuantityReceive == 0` is a no-op credit — the maker's final dust of sell tokens is consumed with no compensation and no refund path, since `MarketUtils.returnSellTokenRemain` (which would restore the sell tokens) is never invoked in this branch.

The comment in the sibling branch even acknowledges the developers were aware of this rounding risk ("the quantity is too small... it would not happen here... for the maker, when sellQuantity < buyQuantity, it will get at least one buyToken") — but that reasoning does not hold when `sellQuantity > buyQuantity` (a low-price sell order), which is exactly the "taker == maker" scenario left unguarded.

### Impact Explanation
This is not merely a freezing bug like the Neutron report — it results in a direct, unauthorized transfer of value from the maker to the taker. An attacker acting as taker can construct a sell order (`MarketSellAssetContract` via `MarketSellAssetActuator`) to precisely consume the residual `sellTokenQuantityRemain` of a targeted low-priced maker order such that the computed `makerBuyTokenQuantityReceive` rounds to zero. The attacker (taker) receives the maker's tokens (`addTrxOrToken(takerOrderCapsule, takerBuyTokenQuantityReceive, ...)`) while the maker's matching order is closed out (`State.INACTIVE`) with zero payment credited and no refund of the consumed remainder — a permanent, uncompensated loss of the maker's assets and unjust enrichment of the attacker. This qualifies as theft of funds reachable via a single signed `MarketSellAssetContract` transaction from any account, requiring no special privileges.

### Likelihood Explanation
Exploitation requires:
1. An existing maker order with a low unit price (`sellTokenQuantity` >> `buyTokenQuantity`) that has been partially filled down to a small remainder (this can be engineered by the attacker themselves by first partially filling their own decoy maker order, or by waiting for/targeting third-party orders with small remainders after natural partial fills).
2. A taker order crafted so `takerBuyTokenQuantityRemain` exactly equals the maker's residual `sellTokenQuantityRemain`.

Both conditions are fully attacker-controllable (the attacker can create the maker order themselves, partially fill it via a throwaway taker order to leave a rounding-favorable remainder, then use a separate account/order to consume the dust remainder), making this practically exploitable with moderate transaction crafting and no reliance on other participants.

### Recommendation
In the "taker == maker" branch of `matchSingleOrder` in `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`, add the same zero-amount guard used in the "taker > maker" branch: if `makerBuyTokenQuantityReceive == 0`, refund the maker's remaining sell tokens via `MarketUtils.returnSellTokenRemain` instead of finalizing the trade with zero payment. More broadly, disallow order matches (maker or taker side) that would settle with a computed receive amount of less than one token unit, consistent with the remediation applied for the analogous Neutron limit-order rounding issue.

### Proof of Concept
1. Attacker creates Maker Order M: sell 1,000,000 of Token A for 1 of Token B (`sellTokenQuantity=1,000,000`, `buyTokenQuantity=1`).
2. Attacker (or colluding account) submits a Taker Order T1 that fills 999,999 of Token A from M, leaving `sellTokenQuantityRemain = 1` on M (the "taker < maker" branch handles this partial fill without issue, since `makerBuyTokenQuantityReceive` there is taken directly from `takerOrderCapsule.getSellTokenQuantityRemain()`, not floor-divided).
3. Attacker submits Taker Order T2 with `takerBuyTokenQuantityRemain` computed (via `MarketUtils.multiplyAndDivide`) to equal exactly `1` (M's remaining sell quantity), entering the "taker == maker" branch.
4. `makerBuyTokenQuantityReceive = multiplyAndDivide(1, 1, 1,000,000) = floor(1/1,000,000) = 0`.
5. M is marked `INACTIVE` with `sellTokenQuantityRemain=0`; `addTrxOrToken(M, 0)` credits the maker nothing; the taker (attacker) receives the final 1 unit of Token A via `addTrxOrToken(takerOrderCapsule, 1, ...)` for free, permanently taking the maker's last unit of Token A with zero payment and no refund path triggered.

  public static long multiplyAndDivide(long a, long b, long c, boolean disableMath) {
    try {
      long tmp = multiplyExact(a, b, disableMath);
      return floorDiv(tmp, c, disableMath);
    } catch (ArithmeticException ex) {
      // do nothing here, because we will use BigInteger to compute again
    }

    BigInteger aBig = BigInteger.valueOf(a);
    BigInteger bBig = BigInteger.valueOf(b);
    BigInteger cBig = BigInteger.valueOf(c);

    return aBig.multiply(bBig).divide(cBig).longValue();
  }
