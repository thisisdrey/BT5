### Title
Active-permission signer can execute `AccountPermissionUpdateContract` and seize full account control — (`File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
`AccountPermissionUpdateActuator.validate()` never checks which permission (`permissionId`) was used to authorize the transaction. As a result, a transaction that overwrites an account's `Owner` permission, `Witness` permission, and all `Active` permissions can be signed with a low-trust `Active` permission key instead of the `Owner` key, provided that `Active` permission's operation bitmap happens to allow the `AccountPermissionUpdateContract` type. This mirrors the Kimai bug class: a credential/permission representing an intermediate, restricted trust level (the "Active" key, analogous to the pre-2FA session) is accepted by a check that should only be satisfied by the highest trust level (the "Owner" key, analogous to the fully-2FA'd session), because the guard tests only generic sufficiency (signature weight ≥ threshold, operation bit set) rather than the specific completed/elevated state required for the sensitive action.

### Finding Description
- The actuator that performs the most sensitive operation on an account — rewriting `Owner`, `Witness`, and all `Active` permission structures — is `AccountPermissionUpdateActuator`. [1](#0-0) 
- Its `validate()` method checks the structural validity of the new `Owner`/`Witness`/`Active` permissions (key counts, weights, threshold, operations bitmap for the *new* permissions being installed) but never inspects `contract.getPermissionId()` — i.e., it never enforces that the transaction itself must have been authorized under permission id `0` (`Owner`). [2](#0-1) 
- The actual authorization gate that decides whether a signature is sufficient to run *any* actuator (including this one) lives generically in `TransactionCapsule.validateSignature`/`checkWeight`/`checkPermission`. This code resolves whichever `permission` corresponds to `contract.getPermissionId()` on the account, and if `permissionId != 0` it merely confirms the permission's `type == Active` and that the contract type's bit is set in that permission's `operations` bitmap — it does not special-case `AccountPermissionUpdateContract` as an owner-only operation. [3](#0-2) [4](#0-3) 
- The `Active` permission's `operations` bitmap is validated only against `dynamicStore.getAvailableContractType()` — the set of all currently-enabled contract types on chain — with no exclusion carved out for `AccountPermissionUpdateContract`. [5](#0-4) 
- Consequently, if any `Active` key on the account has (by design or misconfiguration, or because the account owner granted broad operation rights to a delegated/active key at some point) the `AccountPermissionUpdateContract` bit set, that Active key — which is meant to be a restricted, lower-trust key (e.g., for smart-contract calls or transfers) — can sign a transaction that replaces the account's `Owner` key entirely, replaces all `Active` permissions, and (if a witness) the `Witness` key, fully locking out the legitimate owner and taking over the account. This is a strict privilege escalation from "limited operational key" to "root/owner key," analogous to the Kimai flaw where a pre-2FA (partial-trust) session token was accepted for a fully-privileged action.

### Impact Explanation
Successful exploitation permits unauthorized account takeover: an attacker who compromises or is granted only an `Active` key (intended for restricted delegated operations) can overwrite the `Owner` permission and lock the true owner out, or insert additional attacker-controlled keys with full authority, leading to unauthorized transfers, freezing of funds, or governance/witness credential hijack. This satisfies "concrete unauthorized account operation" and potential "theft or permanent freezing of funds."

### Likelihood Explanation
Exploitability depends on an `Active` permission having the `AccountPermissionUpdateContract` bit enabled in its operations bitmap. This is not blocked at any layer (signing library, actuator validation, or wallet API) — nothing in `checkPermission`/`checkPermissionOperations`/`AccountPermissionUpdateActuator.validate()` special-cases or forbids this bit for non-owner permissions. Any account owner (intentionally or via a permission-management UI default/misclick) who grants a broad "all contract types" active permission to a delegated key — a common multi-sig/delegation pattern for automation — is exposed. No consensus or witness collusion is required; this is reachable purely via a single signed transaction from an unprivileged account holder or a party holding a leaked/delegated active key.

### Recommendation
In `AccountPermissionUpdateActuator.validate()` (and defensively in `TransactionCapsule.checkPermission`), explicitly require `contract.getPermissionId() == 0` (i.e., the transaction must be authorized by the account's `Owner` permission) for `AccountPermissionUpdateContract`, regardless of what bits are set in any `Active` permission's operations bitmap. Treat `AccountPermissionUpdateContract` as a reserved, owner-only operation type that cannot be delegated via the `Active` permission mechanism, analogous to disallowing a partial-trust credential from performing the account's highest-privilege action.

### Proof of Concept
1. Account `A` has `Owner` permission (key `O`, weight 1, threshold 1) and an `Active` permission (id 2) with key `K` (weight 1, threshold 1) whose `operations` bitmap includes the bit for `AccountPermissionUpdateContract` (e.g., because the owner granted `K` broad "all contract" rights for automation).
2. Attacker who controls only `K` (not `O`) constructs an `AccountPermissionUpdateContract` transaction for account `A` that sets a brand-new `Owner` permission containing only the attacker's key `E`, replaces `Active` permissions with attacker-controlled keys, and sets `contract.getPermissionId() = 2`.
3. Sign the transaction with `K`. `TransactionCapsule.validateSignature` resolves permission id 2 (`Active`), confirms `type == Active`, confirms the `AccountPermissionUpdateContract` bit is set via `checkPermissionOperations`, and confirms `weight(K) >= threshold` — signature validation succeeds. [3](#0-2) 
4. `AccountPermissionUpdateActuator.validate()` performs no check on `contract.getPermissionId()`, so it passes, and `execute()` calls `account.updatePermissions(...)`, overwriting `Owner`/`Witness`/`Active` permissions with the attacker's chosen keys. [6](#0-5) 
5. Broadcast via `wallet/broadcasttransaction` (`BroadcastServlet`/`Wallet.broadcastTransaction`); the account is now controlled solely by the attacker's key `E`, and the legitimate owner `O` is permanently locked out. [7](#0-6)

  @Override
  public boolean validate() throws ContractValidateException {

    if (chainBaseManager == null) {
      throw new ContractValidateException(ActuatorConstant.STORE_NOT_EXIST);
    }

    if (this.any == null) {
      throw new ContractValidateException(ActuatorConstant.CONTRACT_NOT_EXIST);
    }

    AccountStore accountStore = chainBaseManager.getAccountStore();
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();

    if (dynamicStore.getAllowMultiSign() != 1) {
      throw new ContractValidateException("multi sign is not allowed, "
          + "need to be opened by the committee");
    }
    if (!this.any.is(AccountPermissionUpdateContract.class)) {
      throw new ContractValidateException(
          "contract type error,expected type [AccountPermissionUpdateContract],real type["
              + any.getClass() + "]");
    }
    final AccountPermissionUpdateContract accountPermissionUpdateContract;
    try {
      accountPermissionUpdateContract = any.unpack(AccountPermissionUpdateContract.class);
    } catch (InvalidProtocolBufferException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractValidateException(e.getMessage());
    }
    byte[] ownerAddress = accountPermissionUpdateContract.getOwnerAddress().toByteArray();
    if (!DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("invalidate ownerAddress");
    }
    AccountCapsule accountCapsule = accountStore.get(ownerAddress);
    if (accountCapsule == null) {
      throw new ContractValidateException("ownerAddress account does not exist");
    }

    if (!accountPermissionUpdateContract.hasOwner()) {
      throw new ContractValidateException("owner permission is missed");
    }

    if (accountCapsule.getIsWitness()) {
      if (!accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("witness permission is missed");
      }
    } else {
      if (accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("account isn't witness can't set witness permission");
      }
    }

    if (accountPermissionUpdateContract.getActivesCount() == 0) {
      throw new ContractValidateException("active permission is missed");
    }
    if (accountPermissionUpdateContract.getActivesCount() > 8) {
      throw new ContractValidateException("active permission is too many");
    }

    Permission owner = accountPermissionUpdateContract.getOwner();
    Permission witness = accountPermissionUpdateContract.getWitness();
    List<Permission> actives = accountPermissionUpdateContract.getActivesList();

    if (owner.getType() != PermissionType.Owner) {
      throw new ContractValidateException("owner permission type is error");
    }
    checkPermission(owner);
    if (accountCapsule.getIsWitness()) {
      if (witness.getType() != PermissionType.Witness) {
        throw new ContractValidateException("witness permission type is error");
      }
      checkPermission(witness);
    }
    for (Permission permission : actives) {
      if (permission.getType() != PermissionType.Active) {
        throw new ContractValidateException("active permission type is error");
      }
      checkPermission(permission);
    }
    return true;
  }

  public static boolean validateSignature(Transaction transaction,
      byte[] hash, AccountStore accountStore, DynamicPropertiesStore dynamicPropertiesStore)
      throws PermissionException, SignatureException, SignatureFormatException {
    Transaction.Contract contract = transaction.getRawData().getContractList().get(0);
    int permissionId = contract.getPermissionId();
    byte[] owner = getOwner(contract);
    AccountCapsule account = accountStore.get(owner);
    Permission permission = null;
    if (account == null) {
      if (permissionId == 0) {
        permission = AccountCapsule.getDefaultPermission(ByteString.copyFrom(owner));
      }
      if (permissionId == 2) {
        permission = AccountCapsule
            .createDefaultActivePermission(ByteString.copyFrom(owner), dynamicPropertiesStore);
      }
    } else {
      permission = account.getPermissionById(permissionId);
    }
    if (permission == null) {
      throw new PermissionException("permission isn't exit");
    }
    checkPermission(permissionId, permission, contract);
    long weight = checkWeight(permission, transaction.getSignatureList(), hash, null);
    if (weight >= permission.getThreshold()) {
      return true;
    }
    return false;
  }
