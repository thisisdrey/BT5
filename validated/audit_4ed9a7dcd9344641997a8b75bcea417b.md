### Title
Missing storage-match validation in `LinkRepositoryToObjectPool` allows cross-storage alternates injection - (File: internal/gitaly/service/objectpool/link.go)

### Summary
`LinkRepositoryToObjectPool` links a caller-specified object pool repository to a caller-specified target repository by computing a relative filesystem path between them and writing it into the target's Git `alternates` file, but the RPC handler itself never verifies that the pool and the target repository reside on the same storage. This mirrors the reported bug class: a caller-controlled value is used to complete a sensitive state transition (granting object access, analogous to granting ownership without verifying the paid amount) without validating it against the expected/required invariant (same-storage relationship) at the point where the trust decision is made.

### Finding Description
`LinkRepositoryToObjectPool` (`internal/gitaly/service/objectpool/link.go`) only validates that the target repository is a valid repository via `s.locator.ValidateRepository`, then resolves the pool via `s.poolForRequest`, which itself only checks that the pool's own storage exists and the pool is a valid Git directory (`internal/gitaly/service/objectpool/util.go`, `objectpool.FromProto`). Neither of these checks asserts that `req.GetObjectPool().GetRepository().GetStorageName() == req.GetRepository().GetStorageName()`. [1](#0-0) [2](#0-1) 

Contrast this with the sibling RPC `FetchIntoObjectPool`, which explicitly guards against this exact condition: [3](#0-2) 

`Link` (`internal/git/objectpool/link.go`) then computes the alternates content purely via `filepath.Rel` between the pool's and repo's on-disk object directories, with no storage-boundary check: [4](#0-3) 

The only cross-storage protection that exists in the codebase is enforced in the gRPC transaction middleware (`internal/gitaly/storage/storagemgr/middleware.go`), which computes an "additional repository" from the request's `additional_repository`-annotated field (the object pool, per `LinkRepositoryToObjectPoolRequest`'s proto annotation) and rejects the call with `ErrRepositoriesInDifferentStorages` if its storage differs from the target repository's storage: [5](#0-4) 

This means the storage-match invariant is enforced only incidentally, as a side effect of the transaction-manager (WAL) middleware picking up the proto field annotation — not as an explicit validation inside the `ObjectPoolService` RPC handler or the underlying `objectpool.Link`/`linkedToRepository` logic itself. Just like `transfer_nft`, which never directly checks "does the bid amount equal the listed price" at the point where the trade is finalized (relying instead on incidental/absent side checks), `LinkRepositoryToObjectPool` and `objectpool.Link` never directly check "is the pool on the same storage as the repository" at the point where the alternates link (a trust/access relationship) is established.

### Impact Explanation
If this RPC is ever reached without the transaction-manager's incidental additional-repository check applying (e.g., a code path, deployment mode, or future refactor where the WAL/partition middleware is bypassed, disabled, or where the additional-repository extraction fails to match reality), an attacker who controls a target repository could request that it be linked to an object pool located on a *different* storage. Because `getRelativeObjectPath` blindly joins paths via `filepath.Rel` without confirming both repositories share a storage root, this can write an alternates entry that, depending on relative storage layout, may not point back into the same storage tree — a violation of the storage isolation the locator's `ValidateRelativePath` mechanism is designed to enforce elsewhere in the codebase. The result is unauthorized cross-repository/cross-storage object access: a repository could dedupe/read objects from a pool the caller does not actually control, undermining the object quarantine and per-storage isolation guarantees documented in `doc/object_quarantine.md`.

### Likelihood Explanation
The direct RPC handler validation gap is concretely present in the shipped code today (`link.go` and `util.go`), and is unprivileged-reachable via the `ObjectPoolService.LinkRepositoryToObjectPool` gRPC call, an RPC ordinary GitLab-side callers (e.g. fork creation flows) invoke. However, exploitability in the current default (WAL-transaction) deployment is mitigated by the middleware's incidental use of the proto `additional_repository` annotation, which is a different enforcement layer than the RPC's own logic. I could not fully verify whether all deployment configurations (e.g. non-WAL/legacy transaction paths, or any other caller of the underlying `objectpool.Link` function) always route through this middleware check, so likelihood is assessed as low-to-moderate and contingent on that middleware always being active for this RPC.

### Recommendation
Add an explicit, defense-in-depth storage-match validation directly in `LinkRepositoryToObjectPool` (`internal/gitaly/service/objectpool/link.go`) and/or inside `objectpool.Link`/`linkedToRepository` (`internal/git/objectpool/link.go`), mirroring the check already present in `validateFetchIntoObjectPoolRequest`:
```go
if req.GetObjectPool().GetRepository().GetStorageName() != req.GetRepository().GetStorageName() {
    return nil, structerr.NewInvalidArgument("object pool and repository are on different storages")
}
```
Do not rely solely on the transaction middleware's incidental use of proto field annotations to enforce this invariant, since that ties correctness of an authorization/isolation boundary to an unrelated concern (transaction partitioning).

### Proof of Concept
Not independently reproduced in this analysis (no execution environment available). The gap is demonstrated statically by comparing `LinkRepositoryToObjectPool`'s validation path (`internal/gitaly/service/objectpool/link.go` + `util.go`, no storage check) against `FetchIntoObjectPool`'s explicit `validateFetchIntoObjectPoolRequest` (`internal/gitaly/service/objectpool/fetch_into_object_pool.go:102-118`), which performs the exact same-storage check that `LinkRepositoryToObjectPool` omits. A concrete PoC would involve configuring two storages, creating a pool repository on storage B and a target repository on storage A, and issuing `LinkRepositoryToObjectPoolRequest{Repository: <storage A repo>, ObjectPool: <storage B pool>}` in a context where the transaction middleware's additional-repository storage check does not intervene, then inspecting the resulting `objects/info/alternates` file for a path that resolves outside storage A.

func (s *server) LinkRepositoryToObjectPool(ctx context.Context, req *gitalypb.LinkRepositoryToObjectPoolRequest) (*gitalypb.LinkRepositoryToObjectPoolResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	pool, err := s.poolForRequest(ctx, req)
	if err != nil {
		return nil, err
	}

	repo := s.localRepoFactory.Build(repository)

	if err := pool.Link(ctx, repo); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	return &gitalypb.LinkRepositoryToObjectPoolResponse{}, nil
}

func (s *server) poolForRequest(ctx context.Context, req PoolRequest) (*objectpool.ObjectPool, error) {
	pool, err := objectpool.FromProto(ctx, s.logger, s.locator, s.gitCmdFactory, s.catfileCache, s.txManager, s.housekeepingManager, req.GetObjectPool())
	if err != nil {
		if errors.Is(err, objectpool.ErrInvalidPoolDir) {
			return nil, errInvalidPoolDir
		}

		if errors.Is(err, objectpool.ErrInvalidPoolRepository) {
			return nil, structerr.NewFailedPrecondition("%w", err)
		}

		return nil, structerr.NewInternal("%w", err)
	}

	return pool, nil
}

func validateFetchIntoObjectPoolRequest(req *gitalypb.FetchIntoObjectPoolRequest) error {
	if req.GetOrigin() == nil {
		return errors.New("origin is empty")
	}

	if req.GetObjectPool() == nil {
		return errors.New("object pool is empty")
	}

	originRepository, poolRepository := req.GetOrigin(), req.GetObjectPool().GetRepository()

	if originRepository.GetStorageName() != poolRepository.GetStorageName() {
		return errors.New("origin has different storage than object pool")
	}

	return nil
}

func getRelativeObjectPath(ctx context.Context, pool, repo *localrepo.Repo) (string, error) {
	poolPath, err := pool.Path(ctx)
	if err != nil {
		return "", fmt.Errorf("getting object pool path: %w", err)
	}

	repoPath, err := repo.Path(ctx)
	if err != nil {
		return "", fmt.Errorf("getting repository path: %w", err)
	}

	relPath, err := filepath.Rel(filepath.Join(repoPath, "objects"), poolPath)
	if err != nil {
		return "", err
	}

	return filepath.Join(relPath, "objects"), nil
}
