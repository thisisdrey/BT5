### Title
Market orders become permanently unrecoverable if `ALLOW_MARKET_TRANSACTION` is toggled off after order placement - (File: actuator/src/main/java/org/tron/core/actuator/MarketCancelOrderActuator.java)

### Summary
The ThunderNFT report shows that a pool checks an admin-controlled "supported asset" flag both when assets enter the pool (`deposit`) and when they must leave it (`withdraw`); once the admin revokes support after a user has deposited, the withdraw check reverts forever, freezing the user's already-escrowed funds. The java-tron market-order subsystem has the same structural pattern: order creation and order cancellation both gate on the same committee-controlled dynamic parameter, `supportAllowMarketTransaction()`.

### Finding Description
`MarketSellAssetActuator.validate()` requires `dynamicStore.supportAllowMarketTransaction()` to place/escrow an order (the "deposit" side), and `MarketCancelOrderActuator.validate()` requires the exact same flag to cancel an order and reclaim the escrowed sell-token (the "withdraw" side): [1](#0-0) 

The same guard exists in the order-creation path: [2](#0-1) 

`ALLOW_MARKET_TRANSACTION` is a proposal-controlled dynamic property, referenced by `ProposalUtil.java`, `DynamicPropertiesStore.java`, and `ProposalService.java`. Once market orders exist (tokens already deducted from the seller's balance and held in escrow within `MarketOrderCapsule`/`MarketPairPriceToOrderStore`), the only exit path for the seller to reclaim escrowed tokens without a match is `MarketCancelOrderActuator`. Because this actuator enforces the identical global flag as order creation, any committee action that flips `supportAllowMarketTransaction()` back to disabled after orders are outstanding removes the only mechanism (cancel) that returns the seller's escrowed tokens — mirroring exactly the ThunderNFT root cause: a single support/whitelist flag is checked identically on both the entry and exit paths, so revoking it after entry permanently locks funds that are already inside the system.

I was not able to fully confirm within this session whether `ALLOW_MARKET_TRANSACTION` is implemented as a one-way, monotonic switch (like `ALLOW_SAME_TOKEN_NAME`, which the codebase's `ExchangeWithdrawActuatorTest` shows can only move from disabled→enabled and never back) or whether committee proposals can freely toggle it back to `0` after being set to `1`. That distinction is critical to the exploitability of this analog and requires inspecting `ProposalUtil.java`'s validation branch for this specific parameter, which I could not retrieve in this session.

### Impact Explanation
If the flag can be disabled again after being enabled, every account with an open, unfilled market order at the time of disablement has its escrowed sell-token quantity permanently frozen: it cannot be canceled (`MarketCancelOrderActuator.validate` reverts) and it cannot be matched by a new taker (`MarketSellAssetActuator.validate` also gates on the same flag, so no new orders/matches can be created while disabled). This is a permanent freezing-of-funds condition reachable by any unprivileged order-placer whose funds are already escrowed when the switch flips.

### Likelihood Explanation
Likelihood is directly proportional to whether the committee/proposal mechanism permits re-disabling `ALLOW_MARKET_TRANSACTION` after enabling it. If it is a monotonic one-way switch (consistent with the precedent set by `ALLOW_SAME_TOKEN_NAME` elsewhere in the codebase), this analog is not practically exploitable and likelihood is low/none. If proposals can toggle it in either direction at will, likelihood is high, since it only requires a single governance action with no additional attacker input.

### Recommendation
- Confirm in `ProposalUtil.java` whether `ALLOW_MARKET_TRANSACTION` validation permits transitioning from `1` back to `0`. If it does, either make it a one-way switch (matching `ALLOW_SAME_TOKEN_NAME` semantics) or exempt `MarketCancelOrderActuator` from the `supportAllowMarketTransaction()` check so users can always withdraw/cancel escrowed assets even when new order creation/matching is paused.
- More generally, any "kill switch" or whitelist-style dynamic property that gates entry into an escrow/pool should not also gate the corresponding exit/refund/cancel path; exit paths should remain available regardless of the current state of the entry-gating flag.

### Proof of Concept
1. Committee proposal enables `ALLOW_MARKET_TRANSACTION` (`supportAllowMarketTransaction() == true`).
2. User A calls `MarketSellAssetContract` via `MarketSellAssetActuator`, escrowing `sellTokenQuantity` of `sellTokenId`; no matching maker order exists, so the order remains active in `MarketOrderStore`/`MarketPairPriceToOrderStore`. [3](#0-2) 
3. Committee proposal disables `ALLOW_MARKET_TRANSACTION`.
4. User A submits `MarketCancelOrderContract` to reclaim the escrowed tokens; `MarketCancelOrderActuator.validate()` throws `"Not support Market Transaction, need to be opened by the committee"` before reaching the refund logic (`MarketUtils.returnSellTokenRemain`), leaving the tokens permanently locked in escrow.
