### Title
Repository write-lock TTL expiry lets a contending transaction "steal" an in-use lock during network/DB congestion, reintroducing the cross-node ref-lock deadlock Serialized Writes is meant to prevent - ([File: internal/praefect/datastore/lock_manager.go])

### Summary
Praefect's Serialized Writes feature is supposed to guarantee that only one write transaction can be inside the "on-disk ref lock" critical section for a given repository at a time, avoiding the classic two-node crossed-lock deadlock described in `doc/serialized_writes.md`. The mutual exclusion is implemented as a PostgreSQL row with a hard TTL (`expired_at`, fixed 20s), not as a true exclusive lock tied to the lifetime of the holder. If the holder is slow to renew (e.g. under network congestion, DB latency, or a large/slow `git-update-ref` transaction), the row is treated as free and another transaction can acquire it while the original holder is still mid-flight and has already taken real on-disk Git ref locks, defeating the very serialization guarantee the feature exists to provide.

### Finding Description
The write lock is acquired at `PREPARING_PHASE` and is expected to be renewed at `PREPARED_PHASE`: [1](#0-0) 

`renew` extends `expired_at` by `renewInterval` (hard-coded to 20 seconds), but if renewal is late enough that a competitor's `tryLock` UPSERT already stole the row (`WHERE locks.expired_at < NOW() OR locks.holder_txn_id = $2`), `renew` fails and the row now belongs to a different `txnID`: [2](#0-1) [3](#0-2) 

Crucially, by the time `PREPARED_PHASE` fires and Praefect calls `renew`, the Gitaly node has *already taken the real, local, on-disk Git ref lock*, because the reference-transaction hook for `Prepared` runs after `updater.Prepare()`: [4](#0-3) 

So the sequence under congestion is:
1. Transaction A wins `PREPARING_PHASE` for repo R, acquires the Postgres write lock, votes `Preparing`.
2. A calls `updater.Prepare()`, which locks refs on-disk locally. This step, or the DB round-trip for the earlier steps, is slow (network/DB congestion, big push, GC/disk contention) and exceeds the 20s TTL.
3. Transaction B (any other client pushing/updating refs on the same repo) sends `PREPARING_PHASE` for repo R. Because A's row is now `expired_at < NOW()`, B's UPSERT succeeds and B is granted the lock — while A is still actively holding the real on-disk lock and has not finished.
4. B proceeds to lock the same repo's refs on-disk on a Gitaly node, potentially interleaved with A across the multi-node replica set exactly as the deadlock scenario documented in `doc/serialized_writes.md` describes (Node1: A locks ref X, B locks ref Y; Node2: B locks ref X, A locks ref Y).
5. A's later `renew` call at `PREPARED_PHASE` fails (`no rows`), causing A's transaction to error out, but only after A has already raced against B at the OS/git level; both transactions may already be blocked on each other's on-disk locks on different nodes, hanging.

This is directly analogous to the reported bug class: a time-bound safeguard (bid expiry / auction deadline) is enforced without accounting for congestion, allowing a "low cost" competitor to seize control of a shared resource while the legitimate holder is still mid-operation, defeating the intended mutual-exclusion/anti-collision guarantee.

### Impact Explanation
This can cause a denial of service against Gitaly/Praefect write RPC handlers for the affected repository (and potentially cluster-wide, since the deadlock is the very cross-node scenario the whole feature exists to prevent): two ordinary users' concurrent pushes to the same repository, under nothing more than normal network/DB congestion (no privileged access, no malicious peer needed), can trigger crossed on-disk ref locks across replica nodes, hanging both write RPCs until client/gRPC timeouts. Because `cleanUpExpiredRepoRefWriteLocks` only sweeps every 40 seconds and the TTL is a fixed, non-adaptive 20 seconds, any congestion event lasting longer than that window is sufficient.

### Likelihood Explanation
Likelihood is moderate: it requires two concurrent write transactions to the same repository plus congestion sufficient to delay a renew beyond 20 seconds (large pushes with many ref updates, slow disks, GC pauses, or Postgres latency spikes are all realistic, unprivileged triggers reachable from ordinary git pushes). No attacker privilege or malicious peer/node is required — this can happen organically or be intentionally amplified by an ordinary user submitting a slow, large push to increase the odds of exceeding the TTL window.

### Recommendation
Do not rely purely on a fixed wall-clock TTL to represent mutual exclusion for an operation whose true duration is variable and congestion-dependent. Options: make the renew interval adaptive/heartbeat-based with a much larger grace period tied to actual operation progress, fence the on-disk lock acquisition with the same lock token, so a stolen Postgres row cannot let a second transaction proceed to on-disk locking while the original holder is still alive (e.g. via lease fencing tokens checked at ref-lock time), or increase the TTL safety margin and add explicit detection/backoff instead of silent lock stealing while a holder may still be active. Ensure the failure path (`renew` failing) actively signals the still-in-flight Gitaly node to abort its in-progress `updater.Prepare()`/on-disk lock immediately rather than only failing at the next hook phase.

### Proof of Concept
1. Configure Praefect with `PraefectSerializedWrite` enabled and Serialized Writes active (Git ≥ 2.54 with `preparing` phase support).
2. Start a large push (many ref updates) to repository R that is slow enough server-side (e.g. many refs, slow disk, or artificially delay `git-update-ref`) such that the time between `PREPARING_PHASE` and the `PREPARED_PHASE` renew exceeds 20 seconds — this can be done deterministically in a test by pausing the renew call.
3. Concurrently start a second push to the same repository R from a different client.
4. Observe that `tryLock`'s `WHERE locks.expired_at < NOW()` allows the second transaction to acquire the lock (`internal/praefect/datastore/lock_manager.go:313-320`) while the first transaction still holds real on-disk ref locks from `updater.Prepare()` (`internal/gitaly/hook/updateref/update_with_hooks.go:283`), producing lock contention/deadlock symptoms (both pushes hang or time out) instead of the fully serialized, deadlock-free behavior the feature is documented to guarantee.

func (r *RepoReferenceWriteLockManager) tryLock(ctx context.Context, virtualStorage, relativePath string, txnID uint64,
) tryLockResult {
	lockID := repoLockID(virtualStorage, relativePath)
	// Register for a lock release notification before attempting the INSERT, so
	// that no release event can be missed between a failed attempt and the caller
	// beginning to wait, thus eliminating the race window between contention detection
	// and notification.
	notificationCh, deregister := r.handler.RegisterForLockRelease(lockID)

	query := `
INSERT INTO repository_reference_write_locks as locks (lock_id, holder_txn_id, expired_at)
VALUES ($1, $2, NOW() + $3::interval)
ON CONFLICT (lock_id) DO UPDATE
  SET holder_txn_id = EXCLUDED.holder_txn_id,
      expired_at    = EXCLUDED.expired_at
WHERE locks.expired_at < NOW() OR locks.holder_txn_id = $2
RETURNING lock_id, holder_txn_id, expired_at;`

	start := time.Now()
	rows, err := r.qc.QueryContext(ctx, query, lockID, txnID, r.renewInterval)
	r.operationDuration.WithLabelValues(virtualStorage, "trylock").Observe(time.Since(start).Seconds())
	if err != nil {
		r.lockAcquiredTotal.WithLabelValues(virtualStorage, "error").Inc()
		deregister()
		return tryLockResult{
			Acquired: false,
			Err:      fmt.Errorf("acquire repo reference write lock: %s, %w", lockID, err),
		}
	}
	defer func() {
		if err := rows.Close(); err != nil {
			r.logger.WithError(err).Error("close rows")
		}
	}()
	if rows.Next() {
		_, alreadyHeld := r.lockAcquiredAt.LoadOrStore(lockID, time.Now())
		if !alreadyHeld {
			r.locksHeld.WithLabelValues(virtualStorage).Inc()
			r.lockAcquiredTotal.WithLabelValues(virtualStorage, "new_acquisition").Inc()
		}
		deregister()
		unlockFn := func() error {
			return r.unlock(virtualStorage, relativePath, txnID)
		}
		renewFn := func(renewCtx context.Context) error {
			return r.renew(renewCtx, virtualStorage, relativePath, txnID)
		}
		return tryLockResult{
			Acquired: true,
			Unlock:   unlockFn,
			Renew:    renewFn,
		}
	}

// renew extends the expiry of the write lock held by txnID by another renewInterval.
// It returns an error if the lock is not currently held by txnID.
func (r *RepoReferenceWriteLockManager) renew(ctx context.Context, virtualStorage string, relativePath string, txnID uint64) error {
	query := `
UPDATE repository_reference_write_locks as locks
SET  expired_at = (NOW() + $3::interval)
WHERE locks.lock_id = $1 AND holder_txn_id = $2
RETURNING expired_at;
`
	lockID := repoLockID(virtualStorage, relativePath)
	start := time.Now()
	rows, err := r.qc.QueryContext(ctx, query, lockID, txnID, r.renewInterval)
	r.operationDuration.WithLabelValues(virtualStorage, "renew").Observe(time.Since(start).Seconds())
	if err != nil {
		return fmt.Errorf("renew repo reference write lock (executing query): %s, %w", lockID, err)
	}
	defer func() {
		if err := rows.Close(); err != nil {
			r.logger.WithError(err).Error("close rows")
		}
	}()
	if rows.Next() {
		return nil
	}
	if err := rows.Err(); err != nil {
		return fmt.Errorf("renew repo reference write lock (iterating rows): %s, %w", lockID, err)
	}
	return fmt.Errorf("renew repo reference write lock (no rows): %s", lockID)
