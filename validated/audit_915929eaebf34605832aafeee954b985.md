### Title
Reserve-ratio manipulation via floor-to-zero rounding in `ExchangeInjectActuator` - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
The bancor-style token exchange pool implemented by `ExchangeCreateActuator`/`ExchangeInjectActuator`/`ExchangeTransactionActuator` is directly analogous to the vault "first depositor / donation" pattern described in the report: a reserve ratio is used to compute an amount owed, and integer flooring of that computation can be driven to zero, letting a party contribute to (or manipulate) the pool for free while the pool's recorded balances are updated as if a fair, proportional contribution had occurred.

### Finding Description
`ExchangeInjectActuator` lets the creator of an exchange add liquidity to one side of the pool; the actuator computes the proportional amount that must be added to the other side using plain integer `floorDiv`: [1](#0-0) 

When `tokenQuant * otherBalance < ownBalance` (i.e., the injected quantity is small relative to the reserve ratio), `floorDiv` truncates `anotherTokenQuant` to `0`. The resulting call:
```
exchangeCapsule.setBalance(addExact(firstTokenBalance, tokenQuant), addExact(secondTokenBalance, anotherTokenQuant));
```
still increases the balance of the injected token by the full `tokenQuant` while leaving the other side of the reserve completely untouched, because `anotherTokenQuant == 0`. This is a direct parallel to the report's flooring bug where `to_b_token_down` truncates `b_tokens_minted` to zero for a depositor due to a skewed reserve ratio — here the "amount owed on the other side" is truncated to zero instead of being blocked.

Unlike the sibling `ExchangeWithdrawActuator`, which explicitly rejects a zero result: [2](#0-1) 

`ExchangeInjectActuator`'s `doValidate()` never checks `anotherTokenQuant <= 0` for a rejection before `execute()` commits the skewed balances (only checks that `tokenQuant > 0` and that the token exists in the pool): [3](#0-2) 

By repeatedly injecting the smallest possible `tokenQuant` on the side with the larger balance, an exchange creator can silently shift the recorded reserve ratio of `firstTokenBalance`/`secondTokenBalance` in `ExchangeCapsule` without contributing anything to the other side. Since `ExchangeTransactionActuator.execute` prices every subsequent swap purely off these two stored balances via `ExchangeProcessor`/bancor formula: [4](#0-3) 

a creator can skew the exchange rate for free, then trade against unsuspecting counterparties at a manipulated price via `ExchangeTransactionContract`, extracting value from other token holders trading on that pool.

### Impact Explanation
An exchange creator (an unprivileged, self-service actor who only needs to broadcast an `ExchangeCreateContract` followed by repeated `ExchangeInjectContract` transactions) can distort a public AMM-like pool's price for free, then exploit that manipulated price against other users trading in the same pool via `ExchangeTransactionContract`, resulting in unbacked/incorrect balances and financial loss for counterparties — matching the "unbacked balance / theft of funds" impact class.

### Likelihood Explanation
The precondition (integer truncation of `anotherTokenQuant` to 0) is trivially reachable by choosing `tokenQuant` small relative to the current reserve ratio, which any exchange creator fully controls at pool creation and subsequent injections. No special privileges, front-running, or witness/committee compromise are required — only ordinary signed transactions (`ExchangeCreateContract` and `ExchangeInjectContract`).

### Recommendation
Add an explicit check in `ExchangeInjectActuator.doValidate()` (mirroring `ExchangeWithdrawActuator`) that rejects the request when the computed `anotherTokenQuant <= 0`, preventing any injection that would alter one side of the reserve without a proportional, non-zero contribution to the other side.

### Proof of Concept
1. Attacker (as any user) submits `ExchangeCreateContract` creating a pool with a large imbalance, e.g. `firstTokenBalance = 1_000_000_000`, `secondTokenBalance = 1`.
2. Attacker (creator) submits `ExchangeInjectContract` with `tokenId = firstTokenId`, `quant = 1` (or any quantity `< secondTokenBalance/firstTokenBalance` ratio threshold).
3. In `ExchangeInjectActuator.execute`, `anotherTokenQuant = floorDiv(secondTokenBalance * tokenQuant, firstTokenBalance)` evaluates to `0`.
4. The pool balance is updated to `firstTokenBalance += 1`, `secondTokenBalance += 0` — the creator paid `1` unit of the first token and received a ratio shift for free.
5. Attacker repeats step 2/3 (or does it once with a larger `tokenQuant` chosen just under the truncation threshold) to meaningfully skew the ratio, then calls `ExchangeTransactionContract` to swap against the now-mispriced pool, or waits for a victim to trade at the skewed rate, extracting value.
