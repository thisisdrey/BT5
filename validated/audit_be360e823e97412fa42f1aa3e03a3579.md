### Title
Unbounded in-memory buffering of `git-fetch --porcelain` output from an attacker-controlled remote causes memory exhaustion - ([File: internal/gitaly/service/repository/fetch_remote.go])

### Summary
`fetchRemoteAtomic` allocates `stdout`/`stderr` as plain `bytes.Buffer` values and passes them directly as the `Stdout`/`Stderr` writers for `git-fetch --porcelain`, which is invoked against a remote URL fully controlled by the requester via `RemoteParams.Url`. No size cap or streaming/limiting mechanism exists between the untrusted remote's fetch output and this buffer, so a malicious remote advertising an extremely large number of matching refs (default refspec `refs/*:refs/*`) can force Gitaly to buffer arbitrarily large porcelain output in memory before it is ever parsed.

### Finding Description
`fetchRemoteAtomic` declares `var stdout, stderr bytes.Buffer` and wires them into `localrepo.FetchOpts{Stdout: &stdout, Stderr: &stderr, ..., Porcelain: true}` [1](#0-0) . These are passed unchanged into `Repo.FetchRemote`, which wires them directly as the git-fetch process's stdout/stderr via `gitcmd.WithStdout(opts.Stdout)` / `gitcmd.WithStderr(opts.Stderr)` with no wrapping limiter [2](#0-1) . The command only returns after `cmd.Wait()` completes [3](#0-2) , meaning the entire porcelain output for the fetch is written into the `bytes.Buffer` in memory before `fetchRemoteAtomic` scans it line-by-line with `gitcmd.NewFetchPorcelainScanner` [4](#0-3) .

The refspec used is attacker-influenced: if `RemoteParams.MirrorRefmaps` is empty (the default for a plain mirror import), `getRefspecs` returns `["refs/*:refs/*"]`, meaning every ref the malicious remote advertises produces a corresponding porcelain status line [5](#0-4) . The remote URL itself comes straight from `req.GetRemoteParams().GetUrl()` with only a non-empty check performed in `validateFetchRemoteRequest` — no restriction on what server it points to [6](#0-5) . I found no size-capping writer (`LimitWriter`, `io.LimitReader`, `MaxBytes`) applied anywhere along this path in the repository search; the only limiting/truncation utilities found (`internal/log/error_truncator.go`, `internal/gitaly/diff/diff.go`) are unrelated to this code path.

### Impact Explanation
An attacker who can trigger `FetchRemote` against a server they control (e.g., via a mirror-pull import, which end users can configure for their own projects) can cause the git-fetch child process to produce porcelain output proportional to the number of refs the malicious remote advertises. Because this output is fully buffered into an unbounded `bytes.Buffer` before any parsing/processing occurs, a remote advertising millions of refs can drive gitaly-server heap usage very high, risking OOM and process crash — a denial-of-service affecting the Gitaly node and any other repositories/RPCs it serves (matches GitLab's "Denial of Service" bounty impact class for Gitaly RPC handlers).

### Likelihood Explanation
Preconditions are modest: the attacker needs the ability to configure a Gitaly `FetchRemote` (e.g., a repository mirror pointing at an attacker-owned Git server), which is available to ordinary unprivileged GitLab users who can create/import projects with pull mirroring or trigger mirror updates. No special role, secret, or Gitaly/Praefect compromise is required — only an attacker-controlled remote Git server returning a large ref advertisement (trivially reproducible, e.g. with `git update-ref` in a loop or a custom smart-HTTP responder). This makes the finding fully reproducible and repeatable per fetch.

### Recommendation
Bound the size of stdout/stderr captured from `git-fetch`, e.g. wrap the buffers with an `io.LimitedWriter`/custom capped writer that errors out (aborting the fetch) once a configurable maximum (e.g., a few MB, or bytes-per-ref-based cap) is exceeded, or switch to streaming/incremental parsing of the porcelain output via a pipe instead of buffering the entire output before scanning. Additionally, consider capping the number of refspecs/refs processed per fetch and/or applying a request-level ref-count limit negotiated during the fetch (e.g., via `--negotiation-tip`/protocol limits) to prevent unbounded ref advertisements from a hostile remote.

```go
func (s *server) validateFetchRemoteRequest(ctx context.Context, req *gitalypb.FetchRemoteRequest) error {
	if err := s.locator.ValidateRepository(ctx, req.GetRepository()); err != nil {
		return structerr.NewInvalidArgument("%w", err)
	}

	if req.GetRemoteParams() == nil {
		return structerr.NewInvalidArgument("missing remote params")
	}

	if req.GetRemoteParams().GetUrl() == "" {
		return structerr.NewInvalidArgument("blank or empty remote URL")
	}

	return nil
}
```

```go
func getRefspecs(refmaps []string) []string {
	if len(refmaps) == 0 {
		return []string{"refs/*:refs/*"}
	}

	refspecs := make([]string, 0, len(refmaps))

	for _, refmap := range refmaps {
		switch refmap {
		case "all_refs":
			// with `all_refs`, the repository is equivalent to the result of `git clone --mirror`
			refspecs = append(refspecs, "refs/*:refs/*")
		case "heads":
			refspecs = append(refspecs, "refs/heads/*:refs/heads/*")
		case "tags":
			refspecs = append(refspecs, "refs/tags/*:refs/tags/*")
		default:
			refspecs = append(refspecs, refmap)
		}
	}
	return refspecs
}
```
