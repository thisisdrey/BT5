### Title
Reward accrual in `pallet-asset-rewards` is not backed by actual pool balance, causing permanent lock of harvestable rewards - (File: `substrate/frame/asset-rewards/src/lib.rs`)

### Summary
`pallet-asset-rewards` implements a Synthetix-style staking reward pool. `create_pool` and `set_pool_reward_rate_per_block` let the pool admin set an arbitrary `reward_rate_per_block` with no requirement that the pool account actually holds (or will hold) enough `reward_asset_id` to cover the rewards that will accrue over the pool's lifetime. `reward_per_token` / `derive_rewards` accrue purely as a function of `reward_rate_per_block * elapsed_blocks / total_tokens_staked`, decoupled from the pool's actual asset balance. When a staker calls `harvest_rewards`, the pallet computes `staker_info.rewards` from this unchecked accrual and then unconditionally calls `T::Assets::transfer(...)` for that amount — this is functionally identical to the reported `NarwhalPool`/`TradingVaultV2` bug where `notifyRewardAmount`/`setRewardDuration` set a reward rate without verifying/enforcing that the contract holds enough reward tokens, later causing `harvest` to revert with insufficient balance.

### Finding Description
- `create_pool` (call_index 0) accepts an admin-chosen `reward_rate_per_block` and creates the pool with `reward_per_token_stored: 0`, `total_tokens_staked: 0`, without any transfer of reward tokens into the pool account: [1](#0-0) 
- `set_pool_reward_rate_per_block` only checks that the new rate is higher than the old one and that the caller is admin — it never checks the pool's reward-asset balance: [2](#0-1) 
- Funding the pool (`deposit_reward_tokens`) is explicitly optional/"convenience", as documented: "This method is not strictly necessary (tokens could be transferred directly to the pool pot address)": [3](#0-2) 
- The pallet doc itself warns this is the operator's responsibility rather than an enforced invariant: "Care should be taken by the pool operator to keep pool accounts adequately funded with the reward asset": [4](#0-3) 
- Reward accrual (`reward_per_token`) is computed purely from `reward_rate_per_block * elapsed_blocks / total_tokens_staked`, with no reference to the pool's actual token balance: [5](#0-4) 
- `harvest_rewards` computes the staker's accrued reward via `update_pool_and_staker_rewards`/`derive_rewards`, then transfers that (potentially unbacked) amount from the pool account: [6](#0-5) 

This is the same broken invariant described in the report: a rate/accrual mechanism is set independently of whether the promised tokens are actually present, and the "insufficiency" check is deferred to the moment of payout via a plain balance-based transfer, which simply fails instead of preventing the promise from being made in the first place.

### Impact Explanation
When `T::Assets::transfer` fails inside `harvest_rewards` (because the pool account's `reward_asset_id` balance is less than the computed `staker_info.rewards`), the whole extrinsic reverts. Because `staker_info.rewards` is only reset to zero *after* a successful transfer, the staker's reward is not cleared, but since the underlying tokens genuinely do not exist in the pool account, the staker can never successfully harvest until someone tops up the pool via `deposit_reward_tokens`. Any staker who is first to attempt `harvest_rewards` on an underfunded pool is permanently blocked from claiming their promised reward. In the worst case, `unstake` for the last staker in a pool followed by `cleanup_pool` sends only whatever `reducible_balance` remains to the admin, meaning if the pool balance runs dry mid-lifetime other stakers' already-accrued (but unbacked) rewards are simply unrecoverable — a "permanent user-fund lock" per the impact-gate criteria (funds are logically owed per on-chain accounting state but not actually redeemable).

### Likelihood Explanation
The pool admin only needs to (a) create a pool and set an aggressive `reward_rate_per_block` relative to expected `total_tokens_staked`, or (b) simply forget/delay to call `deposit_reward_tokens` to keep the pool funded as staking volume grows or reward rate is increased, or (c) allow the pool to run for its full `expiry_block - creation_block` duration while under-funded. None of `create_pool`, `set_pool_reward_rate_per_block`, `set_pool_expiry_block`, or `stake` validate that `reward_rate_per_block * remaining_blocks` is covered by the pool's current reward-asset balance. This requires no malicious relayer, validator, or leaked key — an ordinary pool admin (who is not assumed malicious, merely under-provisioning, exactly analogous to the original report's "governance forgetting to fully fund") combined with normal staker interaction (`stake`/`harvest_rewards`) is sufficient to trigger the stuck state.

### Recommendation
Before allowing `reward_rate_per_block` to be set/increased in `create_pool` / `set_pool_reward_rate_per_block`, and periodically as rewards accrue, require that the pool account's reducible `reward_asset_id` balance is sufficient to cover the maximum possible outstanding obligation (`reward_rate_per_block * (expiry_block - last_update_block)` scaled by total possible claimants), or alternatively require an upfront `transfer`/`hold` of the full reward budget at pool creation/rate-increase time (mirroring the fix recommended in the original report: tie `notifyRewardAmount`-equivalent calls to an actual `transferFrom`). At minimum, `harvest_rewards` should cap the payout to `T::Assets::reducible_balance(...)` and track/emit a deficit rather than reverting and leaving `staker_info.rewards` in a state that can never be settled.

### Proof of Concept
1. Admin calls `create_pool(staked_asset, reward_asset, reward_rate_per_block = R, expiry = now + N blocks, admin)` — no reward tokens are transferred into the pool account (`deposit_reward_tokens` is never called), matching `create_pool` at `substrate/frame/asset-rewards/src/lib.rs:449-467`.
2. Staker A calls `stake(pool_id, amount)`. `total_tokens_staked` becomes `amount`.
3. `N` blocks pass. `reward_per_token()` (lib.rs:786-810) computes `reward_per_token_stored = R * N * PRECISION_SCALING_FACTOR / amount`, purely from the configured rate and elapsed blocks, with zero correlation to the pool's actual `reward_asset_id` balance (which is 0).
4. Staker A calls `harvest_rewards(pool_id, None)`. `update_pool_and_staker_rewards` computes `staker_info.rewards = R * N` (lib.rs:812-824), then `T::Assets::transfer(reward_asset_id, &pool_info.account, &staker, R*N, Preservation::Expendable)` is attempted (lib.rs:588-595) — this fails with an asset "insufficient balance" style error because the pool account never received any reward tokens.
5. The extrinsic reverts; `staker_info.rewards` is never reset. Staker A's promised reward remains permanently unclaimable unless a third party independently funds the pool account with the exact deficit, which is not guaranteed by any pallet invariant.

This reproduces the exact "insufficient reward token balance leads to failed harvest/insolvency" defect described in the external report, adapted to `pallet-asset-rewards`'s reward-per-token accrual and `harvest_rewards` payout path.

		/// Derives the current reward per token for this pool.
		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}

	fn set_pool_reward_rate_per_block(
		admin: &T::AccountId,
		pool_id: PoolId,
		new_reward_rate_per_block: T::Balance,
	) -> DispatchResult {
		let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
		ensure!(pool_info.admin == *admin, BadOrigin);
		ensure!(
			new_reward_rate_per_block > pool_info.reward_rate_per_block,
			Error::<T>::RewardRateCut
		);

		// Always start by updating the pool rewards.
		let rewards_per_token = Self::reward_per_token(&pool_info)?;
		let mut pool_info = Self::update_pool_rewards(&pool_info, rewards_per_token)?;

		pool_info.reward_rate_per_block = new_reward_rate_per_block;
		Pools::<T>::insert(pool_id, pool_info);

		Self::deposit_event(Event::PoolRewardRateModified { pool_id, new_reward_rate_per_block });

		Ok(())
