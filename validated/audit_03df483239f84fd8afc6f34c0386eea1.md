### Title
Out-of-bounds array read in TVM precompile ABI-array parsing due to missing offset bounds check - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`PrecompiledContracts.extractBytes32Array(DataWord[] words, int offset)` decodes an attacker-supplied dynamic-array header (offset + length words) from precompile call data without validating that `offset` is within the bounds of the decoded `words` array, unlike the sibling helpers `extractBytesArray` and `extractSigArray` in the same class, which explicitly guard against this.

### Finding Description
`extractBytes32Array` reads the array length directly from `words[offset]` and then iterates `words[offset + i + 1]` for `i` in `[0, len)`: [1](#0-0) 

Compare this with `extractBytesArray`, which performs a bounds check (`if (offset > words.length - 1) return new byte[0][];`) before touching `words[offset]`: [2](#0-1) 

And `extractSigArray`, which has the identical guard: [3](#0-2) 

`extractBytes32Array` is missing this bounds check entirely. Because `words` is decoded from the raw call-data bytes supplied by any contract caller (an unprivileged transaction that invokes the precompile), `offset` is fully attacker-controlled and can be crafted to point past the end of the `words` array (or so that `offset + len + 1` exceeds `words.length`), causing an `ArrayIndexOutOfBoundsException` when `words[offset]` or `words[offset + i + 1]` is dereferenced. This is directly analogous to the CVE-2022-28734 bug class: a length/offset field taken from attacker-controlled protocol input is used to index into an internal buffer without a bounds check, leading to out-of-bounds memory access during parsing of that input.

### Impact Explanation
An unhandled `ArrayIndexOutOfBoundsException` thrown while executing a precompiled contract during TVM execution of a transaction can propagate up through the actuator/runtime call path. Depending on how far up the exception is caught, this can manifest as an execution-time crash of the node process or, at minimum, an uncontrolled exception path that diverges from the intended "revert on invalid input" behavior expected from all other array-extraction helpers in this file (`extractBytesArray`, `extractSigArray`), which is a state-transition robustness/availability issue directly caused by every account with the ability to invoke this precompile with crafted call data.

### Likelihood Explanation
Any account can submit a transaction (contract call) that invokes the precompiled contract using `extractBytes32Array` with a crafted `offset` value in the ABI-encoded call data; no special privilege is required. The likelihood of triggering the missing bounds check is high because the value is a raw attacker-controlled `DataWord.intValueSafe()` result used directly as an array index, with no upstream validation visible in this method.

### Recommendation
Add the same bounds check used in `extractBytesArray` and `extractSigArray` to `extractBytes32Array`:
```java
private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
  if (offset > words.length - 1) {
    return new byte[0][];
  }
  int len = words[offset].intValueSafe();
  if (len < 0 || offset + len + 1 > words.length) {
    return new byte[0][];
  }
  byte[][] bytes32Array = new byte[len][];
  for (int i = 0; i < len; i++) {
    bytes32Array[i] = words[offset + i + 1].getData();
  }
  return bytes32Array;
}
```
