### Title
Single-step account owner permission update can permanently and irrecoverably lock an account's funds - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
`AccountPermissionUpdateContract`, processed by `AccountPermissionUpdateActuator`, lets any account holder atomically overwrite the account's `owner`, `witness`, and `active` `Permission` structures in a single transaction. There is no two-step "propose then claim" mechanism: the moment the transaction executes, the old owner permission is replaced and the account is bound to whatever keys/threshold were supplied. If the new owner permission's keys do not correspond to key material the sender actually controls (e.g. keys entered/derived incorrectly, or an unreachable weight/threshold combination that still numerically satisfies validation), the account and everything it controls — TRX balance, TRC10/TRC20 holdings, voting/staking rights, and any contracts whose logic gates on this account's signature — becomes permanently and unrecoverably locked, with no path to regain access.

### Finding Description
`AccountPermissionUpdateActuator.execute()` directly calls `account.updatePermissions(...)` and persists the new permission set with no staging/pending state: [1](#0-0) 

`validate()` only checks structural correctness of the supplied `Permission` objects (address format validity, key count bounds, threshold ≤ sum of weights, no duplicate keys, valid operation bitmap) — it never verifies that the caller can actually produce a valid signature set for the *new* permission being installed: [2](#0-1) 

The address validation used, `DecodeUtil.addressValid`, only checks length/prefix byte, not a base58-check-style checksum against the raw bytes supplied in the protobuf, so a mistyped or wrong-but-well-formed address for a permission key is accepted: [3](#0-2) 

Once `execute()` completes, the previous owner permission is gone; there is no "pending permission" state and no mechanism for the previous key holder to reclaim control if the new permission turns out to be unusable. This mirrors exactly the bug class described in the external report: a single-step, unconfirmed transfer of the controlling authority over an account/contract, where any input error is unrecoverable.

### Impact Explanation
Because `owner` permission governs the ability to authorize *all* future actions of the account (transfers, asset issuance updates, voting, resource delegation, contract triggers signed by that account, etc.), an incorrect update permanently freezes every asset and privilege tied to that account. This is a concrete permanent freezing-of-funds outcome, matching the "High impact" characterization from the analog report. Because `AccountPermissionUpdateContract` is reachable by any unprivileged, ordinary signed transaction (any account holder, not a privileged system role), the blast radius is any account performing multisig setup, not just administrators of a special contract.

### Likelihood Explanation
Low, consistent with the analog: it requires human/tooling error on the part of the account owner constructing the new `Permission` (wrong key bytes, wrong threshold/weight combination that is technically valid but not satisfiable with keys the owner controls, or supplying keys they do not hold the private key for). No two-step confirmation exists to catch such mistakes before they become irreversible, exactly the single-step ownership-transfer risk pattern from the external report.

### Recommendation
Introduce a two-phase account permission update: (1) an owner submits a "pending" new permission set via `AccountPermissionUpdateContract`, and (2) the change becomes effective only after being confirmed by a transaction signed under the *new* permission set (proving the new keys are usable), within some validity window, with the old permission remaining authoritative until confirmation. Alternatively, require the update transaction itself to additionally satisfy a signature check under the *proposed* new owner permission (not just the current one) before committing the change, which would prove control of the new keys at update time.

### Proof of Concept
1. Attacker/careless user account `A` holds funds and has default owner permission with key `K_old`.
2. User builds `AccountPermissionUpdateContract` for account `A` setting `owner` permission to `threshold=2` with keys `{K_old weight=1, K_typo weight=1}` where `K_typo` is a validly-formatted (but wrong/uncontrolled) address, mistakenly believing it's their backup key.
3. Transaction passes `AccountPermissionUpdateActuator.validate()` (address format valid, weights sum ≥ threshold, distinct addresses) and is executed, overwriting the owner permission in a single step: [4](#0-3) 
4. Because threshold is 2 and only `K_old` (weight 1) is actually controlled, the account can never again satisfy the owner-permission signature threshold — it, and all TRX/TRC10/TRC20 balances and privileges attached to it, are permanently locked with no recovery path.

  @Override
  public boolean validate() throws ContractValidateException {

    if (chainBaseManager == null) {
      throw new ContractValidateException(ActuatorConstant.STORE_NOT_EXIST);
    }

    if (this.any == null) {
      throw new ContractValidateException(ActuatorConstant.CONTRACT_NOT_EXIST);
    }

    AccountStore accountStore = chainBaseManager.getAccountStore();
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();

    if (dynamicStore.getAllowMultiSign() != 1) {
      throw new ContractValidateException("multi sign is not allowed, "
          + "need to be opened by the committee");
    }
    if (!this.any.is(AccountPermissionUpdateContract.class)) {
      throw new ContractValidateException(
          "contract type error,expected type [AccountPermissionUpdateContract],real type["
              + any.getClass() + "]");
    }
    final AccountPermissionUpdateContract accountPermissionUpdateContract;
    try {
      accountPermissionUpdateContract = any.unpack(AccountPermissionUpdateContract.class);
    } catch (InvalidProtocolBufferException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractValidateException(e.getMessage());
    }
    byte[] ownerAddress = accountPermissionUpdateContract.getOwnerAddress().toByteArray();
    if (!DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("invalidate ownerAddress");
    }
    AccountCapsule accountCapsule = accountStore.get(ownerAddress);
    if (accountCapsule == null) {
      throw new ContractValidateException("ownerAddress account does not exist");
    }

    if (!accountPermissionUpdateContract.hasOwner()) {
      throw new ContractValidateException("owner permission is missed");
    }

    if (accountCapsule.getIsWitness()) {
      if (!accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("witness permission is missed");
      }
    } else {
      if (accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("account isn't witness can't set witness permission");
      }
    }

    if (accountPermissionUpdateContract.getActivesCount() == 0) {
      throw new ContractValidateException("active permission is missed");
    }
    if (accountPermissionUpdateContract.getActivesCount() > 8) {
      throw new ContractValidateException("active permission is too many");
    }

    Permission owner = accountPermissionUpdateContract.getOwner();
    Permission witness = accountPermissionUpdateContract.getWitness();
    List<Permission> actives = accountPermissionUpdateContract.getActivesList();

    if (owner.getType() != PermissionType.Owner) {
      throw new ContractValidateException("owner permission type is error");
    }
    checkPermission(owner);
    if (accountCapsule.getIsWitness()) {
      if (witness.getType() != PermissionType.Witness) {
        throw new ContractValidateException("witness permission type is error");
      }
      checkPermission(witness);
    }
    for (Permission permission : actives) {
      if (permission.getType() != PermissionType.Active) {
        throw new ContractValidateException("active permission type is error");
      }
      checkPermission(permission);
    }
    return true;
