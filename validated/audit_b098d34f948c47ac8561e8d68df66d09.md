This confirms the analog is concrete and strong: for a given signer set (0 or 1), there are `SIGNER_SLOTS_PER_USER` distinct `.signers-{set}-{message_id}` StackerDB contracts, all sharing the *exact same* signer-to-slot assignment (`stackerdb-get-signer-slots-page`) [1](#0-0) [2](#0-1) , and the same signer key persists across many reward cycles that map to the same `reward_cycle % 2` set [3](#0-2) . Since the chunk signature never binds the contract/message-type, a chunk legitimately signed for one `.signers-0-X` contract is a valid, verifiable chunk for every other `.signers-0-Y` contract (and across many reward cycles) that assigns the signer the same slot ID — no attacker key required, just relay/replay of publicly observed data.

### Title
StackerDB chunk signatures omit contract/message-type binding, enabling cross-contract chunk replay - (File: libstackerdb/src/libstackerdb.rs)

### Summary
`SlotMetadata`/`StackerDBChunkData` signatures authenticate only `(slot_id, slot_version, data_hash)` and never the target StackerDB contract. Because many boot-contract StackerDB replicas (`.signers-{0,1}-{message_id}` for `message_id in 0..SIGNER_SLOTS_PER_USER`, and successive reward cycles sharing the same `signer_set`) assign the *same signer address to the same slot_id*, a chunk that a signer legitimately posted to one contract is also a validly-signed chunk for every sibling contract sharing that slot assignment. Any third party (no private key needed) can replay/relay the publicly-broadcast chunk bytes into a different `.signers-*` (or other multi-instance) StackerDB contract to overwrite that contract's slot with unrelated data, as long as the replayed `slot_version` is not stale there.

### Finding Description
`SlotMetadata::auth_digest` (the payload that gets signed and verified) is built purely from `slot_id`, `slot_version`, and `data_hash` [4](#0-3) . `SlotMetadata::sign`/`verify` operate over exactly this digest [5](#0-4) , and `StackerDBChunkData::sign`/`verify` simply delegate to it [6](#0-5) . The smart-contract/StackerDB identity is never part of the signed material.

On the verification side, `StackerDBs::get_slot_signer(smart_contract, slot_id)` looks up the *expected* signer for `(contract, slot_id)` purely from local per-contract DB state [7](#0-6) , and `PeerNetwork::validate_received_chunk` (used both for `handle_unsolicited_StackerDBPushChunk` and download-sync validation) checks only that the chunk's signature recovers to that address, that its version isn't stale, and that it isn't oversized — nothing ties the signature itself to `smart_contract_id` [8](#0-7) . `StackerDBTx::try_replace_chunk`/`db.rs` enforces the identical checks server-side when a chunk is persisted (as exercised by `test_stackerdb_insert_query_chunks`) [9](#0-8) . The HTTP write path (`POST /v2/stackerdb/:contract/chunks`) takes the target contract from the URL and performs the same signature check with `BadSigner`/`StaleChunk` as the only rejection reasons [10](#0-9)  — it accepts any bytes whose signature recovers to the slot's registered signer for *that* contract, regardless of which contract the signature was originally produced for.

Crucially, the boot-code `.signers` contract deliberately fans out one signer→slot assignment across many sibling StackerDB contracts: `stackerdb-get-signer-slots-page` returns the *same* list for every `.signers-{set}-{message_id}` contract in a signer set [2](#0-1) , and each `.signers-0-xxx` / `.signers-1-xxx` contract just proxies to it [1](#0-0) [11](#0-10) . `SIGNER_SLOTS_PER_USER` sibling contracts are instantiated per signer set at boot [12](#0-11) , and the contract name for each is simply `signers-{reward_cycle % 2}-{message_id}` [3](#0-2)  — meaning the same signer keeps the same slot_id across every reward cycle that maps to the same parity, and across every `message_id` sibling contract for that parity, for as long as it remains in the signer set.

This is the direct analog of the KubeVirt issue: a credential (here, a chunk signature) that is valid for one "role"/context (one specific StackerDB contract/message type) carries no cryptographic binding to that context, so it is equally valid — and gets accepted — when replayed into a different context (a sibling contract) where the same principal happens to hold the same slot.

### Impact Explanation
An unauthenticated third party who observes a legitimately-signed chunk broadcast on the p2p network (or fetched via RPC, since StackerDB reads are public) can replay it into a different sibling `.signers-{set}-{other_message_id}` StackerDB, or into the same contract for a different reward cycle sharing the same parity, overwriting that slot with attacker-chosen (but previously-legitimate, from a different context) content — as long as the replayed `slot_version` clears the local freshness check there. This is an unauthorized write to StackerDB state that does not require any private key, satisfying "unauthenticated/unauthorized write to state or StackerDB" and enabling propagation of data into a context it was never intended for (forged-context data served as if it were legitimate for that contract). Consumers of these StackerDB message contracts (e.g. `stacks-signer` message polling) trust the local replica's validated chunks as the latest per-slot message for that specific contract; cross-contract replay can inject stale/foreign signer messages into the wrong per-message-type channel.

### Likelihood Explanation
Requires no compromised key, only the ability to observe (chunks are broadcast/publicly readable) and rewrite the network request to target a sibling contract with an acceptable `slot_version`/size. The main constraint is that the destination slot's current version must be lower than the replayed chunk's version (or that the destination hasn't been written yet), which is common for less-active `message_id` StackerDB instances or reward cycles that reuse the same slot assignment. This is a moderate-likelihood, low-effort attack once an attacker observes any valid chunk.

### Recommendation
Include the target `smart_contract_id` (and ideally reward cycle / `rc_consensus_hash`) inside `SlotMetadata::auth_digest` so that a chunk's signature is only valid for the specific StackerDB replica it was created for. This requires a coordinated protocol/version change since it alters the signed byte layout that both writers (`stacks-signer`, miners) and readers (`stackslib`) must agree on.

### Proof of Concept
1. Node A observes (or the attacker independently causes) a legitimate signer chunk on `.signers-0-3` for signer `S`: `StackerDBChunkData { slot_id: k, slot_version: v, sig, data }`, where `sig` verifies via `SlotMetadata::verify(&S)` [13](#0-12) .
2. Confirm (via public contract read) that `.signers-0-7` (a sibling message-type contract) assigns the same signer `S` to `slot_id = k` — guaranteed structurally since both contracts read the same `stackerdb-get-signer-slots-page` list [2](#0-1) .
3. Submit the identical `StackerDBChunkData` (same `slot_id`, `slot_version`, `sig`, `data`) via `POST /v2/stackerdb/<signers-0-7 contract>/chunks` [10](#0-9) , or inject it as an unsolicited `StackerDBPushChunkData` over p2p targeting `.signers-0-7`'s contract_id [8](#0-7) .
4. Because `validate_received_chunk`/`try_replace_chunk` only check the signature against `get_slot_signer(smart_contract_id, slot_id)` for the *target* contract and the version/size, and the signature itself carries no contract binding, the write for `.signers-0-7` slot `k` is accepted (subject only to `.signers-0-7`'s own current slot version at `k` being `<= v`), replacing that slot's message with data that was never authorized for that specific message channel.
