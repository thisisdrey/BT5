### Title
Missing content-hash verification in `extend_with_attachments` allows attacker-controlled attachment content to poison Atlas resolution - (File: stackslib/src/net/atlas/download.rs)

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` accepts any `Attachment` returned by a peer for a `GET /v2/attachments/{content_hash}` request without verifying that `Hash160::from_data(&attachment.content) == request.content_hash`. Since the batch is later resolved by `attachment.hash()` rather than by the originally requested `content_hash`, a malicious peer can return arbitrary content and cause the real, queued attachment instance to remain permanently unresolved while its own bogus content gets inserted into the AtlasDB.

### Finding Description
In `stackslib/src/net/atlas/download.rs`, `extend_with_attachments` (around line 530-558) iterates over `results.succeeded`, decodes the HTTP response via `response.decode_atlas_get_attachment()`, and unconditionally does `self.attachments.insert(response.attachment)` [1](#0-0)  — there is no comparison against `request.content_hash` anywhere in this function.

Downstream, in `AttachmentsDownloader::run`, when the state machine reaches `Done`, the code drains `context.attachments` and, for each attachment, calls `context.attachments_batch.resolve_attachment(&attachment.hash())` [2](#0-1) . This resolves the batch entry keyed by the *actual* hash of the returned bytes, not the hash that was originally requested (`AttachmentRequest.content_hash`, set in `get_prioritized_attachments_requests` at line 467-472 based on the queued `AttachmentInstance.content_hash`). If a peer returns bytes `B` such that `Hash160::from_data(&B) != H` (the requested hash), the batch entry for `H` is never resolved, so the batch will be endlessly retried/eventually dropped rather than ever obtaining the correct content, while `insert_instantiated_attachment(&attachment)` stores `B` under `hash(B)` into the local AtlasDB regardless.

I was not able to fully inspect `decode_atlas_get_attachment` in `stackslib/src/net/api/getattachment.rs` to confirm with certainty whether any hash-matching check exists there (index size limits truncated the read before I could view that file's contents) — this is a gap in my verification. However, the `extend_with_attachments` function itself, which is the explicitly named target of this question, performs no such check, and the request object (`AttachmentRequest`) carrying `content_hash` is discarded immediately after being used as a `HashMap` key (`for (request, response) in results.succeeded.drain()`) without ever comparing it to the decoded attachment's actual hash.

### Impact Explanation
Any remote peer that a node syncs Atlas attachments from (selected via `get_outbound_sync_peers` / `get_prioritized_attachments_requests`) can serve fabricated attachment bytes for a requested hash. This does not corrupt already-instantiated/validated attachments (`find_attachment` checks would reject re-insertion collisions at the DB layer for a matching hash), but it does mean the specific `AttachmentInstance` queued for hash `H` never gets resolved by legitimate content, causing BNS/Atlas resolution to stay perpetually unresolved for that name/zonefile update — a case of the node failing to serve canonical state for that entry, consistent with the "attachment/BNS mismatch" High-severity category. This is repeatable per attachment instance and requires no privileged access — just answering an outbound Atlas HTTP request from the victim node.

### Likelihood Explanation
Preconditions: the victim node must have an `AttachmentInstance` queued whose content is unknown locally, and must pick the attacker's peer URL as a download source (achieved automatically if the attacker is an outbound sync peer advertising the attachment in its `GetAttachmentsInvResponse` inventory). Attacker cost is low: run a standard Stacks peer, respond honestly to inventory queries, then serve mismatched content on the specific `GET /v2/attachments/{content_hash}` request. No secrets, keys, or special roles are required, and the P2P/RPC port is remotely reachable by design.

### Recommendation
In `extend_with_attachments`, after decoding the response, verify `response.attachment.hash() == request.content_hash` before inserting into `self.attachments`; on mismatch, treat it as a failed request (`report.bump_failed_requests()`) and optionally mark the peer as faulty/deregister the event, rather than silently trusting the returned bytes.

### Proof of Concept
Rust unit test in `stackslib/src/net/atlas/download.rs` test module:
1. Construct an `AttachmentsBatchStateContext` via `AttachmentsBatchStateContext::new` with a fake `AttachmentsBatch` containing one tracked `AttachmentInstance` with `content_hash = H` (e.g., `Hash160::from_data(b"real")`).
2. Build a `BatchedRequestsResult<AttachmentRequest>` whose `succeeded` map has one entry: `AttachmentRequest { content_hash: H, .. }` -> `Some(StacksHttpResponse)` constructed to decode (via `decode_atlas_get_attachment`) into `Attachment { content: b"attacker-controlled".to_vec() }`, i.e., `Hash160::from_data(b"attacker-controlled") != H`.
3. Call `context.extend_with_attachments(&mut results)`.
4. Assert that `context.attachments` contains an `Attachment` whose `.hash() != H`, and separately call `context.attachments_batch.resolve_attachment(&H)` to show it does not resolve the originally tracked instance — i.e., `context.attachments_batch.has_fully_succeed()` remains `false` after processing, demonstrating that the legitimate instance for `H` is permanently starved despite a "successful" HTTP 200 response being received.
