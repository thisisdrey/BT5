### Title
Attacker can dust-spam `DepositToken` transfers to fill a victim's `MAX_TOKENS_PER_USER` slots, blocking new collateral deposits and new borrows (and preventing top-ups needed to avoid liquidation) - (File: contracts/Pool.sol / contracts/DepositToken.sol)

### Summary
`Pool` tracks each account's deposit and debt tokens in `MappedEnumerableSet` lists capped at `MAX_TOKENS_PER_USER = 30` (`contracts/Pool.sol:79,143-148`). Whenever a `DepositToken` recipient's balance moves from 0 to non-zero — via `_mint` or `_transfer` — `pool.addToDepositTokensOfAccount(recipient)` is called and reverts with `UserReachedMaxTokens` once the cap is reached (`contracts/Pool.sol:216-220`, `contracts/DepositToken.sol:517-520`). An attacker can deposit 1 wei into each deployed `DepositToken` and `transfer` dust to a victim, occupying all free slots. Afterwards: any `deposit(amount, onBehalfOf=victim)` in a collateral type the victim doesn't already hold reverts inside `_mint` (`contracts/DepositToken.sol:486-487`), and any `issue` of a synthetic the victim doesn't already owe reverts in `addToDebtTokensOfAccount` (`contracts/Pool.sol:204-208`). Debt tokens are non-transferable (`TransferNotSupported`, `contracts/DebtToken.sol:31`), so the attacker can only fill the deposit side — 30 distinct deposit tokens is enough.

### Finding Description
The per-account token list is intended as a gas bounding measure for `debtPositionOf`/`depositOf` iteration, but the addition path is attacker-reachable: `DepositToken.transfer(to, dust)` requires no consent from `to` and no minimum amount. There is no `minDeposit`/dust threshold anywhere in `deposit` (only `amount_ == 0` reverts, `contracts/DepositToken.sol:215`). The victim cannot always eject the dust: `transfer`/`transferFrom`/`withdraw` all call `_revertIfLocked` (`contracts/DepositToken.sol:180-182,350,362,409`), and `unlockedBalanceOf` returns 0 when the victim's `_issuableInUsd == 0` (`contracts/DepositToken.sol:383-398`). So a victim at or near max leverage cannot remove the dust entries, and — more critically — cannot add a new collateral type to restore health. An attacker can therefore front-run a distressed user's collateral top-up (or preemptively dust-fill likely victims), forcing them into `Pool.liquidate`. The same revert bricks `SmartFarmingManager` leverage flows targeting the victim and blocks anyone depositing on their behalf.

### Impact Explanation
Temporary freezing of protocol functionality and indirect freezing/loss of funds: the victim's existing positions still work (repay, existing-token deposits — wait, deposits of an already-held token still hit `_mint` but the `addTo...` call is skipped since balance is already non-zero, so only *new* token types are blocked). The concrete damage path is: victim holds collateral types A,B; attacker fills remaining slots with dust of types C..N; victim's position turns unhealthy; victim cannot deposit a new collateral type to recapitalize and gets liquidated. Recovery requires either repaying debt (if they hold the synthetic) or governance adding/removing deposit tokens, since locked dust cannot be transferred out. This mirrors the reported bug class — cheap, repeatable attacker action that locks a victim out of their positions.

### Likelihood Explanation
Requires only an EOA and dust amounts of each underlying collateral (plus deposit fees if configured). Cost scales with the number of registered deposit tokens in the pool; capped at 30. No privileged role, oracle manipulation, or flash loan needed — `transfer` is a plain public entry point. The strongest impact needs a victim who is near their collateral factor limit or who wants to open a position in a new asset, which is common.

### Recommendation
Enforce a minimum first-deposit amount per (depositToken, account) before adding to `depositTokensOfAccount`, or only track tokens in the account list when they are actually locked/used as collateral (e.g., add on first deposit above a threshold and on `seize`, not on raw `transfer`). Alternatively, let any account permissionlessly remove itself from the list by burning/withdrawing dust regardless of lock status, or exempt sub-threshold balances from `lockedBalanceOf` accounting so dust is always transferable out. Reject `transfer` amounts below a per-token dust floor when `recipient` does not already hold the token.

### Proof of Concept
Foundry/Hardhat fork sketch against a deployed `Pool`:

```solidity
// Assume `pool` has N registered deposit tokens (each a DepositToken proxy)
// Victim V holds deposits in token[0] and has an open debt position near max CF.

address[] memory dts = pool.getDepositTokens(); // registry view
for (uint256 i; i < dts.length; ++i) {
    DepositToken dt = DepositToken(dts[i]);
    IERC20 underlying = dt.underlying();
    // attacker deposits 1 wei to self (skips tokens where victim already holds balance)
    deal(address(underlying), attacker, 1);
    underlying.approve(address(dt), 1);
    dt.deposit(1, attacker);
    if (dt.balanceOf(victim) == 0) dt.transfer(victim, 1); // adds victim to list
}

// victim now has debt + deposit tokens count == MAX_TOKENS_PER_USER (30)
vm.startPrank(victim);
// any new-collateral deposit reverts
DepositToken newDt = DepositToken(unusedDepositToken);
IERC20(newDt.underlying()).approve(address(newDt), 1e18);
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
newDt.deposit(1e18, victim);
// and minting a synthetic type the victim doesn't owe also reverts
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
IDebtToken(otherDebtToken).issue(1e18, victim); // inside _mint -> addToDebtTokensOfAccount
vm.stopPrank();

// if victim's _issuableInUsd == 0, victim cannot even transfer the dust back:
vm.expectRevert(DepositToken.NotEnoughFreeBalance.selector);
DepositToken(dts[3]).transfer(attacker, 1);
```

Then drop the victim's collateral price (fork warp/quote drift) so `debtPositionOf` is unhealthy: `deposit(newToken, victim)` still reverts, `Pool.liquidate(victim,...)` succeeds — demonstrating the forced-liquidation path.
