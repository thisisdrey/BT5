### Title
Node-level "Disable Shielded Transaction API" setting only hides the Wallet gRPC/HTTP helper methods; `ShieldedTransferActuator` still accepts and executes broadcast shielded transactions - (File: actuator/src/main/java/org/tron/core/actuator/ShieldedTransferActuator.java)

### Summary
`node.allowShieldedTransactionApi` (exposed via `CommonParameter.isAllowShieldedTransactionApi()`) is the operator-facing switch meant to turn off shielded (zk-SNARK) transaction functionality on a node. It is enforced exclusively inside `org.tron.core.Wallet` via `checkAllowShieldedTransactionApi()` guards on dozens of convenience/helper RPCs (`createShieldedTransaction`, `getNewShieldedAddress`, `getDiversifier`, `getRcm`, `createSpendAuthSig`, `createShieldedContractParameters`, `getShieldTransactionHash`, `isShieldedTRC20ContractNoteSpent`, etc.) [1](#0-0) [2](#0-1) [3](#0-2) . However, the actual on-chain state transition for a shielded transfer is performed by `ShieldedTransferActuator.validate()`/`execute()`, invoked from the normal `BroadcastTransaction` path like any other contract type. That actuator only checks the on-chain committee-controlled parameters `getAllowSameTokenName()` and `supportShieldedTransaction()` — it never calls or checks `isAllowShieldedTransactionApi()` [4](#0-3) .

### Finding Description
This is directly analogous to the Zitadel bug: disabling "User Registration allowed" only removed the UI button/one API surface, while the backend endpoint that actually performed registration had no matching check, letting users register anyway by hitting the URL directly. In java-tron, disabling `allowShieldedTransactionApi` only removes the node's own helper methods for *constructing* shielded-transaction proofs/parameters (spend auth sigs, nullifiers, diversifiers, incoming viewing keys, shielded TRC20 parameter builders). It does not gate the actual consensus-level acceptance of a `ShieldedTransferContract` transaction submitted through `BroadcastTransaction`. An attacker (or any party) who builds the zk-SNARK proof material independently — using the same open-source `librustzcash`/proving libraries the node itself uses, without needing the disabled node RPCs — can still construct, sign, and broadcast a valid `ShieldedTransferContract` transaction. `ShieldedTransferActuator.validate()` will accept it as long as chain-level `ALLOW_SHIELDED_TRANSACTION` is on, regardless of the node operator's `allowShieldedTransactionApi=false` setting [5](#0-4) .

This is also explicitly documented (and presumably intentionally regression-tested to demonstrate the gap) by a test named `shieldedTransferValidationWorksWhenApiDisabled`, whose comment states: "This verifies that the API flag only gates wallet/helper APIs, not the core transaction validation logic" [6](#0-5) [7](#0-6) .

### Impact Explanation
Operators who intentionally disable `allowShieldedTransactionApi` (e.g., for regulatory/compliance reasons, to avoid facilitating privacy-obscured/potentially illicit fund transfers on their node, or because they don't want to expose the heavier zk-SNARK proving/verification workload) get a false sense of restriction: the setting does not actually prevent shielded transactions from being processed by their node when relayed from the p2p network or submitted via raw broadcast. This undermines an administrator-facing security/compliance control without any error or warning, and can expose the node to the exact category of activity (shielded transfers) it was configured to reject, along with the corresponding SNARK-proof verification/energy cost the operator sought to avoid. This maps to CWE-287 (Improper Authentication/Authorization enforcement) in the same manner as the Zitadel advisory — a feature disablement path with a security-relevant purpose, not enforced at the object/execution layer that actually performs the sensitive action.

### Likelihood Explanation
High for any node that has set `node.allowShieldedTransactionApi=false` while chain-level `ALLOW_SHIELDED_TRANSACTION` remains enabled. No special privilege is needed — a party only needs the ability to construct a valid shielded transaction (using publicly available proving code) and to broadcast a transaction to the network, both of which are unprivileged.

### Recommendation
Add an explicit check for `isAllowShieldedTransactionApi()` (or an equivalent node-level policy check) inside `ShieldedTransferActuator.validate()`, mirroring the existing chain-parameter check pattern (`supportShieldedTransaction()`), so that broadcast-path execution is consistent with the operator-facing disablement flag. Alternatively/clarify: if this flag is only intended to gate node convenience RPCs and not consensus-level transaction acceptance, this should be explicitly documented so operators are not misled into believing it blocks the feature entirely.

### Proof of Concept
1. Node operator sets `node.allowShieldedTransactionApi = false` in config, intending to disable shielded transaction functionality; chain-level `ALLOW_SHIELDED_TRANSACTION` proposal remains enabled by the committee.
2. Any client (not necessarily using this node's Wallet RPCs) constructs a valid `ShieldedTransferContract` transaction offline using standard zk-SNARK proving libraries, spending an already-existing shielded note or a transparent-to-shielded/shielded-to-transparent transfer.
3. Client signs and broadcasts the transaction via the node's standard `BroadcastTransaction` gRPC/HTTP endpoint.
4. `ShieldedTransferActuator.validate()` and `execute()` process the transaction successfully because they check only `getAllowSameTokenName()`/`supportShieldedTransaction()`, never `isAllowShieldedTransactionApi()` [4](#0-3) . The existing unit test `shieldedTransferValidationWorksWhenApiDisabled` explicitly demonstrates this behavior succeeds even with the API flag disabled [8](#0-7) .

  /**
   * Test that shielded transfer transaction validation works even when
   * allowShieldedTransactionApi is disabled. This verifies that the API flag
   * only gates wallet/helper APIs, not the core transaction validation logic.
   */
  @Test
  public void shieldedTransferValidationWorksWhenApiDisabled() {
    boolean orig = Args.getInstance().isAllowShieldedTransactionApi();
    // Disable the shielded API (this should NOT affect transaction validation)
    Args.getInstance().setAllowShieldedTransactionApi(false);

    dbManager.getDynamicPropertiesStore().saveAllowShieldedTransaction(1);
    dbManager.getDynamicPropertiesStore().saveTotalShieldedPoolValue(AMOUNT);

    try {
      ZenTransactionBuilder builder = new ZenTransactionBuilder(wallet);
      SpendingKey sk = SpendingKey.random();
      ExpandedSpendingKey expsk = sk.expandedSpendingKey();
      PaymentAddress address = sk.defaultAddress();
      Note note = new Note(address, AMOUNT);
      IncrementalMerkleVoucherContainer voucher = createSimpleMerkleVoucherContainer(note.cm());
      byte[] anchor = voucher.root().getContent().toByteArray();
      dbManager.getMerkleContainer()
          .putMerkleTreeIntoStore(anchor, voucher.getVoucherCapsule().getTree());
      builder.addSpend(expsk, note, anchor, voucher);

      addZeroValueOutputNote(builder);

      long fee = dbManager.getDynamicPropertiesStore().getShieldedTransactionCreateAccountFee();
      String addressNotExist =
          Wallet.getAddressPreFixString() + "8ba2aaae540c642e44e3bed5522c63bbc21f0000";

      builder.setTransparentOutput(ByteArray.fromHexString(addressNotExist), AMOUNT - fee);

      TransactionCapsule transactionCap = builder.build();
      Contract contract =
          transactionCap.getInstance().toBuilder().getRawDataBuilder().getContract(0);
      ShieldedTransferActuator actuator = new ShieldedTransferActuator();
      actuator.setChainBaseManager(dbManager.getChainBaseManager()).setContract(contract)
          .setTx(transactionCap);

      // Validation should succeed even when API is disabled
      actuator.validate();
    } catch (ContractValidateException e) {
      Assert.fail("Shielded transfer validation should not throw ContractValidateException: "
          + e.getMessage());
    } catch (Exception e) {
      Assert.fail("Shielded transfer should not throw Exception: " + e.getMessage());
    } finally {
      Args.getInstance().setAllowShieldedTransactionApi(orig);
    }
  }
