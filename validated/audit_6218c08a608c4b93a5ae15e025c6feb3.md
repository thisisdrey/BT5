### Title
Fixed-window per-connection stream throttle allows ~2x stream burst by straddling the reset boundary - ([File: streamer/src/nonblocking/stream_throttle.rs])

### Finding Description
`ConnectionStreamCounter::reset_throttling_params_if_needed` implements a fixed (non-sliding) window: it only resets `stream_count` and `last_throttling_instant` when more than `STREAM_THROTTLING_INTERVAL` (100ms) has elapsed since the last reset [1](#0-0) . `throttle_stream` reads `stream_count` and only sleeps (throttles) once the accumulated count in the *current* window reaches `max_streams_per_throttling_interval`; otherwise it returns immediately and the caller increments the counter and proceeds to process the stream [2](#0-1) .

Because the window boundary is anchored to `last_throttling_instant` and only reset lazily on the next call after the interval fully elapses, a client can:
1. Open `max_streams_per_throttling_interval` streams just before the window's end (e.g., at t=99ms of a window that started at t=0ms), all of which pass the check since `stream_count` stays below the limit until the last one.
2. Immediately after the window resets (e.g., at t=101ms), open another full batch of `max_streams_per_throttling_interval` streams against the fresh `stream_count` starting at 0.

Both batches are processed without any throttling `sleep`, so roughly `2 * max_streams_per_throttling_interval` streams are admitted into stream processing (and subsequently sigverify/dedup) within a ~2ms real-time span rather than the intended 100ms window. This is the classic fixed-window counter boundary-straddling weakness — there is no sliding-window accounting and no cross-window carry-over, so the per-connection cap can be evaded by precise timing alone, requiring no additional privileges.

### Impact Explanation
This is a QoS-evasion issue: a single unstaked connection can transiently push about double its allotted per-connection stream quota into the stream/packet ingestion path (and downstream sigverify/dedup) within a brief window, without violating the nominal window-average rate. The scope is bounded — it affects one connection's allotment (which for unstaked connections is itself already small, capped via `max_unstaked_load_in_throttling_window` derived from `MAX_UNSTAKED_TPS`) — so it produces a short, bounded CPU burst rather than an unbounded resource exhaustion.

### Likelihood Explanation
Fully reachable by an unstaked remote client with only network access to the TPU QUIC port and precise local timing control over when it opens streams relative to the 100ms window boundary; no cluster stake, gossip participation, or validator control is required. It is trivially repeatable every window boundary.

### Recommendation
Replace the fixed-window reset in `ConnectionStreamCounter` with a sliding-window or token-bucket style limiter (e.g., track a rolling count over the last `STREAM_THROTTLING_INTERVAL_MS` using timestamps or a leaky-bucket credit refill) in `reset_throttling_params_if_needed` / `throttle_stream` so that no 100ms sliding window can ever exceed `max_streams_per_throttling_interval`, regardless of alignment with the counter's internal reset boundary.

### Proof of Concept
```rust
// streamer/src/nonblocking/stream_throttle.rs (test module)
#[tokio::test(start_paused = true)]
async fn test_boundary_straddle_doubles_effective_rate() {
    let stats = StreamerStats::default();
    let counter = Arc::new(ConnectionStreamCounter::new());
    let max_streams = 10u64;

    // Simulate N streams arriving at t=99ms (just before reset)
    tokio::time::advance(Duration::from_millis(99)).await;
    for _ in 0..max_streams {
        throttle_stream(&stats, ConnectionPeerType::Unstaked, "127.0.0.1:0".parse().unwrap(), &counter, max_streams).await;
        counter.stream_count.fetch_add(1, Ordering::Relaxed);
    }
    assert_eq!(stats.throttled_streams.load(Ordering::Relaxed), 0);

    // 2ms later, window has reset; another full batch is admitted immediately
    tokio::time::advance(Duration::from_millis(2)).await;
    for _ in 0..max_streams {
        throttle_stream(&stats, ConnectionPeerType::Unstaked, "127.0.0.1:0".parse().unwrap(), &counter, max_streams).await;
        counter.stream_count.fetch_add(1, Ordering::Relaxed);
    }

    // Assert: within a ~4ms sliding window, 2*max_streams were admitted with zero throttling events,
    // violating the intended "max_streams_per_throttling_interval per 100ms" invariant.
    assert_eq!(stats.throttled_streams.load(Ordering::Relaxed), 0);
}
```
Expected result: the test demonstrates that `2 * max_streams_per_throttling_interval` streams are processed with no throttling `sleep` triggered, within a real-time span far shorter than `STREAM_THROTTLING_INTERVAL_MS`, confirming the sliding-window invariant is violated.

    pub(crate) fn reset_throttling_params_if_needed(&self) -> tokio::time::Instant {
        let last_throttling_instant = *self.last_throttling_instant.read().unwrap();
        if tokio::time::Instant::now().duration_since(last_throttling_instant)
            > STREAM_THROTTLING_INTERVAL
        {
            let mut last_throttling_instant = self.last_throttling_instant.write().unwrap();
            // Recheck as some other thread might have done throttling since this thread tried to acquire the write lock.
            if tokio::time::Instant::now().duration_since(*last_throttling_instant)
                > STREAM_THROTTLING_INTERVAL
            {
                *last_throttling_instant = tokio::time::Instant::now();
                self.stream_count.store(0, Ordering::Relaxed);
            }
            *last_throttling_instant
        } else {
            last_throttling_instant
        }
    }

pub(crate) async fn throttle_stream(
    stats: &StreamerStats,
    peer_type: ConnectionPeerType,
    remote_addr: std::net::SocketAddr,
    stream_counter: &Arc<ConnectionStreamCounter>,
    max_streams_per_throttling_interval: u64,
) {
    let throttle_interval_start = stream_counter.reset_throttling_params_if_needed();
    let streams_read_in_throttle_interval = stream_counter.stream_count.load(Ordering::Relaxed);
    if streams_read_in_throttle_interval >= max_streams_per_throttling_interval {
        // The peer is sending faster than we're willing to read. Sleep for what's
        // left of this read interval so the peer backs off.
        let throttle_duration =
            STREAM_THROTTLING_INTERVAL.saturating_sub(throttle_interval_start.elapsed());

        if !throttle_duration.is_zero() {
            debug!(
                "Throttling stream from {remote_addr:?}, peer type: {peer_type:?}, \
                 max_streams_per_interval: {max_streams_per_throttling_interval}, \
                 read_interval_streams: {streams_read_in_throttle_interval} throttle_duration: \
                 {throttle_duration:?}"
            );
            stats.throttled_streams.fetch_add(1, Ordering::Relaxed);
            match peer_type {
                ConnectionPeerType::Unstaked => {
                    stats
                        .throttled_unstaked_streams
                        .fetch_add(1, Ordering::Relaxed);
                }
                ConnectionPeerType::Staked(_) => {
                    stats
                        .throttled_staked_streams
                        .fetch_add(1, Ordering::Relaxed);
                }
            }
            sleep(throttle_duration).await;
        }
    }
