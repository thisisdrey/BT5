### Title
`LinkRepositoryToObjectPool` accepts an unvalidated object pool reference, permitting cross-repository object exposure via alternates - (File: `internal/gitaly/service/objectpool/link.go`)

### Summary
`LinkRepositoryToObjectPool` writes an attacker/caller-supplied `ObjectPool.Repository` path directly into a target repository's `objects/info/alternates` file. Gitaly only checks that the referenced pool *looks like* a valid pool repository (naming convention + being a valid git dir); it never verifies that the pool actually belongs to the same fork network / is the correct pool for the target repository. This mirrors the TOFT bug class: a caller-controlled "address"-like parameter (the pool repository reference) is trusted and used directly for a privileged, state-changing operation (granting persistent object-store access) without ownership/relationship validation.

### Finding Description
`LinkRepositoryToObjectPool` extracts the target repository and pool from the request and calls `pool.Link()`: [1](#0-0) 

`poolForRequest`/`ExtractPool` build the `ObjectPool` purely from the request-supplied protobuf field, with no check that the pool corresponds to the target `Repository`: [2](#0-1) 

`objectpool.FromProto` — the sole gatekeeper — only validates that (a) the given path is a *pool-shaped* path (`storage.IsPoolRepository`) or lies in a temp dir, and (b) the pool is a syntactically valid git repository. It performs no check that this specific pool is associated with the repository being linked: [3](#0-2) 

`Link()` then unconditionally computes the relative path from the target repository to *whatever* pool was passed and writes it into the repository's alternates file, immediately granting the repository read access to every object in that pool: [4](#0-3) 

As with the `removeParams.market` address in the TapiocaOFT report — accepted and acted upon (`approve` + external call) without validating it is the legitimate market — here the `ObjectPool.Repository` address is accepted and acted upon (alternates write, granting durable object access) without validating it is the legitimate pool for the given member repository.

### Impact Explanation
Alternates grant the linked repository (and, through the reciprocal disassociation/hard-link flow described in `doc/object_pools.md`, potentially the pool member set) access to another repository's objects. If this RPC can be invoked with an attacker-chosen `ObjectPool.Repository` that does not belong to the caller's own fork network, an attacker can:
- Link their own repository to an arbitrary pool repository they can name (pool paths follow a deterministic, hash-derived naming scheme under `@pools/`), thereby exposing/retaining unauthorized objects from another project's pool inside a repository they control, and subsequently disclosing those objects (e.g., by pushing a ref pointing at an object that only exists in the pool).
- Cause objects to be shared across unrelated repositories, undermining the per-project isolation the storage layer otherwise enforces (as seen in the strict path/relative-path validation used elsewhere, e.g. `storage.ValidateRelativePath`, `alternateOutsideStorageError`).

This is a concrete "cross-repository object access" outcome, matching the accepted impact categories.

### Likelihood Explanation
Gitaly's storage/locator layer is otherwise defense-in-depth about path/relative-path validation (see `internal/gitaly/storage/locator.go`, `internal/git/dirs.go`'s `alternateOutsideStorageError`, and `internal/gitaly/storage/storagemgr/partition_assigner.go`'s alternate-relationship checks), but `objectpool.FromProto`/`poolForRequest` notably omit any check binding the pool to the specific member repository. Exploitability depends on whether a caller can reach `LinkRepositoryToObjectPool` with a `Repository`/`ObjectPool` pair that Rails would not itself have paired together (e.g. through an authorization gap upstream, or any client with direct Gitaly RPC access). Because Gitaly is the last line of defense for storage-path safety in this codebase (as evidenced by all the other explicit alternates/relative-path guards), the absence of an ownership check here is a structural gap rather than a purely theoretical one.

### Recommendation
In `internal/git/objectpool/pool.go` (`FromProto`) or in `poolForRequest`, verify that the supplied `ObjectPool.Repository` is actually the pool associated with the target `Repository` (e.g., derive the expected pool path from the repository's own metadata/fork-network identifier rather than trusting the RPC field verbatim), rejecting the request if the two do not match — analogous to whitelisting the `market` address in the original finding.

### Proof of Concept
Not independently executable from the index alone (would require a running Gitaly + fixture pools to demonstrate cross-repo linking); the code path is:
1. Attacker (or any caller able to reach the ObjectPool service with two arbitrary repositories) calls `LinkRepositoryToObjectPool` with `Repository = <attacker-controlled repo>` and `ObjectPool.Repository = <existing pool repo not belonging to attacker's fork network>`.
2. `poolForRequest` → `objectpool.FromProto` accepts the pool because it matches the `@pools/...` naming convention and is a valid git dir — no ownership check.
3. `pool.Link()` writes the pool's relative object path into the attacker repository's `objects/info/alternates`, giving it access to the pool's objects. [1](#0-0) [5](#0-4)

func (s *server) LinkRepositoryToObjectPool(ctx context.Context, req *gitalypb.LinkRepositoryToObjectPoolRequest) (*gitalypb.LinkRepositoryToObjectPoolResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	pool, err := s.poolForRequest(ctx, req)
	if err != nil {
		return nil, err
	}

	repo := s.localRepoFactory.Build(repository)

	if err := pool.Link(ctx, repo); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	return &gitalypb.LinkRepositoryToObjectPoolResponse{}, nil
}

func (s *server) poolForRequest(ctx context.Context, req PoolRequest) (*objectpool.ObjectPool, error) {
	pool, err := objectpool.FromProto(ctx, s.logger, s.locator, s.gitCmdFactory, s.catfileCache, s.txManager, s.housekeepingManager, req.GetObjectPool())
	if err != nil {
		if errors.Is(err, objectpool.ErrInvalidPoolDir) {
			return nil, errInvalidPoolDir
		}

		if errors.Is(err, objectpool.ErrInvalidPoolRepository) {
			return nil, structerr.NewFailedPrecondition("%w", err)
		}

		return nil, structerr.NewInternal("%w", err)
	}

	return pool, nil

// FromProto returns an object pool object from its Protobuf representation. This function verifies
// that the object pool exists and is a valid pool repository.
func FromProto(
	ctx context.Context,
	logger log.Logger,
	locator storage.Locator,
	gitCmdFactory gitcmd.CommandFactory,
	catfileCache catfile.Cache,
	txManager transaction.Manager,
	housekeepingManager housekeepingmgr.Manager,
	proto *gitalypb.ObjectPool,
) (*ObjectPool, error) {
	poolPath, err := locator.GetRepoPath(ctx, proto.GetRepository(), storage.WithRepositoryVerificationSkipped())
	if err != nil {
		return nil, err
	}

	if !storage.IsPoolRepository(proto.GetRepository()) {
		// When creating repositories in the ObjectPool service we will first create the
		// repository in a temporary directory. So we need to check whether the path we see
		// here is in such a temporary directory and let it pass.
		tempDir, err := locator.TempDir(proto.GetRepository().GetStorageName())
		if err != nil {
			return nil, fmt.Errorf("getting temporary storage directory: %w", err)
		}

		if !strings.HasPrefix(poolPath, tempDir) {
			return nil, ErrInvalidPoolDir
		}
	}

	pool := &ObjectPool{
		Repo:                localrepo.New(logger, locator, gitCmdFactory, catfileCache, proto.GetRepository()),
		logger:              logger,
		locator:             locator,
		gitCmdFactory:       gitCmdFactory,
		txManager:           txManager,
		housekeepingManager: housekeepingManager,
	}

	if !pool.IsValid(ctx) {
		return nil, ErrInvalidPoolRepository
	}

	return pool, nil
}

// Link will link the given repository to the object pool. This is done by writing the object pool's
// path relative to the repository into the repository's "alternates" file. This does not trigger
// deduplication, which is the responsibility of the caller.
func Link(ctx context.Context, pool, repo *localrepo.Repo, txManager transaction.Manager) (returnedErr error) {
	altPath, err := repo.InfoAlternatesPath(ctx)
	if err != nil {
		return err
	}

	expectedRelPath, err := getRelativeObjectPath(ctx, pool, repo)
	if err != nil {
		return err
	}

	linked, err := linkedToRepository(ctx, pool, repo)
	if err != nil {
		return err
	}

	if linked {
		// When the repository is already linked to the repository, cast a vote to ensure the
		// repository is consistent with the other replicas.
		if err := transaction.VoteOnContext(ctx, txManager, voting.VoteFromData([]byte("repository linked")), voting.Synchronized); err != nil {
			return fmt.Errorf("vote on linked repository: %w", err)
		}

		return nil
	}

	alternatesWriter, err := safe.NewLockingFileWriter(altPath)
	if err != nil {
		return fmt.Errorf("creating alternates writer: %w", err)
	}
	defer func() {
		if err := alternatesWriter.Close(); err != nil && returnedErr == nil {
			returnedErr = fmt.Errorf("closing alternates writer: %w", err)
		}
	}()

	if _, err := io.WriteString(alternatesWriter, expectedRelPath); err != nil {
		return fmt.Errorf("writing alternates: %w", err)
	}

	if err := transaction.CommitLockedFile(ctx, txManager, alternatesWriter); err != nil {
		return fmt.Errorf("committing alternates: %w", err)
	}
