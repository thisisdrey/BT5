## Title
Heap-buffer-over-read parsing a crafted ZIP central directory in ijar's `InputZipFile::ProcessCentralDirEntry` — (File: `third_party/ijar/zip.cc`)

### Summary
`third_party/ijar/zip.cc` implements Bazel's minimal ZIP reader (`InputZipFile`), used both by the `third_party/ijar:zipper` binary (a general-purpose extraction tool invocable from build actions/genrules on any input zip/jar) and internally by ijar's interface-jar generation, which is routinely run over Java dependency jars fetched from external, attacker-influenced sources (e.g. `http_jar`/Maven artifacts). Unlike `ProcessLocalFileEntry`, which calls `EnsureRemaining()` before every variable-length read, `ProcessCentralDirEntry` performs no bounds checking at all when consuming attacker-controlled length/offset fields from the central directory. [1](#0-0) 

### Finding Description
`FindZipCentralDirectory` only validates that the *aggregate* central directory (`cd.central_dir_offset + cd.central_dir_size`) fits inside the mapped input file: [2](#0-1) 

It never validates the *individual* entries inside that region. `ProcessCentralDirEntry` then walks through file_name_length, extra_field_length and file_comment_length fields taken verbatim from attacker-supplied bytes, advancing the read cursor `p` with `p += file_name_length; ... p += extra_field_length; ... while (extra_p != p) { ...; extra_p += data_size; } ... p += file_comment_length;` with no comparison of `p` against the mmap'd file boundary (`bytes + in_length`) or even against `central_dir_size`: [3](#0-2) 

By contrast, the local-file-header parser explicitly guards every read with `EnsureRemaining()`: [4](#0-3) [5](#0-4) 

A crafted central-directory entry can set `file_name_length`/`extra_field_length`/`file_comment_length` (each up to `0xFFFF`) or a bogus zip64 extra-field `data_size` so that the cursor `p`/`extra_p` is advanced past the end of the memory-mapped input file. The very next dereference — either the inner extra-field loop's `get_u2le(extra_p)` or the next call to `ProcessNext()`'s `get_u4le(p)` signature check — reads out of the bounds of the mmap region, i.e. a heap/mmap-based buffer over-read driven entirely by untrusted, attacker-published archive bytes. This is architecturally the same bug class as CVE-2020-27796: a parser trusts size/offset fields taken from a crafted file without validating them against the buffer bounds before dereferencing.

### Impact Explanation
This is invoked on any zip/jar processed by the `zipper` tool or ijar's interface-jar generation, both of which regularly run over jars originating from external dependency downloads. Since sha256/integrity verification in `http_jar`/`http_archive` only certifies that the downloaded bytes equal the bytes an attacker chose to publish — it does nothing to validate the internal structural integrity of the archive — an attacker who controls a dependency's hosted artifact (and its checksum entry) can supply a well-formed-looking jar whose central directory triggers an out-of-bounds read, potentially crashing the build (host process) or leaking adjacent memory contents depending on how the over-read data is subsequently used (e.g. copied into `filename` or memcpy'd via `ProcessLocalFileEntry`/`InputZipFile::Process`).

### Likelihood Explanation
Likelihood is moderate-to-high for any project that consumes external `.jar`/`.zip` dependencies processed by ijar (essentially every `java_library`/`java_import` with an external jar in Bazel), or that runs the `zipper` binary directly on downloaded archives in a genrule. No privileged access is required — only the ability to publish/host a jar that a build later fetches.

### Recommendation
Add the same `EnsureRemaining()`-style bounds check used in `ProcessLocalFileEntry` to `ProcessCentralDirEntry` (and to the zip64 extra-field-locator logic), validating that `file_name_length`, `extra_field_length`, `file_comment_length`, and each extra-field's `data_size` never advance the cursor past `bytes + in_length` (or past `central_dir_current_ + central_dir_size`) before any subsequent dereference.

### Proof of Concept
Extend the existing zipper regression-test harness (which already crafts malicious inputs against this binary, e.g. `test_no_path_traversal`) with a new case that builds a ZIP whose EOCD/central-directory record declares a valid overall `central_dir_size` but whose single central-directory entry sets `file_name_length = extra_field_length = file_comment_length = 0xFFFF` (or a zip64 extra field with an oversized `data_size`), then invokes `${ZIPPER} x crafted.zip` and observes a crash/ASan heap-buffer-overflow report instead of a clean parse error, mirroring the structure of the pre-existing `CreateZipWithMalformedExtraField` proof-of-concept helper used for the analogous singlejar reader: [6](#0-5) [7](#0-6)

        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);

  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);

  *attr = get_u4le(p);
  *offset = get_u4le(p);

      ? file_name_length

    memcpy(reinterpret_cast<void*>(filename), p, len);
