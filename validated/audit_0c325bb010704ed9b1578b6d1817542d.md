### Title
Same-key signature replay inflates approval weight in `ValidateMultiSign` precompile, bypassing multisig threshold - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `ValidateMultiSign` precompiled contract (TVM address `0x...0a`) tallies signer weight from a caller-supplied signature array without deduplicating by recovered signer address — it only skips an entry when the *exact byte-identical* signature has already been counted for that address. Any second, distinct signature that still recovers to the same address (e.g. an ECDSA malleable/alternate-form signature over the same hash) is *not* skipped, and its weight is added again, exactly mirroring the reported TOTP flaw where a value that should be single-use per verification window is accepted repeatedly because only the exact previously-seen value is checked, not the underlying identity/counter it represents.

### Finding Description
`PrecompiledContracts.ValidateMultiSign.execute` computes a weight sum over the provided signatures: [1](#0-0) 

For each signature it recovers the signer address, merges `(recoveredAddr, sign)` into a byte blob, and checks membership:
- If `executedSignList` contains `recoveredAddr` **and** contains the merged `sign` blob → `continue` (skip, don't double count).
- If `executedSignList` contains `recoveredAddr` but **not** that exact merged `sign` blob → it falls through, adds `weight` again, and re-adds the address/sign pair.

This means the "already used" check is keyed on the literal signature bytes rather than on the recovered signer identity. Any second signature that recovers to an address already credited — for instance a different valid ECDSA signature over the same message hash from the same key (there are two mathematically valid `(r, s)`/`(r, n-s)` representations for a given ECDSA signature, and BouncyCastle-based signing does not intrinsically forbid supplying both, or an entirely different valid signature nonce) — is treated as a "new" approval and its weight is added a second time, exactly like the TOTP bug where the same underlying value is accepted twice because the check is stateless with respect to identity/nonce, only exact-value-based.

### Impact Explanation
`ValidateMultiSign` is a TVM precompile invoked via `TriggerSmartContract`/`TriggerConstantContract`, reachable by any address, and is documented as the on-chain primitive smart contracts use to validate an account's multisig approval against its `Permission` (threshold/weight) configuration — analogous to Solidity's `ecrecover` but for TRON's native multisig accounts. A contract (e.g. a custody/vault/DAO contract) that relies on this precompile to gate a privileged operation (fund transfer, admin action) behind "N-of-M signer threshold reached" can be tricked into believing multiple distinct signers approved when in fact only a single key (with weight below the threshold) supplied two differently-encoded signatures over the same hash. This directly enables unauthorized account operations / theft of funds in any contract that trusts this precompile's threshold result, without requiring the full set of legitimate cosigners.

### Likelihood Explanation
Exploitation only requires: (1) a TVM contract using `ValidateMultiSign` for authorization (a documented, intended use case of this precompile), and (2) an attacker controlling one key with non-zero but sub-threshold weight in the target account's permission, who then crafts two distinct valid signatures over the identical hash from that one key. Producing a second, differently-encoded valid ECDSA signature for the same message/key (or leveraging any other same-key signature variance) does not require breaking cryptography — it is within reach of any external, unprivileged caller able to submit calldata to the precompile. This is reachable purely through crafted `TriggerSmartContract` calldata, no special privilege needed.

### Recommendation
Change the dedup key in `ValidateMultiSign.doExecute` from `(recoveredAddr, sign)` byte-matching to recoveredAddr-only: once an address has contributed weight, skip it entirely regardless of the specific signature bytes supplied for it (mirroring the existing correct pattern already present in `TransactionCapsule.checkWeight`, which stores addresses in a map and rejects "has signed twice" strictly by address). This closes the gap where distinct signature encodings recovering to the same key can be counted more than once.

### Proof of Concept
1. Deploy/target an account with an `Active` permission whose threshold is `2`, containing key `K1` with weight `1` (and any other keys), such that `K1` alone is insufficient.
2. Attacker, holding only `K1`, computes `hash = sha256(address || permissionId || data)` per the precompile's construction.
3. Attacker signs `hash` with `K1` twice, producing two syntactically different but both-valid 65-byte signatures `sig_a` and `sig_b` that both recover to `K1`'s address (e.g., via alternate low-level ECDSA encoding/nonce reuse quirks, or any mechanism producing two distinct byte sequences recovering to the same address).
4. Attacker calls the `ValidateMultiSign` precompile (address ending `0a`) with `signatures = [sig_a, sig_b]`.
5. In the loop shown at [1](#0-0) , the first signature adds weight `1` for `K1`; the second signature recovers to the same address but its merged `sign` blob differs from the first, so the `matrixContains(executedSignList, sign)` check is false, and the loop does not `continue` — it adds weight `1` again, giving `totalWeight = 2 >= threshold(2)`, returning `DataWord.ONE()` (success) even though only one distinct authorized key actually approved.

Note: I was unable to directly inspect `recoverAddrBySign`'s exact signature-parsing/normalization logic within the remaining tool budget, so the precise mechanism for obtaining two distinct valid signature byte-encodings from one key (malleability vs. nonce reuse vs. other same-key variance) is asserted based on the observed dedup-by-exact-bytes logic rather than a fully traced cryptographic proof; a Devin session with full repo access would be needed to confirm whether `recoverAddrBySign`/underlying ECDSA verification enforces canonical low-S/single-encoding signatures, which would determine the exact PoC signature construction.
