## Analysis: Stale PostponedReceipt Execution Against a Recreated Account

The scenario in the question is realizable. Tracing the code confirms a genuine state-cleanup gap: `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId`/`ReceivedData` trie entries are never cleared when an account is deleted, and resolution of these entries is keyed purely by `(receiver_id, receipt_id/data_id)` with no binding to "which incarnation" of the account created them.

### Root cause

`remove_account` only clears `Account`, `ContractCode`, access/gas keys, and `ContractData`: [1](#0-0) [2](#0-1) 

It never touches `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, `TrieKey::PostponedReceiptId`, or `TrieKey::ReceivedData` for the account being deleted.

`action_delete_account` calls `remove_account` unconditionally (subject only to storage-size and gas-key-balance checks), with no check for outstanding postponed receipts on the account: [3](#0-2) 

`check_account_existence` only rejects `CreateAccount` when `account.is_some()` — after deletion the account is `None`, so recreation on the same `account_id` is unconditionally permitted: [4](#0-3) 

When the missing `DataReceipt` for the stale postponed receipt eventually arrives, `process_receipt`'s `Data` arm resolves it purely via `receiver_id`/`receipt_id` lookups, with no notion of account generation/incarnation: [5](#0-4) 

`apply_action_receipt` then builds `promise_results` directly from `ReceivedData{receiver_id, data_id}` and executes the action receipt's actions (including `FunctionCall`) against whatever account currently exists at `receiver_id`: [6](#0-5) 

### Exploit flow (fully within an unprivileged attacker's control)

1. Attacker deploys an escrow-style contract V1 on account `X`, and triggers an async cross-contract call to an attacker-controlled "oracle" account `Y` with a `promise_then` callback receipt `R` targeting `X` (e.g. method `release_funds`, crafted args, beneficiary = attacker). `R` is postponed because `Y`'s `DataReceipt` hasn't arrived yet, so `process_action_receipt` stores it (`set_postponed_receipt`), plus `PendingDataCount`/`PostponedReceiptId` links: [7](#0-6) 
2. Attacker (owner of `X`) submits `DeleteAccount` for `X` while `R` is still pending — this succeeds, since no check inspects postponed receipts, and the stale trie rows survive.
3. Attacker recreates `X` (`CreateAccount`, allowed since `account.is_some()` is now false) and deploys a genuine multi-user escrow contract V2 with the same `release_funds` method name/signature, gated on `promise_result(0)`. A legitimate victim deposits funds into V2's escrow expecting release only upon a real verification result.
4. Attacker, controlling `Y`, sends the deferred `DataReceipt` matching the old `data_id`. `process_receipt` finds the still-present `PostponedReceiptId{X, data_id} -> R`, decrements `PendingDataCount` to 0, fetches the stale `PostponedReceipt{X, R}`, and executes it via `apply_action_receipt` against V2's **current** state, passing a `promise_results` value computed from `Y`'s attacker-controlled data — data never produced by any promise V2 created.
5. V2's `release_funds` (near-vm-runner host call `promise_result`) observes a forged `Successful` signal and releases the victim's escrowed funds to the attacker-specified beneficiary.

No existing check (nonce, access-key permission, gas metering, storage staking, or account-existence validation) intercepts this, because each of those checks is local to a single action/receipt and none of them is aware of postponed-receipt survivorship across account deletion/recreation.

### Title
Stale `PostponedReceipt` survives account deletion and executes against a recreated account with forged `promise_results` - (File: `runtime/runtime/src/actions.rs`, `core/store/src/utils/mod.rs`, `runtime/runtime/src/lib.rs`)

### Summary
`action_delete_account`/`remove_account` never clear `PostponedReceipt`, `PendingDataCount`, `PostponedReceiptId`, or `ReceivedData` entries for the deleted account, and receipt resolution in `process_receipt`/`apply_action_receipt` is keyed only by `(receiver_id, receipt_id/data_id)` with no incarnation check. An attacker who fully controls the account lifecycle (create → postpone a callback receipt → delete → recreate with a different contract) can later trigger delivery of the withheld data to run the old callback's `FunctionCall` action against the new contract with attacker-chosen `promise_results`, forging promise-success signals the new contract never legitimately produced.

### Finding Description
See trace above; the vulnerable functions are `remove_account` (`core/store/src/utils/mod.rs:504-575`), `action_delete_account` (`runtime/runtime/src/actions.rs:314-390`), `check_account_existence` (`runtime/runtime/src/actions.rs:787-855`), `process_receipt`'s Data arm (`runtime/runtime/src/lib.rs:1367-1474`), and `apply_action_receipt`'s `promise_results` construction (`runtime/runtime/src/lib.rs:776-845`).

### Impact Explanation
Theft of user funds: a contract's internal accounting (e.g., an escrow releasing funds gated on `promise_result`) can be corrupted by a forged promise-success signal injected via a stale postponed receipt tied to a deleted-and-recreated account, letting the attacker redirect other users' deposited funds. This maps to the "theft of user funds via corrupted contract accounting" / value-conservation bounty category.

### Likelihood Explanation
Requires only ordinary account/contract deployment privileges: the attacker needs full control of the account whose lifecycle is manipulated (own `X` and `Y`), no validator/node access. The attacker fully controls timing (when to delete/recreate, when to deliver the withheld `DataReceipt`), so the attack is deterministic and repeatable. The main precondition is finding/deploying a target-account pattern where a victim later deposits into the recreated contract before the attacker triggers resolution — feasible because the attacker controls exactly when the stale data is delivered.

### Recommendation
On `action_delete_account`/`remove_account`, either (a) reject deletion while any `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` entries exist for the account (forcing all pending async callbacks to resolve or be explicitly failed first), or (b) proactively purge/invalidate all such entries (and corresponding `ReceivedData`) for the account as part of `remove_account`, generating refund/failure semantics for any in-flight postponed receipts instead of leaving them dangling for a future incarnation.

### Proof of Concept
Integration test (test-loop or `runtime/runtime/tests`):
1. Deploy an escrow-style contract on account `X` exposing `release_funds` that checks `promise_result(0)`.
2. From `X`, issue a `promise_then` callback to itself depending on data from account `Y`, producing a postponed receipt `R` on `X` (assert `PostponedReceipt{X,R}` exists in the trie).
3. Delete account `X` via `DeleteAccount` while `R` is still postponed; assert the account no longer exists but `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` rows for `X` remain.
4. Recreate `X`, deploy a fresh escrow contract instance (V2) with the same `release_funds` method, and have a "victim" account deposit funds under V2's genuine escrow logic.
5. Deliver the withheld `DataReceipt` from `Y` (matching the original `data_id`) and let the runtime resolve the stale postponed receipt.
6. Assert that `release_funds` executed on V2 with `promise_result(0) == Successful` even though V2 never created that promise, and that funds were transferred to the attacker-specified beneficiary despite the victim's deposit conditions not being met — demonstrating the value-conservation violation.
