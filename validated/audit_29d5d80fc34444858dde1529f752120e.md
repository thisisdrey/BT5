### Title
Unstaked global QUIC connection-rate token bucket is stake-agnostic and can be depleted by unstaked connection floods to starve staked TPU senders - ([File: streamer/src/nonblocking/quic.rs])

### Summary
`run_server` creates a single, per-endpoint-group `overall_connection_rate_limiter` `TokenBucket` (`MAX_CONNECTION_BURST` = 1000, refill `TOTAL_CONNECTIONS_PER_SECOND` = 2500/s) that is checked/consumed for *every* completed QUIC handshake before stake is known, with no per-stake reservation or priority. An unprivileged attacker distributing connection attempts across many source IPs (to avoid the separate per-IP `ConnectionRateLimiter`) can keep this shared bucket empty, causing the same global check to reject legitimate staked senders' connections.

### Finding Description
In `run_server`, the bucket is created fresh per QUIC server instance (e.g., once for the main TPU port, once for TPU-forwards, once for votes) and shared across *all* connections to that port regardless of stake: [1](#0-0) 

On each incoming connection, before any handshake or stake classification, the loop does a cheap peek-and-ignore check against this shared bucket: [2](#0-1) 

Only after `run_server` passes the connection to `setup_connection` does the code complete the QUIC handshake, register the caller's IP with the per-IP `ConnectionRateLimiter`, and then actually consume a token from `overall_connection_rate_limiter` — this consumption happens *before* `qos.build_connection_context`/`try_add_connection` determine whether the peer is staked or unstaked: [3](#0-2) 

Because stake can only be derived from the TLS client certificate after the QUIC handshake completes, and the global bucket is consumed immediately after handshake but before that classification, there is no mechanism to reserve capacity for staked peers or to refund/exempt them. An attacker with access to many source IPs (satisfying the per-IP limiter, which allows `max_connections_per_ipaddr_per_min * 10` burst per IP) can complete enough handshakes to keep `overall_connection_rate_limiter.current_tokens()` at 0, causing both the fast-path `ignore()` in `run_server` and the `consume_tokens` check in `setup_connection` to reject subsequently arriving staked connections with `CONNECTION_CLOSE_CODE_DISALLOWED`.

### Impact Explanation
This is a QoS-evasion/availability issue on the TPU ingress path: an unstaked, unprivileged attacker can deny staked validators the ability to establish new QUIC connections to a leader's TPU, TPU-forwards, or TPU-vote ports, since each of these uses its own instance of this stake-agnostic shared bucket. This matches the "connection/stream/per-IP QoS limits bypassed to starve legitimate senders of TPU capacity" bounty category — the invariant that staked capacity is protected from unstaked volume is violated at the connection-admission layer, independent of the later per-class `SwQos`/`SimpleQos` staked/unstaked pools.

### Likelihood Explanation
Feasibility requires only network access to the leader's public TPU-family QUIC ports and the ability to originate connection attempts from many distinct source IPs (to stay under the per-IP limiter, which is a much easier constraint than obtaining stake). No stake, keys, or validator control needed. `MAX_CONNECTION_BURST`/`TOTAL_CONNECTIONS_PER_SECOND` are fixed constants, not configurable via `SwQosConfig`, so this cannot be tuned away by operator config. The attack is fully repeatable while the leader is targeted, and races solely against the refill rate.

### Recommendation
Introduce stake-aware admission for the global connection-rate limiter — e.g., reserve a portion of `MAX_CONNECTION_BURST`/`TOTAL_CONNECTIONS_PER_SECOND` tokens exclusively for callers presenting a recognized staked identity (checked immediately post-handshake, before the shared bucket check), or maintain separate token buckets for staked vs. unstaked traffic similar to the separation already used for staked/unstaked connection tables in `SwQos`.

### Proof of Concept
Integration test plan (extending the existing `streamer/src/nonblocking/quic.rs` / `tpu-client-next` test harness):
1. Spin up a QUIC server via `setup_quic_server` with default `SwQosConfig` and a staked-nodes map containing one known staked pubkey with real stake.
2. From N distinct source IPs (test harness can bind sockets to different loopback aliases or mock `remote_address()`), open and complete `MAX_CONNECTION_BURST` (1000) QUIC connections concurrently to the server within under (1000/2500)s, driving `overall_connection_rate_limiter.current_tokens()` to 0.
3. Immediately attempt a connection using the staked identity's keypair (`make_client_endpoint` with the staked `Keypair`).
4. Assert the staked connection is closed with `CONNECTION_CLOSE_CODE_DISALLOWED`/`CONNECTION_CLOSE_REASON_DISALLOWED` and that `stats.connection_rate_limited_across_all` increments for the staked attempt, proving the shared unauthenticated bucket rejected a legitimately staked sender.
