### Title
Cross-contract StackerDB chunk replay: `SlotMetadata` signature omits the target StackerDB contract identity - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` / `StackerDBChunkData` signatures commit only to `(slot_id, slot_version, data_hash)` and never to the target `QualifiedContractIdentifier` (the specific `signers-{set}-{message_id}` StackerDB replica). Because the same signer occupies the identical `slot_id` across every `signers-{set}-{message_id}` contract for a given signer set, a validly-signed chunk from one lane can be replayed, byte-for-byte, into a different lane's StackerDB and will pass all storage-layer checks. This is the direct analog of the reported Nexus bug: an authorization signature that omits a context field (`moduleType` there, "which StackerDB contract" here) lets an attacker reuse a legitimately-authorized artifact outside the scope the signer actually authorized.

### Finding Description
The signed digest for a StackerDB chunk is: [1](#0-0) 

This digest — and thus the signature carried in `StackerDBChunkData.sig` — never includes the contract/DB identity. Verification is likewise scoped only to `(slot_id, slot_version, data_hash)`: [2](#0-1) 

The storage-layer write path (`try_replace_chunk`) validates the signer address (looked up per `smart_contract`/slot from that replica's own configured signer table), the version freshness, and the write-count cap — but the *signed bytes themselves* never encode which contract they were signed for: [3](#0-2) 

`PeerNetwork::validate_received_chunk` (used for both pulled/downloaded chunks and unsolicited `StackerDBPushChunk`s) has the same gap — it resolves the expected signer for `smart_contract_id`/`slot_id`, then just checks `slot_metadata.verify(&addr)`, with nothing tying the signature to `smart_contract_id`: [4](#0-3) 

Critically, the *same* signer occupies the *same* `slot_id` across every message-lane contract of a given signer set, because slot assignment comes from one shared page: [5](#0-4) [6](#0-5) 

and each lane is materialized as its own independent contract keyed by `(reward_cycle % 2, message_id)`: [7](#0-6) 

Consequently, a chunk a signer legitimately signs and pushes into lane A (e.g. `signers-0-1`, `BlockResponse`) at `slot_id = X, version = v` is a byte-identical valid `(slot_id, slot_version, sig, data)` tuple for lane B (e.g. `signers-0-6`, `StateMachineUpdate`) at the *same* `slot_id = X`, since the signer occupies slot `X` in both contracts and the signature never bound which contract it was for. An attacker who observes this chunk on the wire (StackerDB push/gossip is unauthenticated at the transport level; only the chunk signature matters) can resubmit it into lane B's replica. `try_replace_chunk`/`validate_received_chunk` for lane B will accept it as long as lane B's current stored version for slot `X` is `< v` (true for a freshly-initialized replica, or simply by choosing a target lane whose version counter hasn't caught up) — the signature check succeeds because `slot_metadata.verify(&addr)` only re-derives `(slot_id, slot_version, data_hash)`, which is unchanged.

The only downstream defense found is a content-based filter in the signer-event decoder, which checks that the *first byte* of the payload data matches the expected `SignerMessageTypePrefix` for the target lane: [8](#0-7) 

This filters out cross-lane replays for the specific `T::consensus_deserialize`/`libsigner` consumer, but it operates on unauthenticated payload bytes (an implementation-level heuristic, not a cryptographic binding), and it does not prevent the write into the wrong StackerDB replica from succeeding and propagating at the network/storage layer — nodes will still store, ACK, advertise (via `StackerDBChunkInv`) and serve the misplaced chunk as if it were legitimate content for that contract/slot, regardless of whether some higher-level consumer later discards it based on the first payload byte.

### Impact Explanation
This breaks the equality "signature authorizes writing to slot S of *this* StackerDB replica" — the signature only proves "signer authorized *some* chunk with this slot/version/hash", not which contract. That is an unauthorized write to state: a chunk that was never authorized (via signature) for a given StackerDB replica gets accepted and stored there, and is then propagated network-wide through StackerDB sync/inventory/serving paths as legitimate content for that contract/slot. This matches the Critical bucket ("unauthenticated/unauthorized write to state or StackerDB" / "network-wide propagation of forged data").

### Likelihood Explanation
The attack requires no signer private key and no privileged role — only observing one legitimately-signed chunk (chunks are broadcast/gossiped/served over the p2p StackerDB protocol) and resubmitting it to a different, sibling lane contract where the same signer occupies the same slot and the version counter permits it (trivially true for fresh/low-version replicas, or reward-cycle-boundary windows when replicas reset). This is a remote, unprivileged, low-effort action.

### Recommendation
Bind the target contract identity into the signed digest, analogous to fixing `_getEnableModeDataHash()` in the report: include the `QualifiedContractIdentifier` (or an equivalent domain separator, e.g. `contract_id.to_string()` or its hash) inside `SlotMetadata::auth_digest()` in `libstackerdb/src/libstackerdb.rs`, and thread the contract identifier into every call site that signs/verifies (`StackerDBChunkData::sign`/`verify`, `try_replace_chunk`, `validate_received_chunk`, `recover_pk`). This ensures a chunk signed for one StackerDB replica cannot be replayed as valid for another, closing the cross-lane replay path.

### Proof of Concept
1. Let signer `S` have private key `sk`, and occupy `slot_id = 3` in both `signers-0-1` (`BlockResponse` lane) and `signers-0-6` (`StateMachineUpdate` lane) for the current reward cycle (guaranteed by shared slot-page logic in `signers.clar`).
2. `S` legitimately signs and pushes chunk `data`, `slot_version = 1` into `signers-0-1`, slot 3 — this produces `sig = Sign(sk, auth_digest(3, 1, hash(data)))`, accepted by `try_replace_chunk` for `signers-0-1`.
3. Attacker `A` observes this chunk in transit (via `StackerDBGetChunksInv`/`StackerDBPushChunk` gossip) and constructs a `StackerDBPushChunkData` with `contract_id = signers-0-6`, using the identical `chunk_data = StackerDBChunkData { slot_id: 3, slot_version: 1, sig, data }`.
4. `A` submits this to any peer via `handle_unsolicited_StackerDBPushChunk` → `validate_received_chunk` for `signers-0-6`. Signature check `slot_metadata.verify(&addr_of_slot_3_in_signers-0-6)` succeeds (same digest, same signer address occupies slot 3 in that contract too); if `signers-0-6`'s stored version for slot 3 is `0` (fresh), the version-freshness check also passes.
5. The chunk is stored into `signers-0-6` at slot 3 and subsequently advertised/served to the network via `make_StackerDBChunksInv_or_Nack` as legitimate `StateMachineUpdate`-lane data, despite never having been authorized (signed) for that contract.

Note: the effectiveness of step 5's downstream *interpretation* by the specific `libsigner` consumer is reduced by the payload-type-prefix filter in `libsigner/src/events.rs::signer_message_payload_matches_lane` (line 587), but this is a content heuristic outside the signature scheme, does not prevent the wrongful *storage/propagation*, and does not protect any other/future consumer of StackerDB contracts that doesn't apply the same heuristic.

    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }
