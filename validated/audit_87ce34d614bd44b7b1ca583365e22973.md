### Title
Out-of-bounds array read (crash) in TVM precompiled-contract ABI array parsing due to unvalidated declared length - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The precompiled-contract signature-validation helpers `extractBytesArray` and `extractBytes32Array` decode a `bytes[]`/`bytes32[]` ABI array from attacker-controlled TVM call data by trusting a length word taken from the data itself (`words[offset].intValueSafe()`), then iterate that many times indexing further into the same `DataWord[] words` array without verifying the array actually contains that many elements.

### Finding Description
`extractBytesArray` performs only a single, incomplete guard before trusting the declared length: [1](#0-0) 
The check `offset > words.length - 1` only validates that the length word itself is present; it does not validate that the following `len` words (`words[offset + i + 1]` and `words[offset + bytesOffset + 1]`) fit inside `words`. `len`, `bytesOffset`, and `bytesLen` are all derived from attacker-supplied call data via `intValueSafe()`.

`extractBytes32Array` is worse — it has no bounds check at all before dereferencing `words[offset]` or looping over `words[offset + i + 1]`: [2](#0-1) 

This is the same bug class as the OpenEXR HTJ2K issue: a length/count field embedded inside the payload (the codestream's declared tile width in OpenEXR; the ABI array-length word here) is used directly as an iteration/copy bound against an internal buffer (`ojph`'s per-line buffer in OpenEXR; the `DataWord[] words` array here) whose *actual* size was determined by the outer container (the EXR header; the real length of the TVM call-data buffer) — with no cross-check between the two. `words` is populated by splitting the raw call-data byte array into 32-byte `DataWord` chunks, so its true length is fixed by the caller-supplied call-data length, while `len`/`bytesOffset`/`bytesLen` are independently attacker-chosen fields inside that same data, letting an attacker set them arbitrarily large or make them point past the end of `words`.

### Impact Explanation
An attacker who crafts a transaction that invokes a precompiled contract exercising these helpers (used by the multi-signature validation precompiled contracts reachable from ordinary TVM `CALL`/`STATICCALL`) can trigger an `ArrayIndexOutOfBoundsException` deep inside the precompile execution path. Because this occurs inside `PrecompiledContracts`, which is invoked from the standard TVM execution/energy-metering flow for every contract call that targets one of these precompile addresses, any unprivileged contract deployer or caller can reach it with a single crafted transaction. Depending on how the exception propagates through the actuator's execute path, this can manifest as an unhandled runtime exception that disrupts transaction execution/block processing (crash/DoS) rather than a silent corruption, matching the "node crash" impact category.

### Likelihood Explanation
Reaching this code only requires constructing TVM call data with a length field (`words[offset]`) that is inconsistent with the true amount of remaining call data — i.e., a value large enough that `offset + len` exceeds `words.length`. This is trivially achievable by any address able to send a transaction that invokes the affected precompiled contract, with no special privileges, making likelihood high.

### Recommendation
Add explicit bounds checks before using `len`, `bytesOffset`, and `bytesLen` in `extractBytesArray` and `extractBytes32Array`: verify `offset + len` (and each computed `bytesOffset`/`bytesLen` derived index) stays within `words.length` (and within `data.length` for the underlying byte extraction), returning an empty array or throwing a well-defined revert instead of allowing an unchecked `ArrayIndexOutOfBoundsException` to propagate.

### Proof of Concept
1. Construct a transaction that calls a precompiled contract path exercising `extractBytesArray`/`extractBytes32Array` (the multi-signature validation precompile that parses a `bytes[]`/`bytes32[]` array from its input).
2. In the ABI-encoded call data, set the array-length word at the expected offset to a large value (e.g., `0xFFFFFFFF` or any value greater than the number of remaining 32-byte words actually supplied), while providing far fewer actual trailing words than declared.
3. Submit the transaction; execution reaches `extractBytesArray`/`extractBytes32Array`, which loops `len` times indexing `words[offset + i + 1]` past the end of the `words` array, throwing `ArrayIndexOutOfBoundsException` during precompile execution. [3](#0-2)
