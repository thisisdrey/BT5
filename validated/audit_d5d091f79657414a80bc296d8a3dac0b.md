### Title
Stale NAV valuation due to manual interest accrual and DPD bucket transitions - (`NavCalculator.sol`, `PortfolioVault.sol`)

### Summary
The `PortfolioVault` Net Asset Value (NAV) calculation is susceptible to mispricing because it relies on manual ledger updates (`accrue`, `applyWaterfall`) and discrete time-based discount buckets. Similar to the external report where troves diverged in value due to interest accrual timing, Tare's loan valuations can be "sorted" incorrectly in the NAV total if interest is not accrued or if a loan crosses a Days Past Due (DPD) threshold without a subsequent NAV update.

### Finding Description
The protocol calculates NAV by summing the value of loans in a curated list [1](#0-0) . The `NavCalculator` determines each loan's value using its `outstandingInvestorPrincipal` and a discount factor based on its DPD [7](#0-6) . 

There are two primary ways this valuation becomes "incorrect" (the analog to incorrect sorting):
1. **Manual Accrual Lag**: Interest is not automatically added to the loan's value. It only enters the ledger when the servicer calls `accrue()` [8](#0-7) . If a servicer (who may be affiliated with the borrower or vault manager) delays accrual, the loan is undervalued in the NAV.
2. **DPD Threshold Jump**: The `NavCalculator` uses `block.timestamp` to determine if a loan is 30, 60, 90, or 120 days past due [9](#0-8) . A loan's value can drop significantly the moment `block.timestamp` exceeds `nextDueDate + 30 days`.

The `PortfolioVault` attempts to mitigate this with `maxNavAge` [6](#0-5) , but if the underlying ledger state (accruals) or the DPD bucket transitions are not reflected in a new `updateNav` cycle before `approveDeposit` or `approveRedemption` is called, the vault issues or redeems shares at an unfair price.

### Impact Explanation
Material corruption of vault NAV and fair share pricing. If the NAV is undervalued (due to missing accruals), new depositors receive more shares than they should, diluting existing shareholders. If the NAV is overvalued (due to a missed DPD bucket drop), redeeming shareholders receive more assets than their shares are worth, leaving the vault underbacked. This violates the "fair share pricing" requirement for the vault path.

### Likelihood Explanation
Medium. While the "single-entity assumption" [10](#0-9)  suggests shareholders won't exploit each other, the protocol is designed to be ERC-7540/7575 compatible for DeFi integration [11](#0-10) . In a multi-investor scenario, the timing of manual ledger updates and NAV refreshes becomes a critical vector for value extraction.

### Recommendation
1. Implement a "minimum accrual" check in the `NavCalculator` that virtually accrues interest since the last `updatedAt` timestamp for valuation purposes.
2. Require a fresh `updateNav` (where `lastNavUpdate == block.timestamp`) for any `approveDeposit` or `approveRedemption` call if any loan in the curated list has crossed a DPD threshold since the last finalized NAV.

### Proof of Concept
1. A vault holds a loan with `outstandingInvestorPrincipal` of 1,000,000 USDC and a `nextDueDate` of $T$.
2. At time $T + 30$ days, the loan is valued at 100% (par) because it is not yet "DQ30" (DPD > 30) [12](#0-11) .
3. The manager runs `updateNav` at $T + 30$ days. `lastNav` reflects the loan at par.
4. At time $T + 30$ days + 1 second, the loan is now technically in the `DQ30` bucket, which has a 90% discount factor.
5. The manager calls `approveRedemption` for a large shareholder. Because `block.timestamp - lastNavUpdate` is small (1 second), the `_requireFreshNav` check passes [6](#0-5) .
6. The shareholder redeems shares based on the par valuation, effectively extracting 10% more value than the loan's current risk-adjusted worth, leaving the remaining shareholders to absorb the 100,000 USDC loss.
