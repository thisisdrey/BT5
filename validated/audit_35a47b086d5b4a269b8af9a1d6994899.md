## Analysis: Reward-state cleared before cross-chain settlement completes in `pallet-bridge-relayers` Snowbridge payout path

The PirexRewards bug boils down to one broken invariant: **the "claimed" accounting is finalized before the actual value transfer is confirmed to have reached the beneficiary**, so a failure downstream is silently absorbed as loss. The Polkadot SDK has a structurally identical pattern in the Snowbridge v2 relayer reward payout.

### Title
Relayer reward is permanently removed from storage on successful XCM dispatch, not on successful cross-chain settlement, causing silent, unrecoverable reward loss - (File: `bridges/snowbridge/primitives/core/src/reward.rs`)

### Summary
`pallet_bridge_relayers::claim_rewards_to` clears a relayer's `RelayerRewards` entry as soon as `PaymentProcedure::pay_reward` returns `Ok(())`. For the Snowbridge reward kind, `pay_reward` is implemented by `PayAccountOnLocation::pay_reward`, which only validates and *sends* an XCM instruction sequence to AssetHub (`ReserveAssetDeposited` + `DepositAsset`) and returns `Ok(())` once `XcmSender::deliver` succeeds — i.e., once the message is queued for delivery, not once the deposit is actually executed and settled on AssetHub.

### Finding Description
`do_claim_rewards` in `bridges/modules/relayers/src/lib.rs` takes the reward out of storage inside `try_mutate_exists` and only commits removal if the closure returns `Ok`: [1](#0-0) 

The `BridgeReward::Snowbridge` branch of `pay_reward` in the runtime config delegates to `snowbridge_core::reward::PayAccountOnLocation::pay_reward`: [2](#0-1) 

That implementation builds an XCM containing `ReserveAssetDeposited` + `DepositAsset { beneficiary }`, validates it, charges local fees, and returns `Ok(())` as soon as `XcmSender::deliver` succeeds: [3](#0-2) 

`deliver` only confirms the message was accepted into the outbound XCMP queue for the destination chain (AssetHub) — it says nothing about whether the `DepositAsset` instruction actually succeeds there. If execution at AssetHub fails (e.g., the derived beneficiary account cannot receive the asset, the asset is not registered/trusted at that time, weight/barrier issues, or the beneficiary location is malformed), the reserve-minted asset is trapped by the XCM executor rather than delivered. Meanwhile, back on BridgeHub, `do_claim_rewards` has already committed removal of the `RelayerRewards` entry because `pay_reward` returned `Ok(())`. The relayer/beneficiary has no way to re-claim: the local reward record is gone, and any trapped asset at the destination is keyed to the bridge's derived XCM origin (`UniversalOrigin(GlobalConsensus(Ethereum))` after `DescendOrigin`), not to the relayer's own account, making the standard `pallet-xcm::claim_assets` recovery path unusable by an ordinary relayer or beneficiary.

This is the same broken invariant as the PirexRewards report: **payout accounting is finalized ("rewards = 0" / storage entry removed) based on a "was sent" signal rather than a "was settled" signal**, so any failure between dispatch and destination-side settlement is silently absorbed as permanent loss, with no revert and no error surfaced back to the claiming call.

### Impact Explanation
A relayer's already-earned Snowbridge reward can be permanently lost with no revert, no re-claim path, and no on-chain signal distinguishing "claimed and paid" from "claimed and lost." This matches the "permanent user-fund lock" impact category: value that should have settled to the rightful beneficiary can vanish (trapped) while local reward-accounting state has already advanced as if settlement succeeded, violating the atomicity requirement that "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically."

### Likelihood Explanation
The call path `claim_rewards_to` is a plain unprivileged, signed extrinsic available to any registered relayer with a pending reward — no admin, governance, or malicious-peer assumption is required. The failure trigger (destination-side `DepositAsset` failure for a given beneficiary `Location`) is entirely plausible given that the beneficiary is caller-supplied (`BridgeRewardBeneficiaries::AssetHubLocation(VersionedLocation)`), and any edge case in destination-chain execution (account existence, asset registration/trust state, XCM version/format mismatches) after the message has already been "delivered" locally triggers loss.

### Recommendation
Do not remove/finalize the `RelayerRewards` entry based on `deliver()` success alone for cross-chain payment procedures. Either:
- Keep the reward pending until an explicit settlement acknowledgment/receipt from the destination chain is observed, reverting/restoring the entry otherwise; or
- Use a two-phase commit: mark reward as "in-flight" rather than deleting it, and only fully clear it once a confirmation callback (or reconciliation) proves the deposit succeeded on AssetHub, with a path to restore the claimable reward if settlement fails or times out.

### Proof of Concept
1. Relayer accrues a `BridgeReward::Snowbridge` reward via `register_reward` (as in `bridge_rewards_works`, `bridges/modules/relayers` / `bridge-hub-westend` tests: [4](#0-3) ).
2. Relayer calls `claim_rewards_to(reward_kind = Snowbridge, beneficiary = AssetHubLocation(some_location))`, where `some_location` is a `VersionedLocation` that resolves to a `Location` for which `DepositAsset` will fail on AssetHub after delivery (e.g., an account that cannot receive the reserve asset at execution time).
3. On BridgeHub, `PayAccountOnLocation::pay_reward` validates the XCM, charges local fees, and calls `XcmSender::deliver`, which succeeds because it only queues the message — see the `Ok(())` return once `deliver` succeeds: [5](#0-4) .
4. Because `pay_reward` returned `Ok`, `do_claim_rewards`'s `try_mutate_exists` commits removal of the `RelayerRewards` entry and emits `RewardPaid`: [6](#0-5) .
5. On AssetHub, the `DepositAsset` instruction fails during execution of the delivered XCM; the reserve-minted asset is trapped instead of reaching the intended beneficiary.
6. The relayer's reward is now unrecoverable through the pallet (storage entry gone) and the trapped asset cannot practically be reclaimed by the relayer/beneficiary since the trap is keyed to the bridge's Ethereum-derived origin, not their account.

	fn pay_reward(
		relayer: &Relayer,
		_: (),
		reward: RewardBalance,
		beneficiary: Self::Beneficiary,
	) -> Result<(), Self::Error> {
		let ethereum_location = Location::new(2, [GlobalConsensus(EthereumNetwork::get())]);
		let assets: Asset = (ethereum_location.clone(), reward.into()).into();

		let xcm: Xcm<()> = alloc::vec![
			UnpaidExecution { weight_limit: Unlimited, check_origin: None },
			DescendOrigin(InboundQueueLocation::get().into()),
			UniversalOrigin(GlobalConsensus(EthereumNetwork::get())),
			ReserveAssetDeposited(assets.into()),
			DepositAsset { assets: AllCounted(1).into(), beneficiary },
		]
		.into();

		let (ticket, fee) =
			validate_send::<XcmSender>(AssetHubLocation::get(), xcm).map_err(|_| XcmSendFailure)?;
		XcmExecutor::charge_fees(relayer.clone(), fee).map_err(|_| ChargeFeesFailure)?;
		XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;

		Ok(())
	}
