Audit Report

## Title
Missing slippage protection in Snowbridge `system-frontend` fee-swap lets any user's tip/registration payment be drained via price manipulation - (File: `bridges/snowbridge/pallets/system-frontend/src/lib.rs`)

## Summary
`Pallet::add_tip` and `Pallet::register_token` in `pallet-system-frontend` route the caller-supplied fee/tip asset through `swap_fee_asset_and_burn` → `swap_and_burn`, which calls `T::Swap::swap_exact_tokens_for_tokens` with `amount_out_min` hard-coded to `None` at [1](#0-0) . This disables the slippage check (`ensure!(amount_out >= amount_out_min, ...)`) that `pallet_asset_conversion`'s own extrinsic path enforces, allowing the swap output (`ether_gained`) to be manipulated arbitrarily low while the user's full tip/fee asset is still withdrawn and burned.

## Finding Description
`add_tip` is callable by any `ensure_signed` account with an arbitrary `asset` at [2](#0-1) , and `register_token` is reachable by any non-root origin satisfying `RegisterTokenOrigin` at [3](#0-2) . Both paths call `swap_fee_asset_and_burn`, which for non-Ether fee assets calls `swap_and_burn` at [4](#0-3) .

Inside `swap_and_burn`, the swap is executed as:
```rust
let ether_gained = T::Swap::swap_exact_tokens_for_tokens(
    who.clone(),
    swap_path,
    tip_amount,
    None, // No minimum amount required
    who,
    true,
)?;
```
at [1](#0-0) . Because `amount_out_min` is `None`, `pallet_asset_conversion`'s `do_swap_exact_tokens_for_tokens` skips its own protective check, which is only applied `if let Some(amount_out_min) = amount_out_min` as confirmed in `substrate/frame/asset-conversion/src/lib.rs` (the `ProvidedMinimumNotSufficientForSwap` guard is conditional on `Some`, and there are 18 references to `amount_out_min`/the error in that file, consistent with the pallet's own extrinsic enforcing this check while the internal call here bypasses it by construction).

The full `tip_amount`/`fee_amount` is withdrawn from the user's account regardless, and only the (potentially manipulated) `ether_gained` result is burned and forwarded on-chain to BridgeHub via `build_add_tip_call`/`build_register_token_call`, where it determines the relayer reward or registration fee value. An attacker with no special privilege can trade against the same public AMM pool immediately before and after the victim's transaction to depress the quoted price, since the pool is an ordinary `pallet_asset_conversion` pool reachable via the public `swap_exact_tokens_for_tokens`/liquidity extrinsics.

## Impact Explanation
This matches the "public underpriced work that degrades block production or stalls bridge processing" and fund-loss categories in scope. The `ether_gained` value — which determines the relayer reward embedded in the `AddTip`/`RegisterToken` transact call sent to BridgeHub — can be forced near zero by an attacker manipulating the AMM pool immediately around the victim's transaction, while the victim's full tip/fee asset is irrecoverably withdrawn and burned. This degrades the intended incentive/payout mechanism for relayer rewards and registration fees without requiring any privileged access.

## Likelihood Explanation
Any unprivileged, signed account can call `add_tip` with an arbitrary asset and amount, and the corresponding `pallet_asset_conversion` pools are themselves publicly tradable via ordinary extrinsics (`swap_exact_tokens_for_tokens`, `add_liquidity`, `remove_liquidity`). No governance, relayer, or validator privilege is required — the missing bound is a structural code defect (a hard-coded `None`), not merely an opportunistic front-running scenario, since the pallet had the mechanism available (`amount_out_min`) and simply did not expose/thread it through.

## Recommendation
Add an explicit minimum-output parameter to `add_tip`/`register_token` (or compute a safe bound from an oracle/quote), and thread it through `swap_fee_asset_and_burn` → `swap_and_burn` into `T::Swap::swap_exact_tokens_for_tokens` instead of hard-coding `None`, mirroring the enforcement already present in `pallet_asset_conversion::Pallet::swap_exact_tokens_for_tokens`.

## Proof of Concept
1. Deploy `system-frontend` with `T::Swap` pointing at a low-liquidity `pallet_asset_conversion` pool for a fee-asset/Ether pair.
2. Attacker submits a large `swap_exact_tokens_for_tokens` (or liquidity add/remove sequence) against that pool immediately before the victim's transaction is included, depressing the fee-asset price.
3. Victim calls `add_tip(message_id, asset)`; `swap_and_burn` executes `T::Swap::swap_exact_tokens_for_tokens(..., None, ...)` at [1](#0-0) , accepting whatever `ether_gained` the manipulated pool returns since no minimum-output check is enforced on this path.
4. Attacker reverses the initial trade, pocketing the price difference; the victim's tip/fee asset is fully burned via `burn_for_teleport` for a negligible `ether_gained`, which is embedded in the `AddTip`/`RegisterToken` call forwarded to BridgeHub.
