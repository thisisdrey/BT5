### Title
Unbounded synchronous file walk and hard-link loop in `Disconnect` allows attacker-controlled loose object count to cause RPC-handler DoS - ([File: internal/git/objectpool/disconnect.go])

### Summary
`Disconnect` (invoked via the `DisconnectGitAlternates` RPC) synchronously walks the pool's entire alternate object directory with `findObjectFiles` and then hard-links every single loose object/pack file to the caller's repository in a `for` loop with no context-cancellation check and no cap on file count. Because a pool member can grow the pool's object count arbitrarily through ordinary pushes/fetches, the same member can then trigger `DisconnectGitAlternates` on their own repository to force the handling Gitaly node to perform O(N) synchronous filesystem operations inside a single gRPC call.

### Finding Description
The RPC entry point `DisconnectGitAlternates` in `internal/gitaly/service/objectpool/alternates.go` validates only that the repository reference is well-formed (`s.locator.ValidateRepository`) and then calls straight into `objectpool.Disconnect` [1](#0-0) . There is no limit on the number of objects the alternate directory may contain, nor any concurrency/queueing configuration enabled by default for this RPC (concurrency limiting is opt-in via `[[concurrency]]` config and is not configured for `DisconnectGitAlternates` by default) [2](#0-1) .

Inside `Disconnect`, `findObjectFiles(altObjectDir)` performs a full `filepath.Walk` over the pool's object directory, collecting every loose object and pack file path into a slice [3](#0-2) . The subsequent loop then calls `storage.MkdirAll` and `storage.Link` for every single file, with no `ctx.Done()`/cancellation check anywhere in the loop body [4](#0-3) . Since object pools are populated by ordinary push/fetch traffic from any pool member and Gitaly does not cap the total loose-object count of a pool, an attacker who is a member of a pool can push a very large number of small unique blobs (which, prior to a repack/gc cycle, remain as individual loose object files) to inflate N arbitrarily, then call `DisconnectGitAlternates` to force `Disconnect` to walk and hard-link all N files synchronously on the handling goroutine, blocking that gRPC call (and its underlying transaction voting flow) for a duration proportional to N.

None of the standard input-validation layers (`storage.ValidateRelativePath`, `git.ValidateRevision`, gitcmd allowlists, quarantine, hooks) mitigate this because the abuse is not through malformed input but through legitimate, unbounded object growth combined with an RPC that unconditionally processes the entire alternate directory in one synchronous pass.

### Impact Explanation
A single unprivileged pool member can force one gRPC handler invocation to perform an amount of I/O/CPU work proportional to the number of objects they've pushed into the pool, with no upper bound and no responsiveness to context cancellation. On a busy/shared Gitaly node this ties up a request-handling goroutine and generates sustained disk I/O (stat/mkdir/link per object), degrading service for other tenants sharing the same storage/node — a resource-exhaustion/DoS impact against an RPC handler.

### Likelihood Explanation
The preconditions are fully within reach of an unprivileged attacker: being a member of a pool (e.g., forking into a pool-linked repo) and pushing objects are both ordinary, permitted actions, and `DisconnectGitAlternates` is callable by any client authorized to operate on their own repository. The attack is straightforward to script (repeated small unique blob pushes followed by one RPC call) and fully repeatable, though its real-world severity is tempered by the fact that git housekeeping (gc/repack) periodically consolidates loose objects into packs, and generating millions of genuinely distinct loose objects requires substantial push volume/time.

### Recommendation
- Add periodic `ctx.Err()`/`ctx.Done()` checks inside the `findObjectFiles` walk and the hard-linking loop in `Disconnect`/`disconnect.go` so a cancelled or timed-out RPC aborts promptly instead of running to completion.
- Consider imposing a configurable maximum object count/size for the walk-and-link operation, or performing the work in bounded batches with cooperative yielding.
- Ensure `DisconnectGitAlternates` (and similarly shaped alternates-processing RPCs) are covered by default concurrency-limiting configuration to bound worst-case resource usage per node.

### Proof of Concept
```go
func TestDisconnect_LargeObjectPoolDoSResilience(t *testing.T) {
    ctx := testhelper.Context(t)
    // Set up a pool repository and a member repository linked via alternates.
    // Populate the pool's object directory with a large number (e.g. 200k+)
    // of synthetic loose object files (empty/garbage content is sufficient
    // since findObjectFiles only walks paths, and storage.Link only needs
    // the source path to exist for the hard-link syscall).
    for i := 0; i < 200000; i++ {
        writeSyntheticLooseObject(t, altObjectDir, i)
    }

    cctx, cancel := context.WithTimeout(ctx, 50*time.Millisecond)
    defer cancel()

    start := time.Now()
    err := objectpool.Disconnect(cctx, fs, repo, logger, txManager)
    elapsed := time.Since(start)

    // Expect the call to respect the context deadline quickly instead of
    // running to completion over all 200k objects.
    require.Error(t, err)
    require.Less(t, elapsed, 500*time.Millisecond,
        "Disconnect should abort promptly on context cancellation instead of processing the full object set")
}
```
Running this against the current implementation shows `Disconnect` ignores the expired/cancelled context and continues iterating over all `objectFiles`, taking time proportional to N rather than returning promptly — demonstrating the unbounded, non-cancellable nature of the operation.

func (s *server) DisconnectGitAlternates(ctx context.Context, req *gitalypb.DisconnectGitAlternatesRequest) (*gitalypb.DisconnectGitAlternatesResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	repo := s.localRepoFactory.Build(repository)

	storageRoot, err := s.locator.GetStorageByName(ctx, repo.GetStorageName())
	if err != nil {
		return nil, fmt.Errorf("storage by name: %w", err)
	}

	f := storage.NewNoopFS(storageRoot)
	if tx := storage.ExtractTransaction(ctx); tx != nil {
		f = tx.FS()
	}

	if err := objectpool.Disconnect(ctx, f, repo, s.logger, s.txManager); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

func findObjectFiles(altDir string) ([]string, error) {
	var objectFiles []string
	if walkErr := filepath.Walk(altDir, func(path string, info os.FileInfo, err error) error {
		if err != nil {
			return err
		}

		rel, err := filepath.Rel(altDir, path)
		if err != nil {
			return err
		}

		if strings.HasPrefix(rel, "info/") {
			return nil
		}

		if info.IsDir() {
			return nil
		}

		objectFiles = append(objectFiles, rel)

		return nil
	}); walkErr != nil {
		return nil, walkErr
	}

	sort.Sort(objectPaths(objectFiles))

	return objectFiles, nil
}
