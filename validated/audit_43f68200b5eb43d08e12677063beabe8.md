## Analysis

The Sherlock report's bug class — a bonding-curve/AMM function using imprecise arithmetic on a user-supplied liquidity/token amount, producing an incorrect exchanged quantity — maps directly onto java-tron's TRX/TRC10 bonding-curve **Exchange** feature (`ExchangeTransactionContract` / `ExchangeInjectContract` / `ExchangeWithdrawContract`), which implements a Bancor-style constant-product/constant-supply formula.

### Root cause

The default (legacy) calculation path, `ExchangeProcessor`, computes the traded amount using **double-precision floating point** math and truncates via a plain `(long)` cast, with no precision or divisibility check: [1](#0-0) [2](#0-1) 

This is invoked from `ExchangeCapsule.transaction()`, which selects this legacy `ExchangeProcessor` unless the hardened calculation flag is set: [3](#0-2) 

The alternative, exact `SafeExchangeProcessor`, uses `BigDecimal` with fixed rounding and was added later, gated behind `dynamicStore.allowHardenExchangeCalculation()`: [4](#0-3) [5](#0-4) 

`allowHardenExchangeCalculation` is a committee-controlled, proposal-gated dynamic property (see `ProposalUtil.java` / `DynamicPropertiesStore.java`), i.e. it is **off unless the committee explicitly activates it via governance proposal**. Until activated, every `ExchangeTransactionActuator.execute()` call on the network runs through the imprecise floating-point `ExchangeProcessor`: [6](#0-5) 

The project's own test suite (`ExchangeProcessorTest.testStrictMath`) explicitly demonstrates that the legacy floating-point path and the hardened `BigDecimal` path diverge for realistic (sellBalance, buyBalance, sellQuant) triples: [7](#0-6) 

### Why this matches the report's bug class

Just like `estimateWithdrawalAmounts` failing to validate that an `lpAmount` produces a "clean" (decimals-respecting) result, `ExchangeProcessor.exchange()` never validates that its floating-point computation is exact/faithful to the underlying integer token accounting — it simply truncates a `double` to `long`. An attacker who controls the `tokenQuant`/`sellTokenQuant` input to `ExchangeTransactionActuator` (a normal signed `ExchangeTransactionContract` transaction, permission-checked only by `getOwnerAddress()`/standard signature verification) can choose amounts where the double-precision `pow()` computation rounds in the attacker's favor relative to the "true" integer-exact value that `SafeExchangeProcessor` would compute, extracting more of `anotherTokenQuant` than the constant-product invariant should allow, or repeatedly exploiting rounding drift across many small transactions to drain value from the shared `firstTokenBalance`/`secondTokenBalance` pool at the expense of the pool creator/other participants.

Note `ExchangeInjectActuator` and `ExchangeWithdrawActuator` already use `BigInteger`/`BigDecimal` exact division (`longValueExact`, `divideToIntegralValue`) for their ratio math, and `ExchangeWithdrawActuator.doValidate()` additionally has an explicit 0.01% precision-drift check ("Not precise enough"): [8](#0-7) 

`ExchangeTransactionActuator`, however, has no equivalent precision check — it trusts `exchangeCapsule.transaction(...)`'s return value unconditionally.

### Title
Floating-point precision loss in default `ExchangeProcessor` bonding-curve math allows value extraction from TRX/TRC10 Exchange pools - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
`ExchangeTransactionActuator` computes the amount of token a user receives from a bonding-curve swap via `ExchangeCapsule.transaction()`, which by default (until the committee activates `allowHardenExchangeCalculation`) delegates to `ExchangeProcessor`, a class that performs the Bancor formula using `double` arithmetic and truncates the result with a bare `(long)` cast, with no exactness or divisibility validation, unlike the sibling `ExchangeInjectActuator`/`ExchangeWithdrawActuator` (BigInteger/BigDecimal exact math) or the newer `SafeExchangeProcessor`.

### Finding Description
`ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` compute `Maths.pow(...)` on `double` operands and cast the resulting `double` straight to `long`, discarding fractional precision without any check that the computed value is faithful to the exact integer token-balance math the chain is supposed to enforce. This computation directly determines `anotherTokenQuant`, which is credited to the caller's account in `ExchangeTransactionActuator.execute()` and debited from the pool's `firstTokenBalance`/`secondTokenBalance`, all reachable from a single signed `ExchangeTransactionContract` transaction from any account.

### Impact Explanation
Because the legacy path is the default network behavior (hardened math must be turned on by committee proposal), an attacker can craft `tokenQuant`/pool-state combinations (verified feasible by the project's own `ExchangeProcessorTest.testStrictMath`, which shows the legacy and BigDecimal-exact results *always* diverge across realistic values) to consistently bias the floating-point rounding in their favor across repeated `ExchangeTransactionContract` calls, incrementally draining `anotherTokenQuant` value from the shared exchange pool beyond what the exact constant-product/constant-supply invariant permits — an unbacked-balance/theft-of-funds condition affecting the pool creator and other holders of pool-backed assets.

### Likelihood Explanation
High: any unprivileged account can broadcast `ExchangeTransactionContract` transactions against any existing Exchange pool with attacker-chosen `tokenQuant`, and can iterate many small transactions to accumulate rounding-drift profit without needing elevated privileges, special timing, or state races.

### Recommendation
Route `ExchangeTransactionActuator`'s buy-quantity computation through the exact `BigDecimal`/`BigInteger` calculation (as already done in `SafeExchangeProcessor` and in `ExchangeInjectActuator`/`ExchangeWithdrawActuator`) unconditionally rather than gating it behind a governance-controlled flag, and add an explicit precision/consistency check in `ExchangeTransactionActuator.doValidate()` analogous to the "Not precise enough" check already present in `ExchangeWithdrawActuator`.

### Proof of Concept
1. Attacker creates or uses an existing Exchange pool with `firstTokenBalance`/`secondTokenBalance` values.
2. Attacker repeatedly submits `ExchangeTransactionContract` transactions with `tokenQuant` values chosen (offline, via replicating `ExchangeProcessor`'s double-precision formula) to land on rounding boundaries where `(long) issuedSupply`/`(long) exchangeBalance` truncate favorably.
3. Compare against `SafeExchangeProcessor`/BigDecimal-exact result for the same inputs — `ExchangeProcessorTest.testStrictMath` (lines 271-281) already demonstrates the legacy and exact results are never equal for the tested realistic inputs, confirming systematic exploitable drift.
4. Over many transactions, the attacker accumulates a measurable excess of `anotherTokenQuant` beyond the exact bonding-curve entitlement, depleting the pool relative to its true backing.

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
