### Title
Dust transfers fill a victim's `depositTokensOfAccount` list up to `MAX_TOKENS_PER_USER`, blocking new collateral deposits and transfers — unprivileged griefing DoS - ([File: contracts/Pool.sol](contracts/Pool.sol), [File: contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
The Spring Boot advisory (CVE-2023-34055) is an unprivileged-request denial-of-service class. The analogous reachable surface in Metronome is the per-account deposit-token list in `Pool`, capped by `MAX_TOKENS_PER_USER = 30` (`contracts/Pool.sol:79`). Any caller can push entries into *another* account's set for free: `DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance goes from 0 to non-zero (`contracts/DepositToken.sol:517-520`). There is no opt-in and no minimum amount — 1 wei suffices. Once the victim's set reaches 30 entries, `addToDepositTokensOfAccount` reverts with `UserReachedMaxTokens` (`contracts/Pool.sol:32`), which causes every subsequent deposit of a collateral type the victim does not already hold — including deposits made `onBehalfOf_` the victim by a third party (`contracts/DepositToken.sol:211-237` → `_mint` → `addToDepositTokensOfAccount`, `contracts/DepositToken.sol:486-488`) — to revert.

### Finding Description
Attack path, all public/unprivileged:

1. Victim holds debt in the pool (e.g. issued synth against collateral A), so `unlockedBalanceOf(victim)` is small or zero.
2. Attacker deposits dust (or obtains dust amounts) of every other `DepositToken` registered in the pool and calls `DepositToken.transfer(victim, 1)` for each. The `_revertIfLocked` check applies to the *sender* only (`contracts/DepositToken.sol:348-354`); nothing gates the recipient.
3. Each transfer appends the token to `depositTokensOfAccount[victim]` until it hits `MAX_TOKENS_PER_USER = 30`.
4. Result for the victim:
   - `deposit()` of any new collateral reverts at `_mint` → `addToDepositTokensOfAccount` → `UserReachedMaxTokens`. The victim cannot top up a *different* collateral to rescue an unhealthy position before liquidation.
   - The victim also cannot clear the dust entries: removing an entry requires sending the balance to zero via `transfer`/`withdraw`, both guarded by `_revertIfLocked` (`contracts/DepositToken.sol:180-182, 350, 409`). With `unlockedBalanceOf(victim) == 0` (fully utilized position, `contracts/DepositToken.sol:383-398`) every transfer out reverts, so the list cannot be shrunk. The lock is self-reinforcing: debt locks the dust, the dust locks out new collateral.
   - Additionally, `debtPositionOf`/`unlockedBalanceOf` iterate the whole set and call the oracle per entry, raising gas cost of every `transfer`/`withdraw`/`liquidate` touching the account — bounded at 30, but still attacker-inflicted.

No privileged role, oracle manipulation, or governance action is needed; the attacker's only cost is dust collateral and gas.

### Impact Explanation
Temporary freezing of funds / blocked liveness: a leveraged victim is denied the ability to deposit additional (new-type) collateral, which is the standard way to restore health and avoid liquidation. If collateral price moves against them, the position is liquidated where it would otherwise have been saved — indirect loss of funds attributable to the griefing. For debt-free victims the impact is weaker (they can transfer the dust out to reclaim slots), but for the worst case — a maxed-out position with `issuableInUsd == 0` — the victim has no self-help path until debt is repaid, which itself may require collateral they can no longer deposit.

### Likelihood Explanation
Likelihood is moderate-to-high within the DoS class: the attack requires only an EOA, dust amounts of whitelisted collaterals, and ordinary `transfer` calls. It is most effective against accounts that already carry debt, which are exactly the accounts for which blocked deposits are harmful. Cost scales with the number of distinct `DepositToken`s the pool has (bounded by `ReachedMaxDepositTokens`), but even filling a handful of remaining slots is enough to block a specific rescue collateral.

### Recommendation
- Do not mutate the victim's token set on plain transfers: restrict `addToDepositTokensOfAccount` on the `_transfer` path (only track tokens acquired via `deposit`/`seize`), or make transfers skip set insertion and treat untracked balances via a fallback in `debtPositionOf`.
- Alternatively, allow any account to remove zero-valued/dust entries, or exempt tiny balances from the `MAX_TOKENS_PER_USER` check in `addToDepositTokensOfAccount`.
- Allow removal of a token from the account's set regardless of the lock check (e.g. a `transfer` of locked dust is harmless because it doesn't reduce collateral below the locked threshold — the set-removal should be permitted even when `unlockedBalanceOf == 0`).

### Proof of Concept
Hardhat fork sketch (pseudocode — exact fixture names depend on deployment, which I could not fully enumerate within the index):

```ts
// victim has an open position: deposit(A), issue(synth) -> issuableInUsd == 0
for (const dt of allOtherDepositTokens) {
  await underlying(dt).connect(attacker).approve(dt.address, DUST_GROSS)
  await dt.connect(attacker).deposit(DUST_GROSS, attacker.address) // mint dust msdToken
  await dt.connect(attacker).transfer(victim.address, 1)           // adds token to victim's set
}
// assert set is at cap
expect(await pool.depositTokensOf(victim.address)).to.have.length(MAX_TOKENS_PER_USER) // 30

// victim can no longer deposit a new collateral type
await expect(newDepositToken.connect(victim).deposit(amount, victim.address))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')

// victim cannot clear dust entries while fully locked
await expect(dustToken.connect(victim).transfer(attacker.address, 1))
  .to.be.revertedWithCustomError(dustToken, 'NotEnoughFreeBalance')
```

Caveat: I verified the cap constant, the `UserReachedMaxTokens` revert site, the set-insertion on `_transfer`/`_mint`, and the `_revertIfLocked`/`unlockedBalanceOf` lock semantics from the indexed source; I did not read the full body of `addToDepositTokensOfAccount` or `debtPositionOf`, so the exact revert path and iteration cost should be confirmed before finalizing a PoC.
