### Title
Unprivileged dust-transfer griefing fills a victim's `depositTokensOfAccount`/`debtTokensOfAccount` list to `MAX_TOKENS_PER_USER`, blocking all new deposits and issuance for that account - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
The Keycloak advisory is an application-level DoS: an unauthenticated request with an oversized input forces expensive processing and degrades the service. The Metronome analog is an unprivileged account-list exhaustion attack: `Pool.addToDepositTokensOfAccount` is called automatically whenever a `DepositToken` balance moves from zero to positive, and it reverts once a user's combined deposit+debt token list reaches `MAX_TOKENS_PER_USER = 30`. Anyone can push arbitrary dust DepositTokens *to* a victim via plain `transfer`, so an attacker can fill all 30 slots and make every subsequent first-time deposit or new-synth issuance for that account revert with `UserReachedMaxTokens`, effectively DoS-ing position management for that account.

### Finding Description [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

`DepositToken._transfer` unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` when the recipient's balance of that token goes from 0 to positive — there is no opt-in, no minimum-amount check, and the sender-side lock check (`_revertIfLocked`/`unlockedBalanceOf`) only applies to the sender's balance, not the recipient's list state. `Pool.addToDepositTokensOfAccount` enforces `onlyIfAdditionWillNotReachMaxTokens`, which counts `debtTokensOfAccount + depositTokensOfAccount` against the shared cap of 30. The same cap gates `addToDebtTokensOfAccount`, invoked from `DebtToken.issue/mint` when a user first mints a new synthetic. Because `DepositToken.transfer` is a public, permissionless ERC20 entry point, any EOA can deposit a tiny amount of each whitelisted collateral into themselves and then `transfer(1 wei, victim)` per token until the victim's list hits the cap.

### Impact Explanation
Once saturated, the victim permanently (until they clean up) cannot:
- Deposit a *new* collateral type (the `addToDepositTokensOfAccount` call inside `DepositToken._deposit`/`_transfer` reverts, reverting the whole deposit).
- Receive any deposit token they don't already hold (transfers to them revert).
- Issue/mint a synthetic token whose debt token isn't already in their list — i.e. they cannot open new synth positions.

The victim must discover the dust entries and manually `transfer` each dust token out (paying gas per token, and possibly blocked if their position locks part of a balance) to free slots. This is temporary freezing of funds/liveness degradation inflicted unilaterally by an unprivileged attacker, analogous to forcing a Keycloak server to spend resources on crafted input — here the attacker weaponizes bounded storage/iteration coupled to an unconditional revert.

### Likelihood Explanation
- Fully unprivileged: only needs `DepositToken.deposit` + `transfer`, both public.
- Cost is bounded: attacker buys dust of up to 30 whitelisted deposit tokens. On deployments with fewer than 30 whitelisted collaterals the attacker can't fill the list alone with deposit tokens, but combined deposit+debt entries count together, and attack cost scales down linearly with the victim's pre-existing entries (a victim already holding N tokens needs only 30−N dust sends).
- No modifier helps: `whenNotPaused`/`nonReentrant`/`SynthContext` sender resolution do not restrict recipient choice, and `onlyIfAdditionWillNotReachMaxTokens` is the very mechanism being abused.
- The victim cannot preemptively prevent receiving dust since `addToDepositTokensOfAccount` is triggered by balance change, not consent.

### Recommendation
- Make the max-tokens check non-reverting for the *recipient* path: e.g., let `addToDepositTokensOfAccount` return false / silently skip on cap, and enforce the cap only on user-initiated actions (`deposit`, `issue`) where the caller can react.
- Alternatively require a minimum balance (e.g., `debtFloorInUsd`-scaled dust threshold) before adding to the per-account list, or allow anyone to call a `removeFromDepositTokensOfAccount`-style cleanup that deletes zero-balance/no-longer-needed entries so victims can self-heal in one tx.

### Proof of Concept
Hardhat-style sketch (fork or unit environment):

```ts
// attacker deposits dust of each whitelisted collateral and pushes to victim
const victim = bob.address;
const depositTokens = await pool.getDepositTokens(); // whitelisted collaterals
const slotsToFill = 30
  - (await pool.getDepositTokensOfAccount(victim)).length
  - (await pool.getDebtTokensOfAccount(victim)).length;

for (let i = 0; i < slotsToFill; ++i) {
  const dt = await ethers.getContractAt('DepositToken', depositTokens[i]);
  const underlying = await ethers.getContractAt('ERC20Mock', await dt.underlying());
  await underlying.mint(attacker.address, 1);
  await underlying.connect(attacker).approve(dt.address, 1);
  await dt.connect(attacker).deposit(1, attacker.address);
  await dt.connect(attacker).transfer(victim, 1);   // adds to victim's list
}

// victim's next first-time deposit reverts
const newDt = await ethers.getContractAt('DepositToken', depositTokens[slotsToFill]);
await expect(newDt.connect(bob).deposit(1e6, victim))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens');

// victim's first-time issue of a new synth also reverts via addToDebtTokensOfAccount
await expect(debtToken.connect(bob).issue(1, victim))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens');
```
