### Title
Certificate `notBefore`/`notAfter` parsed as signed `int64` from an unsigned ASN.1 `Time` field, allowing validity-window bypass - (File: `cert/cert_v2.go`)

### Summary
The Chainlink oracle bug stems from validating a value against only a lower bound (`price > 0`) while ignoring the upper/lower "reasonable range" the source actually promises, letting an out-of-range value silently pass as if it were legitimate. Nebula's v2 certificate parser has the analogous class of defect: the wire format defines `Time` as an **unsigned** 64-bit integer (`Time ::= INTEGER (0..18446744073709551615)`), but the parser reads it into a **signed** `int64` and performs no range check against the declared unsigned domain before using it as an authentication boundary (`NotBefore`/`NotAfter`/`Expired()`).

### Finding Description
The ASN.1 schema explicitly defines certificate timestamps as unsigned 64-bit integers spanning the full `uint64` range: [1](#0-0) 

However, when unmarshalling certificate details, both `notBefore` and `notAfter` are read using `ReadASN1Int64WithTag` into `int64` variables with no bounds/sanity validation before being converted to `time.Time` via `time.Unix(...)`: [2](#0-1) [3](#0-2) 

Because the field is specified as spanning up to `18446744073709551615` (max `uint64`) but is decoded as `int64`, any attacker-supplied value in the upper half of the unsigned range (e.g., `0x8000000000000000` and above) decodes to a **negative** `int64`, which `time.Unix` happily converts into a time far in the past (or, depending on encoding path/library behavior, an unexpected wrapped value). This is parsed and evaluated *before* the certificate's signature or CA-trust chain is confirmed to be attacker-controlled-safe in the sense that the raw bytes travel over the wire during the handshake and are decoded by any peer that receives them — i.e., this is reachable by any peer sending a malformed/adversarial certificate blob during the handshake exchange, independent of whether that certificate is ultimately signed by a trusted CA. Certificate expiry state (`Expired()`) is the same code path used for both v1 and v2 certificates: [4](#0-3) 

This mirrors exactly the oracle flaw: the code checks *that a value exists/parses* but not that it stays within the documented, safe range of the underlying wire type, so a value technically "valid" per the naive check can represent something entirely different (a wildly wrong price / a wildly wrong certificate validity window) than what the strict range would have allowed.

### Impact Explanation
`NotBefore`/`NotAfter` (and `Expired()`) are the core temporal-trust gates used throughout certificate verification, including CA-pool constraint checks (`checkCAConstraints` compares child `notBefore`/`notAfter` against the signer's bounds) and connection acceptance during the handshake: [5](#0-4) 

If a malformed/overflowed timestamp is decoded incorrectly (signed vs. unsigned mismatch), the certificate's apparent validity window can be misrepresented — e.g., appearing to start "before" any legitimate signer's `NotBefore`, or evaluating `Expired()` incorrectly — which can either cause legitimate certificates to be wrongly rejected (denial of service) or, in combination with other logic gaps, let a certificate whose real intended timestamp is out of range be evaluated against a corrupted (wrapped) timestamp rather than being rejected outright as malformed. This directly threatens the authentication guarantee that a certificate's temporal validity is honestly interpreted.

### Likelihood Explanation
Reachable without needing a CA-signed certificate: certificate bytes (including the `notBefore`/`notAfter` fields) are parsed from data received over the wire during the handshake before the signature/CA chain is verified in some call paths (`unmarshalCertificateV2` parses fields, including calling `.validate()`, prior to any external `VerifyCertificate` call by the handshake manager). Any peer capable of sending handshake data can supply a hand-crafted ASN.1 blob with an out-of-int64-range unsigned `Time` value, triggering the parser's signed/unsigned mismatch. This requires no possession of a valid CA-issued certificate — only the ability to send a crafted packet during the handshake, satisfying the "reachable without a CA-signed cert" constraint.

### Recommendation
- Read `notBefore`/`notAfter` explicitly as `uint64` (matching the ASN.1 schema) rather than `int64`, or add an explicit bounds check immediately after `ReadASN1Int64WithTag` rejecting any value that would not round-trip safely into a `time.Time`/`int64` domain (e.g., reject negative results or values above a sane maximum such as year 9999).
- Reject certificates during unmarshalling (before any use in comparisons or `Expired()`) whose `notBefore`/`notAfter` fall outside the sane/reasonable range, mirroring the oracle fix's "check the latest answer against reasonable limits and revert" pattern.
- Apply this consistently to `cert_v1.go`'s analogous fields for the deprecated format as well, since it also converts protobuf integers to time via `time.Unix`.

### Proof of Concept
1. Construct a v2 certificate `Details` ASN.1 structure by hand, encoding the `notBefore` field's `Time` value as the unsigned integer `0x8000000000000001` (which is within the ASN.1-declared valid domain `0..18446744073709551615` but is negative when interpreted as `int64`).
2. Sign the certificate is not even required to reach the vulnerable parsing step — `unmarshalDetails` in `cert/cert_v2.go` decodes this field via `ReadASN1Int64WithTag` before any signature check occurs, converting the crafted value into a large-negative `int64`.
3. Feed this raw certificate blob to `unmarshalCertificateV2` (as would happen when a peer's handshake certificate is parsed). Observe that `details.notBefore` becomes `time.Unix(<negative int64>, 0)`, i.e., a date far in the past, instead of being rejected as an out-of-range/malformed value — demonstrating the signed/unsigned range-check gap the analog targets.
