### Title
Unbounded per-reference-update loop in non-atomic `proc-receive` hook processing enables push-triggered resource-exhaustion DoS - (File: internal/gitaly/hook/receivepack/receive_pack.go)

### Summary
`procReceiveHook` handles reference updates received from `git-receive-pack(1)` via the `proc-receive` hook mechanism. When the push is non-atomic, it iterates over every reference update in the push with no upper bound on count, and for each single update it spawns a brand-new `git update-ref --stdin` subprocess (via `receivePackReferenceUpdates` → `updateref.New`) plus invokes the `update` hook. An ordinary user's push containing a very large number of ref updates drives this loop to spawn a correspondingly large, unbounded number of Git subprocesses and hook invocations sequentially inside a single RPC call.

### Finding Description
`procReceiveHook` branches on `handler.Atomic()`: [1](#0-0) 

In the non-atomic branch, the loop runs once per element of `handler.ReferenceUpdates()`, and for every single element it calls `receivePackReferenceUpdates(ctx, cfg, req, repo, hookManager, []hook.ReferenceUpdate{update}, handler, handler)` — i.e. one full updater lifecycle per ref.

Inside `receivePackReferenceUpdates`, each call spins up a new `updateref.Updater` process (`updateref.New` → `git update-ref --stdin`) and runs the `update` hook via `hookManager.UpdateHook`: [2](#0-1) 

The updates themselves originate from parsing an attacker-controlled pkt-line stream in `NewProcReceiveHandler`, which appends to `updates` with no cap on the number of entries: [3](#0-2) 

No code path in `procReceiveHook`, `receivePackReferenceUpdates`, or `NewProcReceiveHandler` enforces any maximum count of reference updates per push, nor a cumulative resource/time budget for the loop. This is directly analogous to the reported bug class: an unbounded loop over a client-supplied collection, where each iteration does non-trivial, expensive work (process spawn + hook execution), with no size cap — the git/RPC-resource equivalent of the Solidity `orderbook` DoS.

### Impact Explanation
A malicious or buggy client can push a single request containing an extremely large number of reference updates (e.g. tens of thousands of branch/tag pointer changes) targeting a repository configured to route updates through `receive.procReceiveRefs`/the proc-receive hook. This forces Gitaly to sequentially spawn one `git update-ref` process and one `update` hook invocation per reference inside a single RPC, consuming CPU, memory, file descriptors, and wall-clock time proportional to the number of updates, with no limit. This can stall or exhaust the serving Gitaly node handling that RPC (and, transitively, block the connected `ReceivePack` RPC and transaction that is waiting on the proc-receive handler), producing a denial of service for that repository/node until the request completes, times out, or exhausts server resources.

### Likelihood Explanation
The reachable trigger is an ordinary Git push (`git push` over SSH/HTTP → `ReceivePack`/`SSHReceivePackRequest`/`PostReceivePackRequest` → `git-receive-pack(1)` → proc-receive hook → `ProcReceiveHook` RPC → `procReceiveHook`), which is a normal, unprivileged user action; the only precondition is that the target ref namespace matches the server's `receive.procReceiveRefs` configuration, which is how Gitaly routes writes through its write-ahead log for transactional pushes. No special permissions beyond ordinary push access are required, and the number of ref updates in a push is fully attacker-controlled pkt-line input with no server-side cap.

### Recommendation
Impose a maximum number of reference updates accepted per proc-receive session (and/or per non-atomic `procReceiveHook` invocation), rejecting or chunking/streaming pushes that exceed it. Additionally, consider processing non-atomic updates with a shared/reused updater process (or batching several updates per `updateref.Updater` instance) instead of spawning a fresh Git process and hook execution per single reference, and enforce an overall time/resource budget for the loop so a pathological push cannot monopolize an RPC worker indefinitely.

### Proof of Concept
1. Configure a repository/server such that a pushed ref namespace is routed through `receive.procReceiveRefs` (as Gitaly does for WAL-tracked transactional updates).
2. As an ordinary authorized push user, construct a push (e.g., crafted pkt-line command list to `git-receive-pack`) containing a very large number (e.g. 100,000+) of distinct reference update commands in one request.
3. Observe that `NewProcReceiveHandler` accepts and stores all updates unbounded, and `procReceiveHook`'s non-atomic branch at internal/gitaly/hook/receivepack/receive_pack.go:116 iterates once per update, each iteration spawning a new `git update-ref` process and running the `update` hook via `receivePackReferenceUpdates`. Measure CPU/process/time consumption on the Gitaly node scaling linearly and unbounded with the number of updates, degrading or blocking the RPC handler for other requests.

func receivePackReferenceUpdates(
	ctx context.Context,
	cfg config.Cfg,
	req gitcmd.ReceivePackRequest,
	repo *localrepo.Repo,
	hookManager hook.Manager,
	updates []hook.ReferenceUpdate,
	stdout, stderr io.Writer,
) (returnedErr error) {
	hooksPayload, err := setupHooksPayloadEnv(ctx, cfg, req, repo, gitcmd.UpdateHook)
	if err != nil {
		return fmt.Errorf("creating hooks payload: %w", err)
	}

	updater, err := updateref.New(ctx, repo, updateref.WithNoDeref())
	if err != nil {
		return fmt.Errorf("spawning ref updater: %w", err)
	}
	defer func() {
		if err := updater.Close(); err != nil && returnedErr == nil {
			returnedErr = fmt.Errorf("cancel ref updater: %w", err)
		}
	}()

	if err := updater.Start(); err != nil {
		return fmt.Errorf("start reference transaction: %w", err)
	}

	for _, update := range updates {
		if err := hookManager.UpdateHook(
			ctx,
			req.GetRepository(),
			update.Ref.String(),
			update.OldOID.String(),
			update.NewOID.String(),
			[]string{hooksPayload},
			stdout, stderr,
		); err != nil {
			return fmt.Errorf("running update hook: %w", err)
		}

		if err := updater.Update(update.Ref, update.NewOID, update.OldOID); err != nil {
			return fmt.Errorf("queueing ref to be updated: %w", err)
		}
	}

	if err := updater.Commit(); err != nil {
		return updateError{error: err}
	}

	return nil
}
