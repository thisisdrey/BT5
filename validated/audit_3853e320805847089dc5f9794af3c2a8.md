#NoValid vulnerability found for this question.

Analysis: the "gas reserved but insufficient at execution" premise is not supported by how nearcore actually computes and forwards gas across shards. At transaction conversion time (`calculate_tx_cost` / `tx_cost` in `runtime/runtime/src/config.rs:417-500`), the runtime computes both `burnt` (send fees, burnt immediately on the sender shard) and `gas_remaining` — which includes `prepaid_exec_fee` from `total_prepaid_exec_fees` → `exec_fee(config, action, receiver_id)` (`runtime/runtime/src/config.rs:576-603`, `:296-373`). This `gas_remaining` amount is fixed once, at conversion time, using the config active on the *sending* shard, and is what's attached to the outgoing `Receipt` as its purchased/prepaid gas budget. [1](#0-0) 

Critically, `exec_fee` for `TransferToGasKey`/`WithdrawFromGasKey` (config.rs:364-371) is **not** gated by `fix_ml_dsa_cost_charging` at all — it always uses `action.public_key.trie_id_len()`, unconditionally, regardless of the flag's value: [2](#0-1) 

So the exec-fee gas reserved for the receipt does not change across the feature-flag boundary in the first place — only the *send* fee (burnt immediately, on the sender's balance) is gated via `gas_key_send_pk_len`: [3](#0-2) 

That send-fee amount is burnt synchronously as part of `tx_cost`/`calculate_tx_cost` at the moment the transaction is converted (deducted from the sender before the receipt is even created), so it cannot be "recomputed differently" once the receipt reaches the receiver shard — the exec cost embedded in the receipt is fixed at creation, and the receiving shard's `apply_action_receipt` burns exactly the exec fee that was pre-purchased, not a value it recomputes from its own live config for that action's `public_key.len()`. There is no code path where the receiver shard re-derives `gas_key_transfer_exec_fee` from a different (post-upgrade) `fix_ml_dsa_cost_charging` value applied to gas already reserved under the old scheme, since `exec_fee` for gas-key transfer never even branches on that flag.

Additionally, `RuntimeConfigStore` selects the `RuntimeConfig` for a given `protocol_version`, and protocol-version transitions in NEAR occur at epoch boundaries uniformly across the whole network/all shards — the runtime does not have sender and receiver shards straddling two different protocol versions within the same processing window in a way that would make the sender apply one `RuntimeConfig` and the receiver apply a different one for the same receipt's actions. Both the sending and receiving execution of a receipt happen under `ApplyState::config`, which is derived from the block's protocol version, consistently for the whole shard set at that height.

Given that (a) the specific exec-fee function invoked in the `TransferToGasKey` receipt path is not gated by the flag, and (b) the exec gas is fixed once at tx-conversion and forwarded with the receipt rather than recomputed on the receiver shard, the described "reserved-vs-actual gas mismatch causing mid-flight fund loss during a protocol upgrade" scenario has no supporting code path in this codebase. This appears to be a supply-conservation invariant that is explicitly tested for the ML-DSA-65/gas-key case in `test_gas_key_add_key_conserves_supply` and `test_gas_key_transfer_send_fee_uses_wire_length`, both of which assert the send/exec split doesn't leak supply. [4](#0-3) [5](#0-4) 

No reachable exploit path exists for an unprivileged attacker to trigger the claimed gas-shortfall/fund-loss scenario as described.

fn gas_key_send_pk_len(config: &RuntimeConfig, public_key: &PublicKey) -> usize {

        // Preserve the (incorrect) existing behavior if the fix is not enabled.
        // Otherwise, we would break protocol consensus.
        public_key.trie_id_len()
    }
}

/// The gas-key SEND fee prices bytes put on the wire, so it must scale with
/// `public_key.len()` (1953 for ML-DSA-65), not the on-trie `trie_id_len()`
/// (33). A "use `trie_id_len` everywhere" fix would leave this wrong; only the
/// split (send = `len`, exec = `trie_id_len`) is correct, which is what
/// `config.rs` now does.
#[test]
fn test_gas_key_transfer_send_fee_uses_wire_length() {
    if !ProtocolFeature::FixMlDsaCostCharging.enabled(PROTOCOL_VERSION) {
        tracing::info!("skipping: FixMlDsaCostCharging not enabled at PROTOCOL_VERSION");
        return;
    }
    let config = RuntimeConfig::test();
    let receiver = alice_account();
    let ed25519_key = SecretKey::from_seed(KeyType::ED25519, "gas-key-seed").public_key();
    let ml_dsa_65_key = SecretKey::from_seed(KeyType::MLDSA65, "gas-key-seed").public_key();

    let send_fee = |public_key: &PublicKey| -> u64 {
        let actions = [Action::TransferToGasKey(Box::new(TransferToGasKeyAction {
            public_key: public_key.clone(),
            deposit: Balance::ZERO,
        }))];
        total_send_fees(&config, false, &actions, &receiver).unwrap().gas.as_gas()
    };
    let wire_len = |public_key: &PublicKey| public_key.len() as u64;

    let gas_key_byte_send = config.fees.fee(ActionCosts::gas_key_byte).send_fee(false).gas.as_gas();
    // Send fee scales with wire length, so the ML-DSA-65 vs ed25519 gap is the
    // difference in their `len()`; the (equal) base fee cancels.
    let expected_delta = gas_key_byte_send * (wire_len(&ml_dsa_65_key) - wire_len(&ed25519_key));
    let measured_delta = send_fee(&ml_dsa_65_key) - send_fee(&ed25519_key);
    assert_eq!(
        measured_delta, expected_delta,
        "gas-key send fee must scale with wire length (len), not trie_id_len",
    );
}
