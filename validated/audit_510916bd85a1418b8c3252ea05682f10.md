### Title
Unauthenticated forgery of `StackerDBChunksEvent`/`BlockValidateResponse`/`BurnBlockEvent` via the signer's HTTP event listener - (File: libsigner/src/events.rs)

### Summary
`SignerEventReceiver::next_event` accepts and dispatches any HTTP POST to `/stackerdb_chunks`, `/proposal_response`, or `/new_burn_block` from any TCP client without verifying the sender is the configured Stacks node, and this is confirmed by the node's own event-dispatch code (`stacks-node/src/event_dispatcher/worker.rs::make_http_request`) which never attaches any credential to these outgoing requests. Anyone who can reach the signer's bound listener port can inject forged `StackerDBChunksEvent`, `BlockValidateResponse`, or `BurnBlockEvent` payloads directly into the signer runloop.

### Finding Description
The claimed equality — "sender of the HTTP event-POST == the Stacks node process the signer is configured to trust" — is never enforced anywhere in the code path. `SignerEventReceiver::bind` (`libsigner/src/events.rs:404-408`) opens a plain `tiny_http::HttpServer` on the configured address with no TLS, no peer-identity check, and no shared-secret verification. `next_event` (`libsigner/src/events.rs:413-458`) calls `http_server.recv()` and then dispatches solely on `request.url()` string equality and `request.method()`, handing the request straight to `process_event::<T, StackerDBChunksEvent>` (line 438), `process_event::<T, BlockValidateResponse>` (line 440), or `process_event::<T, BurnBlockEvent>` (line 442). `process_event` (lines 519–542) simply reads the body, does `serde_json::from_slice`, and converts via `TryFrom` into a `SignerEvent`, with no signature, HMAC, or bearer-token check at any point.

The only "auth" mechanism in this codebase, `[connection_options] auth_token` / signer's `auth_password` (documented at `stackslib/src/config/mod.rs:3802-3816`), secures the *opposite* direction — requests **to** the node's RPC endpoints (e.g., `/v2/blocks?broadcast=1`) — not the node's outbound event POSTs to the signer. This is corroborated by `stacks-node/src/event_dispatcher/worker.rs::make_http_request` (lines 325-397), which builds the outbound `StacksHttpRequest` and only sets a `Connection: close` header; no `Authorization` header or token is attached when POSTing to `/stackerdb_chunks`, `/proposal_response`, or `/new_burn_block`. Thus the guard the question describes does not exist anywhere in this path, and the equality is violated: any TCP client that can complete an HTTP/1.1 POST is treated identically to the trusted node.

### Impact Explanation
An attacker who can reach the signer's bound event-listener port can forge a `StackerDBChunksEvent` claiming to be signer/miner boot-contract chunks (processed via `TryFrom<StackerDBChunksEvent>`, `libsigner/src/events.rs:544-625`), a fake `BlockValidateResponse` (`libsigner/src/events.rs:627-635`), or a fake `NewBurnBlock` event (`libsigner/src/events.rs:637-649`). These are forwarded via `forward_event` directly into the signer's runloop channel, which drives block-signing decisions. This is an unauthenticated injection of node-origin data into the signer's decision-making pipeline, repeatable per TCP connection — matching the Critical category of "unauthenticated/unauthorized write to state" feeding forged data into consensus-adjacent logic.

### Likelihood Explanation
No preconditions beyond TCP reachability to the signer's listener port are required — no secret, no StackerDB slot ownership, no peer registration. The `endpoint` in sample configs (`sample/conf/mainnet-signer.toml`, etc.) defaults to `127.0.0.1:30000`/`0.0.0.0:30000`; if bound to a non-loopback or otherwise reachable interface (or reachable via container/network misconfiguration), the attack is trivial and repeatable at will with a single crafted HTTP POST.

### Recommendation
Require the signer's event listener to authenticate the caller — e.g., mirror the node's `auth_token`/`auth_password` scheme by requiring and validating an `Authorization` header on every POST to `/stackerdb_chunks`, `/proposal_response`, `/new_burn_block`, and `/new_block` in `SignerEventReceiver::next_event` before calling `process_event`, or bind exclusively to loopback and document that any non-loopback binding requires a reverse proxy that enforces mTLS/shared-secret auth. Update `stacks-node/src/event_dispatcher/worker.rs::make_http_request` to attach the shared token so both sides agree on a real credential check.
