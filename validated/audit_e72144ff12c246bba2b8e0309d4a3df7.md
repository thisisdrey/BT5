### Title
Chunked-request smuggling via `Content-Length` fallback in `StacksHttp::payload_len`/`read_payload` - (File: stackslib/src/net/httpcore.rs)

### Summary
`StacksHttp` never streams a chunked HTTP *request* body — `stream_payload` hard-fails with `NetError::InvalidState` for the `StacksHttpPreamble::Request` arm. Instead, all requests are treated as fixed-length via `payload_len()`/`read_payload()`, which derive the body length solely from `Content-Length`, defaulting to `0` when it is absent, and the `HttpRequestPreamble` parser never inspects or rejects a `Transfer-Encoding` header. This lets an attacker send a `Transfer-Encoding: chunked` request with no `Content-Length`; the server consumes 0 payload bytes while the chunk-encoded body remains in the buffer to be misparsed as the next request.

### Finding Description
`ProtocolFamily::payload_len` for a request unconditionally computes the length from `Content-Length` alone: [1](#0-0) 

`stream_payload` — the only code path that can consume a body whose length is not known up front (`payload_len() == None`) — explicitly refuses to do this for requests: [2](#0-1) 

Because `payload_len()` for `StacksHttpPreamble::Request` always returns `Some(..)` (it is `Some(get_content_length())`, and `get_content_length()` returns `0` when `content_length` is `None`), `stream_payload`'s request arm is provably unreachable — there is no code path that ever streams/decodes a chunked *request* body. All requests are instead routed through `read_payload`, which slices exactly `content_length` bytes (`0` if absent) as the entire body: [3](#0-2) 

`HttpRequestPreamble` only tracks `content_length: Option<u32>`; there is no field or parsing logic that recognizes `Transfer-Encoding`, so a request with `Transfer-Encoding: chunked` and no `Content-Length` header parses successfully with `content_length == None`: [4](#0-3) 

Attack: send `POST /v2/transactions HTTP/1.1\r\nHost: ...\r\nTransfer-Encoding: chunked\r\n\r\n<chunk-encoded body>` with no `Content-Length`. `read_preamble` finds the `\r\n\r\n` boundary and returns the preamble. `payload_len()` returns `Some(0)` (per the code cited above). The connection/dispatch layer then calls `read_payload` with `len = 0`, so `buf_data = &buf[0..0]` — an empty body is handed to the RPC handler (`try_parse_request`), and the reported bytes-consumed for the payload is `0`. The raw chunk-size line and chunk data the attacker actually sent (e.g. `"1a\r\n...\r\n0\r\n\r\n"`) are never consumed by the HTTP codec and remain sitting in the connection's read buffer immediately after the (now fully "consumed") request. On the next read/parse cycle over the same keep-alive connection, those leftover bytes are fed back into `read_preamble` as if they were the start of a brand-new HTTP message — i.e., request/response framing desync, breaking the invariant "bytes consumed for this request == bytes actually sent by the client for this request."

No guard exists to prevent this: there is no rejection of `Transfer-Encoding` on `HttpRequestPreamble`, no cross-check that `Content-Length` is present/consistent when `Transfer-Encoding: chunked` is set, and `stream_payload`'s request-side rejection only prevents attempting to *decode* chunked framing for requests — it does nothing to prevent the length being silently treated as `0`.

### Impact Explanation
An unauthenticated remote peer connecting to the node's RPC port can desynchronize HTTP framing on a keep-alive connection. Because the attacker fully controls the "leftover" bytes (their own chunk body), they can craft those leftover bytes to look like an attacker-chosen follow-on HTTP request line/headers, which the server will then parse and dispatch as an entirely new, distinct request on the same connection — the classic HTTP request-smuggling primitive. This is repeatable per connection and requires no privileges, matching the "Critical: request smuggling" impact category. The practical severity depends on what downstream component reuses the connection buffer across parsed messages (e.g., any proxy/cache in front of the node, or the node's own connection-handling loop treating the stream as a sequence of independent requests) — but the root desync condition inside `stackslib/src/net/httpcore.rs` is unconditional and confirmed by code.

### Likelihood Explanation
No special peer state, secret, or configuration is required — any remote client able to open a TCP connection to the RPC port can send this crafted request. It costs a single HTTP request and is fully repeatable. The only precondition is that the connection is kept alive so a subsequent parse occurs on the same buffer, which is the normal/default behavior for `keep_alive` HTTP/1.1 requests supported by `HttpRequestPreamble`.

### Recommendation
Reject requests that set `Transfer-Encoding: chunked` (or any `Transfer-Encoding` value) outright at preamble-parse time in `HttpRequestPreamble`'s deserialization, returning a `400 Bad Request` before `payload_len()`/`read_payload()` are ever invoked. Additionally, `get_content_length()` should not silently default missing `Content-Length` to `0` when a body-bearing verb (POST/PUT) is used together with `Transfer-Encoding`; instead this combination should be an explicit parse error.

### Proof of Concept
Rust test in `stackslib::net::tests::httpcore`:
1. Build raw bytes: `"POST /v2/transactions HTTP/1.1\r\nHost: 127.0.0.1:20443\r\nTransfer-Encoding: chunked\r\n\r\n5\r\nhello\r\n0\r\n\r\nGET /v2/info HTTP/1.1\r\nHost: 127.0.0.1:20443\r\n\r\n"`.
2. Call `StacksHttp::read_preamble(&bytes)` to get `(preamble, offset)`, assert it is `StacksHttpPreamble::Request(..)`.
3. Assert `http.payload_len(&preamble) == Some(0)` (line 1553).
4. Call `http.read_payload(&preamble, &bytes[offset..])`, assert it returns `(_, 0)` — zero bytes consumed for the payload — while `bytes[offset..]` still begins with `"5\r\nhello\r\n0\r\n\r\nGET /v2/info..."`.
5. Feed the remaining unconsumed slice (`&bytes[offset..]`, unchanged) back into `read_preamble`; assert it successfully parses a second, attacker-forged `GET /v2/info` request — demonstrating the framing desync/smuggled request.
