Found a concrete analog: java-tron's CREATE2/account-upgrade path converts a pre-existing normal (EOA) account into a `Contract` account type but never clears the account's owner/active permission data, mirroring the Mattermost bug class of "failing to clear credentials on account-type conversion."

### Title
Stale owner/active multisig permissions survive EOA→Contract account-type conversion via CREATE2, allowing the original key holder to retain control of the resulting contract account - (File: `actuator/src/main/java/org/tron/core/vm/program/Program.java`)

### Summary
When a `CREATE`/`CREATE2` deployment targets an address that already holds a pre-existing, non-contract `AccountCapsule` (e.g., funded by a prior `TransferContract` or with custom multisig permissions set via `AccountPermissionUpdateContract`), `createContractImpl` upgrades that account in place to `AccountType.Contract` by calling `existingAccount.updateAccountType(AccountType.Contract)` and `existingAccount.clearDelegatedResource()`, then persists it as the new contract account.

### Finding Description
`updateAccountType` only flips the `type` field of the `Account` proto [1](#0-0) , and `clearDelegatedResource` only zeroes acquired delegated-resource balances [2](#0-1) . Neither clears `ownerPermission`, `activePermission`, or `witnessPermission` that may have been previously set on that address via `AccountPermissionUpdateContract` (which only requires the target account to exist, with no restriction on its future re-use as a CREATE2 contract address) [3](#0-2) . The vulnerable conversion happens in `createContractImpl`: when `existingAccount != null` and the address is not already an active contract, it calls `updateAccountType`/`clearDelegatedResource` and writes the result back as the new contract's account state [4](#0-3) . Because the permission fields are untouched, any address/key that was previously authorized as owner or active permission on that account remains authorized after the conversion to a contract account, and TVM opcodes such as SUICIDE-to-account or subsequent `AccountPermissionUpdateContract`/transfer/freeze/delegate operations can still be authorized by that stale key even though the account is now semantically "owned" by the deployed contract logic.

### Impact Explanation
An attacker (or the original address owner) who pre-funds/pre-configures an address that a contract will later deploy to via CREATE2 (a fully deterministic, attacker-computable address) can retain authorization over that address's balance, frozen/delegated resources, and permission structure after it becomes a smart-contract account, enabling unauthorized transfers, freeze/unfreeze, or permission changes against funds the contract logic believes it exclusively controls. This matches the "unauthorized account operation / theft of funds" impact bar.

### Likelihood Explanation
Reachable purely by an unprivileged transaction broadcaster: send `AccountPermissionUpdateContract` to set custom keys on an address, then trigger any contract's CREATE2 deployment targeting that same address (deterministic via `getCreate2Addr`), which is a normal, permissionless TVM operation exercised in existing tests (`framework/src/test/java/org/tron/common/runtime/vm/FreezeTest.java` `testCreate2SuicideToAccount`) [5](#0-4) . No special privileges or SR/witness role required.

### Recommendation
When `createContractImpl` upgrades a pre-existing account to `AccountType.Contract` (the `existingAccount != null` branch), also clear `ownerPermission`, `activePermission`, and `witnessPermission` (reset to the contract's default/no-multisig state) in the same code path as `updateAccountType`/`clearDelegatedResource`, so no pre-set authorization key can act on the account after it becomes a contract.

### Proof of Concept
1. Attacker computes the deterministic CREATE2 address for a target factory contract and salt.
2. Attacker sends `AccountPermissionUpdateContract` naming the CREATE2 address as `owner_address` with attacker-controlled keys in `owner`/`active` permissions (the actuator only checks that the account currently exists and is not currently a witness) [6](#0-5) .
3. Attacker (or anyone) triggers the factory contract's `CREATE2` deployment to that address; `createContractImpl` converts the existing account in place via `updateAccountType`/`clearDelegatedResource`, leaving the attacker's permissions intact [7](#0-6) .
4. Attacker subsequently broadcasts transactions (transfer, freeze/unfreeze, further `AccountPermissionUpdateContract`) signed with the pre-set keys against the now-contract account and they validate successfully, since the stale permission structure was never cleared.
