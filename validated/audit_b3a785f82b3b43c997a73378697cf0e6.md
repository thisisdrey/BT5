### Title
Missing zero-address check on `depositTokenOf` result silently locks user funds - (File: contracts/NativeTokenGateway.sol)

### Summary
`NativeTokenGateway.deposit` and `VesperGateway.deposit`/`withdraw` call `pool_.depositTokenOf(...)` and use the returned `IDepositToken` without checking it for `address(0)`. Because EVM calls to a codeless address succeed with empty returndata (analogous to a null-pointer dereference that "succeeds" instead of crashing), `SafeERC20.safeApprove` and `deposit()` on `address(0)` are no-ops that do not revert. The transaction completes, but the user's funds (native ETH wrapped to WETH, or underlying ERC-20 converted to vTokens) remain in the gateway with no `msdToken` minted — permanently locked, recoverable only via the governor's `sweep` (which sends them to the governor, not the user).

### Finding Description
In `NativeTokenGateway.deposit` (`contracts/NativeTokenGateway.sol:46-54`):

```solidity
nativeToken.deposit{value: msg.value}();
IDepositToken _depositToken = pool_.depositTokenOf(nativeToken);
nativeToken.safeApprove(address(_depositToken), 0);
nativeToken.safeApprove(address(_depositToken), msg.value);
_depositToken.deposit(msg.value, _msgSender());
```

Only `pool_` is validated via `isPoolRegistered`. If the registered pool has no deposit token for `nativeToken` (e.g., a pool that never added WETH as collateral), `depositTokenOf` returns `address(0)`. `safeApprove(address(0), ...)` is a low-level call on the *WETH contract* targeting no meaningful spender — harmless but pointless — and `_depositToken.deposit(...)` is a high-level Solidity call on `IDepositToken(address(0))`. Since `address(0)` has no code, the EVM call succeeds and returns empty data; no revert occurs. The WETH stays in the gateway.

The same pattern exists in `VesperGateway`:

- `deposit` (`contracts/VesperGateway.sol:61-64`): attacker/user-supplied `vToken_` that is not registered collateral in `pool_` → `depositTokenOf(vToken_)` returns `address(0)` → vTokens stay locked in the gateway.
- `withdraw` (`contracts/VesperGateway.sol:79-83`): `safeTransferFrom` on `address(0)` "succeeds" (empty returndata is interpreted as success by `SafeERC20._callOptionalReturn`), then `_depositToken.withdraw(...)` on `address(0)` returns empty data — the ABI decode of `(uint256,)` reverts, so withdraw actually reverts rather than silently locking; the deposit paths are the exploitable ones.

The transient-sender path via `Operator.execute` is equally affected since `_msgSender()` is resolved but the `address(0)` deposit token is still used.

### Impact Explanation
Any caller who invokes `deposit` on a registered pool that lacks the corresponding deposit token loses the full `amount_`/`msg.value`: the funds sit in the gateway contract which has no withdrawal path for users. They can only be moved by the governor via `TokenHolder.sweep`, which transfers them to the governor — i.e., the user cannot recover them unilaterally, and recovery depends on a privileged party. This is a direct loss / freezing of user funds caused by dereferencing a null (zero-address) contract, the Solidity analog of the libfpx NULL-pointer dereference: a missing validity check turns a null object into silent corruption instead of a clean revert.

### Likelihood Explanation
Requires a registered pool that does not list `nativeToken` (or the given `vToken_`) as collateral — plausible on multi-pool deployments where pools support different collateral sets. No privileged action is needed to trigger; the caller simply supplies a valid registered `pool_`. Reachable by any EOA or contract, directly or through `Operator.execute`. Likelihood is gated on a user (or integrated UI/bot) calling the gateway with an unsupported pool/token pair — the function gives no revert to warn integrators, making integration mistakes silent fund-loss events.

### Recommendation
In `NativeTokenGateway.deposit`/`withdraw` and `VesperGateway.deposit`/`withdraw`, revert if `pool_.depositTokenOf(token)` returns `address(0)` (e.g., `error DepositTokenDoesNotExist()`), and ideally validate `vToken_` against the pool's registered collateral list before pulling any funds. Perform validation before `safeTransferFrom`/`nativeToken.deposit` so no assets are held by the gateway on the failure path.

### Proof of Concept
Foundry fork-style test (Hardhat equivalent works against `E2E.base.test.ts` fixtures):

```solidity
function testDepositNativeIntoPoolWithoutNativeDepositToken() public {
    // pool is registered but has no DepositToken for WETH
    IPool pool = IPool(REGISTERED_POOL_NO_WETH);
    NativeTokenGateway gw = new NativeTokenGateway(poolRegistry, IWETH(WETH));

    vm.deal(alice, 1 ether);
    vm.prank(alice);
    // Should revert, but silently succeeds:
    gw.deposit{value: 1 ether}(pool);

    // Alice received no msdToken, WETH is trapped in the gateway
    assertEq(IERC20(WETH).balanceOf(address(gw)), 1 ether);
    assertEq(pool.depositTokenOf(IERC20(WETH)).balanceOf(alice), 0);
    // Only governor can move the funds (via sweep), not alice
}
```

Equivalent for `VesperGateway.deposit`: approve underlying, call `deposit(registeredPool, unregisteredVToken, amount)` — underlying is pulled, vTokens are minted to the gateway, `IDepositToken(0).deposit` no-ops, vTokens are stuck.
