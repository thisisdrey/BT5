### Title
Hard-Coded Non-Mainnet/Testnet EVM `CHAIN_ID` (399) in the ETH-Implicit Wallet Contract Enables Cross-Chain Transaction Replay - ([File: runtime/near-wallet-contract/build.rs])

### Summary
The NEAR ETH-implicit Wallet Contract embeds an EVM-style `CHAIN_ID` at compile time as a replay-protection value for Ethereum-style transactions routed through `rlp_execute`. Only three fixed values exist — `397` for mainnet, `398` for testnet, and `399` for "localnet" — and nearcore's runtime falls back to the `399`-baked artifact for **every other** chain (any custom/forked NEAR network), exactly mirroring the reported bug class of a compile-time constant that is correct for one network but silently wrong/reused for all others.

### Finding Description
The wallet-contract build script only produces three WASM variants, hard-coding the EVM chain id per variant: [1](#0-0) 

The chain id is baked directly into the contract logic via an `include!`-ed constant: [2](#0-1) 

and is enforced as the sole binding-to-network replay guard inside `validate_tx_relayer_data`, which every `rlp_execute` call must pass: [3](#0-2) 

At runtime, nearcore selects which of the three precompiled artifacts (and which corresponding global-contract hash) to use for a given ETH-implicit account purely by matching on the network's string `chain_id`, defaulting anything that isn't literally `"mainnet"` or `"testnet"` to the `LOCALNET` build (`CHAIN_ID = 399`): [4](#0-3) 

This selection is wired directly into the unprivileged, ordinary-user path of ETH-implicit account creation — any user can trigger it merely by sending a `Transfer` to an address of the form `0x...`: [5](#0-4) 

Because the ETH-implicit account address is derived solely from the user's secp256k1 public key (`keccak256(pubkey)[12:32]`), it is **identical across every NEAR-based chain** for the same key pair, regardless of the chain's actual `chain_id` string. Any two independently operated NEAR networks that are neither `mainnet` nor `testnet` (e.g. two different forks/testing networks/L1s built from this codebase) will therefore both deploy the exact same `LOCALNET` wallet-contract bytecode with the exact same hard-coded `CHAIN_ID = 399` to the exact same account address for a given key. A signed RLP Ethereum transaction (which encodes `chain_id`, `to`, `nonce`, and the action payload) that validly authorizes an action for the user's account on chain A will pass `validate_tx_relayer_data`'s chain-id and nonce checks equally well on chain B, since both contracts accept `chain_id == 399` and both accounts independently track their own nonce starting at 0. Consequently a transaction the user only intended to authorize on one such network can be captured and resubmitted (replayed) by any relayer against the user's identically-addressed account on another such network, executing the same `Transfer`, `FunctionCall`, `AddKey`, or `DeleteKey` action there without the user's separate consent for that chain.

### Impact Explanation
This allows an attacker (or a malicious/careless relayer) who observes a user's signed `rlp_execute` payload on one non-mainnet/testnet NEAR chain to replay it on any other such chain where the user's ETH-implicit account happens to hold funds, causing unauthorized transfers or function calls — i.e., theft/loss of funds and authorization escalation across otherwise-independent chains, without requiring any additional signature from the victim. Because ETH-implicit accounts cannot have a full-access key added or be deleted per protocol design, victims have no way to preemptively neutralize the risk other than never reusing a key across chains built from this same contract — which the protocol offers no way to detect or prevent.

### Likelihood Explanation
Medium — it requires two or more independently deployed NEAR-based chains (both outside the `mainnet`/`testnet` chain-id strings) built from the same nearcore/wallet-contract release, which is a realistic and even encouraged scenario given nearcore is designed to be reused for custom/forked networks and the `LOCALNET` variant is the explicit "catch-all" default for any chain id other than the two production ones.

### Recommendation
Derive the EVM-style `CHAIN_ID` embedded in the wallet contract from the actual NEAR network's `chain_id` (e.g., via a deterministic hash/derivation of the genesis `chain_id` string, or an injected/immutable per-deployment parameter) instead of hard-coding three fixed values and defaulting every other network to the same `399`. At minimum, the runtime selection logic in `wallet_contract_magic_bytes` / `eth_wallet_global_contract_hash` should fail closed (refuse to create the global-contract-backed ETH-implicit account) for any `chain_id` string it does not explicitly recognize, rather than silently reusing the `LOCALNET` artifact.

### Proof of Concept
1. Stand up two independent NEAR-based networks, "chainA" and "chainB", neither of which uses `chain_id` string `"mainnet"` or `"testnet"` (e.g., two separate testing/L1 deployments of nearcore).
2. Both networks resolve to the same `LOCALNET` wallet-contract global hash and the same embedded `CHAIN_ID = 399`, per `eth_wallet_global_contract_hash`/`wallet_contract_magic_bytes` (`runtime/near-wallet-contract/src/lib.rs:68-105`).
3. A user derives the same ETH-implicit account id on both chains from the same secp256k1 key (`derive_eth_implicit_account_id`), and funds both via ordinary `Transfer` actions, creating the same wallet-contract-backed account on each chain (`runtime/runtime/src/actions.rs:246-261`).
4. The user signs one Ethereum-style RLP transaction (nonce 0, chain_id 399) authorizing a `Transfer` of funds intended only for chainA.
5. A relayer submits the identical RLP bytes via `rlp_execute` to the user's account on chainB. `validate_tx_relayer_data` accepts it because `tx.chain_id == Some(399)` matches chainB's `CHAIN_ID` and the nonce (0) matches chainB's independent nonce counter, executing the transfer on chainB without the user's chainB-specific authorization.
