### Title
Unbounded arithmetic overflow in TRC10 market order matching can permanently poison a price level and block all future trades against it - ([File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java])

### Summary
`MarketSellAssetActuator` matches an incoming taker's `MarketSellAssetContract` against a FIFO list of resting maker orders in `matchOrder`/`matchSingleOrder`, crediting both maker and taker accounts via `addTrxOrToken` → `AccountCapsule.addAssetAmountV2`. That credit path uses `addExact`, which throws `ArithmeticException` on overflow. `execute()` only declares a catch clause for `ItemNotFoundException | InvalidProtocolBufferException | BalanceInsufficientException | ContractValidateException` — it does **not** catch `ArithmeticException`, unlike the sibling `ExchangeCreateActuator`, `ExchangeInjectActuator`, and `ExchangeTransactionActuator`, which explicitly catch and wrap `ArithmeticException` into `ContractExeException`. This mirrors the reported "rogue token" pattern: an unprivileged party (here, an order placer) can pre-position state that deterministically makes a shared multi-party settlement path throw, blocking everyone else who tries to use that shared resource.

### Finding Description
`matchOrder` walks the resting order list for a token pair/price and calls `matchSingleOrder` for each match, which calls: [1](#0-0) 
crediting both taker and maker through `addTrxOrToken`, which for non-TRX tokens calls `accountCapsule.addAssetAmountV2(...)`: [2](#0-1) 

`addAssetAmountV2` performs `addExact(currentAmount, amount, disableJavaLangMath)` which throws `ArithmeticException` on `long` overflow: [3](#0-2) 

`execute()`'s catch clause omits `ArithmeticException`: [4](#0-3) 

By contrast, the analogous `Exchange*` actuators explicitly catch this case and have dedicated regression tests for it: [5](#0-4) [6](#0-5) 

An account holder is free to acquire a near-`Long.MAX_VALUE` balance of a TRC10 token they control (e.g., by issuing their own asset with total supply close to `Long.MAX_VALUE` and holding most of it), then place a resting maker order that sells another token for that near-max-balance token at a chosen price. Any subsequent taker order that matches this maker order at that price will trigger `addExact` overflow while crediting the maker, throwing an uncaught `ArithmeticException` instead of the checked exceptions `execute()` expects. Because the maker's poisoned order sits at the head of the `MarketOrderIdListCapsule` for that exact price and is never consumed (the match never completes since the enclosing transaction fails and its state changes revert), every future taker transaction attempting to match that price/pair combination will repeatedly fail in the same way.

### Impact Explanation
Market matching against the poisoned resting order becomes reliably unavailable: any legitimate taker who submits a `MarketSellAssetContract` matching that exact price is guaranteed to have their transaction fail every time it is retried, since the underlying overflow condition and the un-consumed poisoned order persist. Because `MarketSellAssetActuator` shares this order-book queue across all order placers, a single unprivileged account can degrade or deny normal exchange functionality for that specific token pair/price for as long as the poisoned order remains in the book (only the poisoner can remove it via cancellation). This maps to the "exchange and market order handling" surface explicitly in scope, and to the reported bug class of "any unprivileged actor can trigger an unhandled exception in a loop that is supposed to serve other parties, disabling their transactions."

### Likelihood Explanation
Any account can issue a TRC10 asset with `totalSupply` up to `Long.MAX_VALUE` (java-tron does not disallow issuing assets with maximum supply) and hold nearly all of it, then place a maker order via `MarketSellAssetActuator`. No special privilege, whitelist, or governance approval is required — this is fully reachable by any signed transaction from an ordinary account (an "order placer").

### Recommendation
Add `ArithmeticException` to the caught exception types in `MarketSellAssetActuator.execute()` (and any other paths in `matchOrder`/`matchSingleOrder`) so overflow failures are converted to a clean `ContractExeException` and, more importantly, ensure the poisoned maker order can be safely evicted/rolled back or invalidated instead of remaining indefinitely at the head of the price queue, so it cannot permanently block matching for other participants. Consider validating credit amounts against `Long.MAX_VALUE - currentBalance` before attempting the match, and/or automatically retiring/skip an order whose fill would overflow the counterpartyâ€™s balance rather than aborting the whole transaction.

### Proof of Concept
1. Attacker issues TRC10 token `T` with `totalSupply` ≈ `Long.MAX_VALUE` and holds nearly all of it (via `AssetIssueContract`).
2. Attacker places a `MarketSellAssetContract` selling some other token `S` and buying `T` at a chosen price (resting maker order), causing their own account's `T` balance to be pushed to a value just below `Long.MAX_VALUE` after any subsequent partial fill (or set up so the first fill would already overflow, per `matchSingleOrder`'s `addTrxOrToken(makerOrderCapsule, makerBuyTokenQuantityReceive)` call at [7](#0-6) ).
3. A victim taker submits `MarketSellAssetContract` selling `T` and buying `S` at the matching price; `matchOrder` selects the attacker's resting order via `hasMatch`/`priceKeysList` at [8](#0-7) .
4. `addAssetAmountV2` on the attacker's account throws `ArithmeticException` from `addExact`; this propagates unhandled out of `execute()` since it is not in the catch list at [4](#0-3) , and every future taker order matching that exact price fails identically, since the poisoned order remains unconsumed at the head of the queue.
