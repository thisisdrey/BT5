### Title
StackerDB chunk signature omits the target contract identifier, enabling cross-DB replay of validly-signed chunks - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` binds a signed StackerDB chunk only to `(slot_id, slot_version, data_hash)` and never to the smart-contract identifier of the StackerDB it is destined for. Because the Nakamoto signer-set boot contract publishes the *same* per-cycle slot assignment to every signer message-type contract (`signers-<X>-1`, `signers-<X>-2`, `signers-<X>-3`), a given signer occupies the identical `slot_id` in all three contracts of a given reward-cycle parity. A validly signed chunk originally produced for one message-type contract (e.g. `BlockPreCommit`) can therefore be replayed byte-for-byte into another message-type contract (e.g. `StateMachineUpdate`) at the same slot, and it will pass `SlotMetadata::verify()` and `PeerNetwork::validate_received_chunk`/`StackerDBTx::try_replace_chunk` because none of those checks bind the signature to the contract being written.

### Finding Description
`SlotMetadata::auth_digest()` hashes only `slot_id`, `slot_version`, and `data_hash`: [1](#0-0) 

The smart-contract identifier that the chunk is destined for is *not* part of what is signed or verified. In the RPC write path, the contract is taken purely from the URL path and is never checked against anything inside the signed payload: [2](#0-1) 

Server-side acceptance only checks per-contract slot ownership (`get_slot_signer`) and the signature over the contract-agnostic digest, both in the RPC path (`try_replace_chunk`) and in the p2p gossip/download path: [3](#0-2) [4](#0-3) 

Crucially, the slot assignment that determines which address owns which `slot_id` is shared verbatim across all three signer message-type contracts for a given reward-cycle parity: `.signers` stores one `stackerdb-signer-slots-<parity>` list, and every `signers-<parity>-<message_id>` contract reads from that same list via `stackerdb-get-signer-slots-page`: [5](#0-4) 

This is confirmed by the test that iterates over all `message_id` values and asserts identical slot assignments regardless of message type: [6](#0-5) 

The message-type contract itself is only encoded as `X` in `signers-<parity>-X`, resolved by `MessageSlotID::stacker_db_contract`: [7](#0-6) 

Consequently, for a fixed reward-cycle parity, a given signer S occupies the same `slot_id` in the `BlockResponse`, `StateMachineUpdate`, and `BlockPreCommit` StackerDB contracts simultaneously. Any observer who captures a validly-signed `StackerDBChunkData` that S posted to one of these contracts can resubmit it (via `POST /v2/stackerdb/.../chunks` or via unsolicited `StackerDBPushChunk`) at the same `slot_id`/`slot_version` to a *different* message-type contract that S also participates in. `SlotMetadata::verify()` recovers the same public key and matches the same owning address for that slot, so the write is accepted as authentic for the wrong contract's replica, overwriting or blocking S's legitimate content there and causing the mismatched, out-of-context payload to propagate to every peer replicating that DB (via `StackerDBChunkInv`/push relay).

### Impact Explanation
This breaks the intended equality "signed for contract A" == "valid in contract A only." A remote, unprivileged party can cause a chunk that was authorized for one signer message channel to be accepted and propagated as canonical content for a different signer message channel, corrupting that signer's slot content there and forcing that signer to publish a higher version before they can recover the slot. Because acceptance happens in the p2p/gossip and RPC write paths that immediately relay accepted chunks to the network (`validate_received_chunk` gating both `StackerDBChunkInv` bookkeeping and push-chunk buffering/propagation), this is a network-wide propagation of forged/misdirected data into StackerDB replicas — an unauthorized write to StackerDB state from an unprivileged remote actor, matching the Critical impact bucket ("unauthenticated/unauthorized write to state or StackerDB" / "network-wide propagation of forged data").

### Likelihood Explanation
Exploitation requires no privileges beyond observing one legitimately broadcast chunk (StackerDB traffic is itself unauthenticated/observable network traffic) and resubmitting it to a sibling contract endpoint that any node exposes. The precondition — identical slot assignment across the three signer message-type contracts for a given cycle parity — is a structural, deterministic property of `.signers.clar`, not a rare coincidence, so the attack is reliably reproducible whenever version bookkeeping allows the replayed version to be accepted (i.e., whenever the target contract's slot has not yet advanced past that version, which is common immediately after signer-set rotation or on any lagging replica).

### Recommendation
Include the destination StackerDB's `QualifiedContractIdentifier` (or a stable numeric ID tied to it) inside `SlotMetadata::auth_digest()` / the signed payload, and require the verifying node to check that the contract passed to `verify()`/`try_replace_chunk()` matches the one bound into the signature, so a chunk signed for one StackerDB contract cannot be replayed as valid for another.

### Proof of Concept
1. Wait for reward cycle `N` (parity `P`) to start; signer `S` is assigned `slot_id = k` in `signers-P-1`, `signers-P-2`, and `signers-P-3` (guaranteed identical assignment per `signers.clar`'s shared `stackerdb-signer-slots-P` list).
2. Observe `S` legitimately POST/push a `StackerDBChunkData { slot_id: k, slot_version: v, sig, data }` to `signers-P-3` (`BlockPreCommit`).
3. Replay the identical bytes via `POST /v2/stackerdb/<addr>/signers-P-2/chunks` (or `StackerDBPushChunkData` with `contract_id = signers-P-2`).
4. `try_replace_chunk`/`validate_received_chunk` calls `slot_desc.verify(&slot_validation.signer)`, which succeeds because the digest never included the contract, and the slot's owning signer is the same `S` in both contracts; if `v` exceeds `signers-P-2`'s current slot version, the write is accepted and gossiped as the canonical `StateMachineUpdate` chunk for slot `k`, even though `S` never authorized that content for `StateMachineUpdate`.

    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)

            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,

        NakamotoSigners::make_signers_db_contract_id(reward_cycle, self.to_u32(), mainnet)
    }
    fn all() -> &'static [Self] {
        MessageSlotID::ALL
    }
}
