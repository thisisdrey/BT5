### Title
Nanosecond-timestamp handshake staleness comparison allows key collision → legitimate reconnect rejected (stale-handshake bypass) - ([File: handshake_manager.go], [File: handshake/machine.go])

### Summary
Nebula's handshake completion path uses a nanosecond wall-clock timestamp (`payload.Time`, surfaced as `HostInfo.lastHandshakeTime`) purely as a "is this handshake newer than what I already have" comparator. Exactly like the referenced report (timestamp used as a de-facto unique/ordering key that can collide), the timestamp granularity assumption is not guaranteed on all platforms, and the comparison operator used (`>=`) treats equal timestamps as "not newer," which changes trust/acceptance behavior for a new handshake attempt.

### Finding Description
The handshake payload's `Time` field is generated with:
```go
p.Time = uint64(time.Now().UnixNano())
``` [1](#0-0) 

This value is copied into `Result.HandshakeTime` when the payload is processed:
```go
m.result.RemoteIndex = remoteIndex
m.result.HandshakeTime = payload.Time
m.payloadSet = true
``` [2](#0-1) 

and stored on the `HostInfo` as `lastHandshakeTime`, which is documented as being used specifically "to avoid an attack where a handshake packet is replayed after some time":
```go
// lastHandshakeTime records the time the remote side told us about at the stage when the handshake was completed locally
// Stage 1 packet will contain it if I am a responder, stage 2 packet if I am an initiator
// This is used to avoid an attack where a handshake packet is replayed after some time
lastHandshakeTime uint64
``` [3](#0-2) 

`CheckAndComplete()` then uses this field to decide whether a new handshake for an already-known peer should be accepted or rejected as stale:
```go
// Is this a newer handshake?
if existingHostInfo.lastHandshakeTime >= hostinfo.lastHandshakeTime && !existingHostInfo.ConnectionState.initiator {
    return existingHostInfo, ErrExistingHostInfo
}
``` [4](#0-3) 

Two properties combine to create the analog to the referenced timestamp-collision bug class:
1. `time.Now().UnixNano()` is not guaranteed to be monotonically unique across calls on all platforms/clock implementations — the linked upstream report explicitly notes the same class of issue ("There is an issue on mac approximating time in microseconds"), i.e., timer resolution can be coarser than a nanosecond, so two distinct legitimate handshakes can carry an identical `Time` value.
2. The comparison is `>=`, not `>`. When `lastHandshakeTime` collides (equal), the *new* handshake is unconditionally treated as not-newer and rejected with `ErrExistingHostInfo`, even though it is a legitimate, freshly-completed handshake.

This mirrors the report's root cause (a coarse/duplicable timestamp being relied upon as if it were a unique/ordering key), just applied to handshake freshness/replay decisions rather than a DB key.

### Impact Explanation
When a timestamp collision occurs between an existing (older) hostinfo's `lastHandshakeTime` and an incoming legitimate handshake's `Time` (e.g., because the peer's clock resolution or system clock granularity produces the same nanosecond value, or because two rapid re-handshakes from the same remote land in the same tick), Nebula's `CheckAndComplete` will discard the legitimate new handshake and keep the old `HostInfo`/tunnel state. This is a remote state-poisoning-adjacent condition reachable by any peer that can complete a handshake (not requiring a CA-signed cert beyond what any legitimate peer already has for normal operation), and it directly affects the exact mechanism the code comment says exists "to avoid an attack where a handshake packet is replayed after some time" — i.e., the anti-replay/freshness gate for handshake completion can misbehave due to timestamp non-uniqueness, causing valid reconnections/rekeys to be dropped and stale tunnel state to persist.

### Likelihood Explanation
Likelihood is moderate: it requires two `Time` values to be numerically equal at nanosecond granularity, which is more probable on systems/OSes with coarser clock resolution (as explicitly called out in the analogous upstream finding) or under handshake retry storms where completion events can land within the same clock tick. It does not require a malicious/unauthenticated attacker with special privileges — it is triggered by ordinary legitimate re-handshake traffic under adverse timing/clock conditions, making it a real reliability/availability concern rather than a purely theoretical one.

### Recommendation
Do not rely on wall-clock timestamps as an ordering/uniqueness signal for handshake staleness decisions. Options:
- Use a monotonically increasing, collision-free sequence/counter allocated per handshake completion (similar to `localIndexId`/`messageCounter` generation elsewhere in the code) instead of `time.Now().UnixNano()`.
- If a timestamp must be retained for cross-host comparison, combine it with a tie-breaking unique value (e.g., handshake/session nonce or index) so that equal timestamps do not collapse into "not newer."
- At minimum, change the comparison semantics so an equal timestamp does not automatically reject the new handshake (e.g., treat equality as ambiguous and prefer accepting a handshake carrying a valid, freshly-verified certificate/signature over blindly keeping stale state).

### Proof of Concept
Deterministic PoC sketch (unit-test level, mirroring the referenced report's approach):
1. Construct two `handshake.Result`s (or directly two `HostInfo`s) such that `HandshakeTime`/`lastHandshakeTime` are forced to the same `uint64` value — this can be done by mocking `time.Now()` in `handshake/machine.go`'s `marshalOutgoing` (via dependency injection or monkey-patching in tests) to return identical nanosecond values for two sequential calls, simulating coarse clock resolution.
2. Call `HandshakeManager.CheckAndComplete()` with an `existingHostInfo` already installed in `mainHostMap.Hosts` and a new `hostinfo` carrying the colliding `lastHandshakeTime`.
3. Assert that the call returns `ErrExistingHostInfo` even though the new handshake is legitimate and current, demonstrating that the equal-timestamp path incorrectly discards a valid, non-stale handshake — exactly analogous to the linked report's PoC showing that `MsgsToProcessedMsgs()` batches share colliding timestamps.

Note: I could not find any additional monotonic disambiguator (e.g., a nonce or counter) mixed into `lastHandshakeTime`/`HandshakeTime` anywhere in the reachable code paths (`handshake/machine.go`, `handshake_manager.go`, `hostmap.go`), so the collision path described above is the exact analog reachable without a CA-signed certificate beyond normal peer handshake participation.
