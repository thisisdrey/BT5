Confirmed TOCTOU race in `TronJsonRpcImpl.getFilterResult()` / `getFilterLogs()`: `containsKey()` is checked and then `get(filterId)` is called separately, with an intervening `uninstallFilter()` call from another JSON-RPC client able to remove the entry between the two calls.

### Title
Time-of-check/time-of-use race between `uninstallFilter` and `getFilterResult`/`getFilterLogs` causes NullPointerException / crash of JSON-RPC filter handling - (File: framework/src/main/java/org/tron/core/services/jsonrpc/TronJsonRpcImpl.java)

### Summary
`TronJsonRpcImpl` maintains filter maps (`eventFilter2ResultFull`, `blockFilter2ResultFull`, and their solidity counterparts) as `ConcurrentHashMap` instances shared across all JSON-RPC clients [1](#0-0) . `eth_uninstallFilter` removes a filter entry from these maps at any time, from any client, without any coordination with concurrent readers [2](#0-1) . Meanwhile, `getFilterResult()` (used by `eth_getFilterChanges`) and `getFilterLogs()` perform a `containsKey()` check followed by a separate `get()` call, with no atomicity between the two operations [3](#0-2) , [4](#0-3) .

### Finding Description
This mirrors the bug class in CVE-2024-35861: a resource (session/filter) can be torn down concurrently by another actor while a second code path is mid-use of that resource, because the check for validity and the subsequent use are not atomic.

In `getFilterResult()`:
```java
if (blockFilter2Result.containsKey(filterId)) {
  List<String> blockHashList = blockFilter2Result.get(filterId).popAll();   // (1)
  ...
  blockFilter2Result.get(filterId).updateExpireTime();                     // (2)
}
```
If a concurrent `eth_uninstallFilter` call removes `filterId` from the map after `containsKey()` returns `true` but before line (1) or (2) executes, `get(filterId)` returns `null`, and the subsequent `.popAll()` / `.updateExpireTime()` call throws a `NullPointerException`. The same pattern exists in `getFilterLogs()` (`containsKey` at line 1565, `get(filterId)` at line 1569) [4](#0-3) .

Both `newFilter`/`uninstallFilter`/`getFilterChanges`/`getFilterLogs` are reachable by any anonymous JSON-RPC client, since filter IDs are simply generated identifiers with no ownership/authentication check tying a filter to the caller that created it [5](#0-4) , [2](#0-1) . Any anonymous client that can guess or observe a filter ID (filter IDs are sequential/predictable via `generateFilterId()`) can race `eth_uninstallFilter` against another client's `eth_getFilterChanges`/`eth_getFilterLogs` call to trigger the null-pointer condition on the concurrently-executing request thread.

### Impact Explanation
Unlike the kernel UAF (which corrupts memory and can lead to RCE/crash of the whole process), Java's garbage collector prevents true dangling-pointer memory corruption. The concrete impact here is confined to an uncaught `NullPointerException` inside the specific JSON-RPC request-handling thread that lost the race, resulting in a failed request/HTTP 500 response for that call. There is no evidence in the explored code that this exception propagates to crash the whole node process (it is caught by the surrounding request-handling framework), so this does not rise to a full node-crash/halt as required by the acceptance bar, only to a localized, easily-triggerable request failure for legitimate filter consumers under concurrent access.

### Likelihood Explanation
High likelihood of triggering the race under normal or adversarial concurrent JSON-RPC usage, since `eth_uninstallFilter`, `eth_getFilterChanges`, and `eth_getFilterLogs` are all unauthenticated, publicly reachable RPC methods with no synchronization between the check-then-act sequence in the read paths and the removal in `uninstallFilter`.

### Recommendation
Replace the `containsKey()` + `get()` pattern in `getFilterResult()` and `getFilterLogs()` with a single atomic `Map.get()` call (storing the result and null-checking it), or use `computeIfPresent`/`Optional` idioms so a concurrent removal cannot occur between the existence check and the use of the value, analogous to skipping/guarding torn-down entries in the referenced kernel fix.

### Proof of Concept
1. Client A calls `eth_newFilter` (or `eth_newBlockFilter`) and obtains `filterId`.
2. Client A calls `eth_getFilterChanges(filterId)` (or `eth_getFilterLogs`), which enters `getFilterResult`/`getFilterLogs` and passes the `containsKey(filterId)` check.
3. Concurrently, Client B (or a malicious/racing thread) calls `eth_uninstallFilter(filterId)`, removing the entry from the shared map between the `containsKey` check and the subsequent `get(filterId)` call in step 2.
4. Client A's request thread executes `blockFilter2Result.get(filterId).popAll()` (or `eventFilter2Result.get(filterId).getLogFilterWrapper()`), which throws `NullPointerException` because `get(filterId)` now returns `null`, failing the request.

**Uncertainty note:** I could not fully verify from the indexed code whether the outer HTTP/JSON-RPC dispatcher always catches this `NullPointerException` gracefully or whether under some invocation paths it could propagate further; a full session review of the JSON-RPC transport layer (e.g., `TronJsonRpc`, Jetty/JsonRpcServer wiring) would be needed to conclusively bound the blast radius.

  @Override
  public boolean uninstallFilter(String filterId) throws ItemNotFoundException,
      JsonRpcMethodNotFoundException {
    disableInPBFT("eth_uninstallFilter");

    Map<String, BlockFilterAndResult> blockFilter2Result;
    Map<String, LogFilterAndResult> eventFilter2Result;
    if (getSource() == RequestSource.FULLNODE) {
      blockFilter2Result = blockFilter2ResultFull;
      eventFilter2Result = eventFilter2ResultFull;
    } else {
      blockFilter2Result = blockFilter2ResultSolidity;
      eventFilter2Result = eventFilter2ResultSolidity;
    }

    filterId = ByteArray.fromHex(filterId);
    if (eventFilter2Result.containsKey(filterId)) {
      eventFilter2Result.remove(filterId);
    } else if (blockFilter2Result.containsKey(filterId)) {
      blockFilter2Result.remove(filterId);
    } else {
      throw new ItemNotFoundException(FILTER_NOT_FOUND);
    }

    return true;
  }
