### Title
StackerDB write-rate throttle (`write-freq`) is enforced only on the read/sync path, not on the actual chunk-write path, letting a valid slot signer bypass it entirely - ([File: stackslib/src/net/stackerdb/db.rs])

### Summary
The StackerDB `write-freq` parameter is a contract-configured rate limit meant to bound how often a given slot may be rewritten. It is enforced only when a node is deciding whether to *fetch* a chunk from peers, but is never checked on the authoritative *write* path that actually stores/commits a chunk, whether via the HTTP `POST /v2/stackerdb/.../chunks` endpoint or via p2p relay of pushed/synced chunks. A signer who owns a slot can therefore write to it as fast as the network will let them (bounded only by `max_writes`), completely defeating the intended `write-freq` throttle — this mirrors the referenced bug class where a time-based gate meant to bound a costly, network-wide operation is bypassed because the check exists on one path but not on the state-mutating path.

### Finding Description
`StackerDBTx::try_replace_chunk` — the single authoritative function that commits a new chunk version to the database — checks chunk size, slot-signer signature validity, version monotonicity (`StaleChunk`), and `max_writes`, but never checks the elapsed time since the slot's last write against `self.config.write_freq`: [1](#0-0) 

This function is invoked directly by the HTTP chunk-upload RPC handler, which stores whatever the client submits as long as `try_replace_chunk` succeeds: [2](#0-1) 

and it is the same function used when committing chunks obtained via p2p sync/relay: [3](#0-2) 

The only place `write_freq` is actually consulted is `StackerDBSync::make_chunk_request_schedule`, which uses it purely to decide whether the *local* node should bother requesting a chunk from a peer (an advisory, non-authoritative check on the read/pull side): [4](#0-3) 

The chunk-validation routine used for unsolicited pushes/downloads explicitly documents that it skips the write-frequency check, deferring it to "the caller" — but no caller on the write path implements it: [5](#0-4) 

The `write-freq` value itself is a value returned by the StackerDB-controlling smart contract, meant to bound the write cadence of the DB per the documented `stackerdb-trait`: [6](#0-5) 

Because `try_replace_chunk` is the sole gate for both HTTP-submitted and p2p-relayed chunks, a signer holding a valid private key for even one slot can submit a monotonically-incrementing chunk as fast as `max_writes` allows, with zero regard to `write_freq`. Each accepted write is also unconditionally re-broadcast to all peers via `p2p.broadcast_message`, so this bypass additionally forces excessive p2p propagation traffic network-wide.

### Impact Explanation
This breaks the equality between "intended write cadence per the StackerDB-controlling contract" (`write_freq`) and "actually enforced write cadence" (unbounded, up to `max_writes`). An unprivileged-but-registered signer can spam their slot at maximum rate, defeating the throttle the protocol relies on to bound replica storage churn and to bound p2p chunk-broadcast traffic — each accepted write in `relay.rs::process_stacker_db_chunks` triggers a `StackerDBPushChunk` broadcast to the network. This is a bounded-but-real resource-abuse/DoS vector reachable by any legitimate, already-registered signer with no additional privilege, and does not require large volumetric traffic to be effective — the amplification comes from the missing per-write timing gate itself, not from raw request volume.

### Likelihood Explanation
High. Any StackerDB signer already has the two pieces of information required — their own private key and the current slot version — that `try_replace_chunk` checks; nothing stops them from submitting write after write (each with a valid signature and a monotonically increasing `slot_version`) far faster than `write_freq` intends, via the standard `POST /v2/stackerdb/.../chunks` RPC.

### Recommendation
Enforce `write_freq` inside `StackerDBTx::try_replace_chunk` (or immediately before calling it in `insert_chunk`/the RPC handler), by comparing the slot's stored `write_time` against `get_epoch_time_secs()` and rejecting the write (e.g., with a new `Error::TooFrequentWrite`-style variant) if the elapsed time is less than `config.write_freq`, mirroring the same check already performed advisory-side in `sync.rs`.

### Proof of Concept
1. Deploy/observe a StackerDB contract with `write-freq` set to some non-zero value (e.g. 300 seconds).
2. As a registered signer for slot `N`, submit a validly-signed `StackerDBChunkData` with `slot_version = 1` via `POST /v2/stackerdb/<contract>/chunks` — accepted (per `poststackerdbchunk.rs` / `try_replace_chunk` in `db.rs`).
3. Immediately submit another validly-signed chunk for the same slot with `slot_version = 2` — this succeeds instantly (no `write_freq` check exists in `try_replace_chunk`), even though less than 300 seconds have elapsed since the previous write.
4. Repeat up to `max_writes` times, in rapid succession, each one triggering a full `StackerDBPushChunk` broadcast to the p2p network in `relay.rs::process_stacker_db_chunks`, entirely bypassing the intended `write_freq` cadence.

    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
