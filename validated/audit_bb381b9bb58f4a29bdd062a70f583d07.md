Based on my research, I found a genuine analog to the Mattermost archived-channel authorization bypass in java-tron's shielded transaction API gating mechanism.

### Title
Inconsistent enforcement of `allowShieldedTransactionApi` gate allows private-key-bearing shielded API endpoints to be reached when the feature is disabled - (File: `framework/src/main/java/org/tron/core/Wallet.java`)

### Summary
Mattermost's CVE-2024-47145 involves a global "view archived channels" toggle that is checked on the primary UI path but not on a secondary path (direct file links), letting an attacker reach data the setting is supposed to hide. java-tron has a structurally identical pattern: `node.allowShieldedTransactionApi` is documented as an off-by-default safety gate that prevents shielded/Sapling wallet RPCs — which accept raw spending keys (`ak`, `nsk`, `ovk`) as parameters — from being invoked on untrusted/remote nodes [1](#0-0) . The gate is implemented as a single private helper, `checkAllowShieldedTransactionApi()`, that individual `Wallet` methods must explicitly call [2](#0-1) , and it is applied inconsistently across the roughly two dozen shielded-related `Wallet` methods (27 call sites found, e.g. `createShieldedTransactionWithoutSpendAuthSig` [3](#0-2) , `getShieldTransactionHash` [4](#0-3) , `createShieldedContractParametersWithoutAsk` [5](#0-4) ). Notably, `getNullifier(ByteString id)` — a shielded-pool query method sitting immediately next to `checkAllowShieldedTransactionApi()` in the file — does **not** call the gate at all [6](#0-5) , and it is exposed directly over gRPC/HTTP without any check.

### Finding Description
The `allowShieldedTransactionApi` flag exists specifically because "some shielded transaction APIs require sending private keys as parameters. Calling these APIs on untrusted or remote nodes may leak your private keys" [1](#0-0) . Operators who leave this flag at its default `false` value expect *all* shielded RPC/HTTP endpoints to be blocked. However, the enforcement is not centralized in the RPC/HTTP dispatch layer (unlike the generic `disabledApi` mechanism, which is enforced uniformly by `HttpApiAccessFilter` and `RpcApiAccessInterceptor` for arbitrary configured endpoints) [7](#0-6) [8](#0-7) . Instead, each individual `Wallet` shielded method must remember to call the private helper `checkAllowShieldedTransactionApi()` [2](#0-1) . `getNullifier` reads directly from `chainBaseManager.getNullifierStore()` and returns shielded-pool nullifier data with no such check [6](#0-5) , meaning it is reachable via its gRPC/HTTP wrapper on any node regardless of the operator's `allowShieldedTransactionApi = false` setting. This is the same root-cause shape as the Mattermost bug: a security control meant to gate an entire feature category is enforced per-endpoint rather than centrally, so any endpoint the developers forgot to individually gate bypasses the control — an unprivileged anonymous API client only needs to call the ungated endpoint directly.

### Impact Explanation
`getNullifier` itself only discloses shielded-pool nullifier bytes (limited information leak, not private-key or fund-theft impact), so on its own this is a low/medium confidentiality issue. The broader/root concern is architectural: because the flag's enforcement is scattered across dozens of individually-annotated call sites in `Wallet.java` instead of centrally enforced (as `disabledApi` is), any future or currently-missed shielded endpoint that accepts private key material (`ak`/`nsk`/`ovk`) and forgets the `checkAllowShieldedTransactionApi()` call would leak spending keys to a remote, anonymous API caller — directly matching the documented threat model in the config comment. I could not exhaustively verify every one of the ~15+ shielded gRPC service methods in `RpcApiService.java` against the 27 `checkAllowShieldedTransactionApi()` call sites within this session (e.g., I was unable to confirm whether `scanShieldedTRC20NotesByIvk`/`Ovk`, `isShieldedTRC20ContractNoteSpent`, `getTriggerInputForShieldedTRC20Contract`, and `getMerkleTreeVoucherInfo` internally gate correctly), so the full blast radius (whether any key-bearing endpoint besides the confirmed `getNullifier` gap is unguarded) is unconfirmed and would need direct code review of each method body.

### Likelihood Explanation
High for the confirmed gap: `getNullifier` requires no authentication, no special node configuration beyond a default install, and is reachable by any anonymous gRPC/HTTP client via `Wallet.getNullifier`. Exploiting it requires only sending the nullifier ID lookup request to a node the operator believed had shielded APIs disabled.

### Recommendation
Centralize the `allowShieldedTransactionApi` check rather than relying on per-method calls scattered through `Wallet.java`. At minimum, add `checkAllowShieldedTransactionApi()` to `getNullifier`, and audit every gRPC/HTTP shielded endpoint (`RpcApiService`, `RpcApiServiceOnSolidity`, and the corresponding `services/http/*Shielded*Servlet.java` classes) against the full list of 27 existing call sites to ensure no shielded/key-bearing endpoint is missing the gate. Consider enforcing the flag at the interceptor/filter layer (similar to `HttpApiAccessFilter`/`RpcApiAccessInterceptor`) for a fixed list of shielded method names, so new shielded endpoints are gated by default rather than opt-in.

### Proof of Concept
1. Deploy a FullNode with default config (`allowShieldedTransactionApi` unset/false, per `reference.conf`) [1](#0-0) .
2. As an anonymous client, call the gRPC/HTTP wrapper that invokes `Wallet.getNullifier(ByteString id)` with a known nullifier ID.
3. Observe that the shielded-pool nullifier data is returned successfully [6](#0-5) , despite the operator's expectation (per the security warning in the config) that this class of API is fully disabled.
