### Title
Unvalidated attacker-controlled length/offset fields in ABI array extraction helpers cause out-of-bounds array access - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The SQLite bug class is "a length field is read from an untrusted, attacker-supplied buffer and used to index/copy memory without validating that it fits inside the buffer, causing a heap overflow." The same pattern exists in java-tron's precompiled-contract ABI-decoding helpers `extractBytes32Array`, `extractBytesArray`, and `extractSigArray`, which read `len`/`offset` values directly out of the `DataWord[] words` array (itself derived from raw transaction/contract call `data`) and use them to size and index arrays without validating them against the actual bounds of `words` or `data`.

### Finding Description
`extractBytesArray` and `extractSigArray` read a `len` value via `words[offset].intValueSafe()` and then loop `for (int i = 0; i < len; i++)`, dereferencing `words[offset + i + 1]` and computing `bytesOffset`/`bytesLen` from further attacker-controlled words, finally calling `extractBytes(data, ..., bytesLen)` which does `Arrays.copyOfRange(data, offset, offset + len)`: [1](#0-0) 

None of `len`, `bytesOffset`, or `bytesLen` are checked against `words.length` or `data.length` before being used as array indices/copy lengths, apart from a single guard on the initial `offset` (`offset > words.length - 1`). `extractBytes32Array` has no bounds guard at all: [2](#0-1) 

This mirrors `sessionReadRecord`'s root cause: a length taken from untrusted input is trusted implicitly and used to drive memory reads/writes past the end of the backing buffer, rather than being validated against the buffer's real size.

### Impact Explanation
If an attacker supplies calldata to a precompiled contract that uses these helpers with a crafted `len` (e.g., large positive, causing `ArrayIndexOutOfBoundsException` when indexing `words[offset+i+1]`) or crafted offsets pointing beyond `data.length` (causing `ArrayIndexOutOfBoundsException` in `Arrays.copyOfRange`), the JVM throws an unchecked exception during precompiled-contract execution inside the TVM interpreter. If this exception is not caught at every call site (I could not fully confirm this from the code I reviewed), it could propagate out of `Program`/`Runtime` execution during block application, causing node crashes or divergent handling across nodes (potential chain halt or DoS), which matches the "node crash or halt" impact class accepted for this analog.

### Likelihood Explanation
Any unprivileged account can invoke a smart contract that performs a `CALL`/`STATICCALL` to the precompiled contract address backing these helpers with fully attacker-controlled `data`, making this trivially reachable from a single signed transaction — no special privilege is required.

### Recommendation
Add explicit bounds checks in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` verifying that `len`, `offset + i + 1`, `bytesOffset`, and `bytesLen` stay within `words.length` and `data.length` before use, returning an empty/invalid result (matching the pattern already used for the `offset > words.length - 1` guard) instead of allowing raw array indexing on attacker-supplied values. Ensure calling `execute()` methods also defensively catch `RuntimeException` around these calls so malformed input reverts the transaction instead of throwing uncaught exceptions during block processing.

### Proof of Concept
Craft calldata to the precompiled contract that uses `extractBytesArray`/`extractSigArray` such that the encoded array-length word (`words[offset]`) is a very large value (e.g., `0xFFFFFFFF`) or such that a subsequent offset word points past the end of `data`. When decoded, `len` will exceed the actual number of remaining words, causing `words[offset + i + 1]` to throw `ArrayIndexOutOfBoundsException`, or `extractBytes(data, offset, len)` to throw the same when `offset + len > data.length`. This is directly analogous to feeding `sessionReadRecord` a record whose declared field length exceeds the actual buffer size.

**Note on incomplete verification:** I was unable to confirm, within the available tool calls, exactly which precompiled contract(s) (e.g., a batch-signature-validation precompile referenced by `BatchValidateSignContractTest`) invoke `extractSigArray`/`extractBytesArray`, nor whether their `execute()` methods wrap these calls in try/catch that would downgrade the impact to a safe revert rather than an uncaught crash. This should be verified directly in the repository (e.g., via a Devin session with full file access) before treating the "node crash/halt" impact as fully proven.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }

  private static byte[][] extractSigArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          SIG_LENGTH);
    }
    return bytesArray;
  }

  private static byte[] extractBytes(byte[] data, int offset, int len) {
    return Arrays.copyOfRange(data, offset, offset + len);
  }
