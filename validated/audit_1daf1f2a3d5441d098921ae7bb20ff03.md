### Title
Effects-after-interaction ordering in `borrow` / `collateral-add` allows a reentrant call before position state is updated - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`market.clar`'s `borrow` performs the external token transfer (`vault-system-borrow`) *before* the scaled-debt bookkeeping write (`debt-add-scaled` in `v0-market-vault.clar`), and `market-vault.clar`'s `collateral-add` calls `receive-tokens` (an external `contract-call?` into the SIP-010 `ft` trait) *before* it inserts the updated position entry. Unlike the vault contracts (`v0-vault-usdc.clar`, etc.), which guard state-mutating entrypoints with an `in-flashloan` / `ERR-REENTRANCY` check, `v0-4-market.clar` and `v0-market-vault.clar` have no reentrancy guard at all.

### Finding Description
In `borrow` [1](#0-0) , the health check passes, then `(try! (vault-system-borrow asset-id amount funds-receiver))` executes and moves funds out of the vault to `funds-receiver` — only afterward is `debt-add-scaled` called to record the new scaled debt in `market-vault.clar`. This is a checks-effects-interactions violation: the external transfer happens strictly before the position/debt state is committed.

Similarly, `collateral-add` in `v0-market-vault.clar` calls `(try! (receive-tokens ft amount account))` (a `contract-call?` into the caller-supplied `ft <ft-trait>` implementation) and only afterward calls `(insert updated-entry)` to persist the updated mask/collateral amount [2](#0-1) .

The vault contracts (e.g. `v0-vault-usdc.clar`) explicitly recognize this class of risk and guard `deposit`/`redeem` with `(asserts! (not (var-get in-flashloan)) ERR-REENTRANCY)` [3](#0-2) , but no equivalent guard variable or assertion exists anywhere in `v0-4-market.clar` or `v0-market-vault.clar`. If a `ft <ft-trait>` implementation reachable through the registered-asset dispatch (any code path invoked during `contract-call? ft transfer` / `receive-tokens` / `send-tokens`) executes further logic before returning — e.g. an accrual side effect, an internal cross-vault call, or any contract logic that re-enters `market.clar` — it would observe the pre-write mask/scaled-debt/collateral state, since the effects (`insert`, `debt-add-scaled`) have not yet landed. This mirrors exactly the reentrancy class described in the external report for `univTransfer`/`depositAndBorrow`/`borrow`: interaction before effects, with no mutex protecting the affected methods.

### Impact Explanation
If a reentrant call during the token transfer step manages to invoke another market operation (e.g. a second `borrow` or `collateral-remove`) before the first operation's effects are committed, the health/LTV check performed by the nested call would be evaluated against stale collateral/debt state, potentially allowing a borrow or withdrawal that would not pass a correctly-ordered health check. This can result in extraction of funds beyond what the true collateral/health state allows — direct theft of user/protocol funds at rest, or protocol insolvency, which maps to the Critical impact category.

### Likelihood Explanation
Exploitability is currently constrained: `ft` in `borrow`/`collateral-add` must resolve via `get-asset ft-address` to one of the DAO-registered asset contracts, so an attacker cannot trivially substitute a fully attacker-controlled SIP-010 implementation as the callback vector without a registry compromise (out of scope per the rules). However, the ordering flaw itself is a genuine, provable violation of the checks-effects-interactions pattern in code that is otherwise reachable by any ordinary principal's `borrow`/`collateral-add` call, and the vault contracts' own `in-flashloan` guards demonstrate the team is aware such external calls are a reentrancy vector elsewhere in the codebase — yet the guard is absent in `market.clar`/`market-vault.clar`. Likelihood should be treated as low-to-medium pending confirmation of whether any currently-registered asset/vault contract can execute logic during the transfer call that loops back into `market.clar`.

### Recommendation
Reorder `borrow` so `debt-add-scaled` (the state write) occurs before `vault-system-borrow` (the external transfer), or introduce a reentrancy mutex (e.g. a `locked`/`in-flashloan`-style variable analogous to the one already used in the vault contracts) guarding all state-mutating public entrypoints in `v0-4-market.clar` and `v0-market-vault.clar`. Apply the same fix to `collateral-add`'s `receive-tokens`-before-`insert` ordering, and audit all other market/market-vault entrypoints for the same interaction-before-effects pattern.

### Proof of Concept
Conceptual call trace, mirroring the report's `depositAndBorrow` example:
```
borrow(assetA, amount)
  -> health check passes (pre-state)
  -> vault-system-borrow -> contract-call? ft transfer ... (external call to registered asset/vault contract)
       -> [if invoked contract executes further logic before returning]
            -> borrow(assetA, amount) [reentrant]
                 -> health check evaluated against STILL-STALE debt/collateral
                    (debt-add-scaled from the outer call has not yet executed)
                 -> passes, second withdrawal proceeds
  <- debt-add-scaled (outer) finally commits
```
A concrete, fully attacker-controlled trigger requires either (a) a currently-registered asset/vault contract that performs re-entrant logic during transfer, or (b) a future DAO-approved asset addition with such behavior; this could not be fully confirmed against the current registered-asset set within the available index, so this should be verified against the live `assets.clar` registry contents and each registered token/vault's transfer implementation.
