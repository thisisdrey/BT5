This is a legitimate analog to the Fantasm `mint()` bug: an unhardened floating-point (double/`Math.pow`) supply calculation that is reachable pre-activation of the hardening fix, and can also be toggled off-and-on again by a committee proposal, temporarily re-exposing the unsafe legacy math to any TRX/TRC10 holder submitting an `ExchangeTransactionContract`.

### Title
Legacy double-precision bancor-style calculation in `ExchangeProcessor.exchange()` allows attacker-influenced rounding/precision drift when `ALLOW_HARDEN_EXCHANGE_CALCULATION` is not enacted - (File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java)

### Summary
Like Fantasm's `mint()`, whose bonding-curve math used an imprecise decimal computation that let an attacker extract more `xFTM` than backed, java-tron's TRC10 Bancor-style exchange pool computes buy/sell amounts with `double`/`Math.pow` in `ExchangeProcessor` [1](#0-0) . The chain ships a corrected, `BigDecimal`-based implementation, `SafeExchangeProcessor` [2](#0-1) , but which processor is used is controlled entirely by the `hardenedCalc` flag derived from the `ALLOW_HARDEN_EXCHANGE_CALCULATION` dynamic property, checked per-transaction in `ExchangeCapsule.transaction()` [3](#0-2) .

### Finding Description
`ExchangeTransactionActuator.execute()` calls `exchangeCapsule.transaction(tokenID, tokenQuant, dynamicStore.allowStrictMath(), allowHarden())`, where `allowHarden()` simply reads `chainBaseManager.getDynamicPropertiesStore().allowHardenExchangeCalculation()` [4](#0-3) . When this flag is `false` — i.e. before the corresponding committee proposal (`ALLOW_HARDEN_EXCHANGE_CALCULATION`, id 928 range in `ProposalUtil`) is enacted, or if a witness/committee cohort ever proposes to set it back to `0` (the validator explicitly permits toggling it to either `0` or `1`) [5](#0-4)  — the exchange falls back to the legacy `ExchangeProcessor`, which computes the bonding-curve output using raw IEEE-754 `double` arithmetic and `Math.pow` [6](#0-5) . The project's own regression test demonstrates that the legacy path and the hardened path produce *different* results for identical inputs (`Assert.assertNotEquals(anotherTokenQuant, result)`), confirming the double-math path is imprecise relative to the `BigDecimal` ground truth [7](#0-6) . Any account can invoke this arithmetic directly and repeatedly via a normal, unprivileged `ExchangeTransactionContract` broadcast, choosing `sellTokenQuant`/pool ratios that maximize the drift between the imprecise double computation and the true, backed value, extracting the other side's token/TRX balance from the pool at a rate not actually supported by the pool's real value — mirroring exactly how the Fantasm attacker chose `(100e18, 1)` to trigger the "decimal error" in `_xftmOut`.

### Impact Explanation
Exploiting the floating-point drift lets any exchange participant repeatedly siphon value out of a TRC10 `Exchange` pool (theft of pooled TRX/TRC10 assets belonging to other participants) without any privileged access — an unbacked-balance/fund-theft scenario, matching the Medium/High bar for "unauthorized account operation, theft ... of funds."

### Likelihood Explanation
Exploitability depends entirely on the current value of `allowHardenExchangeCalculation`. On networks where the harden proposal has already been enacted and is fixed at `1` forever, this analog is not currently reachable; but the proposal validator explicitly still allows setting the flag back to `0` (`value != 0 && value != 1` is the only proposal-level restriction) [8](#0-7) , and any private/test/fork network that has not yet enacted this fork parameter is running the exact unsafe legacy path today. The only actuation needed by the attacker is broadcasting ordinary `ExchangeTransactionContract` transactions — no elevated privileges are required.

### Recommendation
Remove or restrict the ability for `ALLOW_HARDEN_EXCHANGE_CALCULATION` to ever be reset back to `0` once activated (mirror the "already valid, no need to propose again" pattern used for `ALLOW_STRICT_MATH` instead of allowing bidirectional toggling), and consider retiring `ExchangeProcessor`'s double-based math entirely, always using `SafeExchangeProcessor`, independent of a togglable committee flag.

### Proof of Concept
Analogous to the referenced `Fantasm_exp.sol`: on a chain/testnet where `allowHardenExchangeCalculation()` is `false`, create an `Exchange` pool with two TRC10 tokens (or TRX+TRC10), then broadcast an `ExchangeTransactionContract` with a `quant` chosen so that `sellTokenQuant / newBalance` lands near a `Math.pow` rounding boundary in `exchangeToSupply`/`exchangeFromSupply` (as in `ExchangeProcessorTest.testStrictMath`, which enumerates dozens of such `(balance, buyBalance, quant)` triples yielding divergent legacy vs. hardened results) [9](#0-8) ; repeat the trade to accumulate the excess `anotherTokenQuant` beyond what the pool's true backed reserves support, draining the counterparty side of the pool.

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }
