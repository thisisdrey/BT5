### Title
StackerDB write-frequency (`write_freq`) cooldown is never enforced on the direct HTTP write path, allowing signers to write chunks faster than the replica's configured throttle - (File: `stackslib/src/net/api/poststackerdbchunk.rs`)

### Summary
This is a timing/enforcement analog to the Tapioca bug: two different subsystems are supposed to agree on when an action ("write a chunk"/"exercise an option") is permitted, but one enforcement path checks a time-based cooldown and the other path does not, letting an authorized-but-rate-limited actor act sooner than the protocol intends.

### Finding Description
`StackerDBConfig::write_freq` is documented as "minimum wall-clock time between writes to the same slot" [1](#0-0) . This throttle is enforced in the *replication/sync* path: `StackerDBSync::make_chunk_request_schedule` explicitly skips fetching a chunk if `write_ts + self.write_freq > now` [2](#0-1) , and the sync state machine itself is throttled to run no more often than `write_freq` [3](#0-2) .

However, the actual chunk-acceptance logic in `StackerDBTx::try_replace_chunk` (`stackslib/src/net/stackerdb/db.rs`) only checks chunk size, valid signer signature, version monotonicity (`StaleChunk`), and `max_writes` — it never checks `write_freq` or any last-write timestamp before calling `insert_chunk` [4](#0-3) . The doc comment on `validate_received_chunk` even states explicitly: "NOTE: does not check write frequency, since the caller has different ways of doing this." [5](#0-4) .

The HTTP RPC endpoint `POST /v2/stackerdb/:principal/:contract/chunks`, handled by `RPCPostStackerDBChunkRequestHandler::try_handle_request`, calls `tx.try_replace_chunk(...)` directly with no `write_freq`/timestamp gate anywhere in the handler [6](#0-5) . This is the only enforcement point reachable by an unprivileged remote peer that owns a valid slot key — a legitimate signer (holder of a valid slot private key) can call this RPC endpoint back-to-back, incrementing `slot_version` each time, and every call succeeds as long as the version increases and stays under `max_writes`.

This directly mirrors the Tapioca bug: one subsystem's accounting (sync scheduling / replication) assumes writes are naturally spaced apart by `write_freq`, but the actual state-mutating gate (`try_replace_chunk`) does not enforce that invariant, so a caller using the "wrong" entry point can violate the assumed timing property.

### Impact Explanation
This breaks the equality "chunk write rate obeys `config.write_freq`" that the sync/gossip layer assumes is true for every chunk in the DB. A slot owner (any signer with a valid key for a stacker-db slot, e.g. a Nakamoto block signer) can spam version bumps to their own slot far faster than `write_freq` permits via the direct HTTP write path. Consequences:
- Bandwidth/DoS amplification on the p2p network: every node with a replica of that StackerDB will detect the new (higher) `slot_version` via `StackerDBChunkInv` gossip and attempt to re-fetch/re-propagate the chunk, at a rate the protocol's `write_freq` throttle was specifically designed to bound. This turns a config-limited bounded compute/bandwidth cost into an effectively unbounded one, driven only by how fast the attacker (a legitimate but bandwidth-limited signer) can issue HTTP requests to their own node.
- It also erodes the assumption other nodes' sync state machines rely on (`self.write_freq`), since remote peers' actual on-disk write timestamps no longer correlate with the throttle they use to decide whether to skip re-fetching (`sync.rs:335-352`), potentially causing thrashing/re-fetch loops across the network.

This does not require a signature forgery or unauthorized write — it needs only a legitimate slot-owning signer misusing the local RPC endpoint that lacks the throttle other paths assume is universally enforced, which fits the "bounded compute DoS on a read/write endpoint via a mismatch of enforcement paths" class in scope.

### Likelihood Explanation
High likelihood for anyone who already holds a valid slot signing key (e.g., a block signer registered in a signer-set StackerDB) — no special privilege beyond normal slot ownership is needed, and the RPC endpoint is a standard, always-available `/v2/stackerdb/.../chunks` POST. The only work required is repeatedly signing and POSTing chunks with incrementing `slot_version`.

### Recommendation
Enforce `write_freq` inside `StackerDBTx::try_replace_chunk` (or in `insert_chunk`) by comparing the current time against the previously stored `write_time` for that slot, mirroring the check already present in `sync.rs`. Reject (or delay) writes that arrive before `write_time + write_freq` has elapsed, returning a dedicated error code so `poststackerdbchunk.rs` can surface an appropriate ack (e.g. a new `StackerDBErrorCodes::TooFrequentWrite`).

### Proof of Concept
1. Configure a StackerDB with `write_freq = N` seconds and a signer holding slot 0.
2. As that signer, POST a validly-signed `StackerDBChunkData` with `slot_version = 1` to `/v2/stackerdb/<addr>/<contract>/chunks` — succeeds, per `try_replace_chunk`'s checks (size, signer, staleness, max_writes only) [4](#0-3) .
3. Immediately (within less than `N` seconds) POST again with `slot_version = 2`, still validly signed — this also succeeds because no timestamp/`write_freq` check exists on this path.
4. Repeat as fast as network I/O allows; every peer replicating this StackerDB will observe rapid `slot_version` churn via `StackerDBChunkInv` and attempt fetches, even though the protocol's `write_freq` was meant to bound this rate — confirming the enforcement mismatch between `try_replace_chunk` and the sync-side throttle in `sync.rs:335-352` / `sync.rs:1427-1436`.
