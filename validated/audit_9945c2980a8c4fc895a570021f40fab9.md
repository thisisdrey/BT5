### Title
Attacker-controlled `estimated_len` in POST /v2/fees/transaction allows unbounded multiplication causing integer overflow - ([File: stackslib/src/net/api/postfeerate.rs])

### Summary
The `estimated_len` field in the JSON body of `POST /v2/fees/transaction` is only floored by the actual decoded payload length (`payload_data.len()`) but has no upper bound applied. This value later flows unmodified into `estimated_len * MINIMUM_TX_FEE_RATE_PER_BYTE` in `estimate_tx_fee_from_cost_and_length`, an unchecked multiplication that can overflow.

### Finding Description
In `try_parse_request` [1](#0-0) , `estimated_len` is computed as `std::cmp::max(body.estimated_len.unwrap_or(0), payload_data.len() as u64)`. The `MAX_PAYLOAD_LEN` check at line 153 only bounds the HTTP `Content-Length`/body size (and thus `payload_data.len()`), not `body.estimated_len`, which is a caller-supplied `u64` deserialized directly from JSON with no range validation in `FeeRateEstimateRequestBody` [2](#0-1) . Since `max()` only raises the value to the floor of `payload_data.len()`, it can never *reduce* an attacker-supplied larger value — an attacker sending `estimated_len: u64::MAX` (or any large value) with a small valid `transaction_payload` will have that huge value pass through unchanged.

This `estimated_len` is stored in handler state and later used in `estimate_tx_fee_from_cost_and_length` at `let minimum_fee = estimated_len * MINIMUM_TX_FEE_RATE_PER_BYTE;` [3](#0-2) . This is a plain `*` operation with no `checked_mul`/`saturating_mul`. In a debug build (`overflow-checks`/`debug-assertions` enabled), this panics; in a release build, it silently wraps, producing a bogus `estimate.fee` value returned to the client in the JSON response.

No other guard intervenes: the request requires no authentication (`/v2/fees/transaction` is an unauthenticated RPC endpoint), and no `will_admit_mempool_tx` or mempool-acceptance check is performed on this path since it is a fee-estimation-only endpoint that never inserts anything into the mempool.

### Impact Explanation
A single crafted HTTP POST causes either: (a) a node crash/panic if the node binary is built with overflow checks (debug/`overflow-checks=true` builds), which is a remote unauthenticated DoS via one message, or (b) in optimized release builds where overflow checks are off by default, a wrapped/corrupted `minimum_fee` value is computed and returned as `estimate.fee` in the JSON RPC response, silently serving an incorrect (and unpredictable) fee estimate to any wallet/client that trusts this endpoint. This is repeatable indefinitely and requires no privileged access, matching the Critical categories of "remote crash/unauthenticated DoS from few messages" and "integrity failure of served state."

### Likelihood Explanation
This requires only network reachability to the node's RPC port and a single well-formed POST request with a small valid hex-encoded `TransactionPayload` and a large `estimated_len` value (e.g., `u64::MAX`). No peer registration, no StackerDB slot, no secret, and no special node state is needed. The attacker cost is a single crafted JSON request.

### Recommendation
Cap `estimated_len` to a sane maximum (e.g., `MAX_PAYLOAD_LEN` or some fixed maximum transaction size) when parsing the request, and/or use `checked_mul`/`saturating_mul` for `estimated_len * MINIMUM_TX_FEE_RATE_PER_BYTE` in `estimate_tx_fee_from_cost_and_length`, returning an HTTP 400 error if the value is out of range instead of allowing arbitrary large values to reach the multiplication.

### Proof of Concept
Add a test in `stackslib::net::api::postfeerate` tests module that constructs a `StacksHttpRequest` (or directly calls `try_parse_request` with a crafted preamble/body) with:
- `transaction_payload`: hex of a small, valid `TransactionPayload::TokenTransfer` (a few dozen bytes).
- `estimated_len`: `u64::MAX / MINIMUM_TX_FEE_RATE_PER_BYTE + 1` (guarantees overflow in the later multiplication).

Then invoke `try_handle_request` (or directly `RPCPostFeeRateRequestHandler::estimate_tx_fee_from_cost_and_length` with the resulting `estimated_len`) and assert:
- In a debug/overflow-checks build: the call panics at `stackslib/src/net/api/postfeerate.rs:112`.
- In a release build: `estimate.fee` in the returned `RPCFeeEstimateResponse` is inconsistent with `estimated_len * MINIMUM_TX_FEE_RATE_PER_BYTE` computed via `u128` (i.e., the wrapped `u64` result differs from the true product), demonstrating a corrupted fee estimate served to the client.
