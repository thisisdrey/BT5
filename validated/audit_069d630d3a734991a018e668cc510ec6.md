## Title
Permanent DoS/freeze of an ETH-implicit wallet via gas-exhaustion in a promise callback that rolls back `has_in_flight_tx` reset - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The `WalletContract` (NEP-518, deployed as the sole code on every ETH-implicit account) uses an in-flight flag, `has_in_flight_tx`, to serialize execution of Ethereum-style transactions. This flag is reset to `false` as the very first statement of every `#[private]` callback, and callbacks call into attacker-influenced external contracts (the ERC-20/NEP-141 token contract chosen by the transaction's `to`/target address) before completing. If that callback subsequently fails for any reason (e.g. running out of its statically-allocated prepaid gas while processing an oversized/adversarial promise result), NEAR's per-receipt atomicity rolls back *all* state writes from that function call — including the earlier `self.has_in_flight_tx = false` write — leaving the flag permanently stuck at `true`. Since ETH-implicit accounts have no access key and no other code path (`rlp_execute` is the sole entry point, and it unconditionally rejects when `has_in_flight_tx` is `true`), this permanently freezes the account and all of its funds.

### Finding Description
`rlp_execute` guards against concurrent execution using `has_in_flight_tx`, setting it `true` before returning a promise and requiring each subsequent callback to reset it to `false`: [1](#0-0) 

Every callback resets the flag as its first action, then goes on to process a `PromiseResult` supplied by an externally-controlled contract (the token/address-registrar the transaction targets): [2](#0-1) [3](#0-2) 

Both `nep_141_storage_balance_callback` and `address_check_callback` deserialize the returned `PromiseResult::Successful(value)` bytes with `serde_json::from_slice`, and the gas budget for this work is a small, fixed constant chained onto the original call (`NEP_141_STORAGE_BALANCE_CALLBACK_GAS` / `ADDRESS_CHECK_CALLBACK_GAS`, each on the order of ~10-15 Tgas), independent of how large or complex a payload the target contract chooses to return: [4](#0-3) [5](#0-4) 

If this fixed gas budget is exhausted while parsing an adversarially large/expensive `value` (or the call otherwise panics/traps after the flag reset but before the receipt finishes), the whole receipt fails. Per the documented runtime invariant, a failed receipt rolls back *every* state change it made: [6](#0-5) 

That rollback includes the `self.has_in_flight_tx = false;` write executed moments earlier in the same function call, so the flag reverts to (or remains) `true`. `rlp_execute` unconditionally refuses any further transaction while this flag is `true`: [7](#0-6) 

Because ETH-implicit accounts can never receive a full access key, cannot be deleted, and can only be interacted with through this contract's methods, there is no recovery path once `has_in_flight_tx` is stuck: [8](#0-7) 

### Impact Explanation
This constitutes permanent freezing of funds: once `has_in_flight_tx` is stuck `true`, `rlp_execute` — the only way to move assets out of the ETH-implicit account — is permanently disabled, and the account cannot be recovered via any other mechanism (no access key, no deletion, no redeploy). All $NEAR and NEP-141 token balances held by the account become permanently inaccessible. This maps directly to the erc777 report's core scenario: a value/callback controlled by an adversarial counterparty (here, the NEP-141 token contract the wallet owner's transaction targets) is invoked mid-flow, and its failure/behavior corrupts the surrounding contract's bookkeeping in a way that can never be undone, freezing funds that belong to an unrelated, honest party.

### Likelihood Explanation
Triggering requires an ETH-wallet owner (or their relayer) to send an `ERC20Transfer`-emulated transaction whose target is a malicious or compromised NEP-141 token contract, or an `EOABaseTokenTransfer` with `address_check` routed through a malicious address registrar response path. A malicious token author fully controls the byte payload returned from `storage_balance_of`, and can size/shape it to make the wallet's fixed-gas callback deserialization exceed its statically allocated `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`/`ADDRESS_CHECK_CALLBACK_GAS` budget. This is a realistic griefing/phishing scenario (tricking or waiting for a user to interact with an attacker's token), analogous to the erc777 report's premise that a party can craft a hostile contract that is called during a settlement/callback flow.

### Recommendation
- Reset `has_in_flight_tx = false` and persist it independently of the rest of the callback logic (e.g., via a preceding cheap, separate promise/receipt, or restructure so the flag write cannot be rolled back by a later failure in the same execution).
- Bound/validate the size of any promise-result payload before attempting to deserialize it, and fail fast (returning an `ExecuteResponse` gracefully) rather than letting an unbounded `serde_json::from_slice` run against attacker-supplied bytes under a fixed gas budget.
- Add a recovery mechanism (e.g., a timeout-based or governance-gated way to clear a stuck `has_in_flight_tx`) so a single failed callback cannot cause irrecoverable, permanent account lockout.

### Proof of Concept
1. An eth-implicit wallet owner (or a relayer on their behalf) signs an `rlp_execute` transaction whose decoded action is an `ERC20Transfer` targeting a malicious NEP-141 contract `evil-token.near`.
2. `inner_rlp_execute` builds a promise chain: `evil-token.near::storage_balance_of` → `.then(nep_141_storage_balance_callback(...))`, with the callback funded by the fixed `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`.
3. `evil-token.near::storage_balance_of` returns a crafted successful value engineered so that `serde_json::from_slice::<Option<StorageBalance>>` inside `nep_141_storage_balance_callback` exceeds the callback's fixed prepaid gas (e.g. via a large/complex payload), causing the callback receipt to fail with `GasExceeded`.
4. Per protocol semantics, the entire failed receipt's state changes are rolled back, including the `self.has_in_flight_tx = false;` write made at the top of the callback.
5. `has_in_flight_tx` remains `true` in persisted state forever; every subsequent `rlp_execute` call on this account immediately returns the "transaction already in progress" error, and since ETH-implicit accounts have no other access mechanism, the account's funds are permanently frozen.

        &mut self,
        target: AccountId,
        action: near_action::Action,
        caller_deposit: Option<CallerDeposit>,
    ) -> PromiseOrValue<ExecuteResponse> {
        self.has_in_flight_tx = false;
        let maybe_account_id: Option<AccountId> = match env::promise_result(0) {
            PromiseResult::Failed => {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Call to Address Registrar contract failed".into()),
                });
            }
            PromiseResult::Successful(value) => match serde_json::from_slice(&value) {
                Ok(x) => x,
                Err(_) => {
                    return PromiseOrValue::Value(ExecuteResponse {
                        success: false,
                        success_value: None,
                        error: Some("Unexpected response from account registrar".into()),
                    });
                }
            },
        };
