Audit Report

## Title
`claim_rewards_to` is permanently disabled on Bridge Hub Rococo because `prepare_rewards_account` never returns a beneficiary - ([File: cumulus/parachains/runtimes/bridge-hubs/bridge-hub-rococo/src/lib.rs])

## Summary
Both `BridgeRelayersConfig::prepare_rewards_account` implementations in the Bridge Hub Rococo runtime unconditionally return `None`, causing the `claim_rewards_to` benchmark to fall back to `Weight::MAX`. This is confirmed by the checked-in autogenerated weight files, which literally encode `18_446_744_073_709_551_000` picoseconds (`u64::MAX`) as the weight for `claim_rewards_to()`, making the extrinsic practically un-dispatchable on Bridge Hub Rococo.

## Finding Description
`claim_rewards_to` dispatches via `T::WeightInfo::claim_rewards_to()` as its weight annotation. The benchmark for this call in `bridges/modules/relayers/src/benchmarking.rs` requires `prepare_rewards_account` to return `Some((reward_kind, beneficiary))` to proceed with a real measurement; if it returns `None`, the benchmark is overridden with `Weight::MAX`. Bridge Hub Rococo's two trait implementations (for `RelayersForLegacyLaneIdsMessagesInstance` and `RelayersForPermissionlessLanesInstance`) both deposit funds into a rewards account but then explicitly `return None`, never supplying the beneficiary pair needed for a real benchmark. The resulting autogenerated weight files (`pallet_bridge_relayers_legacy.rs`, `pallet_bridge_relayers_permissionless_lanes.rs`) confirm this landed in production: `claim_rewards_to()` returns the numeric encoding of `Weight::MAX`, sourced from a `Benchmark::Override` marker rather than measured execution, with zero proof size and zero DB reads/writes.

## Impact Explanation
Because this `Weight::MAX` value is baked directly into the runtime's compiled `WeightInfo` for `claim_rewards_to`, any transaction calling it on Bridge Hub Rococo will exceed per-extrinsic/block weight limits and be rejected by the transaction queue/executive before dispatch. Rewards recorded in `RelayerRewards` storage via `register_reward` that a relayer wishes to route to an alternate beneficiary become permanently unclaimable through this call, on this chain — a fund-lock condition.

## Likelihood Explanation
This requires no attacker action beyond attempting the ordinary, public `claim_rewards_to` extrinsic; the broken weight is a pre-existing runtime defect already baked into the shipped weight files, so it is deterministically reproducible on every invocation. The identical defect class was previously found and fixed for Bridge Hub Westend (PR #10952), corroborating that this is a real, previously-acknowledged bug pattern in this codebase, still unpatched for Rococo.

## Recommendation
Update both `prepare_rewards_account` implementations in `cumulus/parachains/runtimes/bridge-hubs/bridge-hub-rococo/src/lib.rs` to return `Some((reward_kind, beneficiary))` with a properly funded beneficiary account, mirroring the Bridge Hub Westend fix, and regenerate the `pallet_bridge_relayers_legacy.rs` / `pallet_bridge_relayers_permissionless_lanes.rs` weight files so `claim_rewards_to` receives a real, bounded weight.
