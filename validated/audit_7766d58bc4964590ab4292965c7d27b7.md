### Title
Unauthenticated `RecvError` packets allow attackers to force-reset an established tunnel's hostinfo state - (File: `outside.go`)

### Summary
The JOJO bug allowed anyone to reset `primaryCredit`/`secondaryCredit` for a protected account (`insurance`) by calling a function that expected only to reset state for a legitimately liquidated trader, because the function did nothing to confirm the target was an appropriate/expected recipient of a state reset. The analogous class here is "a control-plane message that resets protected connection state (hostinfo/tunnel) is processed and acted on with insufficient authentication of the actor triggering the reset."

In nebula, the `header.RecvError` packet type is handled in the unencrypted branch of `readOutsidePackets`, before any decryption or certificate-based authentication, and its handler (`handleRecvError`) tears down (`closeTunnel`) and deletes (`DeleteHostInfo`) the hostinfo for an active tunnel based only on a `RemoteIndex` lookup and a UDP source-address equality check.

### Finding Description
In `outside.go`, incoming packets are dispatched by header type before decryption: [1](#0-0) 

`header.RecvError` is handled immediately, with no certificate/handshake authentication required, unlike `header.Message`/`header.LightHouse`/`header.CloseTunnel`, which are only processed after `ConnectionState.Decrypt` succeeds (i.e., only for a genuine holder of the negotiated symmetric keys): [2](#0-1) 

The `handleRecvError` function itself: [3](#0-2) 

The only "authentication" performed is:
1. An `acceptRecvErrorConfig.ShouldRecvError(addr)` gate (a config-driven allow/rate policy, not a cryptographic check).
2. A comparison of the packet's UDP source `addr` against the hostinfo's currently known remote address (`hr != addr`), which is exactly the kind of address-trust check the rules call out (hostmap/remote address trust) — and it is defeated by ordinary UDP source spoofing, which requires no CA-signed certificate at all.

The `RemoteIndex` used to look up the target hostinfo via `QueryReverseIndex` is also not secret: index values are carried in cleartext in every packet header (handshake and otherwise), so an on-path or off-path observer can learn or guess the correct index/address pair without ever completing a handshake or possessing a certificate.

Just as `handleBadDebt` let an unauthenticated caller reset accounting state for an account it should not have been able to touch (the insurance account) merely by knowing its address and triggering the right precondition, `handleRecvError` lets an unauthenticated packet sender force a reset of a legitimate, already-established tunnel's protected state (`closeTunnel` + `DeleteHostInfo`) merely by knowing the (cleartext, spoofable) `RemoteIndex` and by spoofing the peer's UDP source address — with no proof of possession of a CA-signed certificate or the negotiated session keys.

### Impact Explanation
An attacker who can spoof UDP packets (or who is on-path and can observe/replay handshake headers to learn a target's remote index) can force nebula to tear down and delete the hostinfo of any active tunnel between two legitimately certificate-holding peers, without ever presenting a valid certificate or completing a handshake. This is a remote state-poisoning / denial-of-service primitive against established tunnels: it forces re-handshakes, disrupts routing/relay state (`unlockedDisestablishVpnAddrRelayFor`), and can be triggered repeatedly to keep tearing down tunnels — directly analogous in kind (unauthenticated reset of protected state) to the JOJO `handleBadDebt` issue, even though the specific consequence differs (DoS/tunnel-reset vs. accounting reset).

### Likelihood Explanation
Likelihood depends on the deployment's exposure to UDP source-address spoofing (egress/ingress filtering strength) and the attacker's ability to learn/guess a valid `RemoteIndex`+remote-address pair, both of which are transmitted in plaintext over the wire during normal handshake/traffic flow and thus observable by any network-adjacent, uncertificated attacker. No CA-signed certificate, valid peer status, or completed handshake is required to send the triggering packet.

### Recommendation
- Do not act on `RecvError` (or any pre-authentication control message) using only a UDP source-address equality check; require some proof tied to the current session (e.g., derive an unforgeable per-tunnel token/HMAC over the index, or require the message to be authenticated/encrypted under the established session keys).
- Consider rate-limiting/backoff independent from the address check, and require multiple corroborating signals (e.g., only honor `RecvError` shortly after we actually sent traffic to that remote address/index) before tearing down a hostinfo.
- Treat `RemoteIndex` as non-secret in threat modeling and avoid using its mere possession, combined with a spoofable source address check, as sufficient authorization to mutate protected tunnel/hostinfo state.

### Proof of Concept
1. Observe (via passive network access, or by initiating your own handshake and observing headers) a legitimate tunnel between node A and node B, recording B's `localIndexId` (which becomes the `RemoteIndex` A uses when sending to B) and B's public UDP `AddrPort`.
2. Craft a UDP packet with `header.RecvError` type and the observed `RemoteIndex`, with the UDP source address spoofed to match A's known address (or send from a location where address filtering does not prevent this).
3. Send the packet to B's UDP listener.
4. `readOutsidePackets` routes it directly to `f.handleRecvError` (no decryption/certificate check needed) — [4](#0-3) .
5. `handleRecvError` finds the hostinfo via `QueryReverseIndex`, sees the spoofed address matches the recorded remote, and calls `f.closeTunnel(hostinfo)` and `f.handshakeManager.DeleteHostInfo(hostinfo)`, destroying B's legitimate tunnel state to A without either party consenting or the attacker ever presenting a certificate — [5](#0-4) .

func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
