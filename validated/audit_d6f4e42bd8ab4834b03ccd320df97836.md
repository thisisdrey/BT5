## Title
Null pointer dereference in `UpdateAssetActuator.execute()` when `AllowSameTokenName` migration state is inconsistent with the account's asset record - (File: `actuator/src/main/java/org/tron/core/actuator/UpdateAssetActuator.java`)

### Summary
`UpdateAssetActuator` mirrors the kernel `team` bug class: a code path caches/uses a type-specific field unconditionally (regardless of which "mode" — V1 name-keyed asset vs. V2 id-keyed asset — actually applies), while the corresponding null/consistency check in `validate()` is only performed for the branch matching the *current* value of the `AllowSameTokenName` flag. This is analogous to `header_ops` being applied to a device whose actual type doesn't match, causing a null pointer dereference on a field that only exists for the "other" type.

### Finding Description
`UpdateAssetActuator.validate()` branches strictly on `dynamicStore.getAllowSameTokenName()`: [1](#0-0) 

- If the flag is `0`, it only verifies the V1 path: `account.getAssetIssuedName()` is non-empty and exists in `AssetIssueStore`.
- If the flag is `1`, it only verifies the V2 path: `account.getAssetIssuedID()` is non-empty and exists in `AssetIssueV2Store`.

It never validates the V2 (`assetIssueV2Store` / `getAssetIssuedID()`) branch when the flag is `0`.

`UpdateAssetActuator.execute()`, however, unconditionally performs the V2 lookup and dereferences the result **before** branching on the same flag: [2](#0-1) 

Only afterwards does it branch on `dynamicStore.getAllowSameTokenName()` to decide whether to also update the V1 (`AssetIssueStore`) record: [3](#0-2) 

If an account's `assetIssuedID` is empty or does not correspond to an entry in `AssetIssueV2Store` (i.e., the V1→V2 migration state for that asset is not yet consistent, which is exactly the scenario `AssetUpdateHelper` is designed to reconcile), `assetIssueStoreV2.get(...)` returns `null`, and the very next line `assetIssueCapsuleV2.setFreeAssetNetLimit(newLimit)` throws a `NullPointerException`. `validate()` never caught this because it only checks the V1 branch when the flag is `0`.

This is structurally identical to the Linux `team` bug: the dispatch/validation logic is gated on the "current type" (`AllowSameTokenName` state / device type), but the actual operation performed unconditionally touches a field (`header_ops` / `assetIssueV2Store` entry) that is only guaranteed to be populated for the *other* type, and the consuming code fails to null-check before dereferencing.

### Impact Explanation
`UpdateAssetContract` is a standard broadcastable transaction type dispatched through `ActuatorCreator`/`TransactionFactory` from any signed transaction. `execute()` is invoked as part of normal block application (`Manager`/`TransactionTrace`/`RuntimeImpl` actuator pipeline), so any node (full node, SR, or witness) processing a block containing such a transaction will hit the same `NullPointerException`. Because `execute()`'s uncaught `NullPointerException` is not one of the caught exception types (`InvalidProtocolBufferException`), it propagates up out of the actuator, which can crash/halt transaction processing for that node — a denial-of-service against the node that must be able to keep serving/applying the chain (impact category: node crash or halt).

### Likelihood Explanation
Exploitability depends on the existence of an account address whose `assetIssuedID`/`AssetIssueV2Store` state is inconsistent with the current global `AllowSameTokenName` flag (e.g., pre-migration TRC10 issuers, or any code path that creates/updates an `AccountCapsule`/`AssetIssueCapsule` without keeping both V1 and V2 stores synchronized). I could not fully verify from static analysis alone whether such an inconsistent state is currently reachable on a live/synced chain (the `AllowSameTokenName` proposal has historically only moved forward from 0→1, and `AssetIssueActuator`/`AssetUpdateHelper` generally keep both stores in sync), so likelihood is **uncertain and should be validated dynamically** (e.g., replaying pre-fork chain data, or constructing an `AccountCapsule` with `assetIssuedID` set but no corresponding `AssetIssueV2Store` entry) before treating this as fully exploitable in production. Given this uncertainty, I flag it as Medium-High rather than definitively High.

### Recommendation
- In `UpdateAssetActuator.execute()`, move the `assetIssueV2Store.get(...)` lookup and null-check inside the same `if (dynamicStore.getAllowSameTokenName() == 0) {...} else {...}` branching structure used for the V1 lookup, mirroring `validate()`.
- Add an explicit null check on `assetIssueCapsuleV2` before dereferencing it, and fail with `ContractExeException` rather than allowing an unchecked `NullPointerException` to propagate.
- Audit other actuators that reference `getAssetIssuedID()`/`AssetIssueV2Store` unconditionally outside the `AllowSameTokenName` branch (e.g., `UnfreezeAssetActuator`) for the same TOCTOU-style validate/execute mismatch.

### Proof of Concept
1. Construct (or locate) an `AccountCapsule` where `getAssetIssuedID()` is non-empty but `AssetIssueV2Store` has no entry for that ID (e.g., inconsistent/partial V1→V2 migration state), while `AllowSameTokenName` is `0`.
2. Broadcast a valid, correctly-signed `UpdateAssetContract` transaction from that account's key.
3. `validate()` passes because it only checks the V1 `AssetIssueStore`/`assetIssuedName` path (flag == 0 branch).
4. During `execute()`, `assetIssueStoreV2.get(accountCapsule.getAssetIssuedID().toByteArray())` returns `null`; the immediately following `assetIssueCapsuleV2.setFreeAssetNetLimit(newLimit)` call throws a `NullPointerException`, propagating out of actuator execution during block application.
