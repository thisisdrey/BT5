### Title
Deterministic CREATE1 contract addresses collide after deployer account nonce resets on reap - ([File: substrate/frame/revive/src/exec.rs])

### Summary
`pallet-revive` derives new contract addresses with `address::create1(deployer, account_nonce)`, reusing `frame_system`'s per-account transaction nonce as the uniqueness input, exactly mirroring the `MultiMerkleDistributor` bug pattern where a component (`QuestBoard`) was replaced/reinitialized and its internal id counter (`nextID`) restarted from a low value, causing new entries to collide with — and overwrite the semantics of — earlier ones at the same id/address.

### Finding Description
`create1` computes the contract address purely from `(deployer_address, nonce)`: [1](#0-0) 

The nonce used is `frame_system::Account::<T>::nonce`, fetched via `<System<T>>::account_nonce(&sender)` inside `new_frame` when handling `FrameArgs::Instantiate`: [2](#0-1) 

`frame_system`'s account nonce is not a globally monotonic, permanent counter tied to the account's *identity* forever — it lives in `frame_system::Account` alongside the account's `AccountData`, and when an account's balance drops to zero and it is reaped (the standard `OnKilledAccount`/dust-removal path in `frame_system`), the whole `AccountInfo` entry, including the nonce, is removed from storage. If the same `AccountId` (e.g., an address a user fully controls, or an address reachable via `pallet-revive`'s H160 fallback-account mapping) is later funded and becomes active again, its nonce restarts from `0`, just like `QuestBoard.nextID` restarting from `0` after `MultiMerkleDistributor.updateQuestManager` pointed at a fresh `QuestBoard` instance.

Because `create1(deployer, nonce)` is a pure deterministic function of these two values, once the nonce cycle repeats, an `instantiate`/deployment transaction from `sender` at post-reap nonce `k` computes exactly the same address as an earlier deployment from `sender` at pre-reap nonce `k`. `ContractInfo::new` only guards against a *live* duplicate at that address (`AccountInfo::is_contract` check) — it does not, and cannot, prevent the same address from being reused after the previous occupant at that address was `terminate`d/reaped and its `AccountInfo` cleared: [3](#0-2) 

This is structurally the same invariant break as the report: an id/address space that is supposed to be unique "forever" is instead re-derived from a counter that can be reset by an ordinary lifecycle event (account reaping / component replacement), with no floor value or reservation preventing reuse.

### Impact Explanation
If an attacker can predict/control when their controlling account is reaped and refunded (fully spend down balance below existential deposit so the account/nonce is destroyed, then refund it), they can redeploy a contract that lands at the exact same `H160` address as a contract they (or another party) previously deployed and later `terminate`d from that same deployer/nonce pair. Any off-chain integrator, bridge, or counterfactual-deposit scheme that treats a `create1` address as a permanently unique, non-reusable identifier for a specific contract instance (common in Ethereum tooling ported onto pallet-revive) can be misled into interacting with a different contract than intended at that address — a classic "id/address reuse" trust break, matching the `Impact Gate`'s "forged or mis-bound... state acceptance" and "public underpriced work" categories in spirit (state at that address is not what a consumer expects it to be).

### Likelihood Explanation
This requires no privileged actor: reaping one's own account (spend below existential deposit, letting dust removal execute) and later re-funding it is fully attacker-controlled and unprivileged, exactly matching an "unprivileged attacker" path (no malicious relayer/validator/governance needed). The precondition — deploy a contract, terminate/self-destruct it (freeing the address as non-contract), reap the deployer account, refund it, redeploy — is a normal sequence of currently-supported public extrinsics (`instantiate`, contract self-terminate, balance transfers).

### Recommendation
Do not derive `pallet-revive` contract addresses solely from the reapable, resettable `frame_system` account nonce. Use a dedicated, monotonically increasing, never-reset deployer nonce/counter stored independently of `frame_system::Account` (so reaping the account does not reset it), analogous to fixing `QuestBoard.nextID` to never restart at a low value after replacement. Alternatively, salt address derivation with an unforgeable, never-reused component (e.g., block/genesis-scoped incrementing global counter) so that account reaping cannot cause address collisions.

### Proof of Concept
1. Fund account `A`; call `instantiate` (no salt) → contract deployed at `addr = create1(A, nonce_0)` (existing test confirms this exact derivation): [4](#0-3) 
2. Terminate that contract (frees `addr` from `AccountInfo`/contract map).
3. Drain `A`'s balance below the existential deposit so `A` is reaped by `frame_system`, clearing `frame_system::Account::<T>` (including its nonce) for `A`.
4. Re-fund `A`. `System::account_nonce(&A)` is now back to the same value it held at step 1 (e.g., `nonce_0`).
5. Call `instantiate` (no salt) again from `A` → `create1(A, nonce_0)` recomputes to the identical `addr` from step 1, and `ContractInfo::new`'s only guard (`AccountInfo::is_contract`) passes because the old contract was already removed in step 2 — a brand-new, attacker-chosen contract now occupies the address previously associated with a different contract instance.

**Note on confidence:** I could not fully trace, within the available indexed content, whether `pallet-revive`/`frame_system`'s dust-removal path is unconditionally triggered by any signed extrinsic drain-to-zero without additional holds/locks that might prevent reaping in practice on production runtimes (e.g., existential-deposit exemptions or `frame_system::Config::AccountData` providers holding a reference). If a Devin session with full repo/test access is available, it would be worth running the exact PoC sequence above against `substrate/frame/revive` test/mock runtime to empirically confirm the address collision and settle whether current runtimes have any additional consumer/provider-reference guard that prevents this specific reap-then-reuse sequence.

/// Determine the address of a contract using CREATE semantics.
pub fn create1(deployer: &H160, nonce: u64) -> H160 {
	let mut list = rlp::RlpStream::new_list(2);
	list.append(&deployer.as_bytes());
	list.append(&nonce);
	let hash = keccak_256(&list.out());
	H160::from_slice(&hash[12..])
}

impl<T: Config> ContractInfo<T> {
	/// Constructs a new contract info **without** writing it to storage.
	///
	/// This returns an `Err` if an contract with the supplied `account` already exists
	/// in storage.
	pub fn new(
		address: &H160,
		nonce: T::Nonce,
		code_hash: sp_core::H256,
	) -> Result<Self, DispatchError> {
		if <AccountInfo<T>>::is_contract(address) {
			return Err(Error::<T>::DuplicateContract.into());
		}

		// Reject reuse of an address whose previous occupant still has unflushed
		// `NativeDepositOf` rows in the deletion queue. The on_idle drain will eventually
		// clear them; until it does, instantiating here would let the new contract inherit
		// stale per-payer entitlements.
		let account_id = T::AddressMapper::to_fallback_account_id(address);
		if NativeDepositOf::<T>::iter_prefix(&account_id).next().is_some() {
			return Err(Error::<T>::PendingDepositCleanup.into());
		}
