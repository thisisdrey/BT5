### Title
Unvalidated Bancor-relay exchange math in `ExchangeCapsule.transaction` allows reserve-balance corruption / fund draining on TRC10 `Exchange` swaps - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java])

### Summary
The `Exchange` (TRC10 Bancor-style AMM) subsystem prices swaps using a floating-point-based relay formula in `ExchangeProcessor`. Unless the `AllowHardenExchangeCalculation` chain parameter is enabled (a committee proposal, off by default on many networks), the resulting `buyTokenQuant` is applied to update the pool reserves with **no invariant check that the new reserve balances stay non-negative or within the actual pooled amount**. This is directly analogous to the Inverse Finance incident, where an unvalidated/manipulable on-chain price calculation (rather than a robust invariant-checked oracle) was used to move value out of a protocol in a single attacker-controlled transaction sequence.

### Finding Description
`ExchangeTransactionActuator.execute()` calls `exchangeCapsule.transaction(tokenID, tokenQuant, dynamicStore.allowStrictMath(), allowHarden())`, which is a directly signed-transaction reachable path (`ExchangeTransactionContract`) callable by any account. [1](#0-0) 

Inside `ExchangeCapsule.transaction`, when `hardenedCalc` is `false` (the default unless the `AllowHardenExchangeCalculation` proposal has been activated), the new reserve balances are computed with plain `+`/`-` and the resulting `buyTokenQuant` from the non-strict `ExchangeProcessor` (double-precision `Math.pow`-based Bancor relay formula) is **never checked against the actual pool reserve, nor is the invariant `newFirstTokenBalance >= 0 && newSecondTokenBalance >= 0` enforced** — that check only executes `if (hardenedCalc && ...)`: [2](#0-1) 

The pricing formula itself relies on IEEE-754 double arithmetic and `Math.pow`/`StrictMath.pow` for both the "sell to relay-supply" and "relay-supply to buy" legs: [3](#0-2) 

Compare this to the hardened, invariant-checked `SafeExchangeProcessor`, which uses `BigDecimal` throughout and is only used when `hardenedCalc` is true: [4](#0-3) 

Critically, `ExchangeTransactionActuator.doValidate()` only bounds the *sell*-side balance against `getExchangeBalanceLimit()` and checks `anotherTokenQuant < tokenExpected` (a user-supplied minimum-received check, not a pool-sufficiency check). There is **no check anywhere in `doValidate()` or `execute()` that `anotherTokenQuant <= <buy side reserve>`**: [5](#0-4) 

By contrast, sibling actuators `ExchangeInjectActuator` and `ExchangeWithdrawActuator` do explicitly guard against balances exceeding limits or going negative (`ExchangeInjectActuator` checks `newTokenBalance > balanceLimit`, `ExchangeWithdrawActuator` checks `firstTokenBalance < tokenQuant`). `ExchangeTransactionActuator` has no equivalent guard on the *computed output* side when running the non-hardened, floating-point Bancor formula. [6](#0-5) [7](#0-6) 

The double-precision relay math is also known (per the repo's own tests) to diverge from the hardened `BigDecimal` result for the same inputs — `testStrictMath` explicitly asserts `Assert.assertNotEquals(anotherTokenQuant, result)` between the non-strict and strict/hardened calculations: [8](#0-7) 

Because `buyTokenQuant`/`anotherTokenQuant` returned by the unvalidated double-precision formula is used to both (a) mutate the on-chain `ExchangeCapsule` reserve balances (which can go negative with plain subtraction, silently underflowing/overflowing with no `ArithmeticException`) and (b) credit the caller's account via `addAssetAmountV2`, a sequence of extreme-ratio swaps against a pool (small initial liquidity, large adversary-supplied `tokenQuant`, repeated calls) can push the double-precision `pow`-based calculation into a region where the computed `buyTokenQuant` exceeds the true, backed reserve of the opposite token — crediting the attacker with tokens/TRX that are not actually backed by the pool, while the store keeps a broken (potentially negative) reserve figure that corrupts all subsequent trades and withdrawals for other participants (`ExchangeWithdrawActuator` will attempt to pay out against numbers that no longer reflect real backing).

### Impact Explanation
This maps to "unbacked balance" / "theft of funds" criteria: an unprivileged account issuing ordinary `ExchangeTransactionContract` transactions against a floating-point AMM pool can mint asset/TRX credits not backed by real reserves and permanently corrupt the pool's on-chain balance bookkeeping, which is directly reachable through `ExchangeTransactionActuator`'s `validate`/`execute` path from any signed transaction — no privileged role required. This is High severity because it can drain other users' pooled TRX/TRC10 assets and desynchronize the exchange's `ExchangeCapsule`/`ExchangeV2Store` state.

### Likelihood Explanation
Likelihood depends on whether `AllowHardenExchangeCalculation` has been activated via committee proposal on the target network; if it has not (the historical default), the vulnerable non-hardened `ExchangeProcessor` path is exercised on every trade by default, making this readily reachable by any account holding TRX/TRC10 balances and an existing exchange pair with modest liquidity — no special privileges or contract deployment needed, just crafted `ExchangeCreate`/`ExchangeInject`/`ExchangeTransaction` transactions.

### Recommendation
Enforce the reserve-invariant check (`newFirstTokenBalance >= 0 && newSecondTokenBalance >= 0`, and additionally `buyTokenQuant <= buyTokenBalance`) unconditionally in `ExchangeCapsule.transaction`, not only when `hardenedCalc` is true; retire/deprecate the floating-point `ExchangeProcessor` path entirely in favor of always using `SafeExchangeProcessor`'s `BigDecimal` computation, independent of the `AllowHardenExchangeCalculation` proposal state, so no network configuration leaves the AMM math unguarded.

### Proof of Concept
Not independently executable from the index alone — reproducing the exact double-precision edge case that causes `buyTokenQuant` to exceed the opposite reserve requires driving `ExchangeProcessor.exchange` with extreme sell/buy ratios (as hinted by the divergence demonstrated in `ExchangeProcessorTest.testStrictMath`) and confirming on a running node with `AllowHardenExchangeCalculation` disabled that `ExchangeCapsule`'s stored `secondTokenBalance`/`firstTokenBalance` can be driven negative or under-backed via successive `ExchangeTransactionContract` calls. This would need to be validated with an actual running node/test harness (not available via static code inspection) to confirm the exact numeric conditions that trigger reserve underflow.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
