### Title
Stale `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId`/`ReceivedData` trie rows survive `DeleteAccount`, letting a pre-deletion receipt execute against a re-created account of the same name - (`core/store/src/utils/mod.rs`, `runtime/runtime/src/actions.rs`)

### Summary
`remove_account` (invoked from `action_delete_account`) only removes the `Account`, `ContractCode`, `AccessKey`/gas-key, and `ContractData` trie rows for the deleted account; it never removes `TrieKey::PostponedReceipt`, `TrieKey::PostponedReceiptId`, `TrieKey::PendingDataCount`, or `TrieKey::ReceivedData` rows keyed by that `account_id`. `action_create_account` performs no check for and no cleanup of these dangling rows before instantiating a fresh `Account` under the same name. As a result, a postponed `ActionReceipt` that was addressed to the old account instance can later execute against the state of the newly created account of the identical name.

### Finding Description
`process_action_receipt` (`runtime/runtime/src/lib.rs:1593-1658`) stores an incoming `ActionReceipt` with unresolved `input_data_ids` as `TrieKey::PostponedReceipt{receiver_id, receipt_id}` plus `TrieKey::PendingDataCount{receiver_id, receipt_id}` and one `TrieKey::PostponedReceiptId{receiver_id, data_id}` link per missing dependency, all keyed purely by the `receiver_id` account name (not by any account "generation"/instantiation id) [1](#0-0) .

`action_delete_account` calls `remove_account(state_update, account_id)` [2](#0-1) , and `remove_account` removes only `Account`, `ContractCode`, access/gas keys, and `ContractData` [3](#0-2) . It has no logic that scans or removes `PostponedReceipt`, `PostponedReceiptId`, `PendingDataCount`, or `ReceivedData` rows for the account being deleted.

`action_create_account` then simply validates naming/permission rules and installs a brand-new `Account::new(...)` for the same `account_id`, with no query against any of these lingering rows [4](#0-3) .

Later, when the previously-missing `DataReceipt` finally arrives, `process_receipt`'s data-receipt branch looks up `TrieKey::PostponedReceiptId{receiver_id, data_id}` purely by account name, finds the still-present link left over from before deletion, decrements `PendingDataCount`, and when it reaches zero fetches and executes the original postponed receipt via `apply_action_receipt` — now against the newly created account's trie state [5](#0-4) . Nothing in this path re-validates that the account instance targeted is the same one that existed when the receipt was postponed.

None of the existing checks (nonce, access-key permission, gas metering, storage-staking, `DeleteAccountWithLargeState`, `GasKeyBalanceTooHigh`) address this, because they are all about validating the *transaction/action* that triggers deletion or creation — none of them inspect or purge the account-keyed postponed-receipt machinery, which is a separate, receiver-account-scoped part of the trie.

### Impact Explanation
This is an authorization-exactness violation: a `FunctionCall` action receipt that was addressed to one instantiation of an account name can fire against a completely different, later instantiation of that same name, with the original `predecessor_id`/attached deposit/method arguments intact, and with no way for the new account owner to have vetted or rejected it in advance. In multi-tenant "subaccount factory" patterns (`x.factory.near` created/deleted/re-created by `factory.near` for successive different tenants), this allows a stale receipt crafted while the name was owned by a previous tenant (or attacker) to execute against the new tenant's freshly deployed contract/state — a promise/authorization escalation across accounts. Depending on what the stale receipt's actions do (arbitrary method call with attacker-chosen args/deposit against the new owner's contract), this can be leveraged toward unauthorized state manipulation or fund movement on the newly created account, matching the "authorization escalation across accounts or promises" bounty category.

### Likelihood Explanation
- The attacker fully controls the setup step: any account (including one they fully own, e.g. `x.bob.near`) can be made to receive/generate a `FunctionCall` receipt with an unresolved `input_data_id`, which is a completely ordinary async cross-contract-call/promise pattern.
- The deletion step is a normal `DeleteAccount` action, requiring only a `FullAccess` key on the account and `locked == 0` and storage usage under `Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE`, both trivially arranged.
- Recreating the exact same name requires control of the parent account for subaccounts (or the registrar for top-level names) — plausible whenever the same top-level owner cycles through subaccount tenants, a common "rented subaccount" / factory-contract pattern.
- The bug is 100% deterministic and repeatable; it requires no race condition, no validator/node privilege, and no signature forgery — only ordinary transaction sequencing across blocks.

### Recommendation
When deleting an account in `remove_account` / `action_delete_account`, also iterate and remove all `PostponedReceipt`, `PostponedReceiptId`, and `PendingDataCount` rows keyed by `receiver_id == account_id` (mirroring the existing access-key/contract-data prefix iteration), and either drop or otherwise invalidate `ReceivedData` rows for that account so no stale promise/data linkage can survive into a future re-creation of the same name. Any postponed receipt that would be orphaned by deletion should be resolved (e.g., converted into a failed execution outcome / refund) rather than silently left in the trie.

### Proof of Concept
Runtime/apply-path integration test:
1. Create account `A` (`CreateAccount` + `AddKey` with key K1).
2. Send `A` an `ActionReceipt` with a non-empty `input_data_ids` (e.g. one unresolved data id) and a `FunctionCall` action whose effect is observable (e.g. writes a distinctive key to contract storage or triggers a distinctive log). Apply this receipt so it becomes a `PostponedReceipt` (assert via state that `TrieKey::PostponedReceipt{A, receipt_id}` and `TrieKey::PendingDataCount{A, receipt_id}` exist).
3. From K1, submit and apply `DeleteAccount{beneficiary_id: ...}` for `A`. Assert `Account`/`AccessKey` rows for `A` are gone, but directly query the trie and assert the `PostponedReceipt`/`PostponedReceiptId`/`PendingDataCount` rows for `A` are still present (demonstrating the asymmetry).
4. Re-create `A` (`CreateAccount` + `AddKey` with a new key K2) and deploy a different/fresh contract to it.
5. Deliver the previously missing `DataReceipt` targeting `A`'s pending `data_id`.
6. Assert either that the resulting execution is rejected/ignored, or — showing the bug — that the original `FunctionCall` action from step 2 actually executes against the new `A` (e.g. the distinctive storage write/log from step 2's action appears in the post-step-6 state of the freshly created `A`), proving a stale receipt executed against a re-created account it was never intended for.

pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
