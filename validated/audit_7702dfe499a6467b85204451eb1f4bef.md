### Title
Quarantine gating is bypassed for the initial write into a not-yet-existing repository, allowing unreviewed objects to land directly in the final object store - ([File: internal/gitaly/storage/storagemgr/partition/transaction_manager.go])

### Summary
This maps the "MINIMUM_LIQUIDITY bypass on first mint" bug class onto Gitaly's `TransactionManager.Begin`. The report's root cause is a special-cased branch that only fires on the very first state-initializing operation (`_totalSupply == 0`) and skips the normal safety mechanism (`MINIMUM_LIQUIDITY` lock). In `Begin`, the analogous special case is `!txn.repositoryExists` (the repository does not yet exist), which skips the normal quarantine-directory setup that is otherwise mandatory for every write transaction.

### Finding Description
When a write transaction targets a repository, `Begin` branches on whether the repository already exists: [1](#0-0) 
For existing repositories, a dedicated quarantine directory is created and `Quarantine()` is applied so that incoming objects are isolated from the "real" object store until hooks/access checks pass: [2](#0-1) 

But when the repository does not yet exist (first write into it — e.g., a push that implicitly creates the repository), the code takes the `else` branch and sets `txn.quarantineDirectory` directly to the repository's real, final object directory instead of a temporary quarantine location: [3](#0-2) 

This mirrors the UniswapV2Pair pattern precisely: the safety mechanism (quarantine, analogous to `MINIMUM_LIQUIDITY`) is only applied on the "non-first" path (`_totalSupply != 0` / `repositoryExists == true`), while the "first" path (`_totalSupply == 0` / `!repositoryExists`) has a special branch that skips it. Gitaly's own documentation confirms quarantine is the mechanism relied upon to keep objects "detached from the main repository" until `pre-receive` and hook/access checks succeed: [4](#0-3) 

### Impact Explanation
If the object quarantine is not applied for a repository being created for the first time, objects received in that push are written straight into what becomes the permanent object directory rather than into an isolated staging directory. This is the same class of "safety-check skip on initialization" that the report flags — the objects associated with the very first ref update are not protected by the object-quarantine cleanup path that Gitaly's own docs describe (`doc/object_quarantine.md`) as the way rejected pushes get objects eagerly deleted. If `pre-receive`/access checks subsequently reject the push, the transaction/repository-creation is expected to be rolled back as a whole (unlike the classic single-repo quarantine flow, where only the ref update is undone while quarantined objects are pruned). This is a legitimate divergence from the security invariant documented for quarantine, and any code path (e.g., custom `pre-receive` hooks, GitLab's `/internal/allowed` check) that assumes quarantined isolation for objects associated with a rejected push does not get that isolation when the repository is being created for the first time.

### Likelihood Explanation
This path is reached on the standard, unprivileged repository-creation-via-push flow (an ordinary user pushing to a not-yet-existing repository, e.g. `CreateRepositoryFromBundle`, `CreateFork`, or `git-receive-pack` implicitly creating a repo), which is directly and routinely reachable without any special privileges. However, whether this is truly a security bypass (versus an accepted design trade-off, since creating the whole repository is rolled back atomically by the transaction manager rather than through post-hoc quarantine pruning) could not be fully confirmed from the available code — the actual rollback semantics of `CreateRepository`-time transactions on hook rejection were not verifiable within this pass. This uncertainty should be treated as a caveat.

### Recommendation
Confirm whether repository-creation transactions are always atomically discarded (not just partially rolled back) when `pre-receive`/access checks reject the push, such that no attacker-supplied object ever survives in the final storage location. If atomicity is not guaranteed in all code paths (e.g., partial application after a mid-transaction crash and recovery), apply the same quarantine-directory-then-promote pattern used for existing repositories to the not-yet-existing-repository branch as well, rather than writing directly to `mgr.storagePath/.../objects`.

### Proof of Concept
Not concretely reproducible from static analysis alone; would require constructing a test that (a) pushes to a not-yet-existing repository with a `pre-receive` hook or Rails `/internal/allowed` check configured to reject the push, and (b) inspects whether the transaction's staging/WAL state (rather than only `mgr.storagePath`) contains the objects at the time of rejection, to determine whether any window exists in which the objects are addressable/persisted outside of the atomic rollback of the whole transaction.

// Apply applies the quarantine on the repository. This is done by setting the quarantineDirectory
// as the repository's object directory, and configuring the repository's object directory as an alternate.
func Apply(repoPath string, repo *gitalypb.Repository, quarantineDir string) (*gitalypb.Repository, error) {
	relativePath, err := filepath.Rel(repoPath, quarantineDir)
	if err != nil {
		return nil, fmt.Errorf("creating quarantine: %w", err)
	}

	// All paths are relative to the repository root.
	objectDir := repo.GetGitObjectDirectory()
	if objectDir == "" {
		// Set the default object directory as an alternate if the repository didn't
		// have the object directory overwritten yet.
		objectDir = "objects"
	}

	alternateObjectDirs := make([]string, 0, len(repo.GetGitAlternateObjectDirectories())+1)
	alternateObjectDirs = append(alternateObjectDirs, objectDir)
	alternateObjectDirs = append(alternateObjectDirs, repo.GetGitAlternateObjectDirectories()...)

	quarantinedRepo := proto.Clone(repo).(*gitalypb.Repository)
	quarantinedRepo.GitObjectDirectory = relativePath
	quarantinedRepo.GitAlternateObjectDirectories = alternateObjectDirs

	return quarantinedRepo, nil
}

These hooks perform the following functions:

- `pre-receive`: The pre-receive hook receives all reference updates as a whole
  via standard input, where each change is represented by one line with the old
  and new object ID as well the name of the reference that is to be updated. At
  this point, all objects required to satisfy the update have already been
  received, but they are still in a separate "quarantine directory" and are
  therefore detached from the main repository. This hook first increments a
  reference counter that tracks how many pushes are active at the same time.
  Afterwards, it posts all changes to Rails' `/internal/allowed` API endpoint so
  that Rails can determine whether the change is allowed or not. Because objects
  still live in a quarantine directory, Gitaly tells Rails where it can find the
  quarantine directory using the repository's alternative object directory
  fields so that any subsequent RPC calls that check the change can access those
  objects. When the access checks succeed, any existing custom pre-receive hooks
  installed by the administrator are executed.
