`Webauthn::verify` in `crates/signatures/webauthn/src/lib.rs` performs the standard WebAuthn checks (`UP`/`UV`/`BE`/`BS` flags, `clientDataJSON` type/challenge match) and then delegates the actual signature check to `A::verify` → `Curve::verify`, which is genuine cryptographic verification (ed25519-dalek, p256, or secp256k1/near_sdk env verification), not a short-circuit. [1](#0-0) [2](#0-1) 

None of the concrete curve implementations special-case a zero/default signature or public key to return `true`; they all invoke real elliptic-curve math (`ed25519_dalek::Verifier::verify`, `p256::ecdsa::signature::hazmat::PrehashVerifier::verify_prehash`, `k256`'s equivalent, or the corresponding `near_sdk::env::*_verify` host functions), each of which rejects malformed/zero signatures as invalid. [3](#0-2) [4](#0-3) [5](#0-4) 

There is no code path in `WebauthnAssertion`/`Webauthn::verify` that short-circuits acceptance for a default-constructed or all-zero `Signature`/`PublicKey`; a zero-filled signature would simply fail the underlying cryptographic library's verification, returning `false`. The claimed invariant violation is not present in this file.

            return false;
        };

        cfg_select! {

                // `near_sdk::env::ecrecover` requires recovery_id, so
                // we need to find one by trial recovery
                for id in 0..=RecoveryId::MAX {
                    let recovery_id = RecoveryId::from_byte(id).unwrap_or_else(|| unreachable!());

                    if let Some(recovered) = Self::recover(prehash, signature, recovery_id)
                        && recovered == *public_key
                    {
                        return true;
                    }
                }
                // no recovery id was found
                false
            }
