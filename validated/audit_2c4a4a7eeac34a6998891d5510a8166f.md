### Title
Anti-replay window check-then-update race in `ConnectionState.Decrypt` allows a duplicated ciphertext to be decrypted and accepted twice - ([File: connection_state.go])

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` release the `decryptLock` between the anti-replay `Check` and the anti-replay `Update`, performing the actual AEAD decryption while the replay-window mutex is not held. Nebula supports multiple concurrent UDP reader routines (`listen.routines`) that all dispatch inbound packets against the same `HostInfo`/`ConnectionState`, so two goroutines can race a duplicated/replayed packet with the same `messageCounter` through the unlocked gap and both succeed.

### Finding Description
The reported bug class is: a piece of externally-triggered execution (an ERC1155 receive callback) runs while state relevant to a "price" read is only partially updated, so a caller who reads that state mid-update sees an inconsistent value it can exploit. The direct analog in Nebula's protocol-authentication surface is the anti-replay window, which is exactly the kind of "nonce/replay handling" state this scan is meant to catch.

`Decrypt` is implemented as three separate critical sections instead of one atomic check-and-set: [1](#0-0) 

```go
func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}
```

Between the first `Unlock()` (after `Check`) and the second `Lock()` (before `Update`), the replay-window state is fully released while the (comparatively expensive) AEAD `DecryptDanger` call runs. `Bits.Check` only inspects the window without marking the counter as seen; the counter is only "claimed" by the later `Update` call: [2](#0-1) 

`VerifyRelay` follows the identical unlocked-gap pattern for relay frames: [3](#0-2) 

Nebula's UDP listener supports multiple concurrent reader routines sharing the interface (`listen.routines` config), each independently calling into packet handling and ultimately into `ConnectionState.Decrypt`/`VerifyRelay` for the same `HostInfo`. If an attacker captures one legitimate ciphertext and replays it twice at (near) the same instant so it lands on two different reader routines, both routines can pass `Check` before either has called `Update` (the mutex is not held across the whole operation), so both routines independently run `DecryptDanger` to completion and return the decrypted plaintext to the caller before the second `Update` call finally reports a duplicate. The second call's `Update` failure only prevents a *third* delivery — the plaintext from the second, replayed decryption has already been produced and handed to the caller (e.g., written to the TUN device or otherwise processed) by the time `Update` is invoked.

This mirrors the report's root cause precisely: a security-relevant read (`Check`, standing in for "read price/state") is performed against state that has not yet been finalized (`Update`, standing in for "state updated after transfer"), and the window between the two allows an attacker-triggered operation (packet duplication racing two reader goroutines, standing in for the ERC1155 callback) to produce an outcome that should have been prevented by the guard.

### Impact Explanation
A successful race causes a captured ciphertext to be decrypted and delivered twice despite Nebula's anti-replay window being designed to guarantee single delivery per message counter. This is a concrete traffic-replay/duplication vulnerability in the data plane: it undermines the confidentiality/integrity guarantee that each encrypted message counter is processed exactly once, and can be leveraged to replay application-layer traffic (e.g., resubmitting a captured command/packet) to whatever consumes decrypted tunnel traffic, without needing a valid CA-signed certificate — only the ability to capture and duplicate ciphertext already flowing on the wire (an on-path/eavesdropping attacker, not a certificate holder).

### Likelihood Explanation
Exploitation requires (1) `listen.routines` > 1 (a supported, non-default-only configuration) so multiple goroutines concurrently service inbound UDP packets for the same tunnel, and (2) the attacker being able to inject/duplicate a captured ciphertext onto both routines within the narrow window between `Check` and `Update` (during the time `DecryptDanger` executes). This is a timing-dependent race, not a fully attacker-controlled deterministic trigger, so likelihood is moderate — it depends on configuration and precise timing, but the code path itself unconditionally has the unlocked gap on every decrypt.

### Recommendation
Hold `decryptLock` for the entire `Check` → `DecryptDanger` → `Update` sequence (or use a single atomic check-and-mark operation on the replay window) so that no other goroutine can observe or race the same message counter mid-decryption. Equivalently, make `Bits` expose a single `CheckAndUpdate` method that performs both operations under one lock acquisition, and use it in both `Decrypt` and `VerifyRelay`.

### Proof of Concept
1. Configure a Nebula node with `listen.routines: 2` (or more) so multiple reader goroutines service the UDP socket for the same host tunnel.
2. Capture one legitimate application data packet's ciphertext (message counter `N`) between two established peers.
3. Immediately re-inject two copies of the exact same ciphertext at (near) the same time on the UDP socket so the kernel/SO_REUSEPORT dispatch delivers each copy to a different reader routine.
4. Because `Decrypt`'s `Check` and `Update` are two separate lock acquisitions with `DecryptDanger` running unlocked in between, both routines can pass `Check` for counter `N` before either calls `Update`, both successfully decrypt, and both hand back plaintext to the caller — observable as the tunnel/application processing the same message counter's payload twice (e.g., duplicate TUN writes) instead of the second copy being rejected with `ErrAlreadySeen` before decryption occurs.

// VerifyRelay verifies AEAD protected (but not encrypted) relay frames. packet must be length-checked by the caller.
func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}
