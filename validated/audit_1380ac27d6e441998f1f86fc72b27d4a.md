### Title
Write-Set Completeness Gap in `CrossShardCommitSender::send_remote_update_for_success` Causes Permanent Dependent-Shard Deadlock — (`aptos-move/aptos-vm/src/sharded_block_executor/cross_shard_client.rs`)

---

### Summary

`send_remote_update_for_success` iterates only over the keys present in the committed transaction's write set. If a key K is declared in `dependent_edges` (because the partitioner predicted the transaction would write K) but is absent from the final write set (e.g., the transaction VM-aborted and only emitted gas charges), no `RemoteTxnWriteMsg` is ever sent for K. The dependent shard's `RemoteStateValue` for K remains permanently in `RemoteValueStatus::Waiting`, and every subsequent `get_state_value` call for K blocks indefinitely, deadlocking the entire dependent shard.

---

### Finding Description

**Step 1 — Dependent edges are built from static partitioner analysis, not from the actual write set.**

`CrossShardCommitSender::new` populates `dependent_edges` from `cross_shard_dependencies.dependent_edges()` at construction time. [1](#0-0) 

These edges represent keys that the partitioner *predicts* this transaction will write. A VM abort at runtime does not retroactively remove those edges.

**Step 2 — `send_remote_update_for_success` only sends messages for keys present in the write set.**

```rust
for (state_key, write_op) in txn_output.write_set().expect_write_op_iter() {
    if let Some(dependent_shard_ids) = edges.get(state_key) {
        // send message
    }
}
``` [2](#0-1) 

If K is in `edges` but absent from the write set, the inner `if let` never fires and no message is sent for K. There is no complementary loop over `edges` to send `None` for unmatched keys.

**Step 3 — `on_transaction_committed` is the only hook; there is no `on_execution_aborted`.**

The `TransactionCommitHook` trait exposes only `on_transaction_committed`. [3](#0-2) 

The hook is invoked unconditionally for every finalized output, including VM-aborted transactions that carry only gas-charge writes. [4](#0-3) 

A grep for `on_execution_aborted`, `send_remote_update_for_abort`, and any None-fallback over `dependent_edges` returns zero matches across the entire sharded executor subsystem.

**Step 4 — The dependent shard blocks forever.**

`CrossShardStateView::new` initializes every cross-shard key in `RemoteValueStatus::Waiting`. [5](#0-4) 

`RemoteStateValue::get_value` spins on a condvar until the status transitions to `Ready`. [6](#0-5) 

Because no message is ever sent for K, `set_value` is never called, the condvar is never notified, and every thread in the dependent shard that reads K waits indefinitely.

---

### Impact Explanation

The dependent shard's executor thread pool is fully wedged: all worker threads block inside `get_state_value` → `get_value` → `cvar.wait`. No further transactions in that shard can be committed. This is a durable stuck state caused by a single crafted user transaction, constituting a material chain availability failure under the Availability path impact gate.

---

### Likelihood Explanation

Any transaction whose partitioner-predicted write set includes K but whose runtime execution path aborts before writing K triggers this. This is a normal occurrence: Move `abort`, out-of-gas, or any conditional write that is not taken at runtime. An attacker can reliably craft such a transaction by submitting one that the partitioner assigns a cross-shard write edge for K but that contains a `abort(0)` on the write path.

---

### Recommendation

After iterating over the write set in `send_remote_update_for_success`, add a second pass over `edges` to send an explicit `RemoteTxnWriteMsg(RemoteTxnWrite::new(state_key.clone(), None))` for every key in `edges` that was **not** covered by the write-set iteration. This ensures every declared dependent edge receives exactly one message regardless of whether the transaction committed or aborted.

---

### Proof of Concept

```rust
// Pseudo-integration test sketch
// 1. Partition a two-shard block where txn T on shard 0 has a dependent edge
//    for StateKey K pointing to shard 1.
// 2. Arrange T to VM-abort (e.g., Move abort(0)) so its write set contains
//    only gas charges, not K.
// 3. Execute shard 0; on_transaction_committed fires for T.
// 4. send_remote_update_for_success iterates T's write set — K is absent —
//    no RemoteTxnWriteMsg is sent to shard 1.
// 5. Shard 1's CrossShardStateView still holds K in Waiting.
// 6. Assert: shard 1 execution never completes (timeout / deadlock detected).
// Expected correct behavior: shard 1 receives RemoteTxnWriteMsg(K, None)
//   and proceeds normally.
```

The fix is to add after line 124 of `cross_shard_client.rs`:

```rust
// Send None for every dependent key not covered by the write set
for (state_key, dependent_shard_ids) in edges.iter() {
    if !txn_output.write_set().contains_key(state_key) {
        for (dependent_shard_id, round_id) in dependent_shard_ids.iter() {
            let message = RemoteTxnWriteMsg(RemoteTxnWrite::new(state_key.clone(), None));
            if *round_id == GLOBAL_ROUND_ID {
                self.cross_shard_client.send_global_msg(message);
            } else {
                self.cross_shard_client.send_cross_shard_msg(
                    *dependent_shard_id, *round_id, message,
                );
            }
        }
    }
}
```
