### Title
StackerDB Chunk Signature Digest Omits the Target Contract Identifier, Enabling Cross-StackerDB Chunk Replay - (File: libstackerdb/src/libstackerdb.rs)

### Summary
`SlotMetadata::auth_digest()` computes the message a StackerDB writer signs from only `slot_id`, `slot_version`, and `data_hash` — it never binds the signature to the specific StackerDB smart contract (namespace) the chunk is destined for. This is the same bug class as SFA-06 (COLLATERAL token omitted from the signed digest): the signature authenticates the payload's shape but not the context it is meant to be used in, so a signature/chunk that is valid for one StackerDB instance can be replayed into a different StackerDB instance where the same signer occupies the same slot.

### Finding Description
The digest that a StackerDB writer signs is built here: [1](#0-0) 

Verification uses the exact same digest and only checks the recovered signer against a `principal: &StacksAddress` supplied by the caller: [2](#0-1) 

The caller that supplies the "expected" address does so per-contract, in `PeerNetwork::validate_received_chunk`, which is invoked when processing gossiped/pushed chunks (`StackerDBPushChunk`) or synced chunks: [3](#0-2) 

Note that `smart_contract_id` is a parameter to this function — it is *not* part of what was signed. The lookup `get_slot_signer(smart_contract_id, data.slot_id)` simply resolves whichever address currently owns `slot_id` in the target contract's local table: [4](#0-3) 

Because slot ownership (address → slot_id mapping) is independently configured per StackerDB contract (via each contract's own `stackerdb-get-signer-slots`), and because in practice the Stacks signer-set boot contracts intentionally reuse the *same* slot ordering across multiple per-message-type StackerDB contracts within a reward cycle set: [5](#0-4) [6](#0-5) 

it is common for the same signer address to hold the same `slot_id` in several distinct StackerDB contracts simultaneously (e.g. across the different `.signers-0-<msg-id>` DBs for a given reward cycle, or in principle across reward cycles if slot ordering happens to coincide). Since `auth_digest()` never includes the contract identifier, a `StackerDBChunkData{slot_id, slot_version, sig, data}` tuple that was legitimately signed and gossiped for contract A is a byte-for-byte valid, independently-verifiable payload for contract B as well, as long as:
1. the signer address occupies the same `slot_id` in contract B, and
2. contract B's currently stored version for that slot is `< slot_version` (or the slot is fresh), and
3. `data.len()` fits contract B's configured `chunk_size`.

`insert_chunk`/`try_replace_chunk` perform no additional binding to the target contract beyond the version/size checks already covered above: [7](#0-6) [8](#0-7) 

The unsolicited push-chunk handler that a remote, unauthenticated-at-this-layer peer can trigger accepts the target contract ID directly from the attacker-controlled message and only calls `validate_received_chunk` before storing/propagating: [9](#0-8) 

Nothing in this path re-derives or checks that the `contract_id` supplied in the message matches anything the signature committed to — because the signature never committed to a contract_id in the first place.

### Impact Explanation
This breaks the equality the protocol relies on: "a signature valid for slot X in contract A" should not imply "a signature valid for slot X in contract B." Any remote, unauthenticated observer of gossiped StackerDB traffic (chunks are broadcast/replicated by design) can capture a legitimately signed `(slot_id, slot_version, data, sig)` tuple from one StackerDB contract and resubmit it — wrapped in a `StackerDBPushChunk` naming a *different* target contract — to any node that also assigns the same signer to the same slot in that other contract. If accepted, this is an unauthorized write into a StackerDB slot with attacker-selected forged provenance: data intended (and only validly attributable) to one message-type/context is stored and further gossiped/relayed as if legitimately written to a different StackerDB (namespace confusion / forged-data propagation across contexts), analogous to how the COLLATERAL bug lets a signature meant for one collateral asset be reused for another. The severity depends on how consumers of the target contract interpret arbitrary but hash-consistent bytes (e.g., a `BlockResponse`-shaped or vote-shaped blob landing in a different message-type slot could be misinterpreted or cause downstream deserialization/logic errors), but the core protocol invariant — that a chunk signature authenticates which StackerDB it belongs to — is broken.

### Likelihood Explanation
Exploitation requires only network-level access to observe or receive gossiped StackerDB chunks (no privileged key, no node secret) and the ability to send an unsolicited `StackerDBPushChunk`/POST-chunk request. The only additional precondition is that a signer address occupies the same `slot_id` across two contracts the attacker cares about, which is structurally the norm for per-message-type `.signers-N-*` StackerDBs sharing the same underlying slot ordering. This makes the precondition easy to satisfy in the current signer-set architecture, though the specific consequence (whether the replayed data is "useful" out of context) is data-dependent.

### Recommendation
Bind the signed digest to the target StackerDB contract by including the `smart_contract_id` (and ideally the reward-cycle / rc_consensus_hash context) inside `SlotMetadata::auth_digest()`, mirroring the fix recommended for SFA-06 (include the omitted context value — there, COLLATERAL; here, the contract identifier — directly in the signed digest). This requires updating `sign()`/`verify()`/`auth_digest()` signatures to take the `QualifiedContractIdentifier` as an explicit input, and updating all call sites (`StackerDBChunkData::sign`/`verify`/`recover_pk`, `validate_received_chunk`, and the DB layer) accordingly.

### Proof of Concept
1. Signer S is assigned `slot_id = 0` in both `.signers-0-block-response` and `.signers-0-block-proposal` StackerDB contracts (a common case since both derive their slot ordering from the same `signers` boot contract page).
2. S legitimately signs and pushes a chunk `{slot_id: 0, slot_version: V, data: D}` to `.signers-0-block-response`; this is observed by an attacker via normal StackerDB gossip.
3. The attacker constructs a `StackerDBPushChunk` message with `contract_id = .signers-0-block-proposal`, `rc_consensus_hash` matching the local view, and `chunk_data = {slot_id: 0, slot_version: V, sig, data: D}` (same signature/data as captured).
4. A victim node's `handle_unsolicited_StackerDBPushChunk` → `validate_received_chunk` looks up the slot-0 signer for `.signers-0-block-proposal` (which is S), calls `slot_metadata.verify(&S)`, which succeeds because `auth_digest()` never referenced which contract this was for.
5. If the victim's current stored version for `.signers-0-block-proposal` slot 0 is `< V`, the chunk is accepted and stored under the wrong contract, and is further relayed to the victim's peers as valid inventory for `.signers-0-block-proposal`.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }

    /// Insert a chunk into the DB.
    /// It must be authenticated, and its lamport clock must be higher than the one that's already
    /// there.  These will not be checked.
    fn insert_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        let stackerdb_id = self.get_stackerdb_id(smart_contract)?;
        let sql = "UPDATE chunks SET version = ?1, data_hash = ?2, signature = ?3, data = ?4, write_time = ?5 WHERE stackerdb_id = ?6 AND slot_id = ?7";
        let mut stmt = self.sql_tx.prepare(sql)?;

        let args = params![
            slot_desc.slot_version,
            Sha512Trunc256Sum::from_data(chunk),
            slot_desc.signature,
            chunk,
            u64_to_sql(get_epoch_time_secs())?,
            stackerdb_id,
            slot_desc.slot_id,
        ];

        stmt.execute(args)?;
        Ok(())
    }

    /// Add or replace a chunk for a given reward cycle, if it is valid
    /// Otherwise, this errors out with Error::StaleChunk
    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
