### Title
Out-of-Bounds Heap Read via Unvalidated UTF-8 Constant-Pool Length in ijar Classfile Parser - (File: third_party/ijar/classfile.cc)

### Summary
`ClassFile::ReadConstantPool` in ijar (Bazel's stripped-jar generator used for interface-jar generation on Java dependencies) reads a 16-bit length field for `CONSTANT_Utf8` entries and immediately treats the following `length` bytes as valid data — without ever checking that `p + length` stays within the mapped class-file buffer, mirroring the FlatGeobuf bug class ("length field is checked to be present, but the string body is not checked to be contained in the buffer before being materialized").

### Finding Description
`ClassFile::ReadConstantPool` reads the class file's constant pool directly from a raw pointer `p` walked over the in-memory buffer of a `.class` entry inside a jar: [1](#0-0) 

For `CONSTANT_Utf8`, only the 2-byte `length` prefix is read (`get_u2be(p)`); the code then constructs a `Constant_Utf8` object directly from `p` and unconditionally advances `p += length`, without any comparison against a known end-of-buffer pointer. No `EnsureRemaining`/bounds check exists anywhere in this file (unlike `third_party/ijar/zip.cc`'s `InputZipFile::EnsureRemaining`, which is used before every ZIP header field read — see e.g. `third_party/ijar/zip.cc:334-370`). The verbose debug path even directly materializes the claimed-length bytes into a `std::string`: [2](#0-1) 

Other multi-byte fields in the same loop (`attribute_length` in `HasAttrs::ReadAttrs`) exhibit the identical pattern — the length is trusted and used to skip/copy data with no containment check: [3](#0-2) 

ijar operates on `.class` entries extracted from `.jar` files supplied to Java rules (`java_import`, `java_library` deps, prebuilt jars fetched via `http_archive`/`http_jar` etc.). The outer zip container is validated by `InputZipFile::ProcessLocalFileEntry`/`EnsureRemaining` (see `third_party/ijar/zip.cc:332-419`), so the raw bytes making up an individual `.class` file are correctly extracted and match the declared `sha256`/`integrity` of the jar (integrity of the *archive* holds). However, nothing validates that the *semantic* content inside a single class file entry — an attacker-controlled UTF-8 constant with an inflated length field — stays within the extracted class-file buffer. This is precisely the FlatGeobuf pattern: the outer container's checksum is a red herring; the inner length-prefixed record is what's unsafe.

### Impact Explanation
A crafted `.class` file with a `CONSTANT_Utf8` entry whose declared length exceeds the remaining bytes of the classfile buffer causes ijar to read past the end of the allocated/mapped buffer for that class entry when the `Constant_Utf8` is later written into the generated interface jar (`Constant_Utf8::Write`) or displayed (`Constant_Utf8::Display`, used in diagnostics such as the "Unknown attribute" and constant-pool tag names). This can:
- Disclose adjacent heap memory (process memory not belonging to the class file) by copying it verbatim into the produced interface jar, which is subsequently stored in the build cache / action outputs and can be consumed by other build steps or shared caches.
- Crash the ijar process (segfault) if the read crosses an unmapped page, causing build failures — a secondary DoS effect, consistent with the referenced CVE's dual "memory disclosure or a server crash" impact.

### Likelihood Explanation
Any attacker who can publish a jar (or its transitive dependency archive) consumed by a Bazel build — a hostile mirror, malicious release artifact, or malicious BCR/registry-hosted dependency whose sha256 the victim pins to the attacker's own crafted bytes — can trigger this deterministically. The archive-level checksum does not stop it because the checksum legitimately matches the attacker's crafted (but malformed) class file; the checksum was never meant to validate internal classfile structure. No credentials or root-repo trust are required; this fires purely from parsing dependency bytes during ordinary Java compilation/ijar action execution.

### Recommendation
Add explicit bounds checks in `ClassFile::ReadConstantPool` (and `HasAttrs::ReadAttrs`) analogous to `InputZipFile::EnsureRemaining` in `zip.cc`: before dereferencing/advancing `p` by any length-prefixed field (`CONSTANT_Utf8` length, `attribute_length`, etc.), verify `p + length <= classdata_end` (tracking an explicit end-of-buffer pointer for the class file) and fail parsing with a diagnostic instead of proceeding, mirroring the containment discipline already present in the ZIP-header parsing code path.

### Proof of Concept
Construct a minimal single-class jar where the `.class` file's constant pool contains one `CONSTANT_Utf8` entry (tag `1`) whose 2-byte length field (e.g. `0xFFFF`) is larger than the number of bytes actually remaining in the extracted class-file buffer, then run `ijar` (or trigger it via a `java_library`/`java_import` target depending on that jar). Expected current behavior: `ClassFile::ReadConstantPool` reads/copies `length` bytes starting at `p`, running past the end of the buffer (verifiable under ASan as a heap-buffer-overflow read, or observable as attacker-uncontrolled bytes appearing in the generated interface jar's UTF-8 constant). A `BuildIntegrationTestCase`/`src/test/shell/bazel` test analogous to the existing `test_extract_non_readable_file_zip` pattern in `src/test/shell/bazel/starlark_repository_test.sh` can drive this by packaging the malformed `.class` into a jar consumed by a `java_import` rule and asserting the ijar step fails cleanly (post-fix) instead of over-reading (pre-fix, reproducible with ASan-instrumented ijar binary).
