### Title
Dust-transfer griefing fills a victim's per-account token list (`MAX_TOKENS_PER_USER`), permanently blocking new collateral deposits and new debt issuance while debt-backed dust cannot be removed — (File: contracts/Pool.sol)

### Summary

The CVE-2022-1174 bug class is denial of service triggered by an unprivileged user's specially crafted input. The closest Metronome analog is not an unbounded loop but a state-bloat / revert-DoS: `Pool` maintains per-account enumerable lists (`depositTokensOfAccount`, `debtTokensOfAccount`) capped by `MAX_TOKENS_PER_USER`, and any `DepositToken.transfer`/`transferFrom` to a first-time holder unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)`, which reverts with `UserReachedMaxTokens` once the combined list length reaches the cap. An attacker can force-add entries to any victim's list by transferring dust (1 wei) of each registered deposit token — entries the victim never requested and must actively remove. If the victim has an open debt position, the dust counts as collateral and can be locked, making the griefed state unrecoverable without repaying debt.

### Finding Description

`DepositToken._transfer` adds the token to the recipient's pool-side list whenever `recipient`'s prior balance is zero: [1](#0-0) 

`Pool.addToDepositTokensOfAccount` enforces the cap via `onlyIfAdditionWillNotReachMaxTokens`, which reverts when `debtTokensOfAccount.length + depositTokensOfAccount.length >= MAX_TOKENS_PER_USER`: [2](#0-1) [3](#0-2) 

The same revert path fires inside `DepositToken._mint` (deposit) and `DebtToken` issuance/minting, since both call the `addTo*TokensOfAccount` hooks on a first-time balance change: [4](#0-3) 

The cleanup path is `removeFromDepositTokensOfAccount`, only invoked when a transfer/withdrawal takes the balance to exactly zero — and `transfer`/`transferFrom`/`withdraw` first run `_revertIfLocked`, which consults `unlockedBalanceOf`. When the account carries debt, `unlockedBalanceOf` can return less than the full balance, meaning the attacker's dust can be locked collateral that the victim cannot move out: [5](#0-4) [6](#0-5) 

Attack flow (fully unprivileged, all public entry points):

1. Attacker deposits dust into every registered `DepositToken` (cost: 1 wei of each underlying plus gas; deposit tokens can also be obtained via `Pool.swap` proceeds in synths, but deposit is sufficient).
2. Attacker calls `depositToken.transfer(victim, 1)` for each registered deposit token. Each call succeeds because the check is on the *recipient's* list, which the attacker does not control the size of — the revert only matters once the cap is hit.
3. Victim's combined list reaches `MAX_TOKENS_PER_USER`.
4. Consequences:
   - `depositToken.deposit(amount, victim)` for any deposit token the victim does not already hold reverts (`_mint` → `addToDepositTokensOfAccount` → `UserReachedMaxTokens`).
   - `debtToken.issue(...)` for any synth the victim has not yet borrowed reverts (`addToDebtTokensOfAccount` → `UserReachedMaxTokens`).
   - Anyone sending the victim a new deposit token type reverts, so the victim cannot even receive collateral donations to improve health.
5. If the victim has an outstanding debt, `_revertIfLocked` blocks transferring/withdrawing the dust entries when they are locked, so the victim cannot shrink the list below the cap without first repaying debt — which may itself be impossible or require new collateral that can no longer be deposited. This converts a temporary freeze into a lasting one that can push the position to liquidation (`Pool.liquidate` remains callable by third parties).

### Impact Explanation

- Temporary to effectively permanent freezing of funds and protocol functionality for the victim: no new collateral types, no new debt types, no incoming transfers of unheld deposit tokens.
- Indirect loss of funds: a position approaching the liquidation threshold cannot be rescued with a *different* collateral asset (only with additional amounts of collateral types already in the list), and dust entries locked by existing debt cannot be removed.
- Invariant broken: liveness / free exit-and-entry assumption — a user can always deposit more collateral of a supported type. Third-party account-list pollution violates it.

### Likelihood Explanation

- Attacker cost is proportional to the number of registered deposit tokens (bounded by `addDepositToken`'s own `MAX_TOKENS_PER_USER` check); only dust of each is required, so capital cost is negligible — the attack scales with the number of listed collaterals on a given deployment.
- Works on the deployed configuration: `transfer` has no `onlyIfCanMint`-style gating beyond the sender's own `_revertIfLocked`, and there is no opt-in/whitelist for recipients.
- Mitigations that partially reduce severity: the victim can remove unlocked entries by transferring each dust balance to a second account in full (each removal frees one slot); collateral types already in the victim's list remain usable. Exact value of `MAX_TOKENS_PER_USER` was not confirmed in the retrieved snippets (declared in `PoolStorage`/`Pool` constants); feasibility requires the deployed pool to list enough deposit+debt tokens for stuffing to be practical.

### Recommendation

- Do not let inbound token transfers mutate recipient state against the cap. Options:
  - In `DepositToken._transfer`/`_mint`, skip `addToDepositTokensOfAccount` when the recipient list is at cap instead of reverting the whole transfer, and have `depositOf`/`debtPositionOf` treat missing entries as zero (it already only iterates the list, so a missed token is just ignored for health — note this trades off collateral-accounting accuracy).
  - Or revert only when the account is the actual depositor initiating collateral (`deposit`/`issue`), while allowing unsolicited `transfer`s to succeed without list insertion.
  - Or exclude tokens below a dust threshold from list insertion.
- Alternatively, allow `seize`/liquidation or a dedicated `remove` path to clean a victim's list, so a debt-backed victim is never permanently bricked.

### Proof of Concept

Hardhat sketch (against deployed pool contracts):

```ts
// victim has some position; attacker holds dust of every listed deposit token
const depositTokens: string[] = await pool.getDepositTokens() // all listed
for (const dt of depositTokens) {
  const token = await ethers.getContractAt('DepositToken', dt)
  const underlying = await ethers.getContractAt('ERC20', await token.underlying())
  await underlying.connect(attacker).approve(dt, 1)
  await token.connect(attacker).deposit(1, attacker.address)   // mint dust
  await token.connect(attacker).transfer(victim.address, 1)    // force-adds entry to victim's list
}
// now combined length == MAX_TOKENS_PER_USER
await expect(newDepositToken.connect(victim).deposit(amount, victim.address))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')
await expect(otherDebtToken.connect(victim).issue(1, victim.address))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')
// cleanup attempt while victim has debt: reverts when dust is locked
await expect(dustToken.connect(victim).transfer(attacker.address, 1))
  .to.be.revertedWithCustomError(dustToken, 'NotEnoughFreeBalance')
```

Note: feasibility on a fork depends on the deployed count of listed deposit/debt tokens relative to `MAX_TOKENS_PER_USER`; if few collaterals are listed, stuffing requires the victim's own prior entries plus all listed tokens — still reachable but limited to pools with many listed tokens.
