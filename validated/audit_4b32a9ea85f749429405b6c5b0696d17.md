### Title
Burned synthetic tokens are not deducted from `totalBridgedIn`/`amoSupply`, permanently inflating supply-cap accounting - (File: contracts/SyntheticToken.sol)

### Summary
`SyntheticToken` tracks cumulative counters (`totalBridgedIn`, `totalBridgedOut`, `amoSupply`) that are only updated on the symmetric mint/burn path of the same actor. When tokens minted via the bridge (or by the AMO) are burned through other authorized callers — `DebtToken.repay`/`repayAll`, `Pool.swap`, liquidation burns — `_burn` skips the counter update because `_msgSender()` is the DebtToken/Pool, not `proxyOFT`/`amo`. This is the same bug class as the TAU `currentMinted` report: a mint-side accounting counter is never decremented when the burn is routed through a different privileged caller. [1](#0-0) 

### Finding Description
- `_mint` increments `totalBridgedIn` when the caller is `proxyOFT` and `amoSupply` when the caller is `amo`, enforcing `maxBridgedInSupply` / `maxAmoSupply` caps. [2](#0-1) 
- `_burn` only updates `totalBridgedOut` (caller = `proxyOFT`) or decrements `amoSupply` (caller = `amo`). For burns initiated by a registered Pool or DebtToken, neither counter moves, but `totalSupply` still decreases. [1](#0-0) 
- `DebtToken.repay` burns the payer's synths via `_syntheticToken.burn(_msgSender, _repaid)` where the caller is the DebtToken. [3](#0-2) 
- Bridging in is fully unprivileged: any user calls `ProxyOFT.sendFrom` on a source chain and `_creditTo` mints on this chain, increasing `totalBridgedIn`. [4](#0-3) 
- Since `bridgedInSupply() = max(totalBridgedIn - totalBridgedOut, 0)` [5](#0-4) , burning bridged-in tokens through repay/swap/liquidation destroys them without crediting `totalBridgedOut`, so the net bridged-in figure is permanently overstated.

The same applies to `amoSupply`: AMO-minted synths are deposited into an external Vesper pool (`AMO.mintAndDeposit`) and can leave AMO control; if those tokens are later burned via `DebtToken.repay`, `amoSupply` stays high even though AMO's circulating minted supply decreased. `AMO.withdrawAndBurn` also reverts via `AmountToBurnGreaterThanAmoSupply` accounting checks that rely on `amoSupply`. [6](#0-5) 

### Impact Explanation
- **Bridged-in cap griefing (DoS):** An unprivileged attacker bridges in synths (`ProxyOFT.sendFrom` → `_creditTo` mints, `totalBridgedIn += amount`), then burns them via `DebtToken.repay`/`Pool.swap`. `bridgedInSupply()` never decreases. Repeating the loop pushes `bridgedInSupply()` to `maxBridgedInSupply`, after which every subsequent inbound bridge mint reverts with `SurpassMaxBridgingSupply` — inbound bridging is frozen until governance manually raises `maxBridgedInSupply` or enough users bridge out. Attacker cost is only the bridged tokens they choose to burn (can repay others' debts to recover collateral-locked value, partially offsetting cost).
- **AMO cap exhaustion:** Burns of AMO-origin synths through DebtToken/Pool keep `amoSupply` inflated, shrinking AMO's real mint headroom and eventually blocking `mintAndDeposit` with `SurpassMaxAmoSupply`, again recoverable only via governance (`updateMaxAmoSupply`). [7](#0-6) 

### Likelihood Explanation
- All attacker actions use public entry points (`ProxyOFT.sendFrom`, `DebtToken.repay`) with no privileged role, oracle manipulation, or malicious relayer assumptions.
- Feasibility depends on `maxBridgedInSupply`/`maxAmoSupply` being finite on the deployed configuration; `initialize` defaults `maxTotalSupply` to `type(uint256).max` but the bridged/AMO caps start at 0 and are set by governance, so any nonzero configured cap is reachable. [8](#0-7) 
- No modifier blocks it: `repay` is `whenNotShutdown`/`nonReentrant` only, and `_burn` performs no counter correction for Pool/DebtToken callers.

### Recommendation
Make the supply counters reflect burns regardless of which privileged contract initiates them, e.g., decrement `amoSupply`/`totalBridgedIn` (or track net current supply instead of cumulative counters) when tokens known to have originated from AMO/bridge are burned by Pool/DebtToken paths. At minimum, saturate-decrement in `_burn`:

```solidity
// contracts/SyntheticToken.sol
if (_isMsgSenderProxyOFT(_msgSender)) {
    totalBridgedOut += amount_;
    if (bridgedOutSupply() > maxBridgedOutSupply) revert SurpassMaxBridgingSupply();
} else {
    // Burns via pool/debtToken can destroy bridged-in or AMO-minted supply
    if (totalBridgedIn >= amount_ + totalBridgedOut) {
        totalBridgedOut += amount_; // symmetric offset so bridgedInSupply() decreases
    }
}
```

For `amoSupply`, either decrement it (saturating) whenever burned tokens exceed non-AMO supply, or replace the cumulative counter with a live "AMO-originated circulating supply" measure. Note uncertainty: precisely attributing burned tokens to AMO vs bridge origin is not possible with current accounting, so a conservative cap-side mitigation (saturating decrement) is the practical fix.

### Proof of Concept
Hardhat/Foundry fork sketch (mainnet fork with a deployed msUSD `SyntheticToken`, `ProxyOFT`, and a `DebtToken`):

```solidity
function testBridgedInCapGrief() public {
    uint256 cap = msUSD.maxBridgedInSupply();

    // 1. Attacker bridges in `cap` worth of msUSD (normal LayerZero receive path)
    vm.prank(address(proxyOFT));
    msUSD.mint(attacker, cap);              // totalBridgedIn = cap
    assertEq(msUSD.bridgedInSupply(), cap); // cap already reached

    // 2. Attacker burns the bridged-in tokens through the debt path
    //    (needs an open debt position; alternatively burn via Pool.swap)
    vm.prank(attacker);
    debtToken.repay(victim, cap);           // syntheticToken.burn(attacker, x) by DebtToken

    // 3. totalBridgedIn NOT decremented; bridgedInSupply() still == cap
    assertEq(msUSD.bridgedInSupply(), cap);
    assertEq(msUSD.totalSupply(), /* decreased */);

    // 4. Any legitimate inbound bridge mint now reverts
    vm.prank(address(proxyOFT));
    vm.expectRevert(SurpassMaxBridgingSupply.selector);
    msUSD.mint(user, 1);
}
```

Same pattern for `amoSupply`: AMO `mintAndDeposit` → tokens circulate → attacker acquires and burns via `debtToken.repay` → `amoSupply` unchanged → subsequent `mintAndDeposit` reverts at `SurpassMaxAmoSupply` well before real AMO circulation reaches the cap.

        if (account_ == address(0)) revert BurnFromTheZeroAddress();

        address _msgSender = _msgSender();

        if (_isMsgSenderProxyOFT(_msgSender)) {
            totalBridgedOut += amount_;
            if (bridgedOutSupply() > maxBridgedOutSupply) revert SurpassMaxBridgingSupply();
        } else if (_isMsgSenderAmo(_msgSender)) {
            // AMO can only burn from self address.
            // account_ should be AMO and in this case it is same as _msgSender()

            amoSupply -= amount_;

        if (_currentBalance < amount_) revert BurnAmountExceedsBalance();
        unchecked {
            balanceOf[account_] = _currentBalance - amount_;
            totalSupply -= amount_;
        }

        emit Transfer(account_, address(0), amount_);
    }

        if (amount_ == 0) revert AmountIsZero();

        uint256 _shares = Math.min((amount_ * 1e18) / vPool_.pricePerShare(), vPool_.balanceOf(address(this)));

        if (_amountToBurn > syntheticToken_.amoSupply()) revert AmountToBurnGreaterThanAmoSupply();

        emit WithdrawAndBurn(syntheticToken_, vPool_, _amountToBurn);
