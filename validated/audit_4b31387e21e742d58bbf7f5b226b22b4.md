### Title
Order execution (stop-loss/take-profit) can revert when the group withdrawal rate limit is exhausted by unrelated activity - ([File: programs/marginfi/src/instructions/marginfi_account/withdraw.rs], [File: programs/marginfi/src/state/rate_limiter.rs])

### Summary
`lending_account_withdraw` (and the equivalent Kamino/JupLend/Drift/Solend withdraw instructions) always call `record_withdrawal_outflow`, which enforces the group-level rate limiter, unless the account flag set matches `should_skip_rate_limit`. That skip-list only covers flashloan, receivership (liquidation), and deleverage flows — it does **not** include `ACCOUNT_IN_ORDER_EXECUTION`. As a result, a keeper-executed stop-loss/take-profit order that needs to withdraw collateral as part of `EndExecuteOrder` can be blocked by the group's hourly/daily USD outflow cap even though the withdrawal is not attacker- or user-controlled discretionary spending, but a protective/triggered action.

### Finding Description
The rate limiter's skip logic is defined in `should_skip_rate_limit`: [1](#0-0) 

which only exempts `ACCOUNT_IN_FLASHLOAN`, `ACCOUNT_IN_RECEIVERSHIP`, and `ACCOUNT_IN_DELEVERAGE`. Meanwhile, `lending_account_withdraw` fetches the price and (when the group rate limiter is enabled) unconditionally calls `record_withdrawal_outflow` for the withdrawn amount: [2](#0-1) [3](#0-2) 

The same pattern (checking `in_receivership_or_order_execution` only for price-fetch/oracle purposes, but still invoking `record_withdrawal_outflow` regardless of order-execution state) appears in the Kamino, JupLend, Drift, and Solend withdraw handlers as well. Per the project's own documentation: [4](#0-3) 

which confirms explicitly that liquidations/deleverages/flashloans are exempted, but order execution is not mentioned as exempted anywhere.

This mirrors the external report's root cause: a value-decreasing action taken as part of an automated/triggered flow (there: fee debit inside `matchOrders`; here: the withdraw leg of `EndExecuteOrder`) is subjected to a hard global cap check that has no relation to the specific triggered action, and whose state is affected by unrelated third-party withdrawals in the same window.

### Impact Explanation
If the group's hourly/daily withdrawal rate limit is close to being exhausted by unrelated user withdrawals at the moment a stop-loss or take-profit order should trigger (per `start_execute_order`'s trigger check in `programs/marginfi/src/instructions/marginfi_account/order.rs`), the keeper's withdraw instruction inside the `StartExecuteOrder`/`EndExecuteOrder` bracket can revert with `GroupHourlyRateLimitExceeded`/`GroupDailyRateLimitExceeded`. Since `EndExecuteOrder` requires the whole transaction (including the withdraw) to succeed atomically, the entire order execution fails. This defeats the purpose of a stop-loss (a risk-protection mechanism) exactly during high-volatility/high-outflow periods when protection is most needed, potentially causing the user's position to degrade further or become liquidatable before the order can be retried once the rate-limit window resets.

### Likelihood Explanation
Low — it requires the group rate limiter to be enabled and its window to be nearly saturated by unrelated withdrawal/borrow activity at the same time an order's trigger condition is met. This is a plausible but non-adversarial edge case (matches the "Low" likelihood rated in the original report for the analogous `matchOrders` issue).

### Recommendation
Add `ACCOUNT_IN_ORDER_EXECUTION` to the `should_skip_rate_limit` exemption list (or otherwise bypass `record_withdrawal_outflow` while the account flag is set), consistent with how `ACCOUNT_IN_RECEIVERSHIP` and `ACCOUNT_IN_DELEVERAGE` are already exempted, since order-execution withdrawals are bounded/validated separately via `OrderExecutionOverWithdrawal` and slippage/health checks in `end_execute_order`, making the group rate-limit check redundant risk control that only introduces unnecessary revert risk for a protective action.

### Proof of Concept
1. Group admin enables group rate limiting via `configure_group_rate_limits` with a modest hourly USD cap.
2. Various unrelated accounts perform withdraws/borrows that consume nearly all of the hourly outflow capacity (tracked read-only per `guides/ADMIN/RATE_LIMITS_AND_DELEVERAGE_WITHDRAW_LIMITS.md`).
3. A user's stop-loss order's trigger condition is met (price crosses `stop_loss`), and a keeper calls `marginfi_account_start_execute_order` → withdraw → `marginfi_account_end_execute_order` as in `tests/specs/basic/16_orders.spec.ts` / `programs/marginfi/tests/user_actions/limit_orders.rs`.
4. Inside the withdraw instruction, `record_withdrawal_outflow` computes the projected group outflow and rejects it with `GroupHourlyRateLimitExceeded` because `ACCOUNT_IN_ORDER_EXECUTION` is not exempted, causing the whole order-execution transaction to revert and leaving the user's stop-loss unexecuted.

Note: I could not directly view the full body of `record_withdrawal_outflow` in `programs/marginfi/src/utils/general.rs` in this session (tool call failed) to confirm the exact exemption check used inside that function versus `should_skip_rate_limit`; this should be verified in a follow-up review to confirm whether an additional guard inside `record_withdrawal_outflow` itself already exempts order-execution flows (in which case this finding would not apply), since search results only showed its call sites, not its full implementation.

/// Checks if rate limiting should be skipped based on account flags.
/// Returns true for flashloan, liquidation, and deleverage operations.
pub fn should_skip_rate_limit(account_flags: u64) -> bool {
    (account_flags & ACCOUNT_IN_FLASHLOAN) != 0
        || (account_flags & ACCOUNT_IN_RECEIVERSHIP) != 0
        || (account_flags & ACCOUNT_IN_DELEVERAGE) != 0
}
