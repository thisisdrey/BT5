## Title
Unbounded per-item processing in `CheckBlobsGenerated` allows a single client to exhaust Gitaly CPU/memory - (File: `internal/gitaly/service/analysis/check_generated.go`)

### Summary
The reported CometBFT bug is a resource-exhaustion class issue: a handler iterates over and performs per-item work (allocation, computation) on an attacker-controlled list of items without first bounding the size of that list, so a malicious but otherwise-unprivileged caller can force disproportionate work on the node. The Gitaly RPC `AnalysisService.CheckBlobsGenerated` has the same shape: it accepts a bidirectional stream of `CheckBlobsGeneratedRequest` messages, each carrying a `repeated Blob blobs` field, and it queues/reads/decodes every blob the client names with no limit on the number of blobs per message or the number of messages in the stream.

### Finding Description
`CheckBlobsGenerated` reads requests off the stream in an unbounded loop and, for every blob in every request, performs real work: it calls `queue.RequestObject`/`queue.ReadObject` to invoke `git-cat-file`, reads up to 2048 bytes of blob content, discards any remainder, and runs `enry.IsGenerated` before sending a response [1](#0-0) . The per-request validation only checks that the `blobs` list is non-empty and that each entry has a syntactically valid revision and non-empty path — there is no cap on `len(req.GetBlobs())` and no cap on the number of stream messages a client may send [2](#0-1) . The processing goroutine similarly loops over every request/blob pair it receives from the channel with no bound before doing the `git-cat-file` round-trip and buffering work [3](#0-2) .

Because the RPC is a long-lived bidirectional stream (not a single bounded unary message), the usual gRPC max-message-size protection does not bound total work: a client can keep sending additional request messages, each triggering more `git-cat-file` queue operations, indefinitely for the lifetime of the stream. This mirrors the reported bug class where a party controls the volume of "extra" items handed to a handler and the handler dutifully iterates/allocates for each one rather than rejecting or capping the volume up front.

### Impact Explanation
**Medium.** An authenticated caller (any client permitted to invoke Gitaly RPCs, e.g. via GitLab Rails/Workhorse proxying end-user actions) can drive unbounded `git-cat-file` queue work, blob reads, and `enry.IsGenerated` invocations on a single Gitaly node by continuously streaming `CheckBlobsGeneratedRequest` messages with blob lists. This consumes CPU and object-reader/queue resources tied to the repository's `git-cat-file` process, and — because the loop runs until the client closes or errs out — can degrade the Gitaly node for other repository operations. It does not by itself corrupt data or escape repository isolation, matching the "wasted computation / resource exhaustion" impact class of the original report rather than a data-corruption or auth-bypass class.

### Likelihood Explanation
**Medium.** No special privilege beyond the ability to call the `AnalysisService` RPC (already reachable by ordinary GitLab users exercising code-analysis features, e.g. viewing "is this file generated" indicators) is required, and constructing an oversized/long-running stream requires no more sophistication than a normal gRPC client capable of writing many small messages.

### Recommendation
Enforce an explicit limit on the number of blobs accepted per `CheckBlobsGeneratedRequest` message and/or a cumulative limit across the whole stream (similar to the `objectPoolMembersBatchSize`/`listPoolUpstreamsBatchSize` batching patterns already used elsewhere in Gitaly, e.g. [4](#0-3) ), rejecting requests up front with `InvalidArgument` rather than silently performing the underlying `git-cat-file` work for an unbounded number of items.

### Proof of Concept
1. Open a `CheckBlobsGenerated` stream against a Gitaly node for a repository the caller has read access to.
2. Repeatedly send `CheckBlobsGeneratedRequest` messages, each containing a large `blobs` array with syntactically-valid but numerous revision/path pairs.
3. Because `validateCheckBlobsGeneratedRequest` only checks for non-empty/well-formed entries and there is no maximum blob count or message count enforced [2](#0-1) , Gitaly will keep queuing and executing `git-cat-file` reads for every blob in every message for as long as the client keeps the stream open, consuming server-side CPU and object-reader resources disproportionate to a single client connection.

		chunkSender := chunk.New(&checkBlobsGeneratedSender{stream: stream})

		for req := range requestsChan {
			for _, blob := range req.GetBlobs() {
				object, err := queue.ReadObject(ctx)
				if err != nil {
					return fmt.Errorf("reading object: %w", err)
				}

				// The requested Git revisions must always resolve to a blob. Otherwise, there is
				// not a file to perform the generation check on.
				if !object.IsBlob() {
					return structerr.NewInvalidArgument("object is not a blob")
				}

				// Read an arbitrary number of bytes that is considered enough to determine whether
				// the file is generated.
				content, err := io.ReadAll(io.LimitReader(object, 2048))
				if err != nil {
					return fmt.Errorf("reading blob content: %w", err)
				}

				// Any remaining blob data must be consumed before reading the next object. This is
				// quite inefficient, but there is currently no alternative because git-cat-file(1)
				// cannot be asked to limit the number of bytes it's outputting.
				if _, err := io.Copy(io.Discard, object); err != nil {
					return fmt.Errorf("discarding remaining blob content: %w", err)
				}

				if err := chunkSender.Send(&gitalypb.CheckBlobsGeneratedResponse_Blob{
					Revision:  blob.GetRevision(),
					Generated: enry.IsGenerated(string(blob.GetPath()), content),
				}); err != nil {
					return fmt.Errorf("sending response: %w", err)
				}
			}

			// The sender is flushed for each received request message so that at least one response
			// message is always produced.
			if err := chunkSender.Flush(); err != nil {
				return fmt.Errorf("flushing response: %w", err)
			}
		}

		return nil
	})

func validateCheckBlobsGeneratedRequest(req *gitalypb.CheckBlobsGeneratedRequest) error {
	if len(req.GetBlobs()) == 0 {
		return errors.New("empty blobs")
	}

	for _, blob := range req.GetBlobs() {
		if err := git.ValidateRevision(blob.GetRevision(), git.AllowPathScopedRevision()); err != nil {
			return err
		}

		if len(blob.GetPath()) == 0 {
			return errors.New("empty path")
		}
	}

	return nil
}
