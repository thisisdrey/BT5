### Title
Same-block key delete+recreate resets the FunctionCall access key's nonce baseline, enabling replay of an already-spent transaction against the fresh allowance - ([File: runtime/runtime/src/access_keys.rs])

### Summary
`initial_nonce_value(block_height)` (used by `add_regular_key`) computes a new access key's starting nonce purely as `(block_height - 1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER`, with no dependence on any nonce previously consumed by a same-named public key that existed earlier in the same block height. [1](#0-0)  When an account's owner deletes a `FunctionCall`-permissioned key and re-adds it (same public key) within the same block height as a transaction that already consumed a nonce above the baseline, the fresh key's nonce baseline collapses back to the same value it had before that transaction was ever signed, making the already-executed transaction pass `verify_nonce` again. [2](#0-1) 

### Finding Description
`action_add_key` → `add_regular_key` sets the newly (re-)created key's stored nonce to `initial_nonce_value(apply_state.block_height)`, i.e. `(H-1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER`, regardless of the fact that a key with the *same public key* previously existed and had already advanced its nonce well past that baseline within the same block height `H`. [3](#0-2) 

`verify_nonce`, called from `verify_and_charge_tx_ephemeral`, only requires `tx_nonce > current_nonce` (or `== current_nonce + 1` in Strict mode) and `tx_nonce < block_height * MULTIPLIER`. [4](#0-3)  It has no memory of nonces that were consumed by a prior incarnation of the key once that key's trie entry is deleted (`remove_access_key` in `delete_regular_key`), because nonce tracking lives entirely inside the `AccessKey.nonce` field, which is wiped and reset on `AddKey`. [5](#0-4) 

Exploit flow (attacker controls both keys on their own account — a `FullAccess` key `A` and a `FunctionCall` key `B` with a finite allowance):
1. At block height `H`, `key A` (already existing, baseline `(H-1)*MULT`) signs a `FunctionCall` tx `T1` with `key B`, nonce `N = (H-1)*MULT + 1`, which exhausts `B`'s allowance via `check_and_compute_new_allowance`. [6](#0-5) 
2. Still at height `H`, `key A` signs `DeleteKey(B)` then `AddKey(B, new FunctionCallPermission{allowance: Y})`. Because both actions execute at the same `apply_state.block_height == H`, the recreated `key B`'s nonce is reset to exactly `(H-1)*MULT` — the same baseline it had *before* `T1` was ever processed. [7](#0-6) 
3. The attacker resubmits the byte-identical original `T1` (same signature, same nonce `N`). Since `N > (H-1)*MULT` (the new baseline) and `N < H*MULT` (upper bound, already satisfied originally), `verify_nonce` accepts it again. [8](#0-7) 
4. `check_and_compute_new_allowance` runs against the *new* allowance `Y` and decrements it, and a new `FunctionCall` receipt is dispatched to the receiver contract a second time, executing the contract's side effects twice from what should have been a single-use nonce. [6](#0-5) 

No existing check (signature, nonce upper bound, access-key permission, storage staking) stops this because nonce anti-replay state is scoped to the currently-existing `AccessKey` object and is fully discarded and reinitialized by `DeleteKey`+`AddKey`, and the reinitialization formula depends only on block height, not on any nonce high-water mark for that public key.

### Impact Explanation
This allows an unprivileged account owner to force double execution of a `FunctionCall` receipt that was already fully paid for and executed once, while also making the freshly funded allowance absorb a second charge it should never have been debited for. Scoped impact is the double-spend/replay category: a `FunctionCall`-permissioned key is meant to authorize each nonce exactly once, but the recreate-in-same-block flow lets one signed transaction be executed twice against different allowance instances. If the receiver contract performs stateful actions on each call (e.g., a pool withdrawal, a mint, a governance vote), the doubled receipt causes real state corruption/loss for whichever contract is the receiver, even though the "victim" here is the attacker's own key config — the impact is on the receiver contract's invariants, not merely the attacker's own balance.

### Likelihood Explanation
Preconditions are fully within the attacker's control: they need only their own account, a `FullAccess` key, and a `FunctionCall` key with an allowance, and must arrange for the `T1`, `DeleteKey`, `AddKey`, and replayed `T1'` transactions to land in the same block height (straightforward by choosing nonce `N` close to the baseline and submitting all four to the RPC endpoint back-to-back so the chunk producer includes them sequentially in one chunk). No validator, peer, or leaked-key access is required, and the attack is repeatable at will since it only depends on the deterministic, height-only `initial_nonce_value` formula.

### Recommendation
Do not reset a re-added key's nonce purely from block height when a public key with the same bytes previously existed on the account within the current or a recent height window. Options: (a) persist a per-account-key "last used nonce" tombstone across delete/recreate cycles (at least for the current block) and take the max against `initial_nonce_value`; or (b) forbid `AddKey` from reusing a public key that was deleted within the same block height until a subsequent height, so the baseline computed by `initial_nonce_value(H)` can never collide with nonces already consumed at height `H`.

### Proof of Concept
Runtime integration test:
1. Create account with `FullAccess` key `A` and `FunctionCall` key `B` (allowance `X`, receiver = mock contract with a stateful `withdraw` method).
2. Submit `T1`: `FunctionCall` via `B`, nonce `N`, exhausting allowance `X`; assert receiver contract state mutated once (e.g., counter == 1).
3. In the same block/chunk, submit `T2 = DeleteKey(B)` and `T3 = AddKey(B, new FunctionCallPermission{allowance: Y})`, both signed by `A`.
4. Resubmit the identical `T1` bytes/signature (`T1'`) in the same or the very next chunk.
5. Assert `T1'` is accepted (not rejected with `InvalidNonce`), the receiver contract's stateful counter is now 2 (double execution), and the recreated key `B`'s allowance is decremented from `Y` (double debit of the fresh allowance) — proving both double execution and allowance double-spend from a single originally-consumed nonce.

pub(crate) fn initial_nonce_value(block_height: BlockHeight) -> Nonce {
    // Set default nonce for newly created access key to avoid transaction hash collision.
    // See <https://github.com/near/nearcore/issues/3779>.
    (block_height - 1) * near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER
}

fn add_regular_key(
    fee_config: &RuntimeFeesConfig,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    public_key: &PublicKey,
    access_key: &AccessKey,
    block_height: BlockHeight,
) -> Result<(), StorageError> {
    let mut access_key = access_key.clone();
    access_key.nonce = initial_nonce_value(block_height);
    set_access_key(state_update, account_id.clone(), public_key.clone(), &access_key);

    account.set_storage_usage(
        account
            .storage_usage()
            .checked_add(access_key_storage_usage(fee_config, public_key, &access_key))
            .ok_or_else(|| {
                StorageError::StorageInconsistentState(format!(
                    "Storage usage integer overflow for account {}",
                    account_id
                ))
            })?,
    );
    Ok(())
}

/// Verify that the transaction nonce is valid.
fn verify_nonce(
    tx_nonce: Nonce,
    current_nonce: Nonce,
    block_height: Option<BlockHeight>,
    nonce_mode: NonceMode,
) -> Result<(), InvalidTxError> {
    match nonce_mode {
        NonceMode::Monotonic => {
            if tx_nonce <= current_nonce {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
        NonceMode::Strict => {
            if !current_nonce.checked_add(1).is_some_and(|expected| tx_nonce == expected) {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
    }
    if let Some(height) = block_height {
        let upper_bound = height
            .saturating_mul(near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER);
        if tx_nonce >= upper_bound {
            return Err(InvalidTxError::NonceTooLarge { tx_nonce, upper_bound });
        }
    }
    Ok(())
}

fn check_and_compute_new_allowance(
    access_key: &AccessKey,
    account_id: &AccountId,
    public_key: &PublicKey,
    total_cost: Balance,
) -> Result<Option<Balance>, InvalidTxError> {
    let Some(fc) = access_key.permission.function_call_permission() else {
        return Ok(None);
    };
    let Some(allowance) = fc.allowance else {
        return Ok(None);
    };
    let new_allowance = allowance.checked_sub(total_cost).ok_or_else(|| {
        InvalidTxError::InvalidAccessKeyError(InvalidAccessKeyError::NotEnoughAllowance {
            account_id: account_id.clone(),
            public_key: public_key.clone().into(),
            allowance,
            cost: total_cost,
        })
    })?;
    Ok(Some(new_allowance))
}
