## Title
StackerDB chunk signatures do not commit to the target StackerDB contract, enabling cross-contract signature replay - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata`/`StackerDBChunkData` signatures authenticate only `(slot_id, slot_version, data_hash)` and never bind to the specific StackerDB replica (its `QualifiedContractIdentifier`) or to the network. This is the same class of flaw as the Chakra `ChakraSettlement` bug: a message signed for delivery to context A (one StackerDB contract) is structurally valid for context B (a different StackerDB contract) as long as the same signer address happens to own the same `slot_id` there and the target has a lower stored version. This allows an unprivileged network peer to replay a chunk that was legitimately written/broadcast for one StackerDB contract into a different StackerDB contract instance.

### Finding Description
`SlotMetadata::auth_digest` computes the signed hash as: [1](#0-0) 

```
hasher.update(self.slot_id.to_be_bytes());
hasher.update(self.slot_version.to_be_bytes());
hasher.update(self.data_hash.0);
```

There is no contract identifier, no network/chain id, and no other binding to "which StackerDB replica this write is destined for." `sign`/`verify` operate purely on this digest: [2](#0-1) 

The write path (`StackerDBTx::try_replace_chunk`) takes a `smart_contract: &QualifiedContractIdentifier` argument to select *where* to look up the slot owner and where to store the chunk, but it never checks that the signature was produced *for* that specific contract — it only checks that the recovered signer matches whichever address is configured as the owner of that `slot_id` in that particular `smart_contract`'s slot table: [3](#0-2) 

The same pattern repeats in the p2p unsolicited-push validation path, `StackerDBs::validate_received_chunk`, which resolves the owner address via `get_slot_signer(smart_contract_id, slot_id)` and then calls `slot_metadata.verify(&addr)` — again, the contract identity is used only to pick which owner-table to consult, not incorporated into what was signed: [4](#0-3) 

This exactly mirrors the reported bug class: the equality that should be enforced — "signed-for contract == stored-into contract" — is never checked. Just as Chakra's `to_chain` was omitted from the signed hash (allowing replay across `ChakraSettlement` instances that shared validator/handler addresses), Stacks' `SlotMetadata` signature omits the destination `QualifiedContractIdentifier`, allowing replay across StackerDB instances that happen to assign the same signer address to the same `slot_id`.

In the Nakamoto signer-message system, this scenario is realistic: signer slot assignment is keyed only by `reward_cycle % 2` (parity), i.e., `.signers-0-*` vs `.signers-1-*` contract families, and slot IDs are simply the enumerated index of the address in the reward set for that parity: [5](#0-4) [6](#0-5) 

Because the same signer set (and thus the same address ordering) frequently persists across consecutive reward cycles (validators rarely churn every cycle), the same address can legitimately occupy the same `slot_id` in both the odd-parity and even-parity signer StackerDB contract families. There is no cryptographic reason this couldn't also occur across the several distinct per-parity signer-message contracts (`signers-0-xxx.clar` / `signers-1-xxx.clar`) that exist for different message types/pages.

### Impact Explanation
An unprivileged network observer who captures a validly-signed `StackerDBChunkData` (broadcast via `StackerDBPushChunk` p2p gossip or fetched over the public HTTP StackerDB endpoints) can resubmit the identical bytes (`slot_id`, `slot_version`, `sig`, `data`) against a *different* StackerDB contract, provided:
1. The same signer address owns that `slot_id` in the target contract, and
2. The target contract's current stored version for that slot is `< slot_version`, and it hasn't exceeded `max_writes`.

If satisfied, `try_replace_chunk`/`validate_received_chunk` will accept and store the chunk as authentic in a StackerDB instance the original signer never intended it for. This is a case of unauthorized/forged-context data write and cross-instance propagation of a message outside its intended scope — for example, causing a signer's state-machine update or vote message from one reward-cycle parity/message pool to be replayed and accepted as current in another pool, corrupting consumers (e.g., miners/other signers) that read from that StackerDB and treat its contents as authoritative for that specific contract's purpose. This matches the "forged-data propagation" / "unauthorized write to StackerDB state" impact class.

### Likelihood Explanation
Exploitation requires no secret key and no privileged role — only observing one legitimate, publicly-broadcast/publicly-readable chunk and resubmitting it verbatim to a different contract endpoint via the ordinary p2p push path or the public `POST /v3/stackerdb/...` HTTP RPC. The precondition (same signer address occupying the same `slot_id` across different StackerDB contract instances) is not exotic given how slot assignment is derived purely from reward-set ordering and reused across consecutive cycles/message pools; it does not require deliberately engineered validator addresses as in the Chakra PoC. However, it does require the attacker to first observe a suitable in-the-wild chunk and for slot-id/address coincidence and stale-version conditions to line up, which bounds (but does not eliminate) practical likelihood.

### Recommendation
Bind the signed digest in `SlotMetadata::auth_digest` (and thus `StackerDBChunkData::sign`/`verify`) to the specific StackerDB `QualifiedContractIdentifier` (and ideally the network id/chain id), e.g., include `smart_contract.to_string()` bytes in the hasher input before signing/verifying. Update `try_replace_chunk` and `validate_received_chunk` to pass the contract identifier into the digest computation so that a chunk signed for contract A is cryptographically rejected when replayed against contract B, even if slot ownership coincidentally matches.

### Proof of Concept
1. Reward cycle `N` (even parity) and reward cycle `N+2` (also even parity, same signer set unchanged) both use `.signers-0-*` type contracts; signer address `S` is assigned `slot_id = 3` in both due to identical reward-set ordering.
2. `S` signs and pushes `StackerDBChunkData{slot_id: 3, slot_version: 5, data: msg_for_cycle_N}` to its `.signers-0-1` (cycle `N`) instance; this message is broadcast over p2p (`StackerDBPushChunk`) and/or fetchable via the public HTTP GET chunk endpoint.
3. An attacker observes this chunk (no privileged access needed) and re-submits the identical `(slot_id=3, slot_version=5, sig, data)` to the `.signers-0-1` StackerDB instance for cycle `N+2`, where the current stored version for slot 3 is `< 5`.
4. `StackerDBs::validate_received_chunk` / `StackerDBTx::try_replace_chunk` resolve slot 3's owner in the cycle-`N+2` contract to the same address `S`, `slot_metadata.verify(&addr)` succeeds (digest only covers `slot_id`/`slot_version`/`data_hash`, both identical), and the stale-message from cycle `N` is accepted and stored as current data for cycle `N+2`'s `.signers-0-1` contract — even though `S` never signed anything for cycle `N+2`.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Sign this slot metadata, committing to slot_id, slot_version, and
    /// data_hash.  Sets self.signature to the signature.
    /// Fails if the underlying crypto library fails
    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }

        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
