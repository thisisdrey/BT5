Confirmed vulnerable pattern: the `system-frontend::add_tip` flow **irrevocably burns the user's tip asset on AssetHub before it is known whether the tip can actually be credited on BridgeHub**, and the destination-side crediting can permanently fail — mirroring the batcher-balance report's core defect ("value is consumed/committed with no way to reverse or reroute it once the counterpart operation fails").

### Title
Unbacked/lost user funds from `snowbridge-pallet-system-frontend::add_tip` when destination tip crediting fails - (File: `bridges/snowbridge/pallets/system-frontend/src/lib.rs`)

### Summary
`SystemFrontend::add_tip` (AssetHub) swaps the user's tip asset for Ether and **burns it** via `burn_for_teleport` [1](#0-0)  before sending an unpaid, best-effort `Transact` XCM to BridgeHub instructing `EthereumSystemV2::add_tip` to credit the corresponding `Inbound`/`Outbound` message's reward [2](#0-1) . On BridgeHub, `add_tip` fails permanently (and is only recorded as a "lost tip", not refunded to the user) whenever the referenced nonce/order can no longer accept a tip — e.g. it was already processed (`AddTipError::NonceConsumed` / outbound `AddTipError::UnknownMessage`) [3](#0-2) [4](#0-3) . The `LostTips` storage documents this as a known, only partially mitigated gap ("Capturing the lost tips here supports implementing a recovery method **in the future**") [5](#0-4) , meaning there is currently no on-chain recovery mechanism — the burned Ether is permanently lost to the user, exactly like the AlignedLayer report's "value committed to an account/flow with no way to top-up, redirect, or reverse it".

### Finding Description
`add_tip` is a public, unprivileged, signed extrinsic [1](#0-0) . Any user can call it with any `message_id` and any owned asset. The pallet:
1. Swaps the supplied asset for Ether and immediately burns it via `burn_for_teleport::<T::AssetTransactor>` — an irreversible action performed **before** any confirmation that the destination-side crediting will succeed [6](#0-5) .
2. Sends an `UnpaidExecution`/best-effort `Transact` to BridgeHub with `AddTip { sender, message_id, amount }` [2](#0-1) .
3. On BridgeHub, `EthereumSystemV2::add_tip` dispatches to `InboundQueue::add_tip`/`OutboundQueue::add_tip`. If the nonce has already been consumed (inbound) or no `PendingOrder` exists for it (outbound, e.g. after `process_delivery_receipt` removes the order at [7](#0-6) ), the call returns `Err` but is caught and merely appended to `LostTips`, with **no path back to the user and no on-chain remediation** [8](#0-7) .

Because the burn on AssetHub happens unconditionally and unilaterally before the destination-side check, and the destination check is racing against the relayer processing the underlying message (an attacker or even an ordinary relayer racing the user's tip transaction can consume the nonce first), the value-conservation invariant ("value must conserve and settle exactly once to the rightful beneficiary") required by the impact gate is violated: the tip Ether is destroyed with no corresponding credit anywhere, and no compensating mechanism exists in the repository (`LostTips` is read-only telemetry, not a claim/refund entry point).

This is the direct structural analog of the reported bug: in AlignedLayer, value/state ("batcher balance") could be depleted/consumed with no way to top up or redirect, permanently blocking correct settlement of an already-committed task. Here, value (the user's tip, converted to Ether and burned) is irreversibly consumed by a two-chain, non-atomic protocol with no compensating transaction if the second leg fails — a strict "burn now, hope it lands" pattern with no fallback.

### Impact Explanation
This falls under "public underpriced work" / "permanent user-fund lock" as defined in the gate: an unprivileged, ordinary user calling a normal, non-privileged public extrinsic (`add_tip`) can lose real value (Ether, swapped from their own DOT/asset) with no recovery, purely due to a race between their tip submission and the relayer's normal message processing — not requiring any malicious relayer, validator, or admin. Given tips are explicitly designed to incentivize processing of low-reward messages, and users are expected to add tips to *already-submitted but not-yet-processed* messages, the race window (tip vs. relayer processing) is inherent and not a contrived edge case.

### Likelihood Explanation
High. The race condition is a normal part of expected usage: a user observes a low-value queued message and adds a tip to incentivize a relayer, but a relayer may process the message (consuming the nonce or the `PendingOrders` entry) before or concurrently with the tip's cross-chain XCM delivery — a very plausible timing outcome in production given XCM's asynchronous, unpaid, best-effort delivery model. No special privileges, compromised nodes, or governance actions are required.

### Recommendation
- Do not burn/consume the tip asset on the source chain before the destination-side crediting is confirmed successful. Consider holding/reserving the asset until an XCM response (or receipt) confirms the tip was applied, then burn/finalize only on success.
- Alternatively, implement the "recovery method" alluded to in the `LostTips` doc comment now rather than deferring it — e.g., allow the original `sender` to reclaim (mint back or otherwise recover) the `LostTips` balance recorded on BridgeHub, closing the fund-loss gap.
- Add a settlement/callback so that if `add_tip` fails on BridgeHub, a compensating XCM/message is generated to refund equivalent value to `sender` on the source chain.

### Proof of Concept
1. Attacker/user observes an in-flight Ethereum→Polkadot message with nonce `N` still pending (not yet processed) in `EthereumInboundQueueV2`.
2. User calls `SystemFrontend::add_tip(origin, MessageId::Inbound(N), asset)` on AssetHub; `swap_fee_asset_and_burn` swaps `asset` for Ether and burns it immediately [1](#0-0) .
3. A relayer (not malicious — just doing its normal job) submits the proof for nonce `N` first, so `Nonce::<T>::set(nonce)` runs before the tip XCM arrives at BridgeHub [9](#0-8) .
4. The tip XCM's `Transact` dispatches `EthereumSystemV2::add_tip`, which calls `InboundQueue::add_tip(nonce, amount)`; since `Nonce::<T>::get(nonce)` is now `true`, it returns `AddTipError::NonceConsumed` [3](#0-2) .
5. `EthereumSystemV2::add_tip` catches this `Err`, records it into `LostTips::<T>` for `sender`, and emits `TipProcessed { success: false }` [10](#0-9)  — confirmed by the existing test `add_tip_inbound_fails_when_nonce_is_consumed`, which asserts `lost_tip == 1000` with no refund path [11](#0-10) .
6. The user's Ether (burned in step 2) is permanently gone; `LostTips` is only bookkeeping with "supports implementing a recovery method in the future" — i.e., no recovery exists today [5](#0-4) .

		fn swap_fee_asset_and_burn(
			origin: Location,
			fee_asset: Asset,
		) -> Result<u128, DispatchError> {
			let ether_location = T::EthereumLocation::get();
			let (fee_asset_location, fee_amount) = match fee_asset {
				Asset { id: AssetId(ref loc), fun: Fungible(amount) } => (loc, amount),
				_ => {
					tracing::debug!(target: LOG_TARGET, ?fee_asset, "error matching fee asset");
					return Err(Error::<T>::UnsupportedAsset.into());
				},
			};
			if fee_amount == 0 {
				return Ok(0);
			}

			let ether_gained = if *fee_asset_location != ether_location {
				Self::swap_and_burn(
					origin.clone(),
					fee_asset_location.clone(),
					ether_location,
					fee_amount,
				)
				.inspect_err(|&e| {
					tracing::debug!(target: LOG_TARGET, ?e, "error swapping asset");
				})?
			} else {
				burn_for_teleport::<T::AssetTransactor>(&origin, &fee_asset)
					.map_err(|_| Error::<T>::BurnError)?;
				fee_amount
			};
			Ok(ether_gained)
		}

		pub fn add_tip(
			origin: OriginFor<T>,
			sender: AccountIdOf<T>,
			message_id: MessageId,
			amount: u128,
		) -> DispatchResult {
			T::FrontendOrigin::ensure_origin(origin)?;

			let result = match message_id {
				Inbound(nonce) => <T as pallet::Config>::InboundQueue::add_tip(nonce, amount),
				Outbound(nonce) => <T as pallet::Config>::OutboundQueue::add_tip(nonce, amount),
			};

			if let Err(ref e) = result {
				tracing::debug!(target: LOG_TARGET, ?e, ?message_id, ?amount, "error adding tip");
				LostTips::<T>::mutate(&sender, |lost_tip| {
					*lost_tip = lost_tip.saturating_add(amount);
				});
			}

			Self::deposit_event(Event::<T>::TipProcessed {
				sender,
				message_id,
				amount,
				success: result.is_ok(),
			});

			Ok(())
		}

fn add_tip_inbound_fails_when_nonce_is_consumed() {
	new_test_ext(true).execute_with(|| {
		let origin = make_xcm_origin(FrontendLocation::get());
		let sender: AccountId = Keyring::Alice.into();

		assert_ok!(EthereumSystemV2::add_tip(origin, sender.clone(), message_id.clone(), amount));

		System::assert_last_event(RuntimeEvent::EthereumSystemV2(Event::<Test>::TipProcessed {
			sender: sender.clone(),
			message_id,
			amount,
			success: false,
		}));

		let lost_tip = LostTips::<Test>::get(sender);
		assert_eq!(lost_tip, 1000);
	});
}
