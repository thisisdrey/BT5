### Title
Unbounded delegation-index list allows attacker-inflated, unbounded `prefixQuery` scans in `GetDelegatedResourceAccountIndex`/`V2` API - (File: `chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java`)

### Summary
`DelegatedResourceAccountIndexStore` maintains, per account, a growable list of "from"/"to" delegation-index entries keyed by `FROM_PREFIX`/`TO_PREFIX` (and V2 variants) [1](#0-0) . Every `DelegateResourceContract`/`DelegateResourceProcessor` (TVM native contract) call adds a new independent DB record for the (owner, receiver) pair via `delegateV2`/`delegate`, with no limit on the number of distinct receiver addresses a single account may accumulate [2](#0-1) . The only economic constraint is a minimum of 1 TRX per delegation [3](#0-2) , and delegated balances can be later reclaimed via `UnDelegateResourceActuator`, so an attacker can cheaply and repeatedly delegate 1 TRX to many freshly generated receiver addresses, growing the on-disk index for their own account without bound.

### Finding Description
The read path `getIndex`/`getV2Index` in `DelegatedResourceAccountIndexStore` calls `getWithPrefix`, which performs a `prefixQuery` for both the "from" and "to" prefixes of an address, materializes every matching DB record into an in-memory list, sorts the list by timestamp, and rebuilds the full list into a `DelegatedResourceAccountIndexCapsule` [4](#0-3) . This is invoked directly by the public `GetDelegatedResourceAccountIndex`/`GetDelegatedResourceAccountIndexV2` gRPC and HTTP endpoints, which are unauthenticated, anonymous, read-only API calls [5](#0-4) . Because the number of index entries per address is unbounded (bounded only by how many cheap 1-TRX delegate transactions the attacker is willing to submit and possibly reclaim via `UnDelegateResourceActuator`), an attacker can inflate their own account's delegation index to an arbitrarily large size, then have any anonymous client (or repeatedly themselves) trigger `prefixQuery` scans and in-memory sorts over that inflated dataset by simply querying the public API for that address. This mirrors the reported bug class of an "unbounded externally-controlled list that is iterated in full during a reachable operation," except here the growth is driven by ordinary signed `DelegateResourceContract` transactions from an unprivileged account (not an admin), and the DoS surface is the public query API path (`GetDelegatedResourceAccountIndex(V2)`) rather than an award-completion function.

### Impact Explanation
Each call to the affected API forces the node to scan and sort a large, attacker-controlled key range from the persistent store and build/return a correspondingly large response, consuming CPU, memory, and I/O disproportionate to the requester's cost. Because this endpoint is reachable via unauthenticated JSON-RPC/HTTP/gRPC query paths (`GetDelegatedResourceAccountIndex`, `GetDelegatedResourceAccountIndexV2`, and their Solidity/PBFT node equivalents), it can be repeatedly invoked by anonymous clients to degrade query-serving nodes, potentially exhausting node resources and making the API unavailable to legitimate users ("an API the node can no longer serve").

### Likelihood Explanation
Likelihood is moderate: the attack requires the attacker to first accumulate a large number of distinct delegation index entries under their own address by sending many `DelegateResourceContract` (or native TVM `delegateResource`) transactions, each costing only the 1 TRX minimum (recoverable via undelegate) plus normal transaction fees. This is inexpensive relative to typical blockchain DoS costs and requires no special privileges, unlike the admin-only precondition in the original report. The subsequent exploitation step (querying the public index API) requires no authentication and is instantaneous.

### Recommendation
- Cap the number of distinct delegation-index entries (`toAccounts`/`fromAccounts`) per address, or enforce pagination directly at the storage layer (`prefixQuery`) rather than materializing the full result set before returning.
- Add a maximum result-size limit and/or require offset/limit parameters for `GetDelegatedResourceAccountIndex(V2)` similar to `GetPaginatedProposalList`/`GetPaginatedExchangeList` patterns already present in the API surface [6](#0-5) .
- Consider charging bandwidth/energy proportional to the resulting index size for delegate/undelegate operations, or impose a rate/size limit on repeated delegate-to-new-address operations from a single account within a time window.

### Proof of Concept
1. From an attacker-controlled account, repeatedly submit `DelegateResourceContract` transactions delegating the minimum 1 TRX of bandwidth/energy to a large number of freshly generated, distinct receiver addresses (each such call appends one more entry via `delegatedResourceAccountIndexStore.delegateV2` [7](#0-6) ).
2. Optionally reclaim the delegated TRX via `UnDelegateResourceContract` and repeat to further grow the index at low net cost, since undelegate does not shrink the historical index count in the `DelegatedResourceAccountIndexStore` model used for read (`getV2Index`) — verification of whether `unDelegateV2` removes the underlying keyed record was not fully confirmed in this review and should be validated by a background agent inspecting `UnDelegateResourceActuator`/`DelegatedResourceAccountIndexStore.unDelegateV2`.
3. Issue repeated `GetDelegatedResourceAccountIndexV2` (gRPC/HTTP) queries against the attacker's address from any anonymous client and measure node CPU/memory/latency degradation caused by the `prefixQuery` + sort in `getWithPrefix` [8](#0-7) .

Note: I was not able to fully confirm within the available index whether `unDelegateV2`/`convert` fully removes stale entries after an undelegate, which affects exactly how cheaply the list can be inflated indefinitely versus how large a single "active" delegation set can practically grow; a background agent with full repository/test access should verify this before finalizing severity and remediation scope.

  public DelegatedResourceAccountIndexCapsule getIndex(byte[] address) {
    DelegatedResourceAccountIndexCapsule indexCapsule = get(address);
    if (indexCapsule != null) {
      return indexCapsule;
    }
    return getWithPrefix(FROM_PREFIX, TO_PREFIX, address);
  }

  public DelegatedResourceAccountIndexCapsule getV2Index(byte[] address) {
    return getWithPrefix(V2_FROM_PREFIX, V2_TO_PREFIX, address);
  }

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }

    DelegatedResourceStore delegatedResourceStore = chainBaseManager.getDelegatedResourceStore();
    DelegatedResourceAccountIndexStore delegatedResourceAccountIndexStore = chainBaseManager
        .getDelegatedResourceAccountIndexStore();

    // 1. unlock the expired delegate resource
    long now = chainBaseManager.getDynamicPropertiesStore().getLatestBlockHeaderTimestamp();
    delegatedResourceStore.unLockExpireResource(ownerAddress, receiverAddress, now);

    long expireTime = 0;
    if (lock) {
      expireTime = now + lockPeriod * BLOCK_PRODUCED_INTERVAL;
    }
    byte[] key = DelegatedResourceCapsule.createDbKeyV2(ownerAddress, receiverAddress, lock);
    DelegatedResourceCapsule delegatedResourceCapsule = delegatedResourceStore.get(key);
    if (delegatedResourceCapsule == null) {
      delegatedResourceCapsule = new DelegatedResourceCapsule(ByteString.copyFrom(ownerAddress),
          ByteString.copyFrom(receiverAddress));

      delegatedResourceCapsule.addFrozenBalanceForBandwidth(balance, expireTime);
    } else {
      delegatedResourceCapsule.addFrozenBalanceForEnergy(balance, expireTime);
    }
    delegatedResourceStore.put(key, delegatedResourceCapsule);

    //modify DelegatedResourceAccountIndexStore
    delegatedResourceAccountIndexStore.delegateV2(ownerAddress, receiverAddress,
        dynamicPropertiesStore.getLatestBlockHeaderTimestamp());
