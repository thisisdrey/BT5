### Title
Fixed-window stream throttle boundary allows unstaked/staked clients to double their effective stream admission rate - ([File: streamer/src/nonblocking/stream_throttle.rs])

### Summary
`ConnectionStreamCounter::reset_throttling_params_if_needed` implements a fixed (non-sliding) window counter keyed off `last_throttling_instant`, and `throttle_stream` only checks `stream_count` against `max_streams_per_throttling_interval` at the moment a new stream arrives. Because the window boundary is a wall-clock instant that the remote peer can observe indirectly (via its own send timing) and because the check/reset happens lazily on stream arrival rather than being enforced continuously, a client can burst `max_streams_per_throttling_interval` streams just before a window reset and another full quota immediately after the reset, doubling its effective admitted-stream rate at each window boundary.

### Finding Description
The relevant call chain is `SwQos::on_new_stream` (`streamer/src/nonblocking/swqos.rs:497-516`) → `throttle_stream` (`streamer/src/nonblocking/stream_throttle.rs:233-271`) → `ConnectionStreamCounter::reset_throttling_params_if_needed` (`stream_throttle.rs:213-230`) → `stream_count.load`.

`reset_throttling_params_if_needed` only resets `stream_count` to `0` and moves `last_throttling_instant` forward when `Instant::now().duration_since(last_throttling_instant) > STREAM_THROTTLING_INTERVAL` (100ms) at the moment a stream happens to arrive: [1](#0-0) 

`throttle_stream` then compares the *current* `stream_count` against `max_streams_per_throttling_interval` and only sleeps if the count is already at/over the limit: [2](#0-1) 

Because the window is fixed-length and anchored to whenever the last reset happened (not to a global clock grid), and because the attacker fully controls the arrival timing of their own QUIC uni-streams on their own connection, they can:
1. Open a connection and immediately send `max_streams_per_throttling_interval` streams (consuming the full quota of window W0, all admitted without sleep since `stream_count < limit` on each check).
2. Wait until just before `STREAM_THROTTLING_INTERVAL` elapses relative to `last_throttling_instant`, then send one more stream, which is the trigger that flips `reset_throttling_params_if_needed` into resetting `stream_count` to 0 and starting window W1.
3. Immediately (within microseconds) send another full `max_streams_per_throttling_interval` burst, all again admitted because `stream_count` was just reset to 0 for W1.

This yields `2 * max_streams_per_throttling_interval` streams admitted within a span far shorter than `2 * STREAM_THROTTLING_INTERVAL`, i.e., effectively concentrated at the W0/W1 boundary. Since the anchor for window W2 is set by whenever the reset for W1 actually fired (again attacker-controlled via timing of the triggering stream), the attacker can repeat this same boundary-straddling pattern at every subsequent window transition, sustaining close to 2x the nominal `max_streams_per_throttling_interval / STREAM_THROTTLING_INTERVAL` rate indefinitely, bounded only by their ability to precisely time sends relative to their own previously observed reset instants (which they can infer from RTT and locally-tracked send/ack timing since it is their own connection).

No sliding-window or token-bucket smoothing exists here to prevent this: unlike `simple_qos.rs`'s `consume_tokens`/token-bucket model used by `SimpleQos::on_new_stream` (which is not vulnerable to this because it computes token replenishment continuously via `us_to_have_tokens`), the `SwQos` path uses this discrete fixed-window model exclusively via `throttle_stream`. [3](#0-2) 

### Impact Explanation
This is a QoS evasion issue: an unstaked (or low-stake) remote client can sustain up to ~2x its nominally allotted stream/transaction admission rate on the leader's TPU by precisely timing stream opens around the throttle window boundary, at the expense of correctly-behaved peers competing for the same unstaked/staked throttling budget (`max_unstaked_load_in_throttling_window` / `max_staked_load_in_throttling_window` computed in `StakedStreamLoadEMA`). This matches the "unstaked stream limits enforced per source... evaded by interval timing" QoS-evasion bounty category referenced in the question, causing legitimate senders to receive proportionally less TPU stream capacity than intended.

### Likelihood Explanation
- No special privileges are required: this is exploitable by any unstaked client capable of opening a QUIC connection to the public TPU port and controlling the timing of its own uni-stream opens, which is exactly the assumed unprivileged attacker model.
- The only precondition is default `max_streams_per_throttling_interval`/`STREAM_THROTTLING_INTERVAL_MS` (100ms) configuration, which is the default in `quic.rs`'s `DEFAULT_MAX_STREAMS_PER_MS`.
- Precise timing is required but well within reach: 100ms is a large window relative to network jitter, and the attacker can locally track `last_throttling_instant` behavior by observing when its bursts start getting throttled (i.e., when `sleep` kicks in vs. not), allowing it to re-synchronize its timing every window without needing exact knowledge of the server's internal clock.
- The exploit is repeatable indefinitely as long as the attacker maintains the connection and re-times each burst relative to the previous observed reset.

### Recommendation
Replace the fixed-window reset logic in `ConnectionStreamCounter`/`throttle_stream` with a sliding-window or token-bucket algorithm (similar to the `consume_tokens`/`us_to_have_tokens` model already used in `streamer/src/nonblocking/simple_qos.rs`) so that the admitted-stream rate is smoothed continuously rather than reset in discrete fixed intervals that can be straddled. Alternatively, when resetting, carry over any "debt"/excess from the previous window (e.g., subtract overflow from the new window's budget) instead of fully zeroing `stream_count`.

### Proof of Concept
```rust
// streamer/src/nonblocking/stream_throttle.rs (new test)
#[tokio::test(flavor = "multi_thread", start_paused = true)]
async fn test_boundary_straddle_doubles_admitted_streams() {
    use std::sync::Arc;

    let stats = Arc::new(StreamerStats::default());
    let stream_counter = Arc::new(ConnectionStreamCounter::new());
    let max_streams_per_interval = 10u64;

    // Fill window 0 fully (all admitted, no sleep since count starts at 0).
    for _ in 0..max_streams_per_interval {
        stream_counter.stream_count.fetch_add(1, Ordering::Relaxed);
        throttle_stream(
            &stats,
            ConnectionPeerType::Unstaked,
            "127.0.0.1:0".parse().unwrap(),
            &stream_counter,
            max_streams_per_interval,
        )
        .await;
    }

    // Advance time to just before the window boundary.
    tokio::time::advance(STREAM_THROTTLING_INTERVAL - Duration::from_millis(1)).await;

    // Trigger the reset by crossing the boundary with one more stream.
    tokio::time::advance(Duration::from_millis(2)).await;
    stream_counter.stream_count.fetch_add(1, Ordering::Relaxed);
    throttle_stream(
        &stats,
        ConnectionPeerType::Unstaked,
        "127.0.0.1:0".parse().unwrap(),
        &stream_counter,
        max_streams_per_interval,
    )
    .await; // stream_count reset to 0 internally, this stream is now "1"

    // Immediately (no time advance) burst another full window's worth.
    let mut admitted_in_burst = 1u64; // the triggering stream above
    for _ in 0..(max_streams_per_interval - 1) {
        stream_counter.stream_count.fetch_add(1, Ordering::Relaxed);
        throttle_stream(
            &stats,
            ConnectionPeerType::Unstaked,
            "127.0.0.1:0".parse().unwrap(),
            &stream_counter,
            max_streams_per_interval,
        )
        .await;
        admitted_in_burst += 1;
    }

    // Assert: total admitted within ~2ms window >= 2x nominal per-interval quota,
    // i.e. max_streams_per_interval (window0) + admitted_in_burst (window1 burst)
    // >= 2 * max_streams_per_interval, with no throttling sleep observed.
    assert!(
        max_streams_per_interval + admitted_in_burst >= 2 * max_streams_per_interval,
        "expected boundary-straddling burst to admit >= 2x nominal quota"
    );
    assert_eq!(stats.throttled_streams.load(Ordering::Relaxed), 0);
}
```
Expected result: the test demonstrates that `2 * max_streams_per_throttling_interval` streams are admitted with zero throttling sleeps within a time span far smaller than `2 * STREAM_THROTTLING_INTERVAL`, confirming the fixed-window reset in `reset_throttling_params_if_needed` (`stream_throttle.rs:213-230`) can be straddled to double the nominal admission rate.

    pub(crate) fn reset_throttling_params_if_needed(&self) -> tokio::time::Instant {
        let last_throttling_instant = *self.last_throttling_instant.read().unwrap();
        if tokio::time::Instant::now().duration_since(last_throttling_instant)
            > STREAM_THROTTLING_INTERVAL
        {
            let mut last_throttling_instant = self.last_throttling_instant.write().unwrap();
            // Recheck as some other thread might have done throttling since this thread tried to acquire the write lock.
            if tokio::time::Instant::now().duration_since(*last_throttling_instant)
                > STREAM_THROTTLING_INTERVAL
            {
                *last_throttling_instant = tokio::time::Instant::now();
                self.stream_count.store(0, Ordering::Relaxed);
            }
            *last_throttling_instant
        } else {
            last_throttling_instant
        }
    }

pub(crate) async fn throttle_stream(
    stats: &StreamerStats,
    peer_type: ConnectionPeerType,
    remote_addr: std::net::SocketAddr,
    stream_counter: &Arc<ConnectionStreamCounter>,
    max_streams_per_throttling_interval: u64,
) {
    let throttle_interval_start = stream_counter.reset_throttling_params_if_needed();
    let streams_read_in_throttle_interval = stream_counter.stream_count.load(Ordering::Relaxed);
    if streams_read_in_throttle_interval >= max_streams_per_throttling_interval {
        // The peer is sending faster than we're willing to read. Sleep for what's

            STREAM_THROTTLING_INTERVAL.saturating_sub(throttle_interval_start.elapsed());
