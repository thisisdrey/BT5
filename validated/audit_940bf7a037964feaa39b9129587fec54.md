### Title
Out-of-bounds read parsing untrusted ZIP/JAR central directory entries in `ijar` - (File: `third_party/ijar/zip.cc`)

### Summary
`ijar` (the interface-jar generator used by `run_ijar`/`java_common.run_ijar` and any `java_library`/`java_import` compile action) parses the ZIP central directory of an input jar with `InputZipFile::ProcessCentralDirEntry` [1](#0-0) . Unlike its sibling `ProcessLocalFileEntry`, which guards every field read with `EnsureRemaining()` [2](#0-1) , `ProcessCentralDirEntry` performs no bounds validation before advancing the cursor `p` and dereferencing memory via `get_u4le`/`get_u2le`, which are raw, unchecked pointer reads [3](#0-2) .

### Finding Description
A jar consumed by Bazel's Java toolchain (e.g. one fetched with `http_jar`/`http_archive`, a `maven_install` artifact, or any dependency whose bytes an untrusted origin server or registry ultimately controls) is fed to `ijar` to produce a header jar. `InputZipFile::Open` locates the central directory and hands its start pointer to a loop of `ProcessCentralDirEntry` calls [4](#0-3) .

Inside `ProcessCentralDirEntry`, after checking only the 4-byte signature, the code unconditionally advances `p += 16`, then reads `compressed_size`, `uncompressed_size`, `file_name_length`, `extra_field_length`, `file_comment_length`, `attr`, and `offset` with no check that these bytes remain inside the mapped input file [5](#0-4) . It then does `memcpy(filename, p, len)` where `len` is bounded to the output buffer, but the source `p` is not validated against the mapped file end. Following that, `p += file_name_length_` and later `p += extra_field_length` and the "extra field" parsing loop reads `header_id`/`data_size` via `get_u2le(extra_p)` and advances `extra_p += data_size` an attacker-controlled number of times [6](#0-5) . None of `get_u4le`/`get_u2le`/`get_u8le` perform any bounds checking — they are raw pointer dereferences [7](#0-6) .

A crafted jar's central directory can declare `file_name_length`, `extra_field_length`, or `file_comment_length` values that run past the actual end of the mmap'd file (or past the true end of the central directory before another data structure), causing `get_u4le`/`get_u2le` to read heap/mmap memory beyond the intended region and beyond the file's declared content. That out-of-bounds data is then embedded into `filename[]`, `attr`, `offset`, and (via the ZIP64 extra field parsing) into `*uncompressed_size`/`*compressed_size`/`*offset`, which get propagated into `InputZipFile::ProcessNext`/`ProcessFile`/`CalculateOutputLength` and ultimately into file names, sizes, or attributes written into the resulting interface jar — leaking process memory content into a build artifact.

Because `EnsureRemaining()` exists and is used deliberately in the local-file-header parser but is simply absent from the central-directory parser, the guard that is supposed to hold ("reads never exceed the mapped input buffer") is not total across all parsing entry points.

### Impact Explanation
An attacker able to publish or influence the bytes of a jar dependency consumed via a build (matching whatever checksum/lockfile entry is pinned — the checksum binds to the exact bytes, not to their being a well-formed ZIP structure) can craft a central directory whose length fields point past the mapped file. This causes `ijar` to read out-of-bounds heap/mmap memory and copy fragments of that memory (e.g. adjacent heap contents) into the emitted interface-jar's file name, attribute, or size fields — an information-disclosure primitive analogous to the SQLite OOB read in the referenced CVE, and potentially a crash (denial of the specific build) if the read crosses an unmapped page.

### Likelihood Explanation
`ijar` is invoked on every jar dependency during ordinary Java compilation (`run_ijar`) whenever a `java_library`/`java_import` depends on a prebuilt jar, so any jar sourced from `http_jar`, an untrusted mirror, or a compromised Maven coordinate is reachable. Triggering the bug only requires crafting central-directory length fields inconsistent with the actual archive size, which does not require breaking the pinned sha256/integrity value.

### Recommendation
Add the same `EnsureRemaining()`-style bounds checks used in `ProcessLocalFileEntry` to `ProcessCentralDirEntry` (and to the ZIP64 extra-field walk) before every `get_u2le`/`get_u4le`/`get_u8le` call and before every pointer arithmetic advance (`p += file_name_length`, `p += extra_field_length`, `p += file_comment_length`, `extra_p += data_size`), rejecting the entry with an error instead of reading past the mapped file end.

### Proof of Concept
Construct a minimal ZIP whose End-of-Central-Directory record points to a Central Directory Header near the very end of the mmap'd file, with `file_name_length`/`extra_field_length`/`file_comment_length` set to values that would place `p` past `zipdata_in_ + input_file_->Length()`. Run `ijar` (or `java_common.run_ijar`) on this file; observe via ASan/Valgrind that `get_u2le`/`get_u4le` in `ProcessCentralDirEntry` read past the mapped region, and that the resulting `-interface.jar`'s emitted filename/attr bytes contain out-of-bounds memory content — implementable as a `src/test/shell/bazel` or `third_party/ijar/test` shell test that crafts such a jar and inspects the produced interface jar / runs under a sanitizer build of `ijar.cc`.

bool InputZipFile::ProcessCentralDirEntry(const u1 *&p, u8 *compressed_size,
                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
  const u1 *extra_p = p;
  p += extra_field_length;
  while (extra_p != p) {
    const u2 header_id = get_u2le(extra_p);
    const u2 data_size = get_u2le(extra_p);
    const u1 *extra = extra_p;
    extra_p += data_size;
    if (header_id == ZIP64_EXTRA_FIELD_TAG) {
      if (*uncompressed_size == U4_MAX) {
        *uncompressed_size = get_u8le(extra);
      }
      if (*compressed_size == U4_MAX) {
        *compressed_size = get_u8le(extra);
      }
      if (*offset == U4_MAX) {
        *offset = get_u8le(extra);
      }
    }
  }
  p += file_comment_length;

inline u1 get_u1(const u1 *&p) {
    return *p++;

inline u2 get_u2be(const u1 *&p) {
    u4 x = (p[0] << 8) | p[1];
    p += 2;
    return x;
}

inline u2 get_u2le(const u1 *&p) {
    u4 x = (p[1] << 8) | p[0];
    p += 2;
    return x;
}

inline u4 get_u4be(const u1 *&p) {
    u4 x = (p[0] << 24) | (p[1] << 16) | (p[2] << 8) | p[3];
    p += 4;
    return x;
}

inline u4 get_u4le(const u1 *&p) {
    u4 x = (p[3] << 24) | (p[2] << 16) | (p[1] << 8) | p[0];
    p += 4;
    return x;
}

inline u8 get_u8le(const u1 *&p) {
  u4 lo = get_u4le(p);
  u4 hi = get_u4le(p);
  u8 x = ((u8)hi << 32) | lo;
  return x;
}
