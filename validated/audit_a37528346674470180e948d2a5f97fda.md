## Title
Unbounded Reference Update Loop in `UpdateReferences` RPC Enables Resource-Exhaustion DoS - (File: `internal/gitaly/service/ref/update_references.go`)

### Summary
The `UpdateReferences` RPC accepts a client-controlled, unbounded stream of `UpdateReferencesRequest` messages, each carrying an arbitrarily large `Updates` slice. The handler iterates over every update in every streamed message with no cap on the total count, queues each into a single `updateref.Updater` transaction, and finally commits them all atomically via one `git-update-ref` invocation. This mirrors the reported `redeem` bug class: an unbounded loop over user-supplied collection size executed within one request/transaction, which can be driven arbitrarily large by an ordinary caller with write access to a repository.

### Finding Description
`UpdateReferences` reads an initial request and then loops indefinitely on `server.Recv()`, and for every received message iterates `for _, update := range request.GetUpdates()`, validating and queueing each entry into a single in-flight `updateref.Updater`: [1](#0-0) 

There is no limit on:
- the number of `Updates` entries per streamed message,
- the number of streamed messages the server will accept before calling `updater.Commit()`.

The only per-message size constraint is gRPC's default max message size, which does not bound the number of streamed messages a client may send, nor the number of individual reference updates that must be validated (`git.ValidateReference`, `objectHash.ValidateHex`) and queued (`updater.Update(...)`) in a single, uninterruptible server-side loop before a single `git-update-ref` commit is executed: [2](#0-1) 

This is functionally the same defect class as the reported `redeem` bug: a per-call loop whose iteration count is fully attacker/caller controlled and unbounded, with all work performed synchronously within one RPC invocation/transaction. Internal Gitaly tooling itself acknowledges the need to batch such calls (splitting into slices of 100) precisely because the server does not enforce this limit itself: [3](#0-2) 

### Impact Explanation
Any authenticated/authorized user permitted to invoke `UpdateReferences` (e.g., via a mutator RPC on a repository) can submit hundreds of thousands or millions of reference updates in one logical call, forcing Gitaly to:
- perform per-update validation work in an unbounded Go loop,
- hold an open `git-update-ref` process with unbounded queued updates,
- commit an extremely large single reference transaction, consuming CPU, memory, and potentially blocking the reference store (and the reference-transaction hook path) for an extended period.

This can degrade or deny service for the targeted repository/Gitaly node, matching the "DoS of a handler" acceptance criterion. As in the original report, the operator/caller triggering it is expected to have some legitimate access, but the absence of a server-enforced cap allows disproportionate resource consumption from a single RPC call.

### Likelihood Explanation
Any client capable of calling `RefService.UpdateReferences` (mutator RPC) can trigger this by streaming a large number of updates; no special privileges beyond normal repository write access are required, and no additional bypass is needed since the loop bound is simply absent.

### Recommendation
Enforce an explicit maximum number of reference updates accepted per `UpdateReferences` call (summed across all streamed messages) before rejecting the request or requiring the client to split it into multiple RPC calls/transactions, mirroring the batching already used internally (e.g., cap at a fixed number such as 100–1000 updates per call) with a corresponding `structerr.NewInvalidArgument` (or `ResourceExhausted`) response when exceeded.

### Proof of Concept
1. Open a bidirectional stream to `RefService.UpdateReferences`.
2. Send an initial `UpdateReferencesRequest` with `Repository` set and a very large `Updates` array (or repeatedly send subsequent messages each with large `Updates` arrays) referencing valid-format but distinct reference names/object IDs.
3. Observe the server loop at `internal/gitaly/service/ref/update_references.go:57-88` processing and queuing all entries without any count-based rejection, followed by a single massive `updater.Commit()` — consuming disproportionate CPU/memory/time on the Gitaly node servicing the call.

# Create the refs/refs/zzz-N refs on the pinned revision via bulk
# UpdateReferences. The stream is built by hand because raw.update_refs
# sets `repository` on every message, which Gitaly rejects once a call
# spans multiple 100-ref slices.
_ADDITIONAL_REFS_SCRIPT = r"""
require 'json'

group_path = ENV.fetch('PROVISION_GROUP')
specs = JSON.parse(ENV.fetch('PROVISION_SPECS'))
batch_size = Integer(ENV.fetch('PROVISION_REF_BATCH', '50000'))

bulk_update_refs = lambda do |raw, updates|
  requests = Enumerator.new do |y|
    updates.each_slice(100).with_index do |slice, i|
      msgs = slice.map do |u|
        Gitaly::UpdateReferencesRequest::Update.new(
          old_object_id: u[:old_sha],
          new_object_id: u[:new_sha],
          reference: u[:reference]
        )
      end
      args = { updates: msgs }
      args[:repository] = raw.gitaly_repository if i.zero?
      y.yield Gitaly::UpdateReferencesRequest.new(**args)
    end
  end
  Gitlab::GitalyClient.call(raw.storage, :ref_service, :update_references,
                            requests, timeout: Gitlab::GitalyClient.long_timeout)
