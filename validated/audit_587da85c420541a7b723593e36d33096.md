### Title
Missing frozen-duration bounds check in `FreezeBalanceProcessor` allows expiration-time overflow when freezing balance via TVM contract call - (File: `actuator/src/main/java/org/tron/core/vm/nativecontract/FreezeBalanceProcessor.java`)

### Summary
The Cally bug arises because an attacker-controlled small integer (`vault.durationDays`, `uint8`) is multiplied by a time constant without a preceding range check, causing the intermediate multiplication to overflow before the resulting expiration timestamp is computed. The analogous java-tron code path is the native-contract implementation of `FreezeBalance` reachable from within a smart contract via the TVM, where the duration value used to compute `expireTime` is never bounds-checked before being multiplied by `FROZEN_PERIOD`.

### Finding Description
`FreezeBalanceProcessor.execute()` computes the freeze expiration as: [1](#0-0) 

`param.getFrozenDuration()` is a raw `long` field supplied via `FreezeBalanceParam` (populated from the TVM instruction path in `Program.java`), and is multiplied directly by `FROZEN_PERIOD` (`86_400_000L`) with no upper bound.

Critically, `FreezeBalanceProcessor.validate()` — the counterpart to `execute()` used by the same native-contract path invoked from a smart contract — never validates `frozenDuration` against any minimum/maximum, unlike the ordinary top-level `FreezeBalanceActuator`: [2](#0-1) 

Compare this to `FreezeBalanceActuator.validate()`, which explicitly bounds `frozenDuration` between `minFrozenTime` and `maxFrozenTime` before it is ever multiplied by `FROZEN_PERIOD` in `execute()`: [3](#0-2) [4](#0-3) 

Because `FreezeBalanceProcessor` lacks this check entirely, a sufficiently large `frozenDuration` value (roughly `> Long.MAX_VALUE / FROZEN_PERIOD ≈ 1.0675 × 10^11`) passed to this native contract through a TVM call causes `param.getFrozenDuration() * FROZEN_PERIOD` to silently overflow. Unlike Solidity ≥0.8 (which reverts on overflow, as seen in the original Cally report), Java `long` arithmetic wraps silently with no exception, so `expireTime` becomes an unpredictable (potentially negative or otherwise nonsensical) value that is written directly into account/delegated-resource state via `accountCapsule.setFrozenForBandwidth(...)`, `setFrozenForEnergy(...)`, or `delegatedResourceCapsule.addFrozenBalanceFor...(...)`.

### Impact Explanation
An attacker-deployed contract can freeze TRX (own or delegated) while forcing an out-of-range `expireTime` through this unchecked native-contract path. Since the TRX balance is deducted and total resource weight is incremented unconditionally in `execute()` regardless of the corrupted expiration value, the resulting account/resource state can diverge from the invariants relied on by unfreeze logic and resource accounting elsewhere in the codebase (e.g., the expiry checks used for permitting withdrawal, similar to `unfreezeExpire` checks such as `next.getUnfreezeExpireTime() <= now` seen in `UnfreezeBalanceV2Processor`). This can allow resource weight to be created without a correctly-locked corresponding freeze duration, undermining the freeze/unfreeze accounting invariant and potentially enabling premature or permanently-stuck fund states.

### Likelihood Explanation
This path is reachable by any unprivileged contract deployer/caller: it is invoked purely from a TVM smart-contract call (native contract triggered from `Program.java`), requiring only a crafted duration argument, no special privileges, and no cooperation from other parties. The lack of any bound check (present in the sibling `FreezeBalanceActuator` but absent here) makes the trigger trivial to construct.

### Recommendation
Add the same `minFrozenTime`/`maxFrozenTime` bounds validation to `FreezeBalanceProcessor.validate()` that already exists in `FreezeBalanceActuator.validate()`, rejecting any `frozenDuration` outside the permitted range before it reaches the multiplication in `execute()`. Additionally, consider using `Math.addExact`/`Math.multiplyExact` (as already used elsewhere in the codebase, e.g., `StrictMathWrapper.addExact` in `AssetIssueActuator`) to fail closed rather than silently wrap on overflow.

### Proof of Concept
1. Deploy a smart contract that invokes the TVM `FreezeBalance` native contract op (via `Program.java`) with `frozenDuration` set to a value greater than `Long.MAX_VALUE / FROZEN_PERIOD` (~1.0675 × 10^11).
2. Because `FreezeBalanceProcessor.validate()` performs no bounds check on `frozenDuration`, the call passes validation.
3. In `FreezeBalanceProcessor.execute()`, `param.getFrozenDuration() * FROZEN_PERIOD` overflows the `long` type silently, producing a corrupted `expireTime` that is persisted into account/delegated-resource state alongside the deducted balance and incremented total resource weight.

    AccountCapsule ownerCapsule = repo.getAccount(ownerAddress);
    long frozenBalance = param.getFrozenBalance();
    if (frozenBalance <= 0) {
      throw new ContractValidateException("FrozenBalance must be positive");
    } else if (frozenBalance < TRX_PRECISION) {
      throw new ContractValidateException("FrozenBalance must be greater than or equal to 1 TRX");
    } else if (frozenBalance > ownerCapsule.getBalance()) {
      throw new ContractValidateException("FrozenBalance must be less than or equal to accountBalance");
    }

    // validate frozen count of owner account

    if (frozenCount != 0 && frozenCount != 1) {
      throw new ContractValidateException("FrozenCount must be 0 or 1");

      case ENERGY:
