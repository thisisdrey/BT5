### Title
Silent truncation to zero in PSM decimal conversion allows fund-swallowing / no-op mint-redeem without error - (File: `substrate/frame/psm/src/lib.rs`)

### Summary
`pallet-psm`'s decimal-scaling helpers `external_to_internal` and `internal_to_external` perform integer division to rescale amounts between an external asset's decimals and the internal stablecoin's decimals. When the division underflows to zero (a "dust" amount whose scaled value rounds down to `0`), the code does **not** return an error — it silently returns `Ok(BalanceOf::<T>::zero())` via `unwrap_or_else(BalanceOf::<T>::zero)`. This mirrors the external report's core defect class: an unchecked decimal/precision boundary condition causes a downstream value to collapse to zero, and the surrounding logic has no explicit guard for that outcome, unlike other paths in the same functions (the multiplication branches) that correctly propagate `Error::<T>::ConversionOverflow`.

### Finding Description
`substrate/frame/psm/src/lib.rs`:

```rust
pub(crate) fn external_to_internal(...) -> Result<BalanceOf<T>, Error<T>> {
    match ext_decimals.cmp(&internal_decimals) {
        Equal => Ok(amount),
        Less => {
            let factor = Self::pow10(diff)?;
            amount.checked_mul(&factor).ok_or(Error::<T>::ConversionOverflow)
        },
        Greater => {
            let factor = Self::pow10(diff)?;
            Ok(amount.checked_div(&factor).unwrap_or_else(BalanceOf::<T>::zero))
        },
    }
}

The mirror function `internal_to_external` has the same pattern in its `Less` branch: [2](#0-1) 

Both dividing branches use `checked_div(...).unwrap_or_else(BalanceOf::<T>::zero)` — a `checked_div` can only return `None` on division by zero (the divisor, `factor`, computed by `pow10`, is always `>= 1`, so it never actually returns `None` in practice), but critically **the function returns `Ok(0)` whenever `amount / factor` rounds down to `0`, rather than signalling an error for a below-precision amount**. This is structurally identical to the reported bug class: a rounding condition at a decimal/precision boundary (division performed without an accompanying magnitude check) silently produces a zero value that the caller has no way to detect as anomalous, because the function signature reports success (`Ok`) instead of the caller-expected failure semantics used elsewhere in the same file for overflow.

Because `add_external_asset` allows configuring PSM instances for arbitrary approved external assets with their own decimals, and the scaling factor is `10^(|ext_decimals - internal_decimals|)`, any external asset whose decimals are large relative to the internal asset's decimals (or where a user submits a dust amount below the precision threshold) causes `external_to_internal`/`internal_to_external` to return `Ok(0)` for a non-zero input amount.

### Impact Explanation
If `mint`/`redeem` dispatchables (which call these helpers — visible from the doc examples and pallet overview referencing `Mint`/`Redeem`) do not separately re-validate that the *converted* amount is non-zero before performing the associated asset transfer/mint/burn, a user can:
- Deposit a non-zero (but below-precision) external asset amount, which is transferred into the PSM reserve, while the internal-asset amount computed for minting is silently `0` — resulting in a permanent loss/lock of the user's deposited funds with no minted internal asset issued in return, and no error raised to reject the operation.
- Symmetrically, on the redeem path, a burn of internal asset could compute a `0` external payout, burning the user's internal stablecoin for nothing.

This violates the "Balances ... must conserve value and settle exactly once to the rightful beneficiary and amount" invariant: value enters or leaves the PSM's 1:1 reserve without a corresponding, non-zero counter-leg, because the arithmetic silently absorbs the amount into a rounding error rather than failing the operation.

### Likelihood Explanation
The likelihood depends on the precision difference between an approved external asset's decimals and the internal asset's decimals and the presence (or absence) of a minimum-deposit/minimum-redeem guard elsewhere in the pallet that I was unable to fully inspect within the available context (the `mint`/`redeem` dispatchable bodies were not retrievable before the session ended). Given the pallet is explicitly designed to support multiple, admin-approved external assets with differing decimals (e.g., 18-decimal vs 6-decimal stablecoins), and dust-value transactions are a normal occurrence, this is a plausible and unprivileged, user-triggerable condition rather than one requiring a malicious admin, governance action, or off-chain compromise.

### Recommendation
- In `external_to_internal` and `internal_to_external`, replace `unwrap_or_else(BalanceOf::<T>::zero)` in the dividing branches with an explicit check that rejects (returns an `Error<T>::AmountTooSmall`-style error) instead of silently returning `Ok(0)` when the pre-division amount is non-zero but the post-division result is zero.
- Ensure `mint`/`redeem` dispatchables independently assert that both the input amount and the converted amount are non-zero before performing any transfer/mint/burn, so that dust deposits/redemptions cannot silently pass through the pipeline with a mismatched value leg.

### Proof of Concept
Given an internal asset with 6 decimals and an approved external asset with 18 decimals (`diff = 12`, `factor = 10^12`):
1. User calls `mint` depositing `999_999_999_999` (< `10^12`) units of the external asset.
2. `external_to_internal` computes `amount.checked_div(&factor)` = `999_999_999_999 / 10^12` = `0`, and returns `Ok(0)` instead of an error.
3. If the mint flow proceeds without an additional non-zero check on the converted amount, the external asset is transferred into the PSM reserve, but `0` internal asset is minted to the user — the user's deposit is effectively lost with no corresponding internal token issued and no error raised, breaking the 1:1 conservation invariant that the exact-once, exact-amount settlement guard is supposed to enforce.

*Note: I could not retrieve the full `mint`/`redeem` dispatchable bodies (call sites of these helpers) before the session ended, so I cannot confirm with certainty whether a downstream zero-amount guard already exists in the dispatchable logic that would neutralize this specific PoC. The vulnerable arithmetic pattern itself — silent zero-rounding instead of an error — is, however, directly confirmed in the cited code.*
