### Title
Unbounded prefix-scan in `DelegatedResourceAccountIndexStore.getIndex/getV2Index` allows unauthenticated resource-exhaustion DoS via `getdelegatedresourceaccountindex(V2)` API - (File: chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java)

### Summary
The `GetDelegatedResourceAccountIndex`/`GetDelegatedResourceAccountIndexV2` HTTP/gRPC endpoints resolve an attacker-supplied address by performing an unbounded key-prefix scan of the on-disk DelegatedResourceAccountIndex column family and materializing every matching entry into memory before returning it. Because a single account can accumulate an unlimited number of `FROM_PREFIX`/`TO_PREFIX` (and V2) index entries — one per counterpart address it delegates resources to/from, at a cost of only 1 TRX frozen balance per delegation — an attacker can cheaply grow one address's delegation-index fan-out to a very large size and then repeatedly query it, forcing the node to load, sort and serialize the full set on every call. This is the same bug class as CVE-2023-6563 in Keycloak: an admin/API call that loads an unbounded collection of per-user records with no pagination limit, causing excessive CPU/memory consumption and potential crash.

### Finding Description
`DelegatedResourceAccountIndexStore.getWithPrefix` builds the full index for an address by calling `this.prefixQuery(key)` twice (once for the `FROM`/`V2_FROM` prefix, once for `TO`/`V2_TO`), with no limit on the number of returned rows: [1](#0-0) 

`prefixQuery` itself (inherited from `TronStoreWithRevoking`) delegates to `IRevokingDB.prefixQuery`, which in `Chainbase` scans the underlying LevelDB/RocksDB store for **all** keys sharing the prefix and merges them with any in-memory snapshot deltas — there is no `limit` parameter, unlike the sibling methods `getNext`/`getKeysNext`/`getValuesNext` which explicitly cap results: [2](#0-1) 

This is reachable by any unauthenticated caller via the HTTP servlet `/wallet/getdelegatedresourceaccountindex(v2)` and the equivalent gRPC calls, which pass the caller-supplied address straight through to `Wallet.getDelegatedResourceAccountIndex(V2)`: [3](#0-2) [4](#0-3) 

The number of entries under a given address's prefix is attacker-controlled: each successful `DelegateResourceContract`/`UnDelegateResourceContract` writes a new indexed entry keyed by `prefix + address + counterpartAddress`, requiring only that the sender have ≥1 TRX frozen balance available to delegate (`delegateBalance must be greater than or equal to 1 TRX`), and a distinct receiver account for each entry: [5](#0-4) [6](#0-5) 

An attacker who cheaply fans out millions of 1-TRX delegations from/to one address can then repeatedly hit the query endpoint, causing the node to allocate and sort large in-memory collections on every request, which can exhaust heap/CPU on full nodes servicing this public API.

### Impact Explanation
Repeated invocation of an unbounded, attacker-primed prefix scan on a public, unauthenticated API endpoint can drive excessive memory allocation and CPU usage on full/solidity/PBFT nodes, degrading or crashing the node process (denial of service) and impairing the node's ability to serve other API/RPC requests — consistent with the "node crash or halt / API the node can no longer serve" impact bar.

### Likelihood Explanation
The attack requires no privileges beyond broadcasting ordinary `DelegateResourceContract`/`FreezeBalanceV2` transactions (1 TRX increments) to build up a large fan-out on a chosen address, then issuing repeated GET/POST calls to a public API endpoint (`/wallet/getdelegatedresourceaccountindex`, `/wallet/getdelegatedresourceaccountindexv2`, or the gRPC equivalents) that require no authentication. This is inexpensive and fully automatable, making exploitation practical for any client able to reach the node's wallet HTTP/gRPC interface.

### Recommendation
Add pagination/limits to `DelegatedResourceAccountIndexStore.getWithPrefix`/`prefixQuery` (or cap the number of `FROM`/`TO` entries returned and stored per address), mirroring the bounded `getNext`/`getKeysNext` patterns already used elsewhere in `Chainbase`, and consider capping the number of distinct delegation counterpart entries an account may accumulate, or requiring pagination parameters on the `GetDelegatedResourceAccountIndex(V2)` API.

### Proof of Concept
1. Fund an attacker-controlled account `A` and freeze enough TRXv2 balance for bandwidth/energy.
2. From `A`, submit N (e.g., hundreds of thousands) `DelegateResourceContract` transactions, each delegating the minimum 1 TRX to a distinct freshly-created receiver address `R_i`. Each call adds one entry under `V2_FROM_PREFIX + A + R_i` in `DelegatedResourceAccountIndexStore` (`chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java:77-89`).
3. Call `GET /wallet/getdelegatedresourceaccountindexv2?value=<A>` (or the gRPC `GetDelegatedResourceAccountIndexV2`) repeatedly and concurrently. Each call triggers `Wallet.getDelegatedResourceAccountIndexV2` → `DelegatedResourceAccountIndexStore.getV2Index` → `getWithPrefix`, which performs an unbounded `prefixQuery` scanning and sorting all N entries in memory on every request.
4. Observe increased CPU/memory consumption on the node proportional to N and to concurrent request volume, demonstrating the unbounded-resource-consumption condition.

        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));

  public Map<WrappedByteArray, byte[]> prefixQuery(byte[] key) {
    Map<WrappedByteArray, byte[]> result = prefixQueryRoot(key);
    Map<WrappedByteArray, byte[]>  snapshot = prefixQuerySnapshot(key);
    result.putAll(snapshot);
    result.entrySet().removeIf(e -> e.getValue() == null);
    return result;
  }

  private Map<WrappedByteArray, byte[]> prefixQueryRoot(byte[] key) {
    Map<WrappedByteArray, byte[]> result = new HashMap<>();
    if (((SnapshotRoot) head.getRoot()).db.getClass() == LevelDB.class) {
      result = ((LevelDB) ((SnapshotRoot) head.getRoot()).db).getDb().prefixQuery(key);
    } else if (((SnapshotRoot) head.getRoot()).db.getClass() == RocksDB.class) {
      result = ((RocksDB) ((SnapshotRoot) head.getRoot()).db).getDb().prefixQuery(key);
    }
    return result;
  }

  private Map<WrappedByteArray, byte[]> prefixQuerySnapshot(byte[] key) {
    Map<WrappedByteArray, byte[]> result = new HashMap<>();
    Snapshot snapshot = head();
    if (!snapshot.equals(head.getRoot())) {
      Map<WrappedByteArray, WrappedByteArray> all = new HashMap<>();
      ((SnapshotImpl) snapshot).collect(all, key);
      all.forEach((k, v) -> result.put(k, v.getBytes()));
    }
    return result;
  }
