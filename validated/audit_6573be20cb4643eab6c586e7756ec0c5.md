### Title
Unauthenticated block POST triggers unconditional network relay via `set_relay_message`, bypassing the `broadcast=1`+auth gate - (File: `stackslib/src/net/api/postblock_v3.rs`)

### Summary
`RPCPostBlockRequestHandler::try_handle_request` calls `node.set_relay_message(...)` whenever the posted block is accepted, without checking `self.broadcast` at all. This means any remote, unauthenticated caller who POSTs a valid block to `/v3/blocks/upload/` with no `authorization` header and no `broadcast=1` query arg still causes the block to be queued for network-wide relay, even though `try_parse_request` only meant to gate *explicit* `broadcast=1` requests behind authentication.

### Finding Description
In `try_parse_request` [1](#0-0) , the handler computes `authenticated` from the `authorization` header vs. `self.auth`, and `broadcast` from the `broadcast=1` query arg, rejecting only the case `broadcast && !authenticated`. If the request omits both the header and the query arg, `self.broadcast` is set to `Some(false)` and the request proceeds unauthenticated (line 134).

In `try_handle_request`, the accepted-ness of the block is computed via `Relayer::process_new_nakamoto_block_ext(..., self.broadcast.unwrap_or(false))` [2](#0-1) . After that, the code checks only `data_resp.accepted` — not `self.broadcast` — before calling `node.set_relay_message`: [3](#0-2) 

This breaks the intended equality "relay to network == broadcast=1 AND correct auth". An unauthenticated, non-broadcast POST of a block that the node's chainstate accepts as valid will still result in `set_relay_message` being invoked with that same block, queuing it for propagation to the node's peers — a decision that was supposed to require both `broadcast=1` and the correct `authorization` header.

The existing guard (`broadcast && !authenticated` rejection at parse time) only prevents the caller from explicitly requesting broadcast without auth; it does not prevent the unconditional relay-trigger downstream in `try_handle_request`, which is a separate code path unguarded by `self.broadcast`.

### Impact Explanation
Any remote, unprivileged party who can reach the node's RPC port can force it to relay/gossip an already-valid Nakamoto block to the rest of the network without ever supplying the RPC secret, purely by omitting the `broadcast=1` argument and the `authorization` header (the exact configuration meant to require authentication to trigger propagation). This is an authentication bypass on the propagation control: the auth gate that operators rely on to control "who can trigger this node to broadcast" is void whenever the block is accepted. The action is repeatable per accepted block and is remotely triggerable with no privileged role, matching the Critical category "auth bypass" / "network-wide propagation... bypassing" the gate meant to control it.

### Likelihood Explanation
- Preconditions: node configured with `Some(password)` in `self.auth` (i.e., RPC auth enabled) and the RPC port `/v3/blocks/upload/` reachable, which is the default HTTP RPC configuration for a peer.
- Attacker cost: trivial — send one HTTP POST with a well-formed, valid `NakamotoBlock` in the body, no headers, no query string.
- The block must pass the node's normal chainstate acceptance checks (`process_new_nakamoto_block_ext`) to be `accepted` — so the attacker generally needs to submit a block that is already valid for that chain tip (e.g., replaying/re-submitting a block obtained elsewhere), but no signature/secret of the node itself is required.
- Fully repeatable for every future accepted block submission.

### Recommendation
Gate the `set_relay_message` call on `self.broadcast` in addition to `data_resp.accepted`:
```rust
if data_resp.accepted && self.broadcast.unwrap_or(false) {
    node.set_relay_message(StacksMessageType::NakamotoBlocks(NakamotoBlocksData {
        blocks: vec![block],
    }));
}
```
This restores the intended equality that relay only happens when the request was both accepted and explicitly authenticated+broadcast-requested.

### Proof of Concept
Add a test in `stackslib/src/net/api/tests/postblock_v3.rs` (or equivalent test module):
1. Construct a `StacksNodeState` with `self.auth = Some("secret".to_string())`.
2. Build a valid `NakamotoBlock` acceptable by `process_new_nakamoto_block_ext` for the test chainstate/tip.
3. Send an HTTP POST to `/v3/blocks/upload/` with no `authorization` header and no `broadcast` query parameter (so `try_parse_request` sets `self.broadcast = Some(false)`), containing the serialized block as the body.
4. Call `try_handle_request` and assert that `data_resp.accepted == true`.
5. Assert (via a mock/spy on `StacksNodeState::set_relay_message`, or by inspecting the network's relay-message queue after the call) that `set_relay_message` was invoked with `StacksMessageType::NakamotoBlocks` containing the same block — contradicting the intended requirement that relay requires `broadcast=1` AND correct auth.
