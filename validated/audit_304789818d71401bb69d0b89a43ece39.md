### Title
Precompiled contract array extraction allocates memory based on unvalidated attacker-controlled length field - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`PrecompiledContracts.extractBytesArray`, `extractBytes32Array`, and `extractSigArray` read a length value directly from TVM call-data words and immediately allocate a Java array of that size (`new byte[len][]`) without validating `len` against a sane bound or the actual remaining call-data size before allocating. This mirrors the CVE-2023-5371 bug class ("memory allocation with excessive size value" derived from an untrusted length field), where a length taken from unvalidated input is used to size a memory allocation, enabling resource-exhaustion.

### Finding Description
`extractBytesArray` and `extractBytes32Array` take the array length straight out of caller-supplied `DataWord[] words` via `intValueSafe()` and use it to allocate a two-dimensional byte array before any bound/energy check against that length is performed: [1](#0-0) 

`extractSigArray` follows the same pattern: [2](#0-1) 

The only guard present is `offset > words.length - 1`, which validates that the *offset* pointer is in range, not that `len` (the declared array length) is reasonable or consistent with the actual amount of call data supplied. Because `len` comes from `words[offset].intValueSafe()`, an attacker who calls the precompiled contract that consumes these helpers can craft a single 32-byte word encoding a very large integer (up to `Integer.MAX_VALUE`), causing `new byte[len][]` to attempt to allocate an array of that many object references immediately — independent of how much actual call-data bytes were supplied.

This differs from the CALLDATACOPY/CODECOPY/EXTCODECOPY paths in `OperationActions.java`/`EnergyCost.java`, where memory-expansion energy metering (`calcMemEnergy` → `checkMemorySize` against a 3MB `MEM_LIMIT`) is computed and bounds-checked *before* the corresponding action executes: [3](#0-2) 

The `extractBytesArray`/`extractBytes32Array`/`extractSigArray` helpers have no equivalent pre-allocation size gate.

### Impact Explanation
If the length field is not bounded before the array allocation, a contract call/precompile invocation reachable from a normal signed transaction (TriggerSmartContract call into a precompiled contract address that uses these decoders) can force the node to attempt an outsized allocation, risking `OutOfMemoryError` and node crash/instability — a denial-of-service condition analogous to the Wireshark RTPS dissector bug that allowed a crafted packet to trigger excessive memory allocation.

### Likelihood Explanation
Reachability requires that some precompiled contract actually invokes `extractBytesArray`/`extractBytes32Array`/`extractSigArray` on attacker-supplied call data. I was able to confirm the vulnerable helper implementations and their unguarded length-based allocation with exact line numbers, but I was **not able to confirm, within available tool budget, the specific precompile class/address that calls these helpers**, nor whether that precompile's `getEnergyForData` computes/limits `len` before `execute()` invokes these helpers. This significantly affects confidence in exploitability and should be verified before treating this as conclusively exploitable.

### Recommendation
Before allocating `new byte[len][]` (or similar) in `extractBytesArray`, `extractBytes32Array`, and `extractSigArray`, validate `len` against the actual bounds of `words`/`data` (e.g., `len` must not exceed `(words.length - offset - 1)`), and reject with a normal execution failure if the declared length is inconsistent with the supplied call-data size, mirroring the `verifyLength` bounds check already used in `RLP.java`.

### Proof of Concept
Not fully constructible without confirming the specific precompiled-contract entry point that calls these helpers; this requires locating the precompile class(es) that pass attacker call data through `extractBytesArray`/`extractBytes32Array`/`extractSigArray` and confirming their energy-cost function does not pre-validate `len`. A Devin session with full repository access could grep for internal callers (they may reside in code not indexed/returned in this session) to build a concrete calldata PoC.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }

  private static long calcMemEnergy(long oldMemSize, BigInteger newMemSize,
                             long copySize, int op) {
    long energyCost = 0;

    checkMemorySize(op, newMemSize);

    // memory SUN consume calc
    long memoryUsage = (newMemSize.longValueExact() + 31) / 32 * 32;
    if (memoryUsage > oldMemSize) {
      long memWords = (memoryUsage / 32);
      long memWordsOld = (oldMemSize / 32);
      long memEnergy = (MEMORY * memWords + memWords * memWords / 512)
          - (MEMORY * memWordsOld + memWordsOld * memWordsOld / 512);
      energyCost += memEnergy;
    }

    if (copySize > 0) {
      long copyEnergy = COPY_ENERGY * ((copySize + 31) / 32);
      energyCost += copyEnergy;
    }
    return energyCost;
  }

  private static void checkMemorySize(int op, BigInteger newMemSize) {
    if (newMemSize.compareTo(MEM_LIMIT) > 0) {
      throw Program.Exception.memoryOverflow(op);
    }
  }
