Audit Report

## Title
Silent fund loss when ERC20 asset deposit fails during `transfer_asset` fallback — the `Erc20Credit` imbalance is dropped without any compensating on-chain balance action - (File: `polkadot/xcm/xcm-executor/src/traits/transact_asset.rs`, `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

## Summary
`ERC20Transactor` only overrides the `*_with_surplus` variants of `TransactAsset` (`withdraw_asset_with_surplus`, `deposit_asset_with_surplus`), leaving the plain `deposit_asset`/`withdraw_asset`/`internal_transfer_asset` methods on the default trait implementation, which unconditionally return `Err(XcmError::Unimplemented)`. [1](#0-0) [2](#0-1) [3](#0-2)  Both the plain `transfer_asset` fallback and the `transfer_asset_with_surplus` fallback contain a best-effort refund step whose result is discarded (`let _ = Self::deposit_asset(unspent, from, Some(context));`), and critically, the refund call in *both* paths always uses the plain `deposit_asset` (not `deposit_asset_with_surplus`), which for `ERC20Transactor` is unimplemented and returns `Err(Unimplemented)` immediately — meaning the "best effort" refund is a guaranteed no-op for this transactor, not merely a possible failure. [4](#0-3) 

## Finding Description
For the plain `transfer_asset` fallback path described in the claim, `withdraw_asset` (plain) is what gets called, and since `ERC20Transactor` does not override it, it immediately returns `Err(XcmError::Unimplemented)` via the default trait implementation before any real ERC20 transfer occurs. [5](#0-4)  This means the exact PoC scenario described in the claim (real withdraw succeeds via the plain `withdraw_asset`/`deposit_asset` pair, then deposit and refund both fail, dropping the credit) cannot occur through the plain `transfer_asset` path for `ERC20Transactor`, because no real on-chain transfer happens in that path at all — it fails at the withdraw step with `Unimplemented`, and no ERC20 balance ever moves.

The real production path for `ERC20Transactor` is `transfer_asset_with_surplus`, which does call `withdraw_asset_with_surplus` (a real, irreversible ERC20 transfer into `TransfersCheckingAccount`) followed by `deposit_asset_with_surplus`. [6](#0-5) [7](#0-6)  If the primary deposit to `to` fails (e.g., a blacklist-style or always-`false` ERC20), the fallback attempts a refund to `from`, but this refund call uses plain `deposit_asset` — which for `ERC20Transactor` is unimplemented and returns `Err(Unimplemented)` unconditionally, regardless of whether `from` is blacklisted or not. [8](#0-7)  The result of this refund attempt is discarded via `let _ = ...`, so the `Erc20Credit` unspent value carries no runtime-level balance enforcement per its own doc comment, and it is simply dropped. [9](#0-8)  The real ERC20 tokens, however, have already been irreversibly transferred into the shared `TransfersCheckingAccount` by `withdraw_asset_with_surplus`. [10](#0-9) 

This is a genuine bug (the "best effort" refund is not merely occasionally ineffective but is architecturally guaranteed to fail for `ERC20Transactor`, since the refund helper in `transact_asset.rs` was never updated to call the `_with_surplus` variant), and it does result in silently discarded value accounting whenever a deposit fails after a successful withdraw in this code path.

## Impact Explanation
This matches the "permanent user-fund lock" category in the impact gate: an unprivileged user submitting an ordinary XCM program via `pallet_xcm::execute` that triggers `TransactAsset::transfer_asset_with_surplus` against a non-standard ERC20 token (blacklist-style or always-`false`-returning) can cause a real, irreversible ERC20 transfer into `TransfersCheckingAccount`, followed by a guaranteed-to-fail refund attempt whose failure is silently swallowed, permanently stranding the tokens with no on-chain record of which account is owed what.

## Likelihood Explanation
No privileged actor is required; any user can register or interact with an already-registered non-conforming ERC20 asset location matched by `ERC20Matcher`/`Matcher` and submit a `pallet_xcm::execute` call that triggers the transfer fallback path. The repository's own test suite (`smart_contract_does_not_return_bool_fails`, referenced in the report) demonstrates that deposit failures for non-standard ERC20 tokens are a realistic, already-anticipated failure mode for this transactor, and the refund-path bug (using plain `deposit_asset` instead of `deposit_asset_with_surplus`) makes the "best effort" refund unconditionally a no-op for `ERC20Transactor`, regardless of whether the specific recipient is blacklisted.

## Recommendation
- In `polkadot/xcm/xcm-executor/src/traits/transact_asset.rs`, change the refund call inside `transfer_asset_with_surplus`'s error handler from `Self::deposit_asset(unspent, from, Some(context))` to `Self::deposit_asset_with_surplus(unspent, from, Some(context))` so refunds are attempted through the same code path that the transactor actually implements.
- Do not silently discard the result of the refund attempt; surface a distinct error/event when both the primary deposit and the refund fail, so the stuck value is auditable.
- For `ERC20Transactor`, maintain an on-chain ledger (storage map) of amounts held in `TransfersCheckingAccount` per user/asset so failed deposits can be reconciled via a dedicated recovery extrinsic instead of relying purely on best-effort refunds and an unenforced `Erc20Credit` imbalance.

## Proof of Concept
1. Deploy an ERC20 contract whose `transfer` returns `false` for a specific blacklisted recipient but succeeds otherwise.
2. Register it as an XCM-transactable asset matched by `Matcher` on Asset Hub, so `ERC20Transactor` handles it.
3. As an ordinary user, submit via `pallet_xcm::execute` an XCM program that hits `TransactAsset::transfer_asset_with_surplus` (e.g., via `InitiateTransfer`) moving this ERC20 from `from` to a blacklisted `to`.
4. `withdraw_asset_with_surplus` succeeds, moving real tokens into `TransfersCheckingAccount`. [11](#0-10) 
5. `deposit_asset_with_surplus` to `to` fails (token returns `false`). [12](#0-11) 
6. The fallback attempts `Self::deposit_asset(unspent, from, ...)` — since `ERC20Transactor` doesn't implement plain `deposit_asset`, this immediately returns `Err(Unimplemented)` regardless of `from`'s blacklist status, and the result is discarded. [13](#0-12) 
7. Verify (via an integration test extending `smart_contract_does_not_return_bool_fails` in `cumulus/parachains/runtimes/assets/asset-hub-westend/tests/tests.rs`) that the real ERC20 balance remains in `TransfersCheckingAccount` after the XCM program returns an error, with no compensating state change.

/// A minimal imbalance tracking type that holds an ERC20 token amount.
///
/// This type implements the necessary imbalance accounting traits but does not perform
/// runtime-level balance enforcement. It's used to track ERC20 token amounts within XCM
/// asset holdings, where the actual balance constraints are enforced by the ERC20 smart
/// contract itself rather than the runtime.
struct Erc20Credit(u128);
impl UnsafeConstructorDestructor<u128> for Erc20Credit {
	fn unsafe_clone(&self) -> Box<dyn ImbalanceAccounting<u128>> {
		Box::new(Erc20Credit(self.0))
	}
	fn forget_imbalance(&mut self) -> u128 {
		let amount = self.0;
		self.0 = 0;
		amount
	}
}

	fn transfer_asset(
		asset: &Asset,
		from: &Location,
		to: &Location,
		context: &XcmContext,
	) -> Result<Asset, XcmError> {
		match Self::internal_transfer_asset(asset, from, to, context) {
			Err(XcmError::AssetNotFound | XcmError::Unimplemented) => {
				let credit = Self::withdraw_asset(asset, from, Some(context))?;
				Self::deposit_asset(credit, to, Some(context)).map_err(|(unspent, error)| {
					// best effort try to return the assets to original owner
					let _ = Self::deposit_asset(unspent, from, Some(context));
					error
				})?;
				Ok(asset.clone())
			},
			result => result,
		}
	}

	/// Identical to `transfer_asset` but returning the surplus, if any.
	///
	/// The surplus is the difference between the worst-case weight and the actual
	/// consumed weight.
	/// This can be zero usually if there's no metering involved.
	fn transfer_asset_with_surplus(
		asset: &Asset,
		from: &Location,
		to: &Location,
		context: &XcmContext,
	) -> Result<(Asset, Weight), XcmError> {
		match Self::internal_transfer_asset_with_surplus(asset, from, to, context) {
			Err(XcmError::AssetNotFound | XcmError::Unimplemented) => {
				let (credit, withdraw_surplus) =
					Self::withdraw_asset_with_surplus(asset, from, Some(context))?;
				let deposit_surplus = Self::deposit_asset_with_surplus(credit, to, Some(context))
					.map_err(|(unspent, error)| {
					// best effort try to return the assets to original owner
					let _ = Self::deposit_asset(unspent, from, Some(context));
					error
				})?;
				let total_surplus = withdraw_surplus.saturating_add(deposit_surplus);
				Ok((asset.clone(), total_surplus))
			},
			result => result,
		}
	}
