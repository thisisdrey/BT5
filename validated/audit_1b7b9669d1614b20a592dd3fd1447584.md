Confirmed: `get_u2le`/`get_u8le` in `third_party/ijar/common.h` perform raw pointer dereferences with no bounds checking whatsoever, and `ProcessCentralDirEntry` in `third_party/ijar/zip.cc` parses the extra-field sub-records without any `EnsureRemaining`-style validation (unlike `ProcessLocalFileEntry`, which does call `EnsureRemaining` before reading `file_name`/`extra_field`).

### Title
Heap buffer over-read parsing ZIP64 extra-field records in `ijar`'s central directory parser - (File: third_party/ijar/zip.cc)

### Summary
### Finding Description
`InputZipFile::ProcessCentralDirEntry` (used by `ProcessNext` and `CalculateOutputLength` when Bazel's `ijar` tool builds interface JARs from arbitrary input JARs) walks the per-entry "extra field" data with an unchecked loop: [1](#0-0) 
`header_id` and `data_size` are read via `get_u2le`, and if `header_id == ZIP64_EXTRA_FIELD_TAG` the code immediately calls `get_u8le(extra)` up to three times on the `extra` pointer, without ever verifying that the record actually contains 8 (or 24) bytes of payload, and without verifying that `extra_field_length` bytes are actually present in the mapped input file before entering the loop. `get_u2le`/`get_u8le` themselves do no bounds checking at all: [2](#0-1) 
This is in stark contrast to `ProcessLocalFileEntry`, which explicitly calls `EnsureRemaining()` before touching `file_name`/`extra_field` bytes: [3](#0-2) 
No such `EnsureRemaining` check exists on the path into `ProcessCentralDirEntry`'s extra-field loop, so a crafted central-directory record with `header_id == 0x0001` but a truncated or zero-length payload (or an `extra_field_length` that overruns the actual mapped file) causes `get_u8le` to read up to 8 bytes past the legitimate extra-field bytes — an out-of-bounds heap (mmap) read, directly analogous to the p11-kit RPC byte-array over-read in the CVE (an over-read triggered by trusting a length/tag pair from untrusted, remote-supplied data without validating that the declared payload actually fits in the buffer).

### Impact Explanation
Bazel invokes `ijar` on JAR files that can originate from external, attacker-influenced sources (e.g., a JAR fetched via `http_jar`/`http_file`/a remote Maven artifact processed into an interface jar during the build). A malicious JAR with a crafted central directory extra field triggers an out-of-bounds read within the `ijar` process (used both standalone and linked into `singlejar`/interface-jar generation), which can crash the build worker (`SIGSEGV`) or leak adjacent heap/mmap bytes into computed values (e.g., `uncompressed_size`/`compressed_size`/`offset`) that influence subsequent memory accesses (`p = zipdata_in_ + in_offset_ + offset` in `ProcessNext`), potentially compounding into further out-of-bounds reads/writes deeper in file processing.

### Likelihood Explanation
Moderate-to-high: no checksum, signature, or bounds validation stands between attacker-controlled ZIP metadata and the raw pointer arithmetic in `get_u8le`; the only requirement is a syntactically valid central directory entry with a `ZIP64_EXTRA_FIELD_TAG` extra field whose declared/actual size is smaller than 8/24 bytes, which is trivial to construct with any hex editor or zip-crafting library.

### Recommendation
Add explicit bounds checks (mirroring `EnsureRemaining`) before dereferencing extra-field records in `ProcessCentralDirEntry`'s extra-field loop: verify `data_size >= 8` (or `>= 24` for offset+sizes) and that `extra + data_size` does not exceed the mapped file's end and does not exceed `p` (the extra-field region boundary) before calling `get_u8le`.

### Proof of Concept
Construct a minimal ZIP/JAR whose single central directory entry has `extra_field_length = 4` and an extra field consisting only of the 4-byte ZIP64 tag/size header (`01 00 00 00`, i.e. tag `0x0001`, declared length `0`) with `uncompressed_size`/`compressed_size` fields in the CDH set to `0xFFFFFFFF` (forcing the `U4_MAX` branch to read the zip64 fields). Feed this file to Bazel's `ijar` binary (`bazel-bin/third_party/ijar/ijar input.jar output.jar`); `ProcessCentralDirEntry` will call `get_u8le(extra)` reading 8 bytes starting right after the 4-byte header, running past the 4-byte extra field into adjacent mapped memory — verifiable with ASan (`-fsanitize=address`), which will report a heap-buffer-overflow/over-read in `get_u8le`/`ProcessCentralDirEntry`. A JUnit/shell-integration equivalent would build such a JAR at test-setup time and assert that `ijar`/interface-jar generation either fails cleanly or does not crash/leak under ASan, rather than the current silent over-read.

inline u2 get_u2le(const u1 *&p) {
    u4 x = (p[1] << 8) | p[0];
    p += 2;
    return x;
}

inline u4 get_u4be(const u1 *&p) {
    u4 x = (p[0] << 24) | (p[1] << 16) | (p[2] << 8) | p[3];
    p += 4;
    return x;
}

inline u4 get_u4le(const u1 *&p) {
    u4 x = (p[3] << 24) | (p[2] << 16) | (p[1] << 8) | p[0];
    p += 4;
    return x;
}

inline u8 get_u8le(const u1 *&p) {
  u4 lo = get_u4le(p);
  u4 hi = get_u4le(p);
  u8 x = ((u8)hi << 32) | lo;
  return x;
}
