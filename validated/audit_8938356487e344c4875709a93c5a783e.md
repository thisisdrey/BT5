### Title
Exposure of internal exception class information to anonymous API clients via TriggerSmartContract/TriggerConstantContract/EstimateEnergy HTTP endpoints - (File: framework/src/main/java/org/tron/core/services/http/TriggerSmartContractServlet.java)

### Summary
The `/wallet/triggersmartcontract`, `/wallet/triggerconstantcontract`, and `/wallet/estimateenergy` HTTP endpoints catch generic `Exception`s and embed the raw Java exception class name (`e.getClass()`) together with the raw exception message into the JSON `message` field returned to any anonymous, unauthenticated caller. This mirrors CVE-2021-20289 (RESTEasy), where internal class/method names were leaked in exception responses to unprivileged clients, aiding information disclosure and reconnaissance.

### Finding Description
In `TriggerSmartContractServlet.doPost`, any exception that is not a `ContractValidateException` (e.g. `NullPointerException`, protobuf parsing errors, internal reflection/JSON errors, VM/runtime exceptions surfaced during transaction capsule construction) is caught by the generic `catch (Exception e)` block and turned into a response message that explicitly concatenates the fully-qualified exception class name with the exception's message: [1](#0-0) 

The identical pattern exists in `TriggerConstantContractServlet.doPost`: [2](#0-1) 

And in `EstimateEnergyServlet.doPost`: [3](#0-2) 

All three servlets are reachable by any anonymous HTTP client without authentication — they only require a syntactically valid `TriggerSmartContract` JSON body, and are on the standard Wallet HTTP API surface. Whenever internal processing throws anything other than the expected `ContractValidateException` (malformed hex data, oversized/odd parameter encodings, internal null dereferences during `wallet.createTransactionCapsule`/`wallet.triggerContract`/`wallet.triggerConstantContract`/`wallet.estimateEnergy`, JSON parsing edge cases, etc.), the response leaks the fully-qualified internal class name of the exception (e.g. `java.lang.NullPointerException`, `org.tron.core.exception.StoreException`, `com.google.protobuf.InvalidProtocolBufferException`, or internal package-private exception types used by the TVM actuator/VM chain), which discloses internal implementation structure, package layout, and library usage to an unauthenticated remote caller.

### Impact Explanation
This is a direct analog of GHSA-244r-fcj3-ghjq: exception responses expose internal class information to an unprivileged remote caller, aiding reconnaissance for further attacks (e.g., fingerprinting library versions/internal architecture to craft targeted exploits against the TVM/actuator layer) and violating confidentiality of the server's internal design (CWE-209, CWE-668). It does not by itself cause fund loss or crash, matching the "Medium" severity classification of the original advisory.

### Likelihood Explanation
Any anonymous transaction broadcaster or contract caller can trivially trigger a non-`ContractValidateException` (e.g., by supplying malformed `function_selector`/`function_parameter` hex, or edge-case data causing an internal `NullPointerException` deep in transaction/capsule construction), making this reliably and repeatedly reachable over the standard public HTTP wallet API.

### Recommendation
Do not include `e.getClass()` (or any fully-qualified class name) in externally visible response messages. Return a generic, sanitized error message for unexpected internal exceptions (e.g., `"Internal error"` or a fixed error code), while still logging the full exception with class name and stack trace server-side via `logger.debug/error` for diagnostics, consistent with how `Util.processError`/`Util.printErrorMsg` already avoid exposing raw class names in other servlets.

### Proof of Concept
1. Send a POST request to `/wallet/triggersmartcontract` (or `/wallet/triggerconstantcontract`, `/wallet/estimateenergy`) with a body containing a valid `owner_address`/`contract_address` but a crafted `function_selector`/`function_parameter` or malformed `data` field designed to trigger an internal exception other than `ContractValidateException` during transaction capsule construction.
2. Observe that the HTTP JSON response's `message` field (base64/utf8-decoded) contains a string of the form `"class org.tron.core.exception.XyzException : <message>"` or `"class java.lang.NullPointerException : null"`, confirming that the internal exception class name is exposed to the anonymous caller, as constructed at: [4](#0-3)
