### Title
Replay-window Check/Update TOCTOU in `ConnectionState.Decrypt` allows a duplicate encrypted packet to bypass replay protection - (File: connection_state.go)

### Summary
`ConnectionState.Decrypt` performs the replay-window "check" and the replay-window "update" as two separate, independently-locked operations with the (potentially slow) AEAD decryption happening in between while the lock is released. This is the same class of bug as the GoodEntry finding: a decision is made on state that is read once, external/concurrent work happens, and the state is only durably updated afterwards — allowing two concurrent operations that both pass the initial check to both complete before either one's effect is recorded, resulting in double-acceptance of what should be a single-use value (a replay).

### Finding Description
`ConnectionState.Decrypt` in [1](#0-0)  is implemented as:

```go
func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}
```

The replay window state is only mutated by `Update` (which marks the bit and moves `current`). Between the `Check` call and the `Update` call for a given `messageCounter`, the lock is released, and the (comparatively expensive) `DecryptDanger` AEAD operation runs unlocked. If a second packet carrying the identical `messageCounter` arrives and is processed on another goroutine during this window (nebula processes inbound UDP on multiple reader "routines"/queues per `Interface`, as configured by `routines` in [2](#0-1) , with each queue calling `readOutsidePackets` -> `ConnectionState.Decrypt` in [3](#0-2) ), both goroutines can independently execute `cs.window.Check(l, messageCounter)` and see `true` (not-yet-seen) before either has called `Update`. Both then proceed to decrypt and accept the packet, and the second `Update` call at the end will simply find the bit already set and return `false` — but by that point the payload has already been delivered (`out` returned to the caller and written to `f.readers[q]`/processed) once for each concurrent goroutine that passed the check, i.e. the replay was accepted at least once beyond what a single "check-then-commit" semantics should allow. The `Bits.Check`/`Bits.Update` primitives themselves are internally lock-protected (see comments referencing "Lock replay window updates so concurrent readers can't corrupt it" in the CHANGELOG [4](#0-3) ) but that fix only protects the bit array from corruption; it does not close the check→decrypt→update TOCTOU window at the `Decrypt` call level, exactly mirroring the GoodEntry bug where the fee/liquidity check was performed on stale data and the state used to finalize the operation could diverge before commit.

### Impact Explanation
A successful exploitation weakens Nebula's per-tunnel replay protection: an attacker who can duplicate/race a single already-authenticated data packet (e.g., by re-injecting a captured ciphertext concurrently, or by naturally-duplicated UDP delivery) can cause the same authenticated payload to be delivered to the TUN device / firewall pipeline more than once. This is a directly reachable protocol-level weakening of anti-replay guarantees on the data plane, distinct from and not requiring a valid CA-signed certificate — it operates against already-established tunnels using packets an attacker can observe or duplicate. It is a lower-severity issue than certificate/handshake bypass because it does not forge new content (the AEAD tag must already be valid) — it only allows a bounded double-delivery race, not unlimited replay.

### Likelihood Explanation
Likelihood is limited by the amount of time the AEAD decrypt takes relative to the network's/attacker's ability to deliver a duplicate packet on a different UDP reader routine within that narrow window, and by the fact only already-authenticated ciphertext can be re-used (no forgery). Nebula does run multiple reader routines when `listen.routines`/`routines` > 1 [2](#0-1) , which is the concrete condition needed for two goroutines to race on the same `ConnectionState`. This is a genuine but narrow race window (microseconds), making exploitation plausible but not trivially deterministic.

### Recommendation
Perform the replay check-and-mark as a single atomic critical section instead of two separate lock/unlock pairs around `Check` and `Update`. E.g., hold `cs.decryptLock` for the duration of `Check` + `DecryptDanger` + `Update`, or restructure so that `Update` is attempted first (reserving the counter) and rolled back only on decrypt failure, so no second caller can observe the counter as "not yet seen" while a first caller's decrypt is still in flight.

### Proof of Concept
1. Establish a tunnel between two nebula nodes with `listen.routines` > 1 so inbound UDP packets are processed by multiple goroutines concurrently against the same `HostInfo`/`ConnectionState`.
2. Capture one legitimate encrypted data packet (as done in the existing `TestRelayReplayProtection` test pattern in [5](#0-4) , but for the direct (non-relay) `ConnectionState.Decrypt` path instead of `VerifyRelay`).
3. Inject two copies of the exact same captured packet at (near-)simultaneous times so they land on two different reader routines before either has completed `Decrypt`.
4. Observe that `cs.window.Check` can return `true` for both copies (since `Update` for the first hasn't run yet), causing `DecryptDanger` to run and succeed twice, and the payload to be delivered to the TUN device / firewall path more than once for what should be a single accepted message.
