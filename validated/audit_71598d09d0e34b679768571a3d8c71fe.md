### Title
Repeated tiny-block `accrue()` triggers cause `reserve-inc` to floor to zero, permanently denying DAO treasury fee on real (but sub-unit-per-call) debt growth - ([File: mainnet/contracts/vault/v0-vault-stx.clar])

### Summary
`accrue()` computes `reserve-inc` as `mul-div-down(debt-delta, fee-reserve, BPS)`, a floor division that truncates to zero whenever `debt-delta * fee-reserve < BPS` for a single call's window. An unprivileged user holding a tiny outstanding borrow can repeatedly trigger `accrue()` (via `deposit`/`redeem` of `1` unit, or any other state-mutating call) on every new block, resetting the `index` baseline each time so that the per-call `debt-delta` never accumulates enough to make `reserve-inc` non-zero, while the debt itself is still real and growing over time.

### Finding Description
`accrue()` in `mainnet/contracts/vault/v0-vault-stx.clar` (and identically in the other five vault contracts) computes: [1](#0-0) 

```
(old-debt (mul-div-down scaled-principal idx INDEX-PRECISION))
(new-debt (mul-div-down scaled-principal next INDEX-PRECISION))
(debt-delta (if (> new-debt old-debt) (- new-debt old-debt) u0))
(reserve-inc (mul-div-down debt-delta (var-get fee-reserve) BPS))
```
and then mints `treasury-lp` to `.dao-treasury` only if `reserve-inc > 0`: [2](#0-1) 

Critically, whether or not `reserve-inc` (and thus `treasury-lp`) is non-zero, `index` is always updated to `next` when `idx != next`: [3](#0-2) 

This means every call to `accrue()` resets the baseline (`old-debt`) used for the *next* call's `debt-delta` computation. Any unprivileged caller can force `accrue()` to run on every single block by calling any public function that internally calls `(try! (accrue))` (e.g. `deposit`, `redeem`, `system-borrow`, `system-repay` — all confirmed to call `accrue` first, e.g. `system-borrow` at line 870 `(u (try! (accrue)))`). By keeping an existing borrow position with very small `principal-scaled` and/or low per-block interest accrual, and calling `deposit(1)`/`redeem(1)` (or similar minimal-amount calls) once per block, the attacker forces `debt-delta` to be recomputed from a freshly-reset baseline every block, so it stays below the threshold needed for `mul-div-down(debt-delta, fee-reserve, BPS)` to round up to at least `1`. Because there's no accumulator/remainder tracked across calls for the reserve fee (only the index/debt baseline is tracked), any fractional fee that would have been owed for that block is discarded permanently — it isn't carried forward to the next accrual window.

No existing check (`check-caller-auth`, pause states, slippage, health checks) restricts calling frequency of `accrue()`-triggering functions, and there is no minimum interval enforced between accruals other than blocks having a new `stacks-block-time`.

### Impact Explanation
This causes a permanent loss of unclaimed DAO treasury yield: the `fee-reserve` share of interest accrued on real (nonzero) debt growth is discarded to zero on every affected block, and it is never recovered on a later call because the index baseline has already been advanced. This matches the in-scope **High** category: "permanent freezing/theft of unclaimed yield," since the treasury never receives its due `treasury-lp` mint for that debt growth even though the borrower's `index`/debt compounding proceeds normally.

### Likelihood Explanation
Preconditions are narrow but attacker-achievable without privilege: an existing (or attacker-opened) borrow position with very small `principal-scaled`/interest accrual per block, plus repeated low-cost calls (`deposit(1)`/`redeem(1)`) once per block. Capital cost to the attacker is minimal (transaction fees plus a small collateral/borrow amount); the attack is fully repeatable across arbitrary numbers of blocks. The magnitude of loss per block is bounded by less than one reserve-fee unit, so the practical value drained scales with the number of blocks the attacker sustains this pattern and is capped by how small `fee-reserve`/`BPS`-scaled per-block interest can be kept — meaningful cumulative loss requires sustained low-value borrowing over many blocks, which is plausible but yields a comparatively small absolute value relative to protocol-wide fee income.

### Recommendation
Track a running remainder (dust) for `reserve-inc` truncation across calls (accumulate the un-minted fractional portion and add it into the next accrual's `debt-delta`/`reserve-inc` computation) rather than resetting the baseline unconditionally, or accrue reserve fee using higher internal precision than the raw debt units so floor-rounding to zero only occurs at negligible absolute values regardless of call frequency.

### Proof of Concept
Clarinet/vitest simnet plan:
1. Deploy `v0-vault-stx` with a nonzero `fee-reserve` and a nonzero small interest rate (`points-ir`).
2. Have an attacker account open a small borrow (`system-borrow`) sized so that expected per-block interest accrual in base units is on the order of 0-1.
3. Loop N blocks; each block, call `deposit(u1)` then `redeem(u1)` (or any accrue-triggering call) from the attacker account to force `accrue()` every block.
4. Track `.dao-treasury` zft balance before/after the loop; separately compute the theoretically owed treasury share as `mul-div-down(total-debt-growth-over-N-blocks, fee-reserve, BPS)` using the cumulative debt growth (not per-block).
5. Assert `dao-treasury-balance-increase < theoretical-owed-share`, demonstrating the systematic under-mint caused by per-call floor rounding versus the mathematically owed cumulative share.

Note: I was not able to fully inspect `next-index`/`next-liquidity-index` and `mul-div-down` implementations within the available tool budget to confirm the exact fixed-point precision used for the interest-rate index itself; this does not change the confirmed root cause (per-call floor division on `reserve-inc` with no dust carry-forward) but should be verified in a full Clarinet run to precisely quantify per-block loss magnitude.
