### Title
Unbounded growth of `DelegatedResourceAccountIndex` via repeated resource delegation to distinct new receivers - ([File: chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java])

### Summary
When the legacy (non-optimized) resource delegation path is active, an ordinary account can grow a single stored protobuf record (`DelegatedResourceAccountIndex`) without bound by repeatedly delegating small amounts of frozen bandwidth/energy to a large number of distinct, self-controlled receiver addresses. Each new receiver appends an entry to the owner's `toAccounts` list (and the receiver's `fromAccounts` list), with no maximum size or count check, unlike other repeated-entry fields in the protocol (e.g. votes are capped by `MAX_VOTE_NUMBER`, asset `frozen_supply` by `MAX_FROZEN_SUPPLY_NUMBER`, and unfreeze v2 entries by a max unfreeze count). This mirrors the KubeVirt bug class: an unprivileged actor causes unbounded accumulation of list entries in a stored record that the system must read/rewrite on every subsequent update, degrading the ability to service further operations on that record.

### Finding Description
`FreezeBalanceActuator.delegateResource()` handles resource delegation for the (still-reachable, pre-`AllowDelegateOptimization`) code path: [1](#0-0) 

For each new receiver address, it fetches or creates a `DelegatedResourceAccountIndexCapsule` for the owner, checks only whether the receiver is *already present* in the `toAccountsList`, and if not, calls `addToAccount`, which unconditionally appends to the underlying protobuf list with no upper bound: [2](#0-1) 

The same unbounded pattern applies symmetrically to the receiver's `fromAccounts` list. There is no `MAX_DELEGATE_COUNT`-style validation in `FreezeBalanceActuator.validate()` (the only bounded field validated there is the plain `frozen` list, which is explicitly capped to 0 or 1 entries): [3](#0-2) 

Because the owner only needs to freeze the protocol minimum of 1 TRX per delegation (`frozenBalance >= TRX_PRECISION`) and can generate arbitrarily many receiver addresses (which need not even be pre-funded beyond existing on-chain, since `receiverCapsule` need only exist), a single account can drive the `toAccountsList`/`fromAccountsList` on its `DelegatedResourceAccountIndex` record to an arbitrarily large size across many transactions. Every subsequent delegate/unfreeze/read operation on that account must fetch, deserialize, scan (`contains()` is O(n)), mutate, and re-serialize/write back the entire growing list: [4](#0-3) 

Other repeated-entry fields in the same `Account`/related messages are explicitly bounded (votes ≤ `MAX_VOTE_NUMBER=30`, asset `frozen_supply` ≤ `MAX_FROZEN_SUPPLY_NUMBER`), showing the codebase's established pattern of capping such lists — a pattern absent here: [5](#0-4) [6](#0-5) 

### Impact Explanation
Unbounded growth of a single stored record increases per-transaction cost (linear scan and O(n) re-serialization) for every future delegate/unfreeze operation touching that account, and inflates leveldb/rocksdb value sizes. This can degrade node performance for processing transactions/blocks touching the affected account and for any RPC/HTTP query that retrieves the index (e.g., wallet delegated-resource-account-index queries), matching the "excessive report causing inability to store further updates" pattern from the referenced advisory. This is resource-exhaustion/DoS-class impact against a specific account's future updates and against nodes serving queries for that account, rather than a fund-theft or consensus-halting bug.

### Likelihood Explanation
Reachability depends on `DynamicPropertiesStore.supportAllowDelegateOptimization()` being false for the delegation call to take the legacy list-append path (`FreezeBalanceActuator` branch at lines 319-345); if the corresponding committee proposal has already been permanently activated on the target network, this specific legacy code path is not currently exercised in production even though the code remains in the actuator and is exercised by unit tests. I was not able to fully confirm from the available index whether `AllowDelegateOptimization` is enabled by default on mainnet/this codebase version (the `DynamicPropertiesStore.java` grep for its initialization did not resolve within available context), so likelihood is **uncertain** and should be verified against the live proposal/committee state before treating this as an actively exploitable path.

### Recommendation
Add an explicit maximum-size check (analogous to `MAX_VOTE_NUMBER` / `MAX_FROZEN_SUPPLY_NUMBER`) on `DelegatedResourceAccountIndexCapsule.toAccountsList`/`fromAccountsList` sizes in `FreezeBalanceActuator.validate()` before allowing a new delegation to append a distinct receiver, and reject transactions once the account's index list exceeds the configured cap.

### Proof of Concept
Not runnable from the indexed context alone; conceptually: 1) ensure `AllowDelegateOptimization` is inactive; 2) from a funded owner account, repeatedly submit `FreezeBalanceContract` transactions with `frozenBalance = TRX_PRECISION` (1 TRX) and a freshly generated, distinct `receiverAddress` for each transaction (as in `FreezeBalanceActuatorTest.testMultiFreezeDelegatedBalanceForBandwidth`, which demonstrates the append behavior with 100+ receivers); 3) repeat at scale (tens of thousands of distinct receivers) to grow the owner's `DelegatedResourceAccountIndex` record without any actuator-enforced cap, as shown by the absence of any count/size validation in `FreezeBalanceActuator.validate()`.   private long delegateResource(byte[] ownerAddress, byte[] receiverAddress, boolean isBandwidth,
      long balance, long expireTime) {
    AccountStore accountStore = chainBaseManager.getAccountStore();
    DynamicPropertiesStore dynamicPropertiesStore = chainBaseManager.getDynamicPropertiesStore();
    DelegatedResourceStore delegatedResourceStore = chainBaseManager.getDelegatedResourceStore();
    DelegatedResourceAccountIndexStore delegatedResourceAccountIndexStore = chainBaseManager
        .getDelegatedResourceAccountIndexStore();
    byte[] key = DelegatedResourceCapsule.createDbKey(ownerAddress, receiverAddress);
    //modify DelegatedResourceStore
    DelegatedResourceCapsule delegatedResourceCapsule = delegatedResourceStore
        .get(key);
    if (delegatedResourceCapsule != null) {
      if (isBandwidth) {
        delegatedResourceCapsule.addFrozenBalanceForBandwidth(balance, expireTime);
      } else {
        delegatedResourceCapsule.addFrozenBalanceForEnergy(balance, expireTime);
      }
    } else {
      delegatedResourceCapsule = new DelegatedResourceCapsule(
          ByteString.copyFrom(ownerAddress),
          ByteString.copyFrom(receiverAddress));
      if (isBandwidth) {
        delegatedResourceCapsule.setFrozenBalanceForBandwidth(balance, expireTime);
      } else {
        delegatedResourceCapsule.setFrozenBalanceForEnergy(balance, expireTime);
      }

    }
    delegatedResourceStore.put(key, delegatedResourceCapsule);

    //modify DelegatedResourceAccountIndexStore
    if (!dynamicPropertiesStore.supportAllowDelegateOptimization()) {

      DelegatedResourceAccountIndexCapsule ownerIndexCapsule =
          delegatedResourceAccountIndexStore.get(ownerAddress);
      if (ownerIndexCapsule == null) {
        ownerIndexCapsule = new DelegatedResourceAccountIndexCapsule(
            ByteString.copyFrom(ownerAddress));
      }
      List<ByteString> toAccountsList = ownerIndexCapsule.getToAccountsList();
      if (!toAccountsList.contains(ByteString.copyFrom(receiverAddress))) {
        ownerIndexCapsule.addToAccount(ByteString.copyFrom(receiverAddress));
      }
      delegatedResourceAccountIndexStore.put(ownerAddress, ownerIndexCapsule);

      DelegatedResourceAccountIndexCapsule receiverIndexCapsule
          = delegatedResourceAccountIndexStore.get(receiverAddress);
      if (receiverIndexCapsule == null) {
        receiverIndexCapsule = new DelegatedResourceAccountIndexCapsule(
            ByteString.copyFrom(receiverAddress));
      }
      List<ByteString> fromAccountsList = receiverIndexCapsule
          .getFromAccountsList();
      if (!fromAccountsList.contains(ByteString.copyFrom(ownerAddress))) {
        receiverIndexCapsule.addFromAccount(ByteString.copyFrom(ownerAddress));
      }
      delegatedResourceAccountIndexStore.put(receiverAddress, receiverIndexCapsule);
