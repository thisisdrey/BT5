## Title
Wallet Contract `has_in_flight_tx` lock can permanently strand an ETH-implicit account if not cleared on every completion path - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The Wallet Contract (NEP-518, deployed on every ETH-implicit account) uses a boolean flag `has_in_flight_tx` as a re-entrancy lock: `rlp_execute` refuses to start a new transaction while a previous one is still in flight, and the flag is expected to be cleared once that transaction's promise chain resolves. This is structurally the same pattern as the BendDAO `lockerAddr` bug: a "locked while in-use" marker is set on one code path and must be cleared on *every* exit path of the resource's lifecycle, or the resource becomes permanently unusable to its rightful owner.

### Finding Description
`rlp_execute` sets `self.has_in_flight_tx = true` before returning a `Promise` in two places: the normal execution path [1](#0-0) , and the `Err(Error::Relayer(_))` ban-relayer path. The flag is only cleared inside `address_check_callback` (`self.has_in_flight_tx = false;` at entry, then possibly re-set to `true` again before returning another promise) [2](#0-1) , and in `ban_relayer` [3](#0-2) .

This means the flag's lifecycle depends on a specific promise callback (`address_check_callback` or `ban_relayer`) actually being scheduled and executed for **every** promise chain that `rlp_execute` can create. I was not able to fully enumerate all promise-chain exit paths inside `action_to_promise`/the `rlp_execute_callback` (referenced at line 182) within the available index, so I cannot fully confirm or rule out a path where a promise chain completes (successfully or by failure) without invoking a callback that resets `has_in_flight_tx`. If such a path exists — e.g., a plain action promise created via `action_to_promise(target, action)` that is chained directly to `rlp_execute_callback` without ever calling `address_check_callback`, and where an unforeseen failure mode does not route back into a handler that clears the flag — then the account becomes permanently stuck: every subsequent `rlp_execute` call (from the legitimate key owner or any relayer) would return the "transaction already in progress" error, exactly mirroring the BendDAO NFT being permanently un-withdrawable because `lockerAddr` was never cleared on the liquidation exit path.

### Impact Explanation
If confirmed, this would be a permanent freezing-of-funds/denial-of-service condition: an ETH-implicit account (unprivileged, ordinary user asset) could become permanently unable to execute any further NEAR actions (transfers, function calls, key management) through its Wallet Contract, since `rlp_execute` is the sole entry point for such accounts and it is gated by `has_in_flight_tx`. Given NEAR's rule that ETH-implicit accounts "cannot be deleted, nor can a full access key be added" [4](#0-3) , there is no alternate recovery path — the account's balance would be permanently frozen, matching the "permanent freezing of funds" acceptance criterion.

### Likelihood Explanation
Uncertain. This requires a promise-chain completion (success or failure) that bypasses both `address_check_callback` and `ban_relayer`. The code comments strongly suggest the authors were aware of and tried to defend against exactly this class of bug (comments about not increment/incrementing nonce carefully, and clearing `has_in_flight_tx` at the start of the callback), which suggests they may have already covered all paths. I could not verify this within the tool budget available — specifically I did not get to inspect `rlp_execute_callback` itself, `action_to_promise`, or the failure-callback wiring, which are necessary to determine whether a promise failure (not just success) always routes through a flag-clearing callback.

### Recommendation
A Devin agent with full repo access should:
1. Read the complete `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`, especially `rlp_execute_callback`, `action_to_promise`, and any other private callback methods, to enumerate every promise chain created from `rlp_execute`.
2. For each promise chain, confirm that `has_in_flight_tx` is cleared on both the success and failure branches (NEAR promises deliver `PromiseResult::Failed` to the `#[private]` callback regardless of whether the inner action panicked or was rejected — verify the callback body handles `PromiseResult::Failed` and still clears the flag).
3. Check whether a malformed relayer message, gas exhaustion inside a nested promise, or a receiver contract panicking mid-chain could cause the final callback to never run (e.g., due to insufficient attached gas causing the callback itself to fail before executing the `self.has_in_flight_tx = false` line), which would leave the flag permanently `true`.
4. If a gap is found, add a general "reset the lock in a callback that always fires regardless of the inner promise outcome" pattern (analogous to adding `tokenData.lockerAddr = address(0)` on every exit path in the BendDAO fix), or add a governance/self-owner escape hatch to force-clear the flag.

    /// Callback after checking if an address is contained in the registrar.
    /// This check happens when the target is another eth implicit account to
    /// confirm that the relayer really did check for a named account with that address.
    #[private]
    pub fn address_check_callback(
        &mut self,
        target: AccountId,
        action: near_action::Action,
        caller_deposit: Option<CallerDeposit>,
    ) -> PromiseOrValue<ExecuteResponse> {
        self.has_in_flight_tx = false;
        let maybe_account_id: Option<AccountId> = match env::promise_result(0) {
            PromiseResult::Failed => {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Call to Address Registrar contract failed".into()),
                });
            }
            PromiseResult::Successful(value) => match serde_json::from_slice(&value) {
                Ok(x) => x,
                Err(_) => {
                    return PromiseOrValue::Value(ExecuteResponse {
                        success: false,
                        success_value: None,
                        error: Some("Unexpected response from account registrar".into()),
                    });
                }
            },
        };
        let current_account_id = env::current_account_id();
        let promise = if maybe_account_id.is_some() {
            // We intentionally do not increment the nonce in this case because the
            // error is caused by a faulty relayer, not the user. An honest relayer
            // may still be able to successfully send the user's intended transaction.
            if env::signer_account_id() == current_account_id {
                create_ban_relayer_promise(current_account_id)
            } else {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Invalid target: target is address corresponding to existing named account_id".into()),
                });
            }
        } else {
            // We must increment the nonce at this point to prevent replay of the transaction.
            // Recall that the nonce was not incremented in `inner_rlp_execute` in the case that
            // the registrar contract was called (i.e. in the case we end up inside this callback).
            self.nonce = self.nonce.saturating_add(1);
            let ext =
                WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
            match action_to_promise(target, action)
                .map(|p| p.then(ext.rlp_execute_callback(caller_deposit)))
            {
                Ok(p) => p,
                Err(e) => {
                    return PromiseOrValue::Value(e.into());
                }
            }
        };
        self.has_in_flight_tx = true;
        PromiseOrValue::Promise(promise)
    }
