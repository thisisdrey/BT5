### Title
`NativeWithdraw` to a non-existent named account permanently destroys signer's wNEAR with no NEAR delivered - (File: `contracts/defuse/src/contract/tokens/nep141/native.rs`)

### Finding Description
The binding that must hold is: `wNEAR_debited(signer) == NEAR_delivered(receiver_id) + NEAR_returned(signer)`.

`Contract::native_withdraw` (`contracts/defuse/src/contract/intents/state.rs:212-240`) first synchronously subtracts the signer's wNEAR mt-balance via `self.withdraw(...)`, then schedules `ext_wnear::near_withdraw` (which unwraps the contract's wNEAR into real NEAR held by the Defuse contract itself), chained via `.then(...)` into `Contract::do_native_withdraw`. That callback (`contracts/defuse/src/contract/tokens/nep141/native.rs:12-19`) only checks that `near_withdraw` succeeded, then does:

```rust
Promise::new(withdraw.receiver_id).transfer(withdraw.amount)
``` [1](#0-0) 

This final `Promise` has **no `.then()` callback** to observe its outcome. `NativeWithdraw::receiver_id` is never validated to be an existing account, and only implicit accounts (64-hex-char accounts derived from a public key) are auto-created on receiving a `Transfer` action in NEAR's protocol; a syntactically valid but non-existent **named** account (e.g. `"doesnotexist123.near"`) causes the `Transfer` action to fail. Since `self.withdraw` already ran synchronously and irreversibly debited the signer's mt-tracked wNEAR balance (`contracts/defuse/src/contract/intents/state.rs:213-221`), and the unwrapped real NEAR is refunded by the protocol back to the Defuse contract's own account (as predecessor) rather than to the signer, no code path re-credits the signer or delivers NEAR to the receiver.

An unprivileged signer can craft a `MultiPayload` containing `NativeWithdraw{receiver_id: <non-existent named account>, amount}`, submit it via `execute_intents`, and have their own wNEAR debited while the underlying NEAR becomes unaccounted extra balance sitting in the Defuse contract's own account — inaccessible via any mt-balance bookkeeping.

### Impact Explanation
The signer's wNEAR (an mt-tracked balance the Verifier custodies) is destroyed with no NEAR delivered to the intended receiver and no NEAR returned to the signer, and no compensating ledger entry exists anywhere in the contract's accounts map. This is a permanent loss of user funds — matching the Critical category "user funds permanently frozen" (here, effectively destroyed, since the underlying real NEAR becomes an untracked surplus on the Defuse contract's own account with no mt-balance entry and no rescue path exposed to the signer). Repeatable by any signer, against any of their own wNEAR balance, for any amount, any number of times.

### Likelihood Explanation
No special privileges are needed — only a signed `MultiPayload` with a `NativeWithdraw` intent and sufficient wNEAR balance in the Verifier. The attacker (against their own funds) or a griefer misled into supplying an invalid receiver both trigger the same divergence; from a security-boundary perspective, it is a "signer harms self," but the underlying invariant break — value leaving the Verifier's tracked ledger without a corresponding delivery or refund — is what the audit scope targets. Feasibility is high and fully reproducible in a sandbox test.

### Recommendation
Chain a `.then()` resolve callback after the final `Promise::new(receiver_id).transfer(amount)` in `do_native_withdraw` that checks the transfer's promise result and, on failure, re-credits the signer's wNEAR balance (mirroring the failure-handling pattern used for `ft_withdraw`/`nft_withdraw`/`mt_withdraw`, which appear to call `internal_ft_withdraw`/etc. with resolve-on-failure semantics). Alternatively/additionally validate `receiver_id` existence semantics or restrict `NativeWithdraw` to implicit accounts only if a safe re-credit callback cannot be added.

### Proof of Concept
`cargo test` plan (near-workspaces sandbox, extending `tests/src/tests/defuse/intents/native_withdraw.rs`):
1. Create `user` and deposit wNEAR into the Defuse contract for `user` (mirroring existing `native_withdraw_intent` test setup).
2. Sign a `MultiPayload` from `user` containing a single `NativeWithdraw{ receiver_id: "nonexistent-account-xyz.near".parse().unwrap(), amount }` where the receiver account is never created in the sandbox.
3. Call `execute_intents` with this payload.
4. Assert `mt_balance_of(user, wNEAR token_id) == 0` (signer's wNEAR debited).
5. Assert the receiver account does not exist / has zero balance on-chain (`env.account(receiver_id).await` returns `None`).
6. Assert no other account (including the Defuse contract's own NEAR balance beyond pre-existing storage costs) shows a compensating credit reachable by the signer — demonstrating `wNEAR_debited(signer) != NEAR_delivered(receiver_id) + NEAR_returned(signer)`.
