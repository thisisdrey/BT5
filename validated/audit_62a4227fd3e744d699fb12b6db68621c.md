### Title
Missing fee-balance check lets AccountPermissionUpdate mutate account permissions before fee collection can fail - ([File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java])

### Summary
`AccountPermissionUpdateActuator.validate()` never verifies that the owner account has enough balance to pay `calcFee()` before `execute()` runs, unlike sibling actuators (e.g. `CreateAccountActuator`) that explicitly check `accountCapsule.getBalance() < fee` in `validate()`. This mirrors the reported Escrow bug class: state-changing work is performed using an amount that was never verified to be collectible, and the balance-sufficiency check is deferred to the point of fund movement instead of being enforced upfront.

### Finding Description
In `execute()`, the actuator applies the permission update to the account object and persists it to `AccountStore` *before* attempting to deduct the fee: [1](#0-0) 

`validate()` performs extensive structural checks on the permissions (`checkPermission`, owner/witness/actives checks) but at no point calls `calcFee()` to confirm the owner's balance covers `getUpdateAccountPermissionFee()`: [2](#0-1) 

Contrast this with `CreateAccountActuator.validate()`, which explicitly enforces the fee-balance invariant before `execute()` is allowed to run: [3](#0-2) 

Because the check is missing, `adjustBalance(accountStore, ownerAddress, -fee)` at line 54 is the first point where insufficiency can be detected — after the permission mutation has already been written to `accountStore`. This is analogous to the Escrow bug: the actuator performs its principal state effect (updating permissions / distributing funds) using a value (`fee`) whose availability was never validated upfront, deferring the balance check to the execution/distribution step.

### Impact Explanation
If the underlying persistence layer does not fully revert per-transaction writes on a thrown `ContractExeException` (only rolling back at the session/block level), an account with insufficient balance could have its multisig permissions rewritten as a side effect of a transaction that ultimately reports `FAILED`, without ever having paid the fee — an inconsistency between "transaction succeeded/failed" state and actual account mutation. Even if writes are fully reverted at the enclosing session boundary (which the available context could not conclusively confirm), the design pattern itself is the exact bug class flagged in the Escrow report: a required amount is not validated for availability before the actuator begins mutating state that depends on it, unlike every comparable actuator in the codebase that performs this check consistently in `validate()`.

### Likelihood Explanation
Any account holder can trigger `AccountPermissionUpdateContract` and drain their balance to just below `getUpdateAccountPermissionFee()` (default 100,000,000 sun) before submitting the transaction — this requires no special privilege, only ordinary account/transaction broadcasting rights.

### Recommendation
Add an explicit balance check in `AccountPermissionUpdateActuator.validate()`, mirroring `CreateAccountActuator`:
```java
long fee = calcFee();
if (accountCapsule.getBalance() < fee) {
  throw new ContractValidateException("Insufficient balance to pay AccountPermissionUpdate fee.");
}
```
This ensures fee sufficiency is enforced before any permission-mutation side effects occur in `execute()`.

### Proof of Concept
Not independently reproducible from the available index: confirming actual observable impact (unbacked permission update surviving a failed transaction) requires verifying whether `TransactionTrace.exec()` / the enclosing DB session fully reverts all store writes made inside `execute()` when a `ContractExeException` is thrown. This could not be conclusively confirmed with the tools available (the `TransactionTrace.java` execution/rollback logic was not retrieved before the iteration budget was exhausted), so the severity should be validated by tracing `Manager.processTransaction` → `TransactionTrace.exec()` → session revert behavior for actuator-level exceptions.

  @Override
  public boolean validate() throws ContractValidateException {

    if (chainBaseManager == null) {
      throw new ContractValidateException(ActuatorConstant.STORE_NOT_EXIST);
    }

    if (this.any == null) {
      throw new ContractValidateException(ActuatorConstant.CONTRACT_NOT_EXIST);
    }

    AccountStore accountStore = chainBaseManager.getAccountStore();
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();

    if (dynamicStore.getAllowMultiSign() != 1) {
      throw new ContractValidateException("multi sign is not allowed, "
          + "need to be opened by the committee");
    }
    if (!this.any.is(AccountPermissionUpdateContract.class)) {
      throw new ContractValidateException(
          "contract type error,expected type [AccountPermissionUpdateContract],real type["
              + any.getClass() + "]");
    }
    final AccountPermissionUpdateContract accountPermissionUpdateContract;
    try {
      accountPermissionUpdateContract = any.unpack(AccountPermissionUpdateContract.class);
    } catch (InvalidProtocolBufferException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractValidateException(e.getMessage());
    }
    byte[] ownerAddress = accountPermissionUpdateContract.getOwnerAddress().toByteArray();
    if (!DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("invalidate ownerAddress");
    }
    AccountCapsule accountCapsule = accountStore.get(ownerAddress);
    if (accountCapsule == null) {
      throw new ContractValidateException("ownerAddress account does not exist");
    }

    if (!accountPermissionUpdateContract.hasOwner()) {
      throw new ContractValidateException("owner permission is missed");
    }

    if (accountCapsule.getIsWitness()) {
      if (!accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("witness permission is missed");
      }
    } else {
      if (accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("account isn't witness can't set witness permission");
      }
    }

    if (accountPermissionUpdateContract.getActivesCount() == 0) {
      throw new ContractValidateException("active permission is missed");
    }
    if (accountPermissionUpdateContract.getActivesCount() > 8) {
      throw new ContractValidateException("active permission is too many");
    }

    Permission owner = accountPermissionUpdateContract.getOwner();
    Permission witness = accountPermissionUpdateContract.getWitness();
    List<Permission> actives = accountPermissionUpdateContract.getActivesList();

    if (owner.getType() != PermissionType.Owner) {
      throw new ContractValidateException("owner permission type is error");
    }
    checkPermission(owner);
    if (accountCapsule.getIsWitness()) {
      if (witness.getType() != PermissionType.Witness) {
        throw new ContractValidateException("witness permission type is error");
      }
      checkPermission(witness);
    }
    for (Permission permission : actives) {
      if (permission.getType() != PermissionType.Active) {
        throw new ContractValidateException("active permission type is error");
      }
      checkPermission(permission);
    }
    return true;
  }
