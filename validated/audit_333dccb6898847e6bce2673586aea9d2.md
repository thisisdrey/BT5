### Title
Floating-point (double/Math.pow) precision loss in the TRX/TRC10 bancor-style exchange lets an attacker extract excess tokens from an Exchange pool - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
The `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` actuators price trades through `ExchangeCapsule.transaction()`, which by default (when `allowHarden()`/`ALLOW_HARDEN_EXCHANGE_CALCULATION` is 0, its documented default) uses `ExchangeProcessor`, a bancor-formula implementation built on Java `double` arithmetic and `Math.pow` [1](#0-0) . The double-precision path produces different (rounded) outputs than the exact `BigDecimal`-based `SafeExchangeProcessor` for identical inputs, as directly proven by the project's own regression test [2](#0-1) . This is conceptually the same bug class as the OMNI404 incident: a value used to update reserve/pool balances is derived from an imprecise numeric computation, letting a caller pick input quantities that make the computed "amount out" diverge from the true bonding-curve value, extracting more of the counter-asset than the pool should give up per unit deposited.

### Finding Description
`ExchangeTransactionActuator.execute()` calls `exchangeCapsule.transaction(tokenID, tokenQuant, dynamicStore.allowStrictMath(), allowHarden())` to compute `anotherTokenQuant`, which is both what is credited to the trader and what is subtracted from the pool's `firstTokenBalance`/`secondTokenBalance` [3](#0-2) . Internally, when hardened math is not active, `ExchangeCapsule.transaction()` selects the legacy `ExchangeProcessor`: [1](#0-0) 

`ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` compute the bonding-curve amount using `double` division and `Math.pow(..., 0.0005)` / `Math.pow(..., 2000.0)`, then truncate to `long`: [4](#0-3) 

Floating-point `pow`/division on large `long` reserve balances is not exact; small differences in mantissa rounding compound through the two `pow` calls (sell→relay supply, relay→buy amount). The framework's own test harness demonstrates the divergence: for a batch of real reserve/quantity triples it asserts the double-based `ExchangeProcessor` output is `assertNotEquals` to the exact `BigDecimal` (`SafeExchangeProcessor`) output on the same inputs [5](#0-4) , i.e., the "exact" answer and the on-chain answer are provably different for chosen inputs. Whichever direction the rounding favors the trader, a repeated/optimized sequence of trades (choosing `tokenQuant` values that maximize the rounding-up error in `exchangeFromSupply`) accumulates value taken from the pool beyond what the true bancor curve would allow, echoing how OMNI404 attackers picked specific small integer inputs (1–21) to repeatedly trigger a fixed/mispriced conversion rather than a proportional one.

The "hardened", exact `SafeExchangeProcessor` (BigDecimal, `RoundingMode.HALF_UP`/`DOWN`) exists in the codebase but is gated behind the `ALLOW_HARDEN_EXCHANGE_CALCULATION` chain parameter, whose value defaults to 0 (disabled) until a super-representative committee proposal activates it [6](#0-5) , confirmed by the proposal test which states "current value is 0 (default)" [7](#0-6) . So on any deployment that has not activated this proposal, every `ExchangeTransactionContract`/`ExchangeInjectContract` executed by an ordinary transaction broadcaster runs the imprecise double-math path.

### Impact Explanation
The Exchange pool's `firstTokenBalance`/`secondTokenBalance` and the trader's/injector's TRX/TRC10 asset balances are updated directly from the output of the imprecise calculation [8](#0-7) . Systematic exploitation of rounding bias lets an attacker drain real TRX/TRC10 value from an Exchange pool over repeated trades — an unbacked-balance/theft-of-funds outcome reachable purely through signed `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` transactions from any account, matching the in-scope "exchange and market order handling" category and the required "theft of funds" impact bar.

### Likelihood Explanation
Any account can call `ExchangeTransactionContract` (and `ExchangeInjectContract`) without special privilege; no flash loan mechanism is needed since the actuator itself performs the AMM math with `double` precision. The codebase's own test suite already demonstrates measurable divergence between the double-based and BigDecimal-based paths for realistic reserve sizes [5](#0-4) , and the safer path (`ALLOW_HARDEN_EXCHANGE_CALCULATION`) is off by default, so exploitation requires no privileged state change — only crafting trade sizes/sequences that maximize rounding bias, similar to how the OMNI404 attacker crafted a sequence of small transfer amounts.

### Recommendation
Make `SafeExchangeProcessor` (or an equivalent fixed-point/`BigDecimal` implementation) the default and only pricing path for `ExchangeCapsule.transaction()`, removing the double/`Math.pow`-based `ExchangeProcessor` from consensus-critical balance updates, or activate `ALLOW_HARDEN_EXCHANGE_CALCULATION` network-wide and deprecate the legacy path entirely rather than leaving it reachable pending a committee proposal.

### Proof of Concept
1. Deploy/observe an `Exchange` created via `ExchangeCreateContract` with sizable TRX/TRC10 reserves (e.g. the values exercised in `ExchangeProcessorTest.testStrictMath`, such as `sellBalance=4732214`, `buyBalance=2202692725330`).
2. With `ALLOW_HARDEN_EXCHANGE_CALCULATION` at its chain default (0), submit `ExchangeTransactionContract` transactions whose `quant` values are chosen (via off-chain search, mirroring the test's `testData` table) to maximize the delta between `ExchangeProcessor.exchange()` and the exact bancor output computed by `SafeExchangeProcessor.exchange()` for the same reserves/quant, as the test itself proves diverge (`Assert.assertNotEquals(anotherTokenQuant, result)`).
3. Repeat across many blocks/trades; each trade's `anotherTokenQuant` (credited from the pool) carries the same rounding bias, cumulatively extracting more counter-asset from the pool's `firstTokenBalance`/`secondTokenBalance` than the exact curve would allow, draining pool value analogous to the OMNI404 WETH drain.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
