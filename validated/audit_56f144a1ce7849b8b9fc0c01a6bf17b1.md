### Title
StackerDB chunk signature does not bind to the target contract, enabling cross-StackerDB replay of a validly-signed chunk - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::sign`/`verify` authenticate a StackerDB chunk over `(slot_id, slot_version, data_hash)` only — the target StackerDB contract (`QualifiedContractIdentifier`) is never part of the signed digest. Storage-side validation (`try_replace_chunk`, `validate_received_chunk`) looks up the expected signer *per contract*, but never mixes the contract identity into the signature check itself. Consequently, a chunk validly signed by a key for slot `N` in StackerDB contract `A` can be replayed verbatim into slot `N` of a different StackerDB contract `B`, as long as the same signer address also owns slot `N` in `B` and `B`'s version/staleness/max-writes checks are satisfied. This is the exact analog of the "fid" bug: the signature commits to a slot index but not to the specific StackerDB instance it was meant for.

### Finding Description
`SlotMetadata::auth_digest()` hashes only `slot_id`, `slot_version`, and `data_hash`: [1](#0-0) 

`sign()`/`verify()` operate purely on this digest, with no contract/context binding: [2](#0-1) 

On the write path, `StackerDBTx::try_replace_chunk` receives `smart_contract` as a separate parameter, fetches the expected signer for `(smart_contract, slot_id)`, and then calls `slot_desc.verify(&slot_validation.signer)`, which only checks the slot/version/data-hash-bound signature — never the contract identity itself: [3](#0-2) 

The same pattern exists on the P2P validation path, `PeerNetwork::validate_received_chunk`, which resolves the expected signer for `(smart_contract_id, data.slot_id)` and then verifies the chunk's `SlotMetadata` against that address, again without the contract identity entering the signed digest: [4](#0-3) 

The repo contains a concrete scenario where the same signer key is deterministically assigned slot indices in two parallel, independently-configured StackerDB contracts: `.signers-0-xxx` (even reward cycles) and `.signers-1-xxx` (odd reward cycles), each populated from `stackerdb-signer-slots-0` / `stackerdb-signer-slots-1`, with the slot index for a signer being its position in the (parity-specific) sorted signer list: [5](#0-4) 

Because the ordering is derived by sorting on `signing_key`, a signer that keeps a similar relative rank across cycles (a common and unremarkable case, especially with a small or stable signer set) will occupy the same `slot_id` in both the even- and odd-cycle StackerDB contracts. The same is also possible between any two independently configured `stacker_dbs` contracts (from node config `stacker_dbs`) that happen to assign the same address to the same `slot_id` — nothing in the protocol prevents this, since slot assignment is per-contract Clarity logic entirely decoupled from the signature scheme.

Given that, any previously-observed, validly-signed `(slot_id, slot_version, data_hash)` triple for one StackerDB contract remains a valid signature for the identical `(slot_id, slot_version, data_hash)` in any other contract where that signer owns the same slot. An attacker who observes one signed chunk (StackerDB traffic is broadcast/gossiped, not secret) can replay it into a different StackerDB replica set to force acceptance of attacker-chosen data (the data bytes travel alongside the signature and are not bound to a specific contract either — only their hash is signed, and the hash matches because the attacker replays the exact same `data` bytes) as long as `slot_version`/`max_writes`/staleness checks pass independently in the target contract.

### Impact Explanation
This allows unauthorized/forged data to be written into a StackerDB slot of an unintended contract using a signature that was legitimately produced for a different context, without the signer's consent for that specific contract. Depending on which StackerDB is targeted (e.g. signer message relay for block signing, or any third-party StackerDB with independently-configured slot ownership overlapping by coincidence or design), this can inject stale/forged content that downstream consumers (e.g. signer-set/message readers) will treat as authentic for that contract, since `verify()` returns `true`. This matches the report's "Critical: unauthenticated/unauthorized write to state" / "High: non-canonical/mismatched data served as canonical" bucket, since it is a remote, unprivileged write of attacker-replayed data into an authenticated StackerDB slot in a context the original signer did not intend.

### Likelihood Explanation
Exploitation requires: (1) observing one prior valid chunk signature+data from a signer for slot `N` (trivial — chunks propagate over gossip/HTTP and are not confidential), and (2) that same signer owning slot `N` in a second StackerDB contract with a version/staleness state that still accepts the replayed `slot_version`. The `.signers-0`/`.signers-1` parity split in `signers.clar` is a concrete, already-existing structure where slot-index collisions for the same signer across contracts are plausible without any special manipulation, and node operators can add arbitrary additional `stacker_dbs` contracts, further increasing the chance of slot/signer overlap. No secret key, admin role, or consensus-internals access is required — it is a pure protocol design gap in the signed digest, not user error.

### Recommendation
Bind the StackerDB `smart_contract` identifier (or a domain separator with the reward-cycle/contract identity, similar to `_hashTypedDataV4` domain separation) into `SlotMetadata::auth_digest()`, so a signature is only valid for the specific `(contract_id, slot_id, slot_version, data_hash)` tuple it was created for. This requires updating `auth_digest()` in `libstackerdb/src/libstackerdb.rs`, and threading the contract identifier through `sign()`/`verify()` call sites in `stackslib/src/net/stackerdb/db.rs` and `stackslib/src/net/stackerdb/mod.rs`.

### Proof of Concept
1. Signer `S` is assigned `slot_id = 3` in StackerDB contract `A` (e.g., `.signers-0-xxx`) and also assigned `slot_id = 3` in StackerDB contract `B` (e.g., `.signers-1-xxx`, or any other node-configured `stacker_dbs` contract), which can occur naturally via `signers.clar`'s per-parity sorted slot assignment.
2. `S` legitimately signs and posts chunk `(slot_id=3, slot_version=5, data=D)` to contract `A`; this propagates over P2P/HTTP and is observable by any peer.
3. An attacker captures `(slot_id=3, slot_version=5, data=D, sig)` and submits it (via `POST /v2/stackerdb/.../chunks` or P2P `StackerDBPushChunk`) to contract `B`, where slot 3's current version is `< 5` and `max_writes >= 5`.
4. `try_replace_chunk`/`validate_received_chunk` fetch `B`'s slot-3 signer (`S`), call `slot_desc.verify(&S)`, which succeeds because `auth_digest()` never included the contract identifier — the chunk is accepted and stored in `B`'s slot 3, even though `S` never authorized this write for contract `B`.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }

    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
