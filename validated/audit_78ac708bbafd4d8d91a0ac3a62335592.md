### Title
Missing cap on `ENERGY_FEE`/`EXCHANGE_CREATE_FEE` chain parameters enables integer overflow in energy-fee billing - (`actuator/src/main/java/org/tron/core/utils/ProposalUtil.java`, `chainbase/src/main/java/org/tron/core/capsule/ReceiptCapsule.java`)

### Summary
`ProposalUtil.validator()` validates almost every governance-tunable chain parameter against an explicit `[0, LONG_VALUE]` range (e.g. `CREATE_ACCOUNT_FEE`, `ASSET_ISSUE_FEE`, `MARKET_SELL_FEE`, `MAX_FEE_LIMIT`), but for `ENERGY_FEE` and `EXCHANGE_CREATE_FEE` it performs **no bound check at all**: [1](#0-0) 

This is the exact bug class described in the external report ("no cap on `LicenseFee`... can lead to over/underflow"), applied to `ENERGY_FEE`, which is multiplied unguarded against a raw `long` in the transaction-fee billing path used by every contract call on the network.

### Finding Description
`ENERGY_FEE` (the "sun per energy" rate) can be set to any `long` value via a committee `ProposalCreateContract`/`ProposalApproveContract` flow because the `switch` in `ProposalUtil.validator()` falls straight to `break;` for `ENERGY_FEE` and `EXCHANGE_CREATE_FEE` without any `if (value < 0 || value > X)` check, unlike every neighboring case: [2](#0-1) 

The value is later read directly and used in unchecked multiplication inside `ReceiptCapsule.payEnergyBill`, which executes whenever any contract call's `accountEnergyLeft < usage` (i.e., when the caller runs out of pre-purchased energy and must pay in TRX): [3](#0-2) 

```java
long sunPerEnergy = Constant.SUN_PER_ENERGY;
long dynamicEnergyFee = dynamicPropertiesStore.getEnergyFee();
if (dynamicEnergyFee > 0) {
  sunPerEnergy = dynamicEnergyFee;
}
long energyFee = (usage - accountEnergyLeft) * sunPerEnergy;
...
if (balance < energyFee) {
  throw new BalanceInsufficientException(...);
}
account.setBalance(balance - energyFee);
```

Because this multiplication is a plain `long * long` (not the `multiplyExact`/`Maths` safe-math helper used elsewhere in the same file, e.g. `multiplyExact(receipt.getEnergyUsageTotal(), percent, disableJavaLangMath)` in `payEnergyBill` at line 227), an unbounded `dynamicEnergyFee` set via a governance proposal can make `(usage - accountEnergyLeft) * sunPerEnergy` overflow `Long.MAX_VALUE` and wrap to a negative number. If `energyFee` becomes negative, the `balance < energyFee` check trivially passes and `account.setBalance(balance - energyFee)` **increases** the caller's balance instead of debiting it — an unbacked-balance/fund-creation bug reachable by any ordinary contract-calling transaction once the parameter is mis-set.

### Impact Explanation
This satisfies the "unbacked balance" / "theft of funds" impact bar: once `ENERGY_FEE` is pushed above the overflow threshold, **every unprivileged account that triggers energy-exhaustion billing during a normal contract call** (a routine, frequent, fully public code path — no special permission needed to call a contract and exhaust delegated/frozen energy) can have TRX conjured into its balance instead of debited, corrupting total-supply invariants and letting an attacker drain the network's TRX backing. Even absent full overflow exploitation, an extreme `dynamicEnergyFee` can make `energyFee` astronomically large, causing legitimate users' `BalanceInsufficientException` (denial of service for contract execution) — mirroring the "bricking the contract... preventing users from minting/burning" impact from the reference finding, here manifesting as inability to execute/pay for contract calls network-wide.

### Likelihood Explanation
The bad value must be set through the on-chain committee proposal mechanism (`ProposalCreateActuator` → `ProposalUtil.validator` → maintenance-cycle `ProposalService.process`), which requires witness approval and a maintenance-cycle delay — same governance/timelock gate as the original `LicenseFee` finding that the judge still rated Medium severity because of the missing defense-in-depth cap. The validator explicitly caps every sibling parameter but silently skips `ENERGY_FEE`/`EXCHANGE_CREATE_FEE`, which looks like an oversight rather than an intentional design choice, and the downstream usage lacks overflow-safe arithmetic, unlike other fee calculations in the same class.

### Recommendation
Add an explicit bounded range check for `ENERGY_FEE` and `EXCHANGE_CREATE_FEE` in `ProposalUtil.validator()` (e.g., the same `[0, LONG_VALUE]` or a smaller sane maximum used for other TRX-denominated fees), and replace the raw multiplication in `ReceiptCapsule.payEnergyBill` (`(usage - accountEnergyLeft) * sunPerEnergy`) with the existing overflow-safe `Maths.multiplyExact` helper already used elsewhere in the same method.

### Proof of Concept
1. A witness/committee member creates a `ProposalCreateContract` setting parameter code `11` (`ENERGY_FEE`) to a very large value close to `Long.MAX_VALUE / maxPossibleEnergyUsage` (no validation rejects this, per `ProposalUtil.validator` case `ENERGY_FEE: break;`).
2. Proposal is approved and takes effect at the next maintenance cycle via `ProposalService.process`, updating `DynamicPropertiesStore`'s energy fee value.
3. Any ordinary user calls a smart contract and exhausts their available energy (`accountEnergyLeft < usage`), entering the `else` branch of `ReceiptCapsule.payEnergyBill`.
4. `energyFee = (usage - accountEnergyLeft) * sunPerEnergy` overflows `long` and wraps to a negative value.
5. `balance < energyFee` is false (negative `energyFee`), so `account.setBalance(balance - energyFee)` executes, increasing the user's balance instead of debiting the energy fee — creating unbacked TRX.
