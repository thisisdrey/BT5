### Title
Unbounded microblock count in `MicroblocksData::consensus_deserialize` allows byte-budget-maximized parsing DoS - (File: stackslib/src/net/codec.rs)

### Summary
`MicroblocksData::consensus_deserialize` reads `microblocks: Vec<StacksMicroblock>` using plain `read_next` inside a `BoundReader` capped only at `MAX_MESSAGE_LEN` bytes, with no explicit per-message item-count cap analogous to `BLOCKS_PUSHED_MAX` used for `BlocksData`. A remote peer can pack the maximum number of minimally-sized `StacksMicroblock` structures into a single `MAX_MESSAGE_LEN`-sized payload, forcing the receiver to fully deserialize every one of them from one P2P message.

### Finding Description
`BlocksData::consensus_deserialize` explicitly bounds the number of items with `read_next_at_most::<_, BlocksDatum>(&mut bound_read, BLOCKS_PUSHED_MAX)` [1](#0-0) , but `MicroblocksData::consensus_deserialize` uses unbounded `read_next(&mut bound_read)` for the `Vec<StacksMicroblock>`, relying solely on the enclosing `BoundReader::from_reader(fd, MAX_MESSAGE_LEN as u64)` byte cap [2](#0-1) . This is an asymmetry within the same file: `BlocksData` and (per the question) `NakamotoBlocksData` enforce a named item-count constant, while `MicroblocksData` does not. The comment "loose upper-bound" at line 549 acknowledges the cap is byte-based only, not count-based.

Because the byte cap is the only constraint, the number of microblocks the receiver commits to parsing is a function of `MAX_MESSAGE_LEN` divided by the minimal serialized size of a `StacksMicroblock` (header + empty tx list), which can be substantially larger than any deliberately chosen count-based limit such as `BLOCKS_PUSHED_MAX`. An attacker connected as a P2P peer can craft a single `MicroblocksData` payload filled with minimally-valid-format `StacksMicroblock` entries (need not be cryptographically valid to be parsed by the codec layer — only decodable) up to the `MAX_MESSAGE_LEN` byte limit, and the node will run the full `consensus_deserialize` logic (allocation, header parsing, tx-vec parsing per microblock) for every entry in one message.

### Impact Explanation
This causes increased CPU/allocation cost per P2P message: the node parses as many microblock structures as fit in `MAX_MESSAGE_LEN` bytes rather than a small explicit cap, unlike the `BlocksData`/`NakamotoBlocksData` paths that bound the count directly. This is a bounded (single-message) compute-cost amplification during deserialization, and can be repeated by resending crafted `MicroblocksData` messages, so it multiplies attacker cost linearly rather than being an unbounded/crash bug.

### Likelihood Explanation
Precondition is only an established P2P session (any peer able to handshake) — no additional authentication or state is required to send a `MicroblocksData` message; the relevant deserialization occurs before any block/microblock consensus validation. This is a low-cost, repeatable action for any connected peer.

### Recommendation
Add an explicit maximum microblock count constant (e.g., `MICROBLOCKS_PUSHED_MAX`) and use `read_next_at_most::<_, StacksMicroblock>(&mut bound_read, MICROBLOCKS_PUSHED_MAX)` in `MicroblocksData::consensus_deserialize`, mirroring the pattern already used for `BlocksData` (`BLOCKS_PUSHED_MAX`) and `NakamotoBlocksData`, so the per-message microblock count is bounded independently of the raw byte cap.

### Proof of Concept
Add a test in `stackslib/src/net/codec.rs` (or a `tests` module for `MicroblocksData`) that:
1. Constructs many minimal `StacksMicroblock` instances (empty tx vector, minimal header) and serializes them via `write_next` into a byte buffer up to just under `MAX_MESSAGE_LEN`.
2. Wraps the buffer as a `MicroblocksData` payload (prefixed by an `index_anchor_block` `StacksBlockId`).
3. Calls `MicroblocksData::consensus_deserialize` on the buffer and asserts it succeeds, returning a `microblocks` vector whose length is far larger than `BLOCKS_PUSHED_MAX` (the cap used for `BlocksData`), demonstrating no equivalent count cap exists.
4. Measure wall-clock time/allocations for this payload versus a single-microblock baseline of identical total byte size to show disproportionate parsing cost per message.
