### Title
Precompiled Contract Array Length Field Used to Allocate Unbounded Arrays Without Bounds Check - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`PrecompiledContracts.extractBytes32Array` and `PrecompiledContracts.extractBytesArray` read a length value directly out of attacker-controlled ABI-encoded call data (`words[offset].intValueSafe()`) and immediately use it to allocate a Java array (`new byte[len][]`) before validating that `len` is consistent with the actual size of the supplied `words`/`data` buffers. [1](#0-0) 

### Finding Description
`extractBytes32Array` computes `len` from a single 32-byte word supplied by the caller and allocates `bytes32Array = new byte[len][]` with no upper bound check against `words.length`: [2](#0-1) 

`extractBytesArray` performs the same pattern — it only checks that `offset` is within `words.length`, then reads `len` from `words[offset]` and allocates `bytesArray = new byte[len][]` before any loop that would fail on out-of-range access: [3](#0-2) 

This mirrors the EVE vTPM bug class exactly: a size field is read from untrusted input and used to allocate a buffer of that size before the input is validated against the size actually available (CWE-770 "Allocation of Resources Without Limits", CWE-789 "Memory Allocation with Excessive Size Value"). In the EVE case the size came from a raw socket header; here it comes from ABI-encoded precompiled-contract call data, which is reachable by any account that can send a transaction invoking a TVM precompiled contract that uses these array-decoding helpers.

Because these helper functions live in `PrecompiledContracts`, they execute inside contract/transaction validation and execution, i.e., they are directly reachable from an unprivileged contract caller through the actuator validate/execute path for smart-contract transactions, which is explicitly in scope.

### Impact Explanation
An attacker who calls a precompiled contract that uses `extractBytes32Array`/`extractBytesArray` for its parameter decoding can supply an ABI length word far larger than the actual data supplied. Since `len` is taken from `intValueSafe()` (which returns the raw int value when it fits in 32 bits, only clamping to `Integer.MAX_VALUE` on overflow), an attacker can set `len` to a large value (up to `Integer.MAX_VALUE`, or any large value that fits) and force the node to attempt allocating an array of that many pointer slots. This is a large, attacker-controlled allocation that occurs before any check that the array indices being iterated are actually within `words.length`/`data.length` bounds. On a busy validator/witness node, repeated invocation can drive an `OutOfMemoryError`, crashing the executing node process (denial of service), consistent with the CWE-770/CWE-789 impact described in the referenced advisory (`A:H` in the CVSS vector).

### Likelihood Explanation
Likelihood is high for triggering the allocation: any account can broadcast a transaction calling the affected precompiled contract with a crafted large length word, since these helpers are part of ABI-decoding logic for precompiled-contract inputs and are reachable from ordinary transaction execution, requiring no special privilege, key, or SR/witness role.

### Recommendation
Add an explicit bound check before allocating `bytes32Array`/`bytesArray`, verifying that `len` is non-negative and does not exceed a sane maximum consistent with `words.length` (and, for `extractBytesArray`, with the actual size of `data`) before calling `new byte[len][]`, mirroring the `verifyLength` bounds check already used elsewhere in the codebase (e.g., `RLP.verifyLength`). [4](#0-3) 

### Proof of Concept
1. Deploy or invoke a precompiled contract whose ABI parameter is decoded via `extractBytes32Array`/`extractBytesArray` (array-typed precompile input).
2. Craft the calldata so that the length word at the expected `offset` encodes a very large integer (e.g., close to `Integer.MAX_VALUE`) while the actual supplied `words`/`data` payload is short.
3. Broadcast the transaction; when the node executes the precompiled contract, `extractBytes32Array`/`extractBytesArray` will attempt `new byte[len][]` with the attacker-supplied `len`, triggering excessive memory allocation and potentially an `OutOfMemoryError`, crashing or destabilizing the executing node.

Note: I was unable to fully trace which specific precompiled contract(s) invoke `extractBytes32Array`/`extractBytesArray` (the tool call to confirm callers did not return results before the iteration limit), so the exact precompile entry point and the precise numeric bound accepted by `intValueSafe()` could not be independently confirmed from the index; this should be verified directly in the full `PrecompiledContracts.java` and `DataWord.java` source before remediation.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
