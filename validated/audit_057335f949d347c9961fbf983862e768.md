### Title
Unprivileged dust transfers pollute `Pool.depositTokensOfAccount`, permanently locking victims at `MAX_TOKENS_PER_USER` - (File: contracts/DepositToken.sol)

### Summary
The n8n report is a prototype-pollution bug: an attacker writes attacker-controlled keys into a shared/global object, and that poisoned state later changes behavior for other users' requests. The direct analog in Metronome is the per-account `depositTokensOfAccount` set in `Pool` (`MappedEnumerableSet`), which is written as a side effect of `DepositToken._transfer` and is bounded by `MAX_TOKENS_PER_USER`. Any holder of a deposit token can push an entry into *any* victim's set via a dust `transfer`, "polluting" the victim's collateral list until every operation that adds a new collateral token reverts — freezing the victim's ability to deposit new collateral, receive seized/transfer tokens, or be rescued from liquidation.

### Finding Description
`DepositToken._transfer` unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's prior balance of that token is zero, with no minimum amount and no recipient opt-in [1](#0-0) . The same registration happens on `_mint` (i.e., `deposit(..., onBehalfOf_)`, which is also permissionless — an attacker can deposit dust `onBehalfOf` the victim) [2](#0-1) [3](#0-2) .

`Pool.addToDepositTokensOfAccount` reverts once the account's set reaches `MAX_TOKENS_PER_USER` (the cap enforced in `Pool.sol` against the `MappedEnumerableSet` in `PoolStorage`). Because `debtPositionOf`/`depositOf` iterate this set for collateral valuation, every state-changing path that could add another distinct deposit token — `deposit` on a new collateral, `transfer`/`transferFrom`/`seize` of a not-yet-held msdTOKEN, SmartFarmingManager leverage deposits — reverts once the set is full. Removal only happens when a balance returns to exactly zero, which the attacker controls for the tokens it sent (the victim must spend gas transferring each dust token out, and the attacker can simply re-pollute in the same or a later transaction — classic pollution persistence).

Attack steps:
1. Attacker deposits dust amounts of `N - k` distinct collateral underlying assets via `DepositToken.deposit(1 wei each, onBehalfOf_ = victim)` (deposit is `whenNotPaused`, no per-account authorization) or acquires msdTOKENs and calls `transfer(victim, 1)` for each [4](#0-3) .
2. Victim's `depositTokensOfAccount` now sits at the cap.
3. Victim cannot deposit a new collateral type, cannot receive any new msdTOKEN (each `transfer` reverts inside `addToDepositTokensOfAccount` after balances are already updated — actually the revert rolls back the whole call, so even *inbound* transfers fail), and liquidation `seize` to a liquidator who is at cap also reverts.
4. While poisoned, the victim's position can be pushed underwater by market movement; adding collateral to restore health — the standard remedy — is impossible for any collateral token not already in the victim's set. Attacker can then liquidate the victim, or simply keep the freeze in place by re-sending dust after each removal.

### Impact Explanation
Temporary freezing of funds / forced liquidation: the victim loses the ability to manage their position (deposit new collateral, receive transfers) until they manually remove each dust token — and each removal transaction can be front-run/griefed by the attacker re-adding a token. In volatile conditions this converts directly into loss of funds via unavoidable liquidation. Cost to the attacker is only gas plus dust collateral. This mirrors the advisory's pollution→escalation chain: a write to shared account state (`depositTokensOfAccount`) corrupts a later, otherwise-authorized flow (deposit/liquidation) for another user.

### Likelihood Explanation
Fully reachable by any EOA with tiny collateral amounts: `deposit` and `transfer` are public, `whenNotPaused`/`nonReentrant` only, and none of `onlyPool`, `onlyIfCanMint/Burn/Seize`, `SynthContext` checks, or supply caps stop dust deposits/transfers to arbitrary `onBehalfOf_`/recipients. No privileged role, oracle manipulation, or malicious infra is required.

### Recommendation
- Gate `addToDepositTokensOfAccount` writes behind an opt-in: e.g., only register on `deposit`/`_mint` initiated paths, and require recipients of raw `transfer`s to claim, or allow removal-for-anyone (`sweep` function letting anyone evict zero-value tokens they didn't add).
- Alternatively, make `debtPositionOf` skip tokens with zero effective USD value and drop `MAX_TOKENS_PER_USER` as a hard revert on registration, enforcing the cap only at deposit time for the caller's own account.

### Proof of Concept
```solidity
// Foundry fork test sketch (base/mainnet pool)
function test_DustPollutionFreezesVictim() public {
    address victim = makeAddr("victim");
    address attacker = makeAddr("attacker");

    // victim has an open position on depositTokenA
    depositFor(victim, depositTokenA, 1000e18);
    borrowFor(victim, ...);

    // attacker fills victim's collateral set to MAX_TOKENS_PER_USER
    for (uint i; i < depositTokens.length; ++i) {
        IDepositToken dt = depositTokens[i];
        if (dt == depositTokenA || dt.balanceOf(victim) > 0) continue;
        deal(address(dt.underlying()), attacker, 1);
        vm.startPrank(attacker);
        dt.underlying().approve(address(dt), 1);
        dt.deposit(1, victim); // or dt.transfer(victim, 1)
        vm.stopPrank();
        if (pool.getDepositTokensOfAccount(victim).length == MAX) break;
    }

    // victim can no longer deposit a new collateral type to save the position
    vm.prank(victim);
    vm.expectRevert(); // MaxTokensPerUser / addToDepositTokensOfAccount revert
    depositTokenB.deposit(100e18, victim);

    // and cannot even receive a transfer of a new msdTOKEN
    vm.prank(attacker);
    vm.expectRevert();
    depositTokenC.transfer(victim, 1);
}
```

Caveat: I verified the write side in `DepositToken._transfer`/`_mint` and confirmed `MAX_TOKENS_PER_USER`/`addToDepositTokensOfAccount` exist in `Pool.sol` via search, but the index did not return the exact revert line in `Pool.sol` — the PoC should be run against the deployed fork to confirm the revert reason and the cap value.
