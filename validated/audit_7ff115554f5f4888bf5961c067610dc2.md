### Title
Unauthenticated `/proposal_response` endpoint on the signer's event listener allows remote forgery of block-validation verdicts - (File: `libsigner/src/events.rs`)

### Summary
The signer's `SignerEventReceiver::next_event` dispatches any `POST /proposal_response` body directly into `process_event::<T, BlockValidateResponse>`, which JSON-deserializes the body into a `BlockValidateResponse` and forwards it unchanged as `SignerEvent::BlockValidationResponse` via `TryFrom<BlockValidateResponse>`. There is no signature, secret, or peer-identity check tying this payload to the local node's actual `/v3/block_proposal` validation result.

### Finding Description
`SignerEventReceiver::next_event` (`libsigner/src/events.rs:413-458`) routes any HTTP POST to `/proposal_response` into `process_event::<T, BlockValidateResponse>(request)` (`events.rs:439-440`). `process_event` (`events.rs:519-542`) reads the raw request body, deserializes it with `serde_json::from_slice::<BlockValidateResponse>`, and calls `.try_into()`. The `TryFrom<BlockValidateResponse> for SignerEvent<T>` impl (`events.rs:627-635`) does nothing but wrap the parsed struct into `SignerEvent::BlockValidationResponse(block_validate_response)` — no signature check, no correlation to a `submitted_block_proposal` token, no source-authentication of any kind at this layer.

That event is then forwarded via `forward_event` (`events.rs:469-489`) straight to the runloop channel, where `Signer::handle_event_match` calls `handle_block_validate_response` (`stacks-signer/src/v0/signer.rs:2054-2080`), which trusts the verdict (`Ok`/`Reject`) to drive `handle_block_validate_ok`/`handle_block_validate_reject`, `mark_pre_committed`, `send_block_pre_commit`, etc. (`stacks-signer/src/v0/signer.rs:1888-1984`).

This is intended to only be reachable from the local stacks-node's event-observer dispatch (`stacks-node/src/event_dispatcher.rs:202-229`, `ProposalCallbackHandler::notify_proposal_result`), which is only invoked internally after real block validation (`stackslib/src/net/api/postblock_proposal.rs:347-382`). However, **nothing in `libsigner/src/events.rs` enforces that the HTTP connection to this listener actually comes from that trusted local dispatcher** — the code only checks HTTP method and URL path, not source, not any shared secret/HMAC, not TLS client cert. The bind address for this listener is configured by the operator (`endpoint` in the signer's TOML config, read in `stacks-signer/src/config.rs`); if it is bound to a non-loopback interface (which the config format permits and is common in multi-host signer deployments where the node and signer run on separate hosts), any remote party that can reach that TCP port can POST a forged `BlockValidateResponse` body and have it accepted verbatim.

This breaks the intended equality: "verdict delivered to runloop == verdict this node's validator actually computed." An attacker who can reach the port can set that equality false at will, injecting a fabricated `Ok(BlockValidateOk{...})` or `Reject(...)` for any `signer_signature_hash` value, without ever winning a sortition, running a validator, or holding any signing key.

### Impact Explanation
An attacker with network reachability to the signer's event-listener port can:
- Force `handle_block_validate_ok` to be invoked for a block hash of their choosing even when no corresponding submitted proposal exists (it is dropped harmlessly if the hash isn't tracked in `submitted_block_proposal`/`signer_db`, per the `block_lookup_by_reward_cycle` guard at `signer.rs:1915-1919`), or — more critically — race/spoof the verdict for a block hash the signer *is* currently tracking, causing the signer to `mark_pre_committed` and broadcast a pre-commit (`send_block_pre_commit`) or to `mark_locally_rejected` and broadcast a rejection over StackerDB, based on a value that never came from the actual node validation.
- This is a forged-message injection into the signer's local decision pipeline that can result in network-relayed forged pre-commit/rejection messages being gossiped to other signers over StackerDB, affecting consensus liveness/safety signals — matching the "unauthenticated/unauthorized write to state" and "network-wide propagation of forged data" Critical categories, contingent on the listener being reachable and a matching in-flight proposal hash being guessed/known (block hashes are public/observable via StackerDB miner messages, so this is not a strong barrier).
- Each POST is a fully independent, repeatable operation with no rate limiting evident in `process_event`.

### Likelihood Explanation
Exploitability is entirely conditioned on the deployment topology: if the signer's `/proposal_response` listener is bound to `127.0.0.1` (loopback) as it is in the typical same-host node+signer deployment, this is not remotely reachable and the finding does not apply. The code itself, however, contains no defense-in-depth check (no shared secret, no source-IP allowlist, no signature over the payload) — the security boundary is entirely deployment-configuration dependent, resting on the operator binding the event-observer endpoint to loopback and firewalling that port. Any configuration where the signer and node communicate across a network boundary (a supported and documented pattern for running signers on separate infrastructure) exposes this endpoint to any host with L3/L4 reachability, requiring no credentials, keys, or StackerDB slot ownership. Given the block hash needed to make a "live" injection (rather than a dropped no-op) is observable by any StackerDB reader (miner proposals are broadcast in the clear), the practical precondition beyond reachability is low.

### Recommendation
Authenticate the event-observer callback path: require a shared-secret bearer token or HMAC over the request body (verified in `process_event` or a wrapping middleware before deserialization) that only the local stacks-node's `EventDispatcher`/`ProposalCallbackHandler` possesses, and/or bind the event-observer listener to loopback by default with an explicit, documented opt-in and warning for non-loopback bindings. At minimum, reject `/proposal_response` (and the other event-observer endpoints) from non-configured/non-allowlisted source addresses at the `tiny_http` request-handling layer in `libsigner/src/events.rs`.

fn process_event<T, E>(mut request: HttpRequest) -> Result<SignerEvent<T>, EventError>
where
    T: SignerEventTrait,
    E: serde::de::DeserializeOwned + TryInto<SignerEvent<T>, Error = EventError>,
{
    let mut body = String::new();

    if let Err(e) = request.as_reader().read_to_string(&mut body) {
        error!("Failed to read body: {:?}", &e);
        ack_dispatcher(request);
        return Err(EventError::MalformedRequest(format!(
            "Failed to read body: {:?}",
            e
        )));
    }
    // Regardless of whether we successfully deserialize, we should ack the dispatcher so they don't keep resending it
    ack_dispatcher(request);
    let json_event: E = serde_json::from_slice(body.as_bytes())
        .map_err(|e| EventError::Deserialize(format!("Could not decode body to JSON: {:?}", e)))?;

    let signer_event: SignerEvent<T> = json_event.try_into()?;

    Ok(signer_event)
}
