### Title
`extend_with_attachments` accepts an `Attachment` from an untrusted peer without verifying `attachment.hash() == request.content_hash` - (File: stackslib/src/net/atlas/download.rs)

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` decodes a peer's HTTP response into a `GetAttachmentResponse` and unconditionally inserts `response.attachment` into `self.attachments`, without ever comparing `response.attachment.hash()` to the `request.content_hash` that was requested. This lets any peer serving `/v2/attachments/{hash}` supply arbitrary bytes for a hash it never actually holds.

### Finding Description
The claimed equality — `attachment.hash() == request.content_hash` — is never checked. In `extend_with_attachments`: [1](#0-0) 

the loop drains `results.succeeded`, decodes the response via `response.decode_atlas_get_attachment()`, and on success calls `self.attachments.insert(response.attachment)` directly — there is no `if response.attachment.hash() == request.content_hash` guard anywhere in this function, and no such check was found in `decode_atlas_get_attachment` or the surrounding request-construction code (`get_prioritized_attachments_requests`, lines 404-478, which only records `content_hash` as the key to request, not as a value later re-verified against the response).

The attacker's exact message: any peer that is selected as a source in `AttachmentRequest.sources` (any peer that advertises the attachment bit set in its inventory, `download.rs:434-459`) can respond to the outbound `GET /v2/attachments/{content_hash}` with a `GetAttachmentResponse` containing `attachment.content` bytes that do **not** hash to `content_hash`. `extend_with_attachments` will still store this forged `Attachment` object into `self.attachments`, and the reliability report is bumped as a **successful** request (`report.bump_successful_requests()`), rewarding the malicious peer's reliability score.

Because the mismatch is never detected, the requesting node will treat the attachment for that `content_hash` as resolved (the batch bookkeeping in `attachments_batch.attachments_instances` uses `content_hash` as the value to match against, but the actual bytes stored have never been checked against it) — this can (a) cause the true, correct attachment to never be re-requested since the slot is considered filled, and (b) if this stored/forged attachment later flows into BNS resolution or is served via Atlas/BNS lookups, the node serves attacker-chosen bytes under a hash the chain never actually committed to.

### Impact Explanation
- A single remote, unprivileged peer (anyone who can stand up an HTTP server on the P2P/RPC-reachable network and be selected as an attachment source) can poison a victim node's Atlas attachment cache with content that does not match the canonical hash.
- This is a High-impact "attachment/BNS mismatch" as explicitly called out in scope: canonical hash-committed data is replaced by attacker-controlled bytes with no cryptographic tie to the chain state, and/or the genuine attachment is permanently marked resolved and never fetched from a correct source.
- Repeatable: this can be done for every attachment request the peer is asked to serve, and the fake success also inflates the peer's reliability score, biasing future selection toward the malicious peer.

### Likelihood Explanation
- Precondition: the attacker's peer must be listed among `sources` for the `AttachmentRequest`, which merely requires the peer's advertised attachments inventory bit to be set for the relevant page/position (`download.rs:434-459`) — no privileged role, secret, or slot ownership is required; any peer participating in Atlas attachment inventory gossip can claim to have the attachment.
- Attacker cost is minimal: run a normal Atlas-participating peer and answer with forged content.
- No signature, MAC, or length check exists in this path that would otherwise catch the mismatch before `self.attachments.insert(...)`.

### Recommendation
In `extend_with_attachments` (`stackslib/src/net/atlas/download.rs:547-552`), after decoding the response, verify `response.attachment.hash() == request.content_hash` before inserting; on mismatch, treat it as a failed request (`report.bump_failed_requests()`) and optionally penalize/deregister the offending peer, mirroring how a hash-mismatched attachment should never enter `self.attachments` or be marked resolved in `attachments_batch.attachments_instances`.

### Proof of Concept
Add a test in `stackslib/src/net/atlas/download.rs` (or `tests.rs`) that:
1. Constructs an `AttachmentRequest` with a known `content_hash` (e.g., hash of `b"real"`).
2. Constructs a `BatchedRequestsResult<AttachmentRequest>` whose `succeeded` map pairs that request with a `GetAttachmentResponse` wrapping an `Attachment` built from different bytes, e.g. `Attachment::new(b"forged".to_vec())`, whose `.hash()` differs from `content_hash`.
3. Calls `AttachmentsBatchStateContext::extend_with_attachments(ctx, &mut results)`.
4. Asserts that `ctx.attachments` contains the forged `Attachment` (i.e., `ctx.attachments.iter().any(|a| a.content == b"forged")` is `true`) despite `attachment.hash() != content_hash`, and that `report.bump_successful_requests()` was invoked for the malicious peer — demonstrating the missing equality check at `download.rs:547-552`.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
