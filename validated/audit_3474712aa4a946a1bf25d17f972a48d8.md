Confirmed: `Serve` runs `go c.serve()` per accepted connection with no `recover()` anywhere in the call chain (`serve` → `handleRecord` → `parseParams`), so an unrecovered panic in `parseParams` crashes that goroutine and, since panics in goroutines are fatal to the whole program in Go, takes down the entire FastCGI child process/server.

### Title
Integer-overflow-driven slice-bounds panic in FastCGI child parameter parsing on 32-bit architectures - ([File: src/net/http/fcgi/child.go])

### Summary
`request.parseParams` in `src/net/http/fcgi/child.go` validates attacker-supplied `keyLen`/`valLen` FastCGI PARAMS fields with `int(keyLen)+int(valLen) > len(text)`. On platforms where `int` is 32 bits (`GOARCH=386`, `arm`, `mips`, etc.), two crafted lengths near `math.MaxInt32` overflow this signed addition and wrap to a negative value, causing the bounds check to spuriously pass. The subsequent `text = text[keyLen:]` reslice then panics with "slice bounds out of range", and because `Serve` runs `c.serve()` in an unrecovered goroutine, this crashes the whole process. [1](#0-0) [2](#0-1) 

### Finding Description
Attacker input: a peer connecting to the FastCGI socket (or a compromised/untrusted front end) sends a `typeParams` record whose body is decoded by `readSize`, which for 4-byte encoded sizes only masks off the top bit, allowing values up to `0x7FFFFFFF` (2147483647) for both `keyLen` and `valLen`. [3](#0-2) 

Entry point: `child.handleRecord` accumulates PARAMS bytes and calls `req.parseParams()` once the terminating empty PARAMS record arrives. [4](#0-3) 

Failed check: in `parseParams`, the guard `if int(keyLen)+int(valLen) > len(text) { return }` is supposed to reject lengths exceeding the remaining buffer. On 32-bit `int`, `int(keyLen)+int(valLen)` for two near-max values wraps to a negative number, so the comparison against `len(text)` (non-negative) is false and the check is bypassed. [5](#0-4) 

Sink: `readString(text, keyLen)` itself safely returns `""` because it independently checks `size > uint32(len(s))`, but the immediately following `text = text[keyLen:]` re-slices `text` using the raw, unvalidated `keyLen` (up to ~2^31), which exceeds `len(text)` and triggers a runtime panic ("slice bounds out of range"). [6](#0-5) [7](#0-6) 

This is the closest Go analog to CVE-2025-23016's fcgiapp.c `ReadParams` integer overflow: both stem from unchecked/overflowing length arithmetic on attacker-controlled name/value lengths in FastCGI PARAMS parsing, though Go's memory-safe slices turn the corrupted bounds into a panic rather than a heap overflow.

### Impact Explanation
On 32-bit architectures, a remote peer able to send a crafted FastCGI PARAMS record can crash the FastCGI child process (denial of service) because the panic occurs in a goroutine spawned by `Serve` with no `recover`, which is fatal to the entire process, not just the connection. [2](#0-1)  On 64-bit architectures (`amd64`, `arm64`), `int` is 64 bits, so `int(keyLen)+int(valLen)` (max ~2^32) cannot overflow and the check works correctly — the bug is architecture-specific. This would likely be assessed on Go's PUBLIC track as a low-severity, narrowly-scoped DoS (affecting only 32-bit builds of a legacy, rarely internet-exposed protocol handler), not a memory-corruption or code-execution issue.

### Likelihood Explanation
Exploitability requires: (1) the FastCGI child socket being reachable by an untrusted party (uncommon in typical nginx/Apache-fronted deployments, but possible if directly exposed or if the front end forwards arbitrary attacker-influenced lengths), and (2) the process running on a 32-bit `GOARCH`. Both constraints substantially reduce real-world likelihood compared to the original C CVE, which affected any architecture via a true heap buffer overflow.

### Recommendation
Change the overflow check in `parseParams` to avoid signed-integer wraparound regardless of platform `int` size, e.g. compare using `uint64(keyLen)+uint64(valLen) > uint64(len(text))`, and treat any out-of-range value as a malformed/terminated parameter stream rather than proceeding to reslice `text`.

```go
package fcgi

import (

	"io"

// Simulates the overflow on a 32-bit int by using values that a 386/arm build
// would parse via readSize as ~0x7FFFFFFF each, which currently is guarded only
// by an "int" sized addition — this test documents the 64-bit-safe path and
// should be adapted to GOARCH=386 to observe the panic in slice re-slicing.
func TestMalformedParamsHugeLen(t *testing.T) {
	b := make([]byte, 4)
	binary.BigEndian.PutUint32(b, 0x7FFFFFFF) // keyLen encoded, top bit cleared by readSize
	b2 := make([]byte, 4)
	binary.BigEndian.PutUint32(b2, 0x7FFFFFFF) // valLen encoded
	body := append(append([]byte{}, b...), b2...)
	body = append(body, []byte("short")...) // far shorter than declared lengths

	input := bytes.Join([][]byte{
		makeRecord(typeBeginRequest, 1, []byte{0, byte(roleResponder), 0, 0, 0, 0, 0, 0}),
		makeRecord(typeParams, 1, body),
		makeRecord(typeParams, 1, nil),
	}, nil)

	rw := rwNopCloser{bytes.NewReader(input), io.Discard}
	c := newChild(rw, http.DefaultServeMux)
	c.serve() // on 32-bit int platforms, expect panic: slice bounds out of range
}
```
Expected assertion (on `GOARCH=386`/`arm`): the process panics with "slice bounds out of range" inside `parseParams`'s `text = text[keyLen:]`, uncaught by any `recover`, terminating the process — confirming the bypassed length check. On 64-bit platforms this test passes without panic, illustrating the architecture-dependent nature of the flaw.

```go
	}
}
```

```go
func readSize(s []byte) (uint32, int) {
	if len(s) == 0 {
		return 0, 0
	}
	size, n := uint32(s[0]), 1
	if size&(1<<7) != 0 {
		if len(s) < 4 {
			return 0, 0
		}
		n = 4
		size = binary.BigEndian.Uint32(s)
		size &^= 1 << 31
	}
	return size, n
}
```
