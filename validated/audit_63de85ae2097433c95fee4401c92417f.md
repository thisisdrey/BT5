### Title
Cost model reserves block/account cost budget by user-declared `compute_unit_limit` rather than actual usage, letting an attacker grief/censor legitimate transactions at negligible cost - ([File: cost-model/src/cost_model.rs])

### Summary
The Optimism report's root cause is that `ResourceMetering` charges/limits based on the *requested* resource amount (`gasLimit`) rather than actual usage, and the cost of buying that requested amount is decoupled from the harm it can do to other users' ability to get included. Agave has a structurally analogous pattern: `CostModel::get_estimated_execution_cost` sets `programs_execution_cost` equal to the transaction's *declared* `compute_unit_limit` (from `SetComputeUnitLimit`), not the CU actually consumed, and this pre-execution estimate is what gets reserved against the per-account and per-block cost limits (`MAX_WRITABLE_ACCOUNT_UNITS`, `MAX_BLOCK_UNITS`) used by the leader's scheduler to decide which transactions get packed into a block.

### Finding Description
`CostModel::get_estimated_execution_cost` derives the "programs execution cost" straight from the transaction's requested `compute_unit_limit` sanitized out of `ComputeBudgetInstruction`: [1](#0-0) 

This estimate feeds `CostModel::calculate_cost`, which is the function used by the scheduler at admission/scheduling time (before the transaction is executed) to compute `TransactionCost.sum()`: [2](#0-1) 

The `GreedyScheduler` consumes exactly this pre-execution cost to decrement its available `budget` when deciding whether a transaction can be scheduled onto a thread for the current slot: [3](#0-2) 

The `CostTracker`/`would_fit` logic likewise gates inclusion on the requested-CU-based `tx_cost.sum()` against `MAX_WRITABLE_ACCOUNT_UNITS` (24,000,000 CU per account) and `MAX_BLOCK_UNITS` (60,000,000 CU per block): [4](#0-3) [5](#0-4) 

Crucially, the fee actually paid for a transaction does **not** scale with the declared `compute_unit_limit` unless the user also sets a non-zero `compute_unit_price` (priority fee). `get_prioritization_fee` multiplies `compute_unit_price * compute_unit_limit`; if `compute_unit_price == 0`, the prioritization fee is zero regardless of how large `compute_unit_limit` is: [6](#0-5) 

A transaction can therefore request up to `MAX_COMPUTE_UNIT_LIMIT` while setting `compute_unit_price = 0`, paying only the flat base signature fee, and still have its full declared CU limit reserved against the shared per-account (`MAX_WRITABLE_ACCOUNT_UNITS = 24_000_000`) and per-block (`MAX_BLOCK_UNITS = 60_000_000`) cost budgets for the purposes of admission/scheduling. Only *after* the transaction actually executes and commits does the reservation get corrected down to the real usage via `add_transaction_execution_cost`/`sub_transaction_execution_cost` adjustment: [7](#0-6) [8](#0-7) 

This is confirmed by the test suite documenting that the *reservation* happens using the requested CU limit and only gets "adjusted" post-execution: [9](#0-8) 

This is the same class of flaw as the Optimism bug: the resource-consumption accounting used to gate/throttle other participants is based on a user-supplied "maximum" value rather than actual cost, and the price paid for declaring that maximum is not tied to the harm/blocking-capacity it grants. In Optimism's case the attacker buys `MAX_RESOURCE_LIMIT` gas cheaply and blocks a victim's deposit for that block; in Agave, an attacker can flood transactions declaring near-maximum `compute_unit_limit` against a specific hot account (or against overall block capacity) while paying only the flat base fee, saturating the account-level (`MAX_WRITABLE_ACCOUNT_UNITS`) or block-level (`MAX_BLOCK_UNITS`) reservation for the scheduling pass before the correction/adjustment for those specific transactions is applied, crowding out legitimate transactions targeting the same account/slot that the leader's `GreedyScheduler` would otherwise have scheduled.

### Impact Explanation
This undermines the fairness/censorship-resistance goals of Solana's fee-market/QoS design: the per-account cost cap (`MAX_WRITABLE_ACCOUNT_UNITS`) exists specifically "to prevent too many transactions [from writing] to same account, therefore reduc[ing a] block's parallelism," and priority fees are supposed to be the mechanism by which real contention for block space is priced. By declaring a high `compute_unit_limit` with zero `compute_unit_price`, an attacker gets the account/block cost-reservation weight of a "worst case" transaction while paying the price of a trivial one, letting them grief specific accounts or exhaust scheduling budget for a slot at a cost far below the value of the block space/inclusion priority they deny to others. This does not corrupt consensus state (post-execution adjustment eventually corrects the persisted cost tracker value), but it can prevent legitimate transactions competing for the same account or slot from being scheduled by that leader, which is a real, if temporary, availability/censorship-resistance degradation — directly analogous to the reported impact ("bridging of assets can be DOSed at low cost").

### Likelihood Explanation
Any unprivileged user with a funded fee-payer account and network access to a validator's TPU/QUIC ingest can construct such transactions; no special stake or privilege is required beyond normal QUIC/stake-weighted QoS admission (which limits packet throughput but not the CU-limit-vs-price disconnect). The attack only requires setting `SetComputeUnitLimit` high and `SetComputeUnitPrice` to zero (or minimal), which is standard, unrestricted `ComputeBudgetInstruction` usage. The economic cost is bounded by the flat per-signature fee (`SIGNATURE_COST`/`lamports_per_signature`), independent of the declared CU limit, so the attack scales cheaply with the number of transactions submitted.

### Recommendation
Tie the pre-execution/admission-time cost reservation more tightly to the fee actually paid, e.g., require a minimum `compute_unit_price` proportional to the requested `compute_unit_limit` (so that reserving a large slice of `MAX_WRITABLE_ACCOUNT_UNITS`/`MAX_BLOCK_UNITS` costs proportionally more), or shorten/eliminate the window in which the un-adjusted, request-based cost is used for scheduling decisions by preferring the adjusted/actual cost sooner within a scheduling pass. This mirrors the original report's own recommendation to decouple/close the gap between "cost to acquire the reservation" and "value of the reservation to the network."

### Proof of Concept
Conceptually (not executed, since this is a static code analog rather than a live exploit trace):
1. Attacker submits N transactions each containing `ComputeBudgetInstruction::set_compute_unit_limit(MAX_COMPUTE_UNIT_LIMIT)` and `ComputeBudgetInstruction::set_compute_unit_price(0)`, all write-locking the same target account (the one the victim's transaction also writes to).
2. Each such transaction's `CostModel::calculate_cost` reports `programs_execution_cost = MAX_COMPUTE_UNIT_LIMIT` (per [1](#0-0) ), and this value is what the `GreedyScheduler`/`CostTracker` use to gate/deduct scheduling budget and per-account cost (per [3](#0-2)  and [4](#0-3) ).
3. Because `compute_unit_price = 0`, each attacker transaction pays only the flat base signature fee (per [6](#0-5) ), so `MAX_WRITABLE_ACCOUNT_UNITS` (24,000,000 CU) can be exhausted for that account with roughly `24,000,000 / MAX_COMPUTE_UNIT_LIMIT` transactions at flat-fee cost each.
4. Until the post-execution adjustment (per [7](#0-6) ) corrects the reservation down to actual usage, the victim's transaction touching the same account is rejected/deferred by the cost tracker/scheduler (`WouldExceedMaxAccountCostLimit`), even though the attacker's transactions ultimately consume little real compute.

Because I could not fully trace the exact micro-timing of when `try_add`/adjustment occurs relative to each subsequent transaction within a single scheduling pass (this requires deeper tracing through `consumer.rs`/`transaction_execution.rs` batch-processing order than the available index excerpts show), the precise per-slot magnitude of the exploitable window is not fully verified from the available code and should be confirmed with a live/local-cluster test before treating this as a fully proven, high-severity finding.

    /// Return (programs_execution_cost, loaded_accounts_data_size_cost)
    fn get_estimated_execution_cost(
        transaction: &impl TransactionMeta,
        feature_set: &FeatureSet,
    ) -> (u64, u64) {
        // if failed to process compute_budget instructions, the transaction will not be executed
        // by `bank`, therefore it should be considered as no execution cost by cost model.
        let (programs_execution_costs, loaded_accounts_data_size_cost) =
            match transaction.transaction_configuration(feature_set) {
                Ok(config) => (
                    u64::from(config.compute_unit_limit),
                    Self::calculate_loaded_accounts_data_size_cost(
                        config.loaded_accounts_data_size_limit,
                        feature_set,
                    ),
                ),
                Err(_) => (0, 0),
            };

        (programs_execution_costs, loaded_accounts_data_size_cost)
    }

    fn would_fit(
        &self,
        tx_cost: &TransactionCost<impl TransactionWithMeta>,
    ) -> Result<(), CostTrackerError> {
        let cost: u64 = tx_cost.sum();

        if self.block_cost().saturating_add(cost) > self.limits.block_cost {
            // check against the total package cost
            return Err(CostTrackerError::WouldExceedBlockMaxLimit);
        }

        // check if the transaction itself is more costly than the account_cost_limit
        if cost > self.limits.account_cost {
            return Err(CostTrackerError::WouldExceedAccountMaxLimit);
        }

        let allocated_accounts_data_size =
            self.allocated_accounts_data_size + Saturating(tx_cost.allocated_accounts_data_size());

        if allocated_accounts_data_size.0 > self.limits.allocated_data_size {
            return Err(CostTrackerError::WouldExceedAccountDataBlockLimit);
        }

        // check each account against account_cost_limit,
        for account_key in tx_cost.writable_accounts() {
            match self.cost_by_writable_accounts.get(account_key) {
                Some(chained_cost) => {
                    if chained_cost.saturating_add(cost) > self.limits.account_cost {
                        return Err(CostTrackerError::WouldExceedAccountMaxLimit);
                    } else {
                        continue;
                    }
                }
                None => continue,
            }
        }

        Ok(())
    }

    /// Apply additional actual execution units to cost_tracker
    /// Return the costliest account cost that were updated by `TransactionCost`
    fn add_transaction_execution_cost(
        &mut self,
        tx_cost: &TransactionCost<impl TransactionWithMeta>,
        adjustment: u64,
    ) -> u64 {
        let mut costliest_account_cost = 0;
        for account_key in tx_cost.writable_accounts() {
            let account_cost = self
                .cost_by_writable_accounts
                .entry(*account_key)
                .or_insert(0);
            *account_cost = account_cost.saturating_add(adjustment);
            costliest_account_cost = costliest_account_cost.max(*account_cost);
        }
        self.block_cost.fetch_add(adjustment);

        costliest_account_cost
    }

fn get_prioritization_fee(compute_unit_price: u64, compute_unit_limit: u64) -> u64 {
    let micro_lamport_fee: MicroLamports =
        (compute_unit_price as u128).saturating_mul(compute_unit_limit as u128);
    micro_lamport_fee
        .saturating_add(MICRO_LAMPORTS_PER_LAMPORT.saturating_sub(1) as u128)
        .checked_div(MICRO_LAMPORTS_PER_LAMPORT as u128)
        .and_then(|fee| u64::try_from(fee).ok())
        .unwrap_or(u64::MAX)
}

fn check_block_cost_limits<Tx: TransactionWithMeta>(
    bank: &Bank,
    tx_costs: &[Option<TransactionCost<'_, Tx>>],
) -> TransactionResult<()> {
    let mut cost_tracker = bank.write_cost_tracker().unwrap();
    for tx_cost in tx_costs.iter().flatten() {
        cost_tracker
            .try_add(tx_cost)
            .map_err(TransactionError::from)?;
    }

    Ok(())
}

// Get actual transaction execution costs from transaction commit results
fn get_transaction_costs<'a, Tx: TransactionWithMeta>(
    bank: &Bank,
    commit_results: &[TransactionCommitResult],
    sanitized_transactions: &'a [Tx],
) -> Vec<Option<TransactionCost<'a, Tx>>> {
    assert_eq!(sanitized_transactions.len(), commit_results.len());

    commit_results
        .iter()
        .zip(sanitized_transactions)
        .map(|(commit_result, tx)| {
            if let Ok(committed_tx) = commit_result {
                Some(CostModel::calculate_cost_for_executed_transaction(
                    tx,
                    committed_tx.executed_units,
                    committed_tx.loaded_account_stats.loaded_accounts_data_size,
                    &bank.feature_set,
                ))
            } else {
                None
            }
        })
        .collect()
}
