## Title
Division-Before-Multiplication Precision Loss in Witness Reward/Brokerage Calculation - (File: chainbase/src/main/java/org/tron/core/service/MortgageService.java)

### Summary
`MortgageService.payReward` and `MortgageService.payStandbyWitness` compute reward shares by performing floating-point division first and then multiplying by the total amount, exactly matching the "division before multiplication" precision-loss pattern described in the referenced report. Because this logic executes on every block reward and every standby-witness payout cycle, the resulting truncation errors accumulate across the chain's continuous reward-distribution path.

### Finding Description
In `payReward`, the brokerage (SR commission) amount is computed as:
```java
double brokerageRate = (double) brokerage / 100;
long brokerageAmount = (long) (brokerageRate * value);
``` [1](#0-0) 

Here `brokerage / 100` is computed and truncated to a `double` fraction before being multiplied by `value`, instead of computing `brokerage * value / 100` first. The equivalent flaw exists in `payStandbyWitness`, which computes `eachVotePay = totalPay / voteSum` (division) and then multiplies by each witness's vote count:
```java
double eachVotePay = (double) totalPay / voteSum;
for (WitnessCapsule w : witnessStandbys) {
  long pay = (long) (w.getVoteCount() * eachVotePay);
``` [2](#0-1) 

`payReward` is invoked from `payBlockReward` and `payTransactionFeeReward`, both called during Manager's per-block application logic to distribute block rewards and transaction fees to the block-producing witness. `MortgageService.computeReward` (legacy reward algorithm path, still reachable when `beginCycle < newAlgorithmCycle` or when `allowOldRewardOpt` is disabled) exhibits the same pattern:
```java
double voteRate = (double) userVote / totalVote;
reward += voteRate * totalReward;
``` [3](#0-2) 

This contrasts with the newer VI-based reward computation elsewhere in the same class, which correctly performs multiplication before division using `BigInteger`:
```java
reward += deltaVi.multiply(BigInteger.valueOf(userVote))
    .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
``` [4](#0-3) 

### Impact Explanation
`payReward` fires on every block produced (block reward + transaction fee reward), so the division-before-multiplication truncation is repeated continuously by the block-application logic in `Manager`, which the scope explicitly identifies as a reachable path. Over time, the sum of brokerage amounts and per-witness standby payouts computed via this pattern diverges from the mathematically correct proportional split (`brokerage * value / 100` or `totalPay * voteCount / voteSum`), silently misallocating small amounts between the reward pool credited to voters (`delegationStore.addReward`) and the SR's allowance (`adjustAllowance`). This is a systemic, protocol-wide accounting drift analogous to the referenced report's "protocol accumulates bad debt" impact, since the discrepancy compounds across every block and cycle rather than affecting a single isolated transaction.

### Likelihood Explanation
This code path executes unconditionally on every block (`payBlockReward`/`payTransactionFeeReward`) and every witness-standby payout cycle (`payStandbyWitness`), with no attacker interaction required — it is a deterministic, continuously-triggered accounting bug rather than an exploit requiring privileged access. It is not classified as a malicious-SR/witness scenario because it is triggered by normal, honest block production and reward maintenance, not by adversarial SR behavior.

### Recommendation
Reorder the arithmetic to multiply before dividing, and use integer/`BigInteger` arithmetic instead of `double` to avoid floating-point precision loss, mirroring the pattern already used in `computeReward`'s VI-based branch:
```java
long brokerageAmount = BigInteger.valueOf(value)
    .multiply(BigInteger.valueOf(brokerage))
    .divide(BigInteger.valueOf(100)).longValueExact();
```
Apply the same fix to `eachVotePay`/`pay` computation in `payStandbyWitness` and to `voteRate`/`reward` in the legacy `computeReward(cycle, votes)` overload.

### Proof of Concept
Given `brokerage = 33` (33%) and `value = 100` (sun):
- Correct calculation: `33 * 100 / 100 = 33`.
- Buggy calculation: `brokerageRate = 33.0/100 = 0.33` (exact here, but for values like `brokerage = 1`, `value = 299`): correct `1*299/100 = 2` (integer division), buggy `(double)1/100 = 0.01`, `0.01 * 299 = 2.99 -> (long) 2` — matches in this case, but for values where `double` division introduces binary-fraction rounding error (e.g., non-terminating binary fractions), the truncated `double` intermediate causes `brokerageAmount` to differ from the exact integer result by ±1 sun per call. Since `payReward` is invoked on every single block indefinitely, this ±1 sun drift accumulates across the delegation/allowance pools, producing a persistent, non-zero-sum discrepancy between total value distributed and total value deducted, as referenced in `chainbase/src/main/java/org/tron/core/service/MortgageService.java:79-87`.

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
