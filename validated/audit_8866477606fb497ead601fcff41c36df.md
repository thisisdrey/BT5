## Analysis

The reported bug class — a single-step, irreversible ownership/authority transfer with no way to validate or confirm the new owner before the change takes effect — has a direct analog in java-tron's `AccountPermissionUpdateActuator`.

### Title
Single-step, unverified `AccountPermissionUpdateContract` can permanently brick an account's owner authority - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
`AccountPermissionUpdateContract` lets an account holder replace its `owner`, `witness`, and `active` `Permission` sets in a single atomic transaction. The actuator applies `account.updatePermissions(owner, witness, actives)` immediately with no staging, pending-owner, or two-step acceptance mechanism — mirroring the exact pattern flagged in the external report (`owner = _newOwner` applied unconditionally, no confirmation step).

### Finding Description
`AccountPermissionUpdateActuator.validate()` only performs structural checks on the submitted `Permission` messages (key count bounds, distinct addresses, address format validity, threshold vs. weight sum, operations bitmap size), but never verifies that the new owner key(s) actually correspond to a private key the caller controls or can subsequently sign with: [1](#0-0) 

The change is committed unconditionally in `execute()` via a single call: [2](#0-1) 

which invokes `AccountCapsule.updatePermissions()`, overwriting the owner/witness/active permission fields directly with no rollback path: [3](#0-2) 

Because any future `AccountPermissionUpdateContract` to fix a mistake must itself be authorized under the *current* (already-changed) owner permission threshold, a single erroneous transaction — e.g., a mistyped key address, an unreachable threshold configuration, or a duplicate/typo'd key across owner and active permissions — can make the account's permission structure unrecoverable. Unlike the multisig weight/threshold checks, there is no verification that the resulting configuration is reachable by any signer the submitter actually controls.

### Impact Explanation
If the owner (and correspondingly configured active) permission keys are set to an address with no known private key, or to a threshold combination that can never be met, the account's TRX balance, delegated resources, and voting rights governed by that permission structure become permanently unusable — a permanent freezing of funds/authority with no recovery path, since the very actuator needed to correct the mistake requires the broken permission to authorize it.

### Likelihood Explanation
This requires only a single signed transaction from the account owner (which multisig account setups actively encourage constructing off-chain, increasing the chance of transcription/config errors), matching the same “typo/misconfiguration causes irreversible loss of control” likelihood profile described in the original report. Given java-tron's multisig feature is user-facing and reachable by any account holder without special privilege, the same class of accidental, irrecoverable lockout applies.

### Recommendation
Add either: (1) a validation step requiring a companion signature/proof from each new owner key demonstrating control before committing the change, or (2) a two-phase update (propose → confirm by required weight of new owner keys) analogous to the `transferOwnership`/`acceptOwnership` two-step pattern recommended in the source report, before finalizing `AccountPermissionUpdateContract`.

### Proof of Concept
1. Account A (single-key EOA) submits `AccountPermissionUpdateContract` setting `owner` permission to a `Key` with an address for which no one holds the private key (e.g., a typo of one hex character), while `actives` is likewise reconfigured to require that same key.
2. `validate()` passes all structural checks (valid address format, weight ≥ threshold) since it never checks key controllability, per `checkPermission()`: [4](#0-3) 
3. `execute()` commits the change via `updatePermissions()`: [2](#0-1) 
4. Account A can no longer produce a signature satisfying the new owner/active threshold for any subsequent transaction, including a corrective `AccountPermissionUpdateContract`, permanently freezing the account's funds and permission-gated capabilities.

  private boolean checkPermission(Permission permission) throws ContractValidateException {
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    if (permission.getKeysCount() > dynamicStore.getTotalSignNum()) {
      throw new ContractValidateException("number of keys in permission should not be greater "
          + "than " + dynamicStore.getTotalSignNum());
    }
    if (permission.getKeysCount() == 0) {
      throw new ContractValidateException("key's count should be greater than 0");
    }
    if (permission.getType() == PermissionType.Witness && permission.getKeysCount() != 1) {
      throw new ContractValidateException("Witness permission's key count should be 1");
    }
    if (permission.getThreshold() <= 0) {
      throw new ContractValidateException("permission's threshold should be greater than 0");
    }
    String name = permission.getPermissionName();
    if (!StringUtils.isEmpty(name) && name.length() > 32) {
      throw new ContractValidateException("permission's name is too long");
    }
    //check owner name ?
    if (permission.getParentId() != 0) {
      throw new ContractValidateException("permission's parent should be owner");
    }

    long weightSum = 0;
    List<ByteString> addressList = permission.getKeysList()
        .stream()
        .map(x -> x.getAddress())
        .distinct()
        .collect(toList());
    if (addressList.size() != permission.getKeysList().size()) {
      throw new ContractValidateException(
          "address should be distinct in permission " + permission.getType());
    }
    for (Key key : permission.getKeysList()) {
      if (!DecodeUtil.addressValid(key.getAddress().toByteArray())) {
        throw new ContractValidateException("key is not a validate address");
      }
      if (key.getWeight() <= 0) {
        throw new ContractValidateException("key's weight should be greater than 0");
      }
      try {
        weightSum = addExact(weightSum, key.getWeight());
      } catch (ArithmeticException e) {
        throw new ContractValidateException(e.getMessage());
      }
    }
    if (weightSum < permission.getThreshold()) {
      throw new ContractValidateException(
          "sum of all key's weight should not be less than threshold in permission " + permission
              .getType());
    }

  public void updatePermissions(Permission owner, Permission witness, List<Permission> actives) {
    Builder builder = this.account.toBuilder();

    owner = owner.toBuilder().setId(0).build();
    builder.setOwnerPermission(owner);
    if (witness != null && builder.getIsWitness()) {
      witness = witness.toBuilder().setId(1).build();
      builder.setWitnessPermission(witness);
    }

    builder.clearActivePermission();
    if (actives != null) {
      for (int i = 0; i < actives.size(); i++) {
        Permission permission = actives.get(i).toBuilder().setId(i + 2).build();
        builder.addActivePermission(permission);
      }
    }

    this.account = builder.build();
  }
