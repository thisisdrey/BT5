### Title
Vesting `distribute` DOS via `set_allow_direct_coin_transfers(false)` — (`aptos-move/framework/aptos-framework/sources/vesting.move`)

---

### Summary

The `distribute` function in `vesting.move` uses a push-based mechanism to send APT to every shareholder in a single atomic transaction. Any shareholder whose address has `allow_arbitrary_coin_transfers = false` and no legacy `CoinStore<AptosCoin>` registered will cause `aptos_account::deposit_coins` to abort, reverting the entire transaction and permanently blocking all other shareholders from receiving their vested funds until admin intervention.

---

### Finding Description

`vesting::distribute` is a `public entry fun` callable by anyone:

```move
// vesting.move lines 730-740
let grant_pool = &vesting_contract.grant_pool;
let shareholders = &grant_pool.shareholders();
shareholders.for_each_ref(|shareholder| {
    let shareholder = *shareholder;
    ...
    let recipient_address = get_beneficiary(vesting_contract, shareholder);
    aptos_account::deposit_coins(recipient_address, share_of_coins);  // <-- push
});
``` [1](#0-0) 

`aptos_account::deposit_coins` contains the abort path:

```move
// aptos_account.move lines 123-127
if (!coin::is_account_registered<CoinType>(to)) {
    assert!(
        can_receive_direct_coin_transfers(to),
        error::permission_denied(EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS)
    );
``` [2](#0-1) 

`can_receive_direct_coin_transfers` returns `false` when the account has explicitly called `set_allow_direct_coin_transfers(false)`:

```move
// aptos_account.move lines 226-231
public fun can_receive_direct_coin_transfers(account: address): bool acquires DirectTransferConfig {
    !exists<DirectTransferConfig>(account)
        || borrow_global<DirectTransferConfig>(account).allow_arbitrary_coin_transfers
}
``` [3](#0-2) 

`set_allow_direct_coin_transfers` is an unprivileged `public entry fun` any account can call: [4](#0-3) 

**Attack path:**

1. Shareholder `S` is added to a vesting contract (no APT-registration check on shareholders at creation time).
2. `S` calls `coin::migrate_to_fungible_store<AptosCoin>()`, removing their legacy `CoinStore<AptosCoin>` so `coin::is_account_registered<AptosCoin>(S)` returns `false`.
3. `S` calls `set_allow_direct_coin_transfers(false)`.
4. Any call to `distribute(contract_address)` now hits the abort at line 124–126 of `aptos_account.move` when processing `S`'s share, reverting the entire transaction.
5. Every other shareholder is blocked from receiving their vested APT.

**Partial mitigation that does NOT cover this path:**

`set_beneficiary` has a guard `assert_account_is_registered_for_apt(new_beneficiary)` that prevents setting a *beneficiary* that hasn't registered APT: [5](#0-4) 

However, this guard only applies when the admin explicitly sets a beneficiary. When no beneficiary is set, `get_beneficiary` returns the shareholder address directly, and there is **no registration check on shareholders at contract creation or at distribution time**.

The same push-distribution pattern with no guard exists in `staking_contract::distribute_internal`, which also calls `aptos_account::deposit_coins` for every recipient in a loop: [6](#0-5) 

---

### Impact Explanation

A single malicious (or misconfigured) shareholder can permanently wedge `distribute` for an entire vesting contract. All other shareholders lose access to their vested APT until the admin calls `set_beneficiary` to redirect the blocking shareholder's allocation to a cooperating address. The admin may be unresponsive, slow, or the attack can be repeated by resetting the beneficiary back. Funds are not stolen but are durably inaccessible — a permanent freeze of user-controlled staking/vesting balances.

---

### Likelihood Explanation

- `set_allow_direct_coin_transfers` is a free, unprivileged, on-chain call available to any account.
- `migrate_to_fungible_store` is also a free, unprivileged entry function.
- Vesting contracts are used for large APT grants (team, investor allocations). A single disgruntled or malicious shareholder can trigger this.
- `distribute` is callable by anyone, so the attacker does not even need to be the one calling it — they just need to have their state set up before any caller invokes `distribute`.

---

### Recommendation

Replace the push-based distribution loop with a pull mechanism: accumulate each shareholder's claimable balance in a per-address map during `distribute`, and add a separate `claim(contract_address)` entry function that each shareholder calls individually. This isolates failures to the individual claimant and prevents any single recipient from blocking others.

Alternatively, wrap each `deposit_coins` call in a way that skips failed recipients and records their unclaimed balance for later retrieval, similar to how 0xSplit handles this in the original report.

---

### Proof of Concept

```
1. Admin creates vesting contract with shareholders [Alice, Bob].
2. Bob calls: aptos_account::set_allow_direct_coin_transfers(false)
3. Bob calls: coin::migrate_to_fungible_store<AptosCoin>()
   → Bob's CoinStore<AptosCoin> is deleted; coin::is_account_registered<AptosCoin>(Bob) == false
4. After lockup expires, anyone calls: vesting::distribute(contract_address)
   → Loop reaches Bob's share
   → deposit_coins(Bob, bob_share) checks is_account_registered → false
   → checks can_receive_direct_coin_transfers(Bob) → false
   → ABORT: EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS
   → Entire transaction reverts
5. Alice receives nothing. Bob receives nothing. Funds remain locked in the vesting contract.
6. Admin must call set_beneficiary(admin, contract_address, Bob, some_other_address)
   to unblock — but Bob can repeat step 2–3 with a new address if he controls the beneficiary.
```
