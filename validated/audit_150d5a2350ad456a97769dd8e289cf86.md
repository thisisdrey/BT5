Based on the investigation, I found a strong, well-documented analog in Gitaly that matches the report's bug class: **client-controlled state that bypasses a trusted gating mechanism to gain unauthorized access**.

### Title
Client-supplied `git_object_directory`/`git_alternate_object_directories` fields bypass transaction/quarantine gating, enabling unauthorized cross-repository object access - (File: internal/gitaly/storage/storagemgr/middleware.go)

### Summary
Similar to the Fractional `Buyout.end` bug — where a privileged state (fraction balance) that should only be reachable via a gated, time-boxed function (`sellFractions`) can instead be reached by directly writing to the underlying storage (`safeTransferFrom`) — Gitaly's transaction-routing middleware treats the presence of the `Repository.git_object_directory` / `Repository.git_alternate_object_directories` proto fields as *proof* that a request legitimately originated from the trusted quarantine/access-check loop-back flow. In reality, these are plain client-settable fields on any RPC request, so any caller can set them directly, without ever having gone through the gated quarantine-creation path.

### Finding Description
`beginTransactionForRepository` decides whether to route a request through the normal transactional/partitioned path or to bypass it entirely, based solely on whether `GitObjectDirectory`/`GitAlternateObjectDirectories` are non-empty on the incoming request: [1](#0-0) 

The comment in the code explicitly acknowledges the trust assumption and its fragility: these fields "should only be configured on a repository coming from a request that was already configured with a quarantine directory and is being looped back to Gitaly from Rails' authorization checks," and admits "this property is violated in tests which manually configure the object directory... This allows for circumventing the transaction management." [2](#0-1) 

These fields are defined as ordinary, client-writable proto fields with no server-side provenance/authenticity check (e.g., no HMAC, no binding to an actual quarantine directory that Gitaly itself created): [3](#0-2) 

Once set, `GitAlternateObjectDirectories` is used directly to compose `GIT_ALTERNATE_OBJECT_DIRECTORIES`, exposing arbitrary object directories to Git commands run against the target repository: [4](#0-3) 

Path traversal outside of the storage root is blocked by `ObjectDirectoryPath`'s validation against the quarantine-prefix or repository-relative path (`ValidateRelativePath`) [5](#0-4) , but that validation only confirms the path stays within storage/quarantine boundaries — it does not confirm that the "quarantine" directory referenced was actually created by Gitaly for *this* request's actual push/authorization flow, nor that the caller is authorized to read whatever objects already happen to reside at that path (e.g., another repository's genuine object directory, or a directory the same low-privileged token can write to via a separate RPC). This mirrors the Fractional flaw: the gating check (`isTransactionQuarantineDir` / prefix match) validates *shape*, not *provenance*, exactly as `balanceOf` validated *amount* but not *how the tokens got there*.

### Impact Explanation
Because accessor RPCs (e.g. `RepositoryInfo`, `GetObjectDirectorySize`, `CommitIsAncestor`, `ObjectsSize`, blob/commit read RPCs) accept `Repository.git_object_directory`/`git_alternate_object_directories` directly on the request and are treated as "already inside a quarantine transaction" whenever those fields are non-empty [6](#0-5) , an ordinary authenticated caller who can reach any accessor RPC can point Gitaly's Git invocation at object directories it did not create through the legitimate quarantine workflow. This can be used to read objects belonging to a directory the caller should not have "quarantine" access to, sidestepping the intended design where quarantine directories are exclusively created by Gitaly itself during a push and only looped back by Rails' internal access-check API. The result is unauthorized cross-repository/cross-quarantine object disclosure and bypass of the state machine that is supposed to gate mutator/transaction routing, analogous to how Alice bypassed the `PROPOSAL_PERIOD`-gated `sellFractions` deposit path in the smart-contract report.

### Likelihood Explanation
Reachable directly from a standard authenticated gRPC client: the `Repository` message and its `git_object_directory`/`git_alternate_object_directories` fields are ordinary, unauthenticated-content proto fields settable in any request without needing to go through git-receive-pack or any push at all [3](#0-2) . The code's own comments flag this as a known, currently-unaddressed gap ("We'll leave this unaddressed for now") [7](#0-6) , indicating the maintainers are aware the check is a shape/format check rather than a genuine authorization or provenance check.

### Recommendation
Do not infer trust/bypass eligibility purely from whether `GitObjectDirectory`/`GitAlternateObjectDirectories` are set. Bind quarantine legitimacy to an unforgeable, server-issued token (e.g., signed quarantine ID or transaction-scoped identifier stored server-side) that is verified against the actual transaction/quarantine registry rather than merely checking path shape via `ValidateRelativePath`/prefix matching. Reject or ignore these fields entirely on RPCs where they cannot be tied back to a transaction that Gitaly itself created for the current request, consistent with the TODO already present in `beginTransactionForRepository`.

### Proof of Concept
1. As an ordinary authenticated Gitaly client (no special privileges), issue any accessor RPC (e.g. `RepositoryInfo`, `GetObjectDirectorySize`, `CommitIsAncestor`) against a target repository, explicitly setting `git_alternate_object_directories` to a relative path that resolves (per `ValidateRelativePath`) to a legitimate quarantine-shaped directory under the storage root that the attacker knows about (e.g., one from a concurrent operation, or a leftover directory matching the `quarantine`/`tmp_objdir` naming convention) — see how `ObjectDirectoryPath` accepts such paths purely by shape: [8](#0-7) .
2. `beginTransactionForRepository` sees the field is non-empty and treats the request as already-quarantined/looped-back, skipping normal transaction/partition routing and directly serving the RPC against the attacker-specified object directory: [6](#0-5) .
3. The resulting Git invocation includes the attacker-chosen alternate directory via `GIT_ALTERNATE_OBJECT_DIRECTORIES`, exposing whatever objects reside there to the RPC's read logic [4](#0-3) , without the attacker ever having gone through a real push that created that quarantine.
