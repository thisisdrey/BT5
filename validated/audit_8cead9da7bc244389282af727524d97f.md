The key checks in `Pool.liquidate` that a borrower could influence are `AmountIsTooHigh`, `RemainingDebtIsLowerThanTheFloor` and `maxLiquidable`. Let me check the configured values and the debt repay path.### Title
Borrower can permanently block liquidation of an unhealthy position by repaying dust so every valid `liquidate` call trips `RemainingDebtIsLowerThanTheFloor` - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool.liquidate` enforces two constraints that interact badly: `amountToRepay_` may not exceed `maxLiquidable` percent of the borrower's debt-token balance, and if `debtFloorInUsd > 0` the post-liquidation debt must be either `0` or `>= debtFloorInUsd`, otherwise the call reverts. When `maxLiquidable < 1e18`, a borrower can call the public `DebtToken.repay` (or frontrun a liquidation tx with it) to shrink their debt below `debtFloorInUsd / (1 - maxLiquidable)`. From that point, every `amountToRepay_` the liquidator is allowed to pass leaves a remainder in `(0, debtFloorInUsd)` and reverts, while repaying the full balance is forbidden by `AmountGreaterThanMaxLiquidable`. This is the same bug class as the SymmIO report: a user exploits a post-action solvency/floor check to refuse an unfavorable position close, but here the victim is the protocol (bad debt accrues) rather than partyB. ### Finding Description
In `Pool.liquidate` (contracts/Pool.sol:537-596):

- Line 567: `amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable` reverts — the liquidator can repay at most `maxLiquidable * _debtTokenBalance`.
- Lines 571-579: if `debtFloorInUsd > 0`, `_newDebtInUsd = quote(debtBalance - amountToRepay_)` must be `0` or `>= debtFloorInUsd`, else `RemainingDebtIsLowerThanTheFloor`.

With `maxLiquidable < 1e18` the only way to reach `_newDebtInUsd == 0` (`amountToRepay_ == _debtTokenBalance`) violates the close factor. So liquidation is only possible if `_debtTokenBalance - maxLiquidable * _debtTokenBalance >= debtFloorInUsd`, i.e. `debtUsd >= floor / (1 - maxLiquidable)`.

Attack path (all public, unprivileged):
1. Borrower has an unhealthy position (post price move) with debt `D` just above `floor / (1 - maxLiquidable)`.
2. Borrower calls `IDebtToken.repay(borrower, x)` — callable by anyone holding the synth, including the borrower who received the minted synths at issuance — repaying just enough to land at `floor <= newDebtUsd < floor / (1 - maxLiquidable)`. `DebtToken.repay` itself permits any outcome that leaves debt `== 0` or `>= floor` (contracts/DebtToken.sol:442-451), so this succeeds.
3. Every subsequent `liquidate` reverts with `RemainingDebtIsLowerThanTheFloor`. The position stays below the collateral factor yet cannot be liquidated at all.

The borrower can additionally frontrun individual `liquidate` transactions with a dust `repay` to make a full-debt `amountToRepay_` exceed the new balance and revert via `BurnAmountExceedsBalance` in `DebtToken._burn` (contracts/DebtToken.sol:528-529), forcing liquidators to re-quote.

### Impact Explanation
Liquidation liveness failure → protocol insolvency. An unhealthy account can keep its position frozen in an unliquidatable state by spending a small amount of synth (only the gap `debtUsd - floor/(1-maxLiquidable)`, which can be arbitrarily small for positions just above the window). If collateral keeps falling, the pool is left holding bad debt that no liquidator can clear. The borrower's locked collateral is untouched; they simply refuse the "unfavorable close" exactly as in the SymmIO report.

### Likelihood Explanation
Requires `debtFloorInUsd > 0` and `maxLiquidable < 1e18` in the deployed configuration — both are ordinary governance-set parameters (`debtFloorInUsd` exists specifically to keep liquidations profitable, `MaxLiquidableTooHigh` bounds the close factor). The attack costs only a small repay, needs no flash loan, and `repay`, `swap` (to source synths), and `liquidate` are all public and remain callable while paused (`whenNotShutdown` only). One caveat I could not fully verify from the index alone: the concrete deployed values of `maxLiquidable` and `debtFloorInUsd` per pool — the exploit requires `maxLiquidable < 1e18`, which should be confirmed against live state.

### Recommendation
Allow liquidation to bypass the debt floor when it repays the entire remaining debt *or* when the remaining debt would fall below the floor — e.g. skip the `RemainingDebtIsLowerThanTheFloor` check when `amountToRepay_ == _debtTokenBalance` is impossible due to `maxLiquidable`, or clamp `amountToRepay_` to the full balance and waive the floor for terminal liquidations. Alternatively, exempt `liquidate` from the floor entirely (the floor's purpose — liquidator incentive — is already served by `quoteLiquidateMax`), and/or let `maxLiquidable` be treated as a minimum rather than hard cap when it conflicts with the floor.

Hardhat fork sketch (extends existing `Pool.test.ts` fixtures):

```ts
// Setup: pool with debtFloorInUsd = F, maxLiquidable = m < 1e18
await poolMock.updateDebtFloor(F) // via governor in deployed setup
// alice is unhealthy after price drop, debtUsd D satisfies:
//   F/(1-m) >= D > F   (i.e. currently liquidatable)

// 1) Attacker-side repay: shrink debt so D' < F/(1-m), D' >= F
const debtToken = msEthDebtToken // alice holds msETH she minted
const target = F.div(BigNumber.from(10).pow(18).sub(m)) // floor/(1-maxLiquidable)
const toRepay = aliceDebt.sub(target.sub(1))
await debtToken.connect(alice).repay(alice.address, toRepay) // succeeds: D' >= F

// 2) Any liquidation now reverts
const maxRepay = (await debtToken.balanceOf(alice.address))
  .mul(await pool.maxLiquidable()).div(parseEther('1'))
await expect(
  pool.connect(bob).liquidate(msEth.address, alice.address, maxRepay, msdMET.address)
).to.revertedWithCustomError(pool, 'RemainingDebtIsLowerThanTheFloor')

// Full repay also reverts (close factor)
await expect(
  pool.connect(bob).liquidate(msEth.address, alice.address,
    await debtToken.balanceOf(alice.address), msdMET.address)
).to.revertedWithCustomError(pool, 'AmountGreaterThanMaxLiquidable')
// alice's position remains unhealthy but unliquidatable
```
