### Title
Unrestricted creation of duplicate low-liquidity Exchange pools enables cheap price manipulation of the same token pair - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeCreateActuator.java)

### Summary
The external report describes how Uniswap V3's multiple fee-tier pools for the same asset pair — some deep, some shallow or newly created — let an attacker manipulate price by routing a swap through the thin-liquidity pool instead of the deep one. Java-tron's native TRC10 bancor-style Exchange module has the analogous structural flaw: `ExchangeCreateActuator` allows anyone to create an arbitrary number of `Exchange` pools for the exact same `(firstTokenId, secondTokenId)` pair with independent, attacker-chosen initial balances, and downstream trading actuators (`ExchangeTransactionActuator`, `ExchangeInjectActuator`, `ExchangeWithdrawActuator`) operate purely on a caller-supplied `exchangeId` with no cross-check against liquidity of other exchanges for the same pair.

### Finding Description
`ExchangeCreateActuator.doValidate()` only rejects a request if `firstTokenID` equals `secondTokenID`; it never checks whether an `Exchange` for that same token pair already exists [1](#0-0) . Any account can therefore create a brand-new, thinly-funded `ExchangeCapsule` for a pair that already has a deep, well-known exchange, seeding it with as little as they choose (validated only against an upper `balanceLimit`, not a lower bound) [2](#0-1) . The test fixture `InitExchangeSameTokenNameActive` in `ExchangeWithdrawActuatorTest` explicitly demonstrates this: exchange id 1 for pair `123`/`456` holds balances `100000000L`/`200000000L` while exchange id 3 for the *same* pair holds only `903L`/`737L` [3](#0-2) .

`ExchangeTransactionActuator` (the swap actuator) resolves the exchange purely by the numeric `exchangeId` field embedded in the `ExchangeTransactionContract`, with no verification that this is the deepest/canonical pool for the token pair [4](#0-3) . The price/quote is computed with the bancor-relay formula in `ExchangeCapsule.transaction`, whose output is a direct function of that specific exchange's `firstTokenBalance`/`secondTokenBalance` [5](#0-4) . Because the relay-supply-based curve is far more sensitive to trade size when balances are small, a low-liquidity duplicate exchange can be moved to an arbitrary price with a fraction of the capital needed to move the deep exchange — exactly mirroring the Uniswap low-liquidity-fee-tier manipulation vector described in the report, except here the "tier" is simply a different numeric `exchangeId` chosen by whoever created it.

### Impact Explanation
Any counterparty, wallet, or third-party contract/service that resolves "the" exchange for a token pair by id (e.g., from `GetExchangeIds`, `dynamicStore.getLatestExchangeNum()`-based iteration, or by trusting an externally supplied `exchangeId`) can be steered into trading against a manipulated, thinly-capitalized pool instead of the legitimate deep one. Since the swap output (`anotherTokenQuant`) is computed solely from that specific `ExchangeCapsule`'s balances via `ExchangeInjectActuator`/`ExchangeWithdrawActuator`/`ExchangeTransactionActuator`, an attacker can cheaply skew the shadow pool's implied price and profit at the expense of the victim's TRC10 tokens or TRX — a concrete loss-of-funds condition matching the report's "loss of funds" impact class.

### Likelihood Explanation
Creating a duplicate exchange only costs the fixed `ExchangeCreateContract` fee (`calcFee()`) and the attacker's own choice of (small) initial token/TRX balances — both fully within the reach of a single unprivileged, signed transaction. No governance, permission, or special role is required, making this trivially and repeatedly reachable by any account.

### Recommendation
Add a validation rule in `ExchangeCreateActuator.doValidate()`/`execute()` to reject creation of a new exchange for a `(firstTokenId, secondTokenId)` pair (in either order) that already has one or more existing, sufficiently-liquid exchanges, or otherwise enforce a canonical single exchange per token pair. Alternatively, downstream consumers (APIs, wallets, other contracts) that need "the" price for a pair should aggregate/select by liquidity depth across all exchanges for that pair rather than trusting a single caller-chosen `exchangeId`, mirroring the report's recommendation to dynamically pick the deepest pool rather than a pre-configured/attacker-influenced one.

### Proof of Concept
1. Attacker calls `ExchangeCreateContract` to create `Exchange A` for pair `(TokenX, TRX)` with large balances (the legitimate/expected pool).
2. Attacker calls `ExchangeCreateContract` again for the identical pair `(TokenX, TRX)`, creating `Exchange B` with minimal balances (e.g. `903`/`737`, as shown feasible in `ExchangeWithdrawActuatorTest.InitExchangeSameTokenNameActive`) [6](#0-5) ; `ExchangeCreateActuator` accepts this because it never checks for an existing pair [1](#0-0) .
3. Attacker sends a small `ExchangeTransactionContract` referencing `Exchange B`'s id, which drastically shifts `Exchange B`'s bancor-curve implied price via `ExchangeCapsule.transaction` at negligible cost [5](#0-4) .
4. Any victim (user, wallet, or contract) that is induced to trade against `Exchange B` — believing it to be equivalent to the legitimate `Exchange A` — receives a manipulated `anotherTokenQuant`, resulting in a favorable trade for the attacker and a loss for the victim.
