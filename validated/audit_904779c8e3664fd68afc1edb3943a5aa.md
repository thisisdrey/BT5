### Title
Unprivileged attacker can permanently occupy a victim's per-account token slots via dust transfers, DoS-ing deposits/receipt of new collateral types - (File: contracts/Pool.sol)

### Summary
Analogous to the kernel bug (elements added to a list and never properly released), `Pool` maintains per-account sets `depositTokensOfAccount` / `debtTokensOfAccount` (`MappedEnumerableSet`) capped at `MAX_TOKENS_PER_USER = 30`. Any `DepositToken._transfer` or `_mint` to an address with a zero balance calls `pool.addToDepositTokensOfAccount(recipient)`, and `addToDepositTokensOfAccount` reverts with `UserReachedMaxTokens` once the combined list length reaches 30. An attacker can dust-transfer every distinct `DepositToken` to a victim, permanently occupying all of the victim's slots; the victim cannot remove them without knowing/holding the tokens.

### Finding Description
- `DepositToken._transfer` unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` when the recipient's balance transitions from 0 to >0 (contracts/DepositToken.sol:517-520).
- `Pool.addToDepositTokensOfAccount` enforces `onlyIfAdditionWillNotReachMaxTokens`, reverting when `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` (contracts/Pool.sol:143-148, 216-220).
- The pool-wide `depositTokens` set is also capped at `MAX_TOKENS_PER_USER` (contracts/Pool.sol:703), so the pool itself can host at most ~30 deposit tokens — meaning the attacker can realistically fill all of a victim's slots.
- Once filled, any subsequent transfer or deposit (`DepositToken._mint` → `addToDepositTokensOfAccount`) of a *new* collateral type to the victim reverts, because the add reverts and propagates.
- Note the victim retains self-service removal: transferring the dust tokens out triggers `removeFromDepositTokensOfAccount` (DepositToken.sol:523-525). However the victim must hold each dust token's balance, which they do — so the griefing is remediable, but only if the victim notices and manually clears 30 slots. More importantly, `SmartFarmingManager`-mediated deposits (`withdrawFrom`, leverage flows) and any contract-controlled recipient (e.g. feeCollector, a multisig, or an integration contract that cannot call `transfer`) cannot clear slots at all — for those recipients the DoS is permanent.

The true "leak" analog: entries are added to `depositTokensOfAccount` for contracts like `feeCollector` every time a withdraw fee is transferred (`_withdraw` → `_transfer(account_, feeCollector_, _fee)`, DepositToken.sol:546-547). The feeCollector contract cannot itself call `transfer` to release slots, so once its list reaches 30, *every* withdrawal that pays a fee in a new deposit-token type reverts — a permanent freeze of withdrawals for that token.

### Impact Explanation
Temporary freezing of funds / liveness break: (a) any EOA victim is blocked from receiving or depositing collateral token types not already in their list until they manually evict dust entries; (b) for non-EOA recipients that cannot initiate `DepositToken.transfer` (feeCollector, integrations, SmartFarmingManager flows), the slot exhaustion is permanent and withdrawals that would pay fees in an unlisted deposit token revert, freezing those funds.

### Likelihood Explanation
Cheap and fully unprivileged: attacker deposits 1 wei of each listed collateral, then calls `DepositToken.transfer(victim, 1)` up to 30 times. No privileged role, oracle manipulation, or flash loan needed. Likelihood is high; severity is bounded by the EOA self-recovery path.

### Recommendation
- Skip (rather than revert) when the list is full, or make `addToDepositTokensOfAccount`/`removeFromDepositTokensOfAccount` tolerant so transfers cannot be bricked by a third party's accounting limit.
- Alternatively, only track accounts that opted in via deposit, not passive transfer recipients, and always allow `removeFrom...` cleanup by the account itself.

```solidity
// Foundry fork test sketch
for (uint i; i < depositTokenCount; ++i) {
    IDepositToken dt = pool.depositTokens(i);
    IERC20(dt.underlying()).approve(address(dt), 1);
    dt.deposit(1);                 // mint 1 wei of msdTOKEN to attacker
    dt.transfer(victim, 1);        // occupies one slot of victim

// victim now has 30 entries
vm.prank(victim);
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
newCollateralDepositToken.deposit(amount); // reverts: addToDepositTokensOfAccount fails

```

If the evaluation considers EOA self-recovery sufficient mitigation, this reduces to a griefing note; the permanent variant applies to contract recipients such as `feeCollector`.
