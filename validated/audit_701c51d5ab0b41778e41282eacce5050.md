### Title
Unbounded HTTP body read in `process_event` enables single-request memory-exhaustion DoS on the signer's sole event-processing thread - (File: `libsigner/src/events.rs`)

### Summary
`process_event` reads the entire POST body via `request.as_reader().read_to_string(&mut body)` with no maximum-length check before any JSON parsing occurs. Since `SignerEventReceiver::main_loop` runs in a single dedicated thread that services every `/stackerdb_chunks`, `/new_burn_block`, `/new_block`, and `/proposal_response` event, one oversized POST can force unbounded allocation and stall the only thread that delivers all downstream signer events.

### Finding Description
The broken invariant: elsewhere in this crate, wire-controlled sizes are bounded — `libsigner/src/http.rs` enforces `MAX_HTTP_HEADER_LEN` on header values [1](#0-0)  and `decode_http_body` caps chunked bodies at `MAX_MESSAGE_LEN` [2](#0-1) . No equivalent cap exists in `process_event`:

```
let mut body = String::new();
if let Err(e) = request.as_reader().read_to_string(&mut body) { ... }
``` [3](#0-2) 

This reads the full request body — sized only by the attacker-supplied `Content-Length` — into memory before `serde_json::from_slice` is ever invoked [4](#0-3) . `process_event` is reached for all four data-bearing endpoints dispatched from `next_event` [5](#0-4) , and `next_event`/`main_loop` run on a single thread per `SignerEventReceiver` spawned once via `Signer::spawn` [6](#0-5) . That one thread is used to forward every event type to the signer runloop, so blocking it on a giant read starves all signer event processing.

### Impact Explanation
A single crafted POST with a huge `Content-Length` (e.g., hundreds of MB to multiple GB) causes the event-receiver thread to allocate proportional memory and remain blocked reading, denying service to legitimate node-originated events (`stackerdb_chunks`, block proposals, burn/stacks blocks) for as long as the read takes, and potentially exhausting host memory, resulting in an OOM crash of the signer process. This is a repeatable, single-message, unauthenticated DoS against the signer's sole event pipeline, matching the "Critical - remote crash/unauthenticated DoS from few messages" category.

### Likelihood Explanation
The only precondition is that the attacker can open a TCP connection to the signer's event-listener socket and speak HTTP. The reference/sample configs bind this endpoint to `127.0.0.1` [7](#0-6) , but the code itself warns operators that the listener can be exposed and that doing so is risky [8](#0-7) ; the question's stated precondition is that the port is reachable. No secret, signature, or slot ownership is required to hit `process_event` — it runs before any authentication or content validation. The attack requires only one connection and one request, and can be repeated indefinitely at negligible attacker cost.

### Recommendation
Enforce a maximum body size before/while reading in `process_event`, e.g. validate the `Content-Length` header against a constant such as `MAX_MESSAGE_LEN` (or a dedicated `MAX_EVENT_BODY_LEN`) and reject/close the connection early, or use a bounded reader (`Read::take(max_len)`) instead of `read_to_string` so an oversized body is truncated/rejected rather than fully buffered.

### Proof of Concept
1. In a test module (or a standalone integration test), construct a `SignerEventReceiver::<T>` and call `bind()` on `127.0.0.1:0`.
2. Spawn `main_loop` (or directly call `next_event()`) in a thread.
3. From a second thread, `TcpStream::connect` to the bound address and send:
   `POST /stackerdb_chunks HTTP/1.1\r\nHost: x\r\nContent-Length: 500000000\r\nContent-Type: application/json\r\n\r\n` followed by streaming 500MB of filler bytes (or fewer bytes than declared, to also demonstrate the read blocking indefinitely).
4. Assert that process memory (RSS) grows by roughly the sent byte count and that `next_event()` does not return / the receiver thread is unresponsive to a concurrent `/status` request until the oversized body is fully consumed — demonstrating the missing cap at `request.as_reader().read_to_string(&mut body)` in `process_event` (`libsigner/src/events.rs:526`).
