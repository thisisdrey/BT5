### Title
Unbounded packfile transfer duration in `git-upload-pack` after negotiation allows slow-read resource-exhaustion DoS - (File: `internal/gitaly/service/ssh/upload_command.go`)

### Summary
The negotiation timeout in `runUploadCommand`/`sshUploadPack` only guards the phase before `git-upload-pack` starts generating and writing the packfile; once negotiation completes (client sends `pktline.PktDone()`), the `timeoutTicker`/read-monitor is no longer enforcing any bound, and the pack-writing phase driven by `largeBufferReaderFrom.ReadFrom` can block indefinitely if the client stops reading from the sidechannel socket. This allows an unprivileged user who owns a large repository to pin a Gitaly RPC goroutine, its `git-upload-pack` subprocess, and associated memory/disk-cache pressure for an unbounded time, and to repeat this across many connections to exhaust server capacity.

### Finding Description
In `internal/gitaly/service/ssh/upload_pack.go`, `sshUploadPack` creates a `timeoutTicker` and calls `s.runUploadCommand(ctx, repo, stdin, stdout, stderr, timeoutTicker, pktline.PktDone(), ...)`. [1](#0-0) 

The accompanying comment is explicit that the ticker exists only to mitigate a time-of-check/time-of-use race during the negotiation phase (bounding the time between RPC start and the "done"/flush packet), not the subsequent packfile-generation/transfer phase: [2](#0-1) 

In `runUploadCommand`, the `timeoutTicker` is only passed into `monitor.Monitor(ctx, boundaryPacket, timeoutTicker, cancelCtx)`, which watches for the boundary packet (`PktDone()`) on the *input* side (`pktline.NewReadMonitor`) — it has no visibility into or control over the *output* side once `git-upload-pack` starts streaming the pack: [3](#0-2) 

The pack data is written through `largeBufferReaderFrom`, whose `ReadFrom` uses a plain `io.CopyBuffer` with a 64KB buffer and no deadline or additional context check per iteration: [4](#0-3) 

The handler then blocks on `cmd.Wait()`, which will not return until `git-upload-pack` finishes writing all pack bytes to `stdout` (ultimately the sidechannel connection). If the destination write blocks because the client stops reading its socket, `cmd.Wait()` blocks correspondingly: [5](#0-4) 

The only deadlines set on the sidechannel connection are during connection setup (`sidechannelTimeout = 5 * time.Second`), which are explicitly cleared (`SetDeadline(time.Time{})`) before the actual data phase begins, and are never re-armed for the duration of the pack transfer: [6](#0-5) [7](#0-6) [8](#0-7) 

An existing test, `testUploadPackWithSidechannelTimeout`, exercises the negotiation-phase timeout only — it simulates a client that never completes negotiation, and confirms the server aborts with a `DeadlineExceeded` "waiting for negotiation" error. It does not test (and the code does not implement) a bound on the post-negotiation transfer phase: [9](#0-8) 

Because the RPC's `ctx` is derived from `rpcContext` via `context.WithCancel` with no deadline of its own, and gRPC does not impose a default per-RPC deadline unless the client sets one, an attacker-controlled slow/non-reading client can keep the underlying goroutine, `git-upload-pack` subprocess, and OS-level buffers/disk cache pinned indefinitely once negotiation has succeeded.

### Impact Explanation
This is a Denial-of-Service class finding: an unprivileged attacker who owns a repository (even one they created via fork/import) can complete negotiation and then stall reading from the sidechannel socket, keeping a Gitaly RPC handler goroutine, the `git-upload-pack` subprocess, and any generated pack data resident/consuming memory and I/O for an unbounded duration. Repeating this with many concurrent connections against a large synthetic repository (many large blobs) amplifies memory/CPU/subprocess-count/file-descriptor consumption and can degrade or exhaust Gitaly's serving capacity for all users on that node, matching a resource-exhaustion/DoS of an RPC handler impact class.

### Likelihood Explanation
Preconditions are minimal and within the stated attacker capability: the attacker only needs a repository they control (to make the packfile large, e.g. by pushing many large blobs) and the ability to run `git clone`/`git fetch` over SSH against it, then simply stop reading the socket (or read very slowly) after sending the `done` packet. This requires no special role, no secret, and no non-default configuration — it exploits the documented, intentional narrow scope of the mitigating timeout. It is trivially repeatable and can be scripted to open many concurrent slow-read connections.

### Recommendation
Extend the timeout/deadline enforcement to cover the entire RPC lifetime, not just the negotiation phase — e.g., set and periodically refresh a write deadline on the underlying sidechannel connection during the pack-transfer phase (or wrap `stdout` with a deadline-aware writer that fails if no progress is made within a bounded interval), and/or enforce an overall RPC deadline via gRPC server-side interceptor/timeout so that `runUploadCommand`'s `ctx` is canceled if the client fails to make forward progress reading data, killing the `git-upload-pack` subprocess and freeing resources.

### Proof of Concept
Extend `internal/gitaly/service/ssh/upload_pack_test.go` with a test analogous to `testUploadPackWithSidechannelTimeout`, but simulate a client that: (1) completes negotiation normally by sending `pktline.PktDone()`, then (2) stops reading from `clientConn` entirely (or reads at a fixed slow rate) against a repository seeded with many large blobs to produce a multi-hundred-MB packfile. Assert that:
- `git-upload-pack` subprocess and Gitaly's RPC goroutine remain alive/blocked well past `s.cfg.Timeout`-like values or the default gRPC deadline, i.e., the RPC does not return within a chosen bound (e.g. 30s) even though no per-request cap on transfer duration exists.
- Compare against the existing pre-negotiation test (`testUploadPackWithSidechannelTimeout`) which does return promptly, showing the asymmetry between negotiation-phase and transfer-phase timeout coverage.

		// The read monitor will cancel the local `ctx` when we do not observe a specific packet before the
		// timeout ticker ticks. This is done to address a time-of-check-to-time-of-use-style race, where the
		// client opens a connection but doesn't yet perform the negotiation of what data the server should
		// send. Because access checks only happen at the beginning of the call, it may be the case that the
		// client's permissions have changed since the RPC call started.
		//
		// To address this issue, we thus timebox the maximum amount of time between the start of the RPC call
		// and the end of the negotiation phase. While this doesn't completely address the issue, it's the best
		// we can reasonably do here.
		//
		// To distinguish cancellation of the overall RPC call and a timeout of the negotiation phase we use two
		// different contexts. In the case where the local context has been cancelled, we know that the reason
		// for cancellation is that the negotiation phase did not finish in time and thus return a more specific
		// error.
		if ctx.Err() != nil && rpcContext.Err() == nil {
			return structerr.NewDeadlineExceeded("waiting for negotiation: %w", ctx.Err())
		}

		// A common error case is that the client is terminating the request prematurely,
		// e.g. by killing their git-fetch(1) process because it's taking too long. This is
		// an expected failure, but we're not in a position to easily tell this error apart
		// from other errors returned by git-upload-pack(1). So we have to resort to parsing
		// the error message returned by Git, and if we see that it matches we return an
		// error with a `Canceled` error code.
		//
		// Note that we're being quite strict with how we match the error for now. We may
		// have to make it more lenient in case we see that this doesn't catch all cases.
		if stderrBuilder.String() == "fatal: the remote end hung up unexpectedly\n" {
			return structerr.NewCanceled("user canceled the request")
		}

		return fmt.Errorf("cmd wait: %w, stderr: %q", err, stderrBuilder.String())

func testUploadPackWithSidechannelTimeout(t *testing.T, ctx context.Context, opts ...testcfg.Option) {
	t.Parallel()

	cfg := testcfg.Build(t, opts...)

	cfg.SocketPath = runSSHServerWithOptions(t, cfg, []ServerOpt{
		WithUploadPackRequestTimeoutTickerFactory(func() helper.Ticker {
			// Create a ticker that will immediately tick when getting reset so that the
			// server-side can observe this as an emulated timeout.
			ticker := helper.NewManualTicker()
			ticker.ResetFunc = func() {
				ticker.Tick()
			}
			return ticker
		}),
	})

	repo, repoPath := gittest.CreateRepository(t, testhelper.Context(t), cfg)
	gittest.WriteCommit(t, cfg, repoPath, gittest.WithBranch("main"))

	ctx, cancel := context.WithCancel(ctx)
	defer cancel()

	registry := sidechannel.NewRegistry()
	client := newSSHClientWithSidechannel(t, ctx, registry, cfg.SocketPath)

	ctx, waiter := sidechannel.RegisterSidechannel(ctx, registry, func(clientConn *sidechannel.ClientConn) (returnedErr error) {
		// Discard all data and block on the connection closing. The client says nothing
		// back to the server and doesn't finish the negotiation. This leads to the server
		// closing the connections once the negotiation timeout fires.
		_, err := io.Copy(io.Discard, clientConn)
		assert.NoError(t, err)
		return nil
	})
	defer testhelper.MustClose(t, waiter)

	_, err := client.SSHUploadPackWithSidechannel(ctx, &gitalypb.SSHUploadPackWithSidechannelRequest{
		Repository: repo,
	})

	// Because the client says nothing, the server would block. Because of
	// the timeout, it won't block forever, and return with a non-zero exit
	// code instead.
	testhelper.RequireGrpcError(t, structerr.NewDeadlineExceeded("running upload-pack: waiting for negotiation: context canceled"), err)
}
