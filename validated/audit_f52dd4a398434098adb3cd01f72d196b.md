### Title
Stale MarketOrder record on rounding-edge trade allows double return of sell tokens (unbacked balance) - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
In `MarketSellAssetActuator.matchSingleOrder()`, when a maker order is consumed but the computed `makerBuyTokenQuantityReceive` rounds down to `0`, the code credits the maker's remaining sell-token balance back and returns early, **skipping the persistence of the updated `MarketOrderCapsule` to `MarketOrderStore`**. This leaves the on-disk order record stale (still `ACTIVE`, with its pre-trade `sellTokenQuantityRemain`), even though the order was already marked `INACTIVE` and stripped from the account's active-order list in memory. A subsequent `MarketCancelOrderContract` on the same order ID re-reads the stale `ACTIVE` record and credits the sell tokens back to the owner's balance a second time, minting an unbacked balance.

### Finding Description
`matchSingleOrder()` handles the "taker > maker" branch as follows: [1](#0-0) 

```
makerBuyTokenQuantityReceive = MarketUtils
    .multiplyAndDivide(makerSellRemainQuantity, makerBuyQuantity, makerSellQuantity, ...);

MarketUtils.updateOrderState(makerOrderCapsule, State.INACTIVE, marketAccountStore);
if (makerBuyTokenQuantityReceive == 0) {
  // ... "it would not happen here" ...
  makerOrderCapsule.setSellTokenQuantityReturn();
  returnSellTokenRemain(makerOrderCapsule);
  return;
}
``` [2](#0-1) 

`returnSellTokenRemain(makerOrderCapsule)` fetches the maker's `AccountCapsule`, credits it with `sellTokenQuantityRemain` via `MarketUtils.returnSellTokenRemain()`, and persists the account with `accountStore.put(...)`. However, `MarketUtils.updateOrderState()` only mutates the in-memory capsule's state field and updates `MarketAccountStore` (removing the order from the owner's active-order list); it does not write to `MarketOrderStore`: [3](#0-2) 

The only place that persists the maker order's new state (`INACTIVE`, `sellTokenQuantityRemain=0`) is the line reached at the end of `matchSingleOrder()`: [4](#0-3) 

`orderStore.put(makerOrderCapsule.getID().toByteArray(), makerOrderCapsule);`

The early `return;` at line 477 skips this `orderStore.put()` call entirely, so `MarketOrderStore` still holds the order's *pre-trade* data: `State.ACTIVE` (or whatever it was before this match) with the original, non-zero `sellTokenQuantityRemain`.

The developer's inline comment claims "it would not happen here," reasoning only about the case where `makerSellQuantity < makerBuyQuantity`. The reasoning does not cover the opposite/common case where `makerSellQuantity > makerBuyQuantity` (i.e., the maker sells more units of a cheap token per unit of an expensive one). In that case, `multiplyAndDivide(makerSellRemainQuantity, makerBuyQuantity, makerSellQuantity)` performs floor division and can legitimately evaluate to `0` when `makerSellRemainQuantity * makerBuyQuantity < makerSellQuantity` — e.g. a maker order with `sellTokenQuantity = 1_000_000`, `buyTokenQuantity = 1`, whose remaining sell amount has been driven down to a small residual (e.g. `1`) by prior partial fills, `multiplyAndDivide(1, 1, 1_000_000) = 0`. This is directly analogous to the reported `CyanPeerPlan.revive()` bug class: an entity is logically marked "completed" (order `INACTIVE`, funds returned) while the authoritative on-chain store record is never updated to reflect that completion, leaving a "locked"/stale asset record that can be reused.

### Impact Explanation
Because `MarketCancelOrderActuator.validate()` reads the order directly from `MarketOrderStore` and only checks `marketOrderCapsule.isActive()`: [5](#0-4) 

the stale, still-`ACTIVE` order (with its original non-zero `sellTokenQuantityRemain`) passes validation. `execute()` then calls `MarketUtils.returnSellTokenRemain(orderCapsule, accountCapsule, ...)` again: [6](#0-5) 

crediting the maker's account with the same (or a comparable, non-zero) amount of TRX/TRC-10 tokens a second time — tokens that were already credited by the earlier silent early-return path, or that were already consumed by the trade counterpart. This is a direct creation of unbacked balance (funds minted from nothing), reachable by any unprivileged order placer who constructs matching sell/buy quantities to trigger the rounding edge case — satisfying the "unbacked balance" / "theft of funds" impact criteria required by the validation rules.

### Likelihood Explanation
The vulnerable branch is reachable purely through normal `MarketSellAssetContract` transactions (a market order placer, an unprivileged transaction broadcaster) crafting sell/buy token quantity ratios such that `makerSellQuantity` is a multiple of a small `makerBuyQuantity`, and the maker order's remaining sell quantity is driven to a value below `makerSellQuantity/makerBuyQuantity` through earlier partial fills. No special privileges, SR/witness status, or victim cooperation are required — only two colluding or independent accounts submitting sell orders that match at prices producing the rounding condition, followed by a `MarketCancelOrderContract` from the maker.

### Recommendation
In `MarketSellAssetActuator.matchSingleOrder()`, ensure the `makerOrderCapsule` is persisted to `MarketOrderStore` (`orderStore.put(...)`) on **every** code path that mutates its state, including the `makerBuyTokenQuantityReceive == 0` early-return branch, before returning. Equivalently, refactor the method so state persistence happens once at a single exit point (e.g., wrap the early-return logic to fall through to the existing `orderStore.put()` call), and add a regression test that forces the rounding-to-zero condition on the "taker > maker" path to confirm the order is stored as `INACTIVE` with `sellTokenQuantityRemain = 0` and cannot be cancelled again.

### Proof of Concept
1. Account M creates a sell order: sell 1,000,000 of Token A for 1 unit of Token B (`sellTokenQuantity=1,000,000`, `buyTokenQuantity=1`).
2. A prior taker partially fills M's order, reducing `sellTokenQuantityRemain` to a small residual value `r` (e.g. `r=1`) without fully exhausting the order (so the order stays `ACTIVE` in `MarketOrderStore`).
3. A new taker T places a sell order for Token B against Token A that matches M's order such that the "taker > maker" branch is entered in `matchSingleOrder()`, and `multiplyAndDivide(r, 1, 1_000_000)` evaluates to `0` (since `r * 1 < 1,000,000`).
4. `matchSingleOrder()` marks M's order `INACTIVE` (in `MarketAccountStore` only), credits M's balance with `r` tokens via `returnSellTokenRemain`, and returns early — **never calling `orderStore.put()`** for M's order, leaving the stored record `ACTIVE` with `sellTokenQuantityRemain = r` (or its pre-match value).
5. M then submits a `MarketCancelOrderContract` for the same `orderId`. `MarketCancelOrderActuator.validate()` reads the stale, still-`ACTIVE` record from `MarketOrderStore` and passes validation.
6. `MarketCancelOrderActuator.execute()` calls `MarketUtils.returnSellTokenRemain()` again, crediting M's account with `sellTokenQuantityRemain` (the stale value) a second time — an unbacked, duplicate credit of Token A to M's balance.

Note: I was unable to execute this scenario end-to-end in a live test environment (no execution tooling available in this session); the analysis is based on static code tracing of `MarketSellAssetActuator`, `MarketUtils`, `MarketOrderCapsule`, and `MarketCancelOrderActuator`. A background Devin session with test execution capability would be needed to confirm the exact numeric parameters that trigger the rounding-to-zero condition and to validate the double-credit end-to-end.

  public static void updateOrderState(MarketOrderCapsule orderCapsule,
      State state, MarketAccountStore marketAccountStore) throws ItemNotFoundException {
    orderCapsule.setState(state);

    // remove from account order list
    if (state == State.INACTIVE || state == State.CANCELED) {
      MarketAccountOrderCapsule accountOrderCapsule = marketAccountStore
          .get(orderCapsule.getOwnerAddress().toByteArray());
      accountOrderCapsule.removeOrder(orderCapsule.getID());
      marketAccountStore.put(accountOrderCapsule.createDbKey(), accountOrderCapsule);
    }
  }
