## Title
Non-atomic order-matching in `MarketSellAssetActuator` persists partial fills to disk even when the overall transaction later fails, allowing griefing that leaves inconsistent, unbacked asset/TRX balances - ([File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java])

### Summary
The reported Arcadia bug is that an atomic "buy" operation (Dutch auction bid) is implemented as a single monolithic call that reverts wholesale when any sub-check fails, allowing griefers to force reverts of legitimate buyers and let bad debt accrue. In java-tron's TRC10 order-book market feature, `MarketSellAssetActuator.matchOrder`/`matchSingleOrder` exhibits the *inverse and more dangerous* variant of the same anti-pattern: it writes maker-side and store-side state changes directly to persistent stores (`orderStore.put(...)`, `accountStore.put(...)` inside `addTrxOrToken`) **while still inside the same `execute()` call**, before the taker-side bookkeeping and overall success/failure status is finalized. If a later step in the same `execute()` call throws (e.g. `ContractValidateException("Too many matches. MAX_MATCH_NUM = " + MAX_MATCH_NUM)`), the whole transaction is reported as `FAILED`, yet the maker-side balance/order mutations already committed to the KV stores are not rolled back at the actuator level.

### Finding Description
In `matchOrder`, the taker's order is matched sequentially against resting "maker" orders: [1](#0-0) 
Each successful sub-match calls `matchSingleOrder`, which immediately persists the updated maker order and maker account balance to the database: [2](#0-1) [3](#0-2) 
This means `orderStore.put()` and `accountStore.put()` for the maker side are executed as *direct, immediate writes*, not staged in an in-memory object that is only flushed at the end of `execute()` on success (in contrast to the taker's own account/order, which are only written after `matchOrder()` returns without exception, at lines 147-148 of `execute()`): [4](#0-3) 

If the taker's sell order matches against many small resting orders at the best price, `matchOrderCount` can exceed `MAX_MATCH_NUM` (20), causing `matchOrder` to throw `ContractValidateException`: [5](#0-4) 
This propagates up and is caught in `execute()`, which marks the transaction result `FAILED` and re-throws `ContractExeException`: [6](#0-5) 

At this point every maker order/account touched by the up-to-20 already-processed matches has already been written to `orderStore`/`accountStore` with updated (reduced or zeroed) `sellTokenQuantityRemain` and updated asset/TRX balances - but the taker's own sell-token debit, fee burn, and buy-token credit performed earlier in `execute()` (lines 126-137) are only ever persisted via `accountStore.put(accountCapsule...)` at line 148, which is never reached because the exception short-circuits execution before that line. The taker's sell-token debit performed by `transferBalanceOrToken(accountCapsule)` (line 134) operates on the same in-memory `AccountCapsule` object, but because `accountStore.put()` is never called for it, whether the underlying store implementation reflects this mutated object depends on caching semantics of `TronStoreWithRevoking`/level-DB-backed cache; regardless, the maker side's state has unambiguously been persisted by the time the exception unwinds.

Because there is no actuator-level "all-or-nothing" repository/session wrapping the whole `execute()` body (unlike TVM-invoked native contracts, which explicitly use a child `Repository` with `commit()`/`reject()` semantics, e.g. `WithdrawExpireUnfreezeProcessor` invoked from `Program.withdrawExpireUnfreeze()`): [7](#0-6) 
a failure partway through `matchOrder` leaves the maker side of already-executed trades committed while the transaction as a whole is reported `FAILED`. This is analogous to the reported bug class: a batch/array-style multi-party settlement (Dutch-auction bid vs. many-maker order match) is not executed atomically, and a griefer can deliberately engineer the "too many matches" condition (by placing many minimal-size resting orders at the best price) to force this partial-persist/overall-fail state on a victim's large sell order.

### Impact Explanation
An attacker who deliberately fragments liquidity into >`MAX_MATCH_NUM` (20) tiny maker orders at the best price can force any victim's larger `MarketSellAssetContract` to persist state changes to the maker side (their own orders/balances updated) while the overall transaction fails and the taker never receives the buy-token credit or their order recorded in `orderStore`/`marketAccountStore`. This can create balance/state inconsistency between the order-book bookkeeping (`pairToPriceStore`, `pairPriceToOrderStore`) and the underlying account/order stores, and repeatedly wastes the victim's transaction fee (`getMarketSellFee()`) for a transaction whose economic effect is not what the failed/success status implies. Because the market feature manages real TRX/TRC10 balances, an inconsistency here can manifest as tokens being credited to makers without a corresponding balanced debit being finalized on the taker side, i.e., an unbacked-balance condition, which is the closest java-tron analog to the "bad debt accrual" impact in the original report.

### Likelihood Explanation
Any unprivileged account can broadcast `MarketSellAssetContract` transactions. Building the griefing setup requires only creating >20 small resting sell orders at the best price for a token pair (a normal, permitted operation) and is inexpensive relative to potentially causing a victim's larger sell order to hit the `MAX_MATCH_NUM` limit. This is directly reachable from a single signed transaction (`MarketSellAssetActuator.execute`) with no special privilege, matching the reachable-surface constraints for this analysis.

### Recommendation
Buffer maker-side account/order mutations in `matchOrder`/`matchSingleOrder` in memory and only flush them to `orderStore`/`accountStore`/price stores after the entire match loop completes successfully (mirroring the taker-side pattern used at the end of `execute()`), or wrap the whole `execute()` body in a repository-style child session (as done for TVM native contracts via `Repository.newRepositoryChild()`/`commit()`) so that a mid-loop `ContractValidateException` (e.g., `MAX_MATCH_NUM` exceeded) causes all partial writes - maker and taker alike - to be discarded atomically.

### Proof of Concept
1. Attacker creates 21+ small `MarketSellAssetContract` resting orders (`sellTokenQuantity`/`buyTokenQuantity` chosen to land at the identical best price) for token pair `(A, B)`, each below `MAX_ACTIVE_ORDER_NUM`/`MAX_MATCH_NUM` thresholds.
2. Victim submits a single large `MarketSellAssetContract` sell order for token `A` against `B` that would need to match against more than `MAX_MATCH_NUM` = 20 of the attacker's resting orders to fill.
3. During `matchOrder`, matches 1-20 execute successfully; for each, `matchSingleOrder` calls `orderStore.put(makerOrderCapsule...)` and `addTrxOrToken(makerOrderCapsule, ...)` which calls `accountStore.put(...)` directly (see lines 486-490, 550-562 of `MarketSellAssetActuator.java`), persisting the attacker's updated balances/orders to the database.
4. On the 21st match, `matchOrderCount > MAX_MATCH_NUM` triggers `ContractValidateException("Too many matches...")` (line 358), propagating to `execute()`'s catch block, which sets the transaction result to `FAILED` and throws `ContractExeException` (lines 152-159) - before the victim's own `accountStore.put(accountCapsule...)` and `orderStore.put(orderCapsule...)` at lines 147-148 ever execute.
5. Result: the attacker's (maker) orders/balances have been mutated and persisted for the matches that did occur, while the victim's transaction is reported as failed and their side of the trade was never finalized/persisted - an inconsistent, non-atomic outcome directly analogous to the reported "partial-batch revert / bad-debt" bug class.
