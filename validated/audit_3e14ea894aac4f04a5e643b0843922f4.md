### Title
BurdenMonitor command eviction understates an RPC's tracked CPU/memory burden, letting expensive concurrent Git commands escape load-shedding accounting - ([File: internal/burdenmonitor/rpc_entry.go])

### Summary
The Sherlock finding describes a class of bug where a resource-tracking counter (`holdAmount`) is clamped via `min()` against an already-accumulated value, so it can be driven to zero while the real economic exposure (the position) remains large — decoupling the accounting value used for downstream fee/limit logic from the actual state. The analogous pattern in Gitaly is `RPCEntry.evictCommand()` in `internal/burdenmonitor/rpc_entry.go`, which silently drops the lowest-CPU-consuming *still-running* command from the tracking map, causing `TotalCPUTime()`/`TotalMemory()` to under-report the true, ongoing resource burden of an RPC that is used by the `LoadShedder` to decide which in-flight RPCs to cancel under critical pressure.

### Finding Description
`BurdenMonitor` tracks git subprocesses spawned by an RPC handler in `RPCEntry.Commands`, capped at `maxTrackedCommands` (20) per entry [1](#0-0) . When a new command is registered beyond the cap, `RegisterCommand` calls `evictCommand`, which picks the currently tracked command with the *lowest* `UserTime+SystemTime` and deletes it from `e.Commands` immediately — before that command has actually finished running [2](#0-1) .

`TotalCPUTime()` and `TotalMemory()` only sum `e.completedCPUTime` plus whatever remains in `e.Commands` [3](#0-2) . Because the evicted command is neither in `Commands` (so its ongoing consumption is excluded) nor yet folded into `completedCPUTime` (that only happens later, in `MarkCommandCompleted`, once/if the process actually terminates and reports back) [4](#0-3) , there is a window — potentially the entire remaining lifetime of a long-running process if it never gets a chance to report completion before the RPC ends or is itself evicted again — where the entry's reported CPU/memory burden is understated relative to its actual live resource consumption. This mirrors the DeFi bug's core defect: a per-entity accounting value used to drive external decisions (fees there; load-shedding priority here) is forced down/removed by a bound (`min`/eviction-by-cap) even though the real underlying resource usage continues unabated.

This is reachable by an ordinary, unprivileged client: any RPC classified as `protoregistry.OpAccessor` is wrapped by `BurdenMonitor.UnaryInterceptor`/`StreamInterceptor` when the `BurdenMonitorTrackCommands` feature flag is enabled [5](#0-4) , and any RPC that spawns more than `maxTrackedCommands` git subprocesses (e.g. via crafted input causing many auxiliary git invocations) triggers the eviction path purely through normal request handling — no privileged actor or malicious peer/MITM is required.

### Impact Explanation
`BurdenMonitor.GetTopNEntries`/`entriesSortedBy` feeds the `LoadShedder`, which under critical resource pressure queries the monitor for the highest-CPU/highest-memory in-flight RPCs and cancels them (`SnipeTopN`) to relieve pressure [6](#0-5) . If a request's true resource burden is understated because its most expensive command(s) were evicted from tracking while still running, that request can rank artificially low and evade being selected for cancellation, while a genuinely cheaper request could be sniped instead. This degrades the effectiveness of the DoS mitigation's last line of defense (load shedding) precisely in the scenario it's meant to protect (systems already under critical CPU/memory pressure), potentially prolonging resource exhaustion/DoS conditions.

### Likelihood Explanation
Requires (a) the `BurdenMonitorTrackCommands` feature flag enabled, (b) a single accessor RPC spawning more than 20 concurrent git subprocesses (achievable for some RPCs with many auxiliary invocations depending on input shape, as acknowledged in the code's own comments about "a variable number of Git commands depending on the shape of the user input"), and (c) the system already under critical load for the load shedder to act. This is a narrower, moderate-likelihood scenario compared to a straightforward push/fetch primitive, and I could not confirm from the available code whether any real production RPC realistically exceeds 20 concurrently tracked subprocesses; the code comments suggest it was sized based on a survey implying this is meant to be rare.

### Recommendation
When evicting a command that has not completed, do not simply drop its contribution: either (1) keep a best-effort estimate of its resource usage (e.g., poll once more before eviction and fold that partial reading into `completedCPUTime`/a running "evicted-but-still-active" estimate) so the aggregate doesn't silently drop to a lower value, or (2) prefer evicting completed/idle entries over active high-growth-potential commands, or (3) increase `maxTrackedCommands` dynamically / track an approximate "evicted total" gauge that the load shedder can factor in as a floor when ranking entries.

### Proof of Concept
Not independently verified end-to-end (no test harness run), but the mechanics are demonstrated by the existing unit test `TestRPCEntry_CommandCap` in `internal/burdenmonitor/burdenmonitor_test.go`, which shows that after eviction `entry.TotalCPUTime()` drops by exactly the evicted command's last-observed CPU time (`totalBefore - time.Millisecond`), and stays reduced until/unless `MarkCommandCompleted` is later called for that pid [7](#0-6) . An attacker-controllable RPC that spawns >20 git subprocesses, keeping the highest-CPU ones running while cheap ones get evicted in relative order, would exploit exactly this behavior to keep `TotalCPUTime()`/`TotalMemory()` artificially low for the duration those processes remain untracked.

// TotalCPUTime returns the sum of user and system CPU time across running commands.
func (e *RPCEntry) TotalCPUTime() time.Duration {
	e.mu.RLock()
	defer e.mu.RUnlock()

	total := e.completedCPUTime
	for _, cmd := range e.Commands {
		total += cmd.UserTime + cmd.SystemTime
	}
	return total
}

// TotalMemory returns the sum of anonymous RSS memory across all commands.
func (e *RPCEntry) TotalMemory() int64 {
	e.mu.RLock()
	defer e.mu.RUnlock()

	var total int64
	for _, cmd := range e.Commands {
		total += cmd.AnonRSS
	}
	return total
}

// RegisterCommand adds a new command to the RPC entry's tracking.
func (e *RPCEntry) RegisterCommand(pid int, name string, startTime time.Time) {
	e.mu.Lock()
	defer e.mu.Unlock()

	if _, ok := e.Commands[pid]; !ok && len(e.Commands) >= maxTrackedCommands {
		e.evictCommand()
	}

	e.Commands[pid] = &CommandStats{
		Name:      name,
		Pid:       pid,
		StartTime: startTime,
	}
}

// evictCommand removes the tracked command with the lowest CPU consumption.
// Its resource consumption will be added to the aggregate during the
// MarkCommandCompleted call.
func (e *RPCEntry) evictCommand() {
	var victim *CommandStats
	for _, cmd := range e.Commands {
		if victim == nil || cmd.UserTime+cmd.SystemTime < victim.UserTime+victim.SystemTime {
			victim = cmd
		}
	}
	if victim == nil {
		return
	}

	delete(e.Commands, victim.Pid)

	commandsEvictedTotal.WithLabelValues(e.ServiceName, e.MethodName).Inc()
}

	e.mu.Lock()
	defer e.mu.Unlock()

	delete(e.Commands, pid)

	e.completedCPUTime += userTime + systemTime
	e.completedCount++

// UnaryInterceptor returns a gRPC unary server interceptor that tracks RPC execution.
func (bm *BurdenMonitor) UnaryInterceptor() grpc.UnaryServerInterceptor {
	return func(ctx context.Context, req interface{}, info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (interface{}, error) {
		if featureflag.BurdenMonitorTrackCommands.IsEnabled(ctx) {
			mi, err := protoregistry.GitalyProtoPreregistered.LookupMethod(info.FullMethod)
			if err != nil {
				// The gRPC health checks calls are not part of the Gitaly proto
				// registry, yet they are legitimate requests. Let's not log
				// everytime a health check is received as it pollutes the logs,
				// mostly when using Praefect.
				if !strings.Contains(info.FullMethod, grpchealth.Health_ServiceDesc.ServiceName) {
					bm.logger.WithError(err).Warn("burden monitor stream interceptor: unable to lookup method info")
				}
				return handler(ctx, req)
			}

			// Only track accessor method in the burden monitor
			if mi.Operation == protoregistry.OpAccessor {
				ctx, entry := bm.RegisterRPC(ctx, info.FullMethod)

				defer bm.DeregisterRPC(entry.ID)
				return handler(ctx, req)

			}
		}

		return handler(ctx, req)
	}
}

func TestRPCEntry_CommandCap(t *testing.T) {
	t.Parallel()

	bm := New(testhelper.SharedLogger(t))
	_, entry := bm.RegisterRPC(testhelper.Context(t), "/foo.Service/Method")

	now := time.Now()
	// Fill the map to the cap with commands of strictly increasing CPU
	// consumption.
	for i := range maxTrackedCommands {
		pid := 1000 + i
		entry.RegisterCommand(pid, "git cat-file", now)
		entry.Commands[pid].UserTime = time.Duration(i+1) * time.Millisecond
	}
	require.Equal(t, maxTrackedCommands, entry.ActiveCommandCount())
	totalBefore := entry.TotalCPUTime()
	evictedBefore := testutil.ToFloat64(commandsEvictedTotal.WithLabelValues("foo.Service", "Method"))

	// Registering one more evicts the lowest-CPU command (pid 1000, 1ms) to
	// make room.
	entry.RegisterCommand(2000, "git rev-list", now)
	require.Equal(t, maxTrackedCommands, entry.ActiveCommandCount())
	require.NotContains(t, entry.Commands, 1000)
	require.Contains(t, entry.Commands, 2000)
	require.Equal(t, evictedBefore+1, testutil.ToFloat64(commandsEvictedTotal.WithLabelValues("foo.Service", "Method")))

	// The evicted command's observed CPU leaves the totals until the command
	// completes.
	require.Equal(t, totalBefore-time.Millisecond, entry.TotalCPUTime())

	// When the evicted command completes, its final consumption — including
	// anything it burned after eviction — is folded into the aggregates.
	entry.MarkCommandCompleted(1000, 5*time.Millisecond, 0)
	require.Equal(t, totalBefore+4*time.Millisecond, entry.TotalCPUTime())
