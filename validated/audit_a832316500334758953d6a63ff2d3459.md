### Title
`os.MkdirTemp` on Windows silently ignores the `0700` mode, leaving temp directories with default (inherited) ACLs instead of owner-only permissions - ([File: src/syscall/syscall_windows.go])

### Summary
`os.MkdirTemp` (`src/os/tempfile.go`) calls `Mkdir(name, 0700)` intending to restrict the new temp directory to the owner only, mirroring the exact primitive described in the Python `tempfile.mkdtemp()` CVE. On Windows, `syscall.Mkdir` discards the `mode` parameter entirely and calls `CreateDirectory(pathp, nil)` with `nil` security attributes, so the directory inherits the parent directory's ACL instead of getting owner-only permissions.

### Finding Description
Any code path that calls `os.MkdirTemp` / `ioutil.TempDir` (deprecated wrapper) with the intent of creating a private, owner-restricted directory follows: caller -> `os.MkdirTemp` (`src/os/tempfile.go:86-117`) -> `Mkdir(name, 0700)` (`src/os/tempfile.go:100`) -> platform `Mkdir` syscall. [1](#0-0) 
On Windows the underlying implementation is: [2](#0-1) 
`mode` is never translated into a `SECURITY_ATTRIBUTES`/DACL and `CreateDirectory` is invoked with `nil` security attributes, meaning Windows applies the default security descriptor — inherited from the parent directory's ACL — rather than restricting access to the creating user. This is the identical failure mode as BIT-python-2024-4030: on Windows, POSIX permission bits passed to a directory-creation API are not honored, so a "private" temp directory can end up readable/writable by other local users or accounts inheriting broad ACLs from the parent directory (e.g., a shared or misconfigured `%TEMP%` location).

### Impact Explanation
Any Go program on Windows that relies on `os.MkdirTemp`'s documented 0700 semantics to store sensitive data (secrets, tokens, staged files) in a "private" temp directory gets no such guarantee — the directory's actual access is determined by the parent directory's inherited ACL. This is an integrity/confidentiality concern (local information disclosure / unintended file access) rather than remote code execution, matching the low/PUBLIC-track severity typically assigned to the Python analog (it was rated High but is inherently a local-multiuser-Windows issue, not remote).

### Likelihood Explanation
This requires only an ordinary victim workflow: any Go program on Windows calling `os.MkdirTemp` (directly or via `ioutil.TempDir`, or indirectly via `t.TempDir()` in tests, `go build`'s temp work dirs, etc.) where the ambient `%TMP%`/`%TEMP%` directory has non-restrictive inherited ACLs (e.g., default profile-less service accounts, or explicitly configured shared temp locations, as also called out in the Python advisory). No attacker privilege beyond being another local user/account on the same Windows host is required; this matches the "unprivileged local user" premise, not a remote attacker.

### Recommendation
On Windows, `os.MkdirTemp`/`syscall.Mkdir` should translate POSIX-style modes like `0700` into an owner-only DACL passed via `SECURITY_ATTRIBUTES` to `CreateDirectory`, similar to CPython's fix for `mkdir`/`mkdtemp` referenced in BIT-python-2024-4030 (adding explicit "700"-equivalent ACL support on Windows) — i.e., construct a `SECURITY_ATTRIBUTES` with a DACL granting only the current user Full Control and pass it instead of `nil`.

### Proof of Concept
```go
package tempfile_windows_test

import (
	"os"
	"runtime"
	"testing"
)

// This test demonstrates that on Windows, os.MkdirTemp's mode=0700
// is not enforced as an owner-only ACL; the directory instead inherits
// the parent's (potentially permissive) ACL.
func TestMkdirTempIgnoresModeOnWindows(t *testing.T) {
	if runtime.GOOS != "windows" {
		t.Skip("windows-only analog")
	}

	dir, err := os.MkdirTemp("", "secrettemp")
	if err != nil {
		t.Fatal(err)
	}
	defer os.RemoveAll(dir)

	// Expectation per os.MkdirTemp docs: directory is created with mode 0o700.
	fi, err := os.Stat(dir)
	if err != nil {
		t.Fatal(err)
	}
	// On Windows, os.FileMode from syscall.Mkdir with nil SECURITY_ATTRIBUTES
	// does not actually restrict access to the owner; the reported/enforced
	// ACL is inherited from the parent, not owner-only 0700.
	// A real assertion would use golang.org/x/sys/windows to read the DACL
	// via GetSecurityInfo and confirm non-owner accounts (e.g. Authenticated
	// Users / Everyone inherited from parent) have access, contradicting
	// the intended 0700 semantics.
	if fi.Mode().Perm() != 0o700 {
		t.Fatalf("reported mode is %v, but underlying ACL is not actually owner-restricted on Windows (CreateDirectory called with nil SECURITY_ATTRIBUTES)", fi.Mode().Perm())
	}
}
```
Note: a fully rigorous PoC requires `golang.org/x/sys/windows` to call `GetNamedSecurityInfo` and enumerate the DACL to show non-owner principals retain access inherited from the parent — `os.FileMode` alone cannot represent Windows ACLs, which is itself evidence of the gap. This could not be executed/verified in this environment since it is Windows-specific and depends on live ACL inheritance state, which I was unable to confirm beyond the source-level ignoring of `mode` in `syscall.Mkdir` for Windows.
