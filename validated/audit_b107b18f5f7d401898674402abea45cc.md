### Title
Dust deposits/transfers fill victim's per-account token list (`MAX_TOKENS_PER_USER`), permanently reverting `issue`/`deposit` for any new token — denial of service of core pool operations - ([File: contracts/Pool.sol])

### Summary
Analogous to CVE-2022-36046 (an unhandled error path that crashes a shared process and denies service to all users), `Pool` exposes an unhandled-revert path reachable by any unprivileged account: `onlyIfAdditionWillNotReachMaxTokens` reverts whenever `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= MAX_TOKENS_PER_USER` (30). Because `DepositToken.deposit(amount_, onBehalfOf_)` accepts an arbitrary beneficiary and `DepositToken` transfers mint/add the token to the recipient's per-account set, an attacker can push dust positions into a victim's list until it is full. From then on, every call path that tries to add a new entry for the victim — `DebtToken.issue`/`leverage` (adding a debt token) and `DepositToken.deposit`/`transfer` of a token the victim does not yet hold — reverts with `UserReachedMaxTokens()` [1](#0-0) .

### Finding Description
The per-account token lists are stored in `MappedEnumerableSet` structures `debtTokensOfAccount` and `depositTokensOfAccount` [2](#0-1) . Entries are added only through `addToDebtTokensOfAccount`/`addToDepositTokensOfAccount`, which are invoked by `DebtToken.issue`/`mint` (when balance goes 0→non-zero) and by `DepositToken` mint/transfer. Both are guarded by the same modifier [1](#0-0) .

Attack path (all public entry points, no privilege):

1. Pool allows up to `MAX_TOKENS_PER_USER = 30` deposit tokens (`addDepositToken` enforces `depositTokens.length() >= MAX_TOKENS_PER_USER` revert) [3](#0-2) .
2. For each registered `DepositToken`, the attacker acquires dust of the underlying and calls `DepositToken.deposit(1 wei, victim)` — `deposit` mints msdTOKEN to `onBehalfOf_` and adds the token to `depositTokensOfAccount[victim]` [4](#0-3) . Alternatively the attacker deposits dust to itself and calls `transfer(victim, dust)`; transfers likewise add the token to the recipient's set.
3. Once `depositTokensOfAccount[victim]` reaches 30 (or 30 − existing debt entries), any subsequent operation that would add a new token for the victim reverts:
   - `DebtToken.issue` / `SmartFarmingManager.leverage` → `addToDebtTokensOfAccount` → `UserReachedMaxTokens()`.
   - `DepositToken.deposit(_, victim)` for a new collateral, and inbound `transfer`/`transferFrom` of any msdTOKEN the victim doesn't already hold → `addToDepositTokensOfAccount` → revert.

No modifier stops this: `deposit` only requires `whenNotPaused`, `nonReentrant`, `onlyIfDepositTokenExists`, `amount_ > 0`, and `onBehalfOf_ != 0` — there is no beneficiary consent, no minimum amount, and no opt-in [5](#0-4) . The revert is identical in spirit to the Next.js bug: a single shared guard check aborts the whole operation for the victim every time it runs.

### Impact Explanation
Permanent operational DoS against the victim's ability to interact with new assets: the victim cannot mint/issue any synthetic debt token (borrowing is completely blocked since it always adds a new `debtToken` entry), cannot deposit new collateral types, and cannot receive msdTOKEN transfers of tokens not already in their list. Deposits already held remain withdrawable, so this is a temporary/griefing freeze of functionality rather than direct theft — matching the "temporary freezing of funds / reachable denial of service" impact class. Note also that `debtPositionOf`/`depositOf` iterate the victim's full list per call [6](#0-5) , so the attack additionally maximizes gas cost of every health check involving the victim (bounded by 30, so this alone is not the primary impact).

### Likelihood Explanation
High feasibility, low cost: the attacker pays only gas plus dust deposits (possibly a small `depositFee`) across up to 30 deposit tokens — no flash loan, oracle manipulation, or privileged role needed. The attack persists until the victim actively clears entries (transferring/withdrawing each dust position down to zero so `removeFromDepositTokensOfAccount` runs [7](#0-6) ), which the attacker can re-fill cheaply. Front-run timing: an attacker can fill the list in the same block the victim broadcasts an `issue`/`leverage` transaction, causing it to revert.

### Recommendation
Decouple "victim-initiated" list growth from externally-forced list growth:
- Only add to `depositTokensOfAccount`/`debtTokensOfAccount` when `_msgSender() == account_`, or track positions via a different mechanism (e.g., enumerable per-account balances computed on demand, or a whitelist of "tokens I opted into" set by the account itself).
- Alternatively, gate `DepositToken.deposit`'s `onBehalfOf_ != _msgSender()` path and inbound `transfer` list-adds behind an allowance/consent flag on the `Pool`.
- At minimum, make `addTo*TokensOfAccount` skip the cap check when the caller is `msg.sender`'s own action is impossible — i.e., count only entries the account created itself, so forced dust cannot consume the victim's slots.

### Proof of Concept
Hardhat (fork or local deployment) sketch:

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {IPool} from "../contracts/interfaces/IPool.sol";
import {IDepositToken} from "../contracts/interfaces/IDepositToken.sol";
import {IDebtToken} from "../contracts/interfaces/IDebtToken.sol";

contract MaxTokensGriefingTest is Test {
    IPool pool;          // deployed Pool proxy
    IDepositToken[] depositTokens; // all registered deposit tokens (<= 30)
    IDebtToken debtToken;
    IERC20 underlying;
    address victim = address(0xBEEF);
    address attacker = address(0xA77);

    function test_griefVictimTokenList() public {
        // 1. Attacker fills victim's deposit-token list with 1-wei deposits
        for (uint256 i; i < depositTokens.length; ++i) {
            IDepositToken dt = depositTokens[i];
            IERC20 u = dt.underlying();
            deal(address(u), attacker, 1);
            vm.startPrank(attacker);
            u.approve(address(dt), 1);
            dt.deposit(1, victim); // onBehalfOf_ = victim
            vm.stopPrank();
            assertEq(dt.balanceOf(victim) > 0, true);
        }

        assertEq(pool.getDepositTokensOfAccount(victim).length, 30);

        // 2. Victim now cannot issue any synthetic debt (adds a debt-token entry)
        vm.expectRevert(); // UserReachedMaxTokens()
        vm.prank(victim);
        debtToken.issue(1e18, victim);

        // 3. Victim also cannot receive a new deposit token type / deposit onBehalf
        //    and inbound msdTOKEN transfers of new tokens revert as well.
    }
}
```

Reproduction confirms the revert originates in `onlyIfAdditionWillNotReachMaxTokens` [1](#0-0)  and that recovery requires the victim to zero out each dusted position one at a time, after which the attacker can re-fill slots at dust cost.
