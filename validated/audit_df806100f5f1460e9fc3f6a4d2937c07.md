### Title
JSON response body breaks structure via unescaped exception message injection - (File: `framework/src/main/java/org/tron/core/services/http/GetRewardServlet.java`, `framework/src/main/java/org/tron/core/services/http/GetBrokerageServlet.java`)

### Summary
An anonymous HTTP API client can send a malformed `address` parameter to unauthenticated query endpoints (`/wallet/getreward`, `/wallet/getbrokerage`) whose decode error message is concatenated, unescaped, directly into a hand-built JSON string. Because the underlying decoder's exception message can itself contain the offending raw character from the attacker-supplied input, an attacker can break out of the intended `"Error"` string and inject arbitrary additional JSON content into the API response — the same root-cause class as CVE-2016-9468 (partially user-controllable exception text rendered verbatim into a client-facing response, causing misrepresentation of information).

### Finding Description
`GetRewardServlet.doGet` and `GetBrokerageServlet.doGet` call `Util.getAddress(request)` to decode the `address` request parameter: [1](#0-0) 

`getAddress` routes non-hex-prefixed input through `decodeFromBase58Check`, which uses `Base58.decode`. When it encounters an invalid character, `Base58.decode` throws `IllegalArgumentException("Illegal character " + c + " at " + i)`, embedding the raw offending character verbatim in the exception message: [2](#0-1) 

Both servlets catch `DecoderException | IllegalArgumentException` and manually build a JSON string by string-concatenating `e.getMessage()` directly into the response, without escaping quotes, backslashes, or control characters: [3](#0-2) 

The equivalent unescaped pattern exists in `GetBrokerageServlet`: [4](#0-3) 

Because the character that triggers the exception is exactly the character supplied by the attacker in the `address` query parameter, an attacker can choose that character to be a JSON metacharacter (e.g. `"`), causing the emitted message to prematurely close the `"Error"` string value and let the attacker append arbitrary additional JSON keys/values (or malformed trailing content) into the HTTP response body that the node serves. This is analogous to the DAV content-spoofing bug: an exception message containing attacker-influenced text is rendered verbatim into a response consumed by clients, letting the attacker misrepresent the actual server-generated content of that response.

### Impact Explanation
Any downstream consumer of these unauthenticated JSON API endpoints (wallets, exchanges, monitoring tools, other automated integrations) that parses the response object could be shown attacker-fabricated fields/values appended after the injected break-out, since the JSON is built by naive string concatenation rather than a JSON serializer that escapes special characters. This matches the "misrepresentation of information" impact class of CVE-2016-9468 — it is a content-spoofing/response-integrity issue on a reachable, unauthenticated query path, not privilege escalation or fund theft, but it can deceive clients into trusting attacker-controlled content presented as if it were the node's own response.

### Likelihood Explanation
High reachability: `GetRewardServlet` and `GetBrokerageServlet` are unauthenticated GET/POST HTTP endpoints reachable by any anonymous client with a single crafted `address` parameter — no signed transaction or special permission is required, matching the "anonymous API client" reach criterion.

### Recommendation
Replace manual string concatenation of exception messages into JSON in `GetRewardServlet` and `GetBrokerageServlet` with a proper JSON serializer (e.g., the existing `JSONObject`/Jackson usage elsewhere in the codebase, such as in `Util.printErrorMsg`-style helpers but with correct escaping) so any embedded quotes/control characters in decoder exception messages are escaped rather than rendered verbatim. More broadly, sanitize/escape all exception messages that may echo raw request data before including them in HTTP responses.

### Proof of Concept
1. Send `GET /wallet/getreward?address=<58-char string containing a literal double-quote character as one of the base58check-length characters>` to a java-tron full node's HTTP API.
2. `Util.getAddress` → `decodeFromBase58Check` → `Base58.decode` throws `IllegalArgumentException("Illegal character \" at <i>")`.
3. `GetRewardServlet`'s catch block builds: `"{\"Error\": " + "\"INVALID address, " + e.getMessage() + "\"}"`, producing a response where the embedded `"` from the attacker's input closes the JSON string early, e.g.:
   `{"Error": "INVALID address, Illegal character " at 12", <attacker can shape remaining bytes to append arbitrary JSON>}`
4. A client parsing this response can be misled into interpreting attacker-influenced fields as authoritative node output.
