### Title
StackerDB chunk-freshness check is duplicated with inconsistent equality semantics between the network validator and the storage layer - ([File: stackslib/src/net/stackerdb/mod.rs] / [File: stackslib/src/net/stackerdb/db.rs])

### Summary
`PeerNetwork::validate_received_chunk` and `StackerDBTx::try_replace_chunk` independently reimplement the same "is this chunk version fresh enough to accept" check, but they use different comparison operators at the version-equality boundary. This is exactly the code-duplication anti-pattern described in the external report (two independent, hand-maintained copies of the same validation logic that can silently drift), and here the drift has a concrete, observable consequence: the network-facing gate can accept and advertise a chunk version that the storage layer will reject.

### Finding Description
`validate_received_chunk` treats a chunk as fresh unless its version is *strictly less than* the expected (currently stored) version: [1](#0-0) 

Meanwhile, `StackerDBTx::try_replace_chunk` — the function that actually performs the DB write — treats a chunk as stale (and rejects it) if its version is *less than or equal to* the currently stored version: [2](#0-1) 

Both `expected_version` (in `validate_received_chunk`) and `slot_validation.version` (in `try_replace_chunk`) are sourced from the same underlying stored-version bookkeeping (`get_slot_versions` / `get_slot_validation`), so they represent the same quantity. The two independently-implemented equality checks therefore disagree exactly at the boundary case `chunk.slot_version == current_stored_version`: `validate_received_chunk` says "valid," `try_replace_chunk` says "stale, reject."

This matters because `validate_received_chunk`'s result is used to decide whether an unsolicited pushed chunk should be treated as valid, have the local `StackerDBChunkInv` inventory patched to reflect the (unwritten) version, and be forwarded/relayed to the network, in `handle_unsolicited_StackerDBPushChunk`: [3](#0-2) 

Here, once `validate_received_chunk` returns `true`, the code unconditionally patches the outgoing inventory (`*slot_version = chunk_data.chunk_data.slot_version;`) and replies to the sender / forwards to the relayer — before the chunk has actually been durably stored via `try_replace_chunk`. For the boundary case (`slot_version == expected_version`), this inventory patch is a no-op value-wise, but it still causes the node to acknowledge/relay a chunk whose actual persistence attempt (later, via the relayer calling into `db.rs`) will fail with `StaleChunk`, per the differing `<=` semantics in `try_replace_chunk`.

### Impact Explanation
Because the two duplicated checks disagree at the boundary, a node can advertise/acknowledge (and instruct peers to wake up and resync around) a chunk version that will never actually be committed to its own StackerDB (rejected as `StaleChunk` at the storage layer). This breaks the invariant that "what a node advertises as its StackerDB inventory equals what it can actually serve," i.e., non-canonical/inconsistent state being reflected in inventory responses that peers rely on to schedule downloads. This matches the "serving non-canonical state as canonical" class of High-impact findings for StackerDB gossip, since it can cause peers to believe an update is available/valid and adjust their download/priority scheduling and wake up sync state machines based on state that isn't actually persisted.

### Likelihood Explanation
This is triggered purely by resubmitting a chunk with the same slot_version as the currently-stored one (no privileged key needed beyond the legitimate slot signer, and the signature check itself is unaffected by this bug — it's the freshness/equality check that diverges). This can happen naturally (e.g., a legitimate signer's re-push racing with a state read) or be deliberately induced by a remote peer sending a `StackerDBPushChunk` whose `slot_version` exactly equals the version already reflected in `expected_versions`/`slot_versions` known to the target node.

### Recommendation
Consolidate the version-freshness check into a single shared function/constant semantic (e.g., always reject `slot_version <= stored_version`) used by both `validate_received_chunk` (`stackslib/src/net/stackerdb/mod.rs`) and `try_replace_chunk` (`stackslib/src/net/stackerdb/db.rs`), eliminating the duplicated, independently-maintained comparison logic, consistent with the original report's recommendation to avoid unnecessary reimplementation of equivalent checks.

### Proof of Concept
1. Establish a StackerDB slot at version `V` on victim node `N` (legitimately signed by the slot's authorized key).
2. Send `N` an unsolicited `StackerDBPushChunk` with `slot_version == V` (the current stored version) and a valid signature over that payload.
3. `handle_unsolicited_StackerDBPushChunk` → `validate_received_chunk` compares `V < V` → `false`, so the chunk is treated as *not stale* and accepted at the network-validation layer: [1](#0-0) 
4. The inventory-patch / relay path proceeds (`*slot_version = V`, node replies/forwards/wakes up the sync state machine) as if the chunk is valid new data: [4](#0-3) 
5. When the relayer eventually attempts to actually persist this chunk via `try_replace_chunk`, the check `V <= V` is `true`, so it is rejected with `Error::StaleChunk`: [2](#0-1) 
6. Result: the node has acted on/relayed/acknowledged a chunk update that is never actually stored, demonstrating the inventory/storage inconsistency caused by the duplicated, non-identical validation logic.
