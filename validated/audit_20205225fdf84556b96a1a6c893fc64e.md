This confirms the analog. `checkPermissionOperations` in `TransactionUtil.java` only checks the permission's own stored 32-byte `operations` bitmap against the requested `Contract.getType()` value — it never re-validates against the current `DynamicPropertiesStore.getAvailableContractType()`. That re-validation only happens once, at `AccountPermissionUpdateActuator.checkPermission()` time, when the permission is created/updated.

### Title
Active multisig permissions retain approval for contract types after they are disabled from `AvailableContractType`, allowing indefinite unauthorized operation execution - (File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java, actuator/src/main/java/org/tron/core/utils/TransactionUtil.java)

### Summary
`AccountPermissionUpdateContract` lets an account owner grant an `Active` permission a 256-bit `operations` bitmap enumerating which `ContractType`s that key set may authorize. At creation/update time, the actuator checks each bit against `DynamicPropertiesStore.getAvailableContractType()` so an operation cannot be enabled unless it is currently a valid/enabled contract type. However, once granted, that approval (the bit in `operations`) is never revisited or cleared — this mirrors the AssetManager bug where token/adapter approvals are set once and never cleared on removal.

### Finding Description
`AccountPermissionUpdateActuator.checkPermission()` enforces, only at the time of permission creation/update, that every enabled bit in `permission.getOperations()` maps to a currently valid contract type: [1](#0-0) 

That validated bitmap is persisted into the account's `ActivePermission` via `updatePermissions()`: [2](#0-1) 

The actual authorization check performed for every subsequent multisig transaction is `TransactionUtil.checkPermissionOperations()`, which reads the persisted `operations` bitmap directly and tests the bit for the incoming contract's `getTypeValue()` — with no re-check against the currently available/enabled contract type list: [3](#0-2) 

This is used from `getTransactionSignWeight()` for computing whether a permission has "enough" signing weight to authorize a given transaction: [4](#0-3) 

Consequently, if a `ContractType` bit was validly enabled in an account's Active permission while that contract type was part of `getAvailableContractType()`, and the committee later disables that contract type (removes it from `AvailableContractType` via the corresponding proposal parameter, analogous to "removing an adapter/token"), any key holding that Active permission retains standing authorization to sign and execute that (now supposedly disabled) contract type indefinitely — because the bit is never cleared and the runtime check never re-validates against the live availability list.

### Impact Explanation
If a contract type is disabled system-wide (e.g., due to a discovered vulnerability in that actuator, analogous to the malicious/vulnerable "adapter" or "token" being removed in the original report), accounts that previously delegated multisig Active-permission authority for that operation type to a co-signer/subkey continue to permit that co-signer to construct and sign transactions of that disabled type. This is an unauthorized account operation: a key that should no longer be able to invoke that functionality (because the system decided it is unsafe/removed) can still exercise it, potentially executing an operation the network intended to block, using the owner account's balance/authority. This matches the "concrete unauthorized account operation" acceptance criterion.

### Likelihood Explanation
This requires: (1) an account owner to have previously granted an Active permission with a specific contract-type bit enabled (a normal `AccountPermissionUpdateContract` transaction, reachable by any account with multisign enabled), and (2) the committee subsequently disabling that contract type via `AvailableContractType`. Given that `AvailableContractType` is a maintained security parameter (used specifically to disable problematic contract types), and that permission grants are long-lived and rarely revisited by users, this is a realistic, medium-likelihood scenario mirroring the original report's threat model of "a critical issue found in an adapter/token that was used and removed long ago."

### Recommendation
Re-validate `permission.getOperations()` against the live `DynamicPropertiesStore.getAvailableContractType()` inside `TransactionUtil.checkPermissionOperations()` (or wherever authorization is finally decided, e.g. `TransactionCapsule`'s validate path) at execution time, not only at permission-update time. Alternatively, provide/require a mechanism that forces re-validation or automatic clearing of the corresponding operation bits across all accounts' active permissions when a contract type is removed from `AvailableContractType`.

### Proof of Concept
1. Committee enables `ContractType X` in `AvailableContractType`.
2. Account `A` (owner) submits `AccountPermissionUpdateContract` granting `Active` permission to key `B` with the operations bitmap bit for `X` set — validated successfully by `AccountPermissionUpdateActuator.checkPermission()`.
3. Committee later disables `ContractType X` via proposal, updating `AvailableContractType` to no longer include `X` (intended to prevent any future use of `X`, e.g. because `X`'s actuator was found unsafe).
4. Key `B` still constructs and signs a transaction of `ContractType X` on behalf of account `A`.
5. `TransactionUtil.checkPermissionOperations()` / equivalent signature-weight validation logic checks only `A`'s stored `operations` bitmap (still has bit `X` set) and does not consult the current `AvailableContractType`, so the transaction is accepted and executed — despite the network having disabled `X`.
