### Title
SSRF/DNS-rebinding protection bypass via unnormalized hostname in `http.curloptResolve` pinning - (File: internal/git/gitcmd/command_resolve.go)

### Summary
Gitaly's anti-DNS-rebinding mechanism for user-supplied remote URLs (`CreateRepositoryFromURL`, `FetchRemote`, `UpdateRemoteMirror`, `FindRemoteRootRef`) relies entirely on pinning `http.curloptResolve` to the caller-supplied `resolved_address`, keyed by the raw, unnormalized hostname string extracted from the URL. Because the hostname is never canonicalized, an attacker-controlled hostname whose textual representation legitimately differs from the form Git/curl uses internally for `--resolve` list matching (e.g. a trailing-dot FQDN) can cause the pin to silently fail to apply, letting Git fall back to live DNS resolution of the raw hostname at fetch time — reopening the exact DNS-rebinding/SSRF window the pinning was built to close.

### Finding Description
`gitcmd.GetURLAndResolveConfig` is Gitaly's implementation of GitLab's anti-SSRF/anti-DNS-rebinding contract: the caller (GitLab Rails) validates a remote URL's hostname against its blocklist, resolves it once to a safe IP, and passes both the original URL and that `resolved_address` to Gitaly so that the actual `git clone`/`git fetch` is forced to connect to the pre-validated IP instead of re-resolving DNS.

For HTTP(S)/git:// URLs, this pin is created in `getURLAndResolveConfigForURL`: [1](#0-0) 

The pin key is derived directly from `u.Hostname()`, produced by Go's `net/url.ParseRequestURI` with no normalization step (no trailing-dot stripping, no case-folding, no rejection of unusual host encodings), and the URL string handed back to the actual `git` invocation is the untouched `remoteURL`: [2](#0-1) 

This config is consumed verbatim in the reachable RPC paths without any further verification that the effective connection target matched the pin, e.g. in `CreateRepositoryFromURL`'s clone command builder: [3](#0-2) 

and in `FetchRemote`'s command-options builder: [4](#0-3) 

Since curl's own hostname matching for `--resolve`/`http.curloptResolve` entries is a literal string match against the hostname it derives internally from the URL, any divergence between that internal representation and the un-normalized string Gitaly places in the pin key (for example a trailing-dot FQDN, which public DNS resolvers treat as equivalent to the dotless form but which is not guaranteed to be canonicalized identically by both Go's `net/url` and curl's URL parser) causes the `--resolve` entry to simply not match. Curl does not error in that case — it transparently performs ordinary DNS resolution of the literal hostname at connection time. Gitaly performs no post-hoc check that the git process actually connected to `resolved_address`, so this failure mode is completely silent.

### Impact Explanation
The `resolved_address` pin is the sole technical enforcement, on Gitaly's side, of GitLab's SSRF validation decision for `CreateRepositoryFromURL` (project import-from-URL, reachable by any user permitted to create/import projects) and for `FetchRemote`/`UpdateRemoteMirror` (pull/push mirrors, also user-configurable features). If an attacker registers a domain that resolves to a public/allowed IP at GitLab's validation time (satisfying the Rails-side blocklist check) but crafts the URL's hostname in a form that defeats the pin match described above, they can re-point DNS for that hostname to an internal address (loopback, link-local metadata endpoint, internal service) before Gitaly's `git` process performs its own follow-up resolution. This results in Gitaly issuing HTTP/git requests to internal infrastructure on the attacker's behalf — the same class of impact (SSRF bypassing a validation step via an alternate-but-equivalent address representation) described in the source report, just realized through hostname-canonicalization mismatch instead of an IPv6 literal.

### Likelihood Explanation
Requires an attacker to control a public DNS record they can repoint between GitLab's validation call and Gitaly's `git` invocation, plus crafting the URL's hostname in a representation that diverges from curl's internal normalized form. This is a standard, low-cost DNS-rebinding setup, and the feature surface (import-from-URL, pull mirrors) is reachable by ordinary authenticated users with project-creation or mirror-configuration permissions — no privileged actor, leaked token, or malicious peer is needed.

### Recommendation
Canonicalize the hostname used to build the `http.curloptResolve` key in `getURLAndResolveConfigForURL` (lower-case, strip trailing dot, reject IDN/punycode ambiguity) so it is guaranteed to match the hostname string curl derives internally, and/or verify post-fetch (via `GIT_CURL_VERBOSE`/trace or a Git credential/host callback) that the connection was actually made to `resolved_address` before treating the fetch as successful. Consider failing closed (aborting the fetch) rather than silently falling back to unrestricted DNS resolution whenever the `--resolve` pin cannot be confirmed to apply.

### Proof of Concept
1. Attacker registers `evil.example.` (note trailing dot) and points it to a public IP.
2. Attacker submits `CreateRepositoryFromURL` with `url = "http://evil.example./repo.git"` via GitLab's import-from-URL feature (or a pull mirror configuration).
3. GitLab Rails resolves `evil.example.` (public IP), passes the safe `resolved_address` to Gitaly.
4. Gitaly's `getURLAndResolveConfigForURL` builds `http.curloptResolve = evil.example.:80:<safe-ip>` from the unmodified hostname string [2](#0-1) .
5. Before/while Gitaly's `git clone` executes, the attacker repoints `evil.example.` DNS to `169.254.169.254` or another internal address.
6. If curl's internal host-matching for the `--resolve` entry does not treat `evil.example.` and `evil.example` as identical, the pin fails to apply, curl performs a live DNS lookup, and Gitaly's git process connects to the attacker-controlled internal address — bypassing the SSRF protection that `resolved_address` was designed to guarantee.

```go
func getURLAndResolveConfigForURL(remoteURL, resolvedAddress string) (string, []ConfigPair, error) {
	u, err := url.ParseRequestURI(remoteURL)
	if err != nil {
		return "", nil, fmt.Errorf("couldn't parse remoteURL: %w", err)
	}

	port := u.Port()

	if port == "" {
		switch u.Scheme {
		case "http":
			port = "80"
		case "https":
			port = "443"
		case "git":
			port = "9418"
		default:
			return "", nil, fmt.Errorf("unknown schema provided: %s", u.Scheme)
		}
	}

	return remoteURL, []ConfigPair{
		{Key: "http.curloptResolve", Value: fmt.Sprintf("%s:%s:%s", u.Hostname(), port, resolvedAddress)},
	}, nil
}
```
