### Title
Replay-window check/update race allows duplicate decryption of a replayed data packet - (File: connection_state.go)

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` split the nonce/replay check into two separately-locked steps with the expensive AEAD decrypt operation performed *outside* the lock, in between them. This mirrors the Juicebox `checks-effects-interactions` violation: the "check" (replay window `Check`) and the "effect" (replay window `Update`, which actually records the nonce as seen) are separated by an unlocked "interaction" (the decrypt call), giving a concurrent caller a window to reuse the same nonce before it is marked consumed.

### Finding Description
`Decrypt` takes `decryptLock`, calls `cs.window.Check(l, messageCounter)` to confirm the counter has not been seen, releases the lock, performs `cs.dKey.DecryptDanger(...)` without holding any lock, then re-acquires `decryptLock` only afterward to call `cs.window.Update(l, messageCounter)`, which is what actually marks the counter as consumed: [1](#0-0) 

The identical pattern exists in `VerifyRelay`, used on the relay data path: [2](#0-1) 

Nebula reads inbound UDP packets on multiple concurrent routines (`f.readers[q]`, one per `tun.routines`/listener routine), and every routine can call `readOutsidePackets` → `hostinfo.ConnectionState.Decrypt` for the *same* `HostInfo`/`ConnectionState` concurrently: [3](#0-2) 

Because `Check` and `Update` are not atomic together (the lock is dropped in between), two goroutines that receive the same wire packet (a replay) at nearly the same time can both pass `Check` before either calls `Update`. Both then successfully decrypt and process the packet as legitimate traffic (or, for relay frames, both re-forward it), even though `window.Update` is designed to reject the second occurrence of the same counter. This is analogous to the reported Solidity bug: the "check" happens, an external/interruptible operation (a reentrant call in Solidity; a decrypt performed outside the lock here) runs, and only afterward is the state ("effects") committed — leaving a window where the safety invariant (no duplicate nonce processing) can be violated.

### Impact Explanation
A successful race lets an attacker who can duplicate/replay a captured on-wire packet (no valid CA-signed certificate required — this is a post-handshake data-plane/relay nonce check, reachable by any party that can inject or duplicate UDP datagrams toward the target, e.g. a relay peer or a network-level attacker performing packet duplication) get that packet decrypted and delivered twice on the receiving host, or — on a relay node — get a captured relay frame forwarded twice toward the target, defeating the intended nonce/replay-window remote-state protection guarantee. This directly undermines the "advance the replay window on relayed packets" fix referenced in the CHANGELOG (#1751/#1802), because the fix only serializes each individual `Check`/`Update` call, not the check-decrypt-update sequence as a whole.

### Likelihood Explanation
Exploitability requires winning a race between two packet-processing goroutines on the same `ConnectionState`, which is plausible whenever `tun.routines`/multiple UDP reader routines are configured (a common, documented Nebula deployment option) and an attacker can deliver (or a relay naturally delivers) the same ciphertext to more than one reader routine within the small window between `Check` returning and `Update` being called. The AEAD decrypt operation is the interposed work, giving a realistic — if narrow — timing window, especially on busy/multi-core hosts. This is a genuine race rather than a certainty, so likelihood is moderate; it also requires an attacker able to duplicate packets on the wire (achievable via NIC-level duplication, malicious relay behavior toward this check, or simple resend timing) but does not require holding any legitimate certificate.

### Recommendation
Hold `decryptLock` for the entire check-decrypt-update sequence in both `Decrypt` and `VerifyRelay`, so that `Check`, the AEAD operation, and `Update` execute atomically with respect to other decrypting goroutines for the same `ConnectionState`. If lock contention/performance is a concern, use a single lock acquisition that only releases after `window.Update` has definitively recorded the counter, or restructure the replay window so `Check`+reserve is a single atomic operation (reserve-then-confirm/rollback-on-failure) instead of check-then-later-mark.

### Proof of Concept
Conceptual/timing-based PoC (not independently executed against a live build):
1. Establish a tunnel between two nebula nodes with `tun.routines`/`listen.routines` > 1 so multiple goroutines can concurrently call `readOutsidePackets`.
2. Capture one legitimate encrypted data packet (or relay frame) with message counter N.
3. Duplicate this packet and inject both copies onto the UDP socket at (near-)the same time, either from an attacker positioned on the same network segment or by controlling a relay node forwarding to the victim, so they land on two different reader routines.
4. If both goroutines' `cs.window.Check(l, N)` calls execute before either goroutine's `cs.window.Update(l, N)` call, both `Decrypt`/`VerifyRelay` calls succeed, and the payload is processed/forwarded twice — demonstrating a bypass of the intended one-time nonce consumption guarantee described in `bits.go`'s `Check`/`Update` contract: [4](#0-3)

func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}

// Update has three branches:
//   - i == b.current+1: fast path; advance the cursor by one and lose-count
//     the slot we just stomped (only past warmup; see the i > b.length guard
//     below).
//   - i  >  b.current+1: jump path; clear all slots between current and i
//     (or up to a full window's worth, whichever is smaller) via clearRange,
//     then mark i. Two arms here: a warmup arm that handles the very first
//     window before the cursor has slid, and a steady-state arm that treats
//     every cleared empty slot as a lost packet.
//   - i  <= b.current: in-window check for duplicates; out-of-window otherwise.
//
// NewBits seeds bits[0]=1 so counter 0 looks "received" — Update never
// clears that marker during warmup (clearRange skips position 0 when
// startPos=1), and once b.current >= b.length the marker is no longer
// consulted. The marker prevents a fictitious "lost" hit on the first real
// counter.
func (b *Bits) Update(l *slog.Logger, i uint64) bool {
	// Fast path: i is the next expected counter. Split out so the function
	// stays small and avoids paying for the slow paths' slog argument-build
	// stack frame on every call. The bit read/test/write is inlined to
	// touch the backing word once.
	if i == b.current+1 {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if i > b.length && w&mask == 0 {
			b.lostCounter.Inc(1)
		}
		b.bits[word] = w | mask
		b.current = i
		return true
	}
	return b.updateSlow(l, i)
}
