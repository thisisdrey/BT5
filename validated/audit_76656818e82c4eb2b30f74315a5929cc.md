## Analysis

Confirmed analog vulnerability. The root cause mirrors the reported bug precisely: a signature is computed over a digest that omits a required "domain" component, so a signature that is valid in one context is also valid in an unintended context.

### Title
StackerDB chunk signatures omit the target contract/lane, enabling cross-StackerDB signature replay - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` computes the signed digest as `hash(slot_id || slot_version || data_hash)` only — it never binds the signature to the specific StackerDB smart contract (`QualifiedContractIdentifier`) being written to. Because the Stacks signer boot contracts (`signers-0-1`, `signers-0-2`, `signers-0-3`, ..., one per message lane) assign the *same* slot index to the *same* signer address for a given reward-cycle "page", a chunk legitimately signed and posted by a signer to one lane is also a validly-signed chunk for every sibling lane's identically-indexed slot. Any observer of the (public, unauthenticated) gossip can replay that chunk into a different StackerDB contract, where it will pass signature/version/size validation and be stored and re-broadcast network-wide.

### Finding Description
The signing digest is defined as: [1](#0-0) 

Note it hashes only `slot_id`, `slot_version`, and `data_hash` — there is no contract ID, message-type/lane identifier, network ID, or reward-cycle value mixed in. `verify()` recovers the pubkey from this same digest and checks it against the pubkey-hash configured for that slot in *whatever* contract is asking: [2](#0-1) 

The storage-layer check (`try_replace_chunk`) only consults the `signer` address recorded for that `slot_id` in the target contract's own slot table, and otherwise checks version/size — it never checks which contract the signature was originally computed "for": [3](#0-2) 

The slot→signer assignment is guaranteed identical across sibling lane-contracts by design: all `signers-0-X` contracts (one per message ID) read the exact same signer-slot page from the shared `.signers` contract: [4](#0-3) [5](#0-4) 

So for a given reward-cycle "page" (0 or 1), signer S is assigned the *same* `slot_id` in the `BlockResponse` lane (`signers-0-1`), `StateMachineUpdate` lane (`signers-0-2`), and `BlockPreCommit` lane (`signers-0-3`) simultaneously (message IDs from `MessageSlotID`): [6](#0-5) 

Because the signed digest never includes which of these three contracts the chunk is destined for, a `StackerDBChunkData{slot_id, slot_version, sig, data}` that S legitimately posted to `signers-0-1` is *also* a validly-signed chunk for the identical `slot_id` in `signers-0-2` / `signers-0-3`, provided the target slot's currently-stored version is lower.

At the P2P/relay layer, incoming chunks are validated purely against this scoped-but-domain-less signature/version check and, once accepted, are stored and unconditionally rebroadcast to the network — with no awareness of message "lane" semantics: [7](#0-6) [8](#0-7) 

Any unprivileged remote peer that observes a broadcast `StackerDBPushChunk`/`StackerDBChunkData` (this is normal, unauthenticated gossip) can immediately re-submit the identical bytes against a different lane-contract for the same signer set. The write passes `try_replace_chunk`'s signer/version/size checks (equalities the code intends to enforce — "is this data authenticated *for this replica*" — silently fail open because the signature never encoded "this replica") and the forged-context chunk gets stored and further gossiped to the whole network.

### Impact Explanation
This is an unauthenticated write into StackerDB state attributable to a signer who never wrote it there, plus network-wide propagation of that forged data via `process_stacker_db_chunks`'s unconditional `broadcast_message`. That matches the Critical bucket: "unauthenticated/unauthorized write to state or StackerDB, network-wide propagation of forged data." Downstream, higher layers (e.g. `libsigner`'s `signer_message_payload_matches_lane` filter) may reject content whose serialized type-byte prefix doesn't match the target lane's expected type, which limits — but does not eliminate — the blast radius (the store-and-forward write and node-wide propagation already happened before any such filtering runs, and any consumer that does not perform that extra type check would process attacker-selected stale-but-validly-signed content as current).

### Likelihood Explanation
High. No secret is required — only observation of ordinary, public StackerDB gossip (or reading a chunk via the existing GET-chunk RPC) and a single re-POST/re-broadcast to a sibling contract. The precondition (same slot assignment across sibling `signers-0-X` / `signers-1-X` contracts within a reward-cycle page) is guaranteed by the `.signers` boot contract design, not by coincidence.

### Recommendation
Bind the `SlotMetadata`/`StackerDBChunkData` signature to the specific replica it authorizes writes for, e.g. include the `QualifiedContractIdentifier` (or a fixed per-contract domain tag) and ideally a network identifier in `auth_digest()`:
```rust
fn auth_digest(&self, contract_id: &QualifiedContractIdentifier) -> Sha512Trunc256Sum {
    let mut hasher = Sha512_256::new();
    hasher.update(contract_id.serialize_to_vec());
    hasher.update(self.slot_id.to_be_bytes());
    hasher.update(self.slot_version.to_be_bytes());
    hasher.update(self.data_hash.0);
    Sha512Trunc256Sum::from_hasher(hasher)
}
```
This requires threading the target contract ID through `sign`/`verify`/`recover_pk` in `libstackerdb/src/libstackerdb.rs`, `try_replace_chunk` in `stackslib/src/net/stackerdb/db.rs`, and `validate_received_chunk` in `stackslib/src/net/stackerdb/mod.rs`, and is a signature-format/wire-compatibility-breaking change requiring a coordinated upgrade — analogous to the report's recommendation to add and initialize a proper domain separator.

### Proof of Concept
1. Observe (as any unprivileged peer) a valid `StackerDBPushChunk` gossip message for contract `signers-0-1` (BlockResponse lane) from signer S: `{slot_id: k, slot_version: v, sig, data}` (`stackslib/src/net/relay.rs:2445-2452`).
2. Confirm via the public `.signers` boot contract state that S also owns `slot_id = k` in `signers-0-2` (StateMachineUpdate lane) for the current cycle page — guaranteed by `signers-0-xxx.clar`'s shared `stackerdb-get-signer-slots-page` call.
3. Re-POST the identical `StackerDBChunkData{slot_id: k, slot_version: v, sig, data}` to `signers-0-2` via the standard `/v2/stackerdb/.../chunks` endpoint (or rebroadcast as `StackerDBPushChunk` at the P2P layer) as long as `signers-0-2`'s stored version at slot `k` is `< v`.
4. `SlotMetadata::verify()` succeeds (`libstackerdb/src/libstackerdb.rs:181-193`) because the digest never encoded which contract it was for; `try_replace_chunk` (`stackslib/src/net/stackerdb/db.rs:398-437`) accepts and stores the chunk under `signers-0-2`; `process_stacker_db_chunks`/relay logic then rebroadcasts it network-wide as though S authored it for that lane.

                slot_desc.slot_id,

            });
