## Analog Found: Fire-and-forget XCM reward payout in Snowbridge relayer rewards can silently fail to deliver funds, causing permanent loss to the relayer

The external report's core defect is: a value-transfer primitive that can *fail silently* for a class of legitimate recipients (limited gas / stipend), while the caller-side accounting treats the transfer as already completed. The closest local analog is `snowbridge_core::reward::PayAccountOnLocation::pay_reward`, used by BridgeHub's `claim_rewards_to` extrinsic.

### Title
Unverified fire-and-forget XCM in Snowbridge reward payout can permanently lose relayer rewards - (File: `bridges/snowbridge/primitives/core/src/reward.rs`)

### Summary
`pallet_bridge_relayers::claim_rewards_to` is a public, unprivileged extrinsic that lets a relayer redeem an already-accrued reward to an arbitrary beneficiary `Location` on AssetHub via `PayAccountOnLocation::pay_reward`. The reward record is deleted from on-chain storage as soon as the XCM message is *accepted for delivery* (`XcmSender::deliver` returns `Ok`), not when the `DepositAsset` on the destination chain actually succeeds. If the destination `DepositAsset` fails (e.g., beneficiary account doesn't exist and doesn't meet AssetHub's existential deposit, or is otherwise unable to receive the asset), the reserve-asset deposit gets trapped on AssetHub while BridgeHub has already irreversibly cleared the reward entry, so the relayer permanently loses the reward — mirroring the original bug class where a native-value transfer can silently fail for a legitimate recipient while the caller's bookkeeping assumes success.

### Finding Description
`do_claim_rewards` in [1](#0-0)  uses `try_mutate_exists` to take the stored reward, call `T::PaymentProcedure::pay_reward`, and only commits the storage removal if `pay_reward` returns `Ok`. For the Snowbridge reward kind, `pay_reward` resolves to `PayAccountOnLocation::pay_reward` in [2](#0-1) , which builds an `UnpaidExecution`/`ReserveAssetDeposited`/`DepositAsset` XCM program and calls `XcmSender::deliver(ticket)`. As soon as `deliver` returns `Ok`, the function returns `Ok(())`, `try_mutate_exists` commits the reward removal, and `RewardPaid` is emitted — all *before* the XCM program actually executes on AssetHub.

`deliver` returning `Ok` only means the message was successfully queued/routed (e.g., accepted into the HRMP channel); it provides no guarantee that the remote `DepositAsset { assets: AllCounted(1), beneficiary }` instruction succeeds. If the beneficiary `Location` cannot receive the asset (non-existent account below AssetHub's existential deposit, a filtered/blocked account, or any other execution failure of that single instruction), the deposited reserve asset is trapped (`AssetTrap`) rather than credited to the intended relayer, exactly as the original report describes a "successful" `.transfer()` call at the EVM opcode level masking an unusable recipient at the application level.

### Impact Explanation
This directly matches the "duplicate settlement or payout" / "permanent user-fund or bridge-state lock" impact category: the relayer's accrued, unpaid reward is deleted from `RelayerRewards` storage based only on local message-queuing success, not on remote settlement. Any unprivileged relayer who supplies (or is tricked/mistaken into supplying) an `AssetHubLocation` beneficiary that cannot accept the deposit on AssetHub loses their reward permanently with no local retry or reconciliation path — there is no receipt-based confirmation loop tying the BridgeHub-side "paid" state back to actual AssetHub-side settlement.

### Likelihood Explanation
The `claim_rewards_to` call path is fully public and unprivileged — [3](#0-2)  only requires `ensure_signed(origin)`. No existence/ED check is performed on the `beneficiary` `Location` before the storage mutation commits, and `pay_reward`'s only validation is `Location::try_from(account_location)` for version conversion. A relayer specifying a not-yet-existing AssetHub account (a very plausible operational mistake, since accounts need to be seeded with ED to exist) triggers the loss deterministically, without needing any malicious peer, validator, or governance actor.

### Recommendation
Do not treat XCM `deliver() == Ok` as final settlement confirmation for reward accounting. Options:
- Keep the reward pending until a delivery/execution receipt (already used elsewhere in Snowbridge's V2 flow, e.g. `DeliveryReceipt`/`process_delivery_receipt`) confirms the remote `DepositAsset` succeeded, only then clear `RelayerRewards`.
- Alternatively, validate that the beneficiary account exists / meets ED on the destination chain before allowing storage removal, or provide a safe fallback/re-credit path if the XCM program traps the assets.
This mirrors the report's fix pattern: don't finalize the "transfer succeeded" state based on a low-assurance send primitive; use a mechanism that actually confirms receipt (`.call()` forwarding all gas and checking the return value, vs. relying on `.transfer()`'s narrow, easily-exceeded gas stipend).

### Proof of Concept
1. Relayer accrues a Snowbridge reward via `pallet_bridge_relayers::register_reward` (done automatically on message delivery, see `RewardRegistered` events in [4](#0-3) ).
2. Relayer signs `claim_rewards_to(BridgeReward::Snowbridge, BridgeRewardBeneficiaries::AssetHubLocation(loc))` where `loc` encodes an `AccountId32` that has never been funded on AssetHub (below existential deposit).
3. `do_claim_rewards` takes the reward from storage, calls `PayAccountOnLocation::pay_reward`, which builds the XCM and calls `XcmSender::deliver` — this succeeds (message is routed to AssetHub) so `pay_reward` returns `Ok`, and the `try_mutate_exists` closure commits, deleting the reward and emitting `RewardPaid`.
4. On AssetHub, the `DepositAsset { assets: Wild(AllCounted(1)), beneficiary: loc }` instruction fails because the target account does not exist / cannot satisfy ED, and the reserve-deposited asset is trapped.
5. The relayer has no reward left in storage (step 3) and never receives the funds (step 4) — permanent loss, with no automatic recovery.

		fn do_claim_rewards(
			relayer: T::AccountId,
			reward_kind: T::Reward,
			beneficiary: BeneficiaryOf<T, I>,
		) -> DispatchResult {
			RelayerRewards::<T, I>::try_mutate_exists(
				&relayer,
				reward_kind,
				|maybe_reward| -> DispatchResult {
					let reward_balance =
						maybe_reward.take().ok_or(Error::<T, I>::NoRewardForRelayer)?;
					T::PaymentProcedure::pay_reward(
						&relayer,
						reward_kind,
						reward_balance,
						beneficiary.clone(),
					)
					.map_err(|e| {
						tracing::error!(
							target: LOG_TARGET,
							error=?e,
							?relayer,
							?reward_kind,
							?reward_balance,
							?beneficiary,
							"Failed to pay rewards"
						);
						Error::<T, I>::FailedToPayReward
					})?;

					Self::deposit_event(Event::<T, I>::RewardPaid {
						relayer: relayer.clone(),
						reward_kind,
						reward_balance,
						beneficiary,
					});
					Ok(())
				},
			)
		}

	fn pay_reward(
		relayer: &Relayer,
		_: (),
		reward: RewardBalance,
		beneficiary: Self::Beneficiary,
	) -> Result<(), Self::Error> {
		let ethereum_location = Location::new(2, [GlobalConsensus(EthereumNetwork::get())]);
		let assets: Asset = (ethereum_location.clone(), reward.into()).into();

		let xcm: Xcm<()> = alloc::vec![
			UnpaidExecution { weight_limit: Unlimited, check_origin: None },
			DescendOrigin(InboundQueueLocation::get().into()),
			UniversalOrigin(GlobalConsensus(EthereumNetwork::get())),
			ReserveAssetDeposited(assets.into()),
			DepositAsset { assets: AllCounted(1).into(), beneficiary },
		]
		.into();

		let (ticket, fee) =
			validate_send::<XcmSender>(AssetHubLocation::get(), xcm).map_err(|_| XcmSendFailure)?;
		XcmExecutor::charge_fees(relayer.clone(), fee).map_err(|_| ChargeFeesFailure)?;
		XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;

		Ok(())
	}
