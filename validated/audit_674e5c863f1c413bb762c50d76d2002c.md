### Title
Unbounded storage of unverified attachment content via missing hash-match check and missing cap in `insert_instantiated_attachment` - ([File: stackslib/src/net/atlas/download.rs, stackslib/src/net/atlas/db.rs])

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` (download.rs:530-558) decodes a peer's `GetAttachmentResponse` and inserts `response.attachment` into `self.attachments` without ever checking that `attachment.hash()` equals the `content_hash` that was actually requested. `AttachmentsDownloader::run` (download.rs:153-169) then unconditionally calls `insert_instantiated_attachment` (db.rs:576-592) for every drained attachment, regardless of whether `find_all_attachment_instances` returned any matching, consensus-committed `AttachmentInstance`. Unlike `insert_uninstantiated_attachment` (db.rs:511-536), which enforces `max_uninstantiated_attachments` via `evict_k_oldest_uninstantiated_attachments`, `insert_instantiated_attachment` has no size/count cap and no eviction path for `was_instantiated=1` rows.

### Finding Description
The equality that should hold — "every row persisted with `was_instantiated=1` corresponds to content whose hash matches a confirmed `AttachmentInstance.content_hash`" — is broken. When a node requests an attachment for a specific `content_hash` (derived from a confirmed, on-chain `AttachmentInstance`), a malicious/outbound peer serving the corresponding page can respond with an `Attachment` containing arbitrary, unrelated content. `decode_atlas_get_attachment()` only decodes the wire format; `extend_with_attachments` (download.rs:547-549) does not compare `response.attachment.hash()` against the request's target hash before inserting it into `self.attachments`.

In `AttachmentsDownloader::run` (download.rs:153-169), for each drained attachment the code calls `find_all_attachment_instances(&attachment.hash())` to look up matching confirmed instances, but calls `network.atlasdb.insert_instantiated_attachment(&attachment)` unconditionally — even when `attachments_instances` is empty (i.e., the served content hash matches nothing known). `insert_instantiated_attachment` (db.rs:576-592) simply does an `INSERT OR REPLACE` with `was_instantiated=1` and has no analogous cap/eviction logic like `insert_uninstantiated_attachment`'s `max_uninstantiated_attachments`/`evict_k_oldest_uninstantiated_attachments` (db.rs:511-536, 538-547).

An attacker controlling (or masquerading as) an outbound sync peer that is selected via `network.get_outbound_sync_peers()` can, for every `AttachmentRequest` in a batch, return a distinct, large, non-matching `Attachment`. Each such response is stored permanently as an instantiated attachment with zero binding to any confirmed on-chain `AttachmentInstance`.

### Impact Explanation
Repeated across many attachment batches/reward cycles, this allows a remote unprivileged peer to force unbounded growth of the `attachments` table (disk exhaustion) using content that was never committed to by consensus — matching the "serving non-canonical state as canonical" / attachment mismatch category, since garbage content is durably stored and indistinguishable in the DB from legitimately resolved attachments, with no cap or eviction mechanism to bound it.

### Likelihood Explanation
The attacker only needs to be selected as an outbound sync/data peer for a batch (a normal, permissionless P2P condition — no secret, no privileged role, no StackerDB ownership required beyond running a peer that the victim node dials for attachments) and respond to `AttachmentRequest`s with crafted `GetAttachmentResponse` payloads. This is repeatable indefinitely across batches/reward cycles at low attacker cost (each response merely needs to be well-formed enough to pass `decode_atlas_get_attachment`).

### Recommendation
In `extend_with_attachments` (download.rs:530-558), verify `response.attachment.hash() == request.content_hash` (or the equivalent expected hash from the `AttachmentRequest`) before inserting into `self.attachments`, discarding and penalizing (`bump_failed_requests`) mismatches. Additionally, add a cap/eviction mechanism to `insert_instantiated_attachment` (db.rs:576-592) analogous to `max_uninstantiated_attachments`/`evict_k_oldest_uninstantiated_attachments`, and/or only call `insert_instantiated_attachment` when `find_all_attachment_instances` returns a non-empty result in `AttachmentsDownloader::run` (download.rs:154-169).

### Proof of Concept
Rust test in `stackslib/src/net/atlas/download.rs` test module: construct an `AttachmentsBatchStateContext` for a batch requesting a known `content_hash` H (backed by a real `AttachmentInstance` inserted in `AtlasDB`); mock a peer's `BatchedRequestsResult<AttachmentRequest>::succeeded` with a `GetAttachmentResponse` whose `attachment.content` is large random bytes with hash `H' != H`; call `extend_with_attachments` and observe `self.attachments` contains the mismatched attachment; then drive `AttachmentsDownloader::run` to `Done` and assert `atlasdb.count_uninstantiated_attachments()`/a direct `SELECT COUNT(*) FROM attachments WHERE was_instantiated=1` row for hash `H'` exists despite `find_all_attachment_instances(&H')` being empty. Repeat with N distinct random contents across iterations and assert the `attachments` table row count grows linearly with N with no eviction, and no comparison against `attachments_max_size` occurs prior to insertion.
