This is confirmed. The tests exactly demonstrate the behavior: `pure_precompile_works` sends `value=100` to precompiles at addresses 1–9 (ECRecover, Sha256, Ripemd160, Identity, Modexp, Bn128Add/Mul/Pairing, Blake2F — all `HAS_CONTRACT_INFO = false`), and `Pallet::<Test>::evm_balance(&precompile_addr)` ends up `== U256::from(100)` [1](#0-0) , while `precompiles_work` with `value=0` shows no account/contract info is created [2](#0-1) . The transfer happens unconditionally for non-delegate calls in `do_transaction` before the precompile-specific account-creation branch, and that branch is gated strictly on `precompile.has_contract_info()` [3](#0-2) . No check exists in `precompiles.rs` or `exec.rs` that rejects non-zero `value_transferred()` for `HAS_CONTRACT_INFO = false` precompiles, and neither `ERC20::call` nor `XcmPrecompile::call` reads or forwards `env.value_transferred()`. This matches the claim precisely: unprivileged callers can attach value to a call into these addresses, funds get credited to a mapped account, and there is no mechanism found in this codebase for the precompile or anyone else to reclaim/spend from that account.

Audit Report

## Title
Native value sent to `HAS_CONTRACT_INFO = false` precompiles (e.g. ERC20/XCM/built-in math precompiles) is silently accepted and permanently locked - (File: `substrate/frame/revive/src/exec.rs`)

## Summary
`pallet-revive`'s `Stack::run`/`do_transaction` unconditionally transfers attached native `value` to a callee's mapped account for any non-delegate call, with no distinction for precompiles, before invoking the precompile's `call()` logic. Precompiles that declare `HAS_CONTRACT_INFO = false` (ERC20 asset precompile, XCM precompile, and built-in math precompiles like ECRecover/Sha256/Identity/Modexp/Bn128/Blake2F) neither read, forward, nor reject `value_transferred()`, so any non-zero value attached to a call targeting these addresses gets irrecoverably credited to an address with no contract logic or key able to spend it.

## Finding Description
In `Stack::run`'s `do_transaction`, the balance transfer runs unconditionally for non-delegate calls: `if frame.delegate.is_none() { Self::transfer_from_origin(...) }` [6](#0-5) . Immediately after, the only precompile-specific account-creation/consumer-protection logic is gated on `precompile.has_contract_info()` [7](#0-6) . The generic `transfer` function used underneath will pull a non-existent `to` account into existence — paying ED from `origin` and crediting `value` — whenever `value` is non-zero, independent of whether `to` is a precompile: `if <System<T>>::account_exists(to) { ... } else { ... pay ED ... }; transfer_with_dust::<T>(from, to, value, preservation)` [8](#0-7) .

The `HAS_CONTRACT_INFO` documentation states that when set to `false`, "No account or any other state will be created for the address" and "Only `call` should be implemented" [5](#0-4) . This is contradicted by the actual balance-credit behavior. The `pure_precompile_works` test empirically demonstrates this: sending value=100 to built-in `HAS_CONTRACT_INFO=false` precompiles (ECRecover, Sha256, Ripemd160, Identity, Modexp, Bn128*, Blake2F) results in `Pallet::<Test>::evm_balance(&precompile_addr) == U256::from(100)` [9](#0-8) , while the `precompiles_work` test with value=0 shows the account is never created for a `NoInfo` precompile [2](#0-1) , confirming the account-existence check in `exec.rs` is the deciding factor, not any value-rejection logic.

None of these precompiles' `call()` implementations check or reject `env.value_transferred()`. The `ERC20::call` dispatches directly to `transfer`/`approve`/etc. with no value handling [10](#0-9) , and likewise for `XcmPrecompile::call` [11](#0-10) . Because the affected precompiles' mapped accounts never receive the `mint_into`/`inc_consumers` treatment reserved for `has_contract_info()` precompiles, and no dispatchable or precompile function exists to move funds out of a precompile's mapped account, any value sent this way is permanently stranded.

## Impact Explanation
This is a permanent user-fund lock. An unprivileged caller attaching non-zero `value` to a call into any `HAS_CONTRACT_INFO = false` precompile address (built-in math precompiles at low addresses 1–9, the ERC20 asset precompile, or the fixed-address XCM precompile at address 10) has that value credited to an address with no spending authority and no recovery mechanism in the reviewed code.

## Likelihood Explanation
Any unprivileged external caller can trigger this trivially by attaching non-zero `value` to a standard call (e.g. an ERC20 `transfer`/`approve` call, or a math precompile call) targeting a well-known, discoverable precompile address — no special privileges, governance, or off-chain trust assumptions are required, and the bug is deterministically reproducible.

## Recommendation
Reject calls carrying non-zero `value_transferred()` before invoking `call()` for precompiles with `HAS_CONTRACT_INFO = false` that do not implement value handling — either via a generic check in `Stack::run`/`do_transaction` (e.g., skip/deny the transfer step when the target is a precompile without an explicit "accepts value" flag), or by having each such precompile's `call()` explicitly `ensure!(env.value_transferred().is_zero(), ...)` at the top.

## Proof of Concept
The existing `pure_precompile_works` unit test in `substrate/frame/revive/src/tests/pvm.rs` is itself the proof of concept: it calls built-in `HAS_CONTRACT_INFO=false` precompiles (addresses 1–9) with `value=100` and asserts `Pallet::<Test>::evm_balance(&precompile_addr) == U256::from(100)`, confirming the value is credited and not rejected [12](#0-11) . The companion `precompiles_work` test with `value=0` confirms no account exists absent a value transfer, isolating the transfer path as the root cause [13](#0-12) .
