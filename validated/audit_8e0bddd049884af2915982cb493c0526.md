### Title
Replay-window Check/Update race allows duplicate packet acceptance across multi-queue UDP readers - (File: connection_state.go)

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` split the anti-replay decision into two separately-locked steps (`window.Check` then, after the AEAD open, `window.Update`) instead of atomically checking-and-marking the message counter before doing the expensive decrypt work. When `listen.routines`/`tun.routines` is configured `>1`, multiple goroutines read from the underlay UDP socket concurrently and can invoke `Decrypt`/`VerifyRelay` for the *same* `ConnectionState` concentrated at (near-)identical message counters, allowing a replayed or duplicated packet to pass the `Check` step before the legitimate copy's `Update` call has recorded it, mirroring the reported bug class where a state-dependent decision was computed against stale/unmutated state that is only updated later in the same logical operation.

### Finding Description
`Decrypt` performs: lock → `window.Check(counter)` → unlock → (unprotected) `DecryptDanger` → lock → `window.Update(counter)` → unlock. `VerifyRelay` has the identical shape. [4](#0-3)  Because the `Check` and `Update` steps are not performed under a single critical section spanning the decrypt, two concurrent invocations for the same counter value (or overlapping window state) can both observe `Check` returning `true` before either one calls `Update`. Nebula intentionally supports multiple concurrent reader routines on the underlay socket via `listen.routines`/`f.routines`, each calling `readOutsidePackets` → `ConnectionState.Decrypt`/`VerifyRelay` independently and concurrently for packets belonging to the same tunnel (same `HostInfo`/`ConnectionState`) if they land on different reader queues. [2](#0-1) [5](#0-4)  This is the same root-cause shape as the analog bug: a security-relevant decision (accept vs. reject) is made using state read before an expensive intervening operation, and the state is only updated afterward, rather than atomically combining "check" and "mark" for the entire operation.

### Impact Explanation
If two frames with the same (or window-adjacent) message counter arrive on different reader queues, both may pass `Check`, both get decrypted and delivered up the stack (the AEAD counter/nonce reuse itself is safe against forgery because the ciphertext must match, but a genuinely captured-and-replayed ciphertext will decrypt successfully a second time), and only the second `Update` call will report `false`. By that point the first copy's plaintext has already been dispatched to `handleOutsideMessagePacket`/tun write, so a replayed packet already achieves its effect once extra before the anti-replay tracker converges — a traffic replay against the intended one-packet-per-counter guarantee, and, depending on the message type, can retrigger side effects (e.g., pushed application data) using duplicate delivery on the overlay network.

### Likelihood Explanation
Requires `listen.routines` (or `tun.routines`) configured greater than 1, which is a supported and documented configuration for improved throughput. An attacker on the wire who can capture and quickly re-inject a single legitimate ciphertext packet (a standard on-path/off-path replay capability against UDP) can attempt to win the race by flooding duplicate copies across the multiple reader queues; because both routines execute independent syscall reads and packet dispatch, the timing window between `Check` and `Update` is realistically hittable under load or intentional flooding.

### Recommendation
Combine the check and mark into a single atomic operation held under `decryptLock` for the whole check-decrypt-mark sequence, or perform an optimistic reservation of the counter (mark tentatively before decrypting, and roll back on decrypt failure) so a duplicate counter can never pass `Check` while the legitimate packet's decrypt is still in flight. Alternatively, serialize decrypt calls per `ConnectionState` so that no two goroutines can process the same tunnel's packets concurrently.

### Proof of Concept
1. Start Nebula with `listen.routines: 4` (or higher) so multiple `listenOut` goroutines read from the underlay socket concurrently. [6](#0-5) 
2. Establish a tunnel and capture one legitimate data-plane packet (header + ciphertext) destined for a given `HostInfo`.
3. Rapidly re-inject multiple copies of the captured packet to the underlay socket such that the OS/kernel or `SO_REUSEPORT` distributes them across different reader queues at nearly the same time.
4. Observe that more than one copy is decrypted and delivered to `handleOutsideMessagePacket` (or forwarded, for relay frames) before `window.Update` converges to reject the duplicates, i.e., the replay window's intended "at most once" guarantee is violated during the race window.

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}

func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}
