### Title
Missing Check Between Authenticated Peer Identity and Attacker-Supplied `RelayFromAddr` in `handleCreateRelayRequest` - (File: relay_manager.go)

### Summary
`relayManager.handleCreateRelayRequest` processes an inbound `NebulaControl_CreateRelayRequest` message by extracting `from`/`target` fields directly from the attacker-controllable, unauthenticated-at-this-layer `NebulaControl` protobuf payload, and uses `from` for all subsequent relay bookkeeping (relay-state lookup, `AddRelay`, and response construction) without ever checking that `from` matches the actual authenticated sender's identity (`h.vpnAddrs`, derived from the peer's certificate at handshake time). This mirrors the Infinity Swap bug class: a trusted authenticated identifier (`h`/the cert-verified `HostInfo`, analogous to the "collection") is available, but the code instead trusts an unrelated, attacker-supplied identifier from the message body (`from`, analogous to the "pool" collection) for the bulk of the state-changing logic.

### Finding Description
`HandleControlMsg` unmarshals the `NebulaControl` message and only checks that `RelayFromAddr`/`RelayToAddr` are non-nil before dispatching to `handleCreateRelayRequest`/`handleCreateRelayResponse` [1](#0-0) . It never verifies that the claimed `RelayFromAddr` corresponds to the sender's own certificate-verified vpn address (`h.vpnAddrs`).

In `handleCreateRelayRequest`, `from := protoAddrToNetAddr(m.RelayFromAddr)` is taken straight from the message and used as the key for all relay state operations — checking `h.relayState.QueryRelayForByIp(from)`, calling `AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)`, and completing/creating relay entries keyed by `from` — while `h` (the actual authenticated peer that sent this Control packet, already decrypted/authenticated via the tunnel's `ConnectionState`) is never checked for equality with `from` [2](#0-1) .

Since a `CreateRelayRequest` for "I am the target" is only ever supposed to be sent directly, hop-by-hop, by the actual relay initiator (i.e. `from` should always equal the sender `h.vpnAddrs[0]`), the missing equality check lets any authenticated peer of the relay node claim an arbitrary `from` address that is not their own. The relay node (`h` in the "target is me" branch) will then create/complete relay state (`AddRelay`/`CompleteRelayByIP`) associating an attacker-chosen victim address with the connection actually held by the attacker's `HostInfo`, and will send the `CreateRelayResponse` back to the attacker's own tunnel (`f.SendMessageToHostInfo(header.Control, 0, h, ...)`), not to the real owner of `from`.

The forwarding branch (target is not me) similarly builds `ForwardingType` relay state keyed by the unauthenticated `from` value on the `peer` HostInfo (`AddRelay(rm.l, peer, f.hostMap, from, nil, ForwardingType, Requested)`), again without validating that `from` matches `h.vpnAddrs[0]` [3](#0-2) .

### Impact Explanation
This is a remote hostmap/relay-state poisoning primitive: an authenticated (but otherwise unprivileged) peer of a relay node can inject relay state entries for an arbitrary victim VPN address it does not own, without holding the victim's certificate. Because the relay/forwarding logic in `handleOutsideRelayPacket` and `SendVia`/`QueryVpnAddrsRelayFor` later trusts these `relayState` entries (keyed by `PeerAddr`) to route/forward traffic [4](#0-3) , corrupting this state can misdirect relayed traffic, create denial-of-service by desynchronizing legitimate relay chains for the victim address (index/state confusion, `RemoteIndex` mismatches logged as errors and dropped), or be used to probe/manipulate which peers a relay believes it should forward for. This falls under "remote state poisoning" impact via the relay/hostmap trust surface, reachable by any authenticated peer without needing a CA-signed cert impersonating the victim.

### Likelihood Explanation
Likelihood is moderate-to-high in relay-enabled deployments (`relay.am_relay` / `relay.use_relays`). Any node that has completed a legitimate handshake with a relay node (an ordinary, non-privileged peer) can send a crafted `header.Control` / `NebulaControl_CreateRelayRequest` message with an arbitrary `RelayFromAddr` value — no additional secrets or privileged access are needed beyond a standard tunnel to the relay, which is the normal operating mode of Nebula relays.

### Recommendation
In `handleCreateRelayRequest` (and `handleCreateRelayResponse`), verify that `from` (`RelayFromAddr`) equals one of `h.vpnAddrs` before performing any relay-state lookup/creation, e.g.:
```go
from := protoAddrToNetAddr(m.RelayFromAddr)
if !slices.Contains(h.vpnAddrs, from) {
    logMsg.Error("CreateRelayRequest RelayFromAddr does not match sender's authenticated vpn address",
        "claimedFrom", from, "actual", h.vpnAddrs)
    return
}
```
This mirrors the recommended fix pattern in the report (checking the trusted/authenticated identifier against the attacker-supplied identifier before using the latter for the bulk of the processing logic).

### Proof of Concept
1. Attacker establishes a normal, legitimately authenticated Nebula tunnel to relay node `R` (attacker has a valid CA-signed cert for its own vpn address `attacker_ip`, and `R` has `relay.am_relay = true`).
2. Attacker sends `R` a `header.Control` packet over its authenticated tunnel containing `NebulaControl{Type: NebulaControl_CreateRelayRequest, RelayFromAddr: victim_ip, RelayToAddr: R_ip, InitiatorRelayIndex: idx}`, where `victim_ip` is any other node's vpn address the attacker does not own.
3. `R.HandleControlMsg` → `handleCreateRelayRequest` sees `target == R`'s own address, so it takes the "target is me" branch; since `from == victim_ip` is never checked against `h.vpnAddrs` (which is `attacker_ip`), `R` executes `AddRelay(rm.l, h, f.hostMap, victim_ip, &idx, TerminalType, Established)` on `h` (the attacker's `HostInfo`), inserting relay state `victim_ip -> h` keyed by `victim_ip`.
4. `R` sends a `CreateRelayResponse` back to the attacker's tunnel confirming an established relay entry for `victim_ip`, even though `victim_ip` never participated in this handshake and the attacker's `HostInfo` now impersonates it in `R`'s relay bookkeeping — corrupting `R`'s relay/hostmap state for the real `victim_ip` and its future relay-related traffic decisions.

	//nil-checks for protoAddrToNetAddr handled by caller
	from := protoAddrToNetAddr(m.RelayFromAddr)
	target := protoAddrToNetAddr(m.RelayToAddr)

	logMsg := rm.l.With(
		"relayFrom", from,
		"relayTo", target,
		"initiatorRelayIndex", m.InitiatorRelayIndex,
		"vpnAddrs", h.vpnAddrs,
	)

	logMsg.Info("handleCreateRelayRequest")
	// Is the source of the relay me? This should never happen, but did happen due to
	// an issue migrating relays over to newly re-handshaked host info objects.
	if f.myVpnAddrsTable.Contains(from) {
		logMsg.Error("Discarding relay request from myself", "myIP", from)
		return
	}

	// Is the target of the relay me?
	if f.myVpnAddrsTable.Contains(target) {
		existingRelay, ok := h.relayState.QueryRelayForByIp(from)
		if ok {
			switch existingRelay.State {
			case Requested:
				ok = h.relayState.CompleteRelayByIP(from, m.InitiatorRelayIndex)
				if !ok {
					logMsg.Error("Relay State not found")
					return
				}
			case Established:
				if existingRelay.RemoteIndex != m.InitiatorRelayIndex {
					// We got a brand new Relay request, because its index is different than what we saw before.
					// This should never happen. The peer should never change an index, once created.
					logMsg.Error("Existing relay mismatch with CreateRelayRequest",
						"existingRemoteIndex", existingRelay.RemoteIndex)
					return
				}
			case Disestablished:
				if existingRelay.RemoteIndex != m.InitiatorRelayIndex {
					// We got a brand new Relay request, because its index is different than what we saw before.
					// This should never happen. The peer should never change an index, once created.
					logMsg.Error("Existing relay mismatch with CreateRelayRequest",
						"existingRemoteIndex", existingRelay.RemoteIndex)
					return
				}
				// Mark the relay as 'Established' because it's safe to use again
				h.relayState.UpdateRelayForByIpState(from, Established)
			case PeerRequested:
				// I should never be in this state, because I am terminal, not forwarding.
				logMsg.Error("Unexpected Relay State found",
					"existingRemoteIndex", existingRelay.RemoteIndex,
					"state", existingRelay.State)
			}
		} else {
			_, err := AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)
			if err != nil {
				logMsg.Error("Failed to add relay", "error", err)
				return
			}
		}

		relay, ok := h.relayState.QueryRelayForByIp(from)
		if !ok {
			logMsg.Error("Relay State not found", "from", from)
			return
		}
