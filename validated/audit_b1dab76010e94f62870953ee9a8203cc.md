### Title
Non-hardened Bancor-style exchange calculation permits negative reserve balances, causing pool insolvency and unbacked token redemption - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java`)

### Summary
`ExchangeCapsule.transaction()` computes the counter-token amount for a TRX/TRC10 Bancor-relay exchange using either a floating-point `ExchangeProcessor` (legacy/default path) or a `BigDecimal`-based `SafeExchangeProcessor` (hardened path), and only validates that resulting reserve balances stay non-negative when the hardened path is used. [1](#0-0) 

### Finding Description
`ExchangeCapsule.transaction()` selects the calculation engine based on the `hardenedCalc` flag, which is derived from `AbstractExchangeActuator.allowHarden()` → `chainBaseManager.getDynamicPropertiesStore().allowHardenExchangeCalculation()`, a chain parameter that is off by default and must be turned on via committee proposal. [2](#0-1) 

The critical solvency check is gated on this same flag:
```
if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
  throw new ContractValidateException("Exchange balance must be >=0 after transaction");
}
``` [3](#0-2) 

When `hardenedCalc` is `false` (the default, unless the committee has enabled the proposal), the legacy `ExchangeProcessor` performs the Bancor relay math entirely in `double`/`Math.pow` arithmetic:
```
double issuedSupply = -supply * (1.0 - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, ...));
...
double exchangeBalance = balance * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, ...) - 1.0);
``` [4](#0-3) 

Floating point rounding in `Math.pow` and division can cause the computed `buyTokenQuant` to exceed the actual counter-token reserve, especially near reserve exhaustion or with adversarially chosen `sellTokenQuant` values that stress precision (very large or very small quants relative to the pool). Because the negative-balance guard is skipped on this path, `newFirstTokenBalance`/`newSecondTokenBalance` can go negative and are written back to storage without error by both `ExchangeTransactionActuator.execute()` and `ExchangeWithdrawActuator.execute()`, which then also credit the counterparty account with `anotherTokenQuant` via `addAssetAmountV2`/`setBalance`. [5](#0-4) 

The result is a token/TRX credit to a user account that is not fully backed by the exchange pool's remaining reserves — the AMM analog of the reported Ubiquity Dollar issue, where redemption logic assumes a favorable invariant (1:1 backing / correct AMM output) without an explicit lower-bound solvency check, and only an opt-in flag (analogous to the report's "human interaction" pause mechanism) provides protection.

### Impact Explanation
A negative reserve balance means the `Exchange`/`ExchangeV2` pool capsule records an impossible state (unbacked balance) while the actuator has already unconditionally transferred the corresponding TRX/TRC10 tokens to the trading account's balance. This constitutes unbacked-balance creation / permanent value extraction from the pool that other exchange participants (via `ExchangeWithdrawActuator`) can no longer fully redeem against, since subsequent Bancor computations and withdrawals in `ExchangeWithdrawActuator.doValidate()` rely on `firstTokenBalance`/`secondTokenBalance` being sane, non-negative values. [6](#0-5) 

### Likelihood Explanation
Exploitability depends on whether floating-point drift in `ExchangeProcessor` can be driven to produce an output exceeding the true reserve under the default (non-hardened) configuration, which is the default network state unless the community has already activated `AllowHardenExchangeCalculation` via proposal. The existence of a dedicated `SafeExchangeProcessor`/hardened mode and its accompanying negative-balance guard strongly suggests the java-tron team already identified precision issues in the legacy `double`-based processor as a real risk requiring remediation, but the fix is opt-in rather than mandatory. [7](#0-6) 

I was not able to fully confirm from the index whether `allowHardenExchangeCalculation` currently defaults to enabled or disabled on mainnet (the corresponding getter/setter and default constant in `DynamicPropertiesStore.java` were not returned by search), so the current live-network exposure of the legacy math path is uncertain and should be verified directly in that file.

### Recommendation
Perform the reserve non-negativity check unconditionally in `ExchangeCapsule.transaction()`, regardless of `hardenedCalc`, so that any exchange calculation producing a negative resulting balance is rejected before it is persisted or funds are transferred; alternatively, retire the legacy floating-point `ExchangeProcessor` entirely in favor of the `BigDecimal`-based `SafeExchangeProcessor` for all exchange actuators.

### Proof of Concept
Not independently reproducible from the indexed code alone — a concrete PoC would require driving the network with `AllowHardenExchangeCalculation` disabled (default) and crafting `ExchangeTransactionContract`/`ExchangeWithdrawContract` `quant` values against a pool whose reserves are small enough that `ExchangeProcessor`'s `double`/`Math.pow` rounding yields a `buyTokenQuant` exceeding the counter-token reserve, then observing that `ExchangeCapsule.transaction()` (lines 124-167) writes a negative `firstTokenBalance`/`secondTokenBalance` without throwing, as shown by the unguarded branch at lines 160-162 compared to the equivalent hardened-mode test assertions in `ExchangeCapsuleTest.testHardenedTransactionNegativeBalanceThrows`. [8](#0-7)

      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
