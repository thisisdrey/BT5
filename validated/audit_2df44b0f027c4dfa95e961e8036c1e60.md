## Title
Cross-StackerDB Chunk Replay via Signature Not Binding to Contract Identity - (File: `libstackerdb/src/libstackerdb.rs`, `stackslib/src/net/stackerdb/db.rs`)

### Summary
A `StackerDBChunkData`/`SlotMetadata` signature only commits to `(slot_id, slot_version, data_hash)`. It never binds the signature to the specific StackerDB smart contract (`stackerdb_id` / `QualifiedContractIdentifier`) the chunk is destined for. Any unprivileged relayer who observes a validly signed chunk for one StackerDB replica can resubmit the exact same bytes to any *other* StackerDB replica where the same signer address happens to own the same `slot_id`, and it will be accepted and stored as if it were freshly authored for that other contract/context.

### Finding Description
`SlotMetadata::auth_digest()` computes the signed digest strictly from `slot_id`, `slot_version`, and `data_hash`: [1](#0-0) 

`SlotMetadata::sign()`/`verify()` operate purely on this digest and a target `StacksAddress`, with no notion of *which* StackerDB (contract) the chunk belongs to: [2](#0-1) 

The storage/validation layer in `StackerDBTx::try_replace_chunk` fetches the *expected signer* for `(smart_contract, slot_id)` and calls `slot_desc.verify(&slot_validation.signer)`, but never checks that the signature was produced specifically *for* `smart_contract`: [3](#0-2) 

Notably, the SQL schema comment for the `chunks` table explicitly documents that only `slot_id, version, data_hash, signature` are covered by the signature — the `stackerdb_id` (i.e., which contract this chunk belongs to) is not part of what's cryptographically authenticated: [4](#0-3) 

The same gap exists in the P2P gossip validation path, `PeerNetwork::validate_received_chunk`, which resolves the expected signer via `get_slot_signer(smart_contract_id, data.slot_id)` and then verifies the chunk against that address — again with no binding of the signature to `smart_contract_id`: [5](#0-4) 

**Equality broken:** "signed for contract/slot context A" is treated as equal to "authorized to be stored in contract/slot context B" whenever the same signer address is assigned the same `slot_id` in both StackerDB instances (which is common in practice — signer sets are largely stable and often keep the same slot index across consecutive `.signers-*-*` reward-cycle contracts, or across different message-type StackerDB contracts configured for the same signer set). An unprivileged relayer who has observed one valid, signed chunk can replay the identical bytes (same `slot_id`, `slot_version`, `sig`, `data`) into a different StackerDB replica context, and `try_replace_chunk`/`validate_received_chunk` will accept and store it as genuine, since the only checks are: chunk-size cap, "is this slot assigned to this recovered address in *this* contract," monotonic version, and max-writes — none of which detect the cross-contract substitution.

### Impact Explanation
This allows an unauthenticated/unauthorized write of stale or foreign data into a StackerDB replica that the node believes is freshly authored and properly authorized for that specific contract context. This is a form of forged/foreign-context data being accepted as authentic and propagated across the network (StackerDB chunks are gossiped further via `StackerDBChunkInv`/push-chunk flows once stored), satisfying the "unauthenticated/unauthorized write to state or StackerDB" / "network-wide propagation of forged data" Critical/High criteria. It does not require the attacker's own signing key — only observation and resubmission of a message actually produced by a legitimate signer, applied to a StackerDB instance/slot it was never intended for.

### Likelihood Explanation
Exploitability requires only network observation (any relayer/mempool-watcher-equivalent for StackerDB gossip) and the ability to POST/push a chunk via the existing `/v2/stackerdb/.../chunks` endpoint or the P2P push-chunk message — both unauthenticated, unprivileged actions already reachable by any peer. The precondition (same signer address assigned the same `slot_id` across two StackerDB contexts) is realistic given how `.signers-*` and other StackerDB contracts are provisioned per reward cycle/message type with largely overlapping signer sets and index assignments, and the version/max-writes checks do not defend against this since a "new" target context starts its version counter independently.

### Recommendation
Extend the signed digest in `SlotMetadata::auth_digest()` to include the target StackerDB's contract identifier (or `stackerdb_id`), e.g. `hash(smart_contract_id, slot_id, slot_version, data_hash)`, and update `sign()`/`verify()` call sites (`try_replace_chunk`, `validate_received_chunk`, and the P2P `handle_unsolicited_StackerDBPushChunk` path) to pass and check the contract identifier as part of verification. This mirrors the recommended fix pattern of extending the signed type/digest to cover all fields the recipient relies on for authorization, rather than only a subset.

### Proof of Concept
1. Node A hosts StackerDB contract `SP...signers-5-1` where signer `X` (address derived from `pk`) owns `slot_id=0`.
2. Signer `X` signs and posts chunk `C = (slot_id=0, slot_version=1, sig, data)` to contract `signers-5-1`; it's accepted per `try_replace_chunk`.
3. An unprivileged relayer observes `C` on the wire (via `StackerDBPushChunk` gossip or the public chunk-fetch endpoint).
4. Node B (or Node A itself, in a later reward cycle) also configures StackerDB contract `SP...signers-6-1`, in which the same address `X` is independently also assigned `slot_id=0` (a common outcome since signer sets/indices are frequently stable across cycles).
5. The relayer POSTs the *identical* bytes of `C` to `.../v2/stackerdb/SP.../signers-6-1/chunks`.
6. `try_replace_chunk` looks up the expected signer for `(signers-6-1, slot_id=0)` — finds `X` — and calls `slot_desc.verify(&X)`, which succeeds because `auth_digest()` never included any contract-binding data. The stale/foreign chunk from `signers-5-1` is accepted and stored under `signers-6-1`, and is then eligible for further gossip via inventory exchange, all without contract `signers-6-1`'s signer `X` ever having authored or intended this write for that context.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
