Both `verify_payload_bytes` and `read_payload` for `StacksP2P` truncate the buffer identically via `bytes.get(..preamble.payload_len as usize)` [1](#0-0) , so the exact same byte slice is both signed-checked and deserialized — there is no divergence between "bytes signed" and "bytes executed." The excess bytes beyond `payload_len` in `buf_bytes` (passed from `consume_payload_known_length`) are never included in the signature check or in the parsed message; `read_payload` returns `cursor.position()` as `message_len`, which is used to compute `next_message_ptr = self.message_ptr + message_len`, and the code then slices the buffer starting at `next_message_ptr` to begin parsing the *next* message from scratch (with its own preamble and signature check) [2](#0-1) . This is deliberate support for buffering multiple pipelined messages in a single TCP read, not a bug — each subsequent message still requires its own valid preamble and signature over its own truncated payload. There is no code path where `buf_bytes.len() > payload_len` causes the extra bytes to be silently treated as verified/part of the current message or dropped without being reprocessed as the start of a new message.

        bytes: &[u8],

        let mut cursor = io::Cursor::new(preamble_bytes);
        let (relayers, payload) = StacksMessage::deserialize_body(&mut cursor)?;
        let message = StacksMessage {
            preamble: preamble.clone(),
            relayers,
            payload,
        };
        Ok((message, cursor.position() as usize))
    }
