### Title
Single global `overall_connection_rate_limiter` token bucket allows a many-IP unstaked attacker to deny all new QUIC connections cluster-wide - (File: streamer/src/nonblocking/quic.rs)

### Summary
`run_server` creates one process-wide `TokenBucket` (`overall_connection_rate_limiter`, capacity `MAX_CONNECTION_BURST` = 1000, refill `TOTAL_CONNECTIONS_PER_SECOND` = 2500/s) that is checked/consumed for *every* incoming connection before per-IP limiting or stake is even known. An attacker spreading connection attempts across many source IPs, each individually staying under the per-IP `ConnectionRateLimiter` cap, can collectively exceed 2500 conn/s and fully drain this shared bucket, causing the server to `ignore()`/`close()` all subsequent connection attempts from any source — including well-behaved unstaked peers and even staked nodes trying to open new connections — until the attack rate drops below the refill rate.

### Finding Description
In `run_server` (streamer/src/nonblocking/quic.rs:277-357), a single `Arc<TokenBucket>` is instantiated once per endpoint and shared across all incoming connections regardless of source IP or stake: [1](#0-0) 

For every accepted `Incoming`, the loop first checks `overall_connection_rate_limiter.current_tokens() == 0` and drops (`incoming.ignore()`) if empty: [2](#0-1) 

Only after that does it consult the per-IP `ConnectionRateLimiter::is_allowed` (streamer/src/nonblocking/connection_rate_limiter.rs:34-40), and later, in `setup_connection`, `overall_connection_rate_limiter.consume_tokens(1)` is called again after the handshake completes: [3](#0-2) 

Both checkpoints operate on the exact same global bucket, with no per-IP or per-stake partitioning. `TokenBucket::consume_tokens`/`current_tokens` (net-utils/src/token_bucket.rs:66-94) implement a simple shared-capacity leaky bucket with no notion of "who" is drawing from it. Crucially, this global gate runs *before* stake is determined (stake is only established later via `get_connection_stake`/QoS after `new_connection` handshake), so it starves connection attempts from staked nodes as well as unstaked ones — it is not scoped to "unstaked" traffic at all.

Because the per-IP `ConnectionRateLimiter` (`max_connections_per_ipaddr_per_min`) only bounds a *single* IP's rate, an attacker controlling many distinct source IPs (botnet/IP rotation) can keep every individual IP's rate under its per-IP quota while summing to more than `TOTAL_CONNECTIONS_PER_SECOND` (2500/s) in aggregate. Since the global bucket capacity is only `MAX_CONNECTION_BURST` (1000 tokens) refilling at 2500/s, sustaining an aggregate attack rate above 2500/s (trivial with a modestly sized botnet — e.g. 50 IPs each opening 60 conn/s, well under typical per-IP caps) keeps `current_tokens() == 0` continuously, so every incoming connection — attacker or legitimate — is rejected at the very first check in `run_server`, regardless of the per-IP limiter passing.

No existing check breaks this: per-IP limiting is IP-scoped and cannot detect a multi-IP campaign; stake-based prioritization does not apply here because the global bucket is consumed before stake is known; `max_concurrent_connections`/QoS logic is never reached since the rejection happens earlier in the accept loop.

### Impact Explanation
This is a cluster-wide TPU ingress denial-of-service reachable by a fully unprivileged/unstaked remote attacker who only needs the ability to originate QUIC connection attempts from many source IPs at a modest per-IP rate. The impact is not limited to "other unstaked clients" — because the check precedes stake determination, it can also block new connections from staked validators/forwarders trying to reach the leader's TPU, degrading transaction ingestion for the whole cluster during the attack window. This matches the "DoS bringing down or stalling a validator/leader's core transaction-processing ingress" bounty category, scoped strictly to the connection-acceptance path in `streamer`.

### Likelihood Explanation
Feasibility is high and reproducible without any privileged capability: the attacker only needs many distinct source IPs (cheap via cloud instances, proxies, or a botnet) and standard QUIC client libraries to open connections at rates individually under the default per-IP cap but collectively above 2500/s. No stake, no gossip participation, no validator control, and no protocol-level trickery are required — this is a pure resource-exhaustion property of the shared bucket's design, sustainable for as long as the attacker maintains the aggregate rate.

### Recommendation
Partition the overall connection-rate budget so a single logical actor spread over many IPs cannot exhaust the whole endpoint's admission capacity: e.g., reserve a fraction of `MAX_CONNECTION_BURST`/`TOTAL_CONNECTIONS_PER_SECOND` specifically for known-staked peers (checked after handshake, before final accept) via a second, stake-aware token bucket, and/or apply an additional coarser-grained per-/24-subnet or ASN rate limiter in front of the global bucket so distributed low-and-slow floods from disjoint IPs cannot compound into a single indistinguishable global rate. At minimum, do not gate on the shared global bucket before stake is known if the goal is to protect staked traffic from unstaked floods.

### Proof of Concept
Integration test (extending the existing `tpu-client-next/tests/connection_workers_scheduler_test.rs` harness / `streamer` test utilities):

```rust
#[tokio::test]
async fn test_overall_rate_limiter_starved_by_many_ips() {
    // Spin up a QUIC server with default TOTAL_CONNECTIONS_PER_SECOND (2500) /
    // MAX_CONNECTION_BURST (1000), and a per-IP cap comfortably above the
    // per-IP rate each simulated attacker IP will use.
    let SpawnTestServerResult { server_address, stats, cancel, .. } = setup_quic_server(
        None,
        QuicStreamerConfig {
            max_connections_per_ipaddr_per_min: 10_000, // generous per-IP cap
            ..QuicStreamerConfig::default_for_tests()
        },
        SwQosConfig::default(),
    );

    // Simulate N distinct source IPs (bind N client sockets on different local
    // addrs/ports, or use a test harness that spoofs remote_address per task),
    // each issuing connection attempts at a rate under max_connections_per_ipaddr_per_min
    // but summing above TOTAL_CONNECTIONS_PER_SECOND (2500/s), for >1s to drain
    // the MAX_CONNECTION_BURST=1000 token reserve and keep current_tokens()==0.
    let attacker_ip_count = 50;
    let per_ip_rate = 60; // well under the 10_000/min per-IP cap
    flood_from_many_ips(&server_address, attacker_ip_count, per_ip_rate, Duration::from_secs(2)).await;

    // Now attempt one additional legitimate connection from a fresh, previously
    // unseen IP that has never been rate-limited per-IP.
    let legit_conn = make_client_endpoint(&server_address, None).await;
    let legit_result = timeout(Duration::from_secs(1), legit_conn.connect(...)).await;

    // Expect rejection due to the shared global bucket, not per-IP limiting.
    assert!(legit_result.is_err() || legit_result.unwrap().is_err());
    assert!(stats.connection_rate_limited_across_all.load(Ordering::Relaxed) > 0);
    assert_eq!(stats.connection_rate_limited_per_ipaddr.load(Ordering::Relaxed), 0);

    cancel.cancel();
}
```

Expected assertion: `stats.connection_rate_limited_across_all` increments while `stats.connection_rate_limited_per_ipaddr` stays at 0 for the legitimate client, proving that a distributed multi-IP attacker — each individually compliant with per-IP limits — can exhaust the single global `overall_connection_rate_limiter` and deny service to unrelated legitimate connections.
