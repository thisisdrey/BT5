Based on the investigation, I found a genuine structural analog to the OpenJPEG `pi_next_*` bug class (unbounded loop index derived from attacker-controlled length field, used to index into a fixed-size buffer without validating the length against the buffer's real size) inside java-tron's TVM precompiled-contract dispatch code.

### Title
Unvalidated attacker-controlled length used to index `DataWord[]` in `ValidateMultiSign`/precompile array extraction helpers can throw an uncaught exception outside any try/catch - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`PrecompiledContracts.extractBytesArray`, `extractSigArray`, and `extractBytes32Array` read an array length directly from attacker-supplied calldata (`words[offset].intValueSafe()`) and then loop over that length, indexing into the `words` array without checking that `offset + i + 1` stays within `words.length`. This mirrors the OpenJPEG `pi_next_*` pattern, where a loop bound taken from untrusted input is used to index an array whose real length is never re-validated against that bound.

### Finding Description
`extractBytesArray`/`extractSigArray` only guard against `offset > words.length - 1` before reading `len`, but `len` itself (`words[offset].intValueSafe()`) is fully attacker-controlled and unchecked afterward: [1](#0-0) 
`extractBytes32Array` has no bound check at all, not even on `offset`: [2](#0-1) 

In `ValidateMultiSign.execute`, these helpers are invoked directly, and — critically — the call is placed *outside* the method's inner `try` block that surrounds the signature-recovery/permission logic: [3](#0-2) 
The `MAX_SIZE` bound check that limits `sigArraySize` is only applied `if (VMConfig.allowTvmSelfdestructRestriction())`, and the ABI-shape guard (`isValidAbiEncoding`) is only applied `if (VMConfig.allowTvmOsaka())`. When either hard-fork flag is not yet active on a given chain/network, both guards are skipped and `extractBytesArray`/`extractSigArray` run unguarded on attacker data, which can throw `NegativeArraySizeException`, `ArrayIndexOutOfBoundsException`, or trigger huge allocations (`new byte[len][]`) leading to `OutOfMemoryError`. Because this call sits outside the local `try`/`catch(Throwable)` in `ValidateMultiSign`, the exception propagates straight out of `execute()`.

By contrast, `BatchValidateSign` wraps its entire body in `try { return doExecute(data); } catch (Throwable t) { ... }`, so the equivalent unbounded-index bug there is caught and neutralized: [4](#0-3) 

The test suite explicitly documents this asymmetry as intentional/known, pre-existing legacy behavior that TIP-854 (`allowTvmOsaka`) was designed to fix going forward, while pre-activation behavior is preserved: [5](#0-4) 
and a companion test verifies that only *after* TIP-854 activation is the outer frame protected from a propagated exception: [6](#0-5) 

### Impact Explanation
This is reachable by any unprivileged account: a smart contract can `CALL` the `ValidateMultiSign` precompiled address with a crafted `data` payload where the length word for the signature/address array is malformed (e.g., negative, or larger than the real `words` array), while `allowTvmOsaka`/`allowTvmSelfdestructRestriction` are not yet activated on the target network. This can throw an uncaught runtime exception (or an `OutOfMemoryError`) from inside `Program.callToPrecompiledAddress` during ordinary transaction execution/block application, which — unlike `BatchValidateSign` — is not locally contained. Depending on how far up the call stack the exception propagates (this could not be fully verified without further tracing into `Program`/`Runtime`/`Manager` block-application error handling), this is at minimum an unhandled-exception DoS vector for transaction processing and at worst could destabilize node/block processing consensus paths, matching the "application crash" impact class of the CVE analog.

### Likelihood Explanation
Likelihood is conditional on the hard-fork activation state of `allowTvmOsaka`/`allowTvmSelfdestructRestriction` for the target chain: on networks where these have already been activated (which appears to be the intent of TIP-854), the `isValidAbiEncoding` and `MAX_SIZE` guards make this unreachable. On any chain or test/private network where these proposals are not yet activated, any address can trigger it with a single crafted transaction deploying/invoking a contract that calls the `ValidateMultiSign` precompile — no special privilege required.

### Recommendation
Add unconditional (not feature-flag-gated) bounds validation inside `extractBytesArray`, `extractSigArray`, and `extractBytes32Array` that verifies `len` and every derived offset/index against `words.length` and against `MAX_SIZE`, regardless of `allowTvmOsaka`/`allowTvmSelfdestructRestriction` state. Additionally, wrap the array-extraction calls in `ValidateMultiSign.execute` inside the existing `try`/`catch(Throwable)` block (as already done in `BatchValidateSign`) so that any residual malformed-input exception is converted into a normal `DATA_FALSE` precompile result instead of propagating out of `execute()`.

### Proof of Concept
1. Deploy/trigger a contract on a java-tron network where `allowTvmOsaka` and `allowTvmSelfdestructRestriction` are not activated.
2. Have the contract `CALL` the `ValidateMultiSign` precompiled contract address with calldata where `words[3]` (the offset word) points to a length word whose value, once read as `sigArraySize = words[offset].intValueSafe()`, is either negative or large enough that `offset + i + 1` exceeds `words.length` during the loop in `extractBytesArray`/`extractSigArray`.
3. Observe that `PrecompiledContracts.ValidateMultiSign.execute` throws (e.g., `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException`) from a call site outside its `try` block, propagating the exception out of the precompile invocation instead of returning `DATA_FALSE`, unlike the contained behavior verified in `BatchValidateSign` per the `testTip854OuterFrameContainment` test [7](#0-6) .

**Note on uncertainty:** I was unable to trace the full downstream propagation of this exception (i.e., whether `Program.callToPrecompiledAddress` or the block-application code in `Manager` ultimately catches it and merely fails the transaction, versus letting it crash the node/consensus loop) within the available search iterations. This should be verified directly against `Program.callToPrecompiledAddress` and the calling `VM`/`Runtime` exception-handling code before treating this as a confirmed node-crash vulnerability rather than a contained transaction-failure bug.
