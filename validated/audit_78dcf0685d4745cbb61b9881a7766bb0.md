### Title
Dust deposits on behalf of a victim fill `depositTokensOfAccount` to `MAX_TOKENS_PER_USER`, DoS-ing collateral top-ups, liquidations, withdrawals and leverage - (File: contracts/Pool.sol)

### Summary
The bug class in CVE-2025-25475 is a crafted input causing a NULL-pointer dereference that crashes the process (DoS). The Metronome analog is a crafted state that makes a required lookup/insert fail: every deposit-token balance change inserts the recipient into the per-account `MappedEnumerableSet` `depositTokensOfAccount`, and `Pool.addToDepositTokensOfAccount` reverts with `UserReachedMaxTokens` once the combined `debtTokens + depositTokens` count reaches `MAX_TOKENS_PER_USER = 30` [1](#0-0) . Because `DepositToken.deposit` accepts an arbitrary `onBehalfOf_` beneficiary and `_transfer`/`_mint` unconditionally register first-time recipients [2](#0-1) [3](#0-2) , an unprivileged attacker can permanently mark an arbitrary account's token list as "full" using dust amounts — the storage equivalent of dereferencing a missing/invalid pointer: every subsequent insert-dependent operation reverts.

### Finding Description
`DepositToken.deposit(uint256 amount_, address onBehalfOf_)` lets anyone mint msdTokens to any address [4](#0-3) . `_mint` adds `account_` to `depositTokensOfAccount` when `balanceOf` transitions from zero [5](#0-4) , and `_transfer` does the same for the recipient [6](#0-5) . `addToDepositTokensOfAccount` enforces the combined cap via `onlyIfAdditionWillNotReachMaxTokens` [7](#0-6) .

Attack: the attacker calls `depositToken_i.deposit(dust, victim)` for `30 - N` different deposit tokens, where `N` is the victim's current `debtTokens + depositTokens` count. There is no minimum-amount check beyond `AmountIsZero` [8](#0-7) , so the cost is dust of each underlying plus gas.

Once the victim's list hits 30:

- `deposit`/`depositToken.transfer`/`transferFrom`/`SmartFarmingManager.leverage` into any *new* collateral type revert at `pool.addToDepositTokensOfAccount` → the victim cannot add collateral to defend an unhealthy position.
- `Pool.liquidate` → `depositToken_.seize(account_, liquidator, _toLiquidator)` and the fee seize to `feeCollector` [9](#0-8)  route through `_transfer` → `addToDepositTokensOfAccount`; a liquidator (or the `feeCollector`) whose list is full for that token causes every `liquidate` on that collateral to revert.
- `DepositToken._withdraw` transfers `_fee` to `feeCollector` when `withdrawFee > 0` [10](#0-9) ; if `feeCollector`'s combined list is full for a newly added collateral, all withdrawals of that collateral revert until the feeCollector's own balances change — temporarily freezing funds for the whole collateral, not just the victim.

The victim can only free a slot by zeroing a balance, which requires transferring/withdrawing — but `_revertIfLocked` blocks that while debt is outstanding [11](#0-10) , so a victim with open debt cannot self-recover without repaying first.

### Impact Explanation
- Forced liquidation / loss of funds: a victim holding open debt is prevented from depositing any new collateral type to restore health; the attacker (or anyone) then liquidates them via `Pool.liquidate`, seizing collateral plus incentive. This is direct loss enabled by an unprivileged action.
- Temporary freezing of funds: liquidation `seize` to a maxed-out `feeCollector` and withdraw-fee `_transfer` revert, blocking liquidations and withdrawals protocol-wide for affected collaterals.
- Invariant broken: liveness of deposit/liquidate/withdraw paths, triggered by crafted input analogous to the CVE's crafted-file NULL-deref crash.

### Likelihood Explanation
High feasibility, conditional impact. Requirements: attacker holds dust of each pool collateral (cheap on L2s; pools have ≤30 deposit tokens), and the victim's combined list must be pushable to 30 — most accounts use only a handful of tokens, so ~25–29 dust deposits suffice. `onBehalfOf_` is unrestricted and there is no opt-out. No privileged role, oracle manipulation, or flash loan is needed. The main limitation is that the attack targets the *recipient's* ability to receive a new token type, so liquidations involving collaterals the `feeCollector` already holds still proceed; the strongest, most reliable impact is victim-specific (blocked collateral top-ups → forced liquidation) rather than protocol-wide.

### Recommendation
- Make `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` failures non-fatal for unsolicited receipts: skip adding to the account list instead of reverting (the list is only used for `debtPositionOf` accounting and to gate `unlockedBalanceOf`; a dust balance not tracked still counts in `balanceOf`, so the accounting effect must be evaluated — alternatively track deposit list entries only on explicit `deposit` where `onBehalfOf_ == _msgSender()`).
- Revert dust-registration by requiring `onBehalfOf_` positions to opt in, or require a minimum first-deposit amount per token.
- Alternatively, count only tokens above a dust threshold toward `MAX_TOKENS_PER_USER`, or remove the account-list cap dependency for `seize`/fee paths (`to_ == feeCollector` should never revert on list insertion).

```ts
// test/poc/UserReachedMaxTokens.grief.test.ts
import {expect} from 'chai'
import {ethers} from 'hardhat'

it('attacker fills victim deposit-token list -> victim cannot add collateral', async () => {
  // deploy pool, masterOracle, treasury, feeProvider as in existing Pool.test.ts fixtures
  const [attacker, victim] = await ethers.getSigners()

  // victim borrows once -> has e.g. 1 debt token + 1 deposit token
  await depositTokenA.connect(victim).deposit(amount, victim.address)
  await debtToken.connect(victim).issue(...) // via pool/DebtToken flow

  // attacker dusts victim with every other deposit token
  for (const dt of allDepositTokens.slice(1)) {
    await underlying.connect(attacker).approve(dt.address, DUST)
    await dt.connect(attacker).deposit(DUST, victim.address) // onBehalfOf_ = victim
  }
  expect((await pool.getDepositTokensOfAccount(victim.address)).length
         + (await pool.getDebtTokensOfAccount(victim.address)).length).to.eq(30)

  // victim cannot deposit a collateral type not yet in their list
  await underlyingNew.connect(victim).approve(newDepositToken.address, amount)
  await expect(newDepositToken.connect(victim).deposit(amount, victim.address))
    .revertedWithCustomError(pool, 'UserReachedMaxTokens')

  // liquidate reverts when _toLiquidator recipient list is full for that token
  // (same seize -> _transfer -> addToDepositTokensOfAccount path)
  await expect(pool.connect(liquidator).liquidate(msToken.address, victim.address, repay, depositTokenX.address))
    .revertedWithCustomError(pool, 'UserReachedMaxTokens')
})
```

The revert is deterministic because `_mint`/`_transfer` unconditionally call `pool.addToDepositTokensOfAccount` on a zero-balance recipient [12](#0-11) [1](#0-0) . Caveat I could not fully verify within scope: whether the deployed `feeCollector` already holds all 30 deposit tokens via fee accrual (which would limit the protocol-wide `seize` DoS to the window when a collateral is first added or when `feeCollector`'s combined debt+deposit count can be pushed to 30); the victim-griefing path is unconditional.
