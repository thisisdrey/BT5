### Title
Unbounded array-length field in `ValidateMultiSign`/`BatchValidateSign` precompiles allows attacker-controlled massive memory allocation - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` (address `0x...0a`) and `BatchValidateSign` (address `0x...09`) TVM precompiled contracts parse an attacker-controlled 32-byte "array length" word from calldata and immediately allocate a Java array sized by that value, via `extractBytesArray`, before any check that the value is consistent with the actual size of the supplied calldata. This mirrors the pypdf `/ToUnicode` bug class: an untrusted length field taken from parsed input is used to size a memory allocation without first bounding it against the real payload size, letting a single crafted call trigger disproportionate memory consumption.

### Finding Description
`extractBytesArray` reads a length word directly from calldata and allocates an array of that size before validating it against the actual data present: [1](#0-0) 

`len` comes from `words[offset].intValueSafe()`, i.e. is fully attacker-controlled via the `bytes[]`/`address[]` head-offset word in the ABI-encoded call data. The resulting `byte[len][]` allocation is performed unconditionally, with no upper bound, before the loop even tries to read the (potentially nonexistent) per-item data.

This function is invoked from `ValidateMultiSign.execute` and `BatchValidateSign.execute`: [2](#0-1) [3](#0-2) 

Both call sites only bound the size (`sigArraySize > MAX_SIZE`, `MAX_SIZE` = 5 or 16) when `VMConfig.allowTvmSelfdestructRestriction()` is enabled, and in that case route to the safer `extractSigArray` path instead. When that feature flag is not active for a given call context, `extractBytesArray` is invoked directly with the raw, unbounded `len`, allowing a single call to attempt allocating an array with up to `Integer.MAX_VALUE` (~2^31-1) reference slots — several gigabytes of heap — from one crafted TVM call.

This is reachable by any account through a smart contract that issues a `CALL`/`STATICCALL` to the `batchvalidatesign` (`0x...09`) or `validatemultisign` (`0x...0a`) precompile addresses with malformed calldata, i.e. by an unprivileged contract deployer/caller — matching the required threat model (single signed transaction / contract call).

### Impact Explanation
A successful trigger causes the executing node to attempt a very large heap allocation inside VM/actuator processing. Depending on JVM heap headroom this can throw an `OutOfMemoryError` (caught generically as `Throwable` in `BatchValidateSign.execute`'s wrapper, degrading gracefully) or induce severe GC pressure/latency spikes across the node while executing/validating the block, effectively a resource-exhaustion/DoS vector reachable from ordinary contract calls, satisfying the "node can no longer serve" / degraded availability bar.

### Likelihood Explanation
Likelihood is bounded by execution cost: the energy formula for these precompiles (`getEnergyForData`) charges roughly per encoded 32-byte word of the *supplied calldata*, not per the huge `len` value extracted from a single length word, so an attacker can encode a very large `len` in a small amount of calldata (cheap in energy) while the resulting allocation attempt is enormous — this cost asymmetry is exactly the amplification pattern needed for a memory-exhaustion analog of the pypdf issue.

### Recommendation
Enforce the existing `MAX_SIZE` bound check unconditionally (not gated behind `VMConfig.allowTvmSelfdestructRestriction()`) before calling `extractBytesArray`/`extractSigArray`/`extractBytes32Array`, and additionally validate that the declared `len` is consistent with the remaining `words.length`/`data.length` (as already done via `isValidAbiEncoding` for the Osaka-gated path) prior to any array allocation, for both `ValidateMultiSign` and `BatchValidateSign`, independent of feature-activation flags.

### Proof of Concept
Construct calldata for `validatemultisign(address,uint256,bytes32,bytes[])` (or `batchvalidatesign(bytes32,bytes[],address[])`) where the `bytes[]` head offset word points to a length word set to a very large value (e.g. `0x7fffffff`), while the remainder of the calldata is only a few words long (so total ABI-encoding energy stays low). Call this precompile via a deployed contract's `CALL` opcode with `allowTvmSelfdestructRestriction` not yet active on the relevant execution path; `extractBytesArray` will attempt `new byte[0x7fffffff][]`, consuming/failing to allocate on the order of 16+ GB, before any subsequent bound check on `signatures.length > MAX_SIZE` can reject it.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
