### Title
Vault deposit/redeem accounting trusts nominal `amount` instead of actual tokens received, causing insolvency with fee-on-transfer underlying tokens - ([File: mainnet/contracts/vault/v0-vault-usdc.clar])

### Summary
The report describes `FixedFeeSwap` minting output tokens based on the nominal transferred amount rather than the amount actually received, which is wrong when the underlying ERC20/SIP-010 token charges a transfer fee. The same root-cause pattern exists in every Zest v0 vault contract's `deposit`/`redeem` flow.

### Finding Description
In `deposit`, shares are computed from the caller-supplied `amount` via `convert-to-shares-preview` before the underlying transfer happens, and the internal `assets` variable is incremented by the same nominal `amount`, not by what the vault contract actually receives: [1](#0-0) 

`receive-underlying` and `send-underlying` simply call `transfer` on the underlying SIP-010 token and assume the full `amount` moved, with no post-transfer balance check: [2](#0-1) 

A `ubalance` helper exists that reads the vault's actual token balance from the underlying contract, but it is not used to reconcile `assets` after transfers — `total-assets`/`total-assets-preview` (used for share pricing in `convert-to-shares-preview`/`convert-to-assets-preview`) derive purely from the tracked `assets` var plus accrued interest, never from the real on-chain balance: [3](#0-2) 

If the configured `UNDERLYING` SIP-010 token (`'SP120SBRBQJ00MCWS7TM5R8WJNTTKD5K0HFRC2CNE.usdcx`, or the equivalents wired into `v0-vault-sbtc`, `v0-vault-stx`, `v0-vault-ststx`, `v0-vault-usdh`, `v0-vault-ststxbtc`) implements or is later upgraded/re-pointed by its issuer to implement a transfer fee (a documented real-world possibility the original report calls out for USDT-style tokens), every `deposit` mints zTokens priced on the pre-fee `amount` while the vault's actual token balance grows by the post-fee amount. The tracked `assets` bookkeeping variable then permanently overstates real backing. This same defect is identically present across all six vault modules given the identical `deposit`/`receive-underlying`/`total-assets-preview` pattern.

### Impact Explanation
Because zToken share price (`convert-to-shares-preview`/`convert-to-assets-preview`) is derived from the inflated `assets` bookkeeping value rather than real backing, later redeemers can be paid out more underlying than the vault actually holds, up to the point where `get-available-assets`/liquidity checks fail for remaining holders — a protocol insolvency / permanent freezing of funds situation for the last redeemers, since the shortfall is proportional to the fee percentage compounding across every deposit. This is Critical impact: protocol insolvency and permanent loss of funds for some depositors, not merely disabled functionality.

### Likelihood Explanation
This requires the underlying SIP-010 token used by a given vault to actually implement a non-zero transfer fee. None of the currently wired-in underlying tokens are confirmed to have fee-on-transfer logic today, but — exactly as the source report about USDT states — a token issuer can add or activate such a fee at any time without changing its interface, and Zest's DAO governance only controls the vault/asset registry, not the fee behavior of already-approved third-party token contracts. Given that the vault code makes zero attempt to verify tokens received vs. tokens claimed for every single deposit/withdraw across all six vaults, the likelihood of impact is entirely dependent on external token behavior change, which is outside Zest's control but squarely inside the "not verifying actual balance change" bug class the report targets.

### Recommendation
In `receive-underlying`/`send-underlying`, measure the vault's actual token balance before and after the transfer call (via the existing `ubalance` helper) and use the delta — not the nominal `amount` — to update the `assets` var and to compute minted/burned shares. Apply the same fix uniformly across `v0-vault-usdc.clar`, `v0-vault-sbtc.clar`, `v0-vault-stx.clar`, `v0-vault-ststx.clar`, `v0-vault-usdh.clar`, and `v0-vault-ststxbtc.clar`.

### Proof of Concept
1. Assume `UNDERLYING` token's issuer activates a 1% transfer fee (permitted by that token's own contract, not Zest's).
2. User calls `deposit` with `amount = u1000000` (1 USDC-equivalent). `convert-to-shares-preview` computes shares based on `u1000000`; `ft-mint?` mints that many zTokens to the recipient.
3. `receive-underlying` calls `transfer u1000000 ...`; due to the fee, the vault contract's real token balance only increases by `u990000`.
4. `var-set assets (+ current-assets u1000000)` — the tracked backing is now `u10000` higher than what the vault actually holds.
5. Repeat across many deposits; the gap between tracked `assets` and real `ubalance` grows monotonically.
6. Eventually a `redeem` call computes `inkind` (owed underlying) from the inflated `assets`/share-price ratio and `send-underlying` attempts to pay out more than the vault physically holds, reverting for some users (temporary freeze) or, combined with borrow/repay flows drawing down real liquidity first, leaving later redeemers permanently unable to withdraw their share (protocol insolvency).
