### Title
Fee-fragmentation bypass on NEP-245/IMT `TokenDiff` intents via the `amount <= 1` carve-out - (File: `contracts/defuse/core/src/intents/token_diff.rs`)

### Summary
`TokenDiff::execute_intent` computes and collects the protocol fee independently for each `TokenDiff` intent, using `Self::token_fee(token_id, amount, protocol_fee)` which returns `Pips::ZERO` whenever the per-intent `amount <= 1` for `Nep171`/`Nep245`/`Imt` token types. Since a single signed `DefusePayload`/`MultiPayload` (one `nonce`) can contain an arbitrary `Vec<Intent>` of `TokenDiff` intents that are each executed and fee-computed separately, an attacker can split one large negative delta on a NEP-245/IMT token into many `delta = -1` intents to make every fragment hit the zero-fee carve-out, while the equivalent single `TokenDiff` with the full negative delta would have paid `Pips::fee_ceil(amount)`.

### Finding Description
The broken binding is: total fee credited to `fee_collector` for token `T` across all `TokenDiff` intents sharing one `nonce`/batch should equal `protocol_fee.fee_ceil(|aggregate_negative_delta_of_T|)`, but the code instead computes and sums `Self::token_fee(T, |delta_i|, protocol_fee).fee_ceil(|delta_i|)` independently for each intent `i`: [1](#0-0) 

`Self::token_fee` explicitly zeroes the fee for `Nep171`, `Nep245`, and `Imt` token types whenever `amount <= 1`: [2](#0-1) 

Within a single signed `DefuseIntents` (one `nonce`), the list of `Intent`s is iterated and each executed independently with no cross-intent aggregation of deltas or fees: [3](#0-2) 

and `Engine::execute_signed_intent` verifies the signature/nonce once for the whole `DefuseIntents` batch and then simply calls `intents.execute_intent(...)`, which fans out per-intent fee logic: [4](#0-3) 

**Attacker payload:** sign one `DefusePayload<DefuseIntents>` under a single `nonce` containing 5 `TokenDiff` intents, each with `diff = {token_id: -1, other_token_id: +k}` (or matched via a counterparty payload in the same batch), all referencing the same NEP-245 `token_id`. Each intent independently computes `amount = 1`, hits the `amount <= 1` branch, and `token_fee` returns `Pips::ZERO`, so `fee_ceil(1) = 0` fee is collected per intent. The aggregate negative delta across the batch is `-5` on that token, but because no single intent ever sees `amount > 1`, `fees_collected` for the whole nonce/batch is `0`. Had the same net trade been expressed as one `TokenDiff` with `delta = -5`, `token_fee` would return the full `protocol_fee` (since `amount = 5 > 1`), yielding `protocol_fee.fee_ceil(5) > 0` for any nonzero `protocol_fee`.

No existing guard (`MultiPayload::verify`, `has_public_key`, `verify_intent_nonce`, `MaybeLegacyNonces::commit`, `SaltRegistry::is_valid`, `TransferMatcher::finalize`) inspects or aggregates deltas per token across intents in the same nonce/batch for fee purposes — they only guard signature/nonce/deadline/invariant validity, which are all satisfied here.

### Impact Explanation
The `fee_collector` receives strictly less protocol fee than the aggregate trade size would otherwise generate, for any NEP-245/IMT token whose per-unit value is significant (i.e., not a true 1-of-1 NFT). This is a systemic, repeatable underpayment of protocol fees: any unprivileged signer trading NEP-245/IMT-denominated assets can always fragment their negative deltas into `amount <= 1` chunks within one signed batch to drive fees on that leg to zero, regardless of trade size. This matches the Critical category "protocol fees bypassed or over-collected" since value (fee revenue) that should flow to `fee_collector` is retained by the trading parties instead, with no cap on repeatability across accounts, tokens, or batches.

### Likelihood Explanation
No special privileges are required — only the ability to sign a `MultiPayload` with multiple `TokenDiff` intents in one `nonce` and hold/trade a NEP-245 or IMT-typed token with `protocol_fee > 0`. The attacker's cost is simply constructing more intents per payload (bounded only by gas), which is straightforward and fully controllable client-side. This is directly reproducible in unit tests, since `token_fee`'s branch is unconditionally triggered whenever `amount <= 1` regardless of how many times it's invoked within the same nonce/batch.

### Recommendation
Aggregate deltas (and thus fee computation) per `token_id` across all `TokenDiff` intents within the same signed `DefuseIntents`/nonce before applying the `amount <= 1` carve-out, or restrict the zero-fee carve-out strictly to genuinely non-fragmentable NFTs (`Nep171`) rather than `Nep245`/`Imt`, which can represent divisible, fungible-like balances.

    fn execute_signed_intent(&mut self, signed: MultiPayload) -> Result<()> {
        // verify signed payload and get public key
        let public_key = signed.verify().ok_or(DefuseError::InvalidSignature)?;

        // calculate intent hash
        let hash = signed.hash();

        // extract NEP-413 payload
        let DefusePayload::<DefuseIntents> {
            signer_id,
            verifying_contract,
            deadline,
            nonce,
            message: intents,
        } = signed.extract_defuse_payload()?;

        // check recipient
        if verifying_contract != *self.state.verifying_contract() {
            return Err(DefuseError::WrongVerifyingContract);
        }

        self.inspector.on_deadline(deadline);

        // make sure message is still valid
        if deadline < Timestamp::now() {
            return Err(DefuseError::DeadlineExpired);
        }

        // make sure the account has this public key
        if !self.state.has_public_key(&signer_id, &public_key) {
            return Err(DefuseError::PublicKeyNotExist(signer_id, public_key));
        }

        // commit nonce
        self.verify_intent_nonce(nonce, deadline)?;
        self.state.commit_nonce(signer_id.clone(), nonce)?;

        intents.execute_intent(&signer_id, self, hash)?;
        self.inspector.on_intent_executed(&signer_id, hash, nonce);

        Ok(())
    }
