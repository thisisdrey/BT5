### Title
DNS-rebinding SSRF protection silently bypassed for `git://` URLs due to wrong branch in `GetURLAndResolveConfig` - ([File: internal/git/gitcmd/command_resolve.go])

### Summary
`GetURLAndResolveConfig` routes `git://` URLs through the same code path as `http://`/`https://`, generating an `http.curloptResolve` git-config value instead of rewriting the hostname to the resolved IP. Because the native `git://` transport (`connect.c`) is not implemented via libcurl, `http.curloptResolve` has no effect on it, so the actual outbound connection re-resolves the attacker-supplied hostname via real DNS at fetch/clone time, defeating the DNS-rebinding protection that `ResolvedAddress` is meant to enforce.

### Finding Description
`GetURLAndResolveConfig` in [1](#0-0)  dispatches based on URL prefix:
```go
switch {
case strings.HasPrefix(remoteURL, "http://"), strings.HasPrefix(remoteURL, "https://"), strings.HasPrefix(remoteURL, "git://"):
    return getURLAndResolveConfigForURL(remoteURL, resolvedAddress)
case strings.HasPrefix(remoteURL, "ssh://"):
    return getURLAndResolveConfigForSSH(remoteURL, resolvedAddress)
default:
    return getURLAndResolveConfigForSCP(remoteURL, resolvedAddress)
}
```
The function's own doc comment states the intended design at [2](#0-1) : for the **Git Protocol** the hostname should be *replaced* with the resolved IP (like SSH), while only HTTP/HTTPS should rely on `http.curloptResolve` because HTTPS needs the hostname preserved for TLS SNI/verification. However, the actual `switch` statement groups `git://` with `http/https` and calls `getURLAndResolveConfigForURL`, which at [3](#0-2)  leaves `remoteURL` (and thus the hostname) completely unmodified and only emits a `http.curloptResolve` config pair.

`http.curloptResolve` is consumed exclusively by Git's HTTP transport, which is implemented on top of libcurl (`CURLOPT_RESOLVE`). Git's native `git://` protocol implementation does not use libcurl at all — it opens a raw TCP socket via `git_connect()`/`connect.c`, which performs its own hostname resolution using the system resolver. Consequently, the `http.curloptResolve` config value set via `gitcmd.WithConfigEnv` in `cloneFromURLCommand` ( [4](#0-3) ) and `buildCommandOpts` ( [5](#0-4) ) is silently ignored, and the outbound `git clone`/`git fetch` process resolves the original attacker-controlled hostname from `remoteURL` at connection time via the real DNS resolver.

The existing test suite confirms this exact behavior is treated as correct/expected rather than caught as a bug: [6](#0-5)  shows `git://www.gitlab.com/foo/bar` produces `expectedURL: "git://www.gitlab.com/foo/bar"` (hostname unchanged) with only an `http.curloptResolve` config pair — i.e., the test locks in the non-functional mitigation for the `git://` scheme. By contrast, the `ssh://` case is handled correctly by `getURLAndResolveConfigForSSH`, which actually substitutes `u.Host = resolvedAddress` ( [7](#0-6) ), so SSH is not affected by this issue — only the `git://` scheme is.

No code path validates that `ResolvedAddress` is consistent with the hostname at the moment the git subprocess actually connects for `git://` URLs; the check is purely "IP syntax valid" ( [8](#0-7) ), not "actually pins the connection."

Both `CreateRepositoryFromURL` (via `cloneFromURLCommand`) and `FetchRemote` (via `buildCommandOpts`) accept attacker-controlled `Url`/`RemoteParams.Url` and `ResolvedAddress` fields with no scheme allowlist restricting `git://` before reaching `GetURLAndResolveConfig`, as confirmed by the absence of any scheme validation in these handlers.

### Impact Explanation
This is a Server-Side Request Forgery (SSRF) issue enabling a classic TOCTOU DNS-rebinding attack: an unprivileged attacker who can trigger `CreateRepositoryFromURL` or `FetchRemote` (e.g., via repository import/mirror features that pass through this RPC) with `Url: "git://attacker-domain/repo"` and any syntactically valid `ResolvedAddress` can bypass the intended IP-pinning defense. If the caller (e.g., GitLab Rails) validated `attacker-domain` at request time and computed `ResolvedAddress` from that DNS lookup, but the attacker re-points DNS for `attacker-domain` to an internal address before Gitaly's git subprocess actually connects, Gitaly will connect to the attacker's newly-resolved internal address — because the `http.curloptResolve` config is inert for the native git protocol. This can be leveraged to reach internal-only hosts/services (metadata endpoints, internal git daemons, etc.), matching GitLab's SSRF bounty impact class.

### Likelihood Explanation
Exploitation only requires: (1) the ability to invoke `CreateRepositoryFromURL` or `FetchRemote` with an attacker-controlled URL (available to any user who can import/mirror a repository from an arbitrary URL), and (2) control of DNS for the attacker's own domain to perform rebinding — both are standard, low-privilege SSRF/DNS-rebinding attacker capabilities and require no admin access, secrets, or MITM. The bug is deterministic and 100% reproducible for any `git://` URL, since the resolve-pinning logic never engages for that scheme regardless of DNS state.

### Recommendation
Fix the dispatch in `GetURLAndResolveConfig` so `git://` URLs are handled like `ssh://` — i.e., rewrite the hostname to `resolvedAddress` directly (native git protocol has no TLS/SNI requirement preventing this, unlike HTTPS) rather than relying on `http.curloptResolve`, which has no effect outside the libcurl-based HTTP transport. Update `command_resolve_test.go` to assert the hostname is actually replaced for `git://` URLs, and add a differential/regression test verifying resolve-pinning is enforced for `http://`, `https://`, `ssh://`, and `git://` alike.

```go
func getURLAndResolveConfigForURL(remoteURL, resolvedAddress string) (string, []ConfigPair, error) {
	u, err := url.ParseRequestURI(remoteURL)
	if err != nil {
		return "", nil, fmt.Errorf("couldn't parse remoteURL: %w", err)
	}

	port := u.Port()

	if port == "" {
		switch u.Scheme {
		case "http":
			port = "80"
		case "https":
			port = "443"
		case "git":
			port = "9418"
		default:
			return "", nil, fmt.Errorf("unknown schema provided: %s", u.Scheme)
		}
	}

	return remoteURL, []ConfigPair{
		{Key: "http.curloptResolve", Value: fmt.Sprintf("%s:%s:%s", u.Hostname(), port, resolvedAddress)},
	}, nil
}
```
