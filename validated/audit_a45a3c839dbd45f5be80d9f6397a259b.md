### Title
Firewall CA-name rules are tracked per CA name instead of per unique CA (fingerprint), allowing traffic authenticated by an unintended CA - (File: firewall.go)

### Summary
Nebula's firewall rules that reference a CA by name (`ca_name`) are stored and matched using the CA's human-readable `Name()` string as the map key, rather than the CA's cryptographic identity (fingerprint/SHA). Because `Name()` is not guaranteed to be unique across CAs in the trusted `CAPool`, a firewall rule authored against one specific CA can silently also match traffic signed by any other trusted CA that happens to share the same name.

### Finding Description
`FirewallCA.addRule` stores CA-scoped rules in two maps: `CAShas` keyed by CA fingerprint, and `CANames` keyed by the CA's name string: [1](#0-0) 

At match time, `FirewallCA.match` resolves the signer of the peer's certificate via `caPool.GetCAForCert`, then looks up the rule set purely by `s.Certificate.Name()`: [2](#0-1) 

The `CAPool` itself is keyed by fingerprint, not by name, and nothing enforces name uniqueness among the CAs added to a pool: [3](#0-2) 

This is structurally the same defect as the referenced external report: a mapping is keyed by a coarser, non-canonical identifier (CA "Name") when the actual security-relevant identity is the pair (specific-CA, rule), analogous to tracking oracles per pegged-token instead of per token-pair. If a Nebula CA pool contains two distinct CA certificates that happen to share the same `Name` (e.g., during a CA rotation/re-issuance where the operator keeps the same organizational name, or two independently-generated CAs are combined into one trust bundle with identical names), a `ca_name`-scoped firewall rule intended to admit traffic only from CA-A will also silently admit traffic signed by CA-B, since both resolve to the same `CANames[name]` bucket.

### Impact Explanation
An attacker who can obtain a certificate signed by *any* trusted CA sharing the targeted name (e.g., a CA added later, a CA from a merged trust bundle, or a rotated CA that an operator failed to distinguish by name) can bypass the intended, narrower `ca_name` firewall restriction and reach hosts/ports that were meant to be reachable only by certificates from a specific, named CA. This is a concrete firewall/authorization bypass: the rule evaluator (`FirewallTable.match` → `FirewallCA.match`) returns `true` for a certificate chain the operator did not intend to trust for that rule, letting otherwise-blocked packets through.

### Likelihood Explanation
Exploitation requires that the victim's `CAPool` actually contain two CAs sharing the same `Name` field (this is an operator/config-time property, not enforced unique anywhere in `AddCA`/`AddCAFromPEM`/`NewCAPoolFromPEM`). This is a realistic operational scenario for CA rotation (issuing a new CA cert with the same organizational name while temporarily keeping the old one trusted) and for merging certificate bundles from different sources. No malicious peer/lighthouse behavior is required — the attacker only needs a certificate legitimately signed by any CA in the pool that shares the targeted name, i.e., no special privilege beyond holding a certificate from a differently-provisioned but still-trusted CA.

### Recommendation
Key `CANames`-equivalent rule storage and lookup by the CA's fingerprint (already available via `Fingerprint()`/`CachedCertificate.Fingerprint`) rather than by `Name()`, or require and enforce CA name uniqueness within a `CAPool` at load time (`AddCA`/`NewCAPoolFromPEM`) and reject pools with duplicate CA names. At minimum, `FirewallCA.match` should verify that the resolved signer's fingerprint corresponds to the exact CA the rule was authored against, not just a name match.

### Proof of Concept
1. Build a `CAPool` containing two independently generated CA certificates, `caA` and `caB`, both with `Name() == "corp-ca"` but different key pairs/fingerprints (permitted, since `CAPool.AddCA` at [4](#0-3)  only keys by fingerprint and never checks for name collisions).
2. Configure a firewall rule with `ca_name: "corp-ca"` intended to admit traffic only from hosts whose certificate chains to `caA`.
3. Issue a peer certificate `certB` signed by `caB` (the differently-provisioned but still-trusted CA sharing the same name) and present it in a handshake.
4. On `Firewall.Drop` → `FirewallTable.match` → `FirewallCA.match` ( [5](#0-4) ), `caPool.GetCAForCert(certB)` resolves to `caB`, and `fc.CANames["corp-ca"]` returns the same rule object configured for `caA`'s traffic, so the packet is allowed — even though the rule was intended to trust only `caA`.

```go
func (fc *FirewallCA) match(p firewall.Packet, c *cert.CachedCertificate, caPool *cert.CAPool) bool {
	if fc == nil {
		return false
	}

	if fc.Any.match(p, c) {
		return true
	}

	if t, ok := fc.CAShas[c.Certificate.Issuer()]; ok {
		if t.match(p, c) {
			return true
		}
	}

	s, err := caPool.GetCAForCert(c.Certificate)
	if err != nil {
		return false
	}

	return fc.CANames[s.Certificate.Name()].match(p, c)
}
```

```go
// AddCA verifies a Nebula CA certificate and adds it to the pool.
func (ncp *CAPool) AddCA(c Certificate) error {
	if !c.IsCA() {
		return fmt.Errorf("%s: %w", c.Name(), ErrNotCA)
	}

	if !c.CheckSignature(c.PublicKey()) {
		return fmt.Errorf("%s: %w", c.Name(), ErrNotSelfSigned)
	}

	sum, err := c.Fingerprint()
	if err != nil {
		return fmt.Errorf("could not calculate fingerprint for provided CA; error: %w; %s", err, c.Name())
	}

	cc := &CachedCertificate{
		Certificate:    c,
		Fingerprint:    sum,
		InvertedGroups: make(map[string]struct{}),
	}

	for _, g := range c.Groups() {
		cc.InvertedGroups[g] = struct{}{}
	}

	ncp.CAs[sum] = cc

	if c.Expired(time.Now()) {
		return fmt.Errorf("%s: %w", c.Name(), ErrExpired)
	}

	return nil
}
```
