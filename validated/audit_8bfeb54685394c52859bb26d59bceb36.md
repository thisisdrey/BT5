### Title
Unbounded in-memory buffer accumulation in `sendSearchFilesResultChunked` enables memory-exhaustion DoS via `SearchFilesByContent` - ([File: internal/gitaly/service/repository/search_files.go])

### Summary
`sendSearchFilesResultChunked` accumulates all `git grep` output lines belonging to a single contiguous match "hunk" into an unbounded Go slice (`buf`) before ever sending anything to the client, only flushing when it encounters the literal `--\n` hunk separator that `git grep` normally emits between non-adjacent matches. An attacker who owns a repository can push a large blob where every line matches the search `Query` (with `--before-context`/`--after-context` set to `2`, so all matched lines stay within the same contiguous hunk), which means `git grep` never emits the `--\n` separator until the entire file has been read, forcing the whole file's grep output into memory in one `buf` before any data is streamed out or bounded.

### Finding Description
`SearchFilesByContent` at [1](#0-0)  runs `git grep` with `--before-context 2 --after-context 2` and the attacker-controlled `Query` (`-e`) against the attacker-controlled `Ref`, both of which come directly from the unvalidated (beyond emptiness/leading-dash checks) RPC request at [2](#0-1) .

The output is consumed line-by-line in `sendSearchFilesResultChunked`: [3](#0-2) 

Each line read from `git grep`'s stdout is appended to `buf` with no size cap, and `buf` is only flushed (via `sendMatchInChunks`) when a line exactly equals the `--\n` delimiter that `git grep` emits between two non-adjacent hunks of context. If an attacker crafts a file where every line matches `Query` (e.g., a repeated pattern), then with a 2-line context window, all matched lines form one single, uninterrupted hunk for that file — `git grep` will not emit `--\n` at all until it moves past the end of that hunk. This means `buf` grows to the full size of that file's grep output (matched line + `-` /`:`-separated NUL fields) before a single byte is streamed to the gRPC client, and before `sendMatchInChunks`/`streamio.NewWriter` gets a chance to chunk anything into bounded gRPC messages.

There is no maximum size check on `buf`, no cap tied to file size, and no defensive limit anywhere in `search_files.go` (the only length limit present, `searchFilesFilterMaxLength`, applies only to `SearchFilesByName`'s `Filter` field, not to `SearchFilesByContent`). The repository's existing test suite already demonstrates this exact behavior is intentional/uncontrolled: the `"large file"` test case pushes a 2.1 MB file (`strings.Repeat("abcdefghi\n", 210000)`) where every line matches the query, and the resulting single match blob is accumulated and returned as one chunked unit [4](#0-3) [5](#0-4) . Scaling this file size up to multiple gigabytes (well within what an unprivileged user can push to their own repository) directly translates into multi-gigabyte in-process memory allocation on the Gitaly node handling the request.

None of the existing checks (`validateSearchFilesRequest`, `locator.ValidateRepository`, ref leading-dash check) constrain the size or content of the blob being searched, so this path is fully reachable by an unprivileged, self-repo-owning attacker.

### Impact Explanation
A single `SearchFilesByContent` RPC call against an attacker-owned repository with a crafted multi-gigabyte blob whose every line matches the query can force the Gitaly process to allocate memory proportional to the blob size in one unbounded `buf`. Because Gitaly is multi-tenant (a single Gitaly node serves many repositories/projects), this can exhaust node memory and cause the process to be OOM-killed or become unresponsive, denying service to all other repositories co-located on that storage node — matching a DoS/resource-exhaustion impact class.

### Likelihood Explanation
The attacker only needs standard push access to a repository they own (no special role, no shell/disk access, no admin), and can construct the crafted blob using ordinary git operations. The RPC is a standard user-facing search feature (used by GitLab's code search) and thus reachable without extra privilege. The reproduction is deterministic and repeatable given the existing test scaffolding already exercises this exact code path with smaller files.

### Recommendation
Impose a bound on `buf` in `sendSearchFilesResultChunked` (e.g., flush/stream once `buf` exceeds a fixed threshold, independent of encountering the `--\n` delimiter), or restructure the function to stream matched lines directly via `sendMatchInChunks`/`streamio.NewWriter` as they're read rather than buffering an entire hunk in memory. Additionally, consider limiting maximum grep output size or blob size considered for content search.

### Proof of Concept
Extend the existing test in `internal/gitaly/service/repository/search_files_test.go` with a much larger commit, mirroring the current `"large file"` case but scaled to gigabyte size:

func sendSearchFilesResultChunked(cmd *command.Command, stream gitalypb.RepositoryService_SearchFilesByContentServer) error {
	var buf []byte
	reader := bufio.NewReader(cmd)

	for {
		line, err := reader.ReadBytes('\n')
		if err == io.EOF {
			break
		} else if err != nil {
			return fmt.Errorf("readbytes: %w", err)
		}

		if bytes.Equal(line, contentDelimiter) {
			if err := sendMatchInChunks(buf, stream); err != nil {
				return err
			}

			buf = nil
			continue
		}

		buf = append(buf, line...)
	}

	if len(buf) > 0 {
		return sendMatchInChunks(buf, stream)
	}

	return nil
}

func validateSearchFilesRequest(ctx context.Context, locator storage.Locator, req searchFilesRequest) error {
	if err := locator.ValidateRepository(ctx, req.GetRepository()); err != nil {
		return err
	}

	if len(req.GetQuery()) == 0 {
		return errors.New("no query given")
	}

	if len(req.GetRef()) == 0 {
		return errors.New("no ref given")
	}

	if bytes.HasPrefix(req.GetRef(), []byte("-")) {
		return errors.New("invalid ref argument")
	}

	return nil
}
