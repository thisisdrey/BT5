Audit Report

## Title
`pallet-asset-conversion`'s `do_add_liquidity`/`do_remove_liquidity` trust the requested transfer amount instead of the amount actually moved, allowing under-funded LP-token minting and reserve desynchronization - ([File: substrate/frame/asset-conversion/src/lib.rs])

## Summary
`do_add_liquidity` and `do_remove_liquidity` call `T::Assets::transfer`/`T::PoolAssets::transfer` and discard the returned `Result<T::Balance, DispatchError>` (which carries the *actual* amount moved), instead using the pre-computed `amount1`/`amount2` for LP-token mint/burn math, reserve accounting, and event emission. The generic default `fungibles::Mutate::transfer` implementation performs `decrease_balance`/`increase_balance` with `BestEffort` precision internally but unconditionally returns `Ok(amount)` (the requested amount, not the amount actually settled), and `pallet-assets` does not override `transfer()` to fix this, so the same pallet family already defends against this exact gap elsewhere (`asset-conversion/ops`) but not in the core liquidity path.

## Finding Description
In `do_add_liquidity` (`substrate/frame/asset-conversion/src/lib.rs:855-856`):
```rust
T::Assets::transfer(asset1, who, &pool_account, amount1, Preserve)?;
T::Assets::transfer(asset2, who, &pool_account, amount2, Preserve)?;
```
the return values are discarded via `?`, and `amount1`/`amount2` (the pre-computed *desired* amounts) are then used directly for `mul_div` reserve-ratio math (lines 869-871) to compute `lp_token_amount`, and again emitted in `Event::LiquidityAdded` (lines 885-886) as the authoritative provided amounts.

The same pattern occurs in `do_remove_liquidity` (lines 951-959): `T::Assets::transfer(asset1, &pool_account, withdraw_to, amount1, Expendable)?;` discards the return value, and `amount1`/`amount2` are used in `Event::LiquidityRemoved` and as the function's return value, which callers (`remove_liquidity` extrinsic) treat as the settled result.

The generic default implementation of `fungibles::Mutate::transfer` (`substrate/frame/support/src/traits/tokens/fungibles/regular.rs:366-386`) performs:
```rust
Self::decrease_balance(asset.clone(), source, amount, BestEffort, preservation, Polite)?;
let _ = Self::increase_balance(asset.clone(), dest, amount, BestEffort);
Self::done_transfer(asset, source, dest, amount);
Ok(amount)
```
This always uses `BestEffort` precision for both legs (independent of the caller-specified `preservation`) yet returns the *requested* `amount`, not the actual balance moved. `pallet-assets` does not override `Mutate::transfer` in `substrate/frame/assets/src/impl_fungibles.rs` (only `done_transfer`, `decrease_balance`, `increase_balance` are implemented there), so it inherits this default behavior, meaning any AssetHub-style runtime using `pallet-assets` as `T::Assets`/`T::PoolAssets` is subject to this discrepancy.

Critically, `pallet-assets`' own `increase_balance` override (`substrate/frame/assets/src/impl_fungibles.rs:209-217`) also discards the actual result and unconditionally returns `Ok(amount)`:
```rust
fn increase_balance(...) -> Result<Self::Balance, DispatchError> {
    Self::increase_balance(asset, who, amount, |_| Ok(()))?;
    Ok(amount)
}
```
so the requested amount is echoed back even at this lower level, compounding the gap.

By contrast, `substrate/frame/asset-conversion/ops/src/lib.rs:209-243` explicitly guards against this exact scenario:
```rust
ensure!(
    balance1 == T::Assets::transfer(asset1.clone(), &prior_account, &new_account, balance1, Preservation::Expendable)?,
    Error::<T>::PartialTransfer
);
```
demonstrating the pallet authors are aware `transfer()`'s return value can diverge from the requested amount, yet `do_add_liquidity`/`do_remove_liquidity` — the core liquidity-accounting paths used by every `add_liquidity`/`remove_liquidity` extrinsic call — apply no equivalent check.

The reachable exploit path: `do_add_liquidity` only validates that the *pool account's post-transfer balance* (`amount1.saturating_add(reserve1)`) meets the asset's minimum balance (lines 846-853); it never validates that the *source* (`who`) account can fully deliver `amount1` while preserving its own existence. Since `transfer()` is invoked with `Preserve` (keep-alive) and the default implementation forces `BestEffort` decrease regardless, if `who`'s pre-transfer balance minus `amount1` would fall below the asset's minimum balance, `decrease_balance` under `BestEffort` will silently transfer less than `amount1` rather than erroring, yet `do_add_liquidity` proceeds to mint `lp_token_amount` computed from the full, unverified `amount1`.

## Impact Explanation
This breaks the value-conservation invariant required for pool/AMM accounting: `pallet-asset-conversion` can mint LP tokens (an unbacked mint) that are not fully backed by assets actually deposited into the pool account, and `do_remove_liquidity` can emit/report withdrawal amounts (`amount1`/`amount2`) that do not match what was actually delivered to `withdraw_to`, permanently desynchronizing `get_reserves()`-derived pricing from real balances. This matches the "Balances, assets ... must conserve value and settle exactly once to the rightful beneficiary and amount" pivot and constitutes an unbacked-mint/value-conservation violation reachable via the public `add_liquidity`/`remove_liquidity` extrinsics.

## Likelihood Explanation
The bug is exploitable by any unprivileged liquidity provider using the public `add_liquidity` extrinsic with a `T::Assets`/`T::PoolAssets` configuration backed by `pallet-assets` (which does not override `Mutate::transfer` and thus inherits the default `BestEffort`-then-echo behavior), provided the caller's source account balance is positioned near the asset's minimum balance so that a keep-alive-constrained `BestEffort` withdrawal silently delivers less than requested. No malicious admin, governance, or compromised infrastructure is required — this is directly triggerable through standard, permissionless calls and existing default trait implementations shipped in this repository.

## Recommendation
Capture and validate the actual transferred amounts in `do_add_liquidity` and `do_remove_liquidity`, mirroring the pattern already used in `substrate/frame/asset-conversion/ops/src/lib.rs`:
```rust
let transferred1 = T::Assets::transfer(asset1, who, &pool_account, amount1, Preserve)?;
ensure!(transferred1 == amount1, Error::<T>::PartialTransfer);
```
and use the verified actual amounts for all subsequent LP-token mint/burn and reserve-ratio math and events. Additionally, fix `fungibles::Mutate::transfer`'s default implementation (`substrate/frame/support/src/traits/tokens/fungibles/regular.rs:366-386`) and `pallet-assets`' `increase_balance` override (`substrate/frame/assets/src/impl_fungibles.rs:209-217`) to return the balance actually moved rather than echoing the requested `amount`.

## Proof of Concept
Test plan: configure a mock runtime for `pallet-asset-conversion` using `pallet-assets` as `T::Assets` (default, unmodified). Create an asset with a non-zero minimum balance. Fund an account `who` with a balance equal to `amount1 + minimum_balance - 1`. Call `add_liquidity` with `amount1_desired = amount1`. Because `transfer()` is invoked with `Preserve` and internally uses `BestEffort` precision, `decrease_balance` will withdraw less than `amount1` to keep `who` alive, yet the default `transfer()` still returns `Ok(amount1)` and `do_add_liquidity` proceeds to compute `lp_token_amount` from the full `amount1`. Assert that the pool account's real balance increase is less than `amount1` while `Event::LiquidityAdded.amount1_provided` and the minted `lp_token_amount` reflect the full, unverified `amount1`, demonstrating unbacked LP-token minting.
