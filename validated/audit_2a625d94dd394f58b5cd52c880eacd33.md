### Title
Attacker can fill a victim's per-account token list via dust deposits/transfers, DoSing all new deposits, transfers, and synthetic issuance for that account - ([File: contracts/Pool.sol])

### Summary
`Pool` enforces `MAX_TOKENS_PER_USER = 30` combined slots across `depositTokensOfAccount` and `debtTokensOfAccount` via `onlyIfAdditionWillNotReachMaxTokens` (`Pool.sol:143-148`). Every balance 0→nonzero transition on a `DepositToken` calls `pool.addToDepositTokensOfAccount(account_)` (`DepositToken.sol:486-488` in `_mint`, `DepositToken.sol:518-520` in `_transfer`), which reverts with `UserReachedMaxTokens` once the victim holds 30 distinct tokens. An unprivileged attacker can force-add entries to an arbitrary victim's list by calling `deposit(amount_, onBehalfOf_ = victim)` with dust amounts on every registered `DepositToken`, or by transferring dust of their own msdTOKEN balances. Once the list is full, any subsequent action that would register a new token for the victim — `deposit`/`depositOnBehalf`, `transfer`/`transferFrom` to them, `seize` proceeds, and `issue` of a new `DebtToken` (which calls `addToDebtTokensOfAccount`) — reverts, mirroring the CVE's "easily exploitable, repeatably crash/hang" class.

### Finding Description
- `Pool.addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` are the only writers to the per-account enumerable sets, gated by `onlyIfAdditionWillNotReachMaxTokens(account_)`, which reverts when `length >= 30` (`Pool.sol:79`, `143-148`, `204-220`).
- `DepositToken._mint` adds the recipient whenever `_balanceBefore == 0 && amount_ > 0` — there is no minimum amount and no opt-in by the recipient (`DepositToken.sol:469-489`). The public `deposit(uint256 amount_, address onBehalfOf_)` mints to an arbitrary `onBehalfOf_`, so the attacker never needs the victim's cooperation.
- `DepositToken._transfer` applies the same rule to plain transfers (`DepositToken.sol:498-526`), giving a second, cheaper vector (attacker deposits once per token, then dust-transfers to many victims).
- `DebtToken.issue` records debt on `_msgSender` (`DebtToken.sol:250-262`), so debt tokens can't be pushed onto a victim, but filling deposit-token slots alone saturates the combined counter.

### Impact Explanation
The victim's account is put into a state where any operation requiring a new list entry reverts: they cannot deposit a collateral type they don't already hold, cannot receive msdTOKEN transfers, and — most importantly — cannot `issue` any `DebtToken` they don't already have, since minting the first debt token for a new synthetic triggers `addToDebtTokensOfAccount` and reverts. A liquidator seizing collateral into a fresh account can also be blocked mid-flow. The DoS is repeatable and persistent until the victim manually transfers dust balances back out to zero to trigger `removeFromDepositTokensOfAccount`; many victims (contracts, gateways, SmartFarming position accounts) cannot perform such ERC20 transfers and would be permanently bricked for new-position functionality. This is a temporary-to-permanent freezing of position-management capability, reachable entirely by an unprivileged EOA.

### Likelihood Explanation
Requires no privileged role, no oracle manipulation, and no timing. Cost is dust deposits across the pool's deposit tokens (bounded by the number of registered collaterals, typically far below 30, plus issue of dust debt by the victim's own positions is not needed). One attacker wallet can deposit dust on behalf of unlimited victims. The only prerequisite is that the victim holds fewer than 30 token types.

### Recommendation
- Do not count tokens toward `MAX_TOKENS_PER_USER` (or do not revert) when the addition was not initiated by the account — e.g., let `addTo*` fail-soft and skip adding instead of reverting, since the sets are only used for iterating positions in `debtOf`/`depositOf`/`debtPositionOf`.
- Alternatively, make `deposit(onBehalfOf_)`/`transfer` add-to-list conditional on recipient consent, or sweep dust entries: allow `removeFromDepositTokensOfAccount` to be callable for zero-balance entries regardless of caller context so anyone can clean a victim's list.

### Proof of Concept
Hardhat sketch against deployed-style fixtures:

```ts
// pool has >= 2 deposit tokens msdA, msdB; MAX_TOKENS_PER_USER = 30
// attacker: any EOA holding underlying
for (const dt of allDepositTokens) {           // up to 30 tokens
  const underlying = await dt.underlying();
  await erc20(underlying).approve(dt.address, DUST);
  await dt.deposit(DUST, victim.address);       // adds dt to victim's list
}
// victim's list is now full
await expect(
  newDepositToken.deposit(parseEther('1'), victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// victim also cannot issue a new synthetic
await expect(
  newDebtToken.connect(victim).issue(amount, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

Verification uncertainty: `DebtToken.issue` mints debt to `_msgSender`, so if the victim already has ≥1 debt token the issuance path for that same token still works; the freeze applies only to *new* token types. Also, the victim can self-recover by transferring dust out — the permanent-brick case applies to accounts that cannot call `transfer` (e.g., contracts holding positions).
