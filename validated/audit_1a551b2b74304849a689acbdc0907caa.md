### Title
Unbounded array allocation from attacker-controlled length field in `ValidateMultiSign`/`BatchValidateSign` precompiles - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The Snappy advisory's root cause is that a decoder trusts an attacker-supplied length field and allocates a buffer of that size before validating it against any sane bound. The same pattern exists in java-tron's `ValidateMultiSign` and `BatchValidateSign` TVM precompiles: the helper methods `extractBytesArray`, `extractBytes32Array`, and `extractSigArray` read a signature/address-array length directly from calldata and immediately allocate `new byte[len][]`, with the size cap only enforced conditionally on `VMConfig.allowTvmSelfdestructRestriction()`.

### Finding Description
In `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`: [1](#0-0) 

`extractBytesArray`/`extractBytes32Array`/`extractSigArray` all take `len = words[offset].intValueSafe()` — a value taken straight from the caller-supplied calldata — and immediately do `new byte[len][]` with no upper bound check inside these helper functions themselves.

The `MAX_SIZE` bound (`5` for `ValidateMultiSign`, `16` for `BatchValidateSign`) is only checked *before* calling these helpers, and only when the hard-fork flag `VMConfig.allowTvmSelfdestructRestriction()` is enabled: [2](#0-1) [3](#0-2) 

When `allowTvmSelfdestructRestriction()` is `false` (the pre-activation / legacy code path, still present and reachable on any TRON-based network where that specific proposal has not been approved by the committee, including new private/consortium chains and historically on the public chain prior to that proposal's activation), `extractBytesArray`/`extractSigArray` are invoked with **no size check at all**, and `len` is fully attacker controlled up to whatever `intValueSafe()` yields for a crafted 256-bit calldata word. This allows a single crafted `TriggerSmartContract` call to force allocation of an oversized `byte[len][]` array (or negative length causing `NegativeArraySizeException`) purely from the transaction's calldata content, with no signature verification, no state prerequisites, and no committee/witness privilege required — reachable by any account able to broadcast a `TriggerSmartContract` transaction that calls (or CALLs into) the `validatemultisign`/`batchvalidatesign` precompiled addresses.

The test suite's own comments confirm this is a known intentional legacy gap ("TIP-854: before activation, malformed calldata reaches the legacy decoder... this precompile has no outer catch, so a too-short input raises inside the decoder"), i.e. `ValidateMultiSign.execute()` has no `try/catch` wrapper at all, so an `OutOfMemoryError`/`NegativeArraySizeException`/`ArrayIndexOutOfBoundsException` raised deep in `extractBytesArray` propagates out of `execute()` uncaught by the precompile layer: [4](#0-3) 

### Impact Explanation
`OutOfMemoryError` is an `Error`, not an `Exception`, and typical VM/transaction-processing catch blocks that catch `Exception` (as seen even in the hardened `BatchValidateSign.execute()` which does catch `Throwable`, but `ValidateMultiSign.execute()` does not wrap `doExecute`-equivalent logic in any catch at all) will not intercept it. An uncaught `Error` thrown while processing a transaction inside block application can destabilize/crash the node process or corrupt the deterministic execution path across nodes that have and have not yet activated the guarding proposal, risking a chain split (some nodes with the flag on skip the bug, others without it crash or behave differently). This satisfies the "node crash or halt / chain split" impact bar.

### Likelihood Explanation
The vulnerable helpers are reachable from a single, unprivileged, broadcastable `TriggerSmartContract` transaction that calls the `validatemultisign`/`batchvalidatesign` precompiled contract addresses — no special permission, no deployed malicious contract even required beyond calling the fixed precompile address with crafted calldata. Likelihood is gated entirely on whether `allowTvmSelfdestructRestriction()` is enabled on the target chain; on any TRON-derived chain (private/consortium networks, forks, or historical states of the public chain) where this specific proposal has not been activated, the vulnerable path is unconditionally exercised.

### Recommendation
Move the `MAX_SIZE` length validation inside `extractBytesArray`, `extractBytes32Array`, and `extractSigArray` themselves (unconditionally, not gated behind `allowTvmSelfdestructRestriction()`), rejecting any `len` that is negative or exceeds the maximum reasonably expected array size before allocating `new byte[len][]`. Additionally wrap `ValidateMultiSign.execute()` in a `try/catch(Throwable)` consistent with `BatchValidateSign.execute()` so any residual decode failures degrade to a rejected/false result instead of propagating an `Error`/`RuntimeException` out of the precompile.

### Proof of Concept
1. Craft a `TriggerSmartContract` transaction whose calldata targets the `validatemultisign(address,uint256,bytes32,bytes[])` precompile with the `bytes[]` array-length word (at the offset consumed by `words[3]`) set to a very large value (e.g. `0x7FFFFFFF`) while `VMConfig.allowTvmSelfdestructRestriction()` is disabled (default/legacy state on a fresh or non-activated chain).
2. Broadcast the transaction; `ValidateMultiSign.execute()` calls `extractBytesArray(words, offset, rawData)` which executes `new byte[0x7FFFFFFF][]`, throwing `OutOfMemoryError` (or `NegativeArraySizeException`/`ArrayIndexOutOfBoundsException` for other crafted offsets) directly out of `execute()`, uncaught.
3. Observe abnormal termination/instability of the executing node's transaction-processing thread, or divergent behavior versus nodes that already have the restriction proposal activated.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {

      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
