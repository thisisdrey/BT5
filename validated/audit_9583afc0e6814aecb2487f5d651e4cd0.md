### Title
Path traversal via unsanitized tar extraction in `CreateRepositoryFromSnapshot` - ([File: internal/gitaly/service/repository/create_repository_from_snapshot.go])

### Summary
`server.untar` pipes an attacker-supplied HTTP response body directly into a raw `tar -C <path> -xvf -` subprocess with no per-entry validation of tar member names, unlike the hardened `extractTarToDirectory` used by `ReplicateRepository` which explicitly checks for path escapes, absolute symlinks, and hard-link targets via `strings.HasPrefix` boundary checks. [1](#0-0) [2](#0-1)  If the archive contains entries with absolute paths or `../` traversal segments, GNU `tar` (unless run with `--no-same-owner`/no restriction flags, which are not passed here) will happily write outside the target directory, since no `-P`/anchoring restriction is disabled by default behavior differs by tar implementation but is not something Gitaly enforces itself.

### Finding Description
`CreateRepositoryFromSnapshot` creates a brand-new (previously nonexistent) repository directory via `repoutil.Create`, then calls `s.untar(ctx, path, in)` with `path` being that repo's on-disk path. [3](#0-2)  `untar` fetches `in.GetHttpUrl()` (optionally with `in.GetHttpAuth()`), and streams the raw HTTP response body straight into `tar -C path -xvf -` via `command.New` with `command.WithStdin(rsp.Body)` — there is no Go-level parsing of the tar stream, no per-entry name validation, and no comparison against `path`. [4](#0-3)  The code comment itself acknowledges this: *"NOTE: The received archive is trusted a lot. Before pointing this RPC at endpoints not under our control, it should undergo a lot of hardening."* [5](#0-4)  This is in stark contrast to `ReplicateRepository`'s `extractTarToDirectory`, which manually walks each tar header and enforces `strings.HasPrefix(targetPath, targetDir+string(os.PathSeparator))` for regular files/dirs, symlink targets, and hard-link targets before writing anything to disk. [6](#0-5)  Because `in.GetHttpUrl()` and the content served at that URL are attacker-controlled (an unprivileged user triggering an import/fork flow that supplies a self-hosted `http_url`), the attacker fully controls the tar stream's entry names and can include absolute paths (e.g. `/tmp/evil` or `/home/git/repositories/other-repo/hooks/pre-receive`) or relative traversal (e.g. `../../other-namespace/other-repo.git/hooks/pre-receive`).

### Impact Explanation
If the underlying `tar` binary honors absolute paths and `..` traversal (default GNU tar behavior without `-P` restriction historically allows absolute paths unless `--absolute-names` is disabled, and does not, by default, block `..` in entry names unless it detects it would escape and warns/skips — behavior is implementation- and version-dependent), a successful escape allows arbitrary file write/overwrite outside the newly created repository directory. This could clobber another repository's Git objects/refs/config, or plant/overwrite a hook script (e.g. `hooks/pre-receive`) in another repository, leading to remote code execution when that other repository is next pushed to — a severe cross-tenant compromise on a shared Gitaly storage. This matches the GitLab bounty "Path Traversal" / "Arbitrary File Write leading to RCE" impact class.

### Likelihood Explanation
Preconditions: the attacker must be able to trigger `CreateRepositoryFromSnapshot` with attacker-controlled `HttpUrl`/`HttpAuth` and attacker-controlled response content. Whether this RPC is reachable end-to-end by an unprivileged GitLab user depends entirely on how GitLab Rails invokes it (e.g., project import/fork flows) — this is outside the Gitaly repo and could not be confirmed from the code available here. Within Gitaly itself, no RPC-level authorization beyond standard gRPC/Praefect ACL exists to restrict who can call `CreateRepositoryFromSnapshot`, and the handler itself performs no sanitization of the tar content once the RPC is invoked. Feasibility also depends on the actual behavior of the `tar` binary on the deployed OS/distribution when fed absolute or `..`-containing entry names (some GNU tar builds strip leading `/` and warn on `..` but still proceed, others refuse); this platform-dependent behavior could not be verified against a live binary in this analysis and should be validated in the recommended PoC.

### Recommendation
Replace the raw `tar -C path -xvf -` subprocess invocation in `s.untar` with the same hardened, per-entry-validated extraction logic already implemented as `extractTarToDirectory`/`extractFile` in `replicate.go` (or a shared helper), enforcing `filepath.Clean` + prefix-boundary checks on every tar header's `Name` and `Linkname` (for symlinks and hard links) before any filesystem write, and rejecting absolute paths and any path resolving outside the target repository directory, consistent with the existing hardened implementation.

// extractTarToDirectory extracts a tar archive to the specified directory using Go's tar package
func (s *server) extractTarToDirectory(ctx context.Context, reader io.Reader, targetDir string) error {
	targetDir = filepath.Clean(targetDir)
	tarReader := tar.NewReader(reader)

	for {
		select {
		case <-ctx.Done():
			return ctx.Err()
		default:
		}

		header, err := tarReader.Next()
		if err == io.EOF {
			break // End of archive
		}
		if err != nil {
			return fmt.Errorf("reading tar header: %w", err)
		}

		targetPath := filepath.Join(targetDir, header.Name)

		if !strings.HasPrefix(targetPath, targetDir+string(os.PathSeparator)) &&
			targetPath != targetDir {
			return fmt.Errorf("invalid file path in tar: %s", header.Name)
		}

		switch header.Typeflag {
		case tar.TypeDir:
			if err := os.MkdirAll(targetPath, os.FileMode(header.Mode)); err != nil {
				return fmt.Errorf("creating directory %s: %w", targetPath, err)
			}

		case tar.TypeReg:
			if err := s.extractFile(ctx, tarReader, targetPath, header); err != nil {
				return fmt.Errorf("extracting file %s: %w", targetPath, err)
			}

		case tar.TypeSymlink:
			if filepath.IsAbs(header.Linkname) {
				return fmt.Errorf("absolute symlink not allowed: %s -> %s", header.Name, header.Linkname)
			}

			// Resolve the relative symlink target from the symlink's parent directory
			// and verify it stays within the extraction boundary, consistent with the
			// hard link validation below.
			resolvedTarget := filepath.Join(filepath.Dir(targetPath), header.Linkname)
			if !strings.HasPrefix(resolvedTarget, targetDir+string(os.PathSeparator)) &&
				resolvedTarget != targetDir {
				return fmt.Errorf("symlink target escapes extraction directory: %s -> %s", header.Name, header.Linkname)
			}

			// Remove existing file/symlink if it exists
			if err := os.Remove(targetPath); err != nil && !os.IsNotExist(err) {
				return fmt.Errorf("removing existing file for symlink %s: %w", targetPath, err)
			}

			if err := os.Symlink(header.Linkname, targetPath); err != nil {
				return fmt.Errorf("creating symlink %s -> %s: %w", targetPath, header.Linkname, err)
			}

		case tar.TypeLink:
			linkTarget := filepath.Join(targetDir, header.Linkname)

			if !strings.HasPrefix(linkTarget, targetDir+string(os.PathSeparator)) &&
				linkTarget != targetDir {
				return fmt.Errorf("invalid hard link target: %s", header.Linkname)
			}

			// Remove existing file if it exists
			if err := os.Remove(targetPath); err != nil && !os.IsNotExist(err) {
				return fmt.Errorf("removing existing file for hard link %s: %w", targetPath, err)
			}

			if err := os.Link(linkTarget, targetPath); err != nil {
				return fmt.Errorf("creating hard link %s -> %s: %w", targetPath, linkTarget, err)
			}
