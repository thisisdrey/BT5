### Title
Unbounded, unpaginated `AssetIssueStore`/`ExchangeStore` query endpoints can be DoSed by permissionless asset/exchange creation - ([File: framework/src/main/java/org/tron/core/Wallet.java])

### Summary
The reported bug class — a permissionless registration function that lets anyone grow an on-chain list without limit, combined with a non-paginated view function that must iterate the whole list — has a concrete analog in java-tron. `Wallet.getAssetIssueList()` and `Wallet.getExchangeList()` iterate the *entire* `AssetIssueStore`/`ExchangeStore` with no offset/limit, and both stores can be grown indefinitely by any unprivileged account issuing `AssetIssueContract` or `ExchangeCreateContract` transactions. These legacy unpaginated methods remain reachable through HTTP servlets and gRPC endpoints even though paginated variants exist, meaning the unbounded code paths are still directly callable by any anonymous API client.

### Finding Description
`AssetIssueStore.getAllAssetIssues()` performs a full store scan with no bound: [1](#0-0) . This is invoked directly by the non-paginated `Wallet.getAssetIssueList()`, which also runs bandwidth-usage processing for every entry: [2](#0-1) . The same unbounded full-scan pattern is used by `getAssetIssueByAccount()` and `getAssetIssueListByName()`, which still call `getAllAssetIssues()` and filter client-side instead of using an index: [3](#0-2) [4](#0-3) .

These unbounded methods are directly reachable by any anonymous client via `GetAssetIssueListServlet` (`/wallet/getassetissuelist`) [5](#0-4) , as well as via gRPC (`getAssetIssueList`, exposed on the full node, solidity node and PBFT node) [6](#0-5) [7](#0-6) .

The identical pattern exists for exchanges: `Wallet.getExchangeList()` fully iterates `ExchangeStore`/`ExchangeV2Store` without any limit [8](#0-7) , and is reachable unauthenticated through `ListExchangesServlet` [9](#0-8) .

Growth of these stores is permissionless: `ExchangeCreateActuator.execute()` lets any account with sufficient balance create a new `Exchange` entry, gated only by a configurable fee (`getExchangeCreateFee()`), not by any admin/whitelist check [10](#0-9) [11](#0-10) . `AssetIssueContract` similarly lets any account create a new TRC10 token for a fixed fee, adding a permanent entry to `AssetIssueStore`.

Notably, the project has already recognized this class of problem and added paginated alternatives — `Wallet.getAssetIssueList(offset, limit)` backed by `AssetIssueStore.getAssetIssuesPaginated()` [12](#0-11) [13](#0-12) , and `GetPaginatedExchangeListServlet` for exchanges — but the original unbounded methods and their servlets/RPCs were kept alongside the paginated ones instead of being removed or capped, leaving the unbounded code paths exploitable exactly as in the reported analog.

### Impact Explanation
As `AssetIssueStore`/`ExchangeStore` grow (each entry added permanently and permissionlessly by paying a fixed, non-prohibitive fee), the O(n) full-store scan performed by `getAssetIssueList()`, `getAssetIssueByAccount()`, `getAssetIssueListByName()`, and `getExchangeList()` gets progressively more expensive. Since these are unauthenticated, un-rate-limited-by-size HTTP/gRPC query endpoints served by full nodes, solidity nodes, and PBFT nodes, an attacker who mass-creates TRC10 assets or exchanges can drive CPU/memory usage and response latency of these endpoints up until they time out or exhaust node resources — an API the node can no longer reliably serve, matching the "no-fix-yet, node/API DoS" impact class accepted in the source report.

### Likelihood Explanation
The attack requires no special privilege — any funded account (the "asset issuer" / "order placer" role explicitly in scope) can repeatedly submit `AssetIssueContract`/`ExchangeCreateContract` transactions. The only friction is the configurable creation fee per entry, which bounds the growth rate but not the eventual size, so this is a capital-bounded but fully permissionless and repeatable griefing vector rather than a free one — lower likelihood than the original `middleware-sdk` report (which had no cost at all), but still concretely reachable without any admin or witness role.

### Recommendation
Deprecate and remove (or hard-cap) the unbounded `getAssetIssueList()`, `getAssetIssueByAccount()`, `getAssetIssueListByName()`, and `getExchangeList()` code paths, or transparently redirect them to the paginated implementations with an enforced maximum page size (already partially done via `ASSET_ISSUE_COUNT_LIMIT_MAX` in `AssetIssueStore.getAssetIssuesPaginated`). Add equivalent limit enforcement to `getExchangeList()` and to the by-account/by-name asset lookups by using an indexed store lookup instead of a full scan + filter.

### Proof of Concept
1. Use N funded accounts (or one account, sequentially) to submit `AssetIssueContract` (or `ExchangeCreateContract`) transactions, each paying the fixed creation fee, to add N entries to `AssetIssueStore`/`ExchangeStore`.
2. As N grows large, repeatedly call `GET/POST /wallet/getassetissuelist` (`GetAssetIssueListServlet`) or `/wallet/listexchanges` (`ListExchangesServlet`), or the corresponding gRPC `getAssetIssueList`/`listExchanges` methods.
3. Observe that response latency and node resource usage scale linearly with N, since `Wallet.getAssetIssueList()`/`getExchangeList()` perform a full unbounded store scan and per-entry bandwidth processing on every call, eventually causing request timeouts / node resource exhaustion for these unauthenticated query endpoints.

  private List<AssetIssueCapsule> getAssetIssuesPaginated(List<AssetIssueCapsule> assetIssueList,
      long offset, long limit) {
    if (limit < 0 || offset < 0) {
      return null;
    }

    if (assetIssueList.size() <= offset) {
      return null;
    }
    assetIssueList.sort((o1, o2) -> {
      if (o1.getName() != o2.getName()) {
        return o1.getName().toStringUtf8().compareTo(o2.getName().toStringUtf8());
      }
      return Long.compare(o1.getOrder(), o2.getOrder());
    });
    limit = limit > ASSET_ISSUE_COUNT_LIMIT_MAX ? ASSET_ISSUE_COUNT_LIMIT_MAX : limit;
    long end = offset + limit;
    end = end > assetIssueList.size() ? assetIssueList.size() : end;
    return assetIssueList.subList((int) offset, (int) end);
  }

  public List<AssetIssueCapsule> getAssetIssuesPaginated(long offset, long limit) {
