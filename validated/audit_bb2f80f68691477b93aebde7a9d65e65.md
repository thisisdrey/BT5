### Title
Non-hardened TRC10 Bancor exchange math permits pool-draining rounding exploitation and permanent partial fund lockup - ([File: actuator/src/main/java/org/tron/core/capsule/ExchangeCapsule.java])

### Summary
`ExchangeCapsule.transaction()`, invoked by `ExchangeTransactionActuator.execute()`, selects between a legacy `ExchangeProcessor` (floating/BigDecimal-based, unchecked) and a `SafeExchangeProcessor` ("hardened") implementation purely based on the `hardenedCalc` flag returned by `allowHarden()`, which is gated by the on-chain `AllowHardenExchangeCalculation` proposal parameter. [1](#0-0)  When this parameter is not enabled (its non-default/legacy state), all pool balance updates use unchecked arithmetic and a `Processor` that is not proven safe against rounding error, with no floor check preventing a token balance from being driven to (or effectively locked near) zero. [2](#0-1)  The companion `ExchangeWithdrawActuator` has an equivalent split: a "hardened" `BigDecimal` rounding check and a legacy path that validates precision using **double** arithmetic (`remainder / anotherTokenQuant > 0.0001`), which is a well-known source of floating-point precision drift and can pass validation for values that are not actually precise. [3](#0-2) 

### Finding Description
TRON's TRC10 Bancor-formula exchange (`ExchangeTransactionActuator`, `ExchangeWithdrawActuator`, `ExchangeInjectActuator`) is a decentralized token-swap AMM, directly reachable by any account via a signed `ExchangeTransactionContract`/`ExchangeWithdrawContract` transaction, or via `wallet/exchangetransaction` / `wallet/exchangewithdraw` HTTP-RPC endpoints. [4](#0-3) 

`ExchangeTransactionActuator.execute()` calls `exchangeCapsule.transaction(tokenID, tokenQuant, dynamicStore.allowStrictMath(), allowHarden())` to compute the swap output and update both pool reserves in one step. [5](#0-4)  Inside `transaction()`, when `hardenedCalc` is `false` (the legacy/default-compatible code path still present and selectable via the chain parameter), the new balances are computed with plain `long` arithmetic (`firstTokenBalance + sellTokenQuant`, `secondTokenBalance - buyTokenQuant`) with **no negative-balance check**, unlike the hardened branch which explicitly throws `ContractValidateException` if either resulting balance would go negative. [6](#0-5)  The tests in `ExchangeProcessorTest` explicitly demonstrate the hardened processor is needed to prevent overshoot/divide-by-zero classes of failures (`testSafeProcessorDivByZeroThrows`, `testSafeProcessorNoOvershootForTypicalInputs`), which is direct evidence that the non-hardened legacy processor is vulnerable to exactly these classes of arithmetic errors. [7](#0-6) 

Separately, `ExchangeWithdrawActuator.doValidate()` performs the "not precise enough" sanity check using native Java `double` division and `doubleValue()` conversion in the legacy branch, rather than exact `BigDecimal`/`BigInteger` arithmetic used in the hardened branch. [3](#0-2)  Floating-point division is not exact for most rational token ratios, so this check can systematically pass (or fail) incorrectly compared to the exact integer computation later performed in `execute()` using `BigInteger`. [8](#0-7)  Both actuators additionally treat `firstTokenBalance == 0 || secondTokenBalance == 0` as "the exchange has been closed" and permanently reject all further trades/withdrawals/injections for that pool, so once rounding-driven drift or an unguarded transaction drives either side of a pool to (or effectively to) zero, all counter-party funds still recorded in that pool become permanently unreachable through any actuator path. [9](#0-8) 

This is analogous to the PercentFinance incident: a fork of an AMM/lending market whose internal accounting (interest/exchange-rate math) could drift or divide unsafely, permanently freezing user funds in specific markets while the protocol could only halt further operations rather than recover the funds.

### Impact Explanation
If the `AllowHardenExchangeCalculation` proposal has not been activated by the super representatives (its pre-hardening/legacy default), any unprivileged account holding TRC10 tokens can repeatedly submit small `ExchangeTransactionContract`/`ExchangeWithdrawContract` transactions against a target Bancor pool. Because the legacy path lacks the hardened processor's negative-balance guard and uses inexact double-based precision checks, an attacker can (a) extract more value from a pool than the exact Bancor formula would allow due to rounding drift accumulated over many small trades, and/or (b) drive one side of the pool's balance to zero, which permanently disables further trading/withdrawal for that exchange pair per the `firstTokenBalance == 0 || secondTokenBalance == 0` guard — locking any remaining counter-token liquidity in the pool forever, with no actuator or RPC path to recover it. This is a direct, unauthorized value-extraction and fund-freezing vector reachable purely by broadcasting signed transactions.

### Likelihood Explanation
Likelihood is High: no special privileges are required beyond holding a small amount of TRX/TRC10 tokens and knowing an active exchange/pair id (publicly queryable via `GetMarketPairList`/`GetExchangeList`). The vulnerable legacy math path is reachable any time the chain-wide `AllowHardenExchangeCalculation` parameter is not enabled, and the actuator code explicitly retains and selects the unguarded/double-based branch at runtime based on that flag rather than removing it.

### Recommendation
- Make hardened (checked, exact-arithmetic) exchange math (`SafeExchangeProcessor`, `BigDecimal`/`BigInteger` precision checks) the only code path in `ExchangeCapsule.transaction()`, `ExchangeWithdrawActuator`, and `ExchangeTransactionActuator`, removing the legacy unchecked/double-based branches entirely rather than gating them behind a proposal parameter.
- Add explicit negative/zero-balance invariant checks in the legacy `Processor.exchange()` implementation independent of the `hardenedCalc` flag.
- Replace the double-based "Not precise enough" check in `ExchangeWithdrawActuator.doValidate()` with the exact `BigDecimal` computation used in the hardened branch unconditionally.
- Consider adding a minimum-reserve floor (rather than allowing a pool side to reach exactly `0`) to avoid abrupt, permanent lockup of remaining liquidity.

### Proof of Concept
1. Query an active `Exchange` pool (via `GetMarketPairList`) whose `AllowHardenExchangeCalculation` proposal is inactive.
2. Repeatedly broadcast `ExchangeTransactionContract` transactions with small `quant` values chosen to exploit the legacy `ExchangeProcessor`'s floating/rounding behavior (as demonstrated to be unsafe by `ExchangeProcessorTest.testSafeProcessorDivByZeroThrows` and `testSafeProcessorNoOvershootForTypicalInputs`, which show the *hardened* processor prevents cases where the unguarded one would not). [7](#0-6) 
3. Continue until one side of `Exchange.firstTokenBalance`/`secondTokenBalance` reaches `0`.
4. Attempt any further `ExchangeWithdrawContract`/`ExchangeTransactionContract` on the same `exchange_id`; observe both actuators unconditionally reject with `"Token balance in exchange is equal with 0, the exchange has been closed"`, permanently stranding the counter-party token balance recorded on-chain for that pool. [9](#0-8)
