### Title
Stale ReceivedData/PostponedReceiptId/PendingDataCount/PostponedReceipt entries survive `DeleteAccount`, letting a later-registered account silently inherit and execute an attacker-crafted postponed receipt - ([File: core/store/src/utils/mod.rs])

### Summary
`remove_account` (`core/store/src/utils/mod.rs:505-575`), invoked from `action_delete_account` (`runtime/runtime/src/actions.rs:371`), only clears `Account`, `ContractCode`, `AccessKey`/gas-key nonces, and `ContractData` trie entries for the deleted account. It never removes `ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, or `PostponedReceipt` entries keyed by that `account_id`. Because these keys are namespaced purely by the reusable `AccountId` string and not by any per-instance identifier, a deleted-and-later-recreated account (or an account recreated by a completely different party once the name becomes available again) can inherit dangling receipt-matching state left behind by the original account and have it resolved against the new account instance.

### Finding Description
`process_action_receipt` (`runtime/runtime/src/lib.rs:1593-1658`) stores, for an `ActionReceipt` with unmet `input_data_ids`, a `PendingDataCount{receiver_id, receipt_id}`, one `PostponedReceiptId{receiver_id, data_id}` per missing dependency, and the receipt itself under `PostponedReceipt{receiver_id, receipt_id}`.

`process_receipt`'s `Data` branch (`runtime/runtime/src/lib.rs:1386-1473`) writes `ReceivedData{receiver_id, data_id}` and, if a matching `PostponedReceiptId` exists, decrements `PendingDataCount`; only when it hits zero does it delete `PostponedReceipt` and execute it.

If account `X` (attacker-owned) has an action receipt postponed on two dependencies `data_id_1` (fast) and `data_id_2` (deliberately slow/cross-shard, timing controlled by the attacker), and the attacker resolves `data_id_1` first, then deletes `X` via `DeleteAccountAction`, `action_delete_account` → `remove_account` (`runtime/runtime/src/actions.rs:371`, `core/store/src/utils/mod.rs:505-575`) removes the `Account` record but leaves `ReceivedData{X,data_id_1}`, `PostponedReceiptId{X,data_id_2}`, `PendingDataCount{X,receipt_id}=1`, and `PostponedReceipt{X,receipt_id}` in the trie untouched.

`X` can then be recreated — either by the attacker itself, or, for sufficiently long top-level names, by *any other account* since `action_create_account` (`runtime/runtime/src/actions.rs:167-210`) only restricts short top-level names to the registrar; longer top-level names, once freed by deletion, can be registered by anybody. When the attacker later chooses to deliver the second `DataReceipt` for `data_id_2` (they control when the slow dependency resolves), `process_receipt` finds the surviving `PostponedReceiptId{X,data_id_2}` and `PendingDataCount{X,receipt_id}`, decrements to zero, fetches and executes the still-present `PostponedReceipt`, whose actions were fully determined by the attacker at receipt-creation time — now applied against the new account instance of `X`, which is not the account that was originally addressed. No re-authorization occurs because postponed action receipts are trusted as already-authorized when resumed; only the trie-key namespace ties them to `X`, and that namespace was never invalidated at deletion.

### Impact Explanation
This breaks the invariant that a receipt resolves exactly once against the account instance it was actually addressed to. Because the postponed receipt's action list is attacker-controlled (from when it originally created the receipt on its own contract), and it later executes unauthenticated against whatever account currently owns the recycled name, this is an authorization-escalation vector: an unrelated victim who registers the freed account name can have attacker-chosen actions executed against their fresh account (e.g. state-mutating actions), and/or stale `ReceivedData` from the deleted predecessor is silently consumed as if it belonged to the new account, violating determinism/value-conservation between receipt and receiver. This falls under "authorization escalation across accounts or promises."

### Likelihood Explanation
The attacker needs only: (1) ownership of `X` and the ability to deploy a contract issuing a two-dependency `promise_and`, (2) control over the timing of the second, slow dependency's resolution (trivial — it's their own promise chain), and (3) either self-recreation of `X` or waiting for a third party to register the freed name (feasible for sufficiently long top-level names, which any predecessor can create per `action_create_account`). All steps are ordinary transactions available to any unprivileged account; no validator/node access is required. The attack is repeatable.

### Recommendation
Extend `remove_account` (`core/store/src/utils/mod.rs`) to also purge, for the account being deleted, all `PendingDataCount`, `PostponedReceiptId`, `PostponedReceipt`, and `ReceivedData` trie entries keyed by that `account_id` (via prefix iteration similar to the existing access-key/contract-data cleanup), so no receipt-matching bookkeeping outlives the account instance it was created for.

### Proof of Concept
Integration/unit test in `runtime/runtime/src/tests/apply.rs`, following the pattern of `test_promise_input_size_limit_exceeded_fails_and_cleans_up` (`runtime/runtime/src/tests/apply.rs:5038`):
1. Apply an `ActionReceipt` to account `alice` with `input_data_ids = [data_id_1, data_id_2]` so it is postponed (`PendingDataCount{alice,receipt_id}=2`).
2. Apply a `DataReceipt` for `data_id_1` targeting `alice`, decrementing `PendingDataCount` to 1 and writing `ReceivedData{alice,data_id_1}`.
3. Apply a `DeleteAccountAction` receipt for `alice`.
4. Assert (this should fail today, demonstrating the bug) that `get_postponed_receipt`, `get_received_data`, and the `PendingDataCount`/`PostponedReceiptId` entries for `alice` are `None`/absent immediately after step 3 — mirroring the assertions at `runtime/runtime/src/tests/apply.rs:5093-5095`.
5. Recreate `alice` via `CreateAccountAction`, then apply the `DataReceipt` for `data_id_2`; assert that the previously postponed receipt is *not* executed against the new account (expected fix behavior), whereas on the current code it executes, proving the vulnerability. /// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
