### Title
Inconsistent "available-to-delegate" balance calculation between transaction-path and TVM-precompile-path resource delegation - (File: `actuator/src/main/java/org/tron/core/actuator/DelegateResourceActuator.java`, `actuator/src/main/java/org/tron/core/vm/nativecontract/DelegateResourceProcessor.java`)

### Summary
Two independent code paths enforce the same invariant — "the amount of BANDWIDTH/ENERGY balance an account may delegate to another account must not exceed its unused `FrozenV2` balance" — using different formulas, exactly analogous to the Yearn `_creditAvailable`/`_debtOutstanding` mismatch. A plain `DelegateResourceContract` transaction, processed by `DelegateResourceActuator.validate()`, pads the projected bandwidth usage with `TransactionUtil.estimateConsumeBandWidthSize(...)` when the transaction is itself a bandwidth-consuming "create" transaction. The TVM native/precompile path, `DelegateResourceProcessor.validate()`, invoked when a smart contract calls the delegate-resource native contract, omits this padding entirely. Because the same underlying invariant is checked with two different formulas, a contract-triggered delegation can pass validation with a `delegateBalance` that a functionally equivalent direct transaction would reject.

Because the actuator path inflates `accountNetUsage` (hence `v2NetUsage`) when the wrapping transaction is itself a "create" transaction (i.e., reserves bandwidth for the very transaction that is executing the delegate), it produces a strictly smaller "available to delegate" ceiling than the TVM precompile path for the same account state. A malicious contract can therefore delegate an amount of `FrozenV2` balance to a receiver that a direct-transaction delegate call to the same account state would reject, because it exploits the fact that the precompile path never accounts for the executing transaction's own resource consumption. This is a "two code paths compute the same debt/credit ceiling differently" flaw, structurally identical to the reported Yearn `_creditAvailable` vs. `_debtOutstanding` divergence.

### Impact Explanation
The impact is resource-accounting drift: an account could get more `AcquiredDelegatedFrozenV2Balance` credited to a receiver, or delegate more than its true safety margin (given imminent bandwidth consumption from the transaction itself), than the direct-transaction path would ever allow. In the worst case this can leave the owner's own account under-resourced relative to what its `FrozenV2` balance nominally still backs (an over-commitment / "unbacked" resource-delegation analog), since the two enforcement paths diverge on how conservatively they estimate "available balance." This does not directly move TRX, but it produces an inconsistent, exploitable ceiling for resource delegation reachable purely by deploying/calling a contract — matching the "unbacked balance" class named in the validation rules.

### Likelihood Explanation
Medium. The divergent path is reachable by any address that can deploy a contract and trigger the delegate-resource native contract (an unprivileged, permissionless action). The actual exploitable margin is bounded by `TransactionUtil.estimateConsumeBandWidthSize(...)`, so its magnitude per call is small, but it is deterministically and repeatably reachable, and the discrepancy is a genuine logic bug (not a mocked/dev-only path) present in production actuator/TVM code.

### Recommendation
Unify the "available to delegate" calculation into a single shared function used by both `DelegateResourceActuator.validate()` and `DelegateResourceProcessor.validate()`, so the self-transaction bandwidth reservation (`TransactionUtil.estimateConsumeBandWidthSize`) is either always applied or explicitly and consciously omitted for both entry points, with the same total-vault/global-state view. Document the intended semantics of "available FrozenV2 balance for delegation" so that all enforcement points (transaction actuator, TVM native processor, and the read-only `Wallet.calcCanDelegatedBandWidthMaxSize`/`calcCanDelegatedEnergyMaxSize` API used for `getCanDelegatedMaxSize`) agree exactly.

### Proof of Concept
1. An account `Owner` freezes TRX for bandwidth (`FrozenV2BalanceForBandwidth`) and has an existing `NetUsage` such that, per `DelegateResourceActuator.validate()`'s formula (which adds `estimateConsumeBandWidthSize` when `isTransactionCreate()`), the maximum delegatable balance is `X`.
2. `Owner` deploys/uses a smart contract that invokes the TVM native `delegateResource` precompile with `delegateBalance = X + ε` (still within `FrozenV2BalanceForBandwidth - v2NetUsage` as computed by `DelegateResourceProcessor.validate()`, since that path never adds `estimateConsumeBandWidthSize`).
3. `DelegateResourceProcessor.validate()` accepts the call and `DelegateResourceProcessor.execute()` commits `X + ε` bandwidth to the receiver via `receiverCapsule.addAcquiredDelegatedFrozenV2BalanceForBandwidth(delegateBalance)`, an amount that a functionally identical direct `DelegateResourceContract` transaction from `Owner` would have rejected in `DelegateResourceActuator.validate()`.
4. This demonstrates the same account state yields two different "credit/available balance" answers depending on which enforcement code path is used, reproducing the reported bug class.

  public static long getV2NetUsage(AccountCapsule ownerCapsule, long netUsage, boolean
      disableJavaLangMath) {
    long v2NetUsage= netUsage
        - ownerCapsule.getFrozenBalance()
        - ownerCapsule.getAcquiredDelegatedFrozenBalanceForBandwidth()
        - ownerCapsule.getAcquiredDelegatedFrozenV2BalanceForBandwidth();
    return max(0, v2NetUsage, disableJavaLangMath);
  }

  public static long getV2EnergyUsage(AccountCapsule ownerCapsule, long energyUsage, boolean
      disableJavaLangMath) {
    long v2EnergyUsage= energyUsage
          - ownerCapsule.getEnergyFrozenBalance()
          - ownerCapsule.getAcquiredDelegatedFrozenBalanceForEnergy()
          - ownerCapsule.getAcquiredDelegatedFrozenV2BalanceForEnergy();
    return max(0, v2EnergyUsage, disableJavaLangMath);
  }
