Audit Report

## Title
`ERC20Transactor` withdraw/deposit performs unconditional ERC20 `transfer` without a zero-amount guard, letting a zero-value-revert token abort otherwise-valid XCM programs - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `ERC20Transactor::deposit_asset_with_surplus` build and dispatch an `IERC20::transferCall` with `value: EU256::from(amount)` for whatever `amount` `Matcher::matches_fungibles` resolves from the XCM asset, with no `amount > 0` check before the external call. This mirrors the pattern that Snowbridge's XCM converters explicitly guard against with `ensure!(amount > 0, ZeroAssetTransfer)`, and which was already recognized as a real bug class elsewhere in this codebase (see `prdoc/stable2603/pr_11389.prdoc`, fixing an unconditional zero-amount `AssetsInHolding` entry from `SwapFirstAssetTrader::buy_weight`).

## Finding Description
Both entry points call `Matcher::matches_fungibles` to extract `(asset_id, amount)` and then unconditionally construct and dispatch `IERC20::transferCall { .., value: EU256::from(amount) }` via `pallet_revive::Pallet::<T>::bare_call`, with no check that `amount != 0`: [1](#0-0) [2](#0-1) 

If the target ERC20 contract's `transfer` implementation reverts on a zero-value transfer, `bare_call`'s result will have `did_revert() == true`, and the transactor returns `Err(XcmError::FailedToTransactAsset("ERC20 contract reverted"))` for withdraw, or `Err((what, XcmError::FailedToTransactAsset("ERC20 contract reverted")))` for deposit: [3](#0-2) [4](#0-3) 

Comparable existing code in the repo does guard against exactly this: Snowbridge's v1/v2 XCM converters check `ensure!(amount > 0, ZeroAssetTransfer)` before constructing outbound commands. This confirms zero-amount fungible XCM items are a recognized, real-world condition that other transactor-adjacent code in this repo explicitly defends against, and that `ERC20Transactor` lacks an equivalent guard.

However, I was unable to fully verify within this session whether a zero-amount `Fungible(0)` asset item can actually reach `ERC20Transactor::withdraw_asset_with_surplus`/`deposit_asset_with_surplus` from an unprivileged, non-governance XCM execution path on Asset Hub Westend. Specifically:
- I confirmed `ERC20Transactor` is referenced in `cumulus/parachains/runtimes/assets/asset-hub-westend/src/xcm_config.rs`, but did not fully trace the concrete `Matcher` type used there and whether it or the surrounding `AssetTransactors`/executor tuple filters out zero-amount items before dispatch.
- I did not fully trace the XCM executor's `WithdrawAsset`/`DepositAsset`/`InitiateTransfer` instruction handlers in `polkadot/xcm/xcm-executor/src/lib.rs` to determine whether they pass through a `Fungible(0)` item to `TransactAsset::withdraw_asset_with_surplus`/`deposit_asset_with_surplus` unfiltered, or whether upstream logic (e.g., `AssetsInHolding` accounting, fee-payment rounding, or barrier/filter logic) would prevent a zero-amount item from ever reaching this specific transactor in practice.

## Impact Explanation
If a zero-amount fungible item for an ERC20-backed asset can reach this transactor from unprivileged XCM execution, the resulting `Err(XcmError::FailedToTransactAsset(..))` aborts the surrounding XCM instruction. In a multi-asset `WithdrawAsset`/`InitiateTransfer`/`DepositAsset` sequence, this could cause other, legitimately-valued assets processed in the same instruction to fail atomic settlement, risking `AssetsTrapped` and asset lock, which aligns with the "permanent user-fund or bridge-state lock" impact class and the "message queues... and settlement state must only advance after decode, dispatch, execution, and settlement succeed atomically" pivot — but only if the precondition (a zero-amount item reaching this exact code path) actually holds.

## Likelihood Explanation
Deploying an ERC20 contract via `pallet-revive` that reverts on `transfer(_, 0)` is fully within an attacker's control and requires no privileged role. However, whether such a contract can be registered as a `Matcher`-recognized XCM fungible asset on Asset Hub, and whether an unprivileged XCM sender can actually cause a `Fungible(0)` item for that asset to reach `withdraw_asset_with_surplus`/`deposit_asset_with_surplus` (as opposed to being filtered, deduplicated, or never constructed by the executor/asset registration flow), was not confirmed. The claim itself explicitly acknowledges this gap ("The exact conditions under which a zero-amount item reaches this specific transactor... were not fully verified"), and my own investigation could not close that gap either.

## Recommendation
Add an explicit `amount == 0` guard at the top of both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, mirroring `ensure!(amount > 0, ZeroAssetTransfer)` in the Snowbridge converters (`bridges/snowbridge/primitives/outbound-queue/src/v1/converter/mod.rs`, `bridges/snowbridge/primitives/outbound-queue/src/v2/converter/convert.rs`) and the recent fix pattern in `prdoc/stable2603/pr_11389.prdoc`, so a zero-amount transfer is either treated as a no-op success or fails deterministically without invoking the external contract, independent of the target ERC20's implementation quirks.

## Proof of Concept
Not independently verified. The claim's proposed PoC (deploy a zero-value-reverting ERC20 via `pallet-revive`, register it as a `Matcher`-recognized fungible asset, and craft/trigger an XCM program presenting a `Fungible(0)` entry for it via `WithdrawAsset`/`InitiateTransfer`/`DepositAsset`) is a plausible reproduction path but requires confirming, via a Rust integration test against `AssetHubWestendRuntime`'s actual `Matcher`/`AssetTransactors` config and the XCM executor's instruction handling, that a zero-amount item for this asset class can actually be constructed by an unprivileged sender and routed to `ERC20Transactor` — this step was not completed in this session.
