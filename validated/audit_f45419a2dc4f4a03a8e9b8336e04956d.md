### Title
Malicious Mach-O object file triggers out-of-bounds slice panic via unvalidated section address arithmetic in `loadmacho.Load` - (File: src/cmd/link/internal/loadmacho/ldmacho.go)

### Summary
`loadmacho.Load` parses Mach-O segment/section headers from an untrusted host object file (e.g., a `.syso` file bundled in a Go module or produced by cgo) and computes `dat[sect.addr-c.seg.vmaddr:][:sect.size]` without validating that `sect.addr >= c.seg.vmaddr` or that `sect.addr-c.seg.vmaddr+sect.size` fits within `dat`. This mirrors the QEMU `rom_copy()` bug class: two attacker-controlled address/size values are combined into a copy/slice operation without checking their relationship, leading to an invalid memory access.

### Finding Description
Attacker input is a crafted Mach-O object file (`.syso`) placed in a Go module/package that is linked by `go build`. `loadmacho.Load` reads segment command fields `vmaddr`/`vmsize`/`fileoff`/`filesz` and per-section fields `addr`/`size` via `unpackcmd` [1](#0-0) , with no cross-field validation of `addr` against `vmaddr`. The only bounds check performed is on the segment's file offset/size against the object length [2](#0-1) . The sink is:
```
bld.SetData(dat[sect.addr-c.seg.vmaddr:][:sect.size])
``` [3](#0-2)  If `sect.addr < c.seg.vmaddr`, the `uint64` subtraction underflows to a huge value, producing a slice with an enormous negative-equivalent starting index into `dat` (a `[]byte` slice loaded via `f.Slice(uint64(c.seg.filesz))` [4](#0-3) ), causing a runtime "slice bounds out of range" panic. Even when `sect.addr >= vmaddr`, no check ensures `(sect.addr-vmaddr)+sect.size <= len(dat)`, so an oversized `sect.size` also panics.

### Impact Explanation
This crashes the `go build`/linker process (denial of service against the build) when linking a package containing a malicious host object file. Under Go's security policy this is a parser-panic-on-malicious-input class of issue in a build-time tool (`cmd/link`), which the report's own rules explicitly note "can qualify." It does not achieve code execution beyond what `go build`'s Security Decisions already accept (host object/tool input is not "source" in the same sense as Go source code, but it is still untrusted external input processed without bound checks). This would likely be a PUBLIC-track, low-severity crash/DoS finding rather than URGENT.

### Likelihood Explanation
Reachable whenever a victim runs `go build`/`go install` on a module that supplies a `.syso` (or other host object) file consumed by the linker's Mach-O path — a normal, unprivileged build workflow with a malicious dependency, not requiring any elevated trust.

### Recommendation
In `loadmacho.Load`, before calling `bld.SetData(...)`, validate `sect.addr >= c.seg.vmaddr` and `sect.addr-c.seg.vmaddr+sect.size <= uint64(len(dat))` (and that `sect.size` itself doesn't overflow this arithmetic), returning a load error (as done elsewhere in this file via `errorf`) instead of panicking.
