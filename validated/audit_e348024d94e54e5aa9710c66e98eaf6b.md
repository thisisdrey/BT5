## Title
Front-running griefing of `MarketSellAssetContract` order matching via `MAX_MATCH_NUM` order-book flooding - ([File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java])

### Summary
`MarketSellAssetActuator` lets any account place a TRC10/TRX exchange order that is immediately matched against the resting order book for the opposite pair. An attacker can front-run a victim's legitimate sell order by placing many small maker orders at a matching price for the same pair. When the victim's order is processed, `matchOrder()` iterates the maker order book and throws once more than `MAX_MATCH_NUM` (20) maker orders are consumed in a single match, aborting the victim's transaction after fees have already been deducted.

### Finding Description
`matchOrder()` walks the maker order book for the opposite pair and matches orders one at a time; if the taker order needs to match against more than `MAX_MATCH_NUM` maker orders it throws `ContractValidateException("Too many matches...")` from inside `execute()`: [1](#0-0) 

This check is only evaluated during `execute()`, after the actuator has already:
1. Deducted the fixed `MarketSellFee` from the owner's balance and burned/sent it to the blackhole address,
2. Transferred/locked the sell-side balance or token out of the owner's account,
3. Created and persisted the order via `createAndSaveOrder()`. [2](#0-1) 

Because the number of maker orders that a taker will be matched against depends entirely on the *current* state of the opposing order book at execution time, an attacker who front-runs a soon-to-be-broadcast large sell order can flood the opposing side of the book with more than `MAX_MATCH_NUM` cheap, small resting orders at a matching price (each individually valid, subject only to the `MAX_ACTIVE_ORDER_NUM` per-account cap checked in `validate()`): [3](#0-2) 

When the victim's transaction is finally packed and executed, `matchOrder()` will exceed `MAX_MATCH_NUM` while walking through the flooded maker orders and throw, causing `execute()` to fail via `ContractExeException`. This exactly mirrors the reported bug class: an attacker uses low-cost, front-run state-mutating calls into the *same* interaction surface (the order book keyed by token pair/price) to force a legitimate, later-arriving transaction from the same surface to revert.

### Impact Explanation
Every revert of `MarketSellAssetActuator.execute()` still results in the block producer including the transaction (fee deduction and side effects up to the point of the exception happen inside a revoking session that gets rolled back, but the transaction is still consumed from the sender's account in terms of nonce/ordering and bandwidth/energy is spent attempting it). More importantly, this is a griefing primitive: an adversary can reliably and cheaply deny a specific counterparty's ability to execute market sell orders against a specific token pair by continuously maintaining more than `MAX_MATCH_NUM` cheap resting maker orders at the matching price, forcing repeated transaction failures for the victim. This is a Medium-severity availability/griefing issue against the on-chain decentralized exchange feature.

### Likelihood Explanation
Any account can call `MarketSellAssetContract` (this is a normal, unprivileged actuator reachable by any signed transaction) and place up to `MAX_ACTIVE_ORDER_NUM` (100) small orders. The `MAX_MATCH_NUM` limit is only 20, meaning as few as 21 cheap orders at the correct pair/price are needed to grief a targeted victim's larger order. Since order books and prices are public on-chain data, an attacker can observe pending transactions and front-run with the necessary maker orders before the victim's transaction is packed into a block.

### Recommendation
Move quantity/order-count feasibility checks that can be affected by concurrent order-book state (i.e., predict/limit the number of maker matches) into `validate()` where possible, or make `matchOrder()` degrade gracefully (partially fill and leave the remainder on the book) instead of throwing and aborting the whole transaction when `MAX_MATCH_NUM` is exceeded, so that a state change caused by a third party cannot cause an otherwise valid transaction to fail outright.

### Proof of Concept
1. Attacker observes a pending `MarketSellAssetContract` transaction from victim V selling `sellTokenQuantity` of token A for token B.
2. Attacker rapidly submits 21+ small `MarketSellAssetContract` orders selling token B for token A at a price that will match V's order (each order is independently valid and within `MAX_ACTIVE_ORDER_NUM`).
3. These orders are confirmed first (front-run), populating the maker order book for the A/B pair with more than `MAX_MATCH_NUM` price-matching entries via `saveRemainOrder()`. [4](#0-3) 

4. V's transaction executes, `matchOrder()` walks more than `MAX_MATCH_NUM` maker orders and throws `ContractValidateException("Too many matches. MAX_MATCH_NUM = 20")`, causing `execute()` to fail and V's trade to not go through despite having paid to attempt it.
