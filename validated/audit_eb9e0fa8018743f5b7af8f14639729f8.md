## Confirmed: `get_u2le`/`get_u4le` advance the pointer as a side effect (no bounds check)

`third_party/ijar/common.h` shows all `get_u*` helpers take `const u1*&p` and advance `p` by the field width as a side effect, with **no bounds checking whatsoever** — they trust the caller to have validated remaining length beforehand. [1](#0-0) 

### Title
Out-of-bounds read in ijar's `InputZipFile::ProcessCentralDirEntry` extra-field loop due to unchecked, attacker-controlled `data_size` - (File: third_party/ijar/zip.cc)

### Summary
`ProcessCentralDirEntry` parses a ZIP central directory entry directly from the mmap'd input buffer and then walks the entry's "extra fields" using a `while (extra_p != p)` loop, advancing `extra_p` by an attacker-controlled 16-bit `data_size` on each iteration, with no check that `extra_p` stays within `p` (the previously-computed boundary) or within the mapped file at all. [2](#0-1) [3](#0-2) 

### Finding Description
Unlike `ProcessLocalFileEntry`, which calls `EnsureRemaining()` before trusting `file_name_length_`/`extra_field_length_` against the mapped file bounds [4](#0-3) ,
`ProcessCentralDirEntry` performs **no** `EnsureRemaining` calls at all before reading `file_name_length`, `extra_field_length`, `file_comment_length`, and before iterating the extra-field records. [5](#0-4) 

The extra-field loop is the closest analog to the Xen bug class: it assumes each "extra field" record is well-formed and that summing `data_size` values across iterations will land exactly on `p` (the end of the extra-field region, itself derived from an unchecked `extra_field_length`). A malicious central directory entry can declare a `data_size` for an extra field that causes `extra_p` to jump past `p` without ever equaling it, or `extra_field_length`/`file_name_length` values that point far beyond the actual mapped ZIP central directory / EOCD region — exactly the "extreme fragmentation vs. assumed-safe header region" pattern in the Xen advisory, but here manifesting as reads walking off the end of the mmap'd input file (`zipdata_in_`), since `memcpy(filename, p, len)` and the subsequent `get_u2le`/`get_u4le` calls dereference memory with zero bounds validation. [6](#0-5) 

This code is compiled into the `ijar` tool, which Bazel invokes to build interface/header jars from arbitrary input JARs (including JARs originating from external repositories fetched over HTTP/Maven, i.e., attacker-controllable content when unpinned or when only file-level checksums are verified but internal structure is never re-validated by ijar). A checksum on the whole archive does not protect against structural corruption inside a compressed member's central directory metadata being crafted by a hostile origin server that also satisfies the pinned hash (attacker controls the exact bytes it publishes, so it can craft a byte-for-byte file matching any digest it advertises for its own malicious payload).

### Impact Explanation
An out-of-bounds read past the end of the memory-mapped ZIP file can cause a crash (segfault reading unmapped pages) — a memory-safety violation in a native (C++) tool that processes untrusted archive bytes during the build. Depending on heap/mmap layout this could also leak adjacent process memory into `filename`/`errmsg` diagnostic buffers that get echoed to build output, though full exploitation for information disclosure/RCE is not established from static review alone.

### Likelihood Explanation
Reachability requires only that `ijar` processes a JAR whose central directory contains a malformed extra field — this happens automatically whenever Bazel builds an interface jar (`java_import`, `java_library` `deps`, etc.) from any JAR obtained from an external, potentially malicious source (e.g., unpinned `http_jar`, malicious Maven artifact version). No local sandbox bypass or credential access is needed — the attacker just needs to control the bytes of a jar consumed by the build.

### Recommendation
Add `EnsureRemaining()` checks in `ProcessCentralDirEntry` before reading `file_name_length`, `extra_field_length`, `file_comment_length`, and inside the extra-field loop validate that `extra_p + 4 <= p` before reading `header_id`/`data_size`, and that `extra_p + data_size <= p` before advancing, mirroring the bounds discipline already used in `ProcessLocalFileEntry` and in `singlejar`'s `ExtraField::find` (which does perform these checks) [7](#0-6) .

### Proof of Concept
A concrete PoC could not be fully constructed/verified within the available tool budget (no terminal/build access in this ask-only session). The suggested reproduction path: craft a ZIP/JAR whose single central directory entry declares `extra_field_length` covering one “extra field” record whose 16-bit `data_size` is larger than the remaining declared extra-field region (analogous to `CreateZipWithMalformedExtraField` already used in `singlejar`'s test suite for a similar hazard) [8](#0-7) ,
then feed it to the `ijar` binary (or a `BuildIntegrationTestCase`/`src/test/shell/bazel` test building a `java_import` from that malformed jar) and observe a crash or ASan out-of-bounds read report in `ProcessCentralDirEntry`.

---
**Note on confidence**: I traced the code path and confirmed the missing bounds checks via static analysis of `third_party/ijar/zip.cc` and `common.h`, and cross-referenced the disciplined bounds-checking pattern used elsewhere in the codebase (`EnsureRemaining` in `ProcessLocalFileEntry`, `ExtraField::find` in singlejar) as the expected/missing invariant. I was **not** able to execute a build or run a PoC to confirm actual out-of-bounds behavior at runtime (no ASan crash observed), nor could I fully trace whether any earlier caller (e.g., `Open()`/`CalculateOutputLength()`, which I could not fully read before running out of iterations) performs a coarser sanity check on the whole central directory size that might mitigate this. This should be verified with an actual build/ASan run before treating this as a fully confirmed, exploitable vulnerability.

  const std::string filename = "evil.bin";

  // 1. Local File Header (LFH)
  size_t lh_offset = zip_data.size();
  size_t lh_size = sizeof(LH) + filename.size();
  zip_data.resize(lh_offset + lh_size, 0);
  auto* lh = reinterpret_cast<LH*>(&zip_data[lh_offset]);
  lh->signature();
  lh->version(10);
  lh->file_name(filename.data(), filename.size());

  // 2. Extra field payload containing an oversized payload_size

  auto* ef1 = reinterpret_cast<ExtraField*>(ef_buffer);
  ef1->signature(0x000d);
  ef1->payload_size(0);

  ef2->signature(0xdead);
  ef2->payload_size(0xf000);  // Malformed size exceeding extra field buffer

  size_t cdh_offset = zip_data.size();
