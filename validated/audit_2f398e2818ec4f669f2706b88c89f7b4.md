Based on my investigation, the strongest reachable analog to the "module not wired up" bug class in Zest v2 is a missing initialization step in the production deployment/wiring script for the vault contracts.

### Title
Mainnet initialization proposal never calls `initialize` on any vault, leaving vaults susceptible to the classic first-depositor share-inflation attack - (File: mainnet/contracts/proposals/mainnet/v0-init.clar)

### Summary
The `xfeemarket` report describes a class of bug where a subsystem is fully built (keeper, message handlers, guards) but the wiring/initialization script that is supposed to activate it in production omits the step, silently disabling protections. The same bug class is present in Zest v2's mainnet deployment: the single production initialization script wires up assets, egroups, caps, authorization, and interest curves for every vault, but never calls each vault's one-time `initialize` entrypoint, which is the step responsible for seeding minimum liquidity and flipping the `is-initialized`/`ERR-ALREADY-INITIALIZED` guard.

### Finding Description
`mainnet/contracts/proposals/mainnet/v0-init.clar` is the sole mainnet proposal that wires up the protocol: it inserts all assets/vaults into `.v0-assets`, enables collateral/debt flags, sets `.v0-market-vault` implementation, sets vault supply/debt caps, authorizes `.v0-1-market` in every vault, creates all egroups, and configures interest-rate curves [1](#0-0) [2](#0-1) [3](#0-2) .

Nowhere in this file, or anywhere else under `mainnet/contracts/proposals/**`, is the vaults' `initialize` function invoked — a targeted search for `initialize` under that path returned no matches. By contrast, the local-testing equivalent explicitly performs this step for every vault as a required part of protocol setup: `proposal-init-vaults.clar` mints `MINIMUM_LIQUIDITY` to the executor and calls `initialize` on each vault before authorizing the market [4](#0-3) , and the test-suite treats a missing/duplicate `initialize` call as a hard invariant, explicitly checking `ERR-ALREADY-INITIALIZED` and minimum-liquidity totals [5](#0-4) . Each of the six mainnet vault contracts (`v0-vault-stx`, `v0-vault-sbtc`, `v0-vault-ststx`, `v0-vault-usdc`, `v0-vault-usdh`, `v0-vault-ststxbtc`) contains this same `initialize`/`ERR-ALREADY-INITIALIZED`/`MINIMUM-LIQUIDITY` guard logic, confirming it is a required, security-relevant one-time step mirrored across all vaults, not an optional convenience [6](#0-5) .

This is a direct structural analog to the audited `xfeemarket` bug: a fully implemented, security-critical setup routine (minimum-liquidity seeding to defend against share-price manipulation, exactly like a Cosmos module's genesis-init hook) exists in the codebase and is exercised in test/local tooling, but is omitted from the actual production wiring script that goes live.

### Impact Explanation
Vault initialization exists to seed a minimum liquidity/share baseline before real user deposits are accepted, which is the standard defense against the ERC4626-style "first depositor" vault inflation attack: without seeded liquidity, an attacker can deposit a negligible amount to mint the first shares, then directly donate/transfer underlying assets to the vault to inflate the price-per-share, causing subsequent legitimate depositors' shares to round down to zero while the attacker redeems a disproportionate share of the pool. Since `v0-init.clar` authorizes the market, sets caps, and enables egroups for every vault without ever calling `initialize` on them, the mainnet vaults reach a "live" configuration (tradable, authorized, capped) while skipping the one control designed to prevent this class of attack. This is a theft-of-user-funds-at-rest vector, landing squarely in the Critical impact class.

### Likelihood Explanation
Likelihood is high given the deployment script is deterministic and the sole production initialization path found in the repository (`mainnet/contracts/proposals/mainnet/v0-init.clar`) omits the call; any unprivileged user who is first to interact with a freshly-authorized, un-seeded vault can attempt the deposit/donate sequence with no additional privilege required. I was not able to fully confirm from the indexed contents whether `deposit`/`get-price-per-share` paths in the mainnet vault contracts contain an independent runtime check that blocks all deposits until `initialize` is called (which would fully neutralize this specific vector but would instead manifest as the module being entirely non-functional, similar in spirit to the original report). This should be verified directly against the full vault contract source before treating this as conclusively exploitable in production.

### Recommendation
Add the missing `initialize` calls (with the corresponding minimum-liquidity funding step) for every vault (`v0-vault-stx`, `v0-vault-sbtc`, `v0-vault-ststx`, `v0-vault-usdc`, `v0-vault-usdh`, `v0-vault-ststxbtc`) into `mainnet/contracts/proposals/mainnet/v0-init.clar`, mirroring the pattern already proven correct in `local-testing/contracts/proposals/proposal-init-vaults.clar`, before any vault is authorized for the live market.

### Proof of Concept
1. Deploy/execute `mainnet/contracts/proposals/mainnet/v0-init.clar` exactly as written — this authorizes `.v0-1-market` on every vault and sets caps/egroups [7](#0-6) , without any vault ever having `initialize` invoked (confirmed absent via search of `mainnet/contracts/proposals/**`).
2. Compare against the local-testing flow, which requires `initialize` on each vault (with pre-minted minimum liquidity) before authorization is considered safe [8](#0-7) .
3. An attacker who is first to deposit into an un-initialized mainnet vault can mint the first shares, donate underlying tokens directly to the vault contract to inflate share price, then wait for a legitimate depositor to deposit and receive rounded-down (or zero) shares, after which the attacker redeems their shares for a disproportionate amount of the pooled assets — the standard vault-inflation theft pattern that the missing `initialize`/minimum-liquidity step is designed to prevent.

  (begin
    ;; Set vault caps before initialization
    ;; Called directly since we're already in dao-executor's context
    (try! (contract-call? .vault-sbtc set-cap-supply CAP))
    (try! (contract-call? .vault-sbtc set-cap-debt CAP))
    (try! (contract-call? .vault-usdh set-cap-supply CAP))
    (try! (contract-call? .vault-usdh set-cap-debt CAP))
    (try! (contract-call? .vault-usdc set-cap-supply CAP))
    (try! (contract-call? .vault-usdc set-cap-debt CAP))
    (try! (contract-call? .vault-ststx set-cap-supply CAP))
    (try! (contract-call? .vault-ststx set-cap-debt CAP))
    (try! (contract-call? .vault-stx set-cap-supply CAP))
    (try! (contract-call? .vault-stx set-cap-debt CAP))
    
    ;; Initialize vaults (mints minimum liquidity)
    ;; Called directly - dao-executor's with-all-assets-unsafe handles asset transfers
    (try! (as-contract? ((with-all-assets-unsafe))
      (try! (contract-call? .vault-sbtc initialize))
      (try! (contract-call? .vault-usdh initialize))
      (try! (contract-call? .vault-usdc initialize))
      (try! (contract-call? .vault-ststx initialize))
      (try! (contract-call? .vault-stx initialize))
    ))
    
    ;; Authorize market contract
    ;; Called directly since we're already in dao-executor's context
    (try! (contract-call? .vault-sbtc set-authorized-contract .market true))
    (try! (contract-call? .vault-usdh set-authorized-contract .market true))
    (try! (contract-call? .vault-usdc set-authorized-contract .market true))
    (try! (contract-call? .vault-ststx set-authorized-contract .market true))
    (try! (contract-call? .vault-stx set-authorized-contract .market true))
    
    (ok true)))
