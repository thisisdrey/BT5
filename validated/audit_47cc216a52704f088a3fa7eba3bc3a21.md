### Title
Unbounded blocking write in `SidebandWriter.writeBand` under a stalling client enables single-connection resource-exhaustion / progress-starvation DoS - ([File: internal/git/pktline/pktline.go])

### Summary
`SidebandWriter.writeBand` holds `sw.m` (a `sync.Mutex`) for the full duration of the blocking `sw.w.Write` call that pushes pack/progress/error data to the underlying transport. Because the write has no deadline and the mutex is shared across all bands (stdout/stderr/progress), a client that stops reading its receive buffer after starting an upload-pack/receive-pack RPC can cause the write to block indefinitely, holding the lock and pinning open the goroutine and its associated git process/connection for the life of the stalled read.

### Finding Description
`writeBand` is the single write path used by `SidebandWriter.Writer(band)` for all multiplexed bands (`internal/git/pktline/pktline.go:189-210`). It acquires `sw.m.Lock()` before entering the write loop and only releases it via the deferred unlock after the loop (including the blocking `sw.w.Write(sw.buf[:header])` call) completes: [1](#0-0) 

In `internal/gitaly/service/ssh/upload_pack.go`, this writer is built directly on top of the raw sidechannel connection (`counter := &helper.CountingWriter{W: conn}`, `sidebandWriter := pktline.NewSidebandWriter(counter)`), and both `stdout` (pack data) and `stderr` (progress/errors) share the same `SidebandWriter` instance and therefore the same mutex: [2](#0-1) 

An attacker who is an ordinary authenticated Git user can initiate a normal `git-upload-pack`/`git-receive-pack` SSH RPC, request a large pack (e.g., a full clone of a repository they can read), and then simply stop draining the TCP receive window on the client side after the handshake. Once the OS socket buffer and TCP window fill, `conn.Write` inside `writeBand` blocks. Since this happens while `sw.m` is held, any other writer using the same `SidebandWriter` — including the goroutine trying to write git's stderr progress messages — will also block trying to acquire `sw.m`, starving progress/error reporting for the connection. No write deadline is set anywhere in this code path (`SetWriteDeadline` is not called on the sidechannel connection here, nor is `writeBand` context-aware), so the block persists until the underlying connection is closed by some outer mechanism (e.g., gRPC/OS-level keepalive or explicit context cancellation elsewhere in the stack) rather than being bounded by this layer itself.

None of the general Gitaly request-validation layers (`storage.ValidateRelativePath`, `git.ValidateRevision`, request size limits, hook/quarantine checks) apply here, because this is a transport-layer blocking-I/O issue, not an input-validation issue — the attacker input that matters is simply "request enough data and stop reading," which is normal, unprivileged client behavior.

### Impact Explanation
This matches a DoS-of-RPC-handler impact: the server-side goroutine executing `upload-pack`/`receive-pack`, along with the underlying `git` subprocess and file descriptors, remains pinned open for as long as the attacker withholds TCP reads. Repeating this with many parallel connections (each cheap for the attacker, each consuming a server-side git process, goroutine, and socket) can exhaust Gitaly's concurrency/resource limits (worker threads, open FDs, memory buffers), degrading service for other tenants of the same Gitaly node. It does not grant any of the higher-severity capabilities (arbitrary file access, command injection, auth bypass), so this is scoped to resource exhaustion / availability impact only.

### Likelihood Explanation
Preconditions are minimal and consistent with an unprivileged attacker: they need only fetch/clone access to a repository they control or have read access to, and control over their own TCP receive window (achievable with any raw socket client, e.g. a custom SSH client that stops calling `Read` after the negotiation phase). No elevated privileges, secrets, or non-default configuration are required. The attack is trivially repeatable and parallelizable across many connections, limited only by whatever global concurrency/connection limits Gitaly enforces upstream (not visible within this file). Because no write deadline or context-based cancellation is applied at the `pktline`/`SidebandWriter` layer itself, the bound on how long a stalled connection stays open depends entirely on external layers (gRPC keepalive/idle timeouts, OS TCP keepalive, or RPC-level context deadlines) that were not found configured specifically for this write path in the reviewed code.

### Recommendation
Enforce a bounded write deadline on the underlying connection before each `sw.w.Write` call in `writeBand` (e.g., wrap `sw.w` so it supports `SetWriteDeadline`, or thread a `context.Context` through `SidebandWriter` and use a context-aware writer that aborts/returns an error when the deadline elapses or the context is cancelled). This ensures a stalling reader causes the write to fail fast (releasing the mutex and unwinding the RPC handler) rather than blocking indefinitely, and also prevents progress/error bands from being starved by a stuck data band on the same writer.

### Proof of Concept
Illustrative Go-level PoC of the blocking behavior in isolation (no server infra needed to demonstrate the root cause):

```go
func TestSidebandWriter_BlocksIndefinitelyOnSlowReader(t *testing.T) {
    server, client := net.Pipe() // synchronous, unbuffered pipe simulates a stalling TCP peer
    defer server.Close()
    defer client.Close()

    sw := pktline.NewSidebandWriter(server)
    stdout := sw.Writer(stream.BandStdout)
    stderr := sw.Writer(stream.BandStderr)

    done := make(chan struct{})
    go func() {
        // Large payload; net.Pipe write blocks until something reads.
        _, _ = stdout.Write(bytes.Repeat([]byte("x"), 10*pktline.MaxSidebandData))
        close(done)
    }()

    time.Sleep(100 * time.Millisecond) // let stdout writer acquire sw.m and block on Write

    progressDone := make(chan struct{})
    go func() {
        _, _ = stderr.Write([]byte("progress update"))
        close(progressDone)
    }()

    select {
    case <-progressDone:
        t.Fatal("expected stderr band write to be blocked by held mutex, but it completed")
    case <-time.After(500 * time.Millisecond):
        // Expected: stderr writer is still blocked waiting for sw.m, proving
        // progress/error reporting is starved by the stalled data band and
        // there is no deadline unblocking either goroutine.
    }
}
```

At the RPC level, the equivalent PoC is: open an `SSHUploadPackWithSidechannel` connection, send a request for a large pack, and after the sidechannel handshake stop calling `Read` on the client socket while measuring whether the server-side `sshUploadPack` goroutine and its `git upload-pack` subprocess remain alive past any configured RPC timeout, and whether repeating this with N parallel connections exhausts Gitaly's available upload-pack concurrency slots for legitimate clients.

func (sw *SidebandWriter) writeBand(band byte, data []byte) (int, error) {
	sw.m.Lock()
	defer sw.m.Unlock()

	n := 0
	for len(data) > 0 {
		const headerSize = 5

		chunkSize := copy(sw.buf[headerSize:], data)
		header := chunkSize + headerSize
		copy(sw.buf[:4], fmt.Sprintf("%04x", header))
		sw.buf[4] = band

		if _, err := sw.w.Write(sw.buf[:header]); err != nil {
			return n, err
		}
		data = data[chunkSize:]
		n += chunkSize
	}

	return n, nil
}
