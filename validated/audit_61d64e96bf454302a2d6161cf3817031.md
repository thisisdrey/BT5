### Title
Out-of-bound read parsing ZIP central directory entries without bounds checking - (File: `third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` in `third_party/ijar/zip.cc` reads multi-byte fields (sizes, filename length, extra field length, comment length) directly out of the mmap'd input buffer via `get_u4le`/`get_u2le` and advances the cursor `p` accordingly, without ever validating that the declared lengths fit within the actual mapped file size, unlike the sibling function `ProcessLocalFileEntry`, which explicitly calls `EnsureRemaining()` before every field read and before copying `file_name_length_`/`extra_field_length_` bytes.

### Finding Description
`ProcessLocalFileEntry` guards every read with `EnsureRemaining(n, "state")`, which compares the requested read size against `input_file_->Length() - (p - zipdata_in_)` and errors out on premature EOF [1](#0-0) , and it is invoked before reading fixed fields and before advancing past `file_name_length_`/`extra_field_length_` [2](#0-1) .

In contrast, `ProcessCentralDirEntry` reads the signature, skips 16 bytes, then reads `compressed_size`, `uncompressed_size`, `file_name_length`, `extra_field_length`, `file_comment_length`, external attributes and offset — all directly from `p` with no `EnsureRemaining` calls anywhere in the function [3](#0-2) . It then advances `p` by `file_name_length` and by `extra_field_length`, and parses a Zip64 extra field (reading up to 8-byte little-endian integers from `extra`) purely based on attacker-controlled `header_id`/`data_size` values with no bound check against the buffer end [4](#0-3) . Finally it advances `p` by `file_comment_length`, again unchecked [5](#0-4) .

Since `p` is a pointer directly into the `mmap`'d region backing the archive (`zipdata_in_`), and the function is invoked in a loop from `ProcessNext()` for every central-directory record until the signature no longer matches [6](#0-5) , a hostile archive (e.g., a `.jar`/`.zip` fetched via `http_archive`/`http_jar` and subsequently processed by the `ijar` tool to build an interface jar) can supply oversized `file_name_length`, `extra_field_length`, or `file_comment_length` values, or a crafted Zip64 extra-field `data_size`, that cause `p` (and `extra_p`) to run past the end of the mapped file. Any subsequent `get_u2le`/`get_u4le`/`get_u8le` dereference, or the `memcpy` of the filename in the same function, then reads memory beyond the mapped region — this is directly analogous to the `strscpy()` source over-read in the report: an unterminated/unbounded length value taken from untrusted input is trusted to bound a read from a buffer that is not actually that long.

The one truncation-safety check present, `len = min(file_name_length, filename_size-1)` for the `memcpy` into the fixed local `filename[PATH_MAX]` buffer, protects the *destination* against overflow but does nothing to protect the *source* read length against the mapped file's real end when `file_name_length` (or the subsequent `extra_field_length`/`file_comment_length` advances) exceeds the remaining mapped bytes [7](#0-6) .

### Impact Explanation
An out-of-bound read against the mmap'd input file can cause a crash (SIGSEGV/SIGBUS) if the read crosses a page boundary past the mapping, or leak adjacent process memory into `errmsg`/`filename` buffers or into decisions that affect output content, depending on layout. This is a memory-safety violation triggered purely by content the attacker controls (a downloaded/fetched archive), matching the CVE's bug class (over-read of untrusted-length source data) but reachable from network-supplied build inputs rather than a USB device.

### Likelihood Explanation
Central directory records are fully attacker-controlled fields in any ZIP/JAR fetched from an untrusted URL/registry and then processed by the `ijar` tool (used to build Java interface jars from dependency jars). No credentials or local access are needed — an outsider serving a malicious `.jar` at a dependency URL is sufficient to reach this code path, and no checksum verification of the *content of individual header fields* (only, at best, the overall artifact hash) would catch a structurally malformed but hash-matching archive if the attacker controls the whole file being hashed (i.e., first-party publication of a malicious archive that also matches its own declared `sha256`). Likelihood is moderate: it requires the archive to be routed through `ijar`/`third_party/ijar/zip.cc`'s central-directory parsing, and I could not fully confirm from the excerpts examined which specific Bazel-level rule invariably calls into `InputZipFile::ProcessCentralDirEntry` versus other jar-reading code paths (e.g., `singlejar`'s separate `zip_headers.h`/`InputJar` which does perform CDH size validation via `mapped_file_.mapped()` bounds checks, per `NextEntry`) [8](#0-7) .

### Recommendation
Add `EnsureRemaining()` (or equivalent bounds checks against `input_file_->Length()`) calls in `ProcessCentralDirEntry` before reading the fixed-size central directory header fields, before advancing `p` past `file_name_length`, `extra_field_length`, and `file_comment_length`, and before dereferencing each Zip64 extra-field sub-record based on its `data_size`.

### Proof of Concept
A `BuildIntegrationTestCase`/unit test in `third_party/ijar` would construct a minimal ZIP file whose Central Directory Header declares `file_name_length`, `extra_field_length`, or `file_comment_length` (or a Zip64 extra-field `data_size`) far larger than the bytes actually present in the mapped file (e.g., header at the very end of the mapped region with `file_name_length = 0xFFFF` but only a few trailing bytes actually present), then call `ProcessCentralDirEntry`/`ProcessNext` on it and observe an out-of-bounds read (crash under ASan, or a memory-safety sanitizer flag) as opposed to the graceful "Premature end of file" error produced by `ProcessLocalFileEntry`'s `EnsureRemaining` guard.

    size_t remaining = input_file_->Length() - in_offset;
    if (n > remaining) {
      return error("Premature end of file (at offset %zd, state=%s); "

bool InputZipFile::ProcessNext() {
  // Process the next entry in the central directory. Also make sure that the
  // content pointer is in sync.
  u8 compressed, uncompressed;
  u8 offset;
  if (!ProcessCentralDirEntry(central_dir_current_, &compressed, &uncompressed,
                              filename, PATH_MAX, &attr, &offset)) {
    return false;
  }

  // There might be an offset specified in the central directory that does
  // not match the file offset, so always update our pointer.
  p = zipdata_in_ + in_offset_ + offset;

  if (EnsureRemaining(4, "signature") < 0) {
    return false;
  }
  u4 signature = get_u4le(p);
  if (signature == LOCAL_FILE_HEADER_SIGNATURE) {
    if (ProcessLocalFileEntry(compressed, uncompressed) < 0) {
      return false;
    }
  } else {
    error("local file header signature for file %s not found\n", filename);
    return false;
  }

  return true;
}

                                          u8 *uncompressed_size, char *filename,

                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {

        signature != ZIP64_EOCD_SIGNATURE) {

  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
