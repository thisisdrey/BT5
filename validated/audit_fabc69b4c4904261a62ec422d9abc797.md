Based on the code inspected, the Zest protocol lacks any voting/gauge reward mechanism analogous to Velodrome's `Gauge.sol`, so the literal "checkpoint.voted" report doesn't map 1:1. However, the same *root-cause pattern* — a single mutable "last checkpoint" field that a user can freely overwrite immediately before a protective check runs, defeating the check's intended purpose — has a direct analog in the `last-borrow-block` same-block liquidation guard.

### Title
Same-block liquidation guard can be perpetually refreshed by front-running dust borrows, indefinitely blocking liquidation of insolvent positions - (File: mainnet/contracts/market/v0-4-market.clar / v0-market-vault.clar)

### Summary
The market's flash-loan/oracle-frontrunning protection stores a single `last-borrow-block` value per user position, overwritten on every `debt-add-scaled` call, and checked in `liquidate` only against the *current* block height. Because this is a single unconditionally-overwritten field rather than an append-only or windowed record, a borrower can watch the mempool for an incoming `liquidate` transaction and front-run it with a trivial dust borrow in the same block, resetting `last-borrow-block` to the current block and causing `same-block-check` to revert the liquidation with `ERR-LIQUIDATION-BORROW-SAME-BLOCK`. This mirrors the Velodrome `voted` checkpoint bug: a protective/incentive flag that only reflects the "last write" can be freely toggled by the affected party right before the check that relies on it, letting them sidestep the intended protection every time it matters.

### Finding Description
`debt-add-scaled` unconditionally overwrites `last-borrow-block` with `stacks-block-height` on every borrow, no matter how small: [1](#0-0) 

`liquidate` in the market contract reads this single stored value and rejects liquidation if it equals the current block height, with only that immediate block used to prevent same-block flash-loan borrow-then-liquidate attacks: [2](#0-1) 

There is no minimum borrow size enforced beyond `> amount u0` in `borrow`: [3](#0-2) 

Because Stacks transactions and their target blocks are visible in the mempool before confirmation, a borrower whose position is (or is about to become) liquidatable can observe a pending `liquidate` call targeting them and submit a minimal dust `borrow` transaction that lands in the same block. This refreshes `last-borrow-block` to the current block height, which is exactly the value the `liquidate` call's `same-block-check` compares against, causing the liquidation to revert every time it is attempted in that block. The check has no memory beyond "was there any borrow — of any size — in this exact block," so it can be trivially and repeatedly satisfied by the party who most wants to avoid liquidation, defeating its purpose entirely, exactly as the `voted` boolean in Velodrome's Gauge checkpoint could be trivially re-set by the party who benefited from it.

### Impact Explanation
This falls under "Temporary freezing of funds" (or contributes toward protocol insolvency if abused persistently): a genuinely undercollateralized/liquidatable position can have its liquidation indefinitely delayed by the borrower via repeated dust-borrow front-running, during which further adverse price movement can increase bad debt beyond what liquidators are incentivized to cover, ultimately forcing bad-debt socialization across LPs/suppliers. Because the guard is purely block-scoped and stateless beyond the single overwritten field, the borrower can repeat this defense on every subsequent liquidation attempt as long as they can land a dust-borrow transaction in the same block as the liquidator's transaction.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to observe pending `liquidate` transactions in the mempool and land a competing `borrow` transaction in the same block, which is a realistic capability for a bot-operated malicious borrower monitoring their own position, especially on fast/Nakamoto-era Stacks block times. No special privilege or DAO compromise is required — only an ordinary account calling `borrow` and `liquidate`/observing the mempool, both of which are standard unprivileged market entry points.

### Recommendation
Do not rely on a single overwritable `last-borrow-block` for the same-block liquidation guard. Instead: (1) only refresh `last-borrow-block` when the borrow materially changes the user's health/egroup (or exceeds a meaningful minimum size) rather than on any nonzero debt increase, and/or (2) track the block of debt increases in a way that can't be trivially "reset" once per block (e.g., require a minimum elapsed number of blocks or a minimum borrowed-value threshold before the guard can be re-armed), and/or (3) decouple the anti-flash-loan protection from a general anti-liquidation mechanism so dust borrows cannot be used purely to grief liquidators.

### Proof of Concept
1. Attacker (Bob) opens a position with collateral and near-max debt near the liquidation threshold (`v0-4-market.clar` `borrow`).
2. Price moves adversely; Bob's position becomes liquidatable (`current-ltv >= ltv-liq-partial`).
3. A liquidator submits `liquidate(bob, ...)` into the mempool.
4. Bob observes the pending liquidation transaction and submits `borrow(<any-asset>, 1, ...)` (a dust amount, only constrained by `ERR-AMOUNT-ZERO`) targeting the same upcoming block.
5. `debt-add-scaled` executes first (or in the same block) and sets `last-borrow-block` to the current block height: [4](#0-3) 
6. The liquidator's `liquidate` call in the same block hits `same-block-check` and reverts with `ERR-LIQUIDATION-BORROW-SAME-BLOCK`: [2](#0-1) 
7. Bob repeats step 4–6 for every subsequent liquidation attempt, indefinitely stalling liquidation of an actually insolvent position.
