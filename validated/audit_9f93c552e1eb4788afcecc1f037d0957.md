## Analog Found

### Title
Missing `ForbidTransferToContract` enforcement in `ParticipateAssetIssueActuator` allows TRX to reach smart-contract accounts outside the TVM, breaking the protocol's "no bare TRX transfers to contracts" invariant - (File: `actuator/src/main/java/org/tron/core/actuator/ParticipateAssetIssueActuator.java`)

### Summary
The external report flags a case where one contract's write path (`approve()`) is not routed through the same sanity/permission check (`transferSanity`) enforced on its sibling write paths (`transfer`/`transferFrom`), letting the invariant (no blacklisted party can transact) be silently bypassed. The same defect pattern exists in java-tron: the `getForbidTransferToContract` invariant — "TRX must not reach a smart-contract account outside the TVM; it must go through `TriggerSmartContract`" — is enforced in `TransferActuator` and `TransferAssetActuator`, but is missing from `ParticipateAssetIssueActuator`, even though the latter performs the exact same kind of balance credit to an arbitrary `toAddress`.

### Finding Description
`TransferActuator.validate()` explicitly checks the invariant before crediting a `toAccount`: [1](#0-0) 

`TransferAssetActuator.validate()` enforces the identical check for TRC10 asset transfers: [2](#0-1) 

However, `ParticipateAssetIssueActuator`, which also moves TRX (`cost`) directly into an arbitrary `toAddress` account (the asset issuer) bypassing the TVM entirely, contains no such check in either its `validate()` or `execute()`: [3](#0-2) [4](#0-3) 

The `validate()` method only checks address validity, balance sufficiency, asset period, and asset balance of `toAccount` — never `toAccount.getType() == AccountType.Contract` combined with `dynamicStore.getForbidTransferToContract()`, unlike the two sibling actuators.

### Impact Explanation
`ForbidTransferToContract` exists specifically to stop TRX from landing in a contract's balance without invoking its code (i.e., a bare balance credit rather than a `CALL`). Contracts that maintain their own internal TRX accounting (e.g., escrow/vault-style contracts) rely on all incoming TRX passing through a payable function to update their ledger. `ParticipateAssetIssueContract` lets any unprivileged transaction sender ("participate" in an asset sale issued by a contract account) route TRX straight into that contract's balance via `AccountCapsule.setBalance`, completely bypassing the TVM and any payable-function accounting. This creates a discrepancy between the contract's actual TRX balance and its internally tracked balance — an "unbacked/stuck balance" condition for any contract-based asset issuer, and it constitutes an unauthorized bypass of a documented protocol-level restriction that other transfer-type actuators uphold.

### Likelihood Explanation
Reachable by any unprivileged account: attacker only needs to send a `ParticipateAssetIssueContract` transaction where `toAddress` (the asset's issuer, taken from `AssetIssueCapsule.getOwnerAddress()`) is a smart contract account and `getForbidTransferToContract()` is enabled. Since asset issuance is permissionless and the issuer address is fixed at asset-issue time, an attacker (or even an unaware regular user) can trivially trigger this path once a contract has issued a TRC10 asset.

### Recommendation
Add the same check present in `TransferActuator`/`TransferAssetActuator` to `ParticipateAssetIssueActuator.validate()`:
```java
if (dynamicStore.getForbidTransferToContract() == 1
    && toAccount.getType() == AccountType.Contract) {
  throw new ContractValidateException("Cannot participate asset issue to a smartContract.");
}
```

### Proof of Concept
1. Deploy a contract and have it issue a TRC10 asset (`AssetIssueContract` with `ownerAddress` = contract address).
2. Enable `ForbidTransferToContract` (already default on mainnet).
3. Send a `ParticipateAssetIssueContract` transaction buying that asset; `execute()` credits `cost` TRX directly into the contract's `AccountCapsule.balance` via `toAccount.setBalance(addExact(toAccount.getBalance(), cost))` — no `ContractValidateException` is thrown, unlike an equivalent attempt via `TransferContract` or `TransferAssetContract`, which would fail with "Cannot transfer TRX/asset to a smartContract."
