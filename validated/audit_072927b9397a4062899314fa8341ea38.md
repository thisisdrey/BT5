## Title
Unbounded interest-index growth in `accrue` can overflow Clarity's native `uint` and permanently revert `redeem`/`borrow`/`repay` — (File: `mainnet/contracts/vault/v0-vault-stx.clar` and sibling vaults)

### Summary
The vault's interest-accrual path recomputes `index`/`lindex` via raw, unchecked multiplication that relies on Clarity's native 128-bit `uint` runtime overflow abort. Because `accrue` is invoked unconditionally at the top of state-changing vault entry points, an overflow in the index math makes the whole vault permanently unable to process withdrawals, redemptions, borrows, and repayments — the same liveness failure pattern described in the Euler `initVaultCache` report, where an overflow in accumulator math should never be allowed to block essential fund-recovery paths.

### Finding Description
`next-index` and `next-liquidity-index` compute the updated index by multiplying the current index by a per-period multiplier and dividing back down: [1](#0-0) [2](#0-1) 

Concretely:
- `mul-div-down`/`mul-div-up` are plain `(/ (* x y) z)` / `(/ (+ (* x y) (- z u1)) z)` with no overflow guard. [3](#0-2) 
- `calc-multiplier-delta` multiplies `rate` by `time-delta * INDEX-PRECISION`, and `calc-index-next` multiplies `index-curr` by that `multiplier`, both via `mul-div-down`/`mul-div-up`. [4](#0-3) 
- `next-index`/`next-liquidity-index` chain these calls each time `accrue` runs while unpaused. [5](#0-4) 

Clarity's native `uint` is a checked 128-bit type (`MAX-U128 = 2^128-1`), and any arithmetic that exceeds this range causes the entire transaction to abort at runtime — there is no `try!`/graceful-degradation path around these multiplications, unlike the pause-based short-circuit that exists for the "already paused" case: [6](#0-5) [7](#0-6) 

`accrue` is called with `try!`/directly at the top of essentially every state-mutating vault entry point, e.g. `redeem`: [8](#0-7) 

and `system-borrow` (invoked transitively by `market.clar`'s `borrow`): [9](#0-8) 

Crucially, `last-update` is only advanced on a *successful* accrual: [10](#0-9) 

so once a call to `next-index`/`next-liquidity-index` overflows and the transaction reverts, `last-update` never moves forward; every subsequent call recomputes the same (or a larger, since real time keeps advancing) overflowing multiplier and reverts again. The only escape is the `accrue` pause flag, which is checked before the arithmetic runs and is a separate DAO-controlled state variable: [11](#0-10) 

Until that flag is set, every `redeem`, `system-borrow`, `system-repay`, and `deposit` call for the affected vault reverts unconditionally, because they all route through `accrue` first.

### Impact Explanation
This is a direct analog of the reported Euler issue: an unmitigated overflow deep in the per-block interest index cache computation causes the vault's core liveness-critical functions (`redeem`, `borrow`, `repay`) to permanently revert until a privileged pause action is taken. Users lose the ability to withdraw or repay their own funds through the ordinary path for the affected asset — a temporary (and, absent DAO intervention, effectively unbounded) freezing of user funds, matching the in-scope "temporary freezing of funds" impact class. It is reachable purely through ordinary continued protocol operation (interest compounding over time at the configured rate curve) — no DAO misconfiguration or key compromise is required to trigger it, only DAO awareness/action to remediate it afterward.

### Likelihood Explanation
Triggering the overflow requires the compounded product `index * multiplier` (or `lindex * multiplier`) to exceed `MAX-U128` (≈3.4×10^38), starting from `INDEX-PRECISION = 1e12`. Given `accrue` runs on essentially every user interaction and applies compounding growth based on the configured utilization/rate curve, sustained high utilization/high-rate periods over a long enough operating horizon can drive the index to this range, especially since there is no explicit cap on `index`/`lindex` growth anywhere in the vault code. Likelihood is Low-to-Medium in absolute terms (it requires a long operational horizon or sustained extreme rates) but the root-cause defect — no saturating/overflow-safe accrual path protecting withdraw/redeem/repay — is present today with no compensating control besides manual, reactive DAO pausing.

### Recommendation
Mirror Euler's fix: make interest accrual saturate rather than revert on overflow (cap `index`/`lindex` growth, or freeze further interest accrual while still allowing `total-debt`/`total-assets` reads to succeed) so that `accrue` can never itself block `redeem`, `system-borrow`, or `system-repay`. Add an explicit ceiling check on `index`/`lindex` before/after the multiplication in `next-index`/`next-liquidity-index`, and document (as the whitepaper update did for Euler) the guaranteed behavior when interest accrual saturates.

### Proof of Concept
1. Configure (or let market conditions drive) `points-ir` such that `interest-rate` stays high (near the top of the rate curve) for an extended period while utilization remains high, so `accrue`/`next-index` is repeatedly invoked with nonzero `time-delta`.
2. Over enough elapsed operating time, the compounding multiplication in `calc-index-next` (`idx * multiplier`) for either `index` or `lindex` approaches `MAX-U128 = 340282366920938463463374607431768211455`.
3. The next call to any vault entry point that invokes `accrue` (e.g. `redeem` at `mainnet/contracts/vault/v0-vault-stx.clar#L800`, or `system-borrow` at `#L868`) causes `mul-div-down`'s `(* x y)` in `calc-index-next` to exceed the native `uint` range, aborting the transaction.
4. Because the abort happens before `last-update` is written, every subsequent call to `redeem`/`borrow`/`repay` for that vault repeats the same overflowing computation and also reverts, until the DAO explicitly sets `pause-states.accrue` to `true` via the (separate, non-`accrue`-dependent) pause-state setter to bypass the arithmetic entirely.
