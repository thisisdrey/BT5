## Title
Front-running a multi-spend shielded transaction causes the entire batch to revert, wasting gas and failing unrelated legitimate spends - (File: `actuator/src/main/java/org/tron/core/actuator/ShieldedTransferActuator.java`)

### Summary
`ShieldedTransferActuator` allows a single `ShieldedTransferContract` transaction to batch multiple independent `SpendDescription` notes (and `ReceiveDescription` outputs) together. Both `validate()` and `execute()` iterate over the list of spends and, for each one, perform a global-state check (whether the note's nullifier has already been recorded in the `NullifierStore`). If any single nullifier in the batch is already spent, the whole transaction is rejected/reverted — none of the other, unrelated spends in the same batch are processed, even though they were individually valid.

### Finding Description
In `validate()`, each spend in the batch is checked against the global `NullifierStore` before any state is mutated: [1](#0-0) 

The same all-or-nothing pattern is repeated in `execute()`/`executeShielded()`, which also inserts nullifiers one by one and throws immediately (`"double spend"`) the moment a duplicate is found, aborting processing of the remaining spends/outputs in the batch: [2](#0-1) 

The `NullifierStore.has()` check reflects the current chain state (committed nullifiers), so it is exactly the "status check on each batch element that reverts the whole call if it doesn't match" pattern described in the reference report: [3](#0-2) 

Attack scenario: Alice broadcasts a `ShieldedTransferContract` transaction batching several independent spend notes (e.g., consolidating multiple shielded UTXOs in one transaction to save fees/complexity). Bob observes the pending transaction in the mempool, extracts one of the nullifiers Alice intends to spend, and crafts and broadcasts his own single-spend transaction for that same note with a higher fee/priority. If Bob's transaction lands first, the nullifier for that note becomes recorded in `NullifierStore`. When Alice's batched transaction is then processed, `validate()`/`execute()` throws `"note has been spend in this transaction"` / `"double spend"`, and the **entire** transaction reverts — including the legitimate spends of the other, still-unspent notes that Bob never touched.

### Impact Explanation
Alice loses the transaction fee for the entire batched shielded transaction, and none of her other unrelated (and still valid) notes get spent/consumed in that attempt, forcing her to rebuild and rebroadcast — repeating the same front-running exposure. This is a griefing/gas-loss vector reachable purely by an unprivileged transaction broadcaster observing the mempool; no special privileges are required.

### Likelihood Explanation
Likelihood is Medium: an attacker must observe the pending shielded transaction (nullifiers are visible in the broadcast transaction bytes since `SpendDescription.nullifier` is not encrypted) and race it with a higher-fee transaction spending just one of the same notes. This is straightforward mempool front-running, similar in nature to the referenced "heal" front-running issue, though it requires the attacker to actually control (or guess) a nullifier belonging to Alice's batch, which in practice usually means the attacker is intentionally griefing a known target rather than an opportunistic attacker on arbitrary users.

### Recommendation
Avoid failing the entire batched shielded transaction because of one already-spent note. Options include: (1) validating/consuming nullifiers independently and only rejecting the specific spend(s) that are stale rather than the whole transaction where the protocol allows it, or (2) documenting/enforcing that callers should not batch unrelated notes whose front-running risk they don't control, and (3) at minimum, ensure the failure mode is clearly surfaced early (as already done via `validate()`) rather than partially applying state changes in `execute()`, to avoid inconsistent partial application.

### Proof of Concept
1. Alice builds and broadcasts a `ShieldedTransferContract` with `SpendDescription` list `[S1, S2, S3]` (three independent notes) and corresponding outputs.
2. Bob observes the pending transaction, extracts `nullifier(S2)`, and broadcasts a competing transaction spending only `S2`, with higher priority/fee.
3. Bob's transaction is included first; `NullifierStore.put(nullifier(S2))` records the nullifier: see `chainbase/src/main/java/org/tron/core/store/NullifierStore.java:18-20`.
4. Alice's transaction is then processed. `ShieldedTransferActuator.validate()` iterates over `[S1, S2, S3]` and hits `nullifierStore.has(spendDescription.getNullifier())` true for `S2`, throwing `ContractValidateException("note has been spend in this transaction")` per lines 241-243 of `ShieldedTransferActuator.java`.
5. The entire transaction (including valid `S1` and `S3`) is rejected; Alice pays gas/fee for nothing and must resubmit, remaining exposed to the same griefing on retry.

  private void executeShielded(List<SpendDescription> spends, List<ReceiveDescription> receives,
      TransactionResultCapsule ret, long fee)
      throws ContractExeException {

    NullifierStore nullifierStore = chainBaseManager.getNullifierStore();
    MerkleContainer merkleContainer = chainBaseManager.getMerkleContainer();
    //handle spends
    for (SpendDescription spend : spends) {
      if (nullifierStore.has(
          new BytesCapsule(spend.getNullifier().toByteArray()).getData())) {
        ret.setStatus(fee, code.FAILED);
        ret.setShieldedTransactionFee(fee);
        throw new ContractExeException("double spend");
      }
      nullifierStore.put(new BytesCapsule(spend.getNullifier().toByteArray()));
    }
