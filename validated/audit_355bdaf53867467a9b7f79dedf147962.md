### Title
Unconditional `insert_instantiated_attachment` in attachment-download completion path lets a malicious peer poison `AtlasDB` with uncommitted content, served as canonical via `/v2/attachments/{hash}` - ([File: stackslib/src/net/atlas/db.rs], [File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentsDownloader::run` calls `AtlasDB::insert_instantiated_attachment` for every attachment byte-blob returned by any peer for an `AttachmentRequest`, without ever checking that the actual hash of the received bytes matches the `content_hash` that was requested or any real, chain-committed `AttachmentInstance`. `insert_instantiated_attachment` itself unconditionally sets `attachments.was_instantiated = 1` for whatever content is passed to it. `RPCGetAttachmentRequestHandler::try_handle_request` serves any row with `was_instantiated = 1` to unauthenticated callers via `GET /v2/attachments/<hash>`.

### Finding Description
The equality the endpoint is supposed to preserve — "content served for hash H via `/v2/attachments/{H}` corresponds to a real, on-chain-committed `AttachmentInstance.content_hash == H`" — is broken by the download-completion code path.

In `stackslib/src/net/atlas/download.rs`, `AttachmentsDownloader::run`, the `Done` branch does: [1](#0-0) 
For every `attachment` obtained from `context.attachments.drain()` (populated in `extend_with_attachments` straight from a peer's HTTP response, with no hash validation against the request): [2](#0-1) 
the code computes `find_all_attachment_instances(&attachment.hash())` and then calls `insert_instantiated_attachment(&attachment)` *regardless* of whether that lookup returned any rows. `attachment.hash()` is the hash of whatever bytes the peer actually sent back — not the `content_hash` that was originally requested (`AttachmentRequest::content_hash`), which is only used to build the URL path, not to validate the response.

`insert_instantiated_attachment` in `stackslib/src/net/atlas/db.rs` performs this insert unconditionally: [3](#0-2) 
It sets `was_instantiated = 1` on the `attachments` row for the (attacker-controlled) content hash with no gating on whether any `attachment_instances` row with matching `content_hash` and `status = Checked` exists. The subsequent `UPDATE attachment_instances SET is_available = 1 WHERE content_hash = ?1 AND status = ?2` is a no-op if no such row exists, but the `attachments` table write already succeeded.

Finally, `RPCGetAttachmentRequestHandler::try_handle_request` serves any row satisfying `hash=?1 AND was_instantiated=1` with no further correlation to `attachment_instances`: [4](#0-3) [5](#0-4) 

**Exploit flow:** an attacker runs their own peer that becomes one of the node's `outbound_sync_peers` with a valid data URL (permitted under the stated attacker model). When the victim's `AttachmentsDownloader` issues a legitimate `AttachmentRequest` for some real pending `content_hash` (normal BNS/Atlas sync activity), the attacker's peer answers the `GET /v2/attachments/{content_hash}` request with **arbitrary bytes B** unrelated to the requested hash. `decode_atlas_get_attachment` accepts this with no hash check. `extend_with_attachments` stores it. `run()`'s `Done` branch computes `Hash160(B)`, finds no matching instance, but still calls `insert_instantiated_attachment`, permanently writing `B` into `attachments` with `was_instantiated=1` keyed by `Hash160(B)`. From that point, any unauthenticated remote caller can `GET /v2/attachments/<hex(Hash160(B))>` and receive `B` back — content that no confirmed on-chain `AttachmentInstance`/name operation ever referenced.

### Impact Explanation
Any node's `AtlasDB` "attachments" table can be polluted with arbitrary attacker-chosen content that is unauthenticated-write and then served to any other caller via the public RPC endpoint as if it were validated Atlas/BNS content. This is a "serving non-canonical state as canonical" / "attachment-BNS mismatch" issue (High), and can also be viewed as an unauthenticated write into node state (the `attachments` table), since the write happens with no correlation check to any legitimate committed `content_hash`. It is repeatable per attachment sync round, and does not require the node's RPC secret or any privileged role — only that the attacker's peer is selected to service a pending download.

### Likelihood Explanation
Preconditions: the victim must have at least one pending/queued attachment instance (routine in a BNS-active network), and the attacker's peer must be among the node's outbound sync peers serving a data URL for that batch (achievable by any unprivileged party who runs and connects a peer, per the stated threat model — no secret or admin role needed). Attacker cost is low: run a peer, wait to be selected for an `AttachmentRequest`, and answer with arbitrary bytes. The bug is deterministic given code inspection — `insert_instantiated_attachment` has no gating condition at all — so exploitation reliability depends only on peer selection, not on any race or timing subtlety.

### Recommendation
In `AttachmentsDownloader::run`'s `Done` handling (`stackslib/src/net/atlas/download.rs`), verify that `attachment.hash()` equals the `content_hash` that was actually requested (available via the completed `AttachmentRequest`/`resolve_attachment` bookkeeping) before calling `insert_instantiated_attachment`. Additionally, harden `insert_instantiated_attachment` in `stackslib/src/net/atlas/db.rs` to only set `was_instantiated = 1` when a corresponding `attachment_instances` row with `status = Checked` and matching `content_hash` actually exists (i.e., make the `UPDATE ... is_available` check a precondition/guard for the `attachments` insert as well, or perform the check-then-insert atomically within the same transaction and abort the insert if no matching instance is found).

### Proof of Concept
Rust net test plan (in `stackslib/src/net/atlas/tests.rs` or a new download-focused test module):
1. Instantiate `AtlasDB::connect_memory`.
2. Do **not** insert any `AttachmentInstance` row referencing hash `H` for some payload `B`.
3. Directly construct an `Attachment { content: B }` and call `atlas_db.insert_instantiated_attachment(&attachment)` (simulating the unconditional call in `download.rs::run`'s `Done` branch, since a full P2P harness would require simulating a malicious peer response).
4. Call `atlas_db.find_all_attachment_instances(&attachment.hash())` and assert it returns an **empty vector** (no legitimate instance backs this content).
5. Issue `StacksHttpRequest::new_getattachment(host, attachment.hash())` through the RPC harness (`TestRPC`) targeting `RPCGetAttachmentRequestHandler`.
6. Assert the response is `200 OK` and its `GetAttachmentResponse.attachment.content == B`, proving the endpoint served content with no corresponding `Checked` `AttachmentInstance` — confirming the broken equality and the exact vulnerable line: `stackslib/src/net/atlas/db.rs:582-585` (unconditional `INSERT OR REPLACE INTO attachments ... was_instantiated, 1`).

    pub fn insert_instantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let tx = self.tx_begin()?;
        tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)",
            params![attachment.hash(), attachment.content, now],
        )?;
        tx.execute(
            "UPDATE attachment_instances SET is_available = 1 WHERE content_hash = ?1 AND status = ?2",
            params![attachment.hash(), AttachmentInstanceStatus::Checked],
        )?;
        tx.commit()?;
        Ok(())
    }
