### Title
Unsanitized double-precision exchange math in `ExchangeProcessor` silently corrupts AMM balances instead of failing safely - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
`ExchangeCapsule.transaction()` is the core AMM math routine invoked by `ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator` — all reachable from an unprivileged, signed transaction. By default it uses the legacy `ExchangeProcessor`, which performs its bonding-curve math with raw Java `double` division and casts the result back to `long` [1](#0-0) . Unlike the newer `SafeExchangeProcessor`, which uses `BigDecimal` and is verified to throw `ArithmeticException` on divide-by-zero [2](#0-1) , the legacy path never validates the intermediate `double` results before truncating them into an on-chain `long` token balance [3](#0-2) . This mirrors the CoinGecko report's core defect class: untrusted/derived numeric data flows through arithmetic without sanitization, and edge cases (division producing `NaN`/`±Infinity`) are silently converted into plausible-looking values instead of raising an error — the exact "stale/incorrect result with no error indication" failure mode described in the report, but here it directly determines TRC10/TRX balances rather than a fee price.

### Finding Description
`ExchangeCapsule.transaction()` selects the processor to use:
```
Processor processor = hardenedCalc
    ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);
``` [4](#0-3) 

`hardenedCalc` is `allowHarden()`, which is gated by the committee-controlled dynamic property `allowHardenExchangeCalculation()` [5](#0-4) . Unless/until that proposal is active on the network, every call from `ExchangeTransactionActuator.execute()` and `ExchangeWithdrawActuator.execute()` uses the legacy, unsafe `ExchangeProcessor` [6](#0-5) .

Inside `ExchangeProcessor`:
```java
private long exchangeFromSupply(long balance, long supplyQuant) {
  supply -= supplyQuant;
  double exchangeBalance = balance
      * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
  return (long) exchangeBalance;
}
``` [7](#0-6) 

If the running `supply` ever reaches exactly `0` (or the ratio `supplyQuant/supply` overflows/underflows double precision), the division and subsequent `Math.pow` produce `NaN` or `±Infinity`. Casting these to `long` in Java does **not** throw — `(long) Double.NaN == 0`, `(long) Double.POSITIVE_INFINITY == Long.MAX_VALUE`, `(long) Double.NEGATIVE_INFINITY == Long.MIN_VALUE`. This value is returned as `buyTokenQuant`/`anotherTokenQuant` and written straight into the exchange pool balances and the trader's account balance:
```java
this.exchange = this.exchange.toBuilder()
    .setFirstTokenBalance(newFirstTokenBalance)
    .setSecondTokenBalance(newSecondTokenBalance)
    .build();
return buyTokenQuant;
``` [8](#0-7) 

No `catch`/`recover`-equivalent exists for this in the actuator: `ExchangeTransactionActuator.execute()` only catches `ItemNotFoundException`, `InvalidProtocolBufferException`, `ContractValidateException`, and `ArithmeticException` [9](#0-8)  — none of which are thrown by a `double` NaN/Infinity computation, so the corrupted result is committed to the account and exchange stores unchecked, exactly as the report warns can happen when external/derived numeric data isn't sanitized before being trusted downstream.

### Impact Explanation
A successfully triggered `Long.MAX_VALUE` payout (via `(long) Infinity`) would let an attacker mint an unbacked TRX/TRC10 balance out of an exchange pool — a direct theft/unbacked-balance impact. A `(long) NaN == 0` payout would let an attacker drain `sellToken` from the pool while receiving `0` in return with no validation error (since `anotherTokenQuant <= 0` is checked only in some validate paths, not the actuator's execute path uniformly) — permanent freezing/loss of pooled funds. Both cases corrupt the AMM's invariant/state without producing any exception the node would treat as invalid.

### Likelihood Explanation
Reachability requires only sending a signed `ExchangeTransactionContract`/`ExchangeWithdrawContract` to an existing exchange pool — something any account can do. Driving `supply` (a per-call local variable seeded at `1_000_000_000_000_000_000L` and decremented/incremented by prior legs of the same transaction) to precisely zero, or forcing the `pow`/division into overflow, requires crafting `sellTokenQuant`/pool balances that hit the numeric edge exactly, which is a non-trivial but deterministic math search given the formula is fully known and public. This is comparable in difficulty to the kind of edge-case input crafting Spearbit flagged as exploitable in the CoinGecko report (attacker fully controls the numeric inputs feeding the vulnerable arithmetic).

### Recommendation
Migrate the default exchange path to the already-implemented `SafeExchangeProcessor` (or make `BigDecimal`/checked-arithmetic mandatory regardless of the `allowHardenExchangeCalculation` proposal state), and explicitly validate `Double.isFinite()`/non-NaN before any `(long)` cast of externally-influenced arithmetic results in `ExchangeProcessor`, raising an `ArithmeticException` (already caught by the actuators) instead of silently truncating.

### Proof of Concept
Conceptual reproduction (exact numeric inputs require solving the AMM formula for a `supply == 0` or overflow condition, which was not feasible to brute-force from static analysis alone):
1. Create an `Exchange` pair via `ExchangeCreateActuator` with attacker-controlled initial token balances.
2. Submit an `ExchangeTransactionContract` with a `quant` chosen so that, inside `ExchangeCapsule.transaction()`, the derived `supply` after `exchangeToSupply()` becomes exactly `0` (or drives `supplyQuant/supply` to an extreme ratio) before `exchangeFromSupply()` runs.
3. `Maths.pow(1.0 + Infinity/NaN, 2000.0, ...)` yields `NaN`/`Infinity`; `(long) exchangeBalance` truncates to `0` or `Long.MAX_VALUE`.
4. This value is returned as `anotherTokenQuant` and committed via `Commons.putExchangeCapsule(...)` and `accountStore.put(...)` without triggering any of the actuator's caught exceptions [10](#0-9) .

Note: I was unable to confirm the exact numeric inputs/genesis default of `allowHardenExchangeCalculation()` (whether it is enabled by default on current mainnet) from the indexed code alone; a Devin session with full repo/config access would be needed to pin down the exact proposal default and construct a concrete end-to-end numeric PoC.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
