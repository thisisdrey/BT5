Audit Report

## Title
Silent tip-loss on stale/invalid nonce in `snowbridge-pallet-system-v2::add_tip` — burned funds permanently unrecoverable - (File: `bridges/snowbridge/pallets/system-v2/src/lib.rs`)

## Summary
`EthereumSystemV2::add_tip` never propagates the inner `AddTip::add_tip` error to the caller; on failure it records the amount in `LostTips` and unconditionally returns `Ok(())`. Because the corresponding Ether was already swapped and irreversibly burned on AssetHub in `snowbridge_pallet_system_frontend::add_tip` *before* the best-effort XCM `Transact` even reaches BridgeHub, any race between the user-selected nonce and normal relayer/settlement processing causes permanent, unrecoverable loss of the tip. [1](#0-0) [2](#0-1) 

## Finding Description
The flow: (1) user calls `system_frontend::add_tip(message_id, asset)` on AssetHub, which calls `swap_fee_asset_and_burn` — swapping the tip asset for Ether and irreversibly destroying it via `burn_for_teleport` — *before* the cross-chain call is even sent. [3](#0-2) 
(2) A best-effort, unpaid `Transact` XCM carrying `EthereumSystemCall::AddTip` is dispatched to BridgeHub with `UnpaidExecution`, no delivery/execution guarantee. [4](#0-3) 
(3) On BridgeHub, `EthereumSystemV2::add_tip` dispatches to `InboundQueue::add_tip(nonce, amount)` — which rejects the tip with `AddTipError::NonceConsumed` if the message's nonce bit is already set — or `OutboundQueue::add_tip(nonce, amount)`, which rejects with `AddTipError::UnknownMessage` if the `PendingOrders` entry for that nonce no longer exists (already delivered/settled). [5](#0-4) [6](#0-5) 
(4) `EthereumSystemV2::add_tip` catches any such `Err`, adds the amount into `LostTips::<T>` keyed by sender, emits `TipProcessed{success: false}`, and still returns `Ok(())` — the dispatchable never reverts. [7](#0-6) 
The storage doc comment explicitly acknowledges no recovery mechanism exists yet: "Capturing the lost tips here supports implementing a recovery method in the future." [8](#0-7) 

There is no atomic linkage between the AssetHub-side burn and the BridgeHub-side accounting: the burn happens unconditionally and precedes the destination-side crediting attempt, which is only attempted best-effort over an unpaid, unguaranteed XCM.

## Impact Explanation
This is a permanent user-fund loss: any unprivileged user submitting `add_tip` for a nonce that becomes stale (message already processed inbound, or already delivered/settled outbound) between asset burn and XCM arrival loses the burned Ether tip with no on-chain path to reclaim it — only a bookkeeping entry in `LostTips` with no implemented claim mechanism. This matches the "permanent user-fund lock" impact category, since value is destroyed on the source chain unconditionally before destination-side settlement is confirmed, violating the invariant that payout state should only advance after execution and settlement succeed atomically.

## Likelihood Explanation
No privileged access, governance action, or malicious actor is required — normal, unprivileged use of the public `add_tip` extrinsic under ordinary network timing (an inbound message being processed by a relayer, or an outbound message being delivered/settled) concurrently with a user's tip submission is sufficient to trigger the race, given XCM transport delay between AssetHub and BridgeHub and the asynchronous, independent progression of Ethereum message processing.

## Recommendation
Avoid irreversibly burning the tip asset on AssetHub before the BridgeHub-side add_tip is confirmed to succeed. Options: reserve/hold the asset until success confirmation is received from BridgeHub and only finalize the burn then (refunding on failure); or implement the promised `LostTips` recovery/claim extrinsic now rather than leaving it a documented future gap; at minimum, tighten the timing window by having AssetHub precondition on nonce validity before initiating the burn.

## Proof of Concept
1. On BridgeHub, a relayer submits `EthereumInboundQueueV2::submit` for message nonce `N`; it is processed and `Nonce::<T>::set(N)` marks it consumed.
2. Concurrently, the user on AssetHub calls `SnowbridgeSystemFrontend::add_tip(MessageId::Inbound(N), tip_asset)`; `swap_fee_asset_and_burn` swaps and burns the user's asset for Ether — value destroyed at [9](#0-8) .
3. The XCM `Transact(EthereumSystemCall::AddTip{sender, message_id: Inbound(N), amount})` arrives at BridgeHub after step 1 completes.
4. `InboundQueue::add_tip(N, amount)` finds `Nonce::<T>::get(N) == true`, returning `Err(AddTipError::NonceConsumed)` per [10](#0-9) .
5. `EthereumSystemV2::add_tip` swallows the error, records it in `LostTips::<T>::get(sender)`, and returns `Ok(())` at [11](#0-10) ; the user's burned funds are gone with no on-chain reclaim path.

		pub fn add_tip(
			origin: OriginFor<T>,
			sender: AccountIdOf<T>,
			message_id: MessageId,
			amount: u128,
		) -> DispatchResult {
			T::FrontendOrigin::ensure_origin(origin)?;

			let result = match message_id {
				Inbound(nonce) => <T as pallet::Config>::InboundQueue::add_tip(nonce, amount),
				Outbound(nonce) => <T as pallet::Config>::OutboundQueue::add_tip(nonce, amount),
			};

			if let Err(ref e) = result {
				tracing::debug!(target: LOG_TARGET, ?e, ?message_id, ?amount, "error adding tip");
				LostTips::<T>::mutate(&sender, |lost_tip| {
					*lost_tip = lost_tip.saturating_add(amount);
				});
			}

			Self::deposit_event(Event::<T>::TipProcessed {
				sender,
				message_id,
				amount,
				success: result.is_ok(),
			});

			Ok(())
		}

		fn swap_fee_asset_and_burn(
			origin: Location,
			fee_asset: Asset,
		) -> Result<u128, DispatchError> {
			let ether_location = T::EthereumLocation::get();
			let (fee_asset_location, fee_amount) = match fee_asset {
				Asset { id: AssetId(ref loc), fun: Fungible(amount) } => (loc, amount),
				_ => {
					tracing::debug!(target: LOG_TARGET, ?fee_asset, "error matching fee asset");
					return Err(Error::<T>::UnsupportedAsset.into());
				},
			};
			if fee_amount == 0 {
				return Ok(0);
			}

			let ether_gained = if *fee_asset_location != ether_location {
				Self::swap_and_burn(
					origin.clone(),
					fee_asset_location.clone(),
					ether_location,
					fee_amount,
				)
				.inspect_err(|&e| {
					tracing::debug!(target: LOG_TARGET, ?e, "error swapping asset");
				})?
			} else {
				burn_for_teleport::<T::AssetTransactor>(&origin, &fee_asset)
					.map_err(|_| Error::<T>::BurnError)?;
				fee_amount
			};
			Ok(ether_gained)
		}

			// If the nonce is already processed, return an error

			// Otherwise add the tip.
