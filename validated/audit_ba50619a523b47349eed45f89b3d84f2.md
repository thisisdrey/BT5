### Title
Unprivileged donation to a pool's reward account can overflow `RewardCounter` and permanently lock `unbond`/`claim_payout`/`bond_extra` for all members - (File: substrate/frame/nomination-pools/src/lib.rs)

### Summary
`pallet-nomination-pools` computes each pool's reward accrual via `RewardPool::current_reward_counter`, which converts the pool's *current on-chain balance* of its reward account into a `FixedU128`-based `RewardCounter` using `T::RewardCounter::checked_from_rational(new_pending_rewards, bonded_points)`. Because the reward account is an ordinary derived `AccountId` (`Pallet::<T>::generate_reward_account(id)`), any unprivileged account can transfer funds into it directly, outside of the pool's own reward-accrual mechanism. If the donated balance is large enough relative to the pool's `bonded_points`, the rational-to-fixed-point conversion overflows and returns `None`, which is mapped to `Error::<T>::OverflowRisk`. This mirrors the dForce report's core pattern: a mandatory, revert-causing calculation embedded in the "settlement" path that every important call must succeed through before proceeding.

### Finding Description
`RewardPool::current_reward_counter` at [1](#0-0)  computes:

```
let current_payout_balance = balance.saturating_add(...).saturating_sub(self.last_recorded_total_payouts);
let new_pending_rewards = current_payout_balance.saturating_sub(new_pending_commission);
let current_reward_counter = T::RewardCounter::checked_from_rational(new_pending_rewards, bonded_points)
    .and_then(|ref r| self.last_recorded_reward_counter.checked_add(r))
    .ok_or(Error::<T>::OverflowRisk)?;
```

`balance` is fetched from `Self::current_balance(id)` [2](#0-1) , which is simply the reducible balance of the reward account — a value fully controllable by anyone who transfers tokens into that account, with no relation to the pool's actual points or bonded stake. The pallet's own tests demonstrate this is possible and expected: `create_sets_recorded_data` pre-funds `Pools::generate_reward_account(3)` via a plain `Currency::set_balance` before the pool even exists [3](#0-2) , and `dissolve_pool`'s comment explicitly anticipates "erroneous transfers to the reward account" [4](#0-3) .

`RewardCounter::checked_from_rational` is a `FixedU128`-style conversion that internally multiplies the numerator by `10^18` before dividing — so it overflows well before `new_pending_rewards` reaches `Balance::MAX`. If a pool has small `bonded_points` (e.g., only the minimum depositor bond) and an attacker sends a very large balance directly to the pool's reward account, `new_pending_rewards / bonded_points * 10^18` overflows `u128`, and `checked_from_rational` returns `None`, producing `Error::<T>::OverflowRisk`.

This error propagates through `current_reward_counter` → `RewardPool::update_records` (used at line 1417 via `?`) and `do_reward_payout` (line 3539 via `?`), which are invoked, non-optionally, from:
- `unbond` (`?`-propagated at [5](#0-4) )
- `claim_payout` / `do_claim_payout` ( [6](#0-5) )
- `bond_extra` ( [7](#0-6) )

There is no bypass path: every member-facing extrinsic that touches rewards mandatorily calls this same arithmetic, exactly like `Base._updateInterest` in the dForce report being unconditionally invoked before other state-changing operations. Once the reward account's balance is inflated past the overflow threshold for the pool's point total, `OverflowRisk` will be returned on every subsequent call for *every* member of that pool — not just the attacker — because `bonded_points` and the shared reward-account balance are pool-global state, not per-member.

### Impact Explanation
This is a public, underpriced-work-style denial of service: a single low-value transfer (the DoS payload is the "donation" itself, but since it goes to the pool's own reward account, the attacker mostly just parks funds there rather than burning them, and the pool operator/depositor cannot unilaterally sweep this excess since there is no permissionless correction mechanism analogous to `adjust_pool_deposit` for this specific imbalance) can permanently prevent `unbond`, `claim_payout`, and `bond_extra` for every member of a targeted nomination pool. This locks members' funds inside the pool (`unbond` is required before `withdraw_unbonded` can release funds), directly matching the "permanent user-fund lock" and "public underpriced work that... stalls processing" categories in the Impact Gate.

### Likelihood Explanation
Any signed account with enough balance to transfer to the pool's reward account (a plain, non-gated `AccountId`) can trigger this. Smaller pools (low `bonded_points`, e.g., pools that only just met the minimum-bond requirement) are especially at risk since the overflow threshold scales inversely with `bonded_points`. No governance, admin, relayer, or validator involvement is required — this is a fully permissionless, single-transaction griefing vector.

### Recommendation
- Bound `RewardPool::current_reward_counter`'s balance input independently of arbitrary reward-account credits, e.g., by tracking pool income only through pool-internal bookkeeping rather than trusting `Currency::reducible_balance` of a freely-creditable account, or by clamping/saturating the computation instead of returning a hard error.
- If `checked_from_rational` fails, do not propagate a hard error that blocks `unbond`/`claim_payout`; instead, saturate to `RewardCounter::max_value()` (analogous to fixing the `_updateInterest`-style hard revert in the original report) so essential exit paths (`unbond`, `withdraw_unbonded`) remain available even in a corrupted-accounting scenario.
- Optionally, cap the balance that can be transferred into pool reward accounts via non-pool channels, or add a permissionless "sweep excess" call analogous to `adjust_pool_deposit` that reconciles reward-account balance without touching the reward-counter arithmetic.

### Proof of Concept
1. Create a nomination pool with the minimum allowed `bonded_points`/bond (e.g. just above `MinCreateBond`).
2. As any unprivileged account, call `Balances::transfer_keep_alive` (or equivalent) to send an amount `X` directly to `Pools::generate_reward_account(pool_id)`, where `X` is large enough that `X * 10^18 / bonded_points` exceeds `u128::MAX` (concretely, for `bonded_points` near the minimum bond of a few DOT-equivalent units, `X` on the order of `u128::MAX / 10^18 * bonded_points` suffices — far below `u128::MAX` itself).
3. Any member now calling `Pools::claim_payout`, `Pools::unbond`, or `Pools::bond_extra` on this pool will get `Error::<T>::OverflowRisk` from `RewardPool::current_reward_counter` [8](#0-7) , permanently blocking their ability to exit the pool.

	fn current_reward_counter(
		&self,
		id: PoolId,
		bonded_points: BalanceOf<T>,
		commission: Perbill,
	) -> Result<(T::RewardCounter, BalanceOf<T>), Error<T>> {
		let balance = Self::current_balance(id);

		// Calculate the current payout balance. The first 3 values of this calculation added
		// together represent what the balance would be if no payouts were made. The
		// `last_recorded_total_payouts` is then subtracted from this value to cancel out previously
		// recorded payouts, leaving only the remaining payouts that have not been claimed.
		let current_payout_balance = balance
			.saturating_add(self.total_rewards_claimed)
			.saturating_add(self.total_commission_claimed)
			.saturating_sub(self.last_recorded_total_payouts);

		// Split the `current_payout_balance` into claimable rewards and claimable commission
		// according to the current commission rate.
		let new_pending_commission = commission * current_payout_balance;
		let new_pending_rewards = current_payout_balance.saturating_sub(new_pending_commission);

		// * accuracy notes regarding the multiplication in `checked_from_rational`:
		// `current_payout_balance` is a subset of the total_issuance at the very worse.
		// `bonded_points` are similarly, in a non-slashed pool, have the same granularity as
		// balance, and are thus below within the range of total_issuance. In the worse case
		// scenario, for `saturating_from_rational`, we have:
		//
		// dot_total_issuance * 10^18 / `minJoinBond`
		//
		// assuming `MinJoinBond == ED`
		//
		// dot_total_issuance * 10^18 / 10^10 = dot_total_issuance * 10^8
		//
		// which, with the current numbers, is a miniscule fraction of the u128 capacity.
		//
		// Thus, adding two values of type reward counter should be safe for ages in a chain like
		// Polkadot. The important note here is that `reward_pool.last_recorded_reward_counter` only
		// ever accumulates, but its semantics imply that it is less than total_issuance, when
		// represented as `FixedU128`, which means it is less than `total_issuance * 10^18`.
		//
		// * accuracy notes regarding `checked_from_rational` collapsing to zero, meaning that no
		//   reward can be claimed:
		//
		// largest `bonded_points`, such that the reward counter is non-zero, with `FixedU128` will
		// be when the payout is being computed. This essentially means `payout/bonded_points` needs
		// to be more than 1/1^18. Thus, assuming that `bonded_points` will always be less than `10
		// * dot_total_issuance`, if the reward_counter is the smallest possible value, the value of
		//   the
		// reward being calculated is:
		//
		// x / 10^20 = 1/ 10^18
		//
		// x = 100
		//
		// which is basically 10^-8 DOTs. See `smallest_claimable_reward` for an example of this.
		let current_reward_counter =
			T::RewardCounter::checked_from_rational(new_pending_rewards, bonded_points)
				.and_then(|ref r| self.last_recorded_reward_counter.checked_add(r))
				.ok_or(Error::<T>::OverflowRisk)?;

		Ok((current_reward_counter, new_pending_commission))
	}
