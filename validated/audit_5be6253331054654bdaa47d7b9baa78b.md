### Title
Out-of-bounds read parsing ZIP64 extra fields in central directory entries - (File: `third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` parses the extra-field records of a central directory header without validating that each record's declared `data_size` stays within the bounds of the extra-field region, unlike the local-file-header parser in the same file which uses `EnsureRemaining()` before every read.

### Finding Description
When ijar reads a `.jar`/`.zip` file (e.g. when building interface jars from a jar supplied via `java_import`, downloaded artifacts, or other build inputs that are effectively untrusted content), `ProcessCentralDirEntry` reads `file_name_length`, `extra_field_length`, and other header fields directly from the mapped file: [1](#0-0) 

It then walks the extra-field bytes with a manual loop that trusts each record's `data_size` field completely: [2](#0-1) 

`extra_p` is advanced by `data_size` — a value taken directly from attacker-controlled file bytes — with no check that `extra_p + data_size <= p` (the end of the extra-field region) or that `extra_p + 4` (header_id + data_size) stays within bounds. If `data_size` is large, `extra_p` can run past the end of the extra-field area, past the end of the central directory, and potentially past the end of the memory-mapped file. When the loop condition `header_id == ZIP64_EXTRA_FIELD_TAG` happens to match arbitrary bytes beyond the intended region, `get_u8le(extra)` performs an 8-byte read from that out-of-bounds location.

This is structurally the same bug class as the venus report: a size/length field is read from untrusted data and used to advance a cursor and dereference memory without checking it against the remaining valid buffer length. Notably, the sibling function `InputZipFile::ProcessLocalFileEntry` in the very same file does perform this kind of check via `EnsureRemaining()` before reading `file_name`, `extra_field`, and file data: [3](#0-2) [4](#0-3) 

but `ProcessCentralDirEntry` has no equivalent guard for the extra-field loop, relying only on a comment asserting "the central directory is always followed by another data structure that has a signature, so parsing it this way is safe" — an assumption that does not hold once a crafted `data_size` value is used to walk past the intended region: [5](#0-4) 

### Impact Explanation
An attacker who supplies a crafted `.jar`/`.zip` file that is fed into ijar (e.g. as a `java_import` jar or similar build input) can trigger an out-of-bounds read within the process handling the file. Depending on memory layout this can cause a crash (denial of service for that invocation) or, in the case of the ZIP64 branch, leak adjacent memory content into interpreted size fields, which are subsequently used to determine `compressed_size`/`uncompressed_size`/`offset` for further parsing.

### Likelihood Explanation
I could not fully verify the exact bounds established before `ProcessCentralDirEntry` is invoked (e.g., how `central_dir_current_`/EOCD sizes are validated against total mapped-file length in `InputZipFile::Open()`), since I was not able to retrieve that portion of the file within the available tool budget. This is necessary to confirm whether the read can actually escape the mmap'd region or is constrained to remain within it (which would reduce this to a same-process, in-bounds-but-wrong-data confusion rather than a true OOB read). I am flagging this uncertainty explicitly rather than asserting full exploitability.

### Recommendation
Add a bounds check inside the extra-field parsing loop in `ProcessCentralDirEntry`, mirroring the `EnsureRemaining()` pattern used in `ProcessLocalFileEntry`: before reading `header_id`/`data_size` from `extra_p`, verify at least 4 bytes remain before `p`; before advancing `extra_p` by `data_size`, verify `extra_p + data_size <= p`. Reject the entry (return `false`/error) if the check fails, rather than trusting the declared length unconditionally.

### Proof of Concept
I was unable to fully trace the file-open/EOCD-validation path (`InputZipFile::Open()`) to construct a concrete minimal `.zip` byte sequence and confirm it reaches unmapped memory versus staying in-bounds-but-corrupted within the given tool-call budget. A reproducible PoC would need to be built as a unit test (in the style of `output_jar_simple_test.cc`'s `CreateZipWithMalformedExtraField`) that crafts a central directory header with a ZIP64 extra field whose `data_size` exceeds the actual extra-field buffer length, then runs it through ijar's zip-processing entry point to observe the OOB read (e.g., via ASan). This construction step should be completed and verified by a follow-up engineer with full file access before treating this as a confirmed, exploitable vulnerability rather than a code-quality/defense-in-depth gap.

  // abort with an error message.  "state" is the name of the field
  // we're about to read, for diagnostics.
  int EnsureRemaining(size_t n, const char *state) {
    size_t in_offset = p - zipdata_in_;
    size_t remaining = input_file_->Length() - in_offset;
    if (n > remaining) {
      return error("Premature end of file (at offset %zd, state=%s); "
                   "expected %zd more bytes but found %zd.\n",
                   in_offset, state, n, remaining);
    }
    return 0;
  }
