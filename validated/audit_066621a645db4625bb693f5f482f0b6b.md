### Title
Vault `deposit()` mints 0 shares for small deposits without reverting, causing silent loss of depositor funds - (File: `mainnet/contracts/vault/v0-vault-usdc.clar` and identical logic in `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-stx.clar`, `v0-vault-usdh.clar`)

### Summary
The Zest v2 tokenized vault contracts (`v0-vault-*.clar`) compute shares to mint on deposit via `convert-to-shares-preview`, which performs `mul-div-down amount ts ta` and can floor to `u0` once the share price (`ta/ts`, growing via interest-index accrual) exceeds `1`. `deposit()` only checks `(>= inkind min-out)` for slippage and never asserts `inkind > u0`, unlike `redeem()` which explicitly enforces `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)`. A depositor whose `amount` is small relative to the current share price can have their underlying tokens pulled via `receive-underlying` while `ft-mint?` mints `0` shares to them, permanently transferring their principal to existing shareholders.

### Finding Description
`convert-to-shares-preview` in each vault contract computes:
```
(define-private (convert-to-shares-preview (amount uint))
  (let ((ta (total-assets-preview))
        (ts (total-supply-preview)))
    (if (is-eq ts u0)
        amount
        (if (is-eq ta u0)
            u0
            (mul-div-down amount ts ta)))))
``` [1](#0-0) 

Once `ts != u0` and `ta > u0` (i.e. after the very first deposit, and especially after interest accrual raises `ta` relative to `ts`), any `amount` small enough that `amount * ts / ta` floors to `0` will produce `inkind = u0`.

`deposit()` then proceeds without any zero-output guard:
```
(asserts! (not (get deposit states)) ERR-PAUSED)
(asserts! (var-get initialized) ERR-INIT)
(asserts! (not (var-get in-flashloan)) ERR-REENTRANCY)
(asserts! (> amount u0) ERR-AMOUNT-ZERO)
(asserts! (>= inkind min-out) ERR-SLIPPAGE)
(asserts! (<= (+ current-assets amount) CAP-SUPPLY) ERR-SUPPLY-CAP-EXCEEDED)

(try! (receive-underlying amount account))
(try! (ft-mint? zft inkind recipient))
(var-set assets (+ current-assets amount))
``` [2](#0-1) 

There is no `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)` check on the deposit path. By contrast, `redeem()` in the very same file explicitly guards against this exact zero-output scenario:
```
(asserts! (>= current-assets inkind) ERR-INSUFFICIENT-ASSETS)
(asserts! (not (get redeem states)) ERR-PAUSED)
(asserts! (> amount u0) ERR-AMOUNT-ZERO)
(asserts! (> inkind u0) ERR-OUTPUT-ZERO)
(asserts! (>= inkind min-out) ERR-SLIPPAGE)
``` [3](#0-2) 

This asymmetry means the same "0 in-kind output" defect that the redeem path defends against is left completely unguarded on the deposit path — exactly the root cause identified in the referenced dTRINITY `DStakeToken` report (`previewDeposit()` returning 0, and `_deposit()` not reverting on a 0-share mint).

The `min-out` parameter does not reliably protect against this: if a caller (or an integrating wallet/aggregator using a default of `u0` for `min-out`, which is a legitimate on-chain valid value) does not set a nonzero `min-out`, `(>= inkind min-out)` trivially passes even when `inkind` is `u0`.

### Impact Explanation
`receive-underlying` unconditionally pulls the depositor's full `amount` of underlying tokens into the vault before minting shares, so a depositor whose deposit rounds to `0` shares loses their entire principal permanently — the tokens are absorbed into the vault's `assets` and become upside for all other existing zft holders. This is a direct theft/permanent loss of principal (not merely yield) for the affected depositor, satisfying the in-scope "theft of user funds at rest" / "permanent freezing of funds" impact class, since the ordinary principal cannot ever recover the deposited amount corresponding to the minted `0` shares.

### Likelihood Explanation
The vaults are designed to accrue interest into the share price via a compounding `index` (documented in `docs/vaults.md`: "1 zUSDC = 1.25 USDC ... 25% cumulative interest") [4](#0-3) , meaning `ta/ts` grows over the life of the vault. As the price per share increases, the deposit amount required to round down to `0` shares grows proportionally (e.g. at a 1.25x price, any deposit below the smallest unit needed to yield 1 share rounds to zero). This can be triggered unintentionally by any ordinary user making a small deposit (e.g. dust deposits, UI rounding, or scripted deposits) once the vault has accrued sufficient interest, requiring no privileged access and no DAO involvement.

### Recommendation
Add an explicit zero-output guard in every vault's `deposit()` function, mirroring the existing `redeem()` protection:
```
(asserts! (> inkind u0) ERR-OUTPUT-ZERO)
```
placed alongside the other `asserts!` checks in `deposit()`, so that any deposit resolving to `0` shares reverts instead of silently consuming the depositor's underlying assets.

### Proof of Concept
1. Vault is initialized and has accrued sufficient interest so that `total-assets-preview() / total-supply-preview() > 1` (e.g., price = 1.25 assets per share, achievable after normal operation given interest index appreciation as described in `docs/vaults.md`).
2. A user calls `deposit(amount, u0, recipient)` with an `amount` small enough that `mul-div-down amount ts ta` floors to `u0` (e.g., `amount` less than `ta/ts` in the smallest denomination) and `min-out = u0` (a valid parameter value satisfying `(>= inkind min-out)`).
3. `deposit()` passes all `asserts!` (amount > 0, `inkind (=0) >= min-out (=0)`, within supply cap).
4. `receive-underlying` transfers the user's full `amount` of underlying into the vault; `ft-mint? zft inkind recipient` mints `0` zft to the user.
5. The user's underlying tokens are now part of vault `assets`, backing existing shareholders' redemptions, while the user holds `0` zft and has no path to recover the deposited amount — permanent loss of principal for that depositor.
