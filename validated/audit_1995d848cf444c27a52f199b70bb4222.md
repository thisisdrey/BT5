### Title
Unvalidated attacker-controlled length field used to size and index precompiled-contract argument arrays - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
`extractBytes32Array`, `extractBytesArray`, and `extractSigArray` in `PrecompiledContracts.java` read a length value directly from the ABI-encoded calldata word array (`words[offset].intValueSafe()`) supplied by any TVM caller and use it verbatim to allocate an array (`new byte[len][]`) and to index further into the `words` array, without validating that `len` (or the derived indices) fit within the actual bounds of the caller-supplied `words`/`data` buffers. [1](#0-0) 

### Finding Description
`extractBytes32Array` has no upper-bound or offset check at all before reading `len` and allocating `new byte[len][]`: [2](#0-1) 

`extractBytesArray` and `extractSigArray` only guard against `offset` being out of range, but not `len` itself, and then use `len` to iterate and index `words[offset + i + 1]` and derive further offsets (`bytesOffset`, `bytesLen`) that are also taken straight from calldata: [3](#0-2) 

This mirrors the bug class in the reported CVE: a length/offset field taken from an externally supplied structure (there, a CCA ECC key token; here, ABI-encoded TVM calldata) is used directly to size a copy/allocation operation without checking it against the actual available buffer size. In the kernel this produced a native buffer overflow; in java-tron the analogous unvalidated-length pattern causes either:
- `NegativeArraySizeException` / `OutOfMemoryError` when `len` is very large or negative (`new byte[len][]`), or
- `ArrayIndexOutOfBoundsException` when the derived offset (`offset + i + 1`, or `bytesOffset + offset + 2) * WORD_SIZE`) exceeds the bounds of `words`/`data`.

`VerifyTransferProof.execute` shows the same unvalidated-offset pattern for the Sapling precompile: `spendOffset`, `spendAuthSigOffset`, and `receiveOffset` are parsed directly from the calldata (`parseInt(data, 0/32/64)`) and used unchecked as base offsets for `System.arraycopy` calls further down: [4](#0-3) 

### Impact Explanation
Because Java performs bounds checking on array accesses, the immediate effect of an out-of-range `len`/offset is a thrown `Exception`/`Error` rather than a native memory-safety corruption. Whether this rises to a real security impact depends on whether the exception is caught:
- If the throw is an `Exception` subtype and is caught by the enclosing precompile/TVM dispatch logic (as is done, e.g., in `VerifyTransferProof.execute`'s broad `catch (Throwable any)`), the call simply fails/reverts — limited impact.
- If the throw is an `Error` (e.g., `OutOfMemoryError` from `new byte[Integer.MAX_VALUE][]` in `extractBytes32Array`), it is not an `Exception` and can escape narrower `catch (Exception ...)` blocks, propagating up through the TVM execution path and potentially destabilizing the node process (crash/halt of that thread or JVM-wide memory pressure). This would satisfy the "node crash or halt" impact bar if such an `Error` is not caught anywhere in the call chain up to the transaction-processing/block-application code in `Manager`.

I was not able to fully confirm, within the available search results, the exact precompiled-contract entry point(s) that call `extractBytes32Array` (the calling class name could not be located via `grep_search` for `class ValidateMultiSign`/`class BatchValidateSign` in this file, though related test files `BatchValidateSignContractTest.java` and `ValidateMultiSignContractTest.java` exist), nor whether every call path to these three helper functions is wrapped in a `catch (Throwable ...)`/`catch (Error ...)` block. This uncertainty means I cannot fully validate whether an uncaught `Error` truly reaches an unhandled state in production, versus being caught by an outer TVM guard.

### Likelihood Explanation
These helpers process raw calldata for TVM precompiled contracts, which are reachable by any account that can send a transaction invoking the relevant precompile address (no special privilege required — any contract deployer or transaction broadcaster). Crafting a calldata word with an extreme integer value (e.g., `0xFFFFFFFF`) at the length-field offset is trivial.

### Recommendation
Add explicit range validation for `len` (and any offsets derived from calldata, such as `bytesOffset`, `bytesLen` in `extractBytesArray`, and `spendOffset`/`spendAuthSigOffset`/`receiveOffset` in `VerifyTransferProof.execute`) against the actual size of `words`/`data` before using them to allocate arrays or as `System.arraycopy`/array-index parameters, rejecting the precompile call early (returning failure) instead of allowing unchecked allocation or indexing, mirroring the upstream kernel fix of validating the length field before it is used to derive a copy size.

### Proof of Concept
Not fully verifiable without confirming the exact TVM precompile entry point that invokes `extractBytes32Array`; conceptually: deploy/call a contract that invokes the precompiled contract using `extractBytes32Array` (per test file `ValidateMultiSignContractTest.java`) with the length word at the target offset set to a very large value (e.g., `0x7FFFFFFF`), forcing `new byte[len][]` to attempt an oversized allocation. Confirming whether this throws an uncaught `Error` at the node level, versus being caught by a wrapping TVM exception handler, requires running this against a live node — which I could not do given index-only access.   private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }

  private static byte[][] extractSigArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          SIG_LENGTH);
    }
    return bytesArray;
  }
