## Analysis

The reported bug class — critical, irreversible operations executed in a single function call without a two-step confirm/accept procedure — has a direct, reachable analog in an unprivileged user-facing path: the marginfi account authority-transfer instructions. [1](#0-0) [2](#0-1) 

### Title
Single-step, unconfirmed authority transfer in `transfer_to_new_account`/`transfer_to_new_account_pda` permanently and irrecoverably migrates all account funds/positions to an unvalidated address - (File: programs/marginfi/src/instructions/marginfi_account/transfer_account.rs)

### Summary
`transfer_to_new_account` and `transfer_to_new_account_pda` let an account authority migrate all lending positions to a brand-new `MarginfiAccount` under a caller-supplied `new_authority` in a single atomic instruction. The `new_authority` field is explicitly marked `/// CHECK: WARN: New authority is completely unchecked` and is accepted with zero validation, and the old account is immediately disabled and its `lending_account` zeroed out. There is no acknowledgment/claim step by the `new_authority` itself — the exact bug class described in the source report (single-call critical state change instead of an approve/claim two-step pattern).

### Finding Description
`transfer_to_new_account` performs all of the following irrevocably in one call:
1. Validates the old account isn't in a flashloan/receivership/order-execution state and has no active orders. [3](#0-2) 
2. Initializes a brand-new account with `ctx.accounts.new_authority.key()` as its authority and copies over the entire `lending_account` (all balances/positions). [4](#0-3) [5](#0-4) 
3. Permanently disables the old account, zeroing its `lending_account` and marking `ACCOUNT_DISABLED`, with `migrated_to` set — a state that is explicitly checked to prevent any second migration attempt (`AccountAlreadyMigrated`). [6](#0-5) [7](#0-6) 

The `new_authority` account itself is an `UncheckedAccount` with an explicit developer-added warning that it is "completely unchecked": [2](#0-1) 

There is no `pending_authority` / `accept_transfer` two-step design (analogous to `approve`/`transferFrom`) that would require the `new_authority` to sign a claim transaction before the migration is finalized. Once the transaction lands, the old account is disabled forever and the new account (all deposits/borrows) belongs exclusively to whatever address was placed in `new_authority` — correct or not. The off-chain CLI helper only guards against the zero-pubkey case, and only client-side: [8](#0-7) 
It performs no on-chain equivalent check, and does nothing to protect against a wrong (but non-zero) address, which is the exact class of mistake described in the source report.

The test suite's own comment acknowledges the design risk directly: *"Here the user moves authority to some new wallet. WARN: User picks the new authority with no restrictions!"* [9](#0-8) 

### Impact Explanation
If the account authority (an ordinary, unprivileged user) mistypes, copy-pastes wrong, or is tricked by a malicious front-end/dApp into supplying an incorrect `new_authority` address, all of that user's collateral and borrow positions are migrated to that address in one atomic, irreversible instruction. The old account is simultaneously and permanently disabled (`ACCOUNT_DISABLED`, `migrated_to` set, `lending_account` zeroed), and the protocol explicitly rejects any attempt to retry or undo the migration (`AccountAlreadyMigrated`). This results in a permanent loss of access to funds for the original user — the funds are not destroyed, but control passes irrevocably to whatever address was specified, matching the "permanent lock/freeze" and "unauthorized transfer" impact categories: the resulting new account's authority now has unilateral custody of assets the original owner never intended to relinquish to that address.

### Likelihood Explanation
This is directly reachable by any regular account holder using the normal, documented instruction path (`transfer_to_new_account` / `transfer_to_new_account_pda`), requiring no privileged role. Given how common address-copy mistakes and malicious-frontend address substitution attacks are in the broader ecosystem (the same threat model the original report calls out for Alice), and given the developer's own explicit "unchecked"/"no restrictions" warnings in both code comments and tests, this is a realistic and easily triggered failure mode, not a purely theoretical one.

### Recommendation
Implement a two-step transfer for `transfer_to_new_account`/`transfer_to_new_account_pda`:
1. First step: the current authority proposes/stages a transfer by writing an intended `new_authority` (or a pending-migration record) without finalizing the state change.
2. Second step: require the `new_authority` to sign a claim/accept instruction that finalizes the migration (copies the lending account and disables the old account), analogous to the `approve`→`transferFrom` pattern the original report recommends.
This ensures the destination address is provably reachable/controlled by a real signer before any irreversible custody change occurs, and gives the original owner a window to notice and cancel a mistaken/malicious transfer before finalization.

### Proof of Concept
1. User initializes a `MarginfiAccount` and deposits collateral / opens borrow positions.
2. User calls `transfer_to_new_account` intending to migrate to their own new wallet, but supplies a `new_authority` pubkey that is mistyped or was swapped by a compromised/malicious front-end. [10](#0-9) 
3. The instruction succeeds unconditionally: the new account is created with the incorrect `new_authority`, and the old account is immediately disabled (`ACCOUNT_DISABLED`) with `migrated_to` set, preventing retry. [11](#0-10) 
4. The user has now permanently and irrecoverably lost control of all deposited/borrowed positions to the incorrect address, with no on-chain mechanism to reclaim or reverse the transfer.

pub fn transfer_to_new_account(ctx: Context<TransferToNewAccount>) -> MarginfiResult {
    // Validate the global fee wallet and claim a nominal fee
    let group = ctx.accounts.group.load()?;
    check_eq!(
        ctx.accounts.global_fee_wallet.key(),
        group.fee_state_cache.global_fee_wallet,
        MarginfiError::InvalidFeeAta
    );
    anchor_lang::system_program::transfer(ctx.accounts.transfer_fee(), ACCOUNT_TRANSFER_FEE)?;

    let mut old_account = ctx.accounts.old_marginfi_account.load_mut()?;

    check!(
        !old_account.get_flag(ACCOUNT_IN_FLASHLOAN),
        MarginfiError::AccountInFlashloan
    );

    check!(
        !old_account.get_flag(ACCOUNT_IN_RECEIVERSHIP),
        MarginfiError::ForbiddenIx
    );

    check!(
        !old_account.get_flag(ACCOUNT_IN_ORDER_EXECUTION),
        MarginfiError::ForbiddenIx
    );

    check!(
        old_account.active_orders == 0,
        MarginfiError::IllegalAction,
        "Close all active orders before transfer"
    );

    // Prevent multiple migrations from the same account
    check_eq!(
        old_account.migrated_to,
        Pubkey::default(),
        MarginfiError::AccountAlreadyMigrated
    );

    let mut new_account = ctx.accounts.new_marginfi_account.load_init()?;
    let current_timestamp = Clock::get()?.unix_timestamp as u64;
    initialize_migrated_account(
        &mut new_account,
        &old_account,
        ctx.accounts.new_authority.key(),
        current_timestamp,
        ctx.accounts.old_marginfi_account.key(),
    );

    finalize_migrated_old_account(
        &mut old_account,
        ctx.accounts.new_marginfi_account.key(),
        current_timestamp,
    );

    emit!(MarginfiAccountTransferToNewAccount {
        header: AccountEventHeader {
            signer: Some(ctx.accounts.authority.key()),
            marginfi_account: ctx.accounts.new_marginfi_account.key(),
            marginfi_account_authority: ctx.accounts.new_authority.key(),
            marginfi_group: ctx.accounts.group.key(),
        },
        old_account: ctx.accounts.old_marginfi_account.key(),
        old_account_authority: ctx.accounts.authority.key(),
        new_account_authority: ctx.accounts.new_authority.key(),
    });

    Ok(())
}
