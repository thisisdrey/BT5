### Title
`StackerDBTx::try_replace_chunk` never enforces the configured `write_freq`, allowing unauthenticated write-frequency-limit bypass on StackerDB slots - ([File: stackslib/src/net/stackerdb/db.rs])

### Summary
The StackerDB replica's write path, `StackerDBTx::try_replace_chunk`, validates chunk size, slot signer, staleness, and `max_writes`, but never checks the smart-contract-configured `write_freq` (minimum wall-clock interval between writes to the same slot). The `Error::TooFrequentSlotWrites` variant exists but is never constructed anywhere in the codebase, meaning the "minimum interval between updates" guarantee promised by the StackerDB control-plane contract (`write_freq`) is not enforced at the actual storage layer for either HTTP-submitted chunks or P2P-synced chunks.

### Finding Description
`StackerDBConfig::write_freq` is documented as "minimum wall-clock time between writes to the same slot" [1](#0-0) . It is read from the controlling smart contract and stored per-DB [2](#0-1) .

The only place `write_freq` is actually consulted is in `StackerDBSync::make_chunk_request_schedule`, which uses it purely to decide whether the *local sync engine* should bother *fetching* a chunk from a peer [3](#0-2) . This is a scheduling heuristic on the read/fetch side, not an enforcement gate on the write/store side.

The actual write path, `StackerDBTx::try_replace_chunk`, performs these checks in order: chunk-size cap, signer verification, staleness (`slot_version <= slot_validation.version`), and `max_writes` — but at no point checks `slot_validation.write_time` against `self.config.write_freq` before calling `insert_chunk`: [4](#0-3) .

`insert_chunk` unconditionally updates `write_time` to the current time on every accepted write [5](#0-4) , but nothing reads that stored `write_time` back during validation to reject overly-frequent writes.

This is confirmed by the fact that `net_error::TooFrequentSlotWrites` is defined (with a `Display` implementation) in `stackslib/src/net/mod.rs`, but a repo-wide search shows it is **never constructed** anywhere — it's dead code: [6](#0-5) .

Both write entry points funnel into this unguarded function:
- The HTTP `POST /v2/stackerdb/:address/:contract/chunks` handler calls `tx.try_replace_chunk(...)` directly with only `StaleChunk`, `NoSuchSlot`, `BadSlotSigner`, `StackerDBChunkTooBig`, and `TooManySlotWrites` mapped to ack error codes — there is no frequency-based rejection path at all [7](#0-6) .
- The P2P relay path, which stores chunks obtained from peer sync results, also calls `tx.try_replace_chunk(&sc, &md, &chunk.data)` with no separate frequency check [8](#0-7) .
- `validate_received_chunk`, used to validate pushed/downloaded chunks before storage, explicitly documents that it "does not check write frequency, since the caller has different ways of doing this" [9](#0-8)  — but as shown above, the actual storage function (`try_replace_chunk`) that the caller relies on also does not check it.

So the equality that should hold — "a write is only accepted if `now - slot.write_time >= config.write_freq`" — is never evaluated anywhere in the storage/commit path. Any signer authorized to write to a slot can submit updates back-to-back with no minimum spacing, regardless of what `write-freq` the smart contract configures.

### Impact Explanation
This breaks a control-plane invariant meant to rate-limit slot updates (e.g., to give the network time to converge/replicate between updates, or to prevent a signer from rapidly overwriting state to win a race against slower observers/replicators). Because `write_freq` is silently unenforced, any legitimate slot owner (not even requiring an unauthorized party) can write at unbounded frequency, defeating the anti-front-running/anti-thrashing protection the contract author intended when setting a non-zero `write-freq`. This does not require the node's private key or another party's key — only the slot's own designated signer, which is an expected "remote, authorized-for-that-slot" actor whose behavior is supposed to be bounded by the contract-declared interval. This falls into the "bounded compute DoS on read/replication" / "steering a node off the tip via false inventory" category loosely, but more precisely it is a broken write-rate invariant that other nodes' StackerDB sync/inventory logic implicitly assumes holds (since the fetch-side skip logic in `make_chunk_request_schedule` assumes writers respect `write_freq`, but writers are never actually forced to).

### Likelihood Explanation
High likelihood of triggering: no special conditions are needed beyond having a valid signature for an owned slot (the normal, expected way to write to a StackerDB). Any application relying on `write-freq` from its control contract for rate-limiting/anti-abuse purposes is silently unprotected. The bug requires no race condition or timing trick — it's a straightforward missing check reachable by every write.

### Recommendation
In `StackerDBTx::try_replace_chunk` (`stackslib/src/net/stackerdb/db.rs`), before calling `insert_chunk`, fetch `slot_validation.write_time` and compare `get_epoch_time_secs()` against `slot_validation.write_time + self.config.write_freq`; if the elapsed time is insufficient, return `Err(net_error::TooFrequentSlotWrites(deadline))` (the variant already exists but is unused). Ensure the HTTP handler in `stackslib/src/net/api/poststackerdbchunk.rs` maps this new error to an appropriate `StackerDBErrorCodes` variant (currently none exists for "too frequent"), and that `validate_received_chunk`/`process_stacker_db_chunks` in the P2P path either perform the same check before calling `try_replace_chunk`, or rely on `try_replace_chunk` itself (once fixed) to reject too-frequent writes uniformly across both HTTP and P2P ingestion paths.

### Proof of Concept
1. Configure a StackerDB smart contract with `write-freq: u10` (10-second minimum interval) for a given slot signer.
2. As the slot owner, submit `POST /v2/stackerdb/:address/:contract/chunks` with a validly signed chunk at version `N`; it is accepted and `write_time` is updated to now.
3. Immediately submit a second validly signed chunk at version `N+1` for the same slot (well within the configured 10-second window).
4. Because `try_replace_chunk` (`stackslib/src/net/stackerdb/db.rs:400-438`) never checks `write_freq`/`write_time`, the second write is accepted with `accepted: true`, despite violating the contract-configured 10-second minimum interval — demonstrating the enforcement gap.

    /// Add or replace a chunk for a given reward cycle, if it is valid
    /// Otherwise, this errors out with Error::StaleChunk
    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
