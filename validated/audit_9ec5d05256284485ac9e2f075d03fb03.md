### Title
Missing self-reference check in `LinkRepositoryToObjectPool` causes a repository to corrupt/destroy its own bitmap and alternates state when object pool == target repository - (File: `internal/gitaly/service/objectpool/link.go`)

### Summary
`LinkRepositoryToObjectPool` never validates that the `object_pool` repository and the `repository` field refer to different repositories, mirroring the root cause of the referenced Unlock `transferFrom` bug: a `from == to` self-referential input reaches destructive logic with no guard. When a caller supplies the same repository for both fields, the underlying `Link()` routine treats the repository as its own object pool, writing a self-referential `objects/info/alternates` entry and then unconditionally deleting the repository's own pack bitmap file.

### Finding Description
`LinkRepositoryToObjectPool` builds the pool and target repo directly from caller-supplied protobuf fields with no equality check: [1](#0-0) 

`poolForRequest`/`ExtractPool` similarly perform no cross-validation between `req.GetObjectPool().GetRepository()` and `req.GetRepository()`: [2](#0-1) 

The request is then passed into `objectpool.Link`, which computes the pool's path and the repo's path and only special-cases the "already linked" state - not the "pool equals repo" state: [3](#0-2) 

If `pool` and `repo` are the same repository, `getRelativeObjectPath` computes `filepath.Rel(repoPath/objects, poolPath)`, which resolves to `..`, producing the alternates entry `../objects` - i.e. the repository is told that its own object directory is its alternate: [4](#0-3) 

After writing that alternates file, `Link` unconditionally calls `removeMemberBitmaps(ctx, pool, repo)`. Since `pool.Path()` and `repo.Path()` are identical, `poolBitmaps` and `memberBitmaps` are computed from the exact same directory, so any bitmap files the repository already owns are deleted as if they were "duplicate member bitmaps": [5](#0-4) 

This is structurally the same bug class as the Unlock `transferFrom` finding: a mutating RPC/function that assumes source and destination are distinct entities, with no input validation rejecting the self-referential case, and that reaches destructive code once the assumption is violated.

### Impact Explanation
When `LinkRepositoryToObjectPool` is invoked with `repository == object_pool.repository`:
- The repository's `objects/info/alternates` file is rewritten to point at itself (`../objects`), corrupting its expected alternates/pool linkage semantics.
- Any existing pack bitmap for the repository is silently and irreversibly deleted via `os.Remove` in `removeMemberBitmaps`, since the "pool" and "member" bitmap sets are the same set.
- Because `DisconnectGitAlternates`/pool member accounting in Gitaly and Praefect all rely on the alternates file correctly identifying a *separate* object pool repository, this self-referential state can lead to inconsistent replication/reconciliation logic (e.g. `defaultReplicator.Replicate`'s object pool sync path) and to loss of bitmap-based performance optimizations for the affected repository.

This is a real, if narrower-impact, storage-corruption/DoS-of-optimization analog rather than pure metadata loss; the severity is lower than the original key-destruction bug (no permanent loss of Git objects/refs), but it is a genuine unvalidated self-reference reaching a destructive filesystem mutation.

### Likelihood Explanation
`LinkRepositoryToObjectPool` is a standard mutator RPC (`op_type: MUTATOR`) reachable by any caller with access to the `ObjectPoolService`, the same class of caller that legitimately invokes `CreateObjectPool`/`LinkRepositoryToObjectPool` as part of fork/pool-management workflows. Both the `repository` and `object_pool.repository` fields are attacker/caller-controlled RPC fields, and no code path (proto validation, `ExtractPool`, `poolForRequest`, or `Link`) checks for equality, so the misuse can be triggered by a single crafted RPC call with valid, existing repository identifiers. It requires operator/API misuse (accidental or malicious) similar to the original report's caveat that it "requires user error," but the necessary preconditions (existing repository, no other privileges) are the same threat model accepted in the analogous C4 report.

### Recommendation
Add an explicit guard in `LinkRepositoryToObjectPool` (or in `objectpool.Link`) rejecting the request when the target repository and the object pool's repository resolve to the same storage + relative path, analogous to the `storage.RepoPathEqual` check already used elsewhere in the codebase (e.g. in `FetchSourceBranch`): [6](#0-5) 

For example:
```go
if storage.RepoPathEqual(req.GetRepository(), req.GetObjectPool().GetRepository()) {
    return nil, structerr.NewInvalidArgument("repository cannot be linked to itself")
}
```

### Proof of Concept
1. Create a repository `R` on a storage.
2. Call `LinkRepositoryToObjectPool` with `Repository = R` and `ObjectPool.Repository = R` (same storage name and relative path).
3. Observe:
   - `R`'s `objects/info/alternates` file is written with content `../objects`, a self-referential alternate.
   - If `R` already had a pack bitmap (e.g., after `git repack -adb`), `removeMemberBitmaps` deletes it, since `poolPath == repoPath` makes `poolBitmaps == memberBitmaps`.

This mirrors the pattern verified via the existing `TestLink` test scaffolding (which validates bitmap removal for pool/member pairs) but was not exercised for the `pool == repo` case: [7](#0-6)

func (s *server) LinkRepositoryToObjectPool(ctx context.Context, req *gitalypb.LinkRepositoryToObjectPoolRequest) (*gitalypb.LinkRepositoryToObjectPoolResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	pool, err := s.poolForRequest(ctx, req)
	if err != nil {
		return nil, err
	}

	repo := s.localRepoFactory.Build(repository)

	if err := pool.Link(ctx, repo); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	return &gitalypb.LinkRepositoryToObjectPoolResponse{}, nil

	pool, err := objectpool.FromProto(ctx, s.logger, s.locator, s.gitCmdFactory, s.catfileCache, s.txManager, s.housekeepingManager, req.GetObjectPool())
	if err != nil {
		if errors.Is(err, objectpool.ErrInvalidPoolDir) {
			return nil, errInvalidPoolDir
		}

// removeMemberBitmaps removes packfile bitmaps from the member
// repository that just joined the pool. If Git finds two packfiles with
// bitmaps it will print a warning, which is visible to the end user
// during a Git clone. Our goal is to avoid that warning. In normal
// operation, the next 'git gc' or 'git repack -ad' on the member
// repository will remove its local bitmap file. In other words the
// situation we eventually converge to is that the pool may have a bitmap
// but none of its members will. With removeMemberBitmaps we try to
// change "eventually" to "immediately", so that users won't see the
// warning. https://gitlab.com/gitlab-org/gitaly/issues/1728
func removeMemberBitmaps(ctx context.Context, pool *localrepo.Repo, repo *localrepo.Repo) error {
	poolPath, err := pool.Path(ctx)
	if err != nil {
		return err
	}

	poolBitmaps, err := getBitmaps(poolPath)
	if err != nil {
		return err
	}
	if len(poolBitmaps) == 0 {
		return nil
	}

	repoPath, err := repo.Path(ctx)
	if err != nil {
		return err
	}

	memberBitmaps, err := getBitmaps(repoPath)
	if err != nil {
		return err
	}
	if len(memberBitmaps) == 0 {
		return nil
	}

	for _, bitmap := range memberBitmaps {
		if err := os.Remove(bitmap); err != nil && !os.IsNotExist(err) {
			return err
		}
	}

	return nil
}

func getRelativeObjectPath(ctx context.Context, pool, repo *localrepo.Repo) (string, error) {
	poolPath, err := pool.Path(ctx)
	if err != nil {
		return "", fmt.Errorf("getting object pool path: %w", err)
	}

	repoPath, err := repo.Path(ctx)
	if err != nil {
		return "", fmt.Errorf("getting repository path: %w", err)
	}

	relPath, err := filepath.Rel(filepath.Join(repoPath, "objects"), poolPath)
	if err != nil {
		return "", err
	}

	return filepath.Join(relPath, "objects"), nil
}
