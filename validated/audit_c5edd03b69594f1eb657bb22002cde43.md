### Title
Attacker-controlled precompile `data[0]` byte inflates `PrecompileSignatureDetails` cost/scheduling weight without any check against real instruction data size - ([File: runtime-transaction/src/signature_details.rs])

### Summary
`get_num_signatures_in_instruction` blindly reads `instruction.data[0]` as the signature count for `secp256k1`/`ed25519`/`secp256r1` precompile instructions with no verification that `instruction.data.len()` is actually large enough to hold that many signature-offset structures. This attacker-controlled value flows unchecked into `PrecompileSignatureDetails`, `TransactionSignatureDetails`, and ultimately `CostModel::get_signature_cost`/`cost_tracker`, which drive block-cost accounting and scheduling decisions long before the real (and cheap) precompile `verify()` rejection ever runs.

### Finding Description
`get_num_signatures_in_instruction` in `runtime-transaction/src/signature_details.rs` is: [1](#0-0) 
It performs `u64::from(instruction.data.first().copied().unwrap_or(0))` with **no cross-check** against `instruction.data.len()`. This is invoked from `PrecompileSignatureDetailsBuilder::process_instruction`, which is fed by `get_precompile_signature_details`/`InstructionMeta::try_new` during transaction sanitization: [2](#0-1) 
That, in turn, is called for every packet in `RuntimeTransaction::try_from`/`try_create`, i.e. right after a raw `VersionedTransaction` deserializes and passes basic sanitize checks (size ≤ `PACKET_DATA_SIZE`, instruction count/account count limits) — not after real precompile signature verification: [3](#0-2) [4](#0-3) 

The resulting `num_secp256k1_instruction_signatures`/`num_ed25519_instruction_signatures`/`num_secp256r1_instruction_signatures` counters are consumed by `CostModel::get_signature_cost`, which multiplies them by `SECP256K1_VERIFY_COST`/`ED25519_VERIFY_STRICT_COST`/`SECP256R1_VERIFY_COST` (up to `223*30=6690`, `80*30=2400`, `160*30=4800` CU per claimed signature): [5](#0-4) [6](#0-5) 
This total feeds `CostTracker::try_add`, which governs per-account and per-block CU limits used for scheduling/QoS/buffering decisions (`WouldExceedBlockMaxLimit`, `WouldExceedAccountMaxLimit`): [7](#0-6) 

Meanwhile, the actual precompile verification routines correctly bound-check the claimed count against real data length and reject cheaply with `InvalidInstructionDataSize`: [8](#0-7) [9](#0-8) 
This confirms the disproportion: the claimed count (up to 255 per instruction) can vastly exceed what the actual instruction data supports, yet the cost/scheduling accounting is computed from the claimed count before that cheap rejection ever executes. `sigverify_stage`'s `verify_packet` (`perf/src/sigverify.rs`) only checks the outer Ed25519 transaction signatures against the message — it does not inspect or bound precompile instruction data — so a transaction signed by a disposable, unfunded keypair with a 1–2 byte secp256k1/ed25519/secp256r1 instruction (`data[0] = 255`) passes sigverify and reaches sanitization/costing with the inflated claim intact.

### Impact Explanation
This is an underpriced/disproportionate pre-fee-collection cost model input (Agave bounty category: “DoS on Agave clients” / cost-model mispricing leading to scheduler/QoS distortion). An unstaked attacker can construct minimal-size transactions (few bytes of precompile instruction data) that are assigned CU costs up to `255 * 6690 ≈ 1.7M CU` per secp256k1 instruction (and similarly for ed25519/secp256r1), and can include multiple such instructions in one transaction (bounded only by `MAX_INSTRUCTION_TRACE_LENGTH`/packet size), multiplying the claimed cost far beyond anything the real, near-instant `InvalidInstructionDataSize` rejection performs. Because this inflated cost is computed and applied to the cost tracker/scheduler pipeline at sanitization time — prior to and independent of whether the fee payer can or will ever pay a fee (e.g., an unfunded fee payer causes the transaction to fail before real fees are collected) — an attacker can cheaply consume account/block cost budget slots and skew scheduler prioritization/buffering decisions relative to the near-zero genuine work performed.

### Likelihood Explanation
Highly feasible and repeatable: no staking, no valid signatures on the precompile data, and no funded fee payer are required. The attacker only needs a throwaway keypair to produce a valid outer transaction signature (cheap, unstaked) and can freely set `data[0] = 255` with minimal instruction data. This can be repeated across many transactions/connections from a single unstaked client hitting the public TPU port, since none of the existing checks (packet size sanitize, `MAX_INSTRUCTION_TRACE_LENGTH`, `MAX_ACCOUNTS_PER_INSTRUCTION`) validate the relationship between a precompile's `data[0]` count and its actual `data.len()`.

### Recommendation
In `get_num_signatures_in_instruction` (or in `PrecompileSignatureDetailsBuilder::process_instruction`), cap the reported signature count to what the instruction's actual `data.len()` can support for the given precompile's fixed per-signature offset-structure size (mirroring the `expected_data_size` bound check already present in `precompiles/src/secp256k1.rs` and `precompiles/src/ed25519.rs`), so the cost-model input can never exceed the real, verifiable work implied by the instruction's byte length.

### Proof of Concept
```rust
// runtime-transaction/src/signature_details.rs (test module)
#[test]
fn test_claimed_signature_count_exceeds_real_data_capacity() {
    let program_ids = [solana_sdk_ids::secp256k1_program::ID];
    // Only 1 byte of instruction data: data[0] = 255, no offset structs present.
    let instructions = [make_instruction(&program_ids, 0, &[255])];

    let signature_details = get_precompile_signature_details(instructions.into_iter());
    // BUG: claims 255 signatures for a 1-byte instruction.
    assert_eq!(signature_details.num_secp256k1_instruction_signatures, 255);

    // Real precompile verification rejects almost immediately.
    let result = agave_precompiles::secp256k1::verify(
        &[255u8],
        &[&[255u8]],
        &agave_feature_set::FeatureSet::all_enabled(),
    );
    assert_eq!(result, Err(solana_precompile_error::PrecompileError::InvalidInstructionDataSize));

    // BOUNDED_RESOURCES invariant violated: claimed cost (255 * SECP256K1_VERIFY_COST)
    // vastly exceeds real work (a single length check).
    let claimed_cost = 255u64 * solana_cost_model::block_cost_limits::SECP256K1_VERIFY_COST;
    assert!(claimed_cost > 1_000_000, "claimed cost {claimed_cost} grossly exceeds real O(1) rejection work");
}
```
Expected: the first assertion demonstrates the unchecked claim of 255 signatures from a 1-byte instruction; the second demonstrates the real verifier's cheap rejection; the third quantifies the gap that is fed into `CostModel::get_signature_cost`/`CostTracker::try_add` for scheduling and block-cost accounting.

    pub fn try_add(
        &mut self,
        tx_cost: &TransactionCost<impl TransactionWithMeta>,
    ) -> Result<UpdatedCosts, CostTrackerError> {
        let cost = tx_cost.sum();

        if self.block_cost().saturating_add(cost) > self.limits.block_cost {
            // check against the total package cost
            return Err(CostTrackerError::WouldExceedBlockMaxLimit);
        }

        // check if the transaction itself is more costly than the account_cost_limit
        if cost > self.limits.account_cost {
            return Err(CostTrackerError::WouldExceedAccountMaxLimit);
        }

        let allocated_accounts_data_size =
            self.allocated_accounts_data_size + Saturating(tx_cost.allocated_accounts_data_size());

        if allocated_accounts_data_size.0 > self.limits.allocated_data_size {
            return Err(CostTrackerError::WouldExceedAccountDataBlockLimit);
        }

        // Check each account against account_cost_limit and apply the cost in
        // the same lookup. On failure, undo the applied prefix.
        let mut updated_costliest_account_cost = 0;
        for (index, account_key) in tx_cost.writable_accounts().enumerate() {
            let new_account_cost = match self.cost_by_writable_accounts.entry(*account_key) {
                Entry::Occupied(mut entry) => {
                    let new_account_cost = entry.get().saturating_add(cost);
                    if new_account_cost > self.limits.account_cost {
                        None
                    } else {
                        *entry.get_mut() = new_account_cost;
                        Some(new_account_cost)
                    }
                }
                Entry::Vacant(entry) => {
                    // `cost <= limits.account_cost` was checked above, so an
                    // account without chained cost always fits
                    entry.insert(cost);
                    Some(cost)
                }
            };
            let Some(new_account_cost) = new_account_cost else {
                // the first `index` accounts were applied before this failure
                self.roll_back_applied_costs(tx_cost, cost, index);
                return Err(CostTrackerError::WouldExceedAccountMaxLimit);
            };
            updated_costliest_account_cost = updated_costliest_account_cost.max(new_account_cost);
        }
