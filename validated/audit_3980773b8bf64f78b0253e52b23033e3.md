Audit Report

## Title
`ERC20Transactor` credits/debits XCM holding by nominal transfer amount instead of verified balance delta, and its `ERC20Matcher` accepts any attacker-deployed `H160` contract as a valid asset, letting a malicious ERC20 fabricate unbacked `Erc20Credit` in XCM holding - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` invoke an arbitrary contract's `transfer()` via `pallet_revive::Pallet::<T>::bare_call` and, upon a decoded `true` return, unconditionally mint/burn the caller-supplied nominal `amount` as `Erc20Credit` in XCM `AssetsInHolding`, without verifying any actual balance change. The `Matcher` wired to this transactor on Asset Hub Westend, `assets_common::ERC20Matcher`, is built on `IsLocalAccountKey20`, which matches **any** 20-byte address location with no allowlist — meaning any account can deploy a trivial always-returns-`true` (or fee-on-transfer) contract and have it accepted as a legitimate `asset_id`.

## Finding Description
`withdraw_asset_with_surplus` extracts `(asset_id, amount)` via `Matcher::matches_fungibles(what)`, then calls `IERC20::transferCall { to: checking_address, value: amount }` on `asset_id` through `bare_call`, and on `is_success == true` mints `Erc20Credit(amount)` into holding — the nominal amount requested, not an observed balance delta [5](#0-4) . `deposit_asset_with_surplus` mirrors this on the debit side, transferring from the checking account to the beneficiary and trusting `Ok(true)` from the ABI-decoded return without any balance verification [6](#0-5) .

Critically, `ERC20Matcher = MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>` [1](#0-0)  uses `IsLocalAccountKey20`, whose `contains` implementation matches **any** local location shaped as `(0, [AccountKey20 { .. }])` — i.e., it accepts literally any 20-byte address as a valid matched asset, with no allowlist or registry check [2](#0-1) . This `ERC20Matcher` is the concrete `Matcher` used to instantiate `ERC20Transactor` in the live Asset Hub Westend runtime [3](#0-2) , and `ERC20Transactor` is a member of the `AssetTransactors` tuple actually driving the XCM executor for this chain [4](#0-3) .

Combining these two facts: any unprivileged user can (1) permissionlessly deploy a `pallet-revive` contract implementing `IERC20::transfer` that always returns `true` while performing no real balance change (or under-transferring, as with fee-on-transfer tokens), (2) reference that contract's address as an `AccountKey20` location in an XCM `Asset`, which `ERC20Matcher` accepts unconditionally, and (3) have `ERC20Transactor::withdraw_asset_with_surplus` mint `Erc20Credit(amount)` into `AssetsInHolding` purely because the call didn't revert and decoded to `true`, with no check that the `TransfersCheckingAccount` actually received `amount` tokens.

## Impact Explanation
This is an unbacked-mint vulnerability: an attacker can fabricate `Erc20Credit` in XCM holding with no real value ever transferred to the `TransfersCheckingAccount`, then use `DepositAsset` within the same XCM program to move this fabricated credit to an arbitrary beneficiary — realizing unbacked value directly. This matches the "theft or unbacked mint or unlock" impact class and violates the value-conservation invariant for asset transactors.

## Likelihood Explanation
Fully feasible and repeatable by an unprivileged attacker: contract deployment via `pallet-revive` is a public capability, and `ERC20Matcher`'s underlying `IsLocalAccountKey20` filter imposes no allowlist — any deployed contract address is accepted as a matched asset by the transactor used in the live Asset Hub Westend XCM configuration.

## Recommendation
- After each successful `bare_call` transfer, read back the actual `balanceOf` of the source/checking account and/or destination before and after the call, and credit/debit XCM holding with the verified delta rather than the nominal `amount`.
- Restrict the `Matcher` for `ERC20Transactor` to a governance-curated allowlist of vetted, standards-compliant, non-fee-on-transfer/non-rebasing contracts rather than accepting any `AccountKey20`-shaped location.
- Treat a `true` boolean return as necessary but not sufficient; reconcile against the observed balance change and reject/rollback if the delta doesn't match `amount`.

## Proof of Concept
1. Deploy a `pallet-revive` contract implementing `IERC20` where `transfer(address,uint256)` always returns `true` (ABI-encoded `0x...01`) without moving any internal balance.
2. Reference this contract's `H160` address as an `AccountKey20` location in an XCM `Asset`; `ERC20Matcher`'s `IsLocalAccountKey20` accepts it with no allowlist check.
3. Submit an XCM program invoking `WithdrawAsset` for this asset with a large `amount` from the attacker's own account.
4. `withdraw_asset_with_surplus` observes `did_revert() == false` and `abi_decode_returns_validate(...) == Ok(true)`, minting `Erc20Credit(amount)` into `AssetsInHolding` with no tokens actually held by `TransfersCheckingAccount`.
5. Follow with `DepositAsset` in the same program to move the fabricated `Erc20Credit` to an arbitrary beneficiary, completing the unbacked value transfer.

/// `Contains<Location>` implementation that matches locations with no parents,

pub struct IsLocalAccountKey20;
impl Contains<Location> for IsLocalAccountKey20 {
	fn contains(location: &Location) -> bool {
		matches!(location.unpack(), (0, [AccountKey20 { .. }]))
	}

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),

		}
	}
