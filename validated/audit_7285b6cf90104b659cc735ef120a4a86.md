### Title
Attacker can permanently stall a LayerZero path with an undeliverable destination gas limit - ([File: contracts/ProxyOFT.sol](contracts/ProxyOFT.sol))

### Summary
`ProxyOFT` exposes the inherited `sendFrom()` overload that accepts caller-controlled `_adapterParams`. Production deployment scripts enable `useCustomAdapterParams`, and the validation only enforces a per-destination minimum gas value, with no maximum or destination-chain block-gas cap. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
An unprivileged caller can invoke the raw `IOFTCoreUpgradeable.sendFrom()` function rather than the user-friendly wrapper. The call reaches `_send()`, which validates the adapter parameters, burns the sender’s synthetic tokens through `ProxyOFT._debitFrom()`, and forwards the caller-controlled adapter parameters unchanged to `lzEndpoint.send()`. [4](#0-3) [5](#0-4) [6](#0-5) 

The only gas check is:

```solidity
uint providedGasLimit = _getGasLimit(_adapterParams);
uint minGasLimit = minDstGasLookup[_dstChainId][_type] + _extraGas;
require(minGasLimit > 0, "LzApp: minGasLimit not set");
require(providedGasLimit >= minGasLimit, "LzApp: gas limit is too low");
``` [7](#0-6) 

There is no corresponding upper bound. The attacker can therefore select a destination gas limit above the destination chain’s per-block limit. LayerZero receives `_gasLimit` as the contract-execution budget and processes inbound packets by nonce. [8](#0-7) 

Metronome’s non-blocking receiver cannot rescue this case: `_blockingLzReceive()` can store only a packet that successfully reaches `lzReceive()` and then fails inside application execution. If the requested destination gas cannot fit in a block, the destination transaction cannot be included at all, so no `failedMessages` entry is created and `retryMessage()` is unavailable. [9](#0-8) [10](#0-9) 

### Impact Explanation
The attacker burns only their own synthetic-token amount—potentially dust—and pays the quoted LayerZero fee, but inserts an impossible-to-execute packet at the next ordered nonce for a supported source/destination pair. Subsequent user transfers on that pair remain queued behind the undeliverable nonce, temporarily freezing bridged funds and denying that bridge path. A privileged `forceResumeReceive()` may eventually skip the stuck packet, but that does not prevent the liveness failure. [11](#0-10) 

### Likelihood Explanation
The attack uses a public entry point and requires no privileged role, malicious endpoint, malicious relayer, forged remote, or governance action. Production deployment scripts explicitly set `useCustomAdapterParams` to `true`, while `setupOftPath()` configures only `minDstGasLookup`. [3](#0-2) [12](#0-11)  Bridging must merely be active and the chosen destination must be supported, which are the intended operating conditions checked by `_debitFrom()`. [13](#0-12) 

### Recommendation
Disable arbitrary adapter parameters for ordinary token transfers, or add a per-destination `maxDstGasLookup[dstChainId][packetType]` and require:

```solidity
minDstGas <= providedGasLimit <= maxDstGas
```

The safest fix is to make the raw `sendFrom()` overload use the same `lzBaseGasLimit()` adapter parameters as the wrapper, or override it to reject caller-supplied gas parameters. If custom parameters are retained, configure destination-specific maxima below each supported chain’s executable transaction/block limit and apply the check before burning tokens.

### Proof of Concept
The following Hardhat test can be added inside the existing `test/ProxyOFT.test.ts` `sendFrom` fixture, which already enables custom adapter parameters and configures `minDstGas`. It proves that Metronome accepts and forwards a destination gas limit above a hypothetical 10,000,000-gas destination block limit:

```typescript
it('forwards a destination gas limit above the destination block gas limit', async function () {
  const dstBlockGasLimit = 10_000_000
  const maliciousDstGas = dstBlockGasLimit + 1
  const amount = ethers.utils.parseEther('0.000001')

  const maliciousAdapterParams = ethers.utils.solidityPack(
    ['uint16', 'uint256'],
    [1, maliciousDstGas]
  )

  const toAddress = ethers.utils.solidityPack(['address'], [alice.address])
  const payload = ethers.utils.defaultAbiCoder.encode(
    ['uint16', 'bytes', 'uint256'],
    [PT_SEND, toAddress, amount]
  )
  const trustedRemote = await proxyOFT.trustedRemoteLookup(LZ_MAINNET_ID)

  await proxyOFT
    .connect(alice)
    ['sendFrom(address,uint16,bytes,uint256,address,address,bytes)'](
      alice.address,
      LZ_MAINNET_ID,
      toAddress,
      amount,
      alice.address,
      ethers.constants.AddressZero,
      maliciousAdapterParams,
      {value: 0}
    )

  expect(lzEndpoint.send).to.have.been.calledWith(
    LZ_MAINNET_ID,
    trustedRemote,
    payload,
    alice.address,
    ethers.constants.AddressZero,
    maliciousAdapterParams
  )
})
```

On a destination fork configured with a 10,000,000 block gas limit, a delivery transaction requesting `10,000,001` gas cannot be included. Consequently, `lzReceive()` is never reached, `_blockingLzReceive()` cannot store a failed message, and the ordered nonce remains pending.

    function retryMessage(uint16 _srcChainId, bytes calldata _srcAddress, uint64 _nonce, bytes calldata _payload) public payable virtual {
        // assert there is message to retry
        bytes32 payloadHash = failedMessages[_srcChainId][_srcAddress][_nonce];
        require(payloadHash != bytes32(0), "NonblockingLzApp: no stored message");
        require(keccak256(_payload) == payloadHash, "NonblockingLzApp: invalid payload");
        // clear the stored message
        failedMessages[_srcChainId][_srcAddress][_nonce] = bytes32(0);
        // execute the message. revert if it fails again
        _nonblockingLzReceive(_srcChainId, _srcAddress, _nonce, _payload);
        emit RetryMessageSuccess(_srcChainId, _srcAddress, _nonce, payloadHash);
