### Title
Outgoing receipts generated by successful actions (including `DeterministicStateInit`'s `deposit_refund`) are still forwarded even when the receipt-level `check_storage_stake` re-check fails and `state_update.rollback()` discards the receiver's account/state changes - ([File: runtime/runtime/src/lib.rs -> apply_action_receipt])

### Summary
`action_deterministic_state_init` (`runtime/runtime/src/deterministic_account_id.rs:59-91`) computes `deposit_refund` from `check_storage_stake` using the account's balance *at that point* in the action batch, and unconditionally pushes a `Receipt::new_balance_refund` into `result.new_receipts`. A later action in the same batch (e.g. a `FunctionCall` on the freshly-deployed contract that issues an outgoing `Transfer` promise) can drain the account so that the receipt-level re-check at `apply_action_receipt` (`runtime/runtime/src/lib.rs:955-977`) fails with `LackBalanceForState`. On that failure only `state_update` (trie changes: account creation, balance, storage) is rolled back (`runtime/runtime/src/lib.rs:1024-1034`); the already-accumulated `result.new_receipts` — which include both the `deposit_refund` receipt and any promise/transfer receipts produced by the drain — are converted to `receipt_ids` and forwarded via `receipt_sink.forward_or_buffer_receipt` unconditionally (`runtime/runtime/src/lib.rs:1140-1184`), regardless of `result.result`.

### Finding Description
The exploit path traced through the code:
1. `action_deterministic_state_init` computes `deposit_refund` from `check_storage_stake(account, account.amount(), ...)` mid-batch and pushes a refund receipt into `result.new_receipts` [1](#0-0) .
2. All actions of a receipt execute sequentially against the same account and are merged into one `ActionReceiptResult`; a subsequent `FunctionCall` action in the same batch (invoking the just-deployed contract) can create an outgoing `Transfer` promise that drains the account's real balance before the loop completes [2](#0-1) .
3. After the action loop, `apply_action_receipt` re-checks `check_storage_stake` on the final `account.amount()`; if the drain leaves insufficient balance, `result.result` is set to `Err(LackBalanceForState)` [3](#0-2) .
4. On `Err`, only `state_update.rollback()` runs, discarding trie mutations (account creation/balance/storage) [4](#0-3) .
5. `result.new_receipts` — a plain in-memory `Vec` independent of the trie `state_update`, already populated by the successful `DeterministicStateInit` (`deposit_refund`) and `FunctionCall` (drain-transfer promise) actions — is converted into `receipt_ids` and forwarded as real outgoing receipts with no gating on `result.result` [5](#0-4) .

The consequence is that both the `deposit_refund` and the drain-transfer receipts are dispatched to the network even though the state changes that were supposed to back them (account creation, balance debit) never got committed to the trie. This lets the never-created account's pre-funded balance (from an earlier, separately-committed `Transfer`) be "spent" repeatedly: each failed `DeterministicStateInit` + drain attempt rolls back the account state (so the pre-funding balance is untouched) but still emits the drain receipt, letting the attacker replay this to duplicate value.

### Impact Explanation
If confirmed, this is a token-duplication / theft-of-funds bug: an attacker can cause receipts carrying real NEAR value to be emitted and delivered to arbitrary accounts while the corresponding balance debit on the source account is rolled back and never actually applied, allowing repeated extraction of value from a single pre-funded balance. This matches the "token inflation or loss" bounty category.

### Likelihood Explanation
I was unable to fully verify two remaining points due to reaching the tool-call budget: (1) the exact semantics of `ActionReceiptResult::merge` (whether it could special-case discarding of a failing action's own new receipts — though this is largely moot here since the triggering failure occurs strictly *after* the loop, on already-fully-merged, all-succeeded results), and (2) the precise mechanics of how a `FunctionCall`-issued outgoing `Transfer` promise's deposit is deducted from the receiver account's real `amount()` in-memory versus persisted to `state_update`, which is necessary to confirm the account balance used in the final `check_storage_stake` check reflects the drain. The code I was able to read strongly supports the exploit (unconditional receipt forwarding at lines 1140-1184, rollback restricted to `state_update`), but this requires a runtime/test-loop integration test to conclusively confirm before treating it as proven.

### Recommendation
Gate the emission of `result.new_receipts` (other than the refund receipts computed specifically for the failure case in `refund_unspent_gas_and_deposits`) on `result.result.is_ok()`. On failure, only refund/gas receipts computed against the failed state should be sent; any receipts queued by individual actions that succeeded within a batch which is ultimately rejected by the receipt-level post-check must be discarded together with the `state_update.rollback()`.

### Proof of Concept
Runtime/test-loop integration test plan:
1. Deploy a global contract with a method `drain()` that issues `promise_batch_action_transfer` moving most of `env::account_balance()` to an attacker-controlled account.
2. Fund the not-yet-existing deterministic account (`0s...`) with a `Transfer` of e.g. 100 NEAR in a first, independently committed transaction; assert the account balance is now 100 NEAR.
3. Send a second transaction/receipt containing a batch: `[DeterministicStateInit(deposit=storage_requirement), FunctionCall("drain", deposit=0)]` targeting the same deterministic account, where `drain()` transfers e.g. 99 NEAR out, intentionally leaving the account below its post-deploy storage requirement.
4. Assert the transaction outcome is `Failure(LackBalanceForState)`.
5. Assert that the deterministic account does NOT exist afterward (or retains its pre-funded 100 NEAR, i.e., trie rollback occurred).
6. Assert whether the "drain" receipt (99 NEAR to the attacker account) was nonetheless delivered — if the attacker's account balance increased by 99 NEAR despite step 5 showing the source account's state was rolled back, this proves value was duplicated (the receipt was forwarded independent of the rollback), confirming the finding.
