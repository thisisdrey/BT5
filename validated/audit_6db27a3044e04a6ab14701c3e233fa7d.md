### Title
`SmartFarmingManager.flashRepay` enforces absolute post-operation health, blocking underwater users from partially deleveraging into a healthier position - ([File: contracts/SmartFarmingManager.sol](contracts/SmartFarmingManager.sol))

### Summary
Analogous to the Perennial `maxPendingMagnitude` issue — where a maintenance check evaluates a stale/worst-case position rather than whether the update improves solvency — `SmartFarmingManager.flashRepay` demands the final position be fully healthy (`_debtInUsd <= _issuableLimitInUsd`) instead of merely checking that the operation does not worsen the position. A user whose position is already below the collateral factor cannot use `flashRepay` to partially repay debt and improve health, because the step-5 check reverts with `PositionIsNotHealthy` unless the entire shortfall is cured in one call.

### Finding Description
`Pool.debtPositionOf` defines health as `_isHealthy = _debtInUsd <= _issuableLimitInUsd` (`contracts/Pool.sol:264`). `flashRepay` burns the user's `msdTOKEN` via `depositToken_.flashWithdraw` (which intentionally skips the `_revertIfLocked` check — `contracts/DepositToken.sol:245-250` and the note at `:530`), swaps the collateral for synth, repays debt, and then reverts if the position is not healthy (`contracts/SmartFarmingManager.sol:140-141`).

For an underwater account (`_debtInUsd > _issuableLimitInUsd`):

- `unlockedBalanceOf` returns 0 because `_issuableInUsd == 0` (`contracts/DepositToken.sol:392-397`), so `withdraw`/`transfer`/`withdrawFrom` are all blocked by `_revertIfLocked` (`contracts/DepositToken.sol:181`).
- `flashRepay` is the only path that lets the user repay debt using their own collateral without holding synth upfront. But a partial repayment that improves the collateralization ratio while staying below the CF still reverts at step 5, atomically rolling back the repay.

So any flashRepay that does not fully cure the position is impossible, even when it strictly reduces bad-debt risk. The check measures the absolute end state (like Perennial's `maxPendingMagnitude`) rather than the direction of the update (like the actual new magnitude), incorrectly blocking health-improving operations.

### Impact Explanation
Users with underwater positions are prevented from self-deleveraging through the only mechanism that does not require holding the synthetic asset. Their collateral remains locked in `Treasury` until either the position drifts back to health, the user acquires synth on the open market to `repay` directly, or a third-party liquidation occurs (which charges liquidation fees against the user). This is a temporary (potentially indefinite) freezing of user funds and a liveness break of a core protocol function.

### Likelihood Explanation
Requires the user's position to become unhealthy (collateral price decline or synth price increase) and for the user to be unable to fully cure in a single flashRepay (e.g., insufficient collateral remaining after withdraw fees/slippage, or swapper output cannot cover the full debt). Common in volatile markets — precisely when deleveraging is most needed. Not exploitable by an attacker for profit; the impact is self-inflicted liveness loss identical in character to the reference report.

### Recommendation
Compare pre- and post-operation health instead of requiring full health: snapshot `_debtInUsd / _depositInUsd` (or `_issuableInUsd` shortfall) before step 1, and at step 5 require that the post-operation ratio is strictly better (or that debt decreased and collateralization improved), rather than `!_isHealthy → revert`. Alternatively, allow the check to pass when `_debtInUsd` decreased relative to `_depositInUsd`.

### Proof of Concept
Fork test (Hardhat, mirroring `test/SmartFarmingManager.test.ts:225-318`):

```ts
// Setup: alice leverages vaDAI -> msUSD (deposit ~$150, debt ~$50)
await smartFarmingManager.connect(alice).leverage(
  vaDAI.address, msdVaDAI.address, msUSD.address, parseUnits('100', 18), parseEther('1.5'), 0)

// Drop collateral price so position is underwater
await masterOracle.updatePrice(vaDAI.address, toUSD('0.6')) // debt > issuableLimit
const { _isHealthy } = await pool.debtPositionOf(alice.address)
expect(_isHealthy).to.eq(false)

// Attempt partial flashRepay that would improve but not fully cure health
const tx = smartFarmingManager.connect(alice).flashRepay(
  msUSD.address, msdVaDAI.address, parseEther('20'), 0)

// Reverts even though the operation strictly reduces debt and improves the ratio
await expect(tx).revertedWithCustomError(smartFarmingManager, 'PositionIsNotHealthy')
```

The revert happens at `contracts/SmartFarmingManager.sol:141` after the repay already succeeded internally, proving that a health-improving update is incorrectly blocked by an absolute post-state check.
