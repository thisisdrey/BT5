### Title
Unauthenticated `POST /v2/transactions` lets any peer fill the uninstantiated-attachment cache with content never referenced by an on-chain `AttachmentInstance` - ([File: stackslib/src/net/atlas/db.rs])

### Summary
`AtlasDB::insert_uninstantiated_attachment` stores arbitrary attachment bytes keyed only by their own hash, with no check that a confirmed `AttachmentInstance.content_hash` exists for that hash. The only reachable code path that calls it, `RPCPostTransactionRequestHandler::try_handle_request` in `stackslib/src/net/api/posttransaction.rs`, is the unauthenticated `POST /v2/transactions` RPC endpoint, so any remote party who can produce a mempool-admissible `ContractCall` transaction can push distinct, never-to-be-referenced attachment blobs and force LRU eviction of legitimately inboxed attachments.

### Finding Description
The claimed equality — "for every `was_instantiated=0` row, some confirmed `AttachmentInstance.content_hash` equals `hash`" — does not hold. `insert_uninstantiated_attachment` bounds the table only by count/age: [1](#0-0) 

Eviction is purely LRU-by-`created_at` (`evict_k_oldest_uninstantiated_attachments`) or purely time-based (`evict_expired_uninstantiated_attachments`) — neither checks `attachment_instances.content_hash`: [2](#0-1) 

The only call site of `insert_uninstantiated_attachment` is the `/v2/transactions` RPC handler, reached when a client submits a `ContractCall` transaction with a JSON body containing an `attachment` field: [3](#0-2) 

This handler requires only that the transaction pass `mempool.submit`/`will_admit_mempool_tx` (valid signature, correct nonce, minimum fee, targets an existing public function) — none of which require the transaction to ever be mined, let alone to emit a `print` event that the Atlas event-processing logic in `stackslib/src/net/atlas/download.rs` would turn into a confirmed `AttachmentInstance`. The gating function `should_keep_attachment` only checks the target contract-id against `AtlasConfig.contracts` and the attachment size against `attachments_max_size` — it does not verify the `content_hash` matches any pending or confirmed `AttachmentInstance`. Consequently, an attacker holding a funded key can repeatedly POST distinct-content, distinct-hash attachments paired with valid low-fee `ContractCall` transactions targeting the BNS contract, filling the `attachments` table with `was_instantiated=0` rows that will never be matched by `check_attachment_instances` (`stackslib/src/net/atlas/download.rs:227-286`), since no instance with that `content_hash` was ever committed on-chain.

### Impact Explanation
Once `count_uninstantiated_attachments()` reaches `AtlasConfig.max_uninstantiated_attachments`, each new attacker-submitted attachment evicts the oldest uninstantiated row by `created_at` via `evict_k_oldest_uninstantiated_attachments`. Legitimately inboxed BNS zonefiles (submitted by honest users waiting for their `name-update`/`name-register` transaction to confirm) can be evicted before the corresponding `AttachmentInstance` is created on-chain and matched in `check_attachment_instances`, causing them to be lost and never resolved to the correct instance — an attachment/BNS mismatch, matching the "High" severity bucket in scope. This is repeatable indefinitely for the cost of nonce-incrementing, minimum-fee transactions.

### Likelihood Explanation
The attacker needs only: (1) network reachability to the target node's RPC port (no privileged role, no node secret), (2) a signing key for an account with enough balance to pay `MINIMUM_TX_FEE` and sequential nonces, and (3) knowledge that the target contract is in `AtlasConfig.contracts` (e.g., the well-known BNS contract). No collusion with the node operator or other peers is required. This is straightforward and cheap to repeat at scale, bounded only by nonce sequencing and mempool tx-chaining limits (`MAXIMUM_MEMPOOL_TX_CHAINING`), which an attacker can work around by using multiple funded accounts.

### Recommendation
Do not persist attachment content in `insert_uninstantiated_attachment` purely on the basis of an as-yet-unconfirmed mempool transaction's declared attachment. Instead, only accept/keep an "uninstantiated" attachment if there is already a pending, unresolved `AttachmentInstance` (tracked via `queue_attachment_instance`/`find_unresolved_attachment_instances`) whose `content_hash` matches the posted attachment's hash — mirroring the check already done in `check_attachment_instances` for the download path. Alternatively, require `should_keep_attachment` to look up `atlas_db.find_all_attachment_instances`/unresolved instances by content hash before calling `insert_uninstantiated_attachment`, so only attachments with a real (even if unconfirmed) on-chain instance reference are cached, and rely on the existing LRU/expiry logic only as a secondary bound.

### Proof of Concept
Rust test plan in `stackslib/src/net/atlas/tests.rs` (or a new `posttransaction` integration test):
1. Construct an `AtlasDB` with a small `max_uninstantiated_attachments` (e.g., 3) and no confirmed `AttachmentInstance` rows.
2. Call `AtlasDB::insert_uninstantiated_attachment` directly (simulating what the RPC handler does after `should_keep_attachment` passes) with 4 distinct `Attachment` values whose hashes are never inserted via `insert_attachment_instance`/`queue_attachment_instance`.
3. Assert `count_uninstantiated_attachments() == max_uninstantiated_attachments` and that the first (oldest) attachment is evicted (`find_uninstantiated_attachment` returns `None`) purely due to `created_at` ordering, with no corresponding `find_all_attachment_instances` result for any of the hashes ever existing.
4. Extend by inserting one more "legitimate" attachment that is evicted next, demonstrating that legitimately expected data (represented by an attachment whose hash *would* match a not-yet-created instance) can be pushed out by attacker-controlled unmatched attachments — confirming the fault at the boundary of `insert_uninstantiated_attachment`/`evict_k_oldest_uninstantiated_attachments` in `stackslib/src/net/atlas/db.rs:511-547`.

    pub fn insert_uninstantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        // Insert the new attachment
        let uninstantiated_attachments = self.count_uninstantiated_attachments()?;
        if uninstantiated_attachments >= self.atlas_config.max_uninstantiated_attachments {
            let to_delete =
                1 + uninstantiated_attachments - self.atlas_config.max_uninstantiated_attachments;
            self.evict_k_oldest_uninstantiated_attachments(to_delete)?;
        }

        let tx = self.tx_begin()?;
        let now = util::get_epoch_time_secs() as i64;
        let res = tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 0, ?)",
            params![
                attachment.hash(),
                attachment.content,
                now,
            ],
        );
        res.map_err(db_error::SqliteError)?;
        tx.commit().map_err(db_error::SqliteError)?;
        Ok(())
    }

    pub fn evict_k_oldest_uninstantiated_attachments(&mut self, k: u32) -> Result<(), db_error> {
        let tx = self.tx_begin()?;
        let res = tx.execute(
            "DELETE FROM attachments WHERE hash IN (SELECT hash FROM attachments WHERE was_instantiated = 0 ORDER BY created_at ASC LIMIT ?)",
            params![k],
        );
        res.map_err(db_error::SqliteError)?;
        tx.commit().map_err(db_error::SqliteError)?;
        Ok(())
    }

    pub fn evict_expired_uninstantiated_attachments(&mut self) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let cut_off = now - self.atlas_config.uninstantiated_attachments_expire_after as i64;
        let tx = self.tx_begin()?;
        let res = tx.execute(
            "DELETE FROM attachments WHERE was_instantiated = 0 AND created_at < ?",
            params![cut_off],
        );
        res.map_err(db_error::SqliteError)?;
        tx.commit().map_err(db_error::SqliteError)?;
        Ok(())
    }
