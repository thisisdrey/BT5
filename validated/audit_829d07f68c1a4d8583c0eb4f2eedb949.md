### Title
Second directory walk in `NewLeftoverFileMigration` fails on already-removed files, causing repository write transactions to abort - ([File: internal/gitaly/storage/storagemgr/partition/migration/leftover_file_migration.go])

### Summary
`NewLeftoverFileMigration` performs a first full directory walk that removes ("drains") every non-snapshot-filtered leftover file from the repository, including files under `objects/`. When a `.keep` file or a `logs` directory is encountered, it sets `needBackupObjectsDir = true` and performs a *second* walk over `relativePath/objects` to additionally link those files into the lost-and-found garbage folder. However, by the time this second walk runs, the first walk has already `os.Remove`d every non-excluded file under `objects/`, so the second walk's `linkToGarbageFolder` call on those same paths fails with "no such file or directory", aborting the whole migration (and thus the whole write transaction) with an error. This mirrors the reported dTRINITY pattern: draining a resource first ("transfers all remaining collateral"), then unconditionally trying to act on the same resource a second time ("attempts to transfer the user's entitled collateral"), which reverts/fails because the resource was already exhausted.

### Finding Description
The migration's `entryProcessingFn`, run during the first `storage.WalkDirectory` call over the whole repository tree, for every entry not matched by `snapshotFilter.Matches`:
1. Hard-links (or mkdir's) it into the lost-and-found (garbage) folder via `linkToGarbageFolder`.
2. Immediately calls `os.Remove(srcAbsPath)` to delete the original file/directory from the repository.
3. Records the removal in the transaction's FS layer via `tx.FS().RecordRemoval(path)`. [1](#0-0) 

While doing this walk, the code also detects whether a `.keep` file exists under `objects/pack` or whether a `logs` directory exists, setting `needBackupObjectsDir = true` in that case: [2](#0-1) 

If that flag is set, the code performs a **second** walk, this time scoped to `filepath.Join(relativePath, "objects")`, to link entries there into the garbage folder a second time: [3](#0-2) 

The critical flaw: the `snapshotFilter` (via `NewRegexSnapshotFilter`) only preserves a narrow whitelist of paths under `objects/` — loose object dirs matching `[0-9a-f]{2}/[0-9a-f]{38...}`, `objects/info`, `objects/info/alternates`, `objects/pack/multi-pack-index`, and packfiles matching `.pack|.idx|.rev|.bitmap`: [4](#0-3) 

Everything else under `objects/` that is *not* whitelisted — for example `.keep` files themselves, `.mtime` files, or any other leftover garbage file under `objects/pack` — is *not* matched by `snapshotFilter`, so it is removed by the first walk's `entryProcessingFn` via `os.Remove(srcAbsPath)`. When the second walk subsequently tries to `linkToGarbageFolder(srcAbsPath, ...)` on that same now-removed path (there's no re-check for existence or for whether it was already processed), `os.Link` fails with `os.ErrNotExist`, which is not handled as an ignorable error (only `os.IsExist` is tolerated): [5](#0-4) 

This causes `linkToGarbageFolder` to return an error, which propagates as `"backup objects dir: %w"` up through the second `storage.WalkDirectory` call, then as `"walking directory: %w"` out of the migration `Fn`, and finally as `"migrate repository: %w"` from `Migration.run`: [6](#0-5) 

Since this migration `Fn` is executed as part of a transaction's commit path (the WAL entry is being constructed for the repository being migrated), an error here fails the entire transaction commit — i.e., a normal repository write (e.g., a user's push/fetch/RPC call that triggers a repository's first WAL transaction after the migration is enabled) is aborted.

### Impact Explanation
This is a Denial-of-Service condition: any repository that (a) has not yet been migrated to the WAL/transaction feature, (b) contains a `.keep` file under `objects/pack` or a `logs` directory as leftover state, and (c) also contains any non-whitelisted leftover file/directory under `objects/` (e.g. an old `.mtime` companion file, stray temp files, or other legacy git housekeeping artifacts) will have its `NewLeftoverFileMigration` fail deterministically on the first write transaction after the migration is enabled. Because this failure occurs inside the migration function that runs as part of every future transaction commit for that repository (it re-runs until it succeeds and records the migration ID), the repository becomes permanently unable to commit writes through the transaction/WAL path until an administrator manually removes the offending non-whitelisted `objects/` files — effectively bricking the repository for ordinary users performing pushes, fetches with ref updates, or any other RPC that triggers a write transaction.

### Likelihood Explanation
This is reachable purely by ordinary repository state accumulated before the transaction feature/migration was enabled — no privileged access, malicious peer, or attacker action is required. Legacy repositories commonly retain `.keep` files (used by `git repack`/housekeeping to protect packs from GC) alongside other stray files under `objects/pack` (e.g., `.mtime` files used by some object-database implementations, or files left behind by interrupted repacks). Because `.keep` presence alone is sufficient to trigger `needBackupObjectsDir`, and any additional non-whitelisted file anywhere under `objects/` is sufficient to trigger the double-processing bug, the precondition set is plausible for real-world repositories and does not depend on any adversarial action.

### Recommendation
- Do not perform two independent, un-synchronized destructive walks over overlapping paths. Either:
  - Skip files in the second `objects/` walk that were already processed (and removed) in the first walk (e.g. track processed relative paths in a set and skip them), or
  - Merge the two walks into a single pass that both determines `needBackupObjectsDir` and performs the linking/removal in one traversal, or
  - In the second walk's callback, tolerate `os.ErrNotExist` from `linkToGarbageFolder`/`os.Link` the same way `os.ErrExist` is currently tolerated, since a missing source at that point simply means it was already migrated to the garbage folder.
- Add a test case where a `.keep` file coexists with a non-whitelisted extra file under `objects/` (e.g., `objects/pack/pack-x.mtime` or a stray file directly under `objects/`) to catch this regression.

### Proof of Concept
1. Create (or use a pre-transaction-feature) repository containing:
   - `objects/pack/pack-<id>.keep` (whitelist-excluded, but triggers `needBackupObjectsDir`)
   - Any additional non-whitelisted file under `objects/`, e.g. `objects/pack/pack-<id>.mtime` or `objects/some-garbage` (a directory/file not matched by any `regexIncludePatterns` entry).
2. Enable `featureflag.LeftoverMigration` and trigger any RPC that starts a write transaction against the repository (e.g., a normal push, or any other WAL-transaction-triggering RPC such as `RepositorySize`, as used in `leftover_file_migration_test.go`).
3. During transaction preparation, `NewLeftoverFileMigration`'s `Fn` runs:
   - The first `storage.WalkDirectory` walk removes `objects/pack/pack-<id>.mtime` (or `objects/some-garbage`) via `os.Remove`, since it doesn't match `snapshotFilter`.
   - `needBackupObjectsDir` becomes `true` due to the `.keep` file.
   - The second `storage.WalkDirectory` walk over `objects/` re-encounters — via `fs.WalkDir` semantics reading the directory tree from the underlying filesystem, prior to any removal being reflected there for entries not yet synced, or via re-listing of the (transaction-relative) directory contents — the already-removed path and attempts `os.Link`, which returns `os.ErrNotExist`.
   - This is returned up as an error, causing the transaction commit (and hence the user's push/RPC) to fail. [7](#0-6)
