### Title
`WriteRef` RPC bypasses pre-receive/update hooks and Rails access checks enforced by `OperationService` reference-update RPCs - (File: internal/gitaly/service/repository/write_ref.go)

### Summary
Gitaly exposes two parallel code paths capable of mutating the same underlying primitive — a Git reference. `OperationService` RPCs such as `UserUpdateBranch`, `UserCreateBranch`, `UserDeleteBranch`, and `UserCreateTag`/`UserDeleteTag` are explicitly documented as treating the reference update as untrusted and route every mutation through `updateReferenceWithHooks`/`UpdaterWithHooks.UpdateReference`, which invokes the `pre-receive` hook (Rails `/allowed` access check, custom hooks, branch-protection enforcement), the `update` hook, and the `reference-transaction` hook before committing. `RepositoryService.WriteRef`, however, performs the same class of operation — pointing an arbitrary reference (including `refs/heads/*`) at an arbitrary object — via `updateRef()` using `updateref.New()`/`u.Commit()` directly, with zero hook invocation and no call to the GitLab `Allowed` endpoint. This mirrors the reported bug class: one privileged code path enforces an invariant (here, access-control/branch-protection checks performed via hooks) while a second, equally reachable code path writes the same resource without any of those checks.

### Finding Description
`internal/gitaly/service/repository/write_ref.go` validates only syntactic properties of the request (`validateWriteRefRequest`: repository existence, revision hex format, `refs/` prefix) and then calls `updateRef()`, which directly builds a `git-update-ref` transaction and commits it: [1](#0-0) [2](#0-1) 

No `hook.Manager` is invoked anywhere in this file, unlike the `OperationService` equivalent. `UserUpdateBranch` instead calls `updateReferenceWithHooks`, which drives `UpdaterWithHooks.UpdateReference`. That function explicitly runs `PreReceiveHook` (which calls out to Rails' `Allowed` API and executes custom hooks such as push-rule/branch-protection enforcement), then `UpdateHook`, then the `reference-transaction` hook, before finally committing the ref update: [3](#0-2) [4](#0-3) [5](#0-4) 

`OperationService` itself documents this invariant at the proto level: "The user's operation is treated as untrusted. Any reference update is thus checked against GitLab's `/allowed` endpoint." [6](#0-5) 

`WriteRef` has no equivalent doc/guarantee and, critically, no equivalent enforcement code path — it can move `refs/heads/<protected-branch>` (or any other ref) to any resolvable object ID, or delete it, without the `pre-receive`/`update` hooks ever running. Because both RPCs are reachable via the exact same gRPC authentication mechanism (the shared Gitaly auth token used by all trusted callers, e.g. Rails/Workhorse/gitlab-shell), any caller with that standard credential — the same credential level used to legitimately invoke `UserUpdateBranch` on behalf of an ordinary Git push/merge/branch-update action — can instead invoke `WriteRef` to update the identical resource while completely sidestepping the invariant (access checks, branch protection, push rules, custom hooks) that the "correct" path enforces.

### Impact Explanation
An attacker or a misrouted/compromised internal caller can force-update or delete any reference (including protected branches or tags) in a repository, bypassing:
- GitLab access checks (`Allowed` endpoint) that enforce branch protection, push rules, and permission checks.
- Custom `pre-receive`/`update` hooks (e.g. secret scanning, commit-signing enforcement, compliance hooks).
- The `reference-transaction` hook used for auditing/replication bookkeeping.

This breaks the same invariant class as the RuniverseLand report: a "second minter" (here, `WriteRef`) can write to the same protected resource without going through the constraint-enforcing path (`OperationService`'s hook-gated updates), corrupting the intended security guarantee that all user-driven reference changes are checked.

### Likelihood Explanation
`WriteRef` is a standard, always-registered RPC on `RepositoryService` requiring only the same authentication as any other Gitaly RPC (no special elevated token type is defined in the auth model referenced in this codebase). Its validation (`validateWriteRefRequest`) does not distinguish protected branches from unprotected ones, nor does it require a `User` message or Rails access-check context — unlike every `OperationService` mutator, which mandates a `User` field and always performs the hook flow. Any client capable of driving a ref update at all (i.e., anything that could legitimately call `UserUpdateBranch`) can call `WriteRef` instead to skip enforcement, making this readily reachable without additional privilege escalation.

### Recommendation
Restrict `WriteRef` so it cannot silently substitute for hook-gated user-facing mutators, e.g.:
1. Require `WriteRef` to run the same `pre-receive`/`update`/`reference-transaction` hook sequence (via `UpdaterWithHooks`) whenever a `User` context is present or the target is a "generally reachable" ref such as `refs/heads/*`/`refs/tags/*`.
2. Alternatively, explicitly scope `WriteRef` to only affect internal-only reference namespaces (e.g. `refs/keep-around/*`, `HEAD`) that are not subject to GitLab branch-protection, and reject writes to `refs/heads/*`/`refs/tags/*` from this RPC.
3. Document and enforce (via request field or explicit check) that any RPC capable of mutating `refs/heads/*` must invoke the hook manager, consistent with the invariant already documented for `OperationService`.

### Proof of Concept
1. Obtain the standard Gitaly RPC credential normally used to call `OperationService.UserUpdateBranch` (or any other hook-gated mutator).
2. Instead of calling `UserUpdateBranch`, call `RepositoryService.WriteRef` with:
   - `Ref: "refs/heads/protected-branch"`
   - `Revision: <arbitrary-existing-object-id>`
3. `validateWriteRefRequest` only checks that the ref/revision are syntactically well-formed and the repository exists — see: [7](#0-6) 
4. `writeRef`/`updateRef` commits the reference update directly via `git-update-ref` with no call into `hook.Manager`, so no `pre-receive` (Rails `Allowed`), `update`, or `reference-transaction` hook executes — see: [8](#0-7) 
5. The protected branch is now force-updated/deleted, even though the equivalent `UserUpdateBranch` call against the same branch would have been rejected by Rails' access check or a custom hook.

func validateWriteRefRequest(ctx context.Context, locator storage.Locator, req *gitalypb.WriteRefRequest) error {
	if err := locator.ValidateRepository(ctx, req.GetRepository()); err != nil {
		return err
	}
	if err := git.ValidateRevision(req.GetRef()); err != nil {
		return fmt.Errorf("invalid ref: %w", err)
	}
	if err := git.ValidateRevision(req.GetRevision()); err != nil {
		return fmt.Errorf("invalid revision: %w", err)
	}
	if len(req.GetOldRevision()) > 0 {
		if err := git.ValidateRevision(req.GetOldRevision()); err != nil {
			return fmt.Errorf("invalid OldRevision: %w", err)
		}
	}

	if !bytes.Equal(req.GetRef(), []byte("HEAD")) && !bytes.HasPrefix(req.GetRef(), []byte("refs/")) {
		return fmt.Errorf("ref has to be a full reference")
	}
	return nil
}

func (s *Server) UserUpdateBranch(ctx context.Context, req *gitalypb.UserUpdateBranchRequest) (*gitalypb.UserUpdateBranchResponse, error) {
	// Validate the request
	if err := validateUserUpdateBranchGo(ctx, s.locator, req); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	repo := s.localRepoFactory.Build(req.GetRepository())

	objectHash, err := repo.ObjectHash(ctx)
	if err != nil {
		return nil, fmt.Errorf("detecting object hash: %w", err)
	}

	newOID, err := objectHash.FromHex(string(req.GetNewrev()))
	if err != nil {
		return nil, structerr.NewInternal("could not parse newrev: %w", err)
	}

	oldOID, err := objectHash.FromHex(string(req.GetOldrev()))
	if err != nil {
		return nil, structerr.NewInternal("could not parse oldrev: %w", err)
	}

	referenceName := git.NewReferenceNameFromBranchName(string(req.GetBranchName()))

	quarantineDir, _, cleanup, err := s.quarantinedRepo(ctx, req.GetRepository())
	if err != nil {
		return nil, err
	}
	defer cleanup()

	if err := s.updateReferenceWithHooks(ctx, req.GetRepository(), req.GetUser(), quarantineDir, referenceName, newOID, oldOID); err != nil {
		var customHookErr updateref.CustomHookError
		if errors.As(err, &customHookErr) {
			return &gitalypb.UserUpdateBranchResponse{
				PreReceiveError: customHookErr.Error(),
			}, nil
		}

		// An oddball response for compatibility with the old
		// Ruby code. The "Could not update..."  message is
		// exactly like the default updateRefError, except we
		// say "branch-name", not
		// "refs/heads/branch-name". See the
		// "Gitlab::Git::CommitError" case in the Ruby code.
		return nil, structerr.NewFailedPrecondition("Could not update %s. Please refresh and try again.", req.GetBranchName())
	}

		return structerr.NewInternal("getting repo path: %w", err)
	}

		gitObjectDirRel, gitAltObjectDirRel, err := getRelativeObjectDirs(repoPath, gitObjDir, gitAltObjDirs)
		if err != nil {
