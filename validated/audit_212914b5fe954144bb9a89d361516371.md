### Title
`vesting::distribute()` Permanently Blocked by Shareholder with Disabled Direct Coin Transfers — (`aptos-move/framework/aptos-framework/sources/vesting.move`)

---

### Summary

`vesting::distribute()` iterates over every shareholder in a single transaction and calls `aptos_account::deposit_coins<AptosCoin>` for each one. If any single recipient has explicitly disabled direct coin transfers (`set_allow_direct_coin_transfers(false)`) and has no `CoinStore<AptosCoin>`, the call aborts and the entire transaction reverts — permanently blocking every other shareholder from receiving their vested APT until privileged admin intervention.

---

### Finding Description

`distribute()` loops over all shareholders and calls `aptos_account::deposit_coins` for each: [1](#0-0) 

`aptos_account::deposit_coins` contains the following guard: [2](#0-1) 

If the recipient account exists, has no `CoinStore<AptosCoin>` (possible for accounts created post-FA-migration via `aptos_account::create_account`, which only creates a primary fungible store, not a `CoinStore`), and has called `set_allow_direct_coin_transfers(false)`, the function aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`. Because Move transactions are atomic, the abort rolls back the entire `distribute()` call — no shareholder receives anything.

The developers are explicitly aware of this failure mode for *beneficiaries* set after contract creation: `set_beneficiary` guards against it with: [3](#0-2) 

The comment reads: *"This is a requirement so distribute() wouldn't fail and block all other accounts from receiving APT if one beneficiary is not registered."*

However, **no equivalent check exists for the original shareholders** supplied to `create_vesting_contract`: [4](#0-3) 

Shareholders are added to the grant pool without any APT-registration assertion, leaving the contract permanently vulnerable to a single non-compliant shareholder.

---

### Impact Explanation

A single shareholder who:
1. Has no `CoinStore<AptosCoin>` (accounts created via `aptos_account::create_account` after FA migration only receive a primary fungible store — `register_apt` calls `ensure_primary_fungible_store_exists`, not `coin::register<AptosCoin>`), and
2. Has called `set_allow_direct_coin_transfers(false)`,

causes every call to `distribute()` (and `distribute_many()`, `terminate_vesting_contract()`) to revert. All other shareholders' vested APT is frozen inside the contract until the admin intervenes. If the admin is unavailable, the shareholder is a smart contract whose signer capability is lost, or the admin is the same party as the blocking shareholder, the freeze is effectively permanent.

---

### Likelihood Explanation

- Any shareholder can call `set_allow_direct_coin_transfers(false)` at any time — it is an unprivileged, permissionless transaction.
- New accounts created post-FA-migration do not automatically receive `CoinStore<AptosCoin>`, satisfying condition 2 without any extra action.
- The vesting contract supports up to 30 shareholders; a single malicious or misconfigured one is sufficient.
- The admin escape hatch (`set_beneficiary`) requires the new beneficiary to also be registered for APT, so the admin must know a suitable registered address and act promptly.

---

### Recommendation

Apply the same guard used in `set_beneficiary` to each shareholder at contract creation time:

```move
// In create_vesting_contract, inside the shareholders loop:
shareholders.for_each_ref(|shareholder| {
    let shareholder: address = *shareholder;
    assert_account_is_registered_for_apt(shareholder); // ADD THIS
    ...
});
```

Alternatively, replace `aptos_account::deposit_coins` in `distribute()` with a try-pattern that skips non-receivable addresses and accumulates their share for later claim, avoiding the all-or-nothing atomicity failure.

---

### Proof of Concept

1. Admin creates a vesting contract with two shareholders: `alice` (normal) and `bob` (attacker).
2. `bob` calls `aptos_account::set_allow_direct_coin_transfers(bob_signer, false)` and ensures he has no `CoinStore<AptosCoin>` (e.g., he was created post-FA-migration).
3. After the vesting cliff, anyone calls `vesting::distribute(contract_address)`.
4. The loop reaches `bob`; `aptos_account::deposit_coins(bob, share)` aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`.
5. The entire transaction reverts. `alice` receives nothing.
6. Every subsequent call to `distribute()` fails identically. `alice`'s vested APT is frozen until the admin calls `set_beneficiary` to redirect `bob`'s share — an action that requires admin availability and knowledge of the issue.
