## Analog Found

### Title
Missing validation rejecting the zero/burn address as a permission key in `AccountPermissionUpdateActuator` can permanently freeze an account - (File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java)

### Summary
The original Napier finding is that `TrancheFactory`'s constructor accepts a `management` address without rejecting `address(0)`, allowing a critical control address to be set to an unusable value. The analogous, unprivileged-transaction-reachable pattern in java-tron is in `AccountPermissionUpdateActuator`, the actuator behind the broadcastable `AccountPermissionUpdateContract`. When a user resets their account's `Owner`/`Active`/`Witness` permissions, every key address is validated only with `DecodeUtil.addressValid(...)`, which checks address length/prefix format but does not reject the "zero" TRON address (`0x41` followed by 20 zero bytes) or otherwise unreachable addresses. [1](#0-0) 

### Finding Description
`checkPermission` is invoked from `validate()` for the `Owner` permission (mandatory), `Witness` permission (if the account is a witness) and every `Active` permission supplied in the `AccountPermissionUpdateContract`: [2](#0-1) 

Inside `checkPermission`, each key's address is checked only for structural validity: [3](#0-2) 

`DecodeUtil.addressValid` (declared in `common/src/main/java/org/tron/common/utils/DecodeUtil.java`) performs a length/prefix format check; it does not perform any semantic check that would reject the all-zero body address or other addresses that no private key can ever control. I was not able to retrieve the full body of `DecodeUtil.addressValid` through the index to quote it directly (index size limits may be excluding it), so this specific claim about its internals should be verified against the actual file in a full checkout, but the actuator code itself confirms no additional ownership/reachability check is performed beyond `addressValid` before the key is persisted via `execute()`: [4](#0-3) 

Because the `Owner` permission is mandatory (`hasOwner()` check) and is the only permission type that can authorize future `AccountPermissionUpdateContract` transactions for that account, setting its sole key (or a majority-weight key) to the zero address with a satisfied threshold makes the account's owner permission permanently un-signable — no future permission update, and depending on active-permission configuration, no future spending transaction, can ever be authorized for that account again.

### Impact Explanation
This mirrors the "loss of control over critical contract functionality" impact of the original report, but is directly reachable from a single signed `AccountPermissionUpdateContract` transaction (no admin/witness/committee privilege required — any account holder can submit this against their own account, and if the account is later transferred custody or shared, this becomes an unauthorized-account-operation/permanent-freezing-of-funds vector). Once the `Owner` permission's controlling keys are exclusively zero/unreachable addresses, the account becomes permanently frozen — funds and control can never be recovered, satisfying the "permanent freezing of funds" acceptance criterion.

### Likelihood Explanation
Likelihood is Medium: it requires the transaction to be crafted (accidentally or via a malicious dApp/wallet tricking the user into signing an update with a zero-address key) but no special privilege, node access, or additional条件 beyond one signed transaction is needed. All other structural checks in `checkPermission` (`getKeysCount`, threshold, weight sum, distinctness) are enforced, but none of them address the specific case of an unrecoverable "zero" address, so the transaction validates and executes successfully.

### Recommendation
Add an explicit check in `checkPermission` (and/or in `DecodeUtil.addressValid`'s callers used for permission-critical paths) that rejects the reserved zero address (`0x41` + 20 zero bytes) as a permission key, in addition to the existing structural validation, e.g.:
```java
if (!DecodeUtil.addressValid(key.getAddress().toByteArray())
    || Arrays.equals(key.getAddress().toByteArray(), ZERO_ADDRESS)) {
  throw new ContractValidateException("key is not a validate address");
}
```

### Proof of Concept
1. Attacker/careless owner builds an `AccountPermissionUpdateContract` for `ownerAddress = A`.
2. Sets the `Owner` permission with a single `Key` whose `address` is the zero TRON address (`0x41` + 20×`0x00`) and `weight` ≥ `threshold`.
3. Submits the transaction; `AccountPermissionUpdateActuator.validate()` passes because `DecodeUtil.addressValid` only validates format/prefix/length (see `checkPermission`, lines 105-117 above).
4. `execute()` persists the new `Owner` permission on account `A` (lines 41-59 above).
5. From this point forward, no signature can ever satisfy the account's `Owner` permission threshold (the zero address has no discoverable private key), permanently freezing account `A`'s funds and any dependent `Active`/`Witness` permission changes.
