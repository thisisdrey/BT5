### Title
False StackerDB inventory advertisement before chunk commit in `handle_unsolicited_StackerDBPushChunk` - ([File: stackslib/src/net/stackerdb/mod.rs])

### Summary
`PeerNetwork::handle_unsolicited_StackerDBPushChunk` optimistically patches and replies with an updated `StackerDBChunkInv` (claiming the pushed chunk's `slot_version` is now locally available) *before* the chunk has actually been committed to the `StackerDBs` storage. The actual write (`try_replace_chunk`) only happens later and separately, when the message is forwarded to the relayer and processed via `process_pushed_stacker_db_chunks` → `process_stacker_db_chunks`. This creates a window/ordering gap in which the peer's advertised (served) inventory does not match its actually committed storage.

### Finding Description
`validate_received_chunk` at `stackslib/src/net/stackerdb/mod.rs:649-718` correctly checks signature, size, staleness, and max-writes, and is called from `handle_unsolicited_StackerDBPushChunk` (`stackslib/src/net/stackerdb/mod.rs:742-871`).

In the `StackerDBChunkInv` branch (lines 767-815):
```
*slot_version = chunk_data.chunk_data.slot_version;
``` [1](#0-0) 
this patches the in-memory inventory that is about to be sent back to the pushing peer as an acknowledgement/`StackerDBChunkInv`, and wakes up the sync state machine — **but it never calls `try_replace_chunk`/`insert_chunk` to actually persist the chunk.**

Further down, the comment at line 862 states:
```
// this is a reply to the pushed chunk, and we can store it right now (so don't buffer it)
``` [2](#0-1) 
yet the code that follows only sends the (already-patched) inventory reply; it performs no storage operation. The chunk is only forwarded to `unhandled_messages`/`pushed_stackerdb_chunks` (see `stackslib/src/net/mod.rs:2249-2254`) and gets durably written only later, in `Relayer::process_pushed_stacker_db_chunks` → `process_stacker_db_chunks` (`stackslib/src/net/relay.rs:2385-2467, 2469-2493`), called from `process_network_result` (`stackslib/src/net/relay.rs:2927-2933`).

That second, separate call to `try_replace_chunk` (`stackslib/src/net/stackerdb/db.rs:400-438`) re-validates and can legitimately fail — e.g. `StaleChunk` if a competing write for the same slot lands first, `NoSuchSlot` if the DB config/slot set changed between the two steps, or `TooManySlotWrites`. In all of these cases the chunk is silently dropped (`continue;` at line 2434), while the inventory that this node already told its peer about (claiming the new version is present) is never rolled back. The "served" state (the inventory ack) and the "committed" state (the on-disk StackerDB slot) can therefore diverge for a window of at least one relay-processing cycle, and permanently if the second-stage `try_replace_chunk` call fails.

### Impact Explanation
This breaks the "served vs. committed" invariant the report's bug-class targets: a node can advertise (serve, via `StackerDBChunkInv`) a `slot_version` it has not actually stored. Downstream peers that rely on this advertised inventory to decide what to request/skip (`make_StackerDBChunksInv_or_Nack`, `StackerDBSync` rarest/newest scheduling) may treat this peer as having the newest chunk, deprioritize other sources, and later find the peer cannot actually serve that version — degrading StackerDB replica availability/consistency for signer messages, block-proposal data, etc. This is a lower-severity variant of "serving non-canonical state as canonical" (the node serves an inventory claim that is not backed by committed data), reachable by any remote unauthenticated peer able to send a `StackerDBPushChunk`.

### Likelihood Explanation
Moderate to low. It requires: (1) a chunk arriving via unsolicited push while the storage-processing step for that same event batch has not yet run, and (2) the subsequent `try_replace_chunk` call to fail (stale/no-such-slot/too-many-writes) after the optimistic inventory patch was already sent. Under normal single-threaded network-result processing this window is small, but it is a genuine logic gap rather than a purely theoretical one, and is easily reachable by any peer that can push chunks with a valid signature (no privileged key required — only a signature matching an already-registered StackerDB signer slot, which for many StackerDB instances includes ordinary Stacks accounts).

### Recommendation
Only patch/send the updated `StackerDBChunkInv` after `try_replace_chunk` has actually succeeded (i.e., move the inventory-ack construction and the actual DB write into the same atomic step, similar to how `try_replace_chunk` is used in `process_stacker_db_chunks`), or explicitly document/guard that the ack is provisional and must not be treated as a durability guarantee by remote peers' scheduling logic.

### Proof of Concept
Not independently reproduced end-to-end (would require driving a race between `handle_unsolicited_StackerDBPushChunk`'s inventory patch and a concurrent `try_replace_chunk` failure in `process_stacker_db_chunks`); the code-level gap — inventory ack patched/sent without a corresponding successful storage call — is demonstrated directly by the cited source ranges in `stackslib/src/net/stackerdb/mod.rs:767-871` compared against the separate, later storage path in `stackslib/src/net/relay.rs:2385-2493`.
