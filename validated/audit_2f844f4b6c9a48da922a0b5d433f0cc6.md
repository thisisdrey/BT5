### Title
Uncontrolled memory allocation in TVM precompiles `ValidateMultiSign`/`BatchValidateSign` via unchecked ABI array-length words - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
CVE-2018-6869 describes an uncontrolled-memory-allocation crash in ZZIPlib's directory parser, where an attacker-supplied length field is used directly to size an allocation without validating it against the actual available data, causing an OOM/crash on a crafted input. java-tron's TVM precompiled contracts `ValidateMultiSign` and `BatchValidateSign` contain the same bug-class: they read a 32-byte "array length" word straight out of attacker-controlled `CALL` data and use it, unclamped, to allocate a Java array, before any bound check against the real payload size.

### Finding Description
`extractBytesArray`, `extractBytes32Array`, and `extractSigArray` all take the array length directly from the caller-supplied ABI words: [1](#0-0) 

`len = words[offset].intValueSafe()` can be as large as `Integer.MAX_VALUE` (2^31-1), as shown by `DataWord.intValueSafe()`: [2](#0-1) 

`ValidateMultiSign.execute()` calls `extractSigArray`/`extractBytesArray` with this attacker-controlled offset/length. The `MAX_SIZE` sanity check that bounds the length is only performed when `VMConfig.allowTvmSelfdestructRestriction()` is enabled; if that hard fork flag is not active, the code goes straight to `extractBytesArray(words, words[3].intValueSafe() / WORD_SIZE, rawData)` with no length validation at all: [3](#0-2) 

Critically, this call happens *before* the `try { ... } catch (Throwable t)` block that wraps the rest of the method (which starts at the account-processing section), so any `OutOfMemoryError` thrown while allocating `new byte[len][]` is not caught here.

`BatchValidateSign.doExecute()` has the same pattern; the `sigArraySize`/`addrArraySize` bound checks are also gated behind `VMConfig.allowTvmSelfdestructRestriction()`, and `extractBytes32Array` (called unconditionally, regardless of the flag) has no internal bound check of its own: [4](#0-3) 

Although `BatchValidateSign.execute()` wraps `doExecute` in `catch (Throwable t)`, that only prevents propagation upward — the huge array allocation attempt has already been made by the time the exception is caught, and repeated calls from many transactions/contracts can be used to apply sustained memory pressure to the node.

### Impact Explanation
Any account can deploy a contract, or call an existing one, that invokes the `validateMultiSign`/`batchValidateSign` TVM precompiles (reachable via ordinary `CALL` opcode with crafted `data`) supplying an ABI-encoded length word far larger than the actual payload. This causes the node executing the transaction to attempt a massive array allocation (`new byte[Integer.MAX_VALUE][]`), which can throw `OutOfMemoryError`. In `ValidateMultiSign` this error is uncaught at the point of allocation and propagates out of the precompile execution path into transaction/block application, which can crash or destabilize the node processing the transaction (denial of service) — the same "uncontrolled memory allocation and crash" bug class as CVE-2018-6869.

### Likelihood Explanation
The precompiles are reachable from any unprivileged, unsigned-in-advance contract call — no special permission is needed to invoke `validateMultiSign`/`batchValidateSign` from a smart contract. The bound checks are conditioned on a VMConfig hard-fork flag (`allowTvmSelfdestructRestriction`), so on any chain/fork state where that flag is not yet active the length is completely unchecked, making exploitation straightforward for anyone who can broadcast a contract-calling transaction.

### Recommendation
Validate the extracted array length against `MAX_SIZE`/the actual remaining `words.length` and reject with `DATA_FALSE`/`false` *before* calling `extractBytesArray`/`extractBytes32Array`/`extractSigArray`, unconditionally (not gated behind `allowTvmSelfdestructRestriction`). Additionally, harden `extractBytesArray`/`extractBytes32Array`/`extractSigArray` themselves to bound `len` against `words.length - offset - 1` and against a hard maximum before allocating, mirroring the `verifyLength` bound checks already used in `RLP.java`.

### Proof of Concept
Craft a contract call to the `ValidateMultiSign` precompile (address `0x0000...0011`, or the appropriate TVM precompile address) with ABI-encoded `ecrecover`-style data where:
- word[3] (signature array offset pointer) points to a word position,
- the word at that position (`words[offset]`, the declared array length) is set to `0x7fffffff` (Integer.MAX_VALUE),

and the chain/fork does not yet have `allowTvmSelfdestructRestriction` active. On execution, `extractBytesArray`/`extractSigArray` will attempt `new byte[0x7fffffff][]`, throwing an uncaught `OutOfMemoryError` during transaction execution.

    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();

    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();

          bytesLen);
    }
    return bytesArray;
  }
