## Analog Found: Reentrancy Guard Bypass for Value-Transferring `.transfer()`/`.send()` Calls in pallet-revive's EVM Interpreter

### Title
Broken stipend-detection heuristic grants unrestricted reentrancy to gas-limited `.transfer()`/`.send()` value calls in EVM compatibility layer - (File: `substrate/frame/revive/src/vm/evm/instructions/contract.rs`)

### Summary
The external report's core lesson is that Ethereum contracts historically treated `send()`/`transfer()` (2300-gas-stipend calls) as "safe" against reentrancy, in contrast to `call.value()` which forwards unlimited gas and enabled TheDAO hack. `pallet-revive`'s EVM interpreter reimplements this exact distinction via a `ReentrancyProtection` enum and a heuristic that inspects the raw `gas_limit` operand of the `CALL` opcode to decide whether to apply the stricter `AllowNext` guard. That heuristic is broken for the most common real-world case — non-zero-value `.transfer()`/`.send()` — silently downgrading it to `AllowReentry` (no protection), even though the same code path still restricts the callee to the stipend-only gas/weight budget.

### Finding Description
In `run_call` in `substrate/frame/revive/src/vm/evm/instructions/contract.rs`: [1](#0-0) 

```rust
let (add_stipend, reentracy) =
    match (value.is_zero(), gas_limit.try_into().is_ok_and(|limit: u64| limit == CALL_STIPEND))
    {
        (false, _) => (true, ReentrancyProtection::AllowReentry),
        // Heuristic: detect when solc passes `gas_limit = 2300` (the call stipend).
        // For zero-value transfer/send, solc injects `gas_limit = 2300` explicitly.
        (_, true) => (true, ReentrancyProtection::AllowNext),
        (_, _) => (false, ReentrancyProtection::AllowReentry),
    };
```

Per the project's own documentation of solc's code-generation behavior (`prdoc/stable2603/pr_11227.prdoc`), the compiler emits different `gas_limit` values on the EVM stack depending on the call:

| Solidity call | value | `gas_limit` on stack |
|---|---|---|
| `target.transfer(amount)`, amount>0 | >0 | `0` (EVM auto-adds 2300) |
| `target.send(amount)`, amount>0 | >0 | `0` (EVM auto-adds 2300) |
| `target.transfer(0)` / `target.send(0)` | 0 | `2300` (compiler injects explicitly) |
| `target.call{value: v}("")` | any | remaining gas (no stipend) |

Because the match's first arm `(false, _)` fires whenever `value.is_zero()` is `false` — i.e., for **every non-zero-value call, regardless of `gas_limit`** — the real-world `.transfer(amount)` / `.send(amount)` pattern (the exact pattern the original bug report recommends as the *safe* alternative to `call.value()`) always takes the `AllowReentry` branch. The `(_, true) => AllowNext` branch, which is the one meant to compensate for revive's different gas-to-weight scale (as documented on the `ReentrancyProtection` enum itself), is only reachable for the *zero-value* transfer/send case, which is a corner case with no practical security relevance.

Critically, `add_stipend = true` is still set on the `(false, _)` branch, so the callee's execution frame is still capped to the stipend-equivalent weight budget via `CallResources::from_ethereum_gas(gas_limit, add_stipend)`: [2](#0-1) 

The nested meter computation confirms the callee gets exactly `0 gas + stipend_weight`, i.e. the same restrictive budget the `AllowNext` protection was designed to backstop — but the `ReentrancyProtection::AllowReentry` value means the reentrancy-denial check in `Stack::call`/`Stack::instantiate` (`substrate/frame/revive/src/exec.rs`) is skipped entirely: [3](#0-2) 

The enum doc explicitly states the reason this explicit protection exists: [4](#0-3) 

> "...due to gas scale differences that guarantee does not automatically hold in revive and we enforce it explicitly here."

That explicit enforcement is exactly what is skipped for non-zero-value transfer/send.

### Impact Explanation
Solidity contracts ported to `pallet-revive`'s EVM mode that rely on `.transfer()`/`.send()` as a reentrancy guard (the historically-recommended, audited pattern directly referenced by the source bug report as the fix for the TheDAO-style `call.value()` vulnerability) get **no actual reentrancy protection** on-chain, even though the same contract behaves safely on real Ethereum. If the stipend-equivalent weight budget in revive is sufficient for the callee to perform a state-changing reentrant call back into the caller (plausible, since gas-to-weight conversion differs from Ethereum's precise gas costs), an attacker-controlled receiving contract can re-enter the caller mid-`.transfer()`/`.send()`, before the caller updates its own accounting state — the canonical checks-effects-interactions violation. This can drain balances/accounting state tracked in caller contract storage (e.g. reentrant withdraw patterns), causing fund loss for ported EVM contracts that rely on this widely-used "safe transfer" idiom.

### Likelihood Explanation
This is trivially reachable by any unprivileged account deploying two ordinary Solidity contracts (attacker contract with a `receive()`/fallback that re-enters, and a victim contract using the common `.transfer(amount)`/`.send(amount)` withdrawal pattern) and calling the victim's withdraw function — no validator, relayer, governance, or privileged actor is required. `.transfer()`/`.send()` for non-zero value is one of the most common Solidity idioms for outbound payments, so the affected surface is broad for any EVM-compatible contract migrated onto `pallet-revive`.

### Recommendation
Fix the heuristic in `run_call` so that non-zero-value calls with `gas_limit == 0` (the automatic-stipend case per EVM semantics) are also routed to `ReentrancyProtection::AllowNext`, matching the zero-value case, instead of unconditionally granting `AllowReentry` whenever `value` is non-zero. E.g.:
```rust
let (add_stipend, reentracy) = match (value.is_zero(), gas_limit_is_zero_or_stipend) {
    // value transferred and no/only-stipend gas requested -> stipend semantics
    (false, true) => (true, ReentrancyProtection::AllowNext),
    (false, false) => (true, ReentrancyProtection::AllowReentry),
    (true, is_2300) => (is_2300, if is_2300 { AllowNext } else { AllowReentry }),
};
```
Add regression tests mirroring `testTransferReentrancy`/`testSendReentrancy` in `Stipends.sol` but with non-zero `amount`, asserting that reentrant calls from the receiver are denied (`ReentranceDenied`), not merely gas-starved.

### Proof of Concept
1. Deploy `Victim` with a `mapping(address=>uint) balances` and:
```solidity
function withdraw(uint amount) external {
    balances[msg.sender] -= amount;      // effects... (or update-after pattern)
    payable(msg.sender).transfer(amount); // "safe" call per TheDAO postmortem
}
```
   (or the more classic vulnerable ordering: `transfer` before balance update, which is exactly what `.transfer()` was trusted to make safe).
2. Deploy `Attacker` with a `receive()` that calls back `Victim.withdraw(amount)` again.
3. Call `Attacker.attack()` which triggers `Victim.withdraw()`; on `pallet-revive` (EVM interpreter), trace `run_call`: `value != 0`, `gas_limit == 0` ⇒ `(false, _)` arm ⇒ `ReentrancyProtection::AllowReentry` is applied to `Ext::call`, so `self.allows_reentry(&dest)` never blocks the callback into `Victim`, permitting a second `withdraw` to execute inside the stipend-limited callback before/around the first call unwinds — reproducing the reentrancy the stipend was meant to prevent.
4. Compare against the `Stipends.sol` fixture's `testTransferReentrancy`, which only exercises the case where the attacker's stipend-limited call is expected to run out of gas; no fixture currently tests non-zero-value `.transfer()`/`.send()` reentrancy specifically for the `AllowReentry` misclassification path shown above.
