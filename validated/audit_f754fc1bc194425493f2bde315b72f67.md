### Title
Dust-transfer griefing fills victim's per-account token list, blocking new collateral deposits and debt issuance - ([File: contracts/DepositToken.sol])

### Summary
`DepositToken._transfer` unconditionally calls `Pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance goes from 0 to non-zero. `Pool.onlyIfAdditionWillNotReachMaxTokens` reverts once `debtTokensOfAccount.length + depositTokensOfAccount.length >= MAX_TOKENS_PER_USER` (30). Because `transfer`/`transferFrom` only validate the *sender's* unlocked balance, an attacker can permissionlessly dust-transfer 1 wei of many distinct deposit tokens to a victim, filling their account list until every subsequent mint/transfer of a *new* deposit token or issuance of a *new* debt token to that victim reverts — permanently, since the dust entries can never be removed by anyone but the victim (and removing requires a successful transfer out, which the victim can do, but each new token type added again re-fills the slot).

### Finding Description
- `DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` when the recipient previously held zero of that token [1](#0-0) .
- `Pool.addToDepositTokensOfAccount` is gated by `onlyIfAdditionWillNotReachMaxTokens`, which reverts `UserReachedMaxTokens` once the combined deposit+debt token count hits 30 [2](#0-1) [3](#0-2) .
- `DepositToken.transfer`/`transferFrom` only check `_revertIfLocked` on the *sender*; there is no opt-in or check on the recipient [4](#0-3) .
- `DepositToken._mint` has the same behavior, so `deposit(amount, onBehalfOf=victim)` also reverts for any collateral type the victim doesn't already hold [5](#0-4) .
- `DebtToken.issue` likewise calls `addToDebtTokensOfAccount`, blocking the victim from issuing any new synthetic.

### Impact Explanation
Once the victim's list is full: (1) they cannot deposit a new collateral type to rescue an unhealthy position — `deposit` reverts in `_mint` → forced liquidation and loss of the liquidation fee; (2) they cannot receive any new deposit token (transfers, seized collateral payouts, deposits on their behalf all revert); (3) they cannot issue any new synthetic debt. The attack requires only dust amounts of each listed deposit token, which the attacker can acquire by depositing minimal collateral themselves. This is a state-driven freeze of user funds/top-up capability, not a gas-bound loop DoS.

### Likelihood Explanation
Feasible by any unprivileged EOA using only public entry points (`DepositToken.transfer`). Cost is bounded by dust across ≤30 tokens. Partially mitigated by the number of distinct deposit/debt tokens actually registered in a deployed pool — the attack only fully locks an account if enough distinct tokens exist to reach the cap, and the victim can free slots by transferring dust out, making this a repeatable griefing/liquidation-forcing vector rather than a permanent lock.

### Recommendation
Only add a token to the recipient's account list on user-initiated actions (deposit/issue), not on inbound `transfer`/`transferFrom`/`seize`; or make `addTo*TokensOfAccount` non-reverting on cap-hit for transfer paths (skip the add instead of reverting the whole transfer).

### Proof of Concept
Hardhat sketch (mirroring the existing `UserReachedMaxTokens` test in `test/Pool.test.ts:1386`):
```ts
// attacker deposits dust of each listed collateral into distinct tokens,
// then for each DepositToken dt_i: dt_i.transfer(victim, 1)
// after 30 entries, any of these revert with UserReachedMaxTokens:
//   - newCollateralToken.deposit(amount, victim)
//   - anyListedDepositToken.transfer(victim, x) for a token victim doesn't hold
//   - debtToken.issue(...) minting a new synthetic to victim
```
Use a fork test against a deployed `Pool` plus its registered `DepositToken`s; assert `deposit(onBehalfOf=victim)` reverts and the victim cannot add collateral while their position is unhealthy.
