### Title
Disabled-collateral removal health check double-counts un-removed disabled-asset balance, allowing withdrawal past true collateralization limits - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
The `collateral-remove` function in `v0-4-market.clar` replicates the exact anti-pattern described in the external report: transaction verification for the "disabled collateral" removal path is buried inside deeply nested `let`/`if`/`asserts!` expressions rather than being encapsulated in a single, testable predicate, and this convolution hides an accounting error that lets a user withdraw a disabled-collateral asset while using its own un-removed balance as phantom backing for the health check.

### Finding Description
In `collateral-remove`, when the asset being withdrawn is *not* a normal collateral-enabled asset (`is-collateral-enabled` is `false`, i.e. `(get collateral asset)` is `false` at the protocol/asset-registry level), the code takes a separate branch: [1](#0-0) 

```
(let ((oracle-data (get oracle asset))
      (price (unwrap! (price-resolve oracle-data) ERR-DISABLED-COLLATERAL-PRICE-FAILED))
      (decimals (get decimals asset))
      (user-amount (find-collateral-amount (get collateral pos-full) asset-id))
      (disabled-notional (normalize (* user-amount price) decimals false))
      (removal-notional (normalize (* amount price) decimals true))
      (total-collateral-value (+ collateral-value disabled-notional)))
  (asserts! (>= total-collateral-value removal-notional) ERR-INSUFFICIENT-COLLATERAL)
  (is-healthy (- total-collateral-value removal-notional) debt-value current-ltvb))
```

`collateral-value` here is the notionally-valued sum of the position's *enabled* collateral only (from `get-notional-evaluation`), which does not include disabled-collateral assets because normal borrow/liquidate paths never let disabled-collateral back a loan. However, this branch computes `disabled-notional` as the **user's entire current balance** of the disabled asset (`user-amount`, from `find-collateral-amount` on the *full* pre-removal position), not just the `amount` being withdrawn. It then adds this entire disabled balance into `total-collateral-value`, subtracts only the `removal-notional` for the portion actually withdrawn, and passes the *inflated remainder* into `is-healthy`.

The net effect: any disabled-collateral units that remain in the position after a partial withdrawal are silently counted as if they were valid LTV-backing collateral for the post-removal health check, even though:
- This same disabled asset is never counted as collateral in `borrow` or `liquidate` (`get-notional-evaluation`/`get-assets` for those paths only value collateral through the normal enabled path), and
- The user can immediately follow up with further withdrawals or additional borrows once this artificially “healthy” state is recorded, since the disabled asset balance was never actually usable to satisfy debt in liquidation.

This is exactly the failure mode the external report describes: verification logic (“is this withdrawal safe?”) is scattered across a nested `if`/`let`/`asserts!` structure instead of a single well-defined predicate, and the obscurity directly produces an accounting inconsistency between what counts as collateral for withdrawal-health-checks versus what counts as collateral for borrow/liquidation health-checks.

### Impact Explanation
A user holding a disabled-collateral asset can exploit the inflated `total-collateral-value` to pass the post-removal health check for a *different* asset removal event in the same call, or to justify removing enabled collateral it wouldn't otherwise be able to remove while under debt, effectively unlocking value that should remain locked as collateral backing outstanding debt. Because disabled collateral is never actually seizable/valuable during liquidation (it's excluded from `get-notional-evaluation` in `liquidate`), a position that passes this check can end up with real collateral-to-debt backing below the LTV-borrow threshold, i.e., under-collateralized debt that cannot be fully recovered — this is a theft/freezing-of-funds class impact affecting depositors/protocol solvency (falls under "permanent freezing of funds" / "protocol insolvency" since bad debt becomes unbacked and must be socialized).

### Likelihood Explanation
Reaching this path only requires an ordinary user calling the public `collateral-remove` entry point on an asset whose registry flag `collateral` is `false` while the user also holds debt — no privileged role or DAO action is needed. The condition (`has-debt` true, `is-collateral-enabled` false) is a normal, reachable state for any account holding a disabled-collateral asset such as one that was later disabled by DAO governance while users still hold balances.

### Recommendation
Encapsulate collateral-removal health validation in a single, well-named predicate function (e.g., `verify-removal-health`) that takes the pre/post removal state and asset-enabled flag explicitly, and ensure that only the *portion of the disabled asset actually being retained is optionally counted, if counted at all* — ideally disabled-collateral assets should never contribute to the LTV health check for consistency with `borrow`/`liquidate`. At minimum, replace `disabled-notional` (full balance) with either zero, or the correctly-scoped remaining-balance value used consistently across all health-check code paths, and add dedicated unit tests asserting that disabled-collateral balances never inflate borrowing power.

### Proof of Concept
1. DAO disables `collateral` flag for asset `X` in `assets.clar` (a normal governance action; separately, an account already holds `X` and debt from before the flag change, or the flag was disabled after deposits).
2. Account has: enabled collateral worth `collateral-value`, debt worth `debt-value`, and holds `user-amount` units of disabled asset `X` worth `disabled-notional` in USD.
3. Account calls `collateral-remove` for asset `X` with `amount < user-amount` (partial withdrawal).
4. The health check computes `total-collateral-value = collateral-value + disabled-notional` (full balance, not just remaining) and checks `is-healthy(total-collateral-value - removal-notional, debt-value, current-ltvb)`.
5. Because the check retains most of `disabled-notional` (all except the withdrawn slice) as phantom backing, the check passes even though `collateral-value` (the only real LTV backing recognized by `borrow`/`liquidate`) alone would already fail `is-healthy` against `debt-value`.
6. Withdrawal succeeds, and the resulting position is under-collateralized per the protocol's real accounting used elsewhere (`get-notional-evaluation` in `borrow`/`liquidate`), producing unbacked debt. [2](#0-1)
