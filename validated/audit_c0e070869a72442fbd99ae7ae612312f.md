### Title
ERC20Transactor credits/debits nominal `amount` instead of actual ERC20 balance delta, allowing fee-on-transfer or transfer-hook tokens to desynchronize the shared checking account - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` never verify the actual ERC20 balance change of the shared `TransfersCheckingAccount`; they trust the nominal `amount` extracted from the XCM `Asset` and only check that `IERC20::transfer` returned `true`. Any ERC20 contract that does not move exactly `amount` tokens on a `transfer` call (fee-on-transfer, rebasing, deflationary-burn, or any token with transfer hooks) causes the XCM holding register to become unbacked relative to what the checking account actually possesses.

### Finding Description
`withdraw_asset_with_surplus` performs `IERC20::transferCall { to: checking_address, value: amount }` from the user's mapped address, and on success unconditionally mints holding credit for the full requested `amount`: [1](#0-0) 

`deposit_asset_with_surplus` does the mirror operation, transferring the *same nominal* `amount` out of `TransfersCheckingAccount` to the beneficiary, again relying solely on the boolean return value of `transfer`: [2](#0-1) 

At no point does the code read `balanceOf(checking_account)` before/after the call (unlike Sandclock's `_transferAndCheckUnderlying`, which at least detects the mismatch and reverts). Here there is no detection at all: if the token charges a transfer fee (or has any transfer hook that changes the delivered amount), `withdraw_asset_with_surplus` will still credit the XCM holding register with the full nominal `amount`, even though `TransfersCheckingAccount`'s real ERC20 balance increased by less. `ERC20TransfersCheckingAccount` is a single shared `PalletId`-derived account (`py/revch`) used for every ERC20 asset class matched by `assets_common::ERC20Matcher` across the whole runtime, as configured in: [3](#0-2) 

Because the shortfall is per-token and cumulative, and the account is shared across all users of that ERC20 asset class, the on-chain ledger (XCM holding register accounting) drifts away from the real balance held by the checking account.

### Impact Explanation
- **Public underpriced/broken work causing stalled processing**: once the checking account's real balance for a given ERC20 falls behind the sum of credited nominal amounts, subsequent `deposit_asset_with_surplus` calls for *other, unrelated* users of that same asset will revert with `"ERC20 contract transfer failed"` (insufficient balance in `TransfersCheckingAccount`), even though those users never withdrew any of the missing amount. This causes DoS of deposits/withdrawals for a public ERC20 asset class routed through a common infra account, matching the "public underpriced work that degrades block production or stalls bridge processing" and "permanent user-fund lock" impact categories.
- The bug is a genuine implementation flaw in the transactor logic (missing balance-delta verification), not a malicious-admin or malicious-relayer scenario — anyone can trigger it merely by owning and registering (or interacting with) a legitimately-deployed fee-on-transfer ERC20, then executing a normal `pallet_xcm::execute`/`send` withdraw+deposit sequence, which is exactly the permissionless entrypoint pattern the report seeks.

### Likelihood Explanation
Moderate: this is currently scoped to Asset Hub Westend testnet (`ERC20Transactor` wiring exists only there per `pr_7762.prdoc`), and requires an ERC20 contract with non-1:1 transfer semantics (fee-on-transfer, rebasing, or a hostile/broken transfer hook) to be matched by `assets_common::ERC20Matcher`. Given `pallet-revive` allows arbitrary contract deployment and any `AccountKey20` location can be referenced as an asset id in XCM (as demonstrated by the existing negative tests using deliberately non-conformant contracts, e.g. `smart_contract_does_not_return_bool_fails` and `expensive_erc20_runs_out_of_gas`), an attacker only needs to deploy such a contract and route a withdraw/deposit through it — no special privilege required.

### Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, read `IERC20::balanceOf(checking_account)` (or the counterparty) immediately before and after the `transfer` call, and use the observed delta — not the nominal `amount` — both for the credited `AssetsInHolding` and for erroring out (mirroring, and improving upon, Sandclock's `_transferAndCheckUnderlying` check) so that a mismatch is rejected rather than silently accepted as full-value credit.

### Proof of Concept
1. Deploy an ERC20 contract on Asset Hub (via `pallet-revive`) whose `transfer(to, amount)` deducts e.g. a 1% fee from `amount` before crediting `to`, but still returns `true`.
2. Register this contract's address as an XCM asset (`AccountKey20 { key: contract_addr, network: None }`), matched by `assets_common::ERC20Matcher`.
3. User A executes `withdraw_asset((AccountKey20{contract_addr}, 1000))` + `deposit_asset(..., beneficiary=B)` via `pallet_xcm::execute`, mirroring the pattern in `asset-hub-westend/tests/tests.rs:1931-1969`. The withdraw call transfers only 990 real tokens into `ERC20TransfersCheckingAccount`, but the executor credits holding with 1000, then successfully instructs the deposit of 1000 out of the checking account to B (spending 10 tokens that belong to other users' un-fee'd deposits, or reverting if the checking account is otherwise near-empty).
4. Repeat with multiple users of the same fee-on-transfer asset: eventually `deposit_asset_with_surplus` reverts with `"ERC20 contract transfer failed"` for a user who never interacted with the deficient token, demonstrating the shared checking account's real balance is insufficient to honor the accumulated (inflated) nominal credits.
