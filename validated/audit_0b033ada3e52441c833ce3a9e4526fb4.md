### Title
Unbounded ZIP central-directory sizes drive an out-of-bounds heap read/write in `TransientBytes::ReadEntryContents`/`DecompressEntryContents` - (File: `src/tools/singlejar/transient_bytes.h`)

### Summary
The external report describes `CIccSparseMatrix::CIccSparseMatrix` trusting attacker-supplied dimensions to size a heap allocation, then reading/writing past it (UAF/heap overflow/integer overflow). The closest reachable analog in this repo is Bazel's `singlejar` tool, which merges JAR/ZIP files as part of ordinary Java build actions. Its ZIP-parsing path (`InputJar`, `zip_headers.h` CDH/LH accessors, and `TransientBytes::ReadEntryContents`/`DecompressEntryContents` in `src/tools/singlejar/transient_bytes.h`) trusts size and offset fields taken directly from an attacker-supplied JAR's central directory and local file headers, with no bounds validation against the actual mapped file length before those values are used to drive `memcpy`/`inflate` calls into a heap buffer.

### Finding Description
`InputJar::LocateCentralDirectory` [1](#0-0)  validates that the central-directory offset/size are within the mapped file, but once past that, `TransientBytes::ReadEntryContents` copies `uncompressed_file_size` bytes directly from `lh->data()` based on values taken from the CDH/LH structures with no cross-check against the remaining bytes in the memory-mapped input file: [2](#0-1) 

Similarly, `DecompressEntryContents` trusts `compressed_file_size`/`uncompressed_file_size` from the (attacker-controlled) local/central headers to drive the inflate loop and to size the accumulated output buffer chunks: [3](#0-2) 

Unlike ijar's `InputZipFile::ProcessLocalFileEntry`/`EnsureRemaining`, which explicitly checks that declared field lengths do not exceed the remaining bytes in the mapped input before dereferencing them [4](#0-3) [5](#0-4) , singlejar's simpler `zip_headers.h` structures and `TransientBytes` consumer do not perform the equivalent remaining-length checks before using header-declared sizes to read `lh->data()` for `Append()`/`memcpy`-style buffer construction. A crafted JAR entry with a local/central header size field larger than the bytes actually available in the mapped file, or with a mismatched compressed/uncompressed size, can cause the read cursor to walk past the end of the memory-mapped input file (out-of-bounds heap read of mapped memory), and downstream integer-size mismatches between the claimed and actual sizes can desynchronize the incremental buffer bookkeeping in `TransientBytes` used later during `CompressOut`/`CopyOut` to write into the output-JAR buffer allocated with `malloc(deflated_buffer_size)` in `Concatenator::OutputEntry` [6](#0-5) .

### Impact Explanation
Because `singlejar` is invoked as an ordinary build action to merge JAR outputs (including third-party `.jar` dependencies pulled in via `java_import`/Maven-style rules), a malicious JAR published at a dependency URL (matching its own declared sha256, since the attacker controls the artifact from the start) is untrusted content that a victim's build consumes without any additional integrity check *inside* the ZIP format itself (ZIP headers are not covered by Bazel's download checksum semantics beyond the whole-file digest). If reachable, out-of-bounds reads of mapped file memory or corrupted internal buffer bookkeeping in a native (non-memory-safe) C++ tool executed inside the build could lead to crashes or, in the worse case, memory corruption in the singlejar process — matching the "heap-based buffer overflow / OOB write" class from the CVE, but confined to this native helper rather than Bazel's Java core.

### Likelihood Explanation
This requires a syntactically valid but internally inconsistent ZIP/JAR (bad size fields, or a JAR whose declared entry lengths exceed what fits in the mapped file) to reach `TransientBytes`/`Concatenator` via `singlejar`'s normal merge flow. I was not able to fully trace, within the available iterations, whether `singlejar`'s higher-level `InputJar`/`ZipReader` driver (not surfaced in the search results) performs an additional bounds check on `lh`/`cdh` sizes before invoking `Merge()`, nor whether `zip_headers.h`'s CDH/LH accessors clamp values internally. This is a material gap: without confirming the absence of such a check, I cannot assert this is an unguarded, exploitable path rather than one already screened by the driver loop.

### Recommendation
Because I could not conclusively verify (within the tool-call budget) that no bounds check exists between `InputJar`'s central-directory location logic and `TransientBytes`'s consumption of header-declared sizes, I am not confident this rises to a validated, reproducible vulnerability. A background engineer should specifically inspect `src/tools/singlejar/zip_headers.h` and the `output_jar.cc`/`combiners.cc` driver loop that calls `Merge()` for any remaining-length validation of `lh`/`cdh`-declared sizes before they reach `TransientBytes::ReadEntryContents`/`DecompressEntryContents`, add explicit "declared size ≤ remaining mapped bytes" checks (mirroring ijar's `EnsureRemaining`) if absent, and add a `BuildIntegrationTestCase`/native unit test that feeds a JAR with an inflated/oversized local-header size field into `singlejar` to confirm safe rejection.
