### Title
`SmartFarmingManager.leverage` checks `depositAmountMin_` slippage before the deposit fee is deducted — ([File: contracts/SmartFarmingManager.sol](contracts/SmartFarmingManager.sol))

### Summary
The Rubicon H-11 bug class — comparing the user's minimum-fill/slippage bound against a *pre-fee* amount — exists in `SmartFarmingManager.leverage`. The slippage check `if (_depositAmount < depositAmountMin_) revert LeverageSlippageTooHigh()` is performed on the gross collateral amount *before* `depositToken_.deposit()` subtracts `depositFee` and mints only the net amount to the user. The user's stated minimum is therefore not enforced against what they actually receive. A secondary instance exists in `flashRepay`, where `swapAmountOutMin_` ("the minimum amount to repay") is checked against the raw swap output while `DebtToken.repay` skims `repayFee` off that same amount, so the effective debt reduction is lower than the user's bound.

### Finding Description
In `leverage` (contracts/SmartFarmingManager.sol:155-211):

```solidity
// 3. swap synth for collateral
uint256 _depositAmount = amountIn_ + _swap(_swapper, syntheticToken_, _collateral, _issued, 0);
if (_depositAmount < depositAmountMin_) revert LeverageSlippageTooHigh();

// 4. deposit collateral
(_deposited, ) = depositToken_.deposit(_depositAmount, _msgSender);
```

`depositAmountMin_` is documented as "The min final deposit amount (slippage)". However `DepositToken.deposit` charges `depositFee` via `quoteDepositOut` and mints only `amount_ - _fee` msdToken shares to the beneficiary (contracts/DepositToken.sol:229-234). So the user who sets `depositAmountMin_ = X` receives `X * (1 - depositFee)` in collateral shares whenever `depositFee > 0` — up to 25% less than their bound, since `MAX_FEE_VALUE = 0.25e18` (contracts/FeeProvider.sol:25). The position-health check afterwards does not protect the user's minimum; it only verifies solvency, which a slightly-smaller-but-healthy deposit still satisfies.

In `flashRepay` (contracts/SmartFarmingManager.sol:98-144), `swapAmountOutMin_` is checked against `_swapAmountOut`, but `_debtToken.repay(_msgSender, _amountToRepay)` treats the passed amount as gross and keeps `repayFee` of it as fee (see `test/Integration.test.ts:347-357`, where the caller must pass `debt * (1 + repayFee)` to clear a given debt). The portion actually burned against debt is therefore less than the user's stated minimum.

### Impact Explanation
Direct loss of user funds bounded by the configured fee: a user of `leverage` can end up with a deposit up to `MAX_FEE_VALUE` (25%) smaller than the explicit `depositAmountMin_` they supplied, in a transaction that succeeds. In `flashRepay`, the user's debt is reduced by less than `swapAmountOutMin_` implies whenever `repayFee > 0`, and the "excess refund" logic masks this because the refund is computed on the gross swap output rather than net-of-fee repaid amount. Both are reachable by any unprivileged EOA through public `leverage`/`flashRepay` entry points on the deployed configuration, provided `depositFee`/`repayFee` are non-zero (they are governor-settable up to 25%; I could not confirm the live values from the index, but the code path is reachable whenever they are set).

### Likelihood Explanation
Likelihood is moderate: it requires a non-zero `depositFee` (or `repayFee`) to be configured and users to rely on `depositAmountMin_`/`swapAmountOutMin_` for protection — exactly the intended use of these parameters. No privileged role, oracle manipulation, or external dependency is needed; the check ordering alone breaks the invariant.

### Recommendation
Compute the post-fee amounts before enforcing the user's minimum:

- In `leverage`, either move the check after `deposit()` using `_deposited`, or pre-compute the net amount: `(uint256 _net, ) = depositToken_.quoteDepositOut(_depositAmount); if (_net < depositAmountMin_) revert LeverageSlippageTooHigh();`
- In `flashRepay`, check the slippage bound against the debt amount actually burned (the `_repaid` return of `DebtToken.repay`, or via `quoteRepayOut`) rather than the gross swap output.

### Proof of Concept
Hardhat/Foundry sketch (fork or existing test harness):

```solidity
// Setup: governor sets feeProvider.updateDepositFee(0.10e18) // 10%
// Alice calls:
smartFarmingManager.leverage(
    collateral,          // tokenIn_
    msdVaDAI,            // depositToken_
    msUSD,               // syntheticToken_
    100e18,              // amountIn_
    1.5e18,              // leverage_
    150e18               // depositAmountMin_ = user's min acceptable deposit
);
// Swapper returns 1:1 => _depositAmount = 150e18 >= depositAmountMin_ => check passes
// DepositToken.deposit takes 10% fee => _deposited = 135e18 < depositAmountMin_
// Assert: msdVaDAI.balanceOf(alice) == 135e18  (user's minimum violated, tx succeeded)
```

Same pattern for `flashRepay` with `repayFee > 0`: set `swapAmountOutMin_ = X`; the swap returns `X`, the check passes, but `repay` burns a `repayFee` slice of `X` so debt is reduced by `X / (1 + repayFee) < X`.
