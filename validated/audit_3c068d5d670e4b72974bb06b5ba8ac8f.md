### Title
Unbounded `read_to_end` on signer↔node StackerDB RPC responses enables memory-exhaustion DoS against `stacks-signer` - (File: `libsigner/src/http.rs`)

### Summary
`run_http_request` in `libsigner/src/http.rs` reads an entire HTTP response from the node into memory with `sock.read_to_end(&mut buf)` before any header parsing or length check occurs, and `StackerDBSession::rpc_request` (`libsigner/src/session.rs`) calls it over a plain, unencrypted `TcpStream` for every signer→node StackerDB query (`list_chunks`, `get_chunks`, `get_latest_chunks`, `put_chunk`). This is the same unbounded-read defect (CWE-770) described in the ciguard advisory, but here the transport is plaintext TCP (no TLS at all), so no MITM/cert-bypass is required to exploit it — any network position between the signer and its configured node endpoint can inject an oversized response.

### Finding Description [1](#0-0) 

`run_http_request` writes the request, then unconditionally calls `sock.read_to_end(&mut buf)?` with no cap on `buf`'s size — unlike the main P2P/RPC stack in `stackslib`, which enforces `HTTP_PREAMBLE_MAX_ENCODED_SIZE` via a `BoundReader` and `MAX_MESSAGE_LEN` checks on `payload_len` before buffering (`stackslib/src/net/httpcore.rs:1544-1599`, `stackslib/src/net/connection.rs:716-724`). Only *after* the entire response is buffered does `decode_http_response` parse headers and impose any limits (`MAX_HTTP_HEADER_LEN` on individual header values, `MAX_MESSAGE_LEN` on chunked bodies via `decode_http_body`). The non-chunked path — a normal `Content-Length` response, or a response with no `Content-Length` at all sent as a raw byte stream until connection close — bypasses even that later chunked-transfer bound entirely, since the whole payload was already accumulated by `read_to_end`.

This function is reached via `StackerDBSession::rpc_request` (`libsigner/src/session.rs:162-172`), which is invoked for every `SignerSession` operation over a raw `TcpStream` (`connect_or_reconnect`, `libsigner/src/session.rs:127-136`) with no TLS. A node the signer is configured to talk to (or anyone able to intercept/spoof that plaintext TCP connection) can respond with an arbitrarily large byte stream; the signer process will attempt to buffer all of it in memory in `buf: Vec<u8>` with no cap, before any size validation is applied.

The equality broken here is "bytes received == bytes the protocol is willing to buffer" — the wire length is effectively unchecked prior to buffering, in contrast to every other message-ingestion path in this repo (P2P `connection.rs`, HTTP `httpcore.rs`, StackerDB chunk validation in `stackslib/src/net/stackerdb/mod.rs:656-666`) which all impose an upper bound before or during buffering.

### Impact Explanation
A compromised or spoofed node endpoint (or an on-path attacker on the plaintext signer↔node link, which requires no MITM of TLS since there is no TLS) can force the `stacks-signer` process to allocate unbounded memory per RPC round-trip, leading to OOM kill of the signer process. Because signer availability is required for Nakamoto block signing thresholds, taking signer processes offline via repeated memory-exhaustion has availability impact on the broader signer set, beyond just "the attacker's own node." This is a bounded compute/memory DoS reachable from a single crafted response with no authentication or privilege required, matching the report's Medium-severity, defense-in-depth-style DoS classification (CWE-770), and is plausibly more directly reachable here than in the original ciguard report because there is no TLS to first defeat.

### Likelihood Explanation
Requires the signer to already be configured to talk to a given node host — this is expected, legitimate operator-managed connectivity. The exposure hinges on network position (or on the node itself being compromised/malicious). No authentication bypass or key compromise is required to trigger the bug once network position is achieved, and the plaintext protocol makes injection straightforward compared to TLS-protected alternatives. Likelihood is Medium: it is not exploitable purely remotely without any network position, but it is a realistic threat for node operators using signers behind untrusted networks or in the event of node compromise (same "hostile/compromised endpoint" threat model as the original ciguard finding).

### Recommendation
Bound the read in `run_http_request` similarly to how `stackslib/src/net/httpcore.rs` and `stacks-common/src/util/chunked_encoding.rs` do it:
- Read headers with a capped buffer (e.g., loop reading in small chunks up to `MAX_HTTP_HEADER_LEN * MAX_HTTP_HEADERS` bound until `decode_http_response` can parse the preamble), instead of `read_to_end` on the whole socket.
- Once `Content-Length` (or absence of it, indicating close-delimited body) is known, cap total body bytes read to a fixed maximum (e.g., `MAX_MESSAGE_LEN` or `STACKERDB_MAX_CHUNK_SIZE`), and abort/error if exceeded, mirroring the `payload_len` check in `stackslib/src/net/connection.rs:716-724`.
- Apply the cap during the raw socket read loop, not after buffering.

### Proof of Concept
1. Stand up a fake "node" TCP listener at the address that a `StackerDBSession` will `connect_or_reconnect()` to (`libsigner/src/session.rs:127-136`).
2. Have the signer call any `SignerSession` method, e.g. `list_chunks()` (`libsigner/src/session.rs:188-198`), which triggers `rpc_request` → `run_http_request`.
3. From the fake listener, respond with `HTTP/1.1 200 OK\r\n\r\n` followed by several GB of arbitrary bytes with no `Content-Length` header (or a huge declared `Content-Length`), and never close the connection.
4. Observe `run_http_request`'s `sock.read_to_end(&mut buf)` (`libsigner/src/http.rs:251`) accumulate the entire stream into `buf` in memory before any parsing/limit is applied, growing signer process memory unbounded until OOM (bounded only by the configured socket read timeout, not by data volume). /// Run an HTTP request, synchronously, through the given read/write handle
/// Return the HTTP reply, decoded if it was chunked
pub fn run_http_request<S: Read + Write>(
    sock: &mut S,
    host: &str,
    verb: &str,
    path: &str,
    content_type: Option<&str>,
    payload: &[u8],
) -> Result<Vec<u8>, RPCError> {
    let content_length_hdr = if !payload.is_empty() {
        format!("Content-Length: {}\r\n", payload.len())
    } else {
        "".to_string()
    };

    let req_txt = if let Some(content_type) = content_type {
        format!(
            "{verb} {path} HTTP/1.1\r\nHost: {host}\r\nConnection: close\r\nContent-Type: {content_type}\r\n{content_length_hdr}User-Agent: libsigner/0.1\r\nAccept: */*\r\n\r\n"
        )
    } else {
        format!(
            "{verb} {path} HTTP/1.1\r\nHost: {host}\r\nConnection: close\r\n{content_length_hdr}User-Agent: libsigner/0.1\r\nAccept: */*\r\n\r\n"
        )
    };
    debug!("HTTP request\n{}", &req_txt);

    sock.write_all(req_txt.as_bytes())?;
    sock.write_all(payload)?;

    let mut buf = vec![];

    sock.read_to_end(&mut buf)?;

    let (headers, body_offset) = decode_http_response(&buf)?;
    if body_offset >= buf.len() {
        // no body
        debug!("No HTTP body");
        debug!("Headers: {:?}", &headers);
        return Ok(vec![]);
    }

    decode_http_body(&headers, &buf[body_offset..]).map_err(|e| e.into())
}

    /// connect or reconnect to the node
    fn connect_or_reconnect(&mut self) -> Result<(), RPCError> {
        debug!("connect to {}", &self.host);
        let sock = TcpStream::connect(&self.host)?;
        // Make sure we don't hang forever if for some reason our node does not
        // respond as expected such as failing to properly close the connection
        sock.set_read_timeout(Some(self.socket_timeout))?;
        sock.set_write_timeout(Some(self.socket_timeout))?;
        self.sock = Some(sock);
        Ok(())
    }
