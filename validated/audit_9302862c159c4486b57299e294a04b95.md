### Title
Attached caller deposit is permanently lost when intermediate cross-contract calls fail in the eth-implicit Wallet Contract - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
The `WalletContract::rlp_execute` flow accepts an attached deposit from an external (non-self) caller/relayer and tracks it in a `CallerDeposit` struct so it can be refunded if the emulated action ultimately fails. However, this refund is only implemented in the terminal callback `rlp_execute_callback`. The two intermediate callbacks, `address_check_callback` and `nep_141_storage_balance_callback`, drop the `caller_deposit` on the `PromiseResult::Failed` branch without ever issuing a refund transfer, permanently stranding the caller's attached NEAR inside the wallet contract's own balance.

### Finding Description
`CallerDeposit::new` captures the attached deposit of an external predecessor when `rlp_execute` is invoked, specifically to refund it if the eventual action fails: [1](#0-0) 

For `EOABaseTokenTransfer` transactions that require an address-registrar lookup, and for `ERC20Transfer` transactions that require a NEP-141 `storage_balance_of` check, the `caller_deposit` is threaded as a parameter into intermediate callbacks before the actual target action is even attempted: [2](#0-1) 

In `address_check_callback`, if the call to the address registrar contract fails (`PromiseResult::Failed`), the function immediately returns an error response and never creates a refund promise for `caller_deposit`: [3](#0-2) 

The same pattern exists in `nep_141_storage_balance_callback` when the `storage_balance_of` call to the token contract fails: [4](#0-3) 

This is inconsistent with the only place where a refund is actually performed — the terminal `rlp_execute_callback`, which does construct a `promise_batch_action_transfer` back to `caller_deposit.account_id` on failure: [5](#0-4) 

Because the attached deposit was already credited to the wallet contract's own account balance as part of the `#[payable]` `rlp_execute` call, any failure occurring before the final callback (i.e., in the address-registrar or storage-balance-of legs of the flow) results in that deposit being silently absorbed by the wallet contract instead of returned to the depositor, exactly the same class of bug as the external report: an asset-handling path that assumes a particular happy-path routing of funds and fails to correctly return them to the paying party when that assumption doesn't hold.

### Impact Explanation
Any unprivileged relayer or third-party caller (not the wallet's own eth-implicit account) who attaches NEAR to `rlp_execute` for an `EOABaseTokenTransfer` with an address check, or an `ERC20Transfer` that requires a NEP-141 storage check, can permanently lose that attached deposit if the intermediate cross-contract call (address registrar lookup or `storage_balance_of`) fails for any reason (e.g., the registrar/token contract panics, runs out of gas, or is temporarily unavailable). This is a permanent freezing/loss of funds for an ordinary, unprivileged caller of a deployed contract that ships as part of nearcore's eth-implicit account tooling.

### Likelihood Explanation
The failure path is reachable without any privileged access — it triggers whenever the downstream `address_registrar.lookup` or NEP-141 `storage_balance_of` cross-contract call fails, which can happen due to ordinary conditions such as insufficient gas, a paused/misbehaving registrar, or a token contract that reverts on `storage_balance_of`. No malicious node or validator behavior is required; a legitimate relayer relaying a legitimate signed transaction can trigger this by simple bad luck or an unresponsive dependency.

### Recommendation
In both `address_check_callback` and `nep_141_storage_balance_callback`, mirror the refund logic used in `rlp_execute_callback`: on `PromiseResult::Failed`, if `caller_deposit` is `Some`, issue a `promise_batch_create`/`promise_batch_action_transfer` back to `caller_deposit.account_id` for `caller_deposit.yocto_near` before returning the failure `ExecuteResponse`.

### Proof of Concept
1. An external relayer (unprivileged signer, `predecessor_account_id != current_account_id`) calls `rlp_execute` on a wallet contract with an `EOABaseTokenTransfer` whose target is another eth-implicit account (`address_check: Some(address)`), attaching a non-zero NEAR deposit (e.g., covering a relayer fee or transfer amount).
2. `inner_rlp_execute` computes `caller_deposit = Some(CallerDeposit { account_id: relayer, yocto_near: deposit })` and schedules `address_registrar.lookup(address).then(address_check_callback(target, action, caller_deposit))`.
3. The address registrar cross-contract call fails (e.g., registrar contract is paused, mis-deployed, or runs out of gas) so `env::promise_result(0)` is `PromiseResult::Failed` inside `address_check_callback`.
4. `address_check_callback` returns `ExecuteResponse { success: false, ... }` immediately, without creating any transfer back to the relayer.
5. The relayer's originally attached deposit remains part of the wallet contract's account balance permanently; it is never refunded and the relayer has no on-chain path to reclaim it.
