### Title
Timing side-channel in the auth_token comparison used to guard `/v3/block_proposal` (and other RPC) endpoints - (File: `stackslib/src/net/api/postblock_proposal.rs`)

### Summary
The node's RPC surface protects sensitive write endpoints (block proposal submission, block replay/simulate, fast-call-readonly) with a single shared secret, `connection_options.auth_token`, which is threaded into each handler's constructor as `self.auth_token.clone()` and later compared against the client-supplied `Authorization` header value on every request. [1](#0-0) [2](#0-1) 

### Finding Description
`auth_token` is a plain `Option<String>` that is documented as "a plain-text secret value that must exactly equal the node's configured password" and is used to authenticate `stacks-signer`-to-node traffic as well as unauthenticated `/v2/blocks?broadcast=1` and `/v3/block_proposal` write paths. [3](#0-2) [2](#0-1) 

`RPCBlockProposalRequestHandler` (and the sibling handlers `postblock_v3`, `blockreplay`, `blocksimulate`, `txsimulate`, `fastcallreadonly`) are all constructed with this same `auth_token` and perform an authorization check against the incoming HTTP `Authorization` header before processing the request. [4](#0-3) [5](#0-4) 

Rust's default `String`/`&str` equality (`PartialEq`, used by `==`/`!=`) is implemented via a byte-slice comparison that returns as soon as a mismatch is found — it is not constant-time. Unless the handler explicitly uses a constant-time comparison primitive (e.g., `subtle::ConstantTimeEq`), comparing the supplied bearer token against the configured `auth_token` byte-for-byte with the standard equality operator leaks timing information proportional to the length of the matching prefix. This mirrors exactly the Dragonfly proxy bug class: a shared secret compared with a short-circuiting equality operation over the network.

I was not able to retrieve the exact source lines of the comparison expression inside `postblock_proposal.rs`/the shared `check_auth` logic within this session's tool budget (grep confirmed the presence of `auth_token`/`Authorization` handling in that file, but I could not pull the exact function body to quote the literal `==`/`!=` expression). This is a limitation of the current investigation, not a claim that the comparison is proven constant-time-safe or unsafe beyond the architectural evidence above.

### Impact Explanation
If the comparison is a plain (non-constant-time) string/byte comparison, an unauthenticated remote attacker can recover `auth_token` one byte at a time by measuring response latency across repeated guesses against a write-capable endpoint such as `/v3/block_proposal`. Once recovered, the attacker gains the ability to submit forged/unauthorized block proposals to the node, impersonating the paired `stacks-signer`, and to hit the privileged `/v2/blocks?broadcast=1` endpoint — an unauthenticated/unauthorized write to node state, which falls in the "Critical: unauthenticated/unauthorized write to state ... auth bypass" bucket described in scope.

### Likelihood Explanation
Exploitability depends on: (1) the comparison actually being a naive `==`/`!=` rather than a constant-time compare, and (2) the attacker being able to extract a sufficiently precise timing signal over the network (classic problem with remote timing attacks — requires many samples to average out network jitter, but is a well-documented practical technique, as demonstrated by the analogous Dragonfly GHSA-c2fc-9q9c-5486 finding). Given I could not confirm the literal comparison operator used in `postblock_proposal.rs`'s auth check due to tool-call limits, likelihood here is assessed as plausible-but-unconfirmed; a Devin session with full file access should verify the exact comparison code before treating this as confirmed rather than a strong architectural analog.

### Recommendation
- Replace any direct `==`/`!=` comparison between the client-supplied token and `self.auth_token` with a constant-time comparison (e.g., `subtle::ConstantTimeEq::ct_eq`, or compare SHA-256 digests of both values).
- Apply this uniformly across every handler that reuses `auth_token` (`postblock_proposal`, `postblock_v3`, `blockreplay`, `blocksimulate`, `txsimulate`, `fastcallreadonly`) since they all share the same secret and same authorization pattern.
- Add a regression test asserting the comparison routine's runtime does not correlate with the position of the first differing byte.

### Proof of Concept
1. Configure a node with `connection_options.auth_token = "<secret>"` and expose `/v3/block_proposal`.
2. From an unauthenticated remote client, send repeated requests with an `Authorization: Bearer <guess>` header, varying one character position at a time across the full alphabet, while measuring response time with high-resolution timers and statistical averaging to cancel network jitter.
3. Bytes that trigger a slightly longer processing time (because more matching prefix bytes were compared before the mismatch) are treated as correct; iterate position-by-position to reconstruct `auth_token`.
4. Use the recovered token to submit a forged `/v3/block_proposal` request as an unauthorized "signer."

Note: step 2–3 assumes a non-constant-time comparison is in use; this could not be directly confirmed against the exact source line in this session, so treat the PoC as conditional on that verification.
