## Analysis

I searched for the java-tron analog of the "fee-less loans" bug class — a percentage/ratio calculation on a state-changing operation that can floor to zero via integer division, letting a caller skip the cost that should accompany that operation. The closest reachable match is in `ExchangeInjectActuator`, which computes the counter-token amount for a TRC10 exchange (AMM-style) inject operation using pure integer division, with no floor-to-zero guard — unlike its sibling `ExchangeWithdrawActuator`, which explicitly validates the analogous value.

### Title
Fee-less/cost-less exchange liquidity injection due to unchecked zero-rounding in ratio calculation - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java)

### Summary
`ExchangeInjectActuator` computes the amount of the paired token (`anotherTokenQuant`) that must accompany an `ExchangeInjectContract` using integer division of the pool ratio. When `tokenQuant` is small relative to the pool ratio, `anotherTokenQuant` truncates to `0`, and neither `execute()` nor `doValidate()` rejects this, unlike the withdraw path which explicitly enforces a non-zero counter-amount.

### Finding Description
In `execute()`, the counter-token amount is derived via floor division: [1](#0-0) 
and the same unguarded computation appears in `doValidate()`: [2](#0-1) 

No check exists anywhere in `ExchangeInjectActuator` that rejects `anotherTokenQuant == 0` (contrast the balance/tokenQuant/pool-existence checks at lines 190-207 of the same file). This is the same rounding-to-zero root cause described in the external report (a ratio multiplication then integer division that floors to zero for small enough operands), just applied to a pool-balance ratio instead of a fee percentage.

By contrast, `ExchangeWithdrawActuator` performs the identical style of calculation but explicitly guards against the zero case: [3](#0-2) 
This asymmetry indicates the inject path is missing an equivalent validation that the withdraw path already has.

### Impact Explanation
The exchange creator (a permissionless "asset issuer"-class actor who can create/manage a TRC10 exchange) can call `ExchangeInjectContract` with a `tokenQuant` chosen so that the computed paired-token cost (`anotherTokenQuant`) rounds down to zero. The transaction is accepted, `firstTokenBalance`/`secondTokenBalance` in the exchange pool are updated as if a proportional two-sided deposit occurred, but only one side of tokens is actually debited from the caller — the pool ratio is skewed for free. Since `ExchangeCapsule.transaction()` (used by `ExchangeTransactionActuator`, reachable by any user) prices trades directly off `firstTokenBalance`/`secondTokenBalance`, repeated cost-less ratio skewing can be used to manipulate the exchange price to the creator's advantage against other traders' funds, which constitutes a form of unbacked-balance/theft-adjacent value extraction from counterparties in that exchange, warranting Medium severity.

### Likelihood Explanation
Reachable from a single signed `ExchangeInjectContract` transaction sent by the exchange's creator address (the only precondition enforced is `accountCapsule.getAddress().equals(exchangeCapsule.getCreatorAddress())`, at line 175 of the file). The only cost is the flat `MarketSellFee`-independent `calcFee()` (which returns `0` for this actuator) — i.e., there is no fee at all for this actuator, so the attack has effectively zero incremental cost per call and no built-in economic mitigation.

### Recommendation
Add an explicit check in `ExchangeInjectActuator.doValidate()` (and defensively in `execute()`) rejecting the transaction when the computed `anotherTokenQuant <= 0`, mirroring the check already present in `ExchangeWithdrawActuator`: [3](#0-2) 

### Proof of Concept
1. Attacker creates (or is) the creator of a TRC10 exchange with a highly skewed pool, e.g. `firstTokenBalance = 10_000_000`, `secondTokenBalance = 1`.
2. Attacker submits `ExchangeInjectContract` with `tokenID = firstTokenID`, `tokenQuant = 1` (any value smaller than `firstTokenBalance / secondTokenBalance` ratio threshold).
3. `anotherTokenQuant = bigSecondTokenBalance.multiply(bigTokenQuant).divide(bigFirstTokenBalance).longValueExact()` evaluates to `0` (e.g. `1 * 1 / 10_000_000 = 0`).
4. `doValidate()` performs no check that `anotherTokenQuant > 0`, so validation passes; `execute()` updates `firstTokenBalance += 1`, `secondTokenBalance += 0`, debits only `firstTokenQuantity=1` from the caller, and no `secondToken`/TRX cost is paid for the second side — the pool ratio is altered at zero cost on the second-token leg.

**Caveat / confidence note:** I was unable to trace downstream trading-actuator behavior far enough to conclusively quantify the exact profit an attacker could extract via repeated ratio-skewing before this is flagged as "no vulnerability found" territory; the finding is based on a clear code-level asymmetry (missing zero-check in inject vs. present zero-check in withdraw) that structurally matches the report's rounding-to-zero root cause, but a full economic-exploitability proof (multi-transaction price-manipulation sequence against a victim's trade) would require deeper simulation than the available read-only tools allowed in this session.
