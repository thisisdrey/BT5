### Title
GetSnapshot leaks unreachable pool-member objects across tenants via alternate object directory tar-dump - (File: internal/git/localrepo/snapshot.go)

### Summary
`CreateSnapshot`/`addAlternateFiles` walks the entire alternate object directory (the shared object pool) and copies every loose object and packfile found there into the returned tar archive, without filtering by reachability from the requesting repository's own refs. Because Gitaly's object-pool architecture links multiple, potentially unrelated, private repositories to the same pool via `objects/info/alternates`, any pool member can call the standard `GetSnapshot` RPC on itself and receive a full copy of every object that has ever been fetched into the shared pool, including objects contributed exclusively by other members.

### Finding Description
`GetSnapshot` (`internal/gitaly/service/repository/snapshot.go:12`) only validates that the requested repository exists (`s.locator.ValidateRepository`) before invoking `CreateSnapshot`. [1](#0-0) 

`CreateSnapshot` builds the tar by adding the repo's own `objects` directory (filtered to loose objects/packfiles) and then calls `addAlternateFiles`, which resolves the pool's alternate object directory via `git.AlternateObjectDirectories(ctx, ..., storageRoot, path)` and walks it, copying **every** file matching the loose-object/packfile regexes into the archive under `objects/`. [2](#0-1) [3](#0-2) 

This walk is not scoped by reachability from the calling repository's refs; it dumps the raw contents of the alternate object store's `objects/**` tree. This differs materially from normal Git protocol access (`git-upload-pack`, `git-archive`) to the same repository, which only serves objects that are reachable from the repository's own advertised refs — Git's object negotiation never lets a client fetch arbitrary unreachable loose objects sitting in the alternate. `GetSnapshot` is registered as an `ACCESSOR` RPC [4](#0-3) , the same authorization class as ordinary read operations on a repository the caller already has access to — there is no additional gate requiring pool-ownership or "primary member" status to call it.

Per `doc/object_pools.md`, a repository becomes linked to a pool's alternates whenever GitLab links it as a fork-network member, and `FetchIntoObjectPool` (typically triggered by housekeeping on any linked member, historically the "primary" but not gated at the Gitaly layer) fetches `+refs/*:refs/remotes/origin/*` from that member into the pool and further creates dangling refs to keep any resulting unreferenced objects alive indefinitely. [5](#0-4)  Those objects (including ones that never become reachable from any other member's own refs) persist as loose objects/packfiles inside the pool's `objects` directory forever, per the "Dangling Objects" design note. Since `walkAndAddToBuilder` has no reachability filter, calling `GetSnapshot` on any linked member (including the attacker's own repo A) will include these objects in the returned tar, regardless of whether A's own history ever referenced them.

### Impact Explanation
An attacker who owns pool member A can extract loose objects/blobs/commits/packfiles that were pushed only by another (private) pool member B and fetched into the shared pool, without ever going through the normal Git object-reachability negotiation that both `git-upload-pack` and `git-archive`-based RPCs enforce. This is a cross-tenant confidentiality breach: disclosure of another user's/project's repository content (blobs, commit metadata, file contents) that GitLab's data model intends to keep private to repository B. This matches GitLab's "information disclosure / broken access control" bounty class for cross-project object leakage via object pools.

### Likelihood Explanation
Preconditions require only unprivileged, ordinary GitLab actions: forking/importing a repository so it becomes (or remains) a member of a shared object pool, and the pool being periodically refreshed via `FetchIntoObjectPool` (a routine housekeeping operation, not an admin action). No special role, token, or race condition is needed — the attacker simply calls the standard accessor RPC `GetSnapshot` against a repository they legitimately own and are permitted to read. This is fully repeatable as long as the pool contains dangling/unreachable objects from another member, which the pool's own "keep dangling objects alive forever" design (documented in `doc/object_pools.md`) guarantees will persist.

### Recommendation
Do not raw-copy the entire alternate object directory into the snapshot tar. Instead, either (a) omit alternate-object-directory contents from `GetSnapshot` entirely and rely on `git repack -a`/pack-objects on the pool member's own refs to materialize only reachable objects, or (b) compute the object set to copy by enumerating objects reachable from the snapshotting repository's own refs (e.g., via `git rev-list --objects --all` or `git pack-objects` against the repo's refs with alternates as haves) rather than walking every file in the pool's `objects` tree. If full-alternate replication is required for internal Geo/replication use cases, restrict `GetSnapshot`'s alternate-inclusion behavior to trusted internal callers (e.g., require a Praefect/internal-only auth scope) rather than exposing it as an ordinary `ACCESSOR` RPC callable by any repository owner.

func TestGetSnapshot_leaksPoolPrivateObjects(t *testing.T) {
    ctx := testhelper.Context(t)
    cfg, client := setupRepositoryService(t)

    // Create pool and two members A (attacker) and B (victim).
    poolRepo, poolPath := gittest.CreateRepository(t, ctx, cfg)
    repoA, repoAPath := gittest.CreateRepository(t, ctx, cfg)
    repoB, repoBPath := gittest.CreateRepository(t, ctx, cfg)

    // Link A and B to the pool (objects/info/alternates -> pool objects dir).
    linkToPool(t, repoAPath, poolPath)
    linkToPool(t, repoBPath, poolPath)

    // B pushes a private commit with a unique blob.
    privateBlobContent := []byte("victim-private-secret")
    privateCommit := gittest.WriteCommit(t, cfg, repoBPath,
        gittest.WithTreeEntries(gittest.TreeEntry{Path: "secret.txt", Mode: "100644", Content: string(privateBlobContent)}),
        gittest.WithBranch("private"))

    // FetchIntoObjectPool fetches B's refs into the pool (simulating housekeeping).
    fetchIntoObjectPool(t, ctx, cfg, poolRepo, repoB)

    // Attacker calls GetSnapshot on their own repo A.
    stream, err := client.GetSnapshot(ctx, &gitalypb.GetSnapshotRequest{Repository: repoA})
    require.NoError(t, err)
    tarData := readAllSnapshot(t, stream)

    // Extract tar and search for the victim's blob content.
    require.Contains(t, string(tarData), /* zlib-compressed blob, so instead: */
        privateCommit) // or decompress objects and assert blob content present

```
Expected (vulnerable) result: the tar extracted from `GetSnapshot(Repository=A)` contains loose object files under `objects/**` that decompress to B's private commit/blob content, even though A's own refs never reference `privateCommit`.

func (repo *Repo) addAlternateFiles(ctx context.Context, builder *archive.TarBuilder, storageRoot, repoPath string) error {
	altObjDirs, err := git.AlternateObjectDirectories(ctx, repo.logger, storageRoot, repoPath)
	if err != nil {
		return fmt.Errorf("%w: %w", ErrSnapshotAlternates, err)
	}

	for _, altObjDir := range altObjDirs {
		if err := walkAndAddToBuilder(altObjDir, builder); err != nil {
			return fmt.Errorf("walking alternates file: %w", err)
		}
	}

	return nil
}

func walkAndAddToBuilder(alternateObjDir string, builder *archive.TarBuilder) error {
	matchWalker := archive.NewMatchWalker(objectFiles, func(path string, info os.FileInfo, err error) error {
		if err != nil {
			return fmt.Errorf("error walking %v: %w", path, err)
		}

		relPath, err := filepath.Rel(alternateObjDir, path)
		if err != nil {
			return fmt.Errorf("alternative object directory path: %w", err)
		}

		file, err := os.Open(path)
		if err != nil {
			return fmt.Errorf("opening file %s: %w", path, err)
		}
		defer file.Close()

		objectPath := filepath.Join("objects", relPath)

		if err := builder.VirtualFileWithContents(objectPath, file); err != nil {
			return fmt.Errorf("expected file %v to exist: %w", path, err)
		}

		return nil
	})

	if err := filepath.Walk(alternateObjDir, matchWalker.Walk); err != nil {
		return fmt.Errorf("error when traversing: %w", err)
	}

	return nil
}

1. A fetch is performed from the object pool member into the object pool with a
   `+refs/*:refs/remotes/origin/*` refspec. This fetch is most notably not a
   pruning fetch, that is any reference which gets deleted in the member will
   stay around in the pool.

1. The fetch may create new dangling objects which are not referenced anymore in
   the pool repository. These dangling objects will be kept alive by creating
   dangling references such that they do not get deleted in the pool. See
   [Dangling Objects](#dangling-objects) for more information.

1. Loose references are packed via `git-pack-refs(1)`.
1. The pool is repacked via `git-repack(1)`. The repack produces a single packfile
   including all objects with a bitmap index. In order to improve reuse of
   packfiles where Git will read data from the packfile directly instead of
   generating it on the fly, the packfile uses a delta island including
   `refs/heads` and `refs/tags`. This restricts Git to only generate deltas for
   objects which are directly reachable via either a branch or a tag. Most
   notably, this causes us to not generate deltas against dangling references.

## Dangling Objects

When fetching from pool members into the object pool, then any force-updated
references may cause objects in the pool to not be referenced anymore. For
normal repositories, it is perfectly fine to delete those references after a
certain time. In the context of object pools, any other member of the pool may
still use any of those unreferenced objects. Deleting them would thus
potentially cause corrupt repositories.

This issue is kind of unsolvable: there is no point in time where it's safe to
delete objects from the object pool, as we do not know which repositories may be
linked to it. And even if we knew, we cannot determine all references of all
repositories at once in a race-free manner. We thus must consider each object to
still be referenced somewhere.

As a safeguard to not lose any objects by accident, we thus create dangling
references in the object pool after the fetch in `FetchIntoObjectPool`. For each
dangling object, a reference `refs/dangling/$OID` is created which points into
the object. This assures that each object is still referenced.
```
