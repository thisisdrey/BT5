Audit Report

## Title
`ERC20Transactor::withdraw_asset_with_surplus`/`deposit_asset_with_surplus` treat non-conforming ERC20 tokens (empty/void `transfer` return data) as failed even though the on-chain transfer already succeeded, permanently locking user tokens in `TransfersCheckingAccount` with no XCM credit - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

## Summary
`ERC20Transactor` calls the ERC20 `transfer` function via `pallet_revive::Pallet::<T>::bare_call` and, when the call does not revert, unconditionally treats a failed strict ABI decode of the return data as a transfer failure via `IERC20::transferCall::abi_decode_returns_validate`. For non-conforming ERC20 tokens that return no data on success (the well-known non-standard-return pattern), the underlying on-chain balance transfer succeeds while the transactor incorrectly reports failure, so no `AssetsInHolding` credit is created and the tokens are stranded in `TransfersCheckingAccount` (withdraw path) or already-debited-but-undelivered (deposit path).

## Finding Description
In `withdraw_asset_with_surplus`, the code performs a `bare_call` to the ERC20 contract's `transfer(checking_address, amount)`, then branches only on `did_revert()` and `abi_decode_returns_validate(&return_value.data)`: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs:185-208`. There is no branch for the case where the call did not revert but returned no/insufficient data to decode as `bool` — this produces `Err(XcmError::FailedToTransactAsset("ERC20 contract result couldn't decode"))` at line 191-194, even though the transfer to `checking_address` already executed on-chain. The mirrored logic exists in `deposit_asset_with_surplus` at lines 276-297, where a decode error likewise returns `Err` (returning `what` back to the caller) despite the checking account's tokens having already been transferred out to the beneficiary address on-chain.

Critically, the asset matcher wired for this transactor, `ERC20Matcher = MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>` (`cumulus/parachains/runtimes/assets/common/src/lib.rs:159-160`), matches **any** local `AccountKey20` location without any allow-list or governance-curated registry — `IsLocalAccountKey20::contains` accepts any location shaped as `(0, [AccountKey20 { .. }])` (`cumulus/parachains/runtimes/assets/common/src/lib.rs:134-139`). This means any H160 contract address can be referenced as an XCM asset id and routed through `ERC20Transactor`, so no privileged registration step is required to hit a non-conforming ERC20 contract — any unprivileged user submitting an XCM program (or local extrinsic invoking XCM execution) referencing a non-standard ERC20 as the asset triggers this path.

## Impact Explanation
Once `bare_call` executes the `transfer` without reverting, token custody has already moved (withdraw: user → `TransfersCheckingAccount`; deposit: `TransfersCheckingAccount` → beneficiary) — this is irreversible EVM/`pallet_revive` state, independent of the XCM executor's subsequent bookkeeping. If the return-data decode subsequently fails for a non-conforming token, `withdraw_asset_with_surplus` returns `Err`, so the XCM executor never creates the corresponding `AssetsInHolding` credit and the rest of the XCM program (e.g., `DepositAsset` to a destination) never executes for that asset — the user's tokens are stuck in `TransfersCheckingAccount` with no code path to reclaim them via XCM. This matches the "permanent user-fund lock" impact category and requires no malicious peer, governance, or privileged actor.

## Likelihood Explanation
Because `ERC20Matcher` (`IsLocalAccountKey20`) accepts any local `AccountKey20` location with no allow-list, any user can reference an arbitrary ERC20 contract address in an XCM program processed by `ERC20Transactor`. Non-conforming ERC20 implementations that return no data on success (the classic non-standard-return pattern, historically associated with tokens like USDT) are common in the wild; this repository itself carries fixture contracts demonstrating this class of behavior (`substrate/frame/revive/fixtures/contracts/MyTokenFake.sol`), indicating awareness of the pattern within the codebase but no corresponding guard in the transactor. Any deployment of `ERC20Transactor` that allows arbitrary/foreign ERC20 contracts to be bridged is exposed with no special privilege needed to trigger the bug — an ordinary withdrawal/deposit XCM instruction involving such a token suffices.

## Recommendation
Do not treat a failed strict-bool ABI decode as the sole failure signal. Following the common `SafeERC20`-style semantics, treat a non-reverted call as successful if either (a) `return_value.data` is empty (void return) or (b) it decodes to `true`; only treat an explicit `Ok(false)` decode or an actual revert as failure. Apply this fix symmetrically to both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus` in `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`. Alternatively/additionally, restrict `ERC20Matcher`/asset registration to a curated, audited allow-list of strictly EIP-20-conformant contracts if changing the decode logic is not feasible.

/// `Contains<Location>` implementation that matches locations with no parents,
/// a `PalletInstance` and an `AccountKey20` junction.
pub struct IsLocalAccountKey20;
impl Contains<Location> for IsLocalAccountKey20 {
	fn contains(location: &Location) -> bool {
		matches!(location.unpack(), (0, [AccountKey20 { .. }]))
	}
}

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {
		Some(Location::new(0, [AccountKey20 { key: (*key).into(), network: None }]))
	}
}

/// [`xcm_executor::traits::MatchesFungibles`] implementation that matches
/// ERC20 tokens.

	MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>;
