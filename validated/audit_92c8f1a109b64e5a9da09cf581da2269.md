### Title
Wallet Contract can be permanently frozen if a called external contract's callback response causes the fixed-gas callback to fail before resetting `has_in_flight_tx` - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
The ETH-implicit `WalletContract` guards against transaction reordering with a single boolean flag, `has_in_flight_tx`, which must be reset to `false` inside a private callback once the outgoing cross-contract call resolves. The callback is scheduled with a small, hard-coded static gas budget, and the target of the outgoing call (an arbitrary NEP-141 token or the address registrar) is not controlled by the wallet contract. If that external contract's behavior changes (e.g. it starts returning a larger/different payload from `storage_balance_of`, or its execution otherwise consumes more resources than expected), the callback can run out of gas before it reaches the line that resets `has_in_flight_tx`, and the whole callback receipt reverts — leaving the flag permanently stuck at `true`.

### Finding Description
`WalletContract::rlp_execute` refuses to process any new transaction whenever `self.has_in_flight_tx` is `true`: [1](#0-0) 

The flag is only cleared inside the `#[private]` callbacks (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`), each of which sets `self.has_in_flight_tx = false;` as its very first statement: [2](#0-1) [3](#0-2) [4](#0-3) 

These callbacks are attached with fixed, hard-coded gas amounts computed at compile time, independent of what the invoked external contract actually needs or returns: [5](#0-4) 

The gas is composed additively from constants for each expected call chain (e.g. `NEP_141_STORAGE_BALANCE_CALLBACK_GAS = NEP_141_STORAGE_BALANCE_OF_GAS + NEP_141_STORAGE_DEPOSIT_GAS + RLP_EXECUTE_CALLBACK_GAS`), all in the 5 TGas range. This sizing assumes the shape of the "standard NEP-141 implementation" as noted in the code comment about hard-coding `NEP_141_STORAGE_DEPOSIT_AMOUNT` "since essentially all tokens use" the same value: [6](#0-5) 

If the wallet contract is used against a token/contract whose interface returns a larger response (larger `storage_balance_of` result, different callback data shape needing more deserialization gas), or the promise chain simply needs more gas than these hard-coded budgets provide, the callback function execution can exhaust its gas allowance and the whole receipt fails atomically — including the state write that would have reset `has_in_flight_tx` to `false`. Because NEAR receipts are all-or-nothing, a failed/out-of-gas callback leaves the contract's persisted `has_in_flight_tx` untouched, i.e. still `true` from when `rlp_execute` originally set it: [7](#0-6) 

Once stuck, every future call to `rlp_execute` is rejected at the guard check shown above, and there is no other method on `WalletContract` that can reset `has_in_flight_tx` — the only such method, `ban_relayer`, is itself `#[private]` and can only be invoked as a promise callback from within `inner_rlp_execute`'s error path, which is unreachable once `rlp_execute` short-circuits on the stuck flag. This mirrors the reported bug class: an unprivileged, ordinary interaction (a relayed transaction targeting an arbitrary/foreign NEP-141 token contract) can permanently brick the wallet because the wallet's logic hard-codes assumptions (gas budget, response shape) about an external, not-self-controlled contract's interface.

### Impact Explanation
This is a permanent freezing-of-funds condition for the affected ETH-implicit account: once `has_in_flight_tx` is stuck `true`, the owner can never again submit a transaction through `rlp_execute` (the sole entry point for using funds held by the account), since the guard unconditionally rejects new calls. There is no other action available to unset the flag — NEP-518 ETH-implicit accounts cannot have a full access key added, nor be deleted, so there is no owner-controlled recovery path outside of `rlp_execute` itself. All NEAR and any token balances held by that account become permanently inaccessible via the wallet's transaction path.

### Likelihood Explanation
The trigger requires only an ordinary, unprivileged relayed transaction targeting a NEP-141 token contract (or the address registrar) whose actual runtime behavior does not fit the wallet's hard-coded gas budget/assumptions — no privileged access or malicious node behavior is needed. Because token contract implementations vary (non-standard storage bounds, richer metadata, proxy/wrapper tokens, larger `StorageBalance` payloads, or future upgrades to any of these dependencies), and the gas budgets here are fixed small constants rather than derived from `prepaid_gas`/remaining gas, this is plausible in normal usage, not just a contrived edge case.

### Recommendation
- Do not fix the callback gas as small hard-coded constants; instead attach the maximum remaining prepaid gas (or a generous, protocol-config-driven ceiling) to the callback so that transient underestimation cannot cause a failed receipt.
- Ensure the state mutation that clears `has_in_flight_tx` is not gated behind gas-sensitive logic — e.g., perform the flag reset in a minimal-gas guaranteed step (such as splitting into a tiny, cheap "always-succeeds" finalization action) rather than only at the top of a callback that also does more expensive work (JSON deserialization of arbitrary-sized external contract responses).
- Consider adding a permissionless "unstick" mechanism gated by a timeout (e.g., allow clearing `has_in_flight_tx` if no callback resolved within N blocks), so that even in a worst-case gas-underestimation scenario funds are not frozen forever.

### Proof of Concept
1. Deploy an ETH-implicit account with the `WalletContract`.
2. Have a relayer submit a signed Ethereum-emulated ERC-20 transfer (`EthEmulationKind::ERC20Transfer`) targeting a NEP-141 token contract whose `storage_balance_of` implementation returns an unusually large/complex `StorageBalance`-compatible payload, or whose cross-contract execution graph consumes gas close to or exceeding `NEP_141_STORAGE_BALANCE_CALLBACK_GAS` (5 TGas budget chain) shown at `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:39-41`.
3. `rlp_execute` sets `has_in_flight_tx = true` and schedules `Promise::new(token_id).function_call("storage_balance_of", ...)` chained to `nep_141_storage_balance_callback` with the fixed gas budget (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:440-458`).
4. The callback function call runs out of allotted gas before executing `self.has_in_flight_tx = false;` (line 202), causing the entire callback receipt to fail and revert all its state changes.
5. Any subsequent call to `rlp_execute` on this account is now rejected with `"Error: transaction already in progress, please try again later."` forever, because `has_in_flight_tx` remains `true` in persisted state and no other method can reset it (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:97-105`, `319-327`).

Note: I was not able to execute this scenario in a live test-loop harness to empirically confirm the exact gas margin required to trigger the out-of-gas condition (that would require running the wallet-contract test suite under `runtime/near-wallet-contract/implementation/wallet-contract/src/tests/`); the analysis above is based on static code review of the fixed gas constants and the callback ordering, which is confirmed to exist in the code as cited.
