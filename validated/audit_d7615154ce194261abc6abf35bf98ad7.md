### Title
`VesperGateway.deposit` credits the requested amount instead of the amount actually received - ([File: contracts/VesperGateway.sol](contracts/VesperGateway.sol))

### Summary
`VesperGateway.deposit` pulls `amount_` of a Vesper pool's underlying token, but then approves and deposits the same nominal `amount_` into the Vesper pool rather than measuring the gateway's post-transfer balance delta [1](#0-0) . For a fee-on-transfer underlying asset, the gateway receives less than `amount_`, while the requested deposit still assumes `amount_` is available [2](#0-1) . Normally this only reverts, but any underlying tokens already held by the gateway are silently consumed to satisfy the vault deposit, and the resulting `vToken` shares are deposited into Metronome for the caller [3](#0-2) .

### Finding Description
The vulnerable sequence is public and reachable through `deposit(IPool pool_, IVPool vToken_, uint256 amount_)` [4](#0-3) . The gateway transfers `amount_` from the caller without recording its own pre-transfer balance [5](#0-4) . It then approves the Vesper pool for the original `amount_` instead of the actual received amount [6](#0-5) .

The downstream vault shares minted to the gateway are calculated by balance delta, so all shares produced by the combined caller contribution and pre-existing gateway balance are credited to this operation [7](#0-6) . Finally, `DepositToken.deposit` transfers those shares to the treasury using balance-delta accounting and mints Metronome deposit tokens to `onBehalfOf_` [8](#0-7) .

Unlike `VesperGateway.deposit`, the core `DepositToken.deposit` implementation correctly replaces the requested amount with the treasury balance delta after `safeTransferFrom` [9](#0-8) .

### Impact Explanation
Pre-existing underlying tokens held by `VesperGateway` can be consumed to complete an attacker's underfunded deposit [2](#0-1) . Those tokens are recoverable only through governor-controlled `TokenHolder.sweep`, so they constitute assets entrusted to or recoverable by the protocol rather than part of the attacker's deposit [10](#0-9) .

The attacker receives the full minted `vToken` balance delta and corresponding Metronome deposit tokens, even though part of the nominal vault deposit was funded by the gateway's pre-existing balance [11](#0-10) . This breaks the collateral-deposit identity that minted `msdTOKEN` must represent only collateral contributed by the depositor.

If the Vesper pool calculates shares from the requested deposit amount while its own received underlying balance is lower, the resulting `vToken` position can also be overrepresented relative to the pool's backing; that can translate into overvalued Metronome collateral or a withdrawal claim funded by other Vesper depositors.

### Likelihood Explanation
Exploitation requires a supported Vesper collateral whose underlying asset charges a fee on transfer and requires the gateway to already hold enough underlying tokens to cover the fee-induced shortfall [12](#0-11) . The function itself is permissionless and requires only a registered Metronome pool plus a `vToken_` recognized by that pool [13](#0-12) .

`DepositToken.deposit` does not prevent the issue because it correctly accounts for the `vToken` balance delta; the incorrect accounting has already occurred at the underlying-to-vault stage [8](#0-7) .

### Recommendation
Measure the underlying balance received by the gateway and use that value for both the Vesper approval and deposit:

```solidity
// contracts/VesperGateway.sol
uint256 balanceBefore = _underlying.balanceOf(address(this));
_underlying.safeTransferFrom(_msgSender, address(this), amount_);
uint256 received = _underlying.balanceOf(address(this)) - balanceBefore;

_underlying.safeApprove(address(vToken_), 0);
_underlying.safeApprove(address(vToken_), received);

uint256 vTokenBefore = vToken_.balanceOf(address(this));
vToken_.deposit(received);
uint256 vTokenAmount = vToken_.balanceOf(address(this)) - vTokenBefore;
```

This preserves caller credit while preventing prior gateway balances from being folded into the caller's deposit [1](#0-0) .

### Proof of Concept
The following Hardhat test extends the existing `VesperGateway` fixture and demonstrates that a fee-bearing deposit consumes a pre-existing gateway balance while the caller receives shares/metronome credit based on the nominal amount [14](#0-13) .

```typescript
// test/VesperGateway.test.ts
it('consumes gateway balance when underlying has transfer fee', async function () {
  const latent = parseUnits('10', 6)
  const amount = parseUnits('100', 6)

  // Assets recoverable by the gateway are already present.
  await usdcMock.mint(vesperGateway.address, latent)

  // 10% fee on every ERC20 transfer.
  await usdcMock.updateFee(parseEther('0.1'))

  await usdcMock.connect(user).approve(vesperGateway.address, MaxUint256)
  await vesperGateway.connect(user).deposit(poolMock.address, vaUSDCMock.address, amount)

  // The caller paid 100 USDC, but only 90 reached the gateway.
  // The missing 10 was supplied by the gateway's pre-existing balance.
  expect(await usdcMock.balanceOf(vesperGateway.address)).eq(0)

  // The gateway still caused the vault to debit the nominal amount.
  const sharesMinted = parseUnits('100', 18)
  expect(await vaUSDCMock.balanceOf(treasury.address)).eq(sharesMinted)
  expect(await msdVaUSDC.balanceOf(user.address)).eq(sharesMinted)
})
```

The mock Vesper pool debits the full requested amount and mints shares from that nominal amount, making the consumption of latent gateway funds directly observable [15](#0-14) .
