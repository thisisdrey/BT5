### Title
Postponed self-promise on account X survives `DeleteAccount` and executes privileged actions against the recreated X - authorization escalation across account incarnations ([File: runtime/runtime/src/lib.rs], [File: core/store/src/utils/mod.rs], [File: runtime/runtime/src/actions.rs])

### Summary
`remove_account` (used by `action_delete_account`) removes the `Account`, its keys, gas-key nonces and contract data, but never touches `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, `TrieKey::PostponedReceiptId`, or `TrieKey::ReceivedData` entries keyed on that account's `receiver_id`. If a multi-dependency `ActionReceipt` with `predecessor_id == receiver_id == X` (a self-promise carrying privileged actions such as `AddKey`) was postponed before `X` self-deletes, the postponed state survives deletion and is later matched and executed by `Runtime::process_receipt`'s `Data` arm once the outstanding `DataReceipt`s finally arrive — with no check that `X` has existed continuously since the receipt was created. Because `check_actor_permissions` only compares `actor_id == account_id` by account-id string equality (not by account incarnation), and `actor_id` is seeded from `receipt.predecessor_id()`, the old self-authorized promise passes the permission check and mutates the *new* account's key set/state.

### Finding Description
- `Runtime::process_action_receipt` (`runtime/runtime/src/lib.rs:1593-1658`) postpones an `ActionReceipt` whose `input_data_ids` are not all satisfied, storing it via `set_postponed_receipt`/`PendingDataCount`/`PostponedReceiptId`, all keyed by `receiver_id` (i.e., `X`), independent of any concept of "account generation."
- `Runtime::process_receipt`'s `Data` arm (`runtime/runtime/src/lib.rs:1367-1474`) resolves a postponed receipt purely by looking up `TrieKey::PostponedReceiptId {receiver_id, data_id}` and `TrieKey::PendingDataCount`. When the last dependency arrives it fetches the postponed `Receipt` via `get_postponed_receipt` and immediately calls `apply_action_receipt` on it — there is no check anywhere in this path that account `X` still is the same account (or exists at all) as when the receipt was postponed.
- `remove_account` (`core/store/src/utils/mod.rs:505-575`) — invoked from `action_delete_account` (`runtime/runtime/src/actions.rs:314-390`, specifically line 371) — deletes `TrieKey::Account`, `TrieKey::ContractCode`, access keys/gas-key nonces, and `TrieKey::ContractData`, but does **not** remove any `PostponedReceipt`, `PendingDataCount`, `PostponedReceiptId`, or `ReceivedData` entries for the account being deleted.
- `check_actor_permissions` (`runtime/runtime/src/actions.rs:739-785`) gates privileged actions (`AddKey`, `DeleteKey`, `DeployContract`, `Stake`, `DeleteAccount`, etc.) solely on `actor_id == account_id` string equality. `actor_id` for a top-level receipt is seeded from `receipt.predecessor_id()`. A self-promise (`predecessor_id == receiver_id == X`) therefore always satisfies this check regardless of which "incarnation" of `X` is live when the receipt is finally resolved.

Exploit flow:
1. Attacker controls account `X` (e.g., a sub-account they can later relinquish/hand over, or a namespace they control the creation rules for).
2. From `X`, the attacker issues a batched call that produces a self-targeted `ActionReceipt` (`predecessor_id == receiver_id == X`) containing `Action::AddKey(<attacker-controlled backdoor key>)`, with two `input_data_ids` that depend on two cross-contract calls the attacker fully controls and can defer arbitrarily long.
3. This receipt is postponed (`PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` written under key `X`).
4. In the same or a later transaction, `X` self-deletes via `DeleteAccount` (passes `check_actor_permissions` and `account.locked().is_zero()`), which calls `remove_account` — the `Account` record, keys and code for `X` disappear, but the postponed-receipt bookkeeping above is left intact.
5. `X` is recreated (by the attacker for a victim, or by a third party under whatever creation rule permits it, e.g. via the parent account) as a fresh, funded account with a real access key and possibly a deployed contract.
6. The attacker now resolves the two pending `DataReceipt`s at a time of their choosing. `Runtime::process_receipt`'s `Data` arm finds the still-present `PostponedReceiptId`/`PendingDataCount` links, decrements to zero, fetches the old `AddKey` receipt, and calls `apply_action_receipt` against the trie state of the *new* `X`.
7. `check_actor_permissions` sees `actor_id == account_id == X` and approves the `AddKey`, silently granting the attacker's backdoor key full access on the victim's freshly created account.

Existing tests confirm the design intent that receipts always execute against the *current* state of the receiver id after delete+recreate (see `test_function_call_after_same_chunk_delete_recreate_resolves_fresh_code`, `runtime/runtime/src/tests/apply.rs:4877-4954`), but that test only covers a `FunctionCall`, where identity doesn't matter for authorization. For privileged self-actions gated by `check_actor_permissions`, this same "current state" resolution becomes an authorization bypass, because the self-authorization was made by a *different* account instance than the one being mutated. I was not able to directly view the exact line initializing `actor_id = receipt.predecessor_id()` in `apply_action_receipt` in this session (tool budget exhausted), but this is consistent with `check_actor_permissions`'s signature/usage in `apply_action` (`runtime/runtime/src/lib.rs:523-567`) and the documented "actor_id" semantics in `docs/RuntimeSpec/Actions.md:26-35`, which a background engineer should confirm with a debugger/unit test before finalizing the PoC.

### Impact Explanation
This is an authorization-escalation vulnerability: a postponed self-promise created by the *old* owner of an account executes with full self-authorization against the *new* owner's account state after a delete+recreate cycle, allowing the attacker to add an access key (or perform other `predecessor_id==receiver_id`-gated privileged actions) on an account they no longer legitimately control. This maps to NEAR's "theft of funds" / "authorization escalation across accounts" bounty category, since a full-access key added post-recreation lets the attacker drain the recreated account's balance and contract state.

### Likelihood Explanation
Exploitability requires the attacker to: (a) construct a genuinely postponed multi-dependency self-promise (achievable via a contract that issues a batched promise dependent on two attacker-controlled callback receipts), (b) self-delete the account via a normal `DeleteAccount` action, and (c) arrange for the same account id to be recreated afterward with new value while the dependency receipts are still outstanding. Step (c) is the main constraint — it requires a scenario where account-id reuse under new ownership occurs (e.g., subaccount namespace resale/handoff, or an implicit account whose original controlling key is later reused) and where the resolving `DataReceipt`s can be deliberately delayed by the attacker (fully within an unprivileged attacker's control via which contract/promise chain produces them). No validator, node, or privileged component involvement is needed — everything is driven by ordinary signed transactions from a funded account. This is a real path but with non-trivial setup requirements (dependent on account-id reuse being possible for the target subaccount/namespace).

### Recommendation
When an account is deleted, `remove_account` (or `action_delete_account`) should also purge any outstanding `PostponedReceipt`, `PendingDataCount`, and `PostponedReceiptId` entries (and orphaned `ReceivedData`) keyed by that `receiver_id`, refunding/erroring the pending promise instead of leaving it dangling for a future incarnation of the same account id. Alternatively, `check_actor_permissions`/postponed-receipt resolution should bind postponed receipts to an account-existence generation counter (or simply reject resolution of a postponed receipt whose target account was deleted and recreated since it was postponed), so a stale self-authorization can never apply to a different account incarnation.

### Proof of Concept
Integration/runtime test-loop plan:
1. Deploy a contract on account `X` that, in one call, creates a batched action receipt targeting itself (`predecessor_id == receiver_id == X`) with `Action::AddKey(backdoor_pk)`, and two `input_data_ids` tied to two separate cross-contract promises whose resolution the test controls explicitly (e.g., via `PromiseReturn`/callback receipts constructed directly, similar to `create_receipt_with_actions` helpers already used in `runtime/runtime/src/tests/apply.rs`).
2. Apply the chunk so the `AddKey` receipt becomes postponed (assert `PostponedReceipt`/`PendingDataCount` exist in state via `get_postponed_receipt`/`get`).
3. In a subsequent chunk, apply a `DeleteAccount` receipt (`predecessor_id == receiver_id == X`, `beneficiary_id` = some other account) and commit. Assert `get_account(state_update, X)` is `None`, but `get_postponed_receipt`/`PendingDataCount`/`PostponedReceiptId` for `X` are still present (demonstrating the cleanup asymmetry in `remove_account`).
4. Apply a `CreateAccount` receipt recreating `X` (new owner, new access key, possibly deploy a contract), and commit.
5. Deliver the two outstanding `DataReceipt`s targeting `X` in a following chunk.
6. Assert: (a) the postponed `AddKey(backdoor_pk)` receipt executes successfully (`ExecutionOutcome` success, no `ActorNoPermission` error), and (b) `get_access_key(state_update, X, backdoor_pk)` now returns `Some(..)` on the *new* account — proving the old account's self-authorized action mutated the new account's key set.
7. Compare against expected/fixed behavior: the postponed receipt should instead be purged at deletion time (assert `ActionErrorKind`/receipt failure or absence of postponed state) so step 6's `AddKey` never executes against the recreated account.
