### Title
Attached deposit permanently stuck in eth-implicit `WalletContract` when `address_check_callback`/`nep_141_storage_balance_callback` return early with an error - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
The Ammplify bug is a "funds captured for later transfer, but the transfer path is never reached" class of issue: fees are collected and tracked, but several code paths short-circuit before the mechanism responsible for returning them to the rightful owner ever runs. The `WalletContract` (eth-implicit account contract) in this repo has the same bug class: an external caller's attached deposit (`CallerDeposit`) is tracked so it can be refunded later, but several early-return branches in `address_check_callback` and `nep_141_storage_balance_callback` drop the `caller_deposit` value entirely instead of refunding it, permanently stranding the NEAR balance in the wallet contract.

### Finding Description
`rlp_execute` is `#[payable]`, so any external, non-privileged account can attach a NEAR deposit when calling it on someone else's eth-implicit wallet contract (e.g., as a relayer fee/incentive). `inner_rlp_execute` builds a `CallerDeposit` to track this deposit so it can be refunded if the resulting cross-contract action ultimately fails: [1](#0-0) [2](#0-1) 

The only place this tracked deposit is ever actually refunded is inside `rlp_execute_callback`, and only on the `PromiseResult::Failed` branch: [3](#0-2) 

However, `caller_deposit` is threaded through two intermediate callbacks — `address_check_callback` and `nep_141_storage_balance_callback` — which have multiple early-return branches that produce an error `ExecuteResponse` *without* forwarding `caller_deposit` to `rlp_execute_callback` and without creating any refund promise themselves:

- `address_check_callback`: registrar lookup failed, malformed registrar response, or target resolves to an existing named account: [4](#0-3) 

- `nep_141_storage_balance_callback`: `storage_balance_of` call failed, malformed response, or action type mismatch: [5](#0-4) 

In every one of these branches the function simply returns `PromiseOrValue::Value(ExecuteResponse {...})`; the `caller_deposit` parameter is dropped in scope and no transfer back to `caller_deposit.account_id` is ever issued. Because `WalletContract` exposes no withdrawal/sweep method (only `get_nonce`, `rlp_execute`, the callbacks, and `ban_relayer`), the deposit that was attached to the original `rlp_execute` call remains locked in the wallet contract's balance indefinitely — exactly analogous to the Ammplify case where collected fees land in `NFTManager` but the code path that should forward them to the user is never invoked.

### Impact Explanation
This causes real, permanent freezing of NEAR tokens belonging to an unprivileged external caller (a relayer submitting an eth-emulated transaction on behalf of an eth-implicit account owner, attaching a deposit as network/relayer coverage). Multiple reachable, non-malicious conditions trigger the loss:
- The address registrar contract call fails or returns malformed data.
- The `target` address happens to correspond to an existing named account (a legitimate, commonly occurring condition for `EOABaseTokenTransfer` with `address_check`).
- The `storage_balance_of` call to an NEP-141 token fails or returns unexpected data during an emulated ERC-20 transfer.
- The action decoded is not a `FunctionCall` when a `nep_141_storage_balance_callback` expects a transfer function call (edge case in encoding/decoding but still a callback-reachable branch).

None of these require a malicious actor — they are plausible operational failures (an unavailable registrar, a re-registered account, a flaky/failing token contract) that any relayer following the intended interaction pattern could trigger, resulting in unrecoverable loss of the attached NEAR deposit.

### Likelihood Explanation
Likelihood is moderate-to-high in practice: any relayer using the standard eth-implicit-account flow with `EOABaseTokenTransfer{address_check: Some(_)}` or `ERC20Transfer` and a non-zero attached deposit will hit this bug whenever the auxiliary lookup call (`address_registrar.lookup` or `token.storage_balance_of`) fails or returns an unexpected/negative result — situations that are not adversarial, just ordinary failure modes of external cross-contract calls.

### Recommendation
In every early-return `PromiseOrValue::Value(...)` branch of `address_check_callback` and `nep_141_storage_balance_callback` that carries a `caller_deposit: Some(_)`, issue a transfer refund back to `caller_deposit.account_id` (mirroring the logic already present in `rlp_execute_callback`'s `PromiseResult::Failed` arm) before returning the error response, instead of silently dropping the value.

### Proof of Concept
1. Relayer A calls `rlp_execute` on wallet contract `W` (owned by user U) with a non-zero attached deposit and an RLP-encoded `EOABaseTokenTransfer` targeting address `X` with `address_check: Some(X)`.
2. `inner_rlp_execute` builds `caller_deposit = Some(CallerDeposit{account_id: A, yocto_near: deposit})` and schedules `address_registrar.lookup(X).then(address_check_callback(target, action, caller_deposit))`. [6](#0-5) 
3. The registrar call fails, or succeeds but its response is malformed serde JSON — `address_check_callback` hits the `PromiseResult::Failed` or `Err(_)` branch and returns `PromiseOrValue::Value(ExecuteResponse{success:false,...})` directly, never touching `caller_deposit`. [7](#0-6) 
4. No refund receipt is ever generated back to A; A's deposit remains permanently held in W's account balance with no contract method to retrieve it.
