### Title
Any user can permanently block a victim's ability to add collateral or borrow new synthetics by dust-filling their per-account token list to `MAX_TOKENS_PER_USER` - (File: contracts/Pool.sol)

### Summary
Analogous to CVE-2017-8031 (an authenticated user revoking *other* users' tokens on the same client), Metronome lets any unprivileged account force-add entries into another account's `depositTokensOfAccount` list. Once the combined `depositTokensOfAccount + debtTokensOfAccount` length reaches `MAX_TOKENS_PER_USER = 30`, every code path that would add a new token to the victim — `DepositToken.deposit(onBehalfOf_=victim)`, first-time `transfer`/`transferFrom` of a new DepositToken to the victim, and `DebtToken.issue` for a new synthetic — reverts with `UserReachedMaxTokens`. An attacker can cheaply dust-send the victim 1 wei of each registered DepositToken to reach the cap, denying the victim the ability to deposit new collateral types or open new debt positions until they fully exit an existing token.

### Finding Description
`Pool.addToDepositTokensOfAccount` and `Pool.addToDebtTokensOfAccount` are guarded by `onlyIfAdditionWillNotReachMaxTokens`, which reverts once an account's combined token count hits 30 [1](#0-0) . These functions are invoked from `DepositToken._mint` and `DepositToken._transfer` whenever the recipient's balance of that token transitions 0 → positive [2](#0-1) [3](#0-2) . The sender is never consulted — the entry is added for `recipient_`/`onBehalfOf_`, not for the caller.

Attack path (all calls are public, unprivileged):

1. Attacker deposits a minimal amount of each registered collateral (or acquires dust DepositTokens) under their own account.
2. For each `DepositToken` the victim does not yet hold, attacker calls `depositToken.transfer(victim, 1)` — `transfer` only enforces `_revertIfLocked` on the *sender* [4](#0-3) , and `_transfer` pushes the token onto the victim's list via `addToDepositTokensOfAccount` [3](#0-2) .
3. Equivalently, `deposit(amount_, victim)` mints to the victim, hitting the same list-add [5](#0-4) .
4. Once `debtTokensOfAccount.length(victim) + depositTokensOfAccount.length(victim) >= 30`, `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` revert, and the revert propagates: `deposit()` of any new collateral reverts, `transfer`/`transferFrom`/`seize` to the victim of a token they don't hold reverts, and `DebtToken.issue` of a new synthetic reverts (its `_mint` calls `addToDebtTokensOfAccount`).

No modifier stops this: `transfer`/`deposit` are unprivileged, the victim's consent is not required, `unlockedBalanceOf`/`_revertIfLocked` only restrict the sender, and the list-add is unconditional on the recipient.

### Impact Explanation
Two concrete harms on a victim:

- **Forced liquidation / inability to rescue a position**: if the victim's position drifts unhealthy (including via ordinary market moves or attacker-assisted price manipulation), the victim cannot deposit a *new* collateral type to restore health — every such deposit reverts — while `Pool.liquidate` remains fully usable by anyone against the victim [6](#0-5) . The attacker (or any liquidator) seizes collateral at the liquidation discount, producing a direct loss equal to the liquidation incentive plus protocol fee.
- **Temporary freezing of composability**: the victim cannot receive new DepositToken types (transfers revert), cannot issue new synthetic assets, and cannot be the `onBehalfOf_` beneficiary of new deposits, until they fully zero-out one existing token balance to free a slot.

### Likelihood Explanation
Cost is bounded: one dust transfer per registered DepositToken the victim lacks. Feasibility requires the pool to have enough registered deposit tokens — alone or combined with the victim's existing deposit/debt tokens — to reach 30. This is the main constraint: on pools with fewer registered collaterals the cap may be unreachable for fresh accounts, but accounts already holding several collateral and debt positions (e.g. SmartFarmingManager leverage across multiple vaults) can be pushed over the cap with far fewer dust sends. The revert behavior at the cap is confirmed by the protocol's own tests [7](#0-6) .

### Recommendation
Make list membership opt-in or decouple it from balance receipt: e.g., have `deposit`/`issue` manage list membership only for explicit `onBehalfOf_` accounting while letting plain `transfer` credit balances without registering (with `depositOf`/`debtOf` accounting balances directly rather than via the list), or raise/remove the hard revert by capping iteration cost differently. At minimum, do not let a forced 0→positive transfer consume a slot — skip the list-add on unsolicited dust below a threshold, or allow the recipient to prune entries.

### Proof of Concept
Hardhat-style fork/unit test sketch (existing test harness from `test/Pool.test.ts` applies):

```ts
// Setup: pool with N registered DepositTokens such that
// N (attackable) + victim's existing entries >= MAX_TOKENS_PER_USER (30).
const victim = alice.address
const dust = 1n

// Attacker mints a dust balance of each DepositToken they want to push,
// then sends 1 wei to the victim. Each transfer registers the token on
// the victim's account via addToDepositTokensOfAccount.
for (const dt of depositTokens) {
  await underlying.mint(attacker.address, dust)
  await underlying.connect(attacker).approve(dt.address, dust)
  await dt.connect(attacker).deposit(dust, attacker.address)
  await dt.connect(attacker).transfer(victim, dust) // adds dt to victim's list
}

// Victim's combined token count is now >= 30.
expect(
  (await pool.getDepositTokensOfAccount(victim)).length +
  (await pool.getDebtTokensOfAccount(victim)).length
).to.be.gte(30)

// 1) Victim cannot deposit a collateral type they don't already hold:
await met.mint(victim, parseEther('1000'))
await met.connect(alice).approve(msdNewCollateral.address, MaxUint256)
await expect(
  msdNewCollateral.connect(alice).deposit(parseEther('100'), victim)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')

// 2) Victim cannot issue a new synthetic type:
await expect(
  newDebtToken.connect(alice).issue(parseEther('1'), victim)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')

// 3) A third party cannot even gift the victim a new DepositToken type:
await expect(
  someDepositToken.connect(third).transfer(victim, 1)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')
```

Then, with the victim's position pushed underwater (price move), `pool.liquidate(...)` succeeds while every collateral top-up by the victim reverts — demonstrating the denial of service translating into loss via liquidation.

**Caveat**: the attack is only reachable if the victim's attainable combined token count can reach `MAX_TOKENS_PER_USER = 30`. Attackers can only force-add *deposit* tokens (debt token entries require the victim to issue). If a deployed pool registers fewer deposit tokens than needed and the victim holds few positions, the cap cannot be reached and the DoS is not exploitable on that pool; the severity of this finding therefore depends on the number of registered collaterals in each deployed pool.
