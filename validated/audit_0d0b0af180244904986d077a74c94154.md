## Finding

### Title
Unbounded array allocation from attacker-controlled length field in `BatchValidateSign`/`ValidateMultiSign` precompiles causes OOM/DoS - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The ffmpeg `asf_read_marker()` bug class is: a header declares a large item/loop count, but the code allocates buffers and loops based on that declared count without validating it against the amount of data actually present, causing huge CPU/memory consumption. The analogous pattern exists in java-tron's TVM precompiled-contract helpers `extractBytes32Array`, `extractBytesArray`, and `extractSigArray`, which are reachable from any TVM `CALL`/`STATICCALL` to the `validatemultisign` and `batchvalidatesign` precompiles.

### Finding Description
`extractBytes32Array` reads an attacker-supplied length word directly from calldata and immediately allocates an array of that size before validating it against the real size of the decoded `words` array: [1](#0-0) 

```
private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
}
```

`extractBytesArray` and `extractSigArray` have the same pattern: `len` comes straight from `words[offset].intValueSafe()` (an unconstrained 32-byte ABI word, only clamped to the `int` range, not to the actual `words.length`), and the code both (a) allocates `new byte[len][]` and (b) loops `len` times indexing into `words[offset + i + 1]`, which is far smaller than `len` for a crafted call: [2](#0-1) [3](#0-2) 

In `BatchValidateSign.doExecute`, the guard that caps this length to `MAX_SIZE` (16) is applied *only* when `VMConfig.allowTvmSelfdestructRestriction()` is true; the call to `extractBytes32Array` is unconditional: [4](#0-3) 

```
if (VMConfig.allowTvmSelfdestructRestriction()) {
  int sigArraySize = words[words[1].intValueSafe() / WORD_SIZE].intValueSafe();
  int addrArraySize = words[words[2].intValueSafe() / WORD_SIZE].intValueSafe();
  if (sigArraySize > MAX_SIZE || addrArraySize > MAX_SIZE) {
    return Pair.of(true, DATA_FALSE);
  }
}
...
byte[][] addresses = extractBytes32Array(
    words, words[2].intValueSafe() / WORD_SIZE);
```

`ValidateMultiSign.execute` has the identical conditional guard/unconditional-call structure for `extractBytesArray`/`extractSigArray`: [5](#0-4) 

When `allowTvmSelfdestructRestriction` has not been activated on a given network (it is a TIP hard-fork proposal gated by dynamic-store activation, not a compile-time constant, see `DynamicPropertiesStore.java`/`VMConfig.java`), any account can call these precompiles directly (or via a deployed contract's `CALL`) with an ABI-encoded length word (`words[offset]`) set to a very large value while supplying only a short calldata buffer. `extractBytes32Array`/`extractBytesArray` then attempt `new byte[len][]` for an attacker-chosen `len` up to `Integer.MAX_VALUE`, and the subsequent loop reads `words[offset + i + 1]` far past the bounds of the actual `words` array — mirroring the ffmpeg `asf_read_marker()` defect where a large declared count is used to drive a loop/allocation without checking it against the real backing-data size.

### Impact Explanation
- `new byte[len][]` with an attacker-controlled `len` close to `Integer.MAX_VALUE` triggers an immediate massive heap allocation attempt, which can throw `OutOfMemoryError` inside the TVM execution path. Depending on how far the exception propagates and whether it's caught by the surrounding node/JVM machinery, this can crash the node process or destabilize the JVM (other threads may also start failing due to heap pressure), leading to full-node denial of service.
- Even where allocation succeeds for moderately large `len`, `words[offset + i + 1]` for `i` beyond the actual `words.length` throws `ArrayIndexOutOfBoundsException`; in `BatchValidateSign.execute` this is caught by the outer `try { doExecute(data); } catch (Throwable t) { ... }` and degraded to a no-op false result, but in `ValidateMultiSign.execute` there is no equivalent outer catch around `extractBytesArray`/`extractSigArray`, so it can propagate as an uncaught runtime exception in TVM contract execution.
- The affected precompiles are reachable directly by an unprivileged transaction/contract caller (`TriggerSmartContract`), matching the "unpriv contract caller reaches actuator/TVM precompile" reachability requirement.

### Likelihood Explanation
Reachability requires only a standard `TriggerSmartContract` (or a deployed contract issuing a `CALL`/`STATICCALL`) to the `ValidateMultiSign`/`BatchValidateSign` precompile addresses with crafted calldata — no special privilege, SR/witness status, or p2p access needed. The condition is gated by whether `allowTvmSelfdestructRestriction` has been activated via committee proposal on the target chain; on networks where it has not yet been activated (or is disabled for testing/private chains), the vulnerable code path executes unconditionally.

### Recommendation
Move the `MAX_SIZE` (and a hard upper bound derived from `words.length`) validation of the declared array length into `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` themselves, unconditionally (not gated behind `allowTvmSelfdestructRestriction`), so that `len` is always checked against `words.length - offset - 1` before any allocation, and reject with `Pair.of(false, EMPTY_BYTE_ARRAY)` (or equivalent) when the declared count exceeds the actual available data.

### Proof of Concept
1. Craft calldata for `batchvalidatesign(bytes32,bytes[],address[])` (or `validatemultisign(...)`) where the offset word for the `address[]` (or `bytes[]`) parameter points to a length word encoding a very large value (e.g., `0x7FFFFFFF`), while the total calldata is only a few hundred bytes long.
2. Ensure the target chain has not activated the `AllowTvmSelfdestructRestriction` proposal (default/unactivated state), so the `MAX_SIZE` pre-check in `doExecute`/`execute` is skipped.
3. Submit a `TriggerSmartContract` transaction that performs a `CALL`/`STATICCALL` to the `BatchValidateSign`/`ValidateMultiSign` precompile address with this calldata.
4. `extractBytes32Array`/`extractBytesArray` executes `new byte[0x7FFFFFFF][]`, triggering an `OutOfMemoryError` (or a huge `ArrayIndexOutOfBoundsException` if a smaller-but-still-oversized length is chosen relative to actual `words.length`), reproducing the "huge CPU/memory consumption from unchecked count field" bug class of CVE-2017-14057 within the TVM.

Note: I was unable to fully confirm the exact clamping behavior of `DataWord.intValueSafe()` from the index (its implementation in `common/src/main/java/org/tron/common/runtime/vm/DataWord.java` was not retrievable within the available tool calls), so the precise maximum value `len` can take (e.g., whether it's capped below `Integer.MAX_VALUE`) should be verified directly in that file before finalizing severity/exploitability details.
