Audit Report

## Title
Deterministic asset-conversion failures in inbound message processing revert the extrinsic and roll back nonce consumption, permanently blocking recovery of Ethereum-locked funds for that message - (File: `bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs`, `bridges/snowbridge/primitives/inbound-queue/src/v2/converter.rs`)

## Summary
`Pallet::process_message` marks a message `Nonce` as consumed and then calls `T::MessageProcessor::process_message`, which internally invokes `MessageToXcm::convert` → `prepare`. If the message contains a `ForeignTokenERC20` asset whose `TokenId` cannot be resolved via `ConvertAssetId::maybe_convert` (or whose resolved location fails `reanchored`), `prepare` returns `Err(ConvertMessageError::InvalidAsset)` or `Err(ConvertMessageError::CannotReanchor)` before any XCM is constructed. Because every `#[pallet::call]` dispatchable is wrapped in `frame_support::storage::with_storage_layer`, this `Err` causes the entire `submit` extrinsic — including the prior `Nonce::<T>::set(nonce)` write — to be rolled back, and since these errors are deterministic functions of the message content and runtime configuration, no resubmission can ever succeed for that nonce.

## Finding Description
`process_message` (`bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs:214-245`) does:
```rust
Nonce::<T>::set(nonce);
let message_id = T::MessageProcessor::process_message(relayer.clone(), message)
    .map_err(|e| match e {
        MessageProcessorError::ConvertMessage(e) => Error::<T>::from(e).into(),
        ...
    })?;
```
`MessageProcessor::process_message` calls `MessageToXcm::convert` (`bridges/snowbridge/primitives/inbound-queue/src/v2/converter.rs:375-426`), which first calls `Self::prepare(message)` (line 376). In `prepare` (lines 125-217), a `ForeignTokenERC20` asset whose `TokenId` is unregistered returns `Err(ConvertMessageError::InvalidAsset)` at line 183, and a resolved-but-unreanchorable location returns `Err(ConvertMessageError::CannotReanchor)` at line 195 — both occur *before* any `Xcm` instructions are built, so there is no opportunity to "trap" assets via `AssetClaimer` (that mechanism only exists inside the constructed XCM, e.g. the `SetHints{AssetClaimer}` instruction added at converter.rs:388-392, which is only reached if `prepare` succeeds).

I confirmed the FRAME transactional-rollback premise: `#[pallet::call]` dispatchables are automatically wrapped in `with_storage_layer`, verified in the pallet macro expansion [1](#0-0) 
and documented explicitly: [2](#0-1) 
`with_storage_layer` rolls back all storage changes on `Err`: [3](#0-2) 
Therefore `Nonce::<T>::set(nonce)` at [4](#0-3) 
is reverted whenever `ConvertMessage::convert` returns `Err`, confirmed by the mapping of `ConvertMessageError` to pallet errors: [5](#0-4) 
and the corresponding test asserting the conversion itself errors (not just the XCM being empty): [6](#0-5) 

This is in contrast to the deliberately implemented "invalid remote XCM" fallback, where malformed XCM payload bytes are decoded permissively into an empty `Xcm::new()` (`decode_raw_xcm`, converter.rs:327-342) so that `convert` still succeeds and the message can still be trapped/claimed downstream — confirmed by `test_invalid_xcm` explicitly asserting `assert_ok!` for a garbled payload: [7](#0-6) 
No equivalent graceful-degradation path exists for `ForeignTokenERC20` asset-resolution failures — the code chooses to `Err` outright with `.ok_or(ConvertMessageError::InvalidAsset)?` / `.map_err(|_| ConvertMessageError::CannotReanchor)?` rather than skipping the unresolvable asset or falling back to a trap, unlike the deliberate best-effort handling used for the XCM-payload and claimer-decoding cases (see also `test_invalid_claimer` at lines 730-806, which likewise degrades gracefully instead of erroring).

## Impact Explanation
This matches the impact-gate category "permanent user-fund or bridge-state lock." Once a relayer submits a valid, correctly-proven Ethereum event referencing a `ForeignTokenERC20` with an unregistered/unreanchorable `TokenId`, `submit` will deterministically fail for that exact nonce forever (since message content is fixed once emitted on Ethereum), the nonce is never marked processed (rolled back), and the corresponding locked value on the Ethereum Gateway contract has no on-chain recovery mechanism on the Polkadot side, unlike the "invalid XCM" case which is explicitly designed to succeed and trap funds via `AssetClaimer`.

## Likelihood Explanation
No privileged actor, governance action, or compromised relayer is required. Any unprivileged Ethereum-side sender can construct a message with a `ForeignTokenERC20` `token_id` that is not (or no longer) registered in `ConvertAssetId` (backed by `EthereumSystem`/`snowbridge-pallet-system(-v2)`), and any honest relayer submitting the resulting, correctly-proven event will hit this deterministic revert on every attempt. This requires no adversarial infrastructure control — only ordinary use of the public `submit` extrinsic with content that references an asset id not registered in pallet-system's `ForeignToNativeId`/`NativeToForeignId` mappings (or one whose location later fails to reanchor due to a runtime config change), which is a realistic, plausible operational scenario (e.g., a token being deregistered, or a message referencing a not-yet-registered token).

## Recommendation
- **Short term**: When `ConvertMessage::convert` fails with a deterministic/permanent error (`InvalidAsset`, `CannotReanchor`), still advance `Nonce`/pay the relayer and construct a minimal fallback XCM that traps/deposits the recoverable portion of assets to the message's `claimer` (mirroring the `decode_raw_xcm` graceful-degradation pattern already used for malformed payloads), rather than propagating a hard `Err` that reverts the entire extrinsic.
- **Long term**: Classify `ConvertMessageError`/`MessageProcessorError` variants as retryable vs. permanent, and guarantee nonce/state advancement for all permanent-failure cases, backed by an integration test analogous to `invalid_xcm_traps_funds_on_ah` but for unregistered/unreanchorable `ForeignTokenERC20` assets.

pub fn with_storage_layer<T, E, F>(f: F) -> Result<T, E>
where
	E: From<DispatchError>,
	F: FnOnce() -> Result<T, E>,
{
	with_transaction(|| {
		let r = f();
