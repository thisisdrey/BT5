### Title
Forced-inclusion L2 transactions are blocked by the `SenderIsNotTheOwner` check in `ProxyOFT._debitFrom`, freezing bridged synthetic tokens while the sequencer is down - ([File: contracts/ProxyOFT.sol](contracts/ProxyOFT.sol))

### Summary
`ProxyOFT._debitFrom` enforces that `_msgSender()` equals the `from_` owner of the synthetic tokens being bridged. On OP-Stack/Arbitrum-style rollups where Metronome is deployed (Optimism, Base, Hemi, Swell), a contract that submits `sendFrom` via forced L1 inclusion while the sequencer is down arrives on L2 with an *aliased* `msg.sender`. The alias never equals the contract's real L2 address stored in `from_`, so the call reverts and the tokens cannot be bridged back for the duration of the outage.

### Finding Description
`sendFrom` routes through `OFTCoreUpgradeable._send`, which calls `ProxyOFT._debitFrom`. The ownership check is:

```solidity
if (_msgSender() != from_) revert SenderIsNotTheOwner();
``` [1](#0-0) 

`_msgSender()` resolves through `SynthContext._msgSender`, which returns the raw `msg.sender` unless the caller is the `Operator` (in which case it returns the transiently stored `MSG_SENDER`, which is also set from raw `msg.sender` in `Operator.execute`). [2](#0-1) [3](#0-2) 

Neither path accounts for L1→L2 address aliasing. On Optimism (`L1 → aliased sender = L1_contract + 0x1111...`) and Arbitrum retryable tickets, a contract calling `sendFrom(from_=itself, ...)` via the forced-inclusion/deposit path produces `msg.sender = alias(contract) != contract`. The comparison fails deterministically, `_debitFrom` reverts, and `syntheticToken.burn(from_, amount_)` is never reached.

The check also cannot be worked around by having the aliased address pass `from_` equal to itself, because the token balance sits on the un-aliased contract address — `syntheticToken.burn` would debit an empty balance. Similarly, routing through `Operator.execute` doesn't help: `Operator` stores the aliased caller into `MSG_SENDER`, so `_msgSender()` still resolves to the alias.

### Impact Explanation
Any contract (multisig, protocol treasury, integration contract) holding `msXYZ` synthetic tokens on an L2 deployment cannot bridge them out via `sendFrom`/`sendAndCall`-equivalent flows while the sequencer is down. This is a temporary freezing of funds for the outage window — exactly the liveness invariant broken in the reference report. Positions are not at risk of theft (the check fails closed), but time-sensitive exits (e.g., moving collateral to mainnet to avoid liquidation or to meet obligations) are impossible until the sequencer recovers.

### Likelihood Explanation
Sequencer outages on Optimism/Base/Arbitrum have occurred historically, and forced inclusion is the documented escape hatch. The affected user set is narrowed to contracts (EOAs are not aliased), but contracts holding synthetic tokens are a normal configuration (treasuries, safes, integration contracts). The failure is deterministic — 100% of forced-inclusion `sendFrom` calls by the token-owning contract revert.

### Recommendation
In `ProxyOFT._debitFrom`, additionally accept the L1→L2 aliased form of `from_` when the caller is an L1 contract reaching L2 via forced inclusion, e.g.:

```solidity
address sender = _msgSender();
if (sender != from_ && sender != AddressAliasHelper.applyL1ToL2Alias(from_)) {
    revert SenderIsNotTheOwner();
}
```

Note that applying the alias to `from_` covers the case where `from_` is itself an L1 contract address; the semantics to verify is whether `from_`'s L1 counterpart initiated the deposit. Whichever direction is chosen, the intent is to recognize the aliased counterpart of the token owner so forced-inclusion redemptions succeed. The same consideration applies to any other identity-style check reachable from `Operator.execute` during sequencer downtime.

### Proof of Concept
Hardhat fork of Optimism (Metronome is deployed there: `deployments/optimism/Operator.json` exists):

1. Deploy contract `C` on L2; transfer `msUSD` (a `SyntheticToken` bridged through `ProxyOFT`) to `C` so `C` is the token owner.
2. From `C`, call `proxyOFT.sendFrom(address(C), dstChainId, to, amount)` — succeeds normally.
3. Simulate forced inclusion: derive `alias = address(uint160(address(C)) + 0x1111000000000000000000000000000000001111)` and impersonate `alias` (via `hardhat_impersonateAccount`) to call `proxyOFT.sendFrom(address(C), dstChainId, to, amount)`.
4. Observe `SenderIsNotTheOwner` revert at `contracts/ProxyOFT.sol:77`, while `C`'s token balance remains locked. Optionally repeat via `operator.execute([{target: proxyOFT, callData: sendFrom(...)}])` from `alias` — `SynthContext._msgSender()` resolves to `alias` through `MSG_SENDER` and the call still reverts, confirming no workaround exists during sequencer downtime.
