### Title
Frontrunning dust-size liquidations DoSes liquidators that repay the maximum allowed amount - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool.liquidate` reverts when `amountToRepay_ / debtBalance > maxLiquidable`. A liquidator who repays the maximum liquidable amount (e.g. the full debt when `maxLiquidable == 100%`, or the close factor otherwise) can be permanently frontrun by an unprivileged attacker repaying a dust amount of the same position, which shrinks `_debtTokenBalance` and makes the victim's transaction revert. The same dust-frontrun pattern works against `DebtToken.issue` (via the permissionless `accrueInterest()`) and against `DebtToken.repay` via the `RemainingDebtIsLowerThanTheFloor` check.

### Finding Description
In `Pool.liquidate`, the liquidable fraction is computed against the *current* debt balance inside the transaction, not against the amount the liquidator observed off-chain:

```solidity
uint256 _debtTokenBalance = _debtToken.balanceOf(account_);
if (amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable) {
    revert AmountGreaterThanMaxLiquidable();
}
``` [1](#0-0) 

A liquidator computing `amountToRepay_ = debtBalance * maxLiquidable` (the rational choice to maximize profit per tx) has zero slack. Any prior transaction that reduces `debtBalance` — even by 1 wei — makes the fraction exceed `maxLiquidable` and reverts the whole transaction.

Attack path (fully unprivileged):
1. Attacker opens their own position: deposits collateral via `Pool.deposit`, issues synths via `DebtToken.issue` (needs ≥ `debtFloorInUsd` if set), holding spendable synthetic tokens.
2. Attacker monitors the mempool for `pool.liquidate(synth, victim, maxAmount, depositToken)`.
3. Attacker frontruns with `pool.liquidate(synth, victim, 1 wei, depositToken)`. `liquidate` is permissionless (anyone can liquidate anyone); the only constraints are `amountToRepay_ != 0` and `_msgSender != account_` [2](#0-1) . The dust liquidation also pays the attacker a tiny liquidation bonus.
4. The victim's transaction reverts with `AmountGreaterThanMaxLiquidable`.

The same mechanism exists in two sibling functions:
- `DebtToken.repay`: a user repaying their full balance with `repay(self, fullAmount)` is griefed by a dust `repay(self, dust)` — the leftover debt lands in `(0, debtFloorInUsd)` and reverts at `RemainingDebtIsLowerThanTheFloor` [3](#0-2) . (The user can fall back to `repayAll`, but an attacker can repeat the grief, and integrators/smart contracts calling `repay` with fixed amounts break.)
- `DebtToken.issue`: a user minting the max `_issuableInUsd` is griefed for free — `accrueInterest()` is `public` [4](#0-3) , and calling it grows `balanceOf`, shrinking `_issuableInUsd` so the max mint reverts with `NotEnoughCollateral` [5](#0-4) . Likewise, a dust `issue`/`deposit` fills `maxTotalSupply` and makes cap-sized deposits reverts via `SurpassMaxDebtSupply`/`SurpassMaxDepositSupply` [6](#0-5) .

### Impact Explanation
Temporary freezing of funds / liveness degradation with no capital cost:
- Liquidations sized at the max liquidable amount are griefable repeatedly, delaying liquidation of underwater positions (a solvency-adjacent liveness concern) and forcing liquidators to leave slack, reducing their profit.
- Max-size mints, repays, and cap-boundary deposits revert indefinitely while an attacker is willing to keep frontrunning, forcing users into strictly worse fills or smaller amounts — the exact harm class of the auction-bid dust DoS.

### Likelihood Explanation
High feasibility: `liquidate`, `repay`, `issue`, `deposit`, and `accrueInterest` are all unprivileged public entry points. The attacker needs only a self-opened healthy position (or zero capital for the `accrueInterest` variant) and mempool monitoring. Incentives exist naturally — a competing liquidator griefs rivals' max-size liquidations to win the position itself, mirroring the auction scenario. No modifier (`whenNotShutdown`, `nonReentrant`, existence checks) prevents it, and no minimum liquidation/repay amount exists.

### Recommendation
- In `Pool.liquidate`, cap `amountToRepay_` to `maxLiquidable.wadMul(_debtTokenBalance)` instead of reverting, or add a `minAmountOut`-style slippage parameter.
- In `DebtToken.repay`, when the remaining debt would fall below `debtFloorInUsd`, treat the request as `repayAll` (repay the full balance) rather than reverting.
- For `issue`/deposits, either clamp to available issuable/capacity or add a minimum-received parameter so users can express tolerance for reduced amounts.

### Proof of Concept
Foundry-style sketch against deployed-style fixtures:

```solidity
function test_dustLiquidationGrief() public {
    // alice: unhealthy position with msETH debt = D, collateral = msdMET
    // maxLiquidable = 50% (or 100%)
    uint256 debtBalance = msEthDebtToken.balanceOf(alice);
    uint256 amountToRepay = debtBalance.wadMul(pool.maxLiquidable());

    // bob: healthy position holding synthetic msETH
    vm.prank(bob);
    pool.liquidate(address(msEth), alice, 1, address(msdMET)); // dust frontrun

    // liquidator's precomputed max repay now exceeds maxLiquidable
    vm.prank(liquidator);
    vm.expectRevert(Pool.AmountGreaterThanMaxLiquidable.selector);
    pool.liquidate(address(msEth), alice, amountToRepay, address(msdMET));
}

function test_dustRepayFloorGrief() public {
    uint256 debt = msEthDebtToken.balanceOf(alice);
    // attacker repays dust so remaining debt is in (0, debtFloorInUsd)
    vm.prank(bob);
    msEthDebtToken.repay(alice, debt - dustBelowFloor);
    // alice's full repay now reverts
    vm.prank(alice);
    vm.expectRevert(DebtToken.RemainingDebtIsLowerThanTheFloor.selector);
    msEthDebtToken.repay(alice, debt);
}
```

Both revert deterministically; the grief can be repeated each block while the attacker holds dust amounts of the synthetic token.
