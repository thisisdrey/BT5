### Title
Unprivileged attacker permanently DoSes a victim's account from receiving new deposit tokens or opening new debt positions via dust transfers that fill `MAX_TOKENS_PER_USER` - ([File: contracts/Pool.sol](contracts/Pool.sol), [File: contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
The CVE class is an unprivileged remote denial of service triggered by a specially crafted input. The Metronome analog is a dust-transfer griefing DoS: any EOA can push a victim's `depositTokensOfAccount + debtTokensOfAccount` count to `MAX_TOKENS_PER_USER = 30`, after which every code path that adds a new token to the account reverts with `UserReachedMaxTokens`, permanently blocking the victim from receiving new deposit token types (via `transfer`, `deposit(onBehalfOf)`, or liquidation `seize`) and from opening new debt positions.

### Finding Description
`Pool` tracks per-account token lists in `depositTokensOfAccount` / `debtTokensOfAccount` (`MappedEnumerableSet`), capped at 30 total [1](#0-0) . The cap is enforced by `onlyIfAdditionWillNotReachMaxTokens`, which reverts when the combined list length is `>= 30` [2](#0-1) . This modifier guards `addToDepositTokensOfAccount` and `addToDebtTokensOfAccount`, callable only by registered deposit/debt tokens [3](#0-2) .

`DepositToken._transfer` adds the token to the *recipient's* list whenever the recipient's prior balance was zero — with no opt-in and no way for the recipient to refuse [4](#0-3) . `transfer`/`transferFrom` are public and only check the *sender's* unlocked balance via `_revertIfLocked` [5](#0-4) . So an attacker deposits a small amount into every deposit token in the pool, keeps a nonzero balance of each, and transfers 1-wei dust of each deposit token the victim does not yet hold. Once the combined count reaches 30:

- `deposit(amount, onBehalfOf=victim)` for any new collateral reverts inside `_mint` → `pool.addToDepositTokensOfAccount` [6](#0-5) .
- `DebtToken` issue/mint for a synthetic the victim doesn't hold reverts through `addToDebtTokensOfAccount` [7](#0-6) .
- `Pool.liquidate` → `DepositToken.seize(from, to=victim, ...)` reverts if `victim` is the beneficiary of a new token [8](#0-7) , so third-party "deposit-and-rescue" flows to that account also fail.

Removal only happens when a balance hits exactly zero, and the attacker can re-fill a slot in the same block via front-running or by keeping dust positions across many tokens, so the victim cannot durably free a slot by withdrawing one dust amount while the attacker re-dusts.

### Impact Explanation
The victim suffers a persistent liveness failure: they cannot add any new collateral type to their account (self-deposit, third-party deposit on their behalf, or receiving tokenized deposits) and cannot open any new debt position. Concretely, an account approaching its collateral-factor limit that holds an unregistered-in-account collateral cannot top up to avoid liquidation — the position becomes liquidatable while remediation is blocked — and any victim is frozen out of new borrowing and new-collateral deposits indefinitely while the attacker maintains the dust positions. This is a temporary freezing of funds/protocol functionality for the targeted account, matching the accepted DoS impact class.

### Likelihood Explanation
Fully unprivileged: the attacker only needs small amounts of the underlying assets to mint dust `DepositToken` balances and call `transfer` — no governor, keeper, oracle, or bridge trust assumption. Cost is bounded by ~30 dust deposits/transfers (or fewer, since existing positions count toward the cap). The attacker can monitor `getDepositTokensOfAccount`/`getDebtTokensOfAccount` and re-fill any freed slot, and can front-run a victim's recovery transaction cheaply on L2 deployments (Base/Optimism).

### Recommendation
Do not let unsolicited inbound transfers consume the victim's token slots. Options: only add tokens to the account list on mint/self-initiated actions and account for unlisted balances differently in `debtPositionOf`/`depositOf`; or split accounting so `addToDepositTokensOfAccount` on transfers is skipped when the list is full while `depositOf` iterates the global `depositTokens` set with balance checks; or raise/remove the per-account cap and bound `depositOf`/`debtOf` loops by the protocol-level token lists instead.

### Proof of Concept
Reproducible Hardhat sketch (against deployed `Pool`/`DepositToken` proxies or fixtures as in `test/Pool.test.ts`):

```ts
// victim already holds some deposit tokens; attacker holds none of the victim's
// setup: for each registered deposit token in pool.getDepositTokens():
for (const dt of depositTokens) {
  const token = await ethers.getContractAt('DepositToken', dt)
  const underlying = await ethers.getContractAt('ERC20', await token.underlying())
  if ((await token.balanceOf(attacker.address)).isZero()) {
    await underlying.connect(attacker).approve(token.address, dust.mul(2))
    await token.connect(attacker).deposit(dust.mul(2), attacker.address)
  }
  // send 1 wei of msdTOKEN to victim -> adds token to victim's list
  if ((await token.balanceOf(victim.address)).isZero()) {
    await token.connect(attacker).transfer(victim.address, 1)
  }
}
// once getDepositTokensOfAccount(victim).length + getDebtTokensOfAccount(victim).length == 30:
// 1) victim cannot deposit a new collateral type:
await expect(
  newDepositToken.connect(victim).deposit(amount, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')
// 2) victim cannot issue a new synthetic (DebtToken -> addToDebtTokensOfAccount):
await expect(
  debtToken.connect(victim).issue(1, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')
// 3) even a benevolent deposit/transfer of a new token to victim reverts
```
