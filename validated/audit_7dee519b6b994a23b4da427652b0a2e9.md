### Title
Remote panic (assert failure) in `validate_blocks_push` from a minimal, well-formed `Blocks` push message - (File: `stackslib/src/net/chat.rs`)

### Summary
`ConversationP2P::validate_blocks_push` asserts that `preamble.payload_len > 5` before computing `(preamble.payload_len as u64) - 5` for bandwidth accounting [1](#0-0) . However, the wire-format-level guarantee enforced during `Preamble` deserialization only requires `payload_len >= 5` [2](#0-1) . This mismatch between the "≥ 5" guarantee at parse time and the "> 5" assumption at the point of use means a remote peer can send a minimally-encoded `Blocks`-push message (1-byte type prefix + 4-byte zero-length vector = exactly 5 bytes of payload) that passes preamble validation but then trips the `assert!` and panics the handling thread.

### Finding Description
The `Preamble` codec only rejects `payload_len < 5`, explicitly allowing `payload_len == 5` [2](#0-1) . `validate_blocks_push`, invoked when handling an unsolicited push of blocks over the P2P protocol, assumes a strictly-greater relationship (`> 5`) to safely subtract the 1-byte type prefix and 4-byte vector-length prefix from `payload_len` for bandwidth bookkeeping [3](#0-2) . This is the exact analog of the source report's bug class: an equality/boundary is silently assumed to be strict, and a legitimately-encoded but minimal message (empty blocks vector) satisfies the loose codec-level check while violating the strict assumption made downstream, causing an unchecked-arithmetic-adjacent fault (`assert!` panic instead of an underflow panic, but the same "wrong strictness of an inequality leads to a crash" root cause).

By contrast, the sibling functions `validate_transaction_push` and `validate_stackerdb_push` use `assert!(preamble.payload_len > 1)` [4](#0-3) [5](#0-4) , which is always trivially satisfied because the codec-level minimum of 5 is strictly greater than 1 — so those two are safe. Only `validate_blocks_push`'s `> 5` check sits exactly on the codec-guaranteed boundary of 5, making it the sole vulnerable case.

### Impact Explanation
Any unauthenticated remote peer that can complete a P2P handshake (or, depending on where this validation sits in the unsolicited-message dispatch path, potentially even before full authentication) can craft a single `StacksMessage` with payload type `Blocks` and an empty block vector, giving `payload_len == 5`. Delivering this message triggers `assert!(preamble.payload_len > 5)` to fail, panicking the thread that processes the conversation. This qualifies as a remote, unauthenticated crash/DoS from a single crafted message — matching the "Critical: remote crash/unauthenticated DoS from few messages" impact bar.

### Likelihood Explanation
Likelihood is high for any attacker capable of establishing (or reaching the unsolicited-message-processing stage of) a P2P conversation, since:
- The preamble length check only enforces `>= 5`, which is a documented, intentional minimum (a zero-length vector is a valid encoding).
- No additional gate exists between preamble parsing and `validate_blocks_push` that would reject a `payload_len == 5` message before it reaches the `assert!`.
- Constructing the message requires only standard, permitted framing (type byte + 4-byte zero length) — no forged signatures, cryptographic material, or privileged access needed.

The main uncertainty (which I could not fully resolve given the available tooling) is whether the `Blocks` push message type referenced by `validate_blocks_push` is still reachable in the current unsolicited-message dispatch table given the CHANGELOG entry "Drop unused p2p message types (BlocksAvailable, MicroblocksAvailable, BlocksData)" [6](#0-5) . `validate_blocks_push` itself remains present and referenced across `chat.rs`, `unsolicited.rs`, and `relay.rs` (per grep matches), suggesting the "Blocks" push message (distinct from the removed "BlocksData"/announcement types) is still live, but I was unable to fully trace the exact dispatch call site within the remaining tool budget to give 100% certainty of reachability in this snapshot.

### Recommendation
Change the assertion in `validate_blocks_push` to match the codec-level guarantee, i.e., `assert!(preamble.payload_len >= 5)`, and use `payload_len.saturating_sub(5)` (or equivalent checked arithmetic) instead of a bare assert-then-subtract, so that a minimally-encoded (empty) blocks push cannot panic the node. This mirrors the sherlock report's fix of adding a check for the boundary case (`holdAmount > amount`) before performing the subtraction that assumes it doesn't apply. More broadly, any `assert!` gating arithmetic on attacker-controlled `payload_len` should be replaced with graceful rejection (`return Err(...)`/NACK) rather than a `panic!`-inducing `assert!`, since `assert!` on network-derived input violates the project's own contributing guideline that "functions that act on externally-submitted data must never panic" [7](#0-6) .

### Proof of Concept
1. Construct a `StacksMessage` whose payload type is the blocks-push variant with an empty vector of blocks, such that the serialized payload (type byte + 4-byte big-endian length of `0`) is exactly 5 bytes.
2. Set the `Preamble.payload_len` field to `5` (permitted, since deserialization only rejects `payload_len < 5`) [2](#0-1) .
3. Send this message to a target node over an established P2P conversation.
4. When the node's P2P conversation handler routes this message to `validate_blocks_push`, the assertion `assert!(preamble.payload_len > 5)` evaluates `5 > 5 == false`, triggering a Rust panic [8](#0-7) , crashing the processing thread/node.
