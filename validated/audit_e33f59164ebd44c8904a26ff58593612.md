### Title
Unhardened `ExchangeProcessor` uses raw `double`/`long` bancor-formula math with no overflow or precision guards, enabling manipulated TRC10 exchange trades - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
`ExchangeTransactionActuator`/`ExchangeInjectActuator`/`ExchangeWithdrawActuator` all route their core price computation through `ExchangeCapsule.transaction()`, which by default (when the `allowHarden`/`allowHardenExchangeCalculation` proposal is not active) selects the legacy `ExchangeProcessor` implementation instead of `SafeExchangeProcessor`. This is directly analogous to the reported Panoptic `CollateralTracker.previewMint` bug: a user-reachable, unprivileged actuator (`ExchangeTransactionContract`, callable by any signed transaction) performs its critical share/price computation using raw, unguarded arithmetic, while a "safe" hardened version exists but is gated behind a chain parameter that is not enabled by default.

### Finding Description
`ExchangeCapsule.transaction()` chooses the processor based on the `hardenedCalc` flag: [1](#0-0) 

When not hardened, `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` compute the bancor-style relay/exchange formula using plain `double` arithmetic and raw `long` addition/subtraction with no overflow checks, and truncate the result with a naive `(long)` cast: [2](#0-1) 

By contrast, the "hardened" `SafeExchangeProcessor` performs the same computation with `BigDecimal`, `StrictMathWrapper.addExact`, and exact rounding to protect against overflow/precision loss: [3](#0-2) 

Whether the hardened path is used is controlled entirely by the `allowHarden()` proposal flag checked in `ExchangeTransactionActuator`: [4](#0-3) [5](#0-4) 

Test code explicitly documents that the legacy (non-hardened) `ExchangeProcessor` produces *different* results than the strict-math/hardened path for a wide range of realistic balances/quantities, confirming the divergence is not merely theoretical: [6](#0-5) 

This mirrors the H-02 bug class: a computation reachable directly from an unprivileged, user-controlled transaction (`quant`, `expected`) uses unchecked/unsafe math on the "hot path" by default, while a safe replacement exists only behind an opt-in flag.

### Impact Explanation
If the hardened flag is not activated (the default/legacy state on any chain that has not passed the corresponding committee proposal), any account can submit `ExchangeTransactionContract` with `quant` values that drive `ExchangeProcessor`'s raw `double`/`long` computation into precision-loss or truncation edge cases (e.g., extreme ratios of `quant`/`newBalance`, results near `Long.MAX_VALUE`/`MIN_VALUE`, or values that lose significant digits in the `double` conversion). Because the same result is used both to credit `anotherTokenQuant` to the trader and to update the pool's `firstTokenBalance`/`secondTokenBalance`, manipulated/erroneous results can let an attacker receive tokens from the exchange pool disproportionate to what they contributed, draining pool liquidity - an unbacked-balance/fund-theft outcome analogous to "minting shares for free."

### Likelihood Explanation
Reachable by any transaction sender via a single, unprivileged `ExchangeTransactionContract` (or Inject/Withdraw) broadcast to `ExchangeTransactionActuator.execute`/`validate`, with attacker-controlled `quant`/`expected` fields and attacker-chosen (or attacker-created, since `ExchangeCreateActuator` is also user callable) exchange pool balances. Likelihood of triggering the specific overflow/precision edge case depends on the hardening proposal state of the network at the time; if `allowHardenExchangeCalculation` has not been enabled, the vulnerable path is used unconditionally for every trade.

### Recommendation
Make the hardened (`SafeExchangeProcessor`, `BigDecimal`/`addExact`-based) computation the unconditional default in `ExchangeCapsule.transaction()` rather than gating it behind the `allowHarden()`/`allowHardenExchangeCalculation` proposal, or add explicit bounds/overflow validation directly inside `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` so the legacy path can never produce a result outside safe integer precision.

### Proof of Concept
Not independently reproduced against a live node (no execution environment available); the divergence between `ExchangeProcessor` (legacy) and `SafeExchangeProcessor` (hardened) is already demonstrated by the existing repository test `testStrictMath`, which asserts `Assert.assertNotEquals(anotherTokenQuant, result)` for dozens of realistic `(sellBalance, buyBalance, sellQuant)` triples, showing that the unhardened path systematically yields different (i.e., less trustworthy) settlement amounts than the exact/hardened path: [7](#0-6) 

**Uncertainty**: I could not confirm from the index whether `allowHardenExchangeCalculation` is enabled by default on current mainnet/testnet configurations, nor could I construct a concrete numeric input that forces a `double`-precision-driven fund-theft outcome (as opposed to a mere rounding discrepancy) within the available tool budget. A background Devin session with terminal/test access would be needed to actually run `ExchangeProcessorTest`-style scenarios with extreme `quant`/balance ratios and confirm an exploitable, fund-draining discrepancy end-to-end through `ExchangeTransactionActuator`.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }
