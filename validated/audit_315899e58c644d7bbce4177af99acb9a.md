### Title
Attachment content is authenticated only by a 160-bit `Hash160` commitment, enabling collision-based substitution of Atlas attachment data - (File: `stackslib/src/net/atlas/mod.rs`, `stackslib/src/net/atlas/download.rs`)

### Summary
The Atlas subsystem binds off-chain `Attachment` content to on-chain state using only a 160-bit `Hash160` (RIPEMD160(SHA256(x))) commitment rather than a full 256-bit hash. This mirrors the reported CumulativeMerkleDrop128/160 issue: shortening the commitment hash from 256 bits materially weakens its collision resistance, and any code path that accepts attachment content purely because its `Hash160` matches a stored `content_hash` inherits that weakness.

### Finding Description
`Attachment::hash()` computes the commitment as `Hash160::from_data(&self.content)` [1](#0-0) , and `AttachmentInstance.content_hash` is a `Hash160` field populated from on-chain Clarity contract events [2](#0-1) . Attachment content received from the network is only ever checked against this 20-byte value: `AtlasDB::find_attachment` / `find_uninstantiated_attachment` look up rows by `Hash160` [3](#0-2) , and in the downloader, once content matching a `content_hash` arrives from an untrusted peer, it's stored as canonical and matched against *all* attachment instances that share that hash: `network.atlasdb.find_all_attachment_instances(&attachment.hash())` followed by `insert_instantiated_attachment` and propagation to `resolved_attachments` [4](#0-3) .

Because the equality being enforced is `Hash160(candidate_content) == content_hash`, and `Hash160` output is only 160 bits, this equality is fundamentally weaker than the 256-bit hash the rest of the system's consensus commitments rely on (e.g., `Sha512Trunc256Sum` in StackerDB, `Txid`, `StacksBlockId`). This is exactly the bug class described in the external report: shortening a commitment hash from 256 bits (e.g., to 128/160 bits) makes it practical to search for a second preimage/collision, allowing an attacker to substitute attacker-controlled content that still satisfies the stored commitment.

### Impact Explanation
If an attacker can find (or has pre-computed) two distinct byte strings with the same `Hash160` digest, they can register one value on-chain via the tracked Atlas contract event (setting `content_hash`) and then serve a *different* attachment payload matching that same hash to Atlas peers via `GET /v2/attachments-inv` / attachment content responses. The downloader has no additional integrity check beyond the `Hash160` equality before accepting and rebroadcasting the content as canonical, associating it with every `AttachmentInstance` sharing that hash [5](#0-4) . This is a "serving non-canonical state as canonical" / "network-wide propagation of forged data" scenario: nodes durably store and gossip attacker-supplied content believing it is the content actually committed on-chain (e.g. BNS zonefiles), which can poison downstream consumers relying on Atlas-resolved data.

Practically, RIPEMD160(SHA256(x)) collision search (~2^80 work for a birthday-style collision) is far more expensive than the trivially brute-forceable 1inch example (128-bit/160-bit `keccak` truncated to fit an address+balance leaf, which had much lower effective entropy due to the specific leaf construction). Here the pre-image space is the arbitrary attachment content, so no low-entropy leaf structure narrows the search — a full ~2^80 collision search is required, which is at the edge of current classical brute-force feasibility and not "trivial." This meaningfully lowers confidence in comparing it 1:1 to the reported bug.

### Likelihood Explanation
Low-to-moderate. Finding a Hash160 collision requires roughly 2^80 hash operations (birthday bound), which is computationally very expensive today (though below the ~2^128 bar of a full 256-bit hash) and not something a low-resource attacker can do casually. There is no indication in this codebase of a way to reduce the effective search space (unlike the 1inch report's fixed-format leaf), so exploitation would require substantial, though not utterly infeasible, offline compute investment before any on-chain/network action is taken.

### Recommendation
Migrate the Atlas `content_hash` / `Attachment::hash()` commitment from `Hash160` (160-bit) to a full 256-bit hash (e.g., `Sha256Sum` or `Sha512Trunc256Sum`, consistent with what's already used for StackerDB `data_hash` and other consensus-critical commitments in this codebase), and update the on-chain contract interface / `AttachmentInstance::try_new_from_value` parsing accordingly to accept a 32-byte digest.

### Proof of Concept
Not independently demonstrated (would require an actual ~2^80 collision search against RIPEMD160(SHA256(x)), which is outside the scope of static code review). The root-cause code path is:
1. `Attachment::hash()` truncates to 160 bits [1](#0-0) .
2. Downloaded content is accepted/propagated solely on `Hash160` equality with `content_hash` [4](#0-3) .
3. Lookup/storage APIs key exclusively on this 160-bit value [3](#0-2) .
