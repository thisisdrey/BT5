### Title
Missing domain separation in `SlotMetadata::auth_digest` allows a signature valid for one StackerDB contract to be replayed into a different StackerDB contract (cross-message-type chunk forgery) - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` commits only to `slot_id`, `slot_version`, and `data_hash` — it never binds the signature to the specific smart-contract identifier (StackerDB instance/message type) that the chunk is being written into. Because the node assigns the exact same signer→slot-index layout across every message-type contract for a given signer set (`signers-{set}-{message_id}`, all backed by the same `stackerdb-get-signer-slots-page` in `signers.clar`), a validly-signed chunk observed on one StackerDB contract (e.g. the `Transactions` message channel) is *also* a validly verifiable chunk for a different StackerDB contract (e.g. the `BlockResponse` channel) for the same signer/slot/version, and can be replayed there by any unprivileged network peer.

### Finding Description
`SlotMetadata::verify()` and `StackerDBChunkData::verify()` recover the signer purely from `auth_digest = H(slot_id || slot_version || data_hash)`: [1](#0-0) 

This digest contains no reference to the smart-contract identifier the chunk belongs to. Authorization for who may write to a given `(contract_id, slot_id)` is looked up separately and only at validation time, in `PeerNetwork::validate_received_chunk` (via `get_slot_signer`) and in `StackerDBTx::try_replace_chunk` (via `get_slot_validation`): [2](#0-1) [3](#0-2) 

Both checks only verify "does this signature recover to the address registered for slot `X` **in this contract**?" — they never check that the signature itself was computed with knowledge of *which* contract it is destined for.

Crucially, the per-contract signer→slot assignment is *not* independently randomized per message type. The boot contract `signers.clar` stores a single shared slot-layout page (`stackerdb-signer-slots-0/1`) per signer-set parity, and every `signers-{set}-{message_id}` contract (one per `MessageSlotID`, e.g. `BlockResponse`, `Transactions`, etc.) reads from that same shared page: [4](#0-3) 

This is directly confirmed by the test that iterates over every `message_id` under a given `signer_set` and asserts they all return the **identical** slot list: [5](#0-4) 

Consequently, a given signer occupies slot `N` in *every* message-type contract for that signer-set/parity. Since the signature digest never binds to the contract, a signed `(slot_id, slot_version, data)` triple that is valid in contract A is bit-for-bit valid in contract B, as long as B also assigns that same signer to `slot_id` (guaranteed by the shared layout) and B's current stored version for that slot is `< slot_version` (the only ordering check performed, per `try_replace_chunk`/`validate_received_chunk`).

An unprivileged remote peer can observe any legitimately-broadcast, validly-signed chunk on the network (StackerDB chunks are gossiped/pushed and fetchable via public HTTP `GET .../stackerdb/...`), then simply re-POST the exact same `(slot_id, slot_version, sig, data)` tuple to a different StackerDB contract belonging to the same signer-set/parity (e.g. take a chunk signed for the `Transactions` channel and submit it to the `BlockResponse` channel, or vice versa). `PeerNetwork::handle_unsolicited_StackerDBPushChunk` / `validate_received_chunk` and the HTTP `POST /v2/stackerdb/.../chunks` handler (`poststackerdbchunk.rs`) will accept and store it, because signature verification only checks the recovered address against the target contract's own signer-slot table — which will match, since the same address occupies the same slot in both contracts.

This is exactly analogous to the original report's root cause: an identity/authorization credential (here, a signature over slot metadata) is treated as universally valid across different "domains" (here, different StackerDB message-type contracts) instead of being scoped to the specific domain it was created for.

### Impact Explanation
This allows an unauthenticated, unprivileged network participant to write attacker-chosen (but previously-observed, validly-signed) bytes into a StackerDB slot/contract that the data was never intended for. This is an authorization-bypass/forged-data-propagation issue: data authenticated for one purpose (message type A) gets stored and propagated as authentic data for a different purpose (message type B) under the identity of a signer who never authorized that specific write. Depending on how downstream consumers key their StackerDB reads (by contract only, trusting any content that passes signature check for that contract), this can result in type-confused or spoofed signer messages being accepted as canonical for the wrong channel — matching the "High: serving non-canonical state as canonical" / "forged-data propagation" impact classes in scope for this repo's net/StackerDB layer.

The severity is bounded by the fact that the attacker cannot forge arbitrary content — they can only replay *previously validly signed* data across contracts/slot-versions, and the target must have a lower stored version for that slot. This limits (but does not eliminate) the practical payloads an attacker can inject.

### Likelihood Explanation
Exploitation requires no special privilege: any peer able to read a chunk (via public inventory/gossip or the public GET chunk RPC) and POST/gossip it to a different, but slot-compatible, StackerDB contract can perform the replay. The pre-condition (same slot layout across message-type contracts for the same signer set) is guaranteed by the current implementation (`signers.clar`'s shared slot page), not an unlikely edge case — so the "same identity assumed across domains" precondition from the analog report holds unconditionally here, unlike the original finding which required an attacker to acquire control of a specific address on another chain.

### Recommendation
Bind the `SlotMetadata`/chunk signature to the destination StackerDB contract identity (and ideally the network/chain id), e.g. include the `smart_contract_id` (and `mainnet`/`chain_id`) in `SlotMetadata::auth_digest()`, so a signature computed for one StackerDB contract cannot be verified as valid for another. This mirrors the original report's mitigation of tying the authorization credential to the specific domain (chain/contract) it was issued for, rather than assuming an address/signature is universally valid across all domains that happen to reuse the same identity.

### Proof of Concept
1. Node operates two StackerDB contracts for the same reward-cycle signer-set parity, e.g. `signers-0-<Transactions message_id>` and `signers-0-<BlockResponse message_id>`, both backed by the shared slot page per `signers.clar` (`stackerdb-get-signer-slots-page`), so signer `S` occupies `slot_id = k` in both.
2. Signer `S` legitimately signs and publishes chunk `C = (slot_id=k, slot_version=v, data=D)` to the `Transactions` contract; `sig` verifies via `SlotMetadata::verify(&addr_S)` (`libstackerdb/src/libstackerdb.rs:183-193`).
3. An unprivileged peer captures `(k, v, sig, D)` (via public chunk fetch RPC or gossip observation).
4. The peer resubmits the identical tuple to the `BlockResponse` contract at the same `slot_id=k`, with `slot_version` set higher than that contract's currently stored version for slot `k`.
5. `PeerNetwork::validate_received_chunk` (`stackslib/src/net/stackerdb/mod.rs:679-697`) / `StackerDBTx::try_replace_chunk` (`stackslib/src/net/stackerdb/db.rs:411-423`) looks up `get_slot_signer`/`get_slot_validation` for the `BlockResponse` contract's slot `k`, finds it is also `addr_S`, calls `slot_metadata.verify(&addr_S)`, which succeeds because the digest never referenced the contract — the replayed chunk is accepted and stored/propagated in a contract it was never intended for.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Sign this slot metadata, committing to slot_id, slot_version, and
    /// data_hash.  Sets self.signature to the signature.
    /// Fails if the underlying crypto library fails
    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
