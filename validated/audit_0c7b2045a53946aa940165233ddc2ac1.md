### Title
Unbounded resource consumption from attacker-controlled remote Git servers during URL-based repository creation/mirroring - ([File: internal/gitaly/service/repository/create_repository_from_url.go])

### Summary
`CreateRepositoryFromURL`, `FetchRemote`, and `UpdateRemoteMirror` let an ordinary caller instruct Gitaly to clone/fetch from an arbitrary, caller-supplied remote URL. Unlike the reported Sablier pattern of invoking an untrusted contract's callback without bounding gas, here Gitaly spawns a long-running `git clone`/`git fetch` subprocess against a remote HTTP/SSH endpoint that is fully controlled by whoever supplies the URL (e.g. a malicious/compromised mirror target). Because no Gitaly-side upper bound on execution time is enforced by default, that untrusted remote endpoint can stall the response indefinitely and tie up Gitaly resources (goroutine, subprocess, file descriptor, disk) at negligible cost to itself — the resource-griefing analog of the reported issue.

### Finding Description
`CreateRepositoryFromURL` builds and runs a `git clone` command directly against the caller-provided `repoURL` with no timeout of its own; it relies solely on whatever context deadline the gRPC client happens to set: [1](#0-0) 

`FetchRemote` does add an optional timeout, but only if the client explicitly sets `req.GetTimeout() > 0`; when unset, `ctx` is left unbounded and the fetch runs to completion (or hangs) at the pace dictated by the remote server: [2](#0-1) 

The gRPC server itself installs no default per-RPC deadline: the unary/stream interceptor chains contain auth, logging, correlation, and concurrency-limiter middleware, but nothing that imposes a maximum execution time — the concurrency limiter caps how many git commands run at once per key, but does not bound how long an individual, already-admitted call may run: [3](#0-2) 

The `command.New` spawn path only terminates the subprocess when the caller's `ctx` is canceled — there is no independent per-invocation ceiling: [4](#0-3) 

This is functionally the same bug class as the reported issue: Gitaly (the caller) invests real, unbounded resources into interacting with an untrusted third party (the remote git server named in the request), and that third party fully controls how long/how much data is exchanged before the interaction completes, with no independent cap enforced by the invoking side.

### Impact Explanation
An attacker who controls (or has compromised) the target of a mirror/import URL — a scenario intentionally supported by these RPCs (`CreateRepositoryFromURL`, `FetchRemote`, `UpdateRemoteMirror`, and the URL-based `FindRemoteRepository`/`FindRemoteRootRef` lookups) — can accept the TCP/HTTP connection and then stall indefinitely (slow-loris style) or dribble output extremely slowly. Because `CreateRepositoryFromURL` has no built-in timeout and `FetchRemote`'s timeout is opt-in per request, the spawned `git clone`/`git fetch` subprocess, its file descriptors, the goroutines set up to stream stdout/stderr, and a held slot in the concurrency limiter's semaphore for that repository/RPC key can all be pinned for an extended period. Repeating this concurrently for many repositories degrades Gitaly node capacity and lets an attacker force disproportionate resource consumption in exchange for negligible attacker-side cost — mirroring the "steal gas cheaply from an untrusted callback" dynamic in the Sablier report, translated to compute/FD/goroutine exhaustion on the Gitaly host.

### Likelihood Explanation
Any user able to trigger repository import/creation-from-URL or configure/refresh a remote mirror (a normal, unprivileged GitLab workflow — importing a project by URL, or repository mirroring) can point Gitaly at a server they control. No special Gitaly privileges are required beyond the ordinary "import/fetch from external URL" capability already exposed by these RPCs. If the upstream Rails/Workhorse caller does not always set a `Timeout` on `FetchRemoteRequest`, or when `CreateRepositoryFromURL` is invoked (which has no timeout parameter at all), the exposure is direct and easily reproducible.

### Recommendation
- Enforce a mandatory maximum execution deadline inside Gitaly for all RPCs that clone/fetch from caller-supplied URLs, independent of whether the client population sets one (i.e., don't rely solely on `FetchRemoteRequest.Timeout` or the inbound gRPC deadline).
- Apply the same treatment to `CreateRepositoryFromURL`, which currently has no timeout mechanism at all.
- Consider bounding negotiation/connect time separately from total transfer time (similar to the existing `pktline.ReadMonitor` pattern used for upload-pack negotiation) so that a stalling remote cannot indefinitely occupy resources: [5](#0-4) 
- Ensure the concurrency limiter's queue/slot occupancy for these RPCs is time-bounded consistently with other expensive git operations documented in the backpressure design: [6](#0-5) 

### Proof of Concept
1. Stand up an HTTP server that accepts a `git clone`/`git fetch` connection (matching a Git smart-HTTP handshake) but then withholds/streams the pack data at an extremely low rate (e.g., 1 byte per few seconds), never closing the connection.
2. Call `CreateRepositoryFromURL` (or `FetchRemote` without setting `Timeout`) against that server's URL.
3. Observe that the underlying `git clone`/`git fetch` subprocess, and the RPC handling it, remain active far beyond any reasonable bound, consuming a goroutine, subprocess, and (for `FetchRemote`) a concurrency-limiter slot for the target repository, until the attacker chooses to end the connection or the surrounding infrastructure (e.g., Workhorse/Rails) times out independently of Gitaly.

func (s *server) FetchRemote(ctx context.Context, req *gitalypb.FetchRemoteRequest) (*gitalypb.FetchRemoteResponse, error) {
	if err := s.validateFetchRemoteRequest(ctx, req); err != nil {
		return nil, err
	}

	if req.GetTimeout() > 0 {
		var cancel context.CancelFunc
		ctx, cancel = context.WithTimeout(ctx, time.Duration(req.GetTimeout())*time.Second)
		defer cancel()
	}

	tagsChanged, repoChanged, err := s.fetchRemoteAtomic(ctx, req)
	if err != nil {
		return nil, err
	}

	return &gitalypb.FetchRemoteResponse{TagsChanged: tagsChanged, RepoChanged: repoChanged}, nil
}

func New(ctx context.Context, logger log.Logger, nameAndArgs []string, opts ...Option) (_ *Command, returnedErr error) {
	if ctx.Done() == nil {
		panic("command spawned with context without Done() channel")
	}

	// Don't launch the command if the context is already canceled. This matches
	// Go's own CommandContext's behavior which doesn't start a command if the
	// context is already canceled. We can't use it currently due to it sending a
	// SIGKILL to the command when the context is canceled during execution. This is not
	// fine as we don't have proper logic to recover from git crashes by for example
	// cleaning stale reference locks.
	//
	// Without this, racy behavior will emerge as the command execution will race with the
	// context cancellation. This really only helps with cases when the context is already
	// canceled before calling New. Raciness still ensues if the context is canceled after
	// this check. More details at: https://gitlab.com/gitlab-org/gitaly/-/issues/5021
	if err := ctx.Err(); err != nil {
		return nil, err
	}

// packet doesn't come within a timeout, a cancel function is called. This can

```markdown
An in-memory queue of requests can build up in Gitaly that are waiting their turn. Because
this is a potential vector for a memory leak, two other values in the `[[concurrency]]`
configuration can prevent an unbounded in-memory queue of requests:

- `max_queue_wait` is the maximum amount of time a request can wait in the
  concurrency queue. When a request waits longer than this time, it returns
  an error to the client.
- `max_queue_size` is the maximum size the concurrency queue can grow for a
  given RPC. If a concurrency queue is at its maximum, subsequent requests
  return with an error. The queue size is per repository.

For example:

```toml
[[concurrency]]
rpc = "/gitaly.SmartHTTPService/PostUploadPackWithSidechannel"
max_per_repo = 1
max_queue_wait = "1m"
max_queue_size = 5
```
