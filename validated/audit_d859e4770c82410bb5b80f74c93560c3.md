### Title
No Vulnerability — path-traversal via `..`-containing tar entries in `repoutil.ExtractHooks` is blocked by GNU/BSD tar's own built-in safety checks - ([File: internal/gitaly/repoutil/custom_hooks.go])

### Summary
`repoutil.ExtractHooks` shells out to the external `tar` binary with a fixed `-C path --strip-components N custom_hooks` argument list and does not itself parse or sanitize tar member names [2](#0-1) . However, both GNU tar and BSD tar refuse by default to extract archive members whose paths contain `..` path-traversal components or are absolute, which is the exact defense this question asks whether an attacker can bypass.

### Finding Description
The `SetCustomHooks` RPC handler passes the client-controlled tar stream directly to `ExtractHooks`, which invokes the `tar` command with `path` as the `-C` destination and `custom_hooks` as the sole member/prefix to extract [1](#0-0) . A malicious tar entry such as `custom_hooks/../../../../etc/cron.d/evil` would match the `custom_hooks` prefix filter passed to `tar`, so in principle it reaches the extraction stage. However, this is exactly the class of attack that both GNU tar and BSD tar (libarchive) have hardened against by default since long-standing CVE fixes (e.g., CVE-2001-1267 and later hardening): modern tar implementations detect `..` path components (and absolute paths) in member names during extraction and either strip/refuse them, emit an error (e.g. `tar: <name>: Member name contains '..'`) and skip the entry, or exit with a non-zero status. In this codebase, `ExtractHooks` already treats a non-zero `tar` exit status as fatal unless the stderr matches the specific "Not found in archive" prefix [3](#0-2) , meaning a rejected/skip-worthy malicious member would cause the whole `SetCustomHooks` operation to fail with an error rather than silently write outside `path`. There is no non-default configuration or flag (like `-P`/`--absolute-names`) enabled in the invocation that would disable this built-in tar protection [1](#0-0) . Consequently the described exploit path is not reachable through Gitaly's own code — the mitigating control lives in the `tar` binary itself and is on by default, not bypassed by any option Gitaly supplies.

### Impact Explanation
No concrete impact is achievable given tar's default component-traversal protection; the underlying `tar` binary itself rejects `..`-containing extraction paths, so no file write occurs outside the destination directory.

### Likelihood Explanation
Not applicable — the precondition (tar accepting `..` traversal without extra flags) does not hold for standard GNU/BSD tar installations used in Gitaly's default/documented environment, so this is not exploitable via the described call sequence.

### Recommendation
No code change is required for this specific concern; if additional defense-in-depth is desired, Gitaly could parse tar entries in Go (e.g., using `archive/tar`) and explicitly reject `..`-containing or absolute member names before shelling out, rather than relying solely on the external `tar` binary's behavior.

### Proof of Concept
Not applicable — a Go test using `archive/tar` to write a header named `custom_hooks/../../outside.txt` and calling `ExtractHooks`/`SetCustomHooks` would be expected to either fail with a non-zero `tar` exit error or skip the offending entry, and the outside file would not be created, consistent with existing tests such as `TestSetCustomHooks_corruptTar` [4](#0-3)  that already assert failure behavior for malformed archives.
