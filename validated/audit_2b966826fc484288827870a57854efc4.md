### Title
Symlink prefix-reuse allows worktree escape in `os.CopyFS` - ([File: src/os/dir.go])

### Finding Description
`os.CopyFS(dir, fsys)` walks an untrusted `fs.FS` with `fs.WalkDir` and, for each entry, dispatches on `d.Type()`: for `ModeDir` it calls `MkdirAll`, for `ModeSymlink` it calls `Symlink(target, newPath)`, and for regular files it calls `OpenFile(newPath, O_CREATE|O_EXCL|O_WRONLY, ...)`, all using plain path-joining (`joinPath(dir, fpath)`) with no verification that intermediate path components are still real (non-symlink) directories under `dir`. [1](#0-0) 

Because `Symlink` and `OpenFile` are called with a bare joined path (not via an `os.Root`/`openat`-anchored resolution that re-validates every path segment), if the walked `fsys` yields a symlink entry named `a` before a later entry whose path is `a/b`, the symlink at `a` is created first, and then `newPath := joinPath(dir, "a/b")` for the second entry resolves through the just-created symlink at the OS level. This is exactly the same primitive as the reported `gix_fs::Stack` bug: a leaf/directory-name collision plus deferred/ordered processing causes a previously created symlink to be silently traversed by a subsequent file/dir operation, because no re-validation of intermediate components as "safe, non-symlink directories relative to the root" occurs on each step. Go's own `os.Root`/`doInRoot` machinery, by contrast, performs `openat`-based, per-component symlink checks precisely to avoid this class of issue, but `CopyFS` bypasses that machinery entirely and uses ordinary path-based `Symlink`/`OpenFile`/`MkdirAll` calls. [2](#0-1) 

The attacker-controlled input is the `fs.FS` argument to `CopyFS`. A hostile implementation of `fs.FS` (e.g., a custom filesystem, a network filesystem, or a parser for an archive format the caller trusts as `fs.FS`) can order/name its entries so that `fs.WalkDir` yields the symlink entry `a -> <writable target>` before the entry `a/payload`. `CopyFS`'s doc claims "Symbolic links in dir are followed" only referring to walking into pre-existing symlinks in the destination `dir`; it does not defend against symlinks it itself just created in the middle of the walk.

### Impact Explanation
If successfully triggered by a malicious `fs.FS` supplied to (or produced from data controlled by an attacker and passed to) `os.CopyFS`, a normal caller (victim workflow: unpacking or "installing" a fileset provided by an untrusted source through `os.CopyFS`) can be made to write attacker-chosen file content outside the intended destination directory — including into arbitrary locations the process has write access to. This is a material file-write / worktree-escape primitive analogous to the referenced advisory (CWE-59), and could plausibly be chained to code execution depending on where the write lands (e.g., overwriting a script/config later executed). This would be a Go **PUBLIC** track candidate (security-relevant behavior in a widely used standard-library API) once independently reproduced against the actual `fs.FS` implementations that ship with Go (e.g. `os.DirFS`, `zip.Reader`, `fstest.MapFS`).

### Likelihood Explanation
Exploitability depends entirely on whether a `fs.FS` implementation reachable by ordinary Go programs can produce the necessary entry ordering/collision (symlink at `a` followed by a nested path `a/b`) through `fs.WalkDir`. I was not able to fully verify, within the available tool budget, whether any of Go's built-in `fs.FS` providers (`os.DirFS`, `archive/zip`'s `fs.FS` adapter, `testing/fstest.MapFS`) allow constructing such a colliding tree — `archive/zip`'s file-list/tree-building logic (in `src/archive/zip/reader.go`) and `MapFS`'s directory-inference logic (`src/testing/fstest/mapfs.go:178-208`) both appear to derive directory-ness from the *existence of children with that prefix*, which may make a leaf marked `ModeSymlink` simultaneously have children rejected or coerced to directory-only, but I could not confirm this rejection path with certainty before running out of iterations.

### Recommendation
- In `os.CopyFS`, before writing any file/symlink, verify each intermediate path component under `dir` is still a plain directory (not a symlink) using an `os.Root`-based, `openat`-anchored write path, or explicitly `Lstat` each parent component and refuse to proceed if a symlink is found where a plain directory is expected.
- Alternatively, restrict `CopyFS` symlink handling so symlink targets/entries can never introduce an escape for subsequently processed sibling/child paths (e.g., process all directory creations first, validate the resulting tree contains no symlink-as-intermediate-directory, and only then materialize symlinks last while still checking for pre-existing symlinks introduced during the same walk).

### Proof of Concept
```go
package os_test

import (
	"io/fs"
	"os"
	"path/filepath"
	"testing"
	"testing/fstest"
)

// TestCopyFS_SymlinkPrefixEscape demonstrates that a malicious fs.FS can use a
// symlink entry named "a" together with a nested entry "a/payload" to make
// os.CopyFS write outside the intended destination, if fs.WalkDir yields the
// symlink before descending (this requires an fs.FS that permits such a
// colliding tree; MapFS auto-infers directories from children and may reject
// this particular shape, in which case this test documents the expected safe
// behavior rather than the vulnerability).
func TestCopyFS_SymlinkPrefixEscape(t *testing.T) {
	dst := t.TempDir()
	outside := t.TempDir()

	fsys := fstest.MapFS{
		// "a" is a symlink pointing at a directory outside the copy target.
		"a": &fstest.MapFile{Mode: fs.ModeSymlink, Data: []byte(outside)},
		// "a/payload" would, if processed after the symlink without
		// re-validating "a", be written through the symlink into `outside`.
		"a/payload": &fstest.MapFile{Data: []byte("pwned")},
	}

	err := os.CopyFS(dst, fsys)
	if err != nil {
		t.Logf("CopyFS returned error (expected if the FS/implementation rejects the collision): %v", err)
		return
	}

	// If CopyFS succeeded, verify it did NOT write into the outside directory.
	if _, statErr := os.Stat(filepath.Join(outside, "payload")); statErr == nil {
		t.Fatalf("os.CopyFS wrote payload outside destination via symlink escape: %s",
			filepath.Join(outside, "payload"))
	}
}
```

Note: I could not, within the remaining tool budget, conclusively determine whether `fstest.MapFS` (or `archive/zip`'s `fs.FS` adapter) actually permits constructing the colliding "symlink `a` + nested `a/payload`" tree required to trigger `fs.WalkDir` yielding both entries in the vulnerable order — `MapFS.lstat`'s directory-inference logic derives directory status from the presence of children with a `/` prefix (`src/testing/fstest/mapfs.go:178-208`), which may special-case or reject this exact shape. This is the key remaining uncertainty; if it turns out no shipped `fs.FS` implementation can produce this collision, the `os.CopyFS` code path, while structurally similar to the reported gix-fs primitive, may not be reachable by an unprivileged attacker through Go's own libraries (only through a custom, attacker-controlled `fs.FS` implementation that the *victim* chose to trust, which is a different threat model). I flag this explicitly rather than asserting exploitability with unwarranted confidence.

func CopyFS(dir string, fsys fs.FS) error {
	return fs.WalkDir(fsys, ".", func(path string, d fs.DirEntry, err error) error {
		if err != nil {
			return err
		}

		fpath, err := filepathlite.Localize(path)
		if err != nil {
			return err
		}
		newPath := joinPath(dir, fpath)

		switch d.Type() {
		case ModeDir:
			return MkdirAll(newPath, 0777)
		case ModeSymlink:
			target, err := fs.ReadLink(fsys, path)
			if err != nil {
				return err
			}
			return Symlink(target, newPath)
		case 0:
			r, err := fsys.Open(path)
			if err != nil {
				return err
			}
			defer r.Close()
			info, err := r.Stat()
			if err != nil {
				return err
			}

			if err != nil {
				return err
			}

			if _, err := io.Copy(w, r); err != nil {
				w.Close()
				return &PathError{Op: "Copy", Path: newPath, Err: err}

			return w.Close()

		}
	})
