### Title
Multi-Sig Threshold Bypass via Signature (not Signer) Counting in `ValidateMultiSign` Precompile - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `ValidateMultiSign` TVM precompiled contract, which any deployed smart contract can invoke to verify a k-of-n multi-signature permission on-chain, deduplicates signers by comparing raw signature bytes instead of the recovered signer address in the general case. A single key holder can submit two byte-distinct but cryptographically valid signatures (e.g. via ECDSA signature malleability, flipping `s`→`n-s` with the matching recovery id) that both recover to the same address. The loop only skips re-counting when the *exact* signature bytes repeat; when the bytes differ but the recovered address is the same, it falls through and adds that signer's weight to `totalWeight` again. This mirrors the reported root cause ("signatures are counted, instead of signers") and allows one private key to satisfy a multi-signer weight threshold alone.

### Finding Description
`ValidateMultiSign.execute()` accumulates weight per supplied signature: [1](#0-0) 

The dedup logic is:
```
byte[] recoveredAddr = recoverAddrBySign(sign, hash);
sign = merge(recoveredAddr, sign);
if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
  if (ByteArray.matrixContains(executedSignList, sign)) {
    continue;               // only skip if EXACT same signature bytes seen before
  }
  MUtil.checkCPUTime();      // otherwise just a CPU throttle, no skip
}
long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
...
totalWeight += weight;       // weight added again for the same signer
```
Because the "already counted" check is keyed on the exact signature byte sequence rather than the recovered address, an attacker who controls one key in the permission's key list can craft a second, byte-different signature over the same hash that still recovers to their own address (ECDSA malleability: for signature `(r, s)` the pair `(r, n-s)` with recovery-id flipped is also a valid signature recovering to the same public key, since `recoverAddrBySign` does not appear to enforce low-S canonical form before this comparison). Submitting both signatures causes `totalWeight` to be incremented twice (or N times, for N malleable variants) for a single signer, letting one key satisfy a `permission.getThreshold()` that was designed to require multiple independent signers.

This is architecturally analogous to `TransactionCapsule.checkWeight()`, used for ordinary transaction/permission validation, which correctly dedups by recovered *address* (via a `HashMap` keyed by address after fork `VERSION_4_7_1`) and explicitly rejects a repeat with `"has signed twice!"`: [2](#0-1) 

The `ValidateMultiSign` precompile, however, does not use this hardened, address-keyed dedup path — it re-implements its own weaker signature-byte-based dedup.

### Impact Explanation
The `ValidateMultiSign` precompile is designed for smart contracts (e.g. on-chain multisig wallets, custody contracts, DAO/treasury contracts) to gate privileged operations — releasing funds, executing withdrawals, approving transfers — behind a k-of-n weighted signer threshold defined by a TRON account `Permission`. Any contract that relies on this precompile's boolean result to authorize a fund-moving action can be tricked into believing multiple independent signers approved an action when in fact only a single, insufficiently-weighted signer did. This directly enables unauthorized account operations and theft of funds from contracts that gate value transfer on this precompile's result — matching the "direct loss of funds" / "unauthorized account operation" impact class from the analog report.

### Likelihood Explanation
This is reachable by any unprivileged account: simply deploy or call an existing contract that invokes the `ValidateMultiSign` precompile (address `0x66`/related TVM precompile slot) with attacker-controlled `data` (address, permissionId, message, and signature array). No special privilege, staking, or witness/SR role is required — only knowledge of one private key that is a member (with nonzero weight, below threshold) of the target permission's key list, plus the ability to derive one malleable signature variant, which is a standard ECDSA property (not require guessing/private-key compromise).

### Recommendation
In `ValidateMultiSign.execute()` (and the sibling `BatchValidateSign`), deduplicate strictly by the **recovered address**, not by the raw signature bytes: once `recoveredAddr` has been counted, always `continue` regardless of whether the current signature bytes differ, mirroring the approach used in `TransactionCapsule.checkWeight()`. Additionally, enforce canonical (low-S) signature encoding before recovery to eliminate the malleable-signature source entirely.

### Proof of Concept
1. Deploy (or use) a smart contract that calls the `ValidateMultiSign` precompile with the target account's `permissionId` requiring, e.g., threshold 2 across two distinct keys with weight 1 each.
2. As the holder of only `key1` (weight 1, below threshold 2), sign the target hash to get `(r, s, v)`.
3. Compute the malleable counterpart `(r, n-s, v^1)` — a distinct 65-byte signature that still ECDSA-recovers to `key1`'s address.
4. Submit both signatures in the `signs` array to `ValidateMultiSign`.
5. In the precompile loop: iteration 1 adds `key1`'s weight (1) and records `(recoveredAddr, sign1)`. Iteration 2 finds `recoveredAddr` already present but `sign2 != sign1`, so it does not `continue`, and adds `key1`'s weight (1) a second time.
6. `totalWeight` reaches 2 ≥ `permission.getThreshold()` and the precompile returns `true` (`dataOne()`), even though only one distinct signer authorized the action. [3](#0-2)

      long weight = getWeight(permission, address);
