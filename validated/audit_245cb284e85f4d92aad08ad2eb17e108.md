### Title
Missing Slippage Protection in ExchangeInject/ExchangeWithdraw Actuators Allows Sandwich Attacks on Liquidity Providers - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java, actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java)

### Summary
`ExchangeInjectActuator` and `ExchangeWithdrawActuator` compute the counter-token amount a liquidity provider must pay in (inject) or will receive (withdraw) purely from the exchange pool's *current* on-chain balances, with no user-supplied minimum/maximum bound. Unlike `ExchangeTransactionActuator`, which enforces a `tokenExpected` slippage check, these two actuators have no analogous protection.

### Finding Description
`ExchangeInjectActuator.execute()` derives `anotherTokenQuant` from the live pool ratio at execution time [1](#0-0) , and `doValidate()` recomputes the same ratio-based amount without comparing it to any caller-specified bound [2](#0-1) . `ExchangeWithdrawActuator` follows the identical pattern for withdrawals [3](#0-2) [4](#0-3) .

By contrast, `ExchangeTransactionActuator` explicitly reads a `tokenExpected` value from the contract and rejects the trade if the computed output is worse than the caller's expectation [5](#0-4) . `ExchangeInjectContract` and `ExchangeWithdrawContract`, however, carry only `owner_address`, `exchange_id`, `token_id` and `quant` — there is no equivalent "expected"/min-out field referenced anywhere in either actuator's validate/execute logic.

Because the pool ratio (`firstTokenBalance`/`secondTokenBalance`) can be shifted by any preceding `ExchangeTransactionContract` in the same block (the only actor who is the exchange's `creatorAddress` can inject/withdraw, but an unrelated party can still submit a large trade against the same exchange immediately before the LP's transaction), a broadcaster can front-run the LP's inject/withdraw transaction with a trade, execute the LP's now-unfavorable inject/withdraw, then reverse the trade — a classic sandwich attack that forces the LP to deposit more of the counter-token than intended, or to receive less than intended on withdrawal.

### Impact Explanation
This directly causes unbacked/incorrect exchange-pool accounting relative to the LP's true intended exchange rate and results in a real, measurable loss of funds for the exchange creator performing inject/withdraw, mirroring the "Missing Slippage Protection" bug class from the external report where LP-facing operations (analogous to `deposit`/`withdraw`) lacked bounds while trade-facing operations (`mint`/`burn`, i.e. `ExchangeTransactionContract`) already have them.

### Likelihood Explanation
Exploitation only requires ordinary signed transactions (`ExchangeTransactionContract` sandwiching an `ExchangeInjectContract`/`ExchangeWithdrawContract`) that any account can broadcast; no privileged role is needed. The attacker only needs visibility into the pending transaction (mempool) and to control transaction ordering within a block/bundle, which is a well-known and practical MEV technique on TRON's exchange pools.

### Recommendation
Add an `expected`-style bound to `ExchangeInjectContract` and `ExchangeWithdrawContract` (e.g., `max_another_token_quant` for inject, `min_another_token_quant` for withdraw), and validate it in `ExchangeInjectActuator.doValidate()` / `ExchangeWithdrawActuator.doValidate()` the same way `ExchangeTransactionActuator` validates `tokenExpected`.

### Proof of Concept
1. Attacker observes a pending `ExchangeInjectContract` (or `ExchangeWithdrawContract`) for exchange `E` from victim LP.
2. Attacker submits an `ExchangeTransactionContract` against `E` that shifts `firstTokenBalance`/`secondTokenBalance` unfavorably for the victim, ordered before the victim's transaction.
3. Victim's inject/withdraw executes using the now-skewed ratio computed in `ExchangeInjectActuator.execute()` / `ExchangeWithdrawActuator.execute()` [1](#0-0) , causing the victim to pay in more (or receive less) than the fair-market amount, with no on-chain check to reject the result.
4. Attacker submits a reverse `ExchangeTransactionContract` after the victim's transaction to restore the pool ratio and realize profit at the victim's expense.
