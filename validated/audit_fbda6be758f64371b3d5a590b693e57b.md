## Finding

### Title
Malicious/updatable Token-2022 transfer hook on a liability mint can block `lending_account_liquidate` insurance-fee transfer, permanently freezing liquidation of unhealthy positions - (File: `programs/marginfi/src/instructions/marginfi_account/liquidate.rs`)

### Summary
The `lending_account_liquidate` instruction performs an on-chain SPL transfer of the insurance-fund fee via `Bank::withdraw_spl_transfer`, which for Token-2022 mints calls `spl_token_2022::onchain::invoke_transfer_checked` — a CPI that automatically invokes any active `TransferHook` program registered on the mint. Unlike `lending_pool_emissions_deposit`, which explicitly rejects mints with `has_transfer_hook(...)` or `nonzero_fee(...)`, the liquidation path performs no such check before transferring. A liability mint whose transfer-hook program (or its `ExtraAccountMetaList`, updatable by the mint/hook authority) is made to always revert will cause every `lending_account_liquidate` call involving that liability bank to fail, permanently preventing liquidation of any unhealthy position holding that liability.

### Finding Description
`Bank::withdraw_spl_transfer` in [1](#0-0)  directly invokes `spl_token_2022::onchain::invoke_transfer_checked` for any Token-2022 mint. This underlying SPL function executes the mint's registered `TransferHook` program as part of the transfer CPI.

`lending_account_liquidate` calls this exact function to move the insurance-fund fee from the liquidity vault to the insurance vault as part of its unconditional accounting flow, with `maybe_liab_bank_mint` passed through and no hook-safety validation: [2](#0-1) 

By contrast, `lending_pool_emissions_deposit` explicitly guards against this exact class of hazard by rejecting mints with active transfer hooks or non-zero transfer fees before doing the transfer: [3](#0-2) 

No equivalent check (`has_transfer_hook` / `nonzero_fee`) exists anywhere in the liquidation instruction path, and `has_transfer_hook` itself is defined in [4](#0-3)  but is only ever invoked from the emissions-deposit configuration path — not from `liquidate.rs`, `deposit.rs`, `borrow.rs`, or `withdraw.rs`.

Critically, bank creation (`lending_pool_add_bank`, `lending_pool_add_bank_with_seed`) also performs no check for transfer hooks on the mint — it only flags `IS_T22` when the mint is owned by Token-2022, per [5](#0-4) . This means a Token-2022 mint with an active (or later-activated/updated) transfer hook can be listed as a liability bank, and the hook's authority (a third party unrelated to marginfi's admin — the token issuer or hook program's designated authority) retains the ability to update the `ExtraAccountMetaList`/hook logic at any time via `process_update_extra_account_meta_list`, seen in the bundled test hook implementation at [6](#0-5) . If that authority (or the hook program logic itself, e.g., an allow/deny-list) is configured to reject transfers to the insurance vault (or from the liquidity vault authority), every liquidation of accounts holding that liability becomes unexecutable, matching the underlying bug class from the referenced ERC777/Gearbox report: an unprivileged token-side actor uses callback/hook logic to block a critical liquidation transfer that the protocol cannot bypass or skip.

### Impact Explanation
If a listed liability bank's mint hook is (or becomes) adversarial, the insurance-fee transfer inside `lending_account_liquidate` reverts, and the entire liquidation transaction fails. Since there is no alternate/fallback code path that skips or defers the insurance fee, liquidators cannot liquidate any unhealthy account holding that liability, regardless of how insolvent the position becomes. This can lead to accumulation of unrecoverable bad debt across the protocol for that liability market, a direct protocol-solvency impact.

### Likelihood Explanation
Likelihood depends on whether/when marginfi admin lists a Token-2022 mint with an active or authority-controlled transfer hook as a liability-bank mint. Given the codebase's test suite (`test-utils/src/spl.rs`, `programs/marginfi/tests/misc/token_extensions.rs`, `emissions_deposit.rs`) explicitly exercises `TransferHook` mints and Juplend/Kamino/Solend integrations that also lack this guard at add-pool time, transfer-hook mints are clearly an anticipated, supported category of bank asset — increasing the realistic likelihood that such a mint (and its externally controlled hook) reaches production listing without the same protective check applied elsewhere in the codebase (`nonzero_fee`/`has_transfer_hook`).

### Recommendation
Apply the same `has_transfer_hook` (and `nonzero_fee`, for transfer-fee mints) validation used in `lending_pool_emissions_deposit` at bank-creation time for any T22 mint intended to be borrowable/liquidatable (`lending_pool_add_bank*`), and/or make the insurance-fee transfer in `lending_account_liquidate` (and any other mandatory transfer in the liquidation/repay/withdraw paths) resilient to hook failure — e.g., by disallowing active-transfer-hook mints as liability banks altogether, or by decoupling the insurance-fee transfer from the core liquidation accounting so a hook revert cannot block the underlying debt repayment/collateral seizure.

### Proof of Concept
1. Admin lists a Token-2022 mint with `TransferHook` extension as a liability bank via `lending_pool_add_bank` (no rejection occurs, unlike `lending_pool_emissions_deposit`).
2. Borrower opens an under-collateralized position with this token as liability.
3. The mint's hook authority updates the `ExtraAccountMetaList`/hook program logic (via `process_update_extra_account_meta_list`-style instruction) to always fail, or fails specifically when the destination is the bank's insurance vault.
4. A liquidator calls `lending_account_liquidate`; the flow reaches `liab_bank.withdraw_spl_transfer(...)` for the insurance fee, which CPIs into the hook program and reverts.
5. The whole liquidation transaction fails; the unhealthy position remains unliquidated indefinitely, growing bad debt.

/// Returns `true` if the given mint has an active transfer hook program.
/// If the hook is present but no program is active it would return false.
pub fn has_transfer_hook(mint_ai: AccountInfo) -> MarginfiResult<bool> {
    if mint_ai.owner.eq(&Token::id()) {
        return Ok(false);
    }

    let mint_data = mint_ai.try_borrow_data()?;
    let mint = StateWithExtensions::<spl_token_2022::state::Mint>::unpack(&mint_data)?;

    if let Ok(hook) = mint.get_extension::<TransferHook>() {
        let program_id: Option<Pubkey> = Option::from(hook.program_id);
        return Ok(program_id.is_some());
    }

    Ok(false)
}

/// Processes a
/// [UpdateExtraAccountMetaList](enum.TransferHookInstruction.html)
/// instruction.
pub fn process_update_extra_account_meta_list(
    program_id: &Pubkey,
    accounts: &[AccountInfo],
    extra_account_metas: &[ExtraAccountMeta],
) -> ProgramResult {
    let account_info_iter = &mut accounts.iter();

    let extra_account_metas_info = next_account_info(account_info_iter)?;
    let mint_info = next_account_info(account_info_iter)?;
    let authority_info = next_account_info(account_info_iter)?;

    // check that the mint authority is valid without fully deserializing
    let mint_data = mint_info.try_borrow_data()?;
    let mint = StateWithExtensions::<Mint>::unpack(&mint_data)?;
    let mint_authority = mint
        .base
        .mint_authority
        .ok_or(TransferHookError::MintHasNoMintAuthority)?;

    // Check signers
    if !authority_info.is_signer {
        return Err(ProgramError::MissingRequiredSignature);
    }
    if *authority_info.key != mint_authority {
        return Err(TransferHookError::IncorrectMintAuthority.into());
    }

    // Check validation account
    let expected_validation_address = get_extra_account_metas_address(mint_info.key, program_id);
    if expected_validation_address != *extra_account_metas_info.key {
        return Err(ProgramError::InvalidSeeds);
    }

    // Check if the extra metas have been initialized
    let min_account_size = ExtraAccountMetaList::size_of(0)?;
    let original_account_size = extra_account_metas_info.data_len();
    if program_id != extra_account_metas_info.owner || original_account_size < min_account_size {
        return Err(ProgramError::UninitializedAccount);
    }

    // If the new extra_account_metas length is different, resize the account and
    // update
    let length = extra_account_metas.len();
    let account_size = ExtraAccountMetaList::size_of(length)?;
    if account_size >= original_account_size {
        extra_account_metas_info.resize(account_size)?;
        let mut data = extra_account_metas_info.try_borrow_mut_data()?;
        ExtraAccountMetaList::update::<ExecuteInstruction>(&mut data, extra_account_metas)?;
    } else {
        {
            let mut data = extra_account_metas_info.try_borrow_mut_data()?;
            ExtraAccountMetaList::update::<ExecuteInstruction>(&mut data, extra_account_metas)?;
        }
        extra_account_metas_info.resize(account_size)?;
    }

    Ok(())
}
