## Title
Signature Domain Confusion in `SlotMetadata::auth_digest` Allows Cross-Contract StackerDB Chunk Replay - ([File: libstackerdb/src/libstackerdb.rs])

## Summary
`SlotMetadata::auth_digest()` computes the signed digest for a StackerDB chunk over only `slot_id`, `slot_version`, and `data_hash` — it never binds the signature to the specific StackerDB smart contract (`QualifiedContractIdentifier`) the chunk belongs to. This is analogous to the reported "rounding breaks an implicit invariant" bug class: the code assumes a signature that is valid in one context (one StackerDB contract) is only ever checked in that same context, but nothing in the signed data enforces this equality. Because Stacks nodes host multiple StackerDB replicas (e.g. one per reward-cycle `signers-*` contract) that can share the same signer address/slot-id assignment across reward cycles, a signature produced for slot X in contract A can be replayed to store/accept the same chunk in a different, unrelated contract B where that address also happens to hold slot X — breaking the "signed-for-A" vs "stored-as-valid-for-B" equality.

## Finding Description
Chunk authentication in this repo is centered on `SlotMetadata::sign`/`verify`, which operate on `auth_digest()`: [1](#0-0) 

`verify()` simply recovers the public key from this digest and checks against the `signer` address associated with `(smart_contract_id, slot_id)`: [2](#0-1) 

The actual store/verify path in `StackerDBTx::try_replace_chunk` looks up the expected signer strictly by `(smart_contract, slot_id)` and then calls `slot_desc.verify(&slot_validation.signer)`: [3](#0-2) 

The same pattern is used for chunks received over the wire in `validate_received_chunk`, which resolves the signer via `get_slot_signer(smart_contract_id, data.slot_id)` and then calls `slot_metadata.verify(&addr)`: [4](#0-3) 

In neither path does the contract identifier participate in what is actually signed over (`auth_digest`). The contract only determines *which signer table* is consulted to validate the signature — but the signature itself says nothing about which contract it was produced for. If the same signer address is assigned the same `slot_id` in two different StackerDB contracts hosted by the same node (which is plausible for the reward-cycle-scoped `signers-*` contracts, since signer sets and slot assignments can remain identical or overlapping across consecutive/relevant PoX reward cycles), then a previously valid, fully-signed `StackerDBChunkData` for contract A's slot X at some `(slot_version, data_hash)` will also pass verification against contract B's slot X, as long as B's current stored version for that slot is lower than the replayed `slot_version` and it's within `max_writes`. This is a genuine equality break in the "authenticated vs. stored" sense described in the report: the code implicitly assumes signature-validity-for-A implies signature-validity-only-for-A, but the digest computation makes no such guarantee.

## Impact Explanation
An attacker who has observed one legitimately signed StackerDB chunk from a signer (e.g., by receiving it as its natural StackerDBPushChunk broadcast or by fetching it via chunk sync) can re-submit that exact chunk (unmodified — no new forgery capability is required) to a *different* StackerDB replica context where the same address/slot-id pairing exists, causing the node to accept and store data into a slot without that specific write being authorized for that contract instance. This can be used to inject stale/old-cycle data into a newer reward-cycle's StackerDB replica (or vice versa), polluting state that downstream consumers (e.g. signer coordination, event observers in `stackslib/src/net/relay.rs::process_stacker_db_chunks`) treat as canonical for that specific contract, and it will additionally be rebroadcast to the rest of the network via `p2p.broadcast_message`, propagating the misattributed chunk network-wide: [5](#0-4) 

This matches the High-impact category of "serving non-canonical state as canonical" / propagating cross-context data as if it were validly scoped, since the receiving contract has no cryptographic way to distinguish a chunk intended for it from one replayed from a sibling contract sharing the same signer/slot assignment.

## Likelihood Explanation
Exploitability is bounded by the precondition that the same signer address is assigned the same `slot_id` across two or more StackerDB contracts the target node replicates. I was not able to fully confirm from the code I could inspect (`stackslib/src/net/stackerdb/config.rs`, which loads signer-slot assignments from the on-chain `stackerdb-get-signer-slots` trait function) whether the deployed `signers-*`/`miners` contracts in this codebase guarantee distinct addresses per slot across contracts, or whether slot-id assignment order is stable/overlapping across reward cycles. This uncertainty means the likelihood is "possible/likely under realistic signer-set continuity between reward cycles" but not proven certain purely from the reachable code — a full determination would require inspecting the Clarity boot contracts and reward-cycle rollover logic, which the given index/scope did not surface completely.

## Recommendation
Include the `smart_contract_id` (or a stable numeric StackerDB ID) as part of the signed `auth_digest()` in `SlotMetadata`/`StackerDBChunkData`, so that a signature is only ever valid for the specific StackerDB replica it was produced for. This closes the domain-confusion gap analogous to the reported issue's "burn dead shares" fix, which likewise closed an implicit invariant gap rather than relying on the caller to enforce context out-of-band.

## Proof of Concept
Conceptual PoC (cannot be executed without live node infrastructure and confirmed overlapping signer/slot assignment across two contracts):
1. Signer S is assigned `slot_id = 3` in StackerDB contract `signers-1-5` and also in `signers-1-6` (or any two contracts replicated by the target node).
2. S legitimately signs and pushes chunk `C = StackerDBChunkData{slot_id:3, slot_version:2, data, sig}` to `signers-1-5` via `RPCPostStackerDBChunkRequestHandler`.
3. Attacker observes `C` (via the `StackerDBPushChunk` gossip or a chunk-sync `StackerDBGetChunkData` response) and re-submits the identical bytes of `C`, but addressed to contract `signers-1-6`, using `poststackerdbchunk.rs`'s POST endpoint.
4. `try_replace_chunk` for `signers-1-6` looks up `get_slot_signer(signers-1-6, 3)` → S, calls `slot_desc.verify(&S)`, which succeeds because `auth_digest()` never referenced the contract; if `signers-1-6`'s current stored version for slot 3 is `< 2` and `2 <= max_writes`, the chunk is accepted and stored under `signers-1-6`, then rebroadcast network-wide.     /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }

    /// Add or replace a chunk for a given reward cycle, if it is valid
    /// Otherwise, this errors out with Error::StaleChunk
    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
