### Title
Tempdir cleaner aborts entire storage sweep on first entry error, permanently blocking cleanup of subsequent temporary directories - ([File: internal/tempdir/clean.go])

### Summary
`clean()` iterates over all entries in a storage's `@gitaly/tmp` directory and returns immediately on the first error encountered from `perm.FixDirectoryPermissions` or `os.RemoveAll`, aborting processing of every remaining (stale) entry in that same iteration, analogous to the reported ZetaChain bug where a single chain's failure prevented gas price updates for all other chains.

### Finding Description
`clean()` reads all entries of a storage's temp directory and iterates over them in a single loop: [1](#0-0) 

If `perm.FixDirectoryPermissions` or `os.RemoveAll` returns an error for any single stale entry, the function returns immediately, skipping all subsequent entries in `entries` for that storage on that cleanup pass — not just the failing one. Because `os.ReadDir` returns entries in a fixed sorted order, if an entry near the beginning of the listing persistently fails to be fixed/removed (e.g., due to a permission structure or ownership state that `FixDirectoryPermissions` cannot correct, or a nested filesystem condition causing `RemoveAll` to fail), every subsequent cleanup tick will hit the exact same failing entry first and again abort, meaning all entries alphabetically after it are never cleaned, cycle after cycle.

The caller `cleanTempDir` treats this as a per-storage operation and simply logs the error before moving on to the next storage: [2](#0-1) 

`StartCleaning` invokes `cleanTempDir` on a fixed interval forever, but because `clean()` re-reads the same directory and hits the same first failing entry each time, the accumulated backlog of unremoved stale directories is never given a chance to shrink.

Temporary directories under `@gitaly/tmp` are created by ordinary, unprivileged Gitaly operations (clones, imports, fetches, and other RPCs that use `storage.Locator.TempDir`), so an attacker who can trigger repeated operations that create temp directories, combined with one operation whose resulting temp directory triggers a `FixDirectoryPermissions`/`RemoveAll` failure (e.g., unusual permission bits, deeply nested paths, or a race with another process holding a file open), can effectively freeze cleanup for the entire storage.

### Impact Explanation
Because the fix/removal error blocks all entries "later" in the same batch and the same blocking entry is hit again on every subsequent tick, temp directories accumulate indefinitely instead of being purged after `maxAge`. This is a disk-exhaustion Denial-of-Service risk for a storage shard: normal usage keeps creating new temp directories while the cleaner can no longer make forward progress past the stuck entry, so storage usage grows unbounded over time.

### Likelihood Explanation
Likelihood is moderate: it requires an ordinary user (no special privileges) to be able to produce, directly or indirectly, a temp-directory entry whose permissions/state resists `FixDirectoryPermissions` and/or causes `os.RemoveAll` to fail, and it requires that failing entry to sort before other stale entries. This is plausible in a busy Gitaly node since temp directories are created continuously by unprivileged client-facing operations, and any repeated/persistent failure mode (e.g., a filesystem quirk with concurrent readers) would cause it to be hit on every cleaner pass.

### Recommendation
Change `clean()` to continue processing remaining entries after encountering an error on an individual entry, collecting errors (similar to what's done in `internal/backup/pipeline.go`'s `commandErrors` aggregation) and returning them jointly after the loop completes, so a single stuck entry does not block cleanup of the rest of the temp directory:

```go
var errs []error
for _, entry := range entries {
    ...
    if err := perm.FixDirectoryPermissions(ctx, fullPath); err != nil {
        errs = append(errs, err)
        continue
    }
    if err := os.RemoveAll(fullPath); err != nil {
        errs = append(errs, err)
        continue
    }
}
return errors.Join(errs...)
```

### Proof of Concept
1. Trigger repeated Gitaly RPCs that create entries under `@gitaly/tmp` for a storage (e.g., repeated clone/import operations), so several stale directories accumulate over `maxAge`.
2. Arrange (or rely on a natural race/permission condition) for the entry that sorts first among the stale ones to be one that `perm.FixDirectoryPermissions` or `os.RemoveAll` cannot fully process (e.g., a file busy/locked at cleanup time, or unusual permission bits left by a partially-completed operation).
3. Observe via logs (`"finished tempdir cleaner walk"` with an attached error) that `clean()` returns an error on every tick [3](#0-2)  and that entries sorted after the failing one are never removed across multiple ticks, causing continuous growth of the temp directory.

func cleanTempDir(logger log.Logger, locator storage.Locator, storages []config.Storage) {
	for _, storage := range storages {
		start := time.Now()
		err := clean(logger, locator, storage)

		entry := logger.WithFields(log.Fields{
			"time_ms": time.Since(start).Milliseconds(),
			"storage": storage.Name,
		})
		if err != nil {
			entry = entry.WithError(err)
		}
		entry.Info("finished tempdir cleaner walk")
	}
}
