## Title
Content-addressed HOP entry key allows unauthorized pre-image squatting that permanently blocks a legitimate sender's hand-off submission - (File: substrate/client/hop/src/pool.rs)

### Summary
`HopDataPool::insert` derives the pool's uniqueness key solely from `blake2_256(data)` — the raw payload content — with no binding to the sender's identity, authorization, or a nonce. [1](#0-0)  Any account that is separately authorized to submit to a collator's HOP pool (`can_account_promote`) can pre-compute the same content hash for a predictable/known future payload and submit dummy metadata for it first, permanently occupying that hash and causing `DuplicateEntry` for the real sender when the real hand-off data later arrives — mirroring the reported dispute-game UUID-squatting pattern where a narrow, content-derived uniqueness key (missing the extra binding the original protocol required) lets an unprivileged party occupy the slot before the legitimate value is ready to be submitted.

### Finding Description
`insert()` computes `let hash = H256(blake2_256(&data));` and then checks/reserves this hash as the sole uniqueness key across two lock scopes, rejecting any second submission with the same hash via `HopError::DuplicateEntry`. [2](#0-1) [3](#0-2) 

The RPC entrypoint `hop_submit` only checks:
1. size ≤ `max_promotion_size`,
2. the caller is authorized via `can_account_promote` (a general per-account authorization/quota gate, not tied to a specific payload or hash),
3. a valid submit signature over `blake2_256(HOP_SUBMIT_CONTEXT || hash || submit_timestamp)`. [4](#0-3) 

None of these checks bind the submission to *which* payload the caller is allowed to submit, or require any relationship between the submitter and the intended recipients. Since `HOP_META_VERSION`/`Recipient`/`sender_id` in `HopEntryMeta` are attacker-controlled fields distinct from the content hash, any authorized account can:
- Predict or learn the exact bytes of a future legitimate hand-off payload (e.g., a well-known, deterministically-constructed message that a legitimate sender is about to submit — analogous to the "safe/unsafe L2 block root" in the source report, where the eventual correct value is knowable in advance but not yet the one on-chain/canonical),
- Submit that exact `data` first, with the attacker's own `recipients`/`signer`/`sender_id` in `HopEntryMeta`,
- Cause the hash to be occupied in `self.index` before the honest sender submits the same content.

When the legitimate sender later calls `hop_submit` with the identical `data`, `insert()` hits the duplicate check at line 394 (or the race-losing branch at line 433) and returns `HopError::DuplicateEntry`, permanently blocking the real hand-off — the real recipients can never receive or claim this data through this collator, since the stored metadata belongs to the attacker's bogus recipient list. There is no "parentHash"-style extra binding (no nonce, no recipient-set hash, no sender-id component) folded into the uniqueness key the way the report's fix recommended adding `parentHash` to the game UUID.

### Impact Explanation
This breaks the invariant that "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically" as it relates to hand-off delivery: an unprivileged (but authorized-to-submit) account can durably occupy a slot for content it does not own the recipient list for, preventing a specific hand-off from ever being delivered through `hop_claim`/`hop_ack`, and also preventing that data from ever reaching the promotion path (`HopPromoter`) with the correct recipient/authorization metadata. Because the pool is disk-persisted and the duplicate check spans process restarts (recovered from `.meta` files), the squat is durable, not merely a race window. The affected recipients can never claim the intended payload via this collator, causing a permanent, non-recoverable loss of the intended hand-off for that data — a fund-lock/DoS analog scoped specifically to the affected collator's HOP channel.

### Likelihood Explanation
Exploitability requires only that the attacker (a) is "authorized to promote" on this collator (a broad, non-privileged authorization gate per the runtime policy, not an admin/validator role), and (b) can predict the exact bytes of an upcoming legitimate submission. This is plausible for HOP use cases where payload content is deterministic/publicly derivable ahead of time (e.g., a well-known payload format, templated messages, or content whose bytes are visible from another channel before the legitimate submit call lands on this specific collator). This does not require a malicious validator/collator/relayer, admin, or leaked keys — only an ordinary authorized HOP participant, matching the "unprivileged attacker" bar for this analog.

### Recommendation
Bind the pool's uniqueness key to more than raw content: include the intended recipient set (or its hash) and/or the sender's `account_id` in the derived pool key (e.g., `key = blake2_256(data || recipients.encode())` or a separate composite key `(content_hash, recipients_hash)`), so that two submissions of the same bytes destined for different recipients/senders do not collide. Additionally, consider requiring that duplicate-content submissions from a different signer either be rejected up front by the runtime API (`can_account_promote`, informed by the true intended recipients) or allowed to coexist as distinct pool entries keyed by the composite key.

### Proof of Concept
Conceptual PoC (pool-level, matching `pool.rs` tests such as `test_claim_after_ack_returns_already_claimed`):
1. Attacker learns/predicts the exact bytes `data` that a legitimate sender `S` will submit for a hand-off intended for recipient `R`.
2. Attacker (authorized account `A`, distinct from `S`) calls `insert(data, [A_recipient], A_sender_id, A_signer, A_sig, ts)` — this succeeds because `insert` only checks `index.contains_key(&hash)` where `hash = blake2_256(data)`, and inserts `HopEntryMeta` with the attacker's own bogus `recipients` list. [5](#0-4) 
3. Legitimate sender `S` calls `insert(data, [R], S_sender_id, S_signer, S_sig, ts)` with the same `data`. Because `hash` is identical, `index.contains_key(&hash)` is `true`, and the call returns `Err(HopError::DuplicateEntry)`. [6](#0-5) 
4. `R` can never call `hop_claim`/`hop_ack` successfully for this payload through this collator (the stored `HopEntryMeta.recipients` only contains `A_recipient`), and `S`'s submission is permanently rejected as long as the attacker's entry occupies the hash (until the attacker's entry expires or is acked away, which the attacker fully controls, `HOP_META_VERSION`/`expires_at` fields notwithstanding). [7](#0-6) 

This is a locally-provable analog to the report's core pattern: a public, permissionless entrypoint accepts a uniqueness key derived from a value that is knowable/predictable in advance without being bound to the submitter's authorization scope for *that specific* recipient set, letting an unprivileged party squat the slot and permanently block the correct settlement.

	pub fn claim(&self, hash: &HopHash, signature: &[u8]) -> Result<Vec<u8>, HopError> {
		{
			let index = self.index.lock();
			let meta = index.get(hash).ok_or(HopError::NotFound)?;
			// Map NotRecipient → NotFound so callers cannot probe whether a hash
			// exists by observing different error codes.
			let idx = Self::find_recipient_idx(meta, hash, signature, HOP_CLAIM_CONTEXT)
				.map_err(|_| HopError::NotFound)?;

			// If this recipient already acked, the data may be gone.
			if meta.recipients[idx].claimed {
				return Err(HopError::AlreadyClaimed);
			}
		}
		// Read blob from disk and verify its content hash. May be gone if
		// concurrently acked and deleted, in which case we surface NotFound.
		self.read_and_verify_blob(hash)
	}
