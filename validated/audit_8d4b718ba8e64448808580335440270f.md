### Title
Unbounded ABI-offset array indexing in `ValidateMultiSign`/`extractBytes32Array`/`extractBytesArray` causes uncaught out-of-bounds exception in TVM precompile execution - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The `ValidateMultiSign` and `BatchValidateSign` precompiled contracts (TVM addresses used by `validatemultisign(...)` / `batchvalidatesign(...)`) parse ABI-encoded calldata into a `DataWord[] words` array and then use attacker-controlled offset/length fields taken directly from that data to index back into `words` and into the raw byte buffer, without validating the offsets are within bounds before every access. This mirrors CVE-2022-47938's root cause (a length/offset field consumed from an untrusted network structure and used to index a buffer without validating it against the actual buffer bounds before the read), except that in java-tron the parser is `PrecompiledContracts.extractBytes32Array`/`extractBytesArray`/`extractSigArray`, and the network structure is the TVM `CALL` input to a precompile address, reachable by any transaction sender or smart-contract caller.

### Finding Description
`extractBytes32Array` performs zero bounds validation on the caller-supplied `offset`: [1](#0-0) 
It is called from `BatchValidateSign.doExecute` with `offset = words[2].intValueSafe() / WORD_SIZE`, a value fully controlled by the calldata's ABI-encoded `address[]` offset field, before any check that this offset is `< words.length`: [2](#0-1) 

`extractBytesArray` and `extractSigArray` do check the *initial* `offset` against `words.length`, but not the subsequent derived indices `offset + i + 1` (used to read `bytesOffset`) or `offset + bytesOffset + 1` (used to read `bytesLen`), both of which are also attacker-controlled and unbounded: [3](#0-2) [4](#0-3) 

In `ValidateMultiSign.execute`, the initial array reads (`words[0]`, `words[1]`, `words[2]`, and the `words[words[3].intValueSafe()/WORD_SIZE]` size check) and the `extractBytesArray`/`extractSigArray` calls all occur **outside** the only `try/catch` in the method, which wraps solely the later permission-processing block: [5](#0-4) 

A malformed/short `rawData`, or an oversized `words[3]` offset, throws an uncaught `ArrayIndexOutOfBoundsException` (or `NegativeArraySizeException` for a negative decoded length) from within `execute()`.

A post-hoc mitigation exists — `isValidAbiEncoding` plus a broad outer `try { doExecute } catch (Throwable t)` in `BatchValidateSign.execute` — but both are gated behind `VMConfig.allowTvmOsaka()`, and `ValidateMultiSign.execute` has **no equivalent outer catch at all**, only the guard check: [6](#0-5) [7](#0-6) 

Tests explicitly document that when `allowTvmOsaka()` is disabled, the legacy decoder path can raise an uncaught `RuntimeException` on malformed input: [8](#0-7) 

### Impact Explanation
An uncaught runtime exception thrown from inside `PrecompiledContract.execute()` propagates up through `Program.callToPrecompiledAddress`, which has no surrounding exception handling for this call: [9](#0-8) 
I was unable to fully trace how far up the exception is ultimately caught (e.g., whether the enclosing actuator/`TransactionTrace` catches all `RuntimeException`/`Throwable` and merely fails the single transaction, or whether it could propagate further and disrupt batch/block application in `Manager`). The severity therefore depends on that unverified catch boundary: at minimum this is a reliable way to force any single transaction that triggers `validatemultisign` with malformed calldata to fail/abort abnormally instead of cleanly reverting; if a broader catch is missing somewhere in block-application/`TransactionTrace`, it could disrupt processing of the containing block. Given the uncertainty on the outer catch, I rate this Medium, matching the CVE-2022-47938 severity, as a robustness/DoS-class analog rather than a confirmed node-crash.

### Likelihood Explanation
Trivially reachable: any account can call a smart contract that issues a TVM `CALL` (or directly no bytecode is even required if the target contract simply forwards calldata) to precompile address `0x66` (`validateMultiSign`) with crafted, undersized, or offset-manipulated calldata. No special privileges, existing account state, or specific chain configuration beyond `allowTvmSolidity059()` (already broadly active) are required.

### Recommendation
Add bounds validation for every derived index (`offset + i + 1`, `offset + bytesOffset + 1`, and the offset used in `extractBytes32Array`) against `words.length` before dereferencing, mirroring the existing `isValidAbiEncoding` guard, and make it unconditional (not gated by `allowTvmOsaka()`). Wrap the entirety of `ValidateMultiSign.execute` (not just the permission-processing sub-block) in a `try/catch(Throwable)` that returns `Pair.of(true, DATA_FALSE)` on any decoding failure, consistent with how `BatchValidateSign.execute` already wraps `doExecute`.

### Proof of Concept
Call the TVM precompile at address `0x66` (`validatemultisign(address,uint256,bytes32,bytes[])`) via a `CALL` opcode with calldata that is shorter than 5 words (e.g., only 2 words), or with a valid-looking head but a `bytes[]` offset word (`words[3]`) set to a huge value such as `0xFFFFFFFF`. This causes `words[words[3].intValueSafe()/WORD_SIZE]` or `extractBytesArray`'s internal indexing to throw `ArrayIndexOutOfBoundsException`, which is not caught anywhere in `ValidateMultiSign.execute`, as confirmed by the existing test `testTip854PreActivationNoOp` in `ValidateMultiSignContractTest.java` documenting that pre-`allowTvmOsaka` calls with malformed calldata can raise uncaught `RuntimeException`.     if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
