## Analog Finding

### Title
Sandwich attacks against `ExchangeWithdrawContract` due to missing slippage/minimum-output protection - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
The TRC10 Bancor-style AMM exchange in java-tron supports `ExchangeTransactionContract` (a swap), which includes a user-supplied `expected` minimum-output field that is checked before execution, and `ExchangeWithdrawContract` (a liquidity withdrawal), which has **no** equivalent minimum-output protection. Any unprivileged account can front-run/back-run an exchange creator's withdrawal transaction with ordinary `ExchangeTransactionContract` swaps to manipulate the pool ratio and siphon value from the withdrawer, exactly the class of sandwich attack described in the external report (a withdrawal function that accepts "any price" because it lacks a bound on the output amount).

### Finding Description
`ExchangeTransactionActuator` protects swappers from sandwiching by requiring the caller to supply a minimum expected output (`tokenExpected`), which is validated against the computed `anotherTokenQuant` before the trade is allowed to proceed: [1](#0-0) 

In contrast, `ExchangeWithdrawContract`/`ExchangeWithdrawActuator` computes the paired token amount to return to the withdrawer purely from the *current* on-chain pool ratio (`firstTokenBalance`/`secondTokenBalance`) at execution time, with no user-supplied minimum-output or price-bound parameter in the contract at all: [2](#0-1) 

The protobuf message itself confirms there is no `expected`/limit field, unlike `ExchangeTransactionContract`: [3](#0-2) 

Withdrawal is restricted to the pool's creator address (any account that itself called `ExchangeCreateContract` to make a pool, so this is reachable by an ordinary unprivileged account): [4](#0-3) 

Since `ExchangeTransactionContract` is broadcastable by anyone and directly mutates `firstTokenBalance`/`secondTokenBalance` of the same `ExchangeCapsule` used in withdrawal math, an attacker who observes a pending `ExchangeWithdrawContract` in the mempool can:
1. Front-run it with a large swap (`ExchangeTransactionContract`) that skews the pool ratio in the direction that reduces the `anotherTokenQuant` the victim will receive on withdrawal.
2. Let the victim's withdrawal execute at the skewed ratio (there is no `expected`/min-out check to abort it, only a static 0.0001 relative "precision" check between the two computed BigDecimal/double values, which does not defend against ratio manipulation — see `ExchangeWithdrawActuator.java` lines 228-243).
3. Back-run with an opposite trade to restore the ratio and capture the value extracted from the victim, exactly as described for UniV3 sandwich attacks in the referenced report.

### Impact Explanation
The pool creator withdrawing liquidity can be made to receive materially less of the paired asset than the pool's fair-value ratio would imply, transferring that value to the attacker performing the sandwich trades. This is a direct, unauthorized value-extraction / theft-of-funds scenario reachable purely through ordinary signed transactions (`ExchangeTransactionContract` swaps + `ExchangeWithdrawContract`), matching the medium severity of the original report.

### Likelihood Explanation
Exploitation only requires monitoring the mempool for pending `ExchangeWithdrawContract` transactions and issuing ordinary, unprivileged `ExchangeTransactionContract` swap transactions before and after it — capabilities available to any account holder, with no special permissions, SR/witness status, or protocol-level access required.

### Recommendation
Add a user-specified minimum/maximum bound (analogous to `expected` in `ExchangeTransactionContract`) to `ExchangeWithdrawContract`, and validate the computed `anotherTokenQuant` against it in `ExchangeWithdrawActuator.doValidate()`/`execute()` before mutating balances, rejecting the transaction if the pool ratio has moved unfavorably beyond the caller's tolerance.

### Proof of Concept
1. Attacker observes the exchange creator's pending `ExchangeWithdrawContract` (withdraw `tokenQuant` of `firstTokenID`) in the mempool.
2. Attacker submits an `ExchangeTransactionContract` selling a large amount of `secondTokenID` into the same exchange, which via `ExchangeCapsule.transaction()` shifts `firstTokenBalance`/`secondTokenBalance` unfavorably for the pending withdrawal [5](#0-4) .
3. The victim's `ExchangeWithdrawContract` executes next, computing `anotherTokenQuant` from the now-skewed balances with no minimum-output check to protect them [6](#0-5) .
4. Attacker submits a reverse `ExchangeTransactionContract` trade to restore the ratio, realizing the profit taken from the victim's withdrawal.

      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)

    }
