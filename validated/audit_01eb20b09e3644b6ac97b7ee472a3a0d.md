### Title
Position-scoped `last-borrow-block` allows indefinite same-block liquidation evasion across all debt assets - ([File: mainnet/contracts/market/v0-market-vault.clar], [File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`debt-add-scaled` in `v0-market-vault.clar` stamps a single `last-borrow-block` field on the borrower's *entire position* every time any debt asset is borrowed, and `liquidate()` in `v0-4-market.clar` uses that single field to block liquidation of a *specific* debt asset if it equals the current block. Because the field is not scoped per debt-asset (analogous to the `lastTimeStamp` in the M-15 report being shared across vaults instead of tracked per `vaultNumber`), a borrower can repeatedly trigger a trivial borrow on any asset to keep resetting the shared flag and perpetually block liquidation of an entirely different, already-unhealthy debt position.

### Finding Description
`debt-add-scaled` merges the position with `{ mask: update-mask, last-update: stacks-block-time, last-borrow-block: stacks-block-height }` on every borrow, for any `asset-id`: [1](#0-0) 

`last-borrow-block` is stored once per position/account, not per `asset-id` — there is no map keyed by `{account, asset-id}`. This single field is meant to implement "oracle frontrunning protection: prevent same-block liquidation" for the asset that was just borrowed, but because it lives on the shared position struct, it is overwritten by a borrow of *any* asset.

`liquidate()` reads that same single field and blocks liquidation whenever it equals the current block, regardless of which `debt-aid` is being liquidated: [2](#0-1) 

This mirrors the M-15 pattern exactly: a state variable that conceptually should be tracked per-unit (per `vaultNumber` in the Derby report; per `asset-id`/debt position here) is instead implemented as a single global/shared value, so an action on one "vault" (asset) incorrectly perturbs the state used to gate behavior on another "vault" (asset).

### Impact Explanation
An attacker with an existing unhealthy debt position (e.g., large USDC debt now under-collateralized after a price move) can, every block, issue a trivial borrow of a *different*, healthy, low-value asset (dust amount) purely to refresh `last-borrow-block` to `stacks-block-height`. Because the check in `liquidate()` is keyed on the position, not on `debt-aid`, this trivial unrelated borrow makes `ERR-LIQUIDATION-BORROW-SAME-BLOCK` fire for liquidation attempts against the real, unhealthy debt asset. By repeating this every block, the borrower can indefinitely stall liquidation of their bad debt, which:
- Delays/at the limit prevents socialize-debt / liquidation from ever executing on an insolvent position, exposing lenders/suppliers to growing bad debt and impairing protocol solvency (temporary/permanent freezing of funds owed to the protocol/other users, and a path toward protocol insolvency if price continues to move against the position while liquidation stays blocked).
- Breaks the intended "liquidation must be possible whenever a position crosses the liquidation LTV" invariant that protects all depositors.

This lands in the **Critical** bucket (protocol insolvency / permanent freezing of funds) because it lets a borrower unilaterally and indefinitely suppress the core liquidation safety mechanism for an underwater position at negligible cost (one dust-sized borrow transaction per block).

### Likelihood Explanation
Likelihood is high: the attack requires only a standard, permissionless `borrow`/`debt-add-scaled` call for any enabled borrowable asset with amount as low as 1 unit (the only check is `(> scaled-amount u0)`), executed once per block by the borrower or any bot acting on their behalf. No privileged role, oracle manipulation, or flashloan is needed — it is pure repeated use of an ordinary market entry point (`borrow`) to keep the shared flag "hot" against the intended per-asset liquidation-timing check.

### Recommendation
Track the same-block borrow protection per debt asset (or at minimum, only refresh `last-borrow-block` when the specific asset that is later checked in `liquidate()` was the one just borrowed). Concretely, store `last-borrow-block` in a map keyed by `{account, asset-id}` (mirroring the fix recommended in the referenced report: "keep tracking the state per unit using a map/array" instead of a single shared field), and have `liquidate()` look up the block only for `debt-aid`, not the position as a whole.

### Proof of Concept
1. Attacker opens a position with collateral and borrows `USDC` (debt-aid = USDC) until price movement makes the position eligible for liquidation (LTV ≥ `ltv-liq-partial`).
2. Each subsequent block, before any liquidator's `liquidate` transaction can land, the attacker calls `borrow` for a trivial amount (e.g., `1`) of a different, healthy asset (e.g., `sBTC`), which is only asserted `> u0`: [3](#0-2) 
   This sets the shared `last-borrow-block` on the position to the current `stacks-block-height`.
3. A liquidator attempts `liquidate(borrower, sBTC-collateral, USDC-debt-ft, ...)` targeting the actually-unhealthy `USDC` debt. The check reads the same shared field: [2](#0-1) 
   Since `last-borrow-block == stacks-block-height`, the call reverts with `ERR-LIQUIDATION-BORROW-SAME-BLOCK`, even though the borrow that "protected" the position was for a completely unrelated asset.
4. Attacker repeats step 2 every block, indefinitely blocking liquidation of the unhealthy `USDC` debt while the position accrues further losses, at the cost of one dust-amount transaction per block.
