### Title
Stale `PromiseYieldReceipt` with embedded privileged actions (AddKey/DeployContract) survives `DeleteAccount` and is auto-delivered to a recreated account via yield-timeout resolution, bypassing actor-permission checks - (File: `core/store/src/utils/mod.rs`, `runtime/runtime/src/lib.rs`, `runtime/runtime/src/actions.rs`)

### Summary
`remove_account` deletes an `Account`, its code, access keys and contract data, but never touches `TrieKey::PromiseYieldReceipt` or `TrieKey::PromiseYieldStatus`. A contract can create a self-targeted `PromiseYield` receipt (`predecessor_id == receiver_id`) and, using the same promise index returned by `promise_yield_create`, append additional privileged actions (`AddKey`, `DeployContract`, etc.) to that same underlying receipt via the normal `promise_batch_action_*` host functions. After `DeleteAccount` removes the account, the stale receipt (and its independent `PromiseYieldTimeout` queue entry) remain in state; once the timeout matures, `resolve_promise_yield_timeouts` automatically fires a `PromiseResume` for any account name that still has the matching `PromiseYieldReceipt` key in the trie — with no check that the account is the "same" incarnation that created it — delivering the embedded privileged action against whichever new account now occupies that name.

### Finding Description
`promise_yield_create` (`runtime/near-vm-runner/src/logic/logic.rs:3660-3718`) creates a receipt via `self.ext.create_promise_yield_receipt(...)`, pushes it as an ordinary promise (`checked_push_promise(Promise::Receipt(new_receipt_idx))`), and appends a `FunctionCall` action to it. Because the returned value is a normal promise index, the contract can subsequently call e.g. `promise_batch_action_add_key_with_full_access(promise_idx, ...)` (`runtime/near-vm-runner/src/logic/logic.rs:3447-3471`), which resolves the same `promise_idx` back to the same `receipt_idx` via `promise_idx_to_receipt_idx_with_sir` and calls `append_action_add_key_with_full_access` (`runtime/runtime/src/receipt_manager.rs:544-557`), pushing an `AddKey` action into the *same* `ActionReceiptMetadata.actions` vector that already holds the yield's `FunctionCall`. Nothing restricts a `PromiseYield` receipt to a single `FunctionCall` action.

Once dispatched, the receipt is stored on the receiver's shard as `TrieKey::PromiseYieldReceipt { receiver_id, data_id }` (`runtime/runtime/src/lib.rs:1495-1499`, `set_promise_yield_receipt`), and a corresponding entry is enqueued in the global `PromiseYieldTimeout` queue.

`remove_account` (`core/store/src/utils/mod.rs:505-575`) only removes `TrieKey::Account`, `TrieKey::ContractCode`, access/gas keys, and `TrieKey::ContractData` — it never iterates or removes `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, or the `PromiseYieldTimeout` queue entries (which are indexed independently of the account, by a global `u64` index, not by account-id prefix, so they are never in scope of the account-prefix iteration used by `remove_account` anyway). `action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) calls `remove_account` and clears the account, but the stale yield artifacts persist untouched.

When the block height passes `queue_entry.expires_at`, `resolve_promise_yield_timeouts` (`runtime/runtime/src/lib.rs:3009-3105`) checks only `state_update.contains_key(&promise_yield_key, ...)` (where `promise_yield_key = TrieKey::PromiseYieldReceipt { receiver_id: queue_entry.account_id, data_id: queue_entry.data_id }`) and, if present, automatically constructs and forwards a `PromiseResume` receipt to `queue_entry.account_id` — completely independent of whether the account was deleted and recreated in the interim, and without requiring any transaction from the attacker at delivery time.

When that `PromiseResume` is processed (`runtime/runtime/src/lib.rs:1500-1534`), the stored stale receipt (with its embedded `AddKey`/`DeployContract` action) is retrieved via `get_promise_yield_receipt` and executed as a normal action receipt. `apply_action` runs `check_actor_permissions` (`runtime/runtime/src/actions.rs:739-785`), which for `AddKey`/`DeployContract` only checks `actor_id != account_id` where `actor_id` is initialized from `receipt.predecessor_id().clone()` (`runtime/runtime/src/lib.rs:855`). Since the original receipt was self-targeted (`predecessor_id == receiver_id == <account name>`), this string-equality check trivially passes for the *new* account occupying the same name — there is no invariant binding the check to the specific account "incarnation" that existed when the yield was created.

### Impact Explanation
This is an authorization-escalation / account-takeover primitive: a stale privileged action (full-access `AddKey`, or `DeployContract`) that was authorized under an account that no longer exists gets executed against a completely different, unrelated new owner's account of the same name — solely because `check_actor_permissions` performs string-only comparison and `remove_account` fails to purge yield-related trie state. This maps to the "authorization escalation across accounts or promises" bounty category and can lead directly to full compromise (key takeover) of any freshly (re)created account whose name was previously used by an attacker-controlled account with a pending yield.

### Likelihood Explanation
Preconditions: attacker only needs to (1) deploy an ordinary contract, (2) call `promise_yield_create` targeting itself and use the returned promise index to append an `AddKey`/`DeployContract` action, (3) issue `DeleteAccount` on itself (their locked balance is zero, satisfying `check_actor_permissions`'s `DeleteAccountStaking` check), and (4) wait for the yield timeout to fire (it is unconditional, requiring no attacker transaction at delivery time) — or otherwise ensure it is resumed. All of this is achievable by an ordinary, unprivileged funded account through normal RPC transactions and a custom wasm contract; no validator/node/gossip access is required. The exploit is fully repeatable (any attacker can salt many "trap" account names) but the payoff requires a victim to freely recreate an account under the exact same name after it is deleted, which is a real but not universal scenario (common with sub-accounts of factories, or short/desirable top-level names being deleted and re-registered).

### Recommendation
- Make `remove_account` also enumerate and remove any `TrieKey::PromiseYieldReceipt`/`TrieKey::PromiseYieldStatus`/`TrieKey::YieldIdToDataId`/`TrieKey::DataIdToYieldId` entries for the account being deleted, and/or invalidate corresponding `PromiseYieldTimeout` queue entries (e.g., via a tombstone or generation counter).
- Alternatively/additionally, bind `check_actor_permissions` (and yield-resume delivery) to an account "incarnation" identifier (e.g., a monotonically increasing per-account nonce/generation stored and checked on `CreateAccount`), so that a receipt authorized under a prior incarnation cannot satisfy permission checks against a later one with the same name.
- Restrict `PromiseYield` receipts to only ever carry a single `FunctionCall` action (matching documented behavior) so that no additional privileged actions can be smuggled onto the same promise index.

### Proof of Concept
Runtime integration test plan (test-loop-tests or `runtime/runtime/src/tests/apply.rs` style):
1. Deploy attacker contract to account `trap.near` exposing a method `go()` that calls `promise_yield_create` targeting `trap.near` itself, then, using the returned promise index, calls `promise_batch_action_add_key_with_full_access(promise_idx, attacker_pubkey, 0)`.
2. Call `go()` from `trap.near`; assert the resulting state has a `TrieKey::PromiseYieldReceipt { receiver_id: "trap.near", data_id }` whose `Receipt`'s actions include both the `FunctionCall` and the `AddKey` action.
3. Submit `DeleteAccount { beneficiary_id: attacker_alt.near }` from `trap.near`; assert `Account`/`AccessKey` for `trap.near` are gone but `get_promise_yield_receipt(state_update, &"trap.near".parse().unwrap(), data_id)` still returns `Some(...)`.
4. Have a different, unrelated signer create `CreateAccount` for `trap.near` again (simulating a new owner), funding it and adding its own key.
5. Advance `block_height` past the yield timeout so `resolve_promise_yield_timeouts` fires the `PromiseResume` for `trap.near`/`data_id`.
6. Process the `PromiseResume` receipt and assert: (a) it executes without an `ActorNoPermission` error, and (b) the attacker's public key has been added as a full-access key on the *new* `trap.near` account, proving cross-incarnation privilege escalation.
