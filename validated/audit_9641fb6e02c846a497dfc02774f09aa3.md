### Title
Non-atomic multi-step object pool linking leaves repository partially linked on later-step failure - (File: internal/git/objectpool/link.go)

### Summary
`Link` in `internal/git/objectpool/link.go` performs a multi-step, non-atomic sequence to attach a repository to an object pool: (1) write the `objects/info/alternates` file, (2) transactionally commit/vote on that write, (3) record the file in the transaction FS, and (4) remove the member's packfile bitmaps via `removeMemberBitmaps`. If step (4) fails after steps (1)-(3) have already succeeded and been committed, the function returns an error to the caller, but the alternates file write is not rolled back, leaving the repository durably linked to the object pool while the RPC reports failure.

### Finding Description
`Link` first checks whether the repository is already linked [2](#0-1) , then writes the alternates file and commits it through the transaction manager, recording it into the transaction filesystem [3](#0-2) . Once `transaction.CommitLockedFile` succeeds, the alternates linkage is durable/committed — subsequent replicas will vote as "committed" and, when the WAL-based transaction manager applies the log entry, the alternates file change becomes part of the on-disk repository state. Only after this commit does `Link` call `removeMemberBitmaps(ctx, pool, repo)` [4](#0-3) , which performs additional filesystem operations (`os.ReadDir`, `os.Remove`) that can fail independently of the alternates commit, e.g. due to permission errors, I/O errors, or the pack directory unexpectedly not existing [5](#0-4) . If `removeMemberBitmaps` returns an error, `Link` propagates it up through `ObjectPool.Link` and the gRPC handler `LinkRepositoryToObjectPoolRequest`, which turns it into an internal error with no compensating rollback of the alternates write [6](#0-5) . There is no `defer`-based cleanup, no re-deletion of the alternates file, and no re-vote to undo the prior "Committed" phase.

This mirrors the report's core bug class: a multi-step flow with an irreversible earlier state update (durable alternates linkage) followed by a later step that can fail, with no rollback path, leaving the system in a state inconsistent with what the caller (and any orchestrating logic, e.g. GitLab Rails, that treats an RPC error as "no-op") believes occurred.

### Impact Explanation
An ordinary caller invoking `LinkRepositoryToObjectPool` (reachable via any client with access to that RPC, including replication/Praefect paths such as `internal/praefect/replicator.go`) that hits a transient filesystem error during bitmap removal will receive an RPC error indicating the link failed, yet the target repository will already be sharing objects with (dependent on) the pool via the committed alternates file. This produces:
- A repository silently gaining an alternates dependency on an object pool despite the caller believing the operation failed, which can cause the caller/orchestrator to retry `CreateObjectPool`/`LinkRepositoryToObjectPool` or otherwise mismanage pool membership bookkeeping (e.g. GitLab tracking whether a project belongs to a pool).
- The pre-existing "multiple bitmaps" warning condition that `removeMemberBitmaps` exists specifically to avoid, now guaranteed to persist since the very step meant to fix it failed after the alternates link was already made permanent.
- In WAL-backed transaction mode, the alternates file change is queued in the transaction's recorded FS and will be applied even though the RPC ultimately returns an error, since the failure occurs after `transaction.CommitLockedFile` reaches the `Committed` phase.

### Likelihood Explanation
The `removeMemberBitmaps` step performs ordinary filesystem calls (`os.ReadDir`, `os.Remove`) which can fail for mundane reasons (permission issues, concurrent modification, disk I/O errors) unrelated to the alternates commit that precedes it. Because this is a distinct, later filesystem operation with no dependency-check that would prevent it from being reached in practice on any repository that already has bitmaps, the divergence between "committed alternates" and "returned error" is reachable through normal use of the `LinkRepositoryToObjectPool` RPC without any privileged access or malicious input — it only requires an environment-level failure (e.g., disk pressure, permission drift) at exactly the point of bitmap cleanup.

### Recommendation
Make `Link` atomic with respect to failure: either perform bitmap removal before writing/committing the alternates file so an error prevents any durable filesystem change, or wrap the alternates-file write/commit and bitmap removal in a single rollback-capable sequence (e.g., revert/re-remove the alternates file and re-vote to undo the "Committed" phase) if `removeMemberBitmaps` fails after the alternates commit succeeded. At minimum, treat bitmap-removal failure as non-fatal to the link decision (log and continue) since the code comments already indicate bitmap cleanup is a "nice-to-have" that would eventually converge via garbage collection, rather than surfacing it as a hard RPC failure after the primary state change has already been committed.

### Proof of Concept
1. Set up a repository with existing bitmaps and an object pool eligible to be linked (as in `internal/git/objectpool/link_test.go`, e.g. the `TestLink` "transactional repository link" case).
2. Make the repository's `objects/pack` directory (or one bitmap file within it) unremovable at the moment `removeMemberBitmaps` executes — e.g. mount it read-only, revoke write permission on the directory, or race a concurrent process to delete/replace the pack directory right after the alternates write commits.
3. Call `LinkRepositoryToObjectPool`. Observe:
   - The RPC returns an internal error (from `os.Remove` failing inside `removeMemberBitmaps`, propagated via `internal/gitaly/service/objectpool/link.go:23-25`).
   - Despite the error, `objects/info/alternates` in the repository now durably contains the pool's relative object path (verifiable via `stats.AlternatesInfoForRepository`), and the repository is functionally linked to the pool even though the caller received a failure response.

func (s *server) LinkRepositoryToObjectPool(ctx context.Context, req *gitalypb.LinkRepositoryToObjectPoolRequest) (*gitalypb.LinkRepositoryToObjectPoolResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	pool, err := s.poolForRequest(ctx, req)
	if err != nil {
		return nil, err
	}

	repo := s.localRepoFactory.Build(repository)

	if err := pool.Link(ctx, repo); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	return &gitalypb.LinkRepositoryToObjectPoolResponse{}, nil
}

func removeMemberBitmaps(ctx context.Context, pool *localrepo.Repo, repo *localrepo.Repo) error {
	poolPath, err := pool.Path(ctx)
	if err != nil {
		return err
	}

	poolBitmaps, err := getBitmaps(poolPath)
	if err != nil {
		return err
	}
	if len(poolBitmaps) == 0 {
		return nil
	}

	repoPath, err := repo.Path(ctx)
	if err != nil {
		return err
	}

	memberBitmaps, err := getBitmaps(repoPath)
	if err != nil {
		return err
	}
	if len(memberBitmaps) == 0 {
		return nil
	}

	for _, bitmap := range memberBitmaps {
		if err := os.Remove(bitmap); err != nil && !os.IsNotExist(err) {
			return err
		}
	}

	return nil
