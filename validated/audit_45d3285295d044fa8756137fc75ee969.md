### Title
Off-chain Multisig Authorization Signatures Lack Purpose/Context Binding in `ValidateMultiSign`/`BatchValidateSign` TVM Precompiles - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `ValidateMultiSign` and `BatchValidateSign` precompiled contracts let any smart contract ask the TVM to recover the signer(s) of an arbitrary caller-supplied hash and check their combined `Permission` weight. The hash that gets signed off-chain is fully defined by the calling contract's own encoding scheme (an address, a `permissionId`, and one opaque 32-byte `data` word, or — in the `BatchValidateSign` case — a raw caller-supplied hash with no structure at all). Because the protocol enforces no purpose/action/nonce/contract-address binding on top of this hash, the same off-chain signature produced for one authorization purpose can be replayed to satisfy the multisig gate of an unrelated authorization check, exactly the "signature reuse across different intents" bug class described in the referenced report.

### Finding Description

then recovers each signer via `recoverAddrBySign` and sums the `Permission` weight of the recovered addresses: [2](#0-1) 

`recoverAddrBySign` itself performs a pure ECDSA recovery with no scope check at all: [3](#0-2) 

`BatchValidateSign` is even more permissive: it takes an entirely caller-provided `hash` word (not even combined with address/permissionId at the protocol level) and validates arbitrary `(signature, address)` pairs against it: [4](#0-3) 

In both precompiles, the only "context" baked into the signed payload is whatever the calling contract's author decided to put into `data`/`hash`. There is no protocol-level requirement that this payload include the calling contract's own address, a chain id, an action discriminator, a nonce, or an expiration. This mirrors the CrosschainMerkleDistributor pattern: the beneficiary's signature authenticates a key holder and an arbitrary blob, but nothing forces that blob to be unique to one specific claim/action. Any account whose signature over a given `(address, permissionId, data)` triple has ever been observed on-chain (e.g. included in a prior transaction's calldata, or leaked/sold, exactly as in the report's User A/User B scenario) can have that exact signature re-submitted by anyone to a second, unrelated TVM contract/dApp that happens to compute the same triple for a different action, causing the second contract's multisig check to pass without a fresh authorization from the key holder.

### Impact Explanation
If any TVM contract deployed on java-tron uses `ValidateMultiSign`/`BatchValidateSign` as an authorization gate for a fund-moving action (a common on-chain "meta-transaction"/multisig-approval pattern, since these precompiles exist specifically to let contracts implement TRON's native permission/multisig system), and its `data`/`hash` construction does not itself fully bind the calling contract address, action type, and a nonce, an attacker can capture a previously-published valid signature and replay it into a different consuming path to obtain approval for a transfer the key holder never authorized — i.e., theft of funds/assets gated by that multisig check. Because the precompile is reachable from any unprivileged `TriggerSmartContract` call, exploitation requires no special privileges beyond deploying or calling a contract.

### Likelihood Explanation
Exploitability depends on a downstream contract's calldata construction habits (analogous to generic `ecrecover` misuse on other EVM chains), so it is not automatically exploitable against every user of the precompile, but the precompile itself provides zero domain-separation guardrails, so any contract author who signs off-chain data with these primitives without manually adding a nonce/contract-address/expiry is exposed. Given `ValidateMultiSign`/`BatchValidateSign` are advertised, well-known TRON precompiles for implementing multisig approvals in TVM contracts, this is a realistic and moderately likely misuse pattern.

### Recommendation
Consider hardening the precompiles themselves rather than relying purely on caller discipline:
- For `ValidateMultiSign`, include the calling contract's own address (`msg.sender`/precompile caller) and a chain id in the hash construction so a signature bound to one consuming contract cannot be replayed against another.
- For `BatchValidateSign`, since the hash is fully caller-supplied with no structure, document (and ideally enforce via a required prefix/domain tag) that callers must incorporate contract address, purpose, and a nonce/expiry into the hash before signing off-chain.
- Provide TVM-level guidance/templates for safe usage to discourage naive reuse of these precompiles in "claim"/"airdrop"/"distributor"-style contracts.

### Proof of Concept
1. Contract A (e.g., a rewards distributor) asks users to sign `sha256(ownerAddress || permissionId || sha256(amount, recipient))` off-chain and calls `ValidateMultiSign` on-chain to authorize a payout, as exercised in the existing test harness: [5](#0-4) 
2. An unrelated Contract B independently constructs the identical `data = sha256(amount, recipient)` for a different purpose (e.g. a different token payout with the same amount/recipient encoding) and also calls `ValidateMultiSign` with the same `ownerAddress`/`permissionId`.
3. Because the recovered signer/weight check in `PrecompiledContracts.java` lines 1088-1110 only verifies `(address, permissionId, data)` → hash → recovered signer weight, the signature originally produced for Contract A's payout is accepted by Contract B, letting anyone in possession of that on-chain-visible signature trigger Contract B's payout without a fresh authorization from the key holder.

  private static byte[] recoverAddrBySign(byte[] sign, byte[] hash) {
    byte[] out = null;
    if (ArrayUtils.isEmpty(sign) || sign.length < 65) {
      return new byte[0];
    }
    try {
      Rsv rsv = Rsv.fromSignature(sign);
      SignatureInterface signature = SignUtils.fromComponents(rsv.getR(), rsv.getS(), rsv.getV(),
          CommonParameter.getInstance().isECKeyCryptoEngine());
      if (signature.validateComponents()) {
        out = SignUtils.signatureToAddress(hash, signature,
            CommonParameter.getInstance().isECKeyCryptoEngine());
      }
    } catch (Throwable any) {
      logger.info("ECRecover error", any.getMessage());
    }
    return out;
  }
