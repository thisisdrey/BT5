StackerDB chunk signatures omit the target contract identifier, enabling cross-StackerDB replay of authenticated chunks - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` in `libstackerdb/src/libstackerdb.rs` computes the signed digest for a StackerDB chunk from only `slot_id`, `slot_version`, and `data_hash` — it never binds the signature to the specific StackerDB smart contract (the "domain") the chunk belongs to. This is the same class of bug as the reported EIP-712 issue: the signed payload is missing a domain-binding value (there, `chainId`; here, the StackerDB contract identifier), so a signature that is valid for one context can be replayed in a different context.

### Finding Description
The digest that is signed and verified for every StackerDB chunk is: [1](#0-0) 

`SlotMetadata::sign()` and `SlotMetadata::verify()` operate purely on this digest: [2](#0-1) 

Server-side, `StackerDBTx::try_replace_chunk()` looks up the expected signer address *for a given contract's slot* via `get_slot_validation`, and then calls `slot_desc.verify(&slot_validation.signer)`, which recomputes the very same contract-agnostic digest: [3](#0-2) 

The unauthenticated HTTP write path (`POST /v2/stackerdb/:address/:contract/chunks`, `RPCPostStackerDBChunkRequestHandler`) accepts a `(slot_id, slot_version, sig, data)` tuple from any remote peer and passes it straight to `try_replace_chunk` for the `contract_identifier` parsed from the URL path — there is no additional binding checked between the signature and the target contract: [4](#0-3) 

Because the signed digest never includes the StackerDB `smart_contract_id`, if the same signer address owns the same `slot_id` in two different StackerDB replicas (a common situation: signer sets rotate per reward cycle across distinct `.signers-<cycle>-<page>` contracts, and the same signer key frequently retains the same slot index across cycles/instances), a chunk that was validly signed and broadcast for StackerDB "A" can be resubmitted verbatim (same `slot_id`, `slot_version`, `sig`, `data`) against StackerDB "B" and will pass `verify()` there too, as long as version/size/write-count constraints happen to be satisfiable. This breaks the equality the protocol relies on: "signed for contract A" should not be interchangeable with "authenticated for contract B."

This mirrors the reported bug class exactly: a domain-separation value is omitted from a signed payload, enabling replay of a legitimately-produced signature outside its intended context.

### Impact Explanation
This allows an unauthenticated remote peer to write attacker-replayed (but validly-signed by a legitimate signer key) chunk data into a StackerDB replica it was never intended for, as long as the slot/version/size constraints line up. Depending on which StackerDB contracts share signer/slot layouts (e.g. successive reward-cycle signer-message DBs), this can result in stale or out-of-context signer messages (block responses, transactions, etc.) being propagated as if freshly authored for the current DB/reward cycle, since a successful `try_replace_chunk` also triggers `node.set_relay_message(StacksMessageType::StackerDBPushChunk(...))`, causing network-wide propagation of the replayed chunk: [5](#0-4) 

### Likelihood Explanation
Exploitability depends on the same signer address/key owning the identical `slot_id` in at least two different StackerDB contracts simultaneously served by a node, which is a realistic and recurring scenario in the signer-set rotation design where the same signer keys are commonly assigned the same slot index across successive `.signers-*` contract generations. No secret key or privileged role is required by the attacker beyond observing a previously broadcast, validly signed chunk (which is gossiped in the clear) and re-POSTing it to the other contract's endpoint.

### Recommendation
Include the `QualifiedContractIdentifier` (or a stable numeric `stackerdb_id`) inside `SlotMetadata::auth_digest()` so that signatures are bound to the specific StackerDB instance they were produced for, analogous to including `chainId`/domain separator fields per EIP-712 best practice. This requires a wire-format/version bump since it changes what signers must sign over.

### Proof of Concept
1. Node hosts two StackerDB contracts, `SP...signer-msgs-cycle-10` and `SP...signer-msgs-cycle-11`, where signer key `K` owns `slot_id = 3` in both (a realistic outcome of slot assignment mirroring the signer set order).
2. Signer `K` legitimately signs and pushes chunk `(slot_id=3, slot_version=5, data=D)` to `cycle-10`'s DB; this is gossiped/relayed and observable by any peer.
3. Attacker (no key required) replays the exact same `(slot_id=3, slot_version=5, sig, data=D)` via `POST /v2/stackerdb/.../signer-msgs-cycle-11/chunks`.
4. `try_replace_chunk` calls `get_slot_validation` for `cycle-11`, finds `K` as the expected signer for slot 3, and `slot_desc.verify(&K)` succeeds because `auth_digest()` only hashes `slot_id`, `slot_version`, `data_hash` — none of which differ between the two contracts.
5. The chunk is accepted into `cycle-11`'s StackerDB and relayed network-wide via `StackerDBPushChunk`, even though `K` never authorized this data for `cycle-11`.

    /// data_hash.  Sets self.signature to the signature.
    /// Fails if the underlying crypto library fails
    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
