### Title
Unvalidated `http_authorization_header` RPC field is injected verbatim into Git's `http.<url>.extraHeader` config, enabling HTTP header/request injection toward remote and mirror endpoints - (File: internal/gitaly/service/repository/fetch_remote.go)

### Summary
`FetchRemoteRequest.RemoteParams.HttpAuthorizationHeader`, `UpdateRemoteMirrorRequest.Remote.HttpAuthorizationHeader`, and `FindRemoteRootRefRequest.HttpAuthorizationHeader` are RPC fields under the caller's control. All three call sites concatenate this value directly into an `Authorization: ` HTTP header value and inject it into Git's per-URL `http.<url>.extraHeader` configuration without ever checking for CR/LF or other control characters, mirroring the CGI header-injection bug class in the linked report (unsanitized external value placed straight into an HTTP header).

### Finding Description
In three separate RPC handlers the pattern is identical: the value returned by `req.GetRemoteParams().GetHttpAuthorizationHeader()` (or the equivalent getter) is used to build a Git config value with no sanitization: [1](#0-0) 

The same unsanitized construction appears in the mirror-push path: [2](#0-1) 

and in the root-ref discovery path: [3](#0-2) 

The resulting `ConfigPair{Key: "http.<url>.extraHeader", Value: "Authorization: " + authHeader}` is passed through `WithConfigEnv`, which serializes it as raw `GIT_CONFIG_KEY_N` / `GIT_CONFIG_VALUE_N` environment variables: [4](#0-3) 

Because these are plain environment-variable strings (not shell-escaped, not filtered), an attacker-controlled `http_authorization_header` value containing `\r\n` becomes part of the literal Git config value that Git's HTTP transport later feeds to libcurl as an "extra header" for every request sent to the attacker-influenced/remote URL. Nowhere along this path — request validation (`validateFetchRemoteRequest`), the proto definitions, or `GitConfig.Validate()` (which only validates admin-configured `config.toml` entries, not these dynamically built RPC-derived pairs) — is the header value checked for embedded CR/LF or other control bytes: [5](#0-4) 

This is structurally the same root cause as the reported Ruby CGI issue: a value received from an external/less-trusted source is spliced directly into an HTTP header without stripping CR/LF, allowing the header to be terminated early and additional header lines (or, depending on curl/Git version behavior, request content) to be injected into the outgoing HTTP request that Gitaly makes to the remote/mirror endpoint.

### Impact Explanation
If the underlying libcurl/Git build does not itself reject header values containing embedded CR/LF, an attacker who can set `http_authorization_header` on a `FetchRemote`, `UpdateRemoteMirror`, or `FindRemoteRootRef` RPC can inject arbitrary additional HTTP headers (or split the request) into the outbound request Gitaly issues toward the configured remote URL. This can be used to smuggle extra headers to a backend HTTP proxy/load balancer sitting between Gitaly and the "remote" target (e.g., to manipulate routing, spoof headers such as `Host`, or exfiltrate/replace credentials sent to that endpoint), which falls into the accepted "argument/config injection" / "credential disclosure" impact categories for this analog scan.

### Likelihood Explanation
Exploitability is contingent on the version of libcurl/Git in use — modern curl builds reject `CURLOPT_HTTPHEADER` values containing embedded CR/LF as a defense added specifically against this bug class, which would neutralize the practical exploitation in current deployments. However, the Gitaly code itself performs no defense-in-depth validation of this RPC-controlled field, so likelihood depends entirely on the transport library's own protections rather than on any check in Gitaly.

### Recommendation
Reject (or strip) any `http_authorization_header` value containing `\r`, `\n`, or other control characters before it is used to build the `http.<url>.extraHeader` Git config value, at `validateFetchRemoteRequest` and the equivalent validation points for `UpdateRemoteMirror` and `FindRemoteRootRef`. This restores defense-in-depth independent of the underlying HTTP client library's own CRLF protections.

### Proof of Concept
1. Issue a `FetchRemote` RPC with `RemoteParams.Url` pointing to an HTTP endpoint controlled/observed by the tester and `RemoteParams.HttpAuthorizationHeader` set to `token\r\nX-Injected: evil`.
2. Observe the environment passed to the spawned `git fetch` process: `GIT_CONFIG_VALUE_N` will contain the literal string `Authorization: token\r\nX-Injected: evil` (verifiable via the existing test pattern in `create_repository_from_url_test.go` `TestServer_CloneFromURLCommand`, which already asserts the raw environment content of the config value).
3. On a Git/libcurl build that does not filter embedded CR/LF from header values, the observing HTTP server will see an extra `X-Injected: evil` header (or a malformed/split request) in the request Gitaly sends. [6](#0-5)

// ConfigPairsToGitEnvironment converts the given config pairs into a set of environment variables
// that can be injected into a Git executable.
func ConfigPairsToGitEnvironment(configPairs []ConfigPair) []string {
	env := make([]string, 0, len(configPairs)*2+1)

	for i, configPair := range configPairs {
		env = append(env,
			fmt.Sprintf("GIT_CONFIG_KEY_%d=%s", i, configPair.Key),
			fmt.Sprintf("GIT_CONFIG_VALUE_%d=%s", i, configPair.Value),
		)
	}

	return append(env, fmt.Sprintf("GIT_CONFIG_COUNT=%d", len(configPairs)))
}

		)

}
