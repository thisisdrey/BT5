### Title
Cross-StackerDB chunk signature replay due to missing `contract_id` in signed digest — forged-context chunks pass authentication and propagate network-wide - ([File: libstackerdb/src/libstackerdb.rs])

### Summary
`SlotMetadata::auth_digest()` binds a signer's signature only to `(slot_id, slot_version, data_hash)` and never to the target StackerDB smart-contract identifier. Because slot ownership (which principal owns a given `slot_id`) is frequently identical across multiple distinct StackerDB contracts belonging to the same signer set, a chunk that a signer legitimately authored and signed for one StackerDB contract can be replayed byte-for-byte by any unprivileged relayer into a *different* StackerDB contract's identical slot/version, where it will pass signature verification, get stored, and be gossiped network-wide — exactly mirroring the reported bug class of "a storage/authentication key that omits a discriminator field, allowing data legitimately produced for one logical context to silently satisfy a check in another."

### Finding Description
`SlotMetadata::auth_digest` computes the signed digest as: [1](#0-0) 

This digest — and therefore the signature that authenticates a chunk write — covers only `slot_id`, `slot_version`, and `data_hash`. It never includes the `QualifiedContractIdentifier` of the StackerDB the chunk is destined for. `StackerDBChunkData`'s own doc comment confirms the intended scope: "signature from the stacker over (slot id, slot version, chunk sha512/256)": [2](#0-1) 

`verify()` recovers the pubkey from this contract-agnostic digest and only checks it against whichever address the *target* replica's local config says owns that slot in that contract: [3](#0-2) 

The write path (`StackerDBTx::try_replace_chunk`) authenticates purely via this contract-agnostic `verify()` call against the per-contract slot owner and never checks that the chunk was actually signed "for" this contract: [4](#0-3) 

The same pattern repeats in the P2P chunk-validation path used both for downloaded chunks and for unsolicited pushed chunks: [5](#0-4) 

Critically, slot ownership is *not* independent per contract for the signer-message StackerDBs. The three per-reward-cycle lanes (`signers-<set>-1` = BlockResponse, `signers-<set>-2` = StateMachineUpdate, `signers-<set>-3` = BlockPreCommit) all derive their `(slot_id → signer)` assignment from the very same underlying page data exposed by the shared `.signers` boot contract: [6](#0-5) 

so a given signer occupies the identical `slot_id` in all three contracts for a given signer-set parity. Consequently, a chunk `(slot_id=K, slot_version=V, data, sig)` that signer S legitimately produced and signed for contract A (e.g. `signers-0-3`, BlockPreCommit) is a byte-identical, signature-valid chunk for contract B (e.g. `signers-0-2`, StateMachineUpdate) at the same `(K, V)`, because `verify()` never binds the signature to a specific contract.

Only the *downstream* consumer of `StackerDBChunksEvent` (in `libsigner`) additionally filters by payload-type-byte vs. expected lane: [7](#0-6) 

but this filter runs only in the signer/node event-dispatch consumer, not in the StackerDB storage or P2P replication layer itself. The raw StackerDB write path (`poststackerdbchunk.rs` → `try_replace_chunk`) and P2P gossip path (`handle_unsolicited_StackerDBPushChunk` → `validate_received_chunk`) will accept, store, and propagate the replayed chunk into the wrong contract regardless of that later filter: [8](#0-7) [9](#0-8) 

### Impact Explanation
An unprivileged network peer (not even the signer whose signature is reused) can take a chunk observed on one StackerDB replica/contract and re-POST it, unmodified, to a *different* StackerDB contract where the same principal owns the same slot. This chunk will pass `SlotMetadata::verify()` (Critical: unauthenticated write to state, since the poster need not possess any private key) and be durably stored, bumping the slot's Lamport version and overwriting/blocking legitimate future writes from the real slot owner to that contract (the real chunk is now "stale" relative to the replayed version). It will then be advertised via `StackerDBChunkInv` and pushed to every other replica that syncs that contract, i.e., network-wide propagation of forged (out-of-context) data through the p2p StackerDB replication mechanism. This satisfies the Critical bar ("unauthenticated/unauthorized write to state or StackerDB" and "network-wide propagation of forged data").

### Likelihood Explanation
Exploitation requires no privileged role, no secret key, and no race condition: any node that has previously observed a signer's chunk in one contract (trivial, since chunks are broadcast/downloadable) can immediately replay it into any other StackerDB contract where the same address currently owns the same `slot_id` — a condition that holds by construction for the three per-signer-set message lanes sharing one underlying slot assignment. The only requirement is that the `slot_version` at the target slot in the target contract be lower than the replayed version, which is the normal steady state.

### Recommendation
Bind the signed digest to the specific StackerDB instance. Include the `QualifiedContractIdentifier` (or a stable per-contract StackerDB ID) in `SlotMetadata::auth_digest()`, e.g.:
```rust
fn auth_digest(&self, contract_id: &QualifiedContractIdentifier) -> Sha512Trunc256Sum {
    let mut hasher = Sha512_256::new();
    hasher.update(contract_id.to_string().as_bytes());
    hasher.update(self.slot_id.to_be_bytes());
    hasher.update(self.slot_version.to_be_bytes());
    hasher.update(self.data_hash.0);
    Sha512Trunc256Sum::from_hasher(hasher)
}
```
and thread the contract identifier through `sign()`/`verify()` call sites in `try_replace_chunk`, `validate_received_chunk`, and every other verifier so a signature is only valid for the StackerDB it was produced for.

### Proof of Concept
1. Reward cycle N, signer S is assigned `slot_id = K` in both `signers-0-2` (StateMachineUpdate) and `signers-0-3` (BlockPreCommit), per the shared `.signers` boot-contract slot list.
2. S legitimately signs and posts a `BlockPreCommit` chunk `(slot_id=K, slot_version=V, data=D, sig=SIG)` to `signers-0-3`. `SIG` is computed only over `(K, V, hash(D))` — see `auth_digest`.
3. Attacker (any peer, no keys needed) observes this chunk and constructs an identical `StackerDBChunkData{slot_id: K, slot_version: V, sig: SIG, data: D}` POST to `signers-0-2` via `/v2/stackerdb/{principal}/{contract_name}/chunks`.
4. `try_replace_chunk` looks up the slot-owner for `signers-0-2` slot `K` (same address as S), calls `slot_desc.verify(&signer_addr)`, which recomputes the same contract-agnostic digest and succeeds.
5. The forged chunk is stored in `signers-0-2` and gossiped via `StackerDBChunkInv`/`handle_unsolicited_StackerDBPushChunk` to all peers replicating that contract, even though S never intended or authorized this data for the StateMachineUpdate lane.
