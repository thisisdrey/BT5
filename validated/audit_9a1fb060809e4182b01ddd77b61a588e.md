Audit Report

## Title
Permissionless asset creator can freeze an AMM pool account in `pallet-asset-conversion`, permanently locking LP funds - (File: `substrate/frame/asset-conversion/src/lib.rs`)

## Summary
`do_create_pool` in `substrate/frame/asset-conversion/src/lib.rs` accepts any `T::AssetKind` as poolable without validating who controls that asset's `freezer`/`admin` role, and `T::Assets::touch` creates a live `Account<T,I>` entry for the pool account for that asset. Since `pallet-assets::create` (`substrate/frame/assets/src/lib.rs` L843-889) is reachable by any signed account under a `CreateOrigin = AsEnsureOriginWithArg<EnsureSigned<AccountId>>` configuration (as seen on Asset Hub for `TrustBackedAssetsInstance`), the creator becomes `freezer` and can later call `pallet-assets::freeze` (L1192-1216) on the pool account, permanently blocking any `T::Assets::transfer` out of the pool for that asset.

## Finding Description
`Pallet::create` lets the caller become `owner`/`issuer`/`admin`/`freezer` of a newly minted asset class [1](#0-0) . `do_create_pool` builds a pool for arbitrary `asset1`/`asset2` and calls `T::Assets::touch` for the pool account without checking either asset's freezer/admin role, giving the pool account a live `Account<T,I>` entry that satisfies the precondition for freezing [2](#0-1) . The asset's `freezer` can then call `freeze` on the pool account, which is gated only by `origin == d.freezer` and mutates `AccountStatus::Frozen` on that specific account [3](#0-2) .

`do_remove_liquidity` burns the LP token first, then attempts to transfer both `asset1` and `asset2` out of `pool_account` in sequence [4](#0-3) . `can_decrease` (invoked internally by `transfer`) checks `account.status.is_frozen()` and returns `Frozen` before any balance movement, and this check occurs strictly after the asset-level frozen/destroying checks but before any balance change [5](#0-4) . Because Substrate dispatch is atomic per extrinsic, a `Frozen` error on the second transfer reverts the entire call including the LP-token burn — so no partial state change occurs, but the extrinsic can never complete successfully while the frozen status persists. Swaps that route through the frozen asset held by `pool_account` fail identically. The only way to lift the freeze is `thaw`, gated to `origin == d.admin` — the same attacker who created the asset — giving the attacker unilateral, permanent control over whether liquidity providers can ever exit the pool.

I could not fully verify within the available context whether `T::Assets` for `pallet-asset-conversion` on Asset Hub runtimes is wired directly to `pallet-assets` or to a `fungible`/`fungibles` union type that includes the native `Balances` pallet; the grep for the `pallet_asset_conversion::Config for Runtime` impl in `asset-hub-rococo` returned matches but I was unable to retrieve the surrounding config lines before running out of iterations. This does not change the core vulnerability (it clearly applies to any `T::AssetKind` backed by `pallet-assets`, e.g. two `pallet-assets`-created tokens, or an asset paired with a trust-backed asset), but I cannot confirm from this session whether the specific "attacker token vs. native token" pairing scenario described in the claim is reachable on a given deployed runtime without that confirmation.

## Impact Explanation
This matches the "permanent user-fund lock" impact class: liquidity providers who deposit into a pool containing an externally-controlled, freezable asset can have their entire pool share (both assets, since both transfers happen in the same atomic call) permanently locked once the asset's freezer exercises the `freeze` extrinsic, with only the attacker able to `thaw` it. It also constitutes a permanent DoS on that trading pair since neither swaps nor liquidity removal can complete.

## Likelihood Explanation
High. `pallet-assets::create` and `pallet-asset-conversion`'s pool-creation/liquidity-addition calls are permissionless, public-origin dispatchables under the commonly configured `CreateOrigin = AsEnsureOriginWithArg<EnsureSigned<AccountId>>` [6](#0-5) . No governance, validator, or privileged access is needed — only the ability to create an asset, create/seed a pool, and lure at least one other LP into providing liquidity.

## Recommendation
- Reject pool creation/liquidity provisioning when an asset's `freezer`/`admin` is not root/governance-controlled, or require the pool pallet itself to be registered as the sole freezer authority for pool accounts.
- Alternatively, implement pool-account-specific immunity to third-party `freeze` calls (e.g. via a custom `FrozenBalance` check or a runtime-level allowlist of poolable assets).

## Proof of Concept
1. Attacker calls `pallet_assets::create` to become `owner`/`issuer`/`admin`/`freezer` of asset `X` (`substrate/frame/assets/src/lib.rs` L843-889).
2. Attacker creates a pool pairing `X` with a valuable asset and seeds it via `add_liquidity`, causing `T::Assets::touch` to create a live `Account` entry for `X` at `pool_account` (`substrate/frame/asset-conversion/src/lib.rs` L729-770).
3. A victim LP adds liquidity to the same pool.
4. Attacker calls `pallet_assets::freeze(id=X, who=pool_account)` (`substrate/frame/assets/src/lib.rs` L1192-1216).
5. Any subsequent `remove_liquidity` or swap touching `X` at `pool_account` fails with `Error::<T>::Frozen` inside `can_decrease` (`substrate/frame/assets/src/functions.rs` L199-205), reverting the whole extrinsic; only the attacker's `thaw` call can unblock it.

			creator: &T::AccountId,
			asset1: T::AssetKind,
			asset2: T::AssetKind,
			initial_fee: Option<Permill>,
		) -> Result<T::PoolId, DispatchError> {
			ensure!(asset1 != asset2, Error::<T>::InvalidAssetPair);
			if let Some(fee) = initial_fee {
				ensure!(fee <= T::MaxSwapFee::get(), Error::<T>::FeeTooHigh);
			}

			// prepare pool_id
			let pool_id = T::PoolLocator::pool_id(&asset1, &asset2)
				.map_err(|_| Error::<T>::InvalidAssetPair)?;
			ensure!(!Pools::<T>::contains_key(&pool_id), Error::<T>::PoolExists);

			let pool_account =
				T::PoolLocator::address(&pool_id).map_err(|_| Error::<T>::InvalidAssetPair)?;

			// pay the setup fee
			let fee =
				Self::withdraw(T::PoolSetupFeeAsset::get(), creator, T::PoolSetupFee::get(), true)?;
			T::PoolSetupFeeTarget::on_unbalanced(fee);

			if T::Assets::should_touch(asset1.clone(), &pool_account) {
				T::Assets::touch(asset1.clone(), &pool_account, creator)?
			};

			if T::Assets::should_touch(asset2.clone(), &pool_account) {
				T::Assets::touch(asset2.clone(), &pool_account, creator)?
			};

			let lp_token = NextPoolAssetId::<T>::get()
				.or(T::PoolAssetId::initial_value())
				.ok_or(Error::<T>::IncorrectPoolAssetId)?;
			let next_lp_token_id = lp_token.increment().ok_or(Error::<T>::IncorrectPoolAssetId)?;
			NextPoolAssetId::<T>::set(Some(next_lp_token_id));

			T::PoolAssets::create(lp_token.clone(), pool_account.clone(), false, 1u32.into())?;
			if T::PoolAssets::should_touch(lp_token.clone(), &pool_account) {
				T::PoolAssets::touch(lp_token.clone(), &pool_account, creator)?
			};
