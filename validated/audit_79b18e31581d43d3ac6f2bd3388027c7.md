### Title
Insufficient host validation in `use_netrc` credential matching allows userinfo-based host confusion - (File: tools/build_defs/repo/utils.bzl)

### Summary
`use_netrc`, the Starlark helper used by `http_archive`/`http_file`/`http_jar` (via `get_auth`) to attach netrc-derived Basic-auth/pattern credentials to download URLs, derives the "host" for credential lookup using naive string splitting instead of standards-compliant URI parsing. This mirrors the Mastodon bug class: a validating component (credential-host matcher) and a consuming component (the actual HTTP client that performs the connection) can disagree on how the same string should be interpreted, letting an attacker-chosen string smuggle a different meaning past the check that is supposed to gate it.

### Finding Description
`use_netrc` computes the host to match against netrc entries like this: [1](#0-0) 

It splits on `"://"`, then on `"/"`, then on `":"`, but never accounts for a userinfo component (`user:pass@host`) that is legal in a URL per RFC 3986. A crafted URL such as `http://trusted-host.example:@attacker.example/payload` yields, under this logic, `schemerest[1] = "trusted-host.example:@attacker.example/payload"`, then `.split("/")[0] = "trusted-host.example:@attacker.example"`, then `.split(":")[0] = "trusted-host.example"` — matching a netrc entry for `trusted-host.example` even though, under standard URL semantics, `attacker.example` is the actual host that the connection is made to (the part after `@`), with `trusted-host.example:` merely being userinfo. This causes the netrc-derived credentials for `trusted-host.example` to be selected and attached (as `type: "basic"` or pattern-based `Authorization` header, per lines 465-490) to a request whose real destination is `attacker.example`, i.e. the string used to gate the credential ("does this host match one I have credentials for?") is parsed differently than the string later used to route the actual network request.

This URL string need not originate from a trusted root-repo file: `urls`/mirror lists can come from repository-rule callers, including Bzlmod module extensions that build `http_archive` invocations from registry-provided `source.json` data. A hostile or compromised registry that a user has configured (an unprivileged, remote party from the user's build's perspective) can supply such a URL as one of the mirror URLs for a module.

### Impact Explanation
If a user's netrc file contains credentials for a legitimate, trusted host (e.g. an internal artifact server, GitHub token host, cloud storage host), any code path that lets an external party influence a download URL string (mirror lists, module registry `source.json`, or any repository rule taking user-influenced URLs and calling `use_netrc`/`get_auth`) can redirect those credentials to an attacker-controlled host via the userinfo trick, resulting in **credential exfiltration to an attacker-controlled host**.

### Likelihood Explanation
Requires: (1) the victim has netrc credentials configured for some host that an attacker knows or guesses (common for corporate registries or common cloud hosts), and (2) an attacker who controls a URL string consumed by the build (e.g., a hostile/compromised registry providing mirror URLs, or any repo rule wrapper that forwards externally-influenced URLs into `use_netrc`). This is a plausible but not universal precondition, and requires the actual downstream HTTP client (the Java-side downloader, e.g. `HttpDownloader`) to parse the same URL string with standard userinfo semantics, separating `user:pass@` from the real host — I was unable to fully verify this Java-side parsing behavior within the available investigation budget, so the exact host-confusion outcome on the network layer is not conclusively confirmed here, only the Starlark-side host-matching flaw itself.

### Recommendation
Replace the manual `split("://")/split("/")/split(":")` host extraction in `use_netrc` with parsing via a proper URL/URI abstraction that correctly separates scheme, userinfo, host, and port, and explicitly reject or strip userinfo components before matching against netrc entries, to ensure the host used for credential-matching is identical to the host actually contacted.

### Proof of Concept
A `src/test/shell/bazel/starlark_repository_test.sh`-style test (following the existing `test_use_netrc` pattern at lines 1619+ referenced above) could add a `.netrc` entry for `trusted-host.example`, then call `use_netrc` with the URL `http://trusted-host.example:@attacker.example/payload`, and assert that the resulting `auth` dict either (a) incorrectly attaches `trusted-host.example`'s credentials to a URL whose real host is `attacker.example`, or (b) that no such mismatch occurs — confirming or refuting the exploitability once the downstream HTTP client's exact host-resolution semantics for the same string are also verified: [2](#0-1)
