### Title
Unguarded `assert`/`BigInteger` divide-by-zero in `RepositoryImpl.calculateGlobalEnergyLimit` reachable from a plain TriggerSmartContract call - (File: `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java`)

### Summary
`RepositoryImpl.calculateGlobalEnergyLimit()`, which is invoked on every TVM contract call to size the caller's/creator's energy allowance, relies on an unenforced `assert totalEnergyWeight > 0;` and then unconditionally divides by `totalEnergyWeight` when the "hardened" (`BigInteger`) resource-calculation path is enabled. Unlike the parallel implementation in `chainbase/EnergyProcessor.calculateGlobalEnergyLimit`, it has **no early-return guard** for `totalEnergyWeight <= 0`. If `totalEnergyWeight` is ever zero while an account still reports non-zero `getAllFrozenBalanceForEnergy()` (a state reachable through the delay/undelegate/unfreeze bookkeeping), this method throws an uncaught `ArithmeticException` ("BigInteger divide by zero") from inside the smart-contract call path, which — unlike the `create()` code path — is **not wrapped in a try/catch** in `VMActuator.call()`.

### Finding Description
`RepositoryImpl.calculateGlobalEnergyLimit`: [1](#0-0) 

Compare with the guarded sibling implementation in `EnergyProcessor`, which explicitly returns `0` when `totalEnergyWeight <= 0` before reaching the `assert`: [2](#0-1) 

`RepositoryImpl`'s version skips that guard entirely — it always falls through to `assert totalEnergyWeight > 0;` (a no-op in production JVMs that run without `-ea`) and then, when `VMConfig.allowHardenResourceCalculation()` is true, executes `BigInteger.valueOf(totalEnergyWeight)` as a divisor with no zero check, throwing `ArithmeticException` if `totalEnergyWeight == 0`.

This method is reached from `VMActuator.getAccountEnergyLimitWithFloatRatio()` on every TVM `call()` (trigger a smart contract) when the caller/creator account has a non-zero frozen-for-energy balance: [3](#0-2) 

Critically, `call()` computes the energy limit (`getTotalEnergyLimit(...)` → `getAccountEnergyLimitWithFloatRatio` → `calculateGlobalEnergyLimit`) with **no surrounding try/catch**: [4](#0-3) 

whereas the parallel `create()` path wraps the equivalent logic in `try { ... } catch (Exception e) { throw new ContractValidateException(e.getMessage()); }`, converting any such exception into a normal transaction-validation failure rather than an uncaught runtime error: [5](#0-4) 

This is directly analogous to the TensorFlow CHECK-fail bug class in the report: an internal invariant (`totalEnergyWeight > 0`) is enforced only by a disabled/no-op `assert`, and the code that depends on that invariant (a `BigInteger` division) is exercised on a call path that lacks defensive validation of the precondition, exposed to a value (`totalEnergyWeight`) that is influenced by ordinary, unprivileged account operations (freeze/unfreeze/delegate energy).

### Impact Explanation
An uncaught `ArithmeticException` thrown from deep inside `VMActuator.call()`/`RepositoryImpl` during smart-contract-call execution propagates as a `RuntimeException` out of the actuator's `execute()`/`validate()` flow instead of being converted into a `ContractValidateException`/`ContractExeException` the way the rest of the transaction-processing pipeline expects. Depending on how far up the call stack this propagates during block application, this can abort processing of that transaction/block in an unexpected way (a denial-of-service against the affected node, consistent with the "node crash or halt" impact category called for in the validation rules). This is reachable by any unprivileged account simply calling a deployed smart contract — no special privileges, malicious SR/witness role, or node compromise required.

### Likelihood Explanation
The likelihood hinges on whether `totalEnergyWeight == 0` while some account's `getAllFrozenBalanceForEnergy()` is still non-zero is actually reachable in a live chain state, and I was not able to fully trace every code path that updates `totalEnergyWeight` (freeze/unfreeze/delegate/undelegate energy actuators) within the available time to give a concrete transaction sequence that forces this exact state. What is concretely verified is: (1) the missing zero-guard in `RepositoryImpl.calculateGlobalEnergyLimit` compared to its sibling in `EnergyProcessor`, (2) the fact that `assert` is a no-op without `-ea` (confirmed by the absence of `-ea` in the production run configuration — only present in test config), and (3) that `VMActuator.call()`'s energy-limit computation, unlike `create()`, is not defensively wrapped. Given this uncertainty about full reachability of the zero-weight precondition, this should be treated as a **credible but not fully proven** DoS analog — I recommend validating the exact state transitions (freeze/unfreeze/delegate energy sequences, including `UnfreezeBalanceV2`'s delayed-withdrawal accounting) that can drive `totalEnergyWeight` to zero while `getAllFrozenBalanceForEnergy()` remains non-zero for some account, ideally with a Devin session that can run the full chainbase/actuator test suite and reproduce it end-to-end.

### Recommendation
Add the same `totalEnergyWeight <= 0` early-return guard to `RepositoryImpl.calculateGlobalEnergyLimit` that already exists in `EnergyProcessor.calculateGlobalEnergyLimit`, removing reliance on the no-op `assert` for correctness. Additionally, wrap the energy-limit computation in `VMActuator.call()` in a try/catch that converts unexpected `RuntimeException`s into `ContractValidateException`/`ContractExeException`, mirroring the defensive handling already present in `VMActuator.create()`.

### Proof of Concept
Not fully constructed — this requires reproducing a chain state where `DynamicPropertiesStore.getTotalEnergyWeight() == 0` while an account used as caller/creator in a `TriggerSmartContract` transaction still has non-zero `AccountCapsule.getAllFrozenBalanceForEnergy()`, with `VMConfig.allowHardenResourceCalculation()` enabled. The existing test `CalculateGlobalLimitHardenTest`/`RepositoryImplHardenTest` exercise the "hardened" `BigInteger` division path and already demonstrate `ArithmeticException` being thrown under overflow/degenerate inputs to this same code family: [6](#0-5) 
A full PoC would additionally need to demonstrate the freeze/unfreeze/delegate sequence that drives `totalEnergyWeight` to `0` in that state, then issue a `TriggerSmartContract` transaction from the affected account to hit `VMActuator.call()`'s unguarded path.

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalEnergyLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }

    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
    long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
      return 0;
    } else {
      assert totalEnergyWeight > 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
