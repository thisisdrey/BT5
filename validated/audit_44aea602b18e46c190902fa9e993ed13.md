## Finding

### Title
Git submodule fetch in `git_repository`/`new_git_repository` force-allows the `file://` transport, letting a malicious pinned commit read arbitrary local Git repositories on the build machine - (File: `tools/build_defs/repo/git_worker.bzl`)

### Summary
`tools/build_defs/repo/git_worker.bzl` implements the fetch logic behind the `git_repository`/`new_git_repository` Starlark repository rules. When `init_submodules` or `recursive_init_submodules` is set, it unconditionally overrides Git's own submodule-protocol safety check: [1](#0-0) 

by passing `-c protocol.file.allow=always` to `git submodule update`. This is the exact same bug class as the GitPython advisory: an external, attacker-influenced string (here, a submodule URL taken from `.gitmodules` inside a fetched Git tree) is fed into a `git` subcommand without the sanitization that upstream Git itself intentionally added as a fix for this bug class (CVE-2022-39253, "submodule can use file:// to read local files"), and Bazel deliberately re-enables the disabled behavior.

### Finding Description
`git_repo()` drives cloning: it initializes a bare repo, adds the user-declared `remote`, fetches the `fetch_ref`, resets to `reset_ref`, and — if `init_submodules`/`recursive_init_submodules` is set — calls `update_submodules()`: [2](#0-1) 

`update_submodules()` runs:

```
git -c protocol.file.allow=always submodule update --init [--recursive] --checkout --force
``` [1](#0-0) 

Git ships with `protocol.file.allow` and `protocol.ext.allow` defaulting to `user`, which blocks the `file://` and `ext::` transports when the URL comes from data inside a fetched repository (e.g., `.gitmodules`) rather than being typed directly by the operator — precisely to stop a hostile repository from causing local file disclosure or command execution during recursive submodule fetch. Bazel's `_execute()` passes this override as a Git config flag on every submodule-update invocation, with no scheme allow-list or validation of the submodule URLs beforehand: [3](#0-2) 

Because `.gitmodules` is ordinary tracked content, this data is fully controlled by whoever authored the commit that `git_repository` points to. `git_repository`'s `commit` attribute pins the *outer* repository's content by hash — but that hash equally certifies whatever malicious `.gitmodules` entries the outside author (an "outsider who publishes content a victim's build consumes") placed in that same commit. Nothing in `git.bzl`/`git_worker.bzl` inspects or restricts the submodule URL scheme before or after this override is applied: [4](#0-3) 

The only mitigation note in the code is a comment referencing a *different* problem (allowing local submodule clones needed for issue #17040), not an assessment of the security regression it reintroduces.

### Impact Explanation
An outsider who publishes a Git repository/tag/commit that a victim's `git_repository(..., init_submodules = True)` or `new_git_repository(..., recursive_init_submodules = True)` rule fetches can embed a `.gitmodules` entry with a `file://` URL pointing at an arbitrary path on the victim's build machine (e.g. another checked-out repository, a CI runner's cache of a private repo, or another output base containing embedded credentials in its `.git` history). During `bazel fetch`/`bazel build`, Git will clone that local path into the workspace despite Git's own default protection being designed to prevent exactly this, because Bazel forces `protocol.file.allow=always`. This is a read outside the intended repository/exec-root boundary and a confidentiality bypass, matching the "insufficient sanitization of a repository-supplied URL fed to a `git` subcommand" bug class from the GitPython advisory.

### Likelihood Explanation
Any project using `git_repository`/`new_git_repository` with `init_submodules`/`recursive_init_submodules` enabled (a documented, commonly-used feature) and depending on a third-party Git repository is exposed. No special privileges are required by the attacker beyond authoring/controlling the content of the pinned commit (e.g. maintaining an open-source dependency, or a malicious fork/branch a victim is convinced to point at). The override is unconditional and always applied — there is no flag to opt out.

### Recommendation
Do not blanket-override `protocol.file.allow` (and avoid ever setting `protocol.ext.allow`) to `always` for submodule updates. Instead, restrict allowed submodule protocols to the safe network transports actually needed (e.g. `https`, `ssh`, `git`), or make the override opt-in per-repository-rule invocation with an explicit attribute (defaulting to Git's safe default), and document the risk of enabling it against untrusted repositories.

### Proof of Concept
1. Attacker maintains/publishes `attacker/repo` with a commit whose `.gitmodules` contains:
   ```
   [submodule "leak"]
     path = leak
     url = file:///home/victim/.ssh_backup_repo
   ```
   (`/home/victim/.ssh_backup_repo` being any local bare/worktree Git repo reachable by the build user, e.g. left over from another checkout or CI cache.)
2. Victim's `MODULE.bazel`/`WORKSPACE` declares:
   ```
   git_repository(
       name = "dep",
       remote = "https://example.com/attacker/repo.git",
       commit = "<pinned malicious commit>",
       recursive_init_submodules = True,
   )
   ```
3. On `bazel fetch @dep`, `git_repo()` → `update_submodules()` runs `git -c protocol.file.allow=always submodule update --init --recursive ...`, which clones `/home/victim/.ssh_backup_repo` into the external repo's `leak/` directory, materializing its contents where subsequent build steps (or the attacker's own `BUILD.bazel`/`patch_cmds` bundled in the same repo) can read and exfiltrate them — a JUnit/`src/test/shell/bazel` test can assert that after fetch, `leak/` contains files that originated outside the declared repository/exec root, confirming the containment breach without needing `--depth`/`shallow_since` or the `remote` attribute itself to be attacker-controlled.
