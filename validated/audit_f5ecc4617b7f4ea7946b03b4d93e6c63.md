### Title
Unauthorized theft of victim collateral during receivership — `is_signer_authorized` grants any non-owner signer withdraw rights instead of requiring the designated `liquidation_receiver` - (File: `programs/marginfi/src/state/marginfi_account.rs`, `programs/marginfi/src/instructions/marginfi_account/withdraw.rs`)

### Summary
`is_signer_authorized` authorizes *any* signer that is not the account's own `authority` to perform withdraw/repay/etc. once `ACCOUNT_IN_RECEIVERSHIP` is set, without verifying that the signer matches `LiquidationRecord.liquidation_receiver`. Since `LendingAccountWithdraw` never even references the `LiquidationRecord` account, any unprivileged third party can call `lending_account_withdraw` on a victim account that is mid-receivership (started by a different, legitimate liquidator) and drain collateral to an attacker-controlled `destination_token_account`.

### Finding Description
The authorization primitive: [1](#0-0) 

shows that when `allow_receivership` is true and `ACCOUNT_IN_RECEIVERSHIP` is set, the function returns `marginfi_account.authority != signer` — i.e. **any key other than the frozen-out original owner** is treated as authorized. There is no comparison against `LiquidationRecord.liquidation_receiver` anywhere in this function.

`LendingAccountWithdraw`'s account constraints call exactly this function with `allow_receivership = true`: [2](#0-1) 

Critically, the `LendingAccountWithdraw` accounts struct has **no `liquidation_record` account at all**, so there is no mechanism to tie the withdraw call to the specific receiver that `StartLiquidation` designated: [3](#0-2) 

Once `StartLiquidation` sets `ACCOUNT_IN_RECEIVERSHIP` (persisted in account state across transactions), the health check inside `lending_account_withdraw` is skipped entirely for the duration of receivership: [4](#0-3) 

The only guard against zero-weight (isolated) assets exists, but any normal-weighted asset is fully withdrawable: [5](#0-4) 

Exploit flow:
1. A legitimate liquidator/receiver `X` calls `StartLiquidation` on victim account `V`, setting `ACCOUNT_IN_RECEIVERSHIP` and `LiquidationRecord.liquidation_receiver = X`.
2. Attacker `Y` (unprivileged, unrelated to the record) submits `lending_account_withdraw` with `authority = Y`, `marginfi_account = V`, and `destination_token_account` owned by `Y`.
3. `is_signer_authorized(&a, g.admin, Y, true, true)` returns `true` because `V.authority != Y` and `ACCOUNT_IN_RECEIVERSHIP` is set — no check that `Y == liquidation_record.liquidation_receiver`.
4. The instruction skips the health check (receivership branch) and transfers `V`'s collateral straight to `Y`, with no requirement that `Y` repay any of `V`'s debt.

Only `EndLiquidation`, gated by `has_one = liquidation_receiver` on `LiquidationRecord`, is properly restricted to the designated receiver: [6](#0-5) 

but that check occurs only at settlement time and does nothing to prevent `Y`'s theft, nor recover funds already withdrawn — it only prevents `X`'s own `end_liquidation` from succeeding if the account has been left in a worse state (`WorseHealthPostLiquidation`), potentially leaving `V` permanently stuck in receivership on top of the theft.

The developer-facing documentation confirms this is the actual implemented (not merely theoretical) behavior: "Receivership: If the account is in receivership and the operation allows it, any signer is authorized," matching the code exactly.

### Impact Explanation
This allows unprivileged theft of another user's collateral: any public caller can piggyback on an in-progress receivership started by someone else and withdraw the victim's assets to their own token account without repaying any liability, without health enforcement, and without being the designated `liquidation_receiver`. This can also cause the legitimate liquidator's `EndLiquidation` to fail (health got worse), potentially locking the victim account in receivership indefinitely. This is real, unauthorized fund theft and unauthorized state change, squarely within scope (not a liquidity, oracle, Sybil, or DoS issue).

### Likelihood Explanation
Fully feasible and repeatable by any unprivileged actor: `StartLiquidation` state (`ACCOUNT_IN_RECEIVERSHIP`) is public and persists on-chain across transactions, so an attacker only needs to watch for accounts in receivership and race a `lending_account_withdraw` call with their own signer/destination before the legitimate receiver completes `EndLiquidation`. No special permissions, oracle manipulation, or admin access is required — just a normal signed transaction.

### Recommendation
`is_signer_authorized` (and any caller passing `allow_receivership = true`, including `lending_account_withdraw`, `lending_account_repay`, etc.) must verify the signer against the specific `LiquidationRecord.liquidation_receiver` for that account, not merely `signer != authority`. This requires either passing the `liquidation_record` account into `LendingAccountWithdraw`/`LendingAccountRepay` and checking `record.liquidation_receiver == signer`, or otherwise cryptographically binding the receivership-mode signer check to the receiver stored on the `LiquidationRecord` PDA.

Integration test plan (`programs/marginfi/tests/user_actions/`):
1. Create victim account `V`, deposit collateral, borrow to become unhealthy.
2. Liquidator `X` calls `start_liquidation` on `V`, setting receivership with `liquidation_record.liquidation_receiver = X`.
3. In a separate transaction, unrelated signer `Y` (never touched `V` before, not `liquidation_receiver`) calls `lending_account_withdraw` on `V` with `authority = Y` and `destination_token_account` owned by `Y`.
4. Assert the transaction **succeeds** and `Y`'s token balance increases by the withdrawn amount, and `V`'s collateral balance decreases correspondingly, proving unauthorized withdrawal by a non-receiver.
5. Optionally, have `X` subsequently call `end_liquidation` and assert it fails with `WorseHealthPostLiquidation`, demonstrating the account can be left permanently unresolved due to `Y`'s unauthorized withdrawal.

pub fn is_signer_authorized(
    marginfi_account: &MarginfiAccount,
    group_admin: Pubkey,
    signer: Pubkey,
    allow_receivership: bool,
    allow_order_execution: bool,
) -> bool {
    if allow_receivership && marginfi_account.get_flag(ACCOUNT_IN_RECEIVERSHIP) {
        return marginfi_account.authority != signer; // forbidden to take receivership of your own account
    }

    if allow_order_execution && marginfi_account.get_flag(ACCOUNT_IN_ORDER_EXECUTION) {
        return true;
    }

    if marginfi_account.get_flag(ACCOUNT_FROZEN) {
        return group_admin == signer;
    }

    marginfi_account.authority == signer
}
