### Title
Neighbor identity (PeerDB entry) keyed and overwritten by self-reported (unauthenticated) `addrbytes`/`port` in handshake payload, not the verified TCP peer address - (File: `stackslib/src/net/chat.rs`, `stackslib/src/net/neighbors/db.rs`, `stackslib/src/net/db.rs`)

### Summary
This is the closest reachable analog to the `blockBuilderBLSKeyToAddress[]` overwrite bug: an identity-mapping (in the Solidity report, BLS-key → address; here, `(network_id, addrbytes, port)` → public key in `PeerDB`) is written/overwritten using a value that the remote party fully controls and that is never checked against the value that actually authenticates the write (the real TCP peer address). I was not able to fully trace every call site to a concrete proof-of-concept before running out of iterations, so this should be treated as a partially-verified analog rather than a fully proven exploit chain.

### Finding Description
`PeerDB::insert_or_replace_peer` / `PeerDB::update_peer` (`stackslib/src/net/db.rs:1091-1134`, `1285-1334`) key a `Neighbor` record by `(network_id, addrbytes, port)` and store the peer's public key under that key, using `INSERT OR REPLACE` semantics — i.e., writing to an existing key silently overwrites the previous owner's public key and other fields: [1](#0-0) 

`Neighbor::load_and_update`/`NeighborKey::from_handshake` construct that lookup key from `handshake_data.addrbytes` and `handshake_data.port` — fields that are *self-reported by the remote peer inside the message payload*, not derived from the actual verified TCP socket address of the connection: [2](#0-1) 

`ConversationP2P::validate_handshake` only cross-checks the self-reported `addrbytes`/`port` against the real socket address for **outbound** connections that already have a known public key, and explicitly does *not* perform this check for inbound connections or for first-time handshakes: [3](#0-2) 

Additionally, in the neighbor-walk state machine, when accepting a `HandshakeAccept`/`StackerDBHandshakeAccept` from a peer we deliberately dialed to walk to its "neighbors of neighbors" (`handle_neighbor_handshake_accept`, `stackslib/src/net/neighbors/walk.rs:1092-1124`), the self-reported `data.handshake.addrbytes/port` is passed straight into `add_or_schedule_replace_neighbor` → `Neighbor::load_and_update` → `PeerDB::insert_or_replace_peer`, again without validating that this self-reported address matches the actual socket the reply came from: [4](#0-3) 

In the pingback-handshake path, `check_handshake_pubkey_hash` only verifies that the reported public key hashes to the expected `naddr.public_key_hash`; it does **not** verify that `data.handshake.addrbytes`/`port` matches `naddr`'s address before the same `add_or_schedule_replace_neighbor` write occurs: [5](#0-4) 

This mirrors the Solidity bug class exactly: the mapping's key (identity) is derived from attacker-supplied data at write time, and the write path (`INSERT OR REPLACE`) does not check whether the key already belongs to another, previously-registered owner before overwriting it — an equality between "claimed identity" and "verified identity" is never enforced at the write site.

### Impact Explanation
If exploitable end-to-end, an attacker-controlled node could cause a victim node to overwrite the `PeerDB` (frontier) record for a legitimate, previously-known peer's `(network_id, addrbytes, port)` slot with the attacker's own public key, by self-reporting that peer's address inside a `Handshake`/`HandshakeAccept` payload it sends to (or is asked about by) the victim. This would let the attacker impersonate the honest peer's frontier entry, potentially disrupting the victim's neighbor walk / connectivity to that legitimate peer and diverting future connection attempts or trust decisions keyed off `PeerDB` state. This falls under "High — steering a node off the tip via false inventory"/routing-adjacent impact if — and this is the key uncertainty — the write actually happens without the address being independently re-verified through an outbound connection attempt to that address (which the state machine does perform in some code paths, e.g. handshaking with "neighbors of neighbors" before saving them, which could mitigate the issue in practice).

### Likelihood Explanation
Reaching this requires only sending ordinary, correctly-signed P2P protocol messages (Handshake/HandshakeAccept) with an attacker-chosen `addrbytes`/`port` field — no special privilege, node secret, or third party's key is needed to author the message (the signature only needs to correspond to the attacker's own key, which is normal handshake behavior). However, I could not fully confirm within the remaining budget whether every write path (in particular the primary `handle_handshake` path and the neighbor-walk "neighbors-of-neighbors" path) actually persists the *self-reported* address without ever re-validating it against a real outbound connection to that address before commit — some of the surrounding code (e.g. the neighbor walk deliberately handshakes with newly discovered peers at their reported addresses, which provides an implicit, if weak, secondary check). This uncertainty affects how directly exploitable the finding is without further code tracing (in particular, tracing `handle_handshake_accept` in `chat.rs`, and how `GetNeighborsBegin`/`HandshakeFinish` in `walk.rs` actually dispatches outbound connections before calling `add_or_schedule_replace_neighbor`).

### Recommendation
Before writing/overwriting a `PeerDB` frontier entry keyed by `(network_id, addrbytes, port)`, cross-check that the self-reported handshake address matches an address the local node itself verified (i.e., the actual TCP peer address of an established, outbound connection to that specific `addrbytes:port`), for *all* code paths that call `Neighbor::save`/`Neighbor::save_update`/`PeerDB::insert_or_replace_peer` — not only for the outbound-with-known-key case currently handled in `validate_handshake`. If a self-reported address cannot be independently verified (e.g., NAT scenarios), such peers should be stored under a different, non-authoritative bucket that cannot silently overwrite an existing verified peer record, analogous to rejecting a `blockBuilderBLSKeyToAddress[key]` overwrite when the key is already populated by a different owner.

### Proof of Concept
Not fully constructed — this requires setting up two `TestPeer`s, having peer B legitimately known to the victim at `(network_id, IP_B, port_B)`, then having attacker peer A (dialed by, or replying to, the victim) send a `Handshake`/`HandshakeAccept` whose embedded `HandshakeData.addrbytes`/`port` fields are set to `IP_B:port_B` instead of A's own address, and observing whether `PeerDB::get_peer(network_id, IP_B, port_B)` on the victim now returns A's public key instead of B's. I was unable to trace far enough into `handle_handshake_accept` (`stackslib/src/net/chat.rs`) and the `HandshakeFinish`/`GetNeighborsBegin` transition in `stackslib/src/net/neighbors/walk.rs` to confirm this write occurs without an intervening address-verifying outbound connection, so this PoC is not confirmed and should be validated with a live test harness (e.g. `stackslib/src/net/tests/neighbors.rs`) before treating this as a fully proven vulnerability.

    /// Does a given handshakedata represent an expected public key hash?
    fn check_handshake_pubkey_hash(
        nk: &NeighborKey,
        data: &HandshakeAcceptData,
        naddr: &NeighborAddress,
    ) -> bool {
        let neighbor_pubkey_hash =
            Hash160::from_node_public_key_buffer(&data.handshake.node_public_key);
        if neighbor_pubkey_hash != naddr.public_key_hash {
            debug!(
                "Neighbor {:?} had an unexpected pubkey hash: expected {:?} != {:?}",
                nk, &naddr.public_key_hash, &neighbor_pubkey_hash
            );
            return false;
        }

        true
    }

    /// Finish up connecting to newly-discovered inbound peers
    pub fn pingback_handshakes_try_finish(
        &mut self,
        network: &mut PeerNetwork,
    ) -> Result<bool, net_error> {
        assert!(self.state == NeighborWalkState::PingbackHandshakesFinish);

        // see if we got any replies
        for (naddr, message) in self.comms.collect_replies(network).into_iter() {
            // if we got back a HandshakeAccept, and it's on the same chain as us, we're good!
            let (data, db_data) = match message.payload {
                StacksMessageType::HandshakeAccept(ref data) => {
                    debug!("{:?}: received HandshakeAccept from peer {:?}; now known to be routable from us", network.get_local_peer(), &message.to_neighbor_key(&data.handshake.addrbytes, data.handshake.port));
                    (data, None)
                }
                StacksMessageType::StackerDBHandshakeAccept(ref data, ref db_data) => {
                    debug!("{:?}: received StackerDBHandshakeAccept from peer {:?}; now known to be routable from us", network.get_local_peer(), &message.to_neighbor_key(&data.handshake.addrbytes, data.handshake.port));
                    (data, Some(db_data))
                }
                _ => {
                    let nkey = naddr.to_neighbor_key(network);
                    debug!(
                        "{:?}: Neighbor {:?} replied {:?} instead of pingback handshake",
                        network.get_local_peer(),
                        &nkey,
                        &message.get_message_name()
                    );
                    continue;
                }
            };

            let peer_nk = message.to_neighbor_key(&data.handshake.addrbytes, data.handshake.port);
            if !Self::check_handshake_pubkey_hash(&peer_nk, data, &naddr) {
                continue;
            }

            self.neighbor_db.add_or_schedule_replace_neighbor(
                network,
                &message.preamble,
                &data.handshake,
                db_data,
                &mut self.neighbor_replacements,
            )?;
        }
