## Title
Unbounded array allocation from attacker-controlled length word in TVM signature-batch precompiles enables node OOM/crash - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `BatchValidateSign` (address `0x...9`) and `ValidateMultiSign` (address `0x...a`) precompiled contracts decode a caller-supplied "array length" word straight out of the call data and use it to size a Java array (`new byte[len][]`) with no upper bound check unless the `allowTvmSelfdestructRestriction` VM config flag is active. This mirrors the p11-kit CVE-2020-29361 pattern: an attacker-controlled integer is used to size an allocation (`calloc`/`realloc` in p11-kit, `new byte[len][]` here) without validating it is within a sane range before the allocation is attempted.

### Finding Description
`extractBytesArray` and `extractSigArray` read the array length directly from the ABI-encoded call data with no bound: [1](#0-0) 

`extractBytes32Array` is even less guarded — it does not check the offset is in range and immediately allocates based on the raw length: [2](#0-1) 

In `ValidateMultiSign.execute`, the size check on the extracted array (`sigArraySize > MAX_SIZE`) is only performed **when `VMConfig.allowTvmSelfdestructRestriction()` is true**; when the flag is off, `extractBytesArray` is called with the raw, unchecked length: [3](#0-2) 

The same pattern exists in `BatchValidateSign.doExecute`, where `sigArraySize`/`addrArraySize` are only bounded under the same feature flag before calling `extractSigArray`/`extractBytesArray`/`extractBytes32Array`: [4](#0-3) 

The only other guard, `isValidAbiEncoding`, merely validates that the raw call-data byte length is a multiple of the expected ABI item stride — it does not validate the value embedded at the dynamic array's length slot, which is a separate, independently attacker-controlled 32-byte word: [5](#0-4) 

Because `intValueSafe()` can return any value up to `Integer.MAX_VALUE`, a crafted call to these precompiles can request an array of ~2^31-1 references (each `byte[][]`/`byte[]` reference or 32/192/64-byte entry), immediately consuming huge amounts of heap and throwing `OutOfMemoryError`, or spending excessive CPU/memory before any size validation occurs — when the `allowTvmSelfdestructRestriction` VM config path is not exercised. Whether this flag is currently active as the default on mainnet could not be conclusively confirmed from the available context; the flag is chain-parameter/proposal driven (`ProposalUtil`, `DynamicPropertiesStore`, `ProposalService`), meaning its enablement is a network governance decision, not a hardcoded default in code, so any network/fork where this proposal has not been activated remains exposed to this unbounded allocation path.

### Impact Explanation
An unbounded allocation triggered by a single transaction that calls a TVM contract which in turn invokes the `BatchValidateSign` or `ValidateMultiSign` precompile can cause an `OutOfMemoryError` / large GC pressure on the node executing/validating the transaction. Because block validation/execution in java-tron is performed synchronously per node (Manager/actuator execute path), a hostile transaction of this shape can degrade or crash full nodes and SR nodes processing the block, i.e., node crash/halt — a concrete, reachable impact category permitted by the rules (node crash or halt).

### Likelihood Explanation
The precompile addresses are reachable by any account via a plain `CALL`/`STATICCALL` from a smart contract, requiring no special privilege — any unprivileged contract deployer/caller can construct calldata for `batchvalidatesign(bytes32,bytes[],address[])` or `validatemultisign(...)` with a manipulated dynamic-array length word. The only obstacle is whether `allowTvmSelfdestructRestriction` is active on the target network; on networks/environments where it is not yet enabled (or is disabled for testing/private chains), the exploit requires only a single crafted transaction and no cooperation from other parties, making likelihood high in that state.

### Recommendation
Move the `MAX_SIZE` (and offset-bounds) checks for `extractBytesArray`, `extractSigArray`, and `extractBytes32Array` outside the `VMConfig.allowTvmSelfdestructRestriction()` conditional so they are unconditionally enforced before any array is allocated, regardless of feature-flag state. Additionally, add explicit bounds validation inside `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` themselves (reject `len < 0` or `len` larger than a small constant, and validate `offset`/`bytesOffset` are within `words.length`) so these helper methods are safe by construction rather than relying on call-site gating.

### Proof of Concept
1. Craft ABI-encoded calldata for `batchvalidatesign(bytes32,bytes[],address[])` (or `validatemultisign(...)`) such that the overall data length satisfies `isValidAbiEncoding` (a multiple of the expected word stride, matching header/item word counts) but the 32-byte word located at the dynamic `bytes[]` array's length slot is set to a large value (e.g., `0x7FFFFFFF`).
2. Deploy a contract that performs a low-level `CALL` to precompile address `0x...9` (BatchValidateSign) or `0x...a` (ValidateMultiSign) with this calldata, on a node/network where `allowTvmSelfdestructRestriction` proposal has not been activated.
3. Observe `extractBytesArray`/`extractSigArray`/`extractBytes32Array` executing `new byte[len][]` with `len` ≈ `0x7FFFFFFF`, causing large/failing allocation and `OutOfMemoryError` on the executing node during transaction processing.

  private static boolean isValidAbiEncoding(byte[] data, int headerWords, int itemWords) {
    if (data == null || data.length % WORD_SIZE != 0) {
      return false;
    }
    long tail = subtractExact(data.length, multiplyExact(headerWords, WORD_SIZE));
    return tail > 0 && tail % multiplyExact(itemWords, WORD_SIZE) == 0;
  }
