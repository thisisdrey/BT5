### Title
Missing negative-balance/overflow cap check in legacy `ExchangeCapsule.transaction` path allows unbacked exchange balances - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java`)

### Summary
`ExchangeCapsule.transaction()` computes the new first/second token balances of a TRC10 Bancor-style exchange pool and only validates the result (`newFirstTokenBalance < 0 || newSecondTokenBalance < 0`) when `hardenedCalc` is `true`. The `hardenedCalc` flag is derived from the chain parameter `allowHardenExchangeCalculation` via `AbstractExchangeActuator.allowHarden()`. When that parameter is not enabled (legacy/default path), the exact same balance-mutating calculation is executed with **no floor/negative check at all**, mirroring the GorplesCoin bug class where one code path (`pendingEmission`) enforces a cap and its sibling function (`pendingEmissionPerSecond`) omits the equivalent check. [1](#0-0) 

### Finding Description
`ExchangeCapsule.transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath, boolean hardenedCalc)` computes `buyTokenQuant` via either the legacy floating-point `ExchangeProcessor` or the `SafeExchangeProcessor`, then derives `newFirstTokenBalance`/`newSecondTokenBalance` using either checked (`StrictMathWrapper.addExact/subtractExact`) or plain arithmetic depending on `hardenedCalc`: [2](#0-1) 

The sanity check that the resulting pool balances cannot go negative is gated exclusively behind `hardenedCalc`: [3](#0-2) 

`hardenedCalc` is set from `dynamicStore.allowHardenExchangeCalculation()` in `ExchangeTransactionActuator.execute()`: [4](#0-3) [5](#0-4) 

This is precisely analogous to the GorplesCoin defect: two implementations of the same economic invariant exist (a "hardened"/capped variant and an uncapped variant), and the uncapped variant is reachable through the normal, unprivileged `ExchangeTransactionContract` execution path whenever the hardened-calculation chain parameter is not turned on. Because `allowHardenExchangeCalculation` is a governance-controlled proposal parameter (default state must be confirmed per deployment/config), any network where it has not been activated leaves the legacy path — with no negative-balance/overflow guard — as the one actually executed for every exchange trade.

### Impact Explanation
If the legacy (`hardenedCalc == false`) branch executes and the floating point Bancor calculation (`ExchangeProcessor.exchange`, using `double` math and `Maths.pow`) produces a `buyTokenQuant` that exceeds the pool's actual balance (due to precision/rounding drift at extreme ratios, e.g. very small `newBalance` denominators or extreme quant/balance ratios), `newFirstTokenBalance`/`newSecondTokenBalance` can go negative or wrap on overflow without being rejected. This corrupts `ExchangeCapsule`'s persisted `firstTokenBalance`/`secondTokenBalance`, effectively creating unbacked token/TRX balance in the exchange pool capsule — subsequent traders can then withdraw against this corrupted, unbacked balance, which maps to "unbacked balance" / "theft of funds" impact.

### Likelihood Explanation
The `ExchangeTransactionContract` is a normal, unprivileged transaction any account can broadcast against an existing exchange pool ("order placer" scope). Validation in `doValidate()` only guards against balances exceeding `getExchangeBalanceLimit()` and insufficient user balance; it does not independently bound-check the arithmetic result of `transaction()`: [6](#0-5) 
Whether this is practically triggerable depends on (a) the current activation state of the `allowHardenExchangeCalculation` proposal on the target network, and (b) whether the legacy floating-point Bancor formula can be driven to yield an out-of-bound quant for some feasible pool/quant combination — this precision analysis was not independently verified within available tool budget and should be validated with targeted numeric fuzzing before treating this as confirmed-exploitable.

### Recommendation
Apply the same `newFirstTokenBalance < 0 || newSecondTokenBalance < 0` (and ideally an explicit upper-bound/overflow) check unconditionally in `ExchangeCapsule.transaction()`, regardless of `hardenedCalc`, so that the legacy calculation path can never persist a negative or overflowed exchange balance — mirroring how `pendingEmission`'s max-supply cap needed to be mirrored into `pendingEmissionPerSecond` in the referenced GorplesCoin fix.

### Proof of Concept
Conceptual PoC (not independently executed):
1. On a network/test harness where `allowHardenExchangeCalculation` is `0` (default/unset), create an `Exchange` via `ExchangeCreateActuator` with a highly imbalanced pair (e.g., extremely small `secondTokenBalance` relative to `firstTokenBalance`).
2. Broadcast an `ExchangeTransactionContract` selling a `tokenQuant` chosen so that `ExchangeProcessor.exchange()`'s double-precision Bancor formula returns a `buyTokenQuant` computed to be larger than `secondTokenBalance` (feasible near-zero balances or edge ratios where `Maths.pow` rounding diverges).
3. Because `hardenedCalc` is `false`, `newSecondTokenBalance = secondTokenBalance - buyTokenQuant` is persisted without the `< 0` check, corrupting the exchange pool's on-chain balance to a negative/wrapped value while crediting the trader's account with more tokens/TRX than the pool held.
4. Confirming the exact numeric inputs that trigger this divergence in the legacy floating-point processor requires targeted unit testing of `ExchangeProcessor.exchange` against `SafeExchangeProcessor.exchange`, which was not completed here due to tool-call limits.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
