### Title
Per-IP QUIC connection rate limiter has a TOCTOU gap allowing concurrent connection churn to exceed `max_connections_per_ipaddr_per_min` - (File: streamer/src/nonblocking/connection_rate_limiter.rs)

### Summary
`ConnectionRateLimiter::is_allowed` only peeks at the current token count without consuming a token, and the actual token consumption happens later in `register_connection` after the QUIC handshake completes. Because these two operations are not atomic, an attacker opening many parallel handshakes from a single IP can pass `is_allowed` concurrently before any of them call `register_connection`, allowing more connections to be admitted per minute than `max_connections_per_ipaddr_per_min` intends.

### Finding Description
`is_allowed` in [1](#0-0)  is a read-only check (`current_tokens`) that does not consume any tokens, explicitly to allow "just checking" without mutating state (as shown in the accompanying test at [2](#0-1) ). The actual token consumption occurs only in `register_connection`, at [3](#0-2) , which is invoked after the QUIC handshake (`connection.await`) completes in `run_server`/connection-accept logic in `streamer/src/nonblocking/quic.rs`. If N parallel handshakes are in flight for the same IP before any of them reaches the `register_connection` call, every one of them can independently observe `is_allowed() == true` on the pre-handshake check because none has yet decremented the shared token bucket. Only when they subsequently call `register_connection` does the bucket get decremented — but by then the pre-handshake gating (whatever admission decision, e.g. accepting the raw UDP handshake) has already occurred for all N connections. This is a classic check-then-act race: the check (`is_allowed`) and the act (`register_connection`) are separated by the unbounded-duration QUIC handshake, and multiple accept tasks can race through the check phase in that window.

### Impact Explanation
This is a QoS-evasion bug: a single attacker IP can, via connection churn (rapidly opening many parallel QUIC handshakes), have more connections admitted into the post-handshake accounting path than `max_connections_per_ipaddr_per_min` allows for that per-minute window on the pre-handshake side, since the pre-handshake `is_allowed` check does not reserve/consume capacity. This lets a single unstaked/unprivileged IP consume more `ClientConnectionTracker`/connection-table slots than intended, potentially starving legitimate unstaked peers' connection attempts to the TPU port, matching the "unfair QoS capture / DoS via unprivileged client" bounty category referenced in the audit scope.

### Likelihood Explanation
The precondition is minimal: the attacker only needs to control one source IP and be able to open many parallel QUIC handshakes (`make_client_endpoint`-style connections) to the target's public TPU/QUIC port, which is exactly the "unstaked remote client" threat model in scope. No staking, gossip, or peer control is required. The race window is the QUIC handshake duration, which is easily large enough (network round trips) for many concurrent accept tasks to pass `is_allowed` before any completes `register_connection`. This is straightforward to reproduce with concurrent async tasks in an integration test.

### Recommendation
Make the check-and-reserve atomic: either (1) call `register_connection` (which does the actual token consumption) before starting the handshake and roll back/release the token if the handshake fails or is later rejected, or (2) merge `is_allowed`+reservation into a single atomic "try_consume" operation at accept time, removing the separate non-mutating `is_allowed` pre-check that allows unpaced concurrent bypass.

### Proof of Concept
```rust
// streamer/src/nonblocking/connection_rate_limiter.rs (new test)
#[tokio::test]
async fn test_concurrent_toctou_bypass() {
    use std::sync::Arc;
    let limiter = Arc::new(ConnectionRateLimiter::new(3, 3, 4));
    let ip = IpAddr::V4(Ipv4Addr::new(10, 0, 0, 1));

    // Simulate N concurrent "pre-handshake" checks racing before any
    // "post-handshake" register_connection call has consumed a token.
    let mut allowed_count = 0;
    let mut handles = Vec::new();
    for _ in 0..10 {
        let limiter = limiter.clone();
        handles.push(tokio::spawn(async move {
            // pre-handshake check
            let pre_ok = limiter.is_allowed(&ip);
            // simulate handshake delay
            tokio::time::sleep(std::time::Duration::from_millis(10)).await;
            pre_ok
        }));
    }
    for h in handles {
        if h.await.unwrap() {
            allowed_count += 1;
        }
    }

    // All 10 concurrent checks pass because none has consumed a token yet,
    // even though max_burst is only 3 — demonstrating the TOCTOU bypass.
    assert_eq!(allowed_count, 10, "expected all concurrent pre-checks to pass despite max_burst=3");

    // Now the post-handshake registrations run and only 3 actually succeed,
    // but the pre-handshake admission (e.g. UDP/handshake processing) already
    // happened for all 10, exceeding intended per-IP limit enforcement point.
    let mut registered = 0;
    for _ in 0..10 {
        if limiter.register_connection(&ip) {
            registered += 1;
        }
    }
    assert_eq!(registered, 3);
}
```
This demonstrates that the intended enforcement point (`is_allowed` at accept time) does not actually bound concurrent admissions to `max_connections_per_ipaddr_per_min`/burst, since it performs no reservation — the real integration-level PoC would spawn concurrent `make_client_endpoint` connections against `setup_quic_server` and observe that more than `max_connections_per_ipaddr_per_min` handshakes are processed (consuming handshake/CPU resources) before `connection_rate_limited_per_ipaddr` throttling takes effect on the post-handshake side.
