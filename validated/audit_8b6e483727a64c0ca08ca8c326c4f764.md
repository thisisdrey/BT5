This mirrors the report's root cause: a single momentary, attacker-controlled state read gets baked into a value that persists and affects other parties, because two logically-separable steps (measuring "weight"/rate, then committing it) are collapsed into one atomic, user-triggered action. ### Title
Instantaneous-utilization interest accrual lets a flashloan-funded borrow/repay retroactively distort the persisted debt/liquidity index for the entire idle period since last accrual - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and sibling vault contracts, e.g. `v0-vault-usdc.clar`, `v0-vault-sbtc.clar`)

### Summary
Each vault's `next-index`/`next-liquidity-index` compute `rate = interest-rate()` from the **current block's** `utilization()` and then apply that single rate over the full `time-delta = stacks-block-time - last-update`. If a vault has gone unaccrued for a long period (no user interaction), the very next call's utilization snapshot determines the interest rate charged/paid for the *entire* elapsed period. A user (using flash-loaned capital purely as funding, not exploiting flashloan permissions) can momentarily spike or collapse utilization immediately before triggering accrual, causing the persisted `index`/`lindex` to jump by an amount that does not reflect the true average utilization over the elapsed window, then reverse their position in the same transaction.

### Finding Description
`interest-rate` is computed from `utilization`, which is `calc-utilization (get-available-assets) (total-debt)` - purely a function of the vault's current on-chain balances, directly moved by borrow/repay/deposit/redeem calls. `next-index`/`next-liquidity-index` then apply this single point-in-time rate multiplicatively over `time-delta`, the number of seconds since `last-update` (`var-get last-update`), via `calc-multiplier-delta`. The resulting `index`/`lindex` are written to persistent contract vars in `accrue` (`var-set index next`, `var-set lindex nliq`) and, critically, this same call also permanently mints `treasury-lp` shares to the DAO treasury based on the debt-delta computed with this manipulated multiplier. [3](#0-2) 

Because any ordinary user can call `market::borrow`/`repay` (or the vault's own `system-borrow`/`system-repay` via market) to change `total-debt`/`get-available-assets` immediately before `accrue` executes, and because Clarity contract-calls inside one transaction are atomic, an attacker's own deployed contract can, in one transaction:
1. Take a flashloan (pure capital, out of scope on its own) or use owned capital to supply large collateral and borrow heavily from a vault that has been idle for a long `time-delta`, spiking `utilization`.
2. Trigger `accrue` (any vault interaction — deposit, borrow, repay — calls `accrue`/`next-index` first), which computes `next-index`/`next-liquidity-index` using the now-inflated utilization and applies it over the entire idle `time-delta`, permanently inflating `index` and `lindex`, and permanently minting `treasury-lp` to `dao-treasury` based on that inflated delta.
3. Immediately repay the borrow and withdraw the flashloan-funded collateral in the same atomic transaction, restoring `utilization` to its prior level — but the already-persisted `index`/`lindex`/minted treasury shares remain.

This is the same root-cause pattern as the referenced report: within one atomic transaction, a user temporarily manipulates state that feeds a subsequent "commit" step (there: `pushAllocationsToController` → `pushAllocationsToVaults`; here: utilization spike → `accrue`'s persisted index write), and the "commit" step permanently records the manipulated snapshot rather than a time-weighted or TWAP value.

### Impact Explanation
Because `index`/`lindex` govern every user's accrued debt (`calc-cumulative-debt`) and supply value (ztoken price via `resolve-ztoken`/liquidity index) for the *entire idle period*, an attacker can retroactively inflate the borrow index for all outstanding borrowers (increasing their owed debt beyond the honestly-accrued amount) or distort the liquidity index used to price ztoken collateral throughout the protocol, since ztoken price = `price * lindex / PRECISION`. This can push otherwise-healthy borrower positions into liquidation territory or corrupt collateral valuation market-wide, and it also improperly siphons `treasury-lp` (reserve share minting) based on a single-block artificial rate rather than genuine accrued interest. This lands on theft/permanent freezing of unclaimed yield (mis-minted treasury shares, wrongly-inflated borrower debt) and, in the worst case (large idle `time-delta` combined with an extreme rate curve), can materially misprice collateral used protocol-wide, risking insolvency-adjacent effects — fitting the in-scope Critical/High impact classes tied to vault share math and interest accrual.

### Likelihood Explanation
Likelihood is bounded by how long a vault typically goes without any interaction (`time-delta`) and by how much a single actor can move `utilization` relative to `get-available-assets`/`total-debt`. For lower-liquidity vaults (e.g. `stSTXbtc`, `USDH`), or during low-traffic periods, an attacker with modest flash-loaned capital can produce large swings in utilization, and any idle period (even routine off-peak hours) amplifies the effect since the manipulated rate is multiplied by the full elapsed `time-delta`. No privileged role or DAO action is required — an ordinary user's contract triggers this purely through public `market`/vault entry points.

### Recommendation
Do not apply a single instantaneous-utilization rate over an arbitrarily long elapsed window. Either (a) checkpoint/accrue on a fixed cadence so `time-delta` between accruals is bounded and cannot be dominated by an attacker-chosen snapshot, or (b) use a time-weighted/TWAP utilization (or rate) over the elapsed interval rather than the spot value at the moment `accrue` is invoked, or (c) segment accrual into sub-intervals anchored to prior utilization checkpoints so a single-block manipulation cannot retroactively affect interest already implicitly accrued during the idle window.

### Proof of Concept
1. Deploy an attacker contract that, in one transaction:
   - Deposits/borrows into `vault-usdc` (or any vault idle since `last-update` far in the past) using flashloan-funded capital to push `utilization()` to a high value (e.g. from 20% to 95%).
2. In the same transaction, call any function that triggers `accrue` on that vault (e.g. a 1-wei `deposit` or `borrow`) — this executes `next-index`/`next-liquidity-index` using the manipulated utilization and the full `time-delta` since `last-update`, then `var-set index next` / `var-set lindex nliq` and mints `treasury-lp` based on the resulting `debt-delta`.
3. Still within the same transaction, repay the borrow and withdraw the collateral, restoring `utilization()` to its original level.
4. Observe that `index`/`lindex` remain permanently at the inflated values from step 2, and `treasury-lp` shares were minted to `dao-treasury` based on the manipulated `debt-delta`, even though the true time-weighted utilization over the idle period never reached the manipulated level.
