Checking the exact mechanics of the per-account token list to confirm the reachable DoS surface.### Title
Attacker can permanently block an account from adding new collateral/debt positions by filling its per-account token list via dust deposits - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool` keeps two per-account sets — `depositTokensOfAccount` and `debtTokensOfAccount` — capped by `MAX_TOKENS_PER_USER = 30`. Every first-time credit of a deposit token to an account calls `Pool.addToDepositTokensOfAccount`, which reverts with `UserReachedMaxTokens` once the combined length reaches 30. Critically, `DepositToken.deposit(uint256 amount_, address onBehalfOf_)` mints to an arbitrary `onBehalfOf_` address, so any unprivileged user can forcibly insert tokens into a victim's set by depositing 1-wei dust on their behalf. Like the nghttp2 bug (many cheap, repeated frames that exhaust a fixed resource), a handful of cheap dust deposits exhausts the victim's fixed token-list capacity, after which the revert propagates into the victim's own `deposit`, `transfer`-receive, leverage, and mint paths — a denial of service on that account.

### Finding Description
The flow for any deposit token `D` and victim `V`:

1. Attacker calls `D.deposit(1, V)` (or `D.transfer(V, 1)` if they already hold msdTOKEN). `DepositToken._mint` sees `balanceOf[V] == 0` and calls `pool.addToDepositTokensOfAccount(V)` (`DepositToken.sol:485-488`, `DepositToken.sol:517-520`).
2. `Pool.addToDepositTokensOfAccount` enforces `onlyIfAdditionWillNotReachMaxTokens`, which reverts when `debtTokensOfAccount.length(V) + depositTokensOfAccount.length(V) >= 30` (`Pool.sol:143-148`, `Pool.sol:216-220`).
3. Repeating for every deposit token listed in the pool (the pool supports up to dozens of collaterals; only 30 slots exist across deposits *and* debts) pushes `V` to the cap.
4. Afterwards, any action that would add a *new* token to `V`'s set reverts the entire transaction: `deposit(newToken, V)` by anyone (including V itself and `NativeTokenGateway`/`SmartFarmingManager` flows), incoming `transfer`/`transferFrom` of a token `V` doesn't hold (`DepositToken.sol:518-520`), and `DebtToken.issue`/`mint` of a synthetic `V` hasn't borrowed before (same `UserReachedMaxTokens` guard via `addToDebtTokensOfAccount`, `Pool.sol:204-208`).

The sets are append-only on first credit and only shrink when a balance returns to zero (`DepositToken.sol:460-462`, `523-525`), so the dust entries persist until the victim explicitly cleans them up.

### Impact Explanation
Once saturated, the victim cannot deposit any new collateral type, cannot receive any deposit token they don't already hold, and cannot mint any new synthetic — all those calls revert inside `addTo*TokensOfAccount`. This is a liveness/availability break of position management: a victim nearing liquidation who needs to deposit a collateral type they haven't used before is blocked from topping up and can be liquidated (temporary freezing / forced-loss amplification). Recovery is possible — the victim can transfer each dust balance out to zero it and free a slot — but only if they realize it, only one slot per transaction type per token, and the attacker can re-grief at dust cost; a fresh account or a SmartFarmingManager receiver address can be kept saturated indefinitely at near-zero cost to the attacker.

### Likelihood Explanation
Fully unprivileged: `deposit(amount_, onBehalfOf_)` is public, accepts an arbitrary beneficiary (`DepositToken.sol:211-237`), and requires only owning dust amounts of the underlying of each listed deposit token — no governor, oracle, or privileged role involved. Cost scales linearly with the number of deposit tokens in the pool and is trivially low. The main mitigating factor is impact asymmetry: existing positions keep working (withdrawals and repayments of held tokens reduce/free entries), so the attack blocks *new* position expansion rather than freezing existing funds outright.

### Recommendation
Decouple the cap accounting from unsolicited credits:
- Only count tokens toward `MAX_TOKENS_PER_USER` on user-initiated actions (e.g., check the cap in `deposit` for `onBehalfOf_ == _msgSender()` positions or in `issue`), and let `addToDepositTokensOfAccount` skip or tolerate the cap for inbound transfers; or
- Make the per-account tracking lazy — iterate `depositTokens`/`debtTokens` pool-wide lists with balance checks instead of a per-account set, or drop the revert in favor of silently not tracking unsolicited tokens; or
- Disallow `onBehalfOf_` deposits to accounts other than the caller for first-time token additions (require `balanceOf[onBehalfOf_] > 0 || onBehalfOf_ == _msgSender()`).

### Proof of Concept
Hardhat sketch (fork of an existing deployment with N listed deposit tokens):

```ts
// pool has deposit tokens D1..Dn; victim V holds none / holds few
for (const d of depositTokens.slice(0, 30 - currentLen)) {
  const underlying = await ethers.getContractAt('IERC20', await d.underlying());
  // attacker acquires >= 1 wei of each underlying (e.g., via swap)
  await underlying.approve(d.address, 1);
  await d.deposit(1, victim.address); // adds d to depositTokensOfAccount[victim]
}

// victim is now at MAX_TOKENS_PER_USER
```

One uncertainty I could not fully verify within the index: whether any deployed pool actually lists enough distinct deposit/debt tokens for an attacker to reach 30 entries against a fresh victim (the cap is shared across both sets, so a victim's own holdings partially fill it).
