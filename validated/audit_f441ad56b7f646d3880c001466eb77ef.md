Based on the investigation, I found a concrete analog vulnerability in Gitaly's URL-based repository creation/fetch RPCs, matching the report's bug class: a narrow validation gate ("is the URL non-empty / does it parse?") that, once passed, allows the underlying tool (`git`) to interpret unrestricted, potentially dangerous input — analogous to `canCall()` checking only `sig == 0x415565b0` and then trusting all downstream logic of `transformERC20()`.

### Title
Unrestricted Git transport scheme in user-supplied repository URLs allows remote-helper command injection - ([File: internal/gitaly/service/repository/create_repository_from_url.go])

### Summary
`CreateRepositoryFromURL` and `FetchRemote` accept a fully user-controlled remote URL and pass it directly to `git clone`/`git fetch` as a positional argument, with validation limited to "non-empty" and dash-prefix rejection. Git supports the `ext::` (and other) transport helpers, which execute an arbitrary local command as the "transport". Because Gitaly does not restrict the set of allowed Git protocols (e.g., via `GIT_ALLOW_PROTOCOL`/`protocol.*.allow`) before invoking `git clone`, a caller can smuggle a command-executing transport string through the "safe-looking" positional argument check.

### Finding Description
`validateCreateRepositoryFromURLRequest`/`validateFetchRemoteRequest` only check that `req.GetUrl()` (or `RemoteParams.Url`) is non-empty [1](#0-0) . The URL is then parsed only for extracting user/password/host information and is otherwise passed through unchanged into `git clone`'s positional arguments [2](#0-1) . `commandDescription.args()` (used by every git subcommand, including `clone`) only rejects positional args starting with `-`; it performs no scheme/protocol allowlisting [3](#0-2) . Git natively supports remote helper transports like `ext::<command>`, which are not rejected by this check because they don't start with `-`. This mirrors the 0x pattern: the code checks one narrow condition (URL non-empty, no leading dash) and then unconditionally trusts the downstream component (`git`) to safely interpret everything else, even though `git` itself supports a class of inputs (transport helpers) whose behavior is fundamentally different from a normal HTTP/SSH/git:// fetch and can execute arbitrary logic.

### Impact Explanation
If `git` on the Gitaly host is built with remote-helper support and no `GIT_ALLOW_PROTOCOL`/`protocol.ext.allow=never` restriction is applied by Gitaly for these RPCs, an ordinary authenticated client invoking `CreateRepositoryFromURL` or `FetchRemote` with a URL such as `ext::sh -c "..."` could achieve arbitrary command execution on the Gitaly node, far beyond the RPC's intended scope (repository import/fetch). This is a direct remote code execution / storage-escape-class impact reachable from a routine, user-triggered RPC field (crafted remote URL).

### Likelihood Explanation
`CreateRepositoryFromURL` and `FetchRemote` are ordinary, user/admin-reachable RPCs (repository import/mirroring flows) that take attacker-influenced URL strings as first-class input [4](#0-3) [5](#0-4) . Whether this is exploitable in practice depends on whether Git's global configuration in this Gitaly build already disables the `ext::` helper (e.g., via a global `protocol.allow` setting) — I could not find any such restriction being set by Gitaly's `GlobalConfiguration`/`clone`/`fetch` command descriptions in the code I reviewed [6](#0-5) , so this should be treated as a plausible but not fully confirmed gap, similar to how the 0x team's mitigation depended on external assurances.

### Recommendation
Explicitly allowlist accepted URL schemes (`http`, `https`, `git`, `ssh`, and the SCP-like syntax) before invoking `git clone`/`git fetch`, and set `protocol.ext.allow=never` (or `GIT_ALLOW_PROTOCOL` restricted to the allowlisted schemes) as a global Git configuration for all Gitaly-invoked commands, not just these two RPCs. Reject any URL containing `::` transport-helper syntax outright.

### Proof of Concept
1. As an ordinary authenticated gRPC client, call `CreateRepositoryFromURL` with `Url: "ext::sh -c 'id > /tmp/pwned'"` (or an equivalent OS-appropriate command).
2. `validateCreateRepositoryFromURLRequest` accepts it since the URL is non-empty [7](#0-6) .
3. `cloneFromURLCommand` passes the string unmodified into `git clone`'s `Args` [8](#0-7) .
4. `validatePositionalArg` only rejects leading `-`, so `ext::sh -c ...` passes [3](#0-2) .
5. If the underlying `git` binary's remote-helper support and protocol settings are not otherwise restricted, `git clone` invokes the `ext` remote helper, executing the embedded command on the Gitaly host.

func (s *server) validateFetchRemoteRequest(ctx context.Context, req *gitalypb.FetchRemoteRequest) error {
	if err := s.locator.ValidateRepository(ctx, req.GetRepository()); err != nil {
		return structerr.NewInvalidArgument("%w", err)
	}

	if req.GetRemoteParams() == nil {
		return structerr.NewInvalidArgument("missing remote params")
	}

	if req.GetRemoteParams().GetUrl() == "" {
		return structerr.NewInvalidArgument("blank or empty remote URL")
	}

	return nil
}
