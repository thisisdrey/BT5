### Title
Unbounded array-length field in precompiled contract input drives allocation/loop without validating against actual word count, enabling low-cost DoS - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`extractBytesArray` and `extractSigArray` in `PrecompiledContracts.java` decode a "count" field directly from attacker-controlled TVM call data (`words[offset].intValueSafe()`) and then use it, unvalidated, to size an array allocation and drive a loop that reads further words at derived offsets. Nothing checks that `len` is consistent with the actual number of words present (`words.length`), so a caller can supply a small `data` payload that *declares* a huge element count, exactly the CVE-2017-14175 bug class: a header/count field is trusted to control an allocation/loop while the actual backing data is insufficient.

### Finding Description [1](#0-0) 
```
private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
  if (offset > words.length - 1) {
    return new byte[0][];
  }
  int len = words[offset].intValueSafe();
  byte[][] bytesArray = new byte[len][];
  for (int i = 0; i < len; i++) {
    ...
  }
  return bytesArray;
}
```
The only bound check is `offset > words.length - 1`, i.e., that the *count word itself* exists. `len` is then used directly to allocate `new byte[len][]` before any check that `offset + len` is within `words.length`. The sibling helper `extractSigArray` has the identical pattern: [2](#0-1)

Both are analogous to `extractBytes32Array` at lines 390-397, which has no bound check at all: [3](#0-2) 

These helpers are used by the multi-signature-verification precompiled contracts (`ValidateMultiSign` / `BatchValidateSign`, confirmed present via `framework/src/test/java/org/tron/common/runtime/vm/ValidateMultiSignContractTest.java` and `BatchValidateSignContractTest.java`), which are reachable by any account through a normal `CALL`/`STATICCALL` TVM opcode to the precompile address — i.e., any signed transaction that triggers contract execution can supply crafted `data`.

Because `len` comes straight from a 256-bit word (`intValueSafe()`), an attacker can set it to a very large value (bounded only by `int` range) while supplying only a handful of actual words after it. This causes `new byte[len][]` to attempt allocating a reference array with up to ~2^31 elements — a multi-gigabyte allocation attempt — before the loop even executes and before any check that the declared count is backed by real data, mirroring the ImageMagick XBM bug where the "rows"/"columns" header values are trusted without checking the file actually contains that much data.

### Impact Explanation
A crafted call to the multisig-validation precompile can force the node to attempt a very large array allocation on every invocation, driving heavy GC/CPU pressure or an `OutOfMemoryError`. Because `getEnergyForData()` for these precompiles is typically a small fixed/near-fixed cost unrelated to the attacker-declared `len` (as opposed to the actual, tiny `data.length` supplied), the attacker pays disproportionately little energy for the resource consumption imposed on the executing node — a cheap, repeatable DoS vector against any node that processes the transaction/block, potentially degrading or halting block processing under repeated invocation.

### Likelihood Explanation
The precompiled contract is reachable by any contract call from an unprivileged account (no permission or witness/SR status required), and the vulnerable code path is a small, self-contained decoding routine with no data-length cross-check, making the flaw trivial to trigger with a single crafted transaction.

### Recommendation
Before allocating or looping, validate that `offset + len` (and any subsequently derived offsets/lengths) stay within `words.length`, and additionally bound `len` against a sane maximum derived from `data.length` (e.g., `words.length - offset - 1`) before performing `new byte[len][]`. Reject the call (return a false/DATA_FALSE result) instead of allocating when the declared count cannot possibly be backed by the supplied data.

### Proof of Concept
Construct a transaction that calls the `ValidateMultiSign`/`BatchValidateSign` precompiled contract with ABI-encoded input where the "array length" word (e.g., `words[offset]`) is set to a large value such as `0x7FFFFFFF`, while the actual `data` payload contains only the minimal number of trailing words. When `execute()` reaches `extractBytesArray`/`extractSigArray`, `len` decodes to `2147483647`, and `new byte[len][]` is attempted, causing large memory allocation pressure / `OutOfMemoryError` for the node processing this contract call, with negligible energy charged to the caller since `getEnergyForData` is computed from the small actual `data.length`, not from the declared `len`.

**Note on uncertainty:** I could not directly view the `execute()` bodies of `ValidateMultiSign`/`BatchValidateSign` or the exact energy-cost formulas within the tool budget available, nor confirm whether the TVM's precompile-call dispatcher (e.g., in `Program.java`) wraps `OutOfMemoryError`/`Error` (as opposed to `Exception`) in a way that limits blast radius to the single call. This should be verified directly in the repository to confirm whether the consequence is a contained call failure or a broader node-level impact.
