### Title
Dust deposit-token griefing fills `depositTokensOfAccount`/`debtTokensOfAccount` to `MAX_TOKENS_PER_USER`, permanently DoS-ing the victim's deposits, transfers, and debt issuance - (File: contracts/Pool.sol)

### Summary
Analogous to CVE-2023-3900 (an improperly validated input causes a feature to fail for a target account), `Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` revert with `UserReachedMaxTokens` once a victim's combined token lists reach `MAX_TOKENS_PER_USER`. Because `DepositToken.deposit` mints to an arbitrary `onBehalfOf_` address and `_transfer`/`_mint` auto-register tokens in the recipient's account list, any unprivileged attacker can fill a victim's list by dust-depositing every whitelisted deposit token `onBehalfOf` the victim. From then on, any call that would register a new token for the victim — minting a new deposit token, receiving a deposit-token transfer of a type they don't hold, or issuing a new type of debt — reverts, so the victim cannot open or expand positions.

### Finding Description
- `Pool.onlyIfAdditionWillNotReachMaxTokens` reverts when `debtTokensOfAccount.length + depositTokensOfAccount.length >= MAX_TOKENS_PER_USER`. [1](#0-0) 
- `Pool.addToDepositTokensOfAccount` is guarded by that modifier and is called by `DepositToken._mint` / `_transfer` whenever the recipient's balance goes from 0 → non-zero. [2](#0-1) [3](#0-2) [4](#0-3) 
- `DepositToken.deposit(amount_, onBehalfOf_)` accepts any beneficiary (`onBehalfOf_ != address(0)` is the only check) and mints to it, so the attacker needs no victim cooperation or allowance. [5](#0-4) 
- `depositOf`/`debtPositionOf` iterate the whole per-account list, so there is no way to skip entries; the list can only shrink via `removeFromDepositTokensOfAccount` when a balance hits exactly 0 — dust entries the attacker controls by amount but the victim cannot cheaply clear are not removable without withdrawing/burning, and burn/withdraw of the victim's *own* positions also frees slots, so the attack is repeatable indefinitely at dust cost. [6](#0-5) 

Once the cap is reached, the following victim calls revert inside `_mint`/`_transfer`/`issue`:
- `DepositToken.deposit` for any collateral type the victim doesn't already hold (`_mint` → `addToDepositTokensOfAccount` → `UserReachedMaxTokens`).
- `DepositToken.transfer`/`transferFrom`/`seize` crediting a token type the victim doesn't hold — anyone sending the victim a new deposit token type reverts.
- `DebtToken.issue`/`mint` for any synthetic asset whose debt token isn't already in the victim's list (`addToDebtTokensOfAccount` shares the same cap).

### Impact Explanation
Permanent (as long as the attacker maintains the dust) denial of the victim's ability to deposit new collateral types, receive new deposit tokens, or mint/borrow synthetic assets. If the victim holds collateral but no debt, they cannot borrow at all; the collateral's utility is frozen (it can be withdrawn but cannot back issuance). This is a liveness break / temporary freezing of funds utility, reachable by a purely unprivileged EOA at dust cost, matching the bug class of improper input validation leading to DoS of functionality.

### Likelihood Explanation
Attack cost is one dust `deposit(amount, victim)` per whitelisted deposit token (up to `MAX_TOKENS_PER_USER` entries counting debt tokens the victim already has). No privileged role, no oracle manipulation, no flash requirement. It requires only that the number of listed deposit + debt tokens be at least `MAX_TOKENS_PER_USER` (defined in `PoolStorage`; I could not confirm its exact configured value from the indexed snippets — if it exceeds the count of registered tokens the attack is not reachable on the current deployment, which is the main uncertainty).

### Recommendation
- On first receipt, don't revert the whole mint/transfer when the cap is hit; either revert only for `deposit` initiated by the beneficiary (keep silent cap for unsolicited transfers), or track whether the beneficiary "opted in" (only auto-add on self-initiated deposits/issue, and require a separate `enableCollateral` call for received tokens).
- Alternatively, let `addToDepositTokensOfAccount` fail-soft (skip adding) for unsolicited transfers so the transfer succeeds but the token isn't counted as collateral, which also removes the debtPositionOf griefing vector.

### Proof of Concept
Hardhat sketch (repo uses Hardhat/ethers tests):

```ts
// Attacker fills victim's account list with dust deposits
for (const dt of allDepositTokens) {              // every registered DepositToken
  const underlying = await dt.underlying()
  await erc20(underlying).connect(attacker).approve(dt.address, DUST)
  // balance-delta deposit mints to victim; _mint -> pool.addToDepositTokensOfAccount(victim)
  await dt.connect(attacker).deposit(DUST, victim.address)
}
// victim list length == MAX_TOKENS_PER_USER now

// 1) Victim cannot deposit a new collateral type
await expect(
  newDepositToken.connect(victim).deposit(amount, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')

// 2) Anyone transferring a new deposit-token type to the victim reverts
await expect(
  someDepositToken.connect(thirdParty).transfer(victim.address, 1)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')

// 3) Victim cannot issue a new synthetic asset (new debt token)
await expect(
  msXDebtToken.connect(victim).issue(parseEther('1'), victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')
```

Uncertainty note: I could not verify the deployed value of `MAX_TOKENS_PER_USER` in `contracts/storage/PoolStorage.sol` nor the number of registered deposit/debt tokens per chain from the indexed content; if the cap exceeds the count of registered tokens, the attack is unreachable on that deployment and severity collapses to informational.
