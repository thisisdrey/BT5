### Title
Bounded compute/memory DoS in `parse_map_key_body`: full recursive `Value` deserialization occurs before memory budget is enforced - ([File: stackslib/src/net/api/read_only/parse.rs])

### Summary
`RPCGetMapEntryRequestHandler::try_parse_request` bounds the request body length against `BOUND_VALUE_SERIALIZATION_HEX` and then calls `parse_map_key_body`, which only preflights the *raw serialized byte length* of the hex payload against `max_parse_mem_bytes` before calling `Value::deserialize_read` to fully materialize the nested Clarity `Value` tree. [1](#0-0)  The actual memory check (`limiter.checkpoint()`) only runs *after* the whole value has already been recursively allocated, so a crafted, densely-nested-but-small serialized value can cause allocation far beyond `max_parse_mem_bytes` before the request is rejected. [2](#0-1) 

### Finding Description
`deserialize_value` in `parse.rs` does:
1. `limiter.preflight((hex.len() as u64).div_ceil(2))` — a coarse estimate based only on the raw decoded byte count, not on how many `Value::List`/`Value::Sequence` nodes that byte stream will expand into.
2. `Value::deserialize_read(&mut data.as_slice(), None, false)` — this runs to completion, recursively allocating every nested `Value` (each `Value::List` requires a heap `Vec<Value>`, `ListTypeData`, etc.), with no incremental budget check during recursion.
3. Only after full deserialization does `limiter.checkpoint()` compare actual net allocation (via `ResourceLimiter`/`MemoryTracker`, backed by a thread-local `TrackingAllocator`) against `max_parse_mem_bytes`. [3](#0-2) 

Because Rust's serialized Clarity value format encodes structural overhead per nested container (type tag + length prefix), the "cost per byte" preflight in step 1 is an underestimate of true expansion: each additional nesting level costs only a few serialized bytes but a much larger heap allocation (`Vec` header, `Value` enum size, list-type metadata) once decoded. The `ParseLimiter`'s own doc comment concedes this design tradeoff explicitly: "Preflights charge sizes known before allocating... checkpoints compare the thread's net retained allocations to the limit and measure nothing without [the] `TrackingAllocator`." [4](#0-3)  This means: (a) the real-allocation check only fires post-hoc, after the expensive recursive allocation has already happened, and (b) if the `TrackingAllocator` is not installed as the process's global allocator, the checkpoint measures nothing at all and the memory limit never triggers, degrading silently to only the coarse byte-length preflight. [5](#0-4) 

I was not able to confirm within the available context (a) the exact numeric value of `BOUND_VALUE_SERIALIZATION_HEX`, (b) whether `stacks-node`'s production binary installs the `TrackingAllocator` by default, and (c) whether `Value::deserialize_read` in `clarity-types/src/types/serialization.rs` enforces an independent depth/element-count cap that would bound nesting amplification regardless of the `ParseLimiter`. These are material to precisely quantifying the achievable amplification factor and worst-case peak memory/CPU.

### Impact Explanation
If exploitable, an attacker can force a single `POST /v2/map_entry/:address/:contract/:map` request to cause the node to allocate substantially more memory and CPU time (building/dropping a deep tree of `Value::List` nodes) than the operator's configured `max_parse_mem_bytes` intends, before the request is ultimately rejected (or, in the no-`TrackingAllocator` case, possibly accepted without ever detecting the overrun). This is a bounded, per-request compute/memory cost multiplier on a public, unauthenticated read endpoint (`/v2/map_entry`), matching the "bounded compute DoS on a read endpoint" impact category. It is repeatable per request and reachable by any unprivileged remote HTTP client with RPC access.

### Likelihood Explanation
The endpoint is unauthenticated/public RPC and reachable by any remote party with a network path to the node's RPC port; no privileged role or secret is required. The precondition for full severity is that either the `TrackingAllocator` isn't installed (silently disabling the check) or the underlying Clarity deserializer permits enough nesting within `BOUND_VALUE_SERIALIZATION_HEX` bytes to substantially exceed the linear byte-based preflight estimate — both of which I could not fully verify from the available index.

### Recommendation
Enforce the memory budget incrementally during recursive deserialization (e.g., pass the `ResourceLimiter`/`ParseLimiter` into `Value::deserialize_read` so each nested allocation is checked as it happens), rather than only pre-flighting on raw byte length and checkpointing after the full value tree is built. Additionally, verify/document that `TrackingAllocator` is unconditionally installed in all `stacks-node` release builds, and consider adding an explicit nesting-depth/element-count cap independent of `TrackingAllocator` availability.

### Proof of Concept
Add a `stackslib` unit test in `stackslib/src/net/api/read_only/parse.rs` (or a new test module) that:
1. Constructs a hex-encoded Clarity `Value` representing a deeply nested structure (e.g., repeatedly wrapped empty lists/buffers) whose serialized byte length is just under `BOUND_VALUE_SERIALIZATION_HEX`.
2. Calls `parse_map_key_body(body, max_parse_mem_bytes)` with a small `max_parse_mem_bytes`.
3. Asserts either that the call succeeds despite exceeding the configured budget (if `TrackingAllocator` isn't active in the test harness), or measures wall-clock/peak-RSS during the call and asserts it substantially exceeds `max_parse_mem_bytes` before the error in `limiter.finish()` at `parse.rs:255` is returned.

Given the unresolved uncertainties noted above regarding the exact bound value, default allocator configuration, and any independent depth caps in `clarity-types/src/types/serialization.rs`, this should be treated as a probable but not fully confirmed finding — further verification via a background Devin session with full codebase/test access is recommended to construct the exact PoC and confirm the amplification factor.

/// Decode one hex-encoded Clarity value under the limiter. `error_msg` keeps
/// each endpoint's pre-existing error string.
fn deserialize_value(
    hex: &str,
    limiter: &ParseLimiter,
    error_msg: &'static str,
) -> Result<Value, Error> {
    let hex = hex.strip_prefix("0x").unwrap_or(hex);
    // The decoded size is known before allocating; reject early.
    limiter.preflight((hex.len() as u64).div_ceil(2))?;
    let value = {
        let data = hex_bytes(hex).map_err(|_e| Error::DecodeError(error_msg.into()))?;
        Value::deserialize_read(&mut data.as_slice(), None, false)
            .map_err(|_e| Error::DecodeError(error_msg.into()))?
    };
    limiter.checkpoint()?;
    Ok(value)
}

#[derive(Clone, Copy)]
enum MemoryTracker {
    NoTracking,
    MaxAllocated {
        baseline: AllocationCounter,
        limit_bytes: u64,
    },
}

impl MemoryTracker {
    pub fn unlimited() -> Self {
        Self::NoTracking
    }

    pub fn from_max_allocation(limit_bytes: u64) -> Self {
        if !tracking_allocator_installed() {
            error!(
                "TrackingAllocator is not installed as the global allocator; any configured memory limits will never trigger"
            );
        }

        Self::MaxAllocated {
            baseline: thread_allocated(),
            limit_bytes,
        }
    }

    pub fn check_not_exceeded(&self) -> Result<(), String> {
        match self {
            NoTracking => Ok(()),
            MaxAllocated {
                baseline,
                limit_bytes,
            } => {
                let allocated = thread_allocated().net_allocated(baseline);
                if allocated > *limit_bytes {
                    Err(format!(
                        "Net memory allocation of {} bytes exceeds budget of {} bytes.",
                        allocated, *limit_bytes
                    ))
                } else {
                    Ok(())
                }
            }
        }
    }
