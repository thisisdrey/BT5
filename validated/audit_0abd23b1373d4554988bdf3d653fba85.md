### Title
Out-of-bounds heap read via unvalidated Zip64 extra-field `attr_count` in `Zip64ExtraField::attr64()` - (File: `src/tools/singlejar/zip_headers.h`)

### Summary
`singlejar` (invoked by Bazel to build `deploy.jar` / merge JAR inputs, e.g. from `java_binary`, `java_import`, remote/http-fetched jars) trusts the `attr_count()` implied by an attacker-crafted Zip64 "extra field" without checking it against the number of 64-bit attributes actually needed before indexing into it, mirroring the CVE-2026-31674 pattern where `addrnr` was used to index `rtinfo->addrs[]` without validating it stays within `IP6T_RT_HOPS`.

### Finding Description
`CDH::compressed_file_size()` / `CDH::uncompressed_file_size()` and `LH::compressed_file_size()` / `LH::uncompressed_file_size()` in `zip_headers.h` check only the 32-bit size field for the `0xFFFFFFFF` "needs-ext64" sentinel, then unconditionally call `z64->attr64(index)`: [1](#0-0) [2](#0-1) 

`Zip64ExtraField::attr64(index)` simply indexes a flexible trailing array `attr_[]` with no bounds check of its own: [3](#0-2) 

The only validation performed anywhere in the parsing path is `ExtraField::find()`, which bounds-checks that the declared `payload_size()` (hence `size()`) fits inside the extra-fields buffer of the entry — it does **not** enforce that `attr_count()` (i.e. `payload_size()/8`) is large enough to cover the index (`0` or `1`) that the caller is about to read: [4](#0-3) 

This is structurally identical to the kernel bug: a length/count value taken from attacker-controlled input (`payload_size`/`attr_count` here, `addrnr` there) is used to select an index into a small backing array, but the *consumer* of that index (`attr64()` here, `rt_mt6()` there) never confirms the count actually covers the index it uses. The kernel fix validates `addrnr` at rule-installation time; here there is no equivalent validation of `attr_count()` at the point size fields are consumed.

Concretely, an attacker can craft a JAR entry (Local Header + Central Directory Header) where:
- `compressed_file_size32` and/or `uncompressed_file_size32` are set to `0xFFFFFFFF` (triggering the ext64 path), and
- the accompanying Zip64 extra field has `payload_size() < 16` (e.g. `0` or `8`, giving `attr_count()` of `0` or `1`),

so that `attr64(0)` or `attr64(1)` reads 8 bytes past the field's own declared/allocated payload. `singlejar` mmaps the whole input jar (`third_party/ijar`/`src/tools/singlejar` combiner code reads via `mapped_start()`), so this out-of-bounds `attr64()` read can walk into adjacent extra-field data, past the entry, or — if the malformed field sits at the very end of the mapped/allocated region (e.g. a truncated or minimally sized crafted jar) — beyond the mapped buffer entirely.

`OutputJar::AppendToDirectoryBuffer` (`output_jar.cc:886-969`) additionally propagates `zip64_ef->attr_count()` from this same untrusted field when deciding how many attributes to copy into the merged central directory, compounding the trust placed in the attacker-supplied count without a sanity check against the standard maximum of 3 (uncompressed size, compressed size, local header offset): [5](#0-4) 

### Impact Explanation
An attacker who controls the bytes of a JAR consumed during a Bazel build (e.g. a jar fetched via `http_jar`/`http_file`, a Maven artifact, or any dependency whose contents a victim's `java_binary`/`singlejar` merge step processes) can craft this malformed Zip64 extra field to trigger an out-of-bounds heap read in the `singlejar` native tool during the build. This can crash the build process (denial of service against the build) or, depending on heap layout, leak adjacent process memory contents into the merged output jar (since sizes read via `attr64()` feed into further copy-size computations such as `in_zip_size()`), which is a confidentiality-impacting information disclosure in the build tool consuming untrusted archive content — the exact "reject oversized count field before indexing" class described in the report, applied to Bazel's own archive-parsing code.

### Likelihood Explanation
`singlejar` is exercised on every `java_binary`/`java_import`/deploy-jar build that merges external jars, and JAR content routinely originates from network-fetched dependencies that a remote/malicious actor can influence (a hostile artifact/registry host serving a crafted jar). No sha256/integrity check on individual zip *entry structure* (as opposed to whole-file checksum for `http_jar`) would prevent this, since the file's overall checksum can still match while its internal Zip64 extra field is malformed — the checksum validates file identity, not internal parser invariants relied upon by `zip_headers.h`. This makes the likelihood the same class of "no source-side validation, only whole-file digest" seen in comparable archive-parsing analogs.

### Recommendation
Add an explicit bound check in `Zip64ExtraField` (or at each call site in `zip_headers.h`) that `attr_count()` is sufficient for the index being requested before calling `attr64()`, e.g. reject/treat as malformed any Zip64 extra field where `attr_count() < index + 1` for the specific `compressed_file_size()`/`uncompressed_file_size()`/`local_header_offset()` accessors, and cap/verify `attr_count()` against the documented maximum of 3 attributes wherever it is propagated (`output_jar.cc`'s `zip64_attr_count`). This mirrors the kernel fix pattern: validate the count against its expected bound before it is ever used as an array index.

### Proof of Concept
The existing test harness in `output_jar_simple_test.cc` already demonstrates the pattern used by this codebase to construct malformed extra fields for regression testing (`CreateZipWithMalformedExtraField`), confirming the fetch/parse path is reachable with attacker-controlled bytes and is exactly the kind of harness a `BuildIntegrationTestCase`/`src/test/shell/bazel` proof would extend, by crafting a Local/Central header pair whose 32-bit size fields are `0xFFFFFFFF` and whose Zip64 extra field payload is `0` or `8` bytes (yielding `attr_count() < 2`), then invoking `singlejar` to observe the out-of-bounds `attr64()` read (crash or heap-adjacent bytes copied into the merged JAR's uncompressed/compressed size or local-header offset): [6](#0-5)

class ExtraField {
 public:
  static const ExtraField* find(uint16_t tag, const uint8_t* start,
                                const uint8_t* end) {
    while (start < end) {
      if (ziph::byte_ptr(start) + sizeof(ExtraField) > ziph::byte_ptr(end)) {
        break;
      }
      auto extra_field = reinterpret_cast<const ExtraField*>(start);
      if (ziph::byte_ptr(start) + extra_field->size() > ziph::byte_ptr(end)) {
        break;
      }
      if (extra_field->is(tag)) {
        return extra_field;
      }
      start = ziph::byte_ptr(start) + extra_field->size();
    }
    return nullptr;
  }

std::string CreateZipWithMalformedExtraField() {
  std::string zip_data;
  const std::string filename = "evil.bin";

  // 1. Local File Header (LFH)
  size_t lh_offset = zip_data.size();
  size_t lh_size = sizeof(LH) + filename.size();
  zip_data.resize(lh_offset + lh_size, 0);
  auto* lh = reinterpret_cast<LH*>(&zip_data[lh_offset]);
  lh->signature();
  lh->version(10);
  lh->file_name(filename.data(), filename.size());

  // 2. Extra field payload containing an oversized payload_size
  uint8_t ef_buffer[8] = {0};
  auto* ef1 = reinterpret_cast<ExtraField*>(ef_buffer);
  ef1->signature(0x000d);
  ef1->payload_size(0);

  auto* ef2 = reinterpret_cast<ExtraField*>(ef_buffer + ef1->size());
  ef2->signature(0xdead);
  ef2->payload_size(0xf000);  // Malformed size exceeding extra field buffer

  // 3. Central Directory Header (CDH)
  size_t cdh_offset = zip_data.size();
  size_t cdh_size = sizeof(CDH) + filename.size() + sizeof(ef_buffer);
  zip_data.resize(cdh_offset + cdh_size, 0);
  auto* cdh = reinterpret_cast<CDH*>(&zip_data[cdh_offset]);
  cdh->signature();
  cdh->version(20);
  cdh->version_to_extract(10);
  cdh->local_header_offset32(lh_offset);
  cdh->file_name(filename.data(), filename.size());
  cdh->extra_fields(ef_buffer, sizeof(ef_buffer));

  // 4. End of Central Directory (EOCD)
  size_t ecd_offset = zip_data.size();
  zip_data.resize(ecd_offset + sizeof(ECD), 0);
  auto* ecd = reinterpret_cast<ECD*>(&zip_data[ecd_offset]);
  ecd->signature();
  ecd->this_disk_entries16(1);
  ecd->total_entries16(1);
  ecd->cen_size32(cdh_size);
  ecd->cen_offset32(cdh_offset);

  return zip_data;
}
