### Title
Liquidations can be griefed/DoS'd by front-running with dust repayments, forcing revert on stale `amountToRepay_` - ([contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool.liquidate` requires the caller-supplied `amountToRepay_` to satisfy exact conditions against the victim's current `DebtToken.balanceOf` and `DepositToken.balanceOf` (`AmountGreaterThanMaxLiquidable`, `RemainingDebtIsLowerThanTheFloor`, `AmountIsTooHigh` at `Pool.sol:567-585`). Any unprivileged actor holding synthetic tokens can front-run a liquidation with a dust-size `liquidate` call against the same victim, mutating the victim's debt and collateral balances so the liquidator's pre-computed amount reverts. There is no clamping — the protocol reverts instead of liquidating the maximum valid amount.

### Finding Description
`Pool.liquidate` performs three equality-sensitive checks against state that a frontrunner can shift arbitrarily cheaply:

```solidity
// contracts/Pool.sol:565-585
uint256 _debtTokenBalance = _debtToken.balanceOf(account_);

if (amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable) {
    revert AmountGreaterThanMaxLiquidable();
}

if (debtFloorInUsd > 0) {
    uint256 _newDebtInUsd = masterOracle().quoteTokenToUsd(
        address(syntheticToken_), _debtTokenBalance - amountToRepay_);
    if (_newDebtInUsd > 0 && _newDebtInUsd < debtFloorInUsd) {
        revert RemainingDebtIsLowerThanTheFloor();
    }
}

(_totalSeized, _toLiquidator, _fee) = quoteLiquidateOut(...);

if (_totalSeized > depositToken_.balanceOf(account_)) {
    revert AmountIsTooHigh();
}
```

Attack flow:

1. Victim's position becomes unhealthy. Bob (liquidator) calls `quoteLiquidateMax` off-chain and submits `liquidate(msToken, victim, amountMax, depositToken)` targeting a maximal liquidation (`amountToRepay_ = debt * maxLiquidable`).
2. Griefer (any EOA, or a dummy account controlled by the victim — `CanNotLiquidateOwnPosition` only blocks `msg.sender == account_`) front-runs with `liquidate(msToken, victim, 1 wei, depositToken)`. This succeeds because `1/debt <= maxLiquidable`, it burns 1 wei of the griefer's synth, repays 1 wei of the victim's debt, and seizes a dust amount of collateral.
3. Bob's transaction now executes with `debtTokenBalance` reduced by 1: `amountToRepay_.wadDiv(debt - 1)` exceeds `maxLiquidable` → reverts `AmountGreaterThanMaxLiquidable`. Alternatively, if Bob sized to seize all collateral, the dust seizure makes `_totalSeized > balanceOf` → `AmountIsTooHigh`, or the leftover debt lands below `debtFloorInUsd` → `RemainingDebtIsLowerThanTheFloor`.
4. Repeat each block. The griefer pays only a dust amount of synth per revert plus gas.

The same revert-on-stale-amount pattern exists in the reference JOJO finding; here the bounds are enforced in `Pool.sol:567`, `Pool.sol:577`, and `Pool.sol:584`.

### Impact Explanation
Liquidations can be continuously denied at dust cost, letting unhealthy positions persist and deteriorate into bad debt (protocol insolvency), or letting a victim delay their own liquidation indefinitely via a sybil account while waiting for collateral prices to move. This is a liveness break of the protocol's core solvency mechanism. Test coverage at `test/Pool.test.ts:783-789` confirms the revert path is exercised and intended behavior.

### Likelihood Explanation
- Fully permissionless: `liquidate` is `external` with only `whenNotShutdown`, `nonReentrant`, `onlyIfSyntheticTokenExists`, `onlyIfDepositTokenExists` modifiers — none block the attack.
- The griefer only needs to hold a dust amount of the pool's synthetic token (obtainable via `Pool.swap` or by minting from their own position) — no privileged role, no oracle manipulation, no governance action required.
- Rational liquidators compute `amountToRepay_` via `quoteLiquidateMax`/`quoteLiquidateIn` immediately before calling, so any interleaved liquidation invalidates their amount. On public-mempool chains (mainnet, Optimism, Base, BSC — all deployed per `deployments/`) this is trivially front-runnable.

### Recommendation
Inside `liquidate`, clamp `amountToRepay_` to the currently valid maximum instead of reverting:

```solidity
uint256 _maxRepay = _debtTokenBalance.wadMul(maxLiquidable);
if (amountToRepay_ > _maxRepay) amountToRepay_ = _maxRepay;
```

Similarly, cap `_totalSeized` to `depositToken_.balanceOf(account_)` by recomputing `amountToRepay_` via `quoteLiquidateIn`, and treat `RemainingDebtIsLowerThanTheFloor` as a signal to liquidate the full remaining debt rather than reverting. Emitting the actual executed amount lets liquidators remain robust to front-running.

### Proof of Concept
Foundry fork sketch against a deployed pool (e.g., mainnet `Pool`):

```solidity
function test_liquidationGriefing() public {
    // victim: unhealthy position (mock/oracle price drop)
    // bob reads max repayable:
    uint256 amountMax = pool.quoteLiquidateMax(msToken, victim, depositToken);

    // griefer front-runs with dust liquidation
    vm.prank(griefer); // holds >= 1 wei of msToken
    pool.liquidate(msToken, victim, 1, depositToken);

    // bob's tx now reverts
    vm.prank(bob);
    vm.expectRevert(AmountGreaterThanMaxLiquidable.selector);
    pool.liquidate(msToken, victim, amountMax, depositToken);
}
```

Repeatable every block: each new `quoteLiquidateMax` Bob computes can be invalidated again by another dust `liquidate`. The griefer's per-iteration cost is ~1 wei of synth plus gas; a `DebtToken.burn` that rounds principal down to zero may even make the griefing free modulo gas.
