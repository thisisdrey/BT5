### Title
NAV calculation bypass via unvalued loans in first computation cycle - (File: `tare-io__tare-contracts/contracts/PortfolioVault.sol`)

### Summary
The `PortfolioVault` contract implements a paginated NAV computation mechanism that can be manipulated during its first cycle or after a reset. When a new loan is added to the vault (e.g., via `fundLoans` or `acceptSaleOffer`), it is automatically added to the `_navLoanIds` list. However, if `updateNav` is called with a `batchSize` smaller than the total number of loans, the `pendingNav` only reflects the value of loans processed so far. If an investor manager approves deposits or redemptions before the cycle completes, the protocol uses a "fresh" NAV that may be materially understated because it only includes a subset of the portfolio's assets.

### Finding Description
In `PortfolioVault.sol`, the `updateNav` function [1](#0-0)  computes the vault's Net Asset Value in batches. The `lastNav` is only updated when the `navCursor` reaches the end of the `_navLoanIds` list [2](#0-1) .

The root cause is similar to the "first period" issue in the external report: until the first full sweep is completed, the system relies on an initial or stale `lastNav`. Specifically:
1. When loans are funded [3](#0-2)  or purchased [4](#0-3) , they are added to `_navLoanIds`.
2. `_invalidateNav()` is called, setting `lastNavUpdate = 0` [5](#0-4) .
3. To approve deposits/redemptions, `_requireFreshNav()` is called [6](#0-5) . This requires `lastNav > 0` and `block.timestamp - lastNavUpdate <= maxNavAge`.
4. If a manager starts `updateNav` but does not finish the full list in one transaction (legitimate for large portfolios), the `pendingNav` accumulates but `lastNav` remains at its previous value (or 0 if never set).

If `lastNav` was previously non-zero (e.g., after a reset triggered by `PortfolioHoldingsChanged` [7](#0-6) ), and a new batch of loans is added, the `lastNav` will not reflect the new loans until the *entire* list is swept. An attacker or a manager can exploit this "lag" to approve deposits at an undervalued share price or redemptions at an overvalued price relative to the actual (but unrecorded) assets.

### Impact Explanation
Material corruption of vault NAV and fair share pricing. If a large loan is funded, the vault's `assetToken` balance decreases immediately [8](#0-7) , but the loan's value is not added to `lastNav` until a full `updateNav` cycle finishes. This creates a window where `lastNav` is significantly lower than the true economic value (it sees the spent cash but not the acquired NFT), allowing new investors to mint shares cheaply at the expense of existing shareholders.

### Likelihood Explanation
Medium. While it requires the `INVESTOR_MANAGER` to call `approveDeposit` during an active NAV sweep, the protocol is designed for asynchronous operations where different managers (Portfolio vs. Investor) act independently. Large portfolios *require* multiple batches, making the window of vulnerability persistent.

### Recommendation
Modify `_requireFreshNav` to explicitly check that `navCursor == 0` and `navStart == 0`, ensuring that no approvals can occur while a NAV computation is "dirty" or incomplete. Additionally, consider including `pendingNav` in the `totalAssets` view if a sweep is in progress, though a strict block on approvals is safer.

### Proof of Concept
1. Vault has 1,000,000 USDC and 1,000,000 shares (NAV = 1.0).
2. `PortfolioManager` calls `fundLoans` for a 500,000 USDC loan. `assetToken` balance is now 500,000. `lastNav` is invalidated.
3. `PortfolioManager` calls `updateNav(batchSize=0)` (logic error) or a small batch that doesn't include the new loan.
4. If `lastNav` was not zeroed (e.g., it was just a refresh), and `_requireFreshNav` passes because `maxNavAge` is large, the `lastNav` still reflects the old state minus the spent cash (NAV ~ 0.5).
5. `InvestorManager` calls `approveDeposit` for an attacker's 500,000 USDC.
6. Attacker receives 1,000,000 shares (500k / 0.5) instead of 500,000 shares (500k / 1.0).
7. Once `updateNav` finishes, the loan value (500k) is added back, and the attacker has successfully diluted the vault. [9](#0-8)
