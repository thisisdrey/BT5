### Title
Uncapped Sapling proof verification inside `Manager`'s global lock lets peer-broadcast invalid shielded transactions stall block application - (File: `framework/src/main/java/org/tron/core/db/Manager.java`)

### Summary
`Manager.pushTransaction()` executes the full shielded-transaction actuator validation — including expensive Groth16 zk-SNARK proof verification — while holding the `Manager` instance's intrinsic lock (`synchronized (this)`), the same lock that `pushBlock()`/`processBlock()` acquires to apply blocks to the chain. The pending-shielded-transaction admission control (`shieldedTransInPendingMaxCounts`) is a count of *successfully accepted* shielded transactions, not a cost-based gate on verification attempts, so an unauthenticated peer can submit an unlimited stream of well-formed but cryptographically invalid `ShieldedTransferContract` transactions (cheap to produce, no valid spending key required) that each force one to three real Groth16 pairing checks before being rejected — all serialized behind the same lock that block application needs.

### Finding Description
`ShieldedTransferActuator.validate()` calls `checkProof()`, which performs full Sapling proof verification via `JLibrustzcash.librustzcashSaplingCheckSpend`/`CheckOutput`/`FinalCheck` — real elliptic-curve pairing operations — for every spend/receive description in the transaction: [1](#0-0)  and the actual pairing verification calls: [2](#0-1) 

Structural checks only bound the shape of the transaction (at most 1 spend, at most 2 receives) but do not check proof validity or fee sufficiency before the expensive pairing checks run — the arithmetic/fee check happens after the spend/output proof checks, inside the same `checkProof` call: [3](#0-2) [4](#0-3) 

This `validate()` is invoked from `Manager.processTransaction()`, which is itself called from `Manager.pushTransaction()` while holding the `Manager` object's intrinsic lock (`synchronized (this)`): [5](#0-4) 

The only admission gate for shielded transactions is a count of transactions that have already been *successfully* processed and added to `pendingTransactions`; the counter is incremented only after `processTransaction` succeeds: [6](#0-5)  Because the check `shieldedTransInPendingCounts.get() >= shieldedTransInPendingMaxCounts` runs before `processTransaction`, and the counter is never incremented for transactions that fail validation (invalid proof), the cap does nothing to limit the *rate* of proof-verification attempts — an attacker's rejected transactions never count against the cap, so they can be resubmitted indefinitely.

`Manager.pushBlock()` also serializes block application under `synchronized (this)`: [7](#0-6)  Since this is the same monitor acquired inside `pushTransaction`'s inner block, a peer that keeps the lock busy running Groth16 verification on invalid shielded transactions directly delays block push/apply on the same node — this is structurally identical to the reported Zcash bug class: expensive shielded-proof verification is not gated by a cheap cost check, and shares a resource (here, a lock rather than a queue) with block verification, allowing an unprivileged, unauthenticated peer to stall block processing.

### Impact Explanation
A node can be made to fall behind chain tip / stall block application by any peer capable of broadcasting transactions, without needing valid spending keys, real funds, or any special privilege — only a syntactically valid `ShieldedTransferContract` with canonically-sized (but invalid) Sapling proof material. This is a genuine availability impact on a node's ability to serve the chain (process blocks/transactions), matching the "API/node can no longer serve" bar for a valid finding, though it does not cause consensus faults, fund loss, or crashes.

### Likelihood Explanation
Reachable via the standard unauthenticated transaction broadcast path (`Wallet.broadcastTransaction` → `TronNetDelegate.pushTransaction` → `Manager.pushTransaction`), requiring only that `supportShieldedTransaction()` is enabled (a chain parameter, not attacker-controlled but commonly enabled on public networks that support the shielded pool feature) and a transparent-from address with sufficient TRX/fee balance to satisfy the pre-proof fee check for the "transparent → shielded" variant, or none at all for the fully-shielded ("shielded → shielded/transparent") variant where no upfront transparent balance is required at all (only the shielded nullifier/anchor checks, which are trivially satisfiable with garbage that still forces the pairing checks to run before failing). The attack is cheap to mount and repeatable indefinitely since rejected attempts are never counted against the pending cap.

### Recommendation
- Perform a cheap correctness/fee pre-check (e.g., verify the anchor/nullifier structure and require a minimum posted fee or bond) before invoking `JLibrustzcash` pairing verification in `ShieldedTransferActuator.checkProof()`.
- Move Sapling proof verification for mempool-sourced transactions off the critical `synchronized (this)` path used by block application, e.g., verify proofs outside the lock and only take the lock to commit already-validated results.
- Count/penalize proof-verification *attempts* (not just successes) toward `shieldedTransInPendingMaxCounts`, or apply a per-peer rate limit on invalid-proof shielded submissions, and consider banning/deprioritizing peers that repeatedly submit invalid shielded proofs.

### Proof of Concept
1. Enable `supportShieldedTransaction` on a test network.
2. Craft a `ShieldedTransferContract` with one `SpendDescription` (or fully-shielded receive-only transaction) containing a syntactically valid, canonically-sized but garbage/zero-filled Groth16 proof, anchor, nullifier, and signature fields (no real spending key needed since verification is expected to fail, only structural size/format must pass).
3. Broadcast a continuous stream of such transactions from an unauthenticated peer via the normal P2P transaction relay path (`TransactionsMsgHandler` → `TronNetDelegate.pushTransaction` → `Manager.pushTransaction`).
4. Observe that each transaction forces a real `librustzcashSaplingCheckSpend`/`CheckOutput`/`FinalCheck` invocation inside `Manager`'s `synchronized (this)` block before being rejected, and that rejected transactions never increment `shieldedTransInPendingCounts`, so the attack can be sustained indefinitely; measure block-application latency/backlog on the victim node during the flood versus baseline.
