Confirmed vulnerability. Analysis: `apply_evaluated` (used by `fold`/`map`/`filter` in `clarity/src/vm/functions/sequences.rs`) never calls `check_interpreter_resource_usage`, which only runs inside `eval()` [1](#0-0) . For `BuiltinKind::Native`/`Native205` step functions, `dispatch_args` calls `function.apply(args, ...)` directly without going through `eval()` [2](#0-1) , so the wall-clock `check_not_exceeded` is polled once when `eval()` is invoked on the outer `(fold ...)`/`(map ...)` expression, but not once per iteration inside the loop that repeatedly calls `apply_evaluated` [3](#0-2) . Since `fast-call-read` uses `LimitedCostTracker::new_free()` with no cost budget [4](#0-3) , an attacker who knows the `auth` secret can invoke a function that folds a large caller-supplied list with a cheap-per-element native builtin, causing the interpreter to run through the entire fold loop, with only the single check at fold-entry and none inside, bounded solely by list-size limits enforced by the type/serialization layer rather than by wall time.

### Title
Fast-call-read RPC endpoint allows wall-clock-budget overrun via `fold`/`map`/`filter` loops that bypass per-step time checks - (File: stackslib/src/net/api/fastcallreadonly.rs)

### Summary
`RPCFastCallReadOnlyRequestHandler` runs with `LimitedCostTracker::new_free()` and relies solely on a `Duration`-based `ResourceLimiter` polled inside `eval()` to bound execution time. Because `fold`/`map`/`filter` invoke their step function through `apply_evaluated`, which never calls `check_interpreter_resource_usage`, the time check is only made once at loop entry and not once per element, letting an attacker-supplied large list run the full loop before the time budget is re-checked.

### Finding Description
The claimed equality (compute cost bounded only by wall-time checks) holds, but the fault is sharper than stated: the check isn't merely "polled at coarse intervals" — it's structurally skipped inside the fold/map/filter loop body for native (non-`Special`) step functions. `special_fold`/`special_map_v400`/`special_filter` loop over sequence elements calling `apply_evaluated` per element [3](#0-2) . `apply_evaluated` dispatches native builtins directly via `dispatch_args` → `function.apply(...)` without a return trip through `eval()` [2](#0-1) , and only `eval()` calls `check_interpreter_resource_usage` [1](#0-0) . The `fast-call-read` handler sets `resource_limiter` (a wall-clock `Duration` limiter) as the *only* execution guard because cost tracking is fully disabled via `LimitedCostTracker::new_free()` [4](#0-3) . An attacker who knows the shared `auth` secret can POST to `/v3/contracts/fast-call-read/:principal/:contract/:function`, invoking a contract function that does `(fold my-native-step big-list 0)` where `big-list` is large (bounded only by `maximum_call_argument_size`/`read_only_call_max_mem_bytes`, not by cost-tracker list-length limits since those are also unenforced with a free cost tracker), causing the fold's inner loop to execute many iterations without any time-budget re-check until the loop finishes and control returns to `eval()`.

### Impact Explanation
This causes bounded compute DoS on the RPC-handling thread: a single crafted request can overrun `read_only_max_execution_time` because the interpreter is not rechecked inside the fold/map/filter loop, tying up the thread beyond the configured limit and matching the "bounded compute DoS on a read endpoint" category (High), since it is authenticated (post-auth) and does not crash the node.

### Likelihood Explanation
Requires knowledge of the `auth` secret (a precondition already acknowledged and accepted per the question framing — this is a known post-auth endpoint), a deployed contract or the ability to deploy one with a fold/map/filter over a large caller/contract-controlled list, and remote RPC reachability. Repeatable on every request; attacker cost is a single POST per overrun.

### Recommendation
Call `check_interpreter_resource_usage` (or equivalent time/memory check) inside the `fold`/`map`/`filter` iteration loops in `clarity/src/vm/functions/sequences.rs`, not only within `eval()`, so wall-clock budget is enforced per-element rather than only at loop entry/exit; alternatively, make `apply_evaluated` perform the same resource check `eval` does before dispatching to native functions.

### Proof of Concept
Rust test in `clarity/src/vm/functions/sequences.rs` (or a stackslib test invoking `RPCFastCallReadOnlyRequestHandler`): configure a `ResourceBudget::new().with_max_duration(Some(Duration::from_millis(X)))`, `start_tracking()`, install as `execution_resource_limiter` before executing `(fold + big-list 0)` with `big-list` sized so the fold loop alone takes longer than X once started (loop entry check passes then loop runs uninterrupted); assert that `Instant::now()` measured wall-clock time of the call exceeds X while `special_fold` returns `Ok` (no `ExecutionResourceBudgetExceeded`) — demonstrating the budget was exceeded without being caught until the next `eval()` call after the loop.
