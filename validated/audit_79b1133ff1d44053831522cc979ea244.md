## Finding

Based on the investigation, java-tron contains an authorization-bypass pattern structurally analogous to the FlaskBB CVE: **a transaction's per-item (contract) actions are all executed, but the owner/permission authorization is checked against only the first item in the list.**

### Title
Multi-Contract Transaction Authorization Bypass via Contract(0) Anchoring - (File: chainbase/src/main/java/org/tron/core/capsule/TransactionCapsule.java)

### Summary
`Transaction.raw` allows a `repeated Contract contract` list [1](#0-0) , and `ActuatorCreator.createActuator` iterates over **every** contract in that list, instantiating and later executing an actuator for each one [2](#0-1) . However, the transaction's cryptographic/permission authorization is only ever checked against `getContract(0)` — the first contract in the list — both in the instance method `TransactionCapsule.validateSignature` (explicitly commented "Do not support multi contracts in one transaction") [3](#0-2)  and in the static helper it calls, `TransactionCapsule.validateSignature(Transaction, ...)`, which reads `transaction.getRawData().getContractList().get(0)` to determine the owner/permission and validates signature weight only for that owner [4](#0-3) . The same "index 0" anchoring appears in `TransactionUtil.getTransactionSignWeight` [5](#0-4)  and `Wallet.getTransactionApprovedList` [6](#0-5) .

### Finding Description
This mirrors the FlaskBB bug class exactly: the report describes a batch request where "the permission check applied only to the first result" lets an attacker anchor with a permitted item and then execute unauthorized actions against unmoderated items in the same batch. In java-tron, the "batch" is the `contract` list inside a single `Transaction.raw`, and the "permission check applied only to the first" is `validateSignature`'s use of `getContract(0)` to derive the account/permission that must satisfy the signature-weight threshold. Meanwhile, `ActuatorCreator.createActuator` builds and executes an actuator for **all** contracts in the list [2](#0-1) , and individual actuators (e.g. `DelegateResourceActuator`, `AccountPermissionUpdateActuator`, etc.) validate business-logic constraints on their own `ownerAddress` field but do not re-verify that the transaction signer actually controls that `ownerAddress` — that authorization step is assumed to have already happened via the transaction-level signature check, which only covers contract(0).

### Impact Explanation
If multi-contract transactions with distinct owner addresses per contract reach execution, an attacker could craft one transaction where contract(0) is a cheap, legitimately-signed operation on their own account (satisfying `validateSignature`), while contract(1..n) set `ownerAddress` to a victim account for arbitrary contract types (transfers, resource delegation, freezing/unfreezing, votes, permission updates, etc.). Since actuators execute unconditionally once instantiated, and only contract(0)'s owner is authenticated, this could permit unauthorized account operations, and theft or freezing of victim funds/resources without their signature — a concrete "unauthorized account operation, theft or permanent freezing of funds" impact within the scope rules.

### Likelihood Explanation
**I could not fully confirm this within available search tools**, specifically whether some other validation path (e.g., in `Manager.pushTransaction`, transaction pool admission, or protobuf/consensus rules) rejects transactions containing more than one contract before actuators run. All evidence found (repeated comments "Do not support multi contracts in one transaction", and the contract(0)-only authorization logic) suggests the single-contract restriction is enforced only by convention/wallet client behavior, not by a hard validation check in the core actuator/transaction-processing pipeline that I was able to locate. This uncertainty is material: if such an enforcement check exists elsewhere and rejects `getContractCount() > 1` before `ActuatorCreator.createActuator` or `Manager.processTransaction` run, the vulnerability is not reachable.

### Recommendation
- Confirm whether `Transaction.raw.contract` is restricted to exactly one entry anywhere in the validation pipeline (e.g., transaction pool admission, `TransactionCapsule` validation prior to processing, or block application in `Manager`).
- If not restricted, either (a) enforce and reject `getContractCount() != 1` at transaction validation entry points, or (b) change `validateSignature`/`checkPermission` to authenticate the owner of **every** contract in the list against the signature set, not just index 0.
- Add regression tests asserting that a transaction with contract(0) belonging to signer A and contract(1) with `ownerAddress` = victim B is rejected during signature validation.

### Proof of Concept
Not executable without confirming the missing hard limit described above; conceptually:
1. Construct `Transaction.raw` with `contract[0]` = a valid, cheap contract owned/signed by attacker A (e.g., `TransferContract` of 0 TRX to self).
2. Append `contract[1]` = a high-value contract (e.g., `TransferContract`, `WithdrawBalanceContract`, or `DelegateResourceContract`) with `ownerAddress` set to victim B, without B's signature.
3. Sign the transaction only with A's key.
4. Broadcast via `Wallet.broadcastTransaction`; `validateSignature` only checks contract(0)'s owner (A) [3](#0-2) , then `ActuatorCreator.createActuator` builds actuators for both contracts and executes both [2](#0-1) , potentially executing contract[1] against victim B without B's authorization.   public static boolean validateSignature(Transaction transaction,
      byte[] hash, AccountStore accountStore, DynamicPropertiesStore dynamicPropertiesStore)
      throws PermissionException, SignatureException, SignatureFormatException {
    Transaction.Contract contract = transaction.getRawData().getContractList().get(0);
    int permissionId = contract.getPermissionId();
    byte[] owner = getOwner(contract);
    AccountCapsule account = accountStore.get(owner);
    Permission permission = null;
    if (account == null) {
      if (permissionId == 0) {
        permission = AccountCapsule.getDefaultPermission(ByteString.copyFrom(owner));
      }
      if (permissionId == 2) {
        permission = AccountCapsule
            .createDefaultActivePermission(ByteString.copyFrom(owner), dynamicPropertiesStore);
      }
    } else {
      permission = account.getPermissionById(permissionId);
    }
    if (permission == null) {
      throw new PermissionException("permission isn't exit");
    }
    checkPermission(permissionId, permission, contract);
    long weight = checkWeight(permission, transaction.getSignatureList(), hash, null);
    if (weight >= permission.getThreshold()) {
      return true;
    }
    return false;
  }

  public boolean validateSignature(AccountStore accountStore,
      DynamicPropertiesStore dynamicPropertiesStore) throws ValidateSignatureException {
    if (!isVerified) {
      //Do not support multi contracts in one transaction
      Transaction.Contract contract = this.getInstance().getRawData().getContract(0);
      if (contract.getType() != ContractType.ShieldedTransferContract) {
        validatePubSignature(accountStore, dynamicPropertiesStore);
      } else {  //ShieldedTransfer
        byte[] owner = getOwnerAddress();
        if (!ArrayUtils.isEmpty(owner)) { //transfer from transparent address
          validatePubSignature(accountStore, dynamicPropertiesStore);
        } else { //transfer from shielded address
          if (this.transaction.getSignatureCount() > 0) {
            throw new ValidateSignatureException("there should be no signatures signed by "
                    + "transparent address when transfer from shielded address");
          }
        }
      }
      isVerified = true;
    }
    return true;
  }
