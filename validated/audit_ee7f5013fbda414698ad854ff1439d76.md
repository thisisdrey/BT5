## Analysis Result [1](#0-0) 

### Title
Floating-point precision drift in the default (non-hardened) Bancor-formula Exchange processor allows sub-invariant drainage of `Exchange` reserves - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
`java-tron`'s built-in on-chain DEX (`ExchangeCreateContract`/`ExchangeInjectContract`/`ExchangeTransactionContract`) computes trade output using a Bancor-style relay-token formula implemented with IEEE-754 `double` arithmetic (`Math.pow`) in `ExchangeProcessor`, which is the **default** processor used unless the `ALLOW_HARDEN_EXCHANGE_CALCULATION` proposal has been activated by the committee. This is structurally analogous to the SKP report's root cause: an invariant/accounting check that is computed with an imprecise or manipulable arithmetic path, letting a caller extract value disproportionate to what they put in, one signed transaction at a time, fully reachable from an unprivileged account via `ExchangeTransactionActuator`.

### Finding Description
`ExchangeCapsule.transaction()` selects between two `Processor` implementations depending on the `hardenedCalc` flag, which is itself gated by `allowHarden()` → `dynamicStore.allowHardenExchangeCalculation()`: [2](#0-1) 

The default (`hardenedCalc == false`) path is `ExchangeProcessor`, which computes the relay-supply issuance and redemption using `double` math and `Math.pow` with exponents `0.0005` / `2000.0`: [3](#0-2) 

Unlike the hardened `SafeExchangeProcessor`, which uses `BigDecimal` with fixed scale/rounding and explicit overflow checks (`StrictMathWrapper.addExact`/`subtractExact`) and enforces `newFirstTokenBalance/newSecondTokenBalance >= 0`: [4](#0-3) [5](#0-4) 

The default `ExchangeProcessor` path has none of these safeguards — its long-cast truncation (`(long) issuedSupply`, `(long) exchangeBalance`) and its two-step double-precision formula (`exchangeToSupply` then `exchangeFromSupply`) can drift from the true Bancor invariant, especially at extreme size ratios (very large `sellTokenQuant` relative to `firstTokenBalance`/`secondTokenBalance`, or repeated small trades that each round in the attacker's favor). This is the same bug class as the SKP report's core claim — the invariant/"K-check" that is supposed to bound value extraction is evaluated through an approximate or stale computation instead of an exact one, permitting extraction of more value than was deposited.

`ExchangeTransactionActuator.execute()` calls this unguarded default path directly and immediately mutates account balances and the on-chain `ExchangeCapsule` balances based on its result, with no invariant re-check on the actual token balances after the trade: [6](#0-5) 

The only guard in `doValidate()` is a floor check (`anotherTokenQuant < tokenExpected`) supplied by the caller themselves, which does not protect the pool — it protects the trader from slippage, not the protocol from precision-drift drainage: [7](#0-6) 

### Impact Explanation
Any unprivileged account holding TRX/TRC10 assets and knowledge of an existing `Exchange` pool can broadcast a sequence of `ExchangeTransactionContract` transactions. If the double-precision Bancor computation in `ExchangeProcessor` returns an `anotherTokenQuant` that is systematically larger than the value implied by the exact/closed-form invariant (particularly for skewed reserve ratios or large single trades near `getExchangeBalanceLimit()`), an attacker can repeatedly buy from and sell back into the same pool to accumulate a real, unbacked surplus of the counter-asset, draining honest LPs/injectors of the `Exchange`. This falls under "unbacked balance / theft of funds" impact criteria since state is mutated directly in `AccountStore`/`ExchangeStore` with no reconciliation against a ground-truth invariant.

### Likelihood Explanation
This requires no special privilege — only that an `Exchange` exists (created via `ExchangeCreateActuator`, itself permissionless) with reserves, and that the node still runs with `allowHardenExchangeCalculation() == false` (the default; the hardened path requires an on-chain committee proposal to activate). Exploitation is a sequence of ordinary signed transactions, matching the "single signed transaction / contract call" scope, without needing any privileged role, malicious SR/witness collusion, or network-level manipulation.

### Recommendation
- Verify whether `allowHardenExchangeCalculation` is enabled by default on mainnet; if not, prioritize activation of the hardened `SafeExchangeProcessor` path network-wide.
- Even under the hardened path, add an explicit end-to-end invariant check (`firstTokenBalance * secondTokenBalance` before vs. after, adjusted for fees) in `ExchangeTransactionActuator`/`ExchangeInjectActuator` so any processor implementation is bounded by a hard product-invariant assertion, not solely trusted output values.
- Add fuzz/property tests comparing `ExchangeProcessor` (double-based) output against `SafeExchangeProcessor` (BigDecimal-based) across skewed reserve ratios and large trade sizes to quantify and bound the divergence before relying on it in production.

### Proof of Concept
Conceptual (values would need on-chain reserve inspection to instantiate precisely):
1. Attacker calls `ExchangeCreateActuator`/uses an existing pool with reserves `(A, B)`.
2. Attacker submits `ExchangeTransactionContract` selling a `tokenQuant` chosen (via off-chain simulation of `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply`) to land at a reserve ratio where `double`/`Math.pow` rounding yields an `anotherTokenQuant` output measurably above the value implied by the true Bancor closed form.
3. Attacker repeats the trade (sell back, then sell again) across multiple transactions/blocks, each time realizing a small but nonzero rounding surplus, analogous to the SKP report's "cached/approximate invariant lets extraction exceed true value" pattern.
4. Over many iterations, the accumulated surplus constitutes an unbacked, unauthorized transfer of value out of the pool's other participants (LP injectors), without ever needing owner/whitelist privileges — unlike the SKP case, which required an insider-set whitelist, this java-tron analog is fully permissionless.

Note: I was not able to determine, from the indexed code alone, the exact default on-chain value of `allowHardenExchangeCalculation` (i.e., whether mainnet already activated the hardened path via a historical committee proposal) or to run numeric simulations of the double-precision drift magnitude — confirming actual real-world exploitability (versus a bounded, negligible rounding error) would require running `ExchangeProcessor` vs `SafeExchangeProcessor` against real historical `Exchange` reserve pairs, which requires execution access beyond static code search.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
