### Title
Permissionless `initialize()` in vault contracts allows front-running/DoS of DAO's atomic vault-initialization proposal - (File: `mainnet/contracts/vault/v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`)

### Summary
`initialize()` on every vault contract is a `define-public` function guarded only by a one-time `initialized` boolean flag, with no restriction on which principal may call it. Any ordinary account can call it directly and permanently flip `initialized` to `true` before the DAO's own initialization proposal executes.

### Finding Description
Each vault's `initialize()` function only checks that it hasn't run before: [1](#0-0) 

There is no `check-dao-auth` or any caller check comparable to other admin-gated vault functions such as `set-cap-supply` or `set-authorized-contract`, which explicitly call `check-dao-auth`: [2](#0-1) [3](#0-2) 

The intended deployment flow bundles `set-cap-supply`/`set-cap-debt` and `initialize()` for every vault into a single DAO proposal executed atomically by `dao-executor`: [4](#0-3) 

If, however, vault caps are set in an earlier separate governance action (a legitimate multi-step production deployment) before the DAO's dedicated `initialize()` proposal is submitted, any principal can race the DAO's transaction and call `.vault-X.initialize()` first. Because `deposit` (called internally by `initialize`) requires `cap-supply` to be non-zero via `(asserts! (<= (+ current-assets amount) CAP-SUPPLY) ERR-SUPPLY-CAP-EXCEEDED)`, the front-run only succeeds once cap-supply has already been configured to a non-zero value: [5](#0-4) 

Once an attacker's call succeeds, `initialized` is permanently `true` and `ERR-ALREADY-INITIALIZED` is returned to any subsequent caller, including the DAO's own proposal: [6](#0-5) 

Because the DAO's initialization proposal wraps every step in `try!` (see `proposal-init-vaults.clar` / `proposal-protocol-init.clar` / mainnet `v0-init.clar`), a single reverted `initialize` call aborts the whole atomic proposal transaction — including cap configuration and `set-authorized-contract` calls for every other vault bundled in that proposal: [7](#0-6) 

This differs from the original report's "become admin" impact — there is no admin/owner state set by `initialize()` here (LP shares are minted to a hardcoded `NULL-ADDRESS`, not the caller) — but the unprotected, front-runnable state transition still lets an unprivileged principal permanently block/derail the DAO's legitimate initialization transaction for that vault and any other steps bundled with it.

### Impact Explanation
Front-running `initialize()` does not grant the attacker funds or privileges (shares go to `NULL-ADDRESS`), so this is not a theft vector. It is a griefing/DoS vector: it forces the DAO's atomic initialization proposal to revert, so vault caps, `set-authorized-contract` (market authorization), and any egroup/registration steps bundled in that same proposal are never applied to any vault touched by the proposal, until governance detects the failure and redeploys a corrected proposal that skips the already-initialized vault. Until then, the affected vault(s) cannot be authorized for the market, so deposits/borrows relying on that authorization are unavailable — this constitutes temporary freezing of funds/functionality for the vault's intended users.

### Likelihood Explanation
Exploitation requires: (1) the attacker to observe a pending DAO transaction calling `initialize()` (or independently knowing cap-supply has already been set to non-zero for a not-yet-initialized vault) and (2) the attacker to already hold at least `MINIMUM-LIQUIDITY` (u1000, scaled by decimals) of the vault's underlying token, which they permanently lose (sent to the vault, shares minted to `NULL-ADDRESS`). This makes it a costly, self-sacrificing griefing attack rather than a profit-motivated one, limiting realistic likelihood, but it is technically always exploitable by any funded principal during the specific deployment window where caps are set before `initialize()` executes.

### Recommendation
Restrict `initialize()` to `check-dao-auth` (or equivalent deployer/DAO-only check) the same way other administrative vault functions (`set-cap-supply`, `set-authorized-contract`, etc.) are protected, so only the DAO executor can trigger the one-time initialization step.

### Proof of Concept
1. DAO executes a governance action that sets `cap-supply` for `vault-sbtc` to a non-zero value (a legitimate, separate step from the bundled `proposal-init-vaults.clar` seen in this codebase, but plausible in a staged mainnet rollout).
2. Before the DAO's `initialize()`-calling proposal transaction is mined, an attacker who owns ≥ `MINIMUM-LIQUIDITY` units of the vault's underlying asset submits `(contract-call? .v0-vault-sbtc initialize)` directly with a higher fee.
3. The attacker's transaction succeeds: `initialized` is set to `true`, `MINIMUM-LIQUIDITY` shares are minted to `NULL-ADDRESS`, and the attacker's `MINIMUM-LIQUIDITY` underlying tokens are transferred into the vault.
4. The DAO's subsequently mined proposal transaction, which also calls `(contract-call? .v0-vault-sbtc initialize)` as one of several `try!`-wrapped steps, hits `ERR-ALREADY-INITIALIZED` and the entire proposal transaction reverts, rolling back cap configuration and `set-authorized-contract` calls for all vaults bundled in that proposal.
5. The market/vault remain unauthorized and unusable until governance manually detects the failure and redeploys a corrected proposal omitting the already-initialized vault's `initialize` call.
