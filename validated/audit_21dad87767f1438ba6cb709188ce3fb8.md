### Title
Instantaneous toggling of `ALLOW_STRICT_MATH` / `ALLOW_HARDEN_EXCHANGE_CALCULATION` produces a discontinuous re-pricing of the Bancor-style TRX/TRC10 `Exchange` pool that lets any transaction sender sandwich the switch and drain LP funds - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java`)

### Summary
The Curve/Boot Finance bug lets an attacker sandwich a governance-approved, instantly-applied change to a pricing precision parameter of an AMM pool, extracting value from the pool at the expense of liquidity providers. java-tron's Bancor-formula `Exchange` (TRX/TRC10 liquidity pools created via `ExchangeCreateContract`, injected/withdrawn via `ExchangeInjectActuator`/`ExchangeWithdrawActuator`) has the same structural weakness: the arithmetic used to compute the exchange rate is selected by two committee-controlled dynamic parameters, `ALLOW_STRICT_MATH` and `ALLOW_HARDEN_EXCHANGE_CALCULATION`, which are applied atomically at a maintenance-cycle boundary and change the computed swap output for identical pool reserves and identical trade size.

### Finding Description
`ExchangeCapsule.transaction()` selects the pricing processor based on two booleans read at swap time: [1](#0-0) 

`ExchangeTransactionActuator` (reachable by any signed `ExchangeTransactionContract` from any account) fetches these flags live from `DynamicPropertiesStore` on every execution, both during `validate()` and `execute()`: [2](#0-1) [3](#0-2) 

These flags are not gradually ramped; they are set instantly the moment a committee proposal reaches maintenance, exactly like the reported `stopRampTargetPrice` in the external report: [4](#0-3) [5](#0-4) 

The two pricing engines that flip between produce materially different swap outputs for the exact same reserves/trade size, as shown by the project's own regression test that intentionally asserts the two modes diverge: [6](#0-5) 

This mirrors the root cause in the external report: a governance-triggered instantaneous change to the internal pricing/precision math of an AMM-like pool (`ExchangeProcessor`'s double-based `Maths.pow` vs `SafeExchangeProcessor`'s `BigDecimal`-based `pow`) that holds real user-deposited liquidity (`Exchange.firstTokenBalance`/`secondTokenBalance`), rather than a smooth, ramped transition.

### Impact Explanation
Proposal maintenance times are deterministic and publicly known in advance (`getNextMaintenanceTime()`), so any unprivileged account can pre-build and broadcast an `ExchangeTransactionContract` timed to execute in the very first block after the flag flips. Because the computed `buyTokenQuant` for the identical pool reserves changes discontinuously between the legacy and hardened/strict-math processors, an attacker can extract the price differential from the pool's real TRX/TRC10 reserves at the expense of the liquidity providers who funded the pool via `ExchangeInjectActuator`, resulting in a genuine, unbacked value transfer out of pool balances — a direct funds-loss impact for LPs, analogous to the medium-severity finding in the source report.

### Likelihood Explanation
Exploitation requires only submitting an ordinary, already-supported transaction type (`ExchangeTransactionContract`) at a known, public point in time (maintenance cycle boundary) — no special privilege, no contract deployment, and no reliance on malicious SR/witness behavior. The only precondition is that a committee proposal toggling `ALLOW_STRICT_MATH` or `ALLOW_HARDEN_EXCHANGE_CALCULATION` be approved, which is a normal, expected governance action (both flags already exist and are exercised in the codebase's own tests), making the trigger realistic rather than hypothetical.

### Recommendation
Avoid instantaneous, pool-wide repricing when toggling exchange-calculation modes. Options include: (1) freezing/pausing `ExchangeTransactionActuator` swaps for one maintenance window around any change to `ALLOW_STRICT_MATH`/`ALLOW_HARDEN_EXCHANGE_CALCULATION`, (2) applying the new calculation mode only to pools created after the switch rather than retroactively to all existing pools, or (3) computing both engines' outputs and bounding the delta so a single toggle cannot shift the effective rate beyond a small, LP-protecting tolerance.

### Proof of Concept
1. Assume a proposal to set `ALLOW_HARDEN_EXCHANGE_CALCULATION=1` (or `ALLOW_STRICT_MATH=1`) has accumulated sufficient SR approvals and is scheduled to take effect at the next `nextMaintenanceTime`.
2. An attacker observes the pending proposal (public on-chain data) and prepares an `ExchangeTransactionContract` swap against a target `Exchange` pool.
3. The attacker submits the swap transaction to be included in the first block after maintenance, when `dynamicStore.allowStrictMath()`/`allowHarden()` flips.
4. `ExchangeCapsule.transaction()` computes `buyTokenQuant` using the new processor (`SafeExchangeProcessor` vs `ExchangeProcessor`), which — per `ExchangeProcessorTest.testStrictMath` (`framework/src/test/java/org/tron/core/capsule/utils/ExchangeProcessorTest.java:272-280`) — yields a different result than the pre-toggle processor for identical reserves/quant.
5. The attacker immediately reverses the trade in a follow-up transaction, capturing the discrepancy as risk-free profit extracted from the pool's LP-funded reserves.
