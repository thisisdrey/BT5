Audit Report

## Title
Missing delegatecall guard on `System` precompile's `terminate()` lets an attacker-controlled callee destroy the top-level caller's contract and redirect its funds - (File: `substrate/frame/revive/src/precompiles/builtin/system.rs`)

## Summary
`System::call` in `substrate/frame/revive/src/precompiles/builtin/system.rs` dispatches `ISystemCalls::terminate` to `env.terminate_caller(&h160)` with only an `env.is_read_only()` check guarding it; there is no `is_delegate_call()` check as exists in the sibling `Storage` precompile and in the `ERC20`, `asset-conversion`, `vesting`, and `pallet-xcm` precompiles. [1](#0-0)  Because SELFDESTRUCT-equivalent operations executed via `DELEGATECALL` act on the storage/account context of the frame that issued the outer delegatecall (the well-known EVM "delegatecall self-destruct" hazard, historically exploited in the Parity multisig incident referenced in the PoC), an attacker-controlled intermediary reached via delegatecall can invoke precompile `0x900`'s `terminate` to destroy the top-level victim contract and redirect its balance to an attacker-chosen `beneficiary`.

## Finding Description
The `System` precompile's `call` function only rejects `terminate` when `env.is_read_only()` is true; every other guard present is unrelated to delegatecall provenance. [2](#0-1)  The `terminate` arm charges weight and then unconditionally calls `env.terminate_caller(&h160)` with the attacker-supplied `beneficiary`, deleting the executing frame's contract code and transferring its balance. [3](#0-2)  By contrast, the `Storage` precompile explicitly requires `env.is_delegate_call()` to be true (opposite direction, but demonstrating the codebase is aware `is_delegate_call()` state must be checked contextually), and the `ERC20`/`asset-conversion`/`vesting`/`pallet-xcm` precompiles explicitly *deny* delegatecall via `PrecompileDelegateDenied` because those precompiles derive caller identity from `env.caller()`, which is misleading during delegatecall. [4](#0-3) [5](#0-4) [6](#0-5)  The PR that added those guards documents the exact underlying invariant being violated for `System::terminate`: delegatecall into a precompile lets a malicious contract execute privileged logic in the caller's own frame/storage context, with no legitimate use case for doing so. [7](#0-6) 

I confirmed via `grep_search` that `terminate_caller` and `is_delegate_call` are both defined in `substrate/frame/revive/src/exec.rs`, but I was not able to fully inspect their implementations in the available session to independently verify the exact frame/account semantics under nested delegatecall chains (i.e., whether `terminate_caller` truly operates on the outermost caller's account rather than the immediate precompile-invoking contract's account). This is a real limitation on full verification, though the code as written clearly omits any delegatecall check that the four sibling precompiles apply for the same class of risk, and the semantics described are consistent with standard EVM SELFDESTRUCT-under-DELEGATECALL behavior.

## Impact Explanation
If confirmed, this allows an unprivileged attacker whose code is reached via delegatecall (e.g., a proxy/diamond/plugin pattern) to destroy the calling (victim) contract's account and redirect its full native-token balance to an attacker-chosen `beneficiary`, which is a direct, unbacked theft of contract-held funds with no privileged actor required — matching the "theft ... or unbacked mint or unlock" / "permanent user-fund ... lock" impact gate for `paritytech/polkadot-sdk`.

## Likelihood Explanation
Exploitability only requires a common EVM contract-composition pattern (delegatecall-based proxy/library/plugin) where a victim contract delegatecalls into code an attacker can influence; no malicious validator, collator, relayer, or governance action is needed. The same guard was already recognized as necessary and applied to four sibling precompiles in this codebase, indicating this risk class is acknowledged, and the `System` precompile at address `0x900` appears to have been missed.

## Recommendation
Add a delegatecall check to `System::call`, at minimum for the `terminate` branch (and review other caller-frame-mutating branches), mirroring the `PrecompileDelegateDenied` guard used by `ERC20`, `asset-conversion`, `vesting`, and `pallet-xcm` precompiles:
```rust
frame_support::ensure!(
    !env.is_delegate_call(),
    crate::Error::<T>::PrecompileDelegateDenied,
);
```
placed at the top of the `terminate` arm (or at the top of `System::call`) in `substrate/frame/revive/src/precompiles/builtin/system.rs`.

## Proof of Concept
1. Deploy `Victim`, a contract that at some point performs `address(Module).delegatecall(data)` where `Module` is a facet/library address that can be pointed at attacker-supplied code (upgrade path, configurable module registry, or attacker-deployed unvetted module).
2. Attacker's `Module` code, when reached, issues `address(0x900).delegatecall(abi.encodeWithSelector(ISystem.terminate.selector, attackerAddress))`.
3. Because `System::call` performs no `is_delegate_call()` check, `terminate_caller` executes against `Victim`'s own frame/account state (unchanged through the delegatecall chain), per [3](#0-2) .
4. `Victim`'s contract code is removed and its full native balance is transferred to `attackerAddress`.
5. Write a Rust integration test in `substrate/frame/revive/src/tests.rs` deploying a delegatecall chain analogous to the `Storage` precompile's delegatecall tests, asserting that `terminate` executed through a nested delegatecall destroys the outer caller's account and moves its balance to an attacker-controlled beneficiary, and that no `PrecompileDelegateDenied` error is raised (unlike the sibling precompiles).
