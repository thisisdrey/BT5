Confirmed: the HTTP `POST /v2/stackerdb/:address/:contract/chunks` endpoint takes `contract_identifier` purely from the URL path [1](#0-0) , and neither the signed digest nor the storage/validation logic binds the signature to that specific contract.

### Title
StackerDB chunk signatures are not bound to their target contract, enabling cross-StackerDB signature-wrapping replay - (File: libstackerdb/src/libstackerdb.rs)

### Summary
`SlotMetadata::auth_digest()` computes the signed digest from only `slot_id`, `slot_version`, and `data_hash` [2](#0-1) . The `QualifiedContractIdentifier` (i.e., which StackerDB the chunk belongs to) is never part of what is signed. Both the write-path (`StackerDBTx::try_replace_chunk`) and the read-side validation (`PeerNetwork::validate_received_chunk`) verify the signature only against the slot owner recorded for the *target* contract, never checking that the chunk was actually produced for that contract [3](#0-2) [4](#0-3) .

### Finding Description
A signer's signature over `(slot_id, slot_version, data_hash)` is portable across any StackerDB contract in which that same address happens to own the same `slot_id`. This is common by design: the Stacks boot contracts allocate the *same* signer set and slot ordering across multiple message-type StackerDB contracts for a reward cycle (`signers-0-0`, `signers-0-1`, ... `signers-0-N`, all pulling from the same `stackerdb-signer-slots-0`/`-1` list) [5](#0-4) , so signer address X owns slot `i` identically in `signers-0-0`, `signers-0-1`, etc. [6](#0-5) .

Because the target contract for a POST comes solely from the URL path and is never folded into the signed digest, an attacker (any unprivileged remote peer that observed a legitimately-signed chunk broadcast for contract A, e.g. via P2P gossip or the public read endpoint) can resubmit the exact same signed bytes to a *different* StackerDB contract B (e.g. a different `MessageSlotID`'s contract) that has independent per-contract version counters [7](#0-6) . As long as B's current slot version for that slot is lower than the replayed chunk's version — trivially true for a low-traffic slot/contract — `try_replace_chunk` will accept and store it: `BadSigner` is never triggered because the recovered address genuinely matches the recorded slot owner in contract B.

This breaks the intended equality "a chunk accepted into contract A's slot store was signed *for* contract A" — the signature wraps across contract boundaries, analogous to the SAML signature-wrapping bug class where a signature that authenticates one structure is reused to authenticate an attacker-chosen different structure.

### Impact Explanation
This lets an unprivileged remote peer force wrong-context, signer-authored bytes into a StackerDB slot that consumers (miners, signer coordinators, monitors) will parse as belonging to a different message type/contract than the signer intended — e.g. `stacks-node/src/nakamoto_node/stackerdb_listener.rs` reads chunks keyed only by slot id from the `StateMachineUpdate` contract and deserializes them assuming that schema [8](#0-7) . Feeding it a replayed chunk that was really signed for a `BlockResponse` slot causes parse/type confusion for the consuming logic, and more generally it is an unauthenticated write into a StackerDB namespace the signer never authorized for that content, satisfying "unauthenticated/unauthorized write to state or StackerDB."

### Likelihood Explanation
Requires only observing one legitimately broadcast chunk (trivial — StackerDB chunks are gossiped/relayed to all replicating peers and are also readable via the public GET chunk RPC) and replaying it to a sibling contract with a compatible/lower version counter. No secret key, no privileged role, and no bandwidth flooding is needed.

### Recommendation
Include the target `QualifiedContractIdentifier` (or a domain-separation tag derived from it) in `SlotMetadata::auth_digest()` so a signature is only valid for the specific StackerDB it was created for, and re-verify on both the HTTP POST path and the P2P push/sync validation paths.

### Proof of Concept
1. Observe (via gossip or `GET /v2/stackerdb/:addr/:contract_A/:slot/chunk`) a chunk validly signed by signer X for `slot_id=3`, `slot_version=5` on contract `signers-0-0`.
2. Identify contract `signers-0-1` (or any sibling message-type contract) where signer X also owns `slot_id=3` (guaranteed by shared slot allocation in `signers.clar`) and whose current stored version for slot 3 is `< 5`.
3. POST the identical JSON body (same `sig`, `slot_id`, `slot_version`, `data`) to `/v2/stackerdb/:addr/signers-0-1/chunks`.
4. `try_replace_chunk` recovers the same address X, matching the slot owner recorded for contract `signers-0-1`, passes the version check, and stores the chunk — despite it never having been signed for `signers-0-1`.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)

            ))?;

            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));

                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
