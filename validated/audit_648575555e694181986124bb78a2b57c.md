### Title
`LinkRepositoryToObjectPool` performs no relationship/ownership check between the target repository and the object pool, allowing cross-repository object exposure via alternates - (File: `internal/gitaly/service/objectpool/link.go`)

### Summary
The `ContributionNft::mint` report's root cause is a state-changing entry point that accepts caller-supplied identifiers (which object/parent/dataset to associate) without verifying the caller is authorized or that the supplied relationship is legitimate, letting downstream logic (`ServiceNft`, `AgentRewardV2`, `Minter`) silently trust a bogus linkage. The Gitaly analog is `LinkRepositoryToObjectPool`, which accepts an arbitrary `repository` and an arbitrary `object_pool` in the same RPC request and links them together without ever validating that the repository is actually derived from (a fork of) that pool.

### Finding Description
`LinkRepositoryToObjectPool` only validates that the `repository` field is a well-formed, existing repository via `s.locator.ValidateRepository` and that the pool reference resolves to a valid pool directory via `s.poolForRequest`/`objectpool.FromProto`: [1](#0-0) 

Neither of these checks verifies any actual relationship between `repository` and `object_pool` — e.g. that `repository` was created from the pool's origin, that it belongs to the same project/namespace, or that it lives in a permitted storage/partition relative to the pool. The pool-resolution helper only validates the pool path shape and repository existence, not caller authorization or repo-to-pool ownership: [2](#0-1) 

The actual linking logic in `objectpool.Link` then unconditionally writes the pool's `objects` directory into the target repository's `objects/info/alternates` file: [3](#0-2) 

Once linked, Git will read (and, through packing/quarantine interplay, potentially serve) any object present in the pool as if it belonged to the linked repository, because alternates are a Git-level, not access-control-level, mechanism, as documented: [4](#0-3) 

By contrast, the neighboring `FetchIntoObjectPool` RPC at least enforces that `origin` and `object_pool` share the same storage name before doing any pool operations: [5](#0-4) 

`LinkRepositoryToObjectPool` has no equivalent cross-check at all — it will happily link a repository on one storage/namespace to a pool that has no prior relationship with it, exactly mirroring the external report's pattern: an unauthenticated/unauthorized relationship (`parentId`/`datasetId` in the Solidity report, `object_pool`/`repository` pairing here) is trusted blindly and propagated into object/impact/reward state (here: object visibility via alternates) without verifying legitimacy.

### Impact Explanation
If this RPC is reachable with attacker-influenced parameters (e.g., a compromised or over-privileged caller that can specify both `repository` and `object_pool` — such as a forking/import workflow where either field is derived from user-controlled project identifiers), an attacker can splice their own repository's alternates to point at an unrelated, potentially private pool. This grants the attacker's repository transparent read access to every object contained in that pool (`doc/object_pools.md` describes pool objects as shared and reachable via alternates), a cross-repository object-access / private-object-disclosure primitive. It can also corrupt housekeeping invariants (dangling-object protections, bitmap assumptions) for the victim pool, as `Link` also strips the newly linked member's own bitmaps and assumes a legitimate producer/consumer relationship: [6](#0-5) 

### Likelihood Explanation
The likelihood depends entirely on whether any caller with just gRPC access to `ObjectPoolService` (rather than full storage admin) can freely choose arbitrary `repository` and `object_pool` values in one call — the RPC surface itself performs no ownership check, so likelihood is bounded only by whatever caller/token restricts access to this admin-plane service in the deployment. Because Gitaly's model generally assumes only the trusted GitLab Rails layer invokes `ObjectPoolService`, this is not exploitable by an anonymous end user directly, but it is a real gap relative to the more careful cross-check pattern used by `FetchIntoObjectPool`, and any bug or confusable-identifier issue upstream (e.g., in how Rails derives `object_pool`/`repository` from user-controlled project or fork slugs) would be directly amplified by this missing Gitaly-side guard.

### Recommendation
Add an explicit relationship/ownership check inside `LinkRepositoryToObjectPool` (and in `objectpool.Link`) mirroring `validateFetchIntoObjectPoolRequest`'s storage-name check, but strengthened to verify that the repository is actually a recognized member/origin of the pool (e.g., via metadata such as pool membership records or partition assignment) before writing the alternates file, rather than trusting the RPC caller to have supplied a correct pairing.

### Proof of Concept
1. As a caller with access to `ObjectPoolService` but for two unrelated repositories A (not a fork of, or previously linked to, pool P) and pool P (privately containing sensitive objects), invoke:
   ```
   LinkRepositoryToObjectPool(repository=A, object_pool=P)
   ```
2. `s.locator.ValidateRepository` succeeds because A is a real repository; `poolForRequest`/`objectpool.FromProto` succeeds because P is a real, valid pool directory — no check ties A to P.
3. `objectpool.Link` writes P's `objects` path into A's `objects/info/alternates`, per `internal/git/objectpool/link.go` lines 54-66.
4. Any subsequent read RPC against repository A (e.g. `GetBlob`, `TreeEntry`, `IsAncestor`) will transparently resolve objects that exist only in pool P, exfiltrating pool P's object contents through repository A.

```go
func (s *server) LinkRepositoryToObjectPool(ctx context.Context, req *gitalypb.LinkRepositoryToObjectPoolRequest) (*gitalypb.LinkRepositoryToObjectPoolResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	pool, err := s.poolForRequest(ctx, req)
	if err != nil {
		return nil, err
	}

	repo := s.localRepoFactory.Build(repository)

	if err := pool.Link(ctx, repo); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	return &gitalypb.LinkRepositoryToObjectPoolResponse{}, nil
```

```go
func (s *server) poolForRequest(ctx context.Context, req PoolRequest) (*objectpool.ObjectPool, error) {
	pool, err := objectpool.FromProto(ctx, s.logger, s.locator, s.gitCmdFactory, s.catfileCache, s.txManager, s.housekeepingManager, req.GetObjectPool())
	if err != nil {
		if errors.Is(err, objectpool.ErrInvalidPoolDir) {
			return nil, errInvalidPoolDir
		}

		if errors.Is(err, objectpool.ErrInvalidPoolRepository) {
			return nil, structerr.NewFailedPrecondition("%w", err)
		}

		return nil, structerr.NewInternal("%w", err)
	}

	return pool, nil
}
```

```go
// Link will link the given repository to the object pool. This is done by writing the object pool's
// path relative to the repository into the repository's "alternates" file. This does not trigger
// deduplication, which is the responsibility of the caller.
func Link(ctx context.Context, pool, repo *localrepo.Repo, txManager transaction.Manager) (returnedErr error) {
	altPath, err := repo.InfoAlternatesPath(ctx)
	if err != nil {
		return err
	}

	expectedRelPath, err := getRelativeObjectPath(ctx, pool, repo)
	if err != nil {
		return err
	}

	linked, err := linkedToRepository(ctx, pool, repo)
	if err != nil {
		return err
	}

	if linked {
		// When the repository is already linked to the repository, cast a vote to ensure the
		// repository is consistent with the other replicas.
		if err := transaction.VoteOnContext(ctx, txManager, voting.VoteFromData([]byte("repository linked")), voting.Synchronized); err != nil {
			return fmt.Errorf("vote on linked repository: %w", err)
		}

		return nil
	}

	alternatesWriter, err := safe.NewLockingFileWriter(altPath)
	if err != nil {
		return fmt.Errorf("creating alternates writer: %w", err)
	}
	defer func() {
		if err := alternatesWriter.Close(); err != nil && returnedErr == nil {
			returnedErr = fmt.Errorf("closing alternates writer: %w", err)
		}
	}()

	if _, err := io.WriteString(alternatesWriter, expectedRelPath); err != nil {
		return fmt.Errorf("writing alternates: %w", err)
	}
```

```go
// removeMemberBitmaps removes packfile bitmaps from the member
// repository that just joined the pool. If Git finds two packfiles with
// bitmaps it will print a warning, which is visible to the end user
// during a Git clone. Our goal is to avoid that warning. In normal
// operation, the next 'git gc' or 'git repack -ad' on the member
// repository will remove its local bitmap file. In other words the
// situation we eventually converge to is that the pool may have a bitmap
// but none of its members will. With removeMemberBitmaps we try to
// change "eventually" to "immediately", so that users won't see the
// warning. https://gitlab.com/gitlab-org/gitaly/issues/1728
func removeMemberBitmaps(ctx context.Context, pool *localrepo.Repo, repo *localrepo.Repo) error {
	poolPath, err := pool.Path(ctx)
	if err != nil {
		return err
	}

	poolBitmaps, err := getBitmaps(poolPath)
	if err != nil {
		return err
	}
	if len(poolBitmaps) == 0 {
		return nil
	}

	repoPath, err := repo.Path(ctx)
	if err != nil {
		return err
	}

	memberBitmaps, err := getBitmaps(repoPath)
	if err != nil {
		return err
	}
	if len(memberBitmaps) == 0 {
		return nil
	}
```

```go
func validateFetchIntoObjectPoolRequest(req *gitalypb.FetchIntoObjectPoolRequest) error {
	if req.GetOrigin() == nil {
		return errors.New("origin is empty")
	}

	if req.GetObjectPool() == nil {
		return errors.New("object pool is empty")
	}

	originRepository, poolRepository := req.GetOrigin(), req.GetObjectPool().GetRepository()

	if originRepository.GetStorageName() != poolRepository.GetStorageName() {
		return errors.New("origin has different storage than object pool")
	}

	return nil
}
```
