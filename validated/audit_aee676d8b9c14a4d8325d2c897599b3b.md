## Analysis

The CVE's bug class is "iterating a collection while a helper/removal path can invalidate it mid-walk," causing a crash on stale/dangling elements. The closest reachable analog in java-tron is in the TVM's native vote-witness precompile. [1](#0-0) 

`VoteWitnessProcessor.execute()` builds `Iterator<Protocol.Vote> iterator = param.getVotes().iterator();` and, while walking the list, calls `iterator.remove()` whenever a vote entry has `voteCount == 0`: [2](#0-1) 

This is reached from `Program.java`'s vote-related native contract call path (used by the `vote()` TVM precompile), i.e. directly from an unprivileged contract call/transaction that a caller can construct with an arbitrary vote list, including entries with `voteCount == 0`.

### Concern
`param.getVotes()` in `VoteWitnessParam` wraps the votes that originate from a smart-contract call's decoded parameters. If this list (or the underlying collection returned) is backed by an immutable/fixed-size list (e.g., built via `Collections.unmodifiableList`, `Arrays.asList`, or a protobuf-derived immutable list — I could not fully confirm the concrete backing type of `VoteWitnessParam.getVotes()` within the available index, so this is not fully proven), then `iterator.remove()` would throw `UnsupportedOperationException`. If it is a live view onto another structure that gets mutated/rebuilt elsewhere concurrently or reused across calls, removal during iteration could produce inconsistent/`ConcurrentModificationException` behavior. Either failure mode is directly triggerable by any address invoking the vote-witness native contract with a crafted vote (`voteCount = 0`) — a single unprivileged transaction/contract call — and would throw an uncaught runtime exception during block application, since this exception type is not one of the caught `ContractExeException`/`ArithmeticException` handlers in the method.

I was not able to fully verify the exact backing list type of `param.getVotes()` (I could not inspect the complete `VoteWitnessParam.java` and the `Program.java` call sites that construct it within the tool budget available), so I cannot definitively prove this throws in all code paths — this is the main uncertainty in this finding.

### Title
Unsafe `Iterator.remove()` on Vote List in TVM Vote-Witness Native Contract May Crash Block Processing - (File: actuator/src/main/java/org/tron/core/vm/nativecontract/VoteWitnessProcessor.java)

### Summary
`VoteWitnessProcessor.execute()` iterates over `param.getVotes()` and calls `iterator.remove()` to drop zero-count votes while still inside the loop. If the underlying list backing `param.getVotes()` does not support structural mutation via its iterator (common for lists derived from protobuf message fields or wrapped as unmodifiable), this throws `UnsupportedOperationException`, an unhandled runtime exception in this method's `try/catch` (which only catches `ArithmeticException`).

### Finding Description
The vote-witness native contract, invoked from TVM contract execution, decodes a caller-supplied list of votes into a `VoteWitnessParam`. `execute()` walks this list with an `Iterator`, calling `iterator.remove()` for entries where `voteCount == 0`: [3](#0-2) 
Unlike the legacy `VoteWitnessActuator.validate()` path, which only reads the vote list with a plain iterator and never mutates it, this native-contract path attempts an in-place structural removal. This mirrors the CVE's bug class: iterating and mutating the same collection mid-walk without verifying the mutation is safe/expected, risking an uncontrolled exception or inconsistent state if invariants about the collection's mutability are violated.

### Impact Explanation
An unhandled `RuntimeException` (e.g., `UnsupportedOperationException`) thrown out of `VoteWitnessProcessor.execute()` during block application would propagate up through the actuator/TVM execution path. Depending on how the TVM call frame catches exceptions, this could at minimum cause the containing contract call to fail unexpectedly (denial of a specific vote feature), or in the worst case escape expected exception handling during `processTransaction`/`processBlock` in `Manager`, causing node instability or a crash while applying a block — a node-crash/halt impact.

### Likelihood Explanation
Likelihood depends entirely on the concrete list implementation returned by `param.getVotes()`, which I could not fully confirm in this pass. If it is backed by a mutable `ArrayList` copy, no bug exists. If it is an unmodifiable/fixed-size view, any contract call to the vote-witness precompile with at least one zero-`voteCount` vote entry triggers it deterministically, and any address can construct such a call.

### Recommendation
Verify the concrete type backing `VoteWitnessParam.getVotes()` (trace how it's populated in `Program.java`/decoding logic for the native vote contract). If it is not guaranteed to be a mutable, iterator-remove-safe list, replace the in-place `iterator.remove()` pattern with a filter into a new mutable list (as done safely in `UnfreezeBalanceV2Processor.unfreezeExpire()`, which explicitly copies into a `Lists.newArrayList()` before iterating and removing).

### Proof of Concept
Construct a `TriggerSmartContract` call that invokes the vote-witness native contract with a votes array containing an entry where `voteCount = 0`, submitted as a normal transaction. During `VoteWitnessProcessor.execute()`, the iterator removal is attempted on `param.getVotes()`; if the backing list is immutable/unmodifiable, this throws `UnsupportedOperationException`, which is not caught by the surrounding `catch (ArithmeticException e)` block and propagates as an unhandled runtime exception during transaction/block processing. (Full confirmation requires inspecting `VoteWitnessParam`'s construction path, which was not completely available within this investigation's scope.)
