### Title
Unbounded, Unlimited Stdin Buffering and Hashing in PackObjectsHookWithSidechannel Occurs Before Concurrency-Limit Admission Check - (File: `internal/gitaly/service/hook/pack_objects.go`)

### Summary
`PackObjectsHookWithSidechannel` is the RPC that `gitaly-hooks`/`git-upload-pack` invokes for every fetch/clone to actually run `git-pack-objects`. Before the per-key (`remote_ip`) concurrency limiter is ever consulted, the handler unconditionally buffers the *entire* client-controlled stdin payload (the negotiated `want`/`have` list `git-upload-pack` forwards) to an unlinked temp file and computes a SHA-256 hash over it to build the pack cache key. Only after this expensive, unbounded I/O/CPU work is `packObjectsLimiter.Limit()` invoked to gate the actual `git-pack-objects` subprocess. This is structurally the same ordering defect as the reported analog: expensive, attacker-reachable work is performed before the cheap admission/policy check that is supposed to bound concurrency and resource usage.

### Finding Description
The call chain is: [1](#0-0) 

`PackObjectsHookWithSidechannel` validates the repository and parses `args`, then calls `s.packObjectsHook(ctx, req, args, c, c)`, passing the sidechannel `c` (a bidirectional connection carrying `git-upload-pack`'s negotiated stdin for `git-pack-objects`) directly as `stdinReader`.

Inside `packObjectsHook`: [2](#0-1) 

`s.computeCacheKey(ctx, req, stdinReader)` is invoked **first**, unconditionally, before `s.packObjectsCache.Fetch(...)` (which is what eventually calls `runPackObjectsLimited` → `s.packObjectsLimiter.Limit(...)`).

`computeCacheKey` calls `bufferStdin`: [3](#0-2) [4](#0-3) 

`bufferStdin` creates a temp file, `os.Remove`s it immediately (making it an unlinked/anonymous file), and does `io.Copy(f, io.TeeReader(r, h))` — i.e., it reads the *entire* stdin stream to completion, writes it to disk, and simultaneously hashes it with SHA-256, with **no size cap and no concurrency gate**. Only once this full buffering/hashing completes does control return to `packObjectsHook`, which then calls `s.packObjectsCache.Fetch`, and only on a cache miss does `runPackObjectsLimited` finally acquire the `packObjectsLimiter` token keyed by `remote_ip`: [5](#0-4) 

The proto comment for `remote_ip` explicitly documents the intended design — that this field is "used as the key for concurrency limiting **before** we trigger git-pack-objects command": [6](#0-5) 

But the implementation only limits the `git-pack-objects` subprocess itself, not the stdin buffering/hashing step that precedes admission — exactly mirroring the reported bug class where the expensive, synchronous work (there: FFI script verification; here: full-stream disk buffering + SHA-256 hashing) runs ahead of the "cheap" policy/limiter check meant to bound concurrent expensive work.

### Impact Explanation
Because `computeCacheKey`/`bufferStdin` run for every `PackObjectsHookWithSidechannel` invocation regardless of the concurrency limiter state, an attacker who can initiate many concurrent fetch/clone negotiations (an ordinary, even anonymous, git client if anonymous read access is permitted) can force Gitaly to:
- Buffer arbitrarily large stdin payloads to disk with no size limit, consuming disk I/O and space (temp files, unlinked but still backed by the filesystem until closed).
- Perform SHA-256 hashing over that entire payload synchronously on the request-handling goroutine.

This work happens **before** the `packObjectsLimiter` (keyed per remote IP, with configurable `MaxConcurrency`/`MaxQueueSize`) has any chance to reject or queue the request. The concurrency limiter therefore does not actually bound the number of concurrent expensive buffering/hashing operations in flight — only the number of concurrent `git-pack-objects` subprocess executions. A burst of concurrent fetch requests from a single or few IPs (or many IPs, since the per-key limiter is IP-scoped) can drive unbounded concurrent disk I/O and CPU hashing work, degrading Gitaly's responsiveness for other repository operations — a resource-exhaustion/DoS condition consistent with the "High" severity class of the reported analog (verification-adjacent work occurring ahead of the admission gate meant to bound it).

### Likelihood Explanation
Reaching this code path requires only performing a normal `git fetch`/`git clone` against a Gitaly-served repository (via `git-upload-pack`, which internally invokes `PackObjectsHookWithSidechannel`); no special privilege beyond ordinary read/fetch access is needed, and multiple concurrent fetches from a scripted client are trivial to generate. The vulnerable ordering (buffer/hash-then-limit) is unconditional in the code — it is not behind a feature flag — so likelihood of the resource-exhaustion condition being triggered under sustained concurrent load is high.

### Recommendation
Move the concurrency-limiting admission check ahead of `computeCacheKey`/`bufferStdin`, or otherwise impose a cap on the total bytes read/buffered during `bufferStdin` before consulting the cache/limiter, so that the SHA-256 hashing and full-stream disk buffering are bounded by the same admission control that governs `git-pack-objects` execution. Consider streaming the hash computation with a bounded buffer and applying the concurrency limiter around the entire `packObjectsHook` request (including cache-key computation), not just around the final `git-pack-objects` subprocess invocation.

### Proof of Concept
1. Configure `pack_objects_limiting` with a small `max_concurrency`/`max_per_repo` and a `max_queue_size`/`max_queue_wait`.
2. From an unprivileged git client, issue many concurrent `git fetch`/`git clone` operations against a repository served by Gitaly, each negotiating a distinct large `want`/`have` list (to avoid cache hits and to maximize stdin size).
3. Observe that Gitaly performs full stdin buffering to disk and SHA-256 hashing (`computeCacheKey`/`bufferStdin` in `internal/gitaly/service/hook/pack_objects.go:117-145,342-367`) for every concurrent request — this work is not gated by `packObjectsLimiter`, which is only applied later in `runPackObjectsLimited` (`pack_objects.go:176-212`) — allowing the number of concurrent buffering/hashing operations to exceed the configured concurrency limit and consume disk/CPU resources disproportionate to the configured admission policy.

func (s *server) computeCacheKey(ctx context.Context, req *gitalypb.PackObjectsHookWithSidechannelRequest, stdinReader io.Reader) (string, io.ReadCloser, error) {
	cacheHash := sha256.New()

	repository := req.GetRepository()
	if tx := storage.ExtractTransaction(ctx); tx != nil {
		// The cache uses the requests as the keys. As the request's repository in the RPC handler has been rewritten
		// to point to the transaction's repository, the handler sees each request as different even if they point to
		// the same repository. Restore the original request to ensure identical requests get the same key.
		repository = tx.OriginalRepository(req.GetRepository())
	}

	cacheKeyPrefix, err := protojson.Marshal(&gitalypb.PackObjectsHookWithSidechannelRequest{
		Repository:  repository,
		Args:        req.GetArgs(),
		GitProtocol: req.GetGitProtocol(),
	})
	if err != nil {
		return "", nil, err
	}
	if _, err := cacheHash.Write(cacheKeyPrefix); err != nil {
		return "", nil, err
	}
	stdin, err := bufferStdin(stdinReader, cacheHash)
	if err != nil {
		return "", nil, err
	}
	cacheKey := hex.EncodeToString(cacheHash.Sum(nil))
	return cacheKey, stdin, nil
}

func bufferStdin(r io.Reader, h hash.Hash) (_ io.ReadCloser, err error) {
	f, err := os.CreateTemp("", "PackObjectsHook-stdin")
	if err != nil {
		return nil, err
	}
	defer func() {
		if err != nil {
			f.Close()
		}
	}()

	if err := os.Remove(f.Name()); err != nil {
		return nil, err
	}

	_, err = io.Copy(f, io.TeeReader(r, h))
	if err != nil {
		return nil, err
	}

	if _, err := f.Seek(0, io.SeekStart); err != nil {
		return nil, err
	}

	return f, nil
}
