### Title
Unpriced repository creation enables unbounded storage-bloat DoS via CreateRepository/CreateFork/CreateObjectPool - ([File: internal/gitaly/repoutil/create.go])

### Summary
Gitaly enforces no per-caller, per-repository, or per-storage quota on the number of repositories that a valid client can create. Any authenticated caller able to invoke `CreateRepository`, `CreateFork`, `CreateRepositoryFromBundle`, or `CreateObjectPool` can repeat the call indefinitely to create an unbounded number of tiny repositories at near-zero marginal cost, exhausting storage/inode capacity and inflating directory-walk/metadata overhead for the whole Gitaly node — the same "dust account" storage-bloat pattern described in the source report, where a near-zero minimum cost per unit of state allows unbounded state growth.

### Finding Description
`repoutil.Create` is the common code path used by all repository-creating RPCs. It validates only that the target path does not already exist and then unconditionally creates the repository directory structure (`git init --bare`, refs, config, HEAD, hooks) — there is no check on how many repositories the caller (or the storage as a whole) already owns, and no disk-quota or count-based admission check before proceeding: [1](#0-0) 

The RPC handlers built on top of this (`CreateRepository`, `CreateFork`, `CreateRepositoryFromBundle`, `CreateObjectPool`) are declared as ordinary `MUTATOR` RPCs with no built-in resource limiting: [2](#0-1) 

The only backpressure mechanism Gitaly ships is optional, operator-configured per-RPC concurrency limiting keyed by repository relative path (`LimitConcurrencyByRepo`). Because each repository-creation call targets a distinct, not-yet-existing relative path, this mechanism cannot throttle the *number* of distinct repositories being created — it only limits concurrent operations on the *same* already-existing path: [3](#0-2) 

Gitaly's own documentation confirms that request rate limiting (which would be the natural mitigation for this class of abuse) was intentionally removed and never replaced with a repository-count or storage-quota based limit: [4](#0-3) 

Each created repository carries small but non-zero fixed storage overhead (refs, config, HEAD, directory metadata) — as shown by the repository size tests, an "empty" repository is not actually zero bytes: [5](#0-4) 

There is no analog in Gitaly to Substrate's `ExistentialDeposit`: nothing rejects, reaps, or otherwise cost-limits creation of "dust" repositories. An actor who can drive repository creation (e.g. via project/fork creation flows that ultimately invoke these Gitaly RPCs) can therefore create effectively unlimited numbers of tiny repositories, exactly mirroring the reported bug class of "near-zero cost per unit of persisted state, with no floor to prevent unbounded state growth."

### Impact Explanation
Unbounded repository creation directly bloats on-disk storage (each repo requires its own directory tree, refs, config file, hooks symlink, and now KV/transaction metadata under WAL-enabled storage), consumes inodes, and increases the cost of storage-wide operations such as `RepositoryCounter.countRepositories`'s filesystem walk and disk-usage reporting: [6](#0-5) 

At scale this degrades storage-wide operations (walks, backups, replication, `DiskStatistics`) for all repositories/tenants sharing the storage, and can exhaust disk space or inodes, producing a denial-of-service condition for the whole Gitaly node — analogous to how bloat-attack dust accounts degrade a shared chain state for all users.

### Likelihood Explanation
Likelihood is high: `CreateRepository`/`CreateFork`/`CreateRepositoryFromBundle`/`CreateObjectPool` are standard, routinely used mutator RPCs reachable by any client holding valid Gitaly credentials (which in GitLab's architecture is effectively any user able to create projects/forks through the normal application flow). No configuration exists by default to cap total repository count per caller or per storage, and the only available concurrency limiter does not address this vector since each new repository has a unique path.

### Recommendation
- Introduce an explicit, enforced ceiling on the number of repositories (or on aggregate/incremental storage usage) that a given namespace/token/caller may create, checked inside `repoutil.Create` (or its callers) before the repository directory is materialized.
- Consider tracking per-caller or per-storage repository counts (the existing `RepositoryCounter` infrastructure could be extended) and rejecting further `CreateRepository`/`CreateFork`/`CreateObjectPool`/`CreateRepositoryFromBundle` calls once a configurable quota is exceeded.
- Expose this quota as Gitaly server configuration (similar to `[cgroups.repositories]` limits) so operators can bound worst-case storage/inode growth from repository-creation RPCs, complementing (not replacing) any quota enforcement done at the GitLab application layer.

### Proof of Concept
1. Obtain a valid Gitaly auth token (the same token used by the ordinary GitLab-Rails/Workhorse client for normal project/fork creation).
2. Repeatedly invoke `RepositoryService.CreateRepository` (or `CreateFork`/`CreateRepositoryFromBundle`/`CreateObjectPool`) with a freshly generated `RelativePath` each time.
3. Because `repoutil.Create` at [7](#0-6)  only checks for path collision and performs no count/quota check, and the concurrency limiter in [3](#0-2)  is keyed per unique repository path (so distinct new paths never contend), every call succeeds.
4. Loop indefinitely to create an arbitrarily large number of minimal repositories, each consuming disk inodes/blocks, degrading storage-wide walks (`RepositoryCounter`) and eventually exhausting the storage volume.
