### Title
Stale `ReceivedData`/`PostponedReceipt` rows survive `DeleteAccount`, letting a resumed receipt execute against a recreated account with pre-deletion input data - (File: core/primitives/src/trie_key.rs)

### Summary
`remove_account`, invoked by `action_delete_account`, deletes `Account`, `ContractCode`, `AccessKey`/gas-key, and `ContractData` rows for the deleted account, but never removes `TrieKey::ReceivedData`, `TrieKey::PostponedReceipt`, `TrieKey::PostponedReceiptId`, or `TrieKey::PendingDataCount` rows keyed by that `account_id` [2](#0-1) . If a postponed `ActionReceipt` with multiple `input_data_ids` is still awaiting some data when the account is deleted and later recreated under the same id, the runtime's data-receipt processing logic in `process_receipt`/`process_action_receipt` will treat pre-deletion `ReceivedData` as valid input and execute the old postponed receipt's actions against the new account incarnation.

### Finding Description
The postponed-receipt mechanism persists three kinds of trie rows scoped to `receiver_id`: `ReceivedData` (arrived data payloads), `PostponedReceiptId`/`PendingDataCount` (bookkeeping for missing inputs), and `PostponedReceipt` (the full pending `ActionReceipt`) [4](#0-3) . When a `DataReceipt` arrives, `process_receipt` writes `ReceivedData{receiver_id, data_id}` unconditionally and, if all pending inputs are satisfied, fetches and executes the stored `PostponedReceipt` for that `receiver_id` [5](#0-4) .

`action_delete_account` calls `remove_account`, which only clears `Account`, `ContractCode`, access keys/gas-key nonces, and `ContractData` [6](#0-5) [2](#0-1) . It does not touch `ReceivedData`, `PostponedReceipt`, `PostponedReceiptId`, or `PendingDataCount` rows for that account, nor does the size check that gates deletion (`MAX_ACCOUNT_DELETION_STORAGE_USAGE`) account for them, since `StorageComputer::process_record` explicitly excludes `PostponedReceipt`/`ReceivedData` from storage-usage accounting [1](#0-0) . Subsequently, `action_create_account` simply installs a fresh zero-balance `Account` without clearing any leftover receipt-processing rows under the same `account_id` [3](#0-2) .

Exploit flow (self-controlled contract account A, which can be a subaccount later recreated by the same or different logic/keys via the parent's `CreateAccount` capability):
1. A's own contract issues cross-contract promises joined with `promise_and` and a callback on itself, generating an `ActionReceipt` to A with two `input_data_ids`; since neither is yet available, `process_action_receipt` stores `PostponedReceipt`, `PendingDataCount=2`, and two `PostponedReceiptId` entries.
2. One `DataReceipt` arrives; `process_receipt` writes `ReceivedData{A, data_id1}`, decrements `PendingDataCount` to 1, and removes only the matching `PostponedReceiptId`.
3. Before the second `DataReceipt` arrives, a `DeleteAccount(A)` receipt executes (self-authorized, `actor_id == account_id` per `check_actor_permissions`) [7](#0-6) ; `remove_account` wipes the account/keys/contract but leaves `ReceivedData{A, data_id1}`, `PostponedReceipt{A, receipt_id}`, and `PendingDataCount{A, receipt_id}` intact.
4. `CreateAccount(A)` recreates the account (new contract/keys deployed).
5. The second `DataReceipt(data_id2)` arrives; `has_received_data` is false for `data_id2`, so `PostponedReceiptId{A, data_id2}` (never removed) is matched, `PendingDataCount` reaches 0, and the OLD stored `PostponedReceipt` is fetched and executed via `apply_action_receipt` against the freshly recreated account A, consuming the stale `ReceivedData{A, data_id1}` that predates the deletion.

None of the existing checks (nonce, access-key permission, storage-staking, `MAX_ACCOUNT_DELETION_STORAGE_USAGE`) inspect or block on these receipt-processing rows, because they are deliberately excluded from storage-usage accounting and from `remove_account`'s cleanup scope.

### Impact Explanation
This breaks the "input data delivered to one incarnation of an account should not silently feed a receipt executing against a different incarnation" invariant, matching the "authorization escalation across accounts or promises" bounty category. If the resumed action's arguments/logic (e.g., a self-callback reading `promise_result()` to decide a transfer amount or authorization) depend on the pre-deletion `ReceivedData` payload, the new account incarnation's contract logic executes with attacker-influenced/replayed data it never legitimately received for its current lifetime, potentially enabling unauthorized fund movement or state corruption scoped to that account.

### Likelihood Explanation
Preconditions are fully attacker-controlled and require no privileged access: deploy a wasm contract on account A, schedule a `promise_and`-joined self-callback with two or more sub-promises, delete the account after only some sub-promise results have resolved but before the callback fires, then recreate the account (same predecessor can always recreate its own subaccount) and let the remaining `DataReceipt` complete the chain. Timing control (deleting between arrival of partial vs. complete input data) requires careful receipt scheduling across blocks but is achievable by controlling gas/complexity of the outstanding cross-contract calls. The bug is deterministically reproducible in a unit/runtime test since it does not depend on any race with other validators.

### Recommendation
In `remove_account` (or in `action_delete_account` before/after calling it), also iterate and remove all `ReceivedData`, `PostponedReceipt`, `PostponedReceiptId`, and `PendingDataCount` trie rows keyed by the deleted `account_id`, mirroring the existing access-key/contract-data cleanup loops. Alternatively, block `DeleteAccount` while any `PostponedReceipt`/pending input-data rows exist for the account, similar to the existing `DeleteAccountStaking` check.

### Proof of Concept
Runtime/test-loop test plan:
1. Deploy `rs_contract` (or a custom contract) to account A with a method that issues two cross-contract calls joined via `promise_and`, then a self-callback reading both `promise_result(0)` and `promise_result(1)` to compute a transfer amount/authorization decision.
2. Trigger the call; allow only one of the two cross-contract calls to resolve (e.g., make the second callee's receipt land in a later block or delay it via gas budget), leaving A's callback `ActionReceipt` postponed with `PendingDataCount = 1`.
3. In the same or next block, submit `DeleteAccount(A)` from A itself (self-call), followed by `CreateAccount(A)` with new keys/contract deployed under the same id.
4. Allow the second, delayed `DataReceipt` to arrive.
5. Assert that the callback executes against the recreated account A (e.g., observe a state mutation or transfer effected on the new account) and that its result incorporates the first (pre-deletion) `ReceivedData` value — proving stale data leaked across account incarnations. Additionally assert directly at the trie level, via `has_received_data`/`get_postponed_receipt` on `TrieUpdate`, that `ReceivedData{A, data_id1}` and `PostponedReceipt{A, receipt_id}` are still present immediately after the `DeleteAccount` receipt is applied, before `CreateAccount`.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
