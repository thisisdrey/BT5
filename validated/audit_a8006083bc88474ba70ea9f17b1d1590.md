Based on my research, the strongest analog to this bug class in java-tron is in `ExchangeWithdrawActuator.execute`, which recomputes both AMM pool balances from a creator-controlled `ExchangeWithdrawContract` request and applies `subtractExact` on values derived from a division that a market maker (the exchange creator/liquidity owner) does not fully control across two independent calls — mirroring the original bug's pattern of "accumulator minus a growth-derived value can exceed the accumulator and revert, blocking legitimate fund recovery."

### Title
Exchange pool withdrawal can be permanently blocked by `ArithmeticException` from `subtractExact` due to precision drift between `validate()` and `execute()` - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java)

### Summary
`ExchangeWithdrawActuator.execute` recomputes `anotherTokenQuant` using `BigInteger` exact division (`longValueExact()`, floor-division semantics), while `doValidate()` computed the same quantity using `BigDecimal.divideToIntegralValue` with 4-decimal `remainder` precision tolerance checks. Both paths then feed the result into `subtractExact(firstTokenBalance, tokenQuant)` / `subtractExact(secondTokenBalance, anotherTokenQuant)`. Because validation only checks `firstTokenBalance < tokenQuant || secondTokenBalance < anotherTokenQuant` using a value computed by a *different* rounding method than the one used in `execute()`, a value can pass validation and then cause `subtractExact` to throw `ArithmeticException` in `execute()` if the two computed `anotherTokenQuant` values ever diverge and the second one exceeds the pool balance.

### Finding Description
The exchange withdraw contract type is user-broadcastable by any account that is the recorded creator of an `Exchange`/`ExchangeV2` liquidity pool (`ExchangeWithdrawContract`), reachable directly through `ExchangeWithdrawActuator`. The pattern mirrors the reported Sherlock issue: an accumulator-style subtraction (`secondTokenBalance - anotherTokenQuant`) is performed using `subtractExact`, which throws instead of gracefully failing, on values whose derivation is duplicated across two code paths (`doValidate()` at [1](#0-0)  and `execute()` at [2](#0-1) ) using different arithmetic libraries (`BigDecimal.divideToIntegralValue` with a tolerance/rounding check vs. plain `BigInteger` division). If the underlying pool balances are mutated between validation and execution by a preceding transaction/actuator in the same block (e.g., an `ExchangeTransactionActuator` trade against the same pool), the `execute()`-time recomputed `anotherTokenQuant` can differ from the validated value and exceed the live pool balance, causing `subtractExact` in [3](#0-2)  to throw `ArithmeticException`, which is caught and converted into a `ContractExeException` at [4](#0-3) , reverting the transaction.

### Impact Explanation
Unlike the original report where an underflow permanently prevents *any* future call to the same function, here the effect is transaction-level and race-condition dependent: it can cause a legitimate liquidity creator's withdrawal transaction to fail non-deterministically depending on transaction ordering within a block, but it does not appear to leave the pool in an unrecoverable state — the creator can retry with updated parameters. This is a lower-severity denial-of-service/griefing analog rather than a fund-freezing one, since I could not confirm a state where the pool becomes permanently un-withdrawable (there is no persistent accumulator like `accLoanRatePerSeconds` in java-tron's exchange model; balances are recomputed fresh each call).

### Likelihood Explanation
Requires precise pool-balance manipulation via a preceding trade in the same block and specific rounding-boundary conditions between the two divison methods; I was not able to construct or confirm a concrete boundary value inducing a mismatch given available context, so likelihood is uncertain.

### Recommendation
Use the identical arithmetic (same rounding/precision method) in both `doValidate()` and `execute()` for `ExchangeWithdrawActuator`, or recompute-and-revalidate `anotherTokenQuant` inside `execute()` before calling `subtractExact`, so any precision drift results in a controlled `ContractValidateException` rather than relying on an uncaught arithmetic exception path.

### Proof of Concept
Not independently verified against the runtime; based on static code reading of `ExchangeWithdrawActuator.doValidate()` ( [1](#0-0) ) versus `execute()` ( [2](#0-1) ).

---

**Note on confidence:** I could not find a java-tron analog that reproduces the exact severity of the original report (a permanent, unrecoverable underflow blocking an "emergency"/liquidation-equivalent withdrawal path with no workaround). The closest structurally similar patterns I found — `UnfreezeBalanceV2Actuator`/`UnDelegateResourceActuator` (guarded with `<` checks before subtraction) and `ExchangeTransactionActuator`/`ExchangeCapsule.transaction` (guarded with post-condition `< 0` checks in hardened mode) — are defensively coded and do not exhibit the same unconditional-revert-on-underflow pattern as the reported Solidity bug. Given the strict validation rules requiring High/Medium+Critical impact with concrete permanent fund freezing, and that I could not confirm the `ExchangeWithdrawActuator` mismatch leads to permanent (rather than transient/retriable) fund lock, this finding should be treated as a low-confidence, best-effort analog rather than a confirmed high-severity vulnerability.
