### Title
Fixed-window stream throttling allows ~2x `max_streams_per_throttling_interval` burst at window boundary - (File: streamer/src/nonblocking/stream_throttle.rs)

### Summary
`ConnectionStreamCounter::reset_throttling_params_if_needed` implements a fixed (non-sliding) window rate limiter that resets `stream_count` to 0 only once `STREAM_THROTTLING_INTERVAL` (100ms) has elapsed since the last reset. An attacker controlling stream timing on a single QUIC connection can send a full quota of streams just before the window resets and another full quota immediately after, achieving close to `2 * max_streams_per_throttling_interval` accepted streams within a short real-time span straddling the boundary.

### Finding Description
`throttle_stream` in [1](#0-0)  is invoked (per-connection) via `streamer/src/nonblocking/swqos.rs` to decide whether to sleep/throttle a newly opened stream. It calls `reset_throttling_params_if_needed`, which only resets `stream_count` and `last_throttling_instant` when `duration_since(last_throttling_instant) > STREAM_THROTTLING_INTERVAL`: [2](#0-1) 

Because the window boundary is a hard reset point rather than a sliding accounting mechanism, an attacker on a single connection can:
1. Open `max_streams_per_throttling_interval` streams just before `last_throttling_instant + STREAM_THROTTLING_INTERVAL` elapses (all counted in window N, none throttled since `stream_count` stays below the limit until the last one).
2. Immediately after the reset fires (triggered by the next stream check), open another `max_streams_per_throttling_interval` streams in window N+1.

Within a real-time span potentially much shorter than `STREAM_THROTTLING_INTERVAL` (e.g., streams sent right before and right after the ~100ms boundary), the connection can get close to 2x the intended per-interval quota accepted without the sleep-based backoff in `throttle_stream` (lines 242-269) ever triggering, since each window's count individually stays at or below the threshold.

The check `streams_read_in_throttle_interval >= max_streams_per_throttling_interval` only compares against the current window's counter, which was just reset to 0; there is no accounting of streams sent in the immediately preceding window. This is the classic fixed-window counter flaw and is intrinsic to how the counter is stored (`stream_count: AtomicU64` reset wholesale, `last_throttling_instant` as a single timestamp) rather than a token-bucket or sliding-window scheme.

### Impact Explanation
This affects only the per-connection stream throttle for a single QUIC connection (unstaked or staked). The invariant "no more than `max_streams_per_throttling_interval` streams accepted per `STREAM_THROTTLING_INTERVAL`" is violated by roughly 2x for a short window around the interval boundary, allowing a burst of extra streams (and thus transactions) to reach packet coalescing/banking stage from a single connection. Since `max_streams_per_throttling_interval` for unstaked connections is deliberately kept small (bounded by `MAX_UNSTAKED_TPS` and `EXPECTED_UNSTAKED_STREAMS_RATIO`, see lines 16-19, 64-68), a 2x burst from one connection is a bounded, per-connection resource-consumption increase — not an unbounded DoS, and it does not bypass the separate per-IP/per-connection count limits or overall staked/unstaked load EMA capacity accounting (`StakedStreamLoadEMA`) which operates on a similar throttling-window design at the aggregate level. The impact is a QoS-fairness degradation (unfair capture of TPU stream capacity within a narrow time window) rather than a crash, panic, deadlock, or verification bypass.

### Likelihood Explanation
Fully reachable by an unstaked/unprivileged remote client that can control the timing of stream opens on a QUIC connection to a leader's public TPU port; no special privileges, staking, or validator control needed. The exploit requires precise timing straddling the ~100ms window boundary, which is feasible for an attacker measuring RTT/response behavior, but the gain is bounded to a single extra quota's worth of streams per boundary crossing per connection — it must be repeated at each 100ms boundary to sustain elevated throughput, and each individual connection is still bounded by connection/stream-count limits elsewhere in the QUIC server config.

### Recommendation
Replace the fixed-window reset with a sliding-window or token-bucket scheme for `ConnectionStreamCounter`, e.g., track a rolling count of stream timestamps (or decay the previous window's count proportionally into the new window) so that the maximum number of streams accepted in any sliding `STREAM_THROTTLING_INTERVAL`-length window is bounded by `max_streams_per_throttling_interval`, rather than only bounding fixed, non-overlapping windows.

### Proof of Concept
Rust unit/invariant test plan for `streamer/src/nonblocking/stream_throttle.rs`:

```rust
#[tokio::test]
async fn test_fixed_window_boundary_burst() {
    let stats = StreamerStats::default();
    let counter = Arc::new(ConnectionStreamCounter::new());
    let max_streams = 10u64;

    // Simulate max_streams accepted just before the window boundary.
    for _ in 0..max_streams {
        counter.stream_count.fetch_add(1, Ordering::Relaxed);
    }
    // Manually age last_throttling_instant to just under STREAM_THROTTLING_INTERVAL
    // (in a real fuzz harness, mock/advance tokio::time to boundary - epsilon).

    // Advance time past STREAM_THROTTLING_INTERVAL to trigger reset.
    tokio::time::pause();
    tokio::time::advance(STREAM_THROTTLING_INTERVAL + Duration::from_millis(1)).await;

    // Second burst in the new window.
    for _ in 0..max_streams {
        throttle_stream(&stats, ConnectionPeerType::Unstaked, "127.0.0.1:0".parse().unwrap(), &counter, max_streams).await;
    }

    // Assert: total streams accepted across the two adjacent windows (a span < 2 * STREAM_THROTTLING_INTERVAL)
    // should not exceed max_streams_per_throttling_interval for any STREAM_THROTTLING_INTERVAL-length sliding window,
    // but observed count is close to 2 * max_streams within a short real-time span.
    assert!(stats.throttled_streams.load(Ordering::Relaxed) == 0);
}
```

A fuzz/invariant harness should generate randomized stream-arrival timestamps straddling multiple `STREAM_THROTTLING_INTERVAL` boundaries and assert, for every sliding window of length `STREAM_THROTTLING_INTERVAL`, that the count of accepted (non-throttled) streams never exceeds `max_streams_per_throttling_interval`; the fixed-window implementation will fail this invariant near boundaries while a corrected sliding-window/token-bucket implementation will not.

    pub(crate) fn reset_throttling_params_if_needed(&self) -> tokio::time::Instant {
        let last_throttling_instant = *self.last_throttling_instant.read().unwrap();
        if tokio::time::Instant::now().duration_since(last_throttling_instant)
            > STREAM_THROTTLING_INTERVAL
        {
            let mut last_throttling_instant = self.last_throttling_instant.write().unwrap();
            // Recheck as some other thread might have done throttling since this thread tried to acquire the write lock.
            if tokio::time::Instant::now().duration_since(*last_throttling_instant)
                > STREAM_THROTTLING_INTERVAL
            {
                *last_throttling_instant = tokio::time::Instant::now();
                self.stream_count.store(0, Ordering::Relaxed);
            }
            *last_throttling_instant
        } else {
            last_throttling_instant
        }
    }

pub(crate) async fn throttle_stream(
    stats: &StreamerStats,
    peer_type: ConnectionPeerType,
    remote_addr: std::net::SocketAddr,
    stream_counter: &Arc<ConnectionStreamCounter>,
    max_streams_per_throttling_interval: u64,
) {
    let throttle_interval_start = stream_counter.reset_throttling_params_if_needed();
    let streams_read_in_throttle_interval = stream_counter.stream_count.load(Ordering::Relaxed);
    if streams_read_in_throttle_interval >= max_streams_per_throttling_interval {
        // The peer is sending faster than we're willing to read. Sleep for what's
        // left of this read interval so the peer backs off.
        let throttle_duration =
            STREAM_THROTTLING_INTERVAL.saturating_sub(throttle_interval_start.elapsed());

        if !throttle_duration.is_zero() {
            debug!(
                "Throttling stream from {remote_addr:?}, peer type: {peer_type:?}, \
                 max_streams_per_interval: {max_streams_per_throttling_interval}, \
                 read_interval_streams: {streams_read_in_throttle_interval} throttle_duration: \
                 {throttle_duration:?}"
            );
            stats.throttled_streams.fetch_add(1, Ordering::Relaxed);
            match peer_type {
                ConnectionPeerType::Unstaked => {
                    stats
                        .throttled_unstaked_streams
                        .fetch_add(1, Ordering::Relaxed);
                }
                ConnectionPeerType::Staked(_) => {
                    stats
                        .throttled_staked_streams
                        .fetch_add(1, Ordering::Relaxed);
                }
            }
            sleep(throttle_duration).await;
        }
    }
}
