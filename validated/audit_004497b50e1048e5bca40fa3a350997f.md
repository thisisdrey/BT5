Confirmed: `call-ststx-ratio` in mainnet is a genuine external, unprivileged, permissionless dependency: `(contract-call? 'SP4SZE494VC2YC5JYG7AYFQ44F5Q4PYV7DVMDPBG.block-info-nakamoto-ststx-ratio-v2 get-ststx-ratio-v3)` [1](#0-0) .

### Title
Users holding stSTX/zstSTX will fail to exit or free their position if the third-party stSTX ratio oracle reverts, forcing avoidable liquidation - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`resolve-ststx` unconditionally forwards to the external, unprivileged stSTX ratio contract via `call-ststx-ratio`, and any failure there is propagated as a hard revert (`ERR-ORACLE-CALLCODE`) rather than being handled gracefully, which blocks the price-resolution step that `collateral-remove`, `borrow` health checks, `collateral-add` (new-asset path), and `liquidate` all depend on whenever the position's mask includes stSTX or zstSTX.

### Finding Description
`resolve-ststx` calls `call-ststx-ratio`, unwraps the response, and errors out with `ERR-ORACLE-CALLCODE` on failure [2](#0-1) . `call-ststx-ratio` itself is a thin passthrough to a third-party, unprivileged contract that Zest does not control: `SP4SZE494VC2YC5JYG7AYFQ44F5Q4PYV7DVMDPBG.block-info-nakamoto-ststx-ratio-v2` [1](#0-0) . This mirrors the root cause of the referenced Blueberry bug class: a health-check/exit path is hard-wired to an external, permissionless dependency whose failure state (analogous to Curve's `is_killed`) is entirely outside the protocol's control, and that failure propagates as an unhandled revert rather than being isolated.

`resolve-callcode` routes `CALLCODE-STSTX` and `CALLCODE-ZSTSTX` (used for stSTX and zstSTX assets) through `resolve-ststx`, and any of these callcodes appearing in `get-assets` will cause the *entire* `price-multi-resolve` fold to fail via `iter-price-multi`, since a single failed resolution flips `valid` to `false` for the whole batch [3](#0-2) [4](#0-3) .

This has broad reach because `get-assets` is called unconditionally whenever a user's position (mask) includes stSTX/zstSTX, in:
- `collateral-remove` for the has-debt path (`get-notional-evaluation` requires `assets`) [5](#0-4) 
- `borrow` health checks [6](#0-5) 
- `liquidate`, where `get-assets(mask)` for the *full* borrower position is required before any repay/collateral seizure can proceed [7](#0-6) 
- `collateral-add` capacity check for new collateral additions when the user already carries debt [8](#0-7) 

By contrast, `repay` deliberately avoids price resolution ("Get position WITHOUT resolving prices") [9](#0-8) , so plain debt repayment is not affected — but `collateral-remove` (the actual withdrawal/exit path that lets a user reduce exposure and restore health) IS gated on this external call whenever the user holds any stSTX/zstSTX in their position, even if they are trying to remove a *different* asset.

### Impact Explanation
If the external stSTX ratio contract becomes non-responsive/reverting (deprecated, paused, migrated, or otherwise unavailable — a state entirely outside Zest's control, directly analogous to a Curve pool's `is_killed`), any borrower whose position mask contains stSTX or zstSTX collateral loses the ability to call `collateral-remove` to de-risk their position, or to be liquidated via the normal `liquidate` path, at exactly the time (declining health) when they need it most. This lands on the in-scope **temporary freezing of funds** impact class: affected borrowers cannot withdraw/adjust collateral and can be pushed into loss via accruing interest and unfavorable price movement while unable to act, and liquidators are similarly blocked, risking protocol-side bad debt accumulation until socialization is manually triggered by governance.

### Likelihood Explanation
Likelihood depends entirely on the third-party `block-info-nakamoto-ststx-ratio-v2` contract's availability and is not something Zest controls or can rule out; this matches the "external permissionless dependency can revert" bug class from the source report, though I could not verify from this codebase whether that specific external contract has any history of failure/pausing (out of scope for this analysis) — this is an architectural/reachability finding, not a proven live incident.

### Recommendation
Wrap `call-ststx-ratio` failures so that they degrade gracefully instead of reverting the entire multi-asset price resolution: e.g., cache the last-known-good ratio and fall back to it (with a staleness bound) when the external call fails, or allow `collateral-remove`/`liquidate` to proceed using only the assets that could be priced (similar in spirit to Curve's `remove_liquidity` fallback for `remove_liquidity_one_coin` in the referenced report), rather than failing the whole `get-assets` call via `ERR-ORACLE-CALLCODE`.

### Proof of Concept
1. A borrower supplies stSTX or zstSTX collateral together with other collateral and takes out debt, so their position mask includes the stSTX/zstSTX bit.
2. The external contract `SP4SZE494VC2YC5JYG7AYFQ44F5Q4PYV7DVMDPBG.block-info-nakamoto-ststx-ratio-v2` becomes unavailable or reverts on `get-ststx-ratio-v3` (a state outside Zest's control).
3. Borrower calls `collateral-remove` to withdraw a *different* (non-stSTX) collateral asset to restore health; the has-debt branch calls `get-assets(position-mask)` → `price-multi-resolve` → `resolve-callcode` → `resolve-ststx` → `call-ststx-ratio`, which reverts, causing the entire `collateral-remove` call to fail [5](#0-4) [2](#0-1) .
4. Any liquidator attempting `liquidate` on this borrower also fails at `get-assets(mask)` before repayment/seizure logic runs [7](#0-6) .
5. The borrower's position remains frozen — unable to be adjusted or liquidated — for as long as the external ratio contract remains unavailable.

(define-private (price-multi-resolve
  (data (list 64 { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (aids (list 64 uint)))
  (let ((init { output: (list), valid: true, aids: aids, idx: u0 })
        (response (fold iter-price-multi data init)))
    (asserts! (get valid response) ERR-ORACLE-MULTI)
    (ok (get output response))))

(define-private (iter-price-multi
  (oracle-data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint })
  (acc { output: (list 64 uint), valid: bool, aids: (list 64 uint), idx: uint }))
  (let ((valid (get valid acc))
        (skip? (asserts! valid acc))
        (asset-ids (get aids acc))
        (idx (get idx acc))
        ;; resolve price - will use cache for ztokens
        (price (unwrap! (price-resolve oracle-data) (merge acc { valid: false })))
        (next (unwrap-panic (as-max-len? (append (get output acc) price) u64))))
    { output: next,
      valid: true,
      aids: asset-ids,
      idx: (+ idx u1) }))
