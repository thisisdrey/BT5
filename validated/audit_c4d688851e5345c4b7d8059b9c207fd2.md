### Title
Module extension `facts` are shallow-merged into the lockfile without per-key attribution or reproducibility checks, allowing stale/attacker-influenced facts to be reused by unrelated evaluations - (File: `docs/external/extension.mdx`, lockfile facts mechanism)

### Summary
`module_extension` "facts" are a documented mechanism for a non-reproducible extension to persist network-derived, checksum-less data (e.g., "hashes of artifacts in an immutable repository") into `MODULE.bazel.lock`, and to have that data blindly trusted by future evaluations via `ctx.facts` without re-fetching or re-verifying it.

### Finding Description
The `facts` field of `extension_metadata` is designed for extensions that "rely on effectively immutable data obtained from outside the build, most commonly from the network, but you don't have a checksum available to guard the download" [1](#0-0) . Bazel explicitly documents that it "may shallowly merge multiple facts dicts returned by different versions of the extension in order to resolve merge conflicts on the MODULE.bazel.lock file, as if by applying the `dict.update()` method or the `|` operator", and that this merge is only "partially enforced" since keys can't even be enumerated by the consuming extension [2](#0-1) .

Critically, once persisted, `facts` are handed back to the extension implementation on the next evaluation with **no re-validation against origin data**: the test suite confirms that if the lockfile's facts for a non-reproducible extension change externally (e.g., "a branch switch or pull brings in facts produced by an evaluation of the extension on a different machine"), the extension is *not rerun* and the new facts are trusted as-is: "the cached result must be reused with the new facts as is" [3](#0-2) . Likewise, individually-added or externally-modified fact entries for unrelated keys (e.g. new SDK/version → {hash, url} mappings) are merged straight into the trusted lockfile state and reused without a network fetch or hash check [4](#0-3) .

This maps directly onto the "allowances can be frontran" bug class: instead of validating each entry against a pinned/authenticated origin before trusting it (the equivalent of "increase/decrease" with a check), Bazel performs a raw "set"-style shallow merge of untrusted, unchecksummed key/value data straight into a state (the lockfile facts) that is later trusted implicitly and reused across builds and machines — i.e., cache poisoning that reaches another build. An attacker who can influence what lands in a shared/branch-committed `MODULE.bazel.lock` (a very plausible unprivileged-content-publisher scenario since lockfiles are meant to be checked into source control and consumed by CI across many machines) can inject or tamper with `facts` entries for extensions that rely on this feature (as documented, this is intended for artifact hash/URL mappings), and those tampered facts will be accepted and used to drive subsequent repository-rule instantiation (e.g., constructing download URLs/hashes) without any re-verification, because the extension is treated as already reproducible for a value it never itself re-derived.

### Impact Explanation
If a downstream module extension uses `facts` to cache a mapping of `version -> {url, hash}` (exactly the example given in the documentation) [5](#0-4) , an attacker able to modify the committed lockfile (e.g., by contributing to a shared branch that CI builds, matching the threat model of "untrusted branch CI builds") can add or overwrite `facts[...]` entries. Because these are merged and trusted without re-fetching, this can substitute a URL/hash pair the extension will use to fetch and unpack content into a repository, effectively bypassing the very checksum protections that `facts` was invented to work around, and poisoning every subsequent build that shares the lockfile.

### Likelihood Explanation
This requires a non-reproducible extension that stores security-relevant data (URLs/hashes) into `facts` — an explicitly documented and encouraged pattern for that exact use case — combined with an attacker's ability to modify the workspace `MODULE.bazel.lock` file (checked into VCS, consumed across machines/CI). The lockfile-facts-merge behavior itself is confirmed, current, default (`--lockfile_mode=update`) behavior, verified by the project's own regression tests [6](#0-5) .

### Recommendation
Do not implicitly trust externally-modified `facts` entries for non-reproducible extensions across machines/branches without at least detecting and flagging the change (similar to how reproducible-extension facts changes trigger re-evaluation, per `testExternallyUpdatedFactsRegenerateReproducibleExtension` [7](#0-6) ). Extensions that use `facts` to store checksum/URL data should be required to independently re-verify the referenced content (e.g. checksum verification at consumption time) rather than trusting the persisted value as ground truth.

### Proof of Concept
The behavior is reproducible via the existing test scaffolding in `bazel_lockfile_test.py`: `_setUpExtensionWithFacts` creates a non-reproducible extension with `facts = {"1.25.0": {"hash": "olleh"}, "1.26.1": {"hash": "hello"}}`; `_addFactToLockfile` simulates an externally-modified lockfile adding `"1.27.0": {"hash": "hola"}`; then `testExternallyUpdatedFactsKeptByUpdateModeForNonReproducibleExtension` shows that under default `--lockfile_mode=update` the extension is not rerun and the injected fact is kept verbatim in the lockfile and available via `ctx.facts` [8](#0-7) .

  def _addFactToLockfile(self, extension_id, fact_key, fact_value):
    """Adds a facts entry to the workspace lockfile."""
    # Simulates the workspace lockfile changing underneath a warm output base,
    # e.g. due to a branch switch or pull that brings in facts produced by an
    # evaluation of the extension on a different machine.
    with open(self.Path('MODULE.bazel.lock'), 'r') as f:
      lockfile = json.loads(f.read().strip())
    lockfile['facts'][extension_id][fact_key] = fact_value
    with open(self.Path('MODULE.bazel.lock'), 'w') as f:
      json.dump(lockfile, f, indent=2)

  def testDeletedFactsRegeneratedByUpdateModeAfterUnrelatedBuild(self):
    """Facts are regenerated even if an unrelated build runs after the edit.

    The unrelated build must not overwrite the hidden lockfile's record of the
    facts produced by the extension's most recent evaluation with the manually
    edited workspace facts, as that record is what allows a later build to
    detect that the extension has to be rerun.
    """
    extension_id = self._setUpExtensionWithFacts(reproducible=True)
    self._dropFactsFromLockfile(extension_id, fact_key='1.25.0')

    # This build does not evaluate the extension.
    self.RunBazel(['build', '//:unrelated', '--lockfile_mode=update'])

    self.RunBazel(['build', '@hello//:all', '--lockfile_mode=update'])

    with open(self.Path('MODULE.bazel.lock'), 'r') as f:
      lockfile = json.loads(f.read().strip())
    self.assertEqual(
        lockfile['facts'][extension_id],
        {'1.25.0': {'hash': 'olleh'}, '1.26.1': {'hash': 'hello'}},
    )

  def testExternallyUpdatedFactsKeptByUpdateModeForNonReproducibleExtension(
      self,
  ):
    """UPDATE mode keeps updated facts of a non-reproducible extension.

    The hidden lockfile records the facts produced by the most recent local
    evaluation of the extension. If the workspace lockfile's facts for a
    non-reproducible extension change without any of its inputs changing (e.g.
    a branch switch or pull brings in a re-pin performed on another machine),
    the cached result must be reused with the new facts as is: a cold machine
    would not rerun the extension either and a rerun could require network
    access or credentials that are only available to the person updating the
    pins.
    """
    extension_id = self._setUpExtensionWithFacts(reproducible=False)
    self._addFactToLockfile(extension_id, '1.27.0', {'hash': 'hola'})

    _, _, stderr = self.RunBazel(
        ['build', '@hello//:all', '--lockfile_mode=update']
    )
    self.assertNotIn('lockfile_ext is being evaluated', '\n'.join(stderr))

    with open(self.Path('MODULE.bazel.lock'), 'r') as f:
      lockfile = json.loads(f.read().strip())
    self.assertEqual(
        lockfile['facts'][extension_id],
        {
            '1.25.0': {'hash': 'olleh'},
            '1.26.1': {'hash': 'hello'},
            '1.27.0': {'hash': 'hola'},
        },
    )

  def testExternallyUpdatedFactsRegenerateReproducibleExtension(self):
    """UPDATE mode reruns a reproducible extension on changed facts.

    A reproducible extension's facts can only legitimately change together
    with its inputs, so facts that differ from the record of its most recent
    evaluation despite unchanged inputs indicate an edited workspace lockfile
    and the extension is rerun to regenerate them. This is safe: a reproducible
    extension's result is only ever cached in the machine-local hidden
    lockfile, so a cold machine would rerun it anyway.
    """
    extension_id = self._setUpExtensionWithFacts(reproducible=True)
    self._addFactToLockfile(extension_id, '1.27.0', {'hash': 'hola'})

    _, _, stderr = self.RunBazel(
        ['build', '@hello//:all', '--lockfile_mode=update']
    )
    self.assertIn('lockfile_ext is being evaluated', '\n'.join(stderr))

    with open(self.Path('MODULE.bazel.lock'), 'r') as f:
      lockfile = json.loads(f.read().strip())
    self.assertEqual(
        lockfile['facts'][extension_id],
        {'1.25.0': {'hash': 'olleh'}, '1.26.1': {'hash': 'hello'}},
    )
