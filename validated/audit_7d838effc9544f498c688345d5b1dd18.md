## Title
Missing zero-address (null-payload) validation in `TransferActuator` allows permanent loss of funds sent to an unrecoverable address - (File: `actuator/src/main/java/org/tron/core/actuator/TransferActuator.java`)

## Summary
`TransferActuator.validate()` only checks the destination address via `DecodeUtil.addressValid(toAddress)`, but that helper never rejects an address whose 20-byte payload is entirely zero. A `TransferContract` sent to the all-zero payload address (`0x41` + 20 zero bytes) is treated as valid, a fresh account is silently created for it, and the transferred TRX becomes permanently unspendable, mirroring the C4 finding where `FETH.withdrawFrom` failed to reject `to == address(0)`.

## Finding Description
`DecodeUtil.addressValid` only verifies that the address is non-empty, exactly 21 bytes long, and starts with the network prefix byte; it never inspects the remaining 20 bytes: [1](#0-0) 

`TransferActuator.validate()` calls this exact helper on `toAddress` and performs no additional check that the payload portion is non-zero — it only rejects an empty/invalid-length address or a self-transfer: [2](#0-1) 

In `execute()`, if no account exists at `toAddress`, a brand-new `AccountCapsule` is created for it and the balance is credited unconditionally: [3](#0-2) 

Because no known private key corresponds to the all-zero-payload address, any TRX sent there is permanently unrecoverable — unlike the officially tracked black-hole/burn address, this loss is not reflected in any burn accounting, so it is a straightforward, silent loss-of-funds condition triggerable by any ordinary account holder broadcasting a `TransferContract`.

The same root-cause gap (`DecodeUtil.addressValid` not rejecting the zero payload) also affects other actuators that validate a caller-supplied destination the same way, e.g. `TransferAssetActuator` and `DelegateResourceActuator`/`UnDelegateResourceActuator` receiver checks: [4](#0-3) [5](#0-4) 

## Impact Explanation
A user error (or a malicious front-end / wallet bug) can cause TRX or TRC10 assets to be sent to the zero-payload address, where they become permanently and irrecoverably lost — a direct "permanent freezing of funds" outcome reachable by any unprivileged transaction broadcaster with no special permissions required.

## Likelihood Explanation
Any account can craft and broadcast a `TransferContract` (or `TransferAssetContract`) with `toAddress` set to the all-zero payload address; the actuator's `validate()` will accept it since `DecodeUtil.addressValid` passes. This requires no privileged role, matching the "unprivileged transaction broadcaster" reachable-path requirement.

## Recommendation
Add an explicit check in `TransferActuator.validate()` (and the analogous actuators) rejecting a `toAddress`/`receiverAddress` whose 20-byte payload is all zero, e.g. compare against `DecodeUtil.addressPreFixByte` followed by zero bytes, or centralize this check inside `DecodeUtil.addressValid` itself so all callers benefit.

## Proof of Concept
1. Construct a `TransferContract` with `ownerAddress` = a funded account and `toAddress` = `0x41` followed by 20 `0x00` bytes (21 bytes total, valid length/prefix).
2. Broadcast the transaction; `TransferActuator.validate()` passes since `DecodeUtil.addressValid` only checks length/prefix (`common/src/main/java/org/tron/common/utils/DecodeUtil.java` lines 15-33).
3. `execute()` creates a new `AccountCapsule` for the zero-payload address and credits it with the transferred amount (`TransferActuator.java` lines 48-66).
4. No private key exists for this address, so the funds are permanently unspendable.

  public static boolean addressValid(byte[] address) {
    if (ArrayUtils.isEmpty(address)) {
      logger.warn("Warning: Address is empty !!");
      return false;
    }
    if (address.length != ADDRESS_SIZE / 2) {
      logger.warn(
          "Warning: Address length need " + ADDRESS_SIZE + " but " + address.length
              + " !!");
      return false;
    }

    if (address[0] != addressPreFixByte) {
      logger.warn("Warning: Address need prefix with " + addressPreFixByte + " but "
          + address[0] + " !!");
      return false;
    }
    return true;
  }
