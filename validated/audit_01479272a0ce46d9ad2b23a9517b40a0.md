### Title
Graduated-liquidation curve exponent formula silently ignores the configured sub-linear `LIQ-CURVE-EXP` and always applies a hard-coded square-root instead - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
The graduated-liquidation math derives the liquidation percentage/penalty from a curve-exponent parameter (`LIQ-CURVE-EXP`) that egroups configure per asset combination. For exponents below `BPS` (i.e. sub-linear/"gentle" curves, any value in `(0, 10000)`), the implementation does not use the actual configured exponent at all — it always computes a fixed square-root (exponent = 0.5), regardless of whether the DAO configured 0.3, 0.7, or any other sub-linear value. This is analogous to the PoolTogether `_numberOfPrizesForIndex` bug: a parametrized mathematical formula (meant to vary continuously with an input, here the exponent; there, the tier index) is replaced by an incorrect/simplified closed form that silently diverges from the intended value, producing wrong distribution amounts (there: prize sizes; here: liquidation penalty/seized-collateral amounts) without reverting.

### Finding Description
`calc-liq-factor-exp` is meant to raise the linear liquidation factor to the power encoded by `LIQ-CURVE-EXP` (expressed in bps, where `BPS`=10000 represents an exponent of 1.0): [1](#0-0) 

```clarity
;; Apply curve exponent for graduated liquidation
;; liq-factor = liq-factor^alpha
(define-private (calc-liq-factor-exp (factor uint) (exp uint))
  (if (is-eq exp BPS) 
    factor
    (if (> exp BPS) 
        (/ (pow factor (/ exp BPS)) (pow BPS (- (/ exp BPS) u1)))
        (sqrti (* factor BPS))))) ;; assume factor^0.5
```

For `exp > BPS` the code does a valid integer-exponent computation (though it truncates `exp/BPS` to an integer, so only exact multiples of `BPS` behave as configured — e.g. `15000` silently becomes exponent `1`).

For `exp < BPS` — any egroup configured with a gentle, sub-linear liquidation curve (documented in `docs/egroups.md` as supporting arbitrary values `<10000`, e.g. "square root") — the function unconditionally executes `(sqrti (* factor BPS))`, which is *only* correct when `exp` is exactly `5000` (0.5). Any other sub-linear configuration (e.g. `3000` = 0.3, `7000` = 0.7) is silently coerced to a 0.5 exponent. The `exp` argument is read but never actually used in this branch (only its comparison against `BPS` matters).

This is invoked directly from the public, unprivileged `liquidate` entry point via `calc-liquidation-params`, which is called on every liquidation: [2](#0-1) 

The resulting `liq-pct-scaled` feeds directly into `calc-liq-factor-bound` (penalty interpolation) and `calc-liq-debt-repay` (max debt repayable), both of which determine how much collateral is seized from the borrower and transferred to the liquidator: [3](#0-2) 

Because the actual curve applied (fixed 0.5) diverges from the DAO-configured curve (any other sub-linear shape), the liquidation percentage and penalty computed at intermediate LTVs (between `LTV-LIQ-PARTIAL` and `LTV-LIQ-FULL`) will not match the risk parameters the DAO intended for that egroup. Depending on the configured value vs. 0.5, this systematically over- or under-computes the liquidation percentage/penalty for every liquidation on that egroup for the entire time the egroup exists, exactly the same class of defect as the reported PoolTogether bug: a formula meant to vary by parameter is replaced by an approximation that diverges from the correct value and is exercised on every relevant on-chain operation.

### Impact Explanation
Every liquidation against an egroup configured with a `LIQ-CURVE-EXP` other than exactly `5000`, `10000`, or an exact multiple of `10000` computes an incorrect liquidation percentage/penalty. Depending on the direction of the divergence:
- If the fixed square-root formula computes a *larger* liquidation percentage/penalty than the DAO-configured curve intended, borrowers lose more collateral than the protocol's own risk parameters specify on every affected liquidation — an unintended transfer of value from borrowers to liquidators that is directly reachable by any liquidator calling the public `liquidate` function.
- If it computes a smaller percentage, insufficient collateral may be seized relative to the debt being cleared, increasing bad-debt/insolvency risk for the vault.

This satisfies the "Critical – protocol insolvency" / "High – temporary freezing of funds" thresholds depending on divergence direction, since the affected amounts are real user collateral and debt settled on every liquidation for the misconfigured egroup, not merely unclaimed yield.

### Likelihood Explanation
Likelihood depends entirely on whether any deployed egroup actually uses a `LIQ-CURVE-EXP` value strictly between `0` and `BPS` other than `5000`. The egroup risk-parameter schema and documentation explicitly describe `LIQ-CURVE-EXP < 10000` as a supported "gentle curve" configuration space (not restricted to 0.5), so the DAO is expected to be able to pick values like `3000` or `7000`. I was not able to fully confirm, within the remaining budget, which exact `LIQ-CURVE-EXP` values are set for the currently-deployed mainnet egroups (`mainnet/contracts/proposals/mainnet/v0-init.clar`), so likelihood in the *current* configuration is uncertain — but the code path is reachable by anyone, and the formula itself is provably wrong for any sub-BPS exponent other than exactly 0.5.

### Recommendation
Implement a generic fractional-exponent (or piecewise-linear) approximation that actually consumes `exp` for the `exp < BPS` branch, rather than hard-coding `sqrti`. If a general `pow` with fractional exponent is impractical in Clarity, either (a) restrict `LIQ-CURVE-EXP` at egroup-insertion time to only the values the implementation can correctly compute (`BPS`, integer multiples of `BPS`, and `BPS/2`), rejecting all other sub-linear values, or (b) implement a correct sub-linear formula (e.g., Newton's method-based `n`-th root, or a lookup/interpolation table) so the on-chain behavior matches the parameter the DAO configured.

### Proof of Concept
1. DAO/governance creates an egroup with `LIQ-CURVE-EXP = u3000` (intending a gentle 0.3-exponent liquidation curve), per the documented supported range in `docs/egroups.md`.
2. A borrower's position enters the graduated liquidation zone (LTV between `LTV-LIQ-PARTIAL` and `LTV-LIQ-FULL`), e.g. `liq-pct-linear = 4000` (40%).
3. Any address calls `liquidate`. Internally `calc-liquidation-params` → `calc-liq-factor-exp` is invoked with `factor = 4000`, `exp = 3000`.
4. Since `exp < BPS`, the code computes `sqrti(4000 * 10000) = sqrti(40000000) ≈ 6324`, i.e. it applies a 0.5 exponent curve (`4000^0.5-scaled ≈ 6324`) instead of the DAO-intended 0.3 exponent curve (`4000^0.3-scaled`, a different, non-equal value).
5. This wrong `liq-pct-scaled` propagates into `calc-liq-factor-bound` (penalty) and `calc-liq-debt-repay` (max debt liquidatable), causing every liquidation on this egroup to seize a different (systematically wrong) amount of collateral than the DAO's configured risk curve specifies, with no revert or warning anywhere in the call path.

;; Scale penalty between min and max using liquidation factor
;; liq-penalty = liq-penalty-min + (liq-factor * (liq-penalty-max - liq-penalty-min) / BPS)
;; Capped at bound-max to handle cases where liq-factor > BPS
(define-private (calc-liq-factor-bound (liq-factor uint) (bound-min uint) (bound-max uint))
  (min bound-max (+ bound-min (mul-bps-down liq-factor (- bound-max bound-min)))))

;; Calculate debt to repay based on liquidation factor
;; debt-repay = liq-factor * debt / BPS
(define-private (calc-liq-debt-repay (debt uint) (liq-factor uint)) 
  (mul-bps-down liq-factor debt))

;; Calculate collateral to seize (includes liquidator bonus)
;; collateral-repay = debt-repay * (BPS + liq-penalty) / BPS

;; Graduated liquidation parameter calculation
;; Combines the 4-step liquidation factor calculation into a single helper
;; Returns: { liq-pct-scaled: uint, liq-penalty: uint, max-debt-usd: uint }
(define-private (calc-liquidation-params
  (current-ltv uint)
  (ltv-liq-partial uint)
  (ltv-liq-full uint)
  (liq-penalty-min uint)
  (liq-penalty-max uint)
  (curve-exponent uint)
  (total-debt-usd uint))
  
  (let ((liq-pct-linear (calc-liq-factor current-ltv ltv-liq-partial ltv-liq-full))
        (liq-pct-scaled (calc-liq-factor-exp liq-pct-linear curve-exponent))
        (liq-penalty (calc-liq-factor-bound liq-pct-scaled liq-penalty-min liq-penalty-max))
        (max-debt-usd (calc-liq-debt-repay total-debt-usd liq-pct-scaled)))
    {
      liq-pct-scaled: liq-pct-scaled,
      liq-penalty: liq-penalty,
      max-debt-usd: max-debt-usd
    }))
