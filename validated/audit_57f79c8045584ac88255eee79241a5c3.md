### Title
`claim_child_bounty` pays out the child-bounty account's entire actual balance instead of its recorded `value`, letting anyone drain stray funds sent to that account - ([File: substrate/frame/child-bounties/src/lib.rs])

### Summary
The `ChildBounty` struct records the intended payout amount in the `value` field [1](#0-0) , but `claim_child_bounty` never reads `child_bounty.value` when computing the payout. Instead it reads the *live* free balance of the deterministic, publicly-derivable `child_bounty_account_id`, splits off the curator fee, and forwards the remainder to the beneficiary — mirroring exactly the ETHAdapter flaw of forwarding an account's "entire actual balance" rather than the specific tracked/owed amount.

### Finding Description
`claim_child_bounty` computes the payout as: [2](#0-1) 

```
let balance = T::Currency::free_balance(&child_bounty_account);
let curator_fee = child_bounty.fee.min(balance);
let payout = balance.saturating_sub(curator_fee);
...
T::Currency::transfer(&child_bounty_account, curator, curator_fee, AllowDeath);
T::Currency::transfer(&child_bounty_account, beneficiary, payout, AllowDeath);
```

Notice `balance` is the account's *current actual* balance, not `child_bounty.value` (the recorded, intended amount) that was reserved from the parent bounty when the child bounty was created. The `child_bounty_account_id(parent_bounty_id, child_bounty_id)` is a deterministic `PalletId`-derived sub-account, computable off-chain by anyone from public bounty indices. Any account can send extra native currency (a plain `transfer_allow_death`/`transfer_keep_alive`) directly to that address before `claim_child_bounty` executes — accidentally or otherwise. Because the payout uses the live balance rather than the recorded `value`, any such stray funds are swept up and forwarded entirely to the curator/beneficiary, not returned to their rightful sender or to the treasury. This is the same broken invariant as the ETHAdapter report: paying out "whatever balance the intermediary account currently holds" instead of "the specific amount this operation is entitled to move."

`claim_child_bounty` is permissionless (`ensure_signed(origin)` only, no ownership check) [3](#0-2) , so any signed account can trigger the drain once the child bounty reaches `PendingPayout` status set by `award_child_bounty` [4](#0-3) .

### Impact Explanation
Funds mistakenly (or intentionally, by a third party wanting to "tip" someone else) sent to a child-bounty account are redirected entirely to the curator/beneficiary instead of being recoverable by the original sender or reclaimed by the treasury. This is an unbacked/incorrect settlement of value to a beneficiary who was never entitled to the excess amount — a fund-misdirection bug consistent with the "duplicate settlement or payout" / "theft or unbacked ... unlock" impact class, though the loss is scoped to whatever funds a third party places at the derived account address rather than treasury-owned capital.

### Likelihood Explanation
Exploitability requires only: (1) computing the deterministic account address (public function, deterministic derivation), and (2) sending a normal balance transfer to it before `claim_child_bounty` is called. No privileged access, governance, or malicious validator/relayer is needed — an unprivileged attacker or a user error triggers the loss. The likelihood is limited by the fact that an attacker gains no direct profit unless they also control the beneficiary/curator account, but a curator colluding with an attacker to top up the account and then claim would realize a direct gain beyond the approved bounty `value`.

### Recommendation
Use the recorded `child_bounty.value` (minus any already-slashed/adjusted amounts) as the authoritative payout figure in `claim_child_bounty`, rather than the live `free_balance` of the child-bounty account. Any balance in excess of `value` should be swept back to the parent bounty or treasury account (similar to the pattern already used in `reclaim_bounty_funds` [5](#0-4) ) instead of being forwarded to the curator/beneficiary.

### Proof of Concept
1. Governance/curator creates and approves a child bounty with `value = V`; parent bounty transfers `V` into `child_bounty_account_id(parent_id, child_id)`.
2. `award_child_bounty` is called, moving the child bounty to `PendingPayout` with a designated `beneficiary`.
3. Before the payout delay elapses, any third party computes `child_bounty_account_id(parent_id, child_id)` and sends an additional amount `X` of native currency directly to that account via `Balances::transfer_allow_death`.
4. Once `unlock_at` passes, any signed account calls `claim_child_bounty(parent_id, child_id)`.
5. The pallet computes `balance = V + X`, deducts `curator_fee`, and pays out `payout = V + X - curator_fee` to the beneficiary — the extra `X` is drained to the beneficiary instead of being returned to the original sender of `X` or credited to the treasury [6](#0-5) .

		#[pallet::call_index(4)]
		#[pallet::weight(<T as Config>::WeightInfo::award_child_bounty())]
		pub fn award_child_bounty(
			origin: OriginFor<T>,
			#[pallet::compact] parent_bounty_id: BountyIndex,
			#[pallet::compact] child_bounty_id: BountyIndex,
			beneficiary: AccountIdLookupOf<T>,
		) -> DispatchResult {
			let signer = ensure_signed(origin)?;
			let beneficiary = T::Lookup::lookup(beneficiary)?;

			// Ensure parent bounty exists, and is active.
			let (parent_curator, _) = Self::ensure_bounty_active(parent_bounty_id)?;

			ChildBounties::<T>::try_mutate_exists(
				parent_bounty_id,
				child_bounty_id,
				|maybe_child_bounty| -> DispatchResult {
					let child_bounty =
						maybe_child_bounty.as_mut().ok_or(BountiesError::<T>::InvalidIndex)?;

					// Ensure child-bounty is in active state.
					if let ChildBountyStatus::Active { ref curator } = child_bounty.status {
						ensure!(
							signer == *curator || signer == parent_curator,
							BountiesError::<T>::RequireCurator,
						);
						// Move the child-bounty state to pending payout.
						child_bounty.status = ChildBountyStatus::PendingPayout {
							curator: signer,
							beneficiary: beneficiary.clone(),
							unlock_at: Self::treasury_block_number() +
								T::BountyDepositPayoutDelay::get(),
						};
						Ok(())
					} else {
						Err(BountiesError::<T>::UnexpectedStatus.into())
					}
				},
			)?;

		///
		/// Permissionless. Moves all remaining assets from a closed bounty's account back to the
		/// treasury in a single call. Which assets are swept depends on the `TransferAllAssets`
		/// configuration.
		///
		/// The call is free if funds were reclaimed and paid otherwise, so no-op calls cannot be
		/// used to grief the network. Emits `BountyFundsReclaimed` on success.
		///
		/// ## Complexity
		/// - O(A) where A is the number of relevant assets configured in `TransferAllAssets`.
		#[pallet::call_index(11)]
		#[pallet::weight(<T as Config<I>>::WeightInfo::reclaim_bounty_funds())]
		pub fn reclaim_bounty_funds(
			origin: OriginFor<T>,
			#[pallet::compact] bounty_id: BountyIndex,
		) -> DispatchResultWithPostInfo {
			ensure_signed(origin)?;

			// A live bounty still manages its account, so leave it untouched.
			ensure!(!Bounties::<T, I>::contains_key(bounty_id), Error::<T, I>::BountyStillActive);

			debug_assert!(
				T::ChildBountyManager::child_bounties_count(bounty_id) == 0,
				"child bounties should not exist for a closed bounty"
			);

			let bounty_account = Self::bounty_account_id(bounty_id);
			let treasury_account = Self::account_id();

			let transferred = T::TransferAllAssets::force_transfer_all_assets(
				&bounty_account,
				&treasury_account,
			)?;

			// Free only if something moved, otherwise paid to prevent griefing.
			if !transferred {
				return Ok(Pays::Yes.into());
			}

			Self::deposit_event(Event::<T, I>::BountyFundsReclaimed { bounty_id });

			Ok(Pays::No.into())
		}
