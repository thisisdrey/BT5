### Title
Unbounded HTTP response read in the signer's StackerDB RPC client causes memory-exhaustion DoS - (File: libsigner/src/http.rs)

### Summary
`run_http_request` in `libsigner/src/http.rs`, used by `StackerDBSession::rpc_request` in `libsigner/src/session.rs`, reads the entire HTTP response from the socket into an unbounded `Vec<u8>` via `sock.read_to_end(&mut buf)` before any length checking occurs. This is the exact bug class described in the external report (`OpenTelemetry.Sampler.AWS`/`OpenTelemetry.Resources.AWS`, CWE-770): a remote/MITM-controlled HTTP endpoint can return an arbitrarily large body and force unbounded heap allocation in the reading process.

### Finding Description
`StackerDBSession` connects over a plain `TcpStream` to a configured `host` (`libsigner/src/session.rs:129`, `TcpStream::connect(&self.host)`), and every RPC call (`list_chunks`, `get_chunks`, `get_latest_chunks`, `put_chunk`) is routed through `rpc_request` → `run_http_request`: [1](#0-0)

`sock.read_to_end(&mut buf)` has no size cap at all — it will keep growing `buf` for as long as the peer keeps sending bytes, and only *after* the full response is buffered does `decode_http_response`/`decode_http_body` get a chance to inspect a `Content-Length` or chunked-encoding limit. Even the chunked path bounds itself with `MAX_MESSAGE_LEN` (`decode_http_body`, line 207), but that check is never reached until the entire raw response has already been read into `buf` at line 251, and non-chunked bodies (the common case, e.g. plain `Content-Length` bodies from `list_chunks`/`get_chunks`) are never bounded at all — `buf.to_vec()` (line 213) is taken verbatim regardless of size.

This is a direct analog of the reported bug class: an HTTP client reads a response body with `ReadAsStringAsync()`/`read_to_end()`-style unbounded materialization, with no cap on the amount of memory the peer can force the process to allocate.

Contrast with how the rest of the codebase in scope handles this: the node's own HTTP stack (`stackslib/src/net/httpcore.rs`) always bounds reads by a known `Content-Length` (`payload_len`) or by `HttpChunkedTransferReaderState`'s `max_size` (`stacks-common/src/util/chunked_encoding.rs:160`, rejecting any chunk `> MAX_MESSAGE_LEN`), and streams data through `recv_bytes` in fixed 64KB increments (`stackslib/src/net/connection.rs:1091`) rather than via a single unbounded `read_to_end`. `libsigner/src/http.rs`'s `run_http_request` breaks this pattern entirely.

### Impact Explanation
Any party able to act as (or spoof/MITM) the RPC endpoint that a `StackerDBSession` connects to can respond with an arbitrarily large payload — HTTP status line, headers, and body of any length — and force the connecting signer process to buffer the entire thing in RAM before any parsing/size validation occurs. A sufficiently large response (or a slow-drip stream that never closes) can exhaust the signer's memory and crash the process (OOM), taking that signer offline. Since `StackerDBSession` is the transport used by signer components to fetch StackerDB chunks/metadata from a Stacks node, this is a remote, unauthenticated denial-of-service vector against the signer process reachable by whatever endpoint it's configured to talk to (or anyone positioned to intercept that TCP connection).

### Likelihood Explanation
The `host` is attacker-influenced whenever the configured target node is compromised, malicious, or the connection is interceptable (no TLS is used — plain `TcpStream`), mirroring exactly the "attacker-controlled endpoint or MitM" scenario in the original advisory. No authentication, secret, or privileged role is required to exploit this once such positioning exists — only the ability to respond to (or intercept) the plaintext HTTP connection the signer initiates.

### Recommendation
Wrap the socket in a size-bounded reader (e.g., `stacks_common::util::retry::BoundReader`, already used elsewhere in the codebase) before calling `read_to_end`, and abort once a hard maximum (e.g. `MAX_MESSAGE_LEN` or a StackerDB-appropriate limit) is exceeded, mirroring the bounded reads already used in `stackslib/src/net/httpcore.rs` and `stacks-common/src/util/chunked_encoding.rs`. Alternatively, parse headers first to obtain `Content-Length`, enforce a maximum, and only then read exactly that many bytes (or reject/stream-cap chunked bodies) rather than buffering the whole response unconditionally.

### Proof of Concept
1. Stand up a TCP listener acting as the `host` a `StackerDBSession` connects to.
2. On accept, send a valid HTTP status line/headers (or none) and then stream an effectively unbounded body (e.g., write `A` in a loop without closing the connection, or advertise a huge `Content-Length`).
3. Have a `StackerDBSession::get_chunks`/`list_chunks` call `rpc_request` against this listener.
4. Observe `run_http_request`'s `sock.read_to_end(&mut buf)` (`libsigner/src/http.rs:251`) keep growing `buf` unbounded until the process exhausts memory and is killed by the OS OOM killer, since no size check exists prior to this read completing. [3](#0-2)
