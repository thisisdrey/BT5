### Title
Uncollateralized debt can still be repaid after liquidation drains the position - (File: contracts/DebtToken.sol)

### Summary
`Pool.liquidate()` can seize substantially all of an underwater borrower’s collateral while leaving residual debt, and `DebtToken.repay()`/`repayAll()` subsequently burn the payer’s synthetic tokens without checking that any collateral remains to unlock. [1](#0-0) [2](#0-1) 

### Finding Description
`quoteLiquidateMax()` limits the repayment amount to the lesser of the borrower’s capped debt and the amount needed to seize the borrower’s entire `DepositToken` balance. [1](#0-0) 

For a sufficiently underwater position, the collateral-derived amount is smaller than the debt-derived cap, so liquidation can consume the collateral while `DebtToken.balanceOf(account_)` remains positive. [3](#0-2) 

After collateral has been seized, `unlockedBalanceOf()` returns zero for any residual debt because the position has no positive issuable amount. [4](#0-3) 

Nevertheless, `repay()` only accrues interest, applies the debt-floor check, burns the payer’s synthetic tokens, and reduces `onBehalfOf_` debt. [5](#0-4) 

Likewise, `repayAll()` accepts any nonzero residual debt and burns the corresponding synthetic-token amount without checking `depositOf(onBehalfOf_)`, `unlockedBalanceOf()`, or whether liquidation has already occurred. [2](#0-1) 

An unprivileged liquidator can therefore observe a borrower’s pending repayment, front-run it with `Pool.liquidate()`, receive the seized deposit tokens, and then allow the borrower’s repayment to execute against the now-uncollateralized residual debt. [6](#0-5) [7](#0-6) 

### Impact Explanation
The borrower loses the synthetic tokens burned by `repay()` or `repayAll()` even though the collateral that repayment was intended to unlock has already been transferred to the liquidator and fee collector. [8](#0-7) [9](#0-8) 

This converts a normal liquidation loss into an additional avoidable loss equal to the repayment amount plus any repay fee. [10](#0-9) [11](#0-10) 

The repository’s own liquidation test demonstrates the required state transition: after maximal liquidation, the position remains unhealthy, the deposit balance is approximately zero, residual debt remains, and the borrower still holds the minted synthetic tokens used for repayment. [12](#0-11) 

### Likelihood Explanation
The only preconditions are an underwater borrower and a pending public repayment transaction; the attacker only needs synthetic tokens to burn and can call the public `liquidate()` entry point. [6](#0-5) [13](#0-12) 

The `CanNotLiquidateOwnPosition` check does not impede a third-party liquidator, while `whenNotShutdown`, `nonReentrant`, and the existence checks do not create any ordering or collateral-retention protection for a subsequent repayment. [14](#0-13) [15](#0-14) 

If `maxLiquidable` is below 100%, the attacker can perform consecutive liquidation calls in the same front-running bundle or block until the collateral is exhausted, provided the remaining debt stays above any configured debt floor. [16](#0-15) 

### Recommendation
Add an atomic repayment-and-collateral-withdrawal path, or add caller-controlled protection such as `minDepositInUsdAfterRepay`/`minUnlockedCollateral` to `repay()` and `repayAll()` and revert the whole transaction if the post-repayment collateral state is below the caller’s expectation. [17](#0-16) [4](#0-3) 

At minimum, revert voluntary repayments for accounts whose aggregate deposit value is zero while debt remains, although a minimum-collateral parameter is safer because it also prevents nearly complete collateral extraction before the repayment. [18](#0-17) [19](#0-18) 

### Proof of Concept
The following Hardhat test can be added inside the existing `when the position is unhealthy (collateral:debt < 1)` context in `test/Pool.test.ts`; the sequential liquidation models an attacker ordering its transaction before Alice’s pending `repayAll()` transaction. [20](#0-19) 

```ts
it('lets a liquidator front-run repayAll and make the borrower repay unbacked debt', async function () {
  await feeProvider.updateProtocolLiquidationFee(0)

  const debtBefore = await msEthDebtToken.balanceOf(alice.address)
  const synthBefore = await msEth.balanceOf(alice.address)
  const collateralBefore = await msdMET.balanceOf(alice.address)

  // Alice's pending transaction:
  // msEthDebtToken.connect(alice).repayAll(alice.address)

  // Attacker front-runs it and repays only enough debt to seize Alice's collateral.
  const amountToRepay = await pool.quoteLiquidateMax(msEth.address, alice.address, msdMET.address)

  expect(amountToRepay).gt(0)
  expect(amountToRepay).lt(debtBefore)

  await pool.connect(liquidator).liquidate(msEth.address, alice.address, amountToRepay, msdMET.address)

  const collateralAfterLiquidation = await msdMET.balanceOf(alice.address)
  const residualDebt = await msEthDebtToken.balanceOf(alice.address)

  expect(collateralAfterLiquidation).closeTo(0, collateralBefore.div(1000))
  expect(residualDebt).gt(0)

  // Alice's pending repayment still executes after all economically meaningful
  // collateral has been seized.
  await msEthDebtToken.connect(alice).repayAll(alice.address)

  expect(await msEthDebtToken.balanceOf(alice.address)).eq(0)
  expect(await msdMET.balanceOf(alice.address)).eq(collateralAfterLiquidation)
  expect(await msEth.balanceOf(alice.address)).eq(synthBefore.sub(residualDebt))
})
```

The important assertions are that `amountToRepay < debtBefore`, the post-liquidation deposit balance is approximately zero, and `repayAll()` still burns Alice’s remaining synthetic tokens instead of reverting. [7](#0-6) [2](#0-1)
