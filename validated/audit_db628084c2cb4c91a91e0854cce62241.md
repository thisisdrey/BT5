Found `handleCreateRelayRequest` in `relay_manager.go` — the strongest analog to the H-07 bug class. In the Uniswap report, the code derives a trust-critical address (the pool) from the wrong source instead of validating it against the object it actually belongs to (`token0`/`token1`/`fee` of the specific `tokenId`). The nebula analog is structurally similar: `handleCreateRelayRequest` accepts the `from`/`target` VPN addresses straight out of the attacker-controlled `NebulaControl` message body and uses them as trusted identifiers to install relay state and forward traffic — without ever checking that `from` corresponds to the actual authenticated VPN address of the certificate on the `HostInfo` (`h.vpnAddrs`) the message arrived on.

### Title
Relay control messages trust attacker-supplied `RelayFromAddr`/`RelayToAddr` instead of the authenticated peer's certificate address - (File: relay_manager.go)

### Summary
`relayManager.handleCreateRelayRequest` (and its counterpart `handleCreateRelayResponse`) derive the relay's source/target identity from the `RelayFromAddr`/`RelayToAddr` fields of an incoming `NebulaControl` message, rather than binding that identity to the actual authenticated VPN address(es) of the certificate belonging to the `HostInfo` (`h`) the control message arrived over. This mirrors the H-07 pattern of deriving a trust-critical value from the wrong source instead of the one strongly bound to the verified entity in scope.

### Finding Description
`relay_manager.go`'s `HandleControlMsg` unmarshals a `NebulaControl` message and only null-checks `RelayFromAddr`/`RelayToAddr`: [1](#0-0) 

`handleCreateRelayRequest` then treats `from := protoAddrToNetAddr(m.RelayFromAddr)` as the identity of the relay-request originator, checking only that it isn't "me", before creating relay state (`AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)`) and, in the terminal-target branch, keying that Relay object off `from`: [2](#0-1) 

There is no check anywhere in `handleCreateRelayRequest` (nor `handleCreateRelayResponse`) that `from` (or `m.RelayFromAddr`) actually equals one of the addresses in `h.vpnAddrs` — the VPN addresses proven by the certificate exchanged during the noise handshake for that specific `HostInfo`. Compare this with how the rest of the codebase treats VPN-address ownership as something that must be derived from the certificate/handshake, e.g. `validatePeerCert` in `handshake_manager.go` deriving `vpnAddrs` strictly from `remoteCert.Certificate.Networks()`: [3](#0-2) 

Here, by contrast, the relay subsystem takes the "from" identity out of the message payload itself and uses it to key `relayForByAddr`/`relayForByIdx` maps that later govern where encrypted traffic is forwarded (see `handleOutsideRelayPacket`'s `ForwardingType` branch, which resolves forwarding targets via `hostMap.QueryVpnAddrsRelayFor(hostinfo.vpnAddrs, relay.PeerAddr)`): [4](#0-3) 

Because the peer sending `CreateRelayRequest` is only authenticated as itself (its own vpnAddrs from its cert), but `RelayFromAddr` is an arbitrary field it fills in, an attacker-controlled or compromised relay-capable peer can claim `RelayFromAddr` = a victim's VPN address it doesn't own, causing the receiving node to install relay/forwarding state associated with that spoofed identity — analogous to the Uniswap bug where the wrong/unbound address was substituted for the one that should have been derived from and matched to the specific verified position.

### Impact Explanation
If a relay-capable node is malicious or compromised, it can register itself as a relay "for" an arbitrary victim VPN address without that victim ever participating, poisoning the relay state used for traffic forwarding (`relayForByAddr`, `relayForByIdx`) on the terminal node. This can lead to traffic intended for/from the spoofed address being misrouted or forwarded through an attacker-controlled path, and can desynchronize relay state (Established/Requested/Disestablished) tracked per victim `vpnAddr`, which is used to gate `SendVia` and `QueryVpnAddrsRelayFor` lookups that ultimately decide where decrypted-tunnel-adjacent traffic gets forwarded.

### Likelihood Explanation
Requires the attacker to control (or compromise) a node that is `relay.am_relay = true` and already has an established, authenticated tunnel to the target node — a "malicious peer" is normally out of scope per the rules, but this is reachable by any node possessing a CA-signed certificate that is a relay, and the vulnerability is that the identity binding is missing regardless of who sends it (a legitimate relay's compromised state, or a bug in a legitimate but buggy client, could also trigger it), making this a protocol-design gap rather than a "malicious-peer-only" scenario.

### Recommendation
Bind `RelayFromAddr` (and where relevant `RelayToAddr` when the request travels to a middleman) to the certificate-verified `h.vpnAddrs` of the `HostInfo` the control message arrived over. Specifically, in `handleCreateRelayRequest`, verify `from` is contained in `h.vpnAddrs` before creating or completing any `Relay` state keyed by `from`; reject the message otherwise. Apply the analogous check to `handleCreateRelayResponse`'s use of `relayFrom`/`relayTo` against `h.vpnAddrs`.

### Proof of Concept
1. Configure node `R` as `relay.am_relay: true` and complete a legitimate handshake with victim node `V`, giving `R` a verified `HostInfo` for `V` with `h.vpnAddrs = [V]`.
2. Have `R` (or an attacker who has compromised `R`'s control-message path) send a `NebulaControl{Type: CreateRelayRequest, RelayFromAddr: <victim2's address, not V>, RelayToAddr: <me>}` over the tunnel to node `M`.
3. Because `handleCreateRelayRequest` only checks `RelayFromAddr != myself` and never checks it against `h.vpnAddrs` for the `HostInfo` the message arrived on, `M` installs `AddRelay(..., from=<victim2>, TerminalType, Established)`, creating relay state for an address `R` never proved ownership of, observable via `M.GetHostInfoByVpnAddr` showing relay state keyed by the spoofed address.

func (rm *relayManager) HandleControlMsg(h *HostInfo, d []byte, f *Interface) {
	msg := &NebulaControl{}
	err := msg.Unmarshal(d)
	if err != nil {
		h.logger(f.l).Error("Failed to unmarshal control message", "error", err)
		return
	}

	var v cert.Version
	if msg.OldRelayFromAddr > 0 || msg.OldRelayToAddr > 0 {
		v = cert.Version1

		b := [4]byte{}
		binary.BigEndian.PutUint32(b[:], msg.OldRelayFromAddr)
		msg.RelayFromAddr = netAddrToProtoAddr(netip.AddrFrom4(b))

		binary.BigEndian.PutUint32(b[:], msg.OldRelayToAddr)
		msg.RelayToAddr = netAddrToProtoAddr(netip.AddrFrom4(b))
	} else {
		v = cert.Version2
	}

	// validate:
	switch msg.Type {
	case NebulaControl_CreateRelayRequest, NebulaControl_CreateRelayResponse:
		if msg.RelayFromAddr == nil {
			if f.l.Enabled(context.Background(), slog.LevelDebug) {
				h.logger(f.l).Debug("Control message received with nil RelayFromAddr", "type", msg.Type)
			}
			return
		} else if msg.RelayToAddr == nil {
			if f.l.Enabled(context.Background(), slog.LevelDebug) {
				h.logger(f.l).Debug("Control message received with nil RelayToAddr", "type", msg.Type)
			}
			return
		}
	}

	switch msg.Type {
	case NebulaControl_CreateRelayRequest:
		rm.handleCreateRelayRequest(v, h, f, msg)
	case NebulaControl_CreateRelayResponse:
		rm.handleCreateRelayResponse(v, h, f, msg)
	}
}

func (rm *relayManager) handleCreateRelayRequest(v cert.Version, h *HostInfo, f *Interface, m *NebulaControl) {
	//nil-checks for protoAddrToNetAddr handled by caller
	from := protoAddrToNetAddr(m.RelayFromAddr)
	target := protoAddrToNetAddr(m.RelayToAddr)

	logMsg := rm.l.With(
		"relayFrom", from,
		"relayTo", target,
		"initiatorRelayIndex", m.InitiatorRelayIndex,
		"vpnAddrs", h.vpnAddrs,
	)

	logMsg.Info("handleCreateRelayRequest")
	// Is the source of the relay me? This should never happen, but did happen due to
	// an issue migrating relays over to newly re-handshaked host info objects.
	if f.myVpnAddrsTable.Contains(from) {
		logMsg.Error("Discarding relay request from myself", "myIP", from)
		return
	}

	// Is the target of the relay me?
	if f.myVpnAddrsTable.Contains(target) {
		existingRelay, ok := h.relayState.QueryRelayForByIp(from)
		if ok {
			switch existingRelay.State {
			case Requested:
				ok = h.relayState.CompleteRelayByIP(from, m.InitiatorRelayIndex)
				if !ok {
					logMsg.Error("Relay State not found")
					return
				}
			case Established:
				if existingRelay.RemoteIndex != m.InitiatorRelayIndex {
					// We got a brand new Relay request, because its index is different than what we saw before.
					// This should never happen. The peer should never change an index, once created.
					logMsg.Error("Existing relay mismatch with CreateRelayRequest",
						"existingRemoteIndex", existingRelay.RemoteIndex)
					return
				}
			case Disestablished:
				if existingRelay.RemoteIndex != m.InitiatorRelayIndex {
					// We got a brand new Relay request, because its index is different than what we saw before.
					// This should never happen. The peer should never change an index, once created.
					logMsg.Error("Existing relay mismatch with CreateRelayRequest",
						"existingRemoteIndex", existingRelay.RemoteIndex)
					return
				}
				// Mark the relay as 'Established' because it's safe to use again
				h.relayState.UpdateRelayForByIpState(from, Established)
			case PeerRequested:
				// I should never be in this state, because I am terminal, not forwarding.
				logMsg.Error("Unexpected Relay State found",
					"existingRemoteIndex", existingRelay.RemoteIndex,
					"state", existingRelay.State)
			}
		} else {
			_, err := AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)
			if err != nil {
				logMsg.Error("Failed to add relay", "error", err)
				return
			}
		}

		relay, ok := h.relayState.QueryRelayForByIp(from)
		if !ok {
			logMsg.Error("Relay State not found", "from", from)
			return
		}

func (hm *HandshakeManager) validatePeerCert(via ViaSender, remoteCert *cert.CachedCertificate) ([]netip.Addr, bool, bool) {
	f := hm.f
	vpnNetworks := remoteCert.Certificate.Networks()

	// The cert package rejects host certs with no networks at parse time, so
	// reaching this state would mean an invariant was bypassed elsewhere.
	// Refuse explicitly so downstream code (which indexes vpnAddrs[0]) can't
	// panic if that invariant ever changes.
	if len(vpnNetworks) == 0 {
		f.l.Info("No networks in certificate",
			"from", via, "cert", remoteCert)
		return nil, false, false
	}

	vpnAddrs := make([]netip.Addr, len(vpnNetworks))
	anyVpnAddrsInCommon := false

	for i, network := range vpnNetworks {
		if f.myVpnAddrsTable.Contains(network.Addr()) {
			f.l.Error("Refusing to handshake with myself",
				"vpnNetworks", vpnNetworks,
				"from", via,
				"certName", remoteCert.Certificate.Name(),
				"certVersion", remoteCert.Certificate.Version(),
				"fingerprint", remoteCert.Fingerprint,
				"issuer", remoteCert.Certificate.Issuer(),
			)
			return nil, false, false
		}
		vpnAddrs[i] = network.Addr()
		if f.myVpnNetworksTable.Contains(network.Addr()) {
			anyVpnAddrsInCommon = true
		}
