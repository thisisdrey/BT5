# Rejected/Stalled Auction Analog: Investor Principal Permanently Locked in `FullyFunded` Loans With No Disbursement Escape Path

### Title
Investor capital gets permanently stuck when a `FullyFunded` loan is never disbursed - ([File: tare-io__tare-contracts/contracts/Loans.sol])

### Summary
The external report describes a pool that reaches a terminal "rejected auction" state with no function able to close it or return funds, leaving the pool open indefinitely. The Tare `Loans` contract has an analogous unclosable intermediate state: once a loan is funded to `FullyFunded` (investor capital already pulled into the contract's `ACC_CASH`/`ACC_INVESTOR_PRINCIPAL_PAYABLE`), the *only* path that moves that cash back out to any party is `disburse()` (to the borrower) or `investorWithdraw()` (computed from principal-*repaid* accounts). If the originator never calls `disburse` — e.g. because they walk away, the deal falls through off-chain, or the borrower's terms are later rejected — the loan is stuck in `FullyFunded` with investor cash locked in the contract and no function to unwind it.

### Finding Description
The loan status lifecycle only allows the following transitions relevant here [1](#0-0) :
- `fund` moves `Created -> FullyFunded` when the investor deposits the full commitment.
- `disburse` requires `FullyFunded` and moves to `Active`, calling `originators[loanId]` (or admin) to push funds to the borrower [2](#0-1) .

`fund()` is explicitly single-shot and gated to `status == Created`, so once funded there is no "unfund" function to give the investor their deposit back [3](#0-2) .

`updateLoanData` can flip the status field to any value (e.g., `Cancelled`) but performs **no ledger/cash movement** — it is purely a metadata update [4](#0-3) . This mirrors the reported bug's root cause: a status flag can be forced into a terminal-looking state, but the underlying locked value is never released.

The only functions that actually transfer ERC-20 out of the contract to the investor (`investorWithdraw`) compute the payable amount from `ACC_BORROWER_PRINCIPAL_REPAID` / `ACC_INVESTOR_PRINCIPAL_REPAID` balances, which are populated only after `disburse` → `pay` → `applyWaterfall` have run, per the documented formula `_getNetPrincipalPayableToInvestor = -ACC_BORROWER_PRINCIPAL_REPAID - ACC_INVESTOR_PRINCIPAL_REPAID` [5](#0-4) . For a loan that is `FullyFunded` but never disbursed, both of those accounts are zero, so even if the status is force-flipped (e.g., to `Cancelled`), `investorWithdraw` computes a `0` payout — the investor's already-deposited principal (sitting in `ACC_CASH`) is not recoverable through it.

Additionally, `createLedgerEntries` — the general-purpose manual ledger-adjustment escape hatch used elsewhere in the codebase (see the early-cancellation "recovery flow" pattern) — explicitly forbids `ACC_CASH` as a `from`/`to` account [6](#0-5) , closing off the manual-entry workaround that is otherwise used to recover from bad status transitions (as documented for the `Cancelled` re-open pattern in Scenario C of `early_cancellation.md`) [7](#0-6) .

`refundBorrower` and `returnFunds` are also gated to `_onlyOutstandingOrFullyPaid` (`Active`, `ChargedOff`, `FullyPaid`), so they cannot be used on a `FullyFunded` loan either [8](#0-7) .

### Impact Explanation
If a loan is funded by the investor (full commitment pulled into the contract) but the originator never disburses it (deal cancelled off-chain, originator becomes unresponsive, KYC/underwriting rejection after funding, etc.), the investor's principal is permanently locked in the contract with no on-chain function capable of returning it. This is a real, unrecoverable loss of USDC for an honest investor — matching the "Permanent or practically unrecoverable lock of USDC ... caused by an unprivileged path" impact category, since the investor (an unprivileged, non-admin party) has no recourse once they've funded.

### Likelihood Explanation
This does not require an attacker; it is a normal-looking operational sequence (`create` → `fund`) that stalls before `disburse`. Any originator inaction, dispute, or off-chain rejection after funding — directly analogous to a "rejected auction" — triggers the stuck state. This makes the likelihood of occurrence non-trivial in production usage rather than requiring adversarial conditions.

### Recommendation
Add an explicit unwind/cancellation path for `FullyFunded` loans that have not yet been disbursed, e.g. an `unfund()`/`cancelFullyFundedLoan()` function (servicer/admin or time-boxed investor-triggered) that reverses the `fund` ledger entry (`ACC_INVESTOR_PRINCIPAL_PAYABLE` → `ACC_CASH`) and transfers the deposited principal back to the current NFT holder, then transitions the loan to `Cancelled`. Document this state and its resolution explicitly in the servicing spec so the invariant "every terminal or stalled state has a cash-recovery path" is guaranteed for all pre-`Active` statuses, not only post-`Active` ones.

### Proof of Concept
1. Originator calls `create(...)`, loan status = `Created`.
2. Investor calls `fund(loanId, commitment, ...)`; loan auto-transitions to `FullyFunded`; investor's USDC is now custodied in the contract (`ACC_CASH == commitment`, `ACC_INVESTOR_PRINCIPAL_PAYABLE == -commitment`) [3](#0-2) .
3. Originator never calls `disburse` (or is unable/unwilling to).
4. Investor attempts recovery:
   - `fund()` reverts (`status != Created`).
   - `disburse()` can only be called by the originator/admin — investor cannot self-serve.
   - `refundBorrower`/`returnFunds` revert (`onlyOutstandingOrFullyPaid` fails for `FullyFunded`) [8](#0-7) .
   - Even if servicer/admin calls `updateLoanData(loanId, LoanStatus.Cancelled, ...)`, `investorWithdraw` still computes `0` because `ACC_BORROWER_PRINCIPAL_REPAID`/`ACC_INVESTOR_PRINCIPAL_REPAID` were never populated (only `disburse`+`pay`+`applyWaterfall` populate them) [5](#0-4) .
   - `createLedgerEntries` cannot move `ACC_CASH` manually to fix this [6](#0-5) .
5. Result: `commitment` USDC remains in the contract indefinitely, unattributable to any withdrawal path.

**Note on verification limits:** I was unable to fully inspect the body of `investorWithdraw` (only referenced via its documented formula in `early_cancellation.md`) before running out of tool iterations. I could not confirm whether any other admin-only recovery mechanism (outside the functions checked) exists that could move `ACC_CASH` for a `FullyFunded` loan. If such a path exists, it likely falls under a privileged role and would fall outside the audit's allowed impact gate for non-privileged unlock issues; if not, the finding stands as described.

    uint64 loanId,
    int128 amount,
    uint48 timestamp,

  ) external whenNotPaused nonReentrant withLoanUpdate(loanId, timestamp) returns (uint128 entryIndex) {
    address investorAddress = loansNFT.ownerOf(loanId);

    _requireCallerOrAdmin(investorAddress);
    require(amount > 0, InvalidAmount());

    require(amount == commitment, InvalidAmount());

    _updateLoanData(loanId, LoanStatus.FullyFunded, 0, 0);

        loanId,
        ACC_INVESTOR_PRINCIPAL_PAYABLE,
        amount,
        investorAddress,
        timestamp,
        ENTRY_INVESTOR_CAPITAL_RECEIVED,
        ref
      );

## Scenario C — Status was set to `Cancelled` before borrower repaid

Servicer set `status = Cancelled` via `updateLoanData` while `ACC_BORROWER_PRINCIPAL_RECEIVABLE` was still non-zero.

### Effect of the premature transition

Once `status == Cancelled`, the following calls revert by status guard:

- `pay`, `accrue`, `chargeMiscFee` — `onlyOutstanding`
- `applyWaterfall`, `refundBorrower`, `returnFunds` — `onlyOutstandingOrFullyPaid`
- `updateBorrower`, `updateServicer` — `notTerminal`

`createLedgerEntries`, `updateLoanData`, `originatorWithdraw`, `investorWithdraw`, and `servicerWithdraw` are not status-gated and remain callable.

No funds are lost: cash balances and investor-side payables are untouched by a status flip, and the investor cannot withdraw what was never waterfalled.

### Recovery flow

`updateLoanData` is not guarded by `notTerminal`, so the servicer (or admin) can flip the status back out of `Cancelled`:

1. **Servicer** calls `updateLoanData(loanId, LoanStatus.Active, 0, 0, timestamp)`.
2. Proceed with Scenario A (or Scenario B if interest was accrued).
3. The final `updateLoanData(loanId, LoanStatus.Cancelled, …)` in step 5 returns the loan to terminal state.

The intermediate `Cancelled → Active → Cancelled` transitions are visible in `LoanStatusUpdated` events. Off-chain consumers must tolerate this re-opening pattern.
