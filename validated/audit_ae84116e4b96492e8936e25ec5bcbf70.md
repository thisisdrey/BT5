### Title
Non-constant-time HTTP authorization-token comparison enables timing-based token recovery - ([File: stackslib/src/net/api/postblock_v3.rs])

### Summary
Every authenticated `stacks-node` RPC endpoint that gates access with the shared `auth_token`/password checks the client-supplied `authorization` header against the configured secret using ordinary Rust string inequality (`auth_header != password`), which short-circuits on the first mismatched byte. This produces a timing side-channel discrepancy analogous in class (CWE-203/"Observable Discrepancy" family, which includes the timing variant CWE-208) to the OpenCRX report's password-reset error-message enumeration: an outside, unauthenticated party can distinguish "how many leading bytes I guessed correctly" from response latency instead of from differing error text, and use that oracle to recover the secret token byte-by-byte instead of guessing all the entropy at once.

### Finding Description
Several `net/api/*.rs` request handlers implement the same pattern for validating the shared bearer token before parsing/handling privileged requests: [1](#0-0) [2](#0-1) [3](#0-2) 

In each case, `auth_header != password` is a plain `String`/`str` comparison. Rust's `PartialEq` for byte slices (backing `str`/`String` equality) performs a length check followed by a `memcmp`-style comparison that returns as soon as a differing byte is found; it is not designed to run in constant time relative to the shared-prefix length between the two operands. This breaks the intended equality check's confidentiality property: it is supposed to be a binary secret/not-secret decision, but it actually leaks a partial-match signal through response timing — exactly the same bug class as an oracle that leaks whether a *prefix* of a secret is correct, which is the generalization of the "distinguishable outcome for a partially-correct guess" flaw described in the OpenCRX report (there manifested as differing error text; here as differing timing).

This same comparison pattern recurs across the authenticated endpoint family (`postblock_v3.rs`, `blockreplay.rs`, `blocksimulate.rs`, `txsimulate.rs`, `fastcallreadonly.rs`, `postblock_proposal.rs`), all of which gate write-capable or resource-intensive RPCs (`/v2/blocks?broadcast=1`, `/v3/block_proposal`, `/v3/blocks/replay`, `/v3/blocks/simulate`, `/v3/transactions/simulate`, fast read-only calls) behind the identical `auth_token` secret configured in `connection_options.auth_token`.

### Impact Explanation
If exploitable, an attacker who can send many requests and measure response latency with enough precision could recover the `auth_token` byte-by-byte rather than needing to brute-force the whole secret, which is materially cheaper. Recovering the token yields **authentication bypass** on privileged endpoints — most notably `/v3/block_proposal` (block proposal submission consumed by the signer) and `/v2/blocks?broadcast=1` (authenticated block broadcast), i.e., unauthorized write/control-plane access, which matches the "auth bypass" / "unauthenticated/unauthorized write to state" impact tier called for in scope.

However, this is fundamentally a **timing side-channel**, and its practical exploitability over a real network (with TCP/HTTP stack jitter, OS scheduling noise, and the very short strings typically compared) is uncertain and difficult to demonstrate empirically without live timing measurements against the actual server — something outside what can be verified from static code alone. This weakens confidence versus a hard equality/logic bug and is why this is flagged with lower certainty than a definitive protocol-level flaw.

### Likelihood Explanation
Low-to-medium. The comparison happens once per request at the HTTP parsing layer, wrapped in TLS/TCP round-trip, async I/O scheduling and node-side JSON/DB work variance in some paths, all of which add substantial timing noise that a remote attacker would need to average out over very many samples per byte. It is plausible on a low-latency, low-jitter LAN (e.g., an operator's node and signer on the same network) but harder over the public internet. This is a real code smell/best-practice violation (secret comparisons should use constant-time equality, e.g. `subtle::ConstantTimeEq`) rather than a conclusively demonstrated remote exploit.

### Recommendation
Replace the direct `!=`/`==` comparisons of `auth_header` against `password` in `postblock_v3.rs`, `blockreplay.rs`, `blocksimulate.rs`, `txsimulate.rs`, `fastcallreadonly.rs`, and `postblock_proposal.rs` with a constant-time comparison (e.g., using the `subtle` crate's `ConstantTimeEq`, or an HMAC-based comparison) so that comparison time is independent of the number of matching prefix bytes.

### Proof of Concept
Not independently verified with live timing measurements (would require running the node and performing statistical timing analysis over the network, which is outside what the static code review here can confirm). Conceptually: for endpoints such as `/v3/blocks/replay` or `/v2/blocks?broadcast=1`, send repeated authenticated requests with candidate tokens differing at successive byte positions and measure whether requests that match a longer correct prefix consistently return marginally faster/slower than those that mismatch earlier, then use that signal to iteratively recover the token — this is the intended exploitation shape given the code at [4](#0-3) .
