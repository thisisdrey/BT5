### Title
Rewards emitted while DepositToken/DebtToken `totalSupply` is zero are permanently burned because `_calculateTokenIndex` advances `timestamp` without crediting the index - (contracts/RewardsDistributor.sol)

### Summary
`RewardsDistributor._calculateTokenIndex` consumes elapsed time even when `token_.totalSupply() == 0`, dropping `deltaTimestamp * speed` rewards on the floor. This is the Metronome analog of the StakingRewardsV3-1 bug: rewards scheduled before the first depositor (or during any zero-supply gap after a full exit) are emitted against nobody and can never be claimed, permanently freezing that portion of the `rewardToken` balance in the contract.

### Finding Description
In `_calculateTokenIndex`, when `speed > 0` and `deltaTimestamps > 0` but `totalSupply == 0`, `_ratio` is set to `0`, yet `_newTimestamp` is still returned as `block.timestamp`. `_updateTokenIndex` then stores that new timestamp, so the elapsed window is marked as processed while its rewards were assigned to no one. [1](#0-0)  The write happens in `_updateTokenIndex`, which stores `_newTimestamp` regardless of whether the index increased. [2](#0-1) 

Two reachable paths:

1. `updateTokenSpeed(token, speed>0)` initializes `TokenState{index: INITIAL_INDEX, timestamp: now}` while supply is still zero; the first mint calls `updateBeforeMintOrBurn` pre-mint, sees `totalSupply == 0`, advances `timestamp`, and every second since speed activation is lost. [3](#0-2) 
2. More relevantly for an unprivileged attacker: when the last holder redeems/burns (DepositToken or DebtToken `totalSupply` back to 0) while `tokenSpeeds > 0`, the emission clock keeps running but every `updateBeforeMintOrBurn`/`updateBeforeTransfer`/anyone's call stamps out the zero-supply interval, discarding `deltaTimestamp * speed` rewards. The attacker does not profit directly, but protocol rewards meant for holders are permanently frozen in the contract.

There is no recovery/sweep path in `RewardsDistributor` (it does not inherit `TokenHolder`), and `_transferRewardIfEnoughTokens` only pays out accrued amounts, so the stranded `rewardToken` balance is stuck. [4](#0-3) 

### Impact Explanation
Permanent freezing of unclaimed yield. Every second of `tokenSpeed` emission that elapses while the rewarded token's supply is zero produces rewards that are never assigned to any `accountIndexOf` and can never be claimed — the `rewardToken` stays locked in the distributor forever. Over a long zero-supply window this can be an arbitrarily large fraction of the funded rewards.

### Likelihood Explanation
No privileged action is required once speeds are set: an unprivileged user who is the last depositor/borrower can trigger a zero-supply window by withdrawing/repaying in full, and the contract is permissionlessly poked via `updateBeforeMintOrBurn`, which "may be called by anyone". [5](#0-4)  However, causing a *large* loss requires the supply to stay at zero for an extended period, which depends on organic protocol inactivity rather than attacker control alone — the attacker can open the window but cannot force it to remain open.

### Recommendation
Do not advance `TokenState.timestamp` when `totalSupply == 0` (or when `_ratio == 0` due to zero supply). In `_calculateTokenIndex`, only return `_newTimestamp = block.timestamp` if `totalSupply > 0`, so the elapsed time is not consumed until a real supply exists to absorb it:

```solidity
uint256 _totalSupply = token_.totalSupply();
if (_deltaTimestamps > 0 && _speed > 0 && _totalSupply > 0) {
    uint256 _tokensAccrued = _deltaTimestamps * _speed;
    uint256 _ratio = _tokensAccrued.wadDiv(_totalSupply);
    _newIndex = (_supplyState.index + _ratio).toUint224();
    _newTimestamp = block.timestamp.toUint32();
} else if (_deltaTimestamps > 0 && _supplyState.index > 0) {
    _newTimestamp = block.timestamp.toUint32();
}
```
This way rewards emitted during zero-supply are deferred and distributed to subsequent holders rather than burned.

### Proof of Concept
Hardhat sketch (mirroring `test/RewardDistributor.test.ts` setup with mocked ms/debt tokens):

```ts
// speed active, supply == 0
await rewardDistributor.updateTokenSpeed(msdTOKEN1.address, parseEther('1'));
msdTOKEN1.totalSupply.returns(0);

// one hour passes with zero supply
await increaseTimeOfNextBlock(3600);

// first depositor mints -> updateBeforeMintOrBurn consumes the window
await rewardDistributor.updateBeforeMintOrBurn(msdTOKEN1.address, alice.address);

const { index, timestamp } = await rewardDistributor.tokenStates(msdTOKEN1.address);
// index stayed INITIAL_INDEX (no rewards indexed) ...
expect(index).eq(INITIAL_INDEX);
// ... but timestamp advanced: the 3600 reward tokens are lost forever
expect(timestamp).eq(await time.latest());

// alice mints, another hour passes with supply > 0
msdTOKEN1.totalSupply.returns(parseEther('100'));
msdTOKEN1.balanceOf.returns(parseEther('100'));
await increaseTimeOfNextBlock(3600);

const claimable = await rewardDistributor['claimable(address)'](alice.address);
// alice only receives 3600e18, not 7200e18 — the first hour's emission is stuck in the contract
expect(claimable).eq(parseEther('3600'));
```
