Confirmed: `LinkRepositoryToObjectPool` performs no ownership/relationship check between the caller-controlled `repository` field and the `object_pool` field—both are gitalypb.Repository descriptors an ordinary RPC caller controls, validated only for existing/well-formed paths, not for any fork-network/authorization relation between them.

### Title
Unprivileged cross-repository object disclosure via `LinkRepositoryToObjectPool` linking arbitrary repository to arbitrary object pool - (File: internal/gitaly/service/objectpool/link.go)

### Summary
`LinkRepositoryToObjectPool` writes the target object pool's object directory into the caller-specified repository's `objects/info/alternates` file, granting that repository full read access to every object contained in the pool. Gitaly performs no check that the `repository` and `object_pool` fields actually belong to the same fork network or that the caller is authorized to associate them; it merely validates that both are well-formed, existing paths.

### Finding Description
The handler [1](#0-0)  extracts `repository` and `object_pool`, calling `s.locator.ValidateRepository` (path validity only) and `s.poolForRequest` (pool existence/validity only) before invoking `pool.Link(ctx, repo)`. Neither step verifies that `repository` is a legitimate member of `object_pool`'s fork network. The proto explicitly documents both fields as caller-supplied, independently-addressed repositories: [2](#0-1) . The underlying `Link` function then unconditionally writes the pool's absolute objects path into the repository's alternates file: [3](#0-2) . Once linked, any Git operation on the "member" repository (e.g., `git cat-file`, `git log`, clone) can read every object present in the specified pool, because alternates grant unrestricted object visibility, and `linkedToRepository`/`getRelativeObjectPath` only compare paths for idempotency, not authorization: [4](#0-3) .

This mirrors the reported bug class ("burns from receiver instead of enforcing an owner/relationship check"): the RPC operates on two independently attacker-suppliable repository identifiers without validating that they belong together, and the resulting privileged action (alternates linkage granting cross-repository object access) is performed anyway. Gitaly itself has no server-side notion of "this repository is a fork of this pool's origin"; that check is left entirely to the calling layer (e.g., GitLab Rails), matching the pattern where "validation on the server side" is what currently prevents exploitation, per the report's caveat.

### Impact Explanation
If a Gitaly RPC caller (or any component with access to the `ObjectPoolService`, e.g., a compromised/lower-trust internal caller, or a code path that fails to perform the origin/fork-network check before calling Gitaly) can invoke `LinkRepositoryToObjectPool` with an attacker-controlled `repository` and a victim's private `object_pool`, the attacker's repository becomes able to read every git object stored in that object pool — including commits, blobs, and trees. This is a cross-repository object disclosure of potentially private data, since object pools are typically populated from the objects of the pool's source (often a private upstream) repository. It could also be leveraged to poison packfile/bitmap state or trigger unnecessary computation (`removeMemberBitmaps`, `git fsck` in `Disconnect`) on unrelated repositories.

### Likelihood Explanation
Low but non-negligible, matching the referenced report's own likelihood rating. Gitaly is designed to be called by trusted upstream layers (GitLab Rails/Workhorse/Praefect) that are supposed to perform the fork-network/authorization check before issuing `LinkRepositoryToObjectPool`. As with the analog report, this makes exploitation dependent on validation happening correctly in the rest of the stack; a bug or bypass in that upstream authorization (or any alternate caller of the Gitaly RPC surface) would make this directly exploitable with no additional Gitaly-side defense in depth.

### Recommendation
Add a Gitaly-side invariant check in `LinkRepositoryToObjectPool` (and ideally `FetchIntoObjectPool`/`DisconnectGitAlternates`) that verifies the target `repository` and `object_pool` are related by an expected mechanism — e.g., requiring pool metadata (already tracked via `poolStore`/`relational.PoolStore`, see [5](#0-4) ) confirming that `repository` is a registered/expected member before writing alternates, rather than relying solely on upstream authorization. This provides defense-in-depth analogous to enforcing the action against a validated identity rather than trusting an arbitrary caller-supplied field.

### Proof of Concept
1. As a caller with access to `ObjectPoolService` (e.g., via a bypass of the upstream Rails authorization check, or a caller with direct Gitaly access), create/obtain a `Repository` you control (`repoA`).
2. Obtain the `ObjectPool` descriptor of a victim's private object pool (`poolVictim`) — e.g., leaked or guessed `storage_name`/`relative_path`.
3. Call:
```
LinkRepositoryToObjectPool(ctx, &LinkRepositoryToObjectPoolRequest{
    Repository: repoA,
    ObjectPool: poolVictim,
})
```
4. Gitaly writes `poolVictim`'s object directory into `repoA/objects/info/alternates` (`internal/git/objectpool/link.go:54-66`).
5. Any subsequent read on `repoA` (e.g., `git cat-file -p <oid>` for an object ID from the victim pool, or cloning `repoA`) discloses objects that were only supposed to be accessible within the victim's pool/fork network.

func (s *server) LinkRepositoryToObjectPool(ctx context.Context, req *gitalypb.LinkRepositoryToObjectPoolRequest) (*gitalypb.LinkRepositoryToObjectPoolResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	pool, err := s.poolForRequest(ctx, req)
	if err != nil {
		return nil, err
	}

	repo := s.localRepoFactory.Build(repository)

	if err := pool.Link(ctx, repo); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	return &gitalypb.LinkRepositoryToObjectPoolResponse{}, nil

// Link will link the given repository to the object pool. This is done by writing the object pool's
// path relative to the repository into the repository's "alternates" file. This does not trigger
// deduplication, which is the responsibility of the caller.
func Link(ctx context.Context, pool, repo *localrepo.Repo, txManager transaction.Manager) (returnedErr error) {
	altPath, err := repo.InfoAlternatesPath(ctx)
	if err != nil {
		return err
	}

	expectedRelPath, err := getRelativeObjectPath(ctx, pool, repo)
	if err != nil {
		return err
	}

	linked, err := linkedToRepository(ctx, pool, repo)
	if err != nil {
		return err
	}

	if linked {
		// When the repository is already linked to the repository, cast a vote to ensure the
		// repository is consistent with the other replicas.
		if err := transaction.VoteOnContext(ctx, txManager, voting.VoteFromData([]byte("repository linked")), voting.Synchronized); err != nil {
			return fmt.Errorf("vote on linked repository: %w", err)
		}

		return nil
	}

	alternatesWriter, err := safe.NewLockingFileWriter(altPath)
	if err != nil {
		return fmt.Errorf("creating alternates writer: %w", err)
	}
	defer func() {
		if err := alternatesWriter.Close(); err != nil && returnedErr == nil {
			returnedErr = fmt.Errorf("closing alternates writer: %w", err)
		}
	}()

	if _, err := io.WriteString(alternatesWriter, expectedRelPath); err != nil {
		return fmt.Errorf("writing alternates: %w", err)
	}

// linkedToRepository tests if a repository is linked to an object pool
func linkedToRepository(ctx context.Context, pool, repo *localrepo.Repo) (bool, error) {
	poolPath, err := pool.Path(ctx)
	if err != nil {
		return false, fmt.Errorf("getting object pool path: %w", err)
	}

	repoPath, err := repo.Path(ctx)
	if err != nil {
		return false, fmt.Errorf("getting repo path: %w", err)
	}

	altInfo, err := stats.AlternatesInfoForRepository(repoPath)
	if err != nil {
		return false, fmt.Errorf("getting alternates info: %w", err)
	}

	if !altInfo.Exists || len(altInfo.ObjectDirectories) == 0 {
		return false, nil
	}

	relPath := altInfo.ObjectDirectories[0]
	expectedRelPath, err := getRelativeObjectPath(ctx, pool, repo)
	if err != nil {
		return false, err
	}

	if relPath == expectedRelPath {
		return true, nil
	}

	if filepath.Clean(relPath) != filepath.Join(poolPath, "objects") {
		return false, fmt.Errorf("unexpected alternates content: %q", relPath)
	}

	return false, nil
}
