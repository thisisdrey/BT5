### Title
Stale in-memory `AccountCapsule` overwrite causes loss of maker-side asset credit on order self-match - (File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java)

### Summary
`MarketSellAssetActuator.execute()` loads a single `AccountCapsule` for the taker (`accountCapsule`) at the start of execution and keeps mutating that same in-memory reference throughout order matching, only persisting it once at the very end via `accountStore.put(accountCapsule.createDbKey(), accountCapsule)` [1](#0-0) . However, when the taker order matches against a maker order, the maker-side credit is applied via a helper that independently re-reads the account from the store, mutates it, and writes it back immediately: `addTrxOrToken(MarketOrderCapsule orderCapsule, long num)` [2](#0-1) .

### Finding Description
This mirrors the Perennial `Market.update()` bug class: a function operates on one in-memory copy of state and mutates it, while persistence is driven by a *different* copy of the same underlying record, so the mutations to the first copy are silently discarded (or vice versa) once the final write happens.

In `matchSingleOrder()`, the taker's account is passed in and mutated via `addTrxOrToken(takerOrderCapsule, takerBuyTokenQuantityReceive, takerAccountCapsule)` (the 3-argument overload, which mutates the passed-in `takerAccountCapsule` reference without writing to the store) [3](#0-2) [4](#0-3) . The maker side is credited via the 2-argument overload of `addTrxOrToken`, which does its own fresh `accountStore.get(orderCapsule.getOwnerAddress())`, mutates that separate object, and immediately calls `accountStore.put(...)` [2](#0-1) .

When the taker and maker addresses are the **same account** (a user's own resting order matches their own new taker order — self-match, which is not prevented in the code reachable from this file), the sequence within a single transaction becomes:
1. `accountCapsule` (taker reference) is loaded once and held for the whole `execute()` call, accumulating fee deduction, sell-side debit (`transferBalanceOrToken`), and any taker-side buy credit.
2. During matching, `addTrxOrToken(makerOrderCapsule, makerBuyTokenQuantityReceive)` loads a **second, independent** `AccountCapsule` for the same address from the store (which does not yet reflect the in-memory mutations on `accountCapsule`), credits the maker-side buy token to it, and immediately persists it via `accountStore.put()`.
3. At the end of `execute()`, `accountStore.put(accountCapsule.createDbKey(), accountCapsule)` writes the **original taker-held reference**, which does not include the maker-side credit applied in step 2 — overwriting and erasing that credit.

The root cause is structurally identical to the reported issue: an update is applied to one loaded copy of account state but the function responsible for final persistence uses a stale copy, so the update from the intermediate operation never survives.

### Impact Explanation
For a self-matching order, the account's maker-side proceeds (`makerBuyTokenQuantityReceive` worth of the buy token, or TRX if the buy side is TRX) are computed, briefly written to the store, and then unconditionally overwritten by the final `accountStore.put()` call using the stale taker-held capsule at the end of `execute()`. This causes concrete loss of assets/tokens credited to the account, matching the "loss of account funds" impact category from the analog report, and is reachable from a single unprivileged `MarketSellAssetContract` transaction (no special permission required) via the standard order-placing transaction type.

### Likelihood Explanation
Likelihood requires a user to have a resting maker order in the order book which subsequently matches against their own new taker `MarketSellAssetContract`, on the same trading pair, at a price where `hasMatch()` returns true — something entirely under attacker control since they can place both the maker order and (a moment later) the matching taker order themselves. No validation against self-matching was found within `MarketSellAssetActuator` in the code inspected (a full `validate()` review to definitively rule out an owner-equality check could not be completed in the tool budget, so this should be verified against the actual `validate()` method before treating this as fully confirmed).

### Recommendation
`addTrxOrToken(MarketOrderCapsule orderCapsule, long num)` (the maker-side overload) should reuse the same in-memory `AccountCapsule` reference as the taker when `orderCapsule.getOwnerAddress()` equals the taker's owner address, instead of re-fetching a fresh copy from `accountStore`. More generally, all account mutations touching the same address within one `execute()` invocation should operate on a single cached `AccountCapsule` instance (or be flushed/re-read consistently) before any partial `accountStore.put()` is issued, so that the final write in `execute()` cannot clobber intermediate updates made to the same account during order matching.

### Proof of Concept
1. Account `A` places a sell order O1 (sell token X for token Y) that rests in the order book (`saveRemainOrder`) — reachable via `MarketSellAssetActuator` [5](#0-4) .
2. Account `A` (same address) submits a second `MarketSellAssetContract` selling token Y for token X at a matching price, making O1 the maker order and the new order the taker order.
3. During `matchOrder`/`matchSingleOrder`, `addTrxOrToken(makerOrderCapsule, makerBuyTokenQuantityReceive)` re-reads `A`'s account from `accountStore`, credits it with token X, and writes it back immediately [2](#0-1) .
4. At the end of `execute()`, the stale `accountCapsule` (taker reference, missing the maker credit) is written back via `accountStore.put(accountCapsule.createDbKey(), accountCapsule)` [6](#0-5) , erasing the maker-side token X credit applied in step 3.

  @Override
  public boolean execute(Object object) throws ContractExeException {
    initStores();

    TransactionResultCapsule ret = (TransactionResultCapsule) object;
    if (Objects.isNull(ret)) {
      throw new RuntimeException(TX_RESULT_NULL);
    }

    long fee = calcFee();

    try {
      final MarketSellAssetContract contract = this.any
          .unpack(MarketSellAssetContract.class);

      AccountCapsule accountCapsule = accountStore
          .get(contract.getOwnerAddress().toByteArray());

      sellTokenID = contract.getSellTokenId().toByteArray();
      buyTokenID = contract.getBuyTokenId().toByteArray();
      sellTokenQuantity = contract.getSellTokenQuantity();
      buyTokenQuantity = contract.getBuyTokenQuantity();
      MarketPrice takerPrice = MarketPrice.newBuilder()
          .setSellTokenQuantity(sellTokenQuantity)
          .setBuyTokenQuantity(buyTokenQuantity).build();

      // fee
      accountCapsule.setBalance(accountCapsule.getBalance() - fee);
      // add to blackhole address
      if (dynamicStore.supportBlackHoleOptimization()) {
        dynamicStore.burnTrx(fee);
      } else {
        adjustBalance(accountStore, accountStore.getBlackhole(), fee);
      }
      // 1. transfer of balance
      transferBalanceOrToken(accountCapsule);

      // 2. create and save order
      MarketOrderCapsule orderCapsule = createAndSaveOrder(accountCapsule, contract);

      // 3. match order
      matchOrder(orderCapsule, takerPrice, ret, accountCapsule);

      // 4. save remain order into order book
      if (orderCapsule.getSellTokenQuantityRemain() != 0) {
        saveRemainOrder(orderCapsule);
      }

      orderStore.put(orderCapsule.getID().toByteArray(), orderCapsule);
      accountStore.put(accountCapsule.createDbKey(), accountCapsule);
