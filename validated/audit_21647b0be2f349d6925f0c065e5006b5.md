## Title
Missing slippage/minimum-received protection in `ExchangeInjectContract`/`ExchangeWithdrawContract` enables front-run/sandwich attacks on TRON's built-in Bancor-formula Exchange — (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
Java-tron's on-chain Exchange (a Bancor-formula AMM) exposes three actuators: `ExchangeInjectActuator`, `ExchangeWithdrawActuator`, and `ExchangeTransactionActuator`. Only `ExchangeTransactionContract` carries an `expected` field used to bound the amount of tokens the trader will accept, protecting sellers against slippage. `ExchangeInjectContract` and `ExchangeWithdrawContract` carry no equivalent bound, so the counter-token amount computed at execution time is whatever the current on-chain reserve ratio dictates, with no user-specified minimum/maximum.

### Finding Description
`ExchangeTransactionContract` defines `expected` (minimum tokens to receive) and `ExchangeTransactionActuator.doValidate()` enforces `anotherTokenQuant >= tokenExpected`, rejecting the transaction otherwise: [1](#0-0) 

By contrast, `ExchangeInjectContract` only has `owner_address`, `exchange_id`, `token_id`, `quant` — no expected/min-out field: [2](#0-1) 

and `ExchangeWithdrawContract` is likewise limited to `quant` with no bound: [3](#0-2) 

`ExchangeInjectActuator.execute()` computes `anotherTokenQuant` purely from the exchange's current reserves at execution time, with no floor/ceiling check against a caller-supplied value: [4](#0-3) 

Similarly, `ExchangeWithdrawActuator.execute()` computes `anotherTokenQuant` from the live reserve ratio with no bound supplied by the withdrawer: [5](#0-4) 

The `ExchangeWithdrawActuator.doValidate()` does include a "precision" sanity check comparing the computed value against a re-derived value using BigDecimal, but this only guards against rounding drift — it does not let the caller bound the acceptable rate, so it does not defend against an adversarial reserve shift between transaction signing and inclusion: [6](#0-5) 

This is the direct analog of the reported Curve issue: `add_liquidity()`/withdraw-style operations on an AMM pool are executed without any caller-enforced minimum-received (or maximum-paid) bound, so any state change to the pool's reserves between transaction construction and execution can be exploited.

### Impact Explanation
Any account can submit an `ExchangeTransactionContract` (a public, unprivileged, broadcastable transaction reachable through the HTTP/gRPC wallet APIs) to shift the exchange's reserve ratio immediately before a targeted `ExchangeInjectContract` or `ExchangeWithdrawContract` transaction from the exchange creator is applied in the same or next block. Because these two contract types provide no way for the creator to bound the resulting `anotherTokenQuant`, the creator's inject/withdraw executes at the manipulated rate: on inject the creator can be forced to pay significantly more of the paired token than intended, and on withdraw the creator can receive significantly less than intended. The attacker profits from the resulting price reversion, i.e., a sandwich attack extracting value from the victim's asset balance — a concrete transfer of funds away from the exchange creator to the attacker.

### Likelihood Explanation
Exploitation requires only observing a pending `ExchangeInjectContract`/`ExchangeWithdrawContract` transaction (e.g., via mempool visibility) and racing it with an `ExchangeTransactionContract` from an unprivileged account — no special permission, signature, or witness/SR role is required. This applies to any of TRON's on-chain Exchange pairs where a creator performs inject/withdraw operations, which is a routine, expected operation for exchange liquidity management.

### Recommendation
Add an `expected`-style bound to `ExchangeInjectContract` and `ExchangeWithdrawContract` (e.g., `min_another_token_quant` for withdraw, `max_another_token_quant` for inject), and enforce it in `ExchangeInjectActuator.doValidate()`/`execute()` and `ExchangeWithdrawActuator.doValidate()`/`execute()` analogous to the existing `tokenExpected` check in `ExchangeTransactionActuator`, so that the transaction reverts if the reserve ratio has moved unfavorably beyond the caller's tolerance.

### Proof of Concept
1. Exchange creator constructs and signs an `ExchangeWithdrawContract` for exchange `X` expecting to receive `~N` of the second token based on the current reserve ratio, and broadcasts it.
2. Attacker observes the pending transaction, and before it is included, broadcasts an `ExchangeTransactionContract` selling a large amount of the second token into exchange `X`, shifting the reserve ratio unfavorably for the withdrawer.
3. Once the attacker's transaction is included, the victim's `ExchangeWithdrawContract` executes per `ExchangeWithdrawActuator.execute()` at the now-skewed ratio (lines 74-89 cited above), yielding materially less of the second token than the creator anticipated, with no minimum-received check to abort the transaction.
4. The attacker can then reverse their initial swap (or simply profit from arbitrage) to lock in the value extracted from the victim's withdrawal.
