### Title
Symlinked `custom_hooks` tar entry bypasses directory confinement, enabling arbitrary file write and hook execution outside the repository - ([File: internal/gitaly/repoutil/custom_hooks.go])

### Finding Description
`ExtractHooks` extracts attacker-supplied tar data by shelling out to the system `tar` binary: `tar -xf - -C path --strip-components 0 custom_hooks` [1](#0-0) . This command performs no validation of tar member types or link targets. If the top-level `custom_hooks` entry is crafted as `tar.TypeSymlink` with an absolute or `../`-escaping `Linkname`, `tar` creates `custom_hooks` in the extraction directory as a symlink pointing wherever the attacker chooses, and subsequent archive members named `custom_hooks/<file>` are written through that symlink into the target location.

`SetCustomHooks` extracts into a fresh temp directory via `ExtractHooks(ctx, logger, reader, tmpDir.Path(), false)` [2](#0-1) . The subsequent `os.Mkdir(tempHooksPath, mode.Directory)` call is a no-op once a path already exists (symlink or not), since it only errors when `!errors.Is(err, fs.ErrExist)` [3](#0-2) , so the symlink is preserved rather than replaced by a real directory. The code then performs `os.Rename(tempHooksPath, repoHooksPath)` [4](#0-3) , which renames the symlink itself (not its target) into the repository, leaving `repoPath/custom_hooks` as a symlink pointing to an attacker-chosen location such as `/tmp` or an out-of-repo path.

Because the confinement invariant ("`custom_hooks` must be a real directory contained in the repository") is never enforced, an attacker-controlled second tar entry (e.g. `custom_hooks/pre-receive`) is written through this symlink to an arbitrary writable location on the Gitaly host filesystem. Since `custom_hooks` in the repository now resolves via the symlink to that external location, any subsequent git operation on the repository (e.g., `git push`) will invoke `pre-receive`/`update`/`post-receive` from that external, attacker-written path, resulting in command execution as the Gitaly process user.

This is directly comparable to a fix already present elsewhere in the codebase: `extractTarToDirectory` in `internal/gitaly/service/repository/replicate.go` explicitly rejects absolute symlinks and validates that resolved symlink targets stay within the extraction directory [5](#0-4) , with dedicated tests (`TestExtractTarToDirectory_SymlinkValidation`) covering exactly this scenario [6](#0-5) . No equivalent check exists in `ExtractHooks`/`SetCustomHooks`.

### Impact Explanation
An unprivileged owner of a repository can escape the intended `custom_hooks` sandbox and write attacker-controlled executable content to arbitrary filesystem locations reachable by the Gitaly process (e.g., world-writable directories like `/tmp`), then have git automatically execute that content as a repository hook on the next push. This constitutes remote/arbitrary command execution on the Gitaly host as the Gitaly service account, escalating from a repository-owner privilege level to host-level code execution — matching GitLab's highest-severity "Remote Code Execution" bounty impact class.

### Likelihood Explanation
The only precondition is that the attacker owns (or can push/import into) a repository and can call `RepositoryServiceClient.SetCustomHooks` (or `RestoreCustomHooks`), both of which are reachable by any authenticated GitLab user with a repository they control. No shell access, admin role, secret, or non-default configuration is required. The attack is fully repeatable via a single crafted tar stream.

### Recommendation
Validate tar member types before/while extracting `custom_hooks`: reject or strip `TypeSymlink`/`TypeLink` entries for the top-level `custom_hooks` member (and any nested entries whose resolved path escapes the extraction directory), mirroring the checks already implemented in `extractTarToDirectory` in `replicate.go`. Alternatively, replace the system `tar` invocation in `ExtractHooks` with the same Go `archive/tar`-based extractor that performs symlink/hardlink path-containment validation, and additionally verify post-extraction (via `os.Lstat`) that `custom_hooks` is a real directory before it is moved/renamed into the repository.

```go
func TestSetCustomHooks_symlinkEscape(t *testing.T) {
    ctx := testhelper.Context(t)
    cfg := testcfg.Build(t)
    repo, repoPath := gittest.CreateRepository(t, ctx, cfg, gittest.CreateRepositoryConfig{})

    var buf bytes.Buffer
    tw := tar.NewWriter(&buf)
    require.NoError(t, tw.WriteHeader(&tar.Header{
        Name:     "custom_hooks",
        Typeflag: tar.TypeSymlink,
        Linkname: "../../../../../../../tmp/evil_hooks",
    }))
    require.NoError(t, tw.WriteHeader(&tar.Header{
        Name: "custom_hooks/pre-receive",
        Mode: 0o755,
        Size: int64(len("#!/bin/sh\necho pwned > /tmp/pwned\n")),
    }))
    _, err := tw.Write([]byte("#!/bin/sh\necho pwned > /tmp/pwned\n"))
    require.NoError(t, err)
    require.NoError(t, tw.Close())

    err = repoutil.SetCustomHooks(ctx, testhelper.NewLogger(t), locator, txManager, &buf, repo)
    require.NoError(t, err)

    fi, err := os.Lstat(filepath.Join(repoPath, "custom_hooks"))
    require.NoError(t, err)
    // Vulnerable: this assertion fails because custom_hooks is a symlink.
    require.Zero(t, fi.Mode()&os.ModeSymlink, "custom_hooks must not be a symlink")
}
```
Expected on a patched implementation: `SetCustomHooks` returns an error (e.g. "symlink target escapes extraction directory") and `custom_hooks` remains a plain directory under `repoPath`. On the current implementation, the assertion fails, confirming `custom_hooks` is left as a symlink escaping the repository.
