## Analysis Result

### Title
Unbounded memory allocation from attacker-controlled length field in TVM precompiled-contract array extraction - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The Gophish advisory describes a DoS where an attacker-controlled length/size value drives an allocation (`ioutil.ReadAll` on a zip entry) with no upper bound, letting a small crafted input expand to gigabytes in memory. The same bug class — using an attacker-supplied length taken directly from untrusted input to size a Java allocation before any bound/sanity check — exists in the ABI-array extraction helpers used by TVM precompiled contracts.

### Finding Description
`extractBytes32Array`, `extractBytesArray`, and `extractSigArray` in `PrecompiledContracts.java` read a "length" word directly out of the precompile's call-data words and immediately allocate a Java array of that size: [1](#0-0) [2](#0-1) [3](#0-2) 

In each case, `len` comes from `words[offset].intValueSafe()`, which is derived from attacker-controlled call data passed to the precompiled contract's `execute(byte[] data)`. `intValueSafe()` clamps an arbitrary 256-bit word into an `int` (up to `Integer.MAX_VALUE`) but does not validate that `len` is consistent with, or bounded by, the actual size of the `words`/`data` array before the corresponding `new byte[len][]` (or `new byte[len]` in `extractBytes32Array`) allocation is attempted. Unlike Gophish's `ApplyTemplate()` which calls `ioutil.ReadAll()` per zip entry with no size cap, these helpers immediately request a large heap allocation sized directly from an untrusted 32-byte word before any data-availability or upper-bound check is performed.

This mirrors CWE-770 (Missing allocation of resources limits): a compact, cheaply-constructed input (calldata to a specific precompile address) can request a disproportionately large allocation.

### Impact Explanation
An unprivileged account can invoke a smart contract that performs a `CALL`/`STATICCALL` to a TVM precompiled-contract address whose `execute()` routes through one of these `extract*` helpers, supplying a crafted "length" word near `Integer.MAX_VALUE`. The resulting `new byte[len][]`/`new byte[len]` allocation attempt can trigger an `OutOfMemoryError` in the node process handling the transaction (during broadcast validation, block application, or a JSON-RPC/HTTP `triggerconstantcontract` query). Because this is an `Error` rather than a checked/recoverable exception, and it occurs deep inside VM execution rather than at a point normally instrumented for energy-based rejection, it risks destabilizing or crashing the full node process — a denial of service against a currently running SR/FullNode, consistent with the "node crash or halt" impact bar for this scan.

### Likelihood Explanation
Reaching these helpers only requires constructing a transaction (or constant/JSON-RPC call) that invokes the specific precompiled contract addresses that use `extractBytes32Array`/`extractBytesArray`/`extractSigArray`, with a crafted length word in the calldata. No special privileges, SR/witness status, or prior state are needed — only the ability to submit or simulate a contract call, which any transaction broadcaster or anonymous API client possesses. The main open question (which I could not fully verify due to running out of investigation budget) is which specific precompiled contracts route through these helpers and what energy is charged before the allocation is attempted — if energy metering already caps effective `len` to a small, safe bound before these functions run, the practical exploitability would be reduced. I was unable to trace all call sites of `extractBytes32Array` / `extractBytesArray` / `extractSigArray` back to their `getEnergyForData()` gating within the remaining tool budget.

### Recommendation
Before allocating `new byte[len][]` or `new byte[len]` in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray`, validate `len` against:
1. A hard upper bound consistent with the maximum expected/valid array size for that precompile's ABI, and
2. The actual remaining length of `words`/`data`, so `len` cannot exceed what the supplied calldata can possibly encode.
Reject with a `Pair.of(false, ...)`/false result instead of allocating when `len` is inconsistent with the input size, mirroring the bound checks already present elsewhere in this file (e.g., the `UPPER_BOUND` checks in `ModExp.execute`).

### Proof of Concept
Not independently reproduced against a running node in this session (I only have code-search access, not an execution environment). Conceptually: submit/trigger a contract call to one of the precompiled-contract addresses whose `execute(byte[] data)` invokes `extractBytes32Array`/`extractBytesArray`/`extractSigArray`, with the specific 32-byte "length" word set close to `Integer.MAX_VALUE` (subject to `intValueSafe()` clamping), and observe whether the resulting array allocation throws `OutOfMemoryError` in the node process before any bound check rejects the call. Confirming the exact reachable precompile address(es) and the energy-cost gating requires further investigation with full codebase/runtime access — this would be a good next step for a background agent with build/test access.

    int len = words[offset].intValueSafe();

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
