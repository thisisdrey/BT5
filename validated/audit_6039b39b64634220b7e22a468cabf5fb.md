### Title
`SwapAssetAdapter::correct_and_deposit_fee` re-prices the fee refund from live/manipulable pool spot reserves inside the same atomic extrinsic, allowing self-service pool draining - (File: `substrate/frame/transaction-payment/asset-conversion-tx-payment/src/payment.rs`)

### Summary
`pallet-asset-conversion-tx-payment`'s `SwapAssetAdapter` prices any non-native fee asset by directly asking `pallet-asset-conversion` for its live AMM spot quote (`quote_price_tokens_for_exact_tokens` / `quote_price_exact_tokens_for_tokens`), exactly the same class of bug as the Lido strategy asking Curve's `get_dy` for its "current balance." The refund leg of the fee logic (`correct_and_deposit_fee`) re-quotes this spot price *after* the user's own dispatched `call` has executed, inside the very same extrinsic. Because the dispatched `call` can itself be a `pallet_utility::batch` that swaps the exact pool used for fee conversion, an unprivileged signed account can skew the pool's reserves immediately before the tx-payment extension re-prices its refund, extracting more of the fee-asset than it is entitled to, at the expense of the pool's other liquidity providers.

### Finding Description
`pallet-asset-conversion`'s quote functions read live pool reserves with no TWAP/oracle protection: [1](#0-0) 
The trait doc explicitly warns the quote is only safe "if no other swaps are made after the price is quoted and before the target swap ... within the same transaction": [2](#0-1) 

`SwapAssetAdapter` (used by `ChargeAssetTxPayment`) relies on exactly this unprotected spot quote twice per extrinsic:
- At `withdraw_fee` (pre-dispatch), it quotes `asset_id -> A` for the *predicted* fee, before the user's call runs: [3](#0-2) 
- At `correct_and_deposit_fee` (post-dispatch, called after `post_info` is known — i.e. **after** the user's `call` has fully executed), it re-quotes `A -> asset_id` for the refund amount using the pool state *as it stands after the call*: [4](#0-3) 

Because `ChargeAssetTxPayment` lets the signer freely choose both `asset_id` and the wrapped `call`, an attacker can submit a single extrinsic whose `call` is `pallet_utility::batch([ AssetConversion::swap_exact_tokens_for_tokens(asset_id -> A, large_amount), <real inner call> ])`, paying the tx fee in `asset_id`. That batched swap depletes the `A` reserve and inflates the `asset_id` reserve of the exact pool that will be used for the post-dispatch refund conversion. When `correct_and_deposit_fee` runs afterward, `quote_price_exact_tokens_for_tokens(A::get(), asset_id, refund_amount, true)` is evaluated against this attacker-skewed pool state, producing an inflated `refund_asset_amount`. The subsequent `swap_exact_tokens_for_tokens` then pays out that inflated amount from the pool to the caller, i.e. real value is extracted from the pool's other liquidity providers to fund an over-generous refund — the same "single-transaction pool imbalance abused by an on-chain price/value read" primitive as the Curve `get_dy` case in the report.

### Impact Explanation
This lets any unprivileged, signed account extract value from a public liquidity pool by manipulating the AMM reserves that the fee-refund logic treats as ground truth, within a single self-contained extrinsic (no relayer, validator, or admin involvement required). Repeated across blocks this constitutes an unbacked drain of pool funds (LP losses) funneled to the attacker via the transaction-fee refund path — a fund-theft/mis-settlement outcome directly in scope ("theft or unbacked mint or unlock", "duplicate settlement or payout ... must only advance after decode, dispatch, execution, and settlement succeed atomically" — here settlement price is computed from state the caller itself just mutated).

### Likelihood Explanation
Any parachain/runtime that enables both `pallet-asset-conversion` and `pallet-asset-conversion-tx-payment` with the `SwapAssetAdapter`, and permits `pallet_utility::batch` (a default, widely-enabled pallet), exposes this path. The attack requires only ordinary signed-extrinsic capability and a shallow pool (low TVL relative to attacker capital), matching the report's own observation that the attack is profitable at low TVL because AMM fees (e.g. 0.3%) are much smaller than the achievable price skew.

### Recommendation
Do not re-price the refund leg from the pool's current spot reserves computed *after* the wrapped call executed. Options: (1) snapshot/quote the refund conversion rate before the wrapped `call` dispatches (in `withdraw_fee`) and cap the post-dispatch refund by that pre-call quote; (2) require the refund swap to use `SwapCredit` with a strict `max_amount_in`/slippage bound derived from the pre-dispatch quote rather than trusting the freshly recomputed post-dispatch quote; (3) disallow/flag combining `ChargeAssetTxPayment` fee-asset pools with calls that can mutate the same pool's reserves within the same extrinsic (e.g., reject if `call` touches the fee-conversion pool).

### Proof of Concept
1. Attacker holds a large amount of `asset_id` and a small pool `asset_id/A` (`A` = native fee asset) with shallow reserves.
2. Attacker submits a signed extrinsic with `ChargeAssetTxPayment { asset_id: Some(asset_id), .. }` wrapping:
   ```
   Utility::batch([
       AssetConversion::swap_exact_tokens_for_tokens(path: [asset_id, A], amount_in: LARGE, ...), // skews reserves
       <cheap inner call that yields a large post-dispatch weight refund>
   ])
   ```
3. Pre-dispatch: `withdraw_fee` quotes and withdraws `asset_fee` of `asset_id` based on the pool state *before* the batch runs (unskewed).
4. The batch executes: the swap step depletes `A` reserve / inflates `asset_id` reserve in the pool.
5. Post-dispatch: `correct_and_deposit_fee` computes `refund_asset_amount` via `quote_price_exact_tokens_for_tokens(A, asset_id, refund_amount, true)` against the now-skewed pool, returning an inflated amount, then executes `swap_exact_tokens_for_tokens` to pay that amount to the attacker — value siphoned from the pool beyond the attacker's legitimate fee refund. 			include_fee: bool,

				Self::get_amount_out(fee, &amount, &balance1, &balance2).ok()?

				Precision::Exact,
				Preservation::Preserve,
				Fortitude::Polite,
			)
			.map_err(|_| InvalidTransaction::Payment)?;

			return Ok((fee_credit, fee));
		}

		// Quote the amount of the `asset_id` needed to pay the fee in the asset `A`.
		let asset_fee =
			S::quote_price_tokens_for_exact_tokens(asset_id.clone(), A::get(), fee, true)
				.filter(|asset_fee| !asset_fee.is_zero())
				.ok_or(InvalidTransaction::Payment)?;

		// Withdraw the `asset_id` credit for the swap.
		let asset_fee_credit = F::withdraw(
			asset_id.clone(),
			who,
			asset_fee,
			Precision::Exact,
			Preservation::Preserve,
			Fortitude::Polite,
		)
		.map_err(|_| InvalidTransaction::Payment)?;

		let (fee_credit, change) = match S::swap_tokens_for_exact_tokens(
			vec![asset_id, A::get()],
			asset_fee_credit,
			fee,
		) {
			Ok((fee_credit, change)) => (fee_credit, change),
			Err((credit_in, _)) => {
				defensive!("Fee swap should pass for the quoted amount");
				let _ = F::resolve(who, credit_in).defensive_proof("Should resolve the credit");
				return Err(InvalidTransaction::Payment.into());
			},
		};

		// Since the exact price for `fee` has been quoted, the change should be zero.
		ensure!(change.peek().is_zero(), InvalidTransaction::Payment);

		Ok((fee_credit, asset_fee))
	}
