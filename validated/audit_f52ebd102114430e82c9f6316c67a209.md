### Title
ECRecover Precompile Does Not Enforce Canonical (Low-S) Signatures, Enabling ECDSA Signature Malleability for On-Chain Contract Verification - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The TVM's `ECRecover` precompiled contract, reachable by any deployed smart contract via the standard `ecrecover(...)` Solidity builtin, only validates that the `s` component of a signature lies in `[1, SECP256K1N)`. It never enforces the canonical "low-S" rule (`s <= HALF_CURVE_ORDER`), so for any valid signature `(r, s, v)` an attacker who observes it (no private key needed) can also construct the mathematically equivalent `(r, n-s, v')` and get `ecrecover` to return the identical signer address.

### Finding Description
The energy-metered precompile that backs `ecrecover` in TVM contracts is `ECRecover.execute`: [1](#0-0) 

It builds a `SignatureInterface` via `SignUtils.fromComponents(r, s, v[31], ...)` and only rejects it if `signature.validateComponents()` returns false. For the default (secp256k1) engine, `validateComponents` is implemented in `ECKey.ECDSASignature`: [2](#0-1) 

This check enforces `1 <= r,s < SECP256K1N` and `v in {27,28}`, but does **not** call `toCanonicalised()` or otherwise reject `s > HALF_CURVE_ORDER`: [3](#0-2) 

Because `toCanonicalised()` exists in the codebase but is never invoked from the `ECRecover` precompile path (nor from `PrecompiledContracts.recoverAddrBySign`, used by `BatchValidateSign`/`ValidateMultiSign`), both `(r, s, v)` and `(r, n-s, 1-v_bit)` are accepted as valid inputs and recover to the same address: [4](#0-3) 

This is the on-chain analog of the reported off-chain "contract using raw `ecrecover`" issue: any Tron smart contract that relies on the TVM `ecrecover` builtin for authorization, replay-protection, or nonce/signature-uniqueness logic (e.g., meta-transactions, permit-style approvals, off-chain-signed order/voucher systems) inherits the same malleability weakness that OpenZeppelin's `ECDSA` library was designed to close, because java-tron's precompile does not perform the low-S canonicalization that such libraries add on top of raw `ecrecover`.

### Impact Explanation
Signature malleability by itself does not let an attacker forge a signature for a different signer's key — `recoverAddrBySign`/`ECRecover` still return the *same* address for the manipulated signature. The impact is therefore confined to any contract logic that treats the raw signature bytes (rather than the recovered address plus an explicit nonce) as a unique, single-use token — e.g. a contract that marks a signature-hash as "used" for anti-replay purposes, or a multisig/voting scheme that counts distinct raw signatures per signer. In such contracts, an attacker who intercepts one valid signature can mint a second, distinct-but-equivalent valid signature and replay an authorized action, double-count a vote/approval, or resubmit a one-time voucher — this is a real, medium-severity, unauthorized-operation risk for any deployed contract built on top of the TVM `ecrecover` precompile.

### Likelihood Explanation
Reachability is direct and requires no privileged role: any address can deploy a contract that calls `ecrecover`, or call an already-deployed contract with an attacker-supplied `(v, r, s)` triple, since `ECRecover` is a public precompile at a fixed address available to every TVM execution. Exploitation additionally requires that the calling contract's own business logic depends on signature uniqueness (common pattern for permit/voucher/relay contracts), which is outside java-tron's control — java-tron matches upstream Ethereum `ecrecover` semantics (Ethereum itself has the identical non-canonical behavior), so this is a well-known, low-effort-to-trigger malleability primitive rather than a novel consensus break.

### Recommendation
Enforce canonical low-S signatures in the consensus-critical signature-recovery paths that back contract-facing verification, specifically:
- In `ECKey.ECDSASignature.validateComponents` (or a new gate used specifically by `PrecompiledContracts.ECRecover.execute` and `PrecompiledContracts.recoverAddrBySign`), reject signatures where `s > HALF_CURVE_ORDER` (equivalently, require `sig.equals(sig.toCanonicalised())`), mirroring the check OpenZeppelin's `ECDSA.tryRecover` performs.
- Because this changes existing precompile output for previously "valid" high-S inputs, any change to `ECRecover`/`BatchValidateSign` behavior needs to be treated as a hard-fork-gated consensus change (via `ForkController`), not a silent behavior change, to avoid a chain split between upgraded/non-upgraded nodes.
- Document clearly for TVM contract developers that `ecrecover` alone is malleable and that they must not use raw signature bytes as replay-protection keys — but the java-tron–side fix should still add the canonical-S check to match modern EVM chain conventions.

### Proof of Concept
1. Sign a message hash `h` with a private key `k` producing `(r, s, v)` via `ECKey.sign` (see `ECKey.java:800-819`).
2. Compute the malleable variant: `s' = SECP256K1N - s`, and flip `v` (`27<->28`).
3. Call the TVM `ECRecover` precompile (or any deployed contract's `ecrecover(h, v, r, s)` and `ecrecover(h, v', r, s')`) with both signatures.
4. Observe that `PrecompiledContracts.ECRecover.execute` in `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java:599-630` returns the *same* recovered address for both `(v, r, s)` and `(v', r, s')`, because `validateComponents` (`ECKey.java:923-941`) accepts any `s` in `[1, SECP256K1N)` without checking `s <= HALF_CURVE_ORDER`.     public static boolean validateComponents(BigInteger r, BigInteger s,
        byte v) {

      if (v != 27 && v != 28) {
        return false;
      }

      if (BIUtil.isLessThan(r, BigInteger.ONE)) {
        return false;
      }
      if (BIUtil.isLessThan(s, BigInteger.ONE)) {
        return false;
      }

      if (!BIUtil.isLessThan(r, SECP256K1N)) {
        return false;
      }
      return BIUtil.isLessThan(s, SECP256K1N);
    }

    public ECDSASignature toCanonicalised() {
      if (s.compareTo(HALF_CURVE_ORDER) > 0) {
        // The order of the curve is the number of valid points that
        // exist on that curve. If S is in the upper
        // half of the number of valid points, then bring it back to
        // the lower half. Otherwise, imagine that
        //    N = 10
        //    s = 8, so (-8 % 10 == 2) thus both (r, 8) and (r, 2)
        // are valid solutions.
        //    10 - 8 == 2, giving us always the latter solution,
        // which is canonical.
        return new ECDSASignature(r, CURVE.getN().subtract(s));
      } else {
        return this;
      }
    }
