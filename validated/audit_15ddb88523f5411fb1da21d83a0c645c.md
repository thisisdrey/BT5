Audit Report

## Title
Missing duplicate-registration guard in Snowbridge `register_token` allows repeated `RegisterForeignToken` bridge commands for an already-registered asset - (File: `bridges/snowbridge/pallets/system-v2/src/lib.rs`, `bridges/snowbridge/pallets/system/src/lib.rs`)

## Summary
Both `register_token` in `bridges/snowbridge/pallets/system-v2/src/lib.rs` and `do_register_token` in `bridges/snowbridge/pallets/system/src/lib.rs` guard only the `ForeignToNativeId` storage insert with an `if !contains_key(...)` check, but unconditionally proceed to build and send a fresh `Command::RegisterForeignToken` to the Ethereum Gateway and emit `RegisterToken`, regardless of whether the token is already registered. Any asset owner reachable through the unprivileged `snowbridge-pallet-system-frontend::register_token` extrinsic can therefore trigger repeated `RegisterForeignToken` commands with arbitrary, attacker-chosen metadata for an already-registered token.

## Finding Description
In `bridges/snowbridge/pallets/system-v2/src/lib.rs::register_token` (L211-249), the token ID is computed and checked against `ForeignToNativeId`, but the `if !ForeignToNativeId::<T>::contains_key(token_id)` (L229-231) only skips the storage insert — it is not an `ensure!`/early return. Execution always continues to construct `Command::RegisterForeignToken { token_id, name, symbol, decimals }` from caller-supplied `metadata` (L233-238) and call `Self::send(...)` (L241), then deposits `Event::RegisterToken` (L243-246). The identical pattern exists in `bridges/snowbridge/pallets/system/src/lib.rs::do_register_token` (L476-509), at L491-501.

This `register_token` (v2) call is reachable by any account satisfying `T::FrontendOrigin` via `bridges/snowbridge/pallets/system-frontend/src/lib.rs::register_token` (L225-252), whose origin check `T::RegisterTokenOrigin::ensure_origin(origin, &asset_location)` (L235) is configured in `cumulus/parachains/runtimes/assets/asset-hub-westend/src/bridge_to_ethereum_config.rs` (L50-71) as `EitherOf<EitherOf<LocalAssetOwner<...>, ForeignAssetOwner<...>>, EnsureRootWithSuccess<...>>`. `ForeignAssetOwner::try_origin` in `bridges/snowbridge/runtime/runtime-common/src/v2/register_token.rs` (L13-53) only checks that the caller is the current owner of the asset location — it performs no check against `ForeignToNativeId` or any other "already registered" marker. Consequently, an asset owner can call `register_token` repeatedly for the same already-registered asset, each time supplying a new `AssetMetadata`, and the pallet will always dispatch a new `Command::RegisterForeignToken` and emit a new `RegisterToken` event.

## Impact Explanation
This breaks the intended one-time registration invariant of `RegisterForeignToken`. The storage-level idempotency (`ForeignToNativeId` insert) creates the appearance of deduplication, but the actual bridge-affecting side effect — the outbound `Command::RegisterForeignToken` XCMP/message to the Ethereum Gateway and the `RegisterToken` event — is re-emitted every call, carrying attacker-controlled `name`/`symbol`/`decimals` metadata that can differ from the original registration. This is a duplicate-settlement-style bug: message/command emission for a bridge-state-affecting action ("token registered") is not gated on the same condition as the storage bookkeeping it is supposed to be paired with, so the on-chain "already registered" state and the outbound command stream diverge, undermining any one-time-registration assumption on the Ethereum side.

## Likelihood Explanation
High. Any account that owns (or can satisfy `LocalAssetOwner`/`ForeignAssetOwner`/`RegisterTokenOrigin` for) an already-registered foreign or local asset can call the public, unprivileged `register_token` extrinsic on `snowbridge-pallet-system-frontend` repeatedly, at will, with no governance, root, or relayer/prover trust assumptions required. The only cost is the normal fee-asset swap-and-burn, which does not prevent repeated calls — it merely makes each call non-free, not non-repeatable.

## Recommendation
Add an explicit guard that turns "already registered" into a hard error (or a genuine no-op that also skips the command/event), consistently in both `register_token` (`bridges/snowbridge/pallets/system-v2/src/lib.rs`) and `do_register_token` (`bridges/snowbridge/pallets/system/src/lib.rs`):
```rust
ensure!(!ForeignToNativeId::<T>::contains_key(token_id), Error::<T>::TokenAlreadyRegistered);
ForeignToNativeId::<T>::insert(token_id, location.clone());
```
so the `Command::RegisterForeignToken` dispatch and `RegisterToken` event are only produced on first registration, matching the storage-level dedup intent.

## Proof of Concept
1. Asset owner `A` calls `snowbridge-pallet-system-frontend::register_token(asset_id = X, metadata = M1, fee_asset = F)`. This forwards via XCM `Transact` to BridgeHub's `system-v2::register_token`, which sets `ForeignToNativeId[token_id(X)]` and sends `Command::RegisterForeignToken{token_id, name: M1.name, ...}` to Ethereum; fee `F` is burned.
2. `A`, still owner of `X`, calls `register_token(asset_id = X, metadata = M2, fee_asset = F)` again.
3. On BridgeHub, `contains_key(token_id)` is `true`, so the storage insert is skipped, but execution still proceeds unconditionally to build and send `Command::RegisterForeignToken{token_id, name: M2.name, ...}` and emit `RegisterToken` — a second, differently-parameterized registration command for the same `token_id` — with fee `F` burned again and no error raised.
4. Repeating step 2/3 produces an unbounded number of `RegisterForeignToken` commands with independently attacker-chosen metadata for a single, already-registered `token_id`. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

				metadata,
				ether_gained,
			)?;
