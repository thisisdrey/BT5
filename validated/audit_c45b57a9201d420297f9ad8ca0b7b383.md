Audit Report

## Title
Relayer reward paid regardless of message execution outcome due to unchecked `DeliveryReceipt.success` flag - (File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs)

## Summary
`Pallet::process_delivery_receipt` decodes a `DeliveryReceipt` from a verified Ethereum event log and pays the relayer (or a `reward_address` chosen by the relayer) the full `order.fee` for the corresponding `nonce`, without ever inspecting the `receipt.success` boolean that indicates whether the outbound message actually executed successfully on the Ethereum Gateway contract.

## Finding Description
`DeliveryReceipt` is parsed from the `InboundMessageDispatched` Solidity event (`bool success` field), and the decode implementation copies `event.success` into the Rust struct at `bridges/snowbridge/primitives/outbound-queue/src/v2/delivery_receipt.rs:44-50`. The extrinsic `submit_delivery_receipt` verifies the header/message proof and decodes the receipt, then unconditionally forwards it to `process_delivery_receipt` (`bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs:298-317`). Inside `process_delivery_receipt`, the code checks the gateway address, resolves `reward_account`, looks up the `PendingOrder` by `nonce`, and pays `order.fee` via `T::RewardPayment::register_reward` purely based on `order.fee > 0` (`bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs:466-473`) — `receipt.success` is decoded but never read anywhere in this function or elsewhere in the file.

## Impact Explanation
Any relayer can submit a legitimate, cryptographically verified delivery-receipt proof for a message whose on-chain Ethereum execution reverted (`success = false`) and still collect the full relayer fee from `PendingOrders`, identical to a genuinely successful delivery. This is a public underpriced-work/incorrect-payout condition: the reward-payout invariant is decoupled from actual message settlement on the destination chain, allowing systematic collection of bridge relayer rewards for work that did not achieve its intended effect.

## Likelihood Explanation
High: the path is reachable via the public, unprivileged extrinsic `submit_delivery_receipt`, callable by any signed account holding a valid proof of a real (but possibly reverted) Ethereum transaction. No relayer allow-list, governance action, or malicious-peer/compromised-relayer assumption is required — an ordinary relayer only needs a message whose execution reverts on the Ethereum Gateway (e.g., insufficient gas or application-level revert) and then submits the resulting (real) event/receipt.

## Recommendation
Branch on `receipt.success` in `process_delivery_receipt`: only call `T::RewardPayment::register_reward` when `receipt.success` is `true`. For `false`, withhold/reduce the reward or route to a distinct handling/penalty path, while still removing the `PendingOrder` and emitting an event reflecting the failed outcome.

## Proof of Concept
1. A message is queued via `do_process_message`, creating `PendingOrder { nonce, fee, .. }` (`bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs:431-436`).
2. The relayer relays the message to Ethereum; the Gateway contract's execution reverts, emitting `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. The relayer obtains a valid proof for that (failed) event and calls `submit_delivery_receipt(origin, event)`.
4. `T::Verifier::verify` succeeds, `DeliveryReceipt::try_from` decodes `success = false`, but `process_delivery_receipt` never reads that field and pays `order.fee` to `reward_account` exactly as it would for `success = true`.
