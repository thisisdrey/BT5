The key finding: `verify_and_charge_tx_ephemeral` in `runtime/runtime/src/verifier.rs:269-361` unconditionally enforces `check_storage_stake` on the signer's post-cost balance for **every** transaction, with no exemption for transactions whose action list is a `DeleteAccount` (which would free the storage and refund the balance entirely). This mirrors the MAI Fund bug precisely: an invariant-check function (`totalAssetValue()` / `check_storage_stake()`) that is supposed to only reject "normal" operations ends up also blocking the one action (`redeem`/shutdown` vs. `DeleteAccount`) that would let the user recover their funds, once an edge-case state is reached.

### Title
Storage-stake balance check blocks `DeleteAccount`, permanently locking an account's balance once storage debt exceeds funds - (File: `runtime/runtime/src/verifier.rs`)

### Summary
`verify_and_charge_tx_ephemeral` calls `check_storage_stake(account, new_amount, config)` [1](#0-0)  unconditionally for every transaction, regardless of whether the transaction's actions include a `DeleteAccount` that would free all of the account's storage and refund its remaining balance to a beneficiary. If an account's `amount + locked` ever falls below `storage_amount_per_byte * storage_usage()` (and it is not a NEP-448 zero-balance account), `check_storage_stake` returns `LackBalanceForStorageStaking`, which surfaces as `InvalidTxError::LackBalanceForState` [2](#0-1) , causing the transaction to be rejected **before it is ever converted into a receipt and before `action_delete_account` can run**. This is the same bug class as the MAI Fund report: a defensive invariant check (`marginBalance >= 0` / `available_amount >= required_amount`) that is expected to always hold, but once violated, blocks exactly the recovery/exit action (`redeem`/shutdown vs. `DeleteAccount`) that a user needs to escape the bad state.

### Finding Description
`check_storage_stake` requires `account.amount() + account.locked() >= storage_amount_per_byte * storage_usage()`, exempting only zero-balance accounts under NEP-448 [2](#0-1) . This check is applied at the *transaction* level (not the receipt/action level) inside `verify_and_charge_tx_ephemeral`, using the signer's balance **after** debiting the transaction's gas/deposit cost [3](#0-2) . There is no branch that skips or defers this check when the transaction's actions consist of (or include) a `DeleteAccount` action, even though `action_delete_account` itself performs no such storage-stake check and instead unconditionally refunds the full remaining balance to the beneficiary and removes the account [4](#0-3) .

The project's own documentation acknowledges this exact scenario as a known, unresolved edge case: "Account can end up with not enough balance in case it gets slashed. Account will become unusable as all originating transactions will fail (including deletion). The only way to recover it in this case is by sending extra funds from a different accounts." [5](#0-4) . The accompanying pseudocode in the same document even models `verify_transaction` as checking storage cost unconditionally, gating on `DeleteAccount(tx.signer_id) in tx.actions` only to *still* assert `LackBalanceForState` [6](#0-5) , matching the current unconditional behavior in `verify_and_charge_tx_ephemeral`.

This mirrors the MAI Fund report structurally:
- MAI: `totalAssetValue()` assumes `marginBalance >= 0` (maintained by margin-account liquidation); if violated, it reverts, and everything depending on it — including the very functions meant to let users exit (`redeem`, shutdown) — becomes permanently unusable.
- NEAR: `check_storage_stake` assumes an account can always top up its own balance before it becomes storage-insolvent (enforced by the same check being applied after every balance-reducing action); if an account nonetheless enters a state where `amount + locked < required storage`, every transaction from that signer — including the `DeleteAccount` transaction meant to let the user reclaim their remaining balance — is rejected at verification time, before the account-deletion logic (which needs no such balance) can even run.

### Impact Explanation
Once an account's `amount + locked` balance drops below its storage-staking requirement (e.g., due to storage usage growing via receipts from other accounts/contracts while the account's spendable balance shrinks, or via validator un-staking/kickout dynamics acknowledged in the docs as "slashed"), the account becomes permanently unable to submit *any* self-signed transaction, including the one action (`DeleteAccount`) that would let the owner recover their locked balance by paying it out to a beneficiary. The account's balance is then frozen indefinitely and can only be rescued if a *third party* voluntarily sends it enough extra NEAR to clear the storage-staking deficit — the owner has no unilateral way to reclaim their own funds. This is a permanent freezing-of-funds condition reachable from an ordinary account's own transaction-submission path.

### Likelihood Explanation
The check is on the hot path of every transaction (`verify_and_charge_tx_ephemeral`), so the discrepancy is exercised on every single transaction; the failure mode only requires that a signer's `amount + locked` balance be driven below its storage bill by any state-growing action (not necessarily signed by the account itself, e.g. receipts writing to its storage or a reduction in `amount`/`locked` outside its own control) while the account is not eligible for the NEP-448 zero-balance exemption. The condition is explicitly flagged in project documentation as a real, recognized situation ("Account can end up with not enough balance in case it gets slashed"), indicating it is understood to be reachable in production, not merely theoretical.

### Recommendation
Special-case transactions whose action list consists solely of (or is guaranteed to terminate in) a `DeleteAccount` action in `verify_and_charge_tx_ephemeral`: skip or relax `check_storage_stake` for such transactions, since `action_delete_account` frees all storage and pays out the remaining balance without needing the storage-stake invariant to hold. Alternatively, allow `DeleteAccount` transactions to be validated using a storage-stake check that accounts for the storage being freed by the deletion itself, so that an underfunded account can always be closed out by its owner.

### Proof of Concept
1. Create an account `A` whose storage usage is above the NEP-448 zero-balance threshold (`> ZERO_BALANCE_ACCOUNT_STORAGE_LIMIT`, e.g., by adding several access keys).
2. Drive `A.amount() + A.locked()` below `storage_amount_per_byte * A.storage_usage()` — e.g. through a validator unstake/kickout cycle that reduces `locked`, or by having another account push additional state (e.g., a contract call that grows `A`'s storage_usage while `A`'s own balance stays fixed), so that `check_storage_stake(A, A.amount(), config)` now returns `Err(LackBalanceForStorageStaking(_))`.
3. Sign and submit a transaction from `A` containing a single `DeleteAccount { beneficiary_id: B }` action.
4. Observe that `verify_and_charge_tx_ephemeral` computes `new_amount = A.amount() - total_cost` and calls `check_storage_stake(A, new_amount, config)` at [1](#0-0) , which fails and returns `TxVerdict::Failed(InvalidTxError::LackBalanceForState { .. })` — the transaction never reaches `action_delete_account`, and `A`'s balance stays permanently locked.

pub fn check_storage_stake(
    account: &Account,
    account_balance: Balance,
    runtime_config: &RuntimeConfig,
) -> Result<(), StorageStakingError> {
    let billable_storage_bytes = account.storage_usage();
    let required_amount = runtime_config
        .storage_amount_per_byte()
        .checked_mul(u128::from(billable_storage_bytes))
        .ok_or_else(|| {
            format!(
                "Account's billable storage usage {} overflows multiplication",
                billable_storage_bytes
            )
        })
        .map_err(StorageStakingError::StorageError)?;
    let available_amount = account_balance
        .checked_add(account.locked())
        .ok_or_else(|| {
            format!(
                "Account's amount {} and locked {} overflow addition",
                account.amount(),
                account.locked(),
            )
        })
        .map_err(StorageStakingError::StorageError)?;
    if available_amount >= required_amount {
        Ok(())
    } else {
        if is_zero_balance_account(account) {
            return Ok(());
        }
        Err(StorageStakingError::LackBalanceForStorageStaking(
            required_amount.checked_sub(available_amount).unwrap(),
        ))
    }

    state_update: &mut TrieUpdate,
    account: &mut Option<Account>,
    actor_id: &mut AccountId,
    receipt: &Receipt,
    result: &mut ActionResult,
    account_id: &AccountId,
    delete_account: &DeleteAccountAction,
    config: &RuntimeConfig,
    current_protocol_version: ProtocolVersion,
) -> Result<(), StorageError> {
    let account_ref = account.as_ref().unwrap();
    let account_storage_usage = if ProtocolFeature::FixDeleteAccountGlobalContractStorageUsage
        .enabled(current_protocol_version)
    {
        let contract_storage = get_contract_storage_usage(state_update, account_id, account_ref)?;
        account_ref.storage_usage().saturating_sub(contract_storage)
    } else {
        // Legacy behavior: only subtracts local contract code, misses the
        // global contract identifier overhead.
        let account_storage_usage = account_ref.storage_usage();
        let code_len = get_code_len_or_default(
            state_update,
            account_id.clone(),
            account_ref.local_contract_hash().unwrap_or_default(),
        )?;
        debug_assert!(
            code_len == 0 || account_storage_usage > code_len,
            "account storage usage should be larger than code size. storage usage: {}, code size: {}",
            account_storage_usage,
            code_len
        );
        account_storage_usage.saturating_sub(code_len)
    };
    if account_storage_usage > Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE {
        result.result =
            Err(ActionErrorKind::DeleteAccountWithLargeState { account_id: account_id.clone() }

        return Ok(());

            account_id: account_id.clone(),

            balance: gas_key_balance_to_burn,

        return Ok(());

    let account_balance = account_ref.amount();
