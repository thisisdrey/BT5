### Title
Registry/mirror-controlled `remote` field in `git_repository`/module-extension git fetches enables Git `ext::` transport command execution - (File: tools/build_defs/repo/git_worker.bzl)

### Summary
`git_repository`/`new_git_repository` (and the Bzlmod registry `source.json` type `"git_repository"`) take an attacker-influenced `remote` string and pass it verbatim into `git remote add origin <remote>` and then `git fetch origin`, with no scheme validation and no cryptographic binding (no `integrity`/checksum field exists for this source type, unlike `http_archive`). Git's remote-helper syntax (`ext::<shell command>`) turns an untrusted string into command execution, analogous to how Propel's unsanitized `limit()` integer turned into arbitrary SQL.

### Finding Description
`tools/build_defs/repo/git_worker.bzl` builds up the git invocation directly from rule attributes: [1](#0-0) 
The `remote` value is taken as-is (`str(ctx.attr.remote)`) and used unmodified: [2](#0-1) 
`add_origin` calls `_git(ctx, git_repo, "remote", "add", "origin", remote)`, and `_update` subsequently runs `fetch(ctx, git_repo)`/`git fetch origin` on that same remote: [3](#0-2) 
No validation is performed on the `remote` string's scheme (e.g. rejecting `ext::`, `fd::`, or other Git remote-helper prefixes) before it is handed to the `git` binary.

Bzlmod registries can drive this same code path without any user-authored `MODULE.bazel`/`WORKSPACE` line specifying the git remote: a registry's `source.json` can declare `"type": "git_repository"` and directly forwards `remote`, `commit`, `tag`, etc. to the underlying `git_repository` rule, as documented: [4](#0-3) 
Crucially, unlike the `"archive"` type (which has a mandatory `integrity` field checked against a real digest of the downloaded bytes), the `"git_repository"` type has **no integrity/checksum field at all** — the registry (or, before a lockfile entry exists, an on-path/mirror server) fully controls `remote`, and Bazel does not verify it against anything pinned. This mirrors the Propel bug class precisely: an input that should be constrained to a narrow, safe grammar (a numeric limit / a `git://`, `https://`, `ssh://` remote URL) is instead passed through unsanitized into a powerful interpreter (SQL engine / Git's remote-helper dispatcher).

### Impact Explanation
Git remote-helper URLs of the form `ext::<command>` cause `git` to spawn `<command>` via the shell as the transport for `fetch`/`clone`. If a hostile or compromised registry (or, prior to lockfile pinning, a hostile mirror/MITM on the registry HTTP fetch) supplies `"remote": "ext::sh -c calc"` in `source.json`, then when Bazel resolves that module (or when a user's `git_repository`/`new_git_repository` rule is fed such a value indirectly, e.g. from a registry-provided default), `git remote add origin ext::sh -c ...` followed by `git fetch origin` executes attacker-chosen shell commands on the developer's/CI machine — full remote code execution, matching the CVSS:C:H/I:H/A:H severity class of the Propel advisory.

### Likelihood Explanation
This requires either (a) control of a Bazel registry that a project trusts (including a secondary/mirror `--registry` or a compromised BCR-mirror), or (b) a MITM on the initial (unlocked) fetch of registry index/`source.json` content before a lockfile hash pins it — both are within the stated attacker model ("a hostile origin server, mirror or registry ... where a declared sha256/integrity ... should stop it and fails"). Because the `"git_repository"` `source.json` type has no integrity binding for `remote`/`commit`/`tag` at all (only `http_archive`-backed sources get an `integrity` field), the checksum/lockfile protections that would normally stop tampered content do not apply here, making exploitation straightforward once such content is served or injected.

### Recommendation
- Validate the `remote` attribute (and any registry-supplied `remote` field) against an allow-list of safe URL schemes (`https://`, `http://`, `git://`, `ssh://`, `file://`) before invoking `git remote add`/`git fetch`, rejecting `ext::`, `fd::`, and other remote-helper prefixes.
- Extend the Bzlmod lockfile/registry format to require and verify an integrity-style binding (e.g., pinned commit hash plus signed/hashed `source.json`) for `git_repository`-typed sources, closing the gap relative to `http_archive`'s `integrity` field.
- Consider setting `GIT_ALLOW_PROTOCOL`/`protocol.*.allow=never` for helper-based protocols when invoking `git` from repository-rule code, defense-in-depth against remote-helper abuse.

### Proof of Concept
1. Stand up (or compromise/MITM) an index registry serving a module version whose `source.json` is:
```json
{
  "type": "git_repository",
  "remote": "ext::sh -c 'touch /tmp/pwned'",
  "commit": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef"
}
```
2. Add this registry via `--registry` (or as a fallback/mirror registry) and depend on the module in `MODULE.bazel` with no prior lockfile entry pinning it.
3. Run `bazel build //...`. Bazel resolves the module, materializes a `git_repository` rule with `remote = "ext::sh -c 'touch /tmp/pwned'"`, and `git_worker.bzl`'s `add_origin`/`fetch` invoke `git remote add origin ext::sh -c 'touch /tmp/pwned'` followed by `git fetch origin`, causing `/tmp/pwned` to be created on the build machine — demonstrating command execution.

Note: I could not directly inspect the Java-side `RegistryFunction`/repo-spec builder that converts `source.json`'s `git_repository` type into the Starlark `git_repository` rule attrs (searches for `GitRepoSpecBuilder`/similar class names returned no results in the index), so I was unable to confirm from Java source whether any additional scheme validation exists there before the value reaches `git_worker.bzl`. Given the `.mdx` documentation explicitly states the fields are "directly forwarded," and `git_worker.bzl` itself performs no validation, the finding stands on the Starlark side regardless, but confirming the full Java-to-Starlark data path would benefit from a Devin session with full repository access (the index has coverage limits and may exclude some file contents).
