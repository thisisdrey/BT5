Audit Report

## Title
Unsanitized, arbitrary asset `name`/`symbol` accepted by `register_token` allows spoofing of legitimate ERC20 token identity on the Ethereum side of the bridge - ([File: bridges/snowbridge/pallets/system-v2/src/lib.rs])

## Summary
`pallet-snowbridge-system-frontend::register_token` accepts a caller-supplied `AssetMetadata { name, symbol, decimals }` from any origin (gated only by ownership of a nested `asset_id` location, not by content validation of `metadata`), and relays it unmodified via XCM `Transact` into `pallet-snowbridge-system-v2::register_token` on BridgeHub, which embeds it verbatim into `Command::RegisterForeignToken` sent to the Ethereum Gateway. Because the wrapped-token identity on Ethereum (`name()`/`symbol()`) is entirely attacker-controlled while the internal `token_id` is derived only from the Polkadot-side `Location`, an attacker can register a worthless custom asset labeled `"USDC"`/`"USD Coin"` and deploy a wrapped ERC20 that impersonates a legitimate bridged token to off-chain consumers (wallets, explorers, DEX listings).

## Finding Description
`register_token` in `bridges/snowbridge/pallets/system-frontend/src/lib.rs` (L217-252) is explicitly documented as allowing "All origins," constrained only by requiring `asset_id` to be nested within the caller's own consensus location, verified through `T::RegisterTokenOrigin::ensure_origin(origin, &asset_location)`. This check validates *asset ownership/location*, not the `metadata` argument at all. The pallet then calls `build_register_token_call` (L320-338), which forwards `metadata` unchanged into a `BridgeHubRuntime::EthereumSystem(EthereumSystemCall::RegisterToken { ... metadata ... })` and dispatches it via `Transact` to BridgeHub.

On BridgeHub, `pallet-snowbridge-system-v2::register_token` (`bridges/snowbridge/pallets/system-v2/src/lib.rs` L211-249) checks only `T::FrontendOrigin::ensure_origin(origin)?`, which in the Westend BridgeHub runtime resolves to `EnsureXcm<AllowFromEthereumFrontend>` (`cumulus/parachains/runtimes/bridge-hubs/bridge-hub-westend/src/bridge_to_ethereum_config.rs` L313-334) — verifying only that the XCM origin is AssetHub's system-frontend pallet, not the content of `metadata`. The pallet computes `token_id` purely from `TokenIdOf::convert_location(&location)` (location-bound identity, correctly collision-free), then copies `metadata.name`/`metadata.symbol` directly into `Command::RegisterForeignToken` with no content check.

`AssetMetadata` (`bridges/snowbridge/primitives/core/src/lib.rs` L166-186) enforces only a 32-byte length bound via `BoundedVec<u8, ConstU32<32>>`, with no charset/uniqueness constraint. The command is ABI-encoded (`bridges/snowbridge/primitives/outbound-queue/src/v2/message.rs` L68-78, L228-236) as raw `name`/`symbol` bytes and delivered to the Ethereum Gateway to instantiate/label the wrapped ERC20 contract. No stage in this pipeline — frontend pallet, BridgeHub pallet, or outbound queue — validates that `name`/`symbol` are unique, non-impersonating, or match any allow-list of known tokens.

## Impact Explanation
End users, wallets, block explorers, and DEX listing services commonly identify ERC20 tokens by `name`/`symbol` rather than by internal `token_id` or contract address. A spoofed wrapped-token contract labeled `"USDC"`/`"USD Coin"` but backed by an attacker-controlled, worthless Polkadot asset can deceive users into acquiring or trading it as if it were the canonical bridged USDC, causing direct financial loss to end users and reputational damage to the bridge, matching the "runtime bugs that compromise intended behavior" / identity-spoofing class of impact.

## Likelihood Explanation
The frontend pallet's `register_token` is, by design and by its own doc comment, callable by any origin, gated only on asset ownership of an arbitrary nested location — not a governance or allow-listed origin. An attacker only needs to create or control any distinct asset (even worthless, freely creatable via `pallet-assets` on a parachain) and call this public extrinsic with an arbitrary `name`/`symbol`; no validator, relayer, or governance compromise is required, making this fully reachable by an unprivileged external actor and repeatable at will.

## Recommendation
- Reject `name`/`symbol` values that exactly or closely (e.g., case-insensitively) match already-registered foreign token names/symbols before emitting `Command::RegisterForeignToken`.
- Enforce a defined charset/format policy on `AssetMetadata.name`/`symbol` (e.g., printable ASCII only).
- Consider requiring governance/allow-list approval for registering tokens whose metadata could plausibly impersonate a widely-recognized asset, and/or surface `token_id`/canonical location prominently in any off-chain-facing metadata to reduce reliance on the spoofable `name`/`symbol` fields.

## Proof of Concept
1. Attacker creates a new asset (e.g., `pallet-assets` asset id `999999`) on any parachain, owning it outright.
2. Attacker calls `pallet-snowbridge-system-frontend::register_token(asset_id = Location of their asset, metadata = { name: "USD Coin", symbol: "USDC", decimals: 6 }, fee_asset)` from their own signed origin; `T::RegisterTokenOrigin::ensure_origin` succeeds because the asset is nested within the caller's own location.
3. The pallet builds and sends a `Transact` XCM to BridgeHub calling `EthereumSystem::register_token` with the same unmodified `metadata`.
4. BridgeHub's `register_token` (gated by `FrontendOrigin` checking only that the XCM sender is the AssetHub frontend pallet) computes a fresh, distinct `token_id` for the attacker's location and emits `Command::RegisterForeignToken { token_id, name: "USD Coin", symbol: "USDC", decimals: 6 }`.
5. The Ethereum Gateway deploys/labels a wrapped ERC20 with `name() == "USD Coin"`, `symbol() == "USDC"`, distinct by address/`token_id` from genuine bridged USDC but visually indistinguishable to end users relying on `name`/`symbol`. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)

			let asset_location: Location =

			let location = Self::reanchor(asset_location)?;

				decimals: metadata.decimals,
			};

				foreign_token_id: token_id,
