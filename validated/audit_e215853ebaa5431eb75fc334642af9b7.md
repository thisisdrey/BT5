### Title
Nil `CipherState` causes `DecryptDanger` to silently "succeed" with an empty plaintext, bypassing AEAD authentication - ([File: noiseutil/aesgcm.go], [File: noiseutil/chachapoly.go])

### Summary
The Hifi report flags a class of bug where a status/return-value check is skipped or made ineffective, so a caller treats a failed operation as if it had succeeded. In Nebula the same bug class appears in the AEAD `DecryptDanger` helpers: when the receiver is `nil`, the function returns `([]byte{}, nil)` instead of an error, i.e. it reports success (no error) for an operation that performed no actual authentication or decryption.

### Finding Description
`CipherStateAESGCM.DecryptDanger` and `CipherStateChaChaPoly.DecryptDanger` both special-case a `nil` receiver by returning an empty byte slice and a `nil` error, rather than returning an error: [1](#0-0) [2](#0-1) 

The call sites treat a `nil` error as "authentication succeeded" and continue processing: [3](#0-2) [4](#0-3) 

Compare this to `EncryptDanger`, which correctly returns an explicit error (`"no cipher state available to encrypt"`) on a nil receiver: [5](#0-4) 

`Overhead()` also documents "0 if the receiver is nil" as an intentional degraded-but-safe value, but `DecryptDanger`'s nil-branch is inconsistent with the encrypt-side error contract — it swallows the "no cipher" condition and reports success. This mirrors the Hifi bug class: a function that can indicate failure chooses instead to report a false-positive success, and the caller's `if err != nil` check (the exact ERC20 "checked return value" idiom) is rendered ineffective because the check passes even though nothing was actually verified.

### Impact Explanation
If a `ConnectionState.dKey` (or any `CipherState` used for `DecryptDanger`) is ever `nil` — for example due to an incomplete/partial handshake result, a construction bug, or any code path that builds a `ConnectionState`/`CipherState` without a live key — `Decrypt` and `VerifyRelay` would return success with empty output for any attacker-supplied ciphertext, since `err` is `nil` and the AEAD tag is never actually checked. This is a full authentication/decryption bypass for that path: an unauthenticated packet is accepted as if it were properly decrypted and authenticated, which is exactly the "remote attacker without a CA-signed certificate can forge/replay traffic" impact class in scope (traffic decryption/forgery bypass reachable in the data-plane path that is defended by AEAD authentication rather than certificate checks).

### Likelihood Explanation
Likelihood depends on whether a live `ConnectionState` can ever end up with a `nil` `dKey` while still being reachable from `handleOutsideMessagePacket`/relay processing on the hot path. In the current handshake flow (`newConnectionStateFromResult`), `dKey` is always populated from a completed `handshake.Result`, so under normal operation this nil-branch is not reachable today. However, the defensive nil-check existing in both `DecryptDanger` implementations (mirrored by the correct error-returning behavior in `EncryptDanger`) indicates the authors anticipated a nil-`CipherState` state; the asymmetry between encrypt (fails safe) and decrypt (fails open) is a latent bug that would immediately become exploitable the moment any future code path (partial handshake completion, relay short-circuit, refactor of `ConnectionState` construction) allows a `ConnectionState` to be used for decryption before/without both keys being set — exactly the kind of "unchecked success" defect the ERC20 `transfer()` report warns about.

### Recommendation
Make `DecryptDanger`'s nil-receiver behavior consistent with `EncryptDanger`: return a non-nil error (e.g. `errors.New("no cipher state available to decrypt")`) instead of `([]byte{}, nil)` in both `noiseutil/aesgcm.go` and `noiseutil/chachapoly.go`. This ensures that any caller relying on the standard `if err != nil { return }` idiom cannot be tricked into treating a missing/invalid cipher state as a successfully authenticated decryption.

### Proof of Concept
1. Construct (or reach, via any future/alternate code path) a `ConnectionState` whose `dKey` field is a typed-nil `noiseutil.CipherState` (e.g. `(*CipherStateChaChaPoly)(nil)` or `(*CipherStateAESGCM)(nil)`), as could happen if `newConnectionStateFromResult` were ever called with a `nil` `r.DKey`, or if a `ConnectionState` is otherwise assembled without a fully-initialized cipher.
2. Call `cs.Decrypt(l, messageCounter, out, packet, nb)` (or `cs.VerifyRelay(...)`) with any arbitrary/garbage packet bytes.
3. Observe: `cs.dKey.DecryptDanger(...)` (`noiseutil/aesgcm.go:36-46` / `noiseutil/chachapoly.go:35-45`) returns `([]byte{}, nil)` — no error — so `Decrypt`/`VerifyRelay` proceed past the `if err != nil` check at `connection_state.go:71-73` / `connection_state.go:96-98` as if the packet had been validly authenticated and decrypted, despite the AEAD tag never having been checked.

func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}
