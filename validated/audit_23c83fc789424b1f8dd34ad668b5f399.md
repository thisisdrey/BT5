## Analysis

I traced the outbound-queue fee pipeline: `EthereumBlobExporter::validate` calls `OutboundQueue::validate` (`send_message_impl.rs`), which computes `fee = Self::calculate_fee(gas_used_at_most, T::PricingParameters::get())` and returns it as the XCM `fee` asset to be paid by the sender via `PayFees`. There is **no check anywhere in `validate`, `deliver`, or `calculate_fee` that rejects or floors a zero/near-zero fee** before the message is queued and ultimately committed with a fixed, non-truncated `reward` value that Ethereum-side relayers are paid against. [1](#0-0) 

The repository's own test explicitly demonstrates that `calculate_fee` can return `fee.remote == 0` for non-zero, valid-looking pricing parameters, and the test comment acknowledges this is an unhandled defect ("invalid which should be avoided"): [2](#0-1) 

### Title
Snowbridge outbound-queue fee calculation can round to zero, letting senders underpay for guaranteed relayer rewards - (File: bridges/snowbridge/pallets/outbound-queue/src/lib.rs)

### Summary
`Pallet::calculate_fee` (used by `send_message_impl::validate` and exposed via the `EthereumBlobExporter` XCM exporter) performs integer-truncating arithmetic — `checked_div` by `exchange_rate` followed by `convert_from_ether_decimals`'s `checked_div` by a decimals scaling factor — to compute the local-currency (`fee.remote`) amount a sender must pay to cover the Ethereum-side gas refund plus reward. As the pallet's own test proves, this computation can legitimately round down to `0` for non-zero pricing parameters. Because the committed message still embeds the full, non-truncated `reward` (`pricing_params.rewards.remote`, in wei) that Ethereum-side relayers are entitled to claim from the gateway contract, a message sender can pay `0` (or near-zero) local fee while the bridge/relayer subsidy owed on the Ethereum side remains unchanged.

### Finding Description
`do_process_message` builds a `CommittedMessage` whose `reward` field is taken directly from `pricing_params.rewards.remote` (a fixed wei amount), independent of what the sender actually paid: [3](#0-2) 

Separately, the amount charged to the sender for delivering the message is computed by `calculate_fee`, which chains a `FixedU128` division by `exchange_rate` and then a lossy integer division in `convert_from_ether_decimals` to translate an 18-decimal ether value into the chain's native decimals: [4](#0-3) 

`send_message_impl::validate` uses this fee, unmodified, as the amount the caller (or XCM `PayFees`) must supply, with no minimum-fee floor or zero-fee rejection: [5](#0-4) 

The XCM `EthereumBlobExporter::validate` passes this fee straight through as the `Assets` to be charged to the XCM sender, with no lower-bound sanity check either: [6](#0-5) 

The pallet's test suite confirms the rounding-to-zero outcome occurs for legitimate (non-zero) pricing parameters, explicitly noting it "should be avoided" but with no guard implemented: [2](#0-1) 

This is directly analogous to the reported bug class: a public, permissionless entry point (any parachain user sending an XCM to Ethereum via `pallet_xcm::execute`/`send`) computes an economically required fee via a rounding division with no minimum floor, so the fee charged can go to zero while the corresponding downstream obligation (liquidator/reporter payout in the original bug; the Ethereum relayer reward owed by the bridge in this case) remains fixed and non-zero.

### Impact Explanation
Every message committed to Ethereum carries a fixed reward obligation that relayers can claim from the gateway contract. If the local-side fee that is supposed to fund/backstop that reward rounds to zero (as demonstrated by the repo's own test), an attacker can submit large volumes of small/cheap messages (e.g., pricing parameters near the rounding boundary, or messages structured to minimize `gas_used_at_most` and `reward`, or simply relying on default `exchange_rate`/`Decimals` combinations that produce truncation) that queue for Ethereum delivery while paying negligible or zero local fees. This creates a persistent mismatch between fees collected on the Polkadot side and rewards owed on the Ethereum side, degrading the bridge's economic backing — a bridge-scoped analog of protocol insolvency/bad debt, and "public underpriced work" that can be used to stall or drain the reward/fee accounting that keeps relayers incentivized to process the queue.

### Likelihood Explanation
This requires no privileged actor, relayer, validator, or governance action — only a normal user submitting XCM messages through the standard, permissionless `pallet_xcm` send path with a channel that is `T::Channels::contains`-registered. It depends on governance-set `PricingParameters` (exchange_rate, fee_per_gas, Decimals) falling into a range where truncation to zero (or near-zero) occurs, which the pallet's own test demonstrates is achievable with plausible non-degenerate values (`exchange_rate = 1/1`, `fee_per_gas = 1`). Given that `set_pricing_parameters` is periodically updated by governance and not mathematically guaranteed to avoid the rounding boundary, this is a latent, exploitable condition rather than a purely theoretical one.

### Recommendation
- In `calculate_fee`/`convert_from_ether_decimals`, round up (ceiling division) instead of floor division, and/or enforce a configurable minimum non-zero fee before accepting a message in `validate`.
- Add an explicit `ensure!(fee.remote > T::MinimumFee::get(), SendError::Fee)`-style guard in `send_message_impl::validate` (and the v2 equivalent) so no message can be queued whose collected fee cannot cover its promised Ethereum-side `reward`.
- Add a runtime invariant/test that asserts `fee.total() >= reward-equivalent-in-local-currency` for the full valid range of governance-settable `PricingParameters`.

### Proof of Concept
Using the pallet's existing test harness (`bridges/snowbridge/pallets/outbound-queue/src/test.rs`), the test `test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero` already demonstrates the zero-fee computation with non-zero `PricingParameters { exchange_rate: 1/1, fee_per_gas: 1, rewards: {local:1, remote:1}, multiplier: 1/1 }`, yielding `fee.remote == 0` while `fee.local == 698000000`. Because `do_process_message` still commits a message with `reward: pricing_params.rewards.remote` unrelated to the truncated `fee.remote`, an attacker submitting messages under such pricing conditions (or any parameter combination producing the same truncation) pays zero for the Ethereum-side reward obligation that the bridge nonetheless commits to paying out to relayers, exactly mirroring the "liquidation fee rounds to zero" mechanism from the source report.

		/// Calculate total fee in native currency to cover all costs of delivering a message to the
		/// remote destination. See module-level documentation for more details.
		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

		/// Calculate fee in remote currency for dispatching a message on Ethereum
		pub(crate) fn calculate_remote_fee(
			gas_used_at_most: u64,
			fee_per_gas: U256,
			reward: U256,
		) -> U256 {
			fee_per_gas.saturating_mul(gas_used_at_most.into()).saturating_add(reward)
		}

		/// The local component of the message processing fees in native currency
		pub(crate) fn calculate_local_fee() -> T::Balance {
			T::WeightToFee::weight_to_fee(
				&T::WeightInfo::do_process_message().saturating_add(T::WeightInfo::commit_single()),
			)
		}

		// 1 DOT has 10 digits of precision
		// 1 KSM has 12 digits of precision
		// 1 ETH has 18 digits of precision
		pub(crate) fn convert_from_ether_decimals(value: u128) -> T::Balance {
			let decimals = ETHER_DECIMALS.saturating_sub(T::Decimals::get()) as u32;
			let denom = 10u128.saturating_pow(decimals);
			value.checked_div(denom).expect("divisor is non-zero; qed").into()
		}

		ensure!(

		// Ensure there is a registered channel we can transmit this message on
		ensure!(T::Channels::contains(&message.channel_id), SendError::InvalidChannel);

		// Generate a unique message id unless one is provided
		let message_id: H256 = message
			.id
			.unwrap_or_else(|| unique((message.channel_id, &message.command)).into());

		let gas_used_at_most = T::GasMeter::maximum_gas_used_at_most(&message.command);

		let queued_message: VersionedQueuedMessage = QueuedMessage {
			id: message_id,
			channel_id: message.channel_id,
			command: message.command.clone(),
		}

		// The whole message should not be too large
		let encoded = queued_message.encode().try_into().map_err(|_| SendError::MessageTooLarge)?;
