### Title
StackerDB chunk signatures omit the contract identifier, enabling cross-StackerDB chunk replay - ([File: libstackerdb/src/libstackerdb.rs])

### Summary
The reported Dapper bug is a case of an authentication check that omits a required binding parameter (the calling `address`), so a fully-valid-looking assertion (`onERC721Received` succeeding) is being validated against the wrong context. The same class of defect exists in the Stacks StackerDB chunk-authentication scheme: the signature that authorizes a chunk write binds only `slot_id`, `slot_version`, and `data_hash`, and never binds the StackerDB's contract identifier. Consequently, a chunk validly signed for one StackerDB contract can be replayed into a different StackerDB contract, as long as the same signer address owns the same `slot_id` there too — an equality check (`signed-for-DB-A` vs `accepted-for-DB-B`) that the protocol never actually enforces.

### Finding Description
`SlotMetadata::auth_digest()` computes the digest that is signed/verified for every StackerDB chunk write, and it only incorporates `slot_id`, `slot_version`, and `data_hash`: [1](#0-0) 

`SlotMetadata::verify()` recovers the public key from this digest and checks only that the hash of the recovered key matches the expected `StacksAddress` for that slot — again with no notion of *which* StackerDB contract the check is being performed for: [2](#0-1) 

The on-disk schema comment for the `chunks` table documents the intent that the contract association ("associated stacker DB") is supposed to be part of what's authenticated, distinguishing it from unauthenticated columns like `signer`/`data`/`write_time`: [3](#0-2) 

But the actual signature-verification call sites never mix in `stackerdb_id`/`contract_id`. Both the RPC-write path and the gossip path call `verify()`/`get_slot_metadata().verify()` scoped only by `(contract_id, slot_id)` lookup of the expected signer, not by hashing the contract identifier into the signed digest itself:

- `StackerDBTx::try_replace_chunk` looks up the slot's expected signer for `smart_contract` and calls `slot_desc.verify(&slot_validation.signer)`, but the signature itself carries no reference to `smart_contract`: [4](#0-3) 

- `PeerNetwork::validate_received_chunk` (used both for chunks pulled during StackerDB sync and for unsolicited `StackerDBPushChunk` gossip) does the same: it fetches `get_slot_signer(smart_contract_id, data.slot_id)` and then verifies the chunk's embedded signature against that address, again with the contract id used only to select which signer address to compare against — not folded into the signed bytes: [5](#0-4) 

Because many StackerDB contracts on a Stacks node (e.g. `.signers-<cycle>-<n>` contracts across reward cycles, `.miners`, etc.) assign slot IDs to overlapping sets of signer addresses, it is realistic for the same `(signer_address, slot_id)` pair to be valid in more than one StackerDB contract simultaneously or across cycles. Any chunk a legitimate signer signs for contract A (slot N, version V, hash H) is therefore also a valid, fully-authenticated chunk for contract B's slot N, provided B's slot N is also owned by that same address and its current version is `< V`. An attacker who observes such a signed chunk on the wire (chunks and signatures are broadcast in the clear as part of StackerDB replication) can replay it into the other contract's StackerDB via the unauthenticated `StackerDBPushChunk` gossip path or the `POST /v2/stackerdb/.../chunks` RPC endpoint, and it will pass every check (`try_replace_chunk` / `validate_received_chunk`) because those checks only ever re-derive the expected signer per-slot, never the expected *contract*.

### Impact Explanation
This breaks the equality "signed by owner and intended for this StackerDB" vs. "signed by owner for any StackerDB where they own this slot ID," allowing an unauthorized write of attacker-replayed (forged-context) data into a StackerDB contract that the signer never intended to write to, and — because `handle_unsolicited_StackerDBPushChunk` will accept and then re-broadcast/re-sync such chunks to other replicas — propagation of this cross-context forged data across the network. This matches the "unauthenticated/unauthorized write to state or StackerDB" and "network-wide propagation of forged data" Critical-tier impact categories, since it is a remote, unprivileged (no node secret or admin role needed) write achieved with a handful of gossip/RPC messages.

### Likelihood Explanation
Exploitability requires only: (1) observing one validly-signed chunk broadcast by any StackerDB participant (chunks/signatures are public on the P2P StackerDB gossip protocol and via RPC `GET` endpoints), and (2) at least one other StackerDB contract in which the same signer address also owns the same numeric `slot_id` at a lower version. Given the recurring `.signers-<cycle>-<n>` contract naming/slot-assignment pattern across reward cycles, and other StackerDB uses of the same signer set, such overlaps are plausible without any special access, making this a realistically triggerable, not merely theoretical, condition.

### Recommendation
Include the StackerDB's `QualifiedContractIdentifier` (or a network-wide/DB-specific domain separator derived from it) in `SlotMetadata::auth_digest()` so that a chunk signature is cryptographically bound to the specific StackerDB it was created for. Update `sign()`/`verify()` call sites (`try_replace_chunk`, `validate_received_chunk`, and the `POST /v2/stackerdb/.../chunks` handler) to pass the contract identifier into the digest computation, and bump any relevant protocol/version constant so old and new chunk formats are not silently interchangeable.

### Proof of Concept
1. Set up two StackerDB contracts, A and B, each configuring the same signer address `S` as the owner of slot `0` (e.g. two `.signers-<cycle>-<n>` contracts across consecutive reward cycles, or any two StackerDB configs sharing a signer set).
2. Have the legitimate signer `S` sign and publish chunk `C = (slot_id=0, slot_version=5, data=D)` to StackerDB A via the normal `StackerDBChunkData::sign` flow (as exercised in `libstackerdb::tests::test_stackerdb_slot_metadata_sign_verify`, `libstackerdb/src/tests/mod.rs:26-73`).
3. As an unrelated third party who merely observed chunk `C` and its signature (e.g. from A's public `GET /v2/stackerdb/.../chunks/0` or from P2P `StackerDBChunkData` gossip), construct a `StackerDBPushChunkData { contract_id: B, rc_consensus_hash: <B's current view>, chunk_data: C }` and submit it to a node via the P2P `StackerDBPushChunk` path or `POST /v2/stackerdb/<B>/chunks`.
4. Because `validate_received_chunk`/`try_replace_chunk` for contract B only checks that `C.sig` recovers to `S` (B's slot-0 owner) and that `slot_version=5 > `B's current version, the replayed chunk is accepted and stored in B's slot 0, and further re-gossiped to B's other replicas — despite `S` never having signed anything referencing contract B.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
