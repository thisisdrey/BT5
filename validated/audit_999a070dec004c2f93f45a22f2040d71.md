### Title
Unbounded offset/length trust in Windows reparse-point (symlink/junction) path parsing causes heap buffer over-read - ([File: src/internal/syscall/windows/reparse_windows.go])

### Summary
`SymbolicLinkReparseBuffer.Path()` and `MountPointReparseBuffer.Path()` compute slice bounds directly from attacker/filesystem-controlled `SubstituteNameOffset`/`SubstituteNameLength` fields and reinterpret the trailing `PathBuffer` as a fake `[0xffff]uint16` array without validating those offsets against the actual size of the underlying reparse-data buffer that was filled by `DeviceIoControl`. This mirrors the liblnk CVE-2018-12097 root cause: trusting length/offset fields from parsed data to slice memory without bounds-checking against the real buffer size, producing a heap-based buffer over-read.

### Finding Description
An attacker who can place a malicious NTFS reparse point (symbolic link or junction) on a filesystem that a victim later inspects — e.g. via `os.Readlink`, `os.Lstat`/`os.Stat` walking a directory, or `os.Root` path resolution — reaches `readReparseLinkHandle` in [1](#0-0)  (and equivalently `syscall.Readlink` in [2](#0-1) ). This function calls `DeviceIoControl(FSCTL_GET_REPARSE_POINT, ...)` to fill a fixed 16 KiB (`MAXIMUM_REPARSE_DATA_BUFFER_SIZE`) buffer, then casts it to `REPARSE_DATA_BUFFER`/`SymbolicLinkReparseBuffer` and calls `.Path()`. The `Path()` implementation is:
```go
func (rb *SymbolicLinkReparseBuffer) Path() string {
	n1 := rb.SubstituteNameOffset / 2
	n2 := (rb.SubstituteNameOffset + rb.SubstituteNameLength) / 2
	return syscall.UTF16ToString((*[0xffff]uint16)(unsafe.Pointer(&rb.PathBuffer[0]))[n1:n2:n2])
}
``` [3](#0-2) 
`SubstituteNameOffset` and `SubstituteNameLength` are `uint16` fields taken directly from the on-disk reparse-point data (attacker-controlled if the attacker can write/craft the reparse point, e.g. via a mounted image, removable media, or an archive/checkout tool that materializes junctions/symlinks). There is no check anywhere in `readReparseLinkHandle` or `Path()` that `SubstituteNameOffset+SubstituteNameLength` stays within the bytes actually returned by `DeviceIoControl` (`bytesReturned`) or within the real 16 KiB allocation. The code instead reinterprets the tail of the buffer as a fake `[0xffff]uint16` (131,070-byte) array — deliberately oversized to avoid Go's bounds checks — and slices it using untrusted offsets, which can read far past the end of the actual `rdbbuf` heap allocation.

### Impact Explanation
This is a heap-based buffer over-read: a crafted reparse point with an oversized `SubstituteNameOffset`/`SubstituteNameLength` causes `UTF16ToString` to read adjacent heap memory beyond the legitimately populated reparse buffer, which is then returned as the "link target" string — potentially disclosing unrelated heap contents to the calling process/user, or causing a crash/panic if the read strays outside the mapped page. This matches the CVSS 3.0 vector of CVE-2018-12097 (`C:H/I:N/A:N`, local, low complexity, requires user interaction) — information disclosure via out-of-bounds read triggered by parsing untrusted structured data. This would fall under Go's PUBLIC track as a memory-safety/information-disclosure bug in the standard library's Windows filesystem path handling, reachable by any program calling `os.Readlink`, `os.Lstat`, `filepath.EvalSymlinks`, or `os.Root` operations on an attacker-influenced reparse point.

### Likelihood Explanation
The victim workflow is any Go program that resolves or inspects filesystem links on Windows — directory walkers, backup/archive tools, or servers unpacking uploaded content that includes NTFS junctions/reparse points. The attacker's capability required is limited to controlling the content of a reparse point that the victim's Go program will read (e.g., via a crafted removable drive, mounted VHD, network share, or archive that reconstitutes junctions) — an unprivileged, non-malicious-server threat model consistent with the CVE analog.

### Recommendation
Validate `SubstituteNameOffset` and `SubstituteNameLength` (and the equivalent `PrintName*` fields) against `bytesReturned` (or `rdb.ReparseDataLength`) before slicing, and bound the synthetic `[0xffff]uint16` cast to the actual buffer size rather than a fixed oversized array, returning an error (e.g., a corrupt-reparse-point error) when the computed bounds exceed the real data length.

import (

// Simulates a crafted reparse point whose SubstituteNameOffset/Length
// point far beyond the actual allocated PathBuffer data, analogous to
// liblnk trusting unchecked offset/length fields (CVE-2018-12097).
func TestSymbolicLinkReparseBuffer_OOBRead(t *testing.T) {
	// Small, legitimately-sized backing buffer (simulates real reparse data).
	buf := make([]byte, 32)
	rb := (*SymbolicLinkReparseBuffer)(unsafe.Pointer(&buf[0]))

	// Attacker-controlled offset/length far exceeding the real buffer (32 bytes).
	rb.SubstituteNameOffset = 0
	rb.SubstituteNameLength = 60000 // >> len(buf), well within uint16 range

	defer func() {
		if r := recover(); r == nil {
			t.Fatalf("expected out-of-bounds access (panic or heap over-read), got none")
		}
	}()

	// Path() will index into memory well past the 32-byte allocation,
	// demonstrating the unchecked-offset heap buffer over-read.
	_ = rb.Path()
}
```
Expected: this either panics with a runtime memory fault/segfault, or (worse, if the surrounding heap page is mapped) silently returns garbage/adjacent-heap data as the "link path," demonstrating the same class of unchecked-length heap over-read as CVE-2018-12097.
