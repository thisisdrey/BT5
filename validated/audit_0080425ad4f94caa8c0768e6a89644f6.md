## Title
Out-of-bounds read / unbounded loop in ijar's ZIP central-directory extra-field parser via attacker-controlled `data_size` - (`third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry()` in `third_party/ijar/zip.cc` parses the "extra field" data of each ZIP central-directory entry with no bounds checking against the declared `extra_field_length`. A crafted JAR/ZIP file with an oversized extra-field `data_size` causes the cursor to walk past the end of the extra-field region — and potentially past the mmapped file buffer entirely — reading attacker-influenced out-of-bounds memory, structurally analogous to the unchecked size-driven UB in `CIccTagSpectralViewingConditions()`.

### Finding Description
In the extra-field parsing loop of `ProcessCentralDirEntry`: [1](#0-0) 

```cpp
const u1 *extra_p = p;
p += extra_field_length;
while (extra_p != p) {
  const u2 header_id = get_u2le(extra_p);
  const u2 data_size = get_u2le(extra_p);
  const u1 *extra = extra_p;
  extra_p += data_size;
  if (header_id == ZIP64_EXTRA_FIELD_TAG) { ... }
}
```

`data_size` is read directly from attacker-controlled bytes and is never validated against the remaining bytes in the extra-field block (`p - extra_p`). If `data_size` causes `extra_p` to overshoot `p` (the end of the extra field, itself derived from the unchecked `extra_field_length` u2), the `while (extra_p != p)` loop condition — an exact pointer-equality check rather than a bound check — never becomes false through normal termination once overshot; each iteration continues calling `get_u2le(extra_p)` further and further past the intended region, and in the ZIP64 branch, `get_u8le(extra)` reads even further into unmapped/adjacent memory when `header_id == ZIP64_EXTRA_FIELD_TAG`.

By contrast, the local-file-header path in the same file (`ProcessLocalFileEntry`) rigorously bounds-checks every read via `EnsureRemaining()`: [2](#0-1) 

No equivalent check exists for the central directory's extra-field loop, and `FindZipCentralDirectory` only validates that `central_dir_offset + central_dir_size <= in_length` for the directory as a whole — it does not validate the internal structure of each entry's extra-field sub-records: [3](#0-2) 

This function is used both by `CalculateOutputLength()` (sizing pass over every central-directory entry) and by `ProcessNext()` (the main extraction driver used by the `ijar` interface-jar tool and by `singlejar`'s central-directory consumers), so the unchecked loop executes on every JAR processed by these Bazel-shipped tools during ordinary build actions (e.g., `java_library`, interface-jar generation, deploy-jar assembly) whenever a dependency JAR is supplied — including JARs originating from `http_jar`/`http_archive`/Maven-resolved artifacts. Critically, a `sha256`/integrity check on the fetched archive only pins the specific bytes; it does nothing to prevent those pinned bytes from containing a structurally malformed ZIP central directory that triggers this OOB read, exactly as the ICC advisory's malformed-tag-but-otherwise-valid-file scenario.

### Impact Explanation
An attacker who controls the content of any JAR consumed during a build (a hostile dependency archive, mirror, or a JAR referenced from an untrusted branch/CI-built artifact) can craft a central-directory extra field with an oversized `data_size`, causing `ijar`/`singlejar` to read out-of-bounds memory past the mapped file. Depending on layout this can crash the build tool (denial of the specific build step) or leak adjacent process memory contents into build tool state that could be exposed through error output. This is a memory-safety violation (CWE-125-style OOB read / unbounded pointer walk) reachable purely through file content, matching the "Undefined Behavior" class of the reported analog.

### Likelihood Explanation
Any dependency shipped as a `.jar` (via `http_jar`, `http_archive`+`java_import`, Maven/`rules_jvm_external`, or a plain source-controlled JAR on an untrusted branch) is routinely processed by ijar/singlejar as part of normal `java_library`/`java_import` build actions. No special build configuration is required, and default Bazel flags do not add extra ZIP-structure validation beyond what's shown above, making this readily reachable by any unprivileged party who can get a crafted JAR into the dependency graph a victim builds.

### Recommendation
Bound-check the central-directory extra-field walk the same way `ProcessLocalFileEntry`/`EnsureRemaining` do: before each `get_u2le`/`get_u8le` read, verify `extra_p + N <= p` (the extra-field end) and that `p` itself stays within `[central_dir_, central_dir_ + central_dir_size]` / the mapped file bounds. Reject the entry (return an error) instead of continuing the loop when `data_size` would advance `extra_p` past `p`.

### Proof of Concept
Construct a ZIP whose central-directory entry declares `extra_field_length = N` but whose extra-field sub-record `data_size` exceeds `N` (analogous to the existing `CreateZipWithMalformedExtraField()` helper used for `output_jar.cc`'s local/CDH extra-field checks, but targeting `ProcessCentralDirEntry`'s unchecked loop instead): [4](#0-3) 

Feed this file to the `ijar` binary (`third_party/ijar/ijar.cc`) or to `InputZipFile::ProcessNext()`/`CalculateOutputLength()` directly in a `googletest`-based unit test under `third_party/ijar/`, asserting via ASan/valgrind that the extra-field loop reads past the mapped buffer rather than returning a parse error.
