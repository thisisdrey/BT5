Audit Report

## Title
Relayer reward paid and order settled regardless of on-chain message execution outcome (`success` field ignored) - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
`DeliveryReceipt::try_from` correctly decodes the `success: bool` field from the Ethereum Gateway's `InboundMessageDispatched` event log [1](#0-0) , but `Pallet::process_delivery_receipt` never reads `receipt.success` before unconditionally paying the relayer reward and removing the `PendingOrder` [2](#0-1) . This causes reward payout and permanent settlement of the pending order even when the dispatched command failed on Ethereum.

## Finding Description
The public, unpermissioned `submit_delivery_receipt` extrinsic requires only a valid Merkle-proved Ethereum event log matching `T::GatewayAddress`, verified via `T::Verifier::verify` [3](#0-2) . After decoding, `process_delivery_receipt` checks only `receipt.gateway` against `T::GatewayAddress::get()` and looks up `PendingOrders` by `receipt.nonce`; it never branches on `receipt.success` [4](#0-3) . Regardless of whether the Gateway contract set `success=true` or `success=false`, the reward is paid via `T::RewardPayment::register_reward` and the order is deleted via `<PendingOrders<T>>::remove(nonce)` [5](#0-4) . This breaks the invariant that queue/marker state should only advance after execution and settlement succeed atomically — the receipt only proves the Gateway *processed* the log, not that the command's Ethereum-side effects succeeded. The `PendingOrder` is originally created with fee and block number when the message is queued [6](#0-5) , and once removed there is no retry mechanism in this pallet for the failed nonce.

## Impact Explanation
This allows relayers to be rewarded for delivering messages whose Ethereum-side command execution failed, causing duplicate/incorrect settlement of protocol reward funds outside the intended payout-on-success invariant, and permanently deletes the retry/tracking state (`PendingOrder`) for a failed cross-chain command with no on-chain remediation path. This aligns with the "duplicate settlement or payout" and "message queues/bridge markers/receipts/payout state must only advance after decode, dispatch, execution, and settlement succeed atomically" pivot in scope.

## Likelihood Explanation
The exploit path requires only a genuine Gateway-emitted event with `success=false` (a real command execution failure on Ethereum, e.g., a reverted dispatched command) — no forged proof or privileged access is needed, since `T::Verifier::verify` must succeed against the real log. Any ordinary relayer submitting a legitimate failure receipt through the standard, unpermissioned `submit_delivery_receipt` extrinsic triggers the bug, making this a reachable logic bug under normal operation.

## Recommendation
Branch on `receipt.success` in `process_delivery_receipt`: only pay `T::RewardPayment::register_reward` and call `<PendingOrders<T>>::remove(nonce)` when `success == true`. On `false`, emit a distinct event (e.g., `MessageDeliveryFailed`) and define an explicit retry or refund policy instead of unconditionally rewarding and dropping the order.

## Proof of Concept
1. `do_process_message` queues a message and inserts `PendingOrders[nonce] = { fee, block_number }` [7](#0-6) .
2. The relayer delivers the message to the Ethereum Gateway; the dispatched command fails, and the Gateway emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. The relayer submits this genuine log/proof via `submit_delivery_receipt`; `T::Verifier::verify` succeeds and `DeliveryReceipt::try_from` decodes `success=false` correctly [8](#0-7) .
4. `process_delivery_receipt` ignores `receipt.success`, pays the reward, and removes the order [9](#0-8) , confirmed by the absence of any `success`-based branching anywhere in the function and by existing tests (e.g. `submit_delivery_receipt_succeeds_after_unhalt`) which only assert on order removal/payout without constructing or testing a `success: false` scenario.

```rust
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
```
