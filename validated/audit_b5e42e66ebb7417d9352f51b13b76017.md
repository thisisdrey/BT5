### Title
Anti-replay window race allows duplicate/replayed packet decryption due to non-atomic Check-then-Update - (File: `connection_state.go`)

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` both implement anti-replay protection using a `Check()`-then-decrypt-then-`Update()` sequence, but the `decryptLock` mutex is released between the `Check()` call and the `Update()` call, leaving a window where the replay-window state has not yet been mutated to reflect the in-flight packet.

### Finding Description
The intended invariant of the anti-replay window is that once a message counter has been "seen," no other packet with that same counter should be able to pass. However, the code splits the check-effects-interaction into three separate, unlocked-in-between critical sections:

```go
func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}
``` [1](#0-0) 

The lock is released after `Check()` and before the (comparatively expensive) `DecryptDanger` AEAD operation, and only re-acquired afterward to call `Update()`, which is what actually marks the counter as seen in the sliding-window bitmap: [2](#0-1) [3](#0-2) 

This is structurally the same bug class as the reported ERC721 issue: a security check (`balanceOf(_to) + _amount > max`) is performed against state that has not yet been updated, an external/slow interaction happens (`_safeMint` → reentrant hook / here, AEAD decryption), and only afterward is the authoritative state (`balanceOf` / the replay window bitmap) updated. Any concurrent caller that races between the `Check()` and `Update()` calls observes the same "not yet seen" state and is allowed through.

The `VerifyRelay` function used for authenticating relay-forwarded frames has the identical pattern: [4](#0-3) 

The `Bits.Check`/`Bits.Update` primitives themselves are correct and side-effect-free/effectful as designed — `Check` is read-only and `Update` performs the actual bit-set/window-advance — but the caller's failure to hold the lock across the whole check-decrypt-update sequence is what breaks the atomicity guarantee that the replay window is meant to provide: [5](#0-4) [6](#0-5) 

The changelog itself documents that this exact class of ordering/locking bug has previously caused real anti-replay failures in this codebase (relay frames not advancing the window, and races corrupting the window under concurrent access), showing the codebase is aware this is a live risk area: [7](#0-6) 

### Impact Explanation
If two packets carrying the same `messageCounter` (i.e., an attacker-replayed packet racing the original, or two replayed copies sent back-to-back) are processed concurrently — which can happen because UDP receive processing in Nebula is queued/parallelized across worker goroutines/queues (`q int` parameter threading through `readOutsidePackets`/`Decrypt`) — both can pass `Check()` before either has called `Update()`, since `Update()` is what actually flips the bit. Both would then proceed to successful AEAD decryption of the same counter/nonce and be delivered as distinct, "valid" packets, defeating the anti-replay protection that the noise/AEAD scheme depends on for confidentiality/integrity guarantees (nonce reuse detection). This is a concrete traffic-replay bypass, analogous in root cause to the reported reentrancy issue (check performed against not-yet-updated state due to an intervening slow operation), impacting the confidentiality/replay-safety of the data channel and the relay-frame authentication path.

### Likelihood Explanation
Likelihood is dependent on the packet processing model actually delivering concurrent calls to `Decrypt`/`VerifyRelay` for the same `ConnectionState` on separate goroutines (e.g., multiple UDP read queues per tunnel) — this is plausible given the `q int` queue-index parameters threaded throughout `outside.go`/`interface.go`, but confirming true concurrent dispatch of packets belonging to the *same tunnel* to different queues requires deeper reading of the queue/routine assignment logic that was not fully verified in this pass. An attacker fully controls the network and can trivially generate the racing duplicate packet (a captured/replayed frame) without needing a CA-signed certificate, satisfying the reachability constraint.

### Recommendation
Hold `decryptLock` for the entire check → decrypt → update sequence (or restructure so the window is updated atomically with the check, e.g., a single `CheckAndReserve` that marks the counter as "pending" before decryption and only finalizes/rolls back after), so no other caller can observe the "not yet seen" state for the same counter while decryption is in flight. Apply the same fix to both `Decrypt` and `VerifyRelay`.

### Proof of Concept
1. Attacker captures one encrypted data-plane packet for an established tunnel with message counter `N`.
2. Attacker (or natural network duplication) delivers two copies of this packet to the receiver at (near-)the same time, such that they are dispatched to two different processing goroutines/queues for the same `ConnectionState`.
3. Goroutine A calls `Decrypt`: acquires `decryptLock`, calls `window.Check(N)` → true (not yet marked), releases lock, begins `DecryptDanger`.
4. Before Goroutine A calls `Update(N)`, Goroutine B calls `Decrypt` for the duplicate copy of the same packet: acquires `decryptLock`, calls `window.Check(N)` → still true (A hasn't called `Update` yet), releases lock, begins `DecryptDanger`.
5. Both A and B successfully decrypt counter `N` and return valid plaintext; only one of the two subsequent `Update(N)` calls will succeed, but by that point both packets have already been treated as valid/decrypted, breaking the sliding-window replay guarantee. [1](#0-0)

	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()

	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]

		return err

	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}

func (b *Bits) Update(l *slog.Logger, i uint64) bool {
	// Fast path: i is the next expected counter. Split out so the function
	// stays small and avoids paying for the slow paths' slog argument-build
	// stack frame on every call. The bit read/test/write is inlined to
	// touch the backing word once.
	if i == b.current+1 {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if i > b.length && w&mask == 0 {
			b.lostCounter.Inc(1)
		}
		b.bits[word] = w | mask
		b.current = i
		return true
	}
	return b.updateSlow(l, i)
}
