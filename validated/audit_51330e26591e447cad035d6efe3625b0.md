### Title
CostTracker per-account/block cost desync from asymmetric saturating add vs. non-saturating subtract - (File: `cost-model/src/cost_tracker.rs`)

### Summary
`CostTracker::add_transaction_execution_cost()` and `CostTracker::sub_transaction_execution_cost()` are meant to be inverse operations used to keep a block-level cost counter (`block_cost`) and per-account cost map (`cost_by_writable_accounts`) consistent as transactions are added/removed or their costs are adjusted after execution. Like the reported `increaseUSDEDebt()`/`decreaseUSDEDebt()` asymmetry, the "increase" path always applies the full amount via `saturating_add`, while the "decrease" path applies `saturating_sub` per-account (which floors at 0, silently losing the excess) and a plain, non-saturating `AtomicU64::fetch_sub` for the block-level total (which wraps around on underflow instead of saturating).

### Finding Description
`add_transaction_execution_cost` unconditionally adds `adjustment` to each writable account's cost entry with `saturating_add`, and to `block_cost` with `SharedBlockCost::fetch_add` (backed by `AtomicU64::fetch_add`): [1](#0-0) 

`sub_transaction_execution_cost` is the intended inverse, but it decrements each account's cost with `saturating_sub` (which floors at 0 instead of returning how much was actually subtracted) and decrements `block_cost` with `SharedBlockCost::fetch_sub`, which delegates to plain `AtomicU64::fetch_sub` — not saturating: [2](#0-1) [3](#0-2) 

Because the "add" side is always applied in full while the "subtract" side can (a) silently clamp per-account entries to 0 when `adjustment` exceeds the tracked per-account cost, or (b) wrap `block_cost` around `u64::MAX` when `adjustment` exceeds the tracked `block_cost`, the two counters that are supposed to represent the same aggregate cost (sum of per-account costs vs. total block cost) can diverge — exactly the DefaultPool/ActivePool "increase always full, decrease only up to available" pattern from the external report, transplanted into agave's cost-tracking accounting.

`remove_transaction_cost` (called when a transaction is dropped/reverted, e.g. `CostTracker::remove()` used by `check_block_cost_limits` failure paths and scheduler retry paths) calls `sub_transaction_execution_cost(tx_cost, tx_cost.sum())`: [4](#0-3) 
and `add_transaction_cost`/`try_add` call `add_transaction_execution_cost(tx_cost, tx_cost.sum())`: [5](#0-4) 

In the normal path where every `add` is matched by exactly one `remove` with the identical `tx_cost.sum()`, the values line up and no desync occurs (each `HashMap` entry created by `add` should still hold at least `adjustment` when the corresponding `remove` runs). However, `add_transaction_execution_cost` is also exposed for adjusting costs after actual execution (see the `test_adjust_transaction_execution_cost` unit test, which calls `add_transaction_execution_cost` and `sub_transaction_execution_cost` directly with an independent `adjustment` value not tied to the original `tx_cost.sum()`): [6](#0-5) 
This shows the two functions are designed to be called with adjustment deltas that are not necessarily bounded by prior state for a given account, which is precisely the scenario where the asymmetric saturating/non-saturating behavior produces divergence between `cost_by_writable_accounts` totals and `block_cost`.

### Impact Explanation
If `block_cost` (a shared `AtomicU64` used by `CostPacer`/`try_add`/`would_fit` to gate whether new transactions fit in the block) wraps around due to a `fetch_sub` underflow, `block_cost.load()` would return a value near `u64::MAX`, causing all subsequent `would_fit()` checks to fail (`self.block_cost().saturating_add(cost) > self.limits.block_cost`), effectively halting transaction admission into the block cost tracker until the tracker is reset for a new bank. Conversely, per-account `saturating_sub` clamping to 0 undercounts the cost attributed to a still-hot account, which could let it exceed its intended per-account cost cap since replenished capacity is lost forever for the wrong accounts. Neither is a memory-safety or consensus-critical panic, but both distort the cost-based QoS/DoS mitigation this tracker exists to enforce, and the `u64` wraparound case can produce a persistent (until re-created) denial-of-block-inclusion effect for the current tracker instance.

### Likelihood Explanation
I could not fully verify, within the available search budget, an unprivileged-user-reachable call path where `sub_transaction_execution_cost`/`add_transaction_execution_cost` are invoked with an `adjustment` that structurally differs from the exact `tx_cost.sum()` used at `add` time (which is the precondition for the divergence to actually manifest, since matched add/remove of identical amounts cannot underflow). The grep for `update_execution_cost`/`adjust_transaction_cost` outside `cost_tracker.rs` returned no results, meaning the only exercised asymmetric-adjustment call site found is the unit test itself; I was unable to locate the production caller (if any) that adjusts costs after execution with a different value than the original estimate. This is a gap in my analysis — a background agent with terminal/build access should grep more broadly (including for `CostTracker::add(` / a public "update after execution" API, if one exists elsewhere or was added in a version not indexed) to confirm whether this code path is reachable by ordinary transaction submission (e.g., cost being adjusted downward after actual CU usage is known) rather than only through internal test code.

### Recommendation
Make `sub_transaction_execution_cost` symmetric with `add_transaction_execution_cost`: have it return the amount actually subtracted from each account (analogous to the report's suggested fix for `decreaseUSDEDebt()`), and use a saturating subtract for `block_cost` (e.g., `fetch_update` with `saturating_sub`) instead of a plain `AtomicU64::fetch_sub`, so `block_cost` can never wrap around, and so that any actual under-subtraction is reconciled rather than silently dropped or wrapped.

### Proof of Concept
Not independently verified end-to-end due to the reachability gap noted above. The mechanical bug is directly demonstrable in isolation: repeatedly call `CostTracker::sub_transaction_execution_cost(tx_cost, adjustment)` with `adjustment` greater than the currently tracked `block_cost` (e.g., by calling it without a matching prior `add_transaction_execution_cost` of equal size) causes `SharedBlockCost::fetch_sub` → `AtomicU64::fetch_sub` to wrap `block_cost` to a value near `u64::MAX`, at which point `would_fit()` (`cost-model/src/cost_tracker.rs:278`) permanently rejects new transactions for that `CostTracker` instance until it is replaced for a new bank. Confirming that this exact call sequence is reachable from untrusted transaction processing (rather than only via internal test harnesses) requires further investigation with full build/tooling access.

    fn add_transaction_cost(&mut self, tx_cost: &TransactionCost<impl TransactionWithMeta>) -> u64 {
        self.allocated_accounts_data_size += tx_cost.allocated_accounts_data_size();
        self.transaction_count += 1;
        self.transaction_signature_count += tx_cost.num_transaction_signatures();
        self.secp256k1_instruction_signature_count +=

        self.ed25519_instruction_signature_count += tx_cost.num_ed25519_instruction_signatures();
        self.secp256r1_instruction_signature_count +=
            tx_cost.num_secp256r1_instruction_signatures();
        self.add_transaction_execution_cost(tx_cost, tx_cost.sum())
    }

    fn remove_transaction_cost(&mut self, tx_cost: &TransactionCost<impl TransactionWithMeta>) {
        let cost = tx_cost.sum();
        self.sub_transaction_execution_cost(tx_cost, cost);
        self.allocated_accounts_data_size -= tx_cost.allocated_accounts_data_size();

    fn add_transaction_execution_cost(
        &mut self,
        tx_cost: &TransactionCost<impl TransactionWithMeta>,
        adjustment: u64,
    ) -> u64 {
        let mut costliest_account_cost = 0;
        for account_key in tx_cost.writable_accounts() {
            let account_cost = self
                .cost_by_writable_accounts
                .entry(*account_key)
                .or_insert(0);
            *account_cost = account_cost.saturating_add(adjustment);
            costliest_account_cost = costliest_account_cost.max(*account_cost);
        }
        self.block_cost.fetch_add(adjustment);

        costliest_account_cost
    }

/// Wrapper around blockcost to allow fast sharing of the value without locking.
/// Value is read-only outside of cost-tracker.
#[derive(Debug, Clone)]
pub struct SharedBlockCost(Arc<AtomicU64>);

impl SharedBlockCost {
    pub fn new(value: u64) -> Self {
        Self(Arc::new(AtomicU64::new(value)))
    }

    fn fetch_add(&self, value: u64) -> u64 {
        self.0.fetch_add(value, Ordering::Release)
    }

    fn fetch_sub(&self, value: u64) -> u64 {
        self.0.fetch_sub(value, Ordering::Release)
    }

    pub fn load(&self) -> u64 {
        self.0.load(Ordering::Acquire)
    }
}
