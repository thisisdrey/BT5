### Title
Stale PromiseYield receipt/status/timeout state survives `remove_account`, causing a recreated account to execute the old owner's yield-callback actions - (`core/store/src/utils/mod.rs:505`, `runtime/runtime/src/lib.rs:1500`)

### Finding Description
`remove_account` deletes an account's `Account`, `ContractCode`, access keys, gas-key nonces, and contract data, but never touches `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, `TrieKey::PromiseYieldTimeout`, or the `YieldIdToDataId`/`DataIdToYieldId` mappings, all of which are keyed by `receiver_id`/global index rather than being nested under the account's own subtree cleanup logic. [1](#0-0) 

An attacker deploys a contract on account `X` and calls `promise_yield_create`, which stores a `PromiseYieldStatus::Yielded` entry and (via `set_promise_yield_receipt`) a frozen `ActionReceipt` under `TrieKey::PromiseYieldReceipt{receiver_id: X, data_id}` when the yield receipt is delivered. [2](#0-1) [3](#0-2) 

This frozen `ActionReceipt` was constructed with `receiver_id == predecessor_id == X` (a self-directed promise batch, as is standard for the yield/resume pattern), and it can contain arbitrary batched actions (`AddKey`, `DeleteKey`, `DeployContract`, `Transfer`, `Stake`, etc.), since these are just ordinary promise-batch actions targeting the account itself.

The attacker then submits `DeleteAccountAction` on `X`. `remove_account` wipes the account/code/keys but leaves the `PromiseYieldReceipt`, `PromiseYieldStatus`, and the global `PromiseYieldTimeout` queue entry (which is indexed by a shard-wide counter, not by account, and has no corresponding removal path) intact.

Later, `X` is recreated (e.g., a new parent-account owner or a different keyholder creates the same named account). The dangling `PromiseYieldTimeout` entry (or a race with an in-flight resume) eventually causes `process_receipt`'s `VersionedReceiptEnum::PromiseResume` branch to fire against the *new* `X`. This code path looks up the stored yield receipt purely by `(account_id, data_id)` string/hash equality and, finding it, executes it via `apply_action_receipt` without any check that the account underneath is still the same logical entity that created the yield: [4](#0-3) 

Because privileged self-actions (`AddKey`, `DeleteKey`, `DeployContract`, etc.) are authorized in the runtime by checking `predecessor_id == receiver_id` (both frozen as the literal string `X` inside the serialized receipt), this check passes vacuously against the recreated account even though the new account has entirely different ownership/keys. No signature, nonce, or access-key check applies here because this is an internal receipt replay, not a freshly signed transaction — the authorization was captured once, at yield-creation time, and is never re-validated against the account's current identity.

### Impact Explanation
This is an authorization-escalation / determinism violation: an account that is supposed to start "fresh" after `DeleteAccountAction` (no code, no keys, no storage) can instead be silently mutated — potentially granted a full-access key or have contract code changed — by an action batch that only the *previous* owner of that name ever authorized. This falls under "authorization escalation across accounts or promises" in the accepted impact categories. Depending on the concrete action batch, this can lead to key compromise, code injection, or fund redirection on the recreated account without the new owner's consent.

### Likelihood Explanation
The setup (deploy contract, call `promise_yield_create`, call `DeleteAccountAction`) is fully reachable by an ordinary unprivileged account owner and costs only normal gas/storage fees — no validator or node privilege is required. The harder precondition is getting the *same account name* recreated under different effective ownership (e.g., via NEAR account-name resale/transfer of the parent account's keys, or a targeted subaccount name that a buyer predictably reuses); when the attacker is the same party throughout, there is no cross-ownership escalation, only self-mutation. That said, the underlying invariant break — deleted-account state persisting and later mutating a "fresh" account of the same id — is unconditionally reachable and reproducible with each delete/recreate cycle, independent of whether a hostile-ownership-change scenario is staged.

### Recommendation
`remove_account` should also purge any account-scoped PromiseYield state: iterate and remove all `TrieKey::PromiseYieldReceipt`/`TrieKey::PromiseYieldStatus`/`YieldIdToDataId`/`DataIdToYieldId` entries for `account_id`, and either (a) maintain a per-account index so the global `PromiseYieldTimeout` queue entries can be invalidated/skipped on account deletion, or (b) have the `PromiseResume`/timeout handler verify some incarnation/generation marker on the account (e.g., an account "epoch"/nonce bumped on creation) before executing a stored yield receipt, rejecting stale entries whose target account has been deleted and recreated since the yield was issued.

### Proof of Concept
Unit test in `core/store/src/utils` (or `runtime/runtime/src/tests/apply.rs`) using `TrieUpdate` directly:
1. Call `set_promise_yield_receipt(&mut state_update, &yield_action_receipt)` and `set_promise_yield_status(...)` for `receiver_id = X`, `data_id = D`, where `yield_action_receipt` contains an `AddKey` action granting a new full-access public key.
2. Call `set_account(&mut state_update, X, &account)` to simulate `X` existing, then call `remove_account(&mut state_update, &X)`; assert the account/code/keys are gone.
3. Assert (currently failing) that `get_promise_yield_receipt`/`get_promise_yield_status` for `(X, D)` still return `Some(..)`, proving the stale rows survive deletion.
4. Call `set_account` again for a freshly recreated `X` (no keys).
5. Feed a `VersionedReceiptEnum::PromiseResume` receipt for `(X, D)` through `process_receipt`/`apply_action_receipt` and assert that the new `X` account ends up with the attacker's `AddKey` applied, despite never having authorized it as the new owner.

pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
