### Title
Dust-transfer griefing fills `feeCollector` token-account list, DoS-ing all fee-bearing withdrawals and liquidations - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
The CAN CVE is a single crafted frame that wedges a node. The Metronome analog is a dust-driven account-list griefing attack: `Pool` enforces `MAX_TOKENS_PER_USER` on the combined `debtTokensOfAccount + depositTokensOfAccount` set, and `DepositToken._transfer` unconditionally registers the recipient in that set. An attacker can dust `feeCollector` with every listed deposit token until its set is full; thereafter every `withdraw`/`liquidate` that computes a non-zero fee reverts inside the fee `_transfer` to `feeCollector`, freezing withdrawals and liquidations protocol-wide.

### Finding Description
`DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance was zero before the transfer (`contracts/DepositToken.sol:517-520`). The pool-side hook enforces the cap:

```solidity
// contracts/Pool.sol
if (debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= MAX_TOKENS_PER_USER) {
    revert UserReachedMaxTokens();
}
```

The revert propagates back into `_transfer`, so any transfer of a *new* deposit-token type to an account at the cap reverts.

Two core fee paths transfer deposit tokens to `pool.feeCollector()`:

- `DepositToken._withdraw` — `_transfer(account_, _pool.feeCollector(), _fee)` (`contracts/DepositToken.sol:546-547`), executed for every `withdraw`/`withdrawFrom` whenever `feeProvider().withdrawFee() > 0`.
- `Pool.liquidate` — `depositToken_.seize(account_, _poolRegistry.feeCollector(), _fee)` (`contracts/Pool.sol:591-593`), executed for every liquidation with a non-zero liquidation fee.

Attack: for each `IDepositToken` in `pool.getDepositTokens()` (the number of distinct deposit tokens is itself bounded by `MAX_TOKENS_PER_USER`, `contracts/Pool.sol:703`), the attacker deposits a minimal amount and calls `DepositToken.transfer(feeCollector, 1)`. Once the fee collector's combined list reaches `MAX_TOKENS_PER_USER`, every subsequent `_transfer` of a not-yet-held token reverts. Because the fee transfer happens *before* `_burn`/`pull` in `_withdraw` and *after* `burn`/`seize` in `liquidate` but within the same atomic tx, the entire user-facing operation reverts — no withdrawal, no liquidation, no seized collateral moves.

The recipient has no opt-out: the set entry is added on first receipt and cannot be declined, and the check runs inside the token's transfer logic, not behind `onlyGovernor`, `whenNotPaused`, or a health check. `ReentrancyGuardTransient`/`nonReentrant` do not help — the attack uses plain single calls.

### Impact Explanation
While `feeCollector` is saturated: (a) all withdrawals on every deposit token revert whenever `withdrawFee > 0` — temporary freezing of all users' collateral; (b) all liquidations carrying a fee revert, so unhealthy positions cannot be closed, letting positions go deeper underwater and creating bad-debt / insolvency exposure. Recovery requires the fee collector to empty a dust balance per token type (i.e., a governance/EOA action calling `transfer` on each `DepositToken`), which an attacker can cheaply re-grief by re-dusting after each cleanup, sustaining the DoS. This matches the reported bug class: a cheap, unprivileged message (dust transfers) that crashes the victim node's (the pool's) core processing.

### Likelihood Explanation
Cost scales linearly with the number of listed deposit tokens: one dust deposit + one `transfer` each. No privileged role, oracle manipulation, or malicious infrastructure is required — `transfer` and `deposit` are public and dust amounts are near-free (wrappable native collateral via `NativeTokenGateway` makes the underlying cost trivial). The deployed configuration has non-zero fees on most pools, so the fee-transfer path is live. Residual uncertainty: the exact `MAX_TOKENS_PER_USER` constant and whether a given deployment's `feeCollector` is an EOA/contract able to sweep dust were not fully confirmed from the index; neither changes reachability of the attack.

### Recommendation
Do not add deposit/debt tokens to a recipient's per-account list on bare `transfer`; only register on `deposit`/`mint`, or skip the `UserReachedMaxTokens` check for the protocol's own `feeCollector`. Alternatively, treat the fee transfer as internal accounting (direct `balanceOf` update in `seize`/fee path) so it cannot revert on the recipient's set state.
