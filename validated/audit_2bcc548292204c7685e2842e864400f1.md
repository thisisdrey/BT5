## Analysis: `pallet-revive` storage-deposit refund can be permanently locked, causing indefinite call reversion

### Core broken invariant (from the external report)
The Derby `Vault.rebalance` bug shows a general bug class: a function performs a **charge-then-release** (deposit-then-withdraw) sequence against an account, and the "release" half can permanently fail due to a state constraint on that account (TrueFi/Idle's same-block deposit/withdraw restriction). Once that constraint is hit, the whole operation reverts, and it reverts **every time it is retried**, because the constraint reproduces itself identically on each attempt — a true indefinite block, not a one-off revert.

### Local analog
`substrate/frame/revive/src/lib.rs`, `Pallet::refund_deposit` (lines 2794–2831), used by `metering/storage.rs::ReservingExt::charge` for `Deposit::Refund` amounts: [1](#0-0) 

Every contract call that reduces its storage footprint triggers a "charge-then-refund" cycle within the *same* extrinsic: the meter first `charge`s the increase, then at finalization it must `transfer_on_hold` the excess back to the origin/contributor (`refund_on_hold`, implemented in `substrate/frame/revive/src/deposit_payment.rs`): [2](#0-1) 

If that `transfer_on_hold` fails — e.g. because the contract account (`from`) carries a lock/freeze from participating in some other pallet (the comment explicitly calls out **staking or governance locks**) — `refund_deposit` maps the error to `Error::<T>::StorageRefundLocked` and the whole extrinsic reverts:

```
// There are some locks preventing the refund. This could be the case if the
// contract participates in government. The consequence is that if a contract votes
// with its storage deposit it would no longer be possible to remove storage without first
// reducing the lock.
```

### Why existing guards don't stop this
- `check_limit` in `ReservingExt` (substrate/frame/contracts's older analog) and the analogous pre-flight checks in `pallet-revive` only validate that the **charging** side has enough liquidity; there is no pre-flight check that the **refund** side (transfer out of hold on the contract account) will succeed.
- The failure is deterministic and self-reinforcing: as long as the lock/freeze on the contract account remains in place, every subsequent call that would shrink storage and trigger a refund hits the exact same `Restriction::Free` failure and reverts with `StorageRefundLocked`. There is no automatic recovery path — the contract (or whoever controls the funds behind the lock, e.g. a conviction-voting lock with a fixed unlock block) must first remove the lock, which may not be within the calling user's control or timeframe.
- This is not caused by a malicious actor, governance abuse, or a compromised relayer: it is a normal user/contract combination (funds partially committed to another pallet's hold/freeze mechanism while also carrying a `pallet-revive` storage-deposit hold) hitting an ordering assumption that the codebase's own comment acknowledges as a known but unmitigated failure mode.

### Impact
Every future call to that contract that would reduce its storage usage (and hence trigger `Deposit::Refund`) will revert with `StorageRefundLocked`, blocking normal contract operation for that account indefinitely (a form of permanent/self-inflicted operational lock on contract execution, matching the "permanent user-fund or bridge-state lock" impact category), until the unrelated lock is externally cleared — mirroring exactly the "always reverts once triggered, requiring external intervention to unblock" pattern from the Derby M-40 report.

### Uncertainty
I could not fully trace, within the available indexing budget, every call site that finalizes deposit metering (`execute_postponed_deposits` / `RawMeter::finalize` in `substrate/frame/revive/src/metering/`) to confirm with 100% certainty that a `StorageRefundLocked` error always propagates to a full extrinsic revert in all code paths (vs. being absorbed in some deferred/back-off path). The `defensive_map_err` wrapping and the explicit, dedicated error variant strongly suggest it is treated as a hard failure of the call, but I was not able to review the full finalization state machine to rule out an alternate handling path. I recommend a Devin session with full repository access (not just the indexed subset) to trace `metering/mod.rs` and `metering/storage.rs::finalize` end-to-end and confirm whether this failure is truly unrecoverable without external lock removal, and to check whether an EVM/PVM contract can practically acquire a competing lock/freeze on its own account (e.g. via nomination-pools delegation, conviction-voting, or similar) that outlives the storage deposit hold.

### Title
Storage-deposit refund can be permanently blocked by an unrelated lock/freeze on the contract account, causing indefinite call reversion — (File: `substrate/frame/revive/src/lib.rs`)

### Summary
`Pallet::refund_deposit` performs a charge-then-refund cycle on the contract's held storage deposit within the same extrinsic. If the contract account carries an unrelated lock/freeze (e.g. from staking or governance participation), the refund's `transfer_on_hold` fails deterministically and repeatably with `StorageRefundLocked`, reverting every future call that would shrink storage.

### Finding Description
See analysis above — `refund_deposit` (substrate/frame/revive/src/lib.rs:2794-2831) calls `T::Deposit::refund_on_hold`, whose default implementation (`substrate/frame/revive/src/deposit_payment.rs:212-228`) uses `Restriction::Free`, which can fail if a competing lock/freeze constrains the account's balance movement. The failure is mapped to a dedicated `StorageRefundLocked` error rather than being silently tolerated.

### Impact Explanation
Legitimate, unprivileged contract usage becomes permanently stuck for any call that would reduce storage usage on the affected contract account, until the unrelated lock is externally removed — a self-perpetuating denial of contract functionality.

### Likelihood Explanation
Requires a contract account to simultaneously hold both a `pallet-revive` storage deposit and an independent lock/freeze from another pallet — plausible but not the default/common configuration; likelihood is moderate and depends on runtime composition (whether contracts can realistically acquire such locks).

### Recommendation
Add a pre-flight check (mirroring `check_limit` for the charge path) before finalizing a refund to detect if the refund would fail due to locks, and either defer/skip the refund gracefully (crediting an "owed" ledger rather than reverting the whole call) instead of hard-failing the entire extrinsic.

### Proof of Concept
Conceptual reproduction (needs full-repo access to implement as a runtime test): instantiate a contract, have its account acquire an unrelated `freeze`/`lock` from another pallet configured in the test runtime (e.g. simulate via `T::Currency::set_freeze`) sized to exceed the reducible balance once the storage deposit hold is released, then call the contract with an operation that clears storage/reduces its deposit and observe the extrinsic fail with `Error::StorageRefundLocked` on every retry.

	fn refund_deposit(
		hold_reason: HoldReason,
		from: &T::AccountId,
		dst: deposit_payment::Funds<T::AccountId>,
		amount: BalanceOf<T>,
	) -> Result<(), DispatchError> {
		if amount.is_zero() {
			return Ok(());
		}

		let to = match &dst {
			deposit_payment::Funds::Balance(to) | deposit_payment::Funds::TxFee(to) => *to,
		};
		let result = T::Deposit::refund_on_hold(hold_reason, from, dst, amount);

		result.defensive_map_err(|err| {
			let available = T::Deposit::total_on_hold(hold_reason, from);
			if available < amount {
				// The storage deposit accounting got out of sync with the balance: This would be a
				// straight up bug in this pallet.
				log::error!(
					target: LOG_TARGET,
					"Failed to refund storage deposit {amount:?} from contract {from:?} to origin {to:?}. Not enough deposit: {available:?}. This is a bug.",
				);
				Error::<T>::StorageRefundNotEnoughFunds.into()
			} else {
				// There are some locks preventing the refund. This could be the case if the
				// contract participates in government. The consequence is that if a contract votes
				// with its storage deposit it would no longer be possible to remove storage without first
				// reducing the lock.
				log::warn!(
					target: LOG_TARGET,
					"Failed to refund storage deposit {amount:?} from contract {from:?} to origin {to:?}: {err:?}. First remove locks (staking, governance) from the contracts account.",
				);
				Error::<T>::StorageRefundLocked.into()
			}
		})
	}

	fn refund_on_hold(
		reason: HoldReason,
		from: &T::AccountId,
		dst: Funds<T::AccountId>,
		amount: BalanceOf<T>,
	) -> DispatchResult {
		match dst {
			Funds::Balance(to) => {
				T::Currency::transfer_on_hold(
					&reason.into(),
					from,
					to,
					amount,
					Precision::Exact,
					Restriction::Free,
					Fortitude::Polite,
				)?;
