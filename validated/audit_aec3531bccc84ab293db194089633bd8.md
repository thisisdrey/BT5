### Title
Anti-replay timestamp check on handshake completion is bypassed when the existing tunnel is the initiator, allowing acceptance of a stale/replayed handshake - (File: handshake_manager.go)

### Summary
`HandshakeManager.CheckAndComplete` uses `lastHandshakeTime` as a monotonic, high-water-mark anti-replay value that is meant to reject any completed handshake older than one already recorded for a peer [1](#0-0) . The guard that enforces this, however, is unconditionally skipped whenever the existing tunnel was locally initiated, regardless of how the new handshake's timestamp compares to the existing one. This mirrors the reported bug class: a value that is supposed to only move forward (a high-water mark used to detect/prevent re-processing of stale state) is allowed to be overwritten with a lower/older value through an alternate code path, defeating the anti-replay protection it exists to provide.

### Finding Description
`lastHandshakeTime` is explicitly documented as an anti-replay high-water mark: "This is used to avoid an attack where a handshake packet is replayed after some time" [1](#0-0) .

The enforcement of that invariant lives in `CheckAndComplete`:
```go
// Is this a newer handshake?
if existingHostInfo.lastHandshakeTime >= hostinfo.lastHandshakeTime && !existingHostInfo.ConnectionState.initiator {
    return existingHostInfo, ErrExistingHostInfo
}
``` [2](#0-1) 

Because of the `&& !existingHostInfo.ConnectionState.initiator` clause, the timestamp comparison is only consulted when the *existing* hostinfo was created as a responder. If the existing tunnel was created because we (the local node) initiated the handshake (`existingHostInfo.ConnectionState.initiator == true`), the entire condition evaluates to `false` unconditionally — the `lastHandshakeTime` ordering is never checked. The new handshake (and its `lastHandshakeTime`, sourced from `result.HandshakeTime` in `continueHandshake` [3](#0-2) ) is accepted and replaces the existing tunnel via `unlockedAddHostInfo` [4](#0-3)  even if its `HandshakeTime` is older than the value already recorded, i.e., the "high-water mark" is silently lowered.

This is directly analogous to the `VaultStrategy` bug: there, `lastSharePrice` (meant to be a monotonically-increasing high-water mark) was lowered by `withdrawFromVault()`, causing a later legitimate rise to be mistaken for new yield. Here, `lastHandshakeTime` (meant to be a monotonically-increasing anti-replay marker) can be lowered by accepting an older handshake whenever the local side was the initiator, causing a stale/replayed handshake completion to be mistaken for a legitimate new one.

### Impact Explanation
An attacker who has captured an old, valid handshake-completion packet (e.g., a stage-2 response the real peer previously sent) can replay it after the local node has moved on to a newer session. Because the initiator-side check is bypassed, the replayed old handshake is treated as valid and used to reconstruct/replace the `ConnectionState` (`newConnectionStateFromResult`) for that peer, discarding the current session's more-recent handshake state. This is a concrete handshake-authentication/anti-replay bypass on the data path that legitimate anti-replay logic elsewhere in the codebase (e.g. the `Bits` window in `bits.go`) is designed to prevent at the packet-counter level, but which this timestamp-based guard fails to prevent at the handshake level for initiator-side tunnels.

### Likelihood Explanation
Reachable by any attacker who can inject UDP traffic toward a node and has previously observed (or otherwise obtained) an old handshake packet for a tunnel where the local node was the initiator — no valid CA-signed certificate is required to replay a previously captured packet, and the vulnerable branch is exercised on every completed handshake via `continueHandshake` → `CheckAndComplete`.

### Recommendation
Remove the `!existingHostInfo.ConnectionState.initiator` short-circuit, or otherwise always enforce `existingHostInfo.lastHandshakeTime < hostinfo.lastHandshakeTime` before accepting a new handshake for an existing peer, regardless of which side initiated the existing tunnel, so the anti-replay timestamp can never be lowered by a stale handshake packet.

### Proof of Concept
1. Node A initiates and completes a handshake with Node B; `A`'s `HostInfo.ConnectionState.initiator == true` and `lastHandshakeTime = T1` is recorded [3](#0-2) .
2. An on-path/off-path attacker captures an earlier legitimate handshake completion packet for the same peer pair with an older timestamp `T0 < T1` (e.g., from a prior reconnection attempt).
3. The attacker replays that captured packet to Node A. `continueHandshake` builds a new `hostinfo` with `lastHandshakeTime = T0` and calls `CheckAndComplete`.
4. In `CheckAndComplete`, since `existingHostInfo.ConnectionState.initiator == true`, the condition `existingHostInfo.lastHandshakeTime >= hostinfo.lastHandshakeTime && !existingHostInfo.ConnectionState.initiator` is `false` even though `T1 >= T0`, so `ErrExistingHostInfo` is not returned [2](#0-1) .
5. The stale handshake is accepted, replacing the current tunnel state — the anti-replay high-water mark has been lowered/bypassed.
