## Title
Git submodule `file://` protocol restriction is disabled during `git_repository`/`new_git_repository` submodule fetches, enabling local-file read via attacker-controlled `.gitmodules` - (File: `tools/build_defs/repo/git_worker.bzl`)

### Summary
`git_repository`/`new_git_repository` (and any Starlark repo rule reusing `git_worker.bzl`) supports `init_submodules`/`recursive_init_submodules`, which run `git submodule update --init [--recursive] --checkout --force` with the flag `-c protocol.file.allow=always` explicitly forced on. This unconditionally overrides Git's own default protection (`protocol.file.allow=user`, hardened after CVE‑2022‑39253) that normally blocks submodules from being fetched over the local `file://` transport during a submodule operation. A hostile git repository that the victim's build clones (via `remote`) can ship a `.gitmodules` file whose submodule URL is `file:///<absolute path>`, and Bazel's forced override causes Git to happily clone that local path into the checkout, allowing exfiltration of arbitrary files readable by the build user into the resulting repository content (which subsequently is built/inspected).

### Finding Description
`update_submodules` in `tools/build_defs/repo/git_worker.bzl` builds the submodule command as: [1](#0-0) 

```
def update_submodules(ctx, git_repo, recursive = False):
    if recursive:
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--recursive", "--checkout", "--force")
    else:
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--checkout", "--force")
```

The comment above it explains the intent was only to permit local-directory clones for testing/CI convenience (bazel issue #17040), but the config is applied unconditionally to every `git_repository`/`new_git_repository` invocation that sets `init_submodules = True` or `recursive_init_submodules = True`, regardless of whether the top-level `remote` itself is local or remote: [1](#0-0) 

Git upstream deliberately restricts `file://` submodule transports by default (`protocol.file.allow=user`) because a `.gitmodules` file is *content of the cloned repository* and therefore fully attacker-controlled once an attacker can get a victim to add or update a `git_repository` pointing at their repo (a public mirror, a fork used in CI for an external PR, etc.). Without the restriction, a malicious `.gitmodules` entry such as:

```
[submodule "leak"]
    path = leak
    url = file:///etc/passwd
```

or a path such as `file:///home/<user>/.ssh` will be locally "cloned" by Git as if it were a normal submodule, and its contents are checked out into the resulting repository tree that Bazel treats as trusted repository content and further processes/builds. Bazel's `-c protocol.file.allow=always` disables the safeguard Git specifically introduced to prevent this attack class.

The top-level clone (`git_repo`) is fetched over network protocols honoring Bazel's containment intent (no cross-filesystem access implied), but the *submodule* step, gated by attacker-supplied `.gitmodules` content, is where the override reopens the local-file access path that upstream Git closed by default.

### Impact Explanation
An attacker who can get a Bazel project to `git_repository`/`new_git_repository` a repository they control (a compromised or malicious mirror, a fork built by CI for an external contribution, or any dependency source not otherwise vetted) and who sets `init_submodules`/`recursive_init_submodules` to true can exfiltrate arbitrary files readable by the build process (SSH keys, cloud credentials, CI secrets, etc.) into the checked-out repository content, which subsequently becomes part of the build inputs/output tree — a read outside of the intended external-repository content boundary. This is precisely the class of vulnerability CVE‑2022‑39253 and Git's `protocol.file.allow` default were designed to close; Bazel actively re-disables that protection.

### Likelihood Explanation
`init_submodules`/`recursive_init_submodules` are common, documented, user-facing options of `git_repository`. Any workflow that clones third-party or externally-contributed repositories with submodules enabled (e.g., CI building forks/PR branches, or `git_repository` pointed at a compromised mirror) is exposed with default flags, no opt-in required beyond the already-common `init_submodules = True` setting; the attacker needs only control of the repository content (`.gitmodules`), not the build machine or credentials.

### Recommendation
Do not force `protocol.file.allow=always` unconditionally. Restrict submodule protocol handling to Git's hardened default (`protocol.file.allow=user`/`no`) unless the specific submodule URL is verified to be within an explicitly trusted, Bazel-controlled local path (e.g., only enable the override when the top-level `remote` itself is a local filesystem path used for testing), and otherwise leave Git's default protections intact so untrusted `.gitmodules` content cannot request `file://` fetches.

### Proof of Concept
1. Create `leaker.git` with `.gitmodules`:
```
[submodule "leak"]
    path = leak
    url = file:///etc/hostname
```
(commit the submodule pointer as any valid tree entry).
2. In a Bazel workspace:
```
git_repository = use_repo_rule("@bazel_tools//tools/build_defs/repo:git.bzl", "git_repository")
git_repository(
    name = "leaker",
    remote = "https://example.com/leaker.git",
    branch = "main",
    recursive_init_submodules = True,
)
```
3. Run `bazel fetch @leaker`. Because `update_submodules` runs with `-c protocol.file.allow=always`, Git clones `/etc/hostname` (or any attacker-chosen absolute path readable by the invoking user) into `external/+git_repository+leaker/leak/`, where its contents are now part of the fetched repository tree — contrasted with stock Git behavior (`protocol.file.allow=user`), which refuses the `file://` submodule with `fatal: transport 'file' not allowed`.

A `src/test/shell/bazel/starlark_git_repository_test.sh`-style regression test can assert that after fetching such a crafted repo with `recursive_init_submodules = True`, the submodule directory does NOT contain the contents of the local file, i.e. that Git's `fatal: transport 'file' not allowed` error is produced instead of a successful checkout.
