No cap exists on the number of reference updates processed via the proc-receive hook path. I have enough to write the final analog finding.### Title
Unbounded per-reference-update loop in proc-receive non-atomic path spawns one Git subprocess and update-hook RPC per pushed ref, allowing a single push to exhaust server resources - (File: internal/gitaly/hook/receivepack/receive_pack.go)

### Summary
The Solidity report describes an unbounded loop (`projectCost()`) whose cost scales linearly with an attacker/user-controllable list length (`taskCount`), invoked from a gating/validation function (`lendToProject`, `toggleLendingNeeded`) with no cap, enabling gas-exhaustion DoS. The Gitaly analog is the non-atomic reference-update loop in the `proc-receive` hook handling path used by `git-receive-pack`. The number of reference updates in a single push is fully controlled by the pushing user and is never capped before this loop runs; each iteration spawns a brand-new `git update-ref` subprocess and executes the `update` hook (itself an RPC call, potentially to Rails via custom hooks) once per reference, giving linear, uncapped per-push resource cost analogous to the unbounded `projectCost()` loop.

### Finding Description
`NewProcReceiveHandler` reads an unbounded number of reference updates from the `proc-receive` pkt-line stream with no limit check: [1](#0-0) 

These updates are handed to `procReceiveHook`, which — in the non-atomic case — iterates over every single update and, for each one, calls `receivePackReferenceUpdates` with a slice containing just that one update: [2](#0-1) 

`receivePackReferenceUpdates` itself spawns a fresh `updateref.New(ctx, repo, ...)` process (a new OS-level Git subprocess) and invokes `hookManager.UpdateHook` (which can shell out to custom administrator hooks) for every reference update it's given: [3](#0-2) 

Because the non-atomic branch calls `receivePackReferenceUpdates` once *per reference* rather than once for the whole batch, a push containing N reference updates results in N independent `git update-ref` process spawns and N update-hook executions, with no ceiling on N anywhere in this path (unlike, e.g., `ListCommits`/`GetTreeEntries` elsewhere in the codebase, which explicitly cap iteration via `PaginationParameter`/`WithMaxCount`). This mirrors the reported bug class exactly: an unbounded loop whose per-iteration cost is non-trivial (subprocess spawn + hook RPC) and whose iteration count is dictated by attacker-supplied input (number of refs in one push), reachable through the ordinary `git push` → `git-receive-pack` → `proc-receive` hook path used by any authenticated pushing user.

### Impact Explanation
An ordinary user who can push to a repository (a normal, unprivileged Git operation) can submit a single push containing a very large number of reference updates (e.g., many branch/tag creates or updates in one atomic Git protocol exchange). This forces the Gitaly node to sequentially spawn one Git subprocess and run one (potentially externally-implemented) update hook per reference, with no upper bound. This can exhaust process table slots, CPU, and file descriptors on the Gitaly node, degrading or denying service for that repository and potentially the node as a whole, especially since custom hooks may make outbound network calls (e.g., to Rails) per reference — directly analogous to how attacker-controlled `taskCount` growth degraded `lendToProject()`/`toggleLendingNeeded()` in the original report.

### Likelihood Explanation
Likelihood is moderate-to-high: no special privilege is required beyond normal push access to a repository, and Git natively supports pushing large numbers of refs in one invocation (e.g., `git push origin 'refs/heads/*:refs/heads/*'` against a repo with many local branches, or scripted `--atomic`-disabled pushes with thousands of ref updates). The `proc-receive` hook path is a documented, actively used mechanism (per `doc/hooks.md`) for routing reference updates through the write-ahead log, so it is reachable in normal operation, not a rare code path.

### Recommendation
Introduce an explicit, configurable upper bound on the number of reference updates processed within a single `proc-receive` invocation (mirroring the `--max-count`/`limit` caps already used by other list-oriented RPCs such as `ListCommits`), and reject or chunk pushes that exceed it before the atomic/non-atomic branch executes. Additionally, consider batching the non-atomic path so it does not spawn a distinct `updateref.New` subprocess per reference, but rather reuses one Git subprocess and only branches per-reference at the hook/accept-reject level, similar to how the atomic path already batches into a single `receivePackReferenceUpdates` call.

### Proof of Concept
1. Create N branches locally (e.g., N = 50,000) all pointing at existing commits.
2. Push them all to a Gitaly-backed repository in a single `git push` invocation without `--atomic`, e.g.: `for i in $(seq 1 50000); do git branch "b$i" HEAD; done; git push origin 'refs/heads/b*'`.
3. Observe that Gitaly's `proc-receive` handler (`internal/gitaly/hook/procreceive_handler.go`) parses all 50,000 updates into memory with no cap, and `procReceiveHook`'s non-atomic branch (`internal/gitaly/hook/receivepack/receive_pack.go` lines 116-138) sequentially spawns 50,000 separate `git update-ref` processes and 50,000 update-hook executions, consuming CPU/process resources proportional to N with no configured limit, degrading the Gitaly node's ability to service other requests.

func receivePackReferenceUpdates(
	ctx context.Context,
	cfg config.Cfg,
	req gitcmd.ReceivePackRequest,
	repo *localrepo.Repo,
	hookManager hook.Manager,
	updates []hook.ReferenceUpdate,
	stdout, stderr io.Writer,
) (returnedErr error) {
	hooksPayload, err := setupHooksPayloadEnv(ctx, cfg, req, repo, gitcmd.UpdateHook)
	if err != nil {
		return fmt.Errorf("creating hooks payload: %w", err)
	}

	updater, err := updateref.New(ctx, repo, updateref.WithNoDeref())
	if err != nil {
		return fmt.Errorf("spawning ref updater: %w", err)
	}
	defer func() {
		if err := updater.Close(); err != nil && returnedErr == nil {
			returnedErr = fmt.Errorf("cancel ref updater: %w", err)
		}
	}()

	if err := updater.Start(); err != nil {
		return fmt.Errorf("start reference transaction: %w", err)
	}

	for _, update := range updates {
		if err := hookManager.UpdateHook(
			ctx,
			req.GetRepository(),
			update.Ref.String(),
			update.OldOID.String(),
			update.NewOID.String(),
			[]string{hooksPayload},
			stdout, stderr,
		); err != nil {
			return fmt.Errorf("running update hook: %w", err)
		}

		if err := updater.Update(update.Ref, update.NewOID, update.OldOID); err != nil {
			return fmt.Errorf("queueing ref to be updated: %w", err)
		}
	}
