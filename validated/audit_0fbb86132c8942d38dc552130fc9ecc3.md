## Title
Relay control-plane accepts unverified `RelayFromAddr` from a peer, allowing remote-state poisoning of the relay hostmap - (File: `relay_manager.go`)

## Summary
The external report describes `L2LivepeerToken.burn()` trusting a caller-supplied `_from` parameter instead of restricting the action to the caller's own identity, letting a privileged-but-untrusted actor act on an arbitrary target. The closest reachable analog in this codebase is `relayManager.handleCreateRelayRequest`, which extracts the `from` address directly from the attacker-controlled `NebulaControl.RelayFromAddr` field of an authenticated `Control` message and uses it, unchecked against the sender's certificate-verified `vpnAddrs`, to key relay state on the hostinfo (`h`) that delivered the message.

## Finding Description
`handleCreateRelayRequest` is invoked when a peer with an already-established (cert-verified) tunnel `h` sends a `NebulaControl_CreateRelayRequest` control message: [1](#0-0) 


The certificate-authenticated identity of the sender is `h.vpnAddrs` (populated during the handshake and verified against the CA pool via `certVerifier`/`VerifyCertificate`), but `from` here is taken solely from the wire-format `RelayFromAddr` field of the control message body — a value the peer can set to anything, including an address belonging to a completely different, uninvolved host. There is no check anywhere in this function (or in the caller path) that `from == h.vpnAddrs[i]` for some `i`. [2](#0-1)

Because the relay record's association with a VPN address is derived from an unauthenticated field rather than the mutually-authenticated `vpnAddrs`, a peer that has completed a legitimate handshake (and thus holds a *valid* certificate for its own address) can still claim an arbitrary third-party VPN address as the "from" party of a relay request. This is structurally identical to the `burn(address _from, ...)` flaw: an authenticated actor supplies an unrelated address parameter that the privileged operation (installing relay/routing state) trusts without verifying it belongs to the caller.

## Impact Explanation
This enables remote state poisoning of the relay hostmap: an authenticated-but-malicious peer can insert relay routing entries associated with a victim VPN address it does not own. Depending on downstream consumption of this state (`QueryRelayForByIp`, `QueryVpnAddrsRelayFor`, `CompleteRelayByIP`), this can corrupt how the relay node routes traffic destined for or attributed to the victim's overlay address, enabling traffic misdirection/hijacking through the attacker's tunnel or persistent relay-state corruption that a legitimate peer cannot easily clear. This falls within the accepted impact classes of "remote state poisoning" via hostmap/relay address trust.

## Likelihood Explanation
Any node that can complete a normal Nebula handshake (i.e., holds a certificate signed by the network's own CA, but for its own address only — not for the victim's address) can immediately send a crafted `CreateRelayRequest` control message with an arbitrary `RelayFromAddr`. No additional privilege or victim interaction is required beyond having "am_relay" set on the target relay node, which is a normal peer configuration in relay-enabled deployments. This is a straightforward, deterministic issue in message handling, not a race condition.

## Recommendation
In `handleCreateRelayRequest`, validate that the claimed `from` address is actually one of the sending hostinfo's certificate-verified VPN addresses (`slices.Contains(h.vpnAddrs, from)`), analogous to the existing check already used in `handleHostUpdateNotification` in `lighthouse.go` ("Simple check that the host sent this not someone else"). Reject the request (log and return) if `from` does not match any address in `h.vpnAddrs`, before calling `AddRelay` or performing any `relayState` lookups/mutations keyed by `from`.

## Proof of Concept
Conceptual PoC (not executed, based on code paths reviewed):
1. Attacker `A` completes a legitimate Nebula handshake with relay node `R` (`am_relay: true`), obtaining hostinfo `h` for `A`'s own certificate-verified address `vpnA`.
2. `A` sends `R` a `Control`/`NebulaControl_CreateRelayRequest` message with `RelayFromAddr = vpnVictim` (an address belonging to a different, uninvolved host `V`) and `RelayToAddr` set to `R`'s own address.
3. `R.handleCreateRelayRequest` computes `from = vpnVictim`, confirms `target` is itself, and — finding no existing relay for `vpnVictim` on hostinfo `h` — calls `AddRelay(rm.l, h, f.hostMap, vpnVictim, ..., TerminalType, Established)`, associating `A`'s tunnel `h` with a `TerminalType` relay for `vpnVictim`, without ever checking that `vpnVictim` is in `h.vpnAddrs`.
4. `R` now holds relay state that maps `vpnVictim` to `A`'s hostinfo, which can affect subsequent relay routing/response decisions for traffic referencing `vpnVictim` on `R`.

This confirms the root cause (unchecked `from`) is reachable purely with a valid certificate for one's own identity, matching the "reachable by attacker with no CA-signed certificate for the target identity" analog class.
