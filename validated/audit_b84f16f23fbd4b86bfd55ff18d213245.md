### Title
Unbounded `subArray` Read on Attacker-Controlled Contract Log Data Causes Uncaught Exception in Shielded TRC20 Note Scanning API - (File: framework/src/main/java/org/tron/core/Wallet.java)

### Summary
The `getNoteTxFromLogListByOvk`/`getNoteTxFromLogListByIvk` code path in `Wallet.java`, reachable through the public `scanShieldedTRC20NotesByIvk`/`scanShieldedTRC20NotesByOvk` gRPC/HTTP API, parses a smart-contract emitted event log (`TransactionInfo.Log.getData()`) at fixed byte offsets without first validating the log data length, unlike the analogous branch for `logType == 4` which does perform such a check.

### Finding Description
For `logType` 1–3 (note-producing shielded TRC20 events), the code does: [1](#0-0) 
There is no length check on `logData` before this fixed-offset slicing, in contrast to the `logType == 4` branch a few lines below, which explicitly guards with `if (logData.length < 64 + BURN_CIPHER_RECORD_SIZE) return Optional.empty();` [2](#0-1) 

`ByteArray.subArray` performs a raw `System.arraycopy` with no bounds validation: [3](#0-2) 

Because `log.getData()` originates from an event emitted by an arbitrary, attacker-deployed smart contract (any account can deploy a contract that mimics the expected topic signature used to classify `logType`, while emitting a truncated `data` payload), an attacker can cause `ByteArray.subArray` to throw `ArrayIndexOutOfBoundsException` when the offset/length exceeds `logData.length`. This exception is not declared or caught within `getNoteTxFromLogListByOvk`/`getNoteTxFromLogListByIvk`, `queryTRC20NoteByIvk`, or `scanShieldedTRC20NotesByIvk`, so it propagates as an unchecked `RuntimeException` out of the Wallet API method.

This is analogous to the reported CVE-2026-81532 bug class: user-supplied data whose length is not bounded before it is copied against a fixed-offset/fixed-size structure, corrupting/crashing the consuming code path.

### Impact Explanation
Any account (no special privilege required — asset issuer/contract deployer) can deploy a contract that emits a log entry matching the shielded TRC20 event topic used by `getShieldedTRC20LogType` but with a short `data` payload. Once such a transaction is included in a block, every subsequent call to `scanShieldedTRC20NotesByIvk`/`scanShieldedTRC20NotesByOvk` that covers the block range containing this malicious log will throw an unhandled exception while iterating the log list, since the malformed log is permanently stored in the block's `TransactionInfo`. This makes a wallet/API query permanently unable to be served for that block range — i.e., "an API the node can no longer serve" for legitimate shielded-note scanning callers, satisfying the required impact bar even though it does not corrupt process memory the way the native ODBC CVE does (Java bounds-checks arrays, so this manifests as an exception, not raw memory corruption).

### Likelihood Explanation
Likelihood is high: deploying a contract and emitting a crafted log is a routine, unprivileged operation (`TriggerSmartContract`/`CreateSmartContract`), and the vulnerable code path lacks any length validation that its sibling branch (`logType == 4`) already implements, showing the check was simply omitted rather than being intentionally unnecessary.

### Recommendation
Add an explicit length check for `logData` before slicing in the `logType > 0 && logType < 4` branch (mirroring the `logType == 4` guard), e.g. require `logData.length >= 788` before calling `ByteArray.subArray`, and return `Optional.empty()` (or skip the log) otherwise. Additionally, wrap the per-log processing loop in `queryTRC20NoteByIvk`/`queryTRC20NoteByOvk` with a try/catch to prevent one malformed log entry from aborting the whole scan request.

### Proof of Concept
1. Deploy a smart contract that emits a `LOG` instruction with a topic equal to one of the shielded TRC20 event signatures recognized by `getShieldedTRC20LogType` as `logType` 1, 2, or 3, but with a `data` payload shorter than 788 bytes (e.g., 32 bytes).
2. Wait for the transaction to be confirmed and its `TransactionInfo` (with the log) persisted.
3. Call the `scanShieldedTRC20NotesByIvk` (or `Ovk`) gRPC/HTTP API with a block range including that transaction's block.
4. Observe `ByteArray.subArray` throw `ArrayIndexOutOfBoundsException` inside `getNoteTxFromLogListByOvk`/`ByIvk`, propagating uncaught out of `queryTRC20NoteByIvk`, causing the API call to fail every time it is invoked over that block range.

Note: I was unable to fully verify the exact `getShieldedTRC20LogType` implementation (topic-matching logic) within the available indexed content, so the precise topic values required to trigger `logType` 1–3 classification could not be directly confirmed from source; a full verification would require reading that method's body directly (not returned by the index) to confirm the exact topic constants used for classification.
