## Title
Relayer Reward Paid and Pending Order Cleared Regardless of Ethereum Execution Outcome - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
`DeliveryReceipt` decoded from Ethereum's `InboundMessageDispatched` event carries a `success: bool` field indicating whether the inbound message actually executed successfully on Ethereum, but `Pallet::process_delivery_receipt` never inspects this field before paying the relayer reward and removing the `PendingOrder`. As a result, a relayer submitting a valid receipt for a message whose Ethereum-side execution failed (`success = false`) is still paid the full `order.fee` and the order is permanently deleted, breaking the invariant that settlement must only advance after execution succeeds.

## Finding Description
The `DeliveryReceipt` struct decodes the `success` field straight from the Solidity `InboundMessageDispatched` event log: [1](#0-0) 

`Pallet::process_delivery_receipt` only checks the gateway address and the existence of a `PendingOrder` for the nonce before paying the reward and removing the order — `receipt.success` is never read anywhere in this function: [2](#0-1) 

A repository-wide search for `success` within `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs` returns no matches, confirming the field is decoded upstream but completely unused in the settlement path. The module documentation itself describes the intended flow as "verify proof → fetch pending order → pay reward → remove order," with no mention of checking dispatch success: [3](#0-2) 

This directly violates the required invariant that "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically" — here, reward payment and `PendingOrders::remove` both proceed unconditionally regardless of `receipt.success`.

## Impact Explanation
Any relayer who submits a valid, correctly-proven `InboundMessageDispatched` event for a message whose Ethereum-side command execution reverted (`success = false`) still collects the full `order.fee` via `T::RewardPayment::register_reward`, and `PendingOrders` is unconditionally cleared via `<PendingOrders<T>>::remove(nonce)`. This is an incorrect/duplicate-style settlement bug within the bridge reward accounting: work that did not successfully complete is paid as though it had, and there is no mechanism to retry or dispute the order since it is deleted regardless of outcome. This matches the in-scope impact category of duplicate or incorrect payout/settlement state for bridge message processing.

## Likelihood Explanation
This requires no malicious actor — it triggers under ordinary, permissionless relaying whenever a legitimately relayed inbound command fails execution on Ethereum for any reason (insufficient destination gas, a reverting command, etc.). The relayer need not cause the failure; they only need to submit the real, correctly-proven receipt for a message whose execution failed on Ethereum. Since Ethereum-side execution outcomes for arbitrary commands cannot be guaranteed in advance, this is a realistic, repeatable condition rather than a contrived edge case.

## Recommendation
Gate the reward payment and order removal on `receipt.success` in `process_delivery_receipt`. On `success == false`, either withhold or reduce the reward, and route the failed order to a distinct handling path (retry, dispute, or a separate "failed delivery" accounting flow) rather than unconditionally paying the relayer and deleting the `PendingOrder`.

## Proof of Concept
1. A message is enqueued via `do_process_message`, creating `PendingOrders[nonce]` with a nonzero `fee`, as shown in the storage-insertion logic at `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs:426-436`.
2. The relayer relays the message to Ethereum; the corresponding command execution reverts on the Gateway contract, which nonetheless emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. The relayer obtains a valid proof for this event and calls `submit_delivery_receipt`, decoding it into `DeliveryReceipt { success: false, .. }` per `bridges/snowbridge/primitives/outbound-queue/src/v2/delivery_receipt.rs:35-51`.
4. `process_delivery_receipt` checks only `receipt.gateway` and `PendingOrders::get(nonce)` (`bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs:453-464`); since `order.fee > 0`, `T::RewardPayment::register_reward` is called and `PendingOrders::remove(nonce)` executes unconditionally regardless of `receipt.success`.
5. Expected fix: a unit test asserting that when `receipt.success == false`, `register_reward` is not invoked and/or the order is not silently deleted without a recorded failure state.

			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {

			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward

					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });
