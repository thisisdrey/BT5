Found: `EstablishRelay` in `relay_manager.go` completes a relay by `InitiatorRelayIndex` (a peer-supplied local index) without verifying that the `RelayFromAddr`/`RelayToAddr` in the message still match the address the relay slot was originally allocated for.

### Title
Stale relay-index completion allows relay state to be finalized against mismatched peer/address data - ([File: relay_manager.go])

### Summary
`relayManager.EstablishRelay` (called from `handleCreateRelayResponse`) completes a previously "Requested" relay slot purely by looking up `m.InitiatorRelayIndex` via `CompleteRelayByIdx`, and never re-validates that the `RelayFromAddr`/`RelayToAddr` fields on the incoming `CreateRelayResponse` still correspond to the `PeerAddr` that was recorded when the relay slot was created. This mirrors the reported Zaros pattern: an operation is keyed off a stale identifier (here, `InitiatorRelayIndex`) while other fields on the same message (address/version-dependent `RelayFromAddr`/`RelayToAddr`) are accepted and used to build subsequent messages without cross-checking them against the identifier's original binding.

### Finding Description
`AddRelay` allocates a relay index bound to a specific `vpnIp` (`PeerAddr`) and stores it as `Requested`: [1](#0-0) 

Later, `EstablishRelay` finalizes that slot using only the numeric index taken from the incoming control message, with no check that the message's `RelayFromAddr`/`RelayToAddr` match the `PeerAddr` recorded on the relay when it was allocated: [2](#0-1) 

`handleCreateRelayResponse` then forwards a `CreateRelayResponse` to `peerRelay.PeerAddr` derived from `relay.PeerAddr` (taken from the completed relay object) and, critically, echoes `m.RelayToAddr` back into the outgoing response unmodified: [3](#0-2) 

Because `CompleteRelayByIdx` (`hostmap.go:192-205`) mutates the relay purely by local index lookup, and `EstablishRelay` performs no address-consistency check against the message's `RelayFromAddr`/`RelayToAddr` fields before trusting `relay.PeerAddr`, an index that was allocated for one peer address can be completed/transitioned to `Established` by a control message whose address fields describe a different peer, as long as the attacker (or a compromised/misbehaving relay node) knows or predicts the numeric `InitiatorRelayIndex`. This is directly analogous to the reported bug: the keeper (here, `handleCreateRelayResponse`) uses an old/allocated identifier (`InitiatorRelayIndex`) together with new, unchecked accompanying data (`RelayFromAddr`/`RelayToAddr`) to finalize state, without asserting that the identifier and the data still refer to the same logical entity.

### Impact Explanation
If exploited, a peer participating in the relay handshake (which does not require possession of a CA-signed certificate for the *target* being relayed to — only for the relay leg itself) could cause a relay's control-plane state to be established/finalized for the wrong `PeerAddr`, resulting in relay/forwarding state poisoning: traffic intended for one VPN address could be misrouted or a relay slot intended for one peer could be established using data intended for another. This falls under "remote state poisoning" of the hostmap/relay trust structures explicitly called out as in-scope.

### Likelihood Explanation
Likelihood is moderate: the attacker must be a party already engaged in the relay handshake protocol (i.e., can send `Control`/`NebulaControl` messages that reach `handleCreateRelayResponse`), and must guess or observe the `InitiatorRelayIndex` value, which is a `generateIndex`-derived 32-bit value but is also disclosed to relay participants as part of the normal protocol flow (it's not secret — it's sent to peers in `CreateRelayRequest`). Because the completion path trusts the index alone and does not cross-validate it against the addresses carried in the same message, an adversarial or compromised relay participant has a direct path to trigger the mismatch.

### Recommendation
In `EstablishRelay` (relay_manager.go), after `CompleteRelayByIdx` succeeds, validate that the resulting `relay.PeerAddr` matches the `RelayFromAddr`/`RelayToAddr` (or `OldRelayFromAddr`/`OldRelayToAddr` for v1) decoded from the incoming `NebulaControl` message. If they don't match, treat it as `unknown relay` and reject/log rather than proceeding to build a `CreateRelayResponse` from the (potentially mismatched) `relay.PeerAddr`.

### Proof of Concept
Not directly executable without the full protobuf/handshake harness, but the logical PoC path is:
1. Attacker (party A) requests a relay through relay node R for target `vpnIp1`, receiving/knowing `InitiatorRelayIndex = X` (via the normal `CreateRelayRequest` flow, since indexes are sent over the wire in cleartext control messages).
2. Before R processes/forwards the real response, attacker sends a crafted `CreateRelayResponse` to R with `InitiatorRelayIndex = X` but `RelayFromAddr`/`RelayToAddr` fields describing a different peer (`vpnIp2`).
3. `EstablishRelay` finds the relay by index X only, ignores that the addresses in the message differ from the relay's `PeerAddr`, and returns success — `handleCreateRelayResponse` proceeds to notify `peerHostInfo` (looked up via `relay.PeerAddr`, i.e., `vpnIp1`) using data derived partly from the attacker's mismatched message fields, propagating the poisoned state into the relay chain.

// EstablishRelay updates a Requested Relay to become an Established Relay, which can pass traffic.
func (rm *relayManager) EstablishRelay(relayHostInfo *HostInfo, m *NebulaControl) (*Relay, error) {
	relay, ok := relayHostInfo.relayState.CompleteRelayByIdx(m.InitiatorRelayIndex, m.ResponderRelayIndex)
	if !ok {
		var relayFrom, relayTo any
		if m.RelayFromAddr == nil {
			relayFrom = m.OldRelayFromAddr
		} else {
			relayFrom = m.RelayFromAddr
		}
		if m.RelayToAddr == nil {
			relayTo = m.OldRelayToAddr
		} else {
			relayTo = m.RelayToAddr
		}

		rm.l.Info("relayManager failed to update relay",
			"relay", relayHostInfo.vpnAddrs[0],
			"initiatorRelayIndex", m.InitiatorRelayIndex,
			"relayFrom", relayFrom,
			"relayTo", relayTo,
		)
		return nil, fmt.Errorf("unknown relay")
	}

	return relay, nil
}

func (rm *relayManager) handleCreateRelayResponse(v cert.Version, h *HostInfo, f *Interface, m *NebulaControl) {
	//nil-checks for protoAddrToNetAddr handled by caller
	relayFrom := protoAddrToNetAddr(m.RelayFromAddr)
	relayTo := protoAddrToNetAddr(m.RelayToAddr)
	rm.l.Info("handleCreateRelayResponse",
		"relayFrom", relayFrom,
		"relayTo", relayTo,
		"initiatorRelayIndex", m.InitiatorRelayIndex,
		"responderRelayIndex", m.ResponderRelayIndex,
		"vpnAddrs", h.vpnAddrs,
	)

	relay, err := rm.EstablishRelay(h, m)
	if err != nil {
		rm.l.Error("Failed to update relay for relayTo", "error", err)
		return
	}
	// Do I need to complete the relays now?
	if relay.Type == TerminalType {
		return
	}
	// I'm the middle man. Let the initiator know that the I've established the relay they requested.
	peerHostInfo := rm.hostmap.QueryVpnAddr(relay.PeerAddr)
	if peerHostInfo == nil {
		rm.l.Error("Can't find a HostInfo for peer", "relayTo", relay.PeerAddr)
		return
	}
	peerRelay, ok := peerHostInfo.relayState.QueryRelayForByIp(relayTo)
	if !ok {
		rm.l.Error("peerRelay does not have Relay state for relayTo", "relayTo", peerHostInfo.vpnAddrs[0])
		return
	}
	switch peerRelay.State {
	case Requested:
		// I initiated the request to this peer, but haven't heard back from the peer yet. I must wait for this peer
		// to respond to complete the connection.
	case PeerRequested, Disestablished, Established:
		peerHostInfo.relayState.UpdateRelayForByIpState(relayTo, Established)
		resp := NebulaControl{
			Type:                NebulaControl_CreateRelayResponse,
			ResponderRelayIndex: peerRelay.LocalIndex,
			InitiatorRelayIndex: peerRelay.RemoteIndex,
		}

		peer := peerHostInfo.vpnAddrs[0]
		if v == cert.Version1 {
			if !peer.Is4() {
				rm.l.Error("Refusing to CreateRelayResponse for a v1 relay with an ipv6 address",
					"relayFrom", peer,
					"relayTo", relayTo,
					"initiatorRelayIndex", resp.InitiatorRelayIndex,
					"responderRelayIndex", resp.ResponderRelayIndex,
					"vpnAddrs", peerHostInfo.vpnAddrs,
				)
				return
			}

			b := peer.As4()
			resp.OldRelayFromAddr = binary.BigEndian.Uint32(b[:])
			b = relayTo.As4()
			resp.OldRelayToAddr = binary.BigEndian.Uint32(b[:])
		} else {
			resp.RelayFromAddr = netAddrToProtoAddr(peer)
			resp.RelayToAddr = m.RelayToAddr
		}

		msg, err := resp.Marshal()
		if err != nil {
			rm.l.Error("relayManager Failed to marshal Control CreateRelayResponse message to create relay", "error", err)
			return
		}
		f.SendMessageToHostInfo(header.Control, 0, peerHostInfo, msg, make([]byte, 12), make([]byte, mtu))
		rm.l.Info("send CreateRelayResponse",
			"relayFrom", peer,
			"relayTo", relayTo,
			"initiatorRelayIndex", resp.InitiatorRelayIndex,
			"responderRelayIndex", resp.ResponderRelayIndex,
			"vpnAddrs", peerHostInfo.vpnAddrs,
		)
	}
}
