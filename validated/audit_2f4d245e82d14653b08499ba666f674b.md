### Title
Unauthorized griefing of a deterministic MarginfiAccount PDA slot via `transfer_to_new_account_pda`'s unchecked `new_authority` - (File: `programs/marginfi/src/instructions/marginfi_account/transfer_account.rs`)

### Summary
The `TransferToNewAccountPda` instruction lets any existing marginfi account authority migrate their account into a brand-new PDA account whose seeds are derived from an arbitrary, attacker-supplied `new_authority` pubkey, an `account_index`, and an optional `third_party_id` — with **no signature or consent from `new_authority` required**. This mirrors the reported "delegate assignment front-running" bug class: an unrelated actor can pre-empt/claim a specific identity's canonical deterministic slot before the legitimate owner ever uses it, and once `init`-ed that PDA can never be re-created at that address.

### Finding Description
`TransferToNewAccountPda` only requires the *old* account's `authority` to sign; `new_authority` is explicitly documented as unchecked: [1](#0-0) 

The new account address is a PDA deterministically derived from `(group, new_authority, account_index, third_party_id)`: [2](#0-1) 

Anyone holding (or willing to create) a throwaway `MarginfiAccount` can call `transfer_to_new_account_pda` and set `new_authority` to any target pubkey (e.g., a well-known multisig, an integrator's canonical vault address, or a specific `account_index`/`third_party_id` combination reserved by a third-party protocol). Because `new_marginfi_account` uses Anchor's `init` constraint, the PDA can only ever be initialized once: [3](#0-2) 

The only replay protection is on the *source* account (`old_account.migrated_to == Pubkey::default()`), not on whether the target `new_authority`/index slot has already been claimed by someone else: [4](#0-3) 

The migrated account additionally copies the old account's `lending_account` (its asset/liability shares), `account_flags`, and `indexer_flags` into the newly created PDA under the victim's authority, without the victim's consent: [5](#0-4) 

This is directly analogous to the reported delegateKey front-running: an unprivileged actor can seize a specific deterministic identity/slot that a legitimate party intends to use, before that party ever transacts, and there is no mechanism for the target to approve, reject, or reclaim/reset that specific slot once occupied — the same "no acceptance/cancellation" gap called out in the original report and its recommendation to let the delegate "approve or cancel."

### Impact Explanation
- **Slot griefing / DoS on a specific `account_index`/`third_party_id`**: Third-party integrators that rely on deterministic derivation of `MarginfiAccount::derive_pda(group, authority, account_index, third_party_id)` (as documented directly in `lib.rs`'s comment on `transfer_to_new_account_pda`, describing `account_index` as a fixed convention for per-authority accounts) can have their canonical slot(s) permanently pre-occupied by an attacker before the integrator ever initializes it, since the PDA can only be `init`-ed once. [6](#0-5) 
- **Unwanted state injected under the victim's authority**: the pre-empted account is seeded with the attacker's old `lending_account` (asset/liability shares) and flags, meaning a victim can be handed an account carrying unexpected liabilities/positions or flags (e.g. `ACCOUNT_DISABLED`-adjacent state) they never consented to.
- This does not directly drain victim funds elsewhere (the victim's other accounts/positions are untouched), so it is a permanent-lock/denial-of-service and unauthorized-state-change issue on a specific deterministic slot rather than a direct theft — consistent with the "Won't Fix"/low-severity classification given to the analogous delegateKey report, but still a concrete unauthorized state change worth documenting.

### Likelihood Explanation
Likelihood is low-to-moderate: exploitation requires the attacker to know in advance which `account_index`/`third_party_id` value a specific target intends to use (this is realistic for third-party integrators, who typically use `account_index = 0` or protocol-documented fixed indices), and requires only a cheap throwaway `MarginfiAccount` plus payment of the flat `ACCOUNT_TRANSFER_FEE`. No special privileges are needed — any wallet can trigger this via `transfer_to_new_account_pda`. [7](#0-6) 

### Recommendation
- Require `new_authority` to co-sign (or provide a claim/accept step) before a PDA account can be initialized under their pubkey via migration, analogous to the report's recommendation to let the delegate approve/cancel the assignment.
- Alternatively, restrict `transfer_to_new_account_pda` so `new_authority` must equal the calling `authority` (self-migration) or require an explicit opt-in signature from the target authority for third-party reassignment.
- Consider a commit-reveal or two-step "propose new authority / accept" pattern for both `TransferToNewAccount` and `TransferToNewAccountPda`, consistent with the mitigation suggested for the delegateKey issue.

### Proof of Concept
1. Attacker creates a disposable `MarginfiAccount` (`MarginfiAccountInitialize`) and optionally deposits/borrows a small amount to populate `lending_account`.
2. Attacker computes the PDA for `(group, victim_pubkey, account_index=0, third_party_id=None)` via `MarginfiAccount::derive_pda`. [8](#0-7) 
3. Attacker calls `transfer_to_new_account_pda` with `authority = attacker`, `new_authority = victim_pubkey`, `account_index = 0`, paying `ACCOUNT_TRANSFER_FEE`; no signature from `victim_pubkey` is required. [9](#0-8) 
4. The PDA at `(group, victim_pubkey, 0, None)` is now permanently initialized with the attacker's migrated `lending_account`/flags, and `AccountAlreadyMigrated`/PDA-already-exists errors prevent the victim (or the protocol) from ever re-deriving a fresh canonical account at that same index for that authority. [10](#0-9)

}

    ctx: Context<TransferToNewAccountPda>,
