### Title
Unbounded per-request memory buffering of HTTP API responses in `ServletOutputStreamCopy` - ([File: framework/src/main/java/org/tron/core/services/filter/ServletOutputStreamCopy.java])

### Summary
Every HTTP request served by the full node's Wallet HTTP API (and the solidity/PBFT HTTP variants) is wrapped by `HttpApiAccessFilter` and `HttpInterceptor`, both of which construct a `CharResponseWrapper` that internally uses `ServletOutputStreamCopy` to duplicate the entire response body into an in-memory `ByteArrayOutputStream` for logging/metrics purposes, with no upper bound enforced on its growth [1](#0-0) [2](#0-1) .

### Finding Description
`ServletOutputStreamCopy` declares a field named `MAX_RESPONSE_SIZE = 4096`, but this value is used only as the *initial capacity* of the backing `ByteArrayOutputStream`, never as an actual cap enforced during `write()`: [3](#0-2) 
Every byte written to the real servlet output stream is unconditionally also appended to `copy`, so for any response body larger than the initial 4KB capacity, the `ByteArrayOutputStream` grows and reallocates without limit, exactly mirroring the CVE's "no high-water mark to stop buffering" bug class in `asyncio._SelectorSocketTransport.writelines()`. `CharResponseWrapper` exposes this stream via `getOutputStream()`/`getWriter()`, and only reads its accumulated size after the whole response is flushed [4](#0-3) .

This wrapper is applied globally by two separate servlet filters — `HttpApiAccessFilter` [5](#0-4)  and `HttpInterceptor` [6](#0-5)  — both registered on `FullNodeHttpApiService` (and similarly on the solidity/PBFT HTTP services), meaning every incoming HTTP API request, including anonymous read-only wallet query endpoints, is subject to this double-buffering behavior. Unlike `BufferedResponseWrapper` used in `JsonRpcServlet`, which enforces a configurable `maxBytes` and sets an `overflow` flag to stop buffering [7](#0-6) , `ServletOutputStreamCopy` has no such mechanism despite its misleadingly-named `MAX_RESPONSE_SIZE` field.

### Impact Explanation
An anonymous API client can request any HTTP Wallet endpoint that returns a large response body (e.g., large block ranges, contract listings, or other bulk query endpoints on the full node's HTTP API). For each such request, the node holds two full copies of the response in memory simultaneously (the servlet's own output buffer plus the unbounded `copy` ByteArrayOutputStream) for the duration of the request, and `ByteArrayOutputStream`'s doubling-growth reallocation strategy adds further transient memory pressure. Repeated or concurrent requests targeting large-response endpoints can drive memory exhaustion, leading to increased GC pressure, OOM, or a node crash — a denial-of-service against the node's ability to serve its HTTP/API query paths.

### Likelihood Explanation
High: this code path is unconditionally triggered on every HTTP request to the full node's public Wallet HTTP API by two globally-registered filters, requires no special privileges, no authentication, and no crafted payload beyond causing a large response to be generated (which is achievable via ordinary parameterized read endpoints).

### Recommendation
Enforce a configurable maximum size in `ServletOutputStreamCopy.write()` (mirroring `BufferedResponseWrapper`'s `maxBytes`/`overflow` pattern), discarding or truncating the copy once the limit is exceeded instead of continuing to buffer, and stop naming the field `MAX_RESPONSE_SIZE` if it is not actually enforced as a limit.

### Proof of Concept
1. Start a full node with the HTTP API enabled (default `HttpApiAccessFilter`/`HttpInterceptor` filter chain active).
2. From an unauthenticated client, repeatedly call a Wallet HTTP endpoint known to return a large JSON payload (e.g., queries returning long lists of transactions/blocks/accounts).
3. Observe that for each such request, `ServletOutputStreamCopy.copy` (a `ByteArrayOutputStream`) grows to match the full response size with no truncation, and that concurrent large requests linearly multiply memory usage, eventually causing OOM or severe GC pauses — verifiable via heap profiling while sending a moderate number of concurrent large-response requests.

  private OutputStream outputStream;
  private ByteArrayOutputStream copy;
  private int MAX_RESPONSE_SIZE = 4096;

  public ServletOutputStreamCopy(OutputStream outputStream) {
    this.outputStream = outputStream;
    this.copy = new ByteArrayOutputStream(MAX_RESPONSE_SIZE);
  }

  @Override
  public void write(int b) throws IOException {
    outputStream.write(b);
    copy.write(b);
  }

  public int getStreamByteSize() {
    return this.copy.size();
  }
