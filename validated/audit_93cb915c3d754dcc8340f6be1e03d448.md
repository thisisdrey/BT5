### Title
`remove_account` fails to delete receipt/promise-yield trie keys (ReceivedData, PostponedReceipt, PostponedReceiptId, PendingDataCount, PromiseYieldReceipt, PromiseYieldStatus, YieldIdToDataId, DataIdToYieldId) on `DeleteAccountAction`, allowing stale receipts to execute against a resurrected account - ([File: core/store/src/utils/mod.rs])

### Summary
`remove_account` only deletes `TrieKey::Account`, `TrieKey::ContractCode`, `TrieKey::AccessKey`/`GasKeyNonce`, and `TrieKey::ContractData` for the deleted `AccountId`, leaving all other account-scoped trie key families untouched. Because these leftover keys (`ReceivedData`, `PostponedReceipt`, `PostponedReceiptId`, `PendingDataCount`, and the `PromiseYield*` family) are addressed purely by `AccountId` plus a receipt/data id, a subsequently recreated account with the same `AccountId` inherits this stale state, and a late-arriving `DataReceipt` can trigger execution of a receipt that was postponed before the account was deleted.

### Finding Description
`remove_account` (`core/store/src/utils/mod.rs:504-575`) removes the account record, code, access/gas keys, and contract data: [1](#0-0) [2](#0-1) 

It never iterates or removes `TrieKey::ReceivedData`, `TrieKey::PostponedReceipt`, `TrieKey::PostponedReceiptId`, `TrieKey::PendingDataCount`, or the promise-yield equivalents, all of which are defined in `core/primitives/src/trie_key.rs` and keyed by `receiver_id`/`account_id`: [3](#0-2) 

`action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) calls `remove_account` directly and gates deletion only on `Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE` (derived from `account.storage_usage()`, which tracks contract state, not receipt-processing metadata) and on gas-key balance: [4](#0-3) [5](#0-4) 

None of these checks account for outstanding `PostponedReceipt`/`PendingDataCount`/`ReceivedData` entries, so an account with a receipt awaiting a still-missing `DataReceipt` can still be deleted.

Exploit flow for an unprivileged attacker who controls account `victim.near` (a sub-account they created, so it can be recreated later):
1. From `victim.near`, submit a `FunctionCall` receipt with `input_data_ids` referencing a promise whose resolving `DataReceipt` will arrive later (e.g., a cross-contract call chain). Runtime stores `PostponedReceiptId`, `PendingDataCount`, and `PostponedReceipt` under `victim.near` (`runtime/runtime/src/lib.rs:1593-1658`, `process_action_receipt`): [6](#0-5) 
2. Before the pending `DataReceipt` arrives, submit `DeleteAccountAction` for `victim.near`. `action_delete_account`/`remove_account` deletes the account but leaves the `PostponedReceiptId`/`PendingDataCount`/`PostponedReceipt` entries in the trie.
3. Recreate `victim.near` (e.g., as a fresh sub-account with new keys/contract).
4. When the originally-triggered `DataReceipt` eventually arrives at `victim.near`, `process_receipt`'s Data arm (`runtime/runtime/src/lib.rs:1386-1455`) finds the stale `PostponedReceiptId`, decrements `PendingDataCount`, and — once it hits zero — fetches and executes the old `PostponedReceipt` via `apply_action_receipt`, now against the **new** account's account/contract/key state: [7](#0-6) 

This lets a receipt authorized/created for the old (deleted) account identity execute unexpectedly against the newly created account, i.e., cross-identity execution not authorized by the new account owner — an authorization-escalation-across-accounts/promises scenario. Existing checks (signature, nonce, access-key permission, `DeleteAccountWithLargeState`, gas-key balance limit) do not examine or block this because they only look at the `Account` record and contract-code storage usage, not the receipt-processing columns.

### Impact Explanation
Concrete, reachable impact: an attacker-controlled account can leave dangling promise/receipt state that is not tied to the account's lifetime, causing a resurrected account (same `AccountId`) to have a previously-issued receipt silently execute against it once a delayed `DataReceipt` shows up. This matches the "authorization escalation across accounts or promises" bounty category, since execution attributed to `receiver_id = victim.near` runs under whatever state/contract/keys the *new* occupant of that `AccountId` has, without the new account's involvement or consent. It is also a genuine, reachable storage-hygiene bug (dangling trie entries that a normal delete-then-recreate flow cannot ever clear), independent of whether every instance is weaponizable for fund theft in a given contract.

### Likelihood Explanation
Preconditions: attacker needs only a self-owned sub-account, the ability to issue a self-receiving cross-contract call with an unresolved data dependency (`input_data_ids`), and the ability to submit `DeleteAccountAction` before that dependency resolves, then recreate the same `AccountId`. All of this is achievable by an ordinary funded account with no special privileges, and the race window (delete before the async promise's `DataReceipt` returns) is fully attacker-controlled since they choose when to submit the delete and can engineer arbitrarily long delays in the callback chain (e.g., yield/resume). The bug is deterministic and repeatable once the timing precondition is met.

### Recommendation
Extend `remove_account` (`core/store/src/utils/mod.rs`) to prefix-iterate and remove all account/receiver-scoped trie key families before deletion completes: `ReceivedData`, `PostponedReceipt`, `PostponedReceiptId`, `PendingDataCount`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, and `DataIdToYieldId`, mirroring the existing access-key prefix-iteration pattern. Alternatively/additionally, block `DeleteAccountAction` when any `PostponedReceipt`/`PendingDataCount` entries exist for the account (analogous to the existing staking-lock and large-state checks), since silently discarding in-flight receipt state is unsafe regardless of cleanup completeness.

### Proof of Concept
Table-driven Rust unit test in `runtime/runtime/src/utils/mod.rs` (or a new test module colocated with `remove_account`):
1. For each of the 12 `col::COLUMNS_WITH_ACCOUNT_ID_IN_KEY` trie key variants, construct one canonical instance for `account_id = "victim.near"` (using existing `set_*` helpers such as `set_account`, `set_access_key`, `set_received_data`, `set_postponed_receipt`, and equivalents for `PendingDataCount`, `PostponedReceiptId`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, `DataIdToYieldId`) and write it into a `TrieUpdate`.
2. Commit/finalize the state so all 12 rows exist in the trie.
3. Call `remove_account(&mut state_update, &account_id)`.
4. Assert via `TrieUpdate::contains_key` (or `TrieAccess::contains_key`) that `Account`, `ContractCode`, `AccessKey`, and `ContractData` are gone, while `ReceivedData`, `PostponedReceipt`, `PostponedReceiptId`, `PendingDataCount`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, `DataIdToYieldId` all still return `true` (present) — confirming 8 of 12 columns survive.
5. Integration-level PoC (in `runtime/runtime/src/tests/apply.rs`, alongside `test_function_call_after_same_chunk_delete_recreate_resolves_fresh_code`): create `child.alice.near`, issue a self-targeted `ActionReceipt` with an unresolved `input_data_ids` entry (so `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` are written), then `DeleteAccount` the child, recreate `child.alice.near` with a fresh contract/keys, then deliver the original pending `DataReceipt`; assert that the old postponed `ActionReceipt`'s actions execute against the new account (e.g., observe unexpected state/balance change on the recreated account attributable to the stale receipt).
