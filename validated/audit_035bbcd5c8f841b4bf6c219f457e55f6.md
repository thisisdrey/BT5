Based on my investigation, I found a concrete analog in the TVM precompiled-contract data-decoding helpers.

### Title
Unbounded array-length read from attacker-controlled call data causes OutOfMemoryError/DoS in TVM precompiled contracts - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
CVE-2014-9771 is an integer-overflow bug where a crafted image header length field is used to allocate/read a buffer without validating it against the actual remaining data, causing excessive memory consumption or an invalid read. `PrecompiledContracts.java` contains the same bug-class pattern: several helper methods decode an attacker-supplied 32-byte "length" word from the raw call-data of a contract call and immediately use it to size a Java array, without checking it against the real size of the remaining input.

### Finding Description
`extractBytes32Array`, `extractBytesArray`, and `extractSigArray` each read `len = words[offset].intValueSafe()` directly from caller-controlled `DataWord[] words` (parsed from raw TVM call data) and then allocate `new byte[len][]` before validating that `len` is consistent with the actual amount of data present: [1](#0-0) 

`extractBytesArray` only guards against `offset` being out of bounds, not against `len` itself being arbitrarily large (up to `Integer.MAX_VALUE`, since `intValueSafe()` clamps a 256-bit word to a 32-bit int) — the loop bound is `len`, not the actual size of `words`, so a crafted `len` allocates a huge array on the heap before the loop even hits an out-of-bounds access: [2](#0-1) 
`extractBytes32Array` has no upper-bound check at all: `byte[len][]` is allocated purely from the attacker word. [3](#0-2) 

This mirrors the imlib2 root cause: a length value taken from untrusted input is used to size a memory allocation/read before being validated against the real bounds of the available data, which is exactly the "invalid read"/"memory consumption" class described in the advisory.

### Impact Explanation
A single crafted contract call (an ordinary TVM transaction, no special privileges required) that reaches one of the precompiled contracts using these helpers can force a multi-gigabyte `byte[][]` allocation attempt. This either throws `OutOfMemoryError` (potentially destabilizing the JVM/node process handling the transaction — since `OutOfMemoryError` can leave the JVM in an inconsistent state and is not reliably recoverable) or a `NegativeArraySizeException` if the intValueSafe overflow yields a negative int, both of which are uncaught runtime errors in this code path. This matches the "node crash or halt" acceptance criterion for a High severity issue.

### Likelihood Explanation
I was not able to confirm within the indexed code which specific precompiled contract's `execute(byte[] data)` invokes `extractBytesArray`/`extractBytes32Array`/`extractSigArray` (the index did not return direct call sites for these methods, likely due to size limits on the codebase index). Because I could not directly verify the reachability chain from a specific opcode/precompile address to these helpers, I cannot fully confirm this is triggerable by an ordinary unprivileged transaction without further verification of the call sites and whether `getEnergyForData` is computed (and would fail/limit energy) before `execute` is invoked with the same unbounded length.

### Recommendation
Add an explicit upper bound (and a check against the real remaining length of `data`/`words`) before allocating `bytes32Array`/`bytesArray`/`bytesArray` in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray`, similar to the pattern already used in `isValidAbiEncoding` and `ModExp.execute`'s `UPPER_BOUND` checks elsewhere in the same file: [4](#0-3)
