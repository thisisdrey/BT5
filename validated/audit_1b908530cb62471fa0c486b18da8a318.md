### Title
Race Between CountDownLatch Timeout and Orphaned Worker Tasks in `BatchValidateSign` Precompile Leads to Shared Thread-Pool Exhaustion / Node DoS - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `BatchValidateSign` TVM precompiled contract submits signature-recovery tasks to a single, node-wide, fixed-size static `ExecutorService` and races a `CountDownLatch.await()` against the transaction's remaining CPU-time budget. On timeout it throws and returns to the caller, but never cancels the already-submitted `Future`s. Because the executor is static and shared by every concurrent TVM invocation on the node (both block-application and constant calls), an unprivileged contract deployer/caller can repeatedly trigger timeouts while leaving orphaned tasks queued/running, degrading or exhausting the shared pool — the same class of bug as CVE-2020-5967 (a race condition between a driver's wait/cancel path and outstanding work causing denial of service).

### Finding Description
`BatchValidateSign.doExecute()` builds a `CountDownLatch` sized to the number of signatures, submits one `RecoverAddrTask` per signature to the static `workers` pool, and waits only `getCPUTimeLeftInNanoSecond()`: [1](#0-0) 

The pool itself is a small, fixed-size, **static** executor shared by all VM executions across the whole node (both consensus/block-application threads and RPC/constant-call threads): [2](#0-1) 

If the latch does not fire before the CPU-time budget expires, the method throws `Program.Exception.notEnoughTime(...)` and returns control to `VMActuator`/`Program`, unwinding the transaction — but the `Future` objects created in the loop are never cancelled: [3](#0-2) 

Each `RecoverAddrTask` still runs to completion inside the shared pool regardless of whether its owning transaction has already aborted, since only `countDownLatch.countDown()` runs in the `finally` block and nothing checks whether the parent invocation is still interested in the result: [4](#0-3) 

Because the pool size is fixed at `availableProcessors()/2 + 1` and is never scaled with load, an attacker who repeatedly submits `TriggerSmartContract` calls into `BatchValidateSign` with the maximum allowed `MAX_SIZE = 16` signatures (crafted so ECDSA recovery/verification is comparatively expensive, e.g. malformed/edge-case signature bytes) can race many concurrent transactions against this same static pool. Every submission adds up to 16 tasks to the pool's queue; every timeout on the caller side is not paired with cancellation, so the backlog of running/queued `RecoverAddrTask`s keeps growing across concurrently-processed transactions rather than being bounded by any one transaction's own CPU/energy budget. Since the pool is shared globally, this also affects unrelated transactions and blocks that legitimately call the same precompile, once the queue backs up.

### Impact Explanation
This is directly reachable by any unprivileged transaction broadcaster or contract deployer through the standard `TriggerSmartContract`/`CreateSmartContract` path invoking a precompiled contract (`BatchValidateSign`) at TVM execution time — no special privileges are required. Sustained abuse saturates a single node-wide static thread pool used by every contract call to this precompile (during block application and JSON-RPC/gRPC constant calls alike), degrading transaction processing throughput and risking a denial of service on the affected node(s). Because task completion is not tied to the aborted transaction's lifecycle, resource usage is effectively decoupled from the per-transaction CPU/energy accounting the TVM otherwise enforces, undermining the very CPU-time guard the code tries to implement.

### Likelihood Explanation
Any account can deploy or call a contract that invokes the `BatchValidateSign` precompile with the maximum signature array size and can be repeated at will via ordinary broadcast transactions, so the trigger requires no special role, timing, or witness/committee cooperation — only crafting inputs and submitting transactions at volume, which is within reach of a single unprivileged actor.

### Recommendation
- Cancel all outstanding `Future`s (`future.cancel(true)`) for the current `BatchValidateSign` invocation as soon as the latch times out, and/or track submitted-but-unfinished task counts against a bound so a timed-out caller's tasks cannot continue consuming shared pool capacity.
- Consider sizing/bounding the `workers` queue (e.g., a bounded queue with rejection) so a burst of BatchValidateSign calls cannot build an unbounded backlog on the static pool, and/or make the executor per-invocation-bounded rather than a single global static pool shared by all VM executions.
- Ensure `RecoverAddrTask` checks a cancellation/abort flag before doing the (comparatively expensive) signature recovery work, so cancelled tasks short-circuit instead of always running to completion.

### Proof of Concept
1. Deploy a contract that calls the `BatchValidateSign` precompiled address with the ABI-encoded maximum `MAX_SIZE = 16` signatures and addresses, using signature bytes crafted so `recoverAddrBySign` runs near the CPU-time budget for each call.
2. Broadcast a burst of such transactions concurrently (each an independent `TriggerSmartContract`), so many `doExecute` calls run in parallel against the single static `workers` pool declared at `PrecompiledContracts.java:1125`.
3. Each call races `countDownLatch.await(getCPUTimeLeftInNanoSecond(), ...)`; a fraction will exceed the per-tx CPU budget and throw `notEnoughTime`, but as shown at `PrecompiledContracts.java:1201-1207`, the corresponding `Future`s are never cancelled, so their `RecoverAddrTask`s (lines 1220-1236) keep running in the shared pool.
4. Repeating step 2 at sufficient rate accumulates unresolved/queued tasks in the fixed-size shared pool faster than they can retire, observable as growing latency/timeout rate for subsequent `BatchValidateSign` calls made by unrelated, legitimate transactions and by block application on the same node.
