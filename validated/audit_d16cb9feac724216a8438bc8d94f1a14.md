## Finding Assessment

Based on the code I examined in [1](#0-0) , the described exploit path is plausible and traceable to a real gap in the code, though the root cause is broader than just the `check_storage_stake` boundary — it applies to any multi-action receipt where a later action fails after an earlier action produced outgoing receipts.

### Title
Outgoing receipts generated by an earlier successful action in a receipt are forwarded to `receipt_sink` even when a later action (or the final `check_storage_stake`) fails the whole receipt and `state_update.rollback()` reverts all account/state changes - (File: runtime/runtime/src/lib.rs)

### Summary
`apply_action_receipt` executes all actions of a receipt in a loop, merging each action's result (including any `new_receipts` it produced) into a single `ActionReceiptResult`. After the loop, `check_storage_stake` is evaluated once and can flip an otherwise-successful `result.result` to `Err`, and `state_update.rollback()` is called to discard uncommitted trie writes. However, `result.new_receipts` is a plain Rust `Vec` independent of `TrieUpdate`, and the code that turns `result.new_receipts` into outgoing receipts via `receipt_sink.forward_or_buffer_receipt` runs unconditionally later in the function, with no gate on `result.result.is_ok()`.

### Finding Description
The action loop merges each action's outcome, including generated receipts, unconditionally as long as no error occurred yet: [2](#0-1) . If action 1 (a `FunctionCall` that issues a cross-contract `Transfer` promise) succeeds, its resulting receipt is merged into `result.new_receipts`. If action 2 (`AddKey`) succeeds at the per-action level but subsequently causes `check_storage_stake` to fail after the loop, `result.result` is set to `Err(ActionErrorKind::LackBalanceForState)`: [3](#0-2) .

Based on that `Err`, `state_update.rollback()` is invoked: [4](#0-3) . But `TrieUpdate::rollback` only clears the `prospective` BTreeMap of pending trie key/value writes and rolls back pending contract deploys — it has no knowledge of, and no effect on, `result.new_receipts`: [5](#0-4) .

Further down, the code that assigns receipt IDs and forwards `result.new_receipts` into `receipt_sink.forward_or_buffer_receipt` executes unconditionally, without any check on whether `result.result` is `Ok` or `Err`: [6](#0-5) . This means the `Transfer` receipt created by action 1 is still handed to `receipt_sink` for forwarding to the destination shard, even though the balance deduction associated with creating that promise (which lives in `state_update`'s prospective changes) was just rolled back by `state_update.rollback()` because of the unrelated failure in action 2.

### Impact Explanation
If confirmed end-to-end (see caveat below), this is a **double-spend / token-inflation** bug: the sending shard forwards a receipt representing a transfer of value to another account/shard, but never actually commits the corresponding debit to the sender's balance, because the whole receipt (including the debit) was rolled back due to an unrelated, later failure (e.g. the storage-stake check on an `AddKey` action). The receiving shard would still credit the transferred amount, creating tokens out of nothing / breaking value conservation across shards.

### Likelihood Explanation
I was not able to fully verify, within the remaining tool budget, whether `apply_action`'s handling of `FunctionCall` promises actually leaves already-generated receipts in `new_result.new_receipts` when the *overall* enclosing receipt fails due to a later, unrelated action (as opposed to the FunctionCall action itself failing, which is a case I did confirm is typically discarded inside VM outcome handling). I found no code in the range read (`runtime/runtime/src/lib.rs` lines 891-1200) that clears or filters `result.new_receipts` when `result.result` becomes `Err`, but I could not trace `ActionResult::merge`, the exact semantics of promise-receipt cancellation on receipt failure inside `apply_action` for `FunctionCall`, or historical test coverage that might already assert atomicity here (e.g., "receipt failure discards created receipts" is a widely-expected NEAR invariant, and it's possible this is enforced elsewhere, e.g. inside the VM logic for `FunctionCall` rather than at the `apply_action_receipt` level, in a way I did not inspect).

Given this uncertainty, and because the specific 770/771-byte zero-balance boundary crafting described in the question is not actually necessary to the underlying mechanism (any multi-action receipt with an action failing after an earlier action emits a receipt would trigger the same code path, if the gap is real), I cannot confirm this as a validated, reproducible finding without further tracing of `ActionResult::merge` and the `FunctionCall` VM-outcome-to-receipt conversion path, which was outside my remaining tool budget.

### Recommendation
If the gap is confirmed by tracing `ActionResult::merge` and the FunctionCall promise-generation code, the fix would be to only forward `result.new_receipts` to `receipt_sink` when `result.result.is_ok()`, or to clear `result.new_receipts` whenever the receipt's overall status becomes `Err` (mirroring what `state_update.rollback()` does for trie state) before reaching the receipt-forwarding code at `runtime/runtime/src/lib.rs:1139-1184`.

### Proof of Concept
A unit/integration test would need to:
1. Deploy a contract that in one `FunctionCall` action creates a promise-based `Transfer` receipt to another account.
2. In the same `ActionReceipt`, add a subsequent `AddKey` action that pushes the account's `storage_usage` just past `check_storage_stake`'s threshold with `amount() == 0` (zero-balance account boundary).
3. Call `apply_action_receipt` directly (as in `runtime/runtime/src/tests/apply.rs`) and assert that when `result.result` is `Err(LackBalanceForState)`, `result.new_receipts` is empty (or that no receipt reaches `receipt_sink`'s outgoing buffer) — i.e., that no `Transfer` receipt is forwarded despite the enclosing receipt failing. [7](#0-6) 

**Given the unresolved uncertainty about whether `ActionResult::merge`/FunctionCall promise handling already prevents this at a different layer, I cannot issue a final confirmed vulnerability verdict — this requires further tracing of `ActionResult::merge` and the FunctionCall-to-receipt conversion path that was not completed due to tool-call exhaustion.**
