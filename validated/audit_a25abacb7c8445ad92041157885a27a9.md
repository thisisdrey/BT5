### Title
`WalletContract::rlp_execute` swallows attached NEAR deposit when a transaction is already in flight - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`rlp_execute` is a `#[payable]` entry point on the eth-implicit wallet contract, meaning any predecessor can attach a NEAR deposit to the call. If `self.has_in_flight_tx` is already `true`, the function returns an error response immediately, before `env::attached_deposit()` is ever read or before a `CallerDeposit` refund record is created. The attached NEAR is neither used nor refunded — it is permanently absorbed into the wallet contract's balance, mirroring the Alchemix `RewardsDistributor.claim()` bug where an early return bypasses deposit accounting.

### Finding Description
`rlp_execute` is marked `#[payable]` and is the sole entry point for relayers/callers to submit an Ethereum-style transaction to the wallet contract: [1](#0-0) 

The very first check in the function is a guard against concurrent execution:
```rust
if self.has_in_flight_tx {
    return PromiseOrValue::Value(ExecuteResponse {
        success: false,
        success_value: None,
        error: Some("Error: transaction already in progress, please try again later.".into()),
    });
}
```
This early `return` happens unconditionally before `env::attached_deposit()` is read, and before `inner_rlp_execute` is even called. Only inside `inner_rlp_execute` is `ExecutionContext::new(..., env::attached_deposit())` invoked and `CallerDeposit::new(&context)` constructed to later refund the deposit if the downstream promise fails: [2](#0-1) 

The `CallerDeposit` mechanism exists specifically to guarantee any externally-attached NEAR deposit is refunded if the resulting cross-contract call fails: [3](#0-2) 
and is redeemed in `rlp_execute_callback` only on the failure path: [4](#0-3) 

Because the `has_in_flight_tx` early return in `rlp_execute` bypasses `ExecutionContext::new`/`CallerDeposit::new` entirely, any deposit attached to a call that arrives while another transaction is in flight is not tracked and never refunded by any code path — it simply becomes part of the contract account's balance. There is no `require(attached_deposit == 0)` guard analogous to the fix recommended in the original report.

### Impact Explanation
This is a genuine "permanent freezing of funds" for an ordinary, unprivileged caller: any account (a relayer or the wallet owner submitting through a relayer) that attaches NEAR to an `rlp_execute` call while a previous transaction from the same wallet is still in flight will have that NEAR silently and permanently absorbed by the wallet contract, with no mechanism to reclaim it. Given `has_in_flight_tx` is deliberately used to serialize execution (only one transaction may be in flight per wallet at a time, as documented in the struct comment and exercised by `test_simultaneous_transactions`), concurrent or rapid submissions are a realistically reachable, non-adversarial scenario (e.g., a relayer retries a call before the prior one resolves), not requiring a malicious actor. [5](#0-4) 

### Likelihood Explanation
Moderate/low, similar to the original report: it requires a caller to attach a non-zero deposit to `rlp_execute` while another transaction from the same wallet is already in flight (e.g. due to a retried or duplicated relayer submission, or two legitimate transactions racing). `test_simultaneous_transactions` in the test suite demonstrates this exact race is reachable via a single batched transaction, confirming the scenario is not purely theoretical. [6](#0-5) 

### Recommendation
In `rlp_execute`, before or as part of the `has_in_flight_tx` early-return branch, check `env::attached_deposit()`. If it is non-zero, either reject the call by requiring a zero deposit, or issue an immediate refund `Promise` transferring the attached deposit back to `env::predecessor_account_id()` before returning the failure response, so that no NEAR is ever silently absorbed by the "transaction already in progress" path.

### Proof of Concept
Conceptual reproduction based on the existing `test_simultaneous_transactions` harness:
1. Attach a nonzero deposit to two `rlp_execute` calls batched together (or sent back-to-back before the first resolves), targeting the same wallet contract instance, as done in `test_simultaneous_transactions`. [7](#0-6) 
2. The second call observes `self.has_in_flight_tx == true` and returns immediately at the guard clause, without reading or refunding `env::attached_deposit()`. [8](#0-7) 
3. Compare the wallet contract's balance before/after: the attached deposit from the rejected call remains in the contract with no corresponding refund receipt generated, unlike the failure path handled by `CallerDeposit`/`rlp_execute_callback`, which only refunds deposits recorded via the non-early-return path. [4](#0-3)

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}

/// Only one transaction can be in flight at a time.
#[tokio::test]
async fn test_simultaneous_transactions() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, .. } = TestContext::new().await?;

    let receiver_account = worker.root_account().unwrap();

    let initial_receiver_balance = receiver_account.view_account().await.unwrap().balance;

    let receiver_id = receiver_account.id().as_str().into();
    let action = Action::Transfer { receiver_id, yocto_near: 1 };
    let signed_transaction =
        utils::create_signed_transaction(0, receiver_account.id(), Wei::zero(), action, &wallet_sk);
    let wallet_method_call_1 = near_workspaces::operations::Function::new("rlp_execute")
        .args_json(serde_json::json!({
            "target": receiver_account.id(),
            "tx_bytes_b64": codec::encode_b64(&codec::rlp_encode(&signed_transaction))
        }))
        .gas(near_workspaces::types::Gas::from_tgas(100));
    let wallet_method_call_2 = near_workspaces::operations::Function::new("rlp_execute")
        .args_json(serde_json::json!({
            "target": receiver_account.id(),
            "tx_bytes_b64": codec::encode_b64(&codec::rlp_encode(&signed_transaction))
        }))
        .gas(near_workspaces::types::Gas::from_tgas(100));

    let near_transaction = wallet_contract
        .inner
        .as_account()
        .batch(wallet_contract.inner.id())
        .call(wallet_method_call_1)
        .call(wallet_method_call_2)
        .transact()
        .await?;

    let result: ExecuteResponse = near_transaction.json()?;

    // The second transaction in the batch fails and this is returned as the
    // result of the Near transaction. But the first transaction in the batch
    // spawns promises that resolve, so the transfer was will successful.
    assert!(!result.success);
    assert!(result.error.unwrap().contains("transaction already in progress"));

    let final_receiver_balance = receiver_account.view_account().await.unwrap().balance;
    assert_eq!(final_receiver_balance.as_yoctonear() - initial_receiver_balance.as_yoctonear(), 1,);

    Ok(())
}
