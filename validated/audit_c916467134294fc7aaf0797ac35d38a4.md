### Title
Half-open QUIC handshake flood bypasses both per-IP and global connection rate limiters, exhausting TPU accept-loop capacity - ([File: streamer/src/nonblocking/quic.rs])

### Finding Description
In `run_server`, an incoming QUIC connection is admitted based on two *non-consuming* checks: `overall_connection_rate_limiter.current_tokens() == 0` [1](#0-0)  and `rate_limiter.is_allowed(&incoming.remote_address().ip())` [2](#0-1) . Neither call consumes a token from the respective `TokenBucket`/`ConnectionRateLimiter`. Tokens are only actually consumed in `setup_connection`, and only in the `Ok(new_connection)` branch reached after a QUIC handshake completes: `rate_limiter.register_connection(&from.ip())` and `overall_connection_rate_limiter.consume_tokens(1)` [3](#0-2) .

If the attacker aborts the connection before the handshake completes (e.g. resets after the Initial packet), `setup_connection` instead falls into the `Err(e)` branch (`handle_connection_error`) or, if the abort happens after `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` (2s) with no progress, the `else` branch incrementing `connection_setup_timeout` [4](#0-3) . In both cases `register_connection` and `overall_connection_rate_limiter.consume_tokens` are never invoked, so the per-IP bucket and the global `TOTAL_CONNECTIONS_PER_SECOND` bucket are never drained by this attacker's traffic. Since the pre-accept gates only look at `current_tokens() == 0` (a bucket that is never depleted by this traffic pattern), they never block subsequent connection attempts from the same source.

The only resource actually bounding such an attack is `ClientConnectionTracker::new`, which enforces `qos.max_concurrent_connections()` as a concurrency cap via `stats.open_connections` [5](#0-4) , and `stats.outstanding_incoming_connection_attempts`, which is incremented before `incoming.accept()` and decremented once `setup_connection` finishes (success, error, or timeout) [6](#0-5) [7](#0-6) . Both are concurrency caps, not rate caps: an attacker who resets connections quickly (well before the 2s handshake timeout) can cycle through this concurrency slot at a very high rate, driving continuous `Endpoint::accept()`/task-spawn/handshake-crypto churn in the single `run_server` accept loop without ever being throttled by either rate limiter, and without contributing to `connection_rate_limited_across_all` / `connection_rate_limited_per_ipaddr` stats that operators would use to detect the abuse.

The code comment at [8](#0-7)  shows this is an intentional design trade-off (avoiding IP-spoofing amplification by not penalizing an unverified source IP before handshake completion), but the trade-off leaves connection *attempt rate* unconstrained by the two rate limiters named in the question, bounded only by the concurrency cap and CPU cost of handling each attempt.

### Impact Explanation
An unstaked remote attacker can continuously churn through `max_concurrent_connections` slots and repeatedly trigger `outstanding_incoming_connection_attempts` increments/`Endpoint::accept()`/QUIC handshake crypto work at a rate far exceeding `TOTAL_CONNECTIONS_PER_SECOND` (2500) and `max_connections_per_ipaddr_per_min`, without ever being counted against `connection_rate_limited_across_all`/`connection_rate_limited_per_ipaddr`. This is QoS evasion of the documented connection admission policy and can starve legitimate TPU clients' handshake admission, consistent with the scoped impact described (exhausting accept-loop / outstanding attempt capacity).

### Likelihood Explanation
Fully reachable by a single unstaked remote client with no preconditions beyond opening/aborting QUIC connections to the public TPU port; repeatable indefinitely and requires no staked/gossip/privileged access.

### Recommendation
Introduce a rate limit on connection *attempts* themselves (not just successful post-handshake connections), e.g. consume a token from `overall_connection_rate_limiter`/per-IP limiter at accept time (with a lightweight, spoofing-resistant per-source-address counter, or leveraging QUIC's own address-validation/Retry mechanism via `quinn::ServerConfig::use_retry`/`ValidationTokenConfig`) so that pre-handshake churn is bounded independently of the concurrency cap.

### Proof of Concept
Integration test plan (extending existing tests like `test_rate_limiting` in `streamer/src/nonblocking/testing_utilities.rs`/`quic.rs`):
1. Spawn `setup_quic_server` with default `QuicStreamerConfig` (`max_connections_per_ipaddr_per_min` small, e.g. 8) and default `SwQosConfig`.
2. From a single client IP, repeatedly create a `quinn::Endpoint::connect` and immediately `drop`/abort it (before handshake completes) in a tight loop, at a rate >> `max_connections_per_ipaddr_per_min` and >> `TOTAL_CONNECTIONS_PER_SECOND` for several seconds.
3. Assert `stats.connection_rate_limited_per_ipaddr` and `stats.connection_rate_limited_across_all` remain at/near 0 despite thousands of attempts (`stats.total_incoming_connection_attempts` large), demonstrating the limiters were never engaged.
4. Concurrently attempt a legitimate full handshake from a second client and measure/assert increased latency or failure to be admitted while the flood is ongoing, confirming starvation of `outstanding_incoming_connection_attempts`/`open_connections` capacity for legitimate clients.

impl ClientConnectionTracker {
    /// Check the max_concurrent_connections limit and if it is within the limit
    /// create ClientConnectionTracker and increment open connection count. Otherwise returns Err
    fn new(stats: Arc<StreamerStats>, max_concurrent_connections: usize) -> Result<Self, ()> {
        let open_connections = stats.open_connections.fetch_add(1, Ordering::Relaxed);
        if open_connections >= max_concurrent_connections {
            stats.open_connections.fetch_sub(1, Ordering::Relaxed);
            debug!(
                "There are too many concurrent connections opened already: open: \
                 {open_connections}, max: {max_concurrent_connections}"
            );
            return Err(());
        }

        Ok(Self { stats })
    }
