### Title
`remove_account` leaves stale receipt/promise-yield state (RECEIVED_DATA, POSTPONED_RECEIPT_ID, PENDING_DATA_COUNT, POSTPONED_RECEIPT, PROMISE_YIELD_RECEIPT, PROMISE_YIELD_STATUS, YIELD_ID_TO_DATA_ID, DATA_ID_TO_YIELD_ID) that resurfaces after account recreation - ([File: core/store/src/utils/mod.rs])

### Summary
`remove_account` only clears four of the twelve trie-key columns keyed by `account_id` (`ACCOUNT`, `CONTRACT_CODE`, `ACCESS_KEY`, `CONTRACT_DATA`), while `col::COLUMNS_WITH_ACCOUNT_ID_IN_KEY` lists twelve. The eight uncleared columns hold receipt/promise-yield bookkeeping data (`RECEIVED_DATA`, `POSTPONED_RECEIPT_ID`, `PENDING_DATA_COUNT`, `POSTPONED_RECEIPT`, `PROMISE_YIELD_RECEIPT`, `PROMISE_YIELD_STATUS`, `YIELD_ID_TO_DATA_ID`, `DATA_ID_TO_YIELD_ID`), which are all set by writer paths in `runtime/runtime/src/lib.rs` before an account can be deleted. Because NEAR permits an account id to be deleted and immediately recreated by the same or a different owner, this stale data persists in the trie under the account's key prefix and can be picked up by future receipt processing addressed to the recreated account.

### Finding Description
`remove_account` in [1](#0-0)  performs only:
- `state_update.remove(TrieKey::Account {...})`
- `state_update.remove(TrieKey::ContractCode {...})`
- Iterates and removes `AccessKey`/`GasKeyNonce` entries under `get_raw_prefix_for_access_keys`
- Iterates and removes `ContractData` entries under `get_raw_prefix_for_contract_data`

The authoritative list of columns that are keyed with an `account_id` prefix, `col::COLUMNS_WITH_ACCOUNT_ID_IN_KEY`, contains 12 entries [2](#0-1) . Subtracting the four columns `remove_account` actually clears leaves exactly: `RECEIVED_DATA`, `POSTPONED_RECEIPT_ID`, `PENDING_DATA_COUNT`, `POSTPONED_RECEIPT`, `PROMISE_YIELD_RECEIPT`, `PROMISE_YIELD_STATUS`, `YIELD_ID_TO_DATA_ID`, `DATA_ID_TO_YIELD_ID` — matching the eight-column list in the audit question. These columns are populated by writer call sites in `runtime/runtime/src/lib.rs` whenever a contract on the account issues cross-contract calls with unresolved input data, postponed receipts awaiting data, or `promise_yield_create`/`promise_yield_resume` flows.

None of these eight columns are removed when `remove_account` runs as part of `DeleteAccount` processing in `runtime/runtime/src/actions.rs`. There is no protocol-level precondition that blocks `DeleteAccount` while an account has outstanding postponed receipts, pending data counts, or unresolved promise-yield state — these are receipt-level bookkeeping structures, not part of the account's `storage_usage` accounting that governs storage-staking checks. Consequently, an attacker can: (1) deploy a contract, (2) trigger a cross-contract call or `promise_yield_create` that leaves an entry under `POSTPONED_RECEIPT`/`PENDING_DATA_COUNT`/`PROMISE_YIELD_RECEIPT`/`PROMISE_YIELD_STATUS` for their own account before the corresponding data/resume arrives, (3) delete the account via a `DeleteAccount` action before that pending receipt/yield resolves, and (4) recreate an account with the identical `account_id` (permitted immediately, with no cooldown). The stale trie entries persist under the same account-id prefix and remain reachable by the deferred receipt-processing logic (e.g., delayed receipt execution or promise-yield timeout processing), which looks up state by column + account_id rather than any generation/version identifier tied to account lifetime.

### Impact Explanation
This falls under "authorization escalation across accounts or promises": deferred receipts or promise-yield resumes originally destined for the deleted account's old contract/state can later be delivered into the *new* account occupying the same id (potentially deployed by the same attacker with different code, or by a different, unrelated owner who claims the freed name). This can corrupt state-root computation relative to what honest validators expect if the resurfaced data interacts with the new contract's logic in an unintended way, and in the worst case lets an attacker manipulate promise-result delivery order/content across account "generations."

### Likelihood Explanation
Preconditions require only: an unprivileged attacker deploying their own contract, triggering a cross-contract call/promise-yield, and issuing a `DeleteAccount` + immediate `CreateAccount` sequence — all ordinary, permissionless transaction flows. Cost is limited to normal gas/storage fees for a `FunctionCall`, `DeleteAccount`, and `CreateAccount`, making it fully repeatable. The main uncertainty (not fully verified in this pass due to the read-only tool limit) is the exact downstream behavior of the delayed-receipt/promise-yield-timeout execution path when it encounters state under a recreated account (e.g., whether any generation counter or hash check exists elsewhere in `runtime/runtime/src/lib.rs` to reject stale postponed receipts) — this would need direct code confirmation of the resume/execute path before treating exploitation as fully proven, but the missing-cleanup condition in `remove_account` itself is confirmed and exact.

### Recommendation
Extend `remove_account` to enumerate and delete all remaining `COLUMNS_WITH_ACCOUNT_ID_IN_KEY` prefixes for the account — specifically add iteration/removal for `RECEIVED_DATA`, `POSTPONED_RECEIPT_ID`, `PENDING_DATA_COUNT`, `POSTPONED_RECEIPT`, `PROMISE_YIELD_RECEIPT`, `PROMISE_YIELD_STATUS`, `YIELD_ID_TO_DATA_ID`, and `DATA_ID_TO_YIELD_ID`, using the equivalent `get_raw_prefix_for_*` helpers in `trie_key_parsers`. Alternatively/additionally, block `DeleteAccount` while any of these columns have non-empty entries for the account (similar to how `remove_account` fails or is prevented while access keys with locked balances exist).

### Proof of Concept
1. Runtime integration test (test-loop) in `test-loop-tests/src/tests/create_delete_account.rs`:
   - Deploy a contract to account `A` that issues a cross-contract `FunctionCall` promise (creating a `PostponedReceipt`/`PendingDataCount`/`ReceivedData` entry) or a `promise_yield_create` (creating `PromiseYieldReceipt`/`PromiseYieldStatus`/`YIELD_ID_TO_DATA_ID`/`DATA_ID_TO_YIELD_ID` entries), without letting the callback/resume resolve.
   - Submit `DeleteAccount` for `A` in the next block.
   - Assert via `core/store/src/utils/mod.rs` trie iteration (or state-viewer) that raw keys still exist under prefixes for `RECEIVED_DATA`/`POSTPONED_RECEIPT`/`PROMISE_YIELD_RECEIPT`/etc. for account `A`.
   - Recreate account `A` with a new contract.
   - Advance chain until the original postponed receipt/yield timeout would fire, and assert whether it executes against the new account/contract (expected: it should either be impossible to create, i.e., `DeleteAccount` should be rejected while pending, or the stale entry should have been purged — actual current behavior: entry persists and is not purged by `remove_account`, confirming the gap).

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
