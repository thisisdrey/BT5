### Title
Ciphertext-malleability-style key-collision in TRC10 token balance accounting via lossy `new String(byte[])` conversion - (File: `common/src/main/java/org/tron/common/utils/ByteArray.java`)

### Summary
The Tink advisory's root cause is that raw bytes were converted to a `String` using the JVM's default lossy decoding (invalid byte sequences collapsed to `U+FFFD`), so multiple distinct byte arrays could be mapped to the same `String` key in a lookup table, breaking uniqueness guarantees. java-tron has the same anti-pattern: `ByteArray.toStr(byte[] b)` performs `new String(b)` (no explicit charset, replacement-on-error semantics) and this helper is used pervasively to derive the `String` keys of the TRC10 asset balance maps (`Map<String,Long> asset` / `assetV2`) inside `AccountCapsule`, and directly (`new String(tokenIdWithoutLeadingZero)`) inside the TVM `RepositoryImpl`. Because the TVM entry point accepts attacker-controlled token-id byte strings, distinct byte sequences can be normalized to an identical `String` key, corrupting per-account asset accounting.

### Finding Description
`ByteArray.toStr()` performs an unchecked, lossy byte-to-`String` conversion: [1](#0-0) 

This helper is used as the *sole* means of deriving the `String` key for the protobuf `Map<String, Long>` fields that back TRC10 token balances on an account (`account.getAssetMap()` / `getAssetV2Map()`), in `assetBalanceEnoughV2`, `addAssetAmount`, `addAssetAmountV2`, `reduceAssetAmount`, `reduceAssetAmountV2`, and `addAssetV2`: [2](#0-1) [3](#0-2) 

Critically, the TVM repository layer (`RepositoryImpl.addTokenBalance`), which is the code path used by smart-contract token-transfer opcodes (e.g. token-value transfers to/from contracts during a `CALL`), performs the exact same lossy conversion directly on attacker-influenced token-id bytes coming from the transaction/contract execution: [4](#0-3) 

Because `new String(byte[])` (using the platform default charset without any validation) replaces any malformed/invalid byte subsequence with the Unicode replacement character `U+FFFD` rather than throwing, **two different byte-array token identifiers that are invalid in the same way** are normalized to the identical `String`. Since the underlying store (`Map<String, Long>`) is keyed purely on this lossy `String`, such colliding token-id byte arrays are indistinguishable at the accounting layer — exactly analogous to how Tink's key-ID prefix bytes collided into the same hash-map bucket key, breaking the intended non-malleability of the ciphertext identity.

Unlike Tink's Java map (`HashMap<String,...>`) used only for internal key-ID dispatch, here the colliding `String` key is the literal storage key for **fund balances**, so a collision directly corrupts asset accounting rather than merely "ciphertext integrity."

### Impact Explanation
If an attacker can supply a byte-array token id (via a contract-executed token transfer / TVM call) that, once lossily decoded, collides with the `String` key already used for a different (potentially real/legitimate) token balance entry for the same account, the two distinct token identities become one entry in `assetMap`/`assetV2Map`. Depending on the surrounding sequence of adds/reduces, this can:
- Corrupt/merge unrelated TRC10 balances tracked for the account (data integrity of fund accounting broken).
- Allow one operation to add to, or fraudulently inflate/reduce, a balance slot that was intended to represent a different token, i.e. an "unbacked balance" condition consistent with the report's accepted impact categories.

This is a Medium-severity integrity issue on on-chain balance bookkeeping, reachable purely through normal transaction/contract execution — no privileged role required.

### Likelihood Explanation
Reaching `RepositoryImpl.addTokenBalance` only requires deploying/calling a smart contract that performs a TRC10 token value transfer, something any unprivileged account can do. Crafting the colliding byte sequences requires finding two distinct byte strings that are both invalid under the platform default decoder and normalize (post `U+FFFD` substitution) to the same `String`; this is a mechanically straightforward, attacker-controllable construction (same class of proof used in the original Tink CVE), not a cryptographic hardness problem. The main uncertainty is the exact scope of practical exploitation (e.g., whether it can be forced to collide with a specific victim's *real* token id, versus only colliding among attacker-chosen bogus ids) — this would need to be confirmed with a live PoC against a running node, which is outside static analysis capability here.

### Recommendation
- Replace all lossy `new String(bytes)` / `ByteArray.toStr()` usages that serve as security- or accounting-relevant map/store keys with a canonical, injective encoding (e.g., hex/base64 encoding of the raw bytes, or continuing to use `byte[]`-keyed maps/`ByteArrayWrapper`/`WrappedByteArray` as is already done elsewhere in the codebase, e.g. `common/src/main/java/org/tron/common/utils/ByteArrayMap.java`).
- Specifically harden `RepositoryImpl.addTokenBalance` and the `AccountCapsule` asset-map helpers (`assetBalanceEnoughV2`, `addAssetAmountV2`, `reduceAssetAmountV2`, `addAsset`, `addAssetV2`) to validate/reject token-id byte arrays that are not valid, round-trippable UTF-8 (or ASCII digit strings, matching the real TRC10 id format) before using them as map keys, so no two distinct byte inputs can ever normalize to the same key.
- Add regression tests asserting that decoding is either strict (throws) or injective for all token-id inputs reaching balance-mutating code paths.

### Proof of Concept
Conceptual PoC (illustrating the collision class; exact byte sequences require testing against the specific JVM default charset in use):
1. Deploy a smart contract that performs a TRC10 token transfer/call specifying an attacker-chosen `tokenId` byte array `B1` containing an invalid UTF-8 subsequence at a known offset.
2. Invoke the same contract logic with a different byte array `B2` (different bytes, but invalid in the *same* decoding position/pattern) such that `new String(B1)` and `new String(B2)` both replace the invalid region with `U+FFFD` and consequently produce an identical `String`.
3. Observe that `RepositoryImpl.addTokenBalance` / `AccountCapsule.addAssetAmountV2` (`common/src/main/java/org/tron/common/utils/ByteArray.java:83-85`, `chainbase/.../AccountCapsule.java:733-765`) store/retrieve both "distinct" tokens under the same `assetV2Map` key, causing balance entries intended for `B1` and `B2` to merge/overwrite each other.

Note: I could not trace the full TVM opcode dispatcher (e.g. the `CALLTOKEN`/token-value-transfer opcode implementation in `Program.java`) in the indexed portion of the codebase to pin down the exact byte-length/format constraints imposed on `tokenId` before it reaches `RepositoryImpl.addTokenBalance`; a live Devin session with full repository access would be needed to construct and validate a concrete colliding byte pair end-to-end.

  public boolean assetBalanceEnoughV2(byte[] key, long amount,
      DynamicPropertiesStore dynamicPropertiesStore) {
    importAsset(key);
    Map<String, Long> assetMap;
    String nameKey;
    Long currentAmount;
    if (dynamicPropertiesStore.getAllowSameTokenName() == 0) {
      assetMap = this.account.getAssetMap();
      nameKey = ByteArray.toStr(key);
      currentAmount = assetMap.get(nameKey);
    } else {
      String tokenID = ByteArray.toStr(key);
      assetMap = this.account.getAssetV2Map();
      currentAmount = assetMap.get(tokenID);
    }

    return amount > 0 && null != currentAmount && amount <= currentAmount;
  }

  public boolean addAssetAmount(byte[] key, long amount, boolean useStrict) {
    Map<String, Long> assetMap = this.account.getAssetMap();

    Long currentAmount = assetMap.get(nameKey);
    if (currentAmount == null) {
      currentAmount = 0L;

            addExact(currentAmount, amount, useStrict))

    return true;

  @Override
  public long addTokenBalance(byte[] address, byte[] tokenId, long value) {
    byte[] tokenIdWithoutLeadingZero = ByteUtil.stripLeadingZeroes(tokenId);
    AccountCapsule accountCapsule = getAccount(address);
    if (accountCapsule == null) {
      accountCapsule = createAccount(address, Protocol.AccountType.Normal);
    }
    long balance = accountCapsule.getAssetV2(new String(tokenIdWithoutLeadingZero));
    if (value == 0) {
      return balance;
    }

    if (value < 0 && balance < -value) {
      throw new RuntimeException(
          StringUtil.createReadableString(accountCapsule.createDbKey())
              + " insufficient balance");
    }
    if (value >= 0) {
      accountCapsule.addAssetAmountV2(tokenIdWithoutLeadingZero, value, getDynamicPropertiesStore(),
          getAssetIssueStore());
    } else {
      accountCapsule
          .reduceAssetAmountV2(tokenIdWithoutLeadingZero, -value, getDynamicPropertiesStore(),
              getAssetIssueStore());
    }
    Key key = Key.create(address);
    accountCache.put(key, Value.create(accountCapsule,
         accountCache.get(key).getType().addType(Type.DIRTY)));
    return accountCapsule.getAssetV2(new String(tokenIdWithoutLeadingZero));
  }
