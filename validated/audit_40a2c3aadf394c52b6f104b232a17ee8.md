Based on my research, I found a concrete analog in java-tron matching the audit's bug class: an unchecked configuration/percentage value used unguarded as a divisor/multiplier in a fee-like (energy) calculation.

### Title
Missing range validation of `consumeUserResourcePercent` in `CreateSmartContract`/`UpdateSettingContract` actuators allows malformed divisor to corrupt energy-limit math - (File: `actuator/src/main/java/org/tron/core/vm/VMActuator.java`)

### Summary
The Sherlock report flags `SoftVault.withdraw()` for using an unvalidated `config.withdrawVaultFee() / DENOMINATOR` ratio without checking that the numerator/denominator bounds make sense, letting the fee computation overflow/underflow. The java-tron analog is the `consumeUserResourcePercent` field, which is used exactly the same way — as a fraction (`percent / 100`) inside `VMActuator.getTotalEnergyLimitWithFixRatio` — but the field is only range-checked in a client-side helper, not in the actual on-chain actuator `validate()` path.

### Finding Description
`VMActuator.getTotalEnergyLimitWithFixRatio` divides by `consumeUserResourcePercent` and multiplies by `(ONE_HUNDRED - consumeUserResourcePercent)`: [1](#0-0) 

The only place that enforces `0 <= percent <= 100` for a `CreateSmartContract` is `Wallet.createTransactionCapsule`, a convenience wrapper used by the local wallet/CLI transaction-building helper: [2](#0-1) 

This check is bypassable because it lives outside of the actuator's `validate()`/`execute()` contract lifecycle that consensus nodes run on every incoming transaction (`dbManager.pushTransaction(trx)` in `broadcastTransaction`, and block re-application), and is not duplicated in the actual `CreateSmartContractActuator`. A grep for `ConsumeUserResourcePercent` across the actuator implementing `CreateSmartContract` found no range validation there, unlike `UpdateSettingContractActuator`, which does correctly bound the value: [3](#0-2) 

An attacker can hand-craft and directly sign a `CreateSmartContract` transaction (not going through `Wallet.createTransactionCapsule`) with `consumeUserResourcePercent` set to an out-of-range value (e.g., `> 100` or extremely large), broadcast it via the gRPC/HTTP `BroadcastTransaction` API, and have it accepted because `broadcastTransaction` never calls the range-check that only exists in the wallet helper: [4](#0-3) 

### Impact Explanation
Once such a contract is deployed with an out-of-range percent, every subsequent call to it goes through `getTotalEnergyLimitWithFixRatio`, where `(ONE_HUNDRED - consumeUserResourcePercent)` becomes negative for `percent > 100`, producing a negative `creatorEnergyLimit` that is then combined via `addExact` with the caller's energy limit, corrupting the resulting total energy limit calculation for every call to the malicious contract. For sufficiently large values, `BigInteger...longValueExact()` can throw an uncaught `ArithmeticException` during transaction execution/energy accounting, which is a shared, broadcastable-by-anyone code path (any account can call a deployed contract), making this a denial-of-service/incorrect-accounting vector reachable by an ordinary contract deployer plus any caller of that contract.

### Likelihood Explanation
Likelihood is limited by the fact that this requires bypassing the standard Java wallet helper by constructing a raw protobuf transaction directly (straightforward for any determined attacker using the public gRPC/HTTP broadcast API), and I could not fully confirm within the available index whether any deeper validation exists elsewhere (e.g., in `TransactionCapsule` or `ContractCapsule` setters) that might also enforce this bound before storage — my search for `ConsumeUserResourcePercent` in `ContractCapsule.java` returned matches but I was unable to read their content before running out of tool calls, so I cannot be fully certain no additional clamp exists there.

### Recommendation
Add an explicit `0 <= consumeUserResourcePercent <= 100` check inside `CreateSmartContractActuator.validate()` (mirroring `UpdateSettingContractActuator`'s check) so the invariant is enforced at the actuator/consensus level rather than only in the client wallet helper, and additionally harden `VMActuator.getTotalEnergyLimitWithFixRatio` to reject or clamp out-of-range percentages defensively.

### Proof of Concept
1. Construct a `CreateSmartContract` transaction protobuf directly (bypassing `Wallet.createTransactionCapsule`), setting `new_contract.consume_user_resource_percent` to `1000` (or another value `>100`).
2. Sign and submit it via the `BroadcastTransaction` gRPC/HTTP endpoint.
3. Observe the transaction is accepted because `CreateSmartContractActuator.validate()` performs no range check on the field (confirmed by absence of any `ConsumeUserResourcePercent` reference in that actuator).
4. Call the deployed contract; `VMActuator.getTotalEnergyLimitWithFixRatio` computes a negative `creatorEnergyLimit`, corrupting the energy accounting for the call, or throws an `ArithmeticException` via `BigInteger.longValueExact()` for extreme values. [5](#0-4) 

**Note on confidence:** I was unable to fully verify whether `ContractCapsule`'s own setter/getter for `ConsumeUserResourcePercent` performs any independent clamping before the value reaches `VMActuator`, since my remaining tool budget ran out before I could read that file's content. This should be double-checked before treating the finding as fully confirmed.
