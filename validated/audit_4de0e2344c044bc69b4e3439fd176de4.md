### Title
Malicious peer's unpunished false-positive attachment inventory bit + single-source `AttachmentRequest::get_url` selection causes legitimate `AttachmentInstance` downloads to be permanently dropped - (File: stackslib/src/net/atlas/download.rs)

### Summary
`AttachmentsBatchStateContext::get_prioritized_attachments_requests` builds an `AttachmentRequest.sources` map purely from unauthenticated inventory-bit claims (`has_attachment`), and `Requestable::get_url` for `AttachmentRequest` always resolves to the single highest-`ReliabilityReport`-scored peer via `get_most_reliable_source`. A remote peer can build up a good reputation on unrelated requests, then falsely claim (via inventory bit = 1) to have a specific attachment it does not have; when the HTTP fetch to that peer returns 404, the failure is routed to `faulty_peers` and never reaches `extend_with_attachments`, so the malicious peer's `ReliabilityReport` is never decremented via `bump_failed_requests`. It therefore stays the "most reliable source" every retry round, permanently starving the download of a real, on-chain-committed attachment until `max_attachment_retry_count` is exhausted and the batch is dropped.

### Finding Description
The equality the code implicitly relies on is: *the peer selected to serve `content_hash` H (via `get_most_reliable_source`) is a peer who has actually verified access to H*. This equality is broken because peer selection is based solely on a self-reported inventory bit that is never checked against real possession, combined with a reputation score that is not updated on the specific failure mode a lying peer would trigger.

Code path:
1. `get_prioritized_attachments_requests` (stackslib/src/net/atlas/download.rs:404-478) builds `sources: HashMap<UrlString, ReliabilityReport>` for each missing `content_hash` purely by reading the `has_attachment` bit from each peer's self-reported `GetAttachmentsInvResponse` (lines 439-458) — no cross-check against actual attachment bytes is performed at this stage. [1](#0-0) 
2. `AttachmentRequest::get_most_reliable_source` (lines 1074-1079) and `Requestable::get_url` for `AttachmentRequest` (lines 1104-1108) deterministically pick the single peer with the highest `ReliabilityReport::score()` among `sources` — there is no round-robin or fan-out across all claiming peers within a batch round. [2](#0-1) 
3. In `BatchedRequestsState::try_proceed` (PollRequests branch), if the selected peer's HTTP response is a 404, the request is routed to `state.faulty_peers` and the loop `continue`s — it is never inserted into `state.succeeded`. [3](#0-2) 
4. `AttachmentsBatchStateContext::extend_with_attachments` only updates `ReliabilityReport` (via `bump_successful_requests`/`bump_failed_requests`) for entries found in `results.succeeded`; entries dropped as `faulty_peers` (404 case) never reach this function, so the malicious peer's score is left untouched. [4](#0-3) 
5. The `reliability_reports: HashMap<UrlString, ReliabilityReport>` on `AttachmentsDownloader` persists across retry rounds (`AttachmentsDownloader::run`, lines 182-185), so the same unpunished, artificially-high score is reused on every subsequent retry. [5](#0-4) 
6. After `max_attachment_retry_count` rounds all fail (because the same lying peer is re-selected every time), the batch is permanently dropped: `"Atlas: dropping batch {:?} retries count exceeded"`. [6](#0-5) 

The attacker's exact message is a crafted, unauthenticated HTTP `200` response to `GET /v2/attachments/inv?...` (the `/v2/attachments/inv` endpoint, `stackslib/src/net/api/getattachmentsinv.rs`) with a spoofed inventory bit set to `1` for a page/position it does not actually hold, followed by a `404` on the follow-up `GET /v2/attachments/{content_hash}` request. Because report degradation is coupled only to `succeeded`-path processing and 404s bypass it entirely, this attack is fully repeatable at zero cost to the attacker's reputation.

### Impact Explanation
A single unprivileged remote peer with a moderately good history (attainable by legitimately answering some unrelated requests) can indefinitely block resolution of a specific, legitimately on-chain-committed attachment (e.g., a BNS zonefile), causing the corresponding `AttachmentInstance` to be evicted from the download `priority_queue` even though honest peers in the same `sources` set genuinely have and would have served the data. This creates a persistent mismatch between an on-chain-committed name/attachment operation and the node's locally resolved off-chain state (attachment/BNS mismatch), matching the "High" impact category of serving/perceiving non-canonical off-chain state as final because the attachment is permanently treated as unresolved/dropped rather than fetched from an honest source.

### Likelihood Explanation
Preconditions: the attacker must run its own peer, be selected among `network.get_outbound_sync_peers()`, and have (or build) a `ReliabilityReport` score at least as high as the honest peers serving the same content — achievable by simply answering some inventory/attachment requests correctly to accumulate `total_requests_sent`/`total_requests_success`. No secrets, admin roles, or privileged access are required; connecting a normal P2P/RPC-reachable node satisfies this. The attack is cheap (a handful of forged inventory responses plus repeated 404s) and fully repeatable per targeted `content_hash` across retry rounds.

### Recommendation
- Decrement/punish a peer's `ReliabilityReport` (via `bump_failed_requests`) when a claimed-available attachment turns out to be a 404, instead of silently discarding it into `faulty_peers` without reputation impact.
- When the top-ranked source fails/404s for a given `content_hash` within a batch round, fall back to trying the next-best source in `sources` in the same round rather than waiting for a full retry cycle.
- Consider verifying a random subset of returned inventory claims against real fetch attempts before trusting a peer's inventory bit for prioritization, or requiring corroboration from multiple peers before treating a single peer's inventory claim as authoritative for scheduling.

### Proof of Concept
Rust test in `stackslib::net::atlas::tests` (or `download.rs` test module):
1. Construct an `AttachmentsBatchStateContext` with two peers: `peer_honest` (has the attachment, will 200) and `peer_liar` (claims `has_attachment = true` in its `GetAttachmentsInvResponse` inventory bit for the target page/position, but always returns HTTP 404 for `/v2/attachments/{content_hash}`), giving `peer_liar` a pre-seeded high `ReliabilityReport` (e.g., `ReliabilityReport::new(100, 100)`) and `peer_honest` a lower/empty report.
2. Call `get_prioritized_attachments_requests()` and assert the resulting `AttachmentRequest::get_url()` (via `get_most_reliable_source`) resolves to `peer_liar`'s URL, not `peer_honest`'s.
3. Simulate `connection_options.max_attachment_retry_count` retry rounds of `AttachmentsDownloader::run`, with `peer_liar` always answering the inv request truthfully-claiming and the content request with 404, and `peer_honest` never being contacted.
4. Assert: (a) `peer_liar`'s `ReliabilityReport.total_requests_sent`/`success` are unchanged by the 404s (proving no penalty), (b) after `max_attachment_retry_count` rounds the batch is dropped, asserted by capturing the `"Atlas: dropping batch {:?} retries count exceeded"` log line (or checking the `AttachmentsBatch` is absent from `priority_queue` and `attachments_batch.has_fully_succeed()` is false), and (c) `peer_honest` was never selected/queried for the content, confirming the honest source was starved.

impl AttachmentRequest {
    pub fn get_most_reliable_source(&self) -> (&UrlString, &ReliabilityReport) {
        self.sources
            .iter()
            .max_by_key(|(_, v)| v.score())
            .expect("Atlas: trying to select an Url out of an empty set")
    }
}

impl Hash for AttachmentRequest {
    fn hash<H: Hasher>(&self, state: &mut H) {
        self.content_hash.hash(state)
    }
}

impl Ord for AttachmentRequest {
    fn cmp(&self, other: &AttachmentRequest) -> Ordering {
        other.sources.len().cmp(&self.sources.len()).then_with(|| {
            let (_, report) = self.get_most_reliable_source();
            let (_, other_report) = other.get_most_reliable_source();
            report.cmp(other_report)
        })
    }
}

impl PartialOrd for AttachmentRequest {
    fn partial_cmp(&self, other: &AttachmentRequest) -> Option<Ordering> {
        Some(self.cmp(other))
    }
}

impl Requestable for AttachmentRequest {
    fn get_url(&self) -> &UrlString {
        let (url, _) = self.get_most_reliable_source();
        url
    }
