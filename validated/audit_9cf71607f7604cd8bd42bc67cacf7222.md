### Title
Stale-trust persistence: revoked/removed CA does not tear down already-established tunnels by default - ([File: connection_manager.go])

### Summary
The reported staking bug is a "two-phase trust" flaw: a decision made at request time (token accepted) is never re-validated at finalize time (token removed), leaving the user's funds in limbo. Nebula has a structurally analogous "verify-once, never re-verify" gap in its certificate-trust lifecycle: a peer's certificate is validated against the CA pool only at handshake time (`certVerifier`), and the periodic re-validation that could revoke trust after a CA is later removed/expired is disabled by default.

### Finding Description
`HandshakeManager.certVerifier()` verifies the remote certificate against the *current* `CAPool` exactly once, at handshake completion: [1](#0-0) 

Once the handshake completes, the resulting `HostInfo`/`ConnectionState` is trusted indefinitely for data-plane traffic. The only mechanism that re-checks the peer certificate against a possibly-changed CA pool is `connectionManager.isInvalidCertificate()`: [2](#0-1) 

Critically, this re-check only tears down the tunnel if `pki.disconnect_invalid` is `true`. The CHANGELOG documents this as an opt-in feature, disabled by default: [3](#0-2) 

So the flow is: (1) at handshake time the peer cert is signed by a CA present in `pki.ca` and is accepted; (2) an operator later removes that CA from `pki.ca` (e.g., because the signing CA was compromised or retired) and hot-reloads via `PKI.reloadCAPool`: [4](#0-3) 
(3) with the default configuration, the already-established tunnel is never re-evaluated against the new CA pool — `isInvalidCertificate` is only invoked by the connection manager loop and, even when invoked, does nothing unless `disconnect_invalid` is explicitly enabled. This mirrors the reported bug's root cause: a trust decision recorded during one phase (successful handshake) is never revisited when the underlying authorization condition (CA membership) changes, and there is no forced re-validation path analogous to "refund/abort if condition changed."

### Impact Explanation
If an operator revokes a compromised CA/cert by removing it from `pki.ca` expecting to cut off a rogue peer, any tunnel that already completed a handshake with that peer remains fully trusted and continues to pass encrypted, authenticated traffic under the default configuration. This is a remote-state-poisoning / stale-authentication issue: the intended security boundary (CA trust) is silently bypassed for all sessions established before the CA removal, with no time bound on how long the stale trust persists (unlike the reported 49-hour lock, here it can be indefinite since it's gated behind an off-by-default flag).

### Likelihood Explanation
Medium. It requires an operator-driven CA/cert removal (a routine, expected administrative action during key rotation or compromise response) combined with the default configuration (`pki.disconnect_invalid=false`). No attacker action beyond having obtained a certificate before revocation is required — the "attacker" here is exactly the peer whose trust was supposed to be revoked.

### Recommendation
Make certificate re-validation against the current CA pool mandatory (or default-on) for all live tunnels, not opt-in via `pki.disconnect_invalid`. At minimum, always tear down (or force re-handshake of) tunnels whose signer CA fingerprint is no longer present in the reloaded `CAPool`, independent of the `disconnect_invalid` toggle, mirroring how blocklisted certificates are already always torn down in `isInvalidCertificate`.

### Proof of Concept
1. Start two nebula nodes A and B with CA `ca1` signing B's certificate; default config (`pki.disconnect_invalid` unset/false).
2. Complete a handshake between A and B (tunnel established, verified via `certVerifier` against `ca1`).
3. On A, edit `pki.ca` to remove `ca1` and SIGHUP/reload (`PKI.reloadCAPool`).
4. Observe: A's connection manager `isInvalidCertificate` check (default config) returns `false` for B's tunnel (no blocklist), so the existing tunnel is never torn down — B continues sending/receiving encrypted traffic through A indefinitely despite A no longer trusting `ca1`. [5](#0-4)

// certVerifier returns a CertVerifier that validates certs against the current CA pool.
func (hm *HandshakeManager) certVerifier() handshake.CertVerifier {
	return func(c cert.Certificate) (*cert.CachedCertificate, error) {
		return hm.f.pki.GetCAPool().VerifyCertificate(time.Now(), c)
	}
}

// isInvalidCertificate decides if we should destroy a tunnel.
// returns true if pki.disconnect_invalid is true and the certificate is no longer valid.
// Blocklisted certificates will skip the pki.disconnect_invalid check and return true.
func (cm *connectionManager) isInvalidCertificate(now time.Time, hostinfo *HostInfo) bool {
	remoteCert := hostinfo.GetCert()
	if remoteCert == nil {
		return false //don't tear down tunnels for handshakes in progress
	}

	caPool := cm.intf.pki.GetCAPool()
	err := caPool.VerifyCachedCertificate(now, remoteCert)
	if err == nil {
		return false //cert is still valid! yay!
	} else if err == cert.ErrBlockListed { //avoiding errors.Is for speed
		// Block listed certificates should always be disconnected
		hostinfo.logger(cm.l).Info("Remote certificate is blocked, tearing down the tunnel",
			"error", err,
			"fingerprint", remoteCert.Fingerprint,
		)
		return true
	} else if cm.intf.disconnectInvalid.Load() {
		hostinfo.logger(cm.l).Info("Remote certificate is no longer valid, tearing down the tunnel",
			"error", err,
			"fingerprint", remoteCert.Fingerprint,
		)
		return true
	} else {
		//if we reach here, the cert is no longer valid, but we're configured to keep tunnels from now-invalid certs open
		return false
	}
}

func (p *PKI) reloadCAPool(c *config.C) *util.ContextualError {
	caPool, err := loadCAPoolFromConfig(p.l, c)
	if err != nil {
		return util.NewContextualError("Failed to load ca from config", nil, err)
	}

	p.caPool.Store(caPool)
	p.l.Debug("Trusted CA fingerprints", "fingerprints", caPool.GetFingerprints())
	return nil
}
