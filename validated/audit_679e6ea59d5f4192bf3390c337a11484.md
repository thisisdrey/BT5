### Title
Cross-StackerDB Chunk Replay via Weak Signature Binding in `SlotMetadata::auth_digest` — (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` computes the message that a signer signs over for a StackerDB chunk write, but the digest only commits to `slot_id`, `slot_version`, and `data_hash` [1](#0-0) . It does **not** include the `smart_contract_id` (the StackerDB instance/contract this chunk write is destined for). This is the same bug class as the reported openvm-stark-backend issue: a cryptographic commitment (there, the Fiat-Shamir challenge; here, the signed digest) fails to bind all of the context that determines validity, allowing a value that is valid in one context to be replayed as valid in a different context that the signer never intended.

### Finding Description
`SlotMetadata::sign`/`verify` and `StackerDBChunkData::sign`/`verify`/`recover_pk` all derive their message solely from `auth_digest()`, i.e. `H(slot_id || slot_version || data_hash)` [2](#0-1) . Chunk acceptance on the write path (`validate_received_chunk` / `try_replace_chunk`) then checks:
1. size limits,
2. that `slot_id` is in range,
3. that the signer address recovered from the signature matches the configured signer for that `slot_id` **within the target `smart_contract_id`** (via `get_slot_signer(smart_contract_id, slot_id)`),
4. version/monotonicity and write-count limits [3](#0-2) .

The signer-address check is scoped by `smart_contract_id`, but the *signature itself* never commits to which contract it authorizes. Consequently, if the same signer address is assigned the same `slot_id` in two different StackerDB contracts (which happens by design in the Stacks signer protocol — a given reward-cycle's signer set is replicated across the `signers-0-<cycle>` and `signers-1-<cycle>` StackerDB contracts, each derived from the same ordered signer set, per `stackslib/src/chainstate/stacks/boot/signers-0-xxx.clar` and `signers-1-xxx.clar`), a legitimately-signed chunk originally produced for slot `S` in contract A is *also* a validly-signed chunk for slot `S` in contract B, because `auth_digest` cannot distinguish the two contexts.

Any network participant that has observed a chunk broadcast for contract A (StackerDB chunk gossip is unauthenticated-by-secrecy and openly relayed) can therefore replay that `(slot_id, slot_version, sig, data)` tuple into contract B's replicas via the same code paths used for legitimately-signed chunks: `handle_unsolicited_StackerDBPushChunk` / `validate_downloaded_chunk` → `validate_received_chunk` → `StackerDBTx::try_replace_chunk` [4](#0-3) . The replica has no way to detect that the signature was produced with contract B never in mind — the check only verifies the recovered pubkey-hash matches the configured signer for that slot in that DB, which it does.

### Impact Explanation
This is an unauthenticated/unauthorized write to StackerDB state: an attacker who does not hold the signer's private key can force acceptance of stale/foreign chunk content into a different StackerDB instance than the one the signer intended, as long as version/monotonicity constraints of the target slot happen to permit it (e.g., the target slot's version is behind, or the replay is timed to a version the target accepts). Because accepted chunks are re-broadcast to peers replicating that DB (per `mod.rs:85-96`), this also causes network-wide propagation of forged/foreign data under a legitimate signer's identity in a StackerDB context that signer did not actually author a message for.

### Likelihood Explanation
Exploitation requires only passively observing one legitimately broadcast/signed chunk (chunks are gossiped in the clear) and replaying it against a second StackerDB contract where the same signer address is assigned the same `slot_id`. Given the deterministic, signer-set-derived slot assignment across the `signers-0-*` / `signers-1-*` contract pairs (and potentially across consecutive reward cycles when signer-set ordering repeats), this same-slot-same-signer condition is a realistic and likely-recurring configuration, not a contrived edge case — no node secret, admin role, or other party's key is required.

### Recommendation
Bind the signed digest to the full write context, mirroring the report's fix for weak Fiat-Shamir (commit to *all* relevant context before trusting the derived value): include `smart_contract_id` (and ideally a domain-separation tag) in `SlotMetadata::auth_digest()`:
```rust
fn auth_digest(&self, smart_contract_id: &QualifiedContractIdentifier) -> Sha512Trunc256Sum {
    let mut hasher = Sha512_256::new();
    hasher.update(smart_contract_id.to_string().as_bytes());
    hasher.update(self.slot_id.to_be_bytes());
    hasher.update(self.slot_version.to_be_bytes());
    hasher.update(self.data_hash.0);
    Sha512Trunc256Sum::from_hasher(hasher)
}
```
Update `sign`/`verify` call sites (`libstackerdb/src/libstackerdb.rs:144-245`, `stackslib/src/net/stackerdb/mod.rs:690-697`) to pass the contract identifier through, so a chunk signature is only valid for the specific StackerDB instance it was produced for.

### Proof of Concept
1. Configure two StackerDB contracts, A and B, whose signer sets assign the same signer address to `slot_id = 0` (e.g. reward-cycle-derived `signers-0-N` and `signers-1-N` contracts as constructed in `stacks-node/src/tests/stackerdb.rs`).
2. Have the signer legitimately sign and push chunk `data` for `slot_id=0, slot_version=1` into contract A: `StackerDBChunkData::new(0, 1, data).sign(&signer_privk)`, verified per `libstackerdb.rs:226-231`.
3. Capture this signed chunk from gossip (no secret needed — it's on the wire in `StackerDBPushChunkData`/`StackerDBChunkData`, per `stackslib/src/net/stackerdb/mod.rs`).
4. Replay the identical `StackerDBChunkData { slot_id:0, slot_version:1, sig, data }` against contract B's `PeerNetwork::handle_unsolicited_StackerDBPushChunk` or as a direct `POST /v2/stackerdb/.../chunks` request targeting contract B.
5. `validate_received_chunk` recovers the same pubkey hash for slot 0 in contract B (same signer/slot mapping) and `slot_metadata.verify(&addr)` succeeds because `auth_digest()` never encoded which contract the signature was for [5](#0-4)  — the chunk is accepted into contract B's replica and re-gossiped, even though the signer never authorized a write to contract B with this content.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Sign this slot metadata, committing to slot_id, slot_version, and
    /// data_hash.  Sets self.signature to the signature.
    /// Fails if the underlying crypto library fails
    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
