### Title
Stale postponed receipts survive `DeleteAccount` and execute self-authorized actions against a re-registered account of the same name - ([File: core/store/src/utils/mod.rs])

### Summary
`remove_account` only deletes `TrieKey::Account`, `ContractCode`, `AccessKey`, and `ContractData` for a deleted account, but never removes any `TrieKey::PostponedReceiptId`, `PendingDataCount`, or `PostponedReceipt` entries keyed by that account's `receiver_id`. If the account had an outstanding postponed action receipt (a self-addressed callback awaiting a `DataReceipt`) at the time of deletion, and the account name is later re-registered by a different owner, delivery of the original awaited `DataReceipt` will resurrect and execute the stale receipt against the *new* account, using the old, self-authorized `predecessor_id`/`actor_id`.

### Finding Description
`remove_account` (core/store/src/utils/mod.rs:505-575) removes `Account`, `ContractCode`, `AccessKey`/gas-key, and `ContractData` rows for the account being deleted, but has no logic that scans or clears `TrieKey::PostponedReceiptId`, `TrieKey::PendingDataCount`, or `TrieKey::PostponedReceipt` for that `account_id`. [1](#0-0) [2](#0-1) 

`action_delete_account` (runtime/runtime/src/actions.rs:314-391), which calls `remove_account`, only checks `account_storage_usage` (against `MAX_ACCOUNT_DELETION_STORAGE_USAGE`) and gas-key burn balance before deleting — there is no check for outstanding postponed receipts targeting the account. [3](#0-2) [4](#0-3) 

Postponed receipts are created in `process_action_receipt` (runtime/runtime/src/lib.rs:1593-1658) whenever an incoming `ActionReceipt` has unmet `input_data_ids`: a `PostponedReceiptId` link, a `PendingDataCount`, and the full serialized receipt (`set_postponed_receipt`) are written, all keyed solely by `account_id` (the receiver, i.e. the target account name) with no notion of "account incarnation." [5](#0-4) 

When the matching `DataReceipt` eventually arrives, `process_receipt`'s `Data` branch (runtime/runtime/src/lib.rs:1367-1474) looks up `PostponedReceiptId{receiver_id, data_id}` purely by account-name string match, decrements `PendingDataCount`, fetches the `PostponedReceipt`, and unconditionally executes it via `apply_action_receipt` — with no check that the account currently occupying that name is the same "account" that originally created the pending call. [6](#0-5) 

Because NEAR account IDs have no incarnation/generation counter, `apply_action_receipt` re-derives `actor_id` from the resurrected receipt's own `predecessor_id` field (`let mut actor_id = receipt.predecessor_id().clone();`), which is immutable data baked into the receipt when it was first created (before deletion). [7](#0-6) 

Exploit flow:
1. The attacker (the original owner of `x.near`) has their contract issue `Promise::new(other_contract).function_call(...).then(Self::callback)`. This produces a callback `ActionReceipt` with `receiver_id = x.near`, `predecessor_id = x.near` (self-authorized, since a `.then` callback created by a contract's own execution context is attributed to that contract), and an `input_data_id` pointing at the pending cross-contract result. The callback's actions can include self-authorized administrative actions such as `AddKey`, `Stake`, or `DeleteKey` (these require `actor_id == account_id`, which self-calls satisfy) — e.g. an `AddKey` inserting an attacker-controlled `FullAccess` public key.
2. Before the awaited `DataReceipt` arrives, the attacker deletes `x.near` via `Action::DeleteAccount` (self-authorized, refunding balance to a beneficiary of their choice). `remove_account` clears the `Account`/keys/code/data but leaves the `PostponedReceiptId`/`PendingDataCount`/`PostponedReceipt` rows for `x.near` intact.
3. A different party later re-registers `x.near` (e.g. via the `near` registrar creating the sub-account and adding their own key) — nothing in `action_create_account` (runtime/runtime/src/actions.rs:167-210) or `check_account_existence` checks for or blocks residual postponed-receipt state for the name being (re)created. [8](#0-7) 
4. When the attacker's originally pending call finally completes (fully under the attacker's control, since it's the attacker's own contract chain), a `Data` receipt with the matching `data_id` is delivered. `process_receipt` finds the stale `PostponedReceiptId`, decrements `PendingDataCount` to 0, loads the stale `PostponedReceipt`, and executes it against the account currently occupying `x.near` — i.e. the new owner's account — inserting the attacker's key (or staking, deleting a key, etc.) without the new owner's consent.

No existing signature, nonce, access-key, or action-validation check intercepts this, because the resurrected receipt was already fully validated and authorized at *creation* time (against the old account); none of that authorization is re-checked against the account that currently exists at that name.

### Impact Explanation
This is an authorization-escalation vector against the new legitimate owner of a re-registered account name: a self-authorized administrative action (most severely `AddKey` with `FullAccess`) from a stale postponed receipt executes against the new account without the new owner's consent, letting the old owner gain persistent control (and subsequently steal any funds/assets the new owner deposits into that account). This matches the "authorization escalation across accounts" / "theft of user funds" bounty category.

### Likelihood Explanation
Exploitability requires: (a) the attacker owning `x.near` deliberately engineers a self-addressed pending callback receipt before deleting the account (fully attacker-controlled, no special privilege needed — any account owner can do this with their own contract), and (b) the same account name being re-registered by an unrelated third party before the attacker's own pending call resolves (a timing race that the attacker can influence, since the pending call's resolution point is driven by the attacker's own contract/call chain, which they can delay or trigger at will). Because NEAR explicitly allows deleted account names to be freely re-registered, and there is no cooldown, incarnation counter, or cleanup of postponed-receipt bookkeeping on deletion, this is fully reachable by an ordinary account owner without validator, network, or leaked-key access. It is repeatable per account name.

### Recommendation
When an account is deleted, `remove_account` (or `action_delete_account`) should also iterate and remove all `PostponedReceiptId`, `PendingDataCount`, and `PostponedReceipt` trie entries keyed by that `account_id`, mirroring the access-key/contract-data cleanup already done. Alternately/additionally, `process_receipt`'s Data-receipt resolution path should verify the receiver account still corresponds to the same "incarnation" (e.g. by refusing to resolve/execute a postponed receipt whose receiver account did not exist continuously since the receipt was postponed, or by failing/refunding it instead of executing it once the account has been deleted and recreated).

### Proof of Concept
Extend the apply-path test harness (as used in `runtime/runtime/src/tests/apply.rs`, e.g. alongside `test_function_call_after_same_chunk_delete_recreate_resolves_fresh_code` and `test_promise_input_size_limit_exceeded_fails_and_cleans_up`) with:
1. Set up account `x.near` with keypair A. Submit a receipt to `x.near` with `predecessor_id = x.near`, `input_data_ids = [data_id]`, actions `[AddKey(pubkey_B_attacker)]` — this becomes a postponed receipt (`PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` all keyed by `x.near`).
2. Apply a `DeleteAccount` receipt for `x.near` (self-authorized, beneficiary elsewhere) in the same or a later chunk; assert the account record is gone but `get_postponed_receipt(state, "x.near", receipt_id)` still returns `Some`.
3. Apply a `CreateAccount` + `AddKey(pubkey_C_new_owner)` receipt for `x.near` from a different predecessor (simulating a new, unrelated owner registering the name); assert the account exists with only keypair C.
4. Deliver the `Data` receipt for `data_id` to `x.near`.
5. Assert (this should fail, proving the vulnerability) that keypair B (the attacker's stale key) is now present on the account, or that some self-authorized action executed without keypair C's/owner C's consent — i.e. `get_access_key(state, "x.near", pubkey_B)` returns `Some` despite pubkey_B never being authorized by the account's second (legitimate) owner.

    if account_id.is_top_level() {
        if account_id.len() < account_creation_config.min_allowed_top_level_account_length as usize
            && predecessor_id != &account_creation_config.registrar_account_id
        {
            // A short top-level account ID can only be created registrar account.
            result.result = Err(ActionErrorKind::CreateAccountOnlyByRegistrar {
                account_id: account_id.clone(),
                registrar_account_id: account_creation_config.registrar_account_id.clone(),
                predecessor_id: predecessor_id.clone(),
            }
            .into());
            return;
        } else {
            // OK: Valid top-level Account ID
        }
    } else if !account_id.is_sub_account_of(predecessor_id) {
        // The sub-account can only be created by its root account. E.g. `alice.near` only by `near`
        result.result = Err(ActionErrorKind::CreateAccountNotAllowed {
            account_id: account_id.clone(),
            predecessor_id: predecessor_id.clone(),
        }
        .into());
        return;
    } else {
        // OK: Valid sub-account ID by proper predecessor.
    }

    *actor_id = account_id.clone();
    *account = Some(Account::new(
        Balance::ZERO,
        Balance::ZERO,
        AccountContract::None,
        fee_config.storage_usage_config.num_bytes_account,
    ));

pub(crate) fn action_delete_account(
    state_update: &mut TrieUpdate,
    account: &mut Option<Account>,
    actor_id: &mut AccountId,
    receipt: &Receipt,
    result: &mut ActionResult,
    account_id: &AccountId,
    delete_account: &DeleteAccountAction,
    config: &RuntimeConfig,
    current_protocol_version: ProtocolVersion,
) -> Result<(), StorageError> {
    let account_ref = account.as_ref().unwrap();
    let account_storage_usage = if ProtocolFeature::FixDeleteAccountGlobalContractStorageUsage
        .enabled(current_protocol_version)
    {
        let contract_storage = get_contract_storage_usage(state_update, account_id, account_ref)?;
        account_ref.storage_usage().saturating_sub(contract_storage)
    } else {
        // Legacy behavior: only subtracts local contract code, misses the
        // global contract identifier overhead.
        let account_storage_usage = account_ref.storage_usage();
        let code_len = get_code_len_or_default(
            state_update,
            account_id.clone(),
            account_ref.local_contract_hash().unwrap_or_default(),
        )?;
        debug_assert!(
            code_len == 0 || account_storage_usage > code_len,
            "account storage usage should be larger than code size. storage usage: {}, code size: {}",
            account_storage_usage,
            code_len
        );
        account_storage_usage.saturating_sub(code_len)
    };
    if account_storage_usage > Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE {
        result.result =
            Err(ActionErrorKind::DeleteAccountWithLargeState { account_id: account_id.clone() }
                .into());
        return Ok(());
    }
