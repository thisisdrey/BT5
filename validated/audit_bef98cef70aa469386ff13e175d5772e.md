### Title
Stale mempool signature-verification cache lets an account-permission change ("2FA equivalent") be bypassed when the transaction is later re-applied from a block - ([File: framework/src/main/java/org/tron/core/db/Manager.java])

### Summary
The Redmine CVE describes existing authenticated sessions continuing to be honored after a security-relevant account change (enabling 2FA) that should have invalidated them. The java-tron analog is the `TransactionCapsule.isVerified` cache combined with `Manager#getVerifyTxs`: a transaction admitted to the pending pool is signature/permission-checked once and its `isVerified` flag is cached, but that cached "already authorized" result can be re-used later without re-checking the account's permission state, even after the account has changed its owner/active keys via `AccountPermissionUpdateContract`.

### Finding Description
`TransactionCapsule.validateSignature`/`validatePubSignature` only run the actual `checkPermission` + `checkWeight` logic the first time; once `isVerified` is `true` the check is skipped on every subsequent call: [1](#0-0) 

`Manager#getVerifyTxs` is the mechanism that decides, when a new block is received, which of its transactions still need full re-validation. For every transaction already sitting in `pendingTransactions`, it is only forced to go through full validation if its owner address is flagged as a "multi-sign" address; otherwise, if the block's copy of the transaction has an identical signature list to the pooled copy, the block's copy is simply marked `capsule.setVerified(true)` and skips signature/permission re-checking entirely: [2](#0-1) 

This shortcut assumes that "same signature bytes as what I already verified" implies "still authorized," which is false whenever the owner account's `AccountPermissionUpdateContract` has changed the owner/active permission (removed a key, lowered its weight, or changed the threshold) between the time the transaction was admitted to the pool and the time the block containing it is processed. The actuator itself performs no linkage to pending-pool transactions when permissions are rewritten: [3](#0-2) 

Notably, the codebase already recognizes and defends against exactly this bug class in one place — `switchFork` explicitly clears the cached verification flag before re-applying a fork branch, with a comment stating the exact same root cause ("account permissions may have changed, so a cached signature-verification result is no longer trustworthy"): [4](#0-3) 

That fix, however, only covers the fork-switch path (`applyBlock` during `switchFork`). It does not cover `getVerifyTxs`, which is the normal-path optimization used to decide which pooled transactions can skip re-verification when a regular new block arrives. Because `getVerifyTxs` gates full re-validation on `isMultiSignTransaction`/address tracking rather than on "did this account's permission change since the transaction was pooled," a non-multisig-flagged transaction that becomes unauthorized due to an intervening `AccountPermissionUpdateContract` can still be accepted as verified purely because its signature bytes match what was cached earlier.

### Impact Explanation
If exploitable, this allows a transaction that should have been rejected (because the signing key was removed/reweighted by an `AccountPermissionUpdateContract`) to still execute with its original effect (e.g., a transfer, contract call, or other operation), effectively an unauthorized account operation after the account owner believed they had revoked that key's authority — directly matching the "existing session should have been terminated but wasn't" bug class in the CVE.

### Likelihood Explanation
The scenario requires two transactions from the same account to be sequenced closely (an `AccountPermissionUpdateContract` and a previously-pooled transaction signed under the old key), a condition fully reachable by an ordinary account holder or an attacker who has captured/observed a previously valid but not-yet-mined signed transaction. No special privilege (SR/witness/committee) is required — only that the account being targeted issues a permission update while an old signed transaction is in-flight in the mempool.

### Recommendation
Extend the same defensive pattern already applied in `switchFork` to `getVerifyTxs`/`processBlock`: invalidate (`setVerified(false)`) any pooled transaction whose owner account has had an `AccountPermissionUpdateContract` applied since the transaction was queued, or simply require `getVerifyTxs` to always fully re-validate signature/permission for every transaction rather than trusting byte-identical signatures from the pool.

### Proof of Concept
1. Attacker/account owner signs Transaction T1 (e.g., a transfer) with current owner key K1 and broadcasts it; the node pools T1 and sets `isVerified = true` after successful validation against the current permission.
2. Before T1 is mined, the account owner (or attacker holding K1's old authority) broadcasts an `AccountPermissionUpdateContract` that removes K1 from the owner permission (e.g., because K1 is believed compromised) — validated and executed via `AccountPermissionUpdateActuator.execute`.
3. A later block arrives containing T1 with the exact same signature bytes as the pooled copy. Because T1's owner address was never marked in `multiAddresses` (not itself a multisig transaction) and the signature bytes are identical, `Manager#getVerifyTxs` marks the incoming copy `setVerified(true)` and skips re-checking permission/weight, so T1 executes even though K1 is no longer part of the owner's active permission set.   public boolean validatePubSignature(AccountStore accountStore,
      DynamicPropertiesStore dynamicPropertiesStore)
      throws ValidateSignatureException {
    if (!isVerified) {
      if (this.transaction.getSignatureCount() <= 0
              || this.transaction.getRawData().getContractCount() <= 0) {
        throw new ValidateSignatureException("miss sig or contract");
      }
      if (this.transaction.getSignatureCount() > dynamicPropertiesStore
              .getTotalSignNum()) {
        throw new ValidateSignatureException("too many signatures");
      }

      byte[] hash = getTransactionId().getBytes();

      long startNs = System.nanoTime();
      try {
        if (!validateSignature(this.transaction, hash, accountStore, dynamicPropertiesStore)) {
          isVerified = false;
          throw new ValidateSignatureException("sig error");
        }
      } catch (SignatureException | PermissionException | SignatureFormatException e) {
        isVerified = false;
        throw new ValidateSignatureException(e.getMessage());
      } finally {
        logSlowSigVerify(startNs);
      }
      isVerified = true;
    }
    return true;
  }

  private boolean isSameSig(TransactionCapsule tx1, TransactionCapsule tx2) {
    if (tx1 == null || tx2 == null) {
      return false;
    }

    if (tx1.getInstance().getSignatureCount() != tx2.getInstance().getSignatureCount()) {
      return false;
    }

    boolean flag = true;
    for (int i = 0; i < tx1.getInstance().getSignatureCount(); i++) {
      ByteString sig1 = tx1.getInstance().getSignature(i);
      ByteString sig2 = tx2.getInstance().getSignature(i);
      if (!sig1.equals(sig2)) {
        flag = false;
        break;
      }
    }

    return flag;
  }

  public List<TransactionCapsule> getVerifyTxs(BlockCapsule block) {

    if (pendingTransactions.size() == 0) {
      return block.getTransactions();
    }

    List<TransactionCapsule> txs = new ArrayList<>();
    Map<String, TransactionCapsule> txMap = new HashMap<>();
    Set<String> multiAddresses = new HashSet<>(ownerAddressSet);

    pendingTransactions.forEach(capsule -> {
      String txId = Hex.toHexString(capsule.getTransactionId().getBytes());
      if (isMultiSignTransaction(capsule.getInstance())) {
        String address = Hex.toHexString(capsule.getOwnerAddress());
        multiAddresses.add(address);
      } else {
        txMap.put(txId, capsule);
      }
    });

    block.getTransactions().forEach(capsule -> {
      String address = Hex.toHexString(capsule.getOwnerAddress());
      String txId = Hex.toHexString(capsule.getTransactionId().getBytes());
      if (multiAddresses.contains(address) || !isSameSig(capsule, txMap.get(txId))) {
        txs.add(capsule);
      } else {
        capsule.setVerified(true);
      }
    });

    return txs;
  }
