### Title
`DisconnectGitAlternates` unconditionally hard-fails on an externally-influenced alternates file, permanently blocking pool disconnection and housekeeping for the affected repository - ([File: internal/git/objectpool/disconnect.go])

### Summary
The C4 finding is a general "unchecked-list-item" DoS pattern: an operation iterates/acts on an externally controlled list (reward tokens) and performs an unconditional action per item that can hard-revert on a specific edge-case value, permanently blocking the whole workflow until the external list changes. In gitaly, the closest reachable analog is `objectpool.Disconnect`, which unconditionally inspects the repository's `objects/info/alternates` file — content that is not strictly gitaly-internal-only, since it lives inside the repository working tree and can be affected by repository import/restore operations — and returns a hard, non-recoverable error for any alternates state other than "no alternates" or "exactly one valid alternates entry."

### Finding Description
`objectpool.Disconnect` reads the repository's alternates file via `stats.AlternatesInfoForRepository` and then unconditionally enforces strict invariants on its contents: [1](#0-0) 

If more than one alternate object directory line is present, it returns a hard `errors.New("multiple alternate object directories")`: [2](#0-1) 

If the single alternate path does not exist on disk, or exists but is not a directory, it also returns a hard error: [3](#0-2) 

These are exactly the conditions exercised in the test suite (`multiple Git alternates`, `Git alternate does not exist`), both of which produce unrecoverable errors from `Disconnect`: [4](#0-3) 

The RPC entrypoint, `ObjectPoolService.DisconnectGitAlternates`, does not perform any pre-validation or self-healing before calling `Disconnect` — it simply forwards whatever error comes back as an internal error: [5](#0-4) 

Unlike the C4 report's "arbitrary reward token list," gitaly's `objects/info/alternates` file is normally written by `objectpool.Link`, which always truncates and writes exactly one relative path: [6](#0-5) 

so under normal operation the file should never contain more than one entry. However, this file lives inside the repository directory tree, and the code comment on `DisconnectGitAlternates` itself acknowledges the repository can end up in "a broken state" requiring administrator intervention if crashes or unexpected states occur: [7](#0-6) 

Because `Disconnect` treats any deviation from the single-valid-entry invariant as a hard, non-retriable failure (rather than attempting to self-heal, e.g., by keeping only the first valid entry or treating unreadable/missing directories gracefully), any repository state where the alternates file acquires more than one line, or a line whose target became unreachable (e.g., due to a partially failed prior migration, a crash between writing/removing the file, or any process — including e.g. an import/restore flow that has file-system access to a repository — writing extra lines) will cause every future `DisconnectGitAlternates` call, and by extension any housekeeping/pool operations that depend on being able to disconnect a repository from its pool, to fail indefinitely.

### Impact Explanation
`DisconnectGitAlternates` is used as a precondition for repository housekeeping and object pool lifecycle operations. If a repository is left in (or placed into) a state with a malformed alternates file, all subsequent disconnect/housekeeping attempts against that repository fail deterministically and permanently with an internal error, with no automatic recovery path — mirroring the reward-token DoS in the original finding where the availability of a base function (reward retrieval / here, repository disconnect and downstream housekeeping) becomes unavailable until an administrator manually repairs the file, exactly as documented in the RPC's own doc comment.

### Likelihood Explanation
Likelihood is comparatively low because, under intended operation, `objectpool.Link` is the only code path shown that writes the alternates file and it always writes a single valid entry, so the double-entry/non-existent-path state is not trivially triggerable purely through a single ordinary push or fetch. The condition instead relies on the repository's alternates file being placed into an unexpected state (e.g. through a crash window, a partial/failed migration, or some other flow able to leave file-system artifacts under the repository directory), similar to how the C4 finding depended on the "low probability" event of a reward token that reverts on zero amount ending up in the external, uncontrolled list. The report's own comment ("If we are very unlucky") independently corroborates that gitaly's maintainers consider this an already-recognized, non-negligible risk of unrecoverable state for this exact code path.

### Recommendation
Harden `objectpool.Disconnect` so it does not treat every alternates-file anomaly as a fatal, unrecoverable error:
- When multiple alternate object directories are found, consider deterministically selecting/repairing to the single expected pool alternate (or safely ignoring extras) rather than aborting entirely.
- When the alternate path does not exist, consider treating this the same as "no alternates" (nothing to disconnect) rather than failing, since a missing alternate target means there is nothing to migrate.
- More generally, ensure that an externally-influenceable or partially-corrupted piece of repository state (the alternates file) cannot leave the RPC in a permanently failing condition; add a repair/no-op fallback path and surface a distinguishable, retriable error instead of a blanket internal error.

### Proof of Concept
1. Create a repository whose `objects/info/alternates` file contains two lines (e.g. `/foo/bar\n/qux/baz\n`), as exercised by the existing test case: [8](#0-7) 
2. Call the `DisconnectGitAlternates` RPC against this repository.
3. Observe that `Disconnect` returns `errors.New("multiple alternate object directories")` via `internal/git/objectpool/disconnect.go` lines 69-73, which the RPC handler wraps as `structerr.NewInternal`, and that every subsequent call to `DisconnectGitAlternates` against this repository fails identically and permanently until the alternates file is manually corrected on disk — there is no code path in `Disconnect` that self-heals or falls back.

**Uncertainty**: I was unable to trace, within the available index, a concrete ordinary-user-reachable RPC or import/fork flow that writes more than one line (or a dangling line) into `objects/info/alternates` outside of `objectpool.Link` (which always writes exactly one valid entry). The severity of this finding therefore depends on whether such a state is reachable through some other flow (e.g., partial/interrupted housekeeping, repository restore, or a race condition) that is not fully visible in the indexed code; a full audit of all write paths to `objects/info/alternates` and of repository-restore/import code would be needed to confirm end-to-end reachability from an ordinary user action.

```go
func (s *server) DisconnectGitAlternates(ctx context.Context, req *gitalypb.DisconnectGitAlternatesRequest) (*gitalypb.DisconnectGitAlternatesResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	repo := s.localRepoFactory.Build(repository)

	storageRoot, err := s.locator.GetStorageByName(ctx, repo.GetStorageName())
	if err != nil {
		return nil, fmt.Errorf("storage by name: %w", err)
	}

	f := storage.NewNoopFS(storageRoot)
	if tx := storage.ExtractTransaction(ctx); tx != nil {
		f = tx.FS()
	}

	if err := objectpool.Disconnect(ctx, f, repo, s.logger, s.txManager); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	return &gitalypb.DisconnectGitAlternatesResponse{}, nil
```
