Based on my investigation, I found a concrete analog in the `BatchValidateSign` precompiled contract logic that matches the CVE's bug class: using an attacker-controlled length/offset field to size an allocation and index a buffer before validating it against the actual data bounds.

### Title
Unvalidated array length in BatchValidateSign precompile permits oversized allocation / out-of-bounds indexing from untrusted calldata - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`PrecompiledContracts.BatchValidateSign.doExecute()` reads a signature-array length directly from the caller-supplied calldata and only bounds-checks it against `MAX_SIZE` when the `allowTvmSelfdestructRestriction()` hard-fork switch is active; when that path is not taken, `extractBytesArray()` uses the unvalidated length to both allocate a `byte[len][]` and to index further into the `words` array, mirroring the FF-A bug class of trusting an offset/size field from a message before validating it.

### Finding Description
In `doExecute()`, the code does: [1](#0-0) 

The `MAX_SIZE` guard for `sigArraySize`/`addrArraySize` is only executed inside the `if (VMConfig.allowTvmSelfdestructRestriction())` block. The subsequent ternary chooses `extractSigArray` (guarded) or `extractBytesArray` (unguarded) — but the unguarded `extractBytesArray` path is reachable whenever that specific hard-fork proposal is not (yet) active for the node's configured chain, since it is one of many independently-toggled `VMConfig` allow-flags. Inside `extractBytesArray`: [2](#0-1) 

`len` is taken straight from `words[offset].intValueSafe()` with no upper bound, and is used to both allocate `new byte[len][]` and to index `words[offset + i + 1]` for `i` in `[0, len)`, without checking `offset + i + 1 < words.length`. This is structurally the same defect described in the CVE: an offset/size field parsed from an untrusted buffer is used directly for allocation and to compute follow-on read offsets without validating it fits inside the actual data before use, which can drive an out-of-bounds read (`ArrayIndexOutOfBoundsException` inside a VM opcode execution path) or an oversized allocation (`OutOfMemoryError`) purely from data supplied in a `TriggerSmartContract`/`CREATE` transaction's calldata to this precompile.

### Impact Explanation
Any unprivileged account can invoke this precompile by pointing a smart-contract call at its fixed address with crafted calldata. If the vulnerable flag combination is active on a network, a single transaction can force an oversized array allocation attempt or an unhandled indexing exception during TVM execution of a precompiled contract, which — depending on how far up the call stack the resulting `Error`/`RuntimeException` propagates before being caught — can either simply revert the call or, in the `OutOfMemoryError` case, destabilize the executing node process, since `OutOfMemoryError` is not a checked `Exception` and existing catch blocks in this class only catch `Exception`/`Throwable` explicitly in some sibling contracts but not verified for this one.

### Likelihood Explanation
Reaching `doExecute()` requires only building calldata for the `BatchValidateSign` precompile, something any address can do without special privileges by broadcasting a normal `TriggerSmartContract`; the length field is entirely attacker-controlled ABI data, so likelihood of triggering the malformed-length condition is high whenever the code path lacking the `MAX_SIZE` guard is exercised.

### Recommendation
Move the `sigArraySize`/`addrArraySize` (or an equivalent) bound check outside the `allowTvmSelfdestructRestriction()` conditional so it unconditionally applies to both `extractSigArray` and `extractBytesArray`, and additionally validate inside `extractBytesArray`/`extractSigArray`/`extractBytes32Array` that `offset + i + 1` (and any derived `bytesOffset`) stays within `words.length` before indexing, consistent with the existing `extractBytes` bound style used elsewhere (e.g. `ContractEventParser.subBytes`) at [3](#0-2) .

### Proof of Concept
Craft calldata for `BatchValidateSign(bytes32,bytes[],bytes32[])` where the ABI-encoded length word for the `bytes[]` signatures array is set to a very large value (e.g. `0x7fffffff`) while the actual `data` payload is short. When the network configuration does not have `allowTvmSelfdestructRestriction()` enabled, `doExecute()` calls `extractBytesArray(words, offset, data)`, which reads this attacker-controlled `len`, attempts `new byte[len][]`, and/or indexes `words[offset + i + 1]` beyond `words.length`, triggering `OutOfMemoryError`/`ArrayIndexOutOfBoundsException` during execution of the transaction.

**Caveat**: I was unable to confirm, within the available tooling, exactly how far up the actuator/VM call stack such an `Error`/`RuntimeException` propagates before being caught (i.e., whether it degrades to a simple reverted transaction versus a genuine node crash), and whether `allowTvmSelfdestructRestriction()` is already permanently enabled on mainnet at the current block height. This affects whether the impact should be classified as a real node-crash/DoS or merely a reverted call; confirming the current hard-fork flag state and the outer exception-handling wrapper for this precompile would be needed to finalize severity with certainty.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }

  protected static byte[] subBytes(byte[] src, int start, int length) {

      throw new OutputLengthException(

    byte[] dst = new byte[length];
