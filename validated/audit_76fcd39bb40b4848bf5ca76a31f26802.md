### Title
Lockfile merge driver `bazel-lockfile-merge.jq` lets a later-processed input silently overwrite trusted `registryFileHashes`/`selectedYankedVersions` entries during automatic `MODULE.bazel.lock` merges - (File: `scripts/bazel-lockfile-merge.jq`)

### Summary
The `defu` bug class is: a generic object-merge utility copies an untrusted object's keys over trusted defaults without any conflict/provenance check, letting attacker-controlled input silently clobber legitimate values. Bazel ships an analogous merge utility, `scripts/bazel-lockfile-merge.jq`, registered as the git merge driver for `MODULE.bazel.lock` via `.gitattributes`, so it runs automatically on every `git merge`/rebase/cherry-pick touching that file — including CI merges of pull requests from untrusted contributors/branches. [1](#0-0) [3](#0-2) 

### Finding Description
`shallow_merge(f)` builds an array of the per-lockfile sub-objects (e.g., each side's `registryFileHashes` map), deduplicates *whole* sub-objects that are byte-identical (`stable_unique`), and then folds them together with jq's `+` (add), which is right-biased: for any key present in more than one distinct sub-object, the value from the object that appears **last** in the array wins. [4](#0-3) 

The whole-object dedup only protects a key when an entire side's map is completely unmodified compared to the base (so it is byte-identical and gets removed by `stable_unique`). If two sides both modify the *same* map (even in unrelated, non-conflicting entries), their sub-objects are no longer identical, so `stable_unique` does nothing, and the later side's value for any overlapping key silently wins — with no diff/conflict marker, no error, and no indication to the user that a value was overwritten. [5](#0-4) 

This is the direct structural analog of the `defu` root cause: a merge implementation that combines trusted defaults (`registryFileHashes` pins for BCR registry files, `selectedYankedVersions`) with an untrusted operand using naive last-wins semantics, so a value contributed by the untrusted side overrides the value from the trusted side whenever both sides happen to touch the same key. `registryFileHashes` is documented as the integrity-pinning mechanism for registry-file content used to look up cached registry files before (re)downloading them. [6](#0-5) 

### Impact Explanation
An unprivileged contributor who can get a branch merged by CI (e.g., a PR that also touches `MODULE.bazel.lock`, matching the allowed "attacker publishes/serves content a victim's build consumes via an untrusted branch CI builds" threat model) controls one operand of the 3-way merge. If their branch's `MODULE.bazel.lock` entry for an existing registry URL differs from the trusted value (whether accidentally from a stale local resolution or deliberately crafted), and their side is processed after the trusted side in the merge driver's input ordering, their `registryFileHashes` value overwrites the previously-recorded, trusted hash with no warning. Since this hash is what Bazel consults to accept/skip re-fetching registry files from the repository cache, corrupting it undermines the deterministic-resolution/pinning guarantee that the lockfile exists to provide. The same last-wins clobbering applies to `selectedYankedVersions`, which could let an attacker's merge silently reintroduce/hide yanked-version acceptance state.

### Likelihood Explanation
Requires no special access: the merge driver runs automatically for any git merge touching `MODULE.bazel.lock`, which is common in CI-driven PR merges. The scenario needing "both sides modify the same map, non-identically" is realistic in projects with frequent bzlmod dependency churn, especially since `bazel mod deps --lockfile_mode=refresh` regularly updates `registryFileHashes`/`selectedYankedVersions`, making concurrent, partially-overlapping modifications plausible across parallel branches.

### Recommendation
Change `shallow_merge` to detect per-key conflicts (a key present with different values in more than one distinct, non-base sub-object) and either fail the merge with a conflict error for that key, or require it to be resolved against the base value explicitly, rather than silently taking the last value in array order. At minimum, treat `registryFileHashes` conflicts as hard errors so integrity-pinning data is never silently overwritten by merge order.

### Proof of Concept
Using the existing test harness pattern in `scripts/bazel_lockfile_merge_test.sh`, construct `base`, `left`, `right` `MODULE.bazel.lock` JSON files where both `left` and `right` modify (differently) the hash for the *same* existing `registryFileHashes` URL key (unlike the existing `test_synthetic_merge`, which only adds distinct new keys per side and thus never exercises this conflict path). Run:
```
jq -s -f scripts/bazel-lockfile-merge.jq base left right
```
Observe the merged `registryFileHashes[url]` equals `right`'s value, silently discarding `left`'s (or the trusted) value, with no conflict indication — demonstrating the last-wins clobber analogous to `defu`'s unguarded `Object.assign`/spread merge overwrite. [7](#0-6)

```text
# Like unique, but preserves the order of the first occurrence of each element.
def stable_unique:
  reduce .[] as $item ([]; if index($item) == null then . + [$item] else . end);

# Given an array of objects, shallowly merges the result of applying f to each
# object into a single object, with a few special properties:
# 1. Values are uniquified before merging and then merged with last-wins
#    semantics. Assuming that the first value is the base, this ensures that
#    later occurrences of the base value do not override other values. For
#    example, when this is called with B A1 A2 and A1 contains changes to a
#    field but A2 does not (compared to B), the changes in A1 will be preserved.
# 2. Object keys on the top level are sorted lexicographically after merging,
#    but are additionally split on ":". This ensures that module extension IDs,
#    which start with labels, sort as strings in the same way as they due as
#    structured objects in Bazel (that is, //python/extensions:python.bzl
#    sorts before //python/extensions/private:internal_deps.bzl).
def shallow_merge(f):
  map(f) | stable_unique | add | to_entries | sort_by(.key | split(":")) | from_entries;
```

### Registry File Hashes {#registry-file-hashes}

The `registryFileHashes` section contains the hashes of all files from
remote registries accessed during module resolution. Since the resolution
algorithm is fully deterministic when given the same inputs and all remote
inputs are hashed, this ensures a fully reproducible resolution result while
avoiding excessive duplication of remote information in the lockfile. Note that

the example). This inherently mutable information can be updated via

Bazel uses the hashes from the lockfile to look up registry files in the

resolutions.
