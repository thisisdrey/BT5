### Title
Unbacked-fund creation via missing negative-balance check in `ExchangeCapsule.transaction()` (Bancor-style TRX/TRC10 exchange) - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java`)

### Summary
The PANDORA exploit relies on an AMM pool's reserve accounting becoming desynchronized from real token balances after a trade, letting the attacker compute and extract more value than the pool actually holds. Java-tron's built-in Bancor-style `Exchange` (a first-class blockchain feature reachable from any signed transaction via `ExchangeTransactionContract`) has an analogous bug: the pool-balance update in `ExchangeCapsule.transaction()` only validates that the resulting reserve is non-negative when the "hardened" calculation mode is active. In the default (non-hardened) path, the new first/second token reserve is allowed to go negative, while the actuator still unconditionally credits the trader's real account balance/asset with the full computed `anotherTokenQuant`. This creates value that is not backed by the exchange's actual holdings — the same "phantom/unbacked balance" impact class as the PANDORA case.

### Finding Description
`ExchangeCapsule.transaction()` computes the reserve update after a trade: [1](#0-0) 

Only `if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0))` throws; when `hardenedCalc` is `false` (the non-hardened/legacy path selected by `dynamicStore.allowHardenExchangeCalculation()` being off, see `AbstractExchangeActuator.allowHarden()`), the negative-balance guard is skipped entirely: [2](#0-1) 

The buy amount is derived from a floating-point Bancor formula (`ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply`, using `double`/`Maths.pow`), which is inherently imprecise: [3](#0-2) 

`ExchangeTransactionActuator.execute()` calls `exchangeCapsule.transaction(...)` and then unconditionally pays the computed `anotherTokenQuant` into the caller's real TRX balance or TRC10 asset balance, regardless of whether the exchange's own reserve went negative: [4](#0-3) 

Because the trader's payout (`accountCapsule.setBalance`/`addAssetAmountV2`) always succeeds and is not conditioned on the pool's reserve remaining ≥ 0 in non-hardened mode, a specially crafted `quant`/near-empty-reserve trade can drive `firstTokenBalance`/`secondTokenBalance` negative while the trader still receives real, spendable TRX/TRC10 tokens that the pool never actually held — i.e., unbacked funds are created out of thin air, mirroring the PANDORA reserve-desync exploit pattern (attacker manipulates the pool's internal reserve accounting to extract more value than backed by the pool's real assets).

### Impact Explanation
A successful trade against a thinly-funded or precision-edge-case exchange pool can push the pool's on-chain reserve counters negative while crediting the attacker's account with real TRX or TRC10 tokens. This is a direct "theft of funds / unbacked balance" outcome: value is created without any backing, and subsequent trades against the corrupted (negative) reserve further destabilize pricing, letting an attacker repeatedly siphon value from the pool and from other traders/liquidity providers.

### Likelihood Explanation
Reachable by any unprivileged account that submits a normal, signed `ExchangeTransactionContract` transaction against an existing `Exchange` pool — no special privilege, SR/witness role, or off-chain condition is required. The precondition is that the chain is operating with `allowHardenExchangeCalculation` disabled (the legacy, non-hardened math path), which is the historical/default behavior this hardened path was clearly added to remedy (the presence of `SafeExchangeProcessor`, `StrictMathWrapper`, and `hardenedExecuteOverflowThrowsArithmeticException` test in this codebase indicates the hardened path is an opt-in mitigation, not universally enabled). An attacker can select or wait for a low-liquidity exchange and craft a `quant`/`expected` pair that pushes the floating-point Bancor calculation to yield a `buyTokenQuant` exceeding the counter-token reserve.

### Recommendation
Enforce the non-negative reserve invariant unconditionally in `ExchangeCapsule.transaction()`, not only when `hardenedCalc` is true, or force `allowHardenExchangeCalculation` to always be true regardless of the dynamic property/proposal state. Additionally, replace/complement the double-based Bancor math (`ExchangeProcessor`) with the already-implemented `SafeExchangeProcessor`/`BigDecimal` computation by default, and reject any trade in `ExchangeTransactionActuator.validate()`/`execute()` whose resulting reserve would be ≤ 0.

### Proof of Concept
1. Create (or locate) an `Exchange` pool with a very small `secondTokenBalance` (e.g., via `ExchangeCreateActuator` with minimal token amounts) while `allowHardenExchangeCalculation` is not enabled — see the default (non-hardened) computation path taken in [5](#0-4) .
2. Submit an `ExchangeTransactionContract` selling `firstTokenID` with a `tokenQuant` engineered so that the double-precision Bancor formula in `ExchangeProcessor.exchange()` returns a `buyTokenQuant` greater than the current `secondTokenBalance`.
3. `ExchangeTransactionActuator.execute()` calls `exchangeCapsule.transaction(...)`, which (since `hardenedCalc` is false) skips the negative-balance check and stores `newSecondTokenBalance < 0` into the `ExchangeCapsule`, while still crediting the attacker's account with the full `anotherTokenQuant` via `addAssetAmountV2`/`setBalance` at lines [6](#0-5) .
4. The attacker now holds real, transferable TRX/TRC10 balance that was never backed by the pool's actual reserves, and the pool's persisted reserve is negative, corrupting all future pricing for that exchange.

Note: I was unable to directly confirm from the index the default on-chain value/activation status of the `allowHardenExchangeCalculation` proposal (the exact default-assignment code in `DynamicPropertiesStore.java` was not found via search), so whether this legacy/vulnerable path is currently active on mainnet without a committee proposal vote could not be fully verified from the available index and would need confirmation in a full checkout.

    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;

          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)

    }

      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
