### Title
Value sent via CALL to a precompiled contract address is permanently locked with no recovery mechanism - (File: `actuator/src/main/java/org/tron/core/vm/program/Program.java`)

### Summary
When TVM bytecode executes a `CALL`/`CALLTOKEN` opcode with a non-zero value against one of the reserved precompiled-contract addresses (e.g. `0x01`–`0x0a`, `0x100001`–`0x10000b`, etc.), `Program.callToPrecompiledAddress` unconditionally transfers the callvalue (or TRC10 token value) to that address before invoking the precompile logic or even checking whether enough energy was supplied. None of the `PrecompiledContracts.PrecompiledContract` implementations contain logic to spend, forward, or refund a received balance, and these addresses have no corresponding private key, so any TRX or TRC10 tokens transferred to them become permanently unrecoverable. This mirrors the RocketDAO finding where tribute funds sent along with a challenge become "locked forever in the … contract" with "no means to recover the funds."

### Finding Description
`Program.callToPrecompiledAddress` performs the balance/token transfer to the `contextAddress` (the precompile's fixed address) unconditionally when `endowment > 0`, explicitly noting in a comment that this transfer is irreversible: [1](#0-0) 

This happens *before* the energy sufficiency check: [2](#0-1) 

So even if the precompile call subsequently fails (insufficient energy, or the precompile execution itself fails/reverts), the value has already been debited from the caller and credited to the precompile address, and that debit/credit is not rolled back.

The list of the fixed, keyless precompile addresses (`ecRecover`, `sha256`, `ripempd160`, `identity`, `modExp`, `altBN128*`, `batchValidateSign`, vote/freeze-related precompiles, etc.) is defined in `PrecompiledContracts`: [3](#0-2) 

None of these precompile implementations use, transfer onward, or refund the value that landed on their address as part of the call — their `execute(byte[] data)` methods only compute/return data. There is no `actuator`, no owner key, and no protocol-level "withdraw" path for a balance credited to a precompile address, so any TRX/TRC10 sent there is permanently stranded, analogous to the tribute funds stuck in `RocketDAONodeTrustedActions`.

### Impact Explanation
This causes permanent freezing of funds: any TRX or TRC10 tokens sent as `value`/`tokenValue` in a `CALL`/`CALLCODE`/`CALLTOKEN` targeting a precompiled address become unspendable and unrecoverable forever, since the destination address is not a real EOA/contract with logic or a private key. A contract author or another contract that inadvertently (or an attacker deliberately, e.g. to grief a caller or hide funds it never intends to return) forwards value to these hard-coded addresses causes an irrecoverable balance loss for the sender.

### Likelihood Explanation
The path is reachable by any unprivileged user: deploying a contract that performs `<address>.call{value: x}(...)` (or the low-level `CALL`/`CALLTOKEN` opcodes) against one of the reserved precompile addresses, or a contract that forwards `msg.value` blindly to a caller-supplied target address that happens to be a precompile address, will trigger this behavior on every invocation. No special privilege, witness/committee role, or protocol misconfiguration is required — solely a standard `TriggerSmartContract`/contract-to-contract call.

### Recommendation
Reject or refund non-zero `value`/`tokenValue` transfers directed at addresses resolved by `PrecompiledContracts.getContractForAddress` before performing the balance/token debit-credit in `Program.callToPrecompiledAddress`/`callToAddress`, i.e., treat precompiled addresses as non-payable unless a specific precompile is explicitly designed to receive and account for value.

### Proof of Concept
1. Deploy a contract with a function that executes a low-level call carrying value to the fixed precompile address `0x0000000000000000000000000000000000000001` (ecRecover) or any other precompile address, e.g. `address(0x1).call{value: 100}("")`.
2. Trigger this contract via a standard `TriggerSmartContract` transaction with sufficient callvalue and feeLimit.
3. Observe in `Program.callToPrecompiledAddress` (`actuator/src/main/java/org/tron/core/vm/program/Program.java:1712-1732`) that `MUtil.transfer`/token balance mutation executes unconditionally, crediting the precompile's address.
4. Query the account balance at address `0x1` afterward — the balance is present but there is no actuator, precompile logic, or private key capable of spending or withdrawing it, permanently locking the funds.
