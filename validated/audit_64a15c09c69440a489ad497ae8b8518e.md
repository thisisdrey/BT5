### Title
Pyth pull-oracle price updates bundled atomically with market actions (`borrow`, `collateral-add`, `collateral-remove`, `liquidate`) allow unprivileged price-timing arbitrage - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
Zest's market entry points (`borrow`, `collateral-add`, `collateral-remove`, `liquidate`, and their wrappers `supply-collateral-add`, `collateral-remove-redeem`, `liquidate-redeem`) accept an optional `price-feeds` parameter that is a list of raw Pyth VAA update buffers, submitted and verified via `write-feeds`/`write-feed` before the position's health/liquidation math runs, all inside the same public, callable-by-anyone transaction.

### Finding Description
Every hot-path market function begins by pushing caller-supplied Pyth price updates into the oracle before evaluating collateral/debt value: [1](#0-0) 

`write-feeds`/`write-feed` call `pyth-oracle-v4 verify-and-update-price-feeds`, so the price data itself is cryptographically authentic (a real Wormhole-signed Pyth VAA), but *when* and *which* valid VAA to submit is entirely controlled by the caller — this is the pull-oracle pattern from the report: [2](#0-1) 

The only guard on freshness/ordering is `oracle-timestamp-fresh`, which merely requires the submitted publish-time to be `>=` the previously stored timestamp and within `max-staleness` of current block time — it does not restrict updates to once per block, nor does it check that the update is not itself becoming stale relative to the newest available off-chain price: [3](#0-2) [4](#0-3) 

Crucially, unlike the report's target system (which at least gates the update behind `FeatureFlagSupport.ensureExecutorAccess()`), none of Zest's `borrow`/`collateral-add`/`collateral-remove`/`liquidate` functions restrict who may supply `price-feeds` — any `tx-sender`/`contract-caller`, including an attacker's own deployed contract, can submit an update as part of their own trade: [5](#0-4) 

Because Pyth/Hermes continuously produces multiple valid signed VAAs (differing only in monotonically increasing `publish-time`/price) that remain valid to submit as long as they satisfy `ts >= prev` and `delta <= max-staleness`, an attacker controlling their own contract can, in one atomic transaction: (1) call `collateral-add`/`borrow` supplying a Pyth VAA that pushes the oracle to a price favorable for opening/inflating their position, then (2) in the same transaction call `collateral-remove`/`liquidate` (on a victim, or self) supplying a second, later, less-favorable-to-others VAA to close out or liquidate before the "true" current price the rest of the market sees is otherwise reflected on-chain. This sandwich is possible because the protocol updates its cached price precisely at the moment of the caller's choosing rather than continuously/independently of the caller's trade.

### Impact Explanation
An attacker can atomically pick the entry and exit oracle price used to size a borrow, or to trigger/avoid liquidation of a real position, extracting value from the protocol's vaults/collateral or from other borrowers' collateral. This constitutes direct theft of user funds (collateral seized in an unfairly-timed liquidation, or over-borrowing against a manipulated valuation) and, in aggregate, threatens protocol insolvency in the affected vaults — Critical impact.

### Likelihood Explanation
Likelihood is Medium: no special privileges are required (any principal, including the attacker's own contract, can supply `price-feeds`), but the attacker must have a favorable pair of legitimately-signed Pyth VAAs (differing publish times within the staleness window) and must construct/deploy a contract that chains market calls atomically — achievable during periods of price volatility when Hermes has multiple valid recent updates to choose from.

### Recommendation
Restrict who may submit `price-feeds` updates through market entry points to trusted keepers/executors (mirroring the intended `ensureExecutorAccess` pattern), and/or enforce a strict "one price update per oracle key per block" rule combined with rejecting any update whose `publish-time` is not the most recent available, so that a single transaction cannot straddle two different prices for the same asset.

### Proof of Concept
1. Attacker deploys a contract that, within one transaction:
   a. Calls `.v0-4-market collateral-add` with `price-feeds` containing a recent Pyth VAA `V1` that sets a favorable price for the attacker's collateral asset (see `write-feeds` call at `mainnet/contracts/market/v0-4-market.clar:1244`-equivalent for `collateral-add`).
   b. Immediately calls `.v0-4-market liquidate` (or `borrow`) with `price-feeds` containing a second valid, later-timestamped VAA `V2` (satisfying `oracle-timestamp-fresh`'s `ts >= prev` check) that shifts the debt/collateral asset's price to trigger/avoid liquidation thresholds unfavorably for the victim or favorably for the attacker.
2. Because `oracle-timestamp-fresh` only enforces monotonic timestamps and staleness bounds, not "one update per block" or "must be latest known price," both `V1` and `V2` are accepted in the same block/transaction, letting the attacker realize the price differential atomically without market risk.

  (> p u0))

(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
