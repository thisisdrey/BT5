### Title
Missing boundary check on Central Directory field lengths causes buffer over-read when parsing untrusted ZIP/JAR files - (`third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` in ijar's zip reader trusts attacker-controlled 16-bit length fields (`file_name_length`, `extra_field_length`, `file_comment_length`) taken directly from a memory-mapped, untrusted `.zip`/`.jar` file without validating that they stay within the bounds of the mapped input or even within the previously-validated Central Directory region. This mirrors CVE-2017-13722's root cause (a missing boundary check on a length field taken from an untrusted file, leading to an out-of-bounds read), just in ijar's ZIP central-directory parser instead of libXfont's PCF parser.

### Finding Description
`FindZipCentralDirectory` performs only a coarse, whole-region check: [1](#0-0) 
This confirms `central_dir_offset + central_dir_size <= in_length`, i.e. that the *entire* central directory region lies inside the mapped file, but it never validates the internal structure of that region.

`InputZipFile::ProcessCentralDirEntry` then walks that region entry-by-entry using length fields read straight from the (attacker-controlled) bytes, with **no `EnsureRemaining`-style check** (unlike its sibling `ProcessLocalFileEntry`, which does call `EnsureRemaining` before consuming `file_name_length_`/`extra_field_length_`): [2](#0-1) 

Specifically:
- `file_name_length`, `extra_field_length`, and `file_comment_length` are read via `get_u2le(p)` with no upper bound check against the remaining bytes of the central directory or the mapped file.
- `memcpy(filename, p, len)` reads `len` bytes from `p`, where `p` may already point past the mapped file if a prior entry's declared lengths overran the buffer — the destination copy length is clamped by `filename_size`, but the *source* pointer `p` is not validated to be in-bounds.
- The extra-field loop (`while (extra_p != p) { ... get_u2le(extra_p); get_u2le(extra_p); ... get_u8le(extra); ... }`) reads a nested `data_size` and then unconditionally reads 8-byte ZIP64 values via `get_u8le(extra)` without checking `data_size >= 8` or that `extra + 8` stays within `extra_field_length` or the mapped file — this is a second, independent missing boundary check on a nested length-prefixed field, directly analogous to the PCF property-count off-by-one in the CVE.
- Because the file is `mmap`'d (see `MappedInputFile`), reads past the intended region are reads past the actual backing pages once `p`/`extra_p` walks beyond the mapped span, producing the classic "buffer over-read... for information disclosure or a crash" described in CVE-2017-13722.

Compounding entries (crafted `file_name_length`/`extra_field_length`/`file_comment_length` values in one CDH entry) let an attacker walk `p` arbitrarily far past the legitimate central-directory bounds, so that a subsequent `ProcessCentralDirEntry` call dereferences unmapped or unrelated memory.

### Impact Explanation
ijar (and singlejar, which shares similar patterns but does check more places) processes JAR files that can originate from untrusted network content — e.g. jars fetched via `http_jar`/`http_file`/Maven-style external dependencies, or a compromised third-party binary jar committed to an untrusted branch. If Bazel's build (interface-jar generation via `ijar`) runs this parser over such a file, a hostile origin server can craft a ZIP central directory with length fields chosen to walk the read cursor out of the mapped file, causing a crash (worker/action failure, potential DoS of the build) or, on platforms/allocators where the over-read lands on adjacent heap/mapped data, disclosure of adjacent memory contents through error messages or copied filename bytes.

### Likelihood Explanation
The parser is reached by any code path that runs `ijar`/`singlejar`'s zip-consuming tool over an externally-supplied jar (common for Java external dependencies fetched by http-based repository rules). No special privileges are needed beyond the ability to serve or supply the malicious archive; the checksum verification for the *download* (sha256/integrity) does not validate internal ZIP structural invariants, so a byte-for-byte matching malicious archive would still pass integrity checks and reach this vulnerable parser.

### Recommendation
Add explicit bounds checks in `InputZipFile::ProcessCentralDirEntry` (mirroring `EnsureRemaining` used in `ProcessLocalFileEntry`) before consuming `file_name_length`, `extra_field_length`, and `file_comment_length`, and validate each nested extra-field's `data_size` against the declared `extra_field_length` and the remaining central-directory bytes before reading `u4`/`u8` values out of it.

### Proof of Concept
Construct a ZIP file whose End-of-Central-Directory record and size pass `FindZipCentralDirectory`'s aggregate check, but whose first Central Directory Header declares a `file_name_length`/`extra_field_length` that, when added to the entry's start offset, exceeds the actual mapped file length (while the declared `central_dir_size` recorded in the EOCD is crafted to still satisfy `central_dir_offset + central_dir_size <= in_length`, e.g., by under-counting one entry's true consumed size relative to its declared field lengths). Feed this file to `ijar`/`singlejar`'s zip extraction path (e.g. via `bazel build` on a target with `java_import`/`http_jar` using this file) and observe an out-of-bounds read (crash under ASan, or truncated/garbage filename output) originating in `ProcessCentralDirEntry`, reproducible as a `zip_headers_test.cc`/`output_jar_simple_test.cc`-style unit test asserting a crafted CDH with an oversized field length triggers a bounds violation rather than a controlled diagnostic error.
