## Confirmed: `remove_account` does not clean up PromiseYield state

`remove_account` (`core/store/src/utils/mod.rs:505-575`) only removes `TrieKey::Account`, `TrieKey::ContractCode`, all `AccessKey`/gas-key-nonce entries, and `ContractData` entries for the deleted account. It never touches `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, `TrieKey::PromiseYieldTimeout`, `TrieKey::PromiseYieldIndices`, or the yield-id mapping keys. [1](#0-0) [2](#0-1) 

A `PromiseYieldReceipt` is keyed purely by `(receiver_id: AccountId, data_id)` — by *account name*, not by any per-incarnation identifier — and `resolve_promise_yield_timeouts` finds and executes it based only on `queue_entry.account_id` (again, the plain name) once the timeout fires, with no check that the account that created the yield is "the same" account instance as the one that currently exists under that name. [3](#0-2) [4](#0-3) 

## Can the yield's action list include `AddKey(FullAccess)`?

Yes. `promise_yield_create` pushes a `Promise::Receipt(new_receipt_idx)` onto the promise table and returns that index as `new_promise_idx`. [5](#0-4) 
That same `new_promise_idx` can subsequently be passed to `promise_batch_action_add_key_with_full_access`, which resolves the promise index back to the identical `receipt_idx` via `promise_idx_to_receipt_idx_with_sir` and calls `append_action_add_key_with_full_access`, appending an `Action::AddKey(FullAccess)` onto the same `ActionReceiptMetadata.actions` vector that already holds the yield's callback `FunctionCall`. [6](#0-5) [7](#0-6) [8](#0-7) 
There is no validation anywhere in this path restricting `PromiseYield` receipts to a single `FunctionCall` action — `ActionReceiptMetadata.actions: Vec<Action>` is generic. [9](#0-8) 

Note `receiver_id` for a yield receipt is always forced to `self.context.current_account_id` (the creating contract's own account) — a contract cannot target another account's yield receipt at creation time. [10](#0-9) 

## Why this still results in a real cross-incarnation escalation

Because the yield receipt is self-targeted, the attacker must control the account being deleted/recreated. The exploit path is:

1. Attacker's contract on `victim.near` calls `promise_yield_create` then `promise_batch_action_add_key_with_full_access` on the same promise index, producing a stored `PromiseYieldReceipt{receiver_id: victim.near, data_id}` with `actions = [FunctionCall(callback), AddKey(attacker_key, FullAccess)]`, and a matching `PromiseYieldTimeout{account_id: victim.near, data_id, expires_at}` queue entry.
2. Attacker deletes `victim.near` via `DeleteAccountAction` → `action_delete_account` → `remove_account`, which — as shown above — leaves the `PromiseYieldReceipt`/`PromiseYieldStatus`/`PromiseYieldTimeout` entries untouched in state.
3. Before `expires_at`, some unrelated user creates a new account also named `victim.near` (sub-account names become available for recreation once deleted; this is standard NEAR account-lifecycle behavior) and funds/deploys onto it.
4. At `expires_at`, `resolve_promise_yield_timeouts` fires automatically (no interaction from any party is required), finds the stale `PromiseYieldReceipt` still keyed to `victim.near`, and executes its action list against the *current* account occupying that name — installing the attacker's full-access key on the new owner's account. [11](#0-10) 

This is a genuine violation of "authorization exactness": the actions that get applied were authorized only by the (now-deleted) previous account owner, yet they execute with full-access privileges against a completely different depositor's account, purely because trie keys/queue entries for promise-yield use bare account names with no incarnation binding, and `remove_account` fails to purge them.

### Title
Stale PromiseYieldReceipt/PromiseYieldTimeout entries survive account deletion, enabling cross-account AddKey(FullAccess) execution on a recreated account of the same name - (File: `core/store/src/utils/mod.rs::remove_account`, `runtime/runtime/src/lib.rs::resolve_promise_yield_timeouts`)

### Summary
`remove_account` deletes the Account record, contract code/data, and access keys, but never removes `TrieKey::PromiseYieldReceipt`, `PromiseYieldStatus`, `PromiseYieldTimeout` queue entries, or yield-id mappings tied to the deleted account. Because yielded promises are keyed by plain account name and `promise_yield_create`'s receipt index can have arbitrary batch actions (including `AddKey` with `FullAccess`) appended via `promise_batch_action_add_key_with_full_access`, a malicious account owner can leave a booby-trapped yield/timeout behind that fires against whoever later recreates an account with the same name.

### Finding Description
1. A contract deployed on `victim.near` calls `promise_yield_create(...)`, obtaining `new_promise_idx` bound to a fresh `ActionReceiptMetadata{receiver_id: victim.near, actions: [FunctionCall(callback)], is_promise_yield: true}` (`runtime/near-vm-runner/src/logic/logic.rs:3693-3717`).
2. The same contract then calls `promise_batch_action_add_key_with_full_access(new_promise_idx, attacker_pubkey, nonce)`. Since promise-to-receipt resolution is generic (`promise_idx_to_receipt_idx_with_sir`, `logic.rs:2540-2556`), this appends `Action::AddKey(FullAccess)` onto the *same* action list as the yield callback (`receipt_manager.rs:544-557`), with no restriction preventing extra actions on a promise-yield receipt.
3. On execution this is persisted as `TrieKey::PromiseYieldReceipt{receiver_id: victim.near, data_id}` (`function_call.rs`/`lib.rs:1495-1498`), plus a `PromiseYieldTimeout{account_id: victim.near, data_id, expires_at}` queue entry (`function_call.rs:160-169`).
4. Attacker calls `DeleteAccountAction` on `victim.near`. `action_delete_account` (`runtime/runtime/src/actions.rs:314-389`) calls `remove_account` (`core/store/src/utils/mod.rs:505-575`), which removes Account/ContractCode/AccessKey/ContractData entries only — it never removes `PromiseYieldReceipt`, `PromiseYieldStatus`, or `PromiseYieldTimeout` entries for `victim.near`.
5. `victim.near` is later recreated by an unrelated depositor (standard account-name reuse after deletion).
6. At `expires_at`, `resolve_promise_yield_timeouts` (`runtime/runtime/src/lib.rs:3009-3104`) unconditionally checks `state_update.contains_key(&promise_yield_key)` for `account_id = victim.near` and, finding the still-present stale receipt, synthesizes a `PromiseResume` with `data: None` targeting `victim.near`, which is then applied via `apply_action_receipt`, executing `[FunctionCall(callback), AddKey(attacker_key, FullAccess)]` against the *new* `victim.near` account.

No existing check (signature, nonce, access-key permission, or account "identity"/incarnation binding) prevents this, because the entire promise-yield/timeout subsystem addresses accounts purely by name.

### Impact Explanation
This is authorization escalation / account takeover: an attacker who never controlled the recreated account gains a full-access key on it, letting them steal any funds deposited by the new owner or execute arbitrary actions with owner-level permission on that account. This matches the "authorization escalation across accounts or promises" and "theft of user funds" bounty categories.

### Likelihood Explanation
Preconditions: the attacker must fully control the account they plan to delete (trivial — any self-owned account), must be able to construct a promise-yield receipt with a batch `AddKey` action attached (uses only public, unprivileged host functions, no special permission needed), and must delete the account before the yield times out, then wait/hope (or otherwise arrange) for someone to recreate an account with the identical name before `expires_at`. The attack is fully reproducible and cheap (ordinary transactions + a small deployed contract); the main practical constraint is predicting/waiting for name reuse by an unrelated party within the timeout window, which is more of a targeting constraint than a technical barrier — an attacker could also target well-known naming schemes (e.g., specific sub-account name patterns handed out by a factory contract) to increase odds of collision within the timeout window.

### Recommendation
`remove_account` must also purge all `PromiseYieldReceipt`, `PromiseYieldStatus`, and yield-id mapping entries scoped to the account being deleted (analogous to how it already scans and removes access keys and contract data by prefix), and/or `resolve_promise_yield_timeouts` / the `PromiseResume` handling path in `runtime/runtime/src/lib.rs` should bind the parked yield to some incarnation-stable identifier (e.g., verify the account still exists and was not deleted/recreated since the yield was created) before executing its actions. Additionally, consider disallowing privileged actions (`AddKey`, `DeleteKey`, `Stake`, `DeleteAccount`) from being appended to a `PromiseYield` receipt's action batch given it is designed for callback-style `FunctionCall` continuation only.

### Proof of Concept
Integration test outline (test-loop or `runtime/runtime/tests`):
1. Deploy a test contract to `victim.near` exposing a method that calls `promise_yield_create` followed by `promise_batch_action_add_key_with_full_access` on the returned promise index (add such an export to `near-test-contracts/test-contract-rs`).
2. Call that method, assert the `PromiseYieldReceipt`/`PromiseYieldTimeout` are present in state.
3. Submit `DeleteAccountAction{beneficiary_id: attacker.near}` for `victim.near`; assert success and that `Account`/`AccessKey` entries are gone but (bug) `PromiseYieldReceipt`/`PromiseYieldTimeout` entries for `victim.near` remain via direct trie inspection (`get_promise_yield_receipt`).
4. Have a different signer submit `CreateAccountAction` to recreate `victim.near` with its own key/funds, before `expires_at`.
5. Advance blocks to `expires_at`; let `resolve_promise_yield_timeouts` fire.
6. Assert (this is the exploit confirmation) that the recreated `victim.near` account's access-key set now contains the original attacker's `FullAccess` public key — i.e., iterate `AccessKey` trie entries for `victim.near` and find the attacker's key present without the new owner ever authorizing it.
