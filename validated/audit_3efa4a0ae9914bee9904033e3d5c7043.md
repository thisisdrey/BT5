### Title
Unauthenticated `RecvError` packet lets an attacker without a CA-signed certificate race and tear down an established tunnel - (File: `outside.go`)

### Summary
The external report describes a front-running class of bug: an unauthenticated/unprivileged party (`buyer`) can race a privileged corrective action (`rejectDepositor`) by first calling `updateBuyer`, causing the security-relevant transaction to fail. The structurally equivalent weakness in nebula is `handleRecvError` in `outside.go`, which processes the cleartext, unauthenticated `header.RecvError` packet type and tears down a live tunnel (`f.closeTunnel` + `f.handshakeManager.DeleteHostInfo`) based only on a 32-bit `RemoteIndex` and a source-address equality check — neither of which requires possession of a CA-signed certificate or any cryptographic proof of tunnel membership.

### Finding Description
`RecvError` is dispatched before any decryption or certificate validation: [1](#0-0) 

`handleRecvError` looks up the hostinfo purely by the plaintext `RemoteIndex` field carried in every nebula packet header, and its only authenticity check is that the packet's source `netip.AddrPort` matches the hostinfo's currently known remote: [2](#0-1) 

`RemoteIndex` is not secret: it is transmitted in cleartext in the header of every packet exchanged over the tunnel (handshake and data packets alike), so any attacker capable of observing traffic (or of guessing/brute-forcing the 32-bit value) can learn it without ever presenting a certificate. The address check (`hr.IsValid() && hr != addr`) is a simple equality comparison against a UDP source address, which is trivially spoofable by an off-path attacker (UDP has no source-address authentication) or trivially satisfied by an on-path/same-NAT attacker. Once satisfied, this unauthenticated single UDP datagram immediately: (1) closes the established tunnel via `f.closeTunnel(hostinfo)`, and (2) deletes the corresponding pending-handshake entry via `f.handshakeManager.DeleteHostInfo(hostinfo)` — the same deletion path that a legitimate handshake completion or teardown would use.

This mirrors the `rejectDepositor`/`updateBuyer` bug class: a low-trust actor can race ahead of (or in place of) the legitimate/authenticated flow and force a security-relevant state transition (tunnel teardown, pending-hostinfo deletion) purely by winning a timing/spoofing race, with no CA-signed identity required.

### Impact Explanation
An attacker who can spoof or replay a `RecvError` packet can unilaterally terminate any nebula tunnel it can identify the index for, forcing repeated re-handshakes (denial of service), and — because `DeleteHostInfo` also purges the pending-handshake hostmap entry — can specifically win races against in-flight legitimate handshakes, deleting state a legitimate peer is relying on to complete its handshake. This is a remote, unauthenticated state-poisoning / DoS primitive reachable without holding a certificate signed by the network's CA.

### Likelihood Explanation
`RemoteIndex` is sent unencrypted on every packet, so passive observation of a small amount of traffic (or interception on a shared segment/NAT) discloses it; the source-address check that gates `handleRecvError` is a bare equality test on an easily spoofed UDP source, making the attack low-effort for anyone able to inject spoofed UDP packets toward either endpoint of a tunnel (`listen.accept_recv_error` must be enabled for the target, which is part of default/expected configuration per the historical changelog entry adding `send_recv_error`/`accept_recv_error` controls).

### Recommendation
Do not act on `RecvError` (or any other pre-authentication signal) based solely on index + source-address matching. Require the packet to be authenticated under the existing tunnel's established cipher state (e.g., a MAC/AEAD tag bound to the session keys) before triggering `closeTunnel`/`DeleteHostInfo`, or at minimum rate-limit and require additional corroborating authenticated traffic before tearing down state, analogous to allowing the "seller" (the legitimate peer holding valid session keys) to gate/pause the effect of an unauthenticated party's action.

### Proof of Concept
1. Observe (or infer) the `RemoteIndex` of a target tunnel from any packet header on the wire (index is always cleartext).
2. Craft a `header.RecvError` packet with that index: `header.Encode(buf, header.Version, header.RecvError, 0, index, 0)`.
3. Send it via spoofed UDP with the source address set to the value currently held as the peer's remote in `hostinfo.GetRemote()` (learnable from observed traffic or via off-path spoofing).
4. `handleRecvError` (`outside.go:541-575`) finds the hostinfo via `QueryReverseIndex`, passes the address check, and calls `f.closeTunnel(hostinfo)` plus `f.handshakeManager.DeleteHostInfo(hostinfo)`, terminating the tunnel and purging pending-handshake state without any certificate or session-key validation.

func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
