### Title
Attacker fills a victim's `depositTokensOfAccount` set to `MAX_TOKENS_PER_USER` via dust transfers, permanently blocking new collateral deposits - (`contracts/DepositToken.sol`)

### Summary
Analogous to the Netty advisory (attacker-controlled growth of an internal collection with no effective bound), `DepositToken._transfer` automatically calls `Pool.addToDepositTokensOfAccount(recipient_)` whenever a recipient's balance transitions from zero. `Pool.addToDepositTokensOfAccount` enforces `onlyIfAdditionWillNotReachMaxTokens`, reverting once an account's combined deposit+debt token count reaches `MAX_TOKENS_PER_USER = 30` (`Pool.sol:79,143-148`). An unprivileged attacker can deposit dust into each whitelisted collateral and `transfer` 1 wei of every `DepositToken` to a victim, filling all 30 slots. Afterwards any `_mint`/`_transfer` of a *new* token type to the victim reverts, so the victim cannot deposit additional collateral types — including to rescue an underwater position — and cannot clear the slots if their balances are locked by debt.

### Finding Description
- `DepositToken._transfer` adds the token to the recipient's per-account set whenever `_recipientBalanceBefore == 0` — no opt-in, no minimum amount (`DepositToken.sol:518-520`). Same logic in `_mint` (`DepositToken.sol:486-488`).
- `Pool.addToDepositTokensOfAccount` is gated by `onlyIfAdditionWillNotReachMaxTokens(account_)`, which reverts `UserReachedMaxTokens` at 30 tokens (`Pool.sol:143-148`). The check is on the *recipient*, but the attacker controls the *sender* and picks the victim.
- The victim's only way to free a slot is to drive their balance to zero (`_burn`/`_transfer` → `removeFromDepositTokensOfAccount`, `DepositToken.sol:460-462,523-525`), but both `transfer` and `withdraw` are gated by `_revertIfLocked` (`DepositToken.sol:350,409`). If the victim has debt and `_issuableInUsd == 0` (i.e. an unhealthy or borderline position), `unlockedBalanceOf` returns 0 (`DepositToken.sol:383-398`), so the victim cannot move even 1 wei of the dusted tokens and cannot unbrick the slots themselves.
- Attack path: attacker calls `deposit(dust, attacker)` on each whitelisted `DepositToken` (or flash-borrows underlying to fund it), then `depositToken.transfer(victim, 1)`. Each call adds a slot. Since `addDepositToken` caps whitelisted deposit tokens at `MAX_TOKENS_PER_USER` (`Pool.sol:703`), and the limit is shared with debt tokens, filling the deposit side alone is enough for victims holding several debt positions.

### Impact Explanation
Temporary freezing of funds and loss via forced liquidation: a victim whose collateral value is falling cannot deposit a *new* collateral type to restore their health factor — every `deposit` reverts inside `_mint` → `addToDepositTokensOfAccount`. If their existing deposits don't cover the needed top-up, liquidation becomes unavoidable, producing a direct, attacker-caused loss (liquidator fee + seized collateral). The freeze also blocks receiving deposit tokens, `seize` proceeds are unaffected (liquidator side), but the victim cannot exit-into-new-collateral. The victim cannot self-recover while any balance is locked, so the freeze persists as long as the position is unhealthy — exactly when deposits matter most.

### Likelihood Explanation
Fully permissionless: `deposit` and `transfer` are public, `nonReentrant`/`whenNotPaused` only. Cost is bounded — at most `30 - (victim's existing token count)` dust deposits plus transfers; underlying can be flash-loaned within each tx since `deposit` pulls underlying and returns a transferrable receipt token. No privileged role, oracle manipulation, or malicious bridge required. The cap, modifiers, and pause flags do not prevent it. Requirement: victim must hold fewer than 30 tokens total, which is the common case.

### Recommendation
- Don't revert on the max-tokens check for unsolicited inbound transfers; instead only enforce `onlyIfAdditionWillNotReachMaxTokens` on mint paths (`deposit`, `issue`), or skip set insertion for dust transfers below a threshold.
- Alternatively, track collateral membership lazily (derive tokens from whitelisted list × `balanceOf > 0` in `debtPositionOf`) rather than a per-account enumerable set.
- At minimum, allow an account to purge unsolicited entries: a `sweep`/`removeToken` that sends the dust balance back or burns it regardless of locked state, since dust amounts can never be meaningfully locked.

### Proof of Concept
Hardhat (repo's existing test stack), assuming a live pool with ≥1 whitelisted `DepositToken` set (`dTokens[]`) and a victim with an open debt position:

```ts
// victim has a position near the liquidation threshold
for (const dt of depositTokens) {           // up to 30 distinct deposit tokens
  if ((await dt.balanceOf(victim.address)) === 0) {
    await underlyingOf(dt).connect(attacker).approve(dt.address, DUST);
    await dt.connect(attacker).deposit(DUST, attacker.address); // mints receipt dust
    await dt.connect(attacker).transfer(victim.address, 1);     // adds slot to victim
  }
}
expect(await pool.getDepositTokensOfAccount(victim.address)).to.have.length(30);

// victim tries to deposit a collateral type they don't yet hold -> reverts
await expect(
  newDepositToken.connect(victim).deposit(amount, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// victim cannot clear slots while debt locks balances
expect(await someDustedToken.unlockedBalanceOf(victim.address)).to.eq(0);
await expect(
  someDustedToken.connect(victim).transfer(attacker.address, 1)
).to.be.revertedWithCustomError(someDustedToken, 'NotEnoughFreeBalance');
```

Key assertions: `getDepositTokensOfAccount(victim)` reaches the 30-slot cap purely from attacker-initiated transfers, subsequent first-time deposits revert, and locked balances prevent the victim from removing the dusted entries — confirming a persistent, unprivileged freeze on new-collateral deposits.
