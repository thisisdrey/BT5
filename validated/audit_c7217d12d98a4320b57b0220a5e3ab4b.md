### Title
Attacker can permanently block an account from new deposits/borrows by dust-filling its token list to `MAX_TOKENS_PER_USER` - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
Analogous to the ZIP-bomb DoS (a small crafted input exhausting a bounded server resource), any EOA can exhaust a bounded per-account resource in Metronome: the `debtTokensOfAccount`/`depositTokensOfAccount` list capped at `MAX_TOKENS_PER_USER = 30` in `contracts/Pool.sol:79`. By depositing dust into the pool's deposit tokens and `transfer()`ing 1-wei amounts to a victim, the attacker inflates the victim's token list via the `addToDepositTokensOfAccount` hook in `DepositToken._transfer` (`contracts/DepositToken.sol:518-520`). Once the combined list hits 30, `onlyIfAdditionWillNotReachMaxTokens` (`contracts/Pool.sol:143-148`) reverts every operation that would add a new token entry — blocking all deposits of collateral types the victim doesn't already hold and all first-time borrows.

### Finding Description
`DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance of that token goes from 0 to positive (`contracts/DepositToken.sol:518`). `addToDepositTokensOfAccount` is permissionless from any registered deposit token and enforces `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) < MAX_TOKENS_PER_USER` (`contracts/Pool.sol:143-148`, `204-220`). There is no minimum transfer amount and no opt-in — any holder of msdTOKEN can push entries onto any address's list.

Since `addDepositToken` itself caps listed deposit tokens at `MAX_TOKENS_PER_USER` (`contracts/Pool.sol:703`), a pool that approaches 30 listed deposit tokens lets an attacker unilaterally saturate any target account's list. On smaller pools the attacker saturates the remainder of the victim's remaining slots. After saturation:

- `DepositToken.deposit` → `_mint` → `addToDepositTokensOfAccount` reverts with `UserReachedMaxTokens` for any collateral the victim doesn't already hold (`contracts/DepositToken.sol:486-488`).
- `DebtToken.issue`/`mint` → `addToDebtTokensOfAccount` reverts for any new synthetic debt (same shared cap, `contracts/Pool.sol:204`).
- Incoming `seize()` transfers during liquidation still work for tokens the liquidator already holds, but liquidations paying a collateral the victim... (liquidator-side, unaffected).

Concretely, a victim whose position is drifting toward liquidation cannot top up with a *new* collateral type — every deposit reverts — so the attacker (or any liquidator) can liquidate the position once it crosses the threshold. The victim can only recover slots by sending the dust balances back out in full (`balanceOf → 0` triggers `removeFromDepositTokensOfAccount`, `contracts/DepositToken.sol:523`), which costs up to 30 extra transactions and cannot be done atomically with the blocked deposit unless batched through `Operator.execute`.

### Impact Explanation
Temporary freezing of funds / liveness: the victim is denied service for all new-collateral deposits and new borrows until they manually clear the dust entries. In the worst case (position near the liquidation threshold, attacker front-runs the victim's deposit with the dust-filling transactions), the victim loses the liquidation fee on their seized collateral — an indirect but concrete loss. No privileged role, oracle manipulation, or unbounded loop is required.

### Likelihood Explanation
Requires the pool to list enough deposit tokens that dust transfers can push a target's combined list to 30 (or the victim already occupying most slots). Cost to the attacker is roughly N dust deposits + N transfers (cheap, and the dust is recoverable afterward). No economic barrier besides gas. The attack is fully reproducible on a fork: deposit 1 wei of underlying into each listed `DepositToken`, then `transfer(victim, 1)` for each until `UserReachedMaxTokens`, then show victim's `deposit` of a new collateral reverts.

### Recommendation
- Enforce a minimum first-transfer/deposit threshold (e.g., a USD-denominated dust floor via `masterOracle`) before adding a token to an account's list, or
- Count only tokens above a dust threshold in `onlyIfAdditionWillNotReachMaxTokens`, or
- Add an opt-out/sweep function letting an account remove a dust entry without needing the counterparty's cooperation, or
- Whitelist-based tracking where only deposits above `debtFloorInUsd`-equivalent value register the token.

function test_DustFillsTokenList() public {
    // setup: victim already holds some tokens; pool has D listed deposit tokens
    address[] memory dtokens = pool.getDepositTokens();
    for (uint i; i < dtokens.length; ++i) {
        DepositToken dt = DepositToken(dtokens[i]);
        if (dt.balanceOf(victim) > 0) continue;
        // attacker deposits dust and transfers 1 wei of msdTOKEN to victim

            pool.depositTokensOfAccount.length(victim) >= pool.MAX_TOKENS_PER_USER()) break;
    }
