### Title
Deterministic `CreateSmartContract` address enables front-running DoS of contract deployment - (File: `actuator/src/main/java/org/tron/core/actuator/VMActuator.java`)

### Summary
`VMActuator.create()` computes the new contract's address deterministically from the transaction itself and rejects deployment if *any* account already exists at that address, not just if a contract already exists there. Because the address is fully computable from the signed (even unconfirmed/pending) transaction, any unprivileged party can pre-create an account at that exact address before the deployment transaction is included, permanently blocking that specific `CreateSmartContract` transaction.

### Finding Description
In `VMActuator.create()` the contract address is derived purely from data already present in the (unexecuted) transaction: [1](#0-0) 

`WalletUtil.generateContractAddress(trx)` computes `sha3omit12(txId || ownerAddress)`, where `txId` is `Sha256Hash` of the raw transaction data: [2](#0-1) 

Because `txId` (and therefore the resulting contract address) is fully determined by the raw transaction bytes — which are visible the moment the signed transaction is broadcast to the network / sits in a node's pending pool, before it is packed into a block — an attacker observing the mempool can compute the future contract address ahead of time. The attacker then only needs to get *any* account created at that address before the deploy transaction is processed (e.g., a trivial `TransferContract` sending 1 sun to that address, which is a completely permissionless, unprivileged operation that auto-creates a `Normal` account).

The validation check in `create()` is stricter than the semantics used elsewhere for `CREATE`/`CREATE2` collisions inside the VM, which only treat the address as occupied if it already holds *contract* code (`isContractExist`) once Constantinople rules are active: [3](#0-2) 

But the top-level deploy path in `VMActuator.create()` rejects unconditionally if `rootRepository.getAccount(contractAddress) != null` — i.e., even a plain, non-contract account with a balance is enough to permanently fail that specific deployment transaction: [1](#0-0) 

This mirrors the report's root cause exactly: a deterministic, pre-computable address is checked for "already exists" with a single occupancy check, and once occupied the intended create operation can never succeed for that transaction.

### Impact Explanation
Any unprivileged network participant who observes a pending `CreateSmartContract` transaction (or otherwise learns its raw-data hash in advance) can grief the deployer by front-running with a trivial TRX transfer to the pre-computed address. This forces the specific signed deployment transaction to be permanently rejected by `ContractValidateException`, wasting the deployer's effort/bandwidth for that transaction and, for any use case that relies on deterministic pre-announced deployment addresses (e.g., counterfactual/pre-funded contract addresses, cross-chain address parity schemes, or factory patterns), causes denial of service against that specific deployment attempt.

### Likelihood Explanation
Likelihood is limited by the fact that `txId` embeds transaction-specific fields (`ref_block`, `expiration`, fee limit, owner address, bytecode, etc.), so the deployer can trivially invalidate the attack by resigning with different data (e.g., a different expiration timestamp), producing a new `txId` and therefore a new target address. The attack requires the attacker to observe the pending transaction and race a cheap transfer ahead of it, which is realistic for MEV-style mempool watchers but only griefs a single deployment attempt rather than causing an indefinite, unrecoverable DoS as in the original Uniswap `createPair` report (where the factory nonce made every subsequent deployment collide with the same pre-computed sequence).

### Recommendation
Align the top-level `CreateSmartContract` occupancy check in `VMActuator.create()` with the internal CREATE/CREATE2 semantics (`isContractExist`), so only accounts that actually hold contract code/nonce block deployment, and a plain funded account at the target address does not brick the transaction. Alternatively, allow deployment to proceed and take over a non-contract account at that address (as already done for internal CREATE2 collisions) rather than throwing `ContractValidateException`.

### Proof of Concept
1. Attacker monitors the P2P/mempool for a pending `CreateSmartContract` transaction from victim.
2. Attacker computes `contractAddress = sha3omit12(txId || ownerAddress)` using `WalletUtil.generateContractAddress` logic, from the transaction bytes already visible in the pending transaction.
3. Attacker broadcasts a `TransferContract` sending a minimal TRX amount to `contractAddress`, which is a fully permissionless operation and auto-creates a `Normal` `AccountCapsule` at that address.
4. Once the attacker's transfer is confirmed before the victim's deploy transaction, the victim's `CreateSmartContract` transaction hits `rootRepository.getAccount(contractAddress) != null` in `VMActuator.create()` and throws `ContractValidateException`, permanently failing that specific signed transaction.

```java
  public static byte[] generateContractAddress(Transaction trx) {

    CreateSmartContract contract = ContractCapsule.getSmartContractFromTransaction(trx);
    byte[] ownerAddress = contract.getOwnerAddress().toByteArray();
    TransactionCapsule trxCap = new TransactionCapsule(trx);
    byte[] txRawDataHash = trxCap.getTransactionId().getBytes();

    byte[] combined = new byte[txRawDataHash.length + ownerAddress.length];
    System.arraycopy(txRawDataHash, 0, combined, 0, txRawDataHash.length);
    System.arraycopy(ownerAddress, 0, combined, txRawDataHash.length, ownerAddress.length);

    return Hash.sha3omit12(combined);

  }
```
