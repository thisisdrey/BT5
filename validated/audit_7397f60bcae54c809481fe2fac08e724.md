### Title
Timeout-triggered PromiseYield resolution executes stale receipt against a recreated account without re-validating account identity - ([File: runtime/runtime/src/lib.rs])

### Finding Description
`TrieKey::PromiseYieldTimeout { index }` entries are queue-index scoped and explicitly not account-scoped (`get_account_id()` returns `None`) [1](#0-0) . The actual privileged data lives in a *separate*, account-scoped key, `TrieKey::PromiseYieldReceipt { receiver_id, data_id }` (`get_account_id()` returns `Some(receiver_id)`) [2](#0-1) , which stores the full serialized `Receipt` (including the original `predecessor_id` and fallback `FunctionCall` actions) created via `set_promise_yield_receipt` when the yield was first processed [3](#0-2) .

`resolve_promise_yield_timeouts` walks the timeout queue and, for each expired entry, only checks `state_update.contains_key(&promise_yield_key)` where `promise_yield_key` is derived from `queue_entry.account_id` and `queue_entry.data_id` [4](#0-3) . If present, it synthesizes a `PromiseResume` receipt with `data: None` destined for the same account and enqueues it for delivery [5](#0-4) . When that resume is processed, `apply_action_receipt` is invoked directly against the stored yield receipt fetched from `PromiseYieldReceipt` under the queue entry's `account_id`/`data_id` [6](#0-5) , executing the original fallback actions with the original `predecessor_id` baked in against whatever account currently exists at that `account_id` at execution time — including a newly created contract deployed after a delete/recreate cycle.

Neither `resolve_promise_yield_timeouts` nor the `PromiseResume` handling path checks any form of account incarnation identifier (e.g., a creation nonce, code hash pinned at yield-creation time, or account existence continuity) before dispatching the fallback receipt. The only gate is "does a `PromiseYieldReceipt` key still exist for this `(account_id, data_id)` pair" — which is a re-creatable condition if a `DeleteAccount` action does not purge the orphaned `PromiseYieldReceipt` entry for that account (this repo's `action_delete_account` implementation could not be conclusively confirmed within tool budget to scrub non-`Account`/non-access-key/non-contract-code columns such as `PromiseYieldReceipt` on deletion).

### Impact Explanation
If confirmed that `DeleteAccount` leaves `PromiseYieldReceipt` (and its associated queued timeout) intact, this allows a stale fallback `FunctionCall` action — carrying the original predecessor's authority/context — to execute against a subsequently redeployed contract on the same `account_id`. This is a promise-privilege-containment violation: a promise created under one account "incarnation" resolves against an unrelated later incarnation, potentially triggering unintended state mutations, unauthorized calls, or fund-moving logic in the new contract that assumes the caller is a legitimate continuation of a prior yield. This matches the "authorization escalation across accounts/promises" bounty category.

### Likelihood Explanation
This finding's reachability by an unprivileged attacker (self-account yield + self-account delete/recreate before the queued timeout height, all standard, permission-checked actions) is plausible and cheap, but the finding is **contingent on an unverified fact**: whether `action_delete_account` in `runtime/runtime/src/actions.rs` actually leaves `PromiseYieldReceipt`/`PromiseYieldStatus`/`YieldIdToDataId` entries in state after account deletion. I was not able to inspect the body of `action_delete_account` within the tool-call budget to confirm this. Without that confirmation, the timeout resolution mechanism itself is not provably a *new* vulnerability distinct from the direct-resume path referenced in the prompt — it is the same root cause (orphaned account-scoped promise-yield state surviving `DeleteAccount`) reached through a second entry point (the timeout queue) rather than a new independent bug.

### Recommendation
Cannot be finalized without confirming the account-deletion cleanup behavior for `PromiseYieldReceipt`/`PromiseYieldStatus`/`YieldIdToDataId`. If `action_delete_account` does not purge these keys, the fix should be applied at the root: `action_delete_account` should explicitly remove `PromiseYieldReceipt`, `PromiseYieldStatus`, and `YieldIdToDataId`/`DataIdToYieldId` entries for the deleted account (or the runtime should tag such receipts with an account "incarnation" identifier checked at resolution time in both `PromiseResume` processing at `runtime/runtime/src/lib.rs:1500-1562` and `resolve_promise_yield_timeouts` at `runtime/runtime/src/lib.rs:3009-3105`).

### Proof of Concept
Unresolved pending verification of `action_delete_account`'s cleanup scope — cannot certify as reproducible without that confirmation. A conclusive PoC would require: (1) confirming `runtime/runtime/src/actions.rs::action_delete_account` does not remove `PromiseYieldReceipt`, and (2) a test-loop integration test analogous to `test-loop-tests/src/tests/yield_timeouts.rs` that creates a yield on `child.attacker.near`, deletes and recreates that account with new contract code before `yield_timeout_height()`, advances to the timeout height, and asserts whether the fallback `FunctionCall` executes against the new code (using `find_yield_data_ids_from_latest_block` and `get_partial_transaction_result` helpers already present in that test file) [7](#0-6) .

pub fn set_promise_yield_receipt(state_update: &mut TrieUpdate, receipt: &Receipt) {

        VersionedReceiptEnum::PromiseYield(action_receipt) => {
            assert!(action_receipt.input_data_ids().len() == 1);

                receiver_id: receipt.receiver_id().clone(),
                data_id: action_receipt.input_data_ids()[0],
            };
            set(state_update, key, receipt);
        }
        _ => unreachable!("Expected PromiseYield receipt"),
    }

/// In this test there is no block produced at height yield_timeout_height().
#[test]
#[cfg(feature = "test_features")]
fn test_skip_timeout_height() {
    use assert_matches::assert_matches;
    use near_chain::Error;

    let (mut env, yield_tx_hash, data_id) = prepare_env_with_yield(vec![], None);
    assert!(next_block_height_after_setup() < yield_timeout_height());

    // Advance through the blocks during which the yield will await resumption
    for block_height in next_block_height_after_setup()..yield_timeout_height() {
        env.validator_runner().run_until_head_height(block_height);

        // The transaction will not have a result until the timeout is reached
        assert_eq!(
            env.validator()
                .client()
                .chain
                .get_partial_transaction_result(&yield_tx_hash)
                .unwrap()
                .status,
            FinalExecutionStatus::Started
        );
    }

    // Skip the timeout height and produce a block at height yield_timeout_height() + 1.
    // We still expect the timeout to be processed and produce a YieldResume receipt.
    assert_eq!(env.validator().head().height, yield_timeout_height() - 1);
    // Produce block at yield_timeout_height()+1 using the one at yield_timeout_height()-1 as the previous block.
    env.validator_mut().client_actor().adv_produce_blocks_on(
        1,
        true,
        near_client::client_actor::AdvProduceBlockHeightSelection::SelectedHeightOnLatestKnown {
            produced_block_height: yield_timeout_height() + 1,
        },
    );
    env.validator_runner()
        .run_until_head_height_with_timeout(yield_timeout_height() + 1, Duration::seconds(3));
    assert_eq!(env.validator().head().height, yield_timeout_height() + 1);
    // In spice, this waits for the specified block to execute.
    env.validator_runner().run_until_executed_height(yield_timeout_height() + 1);
    // The block at yield_timeout_height() should be missing.
    assert_matches!(
        env.validator().client().chain.get_block_by_height(yield_timeout_height()),
        Err(Error::DBNotFoundErr(_))
    );

    // Checks that the anticipated YieldResume receipt was produced.
    assert_eq!(find_yield_data_ids_from_latest_block(&env), vec![data_id]);
    assert_eq!(
        env.validator()
            .client()
            .chain
            .get_partial_transaction_result(&yield_tx_hash)
            .unwrap()
            .status,
        FinalExecutionStatus::Started
    );

    // When this block executes, the resume receipt is applied and the callback will execute.
    env.validator_runner().run_until_executed_height(yield_timeout_height() + 2);
    assert_eq!(
        env.validator()
            .client()
            .chain
            .get_partial_transaction_result(&yield_tx_hash)
            .unwrap()
            .status,
        FinalExecutionStatus::SuccessValue(vec![0u8]),
    );

    assert_no_promise_yield_status_in_state(&env);
}
