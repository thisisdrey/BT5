## Analysis: Nomination-pools reward donation is sandwichable exactly like the Balancer `UpliftOnlyExample` bug

The core broken invariant in the external report is: **a lump-sum value injection ("donation") is credited pro‑rata to whoever holds shares at settlement time, rather than to whoever held shares while that value was earned**, enabling an attacker to buy shares immediately before the donation lands and claim a slice of value they never contributed to.

`pallet-nomination-pools` reproduces this exact pattern between `pallet-staking`'s era-based reward payout and the pool's reward-counter accounting.

### The mechanism

- `payout_stakers` / `payout_stakers_by_page` is an explicitly **permissionless** call: "Any account can call this function, even if it is not one of the stakers." It pushes the *entire historical era reward* for a nominator (the pool's bonded account) into the `Payee` account in one lump transfer, based on stake **exposure snapshotted at a past era**. [1](#0-0) 

- For nomination pools, that `Payee` is the pool's **reward account**, a single account shared by all current members regardless of who was actually staked during the rewarded era.

- Once funds land in the reward account, `RewardPool::current_reward_counter` computes each member's share using the reward account's **current balance** and the bonded pool's **current points** — not points held during the era that earned the reward: [2](#0-1) 

- `join()` lets anyone bond into the pool and immediately increase `bonded_pool.points`, snapshotting their `last_recorded_reward_counter` to the counter *before* their own reward-triggering call: [3](#0-2) 

- `do_reward_payout`/`claim_payout` then pays out `pending_rewards = (current_reward_counter - last_recorded_reward_counter) * member.points` using the **current** counter (which reflects the just-landed era reward) — so a member who joined seconds ago, but whose `last_recorded_reward_counter` predates the payout, gets a full slice of the newly-arrived reward proportional to their (freshly inflated) points: [4](#0-3) 

None of `join`, `payout_stakers`, `payout_stakers_by_page`, or `claim_payout` require any privileged origin, cooldown, or minimum dwell time — an attacker can chain `join → payout_stakers → claim_payout` atomically (e.g., via `pallet_utility::batch_all`) in a single transaction, no MEV/front-running needed. This mirrors the reported Balancer bug's "add liquidity → wait for donation → remove liquidity, capturing a slice of value never contributed" primitive, with `payout_stakers` playing the role of the stepwise `addLiquidity(..., DONATION, ...)` call.

### Title
Nomination-pools reward payout is sandwichable via `join` + `payout_stakers`, letting an attacker steal a share of era rewards earned entirely by other members - (File: `substrate/frame/nomination-pools/src/lib.rs`)

### Summary
`pallet-nomination-pools` distributes newly landed reward-account funds to members based on their **current** points share rather than the points they held while the reward was being earned by the underlying `pallet-staking` exposure. Because `payout_stakers`/`payout_stakers_by_page` is fully permissionless and delivers a lump sum for an entire historical era in one transfer, and `join` is permissionless and instantaneous, an attacker can join a pool with a large bond immediately before triggering (or observing) a reward payout, then call `claim_payout` to capture a disproportionate slice of rewards earned by long-standing members, diluting/stealing from them.

### Finding Description
`RewardPool::current_reward_counter` (lib.rs:1450-1511) computes `new_pending_rewards / bonded_points` using the reward account's current balance and the bonded pool's *current* total points. `join` (lib.rs:2118-2174) allows anyone to add points to the bonded pool at any time with no vesting/cooldown, snapshotting the caller's `last_recorded_reward_counter` to the value just before their own subsequent actions. `payout_stakers`/`payout_stakers_by_page` (staking `mod.rs:1716-1738`) is explicitly callable by anyone and transfers the pool's full era-exposure reward into the reward account as one lump sum, unrelated to the pool's *current* membership. When the attacker subsequently calls `claim_payout` (via `do_reward_payout`, lib.rs:3524-3571), the pending-reward formula uses the now-inflated current counter and the attacker's freshly bonded points, granting them a share of a reward that accrued entirely before they joined — diluting the payout owed to members who were actually staked during the rewarded era.

### Impact Explanation
This breaks the "settle exactly once to the rightful beneficiary and amount" invariant for pool reward payouts: value earned by long-term nominators is redirected to a same-block joiner. Since `payout_stakers` can move an entire era's worth of reward for a pool in one call, and pool bond amounts can be arbitrarily large (bounded only by `MaxPoolMembersPerPool`/balance), the stolen fraction scales with the attacker's capital relative to existing pool points, directly transferring value from legitimate LPs (pool members) to the attacker with no compensating loss to themselves beyond opportunity cost of bonding (which they can later unbond).

### Likelihood Explanation
High: no privileged role, governance, relayer, or validator collusion is required. `join`, `payout_stakers`/`payout_stakers_by_page`, and `claim_payout` are all ordinary signed extrinsics documented as callable by any account, and can be composed atomically via `pallet_utility::batch_all` in a single transaction — no mempool race or front-running is even necessary since the attacker can trigger the "donation" (`payout_stakers`) themselves.

### Recommendation
Distribute era-based staking rewards landing in a pool's reward account according to a time-weighted or snapshot-based accounting (e.g., record points-at-era or apply a vesting/dwell-time requirement before newly bonded points participate in already-accrued-but-unclaimed reward counters), rather than allowing `current_reward_counter` to apply lump-sum reward-account inflows pro-rata to points bonded strictly after the reward was earned.

### Proof of Concept
1. Pool P has existing members with total points `X`, and an era `E` reward of `R` is pending (unclaimed) for P's bonded (nominator) account, payable via `payout_stakers(P_bonded_stash, E)`.
2. Attacker submits a single `utility.batch_all([...])` transaction:
   - `Pools::join(pool_id, huge_amount)` — attacker now has points `Y >> X`.
   - `Staking::payout_stakers(P_bonded_stash, E)` — transfers `R` into P's reward account (a permissionless call per the pallet docs).
   - `Pools::claim_payout()` — attacker's `pending_rewards = (current_rc - last_recorded_rc) * Y ≈ R * Y / (X + Y)`, paid directly to attacker's free balance.
3. Attacker immediately owns a share of `R` proportional to `Y`, despite having zero stake during era `E`; the legitimate members' effective share of `R` is correspondingly diluted (computed over `X + Y` points instead of `X`).
4. Attacker can subsequently `unbond`/`withdraw_unbonded` after the standard unbonding duration to fully exit, but the reward theft itself is realized instantly at step 3, independent of the unbonding delay.

```rust
	/// Get the current reward counter, based on the given `bonded_points` being the state of the
	/// bonded pool at this time.
	fn current_reward_counter(
		&self,
		id: PoolId,
		bonded_points: BalanceOf<T>,
		commission: Perbill,
	) -> Result<(T::RewardCounter, BalanceOf<T>), Error<T>> {
		let balance = Self::current_balance(id);

		// Calculate the current payout balance. The first 3 values of this calculation added
		// together represent what the balance would be if no payouts were made. The
		// `last_recorded_total_payouts` is then subtracted from this value to cancel out previously
		// recorded payouts, leaving only the remaining payouts that have not been claimed.
		let current_payout_balance = balance
			.saturating_add(self.total_rewards_claimed)
			.saturating_add(self.total_commission_claimed)
			.saturating_sub(self.last_recorded_total_payouts);

		// Split the `current_payout_balance` into claimable rewards and claimable commission
		// according to the current commission rate.
		let new_pending_commission = commission * current_payout_balance;
		let new_pending_rewards = current_payout_balance.saturating_sub(new_pending_commission);

		// * accuracy notes regarding the multiplication in `checked_from_rational`:
		// `current_payout_balance` is a subset of the total_issuance at the very worse.
		// `bonded_points` are similarly, in a non-slashed pool, have the same granularity as
		// balance, and are thus below within the range of total_issuance. In the worse case
		// scenario, for `saturating_from_rational`, we have:
		//
		// dot_total_issuance * 10^18 / `minJoinBond`
		//
		// assuming `MinJoinBond == ED`
		//
		// dot_total_issuance * 10^18 / 10^10 = dot_total_issuance * 10^8
		//
		// which, with the current numbers, is a miniscule fraction of the u128 capacity.
		//
		// Thus, adding two values of type reward counter should be safe for ages in a chain like
		// Polkadot. The important note here is that `reward_pool.last_recorded_reward_counter` only
		// ever accumulates, but its semantics imply that it is less than total_issuance, when
		// represented as `FixedU128`, which means it is less than `total_issuance * 10^18`.
		//
		// * accuracy notes regarding `checked_from_rational` collapsing to zero, meaning that no
		//   reward can be claimed:
		//
		// largest `bonded_points`, such that the reward counter is non-zero, with `FixedU128` will
		// be when the payout is being computed. This essentially means `payout/bonded_points` needs
		// to be more than 1/1^18. Thus, assuming that `bonded_points` will always be less than `10
		// * dot_total_issuance`, if the reward_counter is the smallest possible value, the value of
		//   the
		// reward being calculated is:
		//
		// x / 10^20 = 1/ 10^18
		//
		// x = 100
		//
		// which is basically 10^-8 DOTs. See `smallest_claimable_reward` for an example of this.
		let current_reward_counter =
			T::RewardCounter::checked_from_rational(new_pending_rewards, bonded_points)
				.and_then(|ref r| self.last_recorded_reward_counter.checked_add(r))
				.ok_or(Error::<T>::OverflowRisk)?;

		Ok((current_reward_counter, new_pending_commission))
```

```rust
		#[pallet::call_index(0)]
		#[pallet::weight(T::WeightInfo::join())]
		pub fn join(
			origin: OriginFor<T>,
			#[pallet::compact] amount: BalanceOf<T>,
			pool_id: PoolId,
		) -> DispatchResult {
			let who = ensure_signed(origin)?;
			// ensure pool is not in an un-migrated state.
			ensure!(!Self::api_pool_needs_delegate_migration(pool_id), Error::<T>::NotMigrated);

			// ensure account is not restricted from joining the pool.
			ensure!(!T::Filter::contains(&who), Error::<T>::Restricted);

			ensure!(amount >= MinJoinBond::<T>::get(), Error::<T>::MinimumBondNotMet);
			// If a member already exists that means they already belong to a pool
			ensure!(!PoolMembers::<T>::contains_key(&who), Error::<T>::AccountBelongsToOtherPool);

			let mut bonded_pool = BondedPool::<T>::get(pool_id).ok_or(Error::<T>::PoolNotFound)?;
			bonded_pool.ok_to_join()?;

			let mut reward_pool = RewardPools::<T>::get(pool_id)
				.defensive_ok_or::<Error<T>>(DefensiveError::RewardPoolNotFound.into())?;
			// IMPORTANT: reward pool records must be updated with the old points.
			reward_pool.update_records(
				pool_id,
				bonded_pool.points,
				bonded_pool.commission.current(),
			)?;

			bonded_pool.try_inc_members()?;
			let points_issued = bonded_pool.try_bond_funds(&who, amount, BondType::Extra)?;

			PoolMembers::insert(
				who.clone(),
				PoolMember::<T> {
					pool_id,
					points: points_issued,
					// we just updated `last_known_reward_counter` to the current one in
					// `update_recorded`.
					last_recorded_reward_counter: reward_pool.last_recorded_reward_counter(),
					unbonding_eras: Default::default(),
				},
			);

			Self::deposit_event(Event::<T>::Bonded {
				member: who,
				pool_id,
				bonded: amount,
				joined: true,
			});

			bonded_pool.put();
			RewardPools::<T>::insert(pool_id, reward_pool);

			Ok(())
		}
```

```rust
	/// If the member has some rewards, transfer a payout from the reward pool to the member.
	// Emits events and potentially modifies pool state if any arithmetic saturates, but does
	// not persist any of the mutable inputs to storage.
	fn do_reward_payout(
		member_account: &T::AccountId,
		member: &mut PoolMember<T>,
		bonded_pool: &mut BondedPool<T>,
		reward_pool: &mut RewardPool<T>,
	) -> Result<BalanceOf<T>, DispatchError> {
		debug_assert_eq!(member.pool_id, bonded_pool.id);
		debug_assert_eq!(&mut PoolMembers::<T>::get(member_account).unwrap(), member);

		// a member who has no skin in the game anymore cannot claim any rewards.
		ensure!(!member.active_points().is_zero(), Error::<T>::FullyUnbonding);

		let (current_reward_counter, _) = reward_pool.current_reward_counter(
			bonded_pool.id,
			bonded_pool.points,
			bonded_pool.commission.current(),
		)?;

		// Determine the pending rewards. In scenarios where commission is 100%, `pending_rewards`
		// will be zero.
		let pending_rewards = member.pending_rewards(current_reward_counter)?;
		if pending_rewards.is_zero() {
			return Ok(pending_rewards);
		}

		// IFF the reward is non-zero alter the member and reward pool info.
		member.last_recorded_reward_counter = current_reward_counter;
		reward_pool.register_claimed_reward(pending_rewards);

		T::Currency::transfer(
			&bonded_pool.reward_account(),
			member_account,
			pending_rewards,
			// defensive: the depositor has put existential deposit into the pool and it stays
			// untouched, reward account shall not die.
			Preservation::Preserve,
		)?;

		Self::deposit_event(Event::<T>::PaidOut {
			member: member_account.clone(),
			pool_id: member.pool_id,
			payout: pending_rewards,
		});
		Ok(pending_rewards)
	}
```
