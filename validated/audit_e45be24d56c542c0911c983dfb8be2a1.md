### Title
Unbounded per-cycle reward-computation loop reachable from `WithdrawBalanceContract`/`VoteWitnessContract` allows a single transaction to trigger O(cycles) CPU/DB work — DoS analog to the finance.js IRR depth issue - ([File: chainbase/src/main/java/org/tron/core/service/MortgageService.java])

### Summary
The finance.js advisory concerns an attacker-controllable iteration count (the IRR `depth`/guess parameter) that is not bounded, letting a caller force unbounded CPU work in a single call. The closest reachable analog in java-tron is `MortgageService.getOldReward`, whose iteration count is `endCycle - beginCycle` — a value entirely controlled by how long an account has gone without interacting with staking/voting, and which is exercised synchronously inside actuator execution for ordinary, unprivileged transactions (`WithdrawBalanceContract`, `VoteWitnessContract`, `UnfreezeBalanceContract`, and TVM `vote`/`withdrawreward` native contracts).

### Finding Description
`MortgageService.withdrawReward(address)` and `MortgageService.queryReward(address)` call `computeReward(beginCycle, endCycle, accountCapsule)`, which for cycles prior to `newRewardCalStartCycle` falls back to: [1](#0-0) 

```java
private long getOldReward(long begin, long end, List<Pair<byte[], Long>> votes) {
  if (dynamicPropertiesStore.allowOldRewardOpt()) {
    return rewardViCalService.getNewRewardAlgorithmReward(begin, end, votes);
  }
  long reward = 0;
  for (long cycle = begin; cycle < end; cycle++) {
    reward += computeReward(cycle, votes);
  }
  return reward;
}
```

When `allowOldRewardOpt()` is not enabled, this loop runs once **per maintenance cycle** between the account's `beginCycle` (last time it withdrew/updated its vote) and the current cycle, and for every cycle it iterates the account's full vote list (up to `MAX_VOTE_NUMBER`) doing store reads (`delegationStore.getReward`, `getWitnessVote`) per vote: [2](#0-1)

`beginCycle`/`endCycle` bookkeeping is per-account, and there is no cap on how many cycles can accumulate — an account only needs to freeze balance, vote for witnesses, and then simply not call `WithdrawBalanceContract`, `VoteWitnessContract`, or any unfreeze/vote action for a long time. Maintenance cycles happen automatically (roughly daily), so cycles accumulate for as long as the account is dormant, with no limit enforced anywhere in `withdrawReward`/`queryReward`/`computeReward`.

This computation is invoked directly and synchronously from unprivileged actuator execution paths:
- `WithdrawBalanceActuator.execute` → `mortgageService.withdrawReward(...)`: [3](#0-2) 
- `VoteWitnessActuator.countVoteAccount` → `mortgageService.withdrawReward(ownerAddress)`: [4](#0-3) 
- Also reachable via the TVM native `vote`/`withdrawreward` path (`VoteRewardUtil.withdrawReward`), which has the analogous `computeReward` loop over votes per call: [5](#0-4) 

Both of these are reachable simply by signing and broadcasting a normal transaction from any address that has previously frozen TRX and voted, then waited many cycles.

### Impact Explanation
If `allowOldRewardOpt` is not active for the relevant cycle range (e.g. cycles prior to the new reward algorithm's effective/calculated point, or if that optimization flag is disabled/not yet enabled on a given network), a single transaction from an account that accumulated a very large `endCycle - beginCycle` gap (long-dormant frozen/voting account) forces the node to execute a loop whose length is attacker/account-controlled and unbounded, each iteration performing DB reads for every voted witness. This can produce excessive CPU/I/O usage inside block-processing/transaction-execution (a "hot path"), potentially causing block processing stalls, degraded validator/witness performance, or a processing-time DoS — directly analogous to the finance.js IRR depth DoS (CWE-400/770/834: uncontrolled resource consumption from an unvalidated iteration/depth value).

### Likelihood Explanation
Likelihood is moderate: exploitation requires the account to have previously frozen balance and voted for one or more witnesses (ordinary, unprivileged actions any account can perform), and then simply avoid touching `WithdrawBalanceContract`/`VoteWitnessContract`/unfreeze for a long span of maintenance cycles before triggering withdrawal/re-vote in one transaction. This is achievable by any user without special privileges and does not require attacking others' accounts. On networks/chains where the new reward algorithm optimization (`allowOldRewardOpt`) is already fully rolled out and used for the entire historical cycle range, this specific loop is bypassed by `rewardViCalService.getNewRewardAlgorithmReward`; the severity therefore depends on how much of the account's reward history still falls into cycles before `newRewardCalStartCycle`/before `allowOldRewardOpt` was enabled, which could not be fully confirmed from the available code alone.

### Recommendation
- Cap the number of un-withdrawn cycles per account (e.g., force periodic reward settlement or checkpointing) so `endCycle - beginCycle` cannot grow unbounded.
- Ensure `getOldReward`'s linear-scan fallback path is only reachable for a bounded historical range, and that `allowOldRewardOpt`/`rewardViCalService` fully supersedes the old O(cycles) loop for all accounts, including long-dormant ones, on all networks.
- Add an explicit maximum iteration/cycle-count guard with a graceful error (analogous to `MAX_VOTE_NUMBER` checks already used for votes) before entering the `for (long cycle = begin; cycle < end; cycle++)` loop.

### Proof of Concept
1. Freeze balance (`FreezeBalanceContract`) and vote for a witness (`VoteWitnessContract`) on an address.
2. Do not call `WithdrawBalanceContract`, `VoteWitnessContract` again, or unfreeze for a very large number of maintenance cycles (simulate by advancing the chain / cycle counter far into the future in a test harness, as done in `MortgageServiceTest`/`VoteTest`).
3. Send a single `WithdrawBalanceContract` (or re-vote) transaction from that address.
4. Observe that `MortgageService.withdrawReward` → `computeReward` → `getOldReward` executes a loop of length `endCycle - beginCycle`, each iteration re-scanning the account's vote list and performing store lookups, causing execution time to scale linearly (unboundedly) with the dormant period — reproducing the "iteration count controlled by an untrusted, unbounded parameter" DoS pattern described in the finance.js advisory.

```java
  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
```

```java
  public static void withdrawReward(byte[] address, Repository repository) {
    if (!VMConfig.allowTvmVote()) {
      return;
    }
    AccountCapsule accountCapsule = repository.getAccount(address);
    long beginCycle = repository.getBeginCycle(address);
    long endCycle = repository.getEndCycle(address);
    long currentCycle = repository.getDynamicPropertiesStore().getCurrentCycleNumber();
    long reward = 0;
    if (beginCycle > currentCycle || accountCapsule == null) {
      return;
    }
    if (beginCycle == currentCycle) {
      AccountCapsule account = repository.getAccountVote(beginCycle, address);
      if (account != null) {
        return;
      }
    }
    if (beginCycle + 1 == endCycle && beginCycle < currentCycle) {
      AccountCapsule account = repository.getAccountVote(beginCycle, address);
      if (account != null) {
        reward = computeReward(beginCycle, endCycle, account, repository);
        adjustAllowance(address, reward, repository);
        reward = 0;
      }
      beginCycle += 1;
    }
    endCycle = currentCycle;
    if (CollectionUtils.isEmpty(accountCapsule.getVotesList())) {
      repository.updateBeginCycle(address, endCycle + 1);
      return;
    }
    if (beginCycle < endCycle) {
      reward += computeReward(beginCycle, endCycle, accountCapsule, repository);
      adjustAllowance(address, reward, repository);
    }
    repository.updateBeginCycle(address, endCycle);
    repository.updateEndCycle(address, endCycle + 1);
    repository.updateAccountVote(address, endCycle, accountCapsule);
  }
```
