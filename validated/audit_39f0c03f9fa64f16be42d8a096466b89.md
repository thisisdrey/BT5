## Analog Found

### Title
`execute_intents` withdrawal intents bypass the per-action `ft_withdraw`/`nft_withdraw`/`mt_withdraw` pause guards - (File: `contracts/defuse/src/contract/intents/state.rs`)

### Summary
The `PSM._redeem()` bug class — an internal state-mutating function reachable through multiple entry points, only some of which enforce the relevant pause/restriction guard — has a direct analog in the Defuse (Verifier) contract. Token withdrawals can be triggered either directly (e.g. `ft_withdraw`, `nft_withdraw`, `mt_withdraw`), which are individually pause-gated, or indirectly through `execute_intents`, which is gated by a *different*, coarser pause flag (`"intents"`). The indirect path reaches the same internal withdrawal logic without ever checking the per-action pause flag.

### Finding Description
The direct withdrawal endpoints are guarded by dedicated pause flags: [1](#0-0) 

Same pattern applies to `nft_withdraw` and `mt_withdraw`: [2](#0-1) 

By contrast, `execute_intents` (the entry point for signed-intent based operations, including `FtWithdraw`/`NftWithdraw`/`MtWithdraw`/`NativeWithdraw` intents) is only gated by a single, unrelated pause name, `"intents"`: [3](#0-2) 

When an `FtWithdraw` intent is processed, it calls straight into `engine.state.ft_withdraw(...)`: [4](#0-3) 

which is implemented on `Contract` as a direct call into the same internal withdrawal function used by the pause-gated public entry point, with no pause check of its own: [5](#0-4) 

`internal_ft_withdraw` is the exact function invoked by the public, pause-guarded `ft_withdraw`: [6](#0-5) 

So if an operator pauses only the `"ft_withdraw"` (or `"nft_withdraw"`/`"mt_withdraw"`) flag — e.g. in response to a discovered issue specific to that withdrawal path — while leaving `"intents"` unpaused (a legitimate, granular use of the pause system, since each entry point declares its own independent pause name), users can still withdraw the exact same funds by wrapping the same `FtWithdraw`/`NftWithdraw`/`MtWithdraw` payload inside a signed `MultiPayload` and calling `execute_intents`. The binding "funds can leave the contract only while the relevant withdraw action is unpaused" is broken: `paused("ft_withdraw") == true` yet a withdrawal of equal value still succeeds through the alternate path.

### Impact Explanation
An unprivileged, signed-intent-holding user can withdraw funds through a path that a pause meant to have blocked did not cover, moving tokens out of the contract without the authorization state (the granular pause) that governs that specific action. This mirrors the "tokens withdrawn without valid authorisation" class: the operator's per-action pause is the authorization gate for the corresponding withdrawal, and that gate is bypassed entirely via the intents path.

### Likelihood Explanation
Likelihood depends on an operator using the granular, per-name pause capability (e.g., pausing `"ft_withdraw"` specifically rather than pausing all `"intents"`), which the code explicitly supports by design (distinct `#[pause(name = "...")]` values). Any user holding a valid signed `FtWithdraw`/`NftWithdraw`/`MtWithdraw` intent can then bypass the pause with no special role required.

### Recommendation
Enforce the same per-action pause check inside the shared internal withdrawal logic (`internal_ft_withdraw`, `internal_nft_withdraw`, `internal_mt_withdraw`), or check the relevant pause flag (e.g. via `Pausable::is_paused("ft_withdraw")`) at the point where `Contract::ft_withdraw`/`nft_withdraw`/`mt_withdraw` (in `contracts/defuse/src/contract/intents/state.rs`) is invoked from the intents-execution path, so that pausing an action blocks it consistently regardless of entry point.

### Proof of Concept
1. Operator (with `PauseManager`/`DAO` role) pauses only the `"ft_withdraw"` action via the `Pausable` interface, leaving `"intents"` unpaused.
2. A direct call to `Contract::ft_withdraw` now reverts due to `#[pause]` guard.
3. User signs a `MultiPayload` containing an `Intent::FtWithdraw(FtWithdraw { token, receiver_id, amount, .. })` and submits it via `execute_intents`.
4. `execute_intents` only checks the `"intents"` pause flag (unpaused), so execution proceeds to `Intent::execute_intent` → `engine.state.ft_withdraw` → `Contract::ft_withdraw` (`contracts/defuse/src/contract/intents/state.rs:197-200`) → `internal_ft_withdraw`, and the withdrawal succeeds despite `"ft_withdraw"` being paused.
