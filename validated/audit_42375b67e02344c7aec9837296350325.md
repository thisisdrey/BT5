### Title
StackerDB chunk signatures don't bind the contract identifier, permitting cross-DB signature replay - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` (and thus the signature a signer produces over a chunk) only covers `slot_id`, `slot_version`, and `data_hash`; it never binds the `QualifiedContractIdentifier` of the StackerDB the chunk belongs to. This breaks the intended equality "a chunk signature authenticates writes to *this* StackerDB slot" — a signature is actually valid for *any* StackerDB contract in which the same signer address happens to own the same `slot_id`, as long as version/staleness checks are also satisfied.

### Finding Description
`auth_digest` is defined as: [1](#0-0) 

and is used both to sign and to verify chunk metadata: [2](#0-1) 

The verification path used on both the write path and gossip/relay path only checks this digest against the *slot signer address for the target contract*, but the digest itself carries no contract-specific context:
- `StackerDBTx::try_replace_chunk` looks up `slot_validation.signer` for the specific `smart_contract` and calls `slot_desc.verify(&slot_validation.signer)`, which recomputes the same contract-agnostic `auth_digest`: [3](#0-2) 
- The gossip validation path (`PeerNetwork::validate_received_chunk`), used both for `StackerDBSync` downloads and unsolicited `StackerDBPushChunk` messages, does the same: it fetches the signer address scoped to `smart_contract_id` but verifies against the contract-agnostic digest: [4](#0-3) 

Because the smart contract's `stackerdb-get-signer-slots` interface lets any StackerDB contract assign an arbitrary signer principal to an arbitrary `slot_id` (Section: `StackerDBConfig::eval_signer_slots` / `parse_slot_entry`), it is entirely possible — and expected in practice — for the same signer address (e.g. a signer/miner key that is reused across multiple `.signers-*` or `.miners-*` StackerDB contracts, or across reward cycles) to be assigned the same numeric `slot_id` in two or more different StackerDB contracts: [5](#0-4) 

In that scenario, a valid signature obtained from one legitimately-signed chunk (say, contract A, `slot_id=3`, `slot_version=5`, some `data_hash`) can be replayed verbatim as a chunk write into contract B's slot 3, as long as the attacker can also produce/observe a chunk whose data hashes to the same value and versioning constraints (`slot_version`, staleness, `max_writes`) are independently satisfiable per-contract. Since `slot_version` is also just a Lamport clock local to a specific slot and is not itself bound to the contract, and the `data_hash` only commits to the *data bytes* (which the replayer controls/observes), this is a straightforward cross-context signature reuse: the digest that gates writes to a StackerDB (`Pool.sol`/`Synth.sol`-style "equality that's supposed to fail-closed but doesn't actually check enough") does not include the one piece of context (`contract_id`) that scopes the trust the smart contract intended to establish.

### Impact Explanation
This allows an unprivileged network peer who has observed (or can construct) one valid signed chunk from a signer to inject/replay that same signed chunk data into a *different* StackerDB contract's identically-numbered slot that the same signer key controls, without holding that signer's private key for that specific DB context. This is an unauthorized write to StackerDB state via forged/misapplied authorization — matching the "unauthenticated/unauthorized write to state or StackerDB" and "network-wide propagation of forged data" impact categories, since accepted pushed/gossiped chunks are relayed to other peers via `StackerDBPushChunk`.

### Likelihood Explanation
Exploitability requires: (1) the same signer address is assigned the same `slot_id` across two+ StackerDB contracts (plausible given the signer/miner StackerDB naming and rotation patterns used in this codebase), and (2) satisfying the target contract's own version/staleness/max_writes gates independently, which is generally easy since versions reset per contract/slot. No secret key or admin role is required — only observation of one legitimately-broadcast chunk (which is, by design, publicly gossiped).

### Recommendation
Bind the StackerDB contract identity into the signed digest. Modify `SlotMetadata::auth_digest` (and the `sign`/`verify` call sites) to also hash the `QualifiedContractIdentifier` (or a network/chain-scoped identifier of the specific StackerDB instance) so that a signature is only valid within its intended contract context:
```rust
fn auth_digest(&self, contract_id: &QualifiedContractIdentifier) -> Sha512Trunc256Sum {
    let mut hasher = Sha512_256::new();
    hasher.update(contract_id.to_string().as_bytes());
    hasher.update(self.slot_id.to_be_bytes());
    hasher.update(self.slot_version.to_be_bytes());
    hasher.update(self.data_hash.0);
    Sha512Trunc256Sum::from_hasher(hasher)
}
```
This requires updating `sign`/`verify` signatures throughout `libstackerdb`, `stackslib/src/net/stackerdb/db.rs`, `stackslib/src/net/stackerdb/mod.rs`, and the HTTP API handlers to thread the contract identifier through, plus a wire-format/versioning consideration since this changes what data is signed (backwards compatibility must be handled via an epoch gate or similar).

### Proof of Concept
1. Deploy (or use existing) two StackerDB contracts, A and B, both assigning slot 0 to the same signer address `S` (realistic if `S` is reused as a signer/miner key across rotations or contract types).
2. Signer `S` legitimately signs and pushes chunk `(slot_id=0, slot_version=1, data=D)` to contract A. This chunk (and its signature) is publicly gossiped over the p2p network per `handle_unsolicited_StackerDBPushChunk`.
3. An attacker observes this chunk/signature on the wire and repackages it as a `StackerDBPushChunk`/HTTP POST to contract B's `/v2/stackerdb/.../chunks` endpoint using slot 0.
4. `RPCPostStackerDBChunkRequestHandler::try_handle_request` calls `tx.try_replace_chunk` for contract B, which calls `slot_desc.verify(&slot_validation.signer)` — this passes because `auth_digest` never included contract A vs B, and the recovered pubkey hash still matches `S`.
5. As long as contract B's slot 0 currently has `slot_version < 1` and `1 <= config.max_writes`, the write succeeds, and the ack causes the node to further relay this chunk into contract B's StackerDBPushChunk gossip, propagating the cross-contract-replayed data to the whole network.         let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
