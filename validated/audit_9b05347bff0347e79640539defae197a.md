### Title
Out-of-bounds read parsing ZIP central directory entries in ijar - (File: `third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry`, used by the `ijar` interface-jar generator to scan a JAR/ZIP's central directory, reads `file_name_length`, `extra_field_length`, and `file_comment_length` directly from attacker-controlled file bytes and advances the read cursor `p` by those lengths with no bounds check against the mmap'd input buffer.

### Finding Description
`FindZipCentralDirectory` only validates that `cd.central_dir_offset + cd.central_dir_size <= in_length` before handing off a pointer into the mmap'd file [1](#0-0) . Once inside the per-entry loop, `ProcessCentralDirEntry` reads the 16-bit length fields straight from the crafted bytes and unconditionally does `p += file_name_length; ... extra_p += data_size; ... p += file_comment_length;` with no equivalent of the `EnsureRemaining()` check that guards the local-file-header parser [2](#0-1) . Compare this to `ProcessLocalFileEntry`, which explicitly calls `EnsureRemaining(file_name_length_, "file_name")` and `EnsureRemaining(extra_field_length_, "extra_field")` before advancing `p` over attacker-controlled lengths [3](#0-2) . No such check exists for the central directory scan.

The input buffer `zipdata_in_` is a raw mmap of the whole file [4](#0-3) , with `in_offset_`/`in_length` fixed at open time. If the last (or any) central-directory entry declares `file_name_length`, `extra_field_length`, or `file_comment_length` values that make the cursor exceed the file's actual size — while the file still satisfies the earlier `central_dir_offset + central_dir_size <= in_length` sanity check (e.g., a short comment/extra field is declared in the fixed EOCD but a later entry's variable-length fields are inflated) — `p`/`extra_p` walk past the end of the mapped region into unmapped memory. This is read via `get_u2le`/`get_u4le`/`get_u8le`/`memcpy` inside `ProcessCentralDirEntry` (the `memcpy(filename, p, len)` call at line 520 is especially notable, since it also copies unmapped/adjacent memory into a fixed 4096-byte stack buffer if the read lands on mapped-but-uninitialized pages rather than faulting) [5](#0-4) . This directly mirrors the CVE-2019-15505 pattern: length/offset fields taken from untrusted, crafted input drive a read past the buffer's real bounds with no local validation.

### Impact Explanation
This is a classic out-of-bounds read: worst case a segmentation fault (denial of service for that build action) and, when the adjacent mapped pages happen to contain other process memory (e.g. zero-fill pages beyond a page-aligned mmap, or heap data if a small buffer was used instead of mmap on some platform paths), a potential information disclosure of adjacent memory copied into the `filename` buffer that is subsequently used/logged. `ijar` runs as a Bazel build tool (`IjarAction`/`ijar` binary) processing jar files provided to the build — including prebuilt/imported jars from `java_import`, `http_jar`/`http_file`, or Maven-resolved artifacts. An attacker who controls the bytes of a jar consumed by a build (a hostile artifact registry/mirror, or any dependency whose bytes the attacker authors even if pinned by hash) can craft a ZIP whose central directory entries have inflated length fields to trigger this OOB read during `ijar` processing.

### Likelihood Explanation
Reaching this path only requires that a jar file with a validly-signed EOCD/central directory (able to pass the coarse `central_dir_offset + central_dir_size <= in_length` check) be run through `ijar`, which is routine for prebuilt/imported jar dependencies in Java rules. Crafting a ZIP with correct EOCD/central-dir-size bookkeeping but oversized per-entry `file_name_length`/`extra_field_length`/`file_comment_length` fields is straightforward with any hex editor or `zipfile` library, analogous to the crafted-device-traffic technique in the referenced CVE. A pinned sha256/integrity check on the archive download does not prevent this, since the check only confirms the bytes match what the attacker published — it does not validate ZIP structural invariants.

### Recommendation
Add bounds checks (an `EnsureRemaining`-equivalent measured against the mapped file length, not just the declared `central_dir_size`) in `ProcessCentralDirEntry` before advancing `p`/`extra_p` past `file_name_length`, `extra_field_length`, `data_size`, and `file_comment_length`, mirroring the checks already present in `ProcessLocalFileEntry`. Reject entries whose declared variable-length fields would read past `zipdata_in_ + in_length`.

### Proof of Concept
A `BuildIntegrationTestCase`/`src/test/shell/bazel` proof would construct a minimal valid ZIP (single stored entry) whose EOCD's `central_dir_size` matches a truncated central directory, but whose sole `CDH` entry declares `file_name_length = 0xFFFF` (or `extra_field_length`/`file_comment_length` similarly inflated) such that `end_of_central_dir - central_dir_size + entry_header_size + file_name_length` exceeds the actual mmap'd file size; feed this file to the `ijar` binary (or an `IjarAction`-driving `java_import` target consuming it as a prebuilt jar) and observe a crash/OOB read in `ProcessCentralDirEntry`, confirming the missing bounds check identified above. ```text
bool InputZipFile::ProcessCentralDirEntry(const u1 *&p, u8 *compressed_size,
                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
  const u1 *extra_p = p;
  p += extra_field_length;
  while (extra_p != p) {
    const u2 header_id = get_u2le(extra_p);
    const u2 data_size = get_u2le(extra_p);
    const u1 *extra = extra_p;
    extra_p += data_size;
    if (header_id == ZIP64_EXTRA_FIELD_TAG) {
      if (*uncompressed_size == U4_MAX) {
        *uncompressed_size = get_u8le(extra);
      }
      if (*compressed_size == U4_MAX) {
        *compressed_size = get_u8le(extra);
      }
      if (*offset == U4_MAX) {
        *offset = get_u8le(extra);
      }
    }
  }
  p += file_comment_length;
  return true;
}
