### Title
Object-quarantine directory check skips per-repository ownership validation for paths ending in `quarantine`/`tmp_objdir*`, enabling cross-repository object access - (File: internal/git/localrepo/paths.go)

### Summary
`Repo.ObjectDirectoryPath` is supposed to guarantee that a client-supplied `GitObjectDirectory` either points inside the repository's own object store, or, if it points at a quarantine directory, that it actually belongs to *that* repository's quarantine (verified via a repository-specific temp-dir prefix). However, the function contains a shortcut that skips the ownership check entirely whenever the *last path segment* of the resolved relative path is literally named `quarantine`, or the parent segment is `quarantine` and the base has a `tmp_objdir` prefix. This heuristic does not verify that the quarantine directory belongs to the target repository or the caller's own transaction — it only checks that the resolved path stays inside the storage root.

### Finding Description
`ObjectDirectoryPath` resolves `repo.GetGitObjectDirectory()` (a field fully controlled by the `gitalypb.Repository` message in the RPC request) and validates it in two steps:

1. It always requires the joined path to stay within the storage root via `storage.ValidateRelativePath(storagePath, ...)`. [1](#0-0) 

2. It then computes `isTransactionQuarantineDir` purely from the final one-or-two path segments of the *resolved relative path*, and if true, **skips** the subsequent check that ties the quarantine directory to the specific repository (via `storage.QuarantineDirectoryPrefix(repo)` and the repo's own temp dir): [2](#0-1) 

The per-repository ownership check (`expectedQuarantinePrefix := filepath.Join(tempDir, storage.QuarantineDirectoryPrefix(repo))` and the `strings.HasPrefix` comparison) is the *only* mechanism that ties a manually-configured object directory to the calling repository/transaction. When `isTransactionQuarantineDir` is true, this tie-back is never evaluated — the code accepts any storage-internal path whose last component is named `quarantine` (this is exactly the directory name used by the transaction manager for its quarantine directories, as shown in `paths_test.go`'s "repo quarantined by transaction manager" case) regardless of which repository or transaction created it. [3](#0-2) 

This value flows directly from the gRPC request: `GitObjectDirectory`/`GitAlternateObjectDirectories` are plain proto string fields with no cryptographic binding to a particular transaction. [4](#0-3) 

Gitaly's own middleware acknowledges that these fields are meant only to be "looped back" by Rails from prior access-check calls, and explicitly documents that this is not enforced for accessor (read-only) RPCs: [5](#0-4) 

The comment at lines 278–281 states verbatim: "This property is violated in tests which manually configure the object directory or the alternate object directory. This allows for circumventing the transaction management by configuring the either of the object directories. We'll leave this unaddressed for now..." — i.e., the Gitaly team is aware that any caller able to set these fields on an accessor RPC (paired with the `relative-path-bin` metadata key, which is not authenticated/bound to a specific transaction either) bypasses transaction-scoped quarantine isolation.

This is structurally the same bug class as the external report: a multi-step, security-sensitive workflow (quarantine → validate → migrate) exposes an intermediate, unauthenticated state (the quarantine directory reference) to being manipulated by an untrusted caller before the "safe" step (migration/eventual authorization) completes, because the system trusts that only an internal, well-behaved component (Rails loop-back / `pre-receive` for the token report; here the caller of an accessor RPC) will ever populate this field.

### Impact Explanation
An attacker who can issue Gitaly RPCs with a crafted `Repository` message (setting `GitObjectDirectory`/`GitAlternateObjectDirectories` to a storage-relative path ending in `quarantine` or `quarantine/tmp_objdir-*`, together with the `relative-path-bin` metadata header) can cause Gitaly to configure `GIT_OBJECT_DIRECTORY`/`GIT_ALTERNATE_OBJECT_DIRECTORIES` for git subprocesses to point at a quarantine directory that does not belong to the caller's own repository/transaction. Because the per-repository prefix check is skipped, git commands run against the target repository will additionally search (and expose the contents of) any other repository's or transaction's in-flight quarantine directory that happens to reside under the same storage, potentially disclosing objects (commits/blobs/trees) that are still pending authorization (i.e., not yet approved by `pre-receive`/`update` hooks or transaction voting) — a cross-repository/cross-tenant object disclosure and a bypass of the quarantine isolation guarantee.

### Likelihood Explanation
Reaching this path requires the caller to be able to set `GitObjectDirectory`/`GitAlternateObjectDirectories` fields on an accessor RPC and to guess/know a valid storage-relative quarantine path. The `relative-path-bin` metadata and the `GitObjectDirectory` field are both attacker-controllable at the RPC layer, and the code path explicitly exists ("does not start a new transaction") to accommodate exactly this case for accessor RPCs. The comment in `middleware.go` confirms this is a known, currently-unaddressed gap. The main mitigating factor is that the caller must be able to reach Gitaly directly with a crafted Repository message (rather than only through Rails) and must guess a live quarantine path, which reduces — but does not eliminate — practical exploitability.

### Recommendation
Do not special-case paths merely because their base name is `quarantine`/`tmp_objdir*`. Always require the manually-configured object directory to be validated against a value that is cryptographically or structurally bound to the requesting transaction/repository (e.g., always enforce the `expectedQuarantinePrefix` check, and/or require the transaction ID embedded in the path to match the transaction extracted from the request context) rather than relying on directory-naming conventions that any caller can reproduce.

### Proof of Concept
Not independently reproduced end-to-end (no execution environment available); the analysis is based on static code review of the referenced files. A concrete PoC would need to: (1) start a write transaction against Repo A, causing Gitaly to create a `.../<tx-tmp>/quarantine` directory containing not-yet-committed objects; (2) as a separate caller, issue an accessor RPC (e.g. `GetObjectDirectorySize`/`FindCommits`) against Repo B with `Repository.GitObjectDirectory` set to the relative path of Repo A's `quarantine` directory and the `relative-path-bin` metadata header set to Repo B's relative path; (3) observe that `ObjectDirectoryPath`'s `isTransactionQuarantineDir` shortcut accepts the path without validating it against Repo B's own quarantine prefix, allowing objects from Repo A's in-flight quarantine to be read via Repo B's RPC context.

	baseDir := filepath.Base(relativeObjectDirectoryPath)
	isTransactionQuarantineDir := (baseDir == "quarantine") || ((parentDir == "quarantine") && strings.HasPrefix(baseDir, "tmp_objdir"))

	// Transactions quarantine a repository by pointing the object directory to a 'quarantine' named
	// directory in the transaction's temporary directory. If the base directory is `quarantine`,
	// Git push may apply an additional layer of quarantine such as `/quarantine/tmp_objdir-incoming-Gbc29N`
	// so we don't assert the `/quarantine` being the last element of the path. We thus also check for
	// whether the parent directory is in `quarantine` and whether the base directory has the expected
	// `tmp_objdir` suffix.
	if !isTransactionQuarantineDir {
		// We need to check whether the relative object directory as given by the repository is
		// a valid path. This may either be a path in the Git repository itself, where it may either
		// point to the main object directory storage or to an object quarantine directory as
		// created by git-receive-pack(1). Alternatively, if that is not the case, then it may be a
		// manual object quarantine directory located in the storage's temporary directory. These
		// have a repository-specific prefix which we must check in order to determine whether the
		// quarantine directory does in fact belong to the repo at hand.

			tempDir, err := repo.locator.TempDir(repo.GetStorageName())
			if err != nil {
				return "", structerr.NewInvalidArgument("getting storage's temporary directory: %w", err)
			}

			expectedQuarantinePrefix := filepath.Join(tempDir, storage.QuarantineDirectoryPrefix(repo))
			absoluteObjectDirectoryPath := filepath.Join(repoPath, objectDirectoryPath)

			// The relative path is outside of the repository
			if !strings.HasPrefix(absoluteObjectDirectoryPath, expectedQuarantinePrefix) {
				return "", structerr.NewInvalidArgument("not a valid relative path: %w", origError)
