### Title
Contract self-destruct leaves stale `StorageRowStore` rows at the address, letting a CREATE2 redeploy inherit residual state from the prior "domain" - (File: `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java`)

### Summary
The Xen CVE is a "resource deassignment leaves stale state that the next owner can access" bug: a PCI device is handed back to dom0 without the IOMMU/host clearing in-flight DMA state, so the old tenant's activity corrupts the new owner's memory. The structural analog in java-tron is `SELFDESTRUCT`/`SELFDESTRUCT`-with-`CREATE2` address reuse: when a contract self-destructs, its account and code are deleted, but its key/value storage rows in `StorageRowStore` are never cleared. If a new contract is deployed to the exact same address (via `CREATE2` with the same salt/init-code, which is fully attacker-controlled), the new contract inherits whatever was left in the old contract's storage slots.

### Finding Description
`RepositoryImpl.deleteContract()` only deletes the code, account and contract-metadata entries — it never touches contract storage: [1](#0-0) 

The same pattern exists in `TransactionTrace.deleteContract()`: [2](#0-1) 

`Program.suicide()`/`suicide2()` call `markSelfDestruct()` and record the address for deletion but likewise never issue a storage-clearing operation on the destroyed contract's `Storage`/`StorageRowStore` rows: [3](#0-2) 

`Storage` is keyed by `addrHash = sha3(address)` (or `sha3(address ++ trxHash)` for CREATE2 contracts via `generateAddrHash`), and rows are only removed from `StorageRowStore` lazily, when a slot is explicitly written to zero during `commit()`: [4](#0-3) 

Because `compose()`/`addrHash()` derive the storage key purely from the contract address (and, for CREATE2, from the deploying transaction hash which is attacker-supplied), redeploying an equivalent contract to the same address via `CREATE2` (same factory, same salt, same init code) reproduces the identical `addrHash`, so any storage rows never explicitly zero-written by the destroyed contract remain readable/writable by the new contract instance. `RepositoryImpl.getStorage()` builds the `Storage` object solely from `address`/`contract.getTrxHash()`, with no check for prior self-destruction: [5](#0-4) 

This is analogous to the Xen issue: the "device" (contract storage namespace) is handed back to a neutral state (dom0/no owner) after teardown, but residual writes ("in-flight DMA") from the old tenant are not cleared before the namespace is reassigned to a new tenant.

### Impact Explanation
If exploitable, an attacker-controlled factory contract could deploy contract A at address X via `CREATE2`, have A write attacker-chosen values into specific storage slots, self-destruct A, then redeploy a different contract B (different bytecode/logic but reusing the same slot layout) at the same address X. B's constructor may implicitly trust that its storage starts zeroed (e.g., an "owner"/"initialized" flag, an allowance, a frozen balance accounting slot used by TVM-level opcodes). If B does not explicitly re-zero all slots it relies on, residual data from A could let an attacker bypass an initialization check, forge an "authorized" flag, or corrupt internal accounting — a form of unauthorized privilege escalation within the TVM execution environment, matching the "gain host/privileged state via residual resource contamination" impact class.

### Likelihood Explanation
Reaching this path requires only an ordinary unprivileged account able to deploy/trigger smart contracts (`CreateSmartContract`/`TriggerSmartContract`), fully within the "contract deployer" threat model allowed by the rules. `CREATE2` and `SELFDESTRUCT` are both standard, always-reachable TVM opcodes; no privileged role or witness/SR access is needed. However, actual exploitation is conditional on there being a specific victim contract pattern that (a) is deployed via `CREATE2` at a predictable/attacker-chosen address and (b) fails to zero-initialize all storage slots it depends on for security decisions — the vulnerability is in the underlying storage-non-clearing primitive, not a self-contained exploit against a fixed contract. This mirrors upstream go-ethereum/EVM implementations, which have long been known to have this exact address-reuse storage characteristic; it is a well-known, low-severity-by-itself, TVM-inherent state-machine property rather than a distinct java-tron logic bug, so exploitability strongly depends on higher-layer (Solidity) contract design rather than the VM itself.

### Recommendation
Because clearing all storage rows for a destroyed contract at commit time would require an expensive full-range delete keyed by `addrHash`, consider either: (1) tracking and explicitly deleting known non-zero storage rows for a self-destructed address before the address can be reused by a subsequent `CREATE2`, or (2) rejecting `CREATE2` redeployment to any address flagged as previously self-destructed (`isSelfDestructed`) within the same repository/lineage, forcing a fresh `addrHash` derivation (e.g., incorporating a monotonically increasing "generation"/nonce component in `addrHash` on redeploy) so residual rows from the prior incarnation are unreachable.

### Proof of Concept
Conceptual reproduction (cannot be validated further without executing the TVM):
1. Deploy `Factory` contract F.
2. From F, `CREATE2(salt, initCodeA)` deploys contract A at address X; A writes a sentinel/privileged value into storage slot `S` and returns.
3. Call `A.selfdestruct(beneficiary)` — `Program.suicide()`/`suicide2()` mark A self-destructed; `RepositoryImpl.deleteContract`/`TransactionTrace.deleteContract` remove account/code/contract metadata for X but leave slot `S` in `StorageRowStore` untouched.
4. From F, `CREATE2(salt, initCodeB)` with the same salt (and, if `trxHash`-based `addrHash` is used, arranged so `addrHash` matches, e.g., same deploying transaction pattern) redeploys contract B at the same address X.
5. B reads slot `S` via `SLOAD` expecting it to be zero (fresh contract); it instead observes A's leftover value, potentially bypassing an initialization guard implemented as `require(slotS == 0)`.

Given the uncertainty of step 4's exact `addrHash` collision conditions (dependent on `contract.getTrxHash()` handling in `RepositoryImpl.getStorage()`), full confirmation of end-to-end exploitability requires running the TVM test harness (e.g., extending `Create2Test`/`FreezeTest`) rather than static review alone.

        storage = new Storage(parentStorage);

      if (!ByteUtil.isNullOrZeroArray(contract.getTrxHash())) {
        storage.generateAddrHash(contract.getTrxHash());
      }
    }
    return storage;
  }

  public void generateAddrHash(byte[] trxId) {
    // update addreHash for create2
    addrHash = addrHash(address, trxId);
  }

  public DataWord getValue(DataWord key) {
    if (rowCache.containsKey(key)) {
      return new DataWord(rowCache.get(key).getValue());
    } else {
      StorageRowCapsule row = store.get(compose(key.getData(), addrHash));
      if (row == null || row.getInstance() == null) {
        return null;
      }
      rowCache.put(key, row);
      return new DataWord(row.getValue());
    }
  }

  public void put(DataWord key, DataWord value) {
    if (rowCache.containsKey(key)) {
      rowCache.get(key).setValue(value.getData());
    } else {
      byte[] rowKey = compose(key.getData(), addrHash);
      StorageRowCapsule row = new StorageRowCapsule(rowKey, value.getData());
      rowCache.put(key, row);
    }
  }

  public void commit() {
    rowCache.forEach((DataWord rowKey, StorageRowCapsule row) -> {
      if (row.isDirty()) {
        if (new DataWord(row.getValue()).isZero()) {
          this.store.delete(row.getRowKey());
        } else {
          this.store.put(row.getRowKey(), row);
        }
      }
    });
  }
