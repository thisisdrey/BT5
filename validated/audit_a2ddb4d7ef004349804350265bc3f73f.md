## Title
Market (TRC10) order matching treats `sellTokenQuantity`/`buyTokenQuantity` as equal-scale integers, ignoring per-asset `precision`, causing severely mispriced trades - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
The reported Carapace bug assumes a token has 18 decimals when it actually has 6 (USDC), so conversion math silently mis-scales value. The analogous flaw in java-tron's on-chain TRC10 exchange (the "Market" feature, reachable from any account via `MarketSellAssetContract`) is that TRC10 tokens can be issued with any `precision` from 0 to 6 (validated only for range, never compared across tokens), yet all Market order price/matching logic operates purely on the raw integer `sellTokenQuantity`/`buyTokenQuantity` fields with no normalization for each token's declared decimal precision.

### Finding Description
When an asset is issued, `AssetIssueActuator` only validates that `precision` is between 0 and `PRECISION_DECIMAL` (6); it does not require all tokens to share a common precision: [1](#0-0) 

When a user places a TRC10 sell order via `MarketSellAssetActuator`, the contract's raw `sellTokenQuantity`/`buyTokenQuantity` are taken directly as the exchange ratio for the order book, with no reference to either token's `precision`: [2](#0-1) 

`validate()` looks up the `AssetIssueCapsule` for both `sellTokenID` and `buyTokenID` (confirming the actuator has access to each token's `precision`) but never reads or compares `getPrecision()` for either side: [3](#0-2) 

The actual matching/price computation (`matchSingleOrder`, `MarketUtils.multiplyAndDivide`, `MarketComparator.comparePrice`) is pure integer ratio arithmetic on `sellTokenQuantity`/`buyTokenQuantity`, with the ratio treated as directly comparable across different token pairs: [4](#0-3) [5](#0-4) [6](#0-5) 

Because two TRC10 tokens can legally have different `precision` values (e.g., token A with precision 0 vs token B with precision 6, differing by a factor of 1,000,000 in "human" units per raw unit), the raw-quantity ratio used for order book price keys and matching does not represent the tokens' true relative economic value. This is structurally the same root cause as the reported bug: code assumes a uniform decimal scale across assets/tokens when the protocol actually allows heterogeneous decimals per asset, and the accounting/pricing math never rescales for it.

### Impact Explanation
An order placer (or counter-party market maker) who is unaware of, or who exploits, the precision mismatch between two TRC10 tokens can create or match sell orders whose "1:1 in raw units" ratio is actually worth orders of magnitude more or less once precision is accounted for. Since the Market matching engine executes real token/TRX transfers between accounts based purely on this raw ratio (`transferBalanceOrToken`, `matchSingleOrder`, asset balance debits/credits), a counter-party can be tricked into an economically catastrophic trade, or a malicious order placer can drain value from unsuspecting makers/takers — a concrete unauthorized transfer/theft of asset value via normal, permitted transaction types.

### Likelihood Explanation
This requires no special privilege: any account can issue a TRC10 asset with `precision` from 0–6 and any other account can freely place `MarketSellAssetContract` orders once `AllowMarketTransaction` is enabled by committee (a normal, already-enabled protocol feature, not a privileged action). Because tokens of differing precision naturally coexist on TRON (this is exactly the field's purpose), the mismatch condition is trivially reachable by ordinary users creating pairs among tokens with different precisions.

### Recommendation
Normalize `sellTokenQuantity`/`buyTokenQuantity` (or the derived price-key ratio) by each token's `AssetIssueCapsule.getPrecision()` before using them for price comparison, order-book key construction (`MarketUtils.createPairPriceKey`), and quantity matching (`MarketUtils.multiplyAndDivide`, `MarketComparator.comparePrice`), or explicitly require/document that Market trading pairs only be created between tokens of equal precision and enforce that check in `MarketSellAssetActuator.validate()`.

### Proof of Concept
1. Issue Token A with `precision = 0` and Token B with `precision = 6` via `AssetIssueActuator` (both pass validation since each precision individually is in `[0,6]`).
2. Account X places `MarketSellAssetContract{sellTokenId=A, sellTokenQuantity=1, buyTokenId=B, buyTokenQuantity=1}` — intending "1 A (whole unit) = 1 B (whole unit, i.e., 0.000001 raw B * precision)" but the system stores this as raw ratio 1:1.
3. Account Y, seeing the order book price key computed from raw quantities (`MarketUtils.createPairPriceKey`), matches with a sell order of B for A at the same 1:1 raw ratio, unaware that 1 raw unit of B is actually worth 1,000,000x less in real terms than the issuer intended if precision were honored.
4. Trade executes via `matchSingleOrder`/`ExchangeCapsule`-analogous token transfer, moving real asset value between accounts at a rate that ignores the 10^6 precision gap, allowing one party to receive far more value than given — mirroring the reported USDC decimals defect (uniform-decimals assumption breaking accounting) but manifesting as fund-losing mispriced trades in java-tron's on-chain Market feature.

  public static long multiplyAndDivide(long a, long b, long c, boolean disableMath) {
    try {
      long tmp = multiplyExact(a, b, disableMath);
      return floorDiv(tmp, c, disableMath);
    } catch (ArithmeticException ex) {
      // do nothing here, because we will use BigInteger to compute again
    }

    BigInteger aBig = BigInteger.valueOf(a);
    BigInteger bBig = BigInteger.valueOf(b);
    BigInteger cBig = BigInteger.valueOf(c);

    return aBig.multiply(bBig).divide(cBig).longValue();
  }
