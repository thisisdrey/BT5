### Title
Silent loss of gas-key refund when a gas-key's public key is deleted and re-added as a non-gas key before the refund receipt executes - ([File: runtime/runtime/src/actions.rs])

### Summary
`try_refund_gas_key_balance` looks up the access key by `(account_id, public_key)` and only credits the refund if `access_key.gas_key_info_mut()` returns `Some`; if the key exists but is no longer a gas key it returns `Ok(false)` without crediting any balance or recording anything in `tokens_burnt`. If an account deletes its gas key and re-adds the same public key as a `FullAccess`/`FunctionCall` key before a pending refund receipt targeting that key resolves, the refund silently vanishes.

### Finding Description
`try_refund_gas_key_balance` (runtime/runtime/src/actions.rs:115-132) fetches the access key for `(account_id, public_key)` and calls `access_key.gas_key_info_mut()`: [1](#0-0) 
When the key no longer carries `GasKeyInfo` (because it was deleted and re-added with `AccessKeyPermission::FullAccess` or `FunctionCall`), the function returns `Ok(false)` and performs no state mutation — the `deposit` amount is not added to the account balance, not added back to the gas key, and not accounted for in `result.tokens_burnt` anywhere in this function.

This mirrors the sibling function `try_refund_allowance` (lines 134-158), which was designed to silently no-op when the target key no longer matches the expected permission type — acceptable there because an allowance is not a token balance, only a spending cap. Applying the same "best effort, silently drop on mismatch" pattern to `try_refund_gas_key_balance`, which handles actual token amounts drawn from `GasKeyInfo.balance`, is a semantic error: a real deposit can disappear without being credited or burnt.

The `DeleteKey`/`AddKey` race is architecturally plausible in NEAR's asynchronous receipt model: a gas-key-signed `FunctionCall` that fails generates a refund receipt that is routed back to `(account_id, public_key)` as a separate receipt, processed later (potentially in a later block, depending on receipt/queue backlog). The signer fully controls the ordering and timing of subsequent `DeleteKey(PK)` + `AddKey(PK, FullAccess)` actions relative to that refund receipt, since both are the signer's own transactions.

### Impact Explanation
If confirmed to reach this code path without a fallback that guarantees crediting or burning the deposit, the impact is **permanent freezing of user funds**: the refund amount is deducted at receipt-creation time from the gas key's balance/escrow but never re-appears anywhere — not in the account's `amount()`, not in `GasKeyInfo.balance`, and not in `tokens_burnt`. This breaks the token-conservation invariant relied upon by the protocol's supply accounting.

### Likelihood Explanation
Preconditions require only actions available to an ordinary account: sign a `FunctionCall` via an existing gas key that is engineered to fail after partial gas consumption (e.g., calling an undeployed method, or exceeding available gas), and issue `DeleteKey`/`AddKey` for the same public key before the resulting refund receipt is applied. Both are ordinary, unprivileged transactions costing only gas/storage fees, and the race is fully controllable by the attacker's own transaction scheduling — no validator or node-level access is needed. Repeatability depends on reliably winning the receipt-ordering race, which is feasible since the account controls both the originating transaction and the follow-up key actions.

### Recommendation
Do not silently drop the deposit in `try_refund_gas_key_balance` when the target key is missing or no longer a gas key. Instead: (1) when the key doesn't exist or lost its gas-key status, fall back to crediting the account's normal balance via `action_transfer`-style logic, or (2) explicitly add the amount to `result.tokens_burnt` so total supply accounting stays consistent, mirroring how `delete_gas_key` explicitly burns remaining gas-key balances rather than dropping them.

### Proof of Concept
Runtime/apply-level test plan (in `runtime/runtime/src/tests/apply.rs` or `runtime/runtime/src/actions.rs` tests):
1. Create an account with a gas key `PK` (`num_nonces=1`) and fund it via `TransferToGasKeyAction`.
2. Submit a `FunctionCall` receipt signed via `PK` targeting a contract/method engineered to fail after partial gas consumption, producing a refund receipt back to `(account_id, PK)`.
3. Before that refund receipt is applied (i.e., insert it into the pending receipt queue but do not yet process it), apply `DeleteKey(PK)` followed by `AddKey(PK, FullAccess)` on the same account.
4. Process the pending refund receipt and call `try_refund_gas_key_balance` (or drive it through the full receipt-application path).
5. Assert: `gas_key_info_mut()` on the resulting access key is unaffected/unchanged, the account's `amount()` did not increase by the refund, and `result.tokens_burnt` did not increase by the refund — demonstrating `initial_balance != final_balance + tokens_burnt + fees`, i.e., conservation is violated and the deposit is unaccounted for.

Note: I was not able to fully inspect the caller of `try_refund_gas_key_balance` in `runtime/runtime/src/lib.rs` within the available tool budget, so I could not confirm whether that call site has an additional fallback (e.g., crediting the plain account balance or adding to `tokens_burnt`) when this function returns `false`. The finding above is proven at the function level (`try_refund_gas_key_balance` itself performs no accounting on the `false` path); confirming end-to-end fund loss requires verifying that the caller in `lib.rs` has no compensating fallback for the `Ok(false)` return.
