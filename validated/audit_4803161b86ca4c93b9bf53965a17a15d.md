### Title
Contract-creation address is predictable from a broadcast (unconfirmed) transaction, allowing front-run griefing that forces `CreateSmartContract` execution to fail - ([File: actuator/src/main/java/org/tron/core/actuator/VMActuator.java])

### Summary
`VMActuator.create()` computes the new contract's address deterministically from the pending transaction and then aborts if an account already exists at that address: [1](#0-0) 

The address is `sha3omit12(txRawDataHash || ownerAddress)`, computed by `WalletUtil.generateContractAddress(Transaction trx)`: [2](#0-1) 

Both inputs (`txRawDataHash`, i.e. the pending transaction's `raw_data` hash/txID, and `ownerAddress`) are fully visible to anyone observing the transaction once it is broadcast to the P2P/mempool layer, before it is packed into a block. This is analogous to the reported `WeightedIndex`/`WeightedIndex` bug: an address that will host a to-be-created contract can be predicted in advance by a third party, who can then race to occupy that address first, causing the legitimate creation to revert.

### Finding Description
In TRON, sending TRX to a non-existent address auto-creates an `AccountCapsule` at that address. Any account broadcaster who observes a pending `CreateSmartContract` transaction in the mempool can:
1. Read its `raw_data` (owner address, bytecode, fee limit, etc.) and compute `txRawDataHash` (the txID, i.e. `Sha256Hash.of(raw_data)`), which is public before the transaction is confirmed.
2. Compute the target contract address exactly as `VMActuator.create()`/`WalletUtil.generateContractAddress` will: `sha3omit12(txRawDataHash || ownerAddress)`.
3. Submit their own transaction (e.g. a simple TRX transfer, or an `AccountCreateContract`) targeting that predicted address, and have it mined first.

When the original `CreateSmartContract` transaction is later executed, `VMActuator.create()` checks: [1](#0-0) 

Since the attacker's transfer already created an `AccountCapsule` at the predicted address, `rootRepository.getAccount(contractAddress) != null` is true, and `create()` throws a `ContractValidateException`, aborting the deployment. The internal EVM-level `CREATE`/`CREATE2` path (`Program.createContractImpl`) has an equivalent, narrower check (`contractAlreadyExists`), but that path is for internal contract-to-contract creation and is comparatively harder to exploit because the salt/nonce derivation is scoped to the calling contract's own state.

This differs from the standard Ethereum threat model in one key respect noted in-repo: TRON's `CREATE` address does **not** depend on sender nonce but instead on the transaction hash (`txRawDataHash`) combined with the owner address, so any attacker observing the raw, unsigned-or-signed transaction data in the mempool learns the exact resulting address without needing to guess a nonce.

### Impact Explanation
A successful front-run causes the legitimate `CreateSmartContract` transaction to fail during execution (not during static validation), meaning it is included in a block and consumes bandwidth/energy fees, yet the contract is never deployed. This is a denial-of-service/griefing vector against specific, high-value contract deployments (e.g. deterministic/pre-announced deployer addresses, cross-chain or vanity deployments) that an unprivileged actor can trigger purely by broadcasting a transaction — no special privileges, keys, or SR/witness status are required. It matches the report's "creation reverts because target address already exists" bug class, but here the effect on java-tron is fee loss plus deployment failure/DoS on a specific transaction, rather than fund theft.

### Likelihood Explanation
Likelihood is low-to-moderate: the attacker must actively monitor the mempool for `CreateSmartContract` transactions and race a cheap transfer transaction ahead of it in the same or an earlier block. This is a purely opportunistic griefing attack with no economic upside for the attacker beyond disrupting a specific deployer, similar to the "Low likelihood" rating given in the original report.

### Recommendation
Before failing the `CreateSmartContract` execution outright when `rootRepository.getAccount(contractAddress) != null`, distinguish between "address holds actual contract code/state" (a real collision that must fail) versus "address only holds an EOA-style account with no code" (created merely via TRX transfer). For the latter case, follow the same pattern already used elsewhere in the codebase for CREATE2 collisions and the TIP‑2935 deploy path — upgrade the account type in place and preserve its balance instead of rejecting the creation: [3](#0-2) 

Applying the same "upgrade existing non-contract account" logic to `VMActuator.create()`'s top-level check (instead of unconditionally throwing `ContractValidateException`) would close this front-running griefing vector.

### Proof of Concept
1. Deployer `D` broadcasts a `CreateSmartContract` transaction `T` (unsigned raw data known, or signed and broadcast to mempool).
2. Attacker `A` observes `T` in the mempool, extracts `raw_data` to compute `txRawDataHash = Sha256Hash.of(T.raw_data)` and `ownerAddress = D`.
3. `A` computes `predicted = sha3omit12(txRawDataHash || ownerAddress)` — identical to what `WalletUtil.generateContractAddress(T)` will compute — [2](#0-1) .
4. `A` broadcasts a `TransferContract` sending 1 sun to `predicted`, which is confirmed in an earlier block, auto-creating an `AccountCapsule` there.
5. When `T` executes, `VMActuator.create()` finds `rootRepository.getAccount(contractAddress) != null` and throws `ContractValidateException("Trying to create a contract with existing contract address: ...")` — [1](#0-0) , so `D`'s deployment fails while still consuming fees.

```java
  public static byte[] generateContractAddress(Transaction trx) {

    CreateSmartContract contract = ContractCapsule.getSmartContractFromTransaction(trx);
    byte[] ownerAddress = contract.getOwnerAddress().toByteArray();
    TransactionCapsule trxCap = new TransactionCapsule(trx);
    byte[] txRawDataHash = trxCap.getTransactionId().getBytes();

    byte[] combined = new byte[txRawDataHash.length + ownerAddress.length];
    System.arraycopy(txRawDataHash, 0, combined, 0, txRawDataHash.length);
    System.arraycopy(ownerAddress, 0, combined, txRawDataHash.length, ownerAddress.length);

    return Hash.sha3omit12(combined);

  }
```
