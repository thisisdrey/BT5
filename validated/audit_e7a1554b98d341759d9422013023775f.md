I found the analog in `harvest_rewards`, which shadows the pool-side update just like the Solidity `rewardRate` bug — but here it's the opposite defect: the pool-side updated state is computed but never persisted to `Pools` storage.

### Title
`harvest_rewards` discards the pool's updated reward-accounting state, causing repeated over-distribution of rewards - (File: `substrate/frame/asset-rewards/src/lib.rs`)

### Summary
`Pallet::update_pool_and_staker_rewards` is a pure function that returns a *new*, updated `PoolInfoFor<T>` (with `reward_per_token_stored` and `last_update_block` advanced) alongside the updated staker info, explicitly documented as having "no side-effects" — the caller is responsible for persisting the result. [1](#0-0)  In `stake` and `unstake`, the caller correctly writes the returned `pool_info` back with `Pools::<T>::insert(pool_id, pool_info)`. [2](#0-1) [3](#0-2)  In `harvest_rewards`, however, the returned `pool_info` is bound as an immutable local and used only to source the `reward_asset_id`/`account` for the transfer — it is never written back to the `Pools` storage map. [4](#0-3) 

### Finding Description
`reward_per_token` is computed incrementally: each update advances `reward_per_token_stored` and `last_update_block` based on elapsed blocks since the last update. [5](#0-4)  Because `harvest_rewards` never calls `Pools::<T>::insert` with the freshly computed `pool_info`, the on-chain `last_update_block` for the pool stays stuck at whatever it was before the harvest (e.g., pool creation time, or the last time `stake`/`unstake` touched it). This mirrors the Solidity bug exactly: a locally-shadowed/returned value that looks like it updates the canonical state, but the write to the real storage location is missing.

The consequence: the *next* time anyone calls `reward_per_token` for this pool (via `stake`, `unstake`, or another `harvest_rewards`), `rewardable_blocks_elapsed` is computed from the stale `last_update_block`, spanning a window that includes blocks already paid out in the prior harvest. `reward_per_token_stored` for that pool is then advanced again over that same overlapping window, and `derive_rewards` for stakers factors in `reward_per_token` — the already-harvested time interval's rewards get counted a second time toward every staker's owed rewards. [6](#0-5) 

### Impact Explanation
This causes duplicate accrual/settlement of reward-asset payouts out of the pool's pot account (`pool_info.account`) — the same block-range worth of `reward_rate_per_block` rewards is credited to stakers more than once across successive harvests, silently draining the pool's reward-asset balance faster than intended and paying more than the reward schedule allows. This falls squarely under "duplicate settlement or payout" / conservation-of-value violation for a reward-payout pallet, since the transfer in `harvest_rewards` moves real assets from the pool's pot account to the staker based on this double-counted amount. [7](#0-6) 

### Likelihood Explanation
This is deterministic and always occurs for every call to `harvest_rewards`, triggerable by any signed staker with a stake in a pool — no privileged, admin, or off-chain actor is needed. [8](#0-7)  Any pool that receives more than one harvest across its lifetime (an extremely common usage pattern) is affected.

### Recommendation
In `harvest_rewards`, persist the updated pool info exactly as `stake`/`unstake` already do:
```rust
let (pool_info, mut staker_info) =
    Self::update_pool_and_staker_rewards(&pool_info, &staker_info)?;

// ... transfer logic ...

Pools::<T>::insert(pool_id, pool_info); // missing write-back
```

### Proof of Concept
1. Create a pool with `reward_rate_per_block = R` and have a staker `stake` `amount` tokens at block `N0` (this sets `last_update_block = N0`).
2. Advance to block `N1`. Call `harvest_rewards` — internally `reward_per_token` advances `reward_per_token_stored` for the `[N0, N1]` window and pays the staker accordingly, but `Pools::<T>::insert` is never called, so on-chain `last_update_block` remains `N0`.
3. Advance to block `N2 > N1`. Call `harvest_rewards` again. `reward_per_token` recomputes `rewardable_blocks_elapsed` as `N2 - N0` (instead of `N2 - N1`), re-crediting the staker for the already-paid `[N0, N1]` window on top of the new `[N1, N2]` window.
4. Repeat: each harvest re-pays the pool's entire history since the last `stake`/`unstake`/`set_pool_*` call (the only calls that do persist `pool_info`), draining the pool's reward pot faster than the configured `reward_rate_per_block` schedule permits.

		#[pallet::call_index(3)]
		pub fn harvest_rewards(
			origin: OriginFor<T>,
			pool_id: PoolId,
			staker: Option<T::AccountId>,
		) -> DispatchResult {
			let caller = ensure_signed(origin)?;
			let staker = staker.unwrap_or(caller.clone());

			// Always start by updating the pool and staker rewards.
			let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
			let now = T::BlockNumberProvider::current_block_number();
			ensure!(now > pool_info.expiry_block || caller == staker, BadOrigin);

			let staker_info =
				PoolStakers::<T>::get(pool_id, &staker).ok_or(Error::<T>::NonExistentStaker)?;
			let (pool_info, mut staker_info) =
				Self::update_pool_and_staker_rewards(&pool_info, &staker_info)?;

			// Transfer unclaimed rewards from the pool to the staker.
			T::Assets::transfer(
				pool_info.reward_asset_id,
				&pool_info.account,
				&staker,
				staker_info.rewards,
				// Could kill the account, but only if the pool was already almost empty.
				Preservation::Expendable,
			)?;

			// Emit event.
			Self::deposit_event(Event::RewardsHarvested {
				caller,
				staker: staker.clone(),
				pool_id,
				amount: staker_info.rewards,
			});

			// Reset staker rewards.
			staker_info.rewards = 0u32.into();

			if staker_info.amount.is_zero() {
				PoolStakers::<T>::remove(&pool_id, &staker);
			} else {
				PoolStakers::<T>::insert(&pool_id, &staker, staker_info);
			}

			Ok(())
		}

		/// Computes update pool and staker reward state.
		///
		/// Should be called prior to any operation involving a staker.
		///
		/// Returns the updated pool and staker info.
		///
		/// NOTE: this function has no side-effects. Side-effects such as storage modifications are
		/// the responsibility of the caller.
		pub fn update_pool_and_staker_rewards(
			pool_info: &PoolInfoFor<T>,
			staker_info: &PoolStakerInfo<T::Balance>,
		) -> Result<(PoolInfoFor<T>, PoolStakerInfo<T::Balance>), DispatchError> {
			let reward_per_token = Self::reward_per_token(&pool_info)?;
			let pool_info = Self::update_pool_rewards(pool_info, reward_per_token)?;

			let mut new_staker_info = staker_info.clone();
			new_staker_info.rewards = Self::derive_rewards(&staker_info, &reward_per_token)?;
			new_staker_info.reward_per_token_paid = pool_info.reward_per_token_stored;
			return Ok((pool_info, new_staker_info));
		}

		/// Derives the current reward per token for this pool.
		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}
