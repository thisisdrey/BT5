### Title
Instruction-data cost floor-division under-charges block/account cost accounting, enabling QoS evasion - (File: `cost-model/src/cost_model.rs`)

### Summary
`CostModel::get_instructions_data_cost` computes the compute-unit cost attributed to a transaction's instruction data by performing integer (floor) division: `transaction.instruction_data_len() / (INSTRUCTION_DATA_BYTES_COST as u16)`. Because `INSTRUCTION_DATA_BYTES_COST` is `140 / COMPUTE_UNIT_TO_US_RATIO` (`= 4`), any instruction-data length that is not an exact multiple of 4 bytes has its cost truncated down instead of rounded up. This mirrors the reported MetaMorpho bug class: a resource-limit-relevant quantity is computed by rounding in the caller's favor, allowing the real resource usage to exceed what is charged against a hard cap.

### Finding Description
`get_instructions_data_cost` is used unconditionally in every cost computation path — `calculate_cost`, `estimate_cost`, and `calculate_cost_for_executed_transaction` — via `Self::get_instructions_data_cost(transaction)`. [1](#0-0) 
This value (`data_bytes_cost`) is added into `TransactionCost::sum()`, which is the exact quantity checked against `CostTrackerLimits::block_cost` and `CostTrackerLimits::account_cost` in `CostTracker::try_add`. [2](#0-1) [3](#0-2) 

Because the division floors instead of ceiling, an instruction-data length like `4n+3` bytes is charged the same `data_bytes_cost` as `4n` bytes — i.e., up to 3 bytes (and, in relative terms, up to 3/4 of one unit-cost bucket) of real data-processing cost per transaction is unaccounted for. Since `try_add` is the sole gatekeeper of `MAX_BLOCK_UNITS` / `MAX_WRITABLE_ACCOUNT_UNITS`, and this per-transaction shortfall is systematic (occurs for 3 out of every 4 possible data lengths), an attacker can craft many transactions whose instruction-data length is deliberately chosen at the `4n+3` boundary to maximize the ratio of unaccounted cost to accounted cost, causing the actual aggregate resource cost admitted into a block to exceed the value the cost tracker believes it has admitted.

This is directly analogous to the reported bug: `_supplyMorpho`'s `toSupply` estimate must round in favor of the protocol (round the subtrahend up) to guarantee the cap is never breached; here, `data_bytes_cost` must round up (ceiling) to guarantee the block/account cost cap is never under-counted, but it rounds down instead.

### Impact Explanation
Systematic underestimation of `data_bytes_cost` lets slightly more real instruction-data processing cost into a block than the cost tracker accounts for. This is a QoS/cost-accounting evasion: the leader's block-cost-limit enforcement (`MAX_BLOCK_UNITS`, `MAX_WRITABLE_ACCOUNT_UNITS`) is meant to bound per-block resource consumption; consistently under-charging one of its cost components erodes that bound. The magnitude per transaction is small (at most 3 raw bytes' worth of the 4-bytes-per-unit rate, i.e., under 1 CU per transaction), so the practical impact is a minor systemic underestimation rather than a large single-shot cap breach.

### Likelihood Explanation
Any transaction whose serialized instruction data length is not a multiple of 4 triggers this rounding, which is the common case (any attacker fully controls their own transaction's instruction data length), so the underestimation is trivially and repeatedly reachable by any unprivileged transaction submitter without special permissions.

### Recommendation
Change `get_instructions_data_cost` to round up (ceiling division) instead of floor division, e.g.:
```rust
fn get_instructions_data_cost(transaction: &impl TransactionMeta) -> u16 {
    transaction
        .instruction_data_len()
        .div_ceil(INSTRUCTION_DATA_BYTES_COST as u16)
}
```
This guarantees `data_bytes_cost` never underestimates the true resource cost, consistent with how `get_prioritization_fee` in `compute-budget/src/compute_budget_limits.rs` already rounds up to protect against underestimation. [4](#0-3) 

### Proof of Concept
1. Construct a transaction whose `instruction_data_len()` is, e.g., `4k+3` bytes for varying `k` (fully controllable by any unprivileged client).
2. Compute `data_bytes_cost = instruction_data_len / 4` (floor division) as done in `get_instructions_data_cost`. [5](#0-4) 
3. Observe that the true "cost-per-byte-rate" implies `ceil(instruction_data_len/4)` units should be charged, but the tracker only ever accounts for `floor(instruction_data_len/4)` via `TransactionCost::sum()`, which feeds directly into `CostTracker::try_add`'s block/account limit checks. [6](#0-5) 
4. Repeating this across many transactions in a block accumulates an under-counted total relative to the true intended per-byte cost rate, without ever tripping `WouldExceedBlockMaxLimit`/`WouldExceedAccountMaxLimit` for the "missing" cost.
