### Title
Protocol fee can be fully bypassed on NEP-245/IMT `TokenDiff` intents by splitting a trade into unit-amount (`delta = ±1`) intents - ([File: contracts/defuse/core/src/intents/token_diff.rs])

### Summary
`TokenDiff::token_fee` deliberately charges `Pips::ZERO` fee whenever the traded amount of a `Nep245` or `Imt` token is `≤ 1`. This exception was added to avoid nonsensical fee rounding on true non-fungible transfers, but `Nep245`/`Imt` token IDs are also used to represent **fungible** balances (e.g. wrapped NEP-141 tokens re-exposed as `nep245:<contract>:<inner_token_id>`, or IMT-minted fungible supplies). Any signer can therefore split one large trade into many separate signed `TokenDiff` intents, each with `|delta| = 1` on the same token, and pay **zero** protocol fee on the entire notional amount instead of the fee that a single intent of the same aggregate size would owe.

### Finding Description
`TokenDiff::execute_intent` computes the fee to collect per negative delta as: [1](#0-0) 

The fee rate itself is derived from `token_fee`: [2](#0-1) 

For `TokenIdType::Nep245` and `TokenIdType::Imt`, the fee rate is forced to `Pips::ZERO` whenever `amount <= 1`, and only applies the configured protocol `fee` when `amount > 1`. This threshold is evaluated **per intent**, not per economic trade. Because `Nep245`/`Imt` token IDs commonly wrap fungible balances (any `TokenId` value with an arbitrarily large `u128` amount, as seen throughout `contracts/defuse/src/contract/tokens/nep245/*`), a single logical transfer of `N` units can be re-expressed as `N` separate `TokenDiff` intents each moving exactly `1` unit. Each such intent independently satisfies `amount <= 1`, so `token_fee` returns `Pips::ZERO` for every one of them, and `fees_collected` stays empty: [3](#0-2) 

The counterparty's required `closure_delta`/`supply_delta` is computed using the same zero fee rate, so the batch still nets to zero token-wise and passes the `TransferMatcher`/`Deltas` invariant check — the trade settles correctly, it simply never pays the fee that the equivalent single-intent trade of the same total size would have paid: [4](#0-3) 

This breaks the intended binding **fees owed == fees collected**: for a Nep245/Imt-denominated trade of size `N > 1`, the fee owed by protocol design is `fee_ceil(N)`, but an attacker can make the fees actually collected `0` by decomposing the trade into `N` unit-sized `TokenDiff` intents, all of which can be delivered inside one `execute_intents(Vec<MultiPayload>)` call.

### Impact Explanation
This is a fee-bypass vulnerability matching the "Critical" bucket ("fees bypassed or over-collected"). Any user trading Nep245/Imt-denominated assets (which includes wrapped fungible balances of other NEP-141 tokens re-represented inside Defuse, or IMT-minted fungible supplies) can avoid protocol fees entirely, at the cost of extra gas/transaction size for issuing many small signed intents (or one `MultiPayload` bundling many single-unit `TokenDiff` intents). The protocol fee collector permanently loses the fee revenue it should have collected on such trades.

### Likelihood Explanation
The exploit requires only standard, unprivileged signer capability — crafting and signing multiple `TokenDiff` intents with `delta = ±1` for the same Nep245/Imt token and submitting them together (or across several `execute_intents` calls). No special role, relayer key, or deployment misconfiguration is needed; it only requires that fees are configured (`fee > 0`) and that the trade involves a `Nep245`/`Imt` token with a fungible-scale balance, which is the common case for wrapped/aggregated assets in this system.

### Recommendation
Compute the fee-exemption threshold based on the aggregate economic size of matched trades rather than per-intent `amount`, or simply remove the `amount <= 1` exemption for `Nep245`/`Imt` and instead special-case true non-fungible transfers (e.g., only skip the fee when the token is known/flagged as strictly non-fungible, or apply `fee_ceil` uniformly and accept that unit trades pay at most 1 unit of fee-equivalent rounding). Alternatively, enforce a per-signer/per-token minimum notional or rate-limit the number of same-token `TokenDiff` intents processed with reduced fee treatment within a batch.

### Proof of Concept
1. Configure protocol fee `> 0` (e.g. `Pips::ONE_PERCENT`), fee collector set as usual.
2. Attacker (as `signer_id`) holds `1000` units of a fungible balance addressed via a `Nep245`/`Imt` `TokenId` (e.g. `nep245:<contract>:<inner_ft>`).
3. Instead of signing one `TokenDiff{ diff: {token: -1000, other_token: +X} }` (which would incur `fee_ceil(1000)` fee per `token_fee`/`fee_ceil` in `contracts/defuse/core/src/intents/token_diff.rs:69-78`), the attacker (with a cooperating or self-controlled counterparty) signs 1000 separate `TokenDiff` intents, each `{ token: -1, other_token: +x }`.
4. For each of the 1000 intents, `token_fee` evaluates `amount == 1 <= 1` for the `Nep245`/`Imt` type and returns `Pips::ZERO` (`contracts/defuse/core/src/intents/token_diff.rs:206-216`), so `fees_collected` accumulates `0` across all 1000 intents.
5. `execute_intents` processes the whole `Vec<MultiPayload>` in one call (`contracts/defuse/src/contract/intents/mod.rs:26-42`); the `TransferMatcher`/`Deltas` invariant still balances because both sides used the same zero-fee closure math, so the batch settles successfully with `0` fees paid on a `1000`-unit trade that should have paid `fee_ceil(1000)`.

    /// Returns total supply delta from token delta
    #[inline]
    fn supply_delta(token_id: &TokenId, delta: i128, fee: Pips) -> Option<i128> {
        if delta < 0 {
            // fee is taken only on negative deltas (i.e. token_in)
            delta.checked_mul_div_ceil(
                Self::token_fee(token_id, delta.unsigned_abs(), fee)
                    .invert()
                    .as_pips()
                    .into(),
                Pips::MAX.as_pips().into(),
            )

            Some(delta)
        }
