### Title
First-liquidity-provider inflation attack on `pallet-asset-conversion` due to `create_pool` / `add_liquidity` being separate transactions and reserves being read from live token balances - (File: `substrate/frame/asset-conversion/src/lib.rs`)

### Summary
`pallet-asset-conversion` splits the classic AMM "initialize pool" and "seed reserves" steps into two independent, permissionless extrinsics: `create_pool` [1](#0-0)  and `add_liquidity` [2](#0-1) . This is exactly the same structural flaw described in the external report (pool initialized in one transaction, reserves supplied in another), and it opens the same "empty pool, manipulate before liquidity is properly seeded" window. Compounding this, the pallet does not track reserves as internal state — it derives `reserve1`/`reserve2` from the pool account's live token balance via `Self::get_balance` at the time of `add_liquidity`/quoting [3](#0-2) , meaning any direct token transfer ("donation") into the pool account between `create_pool` and the legitimate `add_liquidity` call changes the effective reserves used for LP-share math.

### Finding Description
1. `create_pool` (call_index 0) only registers the pool and mints the LP-token asset class; it moves zero funds and leaves the pool account with zero reserves [4](#0-3) .
2. `add_liquidity` (call_index 1) is a fully independent, permissionless extrinsic that anyone can call afterward. Its own doc comment acknowledges the resulting risk: *"NOTE: when encountering an incorrect exchange rate and non-withdrawable pool liquidity, batch an atomic call with `add_liquidity` and `swap_exact_tokens_for_tokens`... to rectify the exchange rate."* [5](#0-4) 
3. Inside `add_liquidity`, when `total_supply` (LP token issuance) is zero — i.e., the very first liquidity provision — the minted LP amount is `sqrt(amount1 * amount2) - MintMinLiquidity` [6](#0-5) . Because `reserve1`/`reserve2` are read straight from the pool account's on-chain asset balance rather than from internally accounted state, an attacker who front-runs the victim's `add_liquidity` call can:
   - call `add_liquidity` first with a minimal amount (satisfying `> MintMinLiquidity`), becoming the sole LP holder, then
   - directly transfer ("donate") a large amount of asset1/asset2 straight into the pool account (no call into the pallet needed, since `T::Assets` is a generic fungible/fungibles implementation reachable by any account), inflating the live balance-derived reserves without minting any additional LP tokens,
   - so the victim's subsequent `add_liquidity` call computes `side1`/`side2` against the inflated reserves and receives disproportionately few LP tokens for the value deposited, while the attacker's LP tokens now represent a much larger claim on the pool `= classic donation/inflation attack`.
4. The `MintMinLiquidity` constant (`100` in the reference runtime configuration [7](#0-6) ) only guards against a *degenerate zero-value* first mint; it does nothing to prevent the balance-donation reserve manipulation once the attacker already holds the (small) initial LP supply.

### Impact Explanation
This lets an unprivileged attacker who observes (or races) a new pool's first `add_liquidity` transaction extract value from the first honest liquidity provider by minting a disproportionate share of LP tokens, then withdrawing more value than deposited once the victim's larger deposit lands. This is a direct "theft/unbacked value transfer between users" impact within the value-conservation invariant scope (assets/pools must conserve value and settle exactly once to the rightful beneficiary/amount).

### Likelihood Explanation
Likelihood is low-to-moderate: it requires a permissionless attacker to observe or race a specific new-pool bootstrapping transaction and to be able to front-run/interleave two calls (their own `add_liquidity` and a raw token transfer) before the victim's `add_liquidity` is included. No privileged role, governance action, or malicious validator/collator is required — only an ordinary account able to submit competing extrinsics, consistent with the in-scope threat model.

### Recommendation
Follow the same remediation the external report prescribes: require pool creation and initial liquidity seeding to occur atomically. Concretely:
- Merge `create_pool` and the first `add_liquidity` into a single extrinsic (or require `create_pool` to optionally take initial `amount1`/`amount2` and perform the transfer + first mint in the same call, similar to `setup_pool_from_genesis` [8](#0-7) , but exposed as a public extrinsic instead of a genesis-only helper), and/or
- Track reserves as internal pallet storage that is only updated through pallet-mediated transfers, instead of reading live `T::Assets` balances, so unsolicited direct transfers into the pool account cannot influence the LP-share calculation.

### Proof of Concept
1. Attacker submits `create_pool(asset1, asset2)` (or waits for anyone to create it).
2. Attacker submits `add_liquidity(asset1, asset2, amount1=101, amount2=101, amount1_min=0, amount2_min=0, mint_to=attacker)`. Since `total_supply == 0`, LP minted = `sqrt(101*101) - 100 = 1`, and attacker becomes the sole holder of the LP token supply.
3. Before the victim's intended `add_liquidity(asset1, asset2, amount1_desired=1_000_000, amount2_desired=1_000_000, ...)` transaction lands, attacker directly transfers (via `pallet_assets`/`pallet_balances` `transfer`, not through the asset-conversion pallet) a large amount of asset1 and asset2 into the pool's sovereign account, inflating `reserve1`/`reserve2` returned by `Self::get_balance` [3](#0-2)  without increasing `total_supply` of the LP token.
4. Victim's `add_liquidity` now computes `side1`/`side2` against the inflated reserves, receiving far fewer LP tokens than their contribution's fair share.
5. Attacker calls `remove_liquidity` burning their single LP token unit and withdraws a proportionally outsized share of the now-large pool, extracting value contributed by the victim.

Note: I was not able to execute this scenario in a live test environment (no sandbox/terminal access in this mode); the above is derived directly from reading the pallet's extrinsic and calculation logic in this repository. If precise confirmation via a running test is needed, that should be done in a Devin session with repository execution access.

	impl<T: Config> Pallet<T> {
		/// Create a pool at genesis, bypassing the setup fee.
		///
		/// The `lp_provider` must already hold sufficient balances of both assets.
		/// If both `amount1` and `amount2` are non-zero, initial liquidity is added.
		/// Returns the LP token amount minted to `lp_provider` (zero if no liquidity).
		pub(crate) fn setup_pool_from_genesis(
			asset1: &T::AssetKind,
			asset2: &T::AssetKind,
			lp_provider: &T::AccountId,
			amount1: T::Balance,
			amount2: T::Balance,
		) -> Result<T::Balance, DispatchError> {
			ensure!(asset1 != asset2, Error::<T>::InvalidAssetPair);

			let pool_id = T::PoolLocator::pool_id(asset1, asset2)
				.map_err(|_| Error::<T>::InvalidAssetPair)?;
			ensure!(!Pools::<T>::contains_key(&pool_id), Error::<T>::PoolExists);

			let pool_account =
				T::PoolLocator::address(&pool_id).map_err(|_| Error::<T>::InvalidAssetPair)?;

			// Allocate LP token ID.
			let lp_token = NextPoolAssetId::<T>::get()
				.or(T::PoolAssetId::initial_value())
				.ok_or(Error::<T>::IncorrectPoolAssetId)?;
			let next_lp_token_id = lp_token.increment().ok_or(Error::<T>::IncorrectPoolAssetId)?;
			NextPoolAssetId::<T>::set(Some(next_lp_token_id));

			// Create LP token asset.
			T::PoolAssets::create(lp_token.clone(), pool_account.clone(), false, 1u32.into())?;

			// Touch asset accounts for the pool account.
			if T::Assets::should_touch(asset1.clone(), &pool_account) {
				T::Assets::touch(asset1.clone(), &pool_account, lp_provider)?;
			}
			if T::Assets::should_touch(asset2.clone(), &pool_account) {
				T::Assets::touch(asset2.clone(), &pool_account, lp_provider)?;
			}
			if T::PoolAssets::should_touch(lp_token.clone(), &pool_account) {
				T::PoolAssets::touch(lp_token.clone(), &pool_account, lp_provider)?;
			}

			// Register pool.
			Pools::<T>::insert(pool_id, PoolInfo { lp_token: lp_token.clone() });

			// Add initial liquidity if amounts are non-zero.
			if !amount1.is_zero() && !amount2.is_zero() {
				T::Assets::transfer(asset1.clone(), lp_provider, &pool_account, amount1, Preserve)?;
				T::Assets::transfer(asset2.clone(), lp_provider, &pool_account, amount2, Preserve)?;

				let lp_token_amount = Self::calc_lp_amount_for_zero_supply(&amount1, &amount2)?;
				T::PoolAssets::mint_into(
					lp_token.clone(),
					&pool_account,
					T::MintMinLiquidity::get(),
				)?;
				T::PoolAssets::mint_into(lp_token, lp_provider, lp_token_amount)?;

				Ok(lp_token_amount)
			} else {
				Ok(Zero::zero())
			}
		}

		pub(crate) fn do_create_pool(
			creator: &T::AccountId,
			asset1: T::AssetKind,
			asset2: T::AssetKind,
			initial_fee: Option<Permill>,
		) -> Result<T::PoolId, DispatchError> {
			ensure!(asset1 != asset2, Error::<T>::InvalidAssetPair);
			if let Some(fee) = initial_fee {
				ensure!(fee <= T::MaxSwapFee::get(), Error::<T>::FeeTooHigh);
			}

			// prepare pool_id
			let pool_id = T::PoolLocator::pool_id(&asset1, &asset2)
				.map_err(|_| Error::<T>::InvalidAssetPair)?;
			ensure!(!Pools::<T>::contains_key(&pool_id), Error::<T>::PoolExists);

			let pool_account =
				T::PoolLocator::address(&pool_id).map_err(|_| Error::<T>::InvalidAssetPair)?;

			// pay the setup fee
			let fee =
				Self::withdraw(T::PoolSetupFeeAsset::get(), creator, T::PoolSetupFee::get(), true)?;
			T::PoolSetupFeeTarget::on_unbalanced(fee);

			if T::Assets::should_touch(asset1.clone(), &pool_account) {
				T::Assets::touch(asset1.clone(), &pool_account, creator)?
			};

			if T::Assets::should_touch(asset2.clone(), &pool_account) {
				T::Assets::touch(asset2.clone(), &pool_account, creator)?
			};

			let lp_token = NextPoolAssetId::<T>::get()
				.or(T::PoolAssetId::initial_value())
				.ok_or(Error::<T>::IncorrectPoolAssetId)?;
			let next_lp_token_id = lp_token.increment().ok_or(Error::<T>::IncorrectPoolAssetId)?;
			NextPoolAssetId::<T>::set(Some(next_lp_token_id));

			T::PoolAssets::create(lp_token.clone(), pool_account.clone(), false, 1u32.into())?;
			if T::PoolAssets::should_touch(lp_token.clone(), &pool_account) {
				T::PoolAssets::touch(lp_token.clone(), &pool_account, creator)?
			};

			let pool_info = PoolInfo { lp_token: lp_token.clone() };
			Pools::<T>::insert(pool_id.clone(), pool_info);

			Self::deposit_event(Event::PoolCreated {
				creator: creator.clone(),
				pool_id: pool_id.clone(),
				pool_account,
				lp_token,
			});

			if let Some(fee) = initial_fee {
				PoolFees::<T>::insert(&pool_id, fee);
				Self::deposit_event(Event::PoolFeeSet { pool_id: pool_id.clone(), fee });
			}

			Ok(pool_id)
