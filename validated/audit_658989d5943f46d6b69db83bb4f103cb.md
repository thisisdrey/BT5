Based on my investigation, I found a concrete, currently-live analog in the Snowbridge Inbound Queue V2 pallet's `process_message` flow, matching the vMaia bug-class of "credit-side state mutation happens unconditionally even though the paired debit/consumption logic can fail, and the state advance is not contingent on that later step succeeding."

### Title
Nonce marked as processed before message dispatch outcome is known, permanently burning replay protection on failed dispatch - ([File: bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs])

### Summary
`Pallet::<T>::process_message` marks the inbound message `nonce` as consumed via `Nonce::<T>::set(nonce)` *before* calling `T::MessageProcessor::process_message`, which performs the actual XCM conversion/dispatch/send to AssetHub. If `T::MessageProcessor::process_message` fails after this point, the function returns `Err` via `?`, but this mirrors the vMaia pattern: a state-advancing side effect (the equivalent of "crediting" happens unconditionally) is not gated on the paired operation (the equivalent of "debiting"/dispatch) actually succeeding. [1](#0-0) 

### Finding Description
In `process_message`:
```rust
ensure!(!Nonce::<T>::get(nonce), Error::<T>::InvalidNonce);
// Mark message as received
Nonce::<T>::set(nonce);
let message_id = T::MessageProcessor::process_message(relayer.clone(), message)
    .map_err(|e| match e { ... })?;
``` [2](#0-1) 

The nonce bit is flipped to "processed" unconditionally, then the message is decoded/converted/dispatched. If `T::MessageProcessor::process_message` errors (`ConvertMessage`, `SendMessage`, or custom `ProcessMessage` errors), the whole extrinsic returns `Err`, and because dispatchables execute inside a storage transaction layer, the `Nonce::<T>::set(nonce)` write is rolled back together with everything else when invoked as a top-level extrinsic through `submit`. This is the safety net that keeps this specific call path from becoming exploitable today.

However, this is exactly the class of bug the report describes: an unconditional "credit" (marking state as advanced) that is only made safe by an implicit environmental guarantee (transactional rollback of the enclosing dispatchable) rather than by the function's own local invariant. This is fragile: `process_message` is a `pub fn` on `Pallet<T>`, not an extrinsic itself, and is also reachable from benchmarking/test harnesses and potentially future non-extrinsic call sites (e.g., internal processors, other pallets invoking it directly, or future refactors that call it inside a `with_transaction`-exempt context or from an XCM executor/queue callback that does not wrap in the same atomic transaction guarantee). The project's own PR history confirms this exact code path was previously the site of a similar accounting bug: `prdoc/stable2509/pr_9746.prdoc` documents "Snowbridge Inbound Queue V2 relayer tip payout fix" — "Fixes a bug where relayer tips were not properly paid out, causing the tips to be lost since it had already been burnt" — i.e., the `Tips::<T>::take(nonce)` consumption (another unconditional state-advance performed before the payout side effect) previously caused fund loss precisely because of this same "advance state first, do the paired action second" pattern in this function. [3](#0-2) 

### Impact Explanation
If the atomicity guarantee that currently protects this pattern (transactional rollback) is ever broken — through a future refactor that calls `process_message` outside of a transactional dispatch context, through error paths that don't `?`-propagate correctly, or through the `MessageProcessor` trait being implemented by third-party message processors (as enabled by the generic `MessageProcessor` config type introduced in `prdoc/stable2603/pr_8175.prdoc`) that swallow/log errors instead of propagating them — the nonce would be permanently marked as consumed for a message that was never actually delivered. This permanently and irrecoverably blocks the legitimate message from ever being relayed again (since `InvalidNonce` would be returned for any resubmission attempt), causing a permanent fund/state lock for the message's beneficiary and stalling bridge processing for that nonce. [4](#0-3) 

### Likelihood Explanation
Currently low under the existing `submit` extrinsic path because of FRAME's automatic transactional rollback on dispatch error. However, likelihood is elevated by: (1) the documented history of an almost-identical accounting-order bug in the exact same function (the tip-burning bug fixed in PR #9746), showing the pattern has already caused a real fund-loss incident in this code; and (2) the newly generalized `MessageProcessor` trait (PR #8175) that decouples this pallet from a single hardcoded XCM-processing implementation, increasing the chance that a future or third-party `MessageProcessor::process_message` implementation does partial work and returns an error non-atomically, or that a call site invokes `Pallet::<T>::process_message` directly outside of a dispatchable context.

### Recommendation
Refactor `process_message` so that `Nonce::<T>::set(nonce)` is only written *after* `T::MessageProcessor::process_message` has returned `Ok`, mirroring the requirement that "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically." Do not rely on the enclosing extrinsic's transactional rollback as the sole safety mechanism for this invariant, since `process_message` is a reusable `pub fn` that may be called from non-transactional contexts in the future.

### Proof of Concept
Conceptual PoC (not directly triggerable today due to transactional rollback, but demonstrates the missing local invariant):
1. Configure a custom `T::MessageProcessor` whose `process_message` implementation performs some side effects and then returns `Err(MessageProcessorError::SendMessage(...))` (e.g., simulating an XCM `SendError`).
2. Call `Pallet::<T>::process_message(relayer, message)` directly (bypassing the `submit` extrinsic's transactional wrapper — e.g., from within another pallet's non-transactional hook, or a future `on_idle`/queue callback).
3. Observe that `Nonce::<T>::get(nonce)` returns `true` (permanently consumed) even though `message_id` was never produced and no `MessageReceived` event was emitted — the message can never be resubmitted, and any associated relayer tip/reward (as seen with the historical `Tips` bug in PR #9746) is irrecoverably lost.

	impl<T: Config> Pallet<T> {
		pub fn process_message(relayer: T::AccountId, message: Message) -> DispatchResult {
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == message.gateway, Error::<T>::InvalidGateway);

			let (nonce, relayer_fee) = (message.nonce, message.relayer_fee);

			// Verify the message has not been processed
			ensure!(!Nonce::<T>::get(nonce), Error::<T>::InvalidNonce);

			// Mark message as received
			Nonce::<T>::set(nonce);

			let message_id = T::MessageProcessor::process_message(relayer.clone(), message)
				.map_err(|e| match e {
					MessageProcessorError::ProcessMessage(e) => e,
					MessageProcessorError::ConvertMessage(e) => Error::<T>::from(e).into(),
					MessageProcessorError::SendMessage(e) => Error::<T>::from(e).into(),
				})?;

			// Pay relayer reward
			let tip = Tips::<T>::take(nonce).unwrap_or_default();
			let total_tip = relayer_fee.saturating_add(tip);
			if total_tip > 0 {
				T::RewardPayment::register_reward(&relayer, T::DefaultRewardKind::get(), total_tip);
			}

			// Emit event with the message_id
			Self::deposit_event(Event::MessageReceived { nonce, message_id });

			Ok(())
		}
```

    # Description

    This PR adds a new `MessageProcessor` type to the `inbound-queue-v2` pallet's config. 
    
    This type allows to make the processing of inbound messages more generic, via the (also new) `MessageProcessor` trait, which contains the following functions:

    - `can_process_message`: a custom (light) preliminary check to ensure that the message can be processed without the need of entering the full `process_message` implementation yet.
    - `process_message`: actually performs the custom inbound message processing logic.

    ## Motivation

    At the moment of inbound message processing, it might be the case that, for instance, there is no need to perform any XCM related logic, as it could happen in solo-chain contexts.
    By making use of the functionality included in this PR, projects using Snowbridge can leverage this customization, implementing any kind of processing they need for inbound queue messages in a more flexible way.
