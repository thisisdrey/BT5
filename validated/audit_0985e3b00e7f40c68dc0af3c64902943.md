### Title
Unrestricted initial/injected reserve ratio in `BufferBinaryPool`-style Bancor exchange pool enables precision-loss theft via `ExchangeCreateActuator`/`ExchangeTransactionActuator` - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeCreateActuator.java`)

### Summary
`java-tron`'s TRC10 Bancor-style token exchange (`Exchange*Actuator` family) mirrors the root cause of the reported `BufferBinaryPool` bug: an exchange rate/price is derived purely from mutable, attacker-controllable reserve balances, and there is no minimum-liquidity or minimum-ratio floor enforced at pool creation or trade time. Any account can create a pool with a maximally skewed reserve ratio and then any other unprivileged account (a trader) interacts with that pool through a floating-point bonding-curve calculation that is vulnerable to precision loss at extreme ratios, directly analogous to the "manipulate the exchange rate, then profit from later users' precision loss" pattern in the original report.

### Finding Description
`ExchangeCreateActuator.doValidate()` only requires that both reserves be strictly positive and below a configurable `balanceLimit`; there is no minimum liquidity or minimum ratio constraint between `firstTokenBalance` and `secondTokenBalance`: [1](#0-0) 

This means any signer can create an exchange pool with an arbitrarily skewed ratio, e.g. `firstTokenBalance = 1` and `secondTokenBalance = balanceLimit` (bounded only by `DynamicPropertiesStore.getExchangeBalanceLimit()`), entirely within a single `ExchangeCreateContract` transaction.

Once created, any other account (not just the creator) can trade against this pool via `ExchangeTransactionActuator`, which computes the counter-amount using `ExchangeCapsule.transaction()`: [2](#0-1) 

The actual pricing math is implemented with double-precision floating point and `Math.pow` against a hard-coded constant-reserve-ratio exponent (`0.0005`/`2000.0`) and a fixed virtual relay-token supply of `1_000_000_000_000_000_000L`: [3](#0-2) 

When one reserve side is very small (as low as `1`, which is fully legal per the validate check above), `quant / newBalance` and subsequent `pow()` computations operate at the edge of `double` precision, and truncation to `long` (`(long) issuedSupply`, `(long) exchangeBalance`) can produce a counter-amount that is disproportionately favorable to the trader relative to the "fair" constant-product/CRR value. This is the same root cause pattern as the reported bug: a price/exchange-rate function is computed from mutable balances with no guardrails on the minimum size of one side of the ratio, and integer truncation on top of that skewed ratio benefits whichever party is positioned to exploit it, at the expense of the counterparty (all subsequent traders against the same pool, since reserves are shared, not per-user shares).

Unlike a standard AMM, `ExchangeInjectActuator`/`ExchangeWithdrawActuator` restrict liquidity add/remove to the pool creator only (confirmed via the `is not creator` check in both actuators' `doValidate()`), so the "later depositor" role in this analog is played by ordinary traders using `ExchangeTransactionActuator` against the attacker-created skewed pool, rather than LPs.

### Impact Explanation
An attacker who creates a pool with an extreme reserve skew (e.g., `1 : balanceLimit`) can subsequently trade against their own pool to extract value via floating-point/integer-truncation errors in the bonding-curve formula, or induce degraded/incorrect pricing for any unsuspecting trader who trades against that pool afterward. This is a direct fund-extraction/theft vector reachable purely through signed `ExchangeCreateContract` and `ExchangeTransactionContract` transactions — no special privilege (SR/witness/committee) is required.

### Likelihood Explanation
Medium-High: creating a skewed-ratio exchange only costs the `ExchangeCreateFee` and requires depositing at least `1` unit of one token, which is trivially affordable. Triggering the precision-loss condition requires choosing extreme but fully-valid reserve ratios/quantities that stay within `getExchangeBalanceLimit()`, which is a config value rather than a hard protocol invariant, and the double-based math in `ExchangeProcessor` (the default, non-hardened path selected when `allowHarden()` is false) has no explicit precision safety margin analogous to the `SafeExchangeProcessor`'s BigDecimal-based hardened path.

### Recommendation
- Enforce a minimum reserve size (and/or minimum ratio bound) for both `firstTokenBalance` and `secondTokenBalance` in `ExchangeCreateActuator.doValidate()`, not just `> 0`.
- Require use of the hardened `SafeExchangeProcessor` (BigDecimal-based) path unconditionally rather than gating it behind `allowHarden()`, or otherwise bound the acceptable input domain (extremely small reserves) before invoking the double-based `ExchangeProcessor`.
- Add an invariant check post-trade (as already partially done via `newFirstTokenBalance < 0` checks in hardened mode) that rejects trades producing a counter-amount inconsistent with a sanity-bounded CRR calculation, for both hardened and non-hardened paths.

### Proof of Concept
1. Attacker submits `ExchangeCreateContract` with `firstTokenBalance = 1` (e.g., 1 sun of TRX) and `secondTokenBalance = <getExchangeBalanceLimit()>` for a TRC10 asset they hold — this passes validation in `ExchangeCreateActuator.doValidate()` since both values are `> 0` and `<= balanceLimit`.
2. The resulting `ExchangeCapsule` stores this extreme 1:`balanceLimit` ratio.
3. Attacker (or a victim, if attacker seeds counter-liquidity via later trades) submits `ExchangeTransactionContract` trading against the skewed pool; `ExchangeCapsule.transaction()` invokes `ExchangeProcessor.exchange()`, whose double-precision `Math.pow` computations on the near-degenerate ratio produce a `long`-truncated `anotherTokenQuant` that deviates from the theoretically correct CRR value.
4. Repeated small trades against the same skewed pool allow the attacker to accumulate value through truncation/precision-loss error, analogous to the "donate to manipulate share price, then profit from later depositors' precision loss" pattern in the original report.

Note: I was unable to fully verify the exact numeric magnitude of `getExchangeBalanceLimit()`'s default value or run the floating-point calculation end-to-end to quantify the precise dollar-value extractable per trade, since I do not have execution access — this would need to be confirmed with a live/test-node calculation to establish concrete extractable amounts.
