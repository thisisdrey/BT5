### Title
Missing chain-binding in `ValidateMultiSign` precompile message hash enables cross-chain/fork signature replay - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The TVM `ValidateMultiSign` precompile (address `0x...0a`, exposed to any Solidity contract as `validatemultisign(address,uint256,bytes32,bytes[])`) builds the digest that off-chain multisig signers must sign purely from the target account address, the permission ID, and an application-supplied 32-byte value. Nothing in this digest binds it to the specific chain (mainnet/testnet/sidechain) or to the calling contract. Any signature collected to authorize a permission-gated action for an account on one java-tron based network can be replayed verbatim against the same account/permission on any other java-tron based network (or any fork), because TRON addresses and permission configurations are deterministic and chain-agnostic.

### Finding Description
`ValidateMultiSign.execute()` computes the digest signers must have signed as: [1](#0-0) 

```
byte[] address = words[0].toTronAddress();
int permissionId = words[1].intValueSafe();
byte[] data = words[2].getData();

byte[] combine = ByteUtil.merge(address, ByteArray.fromInt(permissionId), data);
byte[] hash = Sha256Hash.hash(..., combine);
```

This is exactly the pattern flagged in the external report: `msgHash = f(target, permission, applicationPayload)` with no `block.chainid` and no `address(this)` (verifying-contract identity) folded in. The precompile then recovers each supplied signature's signer against this hash and checks their combined weight against the account's `Permission.threshold`: [2](#0-1) 

The digest is fully determined by `(address, permissionId, data)` and is identical on every java-tron deployment (Mainnet, Shasta, Nile testnets, or any privately forked/sidechain network running the same codebase), because:
- TRON addresses are derived the same way (ECDSA public key → address) regardless of which chain they are used on, so the same private key produces the same `address` everywhere.
- `Permission` configuration (keys/threshold for a given `permissionId`) is set by `AccountCapsule.updatePermissions` and is not chain-bound; multisig committees frequently mirror identical permission setups across mainnet and test/side networks for operational convenience.
- The caller-supplied `data` (a single `bytes32`) is applicationdefined; the precompile itself never mixes in `block.chainid` or the calling contract's own address, unlike a proper EIP-712-style domain separator.

This mirrors the reported Opera-Bridge root cause: any consumer contract (e.g., a bridge/gateway/exchange withdrawal-approval contract) that uses this TVM primitive to gate fund releases with off-chain-collected multisig signatures inherits the replay weakness unless it manually folds chain/contract identity into the 32-byte `data` argument itself — something the protocol primitive does not force or document as mandatory.

### Impact Explanation
Any DApp built on top of `ValidateMultiSign` to gate a state-changing/fund-moving action behind an m-of-n signer threshold (a common bridging/vault pattern reachable by any TVM contract deployer and callable by any transaction broadcaster) is exposed to cross-network signature replay. If the same signer set/permission is present for an account on two java-tron-based networks (mainnet + testnet, mainnet + a sidechain, or pre/post-fork chains), a signature set collected/authorized for one network can be resubmitted on the other to unlock the same threshold-gated action there — leading to unauthorized account operations or theft of funds on the second network.

### Likelihood Explanation
Reaching this code requires only deploying/calling a contract that invokes the `ValidateMultiSign` precompile — no special privilege beyond being a normal contract deployer/caller. The precondition (identical account address + permission across two live java-tron networks) is realistic in practice for exchanges, custodians, and multisig operators who commonly reuse the same key set and configure identical permissions across mainnet and companion test/side networks. No code exists elsewhere in the precompile or in `TransactionCapsule` permission checks to prevent this, since the hash format itself is the root cause.

### Recommendation
Add explicit chain- and contract-binding to the digest computed inside `ValidateMultiSign` (and consider the same for `BatchValidateSign`, whose caller-supplied hash is also not enforced to be chain-bound): fold `block.chainid` (or an equivalent TRON chain identifier already present in `DynamicPropertiesStore`) and, ideally, the calling contract's address into the `combine` byte array before hashing, e.g. `combine = address || permissionId || chainId || callingContract || data`, or document/require that `data` MUST already encode a domain separator and update all TIP references accordingly.

### Proof of Concept
1. Deploy identical accounts with the same active-permission signer set/threshold on two java-tron networks that share the same codebase (e.g. Mainnet and Nile testnet, or Mainnet and a sidechain instance).
2. Off-chain, collect signatures for `combine = address || permissionId || data` (as computed in `ValidateMultiSign.execute()`), where `data` encodes an application payload (e.g., "release deposit #N").
3. Submit these signatures via a call to `validatemultisign(address, permissionId, data, signatures)` on network A — the withdrawal/gate succeeds.
4. Replay the identical `(address, permissionId, data, signatures)` tuple via a call to `validatemultisign` on network B — because the hash construction at [3](#0-2)  is identical and chain-agnostic, the same signatures pass verification and unlock the gated action a second time on a chain where it was never separately authorized.
