### Title
Precompiled contract DoS via unbounded attacker-controlled array-length fields in `PrecompiledContracts.extractBytesArray`/`extractSigArray`/`extractBytes32Array` - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The reported Stirling-PDF CVE is a DoS caused by request parameters (`fontSize`, `widthSpacer`) that are used directly to size/allocate resources without an upper bound, letting an authenticated client exhaust memory/CPU. The closest reachable analog in java-tron is in the TVM precompiled-contract helpers that decode ABI-encoded arrays from smart-contract call data: the "length" word is read straight from attacker-supplied calldata and used to allocate a Java array with no validation against the actual remaining calldata size or any maximum bound.

### Finding Description
`extractBytesArray`, `extractBytes32Array`, and `extractSigArray` in `PrecompiledContracts.java` all follow the same pattern: they read a 32-byte word from the decoded `DataWord[] words` array supplied by the caller and use `intValueSafe()` on it as an array length, then immediately allocate a two-dimensional byte array of that size: [1](#0-0) [2](#0-1) [3](#0-2) 

None of these three helpers validate `len` against `data.length`, against `words.length`, or against any sane maximum before calling `new byte[len][]`. `intValueSafe()` can return any value up to `Integer.MAX_VALUE`, so a crafted call to a precompiled contract that uses these helpers (e.g. `ValidateMultiSign`/`BatchValidateSign`-style precompiles that decode arrays of signatures/hashes) can request allocation of an enormous array, triggering an `OutOfMemoryError` or extreme CPU time in the subsequent per-element loop, before/independently of any meaningful energy accounting for the actual work being requested.

This mirrors the Stirling-PDF bug class exactly: a numeric parameter taken directly from an external, low-privilege request is used to size an allocation/loop with no upper-bound validation, causing resource exhaustion.

### Impact Explanation
Any account able to invoke a smart contract that calls into a precompiled contract using these array-extraction helpers (this is reachable via a standard `TriggerSmartContract` transaction, so any signed transaction sender or `TriggerConstantContract`/`triggersmartcontract` API caller) can attempt to force allocation of a huge array (`new byte[len][]`), causing an `OutOfMemoryError` inside the TVM execution thread. Depending on JVM heap state, this can crash or destabilize the full node process handling the transaction — a Denial-of-Service against the node, matching the "node crash or halt" bar required by the validation rules.

### Likelihood Explanation
The trigger requires only a single contract call with crafted calldata that reaches one of these decode helpers with a very large length word — no special privileges, keys, or SR/witness status are needed, matching the "unprivileged transaction broadcaster / contract deployer" reachability requirement. However, I was not able to fully confirm within the available tool budget which specific precompiled contract(s) invoke `extractBytesArray`/`extractSigArray` in their `execute()`/`getEnergyForData()` paths, nor whether an upstream energy-cost calculation in those specific contracts effectively bounds `len` before this code executes (some precompiles in this file, e.g. `ModExp`, do cap similar length parameters via an `UPPER_BOUND` check [4](#0-3)  — it is unverified whether the same protection exists for the callers of `extractBytesArray`/`extractSigArray`). This uncertainty should be resolved by tracing the actual `getEnergyForData`/`execute` implementations of the precompiled contracts that call these three helpers.

### Recommendation
Add explicit bounds checks in `extractBytesArray`, `extractBytes32Array`, and `extractSigArray` before allocating: validate `len` against a fixed maximum item count and against the actual remaining size of `data`/`words`, rejecting (returning failure) rather than allocating when the value is out of range — analogous to the `UPPER_BOUND` check already used in `ModExp`.

### Proof of Concept
Not fully constructible without confirming the exact precompiled-contract address/selector that reaches these helpers (unresolved due to tool-call budget). Conceptually: craft calldata to the vulnerable precompile where the ABI-encoded "array length" header word is set to a very large value (e.g. `0x7FFFFFFF`) while the rest of the calldata is minimal; invoking this via `TriggerSmartContract` would cause `extractBytesArray`/`extractSigArray` to attempt `new byte[0x7FFFFFFF][]`, exhausting heap memory in the node process handling the transaction.
