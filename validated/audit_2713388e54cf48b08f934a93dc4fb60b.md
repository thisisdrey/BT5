Audit Report

## Title
Snowbridge outbound message delivery fee rounds down to zero, letting users pay nothing for Ethereum-bound messages while relayers/reward pot bear the cost - (File: `bridges/snowbridge/pallets/outbound-queue/src/lib.rs`)

## Summary
`Pallet::calculate_fee` computes the native-currency fee owed for delivering a message to Ethereum, combining a `FixedU128` multiply/divide against `exchange_rate` and `multiplier` with a final truncating integer division in `convert_from_ether_decimals`. For non-zero but small `fee_per_gas`/`reward` pricing parameters, the wei-scaled inner value can fall below the decimal-conversion denominator (`10^8` for 10-decimal chains, `10^6` for 12-decimal chains), causing `checked_div` to truncate the remote fee to exactly `0` even though the inputs were non-zero.

## Finding Description
`calculate_fee` at `bridges/snowbridge/pallets/outbound-queue/src/lib.rs:368-393` computes `calculate_remote_fee` (wei), casts to `u128`, applies `FixedU128::from_inner(fee).saturating_mul(params.multiplier).checked_div(&params.exchange_rate).into_inner()`, and then calls `convert_from_ether_decimals`, which performs `value.checked_div(denom)` where `denom = 10^(18 - T::Decimals)` [1](#0-0) . This plain integer division silently truncates any remainder, and there is no downstream check that the resulting `remote` fee remains positive when the pricing parameters are non-zero.

`validate()` in `send_message_impl.rs` calls `Self::calculate_fee(gas_used_at_most, T::PricingParameters::get())` and returns the resulting `Fee` unconditionally, with no minimum-fee assertion before the `Ticket` is created and accepted for enqueue [2](#0-1) . The pallet's own regression test, `test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero`, reproduces this exact scenario with `exchange_rate = 1`, `fee_per_gas = 1`, `reward = 1`, `multiplier = 1`, `gas_used = 250000`, yielding `fee.remote == 0` while `fee.local == 698000000`, and the test comment explicitly flags this as invalid/undesirable behavior [3](#0-2) .

The only existing guard is `integrity_test`, which merely asserts `T::Decimals` is 10 or 12 [4](#0-3) ; this does not protect against the truncation-to-zero condition for small pricing inputs.

## Impact Explanation
The `remote` fee component is designed to reimburse relayers for gas spent executing commands on the Ethereum gateway plus a reward, as documented in the module-level fee computation formula [5](#0-4) . When pricing parameters combine such that the computed wei value is smaller than the decimal-conversion denominator, any ordinary unprivileged sender calling the public message-send path is charged `remote == 0`, meaning they get Ethereum-side execution for free while the relayer/reward pot absorbs the real ETH gas cost. This is public underpriced work that degrades the economic incentive for relaying and can stall/backlog bridge processing, matching the allowed impact category for public underpriced work.

## Likelihood Explanation
The scenario requires no privileged access — the truncation happens purely inside the deterministic `calculate_fee` function, triggered by any account submitting a message through the standard `SendMessage::validate` path once pricing parameters combine to produce a sub-denominator wei value. This is not a matter of governance abuse; governance setting parameters is a normal, expected operation, and the arithmetic flaw is independent of whether the parameter update is malicious. The pallet's own unit test with plausible small values (`exchange_rate=1`, `fee_per_gas=1`, `reward=1`) already reproduces `fee.remote == 0` deterministically and repeatably.

## Recommendation
- In `convert_from_ether_decimals` / `calculate_fee`, detect when a non-zero pre-division value truncates to zero and either round up or apply a floor of `1` to the resulting remote fee.
- Add an explicit guard in `validate()` (e.g., `ensure!(fee.remote > 0 || params.fee_per_gas.is_zero() && params.rewards.remote.is_zero(), Error::FeeTooLow)`) so a message cannot be queued with a zero remote fee while relayer-facing gas/reward parameters are non-zero.
- Perform the multiply/divide chain in higher precision (e.g., `U256`) to avoid compounding rounding losses across the `FixedU128` division and the final decimal-conversion division.

## Proof of Concept
The existing unit test `test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero` in `bridges/snowbridge/pallets/outbound-queue/src/test.rs:303-319` demonstrates the flaw: with `exchange_rate = FixedU128::from_rational(1,1)`, `fee_per_gas = 1`, `rewards.remote = 1`, `multiplier = 1`, and `gas_used = 250000`, `calculate_fee` returns `fee.remote == 0` despite all pricing inputs being non-zero, confirming that a sender pays nothing toward the relayer's Ethereum gas/reward under these (governance-set) parameters.
