### Title
Unprivileged QUIC client can hold uni-stream & connection slots open indefinitely via slow-drip chunks, bypassing per-chunk timeout with no absolute stream lifetime cap - (File: streamer/src/nonblocking/quic.rs)

### Summary
`handle_connection`'s per-connection task in `streamer/src/nonblocking/quic.rs` accepts and processes uni-streams sequentially, and the only stream-liveness guard is a *per-read* idle timeout (`wait_for_chunk_timeout`, default 2s) that resets every time any bytes arrive. There is no absolute cap on total stream duration, so a client that writes 1 byte every ~1.9s never triggers the timeout and can hold a stream — and the connection slot that owns it — open forever while contributing nothing to `packet_sender`.

### Finding Description
In `handle_connection` (`streamer/src/nonblocking/quic.rs:583-724`), each accepted connection is handled by a single task that loops:
1. `connection.accept_uni()` to get a new stream [1](#0-0) 
2. Enter an inner loop that repeatedly calls `tokio::time::timeout(wait_for_chunk_timeout, stream.read_chunks(&mut chunks))` and only breaks on a read error, a full `wait_for_chunk_timeout` timeout with *zero* bytes received, or `StreamState::Finished` from `handle_chunks`. [2](#0-1) 

Because the `tokio::time::timeout` deadline is freshly created on every loop iteration, any successful (even 1-byte) chunk read resets the clock — there is no tracking of total elapsed time since the stream was opened. This is confirmed by the existing test `test_quic_stream_timeout`, which only verifies that a stream with *zero* follow-up writes times out after `DEFAULT_WAIT_FOR_CHUNK_TIMEOUT`, but never asserts an absolute maximum stream lifetime. [3](#0-2) 

Since `handle_connection`'s outer `'conn` loop only calls `accept_uni()` again after the *current* stream reaches `Finished`/`Err`/timeout, one perpetually-fed stream blocks that same connection's task from ever accepting/processing any further streams. Meanwhile `qos.on_new_stream`/`on_stream_accepted` have already incremented `stats.active_streams` and the connection's `stream_count` (in `ConnectionStreamCounter`) for the slow stream, and the connection itself continues to occupy a slot in the unstaked/staked `ConnectionTable` (bounded by `max_connections_per_unstaked_peer` / `max_unstaked_connections` in `streamer/src/nonblocking/swqos.rs`) for as long as the attacker keeps drip-feeding it. [4](#0-3) [5](#0-4) 

Existing QoS guards (`ConnectionStreamCounter` per-100ms throttling, `StakedStreamLoadEMA`, `max_connections_per_unstaked_peer`/`max_unstaked_connections`) only bound the *rate of new stream admission and connection count*, not the *duration* a stream/connection may be held open once accepted. None of them enforce an absolute stream deadline, so they do not stop this specific slow-drip pattern.

### Impact Explanation
The attack lets an unstaked client tie up, per connection, one `active_streams`/`stream_count` slot and the connection's own entry in the peer's connection table indefinitely, at negligible bandwidth cost (1 byte every ~1.9s). This blocks the *same connection* from ever completing further streams (self-inflicted for that connection), and — bounded by `max_connections_per_unstaked_peer` — the attacker can occupy that many connection slots from a single IP for the lifetime of the attack. This degrades TPU stream/connection availability for other clients sharing the same source IP and inflates `active_streams`/connection-table occupancy metrics without any corresponding useful throughput, matching the "QoS evasion / resource starvation" bounty category. The blast radius is bounded by existing per-peer connection caps, so it is not an unbounded global DoS, but it is a genuine gap in the stream-lifetime invariant.

### Likelihood Explanation
Highly feasible and fully reproducible with a standard QUIC client: open a uni-stream, `write_all(&[0u8])`, `sleep(Duration::from_millis(1900))`, repeat. No stake, no special config, and no more than a single unprivileged connection per slot consumed are required. `DEFAULT_WAIT_FOR_CHUNK_TIMEOUT = 2s` and the reset-on-any-read behavior are both confirmed directly in the code and existing tests.

### Recommendation
Track an absolute per-stream deadline (e.g., record `accum.start_time` or a separate `Instant` at stream-accept time) and, in the `handle_chunks`/read loop of `handle_connection`, close the stream/connection once `start_time.elapsed()` exceeds a configured maximum stream lifetime, independent of the per-chunk `wait_for_chunk_timeout`. Optionally also cap total bytes read as a proxy for expected completion time given `max_stream_data_bytes`.

### Proof of Concept
Extend the existing `test_quic_stream_timeout` in `streamer/src/nonblocking/quic.rs`:
```rust
#[tokio::test(flavor = "multi_thread")]
async fn test_quic_slow_drip_stream_never_times_out() {
    let SpawnTestServerResult { stats, server_address, cancel, join_handle, receiver } =
        setup_quic_server(None, QuicStreamerConfig::default_for_tests(), SwQosConfig::default());

    let conn = make_client_endpoint(&server_address, None).await;
    let mut s = conn.open_uni().await.unwrap();

    // Drip 1 byte just under the per-chunk timeout, repeatedly, well past
    // several multiples of DEFAULT_WAIT_FOR_CHUNK_TIMEOUT.
    for _ in 0..5 {
        s.write_all(&[0u8]).await.unwrap();
        sleep(DEFAULT_WAIT_FOR_CHUNK_TIMEOUT - Duration::from_millis(100)).await;
    }

    // Expected (if fixed): stream should have been forcibly closed by an
    // absolute lifetime cap, active_streams should be 0 and
    // total_stream_read_timeouts (or a new "stream_lifetime_exceeded" stat)
    // should be non-zero.
    assert_eq!(stats.active_streams.load(Ordering::Relaxed), 0); // currently FAILS: stays 1
    cancel.cancel();
    drop(receiver);
    join_handle.await.unwrap();
}
```
This currently fails (the stream/connection remains open with `active_streams == 1` for as long as drip-feeding continues), demonstrating the missing absolute stream-lifetime bound.
