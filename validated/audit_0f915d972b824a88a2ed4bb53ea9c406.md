### Title
Stale contract storage persists across SELFDESTRUCT → CREATE2 redeploy at the same address within one transaction, allowing storage-collision exploits - (File: actuator/src/main/java/org/tron/core/vm/program/Program.java)

### Summary
This is a structural analog of the ERC20SpendingLimitPolicy bug: a component that is destroyed and re-initialized under the same identifier does not have its underlying key-value storage cleared, so an attacker who controls the re-initialization can make new logic operate over stale, attacker-influenced state. In the ERC20SpendingLimitPolicy case the identifier was `configId`; in java-tron's TVM the identifier is the deterministic CREATE2 contract address plus the storage `addrHash`, and the "storage" is the `StorageRowStore` (contract storage slots) keyed via `Storage.compose()`.

### Finding Description
Contract storage rows are addressed by an `addrHash` derived from the contract address, and only additionally salted by the originating transaction hash when the contract was created via CREATE2: [1](#0-0) 

When a contract self-destructs, only an in-memory `selfDestructCache` marker is set; no storage rows are deleted: [2](#0-1) 

When a new contract is created at an address that already has an `AccountCapsule` (e.g., because a prior contract at that same CREATE2 address self-destructed earlier in the same transaction), `createContractImpl` only clears the account's delegated-resource fields — it never clears the `Storage`/`StorageRowStore` entries for that address: [3](#0-2) 

`Storage.generateAddrHash()` is keyed by `address + trxHash` (the root transaction id), and the root transaction id is identical for every internal CREATE2 within the same top-level transaction: [4](#0-3) 

Consequently, if an attacker-controlled outer contract, within a single transaction:
1. Deploys a factory-owned inner contract via CREATE2 with salt `S` (address `A`, storage rows keyed by `hash(A, txId)`), writes some storage,
2. `SELFDESTRUCT`s it,
3. Deploys again via CREATE2 with the same salt `S` (same resulting address `A`, same `txId`),

then the new contract at `A` inherits exactly the same `addrHash`, and thus the same underlying storage rows in `StorageRowStore`/`storageCache`, as the previous, destroyed contract — because `Storage.commit()` only writes dirty rows and never wipes the prior contract's slots, and `createContractImpl` performs no storage-clearing step analogous to the `initializeWithMultiplexer` overwrite that the reported SmartSession/ERC20SpendingLimitPolicy bug relies on. This is the same root cause pattern as the report: "storage is supposed to be overwritten/cleared on re-init, but the implementation does not actually clear it."

The comparison test `CreateContractSuicideTest`/`Create2Test`/`RepositoryImplSelfDestructTest` in the codebase demonstrate the selfdestruct/CREATE2 lifecycle is exercised but do not assert that storage rows are wiped, suggesting this gap in behavior is untested for the same-transaction redeploy scenario.

### Impact Explanation
Solidity contracts routinely rely on the assumption that freshly deployed bytecode runs over zero-initialized storage (constructors initialize owner/admin, balances, reentrancy flags, allowances, etc., under this assumption). If storage from the previous incarnation at the same address silently persists, a malicious factory contract can:
- Pre-seed storage slots (e.g., an `owner`/`admin` address slot, an `initialized` boolean, or an accounting balance) via the first deployment, self-destruct, then redeploy new bytecode via CREATE2 with the same salt whose constructor does not explicitly zero those slots (because Solidity constructors do not clear storage that isn't explicitly written), inheriting attacker-chosen values.
- This can be leveraged to bypass access control (attacker becomes admin of the redeployed contract), fake initialization/whitelisting state, or forge balances that a subsequently deployed different contract logic misinterprets as legitimate — leading to unauthorized privileged operations or theft of funds routed through the redeployed contract.

This is reachable by any account able to submit a `TriggerSmartContract`/`CreateSmartContract` transaction that executes attacker-supplied bytecode performing CREATE2 + SELFDESTRUCT + CREATE2 in one call — i.e., a fully unprivileged, permissionless path.

### Likelihood Explanation
Requires: (a) TVM SELFDESTRUCT and CREATE2 opcodes enabled (`allowTvmConstantinople`/related VMConfig flags, already active on current chain forks), (b) the attacker deploys/controls an outer contract that performs the destroy-and-redeploy sequence within a single transaction, and (c) the victim contract logic (deployed by the attacker's own factory or reused by a third-party protocol expecting fresh storage) does not explicitly re-zero all relevant slots in its constructor. This is a standard, well-known EVM-family "CREATE2 metamorphic contract" pattern; TVM inherits it because storage-row addressing was designed only to disambiguate different CREATE2 transactions, not different generations of the same address within one transaction. Exploitability depends on specific victim contract logic assuming zero-initialized storage, so likelihood is contract-dependent but the underlying storage-persistence primitive itself is concretely demonstrable and requires no privileged access.

### Recommendation
When creating a contract at an address that previously held a self-destructed contract within the same repository/transaction context (`isSelfDestructed(newAddress)` true, or account existed and is being reused per lines 836-852 of `Program.java`), explicitly clear all storage rows associated with that address (or force a fresh, unique `addrHash`, e.g., incorporate a per-creation nonce/counter in addition to the root transaction id) before the new contract begins executing its constructor. This mirrors the recommended fix pattern for the ERC20SpendingLimitPolicy: either fully clear prior storage on re-initialization, or make the identifier (storage address hash) impossible to collide with any prior generation, e.g., include the internal call's creation nonce/depth in `generateAddrHash` rather than only the top-level `trxHash`.

### Proof of Concept
1. Attacker deploys `Factory` contract with a function `deployDestroyRedeploy(bytes salt)` that:
   - `create2` deploys `Victim` bytecode `V1` at deterministic address `A` (`salt`), whose constructor writes `slot0 = msg.sender` (attacker-controlled) intended to later represent a privileged role, then immediately `SELFDESTRUCT`s `A`.
   - In the same call, `create2` deploys different bytecode `V2` at the same address `A` (same `salt`), whose constructor does not explicitly zero `slot0`, and whose public functions treat `slot0` as an `owner`/`admin` address gating privileged actions (e.g., `withdrawAll()`).
2. Because both CREATE2 operations occur in the same top-level transaction, `Storage.generateAddrHash(trxHash)` produces the identical `addrHash` for `A` in both generations (per `actuator/src/main/java/org/tron/core/vm/program/Storage.java:61-71`), and `createContractImpl` (`actuator/src/main/java/org/tron/core/vm/program/Program.java:836-882`) performs no storage wipe when redeploying over the previously self-destructed account.
3. `V2`'s `slot0` therefore already equals the attacker's address left over from `V1`, even though `V2`'s constructor never wrote it — granting the attacker `owner`/`admin` privileges on `V2` without `V2`'s own logic ever authorizing it.
4. Attacker calls `V2.withdrawAll()` (or equivalent privileged function) and drains funds/permissions that legitimate third parties assumed were protected by a freshly-initialized owner slot.

(Note: full exploitation depends on the specific victim contract's constructor/storage layout; the concrete storage-collision primitive itself — same `addrHash` reused across a SELFDESTRUCT+CREATE2 redeploy pair within one transaction — is directly supported by the cited code and was not disproven by any additional protection found in `Program.java`/`RepositoryImpl.java` in the available index.)

  private static byte[] addrHash(byte[] address, byte[] trxHash) {
    if (ByteUtil.isNullOrZeroArray(trxHash)) {
      return Hash.sha3(address);
    }
    return Hash.sha3(ByteUtil.merge(address, trxHash));
  }
