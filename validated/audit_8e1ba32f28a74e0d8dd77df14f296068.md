### Title
Unbounded `io.ReadAll` of push-controlled reference-transaction hook stdin can stall the repository's serialized-write lock - (File: internal/gitaly/hook/referencetransaction.go)

### Summary
The reported bug class is: an untrusted/attacker-influenced payload whose size is never bounded is fully buffered in memory on a critical, serialized code path, allowing a DoS that blocks the pipeline for everyone else. In Gitaly, the `GitLabHookManager.ReferenceTransactionHook` reads the entirety of the reference-transaction hook's stdin — which is driven directly by the set of references an ordinary user pushes in a single `git-receive-pack` invocation — via an unbounded `io.ReadAll`, on the exact code path Gitaly/Praefect uses to serialize writes to a repository (the `preparing`/`prepared`/`committed` phases that hold the cluster-wide per-repository write lock).

### Finding Description
`ReferenceTransactionHook` reads the whole hook stdin into memory with no size cap: [1](#0-0) 

The `changes` buffer is fully user (pusher) controlled: it is the standard-input payload Git's `reference-transaction` hook produces, listing every reference (name + old/new OID) that is part of the current push, per `doc/hooks.md`: [2](#0-1) 

This hook is not a side, best-effort task — it is on Gitaly's serialized-writes critical path. `UpdaterWithHooks.UpdateReference` invokes it three times per reference update — once in `preparing` (before any lock, to acquire the cluster-wide write lock), once in `prepared` (while the reference is locked on disk), and once in `committed`: [3](#0-2) 

`doc/serialized_writes.md` documents that the `preparing` phase is exactly the point where Praefect acquires a global per-repository lock (`WriteLockManager.Lock`) that is held until the `committed` phase releases it, specifically to serialize concurrent writers and avoid ref-lock deadlocks across nodes: [4](#0-3) 

Because `io.ReadAll(stdin)` has no limit, a push containing an extremely large number of reference updates (or very long reference names) in a single `git-receive-pack`/`git push` invocation forces Gitaly to allocate and process an unbounded in-memory buffer while the repository's cluster-wide write lock is held between `preparing` and `committed`. Unlike `git-receive-pack`'s stdout/stderr, which Gitaly explicitly caps via `stderrBuffer`'s 10KB limit (`internal/command/stderrbuffer.go`), this hook-stdin path has no analogous cap: [5](#0-4) [6](#0-5) 

This mirrors the report's core defect: unbounded consumption of attacker-supplied data on a call whose result is unconditionally materialized, on a path that — if slow or memory-exhausting — blocks the shared serialization mechanism (the "checkpoint"/commit gate) rather than just the offending request.

### Impact Explanation
While the lock/hook processing is stalled or the process is put under severe memory pressure by one oversized push, every other write (from any user) targeting the same repository is blocked behind the cluster-wide `WriteLockManager` lock held from `preparing` through `committed`. In a Praefect-managed cluster this can stall reference updates repository-wide, and sustained memory pressure from repeated large pushes can also degrade or crash the Gitaly node hosting other repositories' write paths, which is a concrete DoS of a core RPC handler.

### Likelihood Explanation
Likelihood is bounded by how many distinct references (and how long the names) a single push/`git-receive-pack` invocation can carry, and whether any upstream (Git protocol/Rails) limits already cap this before the hook runs. This requires further validation of practical size limits (e.g., pack/protocol negotiation limits, ref count limits enforced elsewhere), but no such cap is visible at the `io.ReadAll` call site itself, and the operation is reachable by an ordinary authenticated pusher, not a privileged actor.

### Recommendation
Bound the amount of data read from the reference-transaction hook's stdin (e.g., via `io.LimitReader` with a sane maximum number of ref updates / bytes), rejecting or streaming/parsing incrementally instead of buffering the whole payload, consistent with the existing `maxStderrBytes` pattern used elsewhere in `internal/command`.

### Proof of Concept
1. As an ordinary authenticated user with push access to a repository, craft a single push updating an extremely large number of references (or use maximally long valid ref names) in one `git-receive-pack` session.
2. Git's `reference-transaction` hook is invoked with all these updates on stdin at the `prepared`/`committed` phases.
3. `GitLabHookManager.ReferenceTransactionHook` calls `io.ReadAll(stdin)` unconditionally, buffering the full payload while the repository's cluster-wide write lock (acquired at `preparing`) is held, delaying `committed`/lock release and thus delaying/blocking other writers to the same repository.

The reference-transaction hook is executed whenever Git updates a reference from
an old value to a new value, where it hooks into the low-level mechanism to
update references in Git. An update of a hook goes through two phases, where the
hook is executed once for each phase:

1. Git "prepares" the reference transaction. When the hook is called in this
   phase, the references that are about to be updated are locked for concurrent
   modification.
1. Git "commits" or "aborts" the reference transaction.

Depending on how the command updates references, this hook can be executed per
reference that is about to be updated, or for all references at once. The
references that are about to be updated are received on standard input.
