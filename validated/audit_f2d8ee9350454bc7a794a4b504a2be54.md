### Title
Deterministic account permanently freezes deposited funds when its global-contract code fails `prepare_contract` shape validation - (File: `runtime/runtime/src/deterministic_account_id.rs`)

### Summary
`DeterministicStateInitAction` sets a new account's contract to a `GlobalContractIdentifier::CodeHash` without ever validating that the referenced wasm passes `prepare_contract`'s structural checks (e.g. `max_functions_number_per_contract`, `max_locals_per_contract`), only checking `max_contract_size` at global-contract deploy time. Because deterministic accounts never get an access key and their `actor_id` remains the caller (never becomes the account itself), no `DeployContract`, `UseGlobalContract`, or `DeleteAccount` action can ever be authorized against such an account, permanently bricking it and any deposit used to satisfy its storage stake.

### Finding Description
`validate_deploy_global_contract_action` and `DeployGlobalContractAction`'s host-function equivalent (`promise_batch_action_deploy_global_contract_impl`) only bound the raw wasm size against `max_contract_size` [2](#0-1) [4](#0-3) . Full structural validation (`TooManyFunctions`, `TooManyLocals`, etc., enforced in `PrepareContext::run`/`prepare_contract`) is deliberately deferred to the first `FunctionCall`, as documented in `docs/RuntimeSpec/Preparation.md`: "Most of the errors ... are saved and reported when a `FunctionCallAction` is submitted." [3](#0-2) 

For ordinary accounts this deferred-validation design is safe because the deployer retains an access key/`actor_id == account_id`, and can later `DeployContract` again or `DeleteAccount` to reclaim funds — `check_actor_permissions` requires `actor_id == account_id` for `DeployContract`, `UseGlobalContract`, and `DeleteAccount` [5](#0-4) .

Deterministic accounts break this invariant: `create_deterministic_account` explicitly does *not* change `actor_id` to the new account ("Unlike `CreateAccount`, this account creation does not change actor_id... preventing AddKey, DeployContract, or any other actions that only the account owner is permitted to do") [6](#0-5) . `deploy_deterministic_account` calls `use_global_contract`, which sets `AccountContract::Global(code_hash)` and charges storage usage unconditionally, without ever invoking `prepare_contract` [7](#0-6) [1](#0-0) . `action_deterministic_state_init` then uses the attached `deposit` to satisfy `check_storage_stake` and refunds the remainder [8](#0-7) .

Exploit flow:
1. Attacker submits `DeployGlobalContractAction` with wasm that is under `max_contract_size` but violates `max_functions_number_per_contract`/`max_locals_per_contract` — this passes `validate_deploy_global_contract_action` because it only checks size.
2. Attacker computes the derived id via `derive_near_deterministic_account_id` for a `DeterministicAccountStateInit::V1{ code: CodeHash(bad_wasm_hash), data }` and submits `DeterministicStateInitAction` with that receiver and a deposit covering the zero-balance/storage-stake threshold. `validate_deterministic_state_init` only checks the receiver-id match and key/value length limits, not contract validity [9](#0-8) . This succeeds, sets `AccountContract::Global(bad_hash)` and locks the deposit as storage stake.
3. Any subsequent `FunctionCall` receipt to the deterministic account deterministically hits `PrepareError::TooManyFunctions`/`TooManyLocals`, aborting with a guest error and burning gas but performing no useful work.
4. Because `actor_id` for any receipt sent to this account is always the caller's account (never the deterministic account itself, since it can never execute a self-call), `check_actor_permissions` rejects any `DeployContract`, `UseGlobalContract`, or `DeleteAccount` targeting it with `ActorNoPermission`. There is no code path by which the account's contract can be fixed or the account deleted, so the storage-stake deposit is permanently unrecoverable.

### Impact Explanation
This is a permanent freezing-of-funds bug matching the "value conservation / liveness" bounty category: the balance locked to satisfy storage staking on the bricked deterministic account can never be withdrawn, transferred, or refunded through any protocol-defined action, since no actor can ever hold `actor_id == account_id` for it. The amount lost is bounded by the minimal storage-stake requirement (not unlimited), but it is unconditionally and permanently unrecoverable once the account is initialized this way.

### Likelihood Explanation
Fully reachable by an ordinary unprivileged account: deploying a global contract and issuing a `DeterministicStateInitAction` require no special permission, only standard transaction signing and gas/deposit payment. The wasm shaping (e.g., excess function/local counts) needed to fail `prepare_contract` while staying under `max_contract_size` is trivial to construct (as shown by existing `near_test_contracts::LargeContract` test helpers used elsewhere in the repo to trigger `PrepareError::TooManyFunctions`/`TooManyLocals`) [10](#0-9) . The only direct financial loss is to whoever attaches the deposit (typically the same party performing the state init, or a third party persuaded to fund the pre-computed deterministic address before it is "activated" with bad code) — this is fully repeatable and deterministic every time.

### Recommendation
Either (a) validate the referenced global contract's wasm via `prepare_contract` at `DeterministicStateInitAction`/`UseGlobalContract` execution time (or reject state-init when the referenced code is already known to fail preparation), or (b) provide an explicit recovery path for deterministic accounts whose contract can never execute — e.g., allow a permissionless `DeleteAccount`/fund-reclaim mechanism keyed off provable, permanent `PrepareError` status of the account's global contract identifier.

### Proof of Concept
Unit/integration test plan (test-loop-tests, mirroring existing `deterministic_account_id.rs` tests):
1. Deploy a `DeployGlobalContractAction` with `GlobalContractDeployMode::CodeHash` using wasm generated via `near_test_contracts::LargeContract { functions: N, .. }` where `N` exceeds `max_functions_number_per_contract` but the total wasm size stays under `max_contract_size`.
2. Independently call `near_vm_runner::prepare::prepare_contract` on that same wasm and assert it returns `Err(PrepareError::TooManyFunctions)`.
3. Build `DeterministicAccountStateInit::V1{ code: GlobalContractIdentifier::CodeHash(hash_of_bad_wasm), data: {} }`, derive the account id, and submit `DeterministicStateInitAction` with a deposit exactly covering the zero-balance/storage-stake threshold; assert the transaction succeeds and the account now has `AccountContract::Global(bad_hash)` with nonzero `amount()`.
4. Submit a `FunctionCall` receipt to the derived account for any method; assert the execution outcome is a `PrepareError`-based `FunctionCallError` and gas is burnt (`gas_burnt > 0`), with no state change.
5. Attempt `DeleteAccount` (with any predecessor) and `UseGlobalContract`/`DeployContract` against the derived account; assert both fail with `ActionErrorKind::ActorNoPermission` because `actor_id != account_id`, proving there is no in-protocol recovery path and the deposited balance is permanently stuck.

    let key = TrieKey::GlobalContractCode { identifier: contract_identifier.clone().into() };

            identifier: contract_identifier.clone(),

        .into());
        return Ok(());
    }
    clear_account_contract_storage_usage(state_update, account_id, account)?;

            StorageError::StorageInconsistentState(format!(
                "Storage usage integer overflow for account {}",
                account_id
            ))
        })?,
    );
    account.set_contract(contract).or_inconsistent_state(account_id)?;

pub(crate) fn create_deterministic_account(
    initial_balance: Balance,
    storage_usage_config: &StorageUsageConfig,
) -> Account {
    // Unlike `CreateAccount`, this account creation does not change
    // actor_id. This is important to prevent hijacking the account.
    // Actor id remains the predecessor, so any actions following will
    // be checked against that for actor permissions, preventing
    // `AddKey`, `DeployContract`, or any other actions that only the
    // account owner is permitted to do.
    Account::new(
        initial_balance,
        Balance::ZERO,
        AccountContract::None,
        storage_usage_config.num_bytes_account,
    )
}
