### Title
Global (non-URL-scoped) `http.extraHeader` in `cloneFromURLCommand` can leak Authorization credentials to a redirect/attacker host - ([File: internal/gitaly/service/repository/create_repository_from_url.go])

### Summary
`cloneFromURLCommand`, invoked via `CreateRepositoryFromURL` after `validateCreateRepositoryFromURLRequest` only checks for a non-empty URL, injects the Authorization header (built from URL-embedded credentials or `HttpAuthorizationHeader`) using an unscoped `http.extraHeader` git config key instead of the URL-scoped `http.<url>.extraHeader` form used elsewhere in the codebase. Because this header is not bound to a specific host, git will attach it to any HTTP request the `git clone` subprocess makes during that invocation, including one to a different host reached via a redirect.

### Finding Description
In `cloneFromURLCommand` (`internal/gitaly/service/repository/create_repository_from_url.go:41-58`), the authorization header derived from the request is added as: [1](#0-0) 
using the config key `"http.extraHeader"` — a global key that applies to every HTTP request issued in that git invocation, regardless of host. This contrasts with `internal/gitaly/service/remote/find_remote_root_ref.go:33-38` and `internal/gitaly/service/remote/update_remote_mirror.go:93-98`, and `internal/gitaly/service/repository/fetch_remote.go:294-299`, which all scope the header per-URL via `fmt.Sprintf("http.%s.extraHeader", url)`: [2](#0-1) [3](#0-2) 

`validateCreateRepositoryFromURLRequest` performs no host/redirect validation at all — it only rejects an empty URL and validates the target repository path: [4](#0-3) 

The attacker-controlled inputs are `req.GetUrl()` (may embed `user:pass@`) and `req.GetHttpAuthorizationHeader()` (an out-of-band bearer/JWT/Basic credential, as shown being used for GL-Geo tokens in `create_repository_from_url_test.go:92`). Since `cloneFromURLCommand` uses the unscoped key rather than the per-URL key, if the destination server (or any intermediate hop reached over HTTP redirect during `git clone`) redirects the request to a different host, the same `Authorization` header configured for the original host is still attached to the request to the new host — this differs from the `FindRemoteRootRef`/`UpdateRemoteMirror`/`FetchRemote` code paths, which scope the header to the specific URL and are therefore not vulnerable to this cross-host leak in the same way.

Note that the resolved-address / `curloptResolve` pinning (`gitcmd.GetURLAndResolveConfig`) only affects DNS resolution for the *initial* host, not any host a redirect target may specify, so it does not mitigate a credential leak on redirect.

### Impact Explanation
If the auth header is a meaningful, reusable credential (e.g., a GL-Geo JWT, a mirror-pull PAT, or an internal-API token passed via `HttpAuthorizationHeader`), an attacker-controlled or attacker-influenced remote endpoint that responds with an HTTP redirect to a host they control receives that credential in the `Authorization` header. This matches the GitLab bounty "credential/auth-header disclosure to an attacker host" class. For the embedded-URL-credential branch, the leaked credential is one the attacker already possesses (their own import URL credentials), which is not itself sensitive; the higher-severity case is the `HttpAuthorizationHeader` (out-of-band, GitLab-issued) credential.

### Likelihood Explanation
Exploitability depends on whether git's HTTP transport (libcurl-backed) actually forwards a config-level `http.extraHeader` across a cross-host redirect during `git clone`, and on the `http.followRedirects` default git behavior (which by default only follows a redirect for the initial "info/refs" smart-HTTP exchange, using the resulting URL for later requests). I was not able to execute git to empirically confirm whether recent git versions strip the header on cross-host redirect at the transport layer, which they may do independent of the URL-scoping used in the config key. Given the deliberate use of URL-scoped `http.<url>.extraHeader` in the other Gitaly call sites, and this call site's inconsistent unscoped usage, this is a real code-level inconsistency worth flagging, but confirmation of the concrete git-transport leak requires a runtime redirect test (see PoC) rather than static analysis alone.

### Recommendation
Change `cloneFromURLCommand` in `internal/gitaly/service/repository/create_repository_from_url.go` to scope the `http.extraHeader` config key to the specific URL, matching the pattern already used in `find_remote_root_ref.go`, `update_remote_mirror.go`, and `fetch_remote.go`:
```go
config = append(config, gitcmd.ConfigPair{Key: fmt.Sprintf("http.%s.extraHeader", u.String()), Value: authHeader})
```
Additionally, explicitly set `http.followRedirects=false` (or `same` host only) for this clone invocation to guarantee no redirect-based leak regardless of header scoping, and add a regression test analogous to `create_repository_from_snapshot_test.go`'s redirect test that asserts the Authorization header is not sent to a second, different-host test server after a 302 redirect.

### Proof of Concept
```go
func TestServer_CloneFromURLCommand_AuthHeaderNotSentOnCrossHostRedirect(t *testing.T) {
    // Stand up hostA that returns a 302 redirect to hostB (different port/host).
    var hostBGotAuth bool
    hostB := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        if r.Header.Get("Authorization") != "" {
            hostBGotAuth = true
        }
        w.WriteHeader(http.StatusNotFound)
    }))
    defer hostB.Close()

    hostA := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        http.Redirect(w, r, hostB.URL+"/repo.git/info/refs?service=git-upload-pack", http.StatusFound)
    }))
    defer hostA.Close()

    cfg := testcfg.Build(t)
    s := server{cfg: cfg, gitCmdFactory: gittest.NewCommandFactory(t, cfg)}
    ctx := testhelper.Context(t)

    cmd, err := s.cloneFromURLCommand(ctx, hostA.URL+"/repo.git", "", filepath.Join(testhelper.TempDir(t), "target"),
        "Bearer super-secret-token", false, gitcmd.WithDisabledHooks())
    require.NoError(t, err)
    _ = cmd.Wait() // expected to fail (404), that's fine

    // Assert the secret token was never observed by hostB.
    require.False(t, hostBGotAuth, "Authorization header must not be sent to a different host reached via redirect")
}
```
Expected (vulnerable) result: `hostBGotAuth` is `true` because the unscoped `http.extraHeader` is attached regardless of the current request host. Expected (fixed) result: `hostBGotAuth` is `false` once the header is scoped to `http.<originalURL>.extraHeader` and/or redirects are disabled for the clone.
