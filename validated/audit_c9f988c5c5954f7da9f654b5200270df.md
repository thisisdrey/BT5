## Analog Found

### Title
Missing zero-address (all-zero payload) validation in `TransferActuator`/`TransferAssetActuator` can permanently burn TRX/TRC10 tokens - (File: `actuator/src/main/java/org/tron/core/actuator/TransferActuator.java`)

### Summary
`DecodeUtil.addressValid`, used by every actuator that validates a `toAddress` (including `TransferActuator` and `TransferAssetActuator`), only checks that the address is non-empty, exactly 21 bytes, and starts with the correct network prefix byte. It never checks that the 20-byte payload itself is non-zero.

### Finding Description
`TransferActuator.validate()` and `TransferAssetActuator.validate()` call `DecodeUtil.addressValid(toAddress)` before allowing the transfer to proceed: [1](#0-0) [2](#0-1) 

The validation logic itself: [3](#0-2) 

`addressValid` only enforces length (`ADDRESS_SIZE / 2` = 21 bytes) and the prefix byte (`0x41` on mainnet). It does not reject an address whose remaining 20 bytes are all zero (i.e., `0x41 0x00...0x00`). Such an address is a syntactically "valid" Tron address per this check, but it is not a real, controllable account — nobody holds its private key. Since neither `TransferActuator` nor `TransferAssetActuator` has any additional check against this all-zero payload, a caller can build a `TransferContract`/`TransferAssetContract` with `to_address = 0x41` followed by 20 zero bytes. The actuator will happily create a new normal account at that address (since `accountStore.get(toAddress)` returns null) and credit it with the transferred TRX or TRC10 balance: [4](#0-3) [5](#0-4) 

This is directly analogous to the reported bug class: a broadcastable, unprivileged transaction (any signed `TransferContract`/`TransferAssetContract`) can move funds to an address that is not backed by any accessible private key, silently and permanently locking those funds, exactly as `FootiumGeneralPaymentContract::makePayment` can send ETH to the zero address without reverting.

### Impact Explanation
Funds sent to the all-zero-payload address are unrecoverable by the sender (and by anyone else, since no private key corresponds to it), constituting a permanent freezing/loss of funds for the transaction's own balance. While this is self-inflicted (the sender chooses the destination), the root cause matches the reported vulnerability class exactly: lack of validation that the destination address is not a "null"/burn-style value, allowing value to be silently and irreversibly locked rather than the transaction being rejected. This differs from `blackhole` handling in the codebase, which is an intentional, tracked burn mechanism (`dynamicStore.burnTrx`/`accountStore.getBlackhole()`); the all-zero address is not this designated blackhole account and is not accounted for as a burn, so tokens sent there are simply orphaned in a normal, but inaccessible, account.

### Likelihood Explanation
Any unprivileged user constructing and broadcasting a `TransferContract` or `TransferAssetContract` can trigger this by supplying an all-zero 20-byte payload with the correct prefix byte — no special privileges or contract deployment required. The condition is trivial to satisfy since `addressValid` performs no zero-value/blacklist check.

### Recommendation
Add an explicit check in `DecodeUtil.addressValid` (or in each actuator's `validate()`) rejecting addresses whose 20-byte payload is all zero, in addition to the existing length/prefix checks, mirroring the recommendation in the original report to validate the receiver before proceeding with payment.

### Proof of Concept
1. Craft a `TransferContract` with `owner_address` = a funded account and `to_address` = `0x41` followed by 20 `0x00` bytes (21 bytes total, valid prefix, passes `DecodeUtil.addressValid`).
2. Sign and broadcast the transaction.
3. `TransferActuator.validate()` passes all checks (`addressValid` returns true, addresses differ, owner has balance).
4. `TransferActuator.execute()` creates a new `AccountCapsule` at the zero-payload address and credits it with `amount`, permanently locking those funds since no private key exists for that address.

  public static boolean addressValid(byte[] address) {
    if (ArrayUtils.isEmpty(address)) {
      logger.warn("Warning: Address is empty !!");
      return false;
    }
    if (address.length != ADDRESS_SIZE / 2) {
      logger.warn(
          "Warning: Address length need " + ADDRESS_SIZE + " but " + address.length
              + " !!");
      return false;
    }

    if (address[0] != addressPreFixByte) {
      logger.warn("Warning: Address need prefix with " + addressPreFixByte + " but "
          + address[0] + " !!");
      return false;
    }
    return true;
  }
