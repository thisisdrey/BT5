### Title
Unsafe `DataWord.intValue()` truncation in `Program.memoryExpand` allows attacker-controlled length headers to silently wrap/corrupt VM memory sizing - (File: `actuator/src/main/java/org/tron/core/vm/program/Program.java`)

### Summary
The websocket-driver bug is a classic "attacker-controlled length header decoded byte-by-byte into a fixed-precision number, with no bound check, causing silent value corruption that desynchronizes the parser from the real payload boundaries." The TVM analog is `DataWord.intValue()`, which accumulates a 32-byte stack word into a 32-bit `int` with the exact same unchecked, no-bounds-check shift-accumulate pattern, and is used directly (instead of the safe `intValueSafe()` variant) in `Program.memoryExpand`.

### Finding Description
`DataWord.intValue()` decodes an arbitrary, attacker-supplied 256-bit stack value into a 32-bit `int` by repeatedly shifting and OR-ing bytes with no overflow check: [1](#0-0) 

Because this loop discards all high-order bits once the shifted value exceeds 32 bits, a value with the high bit set (or any value ≥ 2^31) is silently truncated/wrapped into a small or negative `int` — mirroring the "bytes with high bit set / 0x80+" corruption pattern from the advisory, except here it is a deterministic integer wraparound instead of floating point precision loss, with the same practical effect: the declared "length" no longer matches the value that downstream code actually consumes.

The codebase is aware of this danger and provides `intValueSafe()`, which checks `bytesOccupied() > 4` and clamps to `Integer.MAX_VALUE` instead of wrapping: [2](#0-1) 

Most memory-touching opcodes correctly use `intValueSafe()` (e.g. `sha3Action`, `callDataCopyAction`, `codeCopyAction`, `extCodeCopyAction`): [3](#0-2) 

However, `Program.memoryExpand` — used to pre-extend memory for the CALL-family "out data" region — calls the unsafe `intValue()` instead: [4](#0-3) 

This creates an inconsistency: the size actually used to *grow* the memory buffer (via `intValue()`, which can wrap to a small/negative number for a huge, attacker-chosen `outDataSize`) can diverge from the size used elsewhere in the same call path via `intValueSafe()` (clamped to `Integer.MAX_VALUE`). That divergence is structurally identical to the websocket-driver flaw: a length header parsed inconsistently by different consumers of the same byte stream, corrupting subsequent data interpretation.

### Impact Explanation
If the memory buffer is not extended to the size that a later step believes it holds (because `memoryExpand` wrapped the requested size to something small or negative while other logic assumes the `intValueSafe()`-clamped size), the VM's `Memory` chunk bookkeeping (`softSize`, chunk list) can become inconsistent with subsequent reads/writes, leading to out-of-bounds memory reads/writes inside the TVM interpreter, corrupted execution results, or an interpreter crash/halt for the node executing the contract. This is reachable by any account that can deploy/call a contract using CALL/CALLCODE/DELEGATECALL/STATICCALL with attacker-chosen `outDataSize` — i.e., any unprivileged contract deployer/caller, with no special privilege required.

### Likelihood Explanation
Reaching this code path only requires crafting a smart contract that issues a CALL-family instruction with a very large `outDataSize` stack value (a value with high bits set, exactly analogous to the `0x80+` byte sequence in the original advisory) and broadcasting a transaction that executes it. No node operator or validator cooperation is needed, making the likelihood of triggering the unsafe `intValue()` path high once the entry point is confirmed to be reachable from `memoryExpand`'s only caller.

### Recommendation
Change `Program.memoryExpand` to use `DataWord.intValueSafe()` for both `outDataOffs` and `outDataSize`, consistent with every other memory-touching opcode in `OperationActions.java`, so that oversized/overflowing length values are clamped rather than silently wrapped.

### Proof of Concept
1. Deploy a contract whose bytecode issues a `CALL` (or `DELEGATECALL`/`STATICCALL`) with an `outDataSize` operand equal to a value ≥ `2^31` (e.g. `0x8000000000000000...`), and a correspondingly large `outDataOffs`.
2. Broadcast the transaction invoking this contract.
3. `Program.memoryExpand` computes `outDataSize.intValue()`, which wraps to a small/negative `int` instead of the intended huge size, while other code paths for the same call may use `intValueSafe()` (clamped to `Integer.MAX_VALUE`). Because `Memory.extend` is never called with the correct size, later reads/writes against the "out data" region operate on unallocated/undersized memory, producing corrupted results or triggering an unexpected internal exception during block/transaction execution.     int intVal = 0;

    for (byte aData : data) {
      intVal = (intVal << 8) + (aData & 0xff);
    }

    return intVal;
  }

  /**
   * In case of int overflow returns Integer.MAX_VALUE otherwise works as #intValue()
   */
  public int intValueSafe() {
    int bytesOccupied = bytesOccupied();
    int intValue = intValue();
    if (bytesOccupied > 4 || intValue < 0) {
      return Integer.MAX_VALUE;
    }
    return intValue;
  }

  public static void codeCopyAction(Program program) {
    byte[] fullCode = program.getCode();

    int memOffset = program.stackPop().intValueSafe();
    int codeOffset = program.stackPop().intValueSafe();
    int lengthData = program.stackPop().intValueSafe();

    int sizeToBeCopied = lengthData;
    if ((long) codeOffset + lengthData > fullCode.length) {
      sizeToBeCopied = fullCode.length < codeOffset ? 0 : fullCode.length - codeOffset;
    }

    byte[] codeCopy = new byte[lengthData];

    if (codeOffset < fullCode.length) {
      System.arraycopy(fullCode, codeOffset, codeCopy, 0, sizeToBeCopied);
    }

    program.memorySave(memOffset, codeCopy);
    program.step();
  }
