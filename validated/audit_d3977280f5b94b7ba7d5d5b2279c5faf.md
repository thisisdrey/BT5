Audit Report

## Title
Outbound Queue V2 accepts an unvalidated, attacker-controllable `fee` for real delivery work, allowing zero relayer compensation - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/send_message_impl.rs`, `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
`SendMessage::validate` in the v2 outbound queue only checks payload size and never validates or floors `Message.fee`, and `Pallet::do_process_message` stores that raw, caller-supplied `fee` verbatim into `PendingOrder.fee` before committing the message into the Merkle root that requires real off-chain relayer work on Ethereum. `process_delivery_receipt` only pays a reward `if order.fee > 0`, so a message enqueued with `fee: 0` still gets committed and requires relaying, but the relayer receives nothing.

## Finding Description
`SendMessage::validate` only bounds payload size, doing nothing with `message.fee`: [1](#0-0) 

`do_process_message` decodes `Message { fee, .. }` and stores it unmodified into `PendingOrder`, with no lower bound enforced anywhere in the path: [2](#0-1) 

`process_delivery_receipt` skips reward payment entirely when `order.fee == 0`: [3](#0-2) 

`AddTip` only adds on top of an existing fee and is not mandatory before commit: [4](#0-3) 

The upstream XCM path (`EthereumBlobExporter` v2 + `XcmConverter::convert`) extracts the fee from the `WithdrawAsset`/`PayFees` XCM instructions and only enforces `reserved_fee_amount >= fee_amount` and that the fee asset is Ether — there is no floor requiring a nonzero or minimum amount: [5](#0-4) [6](#0-5) 

A user constructing a `PayFees { asset: Asset { fun: Fungible(0), .. } }` (or any small value) satisfies `reserved_fee_amount >= fee_amount` trivially, and the converter accepts `fee_amount == 0` into `Message.fee`. This message is then queued, `AliasOrigin`-gated (requiring the origin to pass `AllowedAliasOrigin`, generally sibling parachains like AssetHub — not root/governance), but nothing after that gates the fee value. The `snowbridge_pallet_system_v2::Pallet::send` internal helper takes `fee: u128` as a parameter, but that function is only reachable via governance-restricted extrinsics (`GovernanceOrigin`), so it is not the attacker-reachable path; the XCM export path is the actually unprivileged, reachable path for a sibling chain / user-originated XCM to reach `fee: 0`.

## Impact Explanation
A message with `fee: 0` (or negligible fee) is still committed into the Merkle root, included in the header digest via `SnowbridgeDigestItem::SnowbridgeV2`, and requires a relayer to submit a Beefy-verified delivery receipt after real gas expenditure executing the message on Ethereum. Because `process_delivery_receipt` skips `T::RewardPayment::register_reward` when `order.fee == 0`, this is a case of public, underpriced/unpaid off-chain relayer work that can suppress relayer participation and degrade or stall Snowbridge V2 outbound message delivery to Ethereum — matching the "public underpriced work that degrades block production or stalls bridge processing" impact category.

## Likelihood Explanation
Any unprivileged XCM sender routed through the `EthereumBlobExporter` v2 (e.g., a user on AssetHub sending a `WithdrawAsset`/`PayFees`/`AliasOrigin`/`DepositAsset` XCM program to Ethereum) fully controls the `fee_amount` extracted by `XcmConverter::extract_remote_fee`, and can set it to zero or a trivial value while still producing a valid command (e.g., a token transfer) that requires real relayer work. No privileged role, governance action, or compromised relayer is needed — the flaw is in the pallet/primitive's unconditional acceptance of caller-supplied fee data with no minimum-fee enforcement in `validate`, `do_process_message`, or the XCM converter.

## Recommendation
Enforce a minimum fee at message validation/enqueue time:
- In `SendMessage::validate` (`send_message_impl.rs`) or `do_process_message` (`lib.rs`), reject (`SendError`/`ProcessMessageError`) messages whose `fee` is below a configured `MinimumDeliveryFee` needed to compensate expected relayer gas cost.
- Alternatively, in `XcmConverter::extract_remote_fee` (`convert.rs`), require `fee_amount` to meet a minimum floor before accepting the XCM as routable to Ethereum, rather than only checking `reserved_fee_amount >= fee_amount`.
- Remove or tighten the `if order.fee > 0` shortcut in `process_delivery_receipt` so it cannot silently avoid rewarding valid delivery work; instead the fee floor should be enforced upstream so `order.fee` is never a false/zero value for a message requiring real relay effort.

## Proof of Concept
1. Construct an XCM with `WithdrawAsset(fee: Fungible(0))`, `PayFees { asset: Fungible(0) }`, an ENA/PNA transfer, `AliasOrigin(<sibling-chain-origin>)`, `DepositAsset`, and `SetTopic` — `extract_remote_fee` accepts `fee_amount = 0` since `reserved_fee_amount (0) >= fee_amount (0)` (`convert.rs` lines 94-117), and `convert()` embeds `fee: fee_amount` into `Message` (lines 312-317).
2. Route this XCM through `EthereumBlobExporter::validate`/`deliver`, which calls `OutboundQueue::validate` (`send_message_impl.rs` lines 23-32) — only payload size is checked, so `fee: 0` passes.
3. `deliver` enqueues the message; `do_process_message` runs and stores `PendingOrder { fee: 0, .. }` while committing the message into `MessageLeaves`/Merkle root (`lib.rs` lines 390-436) — this message now requires real off-chain relaying to Ethereum.
4. A relayer performs the actual delivery and calls `submit_delivery_receipt` → `process_delivery_receipt`; since `order.fee == 0`, the `if order.fee > 0` guard skips `T::RewardPayment::register_reward` (`lib.rs` lines 464-473), so the relayer is paid nothing for verified, real delivery work.

		use XcmConverterError::*;
		let reserved_fee_assets = match_expression!(self.next()?, WithdrawAsset(fee), fee)
			.ok_or(WithdrawAssetExpected)?;
		ensure!(reserved_fee_assets.len() == 1, AssetResolutionFailed);
		let reserved_fee_asset =
			reserved_fee_assets.inner().first().cloned().ok_or(AssetResolutionFailed)?;
		let (reserved_fee_asset_id, reserved_fee_amount) = match reserved_fee_asset {
			Asset { id: asset_id, fun: Fungible(amount) } => Ok((asset_id, amount)),
			_ => Err(AssetResolutionFailed),
		}?;
		let fee_asset =
			match_expression!(self.next()?, PayFees { asset: fee }, fee).ok_or(InvalidFeeAsset)?;
		let (fee_asset_id, fee_amount) = match fee_asset {
			Asset { id: asset_id, fun: Fungible(amount) } => Ok((asset_id, *amount)),
			_ => Err(AssetResolutionFailed),
		}?;
