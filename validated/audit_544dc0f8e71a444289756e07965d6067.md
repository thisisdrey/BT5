### Title
Vote-reward calculation diverges between `VoteRewardUtil` (TVM path) and `MortgageService` (native actuator path) - ([File: actuator/src/main/java/org/tron/core/vm/utils/VoteRewardUtil.java])

### Summary
`VoteRewardUtil.computeReward` (used by the TVM freeze/unfreeze/vote/withdraw-reward precompiles) and `MortgageService.computeReward` (used by the native `WithdrawBalanceActuator`, `UnfreezeBalanceActuator`, `UnfreezeBalanceV2Actuator`, `VoteWitnessActuator`) are supposed to compute the *same* quantity — a voter's accumulated SR reward for a cycle range — but they implement different logic, exactly the pattern flagged in the external report where two `_balanceOf`-style functions compute the same value differently.

### Finding Description
`MortgageService.computeReward(beginCycle, endCycle, accountCapsule)` explicitly branches on whether the cycle range predates `NEW_REWARD_ALGORITHM_EFFECTIVE_CYCLE`. For the portion of the range that is "old", it delegates to `getOldReward`, which either calls `rewardViCalService.getNewRewardAlgorithmReward(...)` (which blocks with `lock.await()` until the Vi-index build (`RewardViCalService.isDone()`) completes) or falls back to a legacy per-cycle proportional computation (`voteRate * totalReward`) when the new algorithm is not yet enabled: [1](#0-0) [2](#0-1) 

By contrast, `VoteRewardUtil.computeReward` — invoked from the TVM native-contract processors reachable via ordinary smart-contract calls (`WithdrawRewardProcessor`, `UnfreezeBalanceProcessor`, `UnfreezeBalanceV2Processor`, `VoteWitnessProcessor`, and suicide handling in `Program.java`) — unconditionally uses the Vi-delta formula for the *entire* `[beginCycle, endCycle)` range, with no check for `NEW_REWARD_ALGORITHM_EFFECTIVE_CYCLE`, no fallback to the legacy per-cycle formula, and no wait/guard on `RewardViCalService.isDone()`: [3](#0-2) 

Confirmed call sites showing the TVM/native-contract processors that use `VoteRewardUtil` instead of `MortgageService`: [4](#0-3) 

And the parallel native-transaction path that uses `MortgageService` for the equivalent operation: [5](#0-4) 

Because both code paths read/write the same on-chain state (`DelegationStore` begin/end cycle, `AccountCapsule.allowance`, and `RewardViStore`) but compute the reward amount with different formulas for cycles prior to the new-algorithm cutover, a user's realized reward differs depending on whether they withdraw/vote/freeze/unfreeze via a normal transaction (`MortgageService`) or via a deployed contract invoking the TVM vote/withdraw-reward opcode (`VoteRewardUtil`).

### Impact Explanation
This is a fund-accounting inconsistency, not merely a cosmetic difference: `adjustAllowance` mutates `AccountCapsule.allowance`, which is later moved into `balance` on withdrawal. If the TVM path (`VoteRewardUtil`) computes a reward greater than what `MortgageService`/the legacy per-cycle algorithm would have produced for the same historical cycles (e.g., due to rounding differences between the double-based `voteRate * totalReward` legacy formula and the BigInteger Vi-delta formula, or because it reads `RewardViStore` values before `RewardViCalService` has finished (re)computing them via `startRewardCal`), a contract-triggered withdrawal can mint allowance/balance not backed by the actual reward pool recorded by `DelegationStore.addReward`. Conversely, if it under-computes, funds legitimately owed to voters can be permanently unreachable through the TVM path (temporary/permanent freezing of funds), while a normal `WithdrawBalanceContract` transaction for the same account would yield a different, "correct" amount. This constitutes an unbacked-balance / fund-miscalculation class issue reachable from a single signed transaction (any account triggering a smart contract that exercises TVM voting/withdraw-reward opcodes).

### Likelihood Explanation
Any account can reach `VoteRewardUtil.withdrawReward`/`computeReward` simply by calling a deployed contract that exercises the TVM freeze, unfreeze, vote, or withdraw-reward native opcodes — no special privilege is required. The divergent code paths are always live (both are reachable in production), and the discrepancy is guaranteed to manifest whenever a voter's reward-accrual history straddles `NEW_REWARD_ALGORITHM_EFFECTIVE_CYCLE`, i.e., for essentially all long-lived voter accounts on mainnet given the algorithm was switched over historically. I was not able to fully verify `DelegationStore.getWitnessVi`'s exact backing storage and consistency guarantees in this session (tool budget exhausted), so the precise magnitude/direction of the discrepancy in the current codebase state is not fully confirmed and should be validated with a live trace comparing `MortgageService.queryReward` vs `VoteRewardUtil.queryReward` for the same account/cycle range.

### Recommendation
Unify the reward computation: make `VoteRewardUtil.computeReward` delegate to (or share an implementation with) `MortgageService.computeReward`/`getOldReward`, including the `NEW_REWARD_ALGORITHM_EFFECTIVE_CYCLE` branch and the `RewardViCalService.isDone()`/`lock.await()` guard, so that TVM-triggered and transaction-triggered reward withdrawals always produce identical results for the same account and cycle range.

### Proof of Concept
1. Deploy a contract that calls the TVM `vote`, `freeze`, and `withdrawreward` opcodes (as exercised by `VoteTest.checkRewardAndWithdraw`), for a voter account whose vote history spans cycles before and after `NEW_REWARD_ALGORITHM_EFFECTIVE_CYCLE`. [6](#0-5) 
2. In parallel, compute the same account's reward via `MortgageService.queryReward`/`withdrawReward` (as used by `WithdrawBalanceActuator`) for the identical cycle range. [7](#0-6) 
3. Compare the two resulting `allowance`/`balance` deltas: because `VoteRewardUtil.computeReward` unconditionally applies the Vi-delta formula while `MortgageService.computeReward` applies the legacy per-cycle formula for cycles before the cutover, the two paths can yield different amounts for the same underlying vote/reward state, demonstrating the unbacked/inconsistent balance calculation.

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }

  private static long computeReward(long beginCycle, long endCycle,
                                    AccountCapsule accountCapsule, Repository repository) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    for (Protocol.Vote vote : accountCapsule.getVotesList()) {
      byte[] srAddress = vote.getVoteAddress().toByteArray();
      BigInteger beginVi = repository.getDelegationStore().getWitnessVi(beginCycle - 1, srAddress);
      BigInteger endVi = repository.getDelegationStore().getWitnessVi(endCycle - 1, srAddress);
      BigInteger deltaVi = endVi.subtract(beginVi);
      if (deltaVi.signum() <= 0) {
        continue;
      }
      long userVote = vote.getVoteCount();
      reward += deltaVi.multiply(BigInteger.valueOf(userVote))
          .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
    }
    return reward;
  }

  private void checkRewardAndWithdraw(byte[] contract, boolean isZero) throws Exception {
