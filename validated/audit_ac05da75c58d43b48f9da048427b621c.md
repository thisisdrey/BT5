### Title
Dust debt positions below `debtFloorInUsd` can be opened via `DebtToken.issue` and become permanently unliquidatable - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool.liquidate` enforces two incompatible bounds: a liquidation can repay at most `maxLiquidable` (50%) of the debt balance, and it must not leave a residual debt strictly between `0` and `debtFloorInUsd`. `DebtToken.issue` and `DebtToken.mint` only check position health via `debtPositionOf`, never a minimum debt size, so any user can open a debt position whose USD value is below `debtFloorInUsd`. Once such a position turns unhealthy, every `liquidate` call reverts: a 100% repay violates `maxLiquidable`, and any smaller repay leaves `0 < _newDebtInUsd < debtFloorInUsd` and hits `RemainingDebtIsLowerThanTheFloor`. `repay`/`repayAll` cannot rescue it either (`repay` reverts below the floor; `repayAll` requires holding the full synthetic amount, which a profit-seeking liquidator has no incentive to do at a loss). The result is a permanent liveness failure of liquidation for that position, analogous to the CVE's DoS impact class.

### Finding Description
- `Pool.liquidate` (contracts/Pool.sol:567-579) reverts when `amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable` and when the post-liquidation debt satisfies `0 < _newDebtInUsd < debtFloorInUsd`.
- `maxLiquidable` is initialized to `0.5e18` (contracts/Pool.sol:181), so a repay of 100% always reverts with `AmountGreaterThanMaxLiquidable`.
- `DebtToken.issue` (contracts/DebtToken.sol:235-271) only enforces `NotEnoughCollateral` via `_issuableInUsd`; there is no check that the resulting debt is `>= debtFloorInUsd` or `0`.
- `DebtToken.repay` (contracts/DebtToken.sol:442-451) also enforces the floor on the residual, so neither the borrower nor a third party can partially reduce a sub-floor debt — only `repayAll` (full repayment) is possible.
- Attack path: attacker deposits collateral, calls `issue(dustAmount, attacker)` so `debtInUsd < debtFloorInUsd`, waits for (or induces via allowed same-transaction oracle manipulation / market movement) the position to become unhealthy. From then on, `liquidate` reverts for every `amountToRepay_`. Repeat across many accounts and synthetic tokens to aggregate unliquidatable bad debt.

### Impact Explanation
If the position becomes underwater (debt > collateral value × incentives), no liquidator can ever clear it: the protocol's liquidation mechanism is permanently bricked for that position and the account's collateral is locked from seizure (withdraw is blocked by `_revertIfLocked` while unhealthy, and `seize` is only callable via `liquidate`). This is a permanent freezing of funds plus accruing bad debt — a liveness/availability failure matching the bug class. The per-position bad debt is bounded by `debtFloorInUsd`, but the attack is cheap to replicate across arbitrary accounts and debt tokens.

### Likelihood Explanation
Requires `debtFloorInUsd > 0` on the deployed pool — the floor exists precisely to make liquidations profitable, so it is expected to be nonzero in production (could not confirm the on-chain value from the repo; the deploy scripts reference `updateDebtFloor`). The attack needs no privileged role: `issue` is a public entry point and the attacker spends only collateral plus dust debt minting costs. The blocker is that the attacker must wait for their dust position to become unhealthy, and the profit/loss asymmetry is small per account; scaling requires many accounts.

### Recommendation
Enforce the debt floor at issuance: in `DebtToken.issue`/`mint` (or in `Pool` post-issue health check), require the resulting per-token debt to be either `0` or `>= debtFloorInUsd`, mirroring the check in `repay` (contracts/DebtToken.sol:442-451). Alternatively, exempt full repayments from the `maxLiquidable` cap in `Pool.liquidate` so a sub-floor position can always be closed in one call.
