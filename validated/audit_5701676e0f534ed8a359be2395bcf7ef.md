### Title
Attacker can grief any account by stuffing `depositTokensOfAccount` to `MAX_TOKENS_PER_USER`, blocking collateral top-ups and new positions - ([File: contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
The BIND CVE class is a resource-limit mechanism that can be driven to an unintended state causing denial of service. The Metronome analog is the `MAX_TOKENS_PER_USER` cap in `Pool`, enforced by `onlyIfAdditionWillNotReachMaxTokens` on `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount`. Because `DepositToken._transfer` and `_mint` add the token to the *recipient's* per-account list, an unprivileged attacker can fill a victim's list with dust amounts of every supported deposit token, permanently blocking that victim from using any additional collateral or debt tokens.

### Finding Description
`Pool.addToDepositTokensOfAccount` reverts once `debtTokensOfAccount.length + depositTokensOfAccount.length >= MAX_TOKENS_PER_USER` (30) [1](#0-0) . The list is updated as a side effect whenever a recipient's balance moves from zero [2](#0-1) .

Two permissionless attack paths exist:

1. `DepositToken.deposit(amount_, onBehalfOf_)` accepts an arbitrary beneficiary; `_mint` calls `pool.addToDepositTokensOfAccount(onBehalfOf_)` when the beneficiary's balance is zero [3](#0-2) . The attacker deposits dust of each underlying with `onBehalfOf_ = victim`.
2. `DepositToken.transfer(to_, amount_)` adds the token to `to_`'s list on first receipt [4](#0-3) .

`Pool.addDepositToken` allows up to `MAX_TOKENS_PER_USER` deposit token types [5](#0-4) , so on pools with ~30 collaterals the attacker can fully saturate the victim's list. There is no way for the victim or anyone else to remove an entry except the victim spending gas to transfer/withdraw each dust balance to zero (`_transfer` removes the sender's entry only when their balance hits zero) [6](#0-5) .

No modifier stops this: `deposit`/`transfer` are `whenNotPaused nonReentrant` only, `SynthContext._msgSender` is irrelevant, and `addToDepositTokensOfAccount` cannot be invoked directly by the attacker (it checks `SenderIsNotDepositToken`) but is reached as a side effect [7](#0-6) .

### Impact Explanation
Once saturated, every subsequent action that would add a *new* token to the victim's list reverts with `UserReachedMaxTokens`:

- The victim cannot `deposit` a new collateral type — critical if their position is approaching liquidation and they need to top up with a different asset to avoid seizure.
- The victim cannot `issue` a new synthetic (its `DebtToken._mint` calls `addToDebtTokensOfAccount` [8](#0-7) ).
- If a liquidator's account is stuffed, `Pool.liquidate` → `DepositToken.seize` → `_transfer` → `addToDepositTokensOfAccount(liquidator)` reverts [9](#0-8) , DoS-ing liquidations of that collateral type for targeted liquidator addresses.

The cleanup cost is asymmetric: the attacker pays only dust (plus deposit fee), while the victim must send up to 30 recovery transactions before regaining functionality — temporary freezing of the account's ability to manage its position, and forced liquidation loss if it occurs while the victim is unhealthy.

### Likelihood Explanation
Requires only an EOA with dust amounts of each underlying; `deposit` is a public entry point and `onBehalfOf_` is attacker-chosen. Feasibility depends on the pool having many registered deposit tokens (up to 30 slots). Cost scales linearly with the number of token types and is low. Existing affected positions can be attacked preemptively before they become liquidatable.

### Recommendation
- Do not count a token toward `MAX_TOKENS_PER_USER` unless the account's balance exceeds a minimum meaningful threshold (e.g. dust floor in USD), or
- Track per-account tokens in a way that ignores unsolicited dust (e.g. only add on `deposit`/`issue` initiated for oneself, not on inbound `transfer`/`seize`), or
- Allow accounts to self-remove entries (`removeFromDepositTokensOfAccount` is currently callable only by the token contract [10](#0-9) ).

### Proof of Concept
```solidity
// Foundry test sketch (fork: deployed Pool + DepositTokens)
// victim has 0..k tokens; attacker fills to MAX_TOKENS_PER_USER = 30
function testStuffVictimTokenList() public {
    address victim = makeAddr("victim");
    address attacker = makeAddr("attacker");

    address[] memory dts = pool.getDepositTokens();
    uint256 already = pool.getDepositTokensOfAccount(victim).length
                    + pool.getDebtTokensOfAccount(victim).length;

    for (uint256 i; i < dts.length && already + i < pool.MAX_TOKENS_PER_USER(); ++i) {
        IERC20 underlying = IDepositToken(dts[i]).underlying();
        deal(address(underlying), attacker, 1);           // dust
        vm.startPrank(attacker);
        underlying.approve(dts[i], 1);
        IDepositToken(dts[i]).deposit(1, victim);         // _mint -> addToDepositTokensOfAccount(victim)
        vm.stopPrank();
    }

    // victim can no longer deposit a NEW collateral type
    address newDt = dts[dts.length - 1]; // a deposit token victim doesn't hold
    IERC20 newUnderlying = IDepositToken(newDt).underlying();
    deal(address(newUnderlying), victim, 1e18);
    vm.startPrank(victim);
    newUnderlying.approve(newDt, 1e18);
    vm.expectRevert(Pool.UserReachedMaxTokens.selector);
    IDepositToken(newDt).deposit(1e18, victim);
    vm.stopPrank();
}
```
The revert occurs inside `Pool.addToDepositTokensOfAccount` reached via `DepositToken._mint`, demonstrating a temporary freeze of the victim's ability to add collateral or take new debt until they pay gas to empty each dust balance.
