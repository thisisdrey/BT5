### Title
Liquidation dust-lock: `debtFloorInUsd` + `maxLiquidable` permanently brick a position below the floor - (File: contracts/Pool.sol)

### Summary
`Pool.liquidate` enforces two independent bounds on the repaid amount: `amountToRepay_` cannot exceed `maxLiquidable` (50%) of the account's debt-token balance, and the remaining debt must be either exactly `0` or `>= debtFloorInUsd`. Once an account's debt in a synthetic asset falls into the range `(0, ~2 * debtFloorInUsd)` there is no repay amount that satisfies both constraints: repaying in full exceeds `maxLiquidable` and reverts with `AmountGreaterThanMaxLiquidable`, while any partial repay leaves a residual `0 < residual < debtFloorInUsd` and reverts with `RemainingDebtIsLowerThanTheFloor`. The position becomes permanently unliquidatable, freezing the collateral and stranding bad debt in the protocol — the same DoS-by-abort class as the ImageMagick `MogrifyImageList` assertion, where a crafted state makes every subsequent list operation fail.

### Finding Description
In `Pool.liquidate` (contracts/Pool.sol:537-596):

- Line 567-569: `if (amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable) revert AmountGreaterThanMaxLiquidable();` — with `maxLiquidable = 0.5e18` set in `initialize` (line 181), at most 50% of the debt can be repaid per call.
- Lines 571-579: the floor check computes `_newDebtInUsd` for `_debtTokenBalance - amountToRepay_` and reverts whenever `0 < _newDebtInUsd < debtFloorInUsd`.

Concretely, let `D` be the remaining debt in USD terms and `F = debtFloorInUsd`:
- Full repay (`amountToRepay_ = D`) is rejected whenever `D` per-debt-token share exceeds 50% — i.e., always, once `D` is the only/most debt, since 100% > 50%.
- Partial repay of `x` is rejected whenever `D - x < F`, i.e., `x > D - F`. When `D < 2F`, the allowed interval `x <= min(0.5·D-equivalent, D - F)` still exists, so a liquidator can repay down to exactly `D = F`.
- At `D = F` (or any `0 < D <= F` reached by pushing `D - x` to land on `F`), every non-zero `x` produces `0 < D - x < F` → `RemainingDebtIsLowerThanTheFloor`, and `x = D` produces a 100% repay → `AmountGreaterThanMaxLiquidable`. No valid `amountToRepay_` exists.

An unprivileged liquidator (or the borrower via normal repay paths that share the same `debtFloorInUsd` invariant in `DebtToken`) can deliberately choose repay amounts that land the residual debt exactly on `F`, after which the position can never be liquidated or further reduced in that synthetic asset — aborting every subsequent call, analogous to the crafted-file assertion failure.

### Impact Explanation
- Permanent bad debt: an underwater account whose residual debt is locked at `<= debtFloorInUsd` can never be liquidated. The collateral it still holds is effectively unseizable, so the protocol eats the shortfall — solvency invariant broken.
- Permanent freezing of funds: the victim's remaining collateral in that deposit token cannot be seized, and positions in that state also grief the account's `depositTokensOfAccount`/`debtTokensOfAccount` bookkeeping since balances never reach zero.
- No privileged actor required: the state is reached by ordinary `liquidate` / `repay` calls with attacker-chosen `amountToRepay_`.

### Likelihood Explanation
High whenever `debtFloorInUsd > 0` is configured (it is a governor-set protocol parameter intended to prevent dust debt) and `maxLiquidable < 100%` (default 50%). Reaching the bricked state only requires a liquidator to repay `D - F` — a routine, even natural, liquidation amount — so positions will organically end up locked at the floor. The checks that might stop it (`whenNotShutdown`, `nonReentrant`, `PositionIsHealthy` gate) do not, because the trap applies precisely to unhealthy positions.

### Recommendation
When the remaining debt after a partial repay would fall below `debtFloorInUsd`, allow the repay amount to be clamped to the full debt (waive `maxLiquidable` for the final chunk), or treat `_newDebtInUsd < debtFloorInUsd` as a signal to force/require full repayment within `maxLiquidable` exemption rather than reverting unconditionally.

### Proof of Concept
Hardhat fork sketch (deployed `Pool` with `debtFloorInUsd = 100e18`, `maxLiquidable = 0.5e18`):

```ts
// 1. Victim deposits msdMET and mints msETH; price drops -> unhealthy, debt D = 150 USD
await masterOracle.updatePrice(met.address, toUSD('0.5'));

// 2. Liquidator repays D - F = 50 USD worth (<= maxLiquidable), leaving residual = F
await pool.connect(liq).liquidate(msEth.address, victim.address, repay50, msdMET.address);
// debt balance now corresponds to exactly debtFloorInUsd

// 3. Any further liquidation reverts:
//    - full repay (100% > 50% cap) -> AmountGreaterThanMaxLiquidable
//    - any partial repay -> RemainingDebtIsLowerThanTheFloor
await expect(
  pool.connect(liq).liquidate(msEth.address, victim.address, remaining, msdMET.address)
).to.be.revertedWithCustomError(pool, 'AmountGreaterThanMaxLiquidable');
await expect(
  pool.connect(liq).liquidate(msEth.address, victim.address, remaining.div(2), msdMET.address)
).to.be.revertedWithCustomError(pool, 'RemainingDebtIsLowerThanTheFloor');

// 4. Residual bad debt + collateral are permanently locked.
```
