### Title
Integer-underflow bounds bypass in `InputZipFile::EnsureRemaining` allows out-of-bounds read via forged Central Directory offset - (File: `third_party/ijar/zip.cc`)

### Summary
### Finding Description
`InputZipFile::ProcessNext()` reads an attacker-controlled 32/64-bit `offset` field straight from a ZIP Central Directory Header via `ProcessCentralDirEntry()` and uses it, unvalidated against the mapped file's length, to reposition the read cursor:

```
p = zipdata_in_ + in_offset_ + offset;
if (EnsureRemaining(4, "signature") < 0) { ... }
``` [1](#0-0) 

The only bounds check performed afterwards is `EnsureRemaining()`:

```
int EnsureRemaining(size_t n, const char *state) {
  size_t in_offset = p - zipdata_in_;
  size_t remaining = input_file_->Length() - in_offset;
  if (n > remaining) { return error(...); }
  return 0;
}
``` [2](#0-1) 

`in_offset` and `remaining` are `size_t` (unsigned). If the forged central-directory `offset` pushes `p` past `zipdata_in_ + Length()`, then `in_offset > input_file_->Length()`, and `remaining = Length() - in_offset` underflows to a huge unsigned value. The subsequent check `n > remaining` is then always false, so `EnsureRemaining` reports success even though `p` points outside the mapped buffer. Every later read through `p` (`get_u4le`, `get_u2le`, `memcpy` of `file_name_`, etc., in `ProcessLocalFileEntry`) becomes an out-of-bounds read relative to the memory-mapped input file, directly mirroring the libheif `ImageOverlay::parse()` bug where a forged offset field bypassed the intended bounds check and led to OOB read/write.

This is directly analogous to CVE-2024-41311: a length-delimited container format (HEIF overlay vs. ZIP central directory) stores an attacker-controlled offset that is used to reposition a cursor without validating that the target lies within the mapped buffer, and the "bounds check" that exists is defeated by unsigned arithmetic underflow.

### Impact Explanation
This code parses the Central Directory of a `.zip`/`.jar` file wherever `devtools_ijar::ZipExtractor`/`InputZipFile` is used to process a zip file — used by Bazel's `ijar`/`zipper`/`unzip` support tooling that operates on jar/zip files that ultimately originate from external, potentially attacker-served archives (e.g. artifacts fetched by build/packaging rules). Because the file is memory-mapped (`MappedInputFile`), an out-of-bounds `p` dereference reads adjacent process memory beyond the mapped region, which can crash the process (segfault) or leak adjacent heap/mapped memory contents into build outputs (e.g., through `filename` buffer copies or extracted file contents), constituting the C (confidentiality) and I (integrity of parsed metadata) impact described in the CVE. It does not require write access to the file offset field to be within the file — only a well-formed but boundary-forged ZIP.

### Likelihood Explanation
The attacker only needs to supply a crafted ZIP/JAR (a "bytes at a URL"/archive scenario) with a Central Directory Header `offset` (or the ZIP64 extra-field 8-byte offset override, also unchecked) set to a value that, when added to `in_offset_`, points past the end of the mapped file. No credentials, network position, or local access are required beyond serving/publishing the file that gets processed by this parser. The bug is triggered purely by the arithmetic in `EnsureRemaining`, with no reliance on sandbox escape or DoS-only reasoning — it produces a genuine OOB read past the mapped buffer.

### Recommendation
In `EnsureRemaining` (and any place computing `remaining` similarly), first validate that `p` (and `in_offset`) lies within `[zipdata_in_, zipdata_in_ + input_file_->Length()]` before performing the unsigned subtraction, e.g.:
```
if (p < zipdata_in_ || in_offset > input_file_->Length()) {
  return error("offset out of bounds");
}
```
Additionally validate the raw `offset` field read in `ProcessCentralDirEntry` (and its ZIP64 override) against `input_file_->Length()` before it is used to compute `p` in `ProcessNext()`.

### Proof of Concept
A JUnit/`src/test/shell` proof would construct a ZIP file whose Central Directory Header for an entry sets the local-header `offset` field (bytes at CDH offset 42) to a value such that `zipdata_in_ + in_offset_ + offset` exceeds `zipdata_in_ + Length()` (e.g., `offset = Length()`). Feeding this file through the `zipper x`/`ijar` extraction path (`third_party/ijar/zip_main.cc` `extract()` → `InputZipFile::ProcessNext()`) would need to be run under ASan; because `EnsureRemaining`'s unsigned underflow makes the bounds check pass, ASan would report a heap-buffer-overflow/out-of-bounds read when `get_u4le(p)` (line 319) dereferences past the mapped buffer, analogous to the shell test `third_party/ijar/test/zip_test.sh` `test_no_path_traversal` pattern [3](#0-2)  but targeting a forged local-header offset instead of a path-traversal filename.
