### Title
Hard-coded, non-network-parameterized `ADDRESS_REGISTRAR_ACCOUNT_ID` in the ETH Wallet Contract strands caller deposits on any deployment where the registrar account is unset - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The near-wallet-contract (NEP-518 ETH-implicit account contract) hard-codes the account ID of its Address Registrar as a compile-time constant baked once into the WASM and reused across all networks, exactly the pattern flagged in the external report (a single compile-time constant address assumed valid everywhere). Unlike `CHAIN_ID`, which the build script deliberately swaps per network (mainnet/testnet/localnet), `ADDRESS_REGISTRAR_ACCOUNT_ID` is never varied by network in the production build path, so every deployed wallet-contract variant calls the same fixed account for registrar lookups. When that call fails (e.g. because the registrar contract does not exist or is not correctly initialized on the target network/account), the contract's failure-handling path does not refund the caller's attached deposit, unlike the equivalent failure branch elsewhere in the same file.

### Finding Description
`ADDRESS_REGISTRAR_ACCOUNT_ID` is loaded once at compile time from a static file and used directly as the target of a cross-contract call: [1](#0-0) [2](#0-1) 

The production build script, `build.rs`, only substitutes the `CHAIN_ID` file with per-network values (397 for mainnet, 398 for testnet, 399 for localnet) before invoking the dockerized contract build for each of the three output artifacts; it never touches `ADDRESS_REGISTRAR_ACCOUNT_ID`: [3](#0-2) [4](#0-3) 

The registrar account value itself is the static file content `address-map.near`, which is only ever overwritten in the crate's own integration test harness (not in the production build), confirming that in actual mainnet/testnet/localnet artifacts the very same value is compiled in for all three networks: [5](#0-4) 

This is called during `rlp_execute` whenever an Ethereum-emulated base-token transfer targets another eth-implicit account, in order to verify the target hasn't secretly been registered as a named account: [6](#0-5) 

Crucially, the callback that processes the registrar-lookup promise result does NOT refund the caller's attached deposit if the promise fails: [7](#0-6) 

This is inconsistent with the general execution-callback, `rlp_execute_callback`, which explicitly refunds `caller_deposit` when the downstream promise fails: [8](#0-7) 

So if the fixed `ADDRESS_REGISTRAR_ACCOUNT_ID` does not resolve to a functioning registrar contract on the network where the wallet contract is actually deployed (analogous to WETH not existing/being wrong on Arbitrum/Base), every affected `rlp_execute` call with a non-zero attached deposit permanently loses that deposit inside the wallet contract, because the refund logic that exists for the general case is absent in `address_check_callback`.

### Impact Explanation
Any ordinary end-user (owner of an ETH-implicit account) or relayer submitting an `rlp_execute` call that involves an emulated base-token transfer to another eth-implicit account, with a non-zero `attached_deposit` (`caller_deposit`), will have those NEAR funds permanently stranded in the wallet contract if the hard-coded registrar account does not answer as expected on that deployment. This is a concrete permanent freezing-of-funds bug reachable by an ordinary client's transaction, matching the bug class in the external report (hard-coded mainnet-only constant breaking non-mainnet deployments, causing stranded funds).

### Likelihood Explanation
The wallet contract is explicitly built as three separate artifacts for mainnet, testnet, and localnet (`build.rs`), showing multi-network deployment is a first-class, intended use case of this component — not speculative. Because the address registrar constant is never parameterized alongside `CHAIN_ID`, any network whose registrar account differs from `address-map.near` (or where that account has not yet been deployed/initialized) will trigger this failure path deterministically on every affected transaction, making the likelihood of the fund-stranding branch being hit medium-to-high wherever a non-mainnet deployment is used with the address-check flow.

### Recommendation
- Parameterize `ADDRESS_REGISTRAR_ACCOUNT_ID` per network in `build.rs`, the same way `CHAIN_ID` is parameterized, so each of the mainnet/testnet/localnet build variants gets the correct registrar account for that network.
- Add a refund of `caller_deposit` in the `PromiseResult::Failed` branch of `address_check_callback`, mirroring the refund logic already present in `rlp_execute_callback`, so a registrar-lookup failure (for any reason, including misconfiguration) does not result in permanent loss of the caller's deposit.
- At minimum, validate at deploy/init time that the configured registrar account exists and responds correctly before allowing production traffic.

### Proof of Concept
1. Deploy the ETH wallet contract (as built by `build.rs`) to a network where `address-map.near` does not correspond to a live, correctly initialized Address Registrar contract (e.g., a fresh testnet/localnet where that account is unregistered).
2. As a user, submit an `rlp_execute` RLP-encoded Ethereum transaction representing a base-token transfer whose `to` address corresponds to another eth-implicit account, with `attached_deposit` (`caller_deposit`) > 0 accompanying the call — see `parse_rlp_tx_to_action`/`try_emulation` producing `EOABaseTokenTransfer { address_check: Some(address), .. }` at `runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs:107-122`.
3. `inner_rlp_execute` routes this through the registrar lookup path (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:419-431`), calling the hard-coded `ADDRESS_REGISTRAR_ACCOUNT_ID`.
4. Because the account has no valid registrar contract deployed, the cross-contract call fails, and `address_check_callback` returns `PromiseResult::Failed` without refunding `caller_deposit` (`lib.rs:140-148`).
5. The caller's attached NEAR deposit remains locked in the wallet contract with no path to reclaim it, since the failure branch here (unlike `rlp_execute_callback`) contains no refund logic.
