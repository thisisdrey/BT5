### Title
Unauthenticated tunnel teardown via spoofed `header.RecvError` packet - ([File: outside.go])

### Summary
`Interface.handleRecvError` (outside.go:541-575) tears down an active tunnel (`f.closeTunnel(hostinfo)` and `f.handshakeManager.DeleteHostInfo(hostinfo)`) based solely on a UDP source-address comparison, with no cryptographic authentication of the packet. Because UDP source addresses are trivially spoofable and the `RemoteIndex` is the only other input required, an attacker who can spoof the victim's known remote endpoint and who knows/guesses the session's `RemoteIndex` can force a tunnel teardown without possessing any keys or certificates.

### Finding Description
`handleRecvError` looks up the hostinfo by `h.RemoteIndex` via `f.hostMap.QueryReverseIndex` and then performs the only "authentication" check present:

```go
hr := hostinfo.GetRemote()
if hr.IsValid() && hr != addr {
    f.l.Info("Someone spoofing recv_errors?", ...)
    return
}
f.closeTunnel(hostinfo)
f.handshakeManager.DeleteHostInfo(hostinfo)
``` [1](#0-0) 

This check compares the packet's UDP source `netip.AddrPort` against the stored remote endpoint for that hostinfo — it does not verify the packet with any HMAC, nonce, or handshake-derived key. `header.RecvError` packets carry no encrypted/authenticated payload beyond the header itself, and unlike data/handshake packets there is no AEAD or MAC covering this message type in this path [2](#0-1) . Since UDP has no built-in source verification and no return-routability challenge is performed here, an off-path attacker that can spoof the victim's remote peer's `IP:port` can produce a packet that satisfies `hr == addr` and reach `closeTunnel`/`DeleteHostInfo`. The remaining precondition is knowledge of `h.RemoteIndex`, which is a value assigned per-hostinfo and not otherwise validated in this handler.

### Impact Explanation
If exploited, this allows unauthenticated, remote teardown of an active Nebula tunnel purely from a spoofed UDP packet — a denial-of-service against an established session that forces a full re-handshake. This matches the "remote crash/wedge" / "state poisoning" DoS impact category: no keys, certs, or CA control are needed, only the ability to spoof a UDP source address and know the peer's session index.

### Likelihood Explanation
Feasibility hinges on two independent preconditions:
1. **Source spoofing**: forging UDP packets with an arbitrary source `IP:port` is a well-known, network-dependent capability (blocked by egress/BCP38 filtering on many networks, but not universally).
2. **Knowledge of `RemoteIndex`**: this is the harder precondition for a purely off-path/blind attacker, since it is a per-hostinfo value not sent to unauthenticated third parties. If it is generated with a CSPRNG, brute-forcing the full 32-bit space blind is impractical; the attack becomes practical only if the attacker has some visibility into the target's traffic (e.g., prior on-path position, traffic analysis, or leakage of the index through other channels) — I could not fully verify the index-generation source or the default state of `acceptRecvErrorConfig`/`ShouldRecvError` within the available tool budget, so likelihood for a strictly off-path/blind attacker without any additional information is uncertain and likely low; likelihood is significantly higher for an attacker with any path visibility or ability to spoof the exact peer address.

### Recommendation
Do not tear down a session based solely on an unauthenticated `RecvError` packet matching a source address. At minimum:
- Require the `RecvError` message to be authenticated (e.g., include a MAC computed with a key derived from the session, or send it only in response to packets that were themselves successfully decrypted for that index), so that only a party holding the negotiated session keys can trigger teardown.
- Alternatively, treat `RecvError` purely as a hint to trigger a lightweight liveness/re-handshake probe rather than an immediate `closeTunnel` + `DeleteHostInfo`, requiring corroboration (e.g., repeated loss of authenticated traffic) before tearing down state.

### Proof of Concept
Unit test plan for `TestInterface_handleRecvError_spoofed` in `outside_test.go`:
1. Establish a hostinfo in `f.hostMap` with a known `RemoteIndex` and `remote` endpoint `hr`.
2. Call `f.handleRecvError(hr, &header.H{RemoteIndex: hostinfo.localIndexId})` directly (simulating a spoofed packet whose only correct fields are the source address and index, without any handshake/session proof).
3. Assert that `closeTunnel` and `handshakeManager.DeleteHostInfo` are invoked even though no cryptographic material was presented by the caller — demonstrating the teardown is reachable from an unauthenticated input as long as `addr == hr` and `RemoteIndex` is known.
4. Contrast with an expected-secure design: modify the test to require a MAC/session-key check and assert the call is rejected without it.
