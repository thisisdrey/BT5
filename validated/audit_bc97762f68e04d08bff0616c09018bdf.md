### Title
Stale `PromiseYieldReceipt` survives `DeleteAccount`, letting `resolve_promise_yield_timeouts` execute attacker-planted actions (e.g. `AddKey`) against a later-recreated account without its owner's authorization - ([File: core/store/src/utils/mod.rs], [File: runtime/runtime/src/lib.rs])

### Summary
`remove_account` (called by `action_delete_account`) removes `Account`, `ContractCode`, `AccessKey`/gas-key, and `ContractData` trie entries for an account, but never removes the `TrieKey::PromiseYieldReceipt`, `PromiseYieldStatus`, or the queued `TrieKey::PromiseYieldTimeout` entry that reference that `account_id`. `resolve_promise_yield_timeouts` only checks `contains_key(&TrieKey::PromiseYieldReceipt{...})` when the timeout expires - it never verifies the account still is the one that created the yield - so if the account is deleted and a new account with the same `account_id` is created before the timeout height, the stale yield's actions (which the original contract could have appended arbitrary `promise_batch_action_*` calls to, e.g. `AddKey` with `FullAccess`) execute against the new account's state as a self-originated (`predecessor_id == receiver_id == account_id`) receipt, with no signature from the new account's owner.

### Finding Description
The parking mechanism for `promise_yield_create` stores the receipt keyed only by `(receiver_id, data_id)` via `set_promise_yield_receipt` (`core/store/src/utils/mod.rs:200-212`), and enqueues a `PromiseYieldTimeout{ account_id, data_id, expires_at }` entry (`core/store/src/utils/mod.rs:181-198`).

`promise_yield_create` returns a promise index (`new_promise_idx`) referencing the newly created yield receipt [1](#0-0) . Because promise indices are generic, the calling contract can subsequently append arbitrary actions to that same receipt with any `promise_batch_action_*` host call (e.g. `promise_batch_action_add_key_with_full_access`), which resolves the receipt index via `promise_idx_to_receipt_idx_with_sir` and calls `append_action_add_key_with_full_access` [2](#0-1) [3](#0-2) . Nothing in this path restricts which action kinds may be appended to a `PromiseYield`-flagged receipt.

`action_delete_account` calls `remove_account`, which only clears `Account`, `ContractCode`, access/gas keys, and `ContractData`: [4](#0-3) [5](#0-4) 

It performs no check for and no cleanup of `PromiseYieldReceipt`, `PromiseYieldStatus`, or the pending `PromiseYieldTimeout` queue entry referencing this account: [6](#0-5) 

`resolve_promise_yield_timeouts` runs at the end of every chunk's receipt processing and, for each expired timeout entry, only checks the existence of the `PromiseYieldReceipt` key - not whether the account state is "the same" account that created it: [7](#0-6) 

It then synthesizes a `PromiseResume` with `predecessor_id == receiver_id == queue_entry.account_id` and forwards it to the (now recreated) account, where `process_receipt`'s `PromiseResume` arm fetches and executes the still-present stale `PromiseYieldReceipt` via `apply_action_receipt`: [8](#0-7) 

Because the resume/execution path treats the receipt as self-originated (`sir` = signer-is-receiver), any batched action baked into the original yield receipt (e.g. `AddKey` FullAccess, `Transfer`, `DeleteKey`) executes with full authorization against whatever account currently occupies that `account_id`, regardless of who created/owns the new incarnation and without any new signature.

### Impact Explanation
This is an authorization escalation across account lifetimes: an attacker can plant a self-yield receipt on account `A` carrying, e.g., an `AddKey` FullAccess action targeting a public key the attacker controls, then delete `A` (collecting the balance refund via `beneficiary_id`). If `A`'s `account_id` (a sub-account or once-implicit account) is later recreated by any party before the yield's `expires_at` block height, the dangling timeout will fire and silently grant the attacker a full-access key on the new account - or otherwise execute an unauthorized action - without any signature or consent from the new account's controller. This maps to the "authorization escalation across accounts or promises" bounty category and can lead directly to theft of funds/control of the recreated account.

### Likelihood Explanation
Preconditions are fully within reach of an ordinary, unprivileged client: fund an account, deploy an attacker-controlled contract, call `promise_yield_create` and append a batch action to the returned promise index, then submit a `DeleteAccount` action, all before `yield_timeout_length_in_blocks` elapses. The only external dependency is that the `account_id` gets reused (recreated) before the timeout height - feasible for implicit accounts (any funder can "create" them via a transfer) and for sub-accounts (any account with permission over the parent can recreate). This makes the attack fully deterministic and repeatable once the account_id happens to be reused within the timeout window, requiring no validator/node privileges.

### Recommendation
When removing an account (`remove_account` in `core/store/src/utils/mod.rs`), also enumerate and delete any `PromiseYieldReceipt`/`PromiseYieldStatus`/`YieldIdToDataId`/`DataIdToYieldId` entries keyed by that `account_id`, and either cancel the corresponding `PromiseYieldTimeout` queue entries at delete time or have `resolve_promise_yield_timeouts` verify (e.g., via an account-generation/version stamp recorded at yield-creation time and compared against the current account) that the account instance resolving the timeout is the same instance that created the yield before executing its actions.

### Proof of Concept
Test-loop integration test:
1. Deploy an attacker-controlled contract on account `A` (funded by attacker).
2. Call a method that: invokes `promise_yield_create` (any callback), then appends `promise_batch_action_add_key_with_full_access(promise_idx, attacker_pubkey, nonce)` to the same promise index.
3. Submit a `DeleteAccount(A, beneficiary_id=attacker)` action; confirm `A`'s `Account`/`AccessKey` entries are gone from state but `TrieKey::PromiseYieldReceipt{A, data_id}` (verified via a state-viewer/test helper reading the raw trie key) still exists.
4. Submit a `CreateAccount(A)` action (e.g. via a fresh funder/new owner adding their own new key) before `yield_timeout_length_in_blocks` blocks have passed.
5. Advance blocks past the timeout height (`yield_create_height + yield_timeout_length_in_blocks`).
6. Assert: `A`'s access key list now contains the attacker's planted `FullAccess` public key, even though the new owner never signed a transaction authorizing it - proving the stale yield resume executed unauthorized actions on the recreated account.

pub(crate) fn action_delete_account(
    state_update: &mut TrieUpdate,
    account: &mut Option<Account>,
    actor_id: &mut AccountId,
    receipt: &Receipt,
    result: &mut ActionResult,
    account_id: &AccountId,
    delete_account: &DeleteAccountAction,
    config: &RuntimeConfig,
    current_protocol_version: ProtocolVersion,
) -> Result<(), StorageError> {
    let account_ref = account.as_ref().unwrap();
    let account_storage_usage = if ProtocolFeature::FixDeleteAccountGlobalContractStorageUsage
        .enabled(current_protocol_version)
    {
        let contract_storage = get_contract_storage_usage(state_update, account_id, account_ref)?;
        account_ref.storage_usage().saturating_sub(contract_storage)
    } else {
        // Legacy behavior: only subtracts local contract code, misses the
        // global contract identifier overhead.
        let account_storage_usage = account_ref.storage_usage();
        let code_len = get_code_len_or_default(
            state_update,
            account_id.clone(),
            account_ref.local_contract_hash().unwrap_or_default(),
        )?;
        debug_assert!(
            code_len == 0 || account_storage_usage > code_len,
            "account storage usage should be larger than code size. storage usage: {}, code size: {}",
            account_storage_usage,
            code_len
        );
        account_storage_usage.saturating_sub(code_len)
    };
    if account_storage_usage > Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE {
        result.result =
            Err(ActionErrorKind::DeleteAccountWithLargeState { account_id: account_id.clone() }
                .into());
        return Ok(());
    }
    let gas_key_balance_to_burn = compute_gas_key_balance_sum(state_update, account_id)?;
    if gas_key_balance_to_burn > GasKeyInfo::MAX_BALANCE_TO_BURN {
        result.result = Err(ActionErrorKind::GasKeyBalanceTooHigh {
            account_id: account_id.clone(),
            public_key: None,
            balance: gas_key_balance_to_burn,
        }
        .into());
        return Ok(());
    }
    // We use current amount as a pay out to beneficiary.
    let account_balance = account_ref.amount();
    if account_balance > Balance::ZERO {
        result
            .new_receipts
            .push(Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance));
    }
    let remove_result = remove_account(state_update, account_id)?;
    result.tokens_burnt =
        result.tokens_burnt.checked_add(gas_key_balance_to_burn).ok_or_else(|| {
            StorageError::StorageInconsistentState("tokens_burnt overflow".to_string())
        })?;
    if remove_result.gas_key_nonce_count > 0 {
        let compute = storage_removes_compute(
            &config.wasm_config.ext_costs,
            remove_result.gas_key_nonce_count,
            remove_result.gas_key_nonce_total_key_bytes,
            AccessKey::NONCE_VALUE_LEN * remove_result.gas_key_nonce_count,
        );
        result.compute_usage = safe_add_compute(result.compute_usage, compute).map_err(|_| {
            StorageError::StorageInconsistentState("compute_usage overflow".to_string())
        })?;
    }
    *actor_id = receipt.predecessor_id().clone();
    *account = None;
    Ok(())
}
