### Title

`SmartFarmingManager.leverage()` and `flashRepay()` execute stale swaps without a transaction deadline - (`contracts/SmartFarmingManager.sol`)

### Summary

Both public swap-assisted position-management flows expose slippage bounds but no deadline, and the underlying `ISwapper.swapExactInput()` interface has no expiry parameter. [1](#0-0) [2](#0-1) [3](#0-2) 

A transaction pending in the mempool can therefore be included after market conditions have changed, while still satisfying a stale minimum-output bound and the final health check.

### Finding Description

`flashRepay()` withdraws collateral and swaps the entire withdrawn amount through the configured swapper, passing `amountOutMin_ = 0` into the swapper and only afterward comparing the received amount against `swapAmountOutMin_`. [4](#0-3) 

Similarly, `leverage()` accepts `depositAmountMin_` but passes `0` to the swapper for the optional `tokenIn_` to collateral swap and again for the synthetic-token to collateral swap. [5](#0-4) [6](#0-5) 

The internal `_swap()` helper approves the current swapper, invokes `swapExactInput()`, and measures the recipient’s balance delta, but neither the helper nor the swapper interface supplies or validates a deadline. [7](#0-6) [3](#0-2) 

The deployed mainnet manager exposes the same public `leverage(address,address,address,uint256,uint256,uint256)` and `flashRepay(address,address,uint256,uint256)` signatures, with no timestamp or expiry argument. [8](#0-7) 

### Impact Explanation

The invariant affected is the intended bound on the economic outcome of a user-initiated swap.

A user may construct a transaction using prices and a slippage bound that are reasonable at submission time; if the transaction remains pending, another trader can move the relevant pool price or normal market activity can make that bound stale.

When the old transaction is eventually included:

- `flashRepay()` may sell withdrawn collateral at a materially worse price while still satisfying the stale `swapAmountOutMin_`.
- `leverage()` may convert `tokenIn_` and newly minted synthetic tokens at worse prices while still satisfying the stale `depositAmountMin_`.
- The final `debtPositionOf()` health check only prevents an unhealthy resulting position; it does not restore the lost swap value or guarantee execution near the submission-time market price. [9](#0-8) [10](#0-9) 

The result is a direct loss of user value to liquidity providers or traders on the adverse side of the delayed swap.

### Likelihood Explanation

Exploitation requires a transaction to remain pending long enough for market conditions to move and for its stale slippage bound to remain permissive.

No privileged Metronome role is needed to create the adverse price movement; an unprivileged account can trade in the external venue used by the configured swapper before the victim transaction is included.

The existing checks do not prevent stale inclusion because `onlyIfDepositTokenExists`, `onlyIfSyntheticTokenExists`, `whenNotShutdown`, `nonReentrant`, the swap-output checks, and the final health check contain no timestamp comparison. [11](#0-10) [1](#0-0) [2](#0-1) 

### Recommendation

Add a caller-controlled `deadline` argument to `leverage()` and `flashRepay()` and validate it before withdrawing, transferring, minting, or swapping:

```solidity
if (block.timestamp > deadline) revert TransactionExpired();
```

Update `ISmartFarmingManager` accordingly. [12](#0-11) 

For `leverage()`, use the same deadline for both the optional input-token swap and the synthetic-token swap so only one leg cannot remain executable after expiration. [13](#0-12) 

If the production swapper supports its own router deadline, propagate the caller’s deadline through `ISwapper`; otherwise, validating it in `SmartFarmingManager` before each external swap is still necessary. [3](#0-2) 

### Proof of Concept

A Foundry mainnet-fork test can reproduce the timing flaw against the deployed manager at `0xCfC7Ed8003B2E21098fdCE4C125bbf4084b0BdFF`. [14](#0-13) 

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {IERC20} from "contracts/dependencies/openzeppelin/token/ERC20/IERC20.sol";
import {ISmartFarmingManager} from "contracts/interfaces/ISmartFarmingManager.sol";
import {ISyntheticToken} from "contracts/interfaces/ISyntheticToken.sol";
import {IDepositToken} from "contracts/interfaces/IDepositToken.sol";

contract MissingDeadlineForkTest is Test {
    ISmartFarmingManager constant SFM =
        ISmartFarmingManager(0xCfC7Ed8003B2E21098fdCE4C125bbf4084b0BdFF);

    address user = makeAddr("user");
    address attacker = makeAddr("attacker");

    function test_leverageExecutesAfterStaleInclusionTime() public {
        vm.createSelectFork(vm.envString("MAINNET_RPC_URL"));

        // Configure these from a live mainnet pool and from `SFM.swapper()`'s venue.
        IERC20 tokenIn = IERC20(LIVE_TOKEN_IN);
        IDepositToken depositToken = IDepositToken(LIVE_DEPOSIT_TOKEN);
        ISyntheticToken syntheticToken = ISyntheticToken(LIVE_SYNTHETIC_TOKEN);
        uint256 amountIn = LIVE_AMOUNT_IN;
        uint256 leverage = LIVE_LEVERAGE;

        deal(address(tokenIn), user, amountIn);

        // Bound chosen from the market price at transaction-submission time.
        uint256 quotedDeposit = quoteLiveDeposit(
            depositToken,
            syntheticToken,
            amountIn,
            leverage
        );
        uint256 staleMin = quotedDeposit * 99 / 100;

        bytes memory delayedCall = abi.encodeCall(
            ISmartFarmingManager.leverage,
            (
                tokenIn,
                depositToken,
                syntheticToken,
                amountIn,
                leverage,
                staleMin
            )
        );

        // The user's transaction remains pending.
        vm.warp(block.timestamp + 1 days);

        // An unprivileged account moves the external venue used by the swapper.
        moveLiveVenuePrice(attacker, syntheticToken, depositToken);

        // Inclusion still succeeds because neither the API nor swap call has an expiry.
        vm.startPrank(user);
        tokenIn.approve(address(SFM), amountIn);
        (bool success, bytes memory result) = address(SFM).call(delayedCall);
        vm.stopPrank();

        assertTrue(success);
        (uint256 deposited,) = abi.decode(result, (uint256, uint256));
        assertGe(deposited, staleMin);
        assertLt(deposited, quotedDeposit);
    }

    function quoteLiveDeposit(
        IDepositToken depositToken,
        ISyntheticToken syntheticToken,
        uint256 amountIn,
        uint256 leverage
    ) internal returns (uint256) {
        // Quote the exact route used by `SFM.swapper()`.
    }

    function moveLiveVenuePrice(
        address trader,
        ISyntheticToken syntheticToken,
        IDepositToken depositToken
    ) internal {
        // Execute a real AMM trade through the live venue used by `SFM.swapper()`.
    }
}
```

The decisive assertion is that the delayed call succeeds after `vm.warp()` even though an expiry supplied at submission time should make it revert; the lower `deposited` result demonstrates that the stale minimum does not preserve the original market outcome. [15](#0-14)
