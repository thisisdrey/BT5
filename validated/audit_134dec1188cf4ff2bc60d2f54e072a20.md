Confirmed mechanism: `TokenDiff::execute_intent` computes fee per-intent via `Self::token_fee(token_id, amount, protocol_fee).fee_ceil(amount)` where `amount = delta.unsigned_abs()` is scoped only to that single `TokenDiff`'s delta on that token [1](#0-0) . `token_fee` explicitly zeroes the fee for `Nep245`/`Imt` token types whenever the per-intent `amount <= 1` [2](#0-1) . There is no cross-intent or cross-batch accumulator that tracks cumulative delta magnitude per `TokenId`/signer across a `MultiPayload`; each `TokenDiff` is fee-assessed independently based solely on its own `amount`.

The overall batch invariant enforced elsewhere is only that the sum of all deltas across all intents nets to zero per token via `TransferMatcher::finalize` [3](#0-2)  — this only checks conservation of value between senders/receivers, it does not re-derive or re-check fees. Fees are computed once at intent-execution time and added to `fees_collected`, independent of how many other `TokenDiff` intents move the same token in the same batch [4](#0-3) .

Thus an attacker (or two colluding signers providing the matching counter-leg) can split what would economically be a single N-unit NEP-245/IMT `TokenDiff` (delta = -N, fee = `protocol_fee.fee_ceil(N)`) into N separate `TokenDiff` intents each with delta = -1 on the same `TokenId`, each independently hitting the `amount <= 1` branch and paying `Pips::ZERO` fee, for a total collected fee of 0 instead of `fee_ceil(N)`. This matches the Critical impact category "protocol fees bypassed."

### Title
Fee-exempt `amount <= 1` branch in `TokenDiff::token_fee` lets NEP-245/IMT fees be bypassed via 1-unit intent splitting - (File: contracts/defuse/core/src/intents/token_diff.rs)

### Summary
`TokenDiff::token_fee` waives fees for `TokenIdType::Nep245`/`TokenIdType::Imt` whenever the delta magnitude of a single intent is `<= 1`, and the fee is computed strictly per-`TokenDiff`-intent with no batch- or history-level accumulation. An unprivileged attacker can therefore execute a large fungible-style NEP-245 transfer as N separate 1-unit `TokenDiff` intents in one `MultiPayload`, paying zero protocol fee instead of `protocol_fee.fee_ceil(N)`.

### Finding Description
The broken binding: `sum(fees_collected[fee_collector]) over a batch == protocol_fee.fee_ceil(sum(|negative deltas| on token T))`. In `TokenDiff::execute_intent`, for each `(token_id, delta)` pair, `amount = delta.unsigned_abs()` and `fee = Self::token_fee(token_id, amount, protocol_fee).fee_ceil(amount)` [4](#0-3) . `token_fee` returns `Pips::ZERO` for `Nep245`/`Imt` when `amount <= 1` [2](#0-1) . Because `amount` is scoped to a single intent's delta rather than the cumulative transfer across a batch/session, an attacker structures the trade as N intents each with `delta = -1` on the same `TokenId`, each independently landing in the zero-fee branch, versus one `delta = -N` intent that would use `token_fee(..., N, ...) = protocol_fee` and pay `protocol_fee.fee_ceil(N)`. The `TransferMatcher::finalize` invariant only enforces that deltas sum to zero across senders/receivers [3](#0-2) ; it does not recompute or reconcile fees, so this guard does not catch the divergence. No nonce, signature, or lock check restricts how many separate `TokenDiff` intents a signer can bundle in one `execute_intents` call, and each is independently valid.

### Impact Explanation
The fee collector (`engine.state.fee_collector()`) receives strictly less than the protocol-mandated fee on NEP-245/IMT token trades whenever the attacker structures the trade in 1-unit legs — for large-enough N, the collected fee can be driven to zero regardless of the configured `protocol_fee`. This is a direct, repeatable under-collection of protocol fees affecting every NEP-245/IMT token and every trade size, matching the Critical category "protocol fees bypassed." The attacker's gain equals the fee they would otherwise have paid, so this is not mere griefing but concrete attacker profit (fee savings) at the fee collector's expense.

### Likelihood Explanation
No special privileges are required: any account holding NEP-245/IMT balance can submit a `MultiPayload` with N `TokenDiff` intents (self-signed or matched with a colluding counterparty) instead of one, incurring only ordinary transaction/gas cost, which is out of scope to weigh against. This is trivially repeatable for any amount and any NEP-245/IMT token, so likelihood is high; the only constraint is that the token type must be `Nep245`/`Imt` (not `Nep141`, which is unaffected since its branch has no `amount` gate).

### Recommendation
Track cumulative per-token, per-signer transfer volume across the whole intents batch (or session) before applying the `amount <= 1` fee exemption, or remove/restrict the exemption so it only applies to genuinely non-fungible NEP-245 tokens (e.g., based on token metadata/supply rather than the per-intent delta magnitude), preventing the exemption from being satisfied by splitting a fungible-style transfer into unit-sized legs.

### Proof of Concept
`cargo test` in `contracts/defuse/core` (or a `near-workspaces` sandbox test) comparing fee collector balances:
1. Set up a `Nep245TokenId` representing a fungible-style MT unit and a non-zero `protocol_fee` (e.g. `Pips::ONE_PERCENT`).
2. Execute a single `TokenDiff` intent with `delta = -N` (N > 1) on that token for signer A, paired with an offsetting `+N` delta elsewhere to balance `TransferMatcher`; assert `fees_collected` for the fee collector equals `protocol_fee.fee_ceil(N)`.
3. Execute N separate `TokenDiff` intents, each with `delta = -1` on the same token (same signer or batch), each paired with a matching `+1` counter-leg; sum `fees_collected` across all N intents.
4. Assert `sum(fees_collected_split) < fees_collected_single`, demonstrating the binding `sum(fees_collected) == protocol_fee.fee_ceil(total)` fails for the split case (specifically `sum(fees_collected_split) == 0` when `protocol_fee.fee_ceil(1) == 0`, i.e., fee rate low enough that 1-unit fee_ceil rounds to zero — otherwise even without the `amount<=1` branch fee_ceil(1) could be nonzero, so the exploit is strongest when `protocol_fee` is small enough that `fee_ceil(1)` alone would round to 0 anyway, or specifically leverages the explicit `amount<=1` bypass regardless of fee rate for Nep245/Imt).

        let mut deltas = TokenDeltas::default();

            }

                unmatched_deltas: deltas,
            });
