### Title
Relay manager trusts attacker-supplied `RelayFromAddr` instead of the authenticated peer's certificate-bound address, enabling relay-state poisoning - ([File: relay_manager.go])

### Summary
`handleCreateRelayRequest` in `relay_manager.go` derives the relay's claimed source identity (`from`) directly from an attacker-controlled field in the `NebulaControl` message body, rather than from the certificate-verified `vpnAddrs` of the authenticated `HostInfo` (`h`) that actually sent the message. This is the same bug class as the `OmoRouter.redeem()` finding: an operation that should be scoped to the authenticated caller's own identity instead accepts an arbitrary, caller-supplied identity parameter and uses it to register privileged state on behalf of that (unverified) identity.

### Finding Description
`AddRelay`/`handleCreateRelayRequest` handle `NebulaControl_CreateRelayRequest` messages that arrive over an already-authenticated, cert-verified tunnel identified by `h *HostInfo`. `h.vpnAddrs` is populated only from the peer's Nebula certificate during the handshake, so `h` is a trustworthy, cryptographically bound identity [1](#0-0) .

However, in `handleCreateRelayRequest`, the "source" of the relay (`from`) is taken straight from the message payload the peer supplied, with no check that it matches `h.vpnAddrs`:

```go
from := protoAddrToNetAddr(m.RelayFromAddr)
target := protoAddrToNetAddr(m.RelayToAddr)
...
if f.myVpnAddrsTable.Contains(target) {
    ...
    _, err := AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)
``` [2](#0-1) 

The only identity check performed is that `from` is not one of *my own* addresses [3](#0-2) ; there is no check that `from` equals one of the authenticated peer's own certificate-bound addresses (`h.vpnAddrs`). `AddRelay` then installs `from` as the `PeerAddr` of a `Relay` entry keyed by `h`'s `relayState`, marking it `Established`/`TerminalType` [4](#0-3) . This mirrors the `OmoRouter.redeem(owner)` flaw: the operation should be scoped to `msg.sender`/the authenticated `h`, but instead accepts and trusts a caller-supplied identity (`RelayFromAddr`) for a state-mutating, trust-establishing action.

### Impact Explanation
Because `from` is unauthenticated and attacker-chosen, any peer that can complete a normal handshake (i.e., any valid cert holder acting maliciously, or more importantly any packet delivered over that authenticated channel) can register itself as the relay path for an arbitrary victim VPN address it does not own. This poisons the receiving node's relay routing table (`h.relayState.relayForByAddr`), which is later consulted by the data plane (`f.hostMap.QueryVpnAddrsRelayFor`, `SendVia`) to decide where to forward traffic destined for that address [5](#0-4) [6](#0-5) . This can redirect traffic intended for a legitimate host through the attacking peer, enabling remote state poisoning of the relay hostmap and traffic-forwarding hijack — the "no-CA analog" of the finance report's fund-redirection impact.

### Likelihood Explanation
Likelihood is Medium: the attacker must be a party that can send a `Control`/`CreateRelayRequest` message to a node acting as a relay terminal (i.e., have some established or in-progress handshake path to that node), but no CA-signed certificate forgery, no MITM, and no additional privilege is required — just crafting the `RelayFromAddr` field of an otherwise-legitimate control message.

### Recommendation
In `handleCreateRelayRequest`, validate that `from` (`m.RelayFromAddr`) is actually one of the authenticated peer's own certificate-bound addresses before calling `AddRelay`:
```go
from := protoAddrToNetAddr(m.RelayFromAddr)
if !slices.Contains(h.vpnAddrs, from) {
    logMsg.Error("RelayFromAddr does not match authenticated peer identity")
    return
}
```
This mirrors the recommended fix of restricting the trusted identity to the value derived from the authenticated channel (`h`/`msg.sender`) rather than trusting a caller-supplied parameter.

### Proof of Concept
1. Peer `H` establishes a normal, cert-verified tunnel to terminal node `T` (`T.myVpnAddrsTable` contains `T`'s own address).
2. `H` sends a `NebulaControl_CreateRelayRequest` to `T` with `RelayFromAddr` = `Victim`'s VPN address (not `H`'s own) and `RelayToAddr` = `T`'s address.
3. `T.handleCreateRelayRequest` sees `target == me`, computes `from = Victim`, and since `f.myVpnAddrsTable.Contains(from)` is false (it's the victim's address, not `T`'s), proceeds to call `AddRelay(rm.l, h, f.hostMap, from=Victim, ...)`, registering `H` as an `Established`/`TerminalType` relay for `Victim` in `H`'s `relayState` — despite `H` never proving it controls `Victim`'s certificate/address.
4. Subsequent lookups/forwarding logic that consult this relay state for `Victim`'s address (`QueryVpnAddrsRelayFor`) can now be steered through `H`, hijacking traffic that should have gone directly to or through the real `Victim` path [7](#0-6) .

			return 0, err

				return 0, errors.New("relay hostinfo is no longer in the hostmap")

			}

				newRelay.RemoteIndex = *remoteIdx
			}
			relayHostInfo.relayState.InsertRelay(vpnIp, index, &newRelay)

			return index, nil
		}

func (rm *relayManager) handleCreateRelayRequest(v cert.Version, h *HostInfo, f *Interface, m *NebulaControl) {
	//nil-checks for protoAddrToNetAddr handled by caller
	from := protoAddrToNetAddr(m.RelayFromAddr)
	target := protoAddrToNetAddr(m.RelayToAddr)

	logMsg := rm.l.With(
		"relayFrom", from,
		"relayTo", target,
		"initiatorRelayIndex", m.InitiatorRelayIndex,
		"vpnAddrs", h.vpnAddrs,
	)

	logMsg.Info("handleCreateRelayRequest")
	// Is the source of the relay me? This should never happen, but did happen due to
	// an issue migrating relays over to newly re-handshaked host info objects.
	if f.myVpnAddrsTable.Contains(from) {
		logMsg.Error("Discarding relay request from myself", "myIP", from)
		return
	}

	// Is the target of the relay me?
	if f.myVpnAddrsTable.Contains(target) {
		existingRelay, ok := h.relayState.QueryRelayForByIp(from)
		if ok {
			switch existingRelay.State {
			case Requested:
				ok = h.relayState.CompleteRelayByIP(from, m.InitiatorRelayIndex)
				if !ok {
					logMsg.Error("Relay State not found")
					return
				}
			case Established:
				if existingRelay.RemoteIndex != m.InitiatorRelayIndex {
					// We got a brand new Relay request, because its index is different than what we saw before.
					// This should never happen. The peer should never change an index, once created.
					logMsg.Error("Existing relay mismatch with CreateRelayRequest",
						"existingRemoteIndex", existingRelay.RemoteIndex)
					return
				}
			case Disestablished:
				if existingRelay.RemoteIndex != m.InitiatorRelayIndex {
					// We got a brand new Relay request, because its index is different than what we saw before.
					// This should never happen. The peer should never change an index, once created.
					logMsg.Error("Existing relay mismatch with CreateRelayRequest",
						"existingRemoteIndex", existingRelay.RemoteIndex)
					return
				}
				// Mark the relay as 'Established' because it's safe to use again
				h.relayState.UpdateRelayForByIpState(from, Established)
			case PeerRequested:
				// I should never be in this state, because I am terminal, not forwarding.
				logMsg.Error("Unexpected Relay State found",
					"existingRemoteIndex", existingRelay.RemoteIndex,
					"state", existingRelay.State)
			}
		} else {
			_, err := AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)
			if err != nil {
				logMsg.Error("Failed to add relay", "error", err)
				return
			}
		}
