Confirmed: the exact analog exists in nearcore's meta-transaction (NEP-366) balance-refund logic, and is even explicitly documented and self-acknowledged as a fund-diversion risk to relayers.

### Title
Meta-transaction deposit refunds go to `DelegateAction.sender_id` instead of the relayer who actually funded the deposit, enabling theft of relayer funds - (File: `runtime/runtime/src/config.rs`)

### Summary
When a relayer submits a meta-transaction (`DelegateAction`) on behalf of a sender, the relayer prepays all attached deposits for the inner actions. If an inner action fails on the receiver's shard, the protocol refunds the deposit to the `predecessor_id` of the failed receipt, which is set to the delegate's `sender_id` (the party who merely signed the `DelegateAction`) — not to the relayer who actually supplied the funds. This is structurally identical to the ZetaChain bug: the refund beneficiary is attributed to the transaction's nominal originator/signer rather than the true funding party (an "intermediary"), allowing that originator to steal funds by causing predictable failure.

### Finding Description
`total_deposit()` explicitly documents this behavior: [1](#0-0) 

`apply_delegate_action` constructs the new receipt with `predecessor_id: sender_id.clone()` (the delegate action's `sender_id`, i.e., Alice), while noting the relayer paid for everything: [2](#0-1) 

Deposit refunds are always sent to the `predecessor_id` of the failed receipt (unless `refund_to` is explicitly set by the receipt creator, which is not possible for a raw `DelegateAction`'s inner actions since they are placed directly as the receipt body, not generated by a contract call): [3](#0-2) [4](#0-3) 

The protocol architecture documentation confirms this is a live, acknowledged issue, and frames it exactly as the ZetaChain report frames its bug (wrong refund beneficiary → financial incentive to induce failure and capture funds): [5](#0-4) 

The `refund_to` / `promise_set_refund_to` mechanism (`ActionReceiptV2`, `receipt_manager.rs`) is a mitigation added for contract-generated promises, but it cannot be applied to the top-level actions embedded directly inside a `DelegateAction`, since those become the receipt body verbatim via `apply_delegate_action` without going through a contract's promise API: [6](#0-5) [7](#0-6) 

### Impact Explanation
This allows an ordinary account (the delegate `sender_id`) to steal funds from a relayer: the sender signs a `DelegateAction` whose inner action(s) attach a balance and are engineered to fail on the receiver's shard (e.g., targeting a nonexistent method, insufficient storage balance on receiver, or any other deterministic failure). The relayer's prepaid deposit is refunded not to the relayer but to the delegate sender, resulting in concrete theft of the relayer's funds with no service rendered. This directly matches the ERC-20 deposit bug class: the refund beneficiary is bound to the "signer"/originator identity rather than the true funder ("intermediary" analog = relayer), letting the originator drain funds intended to flow back to the funder.

### Likelihood Explanation
Reachable entirely through the standard, unprivileged meta-transaction flow (`Action::Delegate`/`DelegateV2`) available to any account; no special privileges, validator/node access, or race conditions are required. The only precondition is a relayer that funds deposits for inner actions on behalf of users without independently validating that the inner action cannot fail — a normal relayer operating model. The nearcore documentation itself states this is a known trap for relayer implementations, indicating the path is realistic and already anticipated as exploitable in production relayer designs.

### Recommendation
For inner actions of `DelegateAction`/`DelegateActionV2`, set the refund destination of any produced deposit-refund receipt to the outer transaction's signer (the relayer) rather than the delegate's `sender_id`, e.g., by having `apply_delegate_action` populate `refund_to` on the generated `ActionReceiptV2` with the relayer's account id, mirroring how gas refunds already correctly go to the relayer (`action_receipt.signer_id()`). Alternatively, require relayers to be able to specify a `refund_to` at the `DelegateAction` level that the protocol honors when generating deposit refunds for the inner actions.

### Proof of Concept
1. Relayer `R` receives a `SignedDelegateAction` from account `Alice`, wrapping an inner `FunctionCall` action to `Bob` with `deposit = D` (e.g., attached to a method that Alice knows does not exist on `Bob`, or with any other reliably-failing precondition).
2. `R` wraps it in a transaction and submits it, paying `total_cost` (including `D`) from its own balance, per `tx_cost`/`total_deposit`: [8](#0-7) 
3. On Alice's shard, `apply_delegate_action` forwards the inner action(s) as a new receipt with `predecessor_id = Alice`, `receiver_id = Bob`: [9](#0-8) 
4. The inner `FunctionCall` fails on `Bob`'s shard (e.g., `MethodNotFound`).
5. `refund_unspent_gas_and_deposits` issues a `Receipt::new_balance_refund` to `receipt.balance_refund_receiver()`, which (absent an explicit `refund_to`) resolves to `predecessor_id = Alice`: [10](#0-9) [4](#0-3) 
6. Alice's balance increases by `D`, funded entirely by `R`; `R` receives nothing back. This exactly matches nearcore's own documented risk statement: [11](#0-10)

/// Get the total sum of deposits for given actions.
pub fn total_deposit(actions: &[Action]) -> Result<Balance, IntegerOverflowError> {
    let mut total_balance = Balance::ZERO;
    for action in actions {
        let action_balance;
        if let Some(delegate_action) = delegate_inner_action(action) {
            // Note, here Relayer pays the deposit but if actions fail, the deposit is
            // refunded to Sender of DelegateAction
            let actions = delegate_action.get_actions();
            action_balance = total_deposit(&actions)?;
        } else {
            action_balance = action.get_deposit_balance();
        }

        total_balance = safe_add_balance(total_balance, action_balance)?;
    }
    Ok(total_balance)
}

```markdown
## Balance refunds in meta transactions

Unlike gas refunds, the protocol sends balance refunds to the predecessor
(a.k.a. sender) of the receipt. This makes sense, as we deposit the attached
balance to the receiver, who has to explicitly reattach a new balance to new
receipts they might spawn.

In the world of meta transactions, this assumption is also challenged. If an
inner action requires an attached balance (for example a transfer action) then
this balance is taken from the relayer.

The relayer can see what the cost will be before submitting the meta transaction
and agrees to pay for it, so nothing wrong so far. But what if the transaction
fails execution on Bob's shard? At this point, the predecessor is `Alice` and
therefore she receives the token balance refunded, not the relayer. This is
something relayer implementations must be aware of since there is a financial
incentive for Alice to submit meta transactions that have high balances attached
but will fail on Bob's shard.
```
