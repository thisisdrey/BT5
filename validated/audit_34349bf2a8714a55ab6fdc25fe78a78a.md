## Title
Heap Out-of-Bounds Read in `IsMultiRelease()` via Unterminated JAR Manifest Buffer - (File: `third_party/ijar/ijar.cc`)

### Summary
`ijar`, the tool Bazel uses to build interface jars for every `java_library`/`java_import` dependency, extracts the `META-INF/MANIFEST.MF` entry from an input jar into a heap buffer that is **not null-terminated**, then scans it with `strchr()`, which relies on finding a `'\0'` (or the sought byte) to stop. If the manifest bytes near the end of the buffer do not contain a `'\n'` before the allocation boundary, `strchr` reads past the end of the heap allocation into adjacent memory, exactly mirroring the GSSAPI advisory's root cause ("GSSAPI buffers are not guaranteed to be null-terminated... this results in reading... past the allocated heap buffer").

### Finding Description
`ManifestLocator::Process` copies the raw manifest bytes of a jar entry into a heap buffer with no extra terminator byte: [1](#0-0) 

That buffer and its exact `size` are later passed into `IsMultiRelease()`: [2](#0-1) 

`IsMultiRelease()` scans lines using `strchr(line_start, '\n')`, which is a C standard library call that reads until it finds `'\n'` **or** a `'\0'` byte — it has no awareness of `data_end`: [3](#0-2) 

Because `manifest_buf_` is an exact `malloc(size)` allocation with no null terminator appended, if the tail of the manifest (as extracted from the attacker-supplied jar) does not end in `'\n'` and no `'\n'` byte happens to occur in memory immediately following the allocation, `strchr` continues reading past the allocated buffer boundary — a heap out-of-bounds read, invariant-for-invariant the same class of bug as the GSSAPI advisory (code assumes a buffer is terminated by a particular byte, but the buffer's origin — an untrusted external source — gives no such guarantee).

### Impact Explanation
This is reached whenever Bazel invokes `ijar` to strip a jar for compilation — a routine, unavoidable action for any `java_library`/`java_import` target that depends on an externally fetched `.jar` (e.g. via `http_jar`, `maven_install`/`rules_jvm_external`, or a jar checked into an untrusted branch). The jar's author (an unprivileged, external party) fully controls the bytes of `META-INF/MANIFEST.MF`, including its exact trailing bytes and length, and therefore controls whether the `strchr` scan runs off the end of the heap allocation. The primary consequence is process memory-safety violation (crash or, depending on heap layout, potential information disclosure of adjacent heap contents into control flow, since the OOB bytes influence whether `line_length`/`strncmp` treat the following bytes as matching `"Multi-Release: true"`).

### Likelihood Explanation
Any jar with a manifest lacking a final `'\n'` (or a manifest crafted to place the last "line" flush against the allocation boundary) triggers this on ordinary interface-jar generation — no special build configuration or opt-in flag is needed since `ijar` unconditionally locates and parses `META-INF/MANIFEST.MF` for every jar it processes. A hostile-but-otherwise-valid jar published by any external dependency author (with or without a matching pinned sha256 — the hash is computed over exactly this malicious content, so pinning does not prevent it) is sufficient.

### Recommendation
Bound the `strchr` scan to `data_end`: implement a length-limited search (e.g. `memchr(line_start, '\n', data_end - line_start)` instead of `strchr`) so the scan never reads past `manifest_size` bytes, matching the same fix pattern used to remediate the GSSAPI advisory (stop relying on implicit termination; always pass and respect explicit buffer lengths).

### Proof of Concept
A `BuildIntegrationTestCase`/`src/test/shell/bazel` style reproduction:
1. Build a `.jar` whose `META-INF/MANIFEST.MF` entry ends with no trailing `'\n'` and is placed as the very last bytes of the manifest's `ZipExtractorProcessor::Process` payload (i.e., the entry's stored size ends exactly at a byte that isn't `'\n'`).
2. Reference this jar from a `java_import`/`java_library` and build it with Bazel so `ijar` runs `JarStripperProcessor::WriteManifest` → `IsMultiRelease`.
3. Run under AddressSanitizer (`ASAN_OPTIONS`) or a heap-guard build of `ijar`; observe a heap-buffer-overflow read reported inside `IsMultiRelease`'s `strchr` call in `third_party/ijar/ijar.cc`. [4](#0-3) [5](#0-4)

static bool IsMultiRelease(u1* manifest_data, size_t manifest_size) {
  static const char* enabled_line = "Multi-Release: true";
  static const size_t enabled_length = strlen(enabled_line);
  const char* line_start = (const char*)manifest_data;
  const char* data_end = (const char*)manifest_data + manifest_size;
  while (line_start < data_end) {
    const char* line_end = strchr(line_start, '\n');
    line_end = line_end != nullptr ? line_end + 1 : data_end;
    size_t line_length = line_end - line_start;

    if (line_length >= enabled_length &&
        strncmp(line_start, enabled_line, enabled_length) == 0 &&
        (line_length == enabled_length || line_start[enabled_length] == '\r' ||
         line_start[enabled_length] == '\n')) {
      return true;
    }
    line_start = line_end;
  }
  return false;
}
