### Title
Unauthenticated `vested_transfer` lets anyone permanently fill a victim's bounded vesting-schedule slots, DoS'ing legitimate vesting to that account - (File: `substrate/frame/vesting/src/lib.rs`)

### Summary
`pallet_vesting::vested_transfer` can be called by **any signed account** and pushes a new `VestingInfo` entry into the **target's** bounded `Vesting<T>` list, capped at `T::MAX_VESTING_SCHEDULES`. Because the only guard is `schedules.try_push(...)` failing with `AtMaxVestingSchedules` when the bound is reached, an attacker can pay the small `MinVestedTransfer` amount repeatedly to fill up every slot of an arbitrary victim account with schedules that never fully vest (by choosing a far-future `starting_block`), permanently blocking any future legitimate `vested_transfer`/`force_vested_transfer` to that account. This mirrors the vePeg `MAX_DELEGATES` bug: a cheap, unrelated third-party action fills a bounded per-account collection that the victim does not control, denying them a capability tied to that collection.

### Finding Description
The vesting schedule storage is a `BoundedVec` keyed per account: [1](#0-0) 

`vested_transfer` is a normal signed extrinsic with no relationship requirement between caller and `target` — anyone can transfer to anyone: [2](#0-1) 

The addition path enforces only the bound of the list, with no accounting for who owns/controls the account being filled and no way for the target to reject or evict schedules that are not yet vested: [3](#0-2) 

```rust
let mut schedules = Vesting::<T>::get(who).unwrap_or_default();
ensure!(schedules.try_push(vesting_schedule).is_ok(), Error::<T>::AtMaxVestingSchedules);
```

Just like the vePeg report where `dstRepOld.length + ownerTokenCount <= MAX_DELEGATES` lets an attacker pre-fill Alice's delegate slot with dust NFTs so her real re-delegation later reverts, here an attacker can pre-fill a victim's `Vesting<T>` bound with `MinVestedTransfer`-sized schedules whose `starting_block` is set arbitrarily far in the future. Because a schedule only leaves the list once `locked_at()` reaches zero (checked in `report_schedule_updates`/`exec_action`), a schedule that has not yet reached its `starting_block` remains locked indefinitely and occupies a slot forever, regardless of anyone calling `vest`/`vest_other`: [4](#0-3) 

Repeating this `MAX_VESTING_SCHEDULES` times (a small, fixed, per-runtime constant) permanently exhausts the bound, after which any legitimate `vested_transfer` (e.g. an exchange, a team payroll pallet, or `force_vested_transfer` from governance) targeting that address fails with `AtMaxVestingSchedules`: [5](#0-4) 

Existing guards do not stop this because:
- `vested_transfer` has no origin-vs-target relationship check (any signed account may target any other account).
- `can_add_vesting_schedule`/`try_push` only checks *capacity*, not *ownership or intent* of the existing entries.
- Nothing lets the victim clear an attacker-planted schedule early; schedules can only be removed once fully vested (`locked_at == 0`), and `starting_block` is attacker-controlled and can be set past any realistic time horizon.

### Impact Explanation
This blocks legitimate vesting distributions to a targeted address indefinitely (or for as long as the attacker chooses via `starting_block`), which can disrupt token distribution flows (vested airdrops, salary/vesting streams, treasury-funded vesting grants via `force_vested_transfer`) for the targeted account. The cost to the attacker is `MAX_VESTING_SCHEDULES × MinVestedTransfer`, a small, fixed, one-time amount, for an effectively permanent denial-of-service on that specific capability of the victim account, matching the "public underpriced work" / "permanent user-fund lock"-adjacent impact class (funds destined for the victim cannot be vested to them until the attacker's schedules are manually merged away, which the victim cannot force since `merge_schedules` requires locating and merging attacker-controlled indices and the victim gains no unilateral eviction right for not-yet-started schedules).

### Likelihood Explanation
High. `vested_transfer` is a completely public, unprivileged, always-available extrinsic; the attacker needs no special permission, no front-running, no governance/admin/validator role, and only needs `MAX_VESTING_SCHEDULES × MinVestedTransfer` funds, both of which are attacker-controlled constants of modest size.

### Recommendation
Add an ownership/consent gate to `add_vesting_schedule`/`do_vested_transfer` so that third parties cannot unilaterally add vesting schedules to an unrelated account, for example:
- Require the target's explicit opt-in (a `pending`/`accepted` schedule flow), or
- Only allow one pending "third-party" schedule to occupy an implicit reserved slot while the rest of the bound remains available to the account owner or root, or
- Allow the target/owner to cancel/evict schedules that have not yet started vesting (`now < starting_block`) so griefing schedules can be purged without waiting for `locked_at` to reach zero.

### Proof of Concept
1. Let `M = MAX_VESTING_SCHEDULES` for the runtime (a small fixed constant) and `V = MinVestedTransfer`.
2. Attacker funds a spare account with `M * V` and calls `vested_transfer(target = victim, schedule = VestingInfo::new(V, 1, starting_block = far_future))` `M` times.
3. Each call succeeds via `do_vested_transfer -> add_vesting_schedule -> schedules.try_push(...)` (see lines 780-816) until the victim's `Vesting<T>` list reaches `M` entries, none of which will ever have `locked_at == 0` before `far_future`.
4. Any subsequent `vested_transfer`/`force_vested_transfer` naming `victim` as target now fails with `Error::AtMaxVestingSchedules` (lines 298-312), even though the victim never consented to receiving these dust schedules and cannot remove them.

```rust
	fn report_schedule_updates(
		schedules: Vec<VestingInfo<BalanceOf<T>, BlockNumberFor<T>>>,
		action: VestingAction,
	) -> (Vec<VestingInfo<BalanceOf<T>, BlockNumberFor<T>>>, BalanceOf<T>) {
		let now = T::BlockNumberProvider::current_block_number();

		let mut total_locked_now: BalanceOf<T> = Zero::zero();
		let filtered_schedules = action
			.pick_schedules::<T>(schedules)
			.filter(|schedule| {
				let locked_now = schedule.locked_at::<T::BlockNumberToBalance>(now);
				let keep = !locked_now.is_zero();
				if keep {
					total_locked_now = total_locked_now.saturating_add(locked_now);
				}
				keep
			})
			.collect::<Vec<_>>();

		(filtered_schedules, total_locked_now)
	}
```

```rust
	fn add_vesting_schedule(
		who: &T::AccountId,
		locked: BalanceOf<T>,
		per_block: BalanceOf<T>,
		starting_block: BlockNumberFor<T>,
	) -> DispatchResult {
		if locked.is_zero() {
			return Ok(());
		}

		let vesting_schedule = VestingInfo::new(locked, per_block, starting_block);
		// Check for `per_block` or `locked` of 0.
		if !vesting_schedule.is_valid() {
			return Err(Error::<T>::InvalidScheduleParams.into());
		};

		let mut schedules = Vesting::<T>::get(who).unwrap_or_default();

		// NOTE: we must push the new schedule so that `exec_action`
		// will give the correct new locked amount.
		ensure!(schedules.try_push(vesting_schedule).is_ok(), Error::<T>::AtMaxVestingSchedules);

		debug_assert!(schedules.len() > 0, "schedules cannot be empty after insertion");
		let schedule_index = schedules.len() - 1;
		Self::deposit_event(Event::<T>::VestingCreated {
			account: who.clone(),
			schedule_index: schedule_index as u32,
		});

		let (schedules, locked_now) =
			Self::exec_action(schedules.to_vec(), VestingAction::Passive)?;

		Self::write_vesting(who, schedules)?;
		Self::write_lock(who, locked_now);

		Ok(())
	}
```
