### Title
Optional `resolved_address` field allows callers to skip DNS-rebinding protection in snapshot/mirror RPCs, re-enabling SSRF - ([File: internal/gitaly/service/repository/create_repository_from_snapshot.go])

### Summary
Several Gitaly RPCs that make outbound HTTP/SSH/Git requests to attacker-influenced URLs (`CreateRepositoryFromSnapshot`, `FindRemoteRootRef`, `UpdateRemoteMirror`, `FetchRemote`, `CreateRepositoryFromURL`) implement a DNS-rebinding mitigation by pinning the connection to a caller-supplied `resolved_address` instead of letting the HTTP/Git client re-resolve the hostname at request time. This mitigation is explicitly documented as **optional** in the proto definitions, and the code paths that build the resolved/pinned client or Git config are only invoked when the field is non-empty. This mirrors the reported bug class: an optional parameter (`prices` in the original report) gates a security-relevant conversion/validation step, and omitting it causes the code to silently fall back to a less-safe path instead of failing closed.

### Finding Description
`CreateRepositoryFromSnapshotRequest.resolved_address`, `FindRemoteRootRefRequest.resolved_address`, and `UpdateRemoteMirrorRequest.Remote.resolved_address` are all marked `// Optional.` in the proto definitions: [1](#0-0) [2](#0-1) 

In `internal/gitaly/service/repository/create_repository_from_snapshot.go`, the resolved/pinned HTTP client (`newResolvedHTTPClient`) validates the resolved address and dials directly to `resolvedAddress:port`, bypassing hostname-based DNS resolution at connection time: [3](#0-2) 

Because this pinning is only applied when `resolved_address` is supplied, the RPC handler necessarily has a fallback branch that uses the un-pinned `httpClient` global (which relies on ordinary DNS resolution) when the field is empty. Similarly, `GetURLAndResolveConfig` in `internal/git/gitcmd/command_resolve.go` explicitly errors only when `resolvedAddress` is empty *when called*, but callers such as `findRemoteRootRefCmd` are shown by the accompanying test to have a distinct, unresolved code path for "no resolved address is present": [4](#0-3) 

This is architecturally identical to the reported bug class: a security-relevant transformation (currency conversion / address pinning) is gated behind an optional field, and whichever caller populates the RPC request controls whether the protection is actually applied. If GitLab Rails (or any other caller of these RPCs) fails to resolve and supply `resolved_address` — e.g., for a URL whose scheme/host it didn't pre-resolve, or simply omits it — Gitaly falls back to resolving the hostname itself at request time via the standard HTTP/Git client, which is exactly the TOCTOU condition the DNS-rebinding mitigation was designed to close.

### Impact Explanation
If the pinning field is omitted (whether by caller oversight, a code path in Rails that doesn't populate it, or a lower-privileged internal caller invoking these RPCs), the underlying HTTP/Git/SSH client resolves the attacker-supplied hostname at the time of the actual connection. An attacker who controls a URL fed into `CreateRepositoryFromSnapshot`, `FindRemoteRootRef`, `UpdateRemoteMirror`, `FetchRemote`, or `CreateRepositoryFromURL` (e.g., via project import/mirror configuration) can point DNS to a benign IP during any pre-check and then rebind to an internal address (e.g., cloud metadata service, internal admin endpoints) for the actual fetch, resulting in SSRF against Gitaly's network.

### Likelihood Explanation
Likelihood is moderate: exploitation depends on there being a real caller/code path that legitimately omits `resolved_address` (which the proto explicitly allows), rather than an attacker being able to unset a caller-set field directly over gRPC (which is trivially possible since it's just an optional string in the request message the attacker's own gRPC-facing surface, e.g. via crafted internal API params, may control end-to-end). Since the field is optional at the protocol level and there are tests explicitly exercising the "no resolved address" branch as a supported, non-error case, an unprivileged path (e.g., a mirror or import job that doesn't set the field) reaching the unpinned fallback is plausible without any privileged actor or MITM being required.

### Recommendation
Short term: for RPCs whose purpose is specifically to protect against DNS rebinding (mirror/import/fetch from arbitrary URLs), treat `resolved_address` as effectively mandatory when the target host is not already known-safe — reject the request or require the resolution to happen server-side rather than silently falling back to unpinned resolution. Long term: perform DNS resolution and pinning consistently inside Gitaly itself for all outbound fetches driven by user/attacker-supplied URLs, rather than relying on an optional caller-supplied hint field.

### Proof of Concept
1. Call `CreateRepositoryFromSnapshot` (or `FindRemoteRootRef` / `UpdateRemoteMirror`) with an `HttpUrl`/`RemoteUrl` pointing to an attacker-controlled hostname and leave `ResolvedAddress` unset, as exercised by the "no resolved address is present" test case: [4](#0-3) 
2. Configure the attacker-controlled DNS record to resolve to a benign IP while any upstream validation (e.g., a Rails-side SSRF filter) is performed, then rebind the DNS record to an internal address before Gitaly performs the actual fetch.
3. Because `resolved_address` was never supplied, Gitaly uses the standard `httpClient`/Git resolution path, which re-resolves the hostname at request time and connects to the rebound internal address, achieving SSRF.

Note: I was unable to fully trace every caller in GitLab Rails or Praefect that populates (or fails to populate) `resolved_address` for these RPCs from within this index, so I cannot confirm with certainty that a real unprivileged, attacker-reachable code path always omits the field in production; this should be verified against the calling code (Workhorse/Rails) in a full Devin session with complete repository access.

```go
// newResolvedHTTPClient is a modified version of the httpClient variable but here we resolve the
// URL to predefined IP:PORT. This is to avoid DNS rebinding.
func newResolvedHTTPClient(httpAddress, resolvedAddress string) (*http.Client, error) {
	url, err := url.ParseRequestURI(httpAddress)
	if err != nil {
		return nil, structerr.NewInvalidArgument("parsing HTTP URL: %w", err)
	}

	port := url.Port()
	if port == "" {
		switch url.Scheme {
		case "http":
			port = "80"
		case "https":
			port = "443"
		default:
			return nil, structerr.NewInvalidArgument("unsupported schema %q", url.Scheme)
		}
	}

	// Sanity-check whether the resolved address is a valid IP address.
	if net.ParseIP(resolvedAddress) == nil {
		return nil, structerr.NewInvalidArgument("invalid resolved address %q", resolvedAddress)
	}

	transport := httpTransport.Clone()
	transport.DialContext = func(ctx context.Context, network, _ string) (net.Conn, error) {
		return httpTransport.DialContext(ctx, network, fmt.Sprintf("%s:%s", resolvedAddress, port))
	}

	return &http.Client{
		Transport: correlation.NewInstrumentedRoundTripper(otelhttp.NewTransport(transport)),
		// Here we directly return the `ErrUseLastResponse` to prevent redirects
		CheckRedirect: func(*http.Request, []*http.Request) error {
			return http.ErrUseLastResponse
		},
	}, nil
}
```
