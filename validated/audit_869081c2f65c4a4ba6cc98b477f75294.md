## Title
Witness rewards accrued while vote count is zero are silently dropped and permanently lost — ([File: chainbase/src/main/java/org/tron/core/store/DelegationStore.java])

### Summary
java-tron's Stake 2.0 "new reward algorithm" tracks per-witness reward distribution with an accumulator (`Vi`, analogous to a Uniswap-style/Beedle-style `index`) that is updated once per maintenance cycle in `DelegationStore.accumulateWitnessVi`. Exactly like the reported Beedle `Staking.update()` bug — where the reward `index` is only bumped when `totalSupply > 0`, silently discarding rewards received while `totalSupply == 0` — java-tron's `accumulateWitnessVi` only folds a witness's accumulated cycle reward into `Vi` when `voteCount != 0`. If a witness's vote count is zero at the maintenance boundary for a cycle in which it nevertheless earned block/transaction-fee rewards, those rewards are dropped from the `Vi` accumulator forever, exactly mirroring the "totalSupply == 0 while balance keeps growing" root cause in the report.

### Finding Description
`DelegationStore.accumulateWitnessVi` computes the new `Vi` value per witness per cycle: [1](#0-0) 

If `reward == 0 || voteCount == 0`, the function takes the "just forward pre `Vi`" branch and does **not** fold the cycle's `reward` into the accumulator at all — the reward simply vanishes from the reward-distribution ledger. This is called from `MaintenanceManager.doMaintenance()` once per cycle, using the *current* `witness.getVoteCount()` (i.e., the vote tally as of the end of the cycle, before that maintenance's own vote delta is applied): [2](#0-1) 

Meanwhile, `MortgageService.payReward` (invoked via `payBlockReward`/`payTransactionFeeReward` on every produced block, driven by ordinary user transactions paying bandwidth/energy fees) unconditionally adds to the witness's per-cycle reward pot regardless of whether that witness currently has any votes: [3](#0-2) [4](#0-3) 

So it is entirely possible for `delegationStore.getReward(cycle, witness)` to be non-zero for a cycle where `witness.getVoteCount()` is zero at the maintenance boundary (e.g., all voters withdrew their votes via a normal `VoteWitnessContract`/TVM `voteWitness` unvote while the SR remains in the active/standby witness set and keeps producing blocks or receiving `payStandbyWitness` rewards through the rest of that cycle). When maintenance runs, `accumulateWitnessVi` sees `voteCount == 0` and skips folding that reward into `Vi`. The old (pre-VI) `computeReward(cycle, votes)` path in `MortgageService` has the identical gap — it `continue`s (skips) any witness whose `totalVote == 0` for that cycle: [5](#0-4) 

In both the old and new reward algorithms, the reward amount stored under `delegationStore.getReward(cycle, address)` is never subsequently claimed by anyone once the corresponding cycle's `Vi`/vote-count check is skipped — it is permanently orphaned in the `delegation` store with no code path that ever revisits or redistributes it.

### Impact Explanation
This causes a permanent freezing/loss of witness reward funds: TRX that was already credited to a witness's reward pot for a given cycle (funded by real transaction fees and block rewards paid by ordinary users) becomes permanently unclaimable because it is dropped from both the legacy per-cycle reward computation and the `Vi` accumulator used by the new reward algorithm. No voter or the witness itself can ever claim this reward through `WithdrawRewardProcessor`/`MortgageService.withdrawReward`/`queryReward`, since those only read from `Vi`/`getReward` via the same code paths that skipped the accounting. This matches the "permanent freezing of funds" impact class from the reference report.

### Likelihood Explanation
The trigger only requires an ordinary, unprivileged user action: any voter withdrawing/clearing their vote (`VoteWitnessContract`, or the TVM `voteWitness`/`withdrawReward` native contracts) can drive a witness's vote count to zero mid-cycle while that witness remains part of the active/standby witness set and keeps earning block or fee rewards from other users' normal transactions until the next maintenance cycle. This is a routine occurrence on a live network with fluctuating votes, not a contrived edge case, so likelihood is high, consistent with the "High" severity of the original report which cites the analogous "totalSupply == 0" condition as commonly reachable at deployment or after all stakers unstake.

### Recommendation
When `voteCount == 0` but `reward > 0` in `accumulateWitnessVi` (and in the legacy `MortgageService.computeReward`), do not silently discard the reward. Instead, carry it forward to be included once votes reappear (e.g., accumulate it in a pending/rollover bucket added to the next cycle's reward for that witness) rather than dropping it from the `Vi`/reward computation entirely.

### Proof of Concept
1. An SR `W` is in the active witness set with `voteCount > 0` at the start of cycle `N`.
2. During cycle `N`, ordinary users send transactions; `W` produces blocks and/or is paid standby rewards, so `MortgageService.payReward` accumulates a nonzero `delegationStore.getReward(N, W)`.
3. Before the maintenance boundary of cycle `N`, all voters call `VoteWitnessContract` (or TVM `voteWitness`) to withdraw their votes from `W`, driving `witness.getVoteCount()` to 0 (this is normal, permissionless activity).
4. At maintenance, `MaintenanceManager.doMaintenance()` calls `delegationStore.accumulateWitnessVi(N, W, 0)`.
5. Inside `accumulateWitnessVi`, since `voteCount == 0`, the `reward` accumulated in step 2 is never folded into `Vi(N, W)`; only the previous `Vi` is forwarded.
6. No account can ever recover that reward through `MortgageService.queryReward`/`withdrawReward` or the TVM `VoteRewardUtil.queryReward`/`withdrawReward`, because both rely exclusively on `Vi` deltas (new algorithm) or the `totalVote == 0` skip (old algorithm) to compute claimable amounts — the reward for cycle `N` is permanently stranded.

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
