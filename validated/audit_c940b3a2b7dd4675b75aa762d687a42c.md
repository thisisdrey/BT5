### Title
`delegation_pool::set_beneficiary_for_operator` Does Not Synchronize Pending Commission Before Redirecting It — (`File: aptos-move/framework/aptos-framework/sources/delegation_pool.move`)

---

### Summary

`delegation_pool::set_beneficiary_for_operator` changes the commission beneficiary address without first calling `synchronize_delegation_pool`. Because commission rewards are only committed to the beneficiary's shares at sync time, any accumulated-but-unsynced commission is silently redirected to the new beneficiary. An operator who previously designated a third-party beneficiary can steal that beneficiary's earned-but-uncommitted APT commission by switching the beneficiary address immediately before the next sync.

---

### Finding Description

The delegation pool tracks commission rewards lazily. Rewards accumulate in the underlying stake pool between epochs, and are only converted into shares for the beneficiary when `synchronize_delegation_pool` is called. The critical assignment happens at lines 1949–1956 of `delegation_pool.move`:

```move
// reward operator its commission out of uncommitted active rewards
buy_in_active_shares(pool, beneficiary_for_operator(stake::get_operator(pool_address)), commission_active);
// reward operator its commission out of uncommitted pending_inactive rewards
buy_in_pending_inactive_shares(
    pool,
    beneficiary_for_operator(stake::get_operator(pool_address)),
    commission_pending_inactive
);
``` [1](#0-0) 

`beneficiary_for_operator(...)` is resolved **at sync time**, not at the time rewards are earned. Therefore, whoever is the beneficiary when `synchronize_delegation_pool` runs receives all commission accumulated since the last sync.

`set_beneficiary_for_operator` changes this address without first flushing pending commission:

```move
/// Allows an operator to change its beneficiary. Any existing unpaid commission rewards will be paid to the new
/// beneficiary. To ensure payment to the current beneficiary, one should first call `synchronize_delegation_pool`
/// before switching the beneficiary.
public entry fun set_beneficiary_for_operator(
    operator: &signer,
    new_beneficiary: address
) acquires BeneficiaryForOperator {
    ...
    borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator = new_beneficiary;
    ...
}
``` [2](#0-1) 

The code comment itself acknowledges the problem but does not enforce the invariant. The function does not call `synchronize_delegation_pool` before mutating the beneficiary.

The same structural flaw exists in `staking_contract::set_beneficiary_for_operator`, which carries an identical advisory comment ("one should first call `distribute` before switching the beneficiary") but also does not enforce it. [3](#0-2) 

---

### Impact Explanation

**Direct theft of APT staking commission rewards.**

Scenario:
1. Operator sets beneficiary to address `B` (a revenue-sharing partner or separate treasury).
2. Multiple epochs pass; commission accumulates in the stake pool but is not yet synced to `B`'s shares.
3. Operator calls `set_beneficiary_for_operator(new_beneficiary = C)` — no sync occurs.
4. Anyone (or the operator) calls `synchronize_delegation_pool`. The entire accumulated commission is bought as shares for `C`, not `B`.
5. `B` receives zero commission for the period they were the designated beneficiary.

The stolen amount equals `commission_rate × (active_rewards + pending_inactive_rewards)` accumulated since the last sync. For a high-commission pool with a long sync gap, this can be substantial APT.

This matches the Aptos allowed impact gate: **direct theft of staking balances** via an unprivileged (operator-signed) transaction with no external requirements beyond having previously set a third-party beneficiary.

---

### Likelihood Explanation

- The operator must have previously set a different beneficiary (non-default case).
- The operator must call `set_beneficiary_for_operator` before the next `synchronize_delegation_pool` invocation.
- `synchronize_delegation_pool` is called automatically by every stake-management operation (`add_stake`, `unlock`, `reactivate_stake`, `withdraw`), so the window is bounded by pool activity — but in a quiet pool it can span many epochs.
- The operator controls the timing of both the beneficiary change and can avoid triggering a sync themselves, making the exploit fully controllable.

---

### Recommendation

Enforce synchronization inside `set_beneficiary_for_operator` before mutating the beneficiary:

```move
public entry fun set_beneficiary_for_operator(
    operator: &signer,
    new_beneficiary: address
) acquires DelegationPool, GovernanceRecords, BeneficiaryForOperator, NextCommissionPercentage {
    let operator_addr = signer::address_of(operator);
    // Flush all pending commission to the current beneficiary before changing it.
    // Iterate over all pools operated by this operator, or require pool_address as a parameter.
    synchronize_delegation_pool(pool_address);  // must commit pending rewards first
    ...
    borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator = new_beneficiary;
}
```

Alternatively, require the caller to pass the `pool_address` so the function can synchronize the specific pool before changing the beneficiary, mirroring the pattern used by `set_operator` (line 1264) and `update_commission_percentage` (line 1313), both of which call `synchronize_delegation_pool` before making their state change. ### Proof of Concept

```
1. Pool P is active; operator O has set beneficiary B (a third party).
2. end_aptos_epoch() × N  — rewards accumulate; no sync occurs.
   stake pool: active = 100_000 APT + N epochs of rewards
   delegation pool: last sync was N epochs ago; commission_active ≈ N × reward_rate × commission_pct is unsynced.

3. Operator O calls:
     delegation_pool::set_beneficiary_for_operator(operator=O, new_beneficiary=O_self)
   → BeneficiaryForOperator[O] = O_self
   → NO synchronize_delegation_pool call; pending commission is NOT committed to B.

4. Anyone calls:
     delegation_pool::synchronize_delegation_pool(pool_address=P)
   → synchronize_delegation_pool resolves beneficiary_for_operator(O) = O_self
   → buy_in_active_shares(pool, O_self, commission_active)   ← all N epochs of commission go to O
   → B receives 0 shares for the N epochs they were the designated beneficiary.

5. B has lost their earned commission; O has stolen it.
```

The stolen value is bounded only by the commission rate, the pool size, and the number of epochs since the last sync — all of which can be significant on a large, infrequently-touched delegation pool.

    public entry fun set_beneficiary_for_operator(
        operator: &signer,
        new_beneficiary: address
    ) acquires BeneficiaryForOperator {
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.
        let operator_addr = signer::address_of(operator);
        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator = new_beneficiary;
        } else {
            move_to(operator, BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary });
        };

        emit(SetBeneficiaryForOperator {
            operator: operator_addr,
            old_beneficiary,
            new_beneficiary,
        });
    }
