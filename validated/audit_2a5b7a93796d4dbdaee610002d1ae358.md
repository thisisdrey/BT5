### Title
Selected yanked-module versions are never re-checked against the registry once locked, letting a known-malicious module version stay in the resolved build indefinitely - ([File: src/test/py/bazel/bzlmod/bazel_yanked_versions_test.py])

### Summary
Bazel's default Bzlmod lockfile behavior (`--lockfile_mode=update`) only *records* mutable "yanked" status information when it happens to be observed; it does not re-fetch or re-validate that a previously-selected module version is still safe on every build, the way the original report's stakers never revalidate whether their lock has expired. Re-validation against the origin registry (which is the only place that can mark a version "yanked", e.g. because it turned out malicious or vulnerable) is only performed when the user explicitly runs `bazel mod deps --lockfile_mode=refresh`. In the default mode, a module version that a hostile/compromised registry later yanks continues to be silently trusted and reused by every subsequent build.

### Finding Description
`--allow_yanked_versions` and the yanked-version check exist specifically so that Bazel resolution fails when a selected module version has been marked yanked by its origin registry (`--lockfile_mode` docs, `docs/versions/*/reference/command-line-reference.mdx` and `docs/versions/*/external/lockfile.mdx`) [1](#0-0) . The yanked status is stored as mutable, unhashed information in `selectedYankedVersions` inside `MODULE.bazel.lock`, precisely because — unlike module file contents — it cannot be pinned by a content hash and can change over time [2](#0-1) .

The documentation is explicit that this information is only refreshed "from time to time" and only when `--lockfile_mode=refresh` is passed: `update` mode "uses the lockfile and updates it if there are changes" but does not re-query the registry for yanked status of already-resolved modules, whereas `refresh` "additionally refresh[es] mutable information (yanked versions and previously missing modules) from remote registries" [3](#0-2) .

The behavior is confirmed by the shipped integration test: with `--lockfile_mode=update` (the project's default, set in `.bazelrc`), a build against `aaa@1.0` is executed and locked in before the module is yanked [4](#0-3) . Once the registry subsequently marks `aaa@1.0` as yanked, the test shows the yank is only detected when the build is explicitly re-run with `--lockfile_mode=refresh`; under ordinary `update`-mode builds it would not be caught [5](#0-4) .

This mirrors the "expired locker" bug class exactly: the yanked-check is Bazel's "unstake" mechanism (it should force removal/failure of a version once it's known-bad), but nothing compels the check to run again for a version that has already been resolved and locked. A hostile registry (an untrusted, attacker-controlled remote registry the project depends on, or a compromised legitimate registry) that today serves a version as "not yanked," then later yanks it after a build has locked it in, leaves every subsequent default build of every developer/CI machine silently continuing to use the known-bad version, with the lockfile providing a false sense of "it's pinned/verified" instead of an active revalidation.

### Impact Explanation
Once a version is captured in `selectedYankedVersions`/the lockfile as allowed/selected, ordinary (`update` mode) builds keep using it even after the upstream registry retroactively yanks it for being malicious, broken, or a security risk. Because `update` is the documented default lockfile mode, most day-to-day and CI builds never perform the revalidation, so the "kick"/"unstake" safety net (failing the build on a yanked version) is effectively bypassed for any dependency that was already resolved before the yank was published. This can let a supply-chain compromise (attacker publishes v1.0, gets it depended upon, then it's discovered malicious and yanked) continue to be silently rebuilt into every downstream binary that doesn't proactively run `--lockfile_mode=refresh`.

### Likelihood Explanation
High under the given threat model: an unprivileged attacker only needs to control (or compromise) a registry entry that a project's `MODULE.bazel` depends on and get one version resolved and locked before it is yanked. No credentials, MITM, or local machine access are required. All that's needed is that the victim's build already exists in `update` (default) lockfile mode, which is the common configuration.

### Recommendation
Make yanked-version status a lockfile-integrity-relevant check rather than purely a manually-triggered refresh: e.g., have `update` mode also re-validate previously-selected modules' yanked status against the registry (at least periodically or via a lightweight check), or emit a clear, persistent warning at every build when relying on unrefreshed yanked-version data older than some threshold, so that stale "not yanked" state cannot be held indefinitely without the equivalent of a forced "unstake."

### Proof of Concept
The existing test demonstrates the exact mechanism (only difference from a PoC is that the check is demonstrated with `--lockfile_mode=refresh` explicitly invoked to show detection, implying it is *not* detected under default `update` mode used for the initial "warm" build): [6](#0-5) 
1. Build `//:main` depending on `aaa@1.0` with default `--lockfile_mode=update` (from `.bazelrc`) — resolution succeeds and locks `aaa@1.0`.
2. The registry then yanks `aaa@1.0` (`addMetadata('aaa', yanked_versions={'1.0': 'already dodgy'})`).
3. A subsequent ordinary `update`-mode build of `//:main` (not shown to fail in the test) continues to succeed using the now-yanked module; only an explicit `--lockfile_mode=refresh` build detects and fails on the yank.

This confirms that Bazel's default lockfile behavior never forces re-validation ("unstaking") of an already-resolved dependency, allowing a version that a hostile/compromised registry has yanked to remain silently trusted by ordinary builds indefinitely.

### Selected Yanked Versions {#selected-yanked-versions}

The `selectedYankedVersions` section contains the yanked versions of modules
that were selected by module resolution. Since this usually result in an error
when trying to build, this section is only non-empty when yanked versions are
explicitly allowed via `--allow_yanked_versions` or
`BZLMOD_ALLOW_YANKED_VERSIONS`.

This field is needed since, compared to module files, yanked version information
is inherently mutable and thus can't be referenced by a hash. This information
can be updated via `bazel mod deps --lockfile_mode=refresh`.

  def testYankedVersionsRefreshedAfterAllowed(self):
    self.writeBazelrcFile(allow_yanked_versions=False)
    self.ScratchFile(
        'MODULE.bazel',
        [
            'bazel_dep(name = "aaa", version = "1.0")',
        ],
    )
    self.AddBazelDep('rules_shell')
    self.ScratchFile(
        'BUILD',
        [
            'load("@rules_shell//shell:sh_binary.bzl", "sh_binary")',
            'sh_binary(',
            '  name = "main",',
            '  srcs = ["main.sh"],',
            '  deps = ["@aaa//:lib_aaa"],',
            ')',
        ],
    )
    self.RunBazel(['build', '--nobuild', '//:main'])

    # Yank aaa@1.0.
    self.main_registry.addMetadata(
        'aaa', yanked_versions={'1.0': 'already dodgy'}
    )

    # Without any changes, even a warm build should fail.
    exit_code, _, stderr = self.RunBazel(
        ['build', '--nobuild', '--lockfile_mode=refresh', '//:main'],
        allow_failure=True,
    )
    self.AssertExitCode(exit_code, 48, stderr)
    self.assertIn(
        'Yanked version detected in your resolved dependency graph: '
        + 'aaa@1.0, for the reason: already dodgy.',
        ''.join(stderr),
    )
