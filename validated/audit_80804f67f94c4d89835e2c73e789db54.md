### Title
Downloaded attachment content is stored without enforcing `attachments_max_size` bound - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AtlasConfig::validate` in `stackslib/src/net/atlas/mod.rs` only checks that `attachments_max_size` is not *smaller* than `ATTACHMENTS_MAX_SIZE_MIN`; it never caps the field, and more importantly `attachments_max_size` is never consulted anywhere along the download path. A remote peer serving `GET /v2/attachments/<hash>` can return a body of arbitrary size, which is decoded and stored into `AtlasDB` with no length check against this configured bound.

### Finding Description
`AtlasConfig::validate` enforces only a lower bound: `self.attachments_max_size < ATTACHMENTS_MAX_SIZE_MIN` [1](#0-0) . Searching the whole repo for `attachments_max_size` shows it is referenced only in `mod.rs` (definition/validate), `db.rs` (unrelated), `config/mod.rs`, `Stacks.toml`, and tests — it is never read inside `download.rs`, so nothing enforces it against the size of actually downloaded content.

On the wire, `RPCGetAttachmentRequestHandler::try_parse_response` deserializes the whole HTTP body into a `GetAttachmentResponse` via `parse_json` [2](#0-1) , and `StacksHttpResponse::decode_atlas_get_attachment` further parses it into an `Attachment` whose `content: Vec<u8>` is populated straight from `hex_bytes(&hex_encoded)` with no size check [3](#0-2) .

The decoded `Attachment` is inserted unconditionally into `AttachmentsBatchStateContext::attachments` in `extend_with_attachments` [4](#0-3) , and then in the `Done` branch of `AttachmentsDownloader::run`, every attachment is written to the database via `network.atlasdb.insert_instantiated_attachment(&attachment)` with no size gate [5](#0-4) . `insert_instantiated_attachment` itself just inserts `attachment.content` as-is into the `attachments` table [6](#0-5) .

No code path checks `attachment.content.len()` against `network.atlasdb.atlas_config.attachments_max_size` (or `ATTACHMENTS_MAX_SIZE_MIN`) before this store. The only size-related enforcement found is the config validator's lower-bound check at startup, which has no bearing on what a remote peer can send in an HTTP response body.

### Impact Explanation
Any peer a node queries for an attachment (which occurs whenever it discovers an `AttachmentInstance` referencing an unknown `content_hash`, e.g., via gossiped/BNS-related on-chain events) can respond with a body far larger than `attachments_max_size`/`ATTACHMENTS_MAX_SIZE_MIN`. That data is fully buffered in memory during HTTP/JSON/hex decoding and then written wholesale into the node's local SQLite `attachments` table, with no truncation or rejection. This is an amplification vector against the named `attachments_max_size` bound: a single unauthenticated peer response can force excess memory allocation and unbounded disk growth in `AtlasDB`, matching the "Critical" category (unbounded resource consumption from a single unauthenticated peer response).

### Likelihood Explanation
No special peer privilege, secret, or config flag is required — any node that serves the `/v2/attachments/<hash>` endpoint response for a request the victim node happens to issue can trigger this. The victim only needs to have queued a matching (or apparently matching, since the hash-of-received-content is used to resolve instances rather than any inbound validation of size before storage) attachment instance. This is fully remote and repeatable per download cycle, at minimal attacker cost (crafting one oversized HTTP body).

### Recommendation
In `extend_with_attachments` (or earlier at `RPCGetAttachmentRequestHandler::try_parse_response` / `decode_atlas_get_attachment`), check `attachment.content.len()` (or the raw hex/body length before decoding) against `AtlasConfig::attachments_max_size` and reject/drop the response (bump `report.bump_failed_requests()`) before it is added to `context.attachments` and ultimately passed to `insert_instantiated_attachment`. Ideally also cap the HTTP layer's read of the response body length for this endpoint proportionally to `attachments_max_size` to avoid buffering an oversized payload before validation.

### Proof of Concept
Add a test in `stackslib/src/net/atlas/download.rs` (or `net/api/tests/getattachment.rs`) that:
1. Configures an `AtlasConfig` with `attachments_max_size = ATTACHMENTS_MAX_SIZE_MIN` (1_048_576 bytes).
2. Crafts a `GetAttachmentResponse`-shaped HTTP response body whose hex-encoded content decodes to, e.g., 4 MB of bytes (`content.len() > attachments_max_size`).
3. Feeds this response through `StacksHttpResponse::decode_atlas_get_attachment` and then `AttachmentsBatchStateContext::extend_with_attachments`.
4. Assert that `context.attachments` contains an entry with `content.len() > attachments_max_size` (demonstrating the bound is not enforced), and that subsequently calling `AtlasDB::insert_instantiated_attachment` on it succeeds and stores the oversized content — i.e., `atlasdb.find_attachment(&hash).unwrap().unwrap().content.len() == 4 * 1024 * 1024`, not truncated to `attachments_max_size`.

    pub fn insert_instantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let tx = self.tx_begin()?;
        tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)",
            params![attachment.hash(), attachment.content, now],
        )?;
        tx.execute(
            "UPDATE attachment_instances SET is_available = 1 WHERE content_hash = ?1 AND status = ?2",
            params![attachment.hash(), AttachmentInstanceStatus::Checked],
        )?;
        tx.commit()?;
        Ok(())
    }
