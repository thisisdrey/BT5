### Title
NEP-141/NEP-245 tokens that revert transfers to specific addresses cause permanent loss of withdrawn balance in `ft_resolve_withdraw`/`mt_resolve_withdraw` - ([File: contracts/defuse/src/contract/tokens/nep141/withdraw.rs])

### Summary
When a user withdraws tokens from `defuse` via `ft_withdraw`/`mt_withdraw` with a non-empty `msg` (routing through `ft_transfer_call`/`mt_batch_transfer_call`), the contract debits the user's internal ledger balance *before* the outbound promise resolves, then relies on the promise's return value to decide whether to refund. If the underlying token contract makes the entire outbound call fail outright (e.g. because it enforces a transfer restriction/blacklist on the destination address, similar to OpenZeppelin's `_beforeTokenTransfer` checks referenced in the original Gravity Bridge report), `defuse` cannot distinguish "call failed after tokens were already moved" from "call reverted before anything happened." By design it always assumes the former and skips the refund, permanently burning the user's internal balance while the real tokens never leave the `defuse` contract's own token balance.

### Finding Description
`internal_ft_withdraw` first calls `self.withdraw(...)`, which unconditionally subtracts the amount from the owner's ledger balance and schedules an `mt_burn` event, *before* the cross-contract transfer promise is even created: [1](#0-0) 

The actual token movement is attempted afterward via `do_ft_withdraw`, using `ft_transfer_call` when `msg` is set: [2](#0-1) 

The refund decision is made in `ft_resolve_withdraw`. On the `is_call` path, if the promise cannot be read as a successful `U128` result (`Err(_)` from `promise_result_checked_json`), the code explicitly treats the **entire amount as used and issues no refund**: [3](#0-2) 

The comment justifies this as a deliberate trade-off against a known NEP-141 gas-exhaustion vulnerability where a malicious receiver could force the token contract's own `ft_resolve_transfer` to fail while tokens were already delivered — refunding in that case would let the sender double-spend. However, `env::promise_result_checked` returns the same `Err` for *any* outright failure of the outbound call, including a token contract that reverts the whole `ft_transfer_call` synchronously (before any state change) because it enforces an address-based transfer restriction on `receiver_id`. In that case no tokens ever left `defuse`'s real balance at the token contract, yet `defuse`'s internal ledger has already burned the user's balance and will never refund it. The identical pattern exists for multi-token withdrawals in `mt_resolve_withdraw`: [4](#0-3) 

This breaks the conservation binding "value debited versus value delivered plus refunded": the ledger debits the full amount, but neither the receiver nor the withdrawer ever receives it, and the tokens remain permanently trapped in `defuse`'s own on-chain token balance with no ledger entry pointing to them.

### Impact Explanation
Any withdrawal routed through `ft_transfer_call`/`mt_batch_transfer_call` (i.e. any `FtWithdraw`/`MtWithdraw` intent with `msg` set — a normal, unprivileged, user-triggered code path used for defuse-to-defuse composability and receiver notifications) to a token/receiver combination that causes the token contract to revert the whole transfer results in funds permanently frozen: the user's balance is destroyed on the intents ledger, and the underlying tokens are stranded in the `defuse` contract's own real balance with no accounting path to recover them. This matches the "funds permanently frozen" Critical impact category.

### Likelihood Explanation
This does not require any privileged role, relayer key, or DAO action — any account holder can trigger it by signing a withdrawal intent with `msg` set to a receiver on a token that enforces destination-address restrictions (a common real-world pattern for compliance-restricted bridged assets), or by being directed (e.g. via a malicious dApp/relayer-provided `msg`) to withdraw to such a receiver. The failure mode is inherent to how `promise_result_checked_json`'s `Err` variant is interpreted, so it triggers deterministically whenever the outbound call reverts outright rather than returning a JSON value.

### Recommendation
Distinguish, where possible, between "promise failed before any state change" and "promise failed after tokens were transferred but the result could not be read" — e.g. by having the token's `ft_transfer_call`/`mt_batch_transfer_call` wrapper contract used for such flows always guarantee a readable return value, or by using a two-step reserve/commit accounting so the ledger burn is not finalized until a definitive success signal is received, rather than assuming worst-case "used" on any unreadable promise result.

### Proof of Concept
1. Deploy (or use) a NEP-141 token contract whose `ft_transfer_call` enforces `require!(!is_blocked(receiver_id))` and reverts synchronously (no state change, no call to `ft_on_transfer`) for blocked receivers — analogous to standard blacklist-style ERC20 tokens.
2. User deposits this token into `defuse`, then signs an `FtWithdraw` intent with `token = <blacklisting token>`, `receiver_id = <blocked address>`, `msg = Some("...")` so `do_ft_withdraw` uses `ft_transfer_call` (`contracts/defuse/src/contract/tokens/nep141/withdraw.rs:136-151`).
3. `internal_ft_withdraw` burns the user's ledger balance immediately via `self.withdraw(...)` (`contracts/defuse/src/contract/tokens/mod.rs:76-117`).
4. The token contract's `ft_transfer_call` reverts outright due to the blacklist check; the outbound promise fails with `PromiseResult::Failed`.
5. `ft_resolve_withdraw` calls `promise_result_checked_json::<U128>(0)`, gets `Err(_)`, and per `contracts/defuse/src/contract/tokens/nep141/withdraw.rs:163-181` sets `used = amount.0`, issuing no refund.
6. Result: the user's `defuse` balance is zero, no tokens were ever transferred to the receiver, and the tokens remain stuck in `defuse`'s own balance at the token contract — permanently unaccounted for and unrecoverable through any user-facing intent.

            .accounts

            .ok_or_else(|| DefuseError::AccountNotFound(owner_id.to_owned()))?
            .get_mut_maybe_forced(force)
            .ok_or_else(|| DefuseError::AccountLocked(owner_id.to_owned()))?;

        let mut burn_event = MtBurnEvent {
            owner_id: Cow::Owned(owner_id.to_owned()),
            authorized_id: None,
            token_ids: Vec::new().into(),
            amounts: Vec::new().into(),
            memo: memo.map(Into::into).map(Into::into),
        };

        for (token_id, amount) in token_amounts {
            if amount == 0 {
                return Err(DefuseError::InvalidIntent);
            }

            burn_event.token_ids.to_mut().push(token_id.to_string());
            burn_event.amounts.to_mut().push(amount);

            owner
                .token_balances
                .sub(token_id.clone(), amount)
                .ok_or(DefuseError::BalanceOverflow)?;

            self.storage
                .state
                .total_supplies
                .sub(token_id, amount)
                .ok_or(DefuseError::BalanceOverflow)?;
        }
