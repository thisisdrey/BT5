## Title
ijar/singlejar ZIP parser: attacker-controlled central-directory `local_header_offset` bypasses bounds check via unsigned integer underflow, causing out-of-bounds read - (File: `third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` reads the 32-bit `local_header_offset` field straight out of the central directory record without validating it against the mapped file length [1](#0-0) . `ProcessNext` then uses this untrusted value to compute a raw pointer into the mmap'd buffer before any range check is performed [2](#0-1) . The only guard, `EnsureRemaining`, computes `remaining = input_file_->Length() - in_offset` using unsigned `size_t` arithmetic; when the attacker-chosen offset pushes `p` past the end of the file, `in_offset > Length()` and the subtraction underflows to a huge value, silently defeating the check [3](#0-2) . `get_u4le`/`get_u2le` then dereference the wild pointer with no further validation [4](#0-3) .

### Finding Description
This is the direct analog of the kernel PCI bug: a size/offset value taken from untrusted, attacker-supplied structured data (the ZIP central directory) is used to derive a pointer/offset that is checked with a subtraction-based bounds test, and that test is defeated exactly when the offset is bad enough to matter, because the subtraction underflows instead of failing safe.

Concretely:
1. `ProcessCentralDirEntry` walks the central directory and extracts `*offset = get_u4le(p)` (or the 64-bit ZIP64 extra-field value) directly from bytes supplied by the archive — no check that `offset < in_length` is performed here [5](#0-4) .
2. `ProcessNext` does `p = zipdata_in_ + in_offset_ + offset;` and then calls `EnsureRemaining(4, "signature")` before dereferencing `p` [2](#0-1) .
3. `EnsureRemaining` is meant to prevent OOB reads, but it computes `size_t in_offset = p - zipdata_in_; size_t remaining = input_file_->Length() - in_offset;`. If the attacker's `offset` makes `p` point past `zipdata_in_ + Length()`, `in_offset > Length()`, and `remaining` wraps around to a value near `SIZE_MAX` instead of a small/negative one [3](#0-2) . The subsequent `n > remaining` test therefore always passes, and the function returns success as if there were plenty of remaining bytes.
4. `get_u4le(p)` (and later `get_u2le`, `get_u4le` calls throughout `ProcessLocalFileEntry`) then read from the out-of-bounds pointer [6](#0-5) , walking further off the mapping as file name/extra-field lengths (also attacker-controlled and unvalidated against the real file bounds at this point) are added to `p`.

Because the file is memory-mapped (`MappedInputFile`/`mmap`), reading far enough past the mapping's end triggers a page fault / `SIGSEGV`, mirroring the kernel's `readl()` crash on an out-of-bounds ROM pointer. This code path (`ijar` and the structurally identical central-directory walk logic reused by `singlejar`'s `InputJar`, see `LocalHeader()` computing `cdh->local_header_offset() + preamble_size_` and dereferencing without a length check [7](#0-6) ) runs automatically as part of normal Bazel Java build actions (ijar generates interface jars for every Java dependency, including `java_import`/fetched third-party jars), so a malicious jar published at a dependency URL whose bytes match a declared/pinned `sha256` (the attacker controls both the bytes and, if it's a first-time pin, the checksum that gets recorded) can trigger this once the archive is unpacked/processed during the build — the sha256 check only binds file identity, not the internal structural validity the ZIP parser assumes.

### Impact Explanation
An unprivileged party who can get a victim's build to fetch/process a crafted `.jar`/ZIP archive (e.g., as a `http_jar`/`http_archive` dependency, or a jar embedded in an extracted archive) can craft a central directory entry with an out-of-range `local_header_offset`, causing `ijar`/`singlejar` to read out of the bounds of the memory-mapped archive. This results in a crash (denial of the build/worker via SIGSEGV) and, depending on heap/mapping layout, a broader out-of-bounds read of process memory during archive parsing — a memory-safety violation in a build-time tool that processes untrusted, attacker-published content whose sole gate is a checksum on the whole file, not structural validation of its contents.

### Likelihood Explanation
Any dependency delivered as a ZIP/JAR (http_jar, http_archive containing jars, maven-fetched artifacts staged through java rules) that is subsequently run through `ijar`/`singlejar` — a step performed automatically and unconditionally for Java targets — exercises this parser. Crafting a central directory entry with a bogus 32-bit offset (or ZIP64 64-bit offset) is trivial and requires no special privileges beyond publishing/serving the archive; the existing sha256/integrity check does not inspect internal ZIP structure, so it does not stop a self-consistent but structurally malicious archive.

### Recommendation
In `EnsureRemaining` (and anywhere pointers are derived from untrusted archive offsets, notably `ProcessNext`'s `p = zipdata_in_ + in_offset_ + offset;` and `ProcessCentralDirEntry`'s extraction of `local_header_offset`), validate the offset against `input_file_->Length()` *before* forming the pointer, and perform the remaining-bytes computation in a way that cannot underflow (e.g., check `p >= zipdata_in_ && (size_t)(p - zipdata_in_) <= Length()` first, and use saturating/`if (in_offset > Length()) return error(...)` rather than a plain subtraction). Apply the same offset-bounds validation to `InputJar::LocalHeader` in `src/tools/singlejar/input_jar.h`.

### Proof of Concept
A JUnit/`BuildIntegrationTestCase`-style reproduction: construct a ZIP archive whose Local File Header sits normally, but whose Central Directory Header's `local_header_offset32` field is set to a value close to (or exceeding) the total file size (e.g., `file_size - 2`), similar to the existing `CreateZipWithMalformedExtraField` test helper pattern used for singlejar fuzz-style tests [8](#0-7) , but targeting `local_header_offset32` instead of the extra field. Feed this archive to `ijar` (or `InputZipFile::Open`/`ProcessNext`) and observe that `EnsureRemaining` fails to reject the bad offset due to underflow, and `get_u4le(p)` in `ProcessNext` reads past the mapped file, crashing the process.

inline u2 get_u2le(const u1 *&p) {
    u4 x = (p[1] << 8) | p[0];

std::string CreateZipWithMalformedExtraField() {
  std::string zip_data;
  const std::string filename = "evil.bin";

  // 1. Local File Header (LFH)
  size_t lh_offset = zip_data.size();
  size_t lh_size = sizeof(LH) + filename.size();
  zip_data.resize(lh_offset + lh_size, 0);
  auto* lh = reinterpret_cast<LH*>(&zip_data[lh_offset]);
  lh->signature();
  lh->version(10);
  lh->file_name(filename.data(), filename.size());

  // 2. Extra field payload containing an oversized payload_size
  uint8_t ef_buffer[8] = {0};
  auto* ef1 = reinterpret_cast<ExtraField*>(ef_buffer);
  ef1->signature(0x000d);
  ef1->payload_size(0);

  auto* ef2 = reinterpret_cast<ExtraField*>(ef_buffer + ef1->size());
  ef2->signature(0xdead);
  ef2->payload_size(0xf000);  // Malformed size exceeding extra field buffer

  // 3. Central Directory Header (CDH)
  size_t cdh_offset = zip_data.size();
  size_t cdh_size = sizeof(CDH) + filename.size() + sizeof(ef_buffer);
  zip_data.resize(cdh_offset + cdh_size, 0);
  auto* cdh = reinterpret_cast<CDH*>(&zip_data[cdh_offset]);
  cdh->signature();
  cdh->version(20);
  cdh->version_to_extract(10);
  cdh->local_header_offset32(lh_offset);
  cdh->file_name(filename.data(), filename.size());
  cdh->extra_fields(ef_buffer, sizeof(ef_buffer));

  // 4. End of Central Directory (EOCD)
  size_t ecd_offset = zip_data.size();
  zip_data.resize(ecd_offset + sizeof(ECD), 0);
  auto* ecd = reinterpret_cast<ECD*>(&zip_data[ecd_offset]);
  ecd->signature();
  ecd->this_disk_entries16(1);
  ecd->total_entries16(1);
  ecd->cen_size32(cdh_size);
  ecd->cen_offset32(cdh_offset);

  return zip_data;
}
