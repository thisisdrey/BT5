### Title
Cross-contract StackerDB chunk signature replay due to missing contract binding in `SlotMetadata::auth_digest` - (`libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest` computes the signed digest from only `slot_id`, `slot_version`, and `data_hash`, omitting the StackerDB's `QualifiedContractIdentifier`. Because slot ownership is configured independently per contract, an address that legitimately owns slot N in contract A can have a chunk signature for that slot replayed and accepted as valid for slot N in a different contract B, if the same address also owns slot N there, since the signature never actually commits to which contract it was intended for.

### Finding Description
The equality the protocol needs is: *a signature valid for slot N in contract A implies authorization only for contract A's slot N*. This is broken because `auth_digest` in `libstackerdb/src/libstackerdb.rs` hashes only `slot_id.to_be_bytes()`, `slot_version.to_be_bytes()`, and `data_hash.0` [1](#0-0) . Neither `StackerDBChunkData::sign`/`SlotMetadata::sign` nor `SlotMetadata::verify`/`StackerDBChunkData::verify` fold in the target contract identifier at all [2](#0-1) [3](#0-2) .

Verification at write time (`StackerDBTx::try_replace_chunk` in `stackslib/src/net/stackerdb/db.rs`) resolves the config/slot for the specific `stackerdb_id`/contract being written to, and calls `slot_desc.verify(&slot_validation.signer)` (i.e., `SlotMetadata::verify`) against the expected signer address for that slot in that contract's config. Since the digest never contains the contract ID, a signature produced for `(slot_id, slot_version, data_hash)` under contract A's config is bit-for-bit identical to what would be required for the same `(slot_id, slot_version, data_hash)` under contract B's config. If the same address is configured as the owner of slot N in both contract A and contract B (a realistic overlap for stackerdb configs like `.miners` and `.signers-0-1`, which are often derived from the same signer set), the exact same `StackerDBChunkData` (slot_id, slot_version, sig, data) accepted for A will also pass `verify()` for B.

### Impact Explanation
This allows unauthenticated cross-contract forgery of StackerDB chunk writes: a chunk signed and legitimately written to one contract's slot can be replayed verbatim into a different contract's identically-numbered slot without ever holding the private key context tied to that second contract, as long as the slot owner address happens to coincide. This is an unauthorized write into StackerDB state that then propagates via the normal StackerDB sync/gossip path to other nodes, since downstream code trusts `verify()` succeeding as proof of authorization. This matches the "unauthenticated/unauthorized write to state or StackerDB, network-wide propagation of forged data" Critical category.

### Likelihood Explanation
Exploitation requires: (1) the attacker legitimately controls a StackerDB slot in some contract A (a normal, unprivileged role — e.g. mining or signing participation), and (2) the same address is also assigned ownership of an identically-numbered slot in a different contract B. Whether (2) holds depends entirely on how StackerDB configs assign slot owners across different contracts in a given deployment/testnet/mainnet configuration — this is not guaranteed by the code, but is a plausible and realistic overlap (e.g., signer sets reused across DB instances). No secret key theft, no privileged role, and no local access are required beyond what the attacker already legitimately possesses for contract A.

### Recommendation
Include the StackerDB's `QualifiedContractIdentifier` (or an equivalent contract/DB-specific domain separator, e.g. the `stackerdb_id`) in `SlotMetadata::auth_digest` so that signatures are cryptographically bound to the specific contract instance they were created for, preventing cross-contract replay even when slot owner addresses coincide. This requires updating `sign`/`verify` call sites to pass the contract context in, and is a wire-format-breaking change requiring version negotiation or epoch gating.

### Proof of Concept
Rust test plan in `stackslib/src/net/stackerdb/tests/db.rs`:
1. Create two `StackerDBConfig`s / two `stackerdb_id` entries (contract A `.miners`-like and contract B `.signers-0-1`-like) with the same slot owner address configured for slot 0 in both.
2. Construct a `StackerDBChunkData::new(0, 1, data)`, sign it once with the shared owner's private key via `StackerDBChunkData::sign`.
3. Call `StackerDBTx::try_replace_chunk` for contract A's `stackerdb_id` with this chunk — assert it is accepted.
4. Call `StackerDBTx::try_replace_chunk` for contract B's `stackerdb_id` with the *same unmodified* chunk (same sig, same slot_id/version/data) — assert it is *also* accepted, proving the signature was never bound to contract identity via `auth_digest`.

    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
