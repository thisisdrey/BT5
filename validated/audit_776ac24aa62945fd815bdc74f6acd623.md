### Title
Caller-Supplied `oracle_price` in `take_ready_price_based_orders` Enables Arbitrary Pending-Order Triggering — (`aptos-move/framework/aptos-experimental/sources/trading/market/market_types.move`)

---

### Summary

The Aptos experimental trading framework exposes `market_types::take_ready_price_based_orders` as a `public` function that accepts an unvalidated `oracle_price: u64` directly from the caller. This price is used to decide which pending (stop-loss / take-profit) orders are dequeued and activated. Because no on-chain oracle is consulted and no bounds check is performed, any module — including a user-facing entry function — can supply an arbitrary price, triggering orders that should not yet be active and causing financial loss to the order owners.

---

### Finding Description

`market_types::take_ready_price_based_orders` is declared `public` and delegates directly to `order_book::take_ready_price_based_orders`, which in turn calls `pending_order_book_index::take_ready_price_based_orders`:

```move
// market_types.move
public fun take_ready_price_based_orders<M: store + copy + drop>(
    self: &mut Market<M>, oracle_price: u64, order_limit: u64
): vector<SingleOrder<M>> {
    self.order_book.take_ready_price_based_orders(oracle_price, order_limit)
}
``` [1](#0-0) 

Inside `pending_order_book_index`, the caller-supplied `current_price` is compared directly against each pending order's trigger threshold:

### Impact Explanation

A pending order with a `PriceMoveAbove(X)` trigger condition (take-profit sell) should only activate when the real market price reaches `X`. Because `oracle_price` is caller-supplied:

1. An attacker calls `take_ready_price_based_orders` with `oracle_price = MAX_U64`, instantly dequeuing every `PriceMoveAbove` pending order regardless of actual market conditions.
2. Those orders are returned to the caller, who then places them into the active order book via `place_order_with_order_id` at their original limit prices.
3. If the real market is far below those limit prices, the orders execute as takers against existing bids, filling victims at prices they never intended to accept at that moment — a direct theft of the price-improvement value embedded in the pending order.

The symmetric attack applies to `PriceMoveBelow` (stop-loss) orders by supplying `oracle_price = 0`.

---

### Likelihood Explanation

- The function is `public`, so any module deployed on-chain can call it.
- The `Market<M>` resource is stored by the clearinghouse module; any clearinghouse that exposes an entry function for triggering pending orders (the intended operational flow) passes the price from the transaction arguments, making the attack trivially reachable.
- No special privilege, key, or governance action is required — a single unprivileged transaction suffices.

---

### Recommendation

1. **Remove `oracle_price` from the public API.** The price should be fetched inside the function from a trusted on-chain oracle (e.g., a Pyth or Switchboard price feed stored in the `Market` config), not accepted from the caller.
2. **Add a privileged-caller guard.** Restrict `take_ready_price_based_orders` to `public(friend)` or require a capability object that only the market operator can mint, preventing arbitrary modules from invoking it.
3. **Consider a TWAP or median price.** Even with a trusted oracle feed, using a single spot price is susceptible to flash-loan manipulation within the same block; a time-weighted or multi-source price is more robust.

public entry fun exploit<M: store + copy + drop>(
