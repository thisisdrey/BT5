Audit Report

## Title
Relayer reward is paid on Snowbridge outbound delivery receipts without checking the `success` flag of the dispatched message - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

## Summary
`DeliveryReceipt::try_from` decodes the Ethereum `InboundMessageDispatched(nonce, topic, success, reward_address)` event into a struct carrying an explicit `success: bool` field, but `Pallet::process_delivery_receipt` never reads that field before paying the relayer reward via `T::RewardPayment::register_reward` and clearing the pending order. This allows a relayer to collect a reward for a message the Gateway itself reported as failed.

## Finding Description
The delivery flow: BridgeHub creates a `PendingOrder{nonce, fee, ...}` in `do_process_message`, the Ethereum Gateway emits `InboundMessageDispatched(nonce, topic, success, reward_address)` after attempting the message, and a relayer submits this via `submit_delivery_receipt`, which verifies the proof, decodes the log into `DeliveryReceipt`, and calls `process_delivery_receipt`. That function checks only that `T::GatewayAddress::get() == receipt.gateway` and that a `PendingOrder` exists for the nonce, then unconditionally calls `register_reward` for `order.fee` and removes the order. `receipt.success` is decoded but never inspected anywhere in the pallet. The cryptographic proof only establishes that the log genuinely exists on Ethereum and was emitted by the correct gateway — it says nothing about whether the destination execution succeeded, since `success` is itself a payload field within that same log.

## Impact Explanation
This matches the "duplicate settlement or payout" impact category: a relayer reward is paid, and the `PendingOrder` is closed, for a message that the Gateway explicitly reported as failed (`success: false`), which is a normal outcome the Gateway is designed to emit (e.g. insufficient gas for command execution, command-level revert), not merely an adversarial condition. Rewards are drawn from bridge/protocol reward funds via `T::RewardPayment::register_reward`, so this drains reward funds without corresponding successfully delivered value, and the order is removed so the failure cannot be retried or reconciled.

## Likelihood Explanation
The path requires no privileged actor: any relayer who observes a real `InboundMessageDispatched` event with a valid execution/receipt proof — successful or failed — can submit it through the public `submit_delivery_receipt` extrinsic. Because `success=false` is a legitimate, expected outcome of the Gateway contract's execution logic, this is reachable in ordinary operation without any relayer compromise or malicious behavior; the relayer here is faithfully relaying accurate on-chain data.

## Recommendation
Gate the reward payment on `receipt.success` in `process_delivery_receipt`: only call `register_reward` when `receipt.success && order.fee > 0`. Still remove the `PendingOrder` in both cases (the message has been finally resolved either way), and emit a distinct event (e.g., `MessageDeliveryFailed`) when `success == false` so failed deliveries are observable and can be handled or retried instead of silently rewarding the relayer as if delivery succeeded.

## Proof of Concept
1. BridgeHub queues an outbound message; `do_process_message` creates `PendingOrder{nonce, fee>0}` [4](#0-3) .
2. The Gateway attempts execution and fails, emitting `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer obtains a valid proof for this real `success=false` event and calls `submit_delivery_receipt(origin, event)` [5](#0-4) .
4. Verification and decoding succeed; `process_delivery_receipt` checks only gateway match and pending-nonce existence, then unconditionally pays the reward and removes the order [6](#0-5) .
5. Reproducible directly by constructing `DeliveryReceipt { success: false, .. }` and calling `process_delivery_receipt`, analogous to the existing `success: true` tests [7](#0-6) , and observing the reward is still registered.

				);

sol! {
	event InboundMessageDispatched(uint64 indexed nonce, bytes32 topic, bool success, bytes32 reward_address);

/// Delivery receipt
#[derive(Clone, Debug)]
pub struct DeliveryReceipt {
	/// The address of the outbound queue on Ethereum that emitted this message as an event log
	pub gateway: H160,
	/// The nonce of the dispatched message
	pub nonce: u64,
	/// Message topic
	pub topic: H256,
	/// Delivery status
	pub success: bool,
	/// The reward address
	pub reward_address: [u8; 32],
}

#[derive(Copy, Clone, Encode, Decode, Eq, PartialEq, Debug, TypeInfo)]
pub enum DeliveryReceiptDecodeError {
	DecodeLogFailed,
	DecodeAccountFailed,
}

impl TryFrom<&Log> for DeliveryReceipt {
	type Error = DeliveryReceiptDecodeError;

	fn try_from(log: &Log) -> Result<Self, Self::Error> {
		let topics: Vec<B256> = log.topics.iter().map(|x| B256::from_slice(x.as_ref())).collect();

		let event = InboundMessageDispatched::decode_raw_log_validate(topics, &log.data)
			.map_err(|_| DeliveryReceiptDecodeError::DecodeLogFailed)?;

		Ok(Self {
			gateway: log.address,
			nonce: event.nonce,
			topic: H256::from_slice(event.topic.as_ref()),
			success: event.success,
			reward_address: event.reward_address.0,
		})
	}
