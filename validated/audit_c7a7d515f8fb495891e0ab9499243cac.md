### Title
`ft_resolve_withdraw` never refunds the wNEAR `storage_deposit` leg on `near_withdraw` failure - ([File: contracts/defuse/src/contract/tokens/nep141/withdraw.rs])

### Summary
When `FtWithdraw.storage_deposit` is set, `internal_ft_withdraw` debits both the FT `amount` and the wNEAR `storage_deposit` from the owner's balance in a single synchronous `withdraw()` call, then dispatches an async chain `near_withdraw -> do_ft_withdraw -> ft_resolve_withdraw`. If `near_withdraw` fails, `do_ft_withdraw`'s `require!` panics before any further promise is scheduled, and the only resolver in the chain, `ft_resolve_withdraw`, refunds solely the FT `token`/`amount` — it has no parameters for `wnear_id`/`storage_deposit` and therefore never re-credits it.

### Finding Description
Binding claimed to hold: `internal_sub_balance(owner_id, {token: amount, wnear_id: storage_deposit})` == `assets that actually left custody` + `amount recredited by *_resolve_*`. This is violated for the wNEAR leg.

Code path:
1. `internal_ft_withdraw` (contracts/defuse/src/contract/tokens/nep141/withdraw.rs:60-74) synchronously debits both legs via a single `self.withdraw(...)` call chaining `(token, amount)` and `(wnear_id, storage_deposit)` [1](#0-0) . This debit is committed in the initiating receipt regardless of what happens to the later async promises (standard NEAR semantics).
2. It then schedules `near_withdraw` → `do_ft_withdraw` → `ft_resolve_withdraw` [2](#0-1) .
3. `do_ft_withdraw` panics via `require!(promise_result_checked_void(0).is_ok(), "near_withdraw failed")` if `near_withdraw` failed [3](#0-2) . Since this is a `.then()` callback, `ft_resolve_withdraw` still executes afterward, receiving a failed promise result at index 0.
4. `ft_resolve_withdraw` only knows `token`, `sender_id`, `amount`, `is_call` (no `wnear_id`/`storage_deposit`), and on failure it refunds `amount` (the FT leg) via `self.deposit(sender_id, [(token, refund)], ...)` [4](#0-3) . Nothing in this chain ever calls `self.deposit` for the `wnear_id` token, so the `storage_deposit` amount debited in step 1 is never restored.

Since `near_withdraw` failing means the wnear contract never unwrapped/transferred the NEAR (the wNEAR FT balance the Defuse contract holds on the wnear contract is unaffected), the debited internal ledger entry for `token_balances[owner_id][wnear_id]` represents value that never left custody and is never returned — a permanent, unrecoverable loss on the Defuse contract's internal accounting for that user.

The identical pattern (debit both legs synchronously, resolver only credits the primary asset, no `storage_deposit` refund) also exists in `internal_nft_withdraw`/`nft_resolve_withdraw` and `internal_mt_withdraw`/`mt_resolve_withdraw` [5](#0-4) [6](#0-5) , confirming this is a structural gap rather than an isolated typo.

None of the existing guards (`assert_one_yocto`, `#[private]`, `#[pause]`) address this because the flaw is in the resolver's scope of knowledge, not authorization.

### Impact Explanation
Whoever submits the `FtWithdraw` intent with a non-empty `storage_deposit` that triggers `near_withdraw` failure permanently loses the `storage_deposit` amount of wNEAR from their internal Defuse balance, with no corresponding credit anywhere in the resolved chain. This matches the Critical category "a refund or resolver credit that does not match what failed to settle." However, since `storage_deposit` is a parameter of the caller's own signed intent, this can only be triggered against the caller's own balance (not a third party's), unless a targeted precondition exists that causes `near_withdraw` to fail unpredictably for otherwise-normal withdrawals (e.g., wNEAR contract-side edge cases), which would then affect any legitimate user hitting that edge case.

### Likelihood Explanation
Requires: owner has both the FT `amount` and enough `wnear_id` balance to cover `storage_deposit`; and a condition making `near_withdraw` fail on the wnear contract (e.g. insufficient registration/edge case triggerable by a specific `storage_deposit` value). The reliability of forcing `near_withdraw` to fail deterministically depends on the wNEAR contract implementation, which could not be fully verified with available tools (out of scope: `**/mock.rs`, but `crates/near/wnear` production code was found only as a thin `ext_contract` trait [7](#0-6) ; the actual wNEAR contract implementation deployed was not located in this index).

### Recommendation
Pass `wnear_id` and `storage_deposit` (or a combined refund descriptor) into `ft_resolve_withdraw` (and the analogous `nft_resolve_withdraw`/`mt_resolve_withdraw`), and refund the wNEAR leg based on the actual outcome of `near_withdraw`/`do_ft_withdraw`, mirroring the FT-leg refund logic.

### Proof of Concept
`cargo test` (near-workspaces sandbox) plan:
1. Deploy Defuse contract with a wnear contract that can be made to fail `near_withdraw` for a chosen amount (e.g., call with an amount exceeding wNEAR's registered total supply or an unregistered `storage_deposit` receiver edge case).
2. Fund `owner_id` with FT `amount` and wNEAR `storage_deposit` balance inside Defuse.
3. Sign and execute `FtWithdraw { token, amount, storage_deposit: Some(X), .. }` where `X` is crafted to make `near_withdraw` fail.
4. Assert: `token_balances[owner_id][token]` == original (fully refunded via `ft_resolve_withdraw`'s `Err(_) => 0` / non-call refund path).
5. Assert: `token_balances[owner_id][wnear_id]` decreased by `storage_deposit` and stays decreased after the promise chain resolves (no `deposit()` call credits it back), while `ft.balance_of(defuse_contract)` on the wnear contract is unchanged (proving the value never left custody yet is unrecoverable in the ledger).

#[near]
impl FungibleTokenWithdrawResolver for Contract {
    #[private]
    fn ft_resolve_withdraw(
        &mut self,
        token: AccountId,
        sender_id: AccountId,
        amount: U128,
        is_call: bool,
    ) -> U128 {
        let used = if is_call {
            // `ft_transfer_call` returns successfully transferred amount
            match promise_result_checked_json::<U128>(0) {
                Ok(Ok(used)) => used.0.min(amount.0),
                Ok(Err(_deserialize_err)) => 0,
                // do not refund on failed `ft_transfer_call` due to
                // NEP-141 vulnerability: `ft_resolve_transfer` fails to
                // read result of `ft_on_transfer` due to insufficient gas
                Err(_) => amount.0,
            }
        } else {
            // `ft_transfer` returns empty result on success
            if promise_result_checked_void(0).is_ok() {
                amount.0
            } else {
                0
            }
        };

        let refund = amount.0.saturating_sub(used);
        if refund > 0 {
            self.deposit(
                sender_id,
                [(Nep141TokenId::new(token).into(), refund)],
                Some(REFUND_MEMO),
            )
            .unwrap_or_else(|err| err.panic());
        }

        U128(used)
    }
}

#[near]
impl MultiTokenWithdrawResolver for Contract {
    #[private]
    fn mt_resolve_withdraw(
        &mut self,
        token: AccountId,
        sender_id: AccountId,
        token_ids: Vec<defuse_nep245::TokenId>,
        amounts: Vec<U128>,
        is_call: bool,
    ) -> Vec<U128> {
        require!(
            token_ids.len() == amounts.len() && !amounts.is_empty(),
            "invalid args"
        );

        let mut used = if is_call {
            // `mt_batch_transfer_call` returns successfully transferred amounts
            match promise_result_checked_json_with_len::<Vec<U128>>(0, amounts.len()) {
                Ok(Ok(used)) if used.len() == amounts.len() => used,
                Ok(_) => vec![U128(0); amounts.len()],
                // do not refund on failed `mt_batch_transfer_call` due to
                // NEP-141 vulnerability: `mt_resolve_transfer` fails to
                // read result of `mt_on_transfer` due to insufficient gas
                Err(_) => amounts.clone(),
            }
        } else {
            // `mt_batch_transfer` returns empty result on success
            if promise_result_checked_void(0).is_ok() {
                amounts.clone()
            } else {
                vec![U128(0); amounts.len()]
            }
        };

        self.deposit(
            sender_id,
            token_ids
                .into_iter()
                .zip(amounts)
                .zip(&mut used)
                .filter_map(|((token_id, amount), used)| {
                    // update min during iteration
                    used.0 = used.0.min(amount.0);
                    let refund = amount.0.saturating_sub(used.0);
                    if refund > 0 {
                        Some((Nep245TokenId::new(token.clone(), token_id).into(), refund))
                    } else {
                        None
                    }
                }),
            Some(REFUND_MEMO),
        )
        .unwrap_or_else(|err| err.panic());

        used
    }
}
