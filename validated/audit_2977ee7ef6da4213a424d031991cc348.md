## Title
Client-controlled `remote_ip` bypasses per-IP `PackObjectsHook` concurrency limiting, enabling resource-exhaustion DoS - (File: internal/gitaly/service/hook/pack_objects.go)

## Summary
The external report describes a hardcoded permissive value (`amountOutMin = 0`) that disables an economic safety check on every trade, letting any unprivileged party exploit the missing bound. The closest concrete analog in Gitaly is in `packObjectsHook`, where the value used as the *key* for per-source concurrency limiting (`RemoteIp`, taken directly from the `PackObjectsHookWithSidechannelRequest` field) is trusted at face value with no independent verification, and any value that parses as a loop-back address causes the limiter to be skipped entirely — the RPC-handler resource limit equivalent of "0 slippage tolerance" for an untrusted, attacker-influenced input.

## Finding Description
`packObjectsHook` decides whether to invoke `git-pack-objects` through the concurrency limiter (`runPackObjectsLimited`) or completely unthrottled (`runPackObjects`) based on the `RemoteIp` field of the incoming `PackObjectsHookWithSidechannelRequest`: [1](#0-0) 

```go
ipAddr := net.ParseIP(req.GetRemoteIp())
if ipAddr == nil {
    if ip, _, err := net.SplitHostPort(req.GetRemoteIp()); err == nil {
        ipAddr = net.ParseIP(ip)
    }
}
// Ignore loop-back IPs
if ipAddr != nil && !ipAddr.IsLoopback() {
    return s.runPackObjectsLimited(ctx, w, ipAddr.String(), req, args, stdin, cacheKey)
}
return s.runPackObjects(ctx, w, req, args, stdin, cacheKey)
```

The proto comment on this field states it is "used as the key for concurrency limiting before we trigger git-pack-objects command": [2](#0-1) 

This value originates from gRPC metadata (`remote_ip`) that is forwarded end-to-end from the original client connection through `gitaly-hooks` into `WithPackObjectsHookEnv`, and ultimately embedded into the hook payload sent back to the `PackObjectsHookWithSidechannel` RPC: [3](#0-2) [4](#0-3) 

Just as the MEV report's `amountOutMin = 0` completely disables the intended tolerance check for anyone watching the mempool, an unparseable or loop-back-formatted `remote_ip` (e.g. `"127.0.0.1"`, `"::1"`, or any malformed string that fails both `net.ParseIP` and `net.SplitHostPort`) completely disables the per-key concurrency limiter (`runPackObjectsLimited`/`ConcurrencyLimiter.Limit`) that is otherwise supposed to bound concurrent `git-pack-objects` invocations per remote source: [5](#0-4) [6](#0-5) 

Because the RPC handler trusts this untrusted, request-supplied value for a security/resource-limiting decision rather than deriving it from the actual peer connection, the safety bound can be trivially neutralized.

## Impact Explanation
`git-pack-objects` invocations are CPU- and memory-intensive; the entire purpose of `runPackObjectsLimited`/`ConcurrencyLimiter` is to bound how many such expensive operations a single remote source can trigger concurrently, preventing resource exhaustion of the Gitaly node (see `doc/backpressure.md` and `doc/design_pack_objects_cache.md` for the documented rationale behind this backpressure mechanism): [7](#0-6) 

By supplying a value that resolves to loop-back (or fails to parse into any IP at all, given the code only *skips* limiting on a successfully-parsed loop-back address — an unparsed/garbage value that still evaluates `ipAddr == nil` correctly falls through to the unlimited path as well), a party who can trigger fetches (any user with fetch access, e.g. via CI or repeated clones) can cause unlimited concurrent `git-pack-objects` executions to run without the intended per-source throttling, leading to a denial-of-service condition on the Gitaly host — directly analogous to the unrestrained value loss enabled by the MEV report's `amountOutMin = 0`.

## Likelihood Explanation
The `remote_ip` value is propagated across multiple internal hops (gRPC metadata → hooks payload → PackObjectsHookWithSidechannelRequest) rather than being derived once from an authenticated network-layer source (e.g., `peer.FromContext`). Whether an ordinary, unprivileged client can directly control the initial metadata value is not fully verifiable from the indexed code alone — the value is set inside the internal request pipeline by `gitaly-hooks`/`requestinfohandler`, and I could not conclusively trace whether upstream layers (Workhorse/GitLab-Shell) sanitize or override this field before it reaches Gitaly. This uncertainty should be resolved by a background agent inspecting the full call chain (including GitLab-Shell/Workhorse integration, which is outside this indexed repo) before treating this as a confirmed unauthenticated bypass.

## Recommendation
Do not use a client/request-supplied `RemoteIp` field as the sole key for a resource-limiting decision. Derive the peer address exclusively from the transport layer (e.g. `peer.FromContext(ctx)` on the actual gRPC connection where the sidechannel request/hook payload originates), or, if the value must be forwarded across hops, cryptographically bind/verify it (e.g., via the existing internal auth token) so it cannot be spoofed. Additionally, treat any unparseable `RemoteIp` as an error/log condition rather than silently falling through to the unlimited code path, and always default to the limited path unless a peer address is verified to be loop-back.

## Proof of Concept
1. As a client capable of triggering `git-upload-pack`/`PostUploadPackWithSidechannel` fetches, ensure the request path results in a `PackObjectsHookWithSidechannelRequest.RemoteIp` set to `"127.0.0.1"` (or a malformed value that fails IP parsing) — reachable because the field is carried via gRPC metadata forwarded from client-influenced context in `injectMetadataIntoOutgoingCtx`.
2. Issue many concurrent fetch/clone requests against a large repository from the same effective source.
3. 			return nil
		}

			UserID:   metadata.GetValue(ctx, "user_id"),
			Username: metadata.GetValue(ctx, "username"),
			RemoteIP: metadata.GetValue(ctx, "remote_ip"),
		}

		if err := cc.configureHooks(
			ctx,
			cfg,
			objectHash,
			repo,
			gitCmdFactory,
			userDetails,
			PackObjectsHook,
		); err != nil {
			return fmt.Errorf("pack-objects hook configuration: %w", err)
		}

		cc.globals = append(cc.globals, ConfigPair{
			Key:   "uploadpack.packObjectsHook",
			Value: cfg.BinaryPath("gitaly-hooks"),
		})

		return nil
	}

// Limit will limit the concurrency of the limited function f. There are two distinct mechanisms
// that limit execution of the function:
//
//  1. First, every call will enter the per-key queue. This queue limits how many callers may try to
//     acquire their per-key semaphore at the same time. If the queue is full the caller will be
//     rejected.
//  2. Second, when the caller has successfully entered the queue, they try to acquire their per-key
//     semaphore. If this takes longer than the maximum queueing limit then the caller will be
//     dequeued and gets an error.
func (c *ConcurrencyLimiter) Limit(ctx context.Context, limitingKey string, f LimitedFunc) (interface{}, error) {
	span, ctx := tracing.StartSpanIfHasParent(
		ctx,
		"limiter.ConcurrencyLimiter.Limit",
		[]attribute.KeyValue{
			attribute.String("key", limitingKey),
		},
	)
	defer span.End()

	if c.currentLimit() <= 0 {
		return f()
	}

	sem := c.getConcurrencyLimit(limitingKey)
	defer c.putConcurrencyLimit(limitingKey)

	start := time.Now()

	if err := sem.acquire(ctx, limitingKey); err != nil {
		queueTime := time.Since(start)
		switch {
		case errors.Is(err, ErrMaxQueueSize):
			c.monitor.Dropped(ctx, limitingKey, sem.queueLength(), sem.inProgress(), queueTime, "max_size")
			return nil, structerr.NewResourceExhausted("%w", ErrMaxQueueSize).WithDetail(&gitalypb.LimitError{
				ErrorMessage: err.Error(),
				RetryAfter:   durationpb.New(0),
			})
		case errors.Is(err, ErrMaxQueueTime):
			c.monitor.Dropped(ctx, limitingKey, sem.queueLength(), sem.inProgress(), queueTime, "max_time")
			return nil, structerr.NewResourceExhausted("%w", ErrMaxQueueTime).WithDetail(&gitalypb.LimitError{
				ErrorMessage: err.Error(),
				RetryAfter:   durationpb.New(0),
			})
		default:
			c.monitor.Dropped(ctx, limitingKey, sem.queueLength(), sem.inProgress(), queueTime, "other")
			return nil, fmt.Errorf("unexpected error when dequeueing request: %w", err)
		}
	}
	defer sem.release()

	c.monitor.Enter(ctx, sem.inProgress(), time.Since(start))
	defer c.monitor.Exit(ctx)
	return f()
}

# Request limiting in Gitaly

In the GitLab ecosystem, Gitaly is the service that is at the bottom of the
stack for Git data access. This means that when there is a surge of
requests to retrieve or change a piece of Git data, the I/O happens in Gitaly.
This can lead to Gitaly being overwhelmed due to system resource exhaustion
because all Git access goes through Gitaly.

If there is a surge of traffic beyond what Gitaly can handle, Gitaly should
be able to push back on the client calling. Gitaly shouldn't subserviently agree
to process more than it can handle.

We employ concurrency limiting as our primary backpressure mechanism in Gitaly.
