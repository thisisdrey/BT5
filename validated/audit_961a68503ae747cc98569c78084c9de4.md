## Title
Single-step account permission (ownership) transfer allows permanent loss of account control - (`actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
The `AccountPermissionUpdateContract` / `AccountPermissionUpdateActuator` is java-tron's analog to Solidity `Ownable.transferOwnership`: it lets the current account authority (Owner permission signer) overwrite the `owner`, `witness` and `active` permissions of an account in a single atomic step. There is no two-step "propose and accept" flow, and the new permission's key addresses are only checked for address-format validity, not for control by any real key holder.

### Finding Description
`AccountPermissionUpdateActuator.execute()` directly calls `AccountCapsule.updatePermissions(owner, witness, actives)` and persists it, replacing the account's `OwnerPermission` unconditionally: [1](#0-0) 

`AccountCapsule.updatePermissions` simply overwrites the owner/witness/active permission fields with whatever was supplied in the contract, with no confirmation step from the new key holder(s): [2](#0-1) 

`validate()`/`checkPermission()` only verify structural validity of the new `Permission` (key count, threshold sum, distinct addresses, `DecodeUtil.addressValid`), never that the specified key addresses are reachable/controlled by anyone: [3](#0-2) 

The transaction is authorized by the current Owner permission (default `permission_id = 0`), exactly analogous to the "current authority" in the Ethereum report, since `TransactionCapsule.validateSignature` resolves the permission via `contract.getPermissionId()` (0 = Owner) and requires the current owner threshold to be met before this contract executes: [4](#0-3) 

This contract is reachable directly from an unprivileged HTTP API request via `AccountPermissionUpdateServlet`, which simply forwards the raw request-supplied JSON into an `AccountPermissionUpdateContract` and returns a transaction for signing: [5](#0-4) 

### Impact Explanation
If the new `owner` permission is set to key(s)/threshold that cannot actually produce valid signatures (e.g. a typo'd address, an address with no known private key, or an unreachable threshold configuration), the account's Owner permission becomes permanently unusable. Since Owner permission is required to update permissions again (`permissionId = 0` by default) and there is no fallback or recovery/accept mechanism, this results in permanent loss of control over the account and, transitively, of all TRX balance, TRC10/TRC20 assets, frozen/staked resources and voting rights tied to that account — a permanent freezing of funds analogous to the reported Solidity issue.

### Likelihood Explanation
Because the operation is single-step and irreversible with no confirmation from the new permission holder, any misconfiguration (client bug, malformed API payload, or user error when constructing/broadcasting the transaction) instantly and irrevocably locks the account. There is no signature-based "accept" step to catch such mistakes before the destructive state change is committed.

### Recommendation
Introduce a two-step permission/ownership update flow: first record the pending permission change (e.g., a `pendingOwnerPermission` field or dedicated proposal state), and only commit it once a transaction signed under the *new* permission's keys explicitly accepts/confirms it. Alternatively, require a "proof-of-control" signature from at least one key in the newly proposed Owner permission as part of `AccountPermissionUpdateContract` validation before `execute()` commits the change.

### Proof of Concept
1. Owner account `A` (with Owner permission threshold satisfied) submits an `AccountPermissionUpdateContract` transaction via `wallet/accountpermissionupdate` HTTP endpoint (`AccountPermissionUpdateServlet`), setting `owner.keys = [{address: X, weight: 1}], threshold: 1`, where `X` is an address for which no one holds the private key (e.g., a mistyped or unrelated address).
2. `AccountPermissionUpdateActuator.validate()` passes because `X` is a structurally valid Tron address (`DecodeUtil.addressValid`) — no control check is performed.
3. `AccountPermissionUpdateActuator.execute()` calls `account.updatePermissions(...)`, overwriting `A`'s `OwnerPermission` to require signatures from `X`.
4. Account `A` can never again produce a transaction meeting the Owner permission threshold (no default fallback allows re-updating permissions), permanently locking `A`'s balance, staked TRX, voting power, and any assets/permissions tied to it. [6](#0-5)

  public void updatePermissions(Permission owner, Permission witness, List<Permission> actives) {
    Builder builder = this.account.toBuilder();

    owner = owner.toBuilder().setId(0).build();
    builder.setOwnerPermission(owner);
    if (witness != null && builder.getIsWitness()) {
      witness = witness.toBuilder().setId(1).build();
      builder.setWitnessPermission(witness);
    }

    builder.clearActivePermission();
    if (actives != null) {
      for (int i = 0; i < actives.size(); i++) {
        Permission permission = actives.get(i).toBuilder().setId(i + 2).build();
        builder.addActivePermission(permission);
      }
    }

    this.account = builder.build();
  }
