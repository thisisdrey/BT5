### Title
Dust transfers of deposit tokens can fill a victim's `MAX_TOKENS_PER_USER` slots and block deposits, borrows, and liquidations - (File: contracts/Pool.sol)

### Summary
Analogous to the Circles finding — where any unprivileged actor may perform net-zero token reshuffles that invalidate other users' pending operations — Metronome lets any EOA permissionlessly add entries to another account's `depositTokensOfAccount`/`debtTokensOfAccount` lists simply by calling `DepositToken.transfer(to_, dustAmount)` (or `deposit(amount_, onBehalfOf_)`). Because `Pool.addToDepositTokensOfAccount` enforces a hard cap of `MAX_TOKENS_PER_USER = 30` across deposit + debt tokens (`Pool.sol:143-148`), an attacker can cheaply fill a victim's remaining slots with dust balances of deposit tokens the victim does not hold, after which any operation that would add a *new* token to the victim's account reverts with `UserReachedMaxTokens`. The attacker can also front-run a victim's pending deposit/issue transaction to make it revert, mirroring the race-condition/griefing vector of the original report.

### Finding Description
The vulnerable invariant is liveness: a user must be able to deposit collateral, issue debt, and be liquidated without interference.

Relevant code paths:

- `Pool.sol:79` — `MAX_TOKENS_PER_USER = 30`.
- `Pool.sol:143-148` — `onlyIfAdditionWillNotReachMaxTokens` reverts when `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30`.
- `Pool.sol:216-220` — `addToDepositTokensOfAccount` applies that modifier and is callable by any registered deposit token.
- `Pool.sol:204-208` — same for `addToDebtTokensOfAccount` via debt tokens.
- `DepositToken.sol:348-354` — `transfer` is permissionless; `_transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance goes from 0 to >0 (`DepositToken.sol:517-520`).
- `DepositToken.sol:211-237` — `deposit(amount_, onBehalfOf_)` mints to an arbitrary beneficiary, likewise adding the token to `onBehalfOf_`'s list.

Attack steps (all unprivileged):

1. Attacker deposits dust (1 wei, minus deposit fee) into each registered `DepositToken`, or acquires dust balances by depositing once and splitting via `transfer`.
2. Attacker calls `DepositToken.transfer(victim, 1)` for every deposit token the victim does not yet hold. Each call pushes that token into `depositTokensOfAccount[victim]`.
3. Once `debtTokensOfAccount.length(victim) + depositTokensOfAccount.length(victim) == 30`:
   - `DepositToken.deposit(_, victim)` / `mint` for any new collateral reverts inside `_mint → addToDepositTokensOfAccount` (`DepositToken.sol:486-488`).
   - `DebtToken` issuance/minting of a new synthetic for the victim reverts inside `addToDebtTokensOfAccount`.
   - `Pool.liquidate` → `DepositToken.seize` → `_transfer` reverts if the seized token is new to the recipient list accounting for the cap (relevant when the liquidator routes seizure through an account at the cap).
4. The attacker can repeat this indefinitely: whenever the victim frees a slot by transferring out a full dust balance, the attacker re-fills it with a different token's dust — a persistent, cheap griefing loop, exactly like the net-zero reshuffle front-running in the Circles report.

No modifier stops this: `transfer` has no `whenNotPaused`, no opt-in from the recipient, and `onlyIfAdditionWillNotReachMaxTokens` is enforced on the victim, not the sender. `SynthContext._msgSender` indirection does not change anything since the attacker calls via a normal EOA.

### Impact Explanation
- **Temporary freezing / blocking of position management**: the victim cannot add new collateral types nor mint new synthetic assets while the cap is saturated; recovery requires the victim to fully empty dust balances one by one (each removal only frees a slot the attacker can re-take in the same block via front-running, on chains where ordering favors the attacker).
- **Liquidation disruption**: `seize` uses the same `_transfer` path, so a liquidation that would introduce a new deposit token to an already-capped recipient reverts, delaying bad-debt cleanup.
- **Gas-grievance asymmetry**: each attack transaction costs one ERC-20-style transfer, while the victim's multi-step deposit/issue/liquidation transactions revert late, wasting gas — the same asymmetry highlighted in the Circles report.

### Likelihood Explanation
- Requires only an EOA, dust amounts of each registered deposit token's underlying, and no approvals, oracle manipulation, or privileged role.
- Feasibility scales with the number of registered deposit tokens: a pool with few collaterals cannot single-handedly reach 30, but combined with the victim's existing tokens the margin shrinks; pools listing many deposit tokens (the design anticipates up to 30 per user) are directly exploitable.
- Persistent re-griefing is realistic on chains where the attacker can front-run/back-run the victim's cleanup transactions (e.g., via a contract that bundles "empty dust" detection and re-fill).
- Impact is bounded: it is griefing/liveness rather than direct theft, consistent with Medium severity, matching the source finding.

### Recommendation
- Make list membership opt-in or attacker-proof: e.g., only add to `depositTokensOfAccount` when the token becomes *meaningfully* held, or allow `transfer` recipients to be excluded from the cap accounting until they interact.
- Alternatively, exempt pure inbound transfers from `onlyIfAdditionWillNotReachMaxTokens` and instead let `depositTokensOfAccount` grow, enforcing the cap only on actions the user initiates (`deposit`, `issue`), so third parties cannot push a user into the revert state.
- Provide a `sweepDust`/self-service removal path or allow `removeFromDepositTokensOfAccount` to be triggered by the account owner for zero-value bookkeeping entries, so recovery is a single cheap transaction the attacker cannot race profitably.
- If keeping the current design, document the dust-griefing vector and consider raising `MAX_TOKENS_PER_USER` above the maximum feasible attacker-fillable set (i.e., greater than the number of registered deposit tokens + realistic debt tokens).

### Proof of Concept
Hardhat fork/test sketch:

```ts
// setup: pool with N registered DepositTokens dt1..dtN (N chosen so
// existingVictimTokens + N >= 30), victim holds some debt tokens already.

// 1) Attacker obtains dust of each deposit token
for (const dt of depositTokens) {
  await underlying(dt).approve(dt.address, DUST);
  await dt.deposit(DUST, attacker.address);          // mints dust msToken
}

// 2) Fill victim's token list
const slots = 30 - (await pool.getDepositTokensOfAccount(victim)).length
             - (await pool.getDebtTokensOfAccount(victim)).length;
for (let i = 0; i < slots; i++) {
  await depositTokens[i].connect(attacker).transfer(victim, 1); // +1 slot each
}
expect(await pool.getDepositTokensOfAccount(victim)).to.have.lengthOf(/* capped */);

// 3) Victim can no longer deposit a NEW collateral type
await expect(
  newDepositToken.connect(victim).deposit(amount, victim)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// 4) Victim can no longer issue a NEW synthetic (debt token add also capped)
await expect(
  pool.connect(victim).issue(newSynthetic, amount)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// 5) Front-running persistence: after victim empties one dust token to free a slot,
//    attacker re-fills it in the same block with another token's dust.
await depositTokens[0].connect(victim).transfer(attacker, await depositTokens[0].balanceOf(victim));
await depositTokens[K].connect(attacker).transfer(victim, 1); // slot re-taken
```

Reproduction notes: use a fork of a deployed pool (e.g., `deployments/optimism/Pool.json` addresses) or extend `test/Pool.test.ts`'s `addToDepositTokensOfAccount` suite (`test/Pool.test.ts:1386-1416`) which already demonstrates the `UserReachedMaxTokens` revert — the missing piece is showing the attacker can trigger it for a *victim* account via plain `DepositToken.transfer`/`deposit(onBehalfOf_)`, which the code permits unconditionally.
