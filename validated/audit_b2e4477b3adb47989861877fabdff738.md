### Title
Revoked StackerDB signers retain write authority because reconfiguration is skipped when the new signer set is empty - (File: `stackslib/src/net/stackerdb/mod.rs`)

### Summary
`PeerNetwork::refresh_stacker_db_configs` / `StackerDBs::create_or_reconfigure_stackerdbs` re-evaluate a StackerDB's authorized signer set from its controlling smart contract on every refresh, but the code only pushes that new signer set down into the persisted slot table (`reconfigure_stackerdb`) when the newly computed signer list is non-empty. This mirrors the Hats Protocol bug class: an authoritative source of truth (the on-chain signer set / "toggle") changes, but the change is never synced to the local persisted state that actually gates write authorization, so writes continue to be validated against the stale, no-longer-authoritative signer.

### Finding Description
`create_or_reconfigure_stackerdbs` computes `new_config` from the contract (or falls back to `StackerDBConfig::noop()`, which also has empty `signers`), and only calls `reconfigure_stackerdb` (which rewrites slot ownership and, per `shrink_stackerdb`, deletes slots beyond the new total count) under this guard: [1](#0-0) 

```
} else if (new_config != stackerdb_config && !new_config.signers.is_empty())
    || (new_config == stackerdb_config
        && new_config.signers.len() != self.get_slot_versions(&stackerdb_contract_id)?.len())
{
    // only reconfigure if the config has changed
    ...
}
```

If the controlling contract legitimately updates its signer set to be empty (e.g., all current signers are removed/rotated out for a cycle), `new_config.signers.is_empty()` is `true`, so the `!new_config.signers.is_empty()` clause is `false` and the whole condition is `false` — `reconfigure_stackerdb` is never invoked. Yet `new_stackerdb_configs.insert(stackerdb_contract_id, new_config)` happens unconditionally afterward: [2](#0-1) 

So the in-memory `self.stacker_db_configs` now reflects "authorized signers = []" while the on-disk slot table (`chunks`) still contains the old signer/slot assignment from before revocation. `reconfigure_stackerdb` in `db.rs`, if it *were* called, would correctly wipe the now-unauthorized slots via `shrink_stackerdb(stackerdb_id, 0)`: [3](#0-2) 

But because the guard prevents that call, the stale `chunks` rows (with the old `signer` address) remain fully live. Chunk-write authorization never consults the in-memory `StackerDBConfig.signers`; it consults the persisted per-slot `SlotValidation.signer` fetched straight from the DB: [4](#0-3) 

and similarly for unsolicited/gossiped chunk validation: [5](#0-4) 

Both `try_replace_chunk` and `validate_received_chunk` verify the chunk signature against `slot_validation.signer` / `get_slot_signer`, which is the *stale, unrevoked* signer — never the current, correctly-empty authorized set. This is exactly the Hats "toggle changed but never synced to local state" pattern: the authoritative source (the contract-derived signer set) went to "revoked," but the mechanism whose job is to sync that (`reconfigure_stackerdb`) is skipped specifically because the new state is empty, so the node's actual enforcement point silently keeps honoring the old, revoked authority indefinitely.

### Impact Explanation
A signer whose authorization has been revoked on-chain (signer set now empty for a StackerDB replica) can continue to submit validly-signed chunks that are accepted and stored by every node that hasn't otherwise cleared its `chunks` table, and those chunks are then relayed/gossiped as legitimate StackerDB content (`process_stacker_db_chunks` / `process_pushed_stacker_db_chunks` -> event dispatchers/consumers of StackerDB data). This is an unauthorized write to replicated network state that keeps propagating stale/forged-as-current data network-wide, matching the "unauthenticated/unauthorized write to state or StackerDB" / "network-wide propagation of forged data" Critical impact category, without requiring any privileged key beyond the previously-valid (now revoked) signer key the attacker already possesses.

### Likelihood Explanation
This does not require volumetric traffic or any secret beyond a key that was legitimately a signer at some point. It only requires: (1) the controlling contract's signer-slot function to return an empty list (a normal, reachable state transition, e.g., a reward cycle with zero configured signers for that contract, or any other legitimate business logic that empties the list), and (2) the previously-valid signer to keep signing and pushing chunks with a StackerDB message the node accepts unsolicited. Both are ordinary, remote, unprivileged actions.

### Recommendation
Do not gate `reconfigure_stackerdb` on `!new_config.signers.is_empty()`. The condition should trigger a reconfiguration whenever `new_config != stackerdb_config`, regardless of whether the new signer list is empty, distinguishing the "transient eval failure -> noop()" fallback path (which should preserve prior config/state, not silently swap in an authoritative-looking empty config) from a genuine, successfully-evaluated empty signer set (which should be enforced immediately by wiping/shrinking the slot table). Concretely: only suppress reconfiguration when the *evaluation itself failed* (i.e., use the `Result` from `StackerDBConfig::from_smart_contract` directly, rather than collapsing failure and "legitimately empty" into the same `signers.is_empty()` signal).

### Proof of Concept
1. Node has an active StackerDB replica for contract `C` with signer `S` holding slot 0 (`create_stackerdb` executed previously).
2. Governance/contract logic for `C` legitimately updates `stackerdb-get-signer-slots` to return an empty list (revoking `S`).
3. On the next `refresh_stacker_db_configs` call (`stackslib/src/net/p2p.rs:4465-4478`), `StackerDBConfig::from_smart_contract` succeeds and returns `new_config.signers = []`.
4. In `create_or_reconfigure_stackerdbs`, since `new_config.signers.is_empty()`, the reconfigure branch is skipped; `self.stacker_db_configs[C]` is updated in memory to the empty-signers config, but the on-disk `chunks` table for `C` still has slot 0 owned by `S`.
5. `S` sends a `StackerDBPushChunk` (or is polled and answers a `StackerDBGetChunk`) for slot 0 with a validly-signed chunk and an incremented `slot_version`.
6. `PeerNetwork::validate_received_chunk` fetches the signer via `self.stackerdbs.get_slot_signer(C, 0)`, which still returns `S` (unchanged DB row), the signature verifies, and the chunk is accepted and stored/relayed — despite `S` having zero authority under the current, correctly-evaluated contract state.

    /// Update a database's storage slots, e.g. from new configuration state in its smart contract.
    /// Chunk data for slots that no longer exist will be dropped.
    /// Newly-created slots will be instantiated with empty data.
    /// If the address for a slot changes, then its data will be dropped.
    pub fn reconfigure_stackerdb(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slots: &[(StacksAddress, u32)],
    ) -> Result<(), net_error> {
        let stackerdb_id = self.get_stackerdb_id(smart_contract)?;
        let mut total_slots_read = 0u32;
        for (principal, slot_count) in slots.iter() {
            total_slots_read =
                total_slots_read
                    .checked_add(*slot_count)
                    .ok_or(net_error::OverflowError(
                        "Slot count exceeeds u32::MAX".to_string(),
                    ))?;
            let slots_before_principal = total_slots_read - slot_count;
            for cur_principal_slot in 0..*slot_count {
                let slot_id = slots_before_principal + cur_principal_slot;
                if let Some(existing_validation) =
                    self.get_slot_validation(smart_contract, slot_id)?
                {
                    // this slot already exists.
                    if existing_validation.signer == *principal {
                        // no change
                        continue;
                    }
                }

                debug!("Reset slot {} of {}", slot_id, smart_contract);

                // new slot, or existing slot with a different signer
                let qry = "INSERT OR REPLACE INTO chunks (stackerdb_id,signer,slot_id,version,write_time,data,data_hash,signature) VALUES (?1,?2,?3,?4,?5,?6,?7,?8)";
                let mut stmt = self.sql_tx.prepare(qry)?;
                let args = params![
                    stackerdb_id,
                    principal.to_string(),
                    slot_id,
                    NO_VERSION,
                    0,
                    vec![],
                    Sha512Trunc256Sum([0u8; 32]),
                    MessageSignature::empty(),
                ];

                stmt.execute(args)?;
            }
        }
        debug!("Shrink {} to {} slots", smart_contract, total_slots_read);
        self.shrink_stackerdb(stackerdb_id, total_slots_read)?;
        Ok(())
    }
