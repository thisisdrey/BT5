Based on the investigation, the Go standard library (`src/net/http/fs.go`, `src/archive/zip`, `src/cmd/go/internal/modfetch`, `src/net/http/cgi`) already contains hardened, tested defenses against the exact bug class described in the gatsby-plugin-sharp advisory (unauthenticated HTTP path-traversal reading arbitrary files):

- `net/http`'s file-serving stack cleans and rejects traversal: `ServeFile`/`ServeFileFS` reject `..` via `containsDotDot` [1](#0-0)  and `fileHandler.ServeHTTP` always applies `path.Clean` before calling `serveFile` [2](#0-1) .
- `archive/zip` explicitly guards against "zip slip" traversal (`CVE-2021-27919`) via `filepath.IsLocal` checks and `ErrInsecurePath`, with regression tests for that CVE [3](#0-2) [4](#0-3) .
- `cmd/go/internal/modfetch` double-checks that all module zip entries have the expected `module@version/` prefix before extraction [5](#0-4) .
- `net/http/cgi`'s `PATH_INFO`/`SCRIPT_NAME` are derived from `req.URL.Path` for environment variables passed to the CGI subprocess, not used to open files directly on the Go side [6](#0-5) .
- Even the test/dev-only `vcweb` auth handler relies on `http.Dir`/`fs.Open`, which internally cleans paths, and additionally rejects dot-prefixed names [7](#0-6) .

None of these exhibit the missing-sanitization pattern from the report (raw, unsanitized concatenation of an attacker-controlled URL path into a filesystem read). I did not find a reachable, unfixed analog matching the required primitive (unauthenticated HTTP path traversal to file read) in production Go stdlib code within this repo.

func containsDotDot(v string) bool {
	if !strings.Contains(v, "..") {
		return false
	}
	for ent := range strings.FieldsFuncSeq(v, isSlashRune) {
		if ent == ".." {
			return true
		}
	}
	return false
}
