Based on my investigation, I found a concrete resource-exhaustion analog in the JSON-RPC log filter subsystem that mirrors CVE-2022-2906's bug class (unauthenticated/lightly-authenticated client gradually eroding memory until the process crashes, with the attacker needing to restart the attack after a crash).

### Title
Unbounded per-filter log accumulation in JSON-RPC `eth_newFilter`/`handleLogsFilter` enables remote memory-exhaustion DoS - ([File: framework/src/main/java/org/tron/core/services/jsonrpc/TronJsonRpcImpl.java])

### Summary
An anonymous JSON-RPC client can call `eth_newFilter` with broad/empty address and topic criteria to create a "match everything, track future blocks" filter. Each subsequent block's matching logs are appended to that filter's internal `LinkedBlockingQueue` with no upper bound on queue size. If the client never calls `eth_getFilterChanges`/`eth_getLogs` to drain it, the queue grows without limit for the lifetime of the filter (up to the 5-minute expiry window), and this can be repeated up to `maxLogFilterNum` (default 20,000) times concurrently, per full-node and per-solidity map.

### Finding Description
`eth_newFilter` only rate-limits the *number* of filters via `maxLogFilterNum`, and does not enforce `maxBlockRange` at creation time (`checkBlockRange=false`), so a filter that "tracks future blocks" (`toBlock = Long.MAX_VALUE`) with empty address/topics is trivially created: [1](#0-0) 

Every time a new block is processed, `handleLogsFilter` matches logs against every live filter and unconditionally appends all matches to that filter's queue via `logFilterAndResult.getResult().addAll(localResults)`, with no cap on the accumulated size of an individual filter's result queue: [2](#0-1) 

`LogFilterAndResult` (and `FilterResult`/`BlockFilterAndResult`) back the per-filter results with an unbounded `LinkedBlockingQueue`: [3](#0-2) [4](#0-3) 

The only bound is the filter's 5-minute (`EXPIRE_SECONDS`) expiry, but that is a fixed time window, not a size cap — a busy chain can accumulate a very large amount of log data within that window per filter, and the attacker can create up to `maxLogFilterNum` such filters simultaneously (separately for `eventFilter2ResultFull` and `eventFilter2ResultSolidity`): [5](#0-4) 

This is directly analogous to ALPINE-CVE-2022-2906 (BIND `named` gradual memory exhaustion from unauthenticated queries): here, an unauthenticated JSON-RPC caller creates many long-lived, broad, unpolled filters, and normal chain activity (or attacker-driven low-cost transactions emitting events) causes the node's heap to grow until the JVM OOMs and the node process crashes, matching the "node crash or halt" / "API the node can no longer serve" acceptance criteria.

### Impact Explanation
An anonymous client with only JSON-RPC access (no signed transaction, no special privilege) can drive a full node or solidity node into an `OutOfMemoryError`, crashing the node process (denial of service). Because the queue growth compounds with the number of concurrently open filters (up to `maxLogFilterNum`, default 20,000, independently for full-node and solidity endpoints) and with per-block log volume, the exhaustion can occur well within the 5-minute expiry window, and — like the BIND CVE — the attacker only needs to reissue `eth_newFilter` calls after a crash/restart to repeat the attack.

### Likelihood Explanation
Requires only that `node.jsonrpc.httpFullNodeEnable` (or the solidity/PBFT equivalent) is turned on, which is a common production configuration for nodes exposing Ethereum-compatible RPC to dApps/wallets. No authentication, signature, or on-chain cost is required to call `eth_newFilter` or to simply withhold polling — this is purely an HTTP/JSON-RPC request pattern.

### Recommendation
Enforce a maximum size on each `LogFilterAndResult`/`BlockFilterAndResult` result queue (e.g., drop oldest entries or reject/expire the filter once a configurable cap is reached), and/or enforce `maxBlockRange`/a "must specify bounded range or actively poll" policy at `eth_newFilter` creation time rather than only at `eth_getLogs`/`eth_getFilterLogs` time.

### Proof of Concept
1. Enable `node.jsonrpc.httpFullNodeEnable = true` on a full node.
2. As an anonymous client, repeatedly call `eth_newFilter({})` (empty `FilterRequest`, no address/topics, no `toBlock`) up to `maxLogFilterNum` times to open many long-lived "track all future logs" filters.
3. Never call `eth_getFilterChanges`/`eth_getLogs`/`eth_uninstallFilter` on any of them.
4. As normal chain activity (or attacker-submitted low-fee transactions emitting contract events) produces blocks, `handleLogsFilter` keeps appending matched `LogFilterElement`s into every open filter's unbounded queue via `logFilterAndResult.getResult().addAll(localResults)`, growing heap usage until the JVM throws `OutOfMemoryError` and the node process crashes.

  private void processLogFilterEntry(
      Map.Entry<String, LogFilterAndResult> entry,
      Map<String, LogFilterAndResult> eventFilterMap,
      LogsFilterCapsule logsFilterCapsule) {
    LogFilterAndResult logFilterAndResult = entry.getValue();
    if (logFilterAndResult.isExpire()) {
      eventFilterMap.remove(entry.getKey());
      return;
    }

    long blockNumber = logsFilterCapsule.getBlockNumber();
    long fromBlock = logFilterAndResult.getLogFilterWrapper().getFromBlock();
    long toBlock = logFilterAndResult.getLogFilterWrapper().getToBlock();
    if (!(fromBlock <= blockNumber && blockNumber <= toBlock)) {
      return;
    }

    if (logsFilterCapsule.getBloom() != null && !logFilterAndResult.getLogFilterWrapper()
        .getLogFilter().matchBloom(logsFilterCapsule.getBloom())) {
      return;
    }

    LogFilter logFilter = logFilterAndResult.getLogFilterWrapper().getLogFilter();
    List<LogFilterElement> elements =
        LogMatch.matchBlock(logFilter, blockNumber, logsFilterCapsule.getBlockHash(),
            logsFilterCapsule.getTxInfoList(), logsFilterCapsule.isRemoved());

    List<LogFilterElement> localResults = new ArrayList<>(elements.size());
    for (LogFilterElement element : elements) {
      LogFilterElement cachedElement;
      try {
        // compare with hashcode() first, then with equals(). If not exist, put it.
        cachedElement = logElementCache.get(element, () -> element);
      } catch (ExecutionException e) {
        logger.error("Getting/loading LogFilterElement from cache fails", e); // never happen
        cachedElement = element;
      }
      localResults.add(cachedElement);
    }
    logFilterAndResult.getResult().addAll(localResults);

public class LogFilterAndResult extends FilterResult<LogFilterElement> {

  @Getter
  private final LogFilterWrapper logFilterWrapper;

  public LogFilterAndResult(FilterRequest fr, long currentMaxBlockNum, Wallet wallet)
      throws JsonRpcInvalidParamsException {
    // eth_newFilter, no need to check block range
    this.logFilterWrapper = new LogFilterWrapper(fr, currentMaxBlockNum, wallet, false);
    result = new LinkedBlockingQueue<>();
    this.updateExpireTime();
  }

  @Override
  public void add(LogFilterElement logFilterElement) {
    result.add(logFilterElement);

public abstract class FilterResult<T> {

  private long expireTimeStamp;

  @Getter
  protected BlockingQueue<T> result;

  public void updateExpireTime() {
    expireTimeStamp = System.currentTimeMillis() + TronJsonRpcImpl.EXPIRE_SECONDS * 1000;
  }

  public boolean isExpire() {
    return expireTimeStamp < System.currentTimeMillis();
  }

  public abstract void add(T t);

  public abstract List<T> popAll();
}
