## Analysis

The reported bug class — an actuator/function that appends to a persistent array on every user-triggered call with no cap on array length, causing unbounded storage/gas growth — maps cleanly onto the legacy `DelegatedResourceAccountIndexCapsule.toAccounts` / `fromAccounts` lists in java-tron's freeze/delegate-resource actuator.

### Title
Unbounded Growth of DelegatedResourceAccountIndex `toAccounts`/`fromAccounts` List via Repeated FreezeBalanceContract Delegations - (File: `actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java`)

### Summary
`FreezeBalanceActuator.delegateResource()` appends a new entry to a single account's `DelegatedResourceAccountIndexCapsule` (`toAccountsList` on the delegator, `fromAccountsList` on the receiver) every time a `FreezeBalanceContract` with a distinct receiver address is executed, and the only de-duplication is a linear `.contains()` check — there is no limit on the total number of distinct entries the list can hold. This is functionally identical to the `withdrawRequests.push(...)` pattern flagged in the external report: a broadcastable transaction unconditionally grows a repeated field with no maximum-size enforcement.

### Finding Description
In the legacy (pre-"delegate optimization") code path, delegating resources appends addresses without any cap: [1](#0-0) 

Any signed `FreezeBalanceContract` transaction (an unprivileged, ordinary account operation reachable by any transaction broadcaster) that sets a new, distinct `receiver_address` and calls `delegateResource()` triggers `ownerIndexCapsule.addToAccount(...)` and `receiverIndexCapsule.addFromAccount(...)`: [2](#0-1) 

Each `DelegatedResourceAccountIndexCapsule` is stored as a single protobuf value in `DelegatedResourceAccountIndexStore`, keyed by address; it is not partitioned per delegation relationship. Because de-duplication is only a linear membership check on the growing list itself (`toAccountsList.contains(...)`), an attacker who repeatedly freezes small balances (or the network minimum) to a large number of distinct freshly-generated receiver addresses can force the `toAccountsList` (or the `fromAccountsList` on the receiver side, symmetrically) to grow without bound. There is no analogous size check comparable to `UnfreezeBalanceV2Actuator.UNFREEZE_MAX_TIMES` (used for the newer `UnFreezeV2` list) or `MAX_VOTE_NUMBER` (used for votes) — both of which java-tron *does* enforce for other repeated-field growth vectors, showing this class of bug is otherwise recognized and mitigated elsewhere in the codebase but missed here.

The affected capsule is read and fully deserialized on every subsequent freeze/unfreeze/delegate operation involving that address, and is also served in full by public query endpoints (`GetDelegatedResourceAccountIndexServlet`, `Wallet.getDelegatedResourceAccountIndex`, and the corresponding gRPC service methods), which are reachable by any anonymous HTTP/gRPC client: [3](#0-2) 

### Impact Explanation
An attacker can cheaply and repeatedly submit `FreezeBalanceContract` transactions to distinct receiver addresses (which cost only the resource-freezing amount, no separate fee), causing a single account's `DelegatedResourceAccountIndexCapsule` to accumulate an arbitrarily large `toAccountsList`/`fromAccountsList`. This:
- Increases the cost (CPU/serialization time and I/O) of every subsequent `FreezeBalanceActuator`/`UnfreezeBalanceActuator` execution touching that address, since the full capsule must be deserialized, mutated, and re-serialized on each call.
- Increases the response size/latency of the public `getDelegatedResourceAccountIndex` API for that address, degrading node query-serving capability for any client querying that account — this is the "API the node can no longer serve efficiently" class of impact.
- Because bandwidth for the transaction itself can be paid from free bandwidth allowances, the attack has minimal ongoing cost to the attacker while imposing quadratic-ish read/write costs on the node over time.

### Likelihood Explanation
Likelihood is moderate: this legacy delegation index path (`supportAllowDelegateOptimization() == false`) is the default/original behavior and is only bypassed once the committee activates the delegate-optimization proposal on a given network; on any network (mainnet history, private/test chains, or before the proposal is active) it is directly reachable by any account holder submitting ordinary `FreezeBalanceContract` transactions with a `receiver_address` — no special privilege required.

### Recommendation
Add an explicit maximum-size check (analogous to `UnfreezeBalanceV2Actuator.UNFREEZE_MAX_TIMES` or `VoteWitnessActuator.MAX_VOTE_NUMBER`) on `toAccountsList`/`fromAccountsList` length before calling `addToAccount`/`addFromAccount` in `FreezeBalanceActuator.delegateResource()`, rejecting the transaction in `validate()` once a configurable per-account delegation-index size limit is reached.

### Proof of Concept
1. Account `A` freezes a minimal `frozen_balance` (e.g., 1 drop above minimum) via `FreezeBalanceContract` with `resource = BANDWIDTH` and `receiver_address = R1` (a fresh address). This triggers `delegateResource()`, adding `R1` to `A`'s `toAccountsList`.
2. Repeat step 1 with new receiver addresses `R2, R3, …, Rn` (each freshly generated, so `.contains()` never short-circuits).
3. After `n` iterations, `A`'s `DelegatedResourceAccountIndexCapsule.toAccountsList` contains `n` entries with no upper bound enforced anywhere in `FreezeBalanceActuator.validate()`/`execute()`.
4. Query `GetDelegatedResourceAccountIndex` for address `A` — the response now contains all `n` entries, and every future freeze/unfreeze/delegate call touching `A` must deserialize/reserialize the full growing list.

  public void addFromAccount(ByteString fromAccount) {
    this.delegatedResourceAccountIndex = this.delegatedResourceAccountIndex.toBuilder()
        .addFromAccounts(fromAccount)
        .build();
  }

  public void removeFromAccount(ByteString fromAccount) {
    if (getFromAccountsList().contains(fromAccount)) {
      List<ByteString> fromList = new ArrayList<>(getFromAccountsList());
      fromList.remove(fromAccount);
      setAllFromAccounts(fromList);
    }
  }

  public List<ByteString> getToAccountsList() {
    return this.delegatedResourceAccountIndex.getToAccountsList();
  }

  public void setAllToAccounts(List<ByteString> toAccounts) {
    this.delegatedResourceAccountIndex = this.delegatedResourceAccountIndex.toBuilder()
        .clearToAccounts()
        .addAllToAccounts(toAccounts)
        .build();
  }

  public void addToAccount(ByteString toAccount) {
    this.delegatedResourceAccountIndex = this.delegatedResourceAccountIndex.toBuilder()

        .build();
  }
