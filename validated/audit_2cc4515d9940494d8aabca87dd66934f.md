### Title
`remove_account` fails to purge receipt-processing state (`ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, `DataIdToYieldId`), allowing state to outlive account deletion - ([File: core/store/src/utils/mod.rs])

### Summary
`remove_account` (`core/store/src/utils/mod.rs:505-575`) only clears `TrieKey::Account`, `TrieKey::ContractCode`, `TrieKey::AccessKey`/gas-key-nonce entries, and `TrieKey::ContractData`. It never iterates or removes the receipt-bookkeeping key families that are also account-scoped, leaving stale trie entries after `DeleteAccount` is processed.

### Finding Description
Reading `remove_account` line by line: it issues `state_update.remove(TrieKey::Account{..})` and `TrieKey::ContractCode{..}` directly [1](#0-0) , then iterates the access-key prefix to remove `AccessKey`/`gas_key_nonce` rows [2](#0-1) , then iterates the contract-data prefix to remove `ContractData` rows [3](#0-2) . There is no iteration over the prefixes used for `ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, or `DataIdToYieldId`, all of which are also keyed by `account_id` in `TrieKey` (`core/primitives/src/trie_key.rs`).

Because a receipt can legitimately be "postponed" while waiting on input data from another cross-contract call, and `DeleteAccount` has no precondition requiring all in-flight/postponed receipts targeting the account to be resolved first, an account can be deleted while it still owns postponed-receipt bookkeeping rows in the trie. Those rows remain under the account-id prefix indefinitely. If the same `account_id` is later recreated (trivial for sub-accounts, which any unprivileged attacker who owns the parent account can delete and recreate at will), the new occupant's trie subtree still contains the old owner's `PostponedReceipt`/`ReceivedData`/`PendingDataCount`/promise-yield rows. When a still-in-flight data receipt destined for that account eventually arrives, receipt processing will read/decrement the stale `PendingDataCount` and, once satisfied, execute the stale `PostponedReceipt` against the *new* account's contract/state — receipt content that the new account owner never authorized and that was written under a completely different contract deployment/permission-set.

### Impact Explanation
This breaks the invariant that "state keyed by a name must not outlive that name's account," enabling execution of an old, unauthorized `PostponedReceipt` against a newly-created account context (authorization escalation across accounts/promises), and, depending on the receipt's actions, could corrupt the new account's state or (in the promise-yield case) resolve/callback logic that the current owner never triggered. This is scoped as the root-cause gap for the "survivor-execution escalation" class described in the audit.

### Likelihood Explanation
Precondition is cheap and fully attacker-controlled: create a sub-account, trigger a multi-promise/cross-contract call pattern (or `promise_yield_create`) so that `PendingDataCount`/`ReceivedData`/`PostponedReceipt`/promise-yield rows exist for it, delete the sub-account via `DeleteAccount` before all data receipts resolve, then recreate the sub-account name. No validator/operator access is needed — this uses only standard, unprivileged transaction actions (`CreateAccount`, `DeleteAccount`, contract calls). The remaining requirement — that an in-flight data receipt for the old postponed receipt still be en route when the account is recreated — is timing-dependent but achievable by delaying the dependent call/cross-shard data receipt relative to the delete+recreate sequence.

### Recommendation
Extend `remove_account` to also iterate and delete the account-scoped receipt-processing key families before returning: `ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, `DataIdToYieldId`, using the corresponding `trie_key_parsers`/prefix helpers, mirroring the pattern already used for access keys and contract data.

### Proof of Concept
Unit test in `core/store/src/utils/mod.rs` (or a runtime integration test):
1. For each of the 8 survivor `TrieKey` variants, write one row keyed to `account_id = "test.near"` directly via `TrieUpdate::set`.
2. Call `remove_account(&mut state_update, &"test.near".parse().unwrap())`.
3. Commit and iterate the full key range under the `test.near` account prefix.
4. Assert that each of the 8 rows is still present (test fails/asserts non-removal), while confirming `Account`, `ContractCode`, `AccessKey`/`GasKeyNonce`, and `ContractData` rows are correctly absent.
5. Follow-up integration test: create sub-account, generate a real postponed receipt (via two cross-contract promise dependency), delete the sub-account, recreate it, then let the pending data receipt arrive; assert the stale `PostponedReceipt` executes against the newly created account's state.
