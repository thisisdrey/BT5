### Title
Unbounded memory allocation in `run_http_request` via oversized non-chunked HTTP response - ([File: libsigner/src/http.rs])

### Summary
`run_http_request` reads an entire HTTP response into memory with `sock.read_to_end(&mut buf)` with no size cap, and `decode_http_body` performs `buf.to_vec()` for non-chunked bodies with zero enforcement of `MAX_MESSAGE_LEN`. A malicious node that a `StackerDBSession` connects to (or a MITM on that TCP session) can stream an arbitrarily large non-chunked response to force unbounded allocation and crash the signer process.

### Finding Description
The claimed equality — "bytes read into memory == a validated maximum length" — is broken. `run_http_request` in [1](#0-0)  calls `sock.read_to_end(&mut buf)` which reads until the peer closes the connection, with no cap on `buf`'s size at all. Once headers are parsed via `decode_http_response`, the remaining bytes are passed to `decode_http_body`, whose non-chunked branch is simply `buf.to_vec()` [2](#0-1) , with no length check against `MAX_MESSAGE_LEN`. Contrast this with the chunked branch, which does construct `HttpChunkedTransferReader::from_reader(ptr, MAX_MESSAGE_LEN.into())` [3](#0-2)  and thus enforces a bound — but that protection only applies when the response declares `Transfer-Encoding: chunked`. A response without that header (or with `Content-Length` set to a huge value, or simply an HTTP/1.1 response with `Connection: close` and no length framing) bypasses any bound during both the initial `read_to_end` and the subsequent `to_vec()`.

`run_http_request` is invoked from `StackerDBSession` (in `libsigner/src/session.rs`, used by `list_chunks`/`get_chunks`/`put_chunk` etc., via `crate::http::run_http_request`) [4](#0-3) , which connects out to a configured "host" — a Stacks node's RPC endpoint that the signer is pointed at. If that node is malicious or the connection is intercepted (MITM), the attacker fully controls the HTTP response bytes returned to the signer, with no signature, secret, or length verification gating the response body before it is buffered into memory.

### Impact Explanation
A single malicious/compromised counterparty (the node endpoint configured for `StackerDBSession`, or a MITM) can send a non-chunked HTTP response body of unbounded size, causing the signer process to allocate unbounded memory in `sock.read_to_end` and again in `buf.to_vec()`, leading to OOM and crash of the signer process. This is repeatable on every StackerDB RPC round-trip (`list_chunks`, `get_chunks`, `get_latest_chunks`, `put_chunk`), i.e., every time the signer talks to that node.

### Likelihood Explanation
The attacker must be the node endpoint the signer's `StackerDBSession` is configured to talk to, or capable of a MITM on that TCP connection — this is a plausible threat model since signer operators often point at third-party/relay nodes, and the connection is unauthenticated HTTP with no TLS/pinning enforced at this layer. No secrets or privileged roles are needed to serve an oversized response back to a client that connected to you. Attacker cost is trivial: hold open a TCP connection and stream bytes.

### Recommendation
Enforce a maximum response size in `run_http_request`, e.g., by reading with a bounded reader (cap total bytes read to `MAX_MESSAGE_LEN` plus header overhead) instead of unbounded `read_to_end`, and enforce `MAX_MESSAGE_LEN` in the non-chunked branch of `decode_http_body` by returning an error if `buf.len() > MAX_MESSAGE_LEN` before calling `to_vec()`.

### Proof of Concept
Rust test: spin up a `TcpListener` on localhost; in the accept handler, read the request, then write `HTTP/1.1 200 OK\r\nConnection: close\r\n\r\n` followed by, e.g., 500MB of arbitrary bytes with no `Transfer-Encoding` or `Content-Length` header (or a `Content-Length` far exceeding `MAX_MESSAGE_LEN`), streamed in a loop before closing. Call `run_http_request` against this listener from a `TcpStream` and observe that the process memory grows unbounded / OOM-kills instead of `run_http_request` returning an error once bytes read exceed `MAX_MESSAGE_LEN`. Assertion point: `sock.read_to_end(&mut buf)` at [5](#0-4)  and `buf.to_vec()` at [6](#0-5)  should be bounded but are not.
