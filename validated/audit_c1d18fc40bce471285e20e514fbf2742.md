### Title
Unconditional relayer-fee payout before nonce consumption in `WalletContract::rlp_execute`'s address-check path enables repeated draining of an ETH-implicit account's NEAR balance - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
In the NEP-518 Wallet Contract (used by every ETH-implicit account on NEAR), `inner_rlp_execute` unconditionally dispatches a relayer-fee `Transfer` promise from the wallet's own balance *before* it is known whether the underlying transaction is valid, while nonce consumption for this specific code path is deliberately deferred to a later async callback and is *never* performed when that callback determines the relayer's `target` was invalid. This mirrors the reported bug class: a value-transferring external effect is emitted before the state that should gate/limit it (the nonce) is updated, allowing the same signed message to be resubmitted indefinitely to keep re-triggering the payout.

### Finding Description
`rlp_execute` → `inner_rlp_execute` (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:330-410`) parses the user's RLP-encoded Ethereum transaction and, for the `EOABaseTokenTransfer`/`ERC20Transfer` emulation kinds with `address_check: Some(_)`, explicitly **skips incrementing `nonce`**: [1](#0-0) 

Immediately after, if the fee is non-zero, it unconditionally creates a `Transfer` promise from the wallet (`current_account_id`) to the caller (`context.predecessor_account_id`) for the relayer fee, *before* the address-registrar lookup that determines transaction validity has even started: [2](#0-1) 

The actual validity check happens later, asynchronously, in `address_check_callback` (a separate receipt). If the registrar reports that the target address is already associated with an existing named account, and the caller (relayer) is not the account itself, the callback returns an error **without banning the relayer and without incrementing the nonce**, by explicit design comment: [3](#0-2) 

Because the nonce was never advanced by this failing path, the exact same signed transaction bytes remain valid indefinitely (nonce check in `validate_tx_relayer_data` still matches `expected_nonce`): [4](#0-3) 

Since the wallet's built-in `has_in_flight_tx` guard only prevents *concurrent* in-flight executions, not *repeated sequential* ones, any account (acting as "relayer") can call `rlp_execute(target, tx_bytes_b64)` with the same previously-observed valid signed transaction over and over, and each call unconditionally re-dispatches the relayer-fee transfer taken from the wallet's own NEAR balance, while the address-check always fails the same way and the nonce never moves.

### Impact Explanation
This allows an attacker who has observed one signed relayer transaction whose Ethereum `to` address coincides with a registered NEAR named account (a scenario the registrar mechanism exists specifically to detect, so not a rare edge case) to repeatedly resubmit that transaction as a "relayer" and collect the encoded relayer fee from the victim wallet's own balance every time, draining the ETH-implicit account's NEAR balance without ever needing to advance past this state or obtain a new signature. This is concrete theft of user funds from an eth-implicit account, in scope per the task's allowed category (the eth-implicit wallet contract).

### Likelihood Explanation
The precondition (an address that is both the `to` of a signed relaying transaction and separately registered under the address registrar as a named account) is exactly the situation the registrar check is designed to police, so it is a realistic occurrence rather than a contrived one. No special privileges are needed by the attacker beyond being able to submit a NEAR transaction calling `rlp_execute` with a previously-observed signed payload (which, per the wallet-contract protocol, would ordinarily be shared with relayers to be forwarded).

### Recommendation
Do not dispatch the relayer-fee transfer promise until the transaction's validity (including the address-registrar check) has been fully confirmed successful; alternatively, consume/burn the nonce (or otherwise permanently invalidate the specific transaction) on the "target corresponds to an existing named account" failure path in `address_check_callback`, not just on success, so a failing signed transaction cannot be resubmitted to repeatedly collect the fee.

### Proof of Concept
Not independently reproduced in a running node; derived from static analysis of `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs` (`inner_rlp_execute`, `address_check_callback`) and `internal.rs` (`validate_tx_relayer_data`). The exact economic magnitude (fee size chosen by the transaction signer) and the practical process for causing an address collision with the registrar were not further validated due to lack of runtime access; a Devin session with repo/test access would be needed to write an integration test (similar to `integration-tests/src/tests/features/wallet_contract.rs::test_wallet_contract_interaction`) exercising the `EOABaseTokenTransfer{address_check: Some(_)}` path with a registrar-registered colliding address to confirm the repeated-fee drain end to end.
