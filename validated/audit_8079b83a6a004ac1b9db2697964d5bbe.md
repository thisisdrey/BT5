**Rationale:** The reported issue is XXE (CWE-611) in veraPDF's Java code, caused by using a default `DocumentBuilderFactory` (a full DOM parser) that resolves `<!DOCTYPE ...SYSTEM...>` / `<!ENTITY ...SYSTEM...>` declarations against external resources, and then reflecting the expanded entity content back to the caller.

Go's standard-library `encoding/xml` package (in this repo, `Kohvert/go--025`) does not have an analogous code path:

- The tokenizer's directive-handling branch (`<!DOCTYPE ...>`, `<!ENTITY ...>`) treats the entire declaration as opaque text and returns it unparsed as a `Directive` token; it never re-parses or resolves `SYSTEM`/`PUBLIC` identifiers to fetch external files or URLs. [1](#0-0) 
- Character/entity references inside element text (`&name;`) are resolved only against the built-in XML entities (`lt`, `gt`, `amp`, `apos`, `quot`) and the caller-supplied `Decoder.Entity` map — there is no DTD-driven external entity expansion mechanism at all. [2](#0-1) 
- The only external I/O hook in the decoder is `Decoder.CharsetReader`, which is nil by default and must be explicitly set by the calling program to handle non-UTF-8 encodings declared in the `<?xml ... encoding="..."?>` processing instruction — it is not automatically invoked based on untrusted `DOCTYPE`/`ENTITY` content the way Java's default `DocumentBuilderFactory` is. [3](#0-2) [4](#0-3) 
- Tests explicitly confirm `DOCTYPE`/`ENTITY` declarations are preserved as literal directive text without expansion, e.g. `TestNestedDirectives`. [5](#0-4) 

Because Go's `encoding/xml` is a streaming tokenizer that never implements DTD processing or automatic external-entity/network resolution (unlike a Java `DocumentBuilderFactory`-based DOM parser), there is no reachable production sink in this repository that mirrors the veraPDF `getRichTextStringOrStreamEntryStringRepresentation()` XXE primitive. This is a fundamental architectural difference, not a missing hardening flag, so no closer analog exists to report.
