### Title
Unprivileged attacker can permanently DoS a victim's ability to deposit collateral or take on new positions by filling their per-account token list to `MAX_TOKENS_PER_USER` via dust `onBehalfOf` deposits - (File: contracts/Pool.sol)

### Summary
The CVE describes a low-privileged, network-reachable denial of service (hang/crash of the server). The Metronome analog is a liveness DoS against an individual account: `Pool` caps the number of tokens tracked per account at `MAX_TOKENS_PER_USER = 30` (deposit tokens + debt tokens combined), and `onlyIfAdditionWillNotReachMaxTokens` reverts with `UserReachedMaxTokens` once that cap is hit [1](#0-0) . Because `DepositToken.deposit` accepts an arbitrary `onBehalfOf_` beneficiary and mints directly to it [2](#0-1) , and `DepositToken.transfer`/`transferFrom` to a first-time holder also registers the token on the recipient's list [3](#0-2) , any unprivileged attacker can stuff a victim's `depositTokensOfAccount` list with dust positions in every deposit token the pool supports.

### Finding Description
- `Pool.addToDepositTokensOfAccount(account_)` is callable only by a registered deposit token, but it is invoked from `DepositToken._mint` whenever `balanceOf[account_] == 0` before the mint [4](#0-3) , and from `DepositToken._transfer` whenever the recipient previously held zero [3](#0-2) .
- `DepositToken.deposit(amount_, onBehalfOf_)` pulls `amount_` of underlying from the caller and mints msdTOKEN to `onBehalfOf_` with no consent required from the beneficiary [5](#0-4) .
- Attack path: for each deposit token `D_i` registered in the pool, the attacker calls `D_i.deposit(1 wei_of_underlying, victim)` (or acquires dust and calls `D_i.transfer(victim, 1)`). Each call appends `D_i` to `depositTokensOfAccount[victim]` inside `Pool.addToDepositTokensOfAccount` [6](#0-5) .
- Once `debtTokensOfAccount.length(victim) + depositTokensOfAccount.length(victim) == 30`, every subsequent `deposit`/`transfer`/`seize`-mint of a token the victim does not already hold reverts inside `onlyIfAdditionWillNotReachMaxTokens`, because `_mint`/`_transfer` propagate the revert from `addToDepositTokensOfAccount`.
- The invariant broken is liveness: a core state transition (collateral deposit / receipt of deposit tokens) becomes unreachable for the victim. This also blocks debt positions: any `issue`/`mint` of a new synthetic would add a debt token and likewise revert once the combined cap is reached.
- Modifier checks: `whenNotPaused`, `nonReentrant`, `onlyIfDepositTokenExists`, `onlyIfDepositTokenIsActive`, and `SurpassMaxDepositSupply` do not stop the attack — dust deposits are legitimate protocol calls. There is no minimum deposit amount (`amount_ == 0` reverts, but 1 wei passes), no beneficiary opt-in, and no way for the victim to preemptively reject incoming deposits.

### Impact Explanation
- Temporary freezing of funds / protocol functionality for a targeted victim: the victim cannot deposit any collateral type they don't already hold, cannot receive msdTOKEN transfers of new tokens, and cannot open debt in synthetics they don't already have.
- Liquidation-griefing amplification: if the victim has an open position whose collateral factor deteriorates, the attacker can front-run or pre-fill the list so the victim cannot deposit a *different* collateral to restore health, forcing liquidation that could otherwise have been avoided. The victim's existing collateral in tokens they already hold can still be topped up and withdrawn (removal on zero balance still works [7](#0-6) ), so this is a partial rather than total freeze — matching the CVE's "hang/frequently repeatable crash" availability-only impact.
- The attack is not self-healing for the victim: dust entries persist until the victim transfers each dust balance to zero, and the attacker can re-fill slots cheaply at any time.

### Likelihood Explanation
- Cost is minimal: the attacker only needs dust amounts (1 wei of underlying per deposit token, plus deposit fee if any) and gas. `deposit` has no minimum.
- Reachable by any EOA through a public entry point; no privileged role, oracle manipulation, or governance action required.
- Effectiveness depends on the deployed pool having enough deposit + debt token types to approach 30 slots; the combined cap means fewer than 30 dust deposits may suffice if the victim already holds several tokens. If the pool only has a handful of deposit tokens, the attack may not reach the cap alone — this limits likelihood on sparsely populated pools, but Metronome deployments typically list many collaterals.

### Recommendation
- Enforce a minimum meaningful deposit/transfer amount, or only add a token to `depositTokensOfAccount` when the resulting balance exceeds a dust threshold.
- Alternatively, make `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` best-effort: cap the tracked list size and skip (rather than revert) additions beyond `MAX_TOKENS_PER_USER`, falling back to iterating a bounded set or computing positions per-token on demand.
- Consider requiring beneficiary consent (e.g., an opt-in mapping or EIP-712 signature) for `onBehalfOf_` deposits that would create a new list entry for a third party.

### Proof of Concept
Hardhat-style fork test outline (pseudocode; assumes deployed `Pool`, `DepositToken` list, and underlying whale/faucet for dust):

```typescript
// test/dos-max-tokens.fork.ts
import { ethers } from "hardhat";

it("dust deposits fill victim's token list and DoS new deposits", async () => {
  const pool = await ethers.getContractAt("Pool", POOL);
  const [attacker, victim] = await ethers.getSigners();

  const tokens: string[] = await pool.getDepositTokens(); // all registered deposit tokens
  const max = (await pool.MAX_TOKENS_PER_USER()).toNumber(); // 30

  // Attacker deposits 1 wei of each underlying on behalf of the victim
  for (const dt of tokens.slice(0, max)) {
    const dep = await ethers.getContractAt("DepositToken", dt);
    const underlying = await ethers.getContractAt("IERC20", await dep.underlying());
    await underlying.connect(attacker).approve(dep.address, 1);
    await dep.connect(attacker).deposit(1, victim.address);
  }

  expect((await pool.getDepositTokensOfAccount(victim.address)).length).to.eq(max);

  // Victim can no longer deposit into a deposit token they don't already hold
  const newDep = await ethers.getContractAt("DepositToken", ANOTHER_DEPOSIT_TOKEN);
  const und = await ethers.getContractAt("IERC20", await newDep.underlying());
  await und.connect(victim).approve(newDep.address, ethers.utils.parseEther("100"));
  await expect(newDep.connect(victim).deposit(parseEther("100"), victim.address))
    .to.be.revertedWithCustomError(pool, "UserReachedMaxTokens");

  // Nor receive a transfer of a new msdTOKEN
  const dep0 = await ethers.getContractAt("DepositToken", tokens[0]);
  // (dep0 already in list; use a token not yet held)
});
```

Note: I could not verify within this session the exact number of deposit/debt tokens registered on the deployed pools (that determines how many dust deposits are needed) nor `DebtToken.issue`'s `onBehalfOf` semantics, which may provide an additional griefing vector if debt can be issued to a third-party account. The deposit-side path above is confirmed by the code cited.
