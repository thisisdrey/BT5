### Title
Shielded Transactions Bypass All Bandwidth/Rate Accounting, Enabling Unmetered zk-SNARK Verification Spam - ([File: chainbase/src/main/java/org/tron/core/db/BandwidthProcessor.java])

### Summary
`BandwidthProcessor.consume()` unconditionally skips bandwidth accounting for any contract of type `ShieldedTransferContract`, while every other broadcastable contract type is metered against the sender's bandwidth (net) usage, free-net limit, or byte-based transaction fee. This mirrors the NamelessMC bug class: a user-reachable action (submitting a transaction) has no throughput-limiting mechanism tied to the actual server-side cost of processing it, allowing an authenticated account to submit an unbounded stream of expensive operations.

### Finding Description
`BandwidthProcessor.consume()` iterates the contracts in a transaction and explicitly bypasses bandwidth metering for shielded transfers: [1](#0-0) 
Every other contract path in the same loop (`useAccountNet`, `useFreeNet`, `useTransactionFee`) enforces per-account and global caps that increase with sustained usage: [2](#0-1) 

For `ShieldedTransferContract`, the actuator instead charges a flat, governance-configurable `ShieldedTransactionFee`/`ShieldedTransactionCreateAccountFee` denominated in the ZEN asset token, drawn from the shielded pool value balance rather than from account bandwidth or a byte-proportional TRX fee: [3](#0-2) 
This decoupling is intentional and even unit-tested as expected behavior: [4](#0-3) 

However, every `ShieldedTransferContract` submission forces the full node to perform expensive zk-SNARK verification work in `validate()` — nullifier/anchor lookups, Merkle-root checks, and `checkProof` (Groth16 proof + binding-signature verification via librustzcash) for each spend/receive description — with no cap on the number of such transactions an account can submit per unit time, unlike all bandwidth-metered contract types: [5](#0-4) 

Because the fee is a flat, fixed amount independent of tx size/complexity and is not tied to any accumulating bandwidth counter, an account holding (or repeatedly recycling) shielded pool value can submit shielded transactions back-to-back paying only the flat fee each time, with zero contribution to `NetUsage`/`FreeNetUsage`, and therefore never gets throttled the way a normal `TransferContract` sender would once bandwidth is exhausted.

### Impact Explanation
This lets an unprivileged, authenticated transaction broadcaster flood the mempool/blocks with computationally expensive shielded transactions that bypass the network's designed throughput throttle (bandwidth accounting), forcing full/witness nodes to spend disproportionate CPU on zk-SNARK proof verification for each transaction. Because bandwidth is the mechanism java-tron uses to bound how many transactions from a single account can be processed per time window, and shielded transfers are fully exempted from it, this can produce a CPU-bound resource-exhaustion condition on nodes processing the block/mempool — impacting the node's ability to serve normal RPC/API/block-production duties (falls under "node crash or halt" / "API the node can no longer serve").

### Likelihood Explanation
Requires only that `AllowSameTokenName` and `supportShieldedTransaction` are enabled (both are standard mainnet committee-enabled features) and that the attacker holds or can acquire ZEN-denominated shielded value to pay the flat fee and reuse it across repeated self-transfers. No special privilege beyond a funded account is needed, and the bypass is deterministic and always triggered for this contract type, since the "continue" in `BandwidthProcessor.consume()` is unconditional.

### Recommendation
Remove the unconditional bypass for `ShieldedTransferContract` in `BandwidthProcessor.consume()` and instead charge bandwidth/net usage (or an equivalent cost proportional to zk-proof verification cost, e.g., scaled by spend/receive description count) so that the throughput of shielded transactions per account is bounded the same way as other contract types, or cap the number of shielded transactions/descriptions an account can submit per block/time window independent of the ZEN fee mechanism.

### Proof of Concept
1. Enable `AllowSameTokenName` and `supportShieldedTransaction` (standard mainnet config).
2. Acquire a small amount of shielded (ZEN) pool value in an account-controlled note.
3. Repeatedly build and broadcast `ShieldedTransferContract` transactions that spend the note and re-create an equivalent note back to the same shielded address (shield-to-shield, no transparent legs), paying only the flat `ShieldedTransactionFee` each time from the shielded value balance.
4. Observe via `AccountCapsule.getNetUsage()`/`getFreeNetUsage()` that these transactions never increment bandwidth usage (as asserted in `publicAddressToShieldedAddressNotConsumeBandwidth`), while each transaction still forces full zk-SNARK proof verification (`checkProof`) on every full node, unlike a normal `TransferContract` which is bandwidth throttled after exhausting `FreeNetLimit`.   private long calcFee(ShieldedTransferContract shieldedTransferContract) {
    byte[] toAddress = shieldedTransferContract.getTransparentToAddress().toByteArray();
    boolean hasTransparentTo = (toAddress.length > 0);
    if (hasTransparentTo) {
      AccountCapsule toAccount = chainBaseManager.getAccountStore().get(toAddress);
      if (toAccount == null) {
        return chainBaseManager.getDynamicPropertiesStore()
            .getShieldedTransactionCreateAccountFee();
      }
    }
    return chainBaseManager.getDynamicPropertiesStore().getShieldedTransactionFee();
