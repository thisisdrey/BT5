### Title
Floating-point rounding in `ExchangeProcessor`'s bancor-style AMM math allows repeated-trade drain of TRC10 exchange pools - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
Bunni's loss stemmed from a custom Liquidity Distribution Function that used precision-sensitive arithmetic; an attacker exploited specifically-sized trades to induce rounding errors that compounded through repeated calls, ultimately letting them withdraw more than they should. java-tron's built-in Bancor-relay exchange for TRC10 tokens (`ExchangeInjectActuator`, `ExchangeWithdrawActuator`, `ExchangeTransactionActuator`) has an analogous custom liquidity math engine, `ExchangeProcessor`, whose default calculation path uses `double`-precision floating point (`Math.pow`/`Maths.pow`) instead of exact integer/BigDecimal arithmetic. [1](#0-0) 

### Finding Description
`ExchangeCapsule.transaction()` selects between two calculation engines: the legacy `ExchangeProcessor` (double-precision) and the newer `SafeExchangeProcessor` (BigDecimal, gated by `allowHardenExchangeCalculation`). [2](#0-1) 

The legacy `ExchangeProcessor.exchangeToSupply` and `exchangeFromSupply` compute a bonding-curve relay quantity via `double` math and truncate with a plain cast to `long` (`(long) issuedSupply`, `(long) exchangeBalance`), rather than using exact/deterministic rounding: [1](#0-0) 

Critically, the internal `supply` field is a running, mutable state (`supply += out;` / `supply -= supplyQuant;`) that persists across sequential trades within a single `transaction()` call and, more importantly, is recomputed fresh from the two token balances on every actuator invocation (`exchangeCapsule.transaction(...)`, `new ExchangeProcessor(supply, useStrictMath)`), so each trade recalculates the curve from the current pool reserves using floating-point exponentiation (`pow(x, 0.0005)` and `pow(x, 2000.0)`). Floating-point `pow`/division is not guaranteed to be exactly invertible, and rounding direction is not enforced to always favor the pool. Because both `ExchangeInjectActuator`/`ExchangeWithdrawActuator` (linear share-based formulas using integer `BigInteger`/`floorDiv` — largely rounding-down and appearing safer) and `ExchangeTransactionActuator` (which uses the exponential `ExchangeProcessor`/`SafeExchangeProcessor` bancor formula) operate on the *same* mutable `firstTokenBalance`/`secondTokenBalance` state, an attacker fully controlling `sellTokenQuant` size and call sequence can:
1. Send transactions with `tokenQuant` values chosen to land at floating-point rounding boundaries (e.g., very small quantities, or quantities producing a `newBalance`/`balance` ratio close to a power-of-2 or an irrational boundary in `pow`), causing the truncated `long` result to systematically favor the caller by fractions of a unit per trade.
2. Repeat such transactions (there is no minimum-quant floor other than `anotherTokenQuant <= 0` check, and fees for `ExchangeTransactionActuator.calcFee()` are `0`), accumulating value extracted from the pool reserves over many iterations — exactly the "repeated withdrawals... turning rounding mistakes into cold hard cash" pattern from the Bunni report.
3. Because the default (`allowHardenExchangeCalculation == 0`) path always executes `ExchangeProcessor` rather than `SafeExchangeProcessor`, this floating-point-derived drift is present on any exchange pool that has not opted into (or before the network has activated) the hardened calculation mode.

This mirrors Bunni's exact failure mode: a bespoke, mathematically elegant liquidity/pricing function using non-integer, imprecise arithmetic, where the vulnerability doesn't come from a single big trade but from many small, carefully-sized trades cumulatively skewing balances away from the true invariant.

### Impact Explanation
An attacker (any unprivileged account able to broadcast `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` transactions) can drain value from TRC10 Bancor-relay exchange pools over repeated transactions, at the expense of other liquidity participants/the pool reserves — a direct theft-of-funds / unbacked-balance impact matching the "High" severity class the Bunni report was rated.

### Likelihood Explanation
Exploitation requires precise offline modeling of the `double`-based Bancor formula to find quantities/sequences that produce favorable truncation, and the accumulated skew per trade is likely small (bounded by `double` ULP-level imprecision, not the catastrophic `wei`-level divide-by-near-zero seen in Bunni). This makes the bug harder to trigger for large, single-shot profit compared to Bunni's specific 28-wei-to-4-wei collapse, but the underlying bug class (floating point/rounding drift in a custom AMM curve, invoked repeatedly by an unprivileged caller with full control of trade sizing) is structurally the same, and the code explicitly ships a "hardened"/`SafeExchangeProcessor` alternative — an implicit admission that the default `ExchangeProcessor` path is imprecise and unsafe for production-scale value.

### Recommendation
- Default all exchange calculations to `SafeExchangeProcessor` (or an equivalent full-precision, deterministically-rounded integer arithmetic path), removing the legacy `double`-based `ExchangeProcessor` from production use rather than gating it behind an opt-in flag.
- Enforce rounding that always favors the pool (round down for amounts paid out, round up for amounts taken in) consistently across `ExchangeProcessor`, `SafeExchangeProcessor`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator`.
- Add invariant checks after every exchange operation (e.g., verify the bonding-curve invariant/k value does not decrease beyond a negligible, pool-favoring epsilon) similar to Bunni's post-mortem recommendation for stateful fuzzing across chained/rounding-sensitive operations.
- Add minimum trade-size thresholds and fuzz/property-based tests specifically targeting repeated small trades against `ExchangeProcessor` to confirm no cumulative value leakage from the pool.

### Proof of Concept
Conceptual (cannot be fully executed without a live node, but demonstrates the reachable path and root cause):
1. Create a TRC10 exchange pool via `ExchangeCreateActuator` with default settings (`allowHardenExchangeCalculation = 0`).
2. Repeatedly call `ExchangeTransactionActuator` with `tokenQuant` values crafted so that in `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` the `double` computation of `pow(1 + quant/newBalance, 0.0005)` and `pow(1 + supplyQuant/supply, 2000.0)` truncates favorably for the caller (verifiable offline by iterating candidate `sellTokenQuant` values through the exact same formula in Java/Python and diffing against a `BigDecimal` reference implementation such as `SafeExchangeProcessor`).
3. Execute the identified quantities as a sequence of transactions against the pool, each time re-deriving `firstTokenBalance`/`secondTokenBalance` from `ExchangeCapsule.transaction()` at lines [3](#0-2)  and observe cumulative deviation of extracted `buyTokenQuant` versus the invariant-preserving (`SafeExchangeProcessor`) result over many iterations, as already demonstrated by the codebase's own test `ExchangeProcessorTest.testStrictMath` proving `ExchangeProcessor` and `SafeExchangeProcessor` diverge (`Assert.assertNotEquals(anotherTokenQuant, result)`), confirming the floating point path is measurably imprecise relative to the hardened one.   private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
