Audit Report

## Title
Fee-refund logic in `SwapAssetAdapter::correct_and_deposit_fee` uses post-dispatch AMM spot price, letting a user manipulate their own asset-fee refund - (File: `substrate/frame/transaction-payment/asset-conversion-tx-payment/src/payment.rs`)

## Summary
`ChargeAssetTxPayment` withdraws the fee-asset in `prepare` using `SwapAssetAdapter::withdraw_fee`, which quotes `S::quote_price_tokens_for_exact_tokens(asset_id, A, fee, true)` against the pool state *before* the wrapped call dispatches. [1](#0-0)  The refund is computed and executed later, in `post_dispatch_details` → `correct_and_deposit_fee`, which independently re-quotes `S::quote_price_exact_tokens_for_tokens(A, asset_id, refund_amount, true)` and swaps at whatever pool state exists *after* the call has run, with no binding to the pre-dispatch quote. [2](#0-1) 

## Finding Description
The extension lifecycle is: `validate`/`prepare` withdraws the fee asset via `SwapAssetAdapter::withdraw_fee`, which is invoked from `ChargeAssetTxPayment::prepare` before the wrapped call dispatches. [3](#0-2)  Nothing prevents the wrapped `call` (directly, or via `pallet-utility::batch`/`batch_all`) from itself invoking the public `pallet_asset_conversion::swap_exact_tokens_for_tokens`/`swap_tokens_for_exact_tokens` extrinsics on the exact same `asset_id <-> A` pool, arbitrarily moving the reserve ratio within the same transaction.

After dispatch, `post_dispatch_details` calls `T::OnChargeAssetTransaction::correct_and_deposit_fee`, which independently re-quotes the refund conversion using `S::quote_price_exact_tokens_for_tokens` and executes `S::swap_exact_tokens_for_tokens` against the pool state at that later point — fully attacker-influenced if the wrapped call moved the pool. [4](#0-3)  `pallet_asset_conversion`'s quoting functions are explicitly documented as reflecting only current pool balances, with a caveat aimed at ordinary cross-transaction slippage ("the price may have changed by the time the transaction is executed"), not at a price the *same* transaction's own embedded call just moved. [5](#0-4) [6](#0-5)  There is no re-validation that the pool state used for the refund matches the state used at withdrawal, no TWAP, and no bound tying the refund quote to the price actually paid at withdrawal time — confirmed by inspection of both `withdraw_fee` and `correct_and_deposit_fee` in `payment.rs`, which independently call `S::quote_price_*` with no shared/snapshotted price parameter passed between them.

## Impact Explanation
An unprivileged signed account paying fees in a non-native asset can embed a pool-manipulating swap in the very call protected by `ChargeAssetTxPayment` (or wrap it via `pallet-utility::batch_all`), shifting the fee-asset/native pool's reserves between fee withdrawal and refund. The refund swap then executes at the manipulated ratio, letting the attacker extract additional `asset_id` value from the pool's liquidity providers beyond what the fee actually cost at withdrawal time — a form of value theft from AMM LPs routed through protocol logic, matching the allowed "theft ... or unbacked mint" impact class. Note the extractable amount per transaction is capped by `refund_amount`, which is bounded by the originally withdrawn native-asset fee (`fee_paid.peek()`), so the blast radius per transaction is limited to typical fee magnitude, but this is repeatable across transactions and disproportionately damaging to shallow pools.

## Likelihood Explanation
Medium: exploitation requires only an ordinary signed account holding both the fee asset and enough capital to move the pool, plus a single extrinsic (call or `utility.batch_all`) that both swaps the pool and produces `corrected_fee < fee` (e.g., a `Pays::No` inner call or one whose actual weight is far below its declared `DispatchInfo`). No privileged role, malicious peer, validator, or off-chain infrastructure is required — everything is contained in one atomic, publicly-triggerable transaction from an unprivileged account, matching the accepted "public underpriced work" / unbacked value extraction pattern.

## Recommendation
Snapshot the pool exchange rate once (e.g., quote and lock it during `prepare`) and reuse that same rate for both the withdrawal and the refund rather than re-querying the spot price after the call dispatches. Alternatively, disallow/detect nested swaps against the same fee-asset pool within the extension-protected call, or clamp the refund quote so it can be no more favorable than the rate observed at withdrawal time.

## Proof of Concept
1. Attacker holds asset `X` and submits a transaction using `ChargeAssetTxPayment { asset_id: Some(X) }`.
2. The dispatched call is a `pallet_utility::batch_all` containing: (a) a large `pallet_asset_conversion::swap_exact_tokens_for_tokens` trade dumping `X` into the `X<->Native` pool to sharply skew the reserve ratio, and (b) a cheap or `Pays::No` inner call so `post_info`'s actual fee is much smaller than the fee originally withdrawn.
3. `withdraw_fee` (pre-dispatch, in `prepare`) already converted a modest amount of `X` into `Native` at the pre-manipulation ratio.
4. `correct_and_deposit_fee` (post-dispatch) computes a `refund_amount` in `Native` (large due to step 2b) and quotes/executes the refund swap `Native -> X` at the ratio manipulated in step 2a, yielding more `X` back to the attacker than the fee-asset value actually consumed — drained from the pool's LPs.
5. This can be reproduced as a Rust integration test in the pallet's `tests.rs` mock runtime by: withdrawing fee for asset `X`, invoking a mock swap that alters pool reserves between `withdraw_fee` and `correct_and_deposit_fee`, and asserting the refunded `X` amount exceeds the value implied by the pre-manipulation exchange rate.
