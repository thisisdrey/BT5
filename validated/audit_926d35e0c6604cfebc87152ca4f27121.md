### Title
Fragmentation of NEP-245/IMT `TokenDiff` deltas into unit-sized intents bypasses the protocol fee - (File: `contracts/defuse/core/src/intents/token_diff.rs`)

### Summary
`TokenDiff::execute_intent` computes the protocol fee independently for each `TokenDiff` intent, using `Self::token_fee(token_id, amount, protocol_fee)`, and that helper deliberately returns `Pips::ZERO` for NEP-245/IMT tokens whenever the per-intent amount is `<= 1`. Because `execute_intents` accepts a batch of `DefuseIntents`, each of which can contain an arbitrary `Vec<Intent>`, a signer can split what is logically one large NEP-245/IMT trade into many `TokenDiff` intents that each move only `1` unit of the token. Every such intent is individually exempt from the fee, so the aggregate amount moved across the batch pays zero fee instead of the fee that would apply to a single `TokenDiff` with the same total delta.

### Finding Description
The fee-exemption rule is implemented per intent, not per aggregate value moved: [1](#0-0) 

and it is invoked inside the per-token loop of a single intent's execution: [2](#0-1) 

The comment "do not take fees on NFTs and MTs with `|delta| <= 1`" reflects an intent to exempt genuinely atomic (NFT-like) transfers of NEP-245/IMT tokens. However, `TokenDiff.diff` is a map keyed by `TokenId`, so within one `TokenDiff` only a single delta per token exists — but nothing prevents a signer from including many separate `TokenDiff` intents (each with `delta == 1` or `delta == -1` for the same NEP-245/IMT token) inside one `DefuseIntents.intents` vector, or across multiple signed payloads processed together by `execute_intents`: [3](#0-2) [4](#0-3) 

Each intent is fee-assessed in isolation (`amount = 1` per intent), so `token_fee` returns `Pips::ZERO` every time, while the sum of the deltas across the batch can be arbitrarily large. This is the same root cause as the referenced report: a value that should be evaluated on the aggregate operation (fee owed on the total amount moved) is instead evaluated on a fragment (the per-call amount), letting an attacker split the operation to drive the assessed value to zero.

### Impact Explanation
This lets a signer move any amount of an NEP-245 or IMT-denominated token through `TokenDiff` while paying zero protocol fee, as long as they are willing to submit `N` unit-sized `TokenDiff` intents instead of one intent with the full delta. This directly matches the "fees owed vs fees collected" boundary in scope: fees can be bypassed entirely for a whole class of tokens (any NEP-245 asset stored in the vault, including wrapped/bridged tokens represented as NEP-245, and any IMT), representing a Critical-class impact ("fees bypassed or over-collected").

### Likelihood Explanation
Likelihood is high for any unprivileged user: no special permissions are required, only the ability to sign multiple `TokenDiff` intents (trivial, since `Intent::TokenDiff` is a standard user-facing intent and `DefuseIntents.intents` is an arbitrary-length vector under full signer control). The only cost is proportional gas/transaction size for issuing `N` intents instead of `1`; there is no economic penalty scaling with the fee avoided.

### Recommendation
Compute and charge the NEP-245/IMT fee exemption based on the aggregate amount of the token moved across the whole batch of intents/signed payloads (e.g., accumulate per-`token_id` totals engine-wide before applying `token_fee`'s `amount <= 1` exemption), rather than per individual `TokenDiff` intent. Alternatively, restrict the `amount <= 1` exemption path so it cannot be reached repeatedly for the same `(signer, token_id)` pair within a single `execute_intents` call, or remove the exemption and instead special-case true NFT-only token types (`TokenIdType::Nep171`) which cannot have `amount > 1` by construction.

### Proof of Concept
1. Configure the Defuse contract with a non-zero protocol `fee` (`Pips`), as validated in `FeesConfig` (see wiki "Fees and Protocol Economics").
2. Attacker deposits `1000` units of an NEP-245 (or IMT) token into their account.
3. Instead of signing a single `TokenDiff` intent with `diff = { token: -1000, other_token: +X }` (which would incur `token_fee(token, 1000, fee) = fee` and thus a nonzero `fees_collected`), the attacker signs a `DefuseIntents` payload containing `1000` separate `TokenDiff` intents, each with `diff = { token: -1, other_token: +x_i }`.
4. For every one of these intents, `TokenDiff::execute_intent` calls `Self::token_fee(token_id, 1, protocol_fee)`; because `amount (1) > 1` is false for `TokenIdType::Nep245`/`Imt`, `token_fee` returns `Pips::ZERO` (`contracts/defuse/core/src/intents/token_diff.rs:206-216`), so `fee_ceil(1) == 0` for every intent.
5. `execute_signed_intents` processes all these intents in the same call (`contracts/defuse/core/src/engine/mod.rs:32-40`), applying deltas and collecting fees per intent; since every per-intent fee is `0`, `fees_collected` stays empty for the whole batch (`contracts/defuse/core/src/intents/token_diff.rs:96-101`), even though the aggregate `-1000` delta was moved — a fee-bypass identical in structure to the referenced fragmentation-fee bug.
