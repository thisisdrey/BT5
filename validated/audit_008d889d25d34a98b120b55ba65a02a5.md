### Title
Unconsented dust deposits pollute a victim's per-account token list, hitting `MAX_TOKENS_PER_USER` and blocking all new collateral/debt positions - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
The `ts-nodash` Merge() prototype-pollution analog is Metronome's per-account enumerable token lists (`depositTokensOfAccount`, `debtTokensOfAccount`). These are shared "objects" whose keys get silently populated on behalf of an account that never asked for it. `DepositToken.deposit(amount_, onBehalfOf_)` lets anyone mint dust to an arbitrary victim; `DepositToken._transfer`/`_mint` then call `Pool.addToDepositTokensOfAccount(account_)`, which inserts the token into the victim's set and reverts once the set reaches `MAX_TOKENS_PER_USER` (30). An unprivileged attacker can therefore fill a victim's set with 1-wei dust entries, after which every operation that would add a *new* token type to the victim reverts with `UserReachedMaxTokens`.

### Finding Description [1](#0-0)  `deposit` takes an arbitrary `onBehalfOf_` with no consent check. On first receipt, `_mint` calls `pool.addToDepositTokensOfAccount(account_)` [2](#0-1) . The same happens in `_transfer` for any recipient [3](#0-2) .

In `Pool`, the shared limit is enforced inside `onlyIfAdditionWillNotReachMaxTokens` [4](#0-3) , used by `addToDepositTokensOfAccount` [5](#0-4)  and `addToDebtTokensOfAccount` [6](#0-5) . The modifier counts `debt + deposit` tokens together, so dusting the deposit list also blocks new debt-token additions (i.e., `DebtToken.issue`/`mint` of a synthetic the victim doesn't already hold).

Because the `add` call happens *inside* the token's `_transfer`/`_mint`, the whole transaction reverts: the victim cannot receive, deposit, or issue *any* token type not already in their list. The attacker only pays dust amounts of underlying collateral — no victim action or signature required — and can cheaply refill a slot with `deposit(1 wei, victim)` whenever the victim zeroes a dust balance (removal only happens when balance hits exactly 0, `DepositToken._burn` [7](#0-6) ).

### Impact Explanation
Temporary freezing of funds / griefing:
- Victim cannot deposit a collateral type they don't already hold (the `deposit` reverts in `addToDepositTokensOfAccount`), so they cannot add *new* collateral to improve health — if their existing collateral is insufficient they are pushed toward liquidation they cannot dodge by diversifying.
- Any third party trying to `transfer`/`transferFrom` a new deposit-token type to the victim has their tx revert.
- Victim cannot `issue` a synthetic whose debt token isn't already in their list.
- Recovery requires the victim to `withdraw`/`transfer` each dust balance to exactly zero — a per-slot gas cost — and the attacker can re-pollute slots at dust cost for as long as the pool has ≤30 deposit tokens.

Not permanent (victim can clear slots), and no direct theft, so severity is bounded — but it is a real liveness/funds-usability break reachable by any EOA with dust collateral, matching the "unvalidated merge pollutes shared state" class.

### Likelihood Explanation
Fully attacker-controlled, no privileged role needed: `deposit` is `external whenNotPaused`, `onBehalfOf_` is unrestricted, and each polluting entry costs only the minimum non-zero underlying amount plus gas. The constraint is that the pool has at most `MAX_TOKENS_PER_USER` deposit tokens total (`addDepositToken` enforces `depositTokens.length() < 30` [8](#0-7) ), so the attacker must purchase dust of every listed underlying — feasible for a typical pool. Persistence is limited only by the victim's willingness to repeatedly clean slots.

### Recommendation
- Require recipient opt-in before a deposit token is added to `depositTokensOfAccount` for `onBehalfOf_ != _msgSender()` deposits and incoming transfers (e.g., only add on `deposit` where `onBehalfOf_ == _msgSender()`, or an explicit `enableCollateral(token)` opt-in mapping consulted by `depositOf`/`debtPositionOf`).
- Alternatively, enforce `MAX_TOKENS_PER_USER` on the *sender's* cost basis (revert only the attacker's own actions) rather than the recipient's set, so dust-pushing to victims reverts instead of polluting.
- For a stronger analog fix, `deposit` could reject `onBehalfOf_` that hasn't interacted with the pool, or charge/attribute first-touch additions to the payer's list.

### Proof of Concept
Hardhat sketch (against deployed Base fork; pool addresses from `deployments/base`):

```ts
// Victim V holds collateral A. Attacker fills V's list.
const pool = await ethers.getContractAt("Pool", POOL);
const depositTokens: string[] = await pool.getDepositTokens();

for (const dt of depositTokens) {
  const depositToken = await ethers.getContractAt("DepositToken", dt);
  const underlying = await ethers.getContractAt("IERC20", await depositToken.underlying());
  if (await depositToken.balanceOf(victim.address) == 0) {
    // attacker acquires 1 wei of underlying via DEX/whale, then:
    await underlying.approve(depositToken.address, 1);
    await depositToken.deposit(1, victim.address); // adds dt to victim's set
  }
}

// victim now has ~30 entries; any new token-type action reverts
await expect(
  victimDepositTokenOfUnheldType.deposit(amount, victim.address) // or attacker transfer of new type
).to.be.revertedWithCustomError(pool, "UserReachedMaxTokens");

// victim also cannot issue a synthetic whose debt token is new to them
await expect(
  newDebtToken.connect(victim).issue(1)
).to.be.revertedWithCustomError(pool, "UserReachedMaxTokens");

// recovery: victim withdraws each dust balance to 0 to free slots — attacker re-dusts
```

Caveats not fully verified within available iterations: whether `DebtToken.issue` calls `addToDebtTokensOfAccount` with the same in-tx revert path (it does per the modifier usage, but I did not re-read `DebtToken.sol`), and whether known Metronome audits already cover this griefing vector — the rule excludes "known audit issues," which could not be checked here.
