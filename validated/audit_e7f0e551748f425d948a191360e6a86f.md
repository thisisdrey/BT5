### Title
Deferred connection rate-limiting allows single-IP slow-handshake attack to exhaust the global connection-acceptance slot pool - ([File: streamer/src/nonblocking/quic.rs])

### Summary
Both the per-IP (`ConnectionRateLimiter::is_allowed`) and the global (`overall_connection_rate_limiter.current_tokens()`) checks performed in `run_server` before accepting an `Incoming` are non-consuming "peek" checks; the actual token consumption (`register_connection` / `consume_tokens`) only happens in `setup_connection` after the QUIC/TLS handshake has *completed*. An attacker who never completes the handshake therefore never gets rate-limited, and can keep occupying `ClientConnectionTracker` slots (bounded only by the single global `max_concurrent_connections` counter) for the full `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` (60s), effectively starving legitimate connection acceptance.

### Finding Description
In `run_server` (streamer/src/nonblocking/quic.rs:304-411), for every incoming connection the server performs two "admission" checks before spawning a handshake task:

1. Global check: `overall_connection_rate_limiter.current_tokens() == 0` [1](#0-0) 
2. Per-IP check: `rate_limiter.is_allowed(&incoming.remote_address().ip())` [2](#0-1) 

Neither of these calls actually consumes a token — `ConnectionRateLimiter::is_allowed` only calls `current_tokens` (a peek), and the overall limiter's `current_tokens()` is likewise a read-only check. [3](#0-2) 

Tokens are only actually deducted later, inside `setup_connection`, and only in the success branch reached **after** the handshake completes:
```
let res = timeout(QUIC_CONNECTION_HANDSHAKE_TIMEOUT, connecting).await;
...
if !rate_limiter.register_connection(&from.ip()) { ... }
if overall_connection_rate_limiter.consume_tokens(1).is_err() { ... }
``` [4](#0-3) 

Because of this ordering, a connection that sends the initial QUIC packet and then goes silent (never finishing the TLS/QUIC handshake) never triggers `register_connection` or `consume_tokens`. Both rate limiters therefore never see this attempt as consuming quota, and immediately allow the *next* connection attempt from the same (or another) source, regardless of how many stalled handshakes are already in flight.

The only bound left on concurrently-outstanding handshakes is the single global counter enforced by `ClientConnectionTracker::new`, gated on `qos.max_concurrent_connections()`:
```
fn new(stats: Arc<StreamerStats>, max_concurrent_connections: usize) -> Result<Self, ()> {
    let open_connections = stats.open_connections.fetch_add(1, Ordering::Relaxed);
    if open_connections >= max_concurrent_connections { ... return Err(()); }
    Ok(Self { stats })
}
``` [5](#0-4) 

This counter (`stats.open_connections`) is shared by *all* connections server-wide — staked, unstaked, and attacker — not scoped per IP. Once `ClientConnectionTracker::new` starts returning `Err(())`, every subsequent incoming connection (including legitimate ones) is refused via `incoming.refuse()` and counted in `refused_connections_too_many_open_connections`: [6](#0-5) 

Each accepted-but-stalled connection is tracked via `outstanding_incoming_connection_attempts` and is only released after `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` (60 seconds) elapses in `setup_connection`'s `timeout(...)` call, at which point the `ClientConnectionTracker` is dropped and `stats.open_connections` is decremented. [7](#0-6) [8](#0-7) 

Because neither the per-IP nor the global limiter actually charges quota for incomplete handshakes, an attacker (even from a single source IP) can repeatedly open new QUIC connections faster than any are being freed, driving `open_connections` up to `max_concurrent_connections` and keeping it pinned there for the full 60-second window, on a repeating basis (as soon as one slot frees at t+60s, the attacker immediately re-fills it since it never was rate-limited).

### Impact Explanation
This is a TPU ingress connection-acceptance Denial-of-Service: once `open_connections` reaches `max_concurrent_connections`, all new incoming connections — from legitimate staked and unstaked clients alike — are refused (`incoming.refuse()`) until an attacker-held slot times out, and the attacker can immediately re-occupy it. This matches the "ingress/networking DoS" bounty category: legitimate transaction submitters cannot establish new QUIC connections to the leader's TPU port for the duration of the attack, which can be sustained indefinitely by a single unprivileged client.

### Likelihood Explanation
Feasible and repeatable with a single unstaked/unprivileged client:
- No stake, keys, or privileged network position required — just the ability to open raw UDP/QUIC connections to the public TPU QUIC port.
- The attacker only needs to send the initial QUIC packet (to be accepted by `endpoints[i].accept()`) and then stop responding, never completing `connecting` in `setup_connection`.
- Because rate-limit tokens are only consumed on handshake *success*, there is no cost to opening more of these stalled connections; the attacker can pipeline connection attempts at whatever rate the OS/network allows, limited in practice only by `max_concurrent_connections` (the cap the attack aims to fill) rather than by the per-IP/global limiters, which are designed to gate this exact scenario but only take effect too late.
- The attack is trivially repeatable: as soon as any stalled slot expires at `QUIC_CONNECTION_HANDSHAKE_TIMEOUT`, the attacker opens a replacement connection immediately.

### Recommendation
Move rate-limit admission/consumption earlier, before spawning the handshake task, rather than gating on handshake success:
- Consume a token from `overall_connection_rate_limiter` and reserve/charge the per-IP limiter at `Incoming` accept time (in `run_server`), not after `connecting` completes in `setup_connection`.
- If a stalled/timed-out or failed handshake should be "refunded", explicitly return the token on the timeout/error path in `setup_connection`, rather than never charging it at all.
- Consider adding a per-IP cap on `outstanding_incoming_connection_attempts` (i.e., a per-IP concurrent in-flight-handshake limit), independent of `max_concurrent_connections`, so a single source cannot consume the entire global handshake-slot budget.

### Proof of Concept
Integration-test plan (extending the existing `streamer` QUIC test harness, e.g. `streamer/src/nonblocking/quic.rs` tests or `streamer/src/nonblocking/testing_utilities.rs`):

1. Start a `run_server` instance with a small `max_concurrent_connections` (e.g., 8) and default `QUIC_CONNECTION_HANDSHAKE_TIMEOUT`-equivalent test constant (or a shortened override for test speed).
2. Spawn N = `max_concurrent_connections` client tasks from **the same source IP** that open a raw UDP socket / QUIC `Endpoint::connect`, send only the QUIC initial packet (or use a client that starts `connecting` and then drops the future / stops responding to handshake continuation), and never complete the handshake.
3. Assert via `StreamerStats`:
   - `outstanding_incoming_connection_attempts` reaches `max_concurrent_connections`.
   - `stats.open_connections.load(Ordering::Relaxed) == max_concurrent_connections`.
4. Attempt a legitimate connection from a distinct, well-behaved client (different or same IP) and assert it is refused (`refused_connections_too_many_open_connections` increments, or the `connect()` future errors/times out) while attacker slots are still outstanding.
5. Assert that neither `connection_rate_limited_per_ipaddr` nor `connection_rate_limited_across_all` incremented for the attacker's stalled attempts (proving the limiter never charged them), demonstrating the rate limiters failed to bound the attack.
6. Repeat after the timeout window elapses to show the attacker can re-fill the slot pool immediately, keeping legitimate connections refused indefinitely.

        let open_connections = stats.open_connections.fetch_add(1, Ordering::Relaxed);
