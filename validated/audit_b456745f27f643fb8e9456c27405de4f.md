Audit Report

## Title
CREATE1 contract address derivation diverges between dry-run and actual transaction, breaking deterministic address prediction - (`substrate/frame/revive/src/exec.rs`)

## Summary
`Stack::new_frame` in `substrate/frame/revive/src/exec.rs` derives a to-be-instantiated contract's address via `address::create1(&deployer, nonce)` when no salt is given, subtracting 1 from `account_nonce` whenever `origin_is_caller` is true, to compensate for the pre-dispatch nonce increment applied during real extrinsic execution. This repository's code performs that `-1` adjustment based solely on `origin_is_caller`, without any `ExecContext`/dry-run discriminator, exactly matching the pre-fix bug documented in `prdoc/stable2506/pr_8504.prdoc`.

## Finding Description
In `substrate/frame/revive/src/exec.rs`, the `FrameArgs::Instantiate` branch of `new_frame` computes: [1](#0-0) 

```rust
address::create1(
    &deployer,
    if origin_is_caller {
        account_nonce.saturating_sub(1u32.into()).saturated_into()
    } else {
        account_nonce.saturated_into()
    },
)
```

This unconditionally subtracts 1 from `account_nonce` whenever `origin_is_caller` is true, regardless of whether the call is a real dispatched transaction (where `System::account_nonce` has already been incremented pre-dispatch) or a dry-run/RPC-simulated call (where it has not). `prdoc/stable2506/pr_8504.prdoc` explicitly documents this exact bug and its fix, gating the subtraction on `origin_is_caller && matches!(exec_context, ExecContext::Transaction)`: [2](#0-1) 

A repository-wide search confirms `ExecContext` does not appear anywhere in `substrate/frame/revive/src/exec.rs` or any other source file — it exists only inside the prdoc text itself — confirming the corrective gating from PR #8504 was never applied to this codebase's `exec.rs`. No other caller of `new_frame`, nor `address::create1`/`create2` themselves, re-validates or corrects the nonce value used for address derivation, so this is the sole and insufficient guard.

## Impact Explanation
This causes the address returned by a runtime-API dry-run of `instantiate`/`instantiate_with_code` (no salt) to differ from the address actually used when the real signed extrinsic is later submitted, because the dry-run's nonce is not pre-incremented while the code still subtracts 1 as if it were. Any user, wallet, or contract that pre-funds, whitelists, or binds logic to the dry-run-predicted address before submitting the real deployment transaction will have that value or reference bound to an address that never hosts the deployed contract — a permanent fund/state mismatch, matching the "public underpriced work / wrong beneficiary or address" impact class for `pallet-revive`.

## Likelihood Explanation
This is triggered by the standard, non-adversarial dry-run-then-submit deployment workflow that is the documented/common usage pattern for previewing `CREATE1` contract addresses via RPC before submission; no privileged access or malicious behavior is required, only ordinary user tooling that queries the runtime API before dispatching the real extrinsic.

## Recommendation
Land the fix described in `prdoc/stable2506/pr_8504.prdoc`: thread an `ExecContext` (or equivalent execution-context discriminator) into `new_frame`, and apply the `saturating_sub(1)` nonce adjustment only when `origin_is_caller && matches!(exec_context, ExecContext::Transaction)`. Add a regression test analogous to `nonce_not_incremented_in_dry_run()` that asserts dry-run-computed and transaction-computed `create1` addresses are identical for the same deployer/nonce state.

## Proof of Concept
1. Fund account `ALICE`; note `System::account_nonce(&ALICE)` = `N`.
2. Invoke the runtime API dry-run path for `instantiate_with_code` (no salt) as `ALICE`. This goes through `new_frame` with `origin_is_caller = true` and the pre-dispatch (not-yet-incremented) nonce `N`, but the code subtracts 1, yielding predicted address `create1(ALICE_ADDR, N-1)`.
3. Submit the actual signed `instantiate_with_code` extrinsic as `ALICE`. Because the nonce is incremented to `N+1` pre-dispatch for real extrinsics, the `-1` correction yields `create1(ALICE_ADDR, N)` as the true deployed address.
4. Compare: dry-run predicted `create1(ALICE_ADDR, N-1)` versus actual deployed `create1(ALICE_ADDR, N)` — the two addresses differ, confirming the divergence.
