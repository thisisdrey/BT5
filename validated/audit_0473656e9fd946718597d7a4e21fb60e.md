### Title
Witness reward with zero cycle votes permanently locks delegator rewards - (File: chainbase/src/main/java/org/tron/core/service/MortgageService.java)

### Summary
`MortgageService.payReward()` unconditionally splits every block/transaction-fee reward into a brokerage share (paid immediately to the witness) and a delegator share that is stored via `delegationStore.addReward(cycle, witnessAddress, value)`, without checking whether the witness has any recorded votes (`totalVote`) for that cycle. The corresponding claim path, `computeReward()`, explicitly skips reward accounting whenever `totalVote == 0`, so any delegator-share reward stored against a cycle in which the witness had zero recorded votes becomes permanently unclaimable — this mirrors the reported Deriverse bug where fees were split toward a destination (`pool_fees`) without checking whether a valid recipient (`ps`/liquidity provider) existed.

### Finding Description
`payReward()` computes `brokerageAmount` from the witness's brokerage rate and unconditionally routes the remainder to the delegator pool: [1](#0-0) 

There is no guard analogous to a "no voters" check before calling `delegationStore.addReward(cycle, witnessAddress, value)`. On the withdrawal/claim side, `computeReward(cycle, votes)` explicitly discards any reward for a cycle where the witness's recorded total vote is zero: [2](#0-1) 

The per-cycle `totalVote` snapshot used by `computeReward` is written by `MaintenanceManager.doMaintenance()` from each witness's current `voteCount`, so a witness with `voteCount == 0` (or a witness that is active with no recorded votes for the current cycle) will have `delegationStore.getWitnessVote(cycle, srAddress) == 0`: [3](#0-2) 

`payBlockReward` and `payTransactionFeeReward` are invoked from `Manager.java` during block application for whichever address is the current block-producing witness, with no check that the witness has nonzero votes for the active cycle: [4](#0-3) 

This is structurally identical to the Deriverse bug class: a value is split and a portion is routed to a pool/store intended for a stakeholder group (LPs / voters) without first checking whether that stakeholder group actually exists (`ps == 0` / `totalVote == 0`) for the current period. When it doesn't, that value silently becomes stuck in a store that is provably unreachable by any withdrawal code path.

### Impact Explanation
Any TRX allocated as a delegator-share reward for a witness/cycle combination where the witness's recorded vote total is zero is permanently locked: `computeReward` will always `continue` past that cycle for every possible voter, since `totalVote == 0` for that cycle can never change retroactively. This is a permanent freezing-of-funds condition — the TRX is debited from the reward accounting flow but can never be paid out to the witness (whose brokerage share only covers `brokerageAmount`) or to any delegator.

### Likelihood Explanation
This requires an active/standby witness to have a zero (or unset) vote total recorded for the cycle in which it earns block or transaction-fee rewards — e.g., a witness created via `WitnessCreateActuator` (reachable by any funded account) that becomes active/standby before accumulating votes, or one whose voters fully withdraw such that the maintenance-cycle snapshot records zero votes while the witness continues producing blocks in that cycle. This is most reliably triggered on java-tron-based networks with a candidate count at or below the configured SR/standby-witness slots (common for private/consortium deployments), where a freshly created zero-vote witness becomes an active or standby SR and immediately begins earning rewards through `Manager`'s per-block reward path.

### Recommendation
Mirror the Deriverse fix: in `MortgageService.payReward()`, check the witness's recorded vote total for the current cycle before allocating the delegator-share reward. If `totalVote == 0`, route the entire reward (or at least the would-be delegator share) to the witness's own allowance instead of `delegationStore.addReward()`, ensuring no reward is written into a bucket that `computeReward()` can never redistribute.

### Proof of Concept
1. On a java-tron network where the number of witness candidates is at or below the configured witness/standby slots (or via a scenario where a witness's voters fully unfreeze/withdraw votes right at a maintenance boundary), submit a `WitnessCreateContract` to become an active/standby witness with `voteCount == 0` for the upcoming cycle.
2. `MaintenanceManager.doMaintenance()` snapshots `delegationStore.setWitnessVote(nextCycle, witness, 0)` for that witness/cycle.
3. As the witness produces blocks in that cycle, `Manager` invokes `payBlockReward`/`payTransactionFeeReward` → `payReward()`, which stores the delegator-share portion via `delegationStore.addReward(cycle, witnessAddress, value)` with no check on the zero vote total.
4. Any later call to `withdrawReward`/`queryReward` for that cycle invokes `computeReward`, which skips the reward entirely because `totalVote == 0`, permanently stranding the stored TRX.

```java
  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
```
