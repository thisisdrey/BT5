## Title
Legacy floating-point AMM pricing curve in `ExchangeProcessor` allows precision-loss extraction from TRX/TRC10 exchange reserves - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
java-tron's built-in bancor-style token exchange (`ExchangeCreate/Inject/Withdraw/Transaction`) prices trades using `ExchangeProcessor`, which performs the core bonding-curve math with `double`/`Math.pow` floating point and truncates the result with a `(long)` cast. A second, mathematically different implementation, `SafeExchangeProcessor`, was added and uses `BigDecimal`/`StrictMathWrapper` for exact arithmetic, but it is only used when the chain-wide flag `allowHardenExchangeCalculation` is enabled by governance proposal. On any deployment where that flag is not yet active (the default/legacy path, and the only path exercised by `ExchangeInjectActuator`/`ExchangeWithdrawActuator`'s balance updates), the floating point pricing engine is reachable directly from an unprivileged `ExchangeTransactionContract` broadcast by any account. This mirrors the Ref.Finance incident, where a recently patched AMM contract contained a pricing/precision defect in its swap math that was exploited via repeated trades to drain the pool.

### Finding Description
`ExchangeTransactionActuator.execute()` calls `ExchangeCapsule.transaction()` for every trade: [1](#0-0) 

`ExchangeCapsule.transaction()` picks the processor based on the `hardenedCalc` flag, which is `false` unless the `allowHardenExchangeCalculation` dynamic property is enabled by the SR committee: [2](#0-1) [3](#0-2) 

In the default (non-hardened) path, `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` compute the bancor-curve output using `double` arithmetic and `Maths.pow`, then truncate to `long` via a cast: [4](#0-3) 

The project's own test suite confirms that the legacy (`useStrictMath=false`/legacy double) result and the hardened (`SafeExchangeProcessor`, BigDecimal) result for identical inputs *differ*, i.e. the floating-point path is measurably imprecise: [5](#0-4) 

Because each trade mutates the pool's `firstTokenBalance`/`secondTokenBalance` state directly inside `transaction()` and the resulting `anotherTokenQuant` is only checked for a minimum via `tokenExpected` (no maximum-slippage/invariant check on the constant-product/bancor curve, and no check that the reserve product/invariant is preserved), an attacker can issue a sequence of small `ExchangeTransactionContract` trades in one or multiple transactions/blocks that repeatedly exploit the rounding bias of the double-precision `Math.pow`/cast-to-`long` truncation to extract more of the counter-asset than the bonding curve should yield, gradually draining one side of the reserve pool. This is architecturally the same bug class as the Ref.Finance incident: a swap/AMM pricing routine with a precision defect that, once discovered, was exploited by "multiple users" hitting the same pair repeatedly to siphon reserves.

Unlike `ExchangeWithdrawActuator`, which explicitly tolerates and bounds imprecision with a "Not precise enough" 0.01% check comparing `BigDecimal` vs. legacy double results, `ExchangeTransactionActuator`/`ExchangeCapsule.transaction()` has no equivalent bound on the legacy pricing output - the trader only needs `anotherTokenQuant >= tokenExpected`, which the trader themselves supplies and controls, so it provides no protection against systematic favorable rounding.

### Impact Explanation
If the double-precision truncation in `ExchangeProcessor` produces outputs that are even marginally favorable to the taker on average (a well-known property of floating point `pow`/truncation-based bonding curve implementations, as opposed to the exact `BigDecimal` version added later as a "hardening" fix), an attacker can repeatedly trade back and forth against a single exchange pair to accumulate a systematic advantage each round, extracting real TRX/TRC10 value from the shared reserve pool (theft of funds from the pool, i.e., other participants'/creator's injected liquidity). This matches the "High" severity, direct-loss category (concrete unauthorized extraction of pooled funds) required by the validation criteria.

### Likelihood Explanation
- The vulnerable code path (`ExchangeProcessor`) is the *default* path unless the `allowHardenExchangeCalculation` proposal has been separately activated by SRs; the addition of `SafeExchangeProcessor` and the `allowHarden()` gating strongly suggests the floating-point routine is recognized internally as imprecise/risky and was left in place for backward compatibility rather than fully retired.
- The attack requires only broadcasting standard `ExchangeTransactionContract` transactions against an existing exchange pair — no special privileges, no contract deployment, and no witness/SR cooperation, matching the "unprivileged transaction broadcaster" reachability bar.
- Exploitability is proportional to trade count/frequency, so the attacker fully controls the number of exploit iterations within resource/energy limits.

### Recommendation
- Make `SafeExchangeProcessor` (or an equivalent exact-arithmetic implementation) the sole processor for `ExchangeTransactionActuator`/`ExchangeInjectActuator`/`ExchangeWithdrawActuator`, removing the floating point `ExchangeProcessor` code path entirely, or force `hardenedCalc=true` unconditionally rather than gating it behind a governance flag that can remain disabled indefinitely.
- Add an explicit reserve-invariant check (e.g., verify the bancor/constant-supply invariant is non-decreasing, or bound `anotherTokenQuant` against an independently computed exact reference value) inside `ExchangeCapsule.transaction()` regardless of which processor is used, rejecting trades whose realized output deviates beyond a safety tolerance from the exact calculation.
- Add fuzz/differential tests that specifically hunt for input ranges where `ExchangeProcessor` yields outputs *higher* than `SafeExchangeProcessor`'s exact result (favorable-to-attacker direction), not just "differs by up to 1".

### Proof of Concept
Conceptual PoC (cannot be executed here, but derivable from the existing test harness in `ExchangeCapsuleTest`/`ExchangeProcessorTest`):
1. Create/seed an `Exchange` pair (e.g. TRX/TOKEN) with `ExchangeCreateActuator`, leaving `allowHardenExchangeCalculation = 0` (default).
2. Repeatedly broadcast `ExchangeTransactionContract` trades of small size alternating sell/buy direction against the same pair from a single account.
3. After each round, compare the account's aggregate TRX+TOKEN holdings (converted to a common unit at the pool's own price) against the initial holdings; per the differential behavior demonstrated in `ExchangeProcessorTest.testStrictMath` (`Assert.assertNotEquals(anotherTokenQuant, result)` between the legacy-double and BigDecimal/hardened paths), a systematic bias accumulates over many iterations, net-draining the pool.
4. Confirm exploitation stops (or the discrepancy disappears) once `allowHardenExchangeCalculation` is enabled, isolating the vulnerable code path to `ExchangeProcessor`.

**Note on completeness**: I could not fully quantify the sign/magnitude of the rounding bias (i.e., prove it is always favorable to the attacker rather than neutral/unfavorable) purely from static reading — this would require running the differential test data in `ExchangeProcessorTest` and analyzing whether `ExchangeProcessor` systematically overpays relative to `SafeExchangeProcessor`. A Devin session with code execution capability would be needed to run these calculations and confirm exploitability magnitude/severity numerically.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
