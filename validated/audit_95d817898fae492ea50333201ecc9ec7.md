### Title
Per-key `TokenBucket` clones inherit a stale shared `base_time`, letting every newly-seen IP instantly claim the full connection burst allowance - ([File: net-utils/src/token_bucket.rs])

### Summary
`TokenBucket`'s time accounting is anchored to a `base_time` set once at bucket construction, with elapsed time computed as `now_since(base_time) - last_update`. `KeyedRateLimiter` creates buckets for previously-unseen keys by `Clone`-ing a single long-lived `prototype_bucket` rather than constructing a fresh bucket. Because `Clone` copies `base_time` (the prototype's original creation instant) and `last_update` (which stays `0` because the prototype itself is never consumed from), every brand-new per-key bucket's first access computes an elapsed time equal to the *entire uptime of the prototype* since it was created, instead of the tiny/zero elapsed time that "just created" should imply. This causes a one-shot huge token credit that saturates the new bucket to its maximum burst capacity immediately, defeating the intended "burst must be earned over time" throttling design — directly analogous to the reported `TokenFaucet` bug where a stale `lastDripTimestamp` let a refill trigger disbursement of a large amount of tokens instantly instead of gradually.

### Finding Description
`TokenBucket::new` stores `base_time = Instant::now()` and initializes `last_update` to `0`: [1](#0-0) 

`time_us()` measures elapsed time as `Instant::now().saturating_duration_since(self.base_time)`, and `update_state` computes credited tokens from `now - last_update`, minting `elapsed * new_tokens_per_us` tokens (capped at `max_tokens`): [2](#0-1) 

`Clone` copies `base_time` and the current `last_update`/`tokens` values verbatim: [3](#0-2) 

`KeyedRateLimiter::consume_tokens` creates a bucket for a never-before-seen key by cloning the single, long-lived `prototype_bucket` held by the limiter, rather than constructing a fresh `TokenBucket`: [4](#0-3) 

Since the `prototype_bucket` itself is never passed through `consume_tokens`/`current_tokens` (only its clones are), its `last_update` stays frozen at `0` from the moment the limiter was constructed, while its `base_time` is fixed at that same construction instant. Every subsequently cloned per-key bucket therefore starts with `last_update = 0` but `base_time` anchored far in the past (relative to however long the limiter/server has been running). The very first `update_state` call for that new key computes `elapsed = now_us(shared base_time) - 0`, i.e. the *entire elapsed process/limiter uptime*, not the (near-zero) time since the individual bucket was actually created. This mints an enormous number of tokens that saturates the new bucket straight to `max_tokens` (the configured burst ceiling) instead of leaving it at the intended `initial_tokens` baseline.

This exact `KeyedRateLimiter`/`TokenBucket` pattern is used by `ConnectionRateLimiter`, which QUIC's `run_server` uses to throttle new incoming connections per source IP: [5](#0-4) [6](#0-5) 

The limiter is explicitly designed so a per-IP bucket starts at the baseline `limit_per_minute` and only grows to the `max_burst` (10x) ceiling gradually, per the code comment "allow for 10x burst to make sure we can accommodate legitimate bursts...". Due to the stale shared `base_time`/`last_update` inherited via `Clone`, this design intent is bypassed: once the QUIC server (and thus the `ConnectionRateLimiter`'s prototype bucket) has been running long enough for `elapsed * new_tokens_per_us` to exceed `max_burst - limit_per_minute` (a matter of minutes for typical configured rates), every subsequently-seen new source IP's bucket is created already fully saturated at `max_burst`, not `limit_per_minute`.

### Impact Explanation
This is a QoS-evasion bug reachable by any unprivileged remote peer that can present new source IP addresses to the QUIC TPU-facing listener (e.g., IPv6 address rotation, botnets, or simply many distinct attacking hosts). Instead of being restricted to `max_connections_per_ipaddr_per_min` connection attempts, each newly observed IP instantly receives the full 10x burst allowance configured via `MAX_CONNECTION_BURST`/`max_burst`, multiplying the effective per-IP connection-flood budget by up to 10x from the very first packet, undermining a core QUIC connection-abuse mitigation (per-IP rate limiting) that is explicitly called out as one of the connection/handshake abuse defenses in `run_server`.

### Likelihood Explanation
High likelihood of being triggered unintentionally on any long-running validator (the flaw activates automatically once the process/limiter has been alive long enough, no special timing or race is required), and trivially exploitable by an attacker who simply connects from previously-unseen source IPs, which is the common case for connection-flood attacks against a public-facing QUIC TPU port.

### Recommendation
Do not `Clone` a shared `prototype_bucket`'s stale `base_time`/`last_update` state into freshly-inserted per-key buckets. Either (a) construct a genuinely new `TokenBucket` (via `TokenBucket::new`) for each new key instead of cloning the prototype, so `base_time`/`last_update` reflect the actual creation instant of that specific bucket, or (b) have `Clone` reset `last_update` to the *new* bucket's own `time_us()` at clone-time so no backlog of unaccounted elapsed time is created. This ensures per-key buckets start at the intended `initial_tokens` baseline rather than immediately saturating to `max_tokens`.

### Proof of Concept
1. Start a `ConnectionRateLimiter::new(limit_per_minute, max_burst = 10 * limit_per_minute, num_shards)` (as done in `run_server`) and let the process run for longer than `(max_burst - limit_per_minute) / (limit_per_minute / 60.0)` seconds (e.g., a few minutes for typical defaults) so the prototype bucket's `base_time` is sufficiently in the past.
2. From a brand-new source IP never previously seen by the limiter, call `register_connection(&new_ip)` `max_burst` times in immediate succession.
3. Observe that all `max_burst` connection attempts succeed instantly (instead of only `limit_per_minute` succeeding immediately with the remainder rate-limited), because the newly-cloned bucket for `new_ip` was already saturated to `max_tokens` on creation due to the stale shared `base_time`/`last_update` computed in `TokenBucket::update_state` (`net-utils/src/token_bucket.rs:162-214`) via the `Clone` used in `KeyedRateLimiter::consume_tokens` (`net-utils/src/token_bucket.rs:303-316`).

    fn time_us(&self) -> u64 {
        cfg_if! {
            if #[cfg(feature="shuttle-test")] {
                self.time_us_override.load(Ordering::Relaxed)
            } else {
                let now = Instant::now();
                let elapsed = now.saturating_duration_since(self.base_time);
                elapsed.as_micros() as u64
            }
        }
    }

    /// Updates internal state of the bucket by
    /// depositing new tokens (if appropriate)
    fn update_state(&self, now: u64) {
        // fetch last update time
        let last = self.last_update.load(Ordering::SeqCst);

        // If time has not advanced, nothing to do.
        if now <= last {
            return;
        }

        // Try to claim the interval [last, now].
        // If we can not claim it, someone else will claim [last..some other time] when they
        // touch the bucket.
        // If we can claim interval [last, now], no other thread can credit tokens for it anymore.
        // If [last, now] is too short to mint any tokens, spare time will be preserved in credit_time_us.
        match self.last_update.compare_exchange(
            last,
            now,
            Ordering::AcqRel,  // winner publishes new timestamp
            Ordering::Acquire, // loser observes updates
        ) {
            Ok(_) => {
                // This thread won the race and is responsible for minting tokens
                let elapsed = now.saturating_sub(last);

                // also add leftovers from previous conversion attempts.
                // we do not care about who uses the spare_time_us, so relaxed is ok here.
                let elapsed =
                    elapsed.saturating_add(self.credit_time_us.swap(0, Ordering::Relaxed));

                let new_tokens_f64 = elapsed as f64 * self.new_tokens_per_us;

                // amount of full tokens to be minted
                let new_tokens = new_tokens_f64.floor() as u64;

                let time_to_return = if new_tokens >= 1 {
                    // Credit tokens, saturating at max_tokens
                    self.add_tokens(new_tokens);
                    // Fractional remainder of elapsed time (not enough to mint a whole token)
                    // that will be credited to other minters
                    (new_tokens_f64.fract() / self.new_tokens_per_us) as u64
                } else {
                    // No whole tokens minted → return whole interval
                    elapsed
                };
                // Save unused elapsed time for other threads
                self.credit_time_us
                    .fetch_add(time_to_return, Ordering::Relaxed);
            }

    /// Clones the TokenBucket with approximate state
