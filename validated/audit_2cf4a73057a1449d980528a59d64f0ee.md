Found the key point: `FindAllBranches` has **no pagination parameters at all** in `FindAllBranchesRequest`, unlike `FindLocalBranches` and `ListRefs` which both have `pagination_params`.### Title
Unbounded `FindAllBranches` iteration allows attacker-controlled ref count to exhaust Gitaly resources - (File: internal/gitaly/service/ref/find_all_branches.go)

### Summary
`FindAllBranchesRequest` has no pagination/limit field, unlike its sibling RPCs `ListRefs` and `FindLocalBranches`, which both carry a `pagination_params` field. Any repository owner/pusher can create an unbounded number of branches/remote-tracking refs (e.g. by pushing many small refs, which is an ordinary, unprivileged git operation), and any subsequent `FindAllBranches` call must materialize and catfile-resolve every single one of them into memory in one RPC invocation with no server-side cap, mirroring the Coinswap `GetAllBalances` pattern of iterating an attacker-inflated collection to exhaustion.

### Finding Description
`FindAllBranchesRequest` is defined without any limit/pagination options: [1](#0-0) 

Compare this to `FindLocalBranchesRequest`, which explicitly has `pagination_params`: [2](#0-1) 

and to `ListRefsRequest`, which was patched with `PaginationParameter` support (per `CHANGELOG.md`, "Add pagination support to ListRefs RPC"): [3](#0-2) [4](#0-3) 

The `FindAllBranches` handler calls `s.findRefs`, which uses `buildFindRefsOpts(ctx, nil)` (no pagination params can ever be supplied since the request has none), meaning `opts.Limit` defaults to `math.MaxInt32`, i.e. effectively unlimited: [5](#0-4) [6](#0-5) 

The writer used for `FindAllBranches`, `newFindAllBranchesWriter`, appends every parsed ref into an in-memory `branches` slice per chunk and, for every single one, performs a `catfile.GetCommit` lookup (spawning per-object resolution work) before sending: [7](#0-6) 

Because `git-for-each-ref` itself has no `--count` limit passed in this code path (unlike `FindRefsByOID` which passes `gitpipe.WithCount(...)`), and the RPC handler enforces no upper bound on iteration count, an attacker who can create an arbitrarily large number of branches/remote-tracking refs in a repository they control (a completely ordinary, unprivileged operation via push) can force any caller of `FindAllBranches` against that repository to iterate and catfile-resolve the entire ref set in a single unbounded loop — directly analogous to the reported Coinswap bug where an attacker inflates an array (via ordinary `AddLiquidity` deposits) that a keeper function must then iterate over in full with no cap.

### Impact Explanation
A single `FindAllBranches` RPC call against a repository containing an attacker-inflated number of refs causes the Gitaly node to spend unbounded CPU/memory/time building the full in-memory branch list and issuing one `catfile.GetCommit` per ref, with no way for the caller to page or cap the amount of work per call. This can starve the RPC (and the git process backing it) of resources, degrading or denying service for that repository and, depending on Gitaly's concurrency-limiting configuration, potentially affecting other repositories sharing the same concurrency slot. This matches the accepted "RPC-handler resource limits" / "DoS of a handler" category.

### Likelihood Explanation
Likely, but bounded by practical constraints. Creating a very large number of refs is a fully unprivileged operation (ordinary `git push` of new branches, or repeated small ref updates), and any workflow that calls `FindAllBranches` (e.g. from GitLab Rails/API on that repository) would then hit this unbounded loop. However, this is a self-inflicted-repository-scope issue: the attacker mostly needs write access to the target repository (their own project or a fork) to inflate its ref count, and other components (Rails-side ref-count limits, quotas) may partially mitigate real-world exploitability. No pagination bypass is required because the RPC field for pagination simply doesn't exist for this RPC.

### Recommendation
- Add a `pagination_params` (or `limit`) field to `FindAllBranchesRequest`, matching the pattern already used for `FindLocalBranchesRequest` and the now-paginated `ListRefsRequest`.
- Thread that field through to `buildFindRefsOpts`/`findRefs` for `FindAllBranches` so callers can page through large ref sets instead of requiring the server to materialize and catfile-resolve them all in one call.
- Consider applying the same fix to `FindAllRemoteBranches`, which shares the same unbounded `findRefs`/writer pattern.

### Proof of Concept
1. As an ordinary user with push access to a repository, script a large number of branch creations (e.g. `for i in $(seq 1 200000); do git push origin HEAD:refs/heads/branch-$i; done`), which is a normal, unprivileged git operation.
2. Have any client (e.g. GitLab Rails, or a direct gRPC client) call `RefService.FindAllBranches` against that repository.
3. Observe that the handler in `find_all_branches.go` has no limit/pagination mechanism available (the request message carries none) and must run `git for-each-ref` plus one `catfile.GetCommit` per branch for all 200k+ refs in a single RPC invocation, consuming disproportionate CPU/memory/time compared to a normal request — the same "attacker inflates an unbounded collection that a handler must fully iterate" pattern as the referenced Coinswap `GetAllBalances` bug.

func (s *server) findAllBranches(in *gitalypb.FindAllBranchesRequest, stream gitalypb.RefService_FindAllBranchesServer) error {
	repo := s.localRepoFactory.Build(in.GetRepository())

	args := []gitcmd.Option{
		// %00 inserts the null character into the output (see for-each-ref docs)
		gitcmd.Flag{Name: "--format=" + strings.Join(localBranchFormatFields, "%00")},
	}

	patterns := []string{"refs/heads", "refs/remotes"}

	if in.GetMergedOnly() {
		defaultBranch, err := repo.GetDefaultBranch(stream.Context())
		if err != nil {
			return fmt.Errorf("default branch name: %w", err)
		}

		args = append(args, gitcmd.Flag{Name: fmt.Sprintf("--merged=%s", defaultBranch.String())})

		if len(in.GetMergedBranches()) > 0 {
			patterns = nil

			for _, mergedBranch := range in.GetMergedBranches() {
				patterns = append(patterns, string(mergedBranch))
			}
		}
	}

	ctx := stream.Context()
	objectReader, cancel, err := s.catfileCache.ObjectReader(ctx, repo)
	if err != nil {
		return fmt.Errorf("creating object reader: %w", err)
	}
	defer cancel()

	opts := buildFindRefsOpts(ctx, nil)
	opts.cmdArgs = args

	writer := newFindAllBranchesWriter(stream, objectReader)

	if err = s.findRefs(ctx, writer, repo, patterns, opts); err != nil {
		return fmt.Errorf("finding refs: %w", err)
	}

	return nil
}

func newFindAllBranchesWriter(stream gitalypb.RefService_FindAllBranchesServer, objectReader catfile.ObjectContentReader) lines.Sender {
	return func(refs [][]byte, hasNextPage bool) error {
		var branches []*gitalypb.FindAllBranchesResponse_Branch
		ctx := stream.Context()

		for _, ref := range refs {
			elements, err := parseRef(ref, len(localBranchFormatFields))
			if err != nil {
				return err
			}
			branch, err := buildAllBranchesBranch(ctx, objectReader, elements)
			if err != nil {
				return err
			}
			branches = append(branches, branch)
		}
		return stream.Send(&gitalypb.FindAllBranchesResponse{Branches: branches})
	}
}

func buildPaginationOpts(ctx context.Context, p *gitalypb.PaginationParameter) *paginationOpts {
	opts := &paginationOpts{}
	opts.IsPageToken = func(_ []byte) bool { return true }
	opts.Limit = math.MaxInt32

	if p == nil {
		return opts
	}

	if p.GetLimit() >= 0 {
		opts.Limit = int(p.GetLimit())
	}

	if p.GetPageToken() != "" {
		opts.IsPageToken = func(line []byte) bool {
			// Only use the first part of the line before \x00 separator
			if nullByteIndex := bytes.IndexByte(line, 0); nullByteIndex != -1 {
				line = line[:nullByteIndex]
			}

			return bytes.Equal(line, []byte(p.GetPageToken()))
		}
		opts.PageTokenError = true
	}
