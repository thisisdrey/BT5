### Title
StackerDB config refresh silently falls back to a fully-permissive `noop()` config on any contract-eval failure, erasing the contract's `write-freq`/`max-writes` limits - (File: stackslib/src/net/stackerdb/mod.rs)

### Summary
`StackerDBs::create_or_reconfigure_stackerdbs` derives each StackerDB's operative config from the bound smart contract every time it is refreshed (once per reward cycle / tip change). If the contract-evaluation call `StackerDBConfig::from_smart_contract` fails for *any* reason, the code substitutes `StackerDBConfig::noop()` and stores that as the config actually enforced by the node, rather than preserving the previously-loaded (and intentionally restrictive) config. Because `noop()` sets `write_freq = 0` and `max_writes = u32::MAX`, this silently removes the write-rate-limit and max-write-count protections the contract deployer configured, mirroring the SecondSwap bug class where a routine administrative refresh path resets a security-relevant setting back to a permissive default instead of preserving the operator's/issuer's intended value.

### Finding Description
`StackerDBConfig::noop()` is documented as "does nothing" and is explicitly a maximally-permissive fallback: [1](#0-0) 

`create_or_reconfigure_stackerdbs` computes `new_config` for every configured contract on each refresh. When `StackerDBConfig::from_smart_contract` errors (e.g. any `NetError` surfaced from contract evaluation, DB access, or MARF read), the code unconditionally substitutes `StackerDBConfig::noop()`: [2](#0-1) 

The guard that follows only prevents the *slot/signer table* from being wiped when `new_config.signers.is_empty()`: [3](#0-2) 

Critically, this guard says nothing about `write_freq` or `max_writes`. The `noop()` config (with `write_freq: 0`, `max_writes: u32::MAX`) is inserted into `new_stackerdb_configs` and returned unconditionally: [4](#0-3) 

This map becomes `self.stacker_db_configs` via `refresh_stacker_db_configs`, which is called on every tip change / periodic refresh signal: [5](#0-4) [6](#0-5) 

That config is then the one enforced for actual writes. For P2P-relayed chunks, `validate_received_chunk` checks `data.slot_version > config.max_writes` using exactly this in-memory config: [7](#0-6) 

For locally-submitted chunks over the HTTP `POST /v2/stackerdb/.../chunks` endpoint, the write is committed through a `StackerDBTx` whose `self.config` is the same value; `try_replace_chunk` enforces `slot_desc.slot_version > self.config.max_writes`: [8](#0-7) 

And the wall-clock write-frequency throttle used by the sync engine reads `self.write_freq`, which is reloaded straight from the (possibly `noop()`) config on every `reset()`: [9](#0-8) 

So the equality that should hold — "config enforced by the node == config committed on-chain by the contract" — is broken: a transient/incidental failure to evaluate the contract (any `net_error` from `eval_config`/`from_smart_contract`, not limited to genuinely-missing contracts) causes the node to silently *serve/enforce a non-canonical, maximally-permissive config as if it were canonical* for an entire refresh interval, removing the deployer's intended `write-freq` and `max-writes` protections.

### Impact Explanation
This falls under "High - serving non-canonical state as canonical" for a read/write-gating endpoint: an unauthenticated remote peer (or the local HTTP RPC client, gated only by normal StackerDB slot ownership, not by the write-rate-limit itself) can write chunks at a rate/quantity the contract explicitly forbade, as long as the node's config refresh transiently falls into the `from_smart_contract` error branch. Since `write_freq`/`max_writes` exist specifically to bound update rate/volume for a slot (e.g. anti-spam / anti-replay-flood controls for consensus-relevant data such as `.miners` or `.signers` StackerDBs), removing them defeats an intended DoS/spam mitigation and can let a legitimate slot owner (or anyone who can trigger repeated config-eval failures) flood the StackerDB replica and the P2P broadcast path with chunk churn beyond the contract's limits.

### Likelihood Explanation
The trigger condition (any error returned from `StackerDBConfig::from_smart_contract`/`eval_config`) is reached through ordinary operational failure modes already anticipated in the code (see the `warn!("Failed to load StackerDB config")` logging), and the refresh runs automatically once per reward cycle / burnchain-tip change on every node — no privileged access is required to observe or benefit from the resulting window of relaxed limits. Whether an external, unprivileged party can *deterministically force* the contract-eval failure on demand is not fully verifiable from the available code (it depends on the specific contract's `stackerdb-get-config` implementation and node/chain-state conditions), so likelihood is assessed as opportunistic/best-effort rather than fully attacker-controlled on demand.

### Recommendation
On a `from_smart_contract` (or `eval_config`) failure during `create_or_reconfigure_stackerdbs`, do not substitute `StackerDBConfig::noop()` as the enforced config. Instead, retain the previous `stackerdb_config` (the config passed into the loop, which reflects the last successfully-loaded, contract-mandated settings) so that write-rate and write-count limits are never relaxed by a transient error. Reserve `noop()` strictly for first-time bootstrap before any successful load has ever occurred, and make that state explicit (e.g. via an `Option<StackerDBConfig>` or a dedicated "config not yet loaded" flag) rather than a config value that also happens to be maximally permissive.

### Proof of Concept
1. Configure a StackerDB-bound contract with restrictive `write-freq` (e.g. 600s) and `max-writes` (e.g. 3), as in `test_stackerdb_insert_query_chunks`/`test_reconfigure_stackerdb`, which set `db_config.max_writes = 3; db_config.write_freq = 120;`: [10](#0-9) 
2. Induce (or wait for) `StackerDBConfig::from_smart_contract` to return an `Err` on a subsequent refresh (e.g. transient `eval_read_only` failure) — `create_or_reconfigure_stackerdbs` will log a warning and substitute `StackerDBConfig::noop()`: [11](#0-10) 
3. Because `noop().signers.is_empty()`, the `!new_config.signers.is_empty()` guard prevents any slot/table reconfiguration, so the DB replica keeps its existing signer/slot assignments — but the returned config (`write_freq=0`, `max_writes=u32::MAX`) is installed into `self.stacker_db_configs`.
4. Any existing slot owner can now submit chunks with slot versions far beyond the contract's original `max-writes=3` bound and at a rate far exceeding `write-freq=120s`, and both the HTTP `try_replace_chunk` path and the P2P `validate_received_chunk` path will accept them, since both read `config.max_writes`/`config.write_freq` from the now-`noop()`-populated map: [12](#0-11) [7](#0-6)

impl StackerDBConfig {
    /// Config that does nothing
    pub fn noop() -> StackerDBConfig {
        StackerDBConfig {
            // Cap the chunk size at the protocol-wide maximum rather than u64::MAX.
            // `noop()` is used as a fallback whenever a replica's real config can't be
            // loaded (see `create_or_reconfigure_stackerdbs`), and it can transiently
            // overwrite a good in-memory config on a failed refresh. Since the DB slots
            // persist independently of the config, writes can still land on existing
            // slots while `noop()` is active, so its chunk-size limit must never be
            // looser than `STACKERDB_MAX_CHUNK_SIZE`.
            chunk_size: STACKERDB_MAX_CHUNK_SIZE as u64,
            write_freq: 0,
            max_writes: u32::MAX,
            hint_replicas: vec![],
            max_neighbors: 8,
            signers: vec![],
        }
    }
