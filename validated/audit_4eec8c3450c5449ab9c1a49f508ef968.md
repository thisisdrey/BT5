### Title
Unvalidated `BackupId` enables path traversal into other repositories' backup manifests/bundles - (File: internal/gitaly/service/repository/restore_repository.go, internal/backup/locator.go, internal/backup/backup.go)

### Summary
`RestoreRepository`'s server-side handler validates `PathPrefix` against traversal via `backup.ValidatePathPrefix`, but never validates the `BackupId` field. `BackupId` is concatenated with the repository's storage name and relative path via `filepath.Join` to build the manifest/bundle path (`manifests/<storage>/<relative_path>/<backup_id>.toml`, and bundle paths `<prefix>/<storage>/<relative_path>/<backup_id>/NNN.bundle`), so a `BackupId` containing `../` sequences can walk out of the caller's own repository's backup namespace and resolve to another repository's manifest/bundle path within the same backup sink.

### Finding Description
`RestoreRepository` calls `validateRestoreRepositoryRequest`, which validates `Repository`, `VanityRepository`, and `PathPrefix` (via `backup.ValidatePathPrefix`), but performs **no validation on `in.GetBackupId()`** before passing it into `manager.Restore`: [1](#0-0) 

`Manager.Restore` forwards `req.BackupID` unmodified into `mgr.locator.Find(ctx, req.VanityRepository, req.BackupID, locatorOpts...)`: [2](#0-1) 

`ManifestLocator` documents and implements its path scheme as `manifests/<repo_storage_name>/<repo_relative_path>/<backup_id>.toml`, and the bundle/ref/hooks paths for a backup step are built with `filepath.Join(cfg.pathPrefix, storageName, relativePath, backupID, "001.bundle")`: [3](#0-2) 

`filepath.Join` calls `filepath.Clean`, which resolves `..` segments lexically. Because `backupID` is placed as a path component *after* `relativePath`, a crafted value such as `../../<victim-storage>/<victim-relative-path>/<victim-backup-id>` cancels out the caller's own `relativePath`/`storageName` segments and resolves to an arbitrary sibling path inside the backup sink — i.e., another repository's manifest or bundle directory — while the caller's own `Repository`/`VanityRepository` fields (which are the only parts subject to `s.locator.ValidateRepository`) remain untouched and pass validation. `ValidatePathPrefix` would have caught this pattern (it explicitly rejects `..` components), but it is never applied to `BackupID`.

Once `Find`/`ReadManifest` returns the victim's `Backup` object (with `Steps[].BundlePath` pointing at the victim's real bundle), the flow proceeds unchecked into `restoreFromBundle -> restoreBundle -> repo.FetchBundle`, applying the victim's refs/objects into the attacker's own repository. `FetchBundle` performs no cross-check that the bundle's origin matches the target repository — it is a `Sink` blob path used to construct a Git bundle fetch.

This satisfies the audited invariant violation: repository isolation is broken because the served backup content is not verified to have originated from the requesting repository's own backup lineage.

### Impact Explanation
An attacker who can trigger `RestoreRepository` (or `gitaly-backup restore` with server-side backups) on a project they control can, by supplying a crafted `BackupId` (and optionally `PathPrefix`) targeting another project's known `storage/relative_path`, cause that other project's committed objects/refs to be pulled into their own, attacker-visible repository — exposing another project's private source code. This matches GitLab's "unauthorized access to another user's private data / cross-tenant data exposure" bounty impact class.

### Likelihood Explanation
Exploitation requires:
1. Server-side backups configured and `RestoreRepository` reachable (stated precondition).
2. Knowledge of the victim's Gitaly `storage_name` and `relative_path` — these are typically derived deterministically (e.g., hashed-storage paths keyed off project ID), which is often inferable from public project metadata, and/or achievable via prior access to a project the attacker previously had access to.
3. Knowledge/guessing of a valid `backup_id` for the victim (scheduled/date-based backup IDs used by common backup cron jobs are frequently predictable strings).

Given these, the attack is fully client-driven (a single crafted RPC field), requires no elevated privileges beyond triggering a restore against a repository they own, and is repeatable.

### Recommendation
Validate `BackupId` the same way `PathPrefix` is validated — reject empty-after-clean segments, absolute paths, and any `..` components — before it is used in any `filepath.Join` for locating manifests, bundles, refs, or custom-hooks archives. Apply this check both in `validateRestoreRepositoryRequest`/`validateBackupRepositoryRequest` (gRPC entry points) and defensively inside `ManifestLocator.Find`/`FindLatest`/`ReadManifest` so that any caller (including the `gitaly-backup` CLI path) is protected. Additionally, consider embedding an integrity/ownership binding (e.g., the manifest records the exact `storage_name`/`relative_path` it was created for, and `Find` cross-checks the resolved manifest's recorded repository identity against the requested `Repository`/`VanityRepository` before honoring `Steps[].BundlePath`) as defense in depth.

    backupData := backupLocator.BeginFull(ctx, victimRepo, "victim-backup-id")
    // ... write bundle/refs for victimRepo's backupData.Steps, backupLocator.Commit(...)

    // Attacker's own repo, e.g. relative path "attacker/repo.git"
    attackerRepo, attackerPath := gittest.CreateRepository(t, ctx, cfg, gittest.CreateRepositoryConfig{RelativePath: "attacker/repo.git"})

    require.NotEqual(t, expectedEmptyChecksum, checksum) // victim objects now present in attacker repo
}

Expected (fixed) behavior: `RestoreRepository` should return an `InvalidArgument` error rejecting the traversal-containing `BackupId`, matching the existing `ValidatePathPrefix` error contract.

func (s *server) validateRestoreRepositoryRequest(ctx context.Context, in *gitalypb.RestoreRepositoryRequest) error {
	if err := s.locator.ValidateRepository(ctx, in.GetRepository(),
		storage.WithSkipRepositoryExistenceCheck(),
	); err != nil {
		return fmt.Errorf("repository: %w", err)
	}

	if err := s.locator.ValidateRepository(ctx, in.GetVanityRepository(),
		storage.WithSkipStorageExistenceCheck(),
	); err != nil {
		return fmt.Errorf("vanity repository: %w", err)
	}

	if err := backup.ValidatePathPrefix(in.GetPathPrefix()); err != nil {
		return err
	}

	return nil
}

// ManifestLocator locates backup paths based on manifest files that are
// written to a predetermined path:
//
//	manifests/<repo_storage_name>/<repo_relative_path>/<backup_id>.toml
//
// It relies on Fallback to determine paths of new backups.
type ManifestLocator struct {
	Loader ManifestLoader
}

// NewLocator builds a new ManifestLocator.
func NewLocator(sink *Sink) ManifestLocator {
	return ManifestLocator{
		Loader: NewManifestLoader(sink),
	}
}

// BeginFull returns a tentative first step needed to create a new full backup.
func (l ManifestLocator) BeginFull(ctx context.Context, repo storage.Repository, backupID string, opts ...Option) *Backup {
	cfg := applyOptions(opts)
	storageName := repo.GetStorageName()
	relativePath := repo.GetRelativePath()

	return &Backup{
		ID:         backupID,
		Repository: repo,
		Steps: []Step{
			{
				BundlePath:      filepath.Join(cfg.pathPrefix, storageName, relativePath, backupID, "001.bundle"),
				RefPath:         filepath.Join(cfg.pathPrefix, storageName, relativePath, backupID, "001.refs"),
				CustomHooksPath: filepath.Join(cfg.pathPrefix, storageName, relativePath, backupID, "001.custom_hooks.tar"),
			},
		},
	}
}
