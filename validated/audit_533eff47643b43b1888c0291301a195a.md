### Title
Unbounded array allocation from attacker-controlled length word in TVM precompiled contract input parsing causes JVM OutOfMemoryError - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`PrecompiledContracts.extractBytesArray` and `extractBytes32Array` read an array-length value directly from the ABI-encoded precompile input (a `DataWord`) and immediately use it to allocate a Java array of that size, with no upper bound check against the actual size of the supplied call data. This is the same bug class as the Keycloak advisory (CWE-1284, Improper Validation of Specified Quantity in Input): an untrusted, attacker-supplied "length" field is trusted for a memory-allocation decision, allowing a single call to force the JVM to attempt a huge allocation and throw `OutOfMemoryError`.

### Finding Description
`extractBytes32Array` and `extractBytesArray` take the length purely from the input words themselves: [1](#0-0) 

```
private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    ...
}

private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    ...
}
```

`len` comes from `words[offset].intValueSafe()`, which converts an arbitrary 256-bit word supplied by the caller into a Java `int` (clamped to `Integer.MAX_VALUE` for large values, per the `DataWord.intValueSafe()` semantics used throughout the VM code, e.g. `codeCopyAction`/`extCodeCopyAction` at [2](#0-1)  which also allocate `new byte[lengthData]` directly from an unchecked `intValueSafe()` value). There is no check that `len` (which can be as large as `Integer.MAX_VALUE`, i.e. up to ~2 billion) fits within the actual length of `data`/`words` before the `new byte[len][]` allocation executes. A `byte[][]` array of that size alone (ignoring the elements) requires multiple gigabytes of heap for just the reference array, and any subsequent per-element allocation compounds this.

These helpers are the input-parsing entry points used by TVM precompiled contracts that accept dynamic array parameters (e.g., the `ValidateMultiSign` / `BatchValidateSign` precompiles, exercised in `framework/src/test/java/org/tron/common/runtime/vm/ValidateMultiSignContractTest.java` and `BatchValidateSignContractTest.java`), which are reachable by any unprivileged smart-contract call that invokes the corresponding precompiled contract address with crafted call data.

### Impact Explanation
A contract deployer or any transaction broadcaster can trigger this by calling a precompiled contract (through a deployed contract or directly) with a manipulated length word inside the ABI-encoded input. The resulting `new byte[len][]` allocation attempt can throw an `OutOfMemoryError` in the node's JVM. Because `OutOfMemoryError` is a `Throwable`, not a checked exception, and can occur outside normal `Exception`-based error handling paths in TVM execution, it risks destabilizing or crashing the full node process, producing a denial of service for all users served by that node — directly analogous to the Keycloak JVM-crash-via-OOM scenario described in the advisory.

### Likelihood Explanation
Likelihood is high for any node processing TRC-20-style/precompile calls: no privileged role is required, only crafting a transaction/contract call whose input data contains a large length field at the position read by `extractBytesArray`/`extractBytes32Array`. Energy/gas metering constrains execution steps but does not constrain the size of a single Java array-allocation call, so the attack cost is a single, cheap-to-construct transaction.

### Recommendation
Validate `len` against a sane bound (e.g., derived from `data.length` / `words.length` and/or a hard maximum array-size constant) before allocating `new byte[len][]` in both `extractBytesArray` and `extractBytes32Array`, throwing a `BytecodeExecutionException`/`ContractValidateException` instead of allocating on unchecked attacker input — mirroring the bounds checks already present elsewhere (e.g., `RLP.verifyLength`, `Memory.checkMemorySize`, `ContractEventParser.subBytes`).

### Proof of Concept
1. Deploy or call an existing contract that invokes a TVM precompiled contract using the array-based ABI encoding handled by `extractBytesArray`/`extractBytes32Array` (e.g., `ValidateMultiSign`/`BatchValidateSign`).
2. Encode the call data so the length word at the expected array-offset is a very large value (e.g., close to `Integer.MAX_VALUE`) while the remaining data buffer is small/normal.
3. Submit the transaction; when the precompiled contract's `execute` path calls `extractBytesArray`/`extractBytes32Array`, `new byte[len][]` is invoked with the attacker-controlled `len`, triggering excessive memory allocation and an `OutOfMemoryError` in the node JVM.

Note: I was unable to fully trace `DataWord.intValueSafe()`'s exact clamping behavior (file read was truncated in the final iteration) or confirm the exact call sites within `execute()` for each precompiled contract due to tool-call limits; a Devin session with full file access would be needed to pin down the precise `intValueSafe()` bound and enumerate every precompile that reaches these two helper methods.

  public static void codeCopyAction(Program program) {
    byte[] fullCode = program.getCode();

    int memOffset = program.stackPop().intValueSafe();
    int codeOffset = program.stackPop().intValueSafe();
    int lengthData = program.stackPop().intValueSafe();

    int sizeToBeCopied = lengthData;
    if ((long) codeOffset + lengthData > fullCode.length) {
      sizeToBeCopied = fullCode.length < codeOffset ? 0 : fullCode.length - codeOffset;
    }

    byte[] codeCopy = new byte[lengthData];

    if (codeOffset < fullCode.length) {
      System.arraycopy(fullCode, codeOffset, codeCopy, 0, sizeToBeCopied);
    }

    program.memorySave(memOffset, codeCopy);
    program.step();
