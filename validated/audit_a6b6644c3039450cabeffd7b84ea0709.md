Confirmed: `CDH::compressed_file_size()`, `CDH::uncompressed_file_size()`, and `CDH::local_header_offset()` all index into a `Zip64ExtraField` via `attr64(index)` using an index computed from the 32-bit-sentinel flags of *other* fields, with no check against the extra field's own `attr_count()`. This is called from `OutputJar::AddJar` in `output_jar.cc` while merging input JARs (e.g., building a `deploy.jar` / combining dependency jars), so a malicious jar dependency can trigger an out-of-bounds heap read — directly analogous to the BPF `bpf_tail_call` key-vs-`max_entries` OOB read in CVE-2022-2905.

### Title
Out-of-bounds heap read when parsing Zip64 extra-field attributes in singlejar's `CDH`/`LH` accessors - (File: `src/tools/singlejar/zip_headers.h`)

### Summary
`Zip64ExtraField::attr64(int index)` performs a raw indexed read (`attr_[index]`) into the variable-length `attr_` array with no bounds check against `attr_count()` (derived from the field's own `payload_size()`). Several callers — `CDH::compressed_file_size()`, `CDH::uncompressed_file_size()`, `CDH::local_header_offset()`, and the equivalent `LH` accessors — compute the index they pass to `attr64()` from the *sentinel* (`0xFFFFFFFF`) state of unrelated 32-bit fields (`compressed_file_size32()`, `uncompressed_file_size32()`, `local_header_offset32()`), not from the extra field's declared attribute count. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
A crafted JAR/ZIP entry can set some of `compressed_file_size32`/`uncompressed_file_size32`/`local_header_offset32` to the ZIP64 sentinel `0xFFFFFFFF` (signaling "value stored in the Zip64 extra field") while the *actual* Zip64 extra field it carries declares a smaller `attr_count()` (i.e., a shorter `payload_size()`) than the number of sentinel flags set. `Zip64ExtraField::find()` only validates that the *entire* extra field (header + declared payload) fits within the CDH/LH's `extra_fields` buffer bounds; it never checks that `attr_count()` matches the number of sentineled fields that the caller is about to index. [4](#0-3) 

For example, `CDH::local_header_offset()` computes `attr_no` by summing the sentinel flags of `uncompressed_file_size32()` and `compressed_file_size32()` (0, 1, or 2), then calls `z64->attr64(attr_no)` unconditionally, even though the Zip64 extra field might only have `attr_count() == 0` or `1` if `payload_size()` is small. [3](#0-2) 

This is reached from `OutputJar::AddJar`, which iterates the central directory of an input JAR being merged (e.g., a dependency JAR consumed while building a `deploy.jar` via singlejar) and calls `jar_entry->local_header_offset()`, `no_size_in_local_header()`, and other size accessors on attacker-controlled `CDH` records. [5](#0-4) 

The bug class matches CVE-2022-2905 precisely: an index (`attr_no`/fixed indices `0`/`1`) is used to read from an array (`attr_[]`) whose real size (`attr_count()`, analogous to `max_entries`) is never checked before the read.

### Impact Explanation
Reading `attr_[attr_no]` past the declared/allocated Zip64 extra-field payload causes an out-of-bounds heap read within singlejar's memory-mapped input buffer or heap-allocated combiner buffers. This can leak adjacent memory bytes into the computed size/offset value, which then flows into `WriteBytes`/`memcpy` length or offset calculations in `output_jar.cc`, potentially corrupting the produced deploy jar or, if the extra field sits near the end of the mapped file, reading past the mapping into unrelated memory (crash or information disclosure of adjacent process memory).

### Likelihood Explanation
Any dependency consumed as an input JAR to a `java_binary`/`java_library` deploy-jar build (fetched via `http_jar`, `http_archive`, a Maven registry, or checked into an untrusted branch) can be a hostile ZIP crafted with inconsistent Zip64 sentinel flags vs. extra-field payload length. A declared `sha256`/`integrity` on the download only pins the byte-for-byte content of that malicious JAR — it does not stop the internal structural inconsistency from being served in the first place, since the attacker controls the JAR's bytes (and therefore its own checksum) from the start.

### Recommendation
In `Zip64ExtraField::attr64()` (or at each call site), verify `index < attr_count()` before dereferencing `attr_[index]`, and treat a mismatch between the number of ZIP64-sentineled 32-bit fields and the extra field's `attr_count()` as a corrupt-archive error (as is already done for other consistency checks such as `EnsureRemaining` in `third_party/ijar/zip.cc` and the malformed-extra-field check in `output_jar.cc`). [6](#0-5) 

### Proof of Concept
Construct a minimal ZIP central directory entry (`CDH`) where:
1. `compressed_file_size32` and `uncompressed_file_size32` are both set to `0xFFFFFFFF` (2 sentinel flags set → expects `attr_no` up to 2 for `local_header_offset()`, or index `1` for `compressed_file_size()`).
2. `local_header_offset32` is also `0xFFFFFFFF`.
3. The attached Zip64 extra field has `payload_size() == 8` (i.e., `attr_count() == 1`, only one 64-bit attribute present).

Feed this crafted JAR as an input to `OutputJar::AddJar` (e.g., via a `singlejar` JUnit/`gtest` test in `src/tools/singlejar/zip_headers_test.cc` or `output_jar_simple_test.cc` constructing such a `CDH` in a byte buffer). Calling `cdh->local_header_offset()` then invokes `z64->attr64(2)`, reading 16 bytes past the 8-byte `attr_` payload allocated for that extra field — an out-of-bounds read demonstrable with AddressSanitizer/heap-buffer-overflow detection under a `BuildIntegrationTestCase`-style test that merges such a crafted jar via singlejar.

  static const ExtraField* find(uint16_t tag, const uint8_t* start,

      if (ziph::byte_ptr(start) + sizeof(ExtraField) > ziph::byte_ptr(end)) {
        break;
      }
      auto extra_field = reinterpret_cast<const ExtraField*>(start);

        break;
      }
      if (extra_field->is(tag)) {
        return extra_field;
      }
      start = ziph::byte_ptr(start) + extra_field->size();
    }

  }
