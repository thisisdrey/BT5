### Title
Integer overflow in Mach-O segment section-count bounds check causes out-of-bounds slice access - ([File: src/cmd/link/internal/loadmacho/ldmacho.go])

### Summary
`unpackcmd` in the Go linker's Mach-O object loader allocates a section slice sized by an attacker-controlled `nsect` field *before* validating that the load command actually contains enough bytes for that many sections, and the validation itself is done with 32-bit multiplication that can overflow and wrap to a small value. A crafted Mach-O object file with a huge `nsect` can pass the (overflowed) size check and then drive the subsequent parsing loop to slice `p` past its actual length, causing an out-of-bounds/slice-bounds-out-of-range condition — the same "integer overflow during untrusted object loading places data outside allocated bounds" root cause as CVE-2025-30405, just surfaced in `cmd/link`'s object-file loader rather than ExecuTorch's model loader.

### Finding Description
`unpackcmd` is called by the Mach-O load-command dispatcher in `src/cmd/link/internal/loadmacho/ldmacho.go` while iterating over load commands in an object file being linked (`LdMachoCmdSegment` / `LdMachoCmdSegment64` cases). For `LdMachoCmdSegment`: [1](#0-0) 
`c.seg.nsect` is read directly from the file as a `uint32` (`e4(p[48:])`), then `c.seg.sect = make([]ldMachoSect, c.seg.nsect)` allocates a slice sized by that untrusted value *before* any check that the load-command size `sz` actually contains `nsect` section headers. The subsequent check `uint32(sz) < 56+c.seg.nsect*68` performs the multiplication in `uint32` arithmetic; for a large enough `nsect` (e.g. around `0x3D70A3` or higher, chosen so `nsect*68 mod 2^32` becomes small), `56+c.seg.nsect*68` wraps around to a small number, so the check spuriously passes even though the real command payload (`p`) is far shorter than required. The loop then does `p = p[68:]` and `p[0:16]`, `p[32:]`, etc., `nsect` times, walking past the real end of `p`, which is only backed by the actual (small) command bytes read from the file. The 64-bit variant (`LdMachoCmdSegment64`, `56+... -> 72+c.seg.nsect*80`) has the identical flaw.

### Impact Explanation
Because Go always bounds-checks slice/array accesses, this manifests as a Go runtime panic (`slice bounds out of range`) rather than silent memory corruption, unlike the C/C++ ExecuTorch case. This crashes `cmd/link` (and hence `go build`/`go tool link`) when linking with a malicious/corrupted Mach-O `.o`/`.a` input (e.g., via cgo linking against attacker-supplied static objects, or `go tool link` invoked directly on an untrusted object file). This is a parser-panic/DoS on a build-time tool triggered purely by malformed untrusted input data — it does not require malicious source code execution and does not depend on `go build` "running" attacker code, so it is not excluded by the "go build must not run malicious source" carve-out. It would likely be classified on Go's PUBLIC track as a low-severity, hardening-style panic fix (similar to prior `cmd/link`/`debug/macho`/`debug/elf` malformed-input crash fixes), since exploitation is limited to a build-time DoS, not remote code execution or cross-user data disclosure.

### Likelihood Explanation
The victim workflow is a developer/CI machine running `go build`/`go tool link` and linking against an externally supplied object file or static archive (a realistic cgo/cross-linking scenario) that is malicious or corrupted. The attacker needs no special privileges beyond getting their `.o`/`.a` file into the victim's build inputs (e.g., via a supply-chain dependency shipping a prebuilt object, or a malicious asset in a third-party C library).

### Recommendation
Validate `sz` against `nsect` before allocating `c.seg.sect`, and perform the size arithmetic in a wider (64-bit) type to avoid `uint32` overflow, e.g.:
```go
want := uint64(56) + uint64(c.seg.nsect)*68
if uint64(sz) < want {
    return -1
}
c.seg.sect = make([]ldMachoSect, c.seg.nsect)
```
Apply the analogous fix to the `LdMachoCmdSegment64` branch (`72 + nsect*80`), computing in `uint64` before comparing against `sz`.

### Proof of Concept
```go
package loadmacho

import "testing"

// Demonstrates that unpackcmd's overflow check can be bypassed with a
// crafted nsect value, causing the section-parsing loop to run past the
// real command bytes and panic with "slice bounds out of range".
func TestUnpackcmdOverflow(t *testing.T) {
	defer func() {
		if r := recover(); r == nil {
			t.Fatal("expected panic due to integer-overflow bypass of size check")
		}
	}()

	// nsect chosen so that 56 + nsect*68 overflows uint32 and wraps to
	// a value <= sz, letting a too-small sz pass validation.
	const nsect = 0x3D70A4 // nsect*68 wraps mod 2^32 to a small number
	sz := uint(56 + 8)     // deliberately far too small for nsect sections

	p := make([]byte, sz) // minimal, "real" command bytes
	// set fake nsect field at offset 48 (only valid because sz>=56 here;
	// in the wild sz could be exactly 56 while file claims huge nsect)
	m := &ldMachoObj{} // zero-value byte order etc. assumed little/big set by loader
	c := &ldMachoCmd{}

	// Directly invoke the vulnerable function; this should either:
	// (a) incorrectly return 0 (bypassed check) then panic while
	//     the loop reads/slices past len(p), or
	// (b) at minimum demonstrate that the check accepts an sz that
	//     cannot possibly hold nsect*68+56 bytes.
	unpackcmd(p, m, c, LdMachoCmdSegment, sz)
}
```
Expected assertion: without a fix, the overflowed bounds check in `unpackcmd` allows execution to reach the per-section loop with insufficient backing bytes in `p`, and the loop panics with a slice-bounds-out-of-range error instead of `unpackcmd` returning `-1` for a genuinely too-small `sz`. func unpackcmd(p []byte, m *ldMachoObj, c *ldMachoCmd, type_ uint, sz uint) int {
	e4 := m.e.Uint32
	e8 := m.e.Uint64

	c.type_ = int(type_)
	c.size = uint32(sz)
	switch type_ {
	default:
		return -1

	case LdMachoCmdSegment:
		if sz < 56 {
			return -1
		}
		c.seg.name = cstring(p[8:24])
		c.seg.vmaddr = uint64(e4(p[24:]))
		c.seg.vmsize = uint64(e4(p[28:]))
		c.seg.fileoff = e4(p[32:])
		c.seg.filesz = e4(p[36:])
