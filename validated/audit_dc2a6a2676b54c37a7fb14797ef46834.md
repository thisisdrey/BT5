## Analysis

The Ondo bug class is: a low-level precondition check (`_beforeTokenTransfer`'s blocklist check), which is meant to restrict ordinary user-initiated transfers, is reused inside a privileged/critical function (`burn`) and ends up blocking that privileged operation entirely, even though the privileged operation must always be able to execute regardless of the target account's status.

Zest has a structurally identical pattern in the vault `system-repay` function, which is shared between two very different callers: (1) a normal borrower calling `repay` on the market, and (2) the market's `liquidate` function forcibly repaying debt on behalf of an underwater borrower during liquidation.

### Root cause

Each vault's `system-repay` gates on the vault's `repay` pause flag: [1](#0-0) 

This same `system-repay` is the function the market contract invokes as part of `liquidate` to complete the debt repayment step of a liquidation: [2](#0-1) 

Because the liquidation path funnels through the identical `(asserts! (not (get repay states)) ERR-PAUSED)` check used for voluntary user repayments, there is no differentiation between "user chooses to repay their own healthy/unhealthy position" and "market forcibly repays debt on behalf of a liquidated borrower." The DAO's `set-pause-states` toggles the `repay` flag globally per vault: [3](#0-2) 

If the `repay` pause is set for a given underlying's vault (e.g., during an incident response, an oracle outage, or any operational pause of that asset's repay flow), every attempt to `liquidate` a position whose debt is denominated in that asset will revert at `(try! (vault-system-repay debt-aid debt-to-repay debt-ft debt-address))`, since `system-repay`'s `ERR-PAUSED` check fires unconditionally — with no bypass for the market/liquidator caller.

### Impact

While `repay` is paused for an asset, no position with debt in that asset can be liquidated, even a severely undercollateralized one. Bad debt is not repaid, collateral cannot be seized, and, per the protocol's own bad-debt socialization design, unliquidatable positions accumulate risk without any mitigating action: [4](#0-3) 

This is a **temporary freezing of funds** (liquidator collateral proceeds and the protocol's ability to make itself whole on bad debt) for the duration of the pause, directly analogous to the Ondo finding where a shared precondition check unintentionally blocks a privileged operation that must be unconditionally executable.

### Title
Pausing `repay` on a vault also blocks the market's forced debt-repayment during `liquidate`, freezing liquidations - (File: mainnet/contracts/vault/v0-vault-sbtc.clar / mainnet/contracts/market/v0-4-market.clar)

### Summary
`system-repay` in each vault contract (`v0-vault-sbtc.clar`, `v0-vault-stx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`) checks the vault's `repay` pause flag unconditionally. The market's `liquidate` function calls this same `system-repay` path to complete a liquidation's debt repayment. Because the check does not distinguish between voluntary user repayment and the market's forced liquidation repayment, pausing `repay` on a vault blocks all liquidations of positions with debt in that asset.

### Finding Description
`system-repay` asserts `(not (get repay states))` before performing the debt reduction: [5](#0-4) 

`liquidate` in the market relies on this exact call to reduce the borrower's debt as part of seizing collateral: [6](#0-5) 

There is no separate, always-available code path for the market's system-level repayment during liquidation; it shares the same pausable gate as ordinary user repayments.

### Impact Explanation
When the DAO pauses `repay` for a vault (via `set-pause-states`), the intent is presumably to stop user-initiated voluntary repayments (e.g., for maintenance/incident response). However, this simultaneously disables liquidation of every unhealthy position with debt in that asset, because `liquidate` cannot complete its `vault-system-repay` step. This is a temporary freezing of funds: liquidators cannot seize collateral from unhealthy positions, and the protocol cannot reduce/socialize bad debt for that asset until the pause is lifted, increasing insolvency risk for the affected market while paused.

### Likelihood Explanation
This triggers any time the `repay` pause flag is set true for a vault while any position holds debt in that asset with an LTV above the liquidation threshold — a realistic operational scenario, since pausing `repay` alone (without also pausing accrual or other functions) is a plausible admin action that does not obviously imply "no liquidations."

### Recommendation
Add a caller-aware bypass (e.g., check `contract-caller` is the market contract, similar to `check-caller-auth`) so that `system-repay` invoked from the liquidation path is not blocked by the general `repay` pause flag, or introduce a distinct pause flag for liquidation-driven repayments separate from user-initiated repayments.

### Proof of Concept
1. Borrower opens an undercollateralized position with sBTC collateral and USDC debt.
2. DAO calls `set-pause-states` on the USDC vault, setting `repay: true` (intending only to halt voluntary repayments).
3. Price of sBTC drops, making the position liquidatable.
4. A liquidator calls `market.liquidate(borrower, sbtc-ft, usdc-ft, debt-amount, ...)`.
5. `liquidate` reaches `(try! (vault-system-repay debt-aid debt-to-repay debt-ft debt-address))`, which calls the USDC vault's `system-repay`, which reverts with `ERR-PAUSED` because `repay` is paused.
6. The liquidation transaction reverts; the unhealthy position remains open and un-liquidated for the duration of the pause.
