## Analog Found: Permissionless Purse-Key Squatting DoS in `pallet-scarcity`



### Title
Permissionless Purse-Key Squatting Permanently Blocks Intended NFT/Reward Delivery to a Target Account - (File: `substrate/frame/scarcity/src/lib.rs`)

### Summary
`pallet-scarcity` enforces a "coinage" invariant — each purse key (`T::AccountId`) may hold at most one live NFT at a time, tracked in `NftsByOwner`. Any account can permissionlessly create a collection (`create_collection`) and then, as that collection's owner, mint an instance directly into **any** other account's purse key without that account's consent. Because the map is keyed purely by destination account, an attacker can pre-fill a target account's purse-key slot with a worthless throwaway instance before the intended, legitimate mint or reward payout can land there — exactly mirroring the report's pattern of using a cheap, attacker-controlled action to permanently occupy a uniqueness-checked slot and block the rightful party's use of it.

### Finding Description
The pallet's own module documentation confirms the lack of destination consent: [1](#0-0) 

The underlying storage enforces "one NFT per owner key": [2](#0-1) 

Collection creation itself is permissionless (any signed account becomes a collection owner and gains full control — including minting and force-transferring into arbitrary purse keys), as shown by tests invoking `create_collection`/`force_transfer` from ordinary signed origins with no destination-side authorization check: [3](#0-2) 

Because `mint`/`force_transfer` target an arbitrary `AccountId` chosen entirely by the (attacker-controlled) collection owner, and `NftsByOwner` rejects a second instance while a slot is occupied, an attacker who can predict or observe a victim's purse-key address (e.g., a deterministic reward-distribution account, a known player key, or a fresh key about to be used) can front-run the legitimate mint with a cheap throwaway instance from their own collection. This is functionally identical to the report's "throwaway dispute with the intended evidence hash": a cheap, unprivileged, public-entrypoint action that occupies a uniqueness-checked slot before the legitimate actor can use it — except here the guard is "one live instance per account" rather than "one dispute per evidence hash," and the squatting instance is not even refundable/cancelable by the attacker for a bond (making it strictly worse: the attacker doesn't need a cooldown-and-cancel dance, since minting itself is the entire attack).

### Impact Explanation
Any runtime pallet that integrates `MintWithoutDeposit` (or calls `do_mint`/`mint_into` directly) to automatically deliver rewards, in-game items, or other value to a computed/expected destination account is vulnerable: if the attacker has squatted that account's purse-key slot first, the legitimate payout mint fails outright (the slot is occupied), and there is no way for the runtime/payout logic to force through — someone must notice and separately burn the attacker's junk instance before the payout can be retried. For automated payout flows (matching the "treasury or reward payouts ... must settle exactly once to the rightful beneficiary" impact category), this results in reward/settlement being permanently stuck for the affected accounts. For higher-level game or asset logic that relies on this "coinage" purse model, this is a straightforward, unprivileged fund/asset-delivery denial-of-service.

### Likelihood Explanation
The attack requires no validator, collator, relayer, prover, or admin privilege — any ordinary signed account can call `create_collection` and then `mint`/`force_transfer` into an arbitrary target account. The only precondition is that the attacker can identify the target purse key in advance, which is realistic wherever purse keys are deterministic or publicly known ahead of a scheduled mint/payout (a common pattern for reward distribution). This is a pure implementation/design gap, not a front-run-only mempool race — the attacker can occupy the slot at any point before the legitimate mint, with no time pressure.

### Recommendation
Require destination consent for `mint`/`force_transfer` into a target purse key that the caller does not control, e.g., via a pre-registered "accepting mint from collection X" flag, a pull-based claim mechanism, or restricting unsolicited mints to keys that have never been used/registered by their owner. Alternatively, document and enforce that purse keys used for automated payouts must be single-use and pre-verified empty at the point of construction, and give payout logic a way to detect and route around a squatted slot instead of silently failing.

### Proof of Concept
1. A runtime feature (or off-chain script) plans to reward account `V` (a freshly derived purse key) with an NFT via `Scarcity::mint(owner_origin, collection, item, V, None)` at some future block.
2. Attacker `A` observes/derives `V` in advance, calls `Scarcity::create_collection` (permissionless) to become owner of collection `C_A`, defines a throwaway item, and calls `Scarcity::mint(A_origin, C_A, item, V, None)`.
3. `NftsByOwner::<T>::insert(V, ..)` now holds `A`'s junk instance.
4. When the legitimate reward mint targeting `V` executes, it fails because `NftsByOwner::<T>::get(V)` is already `Some(..)` (per the coinage invariant asserted in the pallet doc and tests), and no automatic remediation exists — `V`'s owner must notice, sign a `burn` transaction on the wrong instance, and only then can a retried legitimate mint succeed, if retried at all.

**Note on scope/uncertainty:** I was unable to fully inspect the `mint`/`force_mint`/`force_transfer` extrinsic bodies (call indices beyond what was captured, e.g., exact permission checks preceding `do_mint`) within the available tool budget; the analysis above rests on the pallet's own documented invariants and the `force_transfer`-related tests confirming permissionless, consent-free writes into arbitrary purse keys. A full audit of `mint`'s call-site guard conditions is recommended to confirm there is no destination-consent check I did not see.
