Audit Report

## Title
Relayer rewards are irrecoverably lost when the cross-chain `DepositAsset` to the claimed beneficiary fails, because the fallback asset-trap claimer is bound to a synthetic bridge origin the relayer cannot control - (File: `bridges/snowbridge/primitives/core/src/reward.rs`)

## Summary
`PayAccountOnLocation::pay_reward` builds an `UnpaidExecution` XCM containing `UniversalOrigin(GlobalConsensus(EthereumNetwork))` followed by `DepositAsset { assets: AllCounted(1).into(), beneficiary }`, with no `SetAssetClaimer` instruction, and returns `Ok(())` as soon as `XcmSender::deliver` succeeds — not once the remote deposit actually executes. `pallet-bridge-relayers::do_claim_rewards` removes the reward from `RelayerRewards` storage in the same atomic closure that calls `pay_reward`, so the debit is finalized purely on send success. If `DepositAsset` fails on AssetHub, the held assets are trapped under `context.origin`, which by then has been overwritten by the preceding `UniversalOrigin` instruction to `GlobalConsensus(Ethereum)` — a location the relayer cannot sign for — resulting in permanent, unrecoverable loss of the relayer's reward.

## Finding Description
The reward-payout XCM is constructed as:
```rust
let xcm: Xcm<()> = alloc::vec![
    UnpaidExecution { weight_limit: Unlimited, check_origin: None },
    DescendOrigin(InboundQueueLocation::get().into()),
    UniversalOrigin(GlobalConsensus(EthereumNetwork::get())),
    ReserveAssetDeposited(assets.into()),
    DepositAsset { assets: AllCounted(1).into(), beneficiary },
]
``` [1](#0-0) 

No `SetAssetClaimer` is present in this program, so `asset_claimer` in the executor remains `None` for this XCM. On the executor side, if execution traps remaining holding after an instruction (such as `DepositAsset`) fails, the claimer used is:
```rust
let claimer = self
    .asset_claimer
    .as_ref()
    .or(self.context.origin.as_ref())
    .unwrap_or(&self.original_origin);
let trap_weight = Config::AssetTrap::drop_assets(claimer, self.holding, &self.context);
``` [2](#0-1) 

Because `asset_claimer` is `None`, the fallback is `context.origin`, which by the time `DepositAsset` executes has already been overwritten by the preceding `UniversalOrigin(GlobalConsensus(EthereumNetwork))` instruction in the message — a synthetic bridge origin the relayer neither owns nor can produce a matching signed origin for on AssetHub. This is confirmed by the presence and semantics of `UniversalOrigin` handling used throughout the XCM executor and builder test suite [2](#0-1) .

`pay_reward` reports success based solely on delivery, not remote execution:
```rust
let (ticket, fee) =
    validate_send::<XcmSender>(AssetHubLocation::get(), xcm).map_err(|_| XcmSendFailure)?;
XcmExecutor::charge_fees(relayer.clone(), fee).map_err(|_| ChargeFeesFailure)?;
XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;
Ok(())
``` [3](#0-2) 

`do_claim_rewards` debits the on-chain reward record atomically with this call:
```rust
let reward_balance =
    maybe_reward.take().ok_or(Error::<T, I>::NoRewardForRelayer)?;
T::PaymentProcedure::pay_reward(
    &relayer,
    reward_kind,
    reward_balance,
    beneficiary.clone(),
)
.map_err(|e| { ... Error::<T, I>::FailedToPayReward })?;
``` [4](#0-3) 

Since `pay_reward` only validates that the XCM ticket was delivered, and the storage removal (`maybe_reward.take()`) happens unconditionally before the beneficiary's remote deposit is confirmed, any failure of `DepositAsset` on AssetHub (unconvertible beneficiary, ED not met, asset trust issues, etc.) results in the reward being both debited on BridgeHub and trapped on AssetHub under an origin the relayer cannot claim from.

## Impact Explanation
This breaks value conservation for relayer rewards: value is debited from `RelayerRewards` storage on BridgeHub and never successfully or recoverably credited to the intended beneficiary on AssetHub, matching the "permanent user-fund or bridge-state lock" impact category. The root cause is a genuine logic defect in `PayAccountOnLocation::pay_reward` and the interaction between `UniversalOrigin` and the implicit asset-claimer fallback in the XCM executor, not any privileged actor or off-repo behavior.

## Likelihood Explanation
Any unprivileged relayer with an accrued reward can call the public `claim_rewards_to` extrinsic with a `beneficiary` `Location` under `BridgeRewardBeneficiaries::AssetHubLocation`. If that beneficiary cannot be resolved to a valid, ED-satisfying deposit target on AssetHub at execution time (which is plausible given locations are relayer-supplied and remote conditions such as asset trust/pause states can change), the deposit fails and the reward becomes permanently trapped and unclaimable, with no privileged action, malicious actor, or off-repo control required.

## Recommendation
- Do not remove the on-chain reward record (`RelayerRewards`) until successful execution of the remote deposit is confirmed, e.g. via a query-response-tracked settlement or a pending-claim state machine, rather than treating `deliver()` success as final.
- Include a `SetAssetClaimer` instruction in the reward XCM program pointing to a location the relayer actually controls (e.g., their own account or the chosen beneficiary) so that any asset trap is reclaimable, rather than relying on the post-`UniversalOrigin` `context.origin` fallback.
- Validate that `beneficiary` converts to an executable AssetHub deposit target (existential deposit, correct account family, asset trust) before consuming/debiting the on-chain reward.

## Proof of Concept
1. Relayer accrues a `BridgeReward::Snowbridge` reward via `process_delivery_receipt` → `T::RewardPayment::register_reward` [5](#0-4) .
2. Relayer calls `pallet_bridge_relayers::claim_rewards_to` with a `BridgeRewardBeneficiaries::AssetHubLocation` beneficiary that cannot successfully execute `DepositAsset` on AssetHub (e.g., an unconvertible or underfunded location).
3. `do_claim_rewards` removes the reward from `RelayerRewards` and calls `pay_reward`, which returns `Ok(())` once the XCM is delivered [6](#0-5) .
4. On AssetHub, `DepositAsset` fails; remaining holding is trapped under `context.origin`, overwritten by the earlier `UniversalOrigin(GlobalConsensus(EthereumNetwork))` instruction rather than any location the relayer controls [2](#0-1) .
5. The relayer's reward is debited on BridgeHub and permanently unrecoverable on AssetHub.
