### Title
Dust-transfer griefing fills victim's per-account token set to `MAX_TOKENS_PER_USER`, blocking new collateral deposits — ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
The advisory's bug class is attacker-controlled, unbounded growth of a stored collection (nonces) that degrades service. Metronome's analog is the per-account token lists `depositTokensOfAccount` / `debtTokensOfAccount` (`MappedEnumerableSet.AddressSet`) in `Pool`. Any EOA can grow a *victim's* list without consent by transferring dust amounts of `DepositToken`s to them; once the combined list length reaches `MAX_TOKENS_PER_USER` (30), every subsequent first-time deposit, mint, transfer, or SmartFarmingManager position involving a not-yet-listed token reverts with `UserReachedMaxTokens`, denying the victim the ability to add new collateral or debt types.

### Finding Description
`DepositToken._transfer` pushes the token into the recipient's set whenever the recipient balance goes `0 → >0` [1](#0-0) . The same add happens on `_mint` (i.e. on `deposit`) [2](#0-1) . On the `Pool` side, `addToDepositTokensOfAccount` and `addToDebtTokensOfAccount` enforce `onlyIfAdditionWillNotReachMaxTokens`, which reverts once `debt + deposit` token count reaches 30 [3](#0-2) . Only the registered token contract itself may call these functions, but that check is satisfied automatically during a normal `transfer`/`transferFrom` — there is no opt-in or allowance requirement for the *recipient* [4](#0-3) .

Attack trace:
1. Attacker deposits a dust amount of each registered `DepositToken` collateral (or acquires it on market).
2. Attacker calls `depositToken.transfer(victim, 1)` for each token the victim does not already hold. Each call executes `pool.addToDepositTokensOfAccount(victim)`.
3. After `N` such transfers (where `N = 30 - victim's existing deposit/debt token count`), the victim's combined set is full.
4. Any subsequent `deposit` into a new collateral type, any inbound `transfer`/`transferFrom`/`seize` of a new deposit token, and any `issue`/`mint` of a new synthetic asset (which calls `addToDebtTokensOfAccount`) reverts with `UserReachedMaxTokens`.

No modifier stops this: `transfer` only checks the *sender's* `_revertIfLocked` [5](#0-4) ; the recipient's set growth is unauthenticated by the recipient.

### Impact Explanation
The victim is denied the ability to onboard new collateral types and to open new synthetic-debt positions for as long as the set stays full. Concretely: a victim approaching liquidation cannot deposit a *different* collateral to restore health — that deposit reverts — so their position is forcibly liquidated, and SmartFarmingManager `leverage`/deposits involving new tokens revert, temporarily freezing the funds committed to those flows. This is a temporary freezing of funds plus forced-liquidation risk, i.e. a liveness break on a per-account invariant.

### Likelihood Explanation
Two constraints bound feasibility:
- The pool must have enough registered deposit tokens for the attacker to fill the remainder of the victim's 30 slots (each slot needs a distinct registered `DepositToken`); victims already holding several tokens need fewer attacker transfers.
- Cost is one dust deposit + one transfer per slot, all in public entry points; no privileged role is required.

Recovery is possible: the victim can empty a slot by transferring the dust balance to another address (which pops the entry via `removeFromDepositTokensOfAccount`), paying only gas. That caps severity — funds are temporarily frozen / positions exposed to liquidation, not permanently lost — consistent with a Medium-severity analog of the reported DoS.

### Recommendation
- Make per-account set insertion recipient-consensual: e.g. in `DepositToken._transfer`, only call `addToDepositTokensOfAccount` for the recipient if `msg.sender == recipient` or inside `deposit`/`_mint` paths, and handle rewards accounting for non-listed recipients separately.
- Alternatively track collateral membership lazily (derive "is collateral" from `balanceOf > 0` at query time) or bound iteration differently so unsolicited dust cannot consume a scarce slot.

### Proof of Concept
Hardhat sketch against a deployed `Pool`/`DepositToken` set (fork):

```ts
// victim starts with k tokens already in their combined list
const MAX = (await pool.MAX_TOKENS_PER_USER()).toNumber(); // 30
const depositTokens: DepositToken[] = /* all pool-registered deposit tokens */;

// 1) Attacker dust-deposits each token, then transfers 1 wei to victim
for (const dt of depositTokens.slice(0, MAX - k)) {
  await underlying.connect(attacker).approve(dt.address, 1);
  await dt.connect(attacker).deposit(1, attacker.address);      // mints dust msdTOKEN
  await dt.connect(attacker).transfer(victim.address, 1);       // adds to victim's list
}

// 2) Victim now cannot deposit a collateral type not already in their list
const newDt = depositTokens[MAX - k]; // a token victim doesn't hold
await underlying.connect(victim).approve(newDt.address, amount);
await expect(
  newDt.connect(victim).deposit(amount, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// 3) Same for inbound transfers of any new token and for issue() of a new synth
await expect(
  newDt.connect(attacker).transfer(victim.address, 1)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

The revert at step 2 demonstrates the DoS: an unprivileged attacker irreversibly-at-will (until the victim pays gas to sweep dust) blocks the victim's collateral onboarding and new-debt issuance.
