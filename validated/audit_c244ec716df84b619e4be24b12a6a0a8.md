## Analysis

Confirmed: `add_gas_key` (`runtime/runtime/src/access_keys.rs:194-228`) always reseeds *every* nonce slot to `initial_nonce_value(block_height)` = `(block_height-1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER`, with no reference to any nonce value previously consumed by that public key. [1](#0-0) 

`delete_gas_key` (`runtime/runtime/src/access_keys.rs:93-134`) fully erases the per-index nonce rows via `remove_gas_key_nonce`, leaving no persistent high-water mark. [2](#0-1) 

`verify_nonce` (`runtime/runtime/src/verifier.rs:211-237`) is the *sole* replay guard: `Monotonic` mode only requires `tx_nonce > current_nonce`, and the upper bound check is purely `tx_nonce < block_height * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` — it has no memory of nonces used by a since-deleted-and-recreated key. [3](#0-2) 

Both the gas-key path (`verify_and_charge_gas_key_tx_ephemeral`, `verifier.rs:415-419`) and the regular path (`verify_and_charge_tx_ephemeral`, `verifier.rs:300-305`) derive `current_nonce`/`effective_nonce` from the *current* stored access-key/gas-key-nonce state only. [4](#0-3) [5](#0-4) 

Because the reseed value depends only on `block_height` and not on the historically-max nonce ever consumed by that public key, an attacker can: fund a gas key, consume nonce index `i` with a transaction whose nonce is deliberately close to the block's nonce ceiling (`block_height * 1_000_000`), then in a later transaction of the same block (or any later block within the tx validity window) `DeleteKey` + `AddKey` the same public key. This resets index `i`'s stored nonce back down to `(block_height-1) * 1_000_000`, which is below the nonce already used by the earlier gas-key transaction. The already-executed transaction (byte-identical, same signature, same nonce) can then be resubmitted and will pass `verify_nonce` a second time (since `tx_nonce > current_nonce` holds again), and will pass the upper-bound check trivially in any later block (ceiling only grows). This violates "no receipt executes twice" and permits replay/double-charging or double-crediting.

### Title
Gas-key (and regular-key) nonce reseed on AddKey after DeleteKey enables replay of an already-executed high-nonce transaction - (File: runtime/runtime/src/access_keys.rs)

### Summary
`add_gas_key` unconditionally reseeds every gas-key nonce slot to `initial_nonce_value(block_height)` regardless of any nonce value previously consumed on that slot, and `delete_gas_key` discards all historical nonce state. Because `verify_nonce` (the only replay guard) compares only against the current on-chain nonce, an attacker who deliberately uses a nonce near the per-block ceiling, then deletes and re-adds the same gas key, lowers the stored nonce floor below that already-used value, making the original signed transaction valid for resubmission and re-execution.

### Finding Description
`action_add_key` routes gas-key additions to `add_gas_key` (`access_keys.rs:149-192`), which sets every nonce index to `initial_nonce_value(block_height)` via `set_gas_key_nonce` (`access_keys.rs:209-214`), independent of any prior nonce used by that same public key. `action_delete_key` routes gas-key deletion to `delete_gas_key` (`access_keys.rs:93-134`), which calls `remove_gas_key_nonce` for every index (`access_keys.rs:114-117`), erasing all trace of previously consumed nonces.

Replay protection is enforced solely by `verify_nonce` (`verifier.rs:211-237`), which for `NonceMode::Monotonic` requires only `tx_nonce > current_nonce`, where `current_nonce` is read from the live (post-deletion) gas-key-nonce state. There is no mechanism that remembers the maximum nonce ever used by a given public key across a delete/re-add cycle.

Exploit flow (all steps are ordinary signed transactions from the attacker's own funded account, no privileged access needed):
1. Attacker adds a `GasKeyFullAccess` key with `num_nonces >= 1` and funds it via `action_transfer_to_gas_key`.
2. Attacker crafts and submits a gas-key transaction on nonce index `i` using a nonce value close to `block_height * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` (the nonce upper bound checked in `verify_nonce`). It executes normally, debiting the gas-key balance/account and producing a receipt (e.g. a transfer to another account).
3. In a subsequent transaction (same block or a later block within the tx validity window), the attacker submits `DeleteKey` followed by `AddKey` re-adding the identical public key as a gas key again. `add_gas_key` resets index `i`'s stored nonce to `(block_height'-1) * 1_000_000`, which is lower than the nonce used in step 2.
4. The attacker resubmits the exact same signed transaction from step 2. `verify_nonce` now sees `tx_nonce > current_nonce` (true again, since the floor was lowered) and the upper-bound check passes trivially in later blocks. The transaction is re-executed: the gas-key balance/account is charged a second time and the receipt (e.g. transfer) is re-issued.

Existing checks that fail to prevent this: nonce monotonicity is key-state-relative, not globally monotonic per public key; there is no "tombstone" or historical-nonce record retained across a delete+recreate cycle; the upper-bound nonce check only grows with block height so it never blocks a stale-but-lowered-below-floor high nonce.

### Impact Explanation
This breaks the "each nonce/transaction executes exactly once" invariant underpinning replay protection. Concretely it allows an attacker to force re-execution of an already-settled gas-key transaction, causing double debits from the gas-key balance/account and duplicate receipts/transfers, matching the "double-spend/replay" bounty category. If the replayed transaction's receipt affects a third-party contract (e.g., a payment, deposit, or state-changing call), the impact extends beyond the attacker's own balance to unauthorized duplicate execution against other parties.

### Likelihood Explanation
Preconditions are all within an ordinary, unprivileged user's control: fund an account, add and fund a `GasKeyFullAccess` key, craft a transaction with a nonce near the current block's ceiling, then send `DeleteKey`+`AddKey` for the same public key. No validator, node-operator, or protocol-level access is required, and the sequence is fully repeatable (any gas key can be cycled this way at any time the attacker chooses to re-add it). Cost is limited to the normal gas/storage fees of a few transactions.

### Recommendation
Do not derive the reseeded nonce purely from `block_height` when recreating a public key that previously existed. Options: (a) persist a per-account monotonically increasing "nonce watermark" per public key (or globally) that survives key deletion and is used as the floor on re-add, taking `max(initial_nonce_value(block_height), historical_max_nonce_for_this_key)`; or (b) forbid re-adding a public key with the same bytes within some cool-down/validity window after deletion; or (c) tie nonce floors to a monotonically increasing global counter rather than block height, ensuring it can never regress below any nonce ever accepted for that key.

### Proof of Concept
Runtime/test-loop integration test:
1. Create account with `GasKeyFullAccess` key, `num_nonces = 1`, funded balance.
2. At block height `N`, submit gas-key tx on index `0` with nonce `N*1_000_000 - 1` (just under the ceiling); assert success and record `get_gas_key_nonce` == that value, and record receiver's post-balance / gas-key balance.
3. In the same block (or block `N+1`, well within `transaction_validity_period`), submit `DeleteKey` then `AddKey` (same public key, `GasKeyFullAccess`, `num_nonces=1`) for the account.
4. Assert `get_gas_key_nonce(account, pubkey, 0)` is now `(block_height-1)*1_000_000`, i.e. lower than the nonce used in step 2.
5. Resubmit the exact same signed transaction from step 2 (identical bytes/signature/nonce).
6. Assert it is accepted (`TxVerdict::Success`/`SuccessValue`) and executes again — gas-key balance/account debited a second time and the receiver credited a second time — proving replay of an already-settled transaction and violating "no receipt executes twice."

fn verify_nonce(
    tx_nonce: Nonce,
    current_nonce: Nonce,
    block_height: Option<BlockHeight>,
    nonce_mode: NonceMode,
) -> Result<(), InvalidTxError> {
    match nonce_mode {
        NonceMode::Monotonic => {
            if tx_nonce <= current_nonce {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
        NonceMode::Strict => {
            if !current_nonce.checked_add(1).is_some_and(|expected| tx_nonce == expected) {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
    }
    if let Some(height) = block_height {
        let upper_bound = height
            .saturating_mul(near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER);
        if tx_nonce >= upper_bound {
            return Err(InvalidTxError::NonceTooLarge { tx_nonce, upper_bound });
        }
    }
    Ok(())
