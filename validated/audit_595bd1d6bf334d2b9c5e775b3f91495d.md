### Title
Aggregate unstaked stream throughput scales with connection count, not bounded by the intended 20% unstaked share - ([File: streamer/src/nonblocking/stream_throttle.rs])

### Finding Description
`StakedStreamLoadEMA::available_load_capacity_in_throttling_duration` grants every `ConnectionPeerType::Unstaked` connection the *same fixed* per-connection budget, `max_unstaked_load_in_throttling_window`, derived from a constant `MAX_UNSTAKED_TPS = 200` (a comment explicitly labels it "Max TPS allowed for unstaked connection", i.e. per-connection, not cluster-wide): [1](#0-0) [2](#0-1) [3](#0-2) 

`EXPECTED_UNSTAKED_STREAMS_RATIO = 0.20` is used only to *shrink the staked budget* (`max_staked_load_in_ms`) at construction time, so staked connections leave 20% of `max_streams_per_ms` "reserved" for unstaked traffic; it is never used as an actual ceiling on aggregate unstaked throughput: [4](#0-3) 

Critically, `increment_load` — which feeds the EMA driving the adaptive `staked_throttling_enabled` flag — only counts *staked* streams; unstaked stream activity is never fed into any shared/aggregate counter at all: [5](#0-4) 

`SwQos::build_connection_context` classifies any peer with `stake_ratio < min_stake_ratio` as `ConnectionPeerType::Unstaked`, so low/zero-stake accounts qualify: [6](#0-5) 

`try_add_connection` admits unstaked connections up to `SwQosConfig::max_unstaked_connections` (default `DEFAULT_MAX_UNSTAKED_CONNECTIONS = 2000`), pruning the oldest 10% when the table fills, but does not otherwise cap total aggregate throughput: [7](#0-6) [8](#0-7) 

Because each of up to 2000 concurrently-admitted unstaked connections independently gets the full 200 TPS per-connection budget, the theoretical aggregate accepted unstaked stream rate is `2000 * 200 = 400,000` streams/sec — vastly more than the "intended" 20% share of the default `max_streams_per_ms = 500` (i.e. `500,000 * 0.20 = 100,000`/sec), and close to the entire node-wide sigverify/dedup budget. Per-peer/IP connection caps (`DEFAULT_MAX_QUIC_CONNECTIONS_PER_UNSTAKED_PEER = 8`) limit connections per single IP but not the aggregate across many source IPs, which an attacker with many low/zero-stake identities and distributed sources can trivially achieve.

### Impact Explanation
This is a QoS-evasion / CPU-DoS finding: an unprivileged attacker who opens many separate unstaked connections (up to `max_unstaked_connections`) forces the leader's dedup/sigverify pipeline to process aggregate unstaked traffic far above the ~20% share the design intends to allocate to unstaked clients, at the direct expense of legitimate staked traffic capacity, since staked budget was pre-shrunk assuming unstaked stays near 20%.

### Likelihood Explanation
Preconditions are exactly as stated: the attacker only needs the ability to open a large number of parallel unstaked QUIC connections (bounded by `max_unstaked_connections`, default 2000) from many source addresses/identities, each streaming at its individually-granted throttle rate — no stake, keys, or validator control required. This is straightforward for a botnet-style attacker and fully reproducible.

### Recommendation
Introduce an aggregate/global unstaked load accounting mechanism (analogous to the staked EMA) that tracks total accepted unstaked streams across all unstaked connections and scales down the per-connection `max_unstaked_load_in_throttling_window` dynamically (or applies a shared token bucket) so the sum across all unstaked connections is bounded to the intended `EXPECTED_UNSTAKED_STREAMS_RATIO` share of `max_streams_per_ms`, rather than granting each connection the same fixed independent budget.

### Proof of Concept
Integration test plan (in `streamer/src/nonblocking/swqos.rs` or `quic.rs` test module, similar to existing `spawn_stake_weighted_qos_server` tests):
1. Configure `SwQosConfig` with `max_unstaked_connections = N` (e.g. 200 for a scaled-down test) and default `max_streams_per_ms`.
2. Spawn `N` distinct unstaked QUIC client connections (from distinct source ports/simulated addresses) concurrently against the test server.
3. Have each connection open streams as fast as permitted by its own `available_load_capacity_in_throttling_duration(ConnectionPeerType::Unstaked, _)` value (i.e., saturate its individual throttle).
4. Sum the total accepted streams/sec across all `N` connections via `StreamerStats` counters.
5. Assert failure of the invariant: total accepted unstaked throughput scales linearly with `N` and exceeds `max_streams_per_ms * EXPECTED_UNSTAKED_STREAMS_RATIO`, demonstrating that the intended 20% cluster-wide unstaked cap is not enforced in aggregate, only per connection.

    pub(crate) fn available_load_capacity_in_throttling_duration(
        &self,
        peer_type: ConnectionPeerType,
        total_stake: u64,
    ) -> u64 {
        match peer_type {
            ConnectionPeerType::Unstaked => self.max_unstaked_load_in_throttling_window,
            ConnectionPeerType::Staked(stake) => {
                if self.staked_throttling_enabled.load(Ordering::Relaxed) {
                    // 1 is added to `max_unstaked_load_in_throttling_window` to guarantee that staked
                    // clients get at least 1 more number of streams than unstaked connections.
                    self.max_staked_load_in_throttling_window
                        .saturating_mul(stake)
                        .checked_div(total_stake)
                        .unwrap_or(self.max_unstaked_load_in_throttling_window + 1)
                        .max(self.max_unstaked_load_in_throttling_window + 1)
                } else {
                    self.max_staked_load_in_throttling_window
                }
            }
        }
    }
