### Title
`remove_account()` fails to purge `TrieKey::PostponedReceipt`/`PostponedReceiptId`/`PendingDataCount`, letting a self-authorized `DeployContractAction` fire on a recreated account - (File: `core/store/src/utils/mod.rs`, `runtime/runtime/src/actions.rs`, `runtime/runtime/src/lib.rs`)

### Summary
`remove_account()` only removes `TrieKey::Account`, `TrieKey::ContractCode`, access/gas keys, and `TrieKey::ContractData`, but never touches `TrieKey::PostponedReceipt`, `TrieKey::PostponedReceiptId`, or `TrieKey::PendingDataCount` for the account being deleted. Because `check_actor_permissions()` authorizes `DeployContract` purely by comparing `AccountId` strings (`actor_id == account_id`, both taken from the receipt's stored `predecessor_id`/`receiver_id`), a postponed self-call `DeployContractAction` receipt parked before deletion remains valid and will execute against whatever account later occupies that same `AccountId`, deploying attacker-controlled code without the new owner's consent.

### Finding Description
- `check_actor_permissions` (`runtime/runtime/src/actions.rs:739-785`) authorizes `Action::DeployContract` solely via `actor_id != account_id` on `AccountId` values, with `actor_id` initialized in `apply_action_receipt` from `receipt.predecessor_id().clone()` (`runtime/runtime/src/lib.rs:855`). This check has no notion of "the same logical owner across time" — it is satisfied as long as the two `AccountId` strings match, even if the account was deleted and recreated in between.
- An attacker who owns account `A` can call a contract that creates a batch receipt targeting `A` itself containing `Action::DeployContract(malicious_code)`, with an `input_data_ids` dependency that is not yet satisfied (e.g., via a promise chained on a pending callback, or the yield/resume mechanism described in `runtime/runtime/AGENTS.md`). `process_action_receipt` (`runtime/runtime/src/lib.rs:1593-1658`) detects the missing data and stores the receipt as **postponed**: `TrieKey::PostponedReceiptId{receiver_id: A, data_id}`, `TrieKey::PendingDataCount{receiver_id: A, receipt_id}`, and the full receipt under `TrieKey::PostponedReceipt{receiver_id: A, receipt_id}` (`set_postponed_receipt`, `core/store/src/utils/mod.rs:120-127`).
- The attacker then self-deletes `A` via `Action::DeleteAccount` (passes `check_actor_permissions`'s `actor_id == account_id` self-delete rule, `actions.rs:761-776`). `action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) calls `remove_account` (`core/store/src/utils/mod.rs:504-575`), whose doc comment explicitly states it "Removes account, code and all access keys and gas keys associated to it." It removes `TrieKey::Account`, `TrieKey::ContractCode`, access/gas keys, and `TrieKey::ContractData` — but never iterates or removes `TrieKey::PostponedReceipt`, `TrieKey::PostponedReceiptId`, or `TrieKey::PendingDataCount` rows keyed to `A`. No check in `action_delete_account` blocks deletion when postponed action receipts exist for the account.
- Later, a third party recreates `A` (e.g., via a fresh `Transfer`/`CreateAccount`) and deposits funds, believing it to be a clean, code-free account.
- The attacker (as sole holder of the withheld data dependency) supplies the missing `DataReceipt`. `process_receipt`'s data branch (`runtime/runtime/src/lib.rs:1367-1474`) looks up `TrieKey::PostponedReceiptId{receiver_id: A, data_id}` (still present — untouched by `remove_account`), decrements `PendingDataCount` to 0, fetches the still-present `get_postponed_receipt(state_update, A, receipt_id)` (`core/store/src/utils/mod.rs:137-143`), and calls `apply_action_receipt` on it. This re-executes `check_actor_permissions` with `actor_id = A` (the receipt's original stored predecessor) and `account_id = A` (the current, third-party-owned account) — the string comparison trivially passes, and `action_deploy_contract` deploys the attacker's malicious code onto the victim's freshly funded account.
- No existing check (signature, nonce, access-key permission, storage-staking, or size-limit) intervenes: the postponed receipt was fully validated and paid for at creation time, and its later execution is treated as ordinary receipt processing with no re-validation against current account ownership.

### Impact Explanation
This is an authorization-escalation bug across account lifecimebounds: an unprivileged attacker can plant a dormant `DeployContract` action that later executes against an account they no longer own, deploying arbitrary WASM without any authorization from the account's actual (new) controller. This directly enables theft: the victim, unaware their account now runs attacker-controlled code, deposits funds that the malicious contract can subsequently drain — matching NEAR's "authorization escalation across accounts" and "theft of user funds" bounty categories.

### Likelihood Explanation
Preconditions are all reachable by an ordinary client: creating an account, deploying/calling one's own contract to build a promise DAG with a withheld data dependency (e.g., via a pending cross-contract call or the yield/resume primitive), self-deleting that account, and later supplying the withheld data (`yield_resume`/matching `DataReceipt`) are all standard, permission-less operations. The main practical constraint is getting a third party to recreate the *exact same* `AccountId` — most naturally satisfied via NEAR's implicit-account mechanism, where any transfer to a given hex-derived address auto-creates the account; an attacker can delete a previously-used implicit account (after planting the postponed receipt) and simply wait for anyone to send funds to that same address again, which reinstates the account and later gets hijacked. This makes the attack low-cost, fully attacker-controlled in timing, and repeatable across many implicit addresses.

### Recommendation
`remove_account()` in `core/store/src/utils/mod.rs` should also enumerate and remove all `TrieKey::PostponedReceipt`, `TrieKey::PostponedReceiptId`, and `TrieKey::PendingDataCount` entries (and any `PromiseYieldReceipt`/`PromiseYieldTimeout` entries) scoped to the account being deleted, mirroring how it already purges access keys and contract data. Alternatively/additionally, `action_delete_account` should reject deletion (similar to the existing `DeleteAccountStaking`/`DeleteAccountWithLargeState` checks) whenever the account still has any pending postponed receipts or unresolved data dependencies, since silently orphaning them changes their authorization context when the account name is reused.

### Proof of Concept
Integration/runtime-test-loop plan:
1. Create account `A` with a full-access key.
2. Have `A` invoke a contract method that issues a batch action receipt to `A` itself containing `Action::DeployContract(malicious_wasm)`, with an `input_data_ids` entry pointing at a `data_id` that is never immediately delivered (e.g. leave a cross-contract callback promise unresolved, or use `yield_create` without an immediate `yield_resume`). Confirm via state inspection that `TrieKey::PostponedReceipt{receiver_id: A, receipt_id}` and `TrieKey::PendingDataCount{receiver_id: A, ..}` are populated.
3. Submit `Action::DeleteAccount{beneficiary_id: attacker}` from `A` to itself; confirm the account is deleted (`get_account(A)` returns `None`) while the `TrieKey::PostponedReceipt` row for `A`/`receipt_id` still exists in the trie.
4. Have an unrelated party recreate `A` (e.g. `CreateAccount` + `Transfer`, or a plain `Transfer` to an implicit-account form of `A`) and deposit a balance.
5. Deliver the withheld `DataReceipt`/`yield_resume` payload for the pending `data_id`.
6. Assert that after processing, `get_account(A).contract()`/`local_contract_hash()` equals the hash of `malicious_wasm`, even though the current owner of `A` never submitted a `DeployContract` action — proving unauthorized contract deployment via the orphaned postponed receipt.
