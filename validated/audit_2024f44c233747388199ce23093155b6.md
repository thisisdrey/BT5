### Title
Anyone can trigger reward accrual for an arbitrary account, and the `accountIndexOf` fallback lets a pre-existing holder drain the entire reward balance - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
`RewardsDistributor.claimRewards` and `updateBeforeMintOrBurn` accept an arbitrary `account_` with no check binding it to the caller (the closest analog to the BuddyPress IDOR: authentication-only, no ownership check). By itself paying rewards to `account_` is harmless, but combined with the `accountIndexOf == 0 → INITIAL_INDEX` fallback in `_calculateTokenDelta`, an account that holds a DepositToken/DebtToken balance while `tokenStates[token].index == INITIAL_INDEX` is credited `balance * 1e18` reward tokens, draining the distributor's reward token balance.

### Finding Description
When the governor (or `syncTokenSpeed` keeper) first activates a reward speed for a token, `_updateTokenSpeed` initializes `tokenStates[token_] = TokenState({index: INITIAL_INDEX, timestamp: now})` (RewardsDistributor.sol:296-299). Any account that already holds a balance of that token (minted while `index == 0`, when `updateBeforeMintOrBurn`/`updateBeforeTransfer` were no-ops) has `accountIndexOf[token][account] == 0`.

In `_calculateTokenDelta` (lines 221-231):
```solidity
uint256 _accountIndex = accountIndexOf[token_][account_];
if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}
uint256 _deltaIndex = _tokenIndex - _accountIndex;
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
```

The fallback only applies when `_tokenIndex > INITIAL_INDEX`. While the index still equals `INITIAL_INDEX` — i.e., in the same block the speed is first set, and *permanently* whenever `tokenSpeeds[token] == 0` (the `_deltaTimestamps > 0 && _speed == 0` branch in `_calculateTokenIndex` updates only the timestamp, never advancing the index past `INITIAL_INDEX`, lines 209-211) — `_deltaIndex = INITIAL_INDEX = 1e18` and `_tokensDelta = balance * 1e18`.

`claimRewards(accounts, tokens)` is `public`, `nonReentrant`, and performs no ownership or permission check on `account_` (lines 150-168); `updateBeforeMintOrBurn` is likewise publicly callable (lines 175-180). `_transferRewardIfEnoughTokens` then transfers up to the full `rewardToken` balance to the account and zeroes `tokensAccruedOf` — but the next call recomputes the same `balance * 1e18` delta, so the drain repeats until the distributor is empty. Rewards legitimately accrued to other users are stolen, and their `tokensAccruedOf` can never be paid once the contract balance is depleted.

The attacker's only privileged dependency is the routine, public-mempool `updateTokenSpeed`/`syncTokenSpeed` transaction, which is sandwiched or front-runnable: deposit before it executes, call `claimRewards(attacker)` in the same block while `index == INITIAL_INDEX`. No governor/guardian/keeper collusion, oracle manipulation, or trusted-third-party failure is needed — the account-parameter authorization gap plus the strict `>` fallback comparison is the flaw.

### Impact Explanation
Direct theft of the protocol's entire undistributed reward-token balance held by `RewardsDistributor` (repeatable: `tokensAccruedOf` is reset to 0 but recomputed to `balance * 1e18` on every subsequent call while `index == INITIAL_INDEX`). Legitimate users' unclaimed yield is permanently stolen/frozen since the contract is drained. This satisfies the "theft of unclaimed yield / direct theft of funds" acceptance criteria.

### Likelihood Explanation
Requires a token whose reward speed is activated after users already hold balances — the normal rollout order for adding a new reward to an existing DepositToken/DebtToken — or a token whose speed is 0 while `index == INITIAL_INDEX`. The attacker only needs a dust balance of the tracked token acquired before the speed-setting transaction, plus mempool monitoring to claim in the same block. All entry points are unprivileged and public.

### Recommendation
- Initialize `accountIndexOf` correctly for all existing holders when a token's speed is first set, or change the fallback to `_tokenIndex >= INITIAL_INDEX` / store per-account index at mint time even when `index == 0`.
- Bind reward claims to the caller (`claimRewards(_msgSender())`) or make claimable-for-another-account payout semantics explicit and safe; restrict `updateBeforeMintOrBurn` to the registered DepositToken/DebtToken contracts.
