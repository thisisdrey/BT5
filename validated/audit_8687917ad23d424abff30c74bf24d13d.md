### Title
Truncated per-call interest accrual in vault interest-index math permanently suppresses lender yield - (File: mainnet/contracts/vault/v0-vault-stx.clar and sibling vault contracts)

### Summary
The vault contracts (`v0-vault-stx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`) compute the borrow/liquidity index growth per `accrue()` call using a single truncating division per call, exactly as BarnBridge's `compound`/`compound2` do per loop iteration. Because `accrue` is a public, unprivileged-callable function whose accrual step is re-derived from `time-delta` since `last-update`, an attacker can force many short-`time-delta` accrual steps instead of one long one. Each short step's fractional interest is floored to zero when `rate * time-delta` is small relative to `SECONDS-PER-YEAR-BPS`, so the compounded result after many small steps is strictly less than the correct result computed once over the full elapsed time — the same "divide-too-early/too-often" amplification described in the M05 report.

### Finding Description
Interest for a period is computed as: [1](#0-0) 

`calc-multiplier-delta` adds `1` (`INDEX-PRECISION`) to a truncated division `rate * time-delta * INDEX-PRECISION / SECONDS-PER-YEAR-BPS`. This fractional part is what represents interest earned in that period. The result then feeds: [2](#0-1) 

`calc-index-next` multiplies the current index by the multiplier and divides by `INDEX-PRECISION` — a second truncation. `next-index`/`next-liquidity-index` invoke this using `time-delta` computed since `last-update`: [3](#0-2) 

The public `accrue` entrypoint recomputes and commits `next-index`/`next-liquidity-index` and resets `last-update` on every call: [4](#0-3) 

Because `last-update` is reset after every accrual, an attacker who repeatedly triggers `accrue` (directly, or indirectly through minimal `deposit`/`redeem`/`system-borrow`/`system-repay` calls, all of which call `accrue` first) forces the protocol to compute interest over many short `time-delta` windows rather than one long window. When `rate * time-delta < SECONDS-PER-YEAR-BPS / INDEX-PRECISION` (i.e. the fractional multiplier term rounds to 0 in `mul-div-up`/`mul-div-down`), that period contributes exactly zero interest to the index, even though non-zero interest should have accrued. Repeating this indefinitely truncates real interest to zero on every step, permanently suppressing growth of the liquidity index (`lindex`) that lenders' underlying share value depends on, and of the borrow index that treasury fee minting in `accrue` depends on (`reserve-inc`/`treasury-lp`, also computed via `mul-div-down` off the truncated `debt-delta`). This is the identical bug class as M05: dividing at every step of a compounding process instead of performing one division over the whole elapsed interval, causing the truncation error to be repeatedly re-applied rather than amortized once.

### Impact Explanation
This lands in the explicitly in-scope category "vault share math and interest accrual." The effect is that legitimate lenders permanently lose yield they are owed (their liquidity index — and hence the exchange rate the vault share `zft` token is redeemable at — grows less than the correct compounded rate would produce), while the DAO treasury also receives less fee-LP than it should since `reserve-inc`/`treasury-lp` are derived from the same truncated `debt-delta`. This is "theft of unclaimed yield" / "permanent freezing of unclaimed yield" — a High-impact class per the rules.

### Likelihood Explanation
Likelihood is bounded by Stacks' block cadence (accrual granularity is at most once per block/microblock, and `time-delta == 0` calls are explicitly no-ops via `(is-eq time-delta u0)`). The truncation-to-zero condition requires `rate * time-delta` to be small relative to `SECONDS-PER-YEAR-BPS / INDEX-PRECISION` (≈ 315.36 with `INDEX-PRECISION = 1e12`, `SECONDS-PER-YEAR-BPS = 3.1536e11`), meaning at low utilization/interest-rate points (which occur naturally when utilization is low) and with block-to-block calling, each step's interest is very likely to floor to zero, and any user willing to pay minimal gas for near-zero-amount `deposit`/`redeem` calls (or calling `accrue` directly, which appears unrestricted to any caller) can keep resetting `last-update` every block to keep every step's fractional interest at zero indefinitely. No privileged access or DAO compromise is required.

### Recommendation
Do not reset `last-update` (and thus the accrual base) on every incidental call. Instead, either (a) always compute the multiplier from the last *actual index-changing* accrual timestamp rather than the last call timestamp, or (b) accumulate a running fractional remainder across accruals so truncated fractions are carried forward instead of discarded, or (c) rate-limit/no-op `accrue` state commits when the elapsed time is too small to produce a non-zero delta while still tracking real elapsed time for the next call (i.e., only update `last-update` when `next != idx` is guaranteed by design, not conditionally as currently done — note the code already conditionally skips `var-set last-update` when index/lindex are unchanged at lines 862-864/858-860 in the accrue snippets, but this alone doesn't prevent the truncation of the *current* step's fractional interest from being lost; carrying the remainder is required to actually fix it).

### Proof of Concept
1. Attacker (any principal) observes a vault (e.g. `v0-vault-stx.clar`) at a utilization level producing a low `rate` (few bps) from `interpolate-rate`.
2. Attacker submits minimal `deposit`/`redeem` transactions (or calls `accrue` directly if unauthenticated) in consecutive blocks, ensuring each call's `time-delta = stacks-block-time - last-update` stays small.
3. Each call computes `calc-multiplier-delta` where `rate * time-delta * INDEX-PRECISION / SECONDS-PER-YEAR-BPS` truncates to `0`, yielding `multiplier = INDEX-PRECISION` and thus `next-index == idx` (no growth) despite real time and real utilization-based interest having accrued.
4. `last-update` is still advanced conditionally; if `idx`/`lindex` are unchanged the timestamp update is skipped in some branches, but subsequent calls repeat the same truncated computation over successive short windows rather than ever accumulating the fractional interest that a single long-window computation would have captured — resulting in a lender yield deficit compared to the mathematically correct compounded value.
5. Compare against the counterfactual: if no calls happened for the same total elapsed time and `accrue` were invoked once, `calc-multiplier-delta` would use the full elapsed `time-delta`, producing a proportionally larger, non-truncated multiplier and correspondingly higher index growth.
