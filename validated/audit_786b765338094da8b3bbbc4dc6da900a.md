Audit Report

## Title
Relayer reward paid on Snowbridge outbound delivery receipt regardless of on-chain execution outcome — `success` flag ignored - (File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs)

## Summary
`Pallet::process_delivery_receipt` in `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs` registers the relayer reward and permanently removes the corresponding `PendingOrder` based solely on the existence of the order and `order.fee > 0`, without ever inspecting the decoded `DeliveryReceipt.success` field. This lets a relayer collect the full reward and close out the order even when the Ethereum-side dispatch of the inbound command reverted.

## Finding Description
`DeliveryReceipt` is decoded from the `InboundMessageDispatched(uint64 indexed nonce, bytes32 topic, bool success, bytes32 reward_address)` Ethereum event log via `TryFrom<&Log>`, explicitly capturing the `success: bool` field [1](#0-0) , and this field is populated straight from `event.success` during decoding [2](#0-1) .

The extrinsic `submit_delivery_receipt` verifies the event log/proof via `T::Verifier::verify`, decodes it into a `DeliveryReceipt`, and passes it straight to `process_delivery_receipt` with no filtering on `success` [3](#0-2) .

`process_delivery_receipt` itself only checks the gateway address, resolves the reward account, fetches the `PendingOrder` by nonce, and — as long as `order.fee > 0` — unconditionally calls `T::RewardPayment::register_reward`, then removes the `PendingOrder` and emits `MessageDelivered`, all without reading `receipt.success` [4](#0-3) . A repo-wide search confirms `success` is never referenced anywhere in this pallet's logic path, so there is no branch, guard, or downstream check that discriminates a failed dispatch from a successful one before payout and order removal.

This is exactly the class of bug where a known outcome flag is discarded, letting a "settlement" (reward registration + `PendingOrders::remove` + `MessageDelivered` event) advance even though the underlying execution did not succeed, violating the pivot that "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically."

## Impact Explanation
The Snowbridge reward pot pays out relayer rewards for messages whose Ethereum-side execution reverted, i.e. work that did not actually complete successfully. Because `PendingOrders::remove(nonce)` executes unconditionally on any well-formed, honestly-proven receipt, there is no way to retry, refund, or reconcile the failed delivery afterward — the order is permanently gone and the reward is already paid. This matches the "duplicate settlement or payout" / broken payout-invariant category from the required impacts.

## Likelihood Explanation
No malicious peer, governance action, or leaked key is needed. Any relayer submitting a legitimately emitted `InboundMessageDispatched` event with `success == false` (e.g., destination dispatch reverted due to out-of-gas or an execution error unrelated to relaying fidelity) and a valid proof triggers the exact same reward/removal path as a genuine success. This is a public extrinsic (`submit_delivery_receipt`) reachable by any signed account, making the condition trivially and repeatably reachable.

## Recommendation
Branch on `receipt.success` in `process_delivery_receipt` before calling `register_reward`. On `success == false`, withhold (or reduce) the relayer reward, emit a distinct failure event (e.g., `MessageDeliveryFailed`), and decide deterministically whether the `PendingOrder` should be retried, refunded, or cleared without payout, instead of unconditionally paying and removing it. Do not conflate "receipt proven" with "message executed successfully" when advancing payout state.

## Proof of Concept
1. A message is queued and gets a `PendingOrder` with `fee > 0` via `do_process_message` [5](#0-4) .
2. The Ethereum gateway executes the inbound command, and it reverts, so the gateway honestly emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer obtains a valid transaction-receipt/proof for this real event log (no forgery required) and calls `submit_delivery_receipt` with it.
4. `T::Verifier::verify` succeeds (the proof is genuine), `DeliveryReceipt::try_from` decodes `success: false` correctly, and `process_delivery_receipt` is invoked [6](#0-5) .
5. Since `order.fee > 0`, `T::RewardPayment::register_reward` is called and `PendingOrders::remove(nonce)` runs, emitting `Event::MessageDelivered { nonce }` — paying the relayer and permanently closing the order despite the failed Ethereum-side execution [7](#0-6) .

		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
