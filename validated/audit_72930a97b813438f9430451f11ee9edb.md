### Title
Silent long overflow in delegation vote-reward computation causes permanent loss of rewards / potential unbacked allowance credit - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`, `actuator/src/main/java/org/tron/core/vm/utils/VoteRewardUtil.java`, `chainbase/src/main/java/org/tron/core/service/RewardViCalService.java`)

### Summary
The `Vi`-based vote-reward accounting in java-tron accumulates an unbounded `BigInteger` per witness per cycle (`witnessVi`), and later multiplies the accumulated delta by a user's vote count and truncates the `BigInteger` result to a `long` using `.longValue()` (which silently wraps on overflow) instead of `.longValueExact()` (which throws). This mirrors the Locke.sol H-09 bug class: an intermediate value that individually fits its type overflows a downstream fixed-width type after multiplication, but instead of reverting it silently truncates, corrupting reward accounting and potentially permanently freezing user rewards or crediting incorrect balances.

### Finding Description
`DelegationStore.accumulateWitnessVi` computes and stores an ever-growing `BigInteger witnessVi` per witness/cycle with no upper bound: [1](#0-0) 

`DECIMAL_OF_VI_REWARD` is `10^18`: [2](#0-1) 

For a witness that receives a nontrivial `reward` but has very low `voteCount` (e.g. `voteCount = 1`, achievable since a user only needs to vote a minimal amount of TRON Power for an under-voted standby witness), `deltaVi = reward * 10^18 / voteCount` can be astronomically large. Because it's stored and accumulated as an unbounded `BigInteger` (`preVi.add(deltaVi)`) across many cycles with no cap, `witnessVi` grows without any long-range constraint over time.

When a voter later withdraws or queries reward, the reward computation multiplies this unbounded `deltaVi` by the voter's own `userVote` (their TRON Power, up to their entire frozen TRX balance) and then calls `.longValue()` on the `BigInteger` result — not `.longValueExact()`: [3](#0-2) 

The identical pattern is duplicated in the TVM-vote reward path: [4](#0-3) 

and in the reward-Vi calculation service used for the "new" reward algorithm: [5](#0-4) 

`BigInteger.longValue()` silently discards all but the low-order 64 bits when the value doesn't fit in a `long`, rather than throwing — unlike `longValueExact()` used elsewhere in the same codebase for similarly hardened arithmetic (e.g. `ResourceProcessor.calculateGlobalLimitV2` and `divideCeilExact`, which explicitly use `longValueExact()` to fail safely on overflow): [6](#0-5) 

The resulting wrapped `reward` value is then accumulated (`reward += ...`) and passed to `adjustAllowance`, which only credits the account when `amount > 0`: [7](#0-6) 

Because `withdrawReward` unconditionally advances `beginCycle`/`endCycle` regardless of whether the reward was actually credited: [8](#0-7) 

if the wrapped `reward` computes to a negative or nonsensical number, `adjustAllowance` silently discards it (`amount <= 0` → no-op) and the cycle window is still marked processed — the legitimate reward for that period is permanently and irrecoverably lost, since the underlying `Vi` deltas for that cycle range will never be revisited.

### Impact Explanation
This is reachable by any unprivileged account performing normal `FreezeBalanceV2`/vote/`WithdrawBalanceContract` or TVM `withdrawReward`/`vote` operations — no special privilege is required, matching the "stake/delegation/reward math" reachable surface. The overflow silently corrupts reward math instead of reverting, which can:
- Cause permanent loss of legitimately earned rewards for a voter (funds are frozen/burned from the user's perspective, matching the "permanent freezing of funds" impact class from the original report), since the wrapped negative reward is silently dropped and the cycle accounting is advanced anyway.
- Potentially produce an unbacked/incorrect `allowance` credit if the wraparound happens to land on a large positive value, resulting in inflated (unbacked) balances not backed by the actual reward pool.

### Likelihood Explanation
Triggering requires an attacker to (a) vote a small amount for an under-voted standby witness so that `voteCount` is tiny relative to `reward`, amplifying `deltaVi` each cycle, and (b) wait a sufficient number of cycles for the unbounded `BigInteger` Vi to grow to a magnitude that, once multiplied by a large `userVote` and divided by `10^18`, exceeds `Long.MAX_VALUE`. This is economically feasible over an extended period since witness reward distribution and vote counts are both attacker-influenceable, and cycle-by-cycle accumulation is unbounded by design (stored as `BigInteger`, never capped).

### Recommendation
Replace `.longValue()` with `.longValueExact()` (or an explicit bounds check throwing a recoverable exception) in all three reward computation sites (`MortgageService.computeReward`, `VoteRewardUtil.computeReward`, `RewardViCalService.getNewRewardAlgorithmReward`), consistent with the hardened pattern already used in `ResourceProcessor`. Additionally, consider capping/normalizing `witnessVi` growth or reward-per-cycle magnitude to prevent unbounded accumulation, and ensure that if an overflow is detected, cycle-advancement bookkeeping is not silently committed (so the reward can be recovered/retried) rather than causing a permanent loss.

### Proof of Concept
1. Attacker freezes a very small amount of TRX and votes for a witness (`WitnessA`) that otherwise has near-zero total votes for several cycles, so `voteCount` used in `accumulateWitnessVi` stays extremely small relative to `WitnessA`'s block/vote rewards. [1](#0-0) 
2. Over many cycles, `witnessVi` for `WitnessA` grows to an extremely large `BigInteger` because `deltaVi = reward * 10^18 / voteCount` is added every cycle with no cap.
3. Attacker then also stakes/votes a large TRON Power amount (`userVote`) for `WitnessA` and waits for `endCycle - beginCycle` to span the accumulated window.
4. On `withdrawReward`/`WithdrawBalanceContract`, `computeReward` calculates `deltaVi.multiply(BigInteger.valueOf(userVote)).divide(DECIMAL_OF_VI_REWARD).longValue()`; because the product before division can vastly exceed `Long.MAX_VALUE`, the truncating `.longValue()` returns a wrapped (potentially negative) value. [3](#0-2) 
5. `adjustAllowance` is a no-op for non-positive `amount`, so the reward is silently dropped, yet `beginCycle`/`endCycle` are advanced past this window, permanently forfeiting the reward for that period. [9](#0-8)

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }

  private static long computeReward(long beginCycle, long endCycle,
                                    AccountCapsule accountCapsule, Repository repository) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    for (Protocol.Vote vote : accountCapsule.getVotesList()) {
      byte[] srAddress = vote.getVoteAddress().toByteArray();
      BigInteger beginVi = repository.getDelegationStore().getWitnessVi(beginCycle - 1, srAddress);
      BigInteger endVi = repository.getDelegationStore().getWitnessVi(endCycle - 1, srAddress);
      BigInteger deltaVi = endVi.subtract(beginVi);
      if (deltaVi.signum() <= 0) {
        continue;
      }
      long userVote = vote.getVoteCount();
      reward += deltaVi.multiply(BigInteger.valueOf(userVote))
          .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
    }
    return reward;
  }
