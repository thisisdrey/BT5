## Analysis

The Sherlock report concerns `OwnableImpl` lacking (1) a zero-address check when setting/transferring ownership and (2) a two-step ownership-transfer procedure, both of which can result in permanent loss of contract control.

The closest reachable analog in java-tron is `AccountPermissionUpdateActuator`, which lets any account owner replace their account's `Owner`/`Witness`/`Active` permissions (including the keys that control the account, i.e. its "ownership") in a single signed transaction, with no two-step confirmation and no rejection of degenerate/unspendable key addresses.

`AccountPermissionUpdateActuator.validate()` only checks that each permission key passes `DecodeUtil.addressValid()`: [1](#0-0) 

`DecodeUtil.addressValid()` only verifies the address length (21 bytes) and the `0x41` mainnet prefix byte — it never checks whether the remaining 20 bytes are non-zero: [2](#0-1) 

So an address such as `0x41` followed by 20 zero bytes is treated as a perfectly "valid" key address. `checkPermission()` accepts it as long as `keysCount`, `weight`, and `threshold` rules are satisfied: [3](#0-2) 

`execute()` then unconditionally overwrites the account's owner permission (and witness/active permissions) via `AccountCapsule.updatePermissions()` in a single, irreversible step — there is no `pendingOwner` staging and no acceptance step by the new key holder: [4](#0-3) [5](#0-4) 

This means an account owner (via a mistake, a compromised signing key, or a buggy wallet/tool constructing the transaction) can submit a single `AccountPermissionUpdateContract` that sets the `Owner` permission's key(s) to an all-zero (or otherwise unspendable) but format-valid address. Since nobody holds the private key for such an address, the account's owner permission — and hence control of the account (transfers, resource management, future permission updates) — is permanently and irreversibly locked, with no two-step recovery mechanism, exactly mirroring the impact described in the source report.

### Title
Missing zero/degenerate-address check and lack of a two-step confirmation in `AccountPermissionUpdateActuator` can permanently lock account ownership - (File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java)

### Summary
`AccountPermissionUpdateActuator` allows an account to atomically overwrite its `Owner` permission (and `Active`/`Witness` permissions) in one transaction. Address validation (`DecodeUtil.addressValid`) only checks address length and the network prefix byte, not whether the address corresponds to a spendable/controllable key. Combined with the single-step, immediately-effective update in `execute()`, a user (or a compromised/careless signer) can set the owner permission key(s) to an address nobody controls, permanently losing control of the account, with no staged/two-step mechanism to catch or reverse the mistake.

### Finding Description
`validate()` in `AccountPermissionUpdateActuator` delegates key-address soundness entirely to `checkPermission()` → `DecodeUtil.addressValid()`. That function only checks that the byte array is 21 bytes long and starts with the chain's address prefix byte (`0x41` for mainnet); it performs no check that the remaining 20 bytes are non-zero or otherwise correspond to a real, key-controlled address. `execute()` then immediately calls `AccountCapsule.updatePermissions()`, which replaces the account's owner permission in the account store in a single atomic step with no pending/staging state and no secondary confirmation from a "new owner." This is directly analogous to the reported `OwnableImpl` weakness: absence of a zero-address sanity check plus a one-step ownership change.

### Impact Explanation
If the owner permission's controlling key(s) are set to an address with no known private key (e.g., an all-zero address, or any address the submitter does not actually control), the account can no longer authorize any operation that requires the `Owner` permission — including issuing a corrective `AccountPermissionUpdateContract` to fix the mistake. This is a permanent freezing of the account's administrative capability (and any funds/resources gated behind owner-level operations), matching the "permanent freezing of funds" impact class.

### Likelihood Explanation
This requires only a single signed `AccountPermissionUpdateContract` transaction from the account itself (multi-sign must be enabled via `AllowMultiSign`, which is a supported, non-privileged chain feature). No special SR/witness/committee privilege is needed — any account holder can trigger this on their own account, whether by mistake, tooling bug, or a partially-compromised signer setting a decoy key.

### Recommendation
In `AccountPermissionUpdateActuator.checkPermission()` (and more generally wherever key addresses are validated for permission updates), reject degenerate addresses such as the all-zero address, and consider requiring the previous owner's active signature plus some acknowledgment/staging mechanism (analogous to a two-step ownership transfer) before a new `Owner` permission fully replaces the old one, so an erroneous update can still be corrected before it becomes final.

### Proof of Concept
1. Attacker/account owner builds an `AccountPermissionUpdateContract` for `ownerAddress` where the `Owner` permission's single key is `0x41` + 20 zero bytes, with `threshold=1`, `weight=1`.
2. `DecodeUtil.addressValid()` returns `true` since it only checks length/prefix.
3. `checkPermission()` passes (keysCount=1, weight>0, weightSum>=threshold).
4. `execute()` calls `account.updatePermissions(...)`, overwriting the owner permission with the unusable key.
5. The account can no longer produce a valid signature meeting the new owner permission threshold, permanently losing the ability to perform owner-level operations (including submitting a corrective permission update).

    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    if (permission.getKeysCount() > dynamicStore.getTotalSignNum()) {
      throw new ContractValidateException("number of keys in permission should not be greater "
          + "than " + dynamicStore.getTotalSignNum());
    }
    if (permission.getKeysCount() == 0) {
      throw new ContractValidateException("key's count should be greater than 0");
    }
    if (permission.getType() == PermissionType.Witness && permission.getKeysCount() != 1) {
      throw new ContractValidateException("Witness permission's key count should be 1");
    }
    if (permission.getThreshold() <= 0) {
      throw new ContractValidateException("permission's threshold should be greater than 0");
    }
    String name = permission.getPermissionName();
    if (!StringUtils.isEmpty(name) && name.length() > 32) {
      throw new ContractValidateException("permission's name is too long");
    }
    //check owner name ?
    if (permission.getParentId() != 0) {
      throw new ContractValidateException("permission's parent should be owner");
    }

    long weightSum = 0;
    List<ByteString> addressList = permission.getKeysList()
        .stream()
        .map(x -> x.getAddress())
        .distinct()
        .collect(toList());
    if (addressList.size() != permission.getKeysList().size()) {
      throw new ContractValidateException(
          "address should be distinct in permission " + permission.getType());
    }
    for (Key key : permission.getKeysList()) {
      if (!DecodeUtil.addressValid(key.getAddress().toByteArray())) {
        throw new ContractValidateException("key is not a validate address");

      if (key.getWeight() <= 0) {
        throw new ContractValidateException("key's weight should be greater than 0");
      }
      try {

      } catch (ArithmeticException e) {
        throw new ContractValidateException(e.getMessage());
      }
    }

      throw new ContractValidateException(
          "sum of all key's weight should not be less than threshold in permission " + permission

    }

      logger.warn(
          "Warning: Address length need " + ADDRESS_SIZE + " but " + address.length

      return false;

    }

  public void updatePermissions(Permission owner, Permission witness, List<Permission> actives) {
    Builder builder = this.account.toBuilder();

    owner = owner.toBuilder().setId(0).build();
    builder.setOwnerPermission(owner);
    if (witness != null && builder.getIsWitness()) {
      witness = witness.toBuilder().setId(1).build();
      builder.setWitnessPermission(witness);
    }

    builder.clearActivePermission();
    if (actives != null) {
      for (int i = 0; i < actives.size(); i++) {
        Permission permission = actives.get(i).toBuilder().setId(i + 2).build();
        builder.addActivePermission(permission);
      }
    }

    this.account = builder.build();
  }
