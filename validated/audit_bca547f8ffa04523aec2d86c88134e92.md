### Title
Unchecked `unwrap-panic` on cross-contract vault accrual causes transaction-wide panic/DoS during position accrual - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`accrue-debt-asset` and `accrue-collateral-asset` in `v0-4-market.clar` call `accrue-and-cache`, whose result (a `(response {index, lindex} uint)`) is discarded via `unwrap-panic` instead of being propagated with `try!`/`unwrap!`. `accrue-and-cache` in turn calls `vault-accrue`, which returns `ERR-UNKNOWN-VAULT` for any asset id that does not match one of the six hardcoded vaults. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
This mirrors the CWE class in the report (Unchecked Return Value / Improper Handling of Exceptional Conditions): a response from processing attacker/user-influenced input is force-unwrapped with a panic primitive instead of being checked and safely propagated as an error. In the nimiq case, an untrusted validator set entry causes an `.unwrap()` panic when hashing a block header. Here, `accrue-user-debts`/`accrue-user-collateral` fold over the *user's own position lists* (`debt-list`, `coll-list`), calling `accrue-and-cache` for every asset id present, and unconditionally `unwrap-panic` the result: [4](#0-3) [5](#0-4) 

The comment `;; will cause ERR-UNKNOWN-VAULT with any value over 64` explicitly acknowledges that a mismatched/unmapped asset id reaches `vault-accrue` and returns an error rather than `ok`. Since the surrounding code uses `unwrap-panic` (which aborts the whole transaction on any `Err`) rather than `try!` (which would return a clean error code), any code path that manages to place an asset id into a user's debt/collateral list that isn't one of the six recognized vault ids, or that reaches this function while a downstream vault's `accrue` briefly errors, results in an uncatchable Clarity runtime abort instead of a graceful error return.

Because `accrue-user-debts`/`accrue-user-collateral` are invoked from core position-mutating and health-check flows (borrow, repay, withdraw, add-collateral, and liquidation — where a *liquidator*, an ordinary unprivileged principal, drives accrual over the *target account's* position), a position that reaches this state becomes unprocessable by anyone: not just the owner's own transactions but also third-party liquidation calls on that account revert. That freezes the position's underlying collateral/debt (and blocks liquidation from resolving accumulating bad debt) until intervention.

### Impact Explanation
This lands in the "temporary freezing of funds" bucket for the in-scope impact classes: once triggered, every operation that must accrue that position's asset list (deposit/borrow/repay/withdraw/liquidate) unconditionally panics, so the user's (and any liquidator-initiated) interaction with that position is blocked and the position's collateral/debt is frozen. It does not directly cause insolvency or direct theft, and it is bounded by the specific asset-list state, so it is best characterized as temporary freezing of funds rather than a Critical permanent freeze, since a DAO-side registry fix would remain possible in principle.

### Likelihood Explanation
The `unwrap-panic` calls are only reachable in-scope if an ordinary principal can get an asset id (in their own debt/collateral list) that isn't one of the six vault ids the `if`-chain in `vault-accrue` recognizes, without any DAO/registry misconfiguration. Whether such an id can be placed into a position purely via unprivileged asset/market entry points (as opposed to requiring a DAO asset-registry change, which is explicitly out of scope) could not be fully confirmed with the available context — the `assets` registry and the exact set of ids that are permitted into `market-vault` positions were not reachable in this pass. This uncertainty affects confidence in the likelihood, though the pattern itself (unchecked cross-contract accrual result force-unwrapped rather than propagated) is confirmed in the code.

### Recommendation
Replace `unwrap-panic (accrue-and-cache ...)` in `accrue-debt-asset` and `accrue-collateral-asset` with `try!`/`unwrap!` propagating a proper error response (e.g., `ERR-UNKNOWN-VAULT`) up through `accrue-user-debts`/`accrue-user-collateral` and their callers, so that any unmapped-asset condition surfaces as a normal Clarity error return instead of an unrecoverable panic that blocks all future interaction (including liquidation) with the affected position.

### Proof of Concept
Not fully constructible from the available index: doing so requires confirming, via `assets.clar`/`market-vault.clar` (not covered in this pass), whether an ordinary principal can cause a non-canonical asset id to be recorded in their own debt or collateral list through a public entry point without any DAO/registry misconfiguration. If such a path exists, the PoC is: get that asset id into your position via that path, then call any market operation that triggers `accrue-user-debts`/`accrue-user-collateral` (or have any third party attempt to liquidate you) — the call unwraps `ERR-UNKNOWN-VAULT` via `unwrap-panic` and the transaction aborts every time, permanently blocking further interaction with the position until remediated.

(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
