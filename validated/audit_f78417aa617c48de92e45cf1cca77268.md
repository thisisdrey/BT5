### Title
Out-of-bounds read via unvalidated Zip64 extra-field attribute count when parsing untrusted jar/zip archives - (File: `src/tools/singlejar/zip_headers.h`)

### Summary
`CDH::compressed_file_size()`, `CDH::uncompressed_file_size()` and `CDH::local_header_offset()` in [1](#0-0)  read a 64-bit value out of a `Zip64ExtraField` at an index derived from *other*, attacker-controlled 32-bit fields (whether `compressed_file_size32()`/`uncompressed_file_size32()` equal `0xFFFFFFFF`), without ever checking that the extra field's own declared `payload_size()` actually contains that many 8-byte attributes.

### Finding Description
`Zip64ExtraField::find()` bounds-checks the extra field header against the CDH's `extra_fields_length()` [2](#0-1) , so the field itself is guaranteed to fit inside the extra-fields buffer. However, once found, `attr64(index)` blindly indexes into the flexible array member `attr_[]` [3](#0-2)  using an index computed independently of `payload_size()`:

- `uncompressed_file_size()` unconditionally reads `attr64(0)` [4](#0-3) .
- `compressed_file_size()` reads `attr64(zfield_has_ext64(uncompressed_file_size32()))`, i.e. index 0 or 1 [5](#0-4) .
- `local_header_offset()` computes `attr_no` by summing whether uncompressed/compressed sizes are 64-bit, then reads `attr64(attr_no)`, which can be index 0, 1, or 2 [6](#0-5) .

None of these call `attr_count()` [7](#0-6)  to confirm the field actually declares that many attributes. A crafted CDH entry can set `uncompressed_file_size32_ = 0xFFFFFFFF` and `compressed_file_size32_ = 0xFFFFFFFF` and `local_header_offset32_ = 0xFFFFFFFF` while attaching a Zip64 extra field whose `payload_size` only covers one `uint64` (8 bytes), forcing `attr64(1)` or `attr64(2)` to read 8–16 bytes past the end of the extra field's declared payload. Since the extra-fields region sits directly before `comment_length` bytes and the end of the mapped/allocated CDH buffer, this reads adjacent heap/mapped memory — the exact bug class described in the reported Vim CVE (an offset/length pair that is internally consistent with its own record but insufficient for the length the *consumer* code assumes, leading to an OOB read when converted to a pointer dereference).

This is directly reachable from attacker-controlled data: `singlejar`/`ijar` process zip/jar files that can originate from external, attacker-served content consumed by a Bazel build (e.g. `http_jar`, `http_archive` fetching a `.jar`, or any rule that runs `singlejar`/`ijar` over a downloaded jar). The archive's own internal CRC/signature checks only validate structural signatures, not the size-consistency between the outer 32-bit "needs Zip64" flags and the payload actually present in the Zip64 extra field.

### Impact Explanation
An attacker who controls the bytes of a jar/zip file consumed by a Bazel build (e.g. served at a URL that Bazel downloads and then processes with `singlejar`/`ijar`, such as through `java_import`, `ijar`-processed deps, or jar merging in `singlejar`) can craft a central directory header whose Zip64 extra field is shorter than what the 32-bit-overflow flags imply. This causes `singlejar`/`ijar` to read memory beyond the extra field's actual payload (heap OOB read), potentially crashing the build tool or leaking adjacent heap bytes into computed offsets/sizes used for further processing of the (attacker-influenced) jar, matching the CVSS profile of the Vim analog (local, low complexity, availability/confidentiality impact, no privileges).

### Likelihood Explanation
Moderate. It requires a build to run `singlejar` or `ijar` over an attacker-supplied jar/zip file (common in Java build actions and via `http_jar`/`http_archive` fetches of jars). No credentials or MITM are needed — a malicious/compromised origin serving the jar is sufficient. The crafted extra field is a small, easily-constructed deviation from the ZIP64 spec (declaring `0xFFFFFFFF` in 32-bit fields but omitting the corresponding attribute(s) in the Zip64 extra field).

### Recommendation
In `zip_headers.h`, before calling `attr64(index)` from `compressed_file_size()`, `uncompressed_file_size()`, and `local_header_offset()`, validate `z64->attr_count() > index` (i.e., that `payload_size()` is large enough to contain the requested attribute). If not, treat the entry as malformed and fail the operation (as is already done elsewhere in `output_jar.cc` for malformed extra fields, e.g. the `diag_errx` checks at [8](#0-7) ), rather than silently returning a garbage/OOB-read value.

### Proof of Concept
A reproducible test can be added to `src/tools/singlejar/zip_headers_test.cc` (or a new focused unit test) that:
1. Constructs a `CDH` in a heap buffer sized exactly to the fixed header + filename + a Zip64 `ExtraField` whose `payload_size` covers only one `uint64` attribute (8 bytes).
2. Sets `compressed_file_size32_ = uncompressed_file_size32_ = local_header_offset32_ = 0xFFFFFFFF`.
3. Calls `cdh->local_header_offset()` (which will compute `attr_no = 2` and call `attr64(2)`), and observes (e.g. under ASan) that the read of `attr_[2]` occurs past the allocated buffer boundary, producing a heap-buffer-overflow (OOB read) report. [9](#0-8)

class ExtraField {
 public:
  static const ExtraField* find(uint16_t tag, const uint8_t* start,
                                const uint8_t* end) {
    while (start < end) {
      if (ziph::byte_ptr(start) + sizeof(ExtraField) > ziph::byte_ptr(end)) {
        break;
      }
      auto extra_field = reinterpret_cast<const ExtraField*>(start);
      if (ziph::byte_ptr(start) + extra_field->size() > ziph::byte_ptr(end)) {
        break;
      }
      if (extra_field->is(tag)) {
        return extra_field;
      }
      start = ziph::byte_ptr(start) + extra_field->size();
    }
    return nullptr;
  }
