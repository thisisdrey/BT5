### Title
False StackerDB chunk inventory advertised before the chunk is actually committed - ([File: stackslib/src/net/stackerdb/mod.rs])

### Summary
`PeerNetwork::handle_unsolicited_StackerDBPushChunk` patches the *outgoing* `StackerDBChunkInv` reply to claim the local node now has a pushed chunk's `slot_version`, and sends that reply back to the peer immediately — before the chunk has actually been committed to the local `StackerDBs` store. Storage only happens later, asynchronously, when the chunk is forwarded to the relayer and processed by `Relayer::process_stacker_db_chunks` / `StackerDBTx::try_replace_chunk`. This is the network analog of the reported bug class: a bookkeeping value (`totalLiquidity` in the original report, here the advertised slot version in the chunk inventory) is updated based on an intermediate/optimistic step rather than the actual, final committed state, breaking the "served vs. committed" equality.

### Finding Description
In `handle_unsolicited_StackerDBPushChunk`: [1](#0-0) 
the function calls `validate_received_chunk` (which only checks the chunk's *signature*, *size*, *staleness against the currently known `data.slot_versions`*, and *max-writes*) and, if it passes, immediately mutates the reply's `slot_versions` entry to the new version and sends this `StackerDBChunkInv` back to the sender: [2](#0-1) 

Crucially, this function never calls `try_replace_chunk` / `insert_chunk` itself — the doc comment explicitly says the actual commit is deferred to the relayer ("Returns (x, true) if we should forward the message to the relayer, so it can be processed"). The real storage happens later and separately, in `Relayer::process_stacker_db_chunks`, which calls `StackerDBTx::try_replace_chunk`: [3](#0-2) 
and `try_replace_chunk` re-validates against the *DB's actual current* `SlotValidation.version` at commit time, which can differ from what `validate_received_chunk` saw earlier (e.g., a concurrent push for the same slot at a different version, or another chunk already committed in between): [4](#0-3) 

Because the inventory-patch step and the actual commit step are decoupled — one happens synchronously on receipt (advertised to the peer right away), the other happens later on the relayer thread and can fail (`StaleChunk`, DB error) — a remote peer can race two (or more) unsolicited, validly-signed `StackerDBPushChunk` messages for the same slot at different versions against a victim node. The victim's `StackerDBChunkInv` will optimistically claim it has the newer version, but the actual commit for that push may fail while a different (older, replayed, or independently pushed) chunk is the one that finally lands in the DB — so the advertised inventory no longer matches what is actually stored.

### Impact Explanation
This causes the node's advertised StackerDB inventory to diverge from its actually committed StackerDB contents ("served vs. committed" mismatch). Downstream peers rely on this inventory (`StackerDBChunkInv`) to decide what to fetch/rarest-first schedule chunks; if a peer believes the victim already has a given slot version (because it advertised it), it may skip re-propagating that chunk to/through the victim, potentially stalling propagation of important StackerDB content (e.g., signer messages, miner block-commit chunks) — matching the "steering a node off the tip via false inventory" pattern called out as High impact. This is consistent with the already-acknowledged race class in this area, evidenced by the existing changelog entry describing a related StackerDB chunk event-loss/race bug: [5](#0-4) .

### Likelihood Explanation
Any unprivileged remote peer able to open a P2P connection can send unsolicited `StackerDBPushChunk` messages; no special key or role beyond a validly-signed chunk (for a slot the sender controls) is required to trigger the inventory patch. Reliably winning the race between the immediate inventory-patch/reply and the deferred relayer commit requires precise timing of multiple concurrent messages, which lowers ease of exploitation somewhat, but the underlying decoupling of "advertise" and "commit" is a structural, deterministic property of the code, not a probabilistic memory bug.

### Recommendation
Do not patch/send the optimistic `StackerDBChunkInv` reply based on validation alone. Either (a) perform the chunk commit synchronously (or under the same lock/transaction) before constructing and sending the inventory reply, or (b) only advertise the true, freshly-read `slot_version` from the StackerDB after the relayer has actually committed the chunk, sending the inventory update as a follow-up rather than inline with the push-chunk acknowledgment.

### Proof of Concept
1. Attacker controls (or has captured) a private key for slot `S` in some `StackerDB` contract that node `V` replicates.
2. Attacker opens two P2P connections to `V` (or reuses one) and sends two `StackerDBPushChunk` messages for slot `S`: message A with `slot_version = N+1` and message B with `slot_version = N+2`, timed so that both pass `validate_received_chunk` (both compared against `V`'s pre-write `slot_versions` state) before either is committed by the relayer.
3. `V` immediately replies to each with a `StackerDBChunkInv` claiming it has `slot_version = N+2` (from B) patched into the reply for both connections, per [6](#0-5) .
4. Both chunks are forwarded to the relayer; due to ordering, `try_replace_chunk` commits A (`N+1`) last (or B's commit fails with `StaleChunk` if A somehow lands after), leaving `V`'s actual stored version at `N+1`, not `N+2`.
5. `V` has now advertised `slot_version = N+2` in its `StackerDBChunkInv` to peers, while its `StackerDBs` DB only actually contains `N+1` — a served-vs-committed mismatch that can cause peers relying on that inventory to skip re-fetching/re-propagating the true chunk for slot `S`.

        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));

            });
