### Title
Unbounded growth of an account's TRC10 `assetV2` map allows a griefing/DoS vector against bandwidth accounting and account resource queries - (File: chainbase/src/main/java/org/tron/core/db/BandwidthProcessor.java)

### Summary
`TransferAssetActuator` allows any address to push arbitrary TRC10 tokens into a victim account's `assetV2` map without the victim's consent, and there is no cap on the number of distinct token IDs an account can accumulate. `BandwidthProcessor.updateUsage()` and the related bandwidth-consumption/query code paths then iterate over the *entire* `assetV2`/`freeAssetNetUsageV2` map of that account on every bandwidth accounting pass and on every `getAccountNet`/`getAccountResource` API query. This mirrors the "loops may consume too much gas/energy" bug class from the external report: an attacker-controlled, unbounded collection is walked on a hot, frequently-invoked path (transaction bandwidth consumption during block application, and node RPC/HTTP query paths).

### Finding Description
`TransferAssetActuator.execute()` transfers a TRC10 asset to any `toAddress` and unconditionally calls `toAccountCapsule.addAssetAmountV2(...)`, creating a brand-new key in the recipient's `assetV2` map with no opt-in from the recipient and no limit on the number of distinct asset IDs an account may hold: [1](#0-0) 

There is no validation anywhere in `TransferAssetActuator.validate()`/`execute()` that limits how many *distinct* token IDs a receiving account may accumulate — only the transferred `amount` and asset existence are checked: [2](#0-1) 

`BandwidthProcessor.updateUsage(AccountCapsule)` — invoked as part of bandwidth consumption on every transaction sent by/for that account, and also invoked from the public API layer (`Wallet.getAccountNet`, `Wallet.getAccountResource`) — iterates the account's `assetMapV2` (and merges it with `freeAssetNetUsageV2`) with an unbounded `forEach` loop: [3](#0-2) 

This same processor's `updateUsage` is called from `consume()`, which runs for every transaction whose owner is this account, on the block-application hot path (`Manager`/transaction trace processing): [4](#0-3) 

It is also invoked directly from the query-serving `Wallet` class for `getAccountNet`/`getAccountResource`, both of which are exposed over gRPC/HTTP JSON-RPC: [5](#0-4) 

Unlike other similar collections in java-tron that are explicitly bounded (e.g. `MAX_VOTE_NUMBER = 30` in `VoteWitnessActuator`, `MAX_MATCH_NUM` in `MarketSellAssetActuator`, `getMaxFrozenSupplyNumber()` in `AssetIssueActuator`), the `assetV2`/`asset` map on `Account` has **no maximum size enforced by any actuator**. An attacker who repeatedly issues low-cost TRC10 tokens (each new asset only needs to pay the asset-issuance fee once) and sends a minimal amount of each to a target address can inflate that target's `assetV2` map to an arbitrary size, since `TransferAssetActuator` requires no cooperation or signature from the recipient.

### Impact Explanation
Because `BandwidthProcessor.updateUsage()` is executed for every transaction from the victim account (as part of `consume()`, itself part of transaction execution during block application) and for every `getAccountNet`/`getAccountResource` query against the victim's address, an attacker can force the per-transaction/per-query cost for a targeted account to grow linearly with the number of distinct assets forcibly deposited into it. This can:
- Degrade the victim account's transaction-processing latency in every subsequent block that includes one of its transactions, since `Manager`/block application calls `consume()`/`updateUsage()` for that account.
- Degrade performance of the HTTP/gRPC/JSON-RPC query paths (`Wallet.getAccountNet`, `Wallet.getAccountResource`) that any anonymous API client can call against the victim address, resulting in resource exhaustion on the serving node for that endpoint.

This is a griefing/DoS class issue rather than a fund-theft or consensus-halting issue; the effect is scoped mostly to the targeted account and to the specific query/consume code path, which the rules classify at most as Medium impact (no direct theft, unbacked balance, chain split, key disclosure, or full node halt is achievable — only degraded performance for one account's transactions/queries).

### Likelihood Explanation
Likelihood is limited by the cost of TRC10 asset creation (each new distinct token ID requires paying the network's asset-issuance fee), so scaling this attack to thousands of assets requires proportional TRX expenditure by the attacker. There is no other precondition — `TransferAssetActuator` can push any already-issued asset (including cheaply/self-issued ones) into any address without the target's permission, and the code path is reachable from ordinary signed transactions and public read-only RPC calls.

### Recommendation
- Enforce a maximum number of distinct TRC10 asset entries (`assetV2`) an account may hold, similar to `MAX_VOTE_NUMBER` / `MAX_MATCH_NUM` / `getMaxFrozenSupplyNumber()`, and reject `TransferAssetContract` executions (or require recipient opt-in) once that limit would be exceeded.
- Alternatively/additionally, bound or cache the cost of `BandwidthProcessor.updateUsage()`'s asset-map iteration (e.g., lazily updating only assets touched by the current transaction rather than the full map) so that account resource accounting/query cost does not scale with attacker-inflated asset counts.
- Add tests that simulate an account receiving a large number of distinct TRC10 tokens via unsolicited transfers and assert that transaction consumption and `getAccountNet`/`getAccountResource` calls remain within acceptable bounds.

### Proof of Concept
1. Attacker issues N distinct TRC10 tokens (`AssetIssueContract`), paying the per-asset issuance fee each time.
2. For each of the N tokens, attacker calls `TransferAssetContract` sending a minimal amount to victim address `V` — `TransferAssetActuator.execute()` unconditionally adds a new entry to `V`'s `assetV2` map with no opt-in required from `V`. [1](#0-0) 
3. Any subsequent transaction sent by `V` triggers `BandwidthProcessor.consume()` → `updateUsage(V)`, which iterates over all N entries in `V`'s `assetMapV2`/`freeAssetNetUsageV2`. [3](#0-2) 
4. Similarly, any client calling `Wallet.getAccountNet(V)` or `Wallet.getAccountResource(V)` over gRPC/HTTP triggers the same unbounded iteration. [5](#0-4) 
5. As N grows, both the per-transaction bandwidth-consumption cost for `V` and the per-query cost for anyone querying `V`'s resource info grow without bound, unlike comparable collections (votes, frozen supply, market matches) which are explicitly capped elsewhere in the codebase.
