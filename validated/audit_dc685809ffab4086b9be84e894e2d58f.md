### Title
Attacker-controlled length word drives unbounded array allocation in TVM `ValidateMultiSign`/`BatchValidateSign` precompile ABI decoders, enabling a cheap-energy OutOfMemoryError DoS - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`PrecompiledContracts.extractBytesArray`, `extractSigArray`, and `extractBytes32Array` decode a "length" directly from attacker-supplied calldata via `DataWord.intValueSafe()` and immediately use it to size a Java array (`new byte[len][]`) with no upper bound check independent of the words actually present in the input. Because `intValueSafe()` clamps any value that doesn't fit in 4 bytes to `Integer.MAX_VALUE` [1](#0-0) , a single crafted 256-bit word in calldata deterministically yields `len = Integer.MAX_VALUE`, causing an immediate allocation of a huge array in `extractBytes32Array`/`extractBytesArray`/`extractSigArray` [2](#0-1) . This mirrors CVE-2015-8665's pattern: an unvalidated count/length field taken from untrusted input drives an out-of-bounds operation.

### Finding Description
`ValidateMultiSign.execute()` reads the signature-array offset directly from calldata and, only when `VMConfig.allowTvmSelfdestructRestriction()` is enabled, performs a size check — but that very check itself indexes `words[...]` without any bounds validation: [3](#0-2) 

`extractBytesArray`/`extractSigArray` bound-check the *offset* against `words.length`, but not the decoded `len`, which is used unconditionally to allocate `new byte[len][]`: [4](#0-3) 

`extractBytes32Array` (used for the `addresses` array in `BatchValidateSign`) has *no* offset bound check at all and unconditionally allocates based on the decoded length: [5](#0-4) 

The `MAX_SIZE` guard (5 for `ValidateMultiSign`, 16 for `BatchValidateSign`) that is meant to cap array sizes is only reachable *after* `VMConfig.allowTvmSelfdestructRestriction()` is true, and even then it itself performs an unguarded `words[words[3].intValueSafe() / WORD_SIZE]` lookup before the size check can reject anything. If that flag is disabled (its default `Snapshot` field is `false` unless explicitly activated via chain parameters, per `VMConfig.Snapshot`/`DynamicPropertiesStore`), `extractBytesArray`/`extractSigArray` are called with **no upper bound on `len` whatsoever** [6](#0-5) .

Crucially, energy is charged based purely on `data.length` (the actual calldata size), not on the length value embedded inside calldata: [7](#0-6) 
So a caller can submit a small, cheap calldata payload whose embedded length word is set to an out-of-range 256-bit value, forcing `intValueSafe()` to return `Integer.MAX_VALUE`, causing `new byte[Integer.MAX_VALUE][]` — an allocation of well over 16 GB of object-reference storage — to be attempted, which triggers an immediate `OutOfMemoryError`.

The critical propagation gap is that `ValidateMultiSign.execute()` has **no top-level `try/catch`** around this decode path (unlike `BatchValidateSign.execute()`, which wraps everything in `catch (Throwable t)`). The VM's opcode dispatch loop only catches `RuntimeException`, not `Error`: [8](#0-7) 
so an `OutOfMemoryError` thrown inside `ValidateMultiSign.execute()` is not contained by the VM's exception handling and propagates out of the interpreter loop into whatever transaction-processing code called it.

### Impact Explanation
An `OutOfMemoryError` triggered mid-transaction can destabilize the JVM heap for the entire node process (not just the single thread), and because it is an `Error` rather than a `RuntimeException`, it bypasses the VM's normal per-opcode exception containment. Depending on where it eventually gets caught (or not) in the block-application/transaction-execution call chain, this can crash or halt node processing — satisfying the "node crash or halt" impact bar. It is triggerable by any account able to deploy/call a contract that invokes the `ValidateMultiSign` precompile with crafted calldata, i.e., by an unprivileged transaction broadcaster/contract deployer.

### Likelihood Explanation
The trigger requires only a single crafted transaction calling a contract's `CALL` to the `ValidateMultiSign` precompile address with calldata whose signature-offset word decodes to an out-of-range value. No special privileges, no cooperation from other participants, and minimal energy cost are needed (energy is billed off `data.length`, not the malicious length field). The `BatchValidateSign` sibling path is protected by its outer `catch (Throwable t)`, but `ValidateMultiSign` is not, making it the concrete reachable path.

### Recommendation
- Bound the decoded `len` in `extractBytesArray`, `extractSigArray`, and `extractBytes32Array` against `MAX_SIZE` (or a hard cap) *before* allocating any array, independent of the `allowTvmSelfdestructRestriction` feature flag.
- Add bounds checks in `extractBytes32Array` for `offset` against `words.length`, matching `extractBytesArray`/`extractSigArray`.
- Wrap `ValidateMultiSign.execute()` in a `catch (Throwable t)` (as already done in `BatchValidateSign.execute()`) so any decode-time `Error`/`RuntimeException` is safely converted into a rejected/false result rather than propagating out of the VM.
- Validate the ABI-encoded length fields against the actual `data.length` before using them for allocation sizing, consistent with the `isValidAbiEncoding` check already used for TIP-854/Osaka-gated validation, but make this bound apply unconditionally, not just when `allowTvmOsaka()`/`allowTvmSelfdestructRestriction()` is active.

### Proof of Concept
1. Deploy or call a contract that performs a low-level `CALL` (or use `abi.encodeWithSignature`) to the `validatemultisign(address,uint256,bytes32,bytes[])` precompile address.
2. Construct calldata so that the ABI head is well-formed for the fixed parameters, but the word at the signature-array-length slot (the word referenced via `words[3]`'s pointed-to offset) is set to a 256-bit value that does not fit in 4 bytes (e.g., `0xFFFFFFFF00000000...`), so `DataWord.intValueSafe()` returns `Integer.MAX_VALUE`.
3. Ensure `VMConfig.allowTvmSelfdestructRestriction()` is not active in the target environment (its default state), so the `MAX_SIZE` early-return check is skipped and `extractBytesArray`/`extractSigArray` is invoked directly with the unbounded `len`.
4. Submit the transaction; `new byte[Integer.MAX_VALUE][]` is attempted inside `extractBytesArray`/`extractSigArray`, throwing `OutOfMemoryError` uncaught by `ValidateMultiSign.execute()`, which is not caught by `VM.play()`'s `catch (RuntimeException e)` block.

Note: I was unable to fully confirm from the index alone whether `allowTvmSelfdestructRestriction` is currently active on TRON mainnet (its activation state is chain-parameter driven and not fixed in code) — this affects whether the "no bound at all" sub-case or the "unguarded size-check indexing" sub-case is the active exploitation path, but both sub-cases independently permit an unguarded `words[]` index/allocation from attacker data, so the underlying vulnerability holds regardless of that flag's state. Confirming live activation state would require checking on-chain `DynamicPropertiesStore` parameters, which is outside the scope of static code search.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
