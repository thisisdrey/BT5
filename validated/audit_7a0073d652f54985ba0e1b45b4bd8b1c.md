### Title
FetchRemote lacks the `transfer.bundleURI=false` guard, allowing SSRF via a malicious remote's bundle-uri capability - ([File: internal/gitaly/service/repository/fetch_remote.go])

### Summary
`CreateRepositoryFromURL`'s `cloneFromURLCommand` explicitly disables `transfer.bundleURI` before invoking `git clone` because the git client can be induced by a server it fetches from to issue an outbound HTTP request to an attacker-chosen URI advertised as a "bundle." `buildCommandOpts` in `fetch_remote.go`, which builds the equivalent config for `git fetch` used by `FetchRemote`, does not apply this same mitigation, leaving the identical attack surface open on the `FetchRemote` RPC.

### Finding Description
`FetchRemote` lets an unprivileged, self-owned-repository user configure a pull mirror or one-off fetch pointing `RemoteParams.Url` at a server they control: [1](#0-0) 
The `remote.inmemory.url` config is set from the fully attacker-controlled URL, and the resulting config is fed into `quarantineRepo.FetchRemote(ctx, "inmemory", opts)`: [2](#0-1) 
Unlike `cloneFromURLCommand`, which sets `transfer.bundleURI=false` on the outbound clone specifically because "the URI can point to any server, including localhost": [3](#0-2) 
`buildCommandOpts` never sets this guard for the `git fetch` invocation. During the smart-HTTP/SSH negotiation with the attacker's server, `git-upload-pack` on the attacker's side can advertise a `bundle-uri` capability containing `bundle.<n>.uri=http://169.254.169.254/` or any other internal address. If the Gitaly host's git client does not have this capability explicitly suppressed, Gitaly's own `git` process (not GitLab Rails, not the attacker's infrastructure) will issue the outbound HTTP request to fetch the advertised bundle from that internal address — the same primitive the codebase's own comment identifies as a security risk in the clone path, but left unmitigated in the fetch path.

The `s.locator.ValidateRepository` and `validateFetchRemoteRequest` checks only validate the repository field and confirm the URL is non-empty; they do not restrict the URL to be non-internal, and no bundle-uri disabling config exists anywhere in `buildCommandOpts` or downstream `localrepo.FetchOpts` construction.

### Impact Explanation
This is an outbound SSRF primitive controlled entirely by an unprivileged user: Gitaly's own git process can be coerced into making an HTTP(S) request to arbitrary internal network addresses (e.g. cloud metadata endpoints, internal admin services) reachable from the Gitaly host, which can be used to probe internal infrastructure or exfiltrate/access endpoints not meant to be internet-reachable from the perspective of GitLab's threat model. This matches GitLab's SSRF bounty impact class and directly violates the invariant called out in the codebase itself ("prevent attack vectors that could abuse this mechanism").

### Likelihood Explanation
Fully reachable by an unprivileged user: any user who can configure a pull mirror or trigger `FetchRemote` (e.g., via project import/pull mirroring features that map to this RPC) with a URL pointing at attacker-controlled infrastructure can serve a crafted `git-upload-pack` response advertising the malicious bundle-uri capability. No admin privilege, stolen secret, or non-default configuration is required — only that Gitaly's git client, absent the explicit `transfer.bundleURI=false` override, processes the advertised capability. I could not fully verify from this repository alone whether the target git version defaults `transfer.bundleURI` to enabled or disabled client-side; however, the very fact that Gitaly's own maintainers found it necessary to explicitly disable this for `CreateRepositoryFromURL` while leaving `FetchRemote` unmitigated demonstrates the developers considered this exploitable in at least one of these otherwise near-identical code paths, and the omission on `FetchRemote` is an inconsistency in the same threat model.

### Recommendation
Apply the same `gitcmd.WithGlobalOption(gitcmd.ConfigPair{Key: "transfer.bundleURI", Value: "false"})` mitigation (or the config-pair equivalent appended in `buildCommandOpts`) to the `git fetch` invocation used by `FetchRemote`, so that outbound fetches from arbitrary attacker-supplied remotes cannot trigger bundle-uri-driven requests to internal endpoints.

### Proof of Concept
```go
func TestFetchRemote_BundleURISSRF(t *testing.T) {
    // Canary HTTP listener representing an "internal" endpoint.
    var hit bool
    canary := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        hit = true
    }))
    defer canary.Close()

    // Malicious upload-pack server advertising bundle-uri capability pointing at canary.URL.
    remoteRepo, remoteURL := gittest.CreateMaliciousUploadPackServer(t, gittest.MaliciousBundleURIConfig{
        BundleURI: canary.URL,
    })

    repo, _ := gittest.CreateRepository(t, ctx, cfg)
    _, err := client.FetchRemote(ctx, &gitalypb.FetchRemoteRequest{
        Repository: repo,
        RemoteParams: &gitalypb.Remote{
            Url: remoteURL, // attacker-controlled
        },
    })
    require.NoError(t, err)

    require.True(t, hit, "expected Gitaly's git process to have requested the internal canary URL via bundle-uri")
}
```
Expected (vulnerable) result: `hit == true`, showing Gitaly's `git fetch` process made an outbound request to the attacker-designated internal address. After applying the `transfer.bundleURI=false` fix to `buildCommandOpts`, the request should not occur and `hit` should remain `false`.

func buildCommandOpts(ctx context.Context, opts *localrepo.FetchOpts, req *gitalypb.FetchRemoteRequest) error {
	remoteURL := req.GetRemoteParams().GetUrl()
	var config []gitcmd.ConfigPair

	for _, refspec := range getRefspecs(req.GetRemoteParams().GetMirrorRefmaps()) {
		config = append(config, gitcmd.ConfigPair{
			Key: "remote.inmemory.fetch", Value: refspec,
		})
	}

	if resolvedAddress := req.GetRemoteParams().GetResolvedAddress(); resolvedAddress != "" {
		modifiedURL, resolveConfig, err := gitcmd.GetURLAndResolveConfig(remoteURL, resolvedAddress)
		if err != nil {
			return fmt.Errorf("couldn't get curloptResolve config: %w", err)
		}

		remoteURL = modifiedURL
		config = append(config, resolveConfig...)
	}

	config = append(config, gitcmd.ConfigPair{Key: "remote.inmemory.url", Value: remoteURL})

	if featureflag.FetchRemoteProactiveAuth.IsEnabled(ctx) {
		if u, err := url.Parse(remoteURL); err == nil && u.User != nil {
			password, _ := u.User.Password()
			if u.User.Username() != "" && password != "" {
				config = append(config, gitcmd.ConfigPair{
					Key:   "http.proactiveAuth",
					Value: "basic",
				})
			}
		}
	}

	if authHeader := req.GetRemoteParams().GetHttpAuthorizationHeader(); authHeader != "" {
		config = append(config, gitcmd.ConfigPair{
			Key:   fmt.Sprintf("http.%s.extraHeader", req.GetRemoteParams().GetUrl()),
			Value: "Authorization: " + authHeader,
		})
	}

	opts.CommandOptions = append(opts.CommandOptions, gitcmd.WithConfigEnv(config...))

	return nil
}
