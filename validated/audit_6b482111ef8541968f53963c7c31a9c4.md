## Analog Vulnerability Found

### Title
Nil-pointer dereference in `RemoteAllowList.Allow`/`getInsideAllowList` causes remote crash when `lighthouse.remote_allow_list` is unset - (File: `allow_list.go`)

### Summary
The Sherlock finding describes `Hats.balanceOfBatch` failing to apply the same guard logic that the singular `Hats.balanceOf` applies, causing inconsistent behavior between two functions that are supposed to enforce the same invariant. In nebula-004, `RemoteAllowList` has three sibling accessor methods that are supposed to share the same "nil-list means allow everything" invariant, but one of them is missing the guard the others have, creating an analogous inconsistency — except here the consequence is a nil-pointer panic rather than a stale balance.

### Finding Description
`RemoteAllowList` exposes three public methods used to decide whether a reported/learned remote address should be accepted: [1](#0-0) 

- `AllowUnknownVpnAddr` explicitly guards against a nil `*RemoteAllowList` receiver:
```go
func (al *RemoteAllowList) AllowUnknownVpnAddr(vpnAddr netip.Addr) bool {
	if al == nil {
		return true
	}
	return al.AllowList.Allow(vpnAddr)
}
```
- `AllowAll` (the "batch" variant, taking `[]netip.Addr`) never dereferences `al` directly before calling `al.AllowList.Allow(...)`, and `AllowList.Allow` itself is nil-safe:
```go
func (al *AllowList) Allow(addr netip.Addr) bool {
	if al == nil {
		return true
	}
	...
}
``` [2](#0-1) 
so `AllowAll` tolerates a nil `RemoteAllowList.AllowList` field, though it still calls `al.getInsideAllowList(vpnAddr)` for each address.

- `Allow` (the singular variant used per-address) and its helper `getInsideAllowList` never check for a nil receiver at all:
```go
func (al *RemoteAllowList) Allow(vpnAddr netip.Addr, udpAddr netip.Addr) bool {
	if !al.getInsideAllowList(vpnAddr).Allow(udpAddr) {
		return false
	}
	return al.AllowList.Allow(udpAddr)
}

func (al *RemoteAllowList) getInsideAllowList(vpnAddr netip.Addr) *AllowList {
	if al.insideAllowLists != nil {
		...
	}
	return nil
}
``` [3](#0-2) 

If the atomic pointer holding the `RemoteAllowList` is nil (i.e., `lighthouse.remote_allow_list` is not configured — the default), `getInsideAllowList` dereferences `al.insideAllowLists` on a nil `*RemoteAllowList` receiver, which is a genuine Go nil-pointer dereference (unlike a no-op method call on nil, field access on a nil struct pointer panics).

This function is reached from the lighthouse's per-address filtering logic used when learning/accepting reported remote addresses from an untrusted, unauthenticated peer:
```go
func (lh *LightHouse) unlockedShouldAddV4(vpnAddr netip.Addr, to *V4AddrPort) bool {
	udpAddr := protoV4AddrPortToNetAddrPort(to)
	allow := lh.GetRemoteAllowList().Allow(vpnAddr, udpAddr.Addr())
	...
}
``` [4](#0-3) 

Both `unlockedShouldAddV4` and `unlockedShouldAddV6` call the unguarded `Allow`, while the batch path `shouldAdd` (used elsewhere) calls the correctly-guarded `AllowAll`: [5](#0-4) 

This is the direct structural analog of the audited bug class: two sibling accessor functions meant to enforce an identical "empty configuration ⇒ default-allow" invariant diverge — the batch/plural (`AllowAll`) function is safe, but the singular per-item function (`Allow`) is not.

### Impact Explanation
Any peer able to send a host update/reply that reaches `unlockedShouldAddV4`/`unlockedShouldAddV6` — i.e., any remote peer reporting addresses for itself, no CA-signed certificate required to trigger the panic once code path is reachable during host-address learning — will crash the receiving nebula process with a nil-pointer panic if the node does not configure `lighthouse.remote_allow_list` (a common, default configuration). This is a remote, unauthenticated denial-of-service against any node processing address updates.

### Likelihood Explanation
Likelihood is high in default deployments: `lighthouse.remote_allow_list` is optional and frequently left unset, meaning `LightHouse.GetRemoteAllowList()` returns a nil `*RemoteAllowList`. Every reported/learned remote address processed through `unlockedShouldAddV4`/`unlockedShouldAddV6` will invoke the vulnerable `Allow` method.

### Recommendation
Add the same nil-receiver guard used in `AllowUnknownVpnAddr` to both `RemoteAllowList.Allow` and `RemoteAllowList.getInsideAllowList`:
```go
func (al *RemoteAllowList) Allow(vpnAddr netip.Addr, udpAddr netip.Addr) bool {
	if al == nil {
		return true
	}
	if !al.getInsideAllowList(vpnAddr).Allow(udpAddr) {
		return false
	}
	return al.AllowList.Allow(udpAddr)
}

func (al *RemoteAllowList) getInsideAllowList(vpnAddr netip.Addr) *AllowList {
	if al == nil || al.insideAllowLists == nil {
		return nil
	}
	...
}
```

### Proof of Concept
1. Start a nebula node without setting `lighthouse.remote_allow_list` in its config (default).
2. As any peer (no special certificate trust required beyond a valid tunnel/host update path), send a host update/reply packet containing V4/V6 address entries that route through `RemoteList.unlockedSetV4`/`unlockedSetV6` → `shouldAdd` callback → for this specific code path `unlockedShouldAddV4`/`unlockedShouldAddV6` → `lh.GetRemoteAllowList().Allow(vpnAddr, addr)`.
3. Because `GetRemoteAllowList()` returns nil and `Allow`/`getInsideAllowList` do not check for a nil receiver, the process panics with "invalid memory address or nil pointer dereference," crashing the nebula process (remote DoS).

I was not able to fully trace every caller path of `unlockedShouldAddV4`/`unlockedShouldAddV6` to `shouldAdd`'s registration inside `RemoteList` (that wiring is in `remote_list.go`, which was only partially inspected), so I cannot cite the exact call chain from a raw incoming packet handler down to this function with full certainty — a background Devin session with full file access would be needed to confirm the precise external trigger packet type and unit-test this panic end-to-end.
