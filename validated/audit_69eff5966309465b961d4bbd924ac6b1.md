### Title
Out-of-bounds read in TVM precompile ABI decoding via unvalidated offsets in `extractBytesArray`/`extractSigArray` - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The CVE-2022-41977 bug class is an out-of-bounds read caused by trusting an attacker-controlled length/offset field when extracting a sub-region of a buffer without validating it against the buffer's actual bounds. The same pattern exists in `PrecompiledContracts.extractBytesArray`, `extractBytes32Array`, and `extractSigArray`, which decode ABI-style calldata passed by any unprivileged contract caller into TVM precompiles (e.g. `BatchValidateSign`/`ValidateMultiSign`), and ultimately call `extractBytes` which performs `Arrays.copyOfRange(data, offset, offset + len)` with no bounds checking.

### Finding Description
`extractBytesArray` reads a length word from attacker-supplied `words[offset]` via `intValueSafe()`, then for each element reads a `bytesOffset` and `bytesLen` also taken directly from attacker-controlled `words[]`, and calls `extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE, bytesLen)`: [1](#0-0) 

`extractSigArray` follows the identical pattern, computing `bytesOffset` from attacker data and calling `extractBytes` with a fixed `SIG_LENGTH`: [2](#0-1) 

`extractBytes` itself performs no validation at all before slicing:
```java
private static byte[] extractBytes(byte[] data, int offset, int len) {
    return Arrays.copyOfRange(data, offset, offset + len);
}
``` [3](#0-2) 

`Arrays.copyOfRange` in the JDK does not throw `ArrayIndexOutOfBoundsException` for an out-of-range `offset` in all cases consistently — it can throw various runtime exceptions (`IndexOutOfBoundsException`, `NegativeArraySizeException`) depending on the combination of negative/overflowing `offset`/`len`, but critically there is no domain-specific bounds check comparing `offset`/`len` against `data.length` before the call, unlike the analogous, already-hardened `subBytes` helper in `ContractEventParser` which explicitly validates `start`/`length` against `src.length` and throws `OutputLengthException`: [4](#0-3) 

This shows the codebase is aware of this exact bug class (unvalidated length/offset fields from untrusted ABI-encoded data leading to out-of-bounds slicing) and has already patched it in `ContractEventParser`, evidenced by dedicated regression tests for oversized/negative lengths: [5](#0-4) [6](#0-5) 

However the equivalent unvalidated slicing logic in `PrecompiledContracts.extractBytesArray`/`extractSigArray`/`extractBytes` was not given the same treatment.

### Impact Explanation
An attacker who invokes a TRC-20/TVM contract that calls into these precompiles (e.g. the batch/multi-signature validation precompiles that use `extractSigArray`) with crafted calldata can trigger integer overflow or negative offsets in the `(bytesOffset + offset + 2) * WORD_SIZE` computation, causing `Arrays.copyOfRange` to throw an uncaught runtime exception, or in the offset-overflow case attempt to read heap memory beyond the intended slice of `data`. Depending on how the exception propagates through the TVM interpreter loop, this can manifest as a node crash/uncaught exception during transaction execution (denial of service for the node processing the block/transaction) rather than a leak returned to the caller, since the copied bytes stay within the `data` array's allocation (an array cannot be read past its own backing allocation in Java) — meaning it is best characterized as an uncontrolled-exception/DoS analog rather than true cross-buffer information disclosure. This still meets the "node crash" impact bar if the exception is not caught by a broad catch block in the calling precompile's `execute()`.

### Likelihood Explanation
Reachable directly from any account by deploying/calling a contract that invokes the affected precompiled contract address (`BatchValidateSign` / `ValidateMultiSign`), passing crafted calldata — no special privilege required. Likelihood depends on whether `execute()` wraps the precompile logic in a catch-all (`Throwable`) that converts the fault into a normal revert rather than propagating up; this could not be fully confirmed from the excerpts retrieved, since the precompile classes for `BatchValidateSign`/`ValidateMultiSign` were not located in the available index.

### Recommendation
Add explicit bounds validation (offset >= 0, len >= 0, `offset + len <= data.length`, guarding against integer overflow) inside `extractBytes` (and validate `bytesOffset`/`bytesLen`/array length in `extractBytesArray`, `extractBytes32Array`, `extractSigArray`) before calling `Arrays.copyOfRange`, mirroring the pattern already used in `ContractEventParser.subBytes`.

### Proof of Concept
Not fully verifiable from the index alone: I could not locate the `BatchValidateSign`/`ValidateMultiSign` precompile `execute()` bodies (to confirm they call `extractSigArray`/`extractBytesArray` and whether exceptions are caught) within the available codebase context — the index has size limits and some file contents may be excluded. Given this uncertainty, I cannot conclusively prove end-to-end reachability and impact without further inspection. If a full PoC is needed, a Devin session with complete repository access would be required to trace the callers of `extractSigArray`/`extractBytesArray` and confirm the exception-handling behavior in the precompile's `execute()`.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }

  protected static byte[] subBytes(byte[] src, int start, int length) {
    if (ArrayUtils.isEmpty(src)) {
      throw new OutputLengthException("source data is empty");
    }
    if (start < 0 || start >= src.length || length < 0 || length > src.length - start) {
      throw new OutputLengthException(
          "data start:" + start + ", length:" + length + ", src.length:" + src.length);
    }
    byte[] dst = new byte[length];
    System.arraycopy(src, start, dst, 0, length);
    return dst;
  }
```
