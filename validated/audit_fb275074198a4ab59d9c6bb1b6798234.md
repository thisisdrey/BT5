### Title
`PeerNetwork::handle_unsolicited_StackerDBPushChunk` advertises a StackerDB slot version to peers before the chunk is actually persisted, breaking the served-vs-committed invariant - (File: stackslib/src/net/stackerdb/mod.rs)

### Summary
The reported bug class is a getter (`maxWithdraw`) promising state (a withdrawable amount) that the actual state-mutating path (`withdraw`/`previewWithdraw`) cannot honor, because the getter and the mutator compute things differently/at different times. The equivalent fault in this repo is in the unsolicited `StackerDBPushChunk` handler: it patches and immediately transmits a `StackerDBChunkInv` reply claiming a new slot version is now held by this node, before that chunk has actually been written to the local StackerDB.

### Finding Description
`PeerNetwork::handle_unsolicited_StackerDBPushChunk` validates an unsolicited pushed chunk with `validate_received_chunk` (signature, staleness, size, max-writes) and, on success, directly mutates the in-memory `StackerDBChunkInvData.slot_versions` entry to the new version: [1](#0-0) 

It then immediately serializes and sends this patched inventory back to the remote peer as the authoritative reply: [2](#0-1) 

Crucially, this function never calls `try_replace_chunk`/`insert_chunk` itself — the chunk's actual persistence is deferred to the relayer via `process_pushed_stacker_db_chunks` → `process_stacker_db_chunks`, invoked later in `Relayer::process_network_result`: [3](#0-2) 

The function's own doc comment even asserts the (false) premise that storage happens synchronously here ("we can store it right now (so don't buffer it)"), while the code path only sends the network reply: [4](#0-3) 

Actual storage enforces its own independent set of checks in `StackerDBTx::try_replace_chunk` (size, signer, staleness, max-writes): [5](#0-4) 

Because the inventory (`StackerDBChunkInv`) is advertised optimistically ahead of the real commit, any peer receiving this inventory reply believes the local node already holds `slot_version` for that slot. If the actual insert is delayed, interleaved with another accepted write for the same slot, or otherwise does not complete, the node has already told the network it possesses data it does not yet (or ever) have — the "served vs. committed" equality is broken, mirroring how `maxWithdraw` advertised an amount `withdraw` could not actually deliver.

### Impact Explanation
A peer that trusts this inventory reply may treat this node as a valid source for that slot version and stop re-fetching/re-propagating it, or a subsequent `GetChunk`/`StackerDBGetChunksInv` request against this exact slot/version can be answered with stale data or fail, since the advertised version was not actually committed at advertisement time. This is a "served vs. committed" mismatch — non-canonical local state (an uncommitted write) is reported as if it were canonical/available inventory to the rest of the network, which can propagate incorrect availability information for StackerDB-backed data (e.g., signer/miner message replicas).

### Likelihood Explanation
The path is reachable by any unauthenticated, connected p2p peer sending a validly-signed `StackerDBPushChunk` message (no special role or secret key beyond the chunk's own valid signer signature, which any legitimate slot owner already produces during normal operation) — `handle_unsolicited_StackerDBPushChunk` runs for all unsolicited pushes. The window for divergence is the gap between the immediate inventory reply and the later, separate persistence step; the likelihood of an actual persistence failure/delay in that window depends on timing/interleaving with other network processing, which I could not fully trace end-to-end (see below), so likelihood should be treated as moderate rather than certain.

### Recommendation
Only patch and advertise the `StackerDBChunkInv` slot version after the chunk has been durably written to the StackerDB (i.e., move the `try_replace_chunk`/`insert_chunk` call, or an equivalent synchronous persistence step, before or inside `handle_unsolicited_StackerDBPushChunk`, and only then update `slot_versions`/send the reply). Alternatively, do not send an updated inventory in the immediate reply at all — reply with the pre-existing (queried) version and let a legitimate inventory refresh occur only after the relayer has actually committed the chunk.

### Proof of Concept
1. As a connected peer, send a validly-signed `StackerDBPushChunk` for a known slot/contract with `slot_version = V+1` (`V` being the current stored version).
2. `handle_unsolicited_StackerDBPushChunk` calls `validate_received_chunk`, which succeeds (size/signature/staleness/max-writes all pass against the freshly-queried `V`) — see `stackslib/src/net/stackerdb/mod.rs:649-718`.
3. The function patches `data.slot_versions[slot_id] = V+1` and immediately signs and sends this `StackerDBChunkInv` back to the sender (`stackslib/src/net/stackerdb/mod.rs:794-870`), before any call to `try_replace_chunk`.
4. Actual storage of the chunk only happens later, out-of-band, via `Relayer::process_pushed_stacker_db_chunks` (`stackslib/src/net/relay.rs:2469-2493`) as part of `process_network_result` (`stackslib/src/net/relay.rs:2927-2933`).
5. Any observer that queries this node's inventory or requests the chunk for slot/version `V+1` in the interval between steps 3 and 4 (or if step 4 never completes for that chunk) will find the advertised state does not match the node's actual committed StackerDB contents.

Note: I was unable to fully trace every failure mode of `process_stacker_db_chunks` (its exact body was not located in the indexed context) to conclusively demonstrate a guaranteed permanent divergence versus a self-correcting race window; this is stated as an open uncertainty. If a full trace is needed, a Devin session with complete repository access should verify `Relayer::process_stacker_db_chunks`'s handling of pushed StackerDB chunks end-to-end.

    /// Add or replace a chunk for a given reward cycle, if it is valid
    /// Otherwise, this errors out with Error::StaleChunk
    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
}
