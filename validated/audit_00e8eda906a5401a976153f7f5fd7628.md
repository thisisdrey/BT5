### Title
Unprotected AMM refund swap in `SwapFirstAssetTrader::refund_weight` allows sandwich extraction of XCM fee-refund value - (File: cumulus/primitives/utility/src/lib.rs)

### Summary
`SwapFirstAssetTrader` is a `WeightTrader` used in production XCM configs (Asset Hub Westend/Rococo, Penpal, staking-async parachain runtime) to let users pay XCM execution fees in a non-native asset by swapping it for the `Target` asset through `pallet-asset-conversion`'s `SwapCredit`. When unused weight is refunded, `refund_weight` swaps the excess `Target` credit back into the user's original fee asset by calling `SwapCredit::swap_exact_tokens_for_tokens` with `amount_out_min` hard-coded to `None` [1](#0-0) . This is the exact bug class from the external report: an AMM swap executed with zero slippage protection.

### Finding Description
`pallet-asset-conversion` fully supports slippage protection via `amount_out_min` on `swap_exact_tokens_for_tokens`, enforcing `ProvidedMinimumNotSufficientForSwap` when the quoted output would be too low [2](#0-1) . However this protection is opt-in per caller, and `SwapFirstAssetTrader::refund_weight` in `cumulus/primitives/utility/src/lib.rs` deliberately bypasses it by passing `None`:

```rust
let refund = self.total_fee.extract(refund_amount);
let refund = match SwapCredit::swap_exact_tokens_for_tokens(
    vec![Target::get(), refund_swap_asset],
    refund,
    None,
) { ... }
``` [1](#0-0) 

`buy_weight`, by contrast, protects the paying side by swapping `swap_tokens_for_exact_tokens` for a fixed `fee` amount [3](#0-2) , so only the refund leg is exposed to arbitrary pool price at execution time. `SwapFirstAssetTrader` is wired into live runtime XCM configurations, e.g. Asset Hub Westend/Rococo, Penpal, and the staking-async parachain runtime, over the same `pallet-asset-conversion` pools that anyone can `add_liquidity`/`remove_liquidity`/`swap_exact_tokens_for_tokens` against in an ordinary, unprivileged extrinsic [4](#0-3) .

Because `pallet-asset-conversion` pools use a simple constant-product AMM (`get_amount_out`/`get_amount_in`), any account can shift the reserve ratio of the `Target`/`refund_swap_asset` pool with a large ordinary swap immediately before an XCM message that triggers `refund_weight` is executed in the same block, then reverse the trade afterward, sandwich-extracting value from the unprotected refund swap — precisely the "no slippage protection, no deadline" pattern flagged in the Cork Protocol report, where `removeLiquidity`/`swapExactTokensForTokens` were called with `0` minimums and `block.timestamp` as deadline.

### Impact Explanation
The refund leg converts already-collected XCM fee credit (protocol/user-held value, `total_fee`) back to the sender's asset at whatever price the pool currently reports, with no floor. A manipulated pool state at the moment of refund can cause the refunded credit amount to be arbitrarily reduced, with the deficit captured as arbitrage profit by whoever manipulated the pool (buy low pre-swap, let the refund swap fill at the bad price, sell back after). This is value leaving legitimate refund recipients into an attacker's pocket via ordinary public AMM calls — consistent with the "theft/loss of protocol or user funds via underpriced/unprotected AMM interaction" impact class.

### Likelihood Explanation
No privileged role, governance action, leaked key, or malicious node/validator/relayer is required — only ordinary `swap_exact_tokens_for_tokens`/`add_liquidity`/`remove_liquidity` extrinsics against the `pallet-asset-conversion` pool paired with normal XCM traffic that exercises `SwapFirstAssetTrader` (fee payment in non-native asset with partial weight refund), which is exactly the flow enabled in Asset Hub and Penpal XCM configs. The precondition is simply that such a pool exists and has exploitable liquidity depth relative to the refunded amount, which is realistic for smaller or newly created pools.

### Recommendation
Do not hard-code `None` for `amount_out_min` in `refund_weight`. Compute an acceptable minimum (e.g., via `QuotePrice::quote_price_exact_tokens_for_tokens` at the time of refund, minus a configurable tolerance) and pass it to `SwapCredit::swap_exact_tokens_for_tokens`; on failure, fall back to holding/returning the `Target`-denominated credit (or another safe path) rather than accepting an unbounded-slippage swap.

### Proof of Concept
1. Configure a chain (mirroring Asset Hub's `xcm_config.rs`) using `SwapFirstAssetTrader<Target, AssetConversion, ..>` as (part of) the `WeightTrader`, with a `pallet-asset-conversion` pool for `Target`/`AssetX` that has shallow liquidity.
2. Attacker (unprivileged) submits `AssetConversion::swap_exact_tokens_for_tokens` to heavily skew the `Target`/`AssetX` reserve ratio, unfavorable to `Target -> AssetX` conversions, in the same block as step 3.
3. A user sends an XCM message paying fees in `AssetX` via `buy_weight` (this locks in `fee` amount of `AssetX -> Target` at a fair/near price) but the message under-consumes weight, triggering `refund_weight`, which swaps leftover `Target` back to `AssetX` with `amount_out_min: None` at the now-skewed price, yielding far less `AssetX` than expected [1](#0-0) .
4. Attacker reverses their swap after the refund executes, capturing the price impact as profit, while the honest user's refund is silently degraded — no revert occurs because there is no minimum-output check on this path, unlike every other public entry point in `pallet-asset-conversion` (`swap_exact_tokens_for_tokens`, `remove_liquidity`) which all enforce `amount_out_min`/`amount_min_receive` [5](#0-4) .
