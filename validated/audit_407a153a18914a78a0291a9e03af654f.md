### Title
Missing Domain Separator in StackerDB Chunk Signatures Enables Cross-Contract Replay - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` computes the signed digest for a StackerDB chunk from only `slot_id`, `slot_version`, and `data_hash`. It never binds the signature to the specific StackerDB smart contract (`QualifiedContractIdentifier`) the chunk belongs to. Because multiple StackerDB contracts commonly reuse the exact same signer-to-slot ordering, a chunk legitimately signed by a signer for one contract can be replayed verbatim into a different contract, and `validate_received_chunk()` will accept it as authentic for that unrelated database. This is the direct analog of the reported cross-chain replay bug: the signed hash lacks a context/domain identifier, so the same signature is valid across multiple unintended "domains" (here, StackerDB contracts instead of chains).

### Finding Description
The digest that gets signed/verified for every StackerDB chunk is: [1](#0-0) 

This digest omits the smart contract identifier of the StackerDB the chunk is destined for. Verification is performed purely against `(slot_id, slot_version, data_hash)`: [2](#0-1) 

The node-side acceptance path, `validate_received_chunk`, resolves the expected signer strictly from `smart_contract_id` + `data.slot_id` and then calls `slot_metadata.verify(&addr)`, which — as shown above — never checks that the signature was produced for *this* `smart_contract_id`: [3](#0-2) 

Multiple StackerDB contracts on the same node deliberately reuse the identical signer ordering. The signer-message-type contracts (`signers-0-{message_id}`, one per message topic for signer set 0) each simply forward to the shared page of signer slots: [4](#0-3) 

and the underlying `.signers` contract stores one shared ordered slot list per signer-set/page that is reused by every one of these topic-specific contracts: [5](#0-4) 

Consequently, for a given signer set, the address occupying `slot_id = k` is identical across all `signers-0-{message_id}` (and all `signers-1-{message_id}`) contracts. Since the chunk signature never commits to `smart_contract_id`, a `StackerDBChunkData` legitimately signed and broadcast for contract A (e.g. block-response topic) at slot `k`/version `v` is a byte-for-byte valid, independently-verifiable chunk for contract B (e.g. transaction topic) at the same `slot_id`, as long as B's `expected_version[k] <= v <= max_writes`. `validate_received_chunk()` performs no additional binding check, so it will accept and store the replayed chunk as if the signer had authored it for contract B.

### Impact Explanation
This breaks the authentication guarantee that a StackerDB chunk actually originates from its claimed signer *for that specific database/topic*. An attacker who observes a legitimately signed, publicly-gossiped chunk (StackerDB chunks are pushed/relayed in the clear over the p2p network) can replay it into a different StackerDB contract slot owned by the same signer, causing unauthorized/forged data to be accepted and stored under a different topic's namespace without the signer's consent for that context. This is an unauthenticated write into StackerDB state via forged/misattributed data, which downstream consumers (miners, other signers) will treat as canonical, legitimately-signed content for that topic — a High/Critical impact per the class of "unauthenticated/unauthorized write to StackerDB" and "network-wide propagation of forged data."

### Likelihood Explanation
Likelihood is high for any attacker capable of observing p2p StackerDB chunk traffic (no special privilege required — StackerDB pushes are broadcast) combined with knowledge of the target signer's slot assignment in the destination contract (public information, since slot orderings are queryable on-chain via `stackerdb-get-signer-slots-page`). No node secret or other party's private key is required — only replaying an already-observed, validly-signed message into a differently-scoped storage target.

### Recommendation
Bind the smart contract identifier (and/or network id) into the signed digest, mirroring the recommended fix for the original bug (including `chain_id`/domain in the hash). Concretely, modify `SlotMetadata::auth_digest()` to also hash the `QualifiedContractIdentifier` of the StackerDB (or another canonical domain separator unique to that DB instance), and update `sign`/`verify`/`StackerDBChunkData::sign`/`verify`/`recover_pk` call sites (`libstackerdb/src/libstackerdb.rs`, and callers in `stackslib/src/net/stackerdb/mod.rs` and `db.rs`) to pass the contract id through so verification is contract-scoped.

### Proof of Concept
1. Signer `S` is assigned `slot_id = 0` in both `signers-0-3.<contract>` and `signers-0-7.<contract>` (guaranteed by the shared slot-ordering design in `signers.clar`/`signers-0-xxx.clar`).
2. `S` legitimately signs and pushes `StackerDBChunkData { slot_id: 0, slot_version: 5, sig, data }` to `signers-0-3`.
3. An observer captures this chunk off the wire (unauthenticated p2p gossip) and re-submits the identical `StackerDBChunkData` to `signers-0-7`.
4. `validate_received_chunk` for `signers-0-7` resolves the same signer address `S` for `slot_id = 0` via `get_slot_signer`, calls `slot_metadata.verify(&addr)`, which succeeds because `auth_digest()` never referenced the contract id — the chunk is accepted and stored in `signers-0-7` even though `S` never intended to author this content for that topic.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
}
