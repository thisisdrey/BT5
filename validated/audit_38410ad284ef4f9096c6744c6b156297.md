### Title
Redundant sequential divisions in vote-power reallocation cause excess rounding loss - (File: actuator/src/main/java/org/tron/core/actuator/UnfreezeBalanceV2Actuator.java)

### Summary
When an account unfreezes TRX2 stake and its remaining TRON Power becomes smaller than the total votes it previously cast, `updateVote()` proportionally scales down every vote using two chained divisions instead of one combined division, exactly the anti-pattern flagged in the external audit (computing `sharesToMint`/`operatorRewards` via two separate divisions instead of delegating to a single division).

### Finding Description
`UnfreezeBalanceV2Actuator.updateVote()` (and the byte-code equivalent `UnfreezeBalanceV2Processor.updateVote()`) recomputes each SR vote after a stake reduction with: [1](#0-0) 

```java
long newVoteCount =
    (long) ((double) vote.getVoteCount() / totalVote * ownedTronPower / TRX_PRECISION);
```

This performs the division `/ totalVote` and then a second, independent division `/ TRX_PRECISION`, each rounding (via the intermediate `double`) before the final narrowing cast to `long`. Mathematically this should be a single division: `(vote.getVoteCount() * ownedTronPower) / (totalVote * TRX_PRECISION)`. Chaining two divisions (with an intervening multiplication) on a `double` amplifies floating point rounding error compared to a single combined division, exactly the class of bug the external report calls out — "we can reduce the number of divisions to 1... This would further avoid the rounding errors that we would get when we divide two numbers."

The identical pattern also exists in the non-TVM path `UnfreezeBalanceV2Actuator`, which recalculates and persists the new (smaller) vote list for the same account, and which is invoked by an ordinary `UnfreezeBalanceV2Contract` broadcast from any unfreezing account. Because `TRON Power` is recomputed after subtracting the unfrozen `FreezeV2`/`unfreezingV2` amounts, any account that partially unfreezes while it still has active votes triggers this recomputation path.

### Impact Explanation
The extra division step introduces additional floating-point rounding versus doing the math as one combined division (or with integer/`BigInteger` arithmetic). Per-vote drift accumulates across the account's SR vote list on every partial-unfreeze event, systematically under- or over-counting an account's remaining voting power (and thus SR vote totals used for standby-witness reward distribution in `IncentiveManager.reward` and the reward-per-vote `Vi` accounting in `DelegationStore`/`RewardViCalService`). This is a rounding/precision correctness bug in stake-vote accounting rather than a fund-theft primitive by itself, so its severity is bounded (matches the source finding's own Medium rating), but it degrades the fairness/accuracy of vote-weighted reward math network-wide.

### Likelihood Explanation
Every account that partially unfreezes TRX2 while its remaining Tron Power falls below its total cast votes hits this code path unconditionally — this requires no special privilege, just a normal `UnfreezeBalanceV2Contract` transaction or the TVM native `unfreezeBalanceV2` call, making the erroneous computation trivially and repeatedly reachable.

### Recommendation
Replace the two-division `double` computation with a single division, ideally computed using integer/`BigInteger` arithmetic to avoid floating point entirely:
```java
long newVoteCount = Math.multiplyHigh(...) // or BigInteger-based
    vote.getVoteCount() * ownedTronPower / (totalVote * TRX_PRECISION);
```
guarding against overflow (e.g., via `BigInteger` or `Math.multiplyExact`/`Math.floorDiv` with widened intermediate types), consistent with how `MortgageService`/`VoteRewardUtil` already use `BigInteger` for the Vi-based reward math elsewhere in the codebase.

### Proof of Concept
1. Freeze TRX2 and cast votes for several SRs such that `totalVote * TRX_PRECISION` and `ownedTronPower` are not exact multiples of each other (e.g., pick vote counts/tron-power values that don't divide evenly).
2. Submit an `UnfreezeBalanceV2Contract` transaction that reduces `ownedTronPower` below `totalVote * TRX_PRECISION`, triggering `updateVote()`.
3. Compare the resulting `newVoteCount` values against the mathematically exact single-division result `(vote.getVoteCount() * ownedTronPower) / (totalVote * TRX_PRECISION)`; observe a discrepancy caused by the intermediate rounding of the two chained divisions in [2](#0-1) .
