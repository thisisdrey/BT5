### Title
Unbounded reference-update loop in `RefService.UpdateReferences` enables resource-exhaustion DoS - ([File: internal/gitaly/service/ref/update_references.go])

### Summary
The `UpdateReferences` RPC handler accepts a client-controlled, unbounded stream of reference-update batches and feeds every single update into a long-lived `git update-ref --stdin` process without any cap on the total number of updates, the number of streamed messages, or the size of the underlying update-ref transaction. A client can keep the stream open indefinitely (or send an extremely large number of `Updates` entries across many messages), forcing Gitaly to hold the transaction open, keep the `git-update-ref` subprocess/pipe alive, and buffer state for an unbounded number of reference operations before any batching, quota, or count check is applied.

### Finding Description
`server.UpdateReferences` reads its first request, builds an `updateref.Updater` (a wrapper around `git update-ref --stdin`), and then enters an unbounded `for { ... }` loop that keeps calling `server.Recv()` and, for every message received, iterates `request.GetUpdates()` and calls `updater.Update()` for each entry: [1](#0-0) 

There is no limit on:
- the number of streamed request messages the loop will process (`for { ...; request, err = server.Recv() }` only terminates on `io.EOF` or an error),
- the number of `Update` entries per message, or
- the cumulative number of `Update` entries across the whole RPC call.

Each accepted update is written synchronously into the pipe of a single `git update-ref --stdin` process via `Updater.Update` → `Updater.write`: [2](#0-1) [3](#0-2) 

Because the entire batch of updates is staged in one reference transaction and only applied via a single `Commit()` at the very end of the stream, Gitaly must keep the `git-update-ref` process, its stdin/stdout pipes, and the transaction's lock state active for the full duration of however many updates (and however long) the client chooses to send. The RPC is a client-streaming RPC (`stream UpdateReferencesRequest`), so it is not bounded by gRPC's single-message size limit the way unary RPCs are — a client can keep sending additional small messages forever.

This matches the reported bug class ("unbounded loops can lead to out-of-gas/DoS errors") mapped onto Gitaly's RPC-handler resource limits: an ordinary authenticated client issuing a crafted `UpdateReferences` stream (a legitimate, unprivileged Gitaly RPC used for atomic reference updates) can drive unbounded loop iterations and unbounded subprocess/pipe resource usage server-side.

### Impact Explanation
An attacker with the ability to call `UpdateReferences` (the same trust level needed to push/write references) can:
- keep a `git-update-ref --stdin` process and its associated file-locking state open indefinitely by continuously streaming small update batches,
- force Gitaly to buffer an unbounded number of pending reference operations in a single transaction, consuming worker goroutine time, memory, and file-descriptor/pipe resources,
- potentially hold reference locks (via `Prepare`) for an extended period, degrading concurrent operations for the same repository or worker exhaustion for the Gitaly node.

This is a Medium-severity availability issue: it degrades or denies service for the affected repository/storage but does not directly cause data corruption or leak data, and requires an actor already authorized to mutate references in the target repository.

### Likelihood Explanation
Likelihood is Medium: it requires being an authenticated client capable of invoking `RefService.UpdateReferences` (a MUTATOR RPC gated the same way as other write RPCs, e.g. `git push`), but no exploit beyond simply keeping the client stream open with a large or endless sequence of update messages is needed — no race, no privilege escalation, no special timing is required.

### Recommendation
- Enforce a maximum number of `Updates` entries processed per `UpdateReferences` call (across the whole stream, not just per message), rejecting the RPC once the limit is exceeded.
- Enforce a maximum number of streamed messages and/or an overall deadline/idle-timeout for receiving subsequent messages in the loop.
- Consider chunking large update sets into multiple bounded transactions rather than a single unbounded `git-update-ref --stdin` session, mirroring the "stream unbounded or oversized payloads" guidance already used elsewhere in Gitaly's RPC design conventions.

### Proof of Concept
1. Open a client-streaming call to `RefService.UpdateReferences` against a repository the attacker can write to.
2. Send the initial `UpdateReferencesRequest` with `Repository` set and one valid `Update`.
3. Continue sending additional `UpdateReferencesRequest` messages, each with one or more `Update` entries (or a large `Updates` array), without ever closing the stream.
4. Observe that Gitaly's `UpdateReferences` handler loop [4](#0-3)  keeps accepting and queuing updates indefinitely, keeping the underlying `git update-ref --stdin` process and its transaction state alive, consuming server resources for as long as the attacker keeps streaming.

func (u *Updater) Update(reference git.ReferenceName, newOID, oldOID git.ObjectID) error {
	if err := u.expectState(stateStarted); err != nil {
		return err
	}

	return u.write("update %s\x00%s\x00%s\x00", reference.String(), newOID, oldOID)
}
