### Title
Dust self-liquidation front-run permanently DoSes liquidation of a marginal position, blocking bad-debt socialization - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`liquidate()` in the Market contract gates all liquidation attempts behind a single health check `(asserts! (>= current-ltv ltv-liq-partial) ERR-HEALTHY)`. Any unprivileged principal — including the borrower themselves acting as their own liquidator — can submit a tiny ("dust") liquidation that nudges a marginally-liquidatable position's LTV just below `ltv-liq-partial`, causing this health check to revert for any subsequent, legitimate liquidator's transaction that same block (or any time the position again creeps to the margin). This mirrors the Inverse Finance `forceReplenish` front-run: a cheap dust transaction placed ahead of the real one flips a threshold check and reverts the victim's call.

### Finding Description
In `liquidate()`, the LTV used for eligibility is: [1](#0-0) 

Because liquidation always seizes collateral valued at `debt-repaid * (1 + liq-penalty)`, removing debt/collateral in that ratio strictly decreases LTV — proportionally to the size of the liquidation, but this holds even for the smallest non-zero amount permitted by the contract. The function only requires the resulting amounts to be non-zero: [2](#0-1) 

There is no minimum-liquidation-size floor and no restriction preventing `contract-caller` (the liquidator) from being the `borrower` themselves. Consequently, for a position sitting exactly at or just barely above `ltv-liq-partial` (a state that occurs naturally as oracle prices and interest accrual move a position across the threshold), a 1-unit-scale self-liquidation is enough — due to integer/BPS rounding in `mul-div-down total-debt-usd BPS total-collateral-usd` — to push `current-ltv` strictly below `ltv-liq-partial`. Any legitimate liquidator's transaction ordered afterward then hits `ERR-HEALTHY` and reverts entirely, regardless of the `debt-amount` they requested (unlike a slippage-only failure, this is a hard block on the whole liquidation, not just amount adjustment).

The batch entry point `liquidate-multi` does soften this for the *rest of a batch* (failures for one position don't revert others), but for a specific targeted position within (or outside) the batch, the individual health check is unaffected — the targeted borrower's dust self-liquidation still blocks that position's liquidation attempt: [3](#0-2) 

### Impact Explanation
A borrower whose position is marginally underwater can repeatedly front-run any liquidator by self-liquidating a dust amount just before a real liquidator's transaction lands, or immediately whenever the LTV creeps back to the threshold. This indefinitely delays recovery of the vault's owed assets and bad-debt socialization for that position, which is a temporary freezing of protocol/lender funds — the position remains under-margined and non-liquidatable for as long as the attacker can keep front-running, extending the window during which the market's stated collateralization is inaccurate and lender funds tied to that debt remain at risk.

### Likelihood Explanation
Likelihood is limited to positions sitting exactly at the liquidation boundary (a narrow but recurring window given price/interest drift), and requires the attacker to win transaction ordering (achievable via fee bumping / same-block ordering) each time a liquidation attempt is made. It is a low-cost, repeatable griefing action funded by the position owner's own capital (they receive the seized collateral back to themselves), making it economically cheap relative to the disruption caused.

### Recommendation
Add a minimum liquidation-size threshold (in USD-normalized terms) below which `liquidate()` reverts, so dust liquidations cannot be used to flip the health check by rounding. Alternatively/additionally, disallow `contract-caller == borrower` in `liquidate()`, and/or recompute liquidation eligibility using a tolerance/hysteresis band so a single small liquidation cannot flip a position from liquidatable to healthy near the boundary.

### Proof of Concept
1. Borrower's position reaches `current-ltv == ltv-liq-partial` (or 1 bps above) due to interest accrual or a price tick.
2. A liquidator broadcasts `liquidate(borrower, ..., debt-amount=X, min-collateral-expected=Y)` intending a real liquidation.
3. Borrower (or colluding party) front-runs with `liquidate(borrower, collateral-ft, debt-ft, debt-amount=1, min-collateral-expected=0, none, none)` — this succeeds because `debt-to-repay > 0` and `coll-final > 0` are the only size constraints (mainnet/contracts/market/v0-4-market.clar:1488-1493), and it lowers `current-ltv` by the rounding-driven decrement in `mul-div-down total-debt-usd BPS total-collateral-usd`.
4. The real liquidator's transaction now evaluates `current-ltv < ltv-liq-partial` and reverts with `ERR-HEALTHY` (mainnet/contracts/market/v0-4-market.clar:1433-1435), regardless of the amount they requested.
5. Repeat step 3 whenever the position again approaches the threshold to indefinitely stall genuine liquidation of this borrower.
