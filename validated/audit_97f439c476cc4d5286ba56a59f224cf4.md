### Title
Attacker can fill a victim's per-account token list to `MAX_TOKENS_PER_USER` via dust deposits/transfers, blocking the victim from using new collateral or receiving deposit tokens - ([File: contracts/Pool.sol])

### Summary
The external report describes a fixed-size buffer being overflowed by attacker-influenced data. The closest analog in Metronome is the per-account token lists `depositTokensOfAccount` / `debtTokensOfAccount`, which are hard-capped at `MAX_TOKENS_PER_USER = 30` and guarded by `onlyIfAdditionWillNotReachMaxTokens`, which reverts with `UserReachedMaxTokens` once the combined list length reaches 30 [1](#0-0) [2](#0-1) . Entries are added as a side effect of `DepositToken._mint`/`_transfer` whenever the recipient's balance goes from 0 to >0 [3](#0-2) [4](#0-3) , and anyone can push entries onto an arbitrary victim's list through the public `deposit(amount_, onBehalfOf_)` or `transfer(to_, amount_)` entry points [5](#0-4) .

### Finding Description
`Pool.addToDepositTokensOfAccount` and `Pool.addToDebtTokensOfAccount` are callable only by registered DepositToken/DebtToken contracts, but those contracts call them on behalf of *any* recipient when the recipient's balance crosses from zero [6](#0-5) . An unprivileged attacker can therefore:

1. Call `DepositToken.deposit(1 wei, victim)` (or `depositToken.transfer(victim, 1)`) for every registered deposit token in the pool.
2. Each call appends that token to `depositTokensOfAccount[victim]` via `_mint`/`_transfer` → `pool.addToDepositTokensOfAccount` [7](#0-6) .
3. Once `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30`, every subsequent attempt to add a *new* token type to the victim's account reverts with `UserReachedMaxTokens` [2](#0-1) .

Because the check runs inside the token's `_mint`/`_transfer`, the revert poisons the entire surrounding call: the victim can no longer `deposit()` into a collateral type they don't already hold, cannot `issue()` a synthetic whose debt token they don't already hold (the mint of the debt position adds a debt-token entry), cannot receive `transfer`/`transferFrom` of any new msdTOKEN, and cannot be the `onBehalfOf_` beneficiary of someone else's deposit in a new token. Withdrawals, repayments, and transfers of already-held tokens still work (removal on balance→0 is not capped) [8](#0-7) , but the victim's ability to add new collateral — the primary lever for restoring a degraded position — is blocked.

The victim can clear slots by transferring each dust balance in full (balance→0 triggers `removeFromDepositTokensOfAccount`), but the attacker can re-fill the slot in the same block or persistently re-dust, since each refill costs only a token's smallest unit plus gas. Debt-token slots cannot be pushed onto a victim directly (`issue` mints debt to `_msgSender` [9](#0-8) ), so the attack is limited to the deposit-token side of the cap — still sufficient, since the cap is on the combined sum and up to 30 deposit tokens can be registered per pool [10](#0-9) .

### Impact Explanation
Temporary freezing of funds / forced position degradation: a victim whose collateral ratio is deteriorating and who needs to deposit a *new* collateral type (the only one they hold, or the only one with liquidity) is unable to do so and becomes liquidatable. It also permanently blocks unsolicited msdTOKEN transfers to the victim and SmartFarmingManager leverage flows that would mint a new deposit-token position to the user. The attack requires no privileged role — only public `deposit`/`transfer` entry points — and its cost scales with the number of registered deposit tokens (bounded by `MAX_TOKENS_PER_USER` via `addDepositToken` [11](#0-10) ).

### Likelihood Explanation
Reachable by any EOA with dust amounts of each underlying collateral; no governance, keeper, oracle, or bridge assumptions needed. The main mitigant is that the victim can evict entries by zeroing balances, making this a renewable griefing vector rather than a permanent lock, and impact depends on the victim needing a token type they don't already hold (e.g., emergency collateral top-up during a drawdown, or receiving msdTOKEN payments).

### Recommendation
- Do not let third parties grow a user's list: gate `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` so entries are only added when the recipient initiated the action (e.g., only on `deposit` where `onBehalfOf_ == _msgSender()` or an explicit opt-in), or only add on actions that also confer collateral value.
- Alternatively, treat dust thresholds: only register a token in the per-account list when the credited amount exceeds a minimum, or silently skip the set-add (or skip the revert) when the cap is reached so the cap degrades accounting rather than DoS-ing the mint/transfer.
- As a defense-in-depth, allow users to purge arbitrary entries from their own lists via a public `removeFromDepositTokensOfAccount`-style self-service call.

### Proof of Concept
Hardhat sketch against deployed contracts (mainnet fork):

```ts
// Victim starts with an empty (or partially filled) token list.
const depositTokens: DepositToken[] = await pool.getDepositTokens(); // up to 30

for (const dt of depositTokens) {
  const underlying = await ethers.getContractAt('IERC20', await dt.underlying());
  // Attacker acquires dust of each underlying (or already holds msdTOKEN).
  await underlying.approve(dt.address, 1);
  // Pushes `dt` onto depositTokensOfAccount[victim]; costs 1 wei of collateral.
  await dt.deposit(1, victim.address);
  // Equivalently: await dt.transfer(victim.address, 1);
}

expect(await pool.getDepositTokensOfAccount(victim.address)).to.have.lengthOf(30);

// Victim can no longer onboard a new collateral type:
const newDepositToken = /* any registered DepositToken victim does not hold */;
await expect(
  newDepositToken.connect(victim).deposit(amount, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// Nor receive a transfer of a new msdTOKEN:
await expect(
  msdOther.connect(attacker).transfer(victim.address, 1)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// Victim can evict an entry by fully transferring the dust,
// but attacker re-adds it in the next block for ~1 wei + gas.
await msdTokenA.connect(victim).transfer(attacker.address, dustBalance);
await msdTokenA.connect(attacker).transfer(victim.address, 1); // re-fills the slot
```

Uncertainty noted: I did not fully enumerate `DebtToken` mint paths beyond `issue`/`flashIssue` to confirm no other public route adds debt-token entries to an arbitrary account; `issue` mints to `_msgSender()` and `flashIssue` is SmartFarmingManager-gated, so the debt side does not appear attacker-pushable, which caps the griefing at the deposit-token portion of the shared limit.
