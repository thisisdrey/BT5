### Title
Market order matching truncates maker's fill amount, allowing a taker to systematically extract value from counterparty orders - (File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java)

### Summary
`MarketSellAssetActuator.matchSingleOrder` computes the token amount a maker receives using integer division (`MarketUtils.multiplyAndDivide`, which performs `floorDiv`). In the "taker == maker" branch, the taker is credited the maker's *full* remaining sell quantity while the maker is credited only the floor-rounded payment amount. Because Solidity/Java integer division always truncates toward zero, this rounding systematically favors the taker on every trade that hits this exact-match branch, letting an unprivileged order placer extract a small amount of value from every counterparty order over repeated trades — the same rounding-favors-one-side pattern as the reported "Fees are wrongly calculated" issue (fee = `value/100` truncating to the detriment of one party).

### Finding Description
In `matchSingleOrder`, when the taker's computed buy-remain exactly equals the maker's sell-remain ("taker == maker" case): [1](#0-0) 

```
makerBuyTokenQuantityReceive = MarketUtils
    .multiplyAndDivide(makerSellRemainQuantity, makerBuyQuantity, makerSellQuantity, ...);
takerBuyTokenQuantityReceive = makerOrderCapsule.getSellTokenQuantityRemain();

long takerSellTokenLeft =
    takerOrderCapsule.getSellTokenQuantityRemain() - makerBuyTokenQuantityReceive;
```

`MarketUtils.multiplyAndDivide` truncates the multiplication result via `floorDiv`: [2](#0-1) 

The taker receives the maker's *entire remaining sell quantity* (`takerBuyTokenQuantityReceive = makerOrderCapsule.getSellTokenQuantityRemain()`), while the maker's order is marked fully filled (`makerOrderCapsule.setSellTokenQuantityRemain(0)`) even though the maker is only credited the floor-rounded (i.e., rounded-down) payment amount `makerBuyTokenQuantityReceive`. Since integer division always truncates toward zero, the maker is systematically paid less than the exact ratio implies for the full quantity it gave up, while the taker's own order retains the rounding remainder (`takerSellTokenLeft`) rather than surrendering it to the maker. This is structurally identical to the reported bug class: a per-trade division (`value/100` in the original report, `a*b/c` here) that truncates and always benefits one party (grant recipient / taker) at the expense of the other (admin / maker).

The same truncation pattern is reused for the "taker > maker" branch: [3](#0-2) 

### Impact Explanation
Any account calling `MarketSellAssetContract` (`MarketSellAssetActuator`) to place a sell order that exactly matches an existing maker order's remaining quantity triggers this branch. Because the rounding consistently favors the taker, a malicious actor can place many small orders sized to trigger the "taker == maker" exact-match path against resting orders, incrementally extracting fractional token value from maker liquidity across the order book. This is a concrete value-transfer/theft-of-funds vector reachable purely through the `MarketSellAssetContract` transaction type, matching the "theft of funds" impact criterion.

### Likelihood Explanation
Reaching this code path requires only submitting a signed `MarketSellAssetContract` transaction with quantities chosen so `takerBuyTokenQuantityRemain` exactly equals the maker order's `sellTokenQuantityRemain` — fully within the control of any unprivileged transaction broadcaster, and the order book state (existing maker orders/prices) is public and queryable, making the exact-match condition straightforward to engineer.

### Recommendation
Use `BigInteger`/exact arithmetic (or a documented rounding policy) so that when the maker's full remaining quantity is being consumed, the maker receives the precise proportional payment without floor truncation, or explicitly disallow/adjust the exact-match branch so leftover rounding dust is returned to (or charged against) the counterparty consistently rather than silently retained by the taker.

### Proof of Concept
1. Maker places a sell order: sell `makerSellQuantity` of token A for `makerBuyQuantity` of token B, where `makerBuyQuantity`/`makerSellQuantity` is not an integer ratio (e.g., sell 100 A for 3 B), leaving it resting in the order book.
2. Taker computes an order size such that `takerBuyTokenQuantityRemain == makerOrderCapsule.getSellTokenQuantityRemain()` (i.e., taker wants to fully consume the maker's remaining 100 A).
3. In `matchSingleOrder`, `makerBuyTokenQuantityReceive = floorDiv(100 * 3, 100) = 3` (exact in this example, but non-exact ratios such as sell 100 A for 7 B with `makerSellRemainQuantity=100` produce `floorDiv(100*7,100)=7`; craft `makerSellRemainQuantity` values, e.g. 33, with `makerBuyQuantity=10, makerSellQuantity=100` → `floorDiv(33*10,100)=3` instead of `3.3`), so the maker gets only 3 B for giving up 33 A worth 3.3 B.
4. The maker's order is closed (`sellTokenQuantityRemain=0`) as fully filled while under-compensated; the taker retains the 0.3 B-equivalent rounding remainder in `takerSellTokenLeft` rather than it being paid to the maker.
5. Repeating this against multiple resting orders lets a taker accumulate systematic rounding gains at maker expense.

  public static long multiplyAndDivide(long a, long b, long c, boolean disableMath) {
    try {
      long tmp = multiplyExact(a, b, disableMath);
      return floorDiv(tmp, c, disableMath);
    } catch (ArithmeticException ex) {
      // do nothing here, because we will use BigInteger to compute again
    }

    BigInteger aBig = BigInteger.valueOf(a);
    BigInteger bBig = BigInteger.valueOf(b);
    BigInteger cBig = BigInteger.valueOf(c);

    return aBig.multiply(bBig).divide(cBig).longValue();
  }
