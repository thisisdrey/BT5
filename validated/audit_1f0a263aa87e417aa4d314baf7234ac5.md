### Title
Any exception in per-block JSON-RPC/event-subscribe trigger processing crashes the entire node via `TronError` - (File: `framework/src/main/java/org/tron/core/db/Manager.java`)

### Summary
`Manager.blockTrigger()` wraps all post-block-application notification work (JSON-RPC block/log filters, event-subscribe block/transaction/contract triggers) in a single `try { ... } catch (Exception e) { throw new TronError(e, TronError.ErrCode.EVENT_SUBSCRIBE_ERROR); }`. Any `TronError` reaching the JVM's default uncaught-exception handler triggers `System.exit`, so a single uncaught `Exception` anywhere in this call chain — which processes transaction-derived data from every applied block — kills the whole node process, analogous to the Apache Subversion CVE-2018-11782 pattern where a well-formed request causes the server process to exit.

### Finding Description
`blockTrigger` is invoked from block application/`pushBlock` for every block the node applies, including blocks containing transactions broadcast by any unprivileged account (transfers, TRC10 operations, smart-contract deployment/invocation, etc.): [1](#0-0) 

```
void blockTrigger(final BlockCapsule block, long oldSolid, long newSolid) {
  try {
    if (CommonParameter.getInstance().isJsonRpcHttpFullNodeEnable()) {
      postBlockFilter(block, false);
      postLogsFilter(block, false, false);
    }
    if (CommonParameter.getInstance().isJsonRpcHttpSolidityNodeEnable()) {
      postSolidityFilter(oldSolid, newSolid);
    }
    ...
    postBlockTrigger(block, false);
    postSolidityTrigger(newSolid);
  } catch (Exception e) {
    logger.error("Block trigger failed. ...", e);
    throw new TronError(e, TronError.ErrCode.EVENT_SUBSCRIBE_ERROR);
  }
}
```

`TronError` is documented and enforced as a fatal, unrecoverable signal that must never be caught, and the framework's global uncaught-exception handler unconditionally calls `System.exit` whenever a `TronError` (or any `Throwable` whose cause chain contains one) surfaces: [2](#0-1) [3](#0-2) 

Inside the `try` block, `postBlockTrigger`/`postSolidityTrigger` eventually call `processTransactionTrigger`, which walks every transaction and its `TransactionInfo` in the block (log counts, energy usage, per-transaction/contract-log/event triggers derived directly from transaction execution results): [4](#0-3) 

This is transaction-content-driven processing (block number, tx count/order mismatches, log counts, cumulative energy, contract log/event trigger construction) executed on the main block-application path for *every* block, without the kind of isolating `catch (Throwable)` that other trigger paths deliberately use. For comparison, the sibling per-transaction contract-trigger dispatch path (`postContractTrigger`) was hardened specifically because it can throw an NPE on crafted/edge-case log data, and its fix was to add a catch-all so a single bad trigger doesn't propagate: [5](#0-4) 

`blockTrigger`, however, has no such isolation for the other calls in its chain (`postBlockFilter`, `postLogsFilter`, `postSolidityFilter`, `postBlockTrigger`'s eth-compatible size-mismatch branch, `postSolidityTrigger`'s solidity log/event contract-trigger loops). Any unexpected `RuntimeException` (NPE, index-out-of-bounds, cast exception, etc.) surfacing from any of these — for example from malformed/edge-case `TransactionInfo`/log data produced by a crafted smart-contract call, or from a race/edge condition in the filter/trigger maps — is caught only by the outer `catch (Exception e)` and unconditionally converted into a fatal `TronError`, which shuts the whole node down.

### Impact Explanation
This turns any latent bug in the JSON-RPC event/log/filter posting pipeline — code that is directly driven by transaction execution results and thus reachable by any unprivileged transaction broadcaster or contract deployer — into a full node crash (denial of service against block production/serving), matching the "node crash or halt" impact accepted by the rules. Because the check runs on the normal block-application path (not an isolated worker), a witness node hitting this would also stop producing/relaying blocks, and any full/solidity node with JSON-RPC or event-subscribe enabled would go down when it applies the offending block — i.e., every node on the network that processes that block, not just the originating node.

### Likelihood Explanation
The exact trigger requires a specific edge case (a `RuntimeException`) inside one of the un-isolated calls in the chain (e.g., a size mismatch/format issue between `TransactionInfoList` and the block's transaction list feeding array/index access, or a null log/topic field reaching an unguarded getter). The general design flaw — "catch all exceptions in per-block trigger posting and turn them into `System.exit`" — is proven directly by the source; whether a concrete reachable exception currently exists in each sub-call could not be exhaustively confirmed within the scope of this analysis (only the sibling `postContractTrigger` path was confirmed to have needed exactly this kind of hardening, evidenced by its dedicated test). Likelihood is assessed as Medium given the fragile blanket-fatal error handling combined with transaction-derived inputs feeding it on every applied block.

### Recommendation
- Do not convert generic `Exception` from `blockTrigger`'s notification/filter-posting logic into a fatal `TronError`/`System.exit`. Reserve `TronError` for genuinely unrecoverable states (as in DB/storage errors), and instead log-and-drop (as already done, e.g., in `postContractTrigger`) for optional event-subscribe/JSON-RPC notification failures, since losing a filter/trigger event is far less severe than crashing the whole node.
- Add defensive `catch (Throwable)` isolation around each independent notification step (`postBlockFilter`, `postLogsFilter`, `postSolidityFilter`, `postBlockTrigger`, `postSolidityTrigger` and its sub-loops) so a failure in one does not abort the others or crash the process.
- Audit `processTransactionTrigger`/`postTransactionTrigger` and the solidity log/event contract-trigger loops for unguarded field access on transaction/log data that ultimately derives from user-submitted transactions.

### Proof of Concept
A fully weaponized PoC (a concrete transaction/log payload that deterministically throws inside `postBlockFilter`/`postLogsFilter`/`postSolidityTrigger`) could not be constructed with the available read-only code search; this requires deeper tracing of `LogsFilterCapsule`, `BlockFilterCapsule`, and the solidity trigger maps' construction under adversarial transaction content (e.g., blocks with logs/receipts that desynchronize `TransactionInfoList` size from `transactionCapsuleList`, or malformed contract event data), which is best explored by a Devin session with the ability to run the node/tests locally and fuzz these code paths. The architectural flaw itself — that `blockTrigger` promotes any `Exception` from this transaction-driven pipeline to a fatal, process-terminating `TronError` — is directly demonstrated by the cited code.

  public static void initExceptionHandler() {
    Thread.setDefaultUncaughtExceptionHandler((t, e) -> {
      findTronError(e).ifPresent(ExitManager::logAndExit);
      logger.error("Uncaught exception", e);
    });
  }

  public static Optional<TronError> findTronError(Throwable e) {
    if (e == null) {
      return Optional.empty();
    }

    Set<Throwable> seen = new HashSet<>();

    while (e != null && !seen.contains(e)) {
      if (e instanceof TronError) {
        return Optional.of((TronError) e);
      }
      seen.add(e);
      e = e.getCause();
    }
    return Optional.empty();
  }

  public static void logAndExit(TronError exit) {
    final int code = exit.getErrCode().getCode();
    logger.error("Shutting down with code: {}, reason: {}", exit.getErrCode(), exit.getMessage());
    Thread exitThread = exitThreadFactory.newThread(() -> System.exit(code));
    exitThread.start();
  }
