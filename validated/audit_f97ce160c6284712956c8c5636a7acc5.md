### Title
Cross-StackerDB chunk replay due to unbound `contract_id` in `SlotMetadata::auth_digest` - ([File: libstackerdb/src/libstackerdb.rs], [File: stackslib/src/net/stackerdb/mod.rs])

### Summary
`SlotMetadata::auth_digest` signs only `(slot_id, slot_version, data_hash)` and never the StackerDB `contract_id`. `PeerNetwork::validate_received_chunk` and `StackerDBTx::try_replace_chunk` verify a chunk's signature against the slot owner resolved from the *claimed* `contract_id` in the incoming `StackerDBPushChunkData`/`StackerDBChunkData`, but nothing ties the signature itself to that contract. A chunk that was validly signed by an address for slot `N` in StackerDB contract A can be relabeled with a different `contract_id` (B) and replayed, and it will pass every check in `validate_received_chunk` as long as the same address also owns slot `N` in B.

### Finding Description
`SlotMetadata::auth_digest` (`libstackerdb/src/libstackerdb.rs:160-166`) computes:
```
hasher.update(self.slot_id.to_be_bytes());
hasher.update(self.slot_version.to_be_bytes());
hasher.update(self.data_hash.0);
``` [1](#0-0) 

There is no `contract_id` field in this digest. `StackerDBChunkData::sign`/`verify` (`libstackerdb/src/libstackerdb.rs:213-244`) reduce to the same digest via `get_slot_metadata()`. [2](#0-1) 

On the receive path, `PeerNetwork::handle_unsolicited_StackerDBPushChunk` (`stackslib/src/net/stackerdb/mod.rs:742-871`) takes `chunk_data.contract_id` from the wire message, looks up `stackerdb_config` for *that* contract, and calls `validate_received_chunk(&chunk_data.contract_id, stackerdb_config, &chunk_data.chunk_data, ...)`. [3](#0-2) 

Inside `validate_received_chunk` (`stackslib/src/net/stackerdb/mod.rs:649-718`), the signer address is resolved via `self.stackerdbs.get_slot_signer(smart_contract_id, data.slot_id)` — i.e. keyed by the *claimed* `contract_id` — and then `slot_metadata.verify(&addr)` is checked against `data.get_slot_metadata()`, whose `auth_digest` never included `contract_id`. [4](#0-3) 

The same pattern exists in the storage path, `StackerDBTx::try_replace_chunk` (`stackslib/src/net/stackerdb/db.rs:400-438`), which resolves `slot_validation.signer` from `smart_contract` and slot id, then calls `slot_desc.verify(&slot_validation.signer)` — again over a digest that omits `contract_id`. [5](#0-4) 

Exploit flow: address `S` is a legitimately registered slot owner of slot `N` in StackerDB contract A (e.g. `signers-0-1` for one reward cycle) and also happens to be the owner of slot `N` in StackerDB contract B (e.g. `signers-1-1` for another reward cycle, or any other configured StackerDB where the signer-set ordering assigns `S` the same slot index — a realistic occurrence given that ordering is derived from `stackerdb-get-signer-slots-page` per reward cycle and often preserves relative signer ordering). Any signed chunk `S` broadcasts for slot `N` in A (observable by any unprivileged peer via ordinary P2P gossip or the public "get chunk" API) can be repackaged by the attacker as a `StackerDBPushChunkData` with `contract_id = B`, `chunk_data` unchanged. `validate_received_chunk` will resolve the slot signer for B (same address `S`), verify the (contract-agnostic) signature successfully, check `data.slot_version >= expected_version` (trivially true for a fresh/early version in B) and `<= max_writes`, and accept it — causing the payload authored for A's context to be written into B's StackerDB slot without `S`'s intent or the attacker's own key.

Existing guards that do NOT close this gap: the chunk-size cap, the version staleness/max-writes checks, and the `rc_consensus_hash`/tip-freshness gate in `make_StackerDBChunksInv_or_Nack` all operate independently of contract binding and do not verify that the signature was scoped to the specific `contract_id` being written.

### Impact Explanation
This is an unauthenticated/unauthorized write into a StackerDB slot: content the true key holder never authorized for that specific contract gets stored and propagated as if it were current, addressed content for a different StackerDB (e.g. a different reward cycle's signer-message DB, or any two configured StackerDBs sharing a slot-owning address). Because pushed chunks get relayed/gossiped further (`stacker_db_sync.wakeup()`, chunk inv patch, `add_relay_handle` in `handle_unsolicited_StackerDBPushChunk`), the forged cross-contract chunk can propagate network-wide, matching the "unauthenticated/unauthorized write to state or StackerDB" Critical category. Repeatable per replay, at zero incremental attacker cost beyond observing one legitimately signed chunk.

### Likelihood Explanation
Requires: (1) attacker can observe/relay one validly signed `StackerDBChunkData` (trivial — StackerDB chunks are gossiped in the clear over P2P and are also servable via the public GET-chunk RPC), and (2) the same signer address holds the same `slot_id` in at least two separately configured StackerDBs the node replicates. Precondition (2) is plausible in the current Stacks signer-set design, where each reward cycle's `signers-N-1` StackerDB independently derives slot ordering from `stackerdb-get-signer-slots-page`, and consecutive/adjacent reward cycles frequently retain overlapping signer sets in similar relative order — so identical `(address, slot_id)` pairs across two contracts are not a rare coincidence. No node secret, admin role, or physical access is required; the attacker only needs ordinary P2P connectivity.

### Recommendation
Bind `contract_id` (the `QualifiedContractIdentifier`) into `SlotMetadata::auth_digest` so that signatures are scoped per-StackerDB, e.g. hash `contract_id.to_string().as_bytes()` (or its serialized form) in addition to `slot_id`, `slot_version`, and `data_hash`, and thread the target contract into `sign`/`verify`/`recover_pk`. Update all callers (`StackerDBChunkData::sign/verify`, `validate_received_chunk`, `try_replace_chunk`, and the RPC POST-chunk handler) to pass the contract for both signing and verification, and add a migration/versioning note since this changes the wire-signed payload semantics.

### Proof of Concept
Rust test plan (in `stackslib/src/net/stackerdb/tests` or `libstackerdb/src/tests`):
1. Create two `StackerDBConfig`s / contracts A and B, each granting slot `0` to the same `StacksAddress` derived from private key `pk`.
2. Build `chunk = StackerDBChunkData::new(0, 1, data)`; `chunk.sign(&pk)`.
3. Call `network.validate_received_chunk(&contract_a, &config_a, &chunk, &expected_versions_a)` → expect `Ok(true)`.
4. Without re-signing, call `network.validate_received_chunk(&contract_b, &config_b, &chunk, &expected_versions_b)` → assert it also returns `Ok(true)`, proving the same signature validates for a different `contract_id`.
5. Additionally exercise `handle_unsolicited_StackerDBPushChunk` by sending a `StackerDBPushChunkData { contract_id: contract_b.clone(), chunk_data: chunk.clone(), .. }` over a fake connection and assert the chunk is accepted/buffered for B, demonstrating the practical replay through the P2P handler.
6. The failing assertion location for the fix would be at `slot_metadata.verify(&addr)` in `stackslib/src/net/stackerdb/mod.rs:691` (and `slot_desc.verify(&slot_validation.signer)` in `stackslib/src/net/stackerdb/db.rs:418`) — after the fix, verification should fail once `contract_id` is included in the digest and the wrong contract is supplied.

    /// Create an owned SlotMetadata describing the metadata of this slot.
    pub fn get_slot_metadata(&self) -> SlotMetadata {
        SlotMetadata {
            slot_id: self.slot_id,
            slot_version: self.slot_version,
            data_hash: self.data_hash(),
            signature: self.sig.clone(),
        }
    }

    /// Sign this given chunk data message with the given private key.
    /// Sets self.signature to the signature.
    /// Fails if the underlying signing library fails.
    pub fn sign(&mut self, privk: &StacksPrivateKey) -> Result<(), Error> {
        let mut md = self.get_slot_metadata();
        md.sign(privk)?;
        self.sig = md.signature;
        Ok(())
    }

    pub fn recover_pk(&self) -> Result<StacksPublicKey, Error> {
        let digest = self.get_slot_metadata().auth_digest();
        StacksPublicKey::recover_to_pubkey_without_validating_low_s(digest.as_bytes(), &self.sig)
            .map_err(|ve| Error::VerifyingError(ve.to_string()))
    }

    /// Verify that this chunk was signed by the given
    /// public key hash (`addr`).  Only fails if the underlying signing library fails.
    pub fn verify(&self, addr: &StacksAddress) -> Result<bool, Error> {
        let md = self.get_slot_metadata();
        md.verify(addr)
    }
