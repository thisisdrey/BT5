### Title
Gas-key nonce replay via DeleteKey + AddKey reset — nonce_index rollback enables re-execution of an already-charged FunctionCall - (File: runtime/runtime/src/access_keys.rs)

### Summary
`add_gas_key` unconditionally reseeds every `gas_key_nonce[i]` to `initial_nonce_value(block_height) = (block_height-1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` whenever a gas key is (re)created, with no memory of the highest nonce ever consumed by that public key. Because `delete_gas_key` fully erases the per-index nonce rows (and only burns the residual balance), an account owner can delete and immediately re-add the same gas-key public key in the same block, resetting a previously-consumed high nonce back below a value it has already signed, letting that already-executed `FunctionCall` transaction be replayed.

### Finding Description
`add_gas_key` (runtime/runtime/src/access_keys.rs:194-228) sets, for every nonce index `i` in `0..num_nonces`: [1](#0-0) 
```
let num_nonces = gas_key_info.num_nonces;
let nonce = initial_nonce_value(block_height);
for i in 0..num_nonces {
    set_gas_key_nonce(state_update, account_id.clone(), public_key.clone(), i, nonce);
}
```
using only the *current* block height, with no check against any nonce previously used by this exact public key. `delete_gas_key` (runtime/runtime/src/access_keys.rs:93-134) removes all `gas_key_nonce` rows entirely via `remove_gas_key_nonce` and burns any remaining balance, but this leaves no trace of the maximum nonce that was historically accepted for `nonce_index=0`: [2](#0-1) 

`action_add_key` (runtime/runtime/src/access_keys.rs:149-192) only rejects re-adding a public key that *currently* exists (`AddKeyAlreadyExists`); it does not prevent re-adding a key that was just deleted in the same or a prior action within the same transaction/block: [3](#0-2) 

Exploit flow:
1. Attacker funds their own gas key via `TransferToGasKeyAction` (`action_transfer_to_gas_key`, runtime/runtime/src/access_keys.rs:257-288).
2. Attacker submits a `FunctionCall` transaction authorized by that gas key, using `nonce_index=0` with a nonce close to whatever upper bound `verify_and_charge_gas_key_tx_ephemeral` (runtime/runtime/src/verifier.rs:370) permits for the current block height. That transaction executes and the runtime persists this high nonce into `gas_key_nonce[0]` as the new watermark.
3. In the same block, the attacker issues `DeleteKey` for the gas key public key — this burns the residual balance and calls `remove_gas_key_nonce` for every index, erasing the watermark entirely.
4. Immediately, the attacker issues `AddKey` re-adding the *same* public key as a gas key. `add_gas_key` reseeds `gas_key_nonce[0]` = `(H-1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER`, which is lower than the nonce consumed in step 2 (since that nonce was chosen near the current upper bound, which is derived from a range that extends beyond `(H-1)*MULTIPLIER`).
5. The attacker (or anyone who has the previously-signed transaction, e.g., a relayer that received it via a meta-transaction flow) resubmits the *exact same signed transaction* from step 2. Because the new stored nonce is now lower than the transaction's nonce, the nonce check in `verify_and_charge_gas_key_tx_ephemeral` passes again, and the `FunctionCall` executes a second time.

### Impact Explanation
This breaks the fundamental nonce-based replay-protection invariant for gas keys: a previously-executed, already-paid `FunctionCall` can be re-executed after a self-service delete/recreate of the gas key, at the cost of only the storage/gas for two extra actions (`DeleteKey`+`AddKey`). If the replayed `FunctionCall` performs a value-moving operation (e.g., a relayed token transfer, a refilled gas-key balance drain, or any state-changing call gated on "this authorization is used exactly once"), the attacker achieves double execution / double-spend of that authorized action — falling under NEAR's "double-spend/replay" and potential "theft of user funds" bounty categories, particularly for gas-station/relayer use cases where a single signed relay transaction is expected to be executable only once.

### Likelihood Explanation
- Preconditions are met purely by an ordinary funded account with a gas key that has `num_nonces >= 1`: no elevated privilege, validator, or node access required.
- All actions involved (`TransferToGasKey`, gas-key-authorized `FunctionCall`, `DeleteKey`, `AddKey`) are ordinary transaction actions available to any account.
- The attack is fully repeatable: the attacker can delete/recreate the same gas key indefinitely to roll back any nonce index whose watermark they wish to reset, as long as they still hold the original signed transaction to replay.
- The only cost is transaction/gas fees for the extra `DeleteKey`+`AddKey` pair, which is negligible compared to the value that could be extracted from a replay.

### Recommendation
Persist a per-(account, public_key) high-water-mark for nonces that survives key deletion (e.g., store it under a stable trie key not removed by `remove_gas_key_nonce`, or fold it into account-level state), and have `add_gas_key` initialize new nonces to `max(initial_nonce_value(block_height), previous_high_water_mark + 1)` instead of unconditionally resetting to `initial_nonce_value(block_height)`. Alternatively, disallow re-adding a public key that was ever used as an access key/gas key on that account (permanently reserve deleted public keys), mirroring protections already needed for regular access keys.

### Proof of Concept
Rust unit test plan (extending `runtime/runtime/src/access_keys.rs` tests and `runtime/runtime/src/verifier.rs` gas-key tests):
1. Create account, add gas key at block height `H0` via `add_gas_key_to_account`, fund it via `TransferToGasKeyAction`.
2. Build and sign a `FunctionCall` transaction using the gas key with `nonce_index=0` and a nonce close to the permitted upper bound for block height `H0` (derive from the same logic `verify_and_charge_gas_key_tx_ephemeral` uses to bound valid nonces).
3. Call `verify_and_charge_gas_key_tx_ephemeral` (or run it through `apply` in a test-loop) and assert the transaction succeeds; assert `get_gas_key_nonce(..., index=0)` now equals the used nonce.
4. Execute `action_delete_key` for the gas key public key at the same block height `H` (assert balance burn and nonce rows removed via `get_gas_key_nonce` returning `None`).
5. Execute `action_add_key` re-adding the same public key as a gas key at height `H`; assert `get_gas_key_nonce(..., index=0) == initial_nonce_value(H)` and that this value is `<` the nonce used in step 2.
6. Re-submit the *identical* signed transaction from step 2 to `verify_and_charge_gas_key_tx_ephemeral`; assert it is accepted again (no `InvalidNonce` error), proving the previously-consumed nonce/authorization is replayed.
