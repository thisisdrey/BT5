### Title
Unauthenticated-by-ownership `StopTransaction`/`VoteTransaction` RPC allows any caller holding the shared Praefect token to abort another user's in-flight push transaction via a guessable sequential transaction ID - (File: internal/praefect/service/transaction/server.go)

### Summary
`Manager.StopTransaction` and `Manager.VoteTransaction` in `internal/praefect/transactions/manager.go` act on any `transactionID` supplied in the request, with no check that the caller (`node`) is actually one of the registered voters for that transaction or is otherwise authorized to affect it.

### Finding Description
Praefect's `RefTransactionServer.StopTransaction` (`internal/praefect/service/transaction/server.go:63-77`) forwards the caller-supplied `TransactionId` directly to `Manager.StopTransaction` (`internal/praefect/transactions/manager.go:228-251`), which looks the transaction up by ID and immediately releases its repo lock and stops it — with no verification that the request actually originates from a legitimate voter/node participating in that transaction. Likewise, `VoteTransaction` (`internal/praefect/transactions/manager.go:181-225`) accepts an arbitrary `node` name and `transactionID`, and `mgr.voteTransaction` records votes against whatever transaction that ID maps to.

Transaction IDs are generated by a simple, predictable, monotonically-incrementing in-memory counter: [1](#0-0) 
This is the same class of flaw as the reported `removeUserFromOrderbook` issue: a state-mutating function that should only be callable by the specific, authorized actor tied to a given resource (there: only `Market`/`Treasury` for a given user's foreclosure; here: only the actual voting Gitaly node for a given transaction) is instead reachable by any caller who can reach the RPC and supply the resource identifier (there: `userHash`; here: `TransactionId`).

`RefTransactionServer` is registered on Praefect's main externally-reachable gRPC server alongside the normal repository RPCs, protected only by the coarse, shared `auth.UnaryServerInterceptor`/`auth.StreamServerInterceptor` (`internal/praefect/server.go:126-148, 213-232`) — the same authentication level used for ordinary push/fetch traffic — rather than any check scoping a caller to a specific transaction it owns.

### Impact Explanation
Because transaction IDs are sequential and predictable, and any request authenticated with the standard (shared) Praefect token can call `StopTransaction`/`VoteTransaction` for an arbitrary ID, an attacker with access to the Praefect RPC surface can enumerate the transaction IDs of other users' concurrent pushes and call `StopTransaction` to prematurely stop them, or inject `VoteTransaction` calls with fabricated `node`/vote data to disrupt quorum. This forces legitimate, unrelated pushes to fail (their reference-transaction hook receives `STOP`/`ABORT`), a denial-of-service against another user's write operation — analogous to Eve front-running Alice's foreclosure-preventing deposit to force her removal.

### Likelihood Explanation
Exploitation requires only knowledge/guessing of a sequential integer ID and network reachability of the Praefect RPC endpoint with the same credential level used for standard git operations; no special node compromise or protocol-level MITM is needed, since the check is missing at the application layer regardless of transport authentication.

### Recommendation
Bind `VoteTransaction`/`StopTransaction` authorization to the specific transaction: verify that the `node` value matches a voter actually registered for that `transactionID` (the `Voter` set is already tracked in `transaction` state), and reject calls from callers/nodes not part of the transaction's registered voter list, rather than trusting the client-supplied `node` and `transactionID` at face value.

### Proof of Concept
1. Praefect processes a legitimate push for repository A, calling `RegisterTransaction`, which yields transaction ID `N` (`internal/praefect/transactions/manager.go:94-119`).
2. An attacker with normal Praefect RPC access sends `StopTransaction{TransactionId: N}` (or `N+1`, `N+2`, ... by enumeration) before the legitimate voters finish, per `Server.StopTransaction` (`internal/praefect/service/transaction/server.go:63-77`).
3. `Manager.StopTransaction` releases the repo lock and stops the transaction for the victim's push without checking that the attacker is a participant (`internal/praefect/transactions/manager.go:228-251`), causing the victim's push to fail with `STOP`/`ABORT`.
