### Title
Disk Cache Poisoning via Unverified Digests on Cache Hit — ([File: CHANGELOG.md])

### Summary
Analogous to the `Multicall.click()` bug — where a value (`msg.value`) is trusted without validating it against the price actually computed at execution time — Bazel's disk cache (`--disk_cache`) no longer validates that content retrieved on a cache hit actually matches the digest that keys it in the Content Addressable Storage (CAS). The declared/expected value (the digest) is treated as authoritative without a corresponding integrity check against the real bytes, the same class of "declared vs. actual" validation gap.

### Finding Description
Bazel's release notes document an intentional behavior change: [1](#0-0)  "Bazel no longer verifies the digests of disk cache entries upon a cache hit. This honors the description but not the previous behavior of the `--remote_verify_downloads` flag, which in fact controlled digest verification for both remote and disk caches." Historically, `--remote_verify_downloads` (default `true`) caused Bazel to "compute the hash sum of all remote downloads and discard the ... cached values if they don't match the expected value" [2](#0-1) , and this same verification previously applied to disk cache reads too. After this change, a disk-cache hit is trusted purely by presence/CAS key lookup — the actual byte content is no longer re-hashed and compared to the digest that names it.

The disk cache is explicitly designed to be shared across workspaces/branches/checkouts on the same machine or CI fleet: [3](#0-2)  "Bazel can use a directory on the file system as a remote cache. This is useful for sharing build artifacts when switching branches and/or working on multiple workspaces of the same project ... This comes in handy when enabling the disk cache for all developers of a project via the project's checked in `.bazelrc` file." Bazel's own docs acknowledge the poisoning risk category exists for these caches: [4](#0-3)  "Create a clean cache after a cache was poisoned."

This is exactly the CI-shared-cache scenario permitted by the attacker model: an unprivileged outsider who can trigger a build on an untrusted branch that shares the same `--disk_cache` directory as trusted builds (a common CI acceleration setup) can populate CAS/AC entries under a digest of their choosing (or one that will be looked up by a future trusted build with the same action key/output digest), placing content that does not actually hash to the digest under which it is stored. Since digest verification is skipped on cache hit, a subsequent trusted build that retrieves this entry will silently accept and materialize the mismatched content as a real action output, without any check catching the discrepancy — mirroring how `Multicall.click()` accepted a `price` value without validating it against `msg.value`.

Existing test coverage confirms disk-cache hits are only checked for presence/action-key match, not content re-verification against the digest: [5](#0-4)  — the tests assert "disk cache hit" behavior functionally but do not assert that corrupted/mismatched blob content is rejected on disk cache retrieval, consistent with the documented removal of that check. Related recent commits reference disk-cache correctness edge cases, e.g. "Update GetActionResult for disk cache to check referenced files when …" [6](#0-5) , but this only checks file *existence*, not digest correctness of *content*.

### Impact Explanation
An attacker with the ability to write into a shared disk cache (e.g., via an untrusted CI branch build sharing `--disk_cache` with trusted branches, which the project's own docs recommend configuring project-wide) can poison the cache so that a subsequent trusted build silently consumes attacker-controlled bytes as a legitimate build output — a direct cache-poisoning-across-builds impact, without needing any preimage attack against the digest algorithm, because the digest is no longer checked against the retrieved content at all.

### Likelihood Explanation
Shared disk caches across branches/CI machines are an explicitly documented and encouraged Bazel configuration pattern. Any CI setup that shares a `--disk_cache` path between untrusted (e.g., fork/PR) branch builds and trusted (main) branch builds is directly exposed once this digest-verification-on-hit is disabled, which per the CHANGELOG is now default behavior in the corresponding release.

### Recommendation
Restore digest verification of disk cache content on cache hit (re-hash retrieved CAS blobs and compare against the digest key before use), independent of, or in addition to, whatever `--remote_verify_downloads` currently controls, so a "declared digest" is always validated against "actual bytes" the same way an `http_archive`'s declared `sha256`/`integrity` is validated against downloaded bytes.

### Proof of Concept
1. Configure two CI jobs (untrusted branch job A, trusted branch job B) sharing the same `--disk_cache=$SHARED_DIR`.
2. In job A (attacker-controlled branch), craft a genrule/action whose action key will collide with an action that job B will later run (e.g., same command/inputs relationship reproducible from public repo state), but have the local execution write attacker payload bytes to the output before it gets stored to `$SHARED_DIR`'s CAS under the digest that job B's real output would use, exploiting the lack of hash verification when the AC/CAS entry is written or subsequently read.
3. Run job B with `--disk_cache=$SHARED_DIR`; observe a "disk cache hit" is reported and the malicious content is materialized as the action's output without any checksum mismatch error, unlike the analogous `http_archive`/`download` path which fails fast with `expect_log "Checksum was..."` as shown in [7](#0-6)  for downloads — no equivalent failure occurs for disk cache hits post-change.

## Disk cache {#disk-cache}

Bazel can use a directory on the file system as a remote cache. This is
useful for sharing build artifacts when switching branches and/or working
on multiple workspaces of the same project, such as multiple checkouts.
Enable the disk cache as follows:

```posix-terminal
build --disk_cache=<var>path/to/build/cache</var>
```

You can pass a user-specific path to the `--disk_cache` flag using the `~` alias
(Bazel will substitute the current user's home directory). This comes in handy
when enabling the disk cache for all developers of a project via the project's
checked in `.bazelrc` file.
```
