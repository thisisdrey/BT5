### Title
Unprivileged dust transfers permanently brick a victim's account by filling `MAX_TOKENS_PER_USER` slots - (File: contracts/Pool.sol)

### Summary
CVE-2021-2372 is an availability bug (InnoDB hang/crash DoS). The Metronome analog is a reachable denial of service: `Pool.MAX_TOKENS_PER_USER = 30` caps the combined length of `depositTokensOfAccount` + `debtTokensOfAccount`, and `Pool.addToDepositTokensOfAccount` reverts with `UserReachedMaxTokens` once the cap is hit. Because `DepositToken._transfer` unconditionally adds the token to the *recipient's* list, any unprivileged attacker can push dust amounts of every registered deposit token to a victim, filling all 30 slots and permanently blocking the victim's position-growing operations — `DepositToken.deposit` (new collateral type), `DebtToken.issue`/`SmartFarmingManager.leverage` (new synthetic debt), `Pool.swap` recipients, and even `DepositToken.seize` to that account during liquidation. [1](#0-0) [2](#0-1) 

### Finding Description
`DepositToken._transfer` (called by `transfer`, `transferFrom`, and `Pool.liquidate → seize`) adds the deposit token to `depositTokensOfAccount[recipient]` whenever the recipient's balance was zero. `Pool.addToDepositTokensOfAccount` enforces `onlyIfAdditionWillNotReachMaxTokens`, which counts debt tokens + deposit tokens together against `MAX_TOKENS_PER_USER = 30` [3](#0-2) . There is no opt-out for receiving tokens and no minimum-transfer amount.

Attack steps (all unprivileged, public entry points):

1. Attacker deposits dust into each of the pool's registered `DepositToken`s (or acquires them via `transfer`), obtaining transferable balances — unlocked because the attacker keeps zero debt, so `unlockedBalanceOf` returns the full balance [4](#0-3) .
2. Attacker calls `depositToken_i.transfer(victim, 1 wei)` for each deposit token until `debtTokensOfAccount.length(victim) + depositTokensOfAccount.length(victim) == 30`. A victim already holding `k` debt tokens needs only `30 − k` dust transfers.
3. Every subsequent call that would add a token to the victim's lists reverts:
   - `DepositToken.deposit(amount, victim)` for any collateral the victim doesn't already hold → `_mint → addToDepositTokensOfAccount` reverts.
   - `DebtToken.issue` / `SmartFarmingManager.leverage` for a synthetic the victim doesn't already owe → `addToDebtTokensOfAccount` reverts.
   - Any incoming `transfer`/`seize` of a new deposit token to the victim reverts.

Cleanup is unreliable: the victim can only free a slot by transferring dust out, but `transfer` is gated by `_revertIfLocked`/`unlockedBalanceOf`, which returns 0 for every token once the position's `_issuableInUsd` is 0 (e.g., during a price drop). A victim at the issuable limit therefore cannot remove the dust at all. [5](#0-4) [6](#0-5) 

### Impact Explanation
Temporary-to-permanent freezing of position management, matching the DoS bug class:

- An underwater or near-liquidation victim cannot deposit a *new* collateral type to restore health — the only remedial path is restricted to collateral tokens already in their list. If the attacker saturated the list with tokens the victim has no underlying for, the victim is locked into forced liquidation and loses collateral to seizure + liquidation fees.
- The victim cannot open new synthetic debt positions or leverage; if the dust is locked (`unlockedBalanceOf == 0` for all tokens), the account is stuck at exactly its current token set until debt is repaid.
- Liquidations that would `seize` a deposit token into an account whose list is full revert, which also propagates to protocol-fee transfers to `feeCollector` inside `_withdraw` (`_transfer(account_, feeCollector, _fee)`) — if `feeCollector`'s combined list ever reaches 30 (it accumulates every deposit token via fees and every debt token via interest-fee mints, and it cannot call `transfer` itself to clean up), withdrawals with fees and liquidation fee collection DoS pool-wide [7](#0-6) .

### Likelihood Explanation
Fully permissionless and cheap: the attacker needs only dust balances of whitelisted deposit tokens — no privileged role, no oracle manipulation, no flash loan required. Cost scales with the number of deposit tokens registered in the pool (bounded by the pool's own set, and the victim's existing debt tokens count toward the 30-slot cap, reducing what the attacker must supply). Recovery requires the victim to hold transferable unlocked balance in the dusted tokens and to spend gas clearing slots — impossible exactly when it matters most (position at the borrowing limit). No modifier (`whenNotPaused`, `nonReentrant`, `SynthContext` checks) intercepts the dust `transfer`.

### Recommendation
- Exclude the cap check from `_transfer`/`seize` credit paths, or charge the cap only against tokens where the recipient's *locked* balance matters (i.e., let `depositTokensOfAccount` hold any number for accounting, and enforce `MAX_TOKENS_PER_USER` only in `issue`/health-relevant paths).
- Alternatively, allow accounts to forcibly remove tokens from their list regardless of lock status (e.g., a `sweepDust`-style removal when balance is below a threshold), and exempt `feeCollector` from the cap.

### Proof of Concept
Foundry-style sketch (Hardhat fork against deployed pool works identically):

```solidity
function test_dustGriefingBlocksVictim() public {
    // victim: has a position; holds 'k' debt tokens
    // attacker: deposits 1 wei of underlying into each DepositToken, no debt
    IDepositToken[] memory tokens = getAllDepositTokens(pool);
    uint256 needed = pool.MAX_TOKENS_PER_USER()
        - pool.getDebtTokensOfAccount(victim).length
        - pool.getDepositTokensOfAccount(victim).length;

    for (uint256 i; i < needed; ++i) {
        tokens[i].transfer(victim, 1); // attacker dust transfer
    }

    // victim now at cap: new collateral deposit reverts
    vm.expectRevert(UserReachedMaxTokens.selector);
    otherDepositToken.deposit(100e18, victim); // onBehalfOf victim

    // new synthetic issuance reverts
    vm.expectRevert(UserReachedMaxTokens.selector);
    newDebtToken.issue(1e18, victim);

    // seize to victim (liquidation top-up flow) reverts
    vm.expectRevert(UserReachedMaxTokens.selector);
    pool.liquidate(synth, thirdParty, amt, tokens[0]); // where seized token credits a capped recipient

    // if victim's issuableInUsd == 0, victim cannot even transfer dust out:
    vm.expectRevert(NotEnoughFreeBalance.selector);
    vm.prank(victim);
    tokens[0].transfer(attacker, 1);
}
```
