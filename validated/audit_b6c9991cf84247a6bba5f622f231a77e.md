Confirmed: `SmartAccountFactory._buildInitializer` passes `address(0)` as the `fallbackHandler` argument to `ISafe.setup`, meaning every Safe deployed through this factory (investor, borrower, originator, servicer accounts) has no `CompatibilityFallbackHandler` installed and therefore no `onERC721Received` support anywhere in its call surface.### Title
Safe smart accounts deployed by `SmartAccountFactory` have no `onERC721Received` support, breaking `LoansNFT.forceTransfer` and `safeTransferFrom`-based NFT delivery, and turning the guardian rescue path itself into a dead end - (File: `tare-io__tare-contracts/contracts/SmartAccountFactory.sol`)

### Summary
`SmartAccountFactory._buildInitializer` deploys every investor/borrower/originator/servicer Safe with `fallbackHandler = address(0)`, so none of these Safes has `CompatibilityFallbackHandler`'s `onERC721Received` support. Any code path that calls the standard ERC-721 receiver check (`safeTransferFrom`, or `LoansNFT.forceTransfer`, which explicitly re-implements the same check) will revert when the recipient is one of these Safes. This is the same root cause as the ether.fi report: a protocol-controlled account contract that value gets pushed to via a "safe" ERC-721 path, but that account cannot satisfy `onERC721Received`.

### Finding Description
`SmartAccountFactory._buildInitializer` (`tare-io__tare-contracts/contracts/SmartAccountFactory.sol:213-224`) builds the `Safe.setup` calldata with `fallbackHandler` hardcoded to `address(0)`: [1](#0-0) 

`configureSmartAccount` (run via delegatecall during `Safe.setup`) enables the `TrustedCalls` module and sets up `TrustedSpender`/currency/NFT approvals, but never installs a fallback handler: [2](#0-1) 

Because Safe's default `fallback()` is a no-op when `fallbackHandler == address(0)` (it returns empty data instead of the 4-byte `onERC721Received` selector), any call that requires the ERC-721 receiver-acceptance check against one of these Safes fails to decode the return value and reverts.

Two protocol code paths depend on that check succeeding against an arbitrary token owner/recipient address:

1. **`LoansNFT.forceTransfer`** — the guardian-only rescue path explicitly built to un-stick an NFT "stuck in a recipient that cannot move it" — calls `ERC721Utils.checkOnERC721Received` after the transfer and reverts (`ERC721InvalidReceiver`) if it fails: [3](#0-2) 

2. **Any token owner's ordinary `safeTransferFrom`** (an unprivileged, standard ERC-721 operation explicitly listed as available to "Token owner / approved address") to another Safe deployed by the factory will revert for the same reason. [4](#0-3) 

The protocol's own spec documents `forceTransfer`'s purpose and its reliance on the receiver check as "guarantees `to` can handle and further move the NFT" — i.e., it is trusted to be the universal recovery mechanism: [5](#0-4) [6](#0-5) 

Note that the design explicitly avoids this class of bug for the *primary* NFT-movement paths — `Loans.create` uses `_mint` and `LoansExchange.acceptOffer` uses `transferFrom` (both non-safe, no callback) — a deliberate mitigation documented in SECURITY.md item 20: [7](#0-6) 
`LoansExchange.acceptOffer` indeed uses `transferFrom`, not `safeTransferFrom`: [8](#0-7) 

However `forceTransfer` — the one path explicitly meant to be the universal fallback/rescue for "any other unlocked ownership-stuck scenario" — was *not* given the same non-safe treatment; it deliberately re-adds the receiver check "mirroring the safe-transfer rescue path," which is precisely what breaks it against a factory-deployed Safe with no fallback handler.

### Impact Explanation
An unprivileged token owner can trigger the stuck state simply by using the standard, documented `safeTransferFrom` capability (no misuse required — it is a listed permission of "Token owner / approved address") to send a loan NFT to another investor's Safe deployed via `SmartAccountFactory`. Because that Safe has no fallback handler, the transfer reverts and cannot be completed that way — forcing the owner toward `transferFrom` for delivery. But if an NFT ever does end up owned by (or gets force-transferred toward) such a Safe via any other path, or if the guardian ever needs to use `forceTransfer` to rescue an NFT that is genuinely stuck at a Safe address (the exact scenario the function's own documentation calls out — "a contract that was used as the buyer of an `acceptOffer` settlement but lacks the surface area to call `transferFrom` from itself"), the rescue itself reverts. Every recovery path that requires `onERC721Received` (both plain `safeTransferFrom` and the guardian's `forceTransfer`) is dead against these Safes, leaving the loan NFT — and all its future investor cashflow entitlements — permanently unrecoverable at that address, since no other unprivileged or privileged mechanism in the codebase exists to move an ERC-721 out of an address without either `transferFrom`/`approve` (which the stuck recipient contract cannot exercise) or the guardian's `forceTransfer` (which is also blocked). This is a **material, permanent, practically unrecoverable lock of a loan NFT and its cashflow entitlements caused by an unprivileged trigger**, matching the allowed impact gate.

### Likelihood Explanation
Every Safe smart account in the protocol is deployed exclusively through `SmartAccountFactory`, so this affects 100% of investor/borrower/originator/servicer accounts by construction — there is no opt-in fallback handler configuration anywhere in the deployment flow. The trigger condition (a `safeTransferFrom`-based NFT delivery landing on a Safe with no handler, or guardian rescue attempted against such a Safe) is a normal, foreseeable operational scenario rather than a contrived edge case, since `forceTransfer` is documented as precisely the tool meant to be reached for when an NFT gets stuck at a "buyer" Safe.

### Recommendation
Set a proper `fallbackHandler` (e.g., Safe's `CompatibilityFallbackHandler`, which implements `onERC721Received`/`onERC1155Received`/`isValidSignature`) in `SmartAccountFactory._buildInitializer` instead of `address(0)`. Additionally, make `LoansNFT.forceTransfer` consistent with the rest of the protocol's "non-safe by design" philosophy (SECURITY.md #20) by using a plain `_update`/`transferFrom`-style delivery without the `onERC721Received` check, so the guardian rescue path can never be blocked by the very condition it exists to fix.

### Proof of Concept
1. Deploy two Safe smart accounts, `SafeA` (investor A) and `SafeB` (investor B), via `SmartAccountFactory.deploySmartAccount` — both get `fallbackHandler = address(0)` per `_buildInitializer`.
2. `Loans.create(...)` mints a loan NFT to `SafeA` via `LoansNFT.mint` → `_mint` (succeeds, no callback).
3. `SafeA`, acting through its owners/`TrustedCalls` module, calls `LoansNFT.safeTransferFrom(SafeA, SafeB, loanId)` — this reverts because `SafeB`'s fallback returns no data and OZ's `ERC721Utils.checkOnERC721Received` cannot decode `retval`, tripping `ERC721InvalidReceiver`.
4. Suppose instead the NFT is stuck at `SafeB` via any other route (e.g., a would-be exchange buyer scenario as the spec describes) and the guardian calls `LoansNFT.forceTransfer(SafeB, recoveryAddr, loanId)` where `recoveryAddr` is also a factory-deployed Safe — this reverts for the identical reason at `ERC721Utils.checkOnERC721Received` in `forceTransfer` (`tare-io__tare-contracts/contracts/LoansNFT.sol:74`), leaving the NFT permanently stuck with no further recovery mechanism available anywhere in the codebase.

```text
  /// @inheritdoc ISmartAccountFactory
  function configureSmartAccount(
    address[] memory delegates,
    address[] memory currencies,
    address[] memory nftCollections,
    address[] memory trustedRecipients,
    uint48 validUntil
  ) external {
    require(address(this) != _SELF, NotDelegateCall());
    _setConfigured();

    // 1. Enable TrustedCalls module
    IModuleManager(payable(address(this))).enableModule(TRUSTED_CALLS_MODULE);

    // 2. Approve currencies for TrustedSpender (standard ERC20 approvals)
    for (uint256 i = 0; i < currencies.length; ++i) {
      IERC20(currencies[i]).forceApprove(TRUSTED_SPENDER, type(uint256).max);
    }

    // 3. Approve NFT collections for TrustedSpender (blanket setApprovalForAll)
    for (uint256 i = 0; i < nftCollections.length; ++i) {
      IERC721(nftCollections[i]).setApprovalForAll(TRUSTED_SPENDER, true);
    }

    // 4. Add delegates to both TrustedCalls module and TrustedSpender contract
    for (uint256 i = 0; i < delegates.length; ++i) {
      // Add to TrustedCalls module
      ITrustedCalls(TRUSTED_CALLS_MODULE).addDelegate(address(this), delegates[i]);

      // Add to TrustedSpender contract
      ITrustedSpender(TRUSTED_SPENDER).addDelegate(address(this), delegates[i]);
    }

    // 5. Set ERC20 allowances for trusted recipients in TrustedSpender.
    //    NFT per-route allowances are set lazily via TrustedSpender.setNFTAllowance.
    for (uint256 i = 0; i < trustedRecipients.length; ++i) {
      for (uint256 j = 0; j < currencies.length; ++j) {
        ITrustedSpender(TRUSTED_SPENDER).setAllowance(
          currencies[j],
          address(this),
          trustedRecipients[i],
          type(uint208).max,
          validUntil
        );
      }
    }
  }
```

```text
  function forceTransfer(address from, address to, uint256 tokenId) external {
    require(IGuardianAccessControl(LOANS_CONTRACT).hasRole(GUARDIAN_ROLE, msg.sender), Unauthorized());

    address currentOwner = _requireOwned(tokenId);
    require(from == currentOwner, InvalidFrom());
    require(to != address(0), InvalidTo());
    require(_unlockers[tokenId] == address(0), TokenLocked());

    // Pass `address(0)` as `auth` to bypass the ERC721 approval check. The
    // override still runs (bumping ownership nonces and emitting `Transfer`).
    _update(to, tokenId, address(0));

    // Ensure `to` can receive ERC-721s, mirroring the safe-transfer rescue path.
    ERC721Utils.checkOnERC721Received(msg.sender, from, to, tokenId, "");

    emit ForceTransfer(from, to, tokenId);
  }
```

```markdown
### 20 — Loan NFTs can land at any address regardless of ERC-721 awareness

**Where:** [`Loans.create`](contracts/Loans.sol), [`LoansExchange._acceptOffer`](contracts/LoansExchange.sol), [`PortfolioVault._transferLoans`](contracts/PortfolioVault.sol)

The protocol uses the **non-safe** variants of ERC-721 mint / transfer on the loan NFT in several places, for example `Loans.create` uses `_mint`, `LoansExchange._acceptOffer` uses `transferFrom`, and `PortfolioVault._transferLoans` exposes a non-safe `transferFrom` branch (`transferLoansUnsafe`). None of these invoke `onERC721Received` on the recipient, so a loan NFT can be delivered to a contract that does not implement the receiver hook (and would normally reject `safeTransferFrom`). Combined with 14, an approved originator can also spam NFTs to arbitrary addresses at create time. Recipients are responsible for ensuring they can manage and transfer the NFT they hold. No funds move at mint time — `fund()` still requires the investor's signed allowance.

This is a deliberate choice: skipping the receiver callback eliminates the re-entrancy surface that `safeTransferFrom` would otherwise hand to an arbitrary recipient contract during mint / exchange settlement / vault evacuation, and prevents a malicious recipient from griefing those flows by reverting from the callback.
```
