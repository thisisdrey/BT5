## Analysis

The Mochi bug class is: **a permissionless function overwrites risk-relevant asset/bank classification state that was previously set (possibly deliberately), without checking whether it should be considered "already configured"/protected.**

The strongest analog in marginfi-v2 is `propagate_staked_settings` (`programs/marginfi/src/instructions/marginfi_group/propagate_staked_settings.rs`). This instruction is fully permissionless (no signer check on the bank side beyond a fee payer to cover the transaction) and unconditionally overwrites a staked bank's oracle key, `asset_weight_init`, `asset_weight_maint`, `deposit_limit`, `total_asset_value_init_limit`, `oracle_max_age`, `risk_tier`, and oracle-related flag bits with the group-wide `StakedSettings` values [1](#0-0) .

Critically, unlike `lending_pool_configure_bank` and `lending_pool_configure_bank_oracle`, which both explicitly check the `FREEZE_SETTINGS` bank flag and refuse to change risk parameters/oracle when a bank is frozen [2](#0-1) [3](#0-2) , `propagate_staked_settings` never checks `FREEZE_SETTINGS` at all before overwriting these same fields [4](#0-3) . The documentation is explicit that `FREEZE_SETTINGS` is meant to be "a credible commitment that the bank's risk parameters, oracle configuration, ... will not change," settable only via `configure_bank`, and that once frozen only deposit/borrow limits should be changeable [5](#0-4) .

The only account-level constraint on `propagate_staked_settings` is that the bank belong to the group and have `asset_tag == ASSET_TAG_STAKED` [6](#0-5)  — there is no check for the freeze flag. This mirrors Mochi's `registerAsset()` flaw: a permissionless/unprivileged-reachable code path can reset previously (and deliberately) fixed risk classification of an asset/bank, changing collateral weights, oracle source, and risk tier, which directly affects liquidation thresholds and can trigger unintended liquidations or open new borrowing/collateral exposure that the admin had explicitly frozen to prevent.

### Title
Permissionless `propagate_staked_settings` bypasses `FREEZE_SETTINGS` and overwrites frozen staked-bank risk parameters - ([File: programs/marginfi/src/instructions/marginfi_group/propagate_staked_settings.rs])

### Summary
`propagate_staked_settings` is a fully permissionless instruction that copies group-level `StakedSettings` onto any staked (`ASSET_TAG_STAKED`) bank, overwriting its oracle key, asset weights, deposit limit, total-asset-value-init limit, oracle max age, risk tier, and staked oracle flags — without checking the bank's `FREEZE_SETTINGS` flag, which every other risk-config path (`lending_pool_configure_bank`, `lending_pool_configure_bank_oracle`) respects.

### Finding Description
Bank risk configuration in marginfi is normally admin-gated through `lending_pool_configure_bank` and `lending_pool_configure_bank_oracle`, both of which check `bank.get_flag(FREEZE_SETTINGS)` and refuse to modify risk-relevant fields (weights, oracle, risk tier, init limit) once a bank is frozen [7](#0-6) [3](#0-2) . `FREEZE_SETTINGS` is documented as "a credible commitment that the bank's risk parameters, oracle configuration, interest rate curves, and other settings will not change" [5](#0-4) .

However, `propagate_staked_settings` — a permissionless instruction intended to sync group-wide `StakedSettings` onto individual staked banks — directly mutates `bank.config.oracle_keys[0]`, `asset_weight_init`, `asset_weight_maint`, `deposit_limit`, `total_asset_value_init_limit`, `oracle_max_age`, `risk_tier`, and `bank.flags` without any `FREEZE_SETTINGS` check [4](#0-3) . The account constraints only verify group membership and `asset_tag == ASSET_TAG_STAKED` [6](#0-5) ; anyone can submit this transaction against any staked bank in a group.

This is directly analogous to the Mochi `registerAsset()` finding: an unprivileged, permissionless call can silently reset risk-classification parameters (asset weight/risk tier equivalent to Mochi's `_assetClass`) that the admin explicitly locked to a known-good configuration, changing collateral factors and oracle source underneath live positions.

### Impact Explanation
If an admin freezes a staked bank (setting `FREEZE_SETTINGS`) to give depositors/borrowers a guarantee that risk parameters and oracle source won't change, any unprivileged user can call `propagate_staked_settings` afterward (e.g., after the group's `StakedSettings` are later updated for a different purpose) to force the frozen bank's `asset_weight_init/maint`, `risk_tier`, `oracle_keys[0]`, and limits back to whatever the current group settings say. This can unexpectedly tighten collateral weights or change the oracle, altering health calculations for existing positions and potentially triggering liquidations that should not be possible under the frozen commitment, or conversely loosening parameters to increase borrowing power beyond what was intended — a state-integrity/insolvency-risk issue.

### Likelihood Explanation
The instruction is permissionless by design (no signer/authority check beyond covering rent/fees) and only requires knowing a staked bank's pubkey and its `StakedSettings` PDA, both of which are public. The only gating condition is `asset_tag == ASSET_TAG_STAKED`, which is a normal, common bank type. Any time an admin updates `StakedSettings` for legitimate reasons (e.g., adjusting one validator's parameters) after having frozen a specific bank, this path is trivially reachable by anyone.

### Recommendation
Add a `FREEZE_SETTINGS` check in `propagate_staked_settings`, mirroring `lending_pool_configure_bank`/`lending_pool_configure_bank_oracle`: if the bank has `FREEZE_SETTINGS` set, skip (or fail) the propagation of oracle/weight/risk-tier fields, allowing at most deposit/borrow-limit-style updates, consistent with the documented guarantee that frozen banks' risk parameters cannot change.

### Proof of Concept
1. Admin creates a staked bank via `lending_pool_add_bank_permissionless` and later calls `lending_pool_configure_bank` with `freeze_settings = true` to lock its risk parameters [8](#0-7) .
2. Admin (or a delegate) later updates the group's `StakedSettings` (e.g., via `edit_staked_settings`) for an unrelated reason (different oracle, weights, or risk tier).
3. Any unprivileged user calls `propagate_staked_settings` against the frozen bank; because the instruction has no `FREEZE_SETTINGS` check, the bank's `oracle_keys[0]`, `asset_weight_init/maint`, `deposit_limit`, `total_asset_value_init_limit`, `oracle_max_age`, and `risk_tier` are overwritten with the new group settings [9](#0-8) , despite the bank having been explicitly frozen — the same "overwrite" pattern as Mochi's `registerAsset()` resetting `_assetClass` on an already-registered asset.

pub fn propagate_staked_settings(ctx: Context<PropagateStakedSettings>) -> Result<()> {
    let settings = ctx.accounts.staked_settings.load()?;
    let mut bank = ctx.accounts.bank.load_mut()?;

    let (oracle_before, oracle_after) = (bank.config.oracle_keys[0], settings.oracle);

    bank.config.oracle_keys[0] = settings.oracle;
    bank.config.asset_weight_init = settings.asset_weight_init;
    bank.config.asset_weight_maint = settings.asset_weight_maint;
    bank.config.deposit_limit = settings.deposit_limit;
    bank.config.total_asset_value_init_limit = settings.total_asset_value_init_limit;
    bank.config.oracle_max_age = settings.oracle_max_age;
    bank.config.risk_tier = settings.risk_tier;
    bank.flags &= !STAKED_ORACLE_FLAGS;
    bank.flags |= settings.flags & STAKED_ORACLE_FLAGS;

    // Only validate the oracle info if it has changed
    if oracle_before != oracle_after {
        bank.config
            .validate_oracle_setup(ctx.remaining_accounts, None, None, None)?;
    }

    bank.config.validate()?;

    Ok(())
}

### Freeze Settings (Bit 3)

- **Bit 3** (`FREEZE_SETTINGS`, value 8): When set, most bank configuration parameters are frozen.
  Only `deposit_limit` and `borrow_limit` can still be changed. Note: `total_asset_value_init_limit`
  is also frozen (it can only be updated when the bank is NOT frozen).

This flag provides a credible commitment that the bank's risk parameters, oracle configuration,
interest rate curves, and other settings will not change. It can only be set through the
`configure_bank` instruction by the group admin. Once frozen, the admin can still adjust capacity
limits, but cannot change anything that affects the risk profile of the bank (such as weights,
oracle setup, interest rate curves, init limit, etc).
