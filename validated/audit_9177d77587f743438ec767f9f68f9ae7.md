### Title
Permanent freeze of an ETH-implicit wallet account via `has_in_flight_tx` lock that only resets inside a callback whose state changes can be reverted - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The `WalletContract` (the NEP-518 wallet deployed as a `Global` contract on every ETH-implicit account) uses a single boolean flag, `has_in_flight_tx`, to serialize transaction execution: `rlp_execute` refuses to start a new transaction while the flag is `true`, and every code path that sets it back to `true` schedules a `.then()` callback that is supposed to set it back to `false` as its very first statement [1](#0-0) . This mirrors the reported "bond" DOS pattern: an unprivileged actor can drive the resource into a locked state, and if the mechanism relies on the *same* actor's follow-up action to unlock it, the lock can become effectively permanent when that follow-up never durably lands.

### Finding Description
`rlp_execute` immediately rejects any call while `has_in_flight_tx == true`, and only sets it back to `false` inside the async callbacks (`address_check_callback`, `rlp_execute_callback`, `nep_141_storage_balance_callback`, `ban_relayer`) [2](#0-1) . Each callback resets the flag as its first line, e.g.: [3](#0-2) [4](#0-3) 

On NEAR, state changes made by a `FunctionCall` action are only committed if the function call finishes without panicking/erroring (including running out of the gas statically attached to that receipt); on any failure of the callback receipt, all of that receipt's state writes — including the `has_in_flight_tx = false` write that executed first — are discarded and never committed. The callback promises are scheduled with a small, hard-coded static gas budget (`RLP_EXECUTE_CALLBACK_GAS = 5 Tgas`, `ADDRESS_CHECK_CALLBACK_GAS`, `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`) [5](#0-4) . The callback logic after the reset performs JSON deserialization of untrusted cross-contract results (`serde_json::from_slice`) and constructs/serializes an `ExecuteResponse` that can embed an attacker-influenced `success_value` byte blob returned by an attacker-controlled `target` contract (up to `max_length_returned_data`, 4 MiB) [6](#0-5) . Any relayer (an ordinary, permissionless NEAR account — `rlp_execute` is a plain public method, callable by anyone who names the `target` and provides an RLP-encoded transaction) can drive execution into this callback and cause it to exceed its small static gas allotment or otherwise abort (e.g., by pointing `target`/registrar/NEP-141 calls at a contract that returns an oversized or malformed payload). If the callback receipt fails for any reason after having entered its body, `has_in_flight_tx` reverts to (or remains) `true` in the committed trie state, and there is **no other method in the contract that can ever set it back to `false`** — `rlp_execute` will forever short-circuit with "transaction already in progress," permanently freezing the ETH-implicit account and all funds/gas-key balances it holds. This is a stricter version of the reported bug: the referenced report's bond lock self-heals after a fixed timeout (24h) via `bondBurn`, whereas here there is no timeout, no unlock method, and no recovery path once the flag is stuck.

### Impact Explanation
Permanent freezing of funds: any $NEAR (and other assets reachable only via calls signed through this account) held by the ETH-implicit account becomes permanently inaccessible once `has_in_flight_tx` gets stuck `true`, because `rlp_execute` is the sole entry point for authorizing any action from that account and it always short-circuits on this flag. This matches the "permanent freezing of funds" acceptance bar for this scan.

### Likelihood Explanation
Reachability requires only an unprivileged NEAR account calling the public `rlp_execute` method with a target/RLP transaction that routes execution into one of the async callbacks and causes that callback's execution to fail after its state-mutating prefix (e.g., attaching a `target` contract, or NEP-141 token, that returns an oversized/malformed value, or exploiting one of the JSON-deserialization/promise-construction paths in the callback body under the fixed 5 Tgas budget). No special access key or trust relationship on the wallet is needed to invoke `rlp_execute` in the first place; only a validly-signed underlying Ethereum-style transaction is needed to get past `validate_tx_relayer_data`, and observed/relayed transaction blobs are not secret. Exact gas-exhaustion feasibility under the current 5 Tgas budget was not empirically re-derived here (see caveat below), but the structural flaw — an unlock that depends on a partially-atomic write inside a receipt that can abort — is independent of the precise gas numbers and is a clear violation of the invariant documented in the code itself ("Invariant: `has_in_flight_tx` must be `true` when a mutable method... returns a promise and `false` otherwise").

### Recommendation
- Do not rely on state written inside a callback body as the *sole* unlock mechanism; instead, reset `has_in_flight_tx = false` unconditionally as part of the callback's outermost, panic-free wrapper (e.g., using a `#[private]` handler pattern verified never to fail regardless of input size/content), or add an independent, permissionless "unstick" mechanism (e.g., a timeout analogous to the yield/resume timeout pattern already used elsewhere in nearcore, `runtime/runtime/src/lib.rs:3009` `resolve_promise_yield_timeouts`) that clears `has_in_flight_tx` after N blocks even if no callback commits.
- Cap/validate the size of any attacker-influenced cross-contract return value before including it in `ExecuteResponse`, and ensure gas budgets for callbacks are sized (or dynamically computed) so that parsing/serializing worst-case attacker-controlled payloads cannot exceed the attached static gas.
- Add defensive tests that specifically simulate a callback receipt failing (e.g., via `FunctionCallError`/gas exhaustion) after `has_in_flight_tx = false` is set in-code, verifying the flag is not left stuck `true` in committed state.

### Proof of Concept
Conceptual (root-cause) PoC — not independently executed against a running node as part of this review:
1. Deploy/observe an ETH-implicit account with the standard Wallet Contract (`Global` contract) as in `test_wallet_contract_interaction` [7](#0-6) .
2. As an arbitrary unprivileged account, call `rlp_execute(target, tx_bytes_b64)` with a validly Secp256k1-signed Ethereum-style transaction whose `to`/`target` routes into `address_check_callback` (unregistered named-account path) or `nep_141_storage_balance_callback`, pointing at a contract controlled by the attacker that returns a maximal-size (~4 MiB) success value, while capping the gas attached to the outer `rlp_execute` call so that only the callback's fixed static gas (5–15 Tgas depending on path, see `RLP_EXECUTE_CALLBACK_GAS`/`ADDRESS_CHECK_CALLBACK_GAS`/`NEP_141_STORAGE_BALANCE_CALLBACK_GAS`) is available to it.
3. If the callback aborts (e.g., "Exceeded the prepaid gas", confirmed as a real, reachable error condition for this contract in `test_insufficient_gas` [8](#0-7) , though that specific test targets the outer call rather than the callback) after the point where `has_in_flight_tx = false` was executed but before the receipt commits, the write is discarded and `has_in_flight_tx` remains `true` in persisted state.
4. Any subsequent call to `rlp_execute` from any account, including the legitimate owner/relayer, now unconditionally returns "Error: transaction already in progress, please try again later." [9](#0-8)  with no code path left to clear the flag, permanently freezing the account.

Note: I was not able to run this against a live node/test harness as part of this review to empirically confirm the exact gas thresholds needed to trigger callback failure after the state write; the finding rests on the structural/atomicity argument (partial-state-revert on receipt failure) plus the codebase's own attacker-reachable size limits (`max_length_returned_data = 4 MiB`) and the fixed, small callback gas constants. A Devin session with node/test access would be needed to empirically pin down the exact conditions that trigger callback failure and confirm the flag remains stuck.

#[tokio::test]
async fn test_insufficient_gas() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, .. } = TestContext::new().await?;

    // If not enough gas is attached to the `rlp_execute` call then the action fails.
    let target = "some.account.near".to_string();
    let action = Action::FunctionCall {
        receiver_id: target.clone(),
        method_name: "greet".into(),
        args: br#"{"name": "Aurora"}"#.to_vec(),
        gas: 5_000_000_000_000,
        yocto_near: 0,
    };
    let signed_transaction = utils::create_signed_transaction(
        0,
        &target.parse().unwrap(),
        Wei::zero(),
        action,
        &wallet_sk,
    );

    let error = wallet_contract
        .inner
        .call(crate::tests::RLP_EXECUTE)
        .args_json(serde_json::json!({
            "target": target,
            "tx_bytes_b64": codec::encode_b64(&codec::rlp_encode(&signed_transaction))
        }))
        .gas(near_gas::NearGas::from_tgas(7))
        .transact()
        .await
        .unwrap()
        .raw_bytes()
        .unwrap_err();

    assert!(
        error.to_string().contains("Exceeded the prepaid gas."),
        "Error should be that there was not enough gas"
    );

    // But the contract is still usable afterwards.
    utils::deploy_and_call_hello(&worker, &wallet_contract, &wallet_sk, 0).await?;

    Ok(())
}
