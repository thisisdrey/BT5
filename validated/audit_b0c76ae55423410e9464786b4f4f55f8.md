### Title
`Wallet.getPaginatedNowWitnessList` performs unbounded full-store iteration regardless of pagination, allowing cheap unauthenticated API calls to exhaust node CPU/memory - ([File: framework/src/main/java/org/tron/core/Wallet.java])

### Summary
`Wallet.getPaginatedNowWitnessList(offset, limit)` is exposed via the unauthenticated HTTP endpoint `GetPaginatedNowWitnessListServlet` and the gRPC `WalletApi.getPaginatedNowWitnessList` / Solidity node proxies. Although the method caps the *returned* page size (`limit > WITNESS_COUNT_LIMIT_MAX`), it unconditionally performs two unbounded, non-paginated full-store scans before applying that limit: it loads every witness via `getAllWitnesses()` and, more importantly, iterates the **entire** `VotesStore` in `countVote()` to recompute real-time vote deltas. This is directly analogous to `GlpManager.getPrice()` in the reported GMX issue, where a "read-only/UI" query function's gas cost grows with the number of on-chain items (whitelisted tokens) and is reachable without restriction, risking exceeding acceptable resource limits as the dataset grows.

### Finding Description
The vulnerable code path: [1](#0-0) 

`limit`/`offset` bound only the final *output* slice via `.skip(offset).limit(limit)` on line 812-815, but the expensive work happens earlier and is **not** gated by these parameters:

1. `chainBaseManager.getWitnessStore().getAllWitnesses()` (line 793) loads all witness records.
2. `countVote(votesStore)` (line 800) iterates the **whole** `VotesStore` — one entry per account that voted since the last maintenance cycle — regardless of what page the caller asked for: [2](#0-1) 

3. The full witness list is then re-sorted (`WitnessStore.sortWitnesses`, O(n log n)) before slicing.

The cost of `countVote` scales with the total number of `VotesCapsule` entries in the epoch (i.e., the number of distinct accounts that cast/changed a vote since the last maintenance), a value that grows with network adoption, not with the caller's requested `limit`/`offset`. This mirrors the reported issue precisely: a nominally "cheap/paginated" query whose true cost is dictated by global state size and is not actually bounded by the caller-controlled pagination parameters.

This endpoint is reachable by any anonymous API client with no fee, no authentication, and no rate-limiting beyond the generic `RateLimiterServlet`: [3](#0-2) [4](#0-3) 

Unlike an on-chain transaction (which is metered via energy/bandwidth and would revert once out of resources), this is a pure off-chain query API call — the caller pays essentially nothing per request while the node performs a full-store scan and sort on every single call.

### Impact Explanation
Repeated, cheap, unauthenticated calls to `getpaginatednowwitnesslist` (HTTP) / `getPaginatedNowWitnessList` (gRPC, including the Solidity-node and PBFT proxies) force the node to repeatedly scan and process the entire `VotesStore` and `WitnessStore` on every invocation. As the number of voting accounts grows over time (analogous to GMX's growing whitelisted-token count), the per-call cost increases, and because callers can fire many concurrent/rapid requests at negligible cost, this can degrade query-serving performance or exhaust CPU/heap on the full node, resulting in "an API the node can no longer serve" for this and potentially other endpoints sharing the same JVM/thread pool — one of the explicitly accepted impacts for this analog class.

### Likelihood Explanation
High reachability: the endpoint requires no special permission, no transaction fee, and is served on the default full-node HTTP/gRPC API surface (also mirrored on Solidity and PBFT read replicas). Any anonymous API client can trigger the full-store scan by simply calling the endpoint with arbitrary `offset`/`limit` values (the limit only affects the output, not the computation). The cost grows unboundedly with chain adoption, exactly matching the "run out of gas/resources as the underlying dataset grows" root cause of the reported analog.

### Recommendation
- Maintain an incrementally-updated, persisted real-time vote-count index (updated on each vote/unvote transaction) instead of recomputing `countVote()` by scanning the full `VotesStore` on every read.
- Alternatively, cache the result of `countVote()` per block/maintenance cycle and invalidate it only when new blocks change the underlying votes, so repeated queries within the same cycle don't reissue the full scan.
- Add server-side cost accounting / stricter rate limiting for this and similarly-shaped "paginated" endpoints whose underlying computation is not actually bounded by the requested page size.

### Proof of Concept
1. Start a full node exposing the default HTTP/gRPC API.
2. Populate `VotesStore` with a large number of distinct voter entries (in production this accumulates naturally as accounts vote/re-vote within an epoch).
3. As an anonymous client, repeatedly call:
   - HTTP: `POST /wallet/getpaginatednowwitnesslist` with `{"offset":0,"limit":1}`
   - or gRPC: `WalletApi.getPaginatedNowWitnessList({offset:0, limit:1})`
4. Observe that despite requesting only 1 result, each call triggers `Wallet.countVote()` to iterate the entire `VotesStore` (line 842-872) and `getAllWitnesses()` plus a full sort of the witness list — work proportional to total vote-store size, not to the requested `limit`.
5. Issue many such requests concurrently to measure CPU/latency degradation on the node as the `VotesStore` size grows, demonstrating the unbounded, dataset-size-dependent cost per query, mirroring the GMX `GlpManager.getPrice()` gas-growth issue.

  public WitnessList getPaginatedNowWitnessList(long offset, long limit) throws
      MaintenanceUnavailableException {
    if (limit <= 0 || offset < 0) {
      return null;
    }
    if (limit > WITNESS_COUNT_LIMIT_MAX) {
      limit = WITNESS_COUNT_LIMIT_MAX;
    }

    /*
      In the maintenance period, the VoteStores will be cleared.
      To avoid the race condition of VoteStores deleted but Witness vote counts not updated,
      return retry error.
      Only apply to requests that rely on the latest block,
      which means the normal fullnode requests with HEAD cursor.
    */
    boolean isMaintenance = chainBaseManager.getDynamicPropertiesStore().getStateFlag() == 1;
    if (isMaintenance && !Args.getInstance().isSolidityNode() && getCursor() == Cursor.HEAD) {
      String message =
          "Service temporarily unavailable during maintenance period. Please try again later.";
      throw new MaintenanceUnavailableException(message);
    }
    // It contains the final vote count at the end of the last epoch.
    List<WitnessCapsule> witnessCapsuleList = chainBaseManager.getWitnessStore().getAllWitnesses();
    if (offset >= witnessCapsuleList.size()) {
      return null;
    }

    VotesStore votesStore = chainBaseManager.getVotesStore();
    // Count the vote changes for each witness in the current epoch, it is maybe negative.
    Map<ByteString, Long> countWitness = countVote(votesStore);

    // Iterate through the witness list to apply vote changes and calculate the real-time vote count
    witnessCapsuleList.forEach(witnessCapsule -> {
      long voteCount = countWitness.getOrDefault(witnessCapsule.getAddress(), 0L);
      witnessCapsule.setVoteCount(witnessCapsule.getVoteCount() + voteCount);
    });

    // Use the same sorting logic as in the Maintenance period
    WitnessStore.sortWitnesses(witnessCapsuleList,
        chainBaseManager.getDynamicPropertiesStore().allowWitnessSortOptimization());

    List<WitnessCapsule> sortedWitnessList = witnessCapsuleList.stream()
        .skip(offset)
        .limit(limit)
        .collect(Collectors.toList());

    WitnessList.Builder builder = WitnessList.newBuilder();
    sortedWitnessList.forEach(witnessCapsule ->
        builder.addWitnesses(witnessCapsule.getInstance()));

    return builder.build();
  }

  private Map<ByteString, Long> countVote(VotesStore votesStore) {
    // Initialize a result map to store vote changes for each witness
    Map<ByteString, Long> countWitness = Maps.newHashMap();

    // VotesStore is a key-value store, where the key is the address of the voter
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();

    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();

      /**
       * VotesCapsule contains two lists:
       * - Old votes: Last votes from the previous epoch, updated in maintenance period
       * - New votes: Latest votes in current epoch, updated after each vote transaction
       */
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        countWitness.put(voteAddress,
            countWitness.getOrDefault(voteAddress, 0L) - voteCount);
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        countWitness.put(voteAddress,
            countWitness.getOrDefault(voteAddress, 0L) + voteCount);
      });
    }
    return countWitness;
  }
