## Analysis

The core broken invariant in the paymaster report is: **a payout/settlement record is finalized based on an optimistic "phase A" success signal, while the actual value transfer that should back that record only happens in a later, decoupled "phase B" that can fail/revert — with no mechanism to reconcile or retry.** The strongest local analog is in the Snowbridge relayer reward-claim flow on BridgeHub, where `pallet_bridge_relayers::claim_rewards`/`claim_rewards_to` permanently deletes the reward ledger entry as soon as the payment XCM is *sent*, not once it is *executed and settled* on AssetHub.

### Title
Snowbridge relayer rewards are irrevocably deleted on mere XCM dispatch, before the cross-chain deposit is confirmed, permanently losing relayer funds on remote execution failure - (File: `bridges/snowbridge/primitives/core/src/reward.rs`, `bridges/modules/relayers/src/lib.rs`)

### Summary
`PayAccountOnLocation::pay_reward` builds an XCM program that performs `ReserveAssetDeposited` + `DepositAsset` on AssetHub and returns `Ok(())` as soon as `XcmSender::deliver(ticket)` succeeds — i.e., as soon as the message is *queued*, not once the destination chain has actually credited the beneficiary. `pallet_bridge_relayers::do_claim_rewards` treats this `Ok(())` as final settlement: it removes the `RelayerRewards` entry (`take()`), and emits `RewardPaid`, before any confirmation that the remote `DepositAsset` succeeded.

### Finding Description
`PayAccountOnLocation::pay_reward` [1](#0-0)  constructs:
```
UnpaidExecution, DescendOrigin, UniversalOrigin, ReserveAssetDeposited, DepositAsset{AllCounted(1), beneficiary}
```
and only checks `validate_send`, `charge_fees`, and `deliver` — all local, pre-execution steps. There is no `SetAssetClaimer` in the program and no feedback path from AssetHub back to BridgeHub confirming that `DepositAsset` actually credited `beneficiary`.

`do_claim_rewards` in `pallet-bridge-relayers` [2](#0-1)  calls `T::PaymentProcedure::pay_reward(...)` inside a `try_mutate_exists`; if that call returns `Ok(())` (which happens purely on successful local dispatch), the reward entry is permanently removed from storage and a `RewardPaid` event is emitted — this is the point where the protocol declares the debt settled.

If the remote `DepositAsset` instruction later fails on AssetHub (e.g., the beneficiary account cannot satisfy the existential deposit, the beneficiary location is not locally routable, congestion/weight limits, or any other execution-time failure independent of the sender), the XCM executor traps the reserve-deposited assets via `AssetTrap::drop_assets` with no explicit claimer set in the program, making recovery impractical. Meanwhile, on BridgeHub the `RelayerRewards` entry is already gone and the event already says the reward was paid — there is no re-claim, no retry, and no reconciliation mechanism.

This mirrors the paymaster analog precisely: the state that governs whether the debt is settled advances based on a "validation/dispatch phase" success signal (message accepted for delivery) rather than the "execution phase" that would actually deliver the value, and reverts in that later phase are not reflected back into the settlement record.

### Impact Explanation
An honest relayer who has already been credited a `RelayerRewards` entry can permanently lose the reward with no attacker or malicious actor required: any transient failure of `DepositAsset` at the AssetHub side (beneficiary below ED, config change, congestion, upgrade) after the message was validly sent leaves the ledger entry deleted and the funds unrecoverable. This is a permanent-fund-lock bug affecting bridge relayer compensation, which falls squarely under the "duplicate settlement or payout" / "permanent user-fund or bridge-state lock" impact category for Snowbridge BridgeHub code.

### Likelihood Explanation
No privileged actor, governance, or malicious peer is required — a normal relayer calling the public `claim_rewards_to` extrinsic with any `AssetHubLocation` beneficiary triggers this path. The failure mode (remote-side execution failure vs. local dispatch success) is a foreseeable and reachable condition in cross-chain XCM flows (e.g., beneficiary account issues), and the code path that finalizes settlement upon send-only success is unconditional and always exercised for `BridgeReward::Snowbridge` claims.

### Recommendation
Do not finalize (delete) the `RelayerRewards` entry based solely on `XcmSender::deliver` succeeding. Either:
- Set an explicit `SetAssetClaimer`/claimer in the reward-payment XCM program so trapped assets are recoverable, and add a reconciliation/retry mechanism keyed to confirmed remote execution (e.g., via a receipt/ack XCM back to BridgeHub) before permanently removing the ledger entry, or
- Keep the reward entry (or a "pending settlement" marker) until execution is confirmed, allowing the relayer to re-claim if the remote deposit did not land.

### Proof of Concept
1. Relayer accrues a `Snowbridge` reward via `register_reward` (as in normal Snowbridge V2 delivery flow, see `bridges/modules/relayers/src/lib.rs` and `cumulus/.../snowbridge_v2_inbound.rs`).
2. Relayer calls `claim_rewards_to(BridgeReward::Snowbridge, BridgeRewardBeneficiaries::AssetHubLocation(loc))` where `loc` resolves to an account that cannot receive the deposit on AssetHub (e.g., below existential deposit, or a location for which `DepositAsset` fails at execution time due to a transient condition unrelated to the sender).
3. `BridgeRewardPayer::pay_reward` → `PayAccountOnLocation::pay_reward` [3](#0-2)  succeeds locally (`validate_send`, `charge_fees`, `deliver` all `Ok`), so `do_claim_rewards` deletes the `RelayerRewards` entry and emits `RewardPaid`.
4. On AssetHub, the XCM executes `ReserveAssetDeposited` then `DepositAsset`; `DepositAsset` fails (beneficiary cannot receive), the reserve-deposited asset is trapped with no explicit claimer set by the program.
5. Result: `RelayerRewards` entry is gone on BridgeHub (no way to re-claim), and the funds are trapped/unrecoverable on AssetHub — permanent loss of the relayer's reward despite the local "success" recorded by `RewardPaid`.

	fn pay_reward(
		relayer: &Relayer,
		_: (),
		reward: RewardBalance,
		beneficiary: Self::Beneficiary,
	) -> Result<(), Self::Error> {
		let ethereum_location = Location::new(2, [GlobalConsensus(EthereumNetwork::get())]);
		let assets: Asset = (ethereum_location.clone(), reward.into()).into();

		let xcm: Xcm<()> = alloc::vec![
			UnpaidExecution { weight_limit: Unlimited, check_origin: None },
			DescendOrigin(InboundQueueLocation::get().into()),
			UniversalOrigin(GlobalConsensus(EthereumNetwork::get())),
			ReserveAssetDeposited(assets.into()),
			DepositAsset { assets: AllCounted(1).into(), beneficiary },
		]
		.into();

		let (ticket, fee) =
			validate_send::<XcmSender>(AssetHubLocation::get(), xcm).map_err(|_| XcmSendFailure)?;
		XcmExecutor::charge_fees(relayer.clone(), fee).map_err(|_| ChargeFeesFailure)?;
		XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;

		Ok(())
	}

		fn do_claim_rewards(
			relayer: T::AccountId,
			reward_kind: T::Reward,
			beneficiary: BeneficiaryOf<T, I>,
		) -> DispatchResult {
			RelayerRewards::<T, I>::try_mutate_exists(
				&relayer,
				reward_kind,
				|maybe_reward| -> DispatchResult {
					let reward_balance =
						maybe_reward.take().ok_or(Error::<T, I>::NoRewardForRelayer)?;
					T::PaymentProcedure::pay_reward(
						&relayer,
						reward_kind,
						reward_balance,
						beneficiary.clone(),
					)
					.map_err(|e| {
						tracing::error!(
							target: LOG_TARGET,
							error=?e,
							?relayer,
							?reward_kind,
							?reward_balance,
							?beneficiary,
							"Failed to pay rewards"
						);
						Error::<T, I>::FailedToPayReward
					})?;

					Self::deposit_event(Event::<T, I>::RewardPaid {
						relayer: relayer.clone(),
						reward_kind,
						reward_balance,
						beneficiary,
					});
					Ok(())
				},
			)
