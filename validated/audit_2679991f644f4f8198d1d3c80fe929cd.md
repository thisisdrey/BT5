Audit Report

## Title
CREATE1 contract address derivation diverges between dry-run and actual transaction, breaking deterministic address prediction - (substrate/frame/revive/src/exec.rs)

## Summary
In `Stack::new_frame`, the `FrameArgs::Instantiate` branch computes the CREATE1 address via `address::create1(&deployer, nonce)`, subtracting 1 from `account_nonce` whenever `origin_is_caller` is true, with no check for whether the call is a real dispatched transaction or a runtime-API dry run. Confirmed by direct inspection, this repository's `exec.rs` contains exactly the "Before Fix" code quoted in `prdoc/stable2506/pr_8504.prdoc`, with no `ExecContext` gating applied. [1](#0-0) 

## Finding Description
The `-1` nonce adjustment is only valid when `System::account_nonce` has already been incremented pre-dispatch, which happens for real signed extrinsics but not for dry-run/simulate calls through the runtime API. Because the code applies the subtraction based solely on `origin_is_caller`, a dry-run call (where the nonce has not yet been bumped) computes `create1(deployer, nonce - 1)`, while the actual on-chain transaction computes `create1(deployer, nonce)` — a genuine, reproducible mismatch. [2](#0-1) 

The prdoc explicitly documents this exact bug and its intended fix (gating the subtraction with `matches!(exec_context, ExecContext::Transaction)`), and confirms the described "Before Fix" behavior matches what is present in this snapshot's code verbatim. [3](#0-2)  A search for `ExecContext` across the repository shows this type/mechanism referenced only in the prdoc text and not implemented anywhere in the source tree, confirming the fix was never landed in this snapshot.

## Impact Explanation
This causes off-chain tooling, wallets, or counterfactual-funding schemes that pre-compute a `pallet-revive` contract's CREATE1 address via dry-run before submitting the deployment transaction to derive an address that will never actually host the deployed contract code. Value or state sent to the predicted (dry-run) address becomes permanently stranded relative to the actually deployed contract, matching the "permanent user-fund lock via wrong beneficiary/address" impact class under the Polkadot SDK Impact Gate — this is a runtime bug in `pallet-revive` that compromises intended (documented, Parity-acknowledged) behavior of address prediction consistency.

## Likelihood Explanation
This requires no privileged access or adversarial behavior — any ordinary user or piece of tooling that performs the standard "dry-run to preview address, then submit real extrinsic" workflow for `instantiate`/`instantiate_with_code` without a salt will trigger the divergence deterministically and repeatably, since `origin_is_caller` is true for both call types and no other differentiator exists in the current code path.

## Recommendation
Introduce an `ExecContext` (or equivalent transaction/dry-run discriminator) threaded into `new_frame`, and apply the `saturating_sub(1)` nonce adjustment only when `origin_is_caller && matches!(exec_context, ExecContext::Transaction)`, exactly as described in `prdoc/stable2506/pr_8504.prdoc`. Add a regression test analogous to `nonce_not_incremented_in_dry_run()` asserting dry-run and transaction-computed addresses are identical for the same deployer/nonce state.

## Proof of Concept
1. Fund `ALICE`; note `System::account_nonce(&ALICE)` = N.
2. Invoke the runtime API dry-run for `instantiate_with_code` (no salt) as `ALICE`. The frame is built with `origin_is_caller = true` and the pre-dispatch nonce N (not yet incremented), yielding predicted address `create1(ALICE_ADDR, N - 1)` due to the unconditional subtraction.
3. Submit the actual signed `instantiate_with_code` extrinsic as `ALICE`. Because the nonce is incremented pre-dispatch to N+1 for real extrinsics, the `-1` correctly compensates, giving the true deployed address `create1(ALICE_ADDR, N)`.
4. Compare: predicted address from step 2 (`create1(ALICE_ADDR, N-1)`) differs from the actual deployed address from step 3 (`create1(ALICE_ADDR, N)`), reproducing the mismatch documented in `pr_8504.prdoc`.

**File:** prdoc/stable2506/pr_8504.prdoc (L9-49)
```text
    The issue stems from the `create1` address derivation logic in `exec.rs`:

    ```rust
    address::create1(
        &deployer,
        // the Nonce from the origin has been incremented pre-dispatch, so we
        // need to subtract 1 to get the nonce at the time of the call.
        if origin_is_caller {
            account_nonce.saturating_sub(1u32.into()).saturated_into()
        } else {
            account_nonce.saturated_into()
        },
    )
    ```

    The code correctly subtracts 1 from the account nonce during a transaction execution (because the nonce is incremented pre-dispatch), but doesn't account for execution context - whether it's a real transaction or a dry run through the RPC.

    ## Review Notes

    This PR adds a new condition to check for the `ExecContext` when calculating the nonce for address derivation:

    ```rust
    address::create1(
        &deployer,
        // the Nonce from the origin has been incremented pre-dispatch, so we
        // need to subtract 1 to get the nonce at the time of the call.
        if origin_is_caller && matches!(exec_context, ExecContext::Transaction) {
            account_nonce.saturating_sub(1u32.into()).saturated_into()
        } else {
            account_nonce.saturated_into()
        },
    )
    ```

    A new test `nonce_not_incremented_in_dry_run()` has been added to verify the behavior.

    ## Before Fix

    - Dry-run contract deployment returns address derived with nonce N
    - Actual transaction deployment creates contract at address derived with nonce N-1
    - Result: Inconsistent addresses between simulation and actual execution
