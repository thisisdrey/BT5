## Title
Out-of-bounds heap read in ijar's ZIP central-directory parser due to unchecked length fields — (`third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry`, the ZIP central-directory-entry parser used by `ijar`/`singlejar` when reading `.jar`/`.zip` files that Bazel builds from (including archives fetched from external repositories and processed as `java_import`/interface-jar inputs), reads attacker-controlled 16-bit length fields (`file_name_length`, `extra_field_length`, `file_comment_length`, and the per-extra-field `data_size`) and advances its read cursor by those lengths **without ever validating that the cursor stays inside the mapped input buffer**. This mirrors the TIPC Gap-ACK bug class: a self-consistent-looking length is trusted and used to size a memory read/copy, but nothing checks it against the actual bounds of the buffer it is being read from.

### Finding Description
`ProcessCentralDirEntry` reads the fixed fields of a Central Directory Header and then three attacker-controlled 16-bit lengths: [1](#0-0) 

It memcpy's up to `filename_size` bytes of the entry name (bounded), but then unconditionally advances `p` by `file_name_length`, and separately walks an inner loop over "extra fields" using a 16-bit `header_id`/`data_size` pair per field: [2](#0-1) 

None of `file_name_length`, `extra_field_length`, `data_size`, or `file_comment_length` is checked against the actual size of the mapped input file (`in_length`) or against the region actually reserved for the central directory. This is the same defect class as the TIPC bug: a length is internally self-consistent (it parses without contradiction) but is never checked against the real bound of the data it describes.

By contrast, the sibling function `InputZipFile::ProcessLocalFileEntry`, which parses the Local File Header for the *same* zip file, explicitly guards every variable-length read with `EnsureRemaining()`: [3](#0-2) [4](#0-3) 

This is exactly the "unicast path checks, broadcast/other path doesn't" asymmetry from the CVE report: one code path in the same parser enforces the invariant, the other (central directory parsing) does not.

The only defense at a higher level is the aggregate check in `FindZipCentralDirectory`, which verifies that the central-directory *region as a whole* fits in the file: [5](#0-4) 

That check only bounds the sum announced in the End-Of-Central-Directory record; it does not validate that any individual entry's `file_name_length`/`extra_field_length`/`file_comment_length`/`data_size` keeps the per-entry cursor `p` inside that region or inside the mapped file at all. A single entry with an inflated `extra_field_length` (or an inner extra-field `data_size`) can push `p`, and therefore all subsequent `get_u2le`/`get_u4le`/`get_u8le` reads, past the end of the mmap'd file.

### Impact Explanation
Because the zip file is opened via `mmap` (`MappedInputFile`), reading past the mapped region causes either a crash (SIGSEGV/SIGBUS — availability impact) or, if adjacent mapped pages happen to be valid (e.g., due to page-alignment padding, or if the attacker also controls a following pseudo-signature field expected by the "safe by construction" comment on line 491), out-of-bounds reads of adjacent heap/mapped memory that get treated as ZIP64 sizes/offsets and used further in `CalculateOutputLength()`/downstream copy logic. This is precisely the "read is already out of bounds regardless of how the bytes are used" scenario from the CVE. `ijar`/`singlejar` process archive content, including `.jar` files that arrive as external dependencies (e.g., via `http_jar`, `http_archive` unpacked Java artifacts, or third-party `java_import` targets), meaning a malicious jar served from an attacker-controlled or compromised mirror can trigger this parser with no additional privilege.

### Likelihood Explanation
`ijar`'s zip reader is invoked automatically as part of normal Java build actions (creating interface jars) whenever Bazel processes a `.jar`, so any project that consumes a hostile jar (registry artifact, mirrored dependency, or malicious tarball entry unpacked to a `.jar`) reaches this code with no user interaction beyond a normal `bazel build`. The bug requires only crafting one Central Directory Header with an oversized length field; no cryptographic bypass is needed since there is no integrity check on the *internal structure* of an already-downloaded/verified archive (the sha256/integrity check in `http_archive` protects the archive's bytes as a whole, not the correctness of each internal zip-format field).

### Recommendation
Add bounds checks in `InputZipFile::ProcessCentralDirEntry` (mirroring `EnsureRemaining()` in `ProcessLocalFileEntry`) before advancing `p` by `file_name_length`, `extra_field_length`, and `file_comment_length`, and before consuming each inner extra-field `data_size`, verifying that `p + <length> <= bytes + in_length` (and ideally `<= central_dir_end`) at every step; reject the entry/central directory otherwise.

### Proof of Concept
Construct a minimal ZIP with a valid End-Of-Central-Directory record whose `central_dir_size`/`central_dir_offset` pass the `FindZipCentralDirectory` aggregate check, but whose single Central Directory Header entry declares `extra_field_length = 0xFFFF` (or an inner extra-field `data_size = 0xFFFF`) such that the parser's cursor `p` in `ProcessCentralDirEntry` is advanced past the actual end of the mapped file. Feed this file to the `ijar`/`zipper` binary (as exercised by `third_party/ijar/test/zip_test.sh`, e.g. extending `test_no_path_traversal`-style tests with a new `test_malformed_extra_field_oob_read` case) or to `bazel build` on a target that treats the crafted file as a `.jar` input; observe a crash or ASan/Valgrind-reported heap-buffer-overflow read inside `ProcessCentralDirEntry`.
