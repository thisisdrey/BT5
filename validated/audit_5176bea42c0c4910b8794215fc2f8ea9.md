### Title
Missing null-check on `AccountCapsule` before dereference in `VoteWitnessProcessor.execute()` - (File: actuator/src/main/java/org/tron/core/vm/nativecontract/VoteWitnessProcessor.java)

### Summary
`VoteWitnessProcessor.execute()` fetches an `AccountCapsule` for the voter address and immediately dereferences it (`accountCapsule.getVotesList()`, `accountCapsule.clearVotes()`, `accountCapsule.getAllTronPower()`/`getTronPower()`) without ever checking it for `null`, mirroring the CVE-2021-47415 bug class ("dereference a possibly-null capsule/context object obtained from a lookup, without a null check").

### Finding Description
`VoteWitnessProcessor.validate()` only checks that the `Repository` is non-null and that the vote list size does not exceed `MAX_VOTE_NUMBER`; it performs no existence check on the voter account: [1](#0-0) 

`execute()` then retrieves the account via `repo.getAccount(ownerAddress)` and immediately dereferences it — first indirectly through `accountCapsule.getVotesList()` when building a fresh `VotesCapsule`, and unconditionally via `accountCapsule.clearVotes()`: [2](#0-1) 

`Repository.getAccount()` (backed by `RepositoryImpl`) returns `null` when the address has no corresponding account record, exactly the same pattern other actuators in this codebase explicitly guard against (e.g. `TransferActuator.validate()` checks `ownerAccount == null` before use — [3](#0-2) , and `UnfreezeBalanceActuator.validate()` similarly checks `accountCapsule == null` — [4](#0-3) ). `VoteWitnessProcessor` is the odd one out: it has no equivalent guard, so if `repo.getAccount(ownerAddress)` returns `null`, `accountCapsule.getVotesList()`/`clearVotes()` throws an unguarded `NullPointerException`.

I could not fully trace, within the available index, the exact call site in `Program.java`/TVM opcode dispatch that supplies `ownerAddress` to `VoteWitnessProcessor` (the file `Program.java` did not show a direct textual match for `VoteWitnessProcessor`/`VoteWitnessParam` in this search pass, likely because the invocation goes through a different native-contract dispatch class not captured by the search). Because of this, I cannot conclusively confirm whether the `ownerAddress` passed into this processor can, in practice, ever correspond to an address without an existing `AccountCapsule` (e.g., a freshly-derived contract address, a delegatecall context, or an address supplied without the normal "account must exist to pay for the transaction" guarantee that protects `msg.sender`-only paths). This uncertainty is significant: if the address is always the transaction's already-charged `msg.sender`/existing caller account, this NPE may not be practically reachable with a null account. Given this unresolved reachability question, I cannot assert with full confidence that this is exploitable by an arbitrary unprivileged caller.

### Impact Explanation
If reachable with a non-existent account, the failure mode is a `NullPointerException` inside VM opcode execution. Depending on how the surrounding `Program`/`VMActuator` exception handling classifies this (contrast with `ContractExeException`/`ContractValidateException`, which are handled gracefully and converted to failed transaction results), an unhandled `RuntimeException`/`NullPointerException` propagating out of native contract execution could either be caught generically by `VMActuator`'s catch-all (see the `Throwable` catch block in `VMActuator.java` around lines 287-301) and converted to a failed execution result — in which case impact is limited to a reverted/failed transaction — or, if any surrounding code path does not catch `Throwable`, it could crash node processing of that transaction/block.

### Likelihood Explanation
Low-to-Medium and **unverified**. The `validate()` method's lack of an account-existence check is a genuine code smell inconsistent with the rest of the actuator/processor code in this repo, but I was unable to confirm from the available index whether the caller-supplied `ownerAddress` can ever be a nonexistent account in the native-contract vote path (TVM opcode invocation typically operates on the calling contract's own address, which would already exist as it paid energy/bandwidth for the call). Without confirming the dispatch site, likelihood of practical exploitation by an unprivileged caller is uncertain.

### Recommendation
Add an explicit null check for `accountCapsule` in `VoteWitnessProcessor.execute()` (or better, in `validate()`) immediately after `repo.getAccount(ownerAddress)`, throwing a `ContractExeException`/`ContractValidateException` analogous to the pattern used in `TransferActuator`, `UnfreezeBalanceActuator`, and other actuators, before any field of `accountCapsule` is accessed. Additionally, trace and confirm the actual TVM opcode/dispatch code that constructs `VoteWitnessParam.voterAddress` to determine whether an attacker-controlled address without a backing account can reach this code path — this verification is necessary to determine the true severity/reachability of the issue.

### Proof of Concept
Not confirmed. A concrete PoC would require identifying (1) the TVM opcode or precompiled-contract entry point that constructs `VoteWitnessParam` and invokes `VoteWitnessProcessor.execute()`, and (2) confirming that the `voterAddress` field can be set to an address with no corresponding `AccountCapsule` in the account store at execution time (e.g., via a crafted contract call using an address that has never been funded/activated). This could not be established with certainty from the indexed code available in this session.
