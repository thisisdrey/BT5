## Title
`process_delivery_receipt` pays relayer reward without checking `DeliveryReceipt.success` - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
`process_delivery_receipt` in the Snowbridge outbound-queue-v2 pallet pays the full relayer reward and clears the `PendingOrder` for a message nonce whenever a validly-proven `InboundMessageDispatched` event is submitted via `submit_delivery_receipt`, without ever inspecting the decoded `receipt.success` field. This means messages whose execution genuinely failed on the Ethereum Gateway (`success == false`) are treated identically to successfully executed messages for payout purposes.

## Finding Description
`submit_delivery_receipt` verifies the Ethereum event log/proof, decodes it into a `DeliveryReceipt`, and forwards it to `process_delivery_receipt`: [1](#0-0) 

`DeliveryReceipt` is decoded from the on-chain `InboundMessageDispatched(uint64 nonce, bytes32 topic, bool success, bytes32 reward_address)` Ethereum event and explicitly carries the `success` flag from that event: [2](#0-1) 

`process_delivery_receipt` checks only that `receipt.gateway` matches the configured `GatewayAddress` and that a `PendingOrder` exists for `receipt.nonce`. It then unconditionally pays `order.fee` via `T::RewardPayment::register_reward` (when `fee > 0`) and removes the pending order — `receipt.success` is never read anywhere in this function: [3](#0-2) 

The `PendingOrder` is created with the message's `fee` when the message is first enqueued via `do_process_message`, prior to any knowledge of Ethereum-side execution outcome: [4](#0-3) 

Because the check is absent, any relayer who observes a legitimate `InboundMessageDispatched` event with `success == false` (e.g., a reverted command, out-of-gas execution, or a rejected command on the Gateway contract) can submit that real proof through the permissionless `submit_delivery_receipt` extrinsic and receive the full reward exactly as if the message had executed successfully. Existing guards (`GatewayAddress` match, `PendingOrder` existence) verify authenticity and nonce binding but do nothing to verify the execution outcome that `success` is designed to signal.

## Impact Explanation
This is a payout-correctness violation: reward settlement advances (fee paid, order cleared) without confirming that dispatch/execution actually succeeded, violating the invariant that message queue/receipt/payout state must only advance after decode, dispatch, execution, and settlement succeed atomically. It results in the reward pool being drained for messages whose execution failed, misallocating value intended only for successful relayers, and removing any economic incentive for relayers to ensure real successful delivery. This aligns with the "duplicate settlement or payout" / underpriced-work style impact category for bridge reward pallets.

## Likelihood Explanation
Likelihood is high. Execution failure on the Ethereum Gateway is a normal, expected occurrence (gas limits, reverted commands, contract-level rejections), and any unprivileged relayer can construct and submit a valid proof for such a genuinely-failed event through the public `submit_delivery_receipt` extrinsic with no special privileges, timing, or infrastructure control required.

## Recommendation
In `process_delivery_receipt`, check `receipt.success` before paying the reward. If `success == false`, do not call `T::RewardPayment::register_reward` with the full fee; instead handle the failure path explicitly — e.g., withhold or reduce the reward, route the pending order to a retry/refund path, or emit a distinct failure event — before removing (or retaining, if retry is intended) the `PendingOrder`.

## Proof of Concept
1. A message is enqueued via `do_process_message`, creating `PendingOrder { nonce, fee, .. }` in storage (`bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs:426-436`).
2. On Ethereum, the Gateway contract executes the message's commands, one of which reverts/fails, and it emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer builds a valid inclusion proof for this real event log and calls `submit_delivery_receipt(origin, event)`.
4. `T::Verifier::verify` succeeds (the event genuinely occurred) and `DeliveryReceipt::try_from` correctly decodes `success = false` (`bridges/snowbridge/primitives/outbound-queue/src/v2/delivery_receipt.rs:38-51`).
5. `process_delivery_receipt` validates only `gateway` and `PendingOrders::get(nonce)`, then calls `T::RewardPayment::register_reward(&reward_account, ..., order.fee)` and removes the order (`bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs:446-480`) — `receipt.success` is never inspected.
6. The relayer is paid the full fee despite the message's execution having failed on Ethereum, and the `PendingOrder` is cleared as though delivery fully succeeded.

A unit test can be added asserting: for a `DeliveryReceipt` with `success = false`, calling `process_delivery_receipt` should either not invoke `RewardPayment::register_reward` or should not clear the `PendingOrder` in the same way as a successful receipt — demonstrating the current code pays identically in both cases.

		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}

sol! {
	event InboundMessageDispatched(uint64 indexed nonce, bytes32 topic, bool success, bytes32 reward_address);
}

/// Delivery receipt
#[derive(Clone, Debug)]
pub struct DeliveryReceipt {
	/// The address of the outbound queue on Ethereum that emitted this message as an event log
	pub gateway: H160,
	/// The nonce of the dispatched message
	pub nonce: u64,
	/// Message topic
	pub topic: H256,
	/// Delivery status
	pub success: bool,
	/// The reward address
	pub reward_address: [u8; 32],
}

#[derive(Copy, Clone, Encode, Decode, Eq, PartialEq, Debug, TypeInfo)]
pub enum DeliveryReceiptDecodeError {
	DecodeLogFailed,
	DecodeAccountFailed,
}

impl TryFrom<&Log> for DeliveryReceipt {
	type Error = DeliveryReceiptDecodeError;

	fn try_from(log: &Log) -> Result<Self, Self::Error> {
		let topics: Vec<B256> = log.topics.iter().map(|x| B256::from_slice(x.as_ref())).collect();

		let event = InboundMessageDispatched::decode_raw_log_validate(topics, &log.data)
			.map_err(|_| DeliveryReceiptDecodeError::DecodeLogFailed)?;

		Ok(Self {
			gateway: log.address,
			nonce: event.nonce,
			topic: H256::from_slice(event.topic.as_ref()),
			success: event.success,
			reward_address: event.reward_address.0,
		})
	}
