### Title
Active-permission key can self-escalate to full account (Owner) control via `AccountPermissionUpdateContract` - (File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java)

### Summary
`AccountPermissionUpdateActuator` never restricts which permission level may authorize an `AccountPermissionUpdateContract`. As long as an `Active` permission's `operations` bitmap includes the bit for `AccountPermissionUpdateContract` (a value the validator accepts, since it only checks the bit against the chain's generic `getAvailableContractType()` list), any key holding that scoped Active permission can broadcast a transaction that rewrites the account's Owner permission, Witness permission, and all Active permissions — fully taking over the account, exactly analogous to the reported bug class where a scoped/delegated role (TENANT_ADMIN) can set fields (`GLOBAL_ADMIN`) that only the top-level role should ever be allowed to grant.

### Finding Description
`AccountPermissionUpdateActuator.validate()` performs only generic structural checks on the submitted `owner`/`witness`/`actives` permissions (key counts, weights, threshold, operations size, and whether each bit maps to a currently "available" `ContractType`) via `checkPermission()`. [1](#0-0) 
It never inspects — nor rejects based on — the `permissionId` that was actually used to *authorize* the `AccountPermissionUpdateContract` transaction itself. That authorization/signature check happens generically and separately in `TransactionCapsule`/`TransactionUtil`, where any `permissionId != 0` is accepted as long as the corresponding stored `Active` permission's `operations` bitmap has the bit for the contract's own type set — with no special-casing to forbid `AccountPermissionUpdateContract` from being included in that bitmap. [2](#0-1) [3](#0-2) 

Because a permission's `operations` bitmap is fully attacker/owner-settable at the time an Active permission is created (subject only to the "is this a currently valid `ContractType`" check), an account can (intentionally or by social-engineering/misconfiguration) grant a low-trust delegated Active-permission key the ability to invoke `AccountPermissionUpdateContract`. That key — which was meant to be scoped to ordinary operations like transfers — can then submit a new `AccountPermissionUpdateContract` transaction that **replaces the Owner permission itself**, adding the attacker's own key with full weight/threshold, and rewriting all other Active/Witness permissions in the same call. `execute()` applies whatever permission set is supplied unconditionally: [4](#0-3) 

This mirrors the external bug class precisely: the schema/structural validation (`checkPermission`) *is* the entire authorization decision for who can rewrite the top-level (Owner) role, with no policy check enforcing "only the current Owner permission may grant/modify the Owner permission."

### Impact Explanation
An attacker who obtains signing rights for a scoped, low-privilege Active permission key (e.g. a co-signer added for routine transfers) can, if that permission's operations bitmap was ever configured to include `AccountPermissionUpdateContract`, unilaterally seize full Owner control of the target TRON account — permanently locking out the legitimate owner, redirecting all funds, and taking over witness voting rights if the account is a witness. This is an unauthorized account takeover with permanent loss-of-control impact, matching the "Critical" severity class of the analog report.

### Likelihood Explanation
Exploitation requires that some Active permission on the account already includes the `AccountPermissionUpdateContract` bit in its `operations` field — a configuration an account owner might set up unaware of the implication (e.g., granting a "manager" role broad operational rights believed to be scoped to normal transaction types), or that could be introduced via a compromised/malicious co-signer setup flow, custodial service, or exchange multisig configuration tooling. Given TRON's multisig feature is actively used by exchanges and custodial wallets to delegate operational permissions to separate hot-key services, this is a realistic misconfiguration/privilege-boundary gap rather than a purely theoretical one.

### Recommendation
In `AccountPermissionUpdateActuator.validate()`, explicitly reject any `AccountPermissionUpdateContract` transaction where the contract's `permission_id` field (in `Transaction.Contract`) is not `0` (i.e., not the Owner permission), regardless of what the stored Active permission's `operations` bitmap allows. Equivalently, hard-code `AccountPermissionUpdateContract` (and any other account-lifecycle contract types) as always requiring Owner-level (`permissionId == 0`) authorization in `TransactionCapsule.checkPermission`/`TransactionUtil.checkPermissionOperations`, independent of the generic `operations` bitmap, so that Active permissions can never be granted the ability to rewrite the account's own permission structure.

### Proof of Concept
1. Owner account `A` sets up permissions via `AccountPermissionUpdateContract`: Owner permission (key `O`), and an Active permission `P2` with keys `[O, M]`, threshold 1, and `operations` bitmap including the bit for `AccountPermissionUpdateContract` (accepted because it is a currently valid `ContractType` per `dynamicStore.getAvailableContractType()`). [5](#0-4) 
2. Attacker controls key `M` (the "manager" collaborator key intended only for routine ops).
3. Attacker crafts a new `AccountPermissionUpdateContract` for account `A`, setting `permission_id = 2` (the Active permission `P2`) in the transaction, with a new Owner permission containing only the attacker's key `X` with threshold 1, and any Active permission list of the attacker's choosing.
4. Attacker signs the transaction with key `M` only. `TransactionCapsule.checkPermission` accepts it because `permissionId != 0` maps to `PermissionType.Active` and `checkPermissionOperations` finds the `AccountPermissionUpdateContract` bit set. [2](#0-1) 
5. `AccountPermissionUpdateActuator.execute()` applies the new permissions unconditionally, overwriting the Owner permission to `[X]`. [6](#0-5) 
6. Account `A` is now fully controlled by attacker key `X`; the original owner key `O` no longer has any authority.
