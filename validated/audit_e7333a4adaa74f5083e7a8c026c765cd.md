### Title
Unprivileged attacker can fill a victim's `depositTokensOfAccount`/`debtTokensOfAccount` list via dust deposits so the `MAX_TOKENS_PER_USER` safety check permanently reverts the victim's deposits and issuance — (File: contracts/Pool.sol)

### Summary
`Pool` enforces `MAX_TOKENS_PER_USER = 30` as a gas-safety bound on the per-account token lists iterated by `debtOf`/`depositOf`/`debtPositionOf`. The bound is enforced in `addToDepositTokensOfAccount` and `addToDebtTokensOfAccount` via `onlyIfAdditionWillNotReachMaxTokens`, which reverts with `UserReachedMaxTokens` once the combined list length hits 30. Because `DepositToken.deposit(amount_, onBehalfOf_)` lets any caller mint deposit tokens to an arbitrary `onBehalfOf_` account — and because `_mint`/`_transfer` unconditionally calls `pool.addToDepositTokensOfAccount(account)` when the recipient's balance goes from 0 — an unprivileged attacker can deposit dust amounts of every registered collateral token on behalf of a victim, filling the victim's list. Afterwards every call that would add a *new* token to the victim's list reverts: deposits of new collateral types and issuance of new synthetic debt. This is the direct analog of CVE-2018-12893: a safety check introduced to bound resource consumption can be deliberately triggered by an unprivileged party to deny service to a victim.

### Finding Description
Relevant code:

- `Pool.sol:79` — `uint256 public constant MAX_TOKENS_PER_USER = 30;`
- `Pool.sol:143-148` — modifier `onlyIfAdditionWillNotReachMaxTokens` reverts `UserReachedMaxTokens()` when `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= 30`.
- `Pool.sol:204-208` — `addToDebtTokensOfAccount` is called by `DebtToken._mint` (issue/mint path) whenever a user's debt-token balance becomes non-zero.
- `Pool.sol:216-220` — `addToDepositTokensOfAccount` is called by `DepositToken._mint`/`_transfer` whenever a user's deposit-token balance becomes non-zero. The unit test at `test/DepositToken.test.ts:552-567` confirms the add happens exactly on a 0→nonzero transition and that a `transfer` triggers it.
- `DepositToken.sol:211-237` — `deposit(uint256 amount_, address onBehalfOf_)` is permissionless (`whenNotPaused nonReentrant onlyIfDepositTokenExists`), requires only `amount_ > 0` and `onBehalfOf_ != 0`, and ends in `_mint(onBehalfOf_, _deposited)`. There is no opt-in from `onBehalfOf_`.
- `DepositToken.sol:348-354` — `transfer` also reaches `_transfer` → `addToDepositTokensOfAccount(recipient)`, giving a second dust vector once the attacker holds any balance.

The combined counter (`debt + deposit`) makes the attack cheaper: slots are shared, so every registered collateral token the attacker dusts into the victim consumes one of the 30 slots that debt positions also need.

### Impact Explanation
Once a victim's combined list reaches 30 entries:

- Any `DepositToken.deposit`/`transfer`/seize/`SmartFarmingManager` flow that would push a **new** deposit token onto the victim's list reverts with `UserReachedMaxTokens`, including deposits made by third parties on the victim's behalf and leverage/zap deposits through `SmartFarmingManager.leverage`.
- Any `DebtToken.issue`/`mint` (and flash-mint flows) into a synthetic the victim does not already hold reverts, blocking new borrowing.
- The victim cannot cheaply recover: a slot is only freed when a token balance returns fully to 0 (`removeFromDepositTokensOfAccount`/`removeFromDebtTokensOfAccount`), which forces paying the withdraw fee / repaying the whole dusted token, and the attacker can re-dust the slot in the same block or later.

Result: temporary freezing of the victim's ability to add collateral or open debt positions — a liveness break driven purely by an unprivileged EOA spending dust amounts. If the victim's position drifts unhealthy and the only viable rescue path requires a collateral type not already in their list (or a leverage/flash-repay path that mints a new token), liquidation proceeds while remediation reverts.

### Likelihood Explanation
Feasibility depends on the deployed pool having enough registered deposit/debt tokens to reach 30 combined. On the public Metronome Synth deployments (multiple collateral types plus multiple ms* synthetics per pool), the combined registered token count approaches or reaches this range; where it does, the attack requires only dust-sized deposits of each missing collateral (the attacker pays real underlying, but each slot costs ~1 wei of collateral after the balance-delta accounting in `deposit`, plus optionally a deposit fee). No privileged role, oracle manipulation, or governance action is required. Where a pool has fewer than ~30 total tokens, the attack is limited to blocking only the remaining free slots and is proportionally weaker.

### Recommendation
Decouple the safety bound from attacker-controllable state:

- Enforce `MAX_TOKENS_PER_USER` only on the entry points the account owner initiates (e.g., inside `deposit`/`issue` when `onBehalfOf_`/sender equals the account), not inside `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` which are also triggered by third-party `deposit(..., onBehalfOf_)`, `transfer`, and `seize`.
- Alternatively, do not revert on the cap in the add functions: return silently and let `debtPositionOf` bound its iteration, or add an opt-in/whitelist so only positions the account itself opened count toward the cap.
- At minimum, count dusted entries at their USD value and ignore/reject adds below a meaningful threshold so filling the list costs real collateral.

### Proof of Concept
Hardhat sketch against deployed-style contracts (mirroring `test/Pool.test.ts:1386-1416`, which already demonstrates the revert):

```ts
// attacker: EOA holding dust of each collateral's underlying
for (const dt of depositTokens) {
  await underlying(dt).approve(dt.address, 1);
  await dt.deposit(1, victim.address); // adds dt to victim's list, no opt-in
}
// repeat until depositTokensOfAccount.length(victim) + debtTokensOfAccount.length(victim) == 30

// victim's legitimate actions now revert:
await expect(newDepositToken.deposit(amount, victim.address))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
await expect(debtToken2.issue(amount)) // mints new debt token for victim
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

The existing test at `test/Pool.test.ts:1386-1416` confirms `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` revert `UserReachedMaxTokens` once 30 combined entries exist; `DepositToken.deposit`'s unrestricted `onBehalfOf_` parameter is what makes the fill reachable by an arbitrary attacker rather than only self-inflicted.

Caveat: I verified the modifier, the add functions, and the `deposit`/`transfer` entry points, but did not fully read `DepositToken._mint`/`DebtToken._mint` internals; the add-on-0→nonzero behavior is confirmed indirectly by the unit tests cited. Whether a given deployed pool exposes enough tokens to reach the 30 cap is configuration-dependent and was not verified against live deployments.
