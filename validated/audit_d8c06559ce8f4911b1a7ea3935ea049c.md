## Analog Found [1](#0-0) 

### Title
Unprivileged principal can front-run `initialize()` on any vault to brick the DAO's atomic protocol-init proposal - (File: `mainnet/contracts/vault/v0-vault-usdc.clar`, mirrored in `v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`)

### Summary
`initialize()` in every `v0-vault-*` contract is a `define-public` entry point with **no `check-dao-auth` guard**, unlike every other vault admin setter (`set-authorized-contract`, `set-points-util`, `set-points-rate`, `set-fee-reserve`, etc., which all call `(try! (check-dao-auth))`). Any ordinary principal can call `initialize()` first, permanently flipping `initialized` to `true` and consuming the one-time initialization slot before the DAO's own deployment proposal executes it.

### Finding Description
`initialize()` is guarded only by an idempotency check, not an authorization check: [1](#0-0) 

Compare this to every other privileged setter in the same file, which explicitly requires `check-dao-auth`: [2](#0-1) 

The DAO's deployment proposal (`v0-init.clar`) calls `initialize` on each vault as one step inside a single atomic `execute` transaction that also sets supply/debt caps, sets interest-rate curves, inserts egroups, and authorizes the `market` contract, all chained with `try!`: [3](#0-2) 

Because `initialize()` has no access control, any unprivileged principal can call it directly on a freshly deployed vault contract before the DAO proposal is submitted/mined. Their call succeeds (it only requires holding/approving `MINIMUM-LIQUIDITY` of the underlying token, which is deposited to `NULL-ADDRESS` via the internal `deposit` call), and `initialized` becomes permanently `true`. When the DAO's `v0-init` `execute` proposal subsequently runs `(try! (contract-call? .v0-vault-usdc initialize))`, that call now hits `(asserts! (not (var-get initialized)) ERR-ALREADY-INITIALIZED)` and returns an error, which propagates up through the outer `try!` and aborts the *entire* proposal transaction — none of the cap-setting, interest-rate-curve, egroup-registration, or `set-authorized-contract` (market authorization) steps for **any** vault in that same proposal execute either, since Clarity contract-call transactions are atomic.

### Impact Explanation
This is a temporary freezing of funds/functionality: the affected vault(s) are left with the market unauthorized, supply/debt caps unset (effectively zero), and no interest-rate curve configured, since the DAO's single atomic launch proposal reverted. Users cannot deposit (capped at 0) or the market cannot mediate borrow/collateral operations against that vault until the DAO detects the failure and deploys a corrected proposal (one that skips the already-completed `initialize` call). This directly parallels the referenced Hats Finance finding where an unprivileged user calling `stake()`/`initialize`-equivalent state-mutating function before the privileged setup step causes downstream configuration calls to permanently fail for that deployment attempt.

### Likelihood Explanation
High likelihood: `initialize()` is a plain public function with no auth check, callable by any address that can source the small `MINIMUM-LIQUIDITY` amount of the underlying token, and vault contract addresses/deployment order are typically observable/predictable on a public mempool before the DAO's proposal is submitted or mined.

### Recommendation
Add `(try! (check-dao-auth))` to `initialize()` in every `v0-vault-*` contract, consistent with all other privileged administrative setters in the same files, so only the DAO (via proposal execution) can trigger initialization.

### Proof of Concept
1. Vault `v0-vault-usdc` is deployed but not yet initialized; the DAO's `v0-init` proposal has not yet been submitted/mined.
2. An attacker (any unprivileged principal) acquires `MINIMUM-LIQUIDITY` units of USDC-equivalent underlying token and calls `(contract-call? .v0-vault-usdc initialize)` directly.
3. `initialize()` executes successfully: `initialized` is set to `true`, `MINIMUM-LIQUIDITY` shares are minted to `NULL-ADDRESS` [1](#0-0) .
4. The DAO later submits `v0-init`'s `execute`, which calls `(try! (contract-call? .v0-vault-usdc initialize))` as part of its atomic setup sequence [3](#0-2) .
5. That call returns `(err ERR-ALREADY-INITIALIZED)`, the enclosing `try!` propagates the error, and the entire `execute` transaction reverts — caps, interest-rate curves, egroups, and market authorization for the vault(s) covered by that proposal are never applied, leaving the vault non-functional until the DAO redeploys a corrected proposal.

(define-public (initialize)
  (begin
    (asserts! (not (var-get initialized)) ERR-ALREADY-INITIALIZED)
    (var-set initialized true)
    (try! (deposit MINIMUM-LIQUIDITY u0 NULL-ADDRESS))
    
    (print {
      action: "vault-initialize",
      caller: contract-caller,
      data: {
        vault: UNDERLYING,
        minimum-liquidity: MINIMUM-LIQUIDITY
      }
    })
    
    (ok true)))
