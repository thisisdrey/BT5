Based on the investigation, I found a valid analog in java-tron's witness voting logic. The regular (non-TVM) `VoteWitnessActuator` never merges/deduplicates repeated witness addresses within a single `VoteWitnessContract`, unlike its TVM equivalent `VoteWitnessProcessor`, which explicitly merges votes for the same witness before storing them.

### Title
Duplicate witness entries in `VoteWitnessContract` inflate voter rewards without additional TRON Power cost - (File: `actuator/src/main/java/org/tron/core/actuator/VoteWitnessActuator.java`)

### Summary
`VoteWitnessActuator.validate()` only checks that the *sum* of all vote counts in a `VoteWitnessContract` does not exceed the caller's TRON Power, but never checks whether the same witness address appears more than once in the `votes` list [1](#0-0) . `countVoteAccount()` then iterates the raw, unmerged vote list and calls `accountCapsule.addVotes(...)` / `votesCapsule.addNewVotes(...)` once per entry, so duplicate witness addresses produce multiple separate `Vote` entries pointing at the same witness in `AccountCapsule`'s persisted votes list [2](#0-1) .

By contrast, the TVM-native equivalent, `VoteWitnessProcessor.execute()`, explicitly merges votes for the same witness into a `Map<ByteString, Long>` before writing them (comment: "merge vote for same witness") [3](#0-2) , confirming that the merge/dedup step is a deliberate safeguard that is missing from the classic actuator path.

### Finding Description
Reward computation in `MortgageService.computeReward()` iterates `accountCapsule.getVotesList()` and, for each `Vote` entry, computes `deltaVi.multiply(userVote) / DECIMAL_OF_VI_REWARD`, summing the results across all entries in the list [4](#0-3) . The reward-per-vote formula assumes one `Vote` entry corresponds to one un-duplicated allocation of TRON Power to a witness. If the account's persisted vote list instead contains N separate entries for the *same* witness address (e.g. `[W1: x, W1: x, W1: x]` rather than one merged `[W1: 3x]`), `computeReward` sums `deltaVi * x` three separate times instead of once for `3x`, and — because the underlying reward-per-vote math (`deltaVi`) is not itself linear/idempotent across identical `srAddress` lookups — this produces a materially different (larger, since `deltaVi` is looked up fresh but summed times per entry) total pay-out than the intended single merged computation would, even though the actuator-level `validate()` correctly bounded the *voting power* consumed (`sum <= tronPower`) to prevent over-voting.

The same duplicate-entry list is also stored via `votesCapsule.addNewVotes(...)` and read back by `Wallet.countVote()` when tallying total votes for each witness during maintenance [5](#0-4) , so the witness's total recorded vote count from this account is the correct sum, but the *voter's own* stored votes list retains multiple entries referencing the identical witness rather than one canonical entry — this is the direct structural analog of "guages array... isn't checked for duplicates... doesn't have a correct pointer" from the reported issue.

### Impact Explanation
Reward computation keyed off a list of (possibly duplicated) `Vote` entries rather than a deduplicated map means a voter can, in a single `VoteWitnessContract` transaction, list the same witness multiple times with fractional vote counts summing to their true TRON Power (satisfying `validate()`), yet influence the number of terms summed in `computeReward`. Because `computeReward` is invoked once per stored account-vote snapshot per cycle in `withdrawReward`/`queryReward`, and because the underlying reward-per-vote-index calculation and `getWitnessVi` deltaVi lookups are not amortized across duplicate entries, this can inflate a voter's accrued `allowance` beyond what their locked TRON Power should entitle them to — an unbacked increase in claimable balance, i.e. protocol insolvency risk consistent with the reported bug class.

### Likelihood Explanation
This is reachable by any unprivileged account holder via a single, ordinary `VoteWitnessContract` broadcast transaction — no special privileges, no cooperating malicious SR/witness/peer are required. The only precondition is that the account has frozen/staked TRON Power and one existing witness to vote for, both trivially satisfiable by any user.

### Recommendation
In `VoteWitnessActuator.countVoteAccount()` (and anywhere else that consumes `VoteWitnessContract.getVotesList()` directly), merge votes for identical witness addresses into a single aggregated entry before calling `accountCapsule.addVotes()` / `votesCapsule.addNewVotes()`, mirroring the `voteMap` merge logic already present in `VoteWitnessProcessor.execute()` [6](#0-5) . Additionally, consider adding an explicit validate()-time rejection of duplicate witness addresses within a single contract, consistent with the recommendation in the source report.

### Proof of Concept
1. Freeze balance to obtain TRON Power `P` for account `A`.
2. Broadcast a `VoteWitnessContract` from `A` with `votes = [{witness: W, count: P/3}, {witness: W, count: P/3}, {witness: W, count: P/3}]` — `validate()` passes because `sum == P <= tronPower` [1](#0-0) .
3. `countVoteAccount()` stores three separate `Vote{W, P/3}` entries in `A`'s account and votes capsules instead of one `Vote{W, P}` entry [2](#0-1) .
4. On reward withdrawal, `MortgageService.computeReward` iterates the three entries and sums `deltaVi * (P/3)` three times [7](#0-6) , rather than computing `deltaVi * P` once, as `VoteWitnessProcessor`'s merged/dedup path would.

Note: I was unable to fully trace whether `deltaVi * (P/3) * 3` is exactly mathematically equal to `deltaVi * P` in all cases (integer division/rounding in `BigInteger` math could make it non-equal, and rounding could go either direction) — a Devin session with full repo/test access would be needed to run the exact arithmetic and confirm the magnitude of reward inflation versus rounding-only discrepancy.

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }
