### Title
Permanent freeze of ETH-implicit accounts via stuck `has_in_flight_tx` flag with no recovery path - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The Wallet Contract (NEP-518) that every ETH-implicit account is deployed with uses a boolean re-entrancy guard, `has_in_flight_tx`, to serialize Ethereum-emulated transactions. This flag is set to `true` by `rlp_execute` before firing off a cross-contract promise, and is only ever reset to `false` inside the corresponding private callback (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`). There is no governance/owner override, no timeout, and — per protocol rules — an ETH-implicit account can never receive a full-access key or be deleted, so if the callback that must clear the flag never successfully commits, the account (and any funds/tokens it holds) is permanently unusable. This mirrors the GasThrottle report's core flaw: a hard gate with no way to disable or recover once it gets stuck in the "blocking" state.

### Finding Description
`rlp_execute` enforces "one in-flight tx at a time": [1](#0-0) 

Every path that sets `has_in_flight_tx = true` does so by returning a `Promise` chain that ends in one of the `#[private]` callbacks, and only those callbacks reset the flag to `false`, always as the very first statement: [2](#0-1) [3](#0-2) [4](#0-3) 

On NEAR, contract state changes made by a function-call receipt are only persisted if that receipt's execution finishes without aborting (out-of-gas, `env::panic_str`, deserialization panic, or a host error). The callback gas budgets are static, hard-coded constants computed at the time the *originating* call is made (e.g. `RLP_EXECUTE_CALLBACK_GAS`, `ADDRESS_CHECK_CALLBACK_GAS`, `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`): [5](#0-4) 

If the resetting callback ever fails to commit — e.g. it runs out of the pre-allocated static gas while processing an attacker-influenced payload (large `promise_result` bytes to deserialize via `serde_json::from_slice`, a large refund/transfer chain, or any other host abort inside the callback body) — the receipt fails, the callback's state mutation (`has_in_flight_tx = false`) is never applied, and the *previously-committed* `has_in_flight_tx = true` (set by the call that scheduled this callback) remains permanently on the account. There is no admin key, no governance call, and no other method on `WalletContract` capable of clearing this flag; `rlp_execute` immediately short-circuits to an error whenever `has_in_flight_tx` is `true`: [6](#0-5) 

Because ETH-implicit accounts can never be deleted or upgraded with a full-access key, this is unrecoverable at the protocol level: [7](#0-6) 

This is structurally identical to the GasThrottle analog: a hard-coded, unprivileged, deployment-time gate (`validateGas`/`has_in_flight_tx`) that can end up permanently "stuck closed" with no governance/owner path to reset it, and — unlike GasThrottle where only swaps fail — here the entire account (including its NEAR balance and any NEP-141/NEP-141-style assets routed through it) becomes permanently inaccessible.

### Impact Explanation
Once `has_in_flight_tx` is stuck `true`, the affected ETH-implicit account can never again execute `rlp_execute`, meaning all subsequent transfers, function calls, or key management for that account permanently fail. Since ETH-implicit accounts cannot be deleted or have a full-access key added, any NEAR tokens or contract state controlled by that account (and any tokens sent to it afterward) are permanently frozen — this satisfies the "permanent freezing of funds" bar.

### Likelihood Explanation
Triggering this requires making one of the reset callbacks (`address_check_callback`, `nep_141_storage_balance_callback`, or `rlp_execute_callback`) exceed its statically-computed gas allowance or otherwise abort before it finishes. Because a relayer (an ordinary, unprivileged NEAR account) fully controls the RLP-encoded Ethereum transaction bytes and the `target`/`tx_bytes_b64` arguments passed into `rlp_execute`, and because gas costs for JSON/RLP parsing and cross-contract data scale with attacker-supplied input (e.g. the `Option<AccountId>`/`StorageBalance` bytes deserialized in the registrar/NEP-141 callback paths, or a target contract crafted to return an oversized/expensive-to-parse promise result), a motivated attacker (or even a relayer's own faulty configuration) can likely construct inputs that cause the resetting callback to run out of gas or otherwise abort, permanently bricking a victim's ETH-implicit account. This does not require any privileged role — a normal transaction signer/relayer is sufficient.

### Recommendation
- Add an unprivileged or time-based recovery path (e.g. allow `has_in_flight_tx` to be cleared after a bounded number of blocks/height, similar to a timeout) so a stuck flag can be self-healed rather than being permanent.
- Reserve a fixed minimum gas margin independent of attacker-controlled payload size for the portion of each callback that resets `has_in_flight_tx`, ensuring the flag write always has a chance to commit even if downstream logic in the same callback aborts.
- Consider resetting `has_in_flight_tx` as an unconditional, first, minimal-gas action refunded/finalized via a separate cheap promise, decoupled from the potentially expensive parsing/refund logic that follows.

### Proof of Concept
1. Create an ETH-implicit account and fund it (per `test_eth_implicit_account_creation`/`test_wallet_contract_interaction` in `runtime/near-wallet-contract/implementation/wallet-contract/src/tests` and `integration-tests/src/tests/features/wallet_contract.rs`).
2. Have a relayer call `rlp_execute` with a transaction whose `target` is an NEP-141 token contract crafted (or configured) to return an oversized `storage_balance_of` response, so that `nep_141_storage_balance_callback`'s `serde_json::from_slice` deserialization plus the subsequent promise construction exceeds `NEP_141_STORAGE_BALANCE_CALLBACK_GAS` (a fixed 5+5+5 Tgas budget): [8](#0-7) 
3. `rlp_execute` (step in `inner_rlp_execute`) sets and commits `has_in_flight_tx = true` before the callback executes: [9](#0-8) 
4. The scheduled `nep_141_storage_balance_callback` receipt aborts (out of gas) before it can execute `self.has_in_flight_tx = false` — because it aborted, that state write is never committed.
5. All future `rlp_execute` calls on this account now immediately return the "transaction already in progress" error, and — per protocol rules — this ETH-implicit account can never be deleted or granted a full-access key, so the account and its held balance are permanently frozen.
