### Title
Health/liquidation checks use stale, un-accrued `asset_share_value`/`liability_share_value` for collateral/debt banks not actively touched in the current instruction - ([File: programs/marginfi/src/state/marginfi_account.rs])

### Summary
Marginfi's risk engine values every position in `get_health_components` by reading each bank's cached `asset_share_value` / `liability_share_value` directly, without accruing interest for that bank first. Only the bank(s) explicitly touched by the current instruction (e.g. the bank being withdrawn from or borrowed against) have `accrue_interest` invoked before the health check runs. Every other bank referenced through `remaining_accounts` (i.e., all of the user's *other* collateral/debt positions) is priced using whatever `asset_share_value`/`liability_share_value` happened to be last written on-chain, which can be arbitrarily stale if nobody has interacted with (or permissionlessly accrued) that bank recently. This is the same bug class as the Morpho report: a risk/health computation that iterates over all of a user's positions can be fooled by stale per-market interest indexes when some markets have not been "touched" recently.

### Finding Description
`get_health_components` [1](#0-0)  iterates over all active balances of a `MarginfiAccount` and, for each one, loads the corresponding `Bank` via `AccountLoader` and computes its weighted value from the bank's current `asset_share_value`/`liability_share_value` fields (via `calc_weighted_value_for_balance` / `calc_weighted_asset_value_cached_standalone`) [2](#0-1) . Nowhere in this loop is `Bank::accrue_interest` called for the banks being priced.

`Bank::accrue_interest` only updates `asset_share_value`/`liability_share_value` when it is explicitly invoked, and only if `time_delta != 0` since `last_update` [3](#0-2) . As the project's own docs state: "Interest accumulates when any transaction that changes funds occurs, so banks without much activity may have stale numbers until someone interacts with them" [4](#0-3) .

Each risky instruction (`withdraw`, `borrow`, `liquidate`) only accrues interest for the bank(s) directly involved in that instruction, then runs a health check that spans *all* of the account's balances via `remaining_accounts`:
- `lending_account_withdraw` accrues interest only for `bank` (the bank being withdrawn from) [5](#0-4) , then calls `check_account_init_health` over the full `remaining_accounts` set representing every other position [6](#0-5) .
- `lending_account_liquidate` accrues interest only for `asset_bank` and `liab_bank` [7](#0-6)  before calling `check_pre_liquidation_condition_and_get_account_health`, which prices every other balance from `liquidatee_remaining_accounts` without accruing those banks [8](#0-7) .
- `check_account_init_health` (used by `borrow`) similarly runs `get_health_components` over all remaining accounts without any interest accrual step [9](#0-8) .

Because `liability_share_value` is monotonically non-decreasing (debt compounds), a stale value *understates* a user's true liability. Because `asset_share_value` is also monotonically non-decreasing, a stale value *understates* a user's true collateral. The net effect on health (`assets - liabilities`) depends on which side of the user's book the stale bank falls: a user with debt concentrated in a bank that hasn't been touched (and whose real accrued interest would push them underwater) will look artificially healthier than they actually are, because the stale, lower `liability_share_value` undercounts the debt used in the health check.

### Impact Explanation
If a user's debt is concentrated in a bank that has not had interest accrued recently (a bank that is low-traffic or momentarily idle), that bank's `liability_share_value` on-chain understates the real, currently-accruing debt. Health checks performed via `check_account_init_health` (borrow/withdraw) or `check_pre_liquidation_condition_and_get_account_health` (liquidation) reference this stale, understated liability value for that bank rather than the actual (higher) debt. This can:
- Allow a user to withdraw collateral or borrow more against other banks while their real (unaccrued) health is already negative, directly risking protocol insolvency/bad debt.
- Prevent a liquidator from liquidating an account that is truly insolvent, because `_isLiquidatable`-equivalent logic (`check_pre_liquidation_condition_and_get_account_health`) computes health using the stale liability value and returns `HealthyAccount`, blocking the liquidation transaction entirely.

This directly maps to the "Accept only concrete theft, unauthorized transfer, insolvency/bad debt" bar in the rules, since it can produce genuine insolvency/bad debt via mispriced (stale) debt escaping timely liquidation, and unauthorized withdraw/borrow beyond real collateralization.

### Likelihood Explanation
Likelihood is Medium. It requires:
1. A bank with meaningful debt for the target account that has not been "touched" (deposit/withdraw/borrow/repay/permissionless `LendingPoolAccrueBankInterest`) for enough time that the accrued-but-uncommitted interest is material relative to the account's health buffer.
2. An account whose real-time health (with correctly accrued interest) is negative, but whose on-chain cached health (using the stale bank) still shows positive.

Since `LendingPoolAccrueBankInterest` is permissionless [10](#0-9) , any liquidator that anticipates this and crafts/watches for the right window can front-run by accruing interest on the debt bank first (as tests already do, e.g., `accrueInterest` is invoked immediately before `liquidateIx` in test helpers [11](#0-10) ), mitigating but not eliminating the window in which a borrower can act on stale collateral/debt state for banks other than the one they are actively interacting with.

### Recommendation
Consider accruing interest for every bank referenced in `remaining_accounts` (not just the bank being actively deposited/withdrawn/borrowed/liquidated) immediately before computing health in `get_health_components`, `check_account_init_health`, and `check_pre_liquidation_condition_and_get_account_health`. Given the gas/CU sensitivity documented in the risk-engine's heap-reuse design, an alternative is to compute a "live" projected share value on-the-fly during health pricing (analogous to a view-only accrual) rather than mutating and persisting bank state, so health/liquidation decisions always reflect current, not stale, indexes without requiring a separate accrual instruction.

### Proof of Concept
Conceptual sequence (cannot be executed without a live network, but derivable directly from the code paths cited above):
1. Alice deposits SOL as collateral in `bank_collateral`, and borrows USDC from `bank_debt`.
2. `bank_debt` is not touched by any other user for an extended period (no deposit/withdraw/borrow/repay on it), so its `liability_share_value` remains fixed at its old (stale) value even though real-world interest is accruing at whatever rate `interest_rate_config` dictates.
3. SOL price drops such that, with the true (currently accruing) USDC debt, Alice's account is now underwater and should be liquidatable.
4. A liquidator calls `lending_account_liquidate` targeting `bank_collateral` as asset bank and a *different* bank than `bank_debt` (or the liquidator omits accruing `bank_debt` because it is not one of `asset_bank`/`liab_bank` for this particular liquidation attempt against another liability bank Alice also has), so `bank_debt`'s stale, understated liability is used in `check_pre_liquidation_condition_and_get_account_health` [12](#0-11) . Because computed `account_health` is (incorrectly) still `> 0`, the call reverts with `MarginfiError::HealthyAccount`, blocking the liquidation.
5. Alice can continue to withdraw remaining collateral via `lending_account_withdraw` before anyone permissionlessly accrues `bank_debt`, since `check_account_init_health` reuses the same stale-liability computation, allowing her to extract value the protocol will never fully recover, producing bad debt once `bank_debt` interest is finally accrued.

pub fn check_pre_liquidation_condition_and_get_account_health<'info>(
    marginfi_account: &MarginfiAccount,
    remaining_ais: &'info [AccountInfo<'info>],
    liability_bank_pk: Option<&Pubkey>,
    health_cache: &mut Option<&mut HealthCache>,
    price_mode: HealthPriceMode<'_>,
    ignore_healthy: bool,
) -> MarginfiResult<(I80F48, I80F48, I80F48)> {
    check!(
        !marginfi_account.get_flag(ACCOUNT_IN_FLASHLOAN),
        MarginfiError::AccountInFlashloan
    );

    if let Some(bank_pk) = liability_bank_pk {
        let lending_account = &marginfi_account.lending_account;
        let liability_balance = lending_account
            .balances
            .iter()
            .find(|b| b.is_active() && b.bank_pk == *bank_pk)
            .ok_or(MarginfiError::LendingAccountBalanceNotFound)?;

        check!(
            !liability_balance.is_empty(BalanceSide::Liabilities),
            MarginfiError::NoLiabilitiesInLiabilityBank
        );

        check!(
            liability_balance.is_empty(BalanceSide::Assets),
            MarginfiError::AssetsInLiabilityBank
        );
    }

    // Get health components using heap reuse
    let (assets, liabs) = get_health_components(
        marginfi_account,
        remaining_ais,
        RequirementType::Maintenance,
        health_cache,
        price_mode,
    )?;

    let account_health = assets.checked_sub(liabs).ok_or_else(math_error!())?;
    let healthy = account_health > I80F48::ZERO;

    if let Some(cache) = health_cache.as_mut() {
        cache.set_healthy(healthy);
    }

    if healthy && !ignore_healthy {
        msg!(
            "pre_liquidation_health: {} ({} - {})",
            account_health,
            assets,
            liabs
        );
        return err!(MarginfiError::HealthyAccount);
    }
