Any single stale/broken oracle among a user's held collateral or debt assets causes `unwrap-panic`-based revert of `borrow`, `collateral-add`, and `collateral-remove` for that user, freezing unrelated healthy assets - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`get-assets`, used by `borrow`, `collateral-add`, and `collateral-remove` to fetch prices for a user's *entire* position mask (not just the asset being manipulated), resolves prices via `(unwrap-panic (price-multi-resolve oracles-list asset-ids))`. If any single asset in the user's position mask has an oracle that fails freshness/validity checks, `price-multi-resolve` returns `(err ERR-ORACLE-MULTI)` and the `unwrap-panic` aborts the entire transaction — even when the asset the user is actually trying to act on (e.g. repay-adjacent collateral top-up, or removing collateral from a *different, healthy* asset) has nothing to do with the broken oracle.

### Finding Description
`get-assets` is defined as: [1](#0-0) 

It is invoked with the user's full position `mask` (all currently held collateral + debt asset IDs), not merely the single asset being deposited/withdrawn/borrowed, in:
- `borrow`: `(assets (get-assets mask))` where `mask` is the user's full position mask [2](#0-1) 
- `collateral-remove` (when the position has debt): calls `(get-assets position-mask)` over the full position mask [3](#0-2) 
- `collateral-add` (when adding a new collateral asset and user has existing debt): calls `(get-assets current-mask)` [4](#0-3) 

Internally, `price-multi-resolve` folds over every asset in that mask and marks the whole batch invalid the moment any single asset's `price-resolve` fails (stale timestamp, non-positive price, oracle callcode failure, unsupported oracle type, etc.): [5](#0-4) 

`get-assets` then does `(unwrap-panic (price-multi-resolve oracles-list asset-ids))` — an `unwrap-panic`, not a graceful `try!`/`asserts!` with a recoverable error code — so a single bad oracle among the user's *unrelated* assets aborts the entire call with a runtime panic: [1](#0-0) 

This is structurally identical to the referenced Kintsu bug class: a batch/aggregate operation over multiple linked sub-entities (there: nomination-agent → pool; here: user-position → per-asset oracle) where *any one* sub-entity being in a bad state (destroying/blocked pool ↔ stale/invalid oracle) causes the entire aggregate operation to revert via an unconditional unwrap, denying service on entities that are themselves perfectly fine.

### Impact Explanation
A user who holds collateral or debt in ≥2 assets can be completely locked out of managing their position — even for the healthy assets — as soon as any single asset they are exposed to has its oracle go stale (e.g., publisher outage, feed staleness threshold exceeded, callcode dependency failure such as `call-ststx-ratio`). Concretely:
- They cannot `collateral-remove` from a healthy, over-collateralized asset to de-risk.
- They cannot `borrow` more against healthy collateral.
- They cannot `collateral-add` a new asset while carrying debt.

This is a temporary freezing of funds/positions: the user's ability to manage or reduce risk on unrelated, healthy assets is blocked for the duration of the outage on one unrelated oracle, which can be an arbitrarily long external condition. `repay` is unaffected (it does not call `get-assets`), so this is not a full DoS but a targeted freeze of collateral-management and borrow paths tied to any co-held asset with a broken oracle.

### Likelihood Explanation
Oracle staleness/failure is a routine operational condition (feed downtime, sequencer lag, third-party callcode dependency like the stSTX ratio contract failing) and does not require any attacker action — it is triggered passively any time a user's diversified position includes an asset whose oracle degrades. Any user holding multiple collateral/debt assets is exposed; no privileged action or malicious input is required, only normal multi-asset usage plus an external oracle hiccup on any one of those assets.

### Recommendation
In `get-assets`, replace the outer `unwrap-panic` around `price-multi-resolve` with a scoped, per-caller recoverable error (e.g. `try!`) so callers can surface `ERR-ORACLE-MULTI` normally, and consider restricting the price-resolution surface in `borrow`/`collateral-add`/`collateral-remove` to only the assets actually required for the health check of the touched asset plus assets with existing debt, rather than the user's entire enabled mask — or provide a fallback/"skip-and-flag" path (mirroring the Kintsu fix of skipping bad pools) so a single broken oracle among many held assets does not block operations on the rest of a diversified position.

### Proof of Concept
1. User A supplies collateral in asset X (e.g. sBTC vault) and separately supplies collateral in asset Y (e.g. USDC vault) with no debt yet, then borrows against X, giving them a position mask covering both X (collateral) and the borrowed debt asset.
2. Asset Y's oracle feed becomes stale (exceeds its configured `max-staleness`) or its callcode dependency (e.g. `call-ststx-ratio`) starts failing — a condition entirely external to User A and unrelated to asset X.
3. User A calls `collateral-remove` to withdraw some of their over-collateralized X position (position remains healthy without needing Y's price at all in principle).
4. `collateral-remove` computes `position-mask` including Y, calls `get-assets(position-mask)` → `price-multi-resolve` iterates Y's oracle data → `price-resolve` fails on Y (stale/invalid) → `iter-price-multi` sets `valid: false` → `price-multi-resolve` returns `(err ERR-ORACLE-MULTI)` → `get-assets`'s `unwrap-panic` panics, aborting the whole `collateral-remove` transaction.
5. User A is unable to withdraw any collateral from the healthy asset X, or to `borrow` further against it, or to `collateral-add` new collateral, for as long as Y's oracle remains broken — despite having no exposure risk tied to X.

(define-private (price-multi-resolve
  (data (list 64 { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (aids (list 64 uint)))
  (let ((init { output: (list), valid: true, aids: aids, idx: u0 })
        (response (fold iter-price-multi data init)))
    (asserts! (get valid response) ERR-ORACLE-MULTI)
    (ok (get output response))))
