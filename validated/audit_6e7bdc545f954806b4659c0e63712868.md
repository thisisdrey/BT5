### Title
HTTP Request Smuggling via bare-LF line-terminator acceptance in vendored httparse (CVE-2019-16785 analog) - (File: `stacks-common/src/deps_common/httparse/mod.rs`)

### Summary
The Stacks node's HTTP preamble parser (used by the RPC HTTP server, e.g. `/v2/*` endpoints) is built on a vendored fork of `httparse` that still implements the RFC 7230 §3.5 "MAY" clause: a bare `\n` (LF) is accepted as a full line terminator everywhere a `\r\n` (CRLF) is expected — in the request/status line, in header-name/value termination, and in the empty-line-skip logic. This is exactly the parsing ambiguity that caused CVE-2019-16785 in Waitress, which was fixed by rejecting bare LF outright (returning 400) starting in Waitress 1.4.0.

### Finding Description
The `newline!` macro accepts either `\r\n` or a solitary `\n`: [1](#0-0) 

The same dual-acceptance repeats in the empty-line skipper used before the request line: [2](#0-1) 

...in the header-block terminator check: [3](#0-2) 

...and in the header-value terminator, which is the exact code path that lets a header value be truncated at a bare `\n`, letting the following bytes be re-interpreted as a brand-new header line: [4](#0-3) 

This parser is invoked directly by `HttpRequestPreamble::consensus_deserialize`, which is the entry point for every inbound RPC HTTP request the node accepts: [5](#0-4) 

The equality that this breaks is: *"the byte stream the front-end/reverse-proxy parsed as N header lines equals the byte stream the Stacks node parses as N header lines."* Any front-end proxy that treats a lone `\n` inside a header value as *data* (not a line break) — which is standard/strict CRLF-only behavior for many HTTP implementations — will see a single header line, while this backend will see two. That is the textbook definition of the request-smuggling primitive described in the advisory: `Content-Length: 100\r\nX-Header: x\nContent-Length: 0\r\n` is treated by this parser as two separate header lines, exactly as in the Waitress example.

Note that `HttpRequestPreamble::consensus_deserialize` does reject *duplicate* headers of the same name once parsed: [6](#0-5) 
This blocks the literal "duplicate Content-Length" reproduction from the advisory, but it does not close the underlying parsing-disagreement primitive for non-colliding header names (e.g., smuggling an extra `Connection:`, `Transfer-Encoding:`-adjacent, or `Host:`-like header, or splitting a single logical value into what the backend treats as two distinct header lines while the front-end treats it as one line with an embedded LF).

### Impact Explanation
This falls under the "request smuggling" impact category called out in scope: when the node sits behind a reverse proxy/load balancer for its RPC HTTP interface, a remote unauthenticated attacker can craft a request whose header block is interpreted differently by the front-end proxy than by the Stacks node itself, enabling smuggling of an extra logical HTTP request or header into the pipeline that the front-end never inspected/filtered. This can be used to bypass proxy-level access controls, cache poisoning, or splitting requests across the keep-alive connection between proxy and node.

### Likelihood Explanation
Likelihood is topology-dependent: it requires the node's RPC endpoint to be fronted by a reverse proxy that itself is strict about CRLF (the common case for hardened deployments, e.g. modern nginx/Envoy), while the Stacks node remains lenient. This exact mismatch (lenient backend behind strict/differently-lenient front-end) is precisely the root cause class in the referenced Waitress CVE, and no authentication or privileged position is needed — a single crafted HTTP request suffices.

### Recommendation
Harden the vendored `httparse` fork in `stacks-common/src/deps_common/httparse/mod.rs` the same way upstream `httparse`/Waitress did: reject any bare CR or bare LF encountered where a CRLF is required (request/status line terminator, header-name/value terminator, empty-line skip) and return a parse error (mapped to an HTTP 400) instead of silently treating a lone LF as a valid line terminator. This should be applied consistently to `newline!`, `skip_empty_lines`, `parse_headers_iter`'s header-value/header-block termination checks.

### Proof of Concept
Send (or use `HttpRequestPreamble::consensus_deserialize` directly, mirroring the existing test harness style in `stackslib/src/net/http/tests.rs`) a raw preamble such as:
```
POST /v2/transactions HTTP/1.1\r\n
Host: node:20443\r\n
Content-Length: 4\r\n
X-Foo: bar\nX-Injected: smuggled\r\n
\r\n
```
`req.parse(&buf_read)` (called from `HttpRequestPreamble::consensus_deserialize`, `stackslib/src/net/http/request.rs:302`) will parse `X-Foo: bar` and `X-Injected: smuggled` as two separate, independently-parsed headers, because the header-value terminator logic at `stacks-common/src/deps_common/httparse/mod.rs:795-807` accepts the bare `\n` after `bar` as a full line break. A front-end proxy that does not treat `\n` alone as a line terminator will instead see one header (`X-Foo: bar\nX-Injected: smuggled`), producing exactly the parsing divergence needed for request smuggling.
