### Title
Out-of-bounds pre-buffer read when locating the Zip64 End-of-Central-Directory locator in `InputJar::LocateCentralDirectory` - (File: `src/tools/singlejar/input_jar.cc`)

### Summary
`singlejar`'s `InputJar` mmaps an entire input jar/zip file and, when parsing the End-of-Central-Directory (ECD) record, unconditionally subtracts `sizeof(ECD64Locator)` (and, if that "looks" valid, `sizeof(ECD64)`) from the ECD pointer to look for the optional Zip64 locator/record, without ever checking that the resulting pointer stays within the mapped buffer. A crafted, minimal zip/jar file can place a fake ECD signature near the very start of the mapped region, causing the code to dereference memory *before* `mapped_file_.start()` — the same "pre-buffer read" bug class as CVE-2025-11000 (Open Babel's PQS `lowerit`).

### Finding Description
`InputJar::Open` maps a whole file into memory and requires only `size() >= sizeof(ECD)` before calling `LocateCentralDirectory` [1](#0-0) .

`LocateCentralDirectory` scans backward from `end() - sizeof(ECD)` down to `ecd_min`, which is clamped to `mapped_file_.start()` for small files, and stops at the *first* (highest-offset) 4-byte match of the ECD signature `0x06054b50` [2](#0-1) . Because the attacker fully controls the file bytes, they can make this match occur at a very small offset `O` from the start of the mapped buffer (as low as `O = 1`) by ensuring no other signature-matching bytes exist elsewhere in the (tiny) file.

Once `ecd` is found, the code validates `cen_size <= mapped_file_.offset(ecd)` (i.e. `cen_size <= O`) but only when `cen_size != 0` do we enter the branch that computes:
```
auto ecd64loc = reinterpret_cast<const ECD64Locator*>(ziph::byte_ptr(ecd) - sizeof(ECD64Locator));
if (ecd64loc->is()) { ... }
``` [3](#0-2) 

`sizeof(ECD64Locator)` is 20 bytes. If `O < 20` (which is achievable, e.g. `O` in `[1, 19]` with `cen_size` in `[1, O]` to satisfy the earlier check), then `ziph::byte_ptr(ecd) - sizeof(ECD64Locator)` produces a pointer at offset `O - 20`, i.e. strictly before `mapped_file_.start()`. The code immediately dereferences this pointer via `ecd64loc->is()`, which reads the (packed) `ECD64Locator` signature field — an out-of-bounds *pre-buffer* read of up to 20 bytes before the start of the mapped region.

Crucially, `MappedFile::mapped()` — the only bounds-check helper available — is never called on `ecd64loc` (or on `ecd64` in the branch that follows, which subtracts a further `sizeof(ECD64)` and an attacker-controlled `cen_size()` value) [4](#0-3) . All bounds checks in this function (`mapped_file_.mapped(...)`, the `cen_size > offset(ecd)` check) only look "forward" (validating the central-directory-offset/size against the *end* of the mapped region relative to `ecd`); none of them protect against reading backward past `mapped_start_`.

### Impact Explanation
This is a memory-safety violation (CWE-125, out-of-bounds read) in a native C++ tool (`singlejar`) that Bazel invokes as part of normal build actions (e.g., assembling deploy jars from `java_binary`/`java_import` dependency jars). `singlejar` inputs can originate from external dependencies fetched via `http_jar`/`http_archive`/Maven-style rules — content controlled by a third party the build consumes, matching the "unprivileged attacker publishes/serves content the victim's build consumes" threat model. Reading memory immediately preceding an `mmap`'d region can crash the process (SIGSEGV, if the preceding page is unmapped — a build-time denial of service for that action) or, depending on memory layout/allocator behavior, read adjacent heap/mapping content into a check whose result influences subsequent parsing.

### Likelihood Explanation
Exploitation requires only a small, fully attacker-crafted zip/jar file (well under 100 bytes) with the ECD signature planted near the start of the file and a small nonzero `cen_size` field; no other data or valid zip structure is required. There is no checksum/integrity gate inside `singlejar` itself that would inspect the byte layout at this granularity — `sha256`/`integrity` attributes on `http_archive`/`http_jar` protect the *whole file's* hash, not its internal structural validity, so a byte-for-byte pinned-but-malicious jar with a matching checksum would still trigger this bug. The bug is deterministic given a suitably small offset, not a race or timing-dependent condition.

### Recommendation
In `InputJar::LocateCentralDirectory`, before dereferencing `ecd64loc` or `ecd64`, verify with `mapped_file_.mapped(ecd64loc)` (and `mapped_file_.mapped(ecd64)`) that the computed pointer — and ideally the full struct extent — lies within `[mapped_file_.start(), mapped_file_.end())`. If not, treat the file as corrupt and fail closed (as is already done for the other corruption cases in this function) rather than dereferencing an out-of-bounds pointer.

### Proof of Concept
A `BuildIntegrationTestCase`/C++ unit test analogous to the existing `InputJarPreambledTest` suite would:
1. Construct an in-memory buffer of ~23–40 bytes consisting of: a few bytes of padding (offset `0..O-1`), followed at offset `O` (with `1 <= O < 20`) by a well-formed `ECD` struct with `signature = 0x06054b50`, `cen_size` set to a nonzero value `<= O` and not `0xFFFFFFFF`, and `cen_offset` consistent with the `mapped_file_.mapped(...)` check.
2. Call `InputJar::Open(path, data, length)` (the in-memory `Open` overload used by tests such as `input_jar_preambled_test.cc`) on this buffer.
3. Run under AddressSanitizer; observe a heap-buffer-underflow / global-buffer-underflow report on the `ecd64loc->is()` dereference in `LocateCentralDirectory`, confirming the pre-buffer read before `mapped_file_.start()`.
