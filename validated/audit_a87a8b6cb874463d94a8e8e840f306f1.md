### Title
Attacker can fill a victim's `depositTokensOfAccount`/`debtTokensOfAccount` list via dust transfers of `DepositToken`s, blocking the victim from issuing new synthetic debt or receiving new collateral types - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool` caps the combined number of deposit tokens and debt tokens an account may interact with at `MAX_TOKENS_PER_USER = 30` via `onlyIfAdditionWillNotReachMaxTokens`. `DepositToken._transfer` unconditionally registers the recipient in `depositTokensOfAccount` whenever their balance goes from 0 to positive. An unprivileged attacker can deposit minimum amounts of every listed collateral and `transfer` 1-wei dust of each `DepositToken` to a victim, filling the victim's 30-slot list. Any subsequent `DepositToken.deposit`/`transfer` of a *new* token type to the victim, and any `DebtToken.issue/mint/flashIssue` of a synthetic the victim does not already hold, reverts with `UserReachedMaxTokens`.

### Finding Description
- `Pool.onlyIfAdditionWillNotReachMaxTokens` reverts when `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= 30` (`Pool.sol:143-148`). [1](#0-0) 
- `addToDepositTokensOfAccount` is callable only by a registered `DepositToken`, but the *recipient* `account_` is fully attacker-controllable (`Pool.sol:216-220`). [2](#0-1) 
- `DepositToken._transfer` adds the recipient to the pool list on a 0→positive balance transition (`DepositToken.sol:517-520`), and `transfer`/`transferFrom` are permissionless ERC20 entry points gated only by the sender's unlocked balance (`DepositToken.sol:348-376`). [3](#0-2) 
- `DepositToken.deposit(amount_, onBehalfOf_)` also mints to an arbitrary beneficiary (`DepositToken.sol:211-237`), giving a second vector that doesn't even require holding the deposit token. [4](#0-3) 
- On the debt side, `addToDebtTokensOfAccount` shares the same combined cap (`Pool.sol:204-208`), so once the list is full, `DebtToken` issuance of any new synthetic to the victim reverts. [5](#0-4) 

Attack path (all public, no privileged role):
1. For each registered `DepositToken d_i`, attacker calls `d_i.deposit(dust, attacker)` once (or obtains dust balances any way).
2. Attacker calls `d_i.transfer(victim, 1)` for every `d_i` the victim doesn't already hold. Each transfer appends `d_i` to `depositTokensOfAccount[victim]`.
3. Once the victim's combined list hits 30, all of the following revert for the victim: depositing/receiving any not-yet-held `DepositToken`, and issuing/minting/flash-issuing any not-yet-held `DebtToken`.

### Impact Explanation
Temporary denial of service against a specific account. The victim cannot open a debt position in a new synthetic asset and cannot receive or deposit collateral types not already in their list. In a market stress event this can block a victim from routing collateral through a different listed deposit token they don't hold yet while being liquidated, or prevent counterparties (e.g., gateways/smart-farming flows) from minting new-token positions on their behalf. The victim retains an escape hatch — transferring a full dust balance out triggers `removeFromDepositTokensOfAccount` (`DepositToken.sol:522-525`) and frees a slot — but this requires the victim to detect the griefing and spend transactions to clear it, so the freeze is temporary rather than permanent. [6](#0-5) 

### Likelihood Explanation
Low-to-medium. The attack requires the pool to list many `DepositToken`s (cap is 30 total registered per `addDepositToken`, `Pool.sol:698-710`) or the victim to already have a partially filled list. Cost scales linearly with the number of tokens the victim doesn't hold: one dust deposit + one transfer each, all permissionless. No privileged actor, oracle manipulation, or flash loan is needed; anyone can do it to anyone at any time. [7](#0-6) 

### Recommendation
Make token-list membership opt-in or self-healable for recipients. Options:
- Only add the recipient in `_transfer` when they have explicitly opted in (e.g., only `deposit(onBehalfOf == msgSender)` registers; transfers require the recipient to call a `claim`/registration function).
- Alternatively, allow `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` to succeed by evicting an entry with zero balance instead of reverting, since dust entries carry no economic weight.
- At minimum, let a user remove entries from their own list directly in `Pool` (an `removeTokenFromMyAccount` escape) so recovery doesn't depend on transferring dust.

### Proof of Concept
Reproducible in the existing Hardhat setup (pattern follows `test/Pool.test.ts` "should revert when reach max tokens", lines 1386-1416, but using real `DepositToken` contracts and a victim EOA instead of fakes):

```ts
// victim starts with an empty list
// attacker deposits dust of each registered DepositToken into themselves, then:
for (const dt of allDepositTokens) {            // k tokens, victim's free slots = 30 - used
  await dt.connect(attacker).transfer(victim.address, 1);  // adds dt to victim's list
}
// victim's combined list is now 30

// victim tries to issue a new synthetic they never held:
await expect(
  newDebtToken.connect(victim).issue(msUSD.address, parseEther('1'))
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// or a friend tries to send victim a not-yet-held DepositToken:
await expect(
  otherDepositToken.connect(friend).transfer(victim.address, 1)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

Note: if the deployment's total registered `DepositToken` count plus the victim's existing entries cannot reach 30, the combined list can't be filled by deposit-token dust alone and the attack is limited to pools with enough collateral listings to cover `30 - debtTokensOfAccount.length(victim)` slots.
