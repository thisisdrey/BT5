### Title
Incorrect proportional resource-usage transfer in `UnDelegateResourceActuator`/`UnDelegateResourceProcessor` corrupts bandwidth/energy accounting - ([File: actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java])

### Summary
`UnDelegateResourceActuator` (and its TVM-precompile twin `UnDelegateResourceProcessor`) computes how much of a receiver's accumulated resource *usage* should be transferred back to the delegator when a delegation is revoked. Like the Bunni `_depositLogic()` idle-balance bug, it **assumes a static, proportional relationship** ("usage transferred is proportional to `unDelegateBalance / totalFrozenBalance`") that holds only at the instant it is computed, and never re-validates that assumption against the actual state that results from user-controlled delegate/undelegate sequencing. Because the ratio is derived from values (`getAllFrozenBalanceForBandwidth()`/`getAllFrozenBalanceForEnergy()`, `getNetUsage()`/`getEnergyUsage()`) that the account owner can manipulate within the same block via ordinary `DelegateResource`/`UnDelegateResource` transactions, an attacker can drive the divisor toward the delegated amount itself or otherwise distort the ratio, causing `transferUsage` to be computed incorrectly and permanently corrupting the owner's and receiver's `NetUsage`/`EnergyUsage` windows — an unbacked-resource / accounting-drift condition analogous to the unbacked idle-balance drift in the Bunni report.

### Finding Description
In `execute()`, when the resource type is BANDWIDTH: [1](#0-0) 

the code computes:
```
long unDelegateMaxUsage = (long) ((double) unDelegateBalance / TRX_PRECISION
    * ((double) (dynamicStore.getTotalNetLimit()) / dynamicStore.getTotalNetWeight()));
transferUsage = (long) (receiverCapsule.getNetUsage()
    * ((double) (unDelegateBalance) / receiverCapsule.getAllFrozenBalanceForBandwidth()));
transferUsage = min(unDelegateMaxUsage, transferUsage);
```
The identical pattern exists for ENERGY, and is duplicated verbatim in the TVM native-contract path reachable from any smart contract call: [2](#0-1) 

This logic assumes `receiverCapsule.getNetUsage()` is uniformly distributed across `receiverCapsule.getAllFrozenBalanceForBandwidth()` (the sum of the receiver's *own* frozen + all delegations-in), and that `unDelegateBalance / totalFrozen` accurately represents the share of usage attributable to this particular delegation being revoked — exactly the "idle balance grows proportionally" assumption in the Bunni bug. This assumption breaks because:

- `getAllFrozenBalanceForBandwidth()`/`getAllFrozenBalanceForEnergy()` include the receiver's *entire* frozen/delegated-in balance, not just the specific delegation from `ownerAddress` being undone, so the proportional split misattributes usage between multiple delegators.
- The owner (delegator) fully controls when/how much they delegate and undelegate (`DelegateResourceActuator`, reachable at will by any signed account), so they can shape `unDelegateBalance` and time the call relative to their own or others' recent `DelegateResource`/`UnDelegateResource` operations to skew the divisor, in the same way the Bunni user could omit the vault fee to skew `reserveChangeInUnderlying`.
- There is no cross-check between the computed `transferUsage` and the pre/post state of the receiver's actual consumption attributable to this specific delegation — mirroring the Bunni report's core defect: "no validation that the computed delta matches the real change."

### Impact Explanation
Because `NetUsage`/`EnergyUsage` directly gate free bandwidth/energy allotment for accounts, a persistently miscomputed `transferUsage` corrupts the resource-usage windows tracked in `AccountCapsule` (via `setNetUsage`/`setEnergyUsage` and `BandwidthProcessor.unDelegateIncrease`/`EnergyProcessor.unDelegateIncrease`). Repeated delegate/undelegate cycles (freely composable by any account, at negligible cost since `calcFee()` returns 0) can accumulate a persistent, incorrect state where usage is under- or over-counted relative to the resources actually backing it — i.e., an "unbacked" bandwidth/energy allocation, analogous to the unbacked LP token ratio in the Bunni report. This is a resource-accounting integrity defect exploitable by an ordinary account (not a validator/witness), fitting the "unbacked balance" impact class.

### Likelihood Explanation
`DelegateResourceContract` and `UnDelegateResourceContract` are ordinary, permissionless transaction types (also exposed as TVM precompiles reachable from any contract call), requiring only that the calling account owns frozen/delegated V2 balance — a low barrier reachable by any unprivileged broadcaster. The double-based proportional math and lack of cross-validation are always present on every undelegate call, making the drift systematically reachable, though the magnitude of exploitable divergence depends on how attackers sequence delegate/undelegate operations across multiple counterparties in the same account.

### Recommendation
Do not derive `transferUsage` from a live, globally-mutable ratio (`unDelegateBalance / getAllFrozenBalanceForBandwidth()`); instead track and transfer usage per specific `(owner, receiver)` delegation relationship, or reconcile the computed value against the actual delegated resource's own recorded usage share. Consider validating that the computed transfer amount does not exceed the total that was ever attributable to that specific delegation, with an explicit invariant check (analogous to Bunni's recommended fix of validating `reserveChangeInUnderlying` against the expected value regardless of whether the input parameter is zero).

### Proof of Concept
Conceptual (not verified end-to-end due to no execution environment access):
1. Account A freezes balance for BANDWIDTH and delegates portions to two different receivers, B and C, at different times so that B's `getNetUsage()` accrues usage while acquiring delegations from both A and other delegators.
2. B consumes bandwidth, increasing `NetUsage` while `getAllFrozenBalanceForBandwidth()` reflects the combined delegated-in total from all delegators.
3. A calls `UnDelegateResource` for only a fraction of its delegation to B. `transferUsage` is computed as `B.getNetUsage() * (unDelegateBalance / B.getAllFrozenBalanceForBandwidth())`, which attributes to A a share of B's usage proportional to A's undelegated amount versus B's *total* frozen balance from all sources — not the usage actually caused by A's delegation.
4. By controlling the timing and amounts of delegate/undelegate calls relative to other delegators' balances, A can extract disproportionately more (or less) `NetUsage` transfer back than it is entitled to, permanently skewing the aggregate `NetUsage` bookkeeping across A and B's accounts, which can be repeated to accumulate free/unbacked bandwidth over time.
