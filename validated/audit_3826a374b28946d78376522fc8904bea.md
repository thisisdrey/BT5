### Title
Non-reproducible module extension `facts` accepted from an attacker-controlled `MODULE.bazel.lock` bypass checksum verification, poisoning the build - (File: `src/main/java/com/google/devtools/build/lib/bazel/bzlmod/` — `RepositoryMappingFunction`/`SingleExtensionEvalFunction`/`BazelLockFileFunction` facts handling; documented in `docs/external/extension.mdx:258-287`)

### Summary
Bzlmod module extensions can declare themselves non-reproducible and store `facts` in `MODULE.bazel.lock` — a JSON blob explicitly intended to hold "effectively immutable data obtained from outside the build, most commonly from the network," such as a version→(URL, checksum) mapping, in lieu of an actual checksum-guarded download. [1](#0-0)  The extension re-reads this data on later evaluations via `ctx.facts` instead of re-fetching/re-verifying it from the network. [2](#0-1) 

For non-reproducible extensions, Bazel's default `--lockfile_mode=update` (and even `--lockfile_mode=error`) trusts whatever `facts` values are present in the committed `MODULE.bazel.lock`, merging in externally-added/edited entries without re-running the extension to validate them, and even preserves entries deleted from the lockfile by restoring them from the hidden per-machine cache. [3](#0-2) [4](#0-3) 

### Finding Description
`MODULE.bazel.lock` is a normal file in the workspace, tracked in version control and, per the report's threat model, reachable by an unprivileged attacker who can get a victim's CI to build an untrusted branch/fork/PR. The `facts` mechanism is specifically documented as a substitute for checksum verification: "If your extension relies on effectively immutable data obtained from outside the build ... but you don't have a checksum available to guard the download, consider using the `facts` parameter ... An example of using `facts` would be to record a mapping from version numbers of some SDK to ... download URL and checksum." [1](#0-0) 

The regression test `testExternallyUpdatedFactsKeptByUpdateModeForNonReproducibleExtension` demonstrates that when the workspace lockfile's facts for a non-reproducible extension are modified externally (its own comment states this simulates "a branch switch or pull that brings in facts produced by an evaluation of the extension on a different machine"), Bazel's `update` mode keeps the new, externally-supplied fact values as-is, without rerunning the extension to verify them: "the cached result must be reused with the new facts as is." [3](#0-2)  `--lockfile_mode=error`, which is meant to reject an out-of-date lockfile, also does not detect or reject tampered/edited facts for non-reproducible extensions: `testDeletedFactsIgnoredByErrorModeForNonReproducibleExtension` confirms edited facts pass silently in error mode. [4](#0-3) 

Consequently, if an extension follows the documented pattern of storing an unverified (URL, checksum) pair in `facts` for use by a subsequent `repository_rule` (e.g. as the `sha256` attribute of a download), an attacker who edits the committed `MODULE.bazel.lock` on a branch/fork can inject an arbitrary fact value — for example a checksum for a legitimate-looking URL that actually points at attacker-controlled malicious content, or a checksum matching an attacker-crafted archive. Because the value is taken directly from the workspace lockfile rather than being re-derived by re-executing the extension against its real source of truth, the "verification" checksum itself becomes attacker-supplied data, and the invariant that "a pinned checksum should stop a hostile origin" never gets a chance to fire: the checksum was forged at the source of truth (the lockfile), not defeated in transit.

### Impact Explanation
Any Bazel module extension author who follows Bazel's own documented guidance to use `facts` as a substitute for checksum-guarded downloads is exposed: an attacker who can influence the committed `MODULE.bazel.lock` (an artifact of the source tree, not a trusted root BUILD/.bzl file, and one CI systems routinely rebuild for arbitrary forks/branches/PRs) can silently substitute the metadata (URLs, hashes, version-to-artifact mappings) that a non-reproducible extension will trust on the next evaluation, without the extension's own network fetch/verification logic ever running. This can steer a `repository_rule` into fetching and accepting attacker-chosen content as if it had been checksum-verified, and because `update` mode re-persists/heals these values, the poisoning can propagate forward into subsequent commits and other clones/builds that trust the lockfile.

### Likelihood Explanation
Likelihood is moderate: it requires (1) an extension author who followed the documented `facts` pattern instead of a real checksum-guarded `ctx.download`, and (2) a victim who builds an attacker-influenced branch/fork with a default `--lockfile_mode` (`update`, the default, or `error`, which is also insufficient here). Both preconditions are realistic — `facts` is Bazel's own documented mechanism for exactly the checksum-less-download case, and building untrusted contributor branches in CI is common practice.

### Recommendation
- For non-reproducible extensions, require the "source of truth" comparison to happen against something Bazel can independently verify (e.g., cross-check `facts` entries against a real checksum verification path once, or record a digest of the facts value that ties it to the extension's own outputs) rather than trusting workspace-lockfile-supplied facts unconditionally in `update`/`error` mode.
- At minimum, document more prominently that `facts` provides no integrity guarantee against a maliciously edited `MODULE.bazel.lock`, and that extension authors must not use `facts` to carry a checksum that is subsequently used to validate a download without an independent verification step.
- Consider making `--lockfile_mode=error` actually validate non-reproducible facts against a re-run of the extension (at least optionally), rather than deliberately skipping this check to avoid "false positives" per issue #28717.

### Proof of Concept
Analogous to `testExternallyUpdatedFactsKeptByUpdateModeForNonReproducibleExtension` [3](#0-2) :
1. Define a non-reproducible module extension that follows the documented pattern: on first evaluation it "fetches" (or is given) a `{version: {"url": ..., "sha256": ...}}` mapping and returns it via `ctx.extension_metadata(reproducible=False, facts=metadata)`; a `repository_rule` uses `facts[version]["sha256"]` as its `sha256` attribute for `ctx.download`.
2. Run `bazel build` once so `MODULE.bazel.lock` records legitimate facts (as in `testFactsInNonReproducibleExtension`). [5](#0-4) 
3. Simulate an attacker-controlled branch: directly edit `MODULE.bazel.lock`'s `facts[extension_id]` entry (as `_addFactToLockfile` does) to point to a malicious URL/sha256 pair.
4. Run `bazel build --lockfile_mode=update` (the default) and observe the extension is not re-evaluated and the tampered fact is kept and used to drive the download, exactly as demonstrated by the existing test assertions that the new fact value is retained unmodified. [6](#0-5) 
5. Repeat with `--lockfile_mode=error` and observe no failure (per `testDeletedFactsIgnoredByErrorModeForNonReproducibleExtension`'s analogous edited-facts case), confirming this mode provides no protection either. [4](#0-3)

If your extension relies on effectively immutable data obtained from outside
the build, most commonly from the network, but you don't have a checksum
available to guard the download, consider using the `facts` parameter of
[`extension_metadata`](/rules/lib/builtins/module_ctx#extension_metadata) to
persistently record such data and thus allow your extension to become
reproducible. `facts` is expected to be a dictionary with string keys and
arbitrary JSON-like Starlark values that is always persisted in the lockfile and
available to future evaluations of the extension via the
[`facts`](/rules/lib/builtins/module_ctx#facts) field of `module_ctx`.

`facts` are not invalidated even when the code of your module extension changes,
so be prepared to handle the case where the structure of `facts` changes.
Bazel also assumes that two different `facts` dicts produced by two different
evaluations of the same extension can be shallowly merged (i.e., as if by using
the `|` operator on two dicts). This is partially enforced by `module_ctx.facts`
not supporting enumeration of its entries, just lookups by key.

An example of using `facts` would be to record a mapping from version numbers of
some SDK to the an object containing the download URL and checksum of that
version. The first time the extension is evaluated, it can fetch this mapping
from the network, but on later evaluations it can use the mapping from `facts`
to avoid the network requests.

  def testExternallyUpdatedFactsKeptByUpdateModeForNonReproducibleExtension(
      self,
  ):
    """UPDATE mode keeps updated facts of a non-reproducible extension.

    The hidden lockfile records the facts produced by the most recent local
    evaluation of the extension. If the workspace lockfile's facts for a
    non-reproducible extension change without any of its inputs changing (e.g.
    a branch switch or pull brings in a re-pin performed on another machine),
    the cached result must be reused with the new facts as is: a cold machine
    would not rerun the extension either and a rerun could require network
    access or credentials that are only available to the person updating the
    pins.
    """
    extension_id = self._setUpExtensionWithFacts(reproducible=False)
    self._addFactToLockfile(extension_id, '1.27.0', {'hash': 'hola'})

    _, _, stderr = self.RunBazel(
        ['build', '@hello//:all', '--lockfile_mode=update']
    )
    self.assertNotIn('lockfile_ext is being evaluated', '\n'.join(stderr))

    with open(self.Path('MODULE.bazel.lock'), 'r') as f:
      lockfile = json.loads(f.read().strip())
    self.assertEqual(
        lockfile['facts'][extension_id],
        {
            '1.25.0': {'hash': 'olleh'},
            '1.26.1': {'hash': 'hello'},
            '1.27.0': {'hash': 'hola'},
        },
    )

  def testDeletedFactsIgnoredByErrorModeForNonReproducibleExtension(self):
    """ERROR mode does not fail on edited facts of a non-reproducible extension.

    A non-reproducible extension must not be rerun in ERROR mode and failing
    based on the hidden lockfile's purely machine-local record could produce
    false positives after a rollback of the extension together with the
    workspace lockfile (https://github.com/bazelbuild/bazel/issues/28717).
    """
    extension_id = self._setUpExtensionWithFacts(reproducible=False)
    self._dropFactsFromLockfile(extension_id)

    self.RunBazel(['build', '@hello//:all', '--lockfile_mode=error'])
