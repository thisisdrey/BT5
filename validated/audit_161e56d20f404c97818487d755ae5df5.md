### Title
Interest accrual uses simple (non-compounded) interest, making collected fees dependent on `accrueInterest()` call frequency - (File: contracts/DebtToken.sol)

### Summary
`DebtToken._calculateInterestAccrual()` accrues debt interest linearly: `interestRatePerSecond() * elapsed`, applied against the *stored* `totalSupply_`. Because accrued interest is only folded back into `totalSupply_` inside `accrueInterest()`, the effective interest collected over a given period depends on how often `accrueInterest()` is invoked. This is the same bug class as the referenced Basket.sol finding: a simple-interest formula produces frequency-dependent, inconsistent fee accrual — infrequent accrual under-collects relative to frequent accrual (which approximates continuous compounding).

### Finding Description
In `contracts/DebtToken.sol` [1](#0-0) :

```solidity
uint256 _interestRateToAccrue = interestRatePerSecond() * (block.timestamp - _lastTimestampAccrued);
if (_interestRateToAccrue > 0) {
    _interestAmountAccrued = _interestRateToAccrue.wadMul(totalSupply_);
    _debtIndex += _interestRateToAccrue.wadMul(_debtIndex);
}
```

And in `accrueInterest()` [2](#0-1)  the accrued amount is added to `totalSupply_` and minted to `pool.feeCollector()` only when accrual is executed.

Concretely: at 10% APR on a 100e18 supply over 1 year —
- `accrueInterest()` called once: interest = `0.1 * 100e18 = 10e18`, total debt `110e18`.
- `accrueInterest()` called every block: each accrual compounds on the larger `totalSupply_`, converging toward `e^0.1`, i.e. total ≈ `110.517e18`.

`accrueInterest()` is permissionless `public` [3](#0-2)  and is triggered implicitly by `issue`, `mint`, `repay`, `burn`, `flashIssue`, and transfers [4](#0-3) . So realized protocol interest income and borrower debt drift depending on network activity rather than on a defined compounding schedule. No modifier, cap, or guard bounds this discrepancy — `whenNotShutdown`, `nonReentrant`, etc. are irrelevant since the issue is deterministic math inside a view-computable path.

### Impact Explanation
Over any interval between accruals, borrowers are charged simple interest while the economically intended rate compounds on the growing supply. Long idle stretches (low-activity DebtTokens, or the window where `pendingInterestFee` accumulates when minting fails) systematically under-collect protocol interest revenue, while busy periods over-charge borrowers relative to a fixed epoch model. The loss is bounded (the compounding delta, ~0.5% of interest at 10% APR/year), matching the "slight precision loss / inconsistent fee" nature of the original finding, but it is real value leakage: `feeCollector` receives fewer synth tokens than the compounded debt growth the `debtIndex` charges users implies the protocol intended, and accrual frequency is influenced by arbitrary callers since `accrueInterest()` is public.

### Likelihood Explanation
Certain — it is inherent to the math and is triggered on every public call path (`issue`, `repay`, `swap` → `repay`, liquidation, or direct `accrueInterest()`). The magnitude of divergence grows with interest rate, time between accruals, and supply size, and is worst precisely for low-activity pools where nobody calls the token for long stretches.

### Recommendation
Compound the index deterministically rather than linearly, e.g. compute `_debtIndex` with an exponential factor (per-second compounding via `rpow`/`wadExp`) instead of `interestRatePerSecond() * dt`, so that accrued interest is independent of call frequency. Alternatively, document and accept the linear model but accrue on a fixed cadence (e.g., keeper-driven per epoch) — though the former is the correct fix consistent with Aave/Compound-style debt indices.

### Proof of Concept
Foundry fork-style test against `DebtToken`:

```solidity
// Assume: msUSDDebt issued 100e18 principal, interestRate = 0.1e18 (10% APR)

// Scenario A: single accrual after 1 year
vm.warp(block.timestamp + 365 days);
msUSDDebt.accrueInterest();
uint256 supplyA = msUSDDebt.totalSupply(); // ≈ 110e18

// Scenario B (fresh fixture): accrue every hour for 1 year
for (uint256 i; i < 8760; ++i) {
    vm.warp(block.timestamp + 1 hours);
    msUSDDebt.accrueInterest();
}
uint256 supplyB = msUSDDebt.totalSupply(); // ≈ 110.51e18 > supplyA

assertGt(supplyB, supplyA); // frequency-dependent interest/fee collection
```

The delta between `supplyB` and `supplyA` is minted (or not) to `feeCollector` purely based on how often a public function was called, demonstrating the inconsistent, non-compounded fee accrual analogous to the Basket.sol finding.

    function _calculateInterestAccrual()
        private
        view
        returns (uint256 _interestAmountAccrued, uint256 _debtIndex, uint256 _lastTimestampAccrued)
    {
        _lastTimestampAccrued = lastTimestampAccrued;
        _debtIndex = debtIndex;

        if (block.timestamp > _lastTimestampAccrued) {
            uint256 _interestRateToAccrue = interestRatePerSecond() * (block.timestamp - _lastTimestampAccrued);
            if (_interestRateToAccrue > 0) {
                _interestAmountAccrued = _interestRateToAccrue.wadMul(totalSupply_);
                _debtIndex += _interestRateToAccrue.wadMul(_debtIndex);
            }
        }
    }
