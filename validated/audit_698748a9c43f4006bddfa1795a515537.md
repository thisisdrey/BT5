### Title
Missing null/burn-address validation in `TransferActuator` allows permanent loss of TRX sent to an unspendable address - (File: actuator/src/main/java/org/tron/core/actuator/TransferActuator.java)

### Summary
`TransferActuator.validate()` only checks that `toAddress` has the correct length and prefix byte via `DecodeUtil.addressValid()`, but never rejects an address whose remaining 20 bytes are all zero (i.e. the "zero"/burn address `0x41000000000000000000000000000000000000000` in hex form). This is directly analogous to the reported `VUSD.withdrawTo()` bug: a user- (or attacker-crafted) destination address that passes format validation but corresponds to no reachable private key results in permanently locked/burned funds once the transfer executes.

### Finding Description
`TransferActuator.validate()` performs the following check on the destination address: [1](#0-0) 

which calls `DecodeUtil.addressValid()`: [2](#0-1) 

This function only validates the array length (21 bytes) and that the first byte equals the network prefix (`0x41` for mainnet). It performs no check that the remaining 20 bytes are non-zero, so a `toAddress` of `0x41` followed by 20 zero bytes passes validation just like any legitimate address. `TransferActuator.execute()` then unconditionally creates the account (if it does not exist) and credits it with the transferred amount: [3](#0-2) 

Because this all-zero-body address has a negligible probability of corresponding to any derivable private key (identical reasoning to Ethereum's `0x0` "burn" address), any TRX sent to it becomes permanently unspendable — the exact "permanent loss of user funds" impact described in the reference report for `VUSD.withdrawTo`. The same missing check exists in `TransferAssetActuator.validate()`, which performs the identical `DecodeUtil.addressValid(toAddress)` check without excluding the zero-body address: [4](#0-3) 

### Impact Explanation
Any TRX or TRC10 asset sent via `TransferContract`/`TransferAssetContract` to the zero-body address is permanently and irrecoverably lost, since no key can practically be derived to control that address. This matches the accepted impact class "permanent freezing/loss of funds," reachable purely by broadcasting a single signed transaction — no privileged role required.

### Likelihood Explanation
Likelihood is limited to accidental or attacker-induced misdirection (e.g. a malicious dApp/wallet front-end tricking a user into confirming a transfer to the burn-pattern address, or a bug in address-generation code producing an all-zero body). The actuator itself provides no defense-in-depth guard, unlike a well-formed implementation that would explicitly reject a recognized burn/zero address in addition to format checks.

### Recommendation
In `TransferActuator.validate()` and `TransferAssetActuator.validate()` (and any other actuator accepting a user-specified destination, e.g. `ParticipateAssetIssueActuator`), add an explicit check rejecting a `toAddress`/`ownerAddress` whose body bytes (excluding the prefix byte) are all zero, in addition to the existing `DecodeUtil.addressValid()` length/prefix check.

### Proof of Concept
1. Construct a `TransferContract` with `ownerAddress` = a funded account and `toAddress` = `0x41` followed by 20 zero bytes (21 bytes total, passes `DecodeUtil.addressValid`).
2. Sign and broadcast the transaction.
3. `TransferActuator.validate()` passes all checks (`addressValid` succeeds, addresses differ, sufficient balance).
4. `TransferActuator.execute()` creates the zero-body account and credits it with `amount`.
5. The transferred TRX is now held by an address with no derivable private key, permanently locked/unspendable — identical impact pattern to the referenced `VUSD.withdrawTo` finding.

  public static boolean addressValid(byte[] address) {
    if (ArrayUtils.isEmpty(address)) {
      logger.warn("Warning: Address is empty !!");

    }

      logger.warn(
          "Warning: Address length need " + ADDRESS_SIZE + " but " + address.length

      return false;
    }

    if (address[0] != addressPreFixByte) {
      logger.warn("Warning: Address need prefix with " + addressPreFixByte + " but "
          + address[0] + " !!");

    }
    return true;
  }
