### Title
Failed native NEAR transfer in `do_native_withdraw` is not resolved/refunded, permanently burning user balance - (File: contracts/defuse/src/contract/tokens/nep141/native.rs)

### Summary
`native_withdraw` immediately debits the user's internal wNEAR-backed balance and then asynchronously unwraps and transfers native NEAR to the receiver. Unlike the FT/NFT/MT withdrawal paths, this chain has no resolver step that checks whether the final `Promise::new(receiver_id).transfer(amount)` succeeded and credits the amount back to the user if it did not.

### Finding Description
`native_withdraw` in [1](#0-0)  subtracts `withdraw.amount` from the caller's internal balance via `self.withdraw(...)` *before* any promise executes, then schedules `near_withdraw` on the wNEAR contract followed by `do_native_withdraw`.

`do_native_withdraw` in [2](#0-1)  only checks that the preceding `near_withdraw` callback succeeded, then fires `Promise::new(withdraw.receiver_id).transfer(withdraw.amount)` as the terminal action — there is no `.then()` continuation that inspects the result of this transfer.

Compare this to the FT/NFT/MT withdrawal flows, which explicitly chain a resolver (`ft_resolve_withdraw`, `nft_resolve_withdraw`, `mt_resolve_withdraw`) that checks `promise_result_checked_*` on the final transfer and re-deposits any unused/failed amount back to the sender's internal balance: [3](#0-2) [4](#0-3) [5](#0-4) 

No equivalent resolver exists for the native-NEAR path. If the final `transfer` action fails for any reason (e.g., the `receiver_id` account does not exist, or any other receipt-level failure at that step), NEAR's runtime returns the attached balance to the *predecessor* of that failed receipt, i.e. it is refunded back into the Defuse contract's own account balance — not credited to the user's internal ledger. The user's internal balance was already debited in `native_withdraw` prior to the async chain and is never restored, since there is no code path that observes the failure and re-deposits funds to `owner_id`.

This breaks the "value debited versus value delivered plus refunded" custody binding described in the report: the internal ledger permanently loses `withdraw.amount` for the user while the underlying NEAR silently remains under the contract's control, unaccounted for and unrecoverable via the intents system.

### Impact Explanation
This is a Critical-class issue under "funds permanently frozen"/lost: a user's `NativeWithdraw` intent can debit their `TokenId::Nep141(wNEAR)` balance while the actual NEAR is never received by them and never credited back, with no on-chain path to reclaim it through the contract's own token accounting.

### Likelihood Explanation
Triggering the failure only requires supplying a syntactically valid but non-existent `receiver_id` (or any other transient failure at that specific receipt), which is fully within an ordinary user's control via `sign_defuse_payload_default` / `NativeWithdraw{ receiver_id, amount }` — no privileged role, relayer, or DAO action needed. It is a fully unprivileged, attacker/self-inflicted-or-third-party-inflicted path, since anyone could specify an attacker-controlled/near-invalid `receiver_id` for a withdrawal not addressed to themselves, causing the target's or their own funds to be lost while it remains a genuine mismatch between debited balance and delivered+refunded value.

### Recommendation
Add a resolver step (mirroring `ft_resolve_withdraw`/`nft_resolve_withdraw`/`mt_resolve_withdraw`) chained after the final `Promise::new(withdraw.receiver_id).transfer(withdraw.amount)` in `do_native_withdraw`, which checks `promise_result_checked_void` and, on failure, re-deposits `withdraw.amount` back to the original `owner_id`'s internal balance (as wNEAR or equivalent), consistent with the refund handling used by the other token-withdrawal flows.

### Proof of Concept
1. User calls `native_withdraw` with `NativeWithdraw { receiver_id: <account that does not exist>, amount }` (contracts/defuse/src/contract/intents/state.rs:212-240) — this immediately deducts `amount` from the caller's internal wNEAR balance.
2. `near_withdraw` succeeds, unwrapping wNEAR into native NEAR held by the Defuse contract.
3. `do_native_withdraw` (contracts/defuse/src/contract/tokens/nep141/native.rs:12-19) issues `Promise::new(receiver_id).transfer(amount)`; because `receiver_id` does not exist, this transfer action fails at the protocol level and the NEAR balance is refunded to the Defuse contract's own account (not the user).
4. No resolver observes this failure, so the user's internal balance is never restored — `amount` is permanently lost from the user's perspective while silently retained by the contract, with no reconciling code path in the reachable in-scope contracts.

    fn ft_resolve_withdraw(
        &mut self,
        token: AccountId,
        sender_id: AccountId,
        amount: U128,
        is_call: bool,
    ) -> U128 {
        let used = if is_call {
            // `ft_transfer_call` returns successfully transferred amount
            match promise_result_checked_json::<U128>(0) {
                Ok(Ok(used)) => used.0.min(amount.0),
                Ok(Err(_deserialize_err)) => 0,
                // do not refund on failed `ft_transfer_call` due to
                // NEP-141 vulnerability: `ft_resolve_transfer` fails to
                // read result of `ft_on_transfer` due to insufficient gas
                Err(_) => amount.0,
            }
        } else {
            // `ft_transfer` returns empty result on success
            if promise_result_checked_void(0).is_ok() {
                amount.0
            } else {
                0
            }
        };

        let refund = amount.0.saturating_sub(used);
        if refund > 0 {
            self.deposit(
                sender_id,
                [(Nep141TokenId::new(token).into(), refund)],
                Some(REFUND_MEMO),
            )
            .unwrap_or_else(|err| err.panic());
        }

        U128(used)
    }

impl MultiTokenWithdrawResolver for Contract {
    #[private]
    fn mt_resolve_withdraw(
        &mut self,
        token: AccountId,
        sender_id: AccountId,
        token_ids: Vec<defuse_nep245::TokenId>,
        amounts: Vec<U128>,
        is_call: bool,
    ) -> Vec<U128> {
        require!(
            token_ids.len() == amounts.len() && !amounts.is_empty(),
            "invalid args"
        );

        let mut used = if is_call {
            // `mt_batch_transfer_call` returns successfully transferred amounts
            match promise_result_checked_json_with_len::<Vec<U128>>(0, amounts.len()) {
                Ok(Ok(used)) if used.len() == amounts.len() => used,
                Ok(_) => vec![U128(0); amounts.len()],
                // do not refund on failed `mt_batch_transfer_call` due to
                // NEP-141 vulnerability: `mt_resolve_transfer` fails to
                // read result of `mt_on_transfer` due to insufficient gas
                Err(_) => amounts.clone(),
            }
        } else {
            // `mt_batch_transfer` returns empty result on success
            if promise_result_checked_void(0).is_ok() {
                amounts.clone()
            } else {
                vec![U128(0); amounts.len()]
            }
        };

        self.deposit(
            sender_id,
            token_ids
                .into_iter()
                .zip(amounts)
                .zip(&mut used)
                .filter_map(|((token_id, amount), used)| {
                    // update min during iteration
                    used.0 = used.0.min(amount.0);
                    let refund = amount.0.saturating_sub(used.0);
                    if refund > 0 {
                        Some((Nep245TokenId::new(token.clone(), token_id).into(), refund))
                    } else {
                        None
                    }
                }),
            Some(REFUND_MEMO),
        )
        .unwrap_or_else(|err| err.panic());

        used
    }
}
