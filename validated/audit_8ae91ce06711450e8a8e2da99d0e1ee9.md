### Title
Shielded transaction nullifiers can be griefed by front-running the public spend proof, causing legitimate `ShieldedTransferContract` transactions to fail (permit-style signature-frontrunning DoS) - (File: `actuator/src/main/java/org/tron/core/actuator/ShieldedTransferActuator.java`)

### Summary
The reported bug class is: a function that unconditionally consumes an externally-supplied, self-authorizing credential (an EIP-2612 `permit()` signature) can be front-run by copying that credential out of the mempool and submitting it first, causing the legitimate caller's transaction to revert. The equivalent authorization primitive in java-tron is the Sapling `SpendDescription` (zk-SNARK proof + `spendAuthoritySignature` + `nullifier`) inside `ShieldedTransferContract`. Like a permit signature, a `SpendDescription` is fully self-contained public data: whoever possesses the bytes of a pending shielded transaction can wrap the same descriptions into a brand-new transaction and get it mined first, consuming the nullifier and causing the original submitter's transaction to fail.

### Finding Description
`ShieldedTransferActuator.validate()` rejects a transaction whose spend nullifier is already present in the `NullifierStore`, throwing `"note has been spend in this transaction"` [1](#0-0) . `executeShielded()` performs the same "already spent" check at execution time and throws `"double spend"` before persisting the nullifier [2](#0-1) .

Both checks key only on the nullifier value derived from the zk proof, not on who submits the transaction. Once a user signs and broadcasts a `ShieldedTransferContract` via `Wallet.broadcastTransaction`, the transaction enters the pending pool and is relayed over P2P via `tronNetService.fastBroadcastTransaction(message)` before being included in a block [3](#0-2) . `Manager.pushTransaction` accepts and processes any transaction whose signature validates, and adds it to `pendingTransactions`, all of which is visible in the public mempool/relay path [4](#0-3) .

Because the `SpendDescription`/`ReceiveDescription` data is public and self-verifying (any node can validate the zk-SNARK proof and Sapling signature independently of who broadcasts the enclosing `Transaction`), an attacker observing a victim's pending shielded transaction in the mempool/P2P layer can copy the exact spend/receive descriptions into a new `Transaction.raw`, resubmit it with higher fee/priority, and get it included first. When the original transaction is subsequently processed, `ShieldedTransferActuator.validate()`/`executeShielded()` will reject it because the nullifier is already recorded — an exact functional analog of the permit-frontrunning DoS: the legitimate signer's transaction reverts even though nothing was wrong with their signature/proof, forcing them to rebuild and resubmit.

### Impact Explanation
This is a griefing/DoS class impact matching the report's classification: no direct fund theft, but any shielded transfer can be forced to fail by a third party who merely observes the pending transaction, wasting the legitimate user's transaction-construction effort and delaying their transfer. Because shielded value transfers underpin the "confidential" transaction feature of java-tron, this griefing vector can be used to repeatedly block a targeted user's shielded transfers, which fits "Griefing (no profit motive but damage to the users or the protocol)".

### Likelihood Explanation
Likelihood is high for any observer with mempool/P2P visibility (an "unprivileged transaction broadcaster") since no privileged role, private key, or additional secret is required — only the already-signed but not-yet-confirmed transaction bytes, which are inherently exposed once broadcast per the design of `pushTransaction`/`fastBroadcastTransaction`.

### Recommendation
Bind nullifier consumption/validation to the originating transaction's identity in a way that a third party cannot reuse (e.g., require the SpendDescription's binding/authorizing signature to also commit to the specific enclosing transaction's fee-payer/owner-transparent fields, or reject re-broadcast of descriptions already seen as pending from a different submitter), and/or treat a "note already spent" failure of a previously-broadcast, still-pending user transaction as a distinguishable, retryable condition (mirroring the `trustlessPermit` fallback pattern: if the copied transaction achieves the same shielded state transition, do not simply hard-fail the original — detect and treat it as already-satisfied rather than as an attacker-inducible validation error).

### Proof of Concept
1. Alice builds and signs a `ShieldedTransferContract` (shield-to-shield) transaction via `ZenTransactionBuilder`, producing `SpendDescription`/`ReceiveDescription` with a valid nullifier and proof, and broadcasts it via `Wallet.broadcastTransaction` [3](#0-2) .
2. While Alice's transaction sits in `pendingTransactions`/P2P relay, Bob observes it, extracts the `SpendDescription`/`ReceiveDescription` bytes, and constructs his own `Transaction.raw` wrapping the identical descriptions (no private key needed, since the proof/signature validate independent of the wrapping transaction), then broadcasts his transaction with a higher relay priority.
3. Bob's transaction is validated and executed first; `executeShielded()` inserts the nullifier into `NullifierStore` [5](#0-4) .
4. Alice's original transaction is then processed and `ShieldedTransferActuator.validate()` throws `ContractValidateException("note has been spend in this transaction")` [6](#0-5) , exactly mirroring the `supplyWithPermit`/`repayWithPermit` DoS pattern from the report where the front-run signature causes the legitimate caller's transaction to revert.
