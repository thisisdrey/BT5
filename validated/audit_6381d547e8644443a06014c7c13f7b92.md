### Title
`debtFloorInUsd` + `maxLiquidable` interaction creates a "poison band" of unliquidatable debt positions — bad debt and collateral can never be freed - ([File: contracts/Pool.sol])

### Summary
`Pool.liquidate` enforces two mutually exclusive constraints on `amountToRepay_`: (1) the repaid fraction cannot exceed `maxLiquidable`, and (2) the remaining debt must be either 0 or ≥ `debtFloorInUsd`. When `maxLiquidable < 100%` and `debtFloorInUsd > 0`, every debt position whose USD value lies in the band `[floor, floor / (1 - maxLiquidable))` can never be liquidated — a partial liquidation reverts with `RemainingDebtIsLowerThanTheFloor`, and a full liquidation reverts with `AmountGreaterThanMaxLiquidable`. This is the same bug class as CVE-2024-0443: a circular dependency between two release conditions that makes cleanup impossible, permanently trapping the debt and its collateral.

### Finding Description
In `Pool.liquidate`:

```solidity
// contracts/Pool.sol:565-579
uint256 _debtTokenBalance = _debtToken.balanceOf(account_);
if (amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable) {
    revert AmountGreaterThanMaxLiquidable();
}
if (debtFloorInUsd > 0) {
    uint256 _newDebtInUsd = masterOracle().quoteTokenToUsd(
        address(syntheticToken_),
        _debtTokenBalance - amountToRepay_
    );
    if (_newDebtInUsd > 0 && _newDebtInUsd < debtFloorInUsd) {
        revert RemainingDebtIsLowerThanTheFloor();
    }
}
``` [1](#0-0) 

- To satisfy the floor check, `amountToRepay_` must either equal `_debtTokenBalance` (full repay) or leave `≥ floor` of debt, i.e. `amountToRepay_ ≤ D - floorInSynth`.
- To satisfy the max-liquidable check, `amountToRepay_ ≤ maxLiquidable · D`.
- When `D_USD < floor / (1 - maxLiquidable)`, we get `maxLiquidable·D < D - floor`, so no `amountToRepay_` in `(0, D)` is valid, and `amountToRepay_ = D` (ratio = 1 > maxLiquidable) also reverts. No valid `amountToRepay_` exists — liquidation is impossible for any caller, any deposit token, any price.

`maxLiquidable` is initialized to `0.5e18` (50%), so with `debtFloorInUsd > 0` the dead band is `D_USD ∈ [floor, 2·floor)`. The same trap applies to the user themselves via `DebtToken.repay`, which enforces the identical floor check (though `repayAll` and full `repay` are exempt there — only `liquidate` is additionally capped by `maxLiquidable`). ### Impact Explanation
An unprivileged attacker deliberately creates a debt position inside the poison band (e.g. with `floor = $3,000` and `maxLiquidable = 50%`, issue debt worth ~$4,000–$5,900), then lets the collateral price decline or their position drift unhealthy. Once `_isHealthy == false`, no liquidator can ever call `liquidate` successfully — every possible `amountToRepay_` reverts. The position's debt becomes permanently unresolvable bad debt and the seized-able collateral is frozen in the protocol, breaking solvency/liquidation-liveness invariants. This requires no privileged role, oracle manipulation, or helper contract — only public `issue`/`deposit` calls and normal market movement. The invariant broken is the guarantee that unhealthy positions can always be liquidated; the result is protocol insolvency and permanent freezing of collateral (accepted impacts: insolvency + permanent freezing).

### Likelihood Explanation
Conditions: `debtFloorInUsd > 0` (a governor-configured anti-dust parameter used on Metronome deployments) and `maxLiquidable < 100%` (default 50%). Both are normal configuration, not adversarial inputs. The attacker fully controls which band their debt lands in via the `issue` amount, and collateral volatility eventually pushes positions unhealthy. No griefing prerequisites, flash loans, or external dependencies are needed — the revert is deterministic math in `liquidate`. I could not confirm the exact live `debtFloorInUsd`/`maxLiquidable` values from the deployment artifacts (only ABI/storage layout is indexed), so this should be verified on a fork; the mechanism itself is unconditional once those parameters hold.

### Recommendation
Allow a full liquidation to bypass `maxLiquidable` whenever it is the only way to clear the floor — e.g. treat `amountToRepay_ == _debtTokenBalance` as always permitted, or clamp: `if remaining < floor, require amountToRepay_ == _debtTokenBalance` and skip the `maxLiquidable` check in that case. Alternatively compute `quoteLiquidateMax` to return the full balance when the position is in the dead band, ensuring the "cleanup path" always has at least one reachable argument — mirroring the kernel fix of breaking the circular dependency so the object can always be freed.

### Proof of Concept
Hardhat fork sketch (against e.g. mainnet `Pool`):

```ts
// assume pool.debtFloorInUsd() = F > 0 and pool.maxLiquidable() = 0.5e18
// 1. Attacker deposits collateral and issues debt D such that
//    F <= debtUsd(D) < F / (1 - 0.5)  (e.g. F=$3000 -> D ≈ $4,500)
await msdMET.connect(attacker).deposit(collateral, attacker.address);
await msEthDebt.connect(attacker).issue(amountInPoisonBand, attacker.address);

// 2. Drop collateral price (fork: move mock/oracle or wait) until unhealthy
const [healthy] = await pool.debtPositionOf(attacker.address);
expect(healthy).false;

// 3. Liquidator attempts every possible repay amount:
//    - full debt
await expect(
  pool.connect(liq).liquidate(msEth.address, attacker.address, debt, msdMET.address)
).revertedWithCustomError(pool, 'AmountGreaterThanMaxLiquidable'); // ratio = 1 > 0.5
//    - max allowed partial
await expect(
  pool.connect(liq).liquidate(msEth.address, attacker.address, debt.div(2), msdMET.address)
).revertedWithCustomError(pool, 'RemainingDebtIsLowerThanTheFloor'); // remaining < floor
// Any intermediate amount violates one of the two checks — debt is permanently unliquidatable.
```

Existing tests confirm both individual reverts (`test/Pool.test.ts:409-421` floor revert; `439-451` max-liquidable revert); the missing case is their conjunction, which the poison-band PoC demonstrates.
