### Title
RewardsDistributor grants a full-balance reward when claiming while a reward token's index is still `INITIAL_INDEX` - (`contracts/RewardsDistributor.sol`)

### Summary
The bug class from the Olympus report is "reward accounting deducts the wrong amount, letting a user claim more than earned." The analog exists in `RewardsDistributor._calculateTokenDelta()`: when an account's stored `accountIndexOf` is `0`, the fallback to `INITIAL_INDEX` is only applied if `_tokenIndex > INITIAL_INDEX`. If the token index is still exactly `INITIAL_INDEX` (1e18), the delta index is computed as `1e18 - 0 = 1e18`, so `tokensDelta = balance.wadMul(1e18) = balance` — the user is credited reward tokens equal to their entire deposit/debt token balance despite zero time having accrued.

### Finding Description
`INITIAL_INDEX` is `1e18` and a token's `TokenState` is initialized to `{index: INITIAL_INDEX, timestamp: block.timestamp}` when `updateTokenSpeed` first enables a non-zero speed (`RewardsDistributor.sol` ~L296-299).

In `_calculateTokenDelta()`:

```solidity
uint256 _accountIndex = accountIndexOf[token_][account_];

if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}

uint256 _deltaIndex = _tokenIndex - _accountIndex;
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
```

The guard is `_tokenIndex > INITIAL_INDEX`, not `>=`. The token index only grows when `_calculateTokenIndex()` runs with `_deltaTimestamps > 0 && _speed > 0`. Therefore, during the block in which `updateTokenSpeed` adds the token, `tokenStates[token_].index` is still exactly `1e18`.

An existing depositor (someone who deposited *before* the reward token was enabled) has `accountIndexOf == 0`. If such an account's accrual is updated in that same block — via `claimRewards`, `updateBeforeMintOrBurn` (callable by anyone, L173-180), `updateBeforeTransfer`, or a deposit/withdraw/transfer hook — then:

- `_accountIndex` stays `0` (the `> INITIAL_INDEX` check fails since index == 1e18),
- `_deltaIndex = 1e18`,
- `_tokensDelta = balance.wadMul(1e18) = balance`.

`_updateTokensAccruedOf` (L261-266) adds this to `tokensAccruedOf`, and `claimRewards` → `_transferRewardIfEnoughTokens` (L248-256) pays out `min(accrued, rewardToken balance of distributor)`. The attacker receives reward tokens equal to their deposit-token balance while accruing for zero seconds. DepositToken and DebtToken hooks are irrelevant to the fixup because `updateBeforeMintOrBurn` is permissionless, so the attacker can trigger it directly the instant the governor's `updateTokenSpeed` transaction lands (back-running/bundling in the same block is sufficient; `block.timestamp` equality is the only requirement).

Note the ordinary path is not exploitable: `updateBeforeMintOrBurn` during a deposit uses the pre-mint balance, and once `block.timestamp` advances, the index grows past `1e18` and the fallback engages correctly. The bug is confined to the block where a reward token's speed is first set to non-zero (or any later state where `index` remains exactly `INITIAL_INDEX` while `index > 0`).

### Impact Explanation
Each existing holder with `accountIndexOf == 0` can claim reward tokens equal to their full balance, once, per newly-added reward token. If the distributor holds enough `rewardToken`, this is direct theft of unclaimed yield belonging to legitimate users; otherwise earlier claimants drain the contract and later legitimate accruals become unclaimable (`_transferRewardIfEnoughTokens` silently skips payment when balance is insufficient, leaving `tokensAccruedOf` intact but permanently underfunded).

### Likelihood Explanation
- Requires the protocol to enable rewards for a token while users already hold it — a routine governance operation (e.g., adding `msdX`/`DebtToken` reward speed after deposits exist).
- Requires a transaction in the same block as `updateTokenSpeed`/`updateTokenSpeeds`. This is achievable by back-running the governor transaction or submitting via a bundle; no privileged role needed.
- If the reward token has been enabled since before a user's position existed, or a block boundary already passed, the window is closed — so exploitation timing is narrow but fully deterministic when the window exists.
- Reward token balance in the distributor caps the profit; if the distributor is funded ahead of (or with) the speed update, the theft succeeds.

### Recommendation
Change the fallback condition to handle the at-`INITIAL_INDEX` case, i.e., treat a zero stored index as "initial" whenever it is zero:

```solidity
- if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
+ if (_accountIndex == 0 && _tokenIndex >= INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}
```

Equivalently, initialize `accountIndexOf` to `INITIAL_INDEX` on first touch. Also consider making `claimRewards`/`updateBefore*` no-op deltas when `_deltaTimestamps == 0` for the token, and ordering `updateTokenSpeed` transactions before large `rewardToken` top-ups.

### Proof of Concept
Hardhat (repo's test stack). Assumes `depositToken` already exists in `pool` and `alice` holds `100` deposit tokens minted *before* rewards were enabled (so `accountIndexOf == 0`).

```typescript
it('drains rewardToken equal to full balance when claimed in the speed-activation block', async () => {
  // given: alice deposited before reward speed existed
  const bal = parseEther('100')
  msdTOKEN1.balanceOf.returns(bal)
  msdTOKEN1.totalSupply.returns(bal.mul(10))

  // fund distributor
  await vsp.mint(rewardDistributor.address, parseEther('1000'))

  // governor enables speed for the token (index := INITIAL_INDEX = 1e18, timestamp := now)
  await rewardDistributor.connect(governor).updateTokenSpeed(msdTOKEN1.address, parseEther('1'))

  // when: alice claims in the SAME block (deltaTimestamps == 0, index still INITIAL_INDEX)
  // accountIndexOf == 0 -> deltaIndex = 1e18 -> tokensDelta = balance
  await rewardDistributor.claimRewards(alice.address, [msdTOKEN1.address])

  // then: alice received rewardToken equal to her deposit balance despite 0s of accrual
  expect(await vsp.balanceOf(alice.address)).to.eq(bal) // steals 100 VSP instead of ~0
  expect(await rewardDistributor.tokensAccruedOf(alice.address)).to.eq(0)
})
```

Tested invariant: `_calculateTokenDelta` must yield `tokensDelta == 0` when the index has not moved; here it yields `balance`, and `claimRewards` transfers it because `balance <= distributor rewardToken balance`.
