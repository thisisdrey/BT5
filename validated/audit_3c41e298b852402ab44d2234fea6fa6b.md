### Title
`ValidateMultiSign`/`BatchValidateSign` precompiles let any smart contract validate a signature without binding it to the calling contract or purpose, enabling cross-contract signature replay (Permit2-style front-running) - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `ValidateMultiSign` precompiled contract (and its batch variant `BatchValidateSign`) exposed to the TVM lets a Solidity contract verify that a set of off-chain ECDSA signatures satisfies an account's multisig `Permission` threshold for an arbitrary 32-byte `data` value supplied by the calling contract. The signed digest is only `sha256(account || permissionId || data)` — it never incorporates the identity of the invoking contract, the entry-point/function being authorized, or any other context that scopes the signer's intent. This is exactly the class of bug described in the external report: a signature that only proves "the owner authorized action tied to this opaque hash" can be captured and replayed against *any* other on-chain contract that happens to construct the same hash, since nothing in the precompile output binds the signature's validity to one particular consumer.

### Finding Description
`ValidateMultiSign.execute` computes the message that must be signed purely from caller-supplied inputs (`address`, `permissionId`, `data`) with no `msg.sender`/target-contract binding: [1](#0-0) 

It then recovers each signer address from the supplied signatures over that same hash and sums permission-key weights to decide the pass/fail result, again with no reference to which contract invoked the precompile: [2](#0-1) 

`BatchValidateSign` has the identical structural weakness: it recovers signer addresses for a caller-supplied `hash` and compares them to a caller-supplied address list, again without incorporating which contract is asking or for what purpose: [3](#0-2) 

Because the "witness" data (the `data`/`hash` field) is entirely defined by whichever smart contract calls the precompile, an off-chain signature that an account owner produces to authorize one specific dApp action (e.g., "withdraw from Contract A using permissionId 2, hash H") can be reused verbatim by *any other* contract that happens to derive the same `(address, permissionId, data)` triple, or that a malicious/independently-deployed contract front-runs to consume before the intended integrator's transaction lands. This mirrors the Sablier Permit2 report precisely: the recommendation there was to bind the signature to the specific target contract and function via `permitWitnessTransferFrom`; here, TRON's precompile provides no analogous mechanism to scope validation to a specific consuming contract or call.

### Impact Explanation
Any project that integrates `ValidateMultiSign`/`BatchValidateSign` into custom on-chain multisig/authorization logic (a common documented TRON pattern for building account-abstraction-like flows) is exposed to unauthorized reuse of a user's signature by an unrelated or malicious contract, provided the hash pre-image collides or is guessable/observable on-chain (transaction data is public, so any signature and its pre-image submitted in one contract call is trivially visible and replayable elsewhere before/in-line with front-running). This can lead to unauthorized execution of privileged operations gated by the multisig check in a victim's or unrelated protocol's contract — i.e., unauthorized account operations / theft of funds guarded by that check.

### Likelihood Explanation
Exploitation only requires deploying an ordinary smart contract that also calls the same precompile with an observed `(address, permissionId, data)`/`hash` and a signature copied from a public transaction — fully reachable by an unprivileged contract deployer/caller through a single `TriggerSmartContract` transaction. No special privileges, validator collusion, or node-level access are needed.

### Recommendation
Extend the precompile ABI (or introduce a new one) so the signed digest incorporates the calling contract address (`msg.sender`/`caller()`), and ideally the calling function selector, so a given signature cannot be reused by a caller other than the contract for which the signature was intended. Document clearly, as Sablier did, that any signature verified via `ValidateMultiSign`/`BatchValidateSign` is not scoped to a single application unless that scoping is explicitly embedded in `data` by every consuming contract, and that reuse across independently deployed contracts is possible.

### Proof of Concept
1. Contract A defines a business action gated by `validatemultisign(accountAddr, permissionId, dataHash, sigs)`, where `dataHash = sha256("withdraw:100:nonce7")`.
2. The account owner signs the corresponding digest `sha256(merge(accountAddr, permissionId, dataHash))` off-chain and submits it in a transaction calling Contract A.
3. An attacker observes this signature/hash in the public mempool or block, and deploys/reuses Contract B, which independently derives the same `dataHash` value for a different, attacker-controlled action (e.g., because both contracts use similarly structured hash inputs, or the attacker crafts Contract B's hash scheme to match) and calls the same precompile with the intercepted signature before or alongside Contract A's transaction.
4. Because `ValidateMultiSign.execute` (actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java:1052-1119) validates purely against `(accountAddr, permissionId, dataHash)` with no binding to Contract A, Contract B's call also returns success, letting the attacker execute an unauthorized action attributed to the same signature/threshold approval.
