### Title
Unbounded-depth JSON parsing of peer HTTP error responses can stack-overflow the requesting node - ([File: stackslib/src/net/httpcore.rs])

### Summary
`StacksHttp::try_parse_error_response` deserializes an HTTP error response body directly into `serde_json::Value` with no depth limit, only a byte-size bound. A remote peer serving a crafted error response with deeply nested JSON arrays (e.g. thousands of `[` characters) can drive `serde_json`'s native (non-tail) recursive descent into `Value` deep enough to overflow the requesting node's stack, crashing the process. This mirrors the xgrammar bug class: unbounded nested-syntax recursion during parsing of attacker-controlled input causing a segfault/DoS, except here the "grammar" is JSON array/object nesting and the reader is `stackslib`'s HTTP client-side response parser.

### Finding Description
`try_parse_error_response` bounds only the number of *bytes* read via `BoundReader::from_reader(&mut ioc, MAX_MESSAGE_LEN as u64)`, then calls `serde_json::from_reader` to build an arbitrary `serde_json::Value`: [1](#0-0) 

`serde_json::Value`'s `Deserialize` implementation recurses once per array/object nesting level with no built-in depth cap (unlike e.g. the Clarity value deserializer in this same repo, which explicitly tracks and enforces `MAX_TYPE_DEPTH`/`UNSANITIZED_DEPTH_CHECK` in `clarity-types/src/types/serialization.rs`, or the AST parser in `clarity/src/vm/ast/parser/v2/mod.rs` which explicitly rejects nesting beyond `max_nesting_depth` to "avoid a stack overflow"). No such guard exists here or in the sibling helper `parse_json` in `stackslib/src/net/http/common.rs`: [2](#0-1) 

A body such as `"[".repeat(N) + "]".repeat(N)` costs 2 bytes per nesting level, so within the `MAX_MESSAGE_LEN` (~16 MB) byte bound an attacker can encode millions of nesting levels — far beyond what a typical thread stack (a few MB) can hold, triggering a native stack overflow and process abort. This is directly analogous to the xgrammar PoC, which used 30,000 layers of nested parentheses in a grammar string to overflow the recursive parser's stack and crash the process.

This code path executes on the **client side** — i.e., whenever a Stacks node makes an outbound HTTP request to a peer (e.g., during health checks, block/tx fetches, or other peer RPC calls) and receives back an HTTP status in the 400–599 range with `Content-Type: application/json`. Any peer a node connects to can supply such a response, making this remotely triggerable by an unprivileged, unauthenticated peer with a single crafted response.

### Impact Explanation
This breaks the "few messages cause remote crash" criterion for Critical impact: a malicious or compromised peer can crash any Stacks node that queries it over HTTP, by returning one crafted error response. This is an unauthenticated, remote DoS requiring no more than a single HTTP response and does not rely on volumetric traffic — it exploits algorithmic/stack-depth behavior of the JSON parser, not bandwidth.

### Likelihood Explanation
Likelihood is high for any node that performs outbound HTTP RPC calls to other Stacks nodes (peer discovery, block/tx propagation checks, contrib tooling like `stacks-inspect`'s `P2PSession`, etc.). Triggering requires only that the attacker's node be queried by the victim and respond with a non-2xx status and `application/json` content-type carrying deeply nested arrays/objects — well within reach of any peer that a target node talks to.

### Recommendation
- Enforce an explicit maximum JSON nesting depth before/while parsing untrusted HTTP bodies in `try_parse_error_response` (`stackslib/src/net/httpcore.rs`) and `parse_json` (`stackslib/src/net/http/common.rs`), e.g. by wrapping the `serde_json::Deserializer` with `serde_stacker` (as already done for Clarity value JSON deserialization in `clarity/src/vm/database/structures.rs`) or by pre-validating/limiting bracket nesting depth before deserializing.
- Alternatively, run this deserialization on a guarded stack (the codebase already uses the `stacker` crate elsewhere for exactly this purpose) so deep recursion spills to the heap instead of overflowing the native stack.
- Add a regression test that submits a crafted deeply-nested JSON error response and asserts a graceful parse error rather than a crash.

### Proof of Concept
1. Stand up a malicious HTTP server that a target Stacks node will query (e.g., register as a peer).
2. When the target node issues any HTTP request to this malicious peer, respond with:
   - Status: `500`
   - `Content-Type: application/json`
   - Body: `"[".repeat(2_000_000) + "]".repeat(2_000_000)` (under the ~16 MB `MAX_MESSAGE_LEN` bound).
3. The target node calls `StacksHttp::try_parse_error_response`, which routes the body into `serde_json::from_reader::<serde_json::Value, _>`, recursing once per `[`; the deep recursion overflows the thread stack and crashes the process (or the thread handling the connection), matching the segfault behavior described in the xgrammar advisory.

pub fn parse_json<T: serde::de::DeserializeOwned>(
    preamble: &HttpResponsePreamble,
    body: &[u8],
) -> Result<T, Error> {
    // content-type has to be JSON
    if preamble.content_type != HttpContentType::JSON {
        return Err(Error::DecodeError(
            "Invalid content-type: expected application/json".to_string(),
        ));
    }

    let item_result: Result<T, serde_json::Error> = serde_json::from_slice(body);
    item_result.map_err(|e| {
        if e.is_eof() {
            Error::UnderflowError("Not enough bytes to parse JSON".to_string())
        } else {
            Error::DecodeError(format!("Failed to parse JSON: {:?}", &e))
        }
    })
}
