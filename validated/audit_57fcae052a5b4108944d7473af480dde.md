### Title
Active-permission delegation allows an unprivileged multisig key to overwrite the Owner permission in `AccountPermissionUpdateContract` - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
CVE-2017-12851 describes an authenticated *standard* user resetting the *admin* password in kanboard by altering form fields that the server trusted without re-checking privilege level. The analogous class of bug in java-tron is: a transaction signed only by a low-privileged **Active** permission key is allowed to completely rewrite an account's **Owner** permission (the account's highest-privilege, "admin" credential set) via `AccountPermissionUpdateContract`, as long as the account owner had at some point granted that Active permission the single bit for `AccountPermissionUpdateContract` (type 46) in its operations bitmap.

### Finding Description
Transaction-level authorization for any contract, including `AccountPermissionUpdateContract`, is resolved generically by `permission_id` in `Transaction.Contract`. `TransactionCapsule.validateSignature`/`checkPermission` only requires that, when `permissionId != 0` (i.e., a non-Owner/Active permission is used), the permission type is `Active` and the specific contract type is enabled in that permission's 256-bit `operations` bitmap: [1](#0-0) [2](#0-1) 

There is no additional, contract-type-specific rule that forces `AccountPermissionUpdateContract` to be signed under `permission_id = 0` (Owner). The actuator itself only validates the *structural* correctness of the new permission sets (key counts, thresholds, address validity, operations bitmap) — it never checks that the caller's *current* authority level (the permission actually used to sign the transaction) is Owner: [3](#0-2) 

In `execute()`, the actuator unconditionally overwrites the account's Owner permission, Witness permission and all Active permissions with whatever is supplied in the contract, keyed only by `ownerAddress`: [4](#0-3) 

Because the `AccountPermissionUpdateActuator.checkPermission` validation for a submitted Active permission explicitly permits the bit for `AccountPermissionUpdateContract` (id 46) to be set in its `operations` bitmap: [5](#0-4) 

an account owner can (deliberately or through a mistaken/overly-broad multisig setup) create an Active permission with a very low `threshold` that is allowed to call `AccountPermissionUpdateContract`. Any holder of that low-weight Active key can then broadcast a new `AccountPermissionUpdateContract` — the equivalent of "altering form data" in the CVE — that installs an entirely new Owner permission (new keys, new threshold) chosen by the attacker, permanently displacing the legitimate Owner keys. This mirrors the kanboard bug class: a lower-privilege, authenticated principal is able to overwrite the highest-privilege credential set of another principal because the server-side authorization model does not require Owner-level authority specifically for that irreversible privilege escalation.

### Impact Explanation
Successful exploitation is a full, permanent account takeover: the attacker replaces the Owner permission's key set/threshold with values they control, locking out the legitimate account owner and gaining unilateral control over all subsequent high-privilege operations (fund withdrawal via `AccountUpdateContract`, freezing/unfreezing, further permission rewrites, etc.). Depending on how the compromised account is used (e.g., an exchange hot wallet, DApp treasury, or SR/committee-linked account configured with a broad Active permission for automation), this can result in unauthorized account operations and theft or permanent freezing of funds.

### Likelihood Explanation
Exploitation requires that some Active permission on the target account currently has bit 46 (`AccountPermissionUpdateContract`) enabled in its `operations` field — this is only possible if the account's Owner previously configured such a permission (e.g., to allow an automation/hot-wallet key to manage multisig membership on their behalf, a legitimate and documented use of the operations bitmap). Given that setup, exploitation needs only a single signed transaction from that Active key; no additional privilege is required. The likelihood therefore hinges on prevalence of such delegated configurations in the wild, which I could not verify from the indexed code/tests alone — this is inherent to how the feature is designed rather than a coding defect I can point to as unambiguously unintended.

### Recommendation
- Require that `AccountPermissionUpdateContract` transactions be signed using the Owner permission (`permission_id == 0`) exclusively, rejecting attempts to authorize it via any Active permission's operations bitmap, since it is the single contract type capable of overwriting the account's own authorization structure.
- Alternatively, if delegation is intentionally supported, disallow the delegated Active permission from being able to modify the Owner permission's key set/threshold (e.g., restrict a non-Owner-signed `AccountPermissionUpdateContract` to only touch Active permissions with weight/threshold no greater than the invoking permission, never the Owner permission).
- Add validation in `AccountPermissionUpdateActuator.checkPermission`/`validate()` that rejects setting bit 46 (`AccountPermissionUpdateContract`) in any Active permission's `operations` bitmap.

### Proof of Concept
1. Owner (Owner permission, threshold T_owner, keys {K_owner}) creates an Active permission P_active with `operations` bit 46 set and a low `threshold` (e.g., 1), assigned to key K_delegate, via a legitimately-validated `AccountPermissionUpdateContract` signed with the Owner key. This passes `AccountPermissionUpdateActuator.validate()` since the operations-bit check at lines 137-144 only rejects bits not enabled in `dynamicStore.getAvailableContractType()`, and 46 (`AccountPermissionUpdateContract`) is an available/broadcastable type.
2. Holder of K_delegate crafts a new `AccountPermissionUpdateContract` for the same `ownerAddress`, setting a brand-new Owner permission with only attacker-controlled keys and threshold 1, plus a minimal Active list to satisfy validation (`activesCount` must be 1–8 per lines 201-206).
3. K_delegate signs the transaction using `permission_id = <id of P_active>`. `TransactionCapsule.validateSignature` accepts it because P_active's operations bitmap has bit 46 set and K_delegate's weight meets P_active's threshold — no Owner signature is required.
4. `AccountPermissionUpdateActuator.execute()` unconditionally overwrites the account's Owner permission with the attacker's new permission at line 49-52, completing takeover.

  public static boolean validateSignature(Transaction transaction,
      byte[] hash, AccountStore accountStore, DynamicPropertiesStore dynamicPropertiesStore)
      throws PermissionException, SignatureException, SignatureFormatException {
    Transaction.Contract contract = transaction.getRawData().getContractList().get(0);
    int permissionId = contract.getPermissionId();
    byte[] owner = getOwner(contract);
    AccountCapsule account = accountStore.get(owner);
    Permission permission = null;
    if (account == null) {
      if (permissionId == 0) {
        permission = AccountCapsule.getDefaultPermission(ByteString.copyFrom(owner));
      }
      if (permissionId == 2) {
        permission = AccountCapsule
            .createDefaultActivePermission(ByteString.copyFrom(owner), dynamicPropertiesStore);
      }
    } else {
      permission = account.getPermissionById(permissionId);
    }
    if (permission == null) {
      throw new PermissionException("permission isn't exit");
    }
    checkPermission(permissionId, permission, contract);
    long weight = checkWeight(permission, transaction.getSignatureList(), hash, null);
    if (weight >= permission.getThreshold()) {
      return true;
    }
    return false;
  }

  @Override
  public boolean validate() throws ContractValidateException {

    if (chainBaseManager == null) {
      throw new ContractValidateException(ActuatorConstant.STORE_NOT_EXIST);
    }

    if (this.any == null) {
      throw new ContractValidateException(ActuatorConstant.CONTRACT_NOT_EXIST);
    }

    AccountStore accountStore = chainBaseManager.getAccountStore();
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();

    if (dynamicStore.getAllowMultiSign() != 1) {
      throw new ContractValidateException("multi sign is not allowed, "
          + "need to be opened by the committee");
    }
    if (!this.any.is(AccountPermissionUpdateContract.class)) {
      throw new ContractValidateException(
          "contract type error,expected type [AccountPermissionUpdateContract],real type["
              + any.getClass() + "]");
    }
    final AccountPermissionUpdateContract accountPermissionUpdateContract;
    try {
      accountPermissionUpdateContract = any.unpack(AccountPermissionUpdateContract.class);
    } catch (InvalidProtocolBufferException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractValidateException(e.getMessage());
    }
    byte[] ownerAddress = accountPermissionUpdateContract.getOwnerAddress().toByteArray();
    if (!DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("invalidate ownerAddress");
    }
    AccountCapsule accountCapsule = accountStore.get(ownerAddress);
    if (accountCapsule == null) {
      throw new ContractValidateException("ownerAddress account does not exist");
    }

    if (!accountPermissionUpdateContract.hasOwner()) {
      throw new ContractValidateException("owner permission is missed");
    }

    if (accountCapsule.getIsWitness()) {
      if (!accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("witness permission is missed");
      }
    } else {
      if (accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("account isn't witness can't set witness permission");
      }
    }

    if (accountPermissionUpdateContract.getActivesCount() == 0) {
      throw new ContractValidateException("active permission is missed");
    }
    if (accountPermissionUpdateContract.getActivesCount() > 8) {
      throw new ContractValidateException("active permission is too many");
    }

    Permission owner = accountPermissionUpdateContract.getOwner();
    Permission witness = accountPermissionUpdateContract.getWitness();
    List<Permission> actives = accountPermissionUpdateContract.getActivesList();

    if (owner.getType() != PermissionType.Owner) {
      throw new ContractValidateException("owner permission type is error");
    }
    checkPermission(owner);
    if (accountCapsule.getIsWitness()) {
      if (witness.getType() != PermissionType.Witness) {
        throw new ContractValidateException("witness permission type is error");
      }
      checkPermission(witness);
    }
    for (Permission permission : actives) {
      if (permission.getType() != PermissionType.Active) {
        throw new ContractValidateException("active permission type is error");
      }
      checkPermission(permission);
    }
    return true;
