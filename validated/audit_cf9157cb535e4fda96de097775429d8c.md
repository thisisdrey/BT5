## Finding

### Title
Unbounded array allocation from attacker-controlled length in `BatchValidateSign` precompile causes memory-exhaustion DoS - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The CVE-2023-2618 report describes `DecodedBitStreamParser::decodeHanziSegment` allocating memory based on an attacker-supplied length field without adequate bounding, causing a memory leak/resource exhaustion. The same bug class exists in java-tron's `PrecompiledContracts.extractBytes32Array`, reachable from any TVM `CALL`/`DELEGATECALL` to the `batchvalidatesign` precompile (address `0x9`), which any unprivileged contract-calling transaction can trigger.

### Finding Description
`extractBytes32Array` allocates a `byte[][]` sized directly from an attacker-controlled word without any upper bound: [1](#0-0) 

`BatchValidateSign.doExecute` calls this function for the `addresses` array unconditionally — the `MAX_SIZE` bound check that exists for the *signatures* array is only applied when `VMConfig.allowTvmSelfdestructRestriction()` is enabled, and even then it only guards the signatures length, not the addresses length: [2](#0-1) 

The energy fee charged for calling this precompile is computed purely from the raw call-data length (`(data.length / WORD_SIZE - 5) / 6`), not from the value embedded in the ABI-encoded "array length" word: [3](#0-2) 

Because `DataWord.intValueSafe()` allows values up to `Integer.MAX_VALUE`, a caller can craft small call-data (cheap in energy) where the word used as the address-array length is set to a huge value (e.g. `Integer.MAX_VALUE`). `getEnergyForData` will only charge for the small call-data size, but `extractBytes32Array` will attempt `new byte[Integer.MAX_VALUE][]`, an allocation of roughly 8–17 GB of references on a 64-bit JVM, before any bounds/energy check catches it.

### Impact Explanation
This is a resource-exhaustion condition analogous to the reported OpenCV memory leak: attacker-controlled length drives unbounded allocation prior to any real validation. On java-tron, the allocation happens inside the shared node JVM heap during ordinary block/transaction execution (not sandboxed per-call), so a burst of such calls (or even a single one on a memory-constrained node) can trigger `OutOfMemoryError`, full-GC storms, and node instability/crash — a real availability impact on the executing node, consistent with the CVSS `A:L` component of the original advisory, and potentially larger given java-tron nodes serve production consensus/RPC traffic.

### Likelihood Explanation
The precompile is reachable by any account that can broadcast a `TriggerSmartContract` transaction performing a `CALL`/`DELEGATECALL` to address `0x9` with crafted call data — no special permission or fork-specific state is required beyond `VMConfig.allowTvmSolidity059()` being active (a long-activated feature). The `MAX_SIZE` guard for signatures shows the team already recognized similar unbounded-allocation risk for the signatures array (see `sigArraySize > MAX_SIZE` check and TIP-854 hardening), but the equivalent guard was not applied to the addresses array in `extractBytes32Array`.

### Recommendation
Bound the value read in `extractBytes32Array` (and any other extractor consuming an attacker-supplied length word) to a small `MAX_SIZE` **before** allocating the array, matching the existing pattern used for the signatures array, and ensure the energy cost model reflects the actual length used for allocation rather than only the physical call-data size.

### Proof of Concept
1. Construct call data for `batchvalidatesign(bytes32,bytes[],address[])` where the `addresses` offset word points at a location inside the small call-data buffer whose word value is set to `0x7FFFFFFF` (Integer.MAX_VALUE) instead of a realistic array length.
2. Keep the rest of the call-data minimal (e.g., a single tiny signature entry) so `getEnergyForData` computes a low energy cost that fits comfortably within a small `feeLimit`.
3. Broadcast a `TriggerSmartContract` transaction (or nest the call inside another contract) invoking address `0x9` with this data.
4. Observe `extractBytes32Array` attempt `new byte[2147483647][]`, causing severe memory pressure / `OutOfMemoryError` on the executing node while the transaction was charged only minimal energy.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];

      bytes32Array[i] = words[offset + i + 1].getData();
