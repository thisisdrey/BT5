### Title
Bridged synthetic tokens are minted to the raw destination address, so smart-contract/smart-wallet holders on the source chain permanently lose their tokens on the destination chain - ([File: contracts/ProxyOFT.sol](contracts/ProxyOFT.sol))

### Summary
Metronome's LayerZero `ProxyOFT` burns `SyntheticToken`s on the source chain and mints them on the destination chain to whatever raw `to_` address the sender provides, with no address aliasing, no contract-awareness check, and no receiver-capability verification. This is the same bug class as the Nouns Builder L2-migration issue: tokens belonging to contract addresses on the source chain are credited on the destination chain either to an address that belongs to someone else / nobody, or to an address the source-chain contract cannot act from, so the bridged funds are permanently locked.

### Finding Description
`ProxyOFT.sendFrom` encodes the caller-supplied `to_` verbatim and calls `_send` [1](#0-0) . On the source chain, `_debitFrom` requires `_msgSender() == from_` and burns the tokens [2](#0-1) . On the destination chain, `_sendAck` decodes `to` and `_creditTo` simply calls `syntheticToken.mint(to, amount)` [3](#0-2) [4](#0-3) .

Two loss modes mirror the original report:

1. A contract (multisig, Safe, vault, wallet) holding msUSD/msETH on chain A calls `sendFrom` with `to_ = address(this)`. The same address on chain B is either an unrelated EOA/contract (CREATE2 addresses differ across chains) or empty code; the minted tokens are unspendable by the source-chain holder.
2. Even if the contract is deployed at the same address on both chains, the tokens are locked on the destination chain unless that contract exposes a generic `transfer`/bridge function — the equivalent of the "L1 contract needs OptimismPortal access" condition in the original report. `sendAndCall` is disabled [5](#0-4) , so there is no atomic "credit + call the receiver to forward" path; `onOFTReceived` only fires for `PT_SEND_AND_CALL`, which always reverts.

The burn on the source chain succeeds before the message is sent, and `SyntheticToken._mint` only rejects `account_ == 0` [6](#0-5) , so nothing in the protocol detects or prevents crediting an uncontrollable destination address.

### Impact Explanation
Permanent freezing/loss of user funds: the source-chain tokens are burned, and the destination-chain tokens are minted to an address the holder cannot control. For a contract holding a large synthetic-token balance (e.g., a treasury multisig or yield vault bridging liquidity), the entire bridged amount is irrecoverable — there is no rescue/withdraw path in `SyntheticToken` or `ProxyOFT`.

### Likelihood Explanation
Likelihood is moderate. `sendFrom` is public and unrestricted (only requires bridging active, destination chain supported, and `msg.sender == from_`), so any contract holder of msUSD/msETH can trigger it. Smart-contract wallets and multisigs bridging funds is a routine operation; the only mitigation is user awareness that `to_` must be an address they control on the destination chain — nothing in the code or the disabled `sendAndCall` flow warns or protects them. No privileged role, oracle manipulation, or malicious endpoint is needed; the loss is triggered by the token holder's own transaction.

### Recommendation
- Apply an explicit guard: either require `to_ == from_`/`msg.sender` for contract senders, or reject `sendFrom` when `from_` is a contract and `to_` is not a verified destination-side owner.
- Re-enable `sendAndCall` (or add a `sendToContract` variant) that credits tokens only after a successful `onOFTReceived` handshake acknowledging control, storing the message in `failedOFTReceivedMessages` for retry instead of minting unconditionally.
- Alternatively implement an aliasing/mirroring scheme (credit the L1-style aliased address or a claimable escrow) so contract holders can recover by proving source-chain ownership.

### Proof of Concept
```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.0;

import "forge-std/Test.sol";
import {ProxyOFT} from "../contracts/ProxyOFT.sol";
import {SyntheticToken} from "../contracts/SyntheticToken.sol";

/// @dev Simulates a smart-contract wallet (e.g., Safe) holding msUSD on chain A.
contract SmartWallet {
    function bridge(ProxyOFT oft, uint16 dstChain, uint256 amount) external payable {
        // Wallet naively sends to itself on the destination chain.
        oft.sendFrom{value: msg.value}(address(this), dstChain, address(this), amount);
    }
}

contract ProxyOFTContractHolderLossTest is Test {
    ProxyOFT oftA;      // source chain ProxyOFT
    ProxyOFT oftB;      // destination chain ProxyOFT (same code, different chain)
    SmartWallet walletA;
    // On chain B the same address holds an *unrelated* contract/EOA (CREATE2
    // addresses are chain-independent, deployments are not).

    function test_contractHolderLosesBridgedTokens() public {
        uint16 DST = 110; // e.g., LZ chain id for Arbitrum/Base
        uint256 amount = 100e18;

        // --- Source chain ---
        // walletA holds msUSD and bridges to `address(walletA)` on chain B.
        walletA.bridge{value: 1 ether}(oftA, DST, amount);

        // Burn succeeded on source chain:
        assertEq(synth.balanceOf(address(walletA)), 0); // tokens burned

        // --- Destination chain (delivered by LZ endpoint) ---
        // _sendAck -> _creditTo mints to raw `to` = address(walletA).
        // On chain B this address is a DIFFERENT contract (or empty EOA),
        // not controlled by walletA's owners.
        // Result: balance minted, but walletA's controllers can never move it;
        // no rescue path exists in SyntheticToken/ProxyOFT.
        assertEq(synthB.balanceOf(address(walletA)), amount); // stuck forever
    }
}
```

The PoC is reproducible on a Foundry fork by deploying the repo's `ProxyOFT`/`SyntheticToken` pair on two forks, impersonating the LZ endpoint (as done in `test/SyntheticToken.plasma.test.ts`) to deliver the `PT_SEND` payload, and showing that a source-chain contract caller's burned balance maps to a minted balance at an address it cannot control on the destination chain, with `sendAndCall` reverting so no receiver hook can save it.
