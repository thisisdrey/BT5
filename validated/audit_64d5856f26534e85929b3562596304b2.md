### Title
Unfunded-eviction of legitimately fee-paying transactions from the bounded `TransactionStateContainer` via unbacked high-priority spam - (File: core/src/banking_stage/transaction_scheduler/receive_and_buffer.rs)

### Summary
`TransactionStateContainer::push_ids_into_queue` maintains a fixed-capacity priority queue and, when full, evicts the *lowest-priority* buffered transaction to admit a new arrival, exactly like the CLOB `_removeNonCompetitiveOrder` pattern that evicts the worst resting order to admit a new one. [1](#0-0)  Before admission, the only defense is `Consumer::check_fee_payer_unlocked`, which checks that the fee-payer's *current on-chain balance* covers the declared fee, but does not debit or reserve that balance against other pending/buffered transactions from the same fee payer. [2](#0-1)  and is invoked per-transaction in the receive loop right before insertion into the priority queue. [3](#0-2) 

### Finding Description
The eviction mechanism mirrors the CLOB bug class: a bounded, priority-ordered container silently discards the lowest-priority legitimate entry whenever a higher-"priority" entry arrives, so a cheap/unbacked flood of high-priority claims can wipe out real, fully-payable, low(er)-priority entries. In the CLOB case the attacker's fake orders cost nothing because they expire or are canceled before ever filling; in agave the analogous "free" claim is a declared compute-unit-price/priority that is never actually charged unless the transaction lands in a block.

`check_fee_payer_unlocked` re-reads the fee payer's balance straight from the bank (`bank.rc.accounts.load_with_fixed_root`) for every transaction independently [4](#0-3) , and this balance is not decremented or reserved for transactions that are merely sitting in the (not-yet-executed) buffer. Consequently, a single funded account with a balance sufficient to cover only one transaction's fee can pass `check_fee_payer_unlocked` for many transactions submitted in the same receive window (each check independently sees the same un-debited on-chain balance). Each of these transactions can then be assigned an arbitrarily high priority fee, causing `push_ids_into_queue` to evict genuinely fee-paying, lower-priority transactions from other users out of the fixed-capacity container. [5](#0-4)  Only one (or none, if none land within `max_processing_age`) of the attacker's transactions can ever actually execute and pay a fee; the rest simply expire (blockhash aged out) and are dropped for free, just as CLOB orders expire and refund for free.

The `forwarding_stage`'s `PacketContainer` exhibits the identical pattern (evict-min-on-full) purely on unauthenticated packet priority with even less validation than the buffering path. [6](#0-5) [7](#0-6) 

### Impact Explanation
This allows an unprivileged network participant to repeatedly clear out other users' legitimately fee-paying transactions from the leader's bounded transaction buffer (`TransactionStateContainer`, capacity-limited) using a single modestly-funded account, at negligible actual cost (only the balance-check floor, never the real fee, since the flood transactions are engineered to age out rather than land). This is a QoS/fee-market evasion: it lets an attacker deny block inclusion to competing, properly-paying transactions without paying commensurate fees, degrading fairness of the priority-fee-based admission model that banking stage/`transaction_scheduler` is designed to enforce.

### Likelihood Explanation
Moderate-to-high. The attack requires no special privileges — only a single funded keypair and the ability to submit many transactions with high declared `compute_unit_price` but blockhashes/structures chosen to guarantee they never actually execute (or execute and fail cheaply) before their `max_processing_age` window elapses. No coordination with the target's specific transactions is needed; the container is FIFO/priority-bounded per validator and shared by all incoming traffic, so continuous submission at high declared priority reliably wins eviction races against genuine lower-fee traffic during periods of buffer saturation (exactly the periods when this protection matters most).

### Recommendation
- Track and reserve/decrement a "pending obligation" per fee payer across all currently-buffered (not-yet-executed) transactions in `TransactionStateContainer`/`TransactionViewStateContainer`, so `check_fee_payer_unlocked` reflects total outstanding fee liabilities, not just the raw committed on-chain balance.
- Cap the number of buffered/queued transactions permitted per fee payer (or per signer) at any time, similar to per-address limits used elsewhere in banking stage, to prevent a single account from occupying an outsized share of the bounded container via high declared, but uncommitted, priority.
- Consider disallowing eviction of a transaction whose priority is only marginally lower, or require a minimum bank-lifetime/age before an incoming transaction is eligible to evict, reducing the value of instantaneously-expiring high-priority spam (an analog to the reporter's "minimum order liveness" recommendation).

### Proof of Concept
1. Fund one keypair `F` with enough lamports to pay exactly one maximum-fee transaction.
2. Submit `N` transactions from `F` in rapid succession, each with a very high `ComputeBudgetInstruction::set_compute_unit_price` (driving `priority` high in `TransactionPriorityId`), and each referencing a blockhash chosen so it will not be selected/executed before it ages out (e.g., differing nonce/duplicate-lock structuring, or simply submitting far more than the leader can execute per slot).
3. Each transaction independently passes `check_fee_payer_unlocked` because the check reads the same un-decremented on-chain balance of `F` each time. [2](#0-1) 
4. Each is inserted via `push_ids_into_queue`; because the container is at capacity, the lowest-priority entries (other users' legitimately funded, lower-priority-fee transactions) are evicted to make room. [1](#0-0) 
5. Only up to one of `F`'s transactions can actually land (limited by real balance); the rest expire for free once their blockhash/max-age is exceeded, while the evicted legitimate transactions are permanently lost from that buffering window.

use {min_max_heap::MinMaxHeap, solana_perf::packet::BytesPacket};

/// Container for storing packets and their priorities.
pub struct PacketContainer(MinMaxHeap<PacketContainerEntry>);

impl PacketContainer {
    pub fn with_capacity(capacity: usize) -> Self {
        Self(MinMaxHeap::with_capacity(capacity))
    }

    pub fn is_empty(&self) -> bool {
        self.0.is_empty()
    }

    pub fn is_full(&self) -> bool {
        self.0.len() == self.0.capacity()
    }

    pub fn min_priority(&self) -> Option<u64> {
        self.0.peek_min().map(|entry| entry.priority)
    }

    pub fn pop_max(&mut self) -> Option<BytesPacket> {
        self.0.pop_max().map(|entry| entry.packet)
    }

    pub fn pop_min(&mut self) -> Option<BytesPacket> {
        self.0.pop_min().map(|entry| entry.packet)
    }

    pub fn insert(&mut self, packet: BytesPacket, priority: u64) {
        self.0.push(PacketContainerEntry::new(packet, priority));
    }
