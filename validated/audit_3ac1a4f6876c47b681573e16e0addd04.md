### Title
StackerDB chunk signatures are not bound to the target contract/slot's identity, enabling cross-contract chunk replay - (File: `libstackerdb/src/libstackerdb.rs`, `stackslib/src/net/stackerdb/mod.rs`)

### Summary
`SlotMetadata::auth_digest()` in `libstackerdb/src/libstackerdb.rs` computes the signed digest as `hash(slot_id || slot_version || data_hash)`, and `SlotMetadata::verify()`/`StackerDBChunkData::verify()` check only that this digest recovers to the expected signer address for a given `(smart_contract_id, slot_id)` pair looked up separately from the wire message's own `contract_id`. The digest itself never incorporates the target `smart_contract_id`. This is the same missing-binding class as the reported Tendermint light-client bug: signatures authenticate content and slot coordinates, but not the "chain"/domain (here, the specific StackerDB contract) they were intended for.

### Finding Description
`validate_received_chunk` in `stackslib/src/net/stackerdb/mod.rs` (around lines 649-718) takes a `smart_contract_id` argument, uses it only to fetch the expected signer address via `self.stackerdbs.get_slot_signer(smart_contract_id, data.slot_id)` [1](#0-0) , then calls `slot_metadata.verify(&addr)`, which recomputes `auth_digest()` from only `slot_id`, `slot_version`, and `data_hash` [2](#0-1) . The `contract_id` that scopes which StackerDB the chunk is destined for is carried out-of-band in `StackerDBPushChunkData.contract_id` on the wire (see `handle_unsolicited_StackerDBPushChunk`, which forwards `chunk_data.contract_id` only to fetch inventory/staleness state, not into the signature check) [3](#0-2) .

The `.signers` boot contracts allocate slot IDs deterministically: for a given reward cycle's signer set, slot assignment is sorted by public-key bytes and is identical across every one of the parallel per-message-type contracts (`.signers-{0|1}-{message_id}` for `message_id` in `0..SIGNER_SLOTS_PER_USER`), as shown by the Clar contract `stackerdb-get-signer-slots-page` and the test `signers_db_get_slots`, which asserts the same slot list is returned for every `message_id` in a reward cycle [4](#0-3) [5](#0-4) . Consequently, a signer address that owns slot `S` in `.signers-0-3` (e.g. the `BlockResponse` message slot) also owns slot `S` in `.signers-0-7` (e.g. `StateMachineUpdate`) for the same reward cycle.

Because the signed digest omits `contract_id`, any chunk legitimately observed on the wire for one contract/message-type can be repackaged into a `StackerDBPushChunkData` (or POST /v2/stackerdb request) naming a different sibling contract, with the same `slot_id`, `slot_version`, `sig`, and `data`. `validate_received_chunk`/`get_slot_signer` will resolve the same signer address for that slot in the new contract, `slot_metadata.verify(&addr)` will still succeed (since the digest never included which contract it targeted), and the version/size checks operate purely on the new contract's own state — so the chunk can be accepted and stored/gossiped as if it were legitimately produced for that contract/message type.

### Impact Explanation
This breaks the implicit equality "chunk signed for contract A" == "chunk accepted into contract A" — an unprivileged network peer (or relayer) who observes any signer's legitimately-signed chunk can replay it as authenticated content into a different `.signers-*` StackerDB contract belonging to the same signer, causing forged-data propagation of one message type's bytes into another message type's slot within the P2P StackerDB replication network. Downstream consumers key off the contract/slot identity to interpret payload semantics (`SignerEvent::<SignerMessageV0>::try_from`, `StackerDBListener::run`), so cross-contract/cross-message-type replay can inject bytes that get mis-deserialized or misattributed to the wrong message class for a signer, propagating through the StackerDB gossip network to every replica. This matches the "network-wide propagation of forged data" / unauthorized StackerDB write bar for Critical-severity findings in this program.

### Likelihood Explanation
The attack requires no privileged key material — it only requires observing one validly-signed, publicly-gossiped chunk (StackerDB chunks are explicitly not confidential) and re-sending it with a different `contract_id` to a peer's unsolicited-push or push-chunk RPC endpoint. Since slot allocation is provably identical across the sibling `.signers-{set}-{message_id}` contracts for a given reward cycle, the precondition (same signer owns the same slot ID in a different sibling contract) is a structural guarantee of the boot contract, not a probabilistic coincidence — making this highly reachable whenever a target signer participates in more than one message-slot contract in a cycle, which is the normal case.

### Recommendation
Bind the signed digest to the specific StackerDB contract (and ideally to the current chain view like `rc_consensus_hash`), not just `(slot_id, slot_version, data_hash)`. Concretely, include `smart_contract_id` (and reward cycle/message-type discriminant) inside `SlotMetadata::auth_digest()` in `libstackerdb/src/libstackerdb.rs`, and thread that context through `sign()`/`verify()` call sites in `stackslib/src/net/stackerdb/mod.rs` (`validate_received_chunk`) and any RPC-side chunk validators. Add regression tests that take a validly-signed chunk from one `.signers-*` contract and assert it is rejected when replayed against a sibling contract with the same signer/slot mapping.

### Proof of Concept
1. Set up two nodes participating in reward cycle `N`, with signer `X` owning slot `3` in both `.signers-0-3` and `.signers-0-7` (guaranteed by the deterministic, identical slot ordering shown in `signers_db_get_slots`).
2. Signer `X` legitimately signs and pushes chunk `C = StackerDBChunkData{slot_id:3, slot_version:5, sig, data}` to `.signers-0-3` (e.g., a `BlockResponse` payload).
3. An unprivileged observer captures `C` from gossip/relay traffic (chunks are not encrypted/private).
4. The observer crafts `StackerDBPushChunkData{contract_id: <.signers-0-7 id>, rc_consensus_hash: current, chunk_data: C}` and sends it via P2P `StackerDBPushChunk` (or POST v2/stackerdb-chunk) to a node.
5. `handle_unsolicited_StackerDBPushChunk` → `validate_received_chunk` looks up the signer for slot 3 in `.signers-0-7`, finds it is also `X`, calls `slot_metadata.verify(&addr)` using only `(slot_id, slot_version, data_hash)` — which matches — and the chunk is accepted/stored into `.signers-0-7`'s slot 3, even though it was never signed for that contract.

*Note:* Full confirmation of downstream message-type parsing behavior (exact effect once the wrong-typed bytes land in `StateMachineUpdate` vs `BlockResponse` slots, e.g., in `SignerEvent::<SignerMessageV0>::try_from` in `libsigner/src/events.rs`) was not fully traced due to iteration limits; the root-cause signature-binding gap in `libstackerdb/src/libstackerdb.rs` and `stackslib/src/net/stackerdb/mod.rs::validate_received_chunk` is confirmed directly from code.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Sign this slot metadata, committing to slot_id, slot_version, and
    /// data_hash.  Sets self.signature to the signature.
    /// Fails if the underlying crypto library fails
    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
