### Title
Unbounded `pages` in `GetAttachmentsInvResponse` enables bounded compute DoS in `get_prioritized_attachments_requests` - (File: `stackslib/src/net/atlas/download.rs`, `stackslib/src/net/api/getattachmentsinv.rs`)

### Summary
A malicious Atlas sync peer (a node chosen from `get_outbound_sync_peers`) can reply to a `/v2/attachments/inv` request with a JSON body containing thousands of `AttachmentPage` entries instead of at most `MAX_ATTACHMENT_INV_PAGES_PER_REQUEST` (8). This response is decoded and stored unchecked, then linearly scanned per missing attachment, causing disproportionate CPU cost on the requester per response.

### Finding Description
`RPCGetAttachmentsInvRequestHandler::try_handle_request` enforces the 8-page cap only on the incoming `page_indexes` request parameter [1](#0-0) . However, `StacksHttpResponse::decode_atlas_attachments_inv_response`, used by the requester to parse a peer's HTTP response, does a bare `serde_json::from_value` into `GetAttachmentsInvResponse` with no size check on `pages` [2](#0-1) . `AttachmentPage` and `GetAttachmentsInvResponse` derive plain `Serialize`/`Deserialize` with no `#[serde(deny_unknown_fields)]` or length validators [3](#0-2) .

The decoded response is stored into `AttachmentsBatchStateContext::inventories` via `extend_with_inventories` without any re-validation of `response.pages.len()` [4](#0-3) . Later, `get_prioritized_attachments_requests` iterates `self.inventories.iter()`, and for every missing attachment does `response.pages.iter().find(|page| page.index == page_index)` — a linear scan of the attacker-controlled `pages` vector — for every peer response and every missing attachment instance [5](#0-4) . This makes per-response iteration cost proportional to attacker-controlled `pages.len()` rather than the bounded 8 the protocol intends.

### Impact Explanation
This is a bounded compute DoS on the requester side: a single malicious/compromised outbound Atlas peer can force the requesting node to do O(pages) work per missing attachment on every processed batch, inflating CPU usage of the `AttachmentsDownloader::run` state machine. It does not corrupt state, forge attachments, or crash the node outright — the `AttachmentPage.inventory: Vec<u8>` values are just bytes checked against index positions, so no out-of-bounds panic occurs (`.get(position_in_page as usize)` safely returns `None` if out of range). The severity is bounded compute DoS on a background sync path (not a "read endpoint" served to clients), and the cost is still bounded by the overall HTTP body size limits enforced by the generic HTTP layer (`max_len`/content-length checks) elsewhere in `net/http`, meaning the attacker cannot achieve unbounded memory/CPU beyond what a single large HTTP body already allows.

### Likelihood Explanation
Requires the attacker to already be one of the node's configured outbound Atlas sync peers (`network.get_outbound_sync_peers()`), i.e., a peer that node has decided to sync attachments from — not an arbitrary unauthenticated party dictating this endpoint. The attack is repeatable per attachment-batch cycle but only affects the atlas download background state machine's linear scan cost, not consensus-critical state.

### Recommendation
Enforce `pages.len() <= MAX_ATTACHMENT_INV_PAGES_PER_REQUEST` (and validate that `page.index` values are within the originally requested `pages` set) inside `decode_atlas_attachments_inv_response` before accepting the response into `inventories`, rejecting/treating as a faulty peer otherwise.

### Proof of Concept
Add a test in `stackslib::net::atlas::download::tests` (or `net::api::tests::getattachmentsinv`) that constructs a `StacksHttpResponse` with a JSON body for `GetAttachmentsInvResponse { block_id, pages: vec![AttachmentPage{index:0,inventory:vec![0]}; 100_000] }`, call `.decode_atlas_attachments_inv_response()` and assert it succeeds despite `pages.len() > MAX_ATTACHMENT_INV_PAGES_PER_REQUEST`; then insert into `AttachmentsBatchStateContext::inventories` and benchmark `get_prioritized_attachments_requests` to show cost scales linearly with the oversized `pages` vector, whereas a compliant peer response is capped at 8 pages.
