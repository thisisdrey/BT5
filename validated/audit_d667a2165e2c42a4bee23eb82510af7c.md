## Title
Missing slippage protection in `ExchangeInjectContract`/`ExchangeWithdrawContract` enables liquidity sandwich attacks on TRON's Bancor-style Exchange - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
TRON's built-in Bancor-style `Exchange` (token-pair AMM pool) supports adding/removing liquidity via `ExchangeInjectContract` and `ExchangeWithdrawContract`. Unlike the swap contract `ExchangeTransactionContract`, which carries an `expected` minimum-output field for slippage protection, neither `ExchangeInjectContract` nor `ExchangeWithdrawContract` carries any minimum/maximum bound on the calculated "other token" amount. This mirrors the reported Napier issue: liquidity is added/removed at the pool's *current* ratio with no slippage guard, so an attacker can manipulate the pool ratio immediately before the victim's inject/withdraw transaction and reverse it immediately after, extracting value from the victim exactly like a reverse-LP sandwich.

### Finding Description
`ExchangeInjectContract` only carries `owner_address`, `exchange_id`, `token_id`, and `quant` — there is no expected/min-out parameter: [1](#0-0) 

In `ExchangeInjectActuator.execute`/`doValidate`, the amount of the paired token required (`anotherTokenQuant`) is derived purely from the *current* on-chain pool ratio (`firstTokenBalance`/`secondTokenBalance`) at execution time, with no caller-supplied bound to reject an unfavorable ratio: [2](#0-1) [3](#0-2) 

The pool ratio itself is trivially moved by any account submitting an `ExchangeTransactionContract` swap, which calls `ExchangeCapsule.transaction`, mutating `firstTokenBalance`/`secondTokenBalance` in the same store the inject actuator reads: [4](#0-3) 

Because block producers order transactions and an attacker can place a swap immediately before and after the victim's inject transaction (front-run/back-run within the same block), the attacker can:
1. Swap to skew the pool ratio (front-run).
2. Let the victim's `ExchangeInjectContract` execute — it deposits both tokens proportional to the *skewed* ratio, effectively donating one token at a disadvantageous ratio.
3. Swap back to restore the ratio (back-run), extracting the excess value contributed by the victim.

`ExchangeWithdrawActuator` has the identical structural weakness: `anotherTokenQuant` for a withdrawal is computed from the live ratio only, with a precision-rounding check but no user-supplied min/max slippage bound: [5](#0-4) 

This is reachable from any unprivileged, signed broadcast transaction — no privileged relationship is needed since any account holding the relevant tokens/TRX can inject or withdraw liquidity from any existing exchange, or create their own and let others use it.

### Impact Explanation
A victim who injects liquidity or withdraws liquidity from a `Exchange` pool can be sandwiched, losing value to an attacker who manipulates the pool ratio around the victim's transaction — a direct, unauthorized transfer of value (theft) from the victim to the attacker, matching the "unauthorized account operation / theft of funds" bar. Because `Exchange` pools handle both TRX and TRC10 assets and any account can trade against them via `ExchangeTransactionContract`, this is broadly exploitable against any liquidity-providing transaction.

### Likelihood Explanation
Likelihood is high: exploiting this requires only ordinary signed transactions (`ExchangeTransactionContract` swap, `ExchangeInjectContract`/`ExchangeWithdrawContract`) that any account can broadcast, and transaction ordering within a block/mempool is influenceable by the attacker (front-run/back-run), which is a well-known, low-cost MEV-style pattern already proven against Bancor/constant-product style pools elsewhere.

### Recommendation
Add slippage-protection fields to `ExchangeInjectContract` and `ExchangeWithdrawContract` (e.g., `expected_another_token_min`/`max`), and enforce them in `ExchangeInjectActuator.doValidate`/`execute` and `ExchangeWithdrawActuator.doValidate`/`execute`, rejecting the transaction if the actual calculated `anotherTokenQuant` falls outside the caller-specified bound — analogous to the existing `expected` field already present in `ExchangeTransactionContract`.

### Proof of Concept
1. Attacker observes a pending `ExchangeInjectContract` transaction from victim (e.g., in mempool) targeting `exchange_id = X`, injecting `quant` of `token_id = A`.
2. Attacker submits `ExchangeTransactionContract` selling a large amount of `A` into the pool (via `ExchangeCapsule.transaction`), skewing `firstTokenBalance`/`secondTokenBalance` heavily in favor of `A`.
3. Victim's `ExchangeInjectContract` executes: `anotherTokenQuant` is computed against the skewed ratio (`ExchangeInjectActuator.execute`, lines 71-83), forcing the victim to inject a disadvantageous amount of the paired token `B`.
4. Attacker submits a second `ExchangeTransactionContract` selling `B` back for `A`, restoring the ratio and extracting the value differential contributed by the victim's injection — net profit to attacker, net loss to victim.

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;

          : secondTokenBalance + sellTokenQuant;

      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();
