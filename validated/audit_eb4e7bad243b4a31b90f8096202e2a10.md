### Title
Missing zero/unspecified-address validation in relay control message handling allows remote-triggered relay state poisoning - (File: relay_manager.go)

### Summary
`relayManager.HandleControlMsg` in `relay_manager.go` validates `CreateRelayRequest`/`CreateRelayResponse` control messages only for nil `RelayFromAddr`/`RelayToAddr` protobuf pointers, but never checks whether the decoded `netip.Addr` values are the zero/unspecified address (e.g. `0.0.0.0`) or otherwise semantically invalid before they are used as VPN-address keys in `AddRelay`, `relayState.InsertRelay`, `hostmap.QueryVpnAddr`, and `f.Handshake`. This mirrors the reported EthBridge pattern where an address-typed input parameter (`_to`) is accepted without a zero-address sanity check, leading to undefined downstream behavior.

### Finding Description
In `relay_manager.go`, `HandleControlMsg` decodes `Addr` protobuf values and only guards against `nil` pointers: [1](#0-0) 

It does not call `IsValid()`/`IsUnspecified()` on the resulting `netip.Addr` from `protoAddrToNetAddr(m.RelayFromAddr)` / `protoAddrToNetAddr(m.RelayToAddr)`. These addresses (`from`, `target`) then flow directly into `handleCreateRelayRequest`: [2](#0-1) 

and are used to key relay state (`AddRelay`, `h.relayState.InsertRelay`), to query the hostmap (`rm.hostmap.QueryVpnAddr(target)`), and to initiate new handshakes (`f.Handshake(target)`): [3](#0-2) 

A remote (unauthenticated at this validation layer — any established peer, or a value forwarded through a relay) can supply a `RelayFromAddr`/`RelayToAddr` that decodes to `0.0.0.0` (a non-nil but zero-valued `Addr{Hi:0, Lo:0}`), which passes the current nil-check unharmed, unlike the certificate-parsing code elsewhere that explicitly rejects `network.Addr().IsUnspecified()` for VPN networks: [4](#0-3) 
No equivalent check exists for the relay-address path in `relay_manager.go`.

The existing unit test confirms the validation intentionally only targets nil-ness, not zero-address semantics: [5](#0-4) 

### Impact Explanation
Accepting an unspecified/zero VPN address as a relay "from" or "to" endpoint allows a peer to:
- Register bogus relay state (`AddRelay`, `InsertRelay`) keyed by `0.0.0.0`, polluting a legitimate host's `RelayState` maps (remote state poisoning).
- Force `f.Handshake(0.0.0.0)` to be invoked, or `rm.hostmap.QueryVpnAddr` lookups on an invalid address, wasting resources and potentially interfering with the relay bookkeeping used to route real traffic through/around the victim.
- Because relay indices and relay state are per-address, a poisoned zero-address entry could shadow or collide with legitimate relay accounting, degrading connectivity for the affected host without requiring the attacker to hold a valid certificate for `0.0.0.0` (since `0.0.0.0`/unspecified networks are already explicitly disallowed for certificates by design elsewhere in the codebase, showing the invariant is expected but not enforced here).

This does not directly bypass certificate/handshake authentication or decrypt traffic, but it is a reachable "unchecked zero address" analog that results in relay/hostmap state corruption triggerable by any already-tunneled peer sending a crafted Control message.

### Likelihood Explanation
Moderate-to-high: this code path is reachable by any peer that has an established Nebula tunnel (`header.Control` messages are processed post-decryption in `outside.go`'s `readOutsidePackets`) — no certificate-signing authority is needed beyond having a valid tunnel, and relayed peers as well, since `via.IsRelayed` isn't checked in `HandleControlMsg`. Constructing a `NebulaControl` message with `RelayFromAddr`/`RelayToAddr` set to `Addr{Hi:0,Lo:0}` is trivial.

### Recommendation
In `relay_manager.go`'s `HandleControlMsg` validation block, after decoding `RelayFromAddr`/`RelayToAddr` via `protoAddrToNetAddr`, explicitly reject the message (with a debug/error log, mirroring the existing nil-check pattern) if either resulting address `!IsValid()` or `IsUnspecified()`, before dispatching to `handleCreateRelayRequest`/`handleCreateRelayResponse`.

### Proof of Concept
1. Establish a tunnel between an attacker-controlled node and the target (a normal, certificate-valid handshake is sufficient — no special CA is required).
2. Send a `header.Control` packet carrying a marshaled `NebulaControl{Type: NebulaControl_CreateRelayRequest, RelayFromAddr: &Addr{Hi:0, Lo:0}, RelayToAddr: &Addr{Hi:0, Lo:0}, InitiatorRelayIndex: <n>}`.
3. Observe (per the code path in `relay_manager.go` lines 320-334 and 426-536) that the message passes the nil-check and is processed: `protoAddrToNetAddr` yields the unspecified `netip.Addr{}`("0.0.0.0"), which is then used to key relay state via `AddRelay`/`InsertRelay` and to attempt `rm.hostmap.QueryVpnAddr`/`f.Handshake` — with no rejection for the zero address, unlike the equivalent check present in certificate validation (`cert/cert_v2.go` lines 404-411).
