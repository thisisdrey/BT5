### Title
Unbounded-length `sellTokenId`/`buyTokenId` in `MarketSellAssetContract` causes uncaught `ArrayIndexOutOfBoundsException` when copied into a fixed-size buffer - ([File: chainbase/src/main/java/org/tron/core/capsule/utils/MarketUtils.java])

### Summary
`TransactionUtil.isNumber()` validates only that the `sellTokenId`/`buyTokenId` byte arrays consist of ASCII digits — it enforces no maximum length. These attacker-controlled byte arrays are later copied with `System.arraycopy` into fixed-size buffers sized `MarketUtils.TOKEN_ID_LENGTH` (19 bytes) without any length check first, mirroring the CVE-2016-8658 pattern of an unbounded, attacker-supplied field (the kernel SSID Information Element) being copied into a fixed-size buffer without a prior bounds check.

### Finding Description
`MarketSellAssetActuator.validate()` only checks that `sellTokenId`/`buyTokenId` are `"_"` or pass `isNumber()`: [1](#0-0) 

`TransactionUtil.isNumber()` (chainbase) only verifies digit characters and rejects a leading zero — it never limits the array length: [2](#0-1) 

`MarketUtils.checkTokenValid`/`checkPairValid`, used elsewhere on the same fields, likewise delegate only to `isNumber` with no length bound: [3](#0-2) 

Downstream, `MarketUtils` builds fixed-size key buffers assuming each token id fits in `TOKEN_ID_LENGTH` (19) bytes, and copies the caller-supplied byte arrays into them with `System.arraycopy` using the *actual* (unbounded) length of the input rather than the fixed slot size: [4](#0-3) [5](#0-4) [6](#0-5) 

If a caller supplies `sellTokenId` (a pure-digit string, e.g. many repeated `9` characters) longer than `TOKEN_ID_LENGTH` bytes, `doCreatePairPriceKey`/`createPairKey` will attempt to write the second field (`buyTokenId`) at an offset (`TOKEN_ID_LENGTH`) that is smaller than where the first field's copy actually ended, and/or write past the fixed-size destination array bounds, throwing an uncaught `ArrayIndexOutOfBoundsException`.

`MarketSellAssetActuator.execute()` only catches a narrow, explicit set of exception types: [7](#0-6) 

An `ArrayIndexOutOfBoundsException` (a `RuntimeException`) is not among the caught types, so it propagates out of `execute()` during block application/transaction processing.

### Impact Explanation
This is directly reachable by any account that can broadcast a `MarketSellAssetContract` transaction (an unprivileged order placer), matching the in-scope category "exchange and market order handling." An uncaught `RuntimeException` thrown from an actuator during transaction execution inside block application can crash or halt node processing of that block, which the validation rules explicitly accept as impact ("node crash or halt"). This is analogous to CVE-2016-8658, where an unbounded, user-controlled length field (SSID) copied into a fixed-size buffer without a length check caused a crash.

### Likelihood Explanation
Likelihood is high for triggering the exception: constructing a purely numeric `sellTokenId`/`buyTokenId` string longer than 19 bytes is trivial (e.g., a string of digits like `"99999999999999999999999999999999"`), and no other check in `validate()` bounds the length before the value reaches `MarketUtils`. However, I was not able to fully trace, within the available tool budget, the exact call path from `MarketSellAssetActuator.execute()`/`matchOrder()` into `MarketUtils.createPairKey`/`createPairPriceKey` (via `MarketPairToPriceStore`) to conclusively confirm that this specific overflow triggers during `execute()` rather than only during off-path lookups — this should be verified with a live test before treating this as fully confirmed.

### Recommendation
Add an explicit maximum length check (e.g., `sellTokenId.length <= MarketUtils.TOKEN_ID_LENGTH` and same for `buyTokenId`) in `MarketSellAssetActuator.validate()` (and any other actuator/validator using `MarketUtils.checkTokenValid`/`checkPairValid`), rejecting the transaction with a `ContractValidateException` before it reaches any fixed-size buffer construction code in `MarketUtils`.

### Proof of Concept
1. Craft a `MarketSellAssetContract` transaction with:
   - `sell_token_id` = a byte string of digits longer than 19 bytes (e.g., 30 `'9'` characters).
   - `buy_token_id` = `"_"` (TRX) or another valid short numeric id.
   - Valid `owner_address` with sufficient balance, valid `sell_token_quantity`/`buy_token_quantity` within `quantityLimit`.
2. Broadcast the signed transaction so it passes `MarketSellAssetActuator.validate()` (all current checks pass since `isNumber` does not bound length).
3. During `execute()`/order matching, `MarketUtils.createPairKey`/`createPairPriceKey` is invoked with the oversized `sellTokenId`, causing `System.arraycopy` to write beyond the fixed 38-byte destination array, throwing an uncaught `ArrayIndexOutOfBoundsException` that is not handled by the actuator's catch clauses.

  public static boolean isNumber(byte[] id) {
    if (ArrayUtils.isEmpty(id)) {
      return false;
    }
    for (byte b : id) {
      if (b < '0' || b > '9') {
        return false;
      }
    }

    return !(id.length > 1 && id[0] == '0');
  }

  public static final int TOKEN_ID_LENGTH = ByteArray
      .fromString(Long.toString(Long.MAX_VALUE)).length; // 19

  public static byte[] calculateOrderId(ByteString address, byte[] sellTokenId,
      byte[] buyTokenId, long count) {

    byte[] addressByteArray = address.toByteArray();
    byte[] countByteArray = ByteArray.fromLong(count);

    byte[] result = new byte[addressByteArray.length + TOKEN_ID_LENGTH
        + TOKEN_ID_LENGTH + countByteArray.length];

    System.arraycopy(addressByteArray, 0, result, 0, addressByteArray.length);
    System.arraycopy(sellTokenId, 0, result, addressByteArray.length, sellTokenId.length);
    System.arraycopy(buyTokenId, 0, result, addressByteArray.length + TOKEN_ID_LENGTH,
        buyTokenId.length);
    System.arraycopy(countByteArray, 0, result, addressByteArray.length
        + TOKEN_ID_LENGTH + TOKEN_ID_LENGTH, countByteArray.length);

    return Hash.sha3(result);
  }
