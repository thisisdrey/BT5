### Title
Unbounded per-element ASN.1 parsing loops in unauthenticated certificate details allow pre-verification CPU exhaustion - (File: cert/cert_v2.go)

### Summary
The external report describes gas-expensive `for` loops in Swapnet-Lite's liquidation path whose iteration count scales with attacker-influenced state (`portfolio.length`), unbounded except by the block gas limit, and reachable before any privileged check completes. The closest reachable analog in this Go codebase is `unmarshalDetails` in `cert/cert_v2.go`, which loops once per encoded network, unsafe-network, and group entry inside a V2 certificate — and this parsing runs during handshake processing on an unauthenticated peer's certificate *before* any CA-pool signature verification occurs.

### Finding Description
`unmarshalCertificateV2` reads the certificate envelope and hands the details sub-string to `unmarshalDetails`, which contains three independent `for !subString.Empty()` loops — one each for `networks`, `unsafeNetworks`, and `groups` — with no cap on the *number* of entries, only a per-entry length cap (`MaxNetworkLength = 17`) and an overall certificate size cap (`MaxCertificateSize = 65536`): [1](#0-0) [2](#0-1) [3](#0-2) 

Because ASN.1 OCTET_STRING/UTF8String entries can be encoded with minimal length (a network prefix can be as small as ~2 bytes, a group string as small as 1 byte plus tag/length overhead), an attacker can pack tens of thousands of minimal entries into a single ~64KB certificate payload, driving each of these loops through many thousands of iterations of allocation (`append`) and prefix/string decoding.

Critically, this parsing occurs on `handshake/machine.go`'s `validateCert`, which calls `cert.Recombine` → `unmarshalCertificateV2` → `unmarshalDetails` and only calls `m.verifier(rc)` (the CA-pool signature/trust check) *after* the full details structure — including all these loops — has already been parsed and validated structurally: [4](#0-3) 

This means the loop cost is paid for any handshake attempt carrying a maximal, self-crafted certificate, regardless of whether the certificate is signed by a trusted CA — i.e., it is reachable by a remote peer with **no CA-signed certificate at all**, since the cost is incurred prior to `m.verifier` rejecting the cert.

### Impact Explanation
An attacker can send repeated handshake-initiation messages, each carrying a maximally-sized, densely-packed bogus certificate. Each such message forces the responder to execute tens of thousands of loop iterations of ASN.1 decoding and slice `append` calls before the certificate is ultimately rejected for failing CA verification. Repeated at volume, this is a remote CPU-exhaustion / amplification vector against nebula nodes processing handshakes, i.e., a remote resource-exhaustion (partial DoS) impact consistent with the "loops may consume too much resource" bug class, reachable without possessing a CA-signed certificate.

### Likelihood Explanation
Likelihood is moderate: the attack requires no prior trust relationship — only the ability to send a UDP handshake packet to a nebula listener — and the certificate content is entirely attacker-controlled up to `MaxCertificateSize`. The per-packet cost multiplier (thousands of loop iterations per handshake attempt) is bounded and not catastrophic on its own, but it is easily automated and amplifiable via many concurrent bogus handshakes from spoofed or unauthenticated sources, similar in spirit to the referenced report's concern about attacker-controlled loop bounds executing before critical gating logic.

### Recommendation
Impose explicit upper bounds on the *count* of networks, unsafe networks, and groups accepted during `unmarshalDetails` (in addition to the existing per-item and total-size limits), and reject/short-circuit parsing as soon as any such bound is exceeded — mirroring the "max number of assets" style fix referenced in the external report (nebula's analog of Notional's PR #56). Additionally, consider deferring or interleaving expensive structural parsing with cheaper pre-checks (e.g., an early bound on entry count derived from the outer ASN.1 length) so that malformed/oversized detail lists are rejected with minimal work performed before verification.

### Proof of Concept
Not independently executed against a running nebula instance; based on static analysis of `cert/cert_v2.go`'s `unmarshalDetails` loops and `handshake/machine.go`'s `validateCert` call order. A concrete PoC would construct a V2 certificate `details` ASN.1 block containing the maximum number of minimally-encoded `TagDetailsGroups` (or `TagDetailsNetworks`) entries fitting within `MaxCertificateSize` (65536 bytes), embed it in a handshake message, and send it repeatedly to a nebula listener while measuring CPU time spent in `unmarshalDetails` prior to certificate rejection.

func (m *Machine) validateCert(payload Payload) error {
	cred := m.getCred(m.myVersion)
	if cred == nil {
		m.failed = true
		return fmt.Errorf("%w: %v", ErrNoCredential, m.myVersion)
	}
	rc, err := cert.Recombine(
		cert.Version(payload.CertVersion),
		payload.Cert,
		m.hs.PeerStatic(),
		cred.Cert.Curve(),
	)
	if err != nil {
		m.failed = true
		return fmt.Errorf("recombine cert: %w", err)
	}

	if !bytes.Equal(rc.PublicKey(), m.hs.PeerStatic()) {
		m.failed = true
		return ErrPublicKeyMismatch
	}

	// Version negotiation, if the peer sent a different version and we have it, switch
	if rc.Version() != m.myVersion {
		if m.getCred(rc.Version()) != nil {
			m.myVersion = rc.Version()
		}
	}

	verified, err := m.verifier(rc)
	if err != nil {
		m.failed = true
		return fmt.Errorf("verify cert: %w", err)
	}

	m.result.RemoteCert = verified
	m.remoteCertSet = true
	return nil
