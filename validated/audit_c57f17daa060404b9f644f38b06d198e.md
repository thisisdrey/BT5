### Title
Unbounded array allocation from attacker-controlled length field in ABI-decoding helpers used by TVM precompiled contracts leads to OutOfMemoryError DoS - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The CVE describes CImg's `load_bmp` allocating memory based on an unvalidated, attacker-controlled size field parsed from a crafted file header, causing an allocation failure/DoS. The analogous pattern in java-tron is found in the ABI-array-decoding helpers `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` in `PrecompiledContracts.java`, which allocate Java arrays directly sized from a length word taken from caller-supplied calldata, without validating that the declared length is consistent with the actual size of the supplied data.

### Finding Description
`extractBytes32Array`, `extractBytesArray`, and `extractSigArray` each read a length value directly from the decoded `DataWord[] words` (attacker-controlled calldata passed to a precompiled contract) and immediately allocate a Java array of that size: [1](#0-0) [2](#0-1) [3](#0-2) 

In each case, `int len = words[offset].intValueSafe();` is used to size `new byte[len][]` (in `extractBytesArray`/`extractSigArray`) or `new byte[len][]` (in `extractBytes32Array`) before any bounds check against the actual size of `data`/`words`. Unlike `extractBytesArray`'s single guard `if (offset > words.length - 1)`, there is no check that `len` itself is sane relative to the remaining calldata size. A crafted `len` value (e.g., close to `Integer.MAX_VALUE`) causes the JVM to attempt allocating an oversized object-reference array, which can throw `OutOfMemoryError` or place enormous memory pressure on the executing node — directly analogous to CImg's `load_bmp` allocating memory from an unchecked crafted size field.

I was not able to fully trace, within the available search budget, the exact precompiled-contract callers (e.g., `BatchValidateSign`/`ValidateMultiSign`, both instantiated in this file) that invoke these three helper methods to confirm whether an outer bound check exists earlier in those `execute()` methods; this should be verified directly in the file before treating this as fully proven.

### Impact Explanation
If reachable without an adequate upstream bound check, any account can trigger a TVM `CALL` to the relevant precompiled contract address with crafted calldata, causing the executing full node (or SR) to throw `OutOfMemoryError` inside VM execution. Depending on how this propagates, this could crash the block-producing/validating thread or destabilize the node, which is a node-crash/halt class impact — in scope per the rules (TVM opcodes/precompiles and energy metering).

### Likelihood Explanation
Precompiled contracts are reachable by any unprivileged contract deployer or caller by issuing a `CALL`/`STATICCALL` to the corresponding precompile address with attacker-chosen calldata — no special privilege is required. The likelihood of exploitability hinges entirely on whether an upstream length/size validation exists in the precompile's `execute()` method before reaching these helpers, which I could not conclusively confirm in this pass.

### Recommendation
Add an explicit bound check comparing `len` against the actual remaining `words.length`/`data.length` (similar to the existing `if (offset > words.length - 1)` guard) before allocating any array in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray`, rejecting the precompile call (or throwing a controlled TVM exception) instead of allocating based on unchecked attacker-controlled length words.

### Proof of Concept
1. Deploy a contract that performs a raw `CALL`/`STATICCALL` to the precompiled contract address backed by `BatchValidateSign` or `ValidateMultiSign`.
2. Craft calldata whose ABI-array "length" word (consumed by `extractBytesArray`/`extractSigArray`) is set to a very large value (e.g., `0xFFFFFFFF`), while providing minimal actual payload bytes.
3. Trigger the contract call via a normal `TriggerSmartContract` transaction from any account.
4. Observe the executing node attempt `new byte[hugeLen][]`, potentially throwing `OutOfMemoryError` or causing severe memory pressure during VM execution — full confirmation requires validating the exact caller path from `BatchValidateSign`/`ValidateMultiSign.execute()` down to these helpers.
