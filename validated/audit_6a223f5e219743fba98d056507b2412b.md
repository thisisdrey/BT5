## Title
Replay window check-then-decrypt-then-update race allows duplicate/replayed packet processing - ([File: connection_state.go])

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` split the anti-replay window check into two separately-locked operations with the expensive decrypt/verify work happening *unlocked* in between. This mirrors the external report's bug class: a value is read from shared mutable state (`window.Check`), used as the basis for accepting the packet, but the state isn't atomically updated to reflect that decision before the "expensive work" runs; only afterward is the state updated (`window.Update`), by which point a concurrent call for the same counter value can have observed the same stale "not yet seen" state and also passed.

### Finding Description
`Decrypt` takes `decryptLock`, calls `cs.window.Check(l, messageCounter)`, then **releases the lock**, performs the AEAD decrypt (`cs.dKey.DecryptDanger`, unlocked), and only then re-acquires the lock to call `cs.window.Update(l, messageCounter)`: [1](#0-0) 

`VerifyRelay` has the identical shape for relay frames: `Check` under lock, unlock, verify/decrypt the AEAD tag unlocked, then re-lock and `Update`: [2](#0-1) 

The replay window itself (`Bits`) is a stateful bitmap that is only safe when `Check` immediately reflects any concurrently-completing `Update`: [3](#0-2) [4](#0-3) 

Because `Check` and `Update` for the *same* counter are not performed as a single atomic critical section, two goroutines racing to process what is effectively the same wire message (e.g. the same UDP datagram delivered twice at the OS/network layer, or a captured-and-replayed relay frame arriving concurrently with the original in a multi-routine (`routines > 1`) deployment) can both observe `Check() == true` for the same `messageCounter` before either has called `Update()`. Both then proceed to decrypt/verify and hand the payload up to the tun device (for `Decrypt`) or forward it through the relay (for `VerifyRelay`). This is conceptually the same defect class as the report: a decision is made from a snapshot of shared counter/window state, real work is performed, and the authoritative state update that should have gated that work is deferred until after the work is already done — so the update "arrives too late" to prevent the duplicate/replayed use.

The project's own CHANGELOG documents prior instances of exactly this fragility class on the same replay-window machinery ("Advance the replay window on relayed packets so a relay drops replayed frames instead of re-forwarding them" and "Lock replay window updates so concurrent readers can't corrupt it"), confirming this is a recognized, previously-patched-in-part risk area rather than a purely theoretical one: [5](#0-4) 

The relay path is the strongest-impact instance: nebula's own regression test explicitly states the pre-fix bug was that a relay authenticated a replayed frame but never advanced the window before re-forwarding, and asserts that replays must be dropped: [6](#0-5) 

### Impact Explanation
An attacker who can capture a single legitimate relay frame or induce duplicate delivery of a data-plane packet (e.g. via a slightly-delayed retransmission colliding with routine scheduling on a multi-routine node) can cause the same authenticated ciphertext to be accepted and processed twice: forwarded twice through a relay, or delivered twice to the local tun interface. This is a traffic-replay/duplication issue on the data plane. It requires no CA-signed certificate and does not require being a trusted peer — it only requires the ability to deliver a captured packet to a listening nebula node, which is exactly the "no CA-signed certificate" attacker model in scope. It does not achieve full decryption or authentication bypass of new traffic, but it does undermine the AEAD replay-protection guarantee that the anti-replay window is supposed to provide, and in the relay case, duplicated forwarding could be leveraged for traffic amplification/duplication against the relay target.

### Likelihood Explanation
The race window depends on precise timing — two goroutines must both call `Check` for the identical counter before either calls `Update`, which is more likely under `routines > 1` configurations (documented as an intentional multi-routine mode in `main.go`) where multiple reader goroutines can concurrently process inbound UDP datagrams that both correspond to the same message counter (e.g., OS-level duplicate delivery, or an attacker deliberately sending the exact same encrypted datagram twice in quick succession to race the two lock/unlock windows). Likelihood is Medium: the window is narrow but not negligible, especially on multi-core, multi-routine deployments processing bursty inbound traffic, and it is directly exploitable by an unauthenticated network attacker without needing valid credentials — they only need to duplicate an observed packet.

### Recommendation
Perform the replay-window check and the eventual mark-as-seen update as a single atomic operation with respect to a given `messageCounter`, e.g. reserve the slot (mark it provisionally consumed) inside the same locked critical section that performs `Check`, before releasing the lock to do the decrypt/verify work, and only roll back / never mark on decrypt failure. Alternatively, hold `decryptLock` for the full duration of `Check` → `Decrypt`/verify → `Update` for a given `ConnectionState`, or use a per-counter test-and-set primitive so a second caller with the same counter is rejected the moment it attempts to be checked while the first is still in flight.

### Proof of Concept
1. Configure a nebula node with `routines` > 1 so that multiple goroutines can independently call into the same `HostInfo.ConnectionState`.
2. Capture one legitimate encrypted data-plane (or relay) frame with message counter `N` destined for that node.
3. Simultaneously inject two copies of the exact same frame at the transport layer (e.g., two near-simultaneous UDP sends of the identical bytes) so that they land on two different reader routines.
4. Both routines call `cs.window.Check(l, N)` before either calls `cs.window.Update(l, N)` (this is the race window opened by the unlock between `Check` and `Update` in `Decrypt`/`VerifyRelay`).
5. Both routines proceed to `DecryptDanger`/verify successfully (same valid ciphertext/tag) and both deliver/forward the payload — observable as duplicate delivery to the tun device, or (for `VerifyRelay`) duplicate forwarding through the relay to the target, contrary to the intended replay-window guarantee demonstrated by `TestRelayReplayProtection`. func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}

// VerifyRelay verifies AEAD protected (but not encrypted) relay frames. packet must be length-checked by the caller.
func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}

func (b *Bits) Update(l *slog.Logger, i uint64) bool {
	// Fast path: i is the next expected counter. Split out so the function
	// stays small and avoids paying for the slow paths' slog argument-build
	// stack frame on every call. The bit read/test/write is inlined to
	// touch the backing word once.
	if i == b.current+1 {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if i > b.length && w&mask == 0 {
			b.lostCounter.Inc(1)
		}
		b.bits[word] = w | mask
		b.current = i
		return true
	}
	return b.updateSlow(l, i)
}
