### Title
wNEAR permanently lost when `near_withdraw` unwrap succeeds but the final NEAR transfer to a non-existent receiver fails, with no resolver credit-back - (File: `contracts/defuse/src/contract/intents/state.rs`)

### Summary
`native_withdraw` (and similarly `storage_deposit`/`auth_call` deposit paths) debit the signer's internal wNEAR balance synchronously via `self.withdraw(...)`, then asynchronously call `ext_wnear::near_withdraw` followed by `do_native_withdraw`, which does `Promise::new(withdraw.receiver_id).transfer(withdraw.amount)`. Unlike the NEP-141 path (`ft_withdraw` → `ft_resolve_withdraw`), there is no resolver callback that re-credits the signer if the final transfer fails, so if `receiver_id` does not exist, the unwrapped NEAR is refunded by the protocol to the contract account itself while the user's internal wNEAR balance remains permanently debited.

### Finding Description
The invariant that must hold is: `wNEAR debited from owner_id == NEAR delivered to withdraw.receiver_id, or wNEAR is returned to owner_id`.

In `native_withdraw` ( [1](#0-0) ), the sequence is:
1. `self.withdraw(owner_id, [wnear amount], ...)` synchronously calls `internal_sub_balance`, permanently decrementing the user's internal wNEAR ledger entry ( [2](#0-1) ) — this state change is committed regardless of what happens in the subsequent cross-contract promises, since NEAR promises are not atomic with the calling receipt.
2. `ext_wnear::near_withdraw` is scheduled with `NEAR_WITHDRAW_GAS` ( [3](#0-2) ), followed by `.then(do_native_withdraw)`.
3. `do_native_withdraw` requires the `near_withdraw` promise succeeded, then does `Promise::new(withdraw.receiver_id).transfer(withdraw.amount)` ( [4](#0-3) ) with **no further `.then()` callback** to detect success/failure and re-credit the user.

If `withdraw.receiver_id` is a syntactically valid but non-existent NEAR account, the `Transfer` action fails at the protocol level and the deposited NEAR is refunded to the predecessor of that action — which is the Defuse contract itself, not the original owner's internal balance. Because there is no resolver analogous to `ft_resolve_withdraw` ( [5](#0-4) ) attached after this final transfer, the NEAR that returns to the contract account is never mapped back to any user's ledger entry, and the already-debited wNEAR is unrecoverable by the user without a privileged (DAO/role) sweep.

The same missing-refund pattern exists for `storage_deposit` (`do_storage_deposit`, called from [6](#0-5) ) and the deposit-bearing branch of `auth_call` ( [7](#0-6) ), both of which debit wNEAR up front via `self.withdraw(...)` and then chain a `do_*` callback whose only failure handling is a `require!` panic on the `near_withdraw` promise result, not a re-credit resolver for the outer action's ultimate success/failure.

An attacker reaches this via `execute_intents`/`simulate_intents` with a `NativeWithdraw` intent (or `StorageDeposit`/`AuthCall` with deposit) naming `receiver_id` (or `withdraw.receiver_id`/deposit target) as an account that does not exist on-chain. No token contract callback (`ft_on_transfer`/`nft_on_transfer`/`mt_on_transfer`) is even required for this specific path — the intent is signed and submitted directly by the attacker (or by anyone) against their own wNEAR balance, though this also composes with token-transfer-triggered intents since `execute_intents` batches are the general entrypoint.

### Impact Explanation
The signer's wNEAR balance is permanently debited from the Verifier's internal ledger while the underlying NEAR silently returns to the contract's own account, unreachable by the affected user without a DAO/`UnrestrictedWithdrawer`-type privileged sweep and manual reimbursement. This is a genuine, repeatable loss of user funds: any user can trigger it against their own balance by naming a non-existent `receiver_id`, and it applies per-withdrawal, so it can be repeated across accounts and amounts. This matches the "Critical — user funds permanently frozen (unrecoverable without a privileged action)" category.

### Likelihood Explanation
This requires no special privilege — any account holding wNEAR balance in the Verifier can submit a `NativeWithdraw` (or `StorageDeposit`/deposit-bearing `AuthCall`) intent naming a non-existent `receiver_id`/target account. This is trivial and free to trigger (attacker can even target their own funds to demonstrate/PoC, or trick a relayer/other into submitting on their behalf if a victim naively supplies a mistyped/non-existent receiver). No adversarial contract deployment or gas griefing is needed — a plain nonexistent `AccountId` string suffices.

### Recommendation
Add a resolver callback after the final `Promise::new(receiver_id).transfer(amount)` in `do_native_withdraw` (and equivalent points in `do_storage_deposit` / `do_auth_call`) that checks the transfer's promise result and re-credits `owner_id`'s wNEAR balance via `self.deposit(...)` when the transfer fails, mirroring the `ft_resolve_withdraw` pattern already used for NEP-141 withdrawals.

### Proof of Concept
Cargo test plan (near-workspaces sandbox, no mainnet):
1. Deploy Defuse contract and a wNEAR contract; fund a test signer account with wNEAR balance inside the Verifier (`internal_add_balance`/deposit flow).
2. Record `balance_before = state.balance_of(signer, wnear_token_id)`.
3. Submit a signed `MultiPayload` with a `NativeWithdraw` intent where `receiver_id` is set to a syntactically valid but non-existent account (e.g. `"nonexistent-account.near"` or an unregistered sub-account never created in the sandbox).
4. Execute via `execute_intents`; await all promise resolution in the sandbox.
5. Assert: (a) `state.balance_of(signer, wnear_token_id) == balance_before - amount` (wNEAR stays debited), and (b) the NEAR native balance of `receiver_id` was never credited (account still doesn't exist / has zero balance), and (c) no `deposit`/refund event was emitted crediting the signer back. This demonstrates `wNEAR debited ≠ NEAR delivered to receiver ∪ returned to owner`, confirming the frozen-funds condition.

    fn internal_sub_balance(
        &mut self,
        owner_id: &AccountIdRef,
        tokens: impl IntoIterator<Item = (TokenId, u128)>,
    ) -> Result<()> {
        let owner = self
            .accounts
            .get_mut(owner_id)
            .ok_or_else(|| DefuseError::AccountNotFound(owner_id.to_owned()))?
            .get_mut()
            .ok_or_else(|| DefuseError::AccountLocked(owner_id.to_owned()))?;

        for (token_id, amount) in tokens {
            if amount == 0 {
                return Err(DefuseError::InvalidIntent);
            }

            owner
                .token_balances
                .sub(token_id.clone(), amount)
                .ok_or(DefuseError::BalanceOverflow)?;
        }

        Ok(())
    }

impl FungibleTokenWithdrawResolver for Contract {
    #[private]
    fn ft_resolve_withdraw(
        &mut self,
        token: AccountId,
        sender_id: AccountId,
        amount: U128,
        is_call: bool,
    ) -> U128 {
        let used = if is_call {
            // `ft_transfer_call` returns successfully transferred amount
            match promise_result_checked_json::<U128>(0) {
                Ok(Ok(used)) => used.0.min(amount.0),
                Ok(Err(_deserialize_err)) => 0,
                // do not refund on failed `ft_transfer_call` due to
                // NEP-141 vulnerability: `ft_resolve_transfer` fails to
                // read result of `ft_on_transfer` due to insufficient gas
                Err(_) => amount.0,
            }
        } else {
            // `ft_transfer` returns empty result on success
            if promise_result_checked_void(0).is_ok() {
                amount.0
            } else {
                0
            }
        };

        let refund = amount.0.saturating_sub(used);
        if refund > 0 {
            self.deposit(
                sender_id,
                [(Nep141TokenId::new(token).into(), refund)],
                Some(REFUND_MEMO),
            )
            .unwrap_or_else(|err| err.panic());
        }

        U128(used)
    }
}
