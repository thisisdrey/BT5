Audit Report

## Title
Relayer reward claim is irreversibly consumed on XCM dispatch success, not on actual settlement, causing permanent loss of reward funds - ([File: bridges/modules/relayers/src/lib.rs])

## Summary
`Pallet::do_claim_rewards` deletes the relayer's pending reward from `RelayerRewards` and emits `RewardPaid` as soon as `T::PaymentProcedure::pay_reward` returns `Ok(())`. For `BridgeReward::Snowbridge`, `PayAccountOnLocation::pay_reward` returns `Ok(())` once the outbound XCM has merely been validated and handed to `XcmSender::deliver`, without any confirmation that `ReserveAssetDeposited`/`DepositAsset` actually executed and credited the beneficiary on AssetHub. Consequently, any downstream execution failure on AssetHub permanently destroys the claim with no retry path, since the BridgeHub-side storage entry is already gone.

## Finding Description
`do_claim_rewards` takes the reward out of storage via `maybe_reward.take()` before calling the payment procedure, and only reverts that `take()` if `pay_reward` returns `Err`: [1](#0-0) 

For the Snowbridge reward kind, `PayAccountOnLocation::pay_reward` builds an unpaid, best-effort XCM program (`UnpaidExecution`, `DescendOrigin`, `UniversalOrigin`, `ReserveAssetDeposited`, `DepositAsset`) with no error handler, and returns `Ok(())` as soon as `validate_send` succeeds, fees are charged, and `XcmSender::deliver(ticket)` succeeds — none of which observe whether AssetHub actually executed `DepositAsset`: [2](#0-1) 

The runtime wiring confirms the beneficiary `Location` is caller-supplied and only version-decoded, not semantically validated, before being passed straight into `pay_reward`: [3](#0-2) 

If AssetHub's execution of `DepositAsset` fails for any reason (unresolvable beneficiary junctions, amount below existential deposit for the ETH-derived asset, transient message-queue failure), the `ReserveAssetDeposited` assets are trapped in AssetHub's holding register instead of being credited, while BridgeHub has already deleted the `RelayerRewards` entry and emitted `RewardPaid`. The only currently-tested failure paths (`LocalAccount` beneficiary rejected for Snowbridge rewards, and XCM `validate`/`deliver` failures) revert correctly via `try_mutate_exists`, but there is no code path that reverts based on *remote execution* outcome — the pallet has no receipt/callback mechanism from AssetHub back to BridgeHub, unlike patterns such as `pallet-treasury`'s `PaymentState::Attempted`/`check_status`.

## Impact Explanation
This violates the required invariant that "payout state must only advance after decode, dispatch, execution, and settlement succeed atomically." The relayer's reward — previously accrued on-chain via `register_reward` — can be permanently and irrecoverably destroyed by a single `claim_rewards_to` call whose remote leg fails, since the storage entry backing the claim is already removed and `RewardPaid` already emitted before settlement is confirmed. This matches the "permanent user-fund or bridge-state lock" impact category.

## Likelihood Explanation
Triggering this requires only the relayer's own signed call to the public, unprivileged `claim_rewards_to` extrinsic with a `BridgeRewardBeneficiaries::AssetHubLocation` value that is well-formed enough to pass `Location::try_from` and XCM send validation, but fails during `DepositAsset` execution on AssetHub (e.g., unresolvable junction combination, or reward amount below AssetHub's existential deposit for the asset). No privileged actor or relayer collusion is needed.

## Recommendation
Do not remove the reward entry from `RelayerRewards` (nor emit `RewardPaid`) until settlement is confirmed. Options: (1) hold the claim in a pending/attempted state until a delivery/execution receipt confirms success, restoring claimability on confirmed failure; or (2) make `pay_reward` for the Snowbridge path only return `Ok` after confirmed deposit execution (e.g., via a paid, error-handled XCM program with explicit success acknowledgment), rather than treating router hand-off as final settlement.

## Proof of Concept
1. Relayer accrues a `BridgeReward::Snowbridge` reward via `register_reward`.
2. Relayer calls `claim_rewards_to(BridgeReward::Snowbridge, BridgeRewardBeneficiaries::AssetHubLocation(loc))` with a `loc` that converts fine via `Location::try_from` but cannot be resolved into a valid deposit target on AssetHub, or where the reward amount is below AssetHub's existential deposit for the asset.
3. On BridgeHub, `PayAccountOnLocation::pay_reward` validates and delivers the XCM successfully, so `do_claim_rewards` commits the `take()` on `RelayerRewards` and emits `RewardPaid`, as shown in the passing test: [4](#0-3) 
4. On AssetHub, `DepositAsset` fails/traps instead of emitting `pallet_assets::Event::Deposited`.
5. The relayer's reward is now permanently gone from `RelayerRewards` with no corresponding value delivered to any beneficiary account, and no code path to reclaim or retry the payout.

		fn do_claim_rewards(
			relayer: T::AccountId,
			reward_kind: T::Reward,
			beneficiary: BeneficiaryOf<T, I>,
		) -> DispatchResult {
			RelayerRewards::<T, I>::try_mutate_exists(
				&relayer,
				reward_kind,
				|maybe_reward| -> DispatchResult {
					let reward_balance =
						maybe_reward.take().ok_or(Error::<T, I>::NoRewardForRelayer)?;
					T::PaymentProcedure::pay_reward(
						&relayer,
						reward_kind,
						reward_balance,
						beneficiary.clone(),
					)
					.map_err(|e| {
						tracing::error!(
							target: LOG_TARGET,
							error=?e,
							?relayer,
							?reward_kind,
							?reward_balance,
							?beneficiary,
							"Failed to pay rewards"
						);
						Error::<T, I>::FailedToPayReward
					})?;

					Self::deposit_event(Event::<T, I>::RewardPaid {
						relayer: relayer.clone(),
						reward_kind,
						reward_balance,
						beneficiary,
					});
					Ok(())
				},
			)

	fn pay_reward(
		relayer: &Relayer,
		_: (),
		reward: RewardBalance,
		beneficiary: Self::Beneficiary,
	) -> Result<(), Self::Error> {
		let ethereum_location = Location::new(2, [GlobalConsensus(EthereumNetwork::get())]);
		let assets: Asset = (ethereum_location.clone(), reward.into()).into();

		let xcm: Xcm<()> = alloc::vec![
			UnpaidExecution { weight_limit: Unlimited, check_origin: None },
			DescendOrigin(InboundQueueLocation::get().into()),
			UniversalOrigin(GlobalConsensus(EthereumNetwork::get())),
			ReserveAssetDeposited(assets.into()),
			DepositAsset { assets: AllCounted(1).into(), beneficiary },
		]
		.into();

		let (ticket, fee) =
			validate_send::<XcmSender>(AssetHubLocation::get(), xcm).map_err(|_| XcmSendFailure)?;
		XcmExecutor::charge_fees(relayer.clone(), fee).map_err(|_| ChargeFeesFailure)?;
		XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;

		Ok(())
	}
