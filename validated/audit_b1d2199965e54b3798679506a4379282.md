Audit Report

## Title
Outbound bridge delivery receipts finalize relayer reward and close pending orders without checking dispatch `success`, permanently losing funds on failed Ethereum-side execution - (File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs)

## Summary
`Pallet::process_delivery_receipt` decodes a `DeliveryReceipt` that carries a `success` flag reflecting whether the Ethereum Gateway actually executed the bridged command, but the function never inspects `receipt.success` before crediting the relayer's reward and permanently deleting the `PendingOrder` for that nonce. [1](#0-0)  This causes a legitimately-relayed but Ethereum-side-reverted message to be treated as fully settled, permanently stranding the corresponding assets already withdrawn on the Polkadot side.

## Finding Description
`do_process_message` computes a static, worst-case `gas` per command via `T::GasMeter::maximum_dispatch_gas_used_at_most(&command)` and inserts a `PendingOrder{ nonce, fee, block_number }` into `PendingOrders` keyed by nonce. [2](#0-1)  The `DeliveryReceipt` type decoded from the Ethereum `InboundMessageDispatched` event explicitly carries a `success: bool` field describing whether the Gateway's dispatch of the command succeeded on Ethereum. [3](#0-2) 

`submit_delivery_receipt` verifies the proof, decodes the `DeliveryReceipt`, and forwards it unmodified to `process_delivery_receipt`. [4](#0-3)  `process_delivery_receipt` only validates the gateway address and looks up the `PendingOrder` by nonce; it pays out `order.fee` to the relayer and unconditionally calls `<PendingOrders<T>>::remove(nonce)`, with no branch on `receipt.success` anywhere in the function body. [5](#0-4)  Once `PendingOrders::remove(nonce)` executes, there is no other storage item tracking the message's Ethereum-side outcome, so a failed dispatch is indistinguishable from a successful one from the pallet's perspective.

## Impact Explanation
Assets destined for the Ethereum side are withdrawn/reserved on the Polkadot side at the time the message is enqueued (`do_process_message`), before any Ethereum-side confirmation exists. If the Gateway's dispatch of the corresponding command fails on Ethereum — including due to the static `maximum_dispatch_gas_used_at_most` gas estimate under-shooting real execution cost, a state-dependent cost change, or a deliberately crafted command that reverts — the pallet still pays the relayer and deletes the `PendingOrder`, permanently foreclosing any retry, replay, or refund path for the corresponding locked/withdrawn funds. This matches the "permanent user-fund or bridge-state lock" impact category, since the settlement state (`PendingOrders` removal) advances to a final, unrecoverable state without confirming successful execution of the underlying transfer.

## Likelihood Explanation
No malicious relayer, admin, or governance action is required. The relayer submits a truthful, cryptographically verified event log (`InboundMessageDispatched` with `success=false`) reflecting real Ethereum state, and `submit_delivery_receipt`/`process_delivery_receipt` will process it deterministically regardless of the `success` value. Any real-world scenario where actual Ethereum execution cost exceeds the pallet's static worst-case gas estimate, or any command constructed to revert on the Ethereum side, triggers this path.

## Recommendation
Branch on `receipt.success` in `process_delivery_receipt`. On `success = false`, do not remove `PendingOrders[nonce]` as fully resolved; instead transition it to a distinct failed/replayable state, or trigger a refund path crediting the original sender, so that funds already withdrawn on the Polkadot side are not permanently stranded when the corresponding Ethereum-side dispatch failed.

## Proof of Concept
1. Send an outbound message (e.g. an asset transfer) from AssetHub to Ethereum, causing `do_process_message` to insert `PendingOrders[nonce]` with `gas` computed via `T::GasMeter::maximum_dispatch_gas_used_at_most`.
2. On the Ethereum Gateway, the actual gas required to execute the dispatched command exceeds the pre-computed estimate (or the command is crafted to revert), causing the Gateway to revert the inner dispatch while still emitting `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer calls `submit_delivery_receipt` with a valid Merkle/verifier proof of this event; `T::Verifier::verify` succeeds and `DeliveryReceipt::try_from` decodes `success=false`.
4. `process_delivery_receipt` pays the relayer's reward and calls `<PendingOrders<T>>::remove(nonce)` regardless of `success`, as shown at `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs` lines 466-475 — no branch exists for `receipt.success == false`.
5. The asset withdrawn on the Polkadot side remains unrecoverable; no on-chain state remains that would allow reissuing or refunding the failed transfer.

```rust
		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
```
