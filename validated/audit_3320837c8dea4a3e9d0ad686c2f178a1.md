### Title
Stale postponed `Action::Stake` receipt can lock a recreated account's balance to an attacker-chosen validator key - ([File: runtime/runtime/src/actions.rs])

### Finding Description
`check_actor_permissions` in `runtime/runtime/src/actions.rs` gates `Action::Stake` (and `DeployContract`/`AddKey`/`DeleteKey`) purely by comparing `actor_id != account_id` as `AccountId` strings [1](#0-0) , with no notion of "account incarnation" — i.e. no check that the account instance targeted by the receipt is the same logical account that originally scheduled it. Likewise, `Action::DeleteAccount` is only blocked when `account.locked()` is non-zero at deletion time [2](#0-1) .

Exploit flow:
1. Attacker's contract at `child.attacker.near` creates a self-targeted (`predecessor_id == receiver_id == "child.attacker.near"`) action receipt bundling `Action::Stake(attacker_controlled_pubkey, stake_amount)` together with an input dependency on a promise that will not resolve immediately (e.g. a cross-contract/cross-shard callback). Because not all input data is ready, this action receipt is postponed (stored as `PostponedReceipt`/`PendingDataCount` records under the account's trie key namespace).
2. While the Stake action is still pending (never executed), `account.locked()` for `child.attacker.near` remains zero, so a subsequent `DeleteAccount` transaction from the same account passes the `DeleteAccountStaking` check at `runtime/runtime/src/actions.rs:770-775` and the account is deleted.
3. Attacker (or anyone) recreates `child.attacker.near` via `CreateAccount`, deposits fresh funds, unrelated to the original stake intent.
4. Attacker completes the outstanding input data dependency, releasing the stale postponed receipt. When it finally executes, `check_account_existence` sees `account.is_some()` (the new account exists) and `check_actor_permissions` sees `actor_id == account_id` (same string), so both checks pass, and the stale `Action::Stake` is applied against the new account's balance — locking funds the new owner never authorized toward a validator key the attacker controls.

The root cause is that postponed-receipt state and the actor/account permission checks are keyed solely by `AccountId` string identity with no generation/incarnation counter tying a postponed receipt to the specific account instance that created it, so deleting and recreating an account under the same name does not invalidate receipts scheduled against the old instance.

### Impact Explanation
This allows unauthorized locking (freezing) of a recreated account's funds via a validator stake the new/current owner never submitted, since unstaking requires discovering the stale stake and waiting out the unbonding period. This maps to a funds-freezing bounty category rather than direct theft, since the staked funds are eventually recoverable by the account owner after unbonding, but are involuntarily locked in the interim.

### Likelihood Explanation
The attacker needs only ordinary account permissions: deploy a contract, submit a self-targeted cross-contract call with a pending promise dependency, submit `DeleteAccount`, then re-create the account and resolve the pending promise — all achievable by an unprivileged client with no validator/node access. The trickiest part is timing the promise resolution to occur after account recreation, which is fully attacker-controlled since the attacker triggers the resolving call.

### Recommendation
Bind postponed receipts (and any deferred/pending action state) to a per-account generation counter incremented on `CreateAccount`/`DeleteAccount`, and validate that a postponed receipt's recorded generation matches the current account's generation before applying actions such as `Stake`, `DeployContract`, `AddKey`, `DeleteKey`. Alternatively, purge all `PostponedReceipt`/`PendingDataCount` entries scoped to an account as part of `DeleteAccount` processing, or reject `DeleteAccount` while there exist outstanding postponed receipts targeting that account.

### Proof of Concept
Runtime/test-loop integration test:
1. Deploy a contract at `child.attacker.near` that, in one action receipt, batches `Action::Stake(attacker_pubkey, N)` and depends on an unresolved promise (postponing the receipt).
2. Assert the receipt is postponed (`PostponedReceipt`/`PendingDataCount` trie entries exist) and `account.locked() == 0`.
3. Submit `DeleteAccount` from `child.attacker.near`; assert it succeeds (locked balance is zero).
4. Submit `CreateAccount` recreating `child.attacker.near` with a fresh deposit and new keys.
5. Resolve the pending promise dependency, allowing the postponed receipt to execute.
6. Assert `account.locked()` on the recreated `child.attacker.near` is non-zero and staked toward `attacker_pubkey`, despite the new owner never submitting a `Stake` action — demonstrating unauthorized fund locking.
