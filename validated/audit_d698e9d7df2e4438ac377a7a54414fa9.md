## Analog Found

### Title
Unbounded, permissionless growth of an account's `assetV2` map via `TransferAssetContract` - (File: `actuator/src/main/java/org/tron/core/actuator/TransferAssetActuator.java`)

### Summary
The external report describes an unauthenticated `onERC721Received()` callback that lets any caller append entries to a persistent `nfts` array belonging to another party, at negligible cost to the attacker but high remediation cost to the victim. The closest reachable analog in java-tron is `TransferAssetActuator`, which lets *any* signed transaction sender push a new entry into an arbitrary recipient's `assetV2` map without any consent, cap, or fee paid by the recipient.

### Finding Description
`TransferAssetActuator.execute()` unconditionally calls `toAccountCapsule.addAssetAmountV2(...)` on the recipient account for whatever `assetName`/token is specified by the caller, with no participation or authorization required from the recipient: [1](#0-0) 

`AccountCapsule.addAssetAmountV2` simply inserts a new key into the protobuf `assetV2` map if the token id is not already present, with no limit on the number of distinct token ids an account can accumulate: [2](#0-1) 

Once inserted, an entry is never removed by `reduceAssetAmountV2`, even when its balance reaches zero — the key simply remains in the map with value `0`: [3](#0-2) 

Because TRC10 asset issuance (`AssetIssueContract`) has existed since genesis, thousands of distinct token ids already exist on-chain, each already paid for by its original issuer. An attacker holding even a tiny balance of many pre-existing tokens can, in a loop, send 1 unit of each different token id to an arbitrary victim address via `TransferAssetContract`. Each transfer costs only ordinary bandwidth/energy (no `AssetIssueFee`, since the attacker is not creating new assets, only moving pre-existing ones), while the victim's `assetV2` map grows by one permanent entry per transfer — with no cap, no opt-in, and no way for the victim to selectively purge a single unwanted entry (only a full `clearAsset()` exists, and it is not exposed as a self-service user operation).

This mirrors the report's bug class exactly: an unauthorized/unprivileged party can append to a data structure (`nfts` array/`assetV2` map) that conceptually "belongs" to another account, at a cost far lower than the burden imposed on the victim, and the victim has no cheap way to reverse it entry-by-entry.

### Impact Explanation
Every account load/serialization in the node (used by `GetAccount`, transfers, freezing, delegation, TVM account access via `RepositoryImpl`, block processing, etc.) must materialize the full `assetV2` protobuf map for the account. Bloating a victim's map with thousands of low-value/no-value token entries increases:
- Storage footprint per account (permanently, since entries aren't pruned).
- CPU/serialization cost of every future read/write touching that account.
- API response size/latency for `GetAccount`/`getaccountnet`-style calls, since the entire map is returned to any HTTP/gRPC caller.

This is a griefing/state-bloat vector against a specific victim account (or, if automated against many/all active accounts, a chain-wide state-growth DoS amplifier), reachable purely by any address holding tiny balances of already-issued TRC10 tokens sending ordinary signed `TransferAssetContract` transactions.

### Likelihood Explanation
Likelihood is high: `TransferAssetContract` is a standard, unprivileged, broadcastable transaction type; no special permission, large capital, or contract deployment is required. The attacker only needs to acquire (even via near-zero-value/dust purchases or airdrops) minimal balances of many different pre-existing TRC10 tokens — of which thousands already exist on mainnet — and repeatedly transfer 1 unit of each to the target address.

### Recommendation
- Enforce a maximum number of distinct entries (`assetV2Map`/`AssetV2` prefix keys in `AccountAssetStore`) per account, similar to the existing `Commons.ASSET_ISSUE_COUNT_LIMIT_MAX` guard used elsewhere in the codebase and the order-count cap seen in `MarketSellAssetActuator` (`exceedMakerBuyOrderNumLimit`), and reject `TransferAssetContract`/`addAssetAmountV2` calls that would introduce a new token id beyond that cap for the recipient.
- Alternatively/additionally, prune zero-balance entries from `assetV2` (and the corresponding `AccountAssetStore` optimized keys) instead of retaining them indefinitely.

### Proof of Concept
1. Attacker acquires a small amount (e.g., 1 unit) of N distinct, already-issued TRC10 tokens (no new `AssetIssueContract` calls needed since these already exist on-chain).
2. For each token, attacker broadcasts a `TransferAssetContract` sending 1 unit to victim address `V`.
3. Each call reaches `TransferAssetActuator.execute()` → `toAccountCapsule.addAssetAmountV2(...)` (`actuator/src/main/java/org/tron/core/actuator/TransferAssetActuator.java:82-84`), inserting a new key into `V`'s `assetV2` map with no cap check.
4. After N transfers, `V`'s account protobuf contains N permanent asset entries that `V` never requested and cannot cheaply remove individually, increasing serialization/storage cost for every future operation touching `V`'s account.

  public boolean addAssetAmountV2(byte[] key, long amount,
      DynamicPropertiesStore dynamicPropertiesStore, AssetIssueStore assetIssueStore) {
    importAsset(key);
    boolean disableJavaLangMath = dynamicPropertiesStore.disableJavaLangMath();
    //key is token name
    if (dynamicPropertiesStore.getAllowSameTokenName() == 0) {
      Map<String, Long> assetMap = this.account.getAssetMap();
      AssetIssueCapsule assetIssueCapsule = assetIssueStore.get(key);
      String tokenID = assetIssueCapsule.getId();
      String nameKey = ByteArray.toStr(key);
      Long currentAmount = assetMap.get(nameKey);
      if (currentAmount == null) {
        currentAmount = 0L;
      }
      this.account = this.account.toBuilder()
          .putAsset(nameKey, addExact(currentAmount, amount, disableJavaLangMath))
          .putAssetV2(tokenID, addExact(currentAmount, amount, disableJavaLangMath))
          .build();
    }
    //key is token id
    if (dynamicPropertiesStore.getAllowSameTokenName() == 1) {
      String tokenIDStr = ByteArray.toStr(key);
      Map<String, Long> assetMapV2 = this.account.getAssetV2Map();
      Long currentAmount = assetMapV2.get(tokenIDStr);
      if (currentAmount == null) {
        currentAmount = 0L;
      }
      this.account = this.account.toBuilder()
          .putAssetV2(tokenIDStr, addExact(currentAmount, amount, disableJavaLangMath))
          .build();
    }
    return true;
  }

  public boolean reduceAssetAmountV2(byte[] key, long amount,
                                     DynamicPropertiesStore dynamicPropertiesStore, AssetIssueStore assetIssueStore) {
    importAsset(key);
    //key is token name
    boolean disableJavaLangMath = dynamicPropertiesStore.disableJavaLangMath();
    if (dynamicPropertiesStore.getAllowSameTokenName() == 0) {
      Map<String, Long> assetMap = this.account.getAssetMap();
      AssetIssueCapsule assetIssueCapsule = assetIssueStore.get(key);
      String tokenID = assetIssueCapsule.getId();
      String nameKey = ByteArray.toStr(key);
      Long currentAmount = assetMap.get(nameKey);
      if (amount > 0 && null != currentAmount && amount <= currentAmount) {
        this.account = this.account.toBuilder()
                .putAsset(nameKey, subtractExact(currentAmount, amount, disableJavaLangMath))
                .putAssetV2(tokenID, subtractExact(currentAmount, amount, disableJavaLangMath))
                .build();
        return true;
      }
    }
    //key is token id
    if (dynamicPropertiesStore.getAllowSameTokenName() == 1) {
      String tokenID = ByteArray.toStr(key);
      Map<String, Long> assetMapV2 = this.account.getAssetV2Map();
      Long currentAmount = assetMapV2.get(tokenID);
      if (amount > 0 && null != currentAmount && amount <= currentAmount) {
        this.account = this.account.toBuilder()
                .putAssetV2(tokenID, subtractExact(currentAmount, amount, disableJavaLangMath))
                .build();
        return true;
      }
    }

    return false;
  }
