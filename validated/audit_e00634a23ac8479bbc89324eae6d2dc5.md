## Title
Missing bounds validation on `ENERGY_FEE` chain parameter enables committee-driven fund theft via fee overflow - (File: `actuator/src/main/java/org/tron/core/utils/ProposalUtil.java`)

### Summary
`ProposalUtil.validator()` enforces strict `[0, LONG_VALUE]` bounds on sibling fee-like chain parameters (`ACCOUNT_UPGRADE_COST`, `CREATE_ACCOUNT_FEE`, `TRANSACTION_FEE`, `ASSET_ISSUE_FEE`, `WITNESS_PAY_PER_BLOCK`, `WITNESS_STANDBY_ALLOWANCE`, `CREATE_NEW_ACCOUNT_FEE_IN_SYSTEM_CONTRACT`, `CREATE_NEW_ACCOUNT_BANDWIDTH_RATE`), but `ENERGY_FEE` and `EXCHANGE_CREATE_FEE` are explicitly whitelisted to skip all validation: [1](#0-0) 

This is the same asymmetry described in the original report: one class of fee parameter is capped (deposit fee ≤ 250), while an analogous fee parameter used against the same asset pool (withdrawal fee) is unbounded, letting the governing party set an unreasonable value.

### Finding Description
Any account can create a chain-parameter proposal via `ProposalCreateActuator`, which delegates value checking to `ProposalUtil.validator()`: [2](#0-1) 

For `ENERGY_FEE`, the switch statement performs `break;` with **no range check at all**, so a value of `Long.MAX_VALUE` (or any arbitrarily large value) passes validation and, once approved by the required witness quorum, is written to the `DynamicPropertiesStore` during `ProposalService.process()`: [3](#0-2) 

This value is later consumed in `ReceiptCapsule.payEnergyBill()` to compute the fee charged to a caller's account when their energy allowance is insufficient. Critically, the multiplication is **not** overflow-checked (unlike other math in the same codebase that explicitly uses `multiplyExact`/`addExact` with `disableJavaLangMath` guards): [4](#0-3) 

Because `sunPerEnergy` (derived from `ENERGY_FEE`) is unbounded, `(usage - accountEnergyLeft) * sunPerEnergy` can silently overflow a signed 64-bit `long`, producing an attacker/committee-controlled wraparound value for `energyFee`. Since the check `balance < energyFee` is performed against this wrapped value rather than the true intended cost, an account's balance can be debited by an amount that has no relationship to the actual resource consumption or to the transaction's own `feeLimit` safeguard, and the drained TRX is sent to the black hole / burned (`Commons.adjustBalance` to blackhole, or `dynamicPropertiesStore.burnTrx`): [5](#0-4) 

This mirrors the reported pattern precisely: an unbounded fee-setting parameter, reachable only by the governing multisig-like body (the witness/committee proposal-approval quorum in java-tron, analogous to the admin/treasury multisig in the Y2K report), can be weaponized to siphon user funds through a fee mechanism that lacks the same bound applied to its sibling parameters.

### Impact Explanation
If `ENERGY_FEE` is pushed to an overflow-triggering value by a colluding witness quorum, ordinary users calling smart contracts can have their account balance debited by amounts disconnected from actual resource usage and from the `feeLimit` they explicitly authorized, with the difference burned/sent to the black hole — a direct, irreversible loss of user funds. This satisfies the "concrete unauthorized... theft... of funds" bar.

### Likelihood Explanation
Requires the same threat model as the original report: a colluding governing quorum (witnesses/SRs approving a proposal), not a single malicious actor — this is exactly the caveat noted in the source report ("Since this is likely a multisig he would need to collude with other signers, but a theft would still be possible"). The root cause (missing bound + non-`multiplyExact` arithmetic) is present in code regardless of how the parameter is set, so likelihood is tied to governance approval, matching the analog's medium severity.

### Recommendation
- Add an explicit upper bound to `ENERGY_FEE` (and `EXCHANGE_CREATE_FEE`) validation in `ProposalUtil.validator()`, consistent with the `[0, LONG_VALUE]` bound already applied to sibling fee parameters.
- Use overflow-safe arithmetic (`multiplyExact`/`StrictMathWrapper`) for the `energyFee` computation in `ReceiptCapsule.payEnergyBill()` so that even a legitimately large `ENERGY_FEE` cannot cause a silent wraparound.

### Proof of Concept
1. A proposal is created with `code = ENERGY_FEE` (11) and `value = Long.MAX_VALUE` (or a value engineered to overflow when multiplied by a plausible `usage - accountEnergyLeft`); `ProposalUtil.validator()` allows it through the empty `case ENERGY_FEE: break;` branch (`actuator/src/main/java/org/tron/core/utils/ProposalUtil.java:74-76`).
2. Once the required witness quorum approves it, `ProposalService.process()` calls `saveEnergyFee(entry.getValue())`, activating the value at the next maintenance cycle (`framework/src/main/java/org/tron/core/consensus/ProposalService.java:83-89`).
3. Any user triggers a smart contract call that exhausts frozen/free energy, forcing `ReceiptCapsule.payEnergyBill()` into the `energyFee = (usage - accountEnergyLeft) * sunPerEnergy` branch (`chainbase/src/main/java/org/tron/core/capsule/ReceiptCapsule.java:288-296`); with the crafted `ENERGY_FEE`, the multiplication overflows to a wrapped value.
4. The wrapped `energyFee` is compared against `account.getBalance()` and, if it passes, subtracted from the account and burned/sent to the black hole (`chainbase/src/main/java/org/tron/core/capsule/ReceiptCapsule.java:297-313`), draining funds disconnected from the actual `feeLimit` the sender authorized.
