### Title
Unstaked repair-request flood can starve staked repair traffic via FIFO-ordered `decode_requests` budget estimate - (File: `core/src/repair/serve_repair.rs`)

### Summary
`ServeRepair::decode_requests` gates the (expensive) sigverify/decode step behind a single shared `remaining_budget_estimate` counter that is decremented in packet-arrival order for *every* successfully decoded request, regardless of stake. Unlike the post-decode stage (`decoded_requests.sort_unstable_by_key(|r| Reverse((r.whitelisted, r.stake)))`), this pre-decode gate has no stake-awareness, so an unstaked attacker who gets enough cheap, self-signed repair packets to the front of the batch can exhaust the estimate and cause later, legitimately staked packets in the same iteration to be dropped via `dropped_requests_load_shed_sigverify` before they are ever sigverified.

### Finding Description
`run_listen` [1](#0-0)  computes a single scalar `effective_data_budget_estimate = data_budget.current_tokens() * 2 / byte_cost_multiplier` and passes it into `decode_requests`, which processes the whole batch's `Vec<BytesPacket>` in FIFO arrival order: [2](#0-1) 

For every packet that successfully decodes (passes format/self-signature checks in `decode_request`, which do **not** require stake — `stake` can be `0`), `remaining_budget_estimate` is decremented by the fixed `MIN_RESPONSE_SIZE` (`PACKET_DATA_SIZE + SIZE_OF_NONCE`) irrespective of the sender's stake. Once the counter drops below `MIN_RESPONSE_SIZE`, every subsequent packet in the batch — staked or not — is short-circuited and counted in `stats.dropped_requests_load_shed_sigverify`, without ever reaching sigverify or stake lookup.

The stake-aware protection only exists *after* decoding: `decoded_requests.sort_unstable_by_key(|r| Reverse((r.whitelisted, r.stake)))` + `truncate(MAX_REQUESTS_PER_ITERATION)` in `run_listen` [3](#0-2) . This cannot rescue packets that were already dropped at the decode stage, since those never enter the `decoded_requests` vector.

Crucially, when the node is currently a leader, `byte_cost_multiplier = LEADER_BYTE_COST_MULTIPLIER = 10` [4](#0-3) , shrinking `effective_data_budget_estimate` tenfold (down to at most `2 * 12_000_000 / 10 = 2_400_000` bytes, i.e. ~1942 requests at `MIN_RESPONSE_SIZE ≈ 1236` bytes). This is well under the per-iteration packet cap of `target_max_buffered_packets` (2048–4096, see `run_listen` lines 1173-1210), meaning an attacker sending well-formed, self-signed `WindowIndex`/`Orphan`/`AncestorHashes` requests can realistically exhaust the estimate within a single ~1 second `run_listen` iteration purely by volume.

The ingress path for repair requests is a plain UDP socket via `streamer::receiver` (`ServeRepairService::new`, `core/src/repair/serve_repair_service.rs`), which — unlike the QUIC TPU path (`streamer/src/nonblocking/quic.rs`, which has `ConnectionRateLimiter`/`overall_connection_rate_limiter`) — has no per-IP connection or packet rate limiting before packets reach `run_listen`/`decode_requests`. Sending a valid decode-passing packet costs the attacker nothing but self-signing a `RepairRequestHeader` with `recipient = leader_pubkey` and a timestamp within `SIGNED_REPAIR_TIME_WINDOW` — no stake, whitelist, or leader-issued nonce is required (`decode_request`, `verify_signed_packet`, lines 1053-1088 and 1430-1484).

### Impact Explanation
This is a bandwidth/CPU-cost-asymmetric denial-of-service: an unstaked, feeless attacker can, at low request volume (well under the channel/iteration caps), force the pre-sigverify budget-gate to short-circuit and drop staked/whitelisted repair traffic (`dropped_requests_load_shed_sigverify`) purely by packet ordering, degrading a leader's ability to answer legitimate shred repair requests during its slot — exactly the "unprivileged attacker forces sigverify/scheduling work exceeding fees collected, degrading the leader below true cost" bounty category referenced in the question.

### Likelihood Explanation
Preconditions are minimal: no stake, no whitelist entry, no gossip/peer control — only the ability to send UDP packets to the target's `serve_repair` port with a self-signed, well-formed `RepairProtocol` variant. The attack is cheap to construct (basic Ed25519 signing), repeatable every `run_listen` iteration (~1s), and most effective while the target is leader (10x tighter budget). The lack of per-IP throttling on the UDP repair-request ingress path (in contrast to the QUIC TPU ingress) makes sustaining the required packet rate straightforward.

### Recommendation
Make the pre-decode budget gate stake-aware (e.g., reserve a portion of `remaining_budget_estimate` for whitelisted/staked traffic, or defer/partition unstaked decode work), or perform a cheap stake/whitelist lookup before consuming budget so unstaked floods cannot consume the shared estimate ahead of staked packets purely by arrival order. Additionally consider adding coarse per-IP rate limiting on the UDP repair listener ingress, analogous to `ConnectionRateLimiter` used for QUIC.

    fn decode_requests(
        requests: Vec<BytesPacket>,
        epoch_staked_nodes: &Option<Arc<HashMap<Pubkey, u64>>>,
        whitelist: &HashSet<Pubkey>,
        my_id: &Pubkey,
        socket_addr_space: &SocketAddrSpace,
        mut remaining_budget_estimate: usize,
        stats: &mut ServeRepairStats,
    ) -> Vec<RepairRequestWithMeta> {
        const MIN_RESPONSE_SIZE: usize = PACKET_DATA_SIZE + SIZE_OF_NONCE;
        let decode_request = |request| {
            if remaining_budget_estimate < MIN_RESPONSE_SIZE {
                stats.dropped_requests_load_shed_sigverify += 1;
                return None;
            }
            let result = Self::decode_request(
                request,
                epoch_staked_nodes,
                whitelist,
                my_id,
                socket_addr_space,
            );
            match &result {
                Ok(req) => {
                    if req.stake == 0 {
                        stats.handle_requests_unstaked += 1;
                    } else {
                        stats.handle_requests_staked += 1;
                    }
                    // assuming we will reply to the request, we need to update the budget estimate
                    // some responses may be larger, but we have to be conservative here
                    remaining_budget_estimate -= MIN_RESPONSE_SIZE;
                }
                Err(e) => {
                    Self::record_request_decode_error(e, stats);
                }
            }
            result.ok()
        };
        requests.into_iter().filter_map(decode_request).collect()
    }
