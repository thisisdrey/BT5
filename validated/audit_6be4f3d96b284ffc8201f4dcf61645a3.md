### Title
Jetty-based HTTP APIs (`HttpService`) lack a header/idle read timeout, enabling a Slowloris-style Denial of Service - (File: framework/src/main/java/org/tron/common/application/HttpService.java)

### Summary
Every HTTP JSON API in java-tron (FullNode wallet API on port 8090, Solidity/PBFT wallet APIs, and the JSON-RPC endpoints on 8545/etc.) is built on the shared `HttpService.initServer()` helper, which constructs a Jetty `Server` via the bare `new Server(this.port)` constructor and never configures a connector-level idle/header-read timeout. This is the same bug class as the reported Chall-Manager gRPC-gateway issue: an HTTP listener that accepts connections and starts reading headers without bounding how long a client may take to complete sending them, allowing a Slowloris attack to exhaust available connections/threads.

### Finding Description
`HttpService.initServer()` builds the server this way: [1](#0-0) 

`new Server(this.port)` uses Jetty's convenience constructor, which creates a default `ServerConnector`/`HttpConnectionFactory` with no explicit `setIdleTimeout` call anywhere in this code path (confirmed absent via repository-wide search for `setIdleTimeout`/`IdleTimeout`/`ServerConnector` outside of test code). The only defensive control added is `ConnectionLimit`, which caps the *total number* of concurrent connections but does nothing to bound the *time* any single connection may take to finish sending its request line/headers: [1](#0-0) 

The `SizeLimitHandler` added in `initContextHandler()` only limits body size once the request has been dispatched — it does not protect the header-parsing phase of the connection: [2](#0-1) 

This base class is reused unauthenticated by every wallet/JSON-RPC HTTP surface reachable by anonymous API clients, e.g.: [3](#0-2) [4](#0-3) 

Because Jetty's default idle timeout (30s) only resets on any byte transfer, an attacker can keep a connection "alive" indefinitely by trickling a single byte of header data every ~25–29 seconds, never triggering the idle timeout, while never completing the HTTP request line/headers. Repeating this across `maxHttpConnectNumber` connections (a config knob that only limits count, not duration) saturates the connector's connection/thread pool, denying the wallet HTTP and JSON-RPC APIs to legitimate unauthenticated and authenticated clients alike — directly matching the CWE-770 (uncontrolled resource consumption via missing timeout) root cause of the reported advisory.

### Impact Explanation
A successful Slowloris attack against the FullNode HTTP wallet API (`/wallet/*`) or the JSON-RPC HTTP endpoint denies service to all API consumers of that node — wallets, exchanges, dApps, and other infrastructure relying on `getnowblock`, `broadcasttransaction`, `eth_*` JSON-RPC calls, etc. This matches the explicitly accepted impact category "an API the node can no longer serve." It does not directly compromise consensus or funds, keeping severity at High rather than Critical, consistent with the original advisory's High rating for the identical bug class.

### Likelihood Explanation
Exploitation requires no authentication, no valid transaction, and no special privileges — only the ability to open TCP connections to the exposed HTTP port and drip-feed header bytes, exactly as in the original Chall-Manager report. Given that java-tron nodes commonly expose `fullNodeHttpPort` (8090) and `jsonRpcHttpFullNodePort` (8545) publicly for wallet/dApp integration, likelihood is high wherever these ports are internet-reachable.

### Recommendation
Explicitly configure a bounded idle/header timeout on the Jetty connector(s) created in `HttpService.initServer()` (e.g., build an explicit `ServerConnector` with `HttpConfiguration` and call `connector.setIdleTimeout(...)` to a low, request-header-appropriate value such as 5–10s), rather than relying on the `new Server(port)` convenience constructor's defaults. Consider also setting `minRequestDataRate` and constraining `maxHttpConnectNumber` in combination with the new timeout so slow/incomplete connections are proactively reaped.

### Proof of Concept
1. Start a FullNode with the default `fullNodeHttpPort = 8090` enabled (`Args.getInstance().isFullNodeHttpEnable()` true) as wired by `FullNodeHttpApiService`. [3](#0-2) 
2. Open `maxHttpConnectNumber` (or more, if unset/unlimited) raw TCP sockets to port 8090.
3. On each socket, send a partial HTTP request line/header, e.g. `GET /wallet/getnowblock HTTP/1.1\r\nHost: x\r\n`, then pause and send one additional byte every 25 seconds, never sending the terminating `\r\n\r\n`.
4. Observe that Jetty's connector never idle-times-out these connections (idle timer resets on each trickled byte) because `HttpService` never overrides the default idle timeout, and no header-completion timeout exists.
5. Once the connection pool is saturated, legitimate requests to `/wallet/getnowblock`, `/wallet/broadcasttransaction`, or the JSON-RPC servlet on the same or sibling `HttpService` instances hang or are refused, demonstrating denial of service.
