Based on my investigation, I found a concrete analog in java-tron's TVM precompiled contracts.

### Title
Unbounded peer-controlled allocation in `PrecompiledContracts.extractBytes32Array` allows contract-call-triggered memory exhaustion - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`extractBytes32Array` reads an array-length word directly from attacker-controlled TVM call data and immediately allocates a Java array sized by that value, with no upper bound check, mirroring the iperf3 `JSON_read()` pattern where a peer-controlled length drives an unbounded allocation.

### Finding Description
`extractBytes32Array` takes the length of an array to extract straight from the ABI-encoded precompile input: [1](#0-0) 

`words[offset].intValueSafe()` clamps values that don't fit in 4 bytes to `Integer.MAX_VALUE` rather than rejecting them: [2](#0-1) 

So an attacker can set the length word to any value up to `Integer.MAX_VALUE` (or a moderately large value that still causes a multi-hundred-MB allocation), and the very next line `new byte[len][]` allocates that many object-reference slots before any bounds check against the actual size of the supplied `data`/`words` array is performed. The sibling helpers `extractBytesArray` and `extractSigArray` have the same pattern — they check `offset > words.length - 1` but never validate that `len` is consistent with the remaining input size before allocating `new byte[len][]`: [3](#0-2) 

These helpers are used by TVM precompiled contracts (e.g. batch signature validation) that any smart contract can invoke via a normal `CALL`/precompile dispatch with attacker-supplied call data, i.e., reachable by an unauthenticated/unprivileged transaction broadcaster who deploys or calls a contract that forwards crafted bytes to the precompile address.

### Impact Explanation
A single crafted transaction can force the full node to attempt an allocation of gigabytes for `new byte[len][]` (each element is an 8-byte reference slot on most JVMs, so even `len` in the tens of millions triggers hundreds of MB, and values near `Integer.MAX_VALUE` request many GB). This can throw `OutOfMemoryError`, stall or crash the executing node/validator process — a node crash/halt DoS reachable from ordinary contract calls, which is more severe than simple wasted energy since it is an allocation performed before/independent of proportional energy metering for the loop that would otherwise bound cost.

### Likelihood Explanation
Reaching this code only requires deploying or calling a contract that invokes the affected precompiled contract with crafted call data — no special privileges, keys, or consensus role needed. This matches the same reachability profile as the CVE-2026-71218 iperf3 report (unauthenticated remote party sending a length-prefixed message that drives allocation).

### Recommendation
Validate `len` against a sane upper bound (e.g., derived from `words.length` / the actual size of `data`) before allocating `new byte[len][]` in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray`, rejecting the precompile call (return `Pair.of(false, ...)`) when the declared length is inconsistent with the available input size, similar to the bound-checking pattern already used elsewhere (e.g. `isValidAbiEncoding`).

### Proof of Concept
Deploy a contract that calls the batch-signature-validation precompile with ABI-encoded input where the array-length word (at the offset consumed by `extractBytes32Array`/`extractBytesArray`/`extractSigArray`) is set to a large value (e.g. `0x7fffffff` or tens of millions) while the actual `data` payload is short; the precompile execution path allocates `new byte[len][]` before validating `len` against the real payload size, causing large/excessive memory allocation on the executing node.

**Note on uncertainty:** I was not able to fully trace the exact caller (e.g., the `BatchValidateSign` class body and its `getEnergyForData`) within the available iterations to confirm whether energy metering happens before or after this allocation, or whether an outer check already bounds `offset`/`len` in that specific precompile before calling these helpers. This should be verified directly in `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java` (search for the class that calls `extractBytes32Array`/`extractBytesArray`/`extractSigArray`) to confirm the exact reachable line and whether any existing guard mitigates it.

   * In case of int overflow returns Integer.MAX_VALUE otherwise works as #intValue()

  public int intValueSafe() {
    int bytesOccupied = bytesOccupied();
    int intValue = intValue();
    if (bytesOccupied > 4 || intValue < 0) {
      return Integer.MAX_VALUE;
    }
