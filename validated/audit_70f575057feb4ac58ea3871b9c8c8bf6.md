### Title
Stale postponed StakeAction survives account deletion and executes against a recreated same-named account, forging a validator proposal - (File: `runtime/runtime/src/lib.rs`, `runtime/runtime/src/actions.rs`)

### Summary
Postponed action receipts and their `PendingDataCount`/`PostponedReceiptId` bookkeeping are keyed only by the receiver's `AccountId` string and `receipt_id`/`data_id`, not by any per-account "incarnation" identifier. `action_delete_account` removes the `Account` record but does not sweep these postponed-receipt trie keys, and because long (≥32-char) top-level account names can be recreated by anyone, a `Data` receipt delivered after deletion+recreation resumes a stale `StakeAction` against the new account, whose only authorization check is string equality between `predecessor_id` and `receiver_id`.

### Finding Description
`process_action_receipt` (`runtime/runtime/src/lib.rs:1593-1658`) stores an incoming action receipt awaiting data under `TrieKey::PostponedReceiptId{receiver_id, data_id}` and `TrieKey::PendingDataCount{receiver_id, receipt_id}` plus `TrieKey::PostponedReceipt{receiver_id, receipt_id}` (`set_postponed_receipt`, `core/store/src/utils/mod.rs:120`). None of these keys reference anything that changes when the account behind `receiver_id` is deleted and recreated — they are purely a function of the account-name string.

`action_delete_account` (`runtime/runtime/src/actions.rs:314-389`) refunds balance, burns gas keys, and calls `remove_account`, but it never touches `PostponedReceiptId`/`PendingDataCount`/`PostponedReceipt` for the account. So a postponed receipt parked before deletion remains fully intact in state after deletion.

Long top-level account names are not registrar-gated: `action_create_account` (`runtime/runtime/src/actions.rs:167-210`) only restricts creation to `registrar_account_id` when `account_id.len() < min_allowed_top_level_account_length` (32); for `len() >= 32` any predecessor can create the account (`actions.rs:176-190`, confirmed by `docs/DataStructures/Account.md:36-41` and `integration-tests/src/tests/features/restrict_tla.rs`). Thus once account A (a long TLA) is deleted, an unrelated party can immediately recreate an account with the exact same name.

When the withheld `Data` receipt finally arrives, `process_receipt`'s `Data` branch (`runtime/runtime/src/lib.rs:1386-1473`) looks up `PostponedReceiptId{receiver_id: "A", data_id}` — this is still present because deletion never cleared it — decrements `PendingDataCount`, and once it reaches 0, calls `apply_action_receipt` on the fetched `PostponedReceipt`. This dispatches to `action_stake` (`runtime/runtime/src/actions.rs:59-99`) using whatever `Account` is *currently* stored under name "A" — the new owner's account, not the original one.

The only actor-permission requirement for `Stake` is `predecessor_id == receiver_id` (`docs/RuntimeSpec/Actions.md:26-32`), which is a pure string comparison on the original receipt's fields, unaffected by the account having been deleted and recreated. `action_stake` pushes `ValidatorStake::new(account_id, stake.public_key, stake.stake)` into `validator_proposals` and moves `amount → locked` on the new account whenever `account.amount().checked_sub(increment)` succeeds (`actions.rs:69-99`), i.e., whenever the new account has been funded enough to cover the stake — a state the new owner naturally reaches if they fund their fresh account before doing anything else.

No check anywhere in this path verifies that the account identity backing `receiver_id` at postponed-receipt-resolution time is the same account that existed when the receipt was originally parked. Signature/nonce checks are irrelevant here because this is action-receipt resumption, not a fresh signed transaction; access-key checks don't apply to receipt-internal actor permission checks for `Stake`.

### Impact Explanation
This is an authorization-escalation bug: a `ValidatorStake` proposal for account A is submitted using a public key chosen by the attacker (not by A's new owner), and A's `locked` balance is force-moved from `amount` without any action ever signed by A's real owner. This falls into the "authorization escalation across accounts/promises" bounty category, and secondarily threatens correct reward/inflation accounting for the affected epoch since an unconsented validator proposal alters stake distribution and reward calculations. ### Likelihood Explanation
Preconditions: attacker needs a long (≥32-char) top-level account A they control, a contract on A capable of chaining a cross-contract call with a `.then()` callback carrying a `Stake` action targeting itself (`predecessor_id == receiver_id == A`), the ability to delay delivery of the dependency `Data` receipt (attacker fully controls this via the receiver contract of the intermediate call), zero `locked` stake on A at delete time (trivially true since the Stake action hasn't executed yet), and a third party who happens to recreate and fund an account with the exact same freed name before the withheld data receipt is released. All of this is achievable by an ordinary unprivileged client deploying its own contract and timing its own cross-shard calls — no validator/node privilege is required. The main practical constraint is the race for a third party to reuse the exact freed name with sufficient funding, which narrows real-world likelihood but does not require any privileged capability.

### Recommendation
Bind postponed-receipt bookkeeping (and pending-data tracking) to more than just the `AccountId` string — e.g., invalidate/sweep all `PostponedReceiptId`, `PendingDataCount`, and `PostponedReceipt` entries for an account when it is deleted (`action_delete_account`/`remove_account`), or fail/expire postponed action receipts whose target account no longer matches an account-creation epoch/nonce recorded at postponement time.

### Proof of Concept
Runtime `apply` integration test (in `runtime/runtime/src/tests/apply.rs`, mirroring the pattern of `test_promise_input_size_limit_exceeded_fails_and_cleans_up`):
1. Fund account A (a ≥32-char top-level name) and have A "park" an `ActionReceipt` containing `Action::Stake` with `predecessor_id == receiver_id == A` and `input_data_ids = [data_id]` (not yet delivered) — write it directly via `set_postponed_receipt`/`PendingDataCount`/`PostponedReceiptId` to simulate the parked state, matching what `process_action_receipt` would produce.
2. Apply a `DeleteAccount` receipt for A with `locked == 0`; assert `get_account(state, A) == None` while `get_postponed_receipt`/`PendingDataCount`/`PostponedReceiptId` for A remain non-`None`.
3. Apply a `CreateAccount` + `Transfer` (sufficient funds) receipt sequence recreating A under a different signer/owner.
4. Deliver the withheld `Data` receipt with `data_id` matching the parked receipt.
5. Assert the resulting `ApplyResult.validator_proposals` contains a `ValidatorStake` for account A with the original attacker-chosen public key, and that the new account's `locked` balance was force-increased — despite no `Stake` transaction ever being signed by the new owner.
