### Title
Missing zero-address (null-address) validation in `TransferActuator`/`TransferAssetActuator` allows permanent loss of TRX/TRC10 tokens - (File: actuator/src/main/java/org/tron/core/actuator/TransferActuator.java)

### Summary
`TransferActuator.validate()` and `TransferAssetActuator.validate()` only check that `toAddress` is *format*-valid via `DecodeUtil.addressValid()`, which verifies length and the network prefix byte, but never rejects an address whose remaining 20 bytes are all zero (i.e., the "null address" `0x41 000...000`). A caller (an unprivileged transaction broadcaster) can send `TransferContract`/`TransferAssetContract` transactions with `toAddress` set to this all-zero address, and both `validate()` and `execute()` will accept and process it, permanently locking the transferred TRX/TRC10 asset in an account nobody can control.

### Finding Description
`DecodeUtil.addressValid()` only checks:
1. the address is non-empty,
2. the address length equals `ADDRESS_SIZE/2` (21 bytes),
3. the first byte matches `addressPreFixByte`. [1](#0-0) 

It performs no check that the remaining 20 bytes are non-zero, so the address `0x41` followed by 20 zero bytes passes `addressValid()` as a legitimate address.

`TransferActuator.validate()` uses only `DecodeUtil.addressValid(toAddress)` plus a self-transfer check (`Arrays.equals(toAddress, ownerAddress)`) — there is no check against the null/zero address: [2](#0-1) 

`TransferActuator.execute()` then creates a new account at `toAddress` (if none exists) and credits it with the transferred amount, with no special-casing for the zero address: [3](#0-2) 

The same pattern exists in `TransferAssetActuator.validate()`/`execute()` for TRC10 token transfers, which also only validates `toAddress` via `DecodeUtil.addressValid()`: [4](#0-3) [5](#0-4) 

`CreateAccountActuator.validate()` similarly only calls `DecodeUtil.addressValid(accountAddress)` without a zero-address check: [6](#0-5) 

This mirrors the reported Hats Protocol issue: the missing-zero-check is not about total absence of address validation, but about validation that accepts a *format-valid but semantically null* address, letting a user accidentally (or a malicious actor deliberately, e.g., to “burn” competitor funds by tricking a UI/wallet into it) send funds to an address that nobody holds a private key for.

### Impact Explanation
TRX or TRC10 tokens sent to the all-zero address become permanently unspendable, since no private key can plausibly produce that address (probability of collision is negligible). This is a direct, unbacked and permanent freezing of user funds triggerable by a single signed `TransferContract` or `TransferAssetContract` transaction from any unprivileged account — matching the "permanent freezing of funds" impact bar from the validation rules. Unlike TRX sent to the pre-defined `Blackhole` account (which is an intentional, accounted-for burn address configured in genesis with `Long.MIN_VALUE` balance so it only increases, per `common/src/main/resources/reference.conf`), the literal zero address is not a recognized/blessed burn destination — it is simply an ordinary newly-created account that nobody controls.

### Likelihood Explanation
Likelihood is moderate: it requires the `toAddress` field of a `TransferContract`/`TransferAssetContract` to be exactly the zero-payload address, which is unlikely to occur by pure chance but plausible via wallet/client bugs, copy-paste errors, or malicious front-end/dApp manipulation that pre-fills a default/uninitialized address value (a very common source of this bug class across blockchains, as demonstrated by the referenced Hats Protocol finding). No special privilege is needed — the transaction is a plain, ordinary transfer from any account holder.

### Recommendation
Add an explicit check in `TransferActuator.validate()` and `TransferAssetActuator.validate()` (and ideally `CreateAccountActuator.validate()`) that rejects `toAddress`/`accountAddress` values equal to the all-zero payload (i.e., `addressPreFixByte` followed by 20 zero bytes), similar to the existing self-transfer check, e.g.:
```java
byte[] zeroAddress = new byte[21];
zeroAddress[0] = DecodeUtil.addressPreFixByte;
if (Arrays.equals(toAddress, zeroAddress)) {
  throw new ContractValidateException("Cannot transfer to the zero address.");
}
```

### Proof of Concept
1. An attacker or a buggy wallet constructs a `TransferContract` with `ownerAddress` = attacker's valid account and `toAddress` = `0x41` + 20 zero bytes (a 21-byte address that satisfies `DecodeUtil.addressValid()`).
2. Broadcast the signed transaction; `TransferActuator.validate()` passes because `addressValid(toAddress)` returns `true` and `toAddress != ownerAddress`.
3. `TransferActuator.execute()` creates a new `AccountCapsule` at the zero address and calls `adjustBalance(accountStore, toAddress, amount)`, crediting the funds.
4. Because no private key can generate the zero address, the funds are permanently inaccessible — repeat with `TransferAssetContract` to similarly strand TRC10 token balances.

Note: I was unable to fully verify whether any downstream code path (e.g., block application in `Manager`, or wallet RPC layers) applies an additional, separate zero-address filter before invoking these actuators; based on the actuator-level `validate()` implementations reviewed, no such check exists at the actuator layer, which is the authoritative place enforcing `ContractValidateException`s for these contract types.

```java
  public static boolean addressValid(byte[] address) {
    if (ArrayUtils.isEmpty(address)) {
      logger.warn("Warning: Address is empty !!");
      return false;
    }
    if (address.length != ADDRESS_SIZE / 2) {
      logger.warn(
          "Warning: Address length need " + ADDRESS_SIZE + " but " + address.length
              + " !!");
      return false;
    }

    if (address[0] != addressPreFixByte) {
      logger.warn("Warning: Address need prefix with " + addressPreFixByte + " but "
          + address[0] + " !!");
      return false;
    }
    return true;
  }
```
