## Title
External caller's attached NEAR deposit is permanently stuck in the eth-implicit Wallet Contract on `address_check_callback` / `nep_141_storage_balance_callback` early-failure paths - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The `WalletContract::rlp_execute` entrypoint is `#[payable]`, so any unprivileged external caller (a relayer or third party, i.e. `predecessor_account_id != current_account_id`) can attach a NEAR deposit when submitting a signed Ethereum-style transaction to be relayed through the wallet. This deposit is tracked as `CallerDeposit` so it can be refunded if the cross-contract call ultimately fails. However, two of the intermediate callback functions — `address_check_callback` and `nep_141_storage_balance_callback` — receive `caller_deposit` as a parameter but have early-return branches that produce a failed `ExecuteResponse` without ever spending or forwarding `caller_deposit` to a refund promise. The deposit is simply dropped, permanently remaining in the wallet contract's account balance instead of being returned to the external caller who attached it.

### Finding Description
`CallerDeposit::new` captures the attached deposit whenever the predecessor differs from the wallet's own account, precisely to support later refunding it if the relayed action fails: [1](#0-0) 

`inner_rlp_execute` builds this `caller_deposit` from the attached deposit on the call to `rlp_execute` and threads it through the various promise chains as a callback argument: [2](#0-1) 

The *only* place that actually performs the refund is `rlp_execute_callback`, which spends `caller_deposit` via `promise_batch_action_transfer` when the final cross-contract call fails: [3](#0-2) 

But `address_check_callback` accepts the same `caller_deposit` parameter and has two paths that return an error `ExecuteResponse` directly, without routing through `rlp_execute_callback` and without ever touching `caller_deposit`:
- when the registrar lookup call itself fails: [4](#0-3) 
- when the target address maps to an existing named account and the caller is not a signer-key relayer (the "Invalid target" branch): [5](#0-4) 

The same pattern exists in `nep_141_storage_balance_callback`, whose `PromiseResult::Failed` and JSON-parse-error branches also short-circuit and return an `ExecuteResponse` without spending `caller_deposit`: [6](#0-5) 

In every one of these early-return branches, the `caller_deposit: Option<CallerDeposit>` local simply goes out of scope and is dropped — no refund receipt is ever created, and there is no other method exposed on `WalletContract` to withdraw or reclaim this stranded balance.

### Impact Explanation
The attached deposit was NEAR tokens transferred from an external, unprivileged caller's own account into the wallet contract's account balance as part of the `#[payable]` `rlp_execute` call. When one of these error branches is taken, that balance is never returned to the caller. The funds remain forever mixed into the wallet owner's account balance, unrecoverable by the depositor and not tracked/exposed as reclaimable by anyone. This is a permanent loss of funds for the external caller — functionally identical to the reported Solidity issue where `msg.value` fee is consumed/stuck in the contract only in specific code paths, with no facility to reclaim it.

### Likelihood Explanation
Reaching `address_check_callback`'s stuck-deposit branch requires only an ordinary, unprivileged flow: any external account can call the payable `rlp_execute` method with a deposit while relaying an `EOABaseTokenTransfer` whose `target` needs an address-registrar lookup. If the registrar call fails (e.g., transient failure, gas exhaustion, or the registrar being temporarily unavailable) or if the looked-up address turns out to correspond to an already-registered named account while the caller isn't using an access key for the wallet (the common case for third-party relayers), the deposit-stuck branch triggers deterministically. No malicious node or privileged actor is needed — an ordinary relayer/caller attaching a deposit can lose it under normal operating conditions.

### Recommendation
In every early-return branch of `address_check_callback` and `nep_141_storage_balance_callback` that produces a failed `ExecuteResponse`, refund `caller_deposit` the same way `rlp_execute_callback` does (via `env::promise_batch_create` + `promise_batch_action_transfer`) before returning, or funnel these failure branches through `rlp_execute_callback`/a shared refund helper so no failure path can be added in the future without also handling the deposit refund.

### Proof of Concept
1. External account `Caller` (not the wallet owner, no access key on the wallet) calls the wallet contract's `rlp_execute(target, tx_bytes_b64)` attaching a NEAR deposit, with an RLP-encoded Ethereum transaction representing an `EOABaseTokenTransfer` whose target address requires an address-registrar lookup (`address_check: Some(address)`), per `inner_rlp_execute`'s dispatch: [7](#0-6) .
2. `CallerDeposit::new` captures `Caller`'s deposit since `predecessor_account_id != current_account_id`.
3. The registrar lookup promise resolves to `Some(existing_account_id)` (the `to` address happens to correspond to an already-registered named account), and `env::signer_account_id() != current_account_id` (typical relayer without an access key).
4. `address_check_callback` takes the "Invalid target" branch and returns `PromiseOrValue::Value(ExecuteResponse{success:false, ...})` immediately, never spending `caller_deposit`.
5. `Caller`'s attached NEAR deposit remains permanently in the wallet contract's account balance; no refund receipt is ever generated, and `Caller` has no way to reclaim the funds.
