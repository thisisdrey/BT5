The binding to validate: for any two `TokenId` values `t1 != t2` (i.e., naming different `(contract, token)` pairs), their canonical string form `t1.to_string() != t2.to_string()` AND their Borsh-serialized bytes `borsh(t1) != borsh(t2)`.

**Tracing the guards:**

`TokenId` is a `#[repr(u8)]` enum with `Nep141(...) = 0, Nep171(...) = 1, Nep245(...) = 2, Imt(...) = 3` and `borsh(use_discriminant = true)`, so Borsh serialization always embeds a distinct 1-byte discriminant per variant before the inner fields — a NEP-245 value can never Borsh-collide with a NEP-141 value. [1](#0-0) 

`Display`/`Debug` for `TokenId` always prefix the output with the `TokenIdType` discriminant name (`"nep141:"`, `"nep171:"`, `"nep245:"`, `"imt:"`), and `FromStr` splits on the first `:` to recover the type tag before delegating to the inner type's parser. [2](#0-1) 

This makes cross-type string collision (e.g., a `nep245:...` string being parsed/displayed identically to a `nep141:...` string) structurally impossible — the type prefixes differ.

**Within a single type (e.g., `Nep245TokenId`):** its `Display` is `"{contract_id}:{mt_token_id}"` and `FromStr` uses `split_once(':')` to separate `contract_id` from `mt_token_id`. [3](#0-2) 

Since `contract_id` is a `near_account_id::AccountId`, which only permits NEAR-valid characters (lowercase alphanumerics, `-`, `_`, `.`) and never a literal `:`, the first `:` in the string can only be the type/field separator — never an injected delimiter inside `contract_id`. This guarantees the split point is unambiguous and the round-trip is injective: distinct `(contract_id, mt_token_id)` pairs always produce distinct strings, and any given string parses back to exactly the pair that produced it (this exact invariant is validated by `display_from_str_roundtrip` for both `Nep141TokenId` and `Nep245TokenId`). [4](#0-3) [5](#0-4) 

The `mt_token_id: String` field itself is unconstrained (can contain colons), but that only affects where subsequent splits land within the same variant's data — it cannot shift the variant-type prefix or fabricate a valid `AccountId` containing `:` for the `contract_id` position, so it cannot manufacture a NEP-141 vs NEP-245 collision as hypothesized.

Because `internal_apply_deltas` keys balances by the `TokenId` enum value (whose `PartialEq`/`Hash`/`Ord` are derived over the full discriminated enum, not just a raw string), and the discriminant is embedded in both serde string form and Borsh form, there is no reachable path where an attacker-crafted `MultiPayload`'s `TokenDiff.diff: Amounts<BTreeMap<TokenId, DisplayFromStr>>` can deserialize a `TokenId` that identifies one asset while later settlement logic (`TransferMatcher::finalize`) resolves a different underlying `(contract, token)`.
