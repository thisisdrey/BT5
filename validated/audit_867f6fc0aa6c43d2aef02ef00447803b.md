### Title
StackerDB signer revocation can be silently ignored, leaving a removed writer permanently authorized to overwrite chunks - (File: `stackslib/src/net/stackerdb/mod.rs`)

### Summary
`StackerDBs::create_or_reconfigure_stackerdbs` decides whether to apply a freshly-loaded `StackerDBConfig` (derived from the controlling smart contract's `stackerdb-get-signer-slots` result) by comparing it to the previously-stored config. The guard on the "changed" branch requires `!new_config.signers.is_empty()` before the reconfiguration is actually persisted: [1](#0-0) 

### Finding Description
Signer authorization for a StackerDB slot is exactly the "current stored" config (`SlotValidation.signer` in `db.rs`) versus the "authoritative" config declared by the controlling contract via `eval_signer_slots`/`from_smart_contract`. `try_replace_chunk` and `validate_received_chunk` gate every remote write purely on whether the chunk's signature recovers to the *stored* `slot_validation.signer`/`get_slot_signer` value: [2](#0-1) [3](#0-2) 

That stored value is only ever updated by `reconfigure_stackerdb`, which is only invoked when:
```
(new_config != stackerdb_config && !new_config.signers.is_empty())
|| (new_config == stackerdb_config && new_config.signers.len() != self.get_slot_versions(...)?.len())
``` [1](#0-0) 

If the controlling contract legitimately revokes all writers for a StackerDB (i.e. `stackerdb-get-signer-slots` now returns an empty list, so `new_config.signers` is empty), the first disjunct is false because of the `!new_config.signers.is_empty()` guard, and the second disjunct is false because `new_config != stackerdb_config` in this case (config changed, versions unaffected on their own). As a result `reconfigure_stackerdb` is never called, `self.stackerdbs` keeps serving the *old* `SlotValidation.signer` entries, and the previously-authorized (now revoked) private key continues to pass `slot_desc.verify(&slot_validation.signer)` / `slot_metadata.verify(&addr)` forever, both for chunks pushed to the P2P port and via `POST /v2/stackerdb/.../chunks`. This is precisely analogous to the reported bug class: an equality that is supposed to gate write authority (`authenticated-signer == currently-authorized-signer`) fails to update when the authoritative source of truth (the contract) issues a revocation, so the stale/soon-to-be-revoked party's writes keep being accepted and propagated network-wide as legitimate StackerDB state, exactly like the veNFT's stale vote being permanently "unpokeable."

Note the existing comment in the code references a related, but distinct, historical bug (#5142 — "a stackerdb could never shrink") which this same conditional was patched to address; the `is_empty()` guard, however, reintroduces an equivalent "stuck old authorization" failure mode specifically for the full-revocation case.

### Impact Explanation
An attacker who previously held a StackerDB slot (e.g. a rotated-out signer/miner key) retains the ability to push and have accepted arbitrary chunk data to that slot on every replica that hits this code path after the contract revokes them, because the local replicas never learn of the revocation. Since StackerDB chunks are gossiped and stored as authoritative state (e.g. `.miners`, signer message relay contracts), this is an unauthorized write to replicated network state by a party the protocol intended to de-authorize — matching the report's "High: serving non-canonical state as canonical" / unauthorized-write class.

### Likelihood Explanation
This triggers on the ordinary, expected admin action of removing/rotating a signer's slot allocation to zero entries via the controlling contract — not an edge case requiring privileged access from the attacker's side. Any node that reaches this reconfiguration branch with a full-revocation config change will exhibit it, requiring no unusual conditions beyond a governance-side signer-set-to-empty update, which is a normal lifecycle event (e.g., removing all writers before recreating the DB with a fresh set).

### Recommendation
Change the reconfiguration guard so it also fires when the signer set has legitimately changed to empty, e.g. reconfigure whenever `new_config.signers != stackerdb_config.signers` (drop the `!new_config.signers.is_empty()` short-circuit), while still guarding against genuinely transient load failures (which fall back to `StackerDBConfig::noop()` and should be distinguished from a real, successfully-evaluated empty signer list) by checking the `Result` of `from_smart_contract` rather than inferring failure from an empty signer vector.

### Proof of Concept
1. Node has a StackerDB replica configured with signer `S` at slot 0 (`stackerdb_config.signers = [(S, 1)]`), stored via `create_stackerdb`/`reconfigure_stackerdb` in `db.rs`.
2. The controlling contract is updated so `stackerdb-get-signer-slots` returns an empty list (revoking `S`). `StackerDBConfig::from_smart_contract` successfully evaluates and returns `new_config.signers == []`.
3. On the next call to `create_or_reconfigure_stackerdbs`, `new_config != stackerdb_config` is true, but `new_config.signers.is_empty()` is also true, so the branch at [1](#0-0)  is skipped — `reconfigure_stackerdb` is never called and `new_stackerdb_configs` records the empty config for in-memory bookkeeping only.
4. The persisted `chunks` table still has `signer = S` for slot 0 (`SlotValidation.signer`), per `get_slot_validation` in `db.rs`.
5. `S` (now supposedly revoked) signs and pushes a new chunk. `try_replace_chunk`/`validate_received_chunk` still recovers `S` as the valid signer and accepts the write, which is then gossiped to peers as legitimate StackerDB inventory via `make_StackerDBChunksInv_or_Nack`.

Note: this analysis is based on static review of the indexed source; I could not execute the code to empirically confirm run-time behavior of `create_or_reconfigure_stackerdbs` under a live revocation scenario, so consider validating with an integration test that revokes a signer via a StackerDB-controlling contract and observes whether old-signer chunk writes are still accepted afterward.
