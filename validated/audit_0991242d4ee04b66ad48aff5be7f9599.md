This confirms the underlying mechanism: cost accounting for the per-account limit (`MAX_WRITABLE_ACCOUNT_UNITS`) is based on `signature_cost + write_lock_cost + programs_execution_cost (requested/default CU) + ...`, which is entirely decoupled from the priority fee (`compute_unit_price`) the attacker actually pays. A transaction with `compute_unit_price = 0` and a minimal/default `compute_unit_limit` still consumes real compute-unit budget against the account's `24_000_000`-CU ceiling.

### Title
Cheap self-conflicting low/zero-fee transactions can exhaust the per-account `MAX_WRITABLE_ACCOUNT_UNITS` cost budget, evicting legitimate transactions on that account from the block - ([File: cost-model/src/cost_tracker.rs])

### Summary
The reported voting bug lets Alice cheaply create a fake "self-challenge" that consumes the scarce resource (the vote outcome / lockout) at negligible cost, crowding out genuine challengers since the resource has no minimum-cost floor tied to its actual value. The same structural weakness exists in Agave's `CostTracker`: the per-writable-account compute-unit budget (`MAX_WRITABLE_ACCOUNT_UNITS = 24_000_000`) is charged based on the cost-model's fixed/estimated compute units (signatures, write locks, requested/default CU limit), not on the fee actually paid (`compute_unit_price` can be `0`). An attacker who owns/controls a hot account (or targets any account they can write-lock) can flood it with a stream of self-authored, minimum-fee transactions that legitimately execute (so they aren't dropped as duplicates) but collectively saturate that account's 24M CU ceiling for the block, at negligible cost, blocking any other user's competing transaction that touches the same account from being scheduled/committed in that slot — analogous to Alice's low-`voterPercent` self-challenge locking out real challengers.

### Finding Description
`CostTracker::would_fit` enforces `WouldExceedAccountMaxLimit` purely on cumulative compute units per writable account, independent of the fee actually paid: [1](#0-0) 
The account limit itself, `MAX_WRITABLE_ACCOUNT_UNITS`, is a fixed constant (24,000,000 CU) meant to bound per-account parallelism/contention, with no fee-based floor: [2](#0-1) 
The compute-unit cost charged per transaction (`signature_cost + write_lock_cost + programs_execution_cost + ...`) is computed by the cost model from static transaction properties — number of signatures, number of write locks, and the transaction's (self-declared or default) compute-unit limit — and has no relationship to `compute_unit_price`/priority fee: [3](#0-2) 
A `compute_unit_price` of `0` is explicitly a valid, minimal-fee configuration, confirmed by the scheduler's own priority calculation test showing priority (and thus effective fee) can be `0`: [4](#0-3) 
So an attacker can author a sequence of otherwise-valid, uniquely-hashed (non-duplicate) transactions that all write-lock the same target account, each declaring a modest `compute_unit_limit` (the cost-model charges the *declared/default* limit, not actual usage, at admission time via `would_fit`/`try_add` in the scheduler's cost-tracking path), while setting `compute_unit_price = 0` or near-zero. Submitting enough such transactions fills the account's 24M-CU budget almost entirely from the attacker's own low-value work. Because `would_fit` rejects *any* further transaction touching that account once the account limit is hit (`WouldExceedAccountMaxLimit`), a legitimate high-value/high-fee transaction from another party touching the same account is refused for the remainder of the block, even though it would have paid far more per unit of "damage" than the attacker's spam. This is the same self-inflicted, low-cost occupation of a bounded/contended resource described in the report, just realized against the banking-stage cost-tracker/account-lock resource instead of a governance vote.

### Impact Explanation
This is a QoS evasion / grossly-underpriced pre-fee work issue: a resource (per-account CU budget, one of the mechanisms that exists specifically "to prevent too many transactions writ[ing] to same account" and preserve fairness/parallelism) can be monopolized by an attacker at minimal fee cost, denying block space to legitimate, better-paying transactions that target the same account for an entire slot. This does not crash a node or corrupt state, but it undermines the fee market's censorship-resistance/fairness guarantee for any hot account (e.g., a popular AMM pool, an NFT mint, or a victim's own account) — the attacker "protects" that account slot from being used by others, mirroring the self-challenge griefing pattern in the report.

### Likelihood Explanation
Any unprivileged user can submit ordinary, individually valid transactions (no special role required); the only requirement is enough SOL to pay minimal base fees for a burst of transactions targeting one writable account within a slot's ~24M CU ceiling. This is directly reachable via normal RPC/TPU submission paths already exercised by `banking_stage`/`cost_tracker` and requires no cluster cooperation beyond normal transaction propagation and no privileged validator/operator role.

### Recommendation
Tie the effective per-account cost admitted into `CostTracker` to the fee/priority actually paid (e.g., require a minimum `compute_unit_price` or minimum aggregate fee per unit of account-cost consumed, similar in spirit to `PrioritizationFee`'s per-account minimum fee tracking), or otherwise ensure that filling the account-cost budget with your own transactions cannot come at negligible marginal cost relative to the value of the block space being denied to others.

### Proof of Concept
1. Choose target account `A` (any account you can write-lock, including one you control).
2. Generate `N` distinct, validly-signed transactions (unique message hashes to avoid `AlreadyProcessed`/dedup), each write-locking `A`, each with `compute_unit_price = 0` and a `compute_unit_limit` set just high enough that `N * per_tx_cost ≈ MAX_WRITABLE_ACCOUNT_UNITS (24_000_000)` per [2](#0-1) .
3. Submit them all to the current leader in the same slot; the greedy/central scheduler admits each via `try_schedule_transaction` → `CostTracker::would_fit`/`try_add`, each succeeding until the account hits its 24M-CU limit as verified by the existing account-limit test [5](#0-4) .
4. Submit a legitimate, high-`compute_unit_price` transaction from a different payer that also writes to `A` in the same slot — observe it is rejected with `WouldExceedMaxAccountCostLimit` for the remainder of the block, despite paying far more per CU than the attacker's transactions.

    fn would_fit(
        &self,
        tx_cost: &TransactionCost<impl TransactionWithMeta>,
    ) -> Result<(), CostTrackerError> {
        let cost: u64 = tx_cost.sum();

        if self.block_cost().saturating_add(cost) > self.limits.block_cost {
            // check against the total package cost
            return Err(CostTrackerError::WouldExceedBlockMaxLimit);
        }

        // check if the transaction itself is more costly than the account_cost_limit
        if cost > self.limits.account_cost {
            return Err(CostTrackerError::WouldExceedAccountMaxLimit);
        }

        let allocated_accounts_data_size =
            self.allocated_accounts_data_size + Saturating(tx_cost.allocated_accounts_data_size());

        if allocated_accounts_data_size.0 > self.limits.allocated_data_size {
            return Err(CostTrackerError::WouldExceedAccountDataBlockLimit);
        }

        // check each account against account_cost_limit,
        for account_key in tx_cost.writable_accounts() {
            match self.cost_by_writable_accounts.get(account_key) {
                Some(chained_cost) => {
                    if chained_cost.saturating_add(cost) > self.limits.account_cost {
                        return Err(CostTrackerError::WouldExceedAccountMaxLimit);
                    } else {
                        continue;
                    }
                }
                None => continue,
            }
        }
