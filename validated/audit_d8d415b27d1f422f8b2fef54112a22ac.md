### Title
Unbounded Full Table Load Before Limit/Offset Enforcement in `AssetIssueStore.getAssetIssuesPaginated` - (File: `chainbase/src/main/java/org/tron/core/store/AssetIssueStore.java`)

### Summary
The paginated asset-issue query, reachable anonymously via HTTP (`/wallet/getpaginatedassetissuelist`), gRPC (`GetPaginatedAssetIssueList`), and their PBFT/Solidity mirrors, applies the caller-supplied `offset`/`limit` only after the entire `AssetIssueStore` has been iterated and materialized into a `List`, exactly mirroring the `SimpleDirectoryReader`/`num_files_limit` flaw in the reported CVE-2025-6208 (limit enforced post-load rather than pre-load).

### Finding Description
`AssetIssueStore.getAssetIssuesPaginated(offset, limit)` calls `getAllAssetIssues()` first, which streams the *entire* underlying LevelDB/RocksDB column for asset issues into a `List<AssetIssueCapsule>` in memory: [1](#0-0) 

Only after this full materialization does the code sort the entire list and slice it by `offset`/`limit`, with the limit clamp (`ASSET_ISSUE_COUNT_LIMIT_MAX = 1000`) applied to the *output size*, not to the amount of work/data loaded: [2](#0-1) [3](#0-2) 

This is invoked directly from `Wallet.getAssetIssueList(offset, limit)`, which further clones the list into a protobuf builder, doubling the resident memory pressure per request: [4](#0-3) 

The call path from an anonymous, unauthenticated client is direct and requires no signed transaction:
- HTTP: `GetPaginatedAssetIssueListServlet.doGet/doPost` → `wallet.getAssetIssueList(offset, limit)` [5](#0-4) 
- gRPC (`WalletSolidityApi`/`WalletApi`): `getPaginatedAssetIssueList` → `wallet.getAssetIssueList(request.getOffset(), request.getLimit())` [6](#0-5) 
- Also mirrored on PBFT/Solidity read-only nodes: [7](#0-6) 

An attacker can request `limit=1` repeatedly, and on every single call the node still: (1) iterates the *entire* asset-issue key range from disk, (2) deserializes every `AssetIssueCapsule` into memory, (3) sorts the full in-memory list by name/order, and (4) copies the sliced result into a protobuf builder — none of which is bounded by the requested `limit`. As the chain's total asset-issue count grows (asset issuance is a normal, cheap, permanent operation — one per funded account, never deleted, validated only by `calcFee()`/balance and the "one asset per account" rule in `AssetIssueActuator.validate`, e.g. lines around ownership/balance checks): [8](#0-7) 
this endpoint's per-request cost scales linearly (plus O(n log n) sort) with the *entire historical* asset-issue table, independent of the caller's requested page size.

### Impact Explanation
Because pagination gives callers the false impression that cost is proportional to `limit`, but the actual work/memory is proportional to the full table size, an unprivileged remote client can trigger disproportionate CPU and memory consumption on any full node/solidity node/PBFT node exposing the HTTP or gRPC wallet API by repeatedly hitting `getpaginatedassetissuelist` with a minimal `limit`. Sustained concurrent requests can degrade or exhaust node memory/CPU, denying the JSON/HTTP/gRPC query service to other users — matching the "API the node can no longer serve" acceptance criterion. This is a resource-exhaustion (CWE-400) issue analogous in root cause to the reported CVE, though the achievable severity in java-tron is capped by how large the historical asset-issue table can realistically grow.

### Likelihood Explanation
The endpoint requires no authentication, no signed transaction, and no special privilege — any anonymous HTTP or gRPC client can call it repeatedly and cheaply (the cost is entirely on the server side; the caller only needs to send small pagination requests). The growth of the underlying dataset (asset issues) is attacker-influenceable over time (each funded account can issue exactly one asset, and issuance is permanent), making the resource cost of this endpoint increase irreversibly as the chain ages or as an attacker seeds many low-cost asset issues in advance.

### Recommendation
Refactor `AssetIssueStore.getAssetIssuesPaginated` to avoid loading the full asset-issue collection for every request. Options: maintain a persistent secondary sorted index (by name/order) that supports range/skip queries directly against the store's iterator, or cache the full sorted list and refresh only on writes, or use `LevelDbDataSourceImpl.getValuesNext`/`RocksDbDataSourceImpl.getNext`-style bounded iteration (as already used for Market/account-trace queries) so the amount of data read from disk and held in memory is bounded by `offset + limit`, not the entire table. Additionally, enforce a maximum `offset` value to prevent unbounded scans even under an indexed approach.

### Proof of Concept
1. Populate the chain (or wait for organic growth) so `AssetIssueStore` contains N asset issues.
2. As an unauthenticated client, repeatedly send:
   `POST http://<node>/wallet/getpaginatedassetissuelist {"offset":0,"limit":1}`
   or the gRPC equivalent `GetPaginatedAssetIssueList(PaginatedMessage{offset=0, limit=1})`.
3. Each request causes the node to execute `AssetIssueStore.getAllAssetIssues()` (full iterator scan + deserialization of all N capsules), sort the full N-element list, then return a 1-element response — i.e., O(N) work and O(N) memory allocation per request regardless of the tiny requested `limit`.
4. Repeating this request concurrently at scale increases CPU/memory pressure on the node proportional to N × request-rate, while the attacker's own bandwidth/cost stays minimal (small request/response size), demonstrating the amplification/DoS vector.

  private List<AssetIssueCapsule> getAssetIssuesPaginated(List<AssetIssueCapsule> assetIssueList,
      long offset, long limit) {
    if (limit < 0 || offset < 0) {
      return null;
    }

    if (assetIssueList.size() <= offset) {
      return null;
    }
    assetIssueList.sort((o1, o2) -> {
      if (o1.getName() != o2.getName()) {
        return o1.getName().toStringUtf8().compareTo(o2.getName().toStringUtf8());
      }
      return Long.compare(o1.getOrder(), o2.getOrder());
    });
    limit = limit > ASSET_ISSUE_COUNT_LIMIT_MAX ? ASSET_ISSUE_COUNT_LIMIT_MAX : limit;
    long end = offset + limit;
    end = end > assetIssueList.size() ? assetIssueList.size() : end;
    return assetIssueList.subList((int) offset, (int) end);
  }

  public List<AssetIssueCapsule> getAssetIssuesPaginated(long offset, long limit) {
    return getAssetIssuesPaginated(getAllAssetIssues(), offset, limit);
  }
