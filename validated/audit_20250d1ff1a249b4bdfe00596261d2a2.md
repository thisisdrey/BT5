## Analysis

Reducing the Sherlock report to its core broken invariant: a **fixed tolerance/gap check compares live external state against a last-accepted checkpoint, and rejects updates once the gap exceeds the tolerance — without any recovery path back into tolerance** — causing extended (or permanent) unavailability of the dependent service (deposits/withdrawals). In the Snowbridge Ethereum light client, the same broken-invariant pattern appears in `verify_update`'s finalized-header gap check. [1](#0-0) 

### Title
Ethereum beacon light client permanently halts bridge processing once the finalized-header gap exceeds `SLOTS_PER_HISTORICAL_ROOT` - (File: `bridges/snowbridge/pallets/ethereum-client/src/lib.rs`)

### Summary
`Pallet::verify_update` enforces that the gap between the currently stored finalized slot and the incoming update's finalized slot must not exceed `SLOTS_PER_HISTORICAL_ROOT` (8192 slots, ~27 hours), otherwise it returns `Error::InvalidFinalizedHeaderGap`. [1](#0-0) 
Any permissionless caller can invoke `submit` via `ensure_signed(origin)` to attempt to advance the finalized state. [2](#0-1) 
Once the on-chain `LatestFinalizedBlockRoot` slot falls behind the real Ethereum finalized slot by more than 8192 slots, **every subsequent `submit` call will always fail** this check, because the stored state can never advance without first passing the very check that is now permanently failing — the gap only grows over time as Ethereum continues finalizing new blocks while the pallet is stuck.

### Finding Description
`verify_update` requires:
```
latest_finalized_state.slot.saturating_add(SLOTS_PER_HISTORICAL_ROOT) >= update.finalized_header.slot
``` [1](#0-0) 

This bound exists because ancestry/execution-header proofs rely on the `block_roots` array in the beacon state, which only covers `SLOTS_PER_HISTORICAL_ROOT` (8192) slots of history — a legitimate cryptographic constraint, not an admin-tunable parameter (unlike Olympus's `THRESHOLD`, this value is a hard-coded protocol constant, so the "tight range" style fix does not directly apply; instead the invariant itself has no forward-recovery path other than governance).

The failure mode mirrors the Sherlock report's core defect: a bound-check against a moving reference value, where **no relayer, admin, or attacker action is required** for the bound to be permanently exceeded — any real-world period of Ethereum non-finality (e.g., an inactivity leak, prolonged missed finality due to validator issues, or simply nobody submitting an update for >27 hours) pushes `update.finalized_header.slot` far enough ahead of `latest_finalized_state.slot` that the check fails forever. Unlike a normal "temporary revert and retry" DoS, this one is **irrecoverable through the permissionless path**: because `LatestFinalizedBlockRoot` can only advance via `submit`, and `submit` requires the very condition that has now become permanently false, there is no sequence of `submit` calls that can ever re-close the gap. The only recovery is the privileged `force_checkpoint` (root-only) call, which re-bootstraps the light client from a fresh checkpoint. [3](#0-2) 

This is the same class as the Sherlock issue: a boundary/tolerance guard that stops accepting valid external state once a drift threshold is crossed, with the drift able to arise from ordinary real-world timing/liveness conditions rather than any malicious input, blocking dependent chain operations (message/asset processing that depends on the beacon client's finalized execution headers) until privileged intervention occurs.

### Impact Explanation
Once the gap check trips, all Ethereum→Polkadot bridge message and execution-header verification relying on this pallet is stalled indefinitely (`ExecutionHeaderTooFarBehind`/inability to produce valid ancestry proofs), since no permissionless `submit` can ever succeed again. This matches "public underpriced work that degrades block production or stalls bridge processing" and "permanent... bridge-state lock" from the impact gate — the pallet's designed self-healing path (permissionless `submit`) is completely closed off, and restoring service requires an out-of-band root/governance `force_checkpoint` call, i.e., unattended operation of the bridge halts.

### Likelihood Explanation
Ethereum's beacon chain has historically experienced multi-epoch non-finality events (e.g., due to client bugs, large-scale validator downtime, or supermajority participation issues) that can exceed 27 hours in adversarial or degraded network conditions. Additionally, if relaying is simply neglected (no relayer actively submits `submit` transactions) for more than ~27 hours, the same permanent lock occurs — this requires no malicious behavior at all, only ordinary relayer downtime, making the likelihood non-trivial for a bridge that depends on continuous permissionless relaying.

### Recommendation
Add a governance-independent recovery path in the gap-exceeded case, e.g., allow `submit` to accept an out-of-band "skip ahead" update (verified purely by sync-committee-signed light client update without requiring an ancestry-consistent gap), or lower operational risk by exposing an early-warning/soft-halt mechanism well before the 8192-slot hard boundary is reached, and ensure monitoring/alerting triggers relayer submissions long before the window closes. At minimum, document and automate that `force_checkpoint` must be triggerable without full governance latency (e.g., via a fast-track technical committee) to bound the downtime.

### Proof of Concept
1. Bootstrap the light client via `force_checkpoint` at slot `S0`.
2. Do not submit any `submit` update for more than `SLOTS_PER_HISTORICAL_ROOT` (8192) slots (~27 hours) — this can happen simply because no relayer submits during that window, or because Ethereum experiences an extended non-finality period.
3. `LatestFinalizedBlockRoot` remains at slot `S0` while the real Ethereum chain's finalized slot is now `S0 + 8193` or more.
4. Any subsequent `submit(update)` call with `update.finalized_header.slot > S0 + 8192` fails `verify_update`'s gap check with `Error::InvalidFinalizedHeaderGap`. [4](#0-3) 
5. Because the stored finalized slot cannot be advanced without passing this same check, no further permissionless `submit` will ever succeed — the pallet is stuck until root calls `force_checkpoint` again with a fresh checkpoint.

/// Check that a gap of more than 8192 slots between finalized headers is not allowed.
#[test]
fn submit_finalized_header_update_with_too_large_gap() {
	let checkpoint = Box::new(load_checkpoint_update_fixture());
	let update = Box::new(load_sync_committee_update_fixture());
	let mut next_update = Box::new(load_next_sync_committee_update_fixture());

	// Adds 8193 slots, so that the next update is still in the next sync committee, but the
	// gap between the finalized headers is more than 8192 slots.
	let slot_with_large_gap = checkpoint.header.slot + SLOTS_PER_HISTORICAL_ROOT as u64 + 1;

	next_update.finalized_header.slot = slot_with_large_gap;
	// Adding some slots to the attested header and signature slot since they need to be ahead
	// of the finalized header.
	next_update.attested_header.slot = slot_with_large_gap + 33;
	next_update.signature_slot = slot_with_large_gap + 43;

	new_tester().execute_with(|| {
		assert_ok!(EthereumBeaconClient::process_checkpoint_update(&checkpoint));
		let result = EthereumBeaconClient::submit(RuntimeOrigin::signed(1), update.clone());
		assert_ok!(result);
		assert_eq!(result.unwrap().pays_fee, Pays::No);
		assert!(<NextSyncCommittee<Test>>::exists());

		let second_result =
			EthereumBeaconClient::submit(RuntimeOrigin::signed(1), next_update.clone());
		assert_err!(second_result, Error::<Test>::InvalidFinalizedHeaderGap);
		assert_eq!(second_result.unwrap_err().post_info.pays_fee, Pays::Yes);
	});
}
