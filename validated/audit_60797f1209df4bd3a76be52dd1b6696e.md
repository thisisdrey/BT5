### Title
Hardcoded mainnet address prefix in TIP-2935 `HistoryBlockHashUtil` breaks/bricks history-storage precompile deployment on non-mainnet networks - (File: framework/src/main/java/org/tron/core/db/HistoryBlockHashUtil.java)

### Summary
`HistoryBlockHashUtil.HISTORY_STORAGE_ADDRESS` and `HISTORY_DEPLOYER_ADDRESS` are hardcoded byte constants that begin with `0x41`, the TRON **mainnet** address prefix, rather than being derived from the network's actual configured address prefix (`DecodeUtil.addressPreFixByte`, which is `0xa0` on Shasta/Nile-style testnets and configurable for private chains). [1](#0-0) [2](#0-1) 

### Finding Description
`HISTORY_STORAGE_ADDRESS` is defined as a raw hex literal `410000f90827f1c53a10cb7a02335b175320002935`, and `HISTORY_DEPLOYER_ADDRESS` as `413462413af4609098e1e27a490f554f260213d685` — both use the `0x41` byte in the address-prefix position, which is only valid for `Constant.ADD_PRE_FIX_BYTE_MAINNET`. The code comment even documents the intent to match Ethereum's address byte-for-byte "on both sides," ignoring that TRON's own address validity check (`DecodeUtil.addressValid`) rejects any address whose first byte differs from the network's configured `addressPreFixByte`. [3](#0-2) 

This function is invoked from `ProposalService.process()` when the `ALLOW_TVM_PRAGUE` committee proposal is activated, which calls `HistoryBlockHashUtil.deploy(manager)` unconditionally, writing the hardcoded, mainnet-prefixed address into `CodeStore`, `ContractStore`, and `AccountStore` directly (bypassing the normal address-prefix validation path used for user-facing transactions). [4](#0-3) [5](#0-4) 

On any TRON network other than mainnet (e.g. Nile, Shasta, or a private chain configured with a different `addressPreFixByte`), the deployed BlockHashHistory contract permanently lives at an address that is invalid/unreachable under that network's own addressing scheme (or collides with an address space users on that network can never construct via normal means since `DecodeUtil.addressValid` would reject a `0x41`-prefixed address). Because `write()`/block-application logic writes the parent hash into `Storage` keyed at this fixed address every block once installed, and `deploy()` is designed to run at most once (gated by `saveBlockHashHistoryInstalled`), there is no mechanism to correct the address for non-mainnet deployments — the feature silently never resolves to a reachable address for those chains' EVM-style `STATICCALL`/`BLOCKHASH`-emulation semantics, exactly analogous to the reported WETH bug where a single hardcoded address broke functionality on every chain except the one it was written for.

### Impact Explanation
This is a chain-config-independent constant embedded in consensus-critical, per-block state-mutation logic (`Manager`/`ProposalService`/block application). Once the `ALLOW_TVM_PRAGUE` proposal passes on a non-mainnet TRON network, `HistoryBlockHashUtil.deploy` installs a contract at an address inconsistent with that network's address space, and the per-block parent-hash write proceeds regardless. This is a protocol-level correctness bug: the TIP-2935 historical-block-hash feature becomes permanently non-functional/misconfigured on that network with no way to redeploy at a corrected address (the deploy path explicitly skips if it detects an installed marker), degrading a consensus-activated feature for every node on that network and affecting any deployed contract or JSON-RPC client relying on `BLOCKHASH`/history-storage semantics there.

### Likelihood Explanation
Deterministic and guaranteed to trigger: any committee/SR quorum activating `ALLOW_TVM_PRAGUE` on a network configured with a non-mainnet address prefix (which is the default committee governance action, not attacker-dependent) will unconditionally execute the flawed hardcoded-address deployment path in `ProposalService.process`. [6](#0-5) 

### Recommendation
Derive `HISTORY_STORAGE_ADDRESS` (and `HISTORY_DEPLOYER_ADDRESS`) from the runtime-configured `DecodeUtil.addressPreFixByte` instead of a hardcoded `0x41` literal, so the same 20-byte suffix is combined with whatever prefix byte is valid for the network the node is actually running on, and route address construction through the existing `DecodeUtil`/`Wallet` address-prefix utilities rather than a raw hex constant.

### Proof of Concept
1. Configure/run a java-tron node with `addressPreFixByte = 0xa0` (a private/test network configuration, per `Args`/`DecodeUtil`).
2. Have the SR/committee quorum pass the `ALLOW_TVM_PRAGUE` proposal, triggering `ProposalService.process` → `HistoryBlockHashUtil.deploy(manager)`. [4](#0-3) 
3. Observe that the contract/account/code are written at `HISTORY_STORAGE_ADDRESS = 0x410000f90827f1c53a10cb7a02335b175320002935`, a `0x41`-prefixed address that `DecodeUtil.addressValid` would reject as invalid for this network (`address[0] != addressPreFixByte`). [7](#0-6) 
4. Any subsequent attempt by users/tools on that network to interact with the intended history-storage contract via a properly-prefixed address fails, and the feature is permanently stuck at an address inconsistent with the network's address space, since `deploy()` only runs once and is gated by `saveBlockHashHistoryInstalled`. [8](#0-7)

  public static boolean addressValid(byte[] address) {
    if (ArrayUtils.isEmpty(address)) {
      logger.warn("Warning: Address is empty !!");
      return false;
    }
    if (address.length != ADDRESS_SIZE / 2) {
      logger.warn(
          "Warning: Address length need " + ADDRESS_SIZE + " but " + address.length
              + " !!");
      return false;
    }

    if (address[0] != addressPreFixByte) {
      logger.warn("Warning: Address need prefix with " + addressPreFixByte + " but "
          + address[0] + " !!");
      return false;
    }
    return true;
  }
