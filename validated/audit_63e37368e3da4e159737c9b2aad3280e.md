Confirmed vulnerability: `StacksChainState::get_confirmed_microblock_index_hash` (and the downstream `load_staging_microblock_info_indexed` / `load_staging_microblock_indexed`) never filter on `processed` or `orphaned` for the anchored block, and only filter `orphaned = 0` (not `processed = 1`) for the microblocks themselves.

### Title
`GET /v2/microblocks/confirmed/<block_id>` serves unprocessed/non-canonical staging data as if it were confirmed - (File: stackslib/src/net/api/getmicroblocks_confirmed.rs)

### Summary
`StacksIndexedMicroblockStream::new_confirmed` resolves the tail-microblock index hash via `StacksChainState::get_confirmed_microblock_index_hash`, which only checks that a `staging_blocks` row exists for `child_block_id` — it does not check the `processed` flag on that block, nor does the subsequent microblock loader require `processed = 1`. This allows any child block/microblocks that have merely landed in `staging_blocks`/`staging_microblocks` (via an unvalidated P2P push) but have not completed `process_next_staging_block` to be served with a 200 and real byte content, distinguishing them from truly unknown blocks (404).

### Finding Description
`get_confirmed_microblock_index_hash` [1](#0-0)  looks up the parent's consensus hash and the child's `staging_blocks` row via `load_staging_block_info`, and returns `Some(index_hash)` derived from `child_block_info.parent_microblock_hash` — with no check of `child_block_info.processed`. That index hash then feeds `StacksIndexedMicroblockStream::new`, which calls `load_staging_microblock_info_indexed` [2](#0-1) ; this query filters only `orphaned = 0`, not `processed = 1`. `generate_next_chunk` then walks the chain via `load_staging_microblock_indexed` [3](#0-2) , which similarly does not require `processed = 1` (see `load_staging_microblock_info`, `orphaned = 0` only) [4](#0-3) . The handler itself only distinguishes `ChainError::NoSuchBlockError` (404) from success (200 + bytes) [5](#0-4) , so any staging-only insertion crosses the 404→200 boundary and its raw bytes are served.

However, tracing the reachable path for this specific claim: reaching this state requires the attacker's block/microblocks to actually be written into `staging_blocks`/`staging_microblocks`. That path (P2P `BlocksData`/`MicroblocksData` handling → block/microblock preprocessing, e.g. `preprocess_anchored_block`/`preprocess_streamed_microblock`) performs structural, signature, and linkage checks before insertion (e.g., block header signature over the recovered miner key, sequence/hash-chain checks, and the anchor relationship to a previously-accepted/staged parent) — it is not a raw unauthenticated write. The question's premise is that a message can "land the block+microblocks into staging without full validation completing" — this is true in the sense that full state-transition/Clarity validation (which happens in `append_block`/`process_next_staging_block`) is deferred until later, but the pre-storage checks (signature, hash-chain linkage, size limits) still gate what can enter `staging_blocks` at all. So an attacker cannot inject arbitrary unvalidated bytes; they can only get a block that passes preprocessing to sit in staging pre-processing, and then have its non-canonical/not-yet-validated microblocks served by this endpoint before the state-transition validation completes.

### Impact Explanation
This does let a remote, unprivileged peer distinguish 404 vs 200 for blocks/microblocks that have only passed structural preprocessing but not full state-transition validation (`processed = 1`) — i.e., data that is not yet, and may never become, canonical (e.g., if `process_next_staging_block` later rejects/orphans it). This matches the "state served that no canonical block committed" category: a client believing 200 = canonical/confirmed data may treat not-yet-validated (and potentially to-be-rejected) microblock bytes as confirmed chain state. It does not grant write access, does not crash the node, and does not forge new data (bytes served are exactly what a legitimate peer submitted and had structurally accepted) — the class is best characterized as High rather than Critical.

### Likelihood Explanation
Requires the attacker to first get a block that passes structural preprocessing (signature, correct anchoring to a previously-accepted parent, valid microblock hash-chain) into `staging_blocks`, then query the RPC endpoint before `process_next_staging_block` runs and either confirms or orphans it. This is a race/timing-window condition, repeatable per submitted block, but bounded by how much attacker-controlled data can pass structural preprocessing while still failing full validation (e.g., invalid state transitions caught only during Clarity execution). No privileged role or secret needed; RPC port is remotely reachable by design.

### Recommendation
In `get_confirmed_microblock_index_hash`, check `child_block_info.processed && !child_block_info.orphaned` before returning `Some(index_hash)` (matching the check already used in `has_processed_microblocks`). Additionally require `processed = 1` in `load_staging_microblock_info_indexed`/`load_staging_microblock_info` when used from this RPC-serving path, or route the RPC through `has_processed_microblocks_indexed` before constructing the stream, so only fully-processed/canonical confirmed streams are ever served with 200.

### Proof of Concept
Rust test in `stackslib/src/net/api/tests/getmicroblocks_confirmed.rs`: use `store_staging_block`/`store_staging_microblock` helpers to insert a child block and its parent microblocks into staging (mirroring the existing `test_stream_confirmed_microblocks` setup at [6](#0-5) ) but **skip** `set_block_processed`/`set_microblocks_processed` for the child block. Then call `RPCMicroblocksConfirmedRequestHandler::try_handle_request` (or directly `StacksIndexedMicroblockStream::new_confirmed`) with the child's index-block-hash and assert it returns `Ok(stream)` with non-empty bytes matching the injected (unprocessed) microblocks, instead of `Err(ChainError::NoSuchBlockError)`/404 — demonstrating the guard gap at `get_confirmed_microblock_index_hash`.
