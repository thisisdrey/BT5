This confirms the mechanism. `mt_resolve_transfer` refunds based on the receiver's *current* `token_balances`, capped at `receiver_balance` and the transferred `amount`, and it only clamps the receiver's balance being reduced back — this cannot exceed what was actually credited to the receiver by `Transfer::execute_intent`, so the equality being tested does not break.

### Analysis

The claimed binding is:

`debit(signer, T) by Transfer::execute_intent == credit(EVIL) + refund(mt_resolve_transfer)`

Tracing this:

1. `Transfer::execute_intent` runs `internal_sub_balance(sender_id, tokens)` then `internal_add_balance(receiver_id, tokens)` **synchronously**, fully completing before any promise is scheduled. [1](#0-0) 
2. Only after both balance changes are committed does `notify_on_transfer` get called, which builds a `Promise` (optionally with `state_init`) and schedules `mt_on_transfer` on `receiver_id`, followed by `mt_resolve_transfer` — all as separate, asynchronous NEAR receipts. [2](#0-1) [3](#0-2) 
3. NEAR's execution model does not allow synchronous reentrancy: promises/callbacks execute in later receipts only after the current receipt (including all its state writes) has fully committed. There is no "pre-debit" balance state left observable to a called contract — by the time EVIL's `mt_on_transfer` executes, `internal_sub_balance`/`internal_add_balance` have already been durably applied to contract storage. Any call EVIL makes back into `ft_withdraw` (as a new transaction/receipt) operates on the fully-updated, correctly-debited balance, not a stale pre-debit snapshot.
4. `mt_resolve_transfer` only ever refunds an amount bounded by `min(refund_requested, amount_transferred, receiver_balance)` [4](#0-3) , which subtracts from the receiver's (EVIL's) actual balance and credits it back to the original sender — this cannot create or duplicate value beyond what was already moved by `Transfer::execute_intent`.

There is no window where `ft_withdraw` (or any other balance-mutating call) can observe a "pre-debit" state concurrently with the in-flight `notify_on_transfer` promise, because NEAR contract calls are not reentrant in the way the question assumes (no shared call stack / no synchronous callback into the same contract's state). The `contracts/defuse/src/contract/state/v0.rs` scope cited in the question contains only legacy migration struct definitions and has no relation to this flow. [5](#0-4)
