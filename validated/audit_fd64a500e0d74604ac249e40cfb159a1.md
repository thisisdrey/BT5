### Title
Firewall-equivalent `remote_allow_list` enforcement trusts spoofable UDP source address as an unauthenticated "price oracle" - ([File: handshake_manager.go])

### Summary
The external report describes a Uniswap price oracle that is trusted for a security-critical decision (how much `paymentToken` to charge) even though the oracle value (`getAmountsIn()`) can be trivially manipulated by an attacker with no prior trust relationship (no allowance, no signed voucher — just a flashloan). The `lighthouse.remote_allow_list` firewall check in Nebula plays an analogous "oracle" role for handshake admission: it is the only gate an unauthenticated attacker (one holding no CA-signed certificate at all) must pass before the daemon begins spending CPU/memory processing a handshake, and the value it trusts — the UDP packet's source address — is exactly as easy to manipulate as a spot price in a thin liquidity pool, because UDP carries no cryptographic binding between packet and sender.

### Finding Description
`HandshakeManager.HandleIncoming` performs the `remote_allow_list` check *before* any certificate exists or is verified: [1](#0-0) 

The decision is based solely on `via.UdpAddr.Addr()`, which is populated directly from the UDP packet's source address as delivered by the socket layer — a value that has no cryptographic authentication at this stage (the Noise handshake and certificate verification only happen afterward, inside `beginHandshake` → `handshake.Machine.ProcessPacket` → the `CertVerifier` backed by `CAPool.VerifyCertificate`): [2](#0-1) [3](#0-2) 

`AllowUnknownVpnAddr` / `Allow` simply do a CIDR lookup against the supplied address with no additional proof of possession: [4](#0-3) 

Just as the Uniswap report's attacker needs no special privilege to move `getAmountsIn()`'s output — only a flashloan of `referenceToken` — an attacker here needs no CA-signed certificate and no ability to receive return traffic to influence the value the `remote_allow_list` "oracle" consumes: a spoofed UDP source address requires only the ability to send a raw/spoofed packet (feasible on networks without egress/ingress source filtering, e.g. many cloud/subnet configurations, tunnels, or when a defender's own `remote_allow_list` is precisely intended to enforce that traffic only originates from a trusted underlay range). By spoofing an allowed source range, the attacker manipulates the trusted signal to pass the enforcement point and force the daemon into `beginHandshake`, which allocates a `handshake.Machine`, runs `generateIndex`, and performs Noise crypto operations, even though the eventual certificate check will fail for a real attacker payload — but the enforcement point that was supposed to block this class of traffic from disallowed underlay ranges is bypassed by the manipulated (spoofed) address.

### Impact Explanation
This mirrors the "cheap manipulated input directs an expensive/high-trust decision" pattern in the source report: the `remote_allow_list` is nebula's documented mechanism ("filters which addresses we accept from lighthouses" / restricts which underlay subnets may initiate handshakes) and is treated in tests as a security boundary (`TestHandshakeRemoteAllowList`, `firewall.go` comments describing "evaluation order" for enforcement). An attacker who can spoof a source IP within the allowed range defeats this boundary and can trigger unauthenticated per-packet handshake-state allocation (Machine creation, index generation, Noise processing) from any address, undermining the very isolation the operator configured `remote_allow_list` to provide, and doing so cheaply and repeatedly (resource exhaustion / remote state poisoning of the pending-handshake table) — the direct networking analog of "spend a very small amount to get an outsized effect" from the oracle report.

### Likelihood Explanation
High for networks that don't perform strict source-address (BCP38-style) filtering, since spoofing a UDP source address requires no cryptographic material and no CA-signed certificate — exactly the attacker capability class this bug report is scoped to. The check is reached on literally the first packet of any incoming handshake, before any authentication.

### Recommendation
Do not treat the raw UDP source address as a trusted enforcement signal for admission control. At minimum:
- Treat `remote_allow_list` pre-cert checks as a coarse, non-authoritative hint only, and re-validate the final `via.UdpAddr` against `remote_allow_list` again *after* certificate verification succeeds (which the code already does in `validatePeerCert`/`continueHandshake`), while ensuring the pre-auth check cannot be relied upon as the sole gate for resource-allocating work.
- Rate-limit/resource-bound pending handshake creation independent of source-IP allow-listing, so a spoofed-source flood cannot force unauthenticated `Machine` allocation regardless of `remote_allow_list` configuration.
- Document explicitly that `lighthouse.remote_allow_list` is not a substitute for network-level anti-spoofing controls (BCP38/ingress filtering), since it consumes an attacker-controllable, unauthenticated value.

### Proof of Concept
1. From a network segment without egress source-address filtering, craft a UDP packet with `MessageCounter=1`, `RemoteIndex=0`, header subtype `HandshakeIXPSK0`, and an arbitrary Noise stage-1 payload.
2. Spoof the source address to one that falls inside the target's configured `lighthouse.remote_allow_list` allow range (as validated in `TestHandshakeRemoteAllowList`, `e2e/handshake_manager_test.go:351-408`, which shows the check operates purely on the packet's `From` address).
3. Send the packet to the target's nebula UDP port from the disallowed real origin, with the spoofed allowed source.
4. Observe (per `handshake_manager.go:164-170` and `beginHandshake`) that the packet passes the `remote_allow_list` gate and the daemon allocates a `handshake.Machine`, generates an index, and performs Noise `ReadMessage` processing — work that `remote_allow_list` was configured to prevent from untrusted underlay sources — even though the packet did not originate from an address the operator intended to trust.

func (hm *HandshakeManager) HandleIncoming(via ViaSender, packet []byte, h *header.H) {
	// Gate on known handshake subtypes. Unknown subtypes (or future ones we
	// don't yet support) are dropped here rather than silently routed through
	// the IX path. Add a case when introducing a new pattern.
	switch h.Subtype {
	case header.HandshakeIXPSK0:
		// supported
	default:
		hm.l.Debug("dropping handshake with unsupported subtype",
			"from", via, "subtype", h.Subtype)
		return
	}

	// First remote allow list check before we know the vpnIp
	if !via.IsRelayed {
		if !hm.lightHouse.GetRemoteAllowList().AllowUnknownVpnAddr(via.UdpAddr.Addr()) {
			hm.l.Debug("lighthouse.remote_allow_list denied incoming handshake", "from", via)
			return
		}
	}

// the first message.
func (hm *HandshakeManager) beginHandshake(via ViaSender, packet []byte, h *header.H) {
	f := hm.f
	cs := f.pki.getCertState()

	v := cs.DefaultVersion()
	if cs.GetCredential(v) == nil {
		f.l.Error("Unable to handshake with host because no certificate is available",
			"from", via, "certVersion", v)
		return
	}

	machine, err := handshake.NewMachine(
		v, cs.GetCredential,
		hm.certVerifier(), func() (uint32, error) { return generateIndex(f.l) },
		false, header.HandshakeIXPSK0,
	)
	if err != nil {
		f.l.Error("Failed to create handshake machine", "from", via, "error", err)
		return
	}

	response, result, err := machine.ProcessPacket(nil, packet)
	if err != nil {
		f.l.Error("Failed to process handshake packet", "from", via, "error", err)
		return
	}

func (hm *HandshakeManager) certVerifier() handshake.CertVerifier {
	return func(c cert.Certificate) (*cert.CachedCertificate, error) {
		return hm.f.pki.GetCAPool().VerifyCertificate(time.Now(), c)
	}
}

func (al *RemoteAllowList) AllowUnknownVpnAddr(vpnAddr netip.Addr) bool {
	if al == nil {

	}

func (al *RemoteAllowList) Allow(vpnAddr netip.Addr, udpAddr netip.Addr) bool {
	if !al.getInsideAllowList(vpnAddr).Allow(udpAddr) {
		return false
	}
	return al.AllowList.Allow(udpAddr)
