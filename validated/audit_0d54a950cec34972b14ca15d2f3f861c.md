## Title
Unauthenticated `RemoteIndex` collision allows silent remote-state poisoning / hostinfo shadowing - (`File: handshake_manager.go`)

### Summary
The external report describes how `Router.sol` trusts an unauthenticated, weakly-collision-resistant identifier (a truncated `create2` address) as a stand-in for "this message came from a legitimate pool," instead of verifying it against an authoritative source (the factory). The analogous bug class in nebula is trusting an unauthenticated, attacker-supplied 32-bit `RemoteIndex` value — sent in cleartext in every handshake/message header — as a lookup key for locating and overwriting `HostInfo` state, without any cryptographic binding or collision rejection.

### Finding Description
Every wire packet carries a plaintext `RemoteIndex` field [1](#0-0)  that the receiver uses via `f.hostMap.QueryIndex(h.RemoteIndex)` / `QueryRelayIndex` to find the local `HostInfo` before any authentication happens. This index is *not* derived from anything cryptographically bound to the peer's certificate or key — it is simply the peer's own `localIndexId`, generated by `generateIndex()` as 4 random bytes [2](#0-1)  and echoed back by the other side into the `remoteIndexId` field of the receiving side's `HostInfo` [3](#0-2) .

Critically, while `localIndexId` collisions *are* checked and rejected (`ErrLocalIndexCollision`) [4](#0-3) , collisions on `remoteIndexId` are explicitly tolerated and only logged, both in `CheckAndComplete` and in `Complete`: [5](#0-4) [6](#0-5) 

Because an attacker who runs their own initiator can freely choose (or simply happen to send) an arbitrary 32-bit value as their own `localIndexId`/handshake `RemoteIndex` field, they can intentionally target a value already in use as another host's `remoteIndexId` in `HostMap.RemoteIndexes` [7](#0-6) . When `unlockedAddHostInfo` (called from `Complete`/`CheckAndComplete`) inserts the new `HostInfo`, it overwrites `hm.RemoteIndexes[hostinfo.remoteIndexId]` with the new (attacker's) `HostInfo`, silently displacing the legitimate mapping — the code path only emits an informational log ("New host shadows existing host remoteIndex") rather than rejecting the handshake.

This mirrors the Kyber Router.sol bug class precisely: an identifier that *looks* like it authenticates "this is host X's tunnel" is actually just an attacker-chosen value with no cryptographic tie to identity, and the code that consumes it (`QueryIndex`/`RemoteIndexes` lookups in the hot packet-receive path, `outside.go:89-103`) does not independently verify authenticity of the mapping before routing/dispatching packets to it.

### Impact Explanation
Once `hm.mainHostMap.RemoteIndexes[idx]` is overwritten, any subsequent packet on the wire carrying that `RemoteIndex` will be routed to the attacker's `HostInfo` via `QueryIndex` in `outside.go`, rather than the legitimate host's. This is remote state poisoning of the hostmap's reverse-index table. While the AEAD `Decrypt` step will subsequently fail for a mismatched key (so full traffic decryption/forgery is not immediately achieved), the attack still corrupts routing state maintained by `HandshakeManager`/`HostMap`, and (depending on how `RemoteIndexes` is consulted elsewhere, e.g. `maybeSendRecvError`, roaming, or relay handling) it can cause legitimate traffic to be misdirected or silently dropped for the victim tunnel — a remote DoS / state-corruption impact reachable pre-authentication by an unprivileged peer with no CA-signed certificate needed to send handshake stage-1/2 packets that populate this index.

### Likelihood Explanation
Unlike the Kyber report, no brute-force hashing is required at all — the attacker fully and directly controls the value placed in the wire's index field; the only "cost" is guessing or observing a 32-bit index currently in use by a victim tunnel (index space is 2^32, but the check that would have rejected it — analogous to `msg.sender == pool` — degenerates to a log-only no-op instead of an authoritative rejection). This makes the likelihood driven purely by knowledge/guessability of live indexes, which is materially easier than the truncated-hash collision scenario in the original report.

### Recommendation
Treat a `remoteIndexId` collision with an existing, different, still-valid `HostInfo` the same way `localIndexId` collisions are treated: reject/refuse to overwrite the existing `RemoteIndexes` entry (or require re-validation/expiry of the prior entry) instead of only logging it in `CheckAndComplete` (`handshake_manager.go:466-473`) and `Complete` (`handshake_manager.go:488-495`).

### Proof of Concept
Not independently verified end-to-end in this pass (would require driving a live handshake to exercise `Complete`/`CheckAndComplete` with a crafted `RemoteIndex` colliding with an existing entry and confirming resulting misrouting in `outside.go`). Based on static code reading, the exploit sketch is:
1. Establish or observe an existing legitimate tunnel so its `HostInfo.remoteIndexId` is known/predictable (or brute-force a live tunnel's index, feasible given the full 32-bit space is attacker-writable with no rejection).
2. As an unauthenticated initiator, send a stage-1 handshake and continue the handshake such that the resulting `HostInfo.remoteIndexId` (chosen entirely client-side by the attacker's own `generateIndex`-equivalent, which they can bypass) equals the victim's remote index.
3. `Complete`/`CheckAndComplete` inserts the attacker's `HostInfo` into `hm.mainHostMap.RemoteIndexes[idx]`, overwriting the victim's entry, logging only "New host shadows existing host remoteIndex."
4. Subsequent inbound packets bearing that `RemoteIndex` are routed via `QueryIndex` in `outside.go` to the attacker's `HostInfo`, corrupting delivery for the victim tunnel.

func generateIndex(l *slog.Logger) (uint32, error) {
	b := make([]byte, 4)

	// Let zero mean we don't know the ID, so don't generate zero
	var index uint32
	for index == 0 {
		_, err := rand.Read(b)
		if err != nil {
			l.Error("Failed to generate index", "error", err)
			return 0, err
		}

		index = binary.BigEndian.Uint32(b)
	}

	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("Generated index", "index", index)
	}
	return index, nil
}
