### Title
NullPointerException on `unlockResource` in `UnDelegateResourceActuator.execute()` causes deterministic block-application crash / chain halt - ([File: actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java])

### Summary
`UnDelegateResourceActuator.validate()` accepts a transaction as valid when the "unlock" delegated-resource record (`createDbKeyV2(owner, receiver, false)`) does not exist, as long as the "lock" record (`createDbKeyV2(owner, receiver, true)`) exists and has expired with sufficient balance. `execute()`, however, unconditionally re-fetches the same "unlock" record and dereferences it without a null check, causing an unhandled `NullPointerException`.

### Finding Description
In `validate()`: [1](#0-0) 
`unlockResourceCapsule` and `lockResourceCapsule` are both fetched, and the code only requires that **at least one** of them is non-null (`if (unlockResourceCapsule == null && lockResourceCapsule == null) throw ...`). The subsequent balance-sufficiency check sums contributions from either record only `if (unlockResourceCapsule != null)` / `if (lockResourceCapsule != null && ...expired)`, so a transaction can pass validation purely on the strength of an expired `lockResourceCapsule`, with `unlockResourceCapsule == null`.

In `execute()`: [2](#0-1) 
The code re-fetches the same "unlock" key into `unlockResource` via `delegatedResourceStore.get(unlockKey)` (line 130-131) and then, in both the `BANDWIDTH` and `ENERGY` branches, calls `unlockResource.addFrozenBalanceForBandwidth(...)` / `unlockResource.addFrozenBalanceForEnergy(...)` (lines 137, 152) with **no null check**. If `unlockResource` is null — which `validate()` explicitly permits — this throws an uncaught `NullPointerException`.

This mirrors the CVE-2021-47541 bug class: one code path (`validate()`) tolerates/accepts a null/absent object, while a later code path (`execute()`) assumes the object is always present and dereferences it, without any recovery in between. In the kernel bug this was a use-after-free; here it is an unchecked null dereference of a persistent store record that legitimately does not exist on the "happy path" of a locked-then-expired delegation.

### Impact Explanation
`execute()` is invoked during block application by `Manager`/`ActuatorCreator` for every transaction in every block. An unhandled `NullPointerException` thrown from inside a `ChainBaseManager`-invoked actuator during block processing is not treated as a normal `ContractExeException` — it propagates as a runtime error. Because block processing is deterministic and every full/witness node executes the same transaction when applying the same block, this crash reproduces identically on all nodes that process the block, resulting in a chain-wide processing failure/halt rather than a single node's uncaught exception. At minimum, it crashes/aborts transaction processing for the node applying the block. This qualifies as "node crash or halt / chain split" impact.

### Likelihood Explanation
Reaching the vulnerable path requires only an ordinary, unprivileged sequence of two self-authored, unprivileged transactions:
1. `DelegateResourceContract` with `lock = true` from owner to receiver for `BANDWIDTH` or `ENERGY` — creating only the "lock" record (`createDbKeyV2(..., true)`), no "unlock" record.
2. After the lock period naturally expires, an `UnDelegateResourceContract` from the same owner/receiver/resource for a balance covered by the expired lock record.

No malicious SR/witness/committee/peer role, no privileged permission, and no race condition across blocks is needed — a single account controlling its own delegation lifecycle can trigger this deterministically. This is a straightforward, unprivileged, broadcastable-transaction reachable bug.

### Recommendation
In `UnDelegateResourceActuator.execute()`, null-check `unlockResource` before dereferencing it (mirroring the `Objects.nonNull` guard already used for `receiverCapsule`), e.g. only call `addFrozenBalanceForBandwidth`/`addFrozenBalanceForEnergy` on `unlockResource` if it is non-null, and skip directly to the `lockResource` deduction path if it's null (symmetric to how `validate()` treats it as optional). Alternatively, construct a fresh `DelegatedResourceCapsule` for the unlock key when absent, consistent with how the "lock" balance transfer into the unlock bucket is expected to work.

### Proof of Concept
1. Attacker account A delegates resource to account B via `DelegateResourceContract` with `lock=true` for `BANDWIDTH` (creates only `DelegatedResourceCapsule` at `createDbKeyV2(A, B, true)`; no record at `createDbKeyV2(A, B, false)`).
2. Wait until `dynamicStore.getLatestBlockHeaderTimestamp()` passes the lock's `expireTimeForBandwidth` (lock period naturally expiring).
3. Attacker broadcasts an `UnDelegateResourceContract(owner=A, receiver=B, resource=BANDWIDTH, balance <= locked amount)`.
4. `validate()` passes: `unlockResourceCapsule == null`, but `lockResourceCapsule` is non-null and expired, and `delegateBalance` from the lock record alone covers `unDelegateBalance`.
5. `execute()` runs `delegatedResourceStore.get(unlockKey)` → returns `null` (no record was ever created there) → `unlockResource.addFrozenBalanceForBandwidth(-unDelegateBalance, 0)` throws `NullPointerException`, uncaught, aborting transaction/block execution deterministically on every node applying this block.
