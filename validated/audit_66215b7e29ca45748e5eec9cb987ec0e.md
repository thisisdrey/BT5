I found a concrete analog: `RemoteIp` on the `PackObjectsHookWithSidechannelRequest` is used as the *sole gate* deciding whether a fetch/clone's `git-pack-objects` invocation goes through the per-client concurrency limiter or is executed unlimited. This mirrors the external report's pattern — an attacker-influenced input value determines whether a resource-accounting/gating check applies at all, letting the attacker escape the limiter that is supposed to make them "pay" (in gas/CPU) proportionally, while forcing the server to absorb unlimited, unaccounted cost.

### Title
Unauthenticated `remote_ip` field lets a client bypass the pack-objects concurrency limiter, causing unbounded resource consumption on `git-pack-objects` - (File: internal/gitaly/service/hook/pack_objects.go)

### Summary
`PackObjectsHookWithSidechannelRequest.RemoteIp` is documented as "the key for concurrency limiting before we trigger `git-pack-objects` command", but the value is round-tripped through client/relay-controlled data (payload propagated from the SSH/HTTP frontend into the Git hook environment, then into the gRPC request) rather than derived from the actual TCP peer address at the point of enforcement. The gating logic in `packObjectsHook` only applies `runPackObjectsLimited` (which enforces per-IP concurrency limits) when the parsed IP is present and non-loopback; any IP that fails to parse, or that is loopback, is dispatched via unlimited `runPackObjects`.

### Finding Description
In `internal/gitaly/service/hook/pack_objects.go`: [1](#0-0)

The proto comment confirms the intended security property of this field: [3](#0-2) 

Because the value is a plain string threaded through hook environment/payload plumbing rather than authenticated at the point of use, any component upstream that lets the field be spoofed, malformed, or set to a loopback address (`127.0.0.1`, `::1`) — or any client path where remote IP resolution legitimately fails and defaults empty/unparseable — causes `ipAddr == nil` or `ipAddr.IsLoopback() == true`, both of which route the request into the **unlimited** `runPackObjects` path instead of `runPackObjectsLimited`. This is structurally identical to the external bug class: an attacker-controllable value governs whether a costly, gated operation is subjected to accounting/limiting, and the "fallback"/edge case (loopback, unparseable) silently drops the gate entirely, letting the requester consume unbounded expensive resources (repeated `git-pack-objects` invocations, which are CPU/memory-intensive) without being charged against the concurrency budget meant to protect the node.

### Impact Explanation
`git-pack-objects` is one of the most expensive operations Gitaly performs on behalf of ordinary fetch/clone/partial-clone requests. The per-IP concurrency limiter (`runPackObjectsLimited`, backed by `limiter.NewConcurrencyLimiter`) exists specifically to bound how many concurrent expensive pack-objects computations a single remote can trigger, protecting the node from resource-exhaustion DoS. If the gating key can be forced into the "no limit" branch, a single ordinary user driving many concurrent fetch/clone requests can bypass this protection entirely, exhausting CPU/memory on the Gitaly node and degrading service for other tenants/repositories — a DoS of the `PackObjectsHookWithSidechannel` RPC handler, without needing any privileged access, matching the "RPC-handler resource limits" bypass category.

### Likelihood Explanation
The concurrency limiter is only exercised through `runPackObjectsLimited`, gated exclusively by whether `net.ParseIP`/`net.SplitHostPort` on `req.GetRemoteIp()` succeeds and produces a non-loopback address; the loopback exemption and the "IP failed to parse" fallback are both handled identically (unlimited execution), as shown by `TestPackObjects_concurrencyLimit`'s "empty IP addresses" case explicitly expecting `shouldLimit: false`. This demonstrates the fallback-to-unlimited behavior is a deliberate, reachable, and tested code path — the only open question (which the available index does not let me verify with certainty) is exactly how strongly the upstream frontend (SmartHTTP/SSH/Workhorse) authenticates or sanitizes the `RemoteIP` value before it reaches this hook payload; if any of those layers allow a client-influenced or default/empty value to reach here, exploitation requires no special privilege — an ordinary fetch/clone client is sufficient.

### Recommendation
Do not rely on a payload-forwarded string for a security-relevant concurrency-limiting key. Resolve and bind the remote IP once, at the point where the actual network connection is authenticated (e.g., at the gRPC/SmartHTTP/SSH ingress), and pass it through a tamper-evident channel (e.g., derived server-side per connection, not re-serialized through the Git hook environment). Additionally, treat "IP failed to parse" and "empty remote IP" as a *fail-closed* condition (apply the limiter with a conservative default key, e.g. `"unknown"`) rather than fail-open (skip the limiter), and reconsider whether loop-back should ever exempt a request that traversed a hook payload rather than an actual local socket.

### Proof of Concept
Not independently reproducible from the indexed code alone (would require driving `PostUploadPackWithSidechannel`/`SSHUploadPack` end-to-end and inspecting how `payload.UserDetails.RemoteIP` is populated). However, the exact bypass condition is directly demonstrated by the existing unit test `TestPackObjects_concurrencyLimit`'s `"empty IP addresses"` case: [4](#0-3) 

which sets `RemoteIp: ""` for two concurrent identical requests from the same `GlId`/repository and asserts `shouldLimit: false` — i.e., the concurrency limiter is confirmed bypassed whenever `RemoteIp` cannot be parsed, matching the `ipAddr == nil` branch in `packObjectsHook`.
