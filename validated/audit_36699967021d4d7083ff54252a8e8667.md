### Title
Dust-transfer griefing fills `depositTokensOfAccount` to `MAX_TOKENS_PER_USER`, bricking liquidations and freezing new-collateral deposits - ([File: contracts/Pool.sol])

### Summary
`Pool` tracks every deposit/debt token a user has ever touched in a `MappedEnumerableSet` capped at `MAX_TOKENS_PER_USER = 30`. `addToDepositTokensOfAccount` reverts with `ReachedMaxDepositTokens` once the list is full. Because `DepositToken` registers the *recipient* of any transfer (including 1-wei dust transfers) into that list, an unprivileged attacker can fill the list of an arbitrary address — most critically the protocol's `feeCollector` — so that every `Pool.liquidate` call that charges a protocol fee permanently reverts. This is the EVM analog of CVE-2016-9588: an exception path (list-full revert) that the caller "declines to handle," crashing a security-critical operation (liquidation) and producing a denial of service against the protocol's solvency mechanism.

### Finding Description
- `Pool` stores per-account token lists in `depositTokensOfAccount`/`debtTokensOfAccount` (`MappedEnumerableSet.AddressSet`), capped by `uint256 public constant MAX_TOKENS_PER_USER = 30` (`contracts/Pool.sol:79`), with `error ReachedMaxDepositTokens()` (`contracts/Pool.sol:50`).
- `DepositToken._afterTokenTransfer`-style hooks call `pool.addToDepositTokensOfAccount(to)` for any recipient whose balance becomes non-zero; `addToDepositTokensOfAccount` reverts once the recipient's list already contains 30 distinct tokens (`contracts/Pool.sol`, `addToDepositTokensOfAccount` near lines 618–635; `DepositToken.sol` invokes it on mint/transfer/seize).
- `Pool.liquidate` performs two `seize` calls at the end (`contracts/Pool.sol:589-593`):

```solidity
depositToken_.seize(account_, _msgSender, _toLiquidator);
if (_fee > 0) {
    depositToken_.seize(account_, _poolRegistry.feeCollector(), _fee);
}
```

Each `seize` internally registers the recipient via `addToDepositTokensOfAccount`. There is no try/catch or "skip registration" fallback — the revert propagates and the entire liquidation fails, exactly like the unhandled `#BP`/`#OF` injection crashing the L2 guest.

Attack path (unprivileged EOA):
1. Attacker deposits dust amounts of the underlying of every deposit token registered in the pool (or simply receives dust msdTokens) and transfers 1 wei of each distinct `DepositToken` to `feeCollector` until its `depositTokensOfAccount` list reaches 30.
2. From then on, every `liquidate` call where `_fee > 0` reverts inside the second `seize`, because `addToDepositTokensOfAccount(feeCollector)` throws `ReachedMaxDepositTokens`.
3. The same dust-fill applied to a victim blocks that victim from ever receiving (or depositing) a *new* collateral type — they cannot add collateral to rescue an unhealthy position even though their existing deposits remain withdrawable.

### Impact Explanation
- **Liquidation DoS → bad debt / protocol insolvency:** With `protocolLiquidationFee > 0` (the deployed configuration; tests set e.g. 1%), all liquidations through `Pool.liquidate` revert once `feeCollector`'s list is saturated. Underwater positions cannot be closed, allowing bad debt to accumulate — identical in spirit to the CVE's guest-OS crash caused by an unhandled exception the hypervisor declined to deliver.
- **Griefing freeze of new-collateral deposits for targeted users:** A victim whose list is filled cannot onboard any new collateral token while unhealthy, indirectly forcing liquidation or blocking normal use of the pool.
- The revert is atomic (no stuck intermediate state), but the *function* is permanently bricked for that recipient — a liveness failure on the protocol's most critical safety path.

### Likelihood Explanation
- Reachable by a pure EOA with only public entry points (`DepositToken.deposit`/`transfer`). Cost is bounded by dust deposits of each registered collateral — no privileged role, oracle manipulation, or malicious infrastructure required.
- Precondition: the pool must have ~30+ registered deposit tokens for the cap to be reachable. On deployments with fewer registered collaterals the list cannot be filled; the exploitability therefore depends on the deployed configuration (pools that have accumulated many deposit tokens across versions, or to which the governor keeps adding collaterals, are vulnerable).
- No existing mitigation blocks it: `nonReentrant`, `whenNotShutdown`, SynthContext checks, and health checks do not inspect list length; `removeFromDepositTokensOfAccount` only fires on a zero balance, and the attacker chooses a recipient (`feeCollector`) that never transfers out.

### Recommendation
- In `DepositToken`'s post-transfer/seize hook (or in `Pool.addToDepositTokensOfAccount`), do not revert when the recipient list is full — silently skip registration or only register accounts whose position accounting actually requires it (e.g., skip `feeCollector`, which never borrows).
- Alternatively, exempt protocol sink addresses (`feeCollector`, `address(0)` burns) from the `MAX_TOKENS_PER_USER` accounting, and allow `seize`/liquidation proceeds to be delivered even when the recipient's list is at capacity.
- Handle the "exception" rather than propagating it: wrap the registration call so a full list cannot revert `liquidate`, mirroring the upstream fix for CVE-2016-9588 where KVM was taught to correctly deliver/queue the exception instead of crashing the guest.

### Proof of Concept
Reproducible in the existing Hardhat suite (`test/Pool.test.ts` / `test/Integration.test.ts` scaffolding):

```ts
// Setup: pool with >=30 deposit tokens registered, protocolLiquidationFee > 0,
// alice has an unhealthy position (as in the existing liquidation tests).

// 1) Attacker fills feeCollector's deposit-token list with dust
for (const dt of allDepositTokens /* length >= 30 */) {
  await underlying.connect(attacker).approve(dt.address, MaxUint256);
  await dt.connect(attacker).deposit(1, attacker.address);           // dust deposit
  await dt.connect(attacker).transfer(feeCollector, 1);              // registers token
}
// feeCollector now has 30 entries in depositTokensOfAccount

// 2) Price drops -> alice unhealthy
await masterOracle.updatePrice(met.address, toUSD('0.5'));

// 3) Liquidation always reverts: second seize() hits ReachedMaxDepositTokens
const amount = await pool.quoteLiquidateMax(msEth.address, alice.address, msdMET.address);
await expect(
  pool.connect(liquidator).liquidate(msEth.address, alice.address, amount, msdMET.address)
).to.be.revertedWithCustomError(pool, 'ReachedMaxDepositTokens');

// 4) Variant: fill a victim's list -> victim cannot deposit any NEW collateral type
for (const dt of allDepositTokens) {
  await dt.connect(attacker).transfer(victim.address, 1);
}
await expect(
  newDepositToken.connect(victim).deposit(parseEther('100'), victim.address)
).to.be.revertedWithCustomError(pool, 'ReachedMaxDepositTokens');
```

Note: step 1 requires the pool to expose ≥30 deposit tokens on the target deployment; where fewer are registered the finding is latent rather than live. The revert-propagation flaw itself (no graceful handling of a full recipient list inside `liquidate`) exists unconditionally.
