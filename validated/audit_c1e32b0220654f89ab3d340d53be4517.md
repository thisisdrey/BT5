### Title
NFT permanently locked in `pallet-nft-fractionalization` when fungible dust-burn drops total supply below the fixed `fractions` unify threshold - (File: `substrate/frame/nft-fractionalization/src/lib.rs`)

### Summary
`pallet-nft-fractionalization::fractionalize` locks a user's NFT in the pallet account and mints an exact, fixed `fractions` amount of a fungible asset. To get the NFT back, `unify` requires a single caller to hold **exactly** `details.fractions` of that asset, which is then burned with `Precision::Exact`. Because the minted asset is a normal transferable `pallet-assets` token, any ordinary transfer of it can trigger the asset pallet's existential-deposit/dust-burn logic, which reduces `Asset::supply` below `details.fractions`. Once that happens there is no path in the codebase to ever bring the circulating supply back to `details.fractions`, so `do_burn_asset`'s `Exact` burn can never succeed and the NFT (plus the depositor's held `Deposit`) is permanently stuck in the pallet, exactly analogous to the reported Solidity bug where collateral NFTs are moved into a pool contract that has no function capable of releasing them.

### Finding Description
- `fractionalize` (`substrate/frame/nft-fractionalization/src/lib.rs:220-263`) transfers the NFT's transferability to the pallet (`do_lock_nft`), creates a new asset owned by the pallet account, and mints exactly `fractions` units to `beneficiary` via `do_mint_asset` [1](#0-0) .
- `unify` (`substrate/frame/nft-fractionalization/src/lib.rs:283-317`) looks up `NftToAsset` details and calls `Self::do_burn_asset(asset_id.clone(), &who, details.fractions)?` before unlocking and transferring the NFT back [2](#0-1) .
- `do_burn_asset` burns from `who` with `Precision::Exact` and `Preservation::Expendable` before calling `T::Assets::start_destroy` [3](#0-2) . `Exact` burning requires `who`'s reducible balance to be `>= amount` — i.e. `who` must hold the full `fractions` amount in one account.
- The minted asset is a standard `pallet-assets` fungible; any subsequent `transfer`/`transfer_approved`/`force_transfer` on it can leave a remainder below `min_balance`, which the asset pallet burns as dust and subtracts from `Asset::supply` (see `transfer_and_die`, `do_burn`, `decrease_balance` in `substrate/frame/assets/src/functions.rs:527-748`) [4](#0-3) .
- Once total circulating `supply` for that asset ID drops below the immutable `details.fractions` value stored in `NftToAsset` at fractionalize time, it becomes mathematically impossible for any single account to ever accumulate `fractions` units again — the required exact amount simply no longer exists on-chain.
- There is no admin/force path, no partial-unify, no reclamation function, and no burn-adjustment mechanism in this pallet to recover from this state. The NFT (transferred into the pallet's custody) and the original depositor's `HoldReason::Fractionalized` deposit are stuck forever, with `NftToAsset` entry unremovable via any dispatchable in the pallet.
- This mirrors the report's core broken invariant: value (NFT collateral) is moved into a pallet-controlled account by a normal, permissionless flow, but the only "release" function has a precondition that can be permanently and irreversibly violated by ordinary, unprivileged token movement (a plain `pallet-assets::transfer` that dusts an account) — with no admin override, no auction/burn-and-settle path, and no receiver-hook equivalent that would guard against this.

### Impact Explanation
Any NFT fractionalized through this pallet can become permanently unrecoverable, together with the collection creator's locked deposit, purely as a side effect of normal fungible-token transfers among holders (not any malicious governance/relayer/validator action). This is a genuine permanent user-fund/NFT lock impact in-scope per the gate ("permanent user-fund or bridge-state lock").

### Likelihood Explanation
Triggering this requires no privileged actor: any holder of the fractionalized asset can perform ordinary transfers that leave dust below `min_balance` on some account, which is standard and expected behavior of `pallet-assets`. Given typical distribution of fractional tokens across many holders and normal wallet activity (people naturally drain small remainders when selling/transferring), the total supply falling below the frozen `fractions` figure is a realistic, unprivileged, likely-to-occur event over the life of any actively-traded fractionalized NFT, especially if `min_balance` is non-trivial relative to typical transfer sizes.

### Recommendation
- Track burnable/circulating supply against `details.fractions` proactively, or require `fractionalize` to also record/adjust for potential future dust burns, e.g. by minting `fractions` as a sufficient/self-sufficient asset that cannot be destroyed on dust, or by disallowing this asset instance from participating in dust-burning transfers.
- Add a recovery/reclamation extrinsic analogous to `pallet-bounties::reclaim_bounty_funds` that lets `unify` succeed with `BestEffort`/partial burn once supply has permanently fallen below `fractions`, refunding remaining value appropriately and releasing the NFT (and the depositor's held `Deposit`) rather than leaving both stuck indefinitely.
- Alternatively, enforce `min_balance = 1` (or otherwise disable dust burning) for fractionalization assets so that `supply` can never drop below the originally minted `fractions`.

### Proof of Concept
1. Alice calls `fractionalize(collection, item, asset_id, beneficiary=Bob, fractions=100)`. NFT is locked into the pallet account; 100 units of `asset_id` are minted to Bob; `NftToAsset` stores `fractions = 100`.
2. Configure/observe `pallet-assets` `min_balance` for `asset_id` (e.g. `min_balance = 10`, as configured by `do_create_asset`/asset creation parameters).
3. Bob transfers 95 units to Carol via `pallet_assets::transfer`. Bob's remaining balance (5) is below `min_balance` (10), so the asset pallet dusts/reaps Bob's account and calls `details.supply.saturating_sub(burn)` in `transfer_and_die`, permanently reducing total `supply` to 95 (`substrate/frame/assets/src/functions.rs:681-736`).
4. Now total circulating supply (95) is permanently below `fractions` (100). No account can ever hold 100 units again.
5. Any subsequent call to `unify(collection, item, asset_id, beneficiary)` from any account fails at `do_burn_asset`'s `Exact`-precision burn (`FundsUnavailable`), for all future time — the NFT and Alice's original `Deposit` hold remain permanently locked in the pallet with no other extrinsic able to release them.

		pub fn fractionalize(
			origin: OriginFor<T>,
			nft_collection_id: T::NftCollectionId,
			nft_id: T::NftId,
			asset_id: AssetIdOf<T>,
			beneficiary: AccountIdLookupOf<T>,
			fractions: AssetBalanceOf<T>,
		) -> DispatchResult {
			let who = ensure_signed(origin)?;
			let beneficiary = T::Lookup::lookup(beneficiary)?;

			let nft_owner =
				T::Nfts::owner(&nft_collection_id, &nft_id).ok_or(Error::<T>::NftNotFound)?;
			ensure!(nft_owner == who, Error::<T>::NoPermission);

			let pallet_account = Self::get_pallet_account();
			let deposit = T::Deposit::get();
			T::Currency::hold(&HoldReason::Fractionalized.into(), &nft_owner, deposit)?;
			Self::do_lock_nft(nft_collection_id, nft_id)?;
			Self::do_create_asset(asset_id.clone(), pallet_account.clone())?;
			Self::do_mint_asset(asset_id.clone(), &beneficiary, fractions)?;
			Self::do_set_metadata(
				asset_id.clone(),
				&who,
				&pallet_account,
				&nft_collection_id,
				&nft_id,
			)?;

			NftToAsset::<T>::insert(
				(nft_collection_id, nft_id),
				Details { asset: asset_id.clone(), fractions, asset_creator: nft_owner, deposit },
			);

			Self::deposit_event(Event::NftFractionalized {
				nft_collection: nft_collection_id,
				nft: nft_id,
				fractions,
				asset: asset_id,
				beneficiary,
			});

			Ok(())
		}
