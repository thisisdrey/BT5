### Title
Cross-Shard Dependency Deadlock on Transaction Abort — (`aptos-move/aptos-vm/src/sharded_block_executor/cross_shard_client.rs`)

---

### Summary

`CrossShardCommitSender::on_transaction_committed` only propagates write-set entries that are **present** in the committed output. When a producing transaction aborts (Move abort), its write set is empty of application-level keys. The dependent shard's `RemoteStateValue::get_value()` blocks indefinitely on a `Condvar` because no `RemoteTxnWriteMsg` is ever delivered for the expected cross-shard key, and no `on_transaction_aborted` path exists to send a `None`-valued sentinel. The result is a permanent executor-thread deadlock for any block whose partitioned sub-block contains such a dependency.

---

### Finding Description

**`TransactionCommitHook` has no abort callback.**

The trait is defined with a single method: [1](#0-0) 

There is no `on_transaction_aborted` method. `CrossShardCommitSender` implements only `on_transaction_committed`: [2](#0-1) 

**`send_remote_update_for_success` only iterates the actual write set.**

For an aborted transaction the write set contains only gas-charge entries, never the application-level cross-shard key `K`: [3](#0-2) 

Because `K` is absent from the write set, the inner `if let Some(...)` branch is never taken, and no `RemoteTxnWriteMsg` is sent to the dependent shard.

**The dependent shard blocks forever.**

Every cross-shard key is initialised as `RemoteValueStatus::Waiting`: [4](#0-3) 

`get_value()` spins on the `Condvar` with no timeout and no cancellation path: [5](#0-4) 

`CrossShardStateView::get_state_value` calls `get_value()` unconditionally for any registered cross-shard key: [6](#0-5) 

**The `StopMsg` does not rescue waiting threads.**

After block execution completes, the executor sends a `StopMsg` to its own `CrossShardCommitReceiver`: [7](#0-6) 

`StopMsg` only breaks the receiver loop on the *sending* shard. It does not resolve any `RemoteStateValue` entries on the *dependent* shard. The dependent shard's rayon worker thread remains blocked on the `Condvar` indefinitely.

---

### Impact Explanation

Any block whose partitioned layout places a transaction `T1` (on Shard A) as the producer of key `K` for transaction `T2` (on Shard B) will deadlock the Shard B executor thread permanently if `T1` aborts. Because `execute_transactions_with_dependencies` uses `rayon::Scope` and `block_on(callback_receiver)`, the calling thread also blocks: [8](#0-7) 

The shard service loop never returns a result to the coordinator, the block is never committed, and the validator is permanently wedged on that block — **material chain availability failure**.

---

### Likelihood Explanation

The sharded block executor is production code (not under `experimental/`). The partitioner creates cross-shard dependency edges based on static read/write-set analysis. Any user transaction that is statically predicted to write key `K` but aborts at runtime (e.g., a Move `assert!` failure, out-of-gas, or any user-controlled abort) triggers the deadlock. No privileged access is required; a normal user transaction is sufficient.

---

### Recommendation

In `CrossShardCommitSender::on_transaction_committed`, after iterating the write set, send a `RemoteTxnWrite` with `write_op = None` for every dependent-edge key that was **not** present in the write set. This signals the dependent shard to fall back to the base state view, unblocking `RemoteStateValue::get_value()`. Alternatively, add an `on_transaction_aborted` method to `TransactionCommitHook` and implement it in `CrossShardCommitSender` to send `None`-valued sentinels for all dependent edges of the aborted transaction.

---

### Proof of Concept

```rust
// Partition two transactions across two shards:
//   Shard 0, Round 0: T1 writes key K (but aborts via Move abort)
//   Shard 1, Round 1: T2 reads key K (cross-shard dependency on T1)
//
// Expected: T2's shard unblocks within a timeout (K resolved to None/base value)
// Actual:   T2's shard blocks forever on RemoteStateValue::get_value()

#[test]
fn cross_shard_abort_deadlock() {
    // Build a CrossShardStateView with key K registered as Waiting
    let key_k = StateKey::raw(b"cross_shard_key");
    let mut keys = HashSet::new();
    keys.insert(key_k.clone());
    let view = Arc::new(CrossShardStateView::new(keys, &EmptyBaseView));

    // Simulate: producing shard commits T1 with an empty write set (abort)
    // CrossShardCommitSender::on_transaction_committed is called but
    // send_remote_update_for_success finds no matching key in the write set,
    // so set_value is never called on the RemoteStateValue for key K.

    // Consuming shard tries to read K — must unblock within 1 second
    let view_clone = view.clone();
    let handle = std::thread::spawn(move || {
        view_clone.get_state_value(&key_k)
    });

    // Without the fix, handle.join() never returns.
    assert!(
        handle.join().is_ok(), // times out / deadlocks without fix
        "dependent shard blocked indefinitely — deadlock confirmed"
    );
}
```

    pub fn get_value(&self) -> Option<StateValue> {
        let (lock, cvar) = &*self.value_condition;
        let mut status = lock.lock().unwrap();
        while let RemoteValueStatus::Waiting = *status {
            status = cvar.wait(status).unwrap();
        }
        match &*status {
            RemoteValueStatus::Ready(value) => value.clone(),
            RemoteValueStatus::Waiting => unreachable!(),
        }
