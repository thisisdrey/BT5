### Title
Cross-StackerDB Chunk Replay via Signature Not Bound to Contract ID - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
The StackerDB chunk-authentication digest signs only `(slot_id, slot_version, data_hash)` and never the StackerDB smart-contract identifier the chunk belongs to. Any unprivileged party that has observed one validly-signed chunk for slot *N* in StackerDB contract *A* can resubmit that exact `(slot_id, slot_version, sig, data)` tuple against a different StackerDB contract *B* that happens to assign the same signer address to slot *N*. The write/relay path (`try_replace_chunk`, `validate_received_chunk`) authenticates the chunk purely by recovering the signer address from the signature and comparing it to the *per-contract* configured signer for that slot — it never checks that the signature was produced for contract *B* specifically. This mirrors the reported bug class: two independent identifiers (`contract_id` and the signed `(slot_id, version, hash)`) that should be bound together are instead verified independently, so a value valid for one binding is silently accepted for another.

### Finding Description
`SlotMetadata::auth_digest` computes the signed digest from only the slot id, slot version, and data hash: [1](#0-0) 

`SlotMetadata::verify`/`StackerDBChunkData::verify` then simply recovers the public key from that digest and checks the resulting address hash against the caller-supplied principal — the contract/DB the chunk is destined for is never part of what was signed: [2](#0-1) 

The storage layer looks up the expected signer *per contract* and then checks the signature against that address, but the `smart_contract` value is a caller-supplied routing parameter, not something the signature commits to: [3](#0-2) 

The same pattern repeats in the P2P validation path used both for scheduled downloads and unsolicited pushes: it resolves `get_slot_signer(smart_contract_id, data.slot_id)` for whatever contract ID accompanies the message, then verifies the chunk's self-contained signature against that address — again with no cryptographic binding between the signature and `smart_contract_id`: [4](#0-3) 

Because reward-cycle StackerDB contracts (e.g. successive `.signers-<cycle>-<page>` instances) are configured independently via `StackerDBConfig::from_smart_contract`/`eval_signer_slots`, which simply reads whatever `(signer, num-slots)` list the controlling contract returns for that specific `contract_id`, nothing prevents the same signer address from being assigned to the same slot index in two different, concurrently-live StackerDB contracts: [5](#0-4) 

Consequently, a chunk that was legitimately signed and broadcast for contract *A*'s slot *N* is also a fully-valid chunk for contract *B*'s slot *N* whenever *B* assigns that same address to slot *N* — regardless of whether the signer ever intended that data to land in *B*. Any observer (the chunk and its signature are public, served over `GET /v2/stackerdb/.../chunks`) can replay it into *B* via the ordinary write path (`POST /v2/stackerdb/.../chunks`, `poststackerdbchunk.rs`) or via unsolicited P2P push (`handle_unsolicited_StackerDBPushChunk`), as long as *B*'s stored version for that slot is lower than the replayed `slot_version`.

### Impact Explanation
This lets an unprivileged network participant write signer-authored-but-misdirected data into a StackerDB instance without that signer's intent or the target contract operator's authorization, and have honest nodes further relay/gossip it as legitimate to slot *N*. Nodes trust `try_replace_chunk`'s signature check as the sole authorization gate for accepting a write, so on the affected slot the replica ends up serving replayed/misdirected content as canonical, and it also gets rebroadcast to peers via `handle_unsolicited_StackerDBPushChunk`, propagating the wrongly-scoped data across the network — matching the "unauthenticated/unauthorized write to state or StackerDB" / "network-wide propagation of forged data" impact bar.

### Likelihood Explanation
Exploitation requires no secret key and no elevated role: only that (a) an attacker can observe an already-broadcast, validly-signed chunk (trivial — StackerDB reads are unauthenticated), and (b) the same signer address is independently assigned to the same slot index in a second, currently-configured StackerDB contract. Slot assignment order is a function of each contract's own `stackerdb-get-signer-slots` result, so this collision is not attacker-controlled per request, but is plausible across successive/parallel `.signers-*` and other StackerDB instances since signer sets are often stable or overlapping across cycles/contracts, and the vulnerability is systemic (the digest simply never scopes to a contract) rather than contract-configuration-specific luck.

### Recommendation
Include the StackerDB `smart_contract`/`contract_id` (and ideally the DB's identifying salt) inside `SlotMetadata::auth_digest` so a chunk signature is cryptographically bound to the specific StackerDB instance it was written for, mirroring the report's fix of binding two previously-independent identifiers together before trusting either in isolation. Update `SlotMetadata::sign`/`verify`, `StackerDBChunkData::sign`/`verify`/`recover_pk`, and all call sites (`try_replace_chunk`, `validate_received_chunk`) to pass and hash the contract id.

### Proof of Concept
1. Observe (via `GET /v2/stackerdb/{contract_A}/{slot}/chunk`) a validly-signed `StackerDBChunkData` for slot `N` in StackerDB contract `A`, signed by address `X` which happens to also be the assigned signer for slot `N` in a second live contract `B` (e.g. via `stackerdb-get-signer-slots` inspection, which is public read-only contract state).
2. Submit that exact `(slot_id=N, slot_version=v, sig, data)` tuple to contract `B` via `POST /v2/stackerdb/{contract_B}/chunks` (`poststackerdbchunk.rs`) or via an unsolicited `StackerDBPushChunk` P2P message.
3. `try_replace_chunk`/`validate_received_chunk` resolve `B`'s configured signer for slot `N` (which is `X`), recover the signer from the signature (also `X`), and accept the chunk — even though `X` never signed anything for contract `B`. The node stores it and rebroadcasts it to peers replicating `B`.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }

            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
