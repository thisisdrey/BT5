### Title
`remove_account` fails to clear async-call and promise-yield trie keys, letting stale receipts execute against a re-created account - (File: `core/store/src/utils/mod.rs`)

### Summary
`remove_account` (`core/store/src/utils/mod.rs:499-575`) only deletes `TrieKey::Account`, `TrieKey::ContractCode`, access/gas keys, and `TrieKey::ContractData`. It never removes `ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, or `DataIdToYieldId`. `action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) calls `remove_account` unconditionally (no check for pending cross-contract data dependencies) and `action_create_account` (`runtime/runtime/src/actions.rs:167-210`) never touches these columns either, so a `DeleteAccount(A)` immediately followed by `CreateAccount(A)` leaves all 8 rows present in state, keyed only by the bare `account_id` string with no binding to "generation" of the account.

### Finding Description
An account can generate a self-addressed callback `ActionReceipt` with two or more `input_data_ids` (e.g. `Promise::and([p1, p2]).then(self_callback)`). When that callback receipt arrives at the runtime before all its `DataReceipt`s have, `process_action_receipt` (`runtime/runtime/src/lib.rs:1593-1658`) writes `PostponedReceiptId`, `PendingDataCount`, and `PostponedReceipt` keyed by `(receiver_id, data_id/receipt_id)` and defers execution. Similarly, `promise_yield_create` writes `PromiseYieldReceipt`/`PromiseYieldStatus`/`YieldIdToDataId`/`DataIdToYieldId` (`core/store/src/utils/mod.rs:181-334`) that only resolve on a later `PromiseResume`/timeout.

If the account owner then submits `DeleteAccountAction` (locked stake == 0, benign beneficiary) while one of these dependencies is still outstanding, `action_delete_account` → `remove_account` deletes the `Account`/`ContractCode`/keys/`ContractData` rows but leaves the 8 async-state rows behind, because `remove_account` has no logic scanning those columns. Nothing in `check_account_existence` / `action_delete_account` requires that pending postponed receipts or promise-yield state be absent before deletion.

If `CreateAccount(A)` is submitted in the next receipt (self-registration, or any third party re-registering the now-vacant name), the runtime happily creates a brand-new `Account` object while the stale rows survive untouched, since `action_create_account` only writes `TrieKey::Account`.

When the deferred dependency eventually resolves — a late `DataReceipt` (`runtime/runtime/src/lib.rs:1386-1474`) or a `PromiseResume` (`runtime/runtime/src/lib.rs:1500-1562`) — the runtime looks up `PostponedReceiptId`/`PendingDataCount`/`PostponedReceipt`/`PromiseYieldReceipt` purely by `(account_id, data_id)`, with no check that the account is "the same" account that requested the callback. It fetches the old, fully attacker-controlled `ActionReceipt` and calls `apply_action_receipt`, which fetches the *current* account via `get_account(state_update, account_id)` (`runtime/runtime/src/lib.rs:853`) — i.e. the newly created account — and executes the old receipt's actions against it. Because the stored receipt's `predecessor_id` is the original account name (self-call), `check_actor_permissions` passes trivially (`actor_id == account_id` as strings), letting the old owner's pre-planted `FunctionCall`/other actions run with authority over the new account's balance and contract storage — value conservation and authorization-exactness invariants are both broken (funds/storage of the *new* occupant can be manipulated by intent baked into the *old* occupant's receipt).

### Impact Explanation
This is a genuine authorization-escalation / value-conservation violation: a ghost postponed/yield receipt, crafted and paid for by the old account owner, executes later against an unrelated account occupying the same name, potentially transferring/spending the new account's balance, mutating its contract storage, or invoking its contract code with attacker-chosen arguments — all attributed to authority the old owner no longer has. This falls under NEAR's "theft of user funds" / "authorization escalation across accounts" bounty category.

### Likelihood Explanation
Fully attacker-reachable with only self-controlled transactions: deploy a contract on account A that creates a multi-dependency self-callback (or a `promise_yield_create`), submit `DeleteAccount(A, beneficiary)` once `locked == 0` while the dependency is outstanding, then submit `CreateAccount(A)` in the following receipt (or wait for/induce a third party to re-register `A`). The attacker fully controls timing of the second leg of the promise/yield (e.g. simply not resolving a yield until near its timeout), giving a wide window to complete the delete+recreate sequence. No validator, protocol, or leaked-key access is required.

### Recommendation
Extend `remove_account` (`core/store/src/utils/mod.rs`) to also iterate and delete the `ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, and `DataIdToYieldId` prefixes for the account (mirroring the existing access-key/gas-key/contract-data iteration), or alternatively reject `DeleteAccountAction` outright when any such pending entry exists for the account.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}

            account_storage_usage,

            account_id: account_id.clone(),
            public_key: None,
            balance: gas_key_balance_to_burn,
        }
        .into());
        return Ok(());
    }

    let account_balance = account_ref.amount();
    if account_balance > Balance::ZERO {
        result
            .new_receipts
            .push(Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance));

            StorageError::StorageInconsistentState("compute_usage overflow".to_string())
        })?;
    }
    *actor_id = receipt.predecessor_id().clone();
    *account = None;
    Ok(())
}

    /// Received a new action receipt. We'll first check how many input data items
    /// were already received before and saved in the state.
    /// And if we have all input data, then we can immediately execute the receipt.
    /// If not, then we will postpone this receipt for later.
    fn process_action_receipt(
        &self,
        receipt: &Receipt,
        receipt_sink: &mut ReceiptSink,
        instant_receipts: &mut VecDeque<Receipt>,
        validator_proposals: &mut Vec<ValidatorStake>,
        state_update: &mut TrieUpdate,
        apply_state: &ApplyState,
        epoch_info_provider: &dyn EpochInfoProvider,
        pipeline_manager: &ReceiptPreparationPipeline,
        stats: &mut ChunkApplyStatsV1,
        account_id: &AccountId,
        action_receipt: VersionedActionReceipt<'_>,
        receipt_to_tx: &mut Vec<(CryptoHash, ReceiptToTxInfo)>,
    ) -> Result<Option<ExecutionOutcomeWithId>, RuntimeError> {
        let mut pending_data_count: u32 = 0;
        for data_id in action_receipt.input_data_ids() {
            if !has_received_data(state_update, account_id, *data_id)? {
                pending_data_count += 1;
                // The data for a given data_id is not available, so we save a link to this
                // receipt_id for the pending data_id into the state.
                set(
                    state_update,
                    TrieKey::PostponedReceiptId {
                        receiver_id: account_id.clone(),
                        data_id: *data_id,
                    },
                    receipt.receipt_id(),
                )
            }
        }

        if pending_data_count == 0 {
            // All input data is available. Executing the receipt. It will cleanup
            // input data from the state.
            return self
                .apply_action_receipt(
                    state_update,
                    apply_state,
                    pipeline_manager,
                    receipt,
                    receipt_sink,
                    instant_receipts,
                    validator_proposals,
                    stats,
                    epoch_info_provider,
                    receipt_to_tx,
                )
                .map(Some);
        } else {
            // Not all input data is available now.
            // Save the counter for the number of pending input data items into the state.
            set(
                state_update,
                TrieKey::PendingDataCount {
                    receiver_id: account_id.clone(),
                    receipt_id: *receipt.receipt_id(),
                },
                &pending_data_count,
            );
            // Save the receipt itself into the state.
            set_postponed_receipt(state_update, receipt);
        }

        Ok(None)
    }
