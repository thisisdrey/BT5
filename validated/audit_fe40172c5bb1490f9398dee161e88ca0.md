Audit Report

## Title
`claim_swap` unconditionally deletes the `PendingSwap` record even when the underlying claim only partially succeeds, permanently stranding the source's reserved funds - (File: `substrate/frame/atomic-swap/src/lib.rs`)

## Summary
`claim_swap` calls `swap.action.claim(&swap.source, &target)` and unconditionally removes the `PendingSwaps` entry regardless of the boolean result, using it only for the emitted event. [1](#0-0)  For `BalanceSwapAction`, `claim()` returns `C::repatriate_reserved(...).is_ok()`, but `repatriate_reserved` performs a `BestEffort`/`Polite` transfer that can move less than `value` (even zero) while still returning `Ok`. [2](#0-1) [3](#0-2) 

## Finding Description
`claim()`'s `.is_ok()` check masks partial delivery: `do_transfer_reserved` is invoked with `BestEffort` precision and `Polite` liveness, so it will not repatriate funds that would push the source below its frozen balance, but it still returns `Ok(actual)` for whatever amount it could move, and `repatriate_reserved` propagates that as `Ok(value - actual)`, i.e., `Ok(_)` in all non-erroring cases. [3](#0-2)  Consequently `succeeded` in `claim_swap` is `true` even when the source's reserved balance was only partially (or not at all) transferred to the target. Immediately after, `PendingSwaps::<T>::remove(target.clone(), hashed_proof)` deletes the swap record unconditionally, and `SwapClaimed { success: true }` is emitted, misreporting the outcome. [1](#0-0) 

Once removed, the only other path capable of unreserving the source's balance is `cancel_swap`, which requires the entry to still exist via `PendingSwaps::<T>::get(&target, hashed_proof).ok_or(Error::<T>::NotExist)?`. [4](#0-3)  Since `claim_swap` already deleted the entry, `cancel_swap` can never run for that swap, and any leftover reserved balance that `action.reserve` locked in `create_swap` but that the `Polite` repatriation refused to move remains permanently reserved with no dispatchable path to release it. [5](#0-4) 

## Impact Explanation
This is a permanent, unrecoverable lock of the swap source's on-chain funds — the reserved balance can never be unreserved once `claim_swap` runs and reports success despite a partial transfer. This matches the allowed "permanent user-fund lock" impact, and the `SwapClaimed{success: true}` event also constitutes a wrong-settlement report since the transferred amount can be less than (or zero of) the intended value.

## Likelihood Explanation
No privileged access is required; both source and target in `create_swap`/`claim_swap` are ordinary signed accounts. The condition needed — the source having a `frozen`/locked balance (from staking, vesting, or governance locks) at claim time such that `Polite` blocks full repatriation — is common for real accounts and can also be deliberately engineered by a counterparty who selects/knows the source's lock state before calling `claim_swap`.

## Recommendation
`claim_swap` should not unconditionally delete the `PendingSwap` entry on partial success. Either change `SwapAction::claim` to report the actually transferred amount/partial-success and only clear storage on full completion (leaving a reduced-value entry recoverable via `cancel_swap` otherwise), or use `Exact` precision in `repatriate_reserved` so a partial transfer errors out and the whole `claim_swap` call fails atomically, preserving the entry and the source's ability to later cancel and reclaim funds.

## Proof of Concept
1. `A` calls `create_swap(target = B, hashed_proof, action = BalanceSwapAction::new(100), duration)`, reserving `100` from `A`'s free balance. [5](#0-4) 
2. Before `B` claims, `A` accumulates a frozen/locked balance such that a `Polite` transfer of the full `100` out of reserved would push `A` below the frozen threshold.
3. `B` calls `claim_swap(proof, action)`. `repatriate_reserved` runs with `BestEffort`+`Polite`, moves less than `100` (possibly `0`) to `B`, and returns `Ok(remaining)`, so `claim()` returns `true`. [2](#0-1) 
4. `claim_swap` removes the `PendingSwap` entry and emits `SwapClaimed { success: true }` despite the shortfall. [1](#0-0) 
5. `A` calls `cancel_swap` and receives `Error::NotExist` since the entry is gone, permanently stranding the un-transferred remainder of `A`'s reserved `100`. [4](#0-3)

	/// Move the reserved balance of one account into the balance of another, according to `status`.
	///
	/// Is a no-op if:
	/// - the value to be moved is zero; or
	/// - the `slashed` id equal to `beneficiary` and the `status` is `Reserved`.
	///
	/// This is `Polite` and thus will not repatriate any funds which would lead the total balance
	/// to be less than the frozen amount. Returns `Ok` with the actual amount of funds moved,
	/// which may be less than `value` since the operation is done on a `BestEffort` basis.
	fn repatriate_reserved(
		slashed: &T::AccountId,
		beneficiary: &T::AccountId,
		value: Self::Balance,
		status: Status,
	) -> Result<Self::Balance, DispatchError> {
		let actual =
			Self::do_transfer_reserved(slashed, beneficiary, value, BestEffort, Polite, status)?;
		Ok(value.saturating_sub(actual))
	}
