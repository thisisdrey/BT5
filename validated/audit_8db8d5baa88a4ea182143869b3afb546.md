### Title
`VesperGateway.deposit` mints vToken shares with no slippage bound, so a depositor can be sandwiched into receiving fewer `msdTokens` than the deposited underlying is worth - ([File: contracts/VesperGateway.sol](contracts/VesperGateway.sol))

### Summary
`VesperGateway.deposit` is the analog of the reported bug class: it routes user underlying into a share-based vault (`IVPool.deposit`) and then mints `msdToken` collateral for whatever share amount comes back, with no `minVTokenOut`/`minShares` parameter. Any change in the vToken price-per-share between transaction submission and inclusion — including deliberate manipulation by an unprivileged attacker — silently reduces the collateral the user receives.

### Finding Description
`VesperGateway.deposit(pool_, vToken_, amount_)` (contracts/VesperGateway.sol:44-65) does:

1. Pulls `amount_` of underlying from the caller.
2. Calls `vToken_.deposit(amount_)` and measures the minted vTokens via a balance delta (`_vTokenAmount = vToken_.balanceOf(this) - _balanceBefore`).
3. Approves and deposits `_vTokenAmount` into `pool_.depositTokenOf(vToken_)`, minting `msdVToken` 1:1 to the caller.

There is no parameter letting the caller bound the acceptable share amount, unlike `DepositToken.deposit` which mints 1:1 minus a fixed fee (`quoteDepositOut`, contracts/DepositToken.sol:294-302) and therefore has no exchange-rate exposure. The Vesper vToken, however, is an ERC4626-like share token whose minted shares depend on the pool's price-per-share at execution time. An attacker can front-run the victim's `deposit` and move the vPool's share price (e.g., deposit a large amount into the vPool then donate underlying directly to the pool/strategy to inflate `totalValue`, or trigger a withdrawal/harvest that raises price-per-share). The victim's `amount_` of underlying then mints proportionally fewer vTokens, so fewer `msdTokens` are minted at step 3. The attacker then redeems their own vPool shares at the inflated price, extracting the value the victim "lost" — a classic deposit-sandwich / share-inflation attack. All entry points used (`VesperGateway.deposit`, `IVPool.deposit/withdraw`, direct ERC20 transfers to the vPool) are public and unprivileged; the registered-pool check (`isPoolRegistered`, line 45) and SynthContext sender do not constrain `vToken_` to a safe price.

### Impact Explanation
Direct loss of user collateral value: the victim deposits `amount_` underlying but receives `msdVToken` backed by fewer vTokens than the fair exchange rate would yield; the difference accrues to existing vPool shareholders (the attacker) and is redeemed by them. The minted `msdTokens` are real collateral in the Pool, so the loss is immediately reflected as reduced borrowable capacity and redemption value.

### Likelihood Explanation
Requires the target vPool's price-per-share to be movable within one block (true for balance-based share accounting and for pools with pending harvest/withdrawal events), and the attacker to hold/dump vPool shares to capture the donated premium. The function is a public gateway intended exactly for vToken collateral onboarding, so users calling it with size are exposed on every deposit.

### Recommendation
Add a `minVTokenAmountOut_` (and/or `minSharesMinted`) parameter to `VesperGateway.deposit`, quote expected shares before executing, and revert if the balance delta at step 2 is below the bound. Apply the same bound on `VesperGateway.withdraw` (minimum underlying out), which likewise performs an unbounded share-to-underlying conversion at lines 86-89.
