### Title
Precision-loss bypass of the withdrawal ratio sanity check in `ExchangeWithdrawActuator.doValidate()` due to BigDecimal→double conversion before comparison - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
The legacy (default-active) branch of `ExchangeWithdrawActuator.doValidate()` verifies that the truncated `anotherTokenQuant` returned to an exchange creator on `ExchangeWithdrawContract` is close enough to the ideal pool ratio, exactly mirroring the pattern in the Tokemak report: a division is performed first, converted to a lossy floating-point representation, and only then compared against a fixed tolerance. This reproduces the same class of rounding-order/precision defect described in the external finding.

### Finding Description
`ExchangeWithdrawActuator.doValidate()` computes the counterpart token amount using exact `BigDecimal`/`BigInteger` floor division, then performs a "Not precise enough" sanity check to make sure the floor-division truncation is not too large relative to the withdrawn amount. This check has two code paths gated by `allowHarden()`, which reads `dynamicStore.allowHardenExchangeCalculation()` [1](#0-0) , a committee-controlled dynamic property that defaults to off unless explicitly activated by a chain proposal.

In the default (non-hardened) branch, the check is:
```java
double remainder = bigSecondTokenBalance.multiply(bigTokenQuant)
    .divide(bigFirstTokenBalance, 4, BigDecimal.ROUND_HALF_UP).doubleValue()
    - anotherTokenQuant;
if (remainder / anotherTokenQuant > 0.0001) {
  throw new ContractValidateException("Not precise enough");
}
``` [2](#0-1) 
and symmetrically for the other token branch: [3](#0-2) 

Exactly as in the Tokemak `verifyLSTPriceGap()` bug, this performs a division (`BigDecimal.divide(..., 4, ROUND_HALF_UP)`), truncates it to a fixed 4-decimal scale, converts to an IEEE-754 `double`, subtracts an integer, and only then divides again and compares to the tolerance `0.0001`. Each of these steps (fixed 4-decimal rounding, `double` conversion, and division-before-comparison) introduces representable error that can push a truly out-of-tolerance ratio to appear within tolerance, or vice versa — the same "divide first, compare after" precision loss pattern flagged in the source report. The actual transferred `anotherTokenQuant`, by contrast, is computed exactly via `BigInteger` floor division in `execute()` [4](#0-3) , so the sanity check is the only thing standing between "acceptable truncation loss" and "excessive truncation loss" on each withdrawal.

Because `BigInteger` division always truncates toward zero, `anotherTokenQuant` is always floor of the ideal (irrational) ratio, i.e., rounding is systematically biased against the withdrawer and in favor of the remaining pool balance. If the floating-point check incorrectly passes for a truncation that is actually larger than the intended 0.01% tolerance, the exchange creator can execute a withdrawal that leaves disproportionately more value trapped in the pool relative to the tokens received. Repeated over many small partial withdrawals (an operation entirely reachable by a normal signed `ExchangeWithdrawContract` transaction sent by the exchange's creator account, which is the only authorization check enforced at line 181-183 of the same file), the cumulative truncation dust becomes unrecoverable because there is no path to reclaim leftover fractional balances once the pool ratio drifts under the creator's control.

### Impact Explanation
This is a Medium-severity issue: value permanently and unrecoverably locked inside the exchange pool balances due to a floating-point precision defect in a safety check that was specifically designed to bound truncation loss to 0.01%. Because the flawed comparison can silently accept truncations larger than intended, the pool's real ratio can be pushed further from its ideal value than the protocol guarantees, and there is no mechanism to reconcile or withdraw the resulting dust, meeting the "permanent freezing of funds" impact bar.

### Likelihood Explanation
The vulnerable code path is the *default* branch — `allowHardenExchangeCalculation` must be explicitly enabled via governance proposal to switch to the safer `BigDecimal`-only comparison branch [5](#0-4) . Any account that is the creator of an `Exchange`/`ExchangeV2` pool can trigger this path with an ordinary, unprivileged `ExchangeWithdrawContract` transaction; no special permission beyond being the pool creator is required, and this is reachable through the standard transaction broadcast path.

### Recommendation
Rework the precision-loss check to avoid mixed-precision floating-point conversion and division-before-comparison, mirroring the recommendation in the source report: perform the comparison purely in integer/`BigInteger`/`BigDecimal` arithmetic without ever converting to `double`, and cross-multiply instead of dividing twice, e.g.:
```java
BigDecimal idealQuant = bigSecondTokenBalance.multiply(bigTokenQuant); // = anotherTokenQuant * bigFirstTokenBalance + remainderNumerator
BigDecimal diff = idealQuant.subtract(BigDecimal.valueOf(anotherTokenQuant).multiply(bigFirstTokenBalance));
if (diff.multiply(BigDecimal.valueOf(10000))
        .compareTo(BigDecimal.valueOf(anotherTokenQuant).multiply(bigFirstTokenBalance)) > 0) {
  throw new ContractValidateException("Not precise enough");
}
```
This eliminates the intermediate scaled `BigDecimal.divide` truncation and `doubleValue()` conversion, removing the precision-loss vector entirely, consistent with the already-implemented (but currently opt-in) hardened branch, which should be made the sole code path.

### Proof of Concept
Not independently reproduced in this analysis; a concrete PoC would require constructing `firstTokenBalance`/`secondTokenBalance`/`tokenQuant` triples (analogous to the Solidity PoC in the source report) where `BigDecimal.divide(..., 4, ROUND_HALF_UP).doubleValue()` rounds/truncates the true quotient enough to move `remainder / anotherTokenQuant` across the `0.0001` boundary versus the exact rational computation — this was not verified end-to-end against the actual `ExchangeWithdrawActuatorTest` harness due to tool/iteration limits, and should be validated with a unit test extending `ExchangeWithdrawActuatorTest.hardenedPrecisionCheckFailsWhenImprecise` [6](#0-5)  but run with `allowHardenExchangeCalculation` left at its default (0) instead of the hardened branch.
