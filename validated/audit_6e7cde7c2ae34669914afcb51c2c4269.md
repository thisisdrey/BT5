## Title
No slippage protection on `ExchangeWithdrawContract` allows front-run value extraction during bancor-pool withdrawal - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`ExchangeWithdrawActuator`, which lets an exchange's creator withdraw liquidity from a TRC10 bancor-style pool, computes the counter-asset amount (`anotherTokenQuant`) purely from the pool's *current* on-chain ratio at execution time, with no user-supplied minimum-output parameter to bound acceptable slippage. This mirrors the reported Arrakis V2 `burn()` issue, where liquidity is withdrawn from a pool without an `amount0Min`/`amount1Min` check, exposing the caller to front-running.

### Finding Description
`ExchangeWithdrawContract` only carries `owner_address`, `exchange_id`, `token_id`, and `quant` — there is no `expected`/minimum-output field, unlike its sibling `ExchangeTransactionContract`, which explicitly has an `expected` field used to enforce a minimum-received check. [1](#0-0) [2](#0-1) 

In `ExchangeTransactionActuator.doValidate()`, the resulting `anotherTokenQuant` is checked against the caller-supplied `tokenExpected` and the transaction is rejected if the ratio is worse than expected: [3](#0-2) 

By contrast, `ExchangeWithdrawActuator.doValidate()` computes `anotherTokenQuant` from the live pool balances (`bigFirstTokenBalance`/`bigSecondTokenBalance`) and only validates balance sufficiency, positivity, and rounding precision ("Not precise enough") — never an economic floor supplied by the caller: [4](#0-3) 

`ExchangeWithdrawActuator.execute()` then re-derives `anotherTokenQuant` from the pool balances at execution time (which may have shifted between broadcast and block-inclusion) and credits/debits the account accordingly, with no slippage guard: [5](#0-4) 

Because the pool ratio is publicly manipulable via `ExchangeTransactionContract` (buy/sell against the same `exchange_id`), an attacker observing a pending `ExchangeWithdrawContract` in the mempool can submit `ExchangeTransactionContract` trades against the same pool immediately beforehand to skew `firstTokenBalance`/`secondTokenBalance`, then trade back afterward, extracting value from the withdrawer's now-mispriced withdrawal — the same sandwich/front-run pattern described in the Arrakis V2 report for `ArrakisV2.burn()`.

### Impact Explanation
The exchange creator withdrawing liquidity receives an amount of the counter-asset determined solely by the pool state at block-inclusion time, which can be manipulated by a third party's preceding transactions within the same block/mempool window. This allows unauthorized extraction of value from the withdrawing account (the creator effectively receives less than a fair-price withdrawal would yield, while the attacker profits from the induced price distortion), constituting an economic theft/loss vector reachable purely via ordinary signed transactions (`ExchangeTransactionContract` + `ExchangeWithdrawContract`) against `Wallet`'s exchange RPC endpoints.

### Likelihood Explanation
The `ExchangeWithdrawContract` can be broadcast by any account that created an exchange, and `ExchangeTransactionContract` trades to manipulate the ratio can be submitted by any account holding TRX/TRC10 balance — no special privilege is required beyond owning an exchange (a low bar since anyone can create one). An attacker only needs to observe the pending withdraw transaction and race it with buy/sell transactions, which is a standard front-running technique on any public mempool.

### Recommendation
Add a caller-supplied minimum-output field(s) (e.g., `expected_another_token_quant`) to `ExchangeWithdrawContract`, and in `ExchangeWithdrawActuator.doValidate()`/`execute()` reject the transaction if the computed `anotherTokenQuant` falls below that caller-specified floor, mirroring the `expected` check already present in `ExchangeTransactionActuator`.

### Proof of Concept
1. Attacker monitors the mempool and observes a pending `ExchangeWithdrawContract` from the exchange creator for `exchangeId` withdrawing `tokenQuant` of `firstTokenId`.
2. Attacker submits an `ExchangeTransactionContract` trade against the same `exchangeId` to shift `firstTokenBalance`/`secondTokenBalance` unfavorably for the pending withdraw (e.g., selling a large amount of `secondTokenId` into the pool), and gets it included in an earlier position in the same or preceding block.
3. The victim's `ExchangeWithdrawContract` executes against the now-skewed balances in `ExchangeWithdrawActuator.execute()` (`actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java:74-89`), yielding a materially worse `anotherTokenQuant` than what the pool ratio showed when the withdraw was signed/broadcast — with no minimum-output check to abort the transaction.
4. Attacker reverses their trade afterward (another `ExchangeTransactionContract`) to restore the pool ratio and capture the spread, profiting at the victim's expense.
