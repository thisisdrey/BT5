### Title
Attacker can fill a victim's deposit-token list with dust transfers to block all future deposits, collateral top-ups and inbound transfers — (File: contracts/DepositToken.sol)

### Summary
`DepositToken._mint` and `DepositToken._transfer` call `pool.addToDepositTokensOfAccount(account_)` whenever a recipient's balance of that token goes from 0 to non-zero (`DepositToken.sol:486-488`, `DepositToken.sol:518-520`). `Pool` enforces a per-account cap (`MAX_TOKENS_PER_USER`) on `depositTokensOfAccount`, and the addition reverts once the cap is reached. Any unprivileged EOA can `deposit(1 wei of each listed collateral, onBehalfOf = victim)` or `transfer()` dust `msdTOKEN`s to a victim to permanently occupy every slot in their list.

### Finding Description
The Samba `rpcecho` bug class is "a publicly reachable call that occupies a shared resource and thereby denies service to other users." In Metronome the shared resource is the per-account `depositTokensOfAccount` enumerable list in `Pool`, which has a hard cap to bound `debtPositionOf` iterations.

Attack path:

1. Attacker calls `DepositToken.deposit(amount_, victim)` — `onBehalfOf_` is attacker-controlled and permissionless (`DepositToken.sol:211-234`). Deposit fee only makes the griefing cheaper (fee minted to `feeCollector`, dust still minted to victim).
2. Each such deposit of a distinct collateral the victim doesn't hold triggers `addToDepositTokensOfAccount(victim)` (`DepositToken.sol:487`).
3. Alternatively, once the attacker holds dust `msdTOKEN`s, `transfer(victim, 1)` does the same through `_transfer` (`DepositToken.sol:519`).
4. After `MAX_TOKENS_PER_USER` distinct tokens are registered for the victim, every subsequent first-time mint/transfer-in to the victim reverts inside `addToDepositTokensOfAccount`, reverting the whole `deposit`, `transfer`, `transferFrom` or `seize` transaction.

Note the list only shrinks when the victim's balance of that token reaches exactly zero (`DepositToken.sol:460-462`, `523-525`), so the victim must actively withdraw/burn each dust position (costing withdraw fees) to free a slot — and the attacker can refill slots faster than the victim clears them, at near-zero marginal cost.

### Impact Explanation
Temporary freezing of funds / forced-liquidation griefing:

- Victim cannot deposit *new* collateral types, so they cannot top-up collateral to defend a deteriorating position — the dust-griefed account becomes unable to increase its health factor via fresh deposits and is exposed to liquidation that would otherwise have been avoidable.
- Any protocol or counterparty that transfers `msdTOKEN`s to the victim (e.g., a `seize` crediting them as `to_` in liquidation, or smart-farming unwind paths that deliver a token the victim doesn't yet hold) reverts, blocking those flows.
- Funds are recoverable only by manually burning each dust position to zero, paying withdraw fees each time — a bleed plus temporary freeze, matching the "temporary freezing of funds" acceptance criterion.

### Likelihood Explanation
- Requires only an EOA, small amounts of each listed underlying (or already-held `msdTOKEN` dust), and public entry points (`deposit` / `transfer`). No privileged role, oracle manipulation, or malicious infrastructure needed.
- Cost scales with the number of listed deposit tokens; the cap is fixed, so the attack is bounded and cheap.
- `whenNotPaused`/`nonReentrant`/`SynthContext` checks do not help: the attacker legitimately passes them; the revert happens on the victim's accounting state, not the attacker's.

### Recommendation
- Remove spam entries automatically: in `addToDepositTokensOfAccount`, if the list is full, either allow the push to fail gracefully or use a capped structure that evicts zero-dust entries.
- Cheaper fix: in `_mint`/`_transfer`, only register the token if `amount_` exceeds a minimum dust threshold, or let `Pool` skip adding when the account list is full instead of reverting (track "unlisted balances" so `debtPositionOf` still accounts for them — e.g., iterate `balanceOf` per known token rather than relying solely on the list, or keep a separate overflow flag).
- Alternatively, whitelist: only count a token toward the cap once the position exceeds a minimum USD value (`debtFloorInUsd`-style floor).

### Proof of Concept
Hardhat/Foundry fork sketch (assumes `MAX_TOKENS_PER_USER` slots and N listed `DepositToken`s on a deployed `Pool`):

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

import "forge-std/Test.sol";

contract DustGriefPoC is Test {
    IPool pool = IPool(POOL);
    IDepositToken[] tokens; // all deposit tokens listed in pool

    function test_dustGriefBlocksVictimDeposits() public {
        address victim = makeAddr("victim");
        address attacker = makeAddr("attacker");

        // 1. Attacker fills victim's deposit-token list with 1-wei deposits
        for (uint i; i < tokens.length && i < MAX_TOKENS_PER_USER; ++i) {
            IERC20 underlying = tokens[i].underlying();
            deal(address(underlying), attacker, 1e6);
            vm.startPrank(attacker);
            underlying.approve(address(tokens[i]), 1);
            tokens[i].deposit(1, victim); // onBehalfOf_ = victim
            vm.stopPrank();
        }

        // victim's list is now full
        assertEq(pool.getDepositTokensOfAccount(victim).length, MAX_TOKENS_PER_USER);

        // 2. Any new collateral type deposit to victim reverts
        IDepositToken newToken = tokens[MAX_TOKENS_PER_USER]; // a token victim doesn't hold
        deal(address(newToken.underlying()), victim, 100e18);
        vm.startPrank(victim);
        newToken.underlying().approve(address(newToken), 100e18);
        vm.expectRevert(); // addToDepositTokensOfAccount hits cap
        newToken.deposit(100e18, victim);
        vm.stopPrank();

        // 3. Inbound transfer of a new msdTOKEN to victim also reverts
        deal(address(newToken.underlying()), attacker, 1e6);
        vm.startPrank(attacker);
        newToken.underlying().approve(address(newToken), 1);
        newToken.deposit(1, attacker);          // attacker holds dust of newToken
        vm.expectRevert();
        newToken.transfer(victim, 1);           // would add entry -> reverts
        vm.stopPrank();
    }
}
```
