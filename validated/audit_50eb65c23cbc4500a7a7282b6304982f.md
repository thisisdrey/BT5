### Title
Unbounded attacker-controlled array-length in TVM precompile signature-array decoding causes OOM/DoS - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` and `BatchValidateSign` TVM precompiled contracts (addresses `0x...a` and `0x...9`) decode a `bytes[]` array of signatures from raw call data by reading a length word directly from the caller-supplied calldata and immediately allocating a Java array of that length, with no upper bound check on the legacy code path. This is directly analogous to the `android-gif-drawable` CVE-2022-23435 pattern: an attacker-controlled length field is trusted and used to allocate memory before any sanity/limit check, enabling a denial-of-service.

### Finding Description
`extractBytesArray` reads `len` straight from `words[offset].intValueSafe()` — fully attacker-controlled via calldata — and immediately does `new byte[len][]`: [1](#0-0) 

This helper is invoked from `ValidateMultiSign.execute` and `BatchValidateSign.doExecute`. Both methods only bound the array length (`sigArraySize > MAX_SIZE` check) when the feature flag `VMConfig.allowTvmSelfdestructRestriction()` is enabled, in which case they switch to the safer `extractSigArray` path instead. When that flag is not active, `extractBytesArray` is called with **no length validation at all**: [2](#0-1) [3](#0-2) 

`intValueSafe()` can return values up to `Integer.MAX_VALUE`, so `new byte[len][]` (an object-reference array, 4–8 bytes per element) can request several gigabytes of heap in a single call, executed synchronously in `Program.callToPrecompiledAddress`, which invokes `contract.execute(data)` with no surrounding try/catch for `Error`/`OutOfMemoryError`: [4](#0-3) 

This mirrors the GHSA-3mm4-w7v6-4rhv root cause: a length field taken from untrusted input is used for allocation before it is bounded, causing memory exhaustion/denial of service — here reachable by any account issuing a plain `CALL`/`triggercontract` to the precompile address with crafted `bytes[]` array-length words, i.e., a single signed transaction from an unprivileged broadcaster.

### Impact Explanation
A crafted transaction calling the `ValidateMultiSign`/`BatchValidateSign` precompile with a huge encoded array-length word can force the node's TVM execution thread to attempt a multi-gigabyte array allocation, throwing `OutOfMemoryError`. Because this happens outside any `try/catch(Throwable)` in `Program.callToPrecompiledAddress`, and `OutOfMemoryError` is not a normal `RuntimeException`, it can propagate up through transaction processing and destabilize/crash the node process handling the block/transaction (denial of service against the full node), rather than being cleanly reverted as a failed transaction.

### Likelihood Explanation
Reachable from any unprivileged transaction sender able to broadcast a TriggerSmartContract transaction that performs a `CALL` to the fixed precompile address `0x...9`/`0x...a` with hand-crafted calldata (no special permission, deployed contract, or governance action is required — a plain contract can invoke the precompile directly). The only gating factor is whether `VMConfig.allowTvmSelfdestructRestriction()` (a chain-parameter-controlled hard-fork flag, `ALLOW_TVM_SELFDESTRUCT_RESTRICTION`) is currently activated on the target network; I was unable to confirm from the index whether this flag is enabled by default on current mainnet/testnet configurations. If it is not active, this bug is fully exploitable today; if active, the vulnerable branch (`extractBytesArray`) is unreachable and only the bounded `extractSigArray` path is used.

### Recommendation
- Enforce a hard upper bound (e.g., `MAX_SIZE`) on the decoded array length in `extractBytesArray`/`extractBytes32Array` unconditionally, not only when `allowTvmSelfdestructRestriction()` is enabled.
- Reject calldata where the decoded length is negative, absurdly large, or inconsistent with the remaining data size, before any allocation (similar to `isValidAbiEncoding`).
- Wrap precompile `execute()` invocation in `Program.callToPrecompiledAddress` to defensively catch `OutOfMemoryError`/`Throwable` and convert it into a normal TVM execution failure rather than letting it propagate.

### Proof of Concept
1. Craft a TriggerSmartContract transaction whose contract performs a `CALL` (energy sufficient to pass the precompile's `getEnergyForData` check) to precompile address `0x...a` (`ValidateMultiSign`) with calldata encoding a `bytes[]` array whose length word (`words[3]`-referenced count) is set to a very large integer (e.g., `0x7FFFFFFF`).
2. On a node where `allowTvmSelfdestructRestriction` is not active, `ValidateMultiSign.execute` calls `extractBytesArray(words, offset, rawData)` with `len = 0x7FFFFFFF`, triggering `new byte[len][]` and an `OutOfMemoryError` during transaction execution.
3. Because `Program.callToPrecompiledAddress` (`actuator/src/main/java/org/tron/core/vm/program/Program.java:1734-1766`) does not catch `Error`, the exception can propagate outside normal TVM revert handling, destabilizing the node processing the transaction/block.

    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];

      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
