This confirms the mechanics: for CREATE2/CREATE1-derived contract addresses (which are 20-byte H160 values with no `0xEE` suffix), `to_account_id` first checks `OriginalAccount` and falls back to `to_fallback_account_id`, which is a purely stateless function of the address bytes alone — it carries no notion of which contract "incarnation" currently occupies that address [1](#0-0) . Since `pallet_assets`' precompile keys allowances by this mapped `AccountId` [2](#0-1) , the allowance is bound to the address, not to any specific contract deployment/generation. `ContractInfo::new` only rejects reuse of an address that is *currently* a live contract or has pending deposit-cleanup rows — it performs no cross-pallet sweep of `pallet_assets::Approvals` [3](#0-2) . `do_terminate` (invoked by `SELFDESTRUCT` via `terminate_if_same_tx`) only clears `ContractInfoOf`/`AccountInfoOf`/`ImmutableDataOf` for the contract and refunds/transfers native balance — it never inspects or clears other pallets' storage keyed by the mapped `AccountId` [4](#0-3) . This validates the reported exploit chain end-to-end: precompute a `CREATE2` address, occupy it with a throwaway contract, `approve()` a spender from that address, `SELFDESTRUCT` in the same tx, let the legitimate factory redeploy to the freed address (allowed since `is_contract` check now passes), and drain assets deposited there via the stale `transferFrom` allowance.

Audit Report

## Title
Pre-funded/pre-approved CREATE2 address state survives contract termination and is inherited by the next legitimate deployment, enabling asset drain - (File: `substrate/frame/assets/precompiles/src/lib.rs`)

## Summary
`pallet-revive` derives deterministic contract addresses via `address::create2`/`create1`, and only guards address reuse against a currently-live contract or pending deposit-cleanup rows, never against other pallets' state keyed by the address's mapped `AccountId`. An ERC-20 allowance set via the `pallet-assets` precompile's `approve()` is keyed by `AddressMapper::to_account_id(&owner)`, which for contract addresses resolves to the stateless, address-derived `to_fallback_account_id`; this allowance survives `SELFDESTRUCT`/`do_terminate` and is inherited by whatever contract is later deployed to the same deterministic address, letting an attacker later drain that contract's assets via `transferFrom`.

## Finding Description
An attacker precomputes a factory's future `CREATE2` pool address from public inputs (`deployer`, init code, `salt`) using the same formula exercised by `create2_works` [5](#0-4) . The attacker deploys a throwaway contract to that exact address first; `ContractInfo::new` only rejects the deployment if the address `is_contract` right now or has unflushed `NativeDepositOf` rows — it does not "reserve" the address against future collision [3](#0-2) . From the throwaway contract the attacker calls the ERC-20 precompile's `approve()`, which writes `pallet_assets::Approvals` keyed by `AddressMapper::to_account_id(&owner)` where `owner` is the throwaway contract's own address [2](#0-1) . In the same transaction the attacker triggers `SELFDESTRUCT`, dispatching to `do_terminate`, which removes `ContractInfoOf`/`AccountInfoOf`/`ImmutableDataOf` for the address and refunds deposits, but never touches `pallet_assets::Approvals` in the other pallet [4](#0-3) . The mapped `AccountId` for that address is derived purely from the address bytes via the stateless `to_fallback_account_id` (`0xEE`-prefixed byte copy), carrying no per-deployment "generation" marker [1](#0-0) . When the legitimate factory later deploys the real contract to the same address, `ContractInfo::new`'s `is_contract` check now passes (nothing is a live contract there), so the deployment succeeds and inherits the stale allowance. The attacker then calls `transferFrom`, which resolves `from`/`spender` via the same `AddressMapper::to_account_id` and calls `do_transfer_approved` using the surviving `Approvals` entry, draining the newly deposited assets [6](#0-5) .

## Impact Explanation
This breaks the required invariant that "assets... must conserve value and settle exactly once to the rightful beneficiary": funds deposited into a legitimately deployed contract at a deterministic address can be stolen via an allowance set by a prior, unrelated occupant of that same address. This is a theft-of-asset-balance impact directly against `pallet_assets::Approvals`/allowance state exposed through the ERC-20 precompile atop `pallet-revive`.

## Likelihood Explanation
The attack requires no hash collision, no privileged role, no leaked keys, and no compromised infrastructure — only public knowledge of a factory's deployer address, init code, and salt (which factory patterns routinely publish), plus the ability to submit ordinary `instantiate_with_code`, `approve`, `SELFDESTRUCT`, and `transferFrom` calls, all of which are unprivileged public dispatchables/precompile entry points already present and tested in the repository.

## Recommendation
When a contract terminates (`do_terminate`/`terminate_if_same_tx`), sweep or cancel outstanding `pallet_assets::Approvals` (and any other pallet-level "owner" state keyed by the address's mapped `AccountId`) for that address before it becomes reusable, or introduce a per-address incarnation/generation counter mixed into the approval key or into `AddressMapper::to_account_id` derivation so that state set under generation N cannot be read or spent by a contract deployed as generation N+1 at the same address.

## Proof of Concept
1. Precompute `pool_addr = create2(factory_addr, pool_code, [], salt)` using `address::create2`.
2. Attacker deploys `AttackContract` to `pool_addr` first via `instantiate_with_code` (succeeds since `is_contract` is false).
3. `AttackContract` calls the ERC-20 precompile `approve(attackerSpender, type(uint256).max)`, then executes `SELFDESTRUCT` in the same transaction.
4. Confirm `pallet_assets::Allowance` for `AddressMapper::to_account_id(pool_addr) -> attackerSpender` remains `u128::MAX` and `AccountInfo::is_contract(&pool_addr)` is `false`.
5. Factory deploys the real `Pool` contract to `pool_addr`; users deposit assets.
6. Attacker calls `transferFrom(pool_addr, attacker, balance)` via the precompile using the pre-set allowance, draining the pool.
