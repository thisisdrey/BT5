## Title
Missing validation against the null/zero address in `AccountPermissionUpdateActuator` allows an account owner to permanently lock itself out of its Owner/Active/Witness permissions - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
The reported bug class is a privileged-role-update function (`updateTokenRoleAdmin`) that accepts an arbitrary address, including `address(0)`, and stores it without validation, permanently and irrecoverably losing that admin role. The closest reachable analog in java-tron is `AccountPermissionUpdateContract`, processed by `AccountPermissionUpdateActuator`, which lets any account owner replace its Owner/Active/Witness permission keys in a single signed transaction. The address-format check used for every key in the new permission, `DecodeUtil.addressValid`, only validates length and the network prefix byte — it never rejects the all-zero (unusable/"burn") address body.

### Finding Description
`AccountPermissionUpdateActuator.validate()` calls `checkPermission()` on the submitted Owner, Witness, and Active permissions, which validates key count, threshold, weight sum and address *format* via: [1](#0-0) 
The only address check performed is `DecodeUtil.addressValid`, which merely checks the length (21 bytes) and that the first byte equals the network prefix (`0x41` on mainnet) — it does not check whether the remaining 20 bytes are all zero or otherwise correspond to an address with no known private key: [2](#0-1) 
Because of this, an account owner can submit an `AccountPermissionUpdateContract` whose Owner permission (and/or Active/Witness permissions) contain only such an unusable address as the sole key (or with sufficient weight to meet the threshold), and the actuator will accept it and overwrite the account's permissions in `execute()`: [3](#0-2) 
Once persisted, the account's Owner permission (and consequently any dependent permission, since further `AccountPermissionUpdateContract`s themselves require Owner-permission signatures to execute) can never be updated again, mirroring the "irrecoverable admin loss" impact described in the reference report.

### Impact Explanation
Losing the Owner permission key to an unusable address permanently and irreversibly strips the account owner's ability to manage its own Active/Witness permissions or to ever again change its Owner permission, since any future `AccountPermissionUpdateContract` requires a valid signature meeting the (now unreachable) Owner threshold. This causes permanent freezing of the account's administrative control and any assets/authorities gated behind that account's owner-permission signature (e.g., multisig-controlled contracts or funds requiring the account's Active permission set by the same Owner key), consistent with the "permanent freezing of funds" impact category.

### Likelihood Explanation
This requires the account owner (a legitimate signer of the account) to submit a single crafted or mistaken `AccountPermissionUpdateContract`; no attacker privilege beyond ordinary transaction broadcasting to one's own account is needed. Given `checkPermission` already performs several defensive checks (key count, weight, threshold, distinctness) but omits a zero/burn-address check, this is a plausible operator/tooling error, matching the "human error, irrecoverable" scenario emphasized in the source report.

### Recommendation
Extend `DecodeUtil.addressValid` (or add a dedicated check inside `AccountPermissionUpdateActuator.checkPermission`) to reject keys whose address body is the all-zero value (i.e., equal to the network prefix byte followed by 20 zero bytes), preventing an Owner/Active/Witness permission from being set exclusively to an unusable address.

### Proof of Concept
1. Account `A` holds funds and has default Owner/Active permissions.
2. `A` (or tooling acting on `A`'s behalf) builds an `AccountPermissionUpdateContract` with `owner` permission containing a single key: address `41` + 20 zero bytes, `weight = 1`, `threshold = 1`.
3. `AccountPermissionUpdateActuator.validate()` passes because `DecodeUtil.addressValid` only checks length/prefix (`common/src/main/java/org/tron/common/utils/DecodeUtil.java:15-33`), and all other `checkPermission` checks (count, weight>0, threshold>0, weightSum>=threshold) pass trivially.
4. `execute()` calls `account.updatePermissions(...)` and persists the new Owner permission (`actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java:47-52`).
5. Account `A` can never again produce a valid signature satisfying the new Owner permission, permanently freezing its ability to update permissions or perform any operation gated by the Owner permission.
