### Title
Native-token deposits can be stranded when the selected registered pool has no native-token deposit token - (File: contracts/NativeTokenGateway.sol)

### Summary

`NativeTokenGateway.deposit` wraps the caller's native asset before checking that the selected registered pool actually supports the wrapped token as collateral. If `pool_.depositTokenOf(nativeToken)` returns `address(0)`, the approval and subsequent deposit-token call can succeed as no-ops, leaving the wrapped native asset locked in the gateway while minting no deposit tokens to the caller.

### Finding Description

The `deposit` function validates only that `pool_` is registered in `PoolRegistry`, then executes:

- `nativeToken.deposit{value: msg.value}()`
- `IDepositToken _depositToken = pool_.depositTokenOf(nativeToken)`
- approvals to `_depositToken`
- `_depositToken.deposit(msg.value, _msgSender())`

There is no `DepositTokenDoesNotExist`, `doesDepositTokenExist`, or non-zero-address check on `_depositToken`.

For a registered pool that does not contain a `DepositToken` for `nativeToken`, the `depositTokenOf` mapping returns `address(0)`. Approving the zero address in WETH succeeds. In Solidity, a high-level function call to `address(0)` also succeeds with empty return data. Consequently, the transaction completes, ETH has been converted to WETH inside the gateway, no deposit-token balance is minted, and the user has no public withdrawal path because the gateway never received a deposit-token position.

The issue is particularly relevant because `pool_` is caller-selected and the registry check only proves that the address is a pool, not that it supports the gateway's native token.

### Impact Explanation

Users can permanently lose access to deposited native assets unless governance uses `sweep` to rescue them. The funds remain in `NativeTokenGateway` as wrapped native tokens while the user receives no claimable collateral position.

This meets the same loss pattern as the reported issue: funds are forwarded or converted before the protocol verifies that the downstream component exists and can actually process the operation. There is no destination-contract return value or post-deposit invariant check that would cause the transaction to revert.

### Likelihood Explanation

The vulnerable call is public and unprivileged. It requires the caller to select a registered pool whose `depositTokenOf(nativeToken)` mapping is unset. That can occur through user error, stale UI/routing data, or malicious transaction construction. No malicious governor, keeper, oracle, bridge endpoint, or privileged actor is required.

The deployed gateway relies on `PoolRegistry.isPoolRegistered`, while collateral support is represented separately by each pool's `depositTokenOf` mapping. Therefore, pool registration alone is insufficient validation for this function.

### Recommendation

Before wrapping or accepting the native asset, resolve and validate the deposit token:

```solidity
IDepositToken _depositToken = pool_.depositTokenOf(nativeToken);
if (address(_depositToken) == address(0) || !pool_.doesDepositTokenExist(_depositToken)) {
    revert DepositTokenDoesNotExist();
}
```

Alternatively, expose a pool/registry method that atomically validates that a registered pool supports a specific underlying asset.

As an additional safety check, compare the deposit-token balance minted to the caller or verify that `_depositToken.deposit` returns the expected deposited amount. Revert if it does not.

### Proof of Concept

The following Hardhat-style sequence demonstrates the state transition using production `PoolRegistry`, `Pool`, and `NativeTokenGateway` logic. The important condition is that the selected pool is registered but has no deposit token for the wrapped native token.

```typescript
it("strands native tokens when the pool has no native-token deposit token", async () => {
  const [user, governor] = await ethers.getSigners();

  // Deploy the wrapped-native token and protocol contracts.
  const WETH = await ethers.getContractFactory("WETHMock");
  const weth = await WETH.deploy();

  const PoolRegistry = await ethers.getContractFactory("PoolRegistry");
  const registry = await upgrades.deployProxy(
    PoolRegistry,
    [oracleAddress, governor.address]
  );

  const Pool = await ethers.getContractFactory("Pool");
  const pool = await upgrades.deployProxy(Pool, [registry.address]);

  await registry.connect(governor).registerPool(pool.address);

  const Gateway = await ethers.getContractFactory("NativeTokenGateway");
  const gateway = await Gateway.deploy(registry.address, weth.address);

  const amount = ethers.parseEther("1");

  // The mapping exists but is unset because this registered pool does not
  // support WETH/nativeToken as collateral.
  expect(await pool.depositTokenOf(weth.address)).to.equal(ethers.ZeroAddress);

  await gateway.connect(user).deposit(pool.address, { value: amount });

  // ETH was wrapped and moved into the gateway.
  expect(await weth.balanceOf(gateway.address)).to.equal(amount);

  // No deposit token exists, so the user received no withdrawable position.
  expect(await pool.depositTokenOf(weth.address)).to.equal(ethers.ZeroAddress);
  expect(await ethers.provider.getBalance(gateway.address)).to.equal(0);
});
```

On a fork test, the same condition can be checked directly by iterating `PoolRegistry.getPools()` and selecting any registered pool for which `depositTokenOf(nativeToken) == address(0)`, then calling `NativeTokenGateway.deposit(pool, { value: amount })`.
