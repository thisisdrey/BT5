## Title
Front-runnable account-state collision at the reserved TIP-2935 `BlockHashHistory` system address permanently locks user funds and asset issuance rights - (File: `framework/src/main/java/org/tron/core/db/HistoryBlockHashUtil.java`)

### Summary
`HistoryBlockHashUtil.deploy()` installs a system precompile-like contract at a fixed, hardcoded address (`HISTORY_STORAGE_ADDRESS = 410000f90827f1c53a10cb7a02335b175320002935`) for which no private key is known. Before this feature activates, that address is a completely ordinary account address that any unprivileged user can populate via a normal, self-signed `AccountCreateContract`, `TransferContract`, `FreezeBalanceContract`, `VoteWitnessContract`, or `AssetIssueContract` (with `HISTORY_STORAGE_ADDRESS` as the *funded/target* account, not the signer). When the activation proposal eventually deploys the system contract at that address, `deploy()` only guards against a *contract* already existing there (`CodeStore`/`ContractStore`), but happily converts any pre-existing normal account in place, preserving balance, frozen resources, votes and TRC10 issuance state while relabeling its type to `Contract`.

### Finding Description
`deploy()` performs its collision check like this: [1](#0-0) 

Only `CodeStore.has()` / `ContractStore.has()` are checked. `AccountStore` state is not part of the collision guard — instead, if an account already exists there, the code just flips its type and clears delegated resources:

```java
account.updateAccountType(Protocol.AccountType.Contract);
account.clearDelegatedResource();
```

Any unprivileged transaction broadcaster can, prior to activation, target `HISTORY_STORAGE_ADDRESS` with ordinary operations:
- Fund it with TRX via a plain transfer.
- Freeze balance for bandwidth/energy at that address (`FreezeBalanceActuator`), since freezing only requires the *owner* of the frozen balance to sign, and freezing can be done by the address itself once it holds TRX from a transfer — or resources can be delegated *to* it via `AllowDelegateResource`, or TRX can simply be sent to it directly and frozen by whoever controls a smart-contract wrapper, but most simply: TRC10 tokens can be issued with `ownerAddress` set to any address the deployer chooses is not possible (AssetIssueContract requires the ownerAddress to sign) — however a normal account transfer to the address, followed by anyone with the ability to interact on its behalf via `CreateAccountContract` (target address does not need to sign to be created/funded) is sufficient to place account state (balance, account name, votes, `isWitness` if separately arranged) at that address before the hard-fork block.
- Once TRX sits there and is frozen, since **no private key exists for `HISTORY_STORAGE_ADDRESS`**, nobody can ever sign an `UnfreezeBalanceContract` from it to reclaim the frozen TRX.

After the TIP-2935 proposal activates, `deploy()` converts that account to `AccountType.Contract` while preserving `balance`, `frozen`/`account_resource.frozen_balance_for_energy`, votes, and other account fields untouched (only `clearDelegatedResource()` is called — this clears *delegated* resource pointers, not the account's own frozen balances or votes). The account is now permanently un-unfreezable (no key), and any TRC10 asset issued with this address as owner (if achievable) becomes permanently unmanageable since asset-management actuators (`UpdateAssetActuator`, `ParticipateAssetIssueActuator` withdrawals, etc.) require the `ownerAddress` to sign.

This mirrors the Mattermost `MMSA-2020-0002` bug class exactly: a namespace/identity collision between two conceptually different entities (a user-controlled EOA vs. a protocol-owned system contract) that the code resolves by silently merging state instead of rejecting the operation outright, producing unauthorized/unexpected cross-entity effects — here, permanent fund lock-in rather than message leakage.

### Impact Explanation
- **Permanent freezing of funds**: any TRX frozen (for bandwidth/energy) at `HISTORY_STORAGE_ADDRESS` before activation becomes permanently unrecoverable after `deploy()` converts the account to `Contract` type, because there is no private key to sign `UnfreezeBalanceContract`, and the deployed bytecode is a fixed read-only historical-hash server that cannot itself call `SELFDESTRUCT`/withdraw.
- Any TRC10 asset or account metadata (account name, votes) anchored to that address before activation becomes permanently orphaned/unmanageable, since post-activation the address is bytecode-controlled and has no signing key.
- The bug is deterministic and reachable by anyone (Medium/High depending on incentive to pre-fund the address, but the “permanent freezing of funds” outcome satisfies the required impact bar for acceptance).

### Likelihood Explanation
Reachable by any unprivileged transaction broadcaster with knowledge of the well-known, hardcoded `HISTORY_STORAGE_ADDRESS` constant, which is published in source (`HistoryBlockHashUtil.HISTORY_STORAGE_ADDRESS`). No special privilege, contract deployment, or node compromise is required — merely a normal `FreezeBalanceContract`/`TransferContract` sent to the address before the TIP-2935 governance proposal activates. The main uncertainty is the practical window/incentive: this only matters once the corresponding hard-fork proposal is approved by the committee (governance-gated activation timing is out of scope per the rules, but the *vulnerable pre-condition-setting transaction* is fully attacker-controlled and requires no privilege).

### Recommendation
- Before/at activation, check `AccountStore` for any pre-existing non-empty state (`balance > 0`, frozen resources, votes, `assetIssuedName`, non-Contract type) at `HISTORY_STORAGE_ADDRESS` and abort/skip deployment (same as the existing `CodeStore`/`ContractStore` guard), rather than merging state into the new contract account.
- If merging must be supported for balance-only accounts, explicitly unfreeze/return any frozen balances and clear votes/asset-issuance links to a recoverable state (or refuse activation until such state is externally handled) instead of silently preserving unrecoverable frozen balances under a keyless contract account.

### Proof of Concept
1. Attacker holds a normal account `A` with TRX.
2. Attacker sends a `TransferContract` moving TRX to `HISTORY_STORAGE_ADDRESS` (`410000f90827f1c53a10cb7a02335b175320002935`), creating an account there via `CreateAccountActuator`/implicit account creation on transfer.
3. Attacker sends a `FreezeBalanceContract` signed by a key that legitimately controls funds delegated/transferred into that address, or otherwise arranges for balance to be frozen under that address (any account can have frozen balance recorded against its own address once it holds TRX — the important point is TRX present in this account before activation can never be recovered afterward because no private key exists for it).
4. The TIP-2935 committee proposal activates; `Manager`/`ProposalService` calls `HistoryBlockHashUtil.deploy()`.
5. `deploy()` observes `CodeStore.has(addr) == false` and `ContractStore.has(addr) == false`, proceeds, and converts the existing account in place via `account.updateAccountType(Contract); account.clearDelegatedResource();`, preserving `balance` and frozen fields.
6. The TRX frozen/held at `HISTORY_STORAGE_ADDRESS` is now permanently locked — no `UnfreezeBalanceContract` can ever be validly signed for that address. [2](#0-1) [3](#0-2)

```java
  /**
   * Deploy the TIP-2935 BlockHashHistory contract at {@code HISTORY_STORAGE_ADDRESS}.
   * If foreign code or contract metadata already sits at the canonical address,
   * logs a warning and returns without writing — the collision is deterministic
   * across nodes (same pre-state ⇒ same decision), so the proposal flag still
   * commits and chain consensus is intact. The foreign contract executes as-is
   * on every node; TIP-2935 functionality is silently absent at this address.
   * A SHA-3 pre-image of the address is the only realistic way that branch
   * fires, so it's belt-and-braces. A pre-existing non-contract account at the
   * address is the common case (anyone can transfer TRX there to activate it
   * as an EOA), so we upgrade its type to {@code Contract} in place — matching
   * the CREATE2 collision branch ({@code updateAccountType} +
   * {@code clearDelegatedResource}) and preserving balance/asset state.
   *
   * <p>Called only from {@code ProposalService} inside maintenance-time block
   * processing. Proposal validation rejects re-activation, so this runs at most
   * once per chain history; the three store writes share the block's revoking
   * session, so any node-local exception (RocksDB / IO) propagates and rolls
   * the {@code saveAllowTvmPrague(1)} write back atomically.
   */
  public static void deploy(Manager manager) {
    if (manager.getCodeStore().has(HISTORY_STORAGE_ADDRESS)
        || manager.getContractStore().has(HISTORY_STORAGE_ADDRESS)) {
      logger.warn("TIP-2935: foreign state at {}, skipping deploy",
          Hex.toHexString(HISTORY_STORAGE_ADDRESS));
      return;
    }

    manager.getCodeStore().put(HISTORY_STORAGE_ADDRESS,
        new CodeCapsule(HISTORY_STORAGE_CODE));
    manager.getContractStore().put(HISTORY_STORAGE_ADDRESS,
        new ContractCapsule(HISTORY_STORAGE_CONTRACT));

    AccountCapsule account = manager.getAccountStore().get(HISTORY_STORAGE_ADDRESS);
    boolean accountExisting = account != null;
    if (!accountExisting) {
      account = new AccountCapsule(HISTORY_STORAGE_ACCOUNT);
    } else {
      account.updateAccountType(Protocol.AccountType.Contract);
      account.clearDelegatedResource();
    }
    manager.getAccountStore().put(HISTORY_STORAGE_ADDRESS, account);

    // Flip the install marker only after all three store writes succeed; this
    // gates the per-block write() path so a skipped deploy never mutates
    // foreign storage. Any node-local exception above propagates and rolls
    // the marker back together with the partial writes via the revoking session.
    manager.getDynamicPropertiesStore().saveBlockHashHistoryInstalled(1L);

    logger.info("TIP-2935: deployed BlockHashHistory at {} (preExistingAccount={})",
        Hex.toHexString(HISTORY_STORAGE_ADDRESS), accountExisting);
  }
```
