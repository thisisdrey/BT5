### Title
Missing-checksum artifacts silently downloaded without integrity verification when building the Bzlmod repository-cache tarball - (File: src/tools/bzlmod/utils.bzl, distdir.bzl)

### Summary
`parse_http_artifacts` in `src/tools/bzlmod/utils.bzl` and the consuming `_repo_cache_tar_impl` in `distdir.bzl` are supposed to enforce that every archive URL pulled from a `MODULE.bazel.lock` file has a pinned `sha256` or `integrity` checksum before it is downloaded and embedded into a distributable, content-addressable repository-cache tarball. For repos generated by module extensions (`generatedRepoSpecs`), the checksum-presence check is done on dictionary *key presence* rather than on the checksum *value*, so an artifact with no declared checksum still causes the code to take the "verified" branch and download the URL with no integrity constraint at all — silently bypassing the explicit `fail()` safety net that exists specifically to prevent this.

### Finding Description
In `parse_http_artifacts` (`src/tools/bzlmod/utils.bzl:113-117`), artifacts synthesized from a module extension's `generatedRepoSpecs` are appended unconditionally with both keys present: [1](#0-0) 

If the underlying `http_archive`/`http_file`/`http_jar` attributes lack both `sha256` and `integrity` (a state Bazel explicitly allows and documents as "a security risk... makes your build non-hermetic"), this still produces `{"sha256": None, "integrity": None, "url": ...}`.

That dict is then consumed by `_repo_cache_tar_impl` in `distdir.bzl`: [2](#0-1) 

The check `if "integrity" in artifact:` (line 55) tests key membership, not truthiness. Since the key is always present (even when its value is `None`), the branch is taken, and `ctx.download(url, "./tempfile", executable = False, integrity = integrity)` is invoked with `integrity = None` at line 64 — i.e., no checksum constraint is passed to `repository_ctx.download`, and whatever bytes the origin server returns are accepted as ground truth. The tool then computes `checksum.sha256` from the *downloaded* (unverified) content and treats that as the trusted key under which the artifact is stored in the tarball (`content_addressable/sha256/<self-computed-hash>/file`). The `fail("Could not find integrity or sha256 hash for artifact %s" % url)` at line 78 — the intended guardrail for exactly this missing-checksum scenario — is never reached for these artifacts, because control flow already exited the loop iteration inside the `integrity` branch (`continue` at line 59) or fell through the `sha256` branch after `artifact["sha256"]` was set from the unverified download (line 66), so the `else: fail(...)` is unreachable for this class of artifact.

This code path is reachable via `repo_cache_tar` (defined in `distdir.bzl`, used from `extensions.bzl`), which builds a repository cache tarball from a lockfile plus a list of required repo names — i.e., it processes attacker-influenced data (whatever module extensions and registries produced in the lockfile / registry source.json for the given module graph) without requiring the operator to notice that a particular generated repo has no pinned checksum.

### Impact Explanation
The `repo_cache_tar` rule is intended to produce a `--repository_cache`-style tarball used to enable offline/airgapped, hermetic builds; consumers rely on the sha256-keyed layout to guarantee that any file served from the cache is exactly the bytes originally referenced. For any `generatedRepoSpecs` entry that omits both `sha256` and `integrity` (permitted by `http_archive`/`http_file`/`http_jar`), the tool fetches the URL with zero integrity checking and blindly trusts the response, rather than failing loudly as its own `else: fail(...)` branch was designed to do. A host serving that URL at cache-build time (a compromised mirror, a hijacked domain, or any origin whose content later changes) can inject arbitrary bytes into the produced offline cache under a hash of the attacker's own choosing, with no error raised to the operator building the cache. This defeats the explicit hermeticity/integrity guarantee the `fail()` check exists to enforce and can propagate unverified, attacker-controlled artifacts into a cache artifact that is subsequently distributed and trusted by other builds.

### Likelihood Explanation
Reaching this requires only that some module extension in the dependency graph produce a `generatedRepoSpecs` entry for an `http_archive`/`http_file`/`http_jar` without a `sha256`/`integrity` attribute — a state Bazel's own documentation acknowledges as common during development and not enforced by the framework. No privileged access, MITM, or credential compromise is needed beyond controlling/serving content at the referenced URL at the moment `repo_cache_tar` is evaluated, which matches the "hostile origin server" premise where a declared checksum should have stopped it. The likelihood of the *safety-net logic itself* firing incorrectly is deterministic (a plain Starlark `dict` key-presence bug), so whenever an unpinned artifact is present in the lockfile, the bypass is guaranteed to trigger rather than being probabilistic.

### Recommendation
Change the checks in `distdir.bzl`'s `_repo_cache_tar_impl` (and ideally the construction in `parse_http_artifacts`) to test the checksum *value*, not key presence, e.g. `if artifact.get("integrity"):` and `if artifact.get("sha256"):`, and only append a checksum key when it has an actual non-`None` value. This restores reachability of the existing `fail("Could not find integrity or sha256 hash for artifact %s" % url)` branch for artifacts lacking a pinned checksum, ensuring `repo_cache_tar` never downloads unverified content into the distributable cache.

### Proof of Concept
1. Configure a `MODULE.bazel` module extension whose `generatedRepoSpecs` include an `http_archive` repo with a `url` pointing at an attacker-controlled/one-time HTTP server and no `sha256`/`integrity` attribute (this is valid per `http_archive`'s optional checksum attributes).
2. Run `bazel mod deps --lockfile_mode=update` (or equivalent) to produce a `MODULE.bazel.lock` containing this `generatedRepoSpecs` entry with no `sha256`/`integrity`.
3. Invoke the `repo_cache_tar` repository rule (`distdir.bzl`) with `lockfiles` pointing at this lockfile and `repos` including the affected repo name.
4. Observe that `_repo_cache_tar_impl` proceeds to call `ctx.download(url, "./tempfile", executable = False, integrity = None)` and successfully builds the cache tarball, embedding whatever content the attacker's server returned under a self-computed sha256 — instead of Bazel raising `fail("Could not find integrity or sha256 hash for artifact %s" % url)`.
5. A `BuildIntegrationTestCase`/`src/test/shell/bazel` regression test can assert that building `repo_cache_tar` over a lockfile containing a checksum-less `generatedRepoSpecs` entry fails with the expected error message, and currently does not.
