Audit Report

## Title
Snowbridge `PayAccountOnLocation::pay_reward` marks relayer rewards as claimed based on local XCM delivery success, not remote settlement, causing permanent loss of reward funds - ([File: bridges/snowbridge/primitives/core/src/reward.rs])

## Summary
`PayAccountOnLocation::pay_reward` returns `Ok(())` as soon as the reward-mint XCM is validated, fee-charged, and handed to `XcmSender::deliver` for local outbound queuing to AssetHub — it never waits for or checks confirmation that the remote `DepositAsset` instruction actually executed and credited the beneficiary. `pallet_bridge_relayers::do_claim_rewards` treats this `Ok(())` as final: it has already removed the `RelayerRewards` entry via `maybe_reward.take()` before calling `pay_reward`, and commits that removal plus a `RewardPaid` event once `pay_reward` succeeds, with no mechanism to detect or recover from a remote-side execution failure.

## Finding Description
In `bridges/snowbridge/primitives/core/src/reward.rs`, `PayAccountOnLocation::pay_reward` builds an `UnpaidExecution` XCM with `DescendOrigin`, `UniversalOrigin`, `ReserveAssetDeposited`, and `DepositAsset`, then performs three purely local operations — `validate_send`, `XcmExecutor::charge_fees`, and `XcmSender::deliver` — before unconditionally returning `Ok(())`: [1](#0-0) . `SendXcm::deliver` only guarantees local transport acceptance (e.g. into the HRMP outbound queue); because the XCM uses `UnpaidExecution` rather than a receipt/query-based mechanism, there is no signal returned to BridgeHub if AssetHub's execution of `DepositAsset` later fails.

The caller, `Pallet::do_claim_rewards` in `bridges/modules/relayers/src/lib.rs`, calls `maybe_reward.take()` to remove the pending reward from storage, then calls `T::PaymentProcedure::pay_reward(...)`, and if that returns `Ok`, emits `Event::RewardPaid` and returns `Ok(())` from the `try_mutate_exists` closure, which commits the removal: [2](#0-1) . There is no callback, receipt tracking, or retry path if the remote `DepositAsset` fails after delivery.

This contrasts with the codebase's own safer established pattern for XCM-based payouts, `PayOverXcm` in `polkadot/xcm/xcm-builder/src/pay.rs`, which is explicitly documented as asynchronous and returns a `QueryId` used later via `check_payment` to confirm remote payment status before considering settlement final: [3](#0-2) . `PayAccountOnLocation` implements no equivalent confirmation step.

## Impact Explanation
If the remote `DepositAsset` execution on AssetHub fails after the message is locally delivered (e.g., beneficiary location filtered/unsupported, reserve-asset trust/registration mismatch for the given `EthereumNetwork`, or insufficient remote weight), the relayer's reward is permanently lost: `RelayerRewards` has already been deleted and `RewardPaid` emitted on BridgeHub, so a subsequent `claim_rewards_to` call for the same reward fails with `Error::<T, I>::NoRewardForRelayer`. This is a duplicate-settlement/permanent-fund-loss scenario — BridgeHub's ledger discharges its obligation while AssetHub never delivers the corresponding value to the beneficiary.

## Likelihood Explanation
No privileged access is required. Any relayer holding a legitimately accrued reward can call the public `claim_rewards_to` extrinsic with a beneficiary `Location` that is valid enough to pass local `validate_send`/`charge_fees`/`deliver` but causes remote execution to fail on AssetHub (malformed/unsupported beneficiary interior, filtered target, or transient remote-side conditions such as congestion or asset-trust misconfiguration). The existing unit tests in `reward.rs` only cover local failure paths (`pay_reward_fails_on_xcm_validate_xcm`, `pay_reward_fails_on_charge_fees`, `pay_reward_fails_on_delivery`) and do not exercise or guard against a silent remote failure after successful local delivery.

## Recommendation
Do not treat `XcmSender::deliver` success as final settlement for `PayAccountOnLocation`. Adopt a receipt/query-based confirmation flow analogous to `PayOverXcm`'s `QueryId` + `check_payment` pattern (e.g., using `ReportError`/`QueryResponse`) so that the `RelayerRewards` entry is only fully cleared after confirmed remote execution success, keeping the reward in a "pending" state with a retry/reclaim path if no confirmation arrives.

## Proof of Concept
1. Relayer accrues a `BridgeReward::Snowbridge` reward via `register_reward`.
2. Relayer calls `claim_rewards_to(BridgeReward::Snowbridge, BridgeRewardBeneficiaries::AssetHubLocation(loc))` where `loc` passes local validation but is incompatible with remote `DepositAsset` execution (e.g., unsupported/filtered beneficiary or untrusted reserve asset on AssetHub).
3. `PayAccountOnLocation::pay_reward` succeeds through `validate_send`, `charge_fees`, and `deliver`, returning `Ok(())`.
4. `do_claim_rewards` deletes the `RelayerRewards` entry and emits `RewardPaid`.
5. On AssetHub, `DepositAsset` fails; no funds are credited to the relayer.
6. Relayer calls `claim_rewards_to` again for the same reward and receives `Error::<T, I>::NoRewardForRelayer`, confirming permanent, unrecoverable loss of the reward.
