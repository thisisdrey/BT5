### Title
Unvalidated `local_header_offset` in Zip Central Directory allows out-of-bounds read of process memory into the built jar - (File: src/tools/singlejar/input_jar.h)

### Summary
`InputJar::LocalHeader()` computes a pointer into the memory-mapped input jar from the attacker-controlled `local_header_offset` field of a Central Directory Header (CDH), without validating that the resulting address actually lies within the mapped file, mirroring the CVE-2016-7128 pattern where a TIFF thumbnail offset field was trusted without checking it against the actual file size.

### Finding Description
`CDH::local_header_offset()` [1](#0-0)  returns a 32/64-bit value read directly from the untrusted zip's Central Directory (optionally widened via the Zip64 extra field). This value is passed straight into `MappedFile::address()`: [2](#0-1) 

`MappedFile::address()` performs no bounds checking — it simply does pointer arithmetic on `mapped_start_`: [3](#0-2) 

Unlike other offset-derived pointers in the same file, which are explicitly checked with `mapped_file_.mapped(...)` before use (e.g. the Central Directory location check in `LocateCentralDirectory`, and the `NextEntry` bounds check on the next CDH record), the `LH*` pointer returned by `LocalHeader()` is **not** validated before being dereferenced: [4](#0-3) [5](#0-4) 

The unchecked `LH*` is then dereferenced by `NextEntry()` callers (e.g. `OutputJar::AddJar`) to read `lh->size()`, `lh->compressed_file_size()`, and ultimately to copy raw bytes starting at `jar_entry->local_header_offset()` into the output jar: [6](#0-5) 

A crafted (but overall sha256-valid) jar/zip dependency can set `local_header_offset` in its CDH to a value that resolves to an address past the end of the mmap'd region (or, if within bounds but semantically wrong, into unrelated file content). Because Bazel's checksum verification (`sha256`/`integrity`) only guarantees the byte stream matches on disk — it does not constrain that internal offset fields are self-consistent with the file's actual size — this bypasses the "integrity is binding" invariant for internal structure, exactly as in the TIFF CVE where a valid file could still carry an invalid internal offset.

### Impact Explanation
If `local_header_offset` (or `preamble_size_ + local_header_offset`) pushes the computed address past `mapped_end_`, subsequent reads of `lh->signature()`, `lh->file_name_length()`, `lh->compressed_file_size()`, etc. read out-of-bounds/unmapped memory (crash) or adjacent heap/mmap memory beyond the file (info disclosure). Because `OutputJar::AddJar` then copies `num_bytes` starting at that offset directly into the produced `.jar` artifact, out-of-bounds process memory can be embedded into a build output that downstream consumers (developers, CI, artifact stores) can read — a direct analog of "obtain sensitive information from process memory" in the CVE.

### Likelihood Explanation
Requires an attacker to control the bytes of a jar/zip dependency consumed by `singlejar` (e.g., a `java_import`/`http_jar`/`http_archive` supplying a `.jar`), which is the standard supply-chain attacker model in scope here. The attacker does not need to break the sha256/integrity check on the whole artifact — only to craft internal Central Directory fields that are inconsistent with the true file layout, something checksum verification does not protect against.

### Recommendation
Validate the pointer returned from `MappedFile::address()` in `InputJar::LocalHeader()` (and any other CDH-offset-derived pointer) with `mapped_file_.mapped(...)` before dereferencing, similar to the existing checks in `LocateCentralDirectory` and `NextEntry`, and fail/`diag_errx` on out-of-range offsets rather than silently constructing an invalid pointer.

### Proof of Concept
A reproducible test would extend `src/tools/singlejar/zip_headers_test.cc` / `input_jar_scan_entries_test.h` style tests: construct a minimal valid zip (as in `CreateZipWithMalformedExtraField()` in `output_jar_simple_test.cc`, [7](#0-6) ) whose CDH sets `local_header_offset32` to a value large enough that `preamble_size_ + local_header_offset` exceeds `mapped_file_.size()`, then call `InputJar::Open()` + `NextEntry()` and assert it currently returns a dangling `LH*` that gets dereferenced (crash under ASan/UBSan, or `EXPECT_DEATH`) instead of failing gracefully via `mapped_file_.mapped()`.

std::string CreateZipWithMalformedExtraField() {
  std::string zip_data;
  const std::string filename = "evil.bin";

  // 1. Local File Header (LFH)
  size_t lh_offset = zip_data.size();
  size_t lh_size = sizeof(LH) + filename.size();
  zip_data.resize(lh_offset + lh_size, 0);
  auto* lh = reinterpret_cast<LH*>(&zip_data[lh_offset]);
  lh->signature();
  lh->version(10);
  lh->file_name(filename.data(), filename.size());

  // 2. Extra field payload containing an oversized payload_size
  uint8_t ef_buffer[8] = {0};
  auto* ef1 = reinterpret_cast<ExtraField*>(ef_buffer);
  ef1->signature(0x000d);
  ef1->payload_size(0);

  auto* ef2 = reinterpret_cast<ExtraField*>(ef_buffer + ef1->size());
  ef2->signature(0xdead);
  ef2->payload_size(0xf000);  // Malformed size exceeding extra field buffer

  // 3. Central Directory Header (CDH)
  size_t cdh_offset = zip_data.size();
  size_t cdh_size = sizeof(CDH) + filename.size() + sizeof(ef_buffer);
  zip_data.resize(cdh_offset + cdh_size, 0);
  auto* cdh = reinterpret_cast<CDH*>(&zip_data[cdh_offset]);
  cdh->signature();
  cdh->version(20);
  cdh->version_to_extract(10);
  cdh->local_header_offset32(lh_offset);
  cdh->file_name(filename.data(), filename.size());
  cdh->extra_fields(ef_buffer, sizeof(ef_buffer));

  // 4. End of Central Directory (EOCD)
  size_t ecd_offset = zip_data.size();
  zip_data.resize(ecd_offset + sizeof(ECD), 0);
  auto* ecd = reinterpret_cast<ECD*>(&zip_data[ecd_offset]);
  ecd->signature();
  ecd->this_disk_entries16(1);
  ecd->total_entries16(1);
  ecd->cen_size32(cdh_size);
  ecd->cen_offset32(cdh_offset);

  return zip_data;
}
