### Title
Unprivileged attacker can permanently fill a victim's per-account token list via dust deposits, DoS-ing new collateral deposits and synthetic issuance - ([File: contracts/Pool.sol])

### Summary
`Pool` caps each account at `MAX_TOKENS_PER_USER = 30` combined deposit+debt token entries, enforced by `onlyIfAdditionWillNotReachMaxTokens` inside `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` [1](#0-0) [2](#0-1) [3](#0-2) . Anyone can add entries to an arbitrary victim's list because `DepositToken.deposit(amount_, onBehalfOf_)` and `DepositToken.transfer(to_, ...)` mint/send to a recipient without consent, and `_mint`/`_transfer` call `pool.addToDepositTokensOfAccount(recipient)` whenever the recipient's prior balance was zero [4](#0-3) [5](#0-4) [6](#0-5) .

### Finding Description
Analogous to CVE-2019-2755 (a remote availability/DoS bug), an unprivileged attacker griefs a victim's ability to use the protocol:

1. The attacker buys/obtains dust amounts of every underlying collateral token listed in the pool (up to `MAX_TOKENS_PER_USER`, and `addDepositToken` itself caps the pool at 30 deposit tokens [7](#0-6) ).
2. For each `DepositToken`, the attacker calls `deposit(1 wei, victim)` (or deposits then `transfer(victim, dust)`). Each first-time balance triggers `addToDepositTokensOfAccount(victim)`, filling `depositTokensOfAccount[victim]` to 30.
3. From then on, every code path that would add a *new* token to the victim's list reverts with `UserReachedMaxTokens`:
   - `DepositToken.deposit`/`transfer` of any collateral type the victim doesn't already hold (the `_mint`/`_transfer` post-hook reverts the whole tx).
   - `DebtToken.issue`/`mint`/`flashIssue` of any synthetic asset the victim doesn't already owe (`addToDebtTokensOfAccount` reverts).
   - `Pool.liquidate` → `depositToken_.seize(account, liquidator, ...)` also reverts if the *liquidator's* list is full — but more importantly the victim cannot add a new collateral type to rescue an unhealthy position.

The victim can recover by zeroing each dust balance (`withdraw`/`transfer` triggers `removeFromDepositTokensOfAccount` [8](#0-7) ), so it is a *temporary* freeze, but recovery is not free: the victim must hold the underlying or spend gas per dust token, and an attacker can re-fill slots after each removal since dust transfers cost only gas.

### Impact Explanation
Availability impact mirroring the CVE class: a targeted victim is prevented from depositing new collateral types and from issuing new synthetic debt. For a victim approaching liquidation who needs to deposit a *different* collateral (e.g., they hold USDC but their existing position is in msETH), the forced `UserReachedMaxTokens` revert blocks the rescue deposit and lets a liquidator seize their collateral — temporary freezing of funds plus forced liquidation. No privileged role, oracle manipulation, or governance action is required.

### Likelihood Explanation
Reachable by any EOA: `deposit(amount_, onBehalfOf_)` has no access control on the beneficiary, `transfer` is public and only gated by `_revertIfLocked` on the *sender* [9](#0-8) . Cost is dust of each listed underlying plus gas. Modifiers (`whenNotPaused`, `nonReentrant`, `onlyIfDepositTokenExists`) do not prevent it on the deployed configuration. The main limitations are the attacker's need for dust of up to 30 distinct underlyings and the victim's ability to clear entries by zeroing balances.

### Recommendation
Do not count attacker-forced dust balances against the cap. Options:
- Whitelist additions only via `deposit(onBehalfOf_ == _msgSender())` or require an opt-in flag before crediting `onBehalfOf_` deposits.
- Skip `addToDepositTokensOfAccount` for amounts below a minimum deposit threshold.
- Track the list off a "user opted-in" set rather than balance>0, or allow removal/withdrawal of dust without requiring underlying liquidity (e.g., donate dust to feeCollector).

### Proof of Concept
Hardhat/Foundry fork outline (concrete, reproducible):

```solidity
// Pool P has >=1 DepositToken list; assume N deposit tokens total.
address victim = makeAddr("victim");

// 1. Attacker fills victim's list
for (uint i; i < depositTokens.length; ++i) {
    DepositToken dt = DepositToken(depositTokens[i]);
    IERC20 under = dt.underlying();
    deal(address(under), attacker, 1);
    under.approve(address(dt), 1);
    dt.deposit(1, victim); // adds dt to victim's list
}
assertEq(pool.getDepositTokensOfAccount(victim).length, pool.MAX_TOKENS_PER_USER());

// 2. Victim tries to deposit a new collateral type -> reverts
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
newDepositToken.deposit(100e18, victim);

// 3. Victim tries to issue a new synthetic -> reverts in addToDebtTokensOfAccount
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
newDebtToken.issue(1e18, victim);

// 4. Show impact: victim at health boundary cannot add new collateral to rescue;
//    liquidator seizes position via pool.liquidate(...).
```
