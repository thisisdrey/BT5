### Title
Out-of-range panic parsing malicious archive symbol map - ([File: src/cmd/link/internal/ld/ar.go])

### Summary
`readArmap` in the linker's host-archive reader parses the armap (symbol table) of a `.a` archive that is untrusted content (e.g., a static library shipped inside a Go module/cgo dependency and consumed via `go build`). On Darwin/iOS and Windows/386 targets it strips a leading underscore from each symbol name by indexing `name[0]` before checking whether `name` is non-empty, so a crafted archive containing a zero-length symbol name in its armap causes an index-out-of-range panic during linking.

### Finding Description
Attacker input: a malicious/crafted static archive (`.a`) file bundled in a Go module (e.g., a cgo package that embeds a prebuilt library) reaches the linker via `cmd/link/internal/ld.hostArchive` [1](#0-0)  which locates the armap entry (`"/"` or `"/SYM64/"`) and calls `readArmap` [2](#0-1) .

Inside `readArmap`, the symbol-name table is walked by scanning for NUL-terminated strings:
```go
n := 0
for names[n] != 0 {
    n++
}
name := string(names[:n])
names = names[n+1:]

if buildcfg.GOOS == "darwin" || buildcfg.GOOS == "ios" || (buildcfg.GOOS == "windows" && buildcfg.GOARCH == "386") {
    if name[0] == '_' && len(name) > 1 {
        name = name[1:]
    }
}
``` [3](#0-2) 

The check evaluates `name[0]` *before* confirming `len(name) > 0`. If the armap contains a symbol entry whose name is the empty string (i.e., two consecutive NUL bytes at that position in the name table, meaning `names[0] == 0` so `n == 0`), then `name` is `""` and `name[0]` panics with "index out of range [0] with length 0". No bounds/length validation is performed on attacker-controlled archive content before this index, and the surrounding loop (`readArmap`, `hostArchive`) has no recovery for malformed input.

### Impact Explanation
This is a denial-of-service via panic during the build/link step: a victim building a Go module that (directly or via a dependency) links a host archive on `darwin`, `ios`, or `windows/386` will crash the `go build` toolchain if the archive's armap contains a zero-length symbol name. This falls under the "real panic on plausible malicious-input parser" carve-out permitted by Go's security policy, so it would be assessed on the PUBLIC track as a low-severity crasher bug in the linker rather than code execution or data compromise. It does not violate the "go build must not run malicious source" boundary since it is a parsing panic, not execution of attacker code.

### Likelihood Explanation
Reachable in an ordinary `go build`/cgo victim workflow: `hostArchive` is invoked whenever the linker resolves undefined symbols against a host archive such as `libgcc.a`-style libraries bundled with cgo dependencies. An attacker only needs to supply a module/package with a cgo build that pulls in a specially crafted `.a` file (an unprivileged, "published module/archive consumed by a normal victim workflow" scenario) targeting one of the three affected GOOS/GOARCH combinations. No special privileges are required beyond publishing the archive/module.

### Recommendation
Reorder/guard the check to test length first: `if len(name) > 0 && name[0] == '_' && len(name) > 1 { name = name[1:] }` (or simplify to `if len(name) > 1 && name[0] == '_'`). More broadly, validate all size/length-derived offsets in `readArmap`/`nextar` against actual buffer bounds before slicing/indexing, since the whole armap-parsing path trusts the archive's `size`/`c` fields without bounds checks against `contents`.

### Proof of Concept
```go
package ld

import (
	"internal/buildcfg"
	"testing"
	"encoding/binary"
)

// TestReadArmapEmptyName demonstrates the index-out-of-range panic in
// readArmap when the armap name table contains a zero-length name.
func TestReadArmapEmptyName(t *testing.T) {
	oldGOOS := buildcfg.GOOS
	buildcfg.GOOS = "darwin" // trigger the underscore-stripping branch
	defer func() { buildcfg.GOOS = oldGOOS }()

	// Build a minimal 32-bit armap: count=1, one offset word,
	// then the name table starting with a NUL byte (empty name).
	var contents []byte
	countBuf := make([]byte, 4)
	binary.BigEndian.PutUint32(countBuf, 1)
	contents = append(contents, countBuf...) // c = 1
	offBuf := make([]byte, 4)
	binary.BigEndian.PutUint32(offBuf, 0)
	contents = append(contents, offBuf...) // one offset entry
	contents = append(contents, 0x00)      // empty name: names[0] == 0

	defer func() {
		if r := recover(); r == nil {
			t.Fatal("expected panic on empty symbol name, got none")
		}
	}()

	// Directly exercise the vulnerable slicing/indexing logic that
	// readArmap performs on the name table portion of `contents`.
	wordSize := 4
	c := uint64(binary.BigEndian.Uint32(contents))
	rest := contents[wordSize:]
	names := rest[c*uint64(wordSize):]

	n := 0
	for names[n] != 0 {
		n++
	}
	name := string(names[:n]) // name == ""

	if name[0] == '_' && len(name) > 1 { // PANIC: index out of range [0] with length 0
		name = name[1:]
	}
}
```
Expected result: the test panics with `index out of range [0] with length 0` inside the underscore-stripping branch, confirming the crash reachable from `readArmap` in `src/cmd/link/internal/ld/ar.go` when parsing a malicious archive's armap on `darwin`/`ios`/`windows-386`.
