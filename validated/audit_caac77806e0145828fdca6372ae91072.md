Based on the evidence gathered, the closest verified local analog to the "operation depends on arbitrary external code accepting a callback, and if it doesn't, funds get permanently stuck" bug class is in the Asset Hub ERC20 XCM transactor.

### Title
Permanent lock of XCM-bridged assets when the underlying ERC20 contract's `transfer()` callback reverts or exceeds the hardcoded weight budget - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

### Summary
`ERC20Transactor` implements XCM's `TransactAsset` for fungible assets that are backed by arbitrary Solidity ERC20 contracts deployed under `pallet-revive`. Both the withdraw path (`withdraw_asset_with_surplus`) and the deposit path (`deposit_asset_with_surplus`) settle value by performing a mandatory external `bare_call` into the asset's own contract code, invoking `IERC20::transferCall`. There is no accounting fallback that bypasses this external call — settlement of the XCM operation is entirely delegated to arbitrary, permissionlessly-matched contract logic executing under a fixed weight limit. [1](#0-0) [2](#0-1) 

### Finding Description
This is the structural equivalent of the `safeTransferFrom` / `onERC721Received` bug: an asset-movement primitive (`withdraw`/`deposit`) is made conditional on a call into external, unprivileged, arbitrary code (`transfer()` on the ERC20 contract) instead of a plain, always-succeeding ledger credit/debit. If that external call reverts, runs out of the hardcoded `WeightLimit`, or the target contract behaves adversarially (e.g. deliberately fails for the fixed `TransfersCheckingAccount` address or a specific beneficiary), the transactor surfaces `XcmError::FailedToTransactAsset` unconditionally, with no alternate settlement path: [3](#0-2) [4](#0-3) 

The code itself acknowledges this is a dead-end failure mode with no user remedy, since the weight budget is fixed and cannot be adjusted per-message: [5](#0-4) 

Because the ERC20 contract backing the asset is arbitrary user-deployed code matched via `Matcher::matches_fungibles`, an attacker can register/use an ERC20 contract whose `transfer()` function is written to always revert (or consume more weight than `WeightLimit`) when `msg.sender` is the well-known `TransfersCheckingAccount`, or when `to` is a specific victim address. This is exactly analogous to a malicious/careless NFT receiver lacking `onERC721Received()`: the withdrawal/deposit step can never complete for that asset/account pair, yet the XCM executor already committed to treating the asset as "in holding" (withdraw case) or the reserve/teleport already debited the source chain (deposit case), so on `deposit_asset_with_surplus` failure the value falls back to the executor's asset-trap mechanism — which replays the identical failing contract call on any claim attempt, so the trap can never be redeemed either.

### Impact Explanation
This causes a permanent lock of bridged/XCM-settled value for that asset, matching the required-impact category "permanent user-fund or bridge-state lock" and "public underpriced work that ... stalls bridge processing," since settlement state (holding, trap, or checking-account balance) can advance only if arbitrary attacker-controlled contract code cooperates within a fixed weight budget it does not control.

### Likelihood Explanation
Any account can be the origin of a reserve-transfer or teleport for an asset whose id resolves (via the configured `Matcher`) to an ERC20 contract on `pallet-revive`; if that matcher permits permissionless registration of arbitrary contract addresses as backing assets (as is implied by the `matches_fungibles`/`AssetId` generic design here), an unprivileged attacker can deploy a contract engineered to always fail for the checking account, making this reliably triggerable without any privileged, admin, relayer, or validator role — satisfying the "unprivileged attacker" requirement of the impact gate.

### Recommendation
Do not gate settlement of the checking-account leg on an external, attacker-controllable contract call. Either (a) restrict `ERC20Transactor` to a fixed allow-list of vetted ERC20 contracts rather than a permissionless matcher, (b) perform the balance movement via a privileged/forced internal accounting path that does not depend on the contract's own `transfer()` logic succeeding, or (c) ensure failed deposits/withdraws have a guaranteed, retryable recovery path that does not simply replay the same failing external call, and make the weight/gas budget for this call auditable/adjustable so legitimate contracts cannot be starved.

### Proof of Concept
1. Deploy (or have any user deploy) an ERC20 contract `Evil` under `pallet-revive` whose `transfer()` function does `require(msg.sender != CHECKING_ACCOUNT)` (or performs a spin-loop that exceeds any reasonable `WeightLimit`).
2. Register/match `Evil` as the backing contract for an asset id recognized by `Matcher::matches_fungibles` in `ERC20Transactor`.
3. Initiate a reserve-transfer/teleport that credits `Evil` tokens into the chain's holding register, then attempt `deposit_asset_with_surplus` to the beneficiary; the call to `Evil::transfer()` from `TransfersCheckingAccount` always reverts, producing `XcmError::FailedToTransactAsset("ERC20 contract reverted")`. [6](#0-5) 
4. The asset falls into the XCM asset-trap; any subsequent claim attempt re-invokes the identical `deposit_asset_with_surplus` path against the same `Evil` contract and fails identically, permanently locking the asset.

**Caveat:** I could not fully verify (due to tool/context limits) the exact `Matcher`/`AssetId` configuration used in the concrete asset-hub runtime instantiation of `ERC20Transactor`, i.e., whether asset registration is permissionless or gated by governance in the deployed runtime. If registration is governance-gated only, the "unprivileged attacker" likelihood is reduced and this would fall under the excluded "privileged governance or admin abuse" category. I recommend a Devin session with full repository/terminal access to trace the concrete `Config` wiring (`Matcher`, `TransfersCheckingAccount`, `WeightLimit`) in the asset-hub runtime to confirm whether contract registration is truly permissionless before treating this as fully confirmed.
