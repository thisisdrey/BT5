### Title
Missing domain separation in StackerDB chunk signatures allows cross-replica signature replay - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` — the digest signed to authenticate a StackerDB chunk — commits only to `slot_id`, `slot_version`, and `data_hash`, but never to the StackerDB's `QualifiedContractIdentifier` (the specific smart contract/replica the chunk belongs to). Because the write path (`StackerDBTx::try_replace_chunk`) and the gossip/HTTP validation path (`PeerNetwork::validate_received_chunk`) both look up the expected signer *per contract* but verify the signature using only this contract-agnostic digest, a chunk that was legitimately signed and broadcast for one StackerDB contract can be replayed verbatim into a different StackerDB contract, as long as the same signing key happens to own the same `slot_id` there.

### Finding Description
The signed payload is constructed here: [1](#0-0) 

Note that `smart_contract`/contract identifier is absent from the hash — only `slot_id`, `slot_version`, and `data_hash` are committed to. `verify()` recovers the public key from this same digest and simply checks it hashes to the expected `principal`: [2](#0-1) 

On the write side, `try_replace_chunk` resolves the expected signer *for this contract's slot* and then calls `slot_desc.verify(&slot_validation.signer)`, but the verification itself has no way to detect that the signature was actually produced/broadcast for a *different* contract's slot: [3](#0-2) 

The same pattern repeats on the gossip/relay validation path used for both push and pull chunk delivery: [4](#0-3) 

Because many StackerDB contracts (e.g., signer-set contracts across cycles, or `.miners`/`.signers-*` contracts) reuse the same set of registered signer addresses at the same `slot_id` positions, an attacker who observes a validly-signed `StackerDBChunkData` broadcast for contract A (via `StacksMessageType::StackerDBPushChunk`, or fetched over HTTP `POST /v2/stackerdb/.../chunks`) can resubmit the identical `(slot_id, slot_version, data, sig)` tuple against contract B. If contract B's slot table assigns the same `slot_id` to the same signer address and contract B's current slot version is still lower than the replayed version, `try_replace_chunk` will accept and store it, and `PeerNetwork::process_stacker_db_chunks` will re-broadcast it network-wide via `broadcast_message`: [5](#0-4) 

This is precisely the class of bug called out in the external report: an operation (`executePayroll`) trusts a signed artifact without tying the signature to the exact context/target it authorizes — here, "signed for StackerDB contract A" is treated as equivalent to "authorized for StackerDB contract B," because the contract identifier is not part of what is signed.

### Impact Explanation
This allows an unauthenticated remote attacker (anyone who observes gossip or HTTP chunk pushes) to inject a chunk into an application's StackerDB replica that the legitimate signer never intended to write to that particular replica, and have honest nodes propagate this forged-context data network-wide. This is an unauthorized write to StackerDB state and forged-data propagation, matching the "Critical" impact bar (unauthenticated/unauthorized write to StackerDB, network-wide propagation of forged data).

### Likelihood Explanation
Exploitability depends on the operational fact that the same signer key is registered at the same `slot_id` across two distinct StackerDB contracts with differing content expectations, and that the target replica's current slot version is behind the replayed version — a configuration that is plausible given how signer sets are reused across reward cycles/contracts in this codebase, but it is not universally guaranteed and requires this specific overlap to exist.

### Recommendation
Include the `QualifiedContractIdentifier` (StackerDB contract address + name) in `SlotMetadata::auth_digest()` so that signatures are cryptographically bound to the specific StackerDB replica they authorize, preventing cross-contract replay. This requires a protocol-versioned change since it alters the signed payload format.

### Proof of Concept
1. Signer key `K` is registered as the owner of `slot_id = 0` in both StackerDB contract `A` and contract `B` (a realistic scenario when the same signer set participates in multiple app-contracts).
2. `K` legitimately signs and pushes chunk `(slot_id=0, slot_version=5, data=D)` for contract `A`; the digest signed is `hash(0 || 5 || sha512_256(D))` per `auth_digest()` — no contract identifier included.
3. An attacker observing this broadcast (or fetching it via HTTP) resubmits the identical `(slot_id, slot_version, sig, data)` tuple, but targets contract `B` (e.g., `POST /v2/stackerdb/{B}/chunks` or by placing it into a gossip `StackerDBPushChunkData` addressed to `B`).
4. `StackerDBTx::try_replace_chunk` for contract `B` looks up `slot_validation.signer = K` (from B's own config) and calls `slot_desc.verify(&K)`, which succeeds because the digest never referenced which contract it was for — the write is accepted into B's state store and rebroadcast to the network by `process_stacker_db_chunks`.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
