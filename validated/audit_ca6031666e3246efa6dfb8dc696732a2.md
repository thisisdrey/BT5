### Title
Unbounded `paths`/`attributes` in `GetFileAttributesRequest` causes O(paths×attributes) synchronous CPU-bound loop in a single RPC handler - ([File: internal/gitaly/service/repository/file_attributes.go])

### Summary
`GetFileAttributes` validates only that `paths` and `attributes` are non-empty, with no upper bound on their length, and then drives a single `git check-attr --stdin` process synchronously for every path in a loop. Since each `Check(path)` call blocks reading exactly `count = len(attributes)` NUL-delimited triplets from the subprocess, the total work for the RPC handler is O(len(paths) × len(attributes)), which an attacker fully controls in the request payload of their own repository.

### Finding Description
`validateGetFileAttributesRequest` at [1](#0-0)  only checks that `Repository`, `Revision`, `Paths`, and `Attributes` are present/non-empty — there is no cap on `len(in.GetPaths())` or `len(in.GetAttributes())`.

`GetFileAttributes` then spawns one `check-attr --stdin -z` process via `gitattributes.CheckAttr` and loops synchronously over every path calling `checkAttrCmd.Check(path)`: [2](#0-1) .

`CheckAttrCmd.Check` writes the path to the child's stdin and then reads `c.count` (`= len(names)`, i.e., the number of requested attributes) NUL-delimited words from stdout in a loop before returning: [3](#0-2) . This means the total synchronous I/O/CPU work inside the single RPC handler scales with `len(paths) * len(attributes)`, all performed sequentially under a mutex with no yielding/streaming and no per-call limit.

The gRPC server is configured in `GitalyServerFactory.New` without any `grpc.MaxRecvMsgSize` override [4](#0-3) , so it falls back to grpc-go's default max receive message size (4 MiB). This bounds the request somewhat but still permits on the order of hundreds of thousands to low millions of short path/attribute strings to be packed into a single unary request (e.g., ~10^6 one-character paths comfortably fit under 4 MiB), which is enough to drive a large O(paths×attributes) synchronous loop and pin a git subprocess plus the handling goroutine for an extended period.

Unlike streaming RPCs elsewhere in Gitaly that chunk large output across multiple messages, `GetFileAttributes` is unary and processes the entire fan-out within one handler invocation before returning any response, so there is no backpressure or early-return mechanism for the caller to abort mid-flight short of canceling the whole RPC.

### Impact Explanation
A single unprivileged, authenticated caller (any GitLab user who can call RPCs against a repo they can access, e.g. their own fork) can force one RPC handler to keep a `git check-attr` subprocess alive and a goroutine spinning for a long duration by submitting many paths/attributes combinations. This consumes CPU and holds resources (subprocess, mutex, buffered stdin/stdout pipes) proportional to `paths * attributes`, which can degrade node responsiveness under repeated/concurrent such requests — a resource-exhaustion/availability impact scoped to the calling node, consistent with the "Denial of Service (application layer, single-node degradation)" class rather than full-fleet outage.

### Likelihood Explanation
Feasibility is high for a moderate resource cost: the attacker needs only a repository they can call `GetFileAttributes` against, and a client capable of constructing a request with a large `paths`/`attributes` array (bounded by the ~4 MiB default gRPC message size, still permitting very large N). No special privileges, secrets, or non-default configuration are required, and the request is fully reproducible/repeatable on demand.

### Recommendation
Add explicit upper bounds in `validateGetFileAttributesRequest` on `len(in.GetPaths())` and `len(in.GetAttributes())` (e.g., a small constant maximum per RPC, consistent with other Gitaly RPCs that cap list sizes), and/or convert `GetFileAttributes` to a streaming RPC that processes and flushes paths in bounded batches so a single call cannot pin a full CPU core / subprocess for an unbounded duration.

### Proof of Concept
```go
func TestGetFileAttributes_LargeFanOut(t *testing.T) {
    ctx := testhelper.Context(t)
    cfg, client := setupRepositoryService(t)
    repoProto, repoPath := gittest.CreateRepository(t, ctx, cfg)
    gittest.WriteCommit(t, cfg, repoPath, gittest.WithBranch("main"),
        gittest.WithTreeEntries(gittest.TreeEntry{Path: "a", Mode: "100644", Content: "x"}))

    // Build a large number of short, distinct paths/attributes to stay under
    // the default 4MiB gRPC message size while maximizing fan-out.
    var paths, attrs []string
    for i := 0; i < 200000; i++ {
        paths = append(paths, fmt.Sprintf("p%d", i))
    }
    for i := 0; i < 20; i++ {
        attrs = append(attrs, fmt.Sprintf("attr%d", i))
    }

    start := time.Now()
    _, err := client.GetFileAttributes(ctx, &gitalypb.GetFileAttributesRequest{
        Repository: repoProto,
        Revision:   []byte("main"),
        Attributes: attrs,
        Paths:      paths,
    })
    elapsed := time.Since(start)
    require.NoError(t, err)
    // Assert should fail today: no bound enforced, elapsed grows with paths*attrs
    require.Less(t, elapsed, 2*time.Second, "single RPC should not be able to consume this much wall-clock time")
}
```
Expected today: the call succeeds but takes proportionally longer as `len(paths) * len(attributes)` grows, with no server-side rejection — demonstrating the missing bound called out in `validateGetFileAttributesRequest`.

// Check the attributes for the file at the given path.
func (c CheckAttrCmd) Check(path string) (Attributes, error) {
	if strings.Contains(path, "\000") {
		return nil, fmt.Errorf("path with NUL byte not allowed")
	}

	c.m.Lock()
	defer c.m.Unlock()

	if _, err := c.stdin.WriteString(path + "\000"); err != nil {
		return nil, fmt.Errorf("write path: %w", err)
	}
	if err := c.stdin.Flush(); err != nil {
		return nil, fmt.Errorf("flush: %w", err)
	}

	attrs := Attributes{}
	buf := make([]string, 0, 3)

	// Using git-check-attr(1) with -z will return data in the format:
	// <path> NUL <attribute> NUL <info> NUL ...
	for i := 0; i < c.count; {
		word, err := c.stdout.ReadBytes('\000')
		if err != nil {
			return nil, fmt.Errorf("read line: %w", err)
		}

		buf = append(buf, string(bytes.TrimSuffix(word, []byte{0})))

		if len(buf) < 3 {
			continue // Keep going until we have 3 words
		}

		if buf[0] != path {
			return nil, fmt.Errorf("wrong path name detected, expected %q, got %q", path, buf[0])
		}
		if buf[2] != Unspecified {
			attrs = append(attrs, Attribute{Name: buf[1], State: buf[2]})
		}

		i++
		buf = buf[:0]
	}

	return attrs, nil
