## Finding: Inconsistent (imprecise, non-hardened) usage→balance conversion formula in `DelegateResourceActuator.validate()` diverges from the precise formula used elsewhere for the same value, enabling over-delegation of frozen resources

### Summary
The reported JOJO bug is a class of vulnerability where two functions that are supposed to compute the *same* conceptual quantity use different formulas — one approximate/lower and one precise — and the approximate one is used to gate a user-controlled action (withdraw) while the precise one governs the real invariant (liquidation). In java-tron's `DelegateResourceActuator`, the analogous pattern exists: the amount of "used" bandwidth/energy is converted back into TRX-balance units using a hard-coded `double` division formula that is never hardened, whereas the rest of the codebase (energy/bandwidth limit calculation, and `RepositoryImpl.usageToBalance`) has an explicit hardened `BigInteger` path specifically because the `double` formula is known to lose precision for large weight/limit values.

### Finding Description
In `DelegateResourceActuator.validate()`, when a user calls `DelegateResourceContract` to delegate frozen BANDWIDTH or ENERGY to another account, the actuator estimates how much of the owner's `FrozenV2` balance is currently "used" (and therefore unavailable to delegate) with: [1](#0-0) 

and for energy: [2](#0-1) 

Both calculations use `(double) totalWeight / totalLimit` unconditionally — there is no branch on `VMConfig.allowHardenResourceCalculation()`/`disableJavaLangMath()` for the *usage→balance* conversion itself (only `getV2NetUsage`/`getV2EnergyUsage` afterwards respect the hardened flag).

This is the same class of divergence as `getTRate` vs `accrueRate`: elsewhere in the codebase, the identical conceptual conversion (turning consumed usage into TRX-weight terms, or vice versa) has a dedicated hardened `BigInteger` implementation precisely because the `double` version silently loses precision for large `totalWeight`/`totalLimit` pairs: [3](#0-2) 

And the dedicated test suite explicitly demonstrates that the naive `double` formula and the hardened `BigInteger` formula diverge for realistic values: [4](#0-3) [5](#0-4) 

The consumption side (`BandwidthProcessor.useAccountNet`, `EnergyProcessor.useEnergy`) calls `calculateGlobalNetLimit`/`calculateGlobalEnergyLimit`, which *does* branch to the hardened `BigInteger` path when enabled: [6](#0-5) [7](#0-6) 

`DelegateResourceActuator.validate()` never uses this hardened path for the usage estimate it uses to gate the delegate amount — it always uses the plain `double` formula regardless of the hardening flag, meaning the value checked against `delegateBalance` can systematically differ from the value the rest of the protocol treats as ground truth for the same account's resource accounting.

### Impact Explanation
Because `validate()`'s `netUsage`/`energyUsage` estimate (used to compute how much `FrozenV2` balance is "free" to delegate) can be lower or higher than the true usage-in-balance-terms computed by the hardened path used elsewhere, an attacker-controlled account can construct `totalNetWeight`/`totalNetLimit` (or energy equivalent) ratios where the `double` computation underestimates actual usage. This lets `DelegateResourceContract` succeed with a `delegateBalance` that exceeds what should genuinely remain available, moving more `FrozenV2` balance than is actually free into `DelegatedFrozenV2BalanceForBandwidth`/`Energy`. This is directly reachable by any unprivileged account issuing a `DelegateResourceContract` transaction and can result in inconsistent/negative "available" resource accounting for the owner account (a form of unbacked resource state), analogous to the over-withdraw in the original report.

### Likelihood Explanation
Any account holder with TRC-10/TRX frozen balance in V2 form can trigger this by simply calling delegate resource with a `TriggerSmartContract`/`DelegateResourceContract`; no special privilege, SR/witness role, or complex setup is required — only crafted usage/weight ratios, which are a function of network-wide `TotalNetWeight`/`TotalNetLimit` (or energy analogues) that fluctuate naturally and are influenced by an attacker's own freeze/unfreeze actions.

### Recommendation
Make the usage→balance conversion in `DelegateResourceActuator.validate()` use the same hardened `BigInteger`-based calculation (respecting `VMConfig.allowHardenResourceCalculation()`/`disableJavaLangMath()`) that is already used in `calculateGlobalNetLimit`/`calculateGlobalEnergyLimit`/`usageToBalance`, so that the value checked against `delegateBalance` is always consistent with the value the rest of the system treats as the true usage/available-balance for the account.

### Proof of Concept
1. Attacker freezes TRX for BANDWIDTH/ENERGY (V2) and accrues `netUsage`/`energyUsage` through normal transaction activity.
2. Attacker (or network conditions) drives `totalNetWeight`/`totalNetLimit` (or the energy equivalents) to values where `(double) totalNetWeight / totalNetLimit` diverges measurably from the exact `BigInteger` ratio (demonstrated by `testGlobalEnergyLimitV2CorrectVsDoublePrecisionLoss`/`testV1FlooredWeightVsV2FractionalWeight` in `CalculateGlobalLimitHardenTest.java`).
3. Attacker submits `DelegateResourceContract` with a `delegateBalance` computed to just pass the (imprecise) check in `DelegateResourceActuator.validate()` lines 157-169 / 172-183, while the true (hardened) usage value would have rejected it.
4. `execute()` moves `delegateBalance` from `FrozenV2` into `DelegatedFrozenV2Balance`, leaving the account's true "used vs. free" resource accounting inconsistent with what the hardened calculation elsewhere in the protocol (`RepositoryImpl.calculateGlobalEnergyLimit`, `BandwidthProcessor.calculateGlobalNetLimit`) would consider valid.

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalEnergyLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }

    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
    long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
      return 0;
    } else {
      assert totalEnergyWeight > 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
