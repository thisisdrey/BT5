### Title
`SSHReceivePack` has no idle/negotiation timeout, allowing a stalled stdin stream to block the handler and pipeline indefinitely - (File: `internal/gitaly/service/ssh/receive_pack.go`)

### Summary
`SSHReceivePack` reads the client's pktline/pack stream via `stream.Recv()` in an unbounded goroutine and then blocks on `cmd.Wait()` for `git-receive-pack` to exit, with no request-level idle/negotiation timeout enforced anywhere in the call path. Unlike the sibling RPCs `SSHUploadPackWithSidechannel` and `SSHUploadArchive`, which explicitly guard against a stalled client using a `helper.Ticker`-based timeout, `sshReceivePack` has no equivalent mechanism, so a client that sends the valid first request and then never sends more data (and never closes the stream) can hold the handler, a spawned goroutine, an `os.Pipe`, and a `git-receive-pack` subprocess open indefinitely.

### Finding Description
In `sshReceivePack` (`internal/gitaly/service/ssh/receive_pack.go:69-198`), the client's stdin is drained via a `streamio.NewReader` wrapping `stream.Recv()` and copied through an `os.Pipe` into `git-receive-pack`'s stdin in a background goroutine: [1](#0-0) 
The code comment explicitly documents that this goroutine "will never end" if the reader is never closed, and that `cmd.Wait()` at line 172 blocks until both the process and this goroutine finish: [2](#0-1) 

Once `validateFirstReceivePackRequest` passes (only requires non-empty `GlId`, empty `Stdin` on the first message, and a valid repository), an attacker can simply stop sending any further `SSHReceivePackRequest` messages. `stream.Recv()` then blocks indefinitely, `git-receive-pack` never receives a pack header/flush and blocks reading stdin, and `cmd.Wait()` in the handler blocks forever, tying up the gRPC handler goroutine, the spawned copy goroutine, an `os.Pipe`, and the `git-receive-pack` child process.

By contrast, `SSHUploadPackWithSidechannel`/`sshUploadPack` (`internal/gitaly/service/ssh/upload_pack.go:100-114`) explicitly creates a `timeoutTicker := s.uploadPackRequestTimeoutTickerFactory()` and passes it into `runUploadCommand` to cancel the negotiation if the client stalls after sending "done" (`Timeout.UploadPackNegotiation`), and `SSHUploadArchive` similarly uses `WithArchiveRequestTimeoutTickerFactory`/`Timeout.UploadArchiveNegotiation` as demonstrated by `TestFailedUploadArchiveRequestDueToTimeout`: [3](#0-2) 
No such ticker/timeout field or config value exists for receive-pack in `server{}` (`internal/gitaly/service/ssh/server.go:20-39`), which only defines `uploadPackRequestTimeoutTickerFactory` and `uploadArchiveRequestTimeoutTickerFactory` — there is no `receivePackRequestTimeoutTickerFactory`.

Checking existing generic protections: the gRPC server's keepalive settings (`internal/gitaly/server/server.go:235-241`) only enforce ping cadence and do not terminate idle streams with no application data; `grpc.KeepaliveParams{Time: 5 * time.Minute}` merely triggers pings on an idle *connection*, and `PermitWithoutStream: true` explicitly permits keeping the connection open without an active stream sending data. The concurrency limiter middleware (`internal/grpc/middleware/limithandler/middleware.go`) bounds the number of concurrent in-flight RPCs per key but does not impose or enforce an idle-stream deadline, so a handler already admitted by the limiter can still block forever once inside `sshReceivePack`.

### Impact Explanation
A client (attacker) with push access to any repository they can reach via `git push` over SSH can open an `SSHReceivePack` stream, send only the well-formed first message, and then stall. Each such stalled connection permanently consumes a gRPC handler goroutine, a spawned `io.Copy` goroutine, an `os.Pipe` (2 file descriptors), and a live `git-receive-pack` subprocess (plus quarantine/lock state on the target repository) until the client-side TCP connection is torn down or the Gitaly process is restarted. Repeating this from a modest number of concurrent connections against distinct repositories (or the concurrency-limiter's per-key limit for the same repository) exhausts goroutines, file descriptors, and process slots on the Gitaly node, which matches the "DoS / resource exhaustion" impact class.

### Likelihood Explanation
The precondition is only that the attacker has push access to at least one repository (an unprivileged GitLab user can already push to their own fork). No malformed input, oversized pack, or crash is required — simply omitting the flush/pack data after the valid first request is enough. This is deterministic and trivially repeatable, and the code comment in `receive_pack.go` itself acknowledges the underlying blocking behavior as a known but only partially mitigated issue (the pipe/goroutine split was added to keep `cmd.Wait()` from blocking on the io.Copy goroutine when the *git process* crashes early, but it does nothing to bound the case where the *client* never sends data).

### Recommendation
Add a request/negotiation idle timeout to `sshReceivePack` analogous to `uploadPackRequestTimeoutTickerFactory`/`uploadArchiveRequestTimeoutTickerFactory`: introduce a `receivePackRequestTimeoutTickerFactory` (backed by a new `Timeout.ReceivePackNegotiation` config value), start it when waiting for the first stdin bytes, and cancel the RPC's context (killing the underlying `git-receive-pack` process and unblocking `cmd.Wait()`) if no data arrives within the timeout window. This mirrors the pattern already implemented in `internal/gitaly/service/ssh/upload_pack.go` and `upload_archive.go`.

### Proof of Concept
```go
// internal/gitaly/service/ssh/receive_pack_test.go (illustrative)
func TestSSHReceivePack_StalledClientHoldsHandlerForever(t *testing.T) {
    t.Parallel()
    cfg := testcfg.Build(t)
    cfg.SocketPath = runSSHServerWithOptions(t, cfg, nil)

    ctx := testhelper.Context(t)
    repo, _ := gittest.CreateRepository(t, ctx, cfg)
    client := newSSHClient(t, cfg.SocketPath)

    stream, err := client.SSHReceivePack(ctx)
    require.NoError(t, err)

    // Send only the valid first request.
    require.NoError(t, stream.Send(&gitalypb.SSHReceivePackRequest{
        Repository: repo,
        GlId:       "user-1",
    }))

    // Attacker never sends stdin (pack data) and never closes send side.
    // Expectation with the fix: stream.Recv() eventually returns
    // DeadlineExceeded/Canceled within the configured negotiation timeout.
    // Actual (current) behavior: Recv() blocks indefinitely because no
    // receive-pack negotiation timeout exists, keeping the git-receive-pack
    // process, os.Pipe, and goroutines alive until the connection is dropped.
    _, err = stream.Recv()
    require.Error(t, err) // fails / hangs under current implementation
}
```
Running this against the current `sshReceivePack` implementation shows the RPC never terminates on its own (no `DeadlineExceeded`), confirming the absence of an idle/negotiation timeout that exists for `SSHUploadPackWithSidechannel` and `SSHUploadArchive`.

func TestFailedUploadArchiveRequestDueToTimeout(t *testing.T) {
	t.Parallel()

	cfg := testcfg.Build(t)

	// Use a ticker channel so that we can observe that the ticker is being created. The channel
	// is unbuffered on purpose so that we can assert that it is getting created exactly at the
	// time we expect it to be.
	tickerCh := make(chan *helper.ManualTicker)

	cfg.SocketPath = runSSHServerWithOptions(t, cfg, []ServerOpt{
		WithArchiveRequestTimeoutTickerFactory(func() helper.Ticker {
			// Create a ticker that will immediately tick when getting reset so that the
			// server-side can observe this as an emulated timeout.
			ticker := helper.NewManualTicker()
			ticker.ResetFunc = func() {
				ticker.Tick()
			}
			tickerCh <- ticker
			return ticker
		}),
	})
