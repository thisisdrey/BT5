### Title
`TrustedSpender.setAllowance` is vulnerable to the same allowance-frontrun pattern as `approve()`, letting a delegate double-spend a route's USDC cap - ([File: tare-io__tare-contracts/contracts/TrustedSpender.sol])

### Summary
`TrustedSpender.setAllowance` unconditionally overwrites the `(token, from, to)` route's `amount`/`validUntil` in a single storage write, exactly like the classic vulnerable ERC20 `approve()` pattern described in the reference report. Because `executeTransfer` is permissionless for any registered delegate up to the currently stored allowance, a delegate who sees a pending `setAllowance` transaction that lowers (or otherwise changes) their route's cap can front-run it, drain the old allowance, then drain the newly set allowance right after, extracting `old + new` instead of the single value the Safe/Guardian intended as the final cap.

### Finding Description
`setAllowance` performs a direct overwrite with no check against the currently stored value: [1](#0-0) 

`executeTransfer` lets any address registered as a delegate for `from` immediately spend up to whatever is currently stored for a route, decrementing it in the same call: [2](#0-1) 

This mirrors exactly the root cause in the external report: mutable state (`allowance`) that is directly replaced instead of incrementally adjusted, combined with a party (the delegate here, the spender in the ERC20 case) who can act on both the pre- and post-transaction values. When a Safe (or a guardian acting on the Safe's behalf, e.g., in response to suspected delegate misbehavior) submits `setAllowance(token, safe, recipient, newAmount, ...)` intending to change the effective cap from `oldAmount` to `newAmount`, a delegate watching the mempool can:
1. Front-run with `executeTransfer(token, safe, recipient, oldAmount)`, draining the full old allowance before the update lands.
2. Let the `setAllowance` transaction execute, resetting the route to `newAmount`.
3. Immediately call `executeTransfer(token, safe, recipient, newAmount)`, draining the new allowance too.

The delegate thus extracts `oldAmount + newAmount` in USDC from the Safe via the pre-approved `to` route, exceeding the single cap the Safe/guardian intended to enforce at any given time.

### Impact Explanation
This causes unauthorized diversion of USDC from a Safe smart account beyond the allowance the Safe/guardian explicitly configured, which falls under "theft, diversion, or unauthorized reassignment of USDC ... from honest users or shared protocol state" in the allowed impact set. The Safe/guardian's attempt to reduce a delegate's spending power (e.g., after detecting anomalous behavior, revoking a compromised delegate's route capacity, or simply re-budgeting) can be defeated, resulting in real value loss to the Safe beyond its intended, most-recent authorization.

### Likelihood Explanation
Exploitation requires: (1) an existing delegate for the Safe who is malicious or compromised (delegates are added by the Safe/guardian, so this is a somewhat privileged actor, but delegate is not on the excluded privileged-role list — it is a routine operational role meant to be limited by allowances), (2) the Safe or guardian issuing a `setAllowance` call that changes a non-zero, non-fully-consumed allowance on a public mempool, and (3) the delegate reacting fast enough to front-run. This is most likely precisely in the security-relevant scenario the allowance mechanism exists for: reducing/revoking a delegate's cap after suspicion of misuse — which is exactly when the delegate is incentivized to race the change.

### Recommendation
Follow the same mitigation pattern recommended in the original report: change `setAllowance` to require the caller to supply the expected current `amount` (revert if it doesn't match, similar to `compareAndSwap`), or split into `increaseAllowance`/`decreaseAllowance` style functions that adjust relative to the current stored value rather than overwriting it outright. Alternatively, require the allowance to be reduced to zero (spent or explicitly zeroed) in a separate transaction before a new nonzero cap can be set for the same route.

### Proof of Concept
1. Safe calls `setAllowance(USDC, safe, recipient, 1_000_000e6, validUntil)` (large initial cap).
2. Guardian, suspecting delegate compromise, submits `setAllowance(USDC, safe, recipient, 10e6, validUntil)` to shrink the cap to 10 USDC.
3. Malicious delegate observes the pending tx in the mempool and front-runs with `executeTransfer(USDC, safe, recipient, 1_000_000e6)`, draining the full old cap.
4. Guardian's `setAllowance` lands, resetting the route allowance to `10e6`.
5. Delegate immediately calls `executeTransfer(USDC, safe, recipient, 10e6)`.
6. Total drained: `1_000_000e6 + 10e6`, instead of the `10e6` the guardian intended as the effective ceiling — demonstrated by the same mechanics as `test_ExecuteTransfer`/`test_SetAllowance` in [3](#0-2) , just reordered around a pending `setAllowance` call.

```text
  function setAllowance(
    address token,
    address from,

    uint208 amount,

  ) external safeOrGuardian(from) {
    require(token != address(0) && from != address(0) && to != address(0), ZeroAddress());
    require(validUntil > block.timestamp, InvalidAllowanceDeadline());

    _allowances[token][from][to] = Allowance({amount: amount, validUntil: validUntil});
    emit AllowanceSet(token, from, to, amount, validUntil);
  }
```

```text
  /// @inheritdoc ITrustedSpender
  function executeTransfer(address token, address from, address to, uint256 amount) external whenNotPaused {
    // Verify sender is a delegate
    require(delegates[from][msg.sender], NotADelegate());

    // Check allowance exists, is sufficient, and has not expired
    Allowance storage allowance = _allowances[token][from][to];
    require(allowance.amount >= amount, InsufficientAllowance());
    require(block.timestamp <= allowance.validUntil, AllowanceExpired());

    // Update allowance if not infinite
    if (allowance.amount != type(uint208).max) {
      allowance.amount -= uint208(amount);
    }

    IERC20(token).safeTransferFrom(from, to, amount);
  }
```
