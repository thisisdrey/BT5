### Title
Unbounded attacker-controlled array-length in `ValidateMultiSign`/`BatchValidateSign` precompiles causes OutOfMemoryError DoS - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `dav1d` CVE is a bug class where an attacker-supplied "large size" value from encoded input is used without adequate bounds checking, leading to memory corruption (OOM/overflow). In java-tron's TVM precompiled contracts `ValidateMultiSign` and `BatchValidateSign`, the legacy signature-array-extraction path takes an attacker-controlled 256-bit word straight from call data, converts it with `intValueSafe()`, and uses it directly to size a Java array (`new byte[len][]`) with no upper bound check on that path, before the bound check (`MAX_SIZE`) is even evaluated.

### Finding Description
`extractBytesArray` and `extractBytes32Array` both derive `len` directly from an attacker-controlled `DataWord` and immediately allocate an array of that size: [1](#0-0) 

In `ValidateMultiSign.execute`, the `MAX_SIZE` bound is only checked when `VMConfig.allowTvmSelfdestructRestriction()` is true. On that same condition, `extractSigArray` (bounded, fixed-size signature slots) is used instead of `extractBytesArray`. When the flag is false, `extractBytesArray` is called directly with the attacker-controlled `len`, with no size cap applied at all: [2](#0-1) 

The same pattern repeats in `BatchValidateSign.doExecute`, where `extractBytes32Array(words, offset)` (used for the `addresses` array) is called unconditionally, and `extractBytesArray` is used for `signatures` whenever `allowTvmSelfdestructRestriction()` is false — again without the `MAX_SIZE` cap applied to that code path: [3](#0-2) 

`DataWord.intValueSafe()` returns `Integer.MAX_VALUE` for any word whose numeric value doesn't fit safely into an `int`, otherwise it returns the raw int value of an attacker-chosen word: [4](#0-3) 

This is confirmed as intentional legacy behavior preserved for backward compatibility, per the existing test comment describing "TIP-854" pre-activation semantics: [5](#0-4) 

### Impact Explanation
An attacker who can trigger a TVM `staticcall`/`call` to the `ValidateMultiSign` (address `0x66...`-style precompile) or `BatchValidateSign` precompile contract — reachable from any Solidity contract invocable by an ordinary transaction — can supply a length word up to `Integer.MAX_VALUE` (or a value near it). `new byte[len][]` for such a length either throws immediately (bounded impact, energy already partly spent) or, depending on JVM heap configuration, can trigger large transient allocations across many calls, causing `OutOfMemoryError`. Because `ValidateMultiSign`/`BatchValidateSign` catch only certain exception types in some branches (`ValidateMultiSign.execute` wraps signature verification in `try/catch(Throwable)` further down but the array allocation itself happens before that block), an uncaught `OutOfMemoryError`/`RuntimeException` from oversized allocation can propagate up through `Runtime`/`Program` execution and crash or destabilize the node process serving that transaction — a node halt/DoS condition.

### Likelihood Explanation
Likelihood depends on whether `VMConfig.allowTvmSelfdestructRestriction()` is active on the target network. On networks/testnets/private chains where this hard-fork flag has not yet been activated (default `0` until enabled via committee proposal), the unguarded path is live and trivially reachable by anyone who can broadcast a transaction invoking these precompiles — no special privilege required.

### Recommendation
Apply the same `MAX_SIZE` bound check unconditionally, before calling `extractBytesArray`/`extractBytes32Array`, regardless of `allowTvmSelfdestructRestriction()`, rather than gating the check on the feature flag. Alternatively, add a hard length cap inside `extractBytesArray` and `extractBytes32Array` themselves (e.g., reject `len < 0 || len > MAX_SIZE` immediately) so the legacy code path can never allocate an oversized array.

### Proof of Concept
1. Craft an ABI-encoded call to `validatemultisign(address,uint256,bytes32,bytes[])` where the dynamic `bytes[]` array-length word (at the offset pointed to by the 4th static parameter) is set to a very large value (e.g. `0x000000000000000000000000000000000000000000000000000000000fffff` or similar large-but-representable int).
2. Ensure the target network/config has `allowTvmSelfdestructRestriction()` returning `false` (pre-activation state).
3. Submit the transaction calling this precompile from a smart contract; `extractBytesArray` executes `new byte[len][]` with the attacker-chosen `len` before any `MAX_SIZE` bound is applied, causing large allocation / `OutOfMemoryError`.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];

      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }

   * In case of int overflow returns Integer.MAX_VALUE otherwise works as #intValue()

  public int intValueSafe() {
    int bytesOccupied = bytesOccupied();
    int intValue = intValue();
    if (bytesOccupied > 4 || intValue < 0) {
      return Integer.MAX_VALUE;
    }
    return intValue;
  }
