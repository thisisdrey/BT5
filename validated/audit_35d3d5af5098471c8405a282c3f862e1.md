### Title
Improper Privilege Management in `AccountPermissionUpdateActuator` — Active Permission Escalation to Owner - ([File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java])

### Summary
`AccountPermissionUpdateActuator` allows a transaction signed under any permission (including a non-Owner "Active" permission) to overwrite the account's Owner permission, Witness permission, and all Active permissions, as long as the signing permission's `operations` bitmask happens to include the `AccountPermissionUpdateContract` bit. The actuator's `validate()`/`execute()` never checks that the signer used the account's Owner permission (`permissionId == 0`) to authorize a change to the Owner permission itself, mirroring the Concrete CMS flaw where a lower-privileged group ("Editor") could reach a privileged operation because the code failed to verify the caller's permission level before performing the sensitive change.

### Finding Description
`TransactionCapsule.validateSignature()`/`addSign()` resolve which `Permission` governs a transaction purely from `contract.getPermissionId()` and validate the signature weight against that permission's threshold: [1](#0-0) 
For non-zero `permissionId` (i.e., an Active permission, not Owner), the only extra check performed is that the contract type being submitted is allowed by that permission's `operations` bitmap: [2](#0-1) [3](#0-2) 

`AccountPermissionUpdateActuator.validate()` only checks structural correctness of the *new* permissions being written (key counts, weights, thresholds, operation-bit sanity, witness-only-if-witness, etc.) — it never inspects which permission signed the transaction, nor restricts the ability to rewrite the Owner permission to Owner-signed transactions: [4](#0-3) 

`execute()` then unconditionally applies whatever Owner/Witness/Actives are specified in the contract to the account, regardless of the signer's actual permission level: [5](#0-4) 

Because `AccountPermissionUpdateContract` is one of the standard `ContractType`s that can be included in an Active permission's `operations` bitmask (confirmed by the default-mask coverage test), an account owner who legitimately scopes an Active permission to allow key-rotation automation (`AccountPermissionUpdateContract` bit set) inadvertently grants that Active key holder the ability to also rewrite the Owner permission and any other Active permission, not merely the delegated function: [6](#0-5) 

This is structurally identical to the Concrete CMS bug class: a component (`bulkupdate`/`AccountPermissionUpdateContract`) that performs a sensitive privilege change fails to verify that the caller's own privilege level (Admin/Owner) is sufficient for the specific change being requested (moving a group to Admin / overwriting the Owner permission), instead only checking that the caller has *some* access to the general endpoint.

### Impact Explanation
Any account owner who grants an Active permission the capability to submit `AccountPermissionUpdateContract` (a common pattern for allowing automated/limited key rotation) unintentionally creates a path for that Active key holder to unilaterally overwrite the account's Owner permission with keys of their choosing. This is a full, permanent account takeover: the attacker becomes able to sign any transaction from the victim account (transfers, TRC10/TRC20 issuance and management, resource delegation, contract calls) with Owner-level authority, resulting in unauthorized account operations and theft of funds.

### Likelihood Explanation
Exploitation requires the victim to have configured an Active permission that includes the `AccountPermissionUpdateContract` operation bit — a configuration that is plausible and even encouraged for automated key-rotation setups, since the actuator provides no warning or restriction preventing an Active permission from touching the Owner permission. No cooperation beyond the initial (reasonable) permission grant is needed from the victim; the malicious Active key holder can act unilaterally at any time afterward.

### Recommendation
In `AccountPermissionUpdateActuator.validate()`, require that any transaction attempting to modify the Owner permission (or a Witness permission, or add new Active permissions with broader `operations` than the signer's own) must be signed by the account's current Owner permission (`permissionId == 0`), analogous to Concrete CMS's fix of validating the caller's own group permission before allowing the privileged group-move operation. At minimum, enforce that Active permissions can never legally include the `AccountPermissionUpdateContract` bit, or that an Active-signed `AccountPermissionUpdateContract` transaction can only modify Active permissions equal to or narrower than the signer's own scope, never the Owner permission.

### Proof of Concept
1. Account owner sets up permissions: Owner permission (threshold 1, key = OwnerKey); Active permission #2 (threshold 1, key = AutomationKey) with `operations` bitmask including the bit for `AccountPermissionUpdateContract` (intended to let AutomationKey rotate other Active keys only).
2. Attacker who controls `AutomationKey` crafts an `AccountPermissionUpdateContract` transaction with `permissionId = 2` (the Active permission), setting:
   - `owner` = new Owner permission with AttackerKey as sole key, threshold 1
   - `actives` = a broad Active permission also controlled by AttackerKey
3. Signs the transaction with `AutomationKey`; `TransactionCapsule.checkPermission`/`checkPermissionOperations` passes because the Active permission's operations bitmap allows `AccountPermissionUpdateContract`.
4. `AccountPermissionUpdateActuator.validate()` passes all structural checks (see `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java:148-229`) because none of them inspect the signer's permission level relative to the Owner permission being overwritten.
5. `execute()` applies the new Owner/Active permissions verbatim (`actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java:41-59`), giving AttackerKey full Owner control of the victim account.

  public static boolean validateSignature(Transaction transaction,
      byte[] hash, AccountStore accountStore, DynamicPropertiesStore dynamicPropertiesStore)
      throws PermissionException, SignatureException, SignatureFormatException {
    Transaction.Contract contract = transaction.getRawData().getContractList().get(0);
    int permissionId = contract.getPermissionId();
    byte[] owner = getOwner(contract);
    AccountCapsule account = accountStore.get(owner);
    Permission permission = null;
    if (account == null) {
      if (permissionId == 0) {
        permission = AccountCapsule.getDefaultPermission(ByteString.copyFrom(owner));
      }
      if (permissionId == 2) {
        permission = AccountCapsule
            .createDefaultActivePermission(ByteString.copyFrom(owner), dynamicPropertiesStore);
      }
    } else {
      permission = account.getPermissionById(permissionId);
    }
    if (permission == null) {
      throw new PermissionException("permission isn't exit");
    }
    checkPermission(permissionId, permission, contract);
    long weight = checkWeight(permission, transaction.getSignatureList(), hash, null);
    if (weight >= permission.getThreshold()) {
      return true;
    }
    return false;
  }

  public static boolean checkPermissionOperations(Permission permission, Contract contract)
      throws PermissionException {
    ByteString operations = permission.getOperations();
    if (operations.size() != 32) {
      throw new PermissionException(String.format("operations size must 32, actual: %d",
          operations.size()));
    }
    int contractType = contract.getTypeValue();
    boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
    return b;
  }

  @Override
  public boolean validate() throws ContractValidateException {

    if (chainBaseManager == null) {
      throw new ContractValidateException(ActuatorConstant.STORE_NOT_EXIST);
    }

    if (this.any == null) {
      throw new ContractValidateException(ActuatorConstant.CONTRACT_NOT_EXIST);
    }

    AccountStore accountStore = chainBaseManager.getAccountStore();
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();

    if (dynamicStore.getAllowMultiSign() != 1) {
      throw new ContractValidateException("multi sign is not allowed, "
          + "need to be opened by the committee");
    }
    if (!this.any.is(AccountPermissionUpdateContract.class)) {
      throw new ContractValidateException(
          "contract type error,expected type [AccountPermissionUpdateContract],real type["
              + any.getClass() + "]");
    }
    final AccountPermissionUpdateContract accountPermissionUpdateContract;
    try {
      accountPermissionUpdateContract = any.unpack(AccountPermissionUpdateContract.class);
    } catch (InvalidProtocolBufferException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractValidateException(e.getMessage());
    }
    byte[] ownerAddress = accountPermissionUpdateContract.getOwnerAddress().toByteArray();
    if (!DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("invalidate ownerAddress");
    }
    AccountCapsule accountCapsule = accountStore.get(ownerAddress);
    if (accountCapsule == null) {
      throw new ContractValidateException("ownerAddress account does not exist");
    }

    if (!accountPermissionUpdateContract.hasOwner()) {
      throw new ContractValidateException("owner permission is missed");
    }

    if (accountCapsule.getIsWitness()) {
      if (!accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("witness permission is missed");
      }
    } else {
      if (accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("account isn't witness can't set witness permission");
      }
    }

    if (accountPermissionUpdateContract.getActivesCount() == 0) {
      throw new ContractValidateException("active permission is missed");
    }
    if (accountPermissionUpdateContract.getActivesCount() > 8) {
      throw new ContractValidateException("active permission is too many");
    }

    Permission owner = accountPermissionUpdateContract.getOwner();
    Permission witness = accountPermissionUpdateContract.getWitness();
    List<Permission> actives = accountPermissionUpdateContract.getActivesList();

    if (owner.getType() != PermissionType.Owner) {
      throw new ContractValidateException("owner permission type is error");
    }
    checkPermission(owner);
    if (accountCapsule.getIsWitness()) {
      if (witness.getType() != PermissionType.Witness) {
        throw new ContractValidateException("witness permission type is error");
      }
      checkPermission(witness);
    }
    for (Permission permission : actives) {
      if (permission.getType() != PermissionType.Active) {
        throw new ContractValidateException("active permission type is error");
      }
      checkPermission(permission);
    }
    return true;
  }
