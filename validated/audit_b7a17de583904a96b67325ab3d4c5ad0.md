### Title
Active permission holder can be granted authority to rewrite the Owner permission via `AccountPermissionUpdateContract`, enabling permanent account takeover - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
Java-tron's multi-sig permission model (`Owner`/`Witness`/`Active` permissions) is analogous to the mutable, self-referential `AccessControl` role model criticized in the report: any signer whose applicable permission's `operations` bitmap enables the `AccountPermissionUpdateContract` bit can completely rewrite `ownerPermission`, `witnessPermission`, and all `activePermission` entries for the account — including deleting the keys of the account's actual Owner — with no requirement that the transaction be authorized by the current Owner permission (id 0) itself.

### Finding Description
`AccountPermissionUpdateActuator.execute()` unconditionally calls `AccountCapsule.updatePermissions()` with the owner/witness/actives supplied in the contract, fully overwriting existing permissions [1](#0-0) [2](#0-1) .

Authorization for which permission may submit this contract is decided purely by bit-flags in the signer's `Permission.operations` field, checked in `TransactionCapsule.checkPermission()`/`checkPermissionOperations()` at signing and validation time [3](#0-2) . If `permissionId != 0`, the code only requires the permission to be of type `Active` and to have the relevant contract-type bit set — there is no additional requirement that the signer possess or approve via the current Owner permission when the transaction being submitted is itself an `AccountPermissionUpdateContract`.

`AccountPermissionUpdateActuator.checkPermission()` validates that any custom `Active` permission's `operations` bitmap is a subset of `dynamicStore.getAvailableContractType()`, which (unlike the *default* active-permission template) does include the `AccountPermissionUpdateContract` bit [4](#0-3) . This is confirmed by the test comparing "available" vs "default active" operation bitmaps, where `AccountPermissionUpdateContract` is explicitly excluded only from the *default* active template, not from the set of contract types an Active permission is legally allowed to carry [5](#0-4) .

Consequently, once an Owner (deliberately, or via a poorly-scoped delegation such as a "cold"/service Active key with a broad operations bitmap) creates an Active permission that includes the `AccountPermissionUpdateContract` bit, that Active-permission key holder gains the ability to unilaterally submit an `AccountPermissionUpdateContract` that replaces the Owner permission entirely (removing the true Owner's key), replaces/removes any Witness permission, and replaces all Active permissions — seizing full, permanent control of the account. This mirrors the reported bug class: a role/permission (the Active permission) intended for narrower operational use is mutable in a way that allows its holder to unilaterally reconfigure the entire privilege hierarchy, including revoking the higher-privileged Owner, exactly as the "malicious minter granting MINTER_ROLE to a non-minter, then revoking the original minter" pattern described in the report.

### Impact Explanation
An attacker who obtains (or is legitimately granted) an Active permission key whose `operations` bitmap includes the `AccountPermissionUpdateContract` bit can permanently seize an account: overwrite the Owner permission's keys/threshold, delete the Witness permission, and delete/replace all other Active permissions. This is a concrete unauthorized account takeover leading to permanent loss of control (and by extension, permanent freezing/theft of funds and any TRX-power/vote rights tied to that account), reachable purely from a single signed `AccountPermissionUpdateContract` transaction broadcast to the network.

### Likelihood Explanation
Likelihood depends on an Owner having configured an Active permission with the `AccountPermissionUpdateContract` bit enabled — this is not the default template, but it is explicitly permitted by validation logic and requires no committee/governance approval, only a normal `AccountPermissionUpdateContract` transaction from the current Owner. Given real-world use of delegated/hot Active keys for automation, and no built-in warning, guardrail, or restriction preventing granting this specific bit to a non-Owner Active permission, this is a realistic misconfiguration/privilege-escalation vector rather than a purely theoretical one.

### Recommendation
Require that any `AccountPermissionUpdateContract` be authorized specifically by the Owner permission (permission id 0) regardless of the signer's `operations` bitmap, i.e., disallow the `AccountPermissionUpdateContract` bit from being settable/honored on non-Owner (`Active`) permissions in `AccountPermissionUpdateActuator.checkPermission()`, and reject it explicitly in `TransactionCapsule.checkPermission()`/`checkPermissionOperations()` when `permissionId != 0`.

### Proof of Concept
1. Owner account `A` (key `K_owner`) creates an `Active` permission `P_active` with an operations bitmap that includes the `AccountPermissionUpdateContract` bit and assigns it to key `K_delegate`, via a normal `AccountPermissionUpdateContract` signed by `K_owner` — accepted because `checkPermission()` only rejects bits outside `getAvailableContractType()`, which includes this bit [6](#0-5) .
2. `K_delegate` now independently crafts and signs a new `AccountPermissionUpdateContract` with `permission_id = P_active.id`, setting a brand-new Owner permission containing only `K_delegate`'s own key, and empty/self-controlled Active permissions.
3. This transaction passes `checkPermission()`/`checkPermissionOperations()` (type is `Active`, bit is set) [3](#0-2)  and `AccountPermissionUpdateActuator.execute()` overwrites the account's Owner permission entirely [2](#0-1) .
4. `K_owner` is now permanently locked out; `K_delegate` has full, sole control of account `A`.

  public void updatePermissions(Permission owner, Permission witness, List<Permission> actives) {
    Builder builder = this.account.toBuilder();

    owner = owner.toBuilder().setId(0).build();
    builder.setOwnerPermission(owner);
    if (witness != null && builder.getIsWitness()) {
      witness = witness.toBuilder().setId(1).build();
      builder.setWitnessPermission(witness);
    }

    builder.clearActivePermission();
    if (actives != null) {
      for (int i = 0; i < actives.size(); i++) {
        Permission permission = actives.get(i).toBuilder().setId(i + 2).build();
        builder.addActivePermission(permission);
      }
    }

    this.account = builder.build();
