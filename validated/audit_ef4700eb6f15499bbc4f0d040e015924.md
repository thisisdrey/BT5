### Title
Fixed 20-Second Write-Lock TTL Lets an Ordinary Push Bypass Praefect's Serialized-Write Deadlock Protection - ([File: internal/praefect/transactions/manager.go])

### Summary
Praefect's serialized-write feature (`praefect_serialized_write`) prevents cross-node ref-lock deadlocks by holding a repository-scoped PostgreSQL lock from the `PREPARING_PHASE` through `COMMITTED_PHASE` of the `reference-transaction` hook. The lock is only renewed at the moment a phase vote arrives and has a fixed 20-second TTL. An ordinary user can craft a push whose `PREPARED`→`COMMITTED` phase work (large number of ref updates, large packfile, slow object writing/hooks on the Gitaly nodes) takes longer than 20 seconds. This causes the lock to expire and be "stolen" by a second concurrent write to the same repository, exactly re-opening the on-disk ref-lock deadlock the mechanism was built to close — mirroring the report's pattern where an attacker-controlled oversized payload blows through a fixed resource/time budget in an error/retry-adjacent code path and defeats an ordering guarantee, causing subsequent writes to the resource to stall.

### Finding Description
`internal/praefect/transactions/manager.go` acquires the repo write lock at `PREPARING_PHASE` and renews it (`lock.Renew`) only when a `PREPARED_PHASE` or `COMMITTED_PHASE` vote message actually arrives: [1](#0-0) 

The lock itself is backed by a PostgreSQL row with a hard-coded `renewInterval` of 20 seconds, set once in the constructor and never made configurable or aware of transaction size/cost: [2](#0-1) 

The acquire query explicitly permits the row to be overwritten ("stolen") by a different `holder_txn_id` once `expired_at < NOW()`: [3](#0-2) 

Renewal only happens at discrete phase-vote boundaries, not continuously while a Gitaly node is doing the actual (potentially slow) work of locking refs on disk and writing the transaction (which for a large/complex push — many ref updates, large packfiles, expensive custom or update hooks) can take much longer than 20 seconds between the `PREPARED` and `COMMITTED` votes reaching Praefect. If that gap exceeds 20 seconds, transaction 1's lock silently expires and PostgreSQL awards it to a second, unrelated write on the same repository (`tryLock`'s `WHERE locks.expired_at < NOW() OR locks.holder_txn_id = $2` clause). Both transactions can now be inside the on-disk ref-locking window simultaneously — precisely the T1/T2 deadlock scenario the feature's own documentation states this mechanism exists to prevent: [4](#0-3) 

Unlike the reported bridge bug (where the fee calculator scaled cost but never enforced a gas reservation for the retry-write path), here the system computes a fixed TTL that never scales with the actual size/complexity of the reference transaction being protected, so a sufficiently large, fully ordinary push can silently exceed the budget and defeat the serialization guarantee.

### Impact Explanation
When the TTL lapses mid-transaction, two concurrent writers can race into Git's on-disk ref-locking phase for the same repository across different Gitaly nodes, reproducing the exact multi-node ref-lock deadlock condition described in `doc/serialized_writes.md` (`Why Serialize Writes`). A deadlocked reference-transaction hook stalls the write RPC on the affected nodes; because Gitaly's per-repository write path is a serialized/single-writer pipeline (`internal/gitaly/storage/storagemgr/partition/transaction_manager.go` documents "each repository has a single TransactionManager; it is the repository's single-writer"), a stuck reference-transaction effectively blocks all subsequent writes queued behind it for that repository until the stall times out or is manually intervened on, denying legitimate pushes, branch/tag operations, and any other mutating RPC against that repository. [5](#0-4) 

### Likelihood Explanation
The trigger requires no special privileges: any user able to push to a repository can construct a request with a large number of reference updates or a large amount of data that makes the `PREPARED`→`COMMITTED` window on the Gitaly side exceed 20 seconds (slow disks, many refs, expensive hooks, or simply large enough payloads/packfiles). The 20-second window is fixed regardless of push size, so this is a straightforward resource-exhaustion/timing race rather than a theoretical corner case, but it does require sustained slow processing (e.g., large-scale ref updates or an overloaded/slow storage backend) to realistically exceed the window, and the feature is currently gated behind the `praefect_serialized_write` feature flag which defaults to disabled. [6](#0-5) 

### Recommendation
- Scale the lock TTL (or renew cadence) to the size/cost of the transaction (number of ref updates, payload size) instead of using a fixed 20-second constant, similar to reserving enough "gas"/time budget for the whole critical section rather than pricing it after the fact.
- Alternatively, renew the lock continuously (e.g., via a background heartbeat goroutine tied to the transaction's lifetime) rather than only at phase-vote boundaries, so slow-but-legitimate work cannot silently outlive the lease.
- Detect and log/alert when a lock is "stolen" from a still-active transaction (i.e., `Renew` fails because the row's `holder_txn_id` no longer matches) and abort the stale transaction defensively instead of allowing it to proceed unprotected into the on-disk locking phase.
- Consider rejecting/streaming very large reference-transaction pushes so the locked critical section has a bounded worst-case duration.

### Proof of Concept
Not independently reproducible from static analysis alone — confirming the exact wall-clock threshold at which a "large" push's `PREPARED`→`COMMITTED` gap exceeds the fixed 20-second `renewInterval` (and thus triggers lock theft under `internal/praefect/datastore/lock_manager.go`'s `tryLock`/`renew`) would require running Praefect with `praefect_serialized_write` enabled against a live cluster under load, which is outside the scope of static code review.

```go
func (r *RepoReferenceWriteLockManager) tryLock(ctx context.Context, virtualStorage, relativePath string, txnID uint64,
) tryLockResult {
	lockID := repoLockID(virtualStorage, relativePath)
	// Register for a lock release notification before attempting the INSERT, so
	// that no release event can be missed between a failed attempt and the caller
	// beginning to wait, thus eliminating the race window between contention detection
	// and notification.
	notificationCh, deregister := r.handler.RegisterForLockRelease(lockID)

	query := `
INSERT INTO repository_reference_write_locks as locks (lock_id, holder_txn_id, expired_at)
VALUES ($1, $2, NOW() + $3::interval)
ON CONFLICT (lock_id) DO UPDATE
  SET holder_txn_id = EXCLUDED.holder_txn_id,
      expired_at    = EXCLUDED.expired_at
WHERE locks.expired_at < NOW() OR locks.holder_txn_id = $2
RETURNING lock_id, holder_txn_id, expired_at;`

	start := time.Now()
	rows, err := r.qc.QueryContext(ctx, query, lockID, txnID, r.renewInterval)
	r.operationDuration.WithLabelValues(virtualStorage, "trylock").Observe(time.Since(start).Seconds())
	if err != nil {
		r.lockAcquiredTotal.WithLabelValues(virtualStorage, "error").Inc()
		deregister()
		return tryLockResult{
			Acquired: false,
			Err:      fmt.Errorf("acquire repo reference write lock: %s, %w", lockID, err),
		}
	}
	defer func() {
		if err := rows.Close(); err != nil {
			r.logger.WithError(err).Error("close rows")
		}
	}()
	if rows.Next() {
		_, alreadyHeld := r.lockAcquiredAt.LoadOrStore(lockID, time.Now())
		if !alreadyHeld {
			r.locksHeld.WithLabelValues(virtualStorage).Inc()
			r.lockAcquiredTotal.WithLabelValues(virtualStorage, "new_acquisition").Inc()
		}
		deregister()
		unlockFn := func() error {
			return r.unlock(virtualStorage, relativePath, txnID)
		}
		renewFn := func(renewCtx context.Context) error {
			return r.renew(renewCtx, virtualStorage, relativePath, txnID)
		}
		return tryLockResult{
			Acquired: true,
			Unlock:   unlockFn,
			Renew:    renewFn,
		}
	}
```

```markdown
## Why Serialize Writes

The voting protocol relies on Git's `reference-transaction` hook to vote on a
ref update at each phase of the transaction. The phases Git historically
exposed are:

- `prepared` — references have been locked on disk
- `committed` — updates have been persisted
- `aborted` — the transaction was rolled back

Praefect collects votes from all Gitaly nodes participating in the transaction
and only allows the write to proceed when quorum is reached.

The problem is that at the `prepared` phase, **on-disk ref locks have already
been taken**. With two concurrent transactions T1 and T2 updating overlapping
refs A and B:

1. Node 1: T1 locks A, T2 locks B
1. Node 2: T2 locks A, T1 locks B

Each transaction is now waiting for the other to release a lock, and neither
can release until quorum is reached for its own lock. The cluster is
deadlocked.

The fix is to serialize transactions **before** any node has taken an on-disk
ref lock. If only one transaction per repository can advance past this point at
a time, lock acquisition order is globally consistent and the deadlock above
cannot occur.
```
