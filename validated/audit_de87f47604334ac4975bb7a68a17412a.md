### Title
Protocol fee bypass on MT/IMT `TokenDiff` intents via unit-splitting across the `amount > 1` threshold - (File: contracts/defuse/core/src/intents/token_diff.rs)

### Summary
`TokenDiff::token_fee` charges zero fee on `Nep245`/`Imt` tokens whenever the *per-intent* `|delta|` is `<= 1`, because the check is evaluated independently for each `TokenDiff::execute_intent` call rather than on the net amount of the token moved across the whole batch. An unprivileged signer (or two colluding signers) can therefore split a single intended transfer of `amount == 2` (or any larger amount) into multiple `TokenDiff` intents each with `|delta| == 1` on the same `TokenId`, causing `Pips::ZERO` to be charged on every leg while the aggregate, netted transfer is still `2` (or more).

### Finding Description
The binding the fee model is supposed to guarantee is: for a given `Nep245`/`Imt` `TokenId` `T`, `total_fee_charged(T) == Pips::fee_ceil(protocol_fee, total_negative_delta(T))` for the batch. What is actually implemented is per-intent, not per-token-aggregate: [1](#0-0) 

and the fee itself is computed with: [2](#0-1) 

`token_fee` only returns a non-zero `fee` when the `amount` **argument passed in that single call** exceeds `1`; for `Nep245`/`Imt` with `amount <= 1` it returns `Pips::ZERO` unconditionally, regardless of `protocol_fee`. Because `fees_collected` in `execute_intent` is accumulated per `TokenDiff` (line 57, reset for every intent) and each `TokenDiff.diff` is a `BTreeMap<TokenId, i128>` (one delta entry per token per intent), a signer can express "transfer 2 units of T" as two separate `TokenDiff` intents, each with `diff = {T: -1}`, submitted in the same `MultiPayload` (or split across two signers whose deltas are later matched together by `TransferMatcher::finalize`, which only nets balances after each intent's fee has already been independently taken): [3](#0-2) 

The netting/matching machinery (`TransferMatcher`) only cares that deltas across the batch sum to zero after fee-adjusted balance changes — it has no visibility into, and does not re-derive, what the "true" aggregate per-token amount was before splitting, so it cannot detect or correct the under-collection. Existing guards (`MultiPayload::verify`, nonce/salt checks, `assert_one_yocto`, `#[private]`/`#[pause]`) are irrelevant here since this is a purely arithmetic fee-calculation flaw, not an authorization bypass — each `TokenDiff` intent is validly signed by its own signer at `amount == 1`, which is exactly the boundary the check permits.

### Impact Explanation
This under-collects protocol fees that would otherwise be credited to `fee_collector` on `Nep245` (multi-token) and `Imt` legs whenever the true per-token swap amount is `> 1` but is expressed as multiple unit legs. The `fee_collector` account never receives the `fee_ceil` amount it is owed on the true aggregate transferred quantity, matching the "protocol fees bypassed or over-collected" Critical category. This is repeatable indefinitely — any signer (or colluding signer pair) can split any Nep245/Imt swap of size `N` into `N` unit legs to pay zero fees regardless of how large `N` is, as long as each leg individually satisfies `amount <= 1`.

### Likelihood Explanation
No special privileges, roles, or preconditions beyond normal usage are required: the attacker only needs a Verifier balance of the `Nep245`/`Imt` token and the ability to sign and submit a `MultiPayload` with multiple `TokenDiff` intents (or coordinate with a counterparty solver, which is a normal part of the intents settlement flow). The cost is simply constructing `N` intents instead of `1`, which is trivial and can be done for every swap involving these token types, making this fully feasible and repeatable across accounts, tokens, and batches.

### Recommendation
Compute and threshold the fee on the net, aggregated per-`TokenId` delta across the entire batch (post-`TransferMatcher`/settlement amount) rather than on the per-`TokenDiff`-intent delta, or remove the `amount > 1` exemption for `Nep245`/`Imt` and charge fees on `|delta|` unconditionally as is done for `Nep141`, so unit-splitting cannot zero out the fee on an aggregate amount greater than 1.
