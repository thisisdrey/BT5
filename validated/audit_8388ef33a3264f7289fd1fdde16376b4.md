### Title
Boundary timestamp comparison causes MET airdrop claim to be locked instead of transferred unlocked - (File: contracts/MetAirdrop.sol)

### Summary
The external report's bug class is an off-by-one timestamp boundary check: a `>` comparison used where `>=` was intended, so the exact deadline instant is mishandled. In Metronome, the reachable analog is `MetAirdrop._transferReward`, which uses `_end < block.timestamp` to decide whether a claim happens after the lock period. At exactly `block.timestamp == updatedAt + lockPeriod`, the lock period has expired by its own definition (`_end = updatedAt + lockPeriod`, i.e. "`lockPeriod` starts from `updatedAt`"), but the strict `<` check routes the claim down the esMET locking path anyway.

### Finding Description
`MetAirdrop` inherits `RecurringAirdrop.claim`, an unprivileged public function. On claim, `_transferReward` computes `_end = updatedAt + lockPeriod` and only transfers unlocked `MET` when `_end < block.timestamp` [1](#0-0) . When `block.timestamp == _end` the code instead computes `_remainLockPeriod = Math.min(Math.max(_end - block.timestamp, _min), _max)` where `_min = ESMET.MINIMUM_LOCK_PERIOD() + 1`, so the claim is locked into esMET for roughly `MINIMUM_LOCK_PERIOD` rather than paid out in liquid `MET` [2](#0-1) . The correct comparison for "the lock period has elapsed" is `_end <= block.timestamp`.

### Impact Explanation
A user who claims at the exact boundary timestamp (`block.timestamp == updatedAt + lockPeriod`) has their claimed `MET` forcibly locked into esMET for `MINIMUM_LOCK_PERIOD + 1` seconds when the code's own accounting says the lock period ended. This is a temporary freezing of funds / unexpected lock of claimed yield. The window is a single timestamp, so the practical impact is small and comparable in severity to the reference report (user inconvenience rather than permanent loss).

### Likelihood Explanation
The trigger requires a claim transaction to land in a block whose timestamp is exactly `updatedAt + lockPeriod`. Since `updatedAt` is set by a governor `updateMerkleRoot` call [3](#0-2)  and `lockPeriod` is 7 days by default, the boundary second exists once per merkle-root epoch. A user can deliberately time their claim for that second, so it is deterministic if anyone chooses to exercise it, but produces only a temporary lock and no fund theft, making exploitability low.

### Recommendation
Change the comparison to include the boundary:

```solidity
// contracts/MetAirdrop.sol
if (_end <= block.timestamp) {
    MET.safeTransfer(to_, amount_);
    return;
}
```

This makes the lock period truly expire at `updatedAt + lockPeriod`, consistent with the documented intent that "`lockPeriod` starts from the current merkle root update".

### Proof of Concept
Foundry-style test sketch (assumes `MetAirdrop`, an esMET stub exposing `MINIMUM_LOCK_PERIOD`/`MAXIMUM_LOCK_PERIOD`, and a funded merkle root):

```solidity
function test_claim_at_exact_expiry_locks_instead_of_transfers() public {
    // governor sets root; updatedAt = t0
    vm.prank(governor);
    airdrop.updateMerkleRoot(root, proofsHash);

    // warp to exactly updatedAt + lockPeriod
    vm.warp(airdrop.updatedAt() + airdrop.lockPeriod());

    // user claims with valid proof for (user, amount)
    vm.prank(user);
    airdrop.claim(amount, proof);

    // BUG: esMET.lockFor was called (MET locked ~MINIMUM_LOCK_PERIOD+1)
    // instead of MET.safeTransfer(user, amount)
    assertEq(met.balanceOf(user), 0);
    assertEq(esmet.lockedOf(user), amount);
}
```

With the fix (`_end <= block.timestamp`), the same call at the boundary timestamp transfers liquid `MET` to the user and makes no esMET lock.
