### Title
Cross-StackerDB Replay Attack Due to Missing Contract/Chain Binding in Chunk Signatures - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` computes the digest that is signed and verified for every StackerDB chunk using only `slot_id`, `slot_version`, and `data_hash` — it never includes the StackerDB's `contract_id` (or any other network/chain-binding value such as `network_id`/`rc_consensus_hash`). Because a signer's cryptographic commitment does not bind to the specific StackerDB replica it was created for, a valid chunk signature captured from one StackerDB contract can be replayed into a *different* StackerDB contract that happens to assign the same signer address to the same `slot_id`, exactly as in the reported cross-chain replay bug where a signed message lacking a chain-binding field can be replayed on a different chain.

### Finding Description
The signed digest is constructed in `auth_digest`: [1](#0-0) 

and used by both `sign()` and `verify()`: [2](#0-1) 

Note that `contract_id` is never part of the signed material. The `contract_id` only arrives out-of-band, e.g. in the HTTP path (`/v2/stackerdb/{contract}/{page}/chunks`) or in the P2P `StackerDBPushChunkData` message: [3](#0-2) 

When a chunk is accepted for storage, `try_replace_chunk` looks up the expected signer *for that specific contract's slot* and calls `slot_desc.verify(&slot_validation.signer)`: [4](#0-3) 

`verify()` only checks that the signature recovers to the expected signer address — it has no way to know, and does not check, that the signature was ever intended for *this* contract: [2](#0-1) 

The same gap exists in the P2P push-chunk validation path, `validate_received_chunk`, which similarly only checks slot signer, version and size — never the contract binding of the signature itself: [5](#0-4) 

Consequence: if the same `StacksAddress` is assigned the same `slot_id` in two different StackerDB smart contracts (a very realistic configuration — e.g. the signer-set StackerDB contracts rotate every reward cycle via `.signers-0-XXX` / `.signers-1-XXX`, each a fresh contract instance created with `create_stackerdb` and a version counter starting at 0, as seen in the boot contract `signers.clar`): [6](#0-5) 

then a chunk that was legitimately signed and broadcast for contract A can be captured off the wire (StackerDB traffic is public/unauthenticated to observe) and replayed — either via the unauthenticated `POST /v2/stackerdb/.../chunks` HTTP endpoint or via the P2P `StackerDBPushChunk` message — against contract B. Because the signature check only validates "was this signed by the address recorded as B's slot signer," and the digest contains no contract-identifying material, the replayed chunk passes verification and is written into B's replica store as if the signer had authored it there, and is further gossiped network-wide via `process_stacker_db_chunks`: [7](#0-6) 

This is the direct analog of the reported vulnerability: just as an Ethereum-style transaction without/with the wrong `chainId` can be replayed on another chain because the signature doesn't bind to the intended chain, a StackerDB chunk's signature doesn't bind to the intended StackerDB "chain" (its contract instance), enabling cross-context signature replay.

### Impact Explanation
This is an unauthenticated/unauthorized write to network-replicated state: an attacker with no privileged key can force acceptance and network-wide propagation of stale/forged-context data into a StackerDB replica that the true signer never intended to write to, by simply replaying an already-observed, validly-signed chunk from a different StackerDB contract. This matches the "Critical" bucket criterion of "unauthenticated/unauthorized write to state or StackerDB" and "network-wide propagation of forged data," since accepted chunks are rebroadcast via `broadcast_message` to the whole network.

### Likelihood Explanation
Exploitability requires only: (1) observing a validly signed chunk on the wire or via public HTTP StackerDB endpoints (StackerDB traffic is not encrypted/private), and (2) a target StackerDB contract that assigns the same signer address to the same `slot_id` with a version counter that hasn't yet caught up to the replayed version. This condition is realistically satisfiable for the signer-set StackerDBs, which rotate contract instances every reward cycle with fresh, low version counters while frequently retaining overlapping signer sets/slot assignments across cycles. No node secret, admin role, or other party's private key is needed — only re-transmission of already-public data.

### Recommendation
Include the `contract_id` (and ideally a chain/network-binding value such as the `network_id` or a `rc_consensus_hash` window) inside the signed digest computed by `SlotMetadata::auth_digest()`, and require verifiers to reconstruct/check that same binding before calling `verify()`. This mirrors EIP-155's fix of binding `chainId` into the signed payload: every `StackerDBChunkData`/`SlotMetadata` signature should cryptographically commit to the specific StackerDB contract it targets so a signature valid for one StackerDB instance cannot be replayed into another.

### Proof of Concept
1. Configure two StackerDB contracts, `A` and `B`, both listing address `S` as the signer for `slot_id = 0` (e.g., two reward-cycle instances of the signer StackerDB boot contract, or any two custom StackerDB-enabled contracts sharing a signer set).
2. Have `S` sign and publish/broadcast a `StackerDBChunkData { slot_id: 0, slot_version: 1, data: D }` for contract `A` (as in `libstackerdb/src/libstackerdb.rs` `sign()`/`auth_digest()`, which never references `A`).
3. As an attacker with no keys, capture this chunk (from the public P2P `StackerDBPushChunk` message or by hitting a node's `GET`/observing `POST /v2/stackerdb/A/0/chunks`).
4. Re-submit the identical `StackerDBChunkData` (unchanged `sig`, `slot_id`, `slot_version`, `data`) to a node's replica of contract `B` via `POST /v2/stackerdb/B/0/chunks`, or replay it as a `StackerDBPushChunk` with `contract_id = B`.
5. Observe that `StackerDBTx::try_replace_chunk` (`stackslib/src/net/stackerdb/db.rs:400-438`) accepts and stores the chunk under contract `B`'s slot 0, because `slot_desc.verify(&slot_validation.signer)` only checks the recovered public key against `B`'s recorded signer for slot 0 — which is also `S` — without any check that the signature was created for contract `A`. The forged-context chunk is then broadcast network-wide via `process_stacker_db_chunks` (`stackslib/src/net/relay.rs:2445-2452`).

    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
