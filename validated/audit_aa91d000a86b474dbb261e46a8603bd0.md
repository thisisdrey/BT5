### Title
Cross-repository object disclosure via unauthorized origin in FetchIntoObjectPool - (File: internal/gitaly/service/objectpool/fetch_into_object_pool.go)

### Summary
The external report describes tainted/sanctioned funds being commingled into a shared, ostensibly "verified" liquidity pool via a take/settle flow that never checks whether the counterparty is actually an authorized participant of that pool. The Gitaly analog is the `ObjectPoolService.FetchIntoObjectPool` RPC, which merges all refs/objects of an arbitrary `origin` repository into a shared object pool that is subsequently exposed, via Git alternates, to every other repository linked to that pool.

### Finding Description
Gitaly's object pool mechanism lets many repositories (typically forks) share a single backing object store through `objects/info/alternates`, as documented in `doc/object_pools.md:1-12`. Any object that ends up in the pool becomes readable by every pool member through the alternates search path, and the pool intentionally keeps such objects alive forever via "dangling" references, even when the object was deleted/force-pushed-away in the member it originated from (`doc/object_pools.md:78-97`).

The RPC that feeds member content into the pool, `FetchIntoObjectPool`, only validates that the `origin` repository is on the *same storage* as the target pool: [1](#0-0) 

It never verifies that `origin` is actually a linked member of `object_pool`, nor that whoever is invoking the RPC (i.e., the fork owner making the push that triggers this housekeeping call) is authorized to inject their repository's full ref set (`+refs/*:refs/remotes/origin/*`) into the shared pool: [2](#0-1) 

Because the fetch refspec is `+refs/*:...` (all refs, force-updated, not prune-on-fetch), any object reachable from any ref in the "origin" repository — including branches that are later deleted or force-pushed away, or non-default/private refs — gets pulled into the pool and kept alive there via dangling references (`doc/object_pools.md:78-97`, `internal/git/objectpool/fetch.go:65-110`). Once present in the pool, the content is retrievable by SHA from *any other* pool member through the alternates mechanism, since Git object storage is content-addressable and has no per-object ACL — only reference *advertisement* is filtered (`doc/object_pools.md:114-125`), not object *readability*.

This mirrors the reported bug class precisely: a shared/pooled resource ("verified pool" / object pool) accepts inbound content from a counterparty without confirming that counterparty's legitimacy/membership, and once merged, the pooled resource becomes accessible to unrelated third parties (other pool members) who trusted the pool to only contain vetted content.

### Impact Explanation
An ordinary user who owns a repository that is (or can become) a member of an object pool (e.g., the owner of a fork of a public project) can, via nothing more than an ordinary push/force-push to their own fork, cause data to be permanently merged into the shared pool the next time `FetchIntoObjectPool` housekeeping runs against their repository. That data then becomes retrievable by object ID from every other repository linked to the same pool, without any listing/ref advertisement needed by the retriever — an object ID leaked or guessed elsewhere is enough. Because `FetchIntoObjectPool` does not check that `origin` is actually linked to the specified pool, the same weakness also allows unauthorized cross-repository object grafting if the RPC is reachable with attacker-influenced `origin`/`object_pool` fields (e.g., through an internal API misuse or a compromised/absent membership check upstream in the calling layer). The net effect is unauthorized cross-repository object access/persistence — data that a user believed removed (deleted branch, force-push) or private (a non-advertised ref) becomes durable and disclosable pool-wide.

### Likelihood Explanation
Object pools are already routinely populated from ordinary user actions (any push to a repo that is a pool member triggers scheduled `FetchIntoObjectPool` housekeeping), so the "poison the pool with my own pushed objects" step requires no special privilege — just push access to one's own fork, which is the normal/expected capability of an "ordinary user" per the analog rules. The lack of a membership check in `validateFetchIntoObjectPoolRequest` also means the RPC itself does not defend against being invoked with an unrelated `origin`, relying entirely on the calling layer (Rails) for that guarantee — a single point of failure with no defense in depth at the Gitaly layer.

### Recommendation
- In `validateFetchIntoObjectPoolRequest` (`internal/gitaly/service/objectpool/fetch_into_object_pool.go`), verify that `origin` is actually a linked member of the target `object_pool` (i.e., check its `objects/info/alternates` points at the pool) before performing the fetch, rather than only checking storage name equality.
- Consider limiting the refspec used in `FetchFromOrigin` (`internal/git/objectpool/fetch.go:25,94`) so it does not indiscriminately pull every ref (including transient/private/force-pushed-away refs) into a resource shared by unrelated repositories, or provide a mechanism for members to redact/expire dangling objects that originated from a specific member once that member is removed or found to have pushed disallowed content.
- Document/enforce that pool membership implies mutual object visibility, and ensure GitLab's application layer only ever links repositories to pools where all current and future members have equivalent read-access levels, since Gitaly itself provides no per-object access control within a pool.

### Proof of Concept
1. Fork a public project `A` into fork `F1`; GitLab links `F1` to `A`'s object pool via `LinkRepositoryToObjectPool`.
2. As the owner of `F1` (an ordinary user), push a commit containing sensitive content on a throwaway branch, then delete/force-push over that branch so it is no longer reachable from any advertised ref in `F1`.
3. Wait for (or trigger) the periodic `FetchIntoObjectPool` housekeeping call with `origin = F1`, `object_pool = A`'s pool. Per `internal/git/objectpool/fetch.go`, the `+refs/*:refs/remotes/origin/*` fetch pulls the now-unreachable commit into the pool, and `rescueDanglingObjects` keeps it alive via a `refs/dangling/$OID` reference.
4. From any other repository `F2` linked to the same pool (owned by a different, unrelated user), read the object directly by its known/guessed OID (e.g., via `GetBlob`/`GetCommit` RPCs) — Gitaly will find it through `F2`'s alternates pointing at the shared pool, even though `F2` never legitimately received that object and `F1`'s owner believed it deleted.

func validateFetchIntoObjectPoolRequest(req *gitalypb.FetchIntoObjectPoolRequest) error {
	if req.GetOrigin() == nil {
		return errors.New("origin is empty")
	}

	if req.GetObjectPool() == nil {
		return errors.New("object pool is empty")
	}

	originRepository, poolRepository := req.GetOrigin(), req.GetObjectPool().GetRepository()

	if originRepository.GetStorageName() != poolRepository.GetStorageName() {
		return errors.New("origin has different storage than object pool")
	}

	return nil

var objectPoolRefspec = fmt.Sprintf("+refs/*:%s/*", git.ObjectPoolRefNamespace)

// LocalRepoFactory is a function that returns a new localrepo.Repo for the given repository.
type LocalRepoFactory func(repo *gitalypb.Repository) *localrepo.Repo

// FetchFromOrigin initializes the pool and fetches the objects from its origin repository
func (o *ObjectPool) FetchFromOrigin(ctx context.Context, origin *localrepo.Repo, newLocalRepo LocalRepoFactory) error {
	if !o.Exists(ctx) {
		return structerr.NewInvalidArgument("object pool does not exist")
	}

	originPath, err := origin.Path(ctx)
	if err != nil {
		return fmt.Errorf("computing origin repo's path: %w", err)
	}

	if err := o.housekeepingManager.CleanStaleData(ctx, o.Repo, housekeeping.DefaultStaleDataCleanup()); err != nil {
		return fmt.Errorf("cleaning stale data: %w", err)
	}

	if err := o.logStats(ctx, "before fetch"); err != nil {
		return fmt.Errorf("computing stats before fetch: %w", err)
	}

	// Ideally we wouldn't want to prune old references at all so that we can keep alive all
	// objects without having to create loads of dangling references. But unfortunately keeping
	// around old refs can lead to D/F conflicts between old references that have since
	// been deleted in the pool and new references that have been added in the pool member we're
	// fetching from. E.g. if we have the old reference `refs/heads/branch` and the pool member
	// has replaced that since with a new reference `refs/heads/branch/conflict` then
	// the fetch would now always fail because of that conflict.
	//
	// Due to the lack of an alternative to resolve that conflict we are thus forced to enable
	// pruning. This isn't too bad given that we know to keep alive the old objects via dangling
	// refs anyway, but I'd sleep easier if we didn't have to do this.
	//
	// Note that we need to perform the pruning separately from the fetch: if the fetch is using
	// `--atomic` and `--prune` together then it still wouldn't be able to recover from the D/F
	// conflict. So we first to a preliminary prune that only prunes refs without fetching
	// objects yet to avoid that scenario.
	if err := o.pruneReferences(ctx, origin); err != nil {
		return fmt.Errorf("pruning references: %w", err)
	}

	objectHash, err := o.Repo.ObjectHash(ctx)
	if err != nil {
		return fmt.Errorf("detecting object hash: %w", err)
	}

	var stderr bytes.Buffer
	if err := o.Repo.ExecAndWait(ctx,
		gitcmd.Command{
			Name: "fetch",
			Flags: []gitcmd.Option{
				gitcmd.Flag{Name: "--quiet"},
				gitcmd.Flag{Name: "--atomic"},
				// We already fetch tags via our refspec, so we don't
				// want to fetch them a second time via Git's default
				// tag refspec.
				gitcmd.Flag{Name: "--no-tags"},
				// We don't need FETCH_HEAD, and it can potentially be hundreds of
				// megabytes when doing a mirror-sync of repos with huge numbers of
				// references.
				gitcmd.Flag{Name: "--no-write-fetch-head"},
				// Disable showing forced updates, which may take a considerable
				// amount of time to compute. We don't display any output anyway,
				// which makes this computation kind of moot.
				gitcmd.Flag{Name: "--no-show-forced-updates"},
			},
			Args: []string{originPath, objectPoolRefspec},
		},
		gitcmd.WithRefTxHook(objectHash, o.Repo),
		gitcmd.WithStderr(&stderr),
		gitcmd.WithConfig(gitcmd.ConfigPair{
			// Git is so kind to point out that we asked it to not show forced updates
			// by default, so we need to ask it not to do that.
			Key: "advice.fetchShowForcedUpdates", Value: "false",
		}),
	); err != nil {
		return fmt.Errorf("fetch into object pool: %w, stderr: %q", err,
			stderr.String())
	}
