### Title
Path traversal via unvalidated `GitObjectDirectory`/`GitAlternateObjectDirectories` in custom hook environment construction - (File: internal/gitaly/hook/custom.go)

### Summary
The reported Solidity bug is a "trusted internal helper receives externally/attacker-influenced input through a path that bypasses the validation normally enforced on that data." The Gitaly analog is `customHooksEnv` in `internal/gitaly/hook/custom.go`, which builds the `GIT_OBJECT_DIRECTORY`/`GIT_ALTERNATE_OBJECT_DIRECTORIES` environment variables for admin-installed custom hooks directly from the `Repository` proto's `GitObjectDirectory`/`GitAlternateObjectDirectories` fields, without ever calling the path-escape validation (`storage.ValidateRelativePath`) that other, functionally identical code paths (e.g. `Repo.ObjectDirectoryPath`) explicitly perform.

### Finding Description
`internal/gitaly/hook/custom.go` builds the object-directory environment for custom hooks like this: [1](#0-0) 

Both `objectDirectory` and each `alternateObjectDirectory` are taken straight from `payload.Repo.GetGitObjectDirectory()` / `GetGitAlternateObjectDirectories()` and joined with `repoPath` via `filepath.Join`, with **no call** to `storage.ValidateRelativePath` or any traversal check.

Contrast this with the equivalent, and much more careful, resolution logic in `internal/git/localrepo/paths.go`, which explicitly validates the same kind of field and even has dedicated tests for `"../bazqux.git"`, `"/../bazqux.git"`, `"objects/../.."`, etc., all returning `codes.InvalidArgument`: [2](#0-1) [3](#0-2) 

The `Repository.GitObjectDirectory` / `GitAlternateObjectDirectories` fields are ordinary proto fields on every `Repository` message that flows through Gitaly (defined on the shared `storage.Repository` interface): [4](#0-3) 

These fields are populated by Rails/gitlab-shell during the pre-receive quarantine round-trip: Gitaly reports a quarantine object directory to Rails, and Rails echoes it back inside the `Repository` message on subsequent Gitaly RPCs (including the `PreReceiveHookRequest`/`PostReceiveHookRequest` that ultimately reach `customHooksEnv`): [5](#0-4) 

Because `customHooksEnv` skips the escape check that `ValidateRelativePath` performs elsewhere, a `GitObjectDirectory`/`GitAlternateObjectDirectories` value containing `../` sequences is joined verbatim against `repoPath` and exported as `GIT_OBJECT_DIRECTORY`/`GIT_ALTERNATE_OBJECT_DIRECTORIES` to the **admin-installed custom hook process**, which is spawned with these environment variables and will use them as its Git object search path.

### Impact Explanation
If the `GitObjectDirectory`/`GitAlternateObjectDirectories` value on the `Repository` message can be influenced with a traversal sequence when reaching this call site (e.g., through the Rails round-trip described in `doc/object_quarantine.md`, or through any RPC caller that sets these fields on the `Repository` message without Gitaly re-validating them before invoking custom hooks), the resulting `GIT_OBJECT_DIRECTORY`/`GIT_ALTERNATE_OBJECT_DIRECTORIES` environment can point the custom hook's `git` invocations at an arbitrary directory outside the intended repository/storage root. This is a cross-repository/storage object-access and information-disclosure risk (custom hooks can read/inspect objects from a directory outside the target repo) inside a component (`GitLabHookManager.customHooksEnv`) that other, parallel code paths in the same codebase treat as needing strict path-escape validation.

### Likelihood Explanation
The likelihood is moderate rather than high: reaching `customHooksEnv` with an attacker-crafted `GitObjectDirectory` requires that the value on the `Repository` message survive the pre-receive round trip to Rails and back without Rails or an intervening Gitaly RPC rejecting it. I was not able to fully verify, within the scope of my tools, whether any earlier layer (Rails or another Gitaly RPC) currently blocks traversal sequences in this specific field before it reaches `customHooksEnv`, since Rails-side validation is out of the Gitaly repo and could not be inspected. This uncertainty is the main open question a reviewer would need to close to fully confirm reachability by an ordinary user's push.

### Recommendation
Route `objectDirectory` and each entry of `alternateObjectDirectories` through `storage.ValidateRelativePath(repoPath, ...)` (the same validation already used in `internal/git/localrepo/paths.go`) inside `customHooksEnv` before joining them into `GIT_OBJECT_DIRECTORY`/`GIT_ALTERNATE_OBJECT_DIRECTORIES`, rejecting any value that escapes `repoPath`/the storage root.

### Proof of Concept
Not independently reproducible with the tools available in this session (no ability to run Gitaly, forge Rails responses, or execute a live push). The evidence supporting the finding is the direct code comparison between the unvalidated join in `customHooksEnv` (`internal/gitaly/hook/custom.go:172-190`) and the validated equivalent in `internal/git/localrepo/paths.go:36-41`, together with `paths_test.go`'s explicit traversal test cases confirming that unvalidated joins of this proto field are a recognized traversal vector elsewhere in the same codebase.
