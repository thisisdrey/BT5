### Title
Full re-credit on `ft_resolve_withdraw` malformed-JSON branch double-credits a `ft_transfer_call` that genuinely delivered funds - ([File: contracts/defuse/src/contract/tokens/nep141/withdraw.rs])

### Summary
`ft_resolve_withdraw` treats any promise result that fails `U128` JSON deserialization as `used = 0`, triggering a full refund of `amount` back to `sender_id`, regardless of whether the underlying FT contract `T` actually delivered the tokens to `receiver_id`. Since `T` is an attacker-deployed contract, the attacker fully controls both the real transfer semantics of `T` and the final JSON payload returned on the `ft_transfer_call` promise chain (the value returned by `T`'s own resolve step becomes `promise_result(0)` seen by `ft_resolve_withdraw`), letting them force this branch while genuinely delivering the tokens.

### Finding Description
The broken binding: `balance debited from sender_id in the Verifier (amount)` should equal `tokens delivered to receiver_id (amount) `. Instead, after the exploit: `ledger credit restored to sender_id (amount) + tokens delivered to receiver_id (amount) = 2 * amount`, while only `amount` was ever custodied on `T` by the Verifier.

Code path:
- `internal_ft_withdraw` schedules `do_ft_withdraw` (which calls `T::ft_transfer_call`) followed by `ft_resolve_withdraw` as a callback: [1](#0-0) 
- `do_ft_withdraw` forwards to `T::ft_transfer_call(receiver_id, amount, memo, msg)`: [2](#0-1) 
- `ft_resolve_withdraw` reads `promise_result_checked_json::<U128>(0)`; on a JSON deserialization failure of that promise result it sets `used = 0` and refunds the whole `amount` back to `sender_id` via `self.deposit`: [3](#0-2) 

Root cause: under NEAR's promise-chaining semantics, the return value the Verifier receives at `promise_result(0)` for `ft_transfer_call` is whatever value `T`'s own internal resolver/callback ultimately returns at the end of that receipt chain — entirely controlled by `T`'s implementation. Since `T` is attacker-deployed, the attacker can make `T` genuinely deliver `amount` to `receiver_id` (real accounting/transfer inside `T`) while returning a non-`U128` JSON value (e.g., a string) as the final resolved value. `ft_resolve_withdraw`'s `Ok(Err(_deserialize_err)) => 0` branch was written to be conservative against nothing failing, but it does not distinguish "receiver's `ft_on_transfer` legitimately signaled full success but the outer resolve payload was garbled" from "nothing happened" — it silently assumes the latter and issues a full refund.

Existing guards do not catch this: `promise_result_checked_json` only checks the receipt succeeded and attempts to parse JSON [4](#0-3) ; it cannot know whether `T`'s real state changed. `self.deposit` allows crediting locked accounts and performs no cross-check against `T`'s real balance [5](#0-4) .

Attacker's exact payload: deploy `T` such that `ft_transfer_call` performs genuine internal delivery of `amount` to `receiver_id`, but the final value returned through its own resolve step is JSON that is not a valid `U128` (e.g., a JSON string). Then sign/execute an `ft_withdraw` intent (or call `ft_withdraw` directly) with `token = T`, `amount`, and a non-empty `msg` (forcing `is_call = true`), targeting any `receiver_id` (can be the attacker's own external account).

### Impact Explanation
This breaks the Verifier's per-token solvency invariant for `TokenId::Nep141(T)`: after the exploit, the Verifier's internal ledger shows `sender_id` still credited `amount` of `T`, while the Verifier's actual custody balance on `T` has decreased by `amount` (delivered out to `receiver_id`). This is exactly the "batch whose balance changes do not net to zero so the Verifier owes more than it custodies" / "a refund or resolver credit that does not match what failed to settle" Critical category. It is repeatable per withdrawal against any token the attacker deploys, and the fabricated internal credit can subsequently be used in further `execute_intents` batches (e.g., transferred or swapped against real balances of counterparties who accept that `TokenId` in a `MultiPayload`), extending the blast radius beyond the attacker's own deposit.

### Likelihood Explanation
Fully unprivileged and self-contained: the attacker only needs to deploy their own FT contract `T` (fully permitted per the threat model), deposit `T` into the Verifier through the normal `ft_transfer_call`/deposit flow, and then call/sign `ft_withdraw` with `msg` set (to force the `ft_transfer_call`/`is_call = true` path) and `T` crafted to return non-`U128` JSON from the terminal promise value while still performing a genuine internal transfer. No relayer key, DAO role, or victim signature is required. Cost is limited to gas and deploying a contract.

### Recommendation
In `ft_resolve_withdraw` (and the analogous `nft_resolve_withdraw` / `mt_resolve_withdraw` deserialize-error branches), do not treat `Ok(Err(_deserialize_err))` as "nothing used." Treat malformed-but-successful promise results the same conservative way as promise failures (`Err(_) => amount.0`, i.e., assume it succeeded and do not refund), or require token contracts used by the Verifier to be pre-registered/vetted so a non-conforming return value cannot be forced by an arbitrary attacker-controlled contract.

### Proof of Concept
`cargo test` plan (near-workspaces sandbox), added under a non-excluded test path (e.g. `tests/src/tests/defuse/tokens/nep141.rs`):
1. Deploy a custom "evil FT" contract `T` whose `ft_transfer_call` genuinely credits `receiver_id`'s balance for `amount`, but whose final resolve callback returns a JSON string (e.g. `"\"oops\""`) instead of `U128`.
2. Deposit `amount` of `T` into `Defuse` for `attacker` (standard `ft_transfer_call` deposit flow).
3. Call `Defuse::ft_withdraw(token = T, receiver_id = attacker_external, amount, msg = Some("x"))` with 1 yoctoNEAR attached.
4. Assert both sides of the binding:
   - `T.balance_of(attacker_external) == amount` (real delivery happened).
   - `Defuse.mt_balance_of(attacker, Nep141TokenId(T)) == amount` (ledger credit was restored) — i.e. `debited(amount) < delivered(amount) + recredited(amount) == 2*amount`, proving the double credit.
