### Title
Unauthenticated Account Pre-Creation Lets Attacker Set Arbitrary `AccountType` for a Victim's Future Address - (File: actuator/src/main/java/org/tron/core/actuator/CreateAccountActuator.java)

### Summary
`CreateAccountActuator` lets any funded, unprivileged account broadcast an `AccountCreateContract` naming an arbitrary, not-yet-existing address as the new account and paying the creation fee itself. The validator never checks the requested `type`/`type_value` field, so the attacker fully controls the `AccountType` written to the victim address's permanent on-chain record before the victim ever transacts.

### Finding Description
`CreateAccountActuator.validate()` checks that the `ownerAddress` (payer) exists and has enough balance, that `accountAddress` is a valid address, and that no account already exists at `accountAddress` — but the check on `contract.getType()` is explicitly commented out: [1](#0-0) 

`execute()` then constructs the new `AccountCapsule` directly from the attacker-supplied contract, copying `type`/`typeValue` verbatim into the stored account: [2](#0-1) [3](#0-2) 

Unlike the flows that create an implicit `Normal` account on first transfer (`TransferActuator`, `ShieldedTransferActuator`), which hard-code `AccountType.Normal`: [4](#0-3) 

`CreateAccountActuator` accepts any `type` value chosen by the calling transaction, for any address the attacker chooses, as long as that address currently holds no account. There is no actuator in the codebase that subsequently changes an existing account's `type` field (`UpdateAccountActuator` only updates the account name): [5](#0-4) 

This mirrors the Mattermost bug class: an unauthenticated/low-privilege "signup"-like operation fails to restrict which fields the caller may set, letting an attacker pre-seed a victim's identity record with an unintended, effectively permanent value chosen by the attacker rather than by the eventual owner.

### Impact Explanation
By front-running any address that has not yet transacted (e.g., a freshly generated wallet address a victim intends to use, or a deterministic address the attacker can predict), an attacker can permanently fix that address's `AccountType` to something other than `Normal` before the legitimate owner ever interacts with the chain. Because no actuator can later change `type`, this state is irreversible for the life of the account. This is a form of unauthorized account-state manipulation of a third party's address performed without that party's signature or consent.

### Likelihood Explanation
Exploitation only requires an already-funded TRON account able to pay the (typically small, potentially zero) account-creation fee and knowledge of a target address that has not yet been used — both are trivial for any unprivileged actor. I was not able to fully enumerate every downstream actuator/precompile branch that keys off `AccountType` within the available time, so I cannot conclusively confirm every consequence (e.g., which specific privileged operations become permanently unavailable to the victim); this should be validated further before relying on a specific secondary impact (such as denial of asset-issuance or witness-related capability) beyond the proven, irreversible unauthorized field corruption itself.

### Recommendation
In `CreateAccountActuator.validate()`, restrict the accepted `type` to `AccountType.Normal` (re-enable and adjust the currently commented-out type check), matching the behavior already used for implicit account creation in `TransferActuator`/`ShieldedTransferActuator`. If non-`Normal` types must ever be settable, gate that ability behind ownership proof of the target address (e.g., require the target address's own signature) rather than allowing any third-party payer to dictate it.

### Proof of Concept
1. Attacker controls address `A` (funded) and knows victim's not-yet-used address `V`.
2. Attacker signs and broadcasts `AccountCreateContract{ owner_address = A, account_address = V, type = AssetIssue (or any non-Normal value) }`.
3. `CreateAccountActuator.validate()` passes because only `A`'s balance/address and `V`'s non-existence are checked — `type` is unchecked: [6](#0-5) 
4. `execute()` persists an `AccountCapsule` at `V` with the attacker-chosen `type`, paid for by `A`: [7](#0-6) 
5. The real owner of `V` later obtains the private key and begins using `V`, but its `AccountType` is permanently the attacker's chosen value — no code path exists to reset it, since `UpdateAccountActuator` only mutates `accountName`.

      Permission active = createDefaultActivePermission(contract.getAccountAddress(),
          dynamicPropertiesStore);

      this.account = Account.newBuilder()

          .setAddress(contract.getAccountAddress())
          .setTypeValue(contract.getTypeValue())
          .setCreateTime(createTime)
          .setOwnerPermission(owner)
          .addActivePermission(active)
          .build();
