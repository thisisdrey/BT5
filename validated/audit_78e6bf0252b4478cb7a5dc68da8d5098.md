### Title
Yield-bearing collateral/debt asset `stSTXbtc` is priced using the wrong reference oracle feed (STX price instead of BTC price) — analog of the Lido wstETH mispricing bug ([File: mainnet/contracts/utility/v0-1-data.clar])

### Summary
The `get-asset-price` helper used for collateral/debt USD accounting prices the yield-bearing asset `stSTXbtc` (a "liquid staked STX with BTC yield" token, per its own inline comment) by fetching the **STX** Pyth price feed instead of the **BTC** feed that its comment says should be used. This is the same root-cause pattern as the audited Lido finding: a wrapped/yield-bearing token's `price()`-equivalent function returns the value in terms of the wrong reference asset, producing a systematically incorrect USD valuation for a core protocol calculation (collateral/debt accounting).

### Finding Description
`get-asset-price` in `mainnet/contracts/utility/v0-1-data.clar` (and the mirrored `local-testing/contracts/utility/protocol-data.clar`) computes USD prices for every registered asset ID, including zTokens and yield-bearing wrapper tokens such as `stSTX` and `stSTXbtc`.

For `stSTX` (a liquid-staked STX token), the code correctly composes the base STX price with a staking ratio: [1](#0-0) 

For `stSTXbtc`, the inline comment explicitly states the intended pricing basis is the **BTC** price ("liquid staked STX with BTC yield"), yet the implementation calls `get-pyth-price PYTH-STX`: [2](#0-1) 

This mirrors the Lido bug exactly: `price()` in the audited report returned the wrap token's value in terms of the wrong "quote" asset (stETH instead of ETH); here, `get-asset-price` returns `stSTXbtc`'s value in terms of the wrong "quote" asset (STX instead of BTC). No conversion/ratio step is applied to translate between the STX-denominated feed and the BTC-denominated economic value the token actually represents, unlike the `resolve-ststx`/`CALLCODE-STSTX` pattern used elsewhere in the callcode system for comparable yield-ratio transformations: [3](#0-2) 

This price feeds directly into the collateral/debt USD accounting helpers: [4](#0-3) [5](#0-4) 

### Impact Explanation
Since BTC's USD price is typically orders of magnitude larger than STX's, using the STX feed to value a BTC-yield-denominated asset causes `stSTXbtc`'s USD value to be dramatically understated wherever these helpers are used to sum collateral or debt value. If `stSTXbtc`/`zstSTXbtc` participates in position collateral/debt accounting derived from this path, an understated debt value could let a borrower appear healthier than they actually are (bypassing the `is-healthy`/LTV check enforced elsewhere), or an understated collateral value could distort liquidation eligibility — both of which map to the in-scope "collateral/debt accounting" impact category and can lead to protocol insolvency or improper fund extraction.

### Likelihood Explanation
The bug is deterministic and always active whenever `get-asset-price` is invoked for asset ID `stSTXbtc`; it requires no attacker action beyond holding/borrowing/using the `stSTXbtc` asset, and the price discrepancy (STX vs BTC, ~4-5 orders of magnitude difference) is severe and immediately observable on every call.

### Recommendation
Change the `stSTXbtc` branch of `get-asset-price` to source the BTC Pyth feed (`PYTH-BTC`), consistent with the function's own comment, and — if `stSTXbtc` accrues a staking/redemption ratio analogous to `stSTX`'s `get-ststx-ratio`, apply that ratio on top of the correct base BTC price, mirroring the `resolve-ststx` pattern already used for `stSTX`.

### Proof of Concept
1. Register/enable `stSTXbtc` (asset ID `stSTXbtc`) as a collateral or debt asset.
2. Call `get-asset-price(stSTXbtc)` (or trigger `sum-collateral-usd`/`sum-debt-usd` via a position query that includes `stSTXbtc`).
3. Observe the returned price equals the current STX/USD Pyth price rather than a BTC-denominated value, understating `stSTXbtc`'s USD value by the STX/BTC price ratio.
4. A position holding `stSTXbtc` debt would show an artificially low USD debt value in the aggregated sum, allowing the position to pass health checks that rely on this aggregation while actually being economically unhealthy.
