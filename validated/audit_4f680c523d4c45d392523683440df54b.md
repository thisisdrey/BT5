### Title
Unbounded per-ref hook invocation in `receivePackReferenceUpdates()`/`procReceiveHook()` allows a single push to exhaust resources without any batching limit - ([File: internal/gitaly/hook/receivepack/receive_pack.go])

### Summary
`procReceiveHook()` and `receivePackReferenceUpdates()` iterate over the full, client-supplied list of reference updates from a single push (via the proc-receive protocol) and, for every single update, synchronously spawn the update hook and queue a `git-update-ref` transaction entry. There is no upper bound, batching, or pagination on the number of ref updates processed in this loop, unlike other list-processing RPCs in the codebase (e.g. `ListPoolUpstreams`, which explicitly caps batches at `objectPoolMembersBatchSize`).

### Finding Description
When a client pushes with the proc-receive protocol enabled, `procReceiveHook()` in `internal/gitaly/hook/receivepack/receive_pack.go` obtains `handler.ReferenceUpdates()` — a list derived directly from the client's push (arbitrarily many ref updates in one `git-receive-pack` invocation) — and processes it in one of two ways:

- Atomic case: calls `receivePackReferenceUpdates(ctx, cfg, req, repo, hookManager, handler.ReferenceUpdates(), handler, handler)` with the entire, unbounded slice. [1](#0-0) 
- Non-atomic case: `for _, update := range handler.ReferenceUpdates()`, invoking `receivePackReferenceUpdates` once per update. [2](#0-1) 

Inside `receivePackReferenceUpdates`, the code loops `for _, update := range updates` and, for every single ref, synchronously calls `hookManager.UpdateHook(...)` (which spawns the `update` hook subprocess and executes a full round trip, potentially including a call out to the GitLab Rails internal API) before queueing the ref update via `updater.Update(...)`: [3](#0-2) 

There is no cap on `len(updates)`, no chunking/offset+limit mechanism, and no early-exit heuristic for abnormally large ref-update sets — in contrast to the mitigation pattern the external report recommends (offset + length, as used elsewhere in the codebase for genuinely unbounded external inputs, e.g. `internal/gitaly/service/internalgitaly/list_pool_upstreams.go`'s `objectPoolMembersBatchSize` batching). [4](#0-3) 

The number of ref updates in a single push is client-controlled: an ordinary user with push access can construct a `git push` (or a raw `receive-pack`/proc-receive session) containing an arbitrarily large number of ref updates (e.g., many thousands of lightweight branch/tag pushes) in one request.

### Impact Explanation
For every ref update in the push, the server synchronously spawns/executes an `update` hook process and a call into the hook manager pipeline (which can include GitLab-side authorization checks) before continuing to the next update. With no cap on the number of updates processed inside a single RPC call, a large-enough push can cause the Gitaly worker handling the request to spend excessive CPU/process-spawn time and hold the underlying transaction/locks for an extended period, single-handedly exhausting per-request resources or exceeding RPC deadlines and causing the request to fail/timeout server-side (a self-inflicted DoS of the handler, analogous to the "run out of gas and revert" pattern from the external report: the whole operation fails due to unbounded iteration over an external list). This is a resource-exhaustion / handler-DoS concern reachable directly from an ordinary user's push, not a privileged or malicious-peer path.

### Likelihood Explanation
Likelihood is moderate: the proc-receive hook path is exercised whenever transactions are enabled and a compatible git client negotiates the proc-receive protocol; standard `git push` clients can send an essentially unbounded number of ref updates in a single request (Git itself imposes no low limit on ref counts per push). No special privileges beyond normal write access to the repository are required to trigger the unbounded loop.

### Recommendation
Apply the same batching/limit approach used elsewhere in the codebase (e.g., `objectPoolMembersBatchSize` / `listPoolUpstreamsBatchSize`) to `procReceiveHook`/`receivePackReferenceUpdates`: enforce a maximum number of ref updates processed per RPC invocation (rejecting or chunking oversized pushes), and/or bound the total time or number of hook invocations permitted within a single push before failing fast with a clear error rather than iterating unbounded over the full update list.

### Proof of Concept
1. As a user with push access to a repository where transactions/proc-receive are enabled, create a local repository and generate a very large number of branch refs (e.g., tens of thousands of trivially-different branches) pointing at existing objects.
2. Push all refs in a single `git push` invocation (`git push origin 'refs/heads/*'`) so that `handler.ReferenceUpdates()` returns a correspondingly large slice.
3. Observe that `procReceiveHook` (`internal/gitaly/hook/receivepack/receive_pack.go:100-139`) processes every single update via `receivePackReferenceUpdates`, which spawns the update hook subprocess per ref (`internal/gitaly/hook/receivepack/receive_pack.go:228-244`) without any batching or limit, causing the RPC handling the push to consume proportionally increasing CPU/time/process resources, potentially exceeding RPC timeouts or exhausting server resources for that request.
