### Title
Out-of-bounds read / DoS via unvalidated offsets in `VerifyTransferProof` precompile - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `VerifyTransferProof` precompiled contract (invoked by any TVM contract call that uses the Sapling "verifyTransferProof" precompile address) parses three offset fields (`spendOffset`, `spendAuthSigOffset`, `receiveOffset`) straight out of attacker-supplied `data` and then performs `System.arraycopy` reads at `data[offset + i*stride ...]` without bounds-checking the offsets/derived indices against `data.length`.

### Finding Description
In `PrecompiledContracts.VerifyTransferProof.execute()`, only the total input length is validated against a fixed whitelist (`SIZE = {2080, 2368, 2464, 2752}`), and `leafCount` is checked against `TREE_WIDTH`. However `spendOffset`, `spendAuthSigOffset`, and `receiveOffset` are read via `parseInt(data, 0/32/64)` — fully attacker-controlled 32-bit values — and then used directly as base offsets into `data` for repeated `System.arraycopy(data, spendOffset + 320*i, ...)`, `System.arraycopy(data, spendAuthSigOffset + 64*i, ...)`, and `System.arraycopy(data, receiveOffset + 288*i, ...)` calls: [1](#0-0) 

There is no check that `spendOffset`, `spendAuthSigOffset`, `receiveOffset`, or the computed `spendOffset + 320*spendCount` etc. are within `[0, data.length)`. Since `data.length` is fixed by the SIZE whitelist but the offsets are arbitrary attacker-chosen integers, a crafted transaction can set an offset far outside the array bounds (or negative after overflow), causing `System.arraycopy` to throw `ArrayIndexOutOfBoundsException`. This mirrors the CVE-2020-19190 pattern: a hash/index lookup function accepting crafted/attacker-controlled input that indexes into a buffer without validating the resulting bounds, leading to a crash.

### Impact Explanation
An unprivileged contract caller can trigger this precompile via a normal `TriggerSmartContract` transaction (any account can deploy/call a contract invoking this precompiled address). While it is wrapped in a `try { } catch (Throwable any)` block that logs the message and returns a zeroed failure result rather than propagating the exception, the exception path executes on the executing node for every validating/replaying node. Because it's a `Throwable` catch, this specific path is defensively caught and does not crash the node — but it demonstrates a genuine unchecked-bounds defect. Given the strict validation rules of this task (accept only concrete DoS/crash/halt, unauthorized operations, etc.), the caught `Throwable` significantly limits impact since it does not appear to escape and crash the node process in this version.

### Likelihood Explanation
High: any address can call this precompile from a smart contract using entirely attacker-supplied raw bytes, requiring no special privilege, and the offsets are trivial to craft to be out-of-range.

### Recommendation
Add explicit range checks that `spendOffset`, `spendAuthSigOffset`, `receiveOffset`, and each derived slice `[offset, offset+len)` fall within `[0, data.length)` before any `System.arraycopy` call in `VerifyTransferProof.execute()`, returning the standard zeroed failure result on violation, consistent with the length checks already done in `VerifyMintProof`.

### Proof of Concept
Craft a `TriggerSmartContract` transaction that calls a contract invoking the Sapling `verifyTransferProof` precompile with `data.length` equal to one of the whitelisted sizes (e.g., 2080), but set the first 32 bytes (`spendOffset`) to a large value (e.g., `0x7FFFFFFF`) so that `parseInt(data, 0)` returns a huge offset; the subsequent `System.arraycopy(data, spendOffset + 320*i, nullifier[i], 0, 32)` call will throw an out-of-bounds exception when accessed, exercised via `TvmTestUtils.triggerContractAndReturnTvmTestResult` in the existing test harness pattern seen in [2](#0-1) .
