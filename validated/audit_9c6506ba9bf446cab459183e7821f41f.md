### Title
Wrong exec-fee accounting for gas-key `AddKey`/`TransferToGasKey` under-prices reserved gas, silently burning total supply - (File: `runtime/runtime/src/config.rs`, `runtime/runtime/src/access_keys.rs`)

### Summary
The gas-key host path reserves the exec (storage) fee for a public key using its full wire length (`PublicKey::len()`), while the pre-execution/refund accounting path (`gas_key_send_pk_len` and the exec-fee equivalent) prices the same key using the shorter on-trie identifier length (`PublicKey::trie_id_len()`) when `fix_ml_dsa_cost_charging` is disabled. This mismatch — analogous to the `InfinityPool.writeOff` bug where an accounting variable (`totalBorrowed`) is decremented by the wrong (smaller) amount instead of the true amount owed — causes gas that was reserved/charged at one size to never be burnt nor refunded at the other size, permanently and silently destroying tokens from total supply for ML-DSA-65 (post-quantum) gas keys.

### Finding Description
In `runtime/runtime/src/config.rs`, `gas_key_send_pk_len` explicitly documents the discrepancy: [1](#0-0) 

which shows that pre-`FixMlDsaCostCharging` behavior deliberately uses `public_key.trie_id_len()` (the short, on-trie hashed form, 33 bytes for ML-DSA-65) for pricing, rather than `public_key.len()` (the true 1953-byte wire form). This function feeds into `total_send_fees` for `TransferToGasKey`/`WithdrawFromGasKey` and (analogously) into the exec-fee accounting used by `refund_unspent_gas_and_deposits` and gas-key `AddKey` processing in `runtime/runtime/src/access_keys.rs`.

Meanwhile, the actual VM/host execution path that reserves gas for a gas-key `AddKey` operation charges based on the full wire-length key (`len()`), because that's the actual data written/handled at that layer. The regression test explicitly documents the resulting bug: [2](#0-1) 

"Before this fix, the pre-execution / refund path priced the key on `trie_id_len()` (33 bytes) while the host path reserved the exec fee on `len()` (1953); the extra reserved gas was neither burnt nor refunded, so total supply silently dropped."

This is precisely the reported bug class: an accounting variable (here, the gas/token amount that should be released back into supply via burn+refund reconciliation) is decremented/tracked using the wrong (smaller) reference value instead of the true amount that was actually reserved, causing a systematic and silent loss rather than an explicit accounting failure that would be caught by an invariant check.

The fix, gated behind `ProtocolFeature::FixMlDsaCostCharging`, corrects this by splitting the two fee kinds correctly: send (wire transmission) fees use `len()`, exec (storage) fees use `trie_id_len()`, consistently across both the pricing and the host-reservation paths: [3](#0-2) 

Critically, this fix is **not active on the stable protocol version** used by this codebase: [4](#0-3) [5](#0-4) 

`FixMlDsaCostCharging` activates at protocol version 153, while `STABLE_PROTOCOL_VERSION` is 87. Therefore the buggy under-accounting behavior described above is the **live, currently-active behavior** for any ordinary user submitting an ML-DSA-65 (post-quantum) gas-key transaction on the current stable protocol.

### Impact Explanation
Every time an account adds an ML-DSA-65 gas key or performs a `TransferToGasKey`/`WithdrawFromGasKey` action with an ML-DSA-65 public key, the discrepancy between the wire-length-priced host reservation and the trie-id-length-priced accounting causes gas tokens to be reserved from the signer's balance but never fully accounted as either burnt (added to `tx_burnt_amount`/`balance_burnt`) or refunded back to the signer. This is a direct, silent token-loss bug: total supply invariants (`new_total_supply = prev.total_supply + minted - balance_burnt`) become desynchronized from the actual amount of currency destroyed, and end users lose real NEAR tokens with no accounting trail, reachable by any ordinary client submitting a standard transaction (no privileged or malicious-node access required). This matches the "token loss" acceptance criterion directly.

### Likelihood Explanation
This requires no adversarial setup: any regular user or wallet using an ML-DSA-65 (post-quantum) key as a gas key — a feature explicitly supported by the protocol (NEP for post-quantum signatures) — will trigger the mispricing on every relevant transaction. Given PostQuantumSignatures and GasKeys are both live features at v85 (below stable v87), and `FixMlDsaCostCharging` is nightly-only (v153), the vulnerable code path is reachable today by ordinary transaction submission with no chunk-producer, malicious-peer, or operator privileges needed.

### Recommendation
Enable/backport `ProtocolFeature::FixMlDsaCostCharging` (or an equivalent protocol-version-gated fix) to the stable path, ensuring that the exec (storage) fee for gas-key public keys is consistently priced by `trie_id_len()` at every reservation and refund site, and the send (transmission) fee is consistently priced by `len()`. Add or promote the existing regression test `test_gas_key_add_key_conserves_supply` (and the wire-length send-fee test) into the default/stable protocol version's test matrix to guard the supply-conservation invariant end-to-end for ML-DSA-65 gas keys before considering this resolved for mainnet.

### Proof of Concept [6](#0-5) 
The existing test `test_gas_key_add_key_conserves_supply` (currently skipped when `FixMlDsaCostCharging` is not enabled at `PROTOCOL_VERSION`, i.e., under the stable configuration) demonstrates the exploit path: a contract call batches `batch_create` + `action_add_gas_key_with_full_access` with an ML-DSA-65 public key from a single signed transaction (closing the balance-accounting scenario), and asserts that Alice's balance decrease equals the recorded `destroyed` (burnt) amount. Running this scenario at the stable protocol version (where the fix is disabled) reproduces the supply leak: Alice's balance decreases by more than what is recorded as burnt, confirming tokens are silently destroyed exactly as in the reported wrong-accounting bug class.

/// Public-key byte length for a gas-key SEND (transmission) fee computation.
fn gas_key_send_pk_len(config: &RuntimeConfig, public_key: &PublicKey) -> usize {
    if config.wasm_config.fix_ml_dsa_cost_charging {
        // This is the proper value - send fee should be based on how many bytes
        // the key occupies on the wire, not in storage.
        public_key.len()
    } else {
        // Preserve the (incorrect) existing behavior if the fix is not enabled.
        // Otherwise, we would break protocol consensus.
        public_key.trie_id_len()
    }
}
