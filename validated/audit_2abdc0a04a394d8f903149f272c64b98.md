### Title
Missing integrity enforcement for `remote_file_urls` entries without a matching `remote_file_integrity` key allows unverified file content in `http_archive` overlays - (File: tools/build_defs/repo/utils.bzl)

### Summary
`download_remote_files()` in `tools/build_defs/repo/utils.bzl` fetches every URL declared in the `remote_file_urls` attribute of `http_archive`, but only enforces a checksum for a given path if that same path key is *also* present in the `remote_file_integrity` dict. When the key is missing, the function silently passes `integrity = ""` to `ctx.download()`, which disables checksum verification entirely for that file. [1](#0-0) 

### Finding Description
`download_remote_files()` builds one `ctx.download()` call per entry of `ctx.attr.remote_file_urls`, and looks up the corresponding integrity value with `ctx.attr.remote_file_integrity.get(path, "")`:

```
pending = {
    path: ctx.download(
        remote_file_urls,
        path,
        canonical_id = ctx.attr.canonical_id,
        auth = get_auth(ctx, remote_file_urls) if auth == None else auth,
        integrity = ctx.attr.remote_file_integrity.get(path, ""),
        block = False,
        executable = True,
    )
    for path, remote_file_urls in ctx.attr.remote_file_urls.items()
}
``` [2](#0-1) 

This `remote_file_urls` / `remote_file_integrity` pair is the mechanism used by `http_archive` to overlay extra files (e.g., registry-provided `BUILD` files or patch-equivalent files) into a fetched repository. Contrast this with the sibling `remote_module_file_urls` mechanism a few lines below in the same file, which explicitly `fail()`s if no integrity value is set:

```
remote_module_file_urls = getattr(ctx.attr, "remote_module_file_urls", [])
if remote_module_file_urls:
    if not ctx.attr.remote_module_file_integrity:
        fail("remote_module_file_integrity must be set when remote_module_file_urls is set")
``` [3](#0-2) 

No equivalent enforcement exists for `remote_file_urls`/`remote_file_integrity`. `_update_http_archive_integrity_attrs` in `http.bzl` only compares the *computed* `integrity.remote_files` map against the currently declared `remote_file_integrity` attribute for lockfile reproducibility purposes; it does not require that every path in `remote_file_urls` have a corresponding entry, nor does it fail the build if one is missing at fetch time. [4](#0-3) 

Any producer that assembles the `remote_file_urls` map for a module (a module extension implementation, or ultimately data derived from a registry's module `source.json` describing overlay files) can therefore supply a URL/path pair with no matching hash — either intentionally, or because of a benign key-mismatch (differing path normalization, encoding, or a stale/incomplete integrity map). Bazel will download and materialize that file's bytes from whatever origin serves that URL, entirely unauthenticated, while treating the fetch as successful and reproducible-looking, since the missing key silently degrades to "no integrity requested" rather than failing loudly like the `remote_module_file_*` path does.

### Impact Explanation
This breaks the invariant that "integrity is binding" for content fetched into a repository: a hostile or compromised mirror/origin serving one of the `remote_file_urls` entries can substitute arbitrary bytes for that file (e.g. a `BUILD` file, a source file used to overlay a registry module) without the discrepancy being detected, because the intended checksum gate (`remote_file_integrity`) is not actually mandatory per-path. Since these overlay files become build inputs of the affected repository, this can lead to injection of attacker-controlled Starlark/BUILD content into a build that is nominally checksum-pinned.

### Likelihood Explanation
Exploitability depends on producing a `remote_file_urls`/`remote_file_integrity` pair with a key mismatch (missing/misspelled path, or a registry/extension author omitting an integrity entry for one file while still declaring its URL). This is plausible in registry-provided overlay data or hand-written module extensions, and, unlike the archive's own `sha256`/`integrity` attribute (which is validated end-to-end and surfaced in error messages/tests such as `test_sha256_incorrect`), there is no test coverage or enforcement guaranteeing `remote_file_integrity` fully covers `remote_file_urls`. [5](#0-4) 

### Recommendation
Mirror the enforcement already applied to `remote_module_file_urls`: in `download_remote_files()`, fail loudly if a path in `remote_file_urls` does not have a corresponding non-empty entry in `remote_file_integrity`, instead of silently defaulting to an empty (i.e., unverified) integrity string.

### Proof of Concept
A reproducible shell-test analog (in the style of `src/test/shell/bazel/external_remote_file_test.sh`) would:
1. Start a local file server serving a "legit" file content at `/overlay/foo.txt` and compute its integrity hash.
2. Define an `http_archive` (or a module extension building its `remote_file_urls`/`remote_file_integrity` attrs) with:
   - `remote_file_urls = {"overlay/foo.txt": ["http://127.0.0.1:$port/overlay/foo.txt"]}`
   - `remote_file_integrity = {}` (i.e., omit the key for `overlay/foo.txt`, simulating a mismatched/incomplete map from a hostile registry/extension).
3. Replace the served content at `/overlay/foo.txt` with attacker-controlled bytes.
4. Run `bazel build @repo//...` and observe that the build succeeds and materializes the attacker-controlled `overlay/foo.txt` unmodified, with no checksum error — demonstrating the missing-key path bypasses verification entirely, unlike the `sha256`/`integrity` mismatch case on the main archive URL which fails per `test_sha256_incorrect`. [1](#0-0)

def _update_http_archive_integrity_attrs(ctx, attrs, integrity):
    integrity_override = {}

    # We don't need to override the integrity attribute if sha256 is already specified.
    # remote_module_file_integrity is for internal use by Bazel only and always
    # set correctly.
    if not ctx.attr.sha256 and not ctx.attr.integrity:
        integrity_override["integrity"] = integrity.archive
    if ctx.attr.remote_file_integrity != integrity.remote_files:
        integrity_override["remote_file_integrity"] = integrity.remote_files
    if ctx.attr.remote_patches != integrity.remote_patches:
        integrity_override["remote_patches"] = integrity.remote_patches
    if not integrity_override:
        return ctx.repo_metadata(reproducible = True)
    return ctx.repo_metadata(attrs_for_reproducibility = update_attrs(ctx.attr, attrs.keys(), integrity_override))

def _http_archive_impl(ctx):
    """Implementation of the http_archive rule."""
    if ctx.attr.build_file and ctx.attr.build_file_content:
        fail("Only one of build_file and build_file_content can be provided.")

    if ctx.attr.strip_prefix and ctx.attr.strip_components:
        fail("Only one of strip_prefix and strip_components can be provided.")

    source_urls = _get_source_urls(ctx)
    download_info = ctx.download_and_extract(
        source_urls,
        ctx.attr.add_prefix,
        ctx.attr.sha256,
        ctx.attr.type,
        ctx.attr.strip_prefix,
        strip_components = ctx.attr.strip_components,
        canonical_id = ctx.attr.canonical_id or get_default_canonical_id(ctx, source_urls),
        auth = get_auth(ctx, source_urls),
        integrity = ctx.attr.integrity,
    )
    workspace_and_buildfile(ctx)

    remote_files_info = download_remote_files(ctx)
    remote_patches_info = patch(ctx)
    symlink_files(ctx)

    integrity = struct(
        archive = download_info.integrity,
        remote_files = {path: info.integrity for path, info in remote_files_info.items()},
        remote_patches = {url: info.integrity for url, info in remote_patches_info.items()},
    )

    return _update_http_archive_integrity_attrs(ctx, _http_archive_attrs, integrity)
