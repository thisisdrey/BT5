### Title
Unbounded memory allocation via attacker-controlled length fields in `ValidateMultiSign`/`BatchValidateSign` precompiles - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `extractBytesArray`/`extractSigArray`/`extractBytes32Array` helpers used by the `ValidateMultiSign` and `BatchValidateSign` TVM precompiled contracts read 32-byte length fields directly out of attacker-supplied calldata and use them, unchecked against the actual size of the calldata, to size a `byte[]` allocation via `Arrays.copyOfRange`. This mirrors the libarchive `apply_substitution` bug class: a small, cheap crafted input encodes an oversized "count/length" value that is trusted for allocation before any bound related to the real input size is enforced.

### Finding Description
`extractBytesArray` reads an item count and, per item, an independent length field taken from the word array, then calls `extractBytes`: [1](#0-0) [2](#0-1) 

`extractBytes` calls `Arrays.copyOfRange(data, offset, offset + len)`, which — regardless of the actual size of `data` — always allocates a new array of length `len` (zero-padding for indices beyond the source array). Since `bytesLen` is parsed straight from `words[offset + bytesOffset + 1].intValueSafe()`, an attacker can set it to a value up to `Integer.MAX_VALUE` while the actual calldata (`rawData`) remains tiny.

This is reached from `ValidateMultiSign.execute` and `BatchValidateSign.doExecute`, both callable by any account via a plain TVM `CALL`/`STATICCALL` to the corresponding precompile address, no special privilege required: [3](#0-2) [4](#0-3) 

Critically, the only pre-allocation guard present (`sigArraySize`/`addrArraySize > MAX_SIZE`) bounds the *item count*, not the *per-item length* (`bytesLen`). That guard is also gated behind `VMConfig.allowTvmSelfdestructRestriction()`: [5](#0-4) 
Even when this flag is active, the per-item `bytesLen` used inside `extractBytesArray` is never validated against the true size of `rawData` before the `Arrays.copyOfRange` allocation, so the mitigation does not close this path.

Energy accounting for these precompiles is computed purely from the *outer* calldata length (`data.length / WORD_SIZE`), not from the internal length fields that drive the allocation: [6](#0-5) 
So a caller pays for a small calldata footprint while triggering a multi-gigabyte allocation attempt inside the JVM.

### Impact Explanation
A single crafted contract call (or `TriggerConstantContract`/`TriggerSmartContract` transaction) that invokes `ValidateMultiSign` or `BatchValidateSign` with a small, cheap calldata payload encoding an oversized length word can force the node to attempt a very large heap allocation. This can throw `OutOfMemoryError` inside `Arrays.copyOfRange`, which is not caught in `ValidateMultiSign.execute` (only `OutOfTimeException` is special-cased, other `Throwable` are logged and swallowed for permission errors, but an `OutOfMemoryError` is an `Error`, not caught by the generic `catch (Throwable t)` semantics reliably, and can destabilize the JVM/node process regardless). This is a low-cost, unprivileged denial-of-service against any full node/SR that executes the transaction, matching the "node crash or halt" impact category.

### Likelihood Explanation
Likelihood is high: the precompiles are reachable by any address via a simple smart-contract call with no special permission, the crafted calldata is small (cheap to construct and broadcast), and the vulnerable code path executes during normal contract execution/transaction validation performed by every node.

### Recommendation
Bound every length field extracted from calldata against the true remaining size of `data` before it is used for allocation. Specifically, in `extractBytesArray`/`extractSigArray`/`extractBytes32Array`, validate `bytesLen` (and `len`) against `data.length` (or a hard maximum such as `SIG_LENGTH`/a small constant) before calling `extractBytes`/`Arrays.copyOfRange`, and reject/return failure if the encoded length exceeds what the actual calldata can support, independent of the `allowTvmSelfdestructRestriction` feature flag.

### Proof of Concept
Construct calldata for `validatemultisign(address,uint256,bytes32,bytes[])` where the ABI-encoded dynamic `bytes[]` array header at the offset read by `words[3]` reports one item whose per-item length word (`bytesLen`) is set to a huge value (e.g., `0x7FFFFFFF`), while the overall calldata blob remains only a few hundred bytes. When `ValidateMultiSign.execute` (or the analogous field in `BatchValidateSign`) calls `extractBytesArray` → `extractBytes` → `Arrays.copyOfRange(data, offset, offset + 0x7FFFFFFF)`, the JVM attempts to allocate a ~2GB array from a transaction whose declared energy cost (computed only from `data.length`) is minimal, as shown at: [7](#0-6)

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
