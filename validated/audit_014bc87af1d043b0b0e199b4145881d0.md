### Title
Unchecked return value of `AccountCapsule.reduceAssetAmountV2` in `ExchangeInjectActuator`/`ExchangeTransactionActuator` allows inflating exchange pool without paying the token - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java])

### Summary
`ExchangeInjectActuator.execute()` and `ExchangeTransactionActuator.execute()` call `AccountCapsule.reduceAssetAmountV2(...)`, a method that returns `boolean` to signal whether the deduction actually succeeded, but the return value is discarded. `reduceAssetAmountV2` silently returns `false` (without throwing) whenever the current asset amount map entry is missing or the requested amount is not `<=` currentAmount, leaving the account's asset balance completely untouched. Because the callers never check this boolean, execution proceeds to update the `ExchangeCapsule` pool balances (crediting the injected/traded amount) and commits the account, even in code paths where the actual token deduction from the user silently failed.

### Finding Description
This mirrors the reported Solidity bug class: a call whose success is signaled via a boolean return value is invoked but never validated, so a "failed" outcome is treated identically to a "succeeded" outcome by the surrounding logic.

In `AccountCapsule`, `reduceAssetAmountV2` is a conditional, non-throwing balance-mutation primitive: [1](#0-0) 

Other call sites in the codebase correctly check the return value and abort the transaction (`throw new ContractExeException/BalanceInsufficientException`) when it is `false`: [2](#0-1) [3](#0-2) 

But in `ExchangeInjectActuator.execute()`, both calls to `reduceAssetAmountV2` ignore the boolean result: [4](#0-3) 

Immediately afterward, the exchange pool balances (already computed/incremented earlier in the same method) are persisted via `Commons.putExchangeCapsule`, and the transaction is marked `SUCESS`: [5](#0-4) 

The same unchecked pattern exists in `ExchangeTransactionActuator.execute()` for the `reduceAssetAmountV2` call (the `addAssetAmountV2` call there is comparatively less concerning because that method always returns `true`): [6](#0-5) 

`validate()` in `ExchangeInjectActuator` calls `accountCapsule.assetBalanceEnoughV2(tokenID, tokenQuant, dynamicStore)` before `execute()`, which is intended to guarantee sufficient balance: [7](#0-6) 

However, `validate()` and `execute()` read the `AccountCapsule` from the store independently and operate on the in-memory asset map at different times relative to the same transaction/block-processing pipeline. `reduceAssetAmountV2`'s failure condition (`currentAmount == null` or `amount > currentAmount`) can diverge from `assetBalanceEnoughV2`'s check when the underlying asset storage mode (`AllowSameTokenName` = 0 vs 1) mismatches the key used, or when the `AssetIssueCapsule` lookup inside `reduceAssetAmountV2` (`assetIssueStore.get(key)`) behaves differently than the `assetBalanceEnoughV2` lookup — both paths independently branch on `dynamicPropertiesStore.getAllowSameTokenName()`, and a discrepancy between the asset map used for validation and the one mutated in `execute()` (e.g., `Map` vs `MapV2`, or a missing map entry under `getAllowSameTokenName() == 0` when only a V2 entry exists) causes `reduceAssetAmountV2` to return `false` while `assetBalanceEnoughV2` returned `true`, or vice versa across the checkpoint boundary of AllowSameTokenName toggling mid-flight. Because the return value is never checked in `execute()`, this silent-failure path is unguarded — the actuator will still commit an increased exchange-pool balance for tokens the user never actually paid.

### Impact Explanation
If `reduceAssetAmountV2` returns `false` in `execute()` (silent no-op), the caller's account is not actually debited for the injected/traded token, yet the `ExchangeCapsule` (an internal AMM-like liquidity pool) balance is incremented as though the deposit occurred. This creates an unbacked increase in the exchange pool's recorded token balance relative to what accounts actually hold — a discrepancy that directly corresponds to "unbacked balance" / inflation of tradable liquidity, which other users can subsequently trade against via `ExchangeTransactionActuator`, extracting real value they did not pay for. This satisfies the "unbacked balance / theft of funds" bar in the validation rules.

### Likelihood Explanation
Reaching the divergent-failure branch requires a state where `assetBalanceEnoughV2` (used in `validate()`) and `reduceAssetAmountV2` (used in `execute()`) disagree about the presence/amount of the asset entry for the same key — most plausibly around the legacy vs V2 asset map split governed by `dynamicPropertiesStore.getAllowSameTokenName()`, or via unusual token-key edge cases (e.g., token id not yet imported via `importAsset(key)` producing a null `currentAmount` in one map but not the other). This is a narrower/more state-dependent condition than a straightforward reentrancy or arithmetic bug, so likelihood is assessed as Medium rather than High, consistent with the reported bug's own "Medium" severity for the analogous unchecked-return-value pattern.

### Recommendation
In `ExchangeInjectActuator.execute()` and `ExchangeTransactionActuator.execute()`, check the boolean returned by every `reduceAssetAmountV2`/`addAssetAmountV2` call and abort the transaction (throwing `ContractExeException`, mirroring the pattern already used in `TransferAssetActuator` and `Commons.adjustAssetBalanceV2`) whenever the call returns `false`, instead of silently proceeding to credit the exchange pool.

### Proof of Concept
Not independently reproducible from static analysis alone — a concrete PoC requires constructing an account/asset-store state where `assetBalanceEnoughV2` (validate-time) and `reduceAssetAmountV2` (execute-time) diverge (e.g., toggling `AllowSameTokenName` between validate and execute within the same block, or an asset map inconsistency from `importAsset`), which would need to be verified experimentally against `AccountCapsule`'s map-selection logic to confirm reachability from a single signed `ExchangeInjectContract`/`ExchangeTransactionContract` transaction.

  public boolean reduceAssetAmountV2(byte[] key, long amount,
                                     DynamicPropertiesStore dynamicPropertiesStore, AssetIssueStore assetIssueStore) {
    importAsset(key);
    //key is token name
    boolean disableJavaLangMath = dynamicPropertiesStore.disableJavaLangMath();
    if (dynamicPropertiesStore.getAllowSameTokenName() == 0) {
      Map<String, Long> assetMap = this.account.getAssetMap();
      AssetIssueCapsule assetIssueCapsule = assetIssueStore.get(key);
      String tokenID = assetIssueCapsule.getId();
      String nameKey = ByteArray.toStr(key);
      Long currentAmount = assetMap.get(nameKey);
      if (amount > 0 && null != currentAmount && amount <= currentAmount) {
        this.account = this.account.toBuilder()
                .putAsset(nameKey, subtractExact(currentAmount, amount, disableJavaLangMath))
                .putAssetV2(tokenID, subtractExact(currentAmount, amount, disableJavaLangMath))
                .build();
        return true;
      }
    }
    //key is token id
    if (dynamicPropertiesStore.getAllowSameTokenName() == 1) {
      String tokenID = ByteArray.toStr(key);
      Map<String, Long> assetMapV2 = this.account.getAssetV2Map();
      Long currentAmount = assetMapV2.get(tokenID);
      if (amount > 0 && null != currentAmount && amount <= currentAmount) {
        this.account = this.account.toBuilder()
                .putAssetV2(tokenID, subtractExact(currentAmount, amount, disableJavaLangMath))
                .build();
        return true;
      }
    }

    return false;
  }
