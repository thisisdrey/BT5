### Title
DeployGlobalContract(AccountId mode) binds contract identity to the receipt `receiver_id`, not to the transaction predecessor, letting a third-party overwrite `GlobalContractIdentifier::AccountId(V1)` after `P` has opted in — (File: `runtime/runtime/src/global_contracts.rs`)

### Summary
`action_deploy_global_contract` / `initiate_distribution` derive the `GlobalContractIdentifier::AccountId` solely from the `account_id` argument, which is the receipt's *receiver* account being mutated, with no check tying it to the transaction's predecessor/signer. Unlike `DeployContract`, `AddKey`, `DeleteKey`, `Stake`, `DeleteAccount` — which the runtime documentation explicitly lists as requiring `predecessor_id == receiver_id` — `DeployGlobalContract` is not in that list, and `validate_deploy_global_contract_action` in `runtime/runtime/src/action_validation.rs` only checks the code size limit.

### Finding Description
`action_deploy_global_contract` (`runtime/runtime/src/global_contracts.rs:24-61`) charges storage cost to `account` (the receiver's account) and calls `initiate_distribution` with `account_id.clone()` [1](#0-0) . `initiate_distribution` then binds `GlobalContractIdentifier::AccountId(account_id)` directly to whatever `account_id` was passed in [2](#0-1) , with no validation of who the predecessor/signer of the receipt is. `validate_deploy_global_contract_action` performs only a `max_contract_size` check, no receiver/predecessor equality check [3](#0-2) .

The published `docs/RuntimeSpec/Actions.md` states: "For the following actions, `predecessor_id` and `receiver_id` are required to be equal: `DeployContract`, `Stake`, `AddKey`, `DeleteKey`, `DeleteAccount`." [4](#0-3)  `DeployGlobalContract` is conspicuously absent from that list, and I could not locate an analogous equality check enforced specifically for `DeployGlobalContract` in the reviewed code paths (`action_validation.rs`, `global_contracts.rs`, the action dispatch in `runtime/runtime/src/lib.rs:594-604` which passes only a single `account_id` — the receiver — into `action_deploy_global_contract`, unlike `action_create_account` which is passed `receiver_id` and `predecessor_id` separately) [5](#0-4) .

If this equality is indeed unenforced for `DeployGlobalContract`, an attacker A could submit `SignedTransaction { signer_id: A, receiver_id: V1, actions: [DeployGlobalContractAction{ code: evil_code, deploy_mode: AccountId }] }` signed with A's own full-access key. The resulting receipt (`predecessor_id = A`, `receiver_id = V1`) would execute against V1's account, rebind `GlobalContractIdentifier::AccountId(V1)` to A's code, and even debit the storage cost from V1's balance rather than A's. Any account `P` that previously called `UseGlobalContract(AccountId(V1))` (trusting V1's code) would transparently execute A's code on its next `FunctionCall`, without any action by `P` or `V1`.

### Impact Explanation
If confirmed, this breaks the authorization/determinism model of NEP-591 global contracts: an unprivileged attacker could silently take over any AccountId-addressed global contract identity and thereby the code executed by every account that has opted into it via `UseGlobalContract`, without owning or controlling the named account at all. This maps to the "authorization escalation across accounts" bounty category and, combined with the victim-account storage-cost debit, also a fund-drain/griefing vector against V1.

### Likelihood Explanation
I was unable to conclusively verify, within available search iterations, whether the transaction/receipt verifier enforces `predecessor_id == receiver_id` for `DeployGlobalContract` through some mechanism outside the files I inspected (e.g., inside `runtime/runtime/src/verifier.rs`'s `check_valid_for_config`, which I did not fully trace). The evidence from `action_validation.rs`, `global_contracts.rs`, and the runtime documentation's action list is consistent with this action *not* being restricted, but that documentation may simply predate the Global Contracts feature (NEP-591) rather than reflecting a deliberate design choice.

### Recommendation
Require `predecessor_id == receiver_id` for `Action::DeployGlobalContract` with `GlobalContractDeployMode::AccountId` (mirroring the restriction already applied to `DeployContract`/`AddKey`/etc.), enforced either in `validate_action_with_mode`/`validate_deploy_global_contract_action` (`runtime/runtime/src/action_validation.rs`) or in `action_deploy_global_contract` (`runtime/runtime/src/global_contracts.rs`) by threading the receipt's `predecessor_id` into the check and rejecting mismatches before `initiate_distribution` runs.

### Proof of Concept
Integration/test-loop test plan (extending `test-loop-tests/src/tests/global_contracts.rs`):
1. Set up accounts `victim` (V1), `attacker` (A), `user` (P), each funded.
2. `victim` deploys a benign global contract with `GlobalContractDeployMode::AccountId` (as in `test_global_contract_by_account_id`).
3. `user` calls `use_global_contract` with `GlobalContractIdentifier::AccountId(victim)` and calls it once, asserting benign behavior (e.g., via `view_call_global_contract`/`assert_call_global_contract_success`).
4. `attacker` constructs `SignedTransaction::from_actions(nonce, attacker, victim /* receiver_id */, attacker_signer, [Action::DeployGlobalContract(DeployGlobalContractAction{ code: evil_code, deploy_mode: AccountId })], block_hash)` and submits it.
5. Assert the transaction succeeds (or, if the fix is applied, assert it fails with an `ActionError` requiring `predecessor_id == receiver_id`, e.g. a new `ActionErrorKind::ActorNoPermission`-style error).
6. If it succeeds pre-fix: run `user`'s next `FunctionCall` against `victim`'s previously-`use_global_contract`-bound account and assert the observed behavior/output now matches `evil_code` instead of the original benign contract — proving code substitution without `user` or `victim` acting.
