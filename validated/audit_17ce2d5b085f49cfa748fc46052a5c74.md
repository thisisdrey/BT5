### Title
Exchange balance manipulation via divergent rounding formulas between `validate()` and `execute()` in `ExchangeInjectActuator` - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java])

### Summary
`ExchangeInjectActuator.doValidate()` computes the counterpart token quantity for an exchange injection using `BigInteger` arithmetic with `divide().longValueExact()` [1](#0-0) , while `execute()` recomputes the same quantity independently using primitive `long` arithmetic via `floorDiv(multiplyExact(...), ...)` [2](#0-1) . Both computations use the same integer division semantics (`BigInteger.divide` truncates toward zero the same as `floorDiv` for positive operands), so in the common case results match — but this is exactly the kind of "compute the state-changing value once at validate time and recompute it a second time independently at execute time" pattern that historically causes drift bugs (the Acala class of issue: an on-chain parameter/formula mismatch between the config check and the actual mint/settle path). Unlike the sibling actuators `ExchangeWithdrawActuator` and `ExchangeTransactionActuator`, which both route their ratio math through the same hardened/legacy branch consistently between `doValidate()` and `execute()` (via `allowHarden()`), `ExchangeInjectActuator.execute()` never calls `allowHarden()` at all and always uses the plain-`long` `floorDiv`/`multiplyExact` path regardless of the `AllowHardenExchangeCalculation` chain parameter, whereas its own `doValidate()` already always uses the `BigInteger` path [3](#0-2) .

### Finding Description
The design intent visible elsewhere in the code (`AbstractExchangeActuator.allowHarden()/addExact()/subtractExact()` and `ExchangeCapsule.transaction()` choosing between `ExchangeProcessor` and `SafeExchangeProcessor` based on the `allowHardenExchangeCalculation` dynamic parameter) [4](#0-3)  is that validate-time and execute-time math for exchange operations must be kept in lock-step by threading the same on-chain-configurable flag through both phases. `ExchangeWithdrawActuator` and `ExchangeTransactionActuator` respect this pattern. `ExchangeInjectActuator`, however, hard-codes two different arithmetic implementations for the identical ratio computation in `validate()` versus `execute()`, with no shared helper and no dependency on the `allowHarden` flag in `execute()`. Any future on-chain committee proposal that changes exchange-related rounding/precision behavior (e.g. via `ProposalUtil`/`ProposalService`, which does toggle `allowHardenExchangeCalculation` and related dynamic parameters at runtime) [5](#0-4)  would only affect `validate()`'s BigInteger math and not `execute()`'s primitive math for this specific actuator, reintroducing exactly the class of validate/execute state divergence that caused Acala's aUSD to be minted beyond what validation intended.

### Impact Explanation
If the two computations were to diverge (e.g., once additional precision/hardening logic is added to one branch but not the other, which is the direct pattern this code already exhibits), the exchange pool's committed `firstTokenBalance`/`secondTokenBalance` state written by `execute()` would no longer match the state that `validate()` verified was sufficient/limited, allowing the injecting account to shift the AMM price ratio by an amount inconsistent with what was checked against `getExchangeBalanceLimit()` and account balance sufficiency. Because TRC10 exchange balances are directly redeemable for real TRX/token balances via `ExchangeTransactionActuator`/`ExchangeWithdrawActuator`, a favorable rounding divergence could be exploited repeatedly to extract value disproportionate to tokens actually deposited — an unauthorized value-extraction analog to unbacked-asset minting.

### Likelihood Explanation
Currently, for all positive `long` operands within the actuator's own bounds, `BigInteger.divide()` and `floorDiv()` produce identical truncated results, so today this is not independently exploitable purely from this divergence — it is a latent maintenance hazard rather than a demonstrated live overflow. I could not fully verify within the available tool budget whether any edge case (e.g., extremely large balances near `Long.MAX_VALUE` where `multiplyExact` in the `execute()` path could throw `ArithmeticException` while the `BigInteger` path in `validate()` succeeds, or vice versa) causes an actual value mismatch reachable by an unprivileged account holding an `ExchangeInjectContract`-eligible balance. This should be treated as a code-quality/architecture defect with real risk given the precedent of related hardening work (`SafeExchangeProcessor`, `allowHarden` flags) already added to sibling actuators but omitted here.

### Recommendation
Unify `ExchangeInjectActuator` to compute `anotherTokenQuant` exactly once (or via one shared, hardened-flag-aware helper) and reuse that value in both `validate()` and `execute()`, mirroring the pattern used by `ExchangeWithdrawActuator`/`ExchangeTransactionActuator`. Ensure `execute()` also respects `allowHarden()`/`allowStrictMath()` so that a future on-chain parameter change cannot decouple the two computations.

### Proof of Concept
Not independently reproducible today with a divergent numeric outcome from the tools available; the finding is that the code paths are structurally divergent (different arithmetic engines for the same computation in `validate()` vs. `execute()`), which is the precise "on-chain calculation path mismatch" bug class implicated in the Acala incident, and it warrants dedicated fuzzing/unit testing (e.g., balances/quantities near `Long.MAX_VALUE` or where `multiplyExact` overflows in `execute()` but `BigInteger` math in `validate()` does not) to confirm exploitability, which a background engineering session with test-execution capability could perform.

package org.tron.core.actuator;

import com.google.protobuf.GeneratedMessageV3;
import org.tron.common.math.StrictMathWrapper;
import org.tron.protos.Protocol.Transaction.Contract.ContractType;

public abstract class AbstractExchangeActuator extends AbstractActuator {

  public AbstractExchangeActuator(ContractType type, Class<? extends GeneratedMessageV3> clazz) {
    super(type, clazz);
  }

  protected boolean allowHarden() {
    return chainBaseManager.getDynamicPropertiesStore().allowHardenExchangeCalculation();
  }

  public long subtractExact(long x, long y) {
    return allowHarden() ? StrictMathWrapper.subtractExact(x, y) : x - y;
  }

  public long addExact(long x, long y) {
    return allowHarden() ? StrictMathWrapper.addExact(x, y) : x + y;
  }
}
