### Title
Postponed receipts and pending-data-count links survive account deletion, allowing a stale self-authorized `AddKey(FullAccess)` receipt to execute against a re-created account with a different owner - (File: runtime/runtime/src/actions.rs, core/store/src/utils/mod.rs)

### Summary
`action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) removes an account's `Account`, `ContractCode`, `AccessKey`, and `ContractData` entries via `remove_account` (`core/store/src/utils/mod.rs:505-575`), but never touches `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, or `TrieKey::PostponedReceiptId` for that account. If the deleted account previously postponed an `ActionReceipt` containing `AddKeyAction{FullAccess}` awaiting a still-unmet `input_data_id`, that receipt remains stored under the account name and will execute with `actor_id == predecessor_id == account_id` once the matching `DataReceipt` arrives — even after the account name has been deleted and re-created by an unrelated new owner.

### Finding Description
`action_delete_account` calls `remove_account(state_update, account_id)` at `runtime/runtime/src/actions.rs:371`. `remove_account` (`core/store/src/utils/mod.rs:505-575`) only removes `TrieKey::Account`, `TrieKey::ContractCode`, access/gas keys, and `TrieKey::ContractData`. It never iterates or removes `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, or `TrieKey::PostponedReceiptId` entries keyed by that `account_id` [1](#0-0) .

Postponed receipts are created in `process_action_receipt` (`runtime/runtime/src/lib.rs:1593-1658`): if an incoming `ActionReceipt` has unmet `input_data_ids`, the runtime stores `TrieKey::PostponedReceiptId{receiver_id, data_id}`, `TrieKey::PendingDataCount{receiver_id, receipt_id}`, and the serialized receipt itself via `set_postponed_receipt` [2](#0-1) . When the missing `DataReceipt` finally lands, `process_receipt` decrements `PendingDataCount`, and once it reaches zero it fetches the stored receipt and calls `apply_action_receipt` on it [3](#0-2) .

Inside `apply_action_receipt`, the account is re-fetched fresh from the *current* state (`get_account(state_update, account_id)`), and `actor_id` is initialized from `receipt.predecessor_id().clone()` — a value frozen inside the postponed receipt at the time it was originally created, not re-derived from current state [4](#0-3) . For each action, `apply_action` runs `check_account_existence` and `check_actor_permissions` (`runtime/runtime/src/actions.rs:787-855` and `739-785`), and for `Action::AddKey`, `check_actor_permissions` only verifies `actor_id == account_id` as plain `AccountId` string equality [5](#0-4) . It does not verify that the account is the *same* logical account (e.g., by comparing creation nonce, or checking that the account hasn't been deleted/re-created in between).

Exploit flow:
1. Attacker controls `victim.near` (e.g., deploys their own contract there, or it is otherwise an account they control at genesis time).
2. The contract's init call issues a `promise_then(self, AddKeyAction{FullAccess})` where the base promise is a call the attacker fully controls (e.g., to another contract they own), so the `input_data_id` will not resolve until the attacker chooses. This causes `process_action_receipt` to postpone the `AddKey` action receipt with `predecessor_id == receiver_id == "victim.near"` frozen in the stored receipt.
3. Attacker submits a `DeleteAccountAction` from `victim.near` with `beneficiary_id` set to their own account. `action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) refunds the balance, calls `remove_account`, and sets `account = None`, but leaves the postponed receipt, `PendingDataCount`, and `PostponedReceiptId` entries intact in the trie, since `remove_account` never touches those `TrieKey` variants.
4. `victim.near` (a subaccount of `near`, so only creatable by `near` per `is_sub_account_of` check in `action_create_account`, `runtime/runtime/src/actions.rs:191-198`) is later re-registered by an unrelated legitimate party through the normal `near` registrar flow.
5. At a time of the attacker's choosing (even after re-creation), the attacker triggers the base promise to resolve, producing the matching `DataReceipt`. `process_receipt` sees the `PostponedReceiptId` link still keyed to `victim.near`/`data_id`, decrements `PendingDataCount` to zero, fetches the postponed `AddKey` receipt, and executes it via `apply_action_receipt` against the **new** account object for `victim.near`.
6. `check_actor_permissions` passes because `actor_id` (frozen `predecessor_id = "victim.near"`) equals `account_id` (`"victim.near"`), even though the account underneath is now owned by someone else. `action_add_key` runs and grants the attacker's chosen full-access public key on the new owner's account, with no transaction ever signed by the new owner.

This breaks the stated invariant of authorization exactness: a promise created by the old incarnation of an account must not carry privilege into a differently-owned incarnation of the same account name.

### Impact Explanation
This is an authorization-escalation bug across account identities: an attacker can obtain a full-access key on an account they do not own and never signed a transaction for, enabling theft of any funds subsequently deposited into that account and full contract/account takeover. This matches the "authorization escalation across accounts or promises" bounty category (theft of user funds via unauthorized full-access key grant).

### Likelihood Explanation
Preconditions: (a) attacker must control the account before deletion (trivial — attacker registers/owns it, e.g., a fresh subaccount they create then later plan to "give up"), (b) the account name must be reused after deletion, which requires the `near` registrar (or another parent account) to re-create that same name for a different party — plausible for short/desirable names or via social engineering of a marketplace/registrar flow, but not guaranteed to happen quickly or automatically. Cost to attacker is minimal (one contract deployment, standard `DeleteAccountAction`, and a later self-triggered `DataReceipt`). The mechanism itself (stale postponed/pending-data trie entries surviving `remove_account`) is fully repeatable and requires no validator/node privilege — only standard signed transactions. The main practical constraint is convincing/arranging for the exact account name to be re-registered, which is outside the attacker's direct control but is a realistic scenario (e.g., name squatting/release ecosystems, or an attacker temporarily "renting" then deleting an account before selling/returning the name).

### Recommendation
In `remove_account` (`core/store/src/utils/mod.rs`), also iterate and remove all `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, and `TrieKey::PostponedReceiptId` entries whose `receiver_id`/`account_id` matches the account being deleted (and any `TrieKey::PromiseYieldReceipt`/timeout entries similarly keyed), mirroring the existing iteration pattern used for access keys and contract data. Alternatively/additionally, `apply_action_receipt` should bind postponed-receipt execution to the account incarnation it was created for (e.g., store and verify an account "creation nonce"/generation id) rather than relying solely on string equality between `predecessor_id` and `account_id`.

### Proof of Concept
Runtime/apply-path integration test (test-loop or `runtime/runtime` apply tests) plan:
1. Deploy a contract on `victim.near` whose method issues `promise_then(base_promise_to_attacker_controlled_contract, AddKeyAction{FullAccess, attacker_pubkey})`, leaving `input_data_id` unresolved (e.g., base promise targets a method on attacker's contract that never returns in the same apply call).
2. Assert via direct trie inspection that `TrieKey::PostponedReceipt{receiver_id: "victim.near", ..}` and `TrieKey::PendingDataCount{receiver_id: "victim.near", ..}` exist in state.
3. Submit a `DeleteAccountAction` transaction signed by `victim.near` with `beneficiary_id = attacker.near`. Apply the block/chunk.
4. Assert `get_account(state_update, "victim.near")` returns `None`, but the `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` entries for `victim.near` still exist in state (proving `remove_account` did not clean them).
5. Submit a `CreateAccountAction` for `victim.near` signed by `near` (registrar) with a fresh key controlled by a "new owner" test account, and fund it.
6. Trigger the pending base promise to resolve (submit the receipt/transaction that produces the matching `DataReceipt` for the stored `data_id`).
7. Assert that after this apply, `get_access_key(state_update, "victim.near", attacker_pubkey)` returns `Some(FullAccess)` — i.e., the attacker's key was added to the new owner's account — despite no transaction ever being signed by the new owner's key. This assertion demonstrates the authorization-exactness violation.
