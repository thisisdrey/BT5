### Title
Out-of-Bounds Read / DoS via Attacker-Controlled Contract `type` Value in Permission Operations Bit-Check - (File: `chainbase/src/main/java/org/tron/core/capsule/TransactionCapsule.java`)

### Summary
During per-transaction multi-signature authentication, `TransactionCapsule.validateSignature` derives a `Permission` for the transaction owner — including a synthesized "default" permission when the owner account does not yet exist in `AccountStore` (the "authentication without a database backend" case) — and then performs an *additional* identity check, `checkPermission`/`checkPermissionOperations`, which indexes a fixed 32-byte `operations` bitmask using the raw, attacker-controlled integer value of the transaction `Contract.type` field.

### Finding Description
`validateSignature` in [1](#0-0)  resolves a `Permission`. When `account == null` (no DB record for the address — analogous to "successful auth without a database backend"), it falls back to `AccountCapsule.getDefaultPermission(...)` or `createDefaultActivePermission(...)` instead of an actuator-validated, on-chain permission.

Right after that, `checkPermission(permissionId, permission, contract)` is invoked as an *additional identity/authorization check* at [2](#0-1) , which calls `checkPermissionOperations`: [3](#0-2) 

```java
public static boolean checkPermissionOperations(Permission permission, Contract contract)
    throws PermissionException {
  ByteString operations = permission.getOperations();
  if (operations.size() != 32) {
    throw new PermissionException("operations size must be 32");
  }
  int contractType = contract.getTypeValue();
  boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
  return b;
}
```

The identical pattern also exists in [4](#0-3) .

`contract.getTypeValue()` returns the *raw wire-encoded integer* of the proto3 `ContractType` enum field, not a value bounded to the declared enum range — an attacker fully controls this int by crafting the transaction's `Contract.type` field on the wire (e.g., value `100000`, or a value with `contractType/8` far beyond 31). `operations` is always exactly 32 bytes (`operations.size() == 32` is the only guard). `ByteString.byteAt(index)` (Protobuf's `LiteralByteString`) throws `ArrayIndexOutOfBoundsException` / `IndexOutOfBoundsException` for indices outside `[0, 32)` — this is the out-of-bounds read.

This check is only reached when `permissionId != 0` (see `checkPermission`), i.e. for any multi-sig/active-permission transaction, and it is only reachable when signature/weight checks up to that point have not yet failed the transaction outright — mirroring the Kamailio pattern of "additional identity checks performed after successful authentication path is taken, on a structure not backed by validated storage."

### Impact Explanation
An unhandled `IndexOutOfBoundsException` thrown deep inside transaction validation, if not caught by an enclosing `catch (Exception)` at every call site, can propagate and crash the transaction-processing thread, or otherwise deny that API/validation path (a broadcasted transaction, or `Wallet`/gRPC calls such as `getTransactionSignWeight` / `TransactionUtil.getTransactionSignWeight`, which do wrap the same `checkPermissionOperations` call in a broad `catch (Exception ex)` per [5](#0-4) ). However, `TransactionCapsule.validatePubSignature`/`validateSignature` (the path used during actual block/transaction application in `Manager`) only catches `SignatureException | PermissionException | SignatureFormatException` — see [6](#0-5)  — and does **not** catch `RuntimeException`/`IndexOutOfBoundsException`. If this path is reached before broader exception handling further up the call stack (in `Manager`/node-processing code, which was not directly inspected in this session), a malicious transaction could crash the validating node process — a denial-of-service analogous to the Kamailio CVE.

### Likelihood Explanation
Reachable by any unprivileged transaction broadcaster: the attacker only needs to submit a transaction whose raw `Contract.type` field encodes an out-of-range integer and whose `permission_id` is non-zero, targeting an address that either has no `AccountStore` entry (triggering the default-permission path) or an existing account (`account.getPermissionById(permissionId)` path also calls the same vulnerable `checkPermissionOperations`). No special privilege, valid signature weight, or witness/committee status is required to reach the vulnerable code — only the shared client library used to build/serialize the transaction needs to allow emitting an out-of-range enum value on the wire (achievable by directly crafting protobuf bytes, bypassing higher-level SDK enum restrictions).

### Recommendation
Bound-check `contractType` before using it as an index in `checkPermissionOperations` (both in `TransactionUtil.java` and `WalletUtil.java`): reject/verify `contractType >= 0 && contractType < 256` (i.e., `contractType/8 < operations.size()`), returning `false`/throwing `PermissionException` for out-of-range values instead of allowing an out-of-bounds `byteAt` call. Additionally, ensure all top-level transaction/permission-validation entry points wrap this logic with a catch-all guard so a malformed/out-of-range value cannot escape as an uncaught `RuntimeException` and crash the node.

### Proof of Concept
1. Construct a `Transaction` whose `raw.contract[0]` has `permission_id = 2` (or any non-zero id) and whose `type` field is set to a wire-level integer far outside the declared `ContractType` enum range (e.g., `100000`), by crafting the serialized protobuf bytes directly (bypassing SDK-level enum validation).
2. Target either (a) an address with no corresponding `AccountStore` entry, so `TransactionCapsule.validateSignature` builds a default permission via `getDefaultPermission`/`createDefaultActivePermission`, or (b) an existing account whose active permission has a 32-byte `operations` field.
3. Sign the transaction and submit it via the broadcast transaction API.
4. During validation, `checkPermission` → `checkPermissionOperations` computes `contractType / 8 = 12500`, calling `operations.byteAt(12500)` on a 32-byte `ByteString`, throwing `IndexOutOfBoundsException`.
5. Observe whether the exception propagates uncaught through the transaction-processing pipeline (crash) or is caught by a generic handler (denial of that specific validation call only).

Note: full confirmation that this exception is uncaught during on-chain block application (inside `Manager.java`'s transaction-processing loop) could not be completed in this session due to tool-call limits; the `Manager.java` call chain into `validatePubSignature`/`validateSignature` should be verified directly to confirm whether a broader catch-all exists above `TransactionCapsule.validatePubSignature`.

  public static boolean validateSignature(Transaction transaction,
      byte[] hash, AccountStore accountStore, DynamicPropertiesStore dynamicPropertiesStore)
      throws PermissionException, SignatureException, SignatureFormatException {
    Transaction.Contract contract = transaction.getRawData().getContractList().get(0);
    int permissionId = contract.getPermissionId();
    byte[] owner = getOwner(contract);
    AccountCapsule account = accountStore.get(owner);
    Permission permission = null;
    if (account == null) {
      if (permissionId == 0) {
        permission = AccountCapsule.getDefaultPermission(ByteString.copyFrom(owner));
      }
      if (permissionId == 2) {
        permission = AccountCapsule
            .createDefaultActivePermission(ByteString.copyFrom(owner), dynamicPropertiesStore);
      }
    } else {
      permission = account.getPermissionById(permissionId);
    }
    if (permission == null) {
      throw new PermissionException("permission isn't exit");
    }
    checkPermission(permissionId, permission, contract);
    long weight = checkWeight(permission, transaction.getSignatureList(), hash, null);
    if (weight >= permission.getThreshold()) {
      return true;
    }
    return false;
  }
