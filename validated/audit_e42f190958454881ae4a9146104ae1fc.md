## Analysis: AMM pool state can be poisoned by pre-funding the deterministic pool account before liquidity is ever added

The Aave/Morpho bug is fundamentally about an attacker being able to pre-seed protocol state at a **deterministically-computable address before the intended initialization path runs**, corrupting an invariant ("first collateral asset decides isolation mode") that the protocol assumed it controlled. The closest real analog in this repository is in `pallet-asset-conversion`, where the pool's account (`T::PoolLocator::pool_address`) is a pure, publicly-computable function of the two asset kinds — exactly like a CREATE2 address — and can be funded by anyone via a plain `Assets::transfer`/`Balances::transfer` before `create_pool` or `add_liquidity` is ever called.

### Title
Pre-funding the deterministic AMM pool account bricks first-liquidity provisioning in `pallet-asset-conversion` - (File: `substrate/frame/asset-conversion/src/lib.rs`)

### Summary
`pallet-asset-conversion` derives the pool's holding account from a pure function of the two asset kinds (`T::PoolLocator::pool_address`/`address`), so anyone can compute it and transfer tokens to it before the pool even exists. `do_add_liquidity` uses the *live balance* of that account (`reserve1`/`reserve2` via `Self::get_balance`) to decide whether this is a "first deposit" (straight desired amounts) or a "ratio-matching" deposit (via `quote`), while it separately uses the *LP token total supply* to decide the minting formula. An attacker can desynchronize these two checks by donating a skewed, minuscule ratio of the two assets to the not-yet-existing pool account, which forces every legitimate `add_liquidity` call afterwards through the `quote()`-based branch with a pathological ratio that rounds every honest deposit down to an amount that fails the pallet's own minimum-balance/minimum-liquidity guards.

### Finding Description
- `T::PoolLocator::address`/`pool_address` computes the pool account deterministically from `asset1`/`asset2` [1](#0-0) , and this same function is exposed publicly via `get_reserves` [2](#0-1) , so any user can compute the address before `create_pool` is even called.
- `get_balance` simply reads the live, unrestricted asset balance of that account with no notion of "has this pool officially started" [3](#0-2) .
- `do_create_pool` never checks or resets any pre-existing balance on the derived `pool_account` — it only checks `Pools::<T>::contains_key` for a duplicate *pool_id*, not for pre-existing token balances [4](#0-3) .
- In `do_add_liquidity`, the branch selection for "first deposit vs. ratio-matched deposit" is driven purely by the account's *current reserves* (`reserve1.is_zero() || reserve2.is_zero()`) [5](#0-4) , while the *minting formula* is driven by the **LP token's total_supply**, not by reserves [6](#0-5) .
- These two checks are supposed to move together (empty pool ⇔ zero LP supply) but an attacker can decouple them: donate non-zero `asset1`/`asset2` balances directly to the not-yet-created `pool_account` in an extreme ratio (e.g., `1` unit of `asset1` vs. a very large amount of `asset2`). No `create_pool`/`add_liquidity` call is required for this — just a bare token transfer to a computable address, exactly like the Aave isolation-mode attacker sending an isolated asset to a not-yet-deployed proxy address.
- Once the real pool is created and a legitimate user calls `add_liquidity`, `reserve1`/`reserve2` are non-zero (attacker-controlled), so the code takes the `quote()`-based branch and computes `amount1_optimal`/`amount2_optimal` against the poisoned ratio. For any realistic `amount_desired`, this either rounds `amount1`/`amount2` down to near zero (failing `AmountOneLessThanMinimal`/`AmountTwoLessThanMinimal` at lines 846-853) or requires an astronomically large counter-deposit that the honest LP will never provide (failing `OptimalAmountLessThanDesired`/`*DepositDidNotMeetMinimum`).
- Because the pool is already registered in `Pools::<T>` (created via `do_create_pool`) but has zero LP-token supply and an attacker-controlled skewed reserve ratio, there is no path in the pallet's public API to reset those reserves or to force the "first deposit" branch again — the pool is permanently unusable for its intended asset pair, matching the "permanent user-fund or bridge-state lock" / "public underpriced work that … stalls" impact class.

### Impact Explanation
This is a public, unprivileged denial-of-service against a specific trading pair on `pallet-asset-conversion` (used by Asset Hub runtimes for the native DEX). Once bricked, that pool can never receive its intended first liquidity provision through the standard pallet API, permanently locking out legitimate market-making for that asset pair and any dependent XCM fee-payment/asset-conversion logic that relies on it (e.g., `AssetConversionApi` quoting, XCM asset-fee trading used by parachains). It requires no governance, validator, relayer, or malicious-node assumption — only an ordinary account able to transfer a tiny amount of `asset1`/`asset2` to a publicly-computable account.

### Likelihood Explanation
High. The attack requires only:
1. Computing `T::PoolLocator::address(asset1, asset2)` — a pure, public function.
2. Sending a small transfer of both assets to that address before/alongside the pool's creation and before any real `add_liquidity` succeeds.
No special timing relative to block production is needed beyond simply acting before the legitimate first liquidity provider, and no privileged role is required.

### Recommendation
Do not rely on live account balances (`reserve1`/`reserve2`) to decide the deposit-amount branch in `do_add_liquidity`. Use `total_supply == 0` (the LP token issuance) as the single source of truth for "is this the pool's first deposit," consistent with the minting-formula branch, and/or have `do_create_pool` snapshot/quarantine or reject creation when the derived pool account already holds a non-zero balance of either asset. This mirrors the report's recommendation to never let externally pre-set balances silently determine protocol-critical state (e.g., isolation mode) — the fix here is to make the "first deposit" determination solely a function of pallet-owned state (LP total supply / `Pools` storage flag), not of externally-influenceable account balances.

### Proof of Concept
1. Compute `pool_account = PoolLocator::address(asset1, asset2)` for a not-yet-created pair.
2. Attacker transfers `1` unit of `asset1` and a very large amount (e.g. `1_000_000_000_000`) of `asset2` directly to `pool_account` (plain `Assets::transfer`/`Balances::transfer`; no pallet call needed).
3. Attacker (or anyone) calls `create_pool(asset1, asset2)` — succeeds, since `do_create_pool` never inspects `pool_account`'s balances [7](#0-6) .
4. A legitimate user calls `add_liquidity(asset1, asset2, amount1_desired, amount2_desired, ...)` with any realistic amounts. Because `reserve1 = 1`, `reserve2 = 1_000_000_000_000` are both non-zero, `do_add_liquidity` takes the `quote()` branch [8](#0-7) ; `quote(amount1_desired, reserve1=1, reserve2=huge)` overflows/produces an unreachable `amount2_optimal`, or the fallback `quote(amount2_desired, reserve2=huge, reserve1=1)` rounds `amount1_optimal` to `0`, which then fails `AmountOneLessThanMinimal` [9](#0-8) .
5. Every subsequent legitimate `add_liquidity` call for this pair fails the same way — the pool is permanently unusable, and the attacker's donated funds simply remain stuck as the pool's un-attributable "reserves" with no LP token ever representing them.

		pub(crate) fn do_create_pool(
			creator: &T::AccountId,
			asset1: T::AssetKind,
			asset2: T::AssetKind,
			initial_fee: Option<Permill>,
		) -> Result<T::PoolId, DispatchError> {
			ensure!(asset1 != asset2, Error::<T>::InvalidAssetPair);
			if let Some(fee) = initial_fee {
				ensure!(fee <= T::MaxSwapFee::get(), Error::<T>::FeeTooHigh);
			}

			// prepare pool_id
			let pool_id = T::PoolLocator::pool_id(&asset1, &asset2)
				.map_err(|_| Error::<T>::InvalidAssetPair)?;
			ensure!(!Pools::<T>::contains_key(&pool_id), Error::<T>::PoolExists);

			let pool_account =
				T::PoolLocator::address(&pool_id).map_err(|_| Error::<T>::InvalidAssetPair)?;

			// pay the setup fee
			let fee =
				Self::withdraw(T::PoolSetupFeeAsset::get(), creator, T::PoolSetupFee::get(), true)?;
			T::PoolSetupFeeTarget::on_unbalanced(fee);

			if T::Assets::should_touch(asset1.clone(), &pool_account) {
				T::Assets::touch(asset1.clone(), &pool_account, creator)?
			};

			if T::Assets::should_touch(asset2.clone(), &pool_account) {
				T::Assets::touch(asset2.clone(), &pool_account, creator)?
			};

			let lp_token = NextPoolAssetId::<T>::get()
				.or(T::PoolAssetId::initial_value())
				.ok_or(Error::<T>::IncorrectPoolAssetId)?;
			let next_lp_token_id = lp_token.increment().ok_or(Error::<T>::IncorrectPoolAssetId)?;
			NextPoolAssetId::<T>::set(Some(next_lp_token_id));

			T::PoolAssets::create(lp_token.clone(), pool_account.clone(), false, 1u32.into())?;
			if T::PoolAssets::should_touch(lp_token.clone(), &pool_account) {
				T::PoolAssets::touch(lp_token.clone(), &pool_account, creator)?
			};

			let pool_info = PoolInfo { lp_token: lp_token.clone() };
			Pools::<T>::insert(pool_id.clone(), pool_info);

			Self::deposit_event(Event::PoolCreated {
				creator: creator.clone(),
				pool_id: pool_id.clone(),
				pool_account,
				lp_token,
			});

			if let Some(fee) = initial_fee {
				PoolFees::<T>::insert(&pool_id, fee);
				Self::deposit_event(Event::PoolFeeSet { pool_id: pool_id.clone(), fee });
			}

			Ok(pool_id)
		}

		pub fn get_reserves(
			asset1: T::AssetKind,
			asset2: T::AssetKind,
		) -> Result<(T::Balance, T::Balance), Error<T>> {
			let pool_account = T::PoolLocator::pool_address(&asset1, &asset2)
				.map_err(|_| Error::<T>::InvalidAssetPair)?;

			let balance1 = Self::get_balance(&pool_account, asset1);
			let balance2 = Self::get_balance(&pool_account, asset2);

				Err(Error::<T>::PoolEmpty)?;
			}

			Ok((balance1, balance2))
