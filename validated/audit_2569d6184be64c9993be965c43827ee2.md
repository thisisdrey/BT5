### Title
StackerDB chunk signatures omit the target contract, enabling cross-contract chunk replay - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` binds a StackerDB chunk signature only to `(slot_id, slot_version, data_hash)` and never to the `QualifiedContractIdentifier` (smart contract / StackerDB instance) the chunk is meant for. Because the Nakamoto `.signers-N-X` StackerDB contracts for a given `reward_cycle % 2` all derive their per-slot signer assignment from the same shared list (`stackerdb-get-signer-slots-page` in the `.signers` boot contract), the same signer address occupies the identical `slot_id` across all of that reward cycle's message-lane contracts (`BlockResponse`, `StateMachineUpdate`, `BlockPreCommit`). A chunk signed for one of these contracts is therefore a valid, replayable chunk for the others, since the storage/validation path never checks contract binding.

### Finding Description
`SlotMetadata::auth_digest()` computes the signed digest as: [2](#0-1) 

only over `slot_id`, `slot_version`, and `data_hash` — no `contract_id` is included. `verify()` recovers the public key from this same digest and checks only that the pubkey hash matches the expected slot signer address: [3](#0-2) 

The write path, `StackerDBTx::try_replace_chunk`, validates the chunk purely against the target contract's slot assignment, version freshness, and max-writes — with no contract-binding check against the signature itself: [4](#0-3) 

The HTTP handler for `POST /v2/stackerdb/:address/:contract/chunks` passes the attacker-supplied `contract_identifier` straight into `try_replace_chunk` alongside the client-supplied chunk/signature, with no verification that the signature was produced for this specific contract: [1](#0-0) 

The same gap exists in the P2P unsolicited-push and download-sync paths via `PeerNetwork::validate_received_chunk`: [5](#0-4) 

Crucially, for a given reward cycle's signer set parity, the `.signers-0-1` (BlockResponse), `.signers-0-2` (StateMachineUpdate), and `.signers-0-3` (BlockPreCommit) contracts (or `-1-*` for the other parity) all read the identical ordered signer list from the shared boot-contract state: [6](#0-5) 

and each message-lane's `StackerDBConfig` is derived from that same list via `stacker_db_contract()`/`MessageSlotID`: [7](#0-6) 

so a given signer's `slot_id` is identical across all three message-lane contracts for that reward cycle. Consequently, a legitimate chunk signed and published by a signer for e.g. `signers-0-1` (BlockResponse) is a completely valid, verifiable chunk for `signers-0-2` (StateMachineUpdate) or `signers-0-3` (BlockPreCommit) as well — the signature check (`slot_metadata.verify(&addr)`) passes identically in all three contracts, because the digest never encoded which contract it was meant for. This mirrors exactly the reported bug class: a signature that authorizes an action fails to bind all context parameters relevant to that authorization (here, contract/channel identity), permitting the signed artifact to be reused/replayed outside its intended context by any third party without needing the signer's key.

### Impact Explanation
Any observer of the public StackerDB gossip/HTTP endpoints (chunks are broadcast in the clear and are also fetchable via `GET /v2/stackerdb/...`) can capture a legitimate, validly-signed chunk from one signer message-lane and resubmit it verbatim (no forgery of the signature needed) to a different message-lane contract for the same reward cycle/signer. This is accepted as a fully valid, "unauthorized write" to a StackerDB replica that the true signer never intended to write to: it bumps that slot's `slot_version` (blocking or interfering with the signer's subsequent legitimate writes to that slot until they resend with a higher version) and propagates as legitimate-looking, network-replicated data to all other nodes replicating that StackerDB (via `handle_unsolicited_StackerDBPushChunk` relaying and further gossip). This can disrupt the Nakamoto signer-to-signer communication protocol (`BlockResponse`/`BlockPreCommit`/`StateMachineUpdate` message lanes) by planting cross-lane chunks that occupy/advance slots signers rely on for consensus signaling, without requiring any private key material from the attacker.

### Likelihood Explanation
High. StackerDB chunks for the signer message lanes are inherently public (broadcast over p2p and queryable over the node's public RPC), so capturing a valid signed chunk requires no special access. Replaying it to a sibling contract requires only a single unauthenticated `POST /v2/stackerdb/:address/:contract/chunks` request (or an unsolicited p2p `StackerDBPushChunk`) with the contract name changed — no cryptography needs to be broken.

### Recommendation
Include the target `QualifiedContractIdentifier` (or at minimum a domain-separation tag identifying the specific StackerDB/message-lane) in `SlotMetadata::auth_digest()` so that a chunk's signature is only valid for the contract it was actually signed for, analogous to how the Story team's fix bound the royalty-token-approval signature check to the specific caller/context it was issued for.

### Proof of Concept
1. Let signer `S` occupy `slot_id = N` in `signers-0-1` (BlockResponse), `signers-0-2` (StateMachineUpdate), and `signers-0-3` (BlockPreCommit) for the current reward cycle (guaranteed by the shared slot-list derivation shown above).
2. `S` legitimately signs and posts a `BlockResponse` chunk to `signers-0-1`: `chunk = StackerDBChunkData{slot_id: N, slot_version: V, sig, data}` where `sig` is over `auth_digest(N, V, hash(data))`.
3. An attacker observes this chunk (via p2p gossip or `GET /v2/stackerdb/<addr>/signers-0-1/chunks/N`).
4. The attacker issues `POST /v2/stackerdb/<addr>/signers-0-3/chunks` with the exact same `{slot_id: N, slot_version: V', sig, data}` body (bumping `slot_version` to satisfy freshness in the new contract if needed — no re-signing required since the digest is contract-agnostic).
5. `RPCPostStackerDBChunkRequestHandler::try_handle_request` → `try_replace_chunk` → `slot_desc.verify(&slot_validation.signer)` succeeds (same signer address owns slot `N` in `signers-0-3`), and the chunk is accepted, stored, and relayed as a legitimate `BlockPreCommit`-lane chunk, even though `S` never signed anything intended for that lane.

    /// Add or replace a chunk for a given reward cycle, if it is valid
    /// Otherwise, this errors out with Error::StaleChunk
    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
}
