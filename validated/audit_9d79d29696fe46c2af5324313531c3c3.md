### Title
`RewardsDistributor` computes an entire accrual period using only the latest `balanceOf`/`totalSupply`, skipping all intermediate balance states — users can steal or lose yield by changing balances before index updates - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
The referenced bug class is a reward-index that only snapshots the *latest* epoch/state when catching up, so every intermediate period is valued with the wrong share counts. `RewardsDistributor` has the same flaw: the global index (`_calculateTokenIndex`) divides all elapsed-time emissions by the *current* `totalSupply()`, and per-account delta (`_calculateTokenDelta`) multiplies the whole index delta by the *current* `balanceOf(account_)`. Neither function replays intermediate balance states. Because `DebtToken.balanceOf`/`totalSupply` grow continuously via accrued interest without any `updateBeforeMintOrBurn` call, and because an unprivileged user can change their balance (mint/issue debt, deposit, transfer) immediately before triggering an index update, past emission windows are retroactively priced with manipulated weights. ### Finding Description
`_calculateTokenIndex` computes `tokensAccrued = deltaTimestamp * speed` for the entire time since `tokenStates[token_].timestamp` and divides it by `token_.totalSupply()` read *now* (line 204-206). `_calculateTokenDelta` then credits `account` with `token_.balanceOf(account_) * deltaIndex` where `deltaIndex = tokenIndex - accountIndexOf[token_][account_]` covers the whole period since the account last accrued (lines 229-230).

Two consequences of the missing intermediate states:

1. **Retroactive weight inflation (theft direction).** A user with `accountIndexOf` lagging can increase `balanceOf` right before calling `claimRewards` (or `updateBeforeMintOrBurn`, which is permissionless per line 173). The full `deltaIndex` is then applied to the new, larger balance — even though they held little or nothing for most of that window. `DebtToken` holders can do this atomically via `DebtToken.issue`/`mint` through `Pool` (deposit collateral → issue debt → `claimRewards` in one transaction), and `DepositToken` holders via a flash-funded deposit.
2. **Retroactive dilution (loss direction).** `DebtToken.totalSupply()` grows every second with interest accrual, but no hook calls `_updateTokenIndex` on that growth. When the index is eventually updated, emissions for the entire elapsed window are divided by the inflated end-of-window supply, permanently under-crediting all holders for time when supply was smaller. The "missing" rewards are emitted implicitly as claimable at a lower rate, i.e., rewards that should have been distributed remain stuck/under-distributed — analogous to the locked-rewards impact in the original finding.

No modifier stops this: `claimRewards(address[], IERC20[])` is `nonReentrant` but fully public, `updateBeforeMintOrBurn` is explicitly callable by anyone, and index updates are lazy (only on interaction), so gaps between updates are the norm.

### Impact Explanation
The reward-accrual invariant is broken: emissions are allocated by end-of-period balances instead of time-weighted balances. An attacker can capture a disproportionate share of a reward window by inflating `balanceOf` just before an update (direct theft of unclaimed yield from other holders), and all holders are systematically diluted whenever `totalSupply` grows between updates (yield locked/misallocated in the contract).

### Likelihood Explanation
- Requires only unprivileged calls: `Pool.deposit`/`DebtToken.issue` (or `DepositToken` mint/transfer) followed by `claimRewards(attacker)`, callable in the same transaction via `Operator.execute`.
- Naturally triggered whenever index updates are infrequent relative to balance changes; `DebtToken` interest growth makes divergence continuous.
- Magnitude depends on speed/emission rate and index staleness — same "small but real loss of yield" profile as the acknowledged original finding.

### Recommendation
Mirroring the original finding's dilemma, exact replay of every balance state is not gas-feasible. Mitigations: update the index more eagerly (on `DebtToken` interest accrual), cap the crediting balance to the balance at last account update for historical deltas, or accept and document the approximation as the Metronome design does for lazy Synthetix-style indexes. If precision matters, snapshot per-account balance at last update and only credit forward-looking deltas on balance change.

### Proof of Concept
Hardhat fork (mainnet deployment exists in `deployments/mainnet/RewardsDistributor.json`):

```typescript
// assumes reward token speed > 0 for a DebtToken or DepositToken `T`
// 1. Let time pass so `tokenStates[T].timestamp` is stale and deltaIndex > 0
await time.increase(1 * DAY);

// 2. Attacker (fresh account, accountIndexOf[T][attacker] = 0 -> falls back to INITIAL_INDEX
//    only if index never moved; otherwise use an account that accrued earlier with balance 0)
//    Inflate balance just before claim:
await pool.deposit(collateral.address, collateralAmount);   // mints DepositToken
// or: await debtToken.issue(attacker, amount) via pool.borrow

// 3. Trigger update + claim in same tx
await rewardsDistributor.claimRewards(attacker.address);

// Observed: tokensAccruedOf[attacker] ≈ balanceOf(attacker) * deltaIndex,
// where deltaIndex spans the whole day although the balance existed for ~1 block.
// Compare with a baseline account holding the same balance for the full day —
// both receive the same reward for that window, proving intermediate states were skipped.
```

For the dilution direction: record `tokenStates[T].index` before and after a period in which `DebtToken.totalSupply()` doubles via interest; the index increment is `speed*Δt / endSupply` rather than the integral over growing supply, and the shortfall is never recoverable.

Caveat: I could not execute a live fork test here; the exact magnitude depends on deployed `tokenSpeeds` and how frequently index updates are triggered on the target chain.

```text
    function _calculateTokenIndex(
        TokenState memory _supplyState,
        IERC20 token_
    ) private view returns (uint224 _newIndex, uint32 _newTimestamp) {
        uint256 _speed = tokenSpeeds[token_];
        uint256 _deltaTimestamps = block.timestamp - uint256(_supplyState.timestamp);
        if (_deltaTimestamps > 0 && _speed > 0) {
            uint256 _totalSupply = token_.totalSupply();
            uint256 _tokensAccrued = _deltaTimestamps * _speed;
            uint256 _ratio = _totalSupply > 0 ? _tokensAccrued.wadDiv(_totalSupply) : 0;
            _newIndex = (_supplyState.index + _ratio).toUint224();
            _newTimestamp = block.timestamp.toUint32();
        } else if (_deltaTimestamps > 0 && _supplyState.index > 0) {
            _newTimestamp = block.timestamp.toUint32();
        }
    }
```

```text
    function _calculateTokenDelta(
        TokenState memory _tokenState,
        IERC20 token_,
        address account_
    ) private view returns (uint256 _tokenIndex, uint256 _tokensDelta) {
        _tokenIndex = _tokenState.index;
        uint256 _accountIndex = accountIndexOf[token_][account_];

        if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
            _accountIndex = INITIAL_INDEX;
        }

        uint256 _deltaIndex = _tokenIndex - _accountIndex;
        _tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
    }
```
