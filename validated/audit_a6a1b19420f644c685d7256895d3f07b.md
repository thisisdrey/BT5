### Title
Unvalidated `local_header_offset` from attacker-controlled JAR produces an out-of-bounds pointer dereferenced by singlejar - (File: `src/tools/singlejar/input_jar.h`)

### Summary
`InputJar::LocalHeader()` computes the address of a ZIP/JAR local file header directly from the `local_header_offset` field stored in the Central Directory Header (CDH), which is fully attacker-controlled data read from an input JAR. Unlike `InputJar::NextEntry()`, which validates that the next CDH record stays within the mapped file (`mapped_file_.mapped(new_cdr)`), `LocalHeader()` performs no equivalent bounds check before returning the computed pointer, and the caller in `output_jar.cc` immediately dereferences it.

### Finding Description
`MappedFile::address()` is a raw pointer-arithmetic helper with no validation: [1](#0-0) 

`InputJar::LocalHeader()` uses this helper on an offset taken straight from the CDH's `local_header_offset()` accessor (which is either the raw 32-bit field or, for Zip64, a value pulled from an extra field — all attacker-supplied bytes) plus a `preamble_size_`, and returns the resulting pointer as an `LH*` with **no check that it lies within `[mapped_start_, mapped_end_)`**: [2](#0-1) 

Contrast this with `NextEntry()`, which does bounds-check the next CDH pointer via `mapped_file_.mapped(new_cdr)` before dereferencing it: [3](#0-2) 

The returned (unvalidated) `LH*` is handed to `OutputJar::AddJar()`, which immediately dereferences it to compute a copy region and byte count from attacker-influenced fields (`lh->size()`, `jar_entry->local_header_offset()` used as `copy_from`, `lh->compressed_file_size()`, and for streamed entries a `DDR*` computed as `lh->data() + jar_entry->compressed_file_size()`): [4](#0-3) 

This mirrors the CVE-2024-53098 bug class exactly: `access_ok()`/the CDH-offset arithmetic only performs range/overflow bookkeeping on the *declared* value, but nothing actually confirms the resulting address is backed by valid, mapped memory before it's dereferenced. A crafted CDH `local_header_offset` (or Zip64 64-bit extension value) can point far outside the `mmap`'d file region (before `mapped_start_`, past `mapped_end_`, or wildly out of the process address space), and the code walks straight into it via `lh->size()`, `lh->data()`, etc.

### Impact Explanation
Because `AddJar()` uses the unvalidated `lh` pointer to determine a byte range that is then **copied into the output jar** (`copy_from`/`num_bytes`, subsequently written by the merge logic), a malicious JAR/ZIP consumed as a build input (e.g. a prebuilt `.jar` dependency fetched via `http_jar`/`http_file`, a Maven artifact, or checked into an untrusted branch that CI builds) can:
- Cause an out-of-bounds read leading to a crash (SIGSEGV) of the `singlejar` build tool, or
- Leak adjacent process heap/mmap memory contents into the merged deploy jar output, since the bytes at the bogus address are copied verbatim into the build artifact — a concrete information-disclosure impact, not merely a crash.

This satisfies the "read outside the repository/output-base" bar: the read escapes the intended memory region of the mapped input file and the leaked bytes can end up embedded in the built artifact.

### Likelihood Explanation
`singlejar` is invoked automatically by `java_binary`/`java_library`-style rules to merge dependency jars; any dependency jar an attacker can get a victim to depend on (a malicious artifact at a URL a victim pins by sha256 — the pinned hash matches exactly the bytes the attacker chose to serve, so checksum verification does not stop a structurally malicious-but-hash-matching JAR) reaches this code path with no additional privilege required from the attacker. The `local_header_offset` field is a normal, attacker-writable ZIP structure field, requiring no exotic corruption — just picking an out-of-range value.

### Recommendation
In `InputJar::LocalHeader()` (and any other place that turns a stored offset into a pointer via `MappedFile::address()`), validate that the resulting `LH*` (and enough bytes for the fixed-size `LH` header) is within `[mapped_start_, mapped_end_)` using `MappedFile::mapped()`, mirroring the check already done in `NextEntry()`, and fail the build with a diagnostic (as `NextEntry()` does via `diag_errx`) instead of returning an unchecked pointer to the caller.

### Proof of Concept
The repository already contains a test scaffold for building a malformed CDH-based zip (`output_jar_simple_test.cc`, `CreateZipWithMalformedExtraField`) that can be extended to set `cdh->local_header_offset32()` to a value that, after `preamble_size_` is added, points past `mapped_end_` (e.g. `0xFFFFFFF0`), then feed that buffer through `OutputJar::AddJar()`. A reproducible `JUnit`/C++ gtest-style proof would:
1. Build an in-memory ZIP with one CDH entry whose `local_header_offset32` is set far beyond the buffer length.
2. Call `InputJar::Open(path, data, length)` then `NextEntry()`/`LocalHeader()` and observe the returned `LH*` lies outside `[mapped_start_, mapped_end_)`.
3. Drive `OutputJar::AddJar()` on this crafted input and observe an out-of-bounds read (ASan report) or corrupted/leaked bytes copied into the output jar. [5](#0-4)

std::string CreateZipWithMalformedExtraField() {
  std::string zip_data;
  const std::string filename = "evil.bin";

  // 1. Local File Header (LFH)
  size_t lh_offset = zip_data.size();
  size_t lh_size = sizeof(LH) + filename.size();
  zip_data.resize(lh_offset + lh_size, 0);
  auto* lh = reinterpret_cast<LH*>(&zip_data[lh_offset]);
  lh->signature();
  lh->version(10);
  lh->file_name(filename.data(), filename.size());

  // 2. Extra field payload containing an oversized payload_size
  uint8_t ef_buffer[8] = {0};
  auto* ef1 = reinterpret_cast<ExtraField*>(ef_buffer);
  ef1->signature(0x000d);
  ef1->payload_size(0);

  auto* ef2 = reinterpret_cast<ExtraField*>(ef_buffer + ef1->size());
  ef2->signature(0xdead);
  ef2->payload_size(0xf000);  // Malformed size exceeding extra field buffer

  // 3. Central Directory Header (CDH)
  size_t cdh_offset = zip_data.size();
  size_t cdh_size = sizeof(CDH) + filename.size() + sizeof(ef_buffer);
  zip_data.resize(cdh_offset + cdh_size, 0);
  auto* cdh = reinterpret_cast<CDH*>(&zip_data[cdh_offset]);
  cdh->signature();
  cdh->version(20);
  cdh->version_to_extract(10);
  cdh->local_header_offset32(lh_offset);
  cdh->file_name(filename.data(), filename.size());
  cdh->extra_fields(ef_buffer, sizeof(ef_buffer));

  // 4. End of Central Directory (EOCD)
  size_t ecd_offset = zip_data.size();
  zip_data.resize(ecd_offset + sizeof(ECD), 0);
  auto* ecd = reinterpret_cast<ECD*>(&zip_data[ecd_offset]);
  ecd->signature();
  ecd->this_disk_entries16(1);
  ecd->total_entries16(1);
  ecd->cen_size32(cdh_size);
  ecd->cen_offset32(cdh_offset);

  return zip_data;
}
