### Title
Reliability reporting for `AttachmentRequest` is not gated on `attachment.hash() == content_hash`, allowing a malicious peer serving forged attachment content to be perpetually favored - (File: stackslib/src/net/atlas/download.rs)

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` bumps a peer's `ReliabilityReport` to "successful" solely based on whether the HTTP response decodes as an attachment (`decode_atlas_get_attachment`), without ever comparing the returned `Attachment::hash()` to the `AttachmentRequest::content_hash` that was actually requested. A peer that always returns well-formed but content-mismatched attachment bytes for any requested hash will have its `ReliabilityReport` improve indefinitely, since every response is decodable.

### Finding Description
The broken equality: the code implicitly treats `decode_atlas_get_attachment().is_ok()` as `success`, when the intended definition of success is `attachment.hash() == request.content_hash`. In `extend_with_attachments` [3](#0-2)  the code does:
```
if let Ok(response) = response.decode_atlas_get_attachment() {
    self.attachments.insert(response.attachment);
    report.bump_successful_requests();
} else {
    report.bump_failed_requests();
}
```
There is no check like `response.attachment.hash() == request.content_hash` before calling `bump_successful_requests()`. The actual hash validation only happens much later in `AttachmentsDownloader::run`, when `Done` state attachments are matched against `AttachmentInstance`s by `find_all_attachment_instances(&attachment.hash())` [2](#0-1)  — but this lookup happening later doesn't retroactively undo the reliability bump that already occurred per-request in `extend_with_attachments`.

Since `ReliabilityReport::score()` is `total_requests_success * 1000 / (n * 1000) + n`, a peer that always responds (even with garbage matching content_hash format but wrong bytes) accrues `total_requests_success == total_requests_sent`, giving it a maximal score that grows with every subsequent request/response cycle. `AttachmentRequest::get_most_reliable_source` selects sources by `max_by_key(|(_, v)| v.score())` [4](#0-3) , and `Requestable::get_url` for `AttachmentRequest` also delegates to `get_most_reliable_source` [5](#0-4) , meaning this inflated score directly determines which peer is queried first/preferentially for all future attachment fetches.

### Impact Explanation
A malicious peer that always returns hash-mismatched (forged) attachment data for any `content_hash` it claims to have in its inventory will never see its `ReliabilityReport` degrade — every response is a "success" from the reliability-accounting perspective, regardless of whether the served data is real. This lets the attacker's peer entrench itself as the `get_most_reliable_source` for a `content_hash`, competing with or crowding out honest peers in the `BinaryHeap<AttachmentRequest>` priority ordering (`Ord for AttachmentRequest` also uses `get_most_reliable_source().1` for tie-breaking) [6](#0-5) . While the forged data itself is not stored as canonical (it is filtered out later via the hash lookup in `run()`), the attacker gains permanent request priority, effectively conducting a resource-wasting/starvation attack against attachment resolution — repeatedly consuming the attachment-download slot for a `content_hash` while providing no useful data, delaying resolution of legitimate attachments (BNS name registration data, etc.) indefinitely. This matches the "steering a node off legitimate data sources via false reliability accounting" class of issue, though it does not cause forged data to be accepted as canonical (the later hash re-check prevents that outcome).

### Likelihood Explanation
Any remote peer that is in the node's `get_outbound_sync_peers()` set and advertises a data URL can be selected as an attachment source; no privileged role, secret, or admin access is required — simply being a connected peer that responds to `/v2/attachments/inv` and `/v2/attachments/<hash>` HTTP requests. The attacker only needs to run a normal peer that claims (falsely) to have attachments in its inventory and returns arbitrary well-formed attachment payloads for every request. This is fully repeatable across every `AttachmentsDownloader::run` cycle.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments`, after successfully decoding the response, verify `response.attachment.hash() == request.content_hash` before calling `report.bump_successful_requests()`; call `report.bump_failed_requests()` (or a stronger penalty) if the hash does not match, and avoid inserting the mismatched attachment into `self.attachments` at all.

### Proof of Concept
Rust test in `stackslib/src/net/atlas/tests.rs` (or a new test module) plan:
1. Construct an `AttachmentsBatchStateContext` with two mock peers ("honest" and "malicious") and a `AttachmentRequest` with a fixed `content_hash`.
2. Construct a `BatchedRequestsResult<AttachmentRequest>::succeeded` map where:
   - the honest peer's response decodes to an `Attachment` whose `.hash()` equals `content_hash`,
   - the malicious peer's response decodes successfully to an `Attachment` with different bytes, so `.hash() != content_hash`.
3. Call `extend_with_attachments` and then inspect `context.peers` reliability reports for both peers.
4. Assert that today, `malicious_peer_report.score() == honest_peer_report.score()` (both bumped as "successful") — demonstrating the bug: `report.total_requests_success == report.total_requests_sent` for the malicious peer despite `attachment.hash() != content_hash`.
5. After applying the fix (checking hash equality before bumping success), re-run and assert `malicious_peer_report.total_requests_success == 0` while `honest_peer_report.total_requests_success == 1`, and that `get_most_reliable_source` on a subsequent `AttachmentRequest` now favors the honest peer.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }
