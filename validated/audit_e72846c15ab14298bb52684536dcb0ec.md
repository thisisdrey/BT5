## Analog Vulnerability Found

### Title
RefService.UpdateReferences RPC Updates References Without Running Pre-Receive/Update Hooks, Bypassing Branch-Protection Access Checks - (File: internal/gitaly/service/ref/update_references.go)

### Summary
Gitaly enforces access control on reference mutations (branch protection, `pre-receive`/`update` custom hooks, and the GitLab Rails `/internal/allowed` authorization check) through the shared `UpdaterWithHooks` code path. However, the `RefService.UpdateReferences` RPC performs raw reference updates using a plain `updateref.Updater` that never invokes this hook chain, allowing arbitrary reference creation, force-update, or deletion — including protected branches — with no authorization check whatsoever. This is structurally the same defect pattern as the reported `emergencyWithdraw` bug: a "normal" code path enforces a restriction, while a functionally equivalent alternate path silently omits it.

### Finding Description
All of Gitaly's user-facing branch/tag mutation RPCs in `OperationService` (`UserFFBranch`, `UserUpdateBranch`, `UserCreateTag`, `UserCherryPick`, etc.) funnel their reference updates through `updateReferenceWithHooks`, which delegates to `UpdaterWithHooks.UpdateReference`: [1](#0-0) 

That function unconditionally executes `PreReceiveHook` (which calls the GitLab Rails `/internal/allowed` endpoint and any custom `pre-receive` hooks) before migrating quarantined objects and committing the ref update, followed by the `update`, `reference-transaction`, and `post-receive` hooks: [2](#0-1) 

This is exactly the mechanism GitLab uses to implement protected-branch enforcement, as documented: [3](#0-2) 

In contrast, `RefService.UpdateReferences` builds a plain `updateref.Updater` directly on the repository and commits arbitrary reference updates (create/force-update/delete, including `refs/heads/*`) without ever calling `hook.Manager.PreReceiveHook`, `UpdateHook`, or any custom hook / Rails-authorization check: [4](#0-3) [5](#0-4) 

The request schema explicitly permits unconditional force-updates and deletions by leaving `old_object_id` empty: [6](#0-5) 

This mirrors the `emergencyWithdraw` flaw precisely: `withdraw()` enforces `lockingPeriod`, while `emergencyWithdraw()` performs the equivalent state-changing operation without that check. Here, `UserFFBranch`/`UserUpdateBranch`/etc. enforce hook-based authorization on ref updates, while `UpdateReferences` performs the equivalent ref-mutation operation without it.

### Impact Explanation
Any caller able to invoke `RefService.UpdateReferences` against a repository can force-update or delete any reference, including protected branches, entirely bypassing GitLab's branch-protection authorization (`/internal/allowed`) and any administrator-installed custom `pre-receive`/`update` hooks. This is a hook/quarantine gating bypass with direct impact on push/branch-protection integrity — a caller could overwrite `main` or delete tags/branches that are supposed to be protected, or push disallowed content that would normally be rejected by custom hooks.

### Likelihood Explanation
The RPC is a standard mutator method exposed by `RefService` and reachable by any client holding a valid Gitaly auth token that can target the repository (the same trust boundary as other repository-mutating RPCs). Within the indexed codebase, the only in-repo caller found is the backup-restore client (`internal/backup/repository.go`), but the RPC itself carries no additional access-check gating in the handler and is generally invokable like any other `RefService` RPC — nothing in `update_references.go` restricts it to internal/backup use only, unlike the hook-enforced `OperationService` RPCs.

### Recommendation
Route `RefService.UpdateReferences` reference mutations through the same hook-enforcing mechanism (`hook.Manager.PreReceiveHook` / `UpdateHook` / `ReferenceTransactionHook`, or equivalent access-check invocation) used by `OperationService`'s `updateReferenceWithHooks`/`UpdaterWithHooks`, or explicitly restrict/gate this RPC to trusted internal callers (e.g., backup/restore) with server-side enforcement, rather than relying on caller trust alone.

### Proof of Concept
1. An authenticated Gitaly client (any principal capable of calling `RefService`, matching the trust level of other push/ref-mutation RPCs) sends an `UpdateReferencesRequest` targeting `refs/heads/main` (a branch normally protected via GitLab's branch-protection settings) with an empty `old_object_id` and an arbitrary `new_object_id`.
2. `UpdateReferences` (`internal/gitaly/service/ref/update_references.go:16-45,85-99`) validates only the reference name and object ID format, then queues and commits the update via a bare `updateref.Updater` — no call to `hook.Manager.PreReceiveHook`/`UpdateHook` occurs anywhere in this path.
3. Compare with `UserFFBranch`/`UserUpdateBranch`, which cannot complete the same ref update without first passing `PreReceiveHook`'s call to `/internal/allowed` (`internal/gitaly/hook/updateref/update_with_hooks.go:224-226`).
4. Result: the protected branch is force-updated/deleted without ever undergoing the GitLab access check or custom hooks that would have blocked the very same logical operation via the intended RPCs.

```markdown
### Receive-Pack Hooks

These hooks are executed by `git-receive-pack` whenever changes are pushed into
a repository and can be used to:

- Verify whether the changes should be allowed into the repository in the first
  place (`pre-receive` and `update` hooks).
- Show information to the user (`post-update` hook).

While the reference-transaction hook executes on all Gitaly nodes, the
receive-pack style hooks only run on a single Gitaly, which is the primary node.
It can thus happen that receive-pack style hooks reject the update on the
primary node, which is not something the secondary nodes would see. The result
is that secondaries would now hang until the timeout for the RPC call triggers
given that the primary is never going to vote on this transaction.

To fix the hang, transactions support graceful stops: if the primary node fails
the RPC call in code that is only executed on the primary, then it will stop the
transaction and thus tell other Gitaly nodes to stop waiting for quorum.

There are two users of these hooks:

- `PostReceivePack` and `SSHReceivePack` directly invoke `git-receive-pack`,
  which then executes the hooks for us.
- Most RPCs in the `OperationService` that write objects into the repository
  manually invoke these hooks using the `updateref.UpdaterWithHooks` structure.

These hooks perform the following functions:

- `pre-receive`: The pre-receive hook receives all reference updates as a whole
  via standard input, where each change is represented by one line with the old
  and new object ID as well the name of the reference that is to be updated. At
  this point, all objects required to satisfy the update have already been
  received, but they are still in a separate "quarantine directory" and are
  therefore detached from the main repository. This hook first increments a
  reference counter that tracks how many pushes are active at the same time.
  Afterwards, it posts all changes to Rails' `/internal/allowed` API endpoint so
  that Rails can determine whether the change is allowed or not. Because objects
  still live in a quarantine directory, Gitaly tells Rails where it can find the
  quarantine directory using the repository's alternative object directory
  fields so that any subsequent RPC calls that check the change can access those
  objects. When the access checks succeed, any existing custom pre-receive hooks
  installed by the administrator are executed.
```

```text
// UpdateReferencesRequest is a request for the UpdateReferences RPC.
message UpdateReferencesRequest {
  // Update represents a reference update.
  message Update {
    // reference is the fully-qualified reference name that should be updated.
    bytes reference = 1;

    // old_object_id is the object ID the reference should be pointing to in order to be updated.
    // This has the intent to avoid time-of-check-time-of-use-style races when the object ID
    // has changed.
    //
    // If empty, the reference will be force-updated without any such checks. If set to the
    // all-zeroes object ID, this will verify that the branch did not exist previously.
    bytes old_object_id = 2;

    // new_object_id is the object ID the reference should be updated to. If set to the all-zeroes
    // object ID the branch will be deleted.
    bytes new_object_id = 3;
  };

  // repository is the repository where references shall be updated in.
  Repository repository = 1 [(target_repository)=true];
  // updates is the set of reference updates that shall be performed.
  repeated Update updates = 2;
}
```
