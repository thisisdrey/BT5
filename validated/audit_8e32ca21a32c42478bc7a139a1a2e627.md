Audit Report

## Title
Delivery receipt `success` flag is never checked before paying relayer rewards - (File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs)

## Summary
`Pallet::<T>::process_delivery_receipt` decodes a `DeliveryReceipt` containing a `success: bool` field but never inspects it before calling `T::RewardPayment::register_reward` and removing the corresponding `PendingOrder`. This allows a relayer (or any account submitting a valid proof of a genuinely failed/reverted Ethereum-side execution) to collect the full relayer fee and permanently clear the pending-order accounting record for a message that was not actually successfully delivered.

## Finding Description
The `DeliveryReceipt` struct explicitly carries a `success` field sourced from the `InboundMessageDispatched` Solidity event (`event InboundMessageDispatched(uint64 indexed nonce, bytes32 topic, bool success, bytes32 reward_address);`), confirming the protocol distinguishes successful vs. failed dispatch on the Ethereum side. [1](#0-0) 

`process_delivery_receipt` verifies the proof and gateway address, fetches the `PendingOrder` by nonce, and unconditionally pays the reward and removes the order — without ever reading `receipt.success`, per the cited code (L445-480) in the claim. The function signature, checks (`ensure!(T::GatewayAddress::get() == receipt.gateway, ...)`, `<PendingOrders<T>>::get(nonce).ok_or(...)`), reward payment (`T::RewardPayment::register_reward`), and unconditional `<PendingOrders<T>>::remove(nonce)` followed by `Event::MessageDelivered` are all consistent with the module's documented flow: "Fetch the pending order by nonce of the message, pay reward with fee attached in the order" and "Remove the order from `PendingOrders` map storage by nonce" — with no mention of any success/failure branching in the module-level docs either. [2](#0-1) 

Since the flag is decoded (`success: event.success`) but discarded by the pallet logic, the reward and accounting state advance identically whether the Ethereum-side execution succeeded or reverted. [3](#0-2) 

## Impact Explanation
This violates the required invariant that "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically." Paying the full relayer fee and destroying the `PendingOrder` accounting record for a message whose Ethereum-side execution failed constitutes an unbacked/incorrect reward payout and an irreversible loss of the ability to reconcile or retry that nonce — a duplicate-settlement/no-recourse class defect that qualifies under the "theft or unbacked mint or unlock" and "duplicate settlement or payout" impact categories.

## Likelihood Explanation
The exploit path requires only a real, valid event log/proof from the configured gateway contract — attainable whenever any relayer's Ethereum-side execution genuinely fails (e.g., out-of-gas or reverted call), a normal, non-malicious occurrence. Any unprivileged, signed account can then call the public extrinsic `submit_delivery_receipt` with that proof; no governance, validator, or malicious-peer assumption is needed, making this a routine, repeatable path.

## Recommendation
Check `receipt.success` in `process_delivery_receipt` before invoking `T::RewardPayment::register_reward`. On `success == false`, skip or reduce the reward payout per protocol design, emit a distinct event (e.g., `MessageDeliveryFailed`), and handle the `PendingOrder` state consistently with intended retry/accounting semantics rather than unconditionally removing it and emitting `Event::MessageDelivered`.

## Proof of Concept
1. A message is enqueued producing a `PendingOrder` with nonce `N` and fee `F > 0`.
2. The relayer's execution on Ethereum reverts, so the gateway contract emits `InboundMessageDispatched` with `success = false` for nonce `N`.
3. Any account submits this real proof via `submit_delivery_receipt`, decoding into `DeliveryReceipt { nonce: N, success: false, gateway: <valid>, .. }`.
4. `process_delivery_receipt` passes verifier and gateway checks, finds the `PendingOrder`, and — never checking `success` — calls `register_reward(&reward_account, .., F)`, removes the `PendingOrder`, and emits `Event::MessageDelivered { nonce: N }` identically to the success case.
5. Result: full fee paid for a failed delivery; the nonce's `PendingOrder` record is irrecoverably destroyed with no distinction from success.
