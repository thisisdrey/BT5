## Finding

### Title
Unchecked arithmetic in renewal price-cap calculation can panic/revert `do_renew` - (`substrate/frame/broker/src/dispatchable_impls.rs`)

### Summary
The external report describes a Dutch-auction price calculation that uses raw, unguarded subtraction (`startingPrice - priceDeduction`) which reverts via underflow once the deducted amount exceeds the starting price — a public-facing pricing function that can be driven into a revert state by the normal passage of time/usage. The closest verified local analog in this repository is in `pallet-broker`'s coretime renewal pricing, `Pallet::<T>::do_renew`, which — unlike essentially every other arithmetic operation in the same file/pallet — uses a bare, non-saturating arithmetic expression to compute the renewal price cap.

### Finding Description
In `substrate/frame/broker/src/dispatchable_impls.rs`, the function `do_renew` (called from the public `renew` extrinsic, reachable by any signed account holding a valid `PotentialRenewalRecord`) computes: [1](#0-0) 

```rust
let begin = sale.region_end;
let end_price = sale.end_price;
// Renewals should never be priced lower than the current `end_price`:
let price_cap = cmp::max(record.price + config.renewal_bump * record.price, end_price);
let now = RCBlockNumberProviderOf::<T::Coretime>::current_block_number();
let price = Self::sale_price(&sale, now).min(price_cap);
```

`record.price + config.renewal_bump * record.price` is computed with the plain `+`/`*` operators on `BalanceOf<T>`, rather than `saturating_add`/`saturating_mul` (or `checked_*`). This is the exact same class of defect as the external report: a bare arithmetic operation in a public, user-triggered pricing computation, in a codebase where every neighboring computation in the same module deliberately uses saturating arithmetic to avoid this exact failure mode — e.g. `duration: sale.region_end.saturating_sub(sale.region_begin)` a few lines above, and `sale.first_core + old_sale.cores_sold` uses saturating helpers elsewhere in `tick_impls.rs`. `record.price` compounds every renewal cycle (`renewal_price_adjusts_to_lower_market_end` test in `substrate/frame/broker/src/tests.rs` shows the bump is reapplied on every renewal: `price = price + Perbill::from_percent(10) * price` repeatedly), so over many renewal epochs of a long-lived auto-renewed core, `record.price` and its bump term can grow without the file providing any explicit bound. [2](#0-1) 

The crate's top-level `Cargo.toml` enables `overflow-checks`, meaning this add/mul will panic (not silently wrap) at the point of overflow. A panic inside a dispatchable's execution results in that transaction/block-authoring path erroring out defensively, and — because `do_renew` is invoked as part of automatic/auto-renewal flows in `tick_impls.rs` as well as manual calls — a stuck/overflowing renewal record could recurrently fail auto-renewal processing for that specific core/task each sale rotation, blocking the legitimate renewal path for that core (an analog to the "auction length is limited" DoS effect described in the report, applied to a Substrate pallet's renewal pricing rather than an NFT dutch auction).

### Impact Explanation
If `price_cap`'s computation overflows, the extrinsic (or the auto-renewal tick logic that calls the same code path) panics during execution. This causes the affected core's renewal to fail repeatedly (the record is never advanced/consumed successfully), effectively locking that potential renewal permanently — matching the "public underpriced/broken work that degrades... stalls processing" and "permanent user-fund or bridge-state lock"-style impact class the gate calls out, translated to the Coretime marketplace: a legitimate renter can no longer renew their core, and/or auto-renewal ticking for that slot is repeatedly disrupted.

### Likelihood Explanation
This requires `record.price` (plus its compounding `renewal_bump` percentage) to approach the numeric ceiling of `BalanceOf<T>` (typically `u128`), which is an extremely large magnitude in absolute token terms and is not directly attacker-supplied in one step — it grows only via repeated legitimate bump compounding across many sale rotations. This makes the practical likelihood of triggering the overflow low under expected economic conditions, though the code path lacks any explicit defensive bound (unlike every neighboring computation in the same function/file), which is the structural weakness being flagged.

### Recommendation
Replace the raw arithmetic in `do_renew`'s price-cap computation with saturating (or checked, with explicit error handling) operations, consistent with the rest of the pallet:

```rust
let bump = config.renewal_bump.saturating_mul_int(record.price);
let price_cap = cmp::max(record.price.saturating_add(bump), end_price);
```

Additionally, consider capping `record.price`/`price_cap` growth (e.g., against `sale.end_price` bounds already used elsewhere) so that compounding bumps cannot mathematically approach the `Balance` type's ceiling over long renewal chains.

### Proof of Concept
Conceptual reproduction path (cannot be executed here, but derivable from existing test scaffolding in `substrate/frame/broker/src/tests.rs`, e.g. `renewal_price_adjusts_to_lower_market_end`):
1. Configure a `renewal_bump` (e.g. `Perbill::from_percent(10)`) and repeatedly call `do_renew` for the same core across many sale rotations, letting `record.price` compound by 10% each cycle (as demonstrated by the existing test's `price = price + Perbill::from_percent(10) * price` pattern).
2. Continue this compounding over a sufficiently large number of iterations (many multiples, since `Balance` is typically `u128`) until `record.price + config.renewal_bump * record.price` would exceed `BalanceOf<T>::MAX`.
3. With `overflow-checks` enabled (as set in this repo's `Cargo.toml`), the arithmetic panics inside `do_renew`, causing the renewal transaction (or the `tick_impls.rs` auto-renewal path invoking the same logic) to fail, permanently blocking further renewal progress for that core/task.

Note: the magnitude required to trigger this is large under `u128`, so this is best characterized as a latent defensive-programming gap (matching the report's underlying bug class — public price-computation without saturating bounds) rather than an immediately practical low-cost exploit; I could not find a lower-cost trigger for this exact code path within the indexed contents of this repository.
