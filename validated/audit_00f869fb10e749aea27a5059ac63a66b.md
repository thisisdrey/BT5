Audit Report

## Title
Unbounded `assets` array in Snowbridge Inbound Queue V2 `Message` allows underpriced execution in a fixed-weight extrinsic - (File: `bridges/snowbridge/primitives/inbound-queue/src/v2/message.rs`)

## Summary
`Message::assets` is a plain `Vec<EthereumAsset>` populated by `Message::extract_assets` with no length cap, and the pallet's sole entrypoint `submit` charges the fixed `T::WeightInfo::submit()` regardless of how many assets (or how large the payload) is decoded. This lets any Ethereum-side caller of the Gateway's outbound message function craft a message with an arbitrarily large `assets` array, forcing disproportionate unbounded iteration in `extract_assets` and in `MessageToXcm::convert` for a cost fixed at benchmark-time.

## Finding Description
`Message` is declared with an unbounded vector: [1](#0-0) . It is populated by looping over every ABI-decoded asset entry with no cap in `extract_assets`: [2](#0-1) .

The pallet's only public dispatchable, `submit`, verifies the proof, decodes via `Message::try_from`, and dispatches under a single fixed weight annotation that does not vary with the decoded message's size: [3](#0-2) . The benchmark backing this fixed weight exercises exactly one fixture message (`T::Helper::initialize_storage()`), so it does not capture worst-case cost for a message carrying many `EthereumAsset` entries: [4](#0-3) .

Downstream, `MessageToXcm::convert` iterates the full `assets` vector to build `ReserveAssetDeposited`/`WithdrawAsset` XCM instructions, with cost proportional to `assets.len()`: [5](#0-4) .

By contrast, the sibling `outbound-queue-v2` pallet explicitly bounds its `commands` collection via `try_into()`, rejecting oversized payloads as `Corrupt`: [6](#0-5) . No equivalent `BoundedVec`/max-length check exists on the inbound side for `assets`, and `T::Verifier::verify` only attests to inclusion of the log in a genuine Ethereum receipt — it makes no claim about the size or shape of the log's ABI-encoded content, so the verification step does not bound this exploit.

## Impact Explanation
Because `submit()`'s weight is fixed independent of `assets.len()`, a message with a very large asset array causes unbounded loop iteration in `extract_assets` (decode) and in `MessageToXcm::convert` (XCM construction) while the pallet only charges the benchmark cost of a single-asset message. This is public underpriced work reachable by an unprivileged actor and degrades block production for the `submit` extrinsic on Bridge Hub, matching the allowed impact category of "public underpriced work that degrades block production."

## Likelihood Explanation
No privileged relayer, validator, or governance action is required. Any Ethereum account that can trigger the Gateway contract's outbound message emission with a large `assets` array can create a genuinely valid, provable log; any honest relayer subsequently calling `submit` with the resulting proof triggers the underpriced unbounded work. The only natural limiting factor is the Ethereum block gas limit for emitting the originating log — an economic/off-chain bound, not a runtime-enforced schema check — so the Substrate-side code itself has no defense.

## Recommendation
Bound `Message.assets` (and the ABI-decoded `payload.assets`) to a fixed maximum length in `extract_assets`/`TryFrom<&Log> for Message`, mirroring the `try_into()` bound in `outbound-queue-v2`, rejecting with `MessageDecodeError`/`Error::InvalidMessage` when exceeded. Additionally, make `submit()`'s weight scale with the (bounded) asset count/payload size, or benchmark and charge for the worst-case bounded size, rather than using a single fixed constant derived from a one-asset fixture.

## Proof of Concept
1. Craft (or simulate) an `OutboundMessageAccepted` event log whose ABI-encoded `Payload.assets` contains a very large number of `EthereumAsset` entries (bounded only by the Ethereum-side gas limit for emitting the log).
2. Construct a valid `EventProof` for this log and call `EthereumInboundQueueV2::submit(origin, event)`.
3. Observe `T::Verifier::verify` succeeds (only checks proof authenticity, not size), and `Message::try_from` decodes the full unbounded `assets` vector via `extract_assets` with no length check (`bridges/snowbridge/primitives/inbound-queue/src/v2/message.rs:182-192`).
4. Observe `process_message` → `MessageToXcm::convert` iterates all assets (`bridges/snowbridge/primitives/inbound-queue/src/v2/converter.rs:396-411`), all executed inside `submit`, which is charged only the fixed `T::WeightInfo::submit()` benchmarked against a single-asset fixture (`bridges/snowbridge/pallets/inbound-queue-v2/src/benchmarking.rs:14-29`), demonstrating cost/weight mismatch scaling with attacker-controlled asset count.

impl Message {
	fn extract_assets(
		payload: &IGatewayV2::Payload,
	) -> Result<Vec<EthereumAsset>, MessageDecodeError> {
		let mut substrate_assets = vec![];
		for asset in &payload.assets {
			substrate_assets.push(EthereumAsset::try_from(asset)?);
		}
		Ok(substrate_assets)
	}
}

		#[pallet::weight(T::WeightInfo::submit())]
		pub fn submit(origin: OriginFor<T>, event: Box<EventProof>) -> DispatchResult {
			let who = ensure_signed(origin)?;
			ensure!(!OperatingMode::<T>::get().is_halted(), Error::<T>::Halted);

			// submit message for verification
			T::Verifier::verify(&event.event_log, &event.proof)
				.map_err(|e| Error::<T>::Verification(e))?;

			// Decode event log into a bridge message
			let message =
				Message::try_from(&event.event_log).map_err(|_| Error::<T>::InvalidMessage)?;

			Self::process_message(who, message)
		}
