### Title
Unbounded attacker-controlled array indexing in `ValidateMultiSign`/`BatchValidateSign` precompiles causes uncaught `ArrayIndexOutOfBoundsException` on TVM contract call - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `extractBytesArray` and `extractSigArray` helper methods in `PrecompiledContracts.java` compute array lengths and offsets entirely from attacker-supplied calldata words without validating those values against the actual size of the decoded `words` array, mirroring the GHCB `snp_begin_psc()` bug class where a guest-controlled length is checked against a fixed maximum but never against the real buffer size.

### Finding Description
`extractBytesArray` reads `len` from `words[offset].intValueSafe()` and then iterates `i` from `0` to `len`, indexing `words[offset + i + 1]` and `words[offset + bytesOffset + 1]` with no check that these indices stay within `words.length`: [1](#0-0) 

`extractSigArray` has the identical unguarded pattern: [2](#0-1) 

In `ValidateMultiSign.execute`, the `sigArraySize > MAX_SIZE` guard is only applied when `VMConfig.allowTvmSelfdestructRestriction()` is enabled, and even then it only checks the size against `MAX_SIZE` (5) — analogous to the kernel checking `end_entry` against `VMGEXIT_PSC_MAX_COUNT` (253) instead of the real buffer bound. Critically, the calls to `extractSigArray`/`extractBytesArray` sit **outside** the method's inner `try { ... } catch (Throwable t)` block: [3](#0-2) 

So a crafted `words[3]` offset (or, when the restriction flag is off, no size cap check at all) can drive `offset + i + 1` past `words.length`, or make `bytesOffset`/`bytesLen` derived from a manipulated calldata word point outside the underlying `rawData` array, causing `Arrays.copyOfRange` in `extractBytes` to throw, or the `words[...]` index access to throw `ArrayIndexOutOfBoundsException`. That exception propagates unguarded out of `ValidateMultiSign.execute(byte[])`.

### Impact Explanation
Unlike the kernel bug, Java's array bounds checking prevents true out-of-bounds memory read/write or heap corruption — the JVM throws `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` instead of silently reading/writing adjacent memory. The remaining risk is availability: if this exception is not caught anywhere in the call chain from `Program.callToPrecompiledAddress` down through contract execution, an unprivileged caller could trigger an unhandled runtime exception during TVM execution of a `TriggerSmartContract`, potentially disrupting transaction processing for that call. I was not able to fully confirm within the available context whether `callToPrecompiledAddress` in `Program.java` wraps precompile `execute()` invocations in a catch-all handler that would gracefully convert this into a reverted transaction (the `BatchValidateSign.execute` wrapper explicitly does this via its own try/catch, but `ValidateMultiSign.execute` does not wrap the `extract*Array` calls). If the wrapping is present at the `Program` level and converts any `Throwable` from precompile execution into a normal transaction revert, this finding would only cause a single transaction to fail (no protocol-level impact). If it is not caught, it could lead to node-level disruption for the processing of that block/transaction.

### Likelihood Explanation
Reaching this code requires only a normal `TriggerSmartContract` transaction that calls the `ValidateMultiSign`/`BatchValidateSign` precompiled contract addresses with crafted calldata — no special privileges. This is directly reachable by any account with enough energy for the call, i.e., any anonymous contract caller.

### Recommendation
Add explicit bounds validation before indexing `words[]` in `extractBytesArray` and `extractSigArray` — verify `offset + i + 1 < words.length` and that computed `bytesOffset`/`bytesLen` stay within `data.length`, returning an empty/failure result instead of allowing an exception to propagate. Additionally, move the `extractSigArray`/`extractBytesArray` invocations in `ValidateMultiSign.execute` inside a try/catch (mirroring `BatchValidateSign.doExecute`'s wrapping) so any malformed-input exception is converted into `Pair.of(true, DATA_FALSE)` rather than propagating out of the precompile.

### Proof of Concept
1. Deploy any contract that performs a low-level `CALL` to the `ValidateMultiSign` precompile address (0x66 or similar reserved address) via `TriggerSmartContract`.
2. Construct calldata as ABI-encoded words where `words[3]` (the signature-array offset) is set to a large value such that `words[3].intValueSafe() / WORD_SIZE` plus the derived `len` from `words[offset]` causes `offset + i + 1` to exceed the actual `words.length` decoded from the (short) `rawData`.
3. With `VMConfig.allowTvmSelfdestructRestriction()` disabled (so the `sigArraySize > MAX_SIZE` guard is skipped) or set such that the size check is bypassed, invoke the contract call; `extractBytesArray`/`extractSigArray` throws `ArrayIndexOutOfBoundsException`, which is not caught by `ValidateMultiSign.execute`, and propagates to the caller of `execute()`.
4. Observe whether this uncaught exception is handled gracefully by `Program.callToPrecompiledAddress` (converts to a normal revert) or surfaces as an unexpected runtime failure during block/transaction processing — the latter would confirm a denial-of-service condition triggerable by any transaction sender.
