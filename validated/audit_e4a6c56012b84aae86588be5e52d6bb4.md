The strongest analog to CVE‑2017‑12453 (an out‑of‑bounds heap read while parsing a crafted binary container's variable-length metadata) is in Bazel's own zip/jar reader, `InputZipFile::ProcessCentralDirEntry` in `third_party/ijar/zip.cc`.

### Title
Out-of-bounds heap read parsing crafted ZIP/JAR central-directory extra fields - (File: third_party/ijar/zip.cc)

### Summary
`InputZipFile::ProcessCentralDirEntry` walks each central-directory record's "extra field" data using an attacker-controlled 16-bit length with no bound checks against the mapped file's actual size, unlike the sibling local-file-header parser which explicitly calls `EnsureRemaining()` before every read.

### Finding Description
`ProcessCentralDirEntry` reads `file_name_length`, `extra_field_length`, `file_comment_length` directly from the central directory header bytes and then iterates the extra-field area: [1](#0-0) [2](#0-1) 

The loop condition is `while (extra_p != p)`, and each iteration unconditionally calls `get_u2le(extra_p)` (header id), `get_u2le(extra_p)` (data_size), then advances `extra_p += data_size` — `data_size` is fully attacker-controlled and never validated against the remaining bytes in the extra field or against the mmap'd file length (`input_file_->Length()`). If `data_size` is crafted so `extra_p` jumps past `p` (the extra-field end) instead of landing exactly on it, the loop's exit condition (`extra_p != p`) is never satisfied by equality, so the loop keeps dereferencing memory beyond the intended extra-field region — and can walk past the end of the memory-mapped input buffer entirely, since there is no check against `zipdata_in_ + in_length`.

This contrasts with `InputZipFile::ProcessLocalFileEntry`, which calls `EnsureRemaining()` before every variable-length read: [3](#0-2) 

`ProcessCentralDirEntry` has no analogous guard, and callers such as `InputZipFile::ProcessNext`/`Open` trust its output to seek `p` and dereference further data: [4](#0-3) 

The class-level comment claims parsing is "safe" because the central directory is always followed by a signature-bearing structure, but that assumption does not hold for the inner extra-field loop, which has no upper bound tied to the actual mapped buffer size: [5](#0-4) 

### Impact Explanation
This parser runs over JAR/ZIP files supplied as build inputs (e.g., third-party `.jar` dependencies processed by the `ijar` interface-jar generator, and the `zipper` tool, both built from this same `third_party/ijar/zip.cc`). A hostile origin that publishes such a jar (matching whatever checksum a build pins, since the attacker controls the exact bytes being pinned) can craft a central directory entry whose extra field length triggers reads past the end of the memory-mapped file — an out-of-bounds heap read that can crash the `ijar`/`zipper` process (information disclosure into process output/crash is also plausible depending on what memory follows the mapping).

### Likelihood Explanation
Any dependency archive processed through `ijar` (used automatically for every `.jar` used as a compile-time dependency to build a stripped interface jar) or through `zipper` goes through this exact code path. Because the vulnerable loop has zero bounds checking (unlike its sibling function), a single crafted central-directory extra field is sufficient — no additional preconditions are needed.

### Recommendation
Add explicit bounds checks in `ProcessCentralDirEntry`'s extra-field loop, mirroring `EnsureRemaining()` in `ProcessLocalFileEntry`: verify `extra_p + 4 <= p` before reading each `header_id`/`data_size` pair, and verify `data_size` does not push `extra_p` past `p`; abort parsing with an error if either check fails. Additionally, validate `file_name_length`, `extra_field_length`, and `file_comment_length` against `input_file_->Length()` before advancing `p`.

### Proof of Concept
Construct a ZIP file whose single central directory header sets `extra_field_length` to a small value (e.g., 4), but embed within those bytes an `ExtraField` entry with `data_size` set to a large value (e.g., `0xF000`) that is inconsistent with the declared length — analogous to the existing test helper `CreateZipWithMalformedExtraField` used elsewhere in the codebase for a related (but different, LFH-focused) scenario: [6](#0-5) 
Feed this file to `ijar`/`zipper` (or a `BuildIntegrationTestCase`/`src/test/shell/bazel` test that builds a `java_library` depending on such a malformed jar) and observe the OOB heap read in `ProcessCentralDirEntry`'s extra-field walk (detectable via ASan/heap-read instrumentation, or a crash on unmapped memory).

  u8 compressed, uncompressed;
  u8 offset;
  if (!ProcessCentralDirEntry(central_dir_current_, &compressed, &uncompressed,
                              filename, PATH_MAX, &attr, &offset)) {
    return false;
  }

  // There might be an offset specified in the central directory that does
  // not match the file offset, so always update our pointer.
  p = zipdata_in_ + in_offset_ + offset;

  if (EnsureRemaining(4, "signature") < 0) {
    return false;
  }
  u4 signature = get_u4le(p);
  if (signature == LOCAL_FILE_HEADER_SIGNATURE) {
    if (ProcessLocalFileEntry(compressed, uncompressed) < 0) {
      return false;
    }
  } else {
    error("local file header signature for file %s not found\n", filename);
    return false;
  }

  return true;
}
