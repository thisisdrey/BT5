### Title
Non-constant-time comparison of the shared `auth_token` secret enables a remote timing side-channel to recover privileged RPC credentials - (File: `stackslib/src/net/api/postblock_v3.rs`)

### Summary
Several privileged Stacks node HTTP RPC endpoints gate access to a single shared secret (`connection_options.auth_token`) by comparing the client-supplied `authorization` header directly against the configured password using Rust's `!=` string operator. This is a plain, short-circuiting byte-by-byte comparison, not a constant-time comparison, which is the same bug class as CVE-2018-19784 (weak cryptography used for computing/checking an authorization value, enabling brute-force/side-channel recovery of authorization data).

### Finding Description
The `authorization` header is compared to the configured secret using ordinary string inequality in multiple RPC request handlers reachable directly from any unauthenticated network peer:

The same identical pattern is used for the block proposal endpoint (`/v3/block_proposal`, which triggers full block validation) and block/tx simulation endpoints, all sharing the same `auth_token` secret defined in `stackslib/src/config/mod.rs:3802-3816` and threaded through `ConnectionOptions.auth_token` (`stackslib/src/net/connection.rs:440-441`). `&str`/`String` `PartialEq` in Rust performs a length check followed by a byte-slice comparison that returns as soon as a mismatching byte is found (`memcmp`-style short-circuit), so the time taken to reject a guess leaks how many leading bytes of the guess matched the real secret. This is directly analogous to the reported bug class: a homegrown/weak equality-based authorization check that can be probed remotely to reconstruct the correct secret byte-by-byte rather than requiring the full secret to be guessed at once.

### Impact Explanation
An attacker with network access to the node's RPC port can send repeated authorization attempts and measure response latency to iteratively recover the `auth_token` value one byte at a time, drastically reducing the effective secret-guessing search space from exponential (over the whole token) to linear (byte-by-byte). Once recovered, the attacker gains an auth bypass: unauthenticated write to node state via the block-broadcast path (`postblock_v3.rs`, `/v2/blocks?broadcast=1`) and the ability to submit forged block proposals for validation (`postblock_proposal.rs`, `/v3/block_proposal`), which is designed to be restricted to the trusted `stacks-signer`. This matches the "auth bypass" / "unauthenticated write to state" high/critical impact criteria.

### Likelihood Explanation
Exploitation requires only network access to the node's configured RPC/HTTP listener (no prior credentials, no node secret key). Because network jitter and Rust's fast `memcmp` make individual timing signals noisy, this would typically require many repeated requests and statistical averaging to reliably measure per-byte timing differences remotely, so the practical difficulty is nontrivial but consistent with known timing side-channel attacks against non-constant-time secret comparisons over a network (well studied against short shared-secret HTTP tokens).

### Recommendation
Replace the direct `!=`/`==` string comparisons against `password`/`self.auth` in `postblock_v3.rs`, `blockreplay.rs`, `txsimulate.rs`, `postblock_proposal.rs`, `blocksimulate.rs`, and `fastcallreadonly.rs` with a constant-time comparison (e.g., `subtle::ConstantTimeEq`, or compare over a fixed-size HMAC/hash of both secret and header rather than the raw strings) so that the comparison time does not depend on the position of the first mismatched byte.

### Proof of Concept
1. Configure a node with `auth_token = "<64+ char secret>"`.
2. From a remote unauthenticated client, repeatedly send `POST /v2/blocks?broadcast=1` (or `GET /v3/blocks/replay/:id`, `POST /v3/transactions/simulate`) with candidate `authorization` header values that share an increasing common prefix with the real secret.
3. Measure response latency for the 401 rejection at `postblock_v3.rs:107` / `blockreplay.rs:581` / `txsimulate.rs:358`; statistically, candidates whose prefix matches more bytes of the real secret take marginally longer to be rejected because more bytes must be compared before the mismatch is found.
4. Iterating this byte-by-byte (as in classic timing side-channel attacks against non-constant-time token checks) allows recovery of the full `auth_token`, which then grants unauthenticated write access to `/v2/blocks?broadcast=1` and the ability to submit block proposals to `/v3/block_proposal`.
