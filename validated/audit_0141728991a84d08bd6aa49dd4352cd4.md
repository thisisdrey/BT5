## Title
Delivery-receipt `success` flag is decoded but never checked, so relayer rewards are paid even for failed Ethereum-side message execution - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

### Summary
`DeliveryReceipt` decodes the `InboundMessageDispatched` Ethereum event log, which carries a `success: bool` field indicating whether the outbound message actually executed successfully on the Gateway contract on Ethereum. `Pallet::process_delivery_receipt`, invoked from the public extrinsic `submit_delivery_receipt`, never reads or checks this field — it pays out the full relayer reward and clears the pending order purely based on nonce/gateway matching, regardless of delivery outcome.

### Finding Description
`DeliveryReceipt` is defined with a `success` field decoded straight from the ABI-encoded Ethereum log: [1](#0-0) 

`process_delivery_receipt` is the function that actually resolves the pending order and pays the reward. It checks `receipt.gateway`, resolves the `reward_account`, looks up the `PendingOrders` entry by `receipt.nonce`, and if `order.fee > 0` unconditionally calls `T::RewardPayment::register_reward`, then removes the order and emits `MessageDelivered`: [2](#0-1) 

`receipt.success` is decoded but is dead data — a `grep` across the pallet (`bridges/snowbridge/pallets/outbound-queue-v2/**`) for any use of `.success` returns no matches, confirming the field is discarded entirely, analogous to the report's commented-out `console.error`: the code path clearly *knows* success/failure occurred (the field exists and is parsed) but the information is dropped instead of being captured and acted upon.

The public extrinsic entry point is: [3](#0-2) 

No other code path in this pallet reads `receipt.success` before the reward is registered and the order removed.

### Impact Explanation
Reward accounting is decoupled from actual bridge delivery outcome. As long as a verifiable delivery-receipt log exists for a given nonce (i.e., the transaction that emitted `InboundMessageDispatched` was included and proven, whether `success` was `true` or `false`), any signed account can call `submit_delivery_receipt` and have the relayer reward for that nonce paid out from `PendingOrders` — even though the corresponding commands failed on the Ethereum Gateway. This breaks the intended invariant that "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically" — settlement (reward payout + order removal) advances on receipt of *any* outcome, not specifically on successful execution. This constitutes an unbacked payout: value (reward fee) leaves the bridge's fee pool without the corresponding successful service being rendered, and the failed message's `PendingOrder` is permanently removed, closing off any possibility of re-processing/retry or penalizing the failure.

### Likelihood Explanation
No privileged, governance, or malicious-relayer assumption is needed: `submit_delivery_receipt` is callable by any signed account with a valid Ethereum-side execution proof, and Ethereum transactions frequently revert/fail for mundane reasons (insufficient gas at execution, gateway-side validation failure, etc.) independent of any malicious relaying — the relayer only needs to submit a proof for whatever `InboundMessageDispatched` event happened to be emitted (success or failure), which is a routine occurrence, not an attack requiring compromised infrastructure.

### Recommendation
**Short term:** In `process_delivery_receipt`, check `receipt.success` before calling `T::RewardPayment::register_reward`. On `false`, either withhold/reduce the reward, emit a distinct failure event (e.g., `MessageDeliveryFailed`), and/or retain the `PendingOrder` for a bounded retry window instead of unconditionally removing it, mirroring the “failed payout must not silently advance settlement” pattern already used in `pallet-treasury`'s `payout`/`check_status` flow (`substrate/frame/treasury/src/lib.rs`).

**Long term:** Ensure every field decoded from an untrusted/external proof (delivery success flags, error codes, revert reasons) is explicitly consumed by the state-transition logic that depends on it; add a lint/test convention that flags decoded-but-unused fields on security-critical structs like `DeliveryReceipt`.

### Proof of Concept
1. A message with nonzero `fee` is queued and processed by `do_process_message`, creating a `PendingOrder { nonce, fee, .. }`. [4](#0-3) 
2. On Ethereum, the Gateway processes the message but the command execution reverts/fails (a normal on-chain outcome, e.g., insufficient gas forwarded to the command), so the emitted `InboundMessageDispatched` event has `success = false`.
3. Any signed account observes this event, builds the proof, and calls `submit_delivery_receipt(origin, event)`.
4. `T::Verifier::verify` succeeds (the proof is valid — it proves a real, if failed, execution), `DeliveryReceipt::try_from` decodes `success: false` correctly, but `process_delivery_receipt` never inspects it.
5. Because `order.fee > 0`, `T::RewardPayment::register_reward` pays out the full relayer reward, and the order is removed — identical to the "successful" path exercised in the emulated test `send_message_from_penpal_to_ethereum` / `EthereumOutboundQueueV2::process_delivery_receipt` assertions, which only checks `MessageDelivered` is emitted and does not assert anything about `receipt.success`: [5](#0-4) 

This demonstrates the reward is paid identically regardless of the `success` field's value, confirming the missing check.

```rust
		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
```
