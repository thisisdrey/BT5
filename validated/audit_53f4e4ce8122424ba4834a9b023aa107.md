## Analysis

The Connext bug's core defect: a payout that pays the "wrong asset" and, because the correct settlement never lands on the intended side, permanently locks funds with no recovery path once the local bookkeeping has already been finalized. The polkadot-sdk analog is in the Snowbridge relayer reward payout path, `PayAccountOnLocation::pay_reward` in `bridges/snowbridge/primitives/core/src/reward.rs`, combined with `pallet_bridge_relayers::do_claim_rewards`.

`do_claim_rewards` removes the relayer's `RelayerRewards` entry from storage (`maybe_reward.take()`) *before* calling `T::PaymentProcedure::pay_reward`, and only restores it on an `Err` return: [1](#0-0) 

For `BridgeReward::Snowbridge`, that payment procedure is `PayAccountOnLocation::pay_reward`, which builds an XCM that performs `ReserveAssetDeposited` (denominated in the `EthereumNetwork` global-consensus location) followed by `DepositAsset` to the beneficiary on Asset Hub, and considers the payment successful as soon as `XcmSender::deliver(ticket)` returns `Ok(())`: [2](#0-1) 

`deliver` only confirms the message was **queued** for cross-chain transport, not that the remote `ReserveAssetDeposited`/`DepositAsset` sequence actually executed successfully on Asset Hub. If Asset Hub does not (yet, or no longer) trust `GlobalConsensus(EthereumNetwork)` as a reserve for the reward asset, or if the `DepositAsset` step traps for any other reason (e.g. beneficiary/asset issues), the remote execution silently fails while the local BridgeHub side has already returned `Ok(())`, causing `do_claim_rewards` to keep the reward storage entry removed and emit `RewardPaid`. The relayer's accumulated reward is now unrecoverable — there is no atomic linkage between "local settlement finalized" and "remote deposit actually succeeded," matching the pivot requirement that "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically."

This is configuration-routed today via `BridgeRewardPayer::pay_reward` on BridgeHub Westend, which dispatches to `PayAccountOnLocation` for the `Snowbridge` reward kind: [3](#0-2) 

### Title
Relayer rewards can be permanently lost due to non-atomic cross-chain settlement in `PayAccountOnLocation::pay_reward` - (File: `bridges/snowbridge/primitives/core/src/reward.rs`)

### Summary
`pallet_bridge_relayers::claim_rewards`/`claim_rewards_to` irrevocably deletes the relayer's pending reward from local storage as soon as `PaymentProcedure::pay_reward` returns `Ok(())`. For Snowbridge rewards, `pay_reward` (`PayAccountOnLocation`) treats successful XCM *dispatch* (`XcmSender::deliver`) to Asset Hub as final settlement, even though the actual value transfer (`ReserveAssetDeposited` + `DepositAsset`) executes asynchronously and can fail on Asset Hub. There is no receipt/confirmation mechanism to roll back the local claim if the remote deposit fails, so the relayer's reward can be destroyed with no way to reclaim it.

### Finding Description
`do_claim_rewards` takes the reward out of `RelayerRewards` before invoking the payment procedure, and only re-inserts it if `pay_reward` returns an `Err`: [4](#0-3) 

`PayAccountOnLocation::pay_reward` builds and sends an XCM program that performs `ReserveAssetDeposited` for the Ethereum-denominated reward asset followed by `DepositAsset` to the caller-supplied beneficiary location on Asset Hub, then returns `Ok(())` once `XcmSender::deliver(ticket)` succeeds: [5](#0-4) 

`deliver` only guarantees the message entered the outbound transport (e.g., HRMP/XCMP to Asset Hub); it says nothing about whether the remote chain will actually execute `ReserveAssetDeposited`/`DepositAsset` successfully. Both instructions can fail independently of anything the relayer or `pay_reward` caller controls — e.g. if Asset Hub's `IsReserve` filter no longer (or not yet) trusts `GlobalConsensus(EthereumNetwork)` for that asset, if the beneficiary location fails to accept the deposit, or if any other step in the remote program traps. Because `UnpaidExecution` is used and the message originates via `DescendOrigin`/`UniversalOrigin`, a failure aborts before any assets are created, so there is nothing left to trap or reclaim via `ClaimAsset` either.

By the time any such remote failure could be observed, the local pallet has already: (1) removed the reward from `RelayerRewards`, (2) emitted `RewardPaid`, and (3) returned success to the relayer's `claim_rewards`/`claim_rewards_to` extrinsic. The settlement state (pending-reward storage) thus advances based on "message queued" rather than "value delivered and received," violating the required invariant that payout state must only advance after execution and settlement succeed atomically.

### Impact Explanation
A relayer's accumulated bridge reward can be permanently and irrecoverably lost through no fault of the relayer or any privileged/malicious actor — simply because the cross-chain settlement step failed asynchronously after the local claim was already finalized. This is a "permanent user-fund lock/loss" impact matching the required impact gate (unbacked burn/loss of otherwise-claimable value with no recovery path), directly analogous to the original report's "cancel always reverts, funds locked forever" pattern, except here it manifests as reward funds being wiped from local accounting while never actually landing at the destination.

### Likelihood Explanation
This does not require a malicious peer, relayer, governance actor, or any privileged operation — any relayer calling `claim_rewards_to` (or the default `claim_rewards`, which for Snowbridge routes through the same `AssetHubLocation` beneficiary path) is exposed whenever the remote Asset Hub side can't complete the deposit (e.g. the trusted-reserve registration for the Ethereum asset changes, is paused, or any transient remote execution failure occurs). Because there is no atomicity or confirmation/rollback mechanism, this is a structural gap rather than an edge-case timing coincidence, and it silently reduces relayer incentive without any error surfaced on BridgeHub.

### Recommendation
Do not treat `pay_reward` as final settlement based solely on successful XCM dispatch. Either:
- Require an explicit delivery/execution confirmation (e.g., a receipt callback or a separate "confirm settlement" step) before removing the `RelayerRewards` entry, or
- Keep the reward in an "in-flight" state that can be retried or refunded if the remote XCM execution fails, mirroring the atomic "advance only after execution and settlement succeed" pattern required elsewhere in the bridge stack.

### Proof of Concept
1. Configure (or simulate a future state where) Asset Hub no longer trusts `GlobalConsensus(EthereumNetwork)` as a reserve for the WETH-equivalent reward asset used by `PayAccountOnLocation` (e.g., asset paused/removed from the trusted-reserve set), while a relayer still has an outstanding `Snowbridge` reward registered in `RelayerRewards`.
2. Relayer calls `pallet_bridge_relayers::claim_rewards_to` with `reward_kind = BridgeReward::Snowbridge` and `beneficiary = BridgeRewardBeneficiaries::AssetHubLocation(...)`.
3. `do_claim_rewards` removes the reward from storage, then `BridgeRewardPayer::pay_reward` → `PayAccountOnLocation::pay_reward` builds the XCM, calls `XcmExecutor::charge_fees` (relayer pays local delivery fee) and `XcmSender::deliver(ticket)`, which succeeds (message is queued) and returns `Ok(())`.
4. `RewardPaid` event is emitted; storage stays cleared — the extrinsic reports success.
5. On Asset Hub, when the message executes, `ReserveAssetDeposited` fails (asset not trusted as reserve) and the whole remote program aborts with no assets created to trap.
6. The relayer's reward is now permanently gone: it's not in `RelayerRewards` (already claimed) and never arrived at the beneficiary on Asset Hub, with no mechanism to detect, retry, or reclaim it.

	fn pay_reward(
		relayer: &Relayer,
		_: (),
		reward: RewardBalance,
		beneficiary: Self::Beneficiary,
	) -> Result<(), Self::Error> {
		let ethereum_location = Location::new(2, [GlobalConsensus(EthereumNetwork::get())]);
		let assets: Asset = (ethereum_location.clone(), reward.into()).into();

		let xcm: Xcm<()> = alloc::vec![
			UnpaidExecution { weight_limit: Unlimited, check_origin: None },
			DescendOrigin(InboundQueueLocation::get().into()),
			UniversalOrigin(GlobalConsensus(EthereumNetwork::get())),
			ReserveAssetDeposited(assets.into()),
			DepositAsset { assets: AllCounted(1).into(), beneficiary },
		]
		.into();

		let (ticket, fee) =
			validate_send::<XcmSender>(AssetHubLocation::get(), xcm).map_err(|_| XcmSendFailure)?;
		XcmExecutor::charge_fees(relayer.clone(), fee).map_err(|_| ChargeFeesFailure)?;
		XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;

		Ok(())
	}
