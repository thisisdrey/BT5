### Title
Out-of-bounds read of Zip64 extra-field attributes via mismatched size-field sentinels - (File: `src/tools/singlejar/zip_headers.h`)

### Summary
`singlejar`'s `CDH`/`LH` accessors compute the index into the variable-length `Zip64ExtraField::attr_[]` array from the 32-bit sentinel values (`0xFFFFFFFF`) of *unrelated* header fields, without ever checking that the field actually contains that many 8-byte attributes (`attr_count()`), allowing a crafted jar/zip to force a read past the end of the extra-field payload.

### Finding Description
`Zip64ExtraField::attr64(int index)` performs a raw, unchecked array read: [1](#0-0) 

Callers derive `index` not from the field's own `attr_count()`/`payload_size()`, but from whichever *other* 32-bit size fields in the same header happen to equal the `0xFFFFFFFF` sentinel: [2](#0-1) 

Per the ZIP64 spec, the extra field is only supposed to carry the subset of {uncompressed size, compressed size, local header offset} whose 32-bit counterpart is `0xFFFFFFFF`, in that fixed order — but nothing enforces that the *actual number of stored attributes* matches how many sentinels are set. An attacker who controls the raw bytes of a `.zip`/`.jar` file (e.g. a dependency jar/archive that `singlejar` merges into a deploy jar) can set `compressed_file_size32`, `uncompressed_file_size32`, and `local_header_offset32` all to `0xFFFFFFFF` while making the accompanying `Zip64ExtraField` payload only 8 bytes long (`attr_count() == 1`). `CDH::local_header_offset()` then computes `attr_no = 2` and calls `z64->attr64(2)`, reading 16 bytes into an 8-byte payload — 8 bytes past the extra field's declared/allocated bounds. The analogous mis-indexing exists in `CDH::compressed_file_size()`/`uncompressed_file_size()` and `LH::compressed_file_size()`/`uncompressed_file_size()`.

This is distinct from the existing hardening in the codebase: `ExtraField::find()` and the extra-field iteration loops in `output_jar.cc` (which back the `MalformedExtraField` regression test) only validate that an extra field's *own* `size()`/`payload_size()` doesn't run past the extra-fields buffer end. They do not, and cannot, validate that a *found* Zip64 field has enough attributes for the index a caller later computes from unrelated sentinel fields: [3](#0-2) 

Because the `Zip64ExtraField` object is obtained by pointer arithmetic over a memory-mapped input file (`InputJar`/`MappedFile`), reading `attr_[2]` when only `attr_[0]` was allocated reads adjacent bytes in the mapped file/heap (comment field, next CDH record, or, if this is the last record before EOF/page boundary, unmapped memory), producing an out-of-bounds read — the same fundamental bug class as CVE-2017-5447 (index derived from one piece of attacker data used unchecked to read an array sized by different logic).

### Impact Explanation
An attacker who supplies a malicious `.jar`/`.zip` as a build input (e.g., a third-party dependency artifact fetched via `http_jar`/`http_archive`, or any file that reaches `singlejar`/`InputJar`) can trigger an out-of-bounds read in the build worker process. This can crash the `singlejar` action (denial of the specific action/build) or, depending on adjacent memory layout, leak bytes from the mapped file/heap into the value returned by `local_header_offset()`/`compressed_file_size()`/`uncompressed_file_size()`, which then influences how much file data `singlejar` copies out of the archive — potentially reading and embedding out-of-bounds memory content into the output jar.

### Likelihood Explanation
Reaching the vulnerable code only requires an attacker-authored zip/jar file with a self-consistent but semantically wrong combination of `0xFFFFFFFF` sentinel fields and a short Zip64 extra field; no compression bomb or invalid extra-field bounds are needed, so it sails past `ExtraField::find()`'s existing bounds checks and the `MalformedExtraField` test's specific check (which targets extra-field-size overrun, not attribute-count mismatch). A declared sha256/integrity for the archive does not stop this, since the attacker controls the archive content that the hash is computed over.

### Recommendation
In `Zip64ExtraField`, bound every `attr64(index)` read (and the derived accessors in `LH`/`CDH`) by `attr_count()`, treating an out-of-range index the same as a missing/`nullptr` Zip64 field (e.g., return the documented error sentinel or abort with a diagnostic like the existing `diag_errx` calls for malformed extra fields), instead of trusting that the number of `0xFFFFFFFF` sentinels in the surrounding header always matches the number of attributes actually present in the extra field.

### Proof of Concept
Extend the existing `output_jar_simple_test.cc` harness (pattern already used by `CreateZipWithMalformedExtraField`/`MalformedExtraField`) with a new `BuildIntegrationTestCase`/gtest case that:
1. Builds a valid `LH`+`CDH` pair where `compressed_file_size32`, `uncompressed_file_size32`, and `local_header_offset32` are all set to `0xFFFFFFFF`.
2. Attaches a `Zip64ExtraField` extra field to the `CDH` with `payload_size == 8` (i.e., `attr_count() == 1`), which is a valid, in-bounds extra field per `ExtraField::find()`.
3. Feeds this crafted jar as a `--sources` input to `OutputJar::Doit()` (as `MalformedExtraField` does), and runs it under ASan/valgrind.
4. Confirm the OOB read is reported when `CDH::local_header_offset()` executes `z64->attr64(2)`, at an offset (16 bytes) beyond the 4+8-byte Zip64 extra field payload actually allocated — this is not currently caught by any existing bounds check, unlike the `MalformedExtraField` test's scenario. std::string CreateZipWithMalformedExtraField() {
  std::string zip_data;
  const std::string filename = "evil.bin";

  // 1. Local File Header (LFH)
  size_t lh_offset = zip_data.size();
  size_t lh_size = sizeof(LH) + filename.size();
  zip_data.resize(lh_offset + lh_size, 0);
  auto* lh = reinterpret_cast<LH*>(&zip_data[lh_offset]);
  lh->signature();
  lh->version(10);
  lh->file_name(filename.data(), filename.size());

  // 2. Extra field payload containing an oversized payload_size
  uint8_t ef_buffer[8] = {0};
  auto* ef1 = reinterpret_cast<ExtraField*>(ef_buffer);
  ef1->signature(0x000d);
  ef1->payload_size(0);

  auto* ef2 = reinterpret_cast<ExtraField*>(ef_buffer + ef1->size());
  ef2->signature(0xdead);
  ef2->payload_size(0xf000);  // Malformed size exceeding extra field buffer

  // 3. Central Directory Header (CDH)
  size_t cdh_offset = zip_data.size();
  size_t cdh_size = sizeof(CDH) + filename.size() + sizeof(ef_buffer);
  zip_data.resize(cdh_offset + cdh_size, 0);
  auto* cdh = reinterpret_cast<CDH*>(&zip_data[cdh_offset]);
  cdh->signature();
  cdh->version(20);
  cdh->version_to_extract(10);
  cdh->local_header_offset32(lh_offset);
  cdh->file_name(filename.data(), filename.size());
  cdh->extra_fields(ef_buffer, sizeof(ef_buffer));

  // 4. End of Central Directory (EOCD)
  size_t ecd_offset = zip_data.size();
  zip_data.resize(ecd_offset + sizeof(ECD), 0);
  auto* ecd = reinterpret_cast<ECD*>(&zip_data[ecd_offset]);
  ecd->signature();
  ecd->this_disk_entries16(1);
  ecd->total_entries16(1);
  ecd->cen_size32(cdh_size);
  ecd->cen_offset32(cdh_offset);

  return zip_data;
}
