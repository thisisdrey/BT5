### Title
`process_tx_internal` returns `ProcessTxResponse::ValidTx` on `InsertTransactionResult::NoSpaceLeft` for the active-validator branch without forwarding or re-queueing - ([File: chain/client/src/rpc_handler.rs])

### Summary
When `ShardedTransactionPool::insert_transaction` returns `InsertTransactionResult::NoSpaceLeft` (pool size limit reached, enforced in `chain/pool/src/lib.rs:99-106`), `process_tx_internal` only logs a trace message [1](#0-0)  and falls through. If the node is `active_validator` for the shard, the function unconditionally returns `ProcessTxResponse::ValidTx` [2](#0-1) , even though the transaction was never inserted into the pool and `possibly_forward_tx_to_next_epoch` only forwards to future-epoch validators, not to current chunk producers for this shard/height. The RPC caller (relayer/wallet) therefore receives a "valid" response that implies acceptance, while the transaction may never be included in a chunk.

### Finding Description
The transaction pool (`TransactionPool` in `chain/pool/src/lib.rs`) enforces a global-per-shard byte-size limit (`total_transaction_size_limit`), returning `InsertTransactionResult::NoSpaceLeft` once exceeded [3](#0-2) . This limit is configurable via `transaction_pool_size_limit` and constructed by `ChunkProducer::new` [4](#0-3) .

In `process_tx_internal`, after `validate_tx` and `can_verify_and_charge_tx` pass (signature, nonce, access-key, gas/storage checks all succeed), the code attempts to insert into the pool only if this node `is_chunk_producer_for_transaction` [5](#0-4) . On `NoSpaceLeft`, unlike `Success` and `Duplicate` (which both return early with clear semantics — `Success` continues into the forwarding branch, `Duplicate` returns `ValidTx` because it's genuinely already present), the `NoSpaceLeft` arm does nothing but log and continues execution into the same code path as a successful insertion. Since `active_validator(shard_id)` is then checked and, if true, the function returns `ProcessTxResponse::ValidTx` unconditionally at line 312, regardless of whether the transaction was actually inserted or forwarded anywhere. This means:
- The doc comment on `process_tx` ("If accepted, it will be added to the transaction pool and possibly forwarded to another validator") does not hold in this branch.
- No error, no `Dropped` response, no explicit "queued but not durable" signal is returned to the caller.
- `possibly_forward_tx_to_next_epoch` (called at line 310) only forwards near epoch boundaries to *next-epoch* validators — it does not requeue to peer chunk producers for the current epoch, so a `NoSpaceLeft` tx handled by the active validator for the current epoch is not forwarded anywhere and is permanently lost from this node's perspective.

An unprivileged attacker can trigger the pool-full condition by flooding the target shard's transaction pool with cheap, validly-signed transactions (each just needs to pass `validate_tx`/`can_verify_and_charge_tx`, i.e., a real access key and enough balance to cover gas fees) up to the configured size limit. Once full, a relayed meta-transaction (`DelegateAction`) submitted to that shard's active validator/chunk producer will hit `NoSpaceLeft`, and if that node is `active_validator` for the shard, `ValidTx` is still returned to the submitter/relayer.

### Impact Explanation
This is a liveness/availability integrity violation: the client-facing RPC boundary reports transaction acceptance (`ValidTx`) when the transaction was not queued and is not being forwarded, with no way for the caller to detect the drop other than manually polling the transaction status and eventually timing out. Scoped impact per the prompt: an off-chain relayer processing meta-transactions (`DelegateAction`) that trusts `ValidTx` as durable-queue confirmation could release counterpart off-chain funds while the actual on-chain action never executes, resulting in funds released against a transaction that will never resolve. This matches a fund-freezing/loss-adjacent liveness bug category (no on-chain state corruption, no consensus divergence — purely an off-chain trust/liveness failure caused by an inaccurate RPC signal).

### Likelihood Explanation
Preconditions: (1) the target shard's chunk-producer transaction pool must be at its size limit, and (2) the RPC node handling the request must be `active_validator` for that shard at that moment. Filling a shard's pool requires submitting enough distinct, validly-signed transactions (from attacker-controlled or attacker-funded accounts) to exceed `total_transaction_size_limit`; this is a real, non-trivial but plausible congestion/spam scenario reachable by an ordinary funded account issuing many transactions, without needing validator or node-operator privileges. It's a probabilistic/timing-dependent bug (depends on pool occupancy at request time) rather than a deterministic, always-triggerable exploit, and requires the attacker or a colluding party to control or predict which meta-transaction lands in the full window. This makes exploitation feasible but requires some transaction volume and timing effort; it is not a one-shot, cost-free attack.

### Recommendation
In the `InsertTransactionResult::NoSpaceLeft` arm of `process_tx_internal`, do not silently fall through to the generic forwarding/active-validator logic. Instead:
- If `!is_forwarded`, explicitly attempt `forward_tx` to other current-epoch chunk producers (not just `possibly_forward_tx_to_next_epoch`) and return `ProcessTxResponse::RequestRouted`, or
- If forwarding also fails/is not applicable, return a distinct response (e.g., a new `ProcessTxResponse::Dropped` or an explicit pool-full error) rather than `ValidTx`, so callers can distinguish "durably accepted" from "rejected due to capacity."
Update the doc comment on `process_tx` to accurately reflect all response semantics once fixed.

### Proof of Concept
Unit test plan (in `chain/client/src/rpc_handler.rs` test module or an integration test using `RpcHandlerActor`):
1. Construct an `RpcHandlerActor` with a `ShardedTransactionPool` configured with a very small `pool_size_limit` (e.g., enough for 1 transaction).
2. Configure the actor's `validator_signer` so `active_validator(shard_id)` returns `true` and `is_chunk_producer_for_transaction` returns `true` for the target shard.
3. Insert one filler transaction directly via `tx_pool.insert_transaction` to saturate the pool for `shard_uid`.
4. Call `RpcHandlerActor::process_tx` (or `process_tx_internal`) with a second valid, signed transaction (e.g., a `DelegateAction`/meta-transaction) targeting the same shard, with `is_forwarded = false`.
5. Assert that:
   - `pool.insert_transaction` returns `InsertTransactionResult::NoSpaceLeft` for the second tx.
   - The response returned by `process_tx` is **not** `ProcessTxResponse::ValidTx` unless the transaction was also verified to have been forwarded (`ForwardTx` network message observed) or otherwise durably handled.
   - Assert the transaction is absent from `tx_pool` after the call, proving it was dropped while `ValidTx` (or any "not rejected") was returned — demonstrating the liveness violation.
