### Title
Missing bounds validation for `limit`/`offset` in `FindCommits` RPC allows unclamped `--max-count`/`--skip` arguments to reach `git log` - ([File: internal/gitaly/service/commit/find_commits.go])

### Summary
`FindCommitsRequest.Limit` and `FindCommitsRequest.Offset` are `int32` fields fully controlled by an RPC caller, but `validateFindCommitsRequest` never checks that they are non-negative before they are formatted directly into `git log` flags.

### Finding Description
`validateFindCommitsRequest` only validates the repository and the revision; it never inspects `req.GetLimit()` or `req.GetOffset()`: [1](#0-0) 

Those unvalidated fields are then interpolated straight into git command-line flags in `getLogCommandSubCmd`: [2](#0-1) 

Note that the `--skip=%d` flag is gated behind `req.GetOffset() > 0`, but the `--max-count=%d` flag is appended unconditionally with whatever raw (possibly negative) `limit` value was supplied — there is no `IsNaturalNumber`/`InRange` style clamp comparable to the one that exists for other numeric config fields (`internal/errors/cfgerror/validate.go`) or the one that the sibling RPC `ListLastCommitsForTree` explicitly performs: [3](#0-2) 

The contrast between `ListLastCommitsForTree` (which rejects `offset < 0` and `limit < 0` with `InvalidArgument`) and `FindCommits` (which performs no such check) indicates a missing clamp analogous to the reported bug class: an argument that is supposed to represent a bounded, non-negative quantity is passed through to a downstream interpreter (here, `git log`) without validating that it is actually in the expected range.

### Impact Explanation
This is reachable by any ordinary authenticated client calling `FindCommits` with a negative `Limit`. Git's `--max-count` option is documented to cap the number of returned commits; supplying a negative count is not part of the API contract and its resulting behavior diverges from Gitaly's intended pagination/limiting semantics, defeating the caller-facing "cap the output" guarantee. Combined with the fact that `FindCommits` is a streaming RPC over `git log`, an unbounded response effectively removes the intended result-count clamp on a git subprocess, which can drive excessive CPU/memory/network usage on the Gitaly node processing the stream (resource-limit bypass / DoS-of-a-handler concern), since the RPC-side numeric clamp — the only defense Gitaly puts between the untrusted field and the git argument — is absent here even though it exists for the analogous field on a neighboring RPC.

### Likelihood Explanation
High: no privilege beyond normal RPC access is required, no crafted repository state is required, and the negative value can be sent in a single, otherwise-valid `FindCommitsRequest`. The bug is a simple omission of an already-established pattern used elsewhere in the same service package (`ListLastCommitsForTree`), so the code path is trivially reachable.

### Recommendation
Add the same clamp used by `ListLastCommitsForTree` to `validateFindCommitsRequest` (and to any other RPC in `internal/gitaly/service/commit` that formats `Offset`/`Limit`/`MaxCount`-style fields directly into git flags), e.g.:
```go
if in.GetOffset() < 0 {
    return fmt.Errorf("offset negative")
}
if in.GetLimit() < 0 {
    return fmt.Errorf("limit negative")
}
```
Consider factoring this into a shared helper (or using the existing `cfgerror.IsNaturalNumber`/`InRange` primitives) so all commit-listing RPCs (`FindCommits`, `CommitsByMessage`, `CountCommits`, `ListCommits`, etc.) validate numeric pagination fields consistently before they are interpolated into git command arguments.

### Proof of Concept
1. As an ordinary authenticated Gitaly client with access to any repository, call:
   ```
   FindCommits(FindCommitsRequest{
       Repository: <valid repo>,
       Limit: -1,
   })
   ```
2. `validateFindCommitsRequest` accepts the request unchanged (no error) because it does not check `Limit`. [1](#0-0) 
3. `getLogCommandSubCmd` builds `git log --format=%H --max-count=-1 <revision>`, i.e., an out-of-contract, un-clamped argument reaches the `git log` subprocess. [2](#0-1) 

I was unable to independently execute `git log --max-count=-1` inside this sandbox to empirically confirm the exact resulting git behavior (e.g., whether it fully disables the cap or is a no-op); this should be verified by the assignee, but the core issue — a caller-controlled numeric field reaching a git argument without the bounds check that a sibling RPC in the same package already performs — is confirmed directly from the code.

func validateFindCommitsRequest(ctx context.Context, locator storage.Locator, in *gitalypb.FindCommitsRequest) error {
	if err := locator.ValidateRepository(ctx, in.GetRepository()); err != nil {
		return err
	}
	if err := git.ValidateRevision(in.GetRevision(), git.AllowEmptyRevision()); err != nil {
		return err
	}
	return nil
}

func validateListLastCommitsForTreeRequest(ctx context.Context, locator storage.Locator, in *gitalypb.ListLastCommitsForTreeRequest) error {
	if err := locator.ValidateRepository(ctx, in.GetRepository()); err != nil {
		return err
	}
	if err := git.ValidateRevision([]byte(in.GetRevision())); err != nil {
		return err
	}
	if in.GetOffset() < 0 {
		return fmt.Errorf("offset negative")
	}
	if in.GetLimit() < 0 {
		return fmt.Errorf("limit negative")
	}
	return nil
}
