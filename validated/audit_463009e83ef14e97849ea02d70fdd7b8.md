### Title
Unbounded DataWord-to-int conversion in TVM precompile signature/address array extraction enables memory-exhaustion DoS - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`PrecompiledContracts.extractBytesArray()` and `extractBytes32Array()` take an array length directly from attacker-supplied call data via `DataWord.intValueSafe()` and use it, unchecked against any sane upper bound, to allocate a Java array (`new byte[len][]`), analogous to the Weaviate type-conversion issue (CWE-704) where an unchecked value conversion led to unbounded resource consumption/DoS.

### Finding Description
`extractBytesArray` and `extractBytes32Array` read the number of elements straight from the calldata-decoded `DataWord`: [1](#0-0) 

`intValueSafe()` only caps the value against `Integer.MAX_VALUE`, it does not enforce any protocol-level maximum: [2](#0-1) 

These helpers are invoked from `ValidateMultiSign.execute()` and `BatchValidateSign.doExecute()`, both of which are TVM precompiled contracts reachable by any account issuing a `TriggerSmartContract` call to their fixed precompile addresses: [3](#0-2) [4](#0-3) 

The bound checks (`sigArraySize > MAX_SIZE`, `addrArraySize > MAX_SIZE`) are only applied when the `allowTvmSelfdestructRestriction` proposal flag is active: [5](#0-4) 

When that flag is not (yet) enabled on a given network (its default off state prior to committee activation, or on any chain that has not adopted the TIP), the code falls through to `extractBytesArray`/legacy path with no length cap, so a caller can embed an array-length field of up to `Integer.MAX_VALUE` in cheap, small calldata while the actual `data.length` used for `getEnergyForData` billing stays tiny — decoupling the requested allocation size from the energy paid for it.

### Impact Explanation
Triggering `new byte[len][]` with `len` near `Integer.MAX_VALUE` attempts to allocate on the order of many gigabytes for the reference array alone. This can throw an `OutOfMemoryError` that occurs outside any narrow `try/catch` in `ValidateMultiSign.execute()` (the `try { ... } catch (Throwable t)` block only wraps the later permission-weight loop, not the array extraction call) and can be triggered repeatedly and cheaply since energy billing is based on actual data length, not the embedded (fake) array length. Repeated invocation can induce heap pressure/GC storms across the node process, degrading or crashing the validator/full node — a resource-exhaustion DoS matching the CWE-704 classification of the referenced advisory.

### Likelihood Explanation
Exploitability is contingent on the `allowTvmSelfdestructRestriction` proposal not being active on the target network. Given that a Devin agent (or any external observer without live chain access) cannot itself verify whether this proposal is currently activated on TRON mainnet, this significantly reduces confidence that the path is live in production today. If already activated, the specific bound bypass reported here is closed; the finding is presented as a defense-in-depth analog worth revalidating against current mainnet proposal state.

### Recommendation
- Enforce the `MAX_SIZE` bound check unconditionally in both `ValidateMultiSign` and `BatchValidateSign`, independent of the `allowTvmSelfdestructRestriction` flag, so the guard is not tied to governance activation.
- Add an explicit sanity cap inside `extractBytesArray`/`extractBytes32Array` themselves (e.g., reject `len` values inconsistent with the actual `data.length`/`words.length`) rather than relying solely on call-site checks.
- Verify current mainnet proposal activation status for `allowTvmSelfdestructRestriction` before treating this as immediately exploitable in production.

### Proof of Concept
1. Craft a `TriggerSmartContract` transaction whose call data targets the `BatchValidateSign` precompile address with minimal actual byte length (to keep `getEnergyForData` cost low) but with the length word at the offset read by `words[2]` (used for `addrArraySize`/array extraction) set to a large value close to `Integer.MAX_VALUE`.
2. Submit on a network where `allowTvmSelfdestructRestriction` has not been activated.
3. Observe the precompile attempting `new byte[len][]`, causing large memory allocation and potential `OutOfMemoryError`/GC pressure on the executing node, repeatable at low TRX cost.
