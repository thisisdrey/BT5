### Title
Read-only enforcement gap in top-level TVM constant calls allows write-capable opcodes to execute when `isConstantCall` is set but `isStaticCall` is not - ([File: actuator/src/main/java/org/tron/core/vm/program/invoke/ProgramInvokeImpl.java])

### Summary
`triggerconstantcontract` (HTTP/gRPC) and `eth_call` (JSON-RPC) are meant to be strictly read-only execution paths: they run the TVM against a throwaway `RepositoryImpl.createRoot` snapshot and never call `rootRepository.commit()` at the top level when `isConstantCall` is true. However, the write-capable resource/opcode guards in `OperationActions.java` (`freezeBalanceV2Action`, `unfreezeBalanceV2Action`, `withdrawExpireUnfreezeAction`, `cancelAllUnfreezeV2Action`, `delegateResourceAction`, `unDelegateResourceAction`, `voteWitnessAction`, `withdrawRewardAction`, `createAction`, `create2Action`, `sStoreAction`, `tStoreAction`, `callAction`) all gate on `program.isStaticCall()`, not on `program.isConstantCall()`.

### Finding Description
The top-level `ProgramInvoke` created for a constant/read-only call (`ProgramInvokeFactory.createProgramInvoke(TrxType, executorType, tx, ...)`, used by `VMActuator.call()`/`create()` at [1](#0-0) ) is built via the `ProgramInvokeImpl` constructor at [2](#0-1) , which never sets `isStaticCall`; it stays at its class-default `false` ( [3](#0-2) ). The caller only invokes `programInvoke.setConstantCall()` afterward ( [4](#0-3) , called from [5](#0-4) ), which sets `isConstantCall = true` but has no effect on `isStaticCall`.

The write-blocking checks throughout `OperationActions.java` consistently test `program.isStaticCall()` only, e.g. `sStoreAction` ( [6](#0-5) ) and the resource-management opcodes (`freezeBalanceV2Action`, `unfreezeBalanceV2Action`, `withdrawExpireUnfreezeAction`, `cancelAllUnfreezeV2Action`, `delegateResourceAction`, `unDelegateResourceAction`, `voteWitnessAction`, `withdrawRewardAction`, `createAction`, `create2Action`) at [7](#0-6) . None of these check `isConstantCall()`, which is the flag actually set for the top-level read-only entry points reachable from `Wallet.callConstantContract` ( [8](#0-7) ), `TriggerConstantContractServlet` ( [9](#0-8) ), `RpcApiService.triggerConstantContract` ( [10](#0-9) ), and `TronJsonRpcImpl.getCall`/`eth_call` (interface at [11](#0-10) ).

This is structurally analogous to CVE-2026-18954: a "read-only mode" is enforced at a coarse control level (VMActuator skips `rootRepository.commit()` when `isConstantCall` is true — see the `execute()` early return at [12](#0-11) ), but the finer-grained opcode/operation guards that should reject write-capable operations check the *wrong* flag (`isStaticCall`) instead of the flag that actually indicates "this is a read-only/constant invocation" (`isConstantCall`).

**Uncertainty / what I could not fully verify:** I was unable to inspect the full bodies of `Program.freezeBalanceV2`, `Program.voteWitness`, `Program.delegateResource`, `Program.withdrawReward`, etc., within the available context window to confirm whether these methods mutate state exclusively through the `Repository`/`deposit` cache-then-commit abstraction (in which case the top-level "no commit for constant calls" behavior in `VMActuator.execute()` would still prevent persistence, making this a defense-in-depth gap rather than an exploitable write) or whether any of them touch chain state through a path that bypasses that commit gate (e.g., direct votes/rewards bookkeeping structures that are committed differently than account/storage state, or nested internal calls where a deeper `Program.callToAddress` does call `deposit.commit()` per internal call as seen at [13](#0-12)  and [14](#0-13) , independent of whether the top-level call ultimately commits). Because internal/nested calls commit their `deposit` immediately upon success regardless of the top-level `isConstantCall` flag, and because the guard that should prevent these state-changing opcodes from running at all (`isStaticCall`) is never set to `true` for a top-level constant call, there is a plausible path where internal-call-level commits of freeze/vote/delegate/reward operations persist into the shared `RepositoryImpl` cache layers before the top-level discard decision is reached — but confirming whether this cache ultimately reaches the persistent store for `triggerconstantcontract`/`eth_call` invocations (as opposed to being purely thread-local and discarded) requires reading `RepositoryImpl.commit()` and `RepositoryImpl.createRoot()`, which I did not have available context for.

### Impact Explanation
If confirmed, an unprivileged caller could invoke `triggerconstantcontract` / `eth_call` against a contract whose selector is marked read-only in the ABI (or against a contract that calls one of the resource-management TVM opcodes internally) and have TRON-native state-changing operations (freeze/unfreeze/vote/delegate resource, withdraw rewards, or contract creation) execute and possibly persist, despite the API being documented and expected to be side-effect-free. This would constitute unauthorized state mutation (theft/misallocation of frozen balances, votes, or rewards) triggered via a query-only API — a Medium/High severity issue matching the CVE-2026-18954 bug class (authorization/read-only enforcement bypass).

### Likelihood Explanation
Medium. The gap in the guard logic (checking `isStaticCall` instead of `isConstantCall`) is real and directly observable in the code, and `triggerconstantcontract`/`eth_call` are reachable by any anonymous API client without special permissions. However, whether this results in an actually *persisted* state change (vs. changes that are always discarded because the top-level repository is never committed) depends on `RepositoryImpl` semantics I could not fully verify in this pass.

### Recommendation
Audit every `OperationActions` guard that currently checks `program.isStaticCall()` for write-prevention purposes and also check `program.isConstantCall()` (i.e., `if (program.isStaticCall() || program.isConstantCall())`), and/or explicitly set `isStaticCall = true` whenever a top-level `ProgramInvoke` is created for a constant call (alongside `setConstantCall()`) in `ProgramInvokeFactory`/`VMActuator`. Additionally, audit `RepositoryImpl.commit()`/nested-call commit paths to confirm no persistent-store writes can occur for any invocation where `isConstantCall` is true, independent of call depth.

### Proof of Concept
Not fully constructible without confirming the `RepositoryImpl` commit semantics for nested calls under `isConstantCall=true`; the concrete PoC would be: deploy a contract with a `view`/`constant`-tagged function (per ABI) whose bytecode internally issues opcodes corresponding to `voteWitnessAction`/`freezeBalanceV2Action`/etc., then call it via `triggerconstantcontract` or `eth_call` and observe whether the account's frozen balance/votes/rewards change after the call, despite the API being labeled read-only.

  public Transaction callConstantContract(TransactionCapsule trxCap,
      Builder builder, Return.Builder retBuilder, boolean isEstimating)
      throws ContractValidateException, ContractExeException, HeaderNotFound, VMIllegalException {

    if (!Args.getInstance().isSupportConstant()) {
      throw new ContractValidateException("this node does not support constant");
    }

    Block headBlock;
    List<BlockCapsule> blockCapsuleList = chainBaseManager.getBlockStore()
        .getBlockByLatestNum(1);
    if (CollectionUtils.isEmpty(blockCapsuleList)) {
      throw new HeaderNotFound("latest block not found");
    } else {
      headBlock = blockCapsuleList.get(0).getInstance();
    }

    BlockCapsule headBlockCapsule = new BlockCapsule(headBlock);
    TransactionContext context = new TransactionContext(headBlockCapsule, trxCap,
        StoreFactory.getInstance(), true, false);
    VMActuator vmActuator = new VMActuator(true);

    try {
      vmActuator.validate(context);
      vmActuator.execute(context);
    } finally {
      // constant call runs on a pooled RPC worker; drop its thread-local VM config view so it
      // can never leak into a later (block/broadcast) execution on the same thread.
      VMConfig.clearLocalSnapshot();
    }
