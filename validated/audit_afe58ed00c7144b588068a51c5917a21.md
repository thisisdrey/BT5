### Title
Dust debt positions can be opened below the liquidation floor and become economically or permanently unliquidatable - (File: `contracts/DebtToken.sol`)

### Summary
`DebtToken.issue()` enforces collateral sufficiency but never checks the resulting debt against `Pool.debtFloorInUsd`, while `Pool.initialize()` leaves that floor at zero and sets `maxLiquidable` to 50%. [1](#0-0) [2](#0-1) 

Consequently, an unprivileged borrower can create many minimal positions whose liquidation incentive is too small to compensate for gas, or, when a nonzero floor is configured, whose debt is already below the floor and cannot be liquidated at all under the 50% close-factor cap. [3](#0-2) [4](#0-3) 

### Finding Description
`DepositToken.deposit()` lets any user deposit accepted collateral, and `DebtToken.issue()` then mints any nonzero synthetic amount that remains within the user's issuable limit. [5](#0-4) [6](#0-5) 

The only liquidity checks in `issue()` are `amount_ != 0` and `amount_ <= quoteUsdToToken(_issuableInUsd)`; neither the new debt value nor the post-issue debt value is compared with `pool.debtFloorInUsd()`. [7](#0-6) [8](#0-7) 

During liquidation, `Pool.liquidate()` first restricts repayment to `maxLiquidable`, which defaults to 50%, and then rejects any partial repayment that leaves nonzero debt below `debtFloorInUsd`. [9](#0-8) 

This creates a contradictory state for a debt `D < debtFloorInUsd`: repaying all `D` exceeds the 50% limit, while repaying at most `0.5 * D` leaves `0.5 * D < debtFloorInUsd`; therefore every liquidation call reverts. [3](#0-2) 

Even when `debtFloorInUsd == 0`, the liquidation reward is only the oracle value of the repayment multiplied by the configured liquidator incentive, so positions can be deliberately sized below gas cost while the protocol has no minimum-opening-size defense. [10](#0-9) [11](#0-10) 

### Impact Explanation
The affected invariant is liquidation liveness and protocol solvency: an underwater borrower can retain minted synthetic assets while rational liquidators cannot profitably remove the position. [12](#0-11) 

With a nonzero floor, the impact is deterministic: every attempt either violates `AmountGreaterThanMaxLiquidable` or `RemainingDebtIsLowerThanTheFloor`, permanently freezing the collateral and leaving bad debt in the pool. [3](#0-2) 

With the default zero floor, the attack is economic rather than absolute; an attacker can batch-create dust positions whose maximum profitable seizure is smaller than transaction cost, causing debt to persist and eventually become bad debt through interest accrual or collateral depreciation. [2](#0-1) [10](#0-9) 

### Likelihood Explanation
The entry path is fully public: approve an accepted underlying, call `DepositToken.deposit(amount, attacker)`, then call `DebtToken.issue(dustAmount, attacker)`. [5](#0-4) [6](#0-5) 

No privileged role, oracle corruption, governance action, flash loan, or malicious contract is required; the attacker only needs the position to become unhealthy through ordinary interest accrual or market movement. [13](#0-12) [14](#0-13) 

Likelihood depends on deployed `debtFloorInUsd`, `maxLiquidable`, liquidation incentive, chain gas cost, and minimum token denominations; those storage values are not fully recoverable from deployment ABI artifacts alone, but the default code initializes `debtFloorInUsd` to zero and `maxLiquidable` to 50%. [2](#0-1) [15](#0-14) 

### Recommendation
Enforce the debt floor at position creation and increase, not only after liquidation. [16](#0-15) [17](#0-16) 

In `DebtToken.issue()` and `DebtToken.mint()`, calculate the resulting synthetic-token debt in USD and require it to be either zero or at least `pool.debtFloorInUsd()`. [18](#0-17) [19](#0-18) 

Additionally, add an emergency liquidation branch that permits full repayment when the whole debt is already below the floor, because the current max-liquidable check otherwise makes such positions impossible to close under a sub-100% cap. [3](#0-2) 

### Proof of Concept
A Foundry fork test can demonstrate the contradiction without privileged calls once the pool's deployed addresses and existing storage configuration are supplied by fork context:

```solidity
function testDustDebtCannotBeLiquidated() public {
    IERC20 underlying = depositToken.underlying();
    deal(address(underlying), attacker, dustCollateral);
    vm.startPrank(attacker);
    underlying.approve(address(depositToken), dustCollateral);
    depositToken.deposit(dustCollateral, attacker);

    uint256 issuableUsd = pool.debtPositionOf(attacker).issuableInUsd;
    uint256 dustDebt = masterOracle.quoteUsdToToken(
        address(syntheticToken),
        dustUsd // Below pool.debtFloorInUsd(), but nonzero
    );
    debtToken.issue(dustDebt, attacker);
    vm.stopPrank();

    // Let accrued interest make the initially healthy dust position unhealthy.
    vm.warp(block.timestamp + 365 days);
    debtToken.accrueInterest();

    uint256 debt = debtToken.balanceOf(attacker);
    uint256 floor = pool.debtFloorInUsd();
    uint256 debtUsd = masterOracle.quoteTokenToUsd(address(syntheticToken), debt);

    require(debtUsd > 0 && debtUsd < floor, "position is not dust");
    assertFalse(pool.debtPositionOf(attacker).isHealthy);

    // Full repayment is bounded by maxLiquidable.
    vm.expectRevert(Pool.AmountGreaterThanMaxLiquidable.selector);
    pool.liquidate(syntheticToken, attacker, debt, depositToken);

    // The largest allowed partial repayment leaves debt below the floor.
    uint256 maxRepay = debt.wadMul(pool.maxLiquidable());
    vm.expectRevert(Pool.RemainingDebtIsLowerThanTheFloor.selector);
    pool.liquidate(syntheticToken, attacker, maxRepay, depositToken);
}
```

The first revert follows from `amountToRepay_ / debt > maxLiquidable`, while the second follows because the remaining `debt - maxRepay` is nonzero and still below `debtFloorInUsd`. [3](#0-2)
