### Title
Unprivileged dust-transfer fills victim's `MAX_TOKENS_PER_USER` slot list, blocking all new deposits and borrows — ([File: contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
Analogous to CVE-2025-51741 (an unauthenticated endpoint pushing resource-consuming messages to arbitrary users), any EOA can push entries into an arbitrary victim's per-account token list in `Pool` by transferring dust amounts of `DepositToken`s. Because `Pool` enforces a hard cap of `MAX_TOKENS_PER_USER = 30` on the combined `debtTokensOfAccount + depositTokensOfAccount` list, filling a victim's list makes every subsequent first-time deposit, borrow, or deposit-token receipt revert with `UserReachedMaxTokens`, griefing the victim out of opening new positions.

### Finding Description
`DepositToken._transfer` unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's prior balance is zero. The recipient never consented to receiving the token and cannot prevent the list insertion.

- `DepositToken._transfer` adds the recipient on first receipt: [1](#0-0) 
- `Pool.addToDepositTokensOfAccount` enforces the cap via `onlyIfAdditionWillNotReachMaxTokens`: [2](#0-1) 
- The same applies on mint (deposit), so `deposit(amount_, onBehalfOf_)` can also be used to push entries to `onBehalfOf_`: [3](#0-2) 
- Once the victim's combined list length is `>= 30`, any new deposit token mint or `DebtToken` issuance reverts: [4](#0-3) 

Attack flow: attacker deposits a dust amount (1 wei of underlying) into each of the pool's deposit tokens for themselves, then calls `depositToken.transfer(victim, 1)` for each token. Each transfer pushes the token into `depositTokensOfAccount[victim]`. `transfer` only checks the sender's unlocked balance via `_revertIfLocked(_msgSender, amount_)`, so an attacker with no debt is unrestricted: [5](#0-4) . Since `addDepositToken` allows up to `MAX_TOKENS_PER_USER` deposit tokens (`if (depositTokens.length() >= MAX_TOKENS_PER_USER) revert ReachedMaxDepositTokens()` at `Pool.sol:703`), a fully-configured pool lets the attacker saturate the victim's entire list alone.

### Impact Explanation
Liveness / position-management griefing: once the list is full, the victim cannot deposit into any collateral they haven't already used, cannot take on any new debt token (`addToDebtTokensOfAccount` shares the same cap), and cannot receive any new deposit token via transfer or `deposit(onBehalfOf)` — all revert `UserReachedMaxTokens`. Existing balances remain withdrawable, and the victim can eject attacker-pushed dust entries by transferring them away (balance→0 triggers `removeFromDepositTokensOfAccount`), so this is a temporary blocking of new positions plus forced gas expenditure to clean the list, not permanent fund freezing. Severity is therefore moderate: denial of new-position functionality for arbitrary users at dust cost.

### Likelihood Explanation
Fully permissionless: requires only a funded EOA depositing dust and calling `transfer` repeatedly. No privileged role, oracle manipulation, or flash loan needed. Effectiveness scales with the number of registered deposit tokens; on deployments with many collaterals a single attacker fills the whole cap.

### Recommendation
Do not add tokens to a recipient's list on unsolicited `transfer`/`seize` receipts — only register on explicit `deposit`/`mint` actions the account initiates — or store a per-account "registered collateral" set opt-in flag. Alternatively, exempt the cap check for inbound transfers and only enforce it when the account itself opens a position, so spammed dust cannot block the victim.

### Proof of Concept
Hardhat sketch (deployed pool with ≥2 deposit tokens `msdA`, `msdB`; victim has zero positions):

```ts
// attacker deposits dust so it holds transferable msdTokens
await underlyingA.approve(msdA.address, 1);
await msdA.deposit(1, attacker.address);
await underlyingB.approve(msdB.address, 1);
await msdB.deposit(1, attacker.address);

// spam-push into victim's list (repeat for all registered deposit tokens)
await msdA.connect(attacker).transfer(victim.address, 1);
await msdB.connect(attacker).transfer(victim.address, 1);

// list grows without victim consent
expect(await pool.getDepositTokensOfAccount(victim.address)).to.have.lengthOf(2);

// after 30 spam entries, victim's own first deposit of a new token reverts
await expect(
  msdC.connect(victim).deposit(parseUnits('1000', 18), victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

Reproduce on a fork with `MAX_TOKENS_PER_USER` distinct deposit tokens; each `transfer(victim, 1)` consumes one list slot.
