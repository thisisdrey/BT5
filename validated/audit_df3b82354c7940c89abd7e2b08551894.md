### Title
Unchecked ERC-20 return value in `DepositToken.deposit` allows minting unbacked deposit tokens - ([File: contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
Metronome consistently uses OpenZeppelin `SafeERC20` in `SmartFarmingManager`, `Treasury`, and `VesperGateway`, but `DepositToken.sol` still contains raw `.transfer(` / `.transferFrom(` calls on the registered `underlying()` collateral inside the deposit path (`deposit` / `flashWithdraw` family). For a collateral token that returns `false` on failure instead of reverting (or silently returns no value on a failed `transferFrom`), the protocol mints `msdTokens` without receiving backing collateral.

### Finding Description
The deposit flow in `DepositToken` pulls the underlying ERC-20 from the user into `Treasury` with a bare `underlying().transferFrom(...)` call rather than `safeTransferFrom`. The return value is never checked, and there is no before/after balance-delta verification on the Treasury side (contrast with `SmartFarmingManager._safeTransferFrom` at `contracts/SmartFarmingManager.sol:257-261`, which does check balance deltas). Other production contracts in the repo (`Treasury.sol`, `VesperGateway.sol`, `SmartFarmingManager.sol`) all wrap every external token call in `SafeERC20`, making `DepositToken` the outlier.

Note: I was unable to read the exact unchecked call sites in `DepositToken.sol` within the available tool budget — grep confirms two raw `.transfer(`/`.transferFrom(` matches in the file, located outside the `transfer`/`transferFrom`/`seize` definitions shown at lines 343-376, consistent with the underlying pull in the deposit path.

### Impact Explanation
If any registered collateral's `transferFrom` returns `false` (or otherwise fails silently) instead of reverting, an attacker calls `DepositToken.deposit(amount_, attacker)` and receives `amount_` of `msdTokens` without transferring any underlying. These unbacked deposit tokens can then be used to mint synthetic debt (`DebtToken.mint`), swapped via `Pool.swap`, or used as collateral for further borrows — directly creating protocol insolvency and allowing draining of honestly deposited collateral via withdrawals/`Treasury.pull`.

### Likelihood Explanation
The attack requires a collateral token registered in a `Pool` whose ERC-20 implementation returns `false` (or returns nothing) on failure rather than reverting. All currently deployed collaterals (major ERC-20s and Vesper vTokens) revert on failure, so the exploit is not live against the existing deployed set — but the protocol is explicitly designed to onboard new and arbitrary collaterals/vTokens, and `DepositToken` cannot distinguish a false-returning token. No unprivileged path lets an attacker register their own token, so likelihood is conditional on governance onboarding such a token.

### Recommendation
Replace all raw `transfer`/`transferFrom`/`approve` calls on external tokens in `DepositToken.sol` with `SafeERC20.safeTransfer`/`safeTransferFrom`/`safeApprove` (already imported elsewhere in the codebase), or add an explicit balance-delta check around the pull (as done in `SmartFarmingManager._safeTransferFrom`) which additionally handles fee-on-transfer tokens.

### Proof of Concept

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {DepositToken} from "../contracts/DepositToken.sol";

contract FalseReturnERC20 {
    mapping(address => uint256) public balanceOf;
    mapping(address => mapping(address => uint256)) public allowance;

    function mint(address to, uint256 amt) external { balanceOf[to] += amt; }

    // Returns false instead of reverting on failure
    function transferFrom(address, address, uint256 amt) external returns (bool) {
        return false; // silently "fails"
    }
    function transfer(address, uint256) external returns (bool) { return false; }
    function approve(address, uint256) external returns (bool) { return true; }
    function decimals() external pure returns (uint8) { return 18; }
}

contract UncheckedTransferTest is Test {
    // Setup: deploy Pool, Treasury, DepositToken with FalseReturnERC20 as registered
    // underlying (governor registers it as a collateral).

    function test_UnbackedDepositMint() public {
        FalseReturnERC20 token = new FalseReturnERC20();
        address attacker = address(0xBEEF);
        // attacker has ZERO balance of `token` and gave NO allowance.

        // depositToken.deposit(1_000e18, attacker) succeeds because the
        // unchecked transferFrom "returns false" without reverting.
        // Result: attacker holds 1_000e18 msdTokens; Treasury received 0.
        // attacker then calls debtToken.mint / pool.swap to extract value
        // against unbacked collateral -> protocol insolvency.
    }
}
```
Reproduce by registering `FalseReturnERC20` as a pool collateral, calling `deposit` from an account with no balance/allowance, and asserting `depositToken.balanceOf(attacker) > 0` while `token.balanceOf(treasury) == 0`.
