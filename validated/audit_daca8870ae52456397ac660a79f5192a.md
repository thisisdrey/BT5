### Title
`ExchangeInjectContract` lacks a slippage/minimum-output parameter, exposing exchange liquidity providers to front-run price manipulation - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java])

### Summary
`ExchangeInjectContract`, unlike `ExchangeTransactionContract`, has no `expected`/minimum bound field. `ExchangeInjectActuator` computes the paired-token amount to be pulled from the caller's balance purely from the exchange's *current* on-chain reserve ratio at execution time, with no way for the caller to bound the acceptable ratio.

### Finding Description
`ExchangeTransactionContract` (a swap) includes an `expected` field that is enforced in `ExchangeTransactionActuator.doValidate()`: [1](#0-0) . This is the equivalent of a `minAmountOut` slippage guard.

By contrast, `ExchangeInjectContract` only carries `exchange_id`, `token_id`, and `quant` — no expected/min/max bound: [2](#0-1) . `ExchangeInjectActuator.doValidate()` computes `anotherTokenQuant` strictly from the live `firstTokenBalance`/`secondTokenBalance` ratio at validation time and only checks that the derived amount is positive, within `ExchangeBalanceLimit`, and that the caller can afford it: [3](#0-2) . `execute()` recomputes the same ratio-based amount and unconditionally debits it from the caller: [4](#0-3) .

Because the ratio can be moved between transaction broadcast and block inclusion — e.g., by another `ExchangeTransactionContract` (swap) against the same exchange pool, which any unprivileged account can submit — the amount of the paired token actually debited from the injector can be significantly different from what was expected when the transaction was signed. This is the exact bug class described in the reference report (mint with no slippage bound), mapped onto java-tron's bonding-curve exchange pool liquidity-injection path.

Note: `ExchangeInjectActuator` restricts the caller to the exchange's `creator` address (`accountCapsule.getAddress().equals(exchangeCapsule.getCreatorAddress())`, line 175), but any unprivileged account can become a creator by first calling `ExchangeCreateContract`, so this is still reachable by an ordinary, unprivileged transaction broadcaster.

### Impact Explanation
An exchange creator injecting liquidity can be front-run by any third party's swap transaction against the same pool, causing the creator's inject transaction to pull a larger-than-expected amount of the paired asset (or credit a smaller-than-expected value at the new ratio) from their balance, resulting in direct, unbacked financial loss for that account with no way to bound the loss on-chain. This matches "unauthorized loss of funds" for the affected account.

### Likelihood Explanation
The attack requires only ordinary transaction broadcast capability (submit a swap via `ExchangeTransactionContract` before the target's `ExchangeInjectContract` is packed into a block) and normal transaction ordering/mempool visibility, which any user can attempt. Given TRON's public mempool and block-production timing, this is straightforward to execute against any actively-traded exchange pair.

### Recommendation
Add a bound parameter to `ExchangeInjectContract` (analogous to `expected` on `ExchangeTransactionContract`), e.g. `min_another_token_quant` / `max_another_token_quant`, and enforce it in `ExchangeInjectActuator.doValidate()`/`execute()` before debiting the caller, rejecting the transaction if the computed `anotherTokenQuant` falls outside the caller-specified bound.

### Proof of Concept
1. Attacker observes a pending `ExchangeInjectContract` transaction from exchange creator `A` referencing `exchangeId=X`, injecting `quant` of `firstTokenID`.
2. Attacker broadcasts and gets mined first an `ExchangeTransactionContract` swap against exchange `X` that shifts `firstTokenBalance`/`secondTokenBalance` significantly (e.g., dumps `secondTokenID` into the pool, or extracts most of `firstTokenID`).
3. `A`'s `ExchangeInjectContract` is processed afterward; `ExchangeInjectActuator` recomputes `anotherTokenQuant = secondTokenBalance * tokenQuant / firstTokenBalance` (or the inverse) using the now-manipulated reserves per lines 217-227 of `ExchangeInjectActuator.java`, forcing `A` to pay a materially different — and uncapped — amount of the paired token than intended when the transaction was signed.
