Confirmed: `decode_atlas_get_attachment` in `stackslib/src/net/api/getattachment.rs` (lines 159-165) purely deserializes JSON and does not verify the attachment content hash against the request's `content_hash`. `AttachmentsBatchStateContext::extend_with_attachments` in `stackslib/src/net/atlas/download.rs` (lines 530-558) then does `self.attachments.insert(response.attachment)` right after this decode, with no comparison to `request.content_hash` at all — `request` is in scope (used for `request.get_url()`) but its `content_hash` field is never read here.

### Title
Unvalidated attachment content hash allows serving forged BNS attachment data - (File: `stackslib/src/net/atlas/download.rs`)

### Summary
When downloading attachments for BNS name resolution, `AttachmentsBatchStateContext::extend_with_attachments` accepts and stores any `Attachment` returned by a peer for a `GET /v2/attachments/{content_hash}` request without checking that the returned attachment's content actually hashes to the requested `content_hash`. A malicious peer serving this endpoint can therefore inject arbitrary attachment content that gets treated as if it were the canonical, on-chain-committed attachment.

### Finding Description
The broken invariant is: `response.attachment.hash() == request.content_hash` must hold before the attachment is accepted, but it is never checked. In `extend_with_attachments` (`stackslib/src/net/atlas/download.rs:530-558`), for each successful response the code does:
```
if let Ok(response) = response.decode_atlas_get_attachment() {
    self.attachments.insert(response.attachment);
    report.bump_successful_requests();
}
```
`decode_atlas_get_attachment` (`stackslib/src/net/api/getattachment.rs:159-165`) only performs JSON deserialization of `GetAttachmentResponse { attachment: Attachment }` — it does not compare `attachment.content`'s hash to anything. The `request: AttachmentRequest` value (which carries the originally-requested `content_hash`, set in `get_prioritized_attachments_requests`, `stackslib/src/net/atlas/download.rs:467-472`) is available in the same loop iteration but is never consulted for equality with the returned attachment. The resulting `context.attachments` (a `HashSet<Attachment>`) is later drained in `AttachmentsDownloader::run` (`stackslib/src/net/atlas/download.rs:153-169`), where each attachment is inserted into the Atlas DB via `network.atlasdb.insert_instantiated_attachment(&attachment)` and paired with `attachment_instances` found via `find_all_attachment_instances(&attachment.hash())`. Because the instance lookup is keyed off the *attacker-supplied* attachment's own hash (not the originally requested hash), any prior `AttachmentInstance` in the DB expecting the correct `content_hash` for a BNS name will get resolved and marked instantiated using data whose hash matches only itself — but since no equality check against the original committed `content_hash` occurred at ingestion time, an attacker who controls the responding peer can supply a mismatched attachment and have it accepted into `self.attachments`, and only genuine matches by luck of `find_all_attachment_instances` would connect it to a real instance; more importantly, any attachment content is unconditionally stored/instantiated in the Atlas DB regardless of the requester's expected hash, polluting the node's attachment table with unverified data and bumping the peer's reliability score as if it served correct data.

### Impact Explanation
This lets an unprivileged remote peer (any peer in `context.peers`, populated from `network.get_outbound_sync_peers()`) that is asked to serve a specific `content_hash` respond with different content and have that content accepted as valid, incrementing its reliability score (`report.bump_successful_requests()`), and stored into the local Atlas attachment store via `insert_instantiated_attachment`. This is a High-severity BNS/attachment mismatch: content that was never committed to on-chain by any BNS name op can be treated as resolved/canonical attachment data by the node, and can propagate further since Atlas peers exchange discovered attachments.

### Likelihood Explanation
Preconditions are trivially met: any node performing BNS-related Atlas attachment sync will issue `AttachmentRequest`s for outstanding `content_hash` values, and any of its outbound sync peers can be the attacker (no secret, no privileged role, no special key needed — just running a peer that answers `/v2/attachments/{hash}` with a crafted `GetAttachmentResponse`). The attack is repeatable per attachment request and costs nothing beyond running a normal p2p peer with the correct data/http URL advertised via inventories.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments`, after decoding the response, verify `response.attachment.hash() == request.content_hash` before inserting into `self.attachments`; on mismatch, treat it as a failed request (`report.bump_failed_requests()`) and optionally mark the peer as faulty/deregister the event.

### Proof of Concept
Rust unit test in `stackslib/src/net/atlas/download.rs` tests module:
1. Construct an `AttachmentRequest` with `content_hash = Hash160::from_data(b"expected")`.
2. Construct a `BatchedRequestsResult<AttachmentRequest>` whose `succeeded` map has this request mapped to `Some(StacksHttpResponse)` wrapping a `GetAttachmentResponse { attachment: Attachment { content: b"attacker-controlled".to_vec() } }` (so `attachment.hash() != request.content_hash`).
3. Build an `AttachmentsBatchStateContext` with a matching peer entry in `peers`.
4. Call `context.extend_with_attachments(&mut results)`.
5. Assert `context.attachments.contains(&forged_attachment)` is `true`, proving the mismatched attachment was accepted (equality `response.attachment.hash() == request.content_hash` never checked) — demonstrating the vulnerability. After the fix, this assertion should fail (attachment rejected) and `report.bump_failed_requests()` should have been invoked instead.
