### Title
Unauthenticated attachment content injection via `POSTtransaction` bypasses on-chain `content_hash` binding, enabling eviction of legitimately-inboxed attachments - ([File: stackslib/src/net/atlas/db.rs])

### Summary
`AtlasDB::insert_uninstantiated_attachment` (db.rs:511-536) admits any `Attachment` whose only gate is `should_keep_attachment` (db.rs:249-266), which checks solely that the target contract is a watched Atlas contract and that the content size is within `attachments_max_size` — it never checks that the attachment's hash matches any `content_hash` referenced by a currently-queued/unresolved `AttachmentInstance`. This is reachable from the unauthenticated `POST /v2/transactions` RPC handler, which stores the caller-supplied attachment blob whenever the posted transaction is a `ContractCall` into a watched contract (e.g. `bns`), regardless of whether that call will ever actually emit a matching attachment event on-chain.

### Finding Description
The claimed equality — "every stored `attachments.hash` corresponds to a `content_hash` referenced by a confirmed/queued `AttachmentInstance`" — is not enforced at insert time:

- `posttransaction.rs:230-251` calls `network.get_atlasdb().should_keep_attachment(&contract_id, attachment)` and, if true, `network.get_atlasdb_mut().insert_uninstantiated_attachment(attachment)` [1](#0-0) .
- `should_keep_attachment` only checks `atlas_config.contracts.contains(contract_id)` and `attachment.content.len() <= attachments_max_size` [2](#0-1) . It never queries `attachment_instances` for a matching `content_hash`.
- `insert_uninstantiated_attachment` then unconditionally does `INSERT OR REPLACE INTO attachments (hash, content, was_instantiated=0, ...)` keyed only on `attachment.hash()`, computed from attacker-chosen bytes [3](#0-2) .
- Before inserting, it evicts the oldest uninstantiated rows once `count_uninstantiated_attachments() >= max_uninstantiated_attachments`, via `evict_k_oldest_uninstantiated_attachments`, which deletes purely by `created_at ASC` with no relation to which `attachment_instances.content_hash` rows are still outstanding [4](#0-3) .

Exploit flow: an attacker submits repeated `POST /v2/transactions` requests, each carrying a syntactically valid signed `ContractCall` transaction targeting a watched contract (e.g. `bns`) plus an `attachment` field containing arbitrary bytes whose hash has no relation to any real name-registration/update the attacker is performing. Each such POST that is accepted into the local mempool (mempool admission only requires a well-formed, correctly signed, nonce/fee-plausible transaction — it does not require the contract call to ever succeed or be mined) triggers `insert_uninstantiated_attachment` with attacker-chosen content. Repeating this up to and beyond `max_uninstantiated_attachments` forces `evict_k_oldest_uninstantiated_attachments` to delete the oldest rows in the `attachments` table — which may include attachments that a legitimate, already-broadcast name operation inboxed and that are awaiting pairing by `check_queued_attachment_instances`/`find_uninstantiated_attachment` (download.rs:255-262, db.rs:594-604).

Existing guards that fail to stop this: mempool admission (signature/nonce/fee checks) filters malformed transactions but not the *semantic* relationship between the attachment payload and any actual on-chain attachment commitment; `should_keep_attachment` filters by contract and size only.

### Impact Explanation
The attacker cannot corrupt already-`was_instantiated=1` (validated) attachments — `insert_instantiated_attachment`/`find_attachment` are separate and only written to by the downloader after hash verification against a real `AttachmentInstance`. The actual harm is storage churn in the *uninstantiated* pool: a legitimately received attachment sitting in `attachments` (was_instantiated=0) waiting to be matched against a `queued`/`Checked` `AttachmentInstance` can be evicted early by attacker-injected garbage, forcing the node to fall back to network re-download of that attachment via `AttachmentsBatchStateMachine`/`priority_queue` rather than serving it immediately. This is a resource-churn/availability degradation on the Atlas subsystem, repeatable per accepted mempool transaction, remotely triggerable via the standard unauthenticated RPC endpoint, with no privileged access needed.

### Likelihood Explanation
- Preconditions: node must have Atlas enabled with the `bns` (or another watched) contract, and the RPC port for `POST /v2/transactions` reachable (default/normal deployment).
- Attacker needs only a syntactically valid, correctly signed `ContractCall` transaction (any account, any nonce/fee that satisfies mempool admission) — no admin role, no node secret, no privileged StackerDB slot.
- Cost per attempt is bounded by producing a valid signed transaction; transactions need not be mined to trigger the insert, since the insert happens synchronously inside the RPC handler upon successful `mempool.submit`, independent of block inclusion.
- Fully repeatable at attacker's chosen rate, bounded only by `max_uninstantiated_attachments` config (config-bounded eviction), matching the question's proof idea.

### Recommendation
At insert time in `insert_uninstantiated_attachment` (or in `should_keep_attachment`), require that `attachment.hash()` matches an existing `attachment_instances.content_hash` row that is `is_available = 0` (queued/unresolved) before accepting the attachment into the uninstantiated pool. Reject/drop attachments posted via `POST /v2/transactions` that do not correspond to any outstanding `AttachmentInstance`, so unrelated attacker-chosen content cannot occupy eviction-bounded storage.

### Proof of Concept
Rust test plan (stackslib/src/net/atlas/tests.rs style):
1. Construct an `AtlasDB` with `max_uninstantiated_attachments = N`.
2. Call `atlas_db.queue_attachment_instance(&legit_instance)` with a known `content_hash`, then `atlas_db.insert_uninstantiated_attachment(&legit_attachment)` where `legit_attachment.hash() == legit_instance.content_hash` — simulating the legitimately-needed inbox entry.
3. Loop N times calling `atlas_db.insert_uninstantiated_attachment(&garbage_attachment_i)` where each `garbage_attachment_i.hash()` is unrelated to any row in `attachment_instances` (simulating the attacker's `POST /v2/transactions` payloads).
4. Assert `atlas_db.find_uninstantiated_attachment(&legit_instance.content_hash)` returns `Ok(None)` — i.e., the legitimate attachment was evicted by `evict_k_oldest_uninstantiated_attachments` (db.rs:538-547) before `check_queued_attachment_instances` (download.rs:295-311) could consume it, confirming storage churn from content never tied to any on-chain `attachment_instances.content_hash`.

    pub fn should_keep_attachment(
        &self,
        contract_id: &QualifiedContractIdentifier,
        attachment: &Attachment,
    ) -> bool {
        if !self.atlas_config.contracts.contains(contract_id) {
            info!(
                "Atlas: will discard posted attachment - {} not in supported contracts",
                contract_id
            );
            return false;
        }
        if attachment.content.len() as u32 > self.atlas_config.attachments_max_size {
            info!("Atlas: will discard posted attachment - attachment too large");
            return false;
        }
        true
    }

    pub fn insert_uninstantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        // Insert the new attachment
        let uninstantiated_attachments = self.count_uninstantiated_attachments()?;
        if uninstantiated_attachments >= self.atlas_config.max_uninstantiated_attachments {
            let to_delete =
                1 + uninstantiated_attachments - self.atlas_config.max_uninstantiated_attachments;
            self.evict_k_oldest_uninstantiated_attachments(to_delete)?;
        }

        let tx = self.tx_begin()?;
        let now = util::get_epoch_time_secs() as i64;
        let res = tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 0, ?)",
            params![
                attachment.hash(),
                attachment.content,
                now,
            ],
        );
        res.map_err(db_error::SqliteError)?;
        tx.commit().map_err(db_error::SqliteError)?;
        Ok(())
    }

    pub fn evict_k_oldest_uninstantiated_attachments(&mut self, k: u32) -> Result<(), db_error> {
        let tx = self.tx_begin()?;
        let res = tx.execute(
            "DELETE FROM attachments WHERE hash IN (SELECT hash FROM attachments WHERE was_instantiated = 0 ORDER BY created_at ASC LIMIT ?)",
            params![k],
        );
        res.map_err(db_error::SqliteError)?;
        tx.commit().map_err(db_error::SqliteError)?;
        Ok(())
    }
