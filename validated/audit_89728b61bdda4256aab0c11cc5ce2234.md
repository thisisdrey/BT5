Audit Report

## Title
Value sent to stateless builtin pre-compile addresses is permanently locked with no withdrawal path - (File: `substrate/frame/revive/src/precompiles.rs`, `substrate/frame/revive/src/vm/pvm.rs`)

## Summary
`pallet-revive`'s value-forwarding logic in `Runtime::call` unconditionally forwards non-zero `value` to any callee, including builtin stateless pre-compiles (`HAS_CONTRACT_INFO = false`, e.g. `ECRecover`, `Sha256`, `Ripemd160`, `Identity`, `Modexp`, `Bn128*`, `Blake2F` at addresses `0x01`–`0x09`), without checking whether the target has any mechanism to spend or return that balance. Since these fixed addresses have no private key and their `call` implementations are pure functions that never touch balance, any value sent there becomes permanently stranded.

## Finding Description
`Precompile::HAS_CONTRACT_INFO` is documented explicitly: when `false`, "No account or any other state will be created for the address" and only `call` (not `call_with_info`) is invoked [1](#0-0) . All fixed Ethereum-compatible pre-compiles set `HAS_CONTRACT_INFO = false` and their `call` implementations are pure computational functions with no balance-handling logic, as demonstrated by the `NoInfo` test precompile pattern [2](#0-1) .

The dispatch path in `pvm.rs::call` reads `value` and forwards it via `self.ext.call(...)` regardless of whether the callee is a precompile, and regardless of `HAS_CONTRACT_INFO`; the only gating condition is `read_only`/`is_read_only()` [3](#0-2) . The legacy WASM path in `wasm/runtime.rs::call` exhibits the identical unconditional value-forwarding pattern [4](#0-3) .

Deeper in `exec.rs`, `new_frame`/`do_transaction` confirms that for pre-compiles without contract info (`has_contract_info() == false`), no account is minted/created at all and no consumer reference is added — this branch only applies `if precompile.has_contract_info()` [5](#0-4) ; nonetheless, `transfer_from_origin` still executes for every non-delegate call regardless of whether the destination is a stateless precompile [6](#0-5) , meaning the underlying account (mapped from the fixed H160 address) still receives and holds a `pallet_balances` credit via the normal transfer path, even though `pallet-revive` never created "contract info" for it and no logic exists to spend it.

This is empirically confirmed by `pure_precompile_works`, which sends `value: 100` to each of the fixed pre-compile addresses `0x01`–`0x09` and asserts `Pallet::<Test>::evm_balance(&precompile_addr) == U256::from(100)` after the call [7](#0-6) . Additionally, `sent_funds_after_terminate_shall_be_credited_to_beneficiary_precompile` shows the codebase already treats sending funds to a precompile address (via `terminate`'s beneficiary) as a supported, intentional operation whose success is explicitly asserted [8](#0-7) , indicating this behavior is a deliberate design choice rather than an accidental omission — precompile addresses being able to hold a balance is treated as valid and tested functionality throughout the test suite, not flagged anywhere as a bug or blocked path.

Because none of the builtin stateless precompiles (`ECRecover`, `Sha256`, `Ripemd160`, `Identity`, `Modexp`, `Bn128Add`, `Bn128Mul`, `Bn128Pairing`, `Blake2F`) implement any balance-spending logic, and there is no known private key for these fixed addresses, value sent to them cannot be moved out through any pre-compile-native mechanism — it would only be recoverable through governance-level intervention (e.g., a forced balance transfer via root/governance, which is out of scope per the Impact Gate's exclusion of "privileged governance or admin abuse").

## Impact Explanation
This matches the "permanent user-fund lock" category from the Impact Gate: an unprivileged user can send value to a precompile address using ordinary `call`/`call_evm` host functions or standard Solidity `call{value: v}(...)` semantics, with no admin or validator involvement required, and no code path within `pallet-revive` restores or forwards that balance elsewhere. This is a legitimate, reachable, unprivileged loss-of-funds path consistent with the claim's evidence.

## Likelihood Explanation
High likelihood: addresses `0x01`–`0x09` are the standard, widely known Ethereum pre-compile addresses that developers frequently interact with when porting Solidity contracts; any low-level call with attached `value` to these addresses (accidental or otherwise) results in a stuck-fund transfer with no special conditions or privileged capability required, and the vulnerable code path is exercised by the pre-existing `pure_precompile_works` test itself.

## Recommendation
Before forwarding a non-zero `value` transfer in `pvm.rs::call` (and the equivalent legacy WASM path in `wasm/runtime.rs::call`), check whether the resolved callee is a pre-compile with `HAS_CONTRACT_INFO == false`; if so, and if the pre-compile does not opt in to a value-handling capability, reject the transfer (e.g., return `TransferFailed`/`StateChangeDenied`) rather than allowing the balance to be unconditionally credited to an address that has no code path to spend or return it.

## Proof of Concept
1. Fund `ALICE`, deploy a caller contract (as in `pure_precompile_works`).
2. Invoke `api::call` targeting `H160::from_low_u64_be(1)` (`ECRecover`) with a non-zero `value` (e.g., `100`) as in the existing test [9](#0-8) .
3. Confirm `Pallet::<Test>::evm_balance(&precompile_addr)` becomes `100`.
4. Observe that no extrinsic, host function, or governance call in `pallet-revive` can move balance out of this address, since `ECRecover::call` never touches balance and no private key exists for `0x0000...0001`.

/// This test does *not* create and terminate the Terminate contract in the same transaction.
/// Therefore, the SYSCALL terminate method does not be transferred to beneficiary.
#[test_matrix(
	[FixtureType::Solc, FixtureType::Resolc],
	[FixtureType::Solc, FixtureType::Resolc]
)]
fn sent_funds_after_terminate_shall_be_credited_to_beneficiary_precompile(
	caller_type: FixtureType,
	callee_type: FixtureType,
) {
	let (code, _) = compile_module_with_type("Terminate", callee_type).unwrap();
	let (caller_code, _) = compile_module_with_type("TerminateCaller", caller_type).unwrap();
	ExtBuilder::default().build().execute_with(|| {
		let min_balance = Contracts::min_balance();
		let _ = <Test as Config>::Currency::set_balance(&ALICE, 100_000_000_000);

		let Contract { addr, .. } = builder::bare_instantiate(Code::Upload(code))
			.constructor_data(
				Terminate::constructorCall {
					skip: true,
					method: METHOD_PRECOMPILE,
					beneficiary: DJANGO_ADDR.0.into(),
				}
				.abi_encode(),
			)
			.build_and_unwrap_contract();
		let account = <Test as Config>::AddressMapper::to_account_id(&addr);

		assert!(get_contract_checked(&addr).is_some(), "contract does not exist after create");
		assert_eq!(get_balance(&account), min_balance, "unexpected contract balance after create");

		let Contract { addr: caller_addr, .. } =
			builder::bare_instantiate(Code::Upload(caller_code))
				.native_value(125)
				.build_and_unwrap_contract();
		let caller_account = <Test as Config>::AddressMapper::to_account_id(&caller_addr);

		assert_eq!(
			get_balance(&caller_account),
			125 + min_balance,
			"unexpected caller balance before terminate"
		);

		let result = builder::bare_call(caller_addr)
			.data(
				TerminateCaller::sendFundsAfterTerminateCall {
					terminate_addr: addr.0.into(),
					value: alloy_core::primitives::U256::from(123_000_000u64),
					method: METHOD_PRECOMPILE,
					beneficiary: DJANGO_ADDR.0.into(),
				}
				.abi_encode(),
			)
			.build_and_unwrap_result();

		assert!(
			!result.did_revert(),
			"sendFundsAfterTerminateCall reverted: {}",
			decode_error(&result.data)
		);
		assert!(
			result.data.is_empty(),
			"sendFundsAfterTerminateCall returned unexpected data: {:?}",
			result.data
		);
		assert!(get_contract_checked(&addr).is_none(), "contract still exists after terminate");
		assert_eq!(
			get_balance(&DJANGO),
			123 + min_balance,
			"unexpected DJANGO balance after terminate"
		);
		assert_eq!(get_balance(&account), 0, "contract has balance after terminate");
	});
}
