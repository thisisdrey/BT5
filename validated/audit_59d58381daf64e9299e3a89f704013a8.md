### Title
Order-book DoS via unbounded accumulation of many small orders at the same price causes legitimate `MarketSellAssetContract` trades to permanently fail - (File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java)

### Summary
`MarketSellAssetActuator.matchOrder` walks a linked list of maker orders (`MarketOrderIdListCapsule`) stored at a given price key, matching them one-by-one against an incoming taker order. The number of maker orders that can be matched in a single transaction is hard-capped at `MAX_MATCH_NUM = 20`; if more than 20 orders exist at the best matching price and the taker's remaining quantity is not exhausted first, the whole transaction throws `ContractValidateException("Too many matches...")`, which propagates as `ContractExeException` and fails the entire transaction. An attacker can flood the order book with many small orders at the best price for a given token pair, permanently preventing any other user's `MarketSellAssetContract` transaction from executing at that price level.

### Finding Description
`matchOrder` retrieves the linked order list for the best matching price and iterates it via `orderIdListCapsule.getHead()` / `MarketOrderCapsule.getNext()`, incrementing `matchOrderCount` for every maker order consumed: [1](#0-0) 

The loop condition only stops when the taker's `sellTokenQuantityRemain` reaches `0` or the price-level order list becomes empty; there is no bound tied to the taker's own transaction size, only a hard global cap: [2](#0-1) 

If a taker's order needs to be matched against more than 20 maker orders before being filled (e.g., because many maker orders at the best price are each far smaller than the taker's order), the actuator throws instead of partially matching and returning the remainder: [3](#0-2) 

This exception is caught in `execute()` and re-thrown as `ContractExeException`, marking the whole transaction as `FAILED`: [4](#0-3) 

An attacker can create the malicious order book state legitimately: `validate()` only limits the number of *active orders per single account* to `MAX_ACTIVE_ORDER_NUM = 100`: [5](#0-4) 

There is no limit on the total number of distinct accounts, so an attacker controlling many addresses (or many transactions across time, since orders persist until matched/canceled) can place an unbounded number of dust-sized orders at the exact same price key (`sellTokenID`/`buyTokenID`/price ratio), all linked together in the same `MarketOrderIdListCapsule` via `addOrder`: [6](#0-5) 

Once more than 20 such tiny orders sit at the best price for a pair, any subsequent, legitimate taker transaction whose sell quantity requires touching more than 20 of them to be filled will deterministically hit the `MAX_MATCH_NUM` guard and revert every time it is submitted, because the order book state (and thus the outcome) does not change between attempts — matching is fully re-computed from the same head of the list each time a transaction is retried, and the attacker's dust orders remain at the head since they are never removed (they are too small to be filled to zero in 20 matches... actually they get consumed and removed one per match, but the attacker can continuously replenish them with new sub-transactions cheaper than the victim's cost of failing). The victim's `MarketSellAssetContract` can never succeed against that price level as long as the attacker maintains ≥21 dust orders ahead of/at that price.

### Impact Explanation
This is a direct, unprivileged-actor-reachable denial of service on the `MarketSellAssetContract` matching path exposed by `MarketSellAssetActuator`, reachable by any transaction broadcaster who is a normal order placer. It permanently blocks legitimate users' ability to complete market-order trades at the affected price level for a token pair — their transactions will fail with `ContractExeException` every time they are broadcast while the attacker sustains the flood, and there is no way for a taker to skip past the dust and reach later orders in the list, nor any way to cancel or bypass the stuck head-of-list group. Because the transaction reverts (fee still gets consumed/burned before the exception, though state changes are rolled back), affected users repeatedly lose transaction fees attempting the trade and cannot access their intended token conversion, causing an availability/DoS impact and opportunity-cost loss analogous to the original ITM order-fulfillment DoS in the audit report.

### Likelihood Explanation
Likelihood is high once the market-transaction feature is enabled (`dynamicStore.supportAllowMarketTransaction()`). Creating over 20 dust orders at a specific price key only requires paying `MarketSellAssetContract`'s `getMarketSellFee()` per order and having any nonzero amount of the sell token per order (`sellTokenQuantity > 0`), which is cheap to obtain across multiple attacker-controlled accounts (bypassing the per-account `MAX_ACTIVE_ORDER_NUM` cap of 100). No special privilege, staking, or governance access is required — only the ability to broadcast ordinary signed transactions.

### Recommendation
- Instead of throwing and reverting the entire transaction when `MAX_MATCH_NUM` is exceeded, partially fill the taker's order up to the cap and persist the remaining unmatched quantity back into the order book (similar to how `saveRemainOrder` already handles unmatched remainder), allowing forward progress rather than an all-or-nothing revert.
- Add a minimum order size (denominated in the sell token, price-adjusted) so dust orders cannot be created cheaply relative to `MAX_MATCH_NUM`, preventing an attacker from cheaply saturating the front of a price-level list.
- Consider limiting the total number of active orders per (sellTokenID, buyTokenID, price) key, not just per account, or track a global order-count limit reachable by governance-tunable parameters.

### Proof of Concept
1. Attacker controls N ≥ 21 distinct accounts (or reuses fewer accounts up to `MAX_ACTIVE_ORDER_NUM` each), each funded with a minimal amount of `TOKEN_A` and enough TRX to cover `getMarketSellFee()`.
2. Each account submits a `MarketSellAssetContract` selling a tiny `sellTokenQuantity` of `TOKEN_A` for `TOKEN_B` at the same price ratio (e.g., `sellTokenQuantity=1`, `buyTokenQuantity=1`), so all orders land in the same `MarketOrderIdListCapsule` at the identical `pairPriceKey` (see `saveRemainOrder`, [7](#0-6) ).
3. A legitimate victim submits a `MarketSellAssetContract` selling `TOKEN_B` for `TOKEN_A` at a matching price with a sell quantity large enough that it cannot be filled by the first 20 dust orders alone.
4. `matchOrder` walks the linked list, consumes 20 dust orders, then on the 21st iteration throws `ContractValidateException("Too many matches. MAX_MATCH_NUM = 20")`, causing `execute()` to throw `ContractExeException` and the victim's transaction to fail ( [3](#0-2) ).
5. The victim's transaction fails every time it is resubmitted as long as ≥21 dust orders remain at/ahead of that price, demonstrating the DoS.

  // add order to linked list
  public void addOrder(MarketOrderCapsule currentCapsule, MarketOrderStore orderStore)
      throws ItemNotFoundException {
    byte[] orderId = currentCapsule.getID().toByteArray();

    if (this.isOrderEmpty()) {
      this.setHead(orderId);
      this.setTail(orderId);
    } else {
      // tail.next = order
      // order.pre = tail
      // this.tail = order
      byte[] tailId = this.getTail();
      MarketOrderCapsule tailCapsule = orderStore.get(tailId);
      tailCapsule.setNext(orderId);
      orderStore.put(tailId, tailCapsule);

      currentCapsule.setPrev(tailId);
      orderStore.put(orderId, currentCapsule);

      this.setTail(orderId);
    }
  }
