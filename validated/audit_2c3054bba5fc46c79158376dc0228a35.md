### Title
Replay-window check-then-decrypt-then-update race allows duplicate/replayed packet acceptance - ([File: connection_state.go])

### Summary
`ConnectionState.Decrypt` (and `VerifyRelay`) validate the anti-replay window in two separate, lock-released phases: `window.Check()` is called and the lock released, then AEAD decryption is performed with no lock held, and only afterward is `window.Update()` called under a freshly-acquired lock. Because `nebula` reads UDP packets on multiple goroutines (`listen.routines`/`tun.routines`, `SO_REUSEPORT`), two threads processing the same replayed ciphertext concurrently can both pass `Check()` before either calls `Update()`, letting an attacker's replayed capture be decrypted and delivered a second time even though the anti-replay window is designed to reject exactly this counter value. [1](#0-0) 

### Finding Description
`Decrypt` performs the anti-replay check and the anti-replay commit as two independent critical sections instead of one atomic operation:
```
cs.decryptLock.Lock()
result := cs.window.Check(l, messageCounter)
cs.decryptLock.Unlock()
...
out, err = cs.dKey.DecryptDanger(...)   // no lock held
...
cs.decryptLock.Lock()
result = cs.window.Update(l, messageCounter)
cs.decryptLock.Unlock()
``` [2](#0-1) 

`Bits.Check` only inspects whether the bit for `messageCounter` is already set; it does not itself mark the bit — that only happens in `Bits.Update`, which is called after decryption completes: [3](#0-2) [4](#0-3) 

Because the lock is dropped between `Check` and the actual state mutation in `Update`, the window bit for a given counter is not "reserved" atomically with the check. If two goroutines call `Decrypt` for the same tunnel with the same `messageCounter` at roughly the same time (e.g. the legitimate packet and an attacker's captured/replayed copy of it, or two replayed copies), both can observe `Check() == true` before either has called `Update()`. Both then proceed to call `DecryptDanger` with the identical (counter, ciphertext) pair — AEAD decryption of the same nonce+ciphertext succeeds deterministically for both — and both deliver the decrypted payload up the stack (to the tun device / cached-packet path) before either commits `Update()`. Only after both decrypt does the `Update()` phase run; even if one of the two `Update()` calls eventually returns `false` (correctly flagging a dup), that check happens too late — the payload has already been decrypted and handed off to the application layer once already, and in the race window it can be handed off twice.

This mirrors the Notional bug class precisely: a security invariant (`checkMinBorrow` / "no duplicate counter delivered") is supposed to be enforced atomically, but an implementation splits it into a check-then-later-enforce sequence across a released lock, and an attacker can exploit the gap to make a normally-unreachable state (a replayed message being accepted) reachable — no valid certificate needed, since the attacker only needs to inject a previously captured UDP ciphertext at the right time; it does not need to be decrypted or forged.

`nebula` explicitly supports multiple concurrent readers of the encrypted socket (multiple `listen.routines`, `SO_REUSEPORT`), which is what makes the race practically reachable rather than purely theoretical, and `readOutsidePackets` is the packet-dispatch entry point that feeds into `Decrypt` for `header.Message` type packets. [5](#0-4) 

### Impact Explanation
A successful race allows an off-path attacker (who can capture and replay ciphertext, with no CA-signed certificate or key material) to cause the receiver to process the same encrypted message twice. Depending on payload content, this can duplicate tunneled application-layer packets (e.g. duplicate transactions, commands, or state-changing requests carried inside the overlay), effectively defeating the anti-replay protection that the Noise/AEAD counter window is meant to guarantee. This is a concrete traffic-replay/forgery-adjacent impact within the stated valid impact categories.

### Likelihood Explanation
Exploitation requires winning a narrow race between two goroutines processing an identical (index, ciphertext) pair, which is inherently probabilistic and requires either multiple listener routines to be enabled or another source of concurrent invocation on the same `ConnectionState`. This limits reliability but does not eliminate exploitability — an attacker can send many duplicate copies of a captured packet to increase the chance of hitting the window, and the code path itself has no atomicity between "haven't seen it" and "mark it seen," which is a genuine design flaw independent of how easy it is to win the race in a given deployment.

### Recommendation
Make the replay check-and-mark atomic: hold `decryptLock` across `Check`, `DecryptDanger`, and `Update` (or, more efficiently, reserve the counter bit before decryption and roll it back on decryption failure) so no two goroutines can ever observe an un-marked bit for the same counter and both proceed to decrypt/deliver. Apply the same fix to `VerifyRelay`, which has an identical pattern.

### Proof of Concept
1. Establish two goroutines reading from the UDP socket concurrently (default in most deployments due to `SO_REUSEPORT`/multiple listen routines).
2. Attacker captures one legitimate encrypted `header.Message` packet destined to a target tunnel (no decryption needed — raw ciphertext is sufficient).
3. Attacker sends two copies of that exact packet to the target in near-simultaneous UDP datagrams.
4. If both copies land on different reader goroutines close enough in time, both call `ConnectionState.Decrypt`: both call `window.Check(messageCounter)` before either calls `window.Update(messageCounter)`, both pass, both successfully `DecryptDanger` (identical inputs), and both deliver the decrypted payload — resulting in double-delivery of a replayed message, defeating the anti-replay window's guarantee. 	var err error

	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}

// Update has three branches:
//   - i == b.current+1: fast path; advance the cursor by one and lose-count
//     the slot we just stomped (only past warmup; see the i > b.length guard
//     below).
//   - i  >  b.current+1: jump path; clear all slots between current and i
//     (or up to a full window's worth, whichever is smaller) via clearRange,
//     then mark i. Two arms here: a warmup arm that handles the very first
//     window before the cursor has slid, and a steady-state arm that treats
//     every cleared empty slot as a lost packet.
//   - i  <= b.current: in-window check for duplicates; out-of-window otherwise.
//
// NewBits seeds bits[0]=1 so counter 0 looks "received" — Update never
// clears that marker during warmup (clearRange skips position 0 when
// startPos=1), and once b.current >= b.length the marker is no longer
// consulted. The marker prevents a fictitious "lost" hit on the first real
// counter.
func (b *Bits) Update(l *slog.Logger, i uint64) bool {
	// Fast path: i is the next expected counter. Split out so the function
	// stays small and avoids paying for the slow paths' slog argument-build
	// stack frame on every call. The bit read/test/write is inlined to
	// touch the backing word once.
	if i == b.current+1 {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if i > b.length && w&mask == 0 {
			b.lostCounter.Inc(1)
		}
		b.bits[word] = w | mask
		b.current = i
		return true
	}
	return b.updateSlow(l, i)
}
