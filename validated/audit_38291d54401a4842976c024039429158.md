### Title
Storage-proof challenge in `check_proof` derives its "random" chunk index solely from `parent_hash`, letting block authors bias which chunk is checked - ([File: substrate/frame/transaction-storage/src/lib.rs])

### Summary
The external report criticizes a KZG verifier that derives its Fiat-Shamir challenge from too little prover-controlled data (only sample commitments), recommending the challenge bind everything the prover can influence, or use unbiased external randomness. The `pallet-transaction-storage` "proof-of-storage" challenge in `check_proof` has the analogous defect: the "random" chunk to be challenged is derived only from `frame_system::Pallet::<T>::parent_hash()`, a value fully known and directly influenced by the very party (the block author / collator) that must subsequently produce the proof.

### Finding Description
`check_proof` computes the challenge chunk index like this: [1](#0-0) 

The randomness source is nothing but the parent block hash, then passed to `verify_chunk_proof`, which turns it into `selected_block_chunk_index` via `random_chunk`: [2](#0-1) [3](#0-2) 

The proof itself (`TransactionStorageProof`) is supplied by the block author as an unsigned inherent, produced via `create_inherent`/`build_proof`, using the same `parent_hash` as the "randomness": [4](#0-3) [5](#0-4) 

This is exactly the "insufficiently random challenge" pattern from the report: the challenge is derived from data that is (a) known in advance to the entity that must answer it, and (b) partially under that entity's control, because a block author who produces block `N` chooses (or can influence, e.g. by re-ordering/omitting transactions, or — in some consensus setups — via block production timing/equivocation) block `N-1`'s hash before needing to supply the storage proof for block `N`. There is no additional binding to unbiased external randomness (e.g. BABE `ParentBlockRandomness`/VRF output, as used elsewhere in the codebase for the same purpose, see `polkadot/runtime/parachains/src/paras_inherent/mod.rs::compute_entropy`) and no binding of the challenge to anything else the "prover" (block author) supplies, such as the specific proof content, transaction data, or session/epoch context.

By contrast, the codebase elsewhere explicitly recognizes that parent-hash randomness is manipulable and warns about it: the `insecure-randomness-collective-flip` pallet documentation states block producers have "significant influence over their block hashes" and that hashing the raw block hash removes any low-influence property, and the parachains runtime deliberately prefers VRF-based `ParentBlockRandomness` over the parent hash "since it's harder to influence the VRF output than the block hash": [6](#0-5) [7](#0-6) 

`pallet-transaction-storage`, however, uses the raw `parent_hash` directly as the sole challenge source, without any of these mitigations.

### Impact Explanation
This pallet implements a proof-of-storage/proof-of-retrievability check meant to make it costly for validators/authors to discard indexed off-chain data early. If the chunk-selection challenge is predictable/influenceable by the author producing the checking block, an author who has discarded some chunks of previously-stored data can:
- Predict, immediately after seeing (or choosing) the parent block, exactly which global chunk index will be challenged before constructing the inherent, and
- In borderline cases (e.g., forks/equivocation, or control over which parent block is built upon) select a parent hash whose derived challenge lands on a chunk they still retain, while having discarded the rest.

This degrades the security guarantee of the whole mechanism: the "random probing" (`fn check_proof` doc comment: "Linear w.r.t the number of indexed transactions ... for random probing") is supposed to statistically guarantee that authors retain full data because they cannot predict which chunk will be checked. If the challenge is derived from data the checking author controls or can foresee/select, the probabilistic security bound underlying the whole retention-incentive design collapses, allowing improper partial data loss to go undetected — i.e., "public underpriced work" / broken audit guarantee for chain-level data-retention consensus, without needing a malicious validator/collator assumption beyond the ordinary "prover" role this pallet already assigns to block authors producing the mandatory inherent.

### Likelihood Explanation
The challenge derivation path is unconditional and always executed for every non-empty target block (`check_proof` is a mandatory inherent call executed each retention-period boundary). No special privileges beyond normal block-authoring capability are required — any block author responsible for building the block that must submit `check_proof` already knows `parent_hash` deterministically before constructing the required inherent data (`InherentDataProvider::new_data_provider` builds the proof directly from the `parent` hash). No additional entropy or binding is layered on top, so exploitability only requires the ordinary capability set of "author of a block," which is a lower bar than "malicious validator" collusion assumptions excluded by the impact gate — this is a design/implementation flaw in the challenge construction itself, not reliance on a malicious actor.

### Recommendation
Bind the storage-proof challenge to unbiased, unpredictable randomness that the checking block author cannot know or influence ahead of proof construction — e.g., derive it from BABE/Sassafras VRF output for the checking block (mirroring `ParentBlockRandomness`/`compute_entropy` pattern used in `polkadot/runtime/parachains/src/paras_inherent/mod.rs`) rather than the raw `parent_hash`. Additionally consider binding the challenge to the full context the prover can affect (target block number, total_chunks, chunk root set) to prevent any grinding attack on chunk selection, consistent with the external report's recommendation to include everything the verifier relies upon and the prover can influence.

### Proof of Concept
Conceptual grinding scenario (cannot be executed without live chain/test harness access):
1. Attacker controls (or repeatedly re-attempts) block production for block `N`, whose `check_proof` inherent challenges the transactions of block `N - RetentionPeriod`.
2. Attacker has discarded some chunks of the target block's stored data but retained others.
3. Before finalizing block `N`, the attacker computes `random_chunk(parent_hash, total_chunks)` off-chain for candidate parent hashes reachable via minor block-production variations (e.g., choice of included extrinsics affecting `parent_hash` of a subsequent block, or selecting among competing tips during a fork/equivocation window).
4. The attacker proceeds only with a block-building path whose resulting `parent_hash` makes `selected_block_chunk_index` land on a chunk it still possesses, submitting a valid proof for that chunk while having discarded the others undetected.
5. `check_proof` accepts the proof at [8](#0-7)  since only the single sampled chunk is ever checked.

/// A utility function to extract a chunk index from the source of randomness.
///
/// # Panics
///
/// This function panics if `total_chunks` is `0`.
pub fn random_chunk(random_hash: &[u8], total_chunks: ChunkIndex) -> ChunkIndex {
	let mut buf = [0u8; 8];
	buf.copy_from_slice(&random_hash[0..8]);
	let random_u64 = u64::from_be_bytes(buf);
	(random_u64 % total_chunks as u64) as u32
}

fn compute_entropy<T: Config>(parent_hash: T::Hash) -> [u8; 32] {
	const CANDIDATE_SEED_SUBJECT: [u8; 32] = *b"candidate-seed-selection-subject";
	// NOTE: this is slightly gameable since this randomness was already public
	// by the previous block, while for the block author this randomness was
	// known 2 epochs ago. it is marginally better than using the parent block
	// hash since it's harder to influence the VRF output than the block hash.
	let vrf_random = ParentBlockRandomness::<T>::random(&CANDIDATE_SEED_SUBJECT[..]).0;
	let mut entropy: [u8; 32] = CANDIDATE_SEED_SUBJECT;
	if let Some(vrf_random) = vrf_random {
		entropy.as_mut().copy_from_slice(vrf_random.as_ref());
	} else {
		// in case there is no VRF randomness present, we utilize the relay parent
		// as seed, it's better than a static value.
		log::warn!(target: LOG_TARGET, "ParentBlockRandomness did not provide entropy");
		entropy.as_mut().copy_from_slice(parent_hash.as_ref());
	}
	entropy
}
