### Title
Unbounded per-cycle reward computation loop in `MortgageService.withdrawReward()`/`queryReward()` can freeze user funds via out-of-resource withdrawal - (File: chainbase/src/main/java/org/tron/core/service/MortgageService.java)

### Summary
`MortgageService.withdrawReward()` and `queryReward()`, which are invoked by the unprivileged, signed `WithdrawBalanceContract` (via `WithdrawBalanceActuator`) as well as indirectly by the TVM `withdrawReward()` native contract path, compute a voter/witness's accumulated reward by calling `computeReward(beginCycle, endCycle, accountCapsule)`. When the "new VI reward algorithm" has not yet taken effect for the relevant range (`beginCycle < newRewardAlgorithmEffectiveCycle`), this delegates to `getOldReward()`, which iterates once **per maintenance cycle** from `beginCycle` to `min(endCycle, newAlgorithmCycle)`, and for every cycle re-iterates the account's entire vote list performing multiple store reads (`getReward`, `getWitnessVote`). This is structurally the same pattern as the reported Biconomy bug: a loop whose iteration count grows with elapsed time/inactivity of the caller, executed synchronously inside a single user-initiated transaction/actuator, with no cap on the number of iterations other than a fixed historical cutoff cycle. ### Finding Description
`computeReward(beginCycle, endCycle, accountCapsule)` in `MortgageService` splits the range into an "old algorithm" segment (`beginCycle` to `min(endCycle, newRewardAlgorithmEffectiveCycle)`) and a "new algorithm" (VI-based, O(1) per vote) segment: [1](#0-0) 

For the old segment, unless `dynamicPropertiesStore.allowOldRewardOpt()` is enabled (which redirects to the O(1)-per-vote cached `RewardViCalService.getNewRewardAlgorithmReward`), the fallback path `getOldReward()` performs a `for (long cycle = begin; cycle < end; cycle++)` loop, calling `computeReward(cycle, votes)` for every single cycle, each of which iterates the full vote list and performs store reads: [2](#0-1) [3](#0-2) 

This is reachable from a completely unprivileged, ordinary signed transaction: `WithdrawBalanceActuator` (a `WithdrawBalanceContract`) calls `mortgageService.queryReward()` during validation and `withdrawReward()` during execution: [4](#0-3) 

If an account votes for witnesses and then never calls `WithdrawBalanceContract` (or otherwise triggers a `beginCycle`/`endCycle` update) for a very long time while the network is still relying on the old reward algorithm path (i.e., before/without `allowOldRewardOpt` being enabled, or for historical cycles predating `newRewardAlgorithmEffectiveCycle`), the number of cycles between `beginCycle` and the cutoff can become very large. Each maintenance cycle occurs roughly every 6 hours, so cycles accumulate over months/years of network operation. When the account finally attempts to withdraw, the single transaction must synchronously execute this large multi-cycle loop, performing repeated DB reads and vote-list iterations, inside one block's processing time — unlike EVM contracts, native actuators in java-tron are not metered by an energy/gas limit that would cleanly revert the transaction; instead the cost is absorbed directly into block-application time, risking excessive block processing latency for a single transaction and, in the worst case, preventing timely block production/validation.

### Impact Explanation
If a voter's `beginCycle` accumulates a large lag (e.g., due to long-term inactivity across many maintenance cycles while the old-reward code path remains active for that account's cycle range), a subsequent withdraw/query call executes an O(cycles × votes) loop synchronously within actuator validation/execution. This can:
- Cause disproportionate resource consumption for a single transaction relative to its declared/charged bandwidth, since native actuators are not gas-metered the way TVM calls are.
- Effectively make it impractical or impossible for the affected account to ever complete a withdrawal in a reasonable amount of time, permanently freezing the reward funds tied to `AccountCapsule.allowance`.
- In aggregate (multiple such accounts, or one account with an extremely large lag), degrade block processing performance for the whole node, since this computation runs during block application for the `WithdrawBalanceContract`/`withdrawReward` TVM opcode.

This matches the Medium-severity classification of the original finding: a permanent, unbounded-cost DoS/fund-freezing path reachable by a completely ordinary, unprivileged actor triggering their own reward withdrawal.

### Likelihood Explanation
The condition requires the account's `beginCycle` to lag far behind `currentCycle` while relying on the per-cycle old-reward loop, which requires `allowOldRewardOpt()` to be disabled (or the account's unclaimed range to predate `newRewardAlgorithmEffectiveCycle`). Since `allowOldRewardOpt` is a chain parameter controllable only via governance proposal (not by the end user), whether this path is actually exercised on a live network depends on network configuration at the time. This makes exploitability network/configuration-dependent rather than universally exploitable by any user at any time, lowering likelihood relative to a purely code-level, always-reachable unbounded loop — but the code path itself is unconditionally present and reachable by an ordinary signed transaction whenever the condition holds.

### Recommendation
- Eliminate the per-cycle fallback loop in `getOldReward()`/`computeReward(cycle, votes)` entirely by making the VI-based (O(1) per vote) algorithm the only computation path, backfilling/precomputing historical VI values once (as `RewardViCalService` already does) rather than relying on a live per-transaction loop as a fallback.
- If the old fallback must be retained for compatibility, bound the number of cycles processed per transaction (e.g., process withdrawals incrementally in capped batches, requiring multiple transactions to fully catch up, while still crediting partial rewards) so a single transaction cannot be forced into unbounded work.
- Add explicit cycle-count/resource limits to `WithdrawBalanceActuator` validation and to `WithdrawRewardProcessor`/`VoteRewardUtil` reachable via TVM `withdrawReward()`, rejecting or splitting work if the pending cycle range exceeds a safe threshold.

### Proof of Concept
1. Ensure the network has `allowOldRewardOpt` disabled (or the account's unclaimed cycle range predates `newRewardAlgorithmEffectiveCycle`), so reward computation for the account's pending range goes through `getOldReward()`.
2. Have an account vote for one or more witnesses, then avoid calling `WithdrawBalanceContract` (or any action that advances `beginCycle`) for a very large number of maintenance cycles (each ~6 hours), letting `beginCycle` fall far behind `currentCycle`.
3. Submit a `WithdrawBalanceContract` transaction for the account (or invoke the TVM `withdrawReward()` opcode from a contract with the same stale vote state).
4. Observe that `WithdrawBalanceActuator.validate()` → `mortgageService.queryReward()` and `execute()` → `mortgageService.withdrawReward()` invoke `computeReward()` → `getOldReward()`, which loops once per pending cycle (`for (long cycle = begin; cycle < end; cycle++) { reward += computeReward(cycle, votes); }`), each iteration re-scanning the vote list and performing DB reads — demonstrating unbounded (time-lag-proportional) work inside a single transaction/block-application step, with no per-transaction cap.   private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }
