### Title
Unbounded refname list in `DeleteRefs` RPC enables permissionless DoS via mass reference locking - ([File: internal/gitaly/service/ref/delete_refs.go])

### Summary
`DeleteRefs` accepts a caller-controlled list of reference names (or a prefix to expand into a list) and processes the *entire* list synchronously and unboundedly inside a single unary RPC call: once for revision validation, once for queuing deletes and updating the vote hash, and then locks every one of the resulting references via `updater.Prepare()`. There is no limit on the number of refnames a client may submit or that a prefix-based deletion can expand to, mirroring the "unbounded denom list iterated in unmetered execution" bug class from the report, but here the unbounded loop occurs inside a synchronous gRPC handler that performs expensive per-item work (validation, git process communication, and reference locking).

### Finding Description
`DeleteRefs` first resolves the concrete refnames to delete via `s.refsToRemove(ctx, repo, in)`, which can expand a request into an arbitrarily long slice of refnames (either an explicit list supplied by the caller or all refs matching an `ExceptWithPrefix`). [1](#0-0) 

It then iterates over the full `refnames` slice twice with no count bound:
1. To validate every refname via `git.ValidateRevision`.
2. To queue every ref for deletion with `updater.Delete(ref)` and update a running `voteHash` for every entry. [2](#0-1) 

Finally, `updater.Prepare()` is called, which locks all queued references at once before any vote or commit occurs. [3](#0-2) 

None of these stages enforce a maximum number of refnames, unlike other ref-related RPCs in the same package that explicitly implement pagination or per-item limits (e.g., `ListRefs`'s `PaginationParameter` and `UpdateRemoteMirror`'s `maxDivergentRefs` cap seen elsewhere in the codebase). There is also no evidence of a configured `MaxRecvMsgSize`/`MaxCallRecvMsgSize` override in this repository, so the only bound on request size is the gRPC default, which for a list of short strings can still admit tens of thousands to hundreds of thousands of refnames per unary call. `git-update-ref`'s locking phase (`Prepare`) over that many entries, executed synchronously inside a single RPC handler on the primary node, directly parallels the reward-plan bug's unbounded-list-processed-in-unmetered-execution pattern.

### Impact Explanation
An ordinary user with permission to call `DeleteRefs` on a repository (a normal delete-refs/administrative operation, not a privileged internal API) can submit a single request with an extremely long refname list (or a broad `ExceptWithPrefix` deletion that expands to a huge set of existing refs) to force the Gitaly node to perform expensive, unbounded validation and reference-locking work synchronously within one RPC. This can starve the git process pipe, hold reference locks across a large fraction of the repository's refs for an extended period, and block other operations on the same repository (or in a Praefect/transactional setup, hold up the associated voting round), causing a localized denial of service against the repository/handler.

### Likelihood Explanation
Likelihood is high for any environment that exposes `DeleteRefs` to normal, non-privileged actors (e.g., internal service accounts used by GitLab or any client with delete-ref permission), since the only requirement is crafting a single RPC request with a large `refnames`/prefix field — no special privileges, no race conditions, and no dependency on other systems are needed. The absence of any explicit count or size guard in `refsToRemove`/`DeleteRefs`, contrasted with paginated/limited counterparts elsewhere in the same service (`ListRefs`, `UpdateRemoteMirror`), further supports that this omission is unintentional.

### Recommendation
Enforce an explicit maximum number of refnames (and/or expanded refs from prefix-based deletion) accepted per `DeleteRefsRequest`, rejecting requests that exceed the limit with `InvalidArgument` before any validation, locking, or git-process work begins. Alternatively, convert bulk deletions to a streaming/chunked RPC (as already done for `UpdateReferences`) so that large deletions are processed incrementally rather than being fully buffered and locked in one synchronous call.

### Proof of Concept
Concrete exploitation details (i.e., minimum refname count required to cause a measurable stall, and exact default gRPC message-size ceiling in the deployed configuration) could not be fully verified from the indexed code — no `MaxRecvMsgSize`/`MaxCallRecvMsgSize` override was found in this repository slice, and the full request-size/refcount interaction depends on runtime gRPC server configuration and git binary behavior. A background Devin session with full repository and runtime access would be needed to build and run an actual `DeleteRefsRequest` with a very large `Refs`/`ExceptWithPrefix` payload against a test repository to empirically measure the handler's execution time as a function of refname count, analogous to the reward-plan PoC in the report.

func (s *server) DeleteRefs(ctx context.Context, in *gitalypb.DeleteRefsRequest) (_ *gitalypb.DeleteRefsResponse, returnedErr error) {
	if err := validateDeleteRefRequest(ctx, s.locator, in); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	repo := s.localRepoFactory.Build(in.GetRepository())

	refnames, err := s.refsToRemove(ctx, repo, in)
	if err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	var invalidRefnames [][]byte

	for _, ref := range refnames {
		if err := git.ValidateRevision([]byte(ref)); err != nil {
			invalidRefnames = append(invalidRefnames, []byte(ref))
		}
	}

	if len(invalidRefnames) > 0 {
		return nil, structerr.NewInvalidArgument("invalid references").WithDetail(
			&gitalypb.DeleteRefsError{
				Error: &gitalypb.DeleteRefsError_InvalidFormat{
					InvalidFormat: &gitalypb.InvalidRefFormatError{
						Refs: invalidRefnames,
					},
				},
			},
		)
	}
	if err := updater.Start(); err != nil {
		return nil, structerr.NewInternal("start reference transaction: %w", err)
	}

	for _, ref := range refnames {
		if err := updater.Delete(ref); err != nil {
			return nil, structerr.NewInternal("unable to delete refs: %w", err)
		}

		if _, err := voteHash.Write([]byte(ref.String() + "\n")); err != nil {
			return nil, structerr.NewInternal("could not update vote hash: %w", err)
		}
	}
