### Title
Order execution "executor" authority race lets a front-runner hijack a pending keeper execution and redirect withdrawn funds - (File: `programs/marginfi/src/instructions/marginfi_account/order.rs`)

### Summary
`StartExecuteOrder` grants an arbitrary, unchecked `executor` account temporary authority to act "as if they are the user authority" for the marginfi account until `EndExecuteOrder` closes out the flow. The `ExecuteOrderRecord` PDA that locks in *who* holds that authority is derived only from the `order` key, not from the caller/executor, exactly the flaw the ENS report describes: a privileged one-shot action (the ENS `register`, here the order-execution authority grant) is committed to a resource identifier (`name` / `order`) but never bound to the caller who is entitled to use it.

### Finding Description
`StartExecuteOrder`'s account validation explicitly notes: [1](#0-0) 
that `executor` is completely unchecked ("executor decides this without restriction"), and the account is granted temporary user-level authority. The uniqueness guard for this authority grant, `execute_record`, is a PDA seeded only by `order.key()`: [2](#0-1) 

`start_execute_order` stores whichever `executor` pubkey happened to land first: [3](#0-2) 

Because the PDA `init` only depends on `order`, not on `executor`/`fee_payer`, this is structurally identical to ENS's `makeCommitment(name, secret)` that omitted `owner`: the first transaction to land for a given `order` wins the slot and pins its own `executor` into `execute_record`, regardless of who originally intended to execute it. Any legitimate keeper's `StartExecuteOrder → (withdraw/repay ixs) → EndExecuteOrder` bundle sitting in the mempool can be observed and front-run by an attacker who resubmits the same `order` with `executor = attacker` and higher priority fee. The original transaction's `init` on `execute_record` then fails (`account already in use`), while the attacker's transaction proceeds and — as far as the program is concerned — is authorized to act "as if they are the user authority" for the account for the remainder of that transaction, including specifying withdrawal destination accounts.

`EndExecuteOrder` only checks that the health/slippage constraints implied by the order are satisfied and that the `executor` on `execute_record` matches the one closing it out: [4](#0-3) 
Nothing constrains where withdrawn/repaid funds go, since destination token accounts for `lending_account_withdraw`/repay CPIs invoked under the executor's temporary authority are supplied by whichever transaction wins the race.

### Impact Explanation
An attacker who front-runs a pending `StartExecuteOrder` for a triggered stop-loss/take-profit order can seize the temporary "act as the account authority" privilege for that execution window and route the freed collateral (or otherwise-legitimate withdrawal) to their own token account instead of the account owner's, while still satisfying the health/slippage bookkeeping checks in `end_execute_order`. This is a concrete theft/unauthorized-transfer vector against unprivileged user accounts in the order-execution path, not merely griefing of keeper fee attribution.

### Likelihood Explanation
Exploitation requires observing a `StartExecuteOrder` transaction (or its constituent instructions) in the mempool/pending queue before it lands and resubmitting a competing transaction with a higher priority fee — a standard, low-cost Solana front-running technique. It does not require any privileged role, only that an order has become executable (trigger condition met), which is a routine and expected occurrence for any account using orders.

### Recommendation
Bind the `execute_record` PDA (and/or the `executor` authorization) to the actual signer/fee payer initiating execution, e.g. include `fee_payer`/intended `executor` in the PDA seeds, or require `executor == fee_payer` and have the account owner (or an allow-listed keeper set) pre-authorize which executor may act, analogous to including `msg.sender`/`owner` in the ENS `makeCommitment`. At minimum, constrain destination accounts for withdraw/repay performed under the temporary executor authority to accounts controlled by the marginfi account's actual `authority`.

### Proof of Concept
1. Alice's account has an order whose trigger condition is met; her keeper bot builds `StartExecuteOrder(order, executor=Alice) + LendingAccountWithdraw(destination=Alice_ATA) + EndExecuteOrder` and broadcasts it.
2. Eve observes this pending transaction bundle in the mempool, and constructs her own transaction `StartExecuteOrder(order, executor=Eve) + LendingAccountWithdraw(destination=Eve_ATA) + EndExecuteOrder` referencing the same `order` account, with a higher priority fee.
3. Eve's transaction lands first: `execute_record` (PDA = `[EXECUTE_ORDER_SEED, order.key()]`) is initialized with `executor = Eve`, per [5](#0-4) .
4. Alice's transaction fails when it tries to `init` the same `execute_record` PDA (`account already in use`).
5. Eve's bundle proceeds: within the `START_EXECUTE_ORDER`/`END_EXECUTE_ORDER` bracket, Eve (as `executor`) is treated as having Alice's account authority and withdraws the order's freed collateral to `Eve_ATA` instead of Alice's own account, while `end_execute_order`'s health/slippage checks still pass since they only validate account-level equity/health, not the withdrawal destination.
