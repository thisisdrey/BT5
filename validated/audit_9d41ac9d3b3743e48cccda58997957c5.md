### Title
Vault runtime configuration (caps, interest-rate curve, fees) defaults to zero/disabled and is never validated at `initialize` - ([File: mainnet/contracts/vault/v0-vault-stx.clar and sibling vault contracts])

### Summary
Each Zest v0 vault (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`) declares its economic "runtime config" (`cap-debt`, `cap-supply`, `fee-flash`, `fee-reserve`, `points-ir`) with zero-valued defaults, and the public `initialize` function only flips `initialized` to `true` and mints minimum liquidity — it neither sets nor asserts non-zero/valid values for these parameters before the vault becomes usable. [3](#0-2) [4](#0-3) 

### Finding Description
The vault's caps (`cap-supply`, `cap-debt`) are set to `u0` by default, and the interest-rate curve `points-ir` defaults to `{util: u0, rate: u0}`. [1](#0-0)  `initialize()` does not populate these before completing initialization, relying entirely on a separate, DAO-only follow-up call (`set-cap-supply`, `set-cap-debt`, `set-points-rate`/`set-points-util`, `set-fee-reserve`, `set-fee-flash`) to configure the vault for real use. [4](#0-3)  This is structurally identical to the NFTCollection.sol analog: `deploymentConfig` is validated at init, but `runtimeConfig` (mint price, etc.) is not, so if the DAO's post-initialize configuration calls are missed, delayed, or executed out of order relative to `market` authorization/deposits going live, the vault operates in an unsafe default state (zero interest rate, zero caps meaning either "no cap" — since caps of `u0` in these vaults are typically treated as unlimited/no-cap sentinel — or, depending on cap-check semantics, blocking all deposits). Because DAO proposal scripts (e.g., `local-testing/contracts/proposals/proposal-init-vaults.clar`) show the caps are expected to be explicitly set with a follow-up `set-cap-supply`/`set-cap-debt` call before `initialize`, any deployment sequencing mistake that authorizes `market` or exposes deposit/borrow before those calls run leaves the interest-rate curve at zero, meaning debt would accrue no interest while supply/borrow caps are not enforced as intended.

### Impact Explanation
If the vault is initialized (and market authorized) before `points-ir` and caps are properly configured, borrowers could take out debt while interest accrues at a permanently zero rate (`rate: u0`) until DAO catches and fixes the config — this constitutes theft of unclaimed yield for lenders/suppliers (interest that should have accrued to depositors is permanently lost for that window), matching the in-scope "theft of unclaimed yield" / "temporary freezing of funds" impact class.

### Likelihood Explanation
Likelihood is low-to-medium: it depends on the DAO deployment/configuration script sequencing being incorrect, i.e., authorizing `market` and enabling deposits/borrow against a vault before the caps/interest-rate config calls run. The existing local-testing proposal script does perform cap-setting before `initialize`, suggesting the operational process is aware of this dependency, but there is no on-chain guard preventing the vault from being used in the misconfigured state if the sequence is not followed exactly (e.g., a partial or reordered DAO proposal execution).

### Recommendation
Add an explicit precondition inside `deposit`/`borrow` (or `initialize`) that reverts if `points-ir` and caps have not been set to valid non-default values, or fold the required runtime configuration parameters directly as arguments into `initialize` with validation (analogous to how `deploymentConfig` is validated), so the vault cannot begin operating with an unconfigured (zero-rate, zero-cap) state.

### Proof of Concept
1. DAO deploys a new vault and calls `initialize()` — this succeeds and mints minimum liquidity, with `points-ir = {util: u0, rate: u0}`, `cap-supply = u0`, `cap-debt = u0`. [4](#0-3) 
2. If the DAO's follow-up proposal authorizes `market` (`set-authorized-contract`) and users begin depositing/borrowing before the separate `set-points-rate`/`set-points-util`/`set-cap-*` calls execute, borrow accrues at `rate: u0` — i.e., debt does not accrue interest for suppliers during that window. [5](#0-4) 
3. This window of zero-rate borrowing represents lost yield to depositors that cannot be retroactively recovered once corrected.

**Uncertainty note:** I was unable to verify from the indexed code whether `cap-supply`/`cap-debt` of `u0` is treated by the market/borrow logic as "unlimited" or "blocked" (i.e., the exact cap-check semantics in `market.clar`), since that logic was not returned by my searches. This affects whether the zero-cap default is itself independently exploitable (unlimited borrowing) or merely blocks activity until configured. I'm confident in the zero-rate/`points-ir` default and lack of validation at `initialize`, which is the core reused bug class from the analog. Given the residual uncertainty on cap semantics and reliance on DAO sequencing, I'd flag this analog as speculative-but-plausible; the audit reviewer should verify cap-check logic in `market.clar` before treating this as a confirmed finding.
