### Title
Snowbridge V1 outbound-queue fee calculation can truncate to zero, allowing free/underpriced messages to be committed for Ethereum delivery - ([File: bridges/snowbridge/pallets/outbound-queue/src/lib.rs])

### Summary
`Pallet::<T>::calculate_fee` in the Snowbridge V1 outbound-queue pallet performs a chain of fixed-point multiplications/divisions to convert an Ethereum-denominated cost into a native-currency `remote` fee that message senders must pay to have a command delivered to the Ethereum Gateway. Under attacker-influenceable but otherwise "valid" pricing parameters, this computation can round down to zero even though all inputs are non-zero, as demonstrated by the pallet's own test `test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero`. This is a direct analog of the reported `getPrice()` bug: a public entrypoint's price/fee function can return `0`, letting an unprivileged caller obtain paid-for work (queued, committed Ethereum-bound messages, each carrying a promised relayer reward) essentially for free.

### Finding Description
`Pallet::<T>::calculate_fee` (called from the public `SendMessage::validate` implementation in `send_message_impl.rs`, reachable by any parachain/XCM user exporting a message to Ethereum) computes: [1](#0-0) 

```
fee = calculate_remote_fee(gas_used_at_most, fee_per_gas, reward)      // U256, in Ether units
fee = fee.try_into::<u128>()                                          // downcast
fee = FixedU128::from_inner(fee) * multiplier / exchange_rate          // fixed-point convert to native currency
fee = convert_from_ether_decimals(fee)                                 // rescale decimals
Fee { local: calculate_local_fee(), remote: fee }
```

The pallet's own unit test proves that, with a perfectly valid, non-zero `PricingParameters` set (`exchange_rate = 1/1`, `fee_per_gas = 1`, `rewards.remote = 1`, `multiplier = 1/1`), the resulting `fee.remote` truncates to `0`: [2](#0-1) 

The test comment itself states: *"Though none zero pricing params the remote fee calculated here is invalid which should be avoided"* — i.e. the maintainers are aware this is a broken invariant, but no guard exists to reject or revert when the computed remote fee rounds to zero (analogous to `getPrice()` silently returning `0` instead of reverting).

Crucially, the value charged to the sender (`fee.remote`) is **decoupled** from the reward that is actually promised to relayers in the committed message. When the message is later processed in `do_process_message`, the committed `reward` field is taken directly from the *live* governance parameter `pricing_params.rewards.remote` (raw ETH amount), not from whatever `fee.remote` was actually collected at submission time: [3](#0-2) 

So whenever the decimal-conversion math causes `fee.remote` to round down to `0` for a given `(exchange_rate, fee_per_gas, multiplier, gas_used_at_most)` combination — which the exchange rate is periodically updated by governance and can transiently pass through low-magnitude/edge values — any unprivileged user can call `validate`/`deliver` (via `ExportMessage`/XCM) to enqueue arbitrarily many Ethereum-bound commands while paying zero remote fee, yet each committed message still nominally promises `rewards.remote` to a relayer and consumes `MaxMessagesPerBlock` capacity in the outbound queue: [4](#0-3) 

### Impact Explanation
This matches the "public underpriced work that degrades block production or stalls bridge processing" category. Because remote-fee collection can silently degrade to zero:
- Attackers can spam the outbound queue with (almost) free messages, consuming the fixed per-block message capacity (`T::MaxMessagesPerBlock`) and crowding out legitimate governance/user messages, degrading bridge throughput.
- The bridge economics break: relayers are nominally promised `rewards.remote` from governance-fixed pricing parameters on the Ethereum side regardless of whether the actual fee collected from the sender covered it, so the queue silently fills with underfunded commitments.
- No explicit revert or floor guard exists on the returned zero fee, unlike a defensively coded system that would reject the submission outright — mirroring the original `getPrice()` bug exactly.

### Likelihood Explanation
The bug is proven to be reachable with parameters that pass all existing sanity checks (`exchange_rate` non-zero, `fee_per_gas` non-zero, `reward` non-zero) — no special/malicious governance action is required, only ordinary parameter values that can occur as ETH/DOT exchange rates or gas prices evolve over time. The path from an unprivileged XCM sender to `calculate_fee` is a normal, non-privileged code path (`send_message_impl.rs::validate`), so exploitation requires no admin, relayer, or validator collusion.

### Recommendation
- In `calculate_fee`, explicitly reject (return `SendError`) or floor to a minimum non-zero value whenever the computed `remote` fee (or `total()`) is zero while inputs (`fee_per_gas`, `reward`, `gas_used_at_most`) are non-zero, rather than silently returning `0`.
- Ensure the reward promised in the committed message (`do_process_message`) can never exceed what was actually collected from the sender at `validate` time (bind the committed `reward`/`max_fee_per_gas` to the fee actually paid, not just the live governance parameter).
- Add a regression test asserting that `SendMessage::validate` fails (rather than succeeding with fee 0) whenever `calculate_fee` would produce a zero remote component.

### Proof of Concept
The existing test in the repository already reproduces the underlying arithmetic bug: [2](#0-1) 

To weaponize it end-to-end: set `PricingParameters` (via governance `set_pricing_parameters`, a normal periodic operation, not privileged-abuse) to values in this zero-rounding regime, then call `SendMessage::validate`/`deliver` (e.g. through `pallet_xcm::send` with an `ExportMessage` to `Ethereum`) as any unprivileged account. `validate` returns `Fee { local: <small>, remote: 0 }`; the sender pays only the negligible `local` component, yet `deliver` successfully enqueues the message, and `do_process_message` commits it with `reward = pricing_params.rewards.remote` (non-zero, taken from governance state) into `Messages`/`MessageLeaves`, consuming outbound-queue capacity at effectively zero remote cost to the sender — repeatable without bound up to `T::MaxMessagesPerBlock` per block.

Note: I could not fully trace, within the available index, the exact runtime configuration flow that charges `fee.local`/`fee.remote` to the sender's account in the current parachain runtimes (e.g., bridge-hub-westend), so the precise on-chain accounting path for the `local` fee component is not fully verified here; a Devin session with full repository access would be needed to confirm end-to-end fee debiting logic in the production runtime configs.

		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

#[test]
fn test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero() {
	new_tester().execute_with(|| {
		let gas_used: u64 = 250000;
		let price_params: PricingParameters<<Test as Config>::Balance> = PricingParameters {
			exchange_rate: FixedU128::from_rational(1, 1),
			fee_per_gas: 1_u32.into(),
			rewards: Rewards { local: 1_u32.into(), remote: 1_u32.into() },
			multiplier: FixedU128::from_rational(1, 1),
		};
		let fee = OutboundQueue::calculate_fee(gas_used, price_params.clone());
		assert_eq!(fee.local, 698000000);
		// Though none zero pricing params the remote fee calculated here is invalid
		// which should be avoided
		assert_eq!(fee.remote, 0);
	});
}
