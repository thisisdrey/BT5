### Title
Unauthenticated broadcast requests write full transactions into an unbounded in-memory queue before signature validation, enabling storage exhaustion - (File: `framework/src/main/java/org/tron/core/db/Manager.java`)

### Summary
`Manager.pushTransaction()` unconditionally inserts every incoming `TransactionCapsule` into `pushTransactionQueue` — an unbounded `LinkedBlockingQueue` — before it calls `trx.validateSignature(...)`. This mirrors the Horizon regression (CVE-2026-43002 / CWE-696): a stateful write to a shared backend occurs before the request is authenticated, so unauthenticated/invalid requests can still consume storage/memory.

### Finding Description
`pushTransactionQueue` is declared as an unbounded queue: [1](#0-0) 

In `pushTransaction()`, the transaction is added to this queue and a metric is incremented *before* any cryptographic signature check occurs; the removal only happens in the `finally` block after `validateSignature` runs: [2](#0-1) [3](#0-2) 

This path is reachable directly from the unauthenticated public API: `Wallet.broadcastTransaction()` accepts a raw, potentially unsigned or garbage-signed `Transaction` from HTTP/gRPC/JSON-RPC callers and forwards it to `dbManager.pushTransaction(trx)`: [4](#0-3) 

The only guard against overload is `dbManager.isTooManyPending()`, which is checked in `Wallet.broadcastTransaction()` *before* calling `pushTransaction`: [5](#0-4) 

and computed from the *current* queue size at check time: [6](#0-5) 

Because the check (`isTooManyPending`) and the write (`pushTransactionQueue.add`) are not atomic with respect to each other across concurrent requests, this is a classic check-then-act (TOCTOU) race: many concurrent HTTP/gRPC callers can all pass the size check simultaneously and then all add their (potentially unsigned/invalid) transactions to the unbounded queue before any of them reach the `validateSignature` call that would normally reject them. Each queued entry retains the full serialized `Transaction` payload (up to `TRANSACTION_MAX_BYTE_SIZE`) in memory for the duration of signature verification (which itself can be relatively expensive per the `logSlowSigVerify` slow-path warning present in the same class): [7](#0-6) 

This is functionally identical to the Horizon bug class: a write to shared, size-limited storage (the pending-queue counted by `isTooManyPending`) happens before the operation is authenticated (`validateSignature`), so the enforcement mechanism intended to bound resource usage can be bypassed by unauthenticated, unsigned or forged-signature submissions racing the check.

### Impact Explanation
An anonymous API client (no valid account, no valid signature required) can send a burst of concurrent `broadcastTransaction` calls (via `BroadcastHexServlet`/gRPC/JSON-RPC) with syntactically valid but unsigned or bogus-signature transactions. Each such transaction is queued in `pushTransactionQueue` before rejection, so a sufficiently large number of concurrent connections can push the queue well beyond `maxTransactionPendingSize`, consuming node heap memory for full transaction payloads and metrics. This is a resource-exhaustion / soft-DoS condition on the node process, potentially degrading or halting its ability to accept legitimate broadcast traffic — an "API the node can no longer serve" class impact.

### Likelihood Explanation
Reaching this code requires nothing beyond forming a syntactically valid `Transaction` protobuf (one contract, arbitrary/garbage signature bytes of the correct length) and issuing many concurrent HTTP/gRPC broadcast requests — no private key, no funded account, no prior authorization. The `RateLimiterServlet` base class may throttle a single client/IP, but the queue is shared node-wide, so distributing the requests across many source IPs/connections defeats per-connection limiting. The TOCTOU window is small but exploitable at scale, and the underlying architectural flaw (write to shared bounded-by-convention state before auth) is deterministic and always present in the order of operations.

### Recommendation
Perform signature/permission validation (and any other authentication of the transaction) before adding the transaction to `pushTransactionQueue`, or use an atomic bounded structure (e.g., `LinkedBlockingQueue` constructed with a fixed capacity, or an atomic counter reserved before the add and released on rejection) so that `isTooManyPending()` and the enqueue operation cannot be bypassed by concurrent racers. Alternatively, move the pending-size check and increment into a single atomic operation performed as part of `pushTransactionQueue.add`, rejecting the add outright when capacity is already reached rather than checking size beforehand in a separate call.

### Proof of Concept
1. Craft N syntactically valid `Transaction` protobufs, each with one `TransferContract`, arbitrary owner/to addresses, and a signature list containing correctly-sized but cryptographically invalid signature bytes (so `SignUtils.isValidLength` passes but `validateSignature` will ultimately fail).
2. From many concurrent client connections (bypassing any single-IP `RateLimiterServlet` throttling by using multiple source addresses), simultaneously POST these transactions to `/wallet/broadcasthex` (or the gRPC/JSON-RPC broadcast equivalent) faster than `maxTransactionPendingSize` (default 2000) worth of signature-verification round trips can be drained.
3. Observe that `Manager.getCachedTransactionSize()` / `pushTransactionQueue` size grows past the configured `maxTransactionPendingSize` threshold during the burst, since every request's `pushTransactionQueue.add(trx)` executes before its `validateSignature` check, and `isTooManyPending()` was evaluated on a stale (pre-add) count for many of the concurrent requests.
4. With a large enough burst of unauthenticated/invalid transactions, memory consumption from queued full transaction payloads rises proportionally to the number of concurrent unauthenticated requests rather than being capped at `maxTransactionPendingSize`, demonstrating the write-before-auth resource-exhaustion condition.

  public GrpcAPI.Return broadcastTransaction(Transaction signedTransaction) {
    GrpcAPI.Return.Builder builder = GrpcAPI.Return.newBuilder();
    TransactionCapsule trx = new TransactionCapsule(signedTransaction);
    trx.setTime(System.currentTimeMillis());
    Sha256Hash txID = trx.getTransactionId();
    try {
      for (ByteString sig : signedTransaction.getSignatureList()) {
        if (!SignUtils.isValidLength(sig.size())) {
          String info = "Signature size is " + sig.size();
          logger.warn("Broadcast transaction {} has failed, {}.", txID, info);
          return builder.setResult(false).setCode(response_code.SIGERROR)
              .setMessage(ByteString.copyFromUtf8("Validate signature error: " + info))
              .build();
        }
      }

      if (tronNetDelegate.isBlockUnsolidified()) {
        logger.warn("Broadcast transaction {} has failed, block unsolidified.", txID);
        return builder.setResult(false).setCode(response_code.BLOCK_UNSOLIDIFIED)
          .setMessage(ByteString.copyFromUtf8("Block unsolidified."))
          .build();
      }

      if (minEffectiveConnection != 0) {
        if (tronNetDelegate.getActivePeer().isEmpty()) {
          logger.warn("Broadcast transaction {} has failed, no connection.", txID);
          return builder.setResult(false).setCode(response_code.NO_CONNECTION)
              .setMessage(ByteString.copyFromUtf8("No connection."))
              .build();
        }

        int count = (int) tronNetDelegate.getActivePeer().stream()
            .filter(p -> !p.isNeedSyncFromUs() && !p.isNeedSyncFromPeer())
            .count();

        if (count < minEffectiveConnection) {
          String info = "Effective connection:" + count + " lt minEffectiveConnection:"
              + minEffectiveConnection;
          logger.warn("Broadcast transaction {} has failed. {}.", txID, info);
          return builder.setResult(false).setCode(response_code.NOT_ENOUGH_EFFECTIVE_CONNECTION)
              .setMessage(ByteString.copyFromUtf8(info))
              .build();
        }
      }

      if (dbManager.isTooManyPending()) {
        logger.warn("Broadcast transaction {} has failed, too many pending.", txID);
        return builder.setResult(false).setCode(response_code.SERVER_BUSY)
            .setMessage(ByteString.copyFromUtf8("Server busy.")).build();
      }

      if (trxCacheEnable) {
        if (dbManager.getTransactionIdCache().getIfPresent(txID) != null) {
          logger.warn("Broadcast transaction {} has failed, it already exists.", txID);
          return builder.setResult(false).setCode(response_code.DUP_TRANSACTION_ERROR)
              .setMessage(ByteString.copyFromUtf8("Transaction already exists.")).build();
        } else {
          dbManager.getTransactionIdCache().put(txID, true);
        }
      }

      if (chainBaseManager.getDynamicPropertiesStore().supportVM()) {
        trx.resetResult();
      }
      if (trx.getInstance().getRawData().getContractCount() == 0) {
        throw new ContractValidateException(ActuatorConstant.CONTRACT_NOT_EXIST);
      }
      trx.checkExpiration(chainBaseManager.getNextBlockSlotTime());
      dbManager.pushTransaction(trx);
