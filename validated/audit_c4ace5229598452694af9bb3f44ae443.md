### Title
Adaptive concurrency limiter increases admission ceiling from spot, two-sample resource checks that an attacker can pace around - ([File: internal/limiter/adaptive_calculator.go])

### Summary
Gitaly's adaptive concurrency limiter (`AdaptiveCalculator`) raises the number of admitted concurrent RPCs every calibration tick based solely on whether a single, coarse, two-sample resource condition fired since the last tick — not on any sustained or averaged measure of actual load or of how much of the increased capacity is genuinely idle. An attacker who paces resource-heavy Git operations (large clones/pushes/`PostUploadPackWithSidechannel`, `ReceivePack`, etc.) so that CPU-throttle/memory-anon ratios never cross the two-poll delta thresholds at exactly the sampled instants can keep the "no backoff event" condition true, causing the limiter to continuously ratchet its ceiling upward (`limit = limit + 1` every `CalibrationInterval`) while the node is, in reality, persistently near-saturated for legitimate users. This mirrors the reported bug class: a rate/limit-governing decision is derived from a manipulable, instantaneous (spot) sample rather than a time-averaged/sustained one, letting an attacker game the sampling boundary to obtain a more favorable (here, higher) limit than true load warrants.

### Finding Description
The `AdaptiveCalculator.calibrateLimits` function performs additive-increase/multiplicative-decrease (AIMD) on the shared concurrency limits used by `ConcurrencyLimiter` (per-RPC and pack-objects limiters): [1](#0-0) 

If `lastBackoffEvent` is `nil` at the moment of the `CalibrationInterval` tick (default 30s, see `DefaultCalibrateFrequency`), every managed limit is incremented by one, unconditionally — with no check on current queue depth, in-flight count, or whether the extra capacity is actually needed: [2](#0-1) 

Whether a backoff event fires is decided by conditions that compare only two consecutive poll samples against a fixed ratio threshold: [3](#0-2) [4](#0-3) 

The underlying `LoadMonitor` itself only samples cgroup stats every `PollInterval` (default 10s) and diffs the two most recent samples: [5](#0-4) 

Because the decision to grow the concurrency ceiling depends on a comparison of exactly two 10-second-apart snapshots against a static ratio (e.g. 50% CPU-throttle, 60% memory-anon), an attacker who controls the timing/intensity of their own resource-heavy Git RPCs can keep the measured delta just under threshold at the sampled instants (e.g., by bursting compute between polls and idling briefly around poll boundaries) while still consuming enough sustained resources to degrade service for other tenants sharing the node/repository quota. Each 30-second calibration round with "no backoff event" grants +1 to the global admitted concurrency for the targeted RPC, up to `Max`, amplifying the number of expensive concurrent Git subprocesses the limiter will admit — working directly against the purpose of `doc/backpressure.md`'s stated goal that Gitaly "shouldn't subserviently agree to process more than it can handle": [6](#0-5) 

This is the same root-cause shape as the reported DeFi bug: an economically/resource-significant threshold decision (interest rate / concurrency ceiling) is derived from an instantaneous, two-point sample of a manipulable signal (utilization ratio / CPU-throttle ratio) rather than a time-averaged one, and the decision compounds (locked-in stable rate / ratcheted-up limit) beyond the manipulation window.

### Impact Explanation
An attacker exploiting this gap can cause the concurrency ceiling for expensive RPCs (e.g. pack-objects, `ReplicateRepository`, `PostUploadPackWithSidechannel`) to be raised beyond what the node can safely sustain, while genuinely keeping the node under real, sustained resource pressure between the sampled instants. This increases the number of concurrently admitted heavy Git subprocesses, worsening contention, increasing latency/timeouts, and potentially triggering OOM or severe throttling for legitimate concurrent users — i.e., DoS of the RPC handler resource-limiting mechanism itself, which is precisely the mechanism meant to protect Gitaly from being overwhelmed.

### Likelihood Explanation
Exploitation only requires an ordinary, unprivileged client capable of issuing repeated Git operations (clone/fetch/push) against a Gitaly node — no privileged access, leaked tokens, or MITM position is needed. The attacker needs some ability to observe or infer the polling cadence (fixed defaults: 10s poll / 30s calibration, both visible in shipped config/documentation), which is a moderate but feasible bar, especially in shared/multi-tenant Gitaly deployments where an external actor can send traffic against their own repositories to affect node-wide limiter state.

### Recommendation
- Base the additive-increase/backoff decision on a time-averaged or sustained-window signal (e.g., require the "no backoff" condition to hold across multiple consecutive polls, or use PSI `avg60`/`avg300` rather than a single two-poll delta) rather than a single two-sample comparison.
- Cap the rate of ceiling growth relative to actual observed queueing/demand (e.g., don't increment the limit if there is no queuing pressure for that limit), similar to how classic AIMD/TCP congestion control ties growth to observed utilization rather than blind periodic increments.
- Consider correlating the `BurdenMonitor`'s per-RPC/per-repo resource tracking with the calibration decision so that an individual noisy client (or repository) doesn't get to raise a shared, global limit that benefits all admitted callers.

### Proof of Concept
Conceptual PoC (no code execution available in this environment):
1. An attacker issues expensive Git operations (e.g., repeated `git-upload-pack`/`git-receive-pack` invocations against a large or crafted repository) in bursts timed to the known/observed `PollInterval` (10s) and `CalibrationInterval` (30s) boundaries, keeping the CPU-throttle-duration delta and memory-anon ratio measured at each two-poll comparison just below `defaultCPUThrottlingThreshold` (0.5) / `defaultMemoryThreshold` (0.6) — see `internal/limiter/condition_cpu.go` and `internal/limiter/condition_memory.go`.
2. Because `lastBackoffEvent` stays `nil` at each 30s calibration tick, `AdaptiveCalculator.calibrateLimits` performs `newLimit = limit.Current() + 1` every round (`internal/limiter/adaptive_calculator.go:261-270`), ratcheting the concurrency ceiling for the targeted RPC/pool upward toward `Max` even though the node is under genuine, near-continuous resource pressure between samples.
3. With the ceiling raised, the attacker (and/or other concurrent clients) can push more concurrently admitted heavy Git subprocesses through `ConcurrencyLimiter.Limit` (`internal/limiter/concurrency_limiter.go:197-241`) than the node can safely sustain, degrading service for legitimate users until a large enough single spike finally trips the multiplicative-decrease path — by which time damage/contention has already occurred.

// newCPUThrottlingCondition returns a Condition that evaluates to true when CPU throttling occurred for more than 50% of the
// time between the last 2 polls.
func newCPUThrottlingCondition(threshold float64) loadmonitor.Condition {
	if threshold <= 0.0 {
		threshold = defaultCPUThrottlingThreshold
	}

	return loadmonitor.Condition{
		Name: conditionCgroupCPU,
		Fn: func(ctx context.Context, previous, current loadmonitor.Stats, pollInterval time.Duration) (bool, string) {
			cur, prev := current.CGroup.ParentStats, previous.CGroup.ParentStats

			// Somehow, cgroup stats are reset. It's usually the consequence of cgroup limits being changed.
			// Alternatively, they can be overridden by another program.
			// Either way, the watcher should update the stats accordingly.
			if cur.CPUThrottledCount < prev.CPUThrottledCount || cur.CPUThrottledDuration < prev.CPUThrottledDuration {
				return false, ""
			}

			throttledDuration := cur.CPUThrottledDuration - prev.CPUThrottledDuration

			// If the total throttled duration since the last poll exceeds 50%.
			if pollInterval > 0 && throttledDuration/pollInterval.Seconds() > threshold {
				return true, eventCPUThrottling
			}
			return false, ""
		},
	}

// newMemoryUsageCondition evaluates to `true` in 2 conditions:
// * The current memory usage exceeds a soft threshold.
// * The cgroup is under OOM.
func newMemoryUsageCondition(threshold float64) loadmonitor.Condition {
	if threshold <= 0.0 {
		threshold = defaultMemoryThreshold
	}

	return loadmonitor.Condition{
		Name: conditionCgroupMemory,
		Fn: func(ctx context.Context, previous, current loadmonitor.Stats, pollInterval time.Duration) (bool, string) {
			if current.CGroup.ParentStats.UnderOOM {
				return true, eventMemoryOOM
			}

			// This check is to avoid a division by 0 below
			if current.CGroup.ParentStats.MemoryLimit == 0 {
				return false, ""
			}

			anonRatio := float64(current.CGroup.ParentStats.TotalAnon) / float64(current.CGroup.ParentStats.MemoryLimit)
			if anonRatio >= threshold {
				return true, eventMemoryAnon
			}
			return false, ""
		},
	}
}

// poll Polls the StatsProvider to get resource usage information.
// It then sets the previous and current Stats on the Monitor, which
// will be used to evaluate the consumer's Condition.
// This method is not thread safe
func (m *DefaultMonitor) poll() error {
	// Record the time right before polling
	now := time.Now()

	// Poll the cgroups stats
	cgroupStats, err := m.cgroupManager.Stats()
	if err != nil {
		return fmt.Errorf("polling cgroup stats failed: %w", err)
	}

	// There is no need to lock access to the state here because poll is called
	// synchronously before notify
	if m.state.lastPoll.IsZero() {
		// This is the first poll, set the previous state to the current state.
		m.state.previousStats.CGroup = cgroupStats
	} else {
		m.state.previousStats = m.state.currentStats
		m.state.lastPollInterval = now.Sub(m.state.lastPoll)
	}

	m.state.currentStats.CGroup = cgroupStats
	m.state.currentStats.pollTime = now
	m.state.lastPoll = now
	return nil
}
