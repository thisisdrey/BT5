## Analog Identified: Nomination Pools reward dust accumulates in the reward pool account with no way to sweep it while the pool remains active

### Title
Nomination Pools reward-counter rounding dust is permanently stranded in the pool reward account until pool destruction, with no sweep mechanism during normal operation - (File: `substrate/frame/nomination-pools/src/lib.rs`)

### Summary
`pallet-nomination-pools` distributes staking rewards to members via a `RewardCounter` (a `FixedU128`-based ratio) that is multiplied against each member's points in `PoolMember::pending_rewards` [1](#0-0) . Because this computation always rounds down, every `claim_payout` leaves a small remainder ("dust") behind in the pool's dedicated reward account. This is the same broken invariant as the M-10 report: reward-rate/reward-share division always leaves stuck value with no dedicated sweep entry point.

### Finding Description
The nomination-pools tests explicitly document that dust remains stuck in the reward account after every member claims their share, e.g. `rewards_are_rounded_down_depositor_collects_them` shows one unit of dust left over after both members claim [2](#0-1) . The `do_try_state` sanity check for the pallet explicitly acknowledges that "the reward math rounds down, we might accumulate some dust" in the reward account balance [3](#0-2) .

Crucially, during *normal* pool operation (pool active, not being destroyed), there is no public or privileged extrinsic that sweeps this accumulated dust out of the reward account back to the pool or to any beneficiary — the only place a leftover-sweep to the depositor exists is inside the one-time storage migration `migration.rs`, which pays any residual `accumulated_reward - sum_paid_out` to the depositor [4](#0-3) . That path only runs once, as part of a historical version migration, not as an ongoing recovery mechanism for a live pool. For a pool that stays active indefinitely (the common real-world case — nomination pools are meant to be long-lived), each `deposit_rewards`/`claim_payout` cycle can leave dust behind (as shown across `rewards_distribution_is_fair_basic_with_fractions` and `if_small_member_waits_long_enough_they_will_earn_rewards`, where sub-unit rewards are simply forfeited to the reward pool balance instead of paid out) [5](#0-4) [6](#0-5) , and this value compounds over the lifetime of the pool with no extrinsic to reclaim it.

This directly mirrors the external report's root cause: "the contract has no function to recover tokens lost due to precision" — here, the pallet has no call to recover reward-counter rounding dust from an active reward pool account.

### Impact Explanation
Per-cycle dust is bounded by the number of members and the `FixedU128` precision (`10^18`), so any single rounding event is small. However, because reward payouts happen continuously (potentially every block/era for active pools with rewards streaming in) and there is no sweep call, the value compounds over the pool's lifetime and is permanently unreachable by anyone (not the depositor, not root, not the members) unless the pool is fully destroyed — at which point only the *migration*-style leftover logic runs, and even that path is not present as a general-purpose recovery extrinsic in current `lib.rs` for a live, non-destroying pool. This matches the "permanent user-fund... lock" impact class, though the magnitude is small per pool and does not affect chain safety, consensus, or unauthorized fund movement.

### Likelihood Explanation
This occurs deterministically on every reward distribution cycle for any active nomination pool — no attacker action, privileged actor, or malicious party is required; it's a natural consequence of `Perbill`/`FixedU128` rounding-down semantics in `pending_rewards` and `current_reward_counter`. The pallet's own tests and `try_state` checks already confirm dust accumulation is expected and observed [3](#0-2) .

### Recommendation
Add a permissionless or root-gated `sweep_reward_dust` extrinsic (or fold dust reclaim into `claim_commission`/an existing maintenance call) that transfers any reward-account balance strictly above `ExistentialDeposit` and above the sum of all members' outstanding `pending_rewards` to a designated beneficiary (e.g., pool depositor or treasury), analogous to the leftover-payout logic already implemented for the one-time migration path.

### Proof of Concept
1. Create a pool with two members holding unequal points (e.g., 10 and 20, as in the existing test) [7](#0-6) .
2. Call `deposit_rewards(40)` to add rewards to the pool's reward account.
3. Both members call `claim_payout`; due to rounding, one unit remains in the reward account instead of being distributed [8](#0-7) .
4. Repeat steps 2-3 for many reward cycles while the pool stays active (never destroyed) — the dust compounds each cycle.
5. Observe there is no extrinsic in `pallet-nomination-pools`'s current dispatchables to reclaim this accumulated balance from the still-active reward account; it is only ever paid out via the one-off migration code path shown at `migration.rs` lines 1032-1044, which does not apply to a live pool.

**Caveat:** This is a pre-existing, already-tested, low-severity behavior (the pallet's own test suite and `try_state` invariant checks explicitly document and tolerate the dust), not a previously unknown defect — comparable to the original M-10 report, which the audited team also acknowledged but chose not to fix due to low severity. I present it as the closest genuine local analog satisfying the "permanent fund lock, no sweep function" bug class from the seed report, but note it does not rise to a chain-safety or unauthorized-execution issue.

impl<T: Config> PoolMember<T> {
	/// The pending rewards of this member.
	fn pending_rewards(
		&self,
		current_reward_counter: T::RewardCounter,
	) -> Result<BalanceOf<T>, Error<T>> {
		// accuracy note: Reward counters are `FixedU128` with base of 10^18. This value is being
		// multiplied by a point. The worse case of a point is 10x the granularity of the balance
		// (10x is the common configuration of `MaxPointsToBalance`).
		//
		// Assuming roughly the current issuance of polkadot (12,047,781,394,999,601,455, which is
		// 1.2 * 10^9 * 10^10 = 1.2 * 10^19), the worse case point value is around 10^20.
		//
		// The final multiplication is:
		//
		// rc * 10^20 / 10^18 = rc * 100
		//
		// the implementation of `multiply_by_rational_with_rounding` shows that it will only fail
		// if the final division is not enough to fit in u128. In other words, if `rc * 100` is more
		// than u128::max. Given that RC is interpreted as reward per unit of point, and unit of
		// point is equal to balance (normally), and rewards are usually a proportion of the points
		// in the pool, the likelihood of rc reaching near u128::MAX is near impossible.

		(current_reward_counter.defensive_saturating_sub(self.last_recorded_reward_counter))
			.checked_mul_int(self.active_points())
			.ok_or(Error::<T>::OverflowRisk)
	}
