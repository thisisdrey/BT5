### Title
Unbounded Full-Scan Asset-Issue Query Endpoints Enable API DoS - ([File: framework/src/main/java/org/tron/core/Wallet.java])

### Summary
`Wallet.getAssetIssueList()`, `Wallet.getAssetIssueListByName(...)`, and `Wallet.getAssetIssueByAccount(...)` each load the entire set of on-chain asset issues into memory via `AssetIssueStore.getAllAssetIssues()` and then iterate over the whole list to run bandwidth-usage recalculation, with no pagination or upper bound. These methods are exposed to any anonymous caller through unauthenticated HTTP and gRPC endpoints.

### Finding Description
`AssetIssueStore.getAllAssetIssues()` streams every entry out of the asset-issue key-value store into a `List<AssetIssueCapsule>` with no size limit: [1](#0-0) 

`Wallet.getAssetIssueList()` calls this unbounded getter and then, for every single asset issue, invokes `BandwidthProcessor.updateUsage(...)` (which does further processing per asset) before adding it to the response: [2](#0-1) 

The same unbounded pattern (`getAllAssetIssues()` followed by a full linear scan/filter and per-item `updateUsage`) is repeated in `getAssetIssueByAccount` and `getAssetIssueListByName`: [3](#0-2) [4](#0-3) 

Unlike `getAssetIssueList(offset, limit)`, which delegates to the store's paginated helper that clamps `limit` to `ASSET_ISSUE_COUNT_LIMIT_MAX`: [5](#0-4) 
the no-argument/no-pagination variants (`getAssetIssueList()`, `getAssetIssueListByName`, `getAssetIssueByAccount`) have no such bound.

These unbounded methods are directly reachable by any unauthenticated HTTP/gRPC client:
- `GetAssetIssueListServlet.doGet` calls `wallet.getAssetIssueList()` with no parameters at all: [6](#0-5) 
- `GetAssetIssueByAccountServlet.fillResponse` calls `wallet.getAssetIssueByAccount(address)`: [7](#0-6) 
- `GetAssetIssueListByNameServlet.fillResponse` calls `wallet.getAssetIssueListByName(...)`: [8](#0-7) 
- Equivalent gRPC handlers in `RpcApiService` (`getAssetIssueList`, `getAssetIssueListByName`) forward directly to the same unbounded `Wallet` methods: [9](#0-8) 

This mirrors the reported bug class exactly: a view/query function iterates a list whose size is controlled by prior on-chain state accumulation (here, the total count of `AssetIssueContract` transactions ever broadcast by any account) with no pagination or cap, so the amount of work the call performs grows unbounded over the life of the chain.

### Impact Explanation
As the total number of issued assets on the network grows (each created by an ordinary, unprivileged `AssetIssueContract` transaction that anyone can broadcast by paying the asset-issue fee), calls to `getassetissuelist`, `getassetissuebyaccount`, and `getassetissuelistbyname` become increasingly expensive: each request performs a full linear scan of every asset ever issued plus per-item bandwidth-usage recomputation and JSON/protobuf serialization of the entire result set. A single such request can consume disproportionate CPU/memory on the full node and block the servlet/gRPC thread handling it, degrading or denying the query service for legitimate API clients — an API-availability impact matching the "node can no longer serve an API" acceptance criterion.

### Likelihood Explanation
Likelihood is moderate: no privileged role is required, an unbounded number of unprivileged `AssetIssueContract` transactions plus repeated unauthenticated calls to these endpoints are sufficient to make the query arbitrarily expensive over time. It requires the asset-issue count to be pushed high (bounded practically by cumulative issuance fees) and then repeated calls to the unbounded endpoints to trigger heavy CPU/memory load; unlike the original report's per-name-unbounded array, here the unbounded dimension is store-wide across all names, but the reachability and lack-of-cap pattern are identical.

### Recommendation
Add pagination/limits to `Wallet.getAssetIssueList()`, `getAssetIssueByAccount`, and `getAssetIssueListByName` (or route them through the existing paginated helper in `AssetIssueStore` with an enforced `ASSET_ISSUE_COUNT_LIMIT_MAX`), and/or enforce a maximum on the number of asset issues that can be created network-wide/per-account, similar to the cap already used for `getAssetIssuesPaginated`.

### Proof of Concept
1. Repeatedly broadcast `AssetIssueContract` transactions (each unprivileged, requiring only the standard asset-issue fee) from many accounts to accumulate a very large number of entries in the `asset-issue`/`asset-issue-v2` stores.
2. Call the unauthenticated HTTP endpoint `GET /wallet/getassetissuelist` (or the gRPC `getAssetIssueList` / `getassetissuelistbyname` / `getassetissuebyaccount` equivalents).
3. Observe that `Wallet.getAssetIssueList()` invokes `AssetIssueStore.getAllAssetIssues()` [10](#0-9)  to materialize the full unbounded list and then runs `BandwidthProcessor.updateUsage` on every entry before returning the complete result, with no offset/limit applied, unlike the paginated sibling method.

  private List<AssetIssueCapsule> getAssetIssuesPaginated(List<AssetIssueCapsule> assetIssueList,
      long offset, long limit) {
    if (limit < 0 || offset < 0) {
      return null;
    }

    if (assetIssueList.size() <= offset) {
      return null;
    }
    assetIssueList.sort((o1, o2) -> {
      if (o1.getName() != o2.getName()) {
        return o1.getName().toStringUtf8().compareTo(o2.getName().toStringUtf8());
      }
      return Long.compare(o1.getOrder(), o2.getOrder());
    });
    limit = limit > ASSET_ISSUE_COUNT_LIMIT_MAX ? ASSET_ISSUE_COUNT_LIMIT_MAX : limit;
    long end = offset + limit;
    end = end > assetIssueList.size() ? assetIssueList.size() : end;
    return assetIssueList.subList((int) offset, (int) end);
  }

  public List<AssetIssueCapsule> getAssetIssuesPaginated(long offset, long limit) {
    return getAssetIssuesPaginated(getAllAssetIssues(), offset, limit);
  }

  public AssetIssueList getAssetIssueList() {
    BandwidthProcessor processor = new BandwidthProcessor(chainBaseManager);
    AssetIssueList.Builder builder = AssetIssueList.newBuilder();

    getAssetIssueStoreFinal(chainBaseManager.getDynamicPropertiesStore(),
        chainBaseManager.getAssetIssueStore(),
        chainBaseManager.getAssetIssueV2Store()).getAllAssetIssues()
        .forEach(
            issueCapsule -> {
              processor.updateUsage(issueCapsule);
              builder.addAssetIssue(issueCapsule.getInstance());
            });

  public AssetIssueList getAssetIssueByAccount(ByteString accountAddress) {
    if (accountAddress == null || accountAddress.isEmpty()) {
      return null;
    }

    List<AssetIssueCapsule> assetIssueCapsuleList =
        getAssetIssueStoreFinal(chainBaseManager.getDynamicPropertiesStore(),
            chainBaseManager.getAssetIssueStore(),
            chainBaseManager.getAssetIssueV2Store()).getAllAssetIssues();

    BandwidthProcessor processor = new BandwidthProcessor(chainBaseManager);
    AssetIssueList.Builder builder = AssetIssueList.newBuilder();
    assetIssueCapsuleList.stream()
        .filter(assetIssueCapsule -> assetIssueCapsule.getOwnerAddress().equals(accountAddress))
        .forEach(
            issueCapsule -> {
              processor.updateUsage(issueCapsule);
              builder.addAssetIssue(issueCapsule.getInstance());
            });

    return builder.build();
  }
