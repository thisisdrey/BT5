### Title
Cross-contract StackerDB chunk signature replay - unauthorized write via signature not bound to `smart_contract_id` (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` computes the signed digest only from `slot_id`, `slot_version`, and `data_hash` — it never includes the StackerDB's `smart_contract_id` (contract namespace). Consequently a legitimately-signed chunk for one StackerDB replica (e.g. one reward cycle's `signers-0-xxx`/`signers-1-xxx` contract) can be replayed verbatim into a *different* StackerDB replica whose configuration happens to assign the same signer address to the same `slot_id`, causing an unauthorized write of stale/foreign data under that signer's identity in a context the signer never authorized.

### Finding Description
The chunk-write authorization path is:
1. `libstackerdb/src/libstackerdb.rs::SlotMetadata::auth_digest()` (lines 159-166) hashes only `slot_id`, `slot_version`, `data_hash`. `sign()`/`verify()` operate purely on this digest. [1](#0-0) 
2. On write (`stackslib/src/net/stackerdb/db.rs::StackerDBTx::try_replace_chunk`), the code fetches `slot_validation.signer` for the **target contract's** slot table and checks `slot_desc.verify(&slot_validation.signer)`, plus version/size/write-count bounds — but the signature payload it verifies still never encodes which contract it belongs to. [2](#0-1) 
3. Likewise, `PeerNetwork::validate_received_chunk` (gossip/relay path) resolves `get_slot_signer(smart_contract_id, slot_id)` and calls `slot_metadata.verify(&addr)`, again using the contract-agnostic digest. [3](#0-2) 
4. The HTTP write endpoint `RPCPostStackerDBChunkRequestHandler::try_handle_request` accepts `contract_identifier` from the URL and a chunk body, and calls `tx.try_replace_chunk(&contract_identifier, &stackerdb_chunk.get_slot_metadata(), ...)` — an unauthenticated remote peer supplies the target contract, and the same signed bytes verify identically against any contract where the recovered address owns the same `slot_id`. [4](#0-3) 

Because Stacks signer-set StackerDB contracts are instantiated per reward cycle from the same fixed schema (`signers-0-xxx.clar` / `signers-1-xxx.clar`) with signer→slot assignments derived from the reward-cycle's signer set, it is common/likely for the same signer address to occupy the same `slot_id` across consecutive or repeated reward-cycle contracts (or across `.signers-0-N`/`.signers-1-N` pairs for the same cycle). This breaks the equality "signature authenticated for contract A" vs. "chunk stored as authentic for contract B": the signed digest carries no contract-scoping, so a chunk signed and published for one StackerDB instance is equally valid for any other instance sharing the same slot/signer mapping.

### Impact Explanation
An unprivileged network participant who has observed one legitimately-signed chunk (chunks are gossiped over P2P and served over unauthenticated HTTP GET `/v2/stackerdb/...`) can replay it into a different StackerDB contract instance, as long as the destination's slot table currently expects a lower `slot_version` for that `slot_id`. This is an unauthorized write to replicated network state: it stores data the signer did not sign for that context, and — via `handle_unsolicited_StackerDBPushChunk` / the HTTP relay path (`node.set_relay_message(StacksMessageType::StackerDBPushChunk(..))`) — the forged-for-that-contract chunk is further relayed/gossiped network-wide as if freshly authored. [5](#0-4)  This matches the "network-wide propagation of forged data" / "unauthenticated write to state or StackerDB" class in scope.

### Likelihood Explanation
Requires no privileged keys or node secrets: the attacker only needs to capture one publicly-served, validly-signed chunk (trivial via HTTP GET or passive P2P observation) and re-submit it against a different contract identifier where the signer/slot mapping coincides. Likelihood of the signer/slot coincidence depends on the specific reward-cycle-to-contract slot-assignment logic (in `stackslib/src/chainstate/stacks/boot/mod.rs`, referenced by `signers-0-xxx.clar`/`signers-1-xxx.clar`), which was not fully traced in this pass — I could not confirm from the available index whether slot assignment is guaranteed, likely, or merely possible to collide across contracts for the same address. This is the main residual uncertainty.

### Recommendation
Include the target `smart_contract_id` (and ideally a network/chain identifier) inside `SlotMetadata::auth_digest()` so that a signature is cryptographically bound to the specific StackerDB replica it was produced for, preventing cross-contract replay. This mirrors the report's recommended mitigation of scoping credit/authorization to the intended context rather than allowing reuse across contexts.

### Proof of Concept
1. Signer key `K` owns `slot_id = 3` in StackerDB contract `A` (e.g., `signers-0-cycleN.clar`) and also owns `slot_id = 3` in contract `B` (e.g., `signers-0-cycleN+1.clar`, or a different `.signers-1-*` variant with an overlapping signer-set ordering).
2. `K` legitimately signs and publishes chunk `data` for slot 3 in `A`, producing `SlotMetadata{slot_id:3, slot_version:1, data_hash, signature}` per `SlotMetadata::sign` (`libstackerdb/src/libstackerdb.rs:171-179`).
3. Attacker observes this chunk (via `GET /v2/stackerdb/.../A/3` or P2P gossip) and re-POSTs the identical `slot_id`, `slot_version`, `sig`, and `data` to `POST /v2/stackerdb/<B-address>/<B-contract>/chunks` — the URL sets `contract_identifier = B`.
4. `RPCPostStackerDBChunkRequestHandler::try_handle_request` calls `tx.try_replace_chunk(&B, &metadata, &data)`, which resolves `B`'s configured signer for slot 3 (also `K`), and `slot_desc.verify(&signer)` succeeds because `auth_digest()` never referenced `A` or `B`. The chunk is accepted into `B`'s replica store and relayed to `B`'s peers as authentic, even though `K` never signed anything for contract `B`.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Sign this slot metadata, committing to slot_id, slot_version, and
    /// data_hash.  Sets self.signature to the signature.
    /// Fails if the underlying crypto library fails
    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
