### Title
Division-Before-Multiplication Precision Loss in Legacy (Un-hardened) Resource-Limit Formulas Overstates Bandwidth/Energy Granted per Frozen TRX - (File: `chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java`, `chainbase/src/main/java/org/tron/core/db/ResourceProcessor.java`)

### Summary
The legacy (non-hardened) resource-limit calculation paths compute integer division (`frozeBalance / TRX_PRECISION`, or truncated intermediate ratios) *before* multiplying by the proportional weight/limit ratio, instead of multiplying first and dividing once at the end. This is exactly the "division before multiplication in fixed-point arithmetic" bug class from the external report, and it is reachable by any account that freezes/stakes TRX and is granted energy/bandwidth (i.e. via the `FreezeBalanceContract`/staking path processed at block application). The project's own hardening replacements (guarded by the `AllowHardenResourceCalculation` committee-controlled flag) confirm this is a genuine, previously-recognized precision defect — but the legacy formula remains live and is used whenever the flag is not enabled.

### Finding Description
In `EnergyProcessor.calculateGlobalEnergyLimit`:
```java
long energyWeight = frozeBalance / TRX_PRECISION;
return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
``` [1](#0-0) 

Here `frozeBalance / TRX_PRECISION` is an **integer division performed first**, truncating any fractional weight below `TRX_PRECISION` before it is ever multiplied by `totalEnergyLimit/totalEnergyWeight`. The mathematically correct order (multiply first, divide once at the end) is exactly what the "hardened" replacement performs:
```java
return BigInteger.valueOf(frozeBalance)
    .multiply(BigInteger.valueOf(totalLimit))
    .divide(BigInteger.valueOf(TRX_PRECISION).multiply(BigInteger.valueOf(totalWeight)))
    .longValueExact();
``` [2](#0-1) 

The project's own test explicitly demonstrates the discrepancy between the legacy truncate-then-multiply formula and the corrected multiply-then-divide formula:
```java
long expected = java.math.BigInteger.valueOf(10000L)
    .multiply(java.math.BigInteger.valueOf(totalEnergyLimit))
    .divide(java.math.BigInteger.valueOf(totalEnergyWeight))
    .longValueExact();
...
long buggy = 10000L * (totalEnergyLimit / totalEnergyWeight);
Assert.assertNotEquals(buggy, resultNew);
``` [3](#0-2) 

Similarly, `usageToBalance` in `RepositoryImpl` (used by TVM energy accounting) has the same legacy/hardened dichotomy:
```java
return (long) ((double) usage * totalWeight / totalLimit * TRX_PRECISION);
``` [4](#0-3) 
versus the BigInteger-hardened version performed above it in the same method.

The correct, safe path only executes when `hardenCalculation()`/`hardenResourceCalculation()` returns true, which is gated by the dynamic property `AllowHardenResourceCalculation` — a committee-proposal-controlled flag [5](#0-4) . Whenever that proposal has not been passed/activated on a given network, every account's energy/bandwidth limit derived from frozen balance is computed using the double/integer-truncating legacy formula, which loses precision in the division step performed ahead of the multiplication.

### Impact Explanation
`calculateGlobalEnergyLimit`/`calculateGlobalNetLimit`-family functions determine how much energy/bandwidth an account is entitled to consume for free based on frozen TRX, a core piece of the staking/resource-accounting model. Truncating the weight ratio before multiplying systematically discards fractional resource allowance for every account whose frozen balance is not an exact multiple of `TRX_PRECISION` (1,000,000 sun) relative to the network-wide weight/limit ratio. Because this computation runs for every account on every resource consumption check, it can:
- systematically under- or over-grant free bandwidth/energy across the whole validator/user set (resource-accounting inconsistency),
- create discrepancies between nodes if some have the hardening proposal active and others do not (implicit state divergence in derived resource accounting), and
- be leveraged by an attacker who structures frozen balances to specific values to gain disproportionately favorable energy/bandwidth ratios relative to what the "correct" (multiply-first) formula would grant, effectively obtaining free execution capacity (a form of unbacked resource allocation) at the expense of network-wide accounting fairness.

### Likelihood Explanation
Any account holder can freeze TRX for bandwidth/energy — an ordinary, unprivileged action reachable via a single signed transaction (`FreezeBalanceContract`) — and the resulting limit is computed by these vulnerable formulas whenever hardening is not enabled network-wide. No special privilege is required; the bug is triggered purely by the natural variety of frozen-balance amounts across accounts.

### Recommendation
Make the hardened (BigInteger, multiply-before-divide) formulas the sole implementation for `calculateGlobalEnergyLimit`, `calculateGlobalEnergyLimitV2`, `calculateGlobalNetLimit`, and `usageToBalance`, removing the legacy double/integer-truncating code paths entirely (or force `AllowHardenResourceCalculation` to be always-on) so that unmitigated, precision-losing math can never be reached in production regardless of proposal state.

### Proof of Concept
1. Ensure the dynamic property `AllowHardenResourceCalculation` is at its default/disabled state (proposal not yet activated).
2. Set `totalEnergyWeight = 1_234_567`, `totalEnergyLimit = 50_000_000_000`, and freeze a balance `frozeBalance` for energy such that `frozeBalance < TRX_PRECISION` fraction misaligns with `totalEnergyWeight` (e.g. `frozeBalance = 10_000_000_000`).
3. Call `EnergyProcessor.calculateGlobalEnergyLimit(account)`; observe the returned limit differs from the value computed via `BigInteger.valueOf(frozeBalance).multiply(BigInteger.valueOf(totalEnergyLimit)).divide(BigInteger.valueOf(TRX_PRECISION).multiply(BigInteger.valueOf(totalEnergyWeight)))`, exactly as asserted by the project's own regression test:
```java
long buggy = 10000L * (totalEnergyLimit / totalEnergyWeight);
Assert.assertNotEquals(buggy, resultNew);
``` [6](#0-5) 

This confirms the legacy path, still reachable by default (unhardened) accounting, produces the exact division-before-multiplication truncation described in the external report.
