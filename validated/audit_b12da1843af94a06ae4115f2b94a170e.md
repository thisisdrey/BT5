I need to verify the interplay between `debtFloorInUsd`, `maxLiquidable`, and whether issuance enforces the floor — that's the strongest analog (forced-close path blocked by internal checks).### Title
Liquidation permanently blocked when remaining debt would fall below `debtFloorInUsd` and full repayment exceeds `maxLiquidable` - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool.liquidate` is Metronome's only forced-close path for unhealthy debt positions, analogous to SymmIO's `emergencyClosePosition`. Two independent bounds inside it — the `maxLiquidable` cap and the `debtFloorInUsd` dust check — can conflict such that *every* possible `amountToRepay_` value reverts. Any account whose debt (in USD) lies in the dead zone `debtFloorInUsd < debtInUsd < debtFloorInUsd / (1 - maxLiquidable)` can never be liquidated once it becomes unhealthy, permanently freezing the collateral inside the pool and leaving the bad debt on the protocol.

### Finding Description
`liquidate` enforces two checks on `amountToRepay_` against the account's `DebtToken` balance `D`:

1. Liquidation cap: `amountToRepay_.wadDiv(D) > maxLiquidable` reverts, so `amountToRepay_ <= maxLiquidable * D` ([contracts/Pool.sol:567](contracts/Pool.sol#L567)).
2. Debt floor: if `0 < D - amountToRepay_ < debtFloorInUsd` it reverts with `RemainingDebtIsLowerThanTheFloor` ([contracts/Pool.sol:571-579](contracts/Pool.sol#L571)). The only exempt remainder is exactly `0`.

When `maxLiquidable < 1` (its sole purpose is to cap partial liquidations; `updateMaxLiquidable` allows any value `<= 1e18`, [contracts/Pool.sol:778](contracts/Pool.sol#L778)), repaying the full debt violates check 1. The best allowed repayment `maxLiquidable * D` leaves `(1 - maxLiquidable) * D`. If `(1 - maxLiquidable) * D < debtFloorInUsd`, i.e. `D < debtFloorInUsd / (1 - maxLiquidable)`, check 2 reverts for every permitted amount.

Concrete example with `maxLiquidable = 0.5e18`, `debtFloorInUsd = $3,000` (the same parameter values exercised in `test/Pool.test.ts:409-420`): any position with debt in `($3,000, $6,000)` that goes underwater is completely unliquidatable. A 50% repay leaves `$1,500–$3,000` of dust → `RemainingDebtIsLowerThanTheFloor`; a 100% repay exceeds `maxLiquidable` → `AmountGreaterThanMaxLiquidable`.

The attacker path is fully permissionless: `DebtToken.issue` mints debt against deposited collateral for any user, and positions in this band are legitimate to open (the floor only forbids debt *below* it). The attacker deposits collateral, issues debt inside the dead zone, and once collateral price drops the position is unhealthy but no liquidator can ever succeed — not partially, not fully. No privileged action, oracle manipulation, or trusted party is required; it relies only on the deployed parameter combination `maxLiquidable < 1` and `debtFloorInUsd > 0`, both of which exist precisely to bound liquidations.

Note: this is analogous to the referenced SymmIO finding — a forced-close path that reverts on an internal accounting precondition — but here the blocker is a hard revert on all inputs rather than an `allocatedBalance` shortfall, which is strictly worse since no workaround (like SymmIO's separate `settleUpnl`) exists.

### Impact Explanation
Permanent freezing of the collateral backing the position plus protocol insolvency risk: the unhealthy debt can never be cleared, so as interest accrues via `accrueInterest` the bad debt grows unbounded while the seized-able collateral stays stuck. The attacker can size the position up to just below `debtFloorInUsd / (1 - maxLiquidable)` per account and repeat across accounts. Ordinary users' positions can also drift into the dead zone organically (interest accrual, or a governance `updateDebtFloor` raise that pushes existing debt below `2x` the new floor), making them immune to liquidation and griefing liquidators with guaranteed reverts.

### Likelihood Explanation
Requires `maxLiquidable < 1e18` and `debtFloorInUsd > 0` to both be set — these are protocol features designed to be used together (partial-liquidation cap plus dust floor). The test suite itself exercises `debtFloor = $3,000` with `maxLiquidable` defaults and documents the `RemainingDebtIsLowerThanTheFloor` revert, confirming the code path is live. The attacker's cost is only the collateral for one position in the dead-zone band; no privileged role, oracle manipulation, or trusted-remote assumption is needed. Positions can also enter the dead zone without any attacker action via interest growth or floor increases.

### Recommendation
- Allow `amountToRepay_ == D` (full repayment) to bypass the `maxLiquidable` cap, or bypass the floor check when it would otherwise make all liquidation amounts revert.
- Alternatively, in the floor check, permit any repayment that results in `D - amountToRepay_ == 0` *or* `>= debtFloorInUsd`, and clamp the effective repayable amount to `min(maxLiquidable * D, D - dust)` only when that range is non-empty; when empty, fall back to allowing full liquidation.
- At minimum, `issue`/`leverage` should enforce `debtInUsd >= debtFloorInUsd / (1 - maxLiquidable)` so positions can never be created inside the dead zone.

### Proof of Concept
Hardhat sketch against deployed pool (fork):

```ts
// assumes pool.maxLiquidable() = 0.5e18, pool.debtFloorInUsd() = $3,000e18
// 1. attacker deposits MET collateral and issues debt D with $4,000 < usdValue(D) < $6,000
await msdMET.connect(attacker).deposit(collateral, attacker.address)
await msEthDebtToken.connect(attacker).issue(amountFor4000Usd, attacker.address)

// 2. collateral price drops -> position unhealthy
await masterOracle.updatePrice(met.address, toUSD('0.50'))
const { _isHealthy } = await pool.debtPositionOf(attacker.address) // false

// 3. every liquidation reverts
const D = await msEthDebtToken.balanceOf(attacker.address)
// partial: leaves $2,000 remainder < floor
await expect(pool.liquidate(msEth.address, attacker.address, D.div(2), msdMET.address))
  .revertedWithCustomError(pool, 'RemainingDebtIsLowerThanTheFloor')
// full: exceeds maxLiquidable
await expect(pool.liquidate(msEth.address, attacker.address, D, msdMET.address))
  .revertedWithCustomError(pool, 'AmountGreaterThanMaxLiquidable')
// any r in (0, maxLiquidable*D]: D - r in (0, floor) -> same revert; r=0 reverts AmountIsZero
// => position is permanently unliquidatable, collateral frozen, bad debt accrues
```
