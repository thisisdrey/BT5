### Title
Malicious `Operator.execute` target can impersonate the caller and withdraw collateral - ([File: contracts/Operator.sol](contracts/Operator.sol))

### Summary
`Operator.execute` stores the original caller in transient storage before executing every attacker-supplied call target. Any contract reached during that batch can call Metronome contracts and be authenticated as the original caller through `SynthContext._msgSender()`. A malicious call target can therefore invoke `DepositToken.withdraw()` as the victim and direct unlocked collateral to an attacker-controlled recipient. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`Operator.execute` writes `msg.sender` to `MSG_SENDER_STORAGE` once, executes every supplied `target.functionCallWithValue(...)`, and only clears the sender after the entire batch completes. [1](#0-0) [4](#0-3) 

Every contract inheriting `SynthContext` replaces `msg.sender == operator` with `operator.getActualMsgSender()`. [2](#0-1)  Consequently, while any user-supplied call target is executing, that target can make additional calls to Synth contracts and act with the victim's identity.

For example, the malicious target can call:

```solidity
depositToken.withdraw(victimUnlockedBalance, attacker);
```

`DepositToken.withdraw()` uses the forwarded `_msgSender()` as the account being debited, while `to_` is unrestricted. [3](#0-2)  `_withdraw()` then burns the victim's `DepositToken` balance and instructs `Treasury.pull()` to send the underlying collateral to the attacker. [5](#0-4)  `Treasury.pull()` performs the actual underlying-token transfer. [6](#0-5) 

The authorization context is therefore not scoped to the requested Metronome operation. It remains valid for arbitrary nested calls made by every target in the batch.

### Impact Explanation
A malicious contract included in an `Operator.execute` batch can steal all of the victim's currently unlocked collateral. The stolen withdrawal does not need an allowance, signature, or separate approval because `DepositToken.withdraw()` authenticates the call as though the victim invoked it directly. [3](#0-2) [7](#0-6) 

For a user with no outstanding debt, `unlockedBalanceOf()` returns the full deposit-token balance. [8](#0-7)  The same forwarded identity can also transfer unlocked `DepositToken` balances or perform other victim-authorized public actions. [9](#0-8) 

### Likelihood Explanation
The exploit only requires the victim to include one attacker-controlled contract in an `Operator.execute` batch. `Operator` explicitly accepts arbitrary targets and call data rather than restricting execution to known protocol contracts. [4](#0-3) 

`nonReentrant` does not prevent this attack because the malicious target does not reenter `Operator.execute`; it makes an ordinary external call to `DepositToken.withdraw()` while `MSG_SENDER_STORAGE` is still populated. [10](#0-9)  Likewise, the `onlyIfDepositTokenExists`, shutdown, unlocked-balance, and treasury checks do not block a legitimate withdrawal—the identity itself has been incorrectly delegated to the malicious target. [5](#0-4) 

### Recommendation
Do not allow arbitrary call targets to inherit the user's Synth identity.

At minimum, `Operator.execute` should only dispatch calls to an allowlist of protocol contracts that are intended to consume `SynthContext` authentication. If external calls such as oracle refreshes must remain supported, split them into unauthenticated helper calls or a separate execution path that does not expose `MSG_SENDER_STORAGE` to arbitrary contract code.

The documentation and user-facing calldata builder should also make explicit that every target in a batch receives complete caller authority for the duration of the transaction.

### Proof of Concept
A Hardhat reproduction can use the existing deployed-test fixture and an attacker-controlled target:

```solidity
// contracts/mock/OperatorIdentityThief.sol
pragma solidity 0.8.24;

import {IDepositToken} from "../interfaces/IDepositToken.sol";

contract OperatorIdentityThief {
    function steal(IDepositToken depositToken, uint256 amount, address thief) external {
        // When this is invoked through Operator.execute, DepositToken sees
        // _msgSender() as the victim who called Operator, not this contract.
        depositToken.withdraw(amount, thief);
    }
}
```

```ts
// test/Operator.identity.test.ts
it('lets an executed target impersonate the caller and steal collateral', async () => {
  const amount = parseUnits('100', 6)

  // Victim deposits USDC into a registered DepositToken.
  await usdc.connect(alice).approve(msdUSDC.address, amount)
  await msdUSDC.connect(alice).deposit(amount, alice.address)

  const thief = await ethers.getContractFactory('OperatorIdentityThief')
      .then((f) => f.connect(attacker).deploy())

  // Victim is induced to execute an apparently harmless call to the attack contract.
  await operator.connect(alice).execute([
    {
      target: thief.address,
      value: 0,
      callData: thief.interface.encodeFunctionData('steal', [
        msdUSDC.address,
        amount,
        attacker.address,
      ]),
    },
  ])

  expect(await msdUSDC.balanceOf(alice.address)).to.eq(0)
  expect(await usdc.balanceOf(attacker.address)).to.eq(amount)
})
```

Inside `OperatorIdentityThief.steal`, `DepositToken.withdraw()` resolves `_msgSender()` to Alice because the immediate caller is the configured `Operator` and the transient sender still contains Alice. [2](#0-1) [11](#0-10)
