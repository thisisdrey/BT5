### Title
Stale/uninitialized `accountIndexOf` lets any holder steal reward tokens when token speed is enabled - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
`RewardsDistributor._calculateTokenDelta` treats an account with `accountIndexOf == 0` as "new" only when the global token index is *strictly greater* than `INITIAL_INDEX` (`1e18`). When the token index equals `INITIAL_INDEX` exactly — which is the case for the entire block in which `updateTokenSpeed` first sets a nonzero speed — the uninitialized account index is used as `0`, producing `_deltaIndex == 1e18` and crediting `tokensAccruedOf[account] += balanceOf(account)` reward tokens. Any EOA holding the tracked token can call the public `updateBeforeMintOrBurn` (explicitly permissionless per its NatSpec) in that window and later drain the distributor via `claimRewards`.

### Finding Description
The bug lives in `_calculateTokenDelta` at contracts/RewardsDistributor.sol:217-231:

```solidity
_accountIndex = accountIndexOf[token_][account_];
if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}
uint256 _deltaIndex = _tokenIndex - _accountIndex;
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
```

When `_updateTokenSpeed` enables a token for the first time it writes `tokenStates[token_] = TokenState({index: INITIAL_INDEX, timestamp: block.timestamp})` (lines 296-299). While `block.timestamp == state.timestamp` (i.e., the same block, `_deltaTimestamps == 0`), `_calculateTokenIndex` returns `_newIndex == 0`, so `_updateTokenIndex` keeps `index == INITIAL_INDEX`. `_updateTokensAccruedOf` then computes:

- `_tokenIndex = INITIAL_INDEX` (1e18)
- `_accountIndex = 0`, and since `INITIAL_INDEX > INITIAL_INDEX` is false, it stays `0`
- `_deltaIndex = 1e18`
- `_tokensDelta = balance.wadMul(1e18) = balance`

So `tokensAccruedOf[account]` grows by the account's full tracked-token balance denominated in reward tokens, and `accountIndexOf` is set to `INITIAL_INDEX`, marking the account as synced — analogous to the dpic UAF where a freed/stale slot is dereferenced as if still valid.

Reachability: `updateBeforeMintOrBurn` and `updateBeforeTransfer` have no access control (line 175, line 186), and `claimRewards` sends `tokensAccruedOf` worth of `rewardToken` if the distributor has balance (lines 150-168, 248-255). The attacker only needs a nonzero `DepositToken`/`DebtToken` balance — obtainable via public `deposit`/`issue` — and must act in the same block as the governor's first `updateTokenSpeed` call for that token (front-running/ sandwiching a governor tx in the same block is within the threat model; alternatively anyone can trigger it for their own account via mempool observation in the same block).

### Impact Explanation
Theft of unclaimed yield: each attack inflates `tokensAccruedOf` by their entire token balance in reward-token units. Calling `claimRewards(attacker)` in a later block transfers real `rewardToken` from the distributor, directly stealing rewards accrued for legitimate depositors/borrowers (the distributor only transfers up to its balance, so the attacker can drain it to zero).

### Likelihood Explanation
Requires (a) the attacker to hold or acquire the reward-tracked deposit/debt token — trivial via normal protocol entry points — and (b) executing `updateBeforeMintOrBurn` in the same block the token's speed is first set to a nonzero value. Token-speed onboarding is a recurring governance operation per pool/token, and the window is deterministic and publicly observable; no privileged role, oracle manipulation, or reentrancy is needed. Repeating is possible for each newly enabled reward token (up to `MAX_REWARD_TOKENS`).

### Recommendation
In `_calculateTokenDelta`, treat `_accountIndex == 0` as fresh whenever `_tokenIndex >= INITIAL_INDEX` (i.e., change `>` to `>=`), or more robustly, clamp `_accountIndex = max(_accountIndex, INITIAL_INDEX)` when uninitialized, so a stale zero index can never yield a positive delta against an index that has not yet moved above the initial value.

### Proof of Concept
Hardhat-style PoC (assuming `msdTOKEN` is a DepositToken and `vsp` the reward token):

```ts
// Setup: attacker deposits collateral to receive msdTOKEN balance
await depositToken.deposit(attacker.address, parseEther('100'))

// Governor enables rewards for msdTOKEN in block T
await rewardDistributor.updateTokenSpeed(msdTOKEN.address, speed)
// Same block (automine off or next tx same timestamp):
// tokenStates[msdTOKEN].index == INITIAL_INDEX (1e18)

// Attacker calls the public update for their own account
await rewardDistributor
  .connect(attacker)
  .updateBeforeMintOrBurn(msdTOKEN.address, attacker.address)

// tokensAccruedOf[attacker] == 100e18 (full balance in reward tokens)
expect(await rewardDistributor.tokensAccruedOf(attacker.address)).to.eq(parseEther('100'))

// Later block: attacker claims and drains the distributor's rewardToken balance
await ethers.provider.send('evm_mine', [])
await rewardDistributor.connect(attacker)['claimRewards(address)'](attacker.address)
expect(await vsp.balanceOf(attacker.address)).to.eq(parseEther('100')) // stolen yield
```

Key assertions: after `updateTokenSpeed`, `tokenStates(msdTOKEN).index == 1e18` and `accountIndexOf(msdTOKEN, attacker) == 0`; the boundary check `_tokenIndex > INITIAL_INDEX` fails, so `_deltaIndex = 1e18` and the accrued amount equals the attacker's full token balance, payable by `_transferRewardIfEnoughTokens`.
