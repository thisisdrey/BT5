Audit Report

## Title
`OutboundQueue::calculate_fee` can silently return a zero remote fee despite validated non-zero `PricingParameters`, underpricing Ethereum message delivery - ([File: bridges/snowbridge/pallets/outbound-queue/src/lib.rs])

## Summary
`Pallet::<T>::calculate_fee` computes the native-currency fee charged to a user for exporting a message to Ethereum, but never validates that the resulting `fee.remote` is non-zero after the multiplier/exchange-rate division and the `convert_from_ether_decimals` truncation step. `PricingParameters::validate` only checks that the raw input fields are non-zero, not the derived fee, so governance-set, fully "valid" parameters can still cause `calculate_fee` to return `fee.remote == 0`, as proven by the repository's own test.

## Finding Description
`calculate_fee` chains `calculate_remote_fee` (gas × fee_per_gas + reward), a `saturating_mul(multiplier)`/`checked_div(exchange_rate)` step guarded only by `.expect("exchange rate is not zero; qed")`, and finally `convert_from_ether_decimals`, which does `value.checked_div(10^(ETHER_DECIMALS - T::Decimals))` [1](#0-0) . For a chain with `T::Decimals = 10` (DOT), this divisor is `10^8`; any intermediate `value` below that magnitude truncates to zero. `PricingParameters::validate` checks only that `exchange_rate`, `fee_per_gas`, `rewards.local`, `rewards.remote`, and `multiplier` are individually non-zero [2](#0-1)  — it never re-checks the derived `fee.remote` output of `calculate_fee`. This is confirmed end-to-end by the existing unit test `test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero`, which uses `exchange_rate = 1/1`, `fee_per_gas = 1`, `rewards.remote = 1`, `multiplier = 1/1` — all non-zero and passing `validate()` — yet asserts `fee.remote == 0` [3](#0-2) .

This `fee` is exactly what `send_message_impl.rs`'s `SendMessage::validate` returns to the fee-charging caller for any unprivileged user submitting an XCM export to Ethereum: `let fee = Self::calculate_fee(gas_used_at_most, T::PricingParameters::get());` followed by `Ok((ticket, fee))` [4](#0-3) . Separately, `do_process_message` embeds the full, uncapped `pricing_params.rewards.remote` directly into the committed message's `reward` field regardless of what was actually collected as `fee.remote` [5](#0-4) . Thus a message can be queued and committed with a full non-zero on-chain reward obligation while the corresponding fee collected from the submitter was zero (or negligible), since no code path re-validates `fee.remote != 0` before enqueuing.

## Impact Explanation
This matches the gate's "public underpriced work that degrades block production or stalls bridge processing" category: any unprivileged user submitting a message for export to Ethereum can be charged `fee.remote == 0` due to decimal-conversion truncation in `convert_from_ether_decimals`, while the committed message still carries the full `rewards.remote` obligation that must ultimately be paid to Ethereum-side relayers. Repeated submissions at zero marginal remote cost degrade the fee-based anti-spam/rate-limiting economics of the outbound queue and create a persistent shortfall between fees collected and rewards promised.

## Likelihood Explanation
High: the vulnerable condition is demonstrated directly in the repository's own passing test suite using non-degenerate, `validate()`-accepted parameters (1:1 exchange rate, minimal but valid gas/reward values) [3](#0-2) . Any deployment with `T::Decimals` less than `ETHER_DECIMALS` (enforced to be 10 or 12 by `integrity_test`) [6](#0-5)  is structurally exposed to this truncation for sufficiently small computed values, and triggering it requires only ordinary, unprivileged message submission — no governance or malicious-actor involvement is needed to exploit it once such parameters exist.

## Recommendation
After computing `fee` in `calculate_fee`, assert or check that the resulting `fee.remote` is non-zero (and sufficient to cover the ether-denominated `rewards.remote` after conversion) before returning it; reject the message submission (return an error from `SendMessage::validate`) if the computed remote fee would be zero, rather than silently enqueuing an underpriced message with a full non-zero reward obligation.

## Proof of Concept
The repository's existing test is a direct, reproducible demonstration: with `PricingParameters { exchange_rate: FixedU128::from_rational(1,1), fee_per_gas: 1, rewards: Rewards { local: 1, remote: 1 }, multiplier: FixedU128::from_rational(1,1) }`, `OutboundQueue::calculate_fee(250_000, price_params)` returns `fee.local = 698000000` and `fee.remote = 0`, despite all pricing inputs being strictly non-zero and passing `PricingParameters::validate()` [3](#0-2) .

		/// Calculate total fee in native currency to cover all costs of delivering a message to the
		/// remote destination. See module-level documentation for more details.
		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

		/// Calculate fee in remote currency for dispatching a message on Ethereum
		pub(crate) fn calculate_remote_fee(
			gas_used_at_most: u64,
			fee_per_gas: U256,
			reward: U256,
		) -> U256 {
			fee_per_gas.saturating_mul(gas_used_at_most.into()).saturating_add(reward)
		}

		/// The local component of the message processing fees in native currency
		pub(crate) fn calculate_local_fee() -> T::Balance {
			T::WeightToFee::weight_to_fee(
				&T::WeightInfo::do_process_message().saturating_add(T::WeightInfo::commit_single()),
			)
		}

		// 1 DOT has 10 digits of precision
		// 1 KSM has 12 digits of precision
		// 1 ETH has 18 digits of precision
		pub(crate) fn convert_from_ether_decimals(value: u128) -> T::Balance {
			let decimals = ETHER_DECIMALS.saturating_sub(T::Decimals::get()) as u32;
			let denom = 10u128.saturating_pow(decimals);
			value.checked_div(denom).expect("divisor is non-zero; qed").into()
		}
