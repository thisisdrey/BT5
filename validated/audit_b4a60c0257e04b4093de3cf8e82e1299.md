### Title
Stale `last-update` timestamp causes inflated interest/index accrual when utilization transitions from 0% to positive - ([File: mainnet/contracts/vault/v0-vault-stx.clar])

### Summary
The vault's interest accrual (`accrue`) only advances the `last-update` timestamp when the computed index actually changes. When utilization (and therefore the interpolated borrow rate) is `0`, the index computation is a no-op and `last-update` is never advanced, exactly like the `RAACMinter.tick` analog where `lastUpdateBlock` was skipped when `amountToMint` was `0`. Once utilization becomes positive again, the next `accrue` call applies the *current* (now-positive) rate across the entire stale window, including the period when the rate should have been `0`, producing an inflated interest/index jump.

### Finding Description
`next-index` and `next-liquidity-index` compute a multiplier from `time-delta = stacks-block-time - last-update` and the current `interest-rate()` (derived from `utilization()`): [1](#0-0) 

`calc-multiplier-delta` with `rate = 0` returns exactly `INDEX-PRECISION` (no change), so `next == index` and `nliq == lindex` whenever utilization/rate is `0`: [2](#0-1) 

In `accrue`, `last-update` is advanced **only** if either index actually changed: [3](#0-2) 

So during any period where the vault has zero borrowed debt (`utilization() == 0` ⇒ `interest-rate() == 0`), calling `accrue` (directly, or transitively via the public, unauthenticated `deposit`, `redeem`, `transfer`, or via `system-borrow`/`system-repay`) leaves `last-update` frozen at the last time the index actually moved, no matter how much real time elapses. As soon as any ordinary user borrows against the vault (via the market's `system-borrow`) and utilization/rate becomes positive, the *next* `accrue` call computes `time-delta` spanning the entire stale window (including the zero-rate period) and applies the now-positive rate across that whole span — inflating `debt-delta`, hence `total-debt`/`total-assets`, and the `treasury-lp` amount minted to `.dao-treasury`: [4](#0-3) 

This is the direct structural analog of the reported `RAACMinter.tick` bug: a rate-like variable transitions from `0` to a positive value while the "last update" tracker was not advanced during the zero period, so the next update wrongly attributes the full stale duration to the new nonzero rate. `accrue` is a public entry point with no `check-dao-auth`/`check-caller-auth` guard, so any unprivileged principal can trigger and permanently commit (`var-set index next`, `var-set lindex nliq`) the inflated result. The identical pattern exists in every vault contract (`v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`).

### Impact Explanation
Once the inflated index is committed, `total-debt`/`total-assets` (via `calc-cumulative-debt`) and the `zft` share price (`convert-to-assets-preview`/`convert-to-shares-preview`) reflect interest that never actually accrued during the zero-utilization window, and excess `treasury-lp` shares are minted to `.dao-treasury`. This overstates the vault's backed value relative to real underlying assets, letting depositors redeem against inflated `total-assets` and extract more underlying than is actually available, which is a temporary/permanent freezing-of-funds / insolvency risk for the vault, and constitutes theft of unclaimed yield (interest that shouldn't exist is captured by depositors' share-price appreciation and by the treasury mint).

### Likelihood Explanation
This requires no privileged access or DAO compromise: any period of zero-utilization (common right after vault deployment, or after all debt is repaid) followed by any ordinary borrow is sufficient to set up the stale window, and any unprivileged principal can then call `accrue`/`deposit`/`redeem`/`transfer` to lock in the inflated index. This is a naturally occurring operational state rather than a crafted edge case, making likelihood Medium-to-High.

### Recommendation
Update `last-update` to `stacks-block-time` on every `accrue` call, regardless of whether the index values changed, so `time-delta` never spans periods that were already "settled" at a different (possibly zero) rate.

### Proof of Concept
1. At `T0`, vault has zero outstanding debt (`principal-scaled == 0`), so `utilization() == 0` and `interest-rate() == 0`. `last-update == T0`.
2. Time passes to `T1 = T0 + Δ` with no borrows; any calls to `accrue` compute `next == index` and `nliq == lindex` (rate is 0), so per lines 851-862 of `v0-vault-stx.clar`, `last-update` stays at `T0`.
3. An ordinary user borrows via the market (`system-borrow`) at `T1`; `accrue` runs first while debt is still 0, so it's a no-op and `last-update` remains `T0`. After the borrow, `principal-scaled > 0`.
4. Time passes to `T2 = T1 + δ`; utilization/rate is now positive because debt is outstanding.
5. Any unprivileged caller invokes `accrue` (or `deposit`/`redeem`/`transfer`). `time-delta = T2 - last-update = (Δ + δ)` instead of the correct `δ`. `next-index`/`next-liquidity-index` apply the current positive rate over `Δ + δ`, inflating `debt-delta`, `total-debt`, `total-assets`, and `treasury-lp` minted to `.dao-treasury` by roughly `(Δ+δ)/δ`×.
6. `var-set index next` / `var-set lindex nliq` permanently commit this inflated result; the error cannot be reversed.

(define-private (next-index)
  (let ((states (var-get pause-states))
        (idx (var-get index)))
    (if (get accrue states)
        idx
        (let (
            (rate (interest-rate))
            (time-delta (- stacks-block-time (var-get last-update)))
            (multiplier (if (is-eq time-delta u0)
                          INDEX-PRECISION
                          (calc-multiplier-delta rate time-delta true))))
          (calc-index-next idx multiplier)))))

            (rate (interest-rate))

(define-public (accrue)
  (let ((states (var-get pause-states))
        (idx (var-get index))
        (lidx (var-get lindex)))
      (if (get accrue states)
          ;; PAUSED: Pass-through without reverting
          (ok { index: idx, lindex: lidx })
          ;; NOT PAUSED: Normal accrual logic
          (let ((next (next-index))
                (nliq (next-liquidity-index))
                (scaled-principal (var-get principal-scaled))
                (old-debt (mul-div-down scaled-principal idx INDEX-PRECISION))
                (new-debt (mul-div-down scaled-principal next INDEX-PRECISION))
                (debt-delta (if (> new-debt old-debt) (- new-debt old-debt) u0))
                (reserve-inc (mul-div-down debt-delta (var-get fee-reserve) BPS))
                (treasury-lp (if (> reserve-inc u0) (mul-div-down reserve-inc (total-supply) (- (total-assets-preview) reserve-inc)) u0)))
            (if (not (is-eq idx next))
                (var-set index next)
                false)
            (if (not (is-eq lidx nliq))
                (var-set lindex nliq)
                false)
            (if (> treasury-lp u0)
                (try! (ft-mint? zft treasury-lp .dao-treasury))
                false)
            (if (or (not (is-eq idx next)) (not (is-eq lidx nliq)))
                (var-set last-update stacks-block-time)
                false)
            (ok { index: next, lindex: nliq })))))
