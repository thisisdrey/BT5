### Title
Firewall conntrack fast-path cache allows traffic to bypass a rule-set reload for the cache-tick window - (File: `firewall.go`, `firewall/cache.go`)

### Summary
The Sherlock/Mellow finding is about a *stale snapshot reused across a batch of operations without incremental revalidation*, which lets an attacker extract value the design intended to only be available after the snapshot was refreshed. The closest reachable analog in nebula is the per-goroutine `ConntrackCache` (`localCache`) that `Firewall.inConns` consults as a fast path *before* re-checking a connection's `rulesVersion` against the live firewall table. Once a flow is marked "allowed" in that cache, every packet in the same tuple is waved through for the remainder of the cache tick, even if the firewall rules were reloaded and would now reject that flow.

### Finding Description
`Firewall.inConns` first checks the caller-supplied `localCache` and returns `true` immediately on a hit, skipping the `rulesVersion` comparison that the persistent `conntrack.Conns` map performs: [1](#0-0) 
Only when the local cache misses does the code fall through to the persistent map and its per-entry rule-set revalidation: [2](#0-1) 

This is the exact same bug shape as the Mellow report: a value (`ProcessWithdrawalsStack`/`s.totalSupply`, `s.totalValue`) is snapshotted once and then reused across a "batch" of subsequent checks without being refreshed against updated ground truth (`f.rulesVersion`). Here, the "batch" is every packet processed while `ConntrackCacheTicker.Get()` returns the same cache generation: [3](#0-2) 
`localCache` is threaded through the entire outside/inside packet-processing path and fed straight to `Drop`/`inConns` for every packet handled in that interval: [4](#0-3) [5](#0-4) 

Because the local cache entry is written the first time a flow is confirmed allowed and is never invalidated when `f.rulesVersion` changes (that invalidation only exists on the `conntrack.Conns[fp]` path), an admin who reloads the firewall config to *revoke* a previously-allowed flow does not immediately stop that flow: any reader goroutine that already cached the tuple will keep allowing it until its local `ConntrackCacheTicker` tick rolls over (controlled by `ConntrackCacheTimeout`).

### Impact Explanation
This allows an already-established flow to continue passing traffic in violation of a freshly tightened firewall policy — a firewall bypass — for up to one cache-tick interval. Depending on configured `net.conntrack_tcp_timeout`-style cache interval, this window can be attacker-relevant if the operator relies on fast rule-reload to shut off ongoing malicious/abusive traffic (e.g., during an incident response). It does not require a valid CA-signed certificate beyond what is already needed to have an established, allowed tunnel and matches the "firewall bypass" category explicitly permitted by scope.

### Likelihood Explanation
Requires: (1) an existing accepted flow matching a firewall rule, (2) the firewall ruleset being reloaded to reject that flow, and (3) the attacker continuing to send packets on the same 4/5-tuple before the local `ConntrackCacheTicker` next ticks. All three conditions are realistic in normal operation (firewall reload is a supported, documented feature per `firewall.go`/`CHANGELOG.md` entries about "Reload the firewall when ... certificate change" and conntrack revalidation), making this a plausible, low-effort persistence mechanism for an already-connected peer whose access is being revoked.

### Recommendation
Do not let the per-goroutine `ConntrackCache` short-circuit the `rulesVersion` check. Either (a) stamp the cached entry with the `rulesVersion` it was validated under and compare on each hit, mirroring what `conntrack.Conns` already does, or (b) invalidate/reset the `ConntrackCacheTicker`'s cache whenever `f.rulesVersion` changes (in addition to the existing time-based tick), so a rule reload takes effect for in-flight traffic without waiting for the next tick.

### Proof of Concept
1. Establish a tunnel and firewall rule allowing UDP flow `(local, remote, ports)`; send one packet so it is accepted and both `conntrack.Conns[fp]` and the reader's `localCache[fp]` are populated (`firewall.go` lines 505-577, `inside.go`/`outside.go` call sites).
2. Reload the firewall config to a ruleset that no longer allows this flow — `f.rulesVersion` increments (see `TestFirewall_DropConntrackReload` at `firewall_test.go:667-729`, which demonstrates the intended revalidation-on-reload behavior for the persistent map).
3. Continue sending packets on the same tuple from the attacker/peer side before the reader's local cache tick advances (`ConntrackCacheTicker.Get()` in `firewall/cache.go:52-67`); `inConns` returns `true` on the `localCache` hit at line 507 without ever reaching the `rulesVersion` comparison at line 527, so the now-disallowed packets keep being forwarded until the tick rolls over.

```go
// Get checks if the cache ticker has moved to the next version before returning
// the map. If it has moved, we reset the map.
func (c *ConntrackCacheTicker) Get() ConntrackCache {
	if c == nil {
		return nil
	}
	if tick := c.cacheTick.Load(); tick != c.cacheV {
		c.cacheV = tick
		if ll := len(c.cache); ll > 0 {
			if c.l.Enabled(context.Background(), slog.LevelDebug) {
				c.l.Debug("resetting conntrack cache", "len", ll)
			}
			c.cache = make(ConntrackCache, ll)
		}
	}

	return c.cache
}
```
