### Title
Unchecked `reduceAssetAmountV2` return value in `ExchangeTransactionActuator`/`ExchangeInjectActuator` can credit counter-party assets without debiting the source token - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java])

### Summary
`AccountCapsule.reduceAssetAmountV2` returns a `boolean` indicating whether the deduction actually succeeded, and `TransferAssetActuator` correctly checks this return value and reverts the transaction via `ContractExeException` if it fails [1](#0-0) . However, `ExchangeTransactionActuator.execute` and `ExchangeInjectActuator.execute` call the same method and discard the return value, then unconditionally proceed to credit the counter-party token/exchange balances as if the deduction had succeeded [2](#0-1) [3](#0-2) . This mirrors the reported bug class ("token burnt/consumed but the counter-asset is still granted, i.e., the debit silently fails while the credit still lands").

### Finding Description
`AccountCapsule.reduceAssetAmountV2` computes success based on the `AllowSameTokenName` dynamic property and the current asset map at the moment of the call, returning `false` (with no side effect) if `currentAmount` is `null` or `amount > currentAmount` [4](#0-3) .

In `ExchangeTransactionActuator.execute`, the exchange pool balances (`exchangeCapsule.transaction(...)`) and `anotherTokenQuant` are computed independently of whether the actual account-level deduction succeeds [5](#0-4) . The code then calls `accountCapsule.reduceAssetAmountV2(tokenID, tokenQuant, ...)` without checking its boolean result and immediately calls `accountCapsule.addAssetAmountV2(anotherTokenID, anotherTokenQuant, ...)` to credit the other token, and persists the exchange pool's updated balances via `Commons.putExchangeCapsule` [6](#0-5) . If `reduceAssetAmountV2` silently returns `false` (no deduction performed) while the rest of the state transition proceeds, the account is credited with the other side of the trade and the exchange pool balances are updated as though a real swap of `tokenQuant` occurred, without the source token ever leaving the account. The identical pattern exists in `ExchangeInjectActuator.execute`, where two consecutive `reduceAssetAmountV2` calls (for the injected token and the computed proportional counter-token) are both unchecked while the exchange pool's `firstTokenBalance`/`secondTokenBalance` are already updated beforehand [7](#0-6) .

This is directly analogous to the reported issue: a value-bearing action (burning/reducing a balance) is assumed to succeed, and downstream effects (crediting another asset, updating a shared pool ledger) are performed regardless of whether that assumption held.

### Impact Explanation
If `reduceAssetAmountV2` fails silently for either actuator, the transaction still reports `code.SUCESS`, the exchange pool's internal accounting (`firstTokenBalance`/`secondTokenBalance`) is mutated to reflect a swap/injection that didn't happen on the account side, and the account is still credited with the counter-asset. This creates an inconsistency between the exchange pool's recorded reserves and the actual TRC10 asset supply backing them — an unbacked-balance condition affecting the shared `ExchangeCapsule`/`ExchangeV2Store` state used by all participants of that exchange pair, not just the calling account.

### Likelihood Explanation
`validate()` in both actuators calls `assetBalanceEnoughV2` (for `ExchangeTransactionActuator`) prior to `execute()` to check sufficient balance, which should normally keep `reduceAssetAmountV2` consistent with the validated state. I was not able to fully verify, within the available tool budget, whether there is a code path where `assetBalanceEnoughV2`'s check diverges from the exact condition evaluated inside `reduceAssetAmountV2` (e.g., different key derivation between name-based and ID-based asset maps under the `AllowSameTokenName` transition, or precision/rounding edge cases in `exchangeCapsule.transaction`) that would let `validate()` pass while `reduceAssetAmountV2` still returns `false` at execute time. Without confirming such a divergence exists, likelihood cannot be rated as more than low-to-moderate; the missing null/false check is a genuine defensive-coding gap (inconsistent with `TransferAssetActuator`'s pattern) but a concrete unauthorized-fund-extraction trigger was not fully proven with the available context.

### Recommendation
In `ExchangeTransactionActuator.execute` and `ExchangeInjectActuator.execute`, check the boolean return value of every `reduceAssetAmountV2` (and `addAssetAmountV2`, if it too can fail) call and throw `ContractExeException` on failure, mirroring the guard already present in `TransferAssetActuator`:
```java
if (!accountCapsule.reduceAssetAmountV2(tokenID, tokenQuant, dynamicStore, assetIssueStore)) {
  throw new ContractExeException("reduceAssetAmount failed !");
}
```
before any exchange pool balance mutation or counter-asset credit is persisted.

### Proof of Concept
Concrete PoC input values that force `reduceAssetAmountV2` to return `false` at execute-time despite `validate()` passing could not be constructed with certainty from the available code/index; this would require confirming a divergence between `assetBalanceEnoughV2`'s check and `reduceAssetAmountV2`'s internal condition (e.g., around the `AllowSameTokenName` key-selection branch) — recommend a Devin session with full repository/test access to trace `assetBalanceEnoughV2` and reproduce via `ExchangeTransactionActuatorTest`/`ExchangeInjectActuatorTest`.

  public boolean reduceAssetAmountV2(byte[] key, long amount,
                                     DynamicPropertiesStore dynamicPropertiesStore, AssetIssueStore assetIssueStore) {
    importAsset(key);
    //key is token name
    boolean disableJavaLangMath = dynamicPropertiesStore.disableJavaLangMath();
    if (dynamicPropertiesStore.getAllowSameTokenName() == 0) {
      Map<String, Long> assetMap = this.account.getAssetMap();
      AssetIssueCapsule assetIssueCapsule = assetIssueStore.get(key);
      String tokenID = assetIssueCapsule.getId();
      String nameKey = ByteArray.toStr(key);
      Long currentAmount = assetMap.get(nameKey);
      if (amount > 0 && null != currentAmount && amount <= currentAmount) {
        this.account = this.account.toBuilder()
                .putAsset(nameKey, subtractExact(currentAmount, amount, disableJavaLangMath))
                .putAssetV2(tokenID, subtractExact(currentAmount, amount, disableJavaLangMath))
                .build();
        return true;
      }
    }
    //key is token id
    if (dynamicPropertiesStore.getAllowSameTokenName() == 1) {
      String tokenID = ByteArray.toStr(key);
      Map<String, Long> assetMapV2 = this.account.getAssetV2Map();
      Long currentAmount = assetMapV2.get(tokenID);
      if (amount > 0 && null != currentAmount && amount <= currentAmount) {
        this.account = this.account.toBuilder()
                .putAssetV2(tokenID, subtractExact(currentAmount, amount, disableJavaLangMath))
                .build();
        return true;
      }
    }

    return false;
  }
