## Finding

### Title
Uncaught `ArithmeticException` in `MarketSellAssetActuator.execute()` can crash block processing - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
`MarketSellAssetActuator.execute()` calls hardened arithmetic helpers (`subtractExact`/`addExact` from `AbstractActuator`, which delegate to `org.tron.common.math.Maths.addExact/subtractExact` and can throw `ArithmeticException` on 64-bit overflow) inside `matchOrder()` → `matchSingleOrder()` → `addTrxOrToken()`, but the `try/catch` block in `execute()` only catches `ItemNotFoundException | InvalidProtocolBufferException | BalanceInsufficientException | ContractValidateException`. [1](#0-0) 

Every other TRX/asset-moving actuator in the codebase (`TransferActuator`, `TransferAssetActuator`, `ParticipateAssetIssueActuator`, `ExchangeCreateActuator`, `ExchangeInjectActuator`, `ExchangeWithdrawActuator`, `ExchangeTransactionActuator`, `ShieldedTransferActuator`) explicitly adds `ArithmeticException` to its `execute()` catch clause and converts it into a `ContractExeException`. [2](#0-1) [3](#0-2) 

`MarketSellAssetActuator` is the outlier that omits this, even though it uses the identical `subtractExact`/`addExact` helpers inherited from `AbstractActuator`. [4](#0-3) 

### Finding Description
`addTrxOrToken()` credits TRX to an account with `accountCapsule.setBalance(addExact(accountCapsule.getBalance(), num))`, and `matchSingleOrder()` performs `subtractExact(...)` on remaining order quantities during order matching. [5](#0-4) [6](#0-5) 

These calls resolve to `Maths.addExact`/`Maths.subtractExact`, which — depending on `disableJavaLangMath()` (a chain parameter that can enable strict overflow checking) — throw `ArithmeticException` on a 64-bit overflow (e.g. an account balance close to `Long.MAX_VALUE` receiving a further credit from a matched trade).

Because `MarketSellAssetActuator.execute()`'s catch clause does not list `ArithmeticException`, such an exception propagates out of `execute()` as an unchecked `RuntimeException`. Tracing the call chain: `TransactionTrace.exec()` invokes actuator `execute()`, which is invoked from `Manager.processTransaction()`, which is invoked from `Manager.processBlock()`/`applyBlock()`. None of these methods declare or catch generic `RuntimeException`/`ArithmeticException` — their catch/throws clauses are restricted to a fixed list of checked exceptions (`ContractValidateException`, `ContractExeException`, `ValidateSignatureException`, etc.). [7](#0-6) 

An uncaught `ArithmeticException` escaping `processBlock`/`applyBlock` during block application is not one of the recognized, gracefully-handled exception types, so it would propagate further up the block-application call stack, aborting in-progress block processing state instead of being converted into a normal transaction failure.

### Impact Explanation
If triggered while a witness/full node is applying a block (which happens on every node in the network, not just the block producer), this causes the block-application path to fail with an unhandled runtime exception instead of the intended "transaction failed, continue block" behavior that all sibling actuators implement. Depending on how the top-level block-processing caller handles an unexpected `RuntimeException` (which is not part of `processBlock`'s declared/caught exception set), this can manifest as a node crash or an inconsistent/halted state while processing an otherwise valid block, which is a network-wide availability risk since every node independently re-executes the same transaction when validating/applying the block.

### Likelihood Explanation
Reaching the vulnerable code path requires only submitting a `MarketSellAssetContract` transaction (Market Sell) referencing an existing trading pair with a matching order — the Market feature is directly submittable by any account once `AllowMarketTransaction` is enabled by the committee, which is already the case on mainnet. Triggering the actual overflow requires an account balance sitting near `Long.MAX_VALUE` sun, which is an extreme edge condition unlikely under normal token-supply constraints, making practical exploitation difficult without either an extraordinarily large account balance or the `disableJavaLangMath`/hardened-math flag being enabled with a crafted preconditions. This lowers the practical likelihood versus the structural code-hygiene issue (missing `ArithmeticException` handling that all analogous actuators include).

### Recommendation
Add `ArithmeticException` to the caught exception set in `MarketSellAssetActuator.execute()`, mirroring `TransferActuator`/`ExchangeWithdrawActuator`/etc., so any arithmetic overflow during order matching is converted into a `ContractExeException`/failed transaction rather than an unchecked `RuntimeException` propagating through block application.

### Proof of Concept
Not independently verified with a runnable exploit given the extreme balance precondition required (`Long.MAX_VALUE`-adjacent account balance) and dependency on the hardened-math (`disableJavaLangMath`) configuration; this is flagged based on static code-path analysis of `MarketSellAssetActuator.execute()`'s exception handling gap relative to sibling actuators, and the absence of a generic `RuntimeException`/`ArithmeticException` catch in `Manager.processBlock`/`processTransaction`.
