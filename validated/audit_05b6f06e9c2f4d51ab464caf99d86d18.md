### Title
`DebtToken.burn()` skips `accrueInterest()`, corrupting debt index accounting and inflating the liquidated user's remaining debt - (File: contracts/DebtToken.sol)

### Summary
Every state-changing entry point in `DebtToken` (`issue`, `flashIssue`, `mint`, `repay`, `repayAll`, `updateInterestRate`) calls `accrueInterest()` before mutating debt state, except `burn()` — the path used by `Pool` during liquidation. `_burn` computes the user's balance with the *virtually accrued* `debtIndex` but writes the *stale stored* `debtIndex` into `debtIndexOf[account_]`, causing interest to be double-counted on the remaining debt and desyncing `totalSupply_` from accrued units.

### Finding Description
`accrueInterest()` materializes pending interest into `totalSupply_`, `debtIndex`, and `lastTimestampAccrued`. `balanceOf()` computes `principalOf[account_] * newIndex / debtIndexOf[account_]` using the *calculated* (not stored) index.

In `_burn` (DebtToken.sol:525-543):

```solidity
uint256 _accountBalance = balanceOf(account_);          // uses virtual accrued index I1
principalOf[account_] = _accountBalance - amount_;      // denominated in I1 units
debtIndexOf[account_] = debtIndex;                      // stale stored index I0 (< I1)
totalSupply_ -= amount_;                                // subtracts I1-units from I0-units supply
```

Because `debtIndexOf` is reset to the stale `I0` while `principalOf` was expressed in `I1` terms, the next `balanceOf` call re-applies the `I1/I0` interest factor on the post-burn principal — interest accrued before the liquidation is charged twice. Analogous to the Yieldy `instantUnstake(false)` skipping the optional rebase, the liquidation burn path skips the mandatory interest accrual before mutating indexed balances.

### Impact Explanation
- The liquidated user's remaining debt is inflated by the factor `I1/I0` applied twice; the longer `lastTimestampAccrued` is stale and the higher `interestRate`, the larger the inflation.
- Inflated debt pushes the position closer to (or past) the liquidation threshold again — the user can be liquidated a second time for debt they do not actually owe, and any eventual repayment overpays the protocol/feeCollector (interest is minted to `feeCollector` in `accrueInterest`, so the phantom interest is later realized as protocol revenue at the user's expense).
- `totalSupply_` accounting is corrupted: an amount measured in accrued units is subtracted from a supply tracked in un-accrued units, and the subsequent `accrueInterest` compounds on the wrong base.
- This satisfies "theft of user funds / protocol accounting insolvency" impact classes.

### Likelihood Explanation
- The trigger is fully permissionless: any liquidator calling `Pool.liquidate` (or wherever `DebtToken.burn` is invoked via `onlyPool`) on an unhealthy account hits this path whenever `block.timestamp > lastTimestampAccrued` and `interestRate > 0`, i.e., virtually always.
- Whether `Pool.liquidate` itself calls `accrueInterest()` before `debtToken.burn()` could not be fully confirmed within the iteration limit — if `Pool` does accrue first, the bug is latent only. However, `DebtToken` is independently upgradeable/versioned (`VERSION = "1.3.2"`), relies on callers for accrual in this one path while handling it internally everywhere else, and `collectPendingInterestFee`/`accrueInterest` being `public` does not change that `_burn` writes a stale `debtIndexOf`.
- There is no guard (e.g., requiring `lastTimestampAccrued == block.timestamp`) preventing the desync.

### Recommendation
Call `accrueInterest()` at the top of `burn()` (or inside `_burn`, mirroring how `issue`/`repay` do it) so that `debtIndex`, `totalSupply_`, and `balanceOf` are all expressed in the same index units before `principalOf` and `debtIndexOf` are rewritten:

```solidity
function burn(address from_, uint256 amount_) external override onlyPool {
    accrueInterest();
    _burn(from_, amount_);
}
```

Alternatively, require `Pool` to accrue before every burn, but enforcing it inside `DebtToken` removes the caller-dependency footgun entirely.

### Proof of Concept
Hardhat fork sketch:

```typescript
// given: alice has debt principal P minted at stored index I0
// time passes so interest accrues: virtual index I1 > I0, lastTimestampAccrued stale
await increaseTime(30 * 24 * 3600);

// sanity: balanceOf uses virtual index
const debtBefore = await debtToken.balanceOf(alice.address); // = P * I1 / I0

// when: liquidator repays part of alice's debt via Pool.liquidate,
// which calls debtToken.burn(alice, D) WITHOUT accruing first
await pool.connect(liquidator).liquidate(synth.address, alice.address, D, depositToken.address);

// then: alice's principal was stored in I1-units but indexed at stale I0
// after the next accrual tick, her debt is (P*I1/I0 - D) * I2/I0  --> I1/I0 charged twice
const debtAfter = await debtToken.balanceOf(alice.address);
expect(debtAfter).to.be.gt(expectedDebtAfter); // inflated vs. correct (P - D*I0/I1) * I2/I0
```

The assertion compares actual `balanceOf` against the mathematically correct remaining debt; the excess equals the double-counted pre-liquidation interest on the non-repaid portion, and also manifests as `totalSupply_` no longer matching the sum of per-account balances.
