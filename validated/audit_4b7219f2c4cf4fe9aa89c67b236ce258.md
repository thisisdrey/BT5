### Title
Address-only peer identity in `PeerDB::update_peer` lets an unauthenticated re-keyed Handshake drop `stackerdb_peers` slot mappings - ([File: stackslib/src/net/db.rs])

### Summary
`PeerDB::update_peer` (db.rs:1286-1334) looks up the "old" peer purely by `(network_id, addrbytes, port)` via `PeerDB::get_peer` (db.rs:940-947), never by public key. When the newly handshaked `Neighbor`'s key differs from the key on record for that same address/port, the code treats this as a "re-key" of the *same* peer and unconditionally calls `PeerDB::drop_stacker_dbs(tx, slot)` (db.rs:1322-1330), with no check that the new key ever produced a StackerDB-slot-signed chunk.

### Finding Description
The intended invariant is: a `stackerdb_peers` row for a slot should only be dropped/changed by an action that the slot's actual key holder authorized. Instead, the equality used to decide "this is the same logical peer re-keying" is `(network_id, addrbytes, port)` identity, not public-key/identity continuity, and it is established purely by a successful `Handshake` exchange — a *Handshake* message need only be well-formed and signed by the sender's own (new, attacker-controlled) private key; it does not need to prove control of the old peer's key, nor does it involve any StackerDB chunk signature.

Call path: any code that receives a peer's `Handshake` reply calls `Neighbor::save_update` (`stackslib/src/net/neighbors/neighbor.rs:50-61`), whose doc comment states "Updates last-contact-time to now, since this is only called when we get back a Handshake." `save_update` calls `PeerDB::update_peer(tx, self)` unconditionally. Inside `update_peer`:
- `old_peer_opt = PeerDB::get_peer(tx, network_id, addrbytes, port)` — keyed only on address triple (db.rs:1287-1292, 940-947).
- The frontier row is blindly updated with the new key (db.rs:1294-1313).
- If `old_peer.public_key != neighbor.public_key`, `drop_stacker_dbs(tx, slot)` fires (db.rs:1322-1330), deleting all `stackerdb_peers` rows for that slot with a raw `DELETE FROM stackerdb_peers WHERE peer_slot = ?1` (db.rs:1084-1088) — no StackerDB chunk, no slot-signature check anywhere in this call chain.

Exploit: a legitimate peer holding key K1 occupies IP:port A and is a StackerDB slot replica (slot S rows populated by `insert_or_replace_stacker_dbs`/`update_peer_stacker_dbs`). If that IP later becomes available to an attacker (e.g., dynamic/CGNAT reassignment, or attacker simply connects claiming to be listening at A — the peer DB's `addrbytes`/`port` for an inbound/outbound conversation partner is derived from the connection/handshake data the attacker controls), the attacker completes an ordinary Handshake with a freshly generated key K2 while claiming address A. `save_update` → `update_peer` observes `old_peer.public_key (K1) != neighbor.public_key (K2)` at the same `(network_id, A, port)` and drops slot S's `stackerdb_peers` rows — purely from a self-signed Handshake, with zero interaction with the actual StackerDB replication/signature protocol.

### Impact Explanation
The attacker can force deletion of `stackerdb_peers` association rows for a slot they do not own, purely by presenting a new key at a previously-used address/port. This breaks the invariant that StackerDB slot-to-peer mappings are only mutated by the actual slot key holder, and does so with a single unauthenticated P2P message (Handshake) rather than any StackerDB-chunk-signed write. This is an unauthenticated write to StackerDB peer-association state, repeatable against any node that has ever recorded a StackerDB replica for that address/port, matching the Critical "unauthenticated/unauthorized write to state or StackerDB" category, though it deletes association metadata (used for `find_stacker_db_replicas`/discovery) rather than actual StackerDB chunk contents.

### Likelihood Explanation
Preconditions: the attacker needs to be able to complete a valid Handshake claiming an address/port `(network_id, addrbytes, port)` that a node currently has on record as hosting a StackerDB replica — realistically via IP churn/CGNAT reassignment as described, or by being the first to reconnect at that tuple after the legitimate peer disconnects. No secrets, no privileged role, and no interaction with StackerDB chunk signing are required; a bare Handshake with a self-generated key suffices, remotely reachable on the P2P port. This is fully repeatable for any slot/address the attacker can occupy.

### Recommendation
Do not gate the "peer re-keyed, drop its DBs" decision solely on `(network_id, addrbytes, port)` identity plus a differing public key. Either (a) require re-announcement/re-authentication of StackerDB participation tied to the actual slot's signing key before dropping `stackerdb_peers`, or (b) key peer identity continuity (and hence the re-key detection) on a stable identifier such as `Hash160::from_node_public_key` bound to the previous key, only dropping stacker DB rows when the *old* key can no longer be shown to control the address (e.g., via an expiry/challenge mechanism), rather than trusting the raw address triple asserted by an unauthenticated Handshake.

### Proof of Concept
```rust
// stackslib/src/net/db.rs (new test)
#[test]
fn test_update_peer_rekey_drops_stackerdb_without_signature() {
    let addr = NeighborKey { peer_version: 1, network_id: 1, addrbytes: PeerAddress::from_ipv4(127,0,0,1), port: 12345 };
    let key1 = Secp256k1PrivateKey::random();
    let pubk1 = Secp256k1PublicKey::from_private(&key1);
    let neighbor1 = Neighbor::empty(&addr, &pubk1, 1000);

    let contract = QualifiedContractIdentifier::new(
        StandardPrincipalData::new(0x01, [0x02; 20]).unwrap(),
        ContractName::from_literal("db-1"),
    );

    let mut db = PeerDB::connect(/* ... */).unwrap();
    {
        let tx = db.tx_begin().unwrap();
        assert!(PeerDB::try_insert_peer(&tx, &neighbor1, &[contract.clone()]).unwrap());
        tx.commit().unwrap();
    }
    // sanity: slot has the stacker db
    assert_eq!(db.get_peer_stacker_dbs(&neighbor1).unwrap(), vec![contract.clone()]);

    // attacker key2 claims same addr, no StackerDB chunk signature involved anywhere
    let key2 = Secp256k1PrivateKey::random();
    let pubk2 = Secp256k1PublicKey::from_private(&key2);
    let mut neighbor2 = Neighbor::empty(&addr, &pubk2, 1000);

    {
        let tx = db.tx_begin().unwrap();
        // simulates Neighbor::save_update() invoked after processing an ordinary Handshake
        PeerDB::update_peer(&tx, &neighbor2).unwrap();
        tx.commit().unwrap();
    }

    // assert: stackerdb_peers row for slot dropped with no chunk signature check
    let dbs_after = db.get_peer_stacker_dbs(&neighbor2).unwrap();
    assert!(dbs_after.is_empty(), "stacker DB association was dropped by unauthenticated re-key");
}
```
This directly exercises `PeerDB::update_peer` (db.rs:1286-1334) and `PeerDB::drop_stacker_dbs` (db.rs:1084-1088), demonstrating that a mere address-collision with a differing public key removes `stackerdb_peers` rows with no StackerDB chunk signature verification anywhere in the path.
