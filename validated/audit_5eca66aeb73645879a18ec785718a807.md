### Title
Unbounded, attacker-controlled length fields in TVM precompile ABI-array decoders cause out-of-bounds array reads / uncontrolled allocation - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`PrecompiledContracts.java` contains three ABI-array extraction helpers — `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` — that decode a length field directly from the untrusted `DataWord[] words` parsed from precompile call data, then loop `len` times indexing into `words`/`data` without ever validating that `len` (or the derived offsets) stay within the bounds of the actual input buffer. This mirrors the CVE-2018-11547 bug class: a parser reads a length/loop-termination value from attacker input and iterates without bounding it against the real buffer size, producing an out-of-bounds read.

### Finding Description
`extractBytes32Array` reads `len = words[offset].intValueSafe()` and then reads `words[offset + i + 1]` for `i` in `[0, len)` with no check that `offset + len` is within `words.length`: [1](#0-0) 

`extractBytesArray` has a guard only for the initial `offset`, not for the derived `len`, `bytesOffset`, or `bytesLen`, which are all taken from attacker-supplied words and then used to slice `data`: [2](#0-1) 

`extractSigArray` follows the identical unsafe pattern, deriving `bytesOffset` from attacker data and calling `extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE, SIG_LENGTH)`, which performs `Arrays.copyOfRange` on arbitrary computed offsets: [3](#0-2) 

Because `len` is fully attacker-controlled (derived from `intValueSafe()` on a 256-bit word), it can be set to very large positive values. `new byte[len][]` or `new byte[bytes32Array.length][]`-style allocations can request array sizes up to `Integer.MAX_VALUE`, and the subsequent `words[offset + i + 1]` / `extractBytes(data, offset, len)` calls will throw `ArrayIndexOutOfBoundsException`, `NegativeArraySizeException`, or trigger extremely large heap allocations (`OutOfMemoryError`) well before the array bound is reached — exactly the "loop mishandles termination against actual buffer length" root cause described in the CVE.

### Impact Explanation
Any contract deployer or transaction sender can trigger these precompile decoders via a TVM `CALL`/`STATICCALL` to the relevant precompiled-contract address with crafted call data containing an oversized length word. Because the allocation size (`new byte[len][]`) is derived directly from attacker input with no upper bound, this can force multi-gigabyte allocation attempts, producing `OutOfMemoryError` — which is not a subtype of `Exception` and would not be caught by ordinary `catch (Exception e)` handlers used elsewhere in the VM/precompile dispatch path, risking a node crash or halted TVM execution for all pending transactions in that block, i.e., a network-reachable denial-of-service against every node validating the transaction.

### Likelihood Explanation
High. The vulnerable helpers are reachable from `getContractForAddress`-selected precompiles that any unprivileged account can invoke by deploying or calling a contract that issues a `CALL` to the applicable precompile address with attacker-chosen calldata; no special privileges or the cooperation of an SR/witness/committee are required.

### Recommendation
In `extractBytes32Array`, `extractBytesArray`, and `extractSigArray`, validate `len` (and any offsets derived from `words`) against the true bounds of `words.length` and `data.length` before allocating result arrays or performing `System.arraycopy`/`copyOfRange`, mirroring the `verifyLength` bound checks already used in `RLP.java`. Reject (return empty/false) rather than throw uncontrolled JVM errors when a length field would exceed the available buffer.

### Proof of Concept
Construct a transaction that calls the multi-sign/array-based precompile (the one using `extractSigArray`/`extractBytesArray`/`extractBytes32Array`) with a calldata word at the "array length" position set to a very large value (e.g., `0x7FFFFFFF`). The precompile execution path will call `new byte[0x7FFFFFFF][]` or attempt `words[offset + i + 1]` far past `words.length`, producing either an immediate `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` or an `OutOfMemoryError` during precompile execution triggered by a single unauthenticated `CALL`.

Note: I could not fully confirm within the available search budget (1) the exact precompile address/name that invokes `extractSigArray` (test evidence in `ValidateMultiSignContractTest.java` suggests it is the multi-sign validation precompile) nor (2) whether an outer `catch` in `VM.java`/`Program.java` converts `OutOfMemoryError`/`ArrayIndexOutOfBoundsException` into a safely-handled revert rather than a JVM-level crash. If the outer VM dispatch catches these as ordinary exceptions and only reverts the current transaction, the practical impact would be reduced to a transaction-scoped revert rather than a node crash — this should be verified against `actuator/src/main/java/org/tron/core/vm/VM.java` before treating this as Critical.

  private static byte[][] extractSigArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          SIG_LENGTH);
    }
    return bytesArray;
  }

  private static byte[] extractBytes(byte[] data, int offset, int len) {
    return Arrays.copyOfRange(data, offset, offset + len);
  }
