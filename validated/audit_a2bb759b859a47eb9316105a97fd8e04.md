The bug class here is a local, unprivileged denial of availability. The strongest reachable Metronome analog is the per-account token-list cap in `Pool`: an attacker can dust-transfer deposit tokens to a victim until their combined `debtTokensOfAccount + depositTokensOfAccount` count hits `MAX_TOKENS_PER_USER`, after which every path that adds a new token for that account reverts.

Relevant mechanics:

- `Pool.onlyIfAdditionWillNotReachMaxTokens` reverts with `UserReachedMaxTokens` once an account holds 30 tokens combined [1](#0-0) .
- `DepositToken._transfer` unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` on first receipt, so the revert propagates and the entire transfer fails [2](#0-1) .
- `DepositToken.deposit` mints via `_mint`, which routes through the same add path when the beneficiary's balance is zero, blocking `deposit(amount, victim)` for any collateral the victim doesn't already hold [3](#0-2) .
- Deposit tokens are permissionlessly transferable (`transfer`/`transferFrom` only check the *sender's* unlocked balance, not the recipient's list capacity), so the attacker can push arbitrary dust onto any victim [4](#0-3) . There is no opt-in/allowlist for incoming tokens.

### Title
Attacker can dust-fill a victim's token list to `MAX_TOKENS_PER_USER`, DoS-ing deposits and transfers of new collateral tokens - ([File: contracts/Pool.sol](contracts/Pool.sol), [File: contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
The `Pool` enforces a hard cap of 30 tokens per account (`MAX_TOKENS_PER_USER`), shared between deposit tokens and debt tokens. Any account that reaches the cap causes `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` to revert, and that revert propagates through `DepositToken._transfer` and the mint path in `deposit`. Because deposit tokens are freely transferable, an unprivileged attacker can deposit dust amounts of each pool collateral and transfer them to a victim until the victim's list is full, after which the victim can no longer receive a new deposit token via `transfer`, `transferFrom`, or `deposit(..., onBehalfOf_ = victim)`.

### Finding Description
1. `Pool` caps per-account tokens: `if (debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= MAX_TOKENS_PER_USER) revert UserReachedMaxTokens()` (`contracts/Pool.sol:143-148`).
2. `DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's prior balance is zero (`contracts/DepositToken.sol:517-520`); the same add happens on mint for first-time holders. Since `addToDepositTokensOfAccount` reverts inside `_transfer`, the whole ERC-20 `transfer`/`transferFrom`/`deposit`/`seize` transaction reverts.
3. The attacker only needs to deposit dust (`deposit` accepts any nonzero amount; `AmountIsZero` is the only floor) of up to 30 distinct deposit tokens (pool itself caps at 30) and `transfer` 1 wei of each to the victim.
4. Result: any subsequent `msdTokenX.transfer(victim, ...)`, `deposit(amount_, victim)`, or liquidation `seize` crediting a token the victim doesn't hold reverts with `UserReachedMaxTokens`, until the victim manually clears slots by transferring dust tokens out (which itself costs gas and requires the victim to even notice).

### Impact Explanation
Temporary freezing of funds and liveness failure for the targeted account: the victim cannot onboard new collateral types, cannot receive deposit tokens (including from smart-farming unwinds or third-party deposits on their behalf), and `seize`-based liquidation proceeds cannot deliver a new collateral token to an account at the cap. This matches the CVE's bug class — an unprivileged actor degrading protocol availability for another user at low cost (a bounded number of dust transfers). It is not a gas/unbounded-loop DoS; it exploits an explicit state cap that makes external calls revert deterministically.

### Likelihood Explanation
Fully permissionless and cheap: the attacker needs only dust balances of each collateral underlying and the gas for ≤30 deposits+transfers. No privileged role, oracle manipulation, or timing dependence. The constraint is that it is temporary — the victim can recover by emptying slots — so the impact is capped at temporary freezing rather than permanent loss, consistent with the source CVE's Medium severity.

### Recommendation
- Decouple the revert from the recipient: have `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` return a boolean and let `_transfer` skip tracking instead of reverting when the recipient is at cap (positions would still be accounted via `balanceOf`, though health checks over the set would need to account for untracked tokens), or
- Make tracking per-token opt-in and compute `debtPositionOf`/`depositOf` over all pool tokens rather than a per-account list, or
- At minimum, allow the recipient to reject/force-remove tokens from their list (e.g., a public `removeFromDepositTokensOfAccount` when the position is zero), so recovery doesn't require a counter-transfer.

### Proof of Concept
Reproducible on a Hardhat fork/test:

```ts
// contracts: Pool (pool), DepositToken[] msdX (all pool deposit tokens), underlying ERC20s
// attacker: EOA; victim: any account holding <30 tracked tokens

for (const msd of depositTokens) {
  // attacker deposits dust of underlying and transfers 1 wei of msdToken to victim
  const under = await ethers.getContractAt('IERC20', await msd.underlying());
  await under.connect(attacker).approve(msd.address, 1);
  await msd.connect(attacker).deposit(1, attacker.address);
  await msd.connect(attacker).transfer(victim.address, 1);
}
// victim now has depositTokensOfAccount.length == 30

// new collateral deposit on behalf of victim reverts:
await expect(
  msdNew.connect(donor).deposit(amount, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// direct transfer of an untracked token to victim also reverts:
await expect(
  msdNew.connect(donor).transfer(victim.address, 1)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

Caveat: severity is bounded by the victim's ability to clear slots by transferring out dust (small gas cost, requires awareness), so this is a temporary-freeze / griefing availability issue rather than permanent loss — consistent with the 4.7 Medium rating of the source advisory.
