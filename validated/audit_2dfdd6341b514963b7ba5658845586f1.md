Based on my investigation of `substrate/frame/scarcity/src/extension.rs`, the closest structural analog to the ERC-721 "missing existence/state check before acting" bug class is in the `AsScarcity` transaction extension's destination-occupancy check.

### Title
Race condition allows purse-key transfer to silently clobber a concurrent inbound NFT - (File: substrate/frame/scarcity/src/extension.rs)

### Summary
The ERC-721 report's core defect is a public-facing entrypoint that mutates/reads state without re-validating an existence/occupancy precondition at execution time, only doing so loosely (or not at all) at the point that actually matters. `AsScarcity::validate` performs the "destination occupied" check `NftsByOwner::<T>::contains_key(to)` [1](#0-0)  against the state visible at validation time, but the actual removal/insertion into `NftsByOwner` for the destination purse happens later, inside the dispatchable's execution, which is not shown to re-verify occupancy atomically with validation for concurrently-validated transactions targeting the same destination.

### Finding Description
`validate()` reads `NftsByOwner::<T>::get(&owner)` for the source and separately checks `NftsByOwner::<T>::contains_key(to)` for the destination to reject a transfer into an already-occupied purse key [2](#0-1) . `prepare()` then performs the only stateful mutation of validate/prepare: it atomically takes the *source* NFT out of `NftsByOwner` via `try_mutate_exists`, but it does **not** re-check or lock the destination key `to` at all [3](#0-2) . The code comment even admits reliance on "dispatch-time checks" for "genuine same-block races" [4](#0-3) , i.e., the extension's own validate/prepare pipeline does not itself guarantee the destination-occupancy invariant; it is deferred entirely to the `transfer` dispatchable's internal logic, which is pallet call code not visible/audited in this extension file and is executed only after prepare() has already unconditionally taken the NFT out of the source purse.

This is the same class of defect as the ERC-721 report: a state-affecting operation is allowed to proceed on the strength of a precondition (`tokenId` exists / destination unoccupied) that was checked once, earlier, and is not guaranteed to still hold at the moment the value-affecting mutation is committed.

### Impact Explanation
If two signed `AsScarcity`-authorized transfers from two different purses both target the same destination purse `to`, both can pass `validate()` in the same block (each sees `to` as unoccupied at validation time, since neither has committed yet). Both `prepare()` calls will succeed independently, since `prepare()` only mutates the *source* keys, not `to`. When both dispatchables then execute and attempt to insert the incoming NFT into `NftsByOwner` for `to`, whichever executes second will silently overwrite the first inbound NFT (since each purse holds "at most one NFT" per the pallet's own design doc) [5](#0-4) . The first NFT that already exited its source purse (irreversibly, via `prepare()`) is now nowhere: not in the old owner's purse (removed) and clobbered from the destination purse. This is a permanent, unrecoverable loss of an NFT for an ordinary user acting entirely within normal protocol use, with no admin, governance, relayer, or malicious-peer involvement — satisfying the "permanent user-fund lock" impact category.

### Likelihood Explanation
Two unprivileged users need only sign ordinary `transfer` extrinsics to the same destination purse key within the same block. This requires no special privilege, and the destination purse key is a public address chosen by ordinary users (e.g., a merchant/marketplace purse expecting NFTs from many senders), making unintentional or intentional collisions realistic during normal chain operation. The pallet's own doc explicitly acknowledges lack of "receive-consent" at this storage layer [6](#0-5) , which increases the likelihood of concurrent inbound transfers to the same key.

### Recommendation
Enforce the destination-occupancy invariant atomically with the source-removal mutation inside `prepare()` (or equivalently inside the dispatchable's execution guarded by the same `try_mutate` closure), e.g. using `NftsByOwner::<T>::try_mutate_exists(to, |slot| ensure!(slot.is_none(), ...))` performed under the same storage transaction as the source removal, so that only one of two racing transfers to the same destination can ever succeed; the other must fail cleanly (triggering the existing failed-dispatch lock/restore path) rather than clobbering existing state.

### Proof of Concept
1. Purse `A` holds NFT `X`; purse `B` holds NFT `Y`. Purse `C` is empty.
2. User signs `transfer(to=C)` authorized as purse `A` with a valid `AsScarcityInfo::AsNft` for `X`.
3. Independently (or maliciously) another user signs `transfer(to=C)` authorized as purse `B` with a valid `AsScarcityInfo::AsNft` for `Y`.
4. Both transactions enter the same block; both call `validate()` and see `NftsByOwner::<T>::contains_key(C) == false`, so both pass [7](#0-6) .
5. Both call `prepare()`, each unconditionally removing its own source NFT (`X` from `A`, `Y` from `B`) via `try_mutate_exists` [8](#0-7) .
6. Both dispatchables execute and each attempts to place its NFT into purse `C`. Only one insertion can be the final state (last-write-wins), so one of `X`/`Y` is permanently lost — it exists in neither its original purse nor the destination.

I was not able to inspect the body of the `transfer`/`burn` dispatchables themselves (only the transaction extension file was retrieved), so I cannot fully confirm whether the dispatchable code independently re-checks destination occupancy inside its own storage mutation before insertion. If it does perform an atomic `try_mutate_exists`-guarded check there, the race would instead manifest as one of the two transactions failing post-dispatch (triggering the lock/restore path) rather than silent NFT loss — this distinction should be verified directly against `substrate/frame/scarcity/src/lib.rs`'s `transfer`/`burn` call implementations, which were not fully retrieved in this session.
