### Title
DoS of `git pack-objects` cache pipe via a client that opens a reader but withholds read progress, causing indefinite resource pinning - ([File: internal/streamcache/pipe.go])

### Summary
The pack-objects cache's backpressure mechanism blocks the writer goroutine (running `git-pack-objects`) until *some* subscribed reader advances the shared read cursor. A client can open the cache entry as a reader (satisfying the "reader exists" check) and then simply stop reading without closing the connection. Because the write-side goroutine is deliberately shielded from the originating request's context cancellation, and the only unblocking conditions are "a reader advances" or "all readers close," an unprivileged client can pin a server-side `git-pack-objects` process indefinitely, analogous to how the ERC777 report's attacker registers a persistent hook/callback that it then never completes, stalling shared execution for other users.

### Finding Description
`packObjectsHook` computes a cache key from the request (repository, args, protocol, remote IP class, and stdin) and calls `s.packObjectsCache.Fetch()`, which either joins an existing cache entry as a new reader or spawns a producer goroutine running `git-pack-objects` via `runPackObjects` [1](#0-0) .

The producer goroutine is explicitly detached from the request's cancellation: `ctx = context.WithoutCancel(ctx)` is used specifically so that one client hanging up does not affect other clients sharing the same cache key [2](#0-1) .

The actual backpressure gating lives in `internal/streamcache/pipe.go`. The writer's `Write()` loops `for p.wcursor.Position() > p.rcursor.Position()`, blocking on either a notification that `rcursor` advanced or `wcursor.Done()` (which only fires once *all* readers have closed) [3](#0-2) . Readers advance `rcursor` only when they actually call `Read()` [4](#0-3) , and `cursor.SetPosition` is monotonic per-subscriber with no deadline or liveness check [5](#0-4) .

Consequently, a reader that is opened but never calls `Read()` and never closes its connection keeps its subscription registered on `wcursor`, so `wcursor.Done()` never fires, and if it is the only (or slowest-but-not-closing) reader, the writer can block forever with no timeout. There is no per-reader liveness timeout enforced by the pipe or by `packObjectsHook`.

This exactly mirrors the bug class in the ERC777 report: an unprivileged actor triggers a shared, cross-user execution path (there: token transfer hooks; here: the pack-objects cache pipe) and then deliberately withholds the action needed to let it complete (there: reverting the hook; here: never reading/never closing), causing indefinite resource lock/DoS of a mechanism that is meant to be shared across multiple ordinary users' requests.

### Impact Explanation
The pinned `git-pack-objects` subprocess and its goroutine consume CPU, memory, and a cache-entry disk file for as long as the attacker's connection to the sidechannel is kept open. Because the goroutine survives cancellation of the original RPC by design (`context.WithoutCancel`), an ordinary client can hold this state open far longer than any single RPC deadline. Repeating this with several concurrent connections/keys (e.g., varying remote IP, protocol, or fetch `want`/`have` sets) allows an unprivileged, unauthenticated-to-repo-write (fetch-only) user to accumulate multiple hung `git-pack-objects` processes and cache files, degrading or exhausting Gitaly server resources (CPU threads, memory, file descriptors, disk in the cache directory) and causing denial of service to fetches/clones from other users, including ones that would otherwise share the same cache key. This is documented as a real operational risk in the design docs, though the docs describe it primarily as a side effect of legitimate slow readers rather than a deliberately hostile "open but never read" client [6](#0-5) .

### Likelihood Explanation
Reaching this path requires only the ability to issue a standard `PostUploadPack`/`SSHUploadPack`/`PackObjectsHookWithSidechannel` fetch request against a repository the caller can already read — no special privileges, no leaked token, and no malicious peer/MITM assumptions are needed. The attacker fully controls when (or whether) they read from the sidechannel socket and when they close it, which is precisely the trigger condition described above. Because backpressure is enabled by default (`backpressure = true`), this is exploitable out of the box unless an operator has proactively disabled it after already observing the documented symptom (hung `git-pack-objects` processes) [7](#0-6) .

### Recommendation
Add a liveness/idle timeout to `pipeReader`/`pipe.Write()` so that a reader which has not advanced its cursor within a bounded period is treated as if it had closed (unsubscribed), unblocking the writer and freeing the underlying `git-pack-objects` process. Alternatively, bound the producer goroutine in `runPackObjects`/`packObjectsHook` with its own hard deadline independent of the originating request's context, so a stalled-but-open reader cannot pin server resources indefinitely.

### Proof of Concept
1. An unprivileged client establishes a fetch/clone that triggers `PostUploadPackWithSidechannel`/`SSHUploadPackWithSidechannel`, causing Gitaly to invoke `PackObjectsHookWithSidechannel` and create a new pack-objects cache entry (cache miss), spawning `runPackObjects` in a background goroutine [1](#0-0) .
2. Over the sidechannel Unix socket, the client sends valid `want`/`have` data so the server starts generating a (large) packfile, then reads at most one byte from the response and stops reading further, while keeping the socket/connection open (not calling `CloseWrite`/closing it). This mirrors the exact interaction pattern already exercised in `TestServer_PackObjectsHook_separateContext`, which shows a caller reading one byte and then stalling before finishing [8](#0-7) .
3. Because `runPackObjects` runs with `context.WithoutCancel(ctx)`, the goroutine is immune to the originating RPC being torn down, and `pipe.Write()` blocks on `p.wnotifier.C`/`p.wcursor.Done()`, neither of which fire since the reader neither advances nor closes [3](#0-2) .
4. Repeating this with several concurrent connections (each yielding a distinct cache key by varying arguments/remote IP/protocol) accumulates multiple indefinitely-blocked `git-pack-objects` processes and cache files, consuming server resources and degrading service for other users' fetches — a testable DoS condition, though full resource-exhaustion at scale would need to be validated against the deployed process/FD limits which are not part of the reviewed code paths.

func (p *pipe) Write(b []byte) (int, error) {
	// Loop (block) until at least one reader catches up with our last write.
	if p.backpressure {
		for p.wcursor.Position() > p.rcursor.Position() {
			select {
			case <-p.wcursor.Done():
				// Prevent writing bytes no-one will read
				return 0, errWrongCloseOrder
			case <-p.wnotifier.C:
			}
		}
	} else {
		// Even though disabling backpressure allows the writer to write data without waiting for readers, it
		// does not make sense to continue writing if nobody is interested in the result anymore.

		case <-p.wcursor.Done():

func (pr *pipeReader) advancePosition(n int) {
	pr.position += int64(n)

	// The writer is subscribed to changes in pr.pipe.rcursor. If it is
	// currently blocked, this call to SetPosition() will unblock it.
	pr.pipe.rcursor.SetPosition(pr.position)
}

func (pr *pipeReader) Read(b []byte) (int, error) {
	pr.waitReadable()
	n, err := pr.reader.Read(b)
	pr.advancePosition(n)
	return n, err
}

// SetPosition sets c.pos to the new value pos, but only if pos>c.pos. In the
// case that c.pos actually grew, all subscribers are notified.
func (c *cursor) SetPosition(pos int64) {
	if pos <= c.Position() {
		return
	}

	c.m.Lock()
	defer c.m.Unlock()

	// Check a second time now we hold the write lock.
	if pos <= c.pos {
		return
	}

	c.pos = pos
	for _, n := range c.subscribers {
		n.Notify()
	}
}

While the backpressure mechanism provides the benefits described above, it can have a side effect:
`git-pack-objects` processes may remain in a waiting state until the fastest client requesting the
same cache key completes its operation. During this waiting period, these processes can occupy
substantial server resources.

Consider disabling backpressure if you observe:

- Hung `git-pack-objects` processes occupying excessive server resources
- Memory pressure during heavy load scenarios
- Slower overall performance with backpressure enabled

When backpressure is disabled, Gitaly will write to the cache at its maximum rate regardless of
client consumption, which may increase I/O but could improve throughput in certain environments,
especially when there are many concurrent fetches of the same data.
