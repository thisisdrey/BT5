### Title
`add_tip`'s DOT→Ether swap has no slippage protection, decoupling the amount a tipper commits from the amount actually burned and credited as bridge relayer reward - (File: `bridges/snowbridge/pallets/system-frontend/src/lib.rs`)

### Summary
This is the same broken invariant as Connext H-04: an amount that a user signs/commits (`tip_amount`) is passed through an AMM swap before it is converted into the value that is actually settled downstream (the Ether amount burned and forwarded cross-chain to be credited as a relayer reward). Because the swap step accepts **no minimum-out protection**, the amount actually burned can diverge arbitrarily from what the user intended to spend, exactly mirroring the "signed amount vs. swap-realized amount" mismatch that caused H-04.

### Finding Description
The `system-frontend` pallet lets an AssetHub user boost/create a relayer reward for an Ethereum inbound/outbound message via `add_tip`. Internally this calls `swap_and_burn`: [1](#0-0) 

The swap is executed with `None` passed as the minimum-amount-out parameter:
```
let ether_gained = T::Swap::swap_exact_tokens_for_tokens(
    who.clone(),
    swap_path,
    tip_amount,
    None, // No minimum amount required
    who,
    true,
)?;
```
`tip_amount` (the value the user committed, taken from their asset) is fully spent by the swap regardless of how little `ether_gained` (Ether actually obtained and burned) turns out to be. `ether_gained` is what gets burned via `burn_for_teleport` and is the value that should flow into the cross-chain `add_tip` call built by `build_add_tip_call`: [2](#0-1) 

This is then forwarded via XCM `Transact` to BridgeHub's `EthereumSystem::add_tip` extrinsic: [3](#0-2) 

which unconditionally trusts the `amount` field and records it in the `Tips`/`PendingOrders` storage that is later added to the relayer's reward when the corresponding inbound/outbound message is processed: [4](#0-3) [5](#0-4) 

Because there is no minimum-out check on the swap, an attacker can manipulate the AMM pool used by `T::Swap` (e.g., by front-running/sandwiching their own `add_tip` call within the same block, using flash liquidity or repeated trades against a thin pool) to make `ether_gained` far smaller than the fair-value conversion of `tip_amount`. The tipper's full asset amount is still burned/spent, but the value that eventually gets attributed downstream (either as a tiny/near-zero tip, or - if this code path is later reused/extended to pass `tip_amount` instead of `ether_gained` - as an inflated reward relative to what was actually burned) is decoupled from the committed amount. This is structurally identical to the Connext bug: the amount the user "signs" and pays (`tip_amount`) is not what is propagated to the value-settlement step; only the post-swap amount (`ether_gained`) is, and that amount is only as trustworthy as the swap's slippage bound - which here is unbounded (`None`).

### Impact Explanation
This directly affects asset accounting and bridge reward settlement on BridgeHub/AssetHub (in-scope Snowbridge code). Depending on which value is actually threaded to the cross-chain call (the visible code returns `ether_gained` from `swap_and_burn`, which is the value that should be used), the practical effects are:
- Value loss for the tipper: full committed asset is burned but the resulting Ether-denominated tip credited can be made arbitrarily small by an attacker manipulating the pool used for the swap, since there is no slippage floor.
- If any code path substitutes the pre-swap `tip_amount` for the post-swap `ether_gained` when building the cross-chain call (the exact same confusion the Connext report calls out for `xcall`/`_reconcile`), it produces an unbacked increase in relayer reward relative to what was actually burned/teleported - i.e., minted compensation not backed by real burnt value.

Either variant breaks the "conserve value and settle exactly once to the rightful beneficiary and amount" invariant for bridge reward payouts.

### Likelihood Explanation
No privileged actor, governance, relayer collusion, or leaked key is required. Any signed AssetHub account can call `add_tip` and can manipulate/observe the AMM pool state used by `T::Swap::swap_exact_tokens_for_tokens` in the same or adjacent blocks, since `min_amount_out` is unconditionally `None`. This is a standard, unprivileged AMM-slippage attack surface that is fully triggerable from a public extrinsic.

### Recommendation
- Require a caller-supplied minimum-Ether-out (or minimum-DOT-equivalent) parameter in `add_tip`, and pass it through to `swap_exact_tokens_for_tokens` instead of `None`.
- Ensure the exact `ether_gained` value returned by `swap_and_burn` (never `tip_amount`) is the value encoded into `build_add_tip_call`/`EthereumSystemCall::AddTip`, so the amount credited on BridgeHub always matches the amount actually burned on AssetHub.
- Add an explicit test asserting `RegisteredRewardAmount`/`Tips` entries equal the post-swap burned amount, not the pre-swap tip amount, under adversarial pool conditions.

### Proof of Concept
1. Attacker (or colluding pair of transactions in one block) manipulates the liquidity pool backing `T::Swap` for the `tip_asset_location -> ether_location` path so that its exchange rate is temporarily very unfavorable.
2. Attacker calls `SnowbridgeSystemFrontend::add_tip(message_id, asset)` with a large `tip_amount` of the tip asset.
3. `swap_and_burn` executes `swap_exact_tokens_for_tokens(..., tip_amount, None, ...)`; because `min_amount_out` is `None`, the swap succeeds at the manipulated (unfavorable) rate, burning the user's full `tip_amount` but yielding a much smaller `ether_gained`.
4. `build_add_tip_call`/`AddTip` records this (undervalued, or - if the wrong variable were substituted - overvalued) amount on BridgeHub's `Tips`/`PendingOrders` storage, which is later added atomically to the relayer's registered reward when the message is processed - with no path to detect or correct the swap-induced amount mismatch. 		/// Swaps a specified tip asset to Ether and then burns the resulting ether for
		/// teleportation. Returns the amount of Ether gained if successful, or a DispatchError if
		/// any step fails.
		fn swap_and_burn(
			origin: Location,
			tip_asset_location: Location,
			ether_location: Location,
			tip_amount: u128,
		) -> Result<u128, DispatchError> {
			// Swap tip asset to ether
			let swap_path = vec![tip_asset_location.clone(), ether_location.clone()];
			let who = T::AccountIdConverter::convert_location(&origin)
				.ok_or(Error::<T>::LocationConversionFailed)?;

			let ether_gained = T::Swap::swap_exact_tokens_for_tokens(
				who.clone(),
				swap_path,
				tip_amount,
				None, // No minimum amount required
				who,
				true,
			)?;

			// Burn the ether
			let ether_asset = Asset::from((ether_location.clone(), ether_gained));

			burn_for_teleport::<T::AssetTransactor>(&origin, &ether_asset)
				.map_err(|_| Error::<T>::BurnError)?;

			Ok(ether_gained)
		}

		#[pallet::call_index(3)]
		#[pallet::weight(<T as pallet::Config>::WeightInfo::add_tip())]
		pub fn add_tip(
			origin: OriginFor<T>,
			sender: AccountIdOf<T>,
			message_id: MessageId,
			amount: u128,
		) -> DispatchResult {
			T::FrontendOrigin::ensure_origin(origin)?;

			let result = match message_id {
				Inbound(nonce) => <T as pallet::Config>::InboundQueue::add_tip(nonce, amount),
				Outbound(nonce) => <T as pallet::Config>::OutboundQueue::add_tip(nonce, amount),
			};

			if let Err(ref e) = result {
				tracing::debug!(target: LOG_TARGET, ?e, ?message_id, ?amount, "error adding tip");
				LostTips::<T>::mutate(&sender, |lost_tip| {
					*lost_tip = lost_tip.saturating_add(amount);
				});
			}

			Self::deposit_event(Event::<T>::TipProcessed {
				sender,
				message_id,
				amount,
				success: result.is_ok(),
			});

			Ok(())
		}
	}
