### Title
Non-constant-time comparison of the `auth_token`/password on privileged RPC endpoints enables timing-based secret recovery and auth bypass - (File: `stackslib/src/net/api/blockreplay.rs`, `blocksimulate.rs`, `fastcallreadonly.rs`, `postblock_proposal.rs`, `postblock_v3.rs`, `txsimulate.rs`)

### Summary
Every privileged Stacks node RPC endpoint that is gated by the node's `connection_options.auth_token` verifies the caller-supplied `authorization` header against the configured secret using a plain Rust string inequality check (`auth_header != password`). This is a non-constant-time comparison, which is the same class of "weak secret" defect as the LoLLMs report: instead of a brute-forceable JWT-signing key, the equality check itself leaks byte-position information about the correct secret to a remote, unauthenticated attacker, who can use timing measurements to incrementally recover the full `auth_token` and then forge authenticated requests to privileged endpoints.

### Finding Description
The node's shared secret (`connection_options.auth_token`, documented at [1](#0-0) ) is meant to gate sensitive endpoints such as `/v3/block_proposal` and `/v2/blocks?broadcast=1`. The OpenAPI spec explicitly states this is a "Plain-text secret value that must exactly equal the node's configured password" [2](#0-1) .

Every handler that enforces this check does so with a naive `!=` comparison on the raw header string, e.g. in `RPCBlockProposalRequestHandler::try_parse_request`: [3](#0-2) 

The identical pattern (`if auth_header != password { return Err(Error::Http(401, "Unauthorized".into())); }`) recurs verbatim in:
- `RPCNakamotoBlockReplayRequestHandler::try_parse_request` [4](#0-3) 
- `RPCFastCallReadOnlyRequestHandler::try_parse_request` [5](#0-4) 
- `RPCTransactionSimulateRequestHandler::try_parse_request` [6](#0-5) 
- `RPCPostBlockRequestHandler::try_parse_request` (guards `broadcast=1`) [7](#0-6) 
- `RPCNakamotoBlockSimulateRequestHandler` (same handler family, `blocksimulate.rs`) [8](#0-7) 

Rust's `str`/`String` `PartialEq` performs a byte-slice comparison that is not designed to run in constant time; it commonly short-circuits on length mismatch and can terminate comparison early depending on the underlying memcmp implementation. Because these handlers run in `try_parse_request`, which executes before any expensive parsing/processing on `401` rejection, the response time is dominated almost entirely by the comparison itself, making a timing side channel plausible for a sufficiently patient/averaging remote attacker. This lets an attacker treat the secret comparison as an oracle and reconstruct the `auth_token` character by character rather than needing to guess the full high-entropy string at once — directly analogous to the GHSA report's scenario where a weak/predictable secret allows offline recovery followed by forgery of privileged credentials.

### Impact Explanation
Recovering `auth_token` allows a remote, unauthenticated attacker to:
- Submit forged, authenticated `POST /v3/block_proposal` requests, injecting attacker-controlled block proposals into the signer coordination path.
- Set `broadcast=1` on `POST /v2/blocks`, forcing the node to broadcast attacker-supplied blocks to the network.
- Access `fast-call-read`, block-replay, and transaction-simulate endpoints that are normally restricted to trusted signer/miner operators.

This matches the "Critical: unauthenticated/unauthorized write to state ... or auth bypass" impact bucket in scope.

### Likelihood Explanation
The `auth_token` is typically a long, high-entropy operator-chosen string (see `sample/conf/mainnet-miner-conf.toml`, `docs/signing.md`), so full guessing/brute force is infeasible. However, none of these handlers apply constant-time comparison (e.g. `subtle::ConstantTimeEq`) despite the value acting as a bearer secret over the network, and this same anti-pattern is duplicated across six independent handler implementations rather than being centralized in one constant-time helper — increasing the attack surface and the chance that any future callers inherit the same flaw. Practical exploitation requires many timed requests and statistical averaging to overcome network jitter, so likelihood is lower than a pure logic/auth-bypass bug, but the underlying design flaw (secret compared via non-constant-time equality on every privileged endpoint) is concretely present and reachable by any unauthenticated remote peer.

### Recommendation
Centralize the auth-token check into a single helper that uses a constant-time comparison (e.g., `subtle::ConstantTimeEq`, or compare over a keyed HMAC of the header/secret) and call it from all six handlers instead of duplicating `auth_header != password` in each file.

### Proof of Concept
1. Configure a node with `connection_options.auth_token = "<secret>"` and enable `/v3/block_proposal`.
2. From an unauthenticated remote client, repeatedly send `POST /v3/block_proposal` with `authorization` headers that are correct-prefix + guessed-next-byte + random suffix, measuring response latency to the 401 for each guess.
3. Statistically, guesses whose prefix matches more of the true secret take marginally longer to be rejected because more bytes must be inspected before the comparison diverges; average many trials per candidate byte to filter noise and iteratively determine the correct next byte until the full `auth_token` is recovered.
4. Use the recovered token to submit an authenticated `POST /v3/block_proposal` or `POST /v2/blocks?broadcast=1` request as proof of forged access to the code paths at [3](#0-2)  and [7](#0-6) .
