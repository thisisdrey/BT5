### Title
Unauthenticated `RecvError` packet allows spoofed-source tunnel teardown / remote state poisoning - ([File: outside.go])

### Summary
Nebula's `handleRecvError` processes the plaintext, unauthenticated `header.RecvError` packet type and tears down a victim's tunnel based on an attacker-controlled index and a spoofable UDP source address, with no certificate or AEAD authentication involved. This mirrors the root cause of the reported `PerpDepository#rebalance` bug: a function trusts an unauthenticated, caller-supplied identifier as if it were a verified identity, and uses it to take a destructive action against a third party's state.

### Finding Description
`readOutsidePackets` dispatches `header.RecvError` before any hostinfo lookup, decryption, or certificate check — it is handled in the same "Unencrypted packets" branch as the handshake type: [1](#0-0) 

That call reaches `handleRecvError`: [2](#0-1) 

The function:
1. Looks up a hostinfo purely by `h.RemoteIndex` — a 32-bit value taken directly from the unauthenticated packet header (`f.hostMap.QueryReverseIndex(h.RemoteIndex)`).
2. Performs a "spoofing" check by comparing the packet's UDP source address (`addr`, which is the raw `fromUdpAddr` passed up from `li.ListenOut` in `listenOut`, i.e., attacker-controlled and never cryptographically bound to the packet) against the hostinfo's currently stored remote address (`hostinfo.GetRemote()`).
3. If the two addresses match (or if the hostinfo has no remote set yet — `hr.IsValid()` is false, which is common while `remotes` haven't converged, e.g. right after a roam or reconnect), it unconditionally calls `f.closeTunnel(hostinfo)` and also deletes any pending handshake state.

Because the RemoteIndex is just the `localIndexId` of the victim's tunnel (a value that is visible in the plaintext header of every ordinary packet the victim sends/receives, and that in this codebase is allocated via `generateIndex`), and because the "remote address" comparison is over a plain UDP source address with no MAC/signature binding, an attacker who can observe or infer the victim's `RemoteIndex`/remote UDP endpoint (e.g., an off-path attacker who knows the victim's public lighthouse-advertised address, or any attacker capable of UDP source spoofing) can forge a single unauthenticated `RecvError` packet that will be accepted as if it came from the legitimate peer, causing the victim's fully-established, cert-authenticated tunnel to be torn down.

This is the same bug class as the report: a privileged/destructive operation (`rebalance`'s shortfall debit; here, tunnel teardown) is gated on an attacker-suppliable value (`account`; here, `RemoteIndex` + spoofable source `addr`) instead of a value that has actually been authenticated (`msg.sender`; here, a MAC/AEAD-protected sender identity). No CA-signed certificate, no completed handshake, and no valid peer state is required by the attacker to trigger it — only a properly-formed 8-byte header of type `RecvError`.

### Impact Explanation
An unauthenticated, off-path attacker who can guess or observe a victim's `RemoteIndex` (leaked in the plaintext header of every packet on that tunnel) and knows/spoofs the tunnel's UDP endpoint can force the victim to tear down an established, mutually-authenticated tunnel at will, repeatedly, denying service and forcing constant re-handshakes. This is a remote state-poisoning / denial-of-service primitive reachable without holding any valid certificate, matching the "Accept only concrete ... remote state poisoning ... impact" bar.

### Likelihood Explanation
Exploitability depends on the attacker knowing the victim's `RemoteIndex` and being able to source a UDP packet appearing to come from the tunnel's current remote endpoint. `RemoteIndex` is not secret — it is transmitted in the clear on every ordinary data packet of that tunnel, so any attacker positioned to observe traffic (or who previously interacted with the host, e.g., as a lighthouse-known peer or via a prior handshake attempt that was subsequently torn down) can learn it. The address check is also bypassable whenever `hostinfo.GetRemote()` is not yet set (`!hr.IsValid()`), which is a legitimate, non-rare state (freshly created hostinfo, mid-roam). No cryptographic proof of possession of any key is required, distinguishing this from the excluded "valid-certificate-holder" analogs.

### Recommendation
Do not act on `RecvError` (or any other pre-authentication packet type) using only the unauthenticated packet header and UDP source address. At minimum:
- Require the `RecvError` payload to include an authenticated tag (e.g., a value derivable only by a party who already possesses the tunnel's negotiated key), rather than relying solely on `RemoteIndex` + a plaintext source-address comparison.
- Treat `hr.IsValid() == false` as "cannot verify sender" and refuse to close the tunnel in that case, rather than allowing it to fall through to teardown.
- Consider requiring some in-window/replay-protected nonce or moving `RecvError` handling to only be honored for packets that carry a valid AEAD tag under the current session keys, closing the tunnel only after that authentication succeeds.

### Proof of Concept
1. Attacker observes (via passive capture, a prior aborted handshake, or knowledge of a lighthouse-advertised endpoint) the victim's current `RemoteIndex` for an established tunnel and the tunnel's remote UDP endpoint address `addr`.
2. Attacker crafts an 8-byte Nebula header with `Type = header.RecvError`, `RemoteIndex = <observed victim localIndexId>`, and sends it over UDP with a spoofed source address equal to `addr` (or simply targets a moment when `hostinfo.remote` is not yet set, e.g. right after the peer roamed).
3. `readOutsidePackets` routes the packet directly to `f.handleRecvError(via.UdpAddr, h)` without any decryption or cert check (see `outside.go:81-83`).
4. `handleRecvError` finds the hostinfo via `QueryReverseIndex`, the address check passes (spoofed match, or `hr.IsValid()==false`), and calls `f.closeTunnel(hostinfo)` plus `f.handshakeManager.DeleteHostInfo(hostinfo)`, terminating the victim's legitimate tunnel without the attacker ever presenting a certificate or completing a handshake.

func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
