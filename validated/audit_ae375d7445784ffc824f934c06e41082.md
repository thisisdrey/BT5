### Title
Liquidation-time debt burn writes a stale `debtIndex` without accruing interest, re-charging already-settled interest - (contracts/DebtToken.sol: `DebtToken.burn` / `_burn`)

### Summary
`DebtToken._burn` snapshots the victim's interest-inclusive balance via `balanceOf(account_)` (which computes the up-to-date index via `_calculateInterestAccrual()`), but then persists `debtIndexOf[account_] = debtIndex` using the *stale stored* index and decrements `totalSupply_` without ever calling `accrueInterest()` or updating the stored `debtIndex`/`lastTimestampAccrued`. Every public debt-mutating entry point (`issue`, `repay`, `repayAll`, `mint`, `flashIssue`) explicitly calls `accrueInterest()` first — except `burn(address,uint256)`, which is `onlyPool` and is invoked by `Pool.liquidate`/`Pool._liquidate`. This mirrors the audited ELFI bug class: a state-changing path that alters the debt principal without first synchronizing the interest index.

### Finding Description
- `accrueInterest()` (contracts/DebtToken.sol:156) updates `totalSupply_`, `debtIndex`, and `lastTimestampAccrued` lazily; `balanceOf` (line 196) computes the *virtual* index from `_calculateInterestAccrual()` (line 551) without storing it.
- `_burn` (lines 525–543) does `principalOf[account_] = _accountBalance - amount_` where `_accountBalance` already includes interest accrued since `lastTimestampAccrued`, but stores `debtIndexOf[account_] = debtIndex` — the *old* stored index — and never adds `_interestAmountAccrued` to `totalSupply_` or stores the new `debtIndex`.
- If `Pool.liquidate` reaches `debtToken.burn(from_, amount_)` without a preceding `accrueInterest()` (the grep shows burn/accrue references in `Pool.sol` but I could not confirm an accrual call on the liquidation path within the available iterations — this is the key link to verify), then after seizure the victim's `balanceOf = principalOf * newIndex / debtIndexOf` uses a denominator that is too small, so the interest that was just folded into `principalOf` is counted a second time.

### Impact Explanation
Over- or under-accrual of debt on liquidated positions: the victim's remaining debt is re-charged the interest accrued between `lastTimestampAccrued` and the liquidation, and `totalSupply_`/`debtIndex` drift out of sync, causing unfair fee accrual and premature or unfair subsequent liquidations — the same invariant break (interest index vs. principal mutation ordering) as the reference finding.

### Likelihood Explanation
Reachable by any unprivileged liquidator via `Pool.liquidate` on an unhealthy position whenever `block.timestamp > lastTimestampAccrued` — i.e., effectively every liquidation. Caveat: validity depends on `Pool.sol` not calling `accrueInterest()` before `debtToken.burn`; I was not able to view the liquidation function body in the available iterations. If `Pool._liquidate` (or a preceding `debtOf`-style call) does not accrue first, the bug is live on deployed configuration.

### Recommendation
Call `accrueInterest()` at the start of `DebtToken.burn` (or at the top of `Pool.liquidate`/`Pool._liquidate` before any debt burn), mirroring `issue`/`repay`; alternatively store the freshly computed `_debtIndex` in `debtIndexOf` inside `_burn`/`_mint` instead of the stale stored `debtIndex`.

### Proof of Concept
Hardhat sketch: deposit collateral and `issue` debt for victim; advance time so interest accrues virtually (stored `debtIndex` unchanged); drop collateral price via mocked oracle so the position is liquidatable; call `pool.liquidate(...)` so `debtToken.burn(victim, x)` executes; assert `debtIndexOf[victim] == debtIndex` where `debtIndex < _calculateInterestAccrual()`'s fresh index, and that a subsequent `accrueInterest()` leaves `balanceOf(victim)` strictly greater than `principalOf[victim]` — i.e., the interest already folded into `principalOf` is charged twice.
