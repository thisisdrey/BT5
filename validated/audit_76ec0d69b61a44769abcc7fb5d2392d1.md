Confirmed: `intValueSafe()` returns `Integer.MAX_VALUE` (not a validated/small number) whenever the encoded length occupies more than 4 bytes or is negative [1](#0-0) , so an attacker fully controls the `len` value fed into `extractBytesArray`/`extractBytes32Array` via ordinary calldata.

### Title
Unbounded array allocation from attacker-controlled length in TVM precompiles causes node OOM/DoS - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `validatemultisign` and `batchvalidatesign` TVM precompiles decode an attacker-supplied "array length" word from contract calldata and use it directly to size a Java array (`new byte[len][]`) **before** any upper-bound check is applied, when the `allowTvmSelfdestructRestriction` hard-fork switch is not the active code path. Because `DataWord.intValueSafe()` clamps out-of-range values to `Integer.MAX_VALUE` rather than rejecting them, a single crafted contract call can attempt to allocate an array with up to `Integer.MAX_VALUE` element slots, which will throw `OutOfMemoryError`/exhaust the JVM heap on the node executing or validating the transaction.

### Finding Description
`extractBytesArray` and `extractBytes32Array` read `len = words[offset].intValueSafe()` and immediately allocate `new byte[len][]` with no maximum size check inside the helper itself [2](#0-1) .

The size guard (`sigArraySize > MAX_SIZE` / `addrArraySize > MAX_SIZE`) that is supposed to prevent this is only applied conditionally on `VMConfig.allowTvmSelfdestructRestriction()`:
- In `ValidateMultiSign.execute`, the bound check runs only `if (VMConfig.allowTvmSelfdestructRestriction())`; the unguarded `extractBytesArray(...)` call is used whenever that flag is false [3](#0-2) .
- In `BatchValidateSign.doExecute`, the same pattern repeats for both `extractBytesArray` and `extractBytes32Array` [4](#0-3) .

Since `intValueSafe()` returns `Integer.MAX_VALUE` for any oversized/negative length word instead of throwing or rejecting [1](#0-0) , an attacker only needs to place a 32-byte word encoding a value ≥ 2^32 (or with the high bit set) at the appropriate calldata offset to drive `len` to `Integer.MAX_VALUE`, causing `new byte[Integer.MAX_VALUE][]` (~17 GB of null references on a 64-bit JVM) to be allocated synchronously inside contract execution.

### Impact Explanation
Any unprivileged account can deploy a contract that calls these precompiles (`0x0...66`-style precompile addresses for `validatemultisign`/`batchvalidatesign`) or directly craft a transaction invoking them, triggering an `OutOfMemoryError` in the executing node's JVM. Because this code runs during both transaction execution (`RuntimeImpl`) and re-execution during block validation by every full node/witness that processes the block, this is a low-cost, repeatable node-crash / consensus-halt vector — matching the "node crash or halt" acceptance bar for this scan.

### Likelihood Explanation
The path is reachable by any anonymous contract deployer/caller with no special permission needed: it only requires crafting calldata for `validatemultisign(address,uint256,bytes32,bytes[])` or `batchvalidatesign(...)` with a malicious length word in the `bytes[]` array header, and the exploit is only effective on chains/paths where `allowTvmSelfdestructRestriction` is not yet enforced for the call route taken (the code demonstrates the guard is explicitly conditional, meaning the unguarded branch is a currently-compiled, reachable code path).

### Recommendation
Move the size checks (`MAX_SIZE`) into `extractBytesArray`/`extractBytes32Array`/`extractSigArray` themselves, unconditionally, before allocating the array, rather than gating them behind `allowTvmSelfdestructRestriction()`. Additionally, `DataWord.intValueSafe()`-derived lengths used for array sizing should always be checked against a small protocol-defined maximum (e.g., `MAX_SIZE`) prior to any `new byte[len][]` allocation, independent of feature-activation flags.

### Proof of Concept
1. Build calldata for `batchvalidatesign(bytes32,bytes[],bytes32[])` (or `validatemultisign`) where the ABI array-length word for the `bytes[]` parameter is set to a value that causes `intValueSafe()` to clamp to `Integer.MAX_VALUE` (e.g., a length word with any byte set beyond the 4 low-order bytes).
2. Submit a transaction that calls this precompile (directly or via a simple contract) on a node where the `allowTvmSelfdestructRestriction` guard is not applied to the invoked code branch.
3. Observe the node's JVM throw `OutOfMemoryError` while attempting `new byte[Integer.MAX_VALUE][]` inside `extractBytesArray`, crashing/halting transaction processing on that node.

**Note on completeness:** I was unable to fully confirm, without deeper cross-referencing of the hard-fork activation status in this specific fork/version (`java-tron--022`), whether `allowTvmSelfdestructRestriction` is already permanently forced "true" on all live networks for this codebase — if so, the unguarded branch would be dead code on mainnet but still reachable on any network/test chain that has not activated this proposal, or during pre-activation processing of historical blocks/replay.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
