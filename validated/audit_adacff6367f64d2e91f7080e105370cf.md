This confirms the analysis. `verify_nonce` at `runtime/runtime/src/verifier.rs:210-237` caps any accepted transaction nonce at `tx_nonce < block_height * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` (the `NonceTooLarge` check at lines 229-234), so any nonce ever accepted for a key while it existed at block height `b` satisfies `tx_nonce < b * 1_000_000`. When the key is deleted and re-added at block height `h`, `add_regular_key` (`runtime/runtime/src/access_keys.rs:230-241`) sets the floor via `initial_nonce_value(h) = (h-1) * 1_000_000` (`access_keys.rs:46-50`). Since `h >= b`, the new floor `(h-1)*1_000_000` is always `>=` the maximum nonce ever accepted at block `b` (`< b*1_000_000`), so the new key can never accept a replay of an old signed transaction — the floor is monotonically non-decreasing in block height, independent of how many DeleteKey/AddKey cycles occur.

Critically, within a single block height `h`, `initial_nonce_value(h)` is a pure function of `h` only — repeating the DeleteKey/AddKey cycle `M` times in block `h` produces the exact same floor `(h-1)*1_000_000` on every cycle. There is no cumulative or incremental effect from cycling; the M-th cycle leaves the key in an identical state to the 1st cycle (same nonce floor, same storage usage delta). So the attacker gains nothing by cycling beyond a single AddKey — there is no "farmable" replay window to amplify, and thus no economic-disincentive gap to speak of.

### Title
No vulnerability - repeated DeleteKey/AddKey cycling does not lower or farm the nonce replay floor - (File: runtime/runtime/src/access_keys.rs)

### Summary
The nonce floor assigned on key re-creation, `initial_nonce_value(block_height) = (block_height-1) * 1_000_000` in `add_regular_key`, is a pure function of the current block height, not of how many DeleteKey/AddKey cycles occur. It is also bounded from below by the `NonceTooLarge` check in `verify_nonce`, guaranteeing the new floor is never less than any nonce previously accepted for that key.

### Finding Description
`action_delete_key`/`add_regular_key` in [1](#0-0)  reset a re-added key's nonce to `initial_nonce_value(block_height)`, defined at [2](#0-1)  as `(block_height - 1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER`. This value depends solely on the current block height `h`, so within one block every DeleteKey/AddKey cycle produces an identical floor — there is no per-cycle progression to "farm." Separately, `verify_nonce` in [3](#0-2)  rejects any transaction whose nonce is `>= block_height * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` (`NonceTooLarge`), which means every nonce ever accepted for a key while active at block `b` is strictly less than `b * 1_000_000`. Since re-addition can only happen at block height `h >= b`, the new floor `(h-1)*1_000_000 >= b*1_000_000 >` any previously accepted nonce, so no previously signed transaction can ever be replayed against the recreated key.

### Impact Explanation
No impact: the mechanism has no operator-controllable "reset amount," so there is nothing to amplify by cycling, and the floor is provably non-decreasing relative to any nonce previously usable for that key, precluding double-spend/replay via this path.

### Likelihood Explanation
Not applicable — the described attack sequence cannot produce any state divergence from a single DeleteKey/AddKey cycle; there is no incremental value to accumulate regardless of `M` or attacker cost.

### Recommendation
No fix required; the existing design (block-height-derived monotonic nonce floor plus the `NonceTooLarge` upper bound in `verify_nonce`) already provides the intended replay-prevention guarantee referenced in the code comments (near/nearcore#3779).

### Proof of Concept
Not applicable — no PoC can demonstrate a marginal benefit from repeated cycling because `add_regular_key`'s nonce floor is idempotent per block height and provably non-decreasing across block heights (would require constructing a test showing `initial_nonce_value` returns different values for repeated calls at the same `block_height`, which it does not, per [2](#0-1) ).

/// Verify that the transaction nonce is valid.
fn verify_nonce(
    tx_nonce: Nonce,
    current_nonce: Nonce,
    block_height: Option<BlockHeight>,
    nonce_mode: NonceMode,
) -> Result<(), InvalidTxError> {
    match nonce_mode {
        NonceMode::Monotonic => {
            if tx_nonce <= current_nonce {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
        NonceMode::Strict => {
            if !current_nonce.checked_add(1).is_some_and(|expected| tx_nonce == expected) {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
    }
    if let Some(height) = block_height {
        let upper_bound = height
            .saturating_mul(near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER);
        if tx_nonce >= upper_bound {
            return Err(InvalidTxError::NonceTooLarge { tx_nonce, upper_bound });
        }
    }
    Ok(())
}
