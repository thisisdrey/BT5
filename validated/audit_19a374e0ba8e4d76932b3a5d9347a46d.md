### Title
Attacker can fill a victim's per-account token list to `MAX_TOKENS_PER_USER`, blocking the victim from depositing new collateral or minting new synthetic debt - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
The pip CVE is a "shared predictable resource squatting" bug: a predictable `/tmp/pip-build-*` path let any local user occupy the slot and deny another user's operation. The Metronome analog is the per-account token registry in `Pool`: `depositTokensOfAccount`/`debtTokensOfAccount` are capped at `MAX_TOKENS_PER_USER = 30` (`Pool.sol:79`), and any first-time receipt of a registered `DepositToken` forcibly occupies one of the victim's slots. An attacker can dust-fill a victim's list so that every subsequent `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` reverts with `UserReachedMaxTokens`, denying the victim the ability to open new collateral positions or borrow any new synthetic asset.

### Finding Description
`DepositToken._mint` and `DepositToken._transfer` push the token into the *recipient's* pool-side list whenever the recipient's balance goes from zero to non-zero:

- `DepositToken.sol:486-488` — `_mint` calls `pool.addToDepositTokensOfAccount(account_)` on first receipt.
- `DepositToken.sol:518-520` — `_transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` on first receipt.

`Pool.addToDepositTokensOfAccount` (`Pool.sol:216-220`) and `Pool.addToDebtTokensOfAccount` (`Pool.sol:204-208`) are gated by `onlyIfAdditionWillNotReachMaxTokens`, which reverts once `debtTokensOfAccount.length(account) + depositTokensOfAccount.length(account) >= 30` (`Pool.sol:143-148`).

Attack path (all public, unprivileged):
1. Attacker calls `DepositToken.deposit(1 wei, victim)` — or `transfer(victim, dust)` — once per registered deposit token. `deposit` accepts arbitrary `onBehalfOf_` (`DepositToken.sol:211-216`), so the attacker never needs the victim's cooperation or even msdTOKEN inventory.
2. Each call mints the victim a dust balance, pushing that token into the victim's `depositTokensOfAccount`.
3. Once 30 slots are occupied, the victim's `deposit(newCollateral)` reverts in `_mint → addToDepositTokensOfAccount`, and `DebtToken.issue/mint` of any new synthetic reverts in `addToDebtTokensOfAccount` (same combined cap).

The victim cannot preemptively refuse the dust: there is no opt-in for receiving deposit tokens. Recovery requires the victim to burn/transfer each dust token (`withdraw` or `transfer` of the full dust balance triggers `removeFromDepositTokensOfAccount`, `DepositToken.sol:460-462,523-525`), paying gas per token and any configured `withdrawFee`. The attacker can re-fill freed slots, keeping the victim pinned.

### Impact Explanation
Liveness/DoS analog of the advisory: a targeted user is denied the protocol's core operations (depositing new collateral types and issuing new debt positions) for as long as the attacker maintains the fill, and must pay gas plus withdrawal fees to evict each squatting token. If the victim's position later becomes unhealthy and a collateral type they need to add to restore health is blocked, the griefing can contribute to liquidation losses. Note funds already deposited remain withdrawable — this is prevention of service, matching the advisory's impact profile.

### Likelihood Explanation
Medium. Attack requires holding dust of the underlying for each deposit token (or dust msdTOKEN), which costs real but tiny capital — bounded by the number of registered deposit/debt tokens per pool (currently far fewer than 30 on deployed pools, so the attacker fills whatever fraction exists and the cap binds only when the victim legitimately holds several tokens). No privileged role, oracle manipulation, or timing is needed; the attack is repeatable and cheap relative to the victim's eviction cost in gas and fees.

### Recommendation
- Track deposit/debt tokens per account only for balances the user opted into, e.g., only add on `deposit()` when `onBehalfOf_ == _msgSender()` or via an explicit opt-in mapping, and never auto-add on plain `transfer`/`seize` receipt.
- Alternatively, let any account remove tokens from its own lists (expose a user-callable removal that verifies zero balance), or drop the hard `MAX_TOKENS_PER_USER` revert in favor of bounding only iteration-heavy view paths.

### Proof of Concept
Hardhat-style reproduction against the deployed `Pool`/`DepositToken` set:

```ts
// victim has no positions; N registered deposit tokens exist
for (const dt of depositTokens) {            // enough distinct tokens to hit MAX_TOKENS_PER_USER
  await underlying(dt).approve(dt.address, 1);
  await dt.deposit(1, victim.address);       // mints dust to victim, occupies a slot
}
// victim's list is now at capacity
await expect(
  newDepositToken.connect(victim).deposit(amount, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
await expect(
  debtToken.connect(victim).issue(1)         // any new synthetic issuance
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

This mirrors the existing cap tests in `test/Pool.test.ts:1386-1416` and `1491-1521`, which confirm `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` revert once the combined list reaches `MAX_TOKENS_PER_USER`.
