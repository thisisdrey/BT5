Audit Report

## Title
Crowdloan `cap` vs `MinContribution` interaction permanently strands unusable remaining capacity - (File: `polkadot/runtime/common/src/crowdloan/mod.rs`)

## Summary
`Crowdloan::create` accepts any `cap` value with no relation to `T::MinContribution`, and `do_contribute` enforces `value >= T::MinContribution::get()` followed by `fund.raised + value <= fund.cap` as two independent, non-interacting checks. Once `fund.cap - fund.raised` drops below `T::MinContribution::get()`, every possible contribution value is rejected by one of the two checks, permanently stranding the remaining crowdloan capacity.

## Finding Description
`do_contribute` performs the checks exactly as claimed: [1](#0-0)  the minimum-contribution check (`value >= T::MinContribution::get()`) and the cap check (`fund.raised <= fund.cap`, after accumulating `value`) are independent and never account for the remaining headroom `fund.cap - fund.raised`.

`create` never validates any relationship between `cap` and `T::MinContribution` when constructing `FundInfo`: [2](#0-1)  `cap` is accepted as-is from the caller with only lease-period and para-registration checks, and stored directly into `Funds::<T>`. There is no `saturating_sub`/remaining-capacity clamp anywhere in the file (confirmed absent by search), so no code path adjusts the effective minimum as the fund nears `cap`.

Consequently, once `fund.cap - fund.raised < T::MinContribution::get()`: any `value < MinContribution` fails `Error::ContributionTooSmall`, and any `value >= MinContribution` causes `fund.raised > fund.cap`, failing `Error::CapExceeded`. This is reachable purely through the public, unprivileged `contribute` extrinsic — any sequence of ordinary contributions that leaves `fund.raised` within `(cap - MinContribution, cap)` permanently locks the gap for the life of the fund, since `raised` only increases via further `contribute` calls (never decreases except via refund/dissolve after failure).

The parachain slot bid subsequently placed uses `fund.raised`, not `fund.cap`: [3](#0-2)  so the stranded capacity directly caps the maximum bid below the fund's intended `cap`.

## Impact Explanation
This is a runtime bug that compromises the intended behavior of the crowdloan mechanism: a configured `cap` is not actually reachable when it is not commensurate with `MinContribution` and contributions arrive close to it, permanently locking out remaining capacity and reducing the parachain's maximum possible auction bid. No funds are lost (raised funds remain refundable via the normal `withdraw`/dissolution flow), so this does not rise to fund theft or an unbacked mint/lock of user funds — it is a degradation of the crowdloan's utility/intended cap semantics, consistent with the "runtime bugs that compromise intended behavior" impact category.

## Likelihood Explanation
High likelihood in ordinary operation: any crowdloan whose `cap` is not an exact multiple/compatible value with `MinContribution`, combined with organic uncoordinated public contributions via `contribute`/`contribute_all`, can land in the unfillable gap with no privileged action, adversarial coordination, or special conditions required.

## Recommendation
In `do_contribute`, when `fund.cap.saturating_sub(fund.raised) < T::MinContribution::get()`, allow the effective minimum for that call to be clamped to the remaining headroom (`cap - raised`) rather than the fixed `MinContribution`, or permit a final exact top-up contribution that fills `cap - raised` regardless of `MinContribution`. Additionally, consider validating at `create` time that `cap` is consistent with `MinContribution`.

## Proof of Concept
1. Configure `T::MinContribution = 100`.
2. Call `Crowdloan::create(origin, para, cap = 950, ...)`.
3. Contributors call `contribute` nine times with `value = 100`, bringing `fund.raised = 900`.
4. Any further `contribute(value)`: `value < 100` fails `Error::ContributionTooSmall` (see check at [4](#0-3) ); `value >= 100` fails `Error::CapExceeded` since `900 + 100 = 1000 > 950` (see check at [5](#0-4) ).
5. `fund.raised` is permanently stuck at `900`, and the para can only ever bid `900` instead of the configured `950`.
