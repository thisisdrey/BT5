### Title
Block-size accounting in `generateBlock()` ignores the `Result` bytes added post-execution, allowing produced blocks to exceed the peer-enforced `BLOCK_SIZE` limit - (File: `framework/src/main/java/org/tron/core/db/Manager.java`)

### Summary
This is the same bug class as the CometBFT report: a size limit is enforced using a value that does not reflect the real, final serialized size of the data being proposed/broadcast, so an honestly-produced block can be larger than the hard limit that peer nodes use to accept/reject it.

### Finding Description
When a witness packs a block, `generateBlock()` measures each transaction's contribution to the running block size with `trx.computeTrxSizeForBlockMessage()` **before** the transaction is executed: [1](#0-0) 

```
// check the block size
long trxPackSize = trx.computeTrxSizeForBlockMessage();
if ((currentSize + trxPackSize) > ChainConstant.BLOCK_SIZE) {
  postponedTrxCount++;
  continue; // try pack more small trx
}
```

`computeTrxSizeForBlockMessage()` simply serializes the transaction as it currently stands: [2](#0-1) 

Immediately after this size check, the transaction is executed via `processTransaction(trx, blockCapsule)`. Inside `processTransaction`, once the VM/contract executes, the transaction object is **mutated** to attach a `Result` (`Ret`) entry describing the execution outcome: [3](#0-2) 

```
trace.finalization();
if (getDynamicPropertiesStore().supportVM()) {
  trxCap.setResult(trace.getTransactionContext());
}
```

`setResult`/`setResultCode` appends a `Result` protobuf message to the transaction: [4](#0-3) 

This happens **after** `trxPackSize` was already computed and added to `currentSize`: [5](#0-4) 

```
try (ISession tmpSession = revokingStore.buildSession()) {
  accountStateCallBack.preExeTrans();
  processTransaction(trx, blockCapsule);
  ...
  toBePacked.add(trx);
  currentSize += trxPackSize;   // <-- uses the PRE-execution size, not the post-Ret size
```

So the size actually counted against `ChainConstant.BLOCK_SIZE` for each transaction is the size **before** the `Result` bytes are attached, while the transaction object that is ultimately packed into the block (`toBePacked.add(trx)`) is the **post**-execution, larger object. Over many transactions in a block this discrepancy accumulates, and the final serialized block (`blockCapsule.getInstance().getSerializedSize()`) can exceed `ChainConstant.BLOCK_SIZE` by more than the small margin the network otherwise allows.

That margin is enforced independently on the receiving/peer side in `BlockMsgHandler`, which rejects any block whose serialized size exceeds `BLOCK_SIZE + Constant.ONE_THOUSAND` (a fixed 1000-byte buffer): [6](#0-5) 

```
private int maxBlockSize = BLOCK_SIZE + Constant.ONE_THOUSAND;
...
if (blockCapsule.getInstance().getSerializedSize() > maxBlockSize) {
  logger.error("Receive bad block {} from peer {}, block size over limit", ...);
  throw new P2pException(TypeEnum.BAD_MESSAGE, "block size over limit");
}
```

Because the producing node (the witness/SR) accounts for size using pre-`Ret` transaction bytes while the accepting/validating peers check the true post-`Ret` serialized block, an honestly produced block that is packed right up against `ChainConstant.BLOCK_SIZE` can cross the hard `maxBlockSize` cutoff enforced elsewhere in the network, exactly mirroring the reported bug class ("the byte size accounted for during construction does not match the byte size enforced during acceptance").

### Impact Explanation
If the accumulated `Result`/`Ret` overhead across many packed transactions pushes the final block past `BLOCK_SIZE + ONE_THOUSAND`, peer full nodes will reject that block with `P2pException(BAD_MESSAGE, "block size over limit")` in `BlockMsgHandler`. A block produced and signed by an honest witness could thus be dropped by some or all peers, which can cause missed blocks, forks between nodes that accepted vs. rejected the block, or repeated production of similarly-oversized blocks by honest witnesses — i.e., the same "chain halt/liveness" impact class described in the source report. The trigger requires no privileged access: any user broadcasting ordinary smart-contract-call transactions that get included in a block contributes to this miscount.

### Likelihood Explanation
The per-transaction overhead is bounded by small constants (`Constant.MAX_RESULT_SIZE_IN_TX = 64`, `MAX_CONTRACT_RESULT_SIZE = 2`), and the buffer between `BLOCK_SIZE` and `maxBlockSize` is `Constant.ONE_THOUSAND` (1000 bytes). Filling a block with the maximum number of transactions that carry `Ret` entries can plausibly consume that entire 1000-byte buffer, especially since `currentSize` already starts near `BLOCK_SIZE` by design of the packing loop (it packs until the pre-Ret estimate is within the limit). This makes the condition realistically, though not trivially, reachable under normal high-throughput network conditions — it does not require any malicious actor, only enough legitimate transaction volume.

### Recommendation
Compute (or re-verify) the transaction's block-message size **after** `processTransaction` has finished mutating it with the execution `Result`, and use that post-execution size for the `currentSize` accounting and for the `(currentSize + trxPackSize) > ChainConstant.BLOCK_SIZE` check, so the packing logic and the peer-side `BlockMsgHandler` limit are checking the same quantity. Alternatively, increase the safety buffer (`Constant.ONE_THOUSAND`) to account for the worst-case aggregate `Result` overhead across the maximum number of transactions a block can contain.

### Proof of Concept
Conceptual PoC (cannot be executed without a running node):
1. As an ordinary account, broadcast a large number of `TriggerSmartContract` transactions in quick succession so that a witness's `generateBlock()` packs as many as possible into a single block, driving `currentSize` (computed from pre-execution `computeTrxSizeForBlockMessage()`) close to `ChainConstant.BLOCK_SIZE`.
2. Each transaction, once executed via `processTransaction`, has a `Result` appended via `trxCap.setResult(...)`, which is not reflected in the `trxPackSize` already added to `currentSize`.
3. When the block is finalized and broadcast, its true serialized size (`blockCapsule.getInstance().getSerializedSize()`) can exceed `BLOCK_SIZE + Constant.ONE_THOUSAND`.
4. Peer nodes running `BlockMsgHandler.processMessage` will reject this block with `"block size over limit"`, dropping an otherwise validly-produced and signed block.

Note: I was unable to confirm the exact numeric value of `ChainConstant.BLOCK_SIZE` from the available index (the constant is defined in `common/src/main/java/org/tron/core/config/Parameter.java`, whose relevant line was not returned by search), so the precise number of transactions needed to exhaust the 1000-byte buffer could not be computed exactly; a Devin session with full file access would be needed to confirm the exact margin and produce a fully quantified PoC.
