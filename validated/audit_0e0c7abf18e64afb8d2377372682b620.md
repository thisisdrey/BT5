### Title
Unbounded Growth of `ownerAddressSet` in `Manager` Leads to Memory Exhaustion - (File: `framework/src/main/java/org/tron/core/db/Manager.java`)

### Summary
`Manager` maintains an in-memory `HashSet<String>` called `ownerAddressSet` that records the owner address of every successfully processed multi-signature transaction (`AccountPermissionUpdateContract`). Entries are added on every matching transaction but are **never removed**, so the set grows monotonically for the lifetime of the node process, mirroring the OpenSSL CMP `extraCerts` cache-growth bug (unbounded accumulation of attacker-influenced data with no expunging mechanism).

### Finding Description
The field is declared without any bound or expiration policy: [1](#0-0) 

Every time `processTransaction` finishes processing a transaction whose contract type is `AccountPermissionUpdateContract` (detected via `isMultiSignTransaction`), the hex-encoded owner address is unconditionally added to this set: [2](#0-1) 

The set is read from multiple places (`getVerifyTxs`, `filterOwnerAddress`, `generateBlock`, `rePush`) but is only ever appended to, never pruned or bounded: [3](#0-2) [4](#0-3) [5](#0-4) 

Unlike the guava-backed caches used elsewhere in the codebase (e.g. `transactionIdCache`, `TronCache`) which are configured with `maximumSize`/`expireAfterAccess`/`expireAfterWrite` via `CacheStrategies`, `ownerAddressSet` is a plain unbounded `HashSet` with no eviction strategy at all — exactly the pattern the OpenSSL CMP advisory flags as the root cause (a long-lived context accumulating attacker-influenced records that are never expunged).

An unprivileged account holder can trigger growth of this set simply by broadcasting an `AccountPermissionUpdateContract` transaction from any account they control. Each new/distinct account address that performs a permission update adds a permanent, never-freed entry (~dozens of bytes for the hex string plus HashSet/String object overhead) to the node's heap.

### Impact Explanation
Because the set has no capacity limit or TTL, a party who creates many accounts and issues one permission-update transaction per account can force every full node in the network to retain an ever-growing, unbounded in-memory structure. Over time this leads to heap exhaustion and OutOfMemoryError, crashing or hanging the node process — a concrete node-crash/halt impact, consistent with the CVSS 5.9 (Availability-only) rating of the referenced advisory.

### Likelihood Explanation
`AccountPermissionUpdateContract` is a standard, unprivileged, broadcastable contract type reachable by any funded account through the normal `broadcastTransaction` path in `Wallet`. No special privileges (SR/witness) are required, only the cost of account creation and the bandwidth/fee for each permission-update transaction, making sustained, low-cost growth of the set feasible over an extended period.

### Recommendation
Bound `ownerAddressSet` the same way other transient caches in the codebase are bounded — e.g., replace the raw `HashSet<String>` with a `Cache` from `TronCache`/Guava configured with `maximumSize` and `expireAfterWrite`/`expireAfterAccess` (as done for `transactionIdCache`), or explicitly remove entries once the corresponding pending/re-push transaction has been consumed instead of only ever adding to the set.

### Proof of Concept
1. Create N distinct TRON accounts (each requires only minimal TRX to activate).
2. For each account, broadcast a valid signed `AccountPermissionUpdateContract` transaction (a normal, unprivileged operation any account owner can perform) via `Wallet.broadcastTransaction`.
3. Each transaction is processed by `Manager.processTransaction`, which unconditionally executes `ownerAddressSet.add(ByteArray.toHexString(trxCap.getOwnerAddress()))` after success — see lines 1600-1602 above.
4. Repeat with large N (attacker-controlled, limited only by account-creation cost) — `ownerAddressSet` grows without bound because no code path ever removes entries, eventually exhausting heap memory on every full node that processes these transactions.
