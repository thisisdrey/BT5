### Title
Exchange inject/withdraw execution can revert with overflow even after validation passes, blocking legitimate liquidity injection/withdrawal - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
`ExchangeInjectActuator` (and similarly `ExchangeWithdrawActuator`) computes the "another token" amount twice: once in `validate()` using wide `BigInteger` arithmetic, and once in `execute()` using narrow `long` arithmetic via `Math.multiplyExact`. When the intermediate product `balance * quant` exceeds `Long.MAX_VALUE` but the final quotient (after division) is a legitimate value that passes all `validate()` checks, `execute()` throws an `ArithmeticException` from `multiplyExact`, causing the transaction to fail even though it was correctly validated. This mirrors the reported bug class: a formula computed safely in one place (wide type) but re-computed unsafely elsewhere (narrow type), causing legitimate operations to revert due to overflow.

### Finding Description
In `validate()`, the "another token" quantity is computed with `BigInteger`, which cannot overflow: [1](#0-0) 

But in `execute()`, the same quantity is recomputed using plain `long` multiplication via `Math.multiplyExact`: [2](#0-1) 

Because `validate()` never checks that the intermediate product `secondTokenBalance * tokenQuant` (or `firstTokenBalance * tokenQuant`) itself fits in a `long` — it only checks the final quotient and the resulting balances against `balanceLimit` — it is possible for a transaction to pass `validate()` and still throw `ArithmeticException` from `multiplyExact` in `execute()`. This exception is caught and converted into `ContractExeException`, causing execution failure: [3](#0-2) 

The same pattern (`BigInteger`/`BigDecimal` in `validate()` vs. `subtractExact`/product-free arithmetic mismatch) exists in `ExchangeWithdrawActuator`, though its `execute()` path also recomputes the quotient with `BigInteger` — the primary discrepancy is concentrated in `ExchangeInjectActuator.execute()`, which is the only place doing a raw `multiplyExact(balance, quant)` on `long` while `validate()` uses `BigInteger.multiply()`. [4](#0-3) 

### Impact Explanation
An `ExchangeInjectContract` transaction can be crafted (or occur naturally as exchange pool balances grow, since `getExchangeBalanceLimit()` can be configured to a very large value) such that `secondTokenBalance * tokenQuant` (or the symmetric case) exceeds `Long.MAX_VALUE` (~9.22e18) while the actual division result (the injected counterpart amount) is small and legitimate, satisfying every check in `validate()` (balance sufficiency, `balanceLimit`, precision). Such a transaction will be accepted into a block by `validate()` but fail during `execute()` with an unexpected `ArithmeticException`/`ContractExeException`, meaning the pool creator cannot inject liquidity into their own exchange even though the operation is economically valid. This blocks legitimate exchange operations, directly analogous to the reported "users may fail to add liquidity because of overflow" issue.

### Likelihood Explanation
Exchange pool balances and TRC10 token quantities are represented as signed 64-bit longs and can independently reach the trillions-to-quintillions range depending on token decimals and injected amounts; `getExchangeBalanceLimit()` is a governance-configurable dynamic parameter that can be set high enough to allow such products to exceed `Long.MAX_VALUE` while the resulting ratio stays small. Any exchange creator performing an inject on a sufficiently large/imbalanced pool can trigger this without any special privilege — it is reachable directly via a normal `ExchangeInjectContract` transaction.

### Recommendation
In `ExchangeInjectActuator.execute()`, compute `anotherTokenQuant` using the same `BigInteger` arithmetic as `validate()` (or reuse the value computed in `validate()`) instead of `Math.multiplyExact(long, long)`, so that the overflow-safe wide computation is consistently used and legitimate transactions do not fail during execution due to an intermediate overflow that does not affect the final result.

### Proof of Concept
1. Create an exchange pool where `firstTokenBalance` and `secondTokenBalance` are both large (e.g., in the trillions range, consistent with token decimals and a high `exchange_balance_limit`).
2. Choose `tokenQuant` such that `secondTokenBalance * tokenQuant > Long.MAX_VALUE` but `secondTokenBalance * tokenQuant / firstTokenBalance` (the `anotherTokenQuant`) is small and within `balanceLimit` and account balance — this transaction passes `validate()` because it uses `BigInteger`.
3. Submit the `ExchangeInjectContract`; in `execute()`, `Math.multiplyExact(secondTokenBalance, tokenQuant)` throws `ArithmeticException`, which is caught and rethrown as `ContractExeException`, causing the transaction to fail despite having passed validation. [5](#0-4)
