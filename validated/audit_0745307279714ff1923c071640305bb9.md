### Title
Attacker can permanently block a victim's deposits and new borrows by dust-stuffing `MAX_TOKENS_PER_USER` via `DepositToken.transfer` — (File: contracts/Pool.sol)

### Summary
`Pool` caps each account at `MAX_TOKENS_PER_USER = 30` combined deposit+debt token entries, enforced by `onlyIfAdditionWillNotReachMaxTokens` in `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount`. `DepositToken._transfer` registers every recipient in `depositTokensOfAccount` on any nonzero transfer. An unprivileged attacker can buy dust of every listed collateral, deposit it, and `transfer` 1 wei of each `DepositToken` to a victim, filling their per-account list. Once the limit is hit, the victim cannot deposit any new collateral type nor mint any new synthetic asset, because both paths call the `addTo*` functions that revert with `UserReachedMaxTokens`.

### Finding Description
- `DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance goes from 0 to >0, with no consent or opt-out from the recipient (`contracts/DepositToken.sol:517-520`).
- `Pool.addToDepositTokensOfAccount` enforces `onlyIfAdditionWillNotReachMaxTokens`, reverting once `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` (`contracts/Pool.sol:143-148`, `contracts/Pool.sol:216-220`).
- `DebtToken` minting (`issue`/`mint`/`leverage` paths via SmartFarmingManager) also calls `addToDebtTokensOfAccount`, so the same cap blocks opening any new debt position (`contracts/Pool.sol:204-208`). `DebtToken` is non-transferable (`TransferNotSupported`), so a victim cannot shed debt-token entries without repaying.
- There is no mechanism for a victim to remove dust entries other than transferring/withdrawing the full dust balance of each token — which costs the victim gas per token and can be re-stuffed by the attacker at any time, making the griefing persistent and asymmetric (attacker pays ~1 wei per token; victim must react per token).

### Impact Explanation
The victim is denied the ability to deposit additional collateral and to open new debt positions. For a leveraged or underwater-risking position, depositing a *new* collateral type is the standard rescue path; stuffing the list forces liquidation (loss via liquidation fee and collateral discount) or forces the victim to source the synthetic asset to repay instead. Funds are effectively temporarily frozen (locked collateral cannot be withdrawn while debt exists, and new deposits revert), matching the availability-loss class of the reference advisory. Accepted impact: temporary freezing of funds / forced liquidation.

### Likelihood Explanation
- Fully unprivileged: attacker needs only an EOA, dust amounts of each collateral, and calls to `deposit()` + `transfer()`.
- Pool has ~12 deposit tokens on mainnet and more on Optimism/Base; combined with the victim's existing entries (each minted synth adds a debt-token entry, each held collateral adds a deposit-token entry), reaching 30 is cheap, especially against users holding many `va*` collaterals or running SmartFarming leverage loops that themselves consume list slots.
- No pause flag, supply cap, or reentrancy guard mitigates it; `_revertIfLocked` only restricts the *sender's* own locked balance, not the recipient.
- Cost to the attacker is bounded by acquiring small amounts of each collateral plus deposit gas; removal cost falls on the victim.

### Recommendation
Do not register recipients in `depositTokensOfAccount` on plain transfers — only register on `deposit`/mint, or add an opt-in list maintained by the depositor's own actions. Alternatively, iterate `depositTokensOfAccount` removal permissionlessly (`removeFromDepositTokensOfAccount` when `balanceOf(account) == 0` already handles cleanup on transfer-out, so alternatively allow the account to prune its own list), or raise the cap and treat dust (balance below a threshold) as not counting.

### Proof of Concept
Hardhat/foundry fork sketch against a live pool:

```solidity
// victim already holds some deposit/debt token entries (e.g., 1 collateral, N debts)
address[] memory dts = pool.getDepositTokens();          // all listed DepositTokens
for (uint i; i < dts.length && i < needed; ++i) {
    IERC20 underlying = DepositToken(dts[i]).underlying();
    deal(address(underlying), attacker, 1e6);            // or swap for dust
    underlying.approve(dts[i], 1);
    DepositToken(dts[i]).deposit(1);                     // attacker gets 1 wei msdTOKEN
    DepositToken(dts[i]).transfer(victim, 1);            // registers victim's list entry
}
// victim now at MAX_TOKENS_PER_USER = 30
vm.prank(victim);
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
DepositToken(newCollateral).deposit(amount);             // revert
vm.prank(victim);
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
DebtToken(debtToken).issue(amount);                      // revert: cannot open new debt
// victim's locked collateral cannot be withdrawn (debtPositionOf locked check),
// and rescue-by-new-collateral is impossible => forced liquidation.
```

Key invariants to assert: `pool.getDepositTokensOfAccount(victim).length + pool.getDebtTokensOfAccount(victim).length == 30`, all `deposit`/`issue` calls for tokens not yet in the list revert, and `_revertIfLocked` prevents withdrawal of collateral backing existing debt.
