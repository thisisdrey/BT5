### Title
Unbounded Array Allocation from Attacker-Controlled Length Field in TVM Precompiled Contracts `ValidateMultiSign` / `BatchValidateSign` - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `extractBytesArray` and `extractSigArray` helper methods used by the `ValidateMultiSign` and `BatchValidateSign` precompiled contracts allocate a Java array whose size is taken directly from an attacker-controlled 32-byte word in the precompile call data, without validating it against the actual size of the supplied data or any hard cap, whenever the `allowTvmSelfdestructRestriction` hard-fork flag is not enabled. This mirrors the ImageSharp GIF decoder issue (CVE-2024-41132): a length value read from untrusted input is used to allocate memory before the input is verified to actually contain that much data, resulting in CWE-770/CWE-789 (uncontrolled resource consumption).

### Finding Description
`extractBytesArray` and `extractSigArray` read a `len` value straight from the ABI-decoded words and immediately allocate an array of that size: [1](#0-0) [2](#0-1) 

`len` comes from `words[offset].intValueSafe()`, i.e., an arbitrary 32-byte word chosen by the caller inside the precompile call data — it is not derived from, or checked against, the actual number of bytes present in `data`.

These helpers are invoked by `ValidateMultiSign.execute` and `BatchValidateSign.doExecute`: [3](#0-2) [4](#0-3) 

The size cap (`sigArraySize > MAX_SIZE`) is only enforced when `VMConfig.allowTvmSelfdestructRestriction()` returns `true`. If that chain parameter/hard-fork is not active, `extractSigArray`/`extractBytesArray` are called directly with the attacker-supplied `len`, and `new byte[len][]` executes with no upper bound before any bounds-check against `words.length` occurs in the subsequent loop. Additionally, `isValidAbiEncoding` (gated by `allowTvmOsaka()`) only validates that the *overall* data length is a multiple of the header/item word sizes; it never cross-checks that an embedded length field matches the true number of items, so even when that check is active the length field itself remains attacker-controlled and can still be set arbitrarily large relative to the small overall payload actually supplied.

### Impact Explanation
Any account able to deploy or call a smart contract can invoke these precompiled contract addresses (part of the TVM precompile dispatch in `getContractForAddress`) with a minimal-size call data blob but with a maliciously large 32-byte "array length" word at the signature/address-count offset. This drives `new byte[len][]` with `len` up to `Integer.MAX_VALUE`, attempting to allocate gigabytes of memory for a reference array in a single EVM/TVM call executed inside `Program`/`Runtime` execution, which can throw `OutOfMemoryError` and destabilize or crash the executing full node — a concrete node crash/DoS impact reachable from a single signed transaction/contract call, consistent with the rules' accepted impact of "node crash or halt."

### Likelihood Explanation
Reachability requires only deploying/calling a contract that performs a `STATICCALL`/`CALL` to the `ValidateMultiSign` or `BatchValidateSign` precompile addresses with crafted calldata — no special privilege, signer role, or witness/SR status is needed. Exploitability depends on the `allowTvmSelfdestructRestriction` (and, for the ABI-shape check, `allowTvmOsaka`) chain parameters not yet being active on the target network; on networks/branches where these proposals have not been activated, the guard is entirely absent, making the path directly reachable.

### Recommendation
Enforce the `MAX_SIZE` bound (and a sanity check that `len` cannot exceed what `words.length` can possibly contain) inside `extractBytesArray` and `extractSigArray` themselves, unconditionally of `VMConfig.allowTvmSelfdestructRestriction()`, so the fix does not depend on a hard-fork toggle. Additionally, validate that any embedded array-length field is consistent with the actual size of `words`/`data` before allocating, rather than relying solely on the coarse `isValidAbiEncoding` total-length check.

### Proof of Concept
1. Deploy a contract that calls the `BatchValidateSign` precompile address with calldata shaped as a minimal valid 5-header-word ABI blob (satisfying `isValidAbiEncoding` if `allowTvmOsaka` is active), but with the word at the "signatures array offset" location decoded to a large value (e.g., `0x7FFFFFFF`).
2. Ensure `allowTvmSelfdestructRestriction` is not active on the target network (so the `sigArraySize > MAX_SIZE` guard at PrecompiledContracts.java:1165-1171 is skipped).
3. On execution, `extractBytesArray`/`extractSigArray` (PrecompiledContracts.java:399-426) executes `new byte[len][]` with `len` derived from the attacker-chosen word, attempting a multi-gigabyte allocation and triggering `OutOfMemoryError` in the node's TVM executor thread.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];

    int len = words[offset].intValueSafe();

          bytesLen);
    }
    return bytesArray;
  }
