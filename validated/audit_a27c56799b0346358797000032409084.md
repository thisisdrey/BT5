### Title
Unbounded token minting via `subsidized_amount` bypass in `promise_batch_action_function_call_weight` for zero-balance accounts - ([File: core/primitives-core/src/account.rs] / [runtime/near-vm-runner/src/logic/logic.rs])

### Summary
`promise_batch_action_function_call_weight` contains a `skip_deduct` branch that skips `deduct_balance` and instead adds the attached amount to `result_state.subsidized_amount` whenever `amount == 1 yoctoNEAR`, `config.one_yocto_on_promise` is enabled, and `current_account_balance.is_zero()`. Because the balance is never actually decremented in this branch, the zero-balance precondition is preserved after every call, allowing the same exemption to be triggered arbitrarily many times within a single execution, each producing a real outgoing receipt carrying 1 yoctoNEAR of value that was never debited from the sender.

### Finding Description
In `promise_batch_action_function_call_weight` [1](#0-0)  the code computes:
```
let skip_deduct = amount == Balance::from_yoctonear(1)
    && self.config.one_yocto_on_promise
    && self.result_state.current_account_balance.is_zero();
if skip_deduct {
    self.result_state.subsidized_amount = self.result_state.subsidized_amount
        .checked_add(amount).expect("subsidized_amount overflow");
} else {
    self.result_state.deduct_balance(amount)?;
}
```
followed unconditionally by `self.ext.append_action_function_call_weight(..., amount, ...)`, which attaches the real 1-yoctoNEAR amount to the outgoing `FunctionCall` action regardless of whether the sender's balance was debited [2](#0-1) . Since `current_account_balance` is never touched in the `skip_deduct` branch, the zero-balance precondition trivially holds for every subsequent call within the same execution (and across future executions, since the account never accumulates real balance from this path). An attacker with a zero-balance contract can therefore issue hundreds of `promise_batch_action_function_call_weight` calls in a single `FunctionCall`, each attaching exactly 1 yoctoNEAR, each triggering `skip_deduct`, and each producing a genuine outgoing receipt with real transferable value — with no compensating debit anywhere in the sender's balance. The equivalent duplicated logic exists in the wasmtime runner variant.

None of the standard checks (nonce, access-key permission, gas metering, storage staking) prevent this, because the exploit does not rely on forging a receipt or bypassing gas costs — gas is paid normally per action — it relies purely on the balance-conservation bypass baked into the `skip_deduct` branch, which has no cap on the number of times it can be triggered per execution or per account lifetime.

### Impact Explanation
This is a token-inflation / minting bug (NEAR bounty category: token inflation). Every triggered `skip_deduct` mints 1 yoctoNEAR of real, spendable value in an outgoing receipt without any matching debit from the sender or any other account, violating the VALUE_CONSERVATION invariant. While each individual unit is only 1 yoctoNEAR, it is unbounded in the number of times it can be repeated (limited only by attached gas, which is a cost paid by the attacker, not a cap on the exploit's issuance), so it should be treated as unbounded inflation, not a negligible dust issue — the funds minted are real and spendable by the receiver of each receipt.

### Likelihood Explanation
The precondition (a zero-balance contract account) is trivial to construct: any deployed contract that has never received a deposit satisfies `current_account_balance.is_zero()`. The attacker only needs to pay for gas to execute repeated `promise_batch_action_function_call_weight` host calls, which is proportional to the number of yoctoNEAR units minted, but the code contains no explicit limit on how many times `skip_deduct` can trigger per execution — the bypass is purely dependent on the balance remaining zero, and it never changes as a side effect of taking the `skip_deduct` path. This makes the exploit fully repeatable across executions and blocks at attacker-controlled cadence.

### Recommendation
Restrict the `skip_deduct` exemption to at most once per account lifetime (or eliminate it entirely), and ensure any `subsidized_amount` is properly and visibly offset against total supply/inflation accounting rather than silently omitted from `deduct_balance`. At minimum, cap the cumulative `subsidized_amount` per execution/receipt and require it to be reconciled against a protocol-controlled subsidy budget rather than an unconditional per-call exemption gated only on the sender's current balance being zero.

### Proof of Concept
Runtime integration test:
1. Deploy a contract with `current_account_balance == 0` and `one_yocto_on_promise` enabled in the runtime config.
2. In a single `FunctionCall`, invoke `promise_batch_action_function_call_weight` N times (e.g., N=500), each attaching `amount = 1 yoctoNEAR` to a batch promise targeting distinct receiver accounts.
3. Execute the receipt and process the resulting outgoing receipts.
4. Assert: `result_state.subsidized_amount == N` yoctoNEAR, `current_account_balance` remains `0` throughout and after execution, and the sum of balance increases across all N receiver accounts equals N yoctoNEAR.
5. Assert this sum was never debited from any account (i.e., total protocol supply before == total protocol supply after minus N), proving unbacked issuance of N yoctoNEAR.
