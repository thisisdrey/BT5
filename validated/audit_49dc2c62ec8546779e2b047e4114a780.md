### Title
Attacker can delete an account while leaving unbacked `ReceivedData`/`PostponedReceipt` trie rows behind, permanently violating the storage-staking invariant - (File: `runtime/runtime/src/actions.rs`, `core/store/src/utils/mod.rs`)

### Summary
`action_delete_account`'s size cap (`Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE = 10_000`) is computed solely from `account.storage_usage()`, a manually-maintained counter that only tracks `Account`/`ContractCode`/`AccessKey`/`ContractData` bytes and explicitly excludes `ReceivedData`/`PostponedReceipt`/`PostponedReceiptId`/`PendingDataCount` rows. `remove_account` likewise only clears `Account`, `ContractCode`, `AccessKey`/`GasKeyNonce`, and `ContractData` trie keys, never the receipt-matching columns. An attacker who accumulates many pending cross-contract callbacks on their own account and deletes that account before the callbacks resolve leaves those rows permanently orphaned in the trie, unbacked by any storage deposit.

### Finding Description
`action_delete_account` computes the deletion-size guard purely from the account's tracked `storage_usage`: [1](#0-0) 

`Account::storage_usage()` is a manually incremented/decremented counter updated by actions such as `action_add_key`, `action_deploy_contract`, and contract-data writes — it is never touched by receipt-matching bookkeeping. This is explicit in the genesis `StorageComputer`, which documents "we don't charge storage for receipts" and maps `PostponedReceipt`/`ReceivedData`/`DelayedReceipt` state records to `None` (no storage charge): [2](#0-1) 

When an `ActionReceipt` with unmet `input_data_ids` arrives at a receiver, the runtime persists `PostponedReceipt`, `PostponedReceiptId`, and `PendingDataCount` rows keyed by that receiver's account id; when a `DataReceipt` arrives it persists a `ReceivedData` row and only then reconciles/removes the postponed bookkeeping once every dependency is satisfied: [3](#0-2) 

Crucially, `remove_account` — invoked by `action_delete_account` — only removes `Account`, `ContractCode`, access/gas keys, and `ContractData`: [4](#0-3) 

It never scans/removes `TrieKey::ReceivedData`, `TrieKey::PostponedReceiptId`, `TrieKey::PendingDataCount`, or `TrieKey::PostponedReceipt` rows for the account being deleted. `TrieKey`'s column layout (`RECEIVED_DATA`, `POSTPONED_RECEIPT_ID`, `PENDING_DATA_COUNT`, `POSTPONED_RECEIPT`) confirms these are distinct, addressable trie prefixes per account that `remove_account` simply does not touch: [5](#0-4) 

**Exploit flow (unprivileged attacker):**
1. Attacker deploys a contract on `acct.alice.near` (an ordinary sub-account they control) and funds it enough to cover the `storage_usage()`-tracked bytes (well under `MAX_ACCOUNT_DELETION_STORAGE_USAGE = 10_000`).
2. The contract issues many self-targeted promise chains (e.g., `promise_and` joins of several `promise_batch_create`/`function_call` receipts targeting itself) that register callbacks awaiting multiple `input_data_ids`. Each unmatched dependency creates a `PostponedReceipt` + `PendingDataCount` + one `PostponedReceiptId` per unmet id, and each arriving `DataReceipt` writes a `ReceivedData` row before the match is reconciled — none of this affects `account.storage_usage()`.
3. Before the pending callbacks fully resolve (i.e., while `PostponedReceipt`/`PendingDataCount`/`ReceivedData` rows are still outstanding for `acct.alice.near`), the attacker submits a `DeleteAccountAction` for `acct.alice.near`.
4. `action_delete_account`'s check only compares `account.storage_usage()` (which never counted the receipt-matching rows) against 10 000, so it passes trivially; `remove_account` deletes `Account`/`ContractCode`/`AccessKey`/`ContractData` and refunds the balance to the beneficiary, but leaves the `ReceivedData`/`PostponedReceipt`/`PostponedReceiptId`/`PendingDataCount` rows in the trie. Since the account no longer exists, nothing will ever again look up or clean those keys — any late-arriving `DataReceipt` for the deceased account still gets written as a fresh orphaned `ReceivedData` row (`process_receipt` writes it unconditionally, without checking account existence).

No existing check (gas metering, storage-staking `check_storage_stake`, or the `MAX_ACCOUNT_DELETION_STORAGE_USAGE` cap) inspects these columns, so nothing stops the deletion.

### Impact Explanation
The result is permanent, unbacked growth of shard state: bytes that were never charged against any account's storage deposit remain in the trie indefinitely after the paying account is gone, and no future rent/refund mechanism reclaims them. This is repeatable at near-zero net cost (attacker only pays for account creation/gas of the postponed-receipt setup, then recovers their storage deposit back via `DeleteAccountAction`'s beneficiary refund), letting the attacker leave arbitrarily many stale trie rows behind each cycle. This violates the value-conservation invariant that all persisted state is backed by a staking deposit (`docs/Economics/Economics.md` "State Stake" model and `verifier.rs::check_storage_stake`), and functions as an unbounded, effectively-free state-bloat vector against the network's storage capacity — a resource/DoS class impact rather than direct fund theft.

### Likelihood Explanation
- Fully reachable by an ordinary funded account with no special privileges: deploy a wasm contract, issue promise/callback receipts to itself, then submit a `DeleteAccountAction`.
- Cost to attacker: gas for chained promise/callback receipts plus minimal storage deposit for the tracked (non-receipt) storage usage, all of which is refunded on deletion.
- Repeatable indefinitely by creating and deleting many such throwaway sub-accounts.
- The only timing constraint is submitting the delete transaction before the runtime naturally resolves/reconciles all pending data dependencies for that receiver, which is well within an attacker's control since they control both ends of the self-targeted promise chain.

### Recommendation
Before allowing `action_delete_account` to proceed, scan (or otherwise account for) the `ReceivedData`, `PostponedReceipt`, `PostponedReceiptId`, and `PendingDataCount` trie prefixes for `account_id`; either fold their sizes into the `MAX_ACCOUNT_DELETION_STORAGE_USAGE` check (rejecting deletion if there is pending receipt-matching state) or have `remove_account` enumerate and remove those columns as it already does for `AccessKey`/`ContractData`, refusing deletion (or delaying it) while unresolved postponed receipts exist for the account.

### Proof of Concept
Integration test plan (runtime/runtime `tests/apply.rs`-style, using `runtime.apply`):
1. Create `acct.alice.near`, deploy a contract that, on a single entrypoint call, issues N (e.g. 50) `promise_batch_create` self-calls joined via `promise_and` into one callback with N `input_data_ids`.
2. Apply the receipt that triggers this fan-out but stop before applying the resulting Data receipts (do not include them in the same `apply` call), leaving `PostponedReceipt`/`PostponedReceiptId`/`PendingDataCount` rows persisted for `acct.alice.near`.
3. Assert via `state_update`/trie iteration (`get_raw_prefix_for_...`-style helpers or direct `TrieKey` iteration) that these rows exist and that `get_account(&state_update, &acct).unwrap().storage_usage()` does **not** include their byte size.
4. Submit a `DeleteAccountAction` receipt for `acct.alice.near` with a beneficiary; assert `action_delete_account`/`apply` succeeds (no `DeleteAccountWithLargeState` error) despite the outstanding rows.
5. After applying the deletion and committing to the trie, iterate the trie under the `RECEIVED_DATA`/`POSTPONED_RECEIPT`/`POSTPONED_RECEIPT_ID`/`PENDING_DATA_COUNT` prefixes for `acct.alice.near`; assert the rows are still present (non-empty), while `get_account(&state_update, &acct)` returns `None`, demonstrating unbacked orphaned state.

/// Computes the expected storage per account for a given stream of StateRecord(s).
/// For example: the storage for Contract depends on its length, we don't charge storage for receipts
/// and we compute a fixed (config-configured) number of bytes for each account (to store account id).
struct StorageComputer<'a> {
    /// Map from account id to number of storage bytes used.
    result: HashMap<AccountId, u64>,
    /// Configuration that keeps information like 'how many bytes should accountId consume' etc.
    config: &'a StorageUsageConfig,
}

impl<'a> StorageComputer<'a> {
    fn new(config: &'a StorageUsageConfig) -> Self {
        Self { result: HashMap::new(), config: &config }
    }

    /// Updates user's storage info based on the StateRecord.
    fn process_record(&mut self, record: &StateRecord) {
        // Note: It's okay to use unsafe math here, because this method should only be called on the trusted
        // state records (e.g. at launch from genesis)
        let account_and_storage = match record {
            StateRecord::Account { account_id, .. } => {
                Some((account_id.clone(), self.config.num_bytes_account))
            }
            StateRecord::Data { account_id, data_key, value } => {
                let storage_usage =
                    self.config.num_extra_bytes_record + data_key.len() as u64 + value.len() as u64;
                Some((account_id.clone(), storage_usage))
            }
            StateRecord::Contract { account_id, code } => {
                Some((account_id.clone(), code.len() as u64))
            }
            StateRecord::AccessKey { account_id, public_key, access_key } => {
                let access_key: AccessKey = access_key.clone();
                let storage_usage = self.config.num_extra_bytes_record
                    + public_key.trie_id_len() as u64
                    + borsh::object_length(&access_key).unwrap() as u64;
                Some((account_id.clone(), storage_usage))
            }
            StateRecord::GasKeyNonce { account_id, public_key, index: _index, nonce } => {
                let storage_usage = self.config.num_extra_bytes_record
                    + public_key.trie_id_len() as u64
                    + size_of::<NonceIndex>() as u64
                    + borsh::object_length(&nonce).unwrap() as u64;
                Some((account_id.clone(), storage_usage))
            }
            StateRecord::PostponedReceipt(_) => None,
            StateRecord::ReceivedData { .. } => None,
            StateRecord::DelayedReceipt(_) => None,
        };

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
