### Title
STATICCALL sandbox restriction is not inherited by child execution contexts spawned via CREATE/CREATE2, allowing state mutation inside a supposedly read-only call - ([File: actuator/src/main/java/org/tron/core/vm/program/Program.java])

### Summary
The OpenClaw advisory describes a spawn-time privilege check that failed to propagate the "sandboxed" restriction from a requester to a spawned child runtime, letting a restricted caller create an unrestricted child. The equivalent invariant in the TVM is the `STATICCALL` read-only context: once execution enters a call created via `STATICCALL` (`isStaticCall()==true`), every further state-mutating action — including spawning a *new* execution context via `CREATE`/`CREATE2` — must remain non-mutating. java-tron's `Program.createContractImpl` builds the `ProgramInvoke` for the newly spawned child contract-creation context with the static flag **hardcoded to `false`**, regardless of the parent's actual `isStaticCall()` state, and no compensating check exists at the `CREATE`/`CREATE2` opcode dispatch to reject contract creation while inside a static context.

### Finding Description
For ordinary message calls, java-tron correctly inherits/enforces the static-call restriction into child contexts: `callAction` explicitly rejects value transfer while static (`OperationActions.java:975-977`), and `callToAddress` propagates the parent's static flag into the child `ProgramInvoke` via `msg.getOpCode() == Op.STATICCALL || isStaticCall()` (`Program.java:1148`).

`createContractImpl`, however, which backs both `CREATE` and `CREATE2`, builds the child `ProgramInvoke` like this: [1](#0-0) 

The static-call argument passed to `ProgramInvokeFactory.createProgramInvoke` is a hardcoded `false`, unlike the equivalent call-path (`Program.java:1148`) which correctly computes `msg.getOpCode() == Op.STATICCALL || isStaticCall()`. This means:
1. The newly spawned child (the constructor execution of the created contract) never inherits the parent's read-only restriction, so any state mutation performed in the constructor (storage writes, balance transfers, further nested creates) is not blocked by the static-call guard.
2. There is no gating check at the `CREATE`/`CREATE2` opcode level itself (unlike `callAction`'s explicit `isStaticCall()` check for value transfer) that would reject contract creation outright while executing inside a static context.

As a result, a contract invoked via `STATICCALL` — which callers rely on as a hard read-only guarantee (a core EVM/TVM invariant used by patterns such as reentrancy guards, price/oracle reads, and "view"-style callback validation) — can still deploy new contracts and, more importantly, the deployed contract's constructor can perform balance transfers/storage writes that should be impossible under `STATICCALL` semantics, exactly mirroring the OpenClaw class of bug where a restricted principal spawns an unrestricted child execution context.

### Impact Explanation
Any contract can be called from another contract via `STATICCALL`, and any caller relying on the "no state changes possible" guarantee of `STATICCALL` (a security-critical invariant in DeFi composability, e.g. read-only price oracles, ERC-style callback checks, or reentrancy-safety patterns that assume static sub-calls cannot alter state) can have that invariant silently violated. An attacker-controlled contract invoked under `STATICCALL` can use `CREATE`/`CREATE2` to deploy a new contract whose constructor mutates global state (creates accounts, moves TRX balance, writes storage, bumps nonces/total resource weights) even though the calling contract assumed no side effects were possible. This is directly reachable by any unprivileged transaction that triggers a smart contract performing a `STATICCALL` to attacker-controlled bytecode — i.e., every TVM contract call path is affected. Because callers build security assumptions (e.g., preventing reentrancy or state-manipulation) on `STATICCALL`'s guarantee, this can be leveraged to bypass those assumptions and manipulate balances/state in ways the calling contract's logic did not anticipate, matching the "unauthorized account operation" / "unbacked balance" impact bar.

### Likelihood Explanation
High reachability: any account can deploy a malicious contract that is invoked by a victim contract via `STATICCALL` (a very common TVM/Solidity pattern for "view" external calls), and the malicious contract simply issues `CREATE`/`CREATE2` in response — no special privileges, keys, or SR/witness status required. The only work needed is crafting bytecode that performs `CREATE` when called, which is trivial.

### Recommendation
Propagate the parent's static-call state into contract-creation sub-contexts the same way it's done for ordinary calls: pass `isStaticCall()` (not a hardcoded `false`) into `ProgramInvokeFactory.createProgramInvoke` inside `createContractImpl`, and additionally add an explicit guard in the `CREATE`/`CREATE2` opcode handlers (mirroring `callAction`'s `if (program.isStaticCall()) throw new Program.StaticCallModificationException();`) so contract creation is rejected outright whenever the current execution context is static, rather than relying solely on downstream inheritance.

### Proof of Concept
1. Deploy `Victim`, which performs `STATICCALL` to an attacker-supplied address (e.g., a generic "read a value" pattern).
2. Deploy `Attacker`, whose fallback/target function executes `CREATE`/`CREATE2` to deploy a new `Child` contract whose constructor writes storage / transfers TRX / creates further accounts.
3. `Victim.staticCallAttacker(attackerAddress)` → enters `Program.isStaticCall() == true` context → calls into `Attacker` → `Attacker` executes `CREATE` → `Program.createContractImpl` builds the `Child` program invoke with `isStaticCall = false` hardcoded → `Child`'s constructor successfully mutates state (e.g., transfers TRX, writes storage) despite executing underneath a `STATICCALL` boundary that should have made this impossible, and no `Program.StaticCallModificationException` is thrown at any point in the call chain.
