## Analysis

The Napier report's bug class is "output-amount check only guards against the zero/failure edge case, not against economically significant slippage." The strongest analog in java-tron is in the on-chain AMM-style bancor exchange (TRC10 <-> TRX/TRC10 relay pools), specifically `ExchangeInjectActuator` and `ExchangeWithdrawActuator`. Unlike `ExchangeTransactionActuator`, which accepts a caller-supplied `expected` minimum-output field and enforces it (`anotherTokenQuant < tokenExpected` check), `ExchangeInjectActuator`/`ExchangeWithdrawActuator` provide no such caller-supplied minimum-output/slippage parameter at all — they only assert the computed counter-amount is `> 0`.

### Title
Missing Slippage/Minimum-Output Protection in ExchangeInjectActuator and ExchangeWithdrawActuator - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java, actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java)

### Summary
`ExchangeInjectContract` and `ExchangeWithdrawContract` transactions let an exchange's creator inject or withdraw liquidity from a TRX/TRC10 bancor-style pool. The counter-token amount (`anotherTokenQuant`) is computed at execution time from the pool's *current* balances, and the only sanity check performed is that the result is `> 0` [1](#0-0)  and, for withdraw, a fixed internal rounding-precision check unrelated to price movement [2](#0-1) . Neither contract exposes a user-supplied minimum-expected-output field, unlike `ExchangeTransactionContract`, which does enforce `getExpected()` [3](#0-2) .

### Finding Description
`ExchangeInjectActuator.execute` recomputes `anotherTokenQuant` from the pool's live `firstTokenBalance`/`secondTokenBalance` at execution time [4](#0-3) , and `doValidate` performs an equivalent computation but the only bound applied is `anotherTokenQuant <= 0` throwing an error [5](#0-4) . `ExchangeWithdrawActuator` is structured identically — it recomputes `anotherTokenQuant` from the current pool ratio in both `execute` [6](#0-5)  and `doValidate`, again bounding only against `<= 0` and a fixed 0.01% self-consistency rounding check, not against price movement between signing and execution [7](#0-6) .

Because any unprivileged account can move the pool ratio arbitrarily beforehand by issuing an `ExchangeTransactionContract` trade against the same exchange (the pool ratio directly determines `anotherTokenQuant` via `ExchangeCapsule.transaction`/`ExchangeProcessor.exchange` [8](#0-7) ), a broadcaster who observes a pending inject/withdraw transaction in the mempool can sandwich it: submit a large trade to skew the ratio immediately before the victim's inject/withdraw is packed into a block, then reverse the trade afterward, extracting value from the victim's transaction while it still satisfies the only on-chain guard (`> 0`).

### Impact Explanation
The exchange creator (an ordinary, unprivileged account — anyone can create an exchange via `ExchangeCreateContract`) who injects or withdraws liquidity has no way to bound the counter-amount they receive/contribute. A front-runner can force the victim's inject to add liquidity at a skewed ratio (effectively donating value to the attacker) or force a withdraw to return far less of the counter-token than the pool ratio implied when the transaction was signed. This is a direct, unbacked value transfer from victim to attacker — a concrete "theft of funds" style impact reachable purely through ordinary signed transactions, matching Medium severity for insufficient slippage protection.

### Likelihood Explanation
Both actuators are reachable by any account that owns an exchange (a permissionless, unprivileged action), and the attack requires only ordering two additional standard `ExchangeTransactionContract` transactions around the victim's transaction within the same block window — well within capabilities of any anonymous broadcaster observing the mempool. No special node or SR/witness privilege is needed.

### Recommendation
Add an explicit minimum/maximum bound field (analogous to `ExchangeTransactionContract.expected`) to `ExchangeInjectContract` and `ExchangeWithdrawContract`, and enforce it in `ExchangeInjectActuator.doValidate`/`ExchangeWithdrawActuator.doValidate` by comparing the freshly computed `anotherTokenQuant` against the caller-supplied bound, rejecting the transaction if it falls outside the caller's tolerance.

### Proof of Concept
1. Attacker observes a pending `ExchangeInjectContract` (or `ExchangeWithdrawContract`) transaction from the exchange creator in the mempool.
2. Attacker submits an `ExchangeTransactionContract` trade against the same `exchangeId` that shifts `firstTokenBalance`/`secondTokenBalance` favorably for the attacker, with higher energy/bandwidth priority so it lands first.
3. The victim's inject/withdraw executes against the skewed pool state; `ExchangeInjectActuator`/`ExchangeWithdrawActuator` only check `anotherTokenQuant > 0` [1](#0-0) , so it succeeds despite the unfavorable ratio.
4. Attacker submits a reversing `ExchangeTransactionContract` trade to restore the ratio and lock in the value extracted from the victim's inject/withdraw.
