## Title
Unbounded User-Controlled PCRE Regex in `SearchFilesByContent` Enables ReDoS - (File: `internal/gitaly/service/repository/search_files.go`)

## Summary
The `SearchFilesByContent` RPC passes the caller-supplied `query` field directly and unvalidated as a `--perl-regexp` pattern to `git grep`, invoking PCRE's backtracking regex engine on the server. Unlike `SearchFilesByName`, which validates and length-limits its filter and compiles it with Go's linear-time RE2 engine, `SearchFilesByContent` has no length restriction and no engine-level backtracking protection, allowing a crafted query to trigger catastrophic backtracking (ReDoS) and monopolize a Gitaly worker/CPU.

## Finding Description
`SearchFilesByContent` builds a `git grep` command using `req.GetQuery()` as the value of `-e` together with the `--perl-regexp` flag, which causes git to evaluate the pattern with PCRE rather than Go's RE2: [1](#0-0) 

The only validation performed on the request is `validateSearchFilesRequest`, which merely checks that `query` and `ref` are non-empty and that `ref` does not start with `-`; it imposes no length or complexity limit on `query`: [2](#0-1) 

This is in stark contrast to the sibling RPC `SearchFilesByName`, which explicitly limits filter length to `searchFilesFilterMaxLength` (1000 bytes) and compiles the pattern with Go's `regexp` package (RE2, which guarantees linear-time matching and is immune to catastrophic backtracking): [3](#0-2) [4](#0-3) 

PCRE (used via `--perl-regexp` in `git grep`), unlike RE2, uses a backtracking NFA engine that is vulnerable to exponential/catastrophic backtracking for patterns such as nested/overlapping quantifiers (e.g. `(a+)+$`, `(a|aa)+$`) matched against crafted non-matching input. Because `SearchFilesByContent` streams `git grep` output over the whole repository tree at a given ref, an attacker who can invoke this RPC (any ordinary client authorized to call Gitaly's RepositoryService, e.g. via GitLab's code-search feature) can supply such a pathological pattern as `query`, causing the spawned `git grep` process to consume CPU for a very long time processing repository content.

## Impact Explanation
This constitutes a resource-exhaustion / Denial-of-Service vector (CWE-1333) reachable via a normal, unprivileged RPC field (`SearchFilesByContentRequest.query`). A single crafted request can pin a CPU core executing the spawned `git grep` subprocess for an extended period, and repeated requests can exhaust the Gitaly host's git-command concurrency limits, degrading service for all repositories served by that Gitaly node.

## Likelihood Explanation
Likelihood is moderate-to-high: the RPC is reachable by any client permitted to call Gitaly's `RepositoryService` (e.g., GitLab's search/code-search feature forwards user search queries essentially unmodified), the vulnerable field (`query`) has no length or complexity restriction, and PCRE-catastrophic-backtracking patterns are well known and trivial to construct.

## Recommendation
- Impose a reasonable maximum length on `req.GetQuery()` similar to `searchFilesFilterMaxLength` used for `SearchFilesByName`.
- Consider dropping `--perl-regexp` in favor of `--extended-regexp` / default POSIX regex mode (which git implements with a non-backtracking or bounded engine) unless PCRE features are strictly required by clients.
- Enforce a wall-clock timeout on the spawned `git grep` command independent of the general RPC deadline, so pathological patterns cannot exhaust CPU beyond a bounded window.
- Optionally validate/reject patterns with excessive nested quantifiers before execution.

## Proof of Concept
Send a `SearchFilesByContentRequest` against a repository with non-trivial file content, setting:
```
query = "(a+)+$"
ref = "refs/heads/main"
```
Because `--perl-regexp` is always applied and there is no length/complexity check, `git grep --perl-regexp -e "(a+)+$"` is executed by the server; against long lines that don't end in a run of `a`s, PCRE's backtracking engine takes exponential time relative to input length, tying up the worker thread/CPU for the duration of the request while normal, unprivileged clients can trigger this repeatedly.

func validateSearchFilesRequest(ctx context.Context, locator storage.Locator, req searchFilesRequest) error {
	if err := locator.ValidateRepository(ctx, req.GetRepository()); err != nil {
		return err
	}

	if len(req.GetQuery()) == 0 {
		return errors.New("no query given")
	}

	if len(req.GetRef()) == 0 {
		return errors.New("no ref given")
	}

	if bytes.HasPrefix(req.GetRef(), []byte("-")) {
		return errors.New("invalid ref argument")
	}

	return nil
}
