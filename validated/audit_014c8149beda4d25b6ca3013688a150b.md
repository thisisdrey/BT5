### Title
Out-of-bounds read in ijar's ZIP local-header parser when skipping the data-descriptor after a streamed entry - ([File: third_party/ijar/zip.cc])

### Summary
`InputZipFile::ProcessLocalFileEntry` in ijar's ZIP reader validates remaining input length before reading the file name, extra field, and file data via `EnsureRemaining()` [1](#0-0) , but when the entry's general-purpose bit flag indicates a streamed/"data descriptor" trailer (bit 3), the code reads a 4-byte signature and then advances the cursor by 8 or 12 more bytes with **no bounds check at all**: [2](#0-1) 

This mirrors the CVE-2018-20615 pattern almost exactly: a flag in the record (PRIORITY flag in HTTP/2 HEADERS / bit 3 of the ZIP general-purpose flag) triggers an additional fixed-size skip of trailing bytes, and the code advances the read cursor without re-verifying that those extra bytes are actually present within the buffer.

### Finding Description
`ProcessLocalFileEntry` is reached while iterating local file headers of a ZIP/JAR that ijar reads via a memory-mapped file (`MappedInputFile`) [3](#0-2) . Every other field access in this function is preceded by an `EnsureRemaining()` call that validates `n <= input_file_->Length() - offset` [4](#0-3) , including the fixed 26-byte header, `file_name_length_`, `extra_field_length_`, and `compressed_size_` for stored (uncompressed) entries [5](#0-4) [6](#0-5) .

However, the trailing "data descriptor" handling, gated on `general_purpose_bit_flag_ & GENERAL_PURPOSE_BIT_FLAG_COMPRESSED` (an attacker-controlled bit read straight from the header at line 338), performs:
```cpp
u4 signature = get_u4le(p);           // reads 4 bytes, unchecked
if (signature == DATA_DESCRIPTOR_SIGNATURE) {
  p += 4 * 3;                          // skips 12 more bytes, unchecked
} else {
  p += 4 * 2;                          // skips 8 more bytes, unchecked
}
``` [2](#0-1) 

If a crafted entry sets this flag but is placed such that the entry data ends at (or near) the end of the mapped file, `get_u4le(p)` reads past the mapped region, and the subsequent `p +=` advances the cursor arbitrarily past the buffer, both without going through `EnsureRemaining`. On the next iteration `ProcessNext`/`ProcessCentralDirEntry` would then dereference this out-of-bounds `p`, which — since the file is `mmap`'d — can produce a `SIGSEGV`/out-of-bounds read into adjacent memory, exactly the "requires extra bytes... total frame length not re-checked" defect described for HAProxy's HTTP/2 PRIORITY-flag handling.

This code is reachable on attacker-supplied bytes: ijar is invoked (via `java_common.run_ijar` / `stamp_jar`, and internally whenever Bazel builds header/interface jars) on `.jar` files that can originate from external dependencies (e.g., a `java_import` or Maven/registry-fetched jar consumed by a build), i.e., content from an untrusted origin server or mirror, with no cryptographic re-validation of the ZIP's internal structure beyond the caller's whole-file `sha256`, which does not stop malformed *internal* length bookkeeping within an otherwise checksum-valid file. The existing `MalformedExtraField` regression test shows Bazel engineers do defend against unchecked extra-field walks elsewhere in this codebase (`singlejar`'s `ExtraField::find`) [7](#0-6) , but no analogous defense exists for ijar's data-descriptor skip.

### Impact Explanation
An out-of-bounds read against a memory-mapped file can crash the ijar subprocess (denial of service against that build action) and, depending on heap/mapping layout, potentially leak adjacent memory content interpreted as ZIP structure into subsequent parsing decisions. This matches the High-severity classification of the CVE-2018-20615 analog (out-of-bounds read causing crash).

### Likelihood Explanation
Reaching this code only requires supplying a ZIP/JAR with the bit-3 general-purpose flag set and truncating (or carefully sizing) the entry so the descriptor bytes fall past the mapped file's end — a low-effort, deterministic crafting task with no need to defeat any hash check on the internal structure, only on the overall archive bytes (which the attacker fully controls since they are the origin of the archive).

### Recommendation
Add an `EnsureRemaining()` check before reading the optional data-descriptor signature and before advancing `p` by 8 or 12 bytes in `ProcessLocalFileEntry`, mirroring the bounds checks already used for the file name, extra field, and file data in the same function [2](#0-1) .

### Proof of Concept
Not fully verified in this session — I was not able to trace `get_u4le`'s implementation (`third_party/ijar/common.h`) or `ProcessNext`'s outer loop to conclusively confirm the absence of any implicit page-level slack that would prevent an actual OOB read on a real `mmap`, nor did I locate/execute an existing JUnit/shell test exercising this exact path. A concrete PoC would need to: build a ZIP with one local file header whose general-purpose bit 3 is set, whose compressed/uncompressed size is `0` (streamed), and whose file data plus optional 4-byte data-descriptor signature is positioned to end exactly at the mapped file's length, then run `ijar` on it and observe a crash/ASAN OOB-read report. I recommend a Devin session with build/test execution access to construct and run this PoC (e.g., as a `third_party/ijar/test/ijar_test.sh` case or a new C++ unit test alongside `zip.cc`) to confirm exploitability before treating this as a fully validated finding.
