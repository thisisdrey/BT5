### Title
Cross-repository/cross-commit replay of Gitaly's system commit signature spoofs `SIGNER_SYSTEM` verification status - ([File: internal/gitaly/service/commit/get_commit_signatures.go])

### Summary
`GetCommitSignatures` classifies a commit's signature as `SIGNER_SYSTEM` (i.e., "signed by Gitaly") purely by checking whether the raw signature bytes verify against the raw commit payload bytes, with no binding to the specific commit object, repository, or any nonce/identifier unique to that signing event. [1](#0-0) 
Because the signed payload is just the literal header text (`tree`, `parent`, `author`, `committer`, message) and does not include the resulting commit OID or any repository-specific value, an attacker who obtains one Gitaly-produced signature (trivially, via this same public RPC) can copy that exact signature and payload into an attacker-crafted commit object using `git hash-object --literally`, causing Gitaly to falsely report that the new, never-actually-signed commit is `SIGNER_SYSTEM` verified.

### Finding Description
`GetCommitSignatures` parses a requested commit and, if the deployment has a Gitaly signing key configured, calls `signingKeys.Verify(signature, commit.SignatureData.Payload)`, and if it succeeds sets `Signer = SIGNER_SYSTEM`: [2](#0-1) 

The verification (`SigningKeys.Verify` / SSH `Verify`) only checks that the signature is a valid signature over the exact byte sequence of `Payload`: [3](#0-2) [4](#0-3) 

The `Payload` is built by `ParseCommit` by concatenating the raw header lines (`tree`, `parent`, `author`, `committer`, etc.) and the message body, excluding only the signature header itself: [5](#0-4) 

Critically, this payload:
- Contains no reference to the resulting commit's own object ID (which would be circular, but also means the signature does not "commit" to a specific object).
- Contains no repository identifier, GlProjectID, or any Gitaly-specific nonce — it is only ever the git-standard signable commit text (tree/parents/author/committer/message).
- Is fully reproducible by anyone who controls a commit's tree, parent(s), author/committer identity strings, dates, and message — all attacker-controlled fields, especially for a root (parentless) commit where the tree content is likewise attacker-constructed from ordinary blobs and thus produces a deterministic, content-addressed OID.

The test suite for this RPC demonstrates the exact primitive an attacker would use: crafting an arbitrary raw commit object with an embedded signature via `git hash-object -w -t commit --stdin --literally`, bypassing any actual git/Gitaly signing step: [6](#0-5) 

Because `GetCommitSignatures` is a normal, unprivileged (repository-read-scoped) RPC that returns both `Signature` and `SignedText` (the payload) in the clear for any commit a caller can read: [7](#0-6) 
an ordinary user who has read access to any repository containing at least one Gitaly-system-signed commit (e.g., their own project, since Gitaly signs commits it authors on behalf of the system/GitLab in `WriteCommit` when `Sign` is set) can extract a valid `(Signature, Payload)` pair and reuse it verbatim — by constructing a new commit object (in the same repo or, since tree/blob OIDs are content-addressed and thus reproducible across repos, potentially a different repo) whose tree, author, committer, dates and message exactly reproduce that payload text — to have Gitaly falsely attest `SIGNER_SYSTEM` for a commit Gitaly never actually signed.

This is structurally the same bug class as the referenced report: a signature intended to authorize/attest one specific transaction (here, one specific commit-signing event by Gitaly) carries no unique nonce or binding, so it can be lifted and replayed to authorize a different, attacker-chosen "transaction" (here, a forged commit) that satisfies the same raw byte-equality check.

### Impact Explanation
`SIGNER_SYSTEM` is the trust signal GitLab uses to indicate a commit was verified as authored/signed by the GitLab/Gitaly system itself (as opposed to `SIGNER_USER`), which downstream consumers (e.g., GitLab's "Verified" badge/UI, or any other consumer relying on this RPC's `Signer` field) treat as an integrity/provenance claim. An attacker able to replay a leaked signature to forge this classification on content Gitaly never actually signed can mislead reviewers/consumers about the provenance of a commit, undermining a security-relevant trust indicator. This is a Medium-severity integrity issue analogous to the reported bug class: the value that the signature was meant to bind to (the specific signing event) is not actually enforced.

### Likelihood Explanation
Likelihood is Medium: it requires the attacker to (1) obtain at least one Gitaly-system-signed commit's `(Signature, Payload)` pair, which is possible from any repository they have read access to that has such a commit (e.g., a repository they create themselves and where Gitaly signs a commit as part of normal operation), and (2) construct a new commit object whose tree/author/committer/message exactly reproduce the payload text, using standard, low-level git plumbing (`hash-object --literally`) that is available to anyone who can push raw objects into a repository they control. No cryptographic break, insider access, or leaked secret is required — only ordinary API/read access plus the ability to push a crafted commit object, both of which are normal capabilities of an unprivileged Gitaly user.

### Recommendation
Bind the Gitaly system signature to a value that is unique per signing event and not attacker-reproducible across contexts, e.g.:
- Include the target repository identity (or a per-transaction/nonce value) as part of the signed payload, or
- Sign over the fully-computed commit OID (post-construction, via a two-step process) rather than only the pre-object header text, so that the signature is bound to the actual, unique object identity and cannot be satisfied by a different, attacker-crafted commit that merely reproduces the header text.
Additionally, consider tracking which specific commit OIDs Gitaly itself has signed (e.g., recording signed OIDs at signing time) so that `GetCommitSignatures` can cross-check against that record rather than relying solely on a stateless signature-verification-over-payload check.

### Proof of Concept
1. As an ordinary user, create/own a repository and have Gitaly write and sign a commit (`WriteCommitConfig.Sign = true` path used internally when GitLab creates commits on the user's behalf, e.g. via `UserCommitFiles`), then call `GetCommitSignatures` for that commit to retrieve `Signature` and `SignedText` — confirmed reachable via `internal/gitaly/service/commit/get_commit_signatures.go:17-84`.
2. Construct a new commit whose `tree`, `author`, `committer`, dates, and message exactly match the `SignedText` bytes obtained in step 1 (attacker fully controls these, e.g., for a root/orphan commit with a self-built tree of ordinary blobs).
3. Use `git hash-object -w -t commit --stdin --literally` to inject the harvested `Signature` bytes as the commit's `gpgsig`/signature header, exactly as done in `createCommitWithSignature` in the test helper (`internal/gitaly/service/commit/get_commit_signatures_test.go:643-668`), producing a new commit ID distinct from the original.
4. Call `GetCommitSignatures` on this new, never-Gitaly-signed commit; `signingKeys.Verify(signature, payload)` succeeds because the payload bytes are identical, causing the response to report `Signer: SIGNER_SYSTEM` for a commit Gitaly never actually signed.

func sendResponse(
	signature []byte,
	commit *catfile.Commit,
	signer gitalypb.GetCommitSignaturesResponse_Signer,
	stream gitalypb.CommitService_GetCommitSignaturesServer,
) error {
	if len(signature) <= 0 {
		return nil
	}

	err := stream.Send(&gitalypb.GetCommitSignaturesResponse{
		CommitId:  commit.Id,
		Signature: signature,
		Signer:    signer,
		Author:    commit.Author,
		Committer: commit.Committer,
	})
	if err != nil {
		return err
	}

	streamWriter := streamio.NewWriter(func(p []byte) error {
		return stream.Send(&gitalypb.GetCommitSignaturesResponse{SignedText: p})
	})

	msgReader := bytes.NewReader(commit.SignatureData.Payload)

	_, err = io.Copy(streamWriter, msgReader)
	if err != nil {
		return fmt.Errorf("failed to send response: %w", err)
	}

	return nil
}

// Verify iterates over all signing keys and returns nil if any
// verification was successful. Otherwise, the last error is returned.
// Note: when Golang 1.19 is no longer supported, can be refactored using errors.Join
func (s *SigningKeys) Verify(signature, signedText []byte) error {
	var err error
	for _, signingKey := range append([]SigningKey{s.primaryKey}, s.secondaryKeys...) {
		err = signingKey.Verify(signature, signedText)
		if err == nil {
			return nil
		}
	}
	return err
}

// Verify method verifies whether a signature has been created by this signing key
func (sk *SSHSigningKey) Verify(signatureText, signedText []byte) error {
	block, rest := pem.Decode(signatureText)
	if block == nil || len(rest) > 0 || block.Type != sshSignatureType {
		return fmt.Errorf("invalid signature text")
	}

	sshSig := &sshSignature{}
	if err := ssh.Unmarshal(block.Bytes, sshSig); err != nil {
		return fmt.Errorf("parse signature text: %w", err)
	}

	signature := &ssh.Signature{}
	if err := ssh.Unmarshal(sshSig.Signature, signature); err != nil {
		return fmt.Errorf("parse signature: %w", err)
	}

	h := sha512.New()
	if _, err := h.Write(signedText); err != nil {
		return fmt.Errorf("failed to create sha for verifying content: %w", err)
	}

	signedData := signedData{
		MagicHeader:   sshSig.MagicHeader,
		Namespace:     sshSig.Namespace,
		HashAlgorithm: sshSig.HashAlgorithm,
		Hash:          h.Sum(nil),
	}

	return sk.PrivateKey.PublicKey().Verify(ssh.Marshal(signedData), signature)
}

func createCommitWithSignature(t *testing.T, cfg config.Cfg, repoPath, signatureField, signature, commitMessage string) (git.ObjectID, string) {
	// Each line of the signature needs to start with a space so that Git recognizes it as a continuation of the
	// field.
	signatureLines := strings.Split(signature, "\n")
	for i, signatureLine := range signatureLines {
		signatureLines[i] = " " + signatureLine
	}

	commitData := fmt.Sprintf(`tree %s
author Bug Fixer <bugfixer@email.com> 1584564725 +0100
committer Bug Fixer <bugfixer@email.com> 1584564725 +0100

%s
`, gittest.DefaultObjectHash.EmptyTreeOID, commitMessage)

	signedCommitData := strings.Replace(commitData, "\n\n", fmt.Sprintf("\n%s%s\n\n", signatureField, strings.Join(signatureLines, "\n")), 1)

	stdout := gittest.ExecOpts(t, cfg, gittest.ExecConfig{
		Stdin: strings.NewReader(signedCommitData),
	}, "-C", repoPath, "hash-object", "-w", "-t", "commit", "--stdin", "--literally")

	commitID, err := gittest.DefaultObjectHash.FromHex(text.ChompBytes(stdout))
	require.NoError(t, err)

	return commitID, commitData
}
