Based on my research, I found a concrete local analog to the H-6 pattern (prover fully controls a size/domain parameter that should be derived from real state) in the Merkle-Mountain-Range (MMR) proof-verification code that backs the BEEFY bridge light client.

### Title
Untrusted `leaf_count` in stateless MMR proof verification allows prover-controlled domain size - (File: `substrate/frame/merkle-mountain-range/src/mmr/mmr.rs`)

### Summary
The stateless MMR leaf-proof verifier `verify_leaves_proof` derives the MMR size used to reconstruct the Merkle proof entirely from the attacker/relayer-supplied `proof.leaf_count` field, with no cross-check against the real, expected leaf count of the MMR the root actually belongs to.

### Finding Description
`verify_leaves_proof` (stateless variant) computes: [1](#0-0) 
`let size = NodesUtils::new(proof.leaf_count).size();` and builds `mmr_lib::MerkleProof::new(size, proof.items...)` directly from that attacker-supplied `proof.leaf_count`, then verifies against `root`. There is no bound check comparing `proof.leaf_count` to any independently known leaf count.

Contrast this with the stateful sibling `Pallet::verify_leaves`, which explicitly guards the same value against on-chain storage before use: [2](#0-1) 
`if proof.leaf_count > NumberOfLeaves::<T, I>::get() || proof.leaf_count == 0 || ...`. This is precisely the "prover-controlled domain size" flaw described in the Pico report: one code path (`verifier.rs::quotient_degree` in Pico, `Pallet::verify_leaves` here) legitimately derives the size from trusted state, while the other trusted-input path (Pico's unchecked prover-supplied degree, here the stateless `verify_leaves_proof`) takes the size straight from the proof with no cross-check.

This stateless verifier is reachable both via the runtime API `verify_proof_stateless` (exposed to any caller supplying `root`, `leaves`, `proof`) as seen in the Rococo/Westend runtime `MmrApi` implementations, and is also the type of primitive that bridge modules such as the BEEFY bridge pallet build on, where the "root" comes from an externally-attested BEEFY commitment and the `mmr_proof` (including `leaf_count`) is untrusted data submitted by a relayer: [3](#0-2) 

### Impact Explanation
If a consumer of the stateless proof-verification primitive treats a validly-verified (root, leaves) pair as proof of *specific* leaf inclusion/position without independently pinning `leaf_count` to the real, expected MMR size for that root, an attacker who controls `leaf_count`, `items`, and `leaf_indices` can potentially construct an internally-consistent-but-wrong MMR structure that still satisfies `p.verify(...)` for a forged leaf set/position, since the "domain" (mmr_size) that determines peak bagging and proof-path decoding is self-declared by the prover rather than being tied to ground truth. This mirrors the H-6 root cause exactly: soundness of a Merkle/FRI-style proof depends on the domain size being derived from real state, not trusted prover input.

### Likelihood Explanation
This is only exploitable to the extent a caller relies on the *stateless* verifier without separately validating `leaf_count`/`root` correspondence out-of-band (the on-chain `Pallet::verify_leaves` path is already safe because it checks against `NumberOfLeaves`). I was not able to fully trace, in the time available, whether `bp_beefy::verify_mmr_leaves_proof` (declared in `bridges/primitives/beefy/src/lib.rs`, which I could not retrieve) itself performs an equivalent bound check before or after calling into this MMR verification primitive, or whether it independently pins `leaf_count` via the BEEFY commitment's own leaf-count field. This is a real gap in my verification and should be checked directly in a follow-up session before treating this as a confirmed exploitable path.

### Recommendation
Ensure every consumer of the stateless `verify_leaves_proof` (and any bridge pallet built on `bp_beefy::verify_mmr_leaves_proof`) independently validates that the proof's declared `leaf_count` matches an authenticated, trusted value (e.g., a leaf-count field bound into the same signed commitment as the MMR root) before using it to reconstruct the proof size — mirroring the `NumberOfLeaves` check already present in the stateful `Pallet::verify_leaves`.

pub fn verify_leaves_proof<H, L>(
	root: H::Output,
	leaves: Vec<Node<H, L>>,
	proof: LeafProof<H::Output>,
) -> Result<bool, Error>
where
	H: Hash,
	L: FullLeaf,
{
	let size = NodesUtils::new(proof.leaf_count).size();

	if leaves.len() != proof.leaf_indices.len() {
		return Err(Error::Verify.log_debug("Proof leaf_indices not same length with leaves"));
	}

	let leaves_and_position_data = proof
		.leaf_indices
		.into_iter()
		.map(|index| mmr_lib::leaf_index_to_pos(index))
		.zip(leaves.into_iter())
		.collect();

	let p = mmr_lib::MerkleProof::<Node<H, L>, Hasher<H, L>>::new(
		size,
		proof.items.into_iter().map(Node::Hash).collect(),
	);
	p.verify(Node::Hash(root), leaves_and_position_data)
		.map_err(|e| Error::Verify.log_debug(e))
}

/// Verify MMR proof of given leaf.
pub(crate) fn verify_beefy_mmr_leaf<T: Config<I>, I: 'static>(
	mmr_leaf: &BridgedBeefyMmrLeaf<T, I>,
	mmr_proof: BridgedMmrProof<T, I>,
	mmr_root: BridgedMmrHash<T, I>,
) -> Result<(), Error<T, I>> {
	let mmr_proof_leaf_count = mmr_proof.leaf_count;
	let mmr_proof_length = mmr_proof.items.len();

	// Verify the mmr proof for the provided leaf.
	let mmr_leaf_hash = BridgedMmrHashing::<T, I>::hash(&mmr_leaf.encode());
	verify_mmr_leaves_proof(
		mmr_root,
		vec![BridgedMmrDataOrHash::<T, I>::Hash(mmr_leaf_hash)],
		mmr_proof,
	)
	.map_err(|e| {
		tracing::error!(
			target: LOG_TARGET,
			error=?e,
			?mmr_leaf_hash,
			root=?mmr_root,
			leaf_count=%mmr_proof_leaf_count,
			len=%mmr_proof_length,
			"MMR proof of leaf verification has failed"
		);

		Error::<T, I>::MmrProofVerificationFailed
	})
}
