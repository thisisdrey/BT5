### Title
`RPCGetAttachmentRequestHandler::try_handle_request` serves attachment content solely on `was_instantiated=1`, without verifying any confirmed on-chain name-operation actually committed to that hash - (File: stackslib/src/net/api/getattachment.rs)

### Summary
`try_handle_request` (getattachment.rs:104-119) resolves the requested `attachment_hash` exclusively through `AtlasDB::find_attachment` (db.rs:641-648), which only checks `hash = ?1 AND was_instantiated = 1`. It never joins against `attachment_instances` to confirm a `Checked`/on-chain-referenced instance exists for that hash, so any row previously written into the `attachments` table with `was_instantiated=1` — however it got there — is served as if it were canonical BNS zonefile/profile data.

### Finding Description
The equality the endpoint is supposed to preserve is: *bytes served for `content_hash` == bytes that some confirmed `AttachmentInstance` (i.e., an on-chain name-operation) committed to for that hash*. The actual query executed is: [1](#0-0) 

which only checks that a row with the given `hash` exists and `was_instantiated = 1` — it does not join or cross-check against `attachment_instances WHERE content_hash = ? AND status = 'Checked'`. `try_handle_request` blindly trusts this result: [2](#0-1) 

Any code path that can flip `was_instantiated` to `1` for an attacker-chosen hash (e.g. `insert_instantiated_attachment`, called from the download state machine or from unsolicited-attachment handling paths established in prior findings) makes that content permanently servable at `/v2/attachments/{hash}`, with no re-validation at read time that a confirmed name-operation ever referenced this hash: [3](#0-2) 

The one piece of self-consistency that does hold is that `insert_instantiated_attachment` keys the row by `attachment.hash()` computed from the actual content bytes, so the stored `(hash, content)` pair is internally consistent (content really does hash to the key). What is missing is any check that the hash is tied to a *confirmed* `AttachmentInstance` — the `UPDATE attachment_instances SET is_available = 1 ...` statement in the same function is a best-effort side effect, not a precondition; the `INSERT OR REPLACE INTO attachments` succeeds unconditionally regardless of whether any instance row exists at all.

### Impact Explanation
Once a bogus `(hash, content)` pair is present in the `attachments` table with `was_instantiated=1` (via the poisoning path from prior questions), the GET endpoint will serve that content with a `200 OK` for the corresponding hash to any unprivileged remote caller. This matches "High: attachment/BNS mismatch" — BNS clients resolving a name's zonefile by content hash will receive attacker-chosen data for a hash that no confirmed name-operation ever committed to, and this is repeatable for every subsequent GET request without further attacker action.

### Likelihood Explanation
This finding is entirely dependent on the storage-poisoning precondition established in the referenced prior questions (an attacker successfully calling/triggering `insert_instantiated_attachment` for a hash of their choosing outside of a confirmed name-operation). Given that precondition, exploiting the serve path is trivial and free: any remote unprivileged client can issue `GET /v2/attachments/{content_hash}` with no authentication, and it is reachable on the node's public RPC port.

### Recommendation
Change `find_attachment` (or the caller) to only return content when there exists a corresponding `attachment_instances` row with `status = Checked` (or equivalently `is_available = 1`) for that `content_hash`, e.g. by joining `attachments` and `attachment_instances` on `content_hash`/`hash` and requiring `status = 'checked'`. This ties serving to the presence of a name-operation-derived instance record rather than solely to the `was_instantiated` flag, closing the gap between "content exists in storage" and "content was committed to by a confirmed on-chain operation."

### Proof of Concept
```rust
// stackslib/src/net/atlas/tests.rs (or a new test)
#[test]
fn getattachment_serves_uninstantiated_link_bogus_content() {
    let atlas_config = AtlasConfig::new(false);
    let mut atlas_db = AtlasDB::connect_memory(atlas_config).unwrap();

    // Bogus attachment never referenced by any AttachmentInstance / name-op
    let bogus = Attachment { content: vec![0xde, 0xad, 0xbe, 0xef] };

    // Simulates the poisoning path from prior questions: no confirmed
    // AttachmentInstance exists for bogus.hash() at all.
    atlas_db.insert_instantiated_attachment(&bogus).unwrap();

    // find_attachment returns it anyway, with no join to attachment_instances
    let found = atlas_db.find_attachment(&bogus.hash()).unwrap();
    assert_eq!(found, Some(bogus.clone()));

    // Sanity: confirm no Checked instance exists referencing this hash
    let instances = atlas_db.find_all_attachment_instances(&bogus.hash()).unwrap();
    assert!(instances.is_empty(), "no confirmed instance should reference this hash");
}
```
Combined with an HTTP-level test (`stackslib/src/net/api/tests/getattachment.rs`) issuing `GET /v2/attachments/{bogus.hash()}` against a node whose `AtlasDB` contains this row, the handler returns `200 OK` with `GetAttachmentResponse { attachment: bogus }` despite the absence of any confirmed on-chain commitment to that hash.

    pub fn insert_instantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let tx = self.tx_begin()?;
        tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)",
            params![attachment.hash(), attachment.content, now],
        )?;
        tx.execute(
            "UPDATE attachment_instances SET is_available = 1 WHERE content_hash = ?1 AND status = ?2",
            params![attachment.hash(), AttachmentInstanceStatus::Checked],
        )?;
        tx.commit()?;
        Ok(())
    }
