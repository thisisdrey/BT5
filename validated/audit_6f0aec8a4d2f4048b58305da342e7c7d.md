### Title
Signature malleability enables multisig-threshold bypass in TVM's `ValidateMultiSign` precompiled contract - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` precompiled contract (TVM address `0x0a`), which lets any deployed smart contract verify a TRON account's M-of-N `Permission` on-chain, deduplicates recovered signers incorrectly: it treats two different raw signature byte-strings from the *same* address as two independent approvals unless the byte-strings are identical. Because ECDSA signatures are malleable (a valid `(r, s, v)` always has an equivalent `(r, n-s, v')` that recovers to the same address), an attacker holding a single valid signature from one key can trivially derive a second, distinct-looking signature and have it counted a second time, inflating `totalWeight` and bypassing the intended multi-signature threshold.

### Finding Description
`ValidateMultiSign.execute()` recovers the signer address for every submitted signature and tracks which addresses/signatures were already counted: [1](#0-0) 

For each signature `sign`:
1. `recoveredAddr = recoverAddrBySign(sign, hash)` recovers the signer address via `SignUtils.signatureToAddress` / `ECKey.recoverPubBytesFromSignature`, which performs no low-S / canonical-signature check. [2](#0-1) [3](#0-2) 
2. If `recoveredAddr` was already used, the code only `continue`s (skips) when the *exact byte-for-byte* `sign` was already recorded — otherwise it falls through and adds the address's weight to `totalWeight` again.

Because `s` and `n-s` (with the complementary recovery id) both recover to the same address but produce different signature bytes, an attacker with exactly one valid signature from a key can submit `[sig, malleate(sig)]` and have that single key's weight counted twice, three times, etc. (bounded only by `MAX_SIZE = 5`). This directly maps to the SWC-117 signature-malleability class cited in the external report, but here it manifests as a threshold-bypass rather than a replay attack.

By contrast, the consensus-level transaction multisig path `TransactionCapsule.checkWeight` correctly dedupes by *recovered address* (rejecting "has signed twice"), showing the intended, safe pattern: [4](#0-3) 
The TVM precompile diverges from this safe pattern by additionally comparing raw signature bytes, reintroducing the malleability weakness in a codepath any smart contract can invoke.

### Impact Explanation
Any smart contract that uses `ValidateMultiSign` (address `0x0a`) to gate privileged actions (custodial withdrawals, multisig wallet approvals, order execution, governance actions, etc.) can have its M-of-N threshold satisfied by an attacker controlling fewer than M real private keys, as long as they possess at least one valid signature for the underlying data. This is an unauthorized account operation / authorization bypass that can lead to theft of funds or unauthorized execution of privileged contract logic gated behind TRON account multi-signature permissions.

### Likelihood Explanation
Exploitation requires only:
- A contract deployed that relies on `ValidateMultiSign` for authorization (a documented, commonly used TRON precompile for on-chain multisig verification).
- The attacker possesses one legitimate signature (their own, or one leaked/obtained legitimately as a partial co-signer) over the message hash.
- Standard, well-known ECDSA malleability arithmetic (`s' = n - s`, flip `v`) — no cryptographic breakthrough needed.

This is reachable by any unprivileged contract caller/deployer and requires no special privileges, node compromise, or malicious validator collusion.

### Recommendation
Change the dedup logic in `ValidateMultiSign.execute()` (and the analogous logic in `BatchValidateSign`) to skip on `recoveredAddr` alone, not on the raw signature bytes — i.e., once an address's weight has been counted, any further signature recovering to that same address must be ignored entirely, mirroring `TransactionCapsule.checkWeight`'s "signed twice" rejection. Additionally, enforce canonical (low-S) signature validation in `recoverAddrBySign`/`ECKey.recoverPubBytesFromSignature` (reject `s > n/2`), consistent with OpenZeppelin's `ECDSA` library recommendation in the referenced report, to eliminate malleable duplicates at the source.

### Proof of Concept
1. Deploy or use an existing contract that calls the `ValidateMultiSign` precompile (`0x0a`) to authorize an action, backed by a TRON account `A` with an Active `Permission` requiring threshold 2, keys `{key1: weight 1, key2: weight 1}`.
2. Attacker controls only `key1`. They obtain (or produce) one valid signature `sig1 = (r, s, v)` of `key1` over the precompile's hash (`sha256(address || permissionId || data)`, per `combine`/`hash` construction at lines 1062–1064 of `PrecompiledContracts.java`). [5](#0-4) 
3. Attacker computes the malleated variant `sig2 = (r, n - s, v')` (standard secp256k1 malleability transform), which recovers to the same `key1` address.
4. Attacker calls the target contract, supplying signatures `[sig1, sig2]` to `ValidateMultiSign(address_A, permissionId, data, [sig1, sig2])`.
5. In `execute()`: iteration 1 recovers `key1` and adds weight 1; iteration 2 recovers `key1` again — `executedSignList` contains `key1`'s address but not `sig2`'s exact bytes, so the `continue` is skipped and weight 1 is added again, reaching `totalWeight = 2 >= threshold`, and the precompile returns `true` (`dataOne()`). [6](#0-5) 
6. The calling contract treats this as a valid 2-of-2 approval despite the attacker controlling only `key1`, bypassing the intended multisig requirement.

  @Nullable
  public static byte[] recoverPubBytesFromSignature(int recId,
      ECDSASignature sig, byte[] messageHash) {
    check(recId >= 0, "recId must be positive");
    check(sig.r.signum() >= 0, "r must be positive");
    check(sig.s.signum() >= 0, "s must be positive");
    check(messageHash != null, "messageHash must not be null");
    // 1.0 For j from 0 to h   (h == recId here and the loop is outside
    // this function)
    //   1.1 Let x = r + jn
    BigInteger n = CURVE.getN();  // Curve order.
    BigInteger i = BigInteger.valueOf((long) recId / 2);
    BigInteger x = sig.r.add(i.multiply(n));
    //   1.2. Convert the integer x to an octet string X of length mlen
    // using the conversion routine
    //        specified in Section 2.3.7, where mlen = ⌈(log2 p)/8⌉ or
    // mlen = ⌈m/8⌉.
    //   1.3. Convert the octet string (16 set binary digits)||X to an
    // elliptic curve point R using the
    //        conversion routine specified in Section 2.3.4. If this
    // conversion routine outputs “invalid”, then
    //        do another iteration of Step 1.
    //
    // More concisely, what these points mean is to use X as a compressed
    // public key.
    ECCurve.Fp curve = (ECCurve.Fp) CURVE.getCurve();
    BigInteger prime = curve.getQ();  // Bouncy Castle is not consistent
    // about the letter it uses for the prime.
    if (x.compareTo(prime) >= 0) {
      // Cannot have point co-ordinates larger than this as everything
      // takes place modulo Q.
      return null;
    }
    // Compressed allKeys require you to know an extra bit of data about the
    // y-coord as there are two possibilities.
    // So it's encoded in the recId.
    ECPoint R = decompressKey(x, (recId & 1) == 1);
    //   1.4. If nR != point at infinity, then do another iteration of
    // Step 1 (callers responsibility).
    if (!R.multiply(n).isInfinity()) {
      return null;
    }
    //   1.5. Compute e from M using Steps 2 and 3 of ECDSA signature
    // verification.
    BigInteger e = new BigInteger(1, messageHash);
    //   1.6. For k from 1 to 2 do the following.   (loop is outside this
    // function via iterating recId)
    //   1.6.1. Compute a candidate public key as:
    //               Q = mi(r) * (sR - eG)
    //
    // Where mi(x) is the modular multiplicative inverse. We transform
    // this into the following:
    //               Q = (mi(r) * s ** R) + (mi(r) * -e ** G)
    // Where -e is the modular additive inverse of e, that is z such that
    // z + e = 0 (mod n). In the above equation
    // ** is point multiplication and + is point addition (the EC group
    // operator).
    //
    // We can find the additive inverse by subtracting e from zero then
    // taking the mod. For example the additive
    // inverse of 3 modulo 11 is 8 because 3 + 8 mod 11 = 0, and -3 mod
    // 11 = 8.
    BigInteger eInv = BigInteger.ZERO.subtract(e).mod(n);
    BigInteger rInv = sig.r.modInverse(n);
    BigInteger srInv = rInv.multiply(sig.s).mod(n);
    BigInteger eInvrInv = rInv.multiply(eInv).mod(n);
    ECPoint.Fp q = (ECPoint.Fp) ECAlgorithms.sumOfTwoMultiplies(CURVE
        .getG(), eInvrInv, R, srInv);
    return q.getEncoded(/* compressed */ false);
  }
