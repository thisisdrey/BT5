### Title
Attacker permanently blocks a victim's deposits and borrows by stuffing `depositTokensOfAccount` to `MAX_TOKENS_PER_USER` via dust deposits/transfers — ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
CVE-2016-0651 is an unprivileged-user availability attack (a feature — the Optimizer — turned into a DoS vector). The Metronome analog is the per-account token list: `Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` revert with `UserReachedMaxTokens` once `debt + deposit tokens >= 30` (`MAX_TOKENS_PER_USER`). Because entries are added whenever a balance goes `0 → >0`, any unprivileged user can push dust `DepositToken` balances onto a victim — via `DepositToken.deposit(amount_, onBehalfOf_=victim)` or `DepositToken.transfer(victim, dust)` — and fill the victim's list to the cap without consent. Once full, every mint/transfer of a *new* deposit or debt token to the victim reverts.

### Finding Description
- `Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` are guarded by `onlyIfAdditionWillNotReachMaxTokens`, which reverts at 30 entries. [1](#0-0) 
- `DepositToken._mint` and `_transfer` unconditionally call `pool.addToDepositTokensOfAccount(account_)` when the recipient's balance was zero — the recipient never opts in. [2](#0-1) [3](#0-2) 
- `deposit(amount_, onBehalfOf_)` lets anyone mint deposit tokens to an arbitrary beneficiary, so the attacker doesn't even need a prior balance — one wei of underlying per call is enough. [4](#0-3) 
- Entries are only removed when the balance returns to exactly zero (`removeFromDepositTokensOfAccount`). [5](#0-4) 
- Escape requires the victim to transfer the dust away, but `transfer`/`transferFrom` call `_revertIfLocked`, which checks `unlockedBalanceOf` — a function that returns `0` when the account's debt consumes its collateral buffer. [6](#0-5)  So for a victim with any meaningful debt, the pushed dust is locked and the slots can never be freed.

Attack path (all unprivileged, all public entry points):
1. Victim holds a leveraged position (deposit tokens + debt tokens already occupy some slots, e.g. 20).
2. Attacker calls `deposit(1 wei, victim)` — or `transfer(victim, 1)` after depositing to themselves — for each remaining registered deposit token until `debtTokensOfAccount + depositTokensOfAccount == 30`.
3. From then on: `DepositToken.deposit`/`transfer`/`mint` of any new token to the victim reverts inside `_mint`/`_transfer`; `DebtToken.issue/mint` of a new synth reverts in `addToDebtTokensOfAccount`. `SmartFarmingManager.leverage` also reverts because it mints debt/deposit tokens.

### Impact Explanation
Liveness/availability loss with path to loss of funds: a victim whose position is drifting toward liquidation cannot deposit new collateral types nor mint new synths; worse, if the pool has ≥30 deposit offerings (or the victim already holds several debt tokens), the attacker fills *all* free slots, and since the dust is locked by `_revertIfLocked`, the victim cannot remove entries, cannot top up collateral, and cannot be rescued — leading to forced liquidation (loss via liquidation fees and seized collateral). Even for healthy users this temporarily blocks deposits, borrows, receipt of deposit tokens, and `seize` to them as liquidator. Invariant broken: position-management liveness.

### Likelihood Explanation
Requires the pool to have enough registered deposit/debt tokens to fill 30 slots when combined with the victim's existing positions (deposit tokens plus victim's own debt tokens count together). Metronome pools list many collaterals and synthetics, so on populated deployments this is reachable with only gas-cost dust transfers. No privileged role, oracle manipulation, or governance action is needed. The only mitigation is the 30 cap itself, which is exactly what the attack weaponizes.

### Recommendation
- Remove attacker-pushable slot consumption: add a per-account opt-in/whitelist for `addToDepositTokensOfAccount` on unsolicited transfers, or require a minimum first-transfer threshold (e.g. dust below `MIN_BALANCE` does not register in the account list).
- Alternatively, auto-remove on the reverse path or allow `removeFromDepositTokensOfAccount` to be triggered for dust balances regardless of lock status, so victims can always free slots.

### Proof of Concept
Hardhat/Foundry fork sketch:

```solidity
// Setup: mainnet fork, Pool pool, DepositToken[] dts = all registered deposit tokens
// victim has an open position with debt (so unlockedBalanceOf(dust) == 0 for pushed tokens)

// 1. Attacker fills victim's list
for (uint i; i < dts.length && !reached30(victim); ++i) {
    IERC20 underlying = dts[i].underlying();
    deal(address(underlying), attacker, 1);
    underlying.approve(address(dts[i]), 1);
    dts[i].deposit(1, victim); // mints dust to victim, adds to depositTokensOfAccount
}
assertEq(pool.getDepositTokensOfAccount(victim).length + pool.getDebtTokensOfAccount(victim).length, 30);

// 2. Victim tries to deposit a new collateral -> reverts
vm.prank(victim);
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
newDepositToken.deposit(1e18, victim);

// 3. Victim tries to free a slot -> dust is locked, reverts
vm.prank(victim);
vm.expectRevert(DepositToken.NotEnoughFreeBalance.selector);
dts[0].transfer(attacker, 1);

// 4. Victim cannot mint a new synthetic -> reverts
vm.prank(victim);
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
newDebtToken.issue(1e18, victim);
```

Caveat for step 1: if the deployed pool has fewer deposit tokens than needed to reach 30, the attack still partially succeeds — it consumes all remaining free slots, blocking the victim's *next* new collateral/debt token; on pools with ≥30 total offerings it becomes permanent for indebted victims.
