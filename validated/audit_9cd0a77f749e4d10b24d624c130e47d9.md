### Title
Unprivileged account can append entries to a victim's per-account deposit-token list via `DepositToken.deposit(amount, onBehalfOf_)` / `transfer`, filling `MAX_TOKENS_PER_USER` and blocking the victim's own collateral operations - (File: contracts/DepositToken.sol)

### Summary
The GitLab bug class is "improper permission check → an unauthorized user reads/adds/edits another user's private resource." The Metronome analog is a missing ownership check on *whose* account list gets mutated: `DepositToken.deposit` mints `msdTOKEN` to an arbitrary `onBehalfOf_`, and `_transfer` credits arbitrary recipients; both paths call back into `Pool.addToDepositTokensOfAccount(account)`/`debtTokensOfAccount`, which insert the token into the victim's bounded `MappedEnumerableSet` (capped at `MAX_TOKENS_PER_USER`). Any EOA can therefore write foreign token entries into another user's private accounting set without that user's consent.

### Finding Description
- `DepositToken.deposit(uint256 amount_, address onBehalfOf_)` performs no check that `onBehalfOf_ == _msgSender()` and no opt-in from the beneficiary; it only rejects `address(0)` and the Treasury (`contracts/DepositToken.sol:211-236`). The attacker pays the underlying, the victim receives `msdTOKEN`.
- `DepositToken.transfer`/`transferFrom` call `_transfer(msgSender → to_)` with no recipient consent check (`contracts/DepositToken.sol:348-376`); `_revertIfLocked` only bounds the *sender's* free balance.
- On every mint/transfer the Pool adds the deposit token to the recipient's `depositTokensOfAccount` set (confirmed by tests asserting `addToDepositTokensOfAccount` is invoked on the recipient, `test/DepositToken.test.ts:525-550`). This set is backed by `MappedEnumerableSet` and bounded by `MAX_TOKENS_PER_USER`; once full, `add` reverts.
- `DebtToken._mint`/`_burn` symmetrically maintain `debtTokensOfAccount`, but debt minting is collateral-checked against `_msgSender`, so the reachable write primitive is the deposit side.

### Impact Explanation
Once the victim's `depositTokensOfAccount` list is full of attacker-chosen dust entries, any operation that tries to add a *new* deposit-token type to the victim's set reverts: the victim cannot deposit a new collateral type, and no one can transfer a new `msdTOKEN` type to them. If the victim holds an unhealthy/near-threshold debt position, they are blocked from topping up the only collateral types that could restore health, leading to liquidation they could otherwise have avoided — i.e., temporary freezing of the user's deposit capability and forced loss via liquidation. Each of the victim's existing entries still works, so the freeze is on adding new collateral, matching the "add to another user's private resource" behavior in the reference bug.

### Likelihood Explanation
- Fully unprivileged: attacker needs only EOAs and dust amounts of each listed collateral underlying; cost scales with the number of `DepositToken`s in the pool and `MAX_TOKENS_PER_USER` headroom.
- No privileged role, oracle manipulation, governance change, or malicious bridge component required — `deposit` is `whenNotPaused`/`nonReentrant` only, and `transfer` has no recipient-side authorization.
- Mitigating factor: the attack cannot freeze already-held balances or withdraws (`_revertIfLocked`/withdraw only check the victim's own unlocked balance), and it does not directly steal funds — impact is griefing that can cascade into liquidation when the victim needs new collateral.

### Recommendation
Either (a) require `onBehalfOf_` to have opted in (e.g., an `allowedDepositor`/permit check) or restrict `deposit`'s beneficiary to `_msgSender()`, and (b) make `Pool.addToDepositTokensOfAccount` non-reverting for recipients (or move the cap enforcement to the sender side / lazily evict zero-balance entries), so third-party dust cannot permanently occupy a victim's bounded account list.

### Proof of Concept
```solidity
// Foundry fork sketch against deployed Pool/DepositTokens
function test_fillVictimDepositTokenList() public {
    address victim = ...;                     // user with open debt position
    IDepositToken[] memory dts = pool.getDepositTokens(); // all listed collateral types

    for (uint i; i < dts.length; ++i) {
        IERC20 underlying = dts[i].underlying();
        deal(address(underlying), attacker, 1); // 1 wei dust
        vm.startPrank(attacker);
        underlying.approve(address(dts[i]), 1);
        dts[i].deposit(1, victim);            // mints msdTOKEN to victim,
        //  -> pool.addToDepositTokensOfAccount(victim)
        vm.stopPrank();
    }
    assertEq(pool.depositTokensOfAccount(victim).length, MAX_TOKENS_PER_USER);

    // Victim tries to deposit a collateral type not already in its list
    vm.startPrank(victim);
    newUnderlying.approve(address(newDepositToken), amount);
    vm.expectRevert();                        // MappedEnumerableSet full
    newDepositToken.deposit(amount, victim);  // blocked -> cannot restore health
    vm.stopPrank();
}
```
Invariant broken: identity/authorization — state belonging to `victim` (its per-account token set) is mutated by an unrelated caller, and the bounded-set DoS can freeze the victim's ability to add collateral (temporary freezing of funds, potentially forcing a liquidation loss).
