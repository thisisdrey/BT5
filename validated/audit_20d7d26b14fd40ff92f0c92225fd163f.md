### Title
Unprivileged account-list stuffing via dust `DepositToken` transfers blocks victims from adding new collateral/debt tokens — ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool` enforces `MAX_TOKENS_PER_USER = 30` across `debtTokensOfAccount + depositTokensOfAccount`. Any EOA can dust-transfer every whitelisted `DepositToken` to a victim, filling their per-account list. Once full, every subsequent `addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` reverts with `UserReachedMaxTokens`, which propagates up and reverts deposits, mints/issues, and even inbound transfers of new token types for that victim — an attacker-controlled exhaustion of a per-account resource, the same bug class as CVE-2016-7551 (unauthenticated resource exhaustion → DoS).

### Finding Description
- `Pool.sol:79` sets `MAX_TOKENS_PER_USER = 30` and `Pool.sol:143-148` `onlyIfAdditionWillNotReachMaxTokens` reverts when `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30`. [1](#0-0) 
- `DepositToken` is a public ERC20; `DepositToken.sol:498-526` `_transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance was zero — so an attacker-controlled `transfer(victim, 1)` inserts that token into the victim's list without consent. [2](#0-1) 
- `Pool.sol:216-220` `addToDepositTokensOfAccount` applies the max-tokens modifier, so once the attacker pushes 30 distinct deposit/debt tokens into the victim's lists, any further addition reverts and the whole caller transaction reverts (mint, deposit, issue, transfer). [3](#0-2) 
- Debt tokens are not permissionlessly transferable, but `DebtToken` entries can also be added to an arbitrary account via `issue`/`mint` flows directed at the account where the code allows `onBehalfOf`-style minting; at minimum the deposit-token vector alone fills all 30 slots.

### Impact Explanation
DoS / forced-liquidation griefing:
- The victim cannot deposit any new collateral type (mint path reverts at `pool.addToDepositTokensOfAccount`), cannot issue debt in a synthetic whose `DebtToken` is new to them, and cannot even *receive* transfers of deposit tokens they don't already hold.
- Critical scenario: a victim whose position is drifting toward liquidation tries to deposit a different collateral token to restore health; the attacker front-runs with dust transfers filling the 30 slots, the deposit reverts, and the position is liquidated — converting the DoS into loss of the victim's collateral via liquidation fees.
- Attack cost is only gas + dust amounts of each whitelisted deposit token (which the attacker can acquire by depositing and keeping the msdTOKENs, or buying on-market). No privileged role needed.

### Likelihood Explanation
- Fully permissionless: `transfer` on each `DepositToken` is a public entry point reachable by any EOA, and SynthContext/pause/reentrancy checks do not restrict transfers to arbitrary recipients.
- Reverts only stop the attacker, not the victim: nothing requires the recipient's consent, and there is no opt-out.
- Mitigations that don't fully close it: the victim can burn/transfer-out dust tokens to free slots, but the attacker can repeat cheaply and front-run, so the DoS is repeatable within the same block window around sensitive operations (deposits to avoid liquidation).

### Recommendation
- Do not count deposit tokens the account never explicitly deposited toward `MAX_TOKENS_PER_USER`, or raise/decouple the cap for received-vs-deposited tokens.
- Alternatively skip `addToDepositTokensOfAccount` on plain `transfer` (track list membership only on mint/deposit) and iterate balances differently, or allow the list to exceed the cap for inbound transfers while still capping deposits.
- Add a `sweep`/opt-out path letting an account remove tokens without needing a full withdrawal flow.

### Proof of Concept
Foundry fork (mainnet) sketch:

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.0;
import "forge-std/Test.sol";

interface IPool {
    function getDepositTokensOfAccount(address) external view returns (address[] memory);
    function getDebtTokensOfAccount(address) external view returns (address[] memory);
    function depositTokens() external view returns (address[] memory); // or enumerate via registry
}
interface IDepositToken { function transfer(address to, uint256 amt) external returns (bool); function deposit(uint256 amt, address to) external; }

contract StuffingTest is Test {
    IPool pool = IPool(POOL_ADDRESS); // deployed Pool on mainnet
    function test_stuffing_blocks_victim() public {
        address attacker = address(0xA11CE);
        address victim   = address(0xB0B);
        address[] memory dts = /* all whitelisted DepositToken addresses */;

        // Attacker holds 1 wei of each deposit token (deposit dust then transfer to victim)
        for (uint i; i < 30 && i < dts.length; ++i) {
            vm.prank(attacker);
            IDepositToken(dts[i]).transfer(victim, 1);
        }
        assertEq(pool.getDepositTokensOfAccount(victim).length +
                 pool.getDebtTokensOfAccount(victim).length, 30);

        // Victim tries to deposit into a collateral they don't hold yet -> reverts
        vm.expectRevert(); // UserReachedMaxTokens
        vm.prank(victim);
        IDepositToken(dts[dts.length - 1]).deposit(1e18, victim); // or pool.deposit path

        // Victim can't even receive a transfer of a new deposit token
        vm.expectRevert();
        vm.prank(attacker);
        IDepositToken(dts[dts.length - 1]).transfer(victim, 1);
    }
}
```

Confirmed reachable on deployed Pools (mainnet/base/optimism/hemi/swell all carry `MAX_TOKENS_PER_USER` and the same `addTo*TokensOfAccount` logic per `deployments/*/Pool.json`), and the behavior is exercised in `test/Pool.test.ts:1386-1416` which asserts `UserReachedMaxTokens` once the shared 30-slot limit is hit.
