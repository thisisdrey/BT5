## Analysis

**Bug class mapped:** Bzlmod lockfile / module extension **facts** trust — analogous to `BazelLockFileFunction` and `SingleExtensionEvalFunction` handling of `MODULE.bazel.lock`'s `facts` field for **non-reproducible** module extensions.

### The Carousel analogy

The original bug is a "stale recorded value trusted without recomputing against current authoritative state": `mintRollovers` uses `queue[index].assets` (captured at enqueue time) to mint new shares instead of recomputing `entitledShares` from the current (post-win) share value — an attacker-influenced/stale quantity is blindly reused for a security-relevant computation.

### The Bazel analog

Bazel's module-extension `facts` mechanism is explicitly designed to persist unauthenticated, network-derived data (e.g., "a mapping from version numbers of some SDK to an object containing the download URL and checksum of that version") precisely for extensions where "you don't have a checksum available to guard the download." [1](#0-0) 

For **non-reproducible** extensions, the test suite documents (and the shipped behavior enforces) that when the workspace `MODULE.bazel.lock`'s `facts` entries change "without any of its inputs changing (e.g. a branch switch or pull brings in a re-pin performed on another machine), the cached result must be reused with the new facts as is": Bazel does **not** re-run the extension or otherwise revalidate the facts content — it just accepts the new facts and reuses the previously generated repo specs. [2](#0-1) 

This is confirmed by `testExternallyUpdatedFactsKeptByUpdateModeForNonReproducibleExtension`, which shows adding an arbitrary new fact entry to the lockfile and then observing that `--lockfile_mode=update` silently accepts it without printing "lockfile_ext is being evaluated" (i.e., no re-run/re-validation occurs), and the injected fact is simply persisted forward. [3](#0-2) 

By contrast, this "accept-as-is" path is explicitly *not* mirrored by an integrity check on the fact contents themselves — only `usagesDigest`/`bzlTransitiveDigest` (i.e., extension code/inputs) trigger re-evaluation; the `facts` payload is unconstrained JSON that the extension author is trusted to have populated correctly the first time. [4](#0-3) 

### Attack path

If an untrusted branch that CI builds from (attacker-controlled content the victim's build consumes, matching the allowed threat model) contains a `MODULE.bazel.lock` whose `facts` map for a non-reproducible extension has been edited to point a package name/version to an attacker-chosen `{"hash": ..., "url": ...}` pair, a build with `--lockfile_mode=update` (the **default** mode) will:
1. Not detect any input change (usages/bzlTransitiveDigest unchanged),
2. Accept the injected facts "as is" per the documented/tested behavior,
3. Feed that attacker-controlled hash/URL straight into the extension's own `repository_rule` calls (e.g., an `http_archive`-style fetch), where the "checksum" being verified is the very value the attacker just supplied — so the checksum check is a no-op self-consistency check, not a real integrity gate.

This mirrors the Carousel flaw precisely: a value recorded at one point in time (facts committed to the lockfile) is trusted and reused for a security decision (what to fetch/build) at a later point, without recomputing/re-validating it against any independent authoritative source — exactly the "stale recorded quantity used instead of recomputed entitled value" bug class.

### Title
Non-reproducible module extension `facts` in `MODULE.bazel.lock` are trusted without revalidation, enabling checksum/URL substitution via an untrusted branch — (`src/test/py/bazel/bzlmod/bazel_lockfile_test.py`, lockfile facts handling)

### Finding Description
Bazel's `extension_metadata(facts=...)` mechanism exists specifically for module extensions that fetch unauthenticated network data (no checksum available) and want to memoize it. [5](#0-4)  For non-reproducible extensions, the lockfile logic reuses new/edited `facts` values found in `MODULE.bazel.lock` "as is," without re-running the extension, as long as the extension's own inputs (usages, tags, transitive `.bzl` digest) are unchanged. [2](#0-1)  This means the content of `facts` — which routinely encodes "the hashes of artifacts in an immutable repository" used to drive subsequent downloads — is not independently verified against the extension's actual upstream data source; the lockfile entry itself becomes the trusted "checksum," and it is directly editable by anyone who can push to a branch the victim's CI checks out.

### Impact Explanation
An attacker who can publish content on a branch/PR that a victim's CI builds (per the allowed threat model: no machine access needed, just committed file content) can rewrite `facts` entries in `MODULE.bazel.lock` to point package identifiers at attacker-chosen hashes/URLs. Since the non-reproducible-extension code path accepts these facts without re-fetching or independently validating them, the build will fetch and materialize attacker-chosen content into the workspace as if it were a legitimately pinned, checksum-verified artifact.

### Likelihood Explanation
Requires: (1) a module extension in the dependency graph that is non-reproducible and uses `facts` to cache hash/URL metadata (a pattern the docs explicitly recommend, e.g., for SDK-version-to-checksum maps), and (2) the victim building from a branch/PR containing an attacker-modified `MODULE.bazel.lock` under the default `--lockfile_mode=update`. This is a realistic supply-chain scenario for any project vendoring such an extension (the tests reference `rules_go` as a real-world example of a facts-using extension). [6](#0-5) 

### Recommendation
For non-reproducible extensions, do not silently accept externally-modified `facts` content when usages/inputs are unchanged. At minimum, require `--lockfile_mode=error` behavior (fail closed) whenever `facts` differ from the hidden/local lockfile's own record for a non-reproducible extension, or require that any `facts` field intended to carry integrity-sensitive data (hashes/URLs) be independently reverified (e.g., via a Bazel-checked signature or freshness proof) rather than trusted purely because it round-trips through `MODULE.bazel.lock`.

### Proof of Concept
The existing regression test `testExternallyUpdatedFactsKeptByUpdateModeForNonReproducibleExtension` already demonstrates the acceptance mechanism: it adds a new facts entry directly to the checked-out `MODULE.bazel.lock` (simulating a branch switch/pull) and shows `--lockfile_mode=update` reuses the cached repo generation without re-evaluating the extension or flagging the change. [2](#0-1)  Converting this into an integrity-bypass PoC only requires modifying an existing hash/URL-bearing fact value (rather than adding a new key) and observing that the subsequently fetched/built repository content reflects the attacker-controlled value with no re-fetch or verification against the actual upstream source.

  def testExternallyUpdatedFactsKeptByUpdateModeForNonReproducibleExtension(
      self,
  ):
    """UPDATE mode keeps updated facts of a non-reproducible extension.

    The hidden lockfile records the facts produced by the most recent local
    evaluation of the extension. If the workspace lockfile's facts for a
    non-reproducible extension change without any of its inputs changing (e.g.
    a branch switch or pull brings in a re-pin performed on another machine),
    the cached result must be reused with the new facts as is: a cold machine
    would not rerun the extension either and a rerun could require network
    access or credentials that are only available to the person updating the
    pins.
    """
    extension_id = self._setUpExtensionWithFacts(reproducible=False)
    self._addFactToLockfile(extension_id, '1.27.0', {'hash': 'hola'})

    _, _, stderr = self.RunBazel(
        ['build', '@hello//:all', '--lockfile_mode=update']
    )
    self.assertNotIn('lockfile_ext is being evaluated', '\n'.join(stderr))

    with open(self.Path('MODULE.bazel.lock'), 'r') as f:
      lockfile = json.loads(f.read().strip())
    self.assertEqual(
        lockfile['facts'][extension_id],
        {
            '1.25.0': {'hash': 'olleh'},
            '1.26.1': {'hash': 'hello'},
            '1.27.0': {'hash': 'hola'},
        },
    )
