### Title
Attachment instance silently discarded when BNS `hash` buffer length is nonzero but not exactly 20 bytes - ([File: stackslib/src/net/atlas/mod.rs])

### Summary
`AttachmentInstance::try_new_from_value` treats an empty `hash` buffer as a legacy zero-hash (`Hash160::empty()`), but for any non-empty buffer whose length is not exactly 20 bytes, `Hash160::from_bytes` fails and the whole function returns `None`, silently dropping the attachment instance. Because the corresponding Clarity argument type is typically `(buff 20)` (a *maximum*-length buffer type, not a fixed length), an unprivileged sender can submit a BNS contract-call with a short (e.g. 1–19 byte) non-empty hash buffer that is perfectly valid Clarity input, gets mined, but results in the node never creating/tracking the `AttachmentInstance` for that confirmed transaction.

### Finding Description
In `try_new_from_value`, the code path is: [1](#0-0) 

- If `content_hash.data.is_empty()` → uses `Hash160::empty()` (special-cased for legacy zero-hash calls).
- Otherwise it calls `Hash160::from_bytes(&content_hash.data[..])`, which requires the slice to be exactly 20 bytes; any other length returns `None`, and the enclosing function immediately `return None`s, discarding the entire `AttachmentInstance` — including the `attachment-index`, `metadata`, `contract_id`, `tx_id`, and block context that were already validated and well-formed.

Because Clarity's `buff N` type is a *maximum length* constraint (buffers can be any length from 0 to N), an attacker calling the BNS boot contract's name-update-style function with a hash argument typed `(buff 20)` can legally supply a buffer of, say, 5 or 19 bytes. This transaction is accepted by the VM (no type violation), gets mined into a block, and the contract emits a `print` event with this attachment tuple. When the node's event/attachment-processing pipeline (invoked from `stackslib/src/chainstate/coordinator/mod.rs`, which calls `try_new_from_value`) parses this event, the function returns `None` and the attachment tracking for that confirmed transaction is lost — it's never added to Atlas's queue of unresolved/needed attachments, and the corresponding zonefile hash commitment is never checked/served.

### Impact Explanation
This causes a confirmed, canonical on-chain BNS operation's attachment commitment to be treated by the node as if it never existed, so BNS name resolution for that name silently fails to fetch/verify the associated zonefile — a BNS attachment/mismatch condition matching the "High" severity category (serving state that doesn't match what the chain actually committed). The effect is deterministic and repeatable: any transaction with a non-empty, non-20-byte hash buffer to the BNS contract in the `AtlasConfig.contracts` allow-list will trigger this for every node processing that block.

### Likelihood Explanation
No privileged role is required — any unprivileged account can submit a contract-call transaction to the boot BNS contract with a crafted hash argument shorter than 20 bytes (but nonzero length), as long as the underlying contract function's hash parameter type permits a shorter buffer (i.e., typed `(buff 20)` rather than requiring exact length). The transaction only needs to be minable at normal cost; no attacker-side infrastructure beyond a standard signed transaction is needed, and the bug reproduces on every node that processes that block.

### Recommendation
In `try_new_from_value`, do not use `Hash160::from_bytes` (fixed-length) directly on attacker/contract-controlled buffer data. Instead, pad or reject explicitly: distinguish "legacy empty buffer → zero hash" from "buffer present but wrong length → reject the transaction's attachment tuple with a specific error/log" rather than a bare `None`, or better, verify at the Clarity contract level (or at parse time) that only buffers of exactly 20 bytes (or exactly 0) are semantically valid, and add explicit handling/logging so an operator can detect this rather than data being silently lost.
