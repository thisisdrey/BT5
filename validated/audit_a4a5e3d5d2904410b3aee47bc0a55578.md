### Title
Signature-verification bypass for messages batch-received before a same-burst Handshake updates the connection's public key - (File: stackslib/src/net/connection.rs, stackslib/src/net/chat.rs)

### Summary
`ConnectionInbox::consume_messages` parses and enqueues *all* messages present in a single `recv_bytes()` buffer before `ConversationP2P::chat()` ever runs. Each message's signature is checked at parse time in `consume_payload_known_length` only `if let Some(ref pubk) = self.public_key`; when the peer is not yet authenticated (`public_key == None`), that check is skipped entirely, so a second, differently/arbitrarily-signed message riding in the same TCP burst as an initial `Handshake` is queued with **no signature check at all**. `chat()` later dequeues the `Handshake` first, calls `handle_handshake` → `update_from_handshake_data` → `self.connection.set_public_key(Some(pubk))`, and then dequeues the second (never-verified) message under `self.connection.has_public_key() == true`, routing it to `handle_authenticated_control_message`, whose comment explicitly (and incorrectly, in this ordering) assumes "the message signature will have been verified by the underlying ConnectionP2P."

### Finding Description
Broken equality: the code assumes "public key used to verify payload bytes for message N" == "public key ConversationP2P::chat() believes is authoritative when message N is dequeued." This holds only if verification and dequeuing are synchronous per-message. They are not:
- `Connection::recv_data` → `ConnectionInbox::recv_bytes` (stackslib/src/net/connection.rs:1078-1143) reads up to 64KB and calls `consume_messages` (connection.rs:953-1073) in a loop that parses *every* complete message in the buffer and pushes it to `self.inbox` before returning.
- `consume_payload_known_length` (connection.rs:799-860) performs the only P2P-level signature check: `if let Some(ref pubk) = self.public_key { protocol.verify_payload_bytes(pubk, preamble, buf_bytes)?; }` (connection.rs:813-815). If `self.public_key` is `None` (a fresh, unauthenticated peer connection), this check is skipped for *every* message in that same `recv_bytes()` call, including any message following an in-batch `Handshake`.
- Only afterward does `ConversationP2P::chat()` (chat.rs:2921-3022) dequeue messages one at a time via `next_inbox_message()`. For message 1 (the Handshake), since `self.connection.has_public_key()` is false, it goes to `handle_unauthenticated_control_message` → `handle_handshake` (chat.rs:1214-1296) → `update_from_handshake_data` (chat.rs:1131-1167), which ends with `self.connection.set_public_key(Some(pubk.clone()))` (chat.rs:1164).
- For message 2 (already sitting in the inbox, unverified), `self.connection.has_public_key()` is now `true`, so `chat()` routes it to `handle_authenticated_control_message` (chat.rs:2530-2600), which explicitly relies on the stale invariant at chat.rs:2946-2948 ("we already have this remote peer's public key, so the message signature will have been verified by the underlying ConnectionP2P") — but it was never verified against any key, since it was parsed while `self.public_key` was `None`.

Attacker's exact message: connect as a brand-new, unauthenticated peer; send in one write() (or a burst that lands in one `recv_bytes()` read) a valid `Handshake` claiming public key K, immediately followed by a second preamble+payload for any message type reachable through `handle_authenticated_control_message` (e.g., `Ping`, `NatPunchRequest`) with an arbitrary/garbage/mismatched signature (or even `MessageSignature::empty()`). Because `self.public_key` is `None` at the moment both messages are parsed in the same `consume_messages` pass, `verify_payload_bytes` is never invoked for either message at the connection layer (the Handshake's own signature is separately checked inside `validate_handshake`/`handle_handshake`, but the second message's preamble signature is not checked by anyone before being dispatched as "authenticated").

Existing guards checked and found insufficient for this path:
- `validate_inbound_message` (chat.rs:2493-2526) only checks preamble network/version/height sanity (`is_preamble_valid`), not signatures.
- `MAX_MESSAGE_LEN`/inbox size caps limit volume but do not affect ordering-dependent verification.
- The `has_public_key()` branch in `chat()` (chat.rs:2946) is the sole gate that is supposed to guarantee "already verified," and it is falsified by this scenario.

### Impact Explanation
The directly reachable "authenticated" message types in `handle_authenticated_control_message` (Ping, NatPunchRequest/Reply, HandshakeAccept/StackerDBHandshakeAccept) are individually low-value (mostly protocol housekeeping), so on their own this does not obviously escalate to a state write. However, the root cause is a genuine authentication-gate bypass: `chat()`'s liveness/statistics accounting (`update_stats`, `msgs_rx` counters, `add_healthpoint`) and any future or already-present code path that trusts `self.connection.has_public_key()` as a proxy for "this specific message was signature-verified" is unsound. Messages that fall through to `handle_data_message` (Blocks/Microblocks/Transactions/StackerDBChunk/StackerDBPushChunk/NakamotoBlocks pushes, chat.rs:2288-2386) go through their own independent `validate_*_push` relayer-count/rate checks rather than a peer-identity signature check at this layer, so the most severe write-paths are not directly gated by `has_public_key()` in this code — I could not confirm within the available context that any StackerDB chunk or block write is reachable purely through this specific ordering bug without also passing chunk-level or block-level cryptographic validation elsewhere. Given the rules require concrete write/relay/crash impact and I was not able to trace a full end-to-end path from this parse-time gap to an unauthenticated *write* to StackerDB or block state (those paths appear to have their own independent chunk/block signature checks downstream), I can only confirm the authentication-bookkeeping bypass itself with confidence, not a stronger Critical/High impact.

### Likelihood Explanation
Preconditions: the attacker only needs to be a fresh, unauthenticated remote peer (`self.public_key == None`), which is the default state for any new inbound P2P connection — no privileged role, secret, or existing peer relationship is required. The attacker must get two P2P messages to land in the same `recv_bytes()` read (same TCP segment/burst), which is fully attacker-controlled by writing both messages in one `write()`/`send()` call before the server's next `read()`. This is trivially repeatable per connection/reconnect.

### Recommendation
Do not use the connection's *current* `has_public_key()` state as a proxy for "this particular message was verified." Instead:
1. Record, per queued inbox message, whether it was verified at parse time (e.g., store an `authenticated: bool` alongside each `P::Message` in the inbox, set at the moment `consume_payload_known_length` runs based on `self.public_key.is_some()` at that instant).
2. In `ConversationP2P::chat()`, dispatch to `handle_authenticated_control_message` only when that per-message flag is true, not based on the connection's public key state at dequeue time.
3. Alternatively, re-verify each dequeued message's signature against the connection's public key at dequeue time (in `chat()`), rather than trusting the parse-time check, closing the ordering gap entirely.

### Proof of Concept
Rust test in `stackslib::net::chat` (alongside existing tests like `convo_handshake_accept` at chat.rs ~4415 and `convo_send_recv` helper at chat.rs:3155):
1. Set up two `ConversationP2P` instances (`convo_1`, `convo_2`) with fresh `local_peer` keys and no public keys known (mirroring setup in `convo_ping_unsolicited`-style tests around chat.rs:5111).
2. Build a valid `Handshake` message from `local_peer_1` signed correctly (as in `sign_message`), and a second `Ping` message signed with a *different*, unrelated private key (or `MessageSignature::empty()`).
3. Serialize both messages back-to-back into a single byte buffer and feed them to `convo_2.connection.recv_data()` in one call (simulating a single-burst TCP read), instead of using two separate `send_signed_request`/`convo_send_recv` round trips.
4. Call `convo_2.chat(...)` once.
5. Assert that `convo_2` produced a `Pong` reply for the Ping (i.e., it was routed through `handle_authenticated_control_message`) despite its preamble signature never matching any key that `convo_2.connection.public_key` held at parse time — demonstrating that `consume_payload_known_length`'s signature check was skipped (because `self.public_key` was `None` when both messages were parsed) yet the second message was still treated as authenticated once the Handshake set the key.
6. Contrast with a control run where the same two messages are sent as separate `recv_bytes()` calls (as `convo_send_recv` normally does, one flush per message) and show the Ping message with a bad/mismatched signature is instead rejected/NACKed — proving the vulnerability is strictly ordering/batching-dependent.
