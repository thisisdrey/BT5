## Title
Per-account HOP submit rate limiter is enforced *after* the expensive authorization/signature work, letting an authorized (unprivileged, non-admin) account flood `hop_submit` and stall a collator's block production - (File: `substrate/client/hop/src/rpc.rs`)

### Summary
`sc-hop`'s `hop_submit` RPC path advertises a per-account token-bucket rate limiter (`RateLimiter::check`) as the DoS defense described in its own module docs. [1](#0-0)  In practice, however, the limiter is only invoked deep inside `HopDataPool::insert`, i.e. *after* the RPC handler has already performed all of the costly work for the request: a runtime-API call for `max_promotion_size`, a second runtime-API call (a state-trie read) for `can_account_promote`, and a full cryptographic signature verification. [2](#0-1)  Any account that satisfies `can_account_promote` (an ordinary, unprivileged runtime-defined authorization, not an admin/governance check) can therefore submit requests far above the configured `submit_rate_per_min`/`submit_burst`/bandwidth limits, and each rejected-by-rate-limit request still costs the node a full authorization check plus a signature verification. This defeats the purpose of the rate limiter and reproduces exactly the HAL-04 pattern ("too many requests… node does not have enough compute resources to handle them") inside this repository's own JSON-RPC surface.

### Finding Description
The `submit` handler in `HopRpcServer` performs, in order:
1. SCALE-decode of `recipients`, `signer`, `signature` (cheap).
2. `runtime_api::max_promotion_size` — a runtime API call. [3](#0-2) 
3. `runtime_api::can_account_promote` — a second runtime API call requiring a state read, explicitly done "before verifying the signature" per the code comment, specifically to avoid one class of DoS (unauthorized flood forcing signature verification). [4](#0-3) 
4. `multi_sig.verify(...)` — CPU-bound signature verification (ed25519/sr25519/ecdsa). [5](#0-4) 
5. Only then is `self.pool.insert(...)` called, which internally calls `self.rate_limiter.check(&sender_id, accounted)` as essentially the *last* gate before storage bookkeeping. [6](#0-5) 

The rate limiter (`RateLimiter::check`) is a straightforward per-`SenderId` token bucket for requests and bandwidth. [7](#0-6)  Its whole purpose, per the module's own docs, is to bound how often one account can hit this expensive path. [8](#0-7)  But because it is checked only inside `insert`, an account that is authorized under `can_account_promote` (this is a normal per-account permission the runtime can grant to any ordinary account — it is not an admin/governance action, and the client-side code treats it as attacker-controllable input) can call `hop_submit` at an arbitrary rate (e.g. the report's demonstrated 300 req/min), forcing:
- one runtime-API dispatch for `max_promotion_size`,
- one runtime-API dispatch (state read) for `can_account_promote`,
- one cryptographic signature verification,

for *every single call*, regardless of the configured `submit_rate_per_min`/`submit_burst` values, before the token bucket ever gets a chance to reject the call. The comment at line 191-193 shows the authors were aware of and mitigated *one* ordering hazard (unauthorized accounts forcing signature verification) but left the symmetric, more relevant hazard unaddressed: an authorized account forcing unlimited authorization-checks-plus-signature-verifications, since the actual admission-control primitive (the token bucket) sits after all of that work rather than before it.

This is a public dispatch/queue-adjacent DoS vector reachable purely through a JSON-RPC method exposed by any HOP-enabled node (collator), with no admin, governance, relayer, or validator privilege required — only possession of one ordinary account that the runtime is willing to authorize (a policy that, per the docs, could be "any other policy" the runtime chooses, e.g. reusing an existing on-chain authorization that many ordinary users hold). [9](#0-8) 

### Impact Explanation
`sc-hop` runs inside Substrate collator/node processes and its maintenance/promotion machinery competes for the same node resources used for block production. [10](#0-9)  By repeatedly invoking `hop_submit` at a rate the rate limiter is supposed to prevent, an attacker forces the node to perform unbounded state-trie reads (`can_account_promote`) and CPU-bound signature verifications on the JSON-RPC thread pool (`#[method(name = "hop_submit", blocking)]`), degrading the collator's ability to service other RPC/consensus-adjacent work and potentially stalling block production or on-chain promotion of legitimate HOP data — squarely the "public underpriced work that degrades block production" impact category. This does not require a malicious peer, validator, or leaked key; it only requires one ordinary account the runtime deems eligible for promotion.

### Likelihood Explanation
High. The attacker needs only:
- one keypair the runtime's `can_account_promote` policy authorizes (by design this can be "any other policy," including broadly-granted authorizations), and
- the ability to construct a syntactically valid submission (data/recipients/signature format), which requires no special resources.

No race condition, timing window, or infrastructure compromise is needed — the ordering bug is deterministic and triggers on every call.

### Recommendation
Move the rate-limiter check to the very first admission-control step in `HopRpcServer::submit`, before the `max_promotion_size` and `can_account_promote` runtime API calls and before signature verification, keyed by the (cheaply obtainable) claimed sender identity. If the sender identity cannot be cheaply established pre-authorization, consider a lightweight, pre-authorization IP/connection-level throttle in addition to the per-account bucket, and reject over-budget requests before performing any runtime API call or cryptographic verification. Ensure `RateLimiter::check` failure paths are reachable without incurring the cost of steps 2-4.

### Proof of Concept
1. Configure a node with HOP enabled and a runtime whose `can_account_promote` authorizes account `A` (a normal, non-privileged account under the runtime's stated policy).
2. Using account `A`'s keypair, send `hop_submit` requests via JSON-RPC at a rate well above `--hop-submit-rate-per-min`/`--hop-submit-burst` (e.g. 300 req/min as in the HAL-04 PoC), each with a distinct 1-byte payload (to dodge `DuplicateEntry`) and a valid signature.
3. Observe that every request still incurs a `HopRuntimeApi_max_promotion_size` call, a `HopRuntimeApi_can_account_promote` state read, and a full `MultiSignature::verify`, per the code path in `HopRpcServer::submit` (`substrate/client/hop/src/rpc.rs:150-220`), before `RateLimiter::check` (`substrate/client/hop/src/pool.rs:374-376`) ever runs — i.e., the configured token-bucket limits only the *stored* entries, not the actual CPU/state-read cost imposed on the node per request. Measure the node's RPC-thread CPU/latency degradation under this sustained rate exceeding the intended `submit_rate_per_min`.

```rust
	pub fn insert(
		&self,
		data: Vec<u8>,
		recipients: RecipientVec,
		sender_id: SenderId,
		signer: MultiSigner,
		signature: MultiSignature,
		submit_timestamp: u64,
	) -> Result<HopHash, HopError> {
		if recipients.is_empty() {
			return Err(HopError::NoRecipients);
		}
		let unique: BTreeSet<&MultiSigner> = recipients.iter().map(|r| &r.signer).collect();
		if unique.len() != recipients.len() {
			return Err(HopError::DuplicateRecipient);
		}

		if data.is_empty() {
			return Err(HopError::EmptyData);
		}

		let data_len = data.len() as u64;

		// Total accounted size includes bounded per-recipient metadata overhead so
		// a submitter cannot inflate memory via large recipient lists while the
		// capacity counter only tracks `data.len()`. Charge the rate limiter the
		// same accounted size, otherwise a 1-byte payload with 256 recipients
		// would cost ~10 KiB of pool capacity while only spending 1 byte of
		// bandwidth tokens — making the bandwidth dimension non-functional for
		// fan-out-heavy entries.
		let accounted = entry_accounted_size(data_len, recipients.len());

		// Rejected requests never reserve capacity — check before any atomic bump.
		if let Err(retry_after_secs) = self.rate_limiter.check(&sender_id, accounted) {
			return Err(HopError::RateLimited { retry_after_secs });
		}
```

```rust
	/// Check whether this account may submit `data_len` bytes right now.
	///
	/// Returns `Ok(())` on admission (tokens consumed) or `Err(retry_after_secs)`
	/// when either bucket is empty.
	pub fn check(&self, sender_id: &SenderId, data_len: u64) -> Result<(), u64> {
		if !self.cfg.enabled {
			return Ok(());
		}

		let now = Instant::now();
		let state = self.get_or_create(sender_id, now);
		let mut state = state.lock();
		state.last_touch = now;

		let req_wait = state.requests.try_consume(1.0, now).err();
		if let Some(wait) = req_wait {
			return Err(wait.as_secs().max(1));
		}

		// If the bandwidth bucket is exhausted, reject immediately and refund the request
		// token so both buckets stay consistent.
		if let Err(wait) = state.bandwidth.try_consume(data_len as f64, now) {
			// Refund the request token we just took so the two buckets stay consistent.
			state.requests.tokens = (state.requests.tokens + 1.0).min(state.requests.capacity);
			return Err(wait.as_secs().max(1));
		}

		Ok(())
	}
```

```markdown
# `sc-hop` — Hand-Off Protocol

Node-level ephemeral data pool for Substrate collators. HOP gives a collator a
disk-backed pool where an authorized sender can upload a blob and hand it off
to one or more recipients who claim it directly from the same collator over
JSON-RPC. Unclaimed blobs are promoted to on-chain storage as a best-effort
fallback before they expire, or simply cleaned up.

HOP keeps short-lived hand-off data off-chain until it actually needs
permanence — data lives on one collator's disk instead of being replicated
across the chain, and round-trip latency stays well under a block time. The
node is agnostic about what "authorized to submit" and "promote on-chain"
mean; both are delegated to the runtime via the `sp_hop::HopRuntimeApi`.
```
