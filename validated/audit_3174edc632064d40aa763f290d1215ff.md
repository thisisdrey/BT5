### Title
Exchange (Bancor-curve) rate manipulation via floating-point precision drift in `ExchangeProcessor` lets a well-capitalized trader extract value from `ExchangeTransactionContract` counterparties - (File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java)

### Summary
`ExchangeTransactionActuator`, reachable by any unprivileged account via a single `ExchangeTransactionContract` transaction, computes the swap output for TRON's built-in Bancor-style TRX/TRC10 `Exchange` using `ExchangeProcessor`, which relies entirely on `double` floating-point arithmetic (`Math.pow`) to derive the relay "supply" and the resulting `buyTokenQuant`. This is directly analogous to the reported `KangarooVault` finding: an actor with sufficiently large capital can perform large, repeated trades against the pool's floating-point curve, accumulate rounding/precision drift in the implied exchange rate (`firstTokenBalance`/`secondTokenBalance`), and profit at the expense of the pool/other traders or the exchange creator on withdrawal. The exact fix pattern (`SafeExchangeProcessor` using `BigDecimal`, gated by `allowHardenExchangeCalculation`) already exists in the codebase as an opt-in path, confirming the floating-point path is recognized as imprecise, but it is not the unconditional default for `ExchangeTransactionActuator`'s core trade path.

### Finding Description
`ExchangeCapsule.transaction()` selects between `ExchangeProcessor` (double math) and `SafeExchangeProcessor` (BigDecimal) based on the `hardenedCalc` flag [1](#0-0) , which in turn comes from `allowHarden()` on `AbstractExchangeActuator`, itself gated by the dynamic property `allowHardenExchangeCalculation` [2](#0-1) .

When the hardened path is not engaged, every trade routed through `ExchangeTransactionActuator.execute()` calls `exchangeCapsule.transaction(...)`, which uses `ExchangeProcessor.exchange()` [3](#0-2) . That processor computes an intermediate "relay supply" and the buy amount purely with IEEE-754 `double` and `Math.pow`, casting the result down to `long`: [4](#0-3) 

Each trade mutates `firstTokenBalance`/`secondTokenBalance` (the pool's exchange-rate state) based on this floating-point result [5](#0-4) . Because `double`/`Math.pow` do not guarantee exact rational results (unlike the `BigDecimal`-based `SafeExchangeProcessor` added later, which is explicitly a "hardened" alternative) [6](#0-5) , repeated large trades by a capital-heavy trader can accumulate rounding bias in the pool ratio over many transactions/blocks, shifting the effective exchange rate away from the "true" invariant in a direction favorable to the trader executing many such transactions — the same class of "exchange rate manipulable given big enough positions over a long enough time" described in the external report for `KangarooVault`'s `markPrice`.

The `ExchangeInjectActuator`/`ExchangeWithdrawActuator` (creator-only operations) independently compute `anotherTokenQuant` at `validate()`-time with exact `BigInteger` math [7](#0-6) , but at `execute()`-time redo the calculation with plain `long` division (`floorDiv`) [8](#0-7) , meaning the pool state driving `firstTokenBalance`/`secondTokenBalance` is itself subject to additional non-BigInteger truncation on top of the trading path's floating-point drift.

### Impact Explanation
An attacker with enough TRX/TRC10 balance and enough transactions (bandwidth/energy is cheap for TRC10-token trades) can drive the implied bancor exchange rate of an `Exchange` pool away from its fair value, extracting value from counterparties trading against the same pool, or from the exchange creator's holdings when they later inject/withdraw at a distorted rate. This is a leak-of-value / griefing vector against pool participants — assets are not "directly" stolen via a single call, but a hypothetical, capital-gated, valid attack path leaks value, matching the C4 "Medium" bar used in the original finding (assets not directly at risk, but a hypothetical attack with external capital/time requirements leaks value).

### Likelihood Explanation
Low-to-medium likelihood in practice: it requires very large capital (comparable to the pool's `getExchangeBalanceLimit()`, currently defaulting to `1_000_000_000_000_000L`) [9](#0-8)  and many repeated transactions to accumulate meaningful floating-point drift, similar to the "1 billion tokens, weeks of setup" caveat in the original report. It is also mitigated whenever `allowHardenExchangeCalculation` is enabled network-wide, since that routes trades through the exact `SafeExchangeProcessor` instead.

### Recommendation
Make the `BigDecimal`-based `SafeExchangeProcessor` computation the unconditional path for `ExchangeTransactionActuator` (and remove/retire the floating-point `ExchangeProcessor`), rather than gating exactness behind an opt-in dynamic property; additionally make `ExchangeInjectActuator`/`ExchangeWithdrawActuator` `execute()` reuse the same `BigInteger`/`BigDecimal` computation already used in their `validate()` methods instead of recomputing with plain `long` arithmetic.

### Proof of Concept
No runnable PoC was executed against this repository; the above is derived from static analysis of `ExchangeProcessor`, `SafeExchangeProcessor`, `ExchangeCapsule.transaction`, and the actuators, all cited above, showing that the default (non-hardened) trade path uses `double`/`Math.pow` for a value that becomes persistent pool state (`firstTokenBalance`/`secondTokenBalance`) read by every subsequent trade. Reproducing the drift concretely (as the original report did with a Forge test) would require a java-tron test harness driving many `ExchangeTransactionContract` calls with large `Quant` values and observing `ExchangeCapsule.getFirstTokenBalance()/getSecondTokenBalance()` divergence from the exact BigInteger-computed invariant — this was not run here.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }
