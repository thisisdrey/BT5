## Title
Null pointer dereference / DoS via `MarketOrderStore.get()` swallowing missing-order lookups instead of throwing `ItemNotFoundException` - ([File: chainbase/src/main/java/org/tron/core/store/MarketOrderStore.java])

## Summary
This is a structural analog of CVE-2021-40944: in GPAC, `gf_filter_pid_get_packet` can return `NULL` and a caller dereferences it without a check, crashing the process. In java-tron, `MarketOrderStore.get(byte[] key)` is declared to throw `ItemNotFoundException` when an order id does not exist, and callers (validate/execute paths reachable from an unprivileged `MarketCancelOrderContract` broadcaster) rely on that contract to reject non-existent orders. However, the implementation never actually throws when the underlying key is absent — it wraps whatever `revokingDB.get(key)` returns (including `null`) directly into a new `MarketOrderCapsule` and returns it: [1](#0-0) 

## Finding Description
`MarketCancelOrderActuator.validate()` looks up the order and expects a thrown `ItemNotFoundException` to signal "order does not exist": [2](#0-1) 

Because `MarketOrderStore.get()` never throws in this situation and instead constructs a `MarketOrderCapsule` from a `null`/empty backing value, the very next line `marketOrderCapsule.isActive()` dereferences a capsule whose underlying protobuf state is not a valid parsed order. Depending on how `MarketOrderCapsule`'s byte-array constructor handles `null`/empty input, this either produces a capsule with a `null` internal message (leading to `NullPointerException` on any getter such as `isActive()`, `getOwnerAddress()`, `getSellTokenId()`) or a default-instance object that silently bypasses the "order not exists" validation entirely, allowing execution to proceed against non-existent order state. The `execute()` path exhibits the same pattern with no defensive check at all: [3](#0-2) 

This is the same root-cause class as the GPAC bug: a getter/accessor contract implies a null/"not found" signal (there, a `NULL` packet pointer; here, an `ItemNotFoundException`), but the actual implementation fails to produce that signal, and the immediate caller dereferences the result without an explicit null/emptiness check.

## Impact Explanation
If dereferencing an order-less `MarketOrderCapsule` throws an unchecked `NullPointerException` inside `validate()`, this exception is not one of the checked exceptions (`ItemNotFoundException`, `InvalidProtocolBufferException`, `BalanceInsufficientException`) that `execute()`/`validate()` declare or the surrounding actuator dispatch explicitly catches at the same granularity as `ContractValidateException`. Depending on how far up the call chain the NPE propagates before being caught, this can manifest as: (a) rejection of only the single broadcast transaction (low impact, if caught generically higher up), or (b) if this code path is reachable during block application/re-execution of a transaction packed into a block (e.g., a malicious cancel-order transaction included in a block), an uncaught RuntimeException during `Manager` block processing could crash or halt transaction processing on nodes replaying that block — a node availability impact consistent with the CVE's DoS class. I was not able to fully confirm from the available index whether the top-level transaction/actuator dispatch loop in `Manager`/`TransactionCapsule` (I could not locate or read its source in this session) wraps arbitrary `RuntimeException` from `validate()` safely, so the severity between "single request fails" and "node crash on block application" is uncertain and would need verification against `Manager.processTransaction`/`TransactionCapsule` executor code.

## Likelihood Explanation
Any unprivileged account holder can broadcast a `MarketCancelOrderContract` with a bogus/non-existent `orderId` — no market order needs to have been created first. This is trivially reachable through the standard HTTP/gRPC `BroadcastTransaction` path with no special privileges, making the trigger condition cheap and repeatable.

## Recommendation
Fix `MarketOrderStore.get()` to check for a `null`/empty value from `revokingDB.get(key)` and explicitly throw `ItemNotFoundException` in that case, matching its declared contract, instead of unconditionally constructing a capsule around a potentially null/empty byte array. Additionally, harden `MarketCancelOrderActuator.validate()`/`execute()` to verify the returned capsule represents an actual persisted order (e.g., check for a non-empty order id) before calling accessor methods like `isActive()` or `getOwnerAddress()`.

## Proof of Concept
1. As any funded account, broadcast a `MarketCancelOrderContract` transaction with `orderId` set to a value that does not correspond to any order ever stored in `MarketOrderStore` (e.g., 32 random bytes).
2. `MarketCancelOrderActuator.validate()` calls `orderStore.get(orderId)` [4](#0-3) ; because `MarketOrderStore.get()` [1](#0-0)  does not throw `ItemNotFoundException` for a missing key, the code proceeds to `marketOrderCapsule.isActive()`.
3. Observe whether this throws an uncaught `NullPointerException` (crash/exception path) or silently returns a bogus default object that lets an attacker manipulate cancel-order state for an order they don't own. I was unable to directly execute this PoC in this session (no runtime/test execution available); the exact runtime behavior (NPE vs. silent default-instance bypass) depends on `MarketOrderCapsule`'s byte-array constructor, whose full source I could not confirm from the index in the time available — this should be validated by running the described transaction against a local java-tron node before treating this as confirmed-exploitable.
