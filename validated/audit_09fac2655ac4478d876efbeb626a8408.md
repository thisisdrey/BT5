### Title
Unauthenticated `RecvError` packets allow remote attackers to force-close arbitrary Nebula tunnels — insufficient entry check in `handleRecvError` (File: `outside.go`)

### Summary
`handleRecvError` is reachable by any UDP sender without a handshake, cert verification, decryption, or replay/nonce check — it is dispatched directly from `readOutsidePackets` before any hostinfo/cert lookup, purely based on packet `Type == header.RecvError` [1](#0-0) . Its only "entry check" against spoofing is a comparison of the current known remote UDP address to the sender address, and that check is skipped entirely if the hostinfo's remote address is not currently valid.

### Finding Description
`readOutsidePackets` parses the header and, for `header.RecvError`, calls `f.handleRecvError` directly — with no cert, no decryption, no nonce/replay validation: [2](#0-1) 

`handleRecvError` then:
1. Checks a simple rate-limiting predicate `ShouldRecvError` (not an authentication check).
2. Looks up the hostinfo purely by the attacker-supplied `h.RemoteIndex` field (which is a plaintext, unencrypted header field visible on every wire packet, including in the clear on all message traffic).
3. Its only anti-spoofing guard is: [3](#0-2) 

If `hr.IsValid()` is false (e.g., roaming state, address not yet fixed, or certain relay/handshake edge cases), the guard is bypassed entirely and the tunnel is torn down unconditionally. Even when `hr.IsValid()` is true, the check only compares the claimed UDP source address to the known remote — and UDP allows arbitrary source-address spoofing with no return-routability proof, so an attacker who has observed (via passive sniffing or a MITM position) the plaintext `RemoteIndex` value in any header from either peer can trivially craft a spoofed `RecvError` packet appearing to originate from the genuine remote address.

Once accepted, `f.closeTunnel(hostinfo)` and `f.handshakeManager.DeleteHostInfo(hostinfo)` unconditionally tear down the tunnel state: [4](#0-3) 

This exactly matches the reported bug class — "no entry check" (or a trivial one) on a function that can be driven with attacker-controlled input values to disturb internal administration/state, here manifesting as forced session/tunnel teardown rather than a rate-limited or cryptographically-verified action.

### Impact Explanation
An attacker who can observe or guess a peer's `RemoteIndex` (transmitted unencrypted in every packet header) can send spoofed, unauthenticated `RecvError` packets to force Nebula nodes to tear down established, authenticated tunnels — a remote state-poisoning / denial-of-service primitive requiring no CA-signed certificate, no successful handshake, and no valid cryptographic material. This can be repeated to persistently disrupt connectivity between arbitrary Nebula peers whose traffic (or index values) the attacker can observe.

### Likelihood Explanation
Likelihood is moderate-to-high in scenarios where an attacker can observe traffic between two nodes (on-path attacker, compromised router, shared network segment) since the `RemoteIndex` is sent in the clear in every header. UDP source-address spoofing is trivial on many networks (especially if egress filtering / BCP38 is not enforced), and the rate limiter (`ShouldRecvError`) is a throttle, not an authentication mechanism.

### Recommendation
- Require some proof of tunnel knowledge stronger than the visible index + best-effort source-address match — e.g., require the `RecvError` to be authenticated (e.g., signed/MAC'd with a key derived from the existing tunnel state) rather than accepted as plaintext.
- Do not skip the anti-spoof check when `hr.IsValid()` is false; treat an unknown/invalid remote as "cannot verify" and drop rather than proceed.
- Consider requiring corroboration (e.g., a matching outstanding sent packet, or requiring repeated recv-errors from the same true source before acting) before tearing down a tunnel.
- Add an explicit comment documenting that this path is deliberately reachable pre-authentication and why, per the reporter's own remediation pattern in the referenced report ("add a comment to notify others the function is meant to be called by everyone" — but here it should instead be hardened, since the impact is a real state-poisoning DoS, unlike the trivial cases in the original report).

### Proof of Concept
1. Passively observe (or otherwise learn) the `RemoteIndex` used in one direction of an established tunnel between node A and node B by capturing any single unencrypted Nebula header (headers are not encrypted; only the payload is).
2. Craft a UDP packet with:
   - Source address spoofed to node B's known/current UDP endpoint (or, in cases where `hostinfo.GetRemote()` is not yet valid, no spoofing is even required).
   - A Nebula header with `Type = header.RecvError`, `RemoteIndex` set to the observed index.
3. Send this packet to node A.
4. `readOutsidePackets` dispatches directly to `handleRecvError` (outside.go:81-84) without any cert/decrypt/replay check.
5. If `ShouldRecvError` throttling permits, and either `hr` is not yet valid or the spoofed source matches, `closeTunnel` and `DeleteHostInfo` are invoked, tearing down node A's tunnel to node B.

Note: I could not fully verify the exact conditions under which `hostinfo.GetRemote()` returns an invalid (`!IsValid()`) `AddrPort` for an established tunnel (e.g., during specific roaming/relay states), nor fully inspect `ShouldRecvError`'s rate-limiting window (`acceptRecvErrorConfig`/`sendRecvErrorConfig` in `interface.go`) within the available search budget; those affect exact exploit conditions/timing but do not change the core finding that the authentication check itself is conditionally bypassable and, when applied, relies solely on a spoofable UDP source address.
