### Title
`validate_received_chunk` uses strict `<` instead of `<=` when buffering FutureView-NACKed chunks, allowing a same-version (stale/equivocating) signed chunk to be buffered for later replay - (File: stackslib/src/net/stackerdb/mod.rs)

### Summary
`PeerNetwork::handle_unsolicited_StackerDBPushChunk` buffers a pushed `StackerDBChunkData` for later retry whenever the peer replies with `Nack(FutureView)` and `validate_received_chunk` returns `true`. `validate_received_chunk` only rejects a chunk when `data.slot_version < *expected_version` (line 700), so a chunk whose `slot_version` is exactly equal to the version already committed in local storage is treated as acceptable and buffered with `Ok((true, false))`.

### Finding Description
In `validate_received_chunk` (stackslib/src/net/stackerdb/mod.rs:649-718), after the signature check (`slot_metadata.verify(&addr)?`, lines 690-697), the version-freshness gate is:

```
if data.slot_version < *expected_version {
    ...
    return Ok(false);
}
``` [1](#0-0) 

This only rejects strictly-older versions. In the `Nack(FutureView)` branch of `handle_unsolicited_StackerDBPushChunk` (lines 816-847), `expected_versions` is populated directly from `self.stackerdbs.get_slot_versions(&chunk_data.contract_id)` — i.e., the version currently committed in local storage — and if `validate_received_chunk` returns true, the function returns `Ok((true, false))`, meaning "buffer this message for retry later": [2](#0-1) 

Because the comparison is strict `<` rather than `<=`, a signed chunk with `slot_version` equal to the already-committed version passes validation and gets buffered, even though it carries no new information and is not "the current or newer version" per the code's own comment ("must be the current or newer version") which is intended to express a monotonic advance, not merely non-regression.

### Impact Explanation
The immediate effect demonstrated in the code is that `handle_unsolicited_StackerDBPushChunk` returns `(true, false)` instead of `(false, false)` for an equal-version replayed chunk. I was not able to fully trace the downstream buffered-message replay path (`process_stacker_db_chunks` in `relay.rs`) and the actual SQLite write path in `stackslib/src/net/stackerdb/db.rs` within the available tool budget, so I cannot confirm with certainty whether the final storage write re-enforces a strict monotonicity check (which would neutralize this at the persistence layer) or whether it trusts the earlier buffering decision. Given this incompleteness, the concrete, provable effect is limited to the buffering decision itself (an incorrect `(true, false)` vs. the expected `(false, false)`), and I cannot confirm actual state corruption or network-wide propagation of stale data without inspecting the storage write path.

### Likelihood Explanation
Any remote peer that can open a P2P connection and push a `StackerDBPushChunk` message can trigger this path; the only precondition is that the pushed chunk's `rc_consensus_hash` causes the responder to answer `Nack(FutureView)` (i.e., the local node believes it might be behind), and that the chunk is validly signed for the target slot by a legitimate slot signer (attacker must already hold/replay a validly-signed chunk for that slot — they cannot forge arbitrary content without the slot owner's key). This bounds the attack to replaying/holding a previously-valid signed chunk at the currently-committed version, not forging new arbitrary content.

### Recommendation
Change the buffering-branch validation (and any place using the same "must be current or newer" semantics for buffering-before-store) to reject equal versions as well, i.e. use `data.slot_version <= *expected_version` when the intent is "strictly newer than what's committed," or explicitly document/verify why equality is intentionally allowed. Additionally, confirm and, if necessary, enforce that the final storage write path in `stackslib/src/net/stackerdb/db.rs` independently re-validates `slot_version` strictly greater than the currently stored version at commit time, so that a buffering-stage laxity cannot alone lead to a stale write.

2. Construct a `StackerDBPushChunkData` with `chunk_data.slot_version = 5` and a valid signature over the slot metadata by the slot's owner key, with a `rc_consensus_hash` that causes `make_StackerDBChunksInv_or_Nack` to return `Nack(FutureView)`.
3. Call `handle_unsolicited_StackerDBPushChunk` and assert the result is `(true, false)`, i.e. the chunk is buffered — confirming that a same-version chunk which should be treated as non-newer (`OWNERSHIP` invariant: buffered version must be strictly greater than the already-committed version) is buffered instead of rejected.
4. (Further work, not completed here due to budget) trace whether this buffered entry, once the buffered-message replay path (`relay.rs`/`process_stacker_db_chunks`) fires and the local node's view catches up, is committed to storage via `stackslib/src/net/stackerdb/db.rs`'s insert/replace logic, and whether that logic independently re-checks strict version monotonicity before writing.
