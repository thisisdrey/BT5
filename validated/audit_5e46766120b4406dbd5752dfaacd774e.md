### Title
Users who become liquidatable during a shutdown can be liquidated by frontrunning bots the moment `open()` re-enables repayments, with no grace period — (File: contracts/Pool.sol)

### Summary
In Metronome, `DebtToken.repay`/`repayAll` and `Pool.liquidate` are all gated by the same `whenNotShutdown` modifier (`everythingStopped` on the Pool and/or PoolRegistry). Shutdown freezes both repaying and liquidating simultaneously. When governance calls `Pauseable.open()`, both features re-enable in the same block, and `Pool.liquidate` contains no timer, cooldown, or grace period. A liquidation bot can therefore frontrun a user's `repay`/`repayAll` transaction in the first block after reopening and seize collateral from a position that only became unhealthy while the user was frozen out of any remediation path — the exact bug class of Blueberry issue 290 / M-9, which Metronome does not mitigate.

### Finding Description
- `Pool.liquidate` is `whenNotShutdown` only (contracts/Pool.sol:541-596); it checks health, `maxLiquidable`, and `debtFloorInUsd`, but has no time-based guard tied to reopening.
- `DebtToken.repay` (contracts/DebtToken.sol:418-457) and `repayAll` (contracts/DebtToken.sol:466-495) are also `whenNotShutdown`.
- `Pauseable.shutdown()` sets `_everythingStopped = true` and `open()` flips it back with no timestamp recorded and no grace window (contracts/utils/Pauseable.sol:97-117).
- `docs/emergency-flags.md` confirms `liquidate`, `repay`, `repayAll`, `withdraw`, `swap` are all disabled by `everythingStopped`, and `pool.pause()` does **not** protect users either: `liquidate` still works while paused (test/Pool.test.ts:353-365 shows `PositionLiquidated` emitted while paused). A paused pool blocks `DepositToken.deposit` (docs line 81), so a user cannot even add collateral to deleverage while `liquidate` remains fully active.
- Every exit route is simultaneously cut during shutdown: `repay`, `repayAll`, `swap`, `withdraw`, and `SmartFarmingManager.flashRepay` (which internally calls `DebtToken.repay`) all revert.

Attack trace (unprivileged):
1. Pool (or PoolRegistry) enters shutdown while user has open debt.
2. Collateral price drops during shutdown; the position becomes unhealthy. The user cannot repay, swap, flashRepay, or withdraw.
3. Governor calls `open()`. A liquidation bot holding the msAsset sees the `Open` event / mempool `open()` tx and calls `pool.liquidate(syntheticToken_, victim, amountToRepay, depositToken_)` in the same block, frontrunning the victim's `repay`/`repayAll`.
4. `syntheticToken_.burn(liquidator, amountToRepay_)`, `_debtToken.burn(victim, ...)`, and `depositToken_.seize(victim, liquidator, ...)` execute; the victim loses collateral including the liquidator incentive and protocol fee, despite being willing and able to repay.

Nothing stops this: `whenNotShutdown` passes after `open()`, `nonReentrant` and `SynthContext` checks are irrelevant, `maxLiquidable`/`debtFloorInUsd` only bound size, and the `CanNotLiquidateOwnPosition` check doesn't apply to third-party bots.

### Impact Explanation
Direct loss of user funds: users who became liquidatable while every remediation path was frozen lose collateral (seized amount plus liquidation incentive) to MEV liquidators without a fair chance to repay. This matches the "unfair liquidation / direct theft of user funds" impact class, identical to the referenced Blueberry finding.

### Likelihood Explanation
Requires an emergency shutdown of a Pool/PoolRegistry — a real, supported operational state (`shutdown()` is callable by governor or guardian). During any shutdown, collateral prices can move; after `open()`, liquidations are permissionless and bots race repays in the mempool. Liquidations are always more profitable than letting a user repay, so frontrunning is economically guaranteed where an unhealthy position exists. Medium likelihood (conditional on a shutdown occurring), high impact when it does.

### Recommendation
Record a `lastReopenedTimestamp` in `open()`/`unpause()` (or in `PoolRegistry`/`Pool`) and have `Pool.liquidate` revert until `block.timestamp >= lastReopenedTimestamp + LIQUIDATION_GRACE_PERIOD` (e.g., 4 hours), so users have a fair window to `repay`, `repayAll`, or `swap` after the shutdown is lifted. Alternatively, allow a `repay`-only "soft-open" phase where `whenNotShutdown` passes for `DebtToken.repay`/`repayAll` but not for `Pool.liquidate`.

### Proof of Concept
Foundry/Hardhat sketch against the repo's test scaffolding (same structure as test/Pool.test.ts:285-404):

```ts
// given: alice has an unhealthy position
await masterOracle.updatePrice(met.address, toUSD('0.95'));
expect((await pool.debtPositionOf(alice.address))._isHealthy).false;

// simulate shutdown window: repay and liquidate both revert
await pool.shutdown();
await expect(
  msEthDebtToken.connect(alice).repay(alice.address, debt)
).revertedWithCustomError(msEthDebtToken, 'IsShutdown');
await expect(
  pool.connect(liquidator).liquidate(msEth.address, alice.address, debt, msdMET.address)
).revertedWithCustomError(pool, 'IsShutdown');

// pool reopens; bot liquidates in the SAME block before alice's repays lands
await pool.open();
// alice's repay tx is broadcast but frontrun:
await pool.connect(liquidator).liquidate(msEth.address, alice.address, debt, msdMET.address); // succeeds

// alice's collateral was seized; her pending repay now reverts (debt already burned / no balance)
await expect(
  msEthDebtToken.connect(alice).repay(alice.address, debt)
).revertedWithCustomError(msEthDebtToken, 'BurnAmountExceedsBalance');
```

Deterministically demonstrates there is no grace window: `liquidate` succeeds in the first post-`open()` transaction, before the victim's `repay` can land.
