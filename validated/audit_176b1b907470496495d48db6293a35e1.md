### Title
Unvalidated `AccountType` field in `AccountCreateContract` allows spoofing an EOA as a smart-contract account, bypassing contract-only safety checks - (File: `actuator/src/main/java/org/tron/core/actuator/CreateAccountActuator.java`)

### Summary
`CreateAccountActuator` builds the on-chain `Account` directly from the attacker-supplied `AccountCreateContract.type` field without any validation, and the required type check is explicitly commented out. This lets any transaction broadcaster create an account whose stored `AccountType` is `Contract` (or `AssetIssue`) even though no bytecode/`ContractStore` entry ever exists for it — the same class of bug as CVE-2019-20844, where changing an object's declared "type" after/at creation lets it bypass type-based access checks (there, a DM channel; here, an account's `AccountType`).

### Finding Description
`CreateAccountActuator.validate()` never checks `contract.getType()`: [1](#0-0) 

```
//    if (contract.getType() == null) {
//      throw new ContractValidateException("Type is null");
//    }

    if (accountStore.has(accountAddress)) {
      throw new ContractValidateException("Account has existed");
    }
```

`execute()` then persists an `AccountCapsule` built straight from the untrusted contract, copying `type`/`typeValue` verbatim: [2](#0-1) 

An unprivileged wallet holder can therefore submit a normal `AccountCreateContract` transaction with `type = Contract` for a brand-new address they control the private key for. The resulting `AccountStore` entry has `AccountType.Contract` but there is **no** entry in `ContractStore`/`CodeStore` — it behaves exactly like a normal EOA (it can sign transactions, since normal permission logic in `AccountCapsule`/`TransactionCapsule.validateSignature` is keyed off owner/active permissions, not `AccountType`), yet several actuators use `AccountType == Contract` as a security boundary assuming such accounts cannot hold private keys or act as senders:

- `FreezeBalanceActuator` / `FreezeBalanceProcessor.validate` refuse to delegate resources to `Contract`-typed accounts: [3](#0-2) 
- `DelegateResourceActuator.validate` refuses to delegate to `Contract`-typed accounts: [4](#0-3) 
- `TransferActuator.validate` blocks TRX transfers to `Contract`-typed accounts once `ForbidTransferToContract`/`AllowTvmCompatibleEvm` is enabled, and treats `Contract`-typed recipients as necessarily having a `ContractStore` entry: [5](#0-4) 

Because `type` is fully attacker-controlled at account-creation time and never re-derived from actual contract deployment, all of these checks can be defeated or subverted: an attacker can either (a) mark their own controlled EOA as `Normal`/`AssetIssue` to receive delegated resources meant only for non-contract addresses under conditions the delegator did not expect, or (b) mark it as `Contract` to be excluded from transfer restrictions meant to protect real smart contracts, and — notably — line 147-155 of `TransferActuator` assumes any `Contract`-typed account has a `ContractStore` entry ("this can not happen"), which is now a false assumption reachable from user input.

### Impact Explanation
This is a type-confusion/authorization-bypass bug reachable by any unprivileged transaction broadcaster via a single signed `AccountCreateContract` transaction (the cheapest, most basic operation in java-tron). It undermines security invariants that multiple actuators (`FreezeBalanceActuator`, `DelegateResourceActuator`, `TransferActuator`, and their VM-native counterparts) rely on to distinguish EOAs from smart contracts, enabling unauthorized bypass of contract-transfer/delegate restrictions and violating an invariant ("this can not happen") that other code paths depend on for correctness. This matches the "unauthorized account operation" / logic-bypass class explicitly listed as in-scope.

### Likelihood Explanation
High likelihood: creating an account with an arbitrary `AccountType` requires nothing more than broadcasting a standard `AccountCreateContract` transaction with the `type` field set — a capability already available to any funded account, no special privilege needed, and the validation gap is unconditional (the check is literally commented out in source).

### Recommendation
In `CreateAccountActuator.validate()`, restrict `contract.getType()` to `Normal` only for user-initiated account creation (or otherwise validate it against the caller's actual privileges), and ensure the `Contract` `AccountType` can only ever be set by internal chain logic (e.g., `CreateSmartContract`/`TriggerSmartContract` deployment paths in `Program.createContractImpl`), never via `AccountCreateContract`. Additionally, hardening consumers of `AccountType.Contract` (e.g., `TransferActuator`) to check for the presence of a `ContractStore` entry rather than trusting the `AccountType` field alone would remove the "can not happen" assumption.

### Proof of Concept
1. Attacker controls address `A` (EOA, has a private key).
2. Attacker broadcasts an `AccountCreateContract` transaction: `owner_address = <funded account>`, `account_address = A`, `type = AccountType.Contract`.
3. `CreateAccountActuator.validate()` passes (no type check), `execute()` stores `AccountCapsule` for `A` with `getType() == Contract`, but no `ContractStore`/`CodeStore` entries exist for `A`.
4. Attacker signs and sends a `TransferContract` from `A` (fully functional since `A` has a real private key and default owner/active permissions) — this now bypasses `ForbidTransferToContract` restrictions applied to real recipient contracts (`toAccount.getType() == AccountType.Contract` check in `TransferActuator.validate`) even though `A` is not a real contract, or conversely triggers the `"Account type is Contract, but it is not exist in contract store"` invariant failure path in the `AllowTvmCompatibleEvm` branch if such transfer is attempted to `A`.

Note: I was not able to fully trace every downstream consumer of `AccountType` (e.g., all TVM opcode/precompile paths, exchange/market order actuators) within the available indexed code to enumerate every exploitable divergence; a full audit of all `getType() == AccountType.Contract`/`Normal`/`AssetIssue` comparisons across the actuator and VM packages would be needed to bound the complete impact.
