### Title
Stale `PromiseYieldReceipt`/`PromiseYieldStatus` survive `DeleteAccountAction` and are re-executed against a re-created account of the same name via the global `PromiseYieldTimeout` queue - ([File: runtime/runtime/src/lib.rs], [File: core/store/src/utils/mod.rs])

### Summary
`remove_account` (used by `action_delete_account`) only removes `TrieKey::Account`, `ContractCode`, `AccessKey`/`GasKeyNonce`, and `ContractData` entries; it never touches `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, `TrieKey::YieldIdToDataId`/`DataIdToYieldId`. If a contract calls `promise_yield_create` and then self-deletes before the yield resolves, the parked `PromiseYieldReceipt` (containing the originally scheduled self-targeted actions) and its `PromiseYieldStatus` remain in the trie under the account name. The global, index-keyed `PromiseYieldTimeout` queue is unaware of account deletion and, once its `expires_at` is reached, unconditionally checks `contains_key(PromiseYieldReceipt{receiver_id, data_id})` and — finding it still present — synthesizes a `PromiseResume` receipt that is delivered to and executed against whoever now owns that account name.

### Finding Description
- `remove_account` (`core/store/src/utils/mod.rs:504-575`) removes account/code/keys/contract-data but never calls `remove_promise_yield_receipt`, `remove_promise_yield_status`, or cleans `YieldIdToDataId`/`DataIdToYieldId` mappings. `action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) calls only `remove_account`, so these promise-yield records are out-of-scope of account deletion by construction. [1](#0-0) [2](#0-1) 

- `resolve_promise_yield_timeouts` (`runtime/runtime/src/lib.rs:3009-3116`) walks the global `PromiseYieldTimeout` queue strictly by `expires_at`, and for each expired entry gates firing on `state_update.contains_key(&promise_yield_key)` where `promise_yield_key = TrieKey::PromiseYieldReceipt{receiver_id: queue_entry.account_id, data_id}` — it never checks whether the account itself still exists or is the same account that created the yield. [3](#0-2) 

- When that synthesized `PromiseResume{data: None}` is processed by `process_receipt` (`runtime/runtime/src/lib.rs:1500-1521`), it looks up `get_promise_yield_status`/`get_promise_yield_receipt` keyed only by `(receiver_id, data_id)` — again with no account-identity/liveness check — finds the stale `PromiseYieldReceipt`, and executes its embedded actions via `apply_action_receipt` against whatever account now exists under that name. [4](#0-3) 

- Because `create_promise_yield_receipt`/`create_promise_yield_receipt_with_id` (`runtime/runtime/src/ext.rs:353-400`) always set `receiver_id = self.context.current_account_id` (the creating account itself), the parked receipt is inherently a *self-targeted* delayed receipt. If additional actions were appended to that promise (via generic `promise_batch_action_*` host calls on the same promise index) before deletion — e.g. `AddKey`, `Transfer`, `DeployContract`, `DeleteAccount` — those self-targeted, owner-level actions execute later against a brand-new, unrelated account owner who registers the same account name after the original was deleted, entirely without the new owner's consent, at a time chosen by the original (attacker) account via the timeout length parameter. [5](#0-4) 

No existing check (nonce, signature, access-key, or account-liveness) intervenes: the timeout queue entry is purely index-driven and global-per-shard, and the paired `PromiseYieldReceipt`/`PromiseYieldStatus` records are account-name-keyed but are never cleaned up on `DeleteAccountAction`.

### Impact Explanation
This is an authorization-escalation / integrity bug: a party that never created or authorized the yield can have privileged, owner-level self-actions (embedded in the stale receipt) forcibly executed against their freshly created account, at a time controlled by the attacker (via a long `yield_timeout_length_in_blocks`-driven expiry, itself upper-bounded by protocol config but can still span a large number of blocks). Depending on which actions were appended to the yield's promise before self-deletion (e.g. `AddFullAccessKey`), this could grant the original attacker persistent unauthorized access to, or otherwise corrupt state of, an account they no longer own. This matches the "authorization escalation across accounts or promises" bounty category.

### Likelihood Explanation
Preconditions are attacker-controlled and cheap: fund an account, call `promise_yield_create`/`promise_yield_create_with_id`, optionally append further actions to the same promise, then self-delete via `DeleteAccountAction`. The attack additionally requires that a third party re-register the exact same account name before the timeout fires — a probabilistic/social dependency the attacker does not fully control, which limits (but does not eliminate) practical exploitability, since NEAR account names can be freely re-created once deleted and are sometimes deliberately reused (e.g., released "vanity" names). The core defect (stale `PromiseYieldReceipt`/`PromiseYieldStatus`/`YieldIdToDataId` surviving `remove_account`) is fully reachable and repeatable through ordinary, unprivileged transactions.

### Recommendation
In `action_delete_account`/`remove_account`, before or during account deletion, enumerate and remove all `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, and `DataIdToYieldId` trie entries scoped to `account_id` (mirroring how `AccessKey`/`ContractData` prefixes are iterated and removed). Alternatively/additionally, have `resolve_promise_yield_timeouts` and the `PromiseResume` handling path verify the receiver account still exists (or matches an account-creation-generation marker) before executing the stale embedded receipt, discarding/burning the entry instead of applying it to a re-created account.

### Proof of Concept
Integration test plan (test-loop / runtime test harness, following the pattern of `test-loop-tests/src/tests/yield_timeouts.rs`):
1. Deploy the test contract on `victim.near`; call a method that invokes `promise_yield_create` with a long timeout (or the default `yield_timeout_length_in_blocks`), and append an `AddFullAccessKey` (attacker-controlled pubkey) action to the returned promise index. Confirm `PromiseYieldReceipt`/`PromiseYieldStatus` are present in state under `victim.near`.
2. Submit a `DeleteAccountAction` for `victim.near` (beneficiary arbitrary) and let it execute; assert the `Account` record is gone but `PromiseYieldReceipt`/`PromiseYieldStatus` entries for `victim.near`/`data_id` are still present in state (proving `remove_account` does not clean them).
3. Re-create `victim.near` via `CreateAccountAction` with a brand-new key pair (simulating an unrelated new owner) before the timeout block height.
4. Advance blocks past `yield_timeout_height()`; assert a `PromiseResume{data: None}` receipt is generated and delivered to `victim.near` (as in `test_simple_yield_timeout`).
5. Advance one more block and assert the embedded `AddFullAccessKey` action executed against the *new* `victim.near` account — i.e., the attacker's original pubkey now has a full access key on the new account, which the new owner never authorized. Assert this constitutes unauthorized privilege grant, and that `assert_no_promise_yield_status_in_state` only becomes true after this unintended execution.
