### Title
Multisig threshold bypass via duplicate-signature weight double-counting in `ValidateMultiSign` TVM precompile - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` precompiled contract (TVM opcode-exposed, callable by any smart contract via `CALL`/`STATICCALL`) is meant to let contracts verify that a threshold of distinct account-permission key holders authorized an action, mirroring the on-chain multisig weight check used for signing transactions. Unlike the reference implementation in `TransactionCapsule.checkWeight`, the precompile's duplicate-signer detection is keyed on the raw signature bytes instead of the signer's recovered address, so a holder of a single low-weight key can submit multiple distinct-but-valid signatures over the same hash and have their weight counted multiple times, crossing the `permission.getThreshold()` gate without actually assembling the required number of independent signers.

### Finding Description
`TransactionCapsule.checkWeight` (the canonical multisig authorization check used to validate signed transactions) explicitly de-duplicates by signer address so the same key cannot be counted twice toward a threshold: [1](#0-0) 

The `ValidateMultiSign` precompile is supposed to provide the equivalent guarantee for smart contracts (e.g. contract-based multisig wallets built on this opcode), but its de-duplication logic is different and broken: [2](#0-1) 

For each supplied signature it computes `recoveredAddr`, then builds `sign = merge(recoveredAddr, sign)` and checks:
- if `executedSignList` already contains `recoveredAddr` **and** already contains the exact `sign` bytes → `continue` (correctly skips an exact signature replay).
- if `executedSignList` contains `recoveredAddr` but **not** this exact `sign` → it only calls `MUtil.checkCPUTime()` (a CPU-time throttle guard) and then **falls through** to add the recovered address's weight to `totalWeight` again.

Because ECDSA signing is non-deterministic unless RFC6979 nonces are enforced, the same private key can produce many different valid `(r, s)` signatures over the identical `hash`. An attacker who controls exactly one key listed in the target `Permission` (with weight less than `permission.getThreshold()`) can generate several distinct valid signatures from that one key and submit them all as the `signatures` array. Each one recovers to the same address, but only the third-and-beyond check re-checks the *signature bytes*, not the *address*, so weight is added once per distinct signature rather than once per distinct signer.

### Impact Explanation
Any smart contract that uses this precompile (address corresponding to TVM opcode `VALIDATEMULTISIGN`, exposed via `Op`/`OperationRegistry`) to gate privileged actions — e.g., a multisig treasury/wallet contract requiring `M`-of-`N` distinct co-signers before releasing TRX/TRC10/TRC20 funds, changing ownership, or approving withdrawals — can have its authorization threshold satisfied by a single account holding only one of the required keys. This is a concrete unauthorized-operation / theft-of-funds primitive: an attacker with 1-of-N signing power can unlock a threshold meant to require the cooperation of multiple key holders, directly enabling unauthorized withdrawal or state changes protected by contract-level multisig logic built on this precompile.

### Likelihood Explanation
The precompile is reachable by any address that can deploy or call a smart contract (anonymous, unprivileged) — no special network role is required. Exploitation only requires possessing one legitimate key in the target `Permission`'s key list and generating additional signatures over the same hash with a different nonce, which is trivial with any standard ECDSA library that doesn't force RFC6979 deterministic `k`. The `MAX_SIZE` cap (5 signatures) is not a defense since the attacker only needs enough repeated entries to reach the threshold.

### Recommendation
Change the de-duplication key in `ValidateMultiSign.execute` from the combined `(recoveredAddr, signatureBytes)` pair to `recoveredAddr` alone: once an address has contributed weight, any further signature recovering to that same address must be skipped/ignored (matching the address-based `addMap` de-duplication already used in `TransactionCapsule.checkWeight`), regardless of whether the raw signature bytes differ.

### Proof of Concept
1. Deploy an account with an `Active` `Permission` containing keys `K1` (weight `w1 < threshold`) and `K2..Kn` (unavailable to the attacker).
2. Attacker, controlling only `K1`, computes `hash = sha256(address || permissionId || data)` as done in `ValidateMultiSign.execute` (`actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java:1062-1064`).
3. Attacker signs `hash` with `K1` multiple times using non-deterministic nonces, producing distinct signatures `sig1, sig2, ..., sigk` (all valid, all recovering to `K1`'s address).
4. Attacker calls a contract that invokes `ValidateMultiSign` with `signatures = [sig1, sig2, ..., sigk]` where `k * w1 >= threshold`.
5. In the loop, the first signature adds weight `w1`; subsequent signatures pass the `matrixContains(executedSignList, recoveredAddr)` branch but fail the exact-bytes check, so only `MUtil.checkCPUTime()` runs and weight `w1` is added again each time — `totalWeight` reaches `threshold` even though only `K1` ever participated, and the precompile returns "success" (`dataOne()`), unlocking whatever action the calling contract gates on this result.
