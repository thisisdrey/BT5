### Title
Unsafe Absolute Value Conversion in NavCalculator - (`contracts/NavCalculator.sol`)

### Summary
The `NavCalculator` contract incorrectly handles potentially negative ledger balances by clamping them to zero using `if (x < 0) x = 0;` logic before casting to `uint256`. While this prevents a direct revert, it mirrors the "total function" anti-pattern described in the external report where unintended state transitions (resulting in negative balances) are masked rather than reverted. In the context of the Tare protocol's double-entry ledger, a negative balance in accounts like `investorPrincipalWithdrawable` or `outstandingInvestorPrincipal` indicates a material corruption of the ledger or an unauthorized state transition. By returning a valid (zeroed) valuation instead of reverting, the system allows the `PortfolioVault` to proceed with share-price-sensitive operations (like `approveDeposit` or `approveRedemption`) using a corrupted NAV, potentially leading to the theft of vault assets.

### Finding Description
In `NavCalculator.getLoansValue`, the contract fetches `LoanValue` data from the `Loans` contract. The `LoanValue` struct contains `int128` fields representing ledger balances. The calculator performs the following operations:

```solidity
// contracts/NavCalculator.sol:80-82
int256 collectedCash = int256(loanData.investorPrincipalWithdrawable) +
  int256(loanData.investorInterestWithdrawable);
if (collectedCash < 0) collectedCash = 0;

// contracts/NavCalculator.sol:86-88
int256 unreturnedInvestorPrincipal = int256(loanData.outstandingInvestorPrincipal) -
  int256(loanData.investorPrincipalWithdrawable);
if (unreturnedInvestorPrincipal < 0) unreturnedInvestorPrincipal = 0;
``` [1](#0-0) [2](#0-1) 

The root cause is the same as the external report: the code assumes that these values should be non-negative and "fixes" them if they are negative. However, in a double-entry system, a negative balance is a symptom of a broken invariant (e.g., more principal repaid than owed, or interest over-allocated). By clamping to zero, the `NavCalculator` produces a "valid" `totalValue` for the `PortfolioVault`. 

The `PortfolioVault` uses this `totalValue` to finalize its `lastNav`, which is the denominator for minting shares and the numerator for redeeming assets. If an attacker can trigger a state where a loan's ledger accounts result in a negative `collectedCash` or `unreturnedInvestorPrincipal` (e.g., via a malicious `applyWaterfall` call if permissions are bypassed, or a logic error in fee charging), the NAV will be mathematically incorrect but the system will not revert.

### Impact Explanation
If the ledger state is corrupted such that a loan's value is negative, the `NavCalculator` will report it as `0`. This results in a Material corruption of vault NAV [3](#0-2) .
1. **Understated NAV**: If the "true" value should have been negative (due to a debt or over-withdrawal), clamping to `0` overstates the NAV, allowing redeemers to exit at an unfair price, draining the `MarginPool` (or `PortfolioVault` liquidity).
2. **Masked Exploits**: Unauthorized state transitions that result in negative balances will not be detected by the valuation engine, allowing an attacker to continue manipulating the vault's accounting without triggering a revert in the asynchronous `updateNav` process.

### Likelihood Explanation
The likelihood is medium-low because it requires a preceding bug in `Loans.sol` or an unauthorized `applyWaterfall` call to produce the negative balance. However, the `NavCalculator` is explicitly designed to be the "valuation strategy" that protects the vault; by failing to revert on invalid ledger states, it fails its primary security purpose.

### Recommendation
Modify `NavCalculator.sol` to revert if any intermediate calculation results in a negative value, rather than clamping to zero. This ensures that any ledger corruption halts the vault's share price machinery immediately.

```solidity
require(collectedCash >= 0, "Negative collected cash");
require(unreturnedInvestorPrincipal >= 0, "Negative unreturned principal");
```

### Proof of Concept
1. A loan is created and funded.
2. Due to a hypothetical bug or unauthorized call in `Loans.applyWaterfall`, the `ACC_INVESTOR_PRINCIPAL_REPAID` account is credited with more than the `ACC_INVESTOR_PRINCIPAL_PAYABLE` balance.
3. `Loans.getLoanValues` returns a negative `outstandingInvestorPrincipal`. [4](#0-3) 
4. `PortfolioVault.updateNav` calls `NavCalculator.getLoansValue`.
5. `NavCalculator` sees the negative value, clamps it to `0`, and returns a successful (but incorrect) aggregate `totalValue`. [5](#0-4) 
6. The Vault finalizes `lastNav` using the zeroed value.
7. Users mint/redeem against a corrupted share price.
