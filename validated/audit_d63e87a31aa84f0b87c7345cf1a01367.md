Audit Report

## Title
`pallet-bags-list::on_update` silently drops score-decrease events while the list is locked, leaving stale (inflated) voter scores uncorrected - ([File: substrate/frame/bags-list/src/lib.rs])

## Summary
`pallet-bags-list`'s `on_insert` has an explicit fallback that queues an account into `PendingRebag` for guaranteed later reconciliation when the list is locked, but `on_update` has no equivalent fallback and simply returns `Err(ListError::Locked)`. The consuming pallet `pallet-staking-async` calls `on_update` after `unbond()` and discards the error with `let _ = ...`, so a staker's stale, higher `ListNodes` score is never queued for correction and persists until the unrelated `on_idle` auto-rebag cursor eventually reaches that account.

## Finding Description
`on_insert` explicitly detects the locked state and, when auto-rebagging is enabled, stores the account in `PendingRebag` and returns `Ok(())`, guaranteeing later correction via `on_idle`: [1](#0-0) 

`on_update`, in contrast, calls `ensure_unlocked()?` and propagates `Error::Locked` directly with no `PendingRebag` enqueue and no other reconciliation mechanism: [2](#0-1) 

`PendingRebag`'s documentation frames it purely as a store for accounts that failed at insertion time, not for failed updates: [3](#0-2) 

`pallet-staking-async::unbond` invokes `on_update` after reducing the ledger's active stake, and discards any error via `let _ = ...`: [4](#0-3) 

This confirms the asymmetry described in the claim: the "increase"/insert path is durably self-healing via `PendingRebag`, but the "decrease"/update path is not, and the one real-world caller (`unbond`) silently swallows the resulting error.

## Impact Explanation
`ListNodes` scores drive the bags-list ordering that `pallet-staking-async` uses to build the sorted voter list consumed by election/voter-snapshot logic. If an `unbond()`-triggered score decrease is dropped while the list is locked (which happens during every election snapshot/voter-list generation cycle — a routine, non-privileged, protocol-driven window), the affected staker is represented with an inflated, stale score for an indeterminate number of blocks, bounded only by the unrelated `on_idle` auto-rebag cursor budget. This is a genuine, reachable defect in intended runtime behavior — a value that must be corrected downward is not corrected — falling under "runtime bugs that compromise intended behavior" for stake-weighted voter selection.

## Likelihood Explanation
No privileged actor is required: any staker can call the public `unbond()` extrinsic, and the lock condition (`pallet_bags_list::Lock`) is set automatically and routinely by the protocol during snapshot generation, not by an attacker-controlled or artificial precondition. The error-discarding pattern (`let _ = ...`) in `unbond()` is confirmed in the code, and the missing `PendingRebag` fallback in `on_update` is confirmed as well, making the described staleness window real and reproducible under normal network operation.

## Recommendation
Make `on_update` symmetric with `on_insert`: when the list is locked, insert the account into `PendingRebag` (guarded by the same `MaxAutoRebagPerBlock` check) rather than returning `Err(Locked)`, so `on_idle` guarantees eventual correction. Alternatively, have `pallet-staking-async::unbond` (and any other caller of `on_update`) explicitly handle a `Locked` error by enqueuing the affected account for reconciliation rather than discarding it.

## Proof of Concept
1. In a runtime pairing `pallet-bags-list` (as `T::VoterList`) with `pallet-staking-async`, have staker `S` bonded with a large active amount, present in `ListNodes` with a high score `X`.
2. Trigger `Lock::<T,I>::put(())` (as occurs automatically during election snapshot/voter-list generation).
3. While locked, call `Staking::unbond(S, large_amount)`. `ledger.active` decreases; since `T::VoterList::contains(&S)` is true, `on_update(&S, lower_weight)` is invoked, returns `Err(ListError::Locked)`, and the error is discarded via `let _ = ...`.
4. Unlock the list. Assert `ListNodes::<T,I>::get(&S)` still equals the old, higher score `X`, and that `S` is absent from `PendingRebag` (since only `on_insert` populates it).
5. Observe `S` remains over-weighted in the sorted voter list until the ordinary `on_idle` rebag cursor (bounded by `MaxAutoRebagPerBlock`) eventually reaches `S`'s position, or until `rebag` is manually called.

```rust
	fn on_insert(id: T::AccountId, score: T::Score) -> Result<(), ListError> {
		if Pallet::<T, I>::ensure_unlocked().is_err() {
			// Pallet is locked - store in PendingRebag for later processing
			// Only queue if auto-rebagging is enabled
			if T::MaxAutoRebagPerBlock::get() > 0u32 {
				PendingRebag::<T, I>::insert(&id, ());
				return Ok(());
			}

			return Err(ListError::Locked);
		};
		List::<T, I>::insert(id, score)
	}
```
