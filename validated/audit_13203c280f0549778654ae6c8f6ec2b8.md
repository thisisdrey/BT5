### Title
Stale Permission-State Signature Caching Allows Execution of Transactions Signed With Revoked Keys Within the Same Block - (File: `framework/src/main/java/org/tron/core/db/Manager.java`)

### Summary
`Manager#processBlock` performs a batch, parallel signature/permission check of every transaction in an incoming block against the `AccountStore` state as it exists *before* any transaction in that block has been applied, and caches the result on each `TransactionCapsule` via the `isVerified` flag. The block is then applied sequentially, transaction by transaction. Because `TransactionCapsule.validateSignature()`/`validatePubSignature()` short-circuit whenever `isVerified` is already `true`, a transaction whose active/owner permission is changed or revoked by an *earlier* transaction in the very same block is never re-checked against the updated permission set — its stale "verified" status from before the block started is trusted for the rest of block application. This mirrors the CVE-2025-58145 bug class: a validity determination is cached/reused across a boundary where the underlying authorization state (page ownership in Xen, account permission in java-tron) can legitimately change, and the missing re-check lets the stale grant be honored after the authorization state has moved on.

### Finding Description
`Manager#processBlock` calls `preValidateTransactionSign(txs)` once, up front, for the whole block: [1](#0-0) 

This dispatches each transaction to a worker pool that calls `trx.validateSignature(manager.getAccountStore(), manager.getDynamicPropertiesStore())`: [2](#0-1) 

`TransactionCapsule.validateSignature`/`validatePubSignature` fetch the owner account's `Permission` from `AccountStore` and validate the signature/weight/permission-operation-mask against it, then set `isVerified = true` and never repeat the check once that flag is set: [3](#0-2) 

After this batch pre-check (run against pre-block-execution `AccountStore` state), `processBlock` executes the block's transactions **sequentially** via `processTransaction`, which calls `trxCap.validateSignature(...)` again — but since `isVerified` is already `true`, this call is a no-op that returns `true` without re-reading current permission data: [4](#0-3) [5](#0-4) 

An `AccountPermissionUpdateContract` transaction can change an account's `owner_permission`/`active_permission` lists (adding/removing keys, changing thresholds/operation masks) and is applied through the normal sequential per-transaction execution path, i.e. it takes effect on `AccountStore` mid-block, between the earlier batch pre-check and the later transactions' actual application. Any subsequent transaction in the same block signed under the *old* permission set (e.g., using a key that the permission update just removed) was already marked `isVerified = true` by the pre-block batch check and is executed without any further permission validation.

### Impact Explanation
This allows a transaction signed with a key/permission configuration that has just been revoked earlier in the same block to still be executed as if it were properly authorized. Concretely: an attacker who compromises (or previously held) a private key belonging to an account's active permission, and who broadcasts a spending/authorization transaction signed with that key, can have that transaction validated *before* the account owner's own `AccountPermissionUpdateContract` (removing that key) is applied within the same block, and then executed later in the block trusting the stale verification — effectively bypassing the just-revoked-key restriction and enabling unauthorized account operations/fund transfers. This is an unauthorized-account-operation / potential-theft-of-funds class impact, matching the required severity bar (unauthorized account operation / theft of funds) reachable purely by ordering two signed transactions within a block that any broadcaster/witness-relay can influence.

### Likelihood Explanation
Reachable from purely broadcaster-controlled inputs: any account holder or attacker who can get two transactions (a permission update and a transaction signed with an about-to-be-revoked key) included in the same block, in the vulnerable order, can trigger the stale-authorization execution. No SR/witness/peer malice is required — this happens on any node applying a normally-received block through `Manager#processBlock`, which is the standard consensus block-application path. The precondition is purely about transaction ordering within a block, which is influenced by mempool ordering/block packing, making it a realistic scenario, not a contrived edge case.

### Recommendation
Do not permanently cache `isVerified = true` from the pre-block batch signature check when the same `AccountStore` can be mutated by earlier transactions within the block. Either (a) skip the parallel pre-check optimization for permission-bearing/multi-sig transactions and always re-validate signatures against the live `AccountStore` state at the point of sequential execution in `processTransaction`, or (b) invalidate/reset `isVerified` on any `TransactionCapsule` whose owner's permission was modified by a preceding transaction in the same block before it is applied.

### Proof of Concept
1. Attacker/insider has a private key `K` in account `X`'s `active_permission` list.
2. Build `TX1`: an `AccountPermissionUpdateContract` from `X` (signed by `X`'s owner key) that removes `K` from `active_permission`.
3. Build `TX2`: any contract from `X` (e.g., `TransferContract`) using `permission_id` referencing the active permission and signed only with `K`.
4. Submit both `TX1` and `TX2` into the mempool such that they land in the same block with `TX2` ordered after `TX1` in `block.getTransactions()`.
5. On block receipt, `Manager#processBlock` calls `preValidateTransactionSign` for the whole block before any transaction is applied — at this point `K` is still valid in `X`'s permission, so `TX2.isVerified` is set `true`.
6. During sequential application, `TX1` executes first and removes `K` from `X`'s permission in `AccountStore`.
7. `TX2` is then processed via `processTransaction`; its `validateSignature` call is skipped because `isVerified` is already `true`, so `TX2` executes successfully even though `K` is no longer part of `X`'s active permission — demonstrating execution of an operation authorized by a key that should have been revoked before `TX2`'s effective validation point.

      } finally {
        countDownLatch.countDown();

  public boolean validatePubSignature(AccountStore accountStore,
      DynamicPropertiesStore dynamicPropertiesStore)
      throws ValidateSignatureException {
    if (!isVerified) {
      if (this.transaction.getSignatureCount() <= 0
              || this.transaction.getRawData().getContractCount() <= 0) {
        throw new ValidateSignatureException("miss sig or contract");
      }
      if (this.transaction.getSignatureCount() > dynamicPropertiesStore
              .getTotalSignNum()) {
        throw new ValidateSignatureException("too many signatures");
      }

      byte[] hash = getTransactionId().getBytes();

      long startNs = System.nanoTime();
      try {
        if (!validateSignature(this.transaction, hash, accountStore, dynamicPropertiesStore)) {
          isVerified = false;
          throw new ValidateSignatureException("sig error");
        }
      } catch (SignatureException | PermissionException | SignatureFormatException e) {
        isVerified = false;
        throw new ValidateSignatureException(e.getMessage());
      } finally {
        logSlowSigVerify(startNs);
      }
      isVerified = true;
    }
    return true;
  }

  /**
   * WARN-logs when a single signature verification exceeds
   * {@link #SLOW_SIG_VERIFY_MS}. Package-private so it can be exercised from
   * tests without forcing a real slow crypto path.
   */
  void logSlowSigVerify(long startNs) {
    long costMs = TimeUnit.NANOSECONDS.toMillis(System.nanoTime() - startNs);
    if (costMs > SLOW_SIG_VERIFY_MS) {
      logger.warn("slow verify: txId={}, sigCount={}, cost={} ms",
          getTransactionId(), this.transaction.getSignatureCount(), costMs);
    }
  }

  /**
   * validate signature
   */
  public boolean validateSignature(AccountStore accountStore,
      DynamicPropertiesStore dynamicPropertiesStore) throws ValidateSignatureException {
    if (!isVerified) {
      //Do not support multi contracts in one transaction
      Transaction.Contract contract = this.getInstance().getRawData().getContract(0);
      if (contract.getType() != ContractType.ShieldedTransferContract) {
        validatePubSignature(accountStore, dynamicPropertiesStore);
      } else {  //ShieldedTransfer
        byte[] owner = getOwnerAddress();
        if (!ArrayUtils.isEmpty(owner)) { //transfer from transparent address
          validatePubSignature(accountStore, dynamicPropertiesStore);
        } else { //transfer from shielded address
          if (this.transaction.getSignatureCount() > 0) {
            throw new ValidateSignatureException("there should be no signatures signed by "
                    + "transparent address when transfer from shielded address");
          }
        }
      }
      isVerified = true;
    }
    return true;
  }
