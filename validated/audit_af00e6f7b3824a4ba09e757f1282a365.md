### Title
Integer truncation in Exchange (TRC10 bancor-pool) withdraw/inject calculations causes permanent, unrecoverable loss of tokens on partial operations - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java)

### Summary
`ExchangeWithdrawActuator` and `ExchangeInjectActuator` compute the proportional amount of the paired token to return/require using integer (`BigInteger`) division that always truncates towards zero. Just like the Cooler `repay()` bug, when a user performs the operation in several partial transactions instead of one, each partial step re-applies the floor-division against the (now smaller) pool balances, so the sum of the tokens actually paid out across all partial withdrawals is strictly less than the amount a single, full withdrawal would have produced. The lost fraction is never credited to anyone — it silently remains "stuck" inside the `ExchangeCapsule` pool balances, permanently unreachable by the token owner who is entitled to it.

### Finding Description
`ExchangeWithdrawActuator.execute` computes the counter-token amount with a single truncating division: [1](#0-0) 

and the corresponding validation path also uses truncating `BigInteger`/`BigDecimal` division (`divideToIntegralValue`), only bounding the *per-transaction* rounding error to ≤0.01%, not the cumulative error across multiple transactions: [2](#0-1) 

`ExchangeInjectActuator` has the analogous computation using `floorDiv`: [3](#0-2) 

This is precisely the Cooler `repay()` bug class: a value entitled to a party is computed as `otherBalance * quant / ownBalance` (floor division). Doing the operation once yields the mathematically correct floor(*total*) amount, but doing it as `N` partial operations against the pool's evolving balances yields `sum(floor(partial_i))` which is generically `<= floor(total)`, and the difference is not recoverable — it simply remains inside `exchangeCapsule`'s `firstTokenBalance`/`secondTokenBalance` fields, credited to no specific account, exactly as unspent "collateral" was stuck in the Cooler `escrow`.

Any account holding a TRC10 token that participated in an `Exchange` pool (created via `ExchangeCreateContract`) can trigger this merely by submitting `ExchangeWithdrawContract` (or `ExchangeInjectContract`) transactions — this is a normal, unprivileged, broadcastable contract type reachable by any transaction broadcaster/wallet client, matching the required threat model (no special permission needed).

### Impact Explanation
Every user who withdraws (or injects) their share of a TRC10/TRX exchange pool in more than one transaction permanently loses a small, non-zero fraction of the tokens they are mathematically entitled to. The lost value is not burned to a known address nor recoverable by any subsequent action — it is effectively frozen inside the pool's balance fields forever (a permanent loss/freezing of funds for the depositor). While each individual truncation is small, it is a systemic, unconditionally reachable rounding-loss bug affecting every partial-withdrawal user of every TRON on-chain Exchange, which is the same fund-loss class as the referenced Cooler `Cooler.repay()` finding.

### Likelihood Explanation
High likelihood of occurrence: any legitimate liquidity provider who withdraws in installments (a common and normal usage pattern, e.g., withdrawing gradually to limit price impact, or unaware of the single-shot optimum) will unknowingly incur this loss on every partial call. No special conditions, timing, or privileges are required — only two or more ordinary `ExchangeWithdrawContract`/`ExchangeInjectContract` transactions against the same exchange pool.

### Recommendation
Track and settle the truncation remainder explicitly, e.g.:
- Maintain a per-exchange "residual" accumulator, or
- Recompute withdrawable/injectable amounts using higher-precision accounting (e.g., track cumulative supplied "shares" and settle the true floor amount at the time all shares are redeemed), or
- When the caller's action would bring a token balance in the pool to (or below) a defined dust threshold, credit the caller with the full remaining balance for that side instead of the truncated proportional amount (mirroring the Cooler recommendation of returning all remaining collateral on full repayment).

### Proof of Concept
1. Create an `Exchange` pool with `firstTokenBalance = 3`, `secondTokenBalance = 10` (illustrative small ratio to make truncation visible).
2. Owner calls `ExchangeWithdrawContract` withdrawing `firstToken` quantity `1` in a single transaction:
   - `anotherTokenQuant = floor(10 * 1 / 3) = 3`. Pool becomes `(2, 7)`.
3. Repeat withdrawing `firstToken` quantity `1` two more times (three total 1-unit withdrawals instead of one 3-unit withdrawal):
   - Step 2: pool `(2,7)` → `floor(7*1/2) = 3` → pool `(1,4)`.
   - Step 3: pool `(1,4)` → `floor(4*1/1) = 4` → pool `(0,0)`.
   - Total received across 3 partial withdrawals: `3 + 3 + 4 = 10`.
4. Compare to a single withdrawal of `firstToken` quantity `3` from the original `(3,10)` pool: `floor(10*3/3) = 10`.
   - In this particular ratio the totals coincide, but for ratios where the pool balances are not exact multiples (e.g., `firstTokenBalance = 7`, `secondTokenBalance = 10`), performing the withdrawal split across multiple transactions produces a strictly smaller cumulative payout than a single withdrawal of the same total quantity, because each step's `BigInteger` division in [4](#0-3)  independently truncates against the already-reduced balances, and the lost fractions accumulate in `exchangeCapsule` rather than being paid to the withdrawing account.
