### Title
`decode_g2` in `alt_bn128_pairing_check` accepts on-curve G2 points outside the prime-order r-subgroup, contradicting the documented subgroup-rejection guarantee - ([File: runtime/near-vm-runner/src/logic/alt_bn128.rs])

### Summary
The doc comments for `alt_bn128_pairing_check` in `runtime/near-vm-runner/src/logic/logic.rs:1156-1158` and `runtime/near-vm-runner/src/wasmtime_runner/logic.rs:1027-1029` state that a point "not in the subgroup" is rejected with `AltBn128InvalidInput`. The actual implementation of `decode_g2` performs only an on-curve check via `bn::AffineG2::new`, with no multiplication by the subgroup order `r` (or the twist cofactor) to confirm the point lies in the prime-order r-subgroup. Because the BN254 twist curve `E'(Fq2)` has order `r * h2` with a non-trivial cofactor `h2`, this allows crafting G2 elements that are on-curve but of a smaller order dividing `h2`, which can be used to manipulate the outcome of `bn::pairing_batch` in ways the documented "subgroup rejected" contract promises will not happen.

### Finding Description
`decode_g2` is defined at: [1](#0-0) 

It parses `(x, y): (Fq2, Fq2)` and, if not the identity, calls `bn::AffineG2::new(x, y)`, which only checks that the point satisfies the twist curve equation `Y^2 = X^3 + 3/(i+9)`. It does not verify `r * P == O` (the subgroup-membership check). This is used directly by `pairing_check`: [2](#0-1) 

`pairing_check` decodes each `(G1, G2)` pair and computes `bn::pairing_batch(&elements) == bn::Gt::one()` with no compensating subgroup check anywhere in the call chain (`alt_bn128_pairing_check` in `logic.rs` and the mirrored `wasmtime_runner/logic.rs` simply forward the parsed bytes to `alt_bn128::pairing_check`): [3](#0-2) 

Yet the host-function documentation explicitly asserts the opposite guarantee — that points outside the subgroup are rejected: [4](#0-3) [5](#0-4) 

An unprivileged attacker who deploys a contract that forwards raw bytes to `alt_bn128_pairing_check` (e.g., a Groth16/zk-SNARK proof verifier, or any contract using pairing checks to authorize a `Promise::transfer`) can supply a G2 element that passes `AffineG2::new` (on the twist curve) but has small order dividing the cofactor `h2` rather than order `r`. This is a well-documented weakness of pairing libraries (including the `bn` crate used here) that omit G2 subgroup checks: since BN254's `E'(Fq2)` cofactor is large and non-trivial (unlike G1, where the curve order over `Fq` equals `r` exactly, so no subgroup check is needed there), small-order or otherwise "wrong-subgroup" twist points exist and are accepted by `AffineG2::new`. Feeding such points into `bn::pairing_batch` can produce pairing outputs that do not correspond to the pairing of the intended r-order group elements, breaking the soundness of any contract-level equation the caller relies upon (e.g., a SNARK verification equation), independent of gas metering, signature checks, or wasm sandboxing — none of which validate cryptographic subgroup membership.

### Impact Explanation
Any deployed contract that uses `alt_bn128_pairing_check` as an authorization gate for value transfer (e.g., zk-proof-gated escrow release, cross-chain bridge proof verification, private voting/payment contracts) can have its pairing check forged by supplying non-r-subgroup G2 points, since the host function's documented invariant ("point not in the subgroup is rejected") is not enforced in code. This falls under theft of funds / authorization-escalation categories in the NEAR bounty scope, scoped specifically to contracts that rely on this host function's documented guarantee.

### Likelihood Explanation
The attacker needs only to fund an account and deploy an ordinary wasm contract exposing a call that forwards attacker-supplied bytes to `env::alt_bn128_pairing_check` — a fully permissionless, low-cost action requiring no special privileges (validator, RPC operator, or leaked keys). Constructing a small-order twist point is a standard elliptic-curve computation (finding a point of order dividing the cofactor `h2`), reproducible deterministically and cheaply offline before submitting the transaction. The precondition is that some target contract's business logic itself trusts this host function's documented subgroup-rejection behavior when gating value transfer; the vulnerability in the host function itself is deterministically reproducible via a unit test.

### Recommendation
Add an explicit subgroup check in `decode_g2` (and audit `decode_g1`, though G1's curve order equals `r` for BN254 so no additional check is needed there): after `AffineG2::new` succeeds, multiply the resulting point by the group order `r` and verify the result is the identity (`(P * r).is_zero()`), returning `InvalidInput`/`AltBn128InvalidInput` otherwise. Update both `runtime/near-vm-runner/src/logic/alt_bn128.rs::decode_g2` and ensure the check is exercised by both the `logic.rs` and `wasmtime_runner/logic.rs` call paths (which share the same `alt_bn128::pairing_check`).

### Proof of Concept
Unit test plan in `runtime/near-vm-runner/src/logic/tests/alt_bn128.rs`:
1. Compute a point `Q` on the BN254 twist `E'(Fq2)` such that `Q` is on-curve (passes `bn::AffineG2::new`) but has order `d` dividing the twist cofactor `h2` (`d != r`), e.g., by taking a random twist point and multiplying by `r` to project into the order-`h2` component, then confirm `d * Q == O` for some `d < r`.
2. Encode `Q` and a legitimate/arbitrary `G1` point `P` (chosen so that with the *intended* r-order G2 counterpart the pairing equation would fail) into the `PAIRING_CHECK_ELEMENT_SIZE`-encoded input for `alt_bn128_pairing_check`.
3. Call `logic.alt_bn128_pairing_check(input.len, input.ptr)` and assert it returns `Ok(1)` (pairing succeeds) even though `bn::pairing(P, Q_r_subgroup_intended) != 1` for the "real" r-subgroup counterpart — demonstrating that `decode_g2` accepts `Q` without a subgroup check and that the result diverges from what the doc comment guarantees.
4. Cross-check against a reference implementation with mandatory subgroup checks (e.g., `ark-bn254` with `is_in_correct_subgroup_assuming_on_curve`) to confirm `Q` would be rejected there but is accepted by nearcore's `decode_g2`.

pub(crate) fn pairing_check(
    elements: &[[u8; PAIRING_CHECK_ELEMENT_SIZE]],
) -> Result<bool, InvalidInput> {
    let elements: Vec<(bn::G1, bn::G2)> = elements
        .iter()
        .map(|chunk| {
            let (g1, g2) = stdx::split_array(chunk);
            let g1 = decode_g1(g1)?;
            let g2 = decode_g2(g2)?;
            Ok((g1, g2))
        })
        .collect::<Result<Vec<_>, InvalidInput>>()?;

    let res = bn::pairing_batch(&elements) == bn::Gt::one();

    Ok(res)
}

fn decode_g2(raw: &[u8; 2 * POINT_SIZE]) -> Result<bn::G2, InvalidInput> {
    let (x, y) = stdx::split_array(raw);
    let x = decode_fq2(x)?;
    let y = decode_fq2(y)?;
    if x.is_zero() && y.is_zero() {
        Ok(bn::G2::zero())
    } else {
        bn::AffineG2::new(x, y)
            .map_err(|_err| InvalidInput::new("invalid g2", raw))
            .map(bn::G2::from)
    }
}
