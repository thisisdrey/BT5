### Title
Attachment content served via GET /v2/attachments/<hash> is never checked against the on-chain `AttachmentInstance` commitment - `find_attachment` trusts whatever was flagged `was_instantiated=1` - ([File: stackslib/src/net/atlas/db.rs], [File: stackslib/src/net/atlas/download.rs], [File: stackslib/src/net/api/getattachment.rs])

### Summary
`RPCGetAttachmentRequestHandler::try_handle_request` returns whatever `AtlasDB::find_attachment` finds in the `attachments` table for a given `Hash160`, and that table's `was_instantiated=1` rows are populated by `AtlasDB::insert_instantiated_attachment` without any join to, or verification against, `attachment_instances` (the table populated exclusively from confirmed on-chain `AttachmentInstance` events). A remote peer answering an attachment download request in `extend_with_attachments` (stackslib/src/net/atlas/download.rs:530-558) is trusted at face value: the decoded `GetAttachmentResponse.attachment` is inserted into the in-memory `self.attachments` set with no check that `attachment.hash()` equals the `content_hash` that was actually requested (`AttachmentRequest.content_hash`, built from a real on-chain-confirmed unresolved instance).

### Finding Description
The claimed equality — "served attachment bytes == bytes committed by the confirmed on-chain `AttachmentInstance`" — is not enforced anywhere on the read path:

- `find_attachment` (stackslib/src/net/atlas/db.rs:641-648) is a plain lookup: `SELECT content, hash FROM attachments WHERE hash = ?1 AND was_instantiated = 1`. It has no join or foreign-key check against `attachment_instances`, so it cannot distinguish "content backed by a confirmed on-chain commitment" from "content merely inserted with `was_instantiated=1`". [1](#0-0) 
- `insert_instantiated_attachment` (stackslib/src/net/atlas/db.rs:576-592) unconditionally `INSERT OR REPLACE`s into `attachments` with `was_instantiated = 1` for whatever `Attachment` value is passed to it. The subsequent `UPDATE attachment_instances SET is_available = 1 WHERE content_hash = ? AND status = Checked` is a best-effort side statement — if no matching `attachment_instances` row exists, the `UPDATE` simply affects zero rows, but the `INSERT` into `attachments` still succeeds and the content is still marked `was_instantiated = 1`. [2](#0-1) 
- On the network path, `extend_with_attachments` (stackslib/src/net/atlas/download.rs:530-558) decodes a peer's `GetAttachmentResponse` and inserts `response.attachment` into `self.attachments` with **no comparison** between `response.attachment.hash()` and the `request.content_hash` that was actually being fetched. [3](#0-2) 
- `RPCGetAttachmentRequestHandler::try_handle_request` (stackslib/src/net/api/getattachment.rs:104-118) serves back exactly what `find_attachment` returns, as an unauthenticated 200 JSON response, to any remote caller. [4](#0-3) 

Root cause: `hash` in the `attachments` table is only ever "self-consistent" (i.e., it's whatever hash the `Attachment` object itself carries at insert time), and there is no code path in `db.rs` or `getattachment.rs` that cross-checks a served attachment's hash against a corresponding *Checked* `attachment_instances` row confirmed by chain processing before or at serve time.

### Impact Explanation
Any code path that calls `insert_instantiated_attachment` with unverified content (e.g., processing of a malicious peer's `GetAttachmentResponse` in `extend_with_attachments`) causes the node's public `/v2/attachments/<hash>` endpoint to serve that content as if it were the legitimate BNS-referenced attachment. Any downstream client resolving that Hash160 via this node gets non-canonical/forged data with no cryptographic or on-chain tie confirmed at serve time, matching the "attachment/BNS mismatch" High-severity category. This is repeatable per attachment hash the attacker can get processed by a victim node's downloader.

### Likelihood Explanation
I was not able to fully trace, within the tool budget, the exact call site(s) that take `AttachmentsBatchStateContext.attachments` (populated by `extend_with_attachments`) and commit them to the database via `insert_instantiated_attachment` (two call sites exist in `download.rs` that I could not read before the iteration limit). It is possible — but unconfirmed — that a hash-equality check against the original `AttachmentRequest.content_hash` exists at that later commit step, which would close this gap for the network-triggered path. What is confirmed, independent of that uncertainty, is that `find_attachment`/`insert_instantiated_attachment` in `db.rs` provide no such check themselves, so any caller (including tests, or any other future/existing code path) that calls `insert_instantiated_attachment` with attacker-influenced content will have it served as authoritative by the GET handler with no additional gate.

### Recommendation
Before calling `insert_instantiated_attachment`, and/or inside `find_attachment`, require that the attachment's hash corresponds to a `Checked` (on-chain-confirmed) row in `attachment_instances` — e.g., join the query in `find_attachment` against `attachment_instances` filtered on `status = Checked`, and/or reject `insert_instantiated_attachment` calls whose `content_hash` has no matching `Checked` `attachment_instances` row. Additionally, in `extend_with_attachments`, verify `response.attachment.hash() == request.content_hash` before inserting into `self.attachments`.

### Proof of Concept
Rust test in `stackslib/src/net/api/tests` (mirroring existing `insert_instantiated_attachment` test usage):
1. Construct an `Attachment` with arbitrary content `C` and compute `let h = attachment.hash();`.
2. Call `atlasdb.insert_uninstantiated_attachment(&attachment)` then `atlasdb.insert_instantiated_attachment(&attachment)` — with **no** corresponding row inserted into `attachment_instances`.
3. Build an `RPCGetAttachmentRequestHandler`, parse `StacksHttpRequest::new_getattachment(host, h)`, and call `try_handle_request`.
4. Assert the response is `200 OK` with `GetAttachmentResponse.attachment.content == C`, proving the endpoint serves content that has no backing `attachment_instances` (on-chain-confirmed) row, at `stackslib/src/net/api/getattachment.rs:104-118` via `stackslib/src/net/atlas/db.rs:641-648`.

    pub fn insert_instantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let tx = self.tx_begin()?;
        tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)",
            params![attachment.hash(), attachment.content, now],
        )?;
        tx.execute(
            "UPDATE attachment_instances SET is_available = 1 WHERE content_hash = ?1 AND status = ?2",
            params![attachment.hash(), AttachmentInstanceStatus::Checked],
        )?;
        tx.commit()?;
        Ok(())
    }

    pub fn find_attachment(&self, content_hash: &Hash160) -> Result<Option<Attachment>, db_error> {
