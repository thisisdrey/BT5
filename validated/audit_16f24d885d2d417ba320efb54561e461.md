Audit Report

## Title
Relayer reward settlement in `EthereumOutboundQueueV2::process_delivery_receipt` ignores the decoded `success` flag - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

## Summary
`DeliveryReceipt`, decoded from the Ethereum `InboundMessageDispatched` log inside `submit_delivery_receipt`, carries a `success: bool` field indicating whether the message actually executed successfully on the Gateway contract, but `process_delivery_receipt` never reads this field before crediting the relayer reward and permanently removing the `PendingOrders` entry. [1](#0-0) [2](#0-1)  As a result, a relayer that submits a valid, verified event for a message that failed to execute on Ethereum receives the same fee payout as one that succeeded, with no downstream recovery mechanism.

## Finding Description
`submit_delivery_receipt` is a public, unprivileged, signed extrinsic that verifies the raw Ethereum log/proof via `T::Verifier::verify`, decodes it into a `DeliveryReceipt` via `DeliveryReceipt::try_from`, and forwards it to `process_delivery_receipt`. [3](#0-2)  The decode step correctly captures `success` from the Solidity event `InboundMessageDispatched(uint64 indexed nonce, bytes32 topic, bool success, bytes32 reward_address)`. [4](#0-3) 

`process_delivery_receipt` only checks the gateway address and looks up the `PendingOrder` by nonce; it pays `order.fee` via `T::RewardPayment::register_reward` whenever `order.fee > 0`, and then unconditionally removes the `PendingOrders` entry — `receipt.success` is never inspected. [2](#0-1)  A codebase-wide search confirms `success` is referenced nowhere else in the `outbound-queue-v2` pallet, i.e., it is decoded and then discarded. The module's own top-level documentation describes the intended flow as simply "Fetch the pending order by nonce of the message, pay reward with fee attached in the order" with no success-gating step, matching the code exactly. [5](#0-4) 

Once processed, `PendingOrders::remove(nonce)` deletes the record permanently — there is no retry, backfill, or claw-back path for that nonce. [6](#0-5) 

## Impact Explanation
This violates the pivot requirement that receipts and payout state must only advance after execution success is checked. Any account able to submit a genuine (light-client-verified) `InboundMessageDispatched` log for a message that reverted or ran out of gas on the Gateway contract still receives the full `order.fee` reward, exactly as if delivery had succeeded. This is an incorrect/unconditional settlement of bridge relayer rewards — a value-conserving operation is executed without honoring the success guarantee the receipt schema itself encodes — with no mechanism to correct the payout afterward since the pending order is deleted.

## Likelihood Explanation
The path is reachable by any signed account (public, unprivileged extrinsic, no governance/admin gate) provided it can produce a light-client-verified event log for a nonce with `order.fee > 0`. This only requires a normal operational occurrence — a failed dispatch on the Gateway contract (e.g., out-of-gas or revert) — not a compromised prover, colluding validator set, or malicious relayer assumption; the verifier only attests to log authenticity, not to enforcement of the `success` field downstream.

## Recommendation
In `process_delivery_receipt`, branch on `receipt.success` before registering the reward: pay the full/expected reward only when `success == true`; on `success == false`, withhold or reduce the reward per protocol policy, and emit a distinct event for failed-delivery receipts so downstream systems can react deterministically.

## Proof of Concept
1. `do_process_message` enqueues a message, inserting `PendingOrders[nonce]` with `fee > 0`. [7](#0-6) 
2. The Gateway contract on Ethereum processes nonce `n` and the dispatch reverts, emitting `InboundMessageDispatched(nonce=n, topic, success=false, reward_address=R)`.
3. Any account submits `submit_delivery_receipt` with a valid proof of that real (failed) event; `T::Verifier::verify` succeeds because the log is genuine. [8](#0-7) 
4. `DeliveryReceipt::try_from` decodes `success = false` correctly, but `process_delivery_receipt` never reads it. [9](#0-8) 
5. `T::RewardPayment::register_reward` credits `order.fee` to `R` exactly as for successful delivery, and `PendingOrders::remove(nonce)` permanently deletes the record with no correction path. [10](#0-9)

		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
