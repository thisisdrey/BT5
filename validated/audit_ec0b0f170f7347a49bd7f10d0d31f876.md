### Title
Active-permission key holders can rewrite an account's Owner permission via `AccountPermissionUpdateContract`, seizing full account control without Owner-level signatures - (File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java)

### Summary
The CephFS report describes an unprivileged user escalating to root-equivalent control over a resource by exploiting a permission-bearing operation (`chmod`) that was checked too loosely, letting a lesser privilege level grant itself full ownership. The closest reachable analog in java-tron is `AccountPermissionUpdateActuator`, which lets a signer holding only an **Active** permission (not the Owner permission) submit a transaction that completely replaces the account's Owner permission, Witness permission, and all Active permissions — as long as that Active permission's `operations` bitmap happens to include the bit for `AccountPermissionUpdateContract`.

### Finding Description
`AccountPermissionUpdateActuator.execute()` unconditionally overwrites the account's permission set based solely on the contract payload, without re-checking that Owner-level authority signed the transaction: [1](#0-0) 

The transaction-level authorization only requires the *permission referenced by `permissionId`* to reach its own threshold — it does not require the Owner permission specifically. This is enforced generically in `TransactionCapsule.checkPermission`/`checkWeight` and duplicated in `Wallet.getTransactionApprovedList`: [2](#0-1) [3](#0-2) 

`WalletUtil.checkPermissionOperations` (and the duplicate in `TransactionUtil`) only checks whether the bit for the contract's `ContractType` is set in the permission's `operations` bitmap — it performs no special-casing for sensitive contract types such as `AccountPermissionUpdateContract`: [4](#0-3) 

Crucially, `AccountPermissionUpdateActuator.checkPermission()` — the validator that restricts what contract types an Active permission's `operations` field may enable — validates the requested bits only against `dynamicStore.getAvailableContractType()`, and does **not** exclude `AccountPermissionUpdateContract` from that allowed set (only a few operational types such as `UpdateBrokerageContract` are excluded elsewhere in the codebase): [5](#0-4) 

This is confirmed by the framework test that builds the full "available contract type" bitmap and includes `AccountPermissionUpdateContract` as a valid bit for `getAvailableContractType()` (only `UNRECOGNIZED` and `UpdateBrokerageContract` are excluded): [6](#0-5) 

Consequently, if an Owner ever grants an Active permission (e.g., a business/automation key meant only for transfers or contract calls) the `AccountPermissionUpdateContract` operation bit, any signer(s) meeting that Active permission's threshold — which can be far lower than the Owner permission's threshold and involve a completely different key set — can submit an `AccountPermissionUpdateContract` transaction and unilaterally replace the account's Owner permission, Witness permission, and Active permissions with attacker-controlled keys. This permanently locks out the legitimate Owner and any co-signers, since after the update the original Owner key set no longer controls the account.

### Impact Explanation
This allows unauthorized account takeover: a party holding a delegated, narrowly-scoped Active key (which itself may have been granted with a low threshold, e.g., threshold 1) can escalate to full, permanent control of the account by rewriting Owner/Witness/Active permissions, exactly mirroring the CephFS pattern of an under-privileged actor leveraging a loosely-checked operation to seize full ownership of a resource it doesn't fully control. This results in permanent loss of account control/funds by the legitimate owner and any co-signers whose keys are dropped from the new permission set — a concrete unauthorized account operation and potential permanent freezing/theft of funds.

### Likelihood Explanation
Exploitation requires the account Owner to have explicitly assigned the `AccountPermissionUpdateContract` bit to an Active permission's `operations` field. Because the actuator's `checkPermission()` and `getAvailableContractType()` do not forbid this specific bit (unlike other explicitly-excluded contract types), nothing in the validation path prevents an Owner — possibly through a misconfigured multisig setup, a compromised signing UI/wallet defaulting to "select all operations," or a malicious co-owner drafting the permission update — from creating this condition. Once created, exploitation by any Active-permission-threshold signer is a single signed transaction, requiring no special network position or additional trust.

### Recommendation
Explicitly exclude `AccountPermissionUpdateContract` (and any other permission-management contract types) from the set of operations assignable to non-Owner (`Active`) permissions in `AccountPermissionUpdateActuator.checkPermission()`, and/or enforce in the actuator's `validate()`/`execute()` that only a signature meeting the account's **Owner** permission (permissionId == 0, or Permission of type `Owner`) can execute `AccountPermissionUpdateContract`, regardless of what an Active permission's `operations` bitmap contains.

### Proof of Concept
1. Owner account `A` creates an Active permission `P2` (id=2, threshold=1) whose 32-byte `operations` bitmap includes the bit for `AccountPermissionUpdateContract` (bit index = `ContractType.AccountPermissionUpdateContract.getNumber()`), assigned to key `K_active` — this passes `AccountPermissionUpdateActuator.checkPermission()` validation since that contract type is present in `getAvailableContractType()`.
2. Holder of `K_active` builds a new `AccountPermissionUpdateContract` transaction for account `A`, setting `permissionId = 2` in the transaction's `Contract`, and supplies a brand-new Owner permission naming only the attacker's key, plus new Active/Witness permissions as desired.
3. `TransactionCapsule.checkPermission`/`checkWeight` validates the signature against permission `P2` (threshold 1), which the attacker's single signature satisfies — no Owner-level signature is required.
4. `AccountPermissionUpdateActuator.validate()` passes (all structural checks succeed), and `execute()` calls `account.updatePermissions(...)`, completely replacing the account's Owner/Witness/Active permissions with the attacker's chosen keys.
5. The original Owner key(s) are now removed from the account's permission structure and have permanently lost the ability to control the account.

  public static boolean checkPermissionOperations(Permission permission, Contract contract)
      throws PermissionException {
    ByteString operations = permission.getOperations();
    if (operations.size() != 32) {
      throw new PermissionException(String.format("operations size must 32, actual: %d",
          operations.size()));
    }
    int contractType = contract.getTypeValue();
    boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
    return b;
  }
