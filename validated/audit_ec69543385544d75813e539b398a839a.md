## Analog Found

### Title
Unbounded HTTP response body read in `libsigner` StackerDB session client causes memory-exhaustion DoS — (File: `libsigner/src/http.rs`)

### Summary
`libsigner::session::StackerDBSession` (used by `stacks-signer` to poll a Stacks node's StackerDB HTTP RPC endpoints) reads the entire HTTP response into memory via `sock.read_to_end(&mut buf)` with no size limit, and non-chunked response bodies are copied verbatim with no cap either. This mirrors the KubeEdge CVE-2022-31079 bug class: a stream endpoint reads a whole message into memory without imposing any limit, enabling memory-exhaustion DoS against the reading peer.

### Finding Description
`run_http_request` in [1](#0-0)  writes the request and then does:
```
let mut buf = vec![];
sock.read_to_end(&mut buf)?;
```
This reads from the socket until EOF with **no upper bound at all**, regardless of any `Content-Length` header — the header/length is not even consulted before or during this read. Only after the read completes does the code call `decode_http_response` to parse headers, and `decode_http_body` in [2](#0-1)  to extract the body. Note that the `MAX_MESSAGE_LEN` bound is applied **only** in the chunked-transfer-encoding branch (`HttpChunkedTransferReader::from_reader(ptr, MAX_MESSAGE_LEN.into())`); for a plain (non-chunked) response, the body is simply `buf.to_vec()` — i.e. whatever `read_to_end` already buffered without limit.

This function is the sole transport used by `StackerDBSession::rpc_request` in [3](#0-2) , which backs every `SignerSession` method (`list_chunks`, `get_chunks`, `get_latest_chunks`, `put_chunk`) that `stacks-signer` uses to talk to its configured Stacks node's `/v2/stackerdb/...` RPC endpoints — e.g. `get_latest_chunks` in [4](#0-3) . Contrast this with the size-consciousness applied everywhere else in the same code path: `get_latest_chunks` explicitly checks `body_bytes.len() > limit` only *after* the unbounded read already happened, and the equivalent StackerDB chunk GET on the node's HTTP server side (`stackslib/src/net/api/getstackerdbchunk.rs`) bounds the parsed response via `parse_bytes(preamble, body, STACKERDB_MAX_CHUNK_SIZE.into())` — but that check applies to `stackslib`'s own HTTP stack, not to `libsigner`'s hand-rolled `run_http_request`, which has no equivalent cap.

This breaks the equality that should hold everywhere else in this codebase: "bytes read == bounded by a declared/maximum message size." Every other reader in scope enforces this — the P2P preamble/payload reader in [5](#0-4)  rejects any `payload_len >= MAX_MESSAGE_LEN` before buffering, and `StacksP2P`'s `payload_len` in [6](#0-5)  is always `Some(..)` and bounded. `libsigner`'s `run_http_request` is the one reader in the in-scope transport code that has no such bound.

### Impact Explanation
Any party able to answer the HTTP connection that a `stacks-signer` process makes to its configured node RPC endpoint (a misbehaving/compromised node, or an on-path responder) can send an arbitrarily large, non-chunked HTTP response (or simply never close a legitimate-looking stream) causing the signer process to attempt to buffer the entire body in memory via `Vec<u8>` growth, exhausting available memory and crashing or hanging the signer (denial of service), exactly matching the CWE-400/CWE-770 impact described in the KubeEdge advisory. This is a bounded-compute/memory DoS on a read/RPC-client path in `libsigner`, one of the explicitly in-scope transport files.

### Likelihood Explanation
No authentication, secret key, or admin role is required from the attacker's side — the only precondition is that the response source (whatever the signer connects to) returns a large body. It requires only a single response containing many bytes, not a volumetric flood, and needs no vulnerability in TCP/TLS/serde; the flaw is purely the absence of a size cap in `run_http_request` itself before/while consuming the socket.

### Recommendation
Bound the client-side read in `run_http_request`: read/parse headers first (respecting a maximum header size, already partially done via `MAX_HTTP_HEADER_LEN`), then read exactly the number of bytes declared by `Content-Length` (rejecting values above `MAX_MESSAGE_LEN`/`STACKERDB_MAX_CHUNK_SIZE`), or wrap the socket read in a bounded reader (similar to `BoundReader` used elsewhere, e.g. in `stackslib/src/net/httpcore.rs`) so `read_to_end` cannot exceed a hard cap regardless of chunked/non-chunked framing.

### Proof of Concept
1. Configure (or compromise/redirect via MITM) the node endpoint that a `stacks-signer` instance's `StackerDBSession` connects to.
2. On any RPC call the signer makes (e.g. `get_latest_chunks`, `list_chunks`, `put_chunk`), have the server respond with valid HTTP headers (`HTTP/1.1 200 OK`) but no `Transfer-Encoding: chunked` and either an absent/false `Content-Length` or a huge one, followed by an effectively unbounded stream of bytes (or simply never terminate the response body before closing).
3. `run_http_request`'s `sock.read_to_end(&mut buf)` will keep growing `buf` unboundedly until the process runs out of memory, crashing or hanging the `stacks-signer` process — denial of service.

/// Decode an HTTP body, given the headers.
pub fn decode_http_body(headers: &HashMap<String, String>, mut buf: &[u8]) -> io::Result<Vec<u8>> {
    let chunked = if let Some(val) = headers.get("transfer-encoding") {
        val == "chunked"
    } else {
        false
    };

    let body = if chunked {
        // chunked encoding
        let ptr = &mut buf;
        let mut fd = HttpChunkedTransferReader::from_reader(ptr, MAX_MESSAGE_LEN.into());
        let mut decoded_body = vec![];
        fd.read_to_end(&mut decoded_body)?;
        decoded_body
    } else {
        // body is just as-is
        buf.to_vec()
    };

    Ok(body)
}
