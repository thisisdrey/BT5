## Analog Identified

This report's core broken invariant — *source-chain funds are consumed/burned before the destination-side effect is guaranteed, with no cancel/refund path if the destination action never succeeds* — has a direct structural analog in the new `pallet-accumulate-and-forward` / `TeleportForwarderForAccountId32` flow used by system parachains (BridgeHub, Collectives, Coretime, People, and the Westend relay chain) to periodically sweep accumulated fees/dust/coretime-revenue to AssetHub's DAP pallet.

### Title
Accumulate-and-forward teleport permanently traps protocol funds on destination with no refund/claim path if the remote deposit fails - (File: `polkadot/xcm/xcm-builder/src/forwarder.rs`)

### Summary
`TeleportForwarderForAccountId32::forward` burns native tokens on the source chain via `WithdrawAsset`+`InitiateTransfer{..Teleport..}` and, once the *local* XCM executor reports `Outcome::Complete`, commits the transaction and enqueues the outbound message. Any failure on the *remote* leg (the `DepositAsset` into the DAP staging account on AssetHub) is not visible to, or recoverable by, the sending pallet. [1](#0-0) 

### Finding Description
The adapter's own doc comment states the exact failure mode: *"Once the local executor reports success, the message is queued and any destination-side rejection results in trapped assets at the destination with no automatic recovery path."* [2](#0-1) 

The commit/rollback logic only guards the *local* leg: [3](#0-2) 

Once `Outcome::Complete` is returned locally, the tokens are already burned on the source chain (teleport-out) and the transaction is `Commit`-ed — there is no tracking of a pending "receipt" and no callback for a later remote failure. The calling pallet, `pallet-accumulate-and-forward`, treats `forward()` as a synchronous success/failure boolean and has no notion of "pending until remote settlement": [4](#0-3) 

If the remote `DepositAsset { assets: Wild(AllCounted(1)), beneficiary }` fails on AssetHub (e.g. the DAP staging account is not yet initialized/does not meet ED, is filtered, or any other transient/remote condition causes the deposit instruction to error), the teleported assets land in AssetHub's asset trap (`AssetsTrapped`) rather than the staging account. Because `preserve_origin: true` causes `InitiateTransfer` to prepend `AliasOrigin(source_location)`, the trap key is bound to the aliased *sending-parachain-account* origin — an origin that neither the source pallet nor any human user can trivially reconstruct and send a matching `ClaimAsset` from, since the pallet contains **no code path at all** that issues a claim; it only performs one-shot `on_idle` forwards. [5](#0-4) 

This mirrors the Linea bug precisely: step 1 (burn/withdraw on source) is irreversible and independent of step 2 (deposit on destination); step 2 can fail for reasons entirely outside the sender's control, and there is no cancellation/refund instruction obtainable from the source chain to recover the funds.

### Impact Explanation
The affected funds are protocol-owned (transaction fees, dust removal, coretime revenue) that are periodically swept by `on_idle` rather than user-initiated, but they are real chain value that becomes **permanently locked/trapped** on AssetHub with no automatic or governance-triggered recovery mechanism coded anywhere in this pipeline. This matches the "permanent user-fund or bridge-state lock" impact category — value crosses a chain boundary via teleport-burn, and if the paired mint/deposit does not settle, there is no code that re-establishes ownership or reverses the burn. Over many `TransferPeriod` cycles this can result in unbounded value loss with only an `AssetsTrapped` event as a forensic trail, and no automated way to redeem it.

### Likelihood Explanation
`forward()` is only reachable from `on_idle`, a privileged internal hook — not a user-callable extrinsic — so this is not an attacker-controlled path in the classic sense. It requires a naturally occurring failure on the destination leg (misconfigured/uninitialized staging account, incorrect ED, temporarily halted DAP pallet, version-negotiation gaps, or filter changes) which is realistically achievable in a multi-chain rollout without any malicious actor, admin abuse, or governance action being the root cause — it is a design/implementation gap in the forwarding adapter itself.

### Recommendation
Do not commit/burn on the local leg until destination-side settlement is confirmed, or track a pending state (analogous to `PendingOrders` in the Snowbridge outbound queue) that can be reconciled via a receipt/ack from AssetHub, or automatically issue `ClaimAsset` back to the accumulation account's local sovereign representation when a delivery-failure signal is observed. At minimum, add a governance-triggered or automatic re-claim path in `pallet-accumulate-and-forward` for funds it forwards, mirroring the reconciliation pattern already used by `snowbridge_pallet_outbound_queue_v2::process_delivery_receipt` for Ethereum-bound messages. [6](#0-5) 

### Proof of Concept
1. Configure `pallet-accumulate-and-forward` with `TeleportForwarderForAccountId32` targeting AssetHub's DAP staging account, as wired in `bridge-hub-westend`/`collectives-westend`/`coretime-westend`/`people-westend` runtimes.
2. Accumulate fees/dust in the accumulation account until `on_idle` triggers a forward at a `TransferPeriod` block, as exercised in the integration test `test_accumulate_forward_transfers_to_asset_hub`. [7](#0-6) 
3. Arrange for the remote `DepositAsset` on AssetHub to fail (e.g. DAP staging account below ED, or DAP pallet not yet initialized) instead of the happy-path used in that test.
4. Observe: source chain emits `ForwardSucceeded` and burns/decreases `total_issuance` (as verified at lines 122–124 of the same test), while AssetHub emits `AssetsTrapped` instead of crediting the staging account — with no subsequent code path in `pallet-accumulate-and-forward` or `TeleportForwarderForAccountId32` ever issuing a `ClaimAsset` to recover the trapped funds. [8](#0-7)

	fn forward(source: AccountId, amount: Balance) -> Result<(), ()> {
		let dest = Dest::get();
		let asset = Asset { id: AssetId(NativeAsset::get()), fun: Fungible(amount.into()) };
		let beneficiary: Location = StagingLocation::get().into_location();

		let remote_xcm = Xcm(vec![DepositAsset { assets: Wild(AllCounted(1)), beneficiary }]);

		// The XCM flow: `ReceiveTeleportedAsset → AliasOrigin(source) → UnpaidExecution →
		// DepositAsset`. `preserve_origin: true` causes `InitiateTransfer` to prepend
		// `AliasOrigin(source_location)` to the remote XCM.
		let xcm: Xcm<XcmConfig::RuntimeCall> = Xcm(vec![
			UnpaidExecution { weight_limit: WeightLimit::Unlimited, check_origin: None },
			DescendOrigin(Junction::AccountId32 { network: None, id: source.into() }.into()),
			WithdrawAsset(asset.into()),
			InitiateTransfer {
				destination: dest,
				remote_fees: None,
				preserve_origin: true,
				assets: BoundedVec::truncate_from(alloc::vec![AssetTransferFilter::Teleport(
					Wild(AllCounted(1))
				),]),
				remote_xcm,
			},
		]);
