### Title
Uncleaned quarantine directory for non-existent repositories persists attacker-written objects after transaction rollback - ([File: internal/gitaly/storage/storagemgr/partition/transaction_manager.go])

### Summary
The HenloKart report shows a state-machine flaw where a user can "deposit" (commit) and immediately "cancel," yet the deposit's effect is not properly reverted, letting the attacker keep value that should have been returned. In `TransactionManager.Begin`, the analogous pattern is that when a write transaction targets a repository that does not yet exist, the "quarantine directory" used to stage incoming Git objects is **not** placed inside the transaction's ephemeral staging area — it is set directly to the real, final on-disk location. If the transaction is later rolled back (the "cancel"), the cleanup logic only removes the staging directory, so any objects/directories the client wrote into that quarantine path remain on disk permanently.

### Finding Description
When `Begin` sets up a write transaction, it distinguishes two cases based on `txn.repositoryExists`: [1](#0-0) 

For an **existing** repository, the quarantine directory is created under `txn.stagingDirectory` (a per-transaction temp directory): [2](#0-1) 

For a **non-existing** repository (i.e. the target of the transaction is being newly created, such as during an initial push/`CreateRepository`/fork), the quarantine directory is instead pointed straight at the real storage path where the repository's `objects` directory would live: [3](#0-2) 

```go
txn.quarantineDirectory = filepath.Join(mgr.storagePath, txn.snapshot.RelativePath(txn.relativePath), "objects")
```

This is `mgr.storagePath` — the storage's real absolute root — not a path under `txn.stagingDirectory` or the transaction's copy-on-write snapshot. Any Git objects/pack files an RPC handler or `git` subprocess writes into this quarantine path during the transaction land directly on the real filesystem at the (attacker-influenced) relative path of the not-yet-created repository.

When the transaction finishes, cleanup only tears down `txn.snapshot`, `txn.stagingSnapshot`, and `txn.stagingDirectory` — it never touches `txn.quarantineDirectory` for this branch: [4](#0-3) 

`Rollback` funnels into this same `finish`/`cleanTemporaryState` path: [5](#0-4) 

So if a write transaction targeting a not-yet-existing repository is aborted (`Rollback`) after objects were already written into the quarantine path — e.g. because a later validation step, access check, hook, or quorum/vote fails, or the client cancels the RPC — the loose objects and any parent directories created under `mgr.storagePath/<relativePath>/objects` are never removed. This mirrors the HenloKart pattern: the "deposit" (objects written to disk) is retained even though the enclosing transaction was "canceled."

### Impact Explanation
This is a concrete storage escape: attacker-controlled loose objects and directory structures persist outside the WAL-journaled, transactional state of the partition, at a relative path the attacker can influence via `RelativePath`/fork/import RPCs. Consequences include:
- Storage exhaustion / DoS: repeatedly starting a repository-creation transaction, writing large packs into quarantine, then aborting (or letting an access/hook check fail) leaves permanent garbage on disk that is invisible to Gitaly's repository accounting (it isn't part of any committed WAL entry and isn't associated with a real repository), so normal repository-deletion/pruning flows won't reclaim it.
- Integrity risk if a repository is later legitimately created at that same relative path: the pre-existing "objects" directory content from the earlier aborted transaction would already be present on disk before `git-init`/`CreateRepository` runs, potentially smuggling untrusted objects into what should be a freshly created repository's object store, bypassing normal write-path validation (dependency verification, hooks) that assumes a clean starting state.

### Likelihood Explanation
The path is reachable by an ordinary user through any RPC that creates a new repository under transaction management (e.g., import/fork/initial push flows) that fails or is canceled after objects were written to quarantine but before the transaction commits. Rollback due to context cancellation, failed access checks, or failed quorum/vote is a normal, easily triggerable occurrence in production (any client can cancel a gRPC call), making this readily reachable without special privileges.

### Recommendation
For repositories that do not yet exist, stage the quarantine objects inside the transaction's `stagingDirectory` (or another location cleaned up unconditionally by `cleanTemporaryState`) rather than directly under `mgr.storagePath`. If writing directly to the real repository path is required for git tooling reasons, ensure `cleanTemporaryState`/`Rollback` explicitly removes the created quarantine/objects directory (and any newly created parent directories) whenever the transaction did not commit, so aborted transactions leave no residual state on disk.

### Proof of Concept
Conceptual reproduction based on the code paths above (exact RPC wiring for triggering a rollback after quarantine writes was not fully traced within the available index; a Devin session with full repo access would be needed to build and run the exact reproducing test):
1. Start a write `Transaction` via `TransactionManager.Begin` targeting a `RelativePath` that does not yet correspond to an existing repository (`doesRepositoryExist` returns false).
2. Have the write path push/unpack Git objects into `txn.quarantineDirectory`, which resolves to `mgr.storagePath/<RelativePath>/objects`.
3. Force the transaction to fail before `Commit` (e.g., cancel the context, fail a hook, or fail quorum), triggering `Rollback`/`finishUnadmitted`.
4. Observe that `mgr.storagePath/<RelativePath>/objects` and its contents remain on disk after rollback, since `cleanTemporaryState` in `transaction_manager.go` only removes `txn.stagingDirectory`/`txn.snapshot`, never this path.

// Rollback releases resources associated with the transaction without performing any changes.
func (txn *Transaction) Rollback(ctx context.Context) error {
	defer trace.StartRegion(ctx, "rollback").End()

	if err := txn.updateState(transactionStateRollback); err != nil {
		return err
	}

	defer prometheus.NewTimer(txn.metrics.rollbackDuration(txn.write)).ObserveDuration()

	return txn.finishUnadmitted()
}

// finishUnadmitted cleans up after the transaction if it wasn't yet admitted. If the transaction was admitted,
// the Transaction is being processed by TransactionManager. The clean up responsibility moves there as well
// to avoid races.
func (txn *Transaction) finishUnadmitted() error {
	if txn.admitted {
		return nil
	}

	return txn.finish(false)
}
