## #Vulnerability found for this question.

### Title
Path-segment parsing bypass in HTTP disabled-API access control - (File: `framework/src/main/java/org/tron/core/services/filter/HttpApiAccessFilter.java`)

### Summary
`HttpApiAccessFilter.isDisabled()` enforces the operator-configured `disabledApiList` deny-list by normalizing the request URI and then extracting the API name via a fixed-index `split("/")[2]` lookup [1](#0-0) . Because this index-based segmentation does not match how the underlying servlet container resolves and dispatches the actual request path, an attacker can craft a request whose "disabled-check" segment differs from the segment actually used to route to the target servlet — exactly the same class of bug as the Vault CVE-2026-12624 report, where a policy engine's path-normalization/deny-check diverged from the routing/enforcement layer, allowing access to a path meant to be blocked.

### Finding Description
`isDisabled()` first normalizes the endpoint with `URI.create(endpoint).normalize()` (which resolves `.`/`..` segments but does not collapse or realign arbitrary internal path segments), then blindly indexes into the split array (`endpoint.split("/")[2]`) to obtain the API name to check against `disabledApiList` [1](#0-0) .

This is a purely positional, container-independent re-implementation of path parsing sitting in front of Jetty's own path-matching/dispatch logic used to route to the real servlet (registered via exact `addServlet(..., "/wallet/xxx")` mappings in `FullNodeHttpApiService`, `SolidityNodeHttpApiService`, `HttpApiOnSolidityService`, `HttpApiOnPBFTService`) [2](#0-1) . Whenever the filter's own re-derivation of "which API segment to check" disagrees with what the servlet container will actually dispatch to, the deny-list enforcement can be defeated while the real (disabled) API is still served.

The project's own test suite already demonstrates this divergence directly: requesting `/wallet/a/b/../getnowblock` causes `isDisabled()` to evaluate the segment `"a"` (not `"getnowblock"`) and return `false` (i.e., "not disabled"), whereas `/wallet/a/../b/../getnowblock` normalizes cleanly and correctly evaluates `"getnowblock"` as disabled [3](#0-2) . This confirms that carefully chosen extra path segments (dot-segments, or embedded empty segments from a doubled slash such as `/wallet//getnowblock`, which Java's `String.split` will preserve as an empty element and shift the index of the true API name) make the fixed-index check inspect the wrong segment and silently allow the request through the filter as "enabled," regardless of the operator's `disabledApiList` configuration — provided the servlet container still routes the crafted path to the intended disabled servlet.

### Impact Explanation
The `disabledApiList` mechanism is a node-operator security/DoS-mitigation control used to turn off specific Wallet HTTP JSON-RPC-style endpoints (e.g., sensitive query, shielded-transaction, or resource-intensive endpoints) without shutting the whole HTTP API down. An anonymous, unprivileged HTTP client reaching this filter [4](#0-3)  can bypass this enforcement and continue to invoke an API the operator explicitly intended to block, undermining an operator-configured protection and re-exposing "an API the node can no longer serve" per the operator's intent.

### Likelihood Explanation
The bypass only requires crafting an HTTP request path with extra path segments (e.g., `..` dot-segments or duplicated slashes) — trivially reachable by any anonymous API caller with no authentication, and the exact divergence is already reproduced in-repo by the existing unit test [5](#0-4) . The remaining uncertainty is whether the specific servlet container configuration will dispatch such a crafted path to the exact-match servlet mapping in every deployment; this is container/version dependent and needs empirical confirmation against the live embedded Jetty configuration.

### Recommendation
Do not re-derive the "API name" via manual string splitting on the raw/normalized URI. Instead, match `disabledApiList` against the actual matched servlet path/pattern that Jetty resolves for the request (e.g., use `HttpServletRequest.getServletPath()`/the resolved `ServletMapping` after container dispatch, or perform the deny-check at the servlet level rather than a generic path-string filter), and add regression tests using duplicated slashes and encoded slash variants in addition to existing dot-segment tests.

### Proof of Concept
Using the existing test harness pattern in `HttpApiAccessFilterTest` [6](#0-5) , configure `disabledApiList` with `getnowblock`, then invoke `isDisabled` (or send an actual HTTP GET) against paths such as `/wallet/a/b/../getnowblock` — the check returns `false` (not disabled) as already demonstrated by the repo's own assertion at line 146, while a request normalized purely by the servlet container may still ultimately be routed to the disabled `getnowblock` servlet, confirming the check/enforcement divergence.

```java
  private boolean isDisabled(String endpoint) {
    boolean disabled = false;

    try {
      endpoint = URI.create(endpoint).normalize().toString();
      List<String> disabledApiList = CommonParameter.getInstance().getDisabledApiList();
      if (!disabledApiList.isEmpty()) {
        disabled = disabledApiList.contains(endpoint.split("/")[2].toLowerCase(Locale.ROOT));
      }
    } catch (Exception e) {
      logger.warn("check isDisabled except, endpoint={}, {}", endpoint, e.getMessage());
    }

    return disabled;
  }
```
