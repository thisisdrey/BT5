### Title
Prefix-level `cleanup_by_prefix` clears already-executed nonce bits sharing the same 31-byte word, enabling replay of a previously settled `MultiPayload` - ([File: contracts/defuse/src/contract/garbage_collector.rs])

### Summary
`GarbageCollector::cleanup_nonces` deletes an entire 256-bit nonce word via `self.0.remove(&prefix)` in `crates/bitmap/src/b256.rs` whenever any single nonce sharing that word's 31-byte prefix is deemed cleanable (`Contract::is_nonce_cleanable`). Because cleanability is judged per-nonce (based on the *attacker-chosen* salt/deadline in that nonce's own `VersionedNonce::V1` encoding) but cleanup acts on the whole word, an attacker who controls an unused nonce `N2` sharing a prefix with their own already-executed nonce `N1` can get `N1`'s committed bit wiped by a legitimate `GarbageCollector`/`DAO` cleanup call, then resubmit the original `N1`-signed `MultiPayload` and have `commit_nonce` succeed a second time.

### Finding Description
The binding that must hold is: `is_used(N1) == true` for all time after `N1`'s legitimate execution (i.e., a committed nonce bit, once set from real fund movement, must never return to `false` without re-verifying it was N1's own salt/deadline that expired). Concretely:

- `Contract::is_nonce_cleanable` (`contracts/defuse/src/contract/garbage_collector.rs:31-43`) decides cleanability from the *nonce value itself* — `deadline < Timestamp::now() || !self.is_valid_salt(salt)` — decoded from the 32-byte nonce passed into `cleanup_nonces`. This check is evaluated per full nonce, not per word.
- `cleanup_nonces` (`contracts/defuse/src/contract/garbage_collector.rs:13-27`) then strips the last byte (`let [prefix @ .., _] = nonce;`) and calls `State::cleanup_nonce_by_prefix(self, &account_id, prefix)`, which in `contracts/defuse/src/contract/intents/state.rs:133-145` calls `Account::cleanup_nonce_by_prefix` → `Nonces::cleanup_by_prefix` (`contracts/defuse/core/src/nonce/mod.rs:47-50`) → `BitMap256::cleanup_by_prefix` (`crates/bitmap/src/b256.rs:48-51`), which does `self.0.remove(&prefix).is_some()` — an unconditional removal of the *entire word* (all 256 bits/32 nonces... actually all 256 possible `bit_pos` values for that 31-byte prefix), regardless of which individual bits were set and why.
- There is no bit-level check before the word removal: the code never verifies that only the specific bit corresponding to the cleanable nonce's `bit_pos` was set, nor does it re-validate that other bits in the same word (e.g., `N1`'s bit) were themselves cleanable.

Exploit flow:
1. Attacker signs and executes a real intent with nonce `N1 = prefix || bit_pos_1`, embedding a valid salt at the time. `commit_nonce(N1)` sets the bit for `bit_pos_1` in word `prefix`, and funds move.
2. Attacker crafts (but never submits, or submits and it fails/never gets committed) a second signed payload with nonce `N2 = prefix || bit_pos_2` (same `prefix`, different `bit_pos`), deliberately encoding it as `VersionedNonce::V1(SaltedNonce { salt: <stale/rotated-out salt>, .. })` so `is_valid_salt(salt)` is `false` (or `deadline` already passed). `N2`'s bit is never set (never committed), but that is irrelevant to cleanability.
3. Any `Role::DAO`/`Role::GarbageCollector` holder later runs routine `cleanup_nonces` including `N2` (this is a normal maintenance action, not attacker-triggered, and out of scope to attack directly per the rules, but the resulting state is in scope). `is_nonce_cleanable(N2)` returns `true`, so `cleanup_nonce_by_prefix(account_id, prefix)` executes and removes the *entire* `prefix` word from the map — clearing `bit_pos_1` (N1's bit) along with everything else in that word.
4. Attacker resubmits the original, previously-executed `N1`-signed `MultiPayload`. `is_nonce_used(N1)` is now `false` (word gone from map, `get_bit` returns `false` for missing entry per `crates/bitmap/src/b256.rs:29-37`), so `commit_nonce(N1)` succeeds again (`Nonces::commit` → `BitMap256::set_bit` returns `old = false`), and the intent executes a second time, moving funds again.

Existing guards do not prevent this: `MaybeLegacyNonces::commit` only rejects nonces found in the immutable legacy map (`contracts/defuse/src/contract/accounts/account/nonces.rs:46-58`), which does not protect the new bitmap from prefix-level clearing; `is_nonce_cleanable` operates purely on attacker-controlled nonce metadata with no cross-check against sibling bits in the same word.

### Impact Explanation
This produces a one-signed-payload-settles-twice condition: `N1`'s legitimate signed intent moves the same funds a second time after garbage collection, violating the invariant that a signed payload settles exactly once. This is a Critical-severity finding per the given rules ("one signed payload settling more than once"). The blast radius spans every account and every nonce word where an attacker can arrange for a sibling nonce (sharing the top 31 bytes) to be judged cleanable — which the attacker fully controls since salt/deadline in `N2` is attacker-chosen at signing time. Since `GarbageCollector`/DAO cleanup runs routinely (out of the attacker's control but not out of the attacker's *anticipation*), the attacker can pre-position `N2` values and simply wait for/trigger conditions (salt rotation making an old salt invalid) that will eventually cause routine cleanup to wipe `N1`'s bit.

### Likelihood Explanation
Preconditions are fully within attacker control: they need only (a) execute one real intent with `N1`, and (b) craft an unexecuted signed payload for `N2` sharing `N1`'s 31-byte prefix, using a salt they know is invalid (e.g., any salt other than the currently active one — trivial to obtain since salts are public/rotatable and old salts are known once rotated) or a passed deadline. No special role or privilege is needed to create `N2` — it need not even be submitted. The only external dependency is that some `GarbageCollector`/DAO role holder eventually calls `cleanup_nonces` including `N2`'s prefix, which is a normal, expected maintenance operation this system is designed to perform periodically (and is explicitly out of scope to say "don't call it" — the vulnerability is that the *legitimate* call has this side effect). This is realistically triggerable and repeatable across accounts/prefixes.

### Recommendation
Change nonce cleanup to operate at bit granularity, not word/prefix granularity: `cleanup_by_prefix`/`cleanup_nonce_by_prefix` should only clear the specific bit(s) corresponding to nonces that were individually verified as cleanable, not the whole 32-byte word. Concretely, in `crates/bitmap/src/b256.rs`, replace the `self.0.remove(&prefix)` word-delete with a bit-clear (`clear_bit`) applied only to the exact nonce passed in, and only remove the map entry once all 256 bits in that word are confirmed clear (e.g., track a live-bit count, or iterate/verify the whole word is zero before removing the entry). Additionally, `is_nonce_cleanable` should not be usable to justify clearing bits belonging to *other* nonces in the same word — cleanup must be nonce-exact.

### Proof of Concept
```rust
// cargo test -p defuse-bitmap (or defuse-contract sandbox test)
// Demonstrates BitMap256::cleanup_by_prefix wipes a sibling committed bit.

#[test]
fn cleanup_by_prefix_wipes_sibling_committed_nonce() {
    use defuse_bitmap::{BitMap256, U256};
    use std::collections::HashMap;

    let mut m = BitMap256::<HashMap<_, _>>::default();

    // N1: previously executed, real fund-moving nonce
    let mut n1: U256 = [0u8; 32];
    n1[31] = 1; // bit_pos = 1, same 31-byte prefix as n2

    // N2: attacker's never-committed nonce, same prefix, different bit_pos
    let mut n2: U256 = [0u8; 32];
    n2[31] = 2;

    // Step 1: commit N1 (simulates real execution moving funds)
    assert!(!m.set_bit(n1));
    assert!(m.get_bit(n1)); // LHS of binding: is_used(N1) == true

    // Step 2/3: GC deems N2 cleanable (attacker chose stale salt/deadline for N2),
    // cleanup_nonce_by_prefix removes the WHOLE prefix word
    let [prefix, ..] = [n2]; // conceptually: let [prefix @ .., _] = n2;
    let prefix31: [u8; 31] = { let [p @ .., _] = n2; p };
    let removed = m.cleanup_by_prefix(prefix31);
    assert!(removed);

    // BINDING VIOLATED: is_used(N1) flips from true -> false without
    // N1 itself ever being deemed cleanable
    assert!(!m.get_bit(n1)); // RHS: now false -- funds-moved nonce is "unused" again

    // Step 4: replay succeeds
    assert!(!m.set_bit(n1)); // old==false => commit_nonce(N1) would return Ok(()) again
    assert!(m.get_bit(n1));
}
```
For end-to-end confirmation, a `near-workspaces` sandbox test should: (1) deploy `defuse` contract, (2) sign and `execute_intents` a real transfer with nonce `N1`, asserting balances moved, (3) craft `N2` sharing `N1`'s prefix with an invalid/rotated salt, (4) as a `GarbageCollector`-role test account call `cleanup_nonces` with `N2`, (5) resubmit the original `N1` `MultiPayload` via `execute_intents`, and assert it succeeds and balances move a second time — proving `REPLAY(N1) == 2` instead of the required `1`.
