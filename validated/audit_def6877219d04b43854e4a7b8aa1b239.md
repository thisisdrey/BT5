### Title
Accrued rewards are permanently locked if the recipient account is blacklisted by the reward token contract - (File: contracts/RewardsDistributor.sol)

### Summary
`RewardsDistributor.claimRewards` always pays accrued rewards to the reward-earning `account_` itself, and `RecurringAirdrop.claim` always pays `msg.sender`. Neither function allows specifying an alternative recipient. If the account is blacklisted by a blocklist-enabled ERC20 reward token (e.g. USDC/USDT), the `safeTransfer` reverts forever and the accrued rewards can never be withdrawn — a permanent freeze of unclaimed yield. `RewardsDistributor` accepts an arbitrary `rewardToken` at `initialize`, so a blocklistable reward token is a supported configuration.

### Finding Description
In `contracts/RewardsDistributor.sol`, all three `claimRewards` overloads funnel into `claimRewards(address[] accounts_, IERC20[] tokens_)`, which calls `_transferRewardIfEnoughTokens(_account, tokensAccruedOf[_account])` [1](#0-0) . The payout is hardcoded to the account itself:

```solidity
function _transferRewardIfEnoughTokens(address account_, uint256 amount_) private {
    IERC20 _rewardToken = rewardToken;
    uint256 _balance = _rewardToken.balanceOf(address(this));
    if (amount_ > 0 && amount_ <= _balance) {
        tokensAccruedOf[account_] = 0;
        _rewardToken.safeTransfer(account_, amount_);
        emit RewardClaimed(account_, amount_);
    }
}
``` [2](#0-1) 

The reward token is an immutable-per-deployment config value set in `initialize` [3](#0-2) , so a blocklistable token like USDC is a valid configuration.

The same pattern exists in `contracts/utils/RecurringAirdrop.sol`: `claim` binds the merkle leaf to `msg.sender` and transfers to `msg.sender` with no recipient override [4](#0-3) [5](#0-4) .

Because the leaf/account is bound to the claimant address and there is no `recipient`/`to` parameter, a blacklisted user has no mechanism to redirect rewards to a clean address. Additionally, `claimRewards` is permissionless (anyone can trigger a claim for any `account_`), but this does not help: the transfer still goes to the blacklisted account and reverts.

### Impact Explanation
If a user's address is placed on the reward token's blocklist (a real occurrence with USDC/USDT), every `claimRewards` call for that account reverts at `safeTransfer`. `tokensAccruedOf[account]` continues to grow via `updateBeforeMintOrBurn`/`updateBeforeTransfer`, but can never be paid out. The rewards are effectively frozen in the distributor contract permanently (or as long as the blocklist entry stands) — permanent freezing of unclaimed yield, matching the accepted impact criteria. For `RecurringAirdrop`/`MetAirdrop`, the same applies to airdrop allocations if the distributed token has a blocklist.

### Likelihood Explanation
Likelihood is conditional: it requires (a) a deployed `RewardsDistributor` whose `rewardToken` is a blocklistable token, and (b) a reward earner being blacklisted (sanctions, compliance actions, or compromised-key flags). Both are low-probability but non-trivial, consistent with Medium severity in the referenced report. No privileged role or attacker action is needed to trigger the freeze once the precondition holds.

### Recommendation
Add a `recipient_` parameter so the entitled account can redirect payout:

```solidity
function claimRewards(address account_, address recipient_, IERC20[] memory tokens_) ... {
    ...
    _transferRewardIfEnoughTokens(recipient_, tokensAccruedOf[account_]);
}
```

For `claimRewards(address[], IERC20[])` being callable by third parties, restrict redirection: only `account_ == msg.sender` (or an authorized operator on behalf of `account_` via `Operator.execute`) may set a `recipient_` different from `account_`, otherwise default `recipient_ = account_`. Apply the same to `RecurringAirdrop.claim(uint256 amount_, address recipient_, bytes32[] proof_)`, keeping the leaf bound to `msg.sender`.

### Proof of Concept
Foundry fork-style test sketch against the deployed mainnet `RewardsDistributor` (assumes reward token with a blocklist, e.g. a hypothetical USDC-reward distributor, or simulated with a mock blocklist token):

```solidity
function test_blacklistedAccountCannotClaim() public {
    // setup: alice holds depositToken/debtToken and accrues rewards
    // 1. Alice accrues rewards
    vm.prank(debtTokenHolder);
    distributor.updateBeforeMintOrBurn(debtToken, alice);
    // warp time so tokensAccruedOf[alice] > 0
    vm.warp(block.timestamp + 1 days);
    distributor.claimRewards(alice); // sanity: works pre-blacklist

    // accrue again
    vm.warp(block.timestamp + 1 days);

    // 2. Reward token admin blacklists alice
    vm.prank(blacklister);
    BlocklistedERC20(rewardToken).blacklist(alice);

    // 3. Any claim attempt for alice reverts on safeTransfer
    vm.expectRevert(); // token's "blacklisted" revert
    distributor.claimRewards(alice);

    // 4. No alternative path exists: permissionless claim by a third party
    // also reverts because payout is hardcoded to `account`
    vm.expectRevert();
    vm.prank(bob);
    distributor.claimRewards(alice);

    // tokensAccruedOf[alice] remains > 0 but is unrecoverable
    assertGt(distributor.claimable(alice), 0);
}
```

The revert occurs inside `_transferRewardIfEnoughTokens` at `_rewardToken.safeTransfer(account_, amount_)`; since `recipient` can never differ from `account_`, there is no code path that lets a blacklisted earner recover accrued rewards.
