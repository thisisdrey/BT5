### Title
Missing Slippage Protection in `ExchangeInjectActuator`/`ExchangeWithdrawActuator` Allows Users to Suffer Unexpected Losses on TRX/TRC10 Bancor-style Exchanges - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java], [File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java])

### Summary
`ExchangeInjectContract` and `ExchangeWithdrawContract` (unlike `ExchangeTransactionContract`) provide no field for the caller to specify a minimum/maximum acceptable counter-token amount. Both `ExchangeInjectActuator` and `ExchangeWithdrawActuator` compute the counter-token amount (`anotherTokenQuant`) from the *live* pool ratio at execution time, and there is no user-supplied bound to protect against ratio changes between broadcast and inclusion, mirroring the `FundContract` slippage issue where deposit/withdraw functions lacked `minSharesOut`/`minAssetsOut` parameters.

### Finding Description
The `ExchangeTransactionContract` explicitly supports slippage protection via an `expected` field (proto), enforced in `ExchangeTransactionActuator.doValidate()`: [1](#0-0) 

However, the sibling operations that also move funds based on the same fluctuating Bancor-formula pool — `ExchangeInjectContract` (adding liquidity) and `ExchangeWithdrawContract` (removing liquidity) — carry only `owner_address`, `exchange_id`, `token_id`, and `quant`, with no analogous `expected`/minimum field: [2](#0-1) 

In `ExchangeInjectActuator.execute()`, the counter-token amount the caller must additionally pay in is derived from the *current* `firstTokenBalance`/`secondTokenBalance` ratio at the moment of execution, not any value chosen by the user: [3](#0-2) 

Likewise, `ExchangeWithdrawActuator.doValidate()` computes `anotherTokenQuant` — the amount of the other token the withdrawer will receive — purely from the live pool ratio, with the only check being a rounding-precision guard (`"Not precise enough"`), not a user-specified minimum: [4](#0-3) 

Because `firstTokenBalance`/`secondTokenBalance` can be moved by any other account submitting an `ExchangeTransactionContract` (buy/sell) transaction that lands in an earlier position within the same block or in a preceding block, a user's `ExchangeInjectContract`/`ExchangeWithdrawContract` transaction can execute against a ratio very different from what was observed when the transaction was signed and broadcast — with no way to bound or reject an unfavorable outcome.

### Impact Explanation
An account submitting a liquidity-inject transaction can be forced to deposit a much larger amount of the counter-token than intended (since `anotherTokenQuant` scales with the pool ratio at execution), or an account withdrawing liquidity can receive far less of the counter-token than expected, both resulting in unintended loss of assets/TRX at execution time with no on-chain recourse. This matches "theft or permanent freezing of funds" impact class in the sense that value is extracted from the transaction sender due to unbounded exposure to ratio manipulation, analogous to the missing `minSharesOut`/`minAssetsOut` issue in the external report.

### Likelihood Explanation
This is reachable by any unprivileged account broadcasting an ordinary `ExchangeInjectContract` or `ExchangeWithdrawContract` transaction — no special privileges (SR/witness/committee) required. The pool ratio can be moved by any other account submitting a normal `ExchangeTransactionContract` transaction beforehand, which is a routine and inexpensive operation. This makes the scenario realistically exploitable in any active TRX/TRC10 Bancor exchange pool, though it requires an adversary (or natural market activity) shifting the ratio between the victim's signing and inclusion — a MEV/front-running-style condition rather than a guaranteed drain, similar in likelihood profile to the referenced ERC-4626 report.

### Recommendation
Add an `expected` (minimum/maximum bound) field to `ExchangeInjectContract` and `ExchangeWithdrawContract`, analogous to the existing field in `ExchangeTransactionContract`, and enforce it in `ExchangeInjectActuator.doValidate()`/`execute()` and `ExchangeWithdrawActuator.doValidate()`/`execute()` by reverting when the computed `anotherTokenQuant` falls outside the caller-specified acceptable range.

### Proof of Concept
1. Attacker/other user observes a pending `ExchangeInjectContract` transaction from Victim (specifying `token_id = firstTokenID`, `quant = Q`) targeting exchange pool with `firstTokenBalance = F`, `secondTokenBalance = S`.
2. Attacker submits and gets included first an `ExchangeTransactionContract` that swaps a large amount of `secondToken` for `firstToken`, shifting the ratio so `S/F` increases substantially.
3. Victim's `ExchangeInjectContract` is then executed by `ExchangeInjectActuator.execute()`, which recomputes `anotherTokenQuant = floorDiv(multiplyExact(secondTokenBalance, tokenQuant), firstTokenBalance)` using the now-inflated `secondTokenBalance` [5](#0-4) , forcing Victim to pay in far more `secondToken` than they anticipated when signing, with no field available on `ExchangeInjectContract` to cap this amount and cause the transaction to fail instead.
