### Title
Unclosed native RocksDB/LevelDB iterators in list-style Store queries cause unbounded native memory leak reachable via unauthenticated HTTP/gRPC APIs - (File: chainbase/src/main/java/org/tron/core/store/AssetIssueStore.java)

### Summary
`AssetIssueStore.getAllAssetIssues()` (and the equivalent pattern in `CodeStore`, `TronStoreWithRevoking.size()`, etc.) builds a `Stream` directly over the raw store `Iterator` without ever calling `close()` on it. The underlying iterator is a native RocksDB/LevelDB iterator (`RockStoreIterator`/`StoreIterator`) that pins a native snapshot/`ReadOptions` object and is explicitly documented as "**CRITICAL**: ... MUST be closed after use to prevent memory leaks", but the call chain from these list APIs never does so. This is directly analogous to CVE-2019-18811, where a Linux kernel error path failed to free allocated buffers, causing an attacker-triggerable memory leak.

### Finding Description
`AssetIssueStore.getAllAssetIssues()` calls `Streams.stream(iterator())...collect(...)`: [1](#0-0) 

`iterator()` is inherited from `TronStoreWithRevoking`, which transforms `revokingDB.iterator()` (a `Chainbase`/`SnapshotRoot` wrapped native iterator) but never closes it: [2](#0-1) [3](#0-2) 

`SnapshotRoot.iterator()` simply forwards to the underlying `DB` (RocksDB/LevelDB) implementation: [4](#0-3) 

The RocksDB implementation's `iterator()` returns a `RockStoreIterator` wrapping a native `RocksIterator` plus a native `ReadOptions` object, and the class-level Javadoc explicitly warns that this native resource must be closed via try-with-resources or it will leak: [5](#0-4) [6](#0-5) 

`Streams.stream(Iterator)` (Guava) simply wraps the `Iterator` as a `Stream` — it never invokes `close()` on the source, so nothing in the `getAllAssetIssues()`/`getAssetIssuesPaginated()` path ever calls `RockStoreIterator.close()`, leaking the native `RocksIterator` and its `ReadOptions` (each of which pins native heap memory / DB snapshot state) on every invocation. The same pattern (`Streams.stream(revokingDB.iterator())`) is used elsewhere, e.g. `CodeStore.getTotalCodes()`: [7](#0-6) 

This is reachable by any anonymous API client with no authentication or transaction signing required. `Wallet.getAssetIssueList()` and `Wallet.getAssetIssueList(offset, limit)` call `getAllAssetIssues()`/`getAssetIssuesPaginated()`: [8](#0-7) [9](#0-8) 

These are exposed via unauthenticated HTTP servlets: [10](#0-9) [11](#0-10) 

as well as via gRPC (`GetAssetIssueList`/`GetPaginatedAssetIssueList`), including on the fullnode, solidity, and PBFT services: [12](#0-11) [13](#0-12) 

### Impact Explanation
Each unauthenticated request to `/wallet/getassetissuelist`, `/wallet/getpaginatedassetissuelist` (and their solidity/PBFT counterparts), or the equivalent gRPC calls, allocates a native RocksDB iterator plus a `ReadOptions` object that is never closed. Native RocksDB iterator objects pin memtable/SST resources outside the JVM heap and are not reliably reclaimed by JVM garbage collection (RocksJava relies on explicit `close()`; native memory reclamation via finalization is unpredictable and can be arbitrarily delayed). Repeated invocation of these list APIs by any anonymous client therefore causes unbounded native memory growth, ultimately leading to node memory exhaustion, degraded performance, and potential crash/denial of service of the full node — impacting the node's ability to continue serving API and consensus operations, matching the CVE's "memory consumption" DoS class.

### Likelihood Explanation
The vulnerable code path is reached by a simple GET/POST HTTP request or gRPC unary call with no signature, no funds, and no special permission — it is one of the most basic wallet/API query endpoints (`getassetissuelist`, `getpaginatedassetissuelist`). An attacker can trivially script repeated calls to accumulate leaked native iterators; the only mitigating factor is any HTTP-level rate limiting (`RateLimiterServlet`), which does not prevent leakage, only slows it.

### Recommendation
Close the underlying `Iterator`/`DBIterator` after use in all list-building code paths that consume `revokingDB.iterator()`/`db.iterator()`. Specifically, wrap `iterator()` usage in `AssetIssueStore.getAllAssetIssues()`, `CodeStore.getTotalCodes()`, and any other caller in try-with-resources (or explicitly call `close()` in a `finally` block) so the native `RocksIterator`/`ReadOptions`/`DBIterator` resources are always released, regardless of how the resulting `Stream` is consumed.

### Proof of Concept
1. Start a java-tron full node with the HTTP API enabled (default config).
2. Repeatedly send anonymous HTTP requests: `GET http://<node>:8090/wallet/getassetissuelist` (or `POST /wallet/getpaginatedassetissuelist`) in a loop, with no authentication.
3. Each call triggers `AssetIssueStore.getAllAssetIssues()` → `Streams.stream(iterator())`, allocating a `RockStoreIterator` (native `RocksIterator` + `ReadOptions`) that is never closed.
4. Monitor the node's native (off-heap) memory usage (e.g., via `pmap`/RSS or RocksDB memory metrics) while repeating the request; observe continuous growth proportional to the number of requests, since none of the allocated native iterators are ever released, eventually leading to memory exhaustion of the node process.

```java
public final class RockStoreIterator implements DBIterator {

  private final RocksIterator dbIterator;
  private boolean first = true;

  private final AtomicBoolean close = new AtomicBoolean(false);
  private final ReadOptions readOptions;

  public RockStoreIterator(RocksIterator dbIterator, ReadOptions readOptions) {
    this.readOptions = readOptions;
    this.dbIterator = dbIterator;
  }

  @Override
  public void close() throws IOException {
    if (close.compareAndSet(false, true)) {
      readOptions.close();
      dbIterator.close();
    }
  }
```
