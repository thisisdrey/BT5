## Title
Sync loss between `MarketPairToPriceStore.priceNum` counter and actual `MarketPairPriceToOrderStore` price-level entries can desynchronize the TRC10 order-book market state - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
The TRC10 exchange order-book (Market actuators) uses the exact same "counter tracks a mutable list" pattern flagged in the external report: `MarketPairToPriceStore` keeps a `priceNum` counter per token pair that is supposed to always equal the number of distinct price levels linked in `MarketPairPriceToOrderStore` for that pair. All three market actuators (`MarketSellAssetActuator`, `MarketCancelOrderActuator`) independently read, decrement/increment, and persist this counter next to (but separately from) the underlying linked list of orders, mirroring the `gameInfo.activeAgents` vs. `agents[]` desync pattern from the Infiltration.sol report.

### Finding Description
`MarketPairToPriceStore.addNewPriceKey()` increments `priceNum` when a new price level is created [1](#0-0) , and `getPriceNum`/`setPriceNum` are plain independent get/put operations on a separate DB key from the actual order list stored in `MarketPairPriceToOrderStore` [2](#0-1) .

In `MarketSellAssetActuator.matchOrder`, the maker-side price count is read once into `remainCount`, and a `priceKeysList` snapshot is fetched with a `makerPriceNumber` bound [3](#0-2) . As price levels are exhausted, `pairPriceToOrderStore.delete(pairPriceKey)` removes the linked-list head entry and `remainCount` is decremented and written back via `pairToPriceStore.setPriceNum(...)` or the whole pair is removed via `pairToPriceStore.delete(makerPair)` when `remainCount == 0` [4](#0-3) .

Symmetrically, `MarketCancelOrderActuator.execute` independently re-reads `pairToPriceStore.getPriceNum(makerPair)`, subtracts 1, and writes it back (or deletes the pair key) after removing an order from `pairPriceToOrderStore` via `orderIdListCapsule.removeOrder(...)` [5](#0-4) .

This is structurally identical to the reported bug class: two data structures (a scalar "active count" and an underlying linked collection) are maintained by separate code paths (`matchOrder`'s in-transaction consumption loop vs. `MarketCancelOrderActuator`'s independent read-decrement-write of `pairToPriceStore`) with no atomic invariant enforced between them. Any code path that touches `pairPriceToOrderStore`'s linked list of orders (add/remove) without correspondingly updating `pairToPriceStore`'s count — or vice versa — leaves the pair's price-level index out of sync with the actual set of active price levels, exactly like `gameInfo.activeAgents` becoming out of sync with the `agents[]` array in the original report.

### Impact Explanation
If `priceNum` overstates the real number of price levels, subsequent `matchOrder` calls compute `priceKeysList` with a stale/incorrect bound and could iterate over or reference price keys that no longer exist in `pairPriceToOrderStore` (already deleted), which can produce null/missing order-list lookups, incorrect matching decisions, or orders that can never be matched or drained from the book — effectively freezing user assets locked in those TRC10 sell orders (the same "permanently unclaimable" class of impact called out in the source report, translated to "permanently unmatchable/uncancellable order funds"). If `priceNum` understates the real number, some legitimate maker price levels become permanently invisible to the matching engine, so the tokens escrowed in those orders can no longer be matched, only recoverable via `MarketCancelOrderActuator` (if cancellation logic itself doesn't hit the same stale count).

### Likelihood Explanation
This is reachable directly by any unprivileged account issuing ordinary `MarketSellAssetContract`/`MarketCancelOrderContract` transactions (via `MarketSellAssetActuator`/`MarketCancelOrderActuator`), with no special privileges required. I could not identify, however, a concrete transaction sequence within the code I reviewed that actually forces the two structures out of sync — the reviewed matching/cancel logic appears to keep `remainCount` and `priceKeysList` consistent within a single execution, and I was not able to fully trace every edge case (e.g., interaction between concurrent partial fills across multiple `matchSingleOrder` calls, `hasMatch`'s `priceKeysList.get(0)` snapshot reuse across the loop, and `MAX_MATCH_NUM` truncation of `priceKeysList` versus the real remaining count) that could produce divergence, due to index and time constraints on further exploration. This is presented as an analog worth targeted verification, not a proven exploit.

### Recommendation
Treat `MarketPairToPriceStore.priceNum` as a derived/cache value and add an invariant check (or recompute it directly from `MarketPairPriceToOrderStore` iteration) whenever a price level is added or removed, rather than maintaining it via independent increment/decrement calls scattered across `MarketSellAssetActuator.matchOrder` and `MarketCancelOrderActuator.execute`. Specifically audit: (1) whether `priceKeysList` truncation by `MAX_MATCH_NUM + 1` in `matchOrder` can cause `remainCount` to diverge from the true count of remaining price keys after the loop exits early or throws; (2) whether a `ContractValidateException` thrown mid-`matchOrder` (e.g., the `"Too many matches"` case) can leave `pairToPriceStore` partially updated while the DB transaction is rolled back inconsistently relative to `pairPriceToOrderStore`.

### Proof of Concept
Not established with certainty. A verification session should attempt: create many maker orders across `MAX_MATCH_NUM+1` distinct price levels for a token pair to trigger the `"Too many matches. MAX_MATCH_NUM"` `ContractValidateException` path in `matchOrder` [6](#0-5) , then check whether `pairToPriceStore`'s `priceNum` for the maker pair reflects the actual remaining `pairPriceToOrderStore` price-key count after the exception unwinds, and whether subsequent sell/cancel transactions on that pair behave correctly or leave orders permanently unmatched/uncancellable.

   * if pair not exits, add token pair, set count = 1, add headKey to pairPriceToOrderStore.
   * otherwise, increase count

  public void addNewPriceKey(byte[] sellTokenId, byte[] buyTokenId,
      MarketPairPriceToOrderStore pairPriceToOrderStore) {
    long number;

    byte[] pairKey = MarketUtils.createPairKey(sellTokenId, buyTokenId);
    if (has(pairKey)) {
      number = getPriceNum(pairKey) + 1;
    } else {
      number = 1;
      byte[] headKey = MarketUtils.getPairPriceHeadKey(sellTokenId, buyTokenId);
      pairPriceToOrderStore.put(headKey, new MarketOrderIdListCapsule());
    }

    setPriceNum(pairKey, number);
  }
