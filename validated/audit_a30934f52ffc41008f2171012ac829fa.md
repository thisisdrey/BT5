### Title
Out-of-bounds read in ijar's ZIP central directory parser due to unchecked attacker-controlled length fields - (`File: third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` in ijar's ZIP/JAR parser reads `file_name_length`, `extra_field_length`, and `file_comment_length` directly from an untrusted archive and uses them to advance pointers and `memcpy` data out of the mmap'd input file without ever validating that the declared lengths fit within the remaining mapped bytes, unlike the sibling local-file-header parser which performs this check via `EnsureRemaining()`. [1](#0-0) [2](#0-1) 

### Finding Description
Ijar (the "interface jar" tool used to strip a JAR down to its ABI) opens the input archive by memory-mapping the file read-only for exactly its length, with no guard region beyond the file's end. [3](#0-2) 

`ProcessLocalFileEntry`, which parses each ZIP local file header, is careful to bounds-check every variable-length field against the remaining bytes in the mapped file before touching it, via the `EnsureRemaining()` helper. [4](#0-3) [2](#0-1) 

`ProcessCentralDirEntry`, which parses each ZIP *central directory* entry, has no equivalent check. It reads `file_name_length`, `extra_field_length`, and `file_comment_length` as raw 16-bit values straight from attacker-controlled bytes, then:
- `memcpy`s `file_name_length` bytes from the current cursor `p` into a fixed-size stack buffer (`filename[PATH_MAX]`) without first confirming that many bytes remain in the mapped region,
- advances `p` by `file_name_length` and then by `extra_field_length`, walking an "extra field" loop (`extra_p`) that trusts each field's declared `data_size` to advance further,
- and finally advances `p` by `file_comment_length`. [5](#0-4) 

Because `file_name_length`, `extra_field_length`, and `file_comment_length` are each attacker-controlled 16-bit values (up to 65535) and are never checked against `input_file_->Length()` before being used to read or copy memory, a crafted central directory record with an inflated length field (especially near the end of a small/truncated archive) causes the parser to read past the end of the `mmap`'d buffer. [6](#0-5) 

This is the direct analog of CVE-2025-23247: cuobjdump used length fields taken from an untrusted ELF file to size a buffer read/copy without validating them against the actual buffer bounds, causing a crash or potential further memory corruption on malformed input. Here, ijar's ZIP central-directory parser uses attacker-controlled `file_name_length`/`extra_field_length`/`file_comment_length` fields the same way, with no bounds validation analogous to the one present just a few functions away for local file headers. [1](#0-0) 

`ProcessCentralDirEntry` is the core primitive driving both real extraction (`InputZipFile::ProcessNext`) and size-estimation (`InputZipFile::CalculateOutputLength`), both of which iterate over every central directory entry of an input JAR during ijar processing. [7](#0-6) [8](#0-7)  Ijar is automatically invoked by Bazel's Java build rules on dependency/source JARs to produce interface JARs, so any JAR consumed by a build — including one obtained from a `http_archive`/`http_jar`/`maven_install`-resolved artifact — is passed through this exact unguarded parser at build time. A pinned `sha256`/`integrity` checksum only guarantees the downloaded bytes match what the attacker published; it does nothing to guarantee that the ZIP central directory's declared field lengths are internally consistent with the actual file size, so a hash-correct-but-malformed archive can still exploit this gap.

### Impact Explanation
A maliciously crafted (but still checksum-matching) JAR/ZIP file processed by ijar can cause the parser to read beyond the end of its `mmap`'d input buffer, which per POSIX `mmap` semantics typically results in a `SIGSEGV`/`SIGBUS` crash of the build action, and in cases where slack bytes exist at the tail of the final mapped page, can leak adjacent process memory into the `filename` buffer or extra-field parsing loop, information that can subsequently be written into the produced interface JAR entry or influence path-handling logic. This is an out-of-bounds read reachable purely from attacker-supplied archive content, matching the class of impact in CVE-2025-23247 (crash / potential arbitrary code execution from malformed binary parsing).

### Likelihood Explanation
Every JAR consumed by a Bazel Java build (including externally fetched dependencies) is routed through ijar to produce its interface jar, so the vulnerable code path is exercised on essentially every Java build. Because the missing check is purely a "length field validated against buffer size" omission — while the neighboring local-header parser already implements the correct pattern — a single crafted central directory entry with an inflated `file_name_length`/`extra_field_length`/`file_comment_length` is sufficient to trigger the out-of-bounds read; no special ordering, races, or multi-step conditions are required.

### Recommendation
Add the same bounds validation used in `ProcessLocalFileEntry`'s `EnsureRemaining()` calls to `ProcessCentralDirEntry`: before reading/copying `file_name_length`, `extra_field_length`, and `file_comment_length` bytes (and before dereferencing each "extra field" entry's `data_size`), verify that the requested length does not exceed the number of bytes actually remaining between the cursor and the end of the mapped input file, and abort parsing with an error (as `EnsureRemaining` does) rather than proceeding.

### Proof of Concept
Construct a ZIP file whose central directory contains a single entry with a valid `CENTRAL_FILE_HEADER_SIGNATURE`, but with `file_name_length` (or `extra_field_length`/`file_comment_length`) set to `0xFFFF`, while the actual file is truncated shortly after the fixed 46-byte central directory header fields. Running ijar's `extract()` (or the build-time interface-jar-stripping path) on this file will cause `ProcessCentralDirEntry` to `memcpy`/advance `p` far past `zipdata_in_ + input_file_->Length()`, producing an out-of-bounds read (crash under `mmap`, or memory disclosure) with no diagnostic comparable to the "Premature end of file" errors that `EnsureRemaining()` produces for local file headers. A JUnit/`BuildIntegrationTestCase` style reproduction would mirror `src/tools/singlejar/zip_headers_test.cc`'s pattern of crafting raw byte buffers, but targeted at `third_party/ijar/zip_test.cc`/`InputZipFile::ProcessCentralDirEntry` with an oversized `file_name_length` against a short backing buffer.

```text
bool InputZipFile::ProcessCentralDirEntry(const u1 *&p, u8 *compressed_size,
                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
  const u1 *extra_p = p;
  p += extra_field_length;
  while (extra_p != p) {
    const u2 header_id = get_u2le(extra_p);
    const u2 data_size = get_u2le(extra_p);
    const u1 *extra = extra_p;
    extra_p += data_size;
    if (header_id == ZIP64_EXTRA_FIELD_TAG) {
      if (*uncompressed_size == U4_MAX) {
        *uncompressed_size = get_u8le(extra);
      }
      if (*compressed_size == U4_MAX) {
        *compressed_size = get_u8le(extra);
      }
      if (*offset == U4_MAX) {
        *offset = get_u8le(extra);
      }
    }
  }
  p += file_comment_length;
  return true;
}
```

```text
u8 InputZipFile::CalculateOutputLength() {
  const u1* current = central_dir_;

  u8 compressed_size = 0;
  u8 uncompressed_size = 0;
  u8 skipped_compressed_size = 0;
  u4 attr;
  u8 offset;
  char filename[PATH_MAX];

  while (true) {
    u8 file_compressed, file_uncompressed;
    if (!ProcessCentralDirEntry(current,
                                &file_compressed, &file_uncompressed,
                                filename, PATH_MAX, &attr, &offset)) {
      break;
    }

    if (processor->Accept(filename, attr)) {
      compressed_size += (u8) file_compressed;
      uncompressed_size += (u8) file_uncompressed;
    } else {
      skipped_compressed_size += file_compressed;
    }
  }

  // The worst case is when the output is simply the input uncompressed. The
  // metadata in the zip file will stay the same, so the file will grow by the
  // difference between the compressed and uncompressed sizes.
  return (u8) input_file_->Length() - skipped_compressed_size
      + (uncompressed_size - compressed_size);
}
```

```text
MappedInputFile::MappedInputFile(const char* name) {
  impl_ = NULL;
  opened_ = false;

  int fd = open(name, O_RDONLY);
  if (fd < 0) {
    snprintf(errmsg, MAX_ERROR, "open(): %s", strerror(errno));
    errmsg_ = errmsg;
    return;
  }

  off_t length = lseek(fd, 0, SEEK_END);
  if (length < 0) {
    snprintf(errmsg, MAX_ERROR, "lseek(): %s", strerror(errno));
    errmsg_ = errmsg;
    return;
  }

  void* buffer = mmap(NULL, length, PROT_READ, MAP_PRIVATE, fd, 0);
  if (buffer == MAP_FAILED) {
    snprintf(errmsg, MAX_ERROR, "mmap(): %s", strerror(errno));
    errmsg_ = errmsg;
    return;
  }

  impl_ = new MappedInputFileImpl();
  impl_->fd_ = fd;
  buffer_ = reinterpret_cast<u1*>(buffer);
  length_ = length;
  opened_ = true;
}
```
