### Title
Floating-point precision drift in the Exchange (Bancor-relay) swap math allows value extraction / reserve draining via `ExchangeTransactionActuator` — (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
TRON's on-chain TRX/TRC10 exchange ("Bancor-style" pools created with `ExchangeCreateContract`) is functionally the same primitive as the Osmosis LP that was drained: a constant-relay-supply AMM whose swap output is computed by curve math. Unless the chain committee has activated `AllowHardenExchangeCalculation`, every `ExchangeTransactionContract` broadcast by an anonymous account is priced using `ExchangeProcessor`, which performs the bonding-curve calculation with IEEE-754 `double` arithmetic and `Maths.pow(...)`. This is the exact bug class the Osmosis report describes: an AMM/LP pricing routine whose internal math does not conserve value exactly, letting an attacker who repeatedly interacts with the pool extract more value than they contributed, draining the pool's reserves.

### Finding Description
`ExchangeCapsule.transaction()` selects the pricing engine based on a governance-controlled flag: [1](#0-0) 

When `hardenedCalc` is false (the default unless the `AllowHardenExchangeCalculation` proposal has been passed), the swap amount for every `ExchangeTransactionContract` is computed by `ExchangeProcessor.exchange()`, which relies on plain `double` math for both legs of the Bancor formula: [2](#0-1) 

`exchangeToSupply` and `exchangeFromSupply` each cast intermediate results with `(long) issuedSupply` / `(long) exchangeBalance` — truncating a floating point value that was itself computed via `Math.pow` on doubles. Floating point `pow`/division is not guaranteed exact, and each swap round-trips through an internal fictitious "relay supply" (`supply`) that is mutated (`supply += out;` / `supply -= supplyQuant;`) and persists across the life of the pool in `ExchangeCapsule`. Because this internal `supply` state is a stateful accumulator across many transactions and the rounding error direction is not provably always in the protocol's favor, repeated small/crafted trades (analogous to the repeated `JoinPool`/`ExitPool` interactions that let Osmosis attackers extract $3M) can accumulate rounding bias between the token amount actually removed from `firstTokenBalance`/`secondTokenBalance` in `ExchangeCapsule.transaction()` and the true bonding-curve-conserving amount.

Confirmation that this is a known, real risk class (not a hypothetical) comes from the codebase itself: a `SafeExchangeProcessor` was added specifically to replace the floating point path with `BigDecimal` fixed-scale arithmetic and `StrictMathWrapper`, gated behind `getAllowHardenExchangeCalculation()`: [3](#0-2) 

This is only used when `allowHarden()` (i.e. the chain parameter) is enabled: [4](#0-3) 

The existence of a dedicated "hardened" replacement path is direct evidence that the original `ExchangeProcessor` double-based path was recognized as imprecise/unsafe — until the corresponding proposal is activated network-wide, every TRX↔TRC10 exchange swap on the live pools is priced with the unhardened, floating-point implementation, reachable by any unprivileged account broadcasting `ExchangeTransactionContract`.

### Impact Explanation
An attacker who can predict or influence the rounding boundary of `Math.pow`/double truncation in `exchangeToSupply`/`exchangeFromSupply` can craft a sequence of trade sizes (quant values) against a specific pool so that the cumulative `anotherTokenQuant` paid out by `ExchangeCapsule.transaction()` exceeds what a value-conserving curve would allow, extracting real TRX/TRC10 balances from the exchange's reserves at the expense of other liquidity/participants — the same fund-drain impact category as the Osmosis incident (concrete theft of pooled funds via AMM/LP accounting drift), reachable purely by broadcasting ordinary transactions.

### Likelihood Explanation
Likelihood is Medium: exploitation requires the attacker to find and repeatedly hit specific quant values where floating point rounding favors them across the accumulating internal `supply` state — this requires analysis/fuzzing of `Maths.pow` behavior at scale, but no privileged access, and the actuator path (`ExchangeTransactionActuator`) is open to any funded account. The severity is reduced on any network where the `AllowHardenExchangeCalculation` proposal has already been activated, since `SafeExchangeProcessor` is used instead; but the vulnerable `ExchangeProcessor` code remains reachable and is the default until that proposal passes.

### Recommendation
- Enforce `SafeExchangeProcessor` (or an equivalent exact fixed-point implementation) unconditionally for all `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` execution paths, removing the double-based `ExchangeProcessor` code path entirely rather than gating it behind an optional proposal.
- Add an invariant check in `ExchangeCapsule.transaction()` that asserts the product `firstTokenBalance * secondTokenBalance` (or the appropriate bonding-curve invariant) does not decrease beyond a protocol fee tolerance after each swap, rejecting the transaction if violated.
- Audit historical mainnet pool balances for below-expected reserves that would indicate this drift has already been exploited.

### Proof of Concept
1. Attacker creates or locates an active TRX/TRC10 `Exchange` pool where `AllowHardenExchangeCalculation` has not been activated (default `ExchangeProcessor` path in effect).
2. Attacker broadcasts a sequence of `ExchangeTransactionContract` transactions with `quant` values chosen (via off-chain simulation of `Maths.pow`/double truncation behavior in `exchangeToSupply`/`exchangeFromSupply`) so that each truncation in `(long) issuedSupply` / `(long) exchangeBalance` rounds in the attacker's favor.
3. Over many iterations, the attacker's TRX/TRC10 balance increases beyond what a value-conserving curve should allow, while `exchangeCapsule.setBalance(...)` records reserves that are less than the true fair value, draining the pool — mirroring the Osmosis pattern of repeated LP interactions extracting value via AMM accounting drift.   private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);

  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }
