Audit Report

## Title
Native/EVM value sent with `CALL` to a stateless (`HAS_CONTRACT_INFO = false`) `pallet-revive` precompile is permanently locked - ([File: substrate/frame/revive/src/exec.rs])

## Summary
`Stack::run` in `substrate/frame/revive/src/exec.rs` unconditionally transfers `frame.value_transferred` to the destination account via `Self::transfer_from_origin` at L1378-1387 for any non-delegate call, including calls to precompiles with `HAS_CONTRACT_INFO = false` (e.g. `ECRecover`, `Sha256`, `Ripemd160`, `Identity`, `Modexp`, `Bn128Add/Mul/Pairing`, `Blake2F`, and the `System` precompile). Because these addresses have no private key, no `ContractInfo`, and their `call()` implementations never move `value` anywhere, any funds sent to them become permanently unrecoverable.

## Finding Description
In the shared call-frame execution path `Stack::run`, the balance transfer happens before the callee code runs, gated only on `frame.delegate.is_none()`: [1](#0-0) . Immediately after, only precompiles with `has_contract_info() == true` receive account/ED/consumer bookkeeping: [2](#0-1) . Precompiles declared with `const HAS_CONTRACT_INFO: bool = false`, such as `System`, never receive this treatment and their `call()` bodies have no concept of forwarding or refunding `value`: [3](#0-2) . The `Precompile` trait's own documentation states that `HAS_CONTRACT_INFO = false` means "No account or any other state will be created for the address," yet the value transfer still proceeds unconditionally through `transfer_from_origin`: [4](#0-3) .

The repository already recognizes and guards against a closely analogous case — sending non-zero `value` to `RUNTIME_PALLETS_ADDR` — by explicitly rejecting the transaction in `GenericTransaction::into_call`: [5](#0-4) . This guard, however, only covers the single fixed `RUNTIME_PALLETS_ADDR` and does not extend to any other `HAS_CONTRACT_INFO = false` precompile (the classic Ethereum-compatibility precompiles at `0x01`–`0x09`, or third-party stateless precompiles), nor does it apply at the internal `Stack::run`/`transfer_from_origin` level reached via direct PVM `CALL` (as opposed to `eth_call` transaction decoding). The repository's own test confirms the value simply accumulates at the precompile's mapped account with no further handling: [6](#0-5) .

## Impact Explanation
This is a permanent user-fund lock: value sent to a fixed, keyless, codeless precompile address becomes permanently unrecoverable, since there is no account owner who can sign a transaction from that address and no contract code path (no `terminate()`/self-destruct) to redirect the balance. This matches the "permanent user-fund or bridge-state lock" category in the impact gate.

## Likelihood Explanation
The bug is deterministic and reproducible on every `CALL`/`eth_call` with `value > 0` targeting any `HAS_CONTRACT_INFO = false` precompile address. It requires no privileged actor — any unprivileged EOA-mapped account or contract can trigger it via a normal, publicly reachable `eth_call` or PVM low-level `CALL`, matching common EVM tooling patterns that reference fixed precompile addresses like `0x01`–`0x09`.

## Recommendation
Extend the existing `RUNTIME_PALLETS_ADDR` value guard pattern in `substrate/frame/revive/src/evm/call.rs` to reject non-zero `value` for any destination resolving to a `HAS_CONTRACT_INFO = false` precompile, or add an equivalent check in `Stack::run` in `substrate/frame/revive/src/exec.rs` that skips/rejects `transfer_from_origin` when the callee is a stateless precompile, consistent with the documented semantics in `substrate/frame/revive/src/precompiles.rs`.

## Proof of Concept
1. From a contract (or via `eth_call`), issue a low-level `CALL` with `value = N > 0` to `0x0000000000000000000000000000000000000001` (`ECRecover`) with valid ABI-encoded input.
2. Observe the call succeeds, returns the expected output, and `Pallet::<T>::evm_balance(&precompile_addr)` equals `N`, as demonstrated by the existing `pure_precompile_works` test in `substrate/frame/revive/src/tests/pvm.rs` (L4751-4782).
3. Confirm there is no code path (no signer, no `ContractInfo`, no `terminate()`) that can move the `N` balance out of that address — the funds are permanently locked.
