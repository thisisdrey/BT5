### Title
Relay identity spoofing via unauthenticated `RelayFromAddr`/`RelayToAddr` fields in `HandleControlMsg` - (File: relay_manager.go)

### Summary
`relayManager.HandleControlMsg` only checks that `RelayFromAddr`/`RelayToAddr` are non-nil before dispatching to `handleCreateRelayRequest`/`handleCreateRelayResponse` [1](#0-0) . Neither handler verifies that the attacker-supplied `RelayFromAddr` (the identity the message claims to represent) actually matches the authenticated `h.vpnAddrs` of the peer whose already-established, cert-verified tunnel delivered the message [2](#0-1) .

### Finding Description
This mirrors the report's bug class: an identity/"sender" field is taken from message content and used for authorization/state decisions without binding it to the actually-authenticated channel identity. In `CredibleAccountModule.preCheck()`, the `sender` came from `msgData` instead of `msg.sender`. Here, in `handleCreateRelayRequest`, `from := protoAddrToNetAddr(m.RelayFromAddr)` is taken directly from the Control message payload and then used to key relay state (`h.relayState.QueryRelayForByIp(from)`, `AddRelay(rm.l, h, f.hostMap, from, ...)`) without ever checking `from == h.vpnAddrs[0]` [3](#0-2) . The only validation performed upstream is a nil-check on the fields, not an identity check against the authenticated `HostInfo h` that decrypted and delivered the message [4](#0-3) .

Because this is dispatched straight from `readOutsidePackets` after successful decryption over host `hostinfo`'s already-authenticated tunnel (`case header.Control: f.relayManager.HandleControlMsg(hostinfo, out, f)`) [5](#0-4) , any peer holding a valid, currently-established tunnel to the relay node can claim to be relaying "from" an arbitrary VPN address rather than its own certified address, and this claimed identity is trusted for relay state bookkeeping and (via `h.vpnAddrs` used elsewhere / relay routing) traffic forwarding decisions.

### Impact Explanation
Because the relay-from identity is never checked against the certificate-authenticated `h.vpnAddrs`, a connected peer can poison the relay's internal relay-state tables (`h.relayState`) with an address that is not its own, causing the relay to associate/forward traffic under a spoofed identity for that VPN address. This can lead to relay-state corruption and potential relay-based traffic misdirection/impersonation for third parties whose address is falsely claimed in the control message, which is a form of remote state poisoning via the relay data plane.

### Likelihood Explanation
Exploitability requires only that the attacker already be a legitimately certificate-holding peer with an established tunnel to a relay-capable node (`relay.am_relay`) — a normal position for any mesh member, not requiring possession of anyone else's certificate. The Control message path is reached automatically after any successful handshake, and `HandleControlMsg`'s only gate is a nil check on the two address fields, so crafting a message with an arbitrary `RelayFromAddr` is straightforward.

### Recommendation
In `handleCreateRelayRequest` (and correspondingly in `handleCreateRelayResponse`), verify that `from` (the claimed relay-from identity) is contained in `h.vpnAddrs` — the certificate-verified addresses of the HostInfo `h` that delivered the Control message — before using it to create/query relay state, exactly analogous to authorizing the `sender` parameter against `msg.sender` in the referenced report.

### Proof of Concept
1. Peer `A` (valid cert, VPN addr `A_ip`) establishes a normal tunnel to relay-capable node `R` (`relay.am_relay=true`).
2. `A` sends a `Control`/`CreateRelayRequest` message over this tunnel with `RelayFromAddr` set to `V_ip` (the VPN address of an unrelated victim `V`, not `A_ip`) and `RelayToAddr` set to some target `T_ip`.
3. `R` receives it via `readOutsidePackets` → `HandleControlMsg` → `handleCreateRelayRequest`; only a nil-check on `RelayFromAddr`/`RelayToAddr` is performed [4](#0-3) ; there is no check that `V_ip ∈ h.vpnAddrs` (`h` here being `A`'s authenticated HostInfo).
4. `R` creates/updates relay state keyed on `V_ip` as if `V` itself had requested the relay, potentially responding to or routing traffic as if `V` were behind this relay path, based purely on `A`'s forged claim [3](#0-2) .

Note: I could not fully trace every downstream consumer of the poisoned `h.relayState` entry to confirm the full blast radius (e.g., whether this alone allows traffic decryption/forgery for `V_ip`'s traffic versus only causing routing-table corruption/DoS against relay bookkeeping); a Devin session with full repo/build access would be needed to trace `relayState.QueryRelayForByIdx`/`QueryVpnAddrsRelayFor` consumers end-to-end and confirm the precise traffic-level impact.
