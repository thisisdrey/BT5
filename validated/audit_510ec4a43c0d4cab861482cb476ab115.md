### Title
Version-monotonicity equality mismatch between `PeerNetwork::validate_received_chunk` (gossip gate) and `StackerDBTx::try_replace_chunk` (storage gate) allows a stale/duplicate-version chunk to be accepted at the gossip layer but rejected at storage - (File: `stackslib/src/net/stackerdb/mod.rs`)

### Summary
The bug class described in the external report is a mismatch between two supposedly equivalent validation checks performed in different code paths, where one path is a "fast gate" that decides whether to accept/relay data, and the other is the "authoritative" check that decides whether to actually commit it. In `stackslib/src/net/stackerdb`, the same kind of split exists between the gossip-facing gate `PeerNetwork::validate_received_chunk` and the storage-facing gate `StackerDBTx::try_replace_chunk`. The two functions check "is this chunk version fresh enough" using different equalities (`<` vs `<=`), so a chunk that the gossip gate calls valid can be rejected by the storage gate, and the two functions disagree about whether an equal-version resubmission is acceptable.

### Finding Description
`PeerNetwork::validate_received_chunk` (used to decide whether a pushed/downloaded StackerDB chunk should be forwarded/relayed/buffered) treats a chunk as fresh enough as long as it is **not strictly less** than the expected version: [1](#0-0) 

i.e. `data.slot_version == *expected_version` is accepted as valid here.

`StackerDBTx::try_replace_chunk` (the authoritative function that actually writes the chunk into the SQL-backed replica, called both from the RPC POST-chunk handler and eventually to persist replicated chunks) instead requires the version to be **strictly greater** than the currently stored version: [2](#0-1) 

This is the same class of fault as the external report: two code paths that are supposed to agree on "is this chunk acceptable" use different comparison operators (`<` vs `<=`) on the same quantity (slot version), so the pre-check gate and the storage gate disagree on the boundary case where the incoming version equals the currently known version.

I attempted to trace the exact call path that stores chunks obtained from `validate_received_chunk`'s callers (`handle_unsolicited_StackerDBPushChunk` in `stackslib/src/net/stackerdb/mod.rs` and `StackerDBSync::validate_downloaded_chunk` in `stackslib/src/net/stackerdb/sync.rs`) through to `stackslib/src/net/relay.rs`, to confirm whether the actual persistence step for gossiped/downloaded chunks calls `try_replace_chunk` (with its stricter `<=` rule) or a different insertion routine. I was not able to fully confirm this within the available tool budget — `stackslib/src/net/relay.rs` references `chunks_to_store`/`try_replace_chunk`, but I could not read those specific line ranges to verify the exact comparison used for the final commit versus the `validate_received_chunk` gate. Given the indexing limits noted for this task, I recommend a Devin session with full repo access to confirm the final storage call site if a more precise PoC is required.

### Impact Explanation
If the persistence path for gossiped/downloaded chunks indeed relies on the `<=`-based `try_replace_chunk` semantics (or a comparable strict check) while the gossip/relay decision (`validate_received_chunk`) uses the more permissive `<` rule, a chunk at exactly the currently-stored version would be accepted for relay/buffering (and the peer's chunk inventory would be optimistically updated, per `handle_unsolicited_StackerDBPushChunk`'s inventory-patch logic) but then rejected at storage time as a `StaleChunk`. This would create a durable mismatch between a node's advertised inventory (`slot_versions`) and what is actually stored, which other peers rely on as canonical to decide what to fetch — i.e., serving/advertising non-canonical state (an inventory entry with no backing chunk) as canonical. This matches the "High" impact bucket (steering peers based on false inventory) called out in scope.

### Likelihood Explanation
This requires no privileged access — a remote, unauthenticated (`allowed = -1` peers are permitted per test scaffolding) attacker who is already an authorized StackerDB slot signer (or a MITM-relayed message from one) can resubmit the exact same-version chunk it previously wrote. Because `validate_received_chunk` accepts version-equal resubmissions but downstream storage enforces strict-increase, the mismatch is deterministically reachable, not merely theoretical, though I could not fully confirm the exact downstream commit function within the available exploration budget.

### Recommendation
Align the version-freshness comparison used in `PeerNetwork::validate_received_chunk` (`stackslib/src/net/stackerdb/mod.rs:699-706`) with the one enforced by `StackerDBTx::try_replace_chunk` (`stackslib/src/net/stackerdb/db.rs:424-429`) — i.e., make both reject `data.slot_version <= expected/stored_version` (or both accept `==`), so the gossip/relay gate and the storage gate always agree on acceptance before a chunk is advertised in inventory or buffered for peers.

### Proof of Concept
1. As an authorized signer for slot `S` in StackerDB contract `C`, publish chunk version `V` (accepted and stored).
2. Re-send (push) the identical chunk with `slot_version = V` again to a peer.
3. `PeerNetwork::validate_received_chunk` evaluates `data.slot_version(V) < expected_version(V)` → `false`, so the freshness check passes and the chunk is treated as valid; in `handle_unsolicited_StackerDBPushChunk` the peer's advertised `slot_versions` entry is patched to `V` and the sync state machine is woken to fetch/store it.
4. When the actual write is attempted through `StackerDBTx::try_replace_chunk`, the check `slot_desc.slot_version(V) <= slot_validation.version(V)` → `true`, causing `Err(net_error::StaleChunk)` and the storage write to be rejected.
5. Net effect: the node's chunk inventory reflects version `V` as freshly obtained/valid while the underlying replica's actual stored data was never re-committed via that path — a rejected-at-storage but accepted-at-gossip inconsistency, mirroring the “accept in one validator, reject in the other” structure of the referenced report. (Full confirmation of the exact downstream commit call requires further inspection of `stackslib/src/net/relay.rs`, which I was unable to complete.)
