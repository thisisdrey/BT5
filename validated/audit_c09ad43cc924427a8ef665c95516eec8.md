### Title
Unsolicited StackerDB chunk pushes are advertised as accepted before storage succeeds, letting served inventory diverge from committed chunk state - (File: stackslib/src/net/stackerdb/mod.rs)

### Summary
The Lyra `canHedge` bug is a case where a cheap, partial check (sign only) is treated as proof of the real invariant (risk reduced), letting the caller act on an assumption that is not actually guaranteed. The closest reachable analog in this repo's StackerDB code is `PeerNetwork::handle_unsolicited_StackerDBPushChunk`, which treats passing the lightweight `validate_received_chunk` check as proof that a pushed chunk is (or will be) durably stored, and immediately advertises the new, higher slot version in the `StackerDBChunkInv` reply sent back to the pusher — before the chunk has actually been committed via `StackerDBTx::try_replace_chunk`.

### Finding Description
`validate_received_chunk` (`stackslib/src/net/stackerdb/mod.rs:649-718`) only checks chunk size, signer identity/signature, that the version is not stale (`data.slot_version < *expected_version` — note: strictly-less, not less-or-equal), and that it does not exceed `max_writes`. It does **not** perform, or wait on, the actual database write. [1](#0-0) 

In `handle_unsolicited_StackerDBPushChunk` (`stackslib/src/net/stackerdb/mod.rs:742-870`), once `validate_received_chunk` returns `true` for the `StackerDBChunkInv` branch, the code immediately patches the in-memory inventory vector that is about to be sent back to the peer, setting the slot's advertised version to the *pushed* version, and only afterwards defers actual persistence to the relay layer (`return Ok((false, true))`, meaning "forward to relayer" for real storage via `try_replace_chunk`): [2](#0-1) 

The actual write path is `StackerDBTx::try_replace_chunk` (`stackslib/src/net/stackerdb/db.rs:400-438`), which is stricter: it rejects `slot_version <= slot_validation.version` as stale (not just `<`) and can otherwise fail (signer mismatch, size, `max_writes`, or a plain DB error). This creates two different acceptance conditions for the "same" chunk: [3](#0-2) 

Because `validate_received_chunk` is only a proxy for "this chunk is plausible", not "this chunk is now committed," the reply already asserts the new version to the network before the deferred `try_replace_chunk` call (performed later by the relay/event-dispatch path, e.g. as in `PeerNetwork::process_stacker_db_chunks` at `stackslib/src/net/relay.rs:2385-2467`) has run. If that later write does not happen or fails — e.g., a concurrent write to the same slot lands first and makes this version stale by the time `try_replace_chunk` runs, or a transient DB error occurs — the node has already told the pushing peer "I have version N," while its committed store may still be at an older version. This is the "served vs. committed" equality break called out in the review rules: the inventory *served* in the immediate reply is not guaranteed to equal the state actually *committed* to the StackerDB.

### Impact Explanation
This does not allow unauthenticated writes or forged data (both the signature and expected-version checks in `validate_received_chunk` are real and match `try_replace_chunk`'s core `verify()` and freshness checks). The consequence is instead a false/non-canonical inventory being served as canonical: peers that rely on this node's `StackerDBChunkInv` reply to decide whether they still need to push or fetch a given slot version may wrongly conclude the data is already replicated here, delaying or preventing legitimate re-propagation of that chunk. This matches the "serving non-canonical state as canonical" / "false inventory" class named in the rubric, but the blast radius is narrower than a tip-steering bug: it affects StackerDB chunk replication liveness/consistency, not consensus state, and self-corrects on the node's next real inventory computation (`make_StackerDBChunksInv_or_Nack`, which reads live from `self.stackerdbs.get_slot_versions`). I could not fully trace, within the available context, the exact scheduling guarantee for when the deferred `try_replace_chunk` runs relative to the reply being flushed, so I can't confirm how often (if ever) the discrepancy is actually observable versus always resolving by the time any peer re-queries.

### Likelihood Explanation
Triggering the discrepancy requires only sending a validly-signed `StackerDBPushChunkData` for a slot the attacker (as the legitimate slot owner) controls, which is a normal, low-cost, unauthenticated-network action; no privileged role is needed to attempt the push. However, actually causing the deferred store to diverge from the advertised value requires a race (e.g., another write landing first) or a transient DB failure, which is not fully attacker-controlled and may be hard to reliably reproduce or weaponize into a durable disruption.

### Recommendation
Only patch and advertise the slot's version in the immediate `StackerDBChunkInv` reply after the corresponding `try_replace_chunk` call has actually succeeded (or defer sending the reply until the relay-layer storage attempt completes), so that the version reported to peers is always backed by the local store's committed state.

### Proof of Concept
Conceptual PoC (not independently executed against a running node in this session):
1. Register as the legitimate signer for a StackerDB slot and connect as a peer.
2. Send an unsolicited `StackerDBPushChunk` with a validly-signed chunk whose `slot_version` is one greater than the node's current expected version (passes `validate_received_chunk`).
3. Simultaneously (or via a second connection) send another validly-signed chunk for the same slot at an even higher version, so that when the relay layer eventually calls `try_replace_chunk` for the first push, it is rejected as `StaleChunk` because the second push's write landed first.
4. Observe that the immediate `StackerDBChunkInv` reply to the first push already advertised the first push's version as accepted, even though the local store never actually committed that intermediate version — demonstrating the served/committed divergence.

I was not able to execute this scenario against a live node within this session; the analysis is based purely on static code reading of `stackslib/src/net/stackerdb/mod.rs`, `stackslib/src/net/stackerdb/db.rs`, and `stackslib/src/net/relay.rs`.
