### Title
Unauthenticated event injection into the signer's HTTP event receiver allows forged StackerDB/block-validation data to be trusted - (File: libsigner/src/events.rs)

### Summary
The `SignerEventReceiver::next_event` handler in `libsigner/src/events.rs`, which accepts HTTP POSTs on the signer's bound event-listener port (`/stackerdb_chunks`, `/proposal_response`, `/new_burn_block`, `/new_block`), performs no authentication check on incoming requests. `decode_http_request` in `libsigner/src/http.rs` parses verb/path/headers but never validates any credential (no `auth_token`/`auth_password` comparison), unlike the node-side RPC endpoints (e.g. `stackslib/src/net/api/postblock_proposal.rs`) which do enforce an `auth_token` check. This breaks the intended equality "message came from the trusted local node" vs. "message came from any reachable TCP client."

### Finding Description
`SignerEventReceiver::next_event()` (`libsigner/src/events.rs:413-459`) dispatches based solely on the request's HTTP path, calling `process_event::<T, StackerDBChunksEvent>`, `process_event::<T, BlockValidateResponse>`, `process_event::<T, BurnBlockEvent>`, or `process_event::<T, StacksBlockEvent>` (`libsigner/src/events.rs:511-542`). None of these paths examine an `Authorization` header or any shared secret before deserializing and forwarding the JSON body as a trusted `SignerEvent`. `decode_http_request` (`libsigner/src/http.rs:61-123`) likewise only extracts verb/path/headers into a map — it never checks header values against a configured secret.

By contrast, the node's own protected RPC surface (`stackslib/src/net/api/postblock_proposal.rs`) does check an `auth_token` before honoring privileged requests, and the documentation (`docs/signing.md`, `sample/conf/mainnet-miner-conf.toml`) describes `auth_token`/`auth_password` as the mechanism meant to secure signer↔node communication. That mechanism, however, is enforced only when the *node* validates inbound RPC calls; the *signer's* event-receiving HTTP server has no matching check for inbound POSTs it receives. Since the sample configs bind the signer's event endpoint to `0.0.0.0:<port>` (see `sample/conf/mainnet-miner-conf.toml:434-436`, `docs/signing.md:44-49`), any host that can reach that port can POST a forged `stackerdb_chunks`/`proposal_response`/`new_burn_block`/`new_block` payload, and the signer will decode and forward it into its runloop as if it were emitted by the trusted node.

### Impact Explanation
This breaks the equality "event originated from the operator's own trusted node" vs. "event originated from an arbitrary network peer." An attacker with network reachability to the signer's event port can inject forged `StackerDBChunksEvent`/`BlockValidateResponse`/burn-block/new-block payloads that the signer's runloop will process as legitimate node-sourced state, without needing the node's private key or any credential. This matches the "unauthenticated/unauthorized write to state" and "forged-data propagation" impact categories in scope.

### Likelihood Explanation
Likelihood depends entirely on network exposure of the signer's event-receiver port. Where operators bind it to `0.0.0.0` (as several sample configs illustrate) or otherwise expose it beyond loopback/VPN, the vulnerability is directly remotely reachable with a single crafted HTTP POST — no authentication, no valid signature, and no special privileges are required to reach `next_event()`'s dispatch logic.

### Recommendation
Add a mandatory shared-secret check in `SignerEventReceiver::next_event` (or in `decode_http_request`) that validates a header (e.g., `Authorization` or `X-Auth-Token`) against the signer's configured secret before dispatching to `process_event`, mirroring the check already performed on the node's protected RPC endpoints such as `postblock_proposal.rs`. Reject and drop any request lacking a valid token, and document/require binding the event-receiver socket to a private interface as a defense-in-depth measure, not as the sole control.

### Proof of Concept
1. Configure a signer with its event endpoint reachable from the network (per `sample/conf/mainnet-miner-conf.toml`, e.g. `endpoint = "0.0.0.0:30000"`).
2. From an unauthenticated remote host, send:
   ```
   POST /stackerdb_chunks HTTP/1.1
   Host: <signer-ip>:30000
   Content-Type: application/json
   Content-Length: <n>

   { ...forged StackerDBChunksEvent JSON... }
   ```
3. `SignerEventReceiver::next_event` matches `request.url() == "/stackerdb_chunks"` and calls `process_event::<T, StackerDBChunksEvent>(request)` (`libsigner/src/events.rs:437-438`) without any credential check, deserializing and forwarding the attacker-controlled payload into the signer's `SignerEvent` channel, which the signer runloop (e.g., `stacks-node/src/nakamoto_node/stackerdb_listener.rs`) then treats as node-originated.

**Note on uncertainty:** I was unable to fully rule out that an authentication check exists further downstream (e.g. inside `SignerEvent::try_from` conversions or in the node-runloop consumer) that rejects unauthenticated/unsigned event content before it has any effect; my search of `libsigner/**` found no `auth`/`Authorization` references outside test files, which supports the finding, but I could not exhaustively review every consumer of `SignerEvent` within the time available.
