## Title
Fetch failure misclassified via stderr heuristic leads to migration of unverified quarantined objects - (File: `internal/gitaly/service/repository/fetch_remote.go`)

### Summary
`fetchRemoteAtomic` in `internal/gitaly/service/repository/fetch_remote.go` does not properly validate the return status of the `git-fetch(1)` external process invocation. Instead of checking a well-defined signal (e.g. exit code categories or explicit "partial failure" markers from Git), it uses a fragile heuristic — an empty `stderr` buffer combined with the literal string `"exit status 1"` — to decide whether a failing fetch is a benign, partial reference-update failure that can be safely ignored, or a real failure that must abort the operation.

### Finding Description
In `fetchRemoteAtomic`, after invoking `quarantineRepo.FetchRemote(ctx, "inmemory", opts)`: [1](#0-0) 

the code inspects `err.Error()` for the *exact string* `"exit status 1"` and `stderr.String()` for emptiness to decide that the underlying `git-fetch` failure is only due to some reference updates being rejected (which is expected and handled later by `git-update-ref`), and therefore continues execution rather than aborting. This is effectively an unchecked/ improperly interpreted return-value pattern: the actual outcome of the external `git-fetch` process (whether objects were fully and correctly received) is not verified through a reliable mechanism — it's guessed from a coincidental combination of exit code and absent stderr output.

Any `git-fetch` failure mode that:
- returns exit status 1 (a very common, generic Git exit code for many failure classes: network interruption, malformed pack, partial data transfer, disk write errors, connection reset, timeouts truncated before Git could print to stderr), and
- happens to produce no stderr output (e.g., process killed, output buffering/flush race, or truncated connection before the error message is written)

will be silently treated as "some refs were rejected, but fetched objects are fine," and control flow proceeds to:
1. Parse `stdout` porcelain output for ref updates,
2. `quarantineDir.Migrate(ctx)` — migrating potentially incomplete or corrupted quarantined pack/loose objects into the *main, non-quarantined* object database,
3. `refUpdater.Commit()` — applying the reference updates. [2](#0-1) 

Because objects are migrated out of quarantine (`quarantineDir.Migrate`) based on this unreliable success signal, an interrupted/corrupted fetch (triggerable by a remote controlled by the requester via `RemoteParams.Url`, or naturally occurring under network instability/timeouts) can result in partially-received or corrupted object data being merged into the durable, non-quarantined repository object store, and reference updates being committed against that state.

### Impact Explanation
This is analogous to the AAVE finding: an external operation's return/exit status is not robustly checked, causing the caller to assume success (or an acceptable partial failure) and proceed to commit an irreversible action — migrating quarantined objects into the live repository and updating references. In Gitaly's case, misclassification of a genuine fetch failure as benign can corrupt the target repository's object database (missing/incomplete objects reachable from newly committed refs), producing repository corruption and potential availability impact (subsequent operations against dangling/missing objects will fail, requiring housekeeping/fsck intervention as described in `internal/git/objectpool/disconnect.go`'s connectivity-check design used elsewhere in the codebase for similar migrate operations).

### Likelihood Explanation
`FetchRemote` is reachable through an ordinary mutator RPC where the caller supplies `RemoteParams.Url` (and optionally SSH key/known hosts), i.e. the fetch target is attacker/operator-influenced. Any interruption of the fetch stream (a controlled remote endpoint that resets the connection mid-transfer, or exploits Git's generic exit-status-1 behavior for various failure modes) can produce exactly the exit-status-1-with-empty-stderr condition, without requiring a privileged actor or MITM — a slow/flaky/malicious HTTP or SSH remote is sufficient to trigger this condition through normal, unprivileged use of the `FetchRemote` RPC.

### Recommendation
Do not infer fetch success/partial-failure solely from `err.Error() == "exit status 1"` combined with empty stderr. Instead:
- Use Git's structured output (the porcelain fetch report already parsed via `gitcmd.NewFetchPorcelainScanner`) to determine exactly which refs failed and confirm that the *only* failure category is `RefUpdateTypeUpdateFailed`, rather than assuming this based on exit code/stderr heuristics.
- Alternatively, perform an explicit connectivity/consistency check (as already done in `internal/git/objectpool/disconnect.go`'s `removeAlternatesIfOk`, which runs `git rev-list --objects --all` before committing an irreversible action) on the quarantined objects before calling `quarantineDir.Migrate`, aborting and rolling back the quarantine if the check fails.
- Treat any non-nil `err` from `FetchRemote` combined with ambiguous signals conservatively (fail closed) rather than proceeding to migrate and commit.

### Proof of Concept
1. Set up a remote HTTP/SSH endpoint that streams a valid ref-advertisement but then abruptly resets the TCP connection partway through the packfile transfer, before Git has a chance to write a diagnostic message to stderr, such that the git-fetch child process exits with status 1 and empty stderr (achievable by killing the server process mid-negotiation, or using a proxy that resets after N bytes).
2. Call `FetchRemote` RPC against a Gitaly repository with `RemoteParams.Url` pointing at this endpoint.
3. Observe that `fetchRemoteAtomic` takes the "assume benign partial failure" branch at lines 110-121 of `internal/gitaly/service/repository/fetch_remote.go`, proceeds to `quarantineDir.Migrate(ctx)` and `refUpdater.Commit()`, and returns success/failure inconsistent with the actual (corrupted/incomplete) fetch outcome, leaving the repository with partially migrated objects and updated references pointing at objects that may be incomplete.

			return false, false, structerr.NewInternal("fetch remote: %q: %w", errMsg, err)
		}

		// Some errors during the `git-fetch(1)` operation do not print to stderr. If the error
		// message is not `exit status 1`, it is determined that the error is unrelated to failed
		// reference updates and the operation halts. Otherwise, it is assumed the error is from a
		// failed reference update and the operation proceeds to update references.
		if err.Error() != "exit status 1" {
			return false, false, structerr.NewInternal("fetch remote: %w", err)
		}
