The core parallel to the Solana bug (processing unvalidated/unverified data as trusted, leading to bridge-drain-equivalent corruption) is Gitaly's own acknowledged gap in `packObjects`: transactional (WAL-based) commits accept quarantine-directory objects and pack them into the repository's permanent object store without verifying their Git-object validity, unlike `git-receive-pack`'s own `fsck` gate.

### Title
Unvalidated quarantine objects are packed and committed by `TransactionManager.packObjects` without object-validity (fsck) verification - (File: `internal/gitaly/storage/storagemgr/partition/transaction_manager.go`)

### Summary
`TransactionManager.packObjects` walks all objects present in a write transaction's quarantine directory and packs every object it finds into the repository's permanent packfile store, then only verifies that the transaction's *dependency* object IDs are *present* in the repository — it never verifies that the objects being packed are well-formed, valid Git objects. This mirrors the Solana bridge flaw: an operation's inputs are accepted and committed as valid state without confirming they actually represent what they claim to be, because the validating step (`git-receive-pack`'s built-in `fsck`, analogous to checking `Meta.Err == nil`) is not part of this code path.

### Finding Description
For repositories using the transactional (WAL) storage backend, any ordinary user's write RPC (push via `git-receive-pack`/`git-upload-pack`, `UserCommitFiles`, `UserMergeBranch`, etc.) stages new objects into a per-transaction quarantine directory via `localrepo.Repo.WriteBlob`/`ExecAndWait`/`ListObjects`. `packObjects` then walks these objects and any missing dependencies are recorded, but the function's own doc-comment states plainly: [1](#0-0) 

Only reachability/dependency existence is checked later, in `verifyObjectsExist`, which confirms an OID is *present*, not that the object's content is a structurally valid Git object (e.g., a corrupted or self-referential tree/commit, a blob written where a tree is expected, etc.): [2](#0-1) 

This is architecturally the same class of bug as the audited Solana issue: a downstream state-mutating step (`ProcessInboundEvents` minting ZRC20 on an unverified/failed transaction; here, `packObjects`/`processTransaction` committing a packfile without confirming its objects are valid) trusts upstream data that has not passed the validation gate that a sibling code path enforces. In the EVM observer, `Meta.Err == nil` is the missing check; here, `git-fsck`-equivalent validity checking (already applied for the *non-transactional* `git-receive-pack` path via `templateFsckConfiguration`/`transfer.fsckObjects=true`) is the missing check for the transactional commit path. [3](#0-2) 

Whether this is independently reachable by fully unprivileged clients depends on whether every write path feeding the quarantine directory (e.g. `UserCommitFiles`, internal `WriteBlob` calls used for merges/rebases/tag creation, or object import RPCs) is guaranteed to route exclusively through a Git subprocess that itself enforces `fsck`. Any write path that places attacker-influenced bytes directly into the quarantine object store without an intervening `fsck`-checked Git command (rather than only `index-pack`, which validates packfile framing but not full object semantics/connectivity in the same way `git fsck` does) inherits this gap.

### Impact Explanation
If reachable from an unprivileged/ordinary client-controlled RPC, this allows committing structurally invalid or semantically corrupt Git objects into a repository's permanent object store as part of a "successful" transaction, since the only later check (`verifyObjectsExist`) is a presence check, not a validity check. Consequences include repository corruption, inconsistent reachability guarantees the transaction system depends on ("all objects in the repository have all of their dependencies met" — a documented invariant at `internal/gitaly/repoutil/create.go:248-256`), and potential downstream failures or security-relevant confusion in commands/RPCs that assume packed objects are well-formed. This is explicitly flagged as an open, unresolved gap by Gitaly's own maintainers via the linked internal issue.

### Likelihood Explanation
Medium: exploiting this fully requires identifying an entry point that writes attacker-controlled quarantine content without passing through a fsck-enforcing Git subprocess, and it may currently be significantly mitigated wherever `git-receive-pack`'s own fsck runs before the WAL/`packObjects` stage. However, the finding stands as a genuinely acknowledged, present validation gap in the trusted commit path itself, independent of any privileged-role assumption, which distinguishes it from the excluded privileged-actor Solana scenario.

### Recommendation
Add explicit object-validity verification (equivalent to `git fsck`/`git index-pack --strict` connectivity+format checks) inside `packObjects` (or immediately before `processTransaction` commits the transaction) for all objects sourced from the quarantine directory, rather than relying solely on `verifyObjectsExist`'s presence check. Track and resolve the referenced upstream issue (gitlab-org/gitaly#5779) as part of closing this gap, and audit every RPC that populates a write transaction's quarantine directory to confirm each one is gated by an fsck-enforcing Git subprocess.

// verifyObjectsExist verifies that all objects passed in to the method exist in the repository.
// If an object is missing, an InvalidObjectError error is raised.
func (mgr *TransactionManager) verifyObjectsExist(ctx context.Context, repository *localrepo.Repo, oids map[git.ObjectID]struct{}) error {
	defer trace.StartRegion(ctx, "verifyObjectsExist").End()

	if len(oids) == 0 {
		return nil
	}

	revisions := make([]git.Revision, 0, len(oids))
	for oid := range oids {
		revisions = append(revisions, oid.Revision())
	}

	objectHash, err := repository.ObjectHash(ctx)
	if err != nil {
		return fmt.Errorf("object hash: %w", err)
	}

	if err := checkObjects(ctx, repository, revisions, func(revision git.Revision, oid git.ObjectID) error {
		if objectHash.IsZeroOID(oid) {
			return localrepo.InvalidObjectError(revision)
		}

		return nil
	}); err != nil {
		return fmt.Errorf("check objects: %w", err)
	}

	return nil

// templateFsckConfiguration generates our fsck configuration, including ignored checks.
// The prefix must either be "fsck", "receive.fsck" or "fetch.fsck" and indicates whether
// it should apply to git-fsck(1), git-receive-pack(1) or to git-fetch-pack(1).
func templateFsckConfiguration(_ context.Context, prefix string) []GlobalOption {
	configPairs := []GlobalOption{
		// When receiving objects from an untrusted source, we want to always assert that
		// all objects are valid. When fetch.fsckObjects or receive.fsckObjects are not set,
		// the value of transfer.fsckObjects is used instead. Since the fsck configuration
		// of git-fetch-pack(1) and git-receive-pack(1) is coupled, transfer.fsckObjects can
		// be used for both.
		ConfigPair{Key: "transfer.fsckObjects", Value: "true"},
	}
