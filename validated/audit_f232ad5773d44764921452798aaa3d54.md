### Title
Voter reward permanently stuck when a Super Representative's total cycle vote is zero - ([File: chainbase/src/main/java/org/tron/core/service/MortgageService.java])

### Summary
`MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)` guards against a division by zero when computing a voter's share of a witness's cycle reward by skipping the calculation entirely if `totalVote == 0` (or `REMARK`). This is the same anti-pattern described in the report: a defensive zero-check that avoids the crash but silently drops the funds instead of accounting for them, leaving already-collected value permanently unclaimable by anyone.

### Finding Description
Block/transaction-fee rewards for a witness are recorded per-cycle via `payReward()`, which is fed by `payBlockReward()` and `payTransactionFeeReward()`: [1](#0-0) 

For the transaction-fee case, the paid amount is first subtracted from the real, previously-collected `TransactionFeePool` balance in `Manager.payReward`, then handed to `mortgageService.payTransactionFeeReward`, which stores it as an entitlement for that cycle/witness via `delegationStore.addReward(cycle, witnessAddress, value)`: [2](#0-1) 

When a voter later calls `withdrawReward`/`queryReward` (reachable from user-broadcast transactions such as `WithdrawBalanceContract`, `VoteWitnessContract`, `UnfreezeBalanceContract`, `UnfreezeBalanceV2Contract`), the old-algorithm path computes each voter's share of that recorded reward proportionally to their vote weight: [3](#0-2) 

The critical guard is:
```java
long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
if (totalVote == DelegationStore.REMARK || totalVote == 0) {
  continue;
}
```
This mirrors exactly the EscrowedToken pattern: `if (totalVesting > 0) { ratePerToken += ... }` — a check added purely to prevent `voteRate = userVote / totalVote` from dividing by zero. But once the reward for that cycle/witness has been recorded via `delegationStore.addReward` (and, in the transaction-fee case, has already been debited from the real `TransactionFeePool`), there is no other code path that later re-attributes or refunds that value. If `totalVote` for that srAddress in that cycle is `0` (e.g., a witness temporarily has no active voters recorded for that cycle, which the delegation-vote snapshot mechanism can produce), the recorded reward amount is simply skipped forever: no voter is ever credited via `adjustAllowance`, and the value is never returned to the `TransactionFeePool` or any other recoverable location.

### Impact Explanation
This causes real, previously-collected TRX (deducted from the `TransactionFeePool`, which is backed by user-paid transaction fees) to become permanently unclaimable — functionally identical to "stuck escrowed funds" in the reported vulnerability class: the value was already removed from the pool that should back it, but no account is ever credited for it, and no recovery mechanism exists. This is a permanent freezing/loss of funds bug reachable purely through the normal reward accounting flow triggered by ordinary user transactions (voting, unfreezing, or withdrawing rewards), without any privileged access needed.

### Likelihood Explanation
The trigger condition — a witness having `totalVote == 0` for a given cycle while still accruing block/fee rewards for that cycle — can occur naturally through the delegation lifecycle (e.g., a witness's vote snapshot briefly reads back as `REMARK`/`0` due to timing of `doMaintenance()` cycle transitions versus reward accrual), and is not something requiring a malicious actor with special privileges; it's an emergent state of the existing DPoS reward bookkeeping reachable by legitimate voting/unfreezing activity from any account. Because `computeReward` is only invoked lazily upon `withdrawReward`/`queryReward`, the condition can persist and repeat across many cycles before being observed.

### Recommendation
When `totalVote == 0` (or `REMARK`) is encountered for a cycle/witness that has a nonzero recorded reward, the reward value should not simply be dropped. Instead, either:
1. Redirect the un-attributable reward back into the `TransactionFeePool` (or an equivalent recoverable pool) instead of silently discarding it in `computeReward`, or
2. Track such orphaned rewards in a separate accounting entry (analogous to the report's `unclaimableFunds` variable) that the committee/governance can recover or redistribute, ensuring the value removed from `TransactionFeePool` is never permanently lost without a path to recovery.

### Proof of Concept
Conceptual scenario (mirrors the report's PoC structure):
1. A witness receives a transaction-fee reward for `cycle N`, causing `Manager.payReward` to deduct `transactionFeeReward` from `TransactionFeePool` and call `mortgageService.payTransactionFeeReward(witnessAddress, transactionFeeReward)`, which stores it via `delegationStore.addReward(N, witnessAddress, value)`.
2. At the same cycle boundary, due to snapshot timing in `MaintenanceManager.doMaintenance()`/`DelegationStore.setWitnessVote`, `delegationStore.getWitnessVote(N, witnessAddress)` returns `0` (or `DelegationStore.REMARK`).
3. Any voter who previously voted for that witness calls `withdrawReward` (e.g., by broadcasting `WithdrawBalanceContract`); `computeReward(N, votes)` hits the `totalVote == 0` branch and `continue`s, contributing `0` to `reward` for that cycle.
4. `TransactionFeePool` has already been permanently decremented by `transactionFeeReward` in step 1, yet no account's `allowance` is ever increased by that amount — the value is unrecoverably lost from system-tracked balances. [3](#0-2) [2](#0-1)

```java
  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
```
