### Title
Unbounded item count in `MicroblocksData::consensus_deserialize` enables bounded compute-DoS via oversized microblock vector - (File: stackslib/src/net/codec.rs)

### Summary
`MicroblocksData::consensus_deserialize` reads `microblocks: Vec<StacksMicroblock>` using a bare `read_next` inside a `BoundReader` capped only at `MAX_MESSAGE_LEN`, with no explicit per-item count cap analogous to `BLOCKS_PUSHED_MAX` used for `BlocksData`. A remote, already-handshaked peer can therefore submit a single ~`MAX_MESSAGE_LEN`-sized `MicroblocksData` payload packed with the maximum number of minimal-size `StacksMicroblock` entries, forcing the node to allocate and validate a much larger number of microblock structs per message than the analogous `BlocksData` path permits.

### Finding Description
`BlocksData::consensus_deserialize` explicitly bounds the number of deserialized items via `read_next_at_most::<_, BlocksDatum>(&mut bound_read, BLOCKS_PUSHED_MAX)` [1](#0-0) . In contrast, `MicroblocksData::consensus_deserialize` only wraps the reader in a `BoundReader::from_reader(fd, MAX_MESSAGE_LEN as u64)` and then calls plain `read_next(&mut bound_read)` for the `Vec<StacksMicroblock>`, with no `read_next_at_most` / item-count cap at all [2](#0-1) . This is a real asymmetry in the codec: one sibling message type (`BlocksData`) enforces a dedicated max-item-count constant, the other (`MicroblocksData`) enforces only a total-byte cap. Because the per-item minimum size of `StacksMicroblock` (header + empty tx vector) is small relative to `MAX_MESSAGE_LEN`, a single wire message can pack a large number of minimal microblock structs, each of which the node must fully deserialize into memory as part of one `consensus_deserialize` call before any content-level validation happens.

### Impact Explanation
This does not allow unbounded memory/compute — `MAX_MESSAGE_LEN` still caps the total payload size, and the resulting allocation is bounded by `MAX_MESSAGE_LEN` bytes worth of `StacksMicroblock` structs, not infinite. However, compared to the deliberately-capped `BlocksData` path (`BLOCKS_PUSHED_MAX`), the microblocks path allows an attacker to maximize the number of items-per-byte, and thus per-item processing (allocation + downstream signature/hash validation once relayed to `relay.rs`) overhead relative to bytes sent, for a single message from any peer that has completed handshake. This matches the "bounded compute DoS on a read endpoint" category — it is a resource-amplification issue bounded by `MAX_MESSAGE_LEN`, not a crash or state-corruption bug.

### Likelihood Explanation
The precondition is only a completed P2P handshake, which any unprivileged remote peer can establish. No StackerDB slot ownership, RPC secret, or privileged role is needed. The attack is trivially repeatable — the attacker can resend such maximal-item-count messages continuously.

### Recommendation
Add an explicit maximum item-count constant (e.g., `MICROBLOCKS_PUSHED_MAX`) analogous to `BLOCKS_PUSHED_MAX`, and use `read_next_at_most::<_, StacksMicroblock>(&mut bound_read, MICROBLOCKS_PUSHED_MAX)` in `MicroblocksData::consensus_deserialize` instead of the unbounded `read_next`.

### Proof of Concept
In `stackslib/src/net/codec.rs` tests: construct a byte buffer consisting of a valid `StacksBlockId` (32 bytes) followed by a `Vec<StacksMicroblock>` length prefix set to a large count, and repeated minimal `StacksMicroblock` encodings (minimal header + empty tx vec) filling the buffer up to just under `MAX_MESSAGE_LEN`. Call `MicroblocksData::consensus_deserialize` on this buffer and assert that `result.unwrap().microblocks.len()` is far larger than `BLOCKS_PUSHED_MAX`, demonstrating the missing per-item cap relative to the `BlocksData` sibling path.
