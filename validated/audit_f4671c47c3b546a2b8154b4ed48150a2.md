### Title
Rewards accrued while a DepositToken/DebtToken has zero supply are permanently lost because `_updateTokenIndex` still advances the timestamp - (File: contracts/RewardsDistributor.sol)

### Summary
`RewardsDistributor` accrues a per-token reward index based on elapsed time × `tokenSpeeds[token]`. In `_calculateTokenIndex`, when `token_.totalSupply() == 0` the accrual ratio is set to 0 but `_newTimestamp` is still set to `block.timestamp`, and `_updateTokenIndex` persists that timestamp. Every second a reward-enabled token has zero supply, its emitted rewards are permanently burned. Because `updateBeforeMintOrBurn` is invoked *before* `_mint` increases `totalSupply`, the very first deposit after speed activation lands on `totalSupply == 0` and wipes out all rewards accumulated since registration — a guaranteed loss for every reward token, identical in mechanism to BlueberryStaking M-03.

### Finding Description
The index update path:

`contracts/RewardsDistributor.sol:197-212`

```solidity
function _calculateTokenIndex(
    TokenState memory _supplyState,
    IERC20 token_
) private view returns (uint224 _newIndex, uint32 _newTimestamp) {
    uint256 _speed = tokenSpeeds[token_];
    uint256 _deltaTimestamps = block.timestamp - uint256(_supplyState.timestamp);
    if (_deltaTimestamps > 0 && _speed > 0) {
        uint256 _totalSupply = token_.totalSupply();
        uint256 _tokensAccrued = _deltaTimestamps * _speed;
        uint256 _ratio = _totalSupply > 0 ? _tokensAccrued.wadDiv(_totalSupply) : 0;
        _newIndex = (_supplyState.index + _ratio).toUint224();
        _newTimestamp = block.timestamp.toUint32();   // <-- advances even when _ratio == 0
    }
    ...
}
```

`contracts/RewardsDistributor.sol:271-282` — `_updateTokenIndex` stores `_newTimestamp` unconditionally when `_newTimestamp > 0`, even if `_newIndex` is unchanged.

Trigger path: `DepositToken._mint` is decorated with `updateRewardsBeforeMintOrBurn(account_)` (`contracts/DepositToken.sol:469-472`), whose modifier calls `IRewardsDistributor(...).updateBeforeMintOrBurn(this, account_)` (`contracts/DepositToken.sol:124-131`) *before* `totalSupply += amount_` executes at line 475. The same pattern applies to `DebtToken` mint/issue and to `updateBeforeMintOrBurn` itself, which is permissionless ("This function also may be called by anyone", line 173).

Additionally, `_updateTokenSpeed` initializes `tokenStates[token_] = TokenState({index: INITIAL_INDEX, timestamp: block.timestamp...})` (`contracts/RewardsDistributor.sol:296-299`) at the moment a speed is set, so the zero-supply loss window starts at speed activation and ends at the first mint — all rewards emitted in that interval vanish.

The same drain repeats every time totalSupply returns to zero (last full withdraw or full debt repayment): while supply is 0, each update call advances the timestamp, erasing rewards that no index can ever distribute.

### Impact Explanation
Reward accrual invariant is broken: emitted rewards are not conserved. All `rewardToken` emitted at `tokenSpeeds[token_]` during zero-supply periods are stranded in the `RewardsDistributor` contract forever — `claimRewards` only transfers amounts recorded in `tokensAccruedOf` (line 248-255), and there is no sweep/rescue path for the unallocated remainder. This is a permanent loss of user/protocol yield, guaranteed to occur at least once per reward-enabled token (the registration→first-deposit gap) and recurring on every full exit.

### Likelihood Explanation
Certain by construction: every token whose speed is activated before it has any holders loses the rewards for the entire gap. No attacker action is required; any user depositing, minting debt, or anyone calling the public `updateBeforeMintOrBurn` while `totalSupply == 0` triggers the timestamp advance. Nothing in `onlyIfDistributorExists`, `onlyIfTokenExists`, pause flags, or reentrancy guards prevents it — the loss path is the normal code path.

### Recommendation
Do not advance `tokenStates[token_].timestamp` when `token_.totalSupply() == 0`. In `_calculateTokenIndex`, return `_newTimestamp = 0` (or keep `_supplyState.timestamp`) when `_totalSupply == 0`, so the elapsed-time window resumes only once supply exists — mirroring the fix applied in Blueberry's PR#29. Alternatively, freeze accrual by treating `totalSupply == 0` as a pause in emission accounting.

### Proof of Concept
Foundry-style reproduction against deployed contract shape:

```solidity
// setup: pool with DepositToken dT registered; governor calls
rewardsDistributor.updateTokenSpeed(dT, 1e18); // 1 reward token/sec
// tokenStates[dT].timestamp = T0, index = INITIAL_INDEX

// 1. warp 1 day with zero deposits
vm.warp(T0 + 1 days);

// 2. Alice makes the first deposit -> _mint -> updateBeforeMintOrBurn
//    runs while dT.totalSupply() == 0:
//    _ratio = 0, but timestamp written to T0+1days
pool.deposit(dT, amount); // or dT.deposit(amount, alice)
(uint224 idx, uint32 ts) = rewardsDistributor.tokenStates(dT);
assertEq(ts, T0 + 1 days);       // timestamp advanced
assertEq(idx, INITIAL_INDEX);    // index never credited 86_400 tokens

// 3. warp another day with Alice holding supply
vm.warp(T0 + 2 days);
rewardsDistributor.updateBeforeMintOrBurn(dT, alice);
// claimable(alice) == 86_400e18, NOT 172_800e18
// the first day's 86_400 reward tokens are stranded in the distributor forever
```
