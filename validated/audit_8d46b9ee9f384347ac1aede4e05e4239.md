### Title
Unfreeze of TRON_POWER can be permanently blocked by dynamic parameter `ALLOW_NEW_RESOURCE_MODEL` toggling - (File: actuator/src/main/java/org/tron/core/actuator/UnfreezeBalanceV2Actuator.java)

### Summary
`UnfreezeBalanceV2Actuator.validate()` gates the withdrawal of an already-frozen `TRON_POWER` resource behind an unrelated, mutable governance flag (`dynamicStore.supportAllowNewResourceModel()`), rather than solely checking whether the user actually has a withdrawable frozen balance. This mirrors the ThunderNFT `Pool.withdraw()` pattern, where withdrawal is conditioned on an external "whitelist" flag (`AssetManager.is_asset_supported`) that can be flipped independently of whether the user's funds are legitimately deposited/frozen, resulting in a temporary freeze of user funds.

### Finding Description
In `UnfreezeBalanceV2Actuator.validate()`, when the requested `ResourceCode` is `TRON_POWER`:
```java
case TRON_POWER:
  if (dynamicStore.supportAllowNewResourceModel()) {
    if (!checkExistFrozenBalance(accountCapsule, TRON_POWER)) {
      throw new ContractValidateException("no frozenBalance(TronPower)");
    }
  } else {
    throw new ContractValidateException("ResourceCode error.valid ResourceCode[BANDWIDTH、Energy]");
  }
  break;
``` [1](#0-0) 

This means the ability to unfreeze `TRON_POWER` depends entirely on the current value of `dynamicStore.supportAllowNewResourceModel()` at unfreeze time — not on whether the account actually has a valid frozen `TRON_POWER` balance recorded via `FreezeBalanceV2Actuator` (which required the same flag to be `true` at freeze time, per the matching check in `FreezeBalanceV2Actuator`). This dynamic property is a committee-controlled chain parameter (`ALLOW_NEW_RESOURCE_MODEL`), set via `ProposalUtil`/`ProposalService` and stored in `DynamicPropertiesStore`. ` [2](#0-1) `

If a user freezes TRX for `TRON_POWER` while `ALLOW_NEW_RESOURCE_MODEL` is enabled, and the committee subsequently disables this parameter (e.g. to roll back a feature or in response to an issue) before the user submits their `UnfreezeBalanceV2Contract`, the `validate()` call unconditionally throws `"ResourceCode error.valid ResourceCode[BANDWIDTH、Energy]"` for `TRON_POWER`, regardless of the user's actual frozen balance. The user's TRX remains locked in the `frozenV2` list with no way to trigger `UnfreezeBalanceV2Actuator.execute()` for that resource type until the flag is re-enabled by the committee — exactly analogous to the ThunderNFT bug where `withdraw()` checked `is_asset_supported()` unconditionally instead of only checking the user's actual deposited balance.

The companion execute-path processor (`UnfreezeBalanceV2Processor` used by the TVM native contract path) contains the identical flag-gated logic pattern for freeze/unfreeze bookkeeping. ` [3](#0-2) `

### Impact Explanation
Any account that froze balance for `TRON_POWER` under `UnfreezeBalanceV2Contract` (or via the TVM `unfreezeBalanceV2` precompile path) is temporarily unable to withdraw/unfreeze that principal if the committee toggles `ALLOW_NEW_RESOURCE_MODEL` off after the freeze occurred. This is a broadcastable, unprivileged-transaction-reachable path (the user submits `UnfreezeBalanceV2Contract`, which is rejected at `validate()`), and funds are frozen with no user-controlled workaround until governance re-enables the flag — a temporary freezing-of-funds condition consistent with the "High" severity classification in the source report.

### Likelihood Explanation
This requires the mutable dynamic property `ALLOW_NEW_RESOURCE_MODEL` to be disabled after having been enabled and used by at least one account to freeze `TRON_POWER`. Whether this parameter is realistically toggled bidirectionally (vs. treated as a one-way, monotonic upgrade switch enforced elsewhere, e.g. in `ProposalUtil` validation) could not be conclusively confirmed within the available tool budget — the `ProposalUtil.java` and `DynamicPropertiesStore.java` matches for `ALLOW_NEW_RESOURCE_MODEL` were located but their exact validation/setter logic was not fully read before the iteration budget was exhausted. If the codebase enforces monotonic (one-directional, 0→1 only) transitions for this parameter via committee proposal validation, this specific scenario would not be practically exploitable, and this finding's likelihood would be significantly reduced or moot.

### Recommendation
In `UnfreezeBalanceV2Actuator.validate()` (and the equivalent `UnfreezeBalanceV2Processor.validate()`), for the `TRON_POWER` case, allow unfreezing whenever `checkExistFrozenBalance(accountCapsule, TRON_POWER)` is true, independent of the current value of `supportAllowNewResourceModel()`. The flag should gate the ability to *newly freeze* for `TRON_POWER`, not the ability to *withdraw already frozen* `TRON_POWER` balance. Additionally, verify (in `ProposalUtil`) whether `ALLOW_NEW_RESOURCE_MODEL` can be set back to `0` after being `1`; if so, this should be disallowed to avoid retroactively invalidating unfreeze eligibility for existing frozen balances.

### Proof of Concept
1. Committee enables `ALLOW_NEW_RESOURCE_MODEL` (dynamic property = 1).
2. User A submits `FreezeBalanceV2Contract` with `resource = TRON_POWER`, successfully freezing TRX (validated/executed in `FreezeBalanceV2Actuator`, which also requires `supportAllowNewResourceModel()==true`).
3. Committee submits a proposal disabling `ALLOW_NEW_RESOURCE_MODEL` (dynamic property = 0).
4. User A submits `UnfreezeBalanceV2Contract` with `resource = TRON_POWER`.
5. `UnfreezeBalanceV2Actuator.validate()` hits the `else` branch of the `TRON_POWER` case and throws `ContractValidateException("ResourceCode error.valid ResourceCode[BANDWIDTH、Energy]")`, rejecting the transaction even though User A has a valid, positive frozen `TRON_POWER` balance in `FreezeV2` list — funds remain locked until the committee re-enables the flag.   private boolean checkUnfreezeBalance(
      AccountCapsule accountCapsule, long unfreezeBalance, Common.ResourceCode freezeType)  {
    if (unfreezeBalance <= 0) {
      return false;
    }
    long frozenBalance = 0L;
    List<Protocol.Account.FreezeV2> freezeV2List = accountCapsule.getFrozenV2List();
    for (Protocol.Account.FreezeV2 freezeV2 : freezeV2List) {
      if (freezeV2.getType().equals(freezeType)) {
        frozenBalance = freezeV2.getAmount();
        break;
      }
    }

    return unfreezeBalance <= frozenBalance;
  }

  private boolean checkExistFrozenBalance(AccountCapsule accountCapsule, Common.ResourceCode freezeType) {
    List<Protocol.Account.FreezeV2> frozenV2List = accountCapsule.getFrozenV2List();
    for (Protocol.Account.FreezeV2 frozenV2 : frozenV2List) {
      if (frozenV2.getType().equals(freezeType) && frozenV2.getAmount() > 0) {
        return true;
      }
    }
    return false;
  }
