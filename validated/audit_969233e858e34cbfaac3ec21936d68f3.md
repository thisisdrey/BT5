## Title
Non-secret, self-referential quarantine ownership check allows cross-repository quarantine-directory spoofing - (`File: internal/git/localrepo/paths.go`)

### Summary
Gitaly's `ObjectDirectoryPath()` is supposed to verify that a client-supplied Git object-quarantine directory actually belongs to the repository being targeted before it is treated as trustworthy. The "ownership proof" it uses, however, is not a real authentication check: it is a plain, unsalted `SHA1` hash of the very same `RelativePath` field that is already fully attacker-controlled in the request, so the check can always be satisfied by the requester itself — exactly the same "signature that never binds the actual sensitive parameters" pattern as the reported `PhiFactory::createArt()` bug, where a valid signature could be replayed with attacker-chosen configuration data.

### Finding Description
`Repo.ObjectDirectoryPath()` resolves the on-disk object directory for a repository from the client-suppliable `GitObjectDirectory` field of a `gitalypb.Repository` message: [1](#0-0) 

When the supplied `GitObjectDirectory` is not a plain path inside the repository itself, Gitaly falls back to treating it as a "manual object quarantine directory located in the storage's temporary directory," and gates that acceptance on a repository-specific prefix: [2](#0-1) 

The "repository-specific prefix" is computed purely as a truncated `SHA1` of `repo.GetRelativePath()`: [3](#0-2) 

The comment states the intent explicitly: this hash is supposed to let Gitaly "verify that a given quarantine object directory indeed belongs to the repository at hand." But `repo` here is the *same* `Repository` message from the incoming request whose `RelativePath` the caller also supplies. This means the "signature" being checked is derived from data the requester fully controls, not from any secret, random, or server-tracked session/transaction identifier. A caller can:

1. Pick any target `RelativePath` (their own, or one they can otherwise infer — e.g. GitLab project paths are often knowable, and `DeriveReplicaPath`/`DerivePoolPath` derive on-disk paths deterministically from a numeric repository ID via unsalted `SHA256`, so replica paths for arbitrary repository IDs are also computable): [4](#0-3) 
2. Compute `QuarantineDirectoryPrefix()` for that path themselves (it uses no secret key), and
3. Set `GitObjectDirectory` to any path under the storage's temp directory that begins with `quarantine-<hash>-`, using `..`-style relative traversal from their own repo path to reach into another repository's/temp-dir location.

Because both inputs to the "ownership" check originate from the same untrusted request, the check can never actually fail for a determined caller — it only verifies internal self-consistency of attacker-supplied data, not that the directory was genuinely created by a legitimate `git-receive-pack` quarantine or WAL/transaction quarantine flow for that specific push. This is structurally identical to the root cause in the referenced report: a validation artifact (there, an ECDSA signature; here, a hash "prefix") that omits the very data it is meant to bind (there, `CreateConfig`; here, the *actual* server-generated quarantine session/transaction), enabling substitution of attacker-chosen values while the check still passes. In addition, the earlier branch of the same function (`isTransactionQuarantineDir`) skips this ownership check *entirely* whenever the path's trailing components merely match the string pattern `.../quarantine` or `.../quarantine/tmp_objdir-*`, relying solely on naming convention rather than any binding to the requesting repository at all: [5](#0-4) 

### Impact Explanation
Object quarantine directories exist specifically to hold objects that are part of an in-flight, not-yet-accepted push (`pre-receive` may still reject them) — see the design rationale in `doc/object_quarantine.md`: [6](#0-5) [7](#0-6) 

If a caller can point their own repository's `GitObjectDirectory`/`GitAlternateObjectDirectories` at another repository's quarantine location and have Gitaly's ownership check pass trivially, RPCs that build `GIT_OBJECT_DIRECTORY`/`GIT_ALTERNATE_OBJECT_DIRECTORIES` from this resolved path (e.g. size/statistics RPCs, or any Git subprocess invoked against the "repo" using this quarantine directory) can be tricked into reading, sizing, or otherwise exposing objects belonging to another repository's pending, unauthorized (possibly rejected) push — a cross-repository object disclosure. This is consistent with tests in the codebase explicitly asserting the opposite (that swapped quarantine directories between two different repositories must be rejected): [8](#0-7) 
demonstrating that the codebase itself treats "quarantine directory belongs to a different repository" as a security property that must hold — a property the self-referential hash check does not actually enforce against a caller who controls both sides of the comparison.

### Likelihood Explanation
Exploitation requires only the ability to issue a Gitaly RPC carrying a `Repository` message with attacker-chosen `RelativePath` and `GitObjectDirectory`/`GitAlternateObjectDirectories` fields — the exact object-quarantine looping-back mechanism that Rails performs automatically as part of every ordinary `git push`'s access-check flow, and which is exposed on any RPC accepting a repository message with these fields set. No cryptographic secret, node compromise, or MITM is needed; the attacker only needs to know or guess the target's `RelativePath` (feasible for public projects or via the deterministic, unsalted `DeriveReplicaPath`/`DerivePoolPath` scheme) and correctly form the traversal path, both of which are purely computational.

### Recommendation
- Do not derive the quarantine "ownership proof" from data supplied in the same request being validated. Bind manual/quarantine object directories to a server-side tracked, unpredictable transaction/session identifier (e.g., the actual `storage.Transaction`/temp-dir handle created by `quarantine.New`), and verify the resolved directory was in fact allocated for *this* transaction rather than merely matching a caller-recomputable hash of the caller-supplied relative path.
- Remove or tighten the `isTransactionQuarantineDir` naming-pattern shortcut so that it, too, verifies the directory was issued for the specific repository/transaction instead of trusting a directory-name convention alone.
- Consider using an HMAC with a server-only secret (or the real transaction identifier from `TransactionRegistry`) instead of an unsalted hash of public data, so the prefix cannot be independently recomputed by any requester.

### Proof of Concept
Conceptual reproduction using the existing test harness pattern from `size_test.go`:
1. Create two repositories, `repoA` (attacker-owned) and `repoB` (victim), and start a legitimate quarantine for `repoB` (e.g. via a concurrent push) so a real `quarantine-<hash(repoB.RelativePath)>-.../tmp_objdir-*` directory exists under the storage's temp dir.
2. As the caller for `repoA`, issue the target RPC (e.g. `GetObjectDirectorySize`) with `Repository{RelativePath: repoA path, GitObjectDirectory: "<relative traversal from repoA path to repoB's quarantine dir>"}`.
3. Because `QuarantineDirectoryPrefix` is computed only from the `RelativePath` field already present in the very same request, and the traversal resolves within the storage root, `ObjectDirectoryPath()` accepts the path without ever verifying it corresponds to a quarantine genuinely created for `repoA`'s own transaction — Gitaly proceeds to use `repoB`'s in-flight quarantine contents in the context of `repoA`'s request. // ObjectDirectoryPath returns the full path of the object directory. The errors returned are gRPC
```go
// errors with relevant error codes and should be passed back to gRPC without further decoration.
func (repo *Repo) ObjectDirectoryPath(ctx context.Context) (string, error) {
	repoPath, err := repo.Path(ctx)
	if err != nil {
		return "", err
	}

	objectDirectoryPath := repo.GetGitObjectDirectory()
	if objectDirectoryPath == "" {
		return "", structerr.NewInvalidArgument("object directory path is not set")
	}

	storagePath, err := repo.locator.GetStorageByName(ctx, repo.GetStorageName())
	if err != nil {
		return "", fmt.Errorf("get storage by name: %w", err)
	}

	// Ensure the path points somewhere in the storage.
	relativeObjectDirectoryPath, err := storage.ValidateRelativePath(storagePath, filepath.Join(repoPath, objectDirectoryPath))
	if err != nil {
		return "", structerr.NewInvalidArgument("validate relative path: %w", err)
	}
```

```go
// QuarantineDirectoryPrefix returns a prefix for use in the temporary directory. The prefix is
// based on the relative repository path and will stay stable for any given repository. This allows
// us to verify that a given quarantine object directory indeed belongs to the repository at hand.
// Ideally, this function would directly be located in the quarantine module, but this is not
// possible due to cyclic dependencies.
func QuarantineDirectoryPrefix(repo Repository) string {
	hash := [20]byte{}
	if repo != nil {
		hash = sha1.Sum([]byte(repo.GetRelativePath()))
	}
	return fmt.Sprintf("quarantine-%x-", hash[:8])
}
```

```markdown
### How Git receives a push

On a Git server, a push goes into `git receive-pack`. This process does the following things:

1. receive the Git objects pushed by the client and write them to disk
1. receive the ref update commands from the client and keep them in memory
1. check connectivity (no missing objects)
1. run `pre-receive` and feed it the intended ref update commands
1. if `pre-receive` rejects the push, clean up and stop
1. apply ref update commands one by one. For each command, run the `update` hook which can reject the ref update.
1. after all ref updates have been applied run the `post-receive` hook
1. report success to the client and end the session

Object quarantine exists for the sake of the cleanup that happens when
`pre-receive` rejects the push (step 5 above). It changes the _timing_ of the
cleanup. Without object quarantine, objects that were part of a
rejected push would sit around until `git gc` would judge them as both
unused and "old". How long that takes depends on how often `git gc`
runs (or `git prune`), and on the configuration of when objects are
"old". Because of object quarantine, rejected objects can be deleted
immediately: Git can just `rm -rf` the quarantine directory and
they're gone.
```

```markdown
## GitLab and Git object quarantine

### Why does all this matter to GitLab

GitLab uses Git hooks, among other things, to implement features that
can reject Git pushes. For example, you can mark a branch as
"protected" in the GitLab web UI, and then certain types of users can
no longer push to that branch. That feature is implemented via the
[Git `pre-receive` hook](https://gitlab.com/gitlab-org/gitaly/-/blob/71d527f4f16c1f0e76793f055def0299b375cc7d/internal/gitaly/service/hook/pre_receive.go).

As mentioned above, Git object quarantine normally works more or less
automatically because `git` commands spawned by the `pre-receive` hook
inherit the special environment variables that contain the path to the
quarantine directory. In the case of the GitLab hooks we have a problem,
however, because the GitLab hooks are "dumb". All the GitLab hooks do
is take the inputs of the hook executable (the list of ref update
commands) and send them to the GitLab Rails internal API via a POST
request. The application logic that decides whether the push is
allowed resides in Rails. The hook just waits and reports back result
of the POST API request to GitLab.

During the POST, the internal GitLab API makes Gitaly calls back into the repo to
examine the objects being pushed. For example, if force pushes are not
allowed, GitLab will call the IsAncestor RPC. That RPC call then wants
to look at a commit that is in the process of being pushed. But
because that commit is in quarantine, the RPC will fail because the
commit cannot be found.

### How GitLab passes the object quarantine information around

To overcome this problem, the GitLab `pre-receive` hook
[reads the object directory configuration from its environment](https://gitlab.com/gitlab-org/gitaly/-/blob/71d527f4f16c1f0e76793f055def0299b375cc7d/internal/gitlabshell/env.go#L9).
and passes this information
[along with the HTTP API call](https://gitlab.com/gitlab-org/gitaly/-/blob/71d527f4f16c1f0e76793f055def0299b375cc7d/internal/gitaly/hook/manager.go#L30-46).
On the Rails side, we then
[put the object directory information in the "request store"](https://gitlab.com/gitlab-org/gitlab/-/blob/master/lib/api/internal/base.rb#L43)
(i.e., request-scoped thread-local storage). And then during that
Rails request, when Rails makes Gitaly requests on this repo, we send back the quarantine information
[in the Gitaly `Repository` struct](https://gitlab.com/gitlab-org/gitlab/-/blob/f81f30c29a0edce20f6737fdccc3315c8baab9d1/lib/gitlab/gitaly_client/util.rb#L8-17).
And finally, inside Gitaly, when we spawn a Git process, we
[re-create the environment variables](https://gitlab.com/gitlab-org/gitaly/-/blob/969bac80e2f246867c1a976864bd1f5b34ee43dd/internal/git/alternates/alternates.go#L21-34)
that were present on the `pre-receive` hook, so that we can see the
quarantined objects.
```
