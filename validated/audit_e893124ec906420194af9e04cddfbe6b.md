Audit Report

## Title
Snowbridge outbound-queue-v2 pays relayer reward on failed message execution because `DeliveryReceipt.success` is never checked - (File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs)

## Summary
`process_delivery_receipt` settles a `PendingOrder` and pays the associated fee purely based on the existence of a nonce entry and a matching Gateway address. It decodes `receipt.success` from the Ethereum event but discards it, so a relayer is rewarded and the order is removed regardless of whether the corresponding message actually executed successfully on Ethereum.

## Finding Description
The `InboundMessageDispatched` Solidity event carries a `success` flag indicating whether the outbound command actually executed successfully on the Ethereum Gateway contract, and `DeliveryReceipt::try_from` faithfully decodes this field into `DeliveryReceipt.success`. However, `process_delivery_receipt` in `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs` only checks that `receipt.gateway == T::GatewayAddress::get()` and that `PendingOrders` contains the nonce, then unconditionally pays `order.fee` via `T::RewardPayment::register_reward` and removes the order — `receipt.success` is never read anywhere in the function or in `submit_delivery_receipt`. This decouples settlement (fee payout, order removal) from actual execution success on Ethereum: a message that failed to execute (`success = false`) still results in the relayer being paid and the pending order permanently cleared, with no retry path since the order is deleted.

## Impact Explanation
This matches the "duplicate settlement or payout" / "public underpriced work that ... stalls bridge processing" categories in the impact gate: relayers are compensated for messages whose intended effect never materialized on Ethereum, silently draining the reward pool, and since `PendingOrders` is removed unconditionally there is no mechanism to reconcile or re-attempt the failed command.

## Likelihood Explanation
`submit_delivery_receipt` is a permissionless, signed extrinsic open to any relayer. `success=false` is a normal, expected outcome for Ethereum-side execution failures (e.g. reverts unrelated to relay honesty), so no malicious relayer, validator, or governance action is required — a legitimate proof for a legitimately failed execution triggers the erroneous payout every time.

## Recommendation
In `process_delivery_receipt`, branch on `receipt.success`: only call `T::RewardPayment::register_reward` and settle/remove the order when `receipt.success == true`. On `false`, handle via a distinct failure path (no reward, and/or retry/re-delivery accounting) rather than paying out and deleting the order unconditionally.

## Proof of Concept
1. A message is queued and a `PendingOrder{nonce, fee}` is created via `do_process_message`.
2. On Ethereum, the Gateway contract execution of the corresponding command fails, emitting `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer builds a valid proof for this real event log and calls `submit_delivery_receipt(origin, event)`.
4. `T::Verifier::verify` succeeds, `DeliveryReceipt::try_from` decodes `success = false`.
5. `process_delivery_receipt` checks only the gateway address and nonce existence, ignores `success`, calls `T::RewardPayment::register_reward(&reward_account, ..., order.fee)`, then removes the `PendingOrder`.
6. The relayer is paid the full fee despite `success == false`, and the failed order can never be retried since it has been deleted from `PendingOrders`. [3](#0-2) [1](#0-0) [4](#0-3)

/// Delivery receipt
#[derive(Clone, Debug)]
pub struct DeliveryReceipt {
	/// The address of the outbound queue on Ethereum that emitted this message as an event log
	pub gateway: H160,
	/// The nonce of the dispatched message
	pub nonce: u64,
	/// Message topic
	pub topic: H256,
	/// Delivery status
	pub success: bool,
	/// The reward address
	pub reward_address: [u8; 32],
}

#[derive(Copy, Clone, Encode, Decode, Eq, PartialEq, Debug, TypeInfo)]
pub enum DeliveryReceiptDecodeError {
	DecodeLogFailed,
	DecodeAccountFailed,
}

impl TryFrom<&Log> for DeliveryReceipt {
	type Error = DeliveryReceiptDecodeError;

	fn try_from(log: &Log) -> Result<Self, Self::Error> {
		let topics: Vec<B256> = log.topics.iter().map(|x| B256::from_slice(x.as_ref())).collect();

		let event = InboundMessageDispatched::decode_raw_log_validate(topics, &log.data)
			.map_err(|_| DeliveryReceiptDecodeError::DecodeLogFailed)?;

		Ok(Self {
			gateway: log.address,
			nonce: event.nonce,
			topic: H256::from_slice(event.topic.as_ref()),
			success: event.success,
			reward_address: event.reward_address.0,
		})
	}
