### Title
Unvalidated `xorOffset` in packfile bitmap parsing causes out-of-range panic / DoS - ([File: internal/git/packfile/bitmap.go])

### Summary
`IndexBitmap.BitmapCommit` in `internal/git/packfile/bitmap.go` uses a per-commit `xorOffset` byte read directly from a `.bitmap` file to index backwards into the `bitmapCommits` slice (`ib.bitmapCommits[j-k]`) without validating that `k <= j`. This mirrors the Sherlock finding's root cause class: a value read from external/untrusted input is assumed to be within a valid range/order relative to another index, and is used directly in arithmetic that indexes into a data structure, with no bounds check before use.

### Finding Description
`LoadBitmap` reads bitmap-commit headers from the `.bitmap` file and stores the raw `xorOffset` byte for each entry without validating it against the entry's own position in the sequence: [1](#0-0) 

Later, `BitmapCommit` walks the chain of bitmap commits up to index `i` and, for XOR-compressed entries, dereferences `ib.bitmapCommits[j-k]` where `k = int(bc.xorOffset)` and `j` is the current loop index: [2](#0-1) 

There is no check that `k <= j`. Since `xorOffset` is an attacker/corruption-controllable byte (0–255) taken straight from file contents, a crafted `.bitmap` file with `xorOffset > j` for an early entry (e.g., the very first entry, `j=0`, with `xorOffset=1`) causes `j-k` to be negative, producing a Go slice index out of range panic. This is directly analogous to the reported bug class: an ordered/relative value taken from data is not validated before being used in index/subtraction arithmetic, leading to a runtime failure of the calling code path instead of a graceful error.

### Impact Explanation
A panic inside `BitmapCommit` is not recovered anywhere in this call chain (unlike, e.g., the Raft replica's `safeExec`), so it will crash the goroutine executing the request. Bitmap files are read during Gitaly-internal packfile utilities (`Index.LabelObjectTypes` → `LoadBitmap` → `BitmapCommit`), which are used by housekeeping/inspection tooling that inspects packfiles on disk (including within object pools, which are populated by fetches/imports from repository forks). Because bitmap files live under `objects/pack/*.bitmap` inside a repository's or object pool's object directory, any code path that processes a repository whose packfile bitmap can be influenced (e.g., a maliciously crafted repository imported, forked, or seeding an object pool prior to gitaly repacking it, or a corrupted/tampered bitmap on disk) can trigger this panic when Gitaly later loads and processes that bitmap. This is a Denial-of-Service on the handler that invokes bitmap parsing.

### Likelihood Explanation
Likelihood is limited by the fact that `.bitmap` files are normally generated by `git repack -b`/`git gc` internally by Gitaly itself, not directly supplied by RPC callers in the common repository lifecycle. However, the parsing logic still operates on file bytes read from disk without validating internal consistency, so any bit-flip corruption, a maliciously crafted repository tree that is imported/restored (e.g., via backup restore, repository import from an untrusted bundle/tarball, or an object pool member seeded from an untrusted fork) that includes an attacker-supplied `.bitmap` file could reach this code and crash the process/goroutine handling that request. This is a lower-likelihood but concretely reachable DoS analog of the described "values not checked to be in increasing/valid order" bug class.

### Recommendation
Validate `xorOffset` against the current index when parsing or when consuming it: reject (return an error) if `int(bc.xorOffset) > j` for the corresponding position `j`, either at parse time in `LoadBitmap` (per RFC bitmap format, `xorOffset` must reference a strictly preceding entry) or defensively in `BitmapCommit` before computing `j-k`. Return a descriptive error (e.g., `fmt.Errorf("invalid xor offset %d at index %d", k, j)`) instead of allowing the negative index to reach the slice access, consistent with how `parseChunks` in `internal/git/mvcc/manifest.go` already validates monotonic chunk offsets.

### Proof of Concept
1. Take a valid packfile `.bitmap` file (as produced by `git repack -b`).
2. Locate the first bitmap-commit entry's 6-byte header (object index[4] + xorOffset[1] + flags[1]) and set `xorOffset = 1` (or any value greater than the entry's own position, e.g. for the first entry `j=0`, any `xorOffset > 0`).
3. Invoke a Gitaly code path that calls `Index.LoadBitmap()` followed by `BitmapCommit(0)` (e.g., via `Index.LabelObjectTypes()`), for instance through `gitaly-debug` bitmap tooling or any internal repository-info/housekeeping code path that walks bitmap commits against this crafted packfile/pool.
4. Observe: `ib.bitmapCommits[j-k]` evaluates to `ib.bitmapCommits[-1]`, causing a Go runtime panic (`index out of range [-1]`) that terminates the goroutine servicing the request, unless the caller wraps it in a panic-recovery handler.

func (ib *IndexBitmap) BitmapCommit(i int) (*BitmapCommit, error) {
	if i >= ib.NumBitmapCommits() {
		return nil, fmt.Errorf("bitmap commit index %d out of range", i)
	}

	// This is wasteful but correct: bitmap commit i may depend, via XOR, on
	// a chain of preceding commits j_0,..., j_m < i. Instead of finding that
	// chain we just build and XOR all commits up to and including i.
	for j, bc := range ib.bitmapCommits[:i+1] {
		if bc.Bitmap.bm != nil {
			continue
		}

		if err := bc.Bitmap.Unpack(); err != nil {
			return nil, err
		}

		if k := int(bc.xorOffset); k > 0 {
			bm := bc.Bitmap.bm
			bm.Xor(bm, ib.bitmapCommits[j-k].Bitmap.bm)
		}
	}

	return ib.bitmapCommits[i], nil
}
