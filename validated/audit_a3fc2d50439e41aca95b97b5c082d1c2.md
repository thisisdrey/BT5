Audit Report

## Title
Permanent loss of burned tip funds when `add_tip` targets an already-consumed or unknown Snowbridge message nonce - (File: `bridges/snowbridge/pallets/system-frontend/src/lib.rs`, `bridges/snowbridge/pallets/system-v2/src/lib.rs`)

## Summary
`EthereumSystemFrontend::add_tip` unconditionally burns the caller's supplied asset via `swap_fee_asset_and_burn` before the cross-chain XCM `Transact` reaches BridgeHub to actually apply the tip to the target inbound/outbound message nonce. If that nonce has already been processed by the time the XCM lands (an expected outcome of normal relayer latency, not an attack), `EthereumSystemV2::add_tip` on BridgeHub only records the lost amount into the `LostTips` storage map, which is written to but never read, drained, or refunded anywhere in the codebase, resulting in permanent, irrecoverable loss of the user's burned Ether.

## Finding Description
`add_tip` in `bridges/snowbridge/pallets/system-frontend/src/lib.rs:261-273` is a public, signed extrinsic. It calls `swap_fee_asset_and_burn`, which either swaps the caller's asset for Ether and burns it, or directly burns Ether via `burn_for_teleport::<T::AssetTransactor>` (`bridges/snowbridge/pallets/system-frontend/src/lib.rs:372-404`). This burn is unconditional and irreversible, and occurs strictly before any validation that the target message nonce is still eligible for a tip.

Only afterward does the pallet dispatch an XCM `Transact` calling `EthereumSystemV2::add_tip` on BridgeHub (`bridges/snowbridge/pallets/system-v2/src/lib.rs:251-281`), which delegates to `InboundQueue::add_tip` or `OutboundQueue::add_tip`. The inbound implementation (`bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs:248-258`) explicitly rejects tips on nonces already marked processed via `Nonce::<T>::get(nonce)`, which is set by `process_message` (`bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs:214-245`) as part of ordinary, permissionless relayer message submission. When this rejection occurs, the failure path in `system-v2::add_tip` does not revert or refund anything — it only mutates `LostTips::<T>` (`bridges/snowbridge/pallets/system-v2/src/lib.rs:266-271`), a storage map that per its own doc comment (`bridges/snowbridge/pallets/system-v2/src/lib.rs:136-139`) is intended only to "support implementing a recovery method in the future." No such recovery method exists: a repository-wide search confirms `LostTips` is referenced only in its own pallet's tests and one integration test assertion, never read or drained by any extrinsic or trait implementation.

The existing guard `ensure!(!Nonce::<T>::get(nonce), AddTipError::NonceConsumed)` correctly prevents a tip from being mis-applied to a stale nonce, but does nothing to prevent the antecedent, irreversible burn from being wasted, because the burn and the destination-chain validity check are not atomic across the XCM hop.

## Impact Explanation
This matches the "permanent user-fund or bridge-state lock" category in the impact gate: any unprivileged user's burned Ether becomes permanently unrecoverable, tracked only in a dead-end `LostTips::<T>` balance for their `AccountId` with no extrinsic anywhere in the codebase to reclaim it. This occurs under entirely honest bridge operation — no malicious relayer, validator, or governance action is required, only the ordinary latency inherent to a two-hop XCM message racing against ordinary, expected relayer message submission.

## Likelihood Explanation
High. Any user calling `add_tip` for a nonce that is processed by a normal, honest relayer before the tip's own XCM `Transact` reaches BridgeHub will lose their burned funds. Since relayers are economically incentivized to submit proofs quickly and users are incentivized to add tips near message submission time, this race condition is expected to occur periodically under normal operating conditions, not merely as a contrived edge case.

## Recommendation
Avoid burning the tip asset before destination-chain confirmation. Options include: (a) validating nonce/order status locally before burning where feasible, (b) reserving/holding the asset locally and only finalizing the burn upon a settlement acknowledgment from BridgeHub, or (c) implementing the promised recovery mechanism — a signed extrinsic allowing the original `sender` account recorded in `LostTips` to reclaim/mint back their lost amount, closing the currently nonexistent redemption path in `bridges/snowbridge/pallets/system-v2/src/lib.rs`.

## Proof of Concept
1. User calls `EthereumSystemFrontend::add_tip(origin, MessageId::Inbound(N), asset)` on AssetHub for an inbound nonce `N` not yet finalized on BridgeHub.
2. `swap_fee_asset_and_burn` immediately and irreversibly burns the user's asset for teleport (`bridges/snowbridge/pallets/system-frontend/src/lib.rs:267`, `:399-401`).
3. Before the deferred XCM `Transact` executes on BridgeHub, any relayer submits a valid proof for nonce `N`, which invokes `process_message` and sets `Nonce::<T>::set(nonce)` (`bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs:225`).
4. The `EthereumSystemV2::add_tip` call executes, calling `InboundQueue::add_tip(N, amount)`, which now returns `Err(AddTipError::NonceConsumed)` (`bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs:252`).
5. `system-v2::add_tip`'s error branch only writes to `LostTips::<T>::mutate(&sender, ...)` (`bridges/snowbridge/pallets/system-v2/src/lib.rs:268-270`), confirmed by the integration test `tip_to_invalid_nonce_is_added_to_lost_tips` in `cumulus/parachains/integration-tests/emulated/tests/bridges/bridge-hub-westend/src/tests/snowbridge_v2_outbound.rs:277-320`, which asserts `relayer_lost_tip > 0` and performs no reclaim.
6. The user's Ether remains burned permanently; no extrinsic in the repository reads or drains `LostTips`.

			sender: AccountIdOf<T>,
			message_id: MessageId,
			amount: u128,
		) -> DispatchResult {
			T::FrontendOrigin::ensure_origin(origin)?;

			let result = match message_id {
				Inbound(nonce) => <T as pallet::Config>::InboundQueue::add_tip(nonce, amount),
				Outbound(nonce) => <T as pallet::Config>::OutboundQueue::add_tip(nonce, amount),
			};

			if let Err(ref e) = result {
				tracing::debug!(target: LOG_TARGET, ?e, ?message_id, ?amount, "error adding tip");
				LostTips::<T>::mutate(&sender, |lost_tip| {
					*lost_tip = lost_tip.saturating_add(amount);
				});
			}

			Self::deposit_event(Event::<T>::TipProcessed {
				sender,
				message_id,
				amount,
				success: result.is_ok(),
			});

			Ok(())
		}

	impl<T: Config> Pallet<T> {
		pub fn process_message(relayer: T::AccountId, message: Message) -> DispatchResult {
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == message.gateway, Error::<T>::InvalidGateway);

			let (nonce, relayer_fee) = (message.nonce, message.relayer_fee);

			// Verify the message has not been processed
			ensure!(!Nonce::<T>::get(nonce), Error::<T>::InvalidNonce);

			// Mark message as received
			Nonce::<T>::set(nonce);

			let message_id = T::MessageProcessor::process_message(relayer.clone(), message)
				.map_err(|e| match e {
					MessageProcessorError::ProcessMessage(e) => e,
					MessageProcessorError::ConvertMessage(e) => Error::<T>::from(e).into(),
					MessageProcessorError::SendMessage(e) => Error::<T>::from(e).into(),
				})?;

			// Pay relayer reward
			let tip = Tips::<T>::take(nonce).unwrap_or_default();
			let total_tip = relayer_fee.saturating_add(tip);
			if total_tip > 0 {
				T::RewardPayment::register_reward(&relayer, T::DefaultRewardKind::get(), total_tip);
			}

			// Emit event with the message_id
			Self::deposit_event(Event::MessageReceived { nonce, message_id });

			Ok(())
		}
