### Title
Missing `attachments_max_size` bound check in `AttachmentsBatchStateContext::extend_with_attachments` / `decode_atlas_get_attachment` allows oversized attachment content from a peer - ([File: stackslib/src/net/atlas/download.rs])

### Summary
A remote peer responding to a `GetAttachment` request can return an `Attachment` whose `content` is arbitrarily large; `extend_with_attachments` decodes and inserts it into the in-memory `attachments` set with no check against `AtlasConfig.attachments_max_size`. The size bound is enforced only in `AtlasDB::should_keep_attachment`, which is documented/used for attachments *posted* to the node via RPC, not for attachments *downloaded* from peers.

### Finding Description
`AttachmentsBatchStateContext::extend_with_attachments` iterates over successful `AttachmentRequest` results and, for each response, calls `response.decode_atlas_get_attachment()` and unconditionally inserts the resulting `Attachment` into `self.attachments`: [1](#0-0) 

`GetAttachmentResponse`'s deserializer builds the `Attachment` directly from attacker-controlled hex bytes with no length gate: [2](#0-1) 

The only place in the codebase that enforces `content.len() <= attachments_max_size` is `AtlasDB::should_keep_attachment`, whose docstring/behavior is for locally-posted attachments (`will discard posted attachment - attachment too large`): [3](#0-2) 

Nothing in `extend_with_attachments` or `decode_atlas_get_attachment` calls `should_keep_attachment` or otherwise checks `attachment.content.len()` before the content is decoded and held in memory. A malicious peer that receives a `GetAttachment` request can therefore respond with a JSON/hex-encoded body decoding to a `content` field far larger than `ATTACHMENTS_MAX_SIZE_MIN = 1_048_576`, and that oversized `Vec<u8>` will be fully allocated and stored into the downloader's `attachments` collection on the p2p thread before any subsequent hash-matching/instance-reconciliation logic can discard it.

### Impact Explanation
Each malicious `GetAttachment` response forces the requesting node's attachment-downloader (running in the p2p thread) to allocate and hold an oversized buffer per response, with no cap besides whatever generic HTTP/JSON decoding limits exist elsewhere in the stack (none were found specific to this response type). This is a bounded-but-large single-response memory allocation on a component of the p2p thread, repeatable on every `GetAttachment` request the node issues to the malicious peer, matching the "bounded compute DoS on a read endpoint" category rather than an unbounded crash.

### Likelihood Explanation
The attacker only needs to be a normal p2p peer capable of answering a `GetAttachment` request that the victim node legitimately issues (e.g., by first advertising the corresponding attachment via inventory gossip so the victim requests it from them) — no authentication, secret, or privileged role is required. The attack is trivially repeatable for every attachment inventory slot the attacker controls or advertises.

### Recommendation
Add an explicit length check in `extend_with_attachments` (or inside `decode_atlas_get_attachment`) that rejects/drops any `Attachment` whose `content.len()` exceeds `atlas_config.attachments_max_size` before inserting it into `self.attachments`, mirroring the check already present in `AtlasDB::should_keep_attachment`.

### Proof of Concept
Rust net test plan:
1. Construct a `StacksHttpResponse` whose body is a JSON string field decoding (via hex) to a `content` `Vec<u8>` of size significantly greater than `ATTACHMENTS_MAX_SIZE_MIN`.
2. Call `response.decode_atlas_get_attachment()` directly and assert it returns `Ok` with `attachment.content.len() > atlas_config.attachments_max_size`.
3. Feed this response through `AttachmentsBatchStateContext::extend_with_attachments` via a `BatchedRequestsResult<AttachmentRequest>` with one `succeeded` entry, and assert that `context.attachments` now contains the oversized attachment with no rejection — i.e., no code path calls `AtlasDB::should_keep_attachment` or an equivalent length check between decode and insertion.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }

    }

    pub fn should_keep_attachment(
        &self,
        contract_id: &QualifiedContractIdentifier,
        attachment: &Attachment,
    ) -> bool {
        if !self.atlas_config.contracts.contains(contract_id) {
            info!(
                "Atlas: will discard posted attachment - {} not in supported contracts",
                contract_id
            );
            return false;
        }
        if attachment.content.len() as u32 > self.atlas_config.attachments_max_size {
            info!("Atlas: will discard posted attachment - attachment too large");
            return false;
        }
        true
    }
