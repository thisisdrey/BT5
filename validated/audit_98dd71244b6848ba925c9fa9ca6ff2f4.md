### Title
Non-deterministic, platform-specific `pow()` implementation in the TRX/TRC-10 Bancor-style exchange AMM can cause consensus divergence between CPU architectures - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
Instead of using a single, deterministic math implementation (or a hardened library-based decimal implementation) for the price-curve calculation used by the built-in TRX↔TRC-10 exchange (Bancor-formula AMM), java-tron implements its own custom `pow()` dispatch that resolves to different native code paths depending on whether the node is compiled/running on x86 or ARM. This is exactly the class of bug the external report calls out: "own custom code for which battle proof libraries exist" leading to correctness problems in the price/oracle math of a DeFi-style AMM. Here the custom implementation is reachable by any account that creates an exchange (`ExchangeCreateActuator`) and calls `ExchangeTransactionContract`, i.e. an ordinary signed transaction.

### Finding Description
`ExchangeCapsule.transaction()` computes the AMM trade output via `Processor.exchange()`, choosing between the legacy `ExchangeProcessor` and the newer `SafeExchangeProcessor` depending on the `hardenedCalc` flag: [1](#0-0) 

The legacy `ExchangeProcessor` performs the Bancor exponentiation using `org.tron.common.math.Maths.pow(double, double, boolean useStrictMath)`: [2](#0-1) 

`Maths.pow` dispatches to either `StrictMathWrapper.pow` (deterministic `StrictMath.pow`) or `MathWrapper.pow` depending on `useStrictMath`: [3](#0-2) 

Critically, `MathWrapper` is **compiled per-CPU-architecture** into separate source sets:
- The x86 build calls plain `java.lang.Math.pow(a, b)`, which the JLS explicitly does **not** guarantee to be bit-for-bit reproducible across platforms/JIT implementations (only `StrictMath` gives that guarantee): [4](#0-3) 
- The ARM build instead consults a hardcoded historical lookup table of (a, b) → result triples collected from mainnet blocks, and only falls back to `StrictMath.pow` for values not in that table: [5](#0-4) 

The very existence of this hardcoded per-block replay table is direct evidence that `Math.pow` previously produced diverging results across architectures on real mainnet blocks — the project's own workaround for a "use of libraries" class defect. However the fix only patches *already observed* historical (a, b) pairs; any **new** trade whose computed `(base, exponent)` pair is not already in the static ARM table will fall through to `StrictMath.pow` on ARM while the x86 build continues to call raw `Math.pow`. Because `Math.pow` and `StrictMath.pow` are only required to agree within 1 ulp (not bit-identical), and the AMM result is derived by casting the double result down with `(long)` truncation: [6](#0-5) 
a 1-ulp difference in the intermediate `pow()` result can flip the truncated integer output by one unit for adversarially/naturally chosen reserve ratios, producing a different `buyTokenQuant`/exchange balance on x86 nodes vs. ARM nodes for the identical `ExchangeTransactionContract`.

A dedicated, deterministic `SafeExchangeProcessor` (BigDecimal + `StrictMathWrapper.pow`) has been added, but it is only used when the `hardenedCalc` flag is true, i.e. gated by the dynamic property controlling hardened exchange calculation. The legacy, architecture-dependent path in `ExchangeProcessor`/`MathWrapper` remains live and reachable through `ExchangeTransactionActuator` whenever that hardening flag is not enabled on a given node/network.

### Impact Explanation
If witness/full nodes are deployed on a mix of x86 and ARM hardware (a realistic and common heterogeneous-node deployment for a public blockchain), the same signed `ExchangeTransactionContract` can be applied by `Manager`'s block-application path with two different resulting account/exchange-pool balances on different architectures. Since Merkle roots/state hashes are derived from these balances, this causes state divergence between nodes — a chain split / consensus halt scenario, which is explicitly an accepted high-impact outcome for this analysis.

### Likelihood Explanation
Likelihood depends on whether the network/node currently has the hardened exchange-calculation flag disabled (legacy path active) and whether ARM-based full nodes/witnesses are actually run in the fleet. The historical mainnet lookup table in the ARM `MathWrapper` proves this exact class of divergence has already occurred and had to be patched retroactively for specific blocks, indicating the underlying non-determinism is real and previously exploited/observed, not theoretical. New, previously-unobserved reserve ratios (easily reachable by any user injecting/withdrawing liquidity via `ExchangeInjectActuator`/`ExchangeWithdrawActuator` before trading) are not covered by the static table and remain exposed.

### Recommendation
- Remove the platform-specific `MathWrapper` split entirely and route all consensus-critical exponentiation exclusively through `StrictMathWrapper` (or better, a fixed-point/BigDecimal implementation as already prototyped in `SafeExchangeProcessor`), eliminating any code path that calls raw `Math.pow`.
- Make `SafeExchangeProcessor`/hardened calculation the unconditional default for all exchange transactions rather than a governance-gated toggle, since the non-hardened path is provably non-deterministic across architectures.
- Delete or freeze the ARM-specific hardcoded historical `powData` table once the deterministic path is mandatory, since it is a symptom of the underlying defect rather than a real fix.

### Proof of Concept
1. Deploy two full nodes participating in consensus/state validation: one on x86_64, one on ARM64, both with `allowHardenExchangeCalculation` left at its non-hardened default.
2. Create an `Exchange` pool via `ExchangeCreateActuator`, then use `ExchangeInjectActuator`/`ExchangeWithdrawActuator` (both reachable by an ordinary account) to drive the pool reserves to a ratio not present in the ARM `MathWrapper.powData` static table (i.e., any ratio absent from the hardcoded block list in `platform/src/main/java/arm/.../MathWrapper.java`).
3. Submit an `ExchangeTransactionContract` trade transaction through the legacy `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` path.
4. Compare the resulting `firstTokenBalance`/`secondTokenBalance` stored in `ExchangeCapsule` on the x86 node (using `Math.pow`) versus the ARM node (using `StrictMath.pow` fallback) — a differing truncated `long` result after `(long) issuedSupply`/`(long) exchangeBalance` demonstrates divergent post-transaction state between architectures for the same block/transaction.

package org.tron.core.capsule;

import lombok.extern.slf4j.Slf4j;
import org.tron.common.math.Maths;

@Slf4j(topic = "capsule")
public class ExchangeProcessor implements ExchangeCapsule.Processor {

  private long supply;
  private final boolean useStrictMath;

  public ExchangeProcessor(long supply, boolean useStrictMath) {
    this.supply = supply;
    this.useStrictMath = useStrictMath;
  }

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
