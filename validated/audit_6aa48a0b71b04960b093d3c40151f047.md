### Title
Same-block `DeleteKey`+`AddKey` nonce reset via `initial_nonce_value` can drop below an already-consumed nonce, enabling replay of a stale signed transaction - (`runtime/runtime/src/access_keys.rs`)

### Summary
`initial_nonce_value(block_height)` seeds a (re)created access key's nonce to `(block_height-1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER`, using only the block height at which the `AddKey` action is applied. If a `DeleteKeyAction` followed by an `AddKeyAction` for the same `PublicKey` is applied in the **same block/chunk** as, and *after*, a transaction that already consumed a higher nonce on that key, the freshly seeded nonce can be lower than the already-consumed nonce, letting the identical, previously signed transaction be resubmitted and executed a second time in a later block.

### Finding Description
`initial_nonce_value` (`runtime/runtime/src/access_keys.rs:46`) computes the new nonce purely from the current block height: [1](#0-0) 
`action_add_key`'s regular-key path (`add_regular_key`) calls this with the block height of the block currently being applied, and unconditionally overwrites the stored nonce, regardless of what nonce that public key previously reached before it was deleted.

`verify_nonce` (`runtime/runtime/src/verifier.rs:211-237`) enforces `Monotonic`/`Strict` ordering against the "current" nonce and an upper bound `tx_nonce < block_height * ACCESS_KEY_NONCE_RANGE_MULTIPLIER`: [2](#0-1) 

The safety of "recreate resets nonce" (the original mitigation for near/nearcore#3779) relies on the invariant that any nonce `N` ever accepted for a key at block height `H0` satisfies `N < H0 * MULT`, and that a *later* recreation at height `H2 > H0` seeds `(H2-1) * MULT >= H0 * MULT > N`, so the recreated key nonce is always ahead of anything usable before. That invariant only holds when the recreation happens in a **strictly later** block than the original use. It breaks down when the `DeleteKeyAction`/`AddKeyAction` pair for the same `PublicKey` land in the **same block height `H0`** as, and are applied *after*, a transaction `tx1` that used that key with nonce `N` in the range `((H0-1)*MULT, H0*MULT)`. In that case the reseeded nonce is `(H0-1)*MULT < N`, so a later resubmission of the byte-identical `tx1` (same hash, same signature) passes `verify_nonce` (since `N` is now greater than the reset "current nonce") and is re-applied.

No other check blocks this: `UniqueChunkTransactions` (`runtime/runtime/src/lib.rs:2031-2042`) only deduplicates identical transaction hashes *within a single chunk*, not across different blocks; there is no chain-wide "this tx hash was already executed" registry — replay protection is deliberately delegated entirely to the nonce + `block_hash`/`transaction_validity_period` mechanism.

### Impact Explanation
This is a replay of an already-executed transaction (double-spend/replay category): any action `tx1` originally executed once (e.g. a `Transfer`/`FunctionCall`) can be re-applied a second time against the same account/receiver after the signer's own key is deleted and recreated within the same block as `tx1`'s original execution. Depending on `tx1`'s content this can duplicate a transfer, a promise/contract call, or any other state-changing action tied to that access key.

### Likelihood Explanation
Preconditions and cost are non-trivial but attacker-controlled and cheap:
- The attacker owns the account and both the "victim" key `pk` (used for `tx1`) and a second full-access key `pk2` (used to sign `DeleteKey`/`AddKey`); no validator or node privilege is required.
- The attacker must get `tx1` (with nonce `N` deliberately chosen close to the upper bound `H0*MULT`), the `DeleteKey(pk)`, and `AddKey(pk)` transactions included and applied **in that order within the same chunk/height `H0`**. `process_tx`/mempool validation does not check the nonce upper bound before inclusion (`block_height: None` is used, skipping that check), so the attacker is not blocked from submitting `tx1` with an aggressive nonce ahead of time; but exact same-block, same-order co-inclusion of three transactions is not directly controllable by an ordinary client and depends on chunk-producer scheduling — this is a probabilistic, retryable race rather than a guaranteed single-shot exploit. It is deterministically reproducible in a runtime/apply or test-loop harness that directly constructs the chunk with the required transaction order, which is how the underlying flaw should be demonstrated and fixed.

### Recommendation
Do not derive the reseeded nonce solely from block height. Options:
- When recreating a key (`AddKeyAction` after a prior `DeleteKeyAction` for the same `public_key` within the same account), never allow the new nonce to be lower than the highest nonce previously observed for that `(account_id, public_key)` pair (e.g. persist/consult a per-account "max nonce ever used" watermark, or simply refuse to reuse `(block_height-1)*MULT` if it is less than or equal to any known prior nonce for that key).
- Alternatively/additionally, bump `initial_nonce_value` based on the true global chain progression already reflected by other keys/nonces on the account rather than solely on the current block height, so the reset can never regress below the current in-block progress of the account.

### Proof of Concept
Runtime unit test plan (mirrors existing tests in `runtime/runtime/src/access_keys.rs` and `verifier.rs`):
1. Set up an account with access key `pk` at block height `H0`, and directly set `pk`'s stored nonce to `N = (H0-1)*ACCESS_KEY_NONCE_RANGE_MULTIPLIER + 500_000` (simulating that `tx1` with this nonce was already applied at height `H0`).
2. Within the *same* `apply_state.block_height == H0`, call `action_delete_key` for `pk`, then `action_add_key` re-adding `pk` (regular full-access key) — using `pk2` semantics is not needed at the unit level, just directly invoke the two actions in sequence.
3. Assert the resulting stored nonce for `pk` equals `initial_nonce_value(H0) = (H0-1)*MULT`, which is `< N`.
4. Construct a `SignedTransaction` reusing nonce `N` for `pk` (representing the replayed `tx1`) and call `verify_and_charge_tx_ephemeral`/`validate_verify_and_charge_transaction` against the post-recreation state; assert it returns `TxVerdict::Success` (currently expected, demonstrating the bug) instead of `InvalidNonce`.
5. As a regression guard for the fix, add a companion test asserting that when delete+recreate happens at a *later* block height `H0+1`, the same replay attempt correctly fails with `InvalidTxError::InvalidNonce`.

pub(crate) fn initial_nonce_value(block_height: BlockHeight) -> Nonce {
    // Set default nonce for newly created access key to avoid transaction hash collision.
    // See <https://github.com/near/nearcore/issues/3779>.
    (block_height - 1) * near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER
}
