### Title
StackerDB unsolicited-push handler acknowledges chunk acceptance before the chunk is actually committed, allowing "accepted" inventory to diverge from stored state - (File: `stackslib/src/net/stackerdb/mod.rs`)

### Summary
`PeerNetwork::handle_unsolicited_StackerDBPushChunk` validates an incoming pushed chunk, then immediately patches an in-memory `StackerDBChunkInv` reply to claim the new `slot_version` was accepted and signs/sends that reply back to the peer — before the chunk is actually written to the StackerDB via `try_replace_chunk`. The real write only happens later, asynchronously, when the message is forwarded to the relayer (`Relayer::process_stacker_db_chunks`) and processed through `try_replace_chunk`. This is the same class of bug as the reported reentrancy issue: an "effect is externally observed/acknowledged" (the signed chunk-inv ack) is decoupled from the actual state mutation (the DB write), so the acknowledgement can be wrong if the actual write later fails (e.g., due to `StaleChunk`, `TooManySlotWrites`, or a race between two chunks for the same slot being validated against the same pre-write on-disk version).

### Finding Description
In `handle_unsolicited_StackerDBPushChunk` [1](#0-0) , the flow is:
1. Build a `StackerDBChunkInv` (or `Nack`) via `make_StackerDBChunksInv_or_Nack`, reflecting the *currently stored* slot versions.
2. Call `validate_received_chunk` against that snapshot [2](#0-1) .
3. If valid, *patch the in-memory inventory* to reflect the new version and mark it "accepted" [3](#0-2) .
4. Sign and send this "accepted" `StackerDBChunkInv` reply back to the peer [4](#0-3) , and separately return `(false, true)` to forward the raw chunk to the relayer for actual storage.

The actual persistence happens later and independently, in `Relayer::process_stacker_db_chunks`, which calls `tx.try_replace_chunk(&sc, &md, &chunk.data)` [5](#0-4) . `try_replace_chunk` re-validates the slot signer, staleness, and write-count against the database's authoritative state at that later time [6](#0-5) , and can fail (`StaleChunk`, `TooManySlotWrites`) even though the earlier validation in `handle_unsolicited_StackerDBPushChunk` (performed against a stale/racing snapshot) succeeded and an "accepted" ack was already dispatched to the peer.

This breaks the equality that a signed `StackerDBChunkInv` ack should only ever reflect state that is actually committed to the local StackerDB replica ("served/acknowledged" vs "stored"). Two chunks for the same slot arriving from different unsolicited pushes in short succession can both pass the "check" step (since the DB hasn't been updated by either yet) and both receive "accepted" replies, but only one (or neither, if a version race causes a `StaleChunk` on both applies) is ultimately committed.

### Impact Explanation
This is a remote, unauthenticated (chunk-owner-signature aside) protocol-inconsistency: unprivileged peers can trigger the node to broadcast a cryptographically signed `StackerDBChunkInv` claiming it holds chunk data it does not actually have committed. Downstream peers use `StackerDBChunkInv` to prioritize which chunks to fetch/rebroadcast (per `stackslib/src/net/stackerdb/mod.rs` module docs on inventory-driven sync) [7](#0-6) ; a node whose inventory is inconsistent with its actual store can steer honest peers to request chunks it cannot actually serve, causing failed/misleading data propagation and app-layer misbehavior for a StackerDB-based subsystem (e.g., signer message relay). This corresponds to the "serving non-canonical/mismatched state as canonical" High-impact category, since the *served inventory* diverges from what is actually stored.

### Likelihood Explanation
Reasonably likely under normal operating conditions: any pair of concurrent unsolicited `StackerDBPushChunk` messages targeting the same slot (from the same or different peers) racing against the deferred relayer-driven commit can trigger this divergence, without needing precise timing tricks — the code comment itself ("this is a reply to the pushed chunk, and we can store it right now") acknowledges the assumption that storage is immediate, when in fact it is deferred to the relayer via the `(false, true)` return path.

### Recommendation
Do not send an "accepted"/updated `StackerDBChunkInv` reply (nor mutate the in-memory `slot_versions`) until after the chunk has actually been durably written via `try_replace_chunk`. Either perform the store synchronously inside `handle_unsolicited_StackerDBPushChunk` before acking, or defer sending the ack until the relayer confirms successful storage, following a strict check-effects-acknowledge ordering so the acked inventory state is a strict function of committed state.

### Proof of Concept
Conceptual PoC (requires a running Devin session with two connections to the target node to fully exercise, but the divergence is structurally provable from the code alone):
1. Attacker (or two colluding peers) sends two valid, correctly-signed `StackerDBPushChunk` messages for the same `contract_id`/`slot_id` in quick succession, e.g. version `V1` then `V2` (`V2 > V1`), both signed by the legitimate slot owner (the attacker only needs the corresponding relayer-signed slot chunks it has legitimately obtained/observed, or is itself the owner of that slot).
2. Both messages arrive on separate connections before the relayer has processed either; `make_StackerDBChunksInv_or_Nack` reads the DB's still-unmodified slot version for both, so `validate_received_chunk` passes for both.
3. Both connections receive a signed `StackerDBChunkInv` claiming their respective new version is now stored.
4. When the relayer later processes both chunks via `process_stacker_db_chunks`/`try_replace_chunk`, the `V1` chunk may be applied first and then `V2`'s attempt to overwrite could still succeed or, depending on interleaving/ordering across `sync_results` batches, one of them can hit `StaleChunk` and be silently dropped — yet the peer that received the "accepted" ack for the dropped version has no way to know its acknowledged version was never actually committed.     pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }

            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
