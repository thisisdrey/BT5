The bug class from the report (an admin-only setter that's actually reachable by anyone because it's missing an ownership check for the "no master contract yet" state, enabling front-running of the legitimate initializer) has a direct analog in marginfi's global fee-state initialization.

### Title
Permissionless front-runnable `init_global_fee_state` / `init_global_fee_state_v2` allows an attacker to seize the `global_fee_admin` role - (File: `programs/marginfi/src/instructions/marginfi_group/init_global_fee_state.rs`)

### Summary
`init_global_fee_state` and `init_global_fee_state_v2` are meant to run exactly once per program deployment to bootstrap the singleton `FeeState`/`FeeStateV2` PDA and assign the `global_fee_admin`. Neither instruction restricts who may call it: the only signer required is an arbitrary `payer`, and the target account is a PDA derived purely from a static seed (`FEE_STATE_SEED` / `FEE_STATE_V2_SEED`), with no check that the caller is a designated deployer/program-upgrade authority.

### Finding Description
`InitFeeState` only requires `payer: Signer<'info>` and initializes the PDA with `admin_key`/`fee_wallet` parameters supplied by the caller: [1](#0-0) . There is no constraint tying `payer` (or any other account) to a known/expected deployer key, and no check that the call is happening as part of an atomic deploy+init sequence. The same pattern exists for the V2 singleton: [2](#0-1) .

Because `init` on the PDA succeeds for whoever submits the transaction first, this is functionally identical to the reported `setVibeFees`/`MintSaleBase` issue: a privileged setter (here, "become the global fee admin") is guarded only by the assumption that it will be called by the legitimate owner immediately after deployment ("no master contract yet" analog = "FeeState PDA not yet created"), but the code enforces no actual ownership check. Whoever calls it first — including an unrelated, unprivileged actor — becomes `global_fee_admin` and sets `global_fee_wallet`.

`global_fee_admin` is a powerful role documented in the permissions guide: it can edit all protocol fee parameters, redirect the global fee wallet, and panic-pause the entire protocol: [3](#0-2) . Every `MarginfiGroup` created after this point pulls its fee configuration from this account at `marginfi_group_initialize` time: [4](#0-3) , and `edit_global_fee_state` is gated purely on `has_one = global_fee_admin`: [5](#0-4) .

### Impact Explanation
An attacker who wins the race to call `init_global_fee_state` becomes the sole `global_fee_admin`/controls `global_fee_wallet` for the entire program. From there they can: redirect the destination of all protocol-level fees (`global_fee_wallet`), arbitrarily inflate `program_fee_fixed`/`program_fee_rate` charged to every group and every bank, and panic-pause the whole protocol at will via `edit_global_fee_state`/`panic_pause`. This is a permanent, protocol-wide unauthorized state takeover affecting core accounting (fee) paths, not a theoretical or purely economic/governance-only issue — it grants unauthorized control of a live administrative singleton due to a missing access-control check, matching the report's root cause exactly (privileged setter reachable without required ownership check before the legitimate owner acts).

### Likelihood Explanation
The instruction is invoked exactly once in the program's lifetime and has no re-run protection other than the account already existing; if the legitimate deploy script does not initialize it in the same atomic sequence as program deployment (e.g., separate transaction, delayed initialization, or a public/permissionless devnet/staging deployment as suggested by the STAGING/LOCALNET checks used elsewhere in this codebase), any observer who notices an uninitialized `FeeState` PDA for a live program ID can submit the init call themselves. Likelihood is moderate-to-high on any environment where deployment and fee-state initialization are not strictly atomic.

### Recommendation
Add an explicit authorization check to `InitFeeState`/`InitFeeStateV2`, e.g. require the payer/signer to match a hard-coded expected deployer/program-upgrade-authority key (analogous to the reported fix `require(msg.sender == owner())` for the no-master-contract case), or perform the `FeeState` initialization atomically inside `marginfi_group_initialize`/the deploy transaction rather than as a separate permissionless instruction.

### Proof of Concept
1. Program `marginfi` is deployed; `FEE_STATE_SEED` PDA does not yet exist.
2. Before the legitimate deployer submits their `init_global_fee_state(admin, fee_wallet, ...)` transaction, an attacker submits their own transaction calling `init_global_fee_state` with `admin = attacker_pubkey`, `fee_wallet = attacker_pubkey`.
3. The PDA `init` succeeds for the attacker's transaction (whichever lands first); the legitimate deployer's subsequent call now fails (`init` on an already-initialized account), since no one else can be assigned as `global_fee_admin` afterward except through `edit_global_fee_state`, which is gated by `has_one = global_fee_admin` now pointing to the attacker: [5](#0-4) .
4. Attacker now controls `global_fee_wallet`/fee parameters/panic-pause for the entire program.

#[allow(unused_variables)]
pub fn initialize_fee_state(
    ctx: Context<InitFeeState>,
    admin_key: Pubkey,
    fee_wallet: Pubkey,
    bank_init_flat_sol_fee: u32,
    liquidation_flat_sol_fee: u32,
    order_init_flat_sol_fee: u32,
    program_fee_fixed: WrappedI80F48,
    program_fee_rate: WrappedI80F48,
    liquidation_max_fee: WrappedI80F48,
    order_execution_max_fee: WrappedI80F48,
) -> Result<()> {
    let mut fee_state = ctx.accounts.fee_state.load_init()?;
    fee_state.global_fee_admin = admin_key;
    fee_state.global_fee_wallet = fee_wallet;
    fee_state.key = ctx.accounts.fee_state.key();
    fee_state.bank_init_flat_sol_fee = bank_init_flat_sol_fee;
    fee_state.bump_seed = ctx.bumps.fee_state;
    fee_state.program_fee_fixed = program_fee_fixed;
    fee_state.program_fee_rate = program_fee_rate;
    fee_state.liquidation_max_fee = liquidation_max_fee;
    fee_state.liquidation_flat_sol_fee = liquidation_flat_sol_fee;
    fee_state.order_execution_max_fee = order_execution_max_fee;
    fee_state.order_init_flat_sol_fee = order_init_flat_sol_fee;

    Ok(())
}

## Global Fee Admin

The `global_fee_admin` is separate from the group-level admin roles. It is stored on the `FeeState`
account (a global singleton).

**Can do:**
- Edit global fee parameters (program fee rates, origination fee shares, init fees)
- Change the global fee wallet
- Set or clear the dedicated pause delegate admin
- Panic-pause the entire protocol (with rate limiting: max 4 consecutive pauses, max 3 per day,
  each lasting 6 hours)

This role is intended for the protocol operator (e.g. the foundation) and controls protocol-level
economics and emergency pause functionality.
