### Title
Active (delegated) multisig permission can escalate to full Owner-permission control via `AccountPermissionUpdateContract` — ([File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java])

### Summary
`AccountPermissionUpdateActuator` allows a transaction signed by a non-Owner "Active" permission to overwrite the account's Owner permission entirely, because the actuator validates the requested Active-permission operations bitmap against the global "available contract types" list rather than against a hard-coded exclusion for `AccountPermissionUpdateContract`. This mirrors the authentik bug class: a delegated, lower-trust permission path (Active permission ≈ "change_user") can be used to perform an operation (rewriting Owner permission ≈ "assign superuser group") that is supposed to be gated behind the stricter, higher-trust path (Owner permission ≈ "enable_group_superuser").

### Finding Description
`AccountPermissionUpdateActuator.checkPermission()` validates the operations bitmap of an `Active` permission against `dynamicStore.getAvailableContractType()`: [1](#0-0) 

The test suite confirms that `AccountPermissionUpdateContract` **is** a member of `getAvailableContractType()` (only `ClearABIContract`/`UpdateBrokerageContract` are excluded from that bitmap): [2](#0-1) 

whereas it is deliberately excluded only from the *default* active-permission operations bitmap (`getActiveDefaultOperations()`): [3](#0-2) 

This means `checkPermission()` (the actual validation gate that decides whether an Active permission's requested operation bit is legal) does **not** reject an Owner-signed request that grants an Active key the right to invoke `AccountPermissionUpdateContract` — it only blocks that bit in the *default* permission generated at account creation. An account owner (or an attacker who already compromised only an Active key with sufficiently low bar to get the Owner to co-sign, or a delegated multisig operator with an Owner-approved but overly broad Active permission) can thus obtain an Active permission whose operations bitmap includes `AccountPermissionUpdateContract`.

Once such an Active permission exists, any transaction signed via that Active permission ID is treated as authorized to invoke `AccountPermissionUpdateContract`, since permission authorization is generically checked by contract-type bit membership, with no special case exempting this sensitive contract type: [4](#0-3) 

`AccountPermissionUpdateActuator.execute()` then unconditionally overwrites the account's Owner permission, Witness permission, and Active permissions with whatever was supplied in the contract, with no check that the operation was authorized specifically via the Owner permission (id 0) rather than a delegated Active permission: [5](#0-4) 

This is the direct analog of the authentik flaw: a "lower-trust" delegated-management capability (Active permission analogous to `change_user`) is permitted, via a generic/loose validation list (`getAvailableContractType()` analogous to the general group list), to perform the single most privileged operation on the resource (rewriting the Owner permission, analogous to assigning `is_superuser` groups) that should be strictly gated behind the higher-trust path (Owner permission, analogous to `enable_group_superuser`).

### Impact Explanation
An Active key holder who is granted (even inadvertently, e.g. via a permission template, DApp multisig tooling, or a broadly-scoped delegation) the `AccountPermissionUpdateContract` bit in their Active permission's operations can unilaterally replace the account's Owner permission with keys they control. This permanently locks out the legitimate Owner key(s) and gives the attacker full, unrestricted control of the account, including draining all TRX/TRC10/TRC20 balances and voting/staking rights — a full account takeover and theft of funds, not merely a "resource" issue.

### Likelihood Explanation
Exploitation requires that an account's Owner has, at some point, granted an Active permission that includes the `AccountPermissionUpdateContract` operation bit. This is not the default configuration, but nothing in `checkPermission()` prevents it, and no comment, validation error, or documentation in the actuator warns that doing so is dangerous — unlike the deliberate exclusion baked into `getActiveDefaultOperations()`. Any multisig tooling, exchange custody setup, or DApp that lets users customize Active-permission operation bitmaps (a supported, intended feature) could allow this to happen either accidentally or via social engineering of the Owner into approving an overly broad permission grant, after which the delegated Active key becomes equivalent to an Owner key.

### Recommendation
In `AccountPermissionUpdateActuator.checkPermission()`, explicitly forbid the `AccountPermissionUpdateContract` bit (and any other account-permission-management contract types) from ever being set on non-Owner (`Active`) permissions, regardless of `getAvailableContractType()` membership — i.e., validate Active-permission operations against `getAvailableContractType()` with `AccountPermissionUpdateContract` unconditionally masked out, matching the intent already expressed by `getActiveDefaultOperations()`. Additionally, consider requiring that `AccountPermissionUpdateContract` transactions be authorized only via `permissionId == 0` (the Owner permission).

### Proof of Concept
1. Owner account `A` creates/updates an Active permission `P` (via `AccountPermissionUpdateContract`, signed with Owner permission) whose 32-byte `operations` bitmap sets the bit for `AccountPermissionUpdateContract` (bit index = `ContractType.AccountPermissionUpdateContract.getNumber()`). `checkPermission()` accepts this because that bit is present in `getAvailableContractType()`.
2. The holder of a key listed in permission `P` (not the Owner permission) crafts and signs a new `AccountPermissionUpdateContract` transaction with `permission_id` referencing `P`, setting a brand-new Owner permission whose only key is one they control.
3. `TransactionUtil`/signature-weight checking accepts the transaction because permission `P` is `Active` type and has the `AccountPermissionUpdateContract` bit set — see `getTransactionSignWeight`. [4](#0-3) 
4. `AccountPermissionUpdateActuator.execute()` overwrites account `A`'s Owner permission with the attacker's key, completing the takeover. [6](#0-5)

  @Override
  public boolean execute(Object object) throws ContractExeException {
    TransactionResultCapsule result = (TransactionResultCapsule) object;
    if (Objects.isNull(result)) {
      throw new RuntimeException(ActuatorConstant.TX_RESULT_NULL);
    }

    AccountStore accountStore = chainBaseManager.getAccountStore();
    long fee = calcFee();
    final AccountPermissionUpdateContract accountPermissionUpdateContract;
    try {
      accountPermissionUpdateContract = any.unpack(AccountPermissionUpdateContract.class);

      byte[] ownerAddress = accountPermissionUpdateContract.getOwnerAddress().toByteArray();
      AccountCapsule account = accountStore.get(ownerAddress);
      account.updatePermissions(accountPermissionUpdateContract.getOwner(),
          accountPermissionUpdateContract.getWitness(),
          accountPermissionUpdateContract.getActivesList());
      accountStore.put(ownerAddress, account);

      adjustBalance(accountStore, ownerAddress, -fee);
      if (chainBaseManager.getDynamicPropertiesStore().supportBlackHoleOptimization()) {
        chainBaseManager.getDynamicPropertiesStore().burnTrx(fee);
      } else {
        adjustBalance(accountStore, accountStore.getBlackhole(), fee);
      }

      result.setStatus(fee, code.SUCESS);
    } catch (BalanceInsufficientException | InvalidProtocolBufferException e) {
      logger.debug(e.getMessage(), e);
      result.setStatus(fee, code.FAILED);
      throw new ContractExeException(e.getMessage());
    }

    return true;
  }
