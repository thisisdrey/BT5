## Title
CREATE2/CREATE address-collision on a pre-funded delegated-resource account permanently locks the frozen TRX of an unrelated third party - (File: actuator/src/main/java/org/tron/core/vm/program/Program.java)

### Summary
This is the closest reachable analog to the ScyllaDB bug class in the current index: an actor who is only authorized to perform a "create" operation (deploying a contract via `CREATE`/`CREATE2`) can, by choosing a predictable target address, silently take over state that belongs to a resource an unrelated account (not the deployer) previously placed there — specifically TRX delegated ("frozen for other") to that address before it became a contract.

### Finding Description
`Program.createContractImpl` computes a deterministic `newAddress` (from `CREATE`/`CREATE2`) and, when Constantinople rules are active, converts whatever pre-existing `AccountCapsule` sits at that address into a contract in place, explicitly clearing its delegated-resource state: [1](#0-0) 

Anyone can pre-fund/pre-freeze TRX toward a not-yet-existing address via `freezeForOther`/`DelegateResource`-type operations (a plain, unprivileged account action), and the address a `CREATE2` factory will eventually produce is fully predictable off-chain from `(sender, salt, initcode hash)`. The contract-deploy actuator itself only guards the *base* `CREATE` path against pre-existing accounts: [2](#0-1) 
but the in-VM `CREATE2` collision path in `createContractImpl` does not reject a pre-existing, delegated-resource-bearing account — it upgrades it and clears the resource-delegation fields (`clearDelegatedResource()`), rather than refusing the deployment or preserving the third party's claim on that state.

The `framework/src/test/java/org/tron/common/runtime/vm/FreezeTest.java` suite documents exactly this scenario end-to-end: [3](#0-2) 
A third party (`userA`/`contract`) delegates ("freezes for other") TRX to `predictedAddr` before any contract exists there. After the factory later deploys a `CREATE2` contract at that exact `predictedAddr`, subsequent `unfreezeForOtherWithException` calls fail — the delegator can no longer reclaim the delegated TRX through the normal path and must go through a separate `clearDelegatedExpireTime` + `unfreezeForOther` recovery flow that depends on internal chain mechanics, not on any action the delegator controls. The equivalent scenario is exercised again for `freezeV2`/self-destruct combinations in `testCreate2SuicideToBlackHole`/`testCreate2SuicideToAccount`: [4](#0-3) 

The `freezeV2Check`/`freezeV1Check` guards in `Program.java` exist to prevent an account with outstanding delegated resources from self-destructing/being reused, but they only check the state *at the moment of the operation*; they do nothing to protect a delegator whose target address is later claimed by a `CREATE2` deployment initiated by an entirely different, unrelated actor: [5](#0-4) 

This mirrors the ScyllaDB bug class precisely: an actor with only a narrow, "create"-scoped privilege (deploy a contract to a computed address) can reach and mutate state that belongs to a different principal (the delegator) without that principal's authorization, because the create path does not check "does someone else already have an unrevoked claim on this address" before converting it.

### Impact Explanation
A user who has frozen/delegated TRX toward a not-yet-existing address (e.g., to grant bandwidth/energy to a counterparty, or in anticipation of a future contract they trust) can have that TRX effectively locked out of normal `unfreeze`/reclaim flow once an unrelated party deploys a `CREATE2` contract to that exact address. This is a form of unauthorized state mutation / freezing of another user's funds triggered purely by an unprivileged "create contract" transaction, satisfying the "permanent freezing of funds" impact bar in the validation rules.

### Likelihood Explanation
`CREATE2` addresses are deterministic and computable off-chain by anyone who knows `(factory address, salt, init-code hash)`. Freezing TRX to an address, and later deploying a factory-created contract to that same address, are both ordinary, fee-only, unprivileged transactions reachable by any account (asset issuer/broadcaster classes in scope). No witness/SR/network-level capability is required — only knowledge of the target address and the ability to broadcast two ordinary transactions (`DelegateResourceContract`/freeze and `CreateSmartContract`/`CREATE2`), which matches the mandated reachable-surface list (actuator validate/execute, TVM opcodes).

### Recommendation
In `createContractImpl` (and the underlying `CREATE`/`CREATE2` address-collision handling), before converting an existing `AccountCapsule` into a contract, explicitly check whether that account still has outstanding delegated resources (`DelegatedFrozenV2BalanceForBandwidth/Energy`, non-empty `UnfrozenV2List`, or v1 equivalents) and reject the contract creation (mirroring the existing "Trying to create a contract with existing contract address" rejection) rather than silently clearing them. Alternatively, preserve/migrate the delegator's claim so it remains independently reclaimable after the address becomes a contract.

### Proof of Concept
1. Deploy a `CREATE2` factory contract F (unprivileged).
2. Compute `predictedAddr = CREATE2(F, salt, initcodeHash)` off-chain (deterministic, as demonstrated by `getCreate2Addr` in `FreezeTest.java`).
3. As an unrelated user, `freezeForOther`/delegate TRX to `predictedAddr` (this succeeds even though no account exists yet at that address, per `Assert.assertNull(dbManager.getAccountStore().get(predictedAddr))` in `testFreezeAndUnfreezeToCreate2Contract`).
4. Call F to `CREATE2`-deploy a contract to `predictedAddr`; the deploy succeeds and `existingAccount.clearDelegatedResource()` runs.
5. Attempt `unfreezeForOther` from the original delegator toward `predictedAddr` — this now throws (`unfreezeForOtherWithException`), demonstrating the delegator's funds are no longer reclaimable through the standard path, exactly as shown at [6](#0-5) .

**Note on confidence**: I was unable to fully trace the exact byte-level accounting inside `clearDelegatedResource()` (defined in `chainbase/.../AccountCapsule.java`, not retrieved in full) or confirm whether the `clearDelegatedExpireTime` recovery path referenced in the tests fully restores the delegator's funds without loss/without requiring cooperation from the new contract owner. If that recovery path is guaranteed to always succeed and return funds intact, the impact would be reduced from "permanent freezing" to "temporary/UX-level friction," which would fall outside the strict validation bar. This should be verified with a live Devin session against the full `AccountCapsule` and `DelegatedResourceStore` implementations before treating this as confirmed-High.

  private boolean freezeV2Check(AccountCapsule accountCapsule) {
    if (!VMConfig.allowTvmFreezeV2()) {
      return true;
    }
    long now = getContractState().getDynamicPropertiesStore().getLatestBlockHeaderTimestamp();

    boolean isDelegatedResourceEmpty =
        accountCapsule.getDelegatedFrozenV2BalanceForBandwidth() == 0
            && accountCapsule.getDelegatedFrozenV2BalanceForEnergy() == 0;
    boolean isUnFrozenV2ListEmpty =
        CollectionUtils.isEmpty(
            accountCapsule.getUnfrozenV2List().stream()
                .filter(unFreezeV2 -> unFreezeV2.getUnfreezeExpireTime() > now)
                .collect(Collectors.toList()));

    return isDelegatedResourceEmpty && isUnFrozenV2ListEmpty;
  }
