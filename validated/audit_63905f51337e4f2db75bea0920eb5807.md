## Local Analog Found

The core broken invariant in the Panoptic report is: **a deterministic contract address can be pre-seeded by an attacker with malicious state (via a throwaway self-destructing deployment), and that state survives to be inherited by the legitimate contract later deployed at the same address.** The `polkadot-sdk` repo has a structurally identical gap in `pallet-revive` + the `pallet-assets` ERC-20 precompile.

### Title
Pre-funded/pre-approved CREATE2 address state survives contract termination and is inherited by the next legitimate deployment, enabling asset drain - (File: `substrate/frame/assets/precompiles/src/lib.rs`)

### Summary
`pallet-revive` derives deterministic contract addresses via `address::create2` and `address::create1` [1](#0-0) , and `ContractInfo::new` only guards against redeploying on top of an address that is *currently* a live contract or has pending storage-deposit cleanup rows [2](#0-1) . It has no notion of, and does not clear, state owned by *other pallets* that is keyed by the mapped `AccountId` of that address — specifically `pallet_assets::Approvals`, which the ERC-20 precompile uses for allowances [3](#0-2) . Contract termination (`do_terminate` / `terminate_if_same_tx`, the runtime implementation of `SELFDESTRUCT`, EIP-6780 compliant) only removes `ContractInfoOf`/`AccountInfoOf`/`ImmutableDataOf` for the contract and refunds deposits [4](#0-3) ; it never touches `pallet_assets::Approvals`. Since an ERC-20 allowance's owner key is just `AddressMapper::to_account_id(&owner_address)` — not tied to `ContractInfo` or any contract-lifecycle marker — an allowance set while an address is occupied by an attacker's throwaway contract persists after that contract self-destructs and is inherited by whatever legitimate contract is later deployed to the same deterministic (`CREATE2`) address.

### Finding Description
1. A factory/pool pattern (e.g. a Panoptic-style pool factory) computes a future pool's address deterministically via `create2(deployer, code, input_data, salt)` before deploying it, exactly as demonstrated in `create2_works`/`existential_deposit_shall_not_be_charged_twice` tests [5](#0-4) . The formula only depends on public inputs (deployer address, init code, salt), so anyone can precompute it before the real deployment happens.
2. An attacker races to deploy a throwaway contract to that exact address first (the `ContractInfo::new` `is_contract` guard only rejects reuse while something is *currently* deployed there — it does not "reserve" the address) [2](#0-1) .
3. From that throwaway contract, the attacker calls the ERC-20 precompile's `approve()` (or `permit()`), setting an allowance from the throwaway contract's own address (as `owner`) to an attacker-controlled `spender` — this writes into `pallet_assets::Approvals` keyed by `AddressMapper::to_account_id(&owner)` [6](#0-5) .
4. In the same transaction, the attacker self-destructs the throwaway contract via `SELFDESTRUCT`, which is allowed for same-tx creations under EIP-6780 [7](#0-6) . `terminate_if_same_tx`/`do_terminate` remove the `ContractInfo`/`AccountInfoOf` entries for the address, but the `pallet_assets::Approvals` entry set in step 3 is untouched — it lives in a different pallet's storage, addressed by `AccountId`, not by `ContractInfo` [4](#0-3) .
5. Later, the legitimate factory deploys the real pool contract to that exact same address (via `CREATE2` with the same deployer/code/salt). `ContractInfo::new`'s `is_contract` check passes because the address is no longer a contract [8](#0-7) ; the deploy succeeds and users deposit funds into the new pool.
6. The attacker calls `transferFrom`/`transfer_approved` using the stale allowance and drains the pool's assets — the allowance check only inspects `pallet_assets::Approvals`, which never knew the "owner" account changed occupants [9](#0-8) .

### Impact Explanation
This breaks the "Balances, assets... must conserve value and settle exactly once to the rightful beneficiary" invariant. An unprivileged attacker can drain any ERC-20-style asset balance later deposited into a deterministically-addressed contract, without needing a hash collision (unlike the original Ethereum report) — only knowledge of the deployer, init code, and salt, all of which are public for any factory pattern used with `pallet-revive`.

### Likelihood Explanation
No hash-collision search, no validator/relayer/admin compromise, and no key leakage is required — the attacker just needs to occupy a known deterministic address before the intended deployer does, and the intended deployer typically announces salts/factory addresses publicly (as in Panoptic's `PanopticFactory`). This is a "someone gets there first" race on a public deterministic value, not a front-run of a specific victim transaction, and every step (`instantiate`, `approve`, `SELFDESTRUCT`, later legitimate `instantiate`, `transferFrom`) uses only public dispatchables/precompiles already covered in-repo.

### Recommendation
- When a contract is terminated (`do_terminate`/`terminate_if_same_tx`), sweep/cancel outstanding `pallet_assets::Approvals` (and any other pallet-level "owner" state keyed by the mapped `AccountId`) for that address before it can be redeployed to.
- Alternatively/additionally, bump a per-address "generation"/incarnation counter in `ContractInfo`/`AccountInfo` that is mixed into the `AddressMapper::to_account_id` derivation or into precompile approval keys, so that state set against generation N cannot be read/spent by a contract deployed as generation N+1 at the same address.
- Consider rejecting `SELFDESTRUCT`-then-redeploy at the same address entirely within a bounded window, matching stricter interpretations of EIP-6780 intent for factory-address reuse.

### Proof of Concept
1. Precompute `pool_addr = create2(factory_addr, pool_code, [], salt)` for a factory's advertised salt (analogous to `crate::address::create2` used in `create2_works`) [10](#0-9) .
2. Attacker calls `instantiate_with_code` (or `Caller.create2`) to deploy `AttackContract` at `pool_addr` before the factory does.
3. `AttackContract`'s constructor calls the ERC-20 precompile `approve(attackerSpender, type(uint256).max)` for the asset the pool will later hold, then executes `SELFDESTRUCT` in the same tx (mirrors `NestedDeployer.deployAndDestroyChild` pattern) [11](#0-10) .
4. Verify via `pallet_assets::Allowance` storage that the allowance entry for `AddressMapper::to_account_id(pool_addr)` → `attackerSpender` still equals `u128::MAX` after termination, and `AccountInfo::<T>::is_contract(&pool_addr)` returns `false`.
5. Factory deploys the real `Pool` contract to `pool_addr` (succeeds, since `is_contract` is false); users deposit assets into `pool_addr`.
6. Attacker calls `transferFrom(pool_addr, attacker, balance)` via the ERC-20 precompile using the pre-set allowance and drains the pool.

/// Determine the address of a contract using the CREATE2 semantics.
pub fn create2(deployer: &H160, code: &[u8], input_data: &[u8], salt: &[u8; 32]) -> H160 {
	let init_code_hash = {
		let init_code: Vec<u8> = code.into_iter().chain(input_data).cloned().collect();
		keccak_256(init_code.as_ref())
	};
	let mut bytes = [0; 85];
	bytes[0] = 0xff;
	bytes[1..21].copy_from_slice(deployer.as_bytes());
	bytes[21..53].copy_from_slice(salt);
	bytes[53..85].copy_from_slice(&init_code_hash);
	let hash = keccak_256(&bytes);
	H160::from_slice(&hash[12..])
}
