### Title
Unbounded Reference-Transaction Hook and `UpdateReferences` Processing May Cause Transaction Finalization DoS - ([File: internal/gitaly/hook/referencetransaction.go])

### Summary
The external report describes a smart-contract `finalizeBlocks` function whose gas cost scales with the number of transactions/logs in a block, with no cap on that cost relative to the block gas limit — allowing a single heavy block to break finalization. The closest unprivileged analog in Gitaly is the `reference-transaction` hook and the `UpdateReferences`/receive-pack path, which process an entirely unbounded number of reference updates from a single push or RPC call, hash/vote on all of them synchronously, and commit them as one atomic transaction — with no limit on the number of updates a single push or RPC can contain.

### Finding Description
Gitaly's `reference-transaction` hook is invoked by `git-receive-pack`/`git-update-ref` whenever references are updated, and captures **all** reference updates in a single push via stdin in one shot: `changes, err := io.ReadAll(stdin)` [1](#0-0)  followed by parsing every change line with no cap on count [2](#0-1) , hashing the whole payload with SHA-1, and casting a single vote for the whole batch that must reach quorum before the push can be finalized [3](#0-2) .

Similarly, the `UpdateReferences` RPC accepts a client-streamed, unbounded set of reference updates, queuing every one of them before a single `updater.Commit()` call finalizes them atomically: [4](#0-3)  and [5](#0-4) . There is no server-side limit on the number of `Update` messages that can be queued before commit — the proto only bounds the size of an individual message, not the aggregate count across the stream [6](#0-5) .

This mirrors the reported bug class: a single logical unit of work (a "block" in the report, a "push"/RPC call in Gitaly) has a processing cost that scales with attacker-controlled input size (number of ref changes), and there is no benchmarked, enforced limit tying that cost to a safe budget. Gitaly's own documentation acknowledges this design point explicitly: "a transaction may update thousands of references at once" and the whole set is hashed for the vote rather than being capped [7](#0-6) .

### Impact Explanation
An unprivileged pusher able to create branches/tags/refs (e.g., via a script pushing very many refs, or an import/mirror producing a huge ref-update set in one push) can force the reference-transaction hook and/or `UpdateReferences` to process, hash, and vote on an unbounded number of updates synchronously within one hook invocation/RPC. Because Gitaly's cluster voting mechanism requires quorum on this single vote before the transaction commits, an unbounded-size operation can substantially inflate hook execution time, CPU (SHA-1 over potentially very large stdin), and memory (accumulating all `Update` messages in the updater before `Commit()`), which delays or blocks finalization of that push and — since the hook and vote path is shared cluster-wide serialization state per repository — can degrade or stall other operations against the same repository, a DoS analogous to a heavy block that cannot be finalized within the "gas" budget.

### Likelihood Explanation
Reachable directly by an ordinary authenticated user with push access, no special privileges required: any push (`git push`) or client-streamed `UpdateReferences` call fully controls the number of ref updates in the payload. Repository-level concurrency limiting (`doc/backpressure.md`) throttles *concurrent* RPCs per repository but does not cap the *size* of a single push/RPC's ref-update set, so it does not mitigate this specific unbounded per-call cost.

### Recommendation
Benchmark the cost of processing N reference updates within the reference-transaction hook and `UpdateReferences`/receive-pack path, and enforce a maximum number of reference updates permitted per push/transaction (returning a client error such as `ResourceExhausted` when exceeded), similar to the way `ListBlobsRequest.limit` and pagination parameters already cap output size elsewhere in the codebase [8](#0-7) . Consider also capping in-memory accumulation of queued updates in `internal/gitaly/hook/updateref` and bounding the size of stdin read by the reference-transaction hook.

### Proof of Concept
1. Create a repository where the pushing user has write access.
2. Generate a push (or a hand-built `UpdateReferences` streaming call) containing an extremely large number of reference updates (e.g., hundreds of thousands of branch/tag creations) in a single atomic push/transaction.
3. Observe that `ReferenceTransactionHook` reads the entire stdin (`io.ReadAll`) and computes a single SHA-1 vote over it [1](#0-0) , and/or that `UpdateReferences` queues every update via `updater.Update(...)` in an unbounded loop before a single `Commit()` [9](#0-8) , with no server-side rejection based on update count, causing elevated CPU/memory use and delayed transaction finalization that can be repeated to degrade the target repository's availability.

// UpdateReferencesRequest is a request for the UpdateReferences RPC.
message UpdateReferencesRequest {
  // Update represents a reference update.
  message Update {
    // reference is the fully-qualified reference name that should be updated.
    bytes reference = 1;

    // old_object_id is the object ID the reference should be pointing to in order to be updated.
    // This has the intent to avoid time-of-check-time-of-use-style races when the object ID
    // has changed.
    //
    // If empty, the reference will be force-updated without any such checks. If set to the
    // all-zeroes object ID, this will verify that the branch did not exist previously.
    bytes old_object_id = 2;

    // new_object_id is the object ID the reference should be updated to. If set to the all-zeroes
    // object ID the branch will be deleted.
    bytes new_object_id = 3;
  };

  // repository is the repository where references shall be updated in.
  Repository repository = 1 [(target_repository)=true];
  // updates is the set of reference updates that shall be performed.
  repeated Update updates = 2;
}

When casting a vote, each voter supplies the transaction identifier as well as

Furthermore, the voter needs to let the transaction service know which

references at once, it was deemed wasteful to pass the list of all reference
