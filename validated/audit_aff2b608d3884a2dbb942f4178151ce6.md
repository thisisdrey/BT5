### Title
Gas-key nonce replay via same-height DeleteKey+AddKey reset - (File: `runtime/runtime/src/access_keys.rs::add_gas_key`)

### Summary
`add_gas_key` unconditionally reinitializes every nonce slot of a newly-added gas key to `initial_nonce_value(block_height)`, with no check for whether the same public key previously existed (and had already consumed higher nonces) at that same block height. Because `action_add_key` only blocks re-adding a key that *currently* exists, an attacker can `DeleteKey`+`AddKey` the same gas-key public key within the same block height where a nonce was already consumed, resetting the on-chain nonce back below that already-used value and enabling a bit-for-bit resubmission of a previously-signed gas-key transaction (or delegate action) to be re-verified as valid by `verify_and_charge_gas_key_tx_ephemeral`.

### Finding Description
`add_gas_key` (`runtime/runtime/src/access_keys.rs:194-228`) writes:
```
let nonce = initial_nonce_value(block_height);
for i in 0..num_nonces {
    set_gas_key_nonce(state_update, account_id.clone(), public_key.clone(), i, nonce);
}
``` [1](#0-0) 

`initial_nonce_value` is purely a function of `block_height`: `(block_height - 1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER`, with no dependence on any prior nonce history for that public key. [2](#0-1) 

`action_add_key` (`access_keys.rs:149-192`) only rejects re-adding a public key if it *currently* exists in state (`AddKeyAlreadyExists`, `:157`); once deleted, the same public key can be added again in a later action of the same or a subsequent transaction/block. [3](#0-2) 

`verify_and_charge_gas_key_tx_ephemeral` only checks nonce monotonicity relative to the value stored in the per-`(account, pubkey, nonce_index)` trie entry (`current_nonce`), via `verify_nonce(tx_nonce, effective_nonce, ...)` where `effective_nonce = max(current_nonce, pending.max_nonce)`. [4](#0-3) 

Exploit flow (all executed by an ordinary, unprivileged account owner acting on their own gas key `G`):
1. Attacker adds gas key `G` (`AddKey` with `GasKeyFullAccess`) and funds it via `TransferToGasKey`, all at block height `h`.
2. Attacker submits gas-key tx `tx1` at `nonce_index 0`, `nonce Y = initial_nonce_value(h)+1`, which is applied (and consumes/updates the stored nonce for that index to `Y`) — still within block height `h` (e.g. earlier transaction of the same block, or a receipt applied in the same chunk).
3. Within the *same* block height `h`, the attacker issues `DeleteKey(G)` followed by `AddKey(G)` (same public key). `delete_gas_key` burns any remaining balance and removes the nonce entries; `add_gas_key` immediately re-creates them, resetting nonce_index 0 back to `initial_nonce_value(h)` — identical to its value *before* `tx1` was applied, i.e., strictly less than `Y`.
4. The attacker resubmits the byte-identical, already-signed `tx1` (or a wrapped delegate action using the same signature/nonce). `verify_and_charge_gas_key_tx_ephemeral` sees `current_nonce = initial_nonce_value(h) < Y` and accepts the nonce check again, so the previously-consumed authorization is replayed and applied a second time.

This breaks the nonce-based single-use guarantee documented as an invariant ("Nonce monotonicity prevents replay", `verify_nonce`) because the guarantee assumes the stored nonce state is monotonically non-decreasing for a given `(account_id, public_key, nonce_index)`, but a delete/re-add cycle of the same public key at the same block height resets it. [5](#0-4) 

None of the existing checks stop this: nonce verification only compares against the currently-stored value (which was just reset), `AddKeyAlreadyExists` only fires while the key is live, and there is no cross-height/cross-generation tracking of a gas key's nonce history once it is deleted and recreated.

### Impact Explanation
This is a replay of a signed, previously-executed gas-key transaction/authorization — a nonce-based double-spend of an authorized action (matches NEAR's "double-spend/replay" bounty category). The severity of the resulting fund impact depends on what balance funds the replayed action's execution:
- If the attacker must re-fund `G`'s balance via a fresh `TransferToGasKey` before the replay (since `delete_gas_key` burns the prior balance), the practical damage is that a specific signed authorization (e.g. a merchant-trusted, single-use delegate action or meta-transaction with idempotency assumed from nonce uniqueness) can be re-executed a second time — an authorization/replay violation independent of where the gas balance comes from.
- I was unable to fully verify, due to tool-call limits, whether `runtime/runtime/src/action_validation.rs` enforces that a raw `AddKeyAction`'s embedded `GasKeyInfo.balance` must be zero when submitted directly (as opposed to via the VM host functions, which always construct it with `balance = Balance::ZERO`). If no such check exists, the impact escalates to unbounded token creation (an attacker could directly encode a non-zero balance in the re-added key's `GasKeyInfo`, bypassing the `TransferToGasKey`/`WithdrawFromGasKey` accounting entirely). This part is flagged as **unconfirmed** and should be independently validated.

### Likelihood Explanation
Preconditions are minimal and fully within an ordinary account owner's control: own a funded account, own a gas key on that account, and be able to submit `DeleteKey`+`AddKey` for the same public key within the same block height as a prior gas-key transaction (achievable by batching actions into one or two transactions in the same chunk). No validator, RPC-operator, or privileged access is required. This is repeatable at will by the key's owner.

### Recommendation
Do not derive the reset nonce solely from `block_height`. When re-adding an access key (particularly a gas key) that reuses a public key which previously existed on the account, persist and honor the highest nonce value ever used for that `(account_id, public_key, nonce_index)` tuple (e.g., via a tombstone/high-water-mark record that survives `DeleteKey`, or by disallowing immediate reuse of a deleted gas-key public key within the same block height). Additionally, confirm (and if missing, add) validation in `action_validation.rs`/`action_add_key` that rejects any `AddKeyAction` whose `GasKeyInfo.balance` is non-zero, since a gas key's balance must only ever be set via `action_transfer_to_gas_key`.

### Proof of Concept
Test-loop integration test (extending `test-loop-tests/src/tests/gas_keys.rs`, using patterns from `test_gas_key_add_then_fund_then_use`):
1. Add gas key `G` on `sender`, fund it, and record `nonce_index=0`'s stored nonce (`gas_key_nonce`) and current block height `h`.
2. Submit and apply `tx1`: a `Transfer` action from `G` at `nonce_index=0`, `nonce = gas_key_nonce + 1`, and confirm success (balance debited, nonce advanced) — all within block height `h`.
3. In the same block height `h`, submit `DeleteKey(G)` followed by `AddKey(G)` (same public key, `GasKeyFullAccess`, same `num_nonces`).
4. Assert via `get_gas_key_nonce` that the stored nonce for `nonce_index=0` has been reset to a value `< gas_key_nonce + 1` (i.e., back to `initial_nonce_value(h)`).
5. Re-fund `G` (or, if the balance-validation gap above is confirmed, directly encode a non-zero balance in step 3's `AddKeyAction`) and resubmit the byte-identical `tx1` bytes.
6. Assert the resubmitted `tx1` is **accepted** (`FinalExecutionStatus::SuccessValue`), demonstrating the replay — this alone violates the single-use nonce invariant regardless of the balance-conservation check.

pub(crate) fn initial_nonce_value(block_height: BlockHeight) -> Nonce {
    // Set default nonce for newly created access key to avoid transaction hash collision.
