## Title
Witness block/transaction-fee rewards accrued in a cycle where the witness's vote count is 0 are permanently and silently lost - ([File: chainbase/src/main/java/org/tron/core/service/MortgageService.java])

### Summary
This is a direct structural analog of the Velocimeter "rewards supplied to a gauge before its first depositor are permanently lost" bug. In java-tron, block rewards and transaction-fee rewards paid to a Super Representative (SR/witness) are unconditionally recorded per-cycle in `DelegationStore` regardless of whether that witness currently has any votes. The subsequent reward-distribution algorithms (both the legacy and the new "Vi" algorithm) explicitly skip accumulating/distributing the reward for any cycle in which the witness's `voteCount` (the "supply") is `0`. Just like unclaimed gauge rewards with no depositor, these witness rewards become permanently unclaimable by any voter.

### Finding Description
`MortgageService.payReward` is invoked automatically for every produced block (`payBlockReward`) and every collected transaction fee (`payTransactionFeeReward`). It unconditionally stores the post-brokerage reward amount keyed by `(cycle, witnessAddress)`, with no check on the current vote total: [1](#0-0) 

That stored reward is only ever redeemable by voters through `computeReward`. In the legacy algorithm, if the witness's recorded vote total for that cycle is `0` (or `REMARK`), the entire per-cycle reward is skipped with `continue` — it is never attributed to anyone: [2](#0-1) 

In the new "Vi" (voter-index) algorithm, the same zero-vote condition causes the delta to simply not be accumulated — the previous `Vi` is forwarded unchanged, discarding the reward that was already recorded in `DelegationStore` for that cycle: [3](#0-2) [4](#0-3) 

The vote total used for the *current* cycle's accumulation is set at the *previous* maintenance boundary and only updated for the *next* cycle at the end of `doMaintenance`, creating a window where a witness can have `voteCount == 0` for the cycle in which it is still actively producing blocks and earning fees: [5](#0-4) [6](#0-5) 

Because witness membership in the active/standby set and vote-count snapshots are only refreshed once per maintenance cycle (every 6 hours), an ordinary, unprivileged sequence of vote-withdrawal transactions (any voter can freely clear/change votes at any time via the vote-clearing/`WithdrawBalance`-style actuators) can drive a witness's recorded vote count to `0` for the current cycle while that witness continues to be part of the active set and keeps producing blocks/collecting fees until the next maintenance boundary. All rewards paid to that witness during that window are then permanently lost — never accumulated into any voter's claimable `Vi`/legacy reward, and never returned to any account.

### Impact Explanation
This results in a **permanent, unrecoverable loss of funds**: TRX that has already been earmarked as block/transaction-fee reward (net of brokerage) is written into `DelegationStore` but can never be withdrawn by any account once the zero-vote-count cycle has passed, since both `computeReward` (legacy) and `accumulateWitnessVi` (new) explicitly discard it. The funds are not returned to any pool and not recoverable through any subsequent API — a permanent freezing/loss of value analogous to the referenced gauge issue.

### Likelihood Explanation
No privileged role is required. Any set of voters can, through completely ordinary vote-withdraw/change-vote transactions, cause a witness's recorded vote count for a cycle to reach zero while the witness is still active and earning block/fee rewards during the lag before the next maintenance cycle applies the updated vote snapshot. This makes the scenario readily reachable by unprivileged transaction broadcasters, similar to how the original issue notes that "distribution happens both automatically and in a permissionless way."

### Recommendation
When accumulating reward per cycle (`MortgageService.computeReward` legacy path, and `DelegationStore.accumulateWitnessVi` / `RewardViCalService.accumulateWitnessVi` new-algorithm path), do not silently discard rewards recorded for a cycle where `voteCount == 0`. Either (a) prevent `payReward` from recording a reward for a witness whose current cycle vote count is `0` and instead redirect/return those funds (e.g., to the treasury or roll them forward to the next cycle actually attributable to voters), or (b) carry forward the un-attributed reward amount so it is combined with the next non-zero-vote cycle's reward pool rather than being dropped.

### Proof of Concept
1. Witness `W` is elected (has non-zero votes) and becomes part of the active set at maintenance boundary for cycle `N`.
2. During cycle `N`, all voters who previously voted for `W` withdraw/change their votes so that `W`'s vote count becomes 0 (ordinary `VoteWitnessContract`/withdraw actuator calls — no special privilege).
3. `W` remains part of the active witness set for the remainder of cycle `N` (set only refreshed at the next maintenance boundary) and continues to produce blocks, triggering `MortgageService.payBlockReward`/`payTransactionFeeReward`, which calls `payReward` and unconditionally stores the reward via `delegationStore.addReward(cycle, W, value)`.
4. At the maintenance boundary, `doMaintenance` records `delegationStore.setWitnessVote(nextCycle, W, 0)` for the now-zero vote count, and `accumulateWitnessVi`/`computeReward` for cycle `N` observes `totalVote == 0`/`voteCount == 0` and skips distributing that cycle's reward to any voter.
5. No account can ever claim the TRX that was recorded for `W` at cycle `N` — the funds are permanently stranded in `DelegationStore`.

```java
  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
```

```java
  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }
```
