### Title
False StackerDBChunksInv acknowledgment advertises unstored chunk version as canonical - (File: `stackslib/src/net/stackerdb/mod.rs`)

### Summary
`PeerNetwork::handle_unsolicited_StackerDBPushChunk` sends a `StackerDBChunkInv` reply that claims the local replica now holds `chunk_data.chunk_data.slot_version` for the given slot, immediately after signature/version validation, but *before* the chunk is actually committed to the on-disk `StackerDBTx`. The commit happens later and asynchronously in the relayer via `process_stacker_db_chunks`, which can still reject the write (e.g. `StaleChunk`, `TooManySlotWrites`, or DB error) with no correction sent to the peer that already received the affirmative inventory ACK.

### Finding Description
In `stackslib/src/net/stackerdb/mod.rs`, `handle_unsolicited_StackerDBPushChunk` builds a `StackerDBChunkInv` reply (`payload`) from the current on-disk inventory (`make_StackerDBChunksInv_or_Nack`), validates the incoming push with `validate_received_chunk` (size/expected-version/signature/max-writes checks against the *snapshotted* inventory), and then unconditionally patches the in-memory copy of the reply's `slot_versions[slot_id]` to the pushed chunk's `slot_version`:
```
*slot_version = chunk_data.chunk_data.slot_version;
```
When `send_reply` is true, this patched `payload` is signed and sent straight back to the sender as the node's `StackerDBChunkInv` — i.e., it tells the peer "I now have version N of slot S" — without ever calling into `StackerDBTx::try_replace_chunk` on this code path. The actual write only occurs afterward, out-of-band, when the message is forwarded to the relayer (`return Ok((false, true))`) and processed by `Relayer::process_pushed_stacker_db_chunks` → `process_stacker_db_chunks`, which calls `tx.try_replace_chunk(...)`. That call independently re-verifies the signature and version, and can still fail (stale version due to a race with another writer, `TooManySlotWrites`, DB error, oversized chunk relative to config drift, etc.), in which case the chunk is simply dropped with a log line — the peer that already received the affirmative ACK is never corrected.

This breaks the equality between "advertised inventory" and "actually stored data": the local node's claimed slot version can diverge from what's really persisted, because the ACK is generated from validation state that precedes, and is decoupled from, the actual commit.

### Impact Explanation
This matches the "steering a node off the tip via false inventory" class of impact for StackerDB gossip: a peer that trusts our `StackerDBChunkInv` reply as ground truth for our replica's holdings may decide it doesn't need to independently fetch/relay that chunk version (since we already claim to have it), even though the write can still fail on our side. This can create transient inconsistency in signer/StackerDB replication (e.g. delayed signer message propagation) triggerable by any peer that can race two pushes to the same slot faster than the relayer processes the first.

### Likelihood Explanation
Medium likelihood: it requires only sending two (or more) valid, properly signed `StackerDBPushChunk` messages for the same slot with increasing versions in quick succession from one or more connections, racing the asynchronous relayer commit — no privileged key or node-internal access is required, only a valid signer/StackerDB slot key (which for many StackerDB configs, e.g. signer message replicas, is externally known/expected to write).

### Recommendation
Do not synthesize the ACK's `slot_versions` entry from the *unwritten* pushed chunk. Either (a) defer sending the `StackerDBChunkInv` reply until after the chunk has actually been committed via `try_replace_chunk` on this code path, or (b) only patch the advertised slot version once storage succeeds, and otherwise reply with the version that is actually on disk (i.e., don't patch it at all, and let a future `StackerDBGetChunksInv` reflect the ground truth after the relayer's write completes).

### Proof of Concept
1. Configure a StackerDB slot owned by key `K`.
2. From two separate connections (or a single connection), rapidly send two properly-signed `StackerDBPushChunk` messages for slot `S` with versions `V` and `V+1`.
3. The p2p thread validates and ACKs both with increasing `slot_versions[S]` values in the `StackerDBChunkInv` replies (as shown at `stackslib/src/net/stackerdb/mod.rs:807` and `858-870`), telling each sender "I now have version V" / "V+1" respectively.
4. Meanwhile, both pushes are forwarded to the relayer; when `process_stacker_db_chunks` (`stackslib/src/net/relay.rs:2406-2437`) processes them, the second-to-arrive write for the higher version can race and be interleaved such that a `try_replace_chunk` call fails (e.g., `StaleChunk` if delivery order to the DB differs from the ACK order), silently dropping the update the peer was already told succeeded — leaving the peer's belief about our inventory out of sync with what's actually stored.
