### Title
Default (non-hardened) `ExchangeProcessor` uses floating-point (`double`) bancor math, allowing precision-loss exploitation to drain TRX/TRC10 from `Exchange` pairs - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
`ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator` allow any account to trade against TRON's built-in bancor-style `Exchange` pairs via a single signed transaction. The price/amount returned for every trade is computed by `ExchangeCapsule.transaction()`, which by default (when `allowHardenExchangeCalculation` is disabled — the default state) uses `ExchangeProcessor`, a `double`-based floating-point implementation of the bancor relay-token formula, instead of the `BigDecimal`-based `SafeExchangeProcessor` that was introduced later. [1](#0-0) [2](#0-1) 

### Finding Description
`ExchangeCapsule.transaction()` selects between two price-calculation strategies based on the `allowHardenExchangeCalculation` dynamic property:
```java
Processor processor = hardenedCalc
    ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);
``` [3](#0-2) 

The legacy `ExchangeProcessor` computes the bancor "issued supply" and "exchange balance" using native `double` arithmetic and `Math.pow`:
```java
double issuedSupply = -supply * (1.0
    - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
...
double exchangeBalance = balance
    * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
``` [4](#0-3) 

This is exactly the reported bug class: the amount of TRX/TRC10 an attacker receives (or pays) on a trade is derived from an untrusted/imprecise pricing computation whose output is trusted verbatim by the actuators that mutate account balances and the `ExchangeCapsule`'s pooled balances:
```java
long anotherTokenQuant = exchangeCapsule.transaction(tokenID, tokenQuant,
    dynamicStore.allowStrictMath(), allowHarden());
...
accountCapsule.addAssetAmountV2(anotherTokenID, anotherTokenQuant, dynamicStore, assetIssueStore);
``` [5](#0-4) 

Floating-point `double` computation of `pow()`/division introduces rounding error that compounds across repeated small trades against the same exchange pair (analogous to a malicious/untrusted "curve" returning an incorrect price). Because `allowHardenExchangeCalculation` defaults to disabled (`0`) — confirmed by the test asserting the unsafe path is used by default:
```java
// Default: hardened disabled (==0) -> contract is treated as exchange
chainManager.getDynamicPropertiesStore().saveAllowHardenExchangeCalculation(0);
Assert.assertTrue("Exchange tx must be detected when hardened disabled", ...);
``` [6](#0-5) 

an attacker can repeatedly call `ExchangeTransactionContract` (via `/wallet/exchangetransaction` or gRPC `ExchangeTransaction`) with quantities chosen to maximize the rounding bias of the `double`-based formula, extracting more value from the pool's TRX/TRC10 balance than the true bancor curve would allow, while the `Exchange`'s internal `firstTokenBalance`/`secondTokenBalance` bookkeeping is updated using the same biased numbers — so the discrepancy is never detected and compounds trade after trade.

### Impact Explanation
An unprivileged, unpermissioned account (any signer who can craft an `ExchangeTransactionContract`) can systematically bias trades to extract more TRX/TRC10 than deposited, gradually draining the pooled liquidity in any `Exchange`/`ExchangeV2` pair created via `ExchangeCreateContract`. This is a direct theft-of-funds / unbacked-balance issue reachable from a single broadcast transaction, matching the High severity of the referenced report (drain of pooled assets due to trusting an imprecise/untrusted price computation).

### Likelihood Explanation
High. `ExchangeTransactionContract` is a standard, publicly reachable contract type requiring no special permission beyond owning the tokens/TRX being sold, and `allowHardenExchangeCalculation` defaults to disabled, meaning the vulnerable floating-point path is the one actually exercised on-chain unless a committee proposal has explicitly enabled the safer BigDecimal path.

### Recommendation
Make `SafeExchangeProcessor` (BigDecimal-based, deterministic rounding) the only exchange pricing implementation, removing the legacy `double`-based `ExchangeProcessor` path entirely (or force `allowHardenExchangeCalculation` to always be treated as enabled) so that trade math cannot be exploited by choosing quantities that maximize floating-point rounding bias. Additionally, add invariant checks in `ExchangeInjectActuator`/`ExchangeWithdrawActuator`/`ExchangeTransactionActuator` verifying the constant-product/bancor invariant approximately holds after each operation, rejecting outlier results before mutating account and exchange balances.

### Proof of Concept
1. Ensure `allowHardenExchangeCalculation` is at its default value (`0`, disabled) — the normal chain state. [7](#0-6) 
2. Create an `Exchange` pair via `ExchangeCreateContract` (e.g., TRX vs. a TRC10 token) with a modest pool size, as done in `ExchangeCreateActuatorTest`. [8](#0-7) 
3. Repeatedly submit `ExchangeTransactionContract` transactions (small `quant` values chosen to maximize `Math.pow` rounding error in `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply`), each time calling into `ExchangeCapsule.transaction()` which uses the unsafe `double`-based `ExchangeProcessor` by default. [9](#0-8) 
4. Observe that the attacker's cumulative extracted `anotherTokenQuant` across many trades exceeds what the exact (BigDecimal) bancor formula in `SafeExchangeProcessor` would have returned for the same sequence of trades — confirmed by the existing test `hardenedSuccessExchangeTransaction`, which shows the two processors are expected to diverge and only the hardened path is "safe." [10](#0-9)

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
