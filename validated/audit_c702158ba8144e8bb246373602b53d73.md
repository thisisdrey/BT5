### Title
Missing AllowTvmCompatibleEvm version-1 contract restriction in TransferAssetActuator allows TRC10 to be sent where TransferActuator would reject the equivalent TRX transfer - (File: actuator/src/main/java/org/tron/core/actuator/TransferAssetActuator.java)

### Summary
`TransferContract` (native TRX transfer) validation blocks sending value directly to an EVM-compatible (version 1) smart contract once the `AllowTvmCompatibleEvm` proposal is active, instructing users to instead use `TriggerSmartContract` [3](#0-2) . `TransferAssetContract` (TRC10 asset transfer), which reaches the same class of destination account (a deployed smart contract) through the same actuator/broadcastable-transaction path, only re-implements the older `ForbidTransferToContract` check and completely omits the version-1/`AllowTvmCompatibleEvm` restriction [2](#0-1) .

### Finding Description
Both actuators represent "plain value transfer to an address" contracts that must apply the same account-type restrictions before crediting a contract account outside of TVM execution. `TransferActuator.validate()` was updated with a second restriction after the `AllowTvmCompatibleEvm` proposal (`ALLOW_TVM_COMPATIBLE_EVM`, proposal #60) specifically to prevent value being sent to version-1 (EVM-compatible bytecode) contracts via a plain actuator, because such contracts must instead be invoked via `TriggerSmartContract` [3](#0-2) . This mirrors the reported bug class in the external report: two structurally parallel code paths implement overlapping-but-incomplete restriction logic, and the incomplete one allows the restricted operation to bypass the safeguard by using a semantically-equivalent alternate function.

`TransferAssetActuator.validate()` checks `dynamicStore.getForbidTransferToContract()` only, and never consults `dynamicStore.getAllowTvmCompatibleEvm()` or the target's `ContractCapsule.getContractVersion()` [2](#0-1) . Any signed `TransferAssetContract` transaction can therefore deliver TRC10 tokens directly into a version-1 (EVM-compatible) contract's balance, exactly the scenario the committee-controlled `AllowTvmCompatibleEvm` proposal was designed to forbid for TRX.

### Impact Explanation
Version-1/EVM-compatible contracts are compiled and executed under different VM semantics than native TVM contracts, and the restriction exists precisely because these contracts should not receive value via the bare actuator path — only via `TriggerSmartContract`, which properly invokes the contract's payable/fallback logic to account for and route the incoming value. Delivering TRC10 balance to such a contract outside of `TriggerSmartContract` risks tokens being credited to the contract's TRC10 balance without any corresponding contract-level accounting or ability to reason about/withdraw them, since the contract logic was never invoked. This can result in TRC10 assets becoming permanently stranded/unrecoverable in the contract account, i.e., a permanent freezing of user funds triggered by a single ordinary `TransferAssetContract` transaction from any unprivileged asset holder — no special privileges are required to trigger it.

### Likelihood Explanation
This is trivially reachable by any account holding a TRC10 token: broadcast a normal `TransferAssetContract` transaction whose `to_address` is a deployed version-1 (EVM-compatible) contract. No committee, SR, or node-operator cooperation is needed beyond the `AllowTvmCompatibleEvm` proposal already being active (which is the intended operating state once the hard fork activates). The condition is exercised purely through `TransferAssetActuator.validate()`/`execute()` on an ordinary signed transaction.

### Recommendation
Add the same `AllowTvmCompatibleEvm`/contract-version-1 check present in `TransferActuator.validate()` to `TransferAssetActuator.validate()` (and consider factoring the shared logic into a common helper to prevent this kind of check divergence going forward):

```java
if (dynamicStore.getAllowTvmCompatibleEvm() == 1
    && toAccount.getType() == AccountType.Contract) {
  ContractCapsule contractCapsule = chainBaseManager.getContractStore().get(toAddress);
  if (contractCapsule != null && contractCapsule.getContractVersion() == 1) {
    throw new ContractValidateException(
        "Cannot transfer asset to a smartContract which version is one. "
            + "Instead please use TriggerSmartContract");
  }
}
```

### Proof of Concept
1. Assume the committee has activated `allowTvmCompatibleEvm` (proposal #60), so newly created contracts get `version = 1` [4](#0-3) .
2. Deploy an EVM-compatible (version-1) contract via `CreateSmartContract`.
3. An account holding a TRC10 asset broadcasts a `TransferAssetContract` with `to_address` set to that contract's address and a positive `amount`.
4. `TransferAssetActuator.validate()` only evaluates `getForbidTransferToContract()`; since it does not check `getAllowTvmCompatibleEvm()`/`getContractVersion()`, validation passes and `execute()` credits the TRC10 balance directly to the contract account [5](#0-4) .
5. Attempting the equivalent operation with `TransferContract` (plain TRX) against the same contract address would be rejected with `"Cannot transfer TRX to a smartContract which version is one..."` [6](#0-5) , confirming the inconsistency between the two otherwise-parallel transfer actuators.
