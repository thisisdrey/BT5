### Title
Anyone can instantly accrue `balance * 1` reward tokens when a token's reward index is at `INITIAL_INDEX`, due to a missing `>=` boundary in `RewardsDistributor._calculateTokenDelta` — (File: contracts/RewardsDistributor.sol)

### Summary
Metronome's `RewardsDistributor` is the analog of the audit's `AbstractRewarder`: it tracks per-account checkpoints (`accountIndexOf`, analogous to `userRewardPerTokenPaid`) and settles rewards lazily via `_updateTokensAccruedOf`. To prevent the "rewards since the beginning" bug, `_calculateTokenDelta` backfills a fresh account's index to `INITIAL_INDEX` — but only when the global index is **strictly greater** than `INITIAL_INDEX`. When `tokenStates[token_].index == INITIAL_INDEX` (i.e., right after a token's speed is first set and before any time accrues), a fresh `accountIndexOf == 0` is left at `0`, producing `_deltaIndex = INITIAL_INDEX = 1e18` and `_tokensDelta = balanceOf(account) * 1`. Any holder of that DepositToken/DebtToken can instantly credit themselves reward tokens equal to their token balance and drain the distributor's `rewardToken` balance via `claimRewards`. [1](#0-0) [2](#0-1) 

### Finding Description
When the governor first calls `updateTokenSpeed(token_, speed_ > 0)` (or `tokenSpeedKeeper` calls `syncTokenSpeed`) for a token that has never had speed, `_updateTokenSpeed` initializes `tokenStates[token_] = TokenState({index: INITIAL_INDEX, timestamp: now})` [3](#0-2) . Until `block.timestamp` advances past that timestamp, `_calculateTokenIndex` returns no new index and the stored index stays exactly `INITIAL_INDEX` [4](#0-3) .

During this window, `_calculateTokenDelta` computes for any account with `accountIndexOf[token_][account] == 0`:

```
if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX)  // false when _tokenIndex == INITIAL_INDEX
    _accountIndex = INITIAL_INDEX;
_deltaIndex = _tokenIndex - _accountIndex;              // = 1e18 - 0 = 1e18
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);  // = balanceOf(account_)
``` [5](#0-4) 

The checkpoint can be reached without any privileged role:
- `updateBeforeMintOrBurn(token_, account_)` is permissionless ("This function also may be called by anyone to update stored indexes") and calls `_updateTokensAccruedOf`, which persists `tokensAccruedOf[account] += balance` [6](#0-5) [7](#0-6) .
- `claimRewards(accounts_, tokens_)` is permissionless, refreshes accrued amounts, and pays out `tokensAccruedOf[account]` if the distributor holds enough `rewardToken` [8](#0-7) [9](#0-8) .

### Impact Explanation
Theft of unclaimed yield / reward drain. For each token at the moment its reward speed is initialized, every existing balance holder (and anyone who sandwiches the governor/keeper `updateTokenSpeed` transaction with a deposit) can claim reward tokens equal to 100% of their msdTOKEN/debt-token balance, until the distributor's `rewardToken` balance is exhausted. This steals rewards owed to honest depositors/borrowers. Unlike the Tokemak report (which required pre- vs post-transfer ordering), Metronome correctly updates indexes before balance changes via `updateRewardsBeforeMintOrBurn`/`updateRewardsBeforeTransfer` modifiers on `_mint`, `_burn`, and `_transfer` [10](#0-9)  — but the `INITIAL_INDEX` boundary in `_calculateTokenDelta` leaves an equivalent accounting hole.

### Likelihood Explanation
The window is narrow but real: it exists once per `(distributor, token)` pair — the block in which speed transitions `0 → >0` for a never-initialized token — and re-opens conceptually whenever `index == INITIAL_INDEX` persists (e.g., the keeper's `syncTokenSpeed` path on Optimism, which recomputes speed each call but preserves the stored index/timestamp pattern). An attacker only needs to hold (or flash-acquire via `deposit`/`DebtToken.issue` in the same block) a balance of the token and call `updateBeforeMintOrBurn` then `claimRewards`. Both are public, unauthenticated entry points; no governor, keeper, or admin action by the attacker is needed beyond the scheduled (predictable, mempool-visible) `updateTokenSpeed`/`syncTokenSpeed` call. Magnitude is bounded by the attacker's token balance and the distributor's reward inventory, which can be substantial since the distributor holds rewards for all users.

### Recommendation
Fix the boundary so a zero `accountIndexOf` is always backfilled to the current index baseline:

```solidity
// contracts/RewardsDistributor.sol::_calculateTokenDelta
if (_accountIndex == 0 && _tokenIndex >= INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}
```

or, more robustly, initialize `accountIndexOf` to `INITIAL_INDEX` whenever it is `0` and the token state exists (`index > 0`), so `_deltaIndex` can never span the full initial index for a fresh account. Add a regression test that deposits, initializes speed in the same block, and asserts `claimable`/`tokensAccruedOf` remain `0`.

### Proof of Concept
Hardhat-style, against a live-fork or unit-mock setup mirroring `test/RewardDistributor.test.ts`:

```ts
// Setup: pool with a DepositToken msdTOKEN registered in RewardsDistributor.
// 1. Alice deposits collateral, minting msdTOKEN (accountIndexOf == 0, balance > 0).
await depositToken.deposit(amount, alice.address); // updateBeforeMintOrBurn runs while index == 0 -> no-op

// 2. Governor (or tokenSpeedKeeper via syncTokenSpeed) sets speed for msdTOKEN for the first time.
await rewardsDistributor.connect(governor).updateTokenSpeed(msdTOKEN.address, parseEther('1'));
// tokenStates[msdTOKEN].index == INITIAL_INDEX (1e18), timestamp == now

// 3. In the SAME block/timestamp (no index growth yet), attacker EOA Alice triggers settlement.
await rewardsDistributor.connect(alice).updateBeforeMintOrBurn(msdTOKEN.address, alice.address);

// BUG: accountIndexOf stays 0 because index == INITIAL_INDEX, deltaIndex = 1e18
expect(await rewardsDistributor.tokensAccruedOf(alice.address)).to.eq(await msdTOKEN.balanceOf(alice.address));
// Expected: 0 — Alice held tokens for zero seconds of reward accrual.

// 4. Alice drains the distributor's reward token up to its balance.
const distributorBal = await rewardToken.balanceOf(rewardsDistributor.address);
await rewardsDistributor.connect(alice)['claimRewards(address)'](alice.address);
expect(await rewardToken.balanceOf(alice.address)).to.eq(min(accrued, distributorBal)); // > 0, stolen
```

The same path works through `DebtToken` balances (debt-token rewards) and through any user who already holds a balance when speed is initialized — no timing race is even needed for pre-existing holders, since the window lasts until the first block where `block.timestamp > tokenStates.timestamp`.
