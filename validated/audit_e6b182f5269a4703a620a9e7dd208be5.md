### Title
Unprivileged attacker can permanently block a victim from adding collateral by saturating `depositTokensOfAccount`/`debtTokensOfAccount` with dust, preventing rescue of an unhealthy position - ([File: contracts/Pool.sol])

### Summary
The SPICE crash bug maps to a reachable denial-of-service class in Metronome: `Pool` enforces a hard cap `MAX_TOKENS_PER_USER = 30` on the combined length of an account's `depositTokensOfAccount` and `debtTokensOfAccount` sets, and any transaction that would add a new token to a victim's set reverts with `UserReachedMaxTokens`. Because `DepositToken.deposit(amount_, onBehalfOf_)` accepts an arbitrary beneficiary and `DepositToken.transfer(to_, ...)` accepts an arbitrary recipient, an EOA can push dust amounts of every registered deposit token into a victim's account until the cap is hit, after which the victim cannot deposit any new collateral type.

### Finding Description
`Pool.onlyIfAdditionWillNotReachMaxTokens` reverts when `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= MAX_TOKENS_PER_USER` [1](#0-0) . Entries are added by `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount`, which are called from `DepositToken._mint`/`_transfer` whenever the recipient's balance goes from zero to positive [2](#0-1) [3](#0-2) . `deposit` mints to an attacker-chosen `onBehalfOf_` [4](#0-3) , and `transfer` sends to an arbitrary `to_` [5](#0-4) , so no victim consent is required. A victim holding an unhealthy or marginally-healthy position who tries to deposit a collateral type not already in their set will revert in `_mint` → `addToDepositTokensOfAccount`, and `liquidate` has no such dependency for the liquidator, so the position remains liquidatable while the victim is blocked.

### Impact Explanation
The invariant broken is liveness of collateral top-up: a borrower who must add a *new* collateral asset to avoid liquidation is DoS'd, leading to liquidation loss of their position (indirect theft of user funds via forced liquidation). On low-fee chains (Base, Optimism, Hemi, Swell deployments exist), the attacker can cheaply re-fill any slot the victim clears by transferring dust back out, sustaining the freeze across the victim's rescue window. Clearing requires `balanceOf → 0` removal via `_transfer` [6](#0-5) , which the attacker can race.

### Likelihood Explanation
Fully permissionless: requires only an EOA with dust amounts of each underlying (or dust msdTOKEN balances). Cost is bounded by `30 × (deposit fee + gas)`. Success depends on the victim needing a new collateral type, but any multi-collateral user near liquidation qualifies; this matches the external report's "crafted messages cause process to crash" availability-loss class without privileged roles.

### Recommendation
Do not auto-add deposit tokens on plain `transfer`/`deposit on behalf`, or track tokens only for the depositor's own address; alternatively keep per-account sets but allow `deposit` to succeed while skipping the bookkeeping add, or raise/remove the cap and iterate lazily.

### Proof of Concept
Hardhat/foundry fork skeleton:
```solidity
// victim has a position near liquidation with depositToken A only
for (uint i; i < N_DEPOSIT_TOKENS; ++i) {
    depositToken[i].deposit(1 wei, victim); // or transfer(victim, 1 wei)
}
// victim now has 30 entries
vm.prank(victim);
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
depositTokenB.deposit(topUpAmount, victim); // reverts inside _mint -> addToDepositTokensOfAccount
// liquidator seizes victim position while top-up is blocked
pool.liquidate(victim, ...);
```

    }
