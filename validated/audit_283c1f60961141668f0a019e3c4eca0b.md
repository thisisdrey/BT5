### Title
Missing slippage/minimum-output protection in `ExchangeWithdrawContract` allows exchange creator to receive far less of the paired token than expected - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`ExchangeWithdrawContract` lets the creator of a bancor-style TRX/TRC10 `Exchange` pool withdraw `quant` of one token and receive a proportional amount (`anotherTokenQuant`) of the paired token, computed from the pool's *current* reserves at execution time. Unlike `ExchangeTransactionContract`, which has an explicit `expected` field used to enforce a minimum-received check, `ExchangeWithdrawContract` has no such field, so the caller cannot bound the minimum amount of the paired token they are willing to accept.

### Finding Description
The proto definitions show the asymmetry directly: [1](#0-0) 

`ExchangeWithdrawContract` only carries `owner_address`, `exchange_id`, `token_id`, `quant` — no `expected`/minimum field — while `ExchangeTransactionContract` carries an extra `expected` field that is used for slippage protection.

In `ExchangeWithdrawActuator`, the amount of the paired token to be paid out (`anotherTokenQuant`) is derived from the pool's live `firstTokenBalance`/`secondTokenBalance` at validation/execution time: [2](#0-1) 

and again recomputed in `execute()`: [3](#0-2) 

The only checks performed are that `anotherTokenQuant > 0`, that reserves are sufficient, and (in "hardened" mode) that the rounding precision is within 0.0001 of the exact ratio — there is no check that `anotherTokenQuant` meets any caller-specified floor. Compare this with `ExchangeTransactionActuator`, which validates the trade against the caller-supplied `expected` value: [4](#0-3) 

Because the pool's reserves (`firstTokenBalance`/`secondTokenBalance`) can be changed by any other `ExchangeTransactionContract`, `ExchangeInjectContract`, or `ExchangeWithdrawContract` transaction that lands in an earlier position within the same block or an earlier block (including transactions submitted or reordered by the block-producing witness), the ratio used to compute `anotherTokenQuant` at the time the creator's withdraw transaction is actually executed can differ arbitrarily from the ratio observed when the creator built and signed their transaction.

### Impact Explanation
An exchange creator's `ExchangeWithdrawContract` transaction is exposed to unbounded price movement between transaction construction and on-chain execution. A third party (or the block producer itself) can execute large `ExchangeTransactionContract` trades against the same pool immediately before the withdraw transaction is applied, skewing the `firstTokenBalance`/`secondTokenBalance` ratio so that the creator's withdrawal yields a much smaller quantity of the paired token than intended. This is a direct loss-of-funds bug class (unbacked/incorrect balance transfer) reachable by any account that created an exchange pool and calls withdraw — it matches the reported bug class (no slippage protection on a claim/withdraw whose output is recomputed from live state) but manifests here in the TRX/TRC10 bancor exchange withdraw path rather than in a vault-claim path.

### Likelihood Explanation
Reaching this path requires only a normal, unprivileged account that created an `Exchange` (via `ExchangeCreateContract`) to submit an `ExchangeWithdrawContract` transaction — no special permissions, witness/committee status, or malicious-node behavior needed. The precondition (another party trading against the same pool before the withdraw is applied) is a routine, expected occurrence for any active exchange, making the scenario realistically triggerable, though it is more of an economic MEV/front-running risk than a guaranteed exploit on every call — likelihood is therefore moderate, contingent on pool activity and transaction ordering within a block.

### Recommendation
Add an `expected`/minimum-output field to `ExchangeWithdrawContract` (mirroring `ExchangeTransactionContract.expected`) and enforce, in `ExchangeWithdrawActuator.doValidate()`/`execute()`, that the computed `anotherTokenQuant` is not less than the caller-specified minimum, failing validation otherwise (as is already done for `ExchangeTransactionContract` via the "token required must greater than expected" check).

### Proof of Concept
1. Account A creates an `Exchange` pool with tokens X/Y via `ExchangeCreateContract`, becoming `creatorAddress`.
2. Account A builds and signs an `ExchangeWithdrawContract` transaction to withdraw `quant` of token X, expecting to receive `anotherTokenQuant` of token Y based on the pool ratio observed at signing time (as computed in `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java:218-227`).
3. Before A's transaction executes on-chain, another account B (or the block producer) submits and gets included one or more large `ExchangeTransactionContract` trades against the same pool, shifting `firstTokenBalance`/`secondTokenBalance` substantially (`actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java:67-91`).
4. When A's withdraw transaction executes, `anotherTokenQuant` is recomputed from the now-skewed reserves (`ExchangeWithdrawActuator.java:74-90`), yielding a far smaller amount of token Y than A anticipated, with no mechanism in the contract to reject the transaction based on a minimum acceptable amount, since `ExchangeWithdrawContract` has no `expected` field (`protocol/src/main/protos/core/contract/exchange_contract.proto:24-29`).
