### Title
Gas-key delete/re-add resets per-index nonce below previously consumed values, enabling meta-transaction (DelegateAction) replay - (File: runtime/runtime/src/access_keys.rs)

### Finding Description
`add_gas_key` re-initializes every gas-key nonce slot to `initial_nonce_value(block_height) = (block_height-1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` whenever a gas key is (re)created, with no dependency on any nonce value previously consumed under the same public key: [1](#0-0) 

`delete_gas_key`, invoked from `action_delete_key`, unconditionally removes all `num_nonces` nonce rows for the key: [2](#0-1) 

`initial_nonce_value` is purely a function of `block_height`, unrelated to what nonce was last used for that `(account, pubkey, index)` triple: [3](#0-2) 

Delegate-action nonce validation for a gas key reads only the currently-stored per-index nonce (`current_nonce`) and requires the new nonce be strictly greater than it, then persists the new nonce back into that slot on success: [4](#0-3) [5](#0-4) 

Exploit flow (attacker acts on their own funded account with a gas key, which is a fully unprivileged action):
1. At block height `H1`, attacker signs and has relayed a `DelegateAction` using gas-key `nonce_index = i` with a nonce `N` close to the upper bound `H1 * ACCESS_KEY_NONCE_RANGE_MULTIPLIER`. It validates (`N > current_nonce`) and executes, and `set_gas_key_nonce` persists `N` into slot `i` (`actions.rs:718-726`).
2. In the same block (or a nearby block `H2` such that `(H2-1) * MULTIPLIER <= N`), the attacker submits `DeleteKey(pubkey)` followed by `AddKey(pubkey, same GasKeyFullAccess/GasKeyFunctionCall permission)`. `delete_gas_key` wipes all nonce rows, and `add_gas_key` reseeds slot `i` to `initial_nonce_value(H2) = (H2-1) * MULTIPLIER`, which can be `<= N`.
3. The attacker (or a relayer still holding the original signed `DelegateAction`, since it is a self-contained signed message, not a single-use ephemeral token enforced elsewhere) resubmits the exact same signed `DelegateAction` with nonce `N` and `nonce_index = i`. `current_nonce` is now the freshly reset, lower value, so `delegate_nonce.nonce() <= current_nonce` (`actions.rs:632`) is false, and the stale action passes validation again and re-executes.

No existing check prevents this: the nonce-replay defense is scoped entirely to the per-`(account, pubkey, index)` stored value, and that value is reset to a block-height-derived constant on every `AddKey` for a gas key, with no floor tied to nonces already consumed under prior incarnations of the same public key.

### Impact Explanation
This breaks the "each signed DelegateAction executes at most once" invariant relied upon by meta-transaction relayers and any contract logic that treats a delegated call as non-replayable (e.g., one-time claims, single-use vouchers, idempotent-by-nonce operations). This is a double-spend/replay category finding: a previously executed, signed `DelegateAction` can be made to execute a second time by the key owner cycling delete/re-add of their own gas key, at attacker-chosen timing relative to block height.

### Likelihood Explanation
The attacker needs only: a funded account, a gas key with at least one used nonce index, and the ability to submit ordinary `DeleteKey`/`AddKey` transactions (all standard, unprivileged operations) timed within the narrow block-height window where `(H2-1) * MULTIPLIER <= N`. Since `N` is chosen by the signer and can be set close to the contemporaneous upper bound, this window is attacker-controllable (can even occur within the very same block as the original consumption), making the attack practically feasible and repeatable across nonce indices and accounts.

### Recommendation
When (re)creating a gas key nonce slot in `add_gas_key`, the new nonce must never be lower than the value most recently used for that `(account_id, public_key, index)` triple — either persist a monotonic "high-water mark" independent of key deletion, or refuse to reuse a public key for a new gas key at all (require a fresh key), or seed new gas-key nonces from a per-account/global monotonic counter rather than solely from `block_height`.

### Proof of Concept
Integration/runtime-test-loop plan:
1. Fund an account and add a gas key (`num_nonces >= 1`) at block `H1`.
2. Execute a `DelegateAction` with `nonce_index = 0` and nonce `N` close to `H1 * ACCESS_KEY_NONCE_RANGE_MULTIPLIER`; assert it succeeds and `get_gas_key_nonce(.., 0) == N`.
3. In the same or next block, submit `DeleteKey` then `AddKey` (same public key, same gas-key permission); read back `get_gas_key_nonce(.., 0)` and assert it is `<= N` (demonstrating the reset).
4. Resubmit the identical signed `DelegateAction` from step 2; assert it is accepted (`DelegateActionInvalidNonce` is NOT returned) and its actions re-execute — proving replay.
5. Generalize as an invariant test: for every `(account, pubkey, index)`, assert the sequence of nonce values written by `set_gas_key_nonce` across delete/recreate cycles is strictly increasing; the PoC should show this invariant currently fails.
