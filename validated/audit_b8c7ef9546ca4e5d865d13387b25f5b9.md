### Title
StackerDB chunk writes are never rate-limited by `write_freq`, allowing signers to bypass the intended minimum-write-interval throttle - ([File: stackslib/src/net/stackerdb/db.rs])

### Summary
`StackerDBConfig::write_freq` is a configured minimum-interval-between-writes value for a given StackerDB slot, and the `net_error::TooFrequentSlotWrites` variant exists specifically to signal that a write arrived too soon. However, the only code path that actually persists a chunk to a slot — `StackerDBTx::try_replace_chunk` — never checks `write_freq` or the slot's `write_time` at all, so this throttle is never enforced on writes, only referenced client-side when deciding whether to *fetch* a chunk from peers.

### Finding Description
`try_replace_chunk` in `stackslib/src/net/stackerdb/db.rs` validates a chunk write against exactly three conditions: signature ownership (`BadSlotSigner`), monotonic version (`StaleChunk` if `slot_desc.slot_version <= slot_validation.version`), and max write count (`TooManySlotWrites` if `slot_desc.slot_version > self.config.max_writes`) [1](#0-0) . It never reads `self.config.write_freq` or the stored `write_time` column, and never returns `net_error::TooFrequentSlotWrites`, even though that error variant exists in the error enum for exactly this purpose [2](#0-1) . A `grep` across the repo shows `TooFrequentSlotWrites` is only ever *defined and displayed*, never constructed anywhere — confirming the check is dead code / never wired up.

This `try_replace_chunk` function is exactly the write path reached by the unauthenticated-but-slot-owner-signed HTTP endpoint `RPCPostStackerDBChunkRequestHandler::try_handle_request`, which calls `tx.try_replace_chunk(...)` directly and maps its `Err` variants to ack codes — but has no `TooFrequentSlotWrites` case because it can never occur [3](#0-2) .

By contrast, the *sync* logic (`StackerDBSync::make_chunk_request_schedule`) does use `write_freq` — but only to decide, locally, whether to bother *fetching* a chunk from remote peers that appears too-recently-written, using the comparison `write_ts + self.write_freq > now` to skip requesting it [4](#0-3) . This is a purely local heuristic for avoiding wasted fetches; it does nothing to prevent a slot owner from actually writing new chunk versions faster than `write_freq` in the first place. `insert_chunk`, the low-level SQL writer invoked at the end of `try_replace_chunk`, unconditionally updates `write_time = get_epoch_time_secs()` on every accepted write with no precondition on the previous `write_time` [5](#0-4) .

### Impact Explanation
Any party who legitimately owns a StackerDB slot (i.e., holds the private key for the slot's assigned address — this is not privilege escalation, since slot ownership is the normal, expected capability of a StackerDB participant such as a signer) can push new versions of their chunk at an arbitrary rate, completely ignoring the `write_freq` throttle that node operators configure via `StackerDBConfig`. Because pushed/accepted chunks are propagated to peers via `StackerDBChunksInv`/gossip and `handle_unsolicited_StackerDBPushChunk`, an unthrottled write stream from one signer becomes a stream of legitimate-looking, validly signed chunk updates that get relayed and stored across the whole replica set at whatever rate the writer chooses, rather than at the rate node operators intended to bound (`write_freq` exists precisely to bound both bandwidth and processing amplification per slot). This does not require forging any signature or breaking StackerDB auth — it only requires that the "minimum time between writes" invariant the codebase clearly intends to enforce (as evidenced by the config field and the dedicated error variant) is never actually checked at the point of writing.

### Likelihood Explanation
High likelihood: this requires no exotic conditions — any signer/slot owner submitting `POST /v2/stackerdb/.../chunks` (or via a peer's push path) faster than `write_freq` succeeds today because `try_replace_chunk` only gates on version and max-write-count, not on elapsed time.

### Recommendation
In `StackerDBTx::try_replace_chunk` (`stackslib/src/net/stackerdb/db.rs`), before calling `self.insert_chunk`, fetch the slot's current `write_time` from `slot_validation` (already loaded) and reject with `net_error::TooFrequentSlotWrites(deadline)` if `get_epoch_time_secs() < slot_validation.write_time + self.config.write_freq` when `write_freq > 0`. Wire the resulting error through `poststackerdbchunk.rs`'s error-to-ack-code mapping (and any P2P push-chunk handling) so remote clients get a proper rejection rather than an unbounded-rate accept.

### Proof of Concept
1. Configure a StackerDB with `write_freq = 120` (as done in the existing test `test_reconfigure_stackerdb`, `stackslib/src/net/stackerdb/tests/db.rs:499-501`).
2. As the owner of slot `i`, call `tx.try_replace_chunk(&sc, &chunk_v1.get_slot_metadata(), &chunk_v1.data)` — succeeds, `write_time` updated to now.
3. Immediately (same second) call `tx.try_replace_chunk(&sc, &chunk_v2.get_slot_metadata(), &chunk_v2.data)` with `slot_version = 2` — this succeeds today with no error, despite `write_freq = 120` seconds not having elapsed, because `try_replace_chunk` never checks `write_time`/`write_freq` (confirmed by reading `stackslib/src/net/stackerdb/db.rs:398-437` — no reference to `write_freq`).                 slot_validation.signer,
                slot_desc.slot_id,
