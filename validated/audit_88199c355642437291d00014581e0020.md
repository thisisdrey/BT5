### Title
StackerDB chunk signatures do not bind the target smart contract, enabling cross-DB chunk replay - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` and `StackerDBChunkData::verify()`/`recover_pk()` authenticate a chunk over only `(slot_id, slot_version, data_hash)`. The `smart_contract_id` (the specific StackerDB replica the chunk is destined for) is never part of the signed digest. The storage-layer validation in `stackslib/src/net/stackerdb/db.rs` (`try_replace_chunk`) and the network-layer validation in `stackslib/src/net/stackerdb/mod.rs` (`validate_received_chunk`) both re-derive the digest the same way and check it only against the slot's configured signer address — never against the contract the chunk is being written into. ### Finding Description
A valid `StackerDBChunkData`/`SlotMetadata` signature only commits to `slot_id`, `slot_version`, and `data_hash` — it never commits to which StackerDB (smart contract) it is intended for:

```
fn auth_digest(&self) -> Sha512Trunc256Sum {
    let mut hasher = Sha512_256::new();
    hasher.update(self.slot_id.to_be_bytes());
    hasher.update(self.slot_version.to_be_bytes());
    hasher.update(self.data_hash.0);
    Sha512Trunc256Sum::from_hasher(hasher)
}
``` [1](#0-0) 

Both consumers of `verify()` — the HTTP write path `try_replace_chunk` (which checks `slot_desc.verify(&slot_validation.signer)`) and the P2P push/pull path `validate_received_chunk` (which checks `slot_metadata.verify(&addr)`) — resolve the "expected signer" purely from the *target* contract's local slot configuration (`get_slot_validation`/`get_slot_signer`), not from anything embedded in the signed bytes themselves: [5](#0-4) [4](#0-3) 

Multiple StackerDB smart contracts commonly assign the same signer address to the same numeric `slot_id` (e.g. the `signer-XXX-YYY` family of contracts distinguished only by `(signer_set, message_id)` in the boot contracts, all populated from the same underlying reward-cycle signer set) — see the boot-contract parsing/routing logic that treats several sibling contracts as belonging to one signer set and dispatches by `message_id`: [6](#0-5) 

Because the signature carries no contract binding, any unprivileged network participant who can observe a validly-signed chunk broadcast/relayed for one StackerDB contract (chunks are not secret — they are served over the unauthenticated `GET /v2/stackerdb/...` endpoint and gossiped in `StackerDBPushChunk`) can resubmit the identical `(slot_id, slot_version, sig, data)` tuple against a *different* StackerDB contract that assigns the same address to the same `slot_id`, provided the target slot's stored version is lower than the replayed `slot_version`. `try_replace_chunk`/`validate_received_chunk` will treat it as a fully authentic write for that unrelated contract, because the digest and signer-address check both pass — the code never verifies "was this specific `(sig, data)` intended for *this* `smart_contract`."

This is the same equality-break class as the reported `setWeight()` bug: the code assumes an implicit invariant ("a chunk signed by X is only valid for the DB it was solicited for") that is never actually enforced, because the enforced equality (`recovered_pubkey_hash == configured_slot_signer`) is weaker than the intended one (`recovered_pubkey_hash == configured_slot_signer AND this signature was produced for this exact contract`).

### Impact Explanation
An attacker with no privileged key can cause forged/foreign data to be accepted and stored as authentic in a StackerDB replica it was never intended for — i.e., an unauthorized write of attacker-selected (but signer-produced) bytes into another contract's slot, and propagation of that forged acceptance via `StackerDBChunkInv`/gossip to other peers. Downstream consumers (e.g. `stacks-node`'s `StackerDBListener`/`libsigner` event parsing) key their trust purely on "signed by the expected signer for that DB," so a replayed chunk can be misinterpreted as a legitimate message for the wrong lane/contract, and be relayed network-wide as though it were canonical for that DB. This matches the report's "network-wide propagation of forged data" / "unauthenticated/unauthorized write to state or StackerDB" impact bar.

### Likelihood Explanation
Exploitation requires: (1) observing one legitimately-signed chunk (trivial — StackerDB chunks are publicly readable/gossiped, not secret), and (2) a target contract that assigns the same signer address to the same `slot_id` and currently has a lower stored version there. Because signer-set-derived StackerDB contracts are provisioned in lock-step from the same reward-cycle signer set, slot-index reuse across sibling contracts is plausible by construction, though I was not able to fully confirm from the indexed code that slot assignment is *always* identical across every pair of sibling `signer-XXX-YYY` contracts (this would need to be checked in `stackslib/src/chainstate/nakamoto/signer_set.rs`, which the index only partially surfaced). This uncertainty tempers confidence but does not change the root defect: the signature itself never binds the contract, so the security of the whole scheme rests entirely on slot-index non-overlap being maintained as an *undocumented, unenforced* invariant.

### Recommendation
Bind the target contract into the signed digest, e.g. include the smart contract's identifier (address + name) bytes in `SlotMetadata::auth_digest()`, and thread the `QualifiedContractIdentifier` through `sign()`/`verify()`/`recover_pk()` in `libstackerdb::libstackerdb.rs`, `StackerDBTx::try_replace_chunk` in `stackslib/src/net/stackerdb/db.rs`, and `PeerNetwork::validate_received_chunk` in `stackslib/src/net/stackerdb/mod.rs`. This is a wire-format/protocol change and needs coordinated versioning with `stacks-signer`.

### Proof of Concept
1. Signer `S` legitimately signs and posts chunk `C = (slot_id=3, slot_version=5, data=D)` to StackerDB contract `signer-7-0`, where `S` owns slot 3 there. This chunk is retrievable by anyone via `GET /v2/stackerdb/<addr>.signer-7-0/chunks/3` (or observed via `StackerDBPushChunk` gossip).
2. Attacker (no keys required) takes the exact bytes `(slot_id=3, slot_version=5, sig, data=D)` and POSTs them to `signer-7-1` (a sibling contract for the same signer set/reward cycle) where `S` also owns slot 3, provided `signer-7-1`'s current stored version for slot 3 is `< 5`.
3. `try_replace_chunk` (`stackslib/src/net/stackerdb/db.rs:400-423`) calls `slot_desc.verify(&slot_validation.signer)`, which recomputes `auth_digest()` over only `(3, 5, hash(D))`, recovers `S`'s pubkey hash, matches it against `signer-7-1`'s configured signer for slot 3, and succeeds — even though `D` was never intended for `signer-7-1`.
4. The forged-context chunk is now stored as canonical for `signer-7-1` and advertised via `StackerDBChunkInv` to peers, propagating it network-wide.
