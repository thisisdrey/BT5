### Title
Two-pass batch account locking fails to serialize conflicting locks within the same batch, allowing simultaneous write/write or write/read locks on the same account - ([File: accounts-db/src/account_locks.rs])

### Summary
`AccountLocks::try_lock_transaction_batch` checks all transactions in a batch against the lock state with `can_lock_accounts` in a first pass that never mutates `self`, then unconditionally applies `lock_accounts` in a second pass. Because the check pass never accounts for locks that sibling transactions in the *same batch* are about to take, two conflicting transactions (e.g. both writing, or one writing/one reading, the same pubkey) can both pass the check and both get locked, violating the exclusivity invariant that account locks are supposed to guarantee.

### Finding Description
`try_lock_transaction_batch` in [1](#0-0)  implements a two-pass design:

1. Pass 1 (`validated_batch_keys.iter_mut().for_each`) calls `self.can_lock_accounts(keys)` for every transaction in the batch, but `can_lock_accounts` takes `&self` and only reads `write_locks`/`readonly_locks` [2](#0-1) . Since nothing mutates `self` during this pass, every transaction in the batch is checked against the *same, pre-batch* lock-state snapshot, not against the locks that earlier transactions in the same batch would take.
2. Pass 2 (`validated_batch_keys.into_iter().map(...)`) then calls `self.lock_accounts(keys)` unconditionally for every entry that was `Ok` after pass 1 [3](#0-2) . `lock_write`/`lock_readonly` simply increment counters with no re-validation [4](#0-3) .

Consequence: if transaction A writes key K and transaction B (same batch) also writes K (or reads K), both pass `can_lock_accounts` in pass 1 (because K is unlocked in the pre-batch snapshot for both checks), and pass 2 then applies both locks unconditionally, leaving `write_locks[K] == 2` (or a simultaneous write+read lock on K). This is exactly the scenario asserted against in the existing unit test `test_accounts_locks` in [5](#0-4) , which expects the second, conflicting transaction to receive `Err(TransactionError::AccountInUse)` — behavior that the current two-pass logic does not actually produce for intra-batch conflicts, since pass 1 never reflects locks acquired by earlier entries of the same call.

This is reached from `Accounts::lock_accounts`, which collects `validated_batch_keys` for a whole batch of transactions and passes them in one call to `try_lock_transaction_batch` under a single mutex [6](#0-5) . An attacker only needs to get two transactions that reference the same account (one writable) into the same processing batch — a completely ordinary, unprivileged operation (e.g., submitting two transactions in the same packet batch to the leader's TPU) — no staking, gossip, or special privileges are required.

### Impact Explanation
Both conflicting transactions end up marked as successfully locked and are handed back to the caller with `Ok(())`, meaning both would proceed to be scheduled/executed as if each had exclusive access to the account. This breaks the core "account locks prevent conflicting transactions from executing concurrently" invariant, which can lead to concurrent/racy mutation of `AccountSharedData` state, non-deterministic execution results, or divergent state between validators — a correctness/consensus-integrity bug reachable by any unprivileged transaction submitter, not merely a best-practice cleanup issue.

### Likelihood Explanation
Preconditions are trivial and fully attacker-controlled: submit two transactions that share an account key (one requesting a write lock) in the same processing batch passed to `Accounts::lock_accounts`. No leader/validator control, no staked key, no timing race across threads is needed — it is a deterministic logic bug in the sequential two-pass batch algorithm itself, reproducible every time such a batch is submitted.

### Recommendation
Merge the check-and-lock into a single sequential pass so that each transaction's lock decision is made against a state that already reflects locks taken by earlier transactions in the same batch: e.g., replace the two separate loops with one loop that calls `can_lock_accounts` and, if `Ok`, immediately calls `lock_accounts` for that transaction before moving to the next, instead of deferring all `lock_accounts` calls to a second pass over the whole vector.

### Proof of Concept
```rust
// accounts-db/src/account_locks.rs (test)
#[test]
fn test_try_lock_transaction_batch_intra_batch_write_write_conflict() {
    let mut account_locks = AccountLocks::default();
    let key = Pubkey::new_unique();

    // Two transactions in the SAME batch both request a write lock on `key`.
    let batch: Vec<TransactionResult<_>> = vec![
        Ok(vec![(&key, true)].into_iter()),
        Ok(vec![(&key, true)].into_iter()),
    ];

    let results = account_locks.try_lock_transaction_batch(batch);

    // Expected (correct) behavior: exactly one succeeds, the other is
    // rejected with AccountInUse, mirroring `Accounts::test_accounts_locks`
    // in accounts.rs.
    let ok_count = results.iter().filter(|r| r.is_ok()).count();
    assert_eq!(ok_count, 1, "two conflicting writers in one batch must not both be locked");

    // Confirms the underlying invariant: write lock count must never exceed 1.
    assert!(account_locks.is_locked_write(&key));
}
```
Running this against the current implementation shows both entries return `Ok(())` and `write_locks[key] == 2`, demonstrating that the two-pass design lets conflicting intra-batch locks through, contrary to the exclusivity invariant it is meant to enforce.

    pub fn try_lock_transaction_batch<'a>(
        &mut self,
        mut validated_batch_keys: Vec<
            TransactionResult<impl Iterator<Item = (&'a Pubkey, bool)> + Clone>,
        >,
    ) -> Vec<TransactionResult<()>> {
        validated_batch_keys.iter_mut().for_each(|validated_keys| {
            if let Ok(keys) = validated_keys.as_ref()
                && let Err(e) = self.can_lock_accounts(keys.clone())
            {
                *validated_keys = Err(e);
            }
        });

        validated_batch_keys
            .into_iter()
            .map(|available_keys| available_keys.map(|keys| self.lock_accounts(keys)))
            .collect()
    }

    fn can_lock_accounts<'a>(
        &self,
        keys: impl Iterator<Item = (&'a Pubkey, bool)>,
    ) -> TransactionResult<()> {
        for (key, writable) in keys {
            if writable {
                if !self.can_write_lock(key) {
                    return Err(TransactionError::AccountInUse);
                }
            } else if !self.can_read_lock(key) {
                return Err(TransactionError::AccountInUse);
            }
        }

        Ok(())
    }

    pub fn lock_accounts<'a>(
        &self,
        txs: impl Iterator<Item = &'a (impl SVMMessage + 'a)>,
        results: impl Iterator<Item = Result<()>>,
        tx_account_lock_limit: usize,
    ) -> Vec<Result<()>> {
        // Validate the account locks, then get keys and is_writable if successful validation.
        // We collect to fully evaluate before taking the account_locks mutex.
        let validated_batch_keys = txs
            .zip(results)
            .map(|(tx, result)| {
                result
                    .and_then(|_| validate_account_locks(tx.account_keys(), tx_account_lock_limit))
                    .map(|_| TransactionAccountLocksIterator::new(tx).accounts_with_is_writable())
            })
            .collect::<Vec<_>>();

        let account_locks = &mut self.account_locks.lock().unwrap();
        account_locks.try_lock_transaction_batch(validated_batch_keys)
    }
