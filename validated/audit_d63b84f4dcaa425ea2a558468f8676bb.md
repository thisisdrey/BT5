### Title
Access key nonce reset on re-add allows replay of previously valid transactions - (File: runtime/runtime/src/access_keys.rs)

### Summary
`action_add_key` always initializes a newly-added access key's nonce from the current block height, with no regard for whether an access key under the *same public key* previously existed and had already advanced its nonce further. This contradicts the protocol's own documented invariant that recreating an access key with the same public key must preserve the old nonce to prevent transaction replay, and it opens a window for replaying previously signed-but-unexecuted (or even previously executed) transactions.

### Finding Description
When `DeleteKey` removes an access key, `remove_access_key` deletes the entire trie entry, including its nonce state [1](#0-0) . When the same public key is subsequently re-added via `AddKey`, `add_regular_key` (and analogously `add_gas_key`) sets the new key's nonce purely from the current block height via `initial_nonce_value`, with no lookup or preservation of any prior nonce value that may have existed for that public key: [2](#0-1) [3](#0-2) 

This directly contradicts the documented protocol invariant in the `AccessKey` struct itself: [4](#0-3) 

> "NOTE: In some cases the access key needs to be recreated. If the new access key reuses the same public key, the nonce of the new access key should be equal to the nonce of the old access key. It's required to avoid replaying old transactions again."

The nonce-freshness check in `verify_and_charge_tx_ephemeral`/`verify_nonce` only compares the incoming transaction's nonce against the access key's *currently stored* nonce value: [5](#0-4) . Because `add_regular_key` resets that stored nonce to `(block_height - 1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` unconditionally, an old, previously-signed transaction whose nonce falls within `[(block_height - 1) * MULTIPLIER, previous_high_nonce)` becomes valid again the moment the key is recreated — even though that nonce range had already been "used up" against the earlier incarnation of the key. This is precisely the class of bug called out in the external report: removing/recreating an entity in one place (the access key/nonce store) fails to properly propagate/preserve state needed by a dependent validation path (nonce replay protection), letting stale, previously-valid artifacts be reused to the detriment of the correctness of the system.

### Impact Explanation
An attacker (or the key owner acting maliciously against their own past commitments, or anyone who has observed a broadcast-but-not-yet-included signed transaction) can resubmit an old, previously signed transaction after the victim's access key is deleted and recreated with the same public key in a single or nearby block. Since NEAR nonces are not required to be sequential (`tx_nonce` just needs to be greater than the access key's current nonce and below `block_height * ACCESS_KEY_NONCE_RANGE_MULTIPLIER`), a nonce can be pre-selected near the top of the currently valid range. Once the key is deleted and re-added at the same or a very close block height, the freshly reset nonce floor can sit below that pre-selected nonce, making the stale transaction valid for inclusion again. This allows replay of actions such as `Transfer`, `FunctionCall`, or other authorized actions, resulting in double-spend/duplicate execution of previously authorized operations — a direct violation of the anti-replay guarantee access-key nonces are supposed to provide.

### Likelihood Explanation
Exploitation requires the victim (or an entity controlling the key) to delete and re-add the identical public key — an operation explicitly anticipated and warned about in the protocol's own documentation, meaning it is a supported/expected user flow (e.g., rotating permissions on a key while keeping the same public key, or restoring a key). Any application, wallet, or contract-driven meta-transaction flow that performs `DeleteKey` + `AddKey` with the same public key in the same transaction/block is directly exposed, requiring no privileged access, network-layer control, or malicious node — only crafting of ordinary transactions and access-key management already exposed to standard signers.

### Recommendation
Before resetting the nonce in `add_regular_key`/`add_gas_key`, check whether a residual/previous nonce value is retained (or otherwise ensure that deleting a key preserves rather than discards its last-used nonce, e.g. by storing a tombstone of `(account_id, public_key) -> last_nonce`, or by making `add_regular_key`/`add_gas_key` take the maximum of `initial_nonce_value(block_height)` and any historically recorded nonce for that specific public key on that account). This restores the invariant documented in `AccessKey.md` and closes the replay window.

### Proof of Concept
1. Account `alice.near` has access key `K` with current nonce `c`, at block height `h1`.
2. Alice signs (but does not submit) transaction `Tx1` (e.g., a `Transfer` action) using key `K` with nonce `n1`, chosen close to the top of the currently valid range: `c < n1 < h1 * ACCESS_KEY_NONCE_RANGE_MULTIPLIER`.
3. At block height `h2` (`h2` close to `h1`, e.g. same or next block), Alice submits a transaction containing `[DeleteKey(K), AddKey(K)]` (same public key `K`). `action_delete_key` removes the key/nonce entirely [6](#0-5) ; `action_add_key` recreates it with nonce `(h2 - 1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` [7](#0-6) .
4. If `(h2 - 1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER < n1`, `Tx1` (still within its `transaction_validity_period`) is now valid again per `verify_nonce`, and can be submitted/replayed, re-executing the original `Transfer` action a second time.

pub(crate) fn initial_nonce_value(block_height: BlockHeight) -> Nonce {
    // Set default nonce for newly created access key to avoid transaction hash collision.
    // See <https://github.com/near/nearcore/issues/3779>.
    (block_height - 1) * near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER
}

pub(crate) fn action_delete_key(
    config: &RuntimeConfig,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    result: &mut ActionResult,
    account_id: &AccountId,
    delete_key: &DeleteKeyAction,
) -> Result<(), RuntimeError> {
    let access_key = get_access_key(state_update, account_id, &delete_key.public_key)?;
    if let Some(access_key) = access_key {
        if let Some(gas_key_info) = access_key.gas_key_info() {
            delete_gas_key(
                config,
                state_update,
                account,
                result,
                account_id,
                &delete_key.public_key,
                &access_key,
                gas_key_info,
            )?;
        } else {
            delete_regular_key(
                &config.fees,
                state_update,
                account,
                account_id,
                &delete_key.public_key,
                &access_key,
            );
        }
    } else {
        result.result = Err(ActionErrorKind::DeleteKeyDoesNotExist {
            public_key: delete_key.public_key.clone().into(),
            account_id: account_id.clone(),
        }
        .into());
    }
    Ok(())
}

pub(crate) fn action_add_key(
    apply_state: &ApplyState,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    result: &mut ActionResult,
    account_id: &AccountId,
    add_key: &AddKeyAction,
) -> Result<(), StorageError> {
    if get_access_key(state_update, account_id, &add_key.public_key)?.is_some() {
        result.result = Err(ActionErrorKind::AddKeyAlreadyExists {
            account_id: account_id.to_owned(),
            public_key: add_key.public_key.clone().into(),
        }
        .into());
        return Ok(());
    }

    let fee_config = &apply_state.config.fees;

    if let Some(gas_key_info) = add_key.access_key.gas_key_info() {
        add_gas_key(
            fee_config,
            state_update,
            account,
            account_id,
            &add_key.public_key,
            &add_key.access_key,
            gas_key_info,
            apply_state.block_height,
        )?;
    } else {
        add_regular_key(
            fee_config,
            state_update,
            account,
            account_id,
            &add_key.public_key,
            &add_key.access_key,
            apply_state.block_height,
        )?;
    }

    Ok(())
}

fn add_regular_key(
    fee_config: &RuntimeFeesConfig,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    public_key: &PublicKey,
    access_key: &AccessKey,
    block_height: BlockHeight,
) -> Result<(), StorageError> {
    let mut access_key = access_key.clone();
    access_key.nonce = initial_nonce_value(block_height);
    set_access_key(state_update, account_id.clone(), public_key.clone(), &access_key);

    account.set_storage_usage(
        account
            .storage_usage()
            .checked_add(access_key_storage_usage(fee_config, public_key, &access_key))
            .ok_or_else(|| {
                StorageError::StorageInconsistentState(format!(
                    "Storage usage integer overflow for account {}",
                    account_id
                ))
            })?,
    );
    Ok(())
}
