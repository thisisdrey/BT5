## Finding

### Title
Denial-of-Service via Unbounded Array Allocation from Attacker-Controlled Length in TVM Precompiles `ValidateMultiSign`/`BatchValidateSign` - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `qs` CVE-2014-7191 pattern — an attacker-controlled length field parsed directly into a large array allocation with no upper bound, causing an out-of-memory crash — has a close analog in java-tron's ABI decoding helpers used by the `ValidateMultiSign` and `BatchValidateSign` precompiled contracts.

### Finding Description
`extractBytes32Array` and `extractBytesArray` in `PrecompiledContracts.java` read an array-length word directly from calldata and use it, unchecked, as the size of a Java array allocation: [1](#0-0) 

`len` comes from `words[offset].intValueSafe()`, which is fully attacker-controlled via the raw calldata passed to the precompile. There is no comparison against calldata length or any sane upper bound before `new byte[len][]` is executed.

These helpers are invoked from `ValidateMultiSign.execute()` and `BatchValidateSign.doExecute()`: [2](#0-1) [3](#0-2) 

The bound check (`MAX_SIZE = 5` / `MAX_SIZE = 16`) that would prevent the oversized allocation is only performed **when `VMConfig.allowTvmSelfdestructRestriction()` is true**: [4](#0-3) [5](#0-4) 

When that feature flag is off (its default `false` value in a fresh `Snapshot`, and the flag it guards is unrelated in purpose — selfdestruct restriction, not array-size validation, so it may be disabled on any chain/testnet that hasn't activated this specific TIP), `extractBytesArray`/`extractBytes32Array` are called with **no size bound at all**. A caller can set the length word to a large value (limited only by `intValueSafe()`, i.e., up to `Integer.MAX_VALUE`), causing `new byte[len][]` to attempt to allocate an object-reference array many gigabytes in size, which throws `OutOfMemoryError` inside the TVM execution thread.

This mirrors the `qs` bug class exactly: a length taken from untrusted, attacker-supplied input is used to size an array allocation before any validation of plausibility against the actual amount of supplied data.

### Impact Explanation
An `OutOfMemoryError` thrown while executing a smart-contract call inside a node's JVM can destabilize or crash the node process, or place the JVM into a degraded state affecting all other node operations (this is the same class of test already present in the repo confirming `OutOfMemoryException`/`OutOfMemoryError` handling is a recognized concern for TVM execution — see `EnergyWhenAssertStyleTest.outOfMemTest`). Because `ValidateMultiSign`/`BatchValidateSign` are reachable by any unprivileged account through a normal `TriggerSmartContract` transaction (via `CALL`/`STATICCALL` to the fixed precompile addresses), this can be triggered by any transaction broadcaster without special privilege, potentially causing node crash/instability across the network if the vulnerable code path is exercised on nodes that have not activated `allowTvmSelfdestructRestriction`.

### Likelihood Explanation
Likelihood depends entirely on whether `allowTvmSelfdestructRestriction` is active on the target network. If it's activated (as it likely is on TRON mainnet after its associated TIP), this specific path is dead code there. However:
- Test networks, private/consortium java-tron deployments, or nodes running from genesis before this proposal activates are exposed.
- The fact that the size check was retrofitted behind a feature flag (rather than unconditionally) confirms the underlying allocation-without-bound-check is a known-risky pattern that was only partially remediated.

I could not verify from the available index whether `allowTvmSelfdestructRestriction` is hard-coded to `true` by default outside of proposal activation; this should be confirmed against `DynamicPropertiesStore`/`ProposalUtil` defaults in a full session, since a background agent with full repository access would need to check the genesis/default proposal values that were referenced in the grep matches but not retrieved in this session.

### Recommendation
Move the length/size sanity check for `extractBytesArray`/`extractBytes32Array`/`extractSigArray` out of the `allowTvmSelfdestructRestriction` conditional so it is unconditionally enforced regardless of that flag's state — e.g., always reject `len <= 0 || len > MAX_SIZE` (or a length that's inconsistent with the actual calldata length) before allocating, independent of any hard-fork gate. Additionally, `extractBytes32Array`/`extractBytesArray` should validate `len` against `(data.length - headerOffset) / itemSize` before allocation, similar to the `isValidAbiEncoding` guard already used elsewhere in the same file.

### Proof of Concept
1. Deploy any contract that performs a `staticcall`/`call` to the `BatchValidateSign` precompile address (or directly craft a `TriggerSmartContractTransaction` targeting that address) on a node where `allowTvmSelfdestructRestriction` is not active.
2. Craft calldata whose ABI encoding places a very large value (e.g., `0xFFFFFFFF`) in the length word read by `extractBytes32Array`/`extractBytesArray` (the array-length slot referenced by `words[1]`/`words[2]` offsets), while otherwise satisfying the minimal `data.length` requirements that pass the initial `getEnergyForData` cost computation.
3. Submit the transaction; `doExecute`/`execute` calls `extractBytesArray`/`extractBytes32Array` with the attacker-controlled `len`, triggering `new byte[len][]`, which throws `OutOfMemoryError` inside the TVM execution thread. [1](#0-0) [3](#0-2)

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
