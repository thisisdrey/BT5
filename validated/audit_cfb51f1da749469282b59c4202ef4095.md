### Title
Stale git-cat-file process cache entries are reused across repository deletion/recreation at the same path - (File: internal/git/catfile/cache.go)

### Summary
`ProcessCache` (Gitaly's git-cat-file process pool) keys cached `object_reader`/`object_reader_without_mailmap` processes purely by `{sessionID, repoStorage, repoRelPath, repoObjDir, repoAltDir}`, with no notion of repository identity, generation, or existence state. Deleting a repository and recreating a new one at the same relative path does not invalidate this cache, so a subsequent RPC can be served by a still-alive `git cat-file` process that was spawned against the old (now deleted) object database.

### Finding Description
Analogous to the `NFTFloorOracle` bug (a `delete` on the outer struct/mapping leaves a nested per-key cache — `feederPrice` — intact, so it gets silently reused once the same key is "recreated"), Gitaly's `ProcessCache` has the same structural flaw: the cache key [1](#0-0) 
contains only storage name and relative path (plus object/alternate dirs and a coarse 5-minute-rounded session id), never a per-repository generation/creation token. Cache lookups and insertion happen in `getOrCreateProcess`/`processes.Checkout`/`processes.Add`, which only compare this `key` struct: [2](#0-1) [3](#0-2) 

Eviction of an entry is driven only by TTL expiry (`defaultBatchfileTTL = 10s`, enforced by a periodic monitor) or by the process being detected as `isDirty()`/`isClosed()` on return: [4](#0-3) [5](#0-4) 

There is no hook that flushes or invalidates cache entries when `RemoveRepository`/`CreateRepository` (or `Create`) act on the same `relativePath`. `repoutil.Create` even documents needing to "recreate the local repository, since the cache of object hash and ref-format needs to be invalidated" for the in-process `localrepo.Repo` wrapper, but this only replaces the light-weight `localrepo.Repo` object — it does not touch the shared `catfileCache` process pool: [6](#0-5) 

Because the `git cat-file --batch`/`--batch-check` subprocess keeps its own open file descriptors/mmaps into the repository's object database, deleting the on-disk repository directory and creating a fresh one at the same relative path does not kill or invalidate the already-running cached process. Within the TTL/session window a subsequent read RPC that reuses the cache key can be served object data belonging to the deleted repository rather than the new one.

### Impact Explanation
An ordinary user performing a normal `create repository → push objects → delete repository → recreate repository at the same path` workflow (all reachable via standard Gitaly RPCs `CreateRepository`/`RemoveRepository`, no special privileges required) can cause subsequent reads (`GetBlob`, `TreeEntry`, various catfile-backed RPCs) against the *new* repository to transiently return objects/content from the *deleted* repository, for as long as the cached process remains alive (up to the 10-second TTL, and gated by the coarse 5-minute session bucket). This is a data-integrity/information-disclosure issue: content that should have been destroyed with the old repository can leak into the lifecycle of the new repository, and readers of the new repo can observe objects that never existed in it. This mirrors the "old prices reused after asset removal" impact in the source report — stale nested state persisting through a delete-then-recreate cycle and being silently reused as if it belonged to the new entity.

### Likelihood Explanation
Likelihood is limited by timing: the stale process must still be resident in the cache (not yet TTL-expired) and the read must hash to the same cache key (same session bucket, same storage/relative path/object-dir/alt-dir). This is plausible in normal high-throughput flows such as rapid project deletion+recreation, forked/renamed repositories reusing a freed relative path, or replica-path reuse in Praefect-routed setups, especially since gRPC "mutator" annotations invalidate the unrelated `SmartHTTP` disk cache (`internal/cache`) on `RemoveRepository`/`CreateRepository`, but not this catfile process cache — showing the disk cache design already assumes this class of invalidation is necessary, while `catfile.ProcessCache` was not wired into it.

### Recommendation
Extend the catfile cache key (or add an explicit invalidation path) so that repository deletion evicts any cached processes for that repository's `{storage, relativePath}` before/at the point of removal, similar to how the disk cache's mutator-triggered invalidation works. Concretely:
- On `RemoveRepository` (and functionally-equivalent recreate-at-same-path flows), call an `Evict`/`EvictRepository(storage, relPath)` on the shared `catfile.Cache` used by the server, removing and killing any matching cached `objectReaders`/`objectReadersWithoutMailmap` entries.
- Alternatively, incorporate a repository generation/creation timestamp (or inode/dev of the repo directory) into the `key` struct so that a process created against the old generation can never satisfy a lookup for the new generation.

### Proof of Concept
Conceptual reproduction (not executed against the codebase, since Gitaly requires the running gRPC server and clock control used in tests like `internal/git/catfile/cache_test.go`):
1. `CreateRepository(A)` at `relative/path`, push commit `C1`, perform an RPC that goes through `catfile.Cache.ObjectReader` (e.g. `GetBlob`) so a process gets cached under key `{session, storage, "relative/path"}`.
2. `RemoveRepository(A)` — the on-disk repo directory at `relative/path` is deleted, but `catfileCache` is not evicted (`internal/git/catfile/cache.go` has no such hook).
3. `CreateRepository(B)` immediately at the same `relative/path`, push a different commit `C2`.
4. Within the TTL/session window, issue a read RPC for `B` that hashes to the same cache key. `getOrCreateProcess` → `processes.Checkout` returns the process cached in step 1, which still holds open descriptors into the deleted repo `A`'s object database, so the response can reflect data from `A`/`C1` instead of `B`/`C2`. func (c *ProcessCache) returnToCache(p *processes, cacheKey key, value cacheable, cancel func()) {
	defer func() {
		c.reportCacheMembers()
	}()

	if value == nil || value.isClosed() {
		cancel()
		return
	}

	if value.isDirty() {
		cancel()
		c.catfileCacheCounter.WithLabelValues("dirty").Inc()
		value.close()
		return
	}

	if sessionID == "" {
		return key{}, false
	}

	return key{
		sessionID:   sessionID,
		repoStorage: repo.GetStorageName(),
		repoRelPath: repo.GetRelativePath(),
		repoObjDir:  repo.GetGitObjectDirectory(),
		repoAltDir:  strings.Join(repo.GetGitAlternateObjectDirectories(), ","),
	}, true
}

func (p *processes) Add(k key, value cacheable, expiry time.Time, cancel func()) bool {
	p.entriesMutex.Lock()
	defer p.entriesMutex.Unlock()

	replacedExisting := false
	if i, ok := p.lookup(k); ok {
		p.delete(i, true)
		replacedExisting = true
	}

	ent := &entry{
		key:    k,
		value:  value,
		expiry: expiry,
		cancel: cancel,
	}
	p.entries = append(p.entries, ent)

	for len(p.entries) > p.maxLen {
		p.evictHead()
	}

	return replacedExisting
}

// Checkout removes a value from p. After use the caller can re-add the value with p.Add.
func (p *processes) Checkout(k key) (*entry, bool) {
	p.entriesMutex.Lock()
	defer p.entriesMutex.Unlock()

	i, ok := p.lookup(k)
	if !ok {
		return nil, false
	}

	entry := p.entries[i]
	p.delete(i, false)
	return entry, true
}
