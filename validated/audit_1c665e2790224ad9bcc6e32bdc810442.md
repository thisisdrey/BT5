### Title
Unbounded `byte[][]` allocation in `ValidateMultiSign`/`BatchValidateSign` precompiles when `allowTvmSelfdestructRestriction` is disabled - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
`PrecompiledContracts.extractBytesArray()` and `extractBytes32Array()` take an attacker-controlled length word straight from calldata and use it as the size argument to `new byte[len][]`, with no upper-bound check, exactly like the `make([]xlsxRow, row)` pattern in the excelize report. The size guard that exists (`MAX_SIZE` check) is only applied when the `allowTvmSelfdestructRestriction` hard-fork flag is active; on the legacy code path the guard is skipped entirely, so a crafted `CALL` to the `ValidateMultiSign` or `BatchValidateSign` precompiled contract address can force a multi-gigabyte array allocation attempt for negligible energy cost.

### Finding Description
`extractBytes32Array` and `extractBytesArray` read `len` directly from calldata via `words[offset].intValueSafe()` and immediately allocate an array of that size: [1](#0-0) 

`ValidateMultiSign.execute()` only bounds `len` against `MAX_SIZE` (5) when the `allowTvmSelfdestructRestriction` flag is enabled; when it is not, `extractBytesArray` is invoked unconditionally with the raw, unchecked offset value: [2](#0-1) 

The same pattern repeats in `BatchValidateSign.doExecute()`, where `extractBytesArray`/`extractSigArray`/`extractBytes32Array` are gated by the same feature flag before the `MAX_SIZE` check is applied: [3](#0-2) 

Energy cost for these precompiles is computed from `data.length` (the ABI header size), not from the requested array length: [4](#0-3) 

This means an attacker can encode a small ABI payload (a handful of 32-byte words) that contains one word equal to `0x7FFFFFFF` at the "array length" slot, paying energy for only a couple of words while forcing the node to attempt `new byte[2147483647][]` — an allocation of on the order of 16 GB of reference slots on a 64-bit JVM (same order of magnitude as excelize's `make([]xlsxRow, 2147483647)`).

Critically, `OutOfMemoryError` is a `java.lang.Error`, not a `RuntimeException`. The VM interpreter loop only explicitly catches `RuntimeException`, `JVMStackOverFlowException`/`OutOfTimeException`, and `StackOverflowError`: [5](#0-4) 

So an `OutOfMemoryError` thrown while trying to allocate the oversized array is not handled at this layer and propagates upward, only being caught by the generic `catch (Throwable e)` in `VMActuator`: [6](#0-5) 

Even though this outer catch eventually absorbs the `Throwable`, the attempted allocation itself (and the GC pressure/heap fragmentation it causes while the JVM tries to satisfy or fail the request) is shared, process-wide resource consumption — a single transaction can force the node's JVM heap toward its limit, which can degrade or crash unrelated concurrent block-processing/transaction-validation threads on the same node. This is conceptually identical to CWE-770 in the report: attacker-controlled length used directly as an allocation size, decoupled from any actual resource/energy cost, with the size validation present in the codebase but bypassable via a feature-flag branch.

### Impact Explanation
Any account that can broadcast a `TriggerSmartContract` transaction calling the `ValidateMultiSign`/`BatchValidateSign` precompiled contract addresses (reachable via a plain `CALL` opcode from any deployed contract, no special privilege required) can trigger this path. If `allowTvmSelfdestructRestriction` is not yet activated on a given network, the `MAX_SIZE` guard is bypassed entirely, and the uncapped length flows straight into `new byte[len][]`. Repeated/concurrent submission of such transactions across many blocks/threads can push node memory usage toward OOM, causing performance degradation, GC storms, or process crashes — a Denial-of-Service against the validating/API-serving node, matching the severity class of the reported excelize issue (CWE-770, "Allocation of Resources Without Limits or Throttling").

### Likelihood Explanation
Likelihood depends on whether `allowTvmSelfdestructRestriction` is active on the target network. On networks/hard-fork states where it is **not yet enabled** (or is disabled for testing/private chains, or on any chain still in the proposal-pending window), the vulnerable branch is live and trivially reachable by an unprivileged transaction with minimal energy cost. On networks where the flag is already active, the `MAX_SIZE` (5/16) check mitigates this specific path, but it demonstrates the underlying design flaw: array-length validation is retrofitted behind a feature flag rather than being unconditional in `extractBytesArray`/`extractBytes32Array`/`extractSigArray` themselves.

### Recommendation
Move the length bound checks (`MAX_SIZE`) unconditionally into `extractBytesArray`, `extractBytes32Array`, and `extractSigArray` themselves (or validate `len` before calling them) regardless of `allowTvmSelfdestructRestriction`, so the guard cannot be bypassed by chain configuration. Additionally, reject negative or excessively large `len` values before allocation (e.g., cap at a small constant such as `MAX_SIZE`), and ensure the CPU/energy cost model accounts for the array length actually requested, not merely `data.length`.

### Proof of Concept
1. Craft calldata for `ValidateMultiSign` (or `BatchValidateSign`) precompile invocation with a compact ABI header (few 32-byte words) where the word at the computed "array length" offset (`words[words[3].intValueSafe()/32]` for `ValidateMultiSign`) is set to `0x7FFFFFFF`.
2. Deploy a minimal contract that performs a `CALL` to the corresponding precompiled contract address with this calldata, or invoke it directly if the address is externally callable.
3. Submit the transaction on a network/state where `allowTvmSelfdestructRestriction` is not active (`VMConfig.allowTvmSelfdestructRestriction()` returns `false`), so the `MAX_SIZE` check at [7](#0-6)  is skipped and `extractBytesArray` is called directly with the unchecked `len`.
4. Observe the node attempt `new byte[2147483647][]` inside `extractBytesArray`/`extractBytes32Array` [1](#0-0) , producing an `OutOfMemoryError` that is not caught by the VM interpreter loop's `RuntimeException`/`StackOverflowError` handlers [5](#0-4)  and propagates to the generic `Throwable` handler in `VMActuator`, evidencing uncontrolled resource consumption for a single low-cost transaction.

Note: I was unable to fully confirm within this session whether `allowTvmSelfdestructRestriction` is currently active by default on java-tron mainnet/testnet at the time of this analysis (its activation state is chain-config/proposal-dependent and stored in `DynamicPropertiesStore`), which affects real-world exploitability at any given moment; a live/mainnet check would need to query the corresponding chain parameter to confirm current activation status.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
