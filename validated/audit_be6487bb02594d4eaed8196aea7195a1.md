### Title
Replay window Check/Update race in `ConnectionState.Decrypt` — captured ciphertext can be double-processed before anti-replay bookkeeping lands - ([File: connection_state.go])

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` split anti-replay enforcement into two separately-locked operations (`window.Check` then, after AEAD decryption happens *unlocked*, `window.Update`), mirroring the reported bug class: a state check is performed, an irreversible action is taken based on that check, and only afterward is the authoritative state advanced — leaving a window where the check is stale relative to the action.

### Finding Description
`Decrypt` in [1](#0-0)  takes the following steps:
1. Lock `decryptLock`, call `cs.window.Check(l, messageCounter)`, unlock.
2. If `Check` says "not yet seen," perform `cs.dKey.DecryptDanger(...)` — this AEAD decryption is done **without holding `decryptLock`**.
3. Re-lock `decryptLock`, call `cs.window.Update(l, messageCounter)`, unlock, and only then return `ErrAlreadySeen` if it turns out the counter was already consumed.

The same pattern is repeated in `VerifyRelay` at [2](#0-1) .

Because `Check` and `Update` are independent, separately-locked calls with an unlocked decryption step in between, two goroutines processing the same captured/duplicated ciphertext (same `messageCounter`) concurrently can both pass `Check` before either one calls `Update`. Both then proceed to decrypt the payload successfully — decryption success depends only on the AEAD key and nonce, not on the anti-replay bitmap. Only the *second* `Update` call will observe the duplicate and return `false`, but by that point the plaintext has already been produced and handed to whatever processes it downstream (relay forwarding in `handleOutsideRelayPacket`, or delivery toward the TUN device for `Decrypt`). The anti-replay window (`Bits`, documented at [3](#0-2) ) is the sole mechanism nebula relies on to reject captured/replayed frames; its Check-then-later-Update split under the packet pipeline's multiple reader workers (`listenOut`/`readOutsidePackets`, referenced at [4](#0-3)  and [5](#0-4) ) is exactly the "check now, mutate state later" gap that the external report's redemption bug describes: an attacker who can inject a captured frame twice within this race window doesn't need any CA-signed certificate — they only need a copy of previously observed ciphertext, i.e., this is reachable by a pure network attacker exploiting nonce/replay handling, one of the explicitly in-scope categories.

Note: this differs from the already-fixed relay-forwarding issue at [6](#0-5)  (`TestRelayReplayProtection`), which tests that a *single-threaded* sequential replay is rejected because `Update` is eventually called before the next replay is checked. That test does not exercise concurrent/simultaneous delivery of the duplicate, so it does not cover the TOCTOU window described here.

### Impact Explanation
If the race is won, a captured relay or data-plane frame can be decrypted and forwarded/delivered a second time despite the replay window being designed to prevent exactly that. For relayed traffic this means a captured frame can be re-forwarded to the target multiple times (traffic amplification / duplicate delivery), undermining the guarantee that "Advance the replay window on relayed packets so a relay drops replayed frames instead of re-forwarding them" (see the fix noted in [7](#0-6)  and [8](#0-7) , which hardened the *sequential* case but not necessarily true concurrent delivery). This is a concrete replay/traffic-forgery impact category.

### Likelihood Explanation
Exploitation requires winning a narrow race: delivering the same captured ciphertext to the interface from two concurrent code paths (e.g., via multiple UDP reader routines/queues, or relay + direct paths) close enough in time that both hit `Check` before either finishes `Update`. This is a timing-dependent race rather than a deterministic bypass, so likelihood is moderate — it depends on the number of reader workers/queues and scheduler timing, which an attacker sending bursts of duplicate frames could increase their odds of hitting.

### Recommendation
Hold `decryptLock` across the entire Check-Decrypt-Update sequence (or otherwise make the check-and-mark operation atomic with respect to decryption), so no two goroutines can observe "not yet seen" for the same counter simultaneously. This mirrors the general fix pattern already applied for the relay-forwarding replay bug (advance/consult the window atomically around the security-critical action) and should be applied uniformly to `Decrypt` as well as `VerifyRelay`.

### Proof of Concept
Not independently reproduced in this analysis (no test-execution environment available); the race is inferred directly from the code structure in [9](#0-8) , where `window.Check` and `window.Update` are separate, independently-locked calls with unlocked AEAD decryption in between. A concrete PoC would require driving two concurrent calls to `Decrypt`/`VerifyRelay` with the same `messageCounter` on the same `ConnectionState` (e.g., via two UDP reader goroutines/queues both receiving an attacker-replayed duplicate frame nearly simultaneously) and observing that both successfully decrypt before either duplicate is rejected.

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}

// VerifyRelay verifies AEAD protected (but not encrypted) relay frames. packet must be length-checked by the caller.
func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}
