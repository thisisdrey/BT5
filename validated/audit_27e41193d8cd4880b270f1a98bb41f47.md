### Stale NAV pricing during asynchronous approvals - ([File: tare-io__tare-contracts/contracts/PortfolioVault.sol])

### Summary
The `PortfolioVault` contract is vulnerable to a "stale pricing" attack similar to the `viewPrice` vulnerability. The vault's `approveDeposit` and `approveRedemption` functions rely on a cached `lastNav` value that is only updated via a manual, paginated `updateNav` process. If the underlying loan state changes (e.g., a loan becomes delinquent or a payment is made) between the time `updateNav` is finalized and when a manager calls `approveDeposit`/`approveRedemption`, the vault will issue shares or reserve assets at an incorrect price.

### Finding Description
In the Tare protocol, the Net Asset Value (NAV) of the `PortfolioVault` is computed by summing the values of its held loan NFTs. This process is paginated and manual due to gas limits [1](#0-0) . The final `lastNav` is calculated at the end of the cycle [2](#0-1) .

The vulnerability occurs because `approveDeposit` and `approveRedemption` use this cached `lastNav` to determine the share conversion rate [3](#0-2) [4](#0-3) . While there is a `_requireFreshNav` check [5](#0-4) , it only verifies that the `maxNavAge` has not been exceeded [6](#0-5)  and that the NFT ownership/calculator configuration hasn't changed [7](#0-6) . 

Crucially, it does **not** detect changes in the loans' internal state (delinquency status or DPD). A loan can move from "Current" to "DQ30" (triggering a discount factor in `NavCalculator.sol`) [8](#0-7)  simply by the passage of time (`block.timestamp > nextDueDate`). If a loan becomes delinquent after `updateNav` finishes but before a deposit is approved, the `lastNav` remains inflated, allowing the depositor to receive more shares than they are entitled to.

### Impact Explanation
This leads to material corruption of ledger balances and unfair minting/redeeming.
1. **Unfair Minting:** A depositor can wait for a loan in the portfolio to become delinquent. If the manager approves the deposit using a `lastNav` that was finalized just before the delinquency, the depositor gets shares at a "par" price for a portfolio that has actually lost value.
2. **Unfair Redemption:** Conversely, if a loan is repaid or its status improves, a redeemer can be approved at an undervalued `lastNav`, effectively stealing value from other shareholders.
3. **Value Extraction:** Arbitrageurs can time their `requestDeposit` or `requestRedeem` calls to exploit these predictable "price jumps" when the manager finally updates the NAV.

### Likelihood Explanation
The likelihood is high because the `NavCalculator` explicitly uses `block.timestamp` and `nextDueDate` to determine value [9](#0-8) . Delinquency is a core part of the lending lifecycle. Since `updateNav` is a manual manager action and the `maxNavAge` is likely set to a reasonable operational window (e.g., 24 hours), there are frequent windows where the on-chain reality of the loan values has diverged from the cached `lastNav`.

### Recommendation
Implement a "dampening" or "pessimistic" check in `_requireFreshNav` or the approval functions. The vault should verify that for a representative sample of loans (or all loans in small portfolios), the current bucket status in the calculator matches the status used during the last `updateNav`. Alternatively, the `NavCalculator` could provide a `viewCurrentValue` for a batch of loans that the vault can use to verify the cached `lastNav` is still conservative.

### Proof of Concept
1. A vault holds a single loan with `principal = 100,000 USDC` and `nextDueDate = T`.
2. At `T - 1 hour`, the manager runs `updateNav`. `lastNav` is set to `100,000 USDC` (Loan is "Current").
3. At `T + 1 second`, the loan is technically delinquent (DQ1). If the `NavCalculator` has a discount for DQ1 (or eventually DQ30), the "true" NAV is now lower.
4. An attacker calls `requestDeposit` for `10,000 USDC`.
5. The manager calls `approveDeposit` at `T + 2 hours`.
6. `_requireFreshNav` passes because `maxNavAge` (e.g., 24h) hasn't passed and ownership hasn't changed.
7. The attacker receives shares based on the `100,000 USDC` NAV, even though the portfolio is now impaired.
