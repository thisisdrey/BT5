### Title
Missing zero-address validation in `DecodeUtil.addressValid` allows permanent lock of TRX/TRC10 sent to the unspendable zero address - (File: common/src/main/java/org/tron/common/utils/DecodeUtil.java)

### Summary
`DecodeUtil.addressValid()` is the single sanity check used across actuators to validate user-supplied `toAddress`/`receiverAddress`/`voteAddress` fields. It only checks the byte length (21) and the network prefix byte (`0x41`), but never rejects the reserved all-zero address (`0x41` followed by 20 zero bytes). This mirrors the reported StarkNet bridge issue where the zero address was accepted as a valid recipient with no dedicated sanity check, leading to permanently locked funds.

### Finding Description
`DecodeUtil.addressValid` performs only length and prefix checks: [1](#0-0) 

This method is the sole address-sanity gate used by `TransferActuator.validate()`: [2](#0-1) 

and by `TransferAssetActuator.validate()`: [3](#0-2) 

as well as `DelegateResourceActuator.validate()` for `receiverAddress`: [4](#0-3) 

Because none of these checks reject `0x41` + 20 zero bytes, a broadcaster of a `TransferContract`/`TransferAssetContract` can set `toAddress` to the all-zero address. Since no ECDSA-derived TRON address can practically equal the all-zero value, no private key exists that can ever spend from that account — the address is only reachable/created as a side effect of `execute()` (`TransferActuator.execute`, lines 48-58 creates the account and credits it if it does not exist). The zero address is distinct from the protocol's actual burn accounts (Blackhole), which are excluded from validation entirely and tracked/initialized specially, so funds sent to `0x4100...00` are neither burned through the sanctioned mechanism nor recoverable by anyone.

This is the direct analog of the report's core defect class: a callable, unprivileged transaction path accepts the zero address as a valid destination for value transfer without a dedicated `to != 0` check, resulting in funds becoming unrecoverable.

### Impact Explanation
Any TRX or TRC10 asset sent via `TransferContract` or `TransferAssetContract` to the zero address is permanently and irrecoverably locked, since the resulting account has no controlling private key. This constitutes a permanent freezing-of-funds condition reachable by any unprivileged user broadcasting a single signed transaction, satisfying the Medium-severity "permanent freezing of funds" impact bucket.

### Likelihood Explanation
The path is trivially reachable: any account holder can craft a `TransferContract`/`TransferAssetContract` with `to_address` set to the all-zero 21-byte value and have it accepted by `validate()`/`execute()` without any special privilege. This could occur accidentally (e.g., a wallet/SDK bug producing a zero-initialized `to_address` field) or be exploited to grief users into thinking a transfer succeeded normally while funds are unrecoverable.

### Recommendation
Extend `DecodeUtil.addressValid` (or add an explicit check in each actuator alongside the existing `addressValid` call) to reject addresses that are all zero-bytes after the prefix, similar to the corrected L1 bridge behavior (`to != 0`). Apply this consistently to `TransferActuator`, `TransferAssetActuator`, `DelegateResourceActuator`, `VoteWitnessActuator`, and the TVM-side `VMUtils.validateForSmartContract` helpers that reuse the same address-validity check.

### Proof of Concept
1. Construct a `TransferContract` with a valid `owner_address` (funded) and `to_address = 0x410000000000000000000000000000000000000000` (21 bytes: prefix `0x41` + 20 zero bytes).
2. Sign and broadcast the transaction.
3. `TransferActuator.validate()` passes `DecodeUtil.addressValid(toAddress)` (length 21, prefix `0x41`) and the self-transfer check (`toAddress != ownerAddress`), so validation succeeds.
4. `TransferActuator.execute()` creates a new `AccountCapsule` for the zero address and credits it with the transferred amount.
5. Because no private key exists for the all-zero address, the credited TRX is permanently unspendable, verifiable by attempting to sign any transaction from that address (impossible, as no corresponding keypair exists).

  public static boolean addressValid(byte[] address) {
    if (ArrayUtils.isEmpty(address)) {
      logger.warn("Warning: Address is empty !!");
      return false;
    }
    if (address.length != ADDRESS_SIZE / 2) {
      logger.warn(
          "Warning: Address length need " + ADDRESS_SIZE + " but " + address.length
              + " !!");
      return false;
    }

    if (address[0] != addressPreFixByte) {
      logger.warn("Warning: Address need prefix with " + addressPreFixByte + " but "
          + address[0] + " !!");
      return false;
    }
    return true;
  }
