### Title
Improper array index validation in `Zip64ExtraField::attr64` reachable from crafted CDH/LH field combinations causes heap buffer over-read - ([File: src/tools/singlejar/zip_headers.h])

### Summary
`CDH::compressed_file_size()`, `CDH::uncompressed_file_size()`, and especially `CDH::local_header_offset()` (and their `LH` counterparts) derive an *index* into `Zip64ExtraField::attr64(int index)` purely from which 32-bit size/offset fields happen to equal `0xFFFFFFFF`, without ever checking that the actual Zip64 extra field's declared payload (`attr_count()`) is large enough to contain that many 8-byte attributes.

### Finding Description
`Zip64ExtraField::attr64` performs no bounds checking: [1](#0-0) 

`ExtraField::find` only validates that the field, based on its own self-declared `payload_size()`, fits within the entry's `extra_fields()`/`extra_fields_length()` window — it does not validate any relationship between `payload_size()` and how many attributes the *consumer* expects: [2](#0-1) 

The consumers, however, assume a fixed correspondence between the 32-bit fields and Zip64 attribute slots. For `CDH::local_header_offset()`, the index is computed by counting how many of `uncompressed_file_size32()`/`compressed_file_size32()` are `0xFFFFFFFF`: [3](#0-2) 

and `CDH::compressed_file_size()`/`uncompressed_file_size()` similarly pick attribute index 0 or 1 based on sentinel values in the 32-bit fields: [4](#0-3) 

Per the ZIP64 spec, the extra field's attribute count should match which 32-bit fields are `0xFFFFFFFF`, and the on-disk `payload_size()` should reflect that. But nothing in this codebase enforces that the crafted file's `payload_size()` (hence `attr_count()`) actually matches the pattern implied by the sentinel 32-bit fields. An attacker who controls the bytes of a jar/zip file (e.g., a dependency archive later merged by singlejar when building a Java deploy jar) can set `local_header_offset32_` to `0xFFFFFFFF` while making the accompanying Zip64 extra field's `payload_size()` only 0 (or 8), so `attr_count()` is 0 or 1. `CDH::local_header_offset()` will still compute `attr_no` up to 2 (if both size fields are also marked `0xFFFFFFFF`) and call `z64->attr64(2)`, reading 8 bytes at offset `4 + 2*8 = 20` into a field whose declared/allocated payload may be far smaller — an out-of-bounds read relative to the field's own extent, and potentially beyond the whole `extra_fields`/CDH buffer into adjacent heap memory, since nothing re-validates the index against the buffer end after the initial `find()` bounds check (which only validated the *field's own* claimed size, not the index used later).

This is functionally the same bug class as the ADMesh CVE: an index computed from untrusted input is used to access an array without validating it stays within the array's actual bounds (CWE-129/CWE-118).

### Impact Explanation
The out-of-bounds `attr64()` read can return attacker-influenced/garbage 64-bit values that are subsequently used as `uncompressed_file_size`/`compressed_file_size`/`local_header_offset` throughout `output_jar.cc` and `transient_bytes.h` (e.g., `TransientBytes::ReadEntryContents`/`DecompressEntryContents` call `Append(lh->data(), uncompressed_file_size)`, copying an attacker-influenced number of bytes from the input buffer). This can turn a simple OOB read into a much larger heap buffer over-read/copy, causing a crash (denial of service) or potential information disclosure from adjacent heap memory of the `singlejar` process, mirroring the ADMesh heap buffer overflow triggered by a crafted file.

### Likelihood Explanation
`singlejar` is invoked by Bazel's Java build rules to merge/repack jar files, including jars originating from external dependencies (e.g. fetched via `http_archive`/Maven artifacts). An attacker who can supply or tamper with a jar consumed in this pipeline (a hostile artifact server/mirror serving a crafted `.jar`) can trigger this path purely by crafting the CDH extra-field bytes; no local access or credential compromise is required. The main determinant of likelihood is whether jar-internal structural correctness is otherwise validated before reaching `zip_headers.h` parsing — based on the code reviewed, it is not; `ExtraField::find` only bounds-checks the field itself, not the index derived from sentinel values elsewhere.

### Recommendation
Add bounds checks before every `Zip64ExtraField::attr64(index)` call site (or centralize it inside `attr64`) so that `index < attr_count()` is enforced for the specific field being read (`compressed_file_size()`, `uncompressed_file_size()`, `local_header_offset()` in both `LH` and `CDH`). If the computed index would exceed `attr_count()`, treat the archive entry as malformed and fail via `diag_errx` rather than reading past the field.

### Proof of Concept
A reproducible check would extend the existing malformed-extra-field test infrastructure in `src/tools/singlejar/output_jar_simple_test.cc` (which already builds a hand-crafted "evil.bin" CDH/LH with malformed extra fields, see `CreateZipWithMalformedExtraField`) to construct a CDH where:
- `local_header_offset32_ = 0xFFFFFFFF`
- `compressed_file_size32_ = 0xFFFFFFFF`
- `uncompressed_file_size32_ = 0xFFFFFFFF`
- The accompanying Zip64 extra field has `payload_size() == 8` (i.e., only one 8-byte attribute present, `attr_count() == 1`)

Then call `CDH::local_header_offset()` (attr index would compute to 2) and observe the out-of-bounds `attr64(2)` read via ASan, which should flag a heap-buffer-overflow read beyond the extra field/CDH allocation. This can be added as a new `TEST` in `zip_headers_test.cc` or `output_jar_simple_test.cc`, run under `--config=asan`.

class ExtraField {
 public:
  static const ExtraField* find(uint16_t tag, const uint8_t* start,
                                const uint8_t* end) {
    while (start < end) {
      if (ziph::byte_ptr(start) + sizeof(ExtraField) > ziph::byte_ptr(end)) {
        break;
      }
      auto extra_field = reinterpret_cast<const ExtraField*>(start);
      if (ziph::byte_ptr(start) + extra_field->size() > ziph::byte_ptr(end)) {
        break;
      }
      if (extra_field->is(tag)) {
        return extra_field;
      }
      start = ziph::byte_ptr(start) + extra_field->size();
    }
    return nullptr;
  }
