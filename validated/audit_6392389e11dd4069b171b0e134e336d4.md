Confirmed: `handleRecvError` in `outside.go` is fully reachable by an attacker who has no valid CA-signed certificate, since `RecvError` packets are processed unencrypted, before any decrypt/AEAD check.

### Title
Unauthenticated RecvError packets allow remote tunnel teardown without proof of remote-address possession - (File: outside.go)

### Summary
`header.RecvError` packets are handled before any certificate/AEAD verification, using only the wire header's `RemoteIndex` field, which is observable by anyone who can see traffic on the path (or simply guess/brute-force, since it is only a 32-bit value). The remote-address check protecting against spoofing is skipped whenever the target hostinfo has no "valid" `GetRemote()` (e.g. tunnels that communicate purely via relay), letting a certificate-less attacker tear down an established tunnel and force expensive re-handshakes.

### Finding Description
In `readOutsidePackets`, `RecvError` is dispatched straight from the unencrypted switch, with no decryption or certificate check required: [1](#0-0) 

`handleRecvError` then looks the hostinfo up purely by the attacker-controlled `h.RemoteIndex`, and only rejects the packet if the hostinfo already has a *valid* recorded remote address that differs from the sender: [2](#0-1) 

```go
hr := hostinfo.GetRemote()
if hr.IsValid() && hr != addr {
    f.l.Info("Someone spoofing recv_errors?", ...)
    return
}
f.closeTunnel(hostinfo)
f.handshakeManager.DeleteHostInfo(hostinfo)
```

If `hr.IsValid()` is false (a tunnel that has no direct/roaming remote recorded, e.g. relay-only tunnels, or a tunnel mid-roam before a remote is set), the spoofing check is bypassed entirely and *any* off-path attacker who can send a UDP packet to the victim, with no cert, no handshake, and no keys, can supply a `RemoteIndex` value and unilaterally invalidate the hostinfo entry: `closeTunnel` calls `hostMap.DeleteHostInfo`, and `handshakeManager.DeleteHostInfo` clears the pending-handshake state too. This is directly analogous to the reported bug class: a piece of authoritative state (the hostinfo/tunnel "ownership") is torn down or manipulated by an actor who never proved they hold the corresponding credential (a valid, CA-signed cert equivalent to true order ownership), because a guard condition (`hr.IsValid()`) that should always enforce provenance is conditionally skipped.

### Impact Explanation
An attacker without a valid Nebula certificate can force repeated tunnel teardown of victim tunnels (especially relay-based ones, which are common in NAT-heavy overlay deployments) by spoofing `RemoteIndex` values in `RecvError` packets. This is a remote state-poisoning / denial-of-service vector: it forces gratuitous handshake churn, drops in-flight traffic, and can be used to pin a victim into a permanent re-handshake loop if repeated. It does not by itself allow decryption or forgery of tunnel traffic, but it does allow an unauthenticated party to manipulate authoritative hostmap/relay state that should require a proven, verified peer identity.

### Likelihood Explanation
`RemoteIndex` values are transmitted in cleartext in the wire header on every packet of an active tunnel, so an attacker capable of observing or guessing traffic between peers (or simply flooding many small guesses, since it's 32 bits and rate limiting on `RecvError` is only best-effort via `acceptRecvErrorConfig.ShouldRecvError`) can trigger this without ever completing a handshake or presenting a certificate. The condition is gated on `hr.IsValid()`, which is false in common deployment patterns (nodes reachable only via relay, or during early roam windows), making exploitation realistic rather than a corner case.

### Recommendation
Do not allow `RecvError`-driven teardown to bypass provenance checks. Either:
- Require that the local peer has already observed the remote address at least once (only accept `RecvError` for tunnels with a recorded remote, and drop `RecvError` for relay-only tunnels since a relayed connection can never legitimately produce a UDP-sourced `RecvError` with a matching direct address), or
- Bind acceptance of `RecvError` to an authenticated channel, e.g. require it to be accompanied by proof tied to the session (such as embedding a MAC keyed by the relevant `ConnectionState`), analogous to zeroing the "owner" on teardown in the original report, ensure that stale/absent provenance (`!hr.IsValid()`) is treated as "reject" rather than "allow", not as a bypass of the anti-spoofing check.

### Proof of Concept
1. Establish a relay-based tunnel between `me` and `them` through `relay` (a relay-only tunnel where `hostinfo.GetRemote()` is never set to a direct/valid address).
2. As an unauthenticated third party (no CA-signed cert, no established session), craft a UDP packet with header `Type=RecvError`, `RemoteIndex` set to the observed/guessed `localIndexId` of `me`'s hostinfo for `them` (or `them`'s hostinfo for `me`), and send it directly to the victim's UDP listener.
3. Because `hostinfo.GetRemote()` is invalid for the relay-only tunnel, `handleRecvError`'s spoofing guard `hr.IsValid() && hr != addr` short-circuits, and the tunnel is torn down and its pending-handshake state removed, without the attacker ever presenting a certificate or completing any handshake.

<br>

Note: I was unable to directly trace every caller and rate-limiting path for `sendRecvErrorConfig`/`acceptRecvErrorConfig` (e.g. exact throttling window, whether `ShouldRecvError` sufficiently limits this given index guessing at scale), and did not verify empirically how frequently `hostinfo.GetRemote()` returns invalid in production relay-only configurations versus roaming windows on direct tunnels; a full confirmation of exploitability at scale would benefit from a live/dynamic test in a background Devin session with terminal access, which is outside what I can verify via static code search alone.

func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
