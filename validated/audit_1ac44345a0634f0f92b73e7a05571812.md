This confirms the claim's core mechanics precisely. On BridgeHub, `system-v2::add_tip` (call_index 3) requires `T::FrontendOrigin` and is only invoked via XCM transact from `system-frontend::add_tip` on AssetHub — it is not a directly user-callable, permissionless BH extrinsic, but the flow originates from a permissionless AssetHub call.

Critically, in `system-frontend::add_tip` [1](#0-0) , the user's tip asset is swapped for ether and **burned for teleport** via `Self::swap_fee_asset_and_burn` *before* the XCM transact call to BH is even sent [2](#0-1) . This means the user's funds are irrevocably destroyed on AssetHub regardless of what happens on BridgeHub. If the BH-side `add_tip` then fails because the nonce/order is already consumed [3](#0-2) , the equivalent ether amount is only recorded in `LostTips` — a bookkeeping entry, not actual custody of funds (the real asset was already burned on AH). There is no dispatchable in the pallet's `Call` enum to reclaim this [4](#0-3) , and the storage doc comment itself confirms recovery is only a future aspiration [5](#0-4) . The `AddTip` trait implementations for both inbound and outbound queues confirm the race condition: `InboundQueue::add_tip` rejects tips for nonces already marked consumed [6](#0-5) , and `OutboundQueue::add_tip` rejects tips when the `PendingOrder` for that nonce no longer exists [7](#0-6) . Both are demonstrated as reachable in the integration tests [8](#0-7)  and unit tests [9](#0-8) .

This validates the claim: an unprivileged, signed user calling `EthereumSystemFrontend::add_tip` on AssetHub can, through the normal permissionless race against relayers processing messages, have their tip asset irrecoverably burned with no path to reclaim the equivalent value once it lands in BridgeHub's `LostTips` map.

Audit Report

## Title
Permanently unrecoverable relayer tips via `LostTips` fallback with no reclaim path - (File: `bridges/snowbridge/pallets/system-v2/src/lib.rs`)

## Summary
When a user calls `SnowbridgeSystemFrontend::add_tip` on AssetHub, their tip asset is swapped for ether and burned for teleportation before the corresponding `EthereumSystemV2::add_tip` transact call reaches BridgeHub. If, by that time, the target message nonce (inbound) or pending order (outbound) has already been consumed/removed — an ordinary outcome of permissionless relayer competition — the tip is diverted into the `LostTips` storage map on BridgeHub instead of the depositor's message reward, while the real underlying asset was already irrevocably burned on AssetHub. No extrinsic exists anywhere in the codebase to reclaim value recorded in `LostTips`.

## Finding Description
The flow spans two pallets. On AssetHub, `EthereumSystemFrontend::add_tip` first swaps the caller's tip asset to ether and burns it for teleport via `swap_fee_asset_and_burn`, then builds and sends an XCM transact call targeting `EthereumSystemCall::AddTip` on BridgeHub (`bridges/snowbridge/pallets/system-frontend/src/lib.rs:261-273`). The burn happens unconditionally and irreversibly, prior to any confirmation that the tip will actually attach to a live message.

On BridgeHub, `EthereumSystemV2::add_tip` (`bridges/snowbridge/pallets/system-v2/src/lib.rs:251-281`) dispatches to `InboundQueue::add_tip` or `OutboundQueue::add_tip` depending on `MessageId`. `InboundQueueV2::add_tip` rejects the tip with `AddTipError::NonceConsumed` if `Nonce::<T>::get(nonce)` is already true (`bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs:248-259`), and `OutboundQueueV2::add_tip` rejects with `AddTipError::UnknownMessage` if `PendingOrders::<T>::get(nonce)` no longer exists (`bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs:483-496`). On any such error, `system-v2::add_tip` increments `LostTips::<T>` for the sender and emits `TipProcessed { success: false }` (`bridges/snowbridge/pallets/system-v2/src/lib.rs:266-271`).

Because `add_tip` and message processing (`InboundQueue::process_message`, or the relevant outbound delivery-receipt handling that removes `PendingOrders`) are both permissionless and independently timed, a routine race — a relayer processing the message before the tip transaction lands — causes this failure path to trigger under normal network conditions, not just adversarial ones. `LostTips` is explicitly documented as a fallback pending a "recovery method in the future" (`bridges/snowbridge/pallets/system-v2/src/lib.rs:136-142`), and no such method exists in the pallet's `Call` enum. Since the actual asset was already burned on AssetHub before the BH-side rejection is even known, the value is unrecoverable in both bookkeeping (`LostTips` has no claim path) and in raw custody (the underlying token no longer exists on AssetHub; only an unclaimable ether-equivalent count remains on BridgeHub).

## Impact Explanation
This is a permanent user-fund lock: a signed, unprivileged user's tip funds are irreversibly burned on AssetHub and the equivalent value becomes stuck as an unclaimable balance entry in `LostTips` on BridgeHub, with no dispatchable anywhere in the codebase to return it to the depositor.

## Likelihood Explanation
High under normal operation. Relayers are economically incentivized to process inbound/outbound messages as fast as possible, so any user tipping a message nonce shortly after (or concurrently with) submission risks losing the tip to this race — no privileged access, malicious behavior, or contrived timing is required. Existing unit tests (`bridges/snowbridge/pallets/system-v2/src/tests.rs:197-219`, `:243-264`) and an integration test (`cumulus/parachains/integration-tests/emulated/tests/bridges/bridge-hub-westend/src/tests/snowbridge_v2_outbound.rs:277-320`) trivially demonstrate the "lost tip" state is reachable.

## Recommendation
Add a permissionless, depositor-restricted `claim_lost_tip` extrinsic on the BridgeHub `system-v2` pallet that lets the original tipper (the `AccountIdOf<T>` key in `LostTips`) withdraw their stranded balance, and ensure the corresponding ether value is actually minted/available to be claimed there (rather than only tracked as a counter) so custody matches the accounting. Alternatively, redesign `add_tip` on AssetHub to defer the burn until BridgeHub has confirmed the tip attached successfully, avoiding irreversible loss of the underlying asset before success is known.

## Proof of Concept
1. User A calls `SnowbridgeSystemFrontend::add_tip` on AssetHub targeting inbound nonce `N`; their tip asset is swapped to ether and burned for teleport, and an XCM transact `EthereumSystemCall::AddTip{sender: A, message_id: Inbound(N), amount}` is sent to BridgeHub.
2. Before this XCM lands, any relayer calls `InboundQueueV2::process_message` for a message with nonce `N`, setting `Nonce::<T>::set(N)`.
3. The transacted `EthereumSystemV2::add_tip` call now hits `InboundQueue::add_tip(N, amount)` → `AddTipError::NonceConsumed`, so `LostTips::<T>::mutate(&A, ...)` increments and `TipProcessed{success: false}` is emitted.
4. User A's original asset is gone (burned in step 1) and no extrinsic exists to claim the `LostTips` entry — confirmed by inspecting the pallet's `#[pallet::call]` block, which contains only `upgrade`, `set_operating_mode`, `register_token`, and `add_tip`.
