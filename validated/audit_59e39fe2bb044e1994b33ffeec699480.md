### Title
DebtToken interest accrual inflates reward share in RewardsDistributor without any index checkpoint - (File: contracts/RewardsDistributor.sol)

### Summary
`RewardsDistributor._calculateTokenDelta` computes an account's accrued rewards as `token_.balanceOf(account_).wadMul(_deltaIndex)` — i.e., the *current* balance is multiplied by the *entire* index delta since the account's last checkpoint (`contracts/RewardsDistributor.sol:217-231`). Index checkpoints are only written when `updateBeforeMintOrBurn` or `updateBeforeTransfer` are invoked by `DepositToken`/`DebtToken` (`contracts/RewardsDistributor.sol:175-192`). For `DebtToken`, `balanceOf` grows passively over time via interest accrual (the balance is `principal * debtIndex` growth, not minted units — see `DebtToken.sol` `balanceOf`/interest accrual), and this growth does not trigger any `updateBefore*` hook. A borrower's reward entitlement is therefore computed on an interest-inflated balance that was never checkpointed, letting them harvest rewards as if the inflated balance existed for the entire accrual period.

### Finding Description
The analog to the YUM.games bug (calling `gamestart`/`draw` to collect a prize without first placing a bet) is: collecting rewards on a balance the account never actually held during the accrual window.

Concretely:
1. Attacker deposits collateral and calls `DebtToken.issue(amount_, attacker)` (`DebtToken.sol:241-271`). The mint calls `updateBeforeMintOrBurn`, setting `accountIndexOf[debtToken][attacker] = currentIndex`.
2. Time passes. Two things grow: the reward `tokenStates[debtToken].index` (via `tokenSpeeds`) and the attacker's `DebtToken.balanceOf` (via `debtIndex` interest accrual). The interest growth never calls `updateBeforeMintOrBurn`, so `accountIndexOf` stays stale while `balanceOf` grows.
3. Attacker calls `RewardsDistributor.claimRewards(attacker, [debtToken])` (`RewardsDistributor.sol:150-168`). `_updateTokensAccruedOf` computes `_tokensDelta = balanceOf(attacker).wadMul(tokenIndex - accountIndex)` using the interest-inflated current balance against the whole historical index delta.
4. `_transferRewardIfEnoughTokens` pays out the inflated `tokensAccruedOf` (`RewardsDistributor.sol:248-256`).

Invariant broken: reward accrual correctness — each account should earn `speed * balance * dt / totalSupply` on the balance actually held during `dt`. Here interest-bearing balance growth is retroactively treated as held since the last checkpoint. The same accounting also means the extra claim dilutes all other participants' shares (the global index divides a fixed `speed` emission over `totalSupply`, so over-crediting one account under-credits the rest), and the pool's `rewardToken` balance is drained faster than emissions authorize.

Additionally, `accountIndexOf`'s `INITIAL_INDEX` fallback (`_accountIndex == 0 && _tokenIndex > INITIAL_INDEX → _accountIndex = INITIAL_INDEX`, lines 225-227) compounds this for any balance-increasing path that skips the `updateBefore*` hooks (e.g., a `seize`/liquidation credit or any internal transfer that does not route through the distributor hooks — I could not fully enumerate every `DepositToken` credit path in the available context, so this secondary vector should be confirmed in the PoC by checking whether `DepositToken.seize`/`Pool.liquidate` calls `updateBeforeTransfer`).

### Impact Explanation
Direct theft of unclaimed yield (an accepted impact class): the attacker withdraws `rewardToken` beyond their fair share, and the excess comes out of the fixed emission budget owed to all other suppliers/borrowers, permanently reducing their claimable amounts. The attack is repeatable — repay, re-issue, wait, claim again — and scales with position size and `interestRate`.

### Likelihood Explanation
Requires only unprivileged calls (`issue`, `claimRewards`) on the deployed configuration: a `DebtToken` with `interestRate > 0` and a nonzero `tokenSpeeds[debtToken]` in a registered `RewardsDistributor`. No privileged role, oracle manipulation, or governance action is needed; `nonReentrant` does not help because the inflation is passive. Likelihood is high wherever borrower rewards are enabled.

### Recommendation
Checkpoint reward indexes on the value that actually earns rewards:
- Use the non-growing `principalOf(account_)` (debt shares) instead of `balanceOf` in `_calculateTokenDelta` for `DebtToken`, or
- Treat `DebtToken` interest accrual as balance-changing: call `updateBeforeMintOrBurn` whenever `balanceOf` would change materially (impractical for continuous interest, so prefer the first option), or
- Track a per-account reward base updated on mint/burn/transfer only.

Also audit every balance-crediting path (`DepositToken.seize`, `Pool.liquidate`, gateway deposits) to confirm it routes through `updateBeforeTransfer`/`updateBeforeMintOrBurn` so the `INITIAL_INDEX` fallback cannot grant retroactive rewards.

### Proof of Concept
Hardhat fork sketch:

```ts
// fork a chain where RewardsDistributor has tokenSpeeds[debtToken] > 0
// and debtToken.interestRate > 0 (e.g., msUSD debt on optimism/mainnet)
const pool = await ethers.getContractAt("Pool", POOL);
const debtToken = await ethers.getContractAt("DebtToken", DEBT_TOKEN);
const distributor = await ethers.getContractAt("RewardsDistributor", DISTRIBUTOR);
const rewardToken = await ethers.getContractAt("IERC20", await distributor.rewardToken());

// 1. deposit collateral and issue max debt
await depositToken.deposit(collateralAmount, attacker.address);
await debtToken.connect(attacker).issue(issueAmount, attacker.address);

// 2. let interest accrue (balanceOf grows, no checkpoint happens)
await time.increase(30 * 24 * 3600);

// 3. compare claimable vs fair share computed on principal held
const claimed = await distributor.claimable(attacker.address);
const principal = await debtToken.principalOf(attacker.address);
// fair = principal * (indexNow - indexAtIssue); observed `claimed` uses
// balanceOf (principal + interest) -> strictly greater
await distributor.claimRewards(attacker.address, [debtToken.address]);
const paid = await rewardToken.balanceOf(attacker.address);
assert(paid > fairShare); // over-crediting = stolen yield
```

Expected result: `paid` exceeds the entitlement computed on the time-weighted principal, and `tokensAccruedOf` for other accounts is correspondingly understated.

Uncertainty note: I verified the delta math and that interest growth emits no `updateBefore*` hook call; I did not get line-level confirmation that `DepositToken.seize`/`Pool.liquidate` routes through the hooks, so the stronger retroactive variant via the `INITIAL_INDEX` fallback remains plausible but unconfirmed.
