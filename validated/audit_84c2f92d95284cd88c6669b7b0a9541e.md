## Analog Found

### Title
Object directory quarantine ownership check bypassed by overly broad `isTransactionQuarantineDir` boolean gate - (File: internal/git/localrepo/paths.go)

### Summary
`Repo.ObjectDirectoryPath()` is supposed to verify that a `GitObjectDirectory` value supplied on an RPC's `Repository` message either lives inside the repository itself, or, if it points to a temporary quarantine directory, that the quarantine directory actually belongs to *that* repository (verified via a per-repository SHA1-derived prefix). The gate that decides whether this ownership check is skipped uses the wrong boolean combination, so any path whose basename is literally `quarantine` bypasses the ownership verification entirely, regardless of whether it is actually this repository's quarantine directory.

### Finding Description
The relevant logic is: [1](#0-0) 

```go
parentDir := filepath.Base(filepath.Dir(relativeObjectDirectoryPath))
baseDir := filepath.Base(relativeObjectDirectoryPath)
isTransactionQuarantineDir := (baseDir == "quarantine") || ((parentDir == "quarantine") && strings.HasPrefix(baseDir, "tmp_objdir"))
...
if !isTransactionQuarantineDir {
    // ownership check using storage.QuarantineDirectoryPrefix(repo), which is a
    // sha1-based prefix computed from the *current* repo's relative path
    ...
}
``` [2](#0-1) 

When `baseDir == "quarantine"` alone, `isTransactionQuarantineDir` is unconditionally `true`, and the subsequent block that verifies the directory prefix matches `storage.QuarantineDirectoryPrefix(repo)` — the check that ties a quarantine directory to a specific repository — is skipped entirely. The only remaining protection is `storage.ValidateRelativePath(storagePath, ...)`, which merely ensures the resolved path stays inside the *storage* root, not that it belongs to the *requesting repository*: [3](#0-2) 

`storage.QuarantineDirectoryPrefix()` is precisely the mechanism designed to prove a quarantine directory belongs to a given repository: [4](#0-3) 

Because the `baseDir == "quarantine"` branch of the `||` short-circuits the whole gate to `true`, an attacker only needs to make the *last path component* of the resolved `GitObjectDirectory` equal to `quarantine` (e.g., another repository's transaction quarantine directory under `tx-state/quarantine`, as exercised in tests, or any directory named `quarantine` anywhere under the storage root) to skip the per-repository ownership check. This is the same class of bug as the reported `onlyAdminOrOperator()` issue: a boolean gate that is supposed to require an additional/AND'd condition to widen access is instead OR'd, over-broadening the branch that is meant to be a narrow exception.

Existing tests document that this exact mechanism is treated as the trust boundary, e.g. the `TestGetObjectDirectorySize_quarantine` "repository quarantined by transaction manager" case explicitly relies on a path with basename `quarantine` skipping verification, and a related sibling test asserts that mismatched quarantines *are* supposed to be rejected via `escapes root directory`: [5](#0-4) [6](#0-5) 

The second test only fails safely because it uses `quarantine-<hash>-*` style directories where the *base* name is not literally `quarantine`, forcing evaluation into the ownership-check branch. Any object directory value whose final path segment is `quarantine` bypasses that branch altogether.

### Impact Explanation
`GitObjectDirectory`/`GitAlternateObjectDirectories` on the `Repository` proto message are used broadly to point Git subprocesses at alternate object stores — this is exactly the mechanism GitLab Rails uses during access checks and that Gitaly's `TransactionManager` uses for write quarantines. If a caller can influence these fields to reference a directory named `quarantine` under a different repository/transaction's staging area within the same storage, `ObjectDirectoryPath()` will resolve and permit access to that directory as an object source without validating repository ownership, i.e. a cross-repository object disclosure/isolation break within a shared storage. This weakens the object quarantine isolation model described in `doc/object_quarantine.md`, whose entire purpose is to keep in-flight/pushed objects scoped to the originating request and repository.

### Likelihood Explanation
Exploitability depends on whether an ordinary caller (or a component acting on data partly influenced by ordinary callers, e.g. Rails relaying repository fields back to Gitaly during access checks) can set `GitObjectDirectory` to an attacker-chosen relative path whose basename is `quarantine` and that concurrently exists on disk (e.g., another in-flight push's transaction quarantine directory under `tx-state/quarantine`, as shown being created in `TransactionManager.Begin`): [7](#0-6) 

Because such directories are transient and only exist during another repository's in-flight write transaction, exploitation requires timing (racing a concurrent push/transaction on the same storage) plus control over the `Repository.GitObjectDirectory` field. I could not fully verify from indexed code alone which gRPC entry points and interceptors validate or strip `GitObjectDirectory` on inbound client requests versus trusting it only when echoed back by Rails/internal callers, so likelihood is assessed as low-to-medium and unconfirmed for a fully external, unprivileged attacker.

### Recommendation
Fix the boolean gate so the "trusted transaction quarantine" branch cannot be satisfied by basename alone; require both the parent-directory match and, even for the `baseDir == "quarantine"` case, verify the directory's ancestry against the specific transaction's/repository's expected temp-directory path (or apply the `storage.QuarantineDirectoryPrefix(repo)` ownership check unconditionally rather than skipping it). For example, require an AND of "is a quarantine-shaped path" with "the resolved path's temp-dir prefix matches this repository," rather than allowing `baseDir == "quarantine"` to skip that verification outright.

### Proof of Concept
Not independently runnable from the indexed context alone (would require constructing a live gRPC request with a crafted `Repository.GitObjectDirectory` while a concurrent transaction on another repository has an active `tx-state/quarantine` directory on the same storage, then invoking an RPC such as `GetObjectDirectorySize` or any RPC that reads via `ObjectDirectoryPath()`). The existing test `TestGetObjectDirectorySize_quarantine`'s "repository quarantined by transaction manager" subtest demonstrates the code path being reached and accepted via the `baseDir == "quarantine"` branch: [5](#0-4) 

I recommend starting a Devin session with filesystem/terminal access to build a concrete end-to-end PoC (spin up a repository, start a concurrent write transaction to create a real `tx-state/quarantine` directory, then issue a second RPC with `GitObjectDirectory` pointed at that path) since this is outside what can be confirmed via static code search alone.

// QuarantineDirectoryPrefix returns a prefix for use in the temporary directory. The prefix is
// based on the relative repository path and will stay stable for any given repository. This allows
// us to verify that a given quarantine object directory indeed belongs to the repository at hand.
// Ideally, this function would directly be located in the quarantine module, but this is not
// possible due to cyclic dependencies.
func QuarantineDirectoryPrefix(repo Repository) string {
	hash := [20]byte{}
	if repo != nil {
		hash = sha1.Sum([]byte(repo.GetRelativePath()))
	}
	return fmt.Sprintf("quarantine-%x-", hash[:8])
