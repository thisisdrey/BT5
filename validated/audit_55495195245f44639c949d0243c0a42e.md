### Title
Gas-key AddKey nonce reseed floor can fall below a same-block nonce ceiling, enabling nonce replay on a re-added key - (File: `runtime/runtime/src/access_keys.rs`)

### Summary
`add_gas_key` reseeds every one of a gas key's `num_nonces` nonce rows to a single floor, `initial_nonce_value(block_height) = (block_height - 1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` [1](#0-0) [2](#0-1) . `verify_nonce`'s upper-bound rejection instead uses the *current* `block_height` (not `block_height - 1`) to compute the nonce ceiling [3](#0-2) . Because these two bounds differ by one full `ACCESS_KEY_NONCE_RANGE_MULTIPLIER` (1,000,000) unit, a nonce validated within block `B` can legally be as large as just under `B * MULTIPLIER`, while a same-block `DeleteKey`+`AddKey` on the same public key resets the floor to `(B - 1) * MULTIPLIER` — strictly below that nonce.

### Finding Description
- `initial_nonce_value` is defined as `(block_height - 1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER`, used both to seed a fresh regular key's nonce and, in `add_gas_key`, to seed **every** `num_nonces` row of a gas key uniformly [1](#0-0) [4](#0-3) .
- `action_delete_key`/`delete_gas_key` fully removes all per-index nonce rows from the trie on `DeleteKey`, so there is no "carry forward" of the historical high-water mark for any index [5](#0-4) .
- `verify_nonce`'s only anti-replay checks are: (a) `tx_nonce > current_nonce` for `Monotonic` mode, and (b) `tx_nonce < block_height * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` [6](#0-5) . There is no check that a resurrected key's new floor exceeds the historical maximum ever recorded for that public key/index pair (that history is deleted, not tracked).
- If an attacker, within a single block `B`, (1) submits a gas-key transaction at `nonce_index=1` with a nonce close to the block's own ceiling (`< B * MULTIPLIER`), then (2) in the same block issues `DeleteKeyAction` followed by `AddKeyAction` re-adding the identical public key as a gas key, the new floor for index 1 becomes `(B-1) * MULTIPLIER`, which can be far below the nonce used in step (1). Any block `B' > B` at which delete/re-add instead occurs would make the new floor `>= B * MULTIPLIER`, which already dominates every nonce legally usable in block `B` — so the gap only opens when the delete/re-add happens in the *same* block as the high-nonce transaction.
- Once the floor is lowered below the previously-used nonce, the exact previously-applied `SignedTransaction` (same hash) can be resubmitted in a *later* block/chunk (bypassing the intra-chunk hash de-duplication, which only guards against exact-hash duplicates within one chunk [7](#0-6) ), and `verify_nonce`'s `tx_nonce > current_nonce` check passes again, re-executing the transaction against the reseeded key.

### Impact Explanation
If the replayed transaction is one that spends the gas key's prepaid balance (e.g., a `WithdrawFromGasKey` or a gas-key-paid `Transfer`), it will be applied a second time against the reseeded nonce state, resulting in double-spend of the gas key's/account's funds — matching the "double-spend/replay" and fund-loss categories in scope.

### Likelihood Explanation
This requires a very narrow precondition: the attacker must get their own high-nonce gas-key transaction and their own `DeleteKey`+`AddKey` (same public key) *all included in the exact same block/chunk*. If even one additional block elapses between the high-nonce transaction and the delete/re-add, the recomputed floor (based on the later block height) already exceeds any nonce legally usable in the earlier block, closing the gap entirely. Achieving same-block ordering of several of one's own sequential transactions is plausible for an unprivileged account (it only needs its own transactions accepted into one chunk), but is not guaranteed and depends on mempool/chunk-producer scheduling, which the attacker does not fully control. I was not able to fully verify, within the available exploration, whether any additional guard (e.g., pending-nonce tracking across the mempool, or `AddKeyAction` validation forcing a fresh gas key's balance to always start at zero, which would limit real monetary impact of a replayed action) further constrains this path — the `add_gas_key` code takes `GasKeyInfo.balance` directly from the caller-supplied `AddKeyAction.access_key`, which is a related but separate concern not fully audited here.

### Recommendation
Compute the gas-key/regular-key nonce reseed floor using the same `block_height` basis as the nonce upper-bound check (e.g., use `block_height * MULTIPLIER` rather than `(block_height - 1) * MULTIPLIER`, or otherwise ensure the floor is always `>=` the maximum nonce ever validated in the current block) so that a same-block `DeleteKey`+`AddKey` cannot produce a floor below any nonce that could have been validated earlier in that same block.

### Proof of Concept
Unit test plan (extending `runtime/runtime/src/access_keys.rs` test module style, using `verify_nonce` from `verifier.rs` and `initial_nonce_value`):
1. Fix `block_height = B`.
2. Assert `verify_nonce` accepts `tx_nonce = B * MULTIPLIER - 1` against a freshly-seeded floor `(B0 - 1) * MULTIPLIER` for `B0 <= B` (simulating the high-water-mark transaction).
3. Compute `new_floor = initial_nonce_value(B)` (simulating same-block `DeleteKey`+`AddKey`) and assert `new_floor < B * MULTIPLIER - 1`, proving the reseed floor is below the previously-valid nonce.
4. Call `verify_nonce(B * MULTIPLIER - 1, new_floor, None, NonceMode::Monotonic)` and assert it returns `Ok(())`, proving the old high-water-mark nonce would pass validation again post-reseed.
5. Table-test across several `(B0, B)` pairs with `B0 == B` (gap exists, assert reseed floor < historical max) versus `B0 < B` (no gap, assert reseed floor >= historical max), confirming the invariant only fails in the same-block case.

pub(crate) fn initial_nonce_value(block_height: BlockHeight) -> Nonce {
    // Set default nonce for newly created access key to avoid transaction hash collision.
    // See <https://github.com/near/nearcore/issues/3779>.
    (block_height - 1) * near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER
}

fn add_gas_key(
    fee_config: &RuntimeFeesConfig,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    public_key: &PublicKey,
    access_key: &AccessKey,
    gas_key_info: &GasKeyInfo,
    block_height: BlockHeight,
) -> Result<(), StorageError> {
    // For gas keys, nonce stored on access key is not used and should always be zero
    let mut access_key = access_key.clone();
    access_key.nonce = 0;
    set_access_key(state_update, account_id.clone(), public_key.clone(), &access_key);

    // Set up nonces for gas key
    let num_nonces = gas_key_info.num_nonces;
    let nonce = initial_nonce_value(block_height);
    for i in 0..num_nonces {
        set_gas_key_nonce(state_update, account_id.clone(), public_key.clone(), i, nonce);
    }

    account.set_storage_usage(
        account
            .storage_usage()
            .checked_add(gas_key_storage_cost(fee_config, public_key, &access_key, num_nonces))
            .ok_or_else(|| {
                StorageError::StorageInconsistentState(format!(
                    "Storage usage integer overflow for account {}",
                    account_id
                ))
            })?,
    );
    Ok(())
}
