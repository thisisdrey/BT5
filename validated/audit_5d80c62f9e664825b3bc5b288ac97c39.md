### Title
Missing chain-domain binding in `ValidateMultiSign` precompile signature digest enables cross-network signature replay - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The Gnosis report flags that `_verifySender()` accepted a cross-chain message without checking `messageSourceChainId() == MIRROR_DOMAIN`, letting a payload root minted on an unintended chain be treated as authoritative because the verification digest carried no chain-scoping. The `ValidateMultiSign` precompile in java-tron has the analogous root cause: the digest it uses to recover signer addresses for a multisig permission check is built purely from `address || permissionId || data`, with no TRON network/chain identifier folded in.

### Finding Description
`ValidateMultiSign.execute()` builds the message hash to be verified as: [1](#0-0) 
This `combine`/`hash` construction has no chain-id, genesis hash, or any other network-specific salt — it is only `address`, `permissionId`, and the caller-supplied `data`. Signatures are then recovered against this hash and weighed against the on-chain `Permission` for `address`: [2](#0-1) 
Because TRON addresses are derived deterministically from the public key and are typically identical across the mainnet and any java-tron-derived network (testnets, private chains, or forks/sidechains built from this codebase), a permission-holder's off-chain signature authorizing one payload for one network can be replayed verbatim against `ValidateMultiSign` on a different network sharing the same address/permission state — exactly the "same contract address on another chain treated as authoritative" pattern flagged in the Gnosis report, just realized at the TVM precompile layer instead of the AMB bridge layer. The precompile is reachable by any contract via a `CALL` to precompile address `0x...0a`, gated only by `VMConfig.allowTvmSolidity059()`: [3](#0-2) 
so any unprivileged transaction sender that triggers a smart contract using this precompile for authorization can supply a signature obtained/observed from another network to pass validation on this one.

### Impact Explanation
Any smart contract that relies on `validatemultisign(address,uint256,bytes32,bytes[])` to authorize sensitive actions (fund transfers, permission changes, order execution) using a multisig scheme keyed only by `address`/`permissionId`/`data` is vulnerable to cross-chain signature replay: a signature legitimately produced for a permission-holder's action on one TRON-compatible network can be reused to satisfy the weight/threshold check on another, resulting in unauthorized account operations or asset transfers protected by that dApp's multisig logic.

### Likelihood Explanation
Exploitation requires: (1) a dApp using `ValidateMultiSign` for authorization without independently adding chain-domain separation in its `data` payload, and (2) the same account/permission structure existing (or being reproducible) on a second java-tron-derived network. Given java-tron code is widely forked/reused for sidechains and test networks, and address derivation is chain-agnostic, this is a realistic occurrence, though it depends on external dApp design not adding its own domain separator.

### Recommendation
Include a chain-scoping value (e.g., the local genesis block hash/chain id, analogous to `messageSourceChainId()`/`MIRROR_DOMAIN` in the Gnosis fix) in the `combine` buffer hashed by `ValidateMultiSign` (and `BatchValidateSign` callers relying on precompile-level authorization), so a signature is only valid for the specific chain it was produced for. At minimum, document clearly that callers must fold in their own chain-id/domain separator into `data`, since the precompile itself does not.

### Proof of Concept
1. Deploy the same contract bytecode (using `validatemultisign`) on java-tron mainnet and on a forked/derived java-tron network (e.g., a private testnet built from this codebase) where the same target `address` retains the same `Permission` (id, keys, threshold) — plausible when addresses/permissions are provisioned identically across environments.
2. On network B, a permission-holder signs `data` intending to authorize an action only on network B via a dApp that reuses this precompile as its sole authorization gate.
3. Attacker captures this signature and submits it through a contract call to `ValidateMultiSign` on network A with the same `address`/`permissionId`/`data`.
4. Because `combine = address || permissionId || data` (`actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java:1062-1065`) is identical on both networks, the recomputed hash and recovered signer match, `getWeight` succeeds, and the call returns `dataOne()` — authorizing the action on network A despite the signer never intending it, mirroring the "spoof cross-chain message from the same contract address" issue in the Gnosis report.
