### Title
Concurrency limiter keys solely on relative path, letting requests for repositories in one storage exhaust the queue of a same-named repository in a different storage - (File: internal/grpc/middleware/limithandler/middleware.go)

### Summary
Gitaly's per-repository concurrency/backpressure limiter uses `LimitConcurrencyByRepo` as the default lock-key function, which derives the limiter key exclusively from the repository's relative path and ignores the storage name.

### Finding Description
`LimitConcurrencyByRepo` extracts the limiting key from the request as follows: [1](#0-0) 

The key returned is `info.Repository.GetRelativePath()` only - `GetStorageName()` is never consulted. The `ConcurrencyLimiter` then buckets all callers using this string as the map key for a shared `keyedConcurrencyLimiter` (semaphore + queue): [2](#0-1) 

Because a Gitaly node can host multiple configured storages (`[[storage]]` entries), and repository relative paths are frequently deterministic/predictable (e.g., hashed-storage paths derived from project IDs, or user-controlled paths in some deployments/tests), two *distinct* repositories that happen to share the same `relative_path` but live in different `storage_name`s will collapse onto the exact same `keyedConcurrencyLimiter` instance and share the same `max_per_repo` / `max_queue_size` / `max_queue_wait` budget, as configured in `[[concurrency]]`: [3](#0-2) 

This is directly analogous to the `asdUSDC` bug class: a resource-accounting mechanism (the withdrawal balance / here, the concurrency quota) is tracked using an identifier (`_usdcVersion` / here, `relative_path`) that does not correspond 1:1 with the actual isolated backing resource (the aggregate USDC balance / here, the actual distinct repository identified by `storage+relative_path`). Just as removing one whitelisted "compartment" while total supply is shared caused unrelated holders to be starved of withdrawals, an ordinary caller issuing requests against a repository in *storage A* can consume the entire concurrency/queue budget nominally intended for a *different, unrelated* repository that merely shares the same relative path in *storage B*.

### Impact Explanation
Any RPC configured under `[[concurrency]]` with `max_per_repo`/`max_queue_size` (e.g. `PostUploadPackWithSidechannel`) is affected. An attacker who can create or clone a repository whose relative path collides with a relative path used on another storage (or who can predict/guess a hashed relative path, since hashed storage paths are derived from a low-entropy, sequential project ID) can flood the shared limiter key with slow requests (large clones, held-open smart-HTTP/SSH sessions). This exhausts the `max_per_repo` semaphore and fills the `max_queue_size` queue, causing legitimate `ErrMaxQueueSize` / `ErrMaxQueueTime` rejections for a completely unrelated repository residing on a different storage - a cross-tenant/cross-storage denial-of-service of the RPC-handler resource-limiting mechanism, triggered purely through ordinary fetch/clone traffic and repository naming, without any privileged access.

### Likelihood Explanation
Likelihood depends on relative-path collisions occurring across storages, which is plausible in multi-storage Gitaly deployments (e.g., Praefect virtual storages with several physical storages sharing the hashed-path scheme, or storages backing different GitLab instances/tenants on the same Gitaly node). Because hashed storage relative paths are a deterministic hash of a monotonically increasing project ID, an attacker on a multi-tenant setup can often predict or brute-force a colliding relative path.

### Recommendation
Include the storage name in the concurrency-limiter key, e.g. change `LimitConcurrencyByRepo` to return a composite key such as `info.Repository.GetStorageName() + "/" + info.Repository.GetRelativePath()`, ensuring the limiter partitions strictly per physical repository rather than per relative path alone.

### Proof of Concept
1. Configure a Gitaly node with two storages, `storage-a` and `storage-b`, and a `[[concurrency]]` rule with `rpc = "/gitaly.SmartHTTPService/PostUploadPackWithSidechannel"`, `max_per_repo = 1`, `max_queue_size = 5`.
2. Create (or arrange, e.g. via colliding hashed relative paths) `repository X` at relative path `R` in `storage-a`, and an unrelated `repository Y` at the same relative path `R` in `storage-b`.
3. From an ordinary client, issue `max_per_repo + max_queue_size` concurrent, slow `PostUploadPackWithSidechannel` clones/fetches against `repository X` (storage-a).
4. Observe that concurrent fetch requests against the unrelated `repository Y` (storage-b) are now rejected with `ErrMaxQueueSize`/`ErrMaxQueueTime`, even though `repository Y` itself has no concurrent traffic - because both share the single `keyedConcurrencyLimiter` keyed only by relative path `R`.

```go
// LimitConcurrencyByRepo implements GetLockKey by using the repository path as lock.
func LimitConcurrencyByRepo(ctx context.Context) string {
	if info := requestinfohandler.Extract(ctx); info != nil {
		return info.Repository.GetRelativePath()
	}

	return ""
}
```

```go
// getConcurrencyLimit retrieves the concurrency limit for the given key. If no such limiter exists
// it will be lazily constructed.
func (c *ConcurrencyLimiter) getConcurrencyLimit(limitingKey string) *keyedConcurrencyLimiter {
	c.m.Lock()
	defer c.m.Unlock()

	if c.limitsByKey[limitingKey] == nil {
		// Set up the queue tokens in case a maximum queue length was requested. As the
		// queue tokens are kept during the whole lifetime of the concurrency-limited
		// function we add the concurrency tokens to the number of available token.
		var queueTokens semaphorer
		if c.maxQueueLength > 0 {
			queueTokens = c.createSemaphore(uint(c.currentLimit() + c.maxQueueLength))
		}

		c.limitsByKey[limitingKey] = &keyedConcurrencyLimiter{
			monitor:               c.monitor,
			maxQueueWait:          c.maxQueueWait,
			setWaitTimeoutContext: c.SetWaitTimeoutContext,
			concurrencyTokens:     c.createSemaphore(uint(c.currentLimit())),
			queueTokens:           queueTokens,
		}
	}

	c.limitsByKey[limitingKey].refcount++

	return c.limitsByKey[limitingKey]
}
```
