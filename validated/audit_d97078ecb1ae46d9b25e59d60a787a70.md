### Title
Missing Invariant Check in Legacy `ExchangeCapsule.transaction()` AMM Math Path - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java])

### Summary
Analogous to the DODOMath issue where the invariant `V0 >= V1 >= V2 > 0` is not enforced on bonding-curve inputs/outputs, java-tron's TRX/TRC10 bancor-style exchange pool math in `ExchangeCapsule.transaction()` only enforces the post-trade balance-positivity invariant when the chain-parameter-gated "hardened" calculation path is used. In the default (legacy) path, the computed new pool balances are never checked to remain `>= 0`.

### Finding Description
`ExchangeCapsule.transaction()` computes new pool balances using either the legacy `ExchangeProcessor` (double-based bancor formula) or, when `allowHarden()` is true, the `SafeExchangeProcessor`/`StrictMathWrapper` overflow-checked path: [1](#0-0) 

The critical invariant check — that both `newFirstTokenBalance` and `newSecondTokenBalance` remain non-negative after the trade — is gated behind `hardenedCalc`: [2](#0-1) 

`hardenedCalc` is only `true` when `allowHarden()` (i.e., the `allowHardenExchangeCalculation` dynamic parameter) is enabled, which is controlled by a committee proposal and is disabled unless separately activated: [3](#0-2) [4](#0-3) 

In the default legacy path, `ExchangeProcessor.exchange()` uses `double`-precision bancor math with no invariant check on the resulting balances: [5](#0-4) 

The only invariant enforcement anywhere on the trade path in the default (non-hardened) configuration is `ExchangeTransactionActuator.doValidate()` checking that `firstTokenBalance` and `secondTokenBalance` are nonzero *before* the trade, and the resulting `anotherTokenQuant` meets `tokenExpected`: [6](#0-5) 

Neither `doValidate()` nor `execute()` re-checks that the *post-trade* pool balances remain positive when `hardenedCalc` is false — unlike DODOMath's missing `V0 >= V1 >= V2 > 0` check, this is a missing post-condition check on AMM state after the trade executes.

### Impact Explanation
Because the legacy path relies purely on `double` arithmetic (`exchangeToSupply`/`exchangeFromSupply` in `ExchangeProcessor.java`), floating-point rounding for extreme/edge-case balances and quantities (e.g., very large `sellTokenQuant` relative to `buyTokenBalance`) can, in principle, produce a `buyTokenQuant` computation whose subtraction from `buyTokenBalance` yields a negative or otherwise invariant-violating pool balance, since no `< 0` guard exists on this branch. If a negative or corrupted pool balance is ever persisted, subsequent trades against that exchange would operate on unbacked/incorrect state, potentially misrepresenting or permanently corrupting the AMM pool's balance and allowing incorrect token issuance/withdrawal accounting for `ExchangeStore`/`ExchangeV2Store` entries. This matches the audit's concern that missing invariant checks in bonding-curve math can lead to "incorrect token pricing" or "critical financial inaccuracies."

### Likelihood Explanation
Reachability is straightforward: any unprivileged account can broadcast an `ExchangeTransactionContract` via `ExchangeTransactionActuator`, hitting `ExchangeCapsule.transaction()` directly. The `tokenExpected` slippage check in `doValidate()` provides a caller-side minimum-output check, but that is a different check (transaction pricing threshold), not the invariant that pool reserves cannot go negative/invalid — the pool-invariant check exists only conditionally on `hardenedCalc`, which is off by default. Exploiting the floating-point edge case reliably requires crafting specific large balance/quantity combinations, which reduces (but does not eliminate) practical likelihood without deeper numerical analysis of `Maths.pow`/double precision behavior.

### Recommendation
Make the post-trade balance invariant check (`newFirstTokenBalance < 0 || newSecondTokenBalance < 0` and, more strictly, `newFirstTokenBalance > 0 && newSecondTokenBalance > 0`) unconditional in `ExchangeCapsule.transaction()`, regardless of `hardenedCalc`, mirroring the DODOMath recommendation to always enforce `V0 >= V1 >= V2 > 0`-style invariants on AMM state after every calculation, not only in the opt-in hardened path.

### Proof of Concept
Not independently reproducible from static review alone — reproducing a concrete floating-point edge case that drives `ExchangeProcessor.exchange()`'s legacy double-based bancor formula to yield a `buyTokenQuant` exceeding `buyTokenBalance` (or otherwise violating the reserve invariant) would require targeted numerical fuzzing of `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` in `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java` against various `(firstTokenBalance, secondTokenBalance, sellTokenQuant)` inputs; this was not verified with an executed test in this review, so likelihood is stated conservatively pending such analysis.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
