### Title
Legacy `ExchangeProcessor` bang-bond calculation can silently truncate/overflow into a negative or wrapped `long`, letting a caller drain an exchange pool with a single `ExchangeTransactionContract` when the harden-calculation proposal is not active - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
### Finding Description
The reported PoolTogether bug is that the `deposit` path checks the input-side cap (`maxDeposit`) but never checks the derived output (`shares`) against `maxMint`, so a pathological ratio (`_assetUnit`/`_exchangeRate`) can make the multiplication produce an out-of-bounds share count that is minted anyway.

The same "input is bounds-checked, but the *derived* output of an unsafe arithmetic formula is not" pattern exists in java-tron's legacy bancor-style exchange math. `ExchangeCapsule.transaction()` computes the counter-asset amount for a `ExchangeTransactionContract` via `Processor.exchange()` [1](#0-0) . When the `ALLOW_HARDEN_EXCHANGE_CALCULATION` proposal is not active (the default/legacy behaviour selected by `allowHarden()`), the calculation is delegated to the unguarded `ExchangeProcessor`, not the newer `SafeExchangeProcessor`: [2](#0-1) 

`ExchangeProcessor.exchangeToSupply` / `exchangeFromSupply` perform the bancor-relay math purely in `double` and then narrow the result with a raw `(long)` cast, with no overflow, no NaN/Infinity check, and no sign check: [3](#0-2) 

`ExchangeTransactionActuator.doValidate()` only checks that the *input* `tokenQuant` is positive and within `balanceLimit`, and that the *computed* `anotherTokenQuant` is `>= tokenExpected` (an analogue of a lower-bound/slippage check, not an upper-bound sanity check): [4](#0-3) 

Nothing bounds the *output* against the actual pool balance available for the opposite token (there is no `anotherTokenQuant <= tokenBalance` style check, analogous to a missing `maxMint` check on the derived quantity), nor is there a check that the `double`-based computation didn't lose precision/overflow into an unexpected value before it's persisted in `execute()`: [5](#0-4) 

Because `double` has only ~15-17 significant decimal digits of precision, and `Maths.pow` is invoked with a hardcoded exponent constant (`0.0005` / `2000.0`), for balances near `Long.MAX_VALUE` (achievable over time through `ExchangeInjectActuator`/`ExchangeWithdrawActuator` or accumulated trades) the multiplication/`pow` chain can produce results that silently truncate or become negative when narrowed to `long`, since Java's `(long) doubleValue` cast for out-of-range doubles clamps to `Long.MAX_VALUE`/`Long.MIN_VALUE` rather than throwing. Only the hardened path (`SafeExchangeProcessor`, gated behind a chain proposal) uses `BigDecimal` and `longValueExact()`, which throws `ArithmeticException` on overflow instead of silently returning a wrong value.

### Impact Explanation
If the legacy `ExchangeProcessor` path returns a corrupted (e.g. clamped or precision-truncated) `anotherTokenQuant`, `ExchangeTransactionActuator.execute()` will still credit that (wrong) amount to the caller via `addAssetAmountV2`/`setBalance` and persist the new pool balances via `Commons.putExchangeCapsule`. This can result in an account being credited with more asset units than the pool should be able to pay out (unbacked balance / theft from the exchange pool), or the pool balances becoming permanently corrupted (potential griefing/freezing of the pool for subsequent traders). This satisfies the "unbacked balance / theft of funds" impact bar.

### Likelihood Explanation
This path is reachable by any account that can broadcast an `ExchangeTransactionContract` (an ordinary trade against a v1/v2 Bancor-style exchange pair), i.e. no special privilege is required — only sufficient asset/TRX balance to trade and the exchange pool being in a state (e.g. via repeated large `ExchangeInject`/`ExchangeTransaction` calls) where its balances are large enough for the `double` math to lose precision or overflow. It is gated behind `allowHardenExchangeCalculation` being disabled (i.e. the legacy math path being active), which is the historical default before the hardening proposal is passed by SRs; it also requires accumulating balances into ranges where double-precision math breaks down, which is a multi-transaction but attacker-achievable precondition, not requiring any malicious node/witness/SR behavior.

### Recommendation
- Make the `SafeExchangeProcessor` (BigDecimal + `longValueExact`) the only computation path, or add symmetrical overflow/precision guards to `ExchangeProcessor` itself (reject non-finite/out-of-`long`-range doubles, reject negative computed quantities) instead of gating the fix behind a chain proposal.
- In `ExchangeTransactionActuator`, add an explicit sanity bound on the derived `anotherTokenQuant` (e.g., it must be strictly less than the current opposite-side pool balance and non-negative) before crediting the account, mirroring a "maxMint"-style upper-bound check on the derived output, not just the `tokenExpected` lower bound.

### Proof of Concept
1. Over multiple blocks, use `ExchangeCreateActuator`/`ExchangeInjectActuator` (or accumulated legitimate trading) to grow one side of an exchange pair's `firstTokenBalance`/`secondTokenBalance` toward the precision boundary of `double` (beyond `2^53`), while `allowHardenExchangeCalculation` remains disabled.
2. Broadcast an `ExchangeTransactionContract` with `quant` chosen so that `exchangeToSupply`/`exchangeFromSupply` in `ExchangeProcessor` (chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java:17-39) compute a `double` result outside representable `long` precision.
3. Because the cast `(long) issuedSupply` / `(long) exchangeBalance` silently narrows without an overflow/NaN check (unlike `SafeExchangeProcessor.exchangeFromSupply`'s `longValueExact()`), the returned `anotherTokenQuant` can be corrupted (e.g., unexpectedly large or negative) yet still satisfy `anotherTokenQuant >= tokenExpected` in `ExchangeTransactionActuator.doValidate()` (actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java:217-221), and is persisted via `execute()` (lines 61-99), crediting the caller's account.

Note: I was not able to fully verify, from the indexed code alone, an exact numeric combination of pool balances that provably clamps/overflows the `double`→`long` cast into an exploitable positive-excess value in this specific codebase snapshot (this would need runtime numerical experimentation, which is out of scope for static/index-based review) — flagging this as the main residual uncertainty. A Devin session with actual test execution would be needed to construct and confirm the precise triggering balances/quantities.

          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)

        .setFirstTokenBalance(newFirstTokenBalance)

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
