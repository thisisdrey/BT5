This confirms the check-then-act race in the anti-replay window. `Decrypt` in `connection_state.go` locks, calls `window.Check`, unlocks, then performs the AEAD decrypt (`dKey.DecryptDanger`) **without holding the lock**, and only afterward locks again to call `window.Update`. This is exactly the same bug class as the audit finding: a shared/global bit of state (the replay window's `current`/bitmap) is read once to make an accept/reject decision, but the actual "commit" of that decision (marking the counter as consumed) happens later, non-atomically, after other concurrent actors could have already relied on the same stale read — precisely mirroring the AURA bug's "compute against current global state, but consumption already happened via someone else's action" pattern, just applied to concurrent decrypt paths instead of concurrent withdrawals.

### Title
Non-atomic check-then-update in the anti-replay window allows a replayed packet to be decrypted and processed twice - (File: connection_state.go)

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` in `connection_state.go` split the anti-replay check into two separately-locked operations: `window.Check` (read) and `window.Update` (write/commit), with the AEAD decryption happening in between while unlocked. Two threads processing the same message counter concurrently can both pass `Check`, both successfully decrypt, and only one will lose to `Update`'s de-duplication — but by then the payload has already been handed off for processing on both paths in `readOutsidePackets`.

### Finding Description
`Bits.Check` and `Bits.Update` are two independent operations on the shared per-tunnel `window *Bits` state (also read by `strictlyWithinWindow`, which itself depends on the mutable `current` counter). [1](#0-0) 
The read (`Check`) is used purely to decide whether to proceed with the expensive decrypt; the actual "consumption" of the counter is deferred to `Update`, which runs after decryption completes, and each locks/unlocks independently rather than holding the lock across the whole Check→Decrypt→Update sequence. This is functionally identical to the AURA/CVX bug class described in the reference report: a decision (mint/pay reward, or here, "accept and process a packet") is computed off of a globally shared piece of state at one point in time, but that state's real consumption/finalization happens later and can be raced against another concurrent actor operating on the same stale read.

`readOutsidePackets` calls `Decrypt` and, on success, immediately continues to `handleHostRoaming`, `connectionManager.In`, and dispatches to `handleOutsideMessagePacket` (which writes to the tun device) before any global replay-window state guarantees the counter was uniquely claimed. [2](#0-1) 

Two goroutines (the interface uses multiple `tun.routines`/UDP reader routines by design) that receive duplicate UDP datagrams carrying the same message counter (a real replay, or an off-path attacker duplicating a captured ciphertext packet before the legitimate one is fully processed) can:
1. Both call `Decrypt` on the same messageCounter.
2. Both call `window.Check`, both observe "not yet seen" (since `Update` hasn't run for either yet), both return `true`.
3. Both proceed to `dKey.DecryptDanger`, which succeeds for both (AEAD decryption success doesn't depend on the replay window).
4. Both continue into packet processing (`handleOutsideMessagePacket` → firewall → tun write, or `handleOutsideRelayPacket` → forwarding) before either calls `Update`.
5. Only the loser of the race on `Update` is rejected — after the fact, i.e., too late to prevent the double processing.

The same non-atomic pattern applies to `VerifyRelay`, used on relay nodes to authenticate forwarded frames; a duplicated relay frame can race through `Check`/decrypt/`Update` the same way, resulting in the relay double-forwarding a captured frame to the target — the exact regression the `TestRelayReplayProtection` test in `e2e/tunnels_test.go` was written to catch for the *sequential* single-threaded case, but that test does not exercise concurrent delivery of the duplicate. [3](#0-2) 

### Impact Explanation
This is a traffic replay/forgery-adjacent bypass of the anti-replay mechanism: a passive or on-path attacker capable of duplicating captured ciphertext UDP datagrams to a Nebula host (no valid certificate required — this is purely a data-plane UDP replay against the existing tunnel) can cause the same application-layer packet to be decrypted and delivered to the tun device more than once, or, on a relay node, cause the same relay frame to be forwarded to the target more than once. This directly undermines the "reject duplicate/out-of-window packets" guarantee that the replay window (`Bits`) exists to provide, mirroring the "loss due to using stale shared state across a race between two concurrent actors" root cause in the referenced report.

### Likelihood Explanation
Exploitability requires only capturing one legitimate ciphertext UDP packet and re-injecting it to the target host quickly enough to race the original packet's processing before `window.Update` commits — no cryptographic material or trust is needed, matching the "no CA-signed certificate" reachability constraint. Nebula's UDP readers run in multiple routines/goroutines by default (`listen.batch`/`tun.routines`), which increases the odds of the racing decrypt paths executing concurrently.

### Recommendation
Hold a single lock (or otherwise make the operation atomic) across the entire "check → decrypt → mark seen" sequence in `ConnectionState.Decrypt` and `ConnectionState.VerifyRelay`, so that once a messageCounter passes the replay check, no other concurrent caller can also pass the check for the same counter until it is marked. Equivalently, fold `Check` and `Update` into one atomic "claim(i)" operation that must succeed before decryption is attempted, so a second concurrent claim for the same counter fails before it reaches the AEAD decrypt step, not after.

### Proof of Concept
1. Establish a normal Nebula tunnel between two hosts.
2. Capture one legitimate ciphertext message packet in flight (e.g., on-path capture, or a malicious relay/lighthouse-adjacent observer).
3. Immediately re-inject two (or more) copies of the identical captured UDP datagram to the receiving host's listener, delivered to different reader routines at close to the same time (feasible given `readOutsidePackets` is invoked per-routine off a shared UDP listener).
4. Observe that `ConnectionState.Decrypt`'s `window.Check(l, messageCounter)` call in `connection_state.go` can return `true` for both concurrent invocations before either has executed `window.Update`, since the two calls are separated by an unlocked AEAD decrypt. [1](#0-0) 
5. Both copies decrypt successfully and are handed to `handleOutsideMessagePacket`/tun write (or, for a relay, `handleOutsideRelayPacket`/forwarding) in `outside.go`, resulting in the duplicate being processed instead of dropped by the anti-replay window. [2](#0-1)
