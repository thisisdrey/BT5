### Title
`RewardsDistributor._calculateTokenIndex()` truncates `block.timestamp` to `uint32`, causing oversized reward accrual after `uint32` wraparound - (contracts/RewardsDistributor.sol)

### Summary
`RewardsDistributor` stores each reward token’s last update time in a `uint32` field, but calculates elapsed time as `uint256(block.timestamp) - uint256(storedTimestamp)` rather than using wrapping `uint32` arithmetic. After Unix timestamp `2**32`, the first update stores a truncated timestamp. The next update therefore calculates approximately `2**32` seconds of extra elapsed time, massively inflating the reward index and allowing an account with a qualifying token balance to claim the distributor’s available reward-token balance.

### Finding Description
`TokenState.timestamp` is defined as `uint32`, while the corresponding index is `uint224`. [1](#0-0) 

`_calculateTokenIndex()` calculates the delta against the truncated stored value:

```solidity
uint256 _deltaTimestamps = block.timestamp - uint256(_supplyState.timestamp);
```

It then writes `block.timestamp.toUint32()` back to storage. [2](#0-1) 

The transition works as follows:

1. Before the wrap, `timestamp` is close to `type(uint32).max`.
2. At or after `block.timestamp == 2**32`, `_updateTokenIndex()` stores only the lower 32 bits, normally a small value such as `0`.
3. On the next update, `_deltaTimestamps` becomes approximately `2**32 + currentOffset` instead of the real elapsed time.
4. `_tokensAccrued = _deltaTimestamps * _speed` is correspondingly inflated.
5. The inflated amount is added to the global reward index. [3](#0-2) 
6. `_calculateTokenDelta()` multiplies a user’s token balance by the inflated index delta and records the result in `tokensAccruedOf`. [4](#0-3) 
7. `claimRewards()` updates the index and account accrual, then transfers rewards up to the distributor’s token balance. [5](#0-4) 

The vulnerable state transition can be triggered through the permissionless `updateBeforeMintOrBurn()` entry point for any already-registered reward token and account. [6](#0-5) 

### Impact Explanation
An attacker holding a rewarded `DepositToken` or `DebtToken` balance can be the first caller after the wrapped timestamp is stored, then call `claimRewards()` and receive rewards for roughly 136 additional years. The transfer is capped only by the distributor’s current reward-token balance, so all available unclaimed rewards can be taken by the first successful claimant. [7](#0-6) 

This is theft of unclaimed yield. If the inflated index calculation exceeds `uint224`, `toUint224()` also causes reward-index updates and token operations that invoke them to revert, potentially freezing reward accounting and associated token operations until an upgrade. Deposit tokens call `updateBeforeMintOrBurn()` and `updateBeforeTransfer()` through their balance-change and transfer hooks. [8](#0-7) 

### Likelihood Explanation
The issue is deterministic after the Unix `uint32` timestamp boundary in 2106, but it cannot be triggered at current chain timestamps. No privileged attacker action is required once the boundary is reached: `updateBeforeMintOrBurn()` is public and `claimRewards()` is callable for the attacker’s own account. The impact requires the deployed pool to have a registered reward token with nonzero `tokenSpeeds`, nonzero token supply, and rewards held by the distributor.

The main mitigating factor is the far-future trigger condition and the protocol’s upgradeability window. The code nevertheless contains the same incorrect assumption as the referenced bug class: a timestamp truncated to `uint32` is later subtracted as though it were a full timestamp.

### Recommendation
Do not mix a wrapped `uint32` timestamp with an unwrapped `uint256` `block.timestamp`.

Either store the full timestamp:

```solidity
struct TokenState {
    uint224 index;
    uint64 timestamp;
}
```

and use:

```solidity
uint256 _deltaTimestamps = block.timestamp - uint256(_supplyState.timestamp);
_newTimestamp = block.timestamp.toUint64();
```

or, if `uint32` storage must be retained, consistently use wrapping `uint32` arithmetic:

```solidity
uint32 _currentTimestamp = block.timestamp.toUint32();
uint32 _deltaTimestamps;

unchecked {
    _deltaTimestamps = _currentTimestamp - _supplyState.timestamp;
}
```

The latter intentionally supports only intervals shorter than `2**32` seconds between updates. Storage-layout implications for the upgradeable contract must also be handled explicitly.

### Proof of Concept
A Foundry test can reproduce the accounting error by warping across `2**32`:

```solidity
function test_RewardsDistributorUint32Wrap() public {
    // Prerequisites:
    // - RewardsDistributor is registered in Pool.
    // - depositToken is registered for rewards.
    // - rewardToken balance exists in RewardsDistributor.
    // - tokenSpeeds[depositToken] > 0.
    // - attacker owns depositToken.

    uint256 wrapTimestamp = uint256(type(uint32).max) + 1;

    // Establish a pre-wrap checkpoint.
    vm.warp(wrapTimestamp - 1);
    rewardsDistributor.updateBeforeMintOrBurn(
        IERC20(address(depositToken)),
        attacker
    );

    // First post-wrap checkpoint stores timestamp == 0.
    vm.warp(wrapTimestamp);
    rewardsDistributor.updateBeforeMintOrBurn(
        IERC20(address(depositToken)),
        attacker
    );

    // Real elapsed time is one second, but the next delta is about 2**32 + 1.
    vm.warp(wrapTimestamp + 1);

    uint256 rewardBalanceBefore =
        rewardToken.balanceOf(address(rewardsDistributor));
    uint256 attackerBefore = rewardToken.balanceOf(attacker);

    vm.prank(attacker);
    rewardsDistributor.claimRewards(attacker);

    uint256 attackerAfter = rewardToken.balanceOf(attacker);

    assertGt(attackerAfter, attackerBefore);
    assertEq(attackerAfter - attackerBefore, rewardBalanceBefore);
}
```

For a lower-level demonstration, the essential assertion is:

```solidity
vm.warp(uint256(type(uint32).max) + 1);
(uint224 index1, uint32 timestamp1) = rewardsDistributor.tokenStates(token);
assertEq(timestamp1, 0);

vm.warp(uint256(type(uint32).max) + 2);
rewardsDistributor.updateBeforeMintOrBurn(token, attacker);

(uint224 index2, uint32 timestamp2) = rewardsDistributor.tokenStates(token);
assertEq(timestamp2, 1);
assertGt(index2, index1);
```

The inflated `index2 - index1` corresponds to approximately `2**32 + 1` seconds rather than one second.
