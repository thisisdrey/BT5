Audit Report

## Title
Premature `NoMoreChunks` `ensure!` blocks same-era unbond requests that would only merge into an existing chunk, not grow the array - (File: `substrate/frame/staking/src/pallet/impls.rs`, also `substrate/frame/staking-async/src/pallet/mod.rs`)

## Summary
`do_unbond` in `pallet-staking` and the `unbond` extrinsic in `pallet-staking-async` enforce `ledger.unlocking.len() < T::MaxUnlockingChunks::get()` unconditionally, before the code determines whether the new unbond value will merge into the existing last `unlocking` chunk (same target era, no growth) or must be pushed as a new chunk. Because the merge path does not increase `unlocking.len()`, a staker whose `unlocking` vector is already at `MaxUnlockingChunks` is wrongly rejected with `Error::NoMoreChunks` even when the new call would only merge into the last chunk and require no additional slot.

## Finding Description
In `substrate/frame/staking/src/pallet/impls.rs`, `do_unbond` first attempts an auto-withdraw of expired chunks only if `unlocking == MaxUnlockingChunks` [1](#0-0) , then unconditionally re-checks the bound via `ensure!(ledger.unlocking.len() < T::MaxUnlockingChunks::get() as usize, Error::<T>::NoMoreChunks)` [2](#0-1) . Only afterward does the code compute `era` and decide whether to merge into `ledger.unlocking.last_mut()` (when its `era` matches) or `try_push` a new chunk [3](#0-2) . The comment explicitly states that same-era unbonds are merged into the existing last chunk to "keep the chunk count down," confirming the merge path performs no growth, yet the `ensure!` at lines 1410-1413 fires purely on current `len()` without knowledge of whether a push is actually needed.

The identical pattern exists in `substrate/frame/staking-async/src/pallet/mod.rs`'s `unbond` extrinsic: the withdraw pre-step [4](#0-3) , the premature `ensure!` [5](#0-4) , and the later merge-or-push decision [6](#0-5) .

Since `try_push` already returns `Error::NoMoreChunks` when the bound is actually violated, the earlier `ensure!` is redundant for the push branch and actively harmful for the merge branch, since it rejects operations that would not grow the bounded vector at all.

## Impact Explanation
A staker with `MaxUnlockingChunks` live (non-withdrawable) unlocking chunks who issues another `unbond` call in the same era as their existing last chunk (i.e., an operation that would merge and not grow the vector) is incorrectly reverted with `NoMoreChunks`. This is a denial-of-service on the core, unprivileged `unbond` extrinsic reachable by any ordinary staker without governance, validator, or privileged access — matching the "runtime bugs that compromise intended behavior" impact category. It does not cause fund loss but does block a legitimate user action that the code's own design (the merge branch) proves should succeed.

## Likelihood Explanation
Reachable purely through normal public extrinsic use: a staker can unbond across `MaxUnlockingChunks` distinct eras (filling the bound) and then attempt a subsequent unbond within the same era as the last chunk while earlier chunks remain within `BondingDuration` (not yet withdrawable). No special privileges, relayer, or governance action is required, making this straightforward to trigger and repeat.

## Recommendation
Reorder the logic so the bound check only applies when a new chunk must actually be pushed: compute `era` and check `ledger.unlocking.last().filter(|c| c.era == era)` first; only in the `else` (push) branch, rely on `try_push`'s own `Error::NoMoreChunks` (or an explicit length check gating only that branch). Remove the premature unconditional `ensure!` before this decision in both `substrate/frame/staking/src/pallet/impls.rs::do_unbond` and `substrate/frame/staking-async/src/pallet/mod.rs::unbond`.

## Proof of Concept
1. Configure `MaxUnlockingChunks = 3`, `BondingDuration = 7`.
2. At eras 1, 2, 3, call `unbond` once per era, producing chunks at eras `8`, `9`, `10` (`unlocking.len() == 3 == MaxUnlockingChunks`).
3. Remain at active era 3 (do not roll to a new era) and call `unbond` again. The computed era for this call is `3 + 7 = 10`, matching the era of the existing last chunk.
4. Expected: since this merges into the existing last chunk (no vector growth), the call should succeed.
5. Actual: the `ensure!(ledger.unlocking.len() < T::MaxUnlockingChunks::get(), Error::<T>::NoMoreChunks)` at [2](#0-1)  fires first (`3 < 3` is false) and the call reverts with `NoMoreChunks`, despite no additional slot being required.
