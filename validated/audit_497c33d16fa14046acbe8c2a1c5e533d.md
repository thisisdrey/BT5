### Title
Unauthenticated relay-identity spoofing via attacker-controlled `RelayFromAddr` in `CreateRelayRequest` - (File: relay_manager.go)

### Summary
`relayManager.handleCreateRelayRequest` accepts a `RelayFromAddr` field from an inbound `NebulaControl_CreateRelayRequest` message and uses it directly as the identity of the "original requester" of the relay, without ever verifying that this claimed identity actually corresponds to a real peer that consented to (or even knows about) the relay. This mirrors the reported bug class: an authenticated-but-unrelated party can unilaterally push state that is nominally "on behalf of" a victim identity, keyed only by an attacker-supplied field that superficially resembles a legitimate identity check, without any proof of consent from that identity.

### Finding Description
When a control message of type `NebulaControl_CreateRelayRequest` arrives from an authenticated peer `h`, `HandleControlMsg` unmarshals attacker-supplied `RelayFromAddr`/`RelayToAddr` fields (or their v1 equivalents) with only a nil-check [1](#0-0) , then dispatches to `handleCreateRelayRequest`.

Inside `handleCreateRelayRequest`, the `from` address is taken verbatim from the attacker-supplied `m.RelayFromAddr` field: `from := protoAddrToNetAddr(m.RelayFromAddr)` [2](#0-1) . The only checks performed are that `from` is not one of my own addresses, and that `target` (the relay destination) is me: [3](#0-2) 

If `target` is me, and no existing relay state exists for `from`, the code immediately installs an **Established** Terminal relay keyed by the attacker-chosen `from` value, with no verification that `from` corresponds to any certificate, that `h` (the actual, cert-authenticated sender) is authorized to speak for that address, or that the claimed party ever requested a relay: [4](#0-3) 

Contrast this with `handleHostUpdateNotification` in `lighthouse.go`, which explicitly guards against exactly this style of spoofing by checking the claimed identity against the certificate-derived `fromVpnAddrs` of the actual sender: `if detailsVpnAddr.IsValid() && !slices.Contains(fromVpnAddrs, detailsVpnAddr) { ... return }` [5](#0-4) . No equivalent check exists in `handleCreateRelayRequest` for the `from` field against `h.vpnAddrs` (the actual, certificate-verified identity of the sender `h`).

This is the direct analog of the "receiver == holder" flaw: just as the vault contract treated an attacker-chosen `receiver` field matching `holder` as implicit proof of consent, `handleCreateRelayRequest` treats an attacker-chosen `RelayFromAddr` field as if it were an authenticated claim about a third party's intent, with no cryptographic binding to that party's certificate.

### Impact Explanation
Any single authenticated Nebula peer `h` (no special privilege beyond a valid, CA-signed certificate for itself) can:
- Fabricate `CreateRelayRequest` messages naming arbitrary `RelayFromAddr` values — including the VPN addresses of other real, legitimate peers on the mesh, whether they exist or not — causing the victim node to allocate and mark **Established** relay/hostmap state (`AddRelay(..., TerminalType, Established)`) on behalf of that fabricated identity [4](#0-3) .
- Repeatedly do this with many distinct fabricated `from` addresses to poison the hostmap/relay tables (`hm.Relays`, `relayState`) and consume victim resources — a remote state-poisoning / resource-exhaustion vector reachable by any authenticated peer without the consent of the impersonated identity.
- Force the victim to send a `CreateRelayResponse` back referencing this bogus relay state [6](#0-5) , wasting network and CPU resources and expanding the amount of live (unverified) relay bookkeeping tied to identities that never asked for it.

Because the tunnel to the actual final endpoint is still separately authenticated via its own Noise handshake and AEAD, this does not appear to grant full traffic decryption or a session hijack by itself; however, it is a genuine authorization gap — a third party can push relay state associated with an unconsenting victim's identity purely by asserting it in an unauthenticated field, exactly the "anyone can push state onto a holder who never agreed" pattern described in the report.

### Likelihood Explanation
High likelihood of exploitability by anyone who is a valid mesh member: no additional trust, lighthouse role, or special certificate attributes are required — only a normal peer certificate and the ability to send a `Control`-type Nebula packet to the intended relay-target node, which is a standard capability of any connected peer, per `readOutsidePackets`'s dispatch of `header.Control` to `f.relayManager.HandleControlMsg(hostinfo, out, f)` [7](#0-6) .

### Recommendation
In `handleCreateRelayRequest`, do not trust `m.RelayFromAddr` as an unauthenticated identity claim when the sending peer `h` is not the one being represented. At minimum:
- Require that `from` equal one of `h.vpnAddrs` (the actual certificate-verified identity of the sender) for the case where `h` itself is initiating a relay to me, **or**
- If `h` is genuinely acting as a relay for a third party, only accept the relay/forwarding assertion once the claimed party's own certificate/handshake corroborates it (as is done for `handleHostUpdateNotification`'s `detailsVpnAddr` vs `fromVpnAddrs` check) rather than trusting the bare protobuf field.
- Rate-limit/bound the number of distinct `from` identities any single peer `h` may register relay state for, to blunt state-poisoning/resource-exhaustion attempts even after the identity check is added.

### Proof of Concept
1. Attacker `E` establishes a normal, valid Nebula tunnel to victim `V` (any CA-signed cert works — no special role needed).
2. `E` sends a `Control` packet to `V` containing a `NebulaControl_CreateRelayRequest` with:
   - `RelayFromAddr` = the VPN address of an arbitrary third party `X` (a real peer `E` has never spoken for, or even a currently-unconnected address).
   - `RelayToAddr` = `V`'s own VPN address (so the "target is me" branch is taken).
3. `V`, per `handleCreateRelayRequest`, finds `f.myVpnAddrsTable.Contains(target)` true, finds no existing relay state for `from` = `X`, and calls `AddRelay(rm.l, h /* = E's HostInfo */, f.hostMap, X, &m.InitiatorRelayIndex, TerminalType, Established)` [4](#0-3) , then sends `E` a `CreateRelayResponse` confirming the bogus relay.
4. `V` now carries `Established` relay/hostmap state tied to `X`'s identity that `X` never requested and that was solely asserted by `E`. Repeating this with many distinct `from` values lets `E` inflate `V`'s relay/hostmap bookkeeping at will.

Note: full end-to-end demonstration of downstream consequences (e.g., precisely how much resource growth this enables, or whether any secondary code path further trusts this `PeerAddr` as an authenticated identity for firewall/ACL decisions) was not exhaustively traced within the indexed subset of `hostmap.go`'s `RelayState` methods; a Devin session with full repository access would be needed to confirm the complete blast radius of the poisoned relay entries.
