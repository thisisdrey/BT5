### Title
Cross-chain `SetAssetClaimer`/trapped-asset claimer bound to a foreign-chain beneficiary makes failed transfers permanently unclaimable - (File: `polkadot/xcm/xcm-executor/src/lib.rs`)

### Summary
The Maia bug's core invariant break is: a "refund" identity for a failed operation is set to the recipient/beneficiary address as it exists on a *different* chain, instead of an identity that is actually controllable/resolvable on the chain where the failure and refund bookkeeping occur. The local analog is the XCM asset-trap/claimer mechanism used throughout the SDK (and explicitly by the Snowbridge v2 message flow), where `asset_claimer` can be set to a beneficiary `Location` describing an account on the *final destination* chain, while the assets may actually get trapped on an *intermediate* chain (e.g. Bridge Hub or Asset Hub) whose `OriginConverter`/signed-origin machinery cannot reproduce that exact multi-hop `Location`.

### Finding Description
In `polkadot/xcm/xcm-executor/src/lib.rs`, `post_process()` decides who can later reclaim trapped holding-register assets: [1](#0-0) 

The claimer used to key the trapped assets is `self.asset_claimer` if set (via the `SetAssetClaimer` instruction), falling back to context/original origin. `SetAssetClaimer` lets a message explicitly set an arbitrary `Location` as the claimer, and the Snowbridge v2 flow does exactly this by deriving the claimer from the **beneficiary on the final destination chain**, as documented:

```
SetAssetClaimer Kilt/Bob       // derived from beneficiary on final destination
AliasOrigin Ethereum/Alice     // derived from msg.sender
InitiateAssetsTransfer asset=(KLT, 100) remoteFee=(WETH, 1) dest=KLT
  DepositAsset (KLT, 100) beneficiary=Bob
```

This message is built and dispatched from Bridge Hub (BH) targeting Asset Hub (AH)/onward to KILT. If execution fails partway — e.g. the `InitiateAssetsTransfer` hop fails on BH itself, or on AH before forwarding to KILT — the leftover holding assets are trapped **on that intermediate chain**, keyed by claimer `Kilt/Bob` (a multi-hop `Location` under `GlobalConsensus(Kilt)`).

To reclaim trapped assets, a user must call `pallet_xcm::claim_assets`, which is a signed extrinsic executed *locally* on the chain holding the trap. The signed origin gets converted to a `Location` via that chain's own origin-conversion machinery (typically producing `AccountId32 { network: None/Local, id }` for a plain signed account on that specific chain). That locally-derived `Location` will never equal the trap's claimer key `[GlobalConsensus(Kilt), Parachain(..), AccountId32 { network: Some(Kilt), id: Bob }]`, because:
1. The claimer is anchored to a foreign consensus system (`Kilt`) relative to the chain doing the trapping (BH or AH), and
2. There is no signed-origin path on BH/AH that can present itself as literally originating "from Kilt" to satisfy that claimer check (unlike a genuine incoming XCM from Kilt, which is not something the affected user can locally trigger via `claim_assets`).

This exactly mirrors the Maia `MulticallRootRouter`/`RootBridgeAgent` bug: the refund/claim identity is bound to an address/location meaningful on the counterparty chain, not one resolvable/controllable on the chain that actually needs to authorize the refund.

### Impact Explanation
If any leg of a multi-hop transfer fails after `SetAssetClaimer` has bound the claimer to a beneficiary Location on a chain other than the one performing the trap, the trapped funds become **permanently unclaimable** by the legitimate beneficiary, since `claim_assets` on the trapping chain can never produce a matching origin `Location`. This is a direct "permanent user-fund lock" impact under the Polkadot SDK Impact Gate (bridge/message value gets stuck with no recovery path), analogous in class and severity to the original Maia H-03 finding.

### Likelihood Explanation
This requires no malicious relayer, governance, or privileged actor — it is a normal, unprivileged multi-hop XCM transfer failure (e.g., insufficient remote fees, filtered asset, weight limit exceeded on an intermediate hop) combined with the documented pattern of setting `SetAssetClaimer` from the final-hop beneficiary rather than a hop-local identity. Since Snowbridge v2 and general multi-hop `InitiateTransfer`/`SetAssetClaimer` XCM programs are user-composable (via `pallet_xcm::execute` or via inbound bridge messages), any user or relayer constructing (or receiving) such a message can trigger the failure condition without any special privilege.

### Recommendation
- Do not bind `asset_claimer` to a `Location` anchored in a different consensus system than the chain that may end up performing the trap; instead set/refresh the claimer per-hop to an identity resolvable via that hop's own `OriginConverter` (e.g., the sovereign/derived account of the beneficiary on that specific chain), or
- Ensure `claim_assets`'s origin-matching logic can accept proof of foreign-chain identity (e.g., via a bridged/verified origin) so that the documented cross-chain claimer semantics are actually satisfiable, and
- Add explicit tests that a failure occurring at each intermediate hop of a `SetAssetClaimer`-annotated multi-hop transfer results in assets that are demonstrably reclaimable by the intended party on that specific hop.

### Proof of Concept
1. From Ethereum (or any origin capable of building the documented Snowbridge v2 program), submit an inbound message that becomes, on Bridge Hub: `SetAssetClaimer Kilt/Bob; AliasOrigin Ethereum/Alice; InitiateAssetsTransfer ... dest=KILT ... DepositAsset(beneficiary=Bob)`.
2. Cause the `InitiateAssetsTransfer` (or a later hop's execution before final deposit) to fail — e.g., by under-funding `remoteFee`, so `Config::AssetTrap::drop_assets(claimer=Kilt/Bob, holding, ctx)` is invoked on Bridge Hub per `polkadot/xcm/xcm-executor/src/lib.rs` lines 415-421.
3. On Bridge Hub, attempt `pallet_xcm::claim_assets` as any signed account, including one controlled by "Bob" locally — the origin conversion on Bridge Hub cannot produce the exact `[GlobalConsensus(Kilt), Parachain(..), AccountId32{Bob}]` claimer key, so the claim fails and the trapped WETH/KLT assets remain locked forever on Bridge Hub.
