## Title
Unsynchronized static `programPrecompileLRUMap` cache in TVM `Program` allows JUMPDEST-analysis cache poisoning across concurrent constant-call executions - (File: `actuator/src/main/java/org/tron/core/vm/program/Program.java`)

### Summary
`Program.getProgramPrecompile()` uses a `static final LRUMap<Key, ProgramPrecompile> programPrecompileLRUMap` shared across all `Program` instances for the JVM lifetime, keyed by a jump-destination analysis cache key derived from the contract's bytecode. `LRUMap` (Apache Commons Collections) is not thread-safe and provides no external synchronization here. `TriggerConstantContractServlet`/`Wallet.triggerConstantContract` and the analogous gRPC/JSON-RPC "call"/"estimateEnergy" paths run TVM execution for arbitrary, unprivileged, read-only contract-call requests, and these can be dispatched concurrently by the HTTP/gRPC server on multiple worker threads, each constructing its own `Program`/bytecode context but sharing the same static map.

### Finding Description
`getProgramPrecompile()` (`actuator/src/main/java/org/tron/core/vm/program/Program.java:208-225`) performs a classic check-then-act sequence on the shared, non-thread-safe `LRUMap`:
```
if (programPrecompileLRUMap.containsKey(key)) {
  programPrecompile = programPrecompileLRUMap.get(key);
} else {
  programPrecompile = ProgramPrecompile.compile(ops);
  programPrecompileLRUMap.put(key, programPrecompile);
}
```
This mirrors the class of bug described in the Linux `huge_zero_pfn` race: a fast-path read/write on a shared cache object that is mutated by concurrent operations (here, LRU eviction and `put()` calls from other threads executing different contracts) without any lock guarding the whole read-modify-write sequence. `LRUMap` internally maintains a hash-linked structure that is mutated on both `get()` (updates recency order) and `put()` (may evict entries and rewire internal links); calling these concurrently from multiple threads without synchronization can corrupt the internal linked-list/bucket structure, causing `get()` to return a `ProgramPrecompile` object associated with a different cache `key` (i.e., a different contract's compiled JUMPDEST set), or throw an unexpected exception (e.g., NPE / infinite loop) during structure traversal.

This cache is reachable via `getProgramPrecompile()` from the constant-call path (`isConstantCall()` bypasses it and always recompiles, but non-constant/estimate paths route through the shared map), which is driven by transaction execution and, more importantly, by the HTTP/gRPC "trigger constant contract" and "estimate energy" query endpoints (`Wallet.triggerConstantContract`, `Wallet.estimateEnergy`, `TronJsonRpcImpl`) — endpoints that any anonymous API client can invoke concurrently with arbitrary bytecode/address combinations. Because `Wallet.triggerConstantContract` and `estimateEnergy` execute TVM code in separate `Runtime`/`Program` instances per request (typically on servlet/gRPC executor threads), many concurrent invocations against different contracts can race on this single static map.

### Impact Explanation
If a race corrupts the map such that a `Program` for contract A receives the compiled `ProgramPrecompile` (JUMPDEST set) of a different contract B, `hasJumpDest(pc)` will validate/invalidate jump destinations against the wrong bytecode. This can cause a `JUMPDEST` check to spuriously pass for an offset that is not actually a valid jump target in the executing bytecode, allowing a `JUMP`/`JUMPI` to redirect control flow into the middle of PUSH-data or otherwise unintended code, corrupting the VM's opcode decoding for that call. Practically, this can produce inconsistent/incorrect execution results for constant calls (`eth_call`/`triggerconstantcontract`), potentially returning fabricated results to a caller, or lead to VM-internal exceptions/`OutOfBoundsException` mid-execution that could destabilize the query-serving thread pool (denial of service on the read API). Corruption of the shared `LRUMap`'s internal structure could also throw unexpected runtime exceptions that are not caught by the narrow `catch` blocks around VM execution, risking uncaught exceptions on request-handling threads.

### Likelihood Explanation
Likelihood is moderate: it requires genuine thread-level concurrency of `triggerConstantContract`/`estimateEnergy` calls against different contracts hitting the non-constant-call code path of `getProgramPrecompile()`, and depends on internal `LRUMap` mutation timing to actually manifest as returned-wrong-object or structural corruption rather than a benign race. No authentication or privileged access is required — any external API caller can trigger `TriggerConstantContractServlet`, `Wallet.triggerConstantContract`, or `TronJsonRpcImpl` concurrently.

### Recommendation
Wrap access to `programPrecompileLRUMap` (both the check-then-act sequence and `get`/`put`) in a `synchronized` block, or replace the `LRUMap` with a thread-safe cache implementation (e.g., Guava `Cache` with `maximumSize`, as already used elsewhere in the codebase, e.g. `TronCache`/`EffectiveCheckService`). Ensure the compiled `ProgramPrecompile` object returned is always consistent with the correct bytecode `key`, mirroring the java-tron style already used for `EventPluginLoader.getInstance()` double-checked locking pattern.

### Proof of Concept
A concrete, reliable single-request PoC cannot be constructed without instrumenting `LRUMap` internals or forcing precise thread interleaving, since this is a timing-dependent data race in a third-party collection under concurrent unsynchronized access. Conceptually: issue many concurrent `wallet/triggerconstantcontract` (or `eth_call`) requests against distinct smart contracts with differing bytecode/JUMPDEST layouts from multiple threads, so that `getProgramPrecompile()` is invoked for different `Key`s at high frequency, forcing concurrent `get()`/`put()`/eviction on the shared `programPrecompileLRUMap`; under sufficient contention, some calls should intermittently execute with the wrong contract's JUMPDEST set or throw a spurious exception. This was not empirically reproduced against the running node from this analysis and would need to be validated in a live/test environment.
