Audit Report

## Title
Value sent to stateless built-in precompiles (ECRecover, Sha256, Identity, Modexp, Bn128*, Blake2F) is permanently locked - (File: `substrate/frame/revive/src/exec.rs`)

## Summary
`Stack::run`/`new_frame` in `substrate/frame/revive/src/exec.rs` unconditionally transfers `frame.value_transferred` to the destination account before dispatching the call, regardless of whether the destination is a real contract, an EOA, or a stateless built-in precompile. Built-in precompiles with `HAS_CONTRACT_INFO = false` (ECRecover, Sha256, Ripemd160, Identity, Modexp, Bn128Add/Mul/Pairing, Blake2F) only implement `Precompile::call` to perform pure cryptographic computation and never reference, forward, or refund the transferred value, so value routed to their fixed addresses becomes permanently unspendable.

## Finding Description
The transfer occurs unconditionally in the non-delegate branch of the call/instantiate flow: [1](#0-0) . The only conditional logic that treats precompiles specially is account/consumer bookkeeping gated on `has_contract_info()`, which is unrelated to whether the value transfer itself happens: [2](#0-1) . The `Precompile::call` entry point used by `HAS_CONTRACT_INFO = false` precompiles has no parameter or facility to read or move the transferred value: [3](#0-2) . The trait documentation itself confirms that when `HAS_CONTRACT_INFO` is false, "No account or any other state will be created for the address," meaning there is no account/storage mechanism through which value could later be reclaimed by that precompile: [4](#0-3) . Contrast this with the deliberate mitigation used for the not-yet-implemented `PointEval` precompile, which rejects the call outright rather than accepting a silent balance transfer, confirming the team recognizes this exact risk pattern but has not applied the fix to already-shipped stateless precompiles.

## Impact Explanation
This matches the "permanent user-fund lock" impact category. An unprivileged account can send native value via `call{value: ...}` (or the pallet-revive `call` extrinsic / EVM `CALL` opcode) to any of the fixed, code-less precompile addresses (`0x1`–`0x9`), and that value is transferred into the destination account with no code path, extrinsic, or governance mechanism in the pallet capable of retrieving it. The exact corrupted/stranded value is the native balance credited to the precompile's account (e.g., `Identity` at `0x...0004`).

## Likelihood Explanation
No privileged actor, governance action, or compromised party is required. Reachability is high because addresses `0x1`–`0x9` are the same well-known low addresses used across EVM-compatible chains, making accidental sends (fat-fingered addresses, buggy clients, or contracts blindly forwarding `msg.value` to a computed address that collides with a reserved address) plausible and repeatable through ordinary use of the public `call` entrypoint.

## Recommendation
Apply the same guard used for `PointEval` uniformly to all `HAS_CONTRACT_INFO = false` built-in precompiles: reject the call (return an error) whenever `frame.value_transferred` is non-zero and the destination is a stateless precompile with no logic to account for that value, before performing the `transfer_from_origin` step. Alternatively, restructure `Stack::run`/`new_frame` so the value transfer is deferred until it's established that the destination can meaningfully receive it (i.e., a contract, EOA, or a precompile explicitly documented to accept value).

## Proof of Concept
1. Fund an account/contract with native balance.
2. Issue a `pallet-revive` `call` extrinsic (or EVM `CALL`) targeting address `0x0000...0004` (`Identity` precompile) with non-zero `value` and arbitrary input data.
3. Observe, consistent with the existing test assertions in `substrate/frame/revive/src/tests/pvm.rs` (`pure_precompile_works`), that `Pallet::<Test>::evm_balance(&precompile_addr)` reflects the transferred amount after the call completes.
4. Confirm there is no subsequent call, extrinsic, or governance action in the codebase capable of moving that balance out of the precompile's account, i.e., the funds are permanently locked.
