### Title
Group-Level Rate Limiter Can Be Bypassed via Read-Only, Deferred-Settlement Check - (File: `programs/marginfi/src/utils/general.rs`)

### Summary
The group-level USD outflow rate limiter — a protocol safety control meant to cap withdraw/borrow outflow during oracle failures or exploits — is checked read-only on every unprivileged user withdraw/borrow, but the counter it checks against (`group.rate_limiter.hourly`/`daily.cur_window_outflow`) is only mutated later by a privileged off-chain worker calling `update_group_rate_limiter`, on a ~10 minute cadence (`MAX_RATE_LIMIT_UPDATE_LAG_SLOTS = 1_500` slots). Any unprivileged user can perform repeated withdraws/borrows within this settlement lag window, each individually checked against the stale, not-yet-updated counter, allowing cumulative outflow far in excess of the configured cap before the state catches up.

### Finding Description
`record_withdrawal_outflow` at [1](#0-0)  validates the projected outflow against `group.rate_limiter.hourly/daily.effective_remaining_capacity(...)` but never calls `try_record_outflow` on the group struct — it only emits a `RateLimitFlowEvent` for later off-chain aggregation. The `MarginfiGroup` account itself is not passed as mutable in the calling instructions (`lending_account_withdraw`, `lending_account_borrow`, and the kamino/juplend/drift/solend withdraws), by design, per [2](#0-1) : "The group rate limiter is only checked read-only... This avoids serializing all activity in a group through one writable group account."

The actual mutation of `cur_window_outflow` only happens when the `delegate_flow_admin` calls `update_group_rate_limiter`, shown at [3](#0-2) , gated by `MAX_RATE_LIMIT_UPDATE_LAG_SLOTS = 1_500` (~10 minutes) at [4](#0-3) .

This is the exact same bug class as the CIF report: the check (`effective_remaining_capacity`) is performed against state that lags the real, already-executed flow, because updating that state is decoupled into a separate transaction driven by an off-chain/admin process. Just as `publishAttestation()` and `setCashInFlight()` are not atomic, `lending_account_withdraw`/`borrow` and `update_group_rate_limiter` are not atomic, and the gap between them is directly exploitable by an ordinary user, since withdraw/borrow are unprivileged actions.

The project's own test confirms the read-only, unmutated nature of the counter during the gap: [5](#0-4)  — after 4 user actions accumulate 6 USD of outflow, `groupBeforeAdmin.rateLimiter.hourly.curWindowOutflow` is asserted to still equal `0`, i.e., group capacity is not consumed until the admin settles it.

### Impact Explanation
The group rate limiter exists specifically as "protocol safety" against "catastrophic outflows during oracle failures or exploits" (per the project README). Because the on-chain counter lags real activity by up to ~1500 slots (~10 minutes) — and in practice by however long the off-chain worker actually takes to run — any unprivileged user (or colluding set of users/bots) can submit many withdraw/borrow transactions in rapid succession, each one passing the read-only check against the same stale `cur_window_outflow`, and drain USD-denominated outflow far beyond the configured hourly/daily cap. This directly defeats the safety control the protocol relies on to bound outflow during incident response, which is precisely the scenario (oracle manipulation / exploit in progress) where the cap is most needed. This does not by itself create insolvency, but it nullifies a specifically-designed circuit breaker meant to bound damage from other categories of attack (e.g., stale/manipulated oracle price attacks), amplifying their blast radius.

### Likelihood Explanation
High under the intended threat model: the guide itself documents this as the standard flow ("checked read-only... settled later"), and the settlement window is bounded only by an off-chain, non-atomic process (`MAX_RATE_LIMIT_UPDATE_LAG_SLOTS` merely caps how stale an *accepted* update batch may be — it does not bound how often the worker actually runs, and nothing prevents a burst of transactions immediately after the group is deployed/updated or during periods of off-chain worker downtime). No special privilege is required — a plain user calling `lending_account_withdraw`/`lending_account_borrow` repeatedly can trigger this.

### Recommendation
As acknowledged conceptually in the original report, this class of lag is hard to eliminate entirely without giving up the design goal (avoiding a globally-serializing writable group account). Mitigations to consider:
- Track a short-lived, in-memory-only per-slot/per-transaction cap in addition to the lagging group counter, or require the group account to be included (even if not the counter-of-record) so a tighter secondary bound can be enforced synchronously.
- Reduce `MAX_RATE_LIMIT_UPDATE_LAG_SLOTS` and/or require the off-chain worker to run far more frequently, with alerting if it falls behind.
- Consider a hard per-instruction/per-account outflow ceiling that is enforced synchronously (e.g., via the bank-level limiter, which is already updated inline) as a backstop independent of the group-level lagging counter.

### Proof of Concept
1. Admin configures `group.rate_limiter.hourly.max_outflow = X` USD via `configure_group_rate_limits`.
2. Within a single settlement window (before `delegate_flow_admin` calls `update_group_rate_limiter`), an unprivileged user repeatedly calls `lending_account_withdraw` (or `lending_account_borrow`) for amounts up to just under `X` each time.
3. Each call independently passes `record_withdrawal_outflow`'s read-only check at [6](#0-5) , because `group.rate_limiter.hourly.cur_window_outflow` has not yet been incremented by any prior call in the same window (mirroring the assertion in [7](#0-6) ).
4. Cumulative outflow across N such calls reaches `N * X` USD, far exceeding the intended single-window cap of `X`, before the off-chain worker aggregates events and calls `update_group_rate_limiter` to finally apply the deferred deduction.

```rust
pub fn update_group_rate_limiter(
    ctx: Context<UpdateGroupRateLimiter>,
    outflow_usd: Option<u64>,
    inflow_usd: Option<u64>,
    update_seq: u64,
    event_start_slot: u64,
    event_end_slot: u64,
) -> MarginfiResult {
    let mut group = ctx.accounts.marginfi_group.load_mut()?;
    let clock = Clock::get()?;

    check!(
        outflow_usd.is_some() || inflow_usd.is_some(),
        MarginfiError::GroupRateLimiterUpdateEmpty
    );
    validate_event_slots(
        event_start_slot,
        event_end_slot,
        group.rate_limiter_last_admin_update_slot,
    )?;
    check!(
        event_end_slot <= clock.slot,
        MarginfiError::GroupRateLimiterUpdateFutureSlot
    );
    check!(
        clock.slot.saturating_sub(event_end_slot) <= MAX_RATE_LIMIT_UPDATE_LAG_SLOTS,
        MarginfiError::GroupRateLimiterUpdateStale
    );
    check!(
        update_seq == group.rate_limiter_last_admin_update_seq.saturating_add(1),
        MarginfiError::GroupRateLimiterUpdateOutOfOrderSeq
    );

    if let Some(inflow) = inflow_usd {
        check!(
            is_valid_rate_limit_amount(inflow),
            MarginfiError::InvalidConfig
        );
        group
            .rate_limiter
            .record_inflow(inflow, clock.unix_timestamp);
        msg!("Group rate limiter inflow recorded: {} USD", inflow);
    }

    if let Some(outflow) = outflow_usd {
        group
            .rate_limiter
            .try_record_outflow(outflow, clock.unix_timestamp)?;
        msg!("Group rate limiter outflow recorded: {} USD", outflow);
    }

    group.rate_limiter_last_admin_update_slot = event_end_slot;
    group.rate_limiter_last_admin_update_seq = update_seq;

    Ok(())
}
```
