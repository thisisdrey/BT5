## Finding: Unbounded array allocation from unchecked length field in TVM precompiled-contract ABI decoding helpers

### Title
Unbounded memory allocation via unchecked length word in precompiled-contract array decoders - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
Several private ABI-decoding helpers used by TVM precompiled contracts allocate Java arrays whose size is taken directly from an attacker-controlled 256-bit word in the call data, with no upper bound or sanity check before the allocation.

### Finding Description
`extractBytes32Array`, `extractBytesArray`, and `extractSigArray` in `PrecompiledContracts.java` each read a length value straight out of the decoded call data and immediately size a Java array with it: [1](#0-0) [2](#0-1) [3](#0-2) 

In each function, `len = words[offset].intValueSafe()` is attacker-supplied (it comes from the `DataWord` array decoded from the precompile's raw input) and is used to allocate `new byte[len][]` (or similarly sized arrays) before any bound is checked against the actual size of `data`/`words`. This is structurally the same bug class as CVE-2017-9473 in `ytnef`: a crafted length field taken from untrusted input drives allocation size with no cap, letting a caller force the JVM to attempt allocating an enormous array (up to `Integer.MAX_VALUE` elements, since `intValueSafe()` clamps to `Integer.MAX_VALUE` rather than rejecting oversized values), producing an immediate `OutOfMemoryError` / large GC pressure while executing inside the block/transaction-processing thread.

Because these are private static helpers inside the same file used for decoding precompiled-contract call data (Tron's equivalent of Solidity ABI-decoded dynamic arrays for a native precompile), reaching them only requires that some enabled precompiled contract that uses them be invoked — i.e. any account able to deploy or call a smart contract that issues a `CALL`/`STATICCALL` to that precompile address with crafted `data`.

### Impact Explanation
An attacker-controlled length word driving array allocation with no bound check can cause the executing node to attempt to allocate memory far beyond what is needed for legitimate input, resulting in `OutOfMemoryError` during transaction/block execution. If this occurs during block application in `Manager` rather than a purely local constant call, it can crash or destabilize the node processing that block, which is a denial-of-service against the chain's ability to serve/execute transactions — matching the accepted impact category "node crash or halt" / "an API the node can no longer serve."

### Likelihood Explanation
The precompiled contracts that use `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` are reachable by any account capable of calling a deployed contract with `CALL` to the corresponding precompile address, i.e. any unprivileged transaction broadcaster or contract deployer. No special privilege, stake, or witness role is required — only a crafted `data` payload with an artificially large length word at the expected offset.

### Recommendation
Add an explicit upper bound check on `len` (e.g., cap it against the number of remaining `words`/bytes actually available in `data`, and reject if `len` exceeds a small sane maximum) in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` before allocating any array, mirroring the bounds checks already present elsewhere in the same file (e.g., the `spendCount`/`receiveCount` range checks at lines 1496-1499 of the same file) rather than relying on `intValueSafe()` clamping alone.

### Proof of Concept
Craft call data to the affected precompiled contract's expected ABI layout such that the length word read at `words[offset]` (used by `extractBytes32Array`/`extractBytesArray`/`extractSigArray`) is set to a very large value (e.g., `0x7fffffff`). Deploy a trivial contract that forwards this data via `CALL`/`STATICCALL` to the precompile address and broadcast a transaction invoking it; the node attempts `new byte[len][...]`, driving excessive memory allocation/`OutOfMemoryError` during execution.

**Caveat:** I was unable to enumerate, within the available tool budget, exactly which precompiled-contract `execute()` method(s) call these three helpers (a `grep_search` for the call sites returned only the file itself without surrounding call context before the session ended), so the specific precompile address/contract type that exercises this path is not fully confirmed. If a Devin session with full repo access is available, the exact caller(s) of `extractBytes32Array`/`extractBytesArray`/`extractSigArray` should be located to confirm end-to-end reachability from a broadcastable transaction.
