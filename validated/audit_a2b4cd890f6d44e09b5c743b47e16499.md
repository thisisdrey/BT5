### Title
Front-runnable "Token exists" check permanently blocks legitimate TRC10 asset issuance - (File: actuator/src/main/java/org/tron/core/actuator/AssetIssueActuator.java)

### Summary
`AssetIssueActuator.validate()` rejects a TRC10 asset-creation transaction if an asset with the same name already exists in `AssetIssueStore`, and `execute()` writes the asset keyed only by its name (when `AllowSameTokenName == 0`). Because `AssetIssueStore` entries are permanent (no delete path once issued) and the name check is a simple existence test on attacker-visible mempool data, any unprivileged account can front-run a victim's `AssetIssueContract` transaction by broadcasting (and getting mined first) their own `AssetIssueContract` with the identical `name`, permanently occupying that name and causing the victim's transaction to fail forever with `"Token exists"`.

### Finding Description
The validation logic is:
```java
if (dynamicStore.getAllowSameTokenName() == 0
    && assetIssueStore.get(assetIssueContract.getName().toByteArray())
    != null) {
  throw new ContractValidateException("Token exists");
}
``` [1](#0-0) 

and `execute()` stores the asset keyed by the raw `name` field into `AssetIssueStore`/`AssetIssueV2Store`, with no mechanism to reclaim or overwrite an existing name: [2](#0-1) 

This mirrors the reported `TokenDistributor.initializeDistributor` bug class: a check compares externally-observable, attacker-mutable state (`assetIssueStore.get(name)`) against a value the legitimate caller committed to ahead of time (the chosen `name`), and any unprivileged party can mutate that state first (front-run) to make the legitimate transaction's precondition fail — deterministically and irrecoverably, since asset names cannot be freed once claimed.

An attacker only needs to observe the pending transaction's `name` field in the mempool/broadcast layer, then submit their own `AssetIssueContract` with that same `name` (paying the `AssetIssueFee`), and get it included first. Any account can call `TriggerContract`-style `AssetIssueContract` transactions — this is fully reachable by an "asset issuer" unprivileged account through the normal transaction broadcast path (`Wallet`/`TronJsonRpcImpl` → actuator).

### Impact Explanation
Once the attacker's dummy asset occupies the name, the legitimate issuer's transaction (and any future transaction wanting to use that exact name) is permanently blocked while `AllowSameTokenName == 0`. Since there's no path to delete or free an issued asset name, this is a permanent denial-of-service against a specific victim's intended token name/business plan — analogous in severity to the original report's DoS-on-initialization finding: the operation can be permanently and irrecoverably blocked with low attacker cost (one fee payment) and no benefit to the attacker beyond griefing.

### Likelihood Explanation
Low-to-moderate. It requires:
1. `AllowSameTokenName` still being `0` at execution time — this is a legacy chain parameter that was switched on by a network proposal on the live mainnet history of java-tron; I could not confirm from the indexed code alone whether the shipped genesis/default value in this repository snapshot is `0` or `1`, since the `DynamicPropertiesStore` default-value grep did not return matches in the indexed content.
2. The attacker seeing the victim's pending transaction (front-running/MEV), same class of "low likelihood, no benefit to attacker" as the original report.

If `AllowSameTokenName` is already permanently `1` in this codebase/network state, this specific check is dead code and not exploitable in production — this caveat should be verified against the live/deployed dynamic property value, which is outside what the index could confirm.

### Recommendation
- Do not use raw, attacker-predictable/observable asset names as the sole existence/collision key evaluated purely from mempool-visible data at validate-time.
- If the legacy `AllowSameTokenName == 0` path is still reachable on any live network, disable it permanently via the same proposal mechanism that activated `AllowSameTokenName == 1`, or add a reservation/commit-scheme (e.g., name reservation tied to `ownerAddress` with a bond, or hashed commit-reveal) so that only the account that reserved a name can finalize its use, preventing front-running griefing.
- More generally, apply this pattern check across the codebase for any actuator using `store.get(userSuppliedKey) != null` as a hard precondition without ownership binding.

### Proof of Concept
1. Precondition: `dynamicStore.getAllowSameTokenName() == 0`.
2. Victim Alice broadcasts `AssetIssueContract` with `name = "GOLD"`.
3. Attacker Bob observes Alice's pending transaction in the mempool, and broadcasts his own `AssetIssueContract` with `name = "GOLD"`, paying the same `AssetIssueFee`, with a higher/competing energy/bandwidth priority so it gets included first (front-running).
4. Bob's transaction executes successfully via `AssetIssueActuator.execute()`, storing `"GOLD"` in `AssetIssueStore`. [3](#0-2) 
5. Alice's transaction is then validated and fails permanently with `"Token exists"`: [1](#0-0) 
6. There is no code path to delete/free `"GOLD"` from `AssetIssueStore`, so Alice can never issue an asset named `"GOLD"` again on this chain — a permanent DoS analogous to the reported `initializeDistributor` front-run.

Note: I was unable to fully confirm from the indexed code whether `AllowSameTokenName` defaults to `0` (vulnerable) or `1` (already hardened) in the current deployed configuration of this repository; a Devin session with full repository/config access would be needed to verify the live dynamic-property default and any related hard-fork activation status before treating this as confirmed-exploitable on a specific running network.
