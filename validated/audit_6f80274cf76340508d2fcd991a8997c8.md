## Analog Found

### Title
Missing chain identifier in `ValidateMultiSign` precompile signature hash enables cross-chain replay of contract-level approvals - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The TVM precompiled contract `ValidateMultiSign` (address `0x66`), used by smart contracts to verify off-chain-signed, permission-weighted approvals against an on-chain account's `Permission`, computes the message hash to recover signer addresses from only `address || permissionId || data` — with no chain identifier mixed in. Any signed approval intended for one java-tron-based network can be replayed verbatim on any other java-tron-based network (mainnet, a testnet such as Nile/Shasta, or any third-party chain bootstrapped from the same java-tron codebase) as long as the same contract/account address and permission configuration exist there, exactly mirroring the Harpie `changeRecipientAddress()` cross-chain replay bug class.

### Finding Description
`ValidateMultiSign.execute()` builds the signed-message hash as: [1](#0-0) 

```java
byte[] address = words[0].toTronAddress();
int permissionId = words[1].intValueSafe();
byte[] data = words[2].getData();

byte[] combine = ByteUtil.merge(address, ByteArray.fromInt(permissionId), data);
byte[] hash = Sha256Hash.hash(CommonParameter
    .getInstance().isECKeyCryptoEngine(), combine);
```

It then recovers each supplied signature against `hash` and accumulates weight from the account's `Permission` keys via `TransactionCapsule.getWeight`, returning success (`DATA_FALSE`/`dataOne()`) once threshold weight is met: [2](#0-1) 

This is functionally identical to the Harpie `Vault.changeRecipientAddress()` pattern: a smart contract accepts a set of off-chain ECDSA signatures over `(address, permissionId, data)` and treats reaching a weight threshold as sufficient authorization to execute a privileged action (e.g., approve a withdrawal, change a recipient, or unlock funds) — without ever binding the signature to a specific chain. Since `chain.id` (or any chain-specific salt) is absent from the hashed payload, a signature that a user or off-chain relayer produced for a contract deployed at address `A` with permission `P` on one java-tron network is equally valid for a contract at the same address `A` with the same permission `P` on a different java-tron-derived network (e.g., a testnet used for staging that mirrors mainnet deployment addresses via deterministic `CREATE2`, or any consortium/private chain forked from java-tron).

This differs from the base-layer `TransactionCapsule.validateSignature()` path, which additionally binds signatures to `ref_block_hash`/`expiration` fields tied to an actual, network-specific block history — giving native transactions incidental protection that this precompile lacks entirely, since callers can supply an arbitrary `data` payload with no such binding.

### Impact Explanation
Any DApp built on top of `ValidateMultiSign` for approval/authorization flows (multisig wallets, meta-transaction relayers, escrow/vault contracts) inherits a signature scheme with no cross-chain replay protection. If the same contract bytecode and permission setup is deployed at the same address on two java-tron-based networks (a common and encouraged pattern via `CREATE2` for cross-chain consistency, or simply mainnet vs. its official testnets), a signature obtained by a user or attacker on one chain can be replayed on the other to pass the weight-threshold check and trigger the contract's privileged logic there, resulting in unauthorized account operations or theft of funds — the same impact class validated in the Harpie report.

### Likelihood Explanation
Exploitation requires only a standard smart-contract call reachable by any unprivileged TVM contract deployer/caller (the precompile is directly invokable from Solidity via the `0x66` address), plus the precondition — realistic in the TRON ecosystem — that the same address/permission configuration is replicated across networks (deterministic deployment is a common practice specifically to keep addresses consistent across chains). No privileged role, consensus manipulation, or node compromise is needed.

### Recommendation
Mix a chain-specific identifier (e.g., `chainId`/genesis block hash exposed via `chainid` opcode or a `DynamicPropertiesStore` value) into the `combine` payload hashed in `ValidateMultiSign.execute()`, so that:
```java
byte[] combine = ByteUtil.merge(chainId, address, ByteArray.fromInt(permissionId), data);
```
This forces contracts relying on this precompile to produce signatures that are only valid on the network they were intended for, closing the replay vector without needing every downstream DApp to independently remember to add chain binding themselves.

### Proof of Concept
1. Deploy an identical contract `C` (using `CREATE2` for a deterministic address) on both TRON Mainnet and a java-tron-based testnet/private chain, with the same on-chain account `A` and `Permission` (`permissionId`, keys, threshold) configured identically on both chains.
2. On Mainnet, contract `C` requests user `U` to sign an authorization for `data` (e.g., "approve withdrawal to address X") via the `ValidateMultiSign` scheme: `U` signs `Sha256(address(C) || permissionId || data)`.
3. Attacker captures this signature (it is typically passed as public calldata/relayed transaction) and submits it unchanged to the equivalent contract `C` at the same address on the testnet/private chain.
4. `ValidateMultiSign.execute()` on the second chain recomputes the identical `hash` (since `address`, `permissionId`, and `data` are unchanged and no chain id is included), recovers the same signer, accumulates the same weight, and returns success — even though `U` never authorized this action on that chain, letting the attacker trigger the privileged operation there.
