### Title
Unauthenticated attacker can fill Atlas uninstantiated-attachment storage with content never referenced by any on-chain BNS/AttachmentInstance commitment - ([File: stackslib/src/net/atlas/db.rs])

### Summary
`RPCPostTransactionRequestHandler::try_handle_request` in `stackslib/src/net/api/posttransaction.rs` accepts an arbitrary, attacker-supplied `Attachment` alongside any `ContractCall` transaction and, as long as `should_keep_attachment` passes (contract is in the configured Atlas `contracts` set and content length ≤ `attachments_max_size`), calls `AtlasDB::insert_uninstantiated_attachment` directly, with no check that the content's hash is ever referenced by a real, confirmed `AttachmentInstance`. Any unprivileged remote client with access to `/v2/transactions` can therefore fill the `attachments` table up to `max_uninstantiated_attachments` with content tied to no consensus commitment.

### Finding Description
The claimed invariant — "every stored uninstantiated attachment's hash equals some `content_hash` of a queued/on-chain `AttachmentInstance`" — is not enforced at insert time. `AtlasDB::insert_uninstantiated_attachment` (stackslib/src/net/atlas/db.rs L511-536) unconditionally performs `INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 0, ?)` keyed by `attachment.hash()`, and only evicts the oldest entries once `count_uninstantiated_attachments() >= max_uninstantiated_attachments` [1](#0-0) .

The only production caller of this function is `RPCPostTransactionRequestHandler::try_handle_request` (stackslib/src/net/api/posttransaction.rs L230-251), which is reachable via the unauthenticated `POST /v2/transactions` RPC endpoint. Any remote peer can submit a JSON body containing an arbitrary `StacksTransaction` with a `ContractCall` payload (targeting any contract in `atlas_config.contracts`, e.g. the boot `bns` contract) plus an arbitrary hex-encoded `attachment` blob. As long as `mempool.submit` accepts the transaction (or even if it's ultimately going to be rejected downstream for unrelated Clarity reasons, the attachment insertion happens right after mempool acceptance, so any accepted-but-otherwise-worthless ContractCall suffices) and `should_keep_attachment` passes size/contract checks, the attachment content is written to `attachments` with `was_instantiated = 0`, without any check that this content_hash matches any existing or future `AttachmentInstance.content_hash` [2](#0-1) .

No `AttachmentInstance` is created or required at this point — that only happens later, on-chain, when/if a BNS operation actually references this hash. Nothing in `try_parse_request` or `try_handle_request` cross-references the attachment hash against `attachment_instances`. The only guard is `should_keep_attachment`, which checks contract membership and size, not whether the content corresponds to any commitment. This confirms the equality claimed in the question is false at insert time, and the only bound is the configurable `max_uninstantiated_attachments` cap combined with time-based eviction (`evict_expired_uninstantiated_attachments`, `evict_k_oldest_uninstantiated_attachments`).

### Impact Explanation
An unprivileged remote peer can repeatedly submit `POST /v2/transactions` requests carrying distinct ContractCall transactions (e.g., varying nonces/fees to bypass `mempool.has_tx` dedup) each paired with a different attacker-chosen attachment blob (up to `attachments_max_size`, default use depends on config but is bounded, e.g. 1MB class sizes are typical for BNS zonefiles). Each accepted request writes one row into the node's `attachments` SQLite table with content tied to no consensus commitment, occupying a slot until `max_uninstantiated_attachments` triggers oldest-first eviction. This causes disk/DB storage growth and pollution of the Atlas attachment cache with garbage content that was never confirmed on-chain, matching the "attachment/BNS mismatch" High-impact category since the node's uninstantiated-attachment store no longer reflects only content referenced by real `AttachmentInstance`s. This is repeatable per request and does not require any privileged role, secret, or admin access — a valid mempool-acceptable transaction plus attachment blob is sufficient.

### Likelihood Explanation
Preconditions: the node's `/v2/transactions` RPC endpoint must be remotely reachable (default, no auth required for this endpoint), and `atlas_config.contracts` must include at least one contract the attacker can legally call (the `bns` contract is included by default in most Atlas configurations). The attacker needs only to craft valid, mempool-acceptable `ContractCall` transactions (any contract-call meeting basic validity/fee/nonce checks) with distinct nonces to avoid `mempool.has_tx` dedup, and pair each with an arbitrary attachment blob under `attachments_max_size`. This is cheap and fully repeatable — cost is bounded only by the fee/nonce requirements for mempool-acceptable transactions, which is a low bar for a well-funded or fee-tolerant attacker, or negligible if invalid-nonce transactions are still accepted into local mempool checks.

### Recommendation
At insert time in `AtlasDB::insert_uninstantiated_attachment` (or in the `posttransaction.rs` handler before calling it), require that `attachment.hash()` matches an existing `attachment_instances.content_hash` entry (queued or on-chain) before persisting the content; otherwise reject/drop the attachment. Alternatively, restrict `insert_uninstantiated_attachment` calls originating from `/v2/transactions` to only speculative future-attachment gossip that is later reconciled and time-bounded much more aggressively (e.g., very small `uninstantiated_attachments_expire_after` and a separate, smaller quota for unconfirmed submissions distinct from the pool used by confirmed `AttachmentInstance` resolution), so unauthenticated submissions cannot starve out slots reserved for legitimately queued attachments.

### Proof of Concept
```rust
// stackslib/src/net/atlas/tests.rs (illustrative, extending existing test file)
#[test]
fn test_unconfirmed_attachment_storage_pollution() {
    let bns_contract_id = boot_code_id("bns", false);
    let mut contracts = HashSet::new();
    contracts.insert(bns_contract_id.clone());

    let atlas_config = AtlasConfig {
        contracts,
        attachments_max_size: 1024,
        max_uninstantiated_attachments: 10,
        uninstantiated_attachments_expire_after: 10_000,
        unresolved_attachment_instances_expire_after: 10_000,
        genesis_attachments: None,
    };
    let mut atlas_db = AtlasDB::connect_memory(atlas_config.clone()).unwrap();

    // Simulate what posttransaction.rs does for 15 distinct attacker-supplied
    // attachments tied to a ContractCall on the `bns` contract, with NO
    // corresponding AttachmentInstance ever created.
    for i in 0..15u8 {
        let content = format!("attacker-garbage-{}", i);
        let attachment = new_attachment_from(&content);
        if atlas_db.should_keep_attachment(&bns_contract_id, &attachment) {
            atlas_db.insert_uninstantiated_attachment(&attachment).unwrap();
        }
    }

    // Storage is bounded only by max_uninstantiated_attachments, eviction is
    // oldest-first, and none of these hashes correspond to any AttachmentInstance.
    assert_eq!(atlas_db.count_uninstantiated_attachments().unwrap(), 10);
    for i in 5..15u8 {
        let content = format!("attacker-garbage-{}", i);
        let hash = new_attachment_from(&content).hash();
        assert!(atlas_db.find_uninstantiated_attachment(&hash).unwrap().is_some());
        // Prove there is no on-chain / queued commitment for this content hash:
        assert!(atlas_db.find_all_attachment_instances(&hash).unwrap().is_empty());
    }
}
```

    pub fn insert_uninstantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        // Insert the new attachment
        let uninstantiated_attachments = self.count_uninstantiated_attachments()?;
        if uninstantiated_attachments >= self.atlas_config.max_uninstantiated_attachments {
            let to_delete =
                1 + uninstantiated_attachments - self.atlas_config.max_uninstantiated_attachments;
            self.evict_k_oldest_uninstantiated_attachments(to_delete)?;
        }

        let tx = self.tx_begin()?;
        let now = util::get_epoch_time_secs() as i64;
        let res = tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 0, ?)",
            params![
                attachment.hash(),
                attachment.content,
                now,
            ],
        );
        res.map_err(db_error::SqliteError)?;
        tx.commit().map_err(db_error::SqliteError)?;
        Ok(())
    }
