### Title
Out-of-bounds read in singlejar's Zip64 extra-field attribute indexing - (File: src/tools/singlejar/zip_headers.h)

### Summary
`singlejar`'s `CDH` and `LH` zip-header classes compute an index into a `Zip64ExtraField`'s attribute array purely from the 32-bit size/offset fields' "needs-extension" flags, then call `attr64(index)`/`timestamp(index)` on the field without ever checking that the field's own `attr_count()`/`timestamp_count()` (derived from the attacker-controlled `payload_size`) actually contains that many entries. This is the same bug class as JLSEC-2026-784: an attacker-controlled index/flag combination drives an unchecked array access into a variable-length, attacker-sized record.

### Finding Description
`Zip64ExtraField::attr64(int index)` and `UnixTimeExtraField::timestamp(int index)` are raw, unchecked accessors: [1](#0-0) 

`CDH::local_header_offset()` and `CDH::compressed_file_size()`/`uncompressed_file_size()` compute the attribute index from the *32-bit fixed-size fields' sentinel values* (`0xFFFFFFFF` ⇒ "needs Zip64 extension"), not from the actual number of attributes present in the located `Zip64ExtraField`: [2](#0-1) [3](#0-2) [4](#0-3) 

`Zip64ExtraField::find()` only verifies that the field's declared `size()` (4-byte header + `payload_size()`) fits within `[extra_fields(), extra_fields()+extra_fields_length())`; it never checks that `payload_size()` is large enough to contain the number of 8-byte attributes that the caller is about to index: [5](#0-4) [6](#0-5) 

Both `CDH` and `LH` are overlaid directly on attacker-supplied bytes mapped from a JAR/ZIP file (`InputJar::LocateCentralDirectory`, `mapped_file_.MapExisting`), with no separate deserialization/validation step: [7](#0-6) [8](#0-7) 

Concretely, an attacker can craft a central-directory entry where `compressed_file_size32`/`uncompressed_file_size32`/`local_header_offset32` are all `0xFFFFFFFF` (signaling "value is in Zip64 extra field"), but the accompanying Zip64 extra field's `payload_size` only declares 0 or 1 attribute (8 or 16 bytes) instead of the 24 bytes needed for all three values. `zip64_extra_field()` still finds and returns this truncated field (size-bounds check on the field header/payload passes because it matches its own declared, undersized `payload_size`), and the caller then calls `attr64(2)` (or `attr64(1)`) which reads 8 bytes past the end of the declared/allocated payload — an out-of-bounds read relative to the mapped input buffer, directly analogous to `sftp_extensions_get_name/data` indexing past the extension array bounds in libssh.

### Impact Explanation
`local_header_offset()` is used by `output_jar.cc`/`input_jar.cc` to seek into the mapped input file to locate the corresponding local file header and copy that entry's bytes into the merged output JAR. If the OOB-read leaks adjacent heap/mapped-memory bytes, that garbage value is used as a file offset (potentially crashing on out-of-range access, or if it happens to fall within the mapped region, copying unrelated bytes from elsewhere in the same buffer). `compressed_file_size()`/`uncompressed_file_size()` similarly feed directly into `memcpy`/decompression length calculations elsewhere in singlejar. This can manifest as a crash (worker/build-tool DoS) or, more concerning, incorrect/garbage data being copied into build outputs. `singlejar` runs as an ordinary build action, so this is a genuine bug in Bazel's own trusted extraction/merging code path, not sandboxed Starlark.

### Likelihood Explanation
`singlejar` processes every JAR that is merged for a `java_import`/`java_library` deploy jar, including jars that arrive as fetched dependencies (e.g., via `http_jar`/`http_file`/Maven rules) with attacker-controlled bytes. As with the libssh advisory, exploitation only requires crafting one malformed central-directory entry inside an otherwise well-formed JAR; sha256/lockfile integrity checks on the *download* do not protect against this because they only prove the bytes match what the attacker published — they say nothing about internal Zip64 extra-field consistency, which is exactly the invariant that is broken here.

### Recommendation
Add explicit bounds checks in `zip_headers.h` before any `attr64(index)`/`timestamp(index)` call:
- In `Zip64ExtraField`, validate `index < attr_count()` before returning the value (or have `attr64` itself assert/bounds-check against `payload_size()`).
- In `UnixTimeExtraField::timestamp()`, validate `index < timestamp_count()`.
- In `CDH::compressed_file_size()`, `CDH::uncompressed_file_size()`, `CDH::local_header_offset()`, and the equivalent `LH` methods, treat a `Zip64ExtraField` whose `attr_count()` is smaller than the computed `attr_no` as corrupt input and fail cleanly (`diag_errx`), the same way `AppendToDirectoryBuffer` already fails on malformed extra fields.

### Proof of Concept
A `BuildIntegrationTestCase`/`src/tools/singlejar` unit test (in the style of `zip_headers_test.cc`) can construct a `CDH` with:
- `compressed_file_size32(0xFFFFFFFF)`, `uncompressed_file_size32(0xFFFFFFFF)`, `local_header_offset32(0xFFFFFFFF)`
- An attached Zip64 extra field with `payload_size = 8` (i.e. `attr_count() == 1`)

then call `cdh->local_header_offset()`, which computes `attr_no = 2` and invokes `z64->attr64(2)`, reading 8 bytes beyond the field's declared/allocated payload — verifiable with ASan by placing the crafted bytes at the end of a heap allocation sized exactly to the declared `extra_fields_length()`. class ExtraField {
 public:
  static const ExtraField* find(uint16_t tag, const uint8_t* start,
                                const uint8_t* end) {
    while (start < end) {
      if (ziph::byte_ptr(start) + sizeof(ExtraField) > ziph::byte_ptr(end)) {
        break;
      }
      auto extra_field = reinterpret_cast<const ExtraField*>(start);
      if (ziph::byte_ptr(start) + extra_field->size() > ziph::byte_ptr(end)) {
        break;
      }
      if (extra_field->is(tag)) {
        return extra_field;
      }
      start = ziph::byte_ptr(start) + extra_field->size();
    }
    return nullptr;
  }
