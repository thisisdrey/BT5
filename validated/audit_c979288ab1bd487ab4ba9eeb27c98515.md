Based on my investigation, this is confirmed to be a valid finding.

The critical evidence is in the test `test_wrapper_worst_case_scenario` in `chain/chain/src/runtime/trie_update_wrapper.rs`, which explicitly demonstrates that reading a single deliberately-crafted trie key generates **52kB of storage proof from a single read** [1](#0-0) , using an attacker-controlled fan-out of sibling keys (account_id/public_key nibble variations) placed on the path to a target key. This confirms that in NEAR's trie, a wide/adversarially-shaped sibling set on the path to a leaf **does** inflate the recorded storage-proof size for a single read well beyond a negligible amount — contrary to the naive assumption that Merkle-Patricia proofs only grow logarithmically. The companion test `test_add_keys_after_large_read_exceed_receipt_storage_proof_limit` in `runtime/runtime/src/tests/apply.rs` similarly documents that "an `AddKey` records the subtree nodes its lookup walks that no earlier one did" when siblings fill a branch [2](#0-1) .

Separately, the soft-limit check in `prepare_transactions_extra` is only evaluated **once per transaction-group visit, before** any transactions from that group are read/validated [3](#0-2) . There is no check after validating an individual transaction, and no per-transaction upper bound on validation storage-proof size (unlike `per_receipt_storage_proof_size_limit` for receipt execution). This means one transaction whose access-key/nonce lookup is deliberately made expensive can push `recorded_storage_size()` far above `new_transactions_validation_state_size_soft_limit` (572,864 bytes / 500 KiB) in a single step, and only on the **next** loop iteration does the chunk producer detect this and set `limited_by = StorageProofSize`, excluding all other pending transaction groups.

### Title
Single-transaction storage-proof soft-limit starvation via wide access-key trie subtree - (File: chain/chain/src/runtime/mod.rs)

### Summary
`prepare_transactions_extra` only checks `new_transactions_validation_state_size_soft_limit` once per transaction-group visit, before validating any transaction in that group, and there is no per-transaction cap on validation-time storage proof. An attacker who pre-populates a wide/adversarial sibling-key subtree on the path to their own access key can craft one transaction whose nonce/access-key lookup alone generates tens of KB to potentially hundreds of KB of recorded storage proof (as demonstrated by `test_wrapper_worst_case_scenario`, which reaches 52kB with a moderate key set), consuming most or all of the 500 KiB soft-limit budget in one step.

### Finding Description
The chunk-building loop in `prepare_transactions_extra` checks the soft limit only at the top of the outer `add_txs_loop`, before pulling transactions from the next signer's group [3](#0-2) . Once a group passes this check, the inner loop reads the trie to validate the transaction's nonce/access key (`get_or_load_entry_mut`, `verify_and_charge_tx_ephemeral`/`verify_and_charge_gas_key_tx_ephemeral`) [4](#0-3) , recording all trie nodes touched. If the attacker has previously added many sibling access keys (or account IDs) that share a long common prefix with their own key's trie path, this single lookup walks many large branch nodes, as proven by `test_wrapper_worst_case_scenario` (52kB from one read) [5](#0-4) . Because the soft-limit check happens only between groups — not after each transaction — this single transaction is admitted regardless of how much proof it generates, and the overage is only detected on the *next* group's pre-check, at which point `PrepareTransactionsLimit::StorageProofSize` is set and the loop breaks [6](#0-5) , excluding every other pending signer's transactions from that chunk. No existing check (signature, nonce, access-key permission, gas, or `max_transaction_size`) bounds the *width* of the attacker's own sibling-key subtree or the resulting validation-time storage-proof size; `per_receipt_storage_proof_size_limit` and `main_storage_proof_size_soft_limit` apply only to receipt execution, not to transaction validation in `prepare_transactions`.

### Impact Explanation
This is a liveness/availability issue: a single unprivileged attacker transaction can monopolize the entire per-chunk transaction-validation storage-proof budget, causing chunk producers to admit only that one transaction and defer all other users' pending transactions to future chunks. This does not cause fund loss, double-spend, or consensus divergence by itself (the documented "soft limit" semantics already tolerate the last item exceeding the budget) — the impact is degraded chunk throughput / transaction censorship for other users, which is a liveness/DoS concern rather than a fund-theft or chain-split bug.

### Likelihood Explanation
Preconditions require the attacker to fund an account and add many access keys (or use adversarially crafted account IDs/public keys) forming a long shared trie-path prefix, each costing NEAR for storage staking and gas for `AddKey` actions — a cost that scales with subtree size (the 52kB PoC required populating on the order of ~1,000+ sibling keys per nibble level across a 32-byte key and up to a 64-byte account ID). This is economically nontrivial but fully within reach of an unprivileged, well-funded attacker, and is repeatable per chunk once the state is set up (the crafted keys/state persist).

### Recommendation
Enforce the `new_transactions_validation_state_size_soft_limit` check after validating each individual transaction (not just once per group visit), and/or introduce a hard per-transaction cap on validation-time storage proof analogous to `per_receipt_storage_proof_size_limit`, so a single transaction cannot silently consume the entire per-chunk budget before the limit is re-evaluated.

### Proof of Concept
Extend `test_wrapper_worst_case_scenario`-style key generation to populate a real trie with a wide access-key subtree for a funded account, then call `prepare_transactions_extra` with `new_transactions_validation_state_size_soft_limit` set to the production value (572,864) and a pool containing (a) the attacker's one transaction using the deeply-nested access key and (b) several honest transactions from unrelated signers. Assert that `state_update.recorded_storage_size()` after processing the attacker's transaction alone exceeds the soft limit, that `prepared.limited_by == PrepareTransactionsLimit::StorageProofSize`, and that none of the honest transactions were included in `prepared.transactions`.
