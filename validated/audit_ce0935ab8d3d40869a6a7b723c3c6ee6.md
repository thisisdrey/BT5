### Title
Kamino Harvest Reward Lacks Reward-Mint-vs-Bank-Mint Check, Allowing Sweep of Bank's Underlying Deposited Liquidity as "Rewards" - ([File: programs/marginfi/src/instructions/kamino/harvest_reward.rs])

### Summary
`kamino_harvest_reward` sweeps the entire post-CPI balance of `user_reward_ata` (an ATA owned by the bank's `liquidity_vault_authority`) to the `destination_token_account` owned by the global fee wallet, computed purely as `post_transfer_balance - pre_transfer_balance` around a Kamino Farms CPI call. Unlike the sibling `DriftHarvestReward` instruction, which explicitly enforces `harvest_drift_spot_market.load()?.mint != bank.load()?.mint` (`MarginfiError::DriftSpotMarketMintMismatch`) to guarantee the harvested asset is never the same as the bank's actual collateral/liability mint, `KaminoHarvestReward` has no equivalent constraint tying `reward_mint` away from `bank.mint`.

### Finding Description
The bug-class from the external report — failing to separate "staked"/principal funds from "reward" funds when both are denominated in the same token, allowing a reward-sweep function to drain principal — maps directly onto this instruction:

- `liquidity_vault_authority` is the same PDA that signs for the bank's real liquidity vault (`BankVaultType::Liquidity`, seeded by `LIQUIDITY_VAULT_AUTHORITY_SEED`), used across deposit/withdraw/borrow/repay and other integration flows (Kamino, Drift, JupLend). [2](#0-1) 
- `user_reward_ata` is simply an "initialized ATA of type reward mint owned by liquidity vault" and is `UncheckedAccount` — there is no constraint validating `reward_mint != bank.mint`. [3](#0-2) 
- The instruction handler computes `received = post_transfer_balance - pre_transfer_balance` around the Kamino `harvest_reward` CPI and unconditionally transfers that full delta out to the global fee wallet's destination account, with no accounting of whether that ATA also happens to hold real bank liquidity of the same mint. [4](#0-3) 
- Contrast with `DriftHarvestReward`, which was hardened specifically against this exact class of bug via an explicit mint/market check: `harvest_drift_spot_market.load()?.mint != bank.load()?.mint @ MarginfiError::DriftSpotMarketMintMismatch` and `harvest_drift_spot_market.key() != bank.load()?.integration_acc_1 @ MarginfiError::DriftHarvestSameMarket`. [5](#0-4) 

If a bank's Kamino farm ever emits a reward denominated in the same mint as the bank's own asset (e.g., a stablecoin bank farming a stablecoin-denominated incentive, or if `user_reward_ata`/`rewards_vault` are misconfigured or reused across banks by an admin/relayer providing the wrong `reward_mint`/`user_state`/`farm_state` remaining-account set), the permissionless caller can direct `kamino_harvest_reward` to sweep tokens of the bank's own mint out of an account effectively controlled by `liquidity_vault_authority`, straight to the global fee wallet — mirroring the reported "rewards drain principal" pattern, since there is no bank-level bookkeeping (unlike `collected_*_fees_outstanding` for `LendingPoolCollectBankFees`) verifying the swept amount corresponds only to genuine incremental rewards distinct from the bank's liquidity.

### Impact Explanation
If reachable (i.e., if the reward mint can coincide with, or be manipulated to coincide with, the bank's own mint, or if the `user_reward_ata`/farm accounts can be pointed at an account that also holds bank liquidity), this results in unauthorized transfer of value out of the protocol's liquidity to the global fee wallet, which is an external, non-depositor destination — a direct value-leak/insolvency vector for depositors of that bank, comparable in severity to the original "withdraw staked funds via rewards function" bug.

### Likelihood Explanation
This instruction is guarded by an asset-tag check (`is_kamino_asset_tag`) restricting it to Kamino-integration banks, and requires the `reward_mint`, `farm_state`, `rewards_vault`, and other CPI accounts to be supplied by the caller/CPI at call time — these are largely `UncheckedAccount`s validated only indirectly through the Kamino CPI itself, meaning correctness depends heavily on off-chain/CPI-level guarantees rather than on-chain constraints. Because `DriftHarvestReward` was explicitly hardened against exactly this scenario (same-mint harvest), while `KaminoHarvestReward` was not, this looks like a missing defense-in-depth check rather than a purely theoretical concern — but it requires either a genuine Kamino farm reward denominated in the bank's own mint, or an admin/permissionless caller supplying manipulated `remaining_accounts`/`user_state`/`farm_state` that Kamino's own CPI does not reject. I could not verify from the indexed code whether Kamino's `harvest_reward` CPI itself independently prevents `reward_mint == bank.mint` scenarios at the protocol level, since `kamino_mocks::kamino_farms` CPI internals are outside indexed scope.

### Recommendation
Add the same defense used in `DriftHarvestReward` to `KaminoHarvestReward`: enforce a constraint that `reward_mint.key() != bank.load()?.mint` (and, if applicable, that `farm_state`/`user_state` correspond to a farm distinct from the bank's own Kamino reserve/obligation), returning a dedicated error (e.g., `KaminoHarvestSameMintError`) if violated. This closes the gap between the two otherwise-symmetric harvest-reward instructions and ensures reward-sweep logic can never touch tokens of the bank's own underlying mint.

### Proof of Concept
Conceptual PoC (cannot be fully executed without live Kamino Farms state, but demonstrates the missing check):
1. Set up a Kamino-integration bank whose `bank.mint` is mint `M`.
2. Configure (or find) a Kamino farm reward stream for that bank's obligation that pays out reward mint `M` (same as `bank.mint`) — nothing in `KaminoHarvestReward`'s account constraints rejects this, unlike `DriftHarvestReward`'s explicit `DriftSpotMarketMintMismatch` check.
3. Call `kamino_harvest_reward` permissionlessly; `cpi_harvest_rewards` credits `user_reward_ata` (owned by `liquidity_vault_authority`) with mint-`M` tokens, and `cpi_transfer_obligation_owner_to_destination` sweeps the entire delta straight to the global fee wallet's ATA — with no on-chain check distinguishing "reward" `M` tokens from "principal" `M` tokens that might reside in/near the same authority's control.
4. Compare to `DriftHarvestReward`, where step 2's equivalent is explicitly rejected via `constraint = harvest_drift_spot_market.load()?.mint != bank.load()?.mint @ MarginfiError::DriftSpotMarketMintMismatch` [6](#0-5) , confirming the asymmetry is a gap rather than an intentional design choice.

pub fn kamino_harvest_reward(
    ctx: Context<KaminoHarvestReward>,
    reward_index: u64,
) -> MarginfiResult {
    let pre_transfer_balance = accessor::amount(&ctx.accounts.user_reward_ata.to_account_info())?;
    ctx.accounts.cpi_harvest_rewards(reward_index)?;
    let post_transfer_balance = accessor::amount(&ctx.accounts.user_reward_ata.to_account_info())?;
    let received = post_transfer_balance - pre_transfer_balance;
    ctx.accounts
        .cpi_transfer_obligation_owner_to_destination(received)?;
    Ok(())
}
