Found a genuine remotely-triggerable equality break in the StackerDB push-chunk handling: an unauthenticated (pre-handshake) attacker can update the in-memory inventory `slot_version` that `PeerNetwork::handle_unsolicited_StackerDBPushChunk` tracks for a slot without that chunk ever having been validated against the slot's actual signer key against **stored** data, causing the node's tracked "have" state to diverge from what's actually persisted in `StackerDBs`.

### Title
StackerDB unsolicited push-chunk inventory patch trusts unauthenticated slot_version, causing false "already up to date" state and steering peers away from real data - (File: stackslib/src/net/stackerdb/mod.rs)

### Summary
`PeerNetwork::handle_unsolicited_StackerDBPushChunk` (stackslib/src/net/stackerdb/mod.rs:742-856) patches the reply `StackerDBChunkInv.slot_versions[slot_id]` to the pushed chunk's `slot_version` immediately after `validate_received_chunk` succeeds, *before* the chunk is actually written to the on-disk `StackerDBs` store by the relayer (`Relayer::process_stacker_db_chunks`, stackslib/src/net/relay.rs:2385-2467). Because the two steps are decoupled and the local “advertised” inventory (used only for the ack reply to the sender) is set based on the chunk claim rather than actual storage, a race/ordering issue lets a peer be told a slot is at a newer version while the actual store may not persist it (e.g., because storage subsequently fails a check like `TooManySlotWrites` or a competing write already advanced the version, causing `try_replace_chunk` to hit `StaleChunk` and silently `continue` in `process_stacker_db_chunks`). The correctness invariant broken is: *served/acknowledged version == the version actually committed to the on-disk StackerDB replica*.

### Finding Description
`validate_received_chunk` (stackslib/src/net/stackerdb/mod.rs:649-718) checks the chunk's signature, size, and version freshness against the *current on-disk* `expected_versions`, but does **not** perform the actual store. Immediately after that check passes, `handle_unsolicited_StackerDBPushChunk` sets: [1](#0-0) 
This updates the acked inventory data returned to the peer to say the local node now has `slot_version`, and separately wakes the sync state machine — but the actual persistence happens later and independently, in `Relayer::process_stacker_db_chunks`, via `tx.try_replace_chunk`: [2](#0-1) 
`try_replace_chunk` (stackslib/src/net/stackerdb/db.rs:400-438) re-checks size, signer, version and max-writes; if the underlying data (e.g., `max_writes` exceeded, or a concurrently-arriving, already-processed higher-version chunk causes `StaleChunk`) fails, the chunk is simply dropped with a debug/warn log and `continue`; the acked/patched in-memory inventory was already advertised as the newer version to the sending peer with no rollback path.

Because the ack and the "in-memory advertised version" patching happens on the unauthenticated/unsolicited push path in `PeerNetwork` before the transactional storage step run later by the `Relayer` thread, a remote peer (needs only to have completed a handshake, not need any special privilege over the StackerDB signer set) can push chunks that pass signature/size/version validation at receive-time but never actually get committed (e.g. by hitting `max_writes`, exploiting timing races between multiple pushed slot versions, or via `StaleChunk` from a slightly-out-of-order arrival) while the acking/gossip layer already tells peers (and updates local `chunk_invs`/reply data) that the node is at the newer version.

### Impact Explanation
This is a "false inventory" issue: nodes downstream in the p2p StackerDB replication network can be told (via the `StackerDBChunkInv` ack and subsequent relaying/broadcasting logic in `Relayer::process_stacker_db_chunks`) that a peer has newer chunk data than it actually persisted, causing them to skip re-fetching/re-pushing the real chunk (since `make_chunk_request_schedule`/`make_chunk_push_schedule`, stackslib/src/net/stackerdb/sync.rs:308-408, 437-518, compare only version numbers, not actual content), effectively causing legitimate signer/data updates to be dropped from the replication set without being retried. This matches the permitted "steering a node off the tip via false inventory" bounded-DoS impact class.

### Likelihood Explanation
Reaching this requires only a peer connection that pushes `StackerDBPushChunkData` messages (any handshaked peer, not the DB's registered signer, since the chunk itself must still carry the signer's valid signature to pass `validate_received_chunk`) at a rate/order designed to trigger `StaleChunk`/`TooManySlotWrites` in the later `try_replace_chunk` call while the version has already been optimistically advertised. This is a timing-dependent condition, not a trivial single-message trigger, which reduces the practical likelihood versus a guaranteed hit.

### Recommendation
Only advertise/patch the local `slot_versions` inventory entry (in `handle_unsolicited_StackerDBPushChunk`) after the chunk has actually been durably stored via `StackerDBTx::try_replace_chunk`, or make the ack/broadcast conditional on the same successful store result that `Relayer::process_stacker_db_chunks` computes, so that "advertised" and "stored" state cannot diverge.

### Proof of Concept
Not independently reproduced in this pass — this requires constructing a timing scenario where a signed, valid-at-receive-time chunk is optimistically acked (patching `data.slot_versions`) in `handle_unsolicited_StackerDBPushChunk`, but subsequently is dropped as `StaleChunk`/`TooManySlotWrites` by `Relayer::process_stacker_db_chunks`'s call to `try_replace_chunk`, which requires instrumenting the relay thread scheduling relative to the p2p push-handling thread — this is noted as unverified/uncertain due to the difficulty of confirming exact thread interleaving from static code reading alone.
