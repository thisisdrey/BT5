Audit Report

## Title
Permanently unclaimable relayer tips recorded in `LostTips` with no recovery mechanism - (File: `bridges/snowbridge/pallets/system-v2/src/lib.rs`)

## Summary
`pallet_bridge_system_v2::add_tip` debits nothing itself but is invoked after a user's tip funds have already been withdrawn on AssetHub via the system-frontend pallet; if the corresponding nonce is already consumed when the XCM-forwarded `add_tip` call lands on BridgeHub, the tip amount is diverted into `LostTips<T>` instead of being paid to a relayer. No pallet in the Snowbridge v2 stack (`system-v2`, `system-frontend`, `inbound-queue-v2`, `outbound-queue-v2`) exposes any extrinsic to read, refund, or drain `LostTips<T>`, so the value is permanently stranded on-chain for the affected account.

## Finding Description
`pallet_bridge_system_v2::add_tip` dispatches to `InboundQueue::add_tip`/`OutboundQueue::add_tip` based on `message_id`, and on any `Err` result it unconditionally moves `amount` into `LostTips::<T>::mutate(&sender, ...)`: [1](#0-0) 

The storage definition and its own doc comment confirm the gap is acknowledged but unimplemented: "Capturing the lost tips here supports implementing a recovery method in the future": [2](#0-1) 

The inbound queue's `AddTip::add_tip` implementation explicitly returns `AddTipError::NonceConsumed` once `Nonce::<T>::get(nonce)` is true, which is exactly the race condition described — a relayer's `process_message` sets the nonce and pays out any *existing* tip atomically, but a tip arriving after that point is rejected: [3](#0-2) [4](#0-3) 

A repository-wide search for any reclaim/refund/withdraw/claim-lost dispatchable touching `LostTips` across the Snowbridge pallets (`system-v2`, `system-frontend`, `inbound-queue-v2`, `outbound-queue-v2`) returns no matches — the storage item is write-only from on-chain logic's perspective, confirmed by inspecting the full `system-v2` pallet call surface, which only contains `upgrade`, `set_operating_mode`, `register_token`, and `add_tip`, none of which read `LostTips`. [5](#0-4) 

## Impact Explanation
This satisfies the "permanent user-fund or bridge-state lock" impact category: real, already-debited ether-denominated value from an ordinary user becomes permanently unrecoverable through any on-chain path, with the exact corrupted/stranded value being the `u128` entry in `LostTips::<T>::get(&sender)`. No privileged actor, malicious peer, or compromised relayer is required — it results purely from the pallet's own bookkeeping design.

## Likelihood Explanation
High: adding a tip is an explicitly documented, encouraged user action to speed up relaying of pending messages, and any ordinary race between a user's `add_tip` XCM message and a relayer's message-processing extrinsic for the same nonce triggers the loss. No adversarial timing, privileged access, or malicious behavior is needed — only normal transaction-inclusion ordering on a live chain.

## Recommendation
Add a signed extrinsic that allows the account recorded in `LostTips<T>` to withdraw/reclaim its stranded balance, or redesign the flow so the tip debit and nonce-consumption check happen atomically (e.g., defer debiting until nonce status is confirmed, or allow the user to unreserve funds when `add_tip` fails) as suggested in the report.

## Proof of Concept
1. User debits `amount` on AssetHub via system-frontend and the XCM-forwarded call reaches BridgeHub as `pallet_bridge_system_v2::add_tip(sender, Inbound(nonce), amount)`.
2. Before this call is processed, a relayer's `EthereumInboundQueueV2::submit` for the same `nonce` executes `process_message`, which sets `Nonce::<T>::set(nonce)` [6](#0-5)  and pays out only the tip present at that time (none, since the user's tip hasn't landed yet).
3. `add_tip` then executes; `InboundQueue::add_tip` sees `Nonce::<T>::get(nonce) == true` and returns `AddTipError::NonceConsumed` [7](#0-6) .
4. `pallet_bridge_system_v2::add_tip` catches the `Err` and moves `amount` into `LostTips::<T>::mutate(&sender, ...)`, emitting `TipProcessed { success: false, .. }` [8](#0-7) .
5. `LostTips::<T>::get(&sender)` now permanently holds the stranded `amount`; no extrinsic in `system-v2`, `system-frontend`, `inbound-queue-v2`, or `outbound-queue-v2` reads or clears this value.

	impl<T: Config> Pallet<T> {
		pub fn process_message(relayer: T::AccountId, message: Message) -> DispatchResult {
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == message.gateway, Error::<T>::InvalidGateway);

			let (nonce, relayer_fee) = (message.nonce, message.relayer_fee);

			// Verify the message has not been processed
			ensure!(!Nonce::<T>::get(nonce), Error::<T>::InvalidNonce);

			// Mark message as received
			Nonce::<T>::set(nonce);

			let message_id = T::MessageProcessor::process_message(relayer.clone(), message)
				.map_err(|e| match e {
					MessageProcessorError::ProcessMessage(e) => e,
					MessageProcessorError::ConvertMessage(e) => Error::<T>::from(e).into(),
					MessageProcessorError::SendMessage(e) => Error::<T>::from(e).into(),
				})?;

			// Pay relayer reward
			let tip = Tips::<T>::take(nonce).unwrap_or_default();
			let total_tip = relayer_fee.saturating_add(tip);
			if total_tip > 0 {
				T::RewardPayment::register_reward(&relayer, T::DefaultRewardKind::get(), total_tip);
			}

			// Emit event with the message_id
			Self::deposit_event(Event::MessageReceived { nonce, message_id });

			Ok(())
		}

	impl<T: Config> AddTip for Pallet<T> {
		fn add_tip(nonce: u64, amount: u128) -> Result<(), AddTipError> {
			ensure!(amount > 0, AddTipError::AmountZero);
			// If the nonce is already processed, return an error
			ensure!(!Nonce::<T>::get(nonce.into()), AddTipError::NonceConsumed);
			// Otherwise add the tip.
			Tips::<T>::mutate(nonce, |tip| {
				*tip = Some(tip.unwrap_or_default().saturating_add(amount));
			});
			return Ok(());
		}
	}
