### Title
Silent, uncompensated wNEAR loss when `storage_deposit()` fails during `ft_withdraw` - ([File: contracts/defuse/src/contract/tokens/nep141/withdraw.rs])

### Summary
`ft_resolve_withdraw` only refunds the FT `amount` leg of an `FtWithdraw{storage_deposit: Some(x), ...}` intent; the wNEAR that was unwrapped via `near_withdraw` and attached to the token's `storage_deposit()` call has no resolver at all. If the target token contract's `storage_deposit()` call fails (e.g., it doesn't implement NEP-145), the attached NEAR is refunded by the NEAR protocol to the Defuse contract's own account (the predecessor of the failed action) rather than to the owner's internal ledger, while `withdraw()` has already permanently debited the owner's internal wNEAR balance for that amount.

### Finding Description
The invariant that should hold for the `storage_deposit` leg is:
`wNEAR_debited(owner_id) == NEAR_delivered_as_storage(token, receiver_id) + NEAR_returned(owner_id)`

In `internal_ft_withdraw`, both the FT `amount` and the `storage_deposit` amount (expressed as a wNEAR `TokenId`) are debited together in a single `self.withdraw(...)` call before any promise executes: [1](#0-0) 

`do_ft_withdraw` then builds the promise chain: it checks only `near_withdraw`'s result (index 0), then unconditionally schedules `storage_deposit()` on the (attacker-controlled) token contract, and chains `ft_transfer_call`/`ft_transfer` directly onto that same promise `p` via `ext_ft_core::ext_on(p)` — a cross-contract promise chain, not a same-contract callback: [2](#0-1) 

Because `ft_transfer_call`/`ft_transfer` targets an external contract rather than calling back into `Self`, it cannot inspect or gate on the outcome of the preceding `storage_deposit()` promise, and NEAR's promise scheduling executes chained actions regardless of the parent action's success. This means the FT transfer proceeds independently of whether `storage_deposit` succeeded.

`ft_resolve_withdraw` then only inspects the result of the final action in that chain (the FT transfer) and only ever refunds the FT `token`/`amount` leg: [3](#0-2) 

There is no code path anywhere that inspects the `storage_deposit()` promise's own success/failure or re-credits the owner's wNEAR balance if it fails. If the attacker's token contract does not implement `storage_deposit` (or otherwise makes it fail) while accepting the `ft_transfer_call`/`ft_transfer` normally, the attached NEAR from the failed `storage_deposit` action is refunded by the protocol to the predecessor of that failed receipt — the Defuse contract's own account, as un-tracked native NEAR — never to the owner. Meanwhile `withdraw()` already irreversibly subtracted that wNEAR amount from `owner_id`'s internal balance via `token_balances.sub(...)`: [4](#0-3) 

No `ft_resolve_withdraw`-style resolver exists for this leg, so `NEAR_returned(owner_id)` is always `0` on `storage_deposit` failure, breaking the invariant regardless of the outcome of the FT transfer itself.

### Impact Explanation
Any owner performing `ft_withdraw`/`ft_force_withdraw` with `storage_deposit = Some(x)` against a token contract that lacks (or fails) NEP-145 `storage_deposit` permanently loses `x` yoctoNEAR of their internal wNEAR balance with no refund, event, or recovery path — the NEAR silently accumulates as unaccounted native balance on the Defuse contract account. This is repeatable for every such withdrawal and against every token contract without NEP-145, making it Critical-class impact: value leaves the owner's Verifier-tracked balance without any compensating credit, and the Verifier's custodied wNEAR no longer matches internal accounting for that leg.

### Likelihood Explanation
The only precondition is a target token contract that fails `storage_deposit()` (either genuinely lacking NEP-145, or an attacker-deployed token/receiver combo built to accept `ft_transfer_call`/`ft_on_transfer` but reject/omit `storage_deposit`). This requires no privileged role — any unrestricted signer holding wNEAR-backed balance and using `FtWithdraw{storage_deposit: Some(x)}` against such a token triggers the loss, including unintentionally against any real-world FT that simply hasn't registered NEP-145 storage for the receiver. Cost to trigger is just the normal withdrawal cost; it is fully repeatable per withdrawal.

### Recommendation
Add a dedicated resolver step (or extend `ft_resolve_withdraw`) that inspects the actual result of the `storage_deposit()` promise specifically (not merely the trailing FT-transfer result), and refunds the wNEAR `storage_deposit` amount back to `sender_id` whenever that call did not succeed, mirroring the existing FT-amount refund logic.

### Proof of Concept
`cargo test` sandbox plan (near-workspaces):
1. Deploy the Defuse contract and a wNEAR contract; fund `owner` with wNEAR-backed internal balance of `x + amount`.
2. Deploy a fake FT token contract implementing `ft_transfer_call`/`ft_on_transfer` (always returns `0`, i.e., accepts full transfer) but with no `storage_deposit` method (or one that always panics).
3. Sign a `MultiPayload` with intent `FtWithdraw{ token: fake_token, receiver_id, amount, storage_deposit: Some(x), msg: Some("ok") }`.
4. Call `execute_intents` and let all promises settle.
5. Assert: `owner`'s internal wNEAR balance decreased by exactly `x`, no `mt_mint`/refund event referencing wNEAR was emitted for `owner`, and `owner`'s internal FT balance for `fake_token` decreased by `amount` (transfer succeeded) — confirming `wNEAR_debited(owner) = x` while `NEAR_delivered_as_storage + NEAR_returned = 0`, i.e., `x` yoctoNEAR is unrecoverably lost.

    #[private]
    pub fn do_ft_withdraw(withdraw: FtWithdraw) -> Promise {
        let min_gas = withdraw.min_gas();
        let p = if let Some(storage_deposit) = withdraw.storage_deposit {
            require!(
                promise_result_checked_void(0).is_ok(),
                "near_withdraw failed",
            );

            ext_storage_management::ext(withdraw.token)
                .with_attached_deposit(storage_deposit)
                .with_static_gas(STORAGE_DEPOSIT_GAS)
                // do not distribute remaining gas here
                .with_unused_gas_weight(0)
                .storage_deposit(Some(withdraw.receiver_id.clone()), None)
        } else {
            Promise::new(withdraw.token)
        };

        let p = ext_ft_core::ext_on(p)
            .with_attached_deposit(NearToken::from_yoctonear(1))
            .with_static_gas(min_gas)
            // distribute remaining gas here
            .with_unused_gas_weight(1);
        if let Some(msg) = withdraw.msg {
            p.ft_transfer_call(
                withdraw.receiver_id,
                withdraw.amount.into(),
                withdraw.memo,
                msg,
            )
        } else {
            p.ft_transfer(withdraw.receiver_id, withdraw.amount.into(), withdraw.memo)
        }
    }

    fn ft_resolve_withdraw(
        &mut self,
        token: AccountId,
        sender_id: AccountId,
        amount: U128,
        is_call: bool,
    ) -> U128 {
        let used = if is_call {
            // `ft_transfer_call` returns successfully transferred amount
            match promise_result_checked_json::<U128>(0) {
                Ok(Ok(used)) => used.0.min(amount.0),
                Ok(Err(_deserialize_err)) => 0,
                // do not refund on failed `ft_transfer_call` due to
                // NEP-141 vulnerability: `ft_resolve_transfer` fails to
                // read result of `ft_on_transfer` due to insufficient gas
                Err(_) => amount.0,
            }
        } else {
            // `ft_transfer` returns empty result on success
            if promise_result_checked_void(0).is_ok() {
                amount.0
            } else {
                0
            }
        };

        let refund = amount.0.saturating_sub(used);
        if refund > 0 {
            self.deposit(
                sender_id,
                [(Nep141TokenId::new(token).into(), refund)],
                Some(REFUND_MEMO),
            )
            .unwrap_or_else(|err| err.panic());
        }

        U128(used)
    }
}
