### Title
Out-of-bounds read parsing ZIP central-directory extra fields in ijar - (File: third_party/ijar/zip.cc)

### Summary
`InputZipFile::ProcessCentralDirEntry` in `third_party/ijar/zip.cc` parses the extra-field records of a ZIP central directory entry without bounds-checking each record against the declared `extra_field_length`, mirroring the Contiki-NG bug class of trusting a length field to walk a buffer without validating it stays within bounds.

### Finding Description
When `ijar` (Bazel's interface-jar stripper, used on every `.jar` that is compiled or imported through Bazel's Java toolchain) parses a ZIP/JAR central directory, it reads each entry's extra fields like this: [1](#0-0) 
```
p += file_name_length;
const u1 *extra_p = p;
p += extra_field_length;
while (extra_p != p) {
  const u2 header_id = get_u2le(extra_p);
  const u2 data_size = get_u2le(extra_p);
  const u1 *extra = extra_p;
  extra_p += data_size;
  ...
}
```
`get_u2le` unconditionally reads and advances the pointer with no check that at least 4 bytes remain before `p` (the end of the declared extra-field block), and `data_size` is attacker-controlled with no validation that `extra_p + data_size <= p`. If `data_size` does not evenly divide into `extra_field_length`, `extra_p` can overshoot `p`, and the `while (extra_p != p)` loop condition never becomes false — the loop keeps reading `header_id`/`data_size` pairs past the intended extra-field block, past the end of the whole memory-mapped central directory, and potentially past the end of the mapped file (`MappedInputFile::Buffer()`/`Length()`), which is an out-of-bounds read of mapped memory. Contrast this with `third_party/ijar/output_jar.cc`, which does perform bound checks when iterating extra fields (`ziph::byte_ptr(ef) + sizeof(ExtraField) > ziph::byte_ptr(ef_end)` etc.) — the input-parsing path in `zip.cc` lacks the equivalent check [2](#0-1) .

The only guard present, `EnsureRemaining`, is used elsewhere (`ProcessLocalFileEntry`, `SkipFile`, `ProcessFile`) for local-file-header parsing [3](#0-2) , but `ProcessCentralDirEntry`'s extra-field loop is not covered by any equivalent remaining-bytes check.

### Impact Explanation
This is an out-of-bounds read of memory-mapped file contents while Bazel's `ijar` tool processes a jar during a normal build (`java_library`/`java_import` interface-jar generation runs on every third-party and first-party jar). An attacker who controls the content of a jar consumed by a build (e.g., a maven/http_jar artifact whose crafted bytes were used to compute the sha256 that got pinned into the lockfile/`MODULE.bazel`/`WORKSPACE` at the time it was first vendored) can shape the extra-field length bytes to run this loop past the mapped region, causing a crash (SIGSEGV) or leaking adjacent mapped memory contents into subsequent parsing/output, analogous to the Contiki-NG SLLAO/option-length OOB read.

### Likelihood Explanation
Medium: this path is exercised on essentially every jar Bazel's Java rules process via ijar, so a malicious but sha256-pinned jar (which nothing else in `ijar` validates for structural integrity beyond the checksum of the whole byte stream) can trigger it. It requires the attacker to control jar contents from the outset (matching the checksum the victim later pins) rather than a live MITM, which fits the "hostile origin server" premise allowed by the rules.

### Recommendation
Add bounds checking in `ProcessCentralDirEntry`'s extra-field loop, mirroring the checks already present in `output_jar.cc`'s `AppendToDirectoryBuffer`/`WriteEntry`: before reading `header_id`/`data_size`, verify `extra_p + 4 <= p`, and after computing `data_size`, verify `extra_p + data_size <= p` before advancing, erroring out via `error(...)` (as `SkipFile`/`ProcessFile` do) rather than looping unboundedly.

### Proof of Concept
I could not fully trace the top-level `Open()`/central-directory iteration function that invokes `ProcessCentralDirEntry` in a loop (grep for the calling loop returned no results within the iteration budget), so I cannot confirm the exact outer loop bound or produce a concrete JUnit/shell reproduction here. This should be validated with a crafted ZIP/JAR whose central directory entry declares an `extra_field_length` that is not a multiple of a single record's `4 + data_size`, feeding it through the `ijar` binary (`third_party/ijar/ijar.cc` or equivalent) and confirming a crash or read past `MappedInputFile::Length()` under ASan.

bool InputZipFile::ProcessCentralDirEntry(const u1 *&p, u8 *compressed_size,
                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
  const u1 *extra_p = p;
  p += extra_field_length;
  while (extra_p != p) {
    const u2 header_id = get_u2le(extra_p);
    const u2 data_size = get_u2le(extra_p);
    const u1 *extra = extra_p;
    extra_p += data_size;
    if (header_id == ZIP64_EXTRA_FIELD_TAG) {
      if (*uncompressed_size == U4_MAX) {
        *uncompressed_size = get_u8le(extra);
      }
      if (*compressed_size == U4_MAX) {
        *compressed_size = get_u8le(extra);
      }
      if (*offset == U4_MAX) {
        *offset = get_u8le(extra);
      }
    }
  }
  p += file_comment_length;
  return true;
}
