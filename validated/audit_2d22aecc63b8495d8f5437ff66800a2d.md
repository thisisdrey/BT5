### Title
StackerDB `write_freq` rate limit is parsed and stored but never enforced on chunk writes, letting any single valid slot-signer flood the network with unthrottled StackerDB writes - (File: `stackslib/src/net/stackerdb/db.rs`)

### Summary
`StackerDBConfig::write_freq` documents a minimum wall-clock time that must elapse between writes to the same slot, and the schema records a `write_time` per slot for exactly this purpose. However, the only function that actually gates a chunk write, `StackerDBTx::try_replace_chunk`, never reads `config.write_freq` or compares it against the stored `slot_validation.write_time`. Any principal holding a valid signing key for a slot can therefore write to that slot as fast as the network will accept the requests, and each accepted write is broadcast/gossiped to the DB's peer replicas, bypassing the intended throttle entirely.

### Finding Description
`StackerDBConfig` documents the field as a real limiting control: [1](#0-0) 

The schema stores a `write_time` per chunk specifically to support enforcing that limit: [2](#0-1) 

and `SlotValidation` exposes it back to callers: [3](#0-2) 

But the write path, `try_replace_chunk`, only checks chunk size, slot existence, signer validity, staleness (`slot_version <= slot_validation.version`), and `max_writes`. It never checks `slot_validation.write_time + config.write_freq` against the current time before calling `insert_chunk`: [4](#0-3) 

`insert_chunk` unconditionally records the new `write_time` but performs no throttling itself either: [5](#0-4) 

The peer-push validation path (`validate_received_chunk`) explicitly documents that it intentionally skips the write-frequency check, deferring to "the caller": [6](#0-5) 

But the actual write-committing function it defers to — `try_replace_chunk` — is the one shown above that never performs this check either. The unauthenticated HTTP endpoint that ultimately calls `try_replace_chunk` for a live node is `POST /v2/stackerdb/{principal}/{contract_name}/chunks`, which requires only a chunk within the size cap and a version/signature that verifies against the slot's registered signer — no write-frequency gate is applied along that path: [7](#0-6) 

This is structurally the same bug class as the reported issue: a rate-limiting invariant (`per-user/global withdraw limit` there, `write_freq` here) is defined and even partially tracked in state (`write_time`/`lastXPeriodReset`), but the enforcement branch that should compare "now" against "last write + limit" is missing from the function that actually commits the write. As in the original report, this "if-branch never checked" pattern lets a legitimate, authorized actor (a slot's rightful signer, analogous to the "whale" who legitimately owns collateral) act far outside the throughput the system was designed to allow, because the check simply doesn't exist on the enforcement path.

### Impact Explanation
StackerDB chunk writes are eventually re-broadcast/gossiped to all peer replicas that mirror the same contract's DB, per the module's own design description ("newly-discovered chunks are stored to the node's local replica and broadcast to a subset of neighbors who also replicate the given StackerDB"): [8](#0-7) 

Because `write_freq` is never enforced, a single slot owner (which in many StackerDB configurations, e.g. signer-set StackerDBs, is one of many parties with write access — not the node operator) can submit valid, correctly-signed writes at whatever rate the local node's HTTP endpoint and connection limits allow, well beyond the interval the contract-configured `write_freq` intended to permit. Every accepted write is then re-propagated to all replicating peers, amplifying one writer's local request rate into network-wide storage churn and gossip bandwidth across every node that mirrors that StackerDB (e.g. signer-set/miner-coordination StackerDBs). This is a bounded-but-unenforced write-throttle bypass that degrades availability/bandwidth of the StackerDB replication network, closest to the "bounded compute DoS" / resource-exhaustion category — though it is somewhat attenuated by the fact that the actor must already hold a legitimate slot-signing key rather than being a fully unauthenticated attacker.

### Likelihood Explanation
High, for any party who is a legitimate signer for at least one StackerDB slot (a common role — e.g. any signer participating in a signer-set StackerDB used for coordination). No special privilege beyond ordinary slot-write access, no race condition, and no exotic setup are required: the caller only needs to increment `slot_version` and re-sign on each request and submit as fast as the RPC endpoint accepts requests. The missing check is unconditional and always reachable via the public POST-chunk RPC.

### Recommendation
In `StackerDBTx::try_replace_chunk` (`stackslib/src/net/stackerdb/db.rs`), add an explicit `write_freq` gate before calling `insert_chunk`: reject (with a dedicated error, e.g. `net_error::TooFrequentWrites`) any write where `get_epoch_time_secs() < slot_validation.write_time + self.config.write_freq`. Mirror this in whichever sync-side code path commits downloaded/pushed chunks if it also bypasses `try_replace_chunk`, so that `write_freq` is uniformly enforced on every code path that can commit a chunk to the DB.

### Proof of Concept
1. Set up a StackerDB contract with `write-freq: u3600` (i.e., writes to the same slot are meant to be at most once per hour) and register `privk1` as the signer for slot 1, as in the existing test harness (`TestRPC` / `TEST_CONTRACT_ID`).
2. As `privk1`, issue repeated `POST /v2/stackerdb/{addr}/{contract}/chunks` requests to slot 1, each time incrementing `slot_version` and re-signing with `privk1` (exactly as `test_request_ok` in `stackslib/src/net/api/tests/poststackerdbchunk.rs` does for two consecutive writes): [9](#0-8) 
3. Observe that every request is accepted immediately (`resp.accepted == true`) regardless of how little time has elapsed since the previous write, because `try_replace_chunk` never inspects `slot_validation.write_time` or `self.config.write_freq` [4](#0-3) 
4. Each of these writes is a candidate for gossip/broadcast to all peers replicating this StackerDB, so the signer can drive unthrottled write/broadcast traffic across the replication set indefinitely, in direct violation of the configured `write_freq` throttle.

    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
