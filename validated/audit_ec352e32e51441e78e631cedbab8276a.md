Based on my research, I found a concrete analog in Bazel's C++ ZIP/JAR parsing code (`third_party/ijar/zip.cc`), which is architecturally the closest match to Pillow's `ImagingLibTiffDecode` buffer overflow class — untrusted-format decoding in native code, driven by attacker-controlled length fields.

### Title
Out-of-bounds read in `InputZipFile::ProcessCentralDirEntry` due to unchecked attacker-controlled length fields - (File: third_party/ijar/zip.cc)

### Summary
`ijar` (bundled at `third_party/ijar/zip.cc`) is Bazel's native C++ tool for reading JAR/ZIP files to generate interface JARs and to repackage JARs (`singlejar` reuses similar zip-parsing logic). This code parses ZIP central-directory records from memory-mapped, attacker-suppliable JAR files (e.g., JARs served by an untrusted HTTP mirror/registry and pinned via `http_jar`/`http_file`/Maven coordinates, whose sha256 only guarantees byte-for-byte integrity of the malicious file itself, not the safety of its internal structure).

### Finding Description
`InputZipFile::ProcessCentralDirEntry` reads `file_name_length`, `extra_field_length`, and `file_comment_length` directly from the central directory record and advances the cursor `p` by these attacker-controlled 16-bit values without ever validating them against the mapped file's remaining size: [1](#0-0) 

Unlike the local-file-header parser (`ReadLocalFileHeader`), which calls `EnsureRemaining(...)` before consuming `file_name_length_`/`extra_field_length_`: [2](#0-1) 

`ProcessCentralDirEntry` has no equivalent bounds check. The subsequent extra-field loop then walks `extra_p` using an attacker-controlled `data_size` and `header_id`, checking only `extra_p != p` for loop termination: [3](#0-2) 

If `data_size` values don't sum exactly to `extra_field_length`, `extra_p` can overshoot `p`, spin past the end of the memory-mapped input file, and cause `get_u2le`/`get_u8le` to dereference unmapped or out-of-bounds heap memory. This function is invoked in a `while (true)` loop from `CalculateOutputLength()`: [4](#0-3) 

with no upper bound tying iteration count or length fields back to the actual mapped file size, so a crafted, oversized `file_name_length`/`extra_field_length`/`file_comment_length` in a single malicious central-directory entry is sufficient to walk the read pointer arbitrarily far past the mapped region.

### Impact Explanation
This is a memory-safety violation (out-of-bounds read, CWE-119 class) in native C++ code that processes externally-supplied JAR bytes. Depending on heap layout, it can crash the build (denial of service is excluded per rules, but the underlying primitive is an uncontrolled OOB read that can also feed corrupted size values into subsequent buffer allocations/copies in `CalculateOutputLength`, risking undersized/oversized allocations and further memory corruption in downstream copy operations) — directly analogous to the Pillow `ImagingLibTiffDecode` overflow where a crafted length field in the file format was trusted without bounds validation.

### Likelihood Explanation
An unprivileged attacker who controls the content of a JAR fetched by a build (via `http_jar`, `http_archive` unpacking a JAR, a compromised/malicious Maven artifact mirror, etc.) can trivially craft such a central directory entry. A pinned sha256 checksum does not mitigate this, since the hash validates that the exact malicious bytes were downloaded — it says nothing about the internal structural safety of those bytes once ijar parses them.

### Recommendation
Add the same `EnsureRemaining`-style bounds validation used in `ReadLocalFileHeader` to `ProcessCentralDirEntry` for `file_name_length`, `extra_field_length`, and `file_comment_length` before advancing `p`, and change the extra-field loop condition from `extra_p != p` to `extra_p < p` with an additional check that `data_size` doesn't cause `extra_p` to exceed `p` or the mapped file's end.

### Proof of Concept
A `BuildIntegrationTestCase`/`src/test/shell/bazel` reproduction would: 1) construct a minimal ZIP whose central directory contains one entry with `file_name_length`/`extra_field_length` fields set so their sum exceeds the actual remaining bytes in the file (e.g., set to `0xFFFF` in a tiny file), 2) feed this file to the `ijar` binary (or a rule using `java_import`/interface-jar generation), and 3) observe a crash/ASan out-of-bounds-read report in `ProcessCentralDirEntry`, matching the pattern of `zip_test.cc`-style fuzz/corruption tests already present in `third_party/ijar`. bool InputZipFile::ProcessCentralDirEntry(const u1 *&p, u8 *compressed_size,
                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
  const u1 *extra_p = p;
  p += extra_field_length;
  while (extra_p != p) {
    const u2 header_id = get_u2le(extra_p);
    const u2 data_size = get_u2le(extra_p);
    const u1 *extra = extra_p;
    extra_p += data_size;
    if (header_id == ZIP64_EXTRA_FIELD_TAG) {
      if (*uncompressed_size == U4_MAX) {
        *uncompressed_size = get_u8le(extra);
      }
      if (*compressed_size == U4_MAX) {
        *compressed_size = get_u8le(extra);
      }
      if (*offset == U4_MAX) {
        *offset = get_u8le(extra);
      }
    }
  }
  p += file_comment_length;
  return true;
}
