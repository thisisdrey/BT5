### Title
Inconsistent reward computation between `VoteRewardUtil` (TVM contract path) and `MortgageService` (EOA path) can cause TVM-voting contract accounts to permanently under-report/lose vote rewards - (File: `actuator/src/main/java/org/tron/core/vm/utils/VoteRewardUtil.java`)

### Summary
`VoteRewardUtil.computeReward` (used by the `WITHDRAWREWARD` / `REWARDBALANCE` TVM precompiles for smart-contract accounts that vote via TVM) always computes the reward using the VI (`accumulatedRewardsPerShare`-style) formula for every cycle range, with no awareness of the network's `newRewardAlgorithmEffectiveCycle`. `MortgageService.computeReward` — the equivalent logic used for ordinary EOA `WithdrawBalanceContract` reward queries/withdrawals — explicitly splits the cycle range at `newAlgorithmCycle`, using the old share-based formula (`getOldReward`) for cycles prior to the switch and the VI-based formula only after it. This mirrors the reported pattern of two parallel reward-computation functions that are supposed to represent the same accounting but diverge, producing understated/stale results from one of them.

### Finding Description
`VoteRewardUtil.computeReward` unconditionally walks `beginCycle`..`endCycle` and derives the reward purely from `DelegationStore.getWitnessVi` deltas: [1](#0-0) 

By contrast, `MortgageService.computeReward` explicitly branches on `newAlgorithmCycle` and uses `getOldReward` (share-ratio based, or `rewardViCalService.getNewRewardAlgorithmReward` if `allowOldRewardOpt` is on) for the pre-switch portion of the range, only using the VI delta approach for cycles at/after the switch: [2](#0-1) [3](#0-2) 

The VI values for cycles prior to `newRewardCalStartCycle` are only backfilled asynchronously by `RewardViCalService.startRewardCal()`/`accumulateWitnessVi`, and only once `isDone()` becomes true: [4](#0-3) 

`VoteRewardUtil.withdrawReward`/`queryReward` (reached via the `WithdrawRewardProcessor` native contract and the `RewardBalance` precompile, both callable by any contract during a normal transaction) call `computeReward` without ever checking whether the VI backfill has completed for the relevant cycle range, unlike `MortgageService`'s more careful `getOldReward` branch: [5](#0-4) [6](#0-5) 

If a contract account's `beginCycle` precedes `newRewardCalStartCycle` (e.g., on a private/consortium chain, or any deployment where TVM voting is enabled before/around the point the "new reward algorithm" cycle is set, or before `RewardViCalService` finishes its backfill), `getWitnessVi` for those early cycles can be zero/absent, so `deltaVi.signum() <= 0` causes the loop to `continue`, silently dropping the reward contribution for that cycle instead of falling back to the true share-based reward the way `MortgageService` does.

### Impact Explanation
After `VoteRewardUtil.withdrawReward` runs, `beginCycle` is unconditionally advanced past the computed range: [7](#0-6) 
Any reward silently dropped due to the missing/backfilling VI values is permanently unrecoverable, because the account's `beginCycle` bookkeeping has already moved forward and the stale, understated amount was already credited via `adjustAllowance`. This is a direct loss-of-funds condition for contract accounts using the TVM `VOTEWITNESS`/`WITHDRAWREWARD` flow, and it is reachable purely through ordinary, unprivileged contract deployment and invocation (freeze, vote, and call `WITHDRAWREWARD`/`REWARDBALANCE` from a deployed contract) — no special privilege is required.

### Likelihood Explanation
On current mainnet, this is unlikely to trigger because `allowTvmVote` was activated well after the network's new-reward-algorithm cycle switch and VI backfill had already completed, so contract accounts' `beginCycle` values will normally be at/after `newRewardCalStartCycle`. However, on any chain (private/consortium/testnet, or a future network bootstrapped with different proposal ordering) where TVM voting is enabled before the VI backfill finishes or before the algorithm-switch cycle is reached, the divergence is directly exploitable/triggerable by ordinary users, resulting in silent, permanent reward loss for contract-voter accounts.

### Recommendation
Make `VoteRewardUtil.computeReward` mirror `MortgageService.computeReward`'s cycle-range handling: branch on `newRewardAlgorithmEffectiveCycle`/`allowOldRewardOpt` and fall back to the share-based (`getReward`/`getWitnessVote` ratio) computation for cycles prior to the switch, exactly as `MortgageService` does, rather than assuming VI is always populated for the full cycle range.

### Proof of Concept
1. Deploy/configure a java-tron network where `allowTvmVote` is enabled at genesis (or `newRewardAlgorithmEffectiveCycle`/`RewardViCalService` backfill has not yet completed).
2. Deploy a contract, freeze TRX for tron power, and vote for a witness via the contract in an early cycle (`beginCycle < newRewardCalStartCycle`), earning real block/vote rewards recorded via `DelegationStore.addReward`/`getWitnessVote`.
3. From the contract, call the `WITHDRAWREWARD` native contract (via `WithdrawRewardProcessor.execute` → `VoteRewardUtil.withdrawReward`) or `REWARDBALANCE` precompile (`PrecompiledContracts.RewardBalance` → `VoteRewardUtil.queryReward`).
4. Because `VoteRewardUtil.computeReward` only reads `DelegationStore.getWitnessVi` (which is unset/zero for the un-backfilled early cycle), `deltaVi.signum() <= 0` causes the reward for that cycle to be skipped, returning/withdrawing an amount less than the true share-based reward that `MortgageService.queryReward`/`withdrawReward` would compute for an equivalent EOA voter in the same cycles.
5. `beginCycle` is advanced past the affected cycles regardless, permanently forfeiting the difference.

  private static long computeReward(long beginCycle, long endCycle,
                                    AccountCapsule accountCapsule, Repository repository) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    for (Protocol.Vote vote : accountCapsule.getVotesList()) {
      byte[] srAddress = vote.getVoteAddress().toByteArray();
      BigInteger beginVi = repository.getDelegationStore().getWitnessVi(beginCycle - 1, srAddress);
      BigInteger endVi = repository.getDelegationStore().getWitnessVi(endCycle - 1, srAddress);
      BigInteger deltaVi = endVi.subtract(beginVi);
      if (deltaVi.signum() <= 0) {
        continue;
      }
      long userVote = vote.getVoteCount();
      reward += deltaVi.multiply(BigInteger.valueOf(userVote))
          .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
    }
    return reward;
  }

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }

  private long getOldReward(long begin, long end, List<Pair<byte[], Long>> votes) {
    if (dynamicPropertiesStore.allowOldRewardOpt()) {
      return rewardViCalService.getNewRewardAlgorithmReward(begin, end, votes);
    }
    long reward = 0;

  private void accumulateWitnessReward(byte[] witness) {
    long startCycle = 1;
    LongStream.range(startCycle, newRewardCalStartCycle)
        .forEach(cycle -> accumulateWitnessVi(cycle, witness));
  }

  private void accumulateWitnessVi(long cycle, byte[] address) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long voteCount = getWitnessVote(cycle, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }
