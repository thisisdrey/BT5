The reported CVE (GHSA-mf92-479x-3373) describes a Spring Security-specific defect where its servlet filter chain (e.g., `HeaderWriterFilter`/`OncePerRequestFilter` ordering) can skip invoking header-writing filters under certain dispatch conditions, causing security headers to be omitted from a response. This is a bug in Spring's filter-chain composition logic, not a generic "HTTP headers not written" primitive.

The Go repository (`Kohvert/go--021`) is the Go standard library/toolchain itself, and it has no analogous filter-chain architecture. Go's `net/http` package writes headers directly in the response path via `(*response).WriteHeader` and `chunkWriter.writeHeader`, which are called unconditionally from `(*response).write` whenever the handler writes body data [1](#0-0) , and there's no middleware/filter-ordering concept where a header-setting component could be silently bypassed the way Spring Security filters can be. The closest related logic — handling of superfluous `WriteHeader` calls, hijacked connections, and informational (1xx) headers — is explicit and tested (e.g. `TestWriteHeaderNoCodeCheck`, `TestHeaderToWire`) [2](#0-1) [3](#0-2) , and does not reproduce the "headers silently skipped under some conditions" primitive described in the advisory.

No concrete, reproducible analog exists in this repository's production `net/http` (or related) code that matches the primitive of security-relevant headers being conditionally dropped due to a broken filter/middleware invocation chain.
