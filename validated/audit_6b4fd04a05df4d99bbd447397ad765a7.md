### Title
Rich adversary can grief bandwidth/energy allocation of all other frozen stakers by flash-manipulating `TotalNetWeight`/`TotalEnergyWeight` within a single block - (File: chainbase/src/main/java/org/tron/core/db/BandwidthProcessor.java, chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java, actuator/src/main/java/org/tron/core/actuator/FreezeBalanceV2Actuator.java, actuator/src/main/java/org/tron/core/actuator/UnfreezeBalanceV2Actuator.java)

### Summary
Every account's free bandwidth/energy allowance is computed on-the-fly for each transaction as a proportional share of a chain-wide pool: `accountWeight * totalLimit / totalWeight`. `totalWeight` (`TotalNetWeight`/`TotalEnergyWeight`) is a global mutable counter that any unprivileged account can inflate by freezing a large amount of TRX, and then deflate again immediately by unfreezing — all within the same block, before any other transaction relying on the old ratio has a chance to be favorably evaluated. This lets a well-funded attacker transiently dilute every other staker's bandwidth/energy quota in a given block, causing their bandwidth/energy-funded transactions to fail or fall back to paying TRX fees, mirroring the JUSD report's "sandwich a global cap check within one block, reverse for free" pattern.

### Finding Description
`BandwidthProcessor.calculateGlobalNetLimit` and `EnergyProcessor.calculateGlobalEnergyLimit` compute an account's resource allowance using the current, mutable `TotalNetWeight`/`TotalEnergyWeight` denominator read live from `DynamicPropertiesStore`: [1](#0-0) [2](#0-1) 

These functions are invoked for every transaction inside `useAccountNet`, which is part of `BandwidthProcessor.consume`, itself called by `Manager.consumeBandwidth` on every transaction pushed through `Manager.processTransaction`, reachable from `Wallet.broadcastTransaction` for any signed transaction submitted by any account: [3](#0-2) [4](#0-3) [5](#0-4) 

`TotalNetWeight`/`TotalEnergyWeight` is updated immediately and synchronously whenever `FreezeBalanceV2Actuator` (freeze) or `UnfreezeBalanceV2Actuator`/`UnfreezeBalanceV2Processor` (unfreeze) execute — the weight change happens at the moment of freeze/unfreeze, independent of the multi-day lock that only gates the later withdrawal of the underlying TRX balance: [6](#0-5) [7](#0-6) 

Because both the freeze and the unfreeze transactions can be signed and broadcast by the same attacker and packed into the same block (block producers order transactions, and users can submit both transactions back-to-back), the attacker can:
1. Broadcast `FreezeBalanceV2Contract` with a very large `frozenBalance` for `BANDWIDTH` (or `ENERGY`), instantly inflating `TotalNetWeight`/`TotalEnergyWeight`.
2. While that block is being filled, any other account's transaction that depends on `calculateGlobalNetLimit`/`calculateGlobalEnergyLimit` for its free/staked resource quota will see a diluted allowance (numerator based on victim's own weight is unchanged, but the shared denominator has spiked), pushing the victim toward `useFreeNet`/`useTransactionFee` fallback or outright `AccountResourceInsufficientException`.
3. Broadcast `UnfreezeBalanceV2Contract` for the same amount, instantly restoring `TotalNetWeight`/`TotalEnergyWeight` back down before the next block, since the weight decrement happens at unfreeze-call time, not at withdrawal-expiry time.

This is the same bug class as the JUSD report: a global, shared limit/ratio denominator is recomputed live from state that an attacker can inflate and immediately deflate within one block, griefing every other legitimate participant relying on that shared resource, at essentially no lasting cost (the TRX is only temporarily locked pending the standard unfreeze waiting period, not spent).

### Impact Explanation
An attacker with sufficient TRX can, for the cost of temporarily staking/unstaking funds (no fee, no permanent loss), repeatedly dilute the bandwidth/energy allowance of all other frozen-balance stakers in the same block. Victims whose transactions depend on their proportional share of `TotalNetLimit`/`TotalEnergyCurrentLimit` may have their free-resource-funded transactions fail (`AccountResourceInsufficientException`) or be forced to burn TRX as fees they otherwise wouldn't need to pay. This is a chain-wide griefing vector against any account relying on frozen-resource allowances, and can be repeated block after block since the freeze/unfreeze cycle carries no fee (`calcFee()` returns 0 for both actuators).

### Likelihood Explanation
Both `FreezeBalanceV2Contract` and `UnfreezeBalanceV2Contract` are ordinary, unprivileged, broadcastable transaction types available to any account holding TRX; no special permission is required. The attack only requires enough TRX to meaningfully move `TotalNetWeight`/`TotalEnergyWeight` and the ability to get two of its own transactions (freeze, unfreeze) included in the same or adjacent blocks — a routine capability for any wallet/API client.

### Recommendation
Avoid using a live, per-transaction snapshot of `TotalNetWeight`/`TotalEnergyWeight` that can be inflated and deflated within a single block. Consider: (a) freezing the denominator used for allowance calculations to a value fixed at the start of the block/epoch rather than the instantaneous value; (b) enforcing a minimum holding period before a freeze's weight can be reversed by unfreeze (decoupling the weight update from the funds-lock delay so weight changes also respect a cooldown); or (c) rate-limiting/capping how much `TotalNetWeight`/`TotalEnergyWeight` can change from freeze/unfreeze actions within one block.

### Proof of Concept
1. Attacker account A holds a large TRX balance and observes current `TotalNetWeight` (`W`) and `TotalNetLimit` (`L`).
2. A broadcasts `FreezeBalanceV2Contract{ownerAddress=A, frozenBalance=X, resource=BANDWIDTH}`. `FreezeBalanceV2Actuator.execute` immediately calls `dynamicStore.addTotalNetWeight(X/TRX_PRECISION)`, so `TotalNetWeight` becomes `W + X/TRX_PRECISION` for the remainder of the block (see lines 60-72 of `FreezeBalanceV2Actuator.java`).
3. Victim account V, holding frozen balance `Vf` for bandwidth, broadcasts an ordinary transaction in the same block. `BandwidthProcessor.useAccountNet` calls `calculateGlobalNetLimit(V)`, which now returns `Vf/TRX_PRECISION * L / (W + X/TRX_PRECISION)` — smaller than before A's freeze — potentially causing V's transaction to fail bandwidth coverage and fall through to `useFreeNet`/`useTransactionFee`, or throw `AccountResourceInsufficientException` if V has no spare TRX.
4. A broadcasts `UnfreezeBalanceV2Contract{ownerAddress=A, unfreezeBalance=X, resource=BANDWIDTH}` in the same block (or next). `UnfreezeBalanceV2Processor.updateTotalResourceWeight` immediately calls `repo.addTotalNetWeight(-(X/TRX_PRECISION))`, restoring `TotalNetWeight` to `W`, while A's TRX is merely queued in the standard unfreeze-withdraw list to be reclaimed later — no fee was paid and no funds were lost, only temporarily locked.
5. Repeat every block to persistently grief resource-based transactions of all other stakers.

  public long calculateGlobalNetLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForBandwidth();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalNetLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long totalNetLimit = chainBaseManager.getDynamicPropertiesStore().getTotalNetLimit();
    long totalNetWeight = chainBaseManager.getDynamicPropertiesStore().getTotalNetWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalNetWeight <= 0) {
      return 0;
    }
    if (totalNetWeight == 0) {
      return 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalNetLimit, totalNetWeight);
    }
    long netWeight = frozeBalance / TRX_PRECISION;
    return (long) (netWeight * ((double) totalNetLimit / totalNetWeight));
  }

  public void updateTotalResourceWeight(AccountCapsule accountCapsule,
                                        Common.ResourceCode freezeType,
                                        long unfreezeBalance,
                                        Repository repo) {
    switch (freezeType) {
      case BANDWIDTH:
        long oldNetWeight = accountCapsule.getFrozenV2BalanceWithDelegated(BANDWIDTH) / TRX_PRECISION;
        accountCapsule.addFrozenBalanceForBandwidthV2(-unfreezeBalance);
        long newNetWeight = accountCapsule.getFrozenV2BalanceWithDelegated(BANDWIDTH) / TRX_PRECISION;
        repo.addTotalNetWeight(newNetWeight - oldNetWeight);
        break;
      case ENERGY:
        long oldEnergyWeight = accountCapsule.getFrozenV2BalanceWithDelegated(ENERGY) / TRX_PRECISION;
        accountCapsule.addFrozenBalanceForEnergyV2(-unfreezeBalance);
        long newEnergyWeight = accountCapsule.getFrozenV2BalanceWithDelegated(ENERGY) / TRX_PRECISION;
        repo.addTotalEnergyWeight(newEnergyWeight - oldEnergyWeight);
        break;
      case TRON_POWER:
        long oldTPWeight = accountCapsule.getTronPowerFrozenV2Balance() / TRX_PRECISION;
        accountCapsule.addFrozenForTronPowerV2(-unfreezeBalance);
        long newTPWeight = accountCapsule.getTronPowerFrozenV2Balance() / TRX_PRECISION;
        repo.addTotalTronPowerWeight(newTPWeight - oldTPWeight);
        break;
      default:
        //this should never happen
        break;
    }
  }
