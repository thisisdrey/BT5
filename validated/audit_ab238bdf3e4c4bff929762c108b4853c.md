### Title
Unauthenticated event injection into `stacks-signer` via `SignerEventReceiver` HTTP listener — ([File: libsigner/src/events.rs])

### Summary
`SignerEventReceiver::next_event` in `libsigner/src/events.rs` accepts and processes `POST` requests on `/stackerdb_chunks`, `/proposal_response`, `/new_burn_block`, and `/new_block` from any TCP client that can reach the bound socket, with no verification that the request actually originated from the paired Stacks node. This is the same bug class as CVE-2023-26114 (missing peer/origin validation on an inbound transport, allowing an unauthenticated party to inject data into a privileged process).

### Finding Description
The signer's event listener is implemented as: [1](#0-0) 

`next_event` dispatches purely on the HTTP method and URL path — there is no check of source IP, no shared-secret/token header, no TLS client cert, nothing that ties the request to the configured Stacks node. Any of the four dispatch branches (`/stackerdb_chunks`, `/proposal_response`, `/new_burn_block`, `/new_block`) will happily deserialize attacker-supplied JSON into a `SignerEvent<T>` via `process_event`: [2](#0-1) 

The only "secret" in the signer/node pairing (`auth_password` / `auth_token`) is used for the outbound direction — the signer authenticating to the node's RPC/block-proposal endpoint — not for the node authenticating to the signer's inbound event listener: [3](#0-2) 

Sample/reference configs explicitly show the signer's event-receiver `endpoint` bound to `0.0.0.0`, i.e., all interfaces, not just loopback: [4](#0-3) 

This breaks the equality "event genuinely emitted by the paired Stacks node" vs. "any bytes POSTed to this socket by anyone who can reach it." Since `bind()` just wraps `tiny_http::Server::http(listener)` with no ACL: [5](#0-4) 

there is no origin validation analogous to the WebSocket handshake check missing in the code-server advisory — the transport accepts data from anyone who can open a TCP connection to the port, exactly as unvalidated WS origin allowed cross-origin pages to talk to code-server.

### Impact Explanation
An attacker who can reach the signer's listening port (exposed per sample configs on `0.0.0.0`, and plausible in real deployments where the signer runs on a separate host from the node) can forge `StackerDBChunksEvent`, `BlockValidateResponse`, burn-block, and new-block payloads and feed them directly into the signer's runloop input channel, bypassing every check the node normally performs before emitting these events (including StackerDB chunk signature verification, which happens on the node side before the event is ever POSTed). This is an unauthenticated write into the signer process's event stream — a network-reachable component whose correctness underpins block signing.

### Likelihood Explanation
Exploitability only requires TCP reachability to the configured event-receiver port; no credentials, no node-side compromise, and no privileged position are needed. The severity is bounded by how the events are subsequently consumed by the signer runloop, which is explicitly out of scope for this scan, but the transport-level gap itself is real and directly analogous to the reported bug class.

### Recommendation
Require the node to authenticate to the signer's event endpoint (e.g., reuse/extend the existing `auth_password`/`auth_token` mechanism to also gate inbound POSTs, similar to how it gates the signer's outbound RPC calls), or at minimum enforce a source-IP allowlist/loopback-only bind by default, and reject unauthenticated requests before deserializing into `SignerEvent`.

### Proof of Concept
1. Deploy a signer using a config such as `sample/conf/signer/mainnet-signer-conf.toml` with `endpoint = "0.0.0.0:30000"`.
2. From a remote host with network access to port 30000, send:
```
POST /stackerdb_chunks HTTP/1.1
Host: <signer-ip>:30000
Content-Type: application/json
Content-Length: <n>

{"contract_id": "...", "modified_slots": [...forged chunk...]}
```
3. `SignerEventReceiver::next_event` (libsigner/src/events.rs, lines 437-438) forwards this straight to `process_event::<T, StackerDBChunksEvent>` with no verification that it came from the paired node, and the resulting `SignerEvent` is delivered to the signer runloop via `forward_event`.

```rust
    fn next_event(&mut self) -> Result<SignerEvent<T>, EventError> {
        self.with_server(|event_receiver, http_server, _is_mainnet| {
            // were we asked to terminate?
            if event_receiver.is_stopped() {
                return Err(EventError::Terminated);
            }
            debug!("Request handling");
            let request = http_server.recv()?;
            debug!("Got request"; "method" => %request.method(), "path" => request.url());

            if request.url() == "/status" {
                request
                .respond(HttpResponse::from_string("OK"))
                .expect("response failed");
                return Ok(SignerEvent::StatusCheck);
            }

            if request.method() != &HttpMethod::Post {
                return Err(EventError::MalformedRequest(format!(
                    "Unrecognized method '{}'",
                    request.method(),
                )));
            }
            debug!("Processing {} event", request.url());
            if request.url() == "/stackerdb_chunks" {
                process_event::<T, StackerDBChunksEvent>(request)
            } else if request.url() == "/proposal_response" {
                process_event::<T, BlockValidateResponse>(request)
            } else if request.url() == "/new_burn_block" {
                process_event::<T, BurnBlockEvent>(request)
            } else if request.url() == "/shutdown" {
                event_receiver.stop_signal.store(true, Ordering::SeqCst);
                Err(EventError::Terminated)
            } else if request.url() == "/new_block" {
                process_event::<T, StacksBlockEvent>(request)
            } else {
                let url = request.url().to_string();
                debug!(
                    "[{:?}] next_event got request with unexpected url {}, return OK so other side doesn't keep sending this",
                    event_receiver.local_addr,
                    url
                );
                ack_dispatcher(request);
                Err(EventError::UnrecognizedEvent(url))
            }
        })?
```

```rust
fn process_event<T, E>(mut request: HttpRequest) -> Result<SignerEvent<T>, EventError>
where
    T: SignerEventTrait,
    E: serde::de::DeserializeOwned + TryInto<SignerEvent<T>, Error = EventError>,
{
    let mut body = String::new();

    if let Err(e) = request.as_reader().read_to_string(&mut body) {
        error!("Failed to read body: {:?}", &e);
        ack_dispatcher(request);
        return Err(EventError::MalformedRequest(format!(
            "Failed to read body: {:?}",
            e
        )));
    }
    // Regardless of whether we successfully deserialize, we should ack the dispatcher so they don't keep resending it
    ack_dispatcher(request);
    let json_event: E = serde_json::from_slice(body.as_bytes())
        .map_err(|e| EventError::Deserialize(format!("Could not decode body to JSON: {:?}", e)))?;

    let signer_event: SignerEvent<T> = json_event.try_into()?;

    Ok(signer_event)
}
```
