### Title
ML-DSA delegate signature verification compute mis-charged to signer shard instead of receiver shard when `fix_ml_dsa_cost_charging` is disabled - (File: runtime/runtime/src/actions.rs, runtime/runtime/src/config.rs)

### Summary
When `apply_state.config.wasm_config.fix_ml_dsa_cost_charging` is `false`, `apply_delegate_action` in `runtime/runtime/src/actions.rs` skips adding `delegate_signature_verification_compute` to `result.compute_usage` on the receiver shard before calling `signed_delegate_action.verify()`, while `signature_verification_cost` in `runtime/runtime/src/config.rs` zeroes out the inner delegate's compute contribution at transaction-conversion time whenever `meter_inner_verify_on_receiver` (i.e. the same flag) is true — but under the *pre-fix* path the inner compute is instead fully charged to the signer's `tx_cost` computation, not the receiver shard where `verify()` actually executes.

### Finding Description
`apply_delegate_action` (`runtime/runtime/src/actions.rs:437-461`) contains an explicit conditional: only if `fix_ml_dsa_cost_charging` is enabled does it add `delegate_signature_verification_compute(&apply_state.config.fees, signed_delegate_action.delegate_action().public_key())` to `result.compute_usage` *before* calling `signed_delegate_action.verify()` on the receiver shard [1](#0-0) . When the flag is disabled, this receiver-side compute accounting is entirely skipped even though `verify()` (the actual ML-DSA signature check) still executes on this shard right afterward [2](#0-1) .

Correspondingly, in `runtime/runtime/src/config.rs`, `signature_verification_cost` computes the send-side (signer-shard) cost added during `tx_cost`/`calculate_tx_cost`. For each inner `Delegate`/`DelegateV2` action, it looks up the full `ParameterCost` (gas + compute) for the inner signer's key type, and only zeroes the compute component (`cost = ParameterCost { compute: 0, ..cost }`) when `meter_inner_verify_on_receiver` (same `fix_ml_dsa_cost_charging` flag) is true [3](#0-2) . When the flag is false, the full compute cost (not just gas) is added to the signer shard's `tx_cost` calculation — even though that shard never executes the ML-DSA `verify()` call for the inner delegate action; only gas is meant to be pre-paid there economically, while wall-clock compute should track where the work happens, per the code's own comments <cite repo="ThankGodontt/nearcore--024" path="runtime/runtime/src/config.rs" start="525="541" /> [4](#0-3) .

This creates the mis-charging described in the question: under the pre-fix path, `apply_delegate_action`'s receiver-shard `result.compute_usage` never reflects the ML-DSA delegate signature verification compute, while `tx_cost`'s signer-shard compute total incorrectly includes it. Compute accounting is used by `process_receipts`/chunk application to enforce `compute_limit` per shard per chunk; since the receiver shard's accounted compute for these receipts is understated relative to the real CPU cost of running ML-DSA `verify()`, an attacker who submits many `DelegateActionV2` relayed transactions with ML-DSA-signed inner keys targeting one receiver shard can cause that shard to perform verification work exceeding what its accounted compute budget reflects, since the actual heavy verification runs on the receiver but its accounting bill was left on the signer side.

### Impact Explanation
This is a compute-metering/liveness issue, not a fund-theft or consensus-divergence bug: the mischarge is deterministic and protocol-version-gated (all validators for a given block use the same `fix_ml_dsa_cost_charging` value derived from the protocol config, so state transition remains agreed-upon and there's no state-root divergence). The scoped impact is that a receiver shard's real verification workload can exceed its `compute_limit`-based throttle under the legacy/pre-fix behavior, potentially causing chunk-application slowdown for that shard, i.e. a liveness-degradation category rather than a safety violation.

### Likelihood Explanation
Preconditions require the network still running with `fix_ml_dsa_cost_charging` disabled and the attacker holding/using ML-DSA-65 (`MLDSA65`) access keys, which any ordinary client can generate; DelegateActionV2 relaying is a standard meta-transaction feature. Cost to the attacker is bounded by the (correctly charged, non-zero) gas fee for ML-DSA signature verification burnt at conversion — this is an economic cost, but it does not prevent the compute mis-accounting on the receiver shard. The finding is inherently protocol-version-scoped: it is explicitly guarded by, and only exists in, the "pre-fix" branch, matching the question's framing.

### Recommendation
Ensure `fix_ml_dsa_cost_charging` is enabled protocol-wide before/at the point ML-DSA (post-quantum) keys and `DelegateActionV2` become usable, so the receiver shard always meters `delegate_signature_verification_compute` unconditionally in `apply_delegate_action`, and `signature_verification_cost` always excludes inner-delegate compute from the signer-side charge, matching where `verify()` actually executes.

### Proof of Concept
Extend the existing test module in `runtime/runtime/src/config.rs` (`mod tests`) plus a new test in `runtime/runtime/src/actions.rs` (or a runtime integration test) with a table test enumerating both flag states:
1. Build an `ApplyState` with `fix_ml_dsa_cost_charging = false` and a `DelegateActionV2` whose inner `public_key` is `MLDSA65`, non-zero `signature_verification_costs[MlDsa65].compute`.
2. Call `apply_delegate_action` directly and assert `result.compute_usage` does NOT include `delegate_signature_verification_compute` (reproducing the mis-charge).
3. Call `calculate_tx_cost` for the signer's transaction and assert `compute_burnt` DOES include the inner ML-DSA compute cost (showing it lands on the signer/send side instead).
4. Repeat with `fix_ml_dsa_cost_charging = true` and assert the compute instead appears in `apply_delegate_action`'s `result.compute_usage` (receiver side) and is absent from `calculate_tx_cost`'s `compute_burnt` (signer side), matching the existing `ml_dsa_65_verify_compute_cost_independent_from_gas` test pattern already present [5](#0-4) .

```rust
fn signature_verification_cost(
    fees: &RuntimeFeesConfig,
    signer_public_key: &PublicKey,
    actions: &[Action],
    meter_inner_verify_on_receiver: bool,
) -> Result<ParameterCost, IntegerOverflowError> {
    let costs = &fees.signature_verification_costs;
    let mut total = costs[signature_kind(signer_public_key.key_type())];
    for action in actions {
        if let Some(delegate_action) = delegate_inner_action(action) {
            let kind = signature_kind(delegate_action.public_key().key_type());
            let mut cost = costs[kind];
            if meter_inner_verify_on_receiver {
                cost = ParameterCost { compute: 0, ..cost };
            }
            total = total.checked_add_result(cost)?;
        }
    }
    Ok(total)
}
```
