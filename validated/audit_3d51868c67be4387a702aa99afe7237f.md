### Title
RemoveRepository fails with FailedPrecondition when the repository lock is already held, allowing an in-flight create/import to block emergency deletion - ([File: internal/gitaly/repoutil/remove.go])

### Summary
`repoutil.remove()` (used by `RemoveRepository` RPC) takes an exclusive on-disk lock on the target repository directory before it will delete it. If the lock is already held — by a normal, in-flight repository-creation/import operation, or by a stale `.lock` file — the removal call **immediately fails** with `FailedPrecondition: "repository is already locked"` instead of retrying or waiting. This mirrors the `Vault.blacklistProtocol` bug class: an operation meant to work in an "emergency" (removing/quarantining a bad actor) is gated behind an action that can fail because of external/attacker-influenced state, so the "blacklist"/removal never takes effect and the system cannot recover.

### Finding Description
`repoutil.remove()` calls `Lock()` before renaming/removing the repository directory: [1](#0-0) 

`Lock()` uses `safe.NewLockingFileWriter(path)` to create/acquire a `<repoPath>.lock` file, returning `safe.ErrFileAlreadyLocked` if another process already holds it: [2](#0-1) 

`remove()` translates that error directly into a `FailedPrecondition` for the caller rather than waiting/retrying: [3](#0-2) 

The doc comment on the lock call — *"Lock the repository such that it cannot be created or removed by any concurrent RPC call"* — indicates the same lock path/mechanism is shared with repository-creation flows (`repoutil.Create`, used by `CreateRepository`, `CreateFork`, `CreateRepositoryFromBundle`, `CreateRepositoryFromURL`, `ReplicateRepository`). This is corroborated by the existing test that exercises exactly this failure mode by simulating a concurrent RPC holding the lock file: [4](#0-3) 

Because creation/import RPCs (e.g., `CreateRepositoryFromURL`, `CreateRepositoryFromBundle`, `ReplicateRepository`) can run for an extended, attacker-influenced duration (slow/malicious remote, large or stalled transfer) while holding this same lock, an administrator's attempt to call `RemoveRepository` on that same relative path during that window fails outright. There is no wait/backoff/retry semantics in `remove()` for this specific error — the RPC simply returns `FailedPrecondition` to the caller.

This is directly analogous to the Solidity bug: `blacklistProtocol` first tries `withdrawFromProtocol`, which can revert due to attacker/external-induced state (hack/pause), thereby preventing the protocol from ever being blacklisted. Here, `RemoveRepository` requires acquiring a lock that can be held (accidentally or through crafted, long-running create/import operations) by another actor, thereby preventing the emergency deletion from ever succeeding on the first attempt.

### Impact Explanation
An operator/administrator trying to urgently remove a compromised, abusive, or legally-problematic repository can be blocked as long as the lock is held. Since repository creation/import RPCs are reachable through ordinary write-path operations (fork, import-from-URL, restore/replicate), a low-privileged or malicious client can keep such an operation in flight (e.g., pointing an import at an extremely slow or hanging endpoint) for the same relative path, causing repeated `RemoveRepository` attempts to fail with `FailedPrecondition` during that window. This is a denial-of-service against the `RemoveRepository` RPC handler for a specific, targeted repository at exactly the time removal is most urgently needed.

### Likelihood Explanation
Moderate. It requires the attacker (or an unlucky legitimate operation) to be actively creating/importing/replicating into the same relative path at the moment an operator tries to remove it, and normal replication/backup flows can also transiently hold the lock. It is not a permanent block (the lock is eventually released), but during an active-incident window it directly reproduces the "can't blacklist while it's actively being abused" scenario from the report.

### Recommendation
Add bounded retry/backoff (or a `force`/wait option) to `repoutil.remove()` when it encounters `safe.ErrFileAlreadyLocked`, instead of surfacing an immediate `FailedPrecondition`, so that an admin-driven removal can eventually win the race against an in-flight create/import holding the lock — analogous to the audit's recommendation to decouple "mark disallowed" from "perform the potentially-failing action," or to allow a forced remove path that bypasses/aborts the pending creation.

### Proof of Concept
1. Start (or simulate) a long-running `CreateRepositoryFromURL`/`ReplicateRepository`/`CreateRepositoryFromBundle` call targeting relative path `R`, which acquires the `R.lock` file via `repoutil.Lock` and holds it for the duration of the transfer (attacker controls duration by controlling the remote/import source).
2. While the lock is held, an administrator calls `RemoveRepository` for `R`.
3. `repoutil.remove()` hits `Lock()` at internal/gitaly/repoutil/remove.go:95, receives `safe.ErrFileAlreadyLocked`, and returns `structerr.NewFailedPrecondition("repository is already locked")` immediately — reproduced deterministically by the existing unit test that manually creates the `.lock` file and calls `RemoveRepository`: [4](#0-3) 
4. The administrator's removal request fails and must be retried manually; as long as the attacker keeps a create/import in flight for `R`, the removal continues to fail.

```go
func Lock(ctx context.Context, logger log.Logger, locator storage.Locator, repository storage.Repository) (func(), error) {
	path, err := locator.GetRepoPath(ctx, repository, storage.WithRepositoryVerificationSkipped())
	if err != nil {
		return nil, err
	}

	// Create the parent directory in case it doesn't exist yet.
	if err := os.MkdirAll(filepath.Dir(path), mode.Directory); err != nil {
		return nil, structerr.NewInternal("create directories: %w", err)
	}

	// We're somewhat abusing this file writer given that we simply want to assert that
	// the target directory doesn't exist and isn't created while we want to move the
	// new repository into place. We thus only use the locking semantics of the writer,
	// but will never commit it.
	locker, err := safe.NewLockingFileWriter(path)
	if err != nil {
		return nil, err
	}

	unlock := func() {
		if err := locker.Close(); err != nil {
			logger.WithError(err).ErrorContext(ctx, "closing repository locker failed")
		}
	}

	if err := locker.Lock(); err != nil {
		unlock()

		return nil, err
	}
```

```go
func TestRemoveRepository_locking(t *testing.T) {
	testhelper.SkipWithWAL(t, `
Repository locks are not acquired with transaction management enabled. The test and the locking
logic will be removed once transaction managements is always enabled.`)

	t.Parallel()

	// Praefect does not acquire a lock on repository deletion so disable the test case for Praefect.
	cfg, client := setupRepositoryService(t, testserver.WithDisablePraefect())
	repo, repoPath := gittest.CreateRepository(t, ctx, cfg)

	// Simulate a concurrent RPC holding the repository lock.
	lockPath := repoPath + ".lock"
	require.NoError(t, os.WriteFile(lockPath, []byte{}, mode.File))
	defer func() { require.NoError(t, os.RemoveAll(lockPath)) }()

	_, err := client.RemoveRepository(ctx, &gitalypb.RemoveRepositoryRequest{Repository: repo})
	testhelper.RequireGrpcError(t, structerr.NewFailedPrecondition("repository is already locked"), err)
}
```
