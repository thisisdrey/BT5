### Title
Attached deposit is permanently stuck (never refunded) when `address_check_callback` rejects a direct (non-relayer) caller after the registrar resolves the target address to a real account - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
`address_check_callback` captures the caller's attached deposit in a `CallerDeposit` (only populated for external, i.e. `predecessor_account_id != current_account_id`, callers) so it can be refunded on failure. When the registrar lookup returns `Some(account_id)` and the caller is not using the wallet's own semi-trusted relayer access key (`env::signer_account_id() != current_account_id`), the function returns `PromiseOrValue::Value(ExecuteResponse{success:false,...})` and silently drops `caller_deposit` without creating any transfer-back promise, permanently losing the attached NEAR.

### Finding Description
`CallerDeposit::new` only returns `Some` when the caller is external to the wallet (`predecessor_account_id != current_account_id`), capturing `predecessor_account_id` and `attached_deposit` explicitly for later refund purposes. [1](#0-0) 

In `inner_rlp_execute`, when the transaction is an `EOABaseTokenTransfer` with `address_check: Some(address)`, the contract calls the hardcoded address registrar and schedules `address_check_callback`, forwarding the `caller_deposit` computed earlier. [2](#0-1) 

Inside `address_check_callback`, if the registrar returns `Some(account_id)` (meaning a real named account is already registered for that Ethereum address), the code branches on whether the caller used the wallet's own semi-trusted relayer access key (`env::signer_account_id() == current_account_id`). If it did, it bans that key via `create_ban_relayer_promise`. If not — i.e., the caller submitted the transaction directly using their own NEAR account as both predecessor and signer (self-relaying, which is an explicitly supported mode per the contract's design/comments) — the function immediately returns `PromiseOrValue::Value(ExecuteResponse{success:false,...})`, and `caller_deposit` (which is `Some` in this exact scenario, since `predecessor_account_id != current_account_id`) simply goes out of scope with no transfer promise ever generated: [3](#0-2) 

This is inconsistent with the pattern used elsewhere in the same file: `rlp_execute_callback` explicitly creates a `promise_batch_create` + `promise_batch_action_transfer` refund when a cross-contract call fails, precisely because a NEAR attached deposit in a successfully-executing (non-panicking) function call is *not* automatically refunded by the protocol — only an actual receipt/Wasm panic triggers automatic refund. [4](#0-3) 

Because `address_check_callback` returns a `Value` (no panic, no promise) in the offending branch, the attached deposit that was transferred to the wallet contract as part of the original `FunctionCall` action to `rlp_execute` is retained by the contract's balance forever, with no code path left to claim or return it.

### Impact Explanation
Permanent freezing of user funds: any attached NEAR deposit sent along with a self-submitted `rlp_execute` call that lands in this specific error branch is irrecoverably stuck in the wallet contract's balance. This matches the "permanent freezing of user funds" bounty category. Note the frozen funds belong to the account triggering the call (self, or any external predecessor caller including relayers submitting with their own keys) — it is a real, protocol-level loss-of-funds bug regardless of whether it is triggered maliciously or accidentally by a legitimate user/relayer misconfiguring the `target` parameter.

### Likelihood Explanation
This is trivially and repeatably reachable by any unprivileged account: an attacker (or an honest but careless relayer/user) calls `rlp_execute` directly as both predecessor and signer (not using the wallet's shared relayer access key) with an attached deposit, an RLP-encoded `EOABaseTokenTransfer` whose derived address happens to resolve via the registrar to `Some(account_id)`, and a `target` that does not correctly match. No special privileges, races, or collisions with cryptographic hash pre-images are needed beyond choosing a `to` address that is already a legitimately registered account in the registrar (a normal, discoverable, public piece of state) — which is exactly the condition this code path is designed to detect. Every attempt through this path loses whatever deposit was attached.

### Recommendation
In `address_check_callback`'s `else` branch (`maybe_account_id.is_some()` and `signer_account_id() != current_account_id`), generate an explicit refund promise (`env::promise_batch_create`/`promise_batch_action_transfer`) using `caller_deposit` before returning `PromiseOrValue::Value(...)`, mirroring the refund logic already implemented in `rlp_execute_callback`'s `PromiseResult::Failed` branch. Also audit the `create_ban_relayer_promise` promise chain (`ban_relayer`) to confirm `caller_deposit` doesn't need equivalent handling there.

### Proof of Concept
Integration/unit test plan:
1. Deploy `WalletContract` at an eth-implicit account `wallet.near`, and a mock address registrar contract at the hardcoded `ADDRESS_REGISTRAR_ACCOUNT_ID` that returns `Some("victim.near")` for a chosen address `addr_x`.
2. From an external account `attacker.near` (funded, acting as both predecessor and signer directly, i.e. not using any access key granted by `wallet.near`), call `rlp_execute(target, tx_bytes_b64)` with `attached_deposit = N` yoctoNEAR, where the RLP transaction is crafted so `internal::parse_rlp_tx_to_action` yields `TransactionKind::EthEmulation(EthEmulationKind::EOABaseTokenTransfer{ address_check: Some(addr_x), .. })`.
3. Let the promise chain resolve: `address_registrar.lookup(addr_x)` returns `Some("victim.near")`, driving execution into `address_check_callback` with `env::signer_account_id() == attacker.near != current_account_id (wallet.near)`.
4. Assert the returned value is `ExecuteResponse{success:false, error: Some("Invalid target: ...") }` and, critically, assert there are **no** outgoing transfer receipts from `wallet.near` back to `attacker.near`.
5. Assert `wallet.near`'s account balance retains the `N` yoctoNEAR that `attacker.near` attached, with no future method able to reclaim it — confirming permanent fund freezing.

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
