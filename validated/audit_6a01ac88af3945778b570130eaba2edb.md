### Title
Missing content-hash verification of downloaded attachments allows a malicious peer to inject mismatched attachment content - (File: stackslib/src/net/atlas/download.rs)

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` decodes a peer's `GetAttachmentResponse` and unconditionally inserts `response.attachment` into `self.attachments` without ever comparing `response.attachment.hash()` against the `request.content_hash` that was originally requested. Any peer the node queries for an attachment (any peer in `network.get_outbound_sync_peers()` with a `ReliabilityReport`) can therefore return arbitrary attachment bytes for a given hash, and the node will accept and store them as if they were the correct content.

### Finding Description
The equality that should be enforced is `response.attachment.hash() == request.content_hash`. Tracing the code: [1](#0-0) 

`extend_with_attachments` iterates `results.succeeded`, retrieves the `ReliabilityReport` for the peer via `request.get_url()`, and then calls `response.decode_atlas_get_attachment()`. If that decode succeeds, `response.attachment` is inserted directly into `self.attachments` at line 548, and the peer's `report.bump_successful_requests()` is called — there is no check anywhere in this function comparing the decoded `attachment.hash()` to `request.content_hash`.

`decode_atlas_get_attachment` itself performs no hash validation either — it only parses JSON into a `GetAttachmentResponse`: [2](#0-1) 

Thus a malicious or compromised outbound peer, upon receiving the node's `GET /v2/attachments/{content_hash}` request, can respond with a well-formed `GetAttachmentResponse{ attachment: Attachment{ content: <attacker bytes> } }` whose content hashes to some `H' != content_hash`. The response passes JSON decoding, is treated as a "successful" request, and is inserted into `self.attachments` with no hash cross-check. The only preconditions are that the peer is a legitimate outbound sync peer the node chose to query (`network.get_outbound_sync_peers()`) and has an existing `ReliabilityReport` entry, both of which are ordinary conditions for any peer the node is already talking to — no privileged role or secret is required.

### Impact Explanation
The node accepts and records attacker-controlled attachment bytes as if they satisfied a specific `content_hash` that was committed to by a confirmed on-chain name/attachment operation (BNS zonefile, etc.). This matches the "attachment/BNS mismatch" High-severity category: canonical BNS metadata can be paired with non-canonical, attacker-chosen content in the node's Atlas subsystem, which is subsequently servable to RPC clients querying attachments/zonefiles associated with that hash. This is repeatable for any attachment the node needs to fetch and is triggerable purely by a remote peer answering a GET request with crafted content — no write access to StackerDB slots, RPC secret, or other privileged capability is needed.

### Likelihood Explanation
- Attacker only needs to be a normal peer that the node has selected as an outbound sync peer and issued an attachment GET request to (ordinary P2P/RPC connectivity, no secret or privileged role).
- The attack requires a single crafted HTTP response per attachment request; it is trivially repeatable for every requested `content_hash`.
- No signature, MAC, or length constraint currently prevents this, since the check that should tie the response to the request (`attachment.hash() == request.content_hash`) is absent from `extend_with_attachments`.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments`, after `decode_atlas_get_attachment()` succeeds, explicitly verify `response.attachment.hash() == request.content_hash` before inserting into `self.attachments`; on mismatch, treat it as a failed request (`report.bump_failed_requests()`) and optionally penalize/deregister the peer, mirroring the validation pattern already used for other decoded Atlas responses (e.g., inventory response validation in `extend_with_inventories`).

### Proof of Concept
Rust test in `stackslib::net::atlas::download` module:
1. Construct an `AttachmentRequest { content_hash: H, sources, .. }` for a fabricated peer URL, and register a `ReliabilityReport` for that peer in `AttachmentsBatchStateContext.peers`.
2. Build a `BatchedRequestsResult<AttachmentRequest>` whose `succeeded` map contains `(request, Some(StacksHttpResponse-equivalent yielding GetAttachmentResponse{ attachment: Attachment{ content: b"attacker bytes" } }))`, where `Attachment::hash()` of that content is `H' != H`.
3. Call `context.extend_with_attachments(&mut results)`.
4. Assert `context.attachments` contains an `Attachment` whose `.hash() != H` (i.e., equals `H'`), demonstrating the request/response hash binding is not enforced at line 548 of `stackslib/src/net/atlas/download.rs`.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }

impl StacksHttpResponse {
    pub fn decode_atlas_get_attachment(self) -> Result<GetAttachmentResponse, NetError> {
        let contents = self.get_http_payload_ok()?;
        let contents_json: serde_json::Value = contents.try_into()?;
        let resp: GetAttachmentResponse = serde_json::from_value(contents_json)
            .map_err(|_e| NetError::DeserializeError("Failed to load from JSON".to_string()))?;
        Ok(resp)
    }
