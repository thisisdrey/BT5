### Title
`NativePositionContext` Missing from Session Extensions and Never Drained — (`aptos-move/framework/position-natives/src/natives.rs`, `aptos-move/aptos-vm/src/move_vm_ext/session/mod.rs`)

---

### Summary

The `native_set_position` and `native_delete_position` native functions unconditionally call `context.extensions().get::<NativePositionContext>()` to stage position writes, but `NativePositionContext` is **never registered** in `make_aptos_extensions` — the sole factory that initialises every transaction session's native extension set. Additionally, even if the extension were registered, `NativePositionContext::into_change_maps()` is **never called** in `SessionExt::finish()`, so staged writes would never reach the `VMChangeSet` and would be silently discarded. The result is a two-layer failure that is the direct Aptos analog of the Tokemak `delegatecall`-vs-`call` bug: a sub-component is invoked but the required execution context is absent, so the operation either crashes or produces no on-chain effect.

---

### Finding Description

**Layer 1 — Missing extension registration (validator crash path)**

`make_aptos_extensions` initialises every native extension that a transaction session may use: [1](#0-0) 

Ten extensions are registered (`NativeTableContext`, `NativeRistrettoPointContext`, `AlgebraContext`, `NativeAggregatorContext`, `RandomnessContext`, `NativeTransactionContext`, `NativeCodeContext`, `NativeStateStorageContext`, `NativeEventContext`, `NativeObjectContext`). `NativePositionContext` is absent from this list. [2](#0-1) 

When the `NATIVE_POSITION` feature flag is enabled and a Move caller invokes `set_position` or `delete_position`, the native implementation immediately calls: [3](#0-2) [4](#0-3) 

`context.extensions().get::<NativePositionContext>()` performs a `TypeId`-keyed lookup. Because the extension was never inserted, this panics, crashing the validator process for every node that executes the transaction.

**Layer 2 — Staged writes never drained (silent data loss path)**

Even if `NativePositionContext` were registered, `SessionExt::finish()` drains every other context into the `VMChangeSet` but has no call to `NativePositionContext::into_change_maps()`: [5](#0-4) 

The `into_change_maps` method exists and is the intended drain path: [6](#0-5) 

But it is never called anywhere in the repository (confirmed by grep: zero matches for `into_change_maps` or `position_write_set` outside the definition file). Staged position writes would be dropped at session end, making every `set_position` / `delete_position` call a no-op with respect to on-chain state.

**Move-side call chain**

The public Move API gates both natives behind `TradingNativeCapability::assert_valid`, but that check passes before the native is entered: [7](#0-6) [8](#0-7) 

The capability check is irrelevant to the crash — any holder of a valid `TradingNativeCapability` can trigger it.

---

### Impact Explanation

- **Validator crash (Layer 1):** When `NATIVE_POSITION` is enabled, any unprivileged transaction that calls `set_position` or `delete_position` causes `extensions().get::<NativePositionContext>()` to panic inside the validator process. Every validator executing that transaction crashes, producing a chain availability failure.
- **Permanent state corruption (Layer 2):** Even without a crash, position writes are silently discarded at session end. No perpetual position can ever be written to the native position store, permanently breaking the trading/perp system's state invariant.

---

### Likelihood Explanation

The `NATIVE_POSITION` feature flag gates the crash path. If the flag is off, the native aborts with `E_FEATURE_DISABLED` before reaching the missing extension lookup. However, the flag exists precisely to be enabled when the feature ships; the code is clearly intended for production use. Any holder of a `TradingNativeCapability` — an unprivileged role relative to the validator — can trigger the crash once the flag is on.

---

### Recommendation

1. **Register the extension.** Add `extensions.add(NativePositionContext::new())` to `make_aptos_extensions` alongside the other ten extensions. [9](#0-8) 

2. **Drain staged writes in `SessionExt::finish`.** After the existing context removals, extract and route the position change map into the `VMChangeSet`: [10](#0-9) 

3. **Add integration tests** that call `set_position` / `delete_position` with the feature flag enabled and assert that the resulting `VMChangeSet` contains the expected position write ops.

---

### Proof of Concept

1. Enable `FeatureFlag::NATIVE_POSITION` in a test environment.
2. Obtain a valid `TradingNativeCapability` (any exchange that has been granted one).
3. Call `aptos_experimental::native_position::set_position(cap, market, account, position)`.
4. **Observed:** `context.extensions().get::<NativePositionContext>()` panics because `NativePositionContext` was never inserted into the extension map by `make_aptos_extensions`. The validator process crashes.
5. **Expected (after fix):** The extension is found, the write is staged in `PositionTxCache`, and `SessionExt::finish` drains it into the `VMChangeSet`'s position write set, which is then committed to `PositionDb`.

#[derive(Tid, Default)]
pub struct NativePositionContext {
    cache: RefCell<PositionTxCache>,
}

impl NativePositionContext {
    pub fn new() -> Self {
        Self::default()
    }

    pub fn stage_set(&self, key: TradingNativeKey, value: NativePosition) {
        POSITION_SETS_STAGED.fetch_add(1, Ordering::Relaxed);
        self.cache.borrow_mut().staged.insert(key, Some(value));
    }

    pub fn stage_delete(&self, key: TradingNativeKey) {
        POSITION_DELETES_STAGED.fetch_add(1, Ordering::Relaxed);
        self.cache.borrow_mut().staged.insert(key, None);
    }

    /// Drain the staged writes for routing into the VMChangeSet bucket.
    pub fn into_change_maps(self) -> BTreeMap<TradingNativeKey, Option<NativePosition>> {
        self.cache.into_inner().staged
    }
