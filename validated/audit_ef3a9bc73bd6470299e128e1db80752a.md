### Title
Unbounded array allocation from attacker-controlled length in TVM precompile ABI decoding leads to Denial-of-Service - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `BatchValidateSign` and `ValidateMultiSign` TVM precompiled contracts decode signature/byte arrays from raw call data using helper methods `extractBytesArray` and `extractSigArray`. These methods read an array-length field directly out of attacker-controlled call data and use it to size a Java array (`new byte[len][]`) without validating that `len` is consistent with the actual size of the supplied `data`, or capping it to any sane maximum.

### Finding Description
`extractBytesArray` and `extractSigArray` take the array length straight from a `DataWord` in the decoded ABI header: [1](#0-0) [2](#0-1) 

In both methods, `len` is derived from `words[offset].intValueSafe()` — a 256-bit value from the transaction's call data coerced into an `int`. The only guard present is `offset > words.length - 1`; there is no check that `len` is bounded by the actual remaining `data` length or by any protocol-defined maximum count. This is structurally the same bug class as CVE-2021-24025: an untrusted, attacker-supplied size value is used directly to drive an allocation/size calculation without validating it against the real amount of available input, allowing a disproportionately large allocation to be triggered from a small amount of attacker-controlled input.

Because these precompiles (`BatchValidateSign`, `ValidateMultiSign`) are invoked via ordinary `CALL`/`STATICCALL` opcodes to their well-known precompile addresses, any contract deployer or caller can reach this code with a single crafted transaction by supplying a large length word (e.g., close to `Integer.MAX_VALUE`) in the encoded call data.

### Impact Explanation
A crafted call with an oversized length field forces the JVM to attempt allocating a huge `byte[][]`/backing arrays, which can throw `OutOfMemoryError` or exhaust node heap/CPU resources during transaction execution. Because this occurs inside VM precompile execution (not always guarded the same way as normal Java exceptions), it risks crashing or destabilizing the executing full node/SR node when processing a single broadcast transaction, which is a node-crash/halt class impact per the validation criteria.

### Likelihood Explanation
Likelihood is high for triggering the resource-exhaustion condition: reaching `BatchValidateSign`/`ValidateMultiSign` only requires deploying or calling a simple contract that performs a `CALL` to the precompile address with attacker-chosen call data — no special privileges, stake, or witness/SR status needed. The exact severity (whether it degrades to a caught exception with revert, vs. an uncatchable `OutOfMemoryError` that destabilizes the JVM/node) depends on downstream exception handling in the TVM `Program`/precompile dispatch path, which I was not able to fully verify in the time available (I could not inspect the full `execute()` bodies of `BatchValidateSign`/`ValidateMultiSign` calling these helpers, nor confirm whether an outer catch converts `OutOfMemoryError`/`NegativeArraySizeException` into a safe revert before reaching the JVM's global OOM state).

### Recommendation
In `extractBytesArray`, `extractSigArray`, and `extractBytes32Array`, validate the decoded `len` against the actual size of `data` (e.g., `len` must not exceed `(data.length - headerOffset) / itemSize`) and enforce an explicit upper bound on the number of elements before allocating any array, rejecting the call (returning `Pair.of(false, ...)`) instead of allocating.

### Proof of Concept
Not fully constructed — building a concrete PoC requires exact ABI layout/offset conventions used by `BatchValidateSign`/`ValidateMultiSign` callers, which I was unable to fully trace within the available search budget (the file is large: 2390+ lines, and I could not view the complete `execute()` methods for these two precompiles to confirm the precise byte offsets an attacker would need to control). Conceptually: craft a contract that `CALL`s the `BatchValidateSign` or `ValidateMultiSign` precompile address with call data whose length-count word is set to a very large value (e.g. `0x7fffffff`), triggering `new byte[len][]` inside `extractBytesArray`/`extractSigArray`.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
