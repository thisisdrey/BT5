### Title
Heap-buffer-overread when parsing malformed ZIP64 extra fields in a jar's central directory - ([File: third_party/ijar/zip.cc])

### Summary
`InputZipFile::ProcessCentralDirEntry` in ijar (Bazel's interface-jar/zip-processing library) parses the `extra field` list of a ZIP central directory record without any bounds checking, unlike sibling routines (`ProcessLocalFileEntry`, `SkipFile`, `ProcessFile`) that explicitly call `EnsureRemaining()` before every read. This mirrors the GnuTLS class of bug: an untrusted, length-prefixed sub-structure (the SCT extension there, the ZIP64 extra field here) is trusted to declare its own size, and that size is used to compute a read offset/length without validating it against the actual buffer boundary, producing a heap-buffer-overread whose leaked bytes become part of subsequently used values.

### Finding Description
`ProcessCentralDirEntry` reads a central-directory entry directly out of the mmap'd input file: [1](#0-0) 

Then it walks the "extra field" chain: [2](#0-1) 

Two problems compound into a heap-buffer-overread:
1. `data_size` (`get_u2le(extra_p)`) is attacker-controlled (0–65535) and is added to `extra_p` with **no check** that `extra_p + 4 <= p` before reading `header_id`/`data_size`, nor that `extra_p + data_size <= p` afterward. A crafted `data_size` can push `extra_p` past `p` (the declared end of the extra-field area) or even past the whole central directory / mapped file, and the loop condition `extra_p != p` will simply never become true again, so the loop keeps consuming attacker-influenced offsets into adjacent memory.
2. When `header_id == ZIP64_EXTRA_FIELD_TAG`, the code unconditionally calls `get_u8le(extra)` (reads 8 bytes from `extra`) even if fewer than 8 bytes remain before `p`/the file end — a direct analog of GnuTLS reading past the declared SCT length.

Crucially, unlike every other reader in this file, `ProcessCentralDirEntry` never calls `EnsureRemaining()`: [3](#0-2) 
compare with the local-header reader, which does gate every variable-length read behind `EnsureRemaining`: [4](#0-3) 

The over-read bytes are not inert — they directly become `*uncompressed_size`, `*compressed_size`, and `*offset`, which `ProcessNext()` uses to compute the pointer into the mapped file that is subsequently read and handed to `processor->Process(...)`: [5](#0-4) 

So a corrupted `offset`/size, poisoned by heap-adjacent memory read through the malformed extra field, can cause ijar to locate and copy content from an unintended location in the mapped file into the output interface jar — i.e., attacker-influenced heap bytes end up embedded in build output, the same "confidential data exposure via malformed length-prefixed extension" pattern as CVE-2025-32989.

### Impact Explanation
This is a genuine integrity/containment break in a code path that processes an attacker-suppliable artifact (a `.jar`/`.zip` consumed by ijar during interface-jar generation for any `java_import`/prebuilt-jar dependency, including ones fetched from an external URL and pinned only by `sha256`). The sha256/integrity check only pins to *this exact byte sequence*, and does not validate ZIP structural correctness — an attacker who controls the artifact bytes (and thus its hash) can freely craft a malformed central-directory extra field. The resulting heap-buffer-overread can (a) crash the build (least severe), or (b) leak adjacent heap memory content into the computed size/offset, causing incorrect regions of the mapped input to be copied into the produced ijar, exposing unrelated heap memory into a build artifact that downstream consumers of the build may read — matching the "Medium" confidentiality-exposure class of the reference CVE. It does not grant code execution or write outside the process's own memory.

### Likelihood Explanation
Likelihood is moderate: the attacker only needs to control (or convince a build to depend on) a single malformed jar/zip file; existing checksum pinning does not stop a self-consistent malicious file. However, this requires a build to actually run ijar (interface jar generation) over the malicious jar, which is a common but not universal path for external Java dependencies, and there is no evidence in the indexed code of an automated fuzz/regression test for `ProcessCentralDirEntry`'s extra-field parsing (existing malformed-extra-field regression tests, e.g. `MalformedExtraField` in singlejar, cover a different, already-hardened code path — `src/tools/singlejar/zip_headers.h`'s `ExtraField::find` and the callers in `output_jar.cc`, which do perform bounds checks and `diag_errx` on violation): [6](#0-5) [7](#0-6) 
No equivalent guard exists for ijar's `ProcessCentralDirEntry`.

### Recommendation
In `third_party/ijar/zip.cc`, before reading `header_id`/`data_size` in the extra-field loop, verify `extra_p + 4 <= p` (i.e. `extra_p` doesn't run past the declared extra-field/central-directory end); after computing `extra_p += data_size`, verify the new `extra_p <= p`, and before calling `get_u8le(extra)` for the ZIP64 tag, verify `extra + 8 <= extra_p` (i.e., at least 8 bytes of payload were declared and are actually present). More generally, route all reads in `ProcessCentralDirEntry` through `EnsureRemaining()` the same way `ProcessLocalFileEntry` does, and fail with `error(...)` on any violation instead of silently continuing.

### Proof of Concept
A JUnit/`src/test/shell/bazel` proof would construct a minimal ZIP whose central directory contains one entry with:
- `compressed_size32`/`uncompressed_size32` = `0xFFFFFFFF` (forcing ZIP64 extra-field lookup),
- an `extra_field_length` of, say, 4 bytes containing only `header_id = 0x0001` (ZIP64 tag) and `data_size = 0xFFFF` (far exceeding the actual remaining extra-field/file bytes),

and feed it to `ijar`'s `ZipExtractor` (as used by `//third_party/ijar:zip.cc`'s public `ProcessAll()`/`ProcessNext()` API, exercised for example via the `ijar` binary or a `BuildIntegrationTestCase` that builds a `java_import` on this crafted jar). Under ASan, this triggers `heap-buffer-overflow READ of size 8` inside `ProcessCentralDirEntry`'s `get_u8le(extra)` call, confirming the over-read; under a non-ASan build, the corrupted `offset`/size values can be observed to make the tool copy unintended bytes from the mapped input file into the generated interface jar's entry contents.
