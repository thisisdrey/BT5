### Title
Two-phase check-then-lock split in `AccountLocks::try_lock_transaction_batch` lets same-batch write-conflicting transactions both succeed - ([File: accounts-db/src/account_locks.rs])

### Summary
`AccountLocks::try_lock_transaction_batch` validates every transaction's account keys in one pass and only afterwards applies the locks in a second pass. Because the validation pass (`can_lock_accounts`) is evaluated against the *pre-batch* lock state for every transaction before any of the batch's own locks are applied, two transactions in the same batch that write-conflict on the same pubkey can both pass validation and both get their locks applied, violating the "no concurrent conflicting writers" invariant.

### Finding Description
The function is implemented as two sequential passes over `validated_batch_keys`: [1](#0-0) 

In the first loop, `can_lock_accounts` is a read-only check against `self` (`write_locks`/`readonly_locks`), and `self` is not mutated anywhere inside that loop: [2](#0-1) 

So if transaction `T1` and `T2` in the same batch both write the same pubkey `A`, and `A` is not already locked before the batch call, `can_lock_accounts` for both `T1` and `T2` sees the *same* unlocked state for `A` and returns `Ok` for both, since neither has been locked yet.

Only in the second loop does the code call `lock_accounts`, which unconditionally increments the write-lock counter with no re-check against locks just taken by prior transactions in the same batch: [3](#0-2) [4](#0-3) 

`lock_write` simply increments a counter (`*self.write_locks.entry(*key).or_default() += 1`), so it never rejects a second writer — conflict rejection is only performed in `can_lock_accounts`, which already ran (against stale state) before any of the batch's locks existed. The net result: `try_lock_transaction_batch` returns `Ok(())` for both `T1` and `T2`, even though they conflict on the same writable account within the same call.

### Impact Explanation
If a caller treats an `Ok(())` result from `try_lock_transaction_batch` as a guarantee that a transaction is safe to execute concurrently with the other `Ok` transactions in the same batch (which is the entire purpose of account locking), two write-conflicting transactions could be scheduled/executed concurrently, corrupting account state and producing a state-inconsistent block — matching the "invalid recorded block / account-lock invariant violation" bounty category. The severity depends entirely on whether any caller passes batches that are not already guaranteed conflict-free by construction; I was not able to fully verify within this session whether all current call sites (`accounts-db/src/accounts.rs`, `runtime/src/bank.rs`) pre-filter intra-batch conflicts before invoking this function, so the end-to-end reachability from an unprivileged TPU client could not be conclusively confirmed against the "Validate" requirement (exact attacker-reachable path through ingress/sigverify/scheduling).

### Likelihood Explanation
The bug is deterministic and requires no timing/concurrency — it reproduces on every call with two write-conflicting keys in the same batch input, entirely within `AccountLocks` in-process logic. Feasibility for an unprivileged remote attacker hinges on whether an upstream batch-forming component (e.g. banking-stage scheduler or block-replay path) can be induced to place two write-conflicting, individually-valid transactions into one `try_lock_transaction_batch` call; this precondition was not fully traced in the time available.

### Recommendation
Make the check-and-lock atomic per transaction within the batch (interleave checking and locking, e.g. call `can_lock_accounts` immediately followed by `lock_accounts` for each transaction in a single pass, so later transactions in the batch see locks taken by earlier ones), rather than splitting validation and locking into two independent full-batch passes.

#[test]
fn test_try_lock_transaction_batch_same_batch_write_conflict() {
    let mut locks = AccountLocks::default();
    let key = Pubkey::new_unique();

    // Two transactions in the same batch both writing `key`.
    let tx1_keys = vec![(&key, true)];
    let tx2_keys = vec![(&key, true)];

    let batch: Vec<TransactionResult<_>> = vec![
        Ok(tx1_keys.into_iter()),
        Ok(tx2_keys.into_iter()),
    ];

    let results = locks.try_lock_transaction_batch(batch);

    // Expected (correct) behavior: only one of the two should succeed.
    let ok_count = results.iter().filter(|r| r.is_ok()).count();
    assert_eq!(
        ok_count, 1,
        "both write-conflicting transactions in the same batch were locked simultaneously: {:?}",
        results
    );
}

    pub fn try_lock_transaction_batch<'a>(
        &mut self,
        mut validated_batch_keys: Vec<
            TransactionResult<impl Iterator<Item = (&'a Pubkey, bool)> + Clone>,
        >,
    ) -> Vec<TransactionResult<()>> {
        validated_batch_keys.iter_mut().for_each(|validated_keys| {
            if let Ok(keys) = validated_keys.as_ref()
                && let Err(e) = self.can_lock_accounts(keys.clone())
            {
                *validated_keys = Err(e);
            }
        });

        validated_batch_keys
            .into_iter()
            .map(|available_keys| available_keys.map(|keys| self.lock_accounts(keys)))
            .collect()
    }

    fn can_lock_accounts<'a>(
        &self,
        keys: impl Iterator<Item = (&'a Pubkey, bool)>,
    ) -> TransactionResult<()> {
        for (key, writable) in keys {
            if writable {
                if !self.can_write_lock(key) {
                    return Err(TransactionError::AccountInUse);
                }
            } else if !self.can_read_lock(key) {
                return Err(TransactionError::AccountInUse);
            }
        }

        Ok(())
    }

    fn can_write_lock(&self, key: &Pubkey) -> bool {
        // If the key is not read-locked or write-locked, it can be write-locked
        !self.is_locked_readonly(key) && !self.is_locked_write(key)
    }

    fn lock_readonly(&mut self, key: &Pubkey) {
        *self.readonly_locks.entry(*key).or_default() += 1;
    }

    fn lock_write(&mut self, key: &Pubkey) {
        *self.write_locks.entry(*key).or_default() += 1;
    }
