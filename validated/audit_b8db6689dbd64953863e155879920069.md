### Title
Self-destructed contract storage rows are never purged from `StorageRowStore`, leaking sensitive contract state after `SELFDESTRUCT` - (File: actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java)

### Summary
When a contract self-destructs via `SUICIDE`/`SUICIDE2`, java-tron removes the contract's account, code, and contract-metadata entries, but never wipes the contract's key/value slots held in `StorageRowStore`. Any unprivileged API client can subsequently query those slots (e.g. via `eth_getStorageAt` / `getStorageAt` in `TronJsonRpcImpl`, exercised in `Create2Test.testJsonRpc`) and still retrieve the destroyed contract's previously-stored values.

### Finding Description
`Program.suicide()`/`suicide2()` ( [1](#0-0) ) transfers balance/TRC10/frozen resources and then only calls `getContractState().markSelfDestruct(owner)`. `RepositoryImpl.deleteContract()` ( [2](#0-1) ) deletes the code store, account store, and contract store entries, but there is no corresponding deletion of the contract's rows in `StorageRowStore`.

`Storage.commit()` ( [3](#0-2) ) only deletes a row when that specific `DataWord` key is present in the in-memory `rowCache` and its value is written to zero — it never enumerates and clears all rows previously written under the contract's `addrHash`. Since `SELFDESTRUCT` does not rewrite every previously-set storage slot to zero, the rows persist indefinitely in the underlying LevelDB/RocksDB store ( [4](#0-3) ), keyed only by `addrHash = sha3(address)` and the 16-byte key prefix ( [5](#0-4) ).

Because the address-to-storage mapping is deterministic and unsalted for plain `CREATE`/`SELFDESTRUCT` (only `CREATE2` mixes in `trxHash` via `generateAddrHash`), and because the JSON-RPC/HTTP query paths (`Storage` reads exercised through `TronJsonRpcImpl.getStorageAt`, confirmed reachable in `Create2Test.testJsonRpc`) read storage rows directly from `StorageRowStore` without checking whether the owning account/contract still exists or was marked self-destructed, an external caller can read stale, "deleted" contract state — including any secrets, balances-in-mappings, or business logic state — that the contract owner believed was gone after `selfdestruct`.

### Impact Explanation
This is an information-disclosure bug consistent with the CVE-2015-7514 bug class ("did not clean the disk after use... allows... users to obtain sensitive information"). Storage that a contract deployer or user reasonably expects to be wiped upon contract destruction (mapping values, allowances, private accounting data written via `SSTORE`) remains permanently queryable through public read APIs. This does not directly cause fund theft but can leak sensitive application-level secrets or business state, and in adversarial scenarios (e.g. re-deployment tooling, wallets, or bridges that rely on "storage cleared after selfdestruct" as an invariant) could be leveraged to reconstruct prior contract state.

### Likelihood Explanation
High reachability: any account can deploy a trivial contract with a `selfdestruct` function, write sensitive values to storage, self-destruct it, and then query the same slots through the standard JSON-RPC/HTTP `getStorageAt` API — no special privilege required. The behavior is deterministic and repeatable, as shown by the existing test infrastructure that manually zeroes storage rows via `Storage.put(..., DataWord.ZERO())` to work around leftover state between test runs ( [6](#0-5) ), which itself demonstrates that stale storage rows are not otherwise cleaned up by the framework.

### Recommendation
On contract self-destruction (`markSelfDestruct` becoming committed at the root repository, in `RepositoryImpl.commitSelfDestructCache` / `deleteContract`), iterate and delete all `StorageRowStore` entries whose row key falls under the contract's `addrHash` prefix (or track and flush all previously-written keys for that address), rather than relying solely on the in-memory `rowCache` zero-write heuristic in `Storage.commit()`.

### Proof of Concept
Not independently executed; based on static code review of `Program.suicide()`, `RepositoryImpl.deleteContract()`, and `Storage.commit()`, which show no code path deleting previously-persisted `StorageRowStore` rows for a self-destructed address. Verification against `TronJsonRpcImpl.getStorageAt` internals to confirm it performs no existence/self-destruct check before serving a stored value could not be completed within the available tool iterations — this should be confirmed by a Devin session with full file access before treating this as conclusively exploitable.
