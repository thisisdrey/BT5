### Title
Attacker can force any account's token list to `MAX_TOKENS_PER_USER`, reverting all fee-bearing withdrawals, liquidations, and deposits - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
The original CVE is a crash/DoS triggered by crafted input hitting an unchecked indexing path. The Metronome analog is a revert-based DoS: `Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` revert with `UserReachedMaxTokens` once an account's combined deposit+debt token list reaches `MAX_TOKENS_PER_USER = 30`. Because the list add happens inside token transfers, mints, seizes, and fee transfers to `feeCollector`, an unprivileged attacker can force-fill a victim's (or the `feeCollector`'s) list via `deposit(amount_, onBehalfOf_)` dust deposits, after which critical protocol paths hard-revert.

### Finding Description
`DepositToken.deposit` accepts an arbitrary `onBehalfOf_` beneficiary and mints msdTokens to it. `_mint` calls `pool.addToDepositTokensOfAccount(account_)` whenever the recipient's balance was zero ( [1](#0-0) ). `addToDepositTokensOfAccount` enforces `onlyIfAdditionWillNotReachMaxTokens`, reverting when `debtTokensOfAccount + depositTokensOfAccount >= 30` ( [2](#0-1) [3](#0-2) ). The same add is triggered inside `_transfer` (so `transfer`, `transferFrom`, `seize`, and fee transfers) ( [4](#0-3) ).

Attack paths:
- Dust-fill a victim: for each registered deposit token, call `depositToken.deposit(dustAmount, victim)`. Once the victim's combined list hits 30, the victim cannot deposit into any new collateral type, cannot receive transfers of tokens they don't already hold, and `seize`/fee transfers that would add a new token to their list revert.
- Dust-fill `feeCollector`: fees are minted/transferred to `feeCollector` in `deposit` (line 231), `_withdraw` ( [5](#0-4) ), and `issue`/`repay` synthetic-fee paths. Once `feeCollector`'s list reaches 30, every withdrawal charging `withdrawFee` reverts in `_withdraw`, and every liquidation whose `seize` routes a fee to `feeCollector` reverts — protocol-wide DoS of withdrawals and liquidations.

`DebtToken` mints (`issue`, `mint`) add to `debtTokensOfAccount` ( [6](#0-5) ) and count toward the same 30 cap, though debt cannot be forced onto a victim since `issue` mints to `_msgSender` ( [7](#0-6) ).

### Impact Explanation
- Temporary freezing of funds: `withdraw`/`withdrawFrom` revert whenever the fee transfer to a capped `feeCollector` adds a new token — all user collateral withdrawals with `withdrawFee > 0` fail until the governor transfers tokens out of `feeCollector`.
- Liquidation DoS → insolvency risk: `Pool.liquidate` reverts on the `seize` fee leg, so underwater positions cannot be liquidated while `feeCollector` is capped, letting bad debt accrue.
- Victim griefing: blocked from depositing new collateral types to cure an unhealthy position, making them easier to liquidate.

### Likelihood Explanation
Requires the pool to list enough tokens that combined deposit+debt tokens can reach 30, and `withdrawFee`/seize-fee to be nonzero for the freeze paths. Attack cost is bounded: ~30 dust deposits plus gas. No privileged role needed — `deposit` is permissionless and `onBehalfOf_` is attacker-controlled. The victim can self-recover by transferring dust out (dust is unlocked since victims typically have room), but `feeCollector` requires governor intervention, making that path the higher-impact variant. Exploitability is configuration-dependent on the number of registered tokens per deployment.

### Recommendation
Do not revert on the cap inside token-list maintenance. Either (a) skip the `add` when the list is full and track collateral for `depositOf`/`debtOf` another way, (b) exempt `feeCollector`/`treasury` from the cap, or (c) compute `depositOf`/`debtOf` by iterating the global token lists and checking `balanceOf > 0` instead of per-account lists, removing the revert surface entirely.

### Proof of Concept
Hardhat fork outline:

```solidity
// Pool has D deposit tokens registered; assume D + debtTokens >= 30 reachable.
address feeCollector = poolRegistry.feeCollector();
uint256 cap = pool.MAX_TOKENS_PER_USER(); // 30

// 1. Fill feeCollector's per-account list
for (uint i; i < depositTokens.length; ++i) {
    underlying_i.mint(attacker, dust);
    underlying_i.approve(depositToken_i, dust);
    depositToken_i.deposit(dust, feeCollector); // balance 0 -> adds to list
    // repeat until depositTokensOfAccount(feeCollector) length hits cap
}

// 2. Any user withdraw with withdrawFee > 0 reverts:
vm.expectRevert(UserReachedMaxTokens.selector);
depositTokenA.withdraw(userAmount, user); // _withdraw -> _transfer(account, feeCollector, fee) -> add -> revert

// 3. Pool.liquidate reverts on the seize fee leg identically,
//    blocking liquidation of underwater positions.
```

Note: full reproduction requires a deployment/fork where registered collateral + debt tokens can reach the 30 cap; on pools with few listed tokens the cap is unreachable and the attack is not viable.
