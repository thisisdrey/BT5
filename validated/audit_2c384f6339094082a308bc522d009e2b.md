### Title
Unbounded exchange list growth causes out-of-gas/DoS-level resource exhaustion in `Wallet.getExchangeList()` served by `ListExchangesServlet`/gRPC `listExchanges` - (File: framework/src/main/java/org/tron/core/Wallet.java)

### Summary
`ExchangeCreateContract` lets any account with sufficient balance create a new exchange pair via `ExchangeCreateActuator.execute()`, which simply increments `getLatestExchangeNum()` and stores a new `ExchangeCapsule` with no limit on the total number of exchanges that can exist on-chain. [1](#0-0)  The only constraint enforced in `validate()` is the create fee and token-balance checks — there is no cap on the number of exchanges. [2](#0-1) 

### Finding Description
`Wallet.getExchangeList()` retrieves the *entire* set of exchanges via `getAllExchanges()` (no pagination, no limit) and builds a full response by iterating every exchange: [3](#0-2) 

`ExchangeStore.getAllExchanges()` performs an unbounded full-table scan and sort over every stored `ExchangeCapsule`: [4](#0-3) 

This unbounded query is exposed directly to unauthenticated API clients through `ListExchangesServlet` (HTTP `/wallet/listexchanges`), as well as analogous gRPC/solidity/PBFT servlets: [5](#0-4) 

A separate, already-paginated variant `getPaginatedExchangeList(offset, limit)` exists and explicitly caps the returned range via `EXCHANGE_COUNT_LIMIT_MAX`, confirming the developers recognized the need to bound exchange enumeration for at least one code path: [6](#0-5)  — but the un-paginated `getExchangeList()` used by `ListExchangesServlet` (and its gRPC/solidity/PBFT equivalents) was not given the same protection.

Because any account can call `ExchangeCreateContract` repeatedly (subject only to paying `getExchangeCreateFee()` and holding minimal token balances), the total number of `ExchangeCapsule` entries in the `ExchangeStore`/`ExchangeV2Store` is attacker-controllable and grows without bound. As this number grows large, every call to the un-paginated `listexchanges` API (and gRPC/solidity/PBFT equivalents) must load, deserialize, and sort every entry, which will consume increasing amounts of memory and CPU per request. This mirrors the reported bug class: an unprivileged, permissionless action (buying protection / here, creating exchanges) inflates an unbounded array that a downstream function must fully traverse, risking a resource-exhaustion condition on that traversal path.

### Impact Explanation
Exceeding a threshold in on-chain exchange count would make every `listexchanges`-family API call increasingly slow and memory-intensive, degrading or eventually starving the serving node (query API service disruption) for legitimate clients (an SPV/wallet/exchange integration querying the full-node API). Because the query endpoint is served synchronously and without pagination/limit, a sufficiently large exchange count could push per-request memory/CPU usage high enough to noticeably impact the node's ability to serve this query path, satisfying the "API the node can no longer serve" impact criterion.

### Likelihood Explanation
`ExchangeCreateContract` is broadcastable by any account holding the create fee and matching token balances; there's no committee-gated cap comparable to `UNFREEZE_MAX_TIMES` seen elsewhere in the codebase for unfreeze lists. An attacker (or organic usage growth) can create a large number of low-balance TRX/asset exchange pairs over time to inflate `getLatestExchangeNum()` and the backing store size, which is a low-cost, repeatable, single-transaction-type attack — likelihood is moderate, gated mainly by cumulative fee cost and time, not by any hard on-chain limit.

### Recommendation
Apply the same protection already used for `getPaginatedExchangeList` to `getExchangeList()`/`ListExchangesServlet` and its gRPC/solidity/PBFT equivalents — i.e., always require offset/limit parameters bounded by `EXCHANGE_COUNT_LIMIT_MAX`, or deprecate/remove the un-paginated full-list API entirely. Additionally, consider imposing a maximum number of exchanges creatable (or a maximum returnable in one query) enforced at the protocol level in `ExchangeCreateActuator.validate()`.

### Proof of Concept
1. Repeatedly submit `ExchangeCreateContract` transactions from one or more funded accounts, each creating a new TRX/asset trading pair with the minimum allowed token balances, paying only `getExchangeCreateFee()` each time — `ExchangeCreateActuator.execute()` places a new `ExchangeCapsule` keyed by an ever-incrementing `id` with no upper bound. [1](#0-0) 
2. After creating a very large number of exchanges, issue repeated HTTP requests to `/wallet/listexchanges` (or the gRPC/solidity/PBFT equivalents), which invoke `Wallet.getExchangeList()` → `ExchangeStore.getAllExchanges()`, forcing the node to deserialize, sort, and marshal every exchange entry on every request. [3](#0-2) [4](#0-3) 
3. Observe increasing latency/memory usage per request as the exchange count grows, contrasted with `getPaginatedExchangeList`, which bounds work via `EXCHANGE_COUNT_LIMIT_MAX` and thus does not exhibit the same unbounded growth. [6](#0-5)

  public ExchangeList getPaginatedExchangeList(long offset, long limit) {
    if (limit < 0 || offset < 0) {
      return null;
    }

    long latestExchangeNum = chainBaseManager.getDynamicPropertiesStore()
        .getLatestExchangeNum();
    if (latestExchangeNum <= offset) {
      return null;
    }
    limit =
        limit > EXCHANGE_COUNT_LIMIT_MAX ? EXCHANGE_COUNT_LIMIT_MAX : limit;
    long end = offset + limit;
    end = end > latestExchangeNum ? latestExchangeNum : end;

    ExchangeList.Builder builder = ExchangeList.newBuilder();
    ImmutableList<Long> rangeList = ContiguousSet
        .create(Range.openClosed(offset, end), DiscreteDomain.longs())
        .asList();
    rangeList.stream().map(ExchangeCapsule::calculateDbKey).map(key -> {
      try {
        return getExchangeStoreFinal(chainBaseManager.getDynamicPropertiesStore(),
            chainBaseManager.getExchangeStore(),
            chainBaseManager.getExchangeV2Store()).get(key);
      } catch (Exception ex) {
        return null;
      }
    }).filter(Objects::nonNull)
        .forEach(exchangeCapsule -> builder
            .addExchanges(exchangeCapsule.getInstance()));
    return builder.build();

  /**
   * get all exchanges.

  public List<ExchangeCapsule> getAllExchanges() {
    return Streams.stream(iterator())
        .map(Map.Entry::getValue)
        .sorted(
            (ExchangeCapsule a, ExchangeCapsule b) -> a.getCreateTime() <= b.getCreateTime() ? 1
                : -1)
        .collect(Collectors.toList());
  }
