### Title
Missing source authentication in `RecvError` handling allows spoofed remote tunnel teardown - (File: outside.go)

### Summary
Nebula's `RecvError` control packet, like the CCIP `Any2EVMMessage` in the external report, carries no cryptographic proof that it originated from the peer it claims to represent. `Interface.handleRecvError` in `outside.go` accepts an unauthenticated, unencrypted `RecvError` packet and tears down an active tunnel based solely on a plaintext index and a UDP source-address comparison, neither of which is protected against spoofing.

### Finding Description
In `readOutsidePackets`, `header.RecvError` packets are dispatched to `f.handleRecvError` before any certificate/handshake state is required — the packet is processed purely based on the cleartext header: [1](#0-0) 

`handleRecvError` then looks up the `HostInfo` purely by the attacker-controlled `h.RemoteIndex` field (which is sent in cleartext on every packet header for that tunnel, so it is observable to anyone who can see the wire traffic) and checks only that the UDP source address of the incoming packet matches the currently known remote address of that HostInfo: [2](#0-1) 

There is no MAC, signature, or nonce binding the `RecvError` packet to the actual peer's authenticated identity — the only "source validation" is `hr.IsValid() && hr != addr`, which is a comparison against a UDP source IP:port that can trivially be spoofed on UDP, exactly like the CCIP report's missing `sender`/`sourceChainSelector` check that allowed forged bridge messages to be accepted as if they came from a trusted source.

### Impact Explanation
An attacker who can observe the cleartext `RemoteIndex` on the wire (or guess it) and spoof a UDP packet with the victim peer's source address can force `f.closeTunnel(hostinfo)` and `f.handshakeManager.DeleteHostInfo(hostinfo)` to run, tearing down an established, authenticated tunnel between two legitimate Nebula nodes. This is a remote state-poisoning/denial-of-service primitive reachable by an attacker holding no CA-signed certificate at all, directly analogous to the CCIP bug where lack of source verification let an attacker manipulate bridge/token accounting state.

### Likelihood Explanation
`RecvError` packets are processed prior to any handshake/certificate check (`outside.go:81-84`), so no authentication is required to reach `handleRecvError`. The only gate is `acceptRecvErrorConfig.ShouldRecvError(addr)`, which is a rate limiter, not an authentication mechanism, and the index/addr pair needed is observable from any vantage point that can see UDP traffic between the two peers (on-path attacker, compromised router, or anyone who can send spoofed UDP source addresses toward the target).

### Recommendation
Do not tear down a tunnel based solely on an unauthenticated `RecvError` packet's plaintext index and UDP source address. Options include: requiring `RecvError` to be authenticated (e.g., signed/MAC'd using the tunnel's established symmetric key, similar to how `VerifyRelay` authenticates relay frames), rate-limiting/backing off harder before acting on it, or requiring corroborating evidence (e.g., several observed encrypted-decrypt failures) before tearing down the tunnel purely from an inbound `RecvError`.

### Proof of Concept
1. Observe (or otherwise learn) the cleartext `RemoteIndex` used in the header of packets flowing between Nebula peer A and peer B — this field is not encrypted (`header.Encode`/`header.H.Parse`).
2. Craft a UDP packet with source address spoofed to match peer B's known remote UDP address, type `header.RecvError`, and `RemoteIndex` set to the index peer A uses for the A→B tunnel.
3. Send this spoofed packet to peer A.
4. `readOutsidePackets` dispatches it directly to `handleRecvError` without decrypting or verifying any certificate.
5. `handleRecvError` finds the HostInfo via `QueryReverseIndex(h.RemoteIndex)`, confirms `hr == addr` (satisfied by the spoofed source address), and calls `f.closeTunnel(hostinfo)` plus `f.handshakeManager.DeleteHostInfo(hostinfo)`, tearing down the legitimate tunnel without any cryptographic proof that the message came from peer B.

func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
