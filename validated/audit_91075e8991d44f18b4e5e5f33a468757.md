Unbounded HTTP response streaming into `tar -xvf -` allows disk/goroutine exhaustion DoS - ([File: internal/gitaly/service/repository/create_repository_from_snapshot.go])

### Summary
`CreateRepositoryFromSnapshot`'s `untar` helper fetches `in.GetHttpUrl()` and pipes the raw `http.Response.Body` directly into a `tar -xvf -` subprocess without any byte-size cap or independent extraction timeout. Since `httpTransport.ResponseHeaderTimeout` only bounds the time to receive response headers and not the body-streaming phase, and the request's only bound is the caller-supplied gRPC context, a server that the attacker controls behind `HttpUrl` can stream data indefinitely or extremely slowly to keep the `tar` process and disk writes running until node resources are exhausted.

### Finding Description
In `untar` [1](#0-0) , the response body `rsp.Body` is passed straight to `command.New(ctx, s.logger, []string{"tar", "-C", path, "-xvf", "-"}, command.WithStdin(rsp.Body))` with no `io.LimitReader`, no `http.MaxBytesReader`, and no separate deadline/`context.WithTimeout` wrapping the extraction — the only bound is whatever context deadline the caller (e.g. GitLab Rails) supplied on the original gRPC call. `httpTransport` [2](#0-1)  sets `ResponseHeaderTimeout: 30 * time.Second`, which only guards how long the client waits for response headers; it does nothing to bound the duration of body streaming once headers are received, nor does it cap total bytes transferred. There is also no gRPC server-side timeout interceptor found in the codebase (`internal/gitaly/server`) and no size/duration limiting logic anywhere in this file or in `command` package usage here. As the RPC comment itself acknowledges, "the received archive is trusted a lot" and hardening was deferred [3](#0-2) .

Given the stated precondition that an attacker controls the HTTP server referenced by `HttpUrl` and can invoke this RPC for a repository they own, they can serve an infinite or extremely slow-trickling (e.g., chunked, `Flusher`-driven) response body. `tar -xvf -` will keep writing extracted content to disk under `s.locator.GetRepoPath` indefinitely, and the goroutine/connection backing `rsp.Body` stays open, until either the caller's own gRPC context deadline fires or the Gitaly process runs out of disk/FDs/memory.

### Impact Explanation
This is a node-level denial of service: unbounded disk consumption in a shared storage location and/or a long-lived subprocess and open HTTP connection tying up resources, affecting all tenants/projects sharing that Gitaly storage. It matches the "resource exhaustion of a handler" impact class explicitly listed in scope. It does not grant data exfiltration or code execution — the impact is limited to availability degradation of the node.

### Likelihood Explanation
Feasibility is high and fully within the attacker's own control: they need only stand up an HTTP server that streams a slow/infinite body and provide its URL as `HttpUrl` for a repository they own, then invoke `CreateRepositoryFromSnapshot`. No secrets, race conditions, or privileged access are required — only the ability to control the RPC's `HttpUrl` field, which the threat model in the prompt grants. Repeatability is trivial and the attack can be run in parallel across many calls to amplify resource pressure, bounded only by whatever gRPC-level timeout/quota GitLab Rails applies (which is not enforced by Gitaly itself).

### Recommendation
- Wrap the response body in an `io.LimitReader` (or `http.MaxBytesReader`) bounded to a sane maximum snapshot size before piping into `tar`.
- Add an explicit, bounded extraction timeout (e.g., `context.WithTimeout`) around the `untar` call independent of the caller-supplied context, so a slow/infinite body cannot outlive a fixed ceiling.
- Consider adding a read-idle/stall timeout on the HTTP transport (e.g., via a wrapping reader that errors out if no bytes are read within N seconds) since `ResponseHeaderTimeout` does not cover body streaming.
- Monitor/limit concurrent in-flight `CreateRepositoryFromSnapshot` calls per repository/user to prevent parallel amplification.

### Proof of Concept
```go
func TestCreateRepositoryFromSnapshot_slowlorisDoS(t *testing.T) {
    t.Parallel()
    ctx := testhelper.Context(t)
    cfg, client := setupRepositoryService(t)

    srv := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        flusher := w.(http.Flusher)
        w.WriteHeader(http.StatusOK)
        buf := make([]byte, 1<<20) // 1MB chunks
        for {
            select {
            case <-r.Context().Done():
                return
            default:
                w.Write(buf)
                flusher.Flush()
                time.Sleep(10 * time.Millisecond) // never terminates, keeps draining disk
            }
        }
    }))
    defer srv.Close()

    repo := &gitalypb.Repository{
        StorageName:  cfg.Storages[0].Name,
        RelativePath: gittest.NewRepositoryName(t),
    }

    ctxTimeout, cancel := context.WithTimeout(ctx, 20*time.Second)
    defer cancel()

    start := time.Now()
    _, err := client.CreateRepositoryFromSnapshot(ctxTimeout, &gitalypb.CreateRepositoryFromSnapshotRequest{
        Repository: repo,
        HttpUrl:    srv.URL,
    })
    // Expect the call to run for the entire 20s window (bounded only by the
    // caller's own context, not by Gitaly), while disk usage under the repo
    // path grows unbounded — assert elapsed time and directory size growth.
    require.Error(t, err) // context deadline exceeded
    require.GreaterOrEqual(t, time.Since(start), 20*time.Second)
}
```
Expected observation: the RPC call is only terminated by the test's own `context.WithTimeout`, not by any internal Gitaly safeguard; disk usage in the target repo path grows continuously for the full duration, demonstrating no size cap or extraction timeout is enforced by `untar`.

func (s *server) untar(ctx context.Context, path string, in *gitalypb.CreateRepositoryFromSnapshotRequest) error {
	req, err := http.NewRequestWithContext(ctx, "GET", in.GetHttpUrl(), nil)
	if err != nil {
		return structerr.NewInvalidArgument("Bad HTTP URL: %w", err)
	}

	client := httpClient
	if resolvedAddress := in.GetResolvedAddress(); resolvedAddress != "" {
		client, err = newResolvedHTTPClient(in.GetHttpUrl(), resolvedAddress)
		if err != nil {
			return structerr.NewInvalidArgument("creating resolved HTTP client: %w", err)
		}
	}

	if in.GetHttpAuth() != "" {
		req.Header.Set("Authorization", in.GetHttpAuth())
	}

	rsp, err := client.Do(req)
	if err != nil {
		return structerr.NewInternal("HTTP request failed: %w", err)
	}
	defer rsp.Body.Close()

	if rsp.StatusCode < http.StatusOK || rsp.StatusCode >= http.StatusMultipleChoices {
		return structerr.NewInternal("HTTP server: %s", rsp.Status)
	}

	cmd, err := command.New(ctx, s.logger, []string{"tar", "-C", path, "-xvf", "-"}, command.WithStdin(rsp.Body))
	if err != nil {
		return err
	}

	return cmd.Wait()
