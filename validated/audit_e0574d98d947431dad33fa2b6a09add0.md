## Analog Finding

### Title
Unbounded/uncaught array index in `ValidateMultiSign` precompile allows attacker-controlled offset to throw `ArrayIndexOutOfBoundsException` outside the class's own exception handling - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The HDF5 report is a heap-overflow caused by trusting an attacker-declared `num_messages` count against a buffer whose real size was never validated (`H5SM__cache_list_deserialize`). The direct java-tron analog is `PrecompiledContracts.ValidateMultiSign.execute()`, which decodes an attacker-supplied offset word from calldata and uses it directly as an index into the `DataWord[] words` array without first checking that the index is within bounds — unlike the sibling precompile `BatchValidateSign`, which performs the identical computation but wraps it in a class-level `catch (Throwable t)`.

### Finding Description
`ValidateMultiSign.execute()` is reachable from any TVM `CALL`/`STATICCALL` to the precompile address (any contract call, i.e. any signed transaction that a contract deployer or caller can broadcast): [1](#0-0) 

`words[3]` is fully attacker-controlled input (the ABI "offset" word for the dynamic `bytes[]` argument). `intValueSafe()` clamps out-of-range values to `Integer.MAX_VALUE` rather than throwing: [2](#0-1) 

So `words[words[3].intValueSafe() / WORD_SIZE]` can compute an index far larger than `words.length` (which is derived from the real calldata length via `DataWord.parseArray`): [3](#0-2) 

That direct index access has no bounds check and is executed *before* any try/catch — the only try/catch in `ValidateMultiSign.execute()` wraps only the later account/permission-weight logic: [4](#0-3) 

`isValidAbiEncoding()`, the TIP-854 guard added specifically to reject malformed calldata shapes, only validates overall length/alignment (`data.length % WORD_SIZE`, header/tail word counts) — it does **not** validate the *value* of any offset word, so it does not prevent this: [5](#0-4) 

By contrast, the sibling precompile `BatchValidateSign`, which performs the exact same unguarded index computation for its own offset words, is safe because its entire `execute()` is wrapped in a class-level `try { return doExecute(data); } catch (Throwable t) { ... }`: [6](#0-5) 

This is the same bug class as the HDF5 advisory: an attacker-supplied count/offset field is trusted as an array index against a buffer whose true bounds were never checked against that value, and unlike the mitigated sibling function, `ValidateMultiSign` lacks the outer defensive catch that would contain the resulting out-of-bounds fault.

### Impact Explanation
If the exception is not caught by a higher layer (e.g. the VM opcode/`CALL` dispatcher in `Program.java`), it propagates out of `execute()` during ordinary transaction/block execution. Since `TransactionTrace`/`VMActuator` in java-tron generally catches `Throwable` at the top of contract execution and converts it into a failed/reverted transaction, the most likely concrete effect is a reliably-failed `validateMultiSign` call (denial of a specific contract feature) rather than a full node crash — I was not able to fully trace `Program.callToPrecompiledAddress`'s exception-catching path in the time available, so I cannot conclusively prove node-crash impact versus contained-call-failure impact. Regardless, the finding demonstrates a genuine bounds-checking inconsistency: the developers explicitly recognized this exact index-computation pattern needed a defensive `catch (Throwable)` in `BatchValidateSign` (comment `// add check`) but omitted the equivalent protection in `ValidateMultiSign`.

### Likelihood Explanation
Trivially reachable: any account can construct a TVM contract that `CALL`s the `validateMultiSign` precompile address with a crafted `words[3]` offset word; no special privileges, SR/witness status, or existing account state are required.

### Recommendation
Add the same class-level `try { ... } catch (Throwable t) { return Pair.of(true, DATA_FALSE); }` (or equivalent bounds validation of `words[3].intValueSafe() / WORD_SIZE` against `words.length` before indexing) to `ValidateMultiSign.execute()` that already protects `BatchValidateSign.execute()`, and audit `extractBytesArray`/`extractSigArray`/`extractBytes32Array` call sites for the same unguarded-offset pattern.

### Proof of Concept
1. Construct calldata for `validatemultisign(address,uint256,bytes32,bytes[])` that passes `isValidAbiEncoding` (32-byte aligned, `(len/32 - 5) % 5 == 0`) but sets the 4th word (`words[3]`, the dynamic-array offset) to a large value such as `0xFFFFFFFFFFFFFFFF...` so `intValueSafe()` returns `Integer.MAX_VALUE`.
2. Enable `allowTvmSelfdestructRestriction` (already default-on in current mainnet parameters).
3. Issue a contract `CALL` to the `validateMultiSign` precompile address with this calldata.
4. `words[Integer.MAX_VALUE / 32]` throws `ArrayIndexOutOfBoundsException`, uncaught inside `ValidateMultiSign.execute()`, unlike the equivalent path in `BatchValidateSign` which is caught and safely neutralized.

I could not fully confirm within this session whether this uncaught exception ultimately crashes the node or is contained by an outer catch in `Program`/`VMActuator`/`TransactionTrace` — that would need direct inspection of `Program.callToPrecompiledAddress` and the transaction-execution wrapper, which I was unable to complete before the tool budget was exhausted.

  public static DataWord[] parseArray(byte[] data) {
    int len = data.length / WORD_SIZE;
    DataWord[] words = new DataWord[len];
    for (int i = 0; i < len; i++) {
      byte[] bytes = Arrays.copyOfRange(data, i * WORD_SIZE, (i + 1) * WORD_SIZE);
      words[i] = new DataWord(bytes);
    }
    return words;
  }
