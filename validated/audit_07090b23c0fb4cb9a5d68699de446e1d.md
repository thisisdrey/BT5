### Title
Protocol fee on Nep245/Imt `TokenDiff` trades bypassed by splitting into unit-sized legs across a batch - (File: contracts/defuse/core/src/intents/token_diff.rs)

### Summary
`TokenDiff::token_fee` waives fees whenever the *per-intent* `|delta|` for a `Nep245`/`Imt` token is `<= 1`, but the check is evaluated independently for each `TokenDiff::execute_intent` call rather than on the aggregate net delta of that token across the whole `execute_intents` batch. An attacker can therefore split any trade of an MT/Imt asset into multiple 1-unit legs (each in its own signed `MultiPayload` within the same `execute_intents` call) and pay zero protocol fee regardless of the total volume traded, whereas performing the identical net trade as a single intent incurs the normal fee.

### Finding Description
The broken binding: fee credited to `fee_collector` for token `T` should equal `protocol_fee.fee_ceil(|net_delta_T|)` over the combined negative delta of `T` in the batch, but the actual code computes and sums `Pips::ZERO` for each leg with `|delta| <= 1`, so for two legs of `delta = -1` each (net `-2`), `fees_collected == 0` instead of `protocol_fee.fee_ceil(2) > 0`.

Code path:
- `TokenDiff::execute_intent` in [1](#0-0)  iterates `self.diff` (the single intent's own map of deltas) and, for each negative delta, computes `fee = Self::token_fee(token_id, amount, protocol_fee).fee_ceil(amount)` using only that intent's own `amount = delta.unsigned_abs()`.
- `TokenDiff::token_fee` in [2](#0-1)  explicitly returns `Pips::ZERO` for `TokenIdType::Nep245`/`TokenIdType::Imt` when `amount <= 1` ("do not take fees on NFTs and MTs with `|delta| <= 1`").
- `execute_intents` in [3](#0-2)  takes `Vec<MultiPayload>` and processes each signed payload's intents sequentially through the same `Engine`; there is no aggregation of per-token deltas across separate `TokenDiff` intents before the fee is assessed — each `TokenDiff::execute_intent` call runs, calculates its own fee, and immediately credits `fee_collector` via `internal_add_balance` at line 100 of `token_diff.rs`, independent of any other intent in the batch.

Root cause: the `amount > 1` fee-exemption threshold in `token_fee` was designed as a per-unit exemption for NFT-like (`Nep171`) and unit-valued MT/Imt transfers, but it is checked against the delta of one `TokenDiff` at a time rather than the net delta of the token across the whole `execute_intents`/`simulate_intents` batch. Because `TokenId` equality is exact and fungible MT/Imt balances can be moved in arbitrary unit increments, an attacker can always decompose a net trade of `N` units of a given Nep245/Imt `TokenId` into `N` separate `TokenDiff` intents of `delta = ±1` each (each matched by a corresponding counter-leg to satisfy the invariant/`TransferMatcher` net-zero check for the whole batch), and every leg independently qualifies for the `Pips::ZERO` exemption.

Attacker's exact call: two signed `MultiPayload`s, each containing a `TokenDiff` intent with `diff = {Nep245TokenId(mt_contract, token_id): -1}` (plus matching counter-legs elsewhere in the batch to satisfy the zero-sum invariant), submitted together in one `execute_intents(signed: Vec<MultiPayload>)` call. No `Role`, relayer key, or victim signature is required — the attacker only needs their own balance and their own (or a willing counterparty's) signature(s) to close the invariant.

None of the existing guards (`MultiPayload::verify`, nonce/salt checks, `Lock`, `assert_one_yocto`, `#[pause]`, invariant/`TransferMatcher::finalize`) prevent this, because they only ensure signature validity, replay protection, and that the batch's deltas net to zero — none of them re-check or aggregate the fee basis across intents.

### Impact Explanation
Protocol fees on `Nep245`/`Imt` assets are under-collected relative to the intended fee model: `fee_collector` receives `0` instead of `protocol_fee.fee_ceil(net_delta)` whenever a trade is decomposed into unit-sized legs. This is deterministic and fully repeatable for any account, any Nep245/Imt token, and any batch size — the attacker (or a colluding pair of accounts) can trade arbitrary volumes fee-free by simply issuing more unit-sized legs. This falls under the explicitly listed Critical category "protocol fees bypassed."

### Likelihood Explanation
Preconditions are minimal: the attacker needs a Verifier balance of the Nep245/Imt token (2+ units) and either a second account they control or any willing counterparty to close the batch's zero-sum invariant. No elevated role, relayer key, or victim key is needed. The attack is cheap (ordinary `execute_intents` transaction cost) and trivially repeatable at any scale by increasing the number of unit legs.

### Recommendation
Compute the Nep245/Imt fee exemption threshold against the aggregated net delta per `TokenId` across the entire batch being executed (e.g., accumulate deltas per token across all `TokenDiff` intents in the `Engine`/`Deltas` state before assessing `token_fee`), rather than against each intent's own local `delta`. Alternatively, move the `amount <= 1` exemption check to operate on the token's post-matching net supply delta (as used in `TransferMatcher`/`Deltas`) instead of the raw intent-level delta.

### Proof of Concept
Add a `cargo test` in `contracts/defuse/core/src/intents/token_diff.rs` (or an integration test under `tests/src/tests/defuse/intents/token_diff.rs` using the sandbox harness) that:
1. Sets `protocol_fee = Pips::ONE_BIP` (or any nonzero fee).
2. Case A (single leg): builds one `TokenDiff` with `diff = {nep245_token_id: -2}` matched by a counter-leg elsewhere in the batch; executes via `execute_intents`; asserts `fees_collected.amount_for(&nep245_token_id) > 0` (equal to `Pips::ONE_BIP.fee_ceil(2)`).
3. Case B (two legs): builds two separate signed `MultiPayload`s, each a `TokenDiff` with `diff = {nep245_token_id: -1}` (matched by corresponding counter-legs), submitted together in a single `execute_intents(vec![payload1, payload2])` call; asserts the total `fees_collected` for `nep245_token_id` summed across both `TokenDiffEvent`s (or the resulting `fee_collector` balance delta) is `0`.
4. Assert the two results differ (`fees_collected_single_leg > 0` while `fees_collected_two_legs == 0`) despite both cases moving the same net `-2` of the same `TokenId`, proving the fee basis is leg-count-dependent instead of batch/aggregate-dependent.
