Found a real local analog: in `pallet-staking`'s unbond flow, the max-length guard on the `unlocking` `BoundedVec` is evaluated **before** the code decides whether the new unbond request will merge into an existing chunk (no growth) or push a brand-new chunk (growth). This mirrors exactly the `wstTAO.sol` bug class: a `require`/`ensure!` that blocks legitimate requests which would not actually grow the bounded collection.

### Title
Premature `NoMoreChunks` `ensure!` blocks same-era unbond requests that would only merge into an existing chunk, not grow the array - (File: `substrate/frame/staking/src/pallet/impls.rs`, also `substrate/frame/staking-async/src/pallet/mod.rs`)

### Summary
`pallet-staking`'s `do_unbond` (and the equivalent `unbond` extrinsic body in `pallet-staking-async`) checks `ledger.unlocking.len() < T::MaxUnlockingChunks::get()` unconditionally before knowing whether the new unbond amount will be merged into the existing last chunk (same era) or pushed as a brand-new chunk. Because the merge path does not increase `unlocking.len()`, a staker whose `unlocking` vector is already at `MaxUnlockingChunks` and whose last chunk's era matches the era computed for the new call is incorrectly rejected with `Error::NoMoreChunks`, even though the operation would not need any additional slot.

### Finding Description
The `unbond` logic first tries to make room via auto-withdraw: [1](#0-0) 
then re-fetches the ledger and enforces the bound unconditionally: [2](#0-1) 
Only afterwards does it decide whether to merge into the last chunk (no size growth) or push a new one: [3](#0-2) 

The comment right above the merge branch explicitly acknowledges that same-era chunks are combined ("To keep the chunk count down, we only keep one chunk per era... if a chunk exists for `era` we know that it will be the last one") — i.e., the code already knows the merge case does not consume a new slot, yet the `ensure!` at lines 1410-1413 fires before this decision is made, using only the *current* `len()` rather than whether a push is actually required.

The identical pattern exists in the async staking pallet: the auto-withdraw attempt, the premature `ensure!`, then the merge-or-push decision. [4](#0-3) [5](#0-4) 

This is structurally the same defect as the `wstTAO.sol` finding: a bound check placed before the array-mutation logic, without accounting for the "no-growth" (merge/reuse) code path, causing an over-eager revert for users who should still be permitted to act because they are not actually exceeding the bound.

### Impact Explanation
A staker who already has `MaxUnlockingChunks` live unlocking chunks (none of which are yet withdrawable, so the auto-withdraw pre-step frees nothing) is unable to submit an additional `unbond` call in the same era as their most recent chunk — even though that call would only merge into the existing last chunk and would not violate the `MaxUnlockingChunks` bound. This is a denial-of-service on a core staking user action (`unbond`): legitimate, bound-respecting operations revert with `Error::NoMoreChunks`. It does not lead to fund loss, but it does directly compromise the intended behavior of a runtime-level financial primitive (users being wrongly prevented from managing their stake), matching the "runtime bugs that compromise intended behavior" impact category.

### Likelihood Explanation
This requires no privileged actor, governance, validator, or malicious peer — any ordinary staker can trigger it purely through normal use: repeatedly unbonding across `MaxUnlockingChunks` distinct eras (a common pattern for active nominators who redelegate/rebalance) and then issuing one more unbond call within the same era as the most recent chunk while earlier chunks are still within `BondingDuration`. Given `MaxUnlockingChunks` is typically small (e.g. 32 on Polkadot/Kusama-style configs, or as low as configured in tests: 1, 2, 3), and `BondingDuration` spans multiple eras, this state is straightforward to reach in normal staking activity.

### Recommendation
Reorder the logic so the bound check is only applied to the "push" branch, mirroring the fix pattern in the report: first determine whether the new unbond value will be merged into an existing last chunk for `era`; only if no matching chunk exists (i.e., a new element must be pushed) should the code enforce `ledger.unlocking.len() < T::MaxUnlockingChunks::get()`. Concretely, compute `era` first, check `ledger.unlocking.last().filter(|c| c.era == era)`, and only guard the `try_push` branch with the length check (as `try_push` itself already returns an error via `.map_err(|_| Error::<T>::NoMoreChunks)?` when full) — dropping the redundant premature `ensure!`.

### Proof of Concept
1. Configure `MaxUnlockingChunks = 3`, `BondingDuration = 7` (as in the existing test `unbonding_rejects_if_max_chunks`). [6](#0-5) 
2. At era 1, 2, 3 call `unbond` once each era with a fresh amount, producing 3 distinct chunks at eras `1+7`, `2+7`, `3+7` — `unlocking.len() == MaxUnlockingChunks == 3`.
3. Remain in era 3 (do not roll to a new era) and call `unbond` again. The era computed for this new call is `active_era (3) + bonding_duration (7) = 10`, which equals the era of the last chunk already in the vector (`3+7=10`).
4. Expected (correct) behavior: since the new chunk would merge into the existing last chunk (same era, no vector growth), the call should succeed.
5. Actual behavior: the `ensure!(ledger.unlocking.len() < T::MaxUnlockingChunks::get(), Error::<T>::NoMoreChunks)` check fires first (`len()==3` is not `< 3`), and the call reverts with `NoMoreChunks`, even though no additional slot is required.

fn unbonding_rejects_if_max_chunks() {
	ExtBuilder::default()
		.max_unlock_chunks(3)
		.bonding_duration(7)
		.build_and_execute(|| {
			// given
			assert_eq!(
				Staking::ledger(11.into()).unwrap(),
				StakingLedgerInspect {
					stash: 11,
					total: 1000,
					active: 1000,
					unlocking: Default::default(),
				}
			);

			// when
			Staking::unbond(RuntimeOrigin::signed(11), 250).unwrap();
			Session::roll_until_active_era(2);
			Staking::unbond(RuntimeOrigin::signed(11), 250).unwrap();
			Session::roll_until_active_era(3);
			Staking::unbond(RuntimeOrigin::signed(11), 250).unwrap();

			// then
			assert_eq!(
				Staking::ledger(11.into()).unwrap(),
				StakingLedgerInspect {
					stash: 11,
					total: 1000,
					active: 250,
					unlocking: bounded_vec![
						UnlockChunk { value: 250, era: 1 + 7 },
						UnlockChunk { value: 250, era: 2 + 7 },
						UnlockChunk { value: 250, era: 3 + 7 },
					],
				},
			);

			// when
			Session::roll_until_active_era(4);
			assert_noop!(Staking::unbond(RuntimeOrigin::signed(11), 100), Error::<T>::NoMoreChunks,);
		});
