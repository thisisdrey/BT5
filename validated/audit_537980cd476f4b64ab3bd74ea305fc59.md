### Title
Unauthenticated `RecvError` packet allows remote attacker to force tunnel teardown without holding a valid certificate - (File: outside.go)

### Summary
The Kinetiq `StakingManager.receive()` bug is a case of untrusted/unauthenticated inbound data (`HYPE` sent by the system address on withdrawal) automatically driving a privileged state-changing action (`stake()`), corrupting protocol state (the exchange ratio) without any check on who/what triggered it. The closest reachable analog in this codebase is `Interface.handleRecvError`, which processes the unauthenticated, unencrypted `header.RecvError` message type and unconditionally tears down an active tunnel (`closeTunnel`) based only on a loose address match, before any certificate or handshake authentication has occurred on that packet.

### Finding Description
`RecvError` packets are dispatched straight out of `readOutsidePackets` before any decryption or certificate check: [1](#0-0) 

`handleRecvError` then looks up the hostinfo purely by the numeric `RemoteIndex` carried in the plaintext header and validates the sender only by comparing the UDP source address to the hostinfo's currently known remote address: [2](#0-1) 

There is no cryptographic authentication of this packet type at all — no Noise/AEAD verification, no certificate check, and no proof that the sender actually is the peer. The only "guard" is an equality check between the source `netip.AddrPort` of the received UDP datagram and the address Nebula currently believes the peer is reachable at (`hr := hostinfo.GetRemote()`). Any attacker who can spoof the source IP:port of the legitimate peer (feasible on many networks, e.g., via IP spoofing on UDP or from an on-path position) satisfies this check and can trigger `f.closeTunnel(hostinfo)` plus `f.handshakeManager.DeleteHostInfo(hostinfo)` on a live tunnel between two certificate-holding peers — without ever presenting a CA-signed certificate or completing a handshake.

This is analogous to the `StakingManager.receive()` issue in spirit: an unauthenticated inbound message type, gated only on a superficial address match rather than genuine authentication, is allowed to automatically drive a destructive state transition (tearing down protocol state) on behalf of an unverified sender.

### Impact Explanation
An attacker with no valid Nebula certificate, who can merely spoof or observe a peer's UDP source `AddrPort`, can force a targeted tunnel teardown (`closeTunnel` + `DeleteHostInfo`) between two legitimate mesh members. This is a remote state-poisoning / denial-of-service primitive reachable purely from the network path: it disrupts established tunnels, forces renegotiation, and can be repeated to keep two nodes from maintaining a stable session — all without ever being an authenticated peer of the mesh.

### Likelihood Explanation
Likelihood is moderate: the attacker does not need a valid certificate or to complete any handshake step, only the ability to send a UDP packet whose source address matches the peer's currently known remote address. On networks or NAT setups where source-address spoofing of UDP datagrams is possible (or where the attacker is on-path/can observe the target's currently active `AddrPort`, e.g., via traffic monitoring), this check provides essentially no protection, since `RecvError` carries no cryptographic proof of origin.

### Recommendation
Do not allow the plaintext, unauthenticated `RecvError` message type to unilaterally close an established, authenticated tunnel. At minimum:
- Require some rate limiting / corroboration (e.g., only treat `RecvError` as a soft hint, and require multiple consecutive out-of-band confirmations, or a subsequent handshake failure) before calling `closeTunnel`.
- Consider gating `RecvError` handling more strictly than a simple `AddrPort` equality check (e.g., only accept it when it is impossible for an off-path attacker to have observed/guessed that address, or bind acceptance to network conditions where spoofing is not feasible), consistent with the existing `recvErrorConfig` (`Always`/`Never`/`Private`) knobs, and document that `Always`/`Private` weakens teardown authentication.
- Longer-term, consider authenticating `RecvError` (e.g., include a MAC keyed by tunnel state) so that only a peer that has previously completed the handshake for that index can send a trusted teardown signal.

### Proof of Concept
Not executed — no sandbox/terminal access is available in this mode. Conceptually:
1. Establish a legitimate tunnel between node A and node B (valid CA-signed certs, completed handshake), observe B's `hr` (`hostinfo.GetRemote()`) address from traffic analysis or knowledge of B's known endpoint.
2. As an attacker with no certificate, craft a `header.RecvError` packet with `RemoteIndex` set to A's `remoteIndexId` for the A↔B tunnel (learnable from captured traffic headers, since indexes are sent in the clear on data packets).
3. Spoof the UDP source `AddrPort` to match B's currently known remote address (`hr`), and send this crafted packet to A.
4. `handleRecvError` passes the `hr == addr` check, and A calls `f.closeTunnel(hostinfo)` and `f.handshakeManager.DeleteHostInfo(hostinfo)`, tearing down the tunnel — with no certificate or handshake ever presented by the attacker.

Whether this is exploitable in a given deployment depends on network conditions (UDP source spoofing feasibility, NAT behavior, and the configured `recvErrorConfig`/`acceptRecvErrorConfig` mode), which I was not able to fully verify (e.g., exact default value of `acceptRecvErrorConfig` and whether egress spoofing filters are assumed by the threat model) given the available tooling.

```go
func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
```
