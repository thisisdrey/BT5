### Title
Missing zero/null-address validation on user-supplied `receiver` parameter in `borrow` and `collateral-remove-redeem` - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
The external report flags `setGov()` for not validating that the new address isn't the zero address, permanently bricking privileged access. The same class of bug (unvalidated destination address controlled by user input) exists in this codebase's unprivileged, user-facing entry points: `borrow` and `collateral-remove-redeem` in `v0-4-market.clar` resolve an optional `receiver` principal supplied directly by the caller and never verify it is a valid, standard (non-null/burn) address before sending funds to it — unlike the protocol's own `flashloan` function, which explicitly performs this check.

### Finding Description
In `borrow`, the receiver is resolved with no validation: [1](#0-0) 
and later used directly to send borrowed funds: [2](#0-1) 

Similarly, `collateral-remove-redeem` resolves a user-supplied `receiver` for the underlying-asset payout without any address validation before calling `vault-redeem`: [3](#0-2) 

By contrast, the vault's own `flashloan` function — operating on the exact same kind of `(optional principal)` receiver pattern — explicitly guards against an invalid/null resolved address: [4](#0-3) 

This asymmetry shows the codebase already recognizes the risk class (unvalidated destination principal) and mitigates it in `flashloan`, but the same protection is missing on the `borrow` and `collateral-remove-redeem` entry points, which are reachable by any ordinary principal (no privilege required), directly analogous to the reported `setGov()` zero-address gap but for a different address parameter.

### Impact Explanation
If a user (or a bug in a caller contract building the `(optional principal)` argument) supplies a malformed/burn address as `receiver`, borrowed tokens or redeemed underlying assets are sent to that unrecoverable destination. This results in a **temporary/permanent freezing of funds** for that transaction's proceeds — the borrowed principal or redeemed underlying becomes irrecoverable, satisfying the in-scope "temporary freezing of funds" / "permanent freezing of funds" impact classes.

### Likelihood Explanation
Likelihood is moderate: it requires the caller (a normal, unprivileged user or an integrating contract) to pass an invalid/burn address as `receiver`, which can happen through integration bugs, front-end input mishandling, or a mistaken constant, without any additional privilege or governance compromise. This mirrors exactly how the original `setGov()` bug can accidentally occur — a mistaken zero-value input with no code-level backstop — but here the loss falls on ordinary users' own funds rather than gov authority.

### Recommendation
Add the same `is-standard` (or equivalent non-null) validation that `flashloan` already performs to the resolved `receiver` in `borrow` and `collateral-remove-redeem` (and any other public function that resolves an `(optional principal)` receiver before sending funds), e.g.:
```
(asserts! (is-standard funds-receiver) ERR-INVALID-ADDRESS)
```
before the funds-transfer call.

### Proof of Concept
1. Caller invokes `borrow` on `v0-4-market.clar` with `receiver` set to `(some <null-address>)`. [1](#0-0) 
2. `funds-receiver` resolves to the null address with no `is-standard` assertion, unlike `flashloan`'s guard. [4](#0-3) 
3. `vault-system-borrow` sends the borrowed amount to that address, permanently losing the borrowed funds while the user's debt position is still recorded, or (for `collateral-remove-redeem`) the redeemed underlying is sent to the invalid receiver and is unrecoverable. [2](#0-1)

(define-public (collateral-remove-redeem (ft <ft-trait>) (amount uint) (min-underlying uint) (receiver (optional principal)) (price-feeds (optional (list 3 (buff 8192)))))
  (let ((ft-address (contract-of ft))
        (asset (try! (get-asset ft-address)))
        (ztoken-id (get id asset))
        (underlying-id (if (is-eq ztoken-id zSTX) STX
                       (if (is-eq ztoken-id zsBTC) sBTC
                       (if (is-eq ztoken-id zstSTX) stSTX
                       (if (is-eq ztoken-id zUSDC) USDC
                       (if (is-eq ztoken-id zUSDH) USDH
                       (if (is-eq ztoken-id zstSTXbtc) stSTXbtc
                       u100)))))))  ;; invalid sentinel for non-ztoken
        (funds-receiver (match receiver recv recv contract-caller)))

    (asserts! (<= underlying-id stSTXbtc) ERR-UNKNOWN-VAULT)
    
    ;; Step 1: Remove collateral - sends zTokens to THIS contract (market)
    ;; receiver=current-contract so market holds the zTokens
    (try! (collateral-remove ft amount (some current-contract) price-feeds))

    ;; vault-redeem calls vault.redeem which burns shares from contract-caller (market)
    ;; Since market now holds the zTokens, this succeeds
    ;; Underlying tokens are sent to the specified receiver
    (vault-redeem underlying-id amount min-underlying funds-receiver)))
