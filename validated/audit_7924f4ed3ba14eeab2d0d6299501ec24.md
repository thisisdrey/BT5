### Title
Unbounded O(N²) growth in `DelegatedResourceAccountIndexStore` legacy delegate-index path when `AllowDelegateOptimization` is off - ([File: chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java])

### Summary
`FreezeBalanceActuator.delegateResource()` and `UnfreezeBalanceActuator.execute()` maintain a per-owner `DelegatedResourceAccountIndexCapsule` containing a `toAccountsList`/`fromAccountsList` of every distinct counterparty address the account has ever delegated bandwidth/energy to. When `dynamicStore.supportAllowDelegateOptimization()` is false (the legacy, non-optimized code path that is still compiled and reachable), every single delegate/undelegate call reads the entire list, does a linear `List.contains()`/`List.remove()` scan over it, rebuilds an `ArrayList` copy, and writes the whole list back to the store.

### Finding Description
In the legacy branch of `FreezeBalanceActuator.delegateResource()` (`actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java:320-345`, guarded by `!dynamicPropertiesStore.supportAllowDelegateOptimization()`), each `FreezeBalanceContract` transaction that names a new `receiverAddress`:
1. Loads the owner's `DelegatedResourceAccountIndexCapsule` (one serialized protobuf list).
2. Calls `ownerIndexCapsule.getToAccountsList()` and does `toAccountsList.contains(ByteString.copyFrom(receiverAddress))` — an O(k) scan where k is the number of distinct receivers already recorded.
3. If absent, appends and re-serializes the whole (now k+1 element) list back to `DelegatedResourceAccountIndexStore`.

The same pattern occurs in reverse in `UnfreezeBalanceActuator.execute()` (`actuator/src/main/java/org/tron/core/actuator/UnfreezeBalanceActuator.java:156-192`), which copies the list into a new `ArrayList`, does `.remove()`, and writes it back — again O(k) per call.

There is no bound on how many distinct receiver addresses a single owner account can delegate to, and no cap on the size of `toAccountsList`/`fromAccountsList`. A single account issuing N `FreezeBalanceContract` (or `UnfreezeBalanceContract`) transactions to N distinct never-before-seen receiver addresses causes the k-th call to scan/copy/rewrite a list of size k−1, i.e. total work is O(1+2+...+N) = O(N²), while each individual transaction pays only the fixed bandwidth/transaction fee for a constant-size contract payload. This mirrors the Zcash bug class precisely: fee-linear input, but quadratic backend cost due to repeatedly cloning/scanning an unbounded per-entity collection instead of using an O(1) indexed structure.

The newer `delegatedResourceAccountIndexStore.delegate()`/`.delegateV2()` path (used when `AllowDelegateOptimization` is enabled) stores each edge under its own keyed row, avoiding this problem — showing the maintainers were aware indexed storage is required at scale, but the legacy list-based path remains in the codebase and is the active default until the committee proposal enabling optimization is passed on a given network. ### Impact Explanation
Any account can grow its own `toAccountsList`/`fromAccountsList` unboundedly for a fixed, small marginal fee per transaction, while the actual per-transaction processing cost climbs linearly with the account's history and the cumulative cost across N transactions is quadratic. This is an asymmetric-resource-consumption / algorithmic-complexity issue (CWE-407/CWE-405 class) that degrades block processing throughput for every node validating these transactions, without requiring any special privilege — the same class of impact as the cited Zebra advisory (processing stalls, no crash or consensus divergence). Because I could not confirm whether `AllowDelegateOptimization` is currently active on TRON mainnet by default, the practical exploitability depends on network configuration; on any network (private chain, testnet, or a mainnet segment) where this parameter has not been enabled via committee proposal, the legacy path is live and exploitable by any funded account.

### Likelihood Explanation
Reachable by any unprivileged account with a small TRX balance to freeze and pay bandwidth fees; each transaction is a completely valid, single-owner `FreezeBalanceContract`/`UnfreezeBalanceContract` with a distinct receiver address. No proof-of-work-equivalent, SR/witness collusion, or special permission is needed — likelihood is high wherever the legacy path is active, but bounded by whether that legacy path is still the operative configuration on the target network (unverified from static analysis alone).

### Recommendation
- Always use the keyed/indexed delegate storage path (`delegate()`/`delegateV2()`, `unDelegate()`/`unDelegateV2()`) rather than the list-append-and-rewrite path, regardless of `AllowDelegateOptimization`, or remove the legacy path entirely once migration is complete.
- If the legacy list must remain for backward compatibility, cap the maximum number of distinct delegation counterparties per account, or convert the check from `List.contains()`/`List.remove()` over the full list to an O(1) set/map-backed lookup so a single call's cost stays independent of history size.
- Audit other list-append-then-write patterns in `DelegatedResourceAccountIndexStore`/actuators for the same anti-pattern before considering the fix complete.

### Proof of Concept
1. On a network where `dynamicPropertiesStore.supportAllowDelegateOptimization()` is `false` (proposal not yet activated).
2. Fund one account with enough TRX to repeatedly freeze a minimal amount (e.g., 1 TRX) with `FreezeBalanceContract`.
3. Submit N `FreezeBalanceContract` transactions from that owner, each specifying a fresh, never-used `receiverAddress` and `BANDWIDTH`/`ENERGY` resource with `supportDR()` enabled.
4. Each transaction triggers `FreezeBalanceActuator.delegateResource()` → `DelegatedResourceAccountIndexStore.get(ownerAddress)` → `toAccountsList.contains(...)` → append → `put(ownerAddress, ...)`, with the list length growing by one per call.
5. Measure processing time per transaction as N grows; observe linear-in-k per-call cost, hence O(N²) cumulative cost for N transactions, versus the constant per-transaction fee paid. [4](#0-3)

  public void convert(byte[] address) {
    DelegatedResourceAccountIndexCapsule indexCapsule = this.get(address);
    if (indexCapsule == null) {
      // convert complete or have no delegate
      return;
    }
    // convert old data
    List<ByteString> toList = indexCapsule.getToAccountsList();
    for (int i = 0; i < toList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(address, toList.get(i).toByteArray(), i + 1L);
    }

    List<ByteString> fromList = indexCapsule.getFromAccountsList();
    for (int i = 0; i < fromList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(fromList.get(i).toByteArray(), address, i + 1L);
    }
    this.delete(address);
  }

  public void delegate(byte[] from, byte[] to, long time) {
    byte[] fromKey = Bytes.concat(FROM_PREFIX, from, to);
    DelegatedResourceAccountIndexCapsule toIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(to));
    toIndexCapsule.setTimestamp(time);
    this.put(fromKey, toIndexCapsule);

    byte[] toKey = Bytes.concat(TO_PREFIX, to, from);
    DelegatedResourceAccountIndexCapsule fromIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(from));
    fromIndexCapsule.setTimestamp(time);
    this.put(toKey, fromIndexCapsule);
  }
