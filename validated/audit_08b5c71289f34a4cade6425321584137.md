I found a concrete analog in Bazel's own git-repository fetching code. Let me confirm the exact lines and context once more.### Title
Bazel's `git_repository`/`new_git_repository` re-enables Git's disabled `file://` submodule protocol, allowing attacker-controlled repository content to read files outside the repository - ([File: tools/build_defs/repo/git_worker.bzl])

### Summary
Bazel's built-in `git_repository`/`new_git_repository` rules unconditionally pass `-c protocol.file.allow=always` when running `git submodule update`, re-enabling a Git transport that upstream Git disabled by default as a security fix (the class of issue tracked as CVE-2022-39253, "arbitrary file read via local `file://` submodule clone"). Any content that can influence what `.gitmodules` looks like at fetch time — i.e., content served by the git host referenced in `remote` — can therefore point a "submodule" at an arbitrary local path on the machine invoking the fetch, and Bazel/Git will hard-link/copy that path's contents into the workspace, reading data from outside the intended repository tree.

### Finding Description
`git_repo()` in `tools/build_defs/repo/git_worker.bzl` drives the whole fetch: it initializes a bare repo, adds the untrusted `remote` as `origin` [1](#0-0) , resets to the requested ref, and — when `init_submodules`/`recursive_init_submodules` is requested — calls `update_submodules()`: [2](#0-1) 

The comment itself documents that this flag is needed to work around Git 2.38.1's tightened default (`protocol.file.allow=user`), which was introduced specifically to stop untrusted repositories from using `.gitmodules` entries with `file://` URLs to make the local `git submodule update` clone from an arbitrary local path (potentially reading files/directories outside the intended checkout and copying them into the build tree). Bazel's code deliberately overrides that mitigation back to `always` for *every* submodule update, regardless of where the top-level repository content came from.

The `.gitmodules` file, and therefore every submodule URL in it, is ordinary tracked file content of the fetched Git tree. If the `git_repository`/`new_git_repository` invocation does not pin an immutable `commit` (e.g. it uses `branch`, `tag`, or the default branch — all supported, documented attributes of this rule), the origin server named in `remote` fully controls what content is served for that ref on each fetch. This is exactly the "hostile origin server/mirror" scenario the task allows: nothing (no sha256, no lockfile hash) binds the ref's content, so the server is free to serve a `.gitmodules` containing a submodule entry such as:
```
[submodule "x"]
    path = x
    url = file:///home/victim/.ssh
```
When `update_submodules` runs with `protocol.file.allow=always` forced on, Git performs a local clone/hardlink of that absolute path into the submodule directory inside the output base, i.e., a read of files outside the fetched repository's boundary and outside the intended repo/output-base scope — the exact "read outside the repository / exec root / output base" impact category called out in the task rules.

This differs from the excluded "malicious third-party dependency" framing: the vulnerable code is Bazel's own `git_worker.bzl`, and the root cause is that Bazel actively disables a protocol allowlist that upstream Git turned on by default as a security control — the same "OS/tool interprets an attacker-supplied URI scheme it shouldn't" pattern as the Nextcloud report, just with `git` as the "OS default handler" and `file://` as the abused scheme instead of `sftp://`/`ext::`.

### Impact Explanation
An attacker who controls (or compromises) the content served for an unpinned git ref used by `git_repository`/`new_git_repository` with submodules enabled can cause the Bazel-driven fetch to read arbitrary local paths reachable by the invoking user (SSH keys, credentials, `.netrc`, other checked-out repositories, etc.) into the fetched repository's directory tree in the output base. Because the submodule content becomes part of the external repository consumed by the build, it can be further read/exfiltrated by subsequent build steps (e.g. packaged into an output, or if the copied directory itself is a `.git` tree, its hooks or objects could be leveraged for further compromise). This is a containment break of the repository/output-base boundary caused directly by Bazel code, not by untrusted Starlark or a sandboxing gap.

### Likelihood Explanation
Reaching this code only requires a `git_repository`/`new_git_repository` usage with `init_submodules = True` or `recursive_init_submodules = True` and a `remote` pointing at a ref that is not pinned by an exact `commit` (a common, supported configuration, and the only one Bazel offers no integrity guard for besides the commit hash itself). No sandbox bypass, no trusted-BUILD-file cooperation, and no credentials are needed by the attacker — only control over what the origin git server returns for the referenced branch/tag/default-branch at fetch time.

### Recommendation
Do not unconditionally force `protocol.file.allow=always` for submodule updates driven by an externally-controlled repository. Instead, restrict it to cases where the submodule URL is verifiably local/expected (e.g., only for the specific relative-path workaround described in bazelbuild/bazel#17040, or by validating `.gitmodules` submodule URLs before invoking `git submodule update`), and leave Git's upstream `protocol.file.allow=user` (or stricter) default in effect for submodules whose content comes from an untrusted/unpinned remote.

### Proof of Concept
1. Set up an "attacker" bare git repository (standing in for a hostile origin/mirror) at ref `main` whose tree contains a `.gitmodules` file:
   ```
   [submodule "leak"]
       path = leak
       url = file:///absolute/path/to/sensitive/dir
   ```
   where `sensitive/dir` is itself a valid git repository (any content works) located outside the fetch's checkout directory.
2. In a `BuildIntegrationTestCase`/`src/test/shell/bazel` test, declare:
   ```
   git_repository(
       name = "dep",
       remote = "<attacker-repo-url>",
       branch = "main",          # unpinned ref — no commit hash
       init_submodules = True,
   )
   ```
3. Run `bazel fetch @dep` (or a build depending on `@dep`) and inspect the resulting external repository directory in the output base: the `leak/` submodule directory will contain the contents of `sensitive/dir`, demonstrating that content from outside the intended repository/output-base boundary was pulled in via the forced `-c protocol.file.allow=always` in `update_submodules` (`tools/build_defs/repo/git_worker.bzl:210-217`). def update_submodules(ctx, git_repo, recursive = False):
    if recursive:
        # "protocol.file.allow=always" allows the submodule command clone from a local directory.
        # It's necessary for Git 2.38.1 and assoicated backport versions.
        # See https://github.com/bazelbuild/bazel/issues/17040
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--recursive", "--checkout", "--force")
