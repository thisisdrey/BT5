### Title
Dust-transfer griefing fills a victim's per-account token list, blocking deposits, issuance and inbound transfers - ([File: contracts/Pool.sol])

### Summary
`Pool` tracks, per account, which `DepositToken`s and `DebtToken`s the account holds, using `MappedEnumerableSet.AddressSet` capped at `MAX_TOKENS_PER_USER = 30` [1](#0-0) . Any unprivileged attacker can, at near-zero cost, push dust amounts of every `DepositToken` to a victim via `DepositToken.transfer`, filling the victim's `depositTokensOfAccount` set. Once the combined `debtTokensOfAccount.length + depositTokensOfAccount.length` reaches 30, every path that would add a new token to the victim's lists reverts with `UserReachedMaxTokens()` [2](#0-1) , causing a persistent denial of service on the victim's position — the same availability-impact bug class as CVE-2021-2352 (repeatable crash/hang DoS).

### Finding Description
- `addToDepositTokensOfAccount` and `addToDebtTokensOfAccount` are called by `DepositToken._mint`/`_transfer` and `DebtToken._mint`/`_transfer` whenever an account's balance moves from 0 to >0 [3](#0-2) .
- The modifier `onlyIfAdditionWillNotReachMaxTokens` reverts if `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= 30` [2](#0-1) .
- `DepositToken.transfer`/`transferFrom` call `_transfer`, which calls `pool.addToDepositTokensOfAccount(to_)` when `to_`'s balance was zero — so sending 1 wei of each distinct deposit token to the victim occupies a slot each [4](#0-3) .
- Once filled: `DepositToken.deposit(amount, onBehalfOf_ = victim)` reverts in `_mint` (new-token add reverts), `DebtToken.issue`/`mint` to the victim reverts, and any transfer of a token the victim doesn't already hold reverts [5](#0-4) .
- No modifier blocks this: `transfer` is unprivileged, `nonReentrant`/`whenNotPaused` don't help, and the check runs on the *recipient*'s set, which the victim cannot prevent from growing because ERC20 transfers can't be refused.

### Impact Explanation
Availability DoS of a victim's position: the victim cannot open new collateral types, mint new debt tokens, receive deposit tokens (including via `deposit onBehalfOf`), and — critically — cannot be liquidated by a liquidator whose own list is full or receive `seize` proceeds into a fresh token slot. The DoS is temporary but persistent: the victim must first spend gas transferring each dust token out (each removal frees a slot via `removeFromDepositTokensOfAccount` on zero balance [6](#0-5) ) before regaining functionality — during a price crash this delay can be the difference between topping up collateral and being liquidated, i.e., indirect loss of funds plus temporary freezing of the deposit/issue/transfer surface.

### Likelihood Explanation
Cost to attacker: up to 30 dust deposits/transfers (one per supported deposit token), all refundable — purely griefing-cost, no capital lockup. Reachable by any EOA through public `DepositToken.deposit` + `transfer`. Effectiveness depends on how many distinct deposit/debt tokens exist in the deployed pool (governor can add up to `MAX_TOKENS_PER_USER` deposit tokens [7](#0-6) ); the more tokens listed, the cheaper the attack. The victim's only mitigation is manually burning slots, and an attacker can race to refill them.

### Recommendation
- Increment the per-account slot only for tokens with a meaningful balance (e.g., add on first mint only above a threshold), or remove the recipient-side cap entirely and bound the off-chain iteration instead of reverting.
- Alternatively, let accounts `claim`/opt-in to tracking (add only on `deposit`/`issue` initiated by the account owner, not on inbound `transfer`), so unsolicited dust cannot occupy slots.
- At minimum, exempt the `seize`/liquidation path so liquidations of the victim are not blocked by the cap.

### Proof of Concept
Hardhat fork-style outline (reproducible against `test/DepositToken.test.ts` fixtures):

```ts
// attacker fills victim's depositTokensOfAccount
for (const dt of allDepositTokens) {              // up to 30 tokens
  await underlying.connect(attacker).approve(dt.address, MAX)
  await dt.connect(attacker).deposit(dust, attacker.address)
  await dt.connect(attacker).transfer(victim.address, 1) // occupies one slot
}
// victim now at MAX_TOKENS_PER_USER
await expect(
  newDepositToken.connect(victim).deposit(amount, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')
// inbound transfers of any token victim doesn't hold also revert
await expect(
  otherToken.connect(attacker).transfer(victim.address, 1)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')
// victim must spend gas transferring each dust token out to recover
```

Note on certainty: the mechanics (cap, revert, dust-fill via `transfer`) are confirmed in `Pool.sol`/`DepositToken.sol`; the exact severity depends on how many tokens are registered per deployed pool, which I could not fully verify from deployment configs within this review.
