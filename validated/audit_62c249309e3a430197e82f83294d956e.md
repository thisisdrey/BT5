### Title
`AccountLocks::try_lock_transaction_batch` performs conflict checks against a stale pre-batch snapshot, allowing two write-conflicting transactions in the same batch to both acquire write locks - ([File: accounts-db/src/account_locks.rs])

### Summary
`try_lock_transaction_batch` splits the "check" and "apply" steps of account locking into two separate, fully-decoupled loops over the whole batch. The check loop (`can_lock_accounts`) evaluates every transaction in the batch against the *same, unmodified* `self` state (i.e., before any of the batch's own locks are applied), then the apply loop (`lock_accounts`) blindly increments the lock counters for every transaction that passed. Because the check never accounts for locks that other transactions in the *same* batch are about to take, two transactions in one batch that write the same account both pass validation and both get their write-lock counter incremented, breaking the "no concurrent conflicting writers" invariant.

### Finding Description
```rust
pub fn try_lock_transaction_batch<'a>(
    &mut self,
    mut validated_batch_keys: Vec<TransactionResult<impl Iterator<Item = (&'a Pubkey, bool)> + Clone>>,
) -> Vec<TransactionResult<()>> {
    validated_batch_keys.iter_mut().for_each(|validated_keys| {
        if let Ok(keys) = validated_keys.as_ref()
            && let Err(e) = self.can_lock_accounts(keys.clone())
        {
            *validated_keys = Err(e);
        }
    });

    validated_batch_keys
        .into_iter()
        .map(|available_keys| available_keys.map(|keys| self.lock_accounts(keys)))
        .collect()
}

`can_write_lock`/`can_read_lock` are read-only checks against `self.write_locks`/`self.readonly_locks` counters: [2](#0-1) 

`lock_write`/`lock_readonly` simply increment counters with no re-validation: [3](#0-2) 

The check loop (lines 28-34) runs `can_lock_accounts` for every transaction key-set in the batch using only `&self` — it never mutates lock state, so entry N's check does not see the locks that entries 0..N-1 are about to take. Only after the entire batch has been validated does the apply loop (lines 36-39) call `lock_accounts`, which unconditionally increments the write/read counters with no re-check. Consequently, for a batch `[tx_A(write X), tx_B(write X)]`, both entries observe `can_write_lock(X) == true` in the check loop (since neither has locked `X` yet), and both then get `lock_write(X)` applied in the apply loop, leaving `write_locks[X] == 2` and both transactions returned as `Ok(())`. This directly contradicts `can_write_lock`'s own invariant, which is designed to prevent more than one writer at a time. Since `write_locks` is a bare counter with no ownership/identity tracking, incrementing it twice does not error - it silently accepts two concurrent writers on the same account within one locking call.

An attacker who can get two transactions writing the same account key processed together in a single `try_lock_transaction_batch` call (i.e., one call to the batch-locking API covering multiple transactions, as opposed to one call per transaction) can trigger this. This is reachable from unstaked/unprivileged senders because sigverify and QUIC ingress perform no cross-transaction write-key-conflict rejection at the batch level; that responsibility is implicitly assumed to be enforced by locking, exactly the mechanism broken here.

### Impact Explanation
If a leader's execution/replay path passes multiple transactions from attacker-controlled packets into a single `try_lock_transaction_batch` call, both conflicting writers are reported as successfully locked, defeating the "conflicting transactions cannot execute concurrently" guarantee that account locking exists to enforce. Downstream, this can allow two transactions writing the same account to be scheduled/executed as if non-conflicting, producing a double-write/state-corruption scenario and divergence between recorded and executed state - matching the "invalid recorded block / state-consistency violation" bounty category.

### Likelihood Explanation
No stake or special privilege is required - the flaw is purely in `AccountLocks`'s internal check/apply split and triggers deterministically whenever two write-conflicting key sets are present in the same call to `try_lock_transaction_batch`, regardless of ordering. It is 100% reproducible in a unit test with `AccountLocks` alone. Confirming full end-to-end exploitability from `tpu-client`/QUIC ingress requires verifying that the leader's actual call site batches multiple transactions per `try_lock_transaction_batch` invocation (in `accounts-db/src/accounts.rs`) rather than invoking it once per transaction; this call site could not be fully inspected in this session due to tool-call limits, so the finding is scoped strictly to the `AccountLocks` API-level invariant violation, which is unambiguously demonstrable in isolation.

### Recommendation
Merge the check and apply phases back into a single per-transaction, per-key sequential pass so that each transaction's lock application is visible to the validation of subsequent transactions in the same batch call - i.e., iterate the batch once, and for each transaction call `can_lock_accounts` immediately followed by `lock_accounts` before moving to the next transaction (as the original single-transaction `try_lock_accounts` pattern did), rather than validating the whole batch against a stale snapshot before applying any locks.

### Proof of Concept
```rust
// accounts-db/src/account_locks.rs (add to `mod tests`)
#[test]
fn test_try_lock_transaction_batch_rejects_intra_batch_write_conflict() {
    let mut locks = AccountLocks::default();
    let x = Pubkey::new_unique();

    // tx_A writes X, tx_B writes X (same batch call)
    let tx_a_keys = vec![(&x, true)].into_iter();
    let tx_b_keys = vec![(&x, true)].into_iter();

    let batch = vec![Ok(tx_a_keys), Ok(tx_b_keys)];
    let results = locks.try_lock_transaction_batch(batch);

    // Expectation: at most ONE of the two conflicting write-locks may succeed.
    let ok_count = results.iter().filter(|r| r.is_ok()).count();
    assert!(
        ok_count <= 1,
        "both conflicting writers were locked concurrently: {:?}",
        results
    );
}
```
Current behavior: `ok_count == 2` (both `Ok(())`), failing the assertion and demonstrating that `try_lock_transaction_batch` violates the single-writer invariant when two transactions in the same batch conflict on a writable key.
