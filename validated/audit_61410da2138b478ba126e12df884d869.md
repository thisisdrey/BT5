### Title
Unauthenticated `RecvError` packet allows any off-path spoofer to force-close another peer's active tunnel, causing DoS - (File: outside.go)

### Summary
`RecvError` packets in Nebula are processed as unencrypted, pre-authentication packets — before any handshake, certificate, or replay-window check runs. `handleRecvError` accepts such a packet if it merely carries a valid `RemoteIndex` and a source `UdpAddr` matching the target host's currently recorded remote address, then unconditionally tears down the tunnel via `f.closeTunnel(hostinfo)` and deletes the pending handshake state. There is no cryptographic proof that the sender possesses the session keys or the CA-signed certificate associated with that tunnel — exactly the same class of bug as the external report, where a caller with no ownership/authentication relationship to a piece of state (a settlement) could force it into a state that DoSes the legitimate owner.

### Finding Description
In `outside.go`, `readOutsidePackets` dispatches `header.RecvError` packets to `f.handleRecvError` in the "Unencrypted packets" switch, i.e. prior to any Noise handshake authentication or AEAD/replay verification: [1](#0-0) 

`handleRecvError` itself performs only two checks: a config gate (`acceptRecvErrorConfig`) and a loose comparison between the packet's source `netip.AddrPort` and the `HostInfo`'s currently recorded remote address obtained via `hostinfo.GetRemote()`: [2](#0-1) 

Neither check is cryptographic:
- `ShouldRecvError`/`acceptRecvErrorConfig` is a static, non-secret configuration toggle (`recvErrorAlways`, `recvErrorNever`, `recvErrorPrivate`), not a proof of identity. [3](#0-2) 
- The `hostinfo.GetRemote() != addr` check only compares the observed UDP source address/port — trivially satisfiable by any attacker who can spoof UDP source addresses or is on-path (e.g. shared LAN, NAT middlebox, or any position that can inject/spoof UDP toward the target), and who can learn/guess the `RemoteIndex` (a 32-bit value transmitted in cleartext in every packet header of that tunnel).

Once `handleRecvError` accepts the packet, it calls `f.closeTunnel(hostinfo)` and `f.handshakeManager.DeleteHostInfo(hostinfo)`, unconditionally destroying the established, authenticated tunnel state for the legitimate peer — with no way for that peer to prevent or detect the forced teardown beyond re-handshaking.

This mirrors the report's root cause precisely: a state-mutating operation (`retrySettlement`/`closeTunnel`) is reachable by any party that satisfies a weak, non-owner-verifying precondition (arbitrary caller / spoofed source+known index) rather than a proof of legitimate ownership (settlement owner / session key possession), letting an attacker force the target's state into a condition that denies the legitimate party's use of the resource (redeem / active tunnel).

### Impact Explanation
An attacker satisfying the weak precondition can repeatedly force-close any peer's tunnel it can address, causing:
- Denial of service: continuous tunnel teardown and forced re-handshakes, disrupting connectivity for the victim.
- Amplification of cost: each spoofed packet is trivial to construct (fixed 16-byte header, no payload, no cryptographic material) whereas the victim must run an expensive real handshake to recover, similar to how the original bug let an attacker cheaply grief a victim's expensive-to-fix state.
- This is remote state poisoning of established secure sessions without possessing a CA-signed certificate or session keys, which is within the specified reachable attack surface (handshake authentication / firewall enforcement / hostmap trust boundary).

### Likelihood Explanation
Exploitability depends on the attacker's position:
- On-path attackers (shared network segment, compromised router, NAT device) can trivially spoof the required source address and observe the cleartext `RemoteIndex`.
- Pure off-path/remote attackers face normal UDP source-spoofing/ingress-filtering constraints, similar to the "no mempool/front-running" caveat raised in the original report's discussion — but the report was still deemed valid there because the underlying access-control gap is real regardless of attacker positioning assumptions. Here too, the underlying gap (no cryptographic authentication for a destructive state transition) is real; only the ease of exploitation varies with network position, which is analogous to the original finding's back-and-forth on front-running feasibility.

### Recommendation
Do not let an unauthenticated, cleartext control packet (`RecvError`) trigger destructive session teardown based solely on a loose source-address match. At minimum:
- Require some proof tied to the current session (e.g., a MAC over the `RecvError` payload using the session's negotiated keys, or piggyback the recv-error signal in an already-authenticated encrypted control message) before acting on it.
- If backward compatibility requires accepting legacy plaintext `RecvError`, treat it only as a hint to *attempt* a re-handshake rather than as authorization to immediately delete the existing `HostInfo`/`ConnectionState`; keep the old tunnel usable until the new handshake actually completes.
- Rate-limit and log repeated `RecvError`-triggered teardowns per remote/hostinfo to reduce griefing potential.

### Proof of Concept
Conceptual PoC (network-level, mirroring the analog's front-run pattern):
1. Establish a legitimate Nebula tunnel between `me` and `them`; note `them`'s `RemoteIndex` for the tunnel (visible in cleartext in every packet header sent to `me`, e.g. via passive observation on a shared segment).
2. From an on-path/spoofing-capable position, craft a `RecvError` packet: `header.Encode(buf, header.Version, header.RecvError, 0, remoteIndex, 0)`, and send it to `me`'s UDP endpoint with a spoofed source address equal to `them`'s currently known remote `UdpAddr`.
3. `me` calls `handleRecvError`, finds `hr == addr`, and calls `f.closeTunnel(hostinfo)` plus `handshakeManager.DeleteHostInfo(hostinfo)` — tearing down the active, legitimate tunnel with `them` even though the attacker never participated in that tunnel's handshake or held its keys.
4. Repeating this at will produces a persistent DoS against the `me`↔`them` tunnel, comparable to the repeated `retrySettlement(...,0)` griefing described in the original report.

Note: I could not find any cryptographic binding (MAC/signature) protecting the `RecvError` path in the indexed code, nor a rate limiter specific to it; if such protections exist elsewhere in the codebase (e.g., in files not covered by the index due to size limits), they were not found here. A Devin session with full repository access could verify whether any additional mitigations (e.g., recent commits altering `handleRecvError`) exist beyond what's reflected in `CHANGELOG.md`'s notes about `send_recv_error`/`accept_recv_error` config knobs, which govern whether to send/accept but not how strongly to authenticate.

```go
func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
```

```go
type recvErrorConfig uint8

const (
	recvErrorAlways recvErrorConfig = iota
	recvErrorNever
	recvErrorPrivate
)

func (s recvErrorConfig) ShouldRecvError(endpoint netip.AddrPort) bool {
	switch s {
	case recvErrorPrivate:
		return endpoint.Addr().IsPrivate()
	case recvErrorAlways:
		return true
	case recvErrorNever:
		return false
	default:
		panic(fmt.Errorf("invalid recvErrorConfig value: %d", s))
	}
}
```
