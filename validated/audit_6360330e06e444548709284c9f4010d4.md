### Title
Public RPC handlers leak raw internal DB/IO error details (`{:?}` debug dumps) to unauthenticated remote clients - ([File: stackslib/src/net/api/getblock.rs])

### Summary
Several `/v2/*` HTTP RPC handlers in stackslib respond to internal failures by formatting the underlying `chainstate::stacks::Error` / `util_lib::db::Error` (`db_error`) with Rust's `{:?}` debug formatter and returning that string verbatim as the HTTP 500 response body to the requesting (unauthenticated) client. This is the direct code-class analog of GHSA-q5qj-x2h5-3945: on a database-layer failure, internal connection/state information (e.g. wrapped `rusqlite::Error::SqliteFailure` extended messages, `io::Error` details, MARF errors) is echoed to the network caller instead of a generic error.

### Finding Description
`db_error` wraps low-level backends directly: [1](#0-0) 
`SqliteError(sqlite_error)` and `IOError(IOError)` carry the raw `rusqlite`/`std::io` error values, whose `Debug`/extended messages can include filesystem paths and low-level backend diagnostics (analogous to Zitadel's DB host/user/name leak on connection failure).

Multiple public request handlers propagate this raw error text straight into the HTTP body sent to the remote peer:
- `getblock.rs`: `let msg = format!("Failed to load block: {:?}\n", &e);` forwarded via `HttpServerError::new(msg)`. [2](#0-1) 
- `getblock_v3.rs`: same pattern for Nakamoto blocks. [3](#0-2) 
- `blockreplay.rs`: same pattern. [4](#0-3) 
- `postblock.rs`: leaks debug info for both the sortition-ID lookup failure and block-processing failure paths. [5](#0-4) 
- `getpoxinfo.rs`: `format!("Failed to load PoX info: {:?}", &e)`. [6](#0-5) 
- `gettenureblocks.rs`'s shared `ToHttpResponse for db_error` helper, used by several tenure-related endpoints: any non-`NotFoundError` variant is rendered with `format!("{error_msg}: {e:?}")`. [7](#0-6) 
- Shared default trait methods in `httpcore.rs` used across handlers for chain-tip/epoch lookups also debug-dump the `db_error`. [8](#0-7) 

By contrast, other handlers in the same module were explicitly hardened to avoid this (e.g. `getstackerdbchunk.rs` logs the detailed error server-side but returns only a generic `"Failed to load StackerDB chunk"` string to the client), showing the project is aware of this exact class of leak but has not applied it uniformly. [9](#0-8) 

### Impact Explanation
An unauthenticated remote peer that can trigger any DB/IO-layer failure on one of these endpoints (e.g. a bad database state, disk error, or lock error surfaced while resolving a block/tenure/chain-tip lookup) receives the raw internal error text — potentially including local filesystem paths to the node's sqlite/MARF databases and other backend implementation details — in the HTTP response body. This is server-side information disclosure (CWE-200) about the node's internal storage layout/state, which can aid further targeted attacks (e.g., locating on-disk state to attack via other primitives, or fingerprinting node internals).

### Likelihood Explanation
These are default-registered, unauthenticated `/v2/*` RPC endpoints reachable by any remote peer with normal node connectivity; no privileged role or secret key is required. The only requirement is causing the underlying DB layer to return a non-"not found" `db_error`/`ChainError`, which is a normal, reachable failure mode (e.g. transient DB error, locked/corrupt state, disk I/O hiccup) rather than something requiring an implausible setup.

### Recommendation
Standardize all public HTTP RPC handlers to log full error detail (`{:?}`) only server-side via `warn!`/`error!`, and return a generic, non-identifying message to the client (mirroring the pattern already used in `getstackerdbchunk.rs`). Update the shared helpers in `httpcore.rs` (`get_canonical_burn_chain_tip`, `get_stacks_epoch`, `get_stacks_chain_tip`) and `ToHttpResponse for db_error` in `gettenureblocks.rs` to strip raw `db_error`/`ChainError` debug text from the HTTP body.

### Proof of Concept
1. Trigger a DB-layer error condition reachable from a public endpoint (e.g., cause `SortitionDB::get_sortition_id_by_consensus` or `StacksBlockStream::new` to return `Err(db_error::SqliteError(..))`/`Err(db_error::IOError(..))` — for example via a transient lock/I-O failure on the node's sqlite files).
2. Issue the corresponding request, e.g. `GET /v2/blocks/<block_id>` or `POST /v2/blocks`.
3. Observe the HTTP 500 response body containing the raw `{:?}` debug dump of the internal error (potentially including sqlite file paths / backend diagnostics), instead of a generic error string.

impl ToHttpResponse for db_error {
    fn to_http_response(
        self,
        preamble: &HttpRequestPreamble,
        not_found_msg: String,
        error_msg: String,
    ) -> StacksHttpResponse {
        match self {
            db_error::NotFoundError | db_error::BlockHeightOutOfRange => {
                StacksHttpResponse::new_error(preamble, &HttpNotFound::new(not_found_msg))
            }
            e => {
                let msg = format!("{error_msg}: {e:?}");
                error!("{msg}");
                StacksHttpResponse::new_error(preamble, &HttpServerError::new(msg))
            }
        }
    }
