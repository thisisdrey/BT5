## Title
Wallet Contract pays the relayer fee unconditionally, before verifying the requested transfer/action actually succeeds - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The reported bug class is about token-transfer helper functions (`Router.convert`, `addLiquidity`, etc.) that fire a transfer and then proceed as if it succeeded without checking whether the transfer actually happened, risking silent failures. The closest reachable analog in nearcore is the ETH-implicit account **Wallet Contract** (NEP-518), which is the on-chain contract an ordinary Ethereum-style user relies on to execute base-token transfers and ERC-20-emulated (NEP-141) transfers relayed by a third party. In `inner_rlp_execute`, the relayer's compensation fee is paid out via an independent, unchained promise *before* the actual requested action (base transfer or `ft_transfer`) is known to succeed.

### Finding Description
`inner_rlp_execute` in `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs` builds the relayer refund and the user's requested action as two **separate, unlinked promises**: [1](#0-0) 

The refund is created with `env::promise_batch_create(&context.predecessor_account_id)` / `env::promise_batch_action_transfer(refund_promise, *fee)` directly, completely independent from the `Promise` chain that eventually executes the user's intended `Action` (base `Transfer` or the NEP-141 `ft_transfer`/`storage_deposit` sequence built later in the same function): [2](#0-1) 

Because these are two distinct receipts with no data/callback dependency between them, the relayer-fee receipt executes and finalizes regardless of the outcome of the main action's receipt. If the main action later fails (e.g., `ft_transfer` fails because the wallet lacks sufficient token balance, or the transfer targets a non-existent/invalid account), that failure is only surfaced later via `rlp_execute_callback`'s `PromiseResult::Failed` branch, which merely refunds the `caller_deposit` (attached NEAR yoctoNEAR value) — it does **not** claw back or cancel the relayer fee that was already unconditionally paid out of the wallet's own NEAR balance: [3](#0-2) 

This mirrors the report's bug class: a value-moving operation (`transfer`) is performed and then treated as done/paid without gating it on the actual success of the associated operation it was meant to compensate for.

### Impact Explanation
The ETH-implicit account (an ordinary user's wallet) pays the relayer fee even when the transaction it signed and paid for completely fails to execute. Since the nonce is incremented immediately for the `ERC20Transfer`/`EOABaseTokenTransfer` (fee != current-account) code paths before the promise is dispatched (see `inner_rlp_execute` lines 358-365), the fee-bearing transaction cannot be resubmitted, so the user permanently loses the fee amount with no service rendered — theft of value paid by the account holder to a relayer that provided no benefit. This directly reduces the user's NEAR balance without an offsetting successful transfer, i.e., a loss of funds from the eth-implicit account.

### Likelihood Explanation
Any relayer using an authorized `FunctionCall` access key that is allowed to call `rlp_execute` on the ETH-implicit account can relay a user-signed transaction whose associated action is guaranteed or likely to fail (e.g., an ERC-20/NEP-141 transfer where the wallet's token balance has already been spent, or a target account that no longer exists) while the `fee` is still collected. No privileged/validator/node role is required — this is reachable purely from the ordinary transaction path (`rlp_execute` function call), matching the "unprivileged-signer" scope of this review.

### Recommendation
Chain the relayer-fee transfer to the outcome of the main action instead of firing it eagerly and independently. For example, only dispatch `promise_batch_action_transfer` for the fee from within `rlp_execute_callback`/`nep_141_storage_balance_callback` after observing `PromiseResult::Successful` for the underlying action, or attach the fee transfer as a batched action to the *same* receipt as the requested transfer/`ft_transfer` call so that a failure of the main action would also prevent (or, since NEAR batched actions in one receipt are atomic, correctly roll back) the fee payment.

### Proof of Concept
1. User signs an RLP/EIP-2930 transaction encoding an ERC-20 `transfer` (mapped to NEP-141 `ft_transfer`) with a non-zero relayer `fee`, where the wallet's token balance is (or becomes, e.g., via a race with another prior relayed transfer) insufficient to cover the transferred `value`.
2. A relayer holding the `rlp_execute`-scoped access key calls `rlp_execute(target, tx_bytes_b64)`.
3. `inner_rlp_execute` immediately creates the relayer-fee transfer promise (`env::promise_batch_create` / `promise_batch_action_transfer`), independent from the `ft_transfer` promise chain (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:381-385`).
4. The `ft_transfer` cross-contract call fails (insufficient balance) → `rlp_execute_callback` observes `PromiseResult::Failed` and returns `success: false`, but the relayer-fee receipt has already independently succeeded and paid out the fee (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:296-311`).
5. The wallet's nonce was already incremented (step in `inner_rlp_execute`), so the user cannot resubmit; the fee is permanently lost with no successful transfer having occurred.
