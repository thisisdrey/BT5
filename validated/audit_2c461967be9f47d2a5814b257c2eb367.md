## Title
Fixed-gas `rlp_execute_callback` reservation lets an oversized callee response permanently strand the Wallet Contract in `has_in_flight_tx == true` - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The ETH-implicit Wallet Contract serializes every `rlp_execute` transaction with an in-progress flag, `has_in_flight_tx`, that must be reset by a follow-up callback receipt. For the generic "Near native action" path, the callback is scheduled with a **fixed** static gas amount (`RLP_EXECUTE_CALLBACK_GAS = 5 Tgas`) that does not scale with the size of data the target contract can return, unlike the two other code paths (ERC-20 transfer / address-check) which explicitly add `action.gas()` to the callback budget.

### Finding Description
`rlp_execute` sets `has_in_flight_tx = true` before returning a promise, and every possible follow-up callback (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`) resets it to `false` as its first statement: [1](#0-0) [2](#0-1) 

The general-purpose ("Near native action") branch of `inner_rlp_execute` schedules the callback with only the fixed `RLP_EXECUTE_CALLBACK_GAS` (5 Tgas), unlike the ERC-20 and address-check branches which add `action.gas()` on top of the callback's static reservation: [3](#0-2) 

`rlp_execute_callback` must consume `env::promise_result(0)`'s `Successful(value)` bytes and copy them into `ExecuteResponse.success_value`, which is then borsh/JSON-serialized as the method's return value: [4](#0-3) 

A `target` contract chosen by the user/relayer (any `FunctionCall` action) can legally return data up to the protocol's `max_length_returned_data` limit (4 MiB, as exercised in `test_promise_input_size_limit_fails_callback`): [5](#0-4) 

Copying/serializing megabytes of data inside a callback that only reserved 5 Tgas can exhaust the callback's gas budget, causing that receipt to fail with `GasExceeded` before it commits its state write. Because NEAR contract execution only commits state changes if the function call completes without panicking/erroring, the earlier commit of `has_in_flight_tx = true` (from the `rlp_execute` receipt) is never undone. All subsequent calls to `rlp_execute` immediately hit the early-return guard and refuse to do anything: [6](#0-5) 

There is no other exposed method to clear `has_in_flight_tx`; `ban_relayer` and the other callbacks are `#[private]` and only reachable via the promise chain that itself failed. This exactly mirrors the reported bug class: a value is written into durable state without validating that it cannot later cause every relevant control-flow path to permanently revert/refuse, "soft-bricking" the account rather than the whole protocol.

### Impact Explanation
An ETH-implicit account (or a relayer with only `FunctionCall` access acting on its behalf) can direct `rlp_execute` at any contract, including one that returns data close to the 4 MiB return-value ceiling. If the fixed 5 Tgas callback budget is insufficient to process that payload, the callback receipt fails and `has_in_flight_tx` is stuck at `true` forever. Since this flag gate is the *only* entry point for using the wallet (all other paths — `AddKey` with full access, `DeleteAccount` — are already disallowed for ETH-implicit accounts), the account's balance becomes permanently inaccessible: a permanent freezing of funds for that account. This can happen accidentally (a legitimate dApp/contract returning a large result) or be triggered deliberately by a malicious/uncooperative relayer or by an attacker who convinces a relayer to route a call through an oversized-response contract.

### Likelihood Explanation
Reaching the vulnerable branch only requires submitting one ordinary `rlp_execute` call whose decoded action is a Near-native `FunctionCall` targeting a contract that returns data whose processing cost in the callback exceeds 5 Tgas — no privileged role, and the call is a fully valid, protocol-visible transaction. The likelihood of hitting the exact gas threshold depends on the actual per-byte gas cost of value handling versus the 5 Tgas reservation, which was not independently benchmarked here, so exploitability at exactly 4 MiB (vs a smaller size) is not proven with certainty — only the structural absence of any gas-scaling or fallback-recovery mechanism is proven from the code.

### Recommendation
Scale the callback's static gas reservation in the generic action branch by the callee's declared `action.gas()` and/or by a term proportional to `max_length_returned_data`, mirroring what is already done for the ERC-20 and address-check paths. Additionally, consider decoupling `has_in_flight_tx` clearing from the same receipt that must also process potentially large/attacker-influenced payloads (e.g., resetting the flag in a minimal, gas-cheap step before any variable-cost processing), and/or providing a recovery path (e.g., a privileged/owner-only or time-locked reset) so a single failed callback cannot permanently strand the account.

### Proof of Concept
Not independently executed; the trace below is derived from static analysis of the cited code paths:
1. Deploy/target a contract `C` whose method returns a value near `max_length_returned_data` (4 MiB), analogous to `return_large_value` used in `test_promise_input_size_limit_fails_callback`.
2. Craft an RLP-encoded Ethereum transaction whose decoded Near action is `FunctionCall` targeting `C`, with `target` not matching any ETH-emulation/ERC-20 special case, so it goes through the fallback branch in `inner_rlp_execute` (lines 466-470) that reserves only `RLP_EXECUTE_CALLBACK_GAS` for the callback.
3. Submit via `rlp_execute`; the wallet sets `has_in_flight_tx = true` and schedules `C`'s call followed by `.then(rlp_execute_callback)`.
4. When `C` returns its large payload, `rlp_execute_callback` must copy/serialize it inside its fixed 5 Tgas budget; if this exceeds the budget, the callback receipt fails with `GasExceeded`, and its `has_in_flight_tx = false` write is discarded.
5. Any further `rlp_execute` call on this account immediately short-circuits with "transaction already in progress" indefinitely, permanently locking the account's funds.

    pub fn rlp_execute_callback(
        &mut self,
        caller_deposit: Option<CallerDeposit>,
    ) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        let n = env::promise_results_count();

        if n == 0 {
            // `rlp_execute_callback` is called directly in the case of an emulated self-transfer.
            return ExecuteResponse { success: true, success_value: None, error: None };
        } else if n > 1 {
            return ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(format!(
                    "Invariant violation: this callback comes after a single promise. n={n}"
                )),
            };
        }

        match env::promise_result(0) {
            PromiseResult::Failed => {
                // The cross-contract call failed, refund the caller if needed
                if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
                    let refund_promise = env::promise_batch_create(&account_id);
                    env::promise_batch_action_transfer(
                        refund_promise,
                        NearToken::from_yoctonear(yocto_near.into()),
                    );
                }

                ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }
            PromiseResult::Successful(value) => {
                ExecuteResponse { success: true, success_value: Some(value), error: None }
            }
        }
    }
