### Title
Unbounded `FrozenSupply` list in `AssetIssueContract` causes unmetered per-entry state growth in `AssetIssueActuator.execute` - (File: actuator/src/main/java/org/tron/core/actuator/AssetIssueActuator.java)

### Summary
`AssetIssueActuator.validate()` never checks the size of `assetIssueContract.getFrozenSupplyList()`, and `execute()` iterates that list unbounded, building a `Frozen` entry and appending it to the issuing account's `frozenSupply` protobuf field for every element. An unprivileged asset-issuer transaction can supply an arbitrarily large `FrozenSupply` array, forcing large iteration and unbounded growth of the persisted `Account` capsule.

### Finding Description
`AssetIssueActuator.validate()` [1](#0-0)  checks many fields (name, precision, url, description, start/end time) but never validates `assetIssueContract.getFrozenSupplyList()` size or count, unlike the bounded `VoteWitnessContract.getVotesCount()` check in `VoteWitnessActuator` (`MAX_VOTE_NUMBER`) or the `getTotalSignNum` bound in `AccountPermissionUpdateActuator.checkPermission`.

In `execute()`, the actuator unpacks the contract, then unconditionally loops over the entire `FrozenSupply` list: [2](#0-1) 

Each iteration builds a `Frozen` object and appends it to `frozenList`, which is then merged wholesale into the owner account's `frozenSupply` repeated field via `addAllFrozenSupply(frozenList)`. There is no cap analogous to `MAX_ACTIVE_ORDER_NUM`/`MAX_MATCH_NUM` in `MarketSellAssetActuator`, or the `permission.getKeysCount() > dynamicStore.getTotalSignNum()` check that bounds keys in `AccountPermissionUpdateActuator`. Because `FrozenSupply` is a plain repeated protobuf message inside `AssetIssueContract`, its size is limited only by the overall transaction size limit, not by any semantic check specific to this field, so a broadcaster can pack many `FrozenSupply` entries into one `AssetIssueContract` to inflate loop iterations and permanently bloat the account's serialized state (which is stored on-chain and re-read/re-serialized on every future account load/save).

This mirrors the reported bug class (unchecked externally supplied array length driving unbounded loop work in a single transaction), but here the impact is state bloat / node processing cost, not "out of gas" refund loss for the user (since the actor triggering it also pays for it) — the more material issue is that the resulting frozen-supply state is permanently written and later iterated again (e.g., in `UnfreezeAssetActuator.execute()` which also loops the full list), leading to repeated cost amplification and larger `Account` records for the lifetime of the asset.

### Impact Explanation
An attacker issuing an asset with an oversized `FrozenSupply` array causes:
- Unbounded work in `AssetIssueActuator.execute()` for a single transaction, larger than any comparable actuator (contrast with the explicit `MAX_MATCH_NUM = 20` guard in `MarketSellAssetActuator` and 5-key permission cap in `AccountPermissionUpdateActuator`).
- A permanently bloated `Account` protobuf (`frozenSupply` field), which will be repeatedly deserialized/serialized on every subsequent read/write of that account, and re-iterated in full inside `UnfreezeAssetActuator.execute()` [3](#0-2)  each time the owner tries to unfreeze, degrading node performance for that account indefinitely.

This is a resource/state-bloat concern rather than a direct fund-theft or freezing-of-funds bug, since the `remainSupply` accounting still works correctly for any list size (each entry only subtracts `frozenAmount` from `remainSupply`).

### Likelihood Explanation
Any account can call `AssetIssueContract` (subject to paying the `AssetIssueFee` and having no existing issued asset), so the precondition is trivially met by any unprivileged broadcaster. The only constraint is the raw transaction size limit enforced elsewhere in the codebase (`TooBigTransactionException`), which bounds — but does not eliminate — the number of `FrozenSupply` entries that can be packed in.

### Recommendation
Add an explicit bound on `assetIssueContract.getFrozenSupplyCount()` in `AssetIssueActuator.validate()`, analogous to the `MAX_VOTE_NUMBER` check in `VoteWitnessActuator` or the key-count check in `AccountPermissionUpdateActuator`, e.g.:
```java
if (assetIssueContract.getFrozenSupplyCount() > MAX_FROZEN_SUPPLY_NUMBER) {
  throw new ContractValidateException("Frozen supply list is too long");
}
```

### Proof of Concept
1. Craft an `AssetIssueContract` with a `FrozenSupply` list containing the maximum number of entries that fit under the transaction size limit (each `FrozenSupply` entry is small — just `frozenAmount`/`frozenDays`).
2. Broadcast the transaction as any account with sufficient balance to pay `AssetIssueFee` and no previously issued asset.
3. Observe `AssetIssueActuator.execute()` iterating the full list [4](#0-3)  and writing all entries into the account's `frozenSupply` field, with no validation error raised, unlike other actuators that reject oversized repeated fields before execution.
