### Title
Out-of-bounds read when parsing ZIP/JAR central directory entry length fields in ijar - (File: `third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` in the `ijar` interface-jar tool reads the file-name, extra-field and comment length fields directly from an attacker-supplied `.jar`/`.zip` file and uses them to advance a raw pointer and `memcpy` bytes, without ever validating that the declared lengths fit inside the memory-mapped input buffer.

### Finding Description
`ijar`/`zip.cc` maps an untrusted `.jar` file with `mmap(NULL, length, PROT_READ, MAP_PRIVATE, fd, 0)` and exposes the raw bytes for parsing [1](#0-0) . `FindZipCentralDirectory` only validates that `central_dir_offset + central_dir_size <= in_length` for the archive as a whole [2](#0-1) ; it never validates that any individual central-directory record's declared `file_name_length`/`extra_field_length`/`file_comment_length` fits within the remaining bytes of that central directory (or of the mmap'd file).

`ProcessCentralDirEntry` then reads these 16-bit length fields straight off the wire and immediately uses them to `memcpy` the file name and to walk the extra-field chain, with no bounds check against the end of the mapped buffer: [3](#0-2) 

This is in sharp contrast to the sibling function `ProcessLocalFileEntry`, which explicitly guards every read with `EnsureRemaining()` before consuming file-name/extra-field bytes [4](#0-3)  and to `InputJar::NextEntry` in the separate `singlejar` tool, which checks `mapped_file_.mapped(new_cdr)` before dereferencing the next central directory header [5](#0-4) . `ProcessCentralDirEntry` has no equivalent guard.

A crafted central directory entry with an oversized `file_name_length`, `extra_field_length`, or `file_comment_length` (larger than the bytes actually remaining in the mmap'd region) causes:
1. `memcpy(filename, p, len)` to read past the end of the mapped file into whatever follows in the process address space [6](#0-5) , and
2. the subsequent extra-field walk (`while (extra_p != p)`) to read `header_id`/`data_size` from out-of-bounds memory and potentially loop indefinitely past the buffer if `extra_p` overshoots `p` [7](#0-6) .

Because `filename` (populated from the OOB read) is later used to decide inclusion and is copied into the generated interface JAR's local/central headers via `WriteLocalFileHeader`/`WriteCentralDirectory`, adjacent process memory contents can leak into the build output artifact, not merely crash the process.

### Impact Explanation
This is a concrete out-of-bounds read directly analogous to CVE-2023-45229 (unvalidated length field driving a read past a buffer boundary). Depending on layout, it results in a crash (denial of service, out of scope per the rules) or — more significantly — disclosure of adjacent heap/mmap memory bytes that get embedded into the resulting `.jar`/interface-jar written to the output tree, a confidentiality-impacting out-of-bounds read.

### Likelihood Explanation
`ijar` is invoked automatically by Bazel to generate interface jars for `java_import`/`java_library` targets whose input `.jar` may originate from third-party sources fetched via `http_jar`/`http_archive`/Maven coordinates. An attacker who controls the content served at such a URL (and who can pass or forge a checksum, or targets a build lacking a pinned `sha256`) can supply a jar with a malformed central directory record to trigger this path with no further privilege required.

### Recommendation
Add explicit bounds checks (mirroring `EnsureRemaining` in `ProcessLocalFileEntry`) in `ProcessCentralDirEntry` before consuming `file_name_length`, `extra_field_length`, and `file_comment_length`, verifying that `p + <declared length>` stays within `[zipdata_in_, zipdata_in_ + input_file_->Length())` before any `memcpy` or pointer advance, and before parsing individual extra-field records.

### Proof of Concept
Construct a minimal ZIP whose End-Of-Central-Directory record legitimately points at a central directory of size N bytes, but whose single central directory header declares `file_name_length = 0xFFFF` (far larger than the bytes actually remaining before EOF). Feed this file to the `ijar` binary (`bazel-bin/third_party/ijar/ijar malicious.jar out.jar`, or transitively via `java_import`/`java_library` on such a jar). `ProcessCentralDirEntry`'s `memcpy(filename, p, len)` reads past the mmap'd region, and the produced `out.jar` central/local headers embed the leaked bytes. A `BuildIntegrationTestCase`/shell test can assert that building a `java_library` depending on such a crafted jar either crashes the `ijar` action or produces an interface jar containing bytes not present in the crafted input.
