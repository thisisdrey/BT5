### Title
Gas-admission clamp bypass in `try_forward` causes real (unclamped) gas to be deducted from `forward_limit.gas`, starving other receipts destined to the same shard - (File: `runtime/runtime/src/congestion_control.rs`)

### Summary
`try_forward` computes an admission gas value clamped to `allowed_shard_outgoing_gas` for the purpose of the admission check, but then deducts the full, unclamped `gas` from `forward_limit.gas` via `saturating_sub`. This mismatch lets a single oversized receipt (e.g. a FunctionCall with near-max attached gas) pass the admission check cheaply while consuming (or zeroing out) the entire remaining gas budget for that destination shard in the current chunk, blocking forwarding of other receipts—including third-party ones—to that shard.

### Finding Description
In `try_forward` [1](#0-0) :

- The admission check computes a clamped value: `admission_gas = gas.min(allowed_shard_outgoing_gas)` under `ProtocolFeature::ClampOutgoingGasAdmission` [2](#0-1) .
- The gate itself only compares `forward_limit.gas >= admission_gas` [3](#0-2) .
- But the actual charge subtracted from the shard's remaining budget uses the raw, unclamped `gas`: `forward_limit.gas = forward_limit.gas.saturating_sub(gas)` [4](#0-3) .

Because `gas` (a receipt's total prepaid gas, which can be close to the ~300 Tgas attached-gas ceiling for a FunctionCall) can be far larger than `allowed_shard_outgoing_gas`, a receipt is admitted based on the small clamped value but "charges" the full real value against `forward_limit.gas`. Since `saturating_sub` floors at zero rather than going negative, a single such receipt can drive `forward_limit.gas` to `0` for the remainder of the chunk, even though the admission check only verified the (much smaller) clamped amount was available. This directly violates the intended invariant that the total gas dispatched to a shard within a chunk should be bounded by the shard's granted `allowed_shard_outgoing_gas`/bandwidth-scheduler grant — instead a single receipt can consume the *entire* nominal budget outright.

No existing validation stops this: the FunctionCall attached-gas ceiling, nonce/signature checks, and access-key permission checks are all satisfied by an ordinary account submitting a normal cross-shard call with high attached gas — there is nothing privileged about crafting a receipt with `gas` close to the maximum attached-gas limit.

### Impact Explanation
This is a liveness/availability bug in congestion control, not a fund-theft or consensus-divergence bug. `forward_limit` is recomputed fresh each chunk from the receiving shard's current congestion state (`CongestionControl`), so the effect is scoped to the current chunk: any receipt destined to the same shard which is later in the outgoing buffer (or produced in the same chunk) after the oversized receipt is admitted can be denied forwarding this chunk purely because the mis-accounted `forward_limit.gas` was zeroed out well beyond what the shard's granted budget actually allowed. If the attacker's receipt is repeatedly placed ahead of (or interleaved with) victim receipts in the per-shard outgoing buffer (FIFO order), this can be repeated chunk after chunk, delaying forwarding of legitimate third-party receipts (including value transfers) to the congested shard. This is a scoped, targeted denial-of-service against traffic to a specific shard, matching a "temporary freezing/delay of funds via liveness degradation" bounty category — it is not a permanent freeze since forwarding resumes once budgets are recomputed and the attacker's oversized receipt is not repeated, and it does not cause state-root divergence since both the check and the subtraction are deterministic and consensus-consistent (all validators compute the same buggy result).

### Likelihood Explanation
Preconditions: the target shard must already be under congestion control such that `allowed_shard_outgoing_gas` is meaningfully smaller than the attacker's receipt's `gas` (this occurs naturally when the receiving shard is congested — the scenario congestion control exists to manage). The attacker needs only an ordinary funded account able to submit a transaction/FunctionCall with high attached gas destined cross-shard — no privileged access is required, and this is directly reachable via public RPC. Repeatability is bounded by needing to place an oversized receipt at/near the head of the outgoing buffer for the target shard each chunk, and cost to the attacker is the gas/fees for their own receipt (largely refunded unused-gas amounts under NEAR's gas refund model), making repeated attempts relatively cheap. However, achieving *guaranteed* head-of-queue placement every chunk to permanently starve third parties is not fully demonstrated by the code alone — it depends on buffer FIFO ordering and bandwidth scheduler grant timing, which would need to be validated with an integration/runtime test.

### Recommendation
Make the amount deducted from `forward_limit.gas` consistent with what was actually checked during admission — i.e., subtract `admission_gas` instead of the raw `gas`, or equivalently reject/clamp the receipt's contribution so that the total gas charged against a shard's outgoing limit in one chunk never exceeds what admission verified was available:

```rust
forward_limit.gas = forward_limit.gas.saturating_sub(admission_gas);
```

Alternatively, if the clamp is only intended to let a single oversized receipt through if it fits within the limit only when clamped (a valid use case for compatibility), ensure the accounting reflects the same clamped quantity everywhere it's used (stats, size checks, and the subtraction), so remaining budget bookkeeping never diverges from what the check enforced.

### Proof of Concept
Unit test plan in `runtime/runtime/src/congestion_control.rs` tests module:
1. Enable protocol version with `ClampOutgoingGasAdmission`.
2. Configure `allowed_shard_outgoing_gas` to a small value (e.g. 10 Tgas) and set `forward_limit.gas` to that same small value for a target shard.
3. Call `try_forward` with a receipt whose `gas` is far larger (e.g. 300 Tgas, simulating a max-attached-gas FunctionCall) destined to that shard — assert it is `Forwarded` (demonstrating the admission clamp bypass).
4. Immediately call `try_forward` again with a modest "victim" receipt (`gas` well under `allowed_shard_outgoing_gas`) to the same shard — assert under current code it is `NotForwarded` (bug reproduced) because `forward_limit.gas` was driven to `0` by the unclamped subtraction of the first receipt.
5. After applying the fix (subtracting `admission_gas` instead of `gas`), rerun the same sequence and assert the victim receipt is `Forwarded`, and that the sum of amounts subtracted across all receipts admitted in the chunk never exceeds the shard's granted `allowed_shard_outgoing_gas`/`forward_limit.gas` starting value.

```rust
    fn try_forward(
        receipt: Receipt,
        gas: Gas,
        mut size: u64,
        shard: ShardId,
        outgoing_limit: &mut HashMap<ShardId, OutgoingLimit>,
        outgoing_receipts: &mut Vec<Receipt>,
        apply_state: &ApplyState,
        stats: &mut ReceiptSinkStats,
    ) -> Result<ReceiptForwarding, RuntimeError> {
        // There is a bug which allows to create receipts that are above the size limit. Receipts
        // above the size limit might not fit under the maximum outgoing size limit. Let's pretend
        // that all receipts are at most `max_receipt_size` to avoid receipts getting stuck.
        // See https://github.com/near/nearcore/issues/12606
        let max_receipt_size = apply_state.config.wasm_config.limit_config.max_receipt_size;
        if size > max_receipt_size {
            tracing::debug!(
                target: "runtime",
                receipt_id=?receipt.receipt_id(),
                size,
                max_receipt_size,
                "try_forward observed a receipt with size exceeding the size limit",
            );
            size = max_receipt_size;
        }

        // Default case set to `Gas::MAX`: If no outgoing limit was defined for the receiving
        // shard, this usually just means the feature is not enabled. Or, it
        // could be a special case during resharding events. Or even a bug. In
        // any case, if we cannot know a limit, treating it as literally "no
        // limit" is the safest approach to ensure availability.
        let default_gas_limit = Gas::MAX;

        // Since bandwidth scheduler, a shard is not allowed to send any receipts if it doesn't have a grant.
        let default_size_limit = 0;

        let default_outgoing_limit =
            OutgoingLimit { gas: default_gas_limit, size: default_size_limit };
        let forward_limit = outgoing_limit.entry(shard).or_insert(default_outgoing_limit);

        let admission_gas = if ProtocolFeature::ClampOutgoingGasAdmission
            .enabled(apply_state.current_protocol_version)
        {
            gas.min(apply_state.config.congestion_control_config.allowed_shard_outgoing_gas)
        } else {
            gas
        };

        if forward_limit.gas >= admission_gas && forward_limit.size >= size {
            tracing::trace!(target: "runtime", ?shard, receipt_id=?receipt.receipt_id(), "forwarding buffered receipt");
            outgoing_receipts.push(receipt);
            forward_limit.gas = forward_limit.gas.saturating_sub(gas);
            forward_limit.size -= size;
            stats.forwarded_receipts.entry(shard).or_default().add_receipt(size, gas);

            Ok(ReceiptForwarding::Forwarded)
        } else {
            tracing::trace!(target: "runtime", ?shard, receipt_id=?receipt.receipt_id(), "not forwarding buffered receipt");
            Ok(ReceiptForwarding::NotForwarded(receipt))
        }
    }
```
