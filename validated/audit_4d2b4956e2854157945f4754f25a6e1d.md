### Title
Unprivileged attacker can permanently block a victim from onboarding new collateral/debt token types via dust `DepositToken` transfers that fill the victim's `MAX_TOKENS_PER_USER` account list - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
Each `Pool` tracks per-account deposit/debt token lists in `depositTokensOfAccount` / `debtTokensOfAccount` (`MappedEnumerableSet`), capped at `MAX_TOKENS_PER_USER = 30` by `onlyIfAdditionWillNotReachMaxTokens`. Because `DepositToken.transfer`/`transferFrom` are public, callable by any EOA, and register the *recipient* in the pool's list whenever `balanceOf[recipient] == 0`, an attacker can dust-transfer 1 wei of every registered `DepositToken` to a victim, irreversibly filling the victim's 30 slots. Thereafter any mint of a *new* deposit token (fresh `deposit`) or new debt token (fresh `issue`/`leverage`) to that account reverts inside `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount`, denying the victim new position types.

### Finding Description
- `DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's prior balance is 0 and `amount_ > 0` (DepositToken.sol:517-520). `transfer` (line 348) and `transferFrom` (line 357) only enforce `_revertIfLocked` on the *sender* — there is no opt-in or minimum amount on the recipient side.
- `Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` apply `onlyIfAdditionWillNotReachMaxTokens`, which reverts with `UserReachedMaxTokens` when `debtTokensOfAccount + depositTokensOfAccount >= 30` (Pool.sol:143-148). Confirmed by test/Pool.test.ts:1386-1416.
- Attack: attacker deposits dust into each of the pool's N deposit tokens (cost = N tiny deposits), then calls `depositToken.transfer(victim, 1)` for each token the victim doesn't hold. Each transfer adds one entry to `depositTokensOfAccount[victim]`. Entries are never removable by anyone except a zero-balance burn of that token by the victim — and the victim cannot remove tokens the attacker chose if removal requires bringing each balance to 0 (they can `transfer` the dust away, which calls `removeFromDepositTokensOfAccount`, but doing so costs them gas per entry and the attacker can re-fill them in the same block they attempt a deposit, i.e., front-run).
- Debt side: any `DebtToken._mint` to the victim (via `issue`/`leverage`/`flashIssue` paths where `to_`/`account_` is the victim) calls `pool.addToDebtTokensOfAccount` (DebtToken.sol:598-600), which also reverts once combined slots are full — so a victim at cap cannot open debt positions in *new* synthetic assets either.
- No privileged actor is required: no oracle manipulation, no governor/guardian, no malicious LZ endpoint. Reentrancy guard does not help — `transfer` itself is unguarded, and `transferFrom`'s `nonReentrant` is per-contract so batch dust transfers through different `DepositToken` contracts succeed.

### Impact Explanation
Liveness/availability impact matching the InnoDB DoS bug class: the victim is denied the ability to (a) deposit any collateral type they don't already hold, and (b) issue any synthetic asset they don't already owe. For a victim with an unhealthy position, the ability to add a *different* collateral type to rescue the position is permanently lost, exposing them to liquidation loss that they cannot prevent via new collateral. The victim's existing balances remain withdrawable, so this is a partial (but persistent and repeatedly re-applicable at near-zero marginal cost) denial of service on core protocol functionality — deposits and issuance — rather than full fund freezing.

### Likelihood Explanation
High reachability: only requires an unprivileged EOA with dust amounts of each underlying; no flash loan needed, no privileged role. The main limiting factor is that the number of filled slots is bounded by the number of `DepositToken`s actually registered in the pool (attacker cannot mint fake entries — `addToDepositTokensOfAccount` only accepts calls from registered deposit tokens via `SenderIsNotDepositToken`). On pools with few collaterals the attacker alone cannot reach 30, but combined with the debt-token side and with pools supporting many collaterals (e.g., mainnet deployments with many vault-share collaterals), the cap is reachable. Victim mitigation (transferring dust out to pop entries) can be front-run/griefed repeatedly, since each re-add costs the attacker only a `transfer` call.

### Recommendation
- Make account-list registration opt-in or economically gated: e.g., only add the token on `deposit`/`issue` (mint paths), not on bare `transfer`, or require a minimum threshold amount for list registration.
- Alternatively, allow `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` to no-op instead of revert at cap when invoked from `transfer`, while still enforcing the cap on `deposit`/`issue`.
- Optionally provide a public "prune" function letting an account force-remove a deposit token entry while forfeiting/sweeping its dust balance.

### Proof of Concept
Hardhat/fork sketch (unverified against deployment; structure follows existing `test/Pool.test.ts` helpers):

```ts
// Setup: pool with N registered DepositTokens (d1..dN), victim = bob, attacker = alice
for (const dt of depositTokens) {
  // attacker obtains a tiny deposit-token balance
  await underlying.connect(alice).approve(dt.address, DUST);
  await dt.connect(alice).deposit(DUST, alice.address);
  // push 1 wei to victim -> registers dt in depositTokensOfAccount[victim]
  await dt.connect(alice).transfer(bob.address, 1);
}

const len = await pool.getDepositTokensOfAccount(bob.address);
// Repeat until combined (deposit + debt) length == 30

// Victim tries to deposit a collateral type they don't yet hold
await expect(
  newDepositToken.connect(bob).deposit(1, bob.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// Victim tries to issue a synth whose debt token they don't yet hold
await expect(
  newDebtToken.connect(bob).issue(MIN_AMOUNT, bob.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

Note: reproducibility on a fork requires the target pool to expose enough distinct `DepositToken`s/`DebtToken`s to reach the cap of 30; on pools with fewer registered tokens the attacker alone cannot fill the list.
