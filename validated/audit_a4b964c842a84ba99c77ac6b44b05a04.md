### Title
Permanent freezing of user funds via predictable TIP-2935 system-account address takeover - (File: framework/src/main/java/org/tron/core/db/HistoryBlockHashUtil.java)

### Summary
`HistoryBlockHashUtil.deploy()` writes contract code/metadata to a fixed, publicly-known address (`HISTORY_STORAGE_ADDRESS = 0x410000f90827f1c53a10cb7a02335b175320002935`) and, if an `AccountCapsule` already exists there, mutates it in place into a `Contract`-type account rather than rejecting or safely handling pre-existing state. [3](#0-2)  Any unprivileged user can trivially create an account at this address today by sending TRX, TRC10 tokens, or freezing balance for bandwidth/energy to it, since account creation on TRON only requires a transfer to an address, not a valid signature from it.

### Finding Description
The `deploy()` method is invoked from `ProposalService.process()` when the `ALLOW_TVM_PRAGUE` proposal is approved by the committee — a normal, expected governance/hard-fork event, not a malicious action. [1](#0-0) 

Inside `deploy()`, the only guard against pre-existing state is a check on the `CodeStore`/`ContractStore`: [4](#0-3) . The `AccountStore` entry is not treated the same way — if an account already exists at `HISTORY_STORAGE_ADDRESS` (which anyone can create merely by sending assets to it before the fork activates), the code takes the *existing* `AccountCapsule`, calls `updateAccountType(Contract)` and `clearDelegatedResource()`, and writes it back: [3](#0-2) .

`clearDelegatedResource()` only zeroes the *acquired* delegated-resource counters; it does not touch the account's own TRX balance, TRC10 asset holdings, self-frozen bandwidth/energy balance (v1/v2), or votes: [5](#0-4) . Because nobody can hold a valid ECDSA private key for this canonical, EIP-2935-style address (it is chosen to be unspendable by construction, mirroring the Ethereum specification's own deploy-sender pattern documented in the same file's comments), once the address is flipped to `AccountType.Contract` and populated with the fixed `BlockHashHistory` bytecode (which only supports reading historical block hashes, with no withdrawal or transfer entry point), any TRX, TRC10 balance, or frozen stake resident at that address becomes permanently unreachable by any signed transaction. There is no mechanism, before or after the `deploy()` call, that prevents ordinary users from funding this specific address, and no recovery path exists once the address becomes a system contract.

### Impact Explanation
This directly meets the "permanent freezing of funds" impact bar. Because the target address is fixed, well-known, and computed the same way on every full node, any user (attacker or unwitting third party) who sends TRX, issues/transfers TRC10 tokens to, or freezes balance for bandwidth/energy at `HISTORY_STORAGE_ADDRESS` before the network-wide `ALLOW_TVM_PRAGUE` proposal is activated will have those funds irreversibly locked the moment the committee-approved upgrade takes effect. Unlike the CREATE2 in-EVM collision case (which requires deliberate, privileged contract-deployer interaction and only affects funds sent to a specific deployer-chosen contract address), this canonical address is reachable via a simple, unprivileged TRX transfer from any account, and the loss is triggered by an unrelated, legitimate governance action outside the depositor's control.

### Likelihood Explanation
Reaching the vulnerable state requires only a standard TRX/TRC10 transfer to a fixed, publicly documented address — no special privileges, contract deployment, or malicious actor cooperation are needed. The trigger (committee approval of `ALLOW_TVM_PRAGUE`) is a normal one-time protocol-upgrade event that the codebase already anticipates and executes automatically via `ProposalService.process()`. Because the address is derived directly from the EIP-2935 specification and is publicly visible in the client source and documentation, it is straightforward for any node operator or user to discover and interact with prior to activation.

### Recommendation
Before flipping the account type in `HistoryBlockHashUtil.deploy()`, explicitly validate that no meaningful state (non-zero balance, TRC10 asset holdings, frozen v1/v2 balances, votes, or custom permissions) is present at `HISTORY_STORAGE_ADDRESS`. If any such state is found, either: (1) skip the deploy and log/alert similarly to the existing foreign-code branch, requiring a follow-up governance decision on how to handle the funds, or (2) refund/migrate the balance and resources to a recoverable location (e.g., burn to the blackhole account or return to depositors) before converting the account to `Contract` type, rather than silently absorbing and stranding the assets.

### Proof of Concept
1. Prior to the network activating the `ALLOW_TVM_PRAGUE` proposal, any account sends TRX (and/or TRC10 tokens, and/or freezes balance for bandwidth/energy) to `410000f90827f1c53a10cb7a02335b175320002935` — a normal, unprivileged transfer/freeze transaction that any broadcaster can send.
2. This creates a normal `AccountCapsule` with a non-zero balance/asset/frozen-resource state at that address in the `AccountStore`.
3. When the committee's `ALLOW_TVM_PRAGUE` proposal reaches its maintenance-cycle activation, `ProposalService.process()` calls `HistoryBlockHashUtil.deploy(manager)`.
4. `deploy()` finds the existing account, calls `account.updateAccountType(Contract)` and `account.clearDelegatedResource()` (which does not clear balance/assets/self-frozen resources), and writes it back to the `AccountStore`, alongside deploying the fixed `BlockHashHistory` bytecode at that address.
5. From this point forward, the address is type `Contract` running immutable read-only bytecode with no private key known to anyone; the TRX/TRC10/frozen balances deposited in step 1 can never be moved by any subsequent signed transaction, permanently freezing those funds.

```java
  public static void deploy(Manager manager) {
    if (manager.getCodeStore().has(HISTORY_STORAGE_ADDRESS)
        || manager.getContractStore().has(HISTORY_STORAGE_ADDRESS)) {
      logger.warn("TIP-2935: foreign state at {}, skipping deploy",
          Hex.toHexString(HISTORY_STORAGE_ADDRESS));
      return;
    }

    manager.getCodeStore().put(HISTORY_STORAGE_ADDRESS,
        new CodeCapsule(HISTORY_STORAGE_CODE));
    manager.getContractStore().put(HISTORY_STORAGE_ADDRESS,
        new ContractCapsule(HISTORY_STORAGE_CONTRACT));

    AccountCapsule account = manager.getAccountStore().get(HISTORY_STORAGE_ADDRESS);
    boolean accountExisting = account != null;
    if (!accountExisting) {
      account = new AccountCapsule(HISTORY_STORAGE_ACCOUNT);
    } else {
      account.updateAccountType(Protocol.AccountType.Contract);
      account.clearDelegatedResource();
    }
    manager.getAccountStore().put(HISTORY_STORAGE_ADDRESS, account);
```
