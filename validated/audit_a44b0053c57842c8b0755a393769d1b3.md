### No Vulnerability found for this question.

**Reasoning:**
The named target — "primary handler" in `runtime/near-vm-runner/src/logic/mod.rs` — does not exist as described. `mod.rs` is purely a module declaration file with no logic: [1](#0-0) 

The actual `storage_write`, `storage_read`, and `storage_remove` host functions live in `runtime/near-vm-runner/src/logic/logic.rs` (and the wasmtime variant in `runtime/near-vm-runner/src/wasmtime_runner/logic.rs`), not in `mod.rs`. [2](#0-1) [3](#0-2) 

More importantly, the recorded-storage limit enforcement mechanism itself is intact: every `storage_write`/`storage_read`/`storage_remove`/`storage_has_key` call invokes `self.recorded_storage_counter.observe_size(self.ext.get_recorded_storage_size())?` immediately after performing the trie operation, and `RecordedStorageCounter::observe_size` returns `HostError::RecordedStorageExceeded` as soon as the observed size exceeds `size_limit`, aborting the receipt. [4](#0-3) 

This check runs after each individual operation (bounded in size by `max_length_storage_key`/`max_length_storage_value`), so the counter can only overshoot the limit by at most one bounded operation's contribution before erroring out — matching the documented design ("hard limit, receipts which generate more than that will fail"). [5](#0-4) 

There is no code path shown where the limit check is skipped, bypassed, or where an attacker-controlled input length "exactly at the accepted maximum" defeats the accounting — the counter uses an upper-bound estimate (`recorded_storage_size_upper_bound`) specifically to stay conservative and never undercount. [6](#0-5) 

Since the stated target function/file doesn't match the actual code (mismatch between claimed location and reality), and the real enforcement path shows no bypass, this finding does not hold up.

    /// Update the latest observed storage proof size and check if it exceeds the limit.
    /// Should be called after every trie operation.
    pub fn observe_size(&mut self, latest_storage_proof_size: usize) -> Result<(), VMLogicError> {
        self.last_observed_storage_size = latest_storage_proof_size;

        let current_size = self.get_storage_size()?;
        if current_size > self.size_limit {
            let limit_u64 = self.size_limit.try_into().map_err(|_| {
                VMLogicError::InconsistentStateError(InconsistentStateError::IntegerOverflow)
            })?;
            return Err(VMLogicError::HostError(HostError::RecordedStorageExceeded {
                limit: ByteSize::b(limit_u64),
            }));
        }

        Ok(())
    }

    fn get_recorded_storage_size(&self) -> usize {
        // `recorded_storage_size()` doesn't provide the exact size of storage proof
        // as it doesn't cover some corner cases (see https://github.com/near/nearcore/issues/10890),
        // so we use the `upper_bound` version to estimate how much storage proof
        // could've been generated by the receipt. As long as upper bound is
        // under the limit we can be sure that the actual value is also under the limit.
        self.trie_update.trie().recorded_storage_size_upper_bound()
    }
