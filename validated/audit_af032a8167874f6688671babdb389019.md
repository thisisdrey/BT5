## Title
Relayer tip funds are burned on AssetHub before the corresponding reward credit is confirmed on BridgeHub, causing permanent loss of user funds when the tip fails to attach - (File: `bridges/snowbridge/pallets/system-frontend/src/lib.rs`, `bridges/snowbridge/pallets/system-v2/src/lib.rs`)

### Summary
The Snowbridge V2 "add tip" flow burns/teleports the user's tip asset synchronously on the sending chain (AssetHub) and only *afterwards* asynchronously asks BridgeHub to credit that value to a pending message's reward via an XCM `Transact`. If that credit step fails (most commonly because the targeted message was already delivered/removed by a relayer in the meantime), BridgeHub merely records the amount in an informational `LostTips` map — it does not, and structurally cannot, reverse the burn that already happened on AssetHub. This mirrors the external report's root cause: an action that destroys/removes real value is decoupled from the accounting step that is supposed to make that value "count", and the accounting step can silently fail or diverge from the real balance movement, leaving no way to reconcile.

### Finding Description
`snowbridge_pallet_system_frontend::Pallet::add_tip` immediately swaps the tip asset for Ether and burns/teleports it via `burn_for_teleport`: [1](#0-0) 

This burn is irrevocable and happens in the same extrinsic on AssetHub, regardless of what happens later on BridgeHub. The pallet then builds and sends an `EthereumSystemCall::AddTip` via an `UnpaidExecution` `Transact` XCM to BridgeHub: [2](#0-1) 

On BridgeHub, `pallet_snowbridge_system_v2::add_tip` forwards the amount to either the inbound or outbound queue's `AddTip::add_tip`. If that call fails (e.g. `UnknownMessage`/`InvalidPendingNonce` because the order was already resolved by `process_delivery_receipt` or `process_message` before the tip arrived), the amount is only logged into `LostTips` — a storage map with no automatic refund/mint mechanism: [3](#0-2) 

The underlying `AddTip` implementation on the outbound queue simply increments `order.fee` if the `PendingOrders` entry for that nonce still exists, and returns `AddTipError::UnknownMessage` otherwise — with no fallback to compensate the sender: [4](#0-3) 

The core broken invariant is identical to the external report: **value removed from a user/account must be conserved into the exact accounting bucket that will later cause it to be reissued/paid.** Here, the burn on AssetHub happens unconditionally and first, while the corresponding credit on BridgeHub (`order.fee += amount`, which is what ultimately drives `T::RewardPayment::register_reward` in `process_delivery_receipt`) is a separate, later, best-effort, unpaid cross-chain step that can fail for reasons entirely outside the tipper's control (relay/timing race with delivery receipt processing). There is no atomicity, no rollback of the AssetHub burn, and `LostTips` provides no code path that actually returns or remints the lost value — it is purely a bookkeeping stub ("Capturing the lost tips here supports implementing a recovery method in the future"), as the code comment itself concedes.

### Impact Explanation
This directly causes permanent, unrecoverable user-fund loss: an ordinary account can lose its tip in full whenever a race between message delivery and tip delivery occurs, which is entirely plausible under normal bridge relaying speeds (a diligent relayer can process/deliver a message and call `submit_delivery_receipt` before the tipper's slower XCM `Transact` reaches BridgeHub). No malicious actor, governance, or admin is required — it is a natural consequence of asynchronous cross-chain messaging combined with an irrevocable synchronous burn. This satisfies the "permanent user-fund lock" / value-conservation impact category in scope for the program, since burned value is not reissued anywhere once the tip attach step fails.

### Likelihood Explanation
High. Any user calling `add_tip` on a message that is close to being finalized by relayers (which is the most economically rational moment to add a tip, i.e., an already fast-moving/near-completion delivery) is exposed to this race. No special privileges or conditions beyond normal transaction ordering/latency are needed, and the loss is deterministic once the race is lost — `LostTips` accumulates but is never paid out by any code in this repository.

### Recommendation
Do not burn/teleport the tip asset on AssetHub until the corresponding `add_tip` acceptance on BridgeHub is confirmed, or make the flow reversible/compensating:
- Hold/reserve the tip asset on AssetHub instead of unconditionally burning it, and only finalize the burn after a confirmation (e.g., via a receipt/ack XCM from BridgeHub) that the tip was successfully attached to the pending order.
- Alternatively, implement the promised "recovery method" for `LostTips` so failed tips are actually remintable/refundable to the `sender`, and make sure whatever the recovery is credits the exact account and exact amount that was burned.

### Proof of Concept
1. User A submits an outbound message to Ethereum via `pallet_snowbridge_system_v2`; a `PendingOrder{nonce, fee}` is created in `outbound-queue-v2`.
2. User A calls `system-frontend::add_tip(message_id = Outbound(nonce), asset)`. This swaps/burns the tip asset immediately on AssetHub via `swap_fee_asset_and_burn` [5](#0-4)  and sends an `UnpaidExecution` `Transact` XCM toward BridgeHub.
3. Before that XCM is executed on BridgeHub, a relayer submits `submit_delivery_receipt` for the same nonce, which calls `process_delivery_receipt`, removing the `PendingOrders` entry for that nonce [6](#0-5) .
4. The delayed `add_tip` XCM Transact now executes on BridgeHub; `OutboundQueue::add_tip` returns `AddTipError::UnknownMessage` since the order no longer exists [7](#0-6) .
5. `pallet_snowbridge_system_v2::add_tip` catches the error and only records it in `LostTips::<T>::mutate(&sender, ...)` [8](#0-7)  — the extrinsic itself still returns `Ok(())`, and User A's originally burned tip asset is never returned or otherwise reissued anywhere in the codebase.

Uncertainty note: I was unable to locate any pallet/extrinsic elsewhere in the indexed codebase that reads and redeems `LostTips`, but given index size limits, it's possible such a redemption path exists in a file not surfaced by search. If the user needs certainty on this, a full-repository review via a Devin session (not just the indexed subset) would confirm whether `LostTips` is ever paid out.

		pub fn add_tip(
			origin: OriginFor<T>,
			sender: AccountIdOf<T>,
			message_id: MessageId,
			amount: u128,
		) -> DispatchResult {
			T::FrontendOrigin::ensure_origin(origin)?;

			let result = match message_id {
				Inbound(nonce) => <T as pallet::Config>::InboundQueue::add_tip(nonce, amount),
				Outbound(nonce) => <T as pallet::Config>::OutboundQueue::add_tip(nonce, amount),
			};

			if let Err(ref e) = result {
				tracing::debug!(target: LOG_TARGET, ?e, ?message_id, ?amount, "error adding tip");
				LostTips::<T>::mutate(&sender, |lost_tip| {
					*lost_tip = lost_tip.saturating_add(amount);
				});
			}

			Self::deposit_event(Event::<T>::TipProcessed {
				sender,
				message_id,
				amount,
				success: result.is_ok(),
			});

			Ok(())
		}

		fn add_tip(nonce: u64, amount: u128) -> Result<(), AddTipError> {
			ensure!(amount > 0, AddTipError::AmountZero);
			PendingOrders::<T>::try_mutate_exists(nonce, |maybe_order| -> Result<(), AddTipError> {

					Some(order) => {
						order.fee = order.fee.saturating_add(amount);
