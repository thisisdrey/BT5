### Title
Dust-transfer resource exhaustion of `MAX_TOKENS_PER_USER` blocks victim deposits, liquidations, and leverage exits - ([File: contracts/Pool.sol])

### Summary
Analogous to CVE-2021-23409 (descriptor/connection-slot exhaustion DoS), `Pool` enforces a fixed slot resource per account: `debtTokensOfAccount.length + depositTokensOfAccount.length < MAX_TOKENS_PER_USER (30)` checked in `onlyIfAdditionWillNotReachMaxTokens`. An unprivileged attacker can forcibly consume a victim's slots by dust-transferring `DepositToken` shares (`_transfer` adds the token to the recipient's list on first receipt), permanently bricking that account's ability to take new positions and causing liquidation `seize` calls to revert for seized collateral types the liquidator hasn't held before.

### Finding Description
`Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` are callable only by registered DepositToken/DebtToken contracts, and they enforce the cap:

- `onlyIfAdditionWillNotReachMaxTokens` reverts `UserReachedMaxTokens` when combined list length >= 30 [1](#0-0) 
- `DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's prior balance was 0, and `DepositToken.transfer` only requires the *sender* to have unlocked balance — there is no opt-in or allowance check on the recipient side [2](#0-1) [3](#0-2) 
- `DepositToken.deposit(amount_, onBehalfOf_)` lets anyone mint deposit shares to an arbitrary `onBehalfOf_` account, providing a second forced-fill vector [4](#0-3) 

Attack: the attacker deposits minimal collateral into each of the pool's deposit tokens, then calls `msdTOKEN_i.transfer(victim, 1)` for ~30 distinct deposit tokens (or uses `deposit(1, victim)`). Each first-time transfer inserts a slot; once `debtTokensOfAccount.length(victim) + depositTokensOfAccount.length(victim) == 30`:

1. Victim cannot `deposit` into any new collateral type — `_mint` → `addToDepositTokensOfAccount` reverts — so they cannot top up collateral to rescue an unhealthy position [5](#0-4) 
2. `Pool.liquidate` → `DepositToken.seize` → `_transfer` reverts whenever the liquidator's list is full *or* — more importantly for the attack — any flow that would add a token to the victim's full list reverts, blocking debt restructuring paths.
3. `DebtToken._mint` → `addToDebtTokensOfAccount` reverts, blocking `issue`/`mint`/`leverage` of a synthetic the victim hasn't used [6](#0-5) 
4. `SmartFarmingManager.leverage`/`flashRepay` paths that mint a new deposit token type for the user revert, freezing leveraged exits.

Removal only happens when a balance returns to zero, so the victim can only recover by spending gas to `transfer`/`withdraw` each dust token out — a reversible but griefing-heavy cleanup, and the attacker can re-dust at negligible cost.

### Impact Explanation
Temporary freezing of funds and forced liquidation: a victim whose position goes unhealthy cannot deposit a new collateral type (the only type that may save them if existing collateral is exhausted or devalued), so the position becomes liquidatable and the collateral is seized — direct loss of user funds caused by the DoS. New deposits, new debt issuance, and smart-farming operations on the account revert indefinitely until the victim manually drains each dust balance.

### Likelihood Explanation
Fully unprivileged: attacker only needs dust amounts of each listed underlying (plus deposit fees). No governor/keeper/oracle involvement, no price manipulation, no reentrancy. The cap is a hard constant (30) and no `whenNotPaused`/health check prevents the forced slot insertion. The only mitigation is that deposit tokens are limited to ≤30 pool-wide, so an account with existing debt tokens is easier to fill; cost scales with the number of enabled collateral types.

### Recommendation
Do not count tokens added via unsolicited inbound transfers/deposits against the recipient's cap, or decouple the cap from the enumerable set used for health accounting — e.g., only revert on `add` for the calling user action and let `_transfer` skip list insertion (tracking balances independently), or allow recipients to permissionlessly remove zero/dust entries (`removeFromDepositTokensOfAccount` on balance==0 already exists — expose a "clean account" function callable by anyone for entries whose balance is 0 or below a dust threshold).

### Proof of Concept
Hardhat/Foundry fork sketch:

```solidity
// pool with N deposit tokens msD_0..msD_k
// 1) Attacker acquires dust of each deposit token:
for (uint i; i < k; ++i) {
    underlying_i.approve(address(msD_i), 1);
    msD_i.deposit(1, attacker);          // or transfer pre-acquired dust
}
// victim already holds some debt tokens such that remaining slots < k
// 2) Fill victim's slots:
for (uint i; i < k; ++i) {
    msD_i.transfer(victim, 1);           // _transfer adds msD_i to victim's list
}
// now debtTokensOfAccount[victim].length + depositTokensOfAccount[victim].length == 30

// 3) Victim attempts to deposit a new collateral type to rescue position:
underlyingNew.approve(address(msD_new), amount);
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
msD_new.deposit(amount, victim);

// 4) Victim's unhealthy position is liquidated; collateral seized, attacker profit ~ dust cost
pool.liquidate(synthetic, victim, repayAmount, msD_x);
```

Key assertions: `msD_i.transfer(victim, 1)` succeeds (sender has free balance since dust adds negligible lock), each call increments `getDepositTokensOfAccount(victim).length`, and the subsequent `msD_new.deposit` reverts with `UserReachedMaxTokens`.
