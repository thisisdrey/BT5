### Title
StackerDB chunk signatures omit the target contract ("audience"), enabling cross-StackerDB chunk replay - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` — the message that a StackerDB writer signs — commits only to `slot_id`, `slot_version`, and `data_hash`. It never includes the `QualifiedContractIdentifier` (the specific StackerDB instance/"audience") that the chunk is destined for. `try_replace_chunk` in `stackslib/src/net/stackerdb/db.rs` and `validate_received_chunk`/`handle_unsolicited_StackerDBPushChunk` in `stackslib/src/net/stackerdb/mod.rs` verify the signature only against the *slot's owning address* recorded for the *contract passed in as a parameter* — but that parameter is attacker-controlled (via the `/v2/stackerdb/:address/:contract/chunks` POST endpoint or via gossip `StackerDBPushChunkData.contract_id`) and is never bound into what was actually signed. Because Stacks Nakamoto signer-slot assignment (`stackslib/src/chainstate/stacks/boot/signers.clar`, `signer_set.rs::update_signers`) gives the same signer the same relative slot index across all of that signer's per-message-kind StackerDB contracts within a reward cycle, this is a real, reachable "aud" confusion: a validly-signed chunk observed on one StackerDB contract can be resubmitted verbatim to a *different* StackerDB contract where the same signer owns the same `slot_id`, and it will pass every check (signature, freshness, size, write-count) even though the signer never signed for that destination contract.

### Finding Description
This is a "wrong-audience" acceptance bug, directly analogous to the Jenkins OIDC plugin's failure to check the `aud` claim: a token/signature that is cryptographically valid — but was scoped to a different intended recipient/context — gets accepted anyway because the verifier never checks that the message was meant for *this* context.

Concretely:
- `SlotMetadata::auth_digest()` hashes only `slot_id.to_be_bytes()`, `slot_version.to_be_bytes()`, and `data_hash.0` [5](#0-4) . No contract/DB identifier is part of the signed payload.
- `SlotMetadata::verify()` / `StackerDBChunkData::verify()` recover the pubkey hash from that digest and compare against the caller-supplied `principal`/`addr` — they have no way to know or enforce which StackerDB contract the signer intended [6](#0-5) .
- `StackerDBTx::try_replace_chunk(smart_contract, slot_desc, chunk)` looks up the slot's owning signer *for the given `smart_contract`* and calls `slot_desc.verify(&slot_validation.signer)` — if the target contract happens to assign the same address to the same `slot_id`, the check passes regardless of which contract the signature was actually produced for [2](#0-1) .
- The HTTP write path `RPCPostStackerDBChunkRequestHandler::try_handle_request` takes the target `contract_identifier` straight from the URL path (fully attacker-controlled) and passes it into `try_replace_chunk` together with the (replayed) chunk body [4](#0-3) .
- The P2P/gossip path is equally exposed: `PeerNetwork::validate_received_chunk` is keyed by the `smart_contract_id` extracted from the incoming `StackerDBPushChunkData`/inv message, and only checks the signature against the slot signer *for that contract id* [3](#0-2) .
- Signer-slot assignment is index-based and identical in structure across the paired per-message-kind contracts for a reward cycle (`stackerdb-get-signer-slots-page`, `update_signers`), so the same signer address commonly maps to the same `slot_id` across multiple StackerDB contracts simultaneously in production.

An attacker who merely *observes* a chunk being broadcast or served (StackerDB chunks are, by design, publicly readable/gossiped — no secret key is needed to obtain one) can resubmit the identical `(slot_id, slot_version, sig, data)` tuple against a different target contract path/gossip message. If the destination contract's slot-signer table happens to assign the same address that slot, and the destination slot's current version is lower than the replayed one, the write succeeds and is then relayed further into the P2P network (`node.set_relay_message(StacksMessageType::StackerDBPushChunk(...))`), propagating attacker-triggered but victim-signed data into an unintended StackerDB.

### Impact Explanation
This maps to the Critical bucket per instructions: unauthenticated/unauthorized write to state (StackerDB) achieved without possessing anyone's private key, and network-wide propagation of the (cross-context) chunk once accepted, since successful writes trigger `set_relay_message`, further gossiping the misapplied chunk to peers. This can corrupt or desynchronize the intended contents of an unrelated StackerDB instance (e.g. causing signer-message and other StackerDB consumers to read stale/foreign data as if it were legitimately written for that DB), without requiring any credentials beyond observing already-public traffic.

### Likelihood Explanation
Likelihood is bounded by the precondition that the *destination* StackerDB contract must assign the *same address* to the *same slot_id* as the source contract, and the destination slot's stored version must be lower than the replayed chunk's version. Given the deterministic, index-based slot assignment scheme shared by paired per-message StackerDB contracts within a reward cycle, this precondition is realistic without any secret information — an attacker only needs to observe the contract layouts (which are public, queryable via read-only Clarity calls like `stackerdb-get-signer-slots-page`) and any already-broadcast chunk.

### Recommendation
Bind the destination StackerDB contract identity into the signed payload. Extend `SlotMetadata::auth_digest()` (and correspondingly `StackerDBChunkData`/verification call sites) to include the target `QualifiedContractIdentifier` (or a network/consensus-scoped identifier analogous to a JWT `aud` claim) so that a signature produced for one StackerDB instance cannot be replayed as valid for another. This requires a coordinated wire-format/signing change across `libstackerdb`, `stackslib/src/net/stackerdb/*`, `stackslib/src/net/api/poststackerdbchunk.rs`, and signer-side signing code in `stacks-signer`/`libsigner`.

### Proof of Concept
1. Reward cycle `N` establishes two StackerDB contracts, `signers-0-A` (message kind A) and `signers-0-B` (message kind B), both derived from the same ordered signer list, so signer `S` at list index `k` maps to `slot_id = k` in both.
2. Signer `S` signs and posts a legitimate chunk `(slot_id=k, slot_version=v, sig, data)` to `signers-0-A` via the normal signer flow; this chunk is now publicly visible (served via `/v2/stackerdb/.../chunks` GET, and gossiped).
3. An unrelated attacker (no keys needed) captures this `(slot_id, slot_version, sig, data)` tuple and issues `POST /v2/stackerdb/<signers-0-B-address>/<signers-0-B-name>/chunks` with the identical body.
4. `RPCPostStackerDBChunkRequestHandler::try_handle_request` resolves the target contract from the URL, calls `try_replace_chunk` against `signers-0-B`; since `S` also owns `slot_id=k` there and (assuming `v` exceeds `signers-0-B`'s current stored version for that slot) `slot_desc.verify(&slot_validation.signer)` succeeds — the chunk is accepted and relayed, even though `S` never signed anything intending it for `signers-0-B`.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Sign this slot metadata, committing to slot_id, slot_version, and
    /// data_hash.  Sets self.signature to the signature.
    /// Fails if the underlying crypto library fails
    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
