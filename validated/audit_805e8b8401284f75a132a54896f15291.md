Based on my investigation, I found a concrete privilege-escalation gap in how `AccountPermissionUpdateContract` interacts with multisig "Active" permissions.

### Title
Active permission can be granted the right to invoke `AccountPermissionUpdateContract`, allowing an active-key holder to unilaterally overwrite the Owner permission - (File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java)

### Summary
`AccountPermissionUpdateActuator` allows any `Active` permission's `operations` bitmap to include the bit for `AccountPermissionUpdateContract` (type 46) itself, because its `checkPermission()` validates the operations bitmap only against the system-wide `AVAILABLE_CONTRACT_TYPE` list, which includes this contract type. There is no dedicated safeguard preventing an `Active` permission (a lower-trust, often lower-threshold key set) from being empowered to rewrite the account's `Owner` permission. This mirrors the EOSBank incident pattern where owner-level authority was altered/stolen through a permission that should not have had that power, and it was subsequently used to drain funds.

### Finding Description
`checkPermission()` in `AccountPermissionUpdateActuator` validates an `Active` permission's `operations` bitmap bit-by-bit only against `dynamicStore.getAvailableContractType()`: [1](#0-0) 

The system-wide `AVAILABLE_CONTRACT_TYPE` bitmap (verified by the `checkAvailableContractType` test) includes essentially all contract types, and explicitly does **not** exclude `AccountPermissionUpdateContract` — only `UpdateBrokerageContract` is excluded: [2](#0-1) 

By contrast, the *default* active permission's operations (`ACTIVE_DEFAULT_OPERATIONS`, used by `AccountCapsule.createDefaultActivePermission`) deliberately excludes `AccountPermissionUpdateContract`, confirming that the intended security model is that only the Owner permission (id 0) should be able to modify account permissions: [3](#0-2) [4](#0-3) 

Because `checkPermission()` in the actuator only checks against the broader `getAvailableContractType()` list (not a restricted "owner-only" set), nothing stops an account from configuring — or being tricked into configuring — an `Active` permission whose `operations` bitmap grants it the right to call `AccountPermissionUpdateContract`. Once such an active permission exists, a transaction signed under that active `permissionId` will pass signature/permission checks in `TransactionCapsule.validateSignature`, which looks up the permission by `permissionId` from the contract, and validates weight/threshold without enforcing that `AccountPermissionUpdateContract` may only run under `permissionId == 0` (Owner): [5](#0-4) 

The actuator's own `execute()` then blindly overwrites the Owner/Witness/Active permissions on the account with attacker-supplied values as soon as `validate()` passes: [6](#0-5) 

The result: a key holder who only has an `Active`-tier grant (typically weaker threshold, meant for day-to-day operations such as transfers/trading) can — if that active permission's operations happen to include the `AccountPermissionUpdateContract` bit — completely replace the `Owner` permission with keys they control, seizing full unilateral control of the account. This is functionally identical to the EOS incident's root cause: the "owner" authority was modified by an actor/permission that should not have had that capability, followed by asset theft.

### Impact Explanation
Gaining Owner permission control over an account allows the attacker to subsequently authorize any operation on that account (transfers, freezes, contract permission grants, etc.) at will, since Owner is the root permission. This constitutes concrete unauthorized account takeover and a direct path to theft of the account's TRX/TRC10/TRC20 holdings — matching the "unauthorized account operation, theft ... of funds" acceptance criteria.

### Likelihood Explanation
Exploitation requires that some Active permission on the target account already includes (or can be made to include) the `AccountPermissionUpdateContract` operation bit — this is not the default (`ACTIVE_DEFAULT_OPERATIONS` excludes it), so an account owner must have explicitly (or mistakenly, e.g. by reusing the broader `AVAILABLE_CONTRACT_TYPE` bitmap as their custom active operations) configured it this way, or a malicious co-signer with owner-level input during initial multisig setup could insert it. Given that `checkPermission()` places no code-level restriction against this and no warning is surfaced, this is a realistic misconfiguration/social-engineering vector for any multisig-managed account (e.g., an exchange hot wallet or DAO treasury), directly matching the EOSBank scenario where a contract account's permission configuration was subverted.

### Recommendation
In `AccountPermissionUpdateActuator.checkPermission()`, explicitly forbid the `AccountPermissionUpdateContract` bit (and ideally other permission-management contract types) from being set in the `operations` bitmap of any non-Owner (`Active`) permission, regardless of what `getAvailableContractType()` allows. Additionally, consider enforcing in `TransactionCapsule.validateSignature`/`checkPermission(int, Permission, Contract)` that `AccountPermissionUpdateContract` transactions may only be authorized via `permissionId == 0` (Owner), independent of the operations bitmap.

### Proof of Concept
1. Attacker (or unaware account owner) submits an `AccountPermissionUpdateContract` transaction, signed with the current valid Owner permission, that defines an `Active` permission whose `operations` bitmap sets the bit corresponding to `AccountPermissionUpdateContract` (id 46) — this passes `checkPermission()` validation since `getAvailableContractType()` includes bit 46.
2. This new Active permission is installed on the account via `account.updatePermissions(...)`. [7](#0-6) 
3. A holder of a key in that Active permission (meeting only the Active threshold, not the Owner threshold) later crafts and signs another `AccountPermissionUpdateContract` transaction with `Permission_id` set to that Active permission's id, replacing the account's Owner permission with keys they fully control.
4. `TransactionCapsule.validateSignature` looks up the permission by that `permissionId`, confirms sufficient active-key weight, and the transaction is accepted — even though it is rewriting Owner authority. [8](#0-7) 
5. The attacker now controls the account's Owner permission and can freely transfer out all funds.

**Note on verification limits**: I was unable to fully inspect the body of the private `checkPermission(int permissionId, Permission permission, Contract contract)` method referenced at `TransactionCapsule.java:490` due to reaching the tool-call limit; I confirmed only its call site and that `validateSignature` does not appear to special-case `AccountPermissionUpdateContract` to require `permissionId == 0`. If that helper method independently enforces this restriction, the exploitability of this analog would be reduced — I recommend a Devin session with full file access to confirm this method's exact logic before treating this as fully proven.

  public static boolean validateSignature(Transaction transaction,
      byte[] hash, AccountStore accountStore, DynamicPropertiesStore dynamicPropertiesStore)
      throws PermissionException, SignatureException, SignatureFormatException {
    Transaction.Contract contract = transaction.getRawData().getContractList().get(0);
    int permissionId = contract.getPermissionId();
    byte[] owner = getOwner(contract);
    AccountCapsule account = accountStore.get(owner);
    Permission permission = null;
    if (account == null) {
      if (permissionId == 0) {
        permission = AccountCapsule.getDefaultPermission(ByteString.copyFrom(owner));
      }
      if (permissionId == 2) {
        permission = AccountCapsule
            .createDefaultActivePermission(ByteString.copyFrom(owner), dynamicPropertiesStore);
      }
    } else {
      permission = account.getPermissionById(permissionId);
    }
    if (permission == null) {
      throw new PermissionException("permission isn't exit");
    }
    checkPermission(permissionId, permission, contract);
    long weight = checkWeight(permission, transaction.getSignatureList(), hash, null);
    if (weight >= permission.getThreshold()) {
      return true;
    }
    return false;
  }
