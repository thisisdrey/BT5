### Title
Unbounded DelegatedResourceAccountIndex growth causes DOS on `getDelegatedResourceAccountIndexV2` / `getdelegatedresourceaccountindexv2` query path - (File: chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java)

### Summary
The current (post-optimization) delegated-resource indexing scheme stores each delegation relationship as a separate key-value entry (`V2_FROM_PREFIX`/`V2_TO_PREFIX` + address) rather than a single bounded list, exactly the pattern the external report warns about (unbounded per-key growth that must later be fully iterated). Any unprivileged account can call `DelegateResourceActuator`/`FreezeBalanceActuator` repeatedly with distinct receiver addresses to make one owner address accumulate an arbitrarily large number of delegation relationships. Reading that owner's index back (`getV2Index`) requires a full prefix scan and in-memory sort over every relationship ever created, with no cap, no pagination, and no gas/CPU accounting since it is invoked from public query paths, not from a metered transaction.

### Finding Description
`DelegateResourceActuator.delegateResource()` (an actuator reachable from any signed `DelegateResourceContract` transaction) calls `delegatedResourceAccountIndexStore.delegateV2(ownerAddress, receiverAddress, timestamp)` for every delegation, regardless of how many distinct receivers the owner has already delegated to: [1](#0-0) 

`delegateV2` unconditionally writes a brand-new key `V2_FROM_PREFIX + from + to` and `V2_TO_PREFIX + to + from` on every call — there is no limit on the number of distinct receivers/senders per address: [2](#0-1) 

To read this data back, `getV2Index` / `getWithPrefix` performs a full key-prefix scan (`prefixQuery`) for both the "to" and "from" directions, collects everything into an `ArrayList`, and sorts it by timestamp in memory before returning: [3](#0-2) 

This is invoked directly, with no limit/pagination parameter, from `Wallet.getDelegatedResourceAccountIndexV2`: [4](#0-3) 

which is exposed unauthenticated via multiple public entry points reachable by any anonymous API client:
- HTTP: `/wallet/getdelegatedresourceaccountindexv2`, `/walletsolidity/getdelegatedresourceaccountindexv2`, and the PBFT/Solidity mirrors [5](#0-4) [6](#0-5) 
- gRPC: `getDelegatedResourceAccountIndexV2` on `WalletGrpc` [7](#0-6) 

The same growth applies symmetrically to the receiver side, since every delegation also registers a `V2_TO_PREFIX` entry under the receiver's address, meaning a single owner spraying delegations to many receivers can also bloat each receiver's index (a receiver has no control over inbound delegations targeting it).

The legacy (pre-`AllowDelegateOptimization`) `DelegatedResourceAccountIndexCapsule` path in `FreezeBalanceActuator`/`UnfreezeBalanceActuator` has essentially the same shape — an unbounded `toAccountsList`/`fromAccountsList` inside one protobuf record that later gets fully deserialized on every read via `getIndex()`/`get()`: [8](#0-7) 

### Impact Explanation
An attacker can drive up the CPU cost of every subsequent `getDelegatedResourceAccountIndex(V2)` query for a chosen address to arbitrarily large levels by submitting many cheap `DelegateResourceContract` transactions (fee for delegate/freeze contracts is `0` per `calcFee()`), each targeting a fresh receiver address: [9](#0-8) 
This makes it possible to degrade or hang the public query API (full/solidity/PBFT nodes) that serves `getdelegatedresourceaccountindex(v2)` for the targeted address — a resource-exhaustion condition on an API the node can no longer serve efficiently, matching the "unbounded loop over attacker-controlled index" bug class in the report. Because delegation records also register against the receiver, a victim address can be targeted for this degradation without the victim's cooperation.

### Likelihood Explanation
High reachability, low cost: `DelegateResourceContract` (and the legacy `FreezeBalanceContract` with `receiverAddress`) is a standard, permissionless transaction type any signed account can submit; `calcFee()` returns `0`, so bandwidth/energy is the only cost, and repeated small-balance delegations to freshly generated receiver addresses are cheap to produce at scale. No admin/SR/committee privilege is required.

### Recommendation
1. Cap the number of distinct delegation relationships (`to`/`from` accounts) tracked per address, or require de-duplication/limits enforced in the actuator (`DelegateResourceActuator`/`FreezeBalanceActuator`) before writing new `V2_FROM_PREFIX`/`V2_TO_PREFIX`/legacy list entries.
2. Change `getWithPrefix`/`getV2Index`/`getIndex` to support pagination (limit/offset) instead of unconditionally scanning and sorting the entire prefix range in `DelegatedResourceAccountIndexStore.java`.
3. Consider moving the sort/ordering requirement off the hot read path (e.g., store entries pre-sorted by using a monotonic key suffix) to avoid full in-memory sorts on every query.

### Proof of Concept
1. Fund an attacker account A.
2. Repeat N times (N large, e.g. tens of thousands): generate a fresh key pair R_i, broadcast a `DelegateResourceContract` from A to R_i (small `balance`, `resource=BANDWIDTH`), which invokes `DelegateResourceActuator.delegateResource` → `delegatedResourceAccountIndexStore.delegateV2(A, R_i, ts)`, creating two new KV rows each time — no existing-relationship check bounds this growth (`chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java:77-89`).
3. Call `GET /wallet/getdelegatedresourceaccountindexv2?value=<A>` (or the gRPC `getDelegatedResourceAccountIndexV2`) repeatedly.
4. Observe that each call triggers `getWithPrefix` to run `prefixQuery` over all N relationship rows and sort them in memory (`chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java:118-137`), with response latency/CPU cost scaling linearly with attacker-controlled N, degrading the node's ability to serve this and potentially other requests.

  public DelegatedResourceAccountIndexCapsule getV2Index(byte[] address) {
    return getWithPrefix(V2_FROM_PREFIX, V2_TO_PREFIX, address);
  }

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }
