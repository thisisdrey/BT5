This confirms the mechanics described in the question are real, but the exploit is only partially the "attacker action" that the question requires — it's a legitimate remote-only path.

`RPCPostTransactionRequestHandler::try_handle_request` calls `insert_uninstantiated_attachment` for any POSTed contract-call transaction that carries an attachment whose content hash matches an attachment already marked `was_instantiated = 1` in the `attachments` table [1](#0-0) , and `insert_uninstantiated_attachment` performs an unconditional `INSERT OR REPLACE ... was_instantiated = 0` keyed only on `hash` [2](#0-1) . Because SQLite's `PRIMARY KEY` on `hash` means the REPLACE clobbers the existing row regardless of its prior `was_instantiated` state, a previously instantiated (available) attachment is downgraded to uninstantiated with a single POST that reuses the same content bytes (hence same `Hash160`). Subsequently, `AtlasDB::find_attachment` only returns rows `WHERE ... was_instantiated = 1` [3](#0-2) , so `RPCGetAttachmentRequestHandler::try_handle_request` gets `Ok(None)`/error from `find_attachment` and returns `HttpNotFound` [4](#0-3) , even though the row (with identical content) still physically exists in the `attachments` table.

This matches the claimed fault exactly: the content bytes for `H` still exist on disk (`was_instantiated=0`), but `GET /v2/attachments/<H>` serves 404, an absence-vs-presence mismatch for a hash that is committed to by a live on-chain name/BNS operation. The precondition (`should_keep_attachment` gate: contract must be in `atlas_config.contracts`, i.e. registered BNS-type contracts, and size limit) is remotely satisfiable by any unprivileged peer using the RPC POST-transaction endpoint [5](#0-4) ; no secret, signature or privileged role is required — `/v2/transactions` is a normal unauthenticated write RPC that accepts any well-formed transaction plus optional attachment content. The only cost is constructing a valid contract-call transaction (any account with STX for fees, or even a transaction that gets accepted into the mempool) whose attachment content byte-for-byte matches the previously-served attachment's content, and submitting it. This is repeatable against any known/observed instantiated attachment hash, since attacker can always resubmit with identical attachment content to re-trigger the downgrade.

### Title
GET /v2/attachments/<hash> serves 404 for an existing instantiated attachment after a same-content re-POST downgrades `was_instantiated` - ([File: stackslib/src/net/atlas/db.rs])

### Summary
`AtlasDB::insert_uninstantiated_attachment` uses `INSERT OR REPLACE` keyed solely on `hash`, so any remote client that POSTs a contract-call transaction with an attachment whose content matches an already-instantiated attachment's hash will silently flip that attachment's `was_instantiated` flag from 1 to 0. `AtlasDB::find_attachment`, used by the `/v2/attachments/:hash` RPC handler, filters on `was_instantiated = 1`, so the previously-available attachment becomes unreachable via the RPC even though its bytes are still stored in the DB.

### Finding Description
The broken invariant is: bytes served by `GET /v2/attachments/<H>` should equal the bytes committed by the confirmed on-chain attachment instance for `H` whenever such an instance and matching content exist. In `stackslib/src/net/api/getattachment.rs:104-118`, the handler calls `AtlasDB::find_attachment`, which in `stackslib/src/net/atlas/db.rs:641-648` runs `SELECT content, hash FROM attachments WHERE hash = ?1 AND was_instantiated = 1`. An attacker who knows or reconstructs the content bytes of an already-instantiated attachment (content is public — anyone who previously fetched `H` via this same endpoint, or observed the original POST, has it) submits a `POST /v2/transactions` with `Content-Type: application/json` containing a valid contract-call transaction targeting one of the Atlas-tracked contracts, plus `attachment` set to that same content, per `RPCPostTransactionRequestHandler::try_handle_request` (`posttransaction.rs:230-251`). Provided `AtlasDB::should_keep_attachment` passes (contract in `atlas_config.contracts`, size under limit), `insert_uninstantiated_attachment` is invoked, which runs `INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 0, ?)` (`db.rs:526-532`), clobbering the row's `was_instantiated=1` state to 0 because `hash` is the table's `PRIMARY KEY`. From that point, `find_attachment` returns no row for `H`, and the RPC handler returns `HttpNotFound` for a hash whose content is still physically present and whose corresponding `AttachmentInstance` may still be `Checked`/`is_available=1` in `attachment_instances`. No signature check, secret, or privileged role guards this path; the mempool/`Relayer::static_check_problematic_relayed_tx` checks validate the transaction itself, not the attachment-hash collision, so they do not prevent the downgrade.

### Impact Explanation
This is a High-severity attachment/BNS state-serving mismatch: a remote, unprivileged client can make a legitimately-instantiated, on-chain-committed attachment (e.g., a BNS zonefile) unretrievable via the node's public RPC API, causing the node to serve "not found" for state that is live and canonical. This degrades BNS resolution correctness for any client relying on that node's `/v2/attachments/:hash` endpoint. It is repeatable against any target hash whose content the attacker can reproduce (which includes every previously-published attachment, since content is not secret), and the affected node's Atlas state remains in that condition until `evict_expired_uninstantiated_attachments` (long expiry-based) or `insert_instantiated_attachment` re-instantiates it via a fresh attachment-instance-check pass.

### Likelihood Explanation
No privileged role, secret, or non-remote capability is required — only the ability to send a normal `POST /v2/transactions` request with attachment (a supported, documented RPC feature) and knowledge of the target attachment's content bytes, which are inherently public once served once. Preconditions: the target hash's contract must be among `atlas_config.contracts` (this is generally the BNS/name contracts Atlas is designed to track, so real targets qualify), and the attacker needs a transaction that passes mempool admission (fee-payable account, valid nonce, non-"problematic" per static checks) — a modest but easily satisfiable cost. The bug is deterministic given the schema (`hash TEXT UNIQUE PRIMARY KEY`) and the `INSERT OR REPLACE` semantics, so it is fully reproducible without race conditions.

### Recommendation
In `AtlasDB::insert_uninstantiated_attachment`, do not blindly downgrade an already-instantiated row. Change the insert to only touch rows that are not already instantiated, e.g. use `INSERT INTO attachments (...) VALUES (..., 0, ...) ON CONFLICT(hash) DO UPDATE SET content = excluded.content, created_at = excluded.created_at WHERE attachments.was_instantiated = 0`, or explicitly check `was_instantiated` for the existing row before performing any REPLACE and skip the write entirely if it is already 1.

### Proof of Concept
Add a test in `stackslib::net::atlas::tests` (or `net::api::tests::getattachment`) that: (1) calls `AtlasDB::insert_instantiated_attachment` for some `Attachment` with known content/hash `H`, and asserts `find_attachment(&H)` returns `Ok(Some(_))`; (2) calls `insert_uninstantiated_attachment` with an `Attachment` carrying the identical content (same hash `H`), simulating the effect of `RPCPostTransactionRequestHandler` processing a duplicate-content contract-call POST; (3) asserts `find_attachment(&H)` now returns `Ok(None)` while `find_uninstantiated_attachment(&H)` returns `Ok(Some(_))` with the same content — demonstrating the row still exists but is unreachable via the instantiated-only query used by the `GET /v2/attachments/:hash` handler.
