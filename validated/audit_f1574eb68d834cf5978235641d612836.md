### Title
`SmartFarmingManager.leverage()` and `SmartFarmingManager.flashRepay()` offer no `deadline` parameter, so pending transactions can be executed at stale prices and sandwiched up to the user's outdated slippage bound - ([File: contracts/SmartFarmingManager.sol](contracts/SmartFarmingManager.sol))

### Summary
Both entry points that perform external-AMM swaps through `ISwapper.swapExactInput` — `leverage()` [1](#0-0)  and `flashRepay()` [2](#0-1)  — allow the user to set a minimum-output slippage parameter (`depositAmountMin_`, `swapAmountOutMin_`), but there is no deadline parameter anywhere. The `ISwapper` interface itself has no deadline field [3](#0-2) . This mirrors the deadline half of the Maia M-20 finding: a transaction signed with a once-reasonable `minOut` remains valid forever and can be executed at much worse prices later.

### Finding Description
In `leverage()`, the intermediate swap `tokenIn_ → collateral` (line 184) and the minted-synth swap `syntheticToken_ → collateral` (line 197) are both dispatched with `amountOutMin_ = 0`; protection relies entirely on the trailing check `if (_depositAmount < depositAmountMin_) revert LeverageSlippageTooHigh()` at line 198. In `flashRepay()`, the collateral→synth swap uses `amountOutMin_ = 0` (line 125) with the check at line 126. These are the correct "check once at the end" pattern — but the user's bound is fixed at signing time with no expiry. A `leverage`/`flashRepay` transaction that sits pending (low gas on mainnet deployment exists — see `deployments/mainnet/SmartFarmingManager.json`) executes whenever a validator includes it. If prices have moved, the stale `depositAmountMin_`/`swapAmountOutMin_` permits a far worse effective trade, and the atomic multi-swap structure (tokenIn→collateral→deposit, or collateral→synth→repay) is a textbook sandwich target.

The health check (`PositionIsNotHealthy`) does not help the victim: a sandwiched `leverage` still produces a healthy position — just with less collateral deposited. The `nonReentrant`, `whenNotShutdown`, and `onlyIf*TokenExists` modifiers do not constrain execution timing. There is no `checkDeadline`-style modifier anywhere in the contracts tree; `block.timestamp` does not appear in `SmartFarmingManager.sol` at all.

### Impact Explanation
The victim receives the minimum collateral/synth amount they were willing to tolerate at signing time, while market prices have moved against them. The extracted value (up to the gap between fair output and the stale bound) goes to the MEV bot. For `leverage`, this is amplified: the sandwichable leg includes the flash-minted synth amount (`_issued`), which is typically larger than the user's own `amountIn_`, so slippage on it is a direct loss on borrowed-notional size. For `flashRepay`, the withdrawn collateral is swapped at a stale bound, leaving the user with less debt repaid. Loss is bounded by the user's own slippage parameter, keeping this at medium severity — same as the source report.

### Likelihood Explanation
Requires a pending/stale transaction or same-block MEV opportunity. On Ethereum mainnet (where the contract is deployed), sandwich bots continuously monitor the mempool; `leverage`/`flashRepay` transactions are large, multi-leg, and routed through a single registered Swapper, making them easy to simulate and sandwich. On L2 deployments (Base, Optimism) with centralized sequencers, mempool-based sandwiching is reduced but the stale-transaction/bad-fill scenario (user's tx included later at moved prices) remains — there is simply no way for a user to bound the execution window.

### Recommendation
Add a `deadline_` parameter to `leverage()` and `flashRepay()`, enforce it with a `if (block.timestamp > deadline_) revert TransactionTooOld()` check (or modifier), and reject `deadline_ == 0` if that is meant to mean "no expiry". Optionally also expose per-leg `amountOutMin` so users can bound the intermediate `tokenIn_ → collateral` swap independently rather than relying on a single end-of-pipeline check.

### Proof of Concept
Foundry fork test sketch (mainnet fork, real Swapper + Uniswap/Curve routes):

```solidity
function test_leverage_stale_tx_sandwich() public {
    // Setup: alice has USDC collateral approved to SmartFarmingManager
    // 1. Alice "signs" her intent at price P0:
    uint256 aliceMin = manager.quoteDepositAmount(...) * 99 / 100; // 1% slippage bound
    bytes memory aliceTx = abi.encodeCall(
        SmartFarmingManager.leverage,
        (usdc, msdVaUSDC, msUSD, amountIn, 2e18, aliceMin)
    );

    // 2. Time passes while tx sits pending (simulate stale inclusion)
    vm.warp(block.timestamp + 12 hours);

    // 3. MEV bot: dump collateral/synth pools to push spot price down.
    //    No deadline check exists -> tx still executes.
    bot.sellCollateral(); // moves AMM price; oracle debt amount unchanged

    // 4. Alice's tx is included; intermediate swaps get ~0-protection,
    //    final deposit only bounded by stale aliceMin -> passes.
    // 5. Bot back-runs, restoring price and pocketing the spread.
    bot.buyCollateral();

    // Assert: alice deposited ~= aliceMin while fair value >> aliceMin;
    //         bot profit > 0; alice's position still passes PositionIsNotHealthy.
}
```

The identical pattern applies to `flashRepay` with `swapAmountOutMin_`. No privileged actor is needed — the attack is executable by any MEV bot watching the mempool.

    function leverage(
        IERC20 tokenIn_,
        IDepositToken depositToken_,
        ISyntheticToken syntheticToken_,
        uint256 amountIn_,
        uint256 leverage_,
        uint256 depositAmountMin_
    )
        external
        override
        whenNotShutdown
        nonReentrant
        onlyIfDepositTokenExists(depositToken_)
        onlyIfSyntheticTokenExists(syntheticToken_)
        returns (uint256 _deposited, uint256 _issued)
    {
        if (amountIn_ == 0) revert AmountIsZero();
        if (leverage_ <= 1e18) revert LeverageTooLow();
        if (leverage_ > uint256(1e18).wadDiv(1e18 - depositToken_.collateralFactor())) revert LeverageTooHigh();

        address _msgSender = _msgSender();
        ISwapper _swapper = swapper();

        // 1. transfer collateral
        IERC20 _collateral = _collateralOf(depositToken_);
        if (address(tokenIn_) == address(0)) tokenIn_ = _collateral;
        amountIn_ = _safeTransferFrom(tokenIn_, _msgSender, amountIn_);
        if (tokenIn_ != _collateral) {
            // Note: `amountOutMin_` is `0` because slippage will be checked later on
            amountIn_ = _swap(_swapper, tokenIn_, _collateral, amountIn_, 0);
        }

        {
            // 2. mint synth + debt
            uint256 _debtAmount = _calculateLeverageDebtAmount(_collateral, syntheticToken_, amountIn_, leverage_);
            IDebtToken _debtToken = pool.debtTokenOf(syntheticToken_);
            (_issued, ) = _debtToken.flashIssue(address(this), _debtAmount);
            _debtToken.mint(_msgSender, _debtAmount);
        }

        {
            // 3. swap synth for collateral
            uint256 _depositAmount = amountIn_ + _swap(_swapper, syntheticToken_, _collateral, _issued, 0);
            if (_depositAmount < depositAmountMin_) revert LeverageSlippageTooHigh();

            // 4. deposit collateral
            _collateral.safeApprove(address(depositToken_), 0);
            _collateral.safeApprove(address(depositToken_), _depositAmount);
            (_deposited, ) = depositToken_.deposit(_depositAmount, _msgSender);
        }

        // 5. check the health of the outcome position
        (bool _isHealthy, , , , ) = pool.debtPositionOf(_msgSender);
        if (!_isHealthy) revert PositionIsNotHealthy();

        emit Leveraged(tokenIn_, depositToken_, syntheticToken_, leverage_, amountIn_, _issued, _deposited);
    }
