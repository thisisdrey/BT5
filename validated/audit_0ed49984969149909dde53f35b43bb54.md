### Title
Global buffer over-read parsing malformed ZIP64 extra fields in ijar's central directory reader - ([File: third_party/ijar/zip.cc])

### Summary

### Finding Description
`InputZipFile::ProcessCentralDirEntry` in `third_party/ijar/zip.cc` walks the extra-field records of each central directory entry with no bounds validation: [1](#0-0) 
```
p += file_name_length;
const u1 *extra_p = p;
p += extra_field_length;
while (extra_p != p) {
  const u2 header_id = get_u2le(extra_p);
  const u2 data_size = get_u2le(extra_p);
  const u1 *extra = extra_p;
  extra_p += data_size;
  ...
}
```
`get_u2le`/`get_u4le`/`get_u8le` are raw, unchecked pointer-advancing readers [2](#0-1) , and the loop never verifies that `extra_p + 4 <= p` before reading the tag/size, nor that `extra_p + data_size <= p` before jumping `extra_p` forward. If an attacker-crafted `.jar`/`.zip` encodes a bogus `data_size` (e.g. larger than the remaining extra-field bytes), `extra_p` overshoots the intended end (`p`), and the loop condition `extra_p != p` never becomes false through normal termination — the code keeps calling `get_u2le`/`get_u8le` on memory beyond the mmap'd input file region, reading (and, for the ZIP64 fields, using) attacker-uncontrolled/out-of-bounds bytes as `uncompressed_size`/`compressed_size`/`offset` until it segfaults on an unmapped page. This is structurally the same bug class as the external report: a decoder trusts internal length fields inside attacker-supplied data without validating them against the enclosing buffer, causing an out-of-bounds read past the legitimate structure (CVE-2020-21596's `decode_CABAC_bit` case).

By contrast, Bazel's own `singlejar` tool already hardened the analogous ZIP64-extra-field parsing: `ExtraField::find` explicitly checks `start + sizeof(ExtraField) > end` and `start + extra_field->size() > end` before dereferencing, and aborts with "malformed extra field" rather than reading out of bounds [3](#0-2) , and there is a dedicated regression test constructing exactly this malformed-extra-field ZIP and asserting a controlled death rather than a crash/OOB read [4](#0-3) . `ijar/zip.cc` (used to build interface jars from `.jar` inputs, including third-party dependency jars) never received the same fix.

### Impact Explanation
`ProcessCentralDirEntry` operates directly on the mmap'd bytes of an input `.jar`/`.zip` supplied to the `ijar`/`zipper` tools [5](#0-4) . Such jars can originate from externally fetched/attacker-published artifacts (e.g., `java_import`, prebuilt jars pulled in via `http_jar`/`http_archive`) that are content-valid (matching whatever checksum was pinned) but structurally malformed. Processing them triggers reads past the end of the mapped input file, which can crash the build tool (denial of the build) or leak adjacent heap/mmap memory contents into computed size/offset fields used later in `CalculateOutputLength`/output generation — a global buffer over-read consistent with the reported bug class, not merely a resource-exhaustion issue.

### Likelihood Explanation
Moderate. It requires the victim's build to run the input jar through ijar (common in Java rules), and requires the attacker to control the byte content of some `.jar` the build consumes (a realistic scenario for third-party dependencies pulled from mutable/attacker-influenced sources, or where checksum pinning happens on first fetch of attacker-controlled content). No special privileges beyond publishing that artifact are needed; standard ZIP tooling would normally reject/ignore malformed extra fields, but this code does not.

### Recommendation
Add the same bounds-checked traversal used in `singlejar`'s `ExtraField::find` to `ijar`'s `ProcessCentralDirEntry` extra-field loop: before reading `header_id`/`data_size`, verify `extra_p + 4 <= p`; before advancing `extra_p += data_size`, verify the result does not exceed `p` (and thus the mapped input bounds), and treat any violation as a fatal, well-defined parse error (like `EnsureRemaining` does elsewhere in this file) rather than continuing to read.

### Proof of Concept
Adapt the existing singlejar test fixture `CreateZipWithMalformedExtraField()` [6](#0-5)  to build a `.zip`/`.jar` whose central directory entry extra field encodes an oversized `payload_size`/`data_size`, then feed it to the `ijar` tool (`ZipExtractor::Create` / `ProcessAll` in `third_party/ijar/zip.cc`) instead of singlejar's `OutputJar`. Under a memory-sanitized build (ASan), this should manifest as a heap/mmap out-of-bounds read inside `InputZipFile::ProcessCentralDirEntry`'s extra-field loop, whereas the equivalent singlejar path safely aborts with "malformed extra field".

*Note:* I was not able to locate a Java `ZipDecompressor` class in this checkout (the named class from the bug-class list) to compare against; the index may not contain it, or the repository fetch-time extraction path may rely on native/`ijar`-adjacent code instead. This finding is grounded in the C++ `ijar` ZIP reader that is present and directly inspectable in this repo.

inline u2 get_u2le(const u1 *&p) {
    u4 x = (p[1] << 8) | p[0];

inline u4 get_u4be(const u1 *&p) {
    u4 x = (p[0] << 24) | (p[1] << 16) | (p[2] << 8) | p[3];
    p += 4;
    return x;

inline u4 get_u4le(const u1 *&p) {

    p += 4;
    return x;

inline u8 get_u8le(const u1 *&p) {

std::string CreateZipWithMalformedExtraField() {
  std::string zip_data;
  const std::string filename = "evil.bin";

  // 1. Local File Header (LFH)
  size_t lh_offset = zip_data.size();
  size_t lh_size = sizeof(LH) + filename.size();
  zip_data.resize(lh_offset + lh_size, 0);
  auto* lh = reinterpret_cast<LH*>(&zip_data[lh_offset]);
  lh->signature();
  lh->version(10);
  lh->file_name(filename.data(), filename.size());

  // 2. Extra field payload containing an oversized payload_size
  uint8_t ef_buffer[8] = {0};
  auto* ef1 = reinterpret_cast<ExtraField*>(ef_buffer);
  ef1->signature(0x000d);
  ef1->payload_size(0);

  auto* ef2 = reinterpret_cast<ExtraField*>(ef_buffer + ef1->size());
  ef2->signature(0xdead);
  ef2->payload_size(0xf000);  // Malformed size exceeding extra field buffer

  // 3. Central Directory Header (CDH)
  size_t cdh_offset = zip_data.size();
  size_t cdh_size = sizeof(CDH) + filename.size() + sizeof(ef_buffer);
  zip_data.resize(cdh_offset + cdh_size, 0);
  auto* cdh = reinterpret_cast<CDH*>(&zip_data[cdh_offset]);
  cdh->signature();
  cdh->version(20);
  cdh->version_to_extract(10);
  cdh->local_header_offset32(lh_offset);
  cdh->file_name(filename.data(), filename.size());
  cdh->extra_fields(ef_buffer, sizeof(ef_buffer));

  // 4. End of Central Directory (EOCD)
  size_t ecd_offset = zip_data.size();
  zip_data.resize(ecd_offset + sizeof(ECD), 0);
  auto* ecd = reinterpret_cast<ECD*>(&zip_data[ecd_offset]);
  ecd->signature();
  ecd->this_disk_entries16(1);
  ecd->total_entries16(1);
  ecd->cen_size32(cdh_size);
  ecd->cen_offset32(cdh_offset);

  return zip_data;
}
