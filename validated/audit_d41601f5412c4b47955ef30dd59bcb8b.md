## Finding

### Title
Exchange pool balances can go negative without reverting when hardened arithmetic is disabled - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java])

### Summary
`ExchangeCapsule.transaction()` computes the counter-token amount using the Bancor-style relay formula and then updates the pool's two token balances by simple subtraction/addition. The check that rejects a resulting negative balance is only performed when the `allowHardenExchangeCalculation` chain parameter is enabled; by default this hardening is off, so the same underflow/invalid-state class of bug described in the external report (unchecked subtraction based on an externally influenced quantity/price calculation) is reachable via a normal `ExchangeTransactionContract`.

### Finding Description
`ExchangeCapsule.transaction()` derives `buyTokenQuant` from `ExchangeProcessor.exchange()`, a floating point (`double`) implementation of the Bancor bonding-curve formula [1](#0-0) . The result is then used to update the pool balances: [2](#0-1) 

The negative-balance guard (`newFirstTokenBalance < 0 || newSecondTokenBalance < 0`) is only enforced `if (hardenedCalc && ...)`. When `hardenedCalc` is `false` — the default, unless the `allowHardenExchangeCalculation` dynamic parameter has been enabled via committee proposal — the computed balances are stored as-is, even if negative [3](#0-2) .

The `hardenedCalc` flag itself is gated purely by this chain parameter in `AbstractExchangeActuator`, and the fallback (non-hardened) `subtractExact`/`addExact` helpers used throughout the exchange actuators are plain, unchecked `x - y` / `x + y` operations rather than something that throws on underflow: [4](#0-3) 

`ExchangeTransactionActuator.doValidate()` only checks that the computed `anotherTokenQuant` meets the caller's minimum expected amount; it never checks that `anotherTokenQuant` is bounded by the pool's actual reserve of that token before allowing the trade to proceed: [5](#0-4)  The same unguarded `transaction()` call is then invoked again in `execute()` and persisted to the store: [6](#0-5) 

This mirrors the report's bug class precisely: a price/quantity formula with attacker-influenced inputs (large `sellTokenQuant`, or an exchange pool set up with extreme first/second balances) is subtracted from a balance without first validating that the subtrahend cannot exceed the balance, and the "safe math" path exists but is opt-in/disabled by default.

### Impact Explanation
If the Bancor-style double-precision formula ever returns a `buyTokenQuant` (or, symmetrically, `anotherTokenQuant` in `ExchangeWithdrawActuator`/`ExchangeInjectActuator` codepaths sharing this pattern) larger than the pool's actual balance of that token — due to floating point rounding at extreme quantity ratios, pool balances near `TRX_PRECISION`/int64 edges, or deliberately engineered pool state — the resulting negative `ExchangeCapsule` balance is committed to the store without any revert. This corrupts the AMM pool's invariant, letting subsequent participants extract more value than the pool actually holds (unbacked balance), a form of fund creation/theft from the bancor exchange feature.

### Likelihood Explanation
Exploitation requires crafting an exchange pool (any account can create an `Exchange` via `ExchangeCreateContract`) and driving quantities/ratios into the region where floating-point Bancor math deviates from the exact ratio enough to exceed reserves, and doing so while `allowHardenExchangeCalculation` is not enabled (the default/legacy state that mainnet has run in historically). This requires no special privilege — any transaction broadcaster can create exchanges and submit `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` transactions.

### Recommendation
Make the negative-balance/overflow guard in `ExchangeCapsule.transaction()` unconditional rather than gated behind `hardenedCalc`, and add an explicit check in `ExchangeTransactionActuator.doValidate()`/`execute()` that the computed `anotherTokenQuant` never exceeds the existing pool balance for that token before persisting.

### Proof of Concept
Not independently reproduced with concrete numeric parameters (would require running `ExchangeProcessor.exchange()` with edge-case pool ratios to find a double-precision case where `buyTokenQuant > buyTokenBalance`); the structural gap — the negative-result guard existing only in the hardened path, while the actuator validation never bounds the computed amount by pool reserves — is directly evidenced in [7](#0-6)  and [5](#0-4) .

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
