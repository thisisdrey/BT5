### Title
Unchecked division by `totalEnergyWeight` in `RepositoryImpl.calculateGlobalEnergyLimit()` can revert TVM energy accounting via a Java assertion that is disabled in production - (File: actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java)

### Summary
`RepositoryImpl.calculateGlobalEnergyLimit()`, used by the TVM to compute an account's frozen-energy limit during contract execution, guards against a zero `totalEnergyWeight` denominator only with a Java `assert` statement rather than a real runtime check. [1](#0-0) 
This is the same bug class as TRST-M-1: a denominator (`veSupply[weekCursor]` in the external report, `totalEnergyWeight` here) is used in a division without a genuine zero check, so if the denominator is ever zero the call reverts.

### Finding Description
`calculateGlobalEnergyLimit(AccountCapsule)` reads `totalEnergyWeight` from `DynamicPropertiesStore` and immediately divides by it (either via `double` math or, when `hardenResourceCalculation()` is enabled, via `BigInteger.divide`): [2](#0-1) 
The only protection is `assert totalEnergyWeight > 0;` at line 1001. Java assertions are disabled by default at runtime unless the JVM is started with `-ea`; production java-tron nodes are not run with assertions enabled, so this line has zero effect on program behavior at runtime. If `totalEnergyWeight` is 0, the `BigInteger.divide` call throws `ArithmeticException` (and even the `double` path would produce `Infinity`/`NaN`, corrupting the returned energy limit).

Contrast this with the equivalent chain-level function `EnergyProcessor.calculateGlobalEnergyLimit()`, which explicitly returns 0 when `totalEnergyWeight <= 0` (guarded by `allowNewReward()`), and `calculateGlobalEnergyLimitV2()`, which has an unconditional `if (totalEnergyWeight == 0) return 0;` check: [3](#0-2) 
The `RepositoryImpl` copy used by the VM/native-contract layer lacks this real guard entirely, relying only on the no-op `assert`.

This method is reachable from the TVM execution path used for every smart contract call, e.g. `VMActuator.getAccountEnergyLimitWithFixRatio`/`getAccountEnergyLimitWithFloatRatio`, which call `rootRepository.calculateGlobalEnergyLimit(account)`: [4](#0-3) 
and from `RepositoryImpl.calculateGlobalEnergyLimit` invocations elsewhere in the TVM repository layer used by native contracts such as `DelegateResourceActuator`/`DelegateResourceProcessor`.

### Impact Explanation
`totalEnergyWeight` is a chain-wide accumulator that decreases whenever accounts unfreeze/undelegate energy-frozen TRX. While it is expected to stay positive under normal mainnet conditions, if the network ever reaches a state where all energy-frozen balances are withdrawn (plausible on low-activity private/permissioned networks, immediately post-genesis before any FreezeBalance transaction, or via coordinated mass-unfreezing during a fork/migration edge case), this denominator becomes 0. Any subsequent smart-contract call (any account broadcasting a TriggerSmartContract/CreateSmartContract transaction) that reaches `calculateGlobalEnergyLimit` in the hardened path would throw an uncaught `ArithmeticException`, causing the TVM call to fail/revert unexpectedly and freezing normal contract-execution flow for all users relying on frozen energy, similar to how the veSatin `_calculateClaim()` bug froze claims for an entire cohort of stakers.

### Likelihood Explanation
The likelihood is lower than the original veSatin report because `totalEnergyWeight == 0` requires an unusual global chain state (no account holding energy-frozen TRX), which is uncommon on a live, active mainnet but realistic on smaller/private chains, freshly bootstrapped test networks, or in the small window right after genesis before freeze transactions accumulate weight. The unprotected `assert`-only guard means the code offers no actual runtime defense once this state occurs, making the class of bug latent and silently unguarded rather than a deliberately-accepted risk.

### Recommendation
Replace the `assert totalEnergyWeight > 0;` at `RepositoryImpl.calculateGlobalEnergyLimit()` (line 1001) with an explicit runtime check, mirroring `EnergyProcessor.calculateGlobalEnergyLimitV2()`'s pattern: e.g. `if (totalEnergyWeight <= 0) { return 0; }` before performing either the `BigInteger` division or the double-precision division, ensuring the function returns a safe value instead of throwing when the network-wide energy weight denominator is zero.

### Proof of Concept
1. Reach (or simulate, e.g., on a private/test java-tron network) a chain state where `DynamicPropertiesStore.getTotalEnergyWeight()` returns 0 — e.g., a freshly initialized chain before any `FreezeBalanceV2Contract`/`FreezeBalanceContract` for ENERGY has been broadcast, or after every energy-frozen account fully unfreezes.
2. Broadcast any `TriggerSmartContractContract` or `CreateSmartContractContract` transaction from an unprivileged account.
3. During TVM setup, `VMActuator.getAccountEnergyLimitWithFloatRatio`/`getAccountEnergyLimitWithFixRatio` invokes `rootRepository.calculateGlobalEnergyLimit(account)` [5](#0-4) , which calls into `RepositoryImpl.calculateGlobalEnergyLimit`.
4. With `hardenResourceCalculation()` enabled and `totalEnergyWeight == 0`, `BigInteger.valueOf(totalEnergyLimit).divide(BigInteger.valueOf(0))` throws `ArithmeticException: / by zero` [6](#0-5) , since `assert totalEnergyWeight > 0;` (line 1001) is a no-op in a production JVM run without `-ea`.
5. This causes the contract-call transaction to fail unexpectedly, effectively freezing normal TVM/contract-call processing dependent on energy-limit accounting until `totalEnergyWeight` becomes non-zero again.

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalEnergyLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }

    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
    long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
      return 0;
    } else {
      assert totalEnergyWeight > 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
