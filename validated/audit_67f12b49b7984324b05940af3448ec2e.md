### Title
Missing G2 Subgroup Check in Fallback BN256 Implementation Causes Cross-Architecture Consensus Divergence in `bn256Pairing` Precompile - (File: `crypto/bn256/google/bn256.go`)

### Summary
Geth's BN256 pairing precompile (address `0x08`, `bn256PairingIstanbul`/`bn256PairingByzantium`) is backed by two different implementations selected by build tag: `gnark` for `amd64`/`arm64`, and `google` for all other architectures. The `gnark` G2 unmarshaller enforces both an on-curve check and a subgroup membership check, but the `google` (and unused `cloudflare`) G2 unmarshaller only checks that the point satisfies the curve equation — it never verifies the point lies in the correct prime-order subgroup. This is the classic "invalid curve / small-subgroup" defect pattern from the external report, applied to the twist group G2 of the BN254 pairing used on-chain.

### Finding Description
`runBn256Pairing` (`core/vm/contracts.go:898-927`) decodes each G2 element via `newTwistPoint`, which calls `bn256.G2.Unmarshal`: [1](#0-0) 

On `amd64`/`arm64`, `bn256.G2` is aliased to the gnark implementation (`crypto/bn256/bn256_fast.go`), whose `Unmarshal` explicitly performs both checks: [2](#0-1) 

On every other architecture (`crypto/bn256/bn256_slow.go`), `bn256.G2` is aliased to the `google` package implementation instead: [3](#0-2) 

That implementation's `G2.Unmarshal` only checks each coordinate is `< P` and that the resulting point satisfies `IsOnCurve()` — it has no equivalent to `IsInSubGroup()`: [4](#0-3) 

Because BN254's G2 twist has a large cofactor, the full curve `E'(F_p²)` contains many points that satisfy the curve equation but do **not** lie in the prime-order subgroup used for pairing security proofs. An attacker can craft such an "invalid-subgroup" point and submit it as one of the 192-byte (G1,G2) tuples to the `bn256Pairing` precompile via any ordinary contract call. On `amd64`/`arm64` nodes, `gnark`'s subgroup check rejects the point (`Unmarshal` returns an error), causing the precompile call to fail/revert. On other architectures, the `google` path accepts the same bytes as a valid point and proceeds to compute `PairingCheck`, which can legally return either `true` or `false` — but critically, the *execution outcome* (success vs. revert) of the calling transaction differs from the `amd64`/`arm64` outcome, and since pairing over a point outside the intended subgroup does not respect the bilinearity relation the precompile is specified (EIP-197) to check, the returned pairing result itself can be attacker-influenced to say "pairing check passed" for inputs that are not a valid pairing relation over the honest subgroup.

### Impact Explanation
This breaks the equality that identical transactions/blocks must produce identical state transitions across all Geth nodes. A single crafted transaction invoking precompile `0x08` with an out-of-subgroup G2 point causes:
- Geth nodes built for `amd64`/`arm64` to reject/revert the precompile call, while Geth nodes built for other architectures (386, arm, mips, riscv, ppc64, s390x, wasm, etc.) accept it and continue execution with a possibly forged "pairing check succeeded" result.
- This is a stateRoot divergence between Geth instances of the *same client* running on different CPU architectures for the identical block — meeting the "Critical" bar of "commits a different stateRoot" for a single valid transaction.
- Downstream, any on-chain verifier contract (e.g., zk-SNARK/zk-Rollup verifiers) relying on the BN256 pairing precompile for cryptographic soundness could have proof verification bypassed on non-`amd64/arm64` nodes, letting an attacker construct forged proofs that different Geth builds disagree on, or that pass verification when they should not.

### Likelihood Explanation
Directly reachable by any unprivileged account submitting a normal transaction that calls the `0x08` precompile (either directly or through any contract using pairing-based verification), with no special privileges required. The divergence is deterministic and depends only on the CPU architecture the Geth binary was built for — an attacker only needs to know that some portion of the network runs Geth on non-`amd64`/`arm64` hardware (e.g., ARM32 embedded nodes, RISC-V, s390x, or WASM light clients) to trigger a stateRoot split against those nodes specifically.

### Recommendation
Add a subgroup membership check (`IsInSubGroup`-equivalent) to `crypto/bn256/google/bn256.go`'s `G2.Unmarshal` (and remove/avoid using the equally-affected `crypto/bn256/cloudflare` package if still reachable anywhere), so that all BN256 backends enforce identical acceptance criteria for G2 points, matching the `gnark` implementation used on `amd64`/`arm64`.

### Proof of Concept
1. Build Geth for a non-`amd64`/`arm64` target (e.g., `GOARCH=386` or `GOARCH=riscv64`), which links `crypto/bn256/google`.
2. Craft a 128-byte G2 encoding `(x1,x0,y1,y0)` such that the point satisfies `y² = x³ + b` (twist curve equation) but does not belong to the order-`r` subgroup used by BN254 (constructible by taking a random point on the full curve `E'(F_p²)` and confirming its order does not divide `r`, which is straightforward given the large cofactor).
3. Submit a transaction calling precompile address `0x08` with this G2 point paired against any G1 point, formatted as a standard 192-byte `bn256Pairing` input.
4. Observe: on an `amd64`/`arm64` Geth node the call reverts with `bn256: malformed point`/subgroup error (rejected at `Unmarshal`); on the `386`/`riscv64` Geth node built as in step 1, the call succeeds and returns a pairing result, producing divergent execution outcomes (and thus a different stateRoot) for the identical transaction between the two builds.

// newTwistPoint unmarshals a binary blob into a bn256 elliptic curve point,
// returning it, or an error if the point is invalid.
func newTwistPoint(blob []byte) (*bn256.G2, error) {
	p := new(bn256.G2)
	if _, err := p.Unmarshal(blob); err != nil {
		return nil, err
	}
	return p, nil
}

func (e *G2) Unmarshal(m []byte) ([]byte, error) {
	// Each value is a 256-bit number.
	const numBytes = 256 / 8
	if len(m) < 4*numBytes {
		return nil, errors.New("bn256: not enough data")
	}
	// Unmarshal the points and check their caps
	if e.p == nil {
		e.p = newTwistPoint(nil)
	}
	e.p.x.x.SetBytes(m[0*numBytes : 1*numBytes])
	if e.p.x.x.Cmp(P) >= 0 {
		return nil, errors.New("bn256: coordinate exceeds modulus")
	}
	e.p.x.y.SetBytes(m[1*numBytes : 2*numBytes])
	if e.p.x.y.Cmp(P) >= 0 {
		return nil, errors.New("bn256: coordinate exceeds modulus")
	}
	e.p.y.x.SetBytes(m[2*numBytes : 3*numBytes])
	if e.p.y.x.Cmp(P) >= 0 {
		return nil, errors.New("bn256: coordinate exceeds modulus")
	}
	e.p.y.y.SetBytes(m[3*numBytes : 4*numBytes])
	if e.p.y.y.Cmp(P) >= 0 {
		return nil, errors.New("bn256: coordinate exceeds modulus")
	}
	// Ensure the point is on the curve
	if e.p.x.x.Sign() == 0 &&
		e.p.x.y.Sign() == 0 &&
		e.p.y.x.Sign() == 0 &&
		e.p.y.y.Sign() == 0 {
		// This is the point at infinity.
		e.p.y.SetOne()
		e.p.z.SetZero()
		e.p.t.SetZero()
	} else {
		e.p.z.SetOne()
		e.p.t.SetOne()

		if !e.p.IsOnCurve() {
			return nil, errors.New("bn256: malformed point")
		}
	}
	return m[4*numBytes:], nil
}
