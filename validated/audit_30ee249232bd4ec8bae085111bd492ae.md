Audit Report

## Title
`RewardPool::update_records` can return `OverflowRisk` and block `unbond`, breaking pool-member withdrawal liveness - (File: `substrate/frame/nomination-pools/src/lib.rs`)

## Summary
`pallet-nomination-pools`'s `RewardPool::current_reward_counter` uses checked fixed-point arithmetic (`checked_from_rational`/`checked_add`) and returns `Error::<T>::OverflowRisk` on overflow instead of saturating. [1](#0-0) 
This function is invoked through `RewardPool::update_records`, whose own doc comment states it "MUST be called whenever the points in the bonded pool change... The reason for the former is that a change in pool points will alter the share of the reward balance among pool members" — and lists `unbond` (alongside `join`/`bond_extra`) as a mandatory call site. [2](#0-1) 
Because the overflow is propagated with `?` rather than degrading gracefully, a pool state that triggers `OverflowRisk` (already demonstrated for `join`) will equally abort `unbond`, locking members' principal behind a reward-accounting error unrelated to their withdrawal.

## Finding Description
The reward-counter computation performs checked fixed-point division and addition, converting any overflow into a hard error: [3](#0-2) 
This is called from `update_records`, whose documented contract explicitly requires it to run on `unbond` in order to correctly attribute rewards before pool points change: [4](#0-3) 
A regression test proves this failure mode is reachable in practice for the sibling call site `join`: creating a pool holding roughly half of projected 10-year DOT issuance, slashing it 99%, and having a large joiner trigger the update causes `Error::<T>::OverflowRisk` to abort the call: [5](#0-4) 
Since `update_records`/`current_reward_counter` is the same shared code path documented to run on `unbond`, an equivalent distorted pool state (extreme historical slashing relative to bonded points) would cause `unbond` to fail identically — reverting the entire call, including the state transition that would reduce a member's active points/balance, rather than merely degrading reward tracking. Existing checks (the `?`/`ok_or(Error::<T>::OverflowRisk)` propagation) do not distinguish between reward-accounting overflow and principal-affecting operations, so there is no fallback that lets unbonding proceed while reward accrual is flagged as stale/degraded.

## Impact Explanation
This matches the "permanent user-fund lock via public dispatch" pivot: an unprivileged pool member calling the public `unbond` extrinsic can find the call unconditionally reverted by an overflow in a reward-accounting subroutine that has nothing to do with their principal. Members of an affected pool would be unable to exit (unbond principal) until the pool's reward-counter overflow condition is resolved, which — absent a code fix — requires privileged/governance intervention, constituting a liveness violation over locked funds.

## Likelihood Explanation
The precondition (reward-counter growth relative to bonded points due to heavy slashing combined with large new joins) is proven reachable via ordinary, unprivileged pool operations (`join`, slashing events processed through normal staking mechanics) and is already reproduced by an in-repo unit test for the `join` path. Because `unbond` shares the identical `update_records`/`current_reward_counter` code, the same class of distorted pool state — reachable without any privileged actor, only heavy slashing plus large public `join`s — would abort `unbond` as well.

## Recommendation
Do not let reward-accounting overflow abort principal-affecting operations such as `unbond`/`withdraw_unbonded`. Options: (1) saturate the reward-counter update instead of erroring on overflow, consistent with other balance updates in this pallet that already use `saturating_add`/`saturating_sub`; (2) decouple the points/balance state transition of `unbond` from the reward-counter refresh so a reward-overflow failure degrades only reward tracking, not withdrawal of principal; (3) add a regression test asserting `unbond` succeeds even when `current_reward_counter` would overflow, mirroring the existing `reward_counter_update_can_fail_if_pool_is_highly_slashed` test but for `unbond`.

## Proof of Concept
1. Create a pool with `pool_bond = inflation(10) / 2`, matching the existing test `reward_counter_update_can_fail_if_pool_is_highly_slashed`. [6](#0-5) 
2. Slash the pool by 99% (`StakingMock::slash_by(1, pool_bond * 99 / 100)`), distorting `last_recorded_reward_counter`/`bonded_points` ratios. [7](#0-6) 
3. Instead of (or in addition to) `Pools::join`, have an already-bonded member call `Pools::unbond(RuntimeOrigin::signed(member), member, some_points)`. Since `unbond` also routes through `update_records` → `current_reward_counter` on the same distorted state, the call is expected to fail with `Error::<T>::OverflowRisk`, leaving the member's funds bonded and unable to be unbonded until the overflow condition is externally resolved.
