### Title
Unbounded `Paths`/`Attributes` cardinality in `GetFileAttributes` causes CPU/memory amplification via `git check-attr --stdin -z` - ([File: internal/gitaly/service/repository/file_attributes.go])

### Summary
`validateGetFileAttributesRequest` only checks that `Paths` and `Attributes` are non-empty, with no cap on their length, and `CheckAttrCmd.Check` synchronously reads exactly `len(names)*3` NUL-delimited tokens per path from the `git check-attr --stdin -z` subprocess with no total output ceiling. An attacker who controls a repository (and its `.gitattributes`) and can invoke `GetFileAttributes` with large `Paths`/`Attributes` arrays can drive output and processing time proportional to `len(Paths) * len(Attributes)` in a single RPC handler invocation.

### Finding Description
`validateGetFileAttributesRequest` (internal/gitaly/service/repository/file_attributes.go:44-61) only validates repository, revision presence, and non-emptiness of `Paths`/`Attributes` - it never bounds their sizes. [1](#0-0) 

`GetFileAttributes` then spawns a single `git check-attr --stdin -z` process for the whole request, passing all requested attribute names as command arguments, and for every path in `Paths` calls `checkAttrCmd.Check(path)` sequentially. [2](#0-1) 

`CheckAttrCmd.Check` writes the path to the subprocess stdin and then loops `ReadBytes('\000')` exactly `c.count` (i.e., `len(names)`) times to consume the `<path> NUL <attribute> NUL <info> NUL` triples emitted by git for that path, with no upper bound on total bytes read across the whole RPC. [3](#0-2) 

Because `git check-attr` emits one triple per `(path, attribute)` pair, the subprocess output size and the handler's synchronous processing time scale with `len(Paths) * len(Attributes)`, both of which are entirely attacker-supplied request fields with no server-side cap in Gitaly's own validation code.

### Impact Explanation
This is a CPU/memory resource-amplification pattern within a single RPC handler: an attacker-controlled multiplicative factor (`Paths × Attributes`) drives subprocess output size and per-request processing work, with no cap enforced in `validateGetFileAttributesRequest`. This matches the DoS-of-RPC-handler impact class (resource exhaustion of the Gitaly process for the request's connection/goroutine), though it is bounded in practice by gRPC's default max message size (4MB), which limits how many `Paths`/`Attributes` strings can be crammed into one request unless the server is configured with a larger `MaxRecvMsgSize` — no override was found in `internal/gitaly/server/server.go`, so the default gRPC 4MB inbound message cap applies and constrains, but does not eliminate, the amplification (many short strings can still yield tens of thousands of paths/attributes within 4MB).

### Likelihood Explanation
The attacker needs only to control a repository's `.gitattributes` content (achievable via normal push) and be able to invoke `GetFileAttributesRequest` with large `Paths`/`Attributes` arrays. Feasibility of triggering the RPC directly with attacker-chosen, large `Paths`/`Attributes` values depends on whether GitLab Rails/Workhorse exposes this RPC's fields directly to end users or constructs them from a bounded, legitimate use case (e.g., diff rendering for a fixed file list); this trust boundary is outside Gitaly's code and could not be verified from this repository. Within Gitaly's own code path, no size cap exists, so the amplification is real if the RPC fields are attacker-influenced.

### Recommendation
Add explicit upper bounds on `len(in.GetPaths())` and `len(in.GetAttributes())` in `validateGetFileAttributesRequest` (e.g., reject requests exceeding a small fixed limit, or process in bounded chunks), and consider adding a total output byte/time ceiling in `CheckAttrCmd.Check`'s read loop to fail fast on abnormal subprocess output.

func TestGetFileAttributes_LargeCardinality(t *testing.T) {
    // Setup repo with .gitattributes mapping N distinct path patterns to M attribute names.
    paths := make([]string, 10000)
    attrs := make([]string, 100)
    for i := range paths { paths[i] = fmt.Sprintf("file%d.txt", i) }
    for i := range attrs { attrs[i] = fmt.Sprintf("attr%d", i) }

    req := &gitalypb.GetFileAttributesRequest{
        Repository: repoProto,
        Revision:   []byte("HEAD"),
        Paths:      paths,
        Attributes: attrs,
    }
    start := time.Now()
    _, err := client.GetFileAttributes(ctx, req)
    require.NoError(t, err)
    t.Logf("elapsed: %s", time.Since(start)) // scales with len(paths)*len(attrs)
}

// Check the attributes for the file at the given path.
func (c CheckAttrCmd) Check(path string) (Attributes, error) {
	if strings.Contains(path, "\000") {
		return nil, fmt.Errorf("path with NUL byte not allowed")
	}

	c.m.Lock()
	defer c.m.Unlock()

	if _, err := c.stdin.WriteString(path + "\000"); err != nil {
		return nil, fmt.Errorf("write path: %w", err)
	}
	if err := c.stdin.Flush(); err != nil {
		return nil, fmt.Errorf("flush: %w", err)
	}

	attrs := Attributes{}
	buf := make([]string, 0, 3)

	// Using git-check-attr(1) with -z will return data in the format:
	// <path> NUL <attribute> NUL <info> NUL ...
	for i := 0; i < c.count; {
		word, err := c.stdout.ReadBytes('\000')
		if err != nil {
			return nil, fmt.Errorf("read line: %w", err)
		}

		buf = append(buf, string(bytes.TrimSuffix(word, []byte{0})))

		if len(buf) < 3 {
			continue // Keep going until we have 3 words
		}

		if buf[0] != path {
			return nil, fmt.Errorf("wrong path name detected, expected %q, got %q", path, buf[0])
		}
		if buf[2] != Unspecified {
			attrs = append(attrs, Attribute{Name: buf[1], State: buf[2]})
		}

		i++
		buf = buf[:0]
	}
