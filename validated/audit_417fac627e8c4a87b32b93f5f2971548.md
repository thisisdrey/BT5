### Title
Unbounded array allocation from attacker-controlled length words in TVM precompiled contract helpers causes OutOfMemoryError / node crash - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`PrecompiledContracts.extractBytes32Array` and `extractBytesArray` allocate Java arrays whose size is taken directly from a 256-bit `DataWord` supplied in the call data of a TVM contract call, with no upper-bound validation before the allocation. This is the same bug class as CVE-2020-35522 (LibTIFF `tif_pixarlog.c`): an attacker-controlled length field from an untrusted input is passed straight into a memory allocation, and a crafted oversized value triggers an allocation failure/abort instead of a graceful, bounded error.

### Finding Description
In `extractBytesArray32` and `extractBytesArray`, the element count is read directly from call-data words with only `intValueSafe()` conversion (which clamps to `Integer.MAX_VALUE`/`Integer.MIN_VALUE` but does not reject large values), and is used immediately to allocate a 2-D byte array: [1](#0-0) [2](#0-1) 

Unlike `Memory.java`, which bounds and checks memory extension size before allocating chunks, these precompile helper methods perform `new byte[len][]` (or `new byte[len][32]`) with `len` fully attacker-controlled and unbounded by energy accounting. Any TVM opcode energy cost model in this codebase (`EnergyCost.java`) charges a cost proportional to memory *words* touched via `Memory`/`checkMemorySize`, but the precompiled-contract input parsing paths here do not go through that same bounded memory-extension logic — the array is allocated straight from the raw word value.

Because `java.lang.OutOfMemoryError` is an `Error`, not a `RuntimeException`, it is not caught by the VM's opcode-execution exception handling, which only catches `RuntimeException` (and a couple of named subclasses): [3](#0-2) 

An `OutOfMemoryError` thrown while executing a precompiled contract during block application therefore propagates as an uncaught `Error` out of transaction execution, rather than being converted into a normal `ContractExeException`/VM revert.

### Impact Explanation
An unprivileged party can call one of the affected precompiled contracts (any TVM `CALL`/`STATICCALL` addressing the precompile that uses `extractBytesArray`/`extractBytes32Array`) with a crafted large length word. This forces the JVM to attempt a huge heap allocation. Depending on heap headroom this either throws `OutOfMemoryError` (uncaught by `VM.play`, propagating up through block/transaction application) or induces heavy GC pressure across the node process, degrading or halting block processing for all validators that execute the transaction — a remote denial-of-service against the node, directly analogous to the LibTIFF "malloc failure ... abort, resulting in remote denial of service".

### Likelihood Explanation
Reachable via a single, unprivileged, signed transaction that calls a smart contract invoking the affected precompiled address with attacker-chosen call data — no special privileges, timing, or state are required. The trigger is a single crafted 32-byte length word.

### Recommendation
Bound `len` in `extractBytes32Array` and `extractBytesArray` (and any other precompile helper that derives an array size from raw call-data words) to a small, energy-justified maximum before allocation, and validate it against remaining energy/available call-data length, mirroring the `checkMemorySize`/overflow-checked pattern already used in `Memory.java`. Additionally, ensure array-size validation happens before allocation rather than relying on catching `OutOfMemoryError`, since `Error` types are intentionally not caught by `VM.play`'s exception handling.

### Proof of Concept
1. Deploy or reuse any contract that performs a `CALL`/`STATICCALL` to the precompiled address whose implementation invokes `extractBytesArray`/`extractBytes32Array` (e.g., the batch/array-based precompile entry points in `PrecompiledContracts.java`).
2. Craft the call data so that the length word at the expected `offset` (`words[offset]`) encodes a very large positive integer (e.g., close to `Integer.MAX_VALUE`).
3. Broadcast the transaction; when the precompile executes, `new byte[len][]` (or `new byte[len][32]`) triggers a massive allocation attempt.
4. Observe `OutOfMemoryError` thrown during opcode execution, propagating uncaught out of `VM.play` (per [3](#0-2) ), disrupting transaction/block processing on the node that executes it.
