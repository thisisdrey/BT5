### Title
Unbounded accumulation of witness reward index (`Vi`) combined with unguarded `BigInteger.longValue()` truncation can silently corrupt or permanently drop voter staking rewards - (File: `chainbase/src/main/java/org/tron/core/store/DelegationStore.java`)

### Summary
The XDeFi report describes a "points-per-unit" accumulator (`_pointsPerUnit`) that is scaled by a large fixed multiplier and divided by a caller-influenceable, potentially tiny denominator, so an early/low-stake actor can inflate the accumulator to a point where later arithmetic overflows and reverts, freezing funds. java-tron's DPoS vote-reward accounting (`Vi`, "value index") uses the structurally identical pattern: an ever-growing `BigInteger` accumulator scaled by a fixed `10^18` multiplier and divided by a witness's vote count, later multiplied back by a user's vote count and truncated to a Java `long`. Because `BigInteger` never overflows/reverts the way Solidity's checked math does, the failure mode here is worse than a revert: it is a **silent** `long` wraparound that corrupts a voter's computed reward, and the surrounding code treats non-positive results as "nothing to pay," so the reward is silently and permanently lost.

### Finding Description
The reward-index accumulation is: [1](#0-0) 

`DECIMAL_OF_VI_REWARD` is a fixed `10^18` multiplier: [2](#0-1) 

Each maintenance cycle, for every witness, `preVi` (a `BigInteger` that is **never reset and only ever grows**) is incremented by `reward * 10^18 / voteCount`: [3](#0-2) 

When a voter later withdraws or queries their reward, the accumulated `Vi` delta is multiplied by the voter's own vote count and then divided back down and truncated to a `long` via `.longValue()`: [4](#0-3) 

The same pattern is duplicated in the TVM-facing vote reward path used by contract-driven voting: [5](#0-4) 

`BigInteger.longValue()` does **not** throw on overflow — it silently returns only the low 64 bits of the value, producing an arbitrary (and potentially negative) result once `deltaVi * userVote / DECIMAL_OF_VI_REWARD` exceeds `Long.MAX_VALUE`. Because `Vi` is a monotonically non-decreasing accumulator with no reset and no cap, and is scaled by `10^18`, sufficiently long-running accumulation (or, as in the original report's PoC pattern, a witness with a disproportionately small `voteCount` relative to the reward it is credited in a cycle) will eventually push `deltaVi` for that witness to a magnitude where multiplying by any large voter's `userVote` and truncating produces an incorrect result.

Once that happens, `adjustAllowance` treats non-positive/garbage results as "nothing to pay" and skips crediting: [6](#0-5) 

Crucially, `withdrawReward` advances `beginCycle`/`endCycle` bookkeeping unconditionally regardless of whether the computed reward was valid: [7](#0-6) 

This means once a reward computation for a given cycle range silently truncates to a wrong/negative value, that reward is **permanently unclaimable** — the cycle window is marked as processed and can never be recomputed correctly.

### Impact Explanation
This is the same class of bug as the reported vulnerability: a fixed large scaling constant (`10^18` / `_pointsMultiplier`) combined with division by an attacker- or circumstance-influenced small denominator (`voteCount` / `totalUnits`) creates an accumulator that grows without bound, and downstream arithmetic that assumes the accumulator stays within a safe numeric range. In java-tron the consequence is not a revert (as Solidity's checked math would produce) but a **silent corruption of the voter's staking reward** that is then permanently discarded by the "amount <= 0 skip" logic in `adjustAllowance`, i.e., a form of stake/vote-reward freezing/loss of funds reachable simply by any account calling `WithdrawBalanceContract`/`VoteWitnessContract`/`TVM vote reward` withdrawal paths once the underlying `Vi` accumulator for a witness they voted for has grown large enough.

### Likelihood Explanation
Likelihood is moderate rather than trivially exploitable in a single transaction like the original report: an attacker cannot directly set `_pointsPerUnit`-equivalent state in one call the way the XDeFi `updateDistribution()` allowed. Here, the accumulator only grows through the normal `doMaintenance()` cycle-by-cycle process, driven by `WitnessCapsule.getVoteCount()` and cycle reward totals, and is not resettable. However, because `Vi` is a monotonically increasing `BigInteger` with no upper bound enforcement anywhere in `DelegationStore`, `RewardViCalService`, or `MortgageService`, and the final consumption path always truncates to `long`, this is an inherent, long-term correctness/DoS-of-rewards risk that requires no privileged access to trigger — any voter's withdrawal call is the trigger once the precondition (sufficiently large accumulated `Vi` relative to a witness's historical vote count) is met, which can also be engineered faster by directing large `payTransactionFeeReward`/`payBlockReward` amounts at a witness with an artificially small `voteCount` in the accumulation cycle.

### Recommendation
- Bound `Vi`/reward computations to detect and reject (rather than silently truncate) values that exceed `Long.MAX_VALUE`, e.g. use `BigInteger` compare against `Long.MAX_VALUE` before calling `.longValue()`, and fail loudly (or clamp) instead of proceeding with a corrupted reward.
- Consider periodically checkpointing/normalizing the `Vi` accumulator (or scaling down `DECIMAL_OF_VI_REWARD` growth) so that it cannot grow unbounded over the chain's lifetime, analogous to how the original report recommends seeding `totalUnits` to prevent a degenerate small-denominator state.
- Add explicit unit tests that simulate multi-year cycle counts / minimal `voteCount` witnesses receiving disproportionate rewards to confirm `Vi`-based reward computation remains correct at the boundaries of `long`.

### Proof of Concept
Conceptual repro path (cannot be fully executed without a running node/test harness in this session):
1. An SR (or a low-vote standby witness) is credited with block/transaction-fee rewards via `payBlockReward`/`payTransactionFeeReward` while its recorded `voteCount` for that cycle is comparatively small. [8](#0-7) 
2. `doMaintenance()` calls `delegationStore.accumulateWitnessVi(cycle, witnessKey, voteCount)`, adding `reward * 10^18 / voteCount` into the persistent `Vi` accumulator for that witness every cycle, with no cap. [3](#0-2) 
3. Over enough cycles (or one cycle with a sufficiently skewed reward-to-vote ratio), `deltaVi` for that witness grows past the point where `deltaVi.multiply(userVoteCount)` divided by `DECIMAL_OF_VI_REWARD` exceeds `Long.MAX_VALUE`. [4](#0-3) 
4. Any voter for that witness calling `withdrawReward` (via `WithdrawBalanceContract` or TVM `VoteRewardUtil.withdrawReward`) receives a silently truncated/garbage `long` reward value; `adjustAllowance` skips crediting it if it's `<= 0`, and `beginCycle`/`endCycle` are still advanced, permanently losing that reward window. [9](#0-8)

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }

    if (!dynamicPropertiesStore.allowChangeDelegation()) {
      return;
    }
    AccountCapsule accountCapsule = accountStore.get(address);
    long beginCycle = delegationStore.getBeginCycle(address);
    long endCycle = delegationStore.getEndCycle(address);
    long currentCycle = dynamicPropertiesStore.getCurrentCycleNumber();
    long reward = 0;
    if (beginCycle > currentCycle || accountCapsule == null) {
      return;
    }
    if (beginCycle == currentCycle) {
      AccountCapsule account = delegationStore.getAccountVote(beginCycle, address);
      if (account != null) {
        return;
      }
    }
    //withdraw the latest cycle reward
    if (beginCycle + 1 == endCycle && beginCycle < currentCycle) {
      AccountCapsule account = delegationStore.getAccountVote(beginCycle, address);
      if (account != null) {
        reward = computeReward(beginCycle, endCycle, account);
        adjustAllowance(address, reward);
        reward = 0;
        logger.info("Latest cycle reward {}, {}.", beginCycle, account.getVotesList());
      }
      beginCycle += 1;
    }
    //
    endCycle = currentCycle;
    if (CollectionUtils.isEmpty(accountCapsule.getVotesList())) {
      delegationStore.setBeginCycle(address, endCycle + 1);
      return;
    }
    if (beginCycle < endCycle) {
      reward += computeReward(beginCycle, endCycle, accountCapsule);
      adjustAllowance(address, reward);
    }
    delegationStore.setBeginCycle(address, endCycle);
    delegationStore.setEndCycle(address, endCycle + 1);
    delegationStore.setAccountVote(endCycle, address, accountCapsule);
    logger.info("Adjust {} allowance {}, now currentCycle {}, beginCycle {}, endCycle {}, "
