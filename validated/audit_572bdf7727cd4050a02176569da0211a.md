## Title
Unbounded, attacker-controlled length fields in `ValidateMultiSign`/`BatchValidateSign` calldata decoding cause uncaught `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` that escape the precompile call and abort transaction/block execution - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

## Summary
The HDF5 bug (`H5FL_arr_malloc` OOB read reachable via `H5S_set_extent_simple`) is a classic case of an attacker-influenced size/length value flowing unchecked into array allocation/indexing, causing an out-of-bounds access. The closest reachable analog in java-tron is in the TVM precompiled contracts `ValidateMultiSign` (address `0x...a`) and `BatchValidateSign` (address `0x...9`), where length/offset fields taken directly from calldata words are used to size and index byte arrays without adequately validating that the derived offsets/lengths stay within the actual `data` buffer, and the resulting exception is not caught along the legacy (pre-`allowTvmSelfdestructRestriction`) code path.

## Finding Description
`ValidateMultiSign.execute` and `BatchValidateSign.doExecute` parse calldata into `DataWord[] words` and then extract nested dynamic arrays using helper functions: [1](#0-0) [2](#0-1) 

Both `extractBytesArray` and `extractSigArray` compute `bytesOffset`/`bytesLen` from attacker-supplied `words[...]` values and then call `extractBytes(data, offset, len)`, which does `Arrays.copyOfRange(data, offset, offset + len)`. If `offset` is negative, `offset > data.length`, or `offset + len` overflows/underflows `int`, `Arrays.copyOfRange` throws `ArrayIndexOutOfBoundsException`; if `len` is negative, `NegativeArraySizeException` is thrown at the earlier `new byte[len][]` allocation. `words[offset + i + 1]` can itself throw `ArrayIndexOutOfBoundsException` if `len` (attacker controlled) exceeds `words.length`.

The `VMConfig.allowTvmOsaka()` gate only calls `isValidAbiEncoding`, which validates the *overall* byte length is 32-aligned and matches a header+N*item shape — it does **not** validate that the internal offset/length words actually point within bounds: [3](#0-2) 

Critically, for `ValidateMultiSign`, when `VMConfig.allowTvmSelfdestructRestriction()` is false (the legacy, pre-TIP path — a chain/parameter-gated feature, not necessarily active on all networks), the code calls `extractBytesArray` directly with **no size-cap check** (the `sigArraySize > MAX_SIZE` guard is only applied in the `allowTvmSelfdestructRestriction()` branch) and with **no surrounding try/catch**: [4](#0-3) 

Unlike `BatchValidateSign.execute`, which wraps `doExecute` in a `catch (Throwable t)`: [5](#0-4) 

`ValidateMultiSign.execute` has **no such wrapper** around the `extractBytesArray`/`extractSigArray` call at line 1072-1074; the only `try/catch` in the method starts *after* extraction (line 1082), so any `RuntimeException` thrown during array extraction propagates straight out of `execute()`.

That exception then propagates through `Program.callToPrecompiledAddress`'s call `contract.execute(data)`: [6](#0-5) 

with no local exception handling in that method for this call. Whether this ultimately manifests as a clean transaction revert or an uncaught propagation that aborts block application depends on the top-level VM/transaction execution loop's exception handling, which I was not able to fully confirm before running out of tool iterations (the `VM.java` step/play loop's `catch` clauses were not retrieved in time). This is the main unverified piece of the chain.

## Impact Explanation
If the uncaught `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` is only caught at the top-level transaction execution boundary and converted into a normal `ContractExeException`/revert, the impact is limited to a failed/revert transaction (no protocol-level harm). However, this analog matches the HDF5 bug-class (unchecked size derived from attacker input driving array allocation/indexing, causing an out-of-bounds condition) precisely in `extractBytesArray`/`extractSigArray`/`extractBytes`, and the missing `MAX_SIZE`/try-catch guard for the legacy `ValidateMultiSign` path (compared to the hardened `BatchValidateSign` and the `allowTvmSelfdestructRestriction()`-gated path) is a genuine defense-in-depth gap: a single crafted transaction from any unprivileged caller can drive this code path with attacker-chosen offset/length words. If the exception is not fully contained by the outer VM/actuator exception handling (unverified), this could manifest as a node crash or halted block application (availability impact), matching the "node crash or halt" acceptance criterion.

## Likelihood Explanation
`ValidateMultiSign` is reachable by any account issuing a `CALL`/`STATICCALL`/`DELEGATECALL` to precompile address `0x...a` with fully attacker-controlled calldata — no special privilege, deployed contract, or SR/witness status is required. The only precondition is that `VMConfig.allowTvmSelfdestructRestriction()` is not active for the relevant path (i.e., the legacy decoding branch is taken), which is a chain-parameter/feature-activation state outside the attacker's control but plausible on chains/testnets that haven't activated that proposal, or via other reachable branches that still call `extractBytesArray`/`extractBytes32Array` (e.g., `BatchValidateSign`'s `extractBytes32Array`, which has no bounds cap at all and is called unconditionally, though it is protected by the outer try/catch in that class).

## Recommendation
- Add explicit bounds validation on every attacker-derived `bytesOffset`, `bytesLen`, and array-length word in `extractBytesArray`, `extractSigArray`, and `extractBytes32Array` before using them to size or index arrays (reject if negative, if it exceeds `words.length`/`data.length`, or if `offset + len` overflows).
- Apply the same `MAX_SIZE` cap check unconditionally in `ValidateMultiSign.execute`, not only inside the `allowTvmSelfdestructRestriction()` branch.
- Wrap the extraction calls in `ValidateMultiSign.execute` (lines 1072-1074) in a `try/catch(Throwable)` analogous to `BatchValidateSign.execute`, returning `Pair.of(true, DATA_FALSE)` on malformed input instead of letting the exception propagate.
- Confirm (this was not fully verified due to tool-iteration limits) that `VM.java`'s opcode execution loop and the actuator-level transaction processing catch all `RuntimeException`/`Error` types thrown from precompiled contract execution and convert them into a contained transaction failure rather than allowing them to escape into block-application code.

## Proof of Concept
1. Craft a transaction that calls a contract which issues `CALL` to precompile address `0x...a` (`ValidateMultiSign`).
2. Build `rawData` such that `words[3]` (the array-offset word) encodes an offset that, after `/WORD_SIZE`, indexes to a `words[...]` slot containing an attacker-chosen huge or negative "length" value (e.g., `0xFFFFFFFF` truncated via `intValueSafe()` to a large positive or negative int).
3. On chains/paths where `VMConfig.allowTvmSelfdestructRestriction()` is false, `extractBytesArray(words, offset, rawData)` is invoked directly (`PrecompiledContracts.java:1072-1074`) without the `MAX_SIZE` guard and without a surrounding try/catch, so the crafted length triggers `NegativeArraySizeException` (from `new byte[len][]`) or `ArrayIndexOutOfBoundsException` (from `words[offset+i+1]` or `Arrays.copyOfRange` in `extractBytes`), propagating uncaught out of `ValidateMultiSign.execute()` and into `Program.callToPrecompiledAddress` (`Program.java:1752`).
4. Observe whether this is contained as a normal revert or propagates further; further investigation using a live/debuggable node build (not possible in the current read-only ask session) is needed to confirm the exact blast radius.
