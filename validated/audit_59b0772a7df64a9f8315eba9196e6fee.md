### Title
Unauthenticated `RecvError` spoofing tears down relay-only tunnels because the source-address check is skipped when `HostInfo.GetRemote()` is invalid - (File: outside.go)

### Summary
`header.RecvError` packets are processed before any certificate/handshake state is required and before any decryption, using only the 32-bit `RemoteIndex` from the plaintext header. The handler only validates the sender's address when the target hostinfo already has a valid direct remote; hostinfos that are relay-only (no direct UDP path, e.g. NAT-traversal via a Nebula relay) have an invalid `GetRemote()`, and for those the address check is bypassed entirely, allowing any off-path attacker who can observe or guess a `RemoteIndex` to force-close the tunnel from a spoofed source.

### Finding Description
`handleRecvError` is reached straight from `readOutsidePackets` for the `header.RecvError` message type, prior to any decryption or cert checks [3](#0-2) . It looks the hostinfo up purely by the attacker-supplied `h.RemoteIndex`:

```
hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
...
hr := hostinfo.GetRemote()
if hr.IsValid() && hr != addr {
    f.l.Info("Someone spoofing recv_errors?", ...)
    return
}
f.closeTunnel(hostinfo)
f.handshakeManager.DeleteHostInfo(hostinfo)
``` [4](#0-3) 

The spoof-detection logic `if hr.IsValid() && hr != addr` only rejects the packet when the hostinfo already has a known, valid direct remote that differs from the packet's source. When `hr` is *not* valid (`IsValid()` false), the condition is false and the packet is accepted unconditionally, regardless of where it actually came from.

`GetRemote()` returns the zero value whenever `i.remote` has never been stored [1](#0-0) . This is exactly the case for tunnels established via a relay: on relay completion the code calls `hostinfo.relayState.InsertRelayTo(...)` instead of `hostinfo.SetRemote(...)` [2](#0-1) , and `sendNoMetrics`/`SendVia` explicitly branch on `!hostinfo.GetRemote().IsValid()` to choose the relay path [5](#0-4) [6](#0-5) , confirming that relay-only hostinfos never populate a direct remote.

`RemoteIndex` is not a secret: it appears in the plaintext header of every encrypted data packet, relay frame, and handshake packet on the wire, so an attacker positioned to observe any traffic to/from a relayed peer (or simply brute-forcing the 32-bit space, since there's no rate limit on `RecvError`) can trivially obtain or guess a valid index for a relay-only tunnel and forge a `RecvError` from any spoofed UDP source address.

### Impact Explanation
This is remote state poisoning / denial of service: an unauthenticated, off-path attacker (no CA-signed certificate required — `RecvError` is handled before any handshake/cert validation) can force `closeTunnel` and `handshakeManager.DeleteHostInfo` on any hostinfo that is relay-only, repeatedly severing tunnels that rely on relays (commonly used specifically to work around difficult NATs where a direct path may never establish). This mirrors the class of bug in the referenced report: a control/limit-enforcing check silently degrades to "always allow" for a subset of legitimately-reachable states (there, deposit accounting on the router `msg.sender`; here, source validation on hostinfos with no direct remote), letting an attacker exploit that gap to disrupt service for others who depend on that shared code path.

### Likelihood Explanation
Likelihood is high for any deployment using `relay.use_relays`/`relay.am_relay` (an explicitly supported, documented feature for NAT traversal) [7](#0-6) . The attacker needs no certificate, no prior handshake, and only the target's 32-bit `RemoteIndex`, which is exposed unencrypted on every packet the target sends/receives and is not rate-limited for `RecvError` handling.

### Recommendation
Do not treat `!hr.IsValid()` as "skip the address check." For relay-only hostinfos, validate that `addr` corresponds to one of the hostinfo's known/established relay peers' current remotes (or otherwise authenticate `RecvError` senders, e.g., by requiring it be relayed through an already-authenticated relay tunnel rather than accepted from raw UDP). At minimum, apply the same allow-list / rate-limiting used for handshakes (`GetRemoteAllowList()`) to `RecvError` processing, and consider requiring `RecvError` to be relayed (as relay frames are) rather than accepted from a bare untrusted UDP source when the target has no direct remote.

### Proof of Concept
1. Configure three nodes: `me` (uses relay), `relay` (`am_relay: true`), `them` (uses relay), matching the existing e2e setup pattern [8](#0-7) .
2. Establish the relayed tunnel between `me` and `them` so neither has a direct UDP remote for the other (relay-only path), as in `TestHandshakeRelayComplete` [9](#0-8) .
3. As an attacker with no certificate, observe/guess `them`'s `localIndexId` (visible in plaintext relay-frame headers routed through `relay`).
4. Craft a bare UDP packet of type `header.RecvError` with `RemoteIndex` set to that index, and send it directly to `me`'s or `them`'s listening UDP port from an arbitrary spoofed source address.
5. Observe that `handleRecvError` finds the hostinfo via `QueryReverseIndex`, sees `hr.IsValid() == false` (relay-only), skips the spoof check, and calls `closeTunnel`/`DeleteHostInfo`, tearing down the tunnel without any valid credential from the attacker.

func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
