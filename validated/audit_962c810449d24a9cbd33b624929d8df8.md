### Title
`disabledApi` access-restriction bypass via the JSON-RPC interface - (File: `framework/src/main/java/org/tron/core/services/jsonrpc/FullNodeJsonRpcHttpService.java`)

### Summary
The `node.disabledApi` config option is the java-tron operator-facing mechanism for shutting off/restricting specific query APIs (e.g. to prevent anonymous exposure of account, block or transaction data). It is enforced for HTTP and gRPC query paths, but is explicitly **not** enforced for the JSON-RPC (Ethereum-compatible) query path, allowing any client to retrieve the same data through `eth_*` JSON-RPC calls even when the equivalent Wallet/WalletSolidity API was disabled by the operator. This mirrors the GitLab CVE-2022-0172 bug class: a data-access restriction is enforced on one query interface (REST) but bypassable through a parallel query interface (GraphQL) that reaches the same underlying data.

### Finding Description
`HttpApiAccessFilter.isDisabled` rejects any HTTP servlet endpoint whose last path segment is in `CommonParameter.getInstance().getDisabledApiList()`, and it is wired into the full node / solidity / PBFT HTTP servlet chains: [1](#0-0) 

Likewise, `RpcApiAccessInterceptor.isDisabled` enforces the same `disabledApiList` check for the gRPC `Wallet`/`WalletSolidity` interface and is registered as a gRPC server interceptor in `RpcService.addInterceptor`: [2](#0-1) [3](#0-2) 

However, `FullNodeJsonRpcHttpService` (and its solidity/PBFT counterparts) only registers `HttpInterceptor` — a metrics-only filter with no `disabledApiList` check — as the filter for the `/jsonrpc` servlet path, and never registers `HttpApiAccessFilter`: [4](#0-3) [5](#0-4) 

This is also explicitly documented as a known limitation in the reference config, confirming the check is scoped only to http/rpc/pbft, not jsonrpc: [6](#0-5) 

A search of the entire repo for `disabledApiList` usage confirms it is referenced only in `HttpApiAccessFilter`, `RpcApiAccessInterceptor`, `CommonParameter`, and `Args` — never in the `org.tron.core.services.jsonrpc` package where `TronJsonRpcImpl` implements the `eth_*` methods (`getBalance`/`eth_getBalance`, `getTransactionByHash`, `call`, `getBlockByNumber`, etc.).

### Impact Explanation
An operator who adds a sensitive endpoint (e.g. `getaccount`, `gettransactionbyid`, `triggerconstantcontract`) to `node.disabledApi` to restrict anonymous read access believes that data is no longer retrievable by unauthorized clients. If the node also has `jsonrpc.httpFullNodeEnable` (or solidity/PBFT variant) turned on — which is common for Ethereum-tooling compatibility — an anonymous API client can retrieve the functionally equivalent data (account balances, transaction details, contract call results, block data) via the corresponding `eth_*` JSON-RPC method, completely bypassing the intended restriction. This is an access-control bypass allowing unauthorized read of account/transaction/contract state that the node operator explicitly tried to block, matching the "unauthorised users can read data through an alternate API path" bug class of the GitLab analog.

### Likelihood Explanation
High reachability: this requires no privileges, no malicious SR/witness/peer behavior, and no code change on the attacker's part — a single unauthenticated JSON-RPC HTTP request against `/jsonrpc` on a node with JSON-RPC enabled is sufficient. The only precondition is that the operator has both (a) added an endpoint to `disabledApi` and (b) enabled the JSON-RPC HTTP service, which is a normal, documented, supported configuration combination.

### Recommendation
Apply the same `disabledApiList` check to the JSON-RPC dispatch path — either by adding an equivalent filter (mapping `eth_*` method names to the Wallet-API names they proxy) to `FullNodeJsonRpcHttpService`/`JsonRpcServiceOnSolidity`/`JsonRpcServiceOnPBFT`'s filter chain, or by checking `disabledApiList` inside `TronJsonRpcImpl` dispatch before invoking the corresponding Wallet API logic. Update `reference.conf` documentation accordingly once fixed.

### Proof of Concept
1. Configure a node with:
   ```
   node.disabledApi = ["getaccount"]
   node.jsonrpc.httpFullNodeEnable = true
   ```
2. Confirm `GET /wallet/getaccount?...` returns `{"Error":"this API is unavailable due to config"}` (per `HttpApiAccessFilterTest.testHttpFilter`, `framework/src/test/java/org/tron/core/services/filter/HttpApiAccessFilterTest.java:51-90`).
3. Send a JSON-RPC request to the same node's `/jsonrpc` endpoint:
   ```
   POST /jsonrpc
   {"jsonrpc":"2.0","method":"eth_getBalance","params":["0x...","latest"],"id":1}
   ```
4. Observe the request succeeds and returns the account balance, i.e. the same information `getaccount` was configured to hide, because `FullNodeJsonRpcHttpService` never applies `HttpApiAccessFilter`/`disabledApiList` to the JSON-RPC servlet chain (`framework/src/main/java/org/tron/core/services/jsonrpc/FullNodeJsonRpcHttpService.java:30-44`).
