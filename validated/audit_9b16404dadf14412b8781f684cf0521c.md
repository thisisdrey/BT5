### Title
Strict equality invariant checks in JupLend deposit/withdraw revert on rounding/precision mismatch, permanently blocking user funds - ([File: programs/marginfi/src/instructions/juplend/deposit.rs], [File: programs/marginfi/src/instructions/juplend/withdraw.rs])

### Summary
`juplend_deposit` and `juplend_withdraw` locally recompute the exact number of fTokens/underlying units that the JupLend CPI *should* produce, and then assert this with a strict `require_eq!` against what the CPI actually returned. This is architecturally the same bug class as the reported NFT royalty issue: a program-side integer computation is expected to exactly match an independently-rounded external computation, and any divergence — even by 1 unit — causes a hard revert via strict equality rather than a tolerant `>=`/`<=` check.

### Finding Description
In `juplend_deposit`, the program computes `expected_shares` via `expected_shares_for_deposit_from_rates` [1](#0-0) , then after the CPI mint, asserts the actual minted amount matches exactly: [2](#0-1) 

Similarly, `juplend_withdraw` computes `shares_to_burn`/`token_amount` locally via `expected_shares_for_withdraw_from_rate` / `expected_assets_for_redeem_from_rate` [3](#0-2) , then strictly compares the CPI's actual result against these locally-computed expectations: [4](#0-3) 

Both of these local math functions replicate JupLend's on-chain rounding logic (floor/ceil against `token_exchange_price`/`liquidity_exchange_price`), which is an external, third-party program (`juplend_mocks`/JupLend). Any divergence between the assumed and actual JupLend rounding behavior — e.g., a difference in exchange-price semantics, an off-by-one in a boundary case, or a future JupLend upgrade that changes internal rounding — causes `MarginfiError::JuplendDepositFailed` / `MarginfiError::JuplendWithdrawFailed` to fire via a strict `==` check rather than a safe inequality, aborting the transaction. Critically, the marginfi-side accounting mutation (`bank_account.withdraw()` / `deposit_no_repay()`) happens *before* the CPI and its equality check in the same instruction, meaning any user hitting this path deterministically (same amount, same state) will have every retry fail identically, since the underlying rounding divergence is a function of price/amount that doesn't change between retries.

### Impact Explanation
If the strict equality mismatch is reachable for any deterministic combination of `token_exchange_price` / `liquidity_exchange_price` / `amount`, affected users become permanently unable to withdraw or deposit through that JupLend bank — a permanent lock/freeze of funds for that specific interaction, since the instruction always reverts atomically (no partial state is persisted) and the failure condition is a function of on-chain state that a user cannot control. This maps to the report's "permanent lock" impact class rather than theft, but is a genuine denial-of-withdrawal risk in the JupLend integration path.

### Likelihood Explanation
Likelihood is uncertain and cannot be proven from the indexed code alone: the local math functions (`expected_shares_for_deposit_from_rates`, `expected_shares_for_withdraw_from_rate`, `expected_assets_for_redeem_from_rate`) are explicitly designed and unit-tested to reproduce JupLend's rounding exactly [5](#0-4) , and the withdraw code even documents (in comments) why dust/mismatch scenarios are believed unreachable under current JupLend math [6](#0-5) . The residual risk is a mismatch between the mocked/tested JupLend behavior and the real on-chain JupLend program (`juplend_mocks` is explicitly a mock crate), or a future JupLend upgrade changing rounding semantics. This is a plausible-but-unproven analog rather than a demonstrated exploit against production JupLend.

### Recommendation
Replace the strict `require_eq!` checks in `programs/marginfi/src/instructions/juplend/deposit.rs` (line 78) and `programs/marginfi/src/instructions/juplend/withdraw.rs` (lines 233, 242) with tolerant checks (e.g., `require_gte!`/`require_lte!` with a documented 1-unit tolerance, mirroring `assert_within_one_token` already used elsewhere in the codebase for Kamino [7](#0-6) ), and trust/use the CPI's actual returned amount for marginfi-side share accounting rather than requiring it to exactly equal a locally-precomputed value. This avoids a hard dependency on perfectly replicating an external program's internal rounding.

### Proof of Concept
No concrete on-chain reproduction was found in the indexed code/tests; existing round-trip tests (`round_trip_deposit_then_redeem_at_same_prices`, `round_trip_never_increases` in `programs/marginfi/src/instructions/juplend/local_tests.rs`) currently pass for the sampled price/amount combinations tested [8](#0-7) , suggesting the mismatch, if it exists, is not trivially reachable with the current mock. A background Devin session with terminal/build access would be needed to fuzz `expected_shares_for_deposit_from_rates`/`expected_shares_for_withdraw_from_rate` against the real (non-mock) JupLend on-chain program's actual rounding to confirm or rule out this analog.

    //
    // NOTE: Unlike Drift (which has reachable dust due to double-rounding in its
    // assets → scaled_balance → assets conversion), this case is UNREACHABLE in JupLend
    // under normal operation because:
    //
    // - JupLend uses single-level math: shares = floor(assets * 1e12 / price)
    // - Minimum shares = 1 (u64 integer, not fractional)
    // - Exchange price >= 1e12 (starts at 1:1, only increases with yield)
    // - Therefore: floor(1 * 1e12 / 1e12) = 1 (always at least 1 underlying)
    //
    // Drift's dust is reachable because it uses multi-step rounding:
    // 1. assets → scaled_balance (floor + variable precision per token)
    // 2. scaled_balance + 1 (round up for safety)
    // 3. scaled_balance → assets (floor again)
    // This cascading rounding can produce 0 tokens from small positions.

    // This defensive code exists for potential edge cases:
    // - Socialized loss reducing JupLend's exchange price below 1e12
    // - Future protocol changes affecting share/price invariants
    //
    // If we can guarantee that JupLend's exchange price never drops below 1e12, this branch is dead code.

use crate::{prelude::MarginfiResult, MarginfiError};
use anchor_lang::prelude::*;

#[inline]
pub fn assert_within_one_token(actual: u64, expected: u64, err: MarginfiError) -> MarginfiResult {
    // Should be sufficient tolerance for 99.999999% of cases
    const TOKEN_AMOUNT_TOLERANCE: u64 = 1;

    let diff = actual.abs_diff(expected);
    if diff > TOKEN_AMOUNT_TOLERANCE {
        msg!(
            "Amount mismatch → actual: {}, expected: {}, diff: {}",
            actual,
            expected,
            diff
        );
        return Err(err.into());
    }
    Ok(())
}

    #[test]
    fn round_trip_deposit_then_redeem_at_same_prices() {
        // Deposit assets -> get shares -> redeem shares -> get assets back.
        // Rounding loss should be at most 1 token unit.
        let l = lending_state(1_200_000_000_000, 1_500_000_000_000);
        let deposit_amount = 100_000_000u64;

        let shares = l.expected_shares_for_deposit(deposit_amount).unwrap();
        let redeemed = l.expected_assets_for_redeem(shares).unwrap();

        assert!(redeemed <= deposit_amount, "redeem must not exceed deposit");
        assert!(
            deposit_amount - redeemed <= 1,
            "rounding loss {} exceeds 1",
            deposit_amount - redeemed
        );
    }

    #[test]
    fn round_trip_never_increases() {
        // Across various price combos: deposit -> redeem never returns more than deposited.
        for &(liq_price, tok_price) in &[
            (1_000_000_000_000u64, 1_000_000_000_000u64),
            (1_200_000_000_000, 1_500_000_000_000),
            (1_000_000_000_000, 2_000_000_000_000),
            (1_500_000_000_000, 1_200_000_000_000),
            (1_100_000_000_000, 1_100_000_000_000),
        ] {
            let l = lending_state(liq_price, tok_price);
            for &amount in &[1u64, 7, 100, 1_000_000, 100_000_000, 1_000_000_000_000] {
                let shares = l.expected_shares_for_deposit(amount).unwrap();
                let redeemed = l.expected_assets_for_redeem(shares).unwrap();
                assert!(
                    redeemed <= amount,
                    "round-trip {} -> {} shares -> {} redeemed should not exceed original (liq={}, tok={})",
                    amount, shares, redeemed, liq_price, tok_price

            }
