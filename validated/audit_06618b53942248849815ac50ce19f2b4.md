### Title
Uncontrolled Resource Consumption via Unvalidated Array-Length Field in `ValidateMultiSign`/`BatchValidateSign` TVM Precompiles - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `ValidateMultiSign` and `BatchValidateSign` TVM precompiled contracts (addresses `0x...0a` and `0x...09`) decode ABI-encoded signature/address arrays using helper functions that read an array-length word directly from attacker-controlled call data and immediately allocate a Java array of that size — with no upper bound check — before any validation of the value against the actual data size. This mirrors the CVE-2024-31669 bug class in rizin, where length fields taken from untrusted binary data (`bin_pe_parse_imports`, `Pe_r_bin_pe_parse_var`, `estimate_slide`) were used to drive allocations/loops without adequate bounds checking, leading to uncontrolled resource consumption.

### Finding Description
`extractBytesArray`, `extractSigArray`, and `extractBytes32Array` all read a length value from the decoded `DataWord[]` (which is itself derived directly from the raw contract call data) and use it, unclamped, to size a Java array: [1](#0-0) 

`extractBytes32Array` has no offset bound check at all before indexing, and `extractBytesArray`/`extractSigArray` only check that `offset` itself is in range — none of them validate `len` before executing `new byte[len][]`.

These helpers are invoked from `ValidateMultiSign.execute` and `BatchValidateSign.execute`: [2](#0-1) [3](#0-2) 

Critically, the only bound (`MAX_SIZE`) check on the array-size word is gated behind `VMConfig.allowTvmSelfdestructRestriction()`:

```java
if (VMConfig.allowTvmSelfdestructRestriction()) {
  int sigArraySize = words[words[3].intValueSafe() / WORD_SIZE].intValueSafe();
  if (sigArraySize > MAX_SIZE) {
    return Pair.of(true, DATA_FALSE);
  }
}
byte[][] signatures = VMConfig.allowTvmSelfdestructRestriction() ?
    extractSigArray(...) :
    extractBytesArray(words, words[3].intValueSafe() / WORD_SIZE, rawData);
```

When this hard-fork flag is not active (e.g. any chain — testnet/private/mainnet-pre-activation — where the corresponding TIP has not yet been enabled), `extractBytesArray`/`extractBytes32Array` are reached with **no length validation whatsoever**. `DataWord.intValueSafe()` can return values up to `Integer.MAX_VALUE`, so a caller can supply a length word such as `0x7FFFFFFF`, causing `new byte[Integer.MAX_VALUE][]` — an attempted allocation of many gigabytes of reference-array memory — inside `extractBytesArray`, `extractBytes32Array`, or `extractSigArray`, before any subsequent loop bound-check ever executes.

### Impact Explanation
Any unprivileged account can invoke a smart contract that performs a `CALL`/`STATICCALL` to the `ValidateMultiSign` (`0x...0a`) or `BatchValidateSign` (`0x...09`) precompile addresses with crafted call data containing an oversized array-length word. This triggers an attempted massive heap allocation inside the TVM execution path of a single transaction, which can throw `OutOfMemoryError` or cause severe GC pressure/node stalls — a resource-exhaustion condition matching "node crash or halt" in the validated impact categories. Because `BatchValidateSign.execute` wraps its logic in a broad `try/catch (Throwable)` that catches `OutOfMemoryError` too, a *single* call may be contained, but the JVM-wide memory pressure from the huge (failed or successful) allocation attempt still affects the whole node process, and repeated invocations (e.g., in a loop, or via many transactions) amplify the effect into an actual denial-of-service against the node's ability to process further transactions/blocks.

### Likelihood Explanation
Exploitation requires only a signed, otherwise-normal contract call — this is fully reachable by any account able to broadcast a transaction (no special privilege), matching the "unprivileged transaction broadcaster/contract deployer" reachability requirement. The condition depends on the `allowTvmSelfdestructRestriction` hard-fork flag being disabled, which is true prior to the TIP's activation and potentially on non-mainnet or forked deployments of this codebase, making the unguarded legacy code path (`extractBytesArray`/`extractBytes32Array`) directly reachable in those configurations.

### Recommendation
Apply an unconditional, pre-allocation bound check (e.g., `len <= MAX_SIZE`, and `len` consistent with the remaining `words.length`) inside `extractBytesArray`, `extractBytes32Array`, and `extractSigArray` themselves, rather than only in the caller and only when `allowTvmSelfdestructRestriction()` is active. This ensures the fix is not tied to hard-fork activation state and closes the legacy/pre-activation code path.

### Proof of Concept
1. Craft ABI call data for `validatemultisign(address,uint256,bytes32,bytes[])` (or `batchvalidatesign(bytes32,bytes[],address[])`) where the dynamic array's length word (the word pointed to by the array's offset) is set to a very large value such as `0x000000000000000000000000000000000000000000000000000000FFFFFFF0`.
2. On a network/build where `allowTvmSelfdestructRestriction` is not yet activated (`VMConfig.allowTvmSelfdestructRestriction()` returns false), submit a `TriggerSmartContract` transaction that performs a `CALL` to precompile address `0x...09` or `0x...0a` with this crafted data.
3. Execution reaches `extractBytesArray`/`extractBytes32Array` (via `PrecompiledContracts.PrecompiledContract.execute`), which executes `new byte[len][]` with `len` ≈ `0xFFFFFFF0`, triggering a massive allocation attempt / `OutOfMemoryError` inside the node's TVM execution thread, degrading or crashing the node process.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
