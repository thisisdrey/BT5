This confirms the vulnerability. Each `signers-{set}-{message_id}` StackerDB contract shares the exact same signer-slot layout (`stackerdb-get-signer-slots-page` calls back into the shared `.signers` contract's `stackerdb-signer-slots-{0,1}` list), so a given signer address occupies the **same `slot_id`** across every message-lane contract (`BlockResponse`, `Transactions`, `MockSignature`, etc.) for a reward cycle. The chunk signature digest, however, never binds to the destination contract:

`SlotMetadata::auth_digest()` hashes only `slot_id`, `slot_version`, and `data_hash` [1](#0-0) , and `validate_received_chunk` accepts a chunk purely by checking this signature against the address configured for that slot in the target contract [2](#0-1) . Nothing in the signed material — nor in the storage/replication path (`poststackerdbchunk.rs`, `handle_unsolicited_StackerDBPushChunk`) — ties the signature to the specific `contract_id`/StackerDB it was intended for [3](#0-2) . This is the structural analog of the EIP-712 report: the "verifying contract" (here, the StackerDB `QualifiedContractIdentifier`) is omitted from the signed domain, so a signature valid in one context is valid in another.

### Title
Cross-contract replay of StackerDB chunk signatures due to missing contract-identity binding in the signed digest - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` computes the signed hash from only `slot_id`, `slot_version`, and `data_hash`, with no `QualifiedContractIdentifier`/StackerDB name in the domain. Because every signer occupies the identical `slot_id` across all `signers-{set}-{message_id}` StackerDB contracts for a reward cycle (all lanes read the same slot assignment from the shared `.signers` contract), any legitimately-signed chunk observed on the network for one message lane can be replayed by any unprivileged network observer into a *different* lane/contract, as long as that destination's expected version/size constraints happen to be satisfiable.

### Finding Description
- `auth_digest()` binds only `(slot_id, slot_version, data_hash)` [1](#0-0) .
- `validate_received_chunk()` looks up the owning address for `(smart_contract_id, slot_id)` via `get_slot_signer` and checks the signature against *that* address only — it never checks that the signature itself commits to `smart_contract_id` [2](#0-1) .
- The `.signers` boot contract assigns identical slot layouts to every message-lane contract for a given signer set: `signers-{set}-{message_id}` all call back into `stackerdb-get-signer-slots-page` on the shared `.signers` contract [4](#0-3) , and `signers_db_get_slots` test confirms all message-id contracts for a signer-set return the same slot list [5](#0-4) .
- This means a given signer's private key signs chunks for the same `slot_id` across `BlockResponse`, `Transactions`, `MockSignature`, etc. — differentiated only by which contract the chunk is POSTed/relayed to, not by anything inside the signature. The event-parsing side later filters by payload-type-vs-lane (`signer_message_payload_matches_lane`) [6](#0-5) , but this filter is applied only when the *signer software* consumes events — it is not enforced by the node when accepting/storing/broadcasting the chunk (`poststackerdbchunk.rs`, `handle_unsolicited_StackerDBPushChunk`, `process_stacker_db_chunks`) [3](#0-2) [7](#0-6) .
- Consequently, an unprivileged network peer that observes a validly-signed chunk destined for contract A can resubmit the identical bytes+signature to contract B (same signer, same `slot_id`), and the node's write path will accept and store/broadcast it as long as `slot_version` and `chunk_size`/`max_writes` constraints of B happen to be satisfied — even though the signer never authorized that data for B's StackerDB.

### Impact Explanation
This breaks the equality the protocol depends on ("signed for StackerDB A" vs "accepted into StackerDB B"), enabling an unauthenticated/unauthorized write into a StackerDB the signature was never intended for, and its subsequent network-wide propagation via `broadcast_message`/relay to peers replicating that StackerDB [8](#0-7) . Because downstream consumers apply the payload-type/lane filter, the direct application-level effect may often be limited to stale/garbage data occupying a slot (denying that reward-cycle slot's real usage until version numbers catch up) rather than direct semantic forgery — but the write and propagation of data foreign to the target StackerDB is itself an unauthorized-write/forged-data-propagation issue under the given severity criteria.

### Likelihood Explanation
High feasibility: an attacker only needs to observe one legitimately broadcast chunk (trivial, since these are periodically pushed p2p/stored StackerDB chunks) and re-POST it (or relay/replay it over p2p) to a differently-named StackerDB contract for the same reward cycle/signer set. No node secret or privileged role is required, and slot assignment collisions across lanes are the default, not an edge case, per the shared `.signers` contract design.

### Recommendation
Include the destination `QualifiedContractIdentifier` (or equivalently, the `MessageSlotID`/lane) in `SlotMetadata::auth_digest()` so that a StackerDB chunk signature is bound to the specific contract it targets — mirroring the EIP-712 fix of committing to the actual "verifying contract" rather than a shared/ambient identity. This requires updating `auth_digest`, `sign`, and `verify` in `libstackerdb/src/libstackerdb.rs`, and threading the contract identifier through `StackerDBChunkData`/callers (`poststackerdbchunk.rs`, `stackerdb/mod.rs`, signer client code) consistently for both signing and verification.

### Proof of Concept
1. Reward cycle `N`, signer `S` (private key `sk`) is assigned `slot_id = k` in both `signers-0-1` (Transactions lane) and `signers-0-3` (some other lane) — guaranteed by shared slot list, per `signers_db_get_slots` test [5](#0-4) .
2. Signer `S` legitimately signs and POSTs a chunk `(slot_id=k, slot_version=v, data=D)` to `signers-0-1` via `send_message_bytes_with_retry` [9](#0-8) ; this is observed by an attacker on the p2p network or via public RPC.
3. Attacker submits the identical `StackerDBChunkData{slot_id:k, slot_version:v', sig, data:D}` (same signature/data, adjusted version if needed to satisfy `validate_received_chunk`'s freshness check) to `signers-0-3` via `POST /v2/stackerdb/<signers-0-3 id>/chunks` [10](#0-9) .
4. `validate_received_chunk` for `signers-0-3` resolves `get_slot_signer(signers-0-3, k)` to the same address `S` (identical slot layout) and `slot_metadata.verify(&addr)` succeeds because the digest never referenced the contract [2](#0-1) , so the chunk is stored and broadcast to `signers-0-3` replicas — data never authorized for that StackerDB.
