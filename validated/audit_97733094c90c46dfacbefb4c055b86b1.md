### Title
Market order matching reverts entirely once MAX_MATCH_NUM is exceeded, discarding already-filled partial matches and delaying order execution - (File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java)

### Summary
`MarketSellAssetActuator.matchOrder()` walks the order book and fills the taker order against maker orders one at a time inside a `while` loop, mutating account balances/asset amounts and order state via `matchSingleOrder()` on every iteration [1](#0-0) . If the number of matches in a single taker order exceeds `MAX_MATCH_NUM` (20), the method throws a `ContractValidateException` from deep inside the loop, after several matches have already mutated in-memory state [2](#0-1) . This exception propagates out of `execute()` as a `ContractExeException` [3](#0-2) , which causes the whole revoking-store session for the transaction to be discarded rather than committed, exactly the "all successful partial work thrown away because of one late-breaking condition" pattern described in the Notional report (where a healthy/unhealthy state discovered late in execution reverts an otherwise-valid batch operation).

### Finding Description
The root cause mirrors the Notional bug class: a condition that depends on dynamic, attacker/market-influenceable state (the depth and fragmentation of the resting order book) is only discovered mid-execution, and when it trips, the code reverts the *entire* transaction instead of gracefully stopping and keeping the fills already made.

- `matchOrder()` iterates prices and orders, incrementing `matchOrderCount` on every successful match [4](#0-3) .
- Each iteration already performs a `matchSingleOrder()` call that transfers balances/tokens between the taker and maker and marks orders `INACTIVE`, i.e. state has already been mutated in the local `Repository`/store objects before the count is checked [5](#0-4) .
- Once `matchOrderCount > MAX_MATCH_NUM`, a `ContractValidateException("Too many matches. MAX_MATCH_NUM = " + MAX_MATCH_NUM)` is thrown from inside `execute()` [2](#0-1) .
- `execute()` catches this and other exceptions and rethrows as `ContractExeException` [3](#0-2) , which in `Manager.processTransaction`/`pushTransaction` results in the surrounding `ISession` (revoking-store session) not being merged, so **all** state mutated in `execute()` — including the several successful maker fills already applied to the in-memory account/order stores before the limit was hit — is rolled back with the transaction [6](#0-5) , [7](#0-6) .

Because the number of matches a taker order will hit depends entirely on the current order book state (how many small-quantity maker orders happen to sit at matching prices), whether a given sell/buy transaction reverts is a moving target: a transaction that would have matched fewer than 20 makers when the user built it can exceed the limit by the time it is actually executed on-chain (new small orders placed in the interim, or a differently fragmented book), causing the whole trade to fail and be resubmitted — an analog of the Notional "healthy/unhealthy toggled between check and execution" TOCTOU revert pattern. Repeated occurrence of this delays order execution for both the taker (whose trade never lands) and every maker order that would have partially filled.

### Impact Explanation
This is a liveness/availability issue on the on-chain order-matching feature (`MarketSellAssetContract`), reachable by any unprivileged account issuing a normal signed transaction. Under volatile/fragmented order-book conditions it causes market sell/buy transactions to systematically and unpredictably fail even though a large fraction of the requested trade could have been executed, wasting transaction fees (the `MarketSellFee` is still charged/attempted) and delaying trade execution/liquidity provisioning, similar in class to the delayed-rebalance impact in the source report. It does not directly cause fund loss because the revoking-session rollback keeps state consistent, but it is a Medium-severity availability/DoS-style flaw in the exchange/order matching logic that a market participant can trivially trigger by placing many small resting orders at a matching price to force the >20-match condition and disrupt others' otherwise-valid trades.

### Likelihood Explanation
Likelihood is fairly high because triggering the 20-match threshold requires no special privilege — any account can place many small maker orders at a favorable price (`MarketSellAssetContract` is available to all users), and any incoming taker order attempting to match against a fragmented book will hit this revert. No consensus-node compromise or malicious-SR/witness behavior is required.

### Recommendation
Rework `matchOrder()`/`matchSingleOrder()` so that when the `MAX_MATCH_NUM` limit is reached, the loop stops matching further makers and returns the unfilled remainder of the taker order back to the order book (as is already done when `sellTokenQuantityRemain` reaches 0 partway), instead of throwing an exception that unwinds and discards the already-applied matches. This preserves the fills that already succeeded and avoids revert-driven delay/resubmission, analogous to the Notional recommendation of skipping/short-circuiting rather than reverting the whole operation.

### Proof of Concept
1. An attacker/market maker places `MAX_MATCH_NUM + 1` (21) small resting sell orders for token pair (A, B) at prices that will all match a prospective taker order (as done in `MarketSellAssetActuatorTest.exceedMaxMatchNumLimit`, which reproduces exactly this scenario) [8](#0-7) .
2. A user submits a `MarketSellAssetContract` transaction sized to match against all of these orders.
3. `matchOrder()` walks the price list, successfully filling matches 1–20 (mutating account balances and order state in the repository/stores) [9](#0-8) .
4. On the 21st match, `matchOrderCount > MAX_MATCH_NUM` triggers `ContractValidateException("Too many matches...")`, propagated as `ContractExeException` from `execute()` [2](#0-1) .
5. The enclosing `ISession` used in `Manager.processTransaction`/`pushTransaction` is not merged, so the whole transaction — including the 20 successful matches — is discarded, and the taker's trade never lands despite most of it being executable [6](#0-5) .

  @Test
  public void exceedMaxMatchNumLimit() throws Exception {

    InitAsset();

    int start = 10;
    int limit = MarketSellAssetActuator.getMAX_MATCH_NUM();
    int step = 1;
    int end = start + step * limit;

    //(sell id_1  and buy id_2)
    String sellTokenId = TOKEN_ID_ONE;
    String buyTokenId = TOKEN_ID_TWO;
    long buyTokenQuant = 400L;
    long sellTokenQuant = buyTokenQuant * (end / start + 1);

    byte[] ownerAddress = ByteArray.fromHexString(OWNER_ADDRESS_FIRST);
    AccountCapsule accountCapsule = dbManager.getAccountStore().get(ownerAddress);
    accountCapsule.addAssetAmountV2(sellTokenId.getBytes(), sellTokenQuant,
        dbManager.getDynamicPropertiesStore(), dbManager.getAssetIssueStore());
    dbManager.getAccountStore().put(ownerAddress, accountCapsule);
    Assert.assertEquals(sellTokenQuant,
            (long) accountCapsule.getAssetV2MapForTest().get(sellTokenId));

    // Initialize the order book

    // at least limit+1 times
    for (int i = start; i <= end; i += step) {
      addOrder(buyTokenId, (long) start, sellTokenId, i, OWNER_ADDRESS_SECOND);
    }

    // this order(taker) need to match 21 times
    MarketSellAssetActuator actuator = new MarketSellAssetActuator();
    actuator.setChainBaseManager(dbManager.getChainBaseManager()).setAny(getContract(
        OWNER_ADDRESS_FIRST, sellTokenId, sellTokenQuant, buyTokenId, buyTokenQuant));

    String errorMessage =
        "Too many matches. MAX_MATCH_NUM = " + MarketSellAssetActuator.getMAX_MATCH_NUM();
    try {
      TransactionResultCapsule ret = new TransactionResultCapsule();
      actuator.validate();
      actuator.execute(ret);
      fail(errorMessage);
    } catch (ContractExeException e) {
      Assert.assertEquals(errorMessage, e.getMessage());
    } catch (Exception e) {
      Assert.assertTrue(false);
    }
  }
