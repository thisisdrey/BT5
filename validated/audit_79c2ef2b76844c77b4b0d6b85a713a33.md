### Title
Missing runtime guard for `totalEnergyWeight == 0` in `RepositoryImpl.calculateGlobalEnergyLimit` allows divide-by-zero / unbounded energy limit - (File: `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java`)

### Summary
`RepositoryImpl.calculateGlobalEnergyLimit()`, used by the TVM `Repository` layer to compute a frozen-energy account's global energy limit for smart-contract execution, guards the divisor `totalEnergyWeight` only with a Java `assert` statement rather than a real conditional check. [1](#0-0) 

### Finding Description
The report's bug class is: a divisor derived from a "total supply"/"total weight" value can legitimately be zero (e.g., before anyone has staked/frozen), and the code either reverts incorrectly or fails to guard the division, producing broken math.

In java-tron, `EnergyProcessor.calculateGlobalEnergyLimit()` (the correctly-hardened sibling implementation) explicitly checks the network-wide weight before dividing: [2](#0-1) 

and `BandwidthProcessor.calculateGlobalNetLimit()` has the same protection twice over (`allowNewReward()` guard plus an unconditional `if (totalNetWeight == 0) return 0;`): [3](#0-2) 

However, the TVM-facing `RepositoryImpl.calculateGlobalEnergyLimit()` — which is exercised on every TVM-triggering transaction to determine how much energy a creator/caller can draw from frozen balance — has **no such runtime check at all**. It only contains:
```java
assert totalEnergyWeight > 0;
``` [4](#0-3) 

`assert` statements in the JVM are disabled by default unless the process is started with `-ea`; the java-tron start scripts do not enable assertions in production. This means the guard is a no-op at runtime, and if `totalEnergyWeight` is ever `0` (e.g. immediately after genesis before any account has frozen TRX for energy, or if the network-wide frozen-energy weight temporarily drops to zero through mass unfreezing), execution falls straight into the division:
- Non-hardened path: `(long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight))` — floating point division by zero yields `Infinity`, and casting `Infinity` to `long` in Java yields `Long.MAX_VALUE`. This grants the calling account an effectively unlimited energy limit, i.e., unbacked/unbounded resource allocation for that account's calls into the TVM.
- Hardened path (`allowHardenResourceCalculation()` enabled): `BigInteger.divide(BigInteger.ZERO)` throws `ArithmeticException`, which is uncaught in this method and would propagate up through the TVM execution path, potentially aborting/crashing the block-processing transaction path for every transaction relying on this calculation.

This is directly analogous to the reported Solidity bug: an exchange-rate-style formula whose divisor can legitimately be zero on first use, with the only "protection" being ineffective in real execution (there `require(kHYPESupply>0)` reverts legitimate first calls; here an `assert` that's compiled out fails to prevent an illegitimate divide-by-zero/overflow).

### Impact Explanation
- Non-hardened build: any account triggering a contract call while `totalEnergyWeight == 0` obtains `Long.MAX_VALUE` as its energy limit, i.e., unlimited free energy consumption — an unbacked resource grant that lets an attacker consume unbounded computation without paying the corresponding TRX cost, undermining the energy-fee economic model.
- Hardened build: an uncaught `ArithmeticException` during transaction processing could disrupt block application for any transaction touching this code path, a node-crash/halt-class impact.

### Likelihood Explanation
`totalEnergyWeight` is a persisted dynamic property tracking cumulative frozen-energy weight; it is normally non-zero on a live mainnet due to already-frozen balances, so the practical trigger window is narrow (fresh private/test networks at genesis before any freeze, or a network where energy weight has been fully unfrozen). This makes the flaw most exploitable on private/consortium chains or test networks and reduces likelihood on a mature mainnet, but the code path itself is unconditionally reachable by any unprivileged smart-contract call and contains no defensive check, matching the report's "not handling the zero/first-mint state" bug class exactly.

### Recommendation
Replace the `assert totalEnergyWeight > 0;` in `RepositoryImpl.calculateGlobalEnergyLimit()` with an explicit runtime check (as already done in `EnergyProcessor` and `BandwidthProcessor`), e.g.:
```java
if (totalEnergyWeight <= 0) {
  return 0;
}
```
before performing either the hardened `BigInteger` division or the double-based division.

### Proof of Concept
1. On a network state (e.g., freshly initialized private chain, or one where `totalEnergyWeight` becomes `0`), have any account with `getAllFrozenBalanceForEnergy() >= TRX_PRECISION` trigger a smart contract call that reaches `RepositoryImpl.calculateGlobalEnergyLimit()`.
2. With `allowHardenResourceCalculation()` disabled (default legacy path): the computation `(long) (energyWeight * ((double) totalEnergyLimit / 0))` evaluates to `Long.MAX_VALUE`, granting unlimited energy to the account for that call.
3. With `allowHardenResourceCalculation()` enabled: `BigInteger.divide(BigInteger.ZERO)` throws `ArithmeticException`, propagating uncaught through the TVM execution path. [1](#0-0)

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalEnergyLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }

    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
    long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
      return 0;
    } else {
      assert totalEnergyWeight > 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
