### Title
Solend Withdraw Fails to Honor `ACCOUNT_IN_ORDER_EXECUTION` Flag Used by Every Other Withdraw Path — (File: `programs/marginfi/src/instructions/solend/withdraw.rs`)

### Summary
The external report describes a security-relevant middleware/check that is applied consistently to some route handlers but silently omitted on others (OKX/cross-chain swap endpoints), creating a class of "inconsistent guard enforcement" bugs. The closest reachable analog in the marginfi-v2 program is the `ACCOUNT_IN_ORDER_EXECUTION` health-check-skip guard, which is applied consistently in `lending_account_withdraw`, `kamino_withdraw`, and `juplend_withdraw`, but is missing from `solend_withdraw`.

### Finding Description
Every withdraw-family instruction that can run inside an order-execution transaction is expected to defer the risk-engine health check until `end_execute_order` finalizes the account, because a mid-execution balance state can be transiently "unhealthy" by design (per the order flow's own final `check_health_and_verify_unchanged`). This is implemented by checking `marginfi_account.get_flag(ACCOUNT_IN_RECEIVERSHIP | ACCOUNT_IN_ORDER_EXECUTION)` before calling `check_account_init_health`:

- `lending_account_withdraw`: `!marginfi_account.get_flag(ACCOUNT_IN_RECEIVERSHIP | ACCOUNT_IN_ORDER_EXECUTION)` [1](#0-0) 
- `kamino_withdraw`: same combined flag check [2](#0-1) 
- `juplend_withdraw`: same combined flag check [3](#0-2) 

`solend_withdraw`, however, only imports and checks `ACCOUNT_IN_RECEIVERSHIP` — `ACCOUNT_IN_ORDER_EXECUTION` is never referenced in the file: [4](#0-3) [5](#0-4) 

This is the exact bug class from the report: a protective gate (`inputValidatorMiddleware` in the report; the order-execution health-check deferral here) is wired into some handlers of a family but omitted from a sibling handler doing the same job (transfer/Hyperliquid vs. OKX/cross-chain in the report; `withdraw`/`kamino_withdraw`/`juplend_withdraw` vs. `solend_withdraw` here).

### Impact Explanation
If `solend_withdraw` is invoked as part of an order-execution transaction (bracketed by `start_execute_order`/`end_execute_order`) while the marginfi account is flagged `ACCOUNT_IN_ORDER_EXECUTION`, it will still run `check_account_init_health` against the account's live, mid-execution state instead of deferring to the order flow's own end-of-execution health verification (`execute_record.check_health_and_verify_unchanged` in `order.rs`) [6](#0-5) . Because intermediate order-execution states are permitted to be transiently unhealthy by design elsewhere in the codebase, this inconsistency causes `solend_withdraw` to unexpectedly abort transactions that would otherwise complete safely, or — depending on how order execution composes withdraw legs — could allow the risk engine to be bypassed/mis-evaluated relative to the intended single end-of-order health gate, undermining the intended uniform accounting invariant that "only one check point governs health during order execution." This is an unauthorized-state-change/accounting-inconsistency class issue in a core lending path (withdraw), not a peer/validator/admin-only issue, and does not appear to be a documented out-of-scope item.

### Likelihood Explanation
Likelihood depends on whether `solend_withdraw` is actually composable as one of the withdraw legs inside an order-execution transaction (the codebase's own comments reference "the equivalent from a third party integration" being valid inside start/end deleverage or order execution windows) [7](#0-6) . If Solend withdraw is a supported integration leg in that flow (as `kamino_withdraw`/`juplend_withdraw` clearly are, given their matching flag checks), the bug is deterministically triggered any time a keeper/executor's order-execution transaction touches a Solend-backed balance, making it a reasonably likely occurrence rather than a purely theoretical one. However, I was not able to fully confirm from available code whether `solend_withdraw` is currently listed among the instructions permitted within the `validate_instructions`-guarded order-execution window (the discriminator allow-list itself lives in constants I could not fully enumerate in this pass), so full exploitability confirmation would need that check.

### Recommendation
Add `ACCOUNT_IN_ORDER_EXECUTION` to the flag check in `solend_withdraw`'s post-withdraw health-check gate so it matches `lending_account_withdraw`, `kamino_withdraw`, and `juplend_withdraw`:
```rust
let in_receivership_or_order_execution =
    marginfi_account.get_flag(ACCOUNT_IN_RECEIVERSHIP | ACCOUNT_IN_ORDER_EXECUTION);
if !in_receivership_or_order_execution { ... }
```
More broadly, since this is the second protocol integration path (Solend) found diverging from the shared flag-gating pattern used by Kamino/Juplend/native withdraw, consider factoring the "skip health check during receivership/order-execution, else check + set engine_ok" logic into one shared helper function called by all four withdraw instructions, so future integrations cannot omit a flag by mistake — directly mirroring the report's own recommendation to centralize the check rather than applying it per-handler.

### Proof of Concept
Conceptual PoC (health-check-gate divergence), not a full end-to-end exploit since full order-execution instruction permission for Solend legs could not be verified in this pass:
1. User has a Solend-backed balance and other tagged order balances; places an order via `place_order`.
2. Executor calls `start_execute_order`, setting `ACCOUNT_IN_ORDER_EXECUTION` [8](#0-7) .
3. Within the same transaction, executor issues `solend_withdraw` against the Solend balance as part of rebalancing the order legs.
4. Unlike `kamino_withdraw`/`juplend_withdraw`, `solend_withdraw` does not see `ACCOUNT_IN_ORDER_EXECUTION` set for its skip-check branch [5](#0-4) , so it runs `check_account_init_health` against the account's transient mid-order state — either reverting the entire order execution unexpectedly (breaking otherwise-valid order flows), or evaluating health using stale/incomplete balance information relative to the order's tagged-balance model, diverging from the single point of truth (`end_execute_order`'s `check_health_and_verify_unchanged`) that all other integrations rely on.
