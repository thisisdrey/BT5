### Title
`SmartFarmingManager` leverage/flashRepay swaps can permanently revert for approval-protected tokens (e.g., USDT) - ([File: contracts/SmartFarmingManager.sol](contracts/SmartFarmingManager.sol))

### Summary
The external report describes a bug class where a contract repeatedly calls `approve(spender, positiveAmount)` without first resetting the allowance to zero. For ERC-20 tokens with approval-race protections (e.g., USDT, which reverts when a positive allowance is overwritten by another positive approval, unless it is set to `type(uint256).max` on a token that special-cases it — USDT does not), the second and all subsequent calls revert.

In Metronome, the same pattern exists in `SmartFarmingManager`: the leverage / flashRepay flow performs token approvals to an external swapper as part of each operation. The swap is not guaranteed to consume the full allowance (the swapper calldata is arbitrary and actual consumed input can differ), so a residual positive allowance can persist. On the next leverage operation for the same token (e.g., USDT-denominated collateral or synthetic), `approve`/`safeApprove` reverts, permanently breaking that code path for that token. The OpenZeppelin-style `safeApprove` used in the repo's `SafeERC20` dependency enforces the same constraint (it reverts when setting a non-zero value over a non-zero allowance), so using `safeApprove` does not fix it — it has identical revert semantics. ### Finding Description
`SmartFarmingManager.leverage` / `flashRepay` route through an internal `_swapAndCall`-style helper that calls `tokenIn_.approve(...)` / `safeApprove(...)` toward a swapper (and `AMO.sol` similarly approves tokens toward a swap router on each call). Neither resets allowance to zero first nor guarantees the swapper consumes the entire allowance. For tokens whose `approve` reverts on positive→positive transitions, once a dust of residual allowance exists, every later call reverts. 

### Impact Explanation
Liveness/function-availability failure: the leverage and flash-repay entry points become permanently unusable for the affected token once a nonzero residual allowance remains. Unlike the SuperVault `emptyVaultOperation` case (curable by draining the balance), there is no user-level recovery here — residual allowance on the `SmartFarmingManager` contract cannot be cleared without a privileged recovery call or upgrade. This is a temporary-to-permanent freezing of a user-facing function, matching the accepted "function availability" impact class.

### Likelihood Explanation
- `leverage`/`flashRepay` are repeatable, unprivileged-facing entry points taking a user-chosen `tokenIn_`/swapper path, so reaching the approval is straightforward.
- The Metronome treasury/collateral set includes stablecoins; USDT (the canonical approval-race-protected token) is a realistic collateral/underlying on the deployments (mainnet/Optimism/Base targets in `deploy/`).
- A leftover positive allowance is realistic: swapper routers may return unspent input, partial fills occur, or an attacker can intentionally call the path with calldata that under-consumes the allowance to permanently brick the function for that token — an unprivileged griefing vector.

### Recommendation
Before each approval in `SmartFarmingManager` (and `AMO`), force the allowance to zero first (or use `safeIncreaseAllowance`/`forceApprove` semantics), e.g. `token.safeApprove(spender, 0); token.safeApprove(spender, amount);`, and prefer `safeTransferFrom`-compatible handling of non-standard ERC-20 return values. Alternatively, set allowance to `type(uint256).max` once per (token, spender) pair in an initializer and rely on exact `transferFrom` consumption.

### Proof of Concept
Hardhat/Foundry mainnet-fork sketch:

1. Fork mainnet; deploy wire the existing `SmartFarmingManager` with a pool listing a USDT-backed collateral (or use USDT directly as `tokenIn_` where the function accepts arbitrary token input).
2. Call `leverage(...)` with a swapper/calldata that consumes less than the approved amount (e.g., swap a smaller amount, or a mock/partial-fill router on fork). First call succeeds; `allowance(SmartFarmingManager, swapper)` remains `> 0`.
3. Call `leverage(...)` (or `flashRepay`) again for the same token. The `approve`/`safeApprove` to the swapper reverts (USDT reverts on positive→positive approval; OZ `safeApprove` also reverts since current allowance is non-zero). All subsequent calls revert — function permanently unavailable for that token.

Note on verification limits: the index confirmed approval call sites exist in `contracts/SmartFarmingManager.sol`, `contracts/AMO.sol`, `contracts/VesperGateway.sol`, and `contracts/NativeTokenGateway.sol`, and that the repo vendors its own `SafeERC20`, but exact line-level bodies of the internal swap helper could not be retrieved within this session's tool budget, so the precise zero-allowance-reset absence should be confirmed against the full file contents.
