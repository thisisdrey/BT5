## Title
Client-controlled quarantine fields bypass transaction-scoped repository resolution, enabling cross-repository object access - (File: `internal/gitaly/storage/storagemgr/middleware.go`)

## Summary
Gitaly's transaction middleware decides how to resolve the "target repository" of an RPC in two different ways. The normal path validates the repository and begins a storage-scoped transaction that rewrites the request to the transaction's own snapshot. But if the incoming request already carries non-empty `GitObjectDirectory`/`GitAlternateObjectDirectories` fields, the middleware takes an entirely different branch that skips `ValidateRepository`/`storageHandle.Begin` and instead trusts a client-supplied gRPC metadata value (`relative-path-bin`) to pick the path the RPC will actually operate on. This mirrors the reported bug class: a legitimate security check (transaction-bound path resolution, analogous to L1→L2 address aliasing) is correctly enforced on the main path, but a secondary, less-scrutinized trigger — reachable by setting ordinary, client-controllable proto fields — disables that check entirely.

## Finding Description
`beginTransactionForRepository` normally resolves the RPC's target repository by validating it and starting a transaction bound to it: [1](#0-0) 

That transaction rewrites the request to the transaction's assigned snapshot via `rewriteRequest`/`tx.RewriteRepository`, which is the mechanism that keeps repository resolution scoped and consistent for every RPC.

However, before reaching that logic, the function special-cases requests that already carry quarantine-like fields: [2](#0-1) 

For any non-mutator (accessor) RPC, if `GitObjectDirectory` or `GitAlternateObjectDirectories` is set on the request, the code assumes this is a "loop back from Rails' authorization checks" and calls `restoreSnapshotRelativePath` instead of beginning a transaction: [3](#0-2) 

This function takes the `relative-path-bin` metadata value verbatim and overwrites `targetRepo.RelativePath` with it — with **no call to `storage.ValidateRelativePath`, no `locator.ValidateRepository`, and no partition/transaction binding at all**. The comment in the surrounding code even acknowledges the underlying assumption is fragile: "This property is violated in tests which manually configure the object directory... This allows for circumventing the transaction management."

Both `GitObjectDirectory`, `GitAlternateObjectDirectories` (proto fields on `Repository`), and the `relative-path-bin` gRPC metadata key are ordinary, caller-suppliable values — nothing in the interceptor authenticates that the metadata actually originated from a genuine Rails access-check round-trip. Any accessor RPC (e.g., in `CommitService`, `RefService`, `BlobService`) that carries these fields is diverted onto the `nonTransactionalRequest` path with a client-chosen relative path, bypassing the same `ValidateRepository`/partition-assignment safety net that every other RPC goes through.

This is structurally identical to the reported issue: `_isOnApproveTrigger` is a caller-selectable flag (triggered via `onApprove()`) that bypasses the aliasing check that is otherwise unconditionally applied. Here, populating `GitObjectDirectory`/`GitAlternateObjectDirectories` is a caller-selectable trigger that bypasses the `ValidateRepository`+transaction-binding check otherwise unconditionally applied to every repository-scoped RPC.

## Impact Explanation
An RPC handler invoked through this branch ultimately still calls `locator.GetRepoPath`/`ObjectDirectoryPath`, which only prevents path traversal *outside the storage root* — it does not enforce that the resolved relative path is the repository the caller is authorized for. Because `restoreSnapshotRelativePath` blindly substitutes the metadata-supplied relative path, a caller able to set both the quarantine fields and the metadata header can direct an accessor RPC (e.g. reading blobs, commits, refs) at an arbitrary repository or snapshot path within the same storage, aside from the repository named in the RPC request itself. This is a cross-repository object access / authorization bypass of the same class as the reported "unaliased" message spoofing — the mechanism meant to keep every RPC's data access scoped is circumvented via a secondary, less-audited path.

## Likelihood Explanation
The proto fields (`GitObjectDirectory`, `GitAlternateObjectDirectories`) and the metadata key `relative-path-bin` are all part of the ordinary, documented request/metadata surface used by GitLab Rails during push access checks (see `doc/object_quarantine.md`), so any gRPC caller capable of reaching Gitaly's public RPC surface with a crafted request/metadata combination can exercise this branch without any special privilege beyond what's needed to call the RPC at all. No malicious peer, MITM, or leaked-token scenario is required — it's a crafted-RPC-field condition on an ordinary accessor call.

## Recommendation
Do not trust `relative-path-bin` (or the presence of quarantine fields) as a sufficient signal to skip transaction/partition validation. At minimum:
- Validate the metadata-derived `snapshotRelativePath` against the same `storage.ValidateRelativePath`/`ValidateRepository` checks used on the main path before substituting it into the request.
- Verify that the substituted relative path is consistent with an actual in-flight transaction/snapshot associated with the current gRPC context (e.g., cross-check with `MetadataKeySnapshotRelativePath` only when the request originates from a verified internal Rails round-trip context), rather than trusting client-supplied `GitObjectDirectory`/`GitAlternateObjectDirectories` fields as a proxy for that trust.

## Proof of Concept
1. As an authenticated Gitaly client, pick a repository A you have legitimate access to and a private repository B you do not.
2. Call any accessor RPC (e.g., `CommitService.FindCommit`) with `Repository.StorageName/RelativePath` pointing at A, but additionally set `Repository.GitObjectDirectory` to any non-empty placeholder string (e.g., `"objects"`).
3. Attach gRPC metadata `relative-path-bin` set to the relative path of repository B.
4. Because `GetGitObjectDirectory() != ""`, `beginTransactionForRepository` at [2](#0-1)  skips `ValidateRepository`/transaction binding and calls `restoreSnapshotRelativePath`, which sets `targetRepo.RelativePath = B` unconditionally per [3](#0-2) .
5. The RPC handler then resolves and returns data from repository B, even though the caller's access rights were only ever checked (by Rails/Workhorse, if at all) against repository A.

func restoreSnapshotRelativePath(ctx context.Context, methodInfo protoregistry.MethodInfo, req proto.Message) (proto.Message, error) {
	// Rails sends RPCs from its access checks with quarantine applied. The quarantine paths are relative to the
	// snapshot repository of the original transaction. While the relative path of the request is the original relative
	// path of the repository before snapshotting, Rails sends the snapshot repository's path in a header. For the
	// quarantine paths to apply correctly, we must thus rewrite the request to point to the snapshot repository here.
	snapshotRelativePath := metadata.GetValue(ctx, MetadataKeySnapshotRelativePath)
	if snapshotRelativePath == "" {
		return nil, ErrQuarantineWithoutSnapshotRelativePath
	}

	rewrittenReq, targetRepo, err := rewritableRequest(methodInfo, req)
	if err != nil {
		return nil, fmt.Errorf("rewritable request: %w", err)
	}

	targetRepo.RelativePath = snapshotRelativePath

	return rewrittenReq, nil
}
