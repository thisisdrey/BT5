### Title
Same-block AddKey→DeleteKey→AddKey resets an access-key nonce to a value below one already consumed, enabling transaction replay - (File: runtime/runtime/src/access_keys.rs / runtime/runtime/src/verifier.rs)

### Summary
`initial_nonce_value` seeds a (re-)created access key's nonce purely from `block_height - 1` [1](#0-0) , without regard to any nonce value already consumed by a same-named key earlier in the *same* block. Combined with `verify_nonce`'s `Monotonic` check (`tx_nonce > current_nonce`) and its upper-bound check (`tx_nonce < block_height * ACCESS_KEY_NONCE_RANGE_MULTIPLIER`) [2](#0-1) , an attacker can delete and immediately re-add the same public key within the same chunk that consumed a high nonce, resetting the stored nonce back down to `(H-1)*MULTIPLIER`, which is below the nonce of a transaction already executed in that same chunk. That previously-executed transaction can then be resubmitted and re-executed.

### Finding Description
`add_regular_key` sets `access_key.nonce = initial_nonce_value(block_height)` on every `AddKey` action, where `initial_nonce_value(h) = (h - 1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` [3](#0-2) . This seed depends only on the current block height, not on any previous nonce state for that public key.

`verify_nonce` enforces two independent checks: a `Monotonic` mode requiring `tx_nonce > current_nonce`, and (when `block_height` is supplied) an upper bound requiring `tx_nonce < block_height * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` [4](#0-3) . Both checks are evaluated only against the *currently stored* `access_key.nonce`, which is fully overwritten by every `AddKey`.

Attack sequence, all included in a single chunk at height `H` (attacker-controlled account, no privileged access needed):
1. `AddKey(pub_k)` signed by the account's existing full-access key — creates `pub_k` with nonce seeded to `(H-1)*MULT`.
2. `FunctionCall`/`Transfer` signed with `pub_k`, using `tx_nonce = V` where `(H-1)*MULT < V < H*MULT` — passes both `verify_nonce` checks and executes (e.g., moves funds), updating `pub_k`'s stored nonce to `V`.
3. `DeleteKey(pub_k)` — removes the access key.
4. `AddKey(pub_k)` again — re-creates the key with `nonce = initial_nonce_value(H) = (H-1)*MULT`, which is **still the current block height H**, so it reproduces the *same* seed as step 1, i.e. strictly less than `V`.

At this point the previously-executed `SignedTransaction` from step 2 (with `tx_nonce = V`, same signature, same `block_hash`) can be resubmitted. `verify_nonce`'s Monotonic check (`V > (H-1)*MULT`) passes, and the upper-bound check (`V < H'*MULT` for the block height `H'` at re-execution, where `H' >= H`) also passes since `V < H*MULT <= H'*MULT`. The transaction and its receipt are therefore accepted and executed a second time.

This works only if steps 1–4 occur within a single block/chunk height `H`: if the `DeleteKey`/`AddKey` re-seed happens at any block height `H2 > H`, the new seed becomes `>= H*MULT`, which already exceeds any valid `V < H*MULT`, closing the window. The narrow, single-chunk timing requirement is achievable by an ordinary account since all four actions are causally dependent standard actions signed with the attacker's own keys, submitted to a public RPC/mempool without needing malicious chunk-production behavior — an honest chunk producer applies whatever pending transactions it selects for a chunk strictly in sequence within one `apply()` call, so `AddKey → high-nonce tx → DeleteKey → AddKey` naturally execute against progressively updated state within that same chunk if selected together.

Existing protections do not stop this: the in-chunk exact-duplicate-hash filter (`UniqueChunkTransactions`) only rejects the identical hash appearing twice **within the same chunk** [5](#0-4) ; the replayed copy is submitted in a *later* chunk, so it is not caught by that mechanism. The `transaction_validity_period`/`block_hash` binding [6](#0-5)  only bounds *how long* the replay window stays open, not whether it exists — the replay is possible any time within that period after the reseed.

### Impact Explanation
Scoped impact: replay of an already-executed signed transaction, breaking the "no double execution of a transaction" invariant. If the replayed transaction moves funds (e.g. `Transfer`/`FunctionCall` with a deposit), the receipt executes a second time, resulting in double-spend / loss of funds for the receiver's counterparty or unintended duplicate state effects — this matches NEAR's "double-spend/replay" and "theft or loss of funds" bounty category.

### Likelihood Explanation
Preconditions: attacker only needs to control a funded account and a key pair for `pub_k`, and pay for 4 ordinary actions' fees; no validator/producer privilege required. The main constraint is timing: all four transactions (`AddKey`, high-nonce tx, `DeleteKey`, `AddKey`) must be included by the (honest) chunk producer within the same chunk/block height, which is plausible under normal mempool inclusion behavior for a lightly loaded shard but not guaranteed — an attacker cannot force ordering across the mempool with certainty, only submit rapidly and rely on typical FIFO/greedy chunk-filling behavior. This makes the attack feasible but timing-sensitive and potentially requiring several attempts to land the sequence in a single chunk.

### Recommendation
Do not let `initial_nonce_value` regress a key's nonce baseline below any nonce previously used by an identically-named public key within the same block-height window. Options: (a) track the highest nonce ever used by any historical key sharing this `(account_id, public_key)` pair (not just the currently live key) and seed new keys strictly above it; or (b) make the seed monotonic across `AddKey` events for a given `(account_id, public_key)`, e.g. by persisting a per-account "last seen block height for this pubkey" watermark that is never allowed to decrease, or by disallowing re-adding a `public_key` that was deleted within the same block height's nonce window until the next block.

### Proof of Concept
Runtime integration test plan (extending `runtime/runtime/tests` or `integration-tests/src/tests/features/access_key_nonce_for_implicit_accounts.rs` style tests):
1. Set up an account with a full-access key `A` and enough balance.
2. In one chunk/block at height `H`, submit, in order: `AddKey(pub_k, FullAccess)` signed by `A`; a `Transfer`/`FunctionCall` transaction `T2` signed by `pub_k` with `tx_nonce = H*MULT - 1` moving funds to a receiver; `DeleteKey(pub_k)` signed by `A`; `AddKey(pub_k, FullAccess)` again signed by `A`. Use `runtime.apply(... , SignedValidPeriodTransactions::new(vec![tx1,t2,tx3,tx4], ...))` to force single-chunk execution and inspect resulting state (confirm receiver balance increased once, and `pub_k`'s stored nonce equals `(H-1)*MULT`).
3. Resubmit `T2` verbatim (same bytes/hash) in a subsequent chunk at height `H+1` (or later, within `transaction_validity_period`).
4. Assert `process_tx`/`verify_and_charge_tx_ephemeral` accepts `T2` (`ProcessTxResponse::ValidTx`, no `InvalidNonce` error) and that after block production the receiver's balance increased a second time — proving double execution of the same signed transaction.

pub(crate) fn initial_nonce_value(block_height: BlockHeight) -> Nonce {
    // Set default nonce for newly created access key to avoid transaction hash collision.
    // See <https://github.com/near/nearcore/issues/3779>.
    (block_height - 1) * near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER
}

fn verify_nonce(
    tx_nonce: Nonce,
    current_nonce: Nonce,
    block_height: Option<BlockHeight>,
    nonce_mode: NonceMode,
) -> Result<(), InvalidTxError> {
    match nonce_mode {
        NonceMode::Monotonic => {
            if tx_nonce <= current_nonce {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
        NonceMode::Strict => {
            if !current_nonce.checked_add(1).is_some_and(|expected| tx_nonce == expected) {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
    }
    if let Some(height) = block_height {
        let upper_bound = height
            .saturating_mul(near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER);
        if tx_nonce >= upper_bound {
            return Err(InvalidTxError::NonceTooLarge { tx_nonce, upper_bound });
        }
    }
    Ok(())
