### Title
Reward withdrawal/query can block the transaction-processing thread on `RewardViCalService`'s completion latch during the reward-algorithm migration window - ([File: chainbase/src/main/java/org/tron/core/service/RewardViCalService.java])

### Summary
`RewardViCalService` performs a one-time, asynchronous background migration that computes historical "vote-interest" (VI) values for every witness/cycle before the new reward algorithm is activated. Until this background job finishes (`isDone()` becomes true), any code path that needs the migrated data blocks on a `CountDownLatch` via `lock.await()`. This getter is reachable from ordinary reward computation (`MortgageService.getOldReward` → `computeReward` → `withdrawReward`/`queryReward`), which in turn is invoked while executing a normal, unprivileged `WithdrawBalanceContract` transaction (or any other flow that calls into `MortgageService.withdrawReward`/`queryReward`). If such a transaction is included in a block before the migration completes, the actuator thread that applies the block stalls until the migration finishes, analogous to the Notional issue where a value expected to be finalized by an asynchronous process (global settlement / here, the VI migration) is read too early, producing unexpected/blocking behavior for any caller who triggers it.

### Finding Description
`RewardViCalService.getNewRewardAlgorithmReward` is the method that supplies the pre-hardfork ("old algorithm") reward contribution when a vote's `beginCycle` predates `newRewardCalStartCycle`: [1](#0-0) 

If the background one-time computation (`startRewardCal()` triggered from `maybeRun()`) has not finished, `isDone()` is false and the calling thread blocks on `lock.await()` with no timeout: [2](#0-1) 

This method is invoked synchronously from `MortgageService.getOldReward`, which is only guarded by the `allowOldRewardOpt()` dynamic parameter (a chain-wide feature flag, not a per-call permission check): [3](#0-2) 

`getOldReward` is called from `computeReward(beginCycle, endCycle, accountCapsule)` whenever any part of the requested cycle range predates `newRewardCalStartCycle`: [4](#0-3) 

`computeReward` is reached from `withdrawReward(address)` and `queryReward(address)`, both public entry points of `MortgageService` used by actuators (e.g. balance withdrawal) and by the wallet/API reward-query path: [5](#0-4) [6](#0-5) 

Because `withdrawReward` is invoked from actuator execution when a normal account claims their voting reward (an ordinary, unprivileged transaction any account can broadcast), and actuator execution happens on the single-threaded block-application path in `Manager`, a transaction that lands on a node before `RewardViCalService`'s background migration is `isDone()` will make that node's transaction-processing thread block indefinitely (bounded only by how long the migration over all historical cycles/witnesses takes). If this occurs consistently across nodes during the same window (e.g. right after the `allowOldRewardOpt` hard fork activates on all nodes near-simultaneously), block processing across the network can stall, mirroring the disclosed pattern where a value that depends on an asynchronous "settlement" step is read too early and produces unexpected behavior for any caller relying on it.

### Impact Explanation
A blocked block-application thread during the migration window means the node cannot make progress on subsequent transactions/blocks until the background `RewardViCalService.startRewardCal()` finishes. Because this condition is triggered by an ordinary, permissionless `WithdrawBalanceContract` transaction (or any reward query hitting the pre-migration path) landing in a block, and the same condition is very likely to be met on every node simultaneously right after the relevant hard fork proposal takes effect, this can manifest as a synchronized node stall/halt across the network rather than an isolated node issue — a concrete "node halt" impact.

### Likelihood Explanation
The condition requires: (1) `allowOldRewardOpt` enabled (a governance-controlled but eventually-activated parameter) and (2) at least one transaction reaching `computeReward` for cycles predating `newRewardCalStartCycle` while `RewardViCalService.isDone()` is still false. Since witnesses/voters routinely withdraw rewards, and the migration necessarily takes non-zero wall-clock time to walk all historical cycles for all witnesses, hitting this window is highly likely immediately after the feature activates, without requiring any malicious actor — any voter's normal withdrawal transaction is sufficient to trigger it.

### Recommendation
- Do not perform blocking waits (`lock.await()` with no timeout) inside a code path reachable from transaction/block execution. Instead, either (a) ensure the migration is guaranteed complete before the flag that enables `getOldReward`'s old-algorithm branch is activated (synchronous barrier at hard-fork activation time rather than lazy background computation), or (b) make reward computation degrerate gracefully (e.g., defer/reject the specific transaction, or serve from a lower-fidelity fallback) instead of blocking the actuator thread indefinitely.
- Add a bounded timeout to the `lock.await()` and handle the timeout case explicitly (e.g., revert/fail the specific transaction) rather than allowing indefinite block application delay.
- Document and test the exact behavior for transactions that touch reward computation during the migration window, verifying that no single transaction can stall block production for other, unrelated transactions.

### Proof of Concept
1. Configure a node/chain with `allowOldRewardOpt` about to become active but with `RewardViCalService.isDone()` still false (background migration in progress right after activation, before `startRewardCal()`/`clearUp(true)` completes — this can take a long time on a chain with many historical cycles/witnesses).
2. Have any account with existing votes broadcast a normal `WithdrawBalanceContract` transaction (or otherwise trigger `MortgageService.queryReward`/`withdrawReward`) whose vote `beginCycle` predates `newRewardCalStartCycle`.
3. When this transaction is applied during block processing, `computeReward` → `getOldReward` → `RewardViCalService.getNewRewardAlgorithmReward` is invoked; since `isDone()` is false, the thread blocks on `lock.await()`.
4. Observe that the node's transaction/block-application thread does not proceed until the background migration completes, stalling processing of the block (and, if replicated across nodes near-simultaneously after activation, the network).

    long reward = 0;

        return;
      }

    if (beginCycle + 1 == endCycle && beginCycle < currentCycle) {
      AccountCapsule account = delegationStore.getAccountVote(beginCycle, address);

        reward = computeReward(beginCycle, endCycle, account);
        adjustAllowance(address, reward);
        reward = 0;

      beginCycle += 1;
    }

  private long getOldReward(long begin, long end, List<Pair<byte[], Long>> votes) {
    if (dynamicPropertiesStore.allowOldRewardOpt()) {
      return rewardViCalService.getNewRewardAlgorithmReward(begin, end, votes);
    }
    long reward = 0;
    for (long cycle = begin; cycle < end; cycle++) {
      reward += computeReward(cycle, votes);
    }
    return reward;
  }
