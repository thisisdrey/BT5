### Title
Fee bypass on Nep245/Imt `TokenDiff` swaps via splitting into unit-sized (`amount == 1`) intents - (`contracts/defuse/core/src/intents/token_diff.rs`)

### Summary
`TokenDiff::token_fee` is applied per individual `TokenDiff` intent using only that intent's own per-token delta magnitude, and returns `Pips::ZERO` for `Nep245`/`Imt` tokens whenever `amount <= 1`. Because fee exemption is decided locally per intent rather than on the aggregate amount actually settled across the batch, an attacker can split what would be a single fee-liable diff of `amount > 1` into many `amount == 1` diffs (matched pairwise by counter-diffs from a second attacker-controlled account) so that every individual `token_fee` call returns zero while the `TransferMatcher` still nets and settles the full aggregate amount.

### Finding Description
The binding that should hold is:
`total_fee_owed = Pips::fee_ceil(sum_over_batch(|negative_delta| for token X), protocol_fee)` must equal `total_fee_actually_collected(token X)`.

In `execute_intent` [1](#0-0) , for each `(token_id, delta)` pair inside a *single* `TokenDiff`, the fee is computed as:
```
let amount = delta.unsigned_abs();
let fee = Self::token_fee(token_id, amount, protocol_fee).fee_ceil(amount);
```
and `Self::token_fee` [2](#0-1)  explicitly special-cases `Nep245`/`Imt` tokens: `if amount > 1 {}` else `return Pips::ZERO`, per the inline note "do not take fees on NFTs and MTs with |delta| <= 1".

This decision is made purely from the `amount` present in that one intent's diff, not from any aggregate over the `MultiPayload`/transaction. Meanwhile, actual balance movement is tracked separately in `TransferMatcher` (via `internal_add_balance`/`internal_sub_balance` recording `deposits`/`withdrawals` per token in `Deltas<S>` [3](#0-2) ), and `finalize()` only checks that total deposits and withdrawals net to zero per token across the whole batch [4](#0-3) . Nothing in `finalize`/`TransferMatcher` recomputes or validates that the correct aggregate fee was collected for the total notional matched.

Exploit flow: attacker controls two accounts A and B. Instead of A signing one `TokenDiff{ MT_token: -100, FT_token: +Q }` and B signing the mirror `{ MT_token: +100, FT_token: -Q }` (which would each call `token_fee(MT_token, 100, fee)` → nonzero fee, since `amount > 1`), the attacker structures the trade as 100 separate `TokenDiff` intents per account, each `{ MT_token: -1, FT_token: +q }` / `{ MT_token: +1, FT_token: -q }`, packed into the same `MultiPayload`(s) submitted together via `execute_intents`/`simulate_intents`. Each of the 200 intents individually calls `token_fee(MT_token, 1, fee)`, which returns `Pips::ZERO`, so `fee_ceil(1) == 0` every time. The `TransferMatcher` still nets the 100 unit withdrawals against the 100 unit deposits and finalizes a single aggregate transfer of 100 MT units, exactly as if it were one big trade — but `fees_collected` accumulated across the whole execution is 0 instead of `fee_ceil(100)`.

None of the existing guards prevent this: `MultiPayload::verify`, nonce checks, and `TransferMatcher::finalize`'s zero-sum-per-token check are all satisfied by construction (the split diffs still net to zero/match correctly); none of them re-derives or enforces the fee that should have been owed on the true aggregate notional.

### Impact Explanation
Protocol fees are structurally bypassed for any `Nep245` (multi-token) or `Imt` token swap of arbitrary size, by chunking it into `amount == 1` legs. This is a direct "protocol fees bypassed" condition, matching the Critical impact category (fees are value that would otherwise accrue to the `fee_collector`; here it never gets collected while the full notional still settles). It is fully repeatable across any Nep245/Imt token, any amount, and any pair of attacker-controlled accounts (or with a willing/complicit counterparty), at the cost of extra signed intents/transaction gas only — no privileged role, key compromise, or third-party cooperation is required.

### Likelihood Explanation
The attacker only needs to control (or sign) two accounts and hold the tokens to trade — ordinary unprivileged capability (`execute_intents`/`simulate_intents` with a self-crafted `MultiPayload`). No role, relayer key, or victim signature is needed. The only cost is packaging N intents instead of 1 (extra payload/signature/gas overhead), which is cheap relative to the fee saved on any nontrivial-value MT/IMT trade. This is straightforwardly reproducible and repeatable indefinitely.

### Recommendation
Compute and enforce the NFT/MT/IMT fee-exemption threshold on the aggregate amount actually settled for a given `TokenId` across the whole execution (e.g., accumulate per-token negative-delta totals across all `TokenDiff` intents in the engine/`TransferMatcher` before deciding fee exemption), rather than evaluating `amount > 1` independently per intent. Alternatively, remove the per-intent-amount fee exemption for `Nep245`/`Imt` entirely and rely on total-supply/aggregate-based fee logic that cannot be defeated by intent decomposition.

### Proof of Concept
`cargo test` (near-workspaces sandbox) plan for `contracts/defuse` / `tests/src/tests/defuse/intents/token_diff.rs`:
1. Set up `Env` with `fee = Pips::ONE_PERCENT` (nonzero) and deploy an MT (`Nep245`) contract; create two attacker-controlled accounts A and B; deposit A with 100 units of MT token `X` and B with sufficient FT `Y` balance.
2. Baseline: have A sign one `TokenDiff{ X: -100, Y: +closure }` and B sign the mirrored closure `TokenDiff{ X: +100, Y: -closure }`; execute via `simulate_intents`/`execute_intents`; assert `fee_collector` balance for `X` (or `Y`) equals `Pips::ONE_PERCENT.fee_ceil(100)` (nonzero) — binding holds: `total_fee_owed == total_fee_collected`.
3. Exploit: reset balances; have A sign 100 separate `TokenDiff{ X: -1, Y: +closure_i }` intents and B sign 100 matching `TokenDiff{ X: +1, Y: -closure_i }` intents (all within the same batch of `MultiPayload`s passed to one `execute_intents` call).
4. Assert: (a) A's MT balance decreased by 100 and B's increased by 100 (i.e., the full aggregate amount settled via `TransferMatcher::finalize`), and (b) `fee_collector`'s balance for token `X`/`Y` remains `0`, demonstrating `total_fee_owed(100, ONE_PERCENT) > 0 == total_fee_actually_collected`, breaking the binding while the batch itself finalizes without `InvariantViolated`.

    // Finalizes all transfers, or returns unmatched deltas.
    // If unmatched deltas overflow, then Err(None) is returned.
    pub fn finalize(self) -> Result<Transfers, InvariantViolated> {
        let mut transfers = Transfers::default();
        let mut deltas = TokenDeltas::default();
        for (token_id, transfer_matcher) in self.0 {
            if let Err(unmatched) = transfer_matcher.finalize_into(&token_id, &mut transfers)
                && (unmatched == 0 || deltas.apply_delta(token_id, unmatched).is_none())
            {
                return Err(InvariantViolated::Overflow);
            }
        }
        if !deltas.is_empty() {
            return Err(InvariantViolated::UnmatchedDeltas {
                unmatched_deltas: deltas,
            });
        }
        Ok(transfers)
    }
