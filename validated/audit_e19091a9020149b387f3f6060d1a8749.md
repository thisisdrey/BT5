### Title
Unauthenticated `RecvError` packets allow any remote attacker to force-close established tunnels — (File: `outside.go`)

### Summary
Nebula's inbound UDP packet handler treats `header.Handshake` and `header.RecvError` packet types as **unencrypted** control packets that are processed before any Noise-protocol decryption or certificate/authentication check is performed. Similar to the reported `fallback()` issue in Nexus — where an unrestricted external entry point let an attacker reach privileged account logic without going through the authenticated entrypoint/userOp path — Nebula's `header.RecvError` handler (`handleRecvError` in `outside.go`) is reachable directly by any UDP sender with no valid Nebula certificate, no completed Noise handshake, and no AEAD-authenticated payload, yet it can tear down a live, fully-authenticated tunnel between two legitimate peers.

### Finding Description
`readOutsidePackets` (in `outside.go`) parses the header and, before any peer/host lookup or decryption, branches on the packet type: [1](#0-0) 

For `header.RecvError`, `f.handleRecvError(via.UdpAddr, h)` is invoked with only the raw header fields — `h.RemoteIndex` — taken straight from the unauthenticated, unencrypted wire packet. All other packet types (`Message`, `LightHouse`, `Test`, `Control`, `CloseTunnel`) are only reached *after* a successful `hostinfo.ConnectionState.Decrypt` call, which requires possession of the session's derived AEAD key established through the mutually-authenticated Noise handshake (itself gated on certificate validation against the CA pool). `RecvError`, however, bypasses this entirely: [2](#0-1) 

`handleRecvError` performs two checks only: a per-endpoint rate/allow check (`f.acceptRecvErrorConfig.ShouldRecvError(addr)`) and, after finding the `HostInfo` by `h.RemoteIndex` via `f.hostMap.QueryReverseIndex`, a comparison that the *currently recorded remote UDP address* for that tunnel matches the address the packet arrived from: [3](#0-2) 

Neither check involves any cryptographic proof of identity, a valid certificate, or an AEAD-authenticated payload — it is purely a 32-bit `RemoteIndex` value copied out of the packet header and a comparison of the *source IP:port*, which is trivially spoofable over UDP by anyone who can inject packets to the target's listening interface (e.g., anyone with network path access, no CA-issued Nebula certificate required). If an attacker can observe (e.g., on-path) or otherwise obtain a peer's `RemoteIndex` and a plausible source address, they can trigger `f.closeTunnel(hostinfo)` and `f.handshakeManager.DeleteHostInfo(hostinfo)`, forcibly terminating an active, authenticated Nebula tunnel between two legitimate nodes.

This mirrors the reported bug class precisely: an externally-callable code path (`fallback()` in the Solidity report; `RecvError` handling here) exists that is intended only to be reached as a side effect of an already-authorized flow (a call routed via the entrypoint/userOp; a signal from an already-authenticated peer that itself received a malformed encrypted packet), but is in fact reachable directly and unrestricted by any outside caller with no signature/certificate validation, letting the attacker manipulate protected state (an active secure tunnel) that they should have no authority over.

### Impact Explanation
An attacker with only network reachability to a Nebula node's UDP listening port — no valid Nebula certificate, no CA trust, no completed handshake — can spoof a `RecvError` packet to sever active, encrypted tunnels between two legitimate, mutually-authenticated peers. This is a remote state-poisoning / denial-of-service primitive against the overlay network: it can disrupt lighthouse-to-node and node-to-node connectivity, force repeated re-handshakes, and be used to selectively partition or destabilize the mesh. It does not by itself grant decryption or forgery of traffic, but it undermines the availability and stability guarantees of the tunnel and can be leveraged as a building block for further attacks (e.g., inducing races during reconnection).

### Likelihood Explanation
Exploitability depends on the attacker's ability to guess or learn the target's current `RemoteIndex` and spoof (or send from) a UDP source matching `hostinfo.GetRemote()`. `RemoteIndex` is a 32-bit locally-assigned tunnel index; I was not able to fully verify within the available context how unpredictable/large the index space is or whether it is exposed anywhere in traffic that an off-path attacker could observe, so likelihood for a purely off-path/blind attacker is uncertain and would need further verification of `hostmap.go`'s index-generation logic. For an on-path or co-located attacker (e.g., sharing a network segment, NAT, or otherwise able to observe/spoof UDP source and infer the index), likelihood is high, since no cryptographic material is required at all — this is the same "unauthenticated alternate path" pattern flagged as Medium severity in the analog report.

### Recommendation
Do not act on unauthenticated `RecvError` packets. Options:
- Require `RecvError` handling to only take effect if it can be tied to a recent, legitimate transmission from this node to the sender (e.g., track outstanding un-acked message counters/indices per remote and only accept a `RecvError` that references one of them within a short window), rather than trusting any inbound packet whose `RemoteIndex` happens to match an existing `HostInfo`.
- Increase the entropy/unpredictability of `RemoteIndex` and avoid ever transmitting it in a way recoverable by non-peers, and/or rate-limit and log repeated `RecvError` events per source more aggressively than the current `ShouldRecvError` allowance.
- Consider requiring `RecvError` to be sent only in direct response to a packet this node just sent (matching counter/index correlation with a short-lived pending table) instead of solely matching `hostinfo.GetRemote() == addr`, which is a spoofable UDP source-address check.

### Proof of Concept
1. Establish a legitimate Nebula tunnel between node A and node B (both with valid CA-signed certs).
2. As an attacker with only network reachability to A (no cert, no handshake), craft a UDP packet with `header.Version` = current version, `header.Type` = `header.RecvError`, `header.Subtype` = 0, and `RemoteIndex` set to B's index value for the A↔B tunnel (obtained via observation, e.g., on-path sniffing of index-bearing traffic, or side channels — exact discoverability is not fully verified here).
3. Spoof the UDP source address to appear as B's known endpoint (`hostinfo.GetRemote()`).
4. Send the packet to A. `readOutsidePackets` routes it to `f.handleRecvError`, which passes the address check and calls `f.closeTunnel(hostinfo)`, tearing down the tunnel without any decryption or certificate validation having occurred. [4](#0-3) [5](#0-4) 

**Note on confidence**: I could not fully inspect `hostmap.go`'s `QueryReverseIndex`/index-assignment code or the exact `ShouldRecvError` rate-limiting semantics before running out of tool budget, so the precise attacker capability required (on-path vs. fully blind/off-path) to learn a valid `RemoteIndex` remains partially unverified and should be confirmed by a follow-up review of `hostmap.go` and `interface.go`'s `recvErrorConfig` definitions.

func (f *Interface) sendRecvError(endpoint netip.AddrPort, index uint32) {
	f.messageMetrics.Tx(header.RecvError, 0, 1)

	b := header.Encode(make([]byte, header.Len), header.Version, header.RecvError, 0, index, 0)
	_ = f.outside.WriteTo(b, endpoint)
	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error sent",
			"index", index,
			"udpAddr", endpoint,
		)
	}
}

func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}
