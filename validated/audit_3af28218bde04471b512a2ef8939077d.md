This confirms the input buffer is a precise `mmap` of the jar file (`length_ = length` from `lseek`, `mmap(NULL, length, PROT_READ, MAP_PRIVATE, fd, 0)`), with no guard page mapped after it, in `third_party/ijar/mapped_file_unix.cc` [1](#0-0) . So any read past `buffer_ + length_` is a genuine out-of-bounds read of unmapped memory (SIGSEGV) or adjacent heap/mapping data, not just "logically wrong but still in-buffer."

### Title
Out-of-bounds read scanning ZIP/JAR central-directory entries without bounds checking - (File: `third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry`, used by the `ijar` tool to strip non-ABI members from `.jar` files (interface-jar generation for `java_import`/precompiled jar dependencies), scans the ZIP central directory by trusting attacker-controlled 16-bit length fields (`file_name_length`, `extra_field_length`, `file_comment_length`) with **no bounds checking at all**, unlike its sibling `ProcessLocalFileEntry`, which calls `EnsureRemaining()` before every field read [2](#0-1) .

### Finding Description
`ProcessCentralDirEntry` reads size fields and then advances the cursor `p` purely based on attacker-supplied lengths, with an inner "extra fields" loop that terminates only when `extra_p == p`: [3](#0-2) 

Unlike `ProcessLocalFileEntry`, which explicitly checks `EnsureRemaining(file_name_length_, "file_name")` and similar before every advance [4](#0-3) , `ProcessCentralDirEntry` never calls `EnsureRemaining` and never checks `p` against the end of the mapped file. It:
1. Reads `compressed size`/`uncompressed size`/`file_name_length`/`extra_field_length`/`file_comment_length`/`attr`/`offset` unconditionally.
2. `memcpy`s `file_name_length` bytes into a fixed `filename` buffer directly from `p`, and advances `p += file_name_length` — if this pointer arithmetic reads past `zipdata_in_ + length_`, it is an out-of-bounds read from the `mmap`'d region.
3. Scans "extra fields" with `while (extra_p != p) { ...; extra_p += data_size; }`. If `data_size` values don't sum exactly to `extra_field_length`, `extra_p` can overshoot `p`, and the loop never terminates on equality — it continues reading `header_id`/`data_size` from arbitrary attacker-controlled offsets indefinitely until it walks off the mapped page and faults, or (if `p` is smaller than expected) silently misreads memory.
4. This CDH-sized/length-driven cursor advance repeats in the caller `ProcessNext`/`CalculateOutputLength` loop for every declared central-directory entry, so a single malformed entry can push subsequent parsing arbitrarily far beyond the actual file bounds.

The `FindZipCentralDirectory` function does validate that the *aggregate* `central_dir_offset + central_dir_size <= in_length` [5](#0-4) , but this only bounds where the whole central directory begins/ends in the file; it does nothing to prevent a single crafted entry's oversized length fields from making the per-entry cursor `p` exceed the buffer boundary before the loop naturally stops, since the loop only stops based on signature mismatch at wherever `p` currently points — which itself is an OOB read if `p` is already past the mapped region.

This exactly parallels the ocfs2 bug class: a structured buffer of variable-length attacker-controlled entries is scanned entry-by-entry using length fields taken from the entries themselves, with no check that the cursor remains inside the valid memory region.

### Impact Explanation
Because the input is `mmap`'d read-only with no trailing guard mapping guaranteed beyond the file's actual pages, an out-of-bounds read here can:
- Crash the Bazel build worker via SIGSEGV/SIGBUS (denial of service for the build), or
- Read adjacent heap/mapped memory contents that get copied into `filename`/`errmsg` buffers or influence subsequent decisions (potential information disclosure of adjacent process memory, e.g. into error messages or size calculations that affect the output jar).

This runs as a normal build action (`ijar`) whenever Bazel needs to construct an interface jar from any `.jar`-typed dependency (e.g., `java_import` pointing at a jar fetched via `http_file`/`http_jar`, or Maven-resolved artifacts). If the initial fetch of that jar is unpinned (no `sha256`/`integrity` recorded yet, so Bazel just downloads and records whatever bytes a hostile server returns), the attacker fully controls the byte layout consumed by this parser.

### Likelihood Explanation
Requires the jar to actually be malformed in a way that overshoots `extra_field_length`/`file_name_length`. This is a purely mechanical crafting task for an attacker publishing a `.jar` at a URL/registry the victim's build fetches unpinned — no cryptographic bypass needed, since ordinary content, not integrity-protected content, is being exploited.

### Recommendation
Add explicit bounds checks in `ProcessCentralDirEntry` mirroring `EnsureRemaining()` in `ProcessLocalFileEntry`: verify `p + 46 (fixed CDH size)`, then `p + file_name_length`, `p + extra_field_length`, `p + file_comment_length` never exceed `zipdata_in_ + input_file_->Length()` before each `memcpy`/pointer advance, and bound the inner extra-field loop by an explicit `extra_p < p` invariant (not `!=`) plus a check that each `header_id`/`data_size` read has at least 4 bytes remaining before `extra_p`.

### Proof of Concept
A `BuildIntegrationTestCase`/shell test analogous to the existing `output_jar_simple_test.cc`'s `CreateZipWithMalformedExtraField()` helper [6](#0-5)  (which already demonstrates the malformed-extra-field pattern for `singlejar`'s CDH/LH parsing, but note `singlejar`'s own `ExtraField::find` *does* bounds-check per-field — see `zip_headers.h` lines 99-115) would be adapted for `third_party/ijar/zip.cc`: build a minimal ZIP with one CDH entry whose `extra_field_length` is set to a large value (e.g., `0xFFFF`) while only a few real bytes follow before EOF, then invoke the `ijar` binary (or `InputZipFile::ProcessCentralDirEntry` directly in a unit test under `third_party/ijar/`) on this file and observe the OOB read/crash when `p`/`extra_p` walk past the mmap'd region.
