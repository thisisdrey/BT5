Audit Report

## Title
`snowbridge-pallet-outbound-queue-v2::process_delivery_receipt` pays relayer reward and permanently settles `PendingOrder` without checking the delivery receipt's `success` field - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

## Summary
`process_delivery_receipt` unconditionally pays `order.fee` to the relayer/reward account and removes the `PendingOrder` for any nonce with a valid, verified delivery receipt, without ever inspecting the `receipt.success` flag decoded from the real Ethereum `InboundMessageDispatched` event. This allows a relayer to claim the full reward and permanently extinguish the pending-order accounting state even when the corresponding message execution on the Ethereum Gateway failed (`success: false`).

## Finding Description
`submit_delivery_receipt` verifies the Merkle/event proof via `T::Verifier::verify`, decodes the event log into a `DeliveryReceipt` via `DeliveryReceipt::try_from`, and calls `Self::process_delivery_receipt(relayer, receipt)`: [1](#0-0) 

The `DeliveryReceipt` struct, decoded from the on-chain `InboundMessageDispatched(uint64 nonce, bytes32 topic, bool success, bytes32 reward_address)` Solidity event, explicitly carries a `success: bool` field reflecting whether the message actually executed successfully on the Ethereum Gateway: [2](#0-1) 

However, `process_delivery_receipt` only checks the gateway address and whether a matching `PendingOrder` exists for the nonce. It never reads `receipt.success`. It fetches the order, and if `order.fee > 0`, unconditionally calls `T::RewardPayment::register_reward(...)`, then unconditionally removes the order from `PendingOrders`, before depositing a generic `MessageDelivered` event: [3](#0-2) 

The only existing guard related to this path is the halted-verifier regression test `poc_m1`, which blocks reward payment when the bridge/verifier is halted — a distinct concern from an honestly-reported `success: false` receipt for a live, non-halted bridge: [4](#0-3) 

No code path anywhere in `submit_delivery_receipt` or `process_delivery_receipt` inspects or branches on `receipt.success`, so a legitimately verified receipt reporting failed execution is treated identically to a successful one.

## Impact Explanation
This is duplicate/incorrect settlement of relayer work: the `PendingOrder.fee` (the exact corrupted/misused value) is paid out via `T::RewardPayment::register_reward` and the `PendingOrder` accounting record is permanently deleted from `PendingOrders` regardless of whether the underlying message delivery actually succeeded on Ethereum. Because removal is irreversible and there is no distinct "failed delivery" path, genuine successful delivery of that message can never be rewarded or reconciled again, and the relayer/reward-account is paid for work that was not completed — a public underpriced/duplicate-payout condition on bridge processing, aligning with the "duplicate settlement or payout" and "public underpriced work" impact categories.

## Likelihood Explanation
High likelihood: `submit_delivery_receipt` is a public extrinsic requiring only `ensure_signed` (no privileged origin). An attacker/relayer needs only a legitimately verifiable Ethereum event log reporting `success: false` (obtainable by triggering or observing an organic failed message execution on the Gateway) and a valid Merkle/event proof — both achievable through normal permissionless bridge participation, with no forged data, compromised keys, or governance/validator assumptions required.

## Recommendation
In `process_delivery_receipt`, branch explicitly on `receipt.success`:
- If `true`, retain current behavior (pay reward, remove `PendingOrder`).
- If `false`, do not call `T::RewardPayment::register_reward`; either retain the `PendingOrder` for a defined retry/settlement policy or move it to a distinct failed-delivery path with its own event (e.g. `MessageDeliveryFailed`) and explicit refund/retry semantics, so unsuccessful execution can never trigger payout or unrecoverable removal of pending accounting state.

## Proof of Concept
1. A message is enqueued, creating `PendingOrders::<T>::insert(nonce, PendingOrder { nonce, fee, block_number })` with `fee > 0` in `do_process_message` (`lib.rs` lines 426-436).
2. The message is delivered to the Ethereum Gateway but execution reverts; the Gateway emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer submits this legitimate event log and its valid Merkle/event proof via `submit_delivery_receipt`.
4. `T::Verifier::verify` succeeds; `DeliveryReceipt::try_from` decodes `success: false`; `process_delivery_receipt` (lines 445-480) never checks `receipt.success`, pays `order.fee` via `T::RewardPayment::register_reward`, and calls `<PendingOrders<T>>::remove(nonce)`.
5. The relayer collects a reward for a message never successfully delivered, and the `PendingOrder` for that nonce can never be settled or retried again.

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
