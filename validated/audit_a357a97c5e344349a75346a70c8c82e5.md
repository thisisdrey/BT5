### Title
`AtlasConfig.attachments_max_size` is never enforced against peer-supplied attachment content — no runtime byte-length ceiling on incoming Atlas attachments - ([File: stackslib/src/net/atlas/mod.rs], [File: stackslib/src/net/atlas/download.rs])

### Summary
`AtlasConfig::validate()` checks `attachments_max_size` only once, at config-load time, against the `ATTACHMENTS_MAX_SIZE_MIN` floor. [1](#0-0)  Neither the wire-decoding of a `GetAttachmentResponse`, nor the code that stages resolved attachments, nor the code that persists them to `AtlasDB` ever reads `attachments_max_size` again, so a remote peer can return an attachment of arbitrary size in response to a legitimate `GetAttachment` request.

### Finding Description
`GetAttachmentResponse::deserialize` hex-decodes the peer-supplied `content` field directly into an `Attachment` with no length check at all. [2](#0-1)  In `AttachmentsBatchStateContext::extend_with_attachments`, the decoded response is unconditionally inserted into the in-memory `attachments` set once `decode_atlas_get_attachment()` succeeds, again with no size check. [3](#0-2)  Finally, in `AttachmentsDownloader::run`, every attachment collected from the batch is persisted via `atlasdb.insert_instantiated_attachment(&attachment)` regardless of size — and notably, this call happens unconditionally for each entry in `context.attachments`, even before/without checking whether the attachment's own hash matches any tracked `content_hash` for the outstanding request. [4](#0-3) 

`attachments_max_size` itself is referenced in exactly one runtime place outside of `validate()`/`tests.rs`/`config/mod.rs` — a single, unrelated hit in `db.rs` — and is not consulted in `decode_atlas_get_attachment`, `extend_with_attachments`, or `insert_instantiated_attachment`. The config-declared "max attachment size" is therefore purely a config-file input validation value, not an actually-enforced runtime ceiling on Atlas attachment gossip.

### Impact Explanation
Any peer that is asked for an attachment by this node's `AttachmentsDownloader` (a routine, unauthenticated interaction that happens whenever the node has BNS-driven attachment instances to resolve) can respond with an attachment body far larger than the configured `attachments_max_size` (e.g., 10MB vs. a configured 1MB cap). That oversized blob is stored to the local `AtlasDB` SQLite database with no cap, enabling unbounded disk/memory growth per response and, because `insert_instantiated_attachment` is called unconditionally for every entry in the resolved set, this can occur even for content whose hash does not correspond to any real, block-committed `AttachmentInstance`. This is a bounded-but-unenforced resource-consumption vector against any node that performs Atlas attachment sync, matching the "attachment/BNS mismatch" / unbounded-write category.

### Likelihood Explanation
No special privilege is required — the attacker only needs to be selected as one of the `outbound_sync_peers` that the requesting node queries for an attachment (a normal, unauthenticated P2P/HTTP interaction), and simply return an oversized `content` field in its `GetAttachmentResponse`. This is repeatable on every attachment-batch cycle and requires no secret, no StackerDB slot, and no admin role.

### Recommendation
Enforce `AtlasConfig.attachments_max_size` at the point where peer-supplied attachment bytes are first decoded — reject in `GetAttachmentResponse::deserialize` (or immediately after, in `decode_atlas_get_attachment`) any content whose length exceeds the configured max, and reject in `extend_with_attachments`/`insert_instantiated_attachment` before the blob is persisted. Additionally, verify the decoded attachment's `hash()` matches the expected `content_hash` of the corresponding `AttachmentRequest` before calling `insert_instantiated_attachment`, rather than storing every returned attachment unconditionally.

### Proof of Concept
Add a net test in `stackslib/src/net/atlas/tests.rs`:
1. Construct an `AtlasConfig` with `attachments_max_size = 1_048_576` (1MB).
2. Build a `StacksHttpResponse` whose body is a `GetAttachmentResponse` JSON payload with a hex-encoded `content` of 10MB.
3. Call `response.decode_atlas_get_attachment()` directly and assert it returns `Ok` (proving no length check at decode time).
4. Feed the same response through `AttachmentsBatchStateContext::extend_with_attachments` with a `BatchedRequestsResult` containing this response in `succeeded`, and assert the resulting `context.attachments` set contains the 10MB attachment (proving no length check at staging time).
5. Call `AtlasDB::insert_instantiated_attachment(&attachment)` directly with the 10MB `Attachment` and assert it succeeds without error (proving no length check at persistence time), confirming `attachments_max_size` is dead at runtime for all three call sites named in the question.
