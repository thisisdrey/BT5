### Title
Cross-chain / cross-fork replay of signed `MultiPayload` intents due to missing chain binding in `DefusePayload` - ([File: contracts/defuse/core/src/payload/mod.rs])

### Summary
`DefusePayload` (the envelope authorized by every `MultiPayload` signing standard: NEP-413, ERC-191, TIP-191, Raw Ed25519, WebAuthn, TonConnect, SEP-53) binds a signed intent only to a `verifying_contract` `AccountId`, `signer_id`, `deadline`, and `nonce`. It contains **no chain/network identifier**. `execute_signed_intent` in the engine checks `verifying_contract` and nonce/salt validity, but never checks that the payload was intended for the specific network the contract is running on. This is the exact bug class described in the reference report: a value that authorizes an action is not bound to the chain it is meant to be executed on, so it can be replayed on another chain/fork where the same `verifying_contract` account id and nonce/salt state exist.

### Finding Description
`DefusePayload<T>` is defined as: [1](#0-0) 

and is verified in `Engine::execute_signed_intent`: [2](#0-1) 

Only `verifying_contract`, `signer_id`/public key, `deadline`, and `nonce`/`salt` are checked — there is no check against a chain identifier or genesis hash. Compare this to the sibling `wallet` contract in the same repo, which deliberately includes and checks a `chain_id` field on its signed `OffchainMessage`/`RequestMessage`: [3](#0-2) [4](#0-3) 

The `defuse` intents core has no equivalent field. The nonce-replay protection relies on `is_valid_salt`/`commit_nonce`, which is per-contract on-chain state: [5](#0-4) 

If the NEAR chain this contract is deployed on ever forks (a scenario NEAR shares with any blockchain, and explicitly the scenario the original judge accepted as valid despite the team's "single network" dispute), both resulting chains inherit identical account IDs, identical nonce/salt state, and identical public keys at the fork block. A `MultiPayload` signed once by a user, intended to settle only on the canonical chain, remains a fully valid signature+payload on the forked chain as well, because `verifying_contract` (just an `AccountId` string) and nonce state match on both chains. An attacker (or simply the natural existence of two chains) can submit the identical signed `MultiPayload` to `execute_intents`/`execute_signed_intents` on both chains, causing the same authorization to settle twice — once per chain — which breaks the invariant that "the times one signed `MultiPayload` settles" should equal one (globally, per signature).

### Impact Explanation
This crosses the "one signed payload settling more than once" boundary explicitly listed as Critical impact. A signed withdrawal/transfer/token_diff intent that a user only intended to authorize once could be executed twice across two forks of the chain hosting the `defuse` contract, effectively duplicating a debit-authorization (e.g., a bridge withdraw intent settling on both forks, draining wrapped-asset backing on one side without a corresponding, freshly-authorized action). This mirrors the accepted analog in the reference report, where the judge overruled the "single network" dispute by noting that chains can and do fork, and that scope can expand to multiple deployments.

### Likelihood Explanation
Likelihood is low under current, single-canonical-chain deployment assumptions (mirroring the original disputed/low-severity nature of the referenced finding), but non-zero and structurally present: the vulnerability requires no attacker skill beyond replaying an already-signed, existing `MultiPayload` on a second deployment/fork that shares the same account-id namespace and nonce/salt state — exactly the mechanism called out by the judge as a legitimate long-tail risk (chain forks, protocol forks, or intentional multi-network deployment of the same `defuse` contract code under the same top-level account naming).

### Recommendation
Add a chain/network identifier (e.g., `env::chain_id()`/genesis hash equivalent, similar to the `wallet` contract's `chain_id` field on `OffchainMessage`) into `DefusePayload`, and have `Engine::execute_signed_intent` reject any payload whose chain identifier does not match the currently executing chain. This closes the binding gap between "the chain the user intended to authorize" and "the chain the payload is actually executed on," consistent with the mitigation already implemented in `contracts/wallet/src/contract.rs`.

### Proof of Concept
1. User signs a `MultiPayload` (e.g., NEP-413) with `verifying_contract = intents.near`, a fresh `nonce`, and an intent to withdraw funds, on chain A (the canonical NEAR chain).
2. Chain A forks into chain A and chain A′ at some block; both chains have identical contract state (same `intents.near` account, same balances, same unused nonces/salts) up to the fork point.
3. The relayer/attacker submits the same signed `MultiPayload` to `execute_intents` on chain A — it settles and the nonce is committed there: [6](#0-5) 
4. The same signed `MultiPayload` bytes are submitted unchanged to `intents.near` on chain A′, where the nonce has not yet been committed (independent state after the fork). Because `DefusePayload` never encodes a chain identifier, verification passes identically on A′, and the intent settles a second time — the identical authorization is executed twice across the two chains.

```rust
    fn execute_signed_intent(&mut self, signed: MultiPayload) -> Result<()> {
        // verify signed payload and get public key
        let public_key = signed.verify().ok_or(DefuseError::InvalidSignature)?;

        // calculate intent hash
        let hash = signed.hash();

        // extract NEP-413 payload
        let DefusePayload::<DefuseIntents> {
            signer_id,
            verifying_contract,
            deadline,
            nonce,
            message: intents,
        } = signed.extract_defuse_payload()?;

        // check recipient
        if verifying_contract != *self.state.verifying_contract() {
            return Err(DefuseError::WrongVerifyingContract);
        }

        self.inspector.on_deadline(deadline);

        // make sure message is still valid
        if deadline < Timestamp::now() {
            return Err(DefuseError::DeadlineExpired);
        }

        // make sure the account has this public key
        if !self.state.has_public_key(&signer_id, &public_key) {
            return Err(DefuseError::PublicKeyNotExist(signer_id, public_key));
        }

        // commit nonce
        self.verify_intent_nonce(nonce, deadline)?;
        self.state.commit_nonce(signer_id.clone(), nonce)?;

        intents.execute_intent(&signer_id, self, hash)?;
```
