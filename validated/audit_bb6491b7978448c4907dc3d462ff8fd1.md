I'll investigate potential analogs in the bazel codebase for this header-injection-to-internal-control bug class.### Title
`git_repository` module-version type forwards attacker-controlled `remote` from a registry's `source.json` directly into `git remote add origin <remote>`, enabling protocol/argument abuse - (File: `tools/build_defs/repo/git_worker.bzl`)

### Summary
Bazel's Bzlmod registry protocol lets a `source.json` for a module version declare `type: git_repository`, whose `remote`, `commit`, `tag`, `shallow_since`, `verbose`, `init_submodules`, and `strip_prefix` fields are forwarded verbatim to the `git_repository` repo rule [1](#0-0) . The `remote` value is then passed unmodified as the URL argument to `git remote add origin <remote>` and subsequent `git fetch`/`clone` invocations [2](#0-1) [3](#0-2) , with no scheme allow-list and no `GIT_ALLOW_PROTOCOL` restriction set in the execution environment.

### Finding Description
For an "archive" module version, `source.json`'s `url`/`integrity` fields are bound by a required SRI checksum verified against the downloaded bytes — the untrusted registry content stays "data" because the checksum pins exactly what gets extracted. For the `git_repository` type, however, the analogous pinning is only the resulting `commit` hash captured for lockfile reproducibility; the `remote` string itself is never validated as "just a URL." It is handed to `git` as a literal command-line argument in `add_origin` → `_git(ctx, git_repo, "remote", "add", "origin", remote)` [2](#0-1) , and later used again during `fetch`/clone through `_execute`, which spawns `git` directly (no shell) with the environment inherited except for a fixed list of `GIT_*` variables that are unset [4](#0-3) .

Git supports a `ext::<command> <args...>` remote-URL transport that spawns an arbitrary command as the transport helper when cloning/fetching. Because Bazel does not set `GIT_ALLOW_PROTOCOL` (or an equivalent allow-list) before invoking `git`, and does not reject non-`http(s)`/`git`/`ssh` schemes in `remote`, a `source.json` with `"type": "git_repository", "remote": "ext::sh -c ...", ...` served by a compromised or attacker-controlled registry (a custom `--registry` mirror, or a compromise of a raw-GitHub-hosted fork) would result in Bazel running the attacker's command with the privileges of the Bazel process when the corresponding repo is fetched. This mirrors the CWE-915 pattern from the camel-coap advisory: an unauthenticated, untrusted party (the registry/mirror server) supplies content that is mapped directly into a field that a downstream, header/argument-sensitive consumer (the `git` CLI transport layer) treats as executable configuration, instead of being confined to "data."

### Impact Explanation
If reachable, this is a full content-controlled command execution during repository fetch — i.e., the same class of impact as the camel-coap RCE (arbitrary command execution with the privileges of the build process), triggered purely by the victim's build resolving a module version from a hostile/compromised registry, without any local access, credentials, or MITM being required beyond serving `source.json` for a `git_repository`-typed module.

### Likelihood Explanation
This can only be fully confirmed with an actual git binary reachability test in this repository; I could not locate any Java-side validation code (`GitRepoSpecBuilder`/registry `RepoSpec` construction) in the indexed sources that sanitizes or restricts the `remote` scheme before it reaches `.bzl` execution, nor any `GIT_ALLOW_PROTOCOL` setting anywhere in `git_worker.bzl`. This is a genuine gap relative to the "archive" type, which is checksum-bound. However:
- The `git_repository` module-version type is a documented but comparatively rare Bzlmod feature; most registries (including BCR) use the "archive" type.
- Whether modern default `git` builds still honor `ext::` without additional opt-in (some distros/newer git versions restrict `ext`/`file` protocols by default via `protocol.ext.allow`) is a factor I could not verify from this codebase alone, since it depends on the system git binary's compile-time/config defaults, not Bazel's code.
- I was not able to find or confirm the Java-side `RegistryFunction`/`ArchiveRepoSpecBuilder` equivalent for the `git_repository` type in the index to check whether there is any additional scheme filtering applied before the Starlark rule attributes are populated; this is a real gap in my verification, not a claim that no such check exists.

### Recommendation
- Restrict the `remote` attribute of `git_repository`/`new_git_repository` (and the registry-forwarded `source.json` `remote` field) to an explicit allow-list of safe schemes (`http`, `https`, `git`, `ssh`), rejecting `ext::`, `file://`, and other locally-executing transports unless explicitly opted into by trusted root-module configuration.
- Set `GIT_ALLOW_PROTOCOL=http:https:git:ssh` (or the rule-specific equivalent) in the environment used by `_execute` in `tools/build_defs/repo/git_worker.bzl` for every invocation of the `git` binary, defense-in-depth regardless of the local git build's defaults.
- Document/require that registries which surface `git_repository`-typed `source.json` entries are as trusted as the module content itself, since the `remote` field currently receives no integrity binding analogous to `integrity`/`sha256` for archive types.

### Proof of Concept
A minimal reproduction (requires an environment where `git`'s `ext::` transport is enabled/unrestricted, which I could not execute in this read-only investigation):
1. Host a custom registry (`--registry=file://...` or a raw-GitHub mirror) whose `modules/<name>/<version>/source.json` contains:
   ```json
   {
     "type": "git_repository",
     "remote": "ext::sh -c 'touch /tmp/pwned; git upload-pack .'",
     "commit": "deadbeef"
   }
   ```
2. Add a module dependency resolving to that registry/version in `MODULE.bazel`, and run `bazel build --registry=file://<path-to-registry> @dep//...`.
3. Observe that Bazel's `git_repository` invocation (via `tools/build_defs/repo/git_worker.bzl`'s `add_origin`/`fetch`) executes the attacker's command as part of `git remote add`/`git fetch`, creating `/tmp/pwned`.

I was unable to actually execute this PoC or inspect the Java-side registry/module-extension code that constructs the `RepoSpec` for `git_repository`-typed modules (not present in the indexed snippets), so this should be validated with a `BuildIntegrationTestCase`/`src/test/shell/bazel` test (e.g., extending `starlark_git_repository_test.sh`) against a live `git` binary before treating this as confirmed rather than a plausible, code-grounded analog.
