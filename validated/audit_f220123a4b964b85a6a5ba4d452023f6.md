### Title
Integer overflow in ZIP64 central-directory bounds check leads to out-of-bounds pointer computation in ijar - (File: third_party/ijar/zip.cc)

### Summary
`FindZipCentralDirectory` validates the central directory location of a (possibly malicious) JAR/ZIP file with a single unchecked 64-bit addition. When Bazel's `ijar` tool (used to build interface jars from jars produced by `java_import`, `http_jar`, `http_archive`, or resolved Maven/http dependencies) processes an attacker-supplied archive containing a crafted Zip64 End-Of-Central-Directory record, the addition can wrap around, bypassing the intended bounds check and producing an out-of-bounds central-directory offset that is later used directly in pointer arithmetic.

### Finding Description
`MaybeReadZip64CentralDirectory` reads `central_dir_size` and `central_dir_offset` as raw attacker-controlled 64-bit values (`u8`) straight from the archive bytes with `get_u8le`, with no range validation against the file length: [1](#0-0) 

`FindZipCentralDirectory` then performs the only sanity check on these fields as a plain unsigned 64-bit addition compared against `in_length`: [2](#0-1) 

If `central_dir_offset + central_dir_size` is crafted to wrap around `UINT64_MAX` (e.g. `central_dir_offset = 0xFFFFFFFFFFFFFFF0`, `central_dir_size` small), the sum becomes small and passes `> in_length`, even though `central_dir_offset` itself is nowhere near a valid in-bounds value. The function then returns this huge `*offset` value to the caller as trusted data.

`InputZipFile::Open` consumes this unchecked value directly in pointer arithmetic to compute the input scan cursor: [3](#0-2) 

`in_offset_` is computed from `zipdata_start + central_dir_offset - central_dir` with no bounds re-check, and `p = zipdata_in_ + in_offset_` becomes a wild pointer that is subsequently dereferenced while scanning entries (`ZipExtractor::ProcessAll`/`NextEntry`), causing an out-of-bounds read (and, depending on layout, out-of-bounds central-directory-header parsing that can propagate to further OOB reads of file names/sizes) within the `ijar`/`unzip_sfx` process.

### Impact Explanation
`ijar` operates on jar files produced anywhere in the dependency graph, including archives fetched via `http_jar`/`http_archive`/Maven resolution — content controlled by a remote, unprivileged origin. A malicious jar with a forged Zip64 EOCD record can corrupt `ijar`'s internal offset invariant (analogous to the Moloch `internalTransfer`/`max()` overflow corrupting balance invariants), causing out-of-bounds memory reads during the build. This can crash the build tool or read attacker-influenced adjacent heap/mapped-file memory, and the resulting bogus offsets undermine the archive's "central directory is always within bounds" invariant that all downstream ZIP parsing in `ijar` relies on.

### Likelihood Explanation
Reachable purely from build-time content: any target consuming a jar from an untrusted URL, mirror, or registry (no local access, no MITM, no privileged root-repo Starlark needed) can trigger this by shipping a crafted Zip64 EOCD record. No `sha256`/integrity check on the archive protects against this — checksums, if present, are verified on the raw bytes before/at fetch time and do not stop a legitimately-hashed archive that is deliberately crafted with malformed Zip64 fields by its (malicious) publisher.

### Recommendation
Perform the bounds check using saturating/checked arithmetic (e.g. verify `central_dir_size <= in_length` and `central_dir_offset <= in_length - central_dir_size` rather than `central_dir_offset + central_dir_size > in_length`), and independently validate that the computed `*central_dir` pointer and resulting `in_offset_`/`p` fall strictly within `[zipdata_in_, zipdata_in_ + in_length)` before use in `InputZipFile::Open`.

### Proof of Concept
Construct a ZIP/JAR file whose tail is a valid End-Of-Central-Directory + Zip64 Locator + Zip64 EOCD record where:
- `central_dir_size` = a small in-bounds value (e.g. 0x40)
- `central_dir_offset` = `0xFFFFFFFFFFFFFFF0` (so `central_dir_offset + central_dir_size` wraps to `0x30`, satisfying `<= in_length`)

Feed this file to `ijar` (or trigger via a `java_import`/`http_jar` target referencing this archive). `FindZipCentralDirectory` (third_party/ijar/zip.cc:766) accepts the forged offset, and `InputZipFile::Open` (third_party/ijar/zip.cc:834-843) computes `p = zipdata_in_ + in_offset_` pointing far outside the mapped file buffer, which is dereferenced on the next `NextEntry()` call, producing an out-of-bounds read/crash. This can be encoded as a `src/test/shell/bazel` regression test analogous to the existing Zip64 tests in `third_party/ijar/test/zip_test.sh` (e.g. `test_unzipper_zip64_archive`), asserting `ijar`/`unzip_sfx` rejects the malformed record instead of computing an out-of-bounds pointer.
