## Analog Found

### Title
Truncating (floor) division when computing the token amount an exchange‑inject caller must pay into the pool - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
`ExchangeInjectActuator` computes the paired ("another") token amount that a liquidity‑injecting user must deposit alongside the token they explicitly specify, using integer division that truncates towards zero (floor). Because this computed amount represents the second asset being paid **into** the exchange pool to keep it balanced, truncation always rounds the amount the caller must pay down, letting the caller under‑pay relative to the exact proportional requirement — the same rounding‑direction defect described in the referenced report (WAD/RAD truncation used for an amount paid into the system, which should round up, not down).

### Finding Description
In `doValidate()` the paired amount is computed with plain `BigInteger` division, which truncates: [1](#0-0) 

The same floor‑rounded value is what is actually collected in `execute()` via `floorDiv(...)`, and then debited from the caller's asset/TRX balance and credited into the exchange pool balance: [2](#0-1) [3](#0-2) 

For an inject, the exchange invariant requires `anotherTokenQuant = secondTokenBalance * tokenQuant / firstTokenBalance` (or the symmetric case) to preserve the pool's price ratio. Because the division floors instead of ceilings, the caller is required to pay strictly less than the exact proportional amount whenever the multiplication is not evenly divisible by the balance. This shifts the pool's implied price ratio in favor of the injecting account at the expense of the pool's other future participants (traders and withdrawers who rely on `firstTokenBalance`/`secondTokenBalance` staying properly proportioned), exactly mirroring the `remainingToRaise`/`WAD` truncation bug in the external report, where an amount owed *into* the system was rounded down instead of up.

### Impact Explanation
Each call only shaves off a fraction of one token unit (`0` to `denominator-1` out of the true value), but:
- The actuator is reachable by any account that can call `ExchangeInjectContract` (the exchange creator — an attacker can create their own exchange via `ExchangeCreateContract` and then become the privileged "creator" for follow‑on `ExchangeInjectContract` calls, so this is reachable by an ordinary, unprivileged transaction broadcaster).
- Repeated invocations (choosing `tokenQuant`/balances to maximize the truncated remainder) accumulate a persistent, systematic under‑contribution to the pool, producing an unbacked/mispriced balance in the `ExchangeCapsule` relative to the token amounts actually held, which can be extracted later through trades or withdrawals against the skewed ratio.

This falls under "unbacked balance" / gradual value extraction from the exchange pool, satisfying the required impact classes for a Medium finding.

### Likelihood Explanation
High reachability: any signed `ExchangeInjectContract` transaction from an account that owns (created) an exchange exercises this path deterministically; no special privileges beyond being the exchange's own creator are needed, and an attacker can trivially become that creator. The rounding effect is deterministic and reproducible for any non‑exact ratio.

### Recommendation
Round the computed `anotherTokenQuant` up (ceiling) in both `doValidate()` and `execute()` of `ExchangeInjectActuator`, e.g. using `BigInteger` ceiling division (`numerator.add(denominator).subtract(ONE)).divide(denominator)` or `RoundingMode.CEILING` for `BigDecimal`), so the injecting account can never pay less than the exact proportional amount required to keep the pool balanced. Ensure `execute()`'s `floorDiv` usage on lines 73/79 is likewise replaced with the same ceiling logic used in validation, and keep both computations consistent to avoid a validate/execute mismatch.

### Proof of Concept
1. Attacker calls `ExchangeCreateContract` to create a new token/TRX exchange with initial balances `firstTokenBalance = 3`, `secondTokenBalance = 10` (attacker is exchange creator).
2. Attacker calls `ExchangeInjectContract` specifying `tokenID = firstTokenID`, `tokenQuant = 1`.
3. `anotherTokenQuant = secondTokenBalance * tokenQuant / firstTokenBalance = 10*1/3 = 3` (floor of `3.33`), instead of the mathematically required `4` (ceil) to preserve ratio `10/3`.
4. Attacker's account is debited `1` of `firstToken` and `3` of `secondToken`, while the pool's ratio shifts favorably for the attacker versus the exact proportional `3.33`.
5. Repeating step 2–4 with carefully chosen `tokenQuant` values lets the attacker systematically under‑contribute `secondToken` on every injection, extracting value from the pool over time relative to other participants who trade or withdraw against the now‑skewed `firstTokenBalance`/`secondTokenBalance` ratio.
