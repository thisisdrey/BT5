### Title
Missing self-target validation in `parse_tx_data` allows AddKey/DeleteKey actions to be dispatched against an arbitrary NEAR account instead of `current_account_id` - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs])

### Summary
`parse_tx_data`'s `ADD_KEY_SELECTOR`/`DELETE_KEY_SELECTOR` branches decode `Action::AddKey`/`Action::DeleteKey` without ever checking that `target` equals `current_account_id`. The only place that special-cases `ParsableTransactionKind::SelfNearNativeAction` is `parse_rlp_tx_to_action`, and it only rewrites the action when `target_kind == TargetKind::EthImplicit(_)`; when `target_kind == TargetKind::OtherNearAccount(_)` the original `AddKey`/`DeleteKey` action passes through unmodified and is later turned into `action_to_promise(target, action)`, sending the AddKey/DeleteKey receipt to `target` rather than to the wallet's own account.

### Finding Description
`parse_tx_data` decodes the ABI payload for `ADD_KEY_SELECTOR`/`DELETE_KEY_SELECTOR` and returns `Ok((Action::AddKey{..}, ParsableTransactionKind::SelfNearNativeAction))` / `Ok((Action::DeleteKey{..}, ParsableTransactionKind::SelfNearNativeAction))` with no comparison of `target` (or `receiver_id`) to `current_account_id` [1](#0-0) .

In `parse_rlp_tx_to_action`, the `SelfNearNativeAction` match arm only substitutes a harmless `Transfer` action when `target_kind` is `TargetKind::EthImplicit(_)`; for any other `target_kind` (including `TargetKind::OtherNearAccount(_)`) it falls through to `(action, TransactionKind::NearNativeAction)`, keeping the original `AddKey`/`DeleteKey` action untouched [2](#0-1) .

`validate_tx_relayer_data` only verifies that the Ethereum `to` address is consistent with `target` (`to == account_id_to_address(target)` for the `OtherNearAccount` case); it never restricts `target` to equal `current_account_id` for AddKey/DeleteKey payloads [3](#0-2) .

Back in `inner_rlp_execute`, since the resulting `transaction_kind` is `TransactionKind::NearNativeAction`, execution falls into the generic branch that calls `action_to_promise(target, action)?.then(...)`, using `target` — not `current_account_id` — as the promise receiver [4](#0-3) . `action_to_promise` then constructs `Promise::new(target).add_access_key_allowance_with_nonce(...)` for FunctionCall-permission AddKey (only `FullAccess` AddKey is explicitly rejected), and `Promise::new(target).delete_key(...)` for DeleteKey [5](#0-4) .

Exploit flow: the owner of an eth-implicit wallet account signs an Ethereum-style transaction whose `to` field is `account_id_to_address(victim_account)` and whose calldata uses `ADD_KEY_SELECTOR` to encode an `AddKey` action (with attacker-chosen `public_key`, `receiver_id`, `method_names`, and `allowance`/`is_limited_allowance=false` for unlimited allowance). Any relayer (including the attacker themselves) calls `rlp_execute(target=victim_account, tx_bytes_b64)` on the attacker's own wallet contract. `validate_tx_relayer_data` accepts this because `to == account_id_to_address(target)` holds by construction, classifying `target_kind` as `TargetKind::OtherNearAccount(victim_account)`. The AddKey action is preserved unmodified through `parse_rlp_tx_to_action`, and `inner_rlp_execute` issues a receipt with a `AddKey` action addressed to `victim_account`.

### Impact Explanation
This is an authorization-escalation bug within the Wallet Contract's own promise-construction logic: the contract lets attacker-controlled ABI-decoded data determine the receiver of a privileged `AddKey`/`DeleteKey` receipt instead of confining `SelfNearNativeAction` results to `current_account_id`. Concretely it allows adding a FunctionCall access key (with attacker-chosen `receiver_id` for the permission and possibly unlimited `allowance`) or deleting a key on any account for which `to == account_id_to_address(target)` can be satisfied — matching the "authorization escalation across accounts or promises" bounty category. Full-access key addition is explicitly blocked (`Err(UserError::UnsupportedAction(AddFullAccessKey))` in `action_to_promise`), which limits (but does not eliminate) the severity: attacker cannot obtain a full-access key this way, but can add a function-call key capable of spending the target account's NEAR balance on gas via the allowance mechanism, or delete an unrelated account's key.

### Likelihood Explanation
The precondition is that the target account chain of custody is entirely attacker-controlled: the attacker signs their own Ethereum-style transaction (they own the eth-implicit wallet's private key) and simply chooses `to = account_id_to_address(victim_account)` and calls `rlp_execute` with `target = victim_account`. No collision search or victim cooperation is required — the attacker deterministically computes `account_id_to_address(victim_account)` and signs against it. This is trivially repeatable at low cost (one relayed transaction). The main open question, not fully verifiable from the available Wallet Contract crate alone, is whether NEAR runtime's action-application semantics for `AddKey`/`DeleteKey` receipts require any predecessor/receiver relationship (this would need confirmation in `runtime/runtime/src/access_keys.rs`, which could not be inspected within the available iterations).

### Recommendation
In `parse_tx_data`'s `ADD_KEY_SELECTOR`/`DELETE_KEY_SELECTOR` branches (or immediately in the `SelfNearNativeAction` match arm of `parse_rlp_tx_to_action`), explicitly require `target_kind == TargetKind::CurrentAccount` before accepting the action; reject with `Error::Relayer(RelayerError::InvalidTarget)` (or a dedicated error) for any other `target_kind`, mirroring the existing rejection already performed for the unparsable-payload `TargetKind::OtherNearAccount(_)` case.

### Proof of Concept
Runtime/integration test (extending `runtime/near-wallet-contract/implementation/wallet-contract/src/tests/`):
1. Deploy the wallet contract to an eth-implicit account `A` and create an unrelated plain account `V` ("victim") with no relationship to `A`.
2. Construct an Ethereum-style transaction signed by `A`'s secret key with `to = account_id_to_address(V)` and calldata = ABI-encoded `ADD_KEY_SELECTOR` for a FunctionCall-permission AddKey action with an attacker-controlled public key, `allowance = None` (unlimited), `receiver_id` set to an attacker-controlled contract, and empty `method_names`.
3. Call `wallet_contract.rlp_execute(target = V, tx_bytes_b64)`.
4. Assert the call succeeds (`result.success == true`) and that account `V`'s access key list now contains the attacker's public key with a `FunctionCall` permission — demonstrating that a key was added to `V` even though `V != A` (the signer's own wallet account), confirming that the self-binding check is bypassed.
