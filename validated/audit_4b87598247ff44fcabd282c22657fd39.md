### Title
Unauthenticated `RecvError` Packet Bypasses Remote-Address Verification and Force-Closes Tunnels for Any HostInfo Whose Remote Endpoint Is Unset - (File: outside.go)

### Summary
`Vether.sol`'s `addExcluded()` had no access control, letting anyone place themselves on a trusted bypass list and skip a security check that was supposed to apply to everyone. The nebula analog is `handleRecvError` in `outside.go`: it processes a completely unauthenticated, unencrypted packet type (`header.RecvError`) and only refuses to act on it when the target hostinfo's stored remote address is "valid" and mismatched. When that stored remote address is not yet set/valid (e.g., relay-only tunnels or in-progress state), the guard is skipped entirely, so *any* off-path attacker who has never presented a CA-signed certificate can send a forged packet and force privileged state changes (tunnel teardown), exactly like Alice adding herself to an "excluded" list with no ownership check.

### Finding Description
`readOutsidePackets` in `outside.go` dispatches `header.RecvError` packets before any certificate/handshake verification is performed: [1](#0-0) 

`f.handleRecvError` is reached with only the raw sender `netip.AddrPort` and the header — no proof of possession of a valid CA-signed certificate is required, because `RecvError` is one of the two "unencrypted packet" types handled prior to any `ConnectionState.Decrypt`/cert check: [2](#0-1) 

The function's only authenticity check is:
```go
hr := hostinfo.GetRemote()
if hr.IsValid() && hr != addr {
    f.l.Info("Someone spoofing recv_errors?", ...)
    return
}
```
This is structurally identical to Vether's unrestricted `addExcluded`: the security-relevant gate (verifying the sender is the legitimate remote peer) is only enforced *if a precondition already holds* (`hr.IsValid()`), and there is no independent authentication of the caller otherwise. When `hr` is not valid — which happens for hostinfo entries reached via a relay, where `SetRemote` is never called and `relayState.InsertRelayTo` is used instead — [3](#0-2) 

— the `hr.IsValid()` short-circuit means the mismatch check never executes, and `handleRecvError` proceeds unconditionally to tear down the tunnel and delete the pending handshake state: [4](#0-3) 

The only "credential" required to reach this branch is knowledge of a valid `RemoteIndex` (`h.RemoteIndex`), which is a locally-chosen 32-bit index resolved via `f.hostMap.QueryReverseIndex(h.RemoteIndex)` — not a certificate, not a handshake, not an authenticated MAC. An attacker with no CA-signed certificate at all who can observe or brute-force this index can trigger the same unauthenticated write path that the Vether bug exploited: an unrestricted, self-service call into privileged internal state (`closeTunnel` / `hm.DeleteHostInfo`) that bypasses the intended ownership/ACL check.

### Impact Explanation
This allows a remote, unauthenticated attacker (no valid nebula certificate, no completed handshake) to forcibly close relay-mediated tunnels and delete their pending handshake state, causing denial of service against relayed peer connections. This is a remote state poisoning / traffic disruption vector because it lets an outsider manipulate hostmap/tunnel state that is supposed to be gated by proof of being the legitimate remote endpoint, mirroring the unrestricted list-mutation bug class from the Vether report (any caller can flip a security-relevant flag/state with no ownership check).

### Likelihood Explanation
Reachability is high for the specific configuration where relays are used: `RecvError` packets are processed before any decryption/cert verification (`outside.go` header switch), so the attacker needs no certificate at all. The only obstacle is guessing/observing a valid `RemoteIndex`, which is transmitted in cleartext in every nebula packet header and is therefore observable by any network-path attacker (e.g., anyone who can see UDP traffic to the target, or who receives it via a relay). No CA-signed certificate or successful handshake is required to construct or send the spoofed `RecvError` packet.

### Recommendation
- Do not gate the spoofing check on `hr.IsValid()`; instead require that `handleRecvError` only act when the sender address can be positively correlated to a known, currently-negotiating or established remote for that hostinfo (including via relay path), or reject `RecvError` packets for hostinfo that have no directly verified remote endpoint.
- Consider requiring `RecvError` handling to additionally validate that the reporting address matches an expected relay/lighthouse-registered address, or rate-limit/log-and-ignore `RecvError` for hostinfo without a valid `hr` rather than silently proceeding to tear down state.
- More generally, apply the fix pattern used for the analogous Vether issue: any function that mutates trust/exclusion state (here, tunnel liveness state) must authenticate the caller unconditionally, not only when a prior condition happens to be true.

### Proof of Concept
1. Attacker observes (via passive network monitoring, since headers are unencrypted) a `RemoteIndex` used by two nebula peers, `A` and `B`, communicating through a relay (`via.IsRelayed == true` on `B`'s handshake completion), so that `B`'s `HostInfo.GetRemote()` was never set via `SetRemote` and remains invalid.
2. Attacker crafts a bare `header.RecvError` packet (no encryption, no certificate) with `RemoteIndex` set to the index observed for `B`'s hostinfo of `A`, and sends it from an arbitrary source address to `B`.
3. `readOutsidePackets` dispatches directly to `f.handleRecvError(via.UdpAddr, h)` without any certificate/handshake check (`outside.go:81-84`).
4. Inside `handleRecvError`, `hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)` finds `B`'s hostinfo for `A`; `hr := hostinfo.GetRemote()` returns an invalid value, so `hr.IsValid() && hr != addr` is `false`, skipping the spoof-detection branch.
5. `f.closeTunnel(hostinfo)` and `f.handshakeManager.DeleteHostInfo(hostinfo)` execute unconditionally, tearing down `B`'s relayed tunnel to `A` — achieved entirely by an attacker holding no CA-signed certificate and having completed no handshake.

```go
func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
```
