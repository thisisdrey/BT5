### Title
A reverting recipient in `claim` / `claimRewards` permanently or temporarily blocks reward distribution - (File: contracts/utils/RecurringAirdrop.sol)

### Summary
The bug class is "a token transfer that throws inside a distribution function reverts the whole payout". Metronome has two reachable analogs: `RecurringAirdrop.claim` and `RewardsDistributor.claimRewards`. Both perform a `safeTransfer` of a fixed, governor-chosen `token`/`rewardToken` to an externally supplied account without any try/catch, so a recipient that makes the transfer revert (e.g., a blacklistable ERC20 such as USDC/USDT where the account is blacklisted) can never receive their distribution. In the airdrop case the freeze is permanent for that claimant; in the batch `claimRewards(accounts_, tokens_)` case one reverting account in the middle of the array reverts the whole transaction, reverting all accrued-index updates and other accounts' payouts in the same call.

### Finding Description
`RecurringAirdrop.claim` verifies a Merkle proof for `(msg.sender, amount_)`, increments `claimed[msg.sender]`, then calls `_transferReward`, which is `token.safeTransfer(to_, amount_)` [1](#0-0) . If `token` is an ERC20 with a blacklist/freeze mechanism and `msg.sender` is blacklisted, the `safeTransfer` reverts and the entire claim — including the `claimed` bookkeeping — rolls back. Since `claim` always transfers to `msg.sender` (the leaf is bound to `msg.sender`), the affected user has no alternative path: their allocation is permanently unclaimable.

`RewardsDistributor.claimRewards(address[] accounts_, IERC20[] tokens_)` is permissionless and iterates over `accounts_`, calling `_transferRewardIfEnoughTokens`, which does `rewardToken.safeTransfer(account_, amount_)` [2](#0-1) [3](#0-2) . A single account whose `rewardToken` transfer reverts aborts the transaction and rolls back the index/accrued updates for all tokens and all accounts processed in that call. Note the caller can simply resubmit without the bad account, so this variant only causes temporary freezing of unclaimed yield for the blacklisted account itself (it can never claim while blacklisted, since every claim path routes through the same reverting transfer).

### Impact Explanation
Permanent freezing of unclaimed yield for any `RecurringAirdrop` claimant (or `RewardsDistributor` account) that is blacklisted by the reward token: their merkle-proven allocation / accrued rewards can never be paid out. For the multi-account `claimRewards`, one reverting recipient also DoSes the other accounts in the same batched call until the list is rebuilt.

### Likelihood Explanation
Requires the deployed `token`/`rewardToken` to implement a blacklist (e.g., USDC/USDT-style) and a legitimate claimant to be on it — not attacker-triggerable in general, matching the original Medium severity. The mechanism itself is deterministic: there is no guard (`nonReentrant`, governor checks, pause flags do not apply to the transfer outcome) and no fallback path.

### Recommendation
Mirror the upstream fix: record `claimed`/`tokensAccruedOf` before the transfer but wrap the transfer in try/catch (or pull-pattern), emitting a "not distributed" event on failure so accounting can be retried or handled off-chain. For `RecurringAirdrop`, consider allowing an override `to_` recipient or a pull-into-escrow fallback. For `claimRewards`, wrap `_transferRewardIfEnoughTokens` per account so one failing account does not revert the batch.

### Proof of Concept
```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {RecurringAirdrop} from "../contracts/utils/RecurringAirdrop.sol";
import {MerkleProof} from "../contracts/dependencies/openzeppelin/utils/cryptography/MerkleProof.sol";

contract BlacklistToken {
    mapping(address => uint256) public balanceOf;
    mapping(address => bool) public blacklist;
    function mint(address to, uint256 a) external { balanceOf[to] += a; }
    function setBlacklist(address a, bool b) external { blacklist[a] = b; }
    function transfer(address to, uint256 a) external returns (bool) {
        require(!blacklist[to], "blacklisted");
        balanceOf[msg.sender] -= a; balanceOf[to] += a; return true;
    }
}

contract RevertingClaimTest is Test {
    function test_blacklistedClaimantCanNeverClaim() public {
        BlacklistToken t = new BlacklistToken();
        RecurringAirdrop airdrop = new RecurringAirdrop(IERC20Like(address(t)));
        t.mint(address(airdrop), 100e18);

        address alice = address(0xA11CE);
        // single-leaf tree: leaf = keccak256(abi.encodePacked(alice, amount))
        bytes32 leaf = keccak256(abi.encodePacked(alice, uint256(50e18)));
        vm.prank(governor);
        airdrop.updateMerkleRoot(leaf, bytes32("ipfs"));

        t.setBlacklist(alice, true);

        bytes32[] memory proof = new bytes32[](0);
        vm.prank(alice);
        vm.expectRevert(); // safeTransfer reverts -> whole claim reverts, claimed stays 0
        airdrop.claim(50e18, proof);
        assertEq(airdrop.claimed(alice), 0);
    }
}
```
The same pattern applies to `RewardsDistributor.claimRewards([alice, bob], tokens_)` with a blacklistable `rewardToken`: `safeTransfer` to blacklisted `alice` reverts the whole call, also rolling back bob's payout in that transaction.


In `contracts/utils/RecurringAirdrop.sol`, wrap the `token.safeTransfer` in `_transferReward`/`claim` path with try/catch (or switch to a pull/escrow pattern) so a reverting recipient does not permanently block their allocation; add a `RewardNotTransferred` event. In `contracts/RewardsDistributor.sol`, wrap the per-account `_transferRewardIfEnoughTokens` call inside `claimRewards(address[],IERC20[])` in try/catch so one failing account does not revert the batch; keep accrued accounting consistent on failure. Add tests covering a blacklistable reward token where one recipient reverts.

    function claim(uint256 amount_, bytes32[] calldata proof_) external nonReentrant {
        if (merkleRoot == bytes32(0)) revert NothingToClaim();

        bytes32 _leaf = keccak256(abi.encodePacked(msg.sender, amount_));
        if (!MerkleProof.verify(proof_, merkleRoot, _leaf)) revert InvalidProof();

        uint256 _claimable = amount_ - claimed[msg.sender];
        if (_claimable == 0) revert NothingToClaim();

        claimed[msg.sender] += _claimable;

        _transferReward(msg.sender, _claimable);

        emit RewardClaimed(msg.sender, _claimable);
    }

    function claimRewards(address[] memory accounts_, IERC20[] memory tokens_) public override nonReentrant {
        uint256 _accountsLength = accounts_.length;
        uint256 _tokensLength = tokens_.length;
        for (uint256 i; i < _tokensLength; ++i) {
            IERC20 _token = tokens_[i];

            if (tokenStates[_token].index > 0) {
                _updateTokenIndex(_token);
                for (uint256 j; j < _accountsLength; j++) {
                    _updateTokensAccruedOf(_token, accounts_[j]);
                }
            }
        }

        for (uint256 j; j < _accountsLength; j++) {
            address _account = accounts_[j];
            _transferRewardIfEnoughTokens(_account, tokensAccruedOf[_account]);
        }
    }
