## Finding: Unchecked Return Value from Low-Level `evm.Call` in EIP-4788 Beacon Root Processing

### Title
Unchecked Return Value of System Call in `ProcessBeaconBlockRoot` (EIP-4788) - (File: `core/state_processor.go`)

### Summary
`ProcessBeaconBlockRoot`, which executes the EIP-4788 system call to the beacon-roots contract, discards the `error` returned by `evm.Call` instead of checking it, unlike every other system-call helper in the same file.

### Finding Description
`ProcessBeaconBlockRoot` invokes the beacon-roots contract via `evm.Call` and throws away all three return values, including the error: [1](#0-0) 

Compare this to the structurally identical EIP-2935 helper `ProcessParentBlockHash`, which checks the same `err` and `panic`s if the system call fails: [2](#0-1) 

And to `processRequestsSystemCall` (used for EIP-7002/7251/8282), which checks `err` and propagates a wrapped error that aborts block processing: [3](#0-2) 

`evm.Call` can legitimately return a non-nil `err` for reasons unrelated to the caller's control — e.g. `ErrOutOfGas` if the fixed `30_000_000`/state-budget gas allotment from `systemCallGasBudget` is insufficient for the deployed contract's runtime, or `ErrExecutionReverted`/other VM errors if the contract at `BeaconRootsAddress` reverts or self-destructs unexpectedly: [4](#0-3) [5](#0-4) 

Because `ProcessBeaconBlockRoot` ignores `err`, if this call ever reverts or halts, `evm.StateDB.RevertToSnapshot(snapshot)` still runs inside `evm.Call` (so no state corruption occurs), but the block-processing pipeline in `PreExecution`/`Process` proceeds exactly as if the beacon-root write had succeeded — no panic, no error return, no block rejection: [6](#0-5) [7](#0-6) 

This is inconsistent with the sibling system-call sites in the same file, which treat a failed system call as fatal to block processing (`panic` for EIP-2935, propagated error for EIP-7002/7251/8282).

### Impact Explanation
If the EIP-4788 system call fails on a mainnet block (e.g., insufficient system-call gas budget, or a beacon-roots contract behaving unexpectedly), Geth silently accepts the block and continues processing as though the beacon root storage write succeeded, while other clients/specs that treat a failed mandatory system call as invalidating block execution would reject it or halt. This produces a state/consensus divergence: Geth's post-state (and hence `stateRoot`) would omit the beacon-root ring-buffer update that a compliant client either enforces or fails on, breaking the equality between the two implementations' resulting state for the same block.

### Likelihood Explanation
Likelihood of the beacon-roots contract itself reverting under normal deployment is very low because it is a fixed, minimal bytecode contract and the gas budget (30M) vastly exceeds its needs. The realistic trigger is any deviation of the deployed contract's behavior from the expected ring-buffer semantics (e.g., a future contract upgrade, or corrupted/incorrect code at `BeaconRootsAddress` on some chain configuration) causing a revert — a scenario the code path was clearly intended to guard against, mirrored by the identical, but correctly-checked, sibling call in `ProcessParentBlockHash`.

### Recommendation
Check the error returned from `evm.Call` in `ProcessBeaconBlockRoot` and handle it consistently with the other system-call sites in `core/state_processor.go` — either `panic` (matching `ProcessParentBlockHash`) or propagate an error up through `PreExecution`/`Process` so an invalid/failing system call aborts block processing instead of being silently accepted:

```go
_, _, err := evm.Call(msg.From, *msg.To, msg.Data, gasBudget, common.U2560)
if err != nil {
    panic(err) // or return an error, consistent with ProcessParentBlockHash / processRequestsSystemCall
}
```

### Proof of Concept
1. Deploy/replace the contract at `params.BeaconRootsAddress` (or otherwise arrange for its execution to revert/exceed the `systemCallGasBudget`) such that the EIP-4788 system call fails when invoked by `ProcessBeaconBlockRoot`.
2. Produce a post-merge block with `ParentBeaconRoot` set, triggering `PreExecution` → `ProcessBeaconBlockRoot` → `evm.Call`.
3. Observe that the call's error is discarded at `core/state_processor.go:336`, block processing proceeds without panic or error, and the resulting `stateRoot`/receipts differ from what a client that enforces the system call's success would produce for the identical block.

// systemCallGasBudget returns the gas budget for system calls.
func systemCallGasBudget(evm *vm.EVM) (gasLimit uint64, gasBudget vm.GasBudget) {
	if !evm.GetRules().IsAmsterdam {
		gasLimit = 30_000_000
		gasBudget = vm.NewGasBudget(gasLimit, 0)
	} else {
		// SYSTEM_MAX_SSTORES_PER_CALL = 16 is the upper bound on the number of
		// new storage slots a single system call is expected to write.
		stateBudget := params.SystemMaxSStoresPerCall * evm.Context.CostPerStateByte * params.StorageCreationSize
		gasLimit = 30_000_000
		gasBudget = vm.NewGasBudget(gasLimit, stateBudget)
	}
	return gasLimit, gasBudget
}
