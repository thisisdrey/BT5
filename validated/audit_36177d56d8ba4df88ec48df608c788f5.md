### Title
Access-key allowance refund (`Receipt::new_gas_refund`) credits the allowance of whatever key currently holds the signer's public key, not the key that was actually debited - ([File: runtime/runtime/src/lib.rs])

### Summary
When a receipt is applied, unused attached gas is refunded to the signer's account via `Receipt::new_gas_refund(&action_receipt.signer_id(), gas_balance_refund, action_receipt.signer_public_key().clone())`, and, per the accompanying code comment, "if the key exists on the account it will increase the allowance by the refund amount." [1](#0-0)  The lookup that applies this credit is keyed only on the account id + public key pair, with no binding to the specific `AccessKey` state (nonce/permission/allowance) that was actually debited when the original transaction was signed.

### Finding Description
The refund flow works as follows:
1. A transaction signed with a FunctionCall-permission access key attaches gas; at verification time the attached gas cost is deducted from that key's `allowance` (standard access-key spend-limiting check in `verifier.rs`).
2. After execution, `refund_unspent_gas_and_deposits` computes `gas_balance_refund` (unused gas + burnt-gas price surplus) and, if positive, enqueues a receipt built by `Receipt::new_gas_refund(signer_id, amount, signer_public_key)` — a system-originated receipt (`predecessor_id == "system"`) addressed back to `signer_id == receiver_id`. [2](#0-1)  This behavior is documented as intentional in `docs/RuntimeSpec/Refunds.md` ("Access Key Allowance refunds").
3. When this refund receipt is later applied (asynchronously, in a subsequent block), the runtime looks up an access key on the receiver's account matching the embedded public key and increases its `allowance` field, presumably via a saturating add so the balance-refund amount is credited back as spendable allowance.
4. Because the credit is applied by public-key match alone, an account owner who controls a FullAccess key can, between the time the FunctionCall-key transaction is accepted and the time its gas refund receipt is applied, submit `DeleteKey` followed by `AddKey` re-using the *same* public key but with a different (e.g., much lower, attacker-chosen) `FunctionCallPermission` allowance. The stale refund receipt from the deleted key's transaction then arrives and blindly inflates the *new* key's allowance by `saturating_add`, even though the new key instance was never debited for that gas and the account never separately funded that allowance amount for the new key configuration.

This bypasses the intended invariant that a FunctionCall access key's allowance is a strict, non-widening spending cap set at `AddKey` time (only reducible via consumption, refundable only up to the amount actually consumed by that same key instance).

### Impact Explanation
This allows a signer who controls a FullAccess key on an account to manufacture extra spendable allowance on a newly-created, more restrictive FunctionCall key beyond the value ever explicitly granted to that key via `AddKey`. This matters specifically in gas-sponsorship / meta-transaction / "gas key" style setups (the codebase has a dedicated `gas_keys` test-loop suite, `test-loop-tests/src/tests/gas_keys.rs`), where a FunctionCall key's `allowance` is meant to be a hard, auditable authorization ceiling controlling how much of the account's funds (or a sponsor-provisioned key) a lower-trust holder of that public key may spend. Falsely inflating that ceiling constitutes an authorization-escalation of the access-key spending limit relative to its configured invariant (AUTHORIZATION_EXACTNESS), matching the "authorization escalation ... across promises" bounty category insofar as it defeats the allowance mechanism as a security boundary, rather than merely being a bookkeeping quirk confined to the account owner's own funds.

### Likelihood Explanation
Preconditions: the account must have (or the attacker must control) a FullAccess key to perform `DeleteKey`+`AddKey`, and the attacker must time the key swap to land in a block after the original FunctionCall transaction is accepted but before its gas refund receipt (an async, cross-block system receipt) is applied. This is fully achievable by an ordinary unprivileged account owner using only standard transaction submission (no validator/node access needed) and is deterministically repeatable, since gas-refund receipts are always generated for any unused/overpaid gas and always target `(signer_id, signer_public_key)`.

### Recommendation
Do not restore allowance based on public-key match alone. Either (a) suppress the allowance restoration if the current on-chain `AccessKey` for that public key does not match the key's identity/nonce at the time gas was reserved, or (b) stop refunding allowance via a separate system receipt entirely and instead perform the allowance restoration synchronously/atomically at the point where unused gas is computed, tied to the specific key state consumed, so a subsequent `DeleteKey`/`AddKey` on the same public key cannot receive stale credit.

### Proof of Concept
Test-loop integration test:
1. Create account `alice` with FullAccess key and FunctionCall-permission key `K` (`public_key = pk`, `allowance = 10 NEAR`, `receiver_id = contract`, unrestricted method).
2. `alice` signs and submits a FunctionCall transaction using key `K` with `attached_gas` large enough that a nontrivial `gas_balance_refund` is produced.
3. In the very next block, `alice` (using her FullAccess key) submits `DeleteKey(pk)` followed by `AddKey(pk, FunctionCallPermission { allowance: 1 yoctoNEAR, ... })`.
4. Allow the gas refund receipt (predecessor `"system"`, `signer_id==receiver_id==alice`, target public key `pk`) to be applied in a subsequent block.
5. Assert: the new key `K'`'s allowance equals `1 yoctoNEAR + gas_balance_refund` (bug) rather than the configured `1 yoctoNEAR` (expected/invariant-preserving behavior), demonstrating the allowance was inflated beyond its configured cap by an amount the new key was never independently authorized/funded for.
