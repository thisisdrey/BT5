### Title
Fragile string-based classification of `git-fetch` failures in `FetchRemote` can let a malicious/misbehaving remote force a partial repository state to be committed — ([File: internal/gitaly/service/repository/fetch_remote.go])

### Summary
`FetchRemote` fetches from a remote (attacker-influenced when the RPC's `RemoteParams.Url` points at a mirror/import source under lesser trust) into a quarantine directory, then decides whether to still apply parsed reference updates or abort, based on an exact string match of the wrapped `exec.ExitError`. This mirrors the GMX bug class: a "safe to proceed" classification of an error condition is derived from an incomplete/fragile check rather than an exhaustive, structured enumeration, so unexpected but semantically-different failures can be silently treated as the benign case.

### Finding Description
In `fetchRemoteAtomic`, after invoking `git-fetch` in dry-run/porcelain mode into a quarantine directory, Gitaly must decide whether a non-nil error from the fetch means "some ref updates failed, but the successful ones should still be applied" (the expected/benign case) or "there was a real failure and everything must be aborted."

That decision is made purely by:
1. Checking whether `stderr` is non-empty → treat as fatal.
2. If `stderr` is empty, comparing the wrapped Go error's string representation against the literal `"exit status 1"` → treat as the benign "some refs failed" case and continue to apply the successfully-parsed reference updates and migrate the quarantine directory. [1](#0-0) 

This is exactly analogous to the `EmptyFeedPrice` bug: instead of enumerating the actual well-defined set of conditions that legitimately correspond to "git-fetch exited 1 solely because of failed ref updates," the code approximates that set with a brittle heuristic (empty stderr + exact string `"exit status 1"`). Any other failure mode of the spawned `git-fetch` process that happens to produce no stderr output and an `exec.ExitError` with `ExitCode() == 1` (for example, truncated/redirected stderr, a wrapped/proxy git binary, a crash mid-write after partial output, or a remote deliberately crafted to trigger such a condition) is misclassified as benign. In that case Gitaly proceeds to:
- Parse whatever was written to `stdout` before the failure via `gitcmd.NewFetchPorcelainScanner` [2](#0-1) 
- Migrate the quarantine directory into the repository [3](#0-2) 
- Commit the queued reference updates [4](#0-3) 

instead of aborting the whole operation, as the surrounding comments intend for genuine unrelated errors [5](#0-4) .

### Impact Explanation
Because the classification gate is based on an exact string match of a Go-wrapped `exec.ExitError` rather than a structurally verified set of causes, a remote source (reachable via project mirroring / repository import configuration, which is `RemoteParams.Url` — a crafted RPC field) that can influence the timing or content of `git-fetch`'s stderr output (e.g., through network truncation, a compromised/incompatible git server, or an attacker-controlled proxy in the fetch path) could cause Gitaly to commit a partial, inconsistent reference state derived from an incompletely/erroneously-terminated fetch, rather than aborting atomically as the quarantine mechanism is designed to guarantee. This weakens the atomicity guarantee that the quarantine + dry-run + porcelain design in this function is explicitly built to provide.

### Likelihood Explanation
Likelihood is moderate-to-low: it requires the underlying `git-fetch` process to exit with status 1, produce empty stderr, and have already written some porcelain status lines to stdout — a fairly specific combination that isn't the normal failure mode (git normally reports failures to stderr). However, it is plausible under network interruption, a misbehaving/malicious remote endpoint, or output buffering edge cases, all of which are conditions influenced by the (potentially less trusted) fetch target configured through the RPC's remote parameters.

### Recommendation
Do not rely on matching the literal string `"exit status 1"` of a wrapped error to distinguish "some ref updates failed" from other failures. Instead:
- Use `errors.As` to extract the `*exec.ExitError` and check its `ExitCode()` value structurally rather than string-comparing the wrapped error's `Error()` output.
- Additionally verify that the fetch actually produced parseable porcelain output consistent with a "some refs failed" outcome (e.g., require the scanner to observe at least one `RefUpdateTypeUpdateFailed` status) before treating the failure as benign.
- Treat any other combination (unexpected exit code, no parseable porcelain updates, or stderr present) as fatal and abort without committing/migrating.

### Proof of Concept
Not applicable as a concrete exploit chain — the finding is a structural error-classification weakness identified by code inspection, analogous to the referenced report's incomplete `isEmptyPriceError()` allow-list. Reproducing it deterministically would require crafting a `git-fetch` failure that exits with status 1, writes no stderr, and leaves partial `--porcelain` stdout output, which depends on environment/timing conditions rather than a single deterministic input.

		// failed reference update and the operation proceeds to update references.
