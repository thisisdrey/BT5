### Title
Wallet Contract pays relayer fee before address-registrar validation completes, causing unrecoverable fund loss on address-check failure - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The Slingshot bug is a class of "premature balance/settlement" bug: a value (`initialBalance`) is captured/committed using a measurement that does not yet reflect the true, final state of the operation, so a later step (fund transfer/refund) is computed and executed on stale/incorrect information, causing users to lose funds. The NEAR ETH-implicit Wallet Contract (`runtime/near-wallet-contract`) contains an analogous pattern: it unconditionally pays out the relayer's `tx_fee` for an emulated EOA base-token transfer *before* the asynchronous address-registrar validation (which determines whether the transaction is even valid) has completed.

### Finding Description
`inner_rlp_execute` (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:330-410`) parses the Ethereum transaction and, for `EOABaseTokenTransfer`/`ERC20Transfer` kinds, immediately schedules an irreversible transfer of `tx_fee` from the wallet's own NEAR balance to `context.predecessor_account_id` (the relayer): [1](#0-0) 

This fee-payment code fires *unconditionally* for `EOABaseTokenTransfer`, regardless of whether `address_check` is `Some` or `None`. However, when `address_check: Some(address)` is present, validity of the transaction has **not yet been established** — a separate, asynchronous cross-contract promise is scheduled to query the address registrar and only resolves later in `address_check_callback`: [2](#0-1) 

If that registrar lookup returns `Some(account_id)` (i.e., the `target` chosen for the transaction actually corresponds to an existing named Near account, meaning the transaction/target was invalid), the callback treats this as a faulty-relayer condition and either bans the relayer or returns an explicit `error` response: [3](#0-2) 

In both outcomes the underlying user action never executes and the nonce is *not* incremented for the failed attempt, yet the `tx_fee` transfer to the relayer created earlier in `inner_rlp_execute` has already been irreversibly scheduled and cannot be rolled back — the two promises (fee transfer and registrar lookup) are independent batches, not chained. Just like the Slingshot bug (`initialBalance` captured before `finalBalance`'s reference point is actually settled, letting an unrelated event desync the diff), the wallet contract commits an irreversible payout based on a snapshot ("this looks like a legitimate transfer worth `tx_fee`") taken before the fact that actually determines correctness (the registrar check) is known.

### Impact Explanation
The user's ETH-implicit wallet account loses `tx_fee` yoctoNEAR to the relayer even though the corresponding action is rejected/never executed. This is a direct, unrecoverable loss of the wallet owner's funds triggered by a normal validation-failure path (concurrent registration of the target account, or a relayer's incorrect `target` choice), not requiring any privileged or malicious network behavior — the relayer is an ordinary, potentially even honest but out-of-date, caller using a restricted `FunctionCallPermission` access key intended only to relay signed user transactions (per NEP-518 meta-tx model).

### Likelihood Explanation
This path is reachable by any user of an ETH-implicit account whose relayer submits a base-token transfer to a `target` that turns out to be (or becomes) a registered named account by the time the registrar lookup resolves — a legitimate race condition given the registrar mapping can change between when a relayer builds a transaction and when it executes on-chain, and no special privileges are needed to trigger it (any relayer that possesses the standard `rlp_execute`-only access key can hit it, intentionally or not).

### Recommendation
Delay the relayer fee payment until after the address-check callback confirms the target is valid (i.e., move the `promise_batch_action_transfer` for `tx_fee` into `address_check_callback`'s success branch, chained after the registrar lookup, mirroring how `caller_deposit` refunds are only issued after the outcome of the dependent promise is known in `rlp_execute_callback`).

### Proof of Concept
1. Relayer holds a `FunctionCallPermission` access key on an ETH-implicit wallet contract, scoped to `rlp_execute` (standard onboarding flow, see `docs/DataStructures/Account.md` "Wallet Contract" section).
2. User signs an Ethereum-style transaction meant as a base-token transfer to an address that is not currently a registered named account, and includes a non-zero `max_fee_per_gas` (i.e., non-zero `tx_fee`).
3. Relayer calls `rlp_execute(target, tx_bytes_b64)` with a `target` account ID hashing to that address; `parse_rlp_tx_to_action` classifies this as `EthEmulationKind::EOABaseTokenTransfer { address_check: Some(address), fee: tx_fee }`.
4. `inner_rlp_execute` immediately schedules the `tx_fee` transfer to the relayer (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:374-385`) and separately kicks off the registrar lookup promise.
5. Before that receipt resolves, the target address becomes registered to a real named account (e.g., another user claims that same address via the registrar) — or the relayer simply picked a `target` incorrectly.
6. `address_check_callback` receives `Some(account_id)` and returns a failure/ban response (`lib.rs:160-192`); the user's intended transfer never happens and the nonce is not consumed for the failed attempt.
7. The wallet account's balance is nonetheless permanently reduced by `tx_fee`, which was already sent to the relayer in step 4 and cannot be reclaimed.
