### Title
CREATE2's failure path leaves the pre-Osaka RETURNDATA buffer unreset, letting a contract read stale return data as if it belonged to the failed CREATE2 - (File: `actuator/src/main/java/org/tron/core/vm/program/Program.java`)

### Summary
`Program.createContract2()` (the `CREATE2` opcode handler) only resets `returnDataBuffer` before executing the sub-call when `VMConfig.allowTvmOsaka()` is enabled: [1](#0-0) 

By contrast, the sibling opcodes `CREATE` and precompile calls unconditionally clear it first: `createContract()` at [2](#0-1)  and `callToPrecompiledAddress()` at [3](#0-2) . On a genuine exception path inside `createContractImpl` (e.g. `createResult.getException() != null`), the method pushes zero and returns immediately **without** setting `returnDataBuffer`: [4](#0-3) . When the Osaka reset is not active (feature not enabled), this leaves whatever `returnDataBuffer` was populated by the *previous* opcode (a prior `CALL`, `CALLCODE`, `DELEGATECALL`, `STATICCALL`, or precompile invocation) still readable via `RETURNDATASIZE`/`RETURNDATACOPY`, even though a new `CREATE2` was just attempted and failed.

### Finding Description
`RETURNDATASIZE`/`RETURNDATACOPY` read directly from `returnDataBuffer` through `getReturnDataBufferSizeI()`/`getReturnDataBufferData()`: [5](#0-4) . Per EVM semantics, every `CREATE`/`CREATE2`/`CALL*` should reset the return-data buffer before executing so the buffer always reflects the outcome of the *most recent* external interaction. `Program.java`'s own regression test acknowledges this was a real, previously-shipped divergence: `TvmIssueVerifierTest.verifyTvmOsakaFixesWithSolidity()` explicitly checks that "failed CREATE2 keeps the previous 32-byte return data buffer" pre-Osaka and only "clears the previous return data buffer after Osaka": [6](#0-5) . This confirms the vulnerable, non-conformant behavior is present and reachable whenever the Osaka hardfork switch is off (i.e., before/unless `allowTvmOsaka` is activated on the network), which is the analog of an "uninitialized/stale buffer" being exposed to a reader that expects fresh data — the buffer is not (re)initialized for the new operation, so a downstream `RETURNDATACOPY` call surfaces content belonging to a logically unrelated prior interaction.

### Impact Explanation
Smart contracts commonly gate security-critical logic (fund release, minting, access checks) on `RETURNDATASIZE`/`RETURNDATACOPY` immediately following a `CREATE2` to validate/consume constructor output or detect deployment failure. If `CREATE2` fails via the exception branch, the stale buffer from an unrelated earlier call can be misinterpreted by the contract's control flow as belonging to the just-attempted `CREATE2`, causing incorrect branching. Depending on the deployed contract's logic (e.g., a factory that trusts `RETURNDATA` after CREATE2 to decide whether to transfer funds or record a deployment as successful), this state confusion can lead to funds being moved or accounted incorrectly, satisfying the "unauthorized account operation / unbacked balance" impact bar. It is also a consensus-semantics bug: any contract whose behavior differs between "correct" (Osaka) and "buggy" (pre-Osaka) RETURNDATA state could produce diverging execution results depending on activation status, which is a correctness/consensus-relevant defect in the TVM.

### Likelihood Explanation
Any unprivileged account can deploy a contract that performs `CALL`/`STATICCALL` (populating `returnDataBuffer`) followed by a `CREATE2` designed to fail (e.g., colliding address, out-of-energy inside the init code, invalid EOF), and then execute `RETURNDATACOPY` to observe/act on the stale buffer — fully reachable through a single signed transaction/contract call with no special privileges. The behavior is deterministically triggerable and depends only on `allowTvmOsaka` not yet being enabled on the target chain.

### Recommendation
Make the `returnDataBuffer = null` reset in `createContract2()` unconditional (matching `createContract()` and `callToPrecompiledAddress()`), independent of `VMConfig.allowTvmOsaka()`, so RETURNDATA state is always reinitialized before a `CREATE2` attempt regardless of hardfork flag status. If backward-compatibility for un-upgraded chains is required, ensure the fix is retroactively backported/activated rather than gated behind a future-only hardfork switch.

### Proof of Concept
1. Deploy contract `V` with two entry points:
   - `probe()`: performs a `STATICCALL` to any contract/precompile that returns non-empty data (populating `returnDataBuffer`), then attempts a `CREATE2` with init code guaranteed to revert/except (e.g., deploying to an address that already has code, or init code that runs out of gas), then executes `RETURNDATASIZE`/`RETURNDATACOPY` and returns the result.
2. With `allowTvmOsaka` disabled (default/pre-activation), call `probe()`; observe that `RETURNDATASIZE` reflects the earlier `STATICCALL`'s data rather than 0/empty as expected for a failed `CREATE2`, matching the assertions in `TvmIssueVerifierTest.verifyTvmOsakaFixesWithSolidity()` (lines 108-116) where `create2Return` word[2] equals 32 (stale) instead of 0.
3. With `allowTvmOsaka` enabled, repeat the same call and observe `RETURNDATASIZE` correctly resets to 0, confirming the divergence is tied specifically to the conditional reset at [7](#0-6) .

  private int getReturnDataBufferSizeI() {
    return returnDataBuffer == null ? 0 : returnDataBuffer.length;
  }

  public byte[] getReturnDataBufferData(DataWord off, DataWord size) {
    if ((long) off.intValueSafe() + size.intValueSafe() > getReturnDataBufferSizeI()) {
      return null;
    }
    return returnDataBuffer == null ? new byte[0] :
        Arrays.copyOfRange(returnDataBuffer, off.intValueSafe(),

  }
