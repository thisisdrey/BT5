Audit Report

## Title
System precompile (`0x900`) is missing the `PrecompileDelegateDenied` delegatecall guard applied to every other caller-sensitive precompile - (File: `substrate/frame/revive/src/precompiles/builtin/system.rs`)

## Summary
`System::call` in `substrate/frame/revive/src/precompiles/builtin/system.rs` handles `callerIsOrigin`, `callerIsRoot`, and `ownCodeHash` by deriving identity from `env.caller()` / `caller_is_origin()` / `caller_is_root()`, without any `is_delegate_call()` check [1](#0-0) . `Stack::caller()` explicitly returns the *original delegating caller* (`DelegateInfo.caller`) rather than the immediate calling contract when the current frame is a delegate-call frame [2](#0-1) . This is the exact same bug class that was already identified and fixed via `PrecompileDelegateDenied` for the assets, asset-conversion, XCM, and vesting precompiles [3](#0-2) [4](#0-3) , and enforced in the opposite direction by the Storage precompile [5](#0-4) , but was never applied to System.

## Finding Description
The `PrecompileDelegateDenied` pattern exists precisely because delegatecall preserves the storage/execution context of the calling contract but the precompile's caller-derived checks resolve to the *original* external caller instead of the immediate delegating contract — as documented in the fix rationale for `PR 11715`: "The precompiles derive caller identity from `env.caller()`, which during delegatecall returns the original caller — letting the intermediary contract act on the caller's assets or send XCM on their behalf" [6](#0-5) . This rationale generically applies to any precompile that consumes `env.caller()`, `env.caller_is_origin()`, or `env.caller_is_root()`.

The System precompile's `callerIsOrigin`, `callerIsRoot`, and `ownCodeHash` handlers all consume these caller-derived primitives with no delegatecall guard anywhere in `System::call` [7](#0-6) . The root cause is confirmed at the engine level: `Stack::caller()` returns `DelegateInfo.caller` (the original delegating caller) whenever the top frame is a delegate-call frame [2](#0-1) . No existing guard in `system.rs` mitigates this: the only check present is a read-only guard on `terminate` [8](#0-7) , which does not address delegate-call framing for any of the identity-sensitive branches.

Regarding the `terminate` sub-case specifically: I was unable to retrieve the implementation of `terminate_caller` in `substrate/frame/revive/src/exec.rs` within the available tool budget to confirm or rule out an independent delegate-call guard at that layer, despite the presence of a related guard string in `substrate/frame/revive/src/tests/sol/terminate.rs`. This remains unverified and should not be treated as conclusively exploitable without further investigation. The `callerIsOrigin`/`callerIsRoot`/`ownCodeHash` identity-leak sub-case, however, is directly confirmed by the code cited above with no such caveat.

## Impact Explanation
A contract that delegatecalls to `0x900` can obtain `callerIsRoot()`/`callerIsOrigin()`/`ownCodeHash()` results describing the *original* external caller rather than itself. Any downstream contract logic that gates privileged behavior on these results (e.g., trusting `callerIsRoot()` as an authorization check, or `ownCodeHash()` as a self-identity attestation) can be tricked by an intermediary contract into granting privileges or attestations that belong to a different, more-privileged account. This matches the "unauthorized execution or origin escalation" impact category in the Polkadot SDK Impact Gate, since the effective origin/identity observed by consuming logic is corrupted relative to the true immediate caller.

## Likelihood Explanation
Exploitability requires only an unprivileged contract deployer crafting a delegatecall from an arbitrary contract to the fixed precompile address `0x900` — no privileged actor, governance, or off-chain compromise is needed. This is directly reachable via ordinary contract calls, consistent with the codebase's own established exploit pattern (`Caller.sol`-style intermediary used in the XCM/vesting/assets precompile delegatecall tests).

## Recommendation
Add the same `PrecompileDelegateDenied` guard used in the assets, asset-conversion, XCM, and vesting precompiles to the top of `System::call` in `substrate/frame/revive/src/precompiles/builtin/system.rs`, rejecting delegate-call invocation before dispatching to any caller-identity-consuming branch (`callerIsOrigin`, `callerIsRoot`, `ownCodeHash`), mirroring `polkadot/xcm/pallet-xcm/precompiles/src/lib.rs` lines 73-81. Separately verify whether `terminate_caller` in `exec.rs` independently guards against delegate-call framing; if not, extend the guard to cover `terminate` as well. Add a `delegatecall_is_rejected` regression test mirroring the existing tests in the assets/asset-conversion/XCM/vesting precompile suites.

## Proof of Concept
1. Deploy an intermediary contract exposing `delegateCall(address callee, bytes data, uint64 gas)`, as used in `polkadot/xcm/pallet-xcm/precompiles/src/tests.rs` (lines 757-819 per the report).
2. From this contract, delegatecall to `0x0000...0900` invoking `callerIsRoot()` or `ownCodeHash()`.
3. Because `Stack::caller()` resolves to the original external caller under delegate-call framing [9](#0-8) , the intermediary contract obtains identity/root attestations belonging to the original caller rather than itself, which any consuming contract trusting System's precompile output for authorization would incorrectly honor.
