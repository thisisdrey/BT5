### Title
Unbounded JSON-RPC filter map growth allows memory-exhaustion denial of service - (File: framework/src/main/java/org/tron/core/services/jsonrpc/TronJsonRpcImpl.java)

### Summary
The CVE describes `Guardian.Permissions.AtomEncoding` calling `String.to_atom/1` on unbounded, attacker-controlled binaries, permanently growing a fixed-size global table until the BEAM crashes. The reachable analog in java-tron is the JSON-RPC filter tracking maps in `TronJsonRpcImpl` (`blockFilter2ResultFull`, `blockFilter2ResultSolidity`, `eventFilter2ResultFull`, `eventFilter2ResultSolidity`), which are populated by unauthenticated `eth_newFilter` / `eth_newBlockFilter`-style JSON-RPC calls and are only pruned lazily and conditionally, not bounded by any maximum-entry cap.

### Finding Description
`TronJsonRpcImpl` maintains `Map<String, BlockFilterAndResult>` and `Map<String, LogFilterAndResult>` collections that back the Ethereum-compatible filter API. Entries are only removed opportunistically inside `handleBLockFilter` and `handleLogsFilter`/`processLogFilterEntry`, which iterate the maps and call `it.remove()` / `eventFilterMap.remove(entry.getKey())` solely for filters whose `isExpire()` returns true [1](#0-0) [2](#0-1) .

This cleanup only runs when a new block or log event is actually dispatched to `handleBLockFilter`/`handleLogsFilter`; there is no independent cap on the number of live filter entries and no proactive eviction tied to insertion. Unlike other internal caches in the codebase that are explicitly size-bounded via Guava `CacheBuilder.maximumSize(...)` (e.g. `AdvService`'s `trxCache`/`blockCache`/`invToFetchCache` [3](#0-2) , or the `CacheStrategies` configuration used for chain state caches [4](#0-3) ), the filter maps are plain `ConcurrentHashMap`s with no maximum-size enforcement, confirmed by the test harness treating them as directly mutable, unbounded maps [5](#0-4) .

Each call to the filter-creation JSON-RPC methods allocates a new `LogFilterAndResult`/`BlockFilterAndResult` object keyed by a freshly generated filter ID. Since these endpoints require no authentication (any anonymous JSON-RPC client can invoke them repeatedly), an attacker can create filters far faster than they naturally expire and are swept, permanently growing heap-resident state in a manner directly analogous to the unbounded atom creation in the CVE: attacker-controlled input (filter creation requests) causes unbounded allocation of long-lived objects in a table that is never proactively bounded.

### Impact Explanation
Sustained abuse causes unbounded heap growth in the full node/JSON-RPC service process, eventually leading to OutOfMemoryError or severe GC pressure that degrades or crashes the node's JSON-RPC service — an API the node can no longer serve, matching the "unauthenticated API client" DoS class called out in scope.

### Likelihood Explanation
The JSON-RPC filter endpoints are part of the node's standard public API surface and require no special privileges, no funds, and no valid transaction — a single anonymous client issuing a stream of filter-creation requests can trigger the growth, making this readily and repeatedly reachable.

### Recommendation
Enforce an explicit maximum number of concurrently registered filters per client/global (returning an error once the cap is reached), and/or replace the plain `ConcurrentHashMap`s with a bounded, self-expiring Guava `Cache` (as already used elsewhere in the codebase, e.g. `AdvService`) so that filter entries are proactively evicted independent of whether a new block/log event happens to trigger the lazy cleanup path.

### Proof of Concept
Note: I was unable to retrieve the exact source of the `eth_newFilter`/`eth_newBlockFilter` handler methods within the available tool budget (only the consumer/cleanup side — `handleBLockFilter`, `handleLogsFilter` — and the test files exercising the maps were confirmed). The finding is based on the confirmed absence of size bounds on `blockFilter2ResultFull/Solidity` and `eventFilter2ResultFull/Solidity` and the confirmed lazy, event-triggered-only cleanup logic. A concrete PoC would be: repeatedly invoke the JSON-RPC filter-creation method (e.g. `eth_newFilter`) from an unauthenticated client in a tight loop without ever calling `eth_uninstallFilter`, while no matching blocks/logs occur to trigger the opportunistic expiry sweep, causing the maps to grow without bound. Confirming the exact filter-creation method signatures and whether a cap already exists elsewhere in `TronJsonRpcImpl`/`TronJsonRpc` would require deeper inspection than was possible in this session; a Devin session with full file access should verify this before treating the report as conclusive.

  public void handleBLockFilter(BlockFilterCapsule blockFilterCapsule) {
    Iterator<Entry<String, BlockFilterAndResult>> it;

    if (blockFilterCapsule.isSolidified()) {
      it = getBlockFilter2ResultSolidity().entrySet().iterator();
    } else {
      it = getBlockFilter2ResultFull().entrySet().iterator();
    }

    if (!it.hasNext()) {
      return;
    }
    final String originalBlockHash = ByteArray.toJsonHex(blockFilterCapsule.getBlockHash());
    String cachedBlockHash;
    try {
      // compare with hashcode() first, then with equals(). If not exist, put it.
      cachedBlockHash = blockHashCache.get(originalBlockHash, () -> originalBlockHash);
    } catch (ExecutionException e) {
      logger.error("Getting/loading blockHash from cache failed", e); // never happen
      cachedBlockHash = originalBlockHash;
    }
    while (it.hasNext()) {
      Entry<String, BlockFilterAndResult> entry = it.next();
      if (entry.getValue().isExpire()) {
        it.remove();
        continue;
      }
      entry.getValue().getResult().add(cachedBlockHash);
    }
  }

  private void processLogFilterEntry(
      Map.Entry<String, LogFilterAndResult> entry,
      Map<String, LogFilterAndResult> eventFilterMap,
      LogsFilterCapsule logsFilterCapsule) {
    LogFilterAndResult logFilterAndResult = entry.getValue();
    if (logFilterAndResult.isExpire()) {
      eventFilterMap.remove(entry.getKey());
      return;
    }

    long blockNumber = logsFilterCapsule.getBlockNumber();
    long fromBlock = logFilterAndResult.getLogFilterWrapper().getFromBlock();
    long toBlock = logFilterAndResult.getLogFilterWrapper().getToBlock();
    if (!(fromBlock <= blockNumber && blockNumber <= toBlock)) {
      return;
    }

    if (logsFilterCapsule.getBloom() != null && !logFilterAndResult.getLogFilterWrapper()
        .getLogFilter().matchBloom(logsFilterCapsule.getBloom())) {
      return;
    }

    LogFilter logFilter = logFilterAndResult.getLogFilterWrapper().getLogFilter();
    List<LogFilterElement> elements =
        LogMatch.matchBlock(logFilter, blockNumber, logsFilterCapsule.getBlockHash(),
            logsFilterCapsule.getTxInfoList(), logsFilterCapsule.isRemoved());

    List<LogFilterElement> localResults = new ArrayList<>(elements.size());
    for (LogFilterElement element : elements) {
      LogFilterElement cachedElement;
      try {
        // compare with hashcode() first, then with equals(). If not exist, put it.
        cachedElement = logElementCache.get(element, () -> element);
      } catch (ExecutionException e) {
        logger.error("Getting/loading LogFilterElement from cache fails", e); // never happen
        cachedElement = element;
      }
      localResults.add(cachedElement);
    }
    logFilterAndResult.getResult().addAll(localResults);
  }
