### Title
Heap buffer over-read in ZIP central-directory extra-field parsing - (File: `third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` in the `ijar` ZIP/JAR reader parses each central-directory entry's "extra field" block by iterating over a series of `(header_id, data_size)` pairs and advancing a raw pointer `extra_p` by attacker-controlled `data_size`, with no bound check that `extra_p` stays inside the entry's own `extra_field_length` region, nor inside the mapped input file at all. A crafted `.zip`/`.jar` (as consumed by `http_archive`/`http_jar`, `java_import`, or any rule that runs `ijar`/`singlejar`-family tooling on a downloaded archive) can drive this pointer past the end of the mmap'd file, causing a heap/mmap buffer over-read that can corrupt derived offsets (`compressed_size`, `uncompressed_size`, `local_header_offset`) with adjacent memory content, which can crash the process or leak process memory content into the entry offsets used for subsequent reads.

### Finding Description
`ProcessCentralDirEntry` reads `file_name_length` and `extra_field_length` straight from the central directory header, computes `extra_p = p` and `p += extra_field_length`, and then loops: [1](#0-0) 

Inside the loop it does:
```
while (extra_p != p) {
  const u2 header_id = get_u2le(extra_p);
  const u2 data_size = get_u2le(extra_p);
  const u1 *extra = extra_p;
  extra_p += data_size;
  ...
}
```
There is no check that at least 4 bytes remain between `extra_p` and `p` before reading `header_id`/`data_size`, and no check that `extra_p + data_size <= p`. If a malicious extra-field entry declares a `data_size` that overshoots the end of the extra-field region (`p`), `extra_p` moves past `p`; the loop condition `extra_p != p` remains true and the loop continues dereferencing memory beyond the intended extra-field bounds — and beyond the memory-mapped input file entirely, since nothing here is checked against `input_file_->Length()`. This function is called for every central directory entry both by `InputZipFile::ProcessNext` (via `p = zipdata_in_ + in_offset_ + offset` from the same function) and by `InputZipFile::CalculateOutputLength`: [2](#0-1) [3](#0-2) 

Unlike this code, the structurally similar extra-field walkers in `src/tools/singlejar/output_jar.cc` explicitly bounds-check each extra field against the end of the extra-fields buffer before trusting its `size()`: [4](#0-3) [5](#0-4) 

and a regression test specifically exercises a malformed, oversized extra-field payload to confirm the check fires: [6](#0-5) 

No equivalent bound check exists in `third_party/ijar/zip.cc`'s central-directory extra-field loop, so the same bug class that was hardened against in `singlejar` remains present in `ijar`'s ZIP reader.

### Impact Explanation
`ijar` is Bazel's tool for generating interface JARs from compiled/prebuilt `.jar` inputs used across `java_library`/`java_import` and similar build actions. A `.jar` fetched via `http_jar`/`http_archive` (or committed to an untrusted branch that CI builds) is attacker-controlled content that this parser processes with no filesystem/sandbox mediation of the read — it is a pure in-process pointer walk over the mmap'd file. Overshooting `data_size` moves the read pointer past the process's mapped region, which can (a) crash the build tool (denial of service) or (b) if the OOB bytes happen to be interpretable as a `ZIP64_EXTRA_FIELD_TAG`, cause `get_u8le(extra)` to read further out-of-bounds heap/mmap memory into `*compressed_size`, `*uncompressed_size`, or `*offset`. Since `*offset` is subsequently used unchecked to compute the next local-file-header pointer (`p = zipdata_in_ + in_offset_ + offset`), corrupted offsets stemming from leaked memory content can be used as read pointers for "file data" that is copied into the generated ijar output — an information-disclosure path where adjacent process memory ends up embedded in a build artifact.

### Likelihood Explanation
Any build that consumes a `.jar`/`.zip` from an untrusted/attacker-published source (a malicious or compromised third-party Maven/HTTP artifact referenced via `http_jar`/`http_archive`, or a file on an untrusted branch a CI job builds) and runs it through `ijar`-based interface-jar generation reaches this code path. No special privileges are required — the attacker only needs to control the bytes of the archive being fetched/built. A pinned `sha256`/`integrity` checksum does not prevent this because the checksum only verifies that the fetched bytes match what was declared, not that the declared/malicious content itself is well-formed; the attacker (as origin publisher) controls both the malicious bytes and their matching digest.

### Recommendation
In `third_party/ijar/zip.cc::InputZipFile::ProcessCentralDirEntry`, bound-check the extra-field walk the same way `output_jar.cc` does: before reading `header_id`/`data_size`, verify at least 4 bytes remain between `extra_p` and the extra-field end (`p`), and after computing `data_size`, verify `extra_p + data_size <= p` before advancing or dereferencing `extra`. Reject the entry (return `false`/error) instead of continuing the loop on an inconsistent extra-field length. Consider also validating parsed sizes/offsets against `input_file_->Length()` before using them to seek elsewhere in the file.

### Proof of Concept
Construct a JAR whose single central-directory entry has `extra_field_length` set to, e.g., 4, but whose 2-byte `data_size` subfield value is set to something large (e.g. `0xFFF0`) so that `extra_p` after `extra_p += data_size` lands past `p` (the extra-field end) yet not exactly equal to it. Feed this file to the `ijar` binary (or any Bazel action that runs `ijar` over a `java_import`-style dependency, e.g. via `http_jar`). Under ASan/valgrind this reproduces as a heap-buffer-overflow read in `ProcessCentralDirEntry`'s extra-field loop; this can be encoded as a `src/test/shell/bazel` regression analogous to `CreateZipWithMalformedExtraField` in `output_jar_simple_test.cc`, but targeting `ijar`'s `zip.cc` reader instead of `singlejar`'s already-hardened `output_jar.cc`.

bool InputZipFile::ProcessNext() {
  // Process the next entry in the central directory. Also make sure that the
  // content pointer is in sync.
  u8 compressed, uncompressed;
  u8 offset;
  if (!ProcessCentralDirEntry(central_dir_current_, &compressed, &uncompressed,
                              filename, PATH_MAX, &attr, &offset)) {
    return false;
  }

  // There might be an offset specified in the central directory that does
  // not match the file offset, so always update our pointer.
  p = zipdata_in_ + in_offset_ + offset;

  if (EnsureRemaining(4, "signature") < 0) {
    return false;
  }
  u4 signature = get_u4le(p);
  if (signature == LOCAL_FILE_HEADER_SIGNATURE) {
    if (ProcessLocalFileEntry(compressed, uncompressed) < 0) {
      return false;
    }
  } else {
    error("local file header signature for file %s not found\n", filename);
    return false;
  }

  return true;
}

std::string CreateZipWithMalformedExtraField() {
  std::string zip_data;
  const std::string filename = "evil.bin";

  // 1. Local File Header (LFH)
  size_t lh_offset = zip_data.size();
  size_t lh_size = sizeof(LH) + filename.size();
  zip_data.resize(lh_offset + lh_size, 0);
  auto* lh = reinterpret_cast<LH*>(&zip_data[lh_offset]);
  lh->signature();
  lh->version(10);
  lh->file_name(filename.data(), filename.size());

  // 2. Extra field payload containing an oversized payload_size
  uint8_t ef_buffer[8] = {0};
  auto* ef1 = reinterpret_cast<ExtraField*>(ef_buffer);
  ef1->signature(0x000d);
  ef1->payload_size(0);

  auto* ef2 = reinterpret_cast<ExtraField*>(ef_buffer + ef1->size());
  ef2->signature(0xdead);
  ef2->payload_size(0xf000);  // Malformed size exceeding extra field buffer

  // 3. Central Directory Header (CDH)
  size_t cdh_offset = zip_data.size();
  size_t cdh_size = sizeof(CDH) + filename.size() + sizeof(ef_buffer);
  zip_data.resize(cdh_offset + cdh_size, 0);
  auto* cdh = reinterpret_cast<CDH*>(&zip_data[cdh_offset]);
  cdh->signature();
  cdh->version(20);
  cdh->version_to_extract(10);
  cdh->local_header_offset32(lh_offset);
  cdh->file_name(filename.data(), filename.size());
  cdh->extra_fields(ef_buffer, sizeof(ef_buffer));

  // 4. End of Central Directory (EOCD)
  size_t ecd_offset = zip_data.size();
  zip_data.resize(ecd_offset + sizeof(ECD), 0);
  auto* ecd = reinterpret_cast<ECD*>(&zip_data[ecd_offset]);
  ecd->signature();
  ecd->this_disk_entries16(1);
  ecd->total_entries16(1);
  ecd->cen_size32(cdh_size);
  ecd->cen_offset32(cdh_offset);

  return zip_data;
}
