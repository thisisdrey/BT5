### Title
Out-of-bounds heap read in ijar's ZIP central-directory extra-field parser - (File: third_party/ijar/zip.cc)

### Summary
`InputZipFile::ProcessCentralDirEntry` in `third_party/ijar/zip.cc` walks the "extra fields" blob of a ZIP Central Directory Header by repeatedly reading a 2-byte header id and a 2-byte data-size field and then advancing the cursor by that attacker-controlled `data_size`, with **no check that the remaining bytes in the extra-field region (or in the mapped file at all) are sufficient** before each read. This mirrors the mptcp bug class in the CVE: a length-driven parsing loop reads a fixed-size record (2+2 bytes) without first verifying that at least that many bytes remain, so a short/malformed length field lets the parser walk past the intended buffer.

### Finding Description
`ProcessCentralDirEntry` reads `file_name_length`, `extra_field_length`, and `file_comment_length` directly from attacker-supplied bytes and then parses the extra-field area purely based on `extra_field_length`, without ever confirming those lengths are consistent with the amount of data actually present in the mapped input file: [1](#0-0) 

The extra-field walking loop is the vulnerable part: [2](#0-1) 

The loop condition is `while (extra_p != p)`, where `p = extra_p_start + extra_field_length`. Each iteration unconditionally calls `get_u2le` twice (4 bytes total) to read `header_id` and `data_size`, then advances `extra_p` by the attacker-controlled `data_size`:
- If `extra_field_length` is 1, 2, or 3 (i.e., too short to contain even one full 4-byte record), the loop still enters and reads 4 bytes — 1–3 bytes past the declared extra-field region — exactly analogous to the mptcp bug reading past a 1-byte TCP option length.
- If `data_size` is crafted so that `extra_p + data_size != p` after advancing, the loop keeps iterating and dereferencing memory past the declared extra-field boundary, and can walk arbitrarily far past the entire mapped file buffer (there's no comparison against `input_file_->Length()` anywhere in this function), unlike `ProcessLocalFileEntry`, which does bound every read with `EnsureRemaining`: [3](#0-2) [4](#0-3) 

Notably, Bazel's sibling tool `singlejar` already hardened the equivalent extra-field walk with an explicit boundary check against the known end pointer of the header (`lh_ef_end`/`ef_end`), and has a regression test for a "malformed extra field" precisely because of this class of bug: [5](#0-4) [6](#0-5) 

`third_party/ijar/zip.cc`'s central-directory parser has no analogous fix.

### Impact Explanation
`ijar` is Bazel's interface-jar generator, run as a build action over jar files that can originate from external, attacker-influenced sources (e.g., a jar fetched via `http_jar`/`http_archive`/Maven dependency resolution, whose bytes the origin/mirror controls). A crafted central-directory entry with an undersized or inconsistent `extra_field_length`/`data_size` causes the parser to read heap memory outside the mapped input buffer. This can:
- Crash the `ijar` action (denial of build), or
- Cause corrupted `header_id`/`data_size` values from adjacent heap memory to be interpreted as a bogus Zip64 extra field, which then overwrites `*uncompressed_size`, `*compressed_size`, or `*offset` with attacker-uncontrolled heap data — subsequently used to compute offsets/sizes for later memory operations on the same mapped buffer, compounding the corruption.

This is a genuine out-of-bounds read of process memory driven entirely by untrusted archive content, not a mocked/local-only or DoS-only condition.

### Likelihood Explanation
Any build that processes an externally-supplied JAR through `ijar` (a very common, largely implicit step in Java rules for compilation-avoidance interface jars) is exposed. An attacker who controls or compromises the origin/mirror serving a jar dependency can trivially construct such a malformed central directory header, since ZIP format allows entirely arbitrary vendor extra-field bytes — no existing check in `ProcessCentralDirEntry` validates them against the file's actual remaining length.

### Recommendation
Add bounds checking in `InputZipFile::ProcessCentralDirEntry`, mirroring the `EnsureRemaining`-style checks already used in `ProcessLocalFileEntry` and the explicit boundary checks in `src/tools/singlejar/output_jar.cc`:
- Validate `file_name_length`, `extra_field_length`, and `file_comment_length` against the number of bytes actually remaining in the mapped input before advancing `p`.
- In the extra-field loop, before each 4-byte header/size read, confirm at least 4 bytes remain within `[extra_p, p)`, and after reading `data_size`, confirm `extra_p + data_size <= p` before advancing, aborting/erroring otherwise (as `output_jar.cc` does with `diag_errx`).

### Proof of Concept
A JUnit/shell reproduction can follow the existing pattern in `output_jar_simple_test.cc`'s `CreateZipWithMalformedExtraField()` (which already demonstrates constructing a ZIP with an oversized/inconsistent extra-field `payload_size` to catch this bug class in singlejar): [7](#0-6) 

An analogous test for `third_party/ijar/zip_test.cc`/`ijar_test.sh` would craft a Central Directory Header where `extra_field_length` is set to 1–3 (or to a value inconsistent with an embedded `data_size`), feed it to `ijar`, and run it under ASan to detect the heap-buffer-overflow read in `ProcessCentralDirEntry`'s extra-field loop, analogous to `test_wrong_centraldir`/`test_corrupted_end_of_centraldir` in `third_party/ijar/test/ijar_test.sh`: [8](#0-7)

  int EnsureRemaining(size_t n, const char *state) {
    size_t in_offset = p - zipdata_in_;
    size_t remaining = input_file_->Length() - in_offset;
    if (n > remaining) {
      return error("Premature end of file (at offset %zd, state=%s); "
                   "expected %zd more bytes but found %zd.\n",
                   in_offset, state, n, remaining);
    }
    return 0;
  }

std::string CreateZipWithMalformedExtraField() {
  std::string zip_data;
  const std::string filename = "evil.bin";

  // 1. Local File Header (LFH)
  size_t lh_offset = zip_data.size();
  size_t lh_size = sizeof(LH) + filename.size();
  zip_data.resize(lh_offset + lh_size, 0);
  auto* lh = reinterpret_cast<LH*>(&zip_data[lh_offset]);
  lh->signature();
  lh->version(10);
  lh->file_name(filename.data(), filename.size());

  // 2. Extra field payload containing an oversized payload_size
  uint8_t ef_buffer[8] = {0};
  auto* ef1 = reinterpret_cast<ExtraField*>(ef_buffer);
  ef1->signature(0x000d);
  ef1->payload_size(0);

  auto* ef2 = reinterpret_cast<ExtraField*>(ef_buffer + ef1->size());
  ef2->signature(0xdead);
  ef2->payload_size(0xf000);  // Malformed size exceeding extra field buffer

  // 3. Central Directory Header (CDH)
  size_t cdh_offset = zip_data.size();
  size_t cdh_size = sizeof(CDH) + filename.size() + sizeof(ef_buffer);
  zip_data.resize(cdh_offset + cdh_size, 0);
  auto* cdh = reinterpret_cast<CDH*>(&zip_data[cdh_offset]);
  cdh->signature();
  cdh->version(20);
  cdh->version_to_extract(10);
  cdh->local_header_offset32(lh_offset);
  cdh->file_name(filename.data(), filename.size());
  cdh->extra_fields(ef_buffer, sizeof(ef_buffer));

  // 4. End of Central Directory (EOCD)
  size_t ecd_offset = zip_data.size();
  zip_data.resize(ecd_offset + sizeof(ECD), 0);
  auto* ecd = reinterpret_cast<ECD*>(&zip_data[ecd_offset]);
  ecd->signature();
  ecd->this_disk_entries16(1);
  ecd->total_entries16(1);
  ecd->cen_size32(cdh_size);
  ecd->cen_offset32(cdh_offset);

  return zip_data;
