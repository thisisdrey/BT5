### Title
Precision loss in `MortgageService.computeReward` (old reward algorithm) causes incorrect voter reward payouts - (File: chainbase/src/main/java/org/tron/core/service/MortgageService.java)

### Summary
The legacy (pre-`NEW_REWARD_ALGORITHM_EFFECTIVE_CYCLE`) per-cycle reward computation in `MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)` performs the classic "divide-then-multiply" pattern using `double` arithmetic instead of computing `userVote * totalReward / totalVote` with a single truncation (e.g. via `BigInteger`/`BigDecimal`), exactly the pattern flagged in the referenced Gitcoin `RoundImplementation.setReadyForPayout` finding.

### Finding Description
In `computeReward`:
```java
double voteRate = (double) userVote / totalVote;
reward += voteRate * totalReward;
``` [2](#0-1) 

`userVote / totalVote` is computed first as a `double`, losing precision before being multiplied by `totalReward`. This differs from the correct order (`userVote * totalReward / totalVote`), and also from the exact `BigInteger` math used elsewhere in the same class for the new reward algorithm:
```java
reward += deltaVi.multiply(BigInteger.valueOf(userVote))
    .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
``` [3](#0-2) 

This legacy `computeReward(cycle, votes)` path is reached from `computeReward(beginCycle, endCycle, accountCapsule)` → `getOldReward(...)` whenever a voter has cycles that predate `newAlgorithmCycle`:
```java
if (beginCycle < newAlgorithmCycle) {
  long oldEndCycle = min(endCycle, newAlgorithmCycle, ...);
  reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
  ...
}
``` [4](#0-3) 

This is invoked by `withdrawReward(address)`/`queryReward(address)`, which are called directly from the `WithdrawBalanceActuator`, an actuator reachable by any unprivileged account broadcasting a `WithdrawBalanceContract` transaction:
```java
mortgageService.withdrawReward(withdrawBalanceContract.getOwnerAddress().toByteArray());
``` [1](#0-0) 

Because `double` has only 52 bits of mantissa, for large `userVote`/`totalVote` values (Tron balances routinely exceed 2^52 sun in aggregate vote counts across many cycles/accounts) the computed `voteRate` is not exact, and summing `voteRate * totalReward` across many votes/cycles accumulates rounding error. Since the individual per-account rewards computed this way are not reconciled against the fixed `totalReward` pool recorded via `delegationStore.addReward`, the sum of all voters' truncated/rounded shares can legitimately diverge from the total reward pool actually funded for that cycle/SR.

### Impact Explanation
Reward accounting drift directly affects fund distribution correctness for staking rewards, a core economic security property of java-tron's DPoS incentive system. Depending on rounding direction, voters can be systematically underpaid (fund freezing of the difference, which is never recoverable because `delegationStore`'s per-cycle reward record isn't decremented/tracked for leftover) or, in aggregate across many small-vote holders splitting votes to exploit favorable rounding, slightly overpaid relative to the actual funded reward — a "theft of dust" pattern common to divide-before-multiply bugs. Because this affects every voter's withdrawal calculation for any cycle prior to `newAlgorithmCycle`, the scope is broad (all historical voting cycles under the legacy algorithm), which is why this class of bug is rated medium severity in the original report as well.

### Likelihood Explanation
This code path is exercised on every `WithdrawBalanceContract` transaction for accounts with pending rewards from cycles under the old algorithm, which is the default/mainnet path unless the chain has already transitioned entirely past `newAlgorithmCycle` for all in-scope cycles. Any account holder who has ever voted can trigger it merely by broadcasting a standard withdraw-balance transaction — no special privileges, precompiles, or malicious-SR behavior required.

### Recommendation
Replace the `double`-based `voteRate` computation with exact integer arithmetic that multiplies before dividing, using `BigInteger`/`BigDecimal` (consistent with the pattern already used in the new-algorithm branch and in `VoteRewardUtil.computeReward`):
```java
reward += BigInteger.valueOf(userVote)
    .multiply(BigInteger.valueOf(totalReward))
    .divide(BigInteger.valueOf(totalVote))
    .longValueExact();
```
This avoids floating-point precision loss and keeps ordering (multiply-then-divide) so that per-account rounding error is minimized to a single truncation, matching the recommendation given in the reference report (use precise fixed-point/BigInteger math rather than floating point division before multiplication).

### Proof of Concept
1. Set up two voters (`totalVote` across the SR for a given cycle) with vote amounts such that `userVote/totalVote` is not exactly representable in binary floating point (e.g. `totalVote = 3`, voters with `userVote = 1` and `userVote = 2`, `totalReward` large, e.g. `10^15`).
2. Call `MortgageService.computeReward(cycle, votes)` (reachable indirectly via `withdrawReward`/`queryReward` triggered by `WithdrawBalanceActuator`) for both voters and sum the results.
3. Compare the sum to `totalReward`: due to the `double` division-then-multiplication, the sum of `voteRate * totalReward` for the two voters will not exactly equal `totalReward`, whereas exact integer math (`userVote * totalReward / totalVote`, summed, plus reconciliation) would show the discrepancy is attributable to `double` truncation rather than to unavoidable integer division remainder (which is bounded and predictable, unlike compounding floating-point error across large-magnitude multiplications).

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
