### Title
Sub-1-TRX unfreeze amounts cause account frozen balance to decrease while global resource weight totals are not updated - (File: `actuator/src/main/java/org/tron/core/actuator/UnfreezeBalanceV2Actuator.java`, `actuator/src/main/java/org/tron/core/vm/nativecontract/UnfreezeBalanceV2Processor.java`)

### Summary
`UnfreezeBalanceV2Actuator.checkUnfreezeBalance` accepts any `unfreezeBalance > 0` up to the frozen amount, with no requirement that the value be an integer multiple of `TRX_PRECISION` (1,000,000 sun). [3](#0-2)  The account's per-user frozen balance (`FrozenV2BalanceForBandwidth`/`Energy`/`TronPower`) is reduced by the exact `unfreezeBalance`, and the amount is queued for withdrawal via `addUnfrozenV2List`. [4](#0-3)  However, the corresponding global weight counter (`totalNetWeight`, `totalEnergyWeight`, `totalTronPowerWeight`) is updated only by the *floor-divided* delta: `oldWeight = frozenBalance / TRX_PRECISION`, `newWeight = (frozenBalance - unfreezeBalance) / TRX_PRECISION`, `addTotalWeight(newWeight - oldWeight)`. [5](#0-4)  When `unfreezeBalance` is smaller than `TRX_PRECISION` and does not cross a whole-TRX boundary, `oldWeight == newWeight`, so the delta is `0` and the global total is left unchanged even though real TRX has been moved out of the account's locked/frozen balance and queued for return via the unfreeze/withdraw flow. The same rounding pattern also appears in `UnfreezeBalanceV2Actuator.updateVote`/`UnfreezeBalanceV2Processor.updateVote`, which recompute vote counts using floating-point division of `vote.getVoteCount() / totalVote * ownedTronPower / TRX_PRECISION`, and in `CancelAllUnfreezeV2Processor.updateFrozenInfoAndTotalResourceWeight`, which follows the identical pattern. [6](#0-5)  This mirrors the JOJO bug class: a state-changing operation whose bookkeeping delta is computed via integer division can silently round to zero for small enough operand values, decoupling the "recorded" quantity from the "actually transferred/moved" quantity.

### Finding Description
The bug class from the report is: an accounting delta computed as `amount / rate` (or similarly, `newBucket - oldBucket` computed from two floor-divisions) can legitimately be `0` for small `amount`, even though a real state change (fund transfer / balance decrement) has genuinely occurred. In JOJO, this caused `t0BorrowBalance` to remain unchanged despite JUSD actually being transferred from the payer.

In java-tron's resource-freezing subsystem, `updateTotalResourceWeight` performs the analogous computation: it derives a "weight" bucket by floor-dividing the frozen balance by `TRX_PRECISION` both before and after the unfreeze, then applies only the difference to the chain-wide `totalNetWeight`/`totalEnergyWeight`/`totalTronPowerWeight`. [2](#0-1)  Because `checkUnfreezeBalance` in the actuator's `validate()` only requires `unfreezeBalance > 0`, there is no lower bound forcing `unfreezeBalance` to be a multiple of `TRX_PRECISION`. [1](#0-0)  An attacker/user can therefore call `UnfreezeBalanceV2Contract` repeatedly with tiny `unfreezeBalance` values (e.g., 1 sun each) that never cross a `TRX_PRECISION` boundary; each call correctly reduces the account's own `FrozenV2Balance...` field (and correctly enqueues the withdrawal amount to be paid back later), but the network-wide weight total used to compute every account's proportional bandwidth/energy limit (`calculateGlobalNetLimit`/`calculateGlobalEnergyLimit`, seen in `BandwidthProcessor`/`EnergyProcessor`) is never decremented for that fraction. Over many such sub-TRX-precision unfreeze calls, the account's real locked TRX shrinks toward zero while the chain's aggregate weight bookkeeping keeps counting a full TRX unit that no longer corresponds to any actually-frozen balance, producing a permanent drift between recorded global resource weight and the sum of underlying frozen balances.

### Impact Explanation
This is an accounting/state-consistency issue rather than direct fund theft: it does not let the attacker steal TRX (the withdrawal amount is still correctly queued and paid via `withdrawExpireAmount`), but it corrupts the `totalNetWeight`/`totalEnergyWeight`/`totalTronPowerWeight` invariant that the entire bandwidth/energy allocation formula depends on (`calculateGlobalNetLimit`, `calculateGlobalEnergyLimit`). A sustained drift inflates other accounts' effective resource limits relative to real backing TRX (since `totalLimit / totalWeight` no longer reflects the true amount of TRX actually locked), which can manifest as free/inflated bandwidth or energy allowance system-wide — an "unbacked" resource-limit condition analogous to unbacked balance issues.

### Likelihood Explanation
Reachable by any signed `UnfreezeBalanceV2Contract` transaction (or the TVM-native equivalent triggering `UnfreezeBalanceV2Processor`) from an unprivileged account — no special permissions are required, and `checkUnfreezeBalance` performs no minimum-precision check. It is repeatable arbitrarily (bounded only by `UNFREEZE_MAX_TIMES = 32` per unfreezing window and standard transaction fees/bandwidth costs), meaning an attacker willing to pay transaction overhead can accumulate drift over time, though the effect per call is bounded to at most `TRX_PRECISION - 1` sun of unaccounted weight.

### Recommendation
Enforce that `unfreezeBalance` values processed by `checkUnfreezeBalance` are always multiples of `TRX_PRECISION` (matching how freeze operations already round to whole-TRX units), or change `updateTotalResourceWeight` to track weight using undivided (sub-TRX) precision internally and only floor-divide at the point of external limit calculation, so that no fractional TRX amount is silently dropped from the global weight total across repeated operations.

### Proof of Concept
1. An account freezes `1,999,999` sun (`FROZEN_BALANCE` just under 2×`TRX_PRECISION`) for BANDWIDTH; `totalNetWeight` is incremented by `1` (`1,999,999 / 1,000,000 = 1`).
2. The account calls `UnfreezeBalanceV2Contract` with `unfreezeBalance = 999,999` sun. `checkUnfreezeBalance` accepts it (`0 < 999,999 <= 1,999,999`). [1](#0-0) 
3. In `updateTotalResourceWeight`, `oldNetWeight = 1,999,999 / 1,000,000 = 1`; after subtracting, `newNetWeight = 1,000,000 / 1,000,000 = 1`. Delta is `0`, so `totalNetWeight` is unchanged, even though `999,999` sun of real frozen TRX has been moved into the pending-unfreeze/withdrawal queue. [7](#0-6) 
4. Repeating such sub-`TRX_PRECISION` unfreezes accumulates unaccounted weight drift in the global `totalNetWeight`/`totalEnergyWeight`/`totalTronPowerWeight`, which is used unconditionally by `calculateGlobalNetLimit`/`calculateGlobalEnergyLimit` for every account's resource-limit calculation.

  public boolean checkUnfreezeBalance(AccountCapsule accountCapsule,
                                      final UnfreezeBalanceV2Contract unfreezeBalanceV2Contract,
                                      ResourceCode freezeType) {
    boolean checkOk = false;

    long frozenAmount = 0L;
    List<FreezeV2> freezeV2List = accountCapsule.getFrozenV2List();
    for (FreezeV2 freezeV2 : freezeV2List) {
      if (freezeV2.getType().equals(freezeType)) {
        frozenAmount = freezeV2.getAmount();
        break;
      }
    }

    if (unfreezeBalanceV2Contract.getUnfreezeBalance() > 0
        && unfreezeBalanceV2Contract.getUnfreezeBalance() <= frozenAmount) {
      checkOk = true;
    }

    return checkOk;
  }

  public void updateTotalResourceWeight(AccountCapsule accountCapsule,
                                        Common.ResourceCode freezeType,
                                        long unfreezeBalance,
                                        Repository repo) {
    switch (freezeType) {
      case BANDWIDTH:
        long oldNetWeight = accountCapsule.getFrozenV2BalanceWithDelegated(BANDWIDTH) / TRX_PRECISION;
        accountCapsule.addFrozenBalanceForBandwidthV2(-unfreezeBalance);
        long newNetWeight = accountCapsule.getFrozenV2BalanceWithDelegated(BANDWIDTH) / TRX_PRECISION;

        break;
