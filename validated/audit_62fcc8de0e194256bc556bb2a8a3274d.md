### Title
Heap-buffer-overflow while parsing ZIP "extra field" (side-data) in `InputZipFile::ProcessCentralDirEntry` — (`third_party/ijar/zip.cc`)

### Summary
`third_party/ijar` (`zip.cc`) is Bazel's own C++ ZIP/JAR reader, used to build interface jars from `.jar`/`.zip` inputs that can originate from externally-fetched artifacts (e.g. `http_jar`, `http_archive` of type `jar`, or jars vendored into a repository that Bazel later processes). Unlike its sibling parser in `src/tools/singlejar/zip_headers.h`, the central-directory "extra field" parsing loop in `zip.cc` performs no bounds checking against the buffer/file boundary, mirroring the exact bug class in the referenced GPAC CVE (`ffdmx_parse_side_data`): unchecked, attacker-controlled length fields drive a byte-cursor past the end of the mapped input, producing an out-of-bounds heap read.

### Finding Description
`InputZipFile::ProcessCentralDirEntry` reads `file_name_length`, `extra_field_length`, and `file_comment_length` directly from the (attacker-supplied) central directory record with no call to `EnsureRemaining`, unlike `ProcessLocalFileEntry`, which validates every variable-length field against the mapped file length before advancing the cursor: [1](#0-0) [2](#0-1) 

In contrast, `ProcessCentralDirEntry` blindly trusts the lengths taken straight from the record and then walks a nested "extra field" loop using an attacker-controlled `data_size` with no per-field or overall-remaining check: [3](#0-2) 

Specifically:
- `extra_field_length` sets `p = extra_p + extra_field_length` as the loop terminator, but the inner `while (extra_p != p)` loop reads a 2-byte `header_id` and 2-byte `data_size`, then advances `extra_p += data_size`. If `data_size` (fully attacker controlled, up to 0xFFFF) causes `extra_p` to overshoot `p` (e.g., an odd/malformed `extra_field_length`, or a `data_size` value not aligned with the declared field boundary), the loop condition `extra_p != p` remains true, and the loop continues reading `header_id`/`data_size` (and potentially `get_u8le`) from memory beyond the intended extra-field region — with no check against the file's mapped length at all.
- This is functionally the same class of bug already fixed in the sibling singlejar implementation: `zip_headers.h`'s `ExtraField::find` explicitly checks `byte_ptr(start) + sizeof(ExtraField) > byte_ptr(end)` and `byte_ptr(start) + extra_field->size() > byte_ptr(end)` before dereferencing, and `output_jar.cc` performs equivalent bounds checks with `diag_errx(1, "malformed extra field...")`: [4](#0-3) [5](#0-4) 

`ijar`'s `zip.cc` has no analogous guard for this loop, so a crafted extra field (or an inconsistent `extra_field_length`/inner `data_size`) drives `extra_p` past the mapped input buffer end, and subsequent `get_u2le`/`get_u8le` calls dereference out-of-bounds heap memory — a read primitive directly analogous to the GPAC `ffdmx_parse_side_data` heap-buffer-overflow.

### Impact Explanation
An attacker who publishes a malicious jar/zip artifact that a victim's build fetches (via `http_jar`, `http_archive`, or a `java_import`-style external jar dependency later processed for interface-jar generation) can trigger an out-of-bounds heap read inside the Bazel-controlled `ijar` binary during a normal build action. This is a memory-safety violation reachable purely from untrusted content the build consumes — not a sandbox escape, not a third-party CVE, and not simply resource exhaustion. Depending on heap layout, this can crash the build (denial of a single action) or leak adjacent heap bytes into subsequently parsed fields (filename buffer, attribute fields) that influence generated interface-jar content.

### Likelihood Explanation
This code path executes on every ZIP/JAR file processed by `ijar` when reading the central directory, and the vulnerable loop is trivial to trigger: a jar with any extra field whose declared per-record `data_size` doesn't line up with the declared `extra_field_length` (or the reverse) will run the `while (extra_p != p)` loop out of its intended bounds. Because the sha256/integrity check on the download only pins content the attacker themselves chooses (an attacker can construct the malicious jar and publish its correct hash from the start), checksum verification does not stop this — it only guarantees the fetched bytes match what the attacker published, not that those bytes are well-formed.

### Recommendation
Add the same bounds validation used in `src/tools/singlejar/zip_headers.h`/`output_jar.cc` to `InputZipFile::ProcessCentralDirEntry` in `third_party/ijar/zip.cc`:
- Validate `file_name_length + extra_field_length + file_comment_length` (and the base fixed-size header) against `EnsureRemaining`/the mapped file length before advancing `p`.
- In the extra-field loop, check that at least 4 bytes remain between `extra_p` and the field boundary before reading `header_id`/`data_size`, and that `extra_p + data_size` does not exceed the field boundary; abort with an error (matching the `diag_errx(1, "malformed extra field...")` pattern) instead of continuing to read.

### Proof of Concept
A reproducible proof would follow the pattern already used for the singlejar regression test `OutputJarSimpleTest.MalformedExtraField` (`src/tools/singlejar/output_jar_simple_test.cc:1179-1236`), but targeting `ijar`'s `zip.cc`:
1. Construct a minimal ZIP with one central directory entry whose `extra_field_length` is small (e.g., 1) but whose embedded extra-field `data_size` value is large/misaligned so that `extra_p` overshoots `p` inside the `while (extra_p != p)` loop.
2. Feed this file to the `ijar` binary (or invoke `InputZipFile::ProcessCentralDirEntry` directly in a unit test analogous to `zip_headers_test.cc`).
3. Run under ASan; observe a heap-buffer-overflow read when `get_u2le`/`get_u8le` dereference memory past the mapped input's end, in contrast to the sibling singlejar path which already asserts (`ASSERT_DEATH(..., "malformed extra field")`) on the equivalent malformed input. [6](#0-5)

std::string CreateZipWithMalformedExtraField() {
  std::string zip_data;
  const std::string filename = "evil.bin";

  // 1. Local File Header (LFH)
  size_t lh_offset = zip_data.size();
  size_t lh_size = sizeof(LH) + filename.size();
  zip_data.resize(lh_offset + lh_size, 0);
  auto* lh = reinterpret_cast<LH*>(&zip_data[lh_offset]);
  lh->signature();
  lh->version(10);
  lh->file_name(filename.data(), filename.size());

  // 2. Extra field payload containing an oversized payload_size
  uint8_t ef_buffer[8] = {0};
  auto* ef1 = reinterpret_cast<ExtraField*>(ef_buffer);
  ef1->signature(0x000d);
  ef1->payload_size(0);

  auto* ef2 = reinterpret_cast<ExtraField*>(ef_buffer + ef1->size());
  ef2->signature(0xdead);
  ef2->payload_size(0xf000);  // Malformed size exceeding extra field buffer

  // 3. Central Directory Header (CDH)
  size_t cdh_offset = zip_data.size();
  size_t cdh_size = sizeof(CDH) + filename.size() + sizeof(ef_buffer);
  zip_data.resize(cdh_offset + cdh_size, 0);
  auto* cdh = reinterpret_cast<CDH*>(&zip_data[cdh_offset]);
  cdh->signature();
  cdh->version(20);
  cdh->version_to_extract(10);
  cdh->local_header_offset32(lh_offset);
  cdh->file_name(filename.data(), filename.size());
  cdh->extra_fields(ef_buffer, sizeof(ef_buffer));

  // 4. End of Central Directory (EOCD)
  size_t ecd_offset = zip_data.size();
  zip_data.resize(ecd_offset + sizeof(ECD), 0);
  auto* ecd = reinterpret_cast<ECD*>(&zip_data[ecd_offset]);
  ecd->signature();
  ecd->this_disk_entries16(1);
  ecd->total_entries16(1);
  ecd->cen_size32(cdh_size);
  ecd->cen_offset32(cdh_offset);

  return zip_data;
}
