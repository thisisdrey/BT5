### Title
Dust-transfer of deposit tokens fills a victim's `depositTokensOfAccount` list to `MAX_TOKENS_PER_USER`, permanently blocking new deposits, borrows, and liquidations for that account - (File: contracts/DepositToken.sol)

### Summary
`DepositToken._transfer` unconditionally registers the recipient in the pool's per-account token list whenever their balance was zero, and `Pool.addToDepositTokensOfAccount` enforces a hard cap (`MAX_TOKENS_PER_USER`) shared between deposit and debt tokens. An unprivileged attacker can transfer 1 wei of every listed deposit token to a victim, exhausting the cap. Afterwards, any action that would add a *new* token to the victim's account reverts with `UserReachedMaxTokens`, DoS-ing deposits, new-collateral rescue of unhealthy positions, new synthetic mints, and — critically — liquidations that would seize a collateral type the liquidator/victim does not yet hold.

### Finding Description
The vulnerability arises from the interaction of three pieces:

1. `DepositToken._transfer` adds the token to the recipient's account list on any nonzero transfer when `balanceOf[recipient_] == 0`:
```solidity
if (_recipientBalanceBefore == 0 && amount_ > 0) {
    pool.addToDepositTokensOfAccount(recipient_);
}
``` [1](#0-0) 

2. `Pool.addToDepositTokensOfAccount` is gated by `onlyIfAdditionWillNotReachMaxTokens(account_)`, which sums `depositTokensOfAccount.length(account_) + debtTokensOfAccount.length(account_)` and reverts `UserReachedMaxTokens` once the combined count reaches `MAX_TOKENS_PER_USER`: [2](#0-1) 

3. `DepositToken.transfer`/`transferFrom` are public, permissionless, and only require the *sender's* balance to be unlocked — there is no opt-in on the recipient side and no minimum amount: [3](#0-2) 

The same mechanism exists on the debt side via `DebtToken` issue and `addToDebtTokensOfAccount` (Pool.sol:204-208), meaning the shared cap can also be exhausted by pushing new debt positions onto a victim through flash-mint/donation paths, though the deposit-token dust route alone suffices.

Attack sequence:
- Attacker acquires dust amounts (1 wei) of every whitelisted `DepositToken` (via own deposits of each underlying, then `transfer`).
- Attacker calls `depositToken_i.transfer(victim, 1)` for each token until the victim's combined list hits `MAX_TOKENS_PER_USER`. Cost: negligible — the dust can even be re-borrowed against.

### Impact Explanation
- **Deposit DoS**: victim can never `deposit()` any collateral type they don't already hold, because `_mint` → `addToDepositTokensOfAccount` reverts (`DepositToken.sol:486-487`). A victim approaching liquidation cannot top up with a new collateral asset.
- **Borrow DoS**: minting a new `DebtToken` type for the victim likewise reverts.
- **Liquidation DoS / bad debt**: `Pool.liquidate` → `DepositToken.seize` → `_transfer` → `addToDepositTokensOfAccount(to_)`. If the seize beneficiary doesn't already hold that deposit token type and their list is full, the whole liquidation reverts. An attacker can saturate their own *or* grief a liquidator's list to make a position unliquidatable, forcing the pool to accrue bad debt.
- Removal only happens when a balance returns to zero, so once stuffed, the victim cannot clear entries themselves — the dust sits locked as a minuscule "balance" the victim must withdraw one token at a time; they can self-clean only via `withdraw`, but each withdraw also hits the cap only after removal succeeds, and filling is faster/cheaper than the cleanup in repeated attacks.

### Likelihood Explanation
Fully unprivileged: any EOA with dust collateral can execute. No governor/keeper/oracle required. Gas cost is bounded by the number of whitelisted deposit tokens (small). The deployed configuration confirms the guard exists on live pools (`deployments/*/Pool.json` expose `UserReachedMaxTokens`/`MAX_TOKENS_PER_USER`). Main mitigation in practice is that the victim can still deposit/withdraw the *already-held* token types and can withdraw dust to free slots, so the freeze is temporary and partial — matching a Medium-severity availability/integrity impact analogous to the CVE's integrity/DoS profile.

### Recommendation
- Move the max-tokens check out of `addTo*TokensOfAccount` into user-initiated actions only: allow the account-list `add` to succeed unconditionally (or revert only on `deposit`/`issue`, not on inbound `transfer`/`seize`).
- Alternatively, treat `seize`/liquidation credit as exempt from the cap so liquidations can never be bricked by a saturated recipient list.
- Consider tracking "has balance" via `balanceOf > 0` lookups or a bounded set with automatic eviction of dust balances.

### Proof of Concept
Hardhat/Foundry fork sketch (against a live Pool, e.g. Optimism deployment):

```solidity
// Setup: victim holds only msdA. Attacker deposits dust into each whitelisted
// deposit token D1..Dn to mint 1 wei each.
for (uint i; i < depositTokens.length; ++i) {
    IERC20 underlying = depositTokens[i].underlying();
    deal(address(underlying), attacker, 1e6);
    underlying.approve(address(depositTokens[i]), 1e6);
    depositTokens[i].deposit(1e6, attacker);
    depositTokens[i].transfer(victim, 1); // fills victim's list
}
// victim's combined list is now at MAX_TOKENS_PER_USER.
// Victim tries to deposit a NEW collateral type D_new:
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
depositTokenNew.deposit(1e18, victim);   // reverts in _mint -> addToDepositTokensOfAccount

// Liquidator path: liquidate victim's underwater position, seizing a token
// the liquidator has never held and whose list was dust-filled:
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
pool.liquidate(debtToken, victim, amountToRepay, depositTokenSeized, liquidator);
```

Key assertions in the test: `pool.getDepositTokensOfAccount(victim).length + pool.getDebtTokensOfAccount(victim).length == MAX_TOKENS_PER_USER`, `deposit` reverts, `liquidate` reverts, and the victim's `debtPositionOf` remains unhealthy — demonstrating forced bad debt / frozen account functionality.
