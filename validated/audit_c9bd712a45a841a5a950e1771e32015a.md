Audit Report

## Title
`process_delivery_receipt` in Snowbridge outbound-queue-v2 ignores the on-chain `success` flag, rewarding relayers and clearing pending orders even when the Ethereum-side execution failed - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
`DeliveryReceipt::success`, decoded from the Ethereum `InboundMessageDispatched` event log, is never read inside `process_delivery_receipt`. The function pays the relayer reward and removes the `PendingOrder` unconditionally, regardless of whether the Ethereum-side dispatch actually succeeded or failed. [1](#0-0) [2](#0-1) 

## Finding Description
`DeliveryReceipt` decodes `success: bool` from the raw Ethereum event log `InboundMessageDispatched(nonce, topic, success, reward_address)` via `TryFrom<&Log>`. [3](#0-2) 

The extrinsic `submit_delivery_receipt` verifies the log/proof via `T::Verifier::verify`, decodes the receipt, and forwards it directly to `process_delivery_receipt` with no inspection of `success`: [4](#0-3) 

Inside `process_delivery_receipt`, the code only checks `receipt.gateway` against `T::GatewayAddress::get()`, resolves `reward_account`, fetches `PendingOrder` by `receipt.nonce`, unconditionally pays `order.fee` to the reward account when `order.fee > 0`, removes the order from `PendingOrders`, and emits `MessageDelivered`. `receipt.success` is never read anywhere in this function: [5](#0-4) 

The module doc explicitly frames the delivery-receipt flow as occurring "when the message has been verified and executed," implying an assumption of success that is never actually validated in code: [6](#0-5) 

Because assets are withdrawn/reserved on Asset Hub *before* this receipt is processed (via `WithdrawAsset`/`InitiateTransfer`/`ReserveWithdraw` in the outbound XCM), and no other code path re-examines `success` to trigger a refund, a message whose Ethereum-side dispatch legitimately failed (`success: false`) is treated identically to a successful delivery: the relayer is paid, and the `PendingOrder` bookkeeping for that nonce is permanently destroyed with no recovery path for the underlying assets.

## Impact Explanation
This falls under "duplicate settlement or payout" and "permanent user-fund or bridge-state lock": the pallet settles (rewards relayer, clears pending state) for message nonces that failed on the Ethereum side just as it does for successes, discarding the on-chain success signal that should gate settlement, with no path back to refund or reroute the already-withdrawn source-side assets.

## Likelihood Explanation
This is reachable via the ordinary, unprivileged `submit_delivery_receipt` extrinsic, which only requires `ensure_signed` and a valid Ethereum log/proof passing `T::Verifier::verify` — it does not require malicious relayer behavior, since any relayer submitting a receipt for a legitimately failed dispatch (revert, insufficient gas, destination-side failure) triggers this exact code path deterministically.

## Recommendation
In `process_delivery_receipt`, branch on `receipt.success`. On `true`, keep current behavior. On `false`, avoid rewarding the relayer as if delivery succeeded and avoid destructively removing the `PendingOrder` without first surfacing a distinct failure event and/or driving a refund path for the assets already withdrawn/reserved on Asset Hub for that nonce.

## Proof of Concept
1. On Asset Hub, submit an outbound XCM with `WithdrawAsset` + `InitiateTransfer`/`ReserveWithdraw` targeting Ethereum, generating nonce `n` and inserting `PendingOrder { nonce: n, fee, .. }` via `do_process_message`. [7](#0-6) 
2. Assume the Ethereum Gateway contract execution for nonce `n` reverts, emitting `InboundMessageDispatched(n, topic, success=false, reward_address)`.
3. A relayer calls `submit_delivery_receipt` with a valid proof of that log; `T::Verifier::verify` succeeds and `DeliveryReceipt::try_from` decodes `success: false` correctly.
4. `process_delivery_receipt` still executes the reward payment (if `order.fee > 0`) and calls `<PendingOrders<T>>::remove(nonce)`, emitting `MessageDelivered`, exactly as it would for `success: true`.
5. Result: relayer is paid for a failed delivery, and the nonce's pending-order state is destroyed with no refund path for the assets withdrawn on Asset Hub in step 1.

impl TryFrom<&Log> for DeliveryReceipt {
	type Error = DeliveryReceiptDecodeError;

	fn try_from(log: &Log) -> Result<Self, Self::Error> {
		let topics: Vec<B256> = log.topics.iter().map(|x| B256::from_slice(x.as_ref())).collect();

		let event = InboundMessageDispatched::decode_raw_log_validate(topics, &log.data)

			nonce: event.nonce,
			topic: H256::from_slice(event.topic.as_ref()),
			success: event.success,
			reward_address: event.reward_address.0,

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
