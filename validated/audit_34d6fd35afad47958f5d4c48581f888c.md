Audit Report

## Title
`ERC20Transactor::withdraw_asset_with_surplus`/`deposit_asset_with_surplus` hard-fail on non-standard ERC-20 return data, permanently stranding on-chain-transferred tokens - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

## Summary
`ERC20Transactor` performs the actual on-chain ERC-20 `transfer` call *before* validating its return data, then requires that data to strictly ABI-decode as `bool` via `IERC20::transferCall::abi_decode_returns_validate`. Any ERC-20 contract that succeeds but returns no data (a valid, common real-world token behavior, e.g., original EIP-20 reference style contracts) causes the runtime to report `XcmError::FailedToTransactAsset("ERC20 contract result couldn't decode")` even though the token balance has already moved on-chain, and this asset never enters `AssetsInHolding` to be reclaimed. Because the matcher (`assets_common::ERC20Matcher`) accepts *any* `AccountKey20`-addressed contract with no governance gating, any unprivileged user can deploy such a contract and trigger this permanently.

## Finding Description
In `withdraw_asset_with_surplus`, the transfer is dispatched via `pallet_revive::Pallet::<T>::bare_call` moving tokens from the withdrawing account to the internal `TransfersCheckingAccount` [1](#0-0) . Only after this on-chain transfer executes does the code check `did_revert()` and then require `IERC20::transferCall::abi_decode_returns_validate(&return_value.data)` to succeed as a `bool`; any decode failure returns `Err(XcmError::FailedToTransactAsset(...))` [2](#0-1) . The mirror logic exists in `deposit_asset_with_surplus`, transferring from the checking account to the beneficiary before the same strict decode gate [3](#0-2) .

The matcher wired to this transactor, `assets_common::ERC20Matcher`, is `MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>`, which matches *any* location of the shape `(0, [AccountKey20 { key, .. }])` [4](#0-3) . There is no allowlist or governance registration step — any deployed `pallet-revive` contract address is automatically eligible, as confirmed by the corresponding PRDoc description of this feature [5](#0-4) .

Because the on-chain transfer already succeeded (balance moved to/from the checking account) by the time the decode check runs, a decode failure leaves the runtime and the contract state inconsistent: the XCM instruction returns `Err`, so no credit is ever placed into `AssetsInHolding` (on withdraw) and the assets are returned to the caller for trapping only in the deposit direction, but the withdraw direction has no such recovery path — the tokens are already sitting in `TransfersCheckingAccount` with no accounting linking them back to a claimable holding entry. This exact strict-`bool`-decode pattern is also present elsewhere in the same feature, in `pallet-revive`'s `fungibles::Mutate` impl, where a decode failure on `burn_from`/`mint_into` even triggers `.expect("Failed to ABI decode")` [6](#0-5) , confirming this is a systemic assumption baked into the ERC-20 integration, not an isolated one-off.

## Impact Explanation
Any ERC-20 contract deployed under `pallet-revive` that returns no data on a successful `transfer` (a legitimate, spec-compliant behavior for the original EIP-20 and used by several real deployed tokens) becomes permanently unusable through `ERC20Transactor` for `withdraw_asset`/`deposit_asset`: the withdraw call moves the user's tokens on-chain to `TransfersCheckingAccount` but the XCM instruction fails with `FailedToTransactAsset`, so the holding register never reflects the withdrawn amount and the tokens are stranded in the checking account with no XCM-level path back to the user. This matches the "permanent user-fund or bridge-state lock" category of the impact gate, since it is a genuine on-chain custody/accounting desync caused purely by the transactor's hard-coded decode assumption, not by any admin misconfiguration (the matcher itself is permissionless and requires no registration).

## Likelihood Explanation
No privileged actor, governance action, or malicious peer is required. Because `ERC20Matcher` matches any `AccountKey20`-addressed contract without an allowlist, any unprivileged user can deploy a non-`bool`-returning ERC-20 contract via `pallet-revive` and immediately attempt an XCM `WithdrawAsset`/`DepositAsset` against it, hitting the strict decode failure deterministically and repeatably every time.

## Recommendation
Do not treat an ABI-decode failure of the `transfer` return data as an unconditional failure. Follow the common "safe ERC-20" handling pattern: treat "call succeeded (`!did_revert()`) and either returned no data or decoded `true`" as success, and only treat an explicit decoded `false` or a revert as failure. Additionally, since the on-chain transfer already executes before this check, consider performing a pre-flight simulation/dry-run or otherwise ensuring the decode/interpretation logic cannot diverge from the already-committed on-chain state.

## Proof of Concept
1. Deploy via `pallet-revive` a minimal ERC-20 contract whose `transfer(address,uint256)` correctly updates balances but returns no data (valid per the original EIP-20 spec).
2. Because `assets_common::ERC20Matcher` matches any `AccountKey20` location with no registration step, this contract's address is automatically usable as an asset ID through `ERC20Transactor` on Asset Hub (wired in `cumulus/parachains/runtimes/assets/asset-hub-westend/src/xcm_config.rs`).
3. Submit an XCM program invoking `WithdrawAsset` for this asset from an account holding a balance.
4. Observe: `bare_call` executes the `transfer` successfully (`did_revert() == false`, balance moves to `ERC20TransfersCheckingAccount`), but `IERC20::transferCall::abi_decode_returns_validate(&return_value.data)` fails on the empty return data, causing `withdraw_asset_with_surplus` to return `Err(XcmError::FailedToTransactAsset("ERC20 contract result couldn't decode"))` while the tokens remain moved on-chain with no corresponding `AssetsInHolding` credit.

/// `Contains<Location>` implementation that matches locations with no parents,
/// a `PalletInstance` and an `AccountKey20` junction.
pub struct IsLocalAccountKey20;
impl Contains<Location> for IsLocalAccountKey20 {
	fn contains(location: &Location) -> bool {
		matches!(location.unpack(), (0, [AccountKey20 { .. }]))
	}
}

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {
		Some(Location::new(0, [AccountKey20 { key: (*key).into(), network: None }]))
	}
}

/// [`xcm_executor::traits::MatchesFungibles`] implementation that matches
/// ERC20 tokens.
pub type ERC20Matcher =
	MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>;
