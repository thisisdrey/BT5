### Title
Missing `checkAllowShieldedTransactionApi()` guard in `scanShieldedTRC20NotesByOvk` allows unauthorized shielded-transaction data disclosure - (File: `framework/src/main/java/org/tron/core/Wallet.java`)

### Summary
Every other shielded-note scanning entry point in `Wallet.java` — `scanNoteByIvk`, `scanAndMarkNoteByIvk`, `scanNoteByOvk`, and `scanShieldedTRC20NotesByIvk` — begins by calling `checkAllowShieldedTransactionApi()` to enforce the node-operator's decision on whether the shielded-transaction API surface is enabled. `scanShieldedTRC20NotesByOvk` omits this call entirely, so it remains reachable over gRPC/HTTP even when the node has disabled shielded-transaction APIs.

### Finding Description
`checkAllowShieldedTransactionApi()` is consistently invoked as the first statement in the sibling scan methods: [1](#0-0) [2](#0-1) [3](#0-2) 

By contrast, `scanShieldedTRC20NotesByOvk`'s body (which follows immediately after `scanShieldedTRC20NotesByIvk`) goes straight into range validation and block scanning without any call to `checkAllowShieldedTransactionApi()`: [4](#0-3) 

This method is directly exposed over gRPC (`RpcApiService`) and HTTP (`ScanShieldedTRC20NotesByOvkServlet`), both of which pass the client-supplied `ovk` and contract address straight through to `wallet.scanShieldedTRC20NotesByOvk(...)` with no additional gating: [5](#0-4) 

The `checkAllowShieldedTransactionApi()` flag is the node operator's designated access-control boundary for this entire class of shielded-note-decryption functionality (analogous to GitLab's per-object visibility check that the Search API bypassed for private milestones): any caller who possesses (or brute-forces/derives) an `ovk`/contract-address pair can query and decrypt outgoing shielded TRC20 note plaintext — payment address, value, memo — through this one code path even on nodes where the operator has explicitly turned the shielded API off via configuration, while the identical `Ivk`-based endpoint and the plain (non-TRC20) `Ovk` endpoint correctly honor that same restriction.

### Impact Explanation
On a node configured with `allowShieldedTransactionApi = false` (a legitimate operational/privacy control), an anonymous API client can still invoke `scanShieldedTRC20NotesByOvk` to enumerate and decrypt shielded TRC20 transaction metadata (recipient payment address, amount, memo) that the operator intended to keep unreachable. This is a genuine access-control bypass exposing private transaction metadata, directly matching the CVE's "improper access control" bug class of a bypassed visibility/permission check exposed via a query/search API.

### Likelihood Explanation
High likelihood of exploitation whenever the flag is disabled: no authentication, signing, or special privilege is required — any HTTP/gRPC caller who knows (or is the counterparty to) an `ovk` can call this single endpoint directly, since the method is a straightforward public passthrough with no internal permission logic besides the (missing) flag check.

### Recommendation
Add `checkAllowShieldedTransactionApi();` as the first statement of `scanShieldedTRC20NotesByOvk` in `Wallet.java`, mirroring the guard present in `scanNoteByIvk`, `scanAndMarkNoteByIvk`, `scanNoteByOvk`, and `scanShieldedTRC20NotesByIvk`, so the API-disablement control is uniformly enforced across all shielded-note scan endpoints.

### Proof of Concept
1. Configure a full node with `node.shieldedTransactionApi.enable = false` (or equivalent config disabling `allowShieldedTransactionApi`).
2. Confirm `scannotebyivk`, `scannotebyovk`, and `scanshieldedtrc20notesbyivk` HTTP/gRPC calls are rejected due to `checkAllowShieldedTransactionApi()`.
3. Call `POST /wallet/scanshieldedtrc20notesbyovk` (or the gRPC `ScanShieldedTRC20NotesByOvk` RPC) with a valid `ovk`, `shielded_TRC20_contract_address`, `start_block_index`, `end_block_index`.
4. Observe the call succeeds and returns decrypted `DecryptNotesTRC20` note data (payment address, value, memo) despite the shielded API being disabled — demonstrating the bypass, backed by [4](#0-3)  lacking the guard present in its siblings.
