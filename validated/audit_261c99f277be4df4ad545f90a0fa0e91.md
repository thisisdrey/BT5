### Title
Client-Controlled `GitObjectDirectory`/`GitAlternateObjectDirectories` Fields Spoof "Trusted Rails Access-Check" Origin and Bypass Transaction/Snapshot Scoping - (File: internal/gitaly/storage/storagemgr/middleware.go)

### Summary
`beginTransactionForRepository` in `middleware.go` decides whether an incoming RPC is a legitimate quarantine-scoped access-check loop-back from Rails purely by checking whether the request's `Repository.GitObjectDirectory` / `GitAlternateObjectDirectories` fields are non-empty — both of which are ordinary, client-settable protobuf fields, not authenticated markers. This is structurally the same flaw as the FSDVesting bug: a caller-supplied field is used as a stand-in for verified identity/origin, letting anyone spoof "this came from a trusted internal caller" and skip the security control (transaction/snapshot scoping) that control is supposed to gate.

### Finding Description
`storage.Repository.GetGitObjectDirectory()` / `GetGitAlternateObjectDirectories()` are plain fields on the `gitalypb.Repository` message [1](#0-0) , settable by any gRPC caller. In `beginTransactionForRepository`, if these fields are non-empty on an accessor RPC, Gitaly infers — without any authentication — that "the repository [is] coming from a request that was already configured with a quarantine directory and is being looped back to Gitaly from Rails' authorization checks" and therefore skips starting a new transaction, instead calling `restoreSnapshotRelativePath` and returning a `nonTransactionalRequest`: [2](#0-1) 

`restoreSnapshotRelativePath` then overwrites the target repository's `RelativePath` with whatever value is present in the `relative-path-bin` gRPC metadata header — again, a plain client-settable header with no signature or binding to any real transaction/snapshot, only checked for non-emptiness: [3](#0-2) 

Critically, this bypass branch skips the `locator.ValidateRepository(ctx, targetRepo, storage.WithSkipRepositoryExistenceCheck())` call that the normal path performs before beginning a transaction [4](#0-3) . The code comment explicitly acknowledges the weakness is intentionally left open: *"This property is violated in tests which manually configure the object directory or the alternate object directory. This allows for circumventing the transaction management by configuring either of the object directories. We'll leave this unaddressed for now..."* [5](#0-4) .

This mirrors the FSDVesting root cause precisely: `updateVestedTokens()` trusted the caller-supplied `_user` argument as a stand-in for verified caller identity (`_user == beneficiary`) instead of deriving identity from an authenticated source (`msg.sender`/an `onlyFSD` check). Here, Gitaly trusts caller-supplied `Repository.GitObjectDirectory`/`GitAlternateObjectDirectories` fields (and a caller-supplied metadata header) as a stand-in for "this request is an authenticated Rails access-check loop-back," instead of deriving that fact from an actual authenticated channel.

### Impact Explanation
Any authenticated Gitaly client (which, per Gitaly's threat model, includes any caller holding a valid gRPC auth token — not necessarily Rails) can attach non-empty `git_object_directory`/`git_alternate_object_directories` fields plus a `relative-path-bin` metadata value to an ordinary accessor RPC. This causes Gitaly to:
1. Skip the transaction/snapshot machinery that normally scopes and isolates the repository access, and
2. Skip the `ValidateRepository` check that is otherwise performed before touching the repository,
3. Substitute an attacker-chosen relative path into the request before it reaches the RPC handler.

Downstream, object-directory path resolution (`ObjectDirectoryPath`) does constrain the object directory to either the target repo's own tree or a path matching a deterministic, unsalted `sha1(relative_path)`-derived quarantine prefix under the storage temp dir [6](#0-5) [7](#0-6) , limiting straightforward cross-storage traversal for that specific check. However, the transaction-bypass and validation-bypass behavior itself is a real, developer-acknowledged control gap: repository-scoped RPCs that are supposed to run against a committed/validated transactional view can instead be forced onto the non-transactional, unvalidated code path by any caller who sets these fields, using a spoofed identity claim ("I am Rails' access-check loop-back") that is never actually verified.

### Likelihood Explanation
Reaching this code path requires only setting two ordinary, documented, client-visible request fields (`Repository.git_object_directory` / `git_alternate_object_directories`) plus one metadata header (`relative-path-bin`) on any repository-scoped accessor RPC — no special privilege beyond normal Gitaly RPC access is needed, and the comment in the code confirms this is a known, currently-unenforced assumption rather than a hardened invariant.

### Recommendation
Do not infer trusted internal origin from client-controlled proto fields or metadata. Instead:
- Require an explicit, server-verified marker (e.g., a value derived from the transaction registry / a signed/opaque snapshot token issued by Gitaly itself when it invoked Rails, and checked against the live transaction/snapshot store) before allowing the "loop-back" bypass path.
- Always run `locator.ValidateRepository` (or equivalent) on the rewritten repository, even in the quarantine loop-back branch.
- Reject the bypass entirely if the caller cannot be tied to an existing, still-open transaction referenced by `MetadataKeySnapshotRelativePath`, rather than trusting the header's value at face value.

### Proof of Concept
Not fully verifiable end-to-end from static review alone (would require confirming exactly which accessor RPCs are reachable by ordinary clients with only base gRPC auth and no additional authorization, and how far attacker control over the resulting `RelativePath`/object directories propagates through each handler). Conceptual PoC:
1. As an authenticated Gitaly client (not Rails), issue any repository-scoped accessor RPC (e.g. one in `protoregistry.OpAccessor`) targeting a repository you have access to.
2. Set `Repository.git_object_directory` to a non-empty value (e.g. `"objects"`) and/or `git_alternate_object_directories` to a non-empty list.
3. Set the `relative-path-bin` gRPC metadata header to an arbitrary relative path string.
4. Observe that `beginTransactionForRepository` takes the "loop-back" branch [2](#0-1) , skips `ValidateRepository`, rewrites `RelativePath` to the attacker-supplied metadata value via `restoreSnapshotRelativePath` [3](#0-2) , and the handler executes non-transactionally against attacker-influenced path/quarantine parameters instead of the normal transaction-scoped snapshot.

// QuarantineDirectoryPrefix returns a prefix for use in the temporary directory. The prefix is
// based on the relative repository path and will stay stable for any given repository. This allows
// us to verify that a given quarantine object directory indeed belongs to the repository at hand.
// Ideally, this function would directly be located in the quarantine module, but this is not
// possible due to cyclic dependencies.
func QuarantineDirectoryPrefix(repo Repository) string {
	hash := [20]byte{}
	if repo != nil {
		hash = sha1.Sum([]byte(repo.GetRelativePath()))
	}
	return fmt.Sprintf("quarantine-%x-", hash[:8])
}

func restoreSnapshotRelativePath(ctx context.Context, methodInfo protoregistry.MethodInfo, req proto.Message) (proto.Message, error) {
	// Rails sends RPCs from its access checks with quarantine applied. The quarantine paths are relative to the
	// snapshot repository of the original transaction. While the relative path of the request is the original relative
	// path of the repository before snapshotting, Rails sends the snapshot repository's path in a header. For the
	// quarantine paths to apply correctly, we must thus rewrite the request to point to the snapshot repository here.
	snapshotRelativePath := metadata.GetValue(ctx, MetadataKeySnapshotRelativePath)
	if snapshotRelativePath == "" {
		return nil, ErrQuarantineWithoutSnapshotRelativePath
	}

	rewrittenReq, targetRepo, err := rewritableRequest(methodInfo, req)
	if err != nil {
		return nil, fmt.Errorf("rewritable request: %w", err)
	}

	targetRepo.RelativePath = snapshotRelativePath

	return rewrittenReq, nil
}
