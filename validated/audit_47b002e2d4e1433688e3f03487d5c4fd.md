### Title
Committee-enforced `ForbidTransferToContract` restriction is bypassable via TVM internal value/TRC10 transfers - ([File: actuator/src/main/java/org/tron/core/vm/VMUtils.java])

### Summary
The `FORBID_TRANSFER_TO_CONTRACT` dynamic property, once enabled by committee proposal, is meant to stop TRX and TRC10 tokens from being sent directly to smart-contract addresses. This restriction is enforced only in `TransferActuator.validate()` and `TransferAssetActuator.validate()`, but the equivalent internal-transfer validation used by the TVM (`VMUtils.validateForSmartContract`) never checks this flag, so the same transfer can be performed through a smart contract's `CALL`, plain `transfer`/`send`, or `transferToken` and the restriction is silently bypassed — mirroring the reported pattern where an admin-side restriction (`toggleCollateralStatus`) is enforced on one code path but bypassed via a generic/`exec`-style execution path (`AccountManager.exec()` in the referenced report).

### Finding Description
`TransferActuator.validate()` and `TransferAssetActuator.validate()` both explicitly check `dynamicStore.getForbidTransferToContract() == 1 && toAccount.getType() == AccountType.Contract` and reject the transaction with `"Cannot transfer TRX/asset to a smartContract."`: [1](#0-0) [2](#0-1) 

However, the identical value/asset movement can be performed from inside a smart contract (a normal `address.transfer()`, `.call.value()()`, or `.transferToken()` executed via `TriggerSmartContract`). These paths route through `MUtil.transfer` / `MUtil.transferToken`, which call `VMUtils.validateForSmartContract`, a completely separate validation routine that has no awareness of `FORBID_TRANSFER_TO_CONTRACT`: [3](#0-2) [4](#0-3) 

`Program.callToAddress` (regular internal `CALL`/`CALLCODE`/`DELEGATECALL`) and `Program.callToPrecompiledAddress` both invoke `VMUtils.validateForSmartContract` for TRX and TRC10 transfers with no check of the forbid flag: [5](#0-4) [6](#0-5) 

The dynamic property itself is defined and toggled through the committee proposal mechanism: [7](#0-6) 

### Impact Explanation
This is the exact analog of the reported bug class: a governance/committee-level asset-movement restriction is enforced only in one type of user-facing transaction (`TransferContract`/`TransferAssetContract`), but not in the generic execution path (`TriggerSmartContract` → TVM `CALL`/`transferToken`). Any unprivileged account can deploy a trivial contract that forwards TRX or TRC10 tokens to any other contract address, defeating a protocol-level safety control that the SR committee explicitly turned on (e.g., to prevent assets from becoming stuck in contracts not designed to receive them, or to enforce a broader policy decision). Because the restriction is completely and deterministically bypassable by any address capable of sending a `TriggerSmartContract` transaction, this undermines a security control the network relies on.

### Likelihood Explanation
Any account able to deploy and trigger a smart contract (i.e., a normal signed transaction) can trivially exploit this: deploy a one-line forwarding contract and call it with `callValue`/`tokenValue`, or call an existing contract that forwards TRX/TRC10 via `.transfer()`/`.transferToken()`. No special permission or race condition is required, making this reliably and repeatedly exploitable whenever the `FORBID_TRANSFER_TO_CONTRACT` proposal is active.

### Recommendation
Add a `dynamicStore.getForbidTransferToContract() == 1 && (destination is Contract)` check inside `VMUtils.validateForSmartContract` (used by both `MUtil.transfer`/`MUtil.transferToken` and the `callToPrecompiledAddress` path), so that the restriction is uniformly enforced for both actuator-level transfers and TVM-internal transfers/token transfers.

### Proof of Concept
1. Committee approves the `ForbidTransferToContract` proposal, setting `FORBID_TRANSFER_TO_CONTRACT = 1`.
2. Direct attempt via `TransferContract`/`TransferAssetContract` to send TRX/TRC10 to contract address `C` is rejected with `"Cannot transfer TRX/asset to a smartContract."` (see `TransferActuator.validate()` / `TransferAssetActuator.validate()`).
3. Attacker deploys contract `F` with a function `forward(address payable to) payable { to.transfer(msg.value); }` (or an equivalent `transferToken` call).
4. Attacker calls `F.forward(C)` via `TriggerSmartContract` with `callValue`/`callTokenValue` set — this routes through `Program.callToAddress` → `MUtil.transfer`/`transferToken` → `VMUtils.validateForSmartContract`, none of which check `FORBID_TRANSFER_TO_CONTRACT`.
5. The transfer to contract `C` succeeds despite the committee-enabled restriction, confirming the bypass.

  public static boolean validateForSmartContract(Repository deposit, byte[] ownerAddress,
      byte[] toAddress, byte[] tokenId, long amount) throws ContractValidateException {
    if (deposit == null) {
      throw new ContractValidateException("No deposit!");
    }

    byte[] tokenIdWithoutLeadingZero = ByteUtil.stripLeadingZeroes(tokenId);

    if (!DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("Invalid ownerAddress");
    }
    if (!DecodeUtil.addressValid(toAddress)) {
      throw new ContractValidateException("Invalid toAddress");
    }

    if (amount <= 0) {
      throw new ContractValidateException("Amount must greater than 0.");
    }

    if (Arrays.equals(ownerAddress, toAddress)) {
      throw new ContractValidateException("Cannot transfer asset to yourself.");
    }

    AccountCapsule ownerAccount = deposit.getAccount(ownerAddress);
    if (ownerAccount == null) {
      throw new ContractValidateException("No owner account!");
    }

    if (deposit.getAssetIssue(tokenIdWithoutLeadingZero) == null) {
      throw new ContractValidateException("No asset !");
    }
    if (!Commons.getAssetIssueStoreFinal(deposit.getDynamicPropertiesStore(),
        deposit.getAssetIssueStore(), deposit.getAssetIssueV2Store())
        .has(tokenIdWithoutLeadingZero)) {
      throw new ContractValidateException("No asset !");
    }

    Long assetBalance = ownerAccount.getAsset(deposit.getDynamicPropertiesStore(),
            ByteArray.toStr(tokenIdWithoutLeadingZero));
    if (null == assetBalance || assetBalance <= 0) {
      throw new ContractValidateException("assetBalance must greater than 0.");
    }
    if (amount > assetBalance) {
      throw new ContractValidateException("assetBalance is not sufficient.");
    }

    AccountCapsule toAccount = deposit.getAccount(toAddress);
    if (toAccount != null) {
      assetBalance = toAccount.getAsset(deposit.getDynamicPropertiesStore(),
              ByteArray.toStr(tokenIdWithoutLeadingZero));
      if (assetBalance != null) {
        try {
          addExact(assetBalance, amount,
              VMConfig.disableJavaLangMath()); //check if overflow
        } catch (Exception e) {
          logger.debug(e.getMessage(), e);
          throw new ContractValidateException(e.getMessage());
        }
      }
    } else {
      throw new ContractValidateException(
          "Validate InternalTransfer error, no ToAccount. And not allowed to create account in smart contract.");
    }

    return true;
  }
