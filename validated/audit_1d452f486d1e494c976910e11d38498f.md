### Title
Malicious attachment-serving peer can inject content whose hash does not match any committed BNS `content_hash`, polluting `attachments` as `was_instantiated=1` — ([File: stackslib/src/net/atlas/db.rs])

### Summary
`AtlasDB::insert_instantiated_attachment` unconditionally executes `INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)` using `attachment.hash()` computed from whatever bytes the remote peer returned, with no check that this hash equals the `content_hash` of the `AttachmentInstance` that triggered the fetch, and no enforcement of `AtlasConfig.attachments_max_size`. This lets a malicious peer that is selected as a download source mark arbitrary content as "instantiated" in the local Atlas store, even though it does not correspond to any confirmed on-chain name-operation commitment.

### Finding Description
The equality that should hold is: every row in `attachments` with `was_instantiated = 1` should have a `hash` equal to some `content_hash` value committed by a confirmed name operation and recorded in `attachment_instances`. This equality is not enforced at the point of insertion.

Trace of the reachable path:
- `AttachmentsDownloader::run` selects one of `network.get_outbound_sync_peers()` to serve a batch of missing attachments [1](#0-0) .
- The downloader issues `GetAttachmentRequest`s and decodes the HTTP body via `decode_atlas_get_attachment`, then simply does `self.attachments.insert(response.attachment)` with no comparison of `response.attachment.hash()` against the content_hash that was actually requested [2](#0-1) .
- When the state machine reaches `Done`, every attachment collected this way is passed unconditionally to `insert_instantiated_attachment`, and only afterward is an `UPDATE attachment_instances SET is_available = 1 WHERE content_hash = ?1 ...` attempted — which simply matches zero rows if the peer's returned content doesn't correspond to any real instance [3](#0-2) .
- `insert_instantiated_attachment` itself performs the `INSERT OR REPLACE` with no size check against `atlas_config.attachments_max_size` (that check, `should_keep_attachment`, is only used for the RPC-post attachment path, not this download path) and no lookup/verification against `attachment_instances.content_hash` before insertion [4](#0-3) .

A malicious peer that is dialed as an outbound Atlas download source can therefore respond to a `GET /v2/attachments/{hash}` request with arbitrary JSON content whose declared bytes hash to something other than the requested hash. That garbage gets durably stored with `was_instantiated = 1`, i.e., treated by the local node as validated/canonical attachment data, even though no BNS name operation ever committed that hash.

Existing guards that do NOT stop this:
- `should_keep_attachment`'s size/contract check is not invoked on this insertion path.
- The `UPDATE ... WHERE content_hash = ?1` afterward fails silently for mismatched hashes; it does not roll back or reject the preceding `INSERT`.

### Impact Explanation
This is an attachment/BNS mismatch: the node's local Atlas store can be made to contain, and later serve via the `/v2/attachments/{hash}` RPC endpoint (`find_attachment` reads directly from the `attachments` table with no cross-check against confirmed commitments — see `stackslib/src/net/api/getattachment.rs`), content that no canonical block ever committed. A node repeatedly choosing (or being tricked into choosing) the malicious peer as an attachment source accumulates such rows, growing the `attachments` table with data unrelated to any confirmed `attachment_instances` row.

### Likelihood Explanation
Preconditions: the attacker must be selected as one of the victim's `outbound_sync_peers` for Atlas downloads (achievable by running an ordinary unprivileged peer that the victim dials), and the victim must have at least one queued/unresolved `AttachmentInstance` to fetch (i.e., there must be genuine on-chain BNS activity referencing an attachment). Growth is bounded per real unresolved instance by `max_attachment_retry_count` retries of that specific batch before it is dropped, so pure "unbounded, request-anything" volumetric growth as posed in the question is overstated — the amount of pollution scales with (number of legitimately triggered fetch attempts) × (retry count), not with attacker-chosen hash counts alone. The structural flaw (missing content-hash equality check and missing size cap) is nonetheless real and reachable by a fully unprivileged remote peer with no secret/role required.

### Recommendation
In `insert_instantiated_attachment` (or its caller in `download.rs`), before executing the `INSERT OR REPLACE`, verify that `attachment.hash()` matches the `content_hash` of the specific `AttachmentInstance`/request that produced this response, and enforce `attachment.content.len() as u32 <= atlas_config.attachments_max_size` (reusing `should_keep_attachment`-style logic) before persisting. Reject and penalize (bump failed-request reliability report) any response whose returned attachment hash does not match what was requested.

### Proof of Concept
Rust test plan in `stackslib::net::atlas::tests`:
1. Construct an `AtlasDB` with a small `attachments_max_size` and no queued `AttachmentInstance` rows.
2. Directly call `atlas_db.insert_instantiated_attachment(&attachment)` for N synthetic `Attachment` values (via `new_attachment_from` helper already used in `tests.rs`), each with distinct/oversized content and none corresponding to any `attachment_instances.content_hash`.
3. Assert `SELECT COUNT(*) FROM attachments WHERE was_instantiated = 1` equals N despite `SELECT COUNT(*) FROM attachment_instances` being 0, and that at least one inserted row's `content` length exceeds `atlas_config.attachments_max_size`, showing the missing hash-equality and size-cap enforcement described above.

    pub fn insert_instantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let tx = self.tx_begin()?;
        tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)",
            params![attachment.hash(), attachment.content, now],
        )?;
        tx.execute(
            "UPDATE attachment_instances SET is_available = 1 WHERE content_hash = ?1 AND status = ?2",
            params![attachment.hash(), AttachmentInstanceStatus::Checked],
        )?;
        tx.commit()?;
        Ok(())
    }
