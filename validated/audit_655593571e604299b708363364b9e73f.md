### Title
Protocol reserve-fee (treasury LP mint) can be permanently bypassed via frequent tiny accruals - (File: `mainnet/contracts/vault/v0-vault-usdc.clar` and sibling vault contracts)

### Summary
The vault contracts mint DAO-treasury shares ("treasury LP") representing the protocol's reserve-factor cut of accrued interest, computed with `calc-treasury-lp-preview`, which truncates (`mul-div-down`) the `reserve-inc` value. This is the same class of bug as the reported BarnBridge issue: rounding fee calculations down instead of in the protocol's favor allows the fee to be repeatedly reduced to zero.

### Finding Description
`calc-treasury-lp-preview` computes the protocol's reserve cut of newly accrued interest as follows: [1](#0-0) 

`old-debt`/`new-debt` are derived from `principal-scaled` times the current and next index, and `debt-delta` is the interest accrued since the index was last updated; `reserve-inc` (the protocol's fee share of that interest) is computed with `mul-div-down`, truncating toward zero. If `reserve-inc` truncates to `0` it returns `u0` explicitly: [2](#0-1) 

The index itself, and therefore `debt-delta`, is a function of elapsed time (`next-index` / `calc-multiplier-delta`): [3](#0-2) 

Every state-mutating vault entry point (`deposit`, `redeem`, `borrow`, `repay`, etc.) calls `(try! (accrue))` first, e.g.: [4](#0-3) 

Because `debt-delta` shrinks with the elapsed time since the last accrual, an unprivileged caller who repeatedly triggers `accrue()` at short intervals (e.g. by depositing/withdrawing the minimum non-zero amount every block) keeps each individual `debt-delta` small enough that `mul-div-down(debt-delta, fee-reserve, BPS)` truncates to `0`. Interest still compounds into `total-debt`/`total-assets` for depositors/borrowers (since `calc-index-next` and `calc-cumulative-debt` are computed independently of the reserve fee), but the DAO treasury's cut of that interest — which should be minted as `treasury-lp` shares — is silently dropped to zero on every such accrual, indefinitely.

### Impact Explanation
This causes permanent freezing/theft of the protocol's (DAO treasury's) unclaimed yield: the reserve-factor cut of interest that the DAO is entitled to on every vault (`v0-vault-usdc`, `v0-vault-ststx`, `v0-vault-ststxbtc`, `v0-vault-stx`, `v0-vault-sbtc`, `v0-vault-usdh`) can be suppressed to near-zero by any user forcing frequent small accruals, denying the protocol its intended fee revenue over time. This matches the in-scope High impact class: theft/permanent freezing of unclaimed yield.

### Likelihood Explanation
Likelihood is significant because any unprivileged user can call `deposit`/`redeem`/other vault entry points with trivial nonzero amounts (bounded only by `ERR-AMOUNT-ZERO`/`ERR-OUTPUT-ZERO` checks) as often as desired, at negligible cost, to keep `debt-delta` per accrual under the truncation threshold, and no fee-exemption/whitelist gates this path the way flashloan fees are gated.

### Recommendation
Round the reserve fee calculation in the protocol's favor (round up) instead of using `mul-div-down` for `reserve-inc` in `calc-treasury-lp-preview`, mirroring the `mul-div-up` pattern already used elsewhere in the same contracts (e.g., for `calc-cumulative-debt` and the flashloan fee). Alternatively, accumulate a fee-remainder across accruals so truncated dust is not permanently lost.

### Proof of Concept
1. Attacker deposits a minimal amount into `v0-vault-usdc` to establish a position.
2. Immediately (or every block) the attacker calls a trivial vault action (e.g. `deposit` of `u1`), which forces `accrue()`.
3. Each call computes a tiny `debt-delta` (since only a few seconds/one block of interest has accrued) such that `mul-div-down(debt-delta, fee-reserve, BPS)` == `0`.
4. Repeating step 2 indefinitely means the treasury never accumulates its reserve-factor share of interest, even though the same interest fully compounds into borrower debt and depositor assets — the DAO's cut is bypassed via truncation, exactly analogous to the BarnBridge `buyTokens` fee-bypass report.

Note: I was not able to view the full body of the `accrue` public function in `v0-vault-usdc.clar` (only line-count matches were retrieved, not the code), so I could not directly confirm the exact call site where `calc-treasury-lp-preview`'s result is minted to `dao-treasury`; this is inferred from `docs/dao.md`'s description of the AAVE-style reserve-mint model and the helper function definitions shown above.
