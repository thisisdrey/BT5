### Title
NEAR-implicit account nonce reseed uses same-block height, allowing nonce-window collision and transaction replay/double-spend when delete+recreate occur in one block - ([File: runtime/runtime/src/access_keys.rs])

### Summary
`initial_nonce_value(block_height)` seeds a recreated NEAR-implicit account's `FullAccess` key with `(block_height-1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER`, while `verify_nonce`'s replay-prevention upper bound for any transaction processed in that same block is `block_height * ACCESS_KEY_NONCE_RANGE_MULTIPLIER`. Both values are derived from the *same* `apply_state.block_height` when the delete and the re-creation of an implicit account happen in a single block/chunk, leaving a `MULTIPLIER`-sized (1,000,000) nonce window in which a previously-executed transaction from the deleted incarnation can be replayed against the freshly recreated account.

### Finding Description
`action_implicit_account_creation_transfer` (`runtime/runtime/src/actions.rs:213-244`) seeds the new access key nonce via: [1](#0-0) 
which calls `initial_nonce_value`: [2](#0-1) 

The comment explains this exists to prevent tx-hash/nonce collisions after account recreation (GH issue #3779), and relies on `block_height` at recreation time being *strictly greater* than the block height at which the deleted incarnation last used its nonce — a `MULTIPLIER`-sized (1,000,000) headroom per block is normally sufficient because `verify_nonce`'s upper bound at any earlier height `h'` is `h' * MULTIPLIER`, always `<= (block_height-1) * MULTIPLIER` for `h' < block_height`: [3](#0-2) 

However, when the attacker forces the sequence of (a) consuming a high nonce N via a self-signed transaction, (b) `DeleteAccount`, and (c) the implicit-recreation `Transfer` to all execute **within the same chunk/block height `h`**, both the nonce upper bound for (a) and the reseed for (c) are computed from the identical `apply_state.block_height = h` used throughout that chunk's application (confirmed in `runtime/runtime/src/lib.rs`, where `block_height = processing_state.apply_state.block_height` is passed uniformly into `verify_and_charge_tx_ephemeral`/`verify_and_charge_gas_key_tx_ephemeral` for every tx in the chunk). This means:
- Step (a) can use a nonce N up to just under `h * MULTIPLIER`.
- Step (b) `DeleteAccount` consumes an even higher nonce, still `< h * MULTIPLIER`.
- Step (c) reseeds the new key to `(h-1) * MULTIPLIER`, which is **less than N**.

Because `N > (h-1) * MULTIPLIER`, replaying the exact same signed transaction from step (a) against the recreated account passes `verify_nonce`'s `Monotonic` check (`tx_nonce > current_nonce`) since `current_nonce` is now `(h-1)*MULTIPLIER`: [4](#0-3) 

There is no additional guard (e.g., requiring a minimum block-height gap between account deletion and recreation, or basing the reseed on the deletion height rather than `block_height-1`) preventing this same-block collision. The existing regression test `get_status_of_tx_hash_collision_for_near_implicit_account` (`integration-tests/src/tests/features/access_key_nonce_for_implicit_accounts.rs:112-194`) only validates the multi-block-gap case (each phase separated by `blocks_number=5` blocks), so it does not cover the same-block scenario.

### Impact Explanation
This is a double-spend / replay of a previously executed transfer: an attacker can re-execute a stale signed transaction (e.g., a `Transfer` moving funds out of the implicit account) a second time after the account is deleted and recreated within the same block, effectively debiting the newly-deposited balance a second time using a transaction that had already been fully settled. This falls under the "double-spend/replay" bounty category and directly violates the nonce-monotonicity/replay-prevention invariant this mechanism was designed to enforce.

### Likelihood Explanation
The attacker needs only ordinary, unprivileged capabilities: control of the NEAR-implicit account's private key, ability to submit several transactions in quick succession so they land in the same chunk, a valid beneficiary for `DeleteAccount`, and a follow-up transfer to the same implicit account id. All of this is achievable by any funded client submitting to a public RPC without any validator/node privilege. The only external dependency is that the 2-3 transactions (nonce-consuming tx, `DeleteAccount`, recreation `Transfer`) all get included in a single chunk on the shard hosting the implicit account — plausible for an attacker deliberately racing a burst of transactions, and fully repeatable since the attacker fully controls nonce values chosen (up to the `NonceTooLarge` cap) to land inside the vulnerable window.

### Recommendation
Base the reseed value on a height that is guaranteed to exceed any nonce consumable within the same block as the recreation, e.g., seed with `block_height * MULTIPLIER` (removing the `-1`) so the reseed value equals the upper bound enforced for transactions processed in that same block, closing the collision window; alternatively, track the last-used nonce/height of a deleted account's key explicitly and reseed strictly above it, or reject implicit-account recreation transfers processed in the same block height as the account's deletion.

### Proof of Concept
Integration test (mirroring `get_status_of_tx_hash_collision_for_near_implicit_account`) that forces the delete and recreate into the SAME block height as the high-nonce usage:
1. Create the NEAR-implicit account (block h0) via `send_money`.
2. In a single subsequent chunk at height `h`, submit in order: (i) a `Transfer` (nonce = `h*MULTIPLIER - 2`) signed by the implicit account's key transferring funds to a victim/attacker-controlled account, (ii) `DeleteAccount` (nonce = `h*MULTIPLIER - 1`) with a valid beneficiary, (iii) a `Transfer` from a third account to the same implicit account id (triggering recreation) — engineered so all three land in block `h`.
3. Confirm the account is recreated with a `FullAccess` key whose nonce equals `(h-1)*MULTIPLIER` (via `ViewAccessKey`).
4. Resubmit the exact same signed transaction from step (i) (nonce = `h*MULTIPLIER - 2`).
5. Assert this resubmission is accepted (`ProcessTxResponse::ValidTx`) and executes successfully, and that the recreated account's balance is debited a second time — proving replay/double-spend, instead of being rejected with `InvalidTxError::InvalidNonce`.

```rust
pub(crate) fn initial_nonce_value(block_height: BlockHeight) -> Nonce {
    // Set default nonce for newly created access key to avoid transaction hash collision.
    // See <https://github.com/near/nearcore/issues/3779>.
    (block_height - 1) * near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER
}
```

```rust
fn verify_nonce(
    tx_nonce: Nonce,
    current_nonce: Nonce,
    block_height: Option<BlockHeight>,
    nonce_mode: NonceMode,
) -> Result<(), InvalidTxError> {
    match nonce_mode {
        NonceMode::Monotonic => {
            if tx_nonce <= current_nonce {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
        NonceMode::Strict => {
            if !current_nonce.checked_add(1).is_some_and(|expected| tx_nonce == expected) {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
```
