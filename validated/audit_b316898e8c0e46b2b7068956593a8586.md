## Analysis

The Chainlink report's core broken invariant: an external numeric value is converted/cast between representations without validating that the conversion preserves meaning, silently producing an unexpected (near-zero/underflowed) result that downstream logic then trusts and acts on.

The local analog is in Snowbridge's outbound-queue fee computation: `Pallet::calculate_fee()` performs a chain of unchecked-truncating numeric conversions (`U256` → `u128` truncation via `defensive_unwrap_or(u128::MAX)`, reinterpreting a raw integer as `FixedU128` inner value, then an integer division in `convert_from_ether_decimals`) that can silently round the *remote* (Ethereum-side relayer) fee down to exactly zero for legitimate, attacker-influenced inputs — while `validate()` never checks that the resulting `Fee` is non-zero before accepting the message into the queue.

### Title
Fee-conversion rounding in `OutboundQueue::calculate_fee` lets messages be enqueued with zero relayer reward, underpricing Snowbridge delivery work - (File: `bridges/snowbridge/pallets/outbound-queue/src/lib.rs`)

### Summary
`Pallet::<T>::calculate_fee()` converts the Ethereum-denominated remote fee (`U256`) into the parachain's native `Balance` type through several unchecked numeric transformations: a truncating `U256`→`u128` cast, reinterpretation of that integer as a `FixedU128` "inner" fixed-point value, division by the governance-set exchange rate, and finally an integer division to rescale ether's 18 decimals down to the local asset's decimals in `convert_from_ether_decimals`. None of these steps validate that the final result is non-zero, and `SendMessage::validate()` in `send_message_impl.rs` accepts the ticket regardless of the computed fee.

### Finding Description
`calculate_fee` at [1](#0-0)  computes:
1. `calculate_remote_fee` = `fee_per_gas * gas_used_at_most + reward` (a `U256`).
2. Downcast: `let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);` — this only guards the overflow direction, not precision loss on the low end.
3. `FixedU128::from_inner(fee)` treats the raw wei integer as an *inner* fixed-point value (i.e. implicitly divides by 10^18), then multiplies by `multiplier` and divides by `exchange_rate`.
4. `convert_from_ether_decimals` then performs `value.checked_div(denom)` where `denom = 10^(18 - local_decimals)` — a **floor** integer division at [2](#0-1) .

Because `gas_used_at_most` is derived from `T::GasMeter::maximum_gas_used_at_most(&message.command)` — a value that depends on the `Command` an ordinary user builds via XCM export (`EthereumBlobExporter::deliver` → `Pallet::validate`) — a caller can choose low-cost commands or otherwise land on gas/fee/exchange-rate combinations where the successive multiply/divide/rescale chain rounds the *remote* component of the fee to **zero**, even though `PricingParameters::validate()` requires every individual parameter (`exchange_rate`, `fee_per_gas`, `rewards.local`, `rewards.remote`, `multiplier`) to be non-zero at [3](#0-2) . That per-parameter validation does not guarantee the *derived* fee survives the decimal-rescaling division, exactly as the external report's Chainlink `consult()` validated round-completeness/price-sign but not the final cast's correctness.

The repository's own test acknowledges this outcome without treating it as an error: [4](#0-3) 
```
// Though none zero pricing params the remote fee calculated here is invalid
// which should be avoided
assert_eq!(fee.remote, 0);
```

`SendMessage::validate` at [5](#0-4)  computes this `fee`, but never asserts `fee.remote > 0` (or `fee.local > 0`) before returning `Ok((ticket, fee))`; the caller of `validate`/`deliver` charges whatever `fee` was computed and the message is unconditionally enqueued via `T::MessageQueue::enqueue_message`.

### Impact Explanation
A zero (or near-zero) remote fee means the message is committed to the outbound Merkle root and eventually relayed to Ethereum, but the fee paid does not include a viable relayer reward/gas-refund component. Per the module's own fee-model documentation at [6](#0-5) , on the Ethereum gateway side "relayers are refunded for gas consumption ... Or in plain english". If the committed `Message.Reward`/`MaxFeePerGas` accounting is zero, relaying becomes unprofitable, so relayers have no economic incentive to submit the message on Ethereum. This is a "public underpriced work that ... stalls bridge processing" impact: messages can pile up undelivered because they were priced at zero despite passing all stated pricing-parameter validations, degrading Snowbridge's Polkadot→Ethereum delivery pipeline.

### Likelihood Explanation
Any unprivileged user constructing an XCM message routed through `EthereumBlobExporter` (or a low-cost `Command`) reaches `calculate_fee` with parameters and gas estimates that are, at least in part, influenced by the message content the caller chooses. Governance sets `PricingParameters`, but the parameters only need to satisfy the non-zero checks in `PricingParameters::validate`; they do not need to be adversarial for the rounding to zero — the repository's own passing unit test reproduces the zero-fee outcome using otherwise "valid" non-zero parameters (`exchange_rate = 1/1`, `fee_per_gas = 1`, `reward = 1`, `gas_used = 250000`). This shows the zero-fee condition is reachable with realistic, currently-accepted parameter/gas combinations, not just contrived edge cases, making it plausible in production configurations with different decimal counts or exchange rates that shift the rounding boundary.

### Recommendation
- After computing `fee.remote` (and `fee.local`) in `calculate_fee`, explicitly `ensure!`/return an error if the computed remote fee is zero (or below a configured minimum), rather than silently truncating.
- Avoid `defensive_unwrap_or(u128::MAX)` masking truncation; instead propagate a hard error for both overflow and any precision loss that would zero out the result.
- In `convert_from_ether_decimals`, round up (ceiling division) instead of floor division when converting fee components, so relayer compensation is never underpaid due to rounding.
- Add validation in `SendMessage::validate` that rejects tickets whose `Fee` would not cover a minimum relayer incentive before enqueuing the message.

### Proof of Concept
Using the existing test harness in `bridges/snowbridge/pallets/outbound-queue/src/test.rs`:
```rust
let gas_used: u64 = 250000;
let price_params: PricingParameters<<Test as Config>::Balance> = PricingParameters {
    exchange_rate: FixedU128::from_rational(1, 1),
    fee_per_gas: 1_u32.into(),
    rewards: Rewards { local: 1_u32.into(), remote: 1_u32.into() },
    multiplier: FixedU128::from_rational(1, 1),
};
let fee = OutboundQueue::calculate_fee(gas_used, price_params.clone());
assert_eq!(fee.remote, 0); // passes today — remote fee silently rounds to zero
```
This demonstrates that `calculate_fee`/`SendMessage::validate` will happily produce and accept a `Fee { remote: 0, .. }` for a message that still consumes real Ethereum gas, with no guard preventing the message from being queued and later delivered underpriced.

		/// Calculate total fee in native currency to cover all costs of delivering a message to the
		/// remote destination. See module-level documentation for more details.
		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

	fn validate(
		message: &Message,
	) -> Result<(Self::Ticket, Fee<<Self as SendMessageFeeProvider>::Balance>), SendError> {
		// The inner payload should not be too large
		let payload = message.command.abi_encode();
		ensure!(
			payload.len() < T::MaxMessagePayloadSize::get() as usize,
			SendError::MessageTooLarge
		);

		// Ensure there is a registered channel we can transmit this message on
		ensure!(T::Channels::contains(&message.channel_id), SendError::InvalidChannel);

		// Generate a unique message id unless one is provided
		let message_id: H256 = message
			.id
			.unwrap_or_else(|| unique((message.channel_id, &message.command)).into());

		let gas_used_at_most = T::GasMeter::maximum_gas_used_at_most(&message.command);
		let fee = Self::calculate_fee(gas_used_at_most, T::PricingParameters::get());

		let queued_message: VersionedQueuedMessage = QueuedMessage {
			id: message_id,
			channel_id: message.channel_id,
			command: message.command.clone(),
		}
		.into();
		// The whole message should not be too large
		let encoded = queued_message.encode().try_into().map_err(|_| SendError::MessageTooLarge)?;

		let ticket = Ticket { message_id, channel_id: message.channel_id, message: encoded };

		Ok((ticket, fee))
	}
