Audit Report

## Title
Fee-decimal conversion rounds Ethereum delivery fee down to zero, letting senders underpay the Snowbridge relayer/gas fee - (File: bridges/snowbridge/pallets/outbound-queue/src/lib.rs)

## Summary
`Pallet::calculate_fee` converts the Ethereum-side wei-denominated fee (gas + relayer reward) into local balance decimals via `convert_from_ether_decimals`, which performs a raw `checked_div` with no rounding-up or minimum-floor guard. When `PricingParameters` (governance-settable `fee_per_gas`, `rewards.remote`, `exchange_rate`, `multiplier`) yield a wei value small relative to `10^(18 - T::Decimals)`, the division truncates the remote fee to exactly `0`, while the full reward is still promised to relayers in the `CommittedMessage` sent on-chain to Ethereum.

## Finding Description
`calculate_fee` computes the remote fee in wei via `calculate_remote_fee`, downcasts to `u128`, applies `multiplier`/`exchange_rate`, then calls `convert_from_ether_decimals`: [1](#0-0) 
which computes `denom = 10^(18 - T::Decimals)` and performs `value.checked_div(denom)` with no round-up or floor enforcement.

This is invoked unconditionally from `calculate_fee`, which is called from the public `SendMessage::validate` entrypoint every time any user or sibling parachain submits a message to be bridged to Ethereum: [2](#0-1) 

Meanwhile, `do_process_message` unconditionally embeds `pricing_params.rewards.remote` into the `CommittedMessage.reward` field regardless of what was actually collected as fee from the sender: [3](#0-2) 

`PricingParameters::validate` only checks each parameter is individually non-zero, never that the combined wei amount survives decimal conversion without truncating to zero — confirming no code path guards against this outcome. The pallet's own regression test, `test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero`, demonstrates the exact truncation-to-zero condition with realistic (small) pricing parameters and a 12-decimal chain, explicitly noting in a comment that this outcome "should be avoided."

## Impact Explanation
This matches the "public underpriced work that degrades block production or stalls bridge processing" impact category. The module's own documentation states the fee covers gas refunds and relayer rewards for Ethereum-side message delivery. When `fee.remote` rounds to zero, every message sender on this public path is charged nothing for that component while the full `reward` value is still committed on-chain and promised to relayers via `CommittedMessage.reward`, silently draining the funding source that incentivizes relayers to service the bridge. This is a durable systemic effect (persists until governance updates `PricingParameters` again), not a one-off griefing incident, and it corrupts the intended invariant that `fee.remote` charged to the sender should cover the `reward` amount embedded in the committed message.

## Likelihood Explanation
Likelihood is Medium: it requires `PricingParameters` — an ordinary, periodically-governance-updated value per the module's own documented operational process — to land in a regime where wei fee values are small relative to `10^(18 - T::Decimals)` (e.g., BridgeHub Polkadot/Kusama with 10/12 decimals). No code enforces that the resulting `fee.remote` remains non-zero, and the pallet's own test suite independently reproduces this exact scenario with realistic parameter magnitudes, confirming it is a readily reachable operational condition rather than a purely theoretical edge case.

## Recommendation
- Replace the raw `checked_div` in `convert_from_ether_decimals` with `multiply_by_rational_with_rounding` (from `sp_arithmetic::helpers_128bit`) using `Rounding::Up`, so the computed fee never truncates below the true remote cost.
- Add an explicit invariant in `calculate_fee` (or `PricingParameters::validate`) ensuring `fee.remote` is non-zero whenever the pre-conversion wei amount is non-zero, erroring out or defensively flooring the amount rather than silently charging 0.

## Proof of Concept
The repository's existing test `test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero` in `bridges/snowbridge/pallets/outbound-queue/src/test.rs` reproduces this directly: with `gas_used=250000`, `fee_per_gas=1`, `rewards.remote=1`, `exchange_rate=1/1`, `multiplier=1/1`, and mock `Decimals=12`, `calculate_fee` returns `Fee { local: 698000000, remote: 0 }`, confirming any sender calling `validate()` under such (governance-set) parameters pays zero for the remote/reward component while the full reward is still committed to the outbound `CommittedMessage`. 		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

#[test]
fn test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero() {
	new_tester().execute_with(|| {
		let gas_used: u64 = 250000;
		let price_params: PricingParameters<<Test as Config>::Balance> = PricingParameters {
			exchange_rate: FixedU128::from_rational(1, 1),
			fee_per_gas: 1_u32.into(),
			rewards: Rewards { local: 1_u32.into(), remote: 1_u32.into() },
			multiplier: FixedU128::from_rational(1, 1),
		};
		let fee = OutboundQueue::calculate_fee(gas_used, price_params.clone());
		assert_eq!(fee.local, 698000000);
		// Though none zero pricing params the remote fee calculated here is invalid
		// which should be avoided
		assert_eq!(fee.remote, 0);
	});
}
