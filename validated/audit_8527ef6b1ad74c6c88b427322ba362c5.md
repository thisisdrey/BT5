### Title
Uninitialized `accountIndexOf` fallback lets a depositor claim their full token balance as rewards when global index equals `INITIAL_INDEX` - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
`RewardsDistributor._calculateTokenDelta` uses `0` as the sentinel for "account index not yet initialized" and substitutes `INITIAL_INDEX` (1e18) only when the global `tokenIndex > INITIAL_INDEX`. When the global index is still exactly `INITIAL_INDEX`, an uninitialized account's delta is computed as `INITIAL_INDEX - 0 = 1e18`, so `_tokensDelta = balanceOf(account).wadMul(1e18) = balance` — the user's entire DepositToken/DebtToken balance is credited as claimable reward tokens, and `claimRewards` pays it out from the distributor's reward balance.

### Finding Description
The bug class is improper initialization of a memory/storage object (the uninitialized account index is treated as `0` instead of `INITIAL_INDEX`).

Relevant code in `contracts/RewardsDistributor.sol`:

```solidity
// _calculateTokenDelta, lines ~222-230
_tokenIndex = _tokenState.index;
uint256 _accountIndex = accountIndexOf[token_][account_];

if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}

uint256 _deltaIndex = _tokenIndex - _accountIndex;
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
```

When `tokenStates[token_].index == INITIAL_INDEX` (index initialized but never grown) and `accountIndexOf[token_][account_] == 0` (account deposited before the reward token was registered, so `updateBeforeMintOrBurn`'s `index > 0` guard at line ~176 skipped them), the `> INITIAL_INDEX` guard fails, `_accountIndex` stays `0`, and `_deltaIndex = 1e18`, crediting `balance` reward tokens.

Global index stays at `INITIAL_INDEX` in three reachable states:

1. **Same-block claim after speed set.** `_updateTokenSpeed` sets `index = INITIAL_INDEX` and `timestamp = block.timestamp` (line ~298). In the same block, `_calculateTokenIndex` computes `_deltaTimestamps = 0`, so `_newIndex = 0` and the index stays `INITIAL_INDEX`. Anyone can call `claimRewards(accounts_, tokens_)` (line ~150) for any account.
2. **Speed later set to 0.** With `speed == 0`, `_calculateTokenIndex` only bumps the timestamp; the index remains `INITIAL_INDEX` forever.
3. **Rounding to zero.** With `speed > 0`, `_ratio = _tokensAccrued.wadDiv(_totalSupply)` floors to `0` whenever `_deltaTimestamps * _speed * 1e18 < totalSupply`, leaving `_newIndex == INITIAL_INDEX` indefinitely for low speeds / large supplies.

The payout path `claimRewards` → `_updateTokensAccruedOf` → `_transferRewardIfEnoughTokens` (line ~248) transfers `rewardToken` to the account whenever `tokensAccruedOf[account] <= rewardToken.balanceOf(this)`.

### Impact Explanation
Direct theft of unclaimed yield: the attacker receives reward tokens equal to their full DepositToken/DebtToken balance (denominated in the reward token, e.g. MET), drained from the distributor contract, which holds rewards owed to all users. There is no cap on repeats across different accounts the attacker controls, and any third party can trigger the same credit for any stale account via the public `claimRewards(accounts_, tokens_)`.

### Likelihood Explanation
- Preconditions: a rewards distributor registered on the pool, a token whose global index is still `INITIAL_INDEX` (states 1–3 above), and an account with a nonzero token balance whose `accountIndexOf` is `0` (trivially satisfied by depositing before the token's speed is first set, or before the distributor is registered — `updateBeforeMintOrBurn` silently skips while `index == 0`).
- Fully unprivileged: `claimRewards` is public and permissionless; the attacker only needs an EOA and a deposit.
- No modifier stops it: `onlyIfDistributorExists`/`onlyIfTokenExists` are only checked on the governor path; `nonReentrant` doesn't help; there is no health or SynthContext check on the claim path.
- The window is deterministic in states 2 and 3, and in state 1 it exists for at least one block (longer whenever `_ratio` rounds to 0).

### Recommendation
Initialize the account fallback consistently so the delta is zero when no interest has accrued:

```solidity
if (_accountIndex == 0) {
    _accountIndex = _tokenIndex > INITIAL_INDEX ? _tokenIndex : INITIAL_INDEX;
}
```

or equivalently treat `accountIndex == 0` as `min(INITIAL_INDEX, _tokenIndex)`... the intended semantics is that an account first seen at index `i` should start earning from `max(INITIAL_INDEX, i)`. The minimal fix is changing `>` to cover the equal case:

```solidity
if (_accountIndex == 0 && _tokenIndex >= INITIAL_INDEX) {
    _accountIndex = _tokenIndex; // start accruing from current index, no retroactive credit
}
```

(verify against the intended "existing holders get no retro rewards" semantic — the key is that `_accountIndex` must never remain `0` when `_tokenIndex >= INITIAL_INDEX`). Add a regression test: register token, deposit, set speed, and claim in the same block must yield `0`.

### Proof of Concept
Foundry fork sketch against a deployed pool with a registered `RewardsDistributor` whose reward token has a nonzero balance:

```solidity
// Assume: pool, depositToken (registered on pool), distributor (registered on pool),
// rewardToken balance sits in distributor. Attacker EOA with collateral.
function testUninitializedIndexRewardTheft() public {
    // 1. Attacker deposits collateral BEFORE the token speed is set
    //    (or before distributor registration) so accountIndexOf stays 0.
    underlying.approve(address(depositToken), DEPOSIT);
    depositToken.deposit(DEPOSIT, attacker);   // updateBeforeMintOrBurn no-ops: index == 0
    assertEq(distributor.accountIndexOf(depositToken, attacker), 0);

    // 2. Governor sets speed (index = INITIAL_INDEX). Attacker calls
    //    claimRewards in the same block (or once speed returns to 0 /
    //    ratio rounds to 0), while tokenStates[token].index == INITIAL_INDEX.
    vm.prank(governor);
    distributor.updateTokenSpeed(depositToken, 1); // any nonzero speed; same timestamp
    // block.timestamp unchanged

    // 3. Anyone claims on behalf of attacker
    IERC20[] memory toks = new IERC20[](1);
    toks[0] = IERC20(address(depositToken));
    distributor.claimRewards(attacker, toks);

    // tokensDelta = balanceOf(attacker).wadMul(1e18) = balanceOf(attacker)
    assertEq(rewardToken.balanceOf(attacker), depositToken.balanceOf(attacker));
}
```

Expected: `tokensAccruedOf[attacker] == depositToken.balanceOf(attacker)` and the distributor pays out that amount in `rewardToken`, draining user rewards.
