### Title
Floating-point Bancor-relay pricing in TRON's native Exchange enables low-liquidity price manipulation via repeated `ExchangeTransactionContract` trades - (File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java)

### Summary
TRON's native asset-to-asset AMM ("Exchange"/"Bancor" contracts, reachable by any account via `ExchangeCreateContract`, `ExchangeInjectContract`, and `ExchangeTransactionContract`) prices trades using a two-step relay/bonding-curve formula that is computed with Java `double` floating point math in the default (non-"hardened") code path. This is directly analogous to the WOOFi incident: an internally-priced AMM whose pricing function is imprecise/manipulable and whose behavior degrades sharply on low-liquidity pools, allowing an attacker to extract value via a rapid sequence of same-account trades against a thinly-liquid pair.

### Finding Description
`ExchangeTransactionActuator.execute` calls `ExchangeCapsule.transaction`, which selects between two pricing engines based on the `allowHardenExchangeCalculation` dynamic property: [1](#0-0) 

When hardening is not enabled, pricing runs through `ExchangeProcessor`, which converts the sell amount into an intermediate "relay supply" and back into the buy token using `double`-precision `Math.pow` calls with hard-coded exponents (`0.0005` / `2000.0`) that approximate the bonding-curve math: [2](#0-1) 

Because the two legs (`exchangeToSupply` then `exchangeFromSupply`) are independent floating-point operations rather than a single atomic constant-product invariant, they are not guaranteed to be exact inverses of one another. This is acknowledged in the codebase itself: a "hardened" `SafeExchangeProcessor` using `BigDecimal` with explicit rounding and overflow checks was added as an *opt-in* alternative: [3](#0-2) 

The existing test suite confirms the two engines produce materially different results on identical inputs (`assertNotEquals(anotherTokenQuant, result)`), which is only asserted safe because the hardened engine is compared against itself, not against a proof of economic soundness of the legacy engine: [4](#0-3) 

An unprivileged account can:
1. Create (or find) a low-liquidity `Exchange` pair via `ExchangeCreateContract`/`ExchangeInjectContract` (reachable, unprivileged flows).
2. Repeatedly submit `ExchangeTransactionContract` swaps back and forth on the same pair in quick succession (each is validated purely against current pool state in `ExchangeTransactionActuator.doValidate`/`execute`, with no cooldown, TWAP, or minimum-liquidity floor beyond a simple non-zero balance check): [5](#0-4) [6](#0-5) 

Since the price impact function is entirely internal (no oracle, no external anchor) and computed with floating point, on small-balance pools (the WOOFi-style "low liquidity" condition) accumulated floating-point drift and asymmetric truncation (`(long) issuedSupply` / `(long) exchangeBalance`, both truncating toward zero rather than using a consistent rounding direction favoring the pool) can be leveraged by round-tripping trades to extract more value from the pool than a mathematically-consistent constant-product/bonding-curve formula would allow, at the expense of the pool creator/other participants' deposited balances.

### Impact Explanation
Exploitation drains real TRX/TRC10 token balances held inside a native `Exchange` object (funds contributed by the exchange creator via `ExchangeInjectContract`), which constitutes unauthorized extraction of pooled user funds — a concrete "theft of funds" impact reachable purely through unprivileged, unsigned-permission transactions (`ExchangeTransactionContract`). This is High severity because it directly moves real on-chain TRX/token value out of legitimate holders' balances with no special privilege required, mirroring the WOOFi exploit's characteristic of "manipulate internal pricing via low liquidity, repeat rapidly, extract profit."

### Likelihood Explanation
Likelihood is Medium-High: any account can create thinly-liquid `Exchange` pairs or target existing ones, and repeated `ExchangeTransactionContract` submissions require no special permission, only transaction fees/bandwidth. The severity of extractable value scales inversely with pool liquidity, matching the WOOFi pattern of targeting low-liquidity pairs for maximum price impact per unit of capital. The main open question — which could not be conclusively verified from static review alone — is the exact numeric magnitude of exploitable drift for realistic pool sizes and whether `allowHardenExchangeCalculation` is enabled by default on mainnet (if enabled, the vulnerable legacy `ExchangeProcessor` path is bypassed).

### Recommendation
- Confirm and, if not already done, enable `allowHardenExchangeCalculation` by default so all exchange pricing routes through `SafeExchangeProcessor`'s `BigDecimal` arithmetic.
- Even under hardening, review `exchangeToSupply`/`exchangeFromSupply` for consistent rounding direction that always favors the pool (never the trader) to prevent value leakage from repeated round-trips.
- Add minimum-liquidity thresholds and/or per-block trade-count/size limits on a single `Exchange` pair to blunt low-liquidity manipulation, analogous to slippage/oracle protections recommended post-WOOFi.

### Proof of Concept
Conceptual reproduction (cannot be fully numerically validated without live network state):
1. Attacker calls `ExchangeCreateContract` then `ExchangeInjectContract` to create/fund a `firstToken`/`secondToken` pair with minimal balances (e.g., hundreds of units, as used in existing tests such as `exchangeCapsule3.setBalance(903L, 737L)` in `ExchangeWithdrawActuatorTest`).
2. Attacker submits a `ExchangeTransactionContract` selling `firstToken` for `secondToken` via `ExchangeTransactionActuator.execute`, which calls `ExchangeCapsule.transaction(...)` → `ExchangeProcessor.exchange(...)`.
3. Attacker immediately submits a reverse `ExchangeTransactionContract` selling the received `secondToken` back for `firstToken`.
4. Due to the independent floating-point `exchangeToSupply`/`exchangeFromSupply` computations and truncating casts, repeating steps 2–3 several times on the low-liquidity pool can yield a net token surplus relative to the pool's true invariant, extractable via `ExchangeWithdrawContract` if the attacker also controls pool liquidity, or as direct arbitrage profit against the pool's other depositors otherwise.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
