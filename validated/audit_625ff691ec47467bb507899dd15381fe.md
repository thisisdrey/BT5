### Title
Postponed self-`DeployContract` receipt survives `DeleteAccount` and silently overwrites a later recreated account's contract - ([File: runtime/runtime/src/lib.rs], [File: runtime/runtime/src/actions.rs])

### Summary
`check_actor_permissions` authorizes `Action::DeployContract` purely by comparing `actor_id` (the receipt's `predecessor_id`) to `account_id` (the receiver) as plain `AccountId` strings, with no notion of "account incarnation." A postponed action receipt is keyed only by `(receiver_id, receipt_id)` and is never invalidated by `remove_account`, so a self-targeted `DeployContract` receipt that is still waiting on a data dependency when its account is deleted will still pass all permission and existence checks and execute against whatever account later comes to occupy that same `AccountId`, silently overwriting that account's contract code.

### Finding Description
`check_actor_permissions` in `runtime/runtime/src/actions.rs` treats `DeployContract` as authorized whenever `actor_id == account_id`: [1](#0-0) 
`actor_id` is initialized from `receipt.predecessor_id()` at the start of `apply_action_receipt`: [2](#0-1) 
Neither of these checks reference anything that changes when an account is deleted and later recreated - `AccountId` is just a string, and there is no per-account "epoch"/incarnation counter tied into the permission check.

Postponed receipts are persisted keyed by `(receiver_id, receipt_id)` in `TrieKey::PostponedReceipt`/`PostponedReceiptId`/`PendingDataCount`: [3](#0-2) 
and are created in `process_action_receipt` whenever `input_data_ids` are not yet satisfied: [4](#0-3) 
They are resolved independently in `process_receipt`'s `Data` arm once the last dependency's `Data` receipt arrives - this path unconditionally fetches and executes `get_postponed_receipt`/`apply_action_receipt` without checking whether the target account still exists, was deleted, or was recreated in the interim: [5](#0-4) 

`action_delete_account` / `remove_account` remove `Account`, `ContractCode`, `AccessKey`s and `ContractData`, but do **not** touch `PostponedReceipt`, `PostponedReceiptId`, or `PendingDataCount` entries: [6](#0-5) [7](#0-6) 

Exploit flow: an attacker who controls account `A` (which must be a namespace whose name a third party can later re-create, e.g. a sub-account under a namespace not solely controlled by the attacker) has a contract on `A` create a chained promise whose final action batch is `Action::DeployContract{code: attacker_wasm}` targeting itself (`predecessor_id == receiver_id == A`), with an `input_data_id` still pending on another cross-contract call. Since this receipt cannot execute yet, it is stored as a `PostponedReceipt`. The attacker then submits a separate `DeleteAccount` transaction signed by `A`'s own key; `DeleteAccount` receipts execute instantly (`Receipt::is_instant_receipt`) and remove `A`'s `Account`/`ContractCode`/keys, but leave the postponed `DeployContract` receipt and its dependency bookkeeping intact. A third party later recreates `A` (`CreateAccount` + `DeployContract{victim_code}` in one receipt/transaction) and funds it. When the attacker's pending data dependency is eventually satisfied (fully attacker-controlled timing, since the attacker created the dependency chain), `process_receipt`'s `Data` arm fetches and executes the stale postponed receipt. `check_account_existence` sees `account.is_some() == true` (the recreated account) and passes; `check_actor_permissions` sees `actor_id (A) == account_id (A)` and passes trivially - neither check distinguishes the old incarnation of `A` from the new one. The attacker's `DeployContract` action then overwrites the victim's just-deployed `ContractCode`.

Note: `runtime/runtime/src/pipelining.rs` already documents and defends against a related but distinct problem - a *same-chunk* preparation-cache staleness issue where `ReceiptPreparationPipeline` might prepare a `FunctionCall` against stale code if the account is deleted/recreated within the same chunk (`block_accounts`, `expected_hash` defense-in-depth) - and there is a regression test for that specific scenario (`test_function_call_after_same_chunk_delete_recreate_resolves_fresh_code`). That mechanism only blocks speculative contract *preparation* for the remainder of the chunk; it does not address the cross-chunk, postponed-receipt authorization gap described here, and no equivalent cleanup or account-incarnation check exists for postponed `DeployContract` receipts that outlive a `DeleteAccount`.

### Impact Explanation
This is an authorization escalation / contract-substitution bug: a third party (or the original victim who recreates an account name they believe is fresh) can have their freshly deployed, funded contract silently replaced by attacker-chosen bytecode with no signature, key, or nonce check ever failing. Since the substituted contract is entirely attacker-authored, it can then drain funds sent to the account by any unsuspecting caller/user of the "new" contract, matching the "authorization escalation across accounts / theft of user funds" bounty category.

### Likelihood Explanation
Exploitability requires: (1) attacker control of account `A` with a full-access key and the ability to author/deploy a contract that creates a promise chain ending in a self-`DeployContract`; (2) `A`'s name must be one that a third party can and will recreate later (e.g., a recyclable sub-account name under some other namespace owner, a common pattern for apps/exchanges that provision and later delete per-user sub-accounts); (3) the attacker must control or predict when the dangling data dependency resolves (fully attacker-controlled since they construct the promise chain themselves). All of these are achievable by an ordinary, unprivileged client using only standard signed transactions and self-authored WASM - no validator, node-operator, or leaked-key access is required. The main constraint is the account-naming precondition (someone else must reuse the exact deleted account name), which narrows real-world applicability but is realistic for platforms that programmatically create/delete/recreate sub-accounts.

### Recommendation
Bind postponed-receipt authorization/execution to the specific account incarnation rather than just the `AccountId` string: e.g., clear all `PostponedReceipt`, `PostponedReceiptId`, and `PendingDataCount` entries for an account as part of `remove_account`/`action_delete_account`, or record an account "generation"/creation-height and reject (or refund/fail) postponed action receipts whose captured generation no longer matches the current account's generation at execution time in `apply_action_receipt`.

### Proof of Concept
Integration/runtime test plan (analogous to existing `runtime/runtime/src/tests/apply.rs` cross-chunk `DeleteAccount` tests):
1. Apply a chunk where account `A` receives a postponed `ActionReceipt` (`predecessor_id == receiver_id == A`) containing `Action::DeployContract{code: attacker_wasm}` with one unmet `input_data_ids` entry (construct directly via `ReceiptV0`/`ActionReceipt` as in `action_receipt_awaiting`), so it is stored via `set_postponed_receipt`/`PendingDataCount`.
2. In the same or a subsequent chunk, apply a `DeleteAccount` receipt for `A` (self-delete, `locked() == 0`) and confirm via `remove_account`/state view that `Account`/`ContractCode` for `A` are gone.
3. Apply a chunk with `CreateAccount(A) + DeployContract{victim_code}` from a distinct predecessor (the "third party"), and commit, asserting `ContractCode` for `A` now hashes to `victim_code`.
4. Apply a chunk delivering the missing `Data` receipt for the earlier dependency (matching `data_id`), triggering `process_receipt`'s `Data` arm to execute the stale postponed receipt.
5. Assert that the execution outcome for that receipt is `Success` (not `AccountDoesNotExist`/`ActorNoPermission`), and that `ContractCode` for `A` now hashes to `attacker_wasm` instead of `victim_code`, proving the silent overwrite.

    action: &Action,
    account: &Option<Account>,
    actor_id: &AccountId,

) -> Result<(), ActionError> {
    match action {
        Action::DeployContract(_)
        | Action::Stake(_)
        | Action::AddKey(_)
        | Action::DeleteKey(_)
        | Action::DeployGlobalContract(_)
        | Action::UseGlobalContract(_)
        | Action::WithdrawFromGasKey(_) => {
            if actor_id != account_id {
                return Err(ActionErrorKind::ActorNoPermission {
                    account_id: account_id.clone(),
                    actor_id: actor_id.clone(),
                }
                .into());
            }
        }

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
