### Title
WFP permit filters override lower-sublayer WDF deny rules via `fwpmFilterFlagClearActionRight` and weight-0xFFFF sublayer, defeating admin firewall block policy - ([File: wfp/wfp_windows.go])

### Summary
`addInterfaceFilter` and `addUDPPortFilter` install PERMIT filters into a dynamically-registered sublayer with weight `0xFFFF` and set `fwpmFilterFlagClearActionRight` on every filter, which by WFP arbitration semantics causes these filters to win over any WDF (Windows Defender Firewall, the default MPSSVC_WF sublayer) deny/block filter matching the same layer/5-tuple. This means an administrator-configured block rule for a hostile remote CIDR targeting the nebula UDP listener port or tun interface is silently overridden, and the blocked traffic reaches the host's UDP socket / tun-routed hosts anyway.

### Finding Description
`registerSublayer` creates a dynamic sublayer with `weight: 0xFFFF`, explicitly chosen "so its filters arbitrate above WDF's default sublayer" [1](#0-0) . Both `addInterfaceFilter` and `addUDPPortFilter` then add PERMIT filters into that sublayer at `FWPM_LAYER_ALE_AUTH_RECV_ACCEPT_V4/V6`, each with `flags: fwpmFilterFlagClearActionRight` [2](#0-1) [3](#0-2) .

The `fwpmFilterFlagClearActionRight` constant is documented in the file itself as existing specifically to prevent "a default WDF block at the same sublayer weight" from winning arbitration [4](#0-3) . Combined with the higher sublayer weight (`0xFFFF` vs WDF's default), WFP evaluates filters across sublayers in weight order and the terminating PERMIT action (`fwpActionPermit` has `FWP_ACTION_FLAG_TERMINATING` set, per the constant definition at line 60) in the higher-weight sublayer is applied before any lower-weight WDF deny filter is even considered, and `ClearActionRight` additionally revokes the right of lower-weight filters to veto the decision.

Consequently, any inbound UDP packet to the nebula listening port (`PermitUDPPort`) or any inbound packet on the nebula tun interface (`PermitInterface`) is allowed through regardless of any WDF block rule an administrator has configured for that same port/interface — including a rule specifically blocking a known-hostile remote CIDR. This is not gated on any Nebula-level authentication; the WFP layer operates purely on network/transport-layer conditions (interface LUID, or UDP+port), so no certificate or handshake validation occurs before the packet is allowed past the OS firewall layer into the Nebula UDP socket.

### Impact Explanation
This is a firewall-bypass: it removes a layer of defense-in-depth an administrator relies on (WDF CIDR-based deny rules) for traffic destined to the nebula listener port or tun interface. An attacker whose source address/CIDR has been explicitly blocked by the administrator can still deliver UDP packets to the nebula listen port (or, once inside the tun interface's permit scope, other packets), because the OS-level block is silently superseded by Nebula's own permit filter. This does not bypass Nebula's own handshake/certificate verification, but it does defeat the administrator's explicit network-layer policy enforcement, which is exactly the "firewall bypass" category the audit scope calls out as acceptable impact.

### Likelihood Explanation
This triggers deterministically whenever Nebula runs on Windows with these WFP filters installed (i.e., whenever `PermitInterface`/`PermitUDPPort` is used) and an administrator has a WDF block rule for the nebula port/interface at the default sublayer weight — which is the documented and intended default WDF placement. No attacker action beyond sending traffic from the blocked CIDR is required; the override is unconditional and applies to 100% of matching packets, not probabilistic.

### Recommendation
Do not blanket-apply `fwpmFilterFlagClearActionRight` with a maximal sublayer weight for all inbound traffic to the nebula port/interface. Instead, scope the permit filters more narrowly (e.g., only interfaces recognized as Nebula-owned, and prefer not clearing action rights so administrator WDF deny rules for specific remote CIDRs remain authoritative), or document explicitly and provide an opt-out configuration so administrators are aware their block rules on the tunnel port/interface will not be enforced by Nebula's WFP bypass. At minimum, surface this behavior prominently in operator-facing documentation/configuration rather than only in source comments.

### Proof of Concept
Integration test plan (Windows, requires admin):
1. Configure a WDF (`netsh advfirewall firewall add rule`) block rule denying inbound UDP from a specific test CIDR (e.g., `203.0.113.0/24`) to the nebula listen port.
2. Call `PermitUDPPort(port)` from `wfp/wfp_windows.go` to install the Nebula bypass filters.
3. From a host within `203.0.113.0/24`, send a UDP packet to the target's nebula listen port.
4. Assert (via packet capture / socket receive on the Nebula listener) that the packet is delivered to the application socket despite the WDF block rule — demonstrating that arbitration favors the permit filter.
5. Compare against a control run without step 2 (i.e., no `fwpmFilterFlagClearActionRight`/high-weight sublayer) where the same packet is correctly dropped by WDF, confirming the override is caused specifically by `registerSublayer`'s weight `0xFFFF` and `addUDPPortFilter`'s `fwpmFilterFlagClearActionRight`.

// registerSublayer adds a session-scoped sublayer with a freshly generated GUID, weight 0xFFFF so its filters arbitrate
// above WDF's default sublayer. The sublayer is dynamic (no PERSISTENT flag) and goes away when the engine handle closes.
func registerSublayer(engine uintptr) (windows.GUID, error) {
	key, err := windows.GenerateGUID()
	if err != nil {
		return windows.GUID{}, fmt.Errorf("GenerateGUID for sublayer: %w", err)
	}

	name, _ := windows.UTF16PtrFromString("Nebula WDF bypass sublayer")
	desc, _ := windows.UTF16PtrFromString("Permit filters bypassing Windows Defender Firewall")
	sl := fwpmSublayer0{
		subLayerKey: key,
		displayData: fwpmDisplayData0{name: name, description: desc},
		weight:      0xFFFF,
	}
