### Title
Exchange withdraw/inject use spot-balance ratio pricing that is inconsistent with (and manipulable through) the swap bonding curve, allowing the pool creator to drain value from `Exchange` pairs - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`ExchangeInjectActuator` and `ExchangeWithdrawActuator` compute the "other side" token amount for liquidity add/remove using the raw current pool reserve ratio (`secondTokenBalance * tokenQuant / firstTokenBalance`), exactly the kind of manipulable spot-price formula described in the report. Meanwhile `ExchangeTransactionActuator` (open to any account) moves the reserves through a completely different Bancor-style bonding-curve formula in `ExchangeProcessor`/`SafeExchangeProcessor`. Because the two formulas diverge, the pool's creator can trade against their own pool to distort the reserve ratio and then withdraw liquidity at a ratio that no longer reflects the value actually backing the pool, extracting more value than they are entitled to.

### Finding Description
`ExchangeWithdrawActuator.execute`/`doValidate` derives `anotherTokenQuant` purely from the instantaneous reserves: [1](#0-0) 
and the equivalent inject path does the same: [2](#0-1) 

This is a naive constant-ratio (spot price) formula. However, the *swap* path that anyone can call, `ExchangeTransactionActuator`, moves the same reserves through `ExchangeCapsule.transaction`, which delegates to a Bancor "relay-supply" bonding curve, not a simple constant-ratio curve: [3](#0-2) [4](#0-3) 

Because withdrawal pricing (linear ratio) and trading pricing (bonding curve with a fixed 1e18 relay supply) are mathematically inconsistent, the reserve ratio right after a large self-trade does not represent the same "fair value" that the bonding curve used to produce it. The pool creator — the only account permitted to call `ExchangeWithdrawActuator`, enforced by the creator check — [5](#0-4) 
can (1) call `ExchangeTransactionActuator` to push the reserve ratio in either direction, (2) immediately call `ExchangeWithdrawActuator`, which prices the withdrawal off that distorted ratio rather than the bonding-curve-consistent value, and (3) trade back. This is the same structural bug class as the reported LimboDAO issue: a reserve-ratio "spot price" is used as a value oracle for a privileged operation (withdraw/inject) while a different, manipulable mechanism (the swap curve here, a UniswapV2 pool there) controls that same ratio, letting a single self-controlled sequence of ordinary signed transactions extract more value than was actually deposited.

### Impact Explanation
A pool creator can repeatedly extract more TRX/TRC10 tokens than the pool's true bonding-curve-backed value, i.e., produce an unbacked balance / drain funds from the `Exchange` reserve, harming future traders who rely on `ExchangeTransactionActuator` pricing against that now-undercollateralized pool. This falls under theft/permanent loss of funds and unbacked balance categories.

### Likelihood Explanation
No special privilege beyond being the creator of one's own `Exchange` pair (created via `ExchangeCreateActuator`, open to any account) and issuing ordinary `ExchangeTransactionContract`/`ExchangeWithdrawContract`/`ExchangeInjectContract` transactions is required. No flashloan or external DeFi composability is even necessary since java-tron's Exchange model has only a single creator/LP and public swappers; the attacker self-funds the manipulation across a short sequence of their own transactions.

### Recommendation
Make the inject/withdraw pricing formula consistent with the swap bonding curve (e.g., derive the withdrawable/injectable amounts from the same relay-supply invariant used in `ExchangeProcessor`/`SafeExchangeProcessor`, or track LP "relay" shares explicitly instead of computing amounts from the instantaneous raw balances), and/or add slippage/rate-of-change limits or a time-weighted reserve check before allowing inject/withdraw immediately following large swaps in the same pool.

### Proof of Concept
1. Attacker calls `ExchangeCreateActuator` to create pair (TokenA, TokenB) with reserves R_a, R_b, becoming its sole creator (only they can later inject/withdraw, per `ExchangeWithdrawActuator.doValidate` creator check).
2. Attacker calls `ExchangeTransactionActuator` to sell a large amount of TokenA into the pool. Reserves move to R_a', R_b' according to the Bancor curve in `ExchangeCapsule.transaction`/`ExchangeProcessor`, skewing the raw ratio R_a'/R_b' away from the curve-consistent marginal price.
3. Attacker immediately calls `ExchangeWithdrawActuator` withdrawing a small `tokenQuant` of TokenA; `anotherTokenQuant` is computed purely from the skewed ratio R_a'/R_b' (`ExchangeWithdrawActuator.java` lines 74-89), yielding more TokenB than the bonding curve would justify.
4. Attacker calls `ExchangeTransactionActuator` again to swap back, restoring most of TokenA, keeping the excess TokenB extracted in step 3.
5. Net effect: attacker's combined TokenA+TokenB holdings increase beyond what the true bonding-curve invariant supports, at the expense of the pool's remaining backing for future swappers.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
