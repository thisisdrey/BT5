### Title
`LinkRepositoryToObjectPool` links a repository to an object pool without verifying both belong to the same storage - (File: `internal/gitaly/service/objectpool/link.go`)

### Summary
### Finding Description
The reported bug class is: a migration/linking operation moves state from one entity to another without verifying that the two entities are compatible (same "base"), silently corrupting or losing the ability to use the migrated state. The closest reachable analog in Gitaly is object pool linking: `LinkRepositoryToObjectPool` builds the target object pool purely from client-supplied proto fields via `objectpool.FromProto` [1](#0-0) , and the RPC handler only validates the *target repository* argument, never checking that the pool's `StorageName` matches the target repository's `StorageName` before calling `pool.Link` [2](#0-1) .

The actual link write happens in `Link`/`getRelativeObjectPath`, which computes the alternates entry purely with `filepath.Rel(repoPath/objects, poolPath)` [3](#0-2) . If `pool` and `repo` resolve to different storage roots, `filepath.Rel` still produces a syntactically valid `../../...` relative path, and this string is written unconditionally into the repository's `objects/info/alternates` file [4](#0-3) . Nothing in `Link`, `linkedToRepository`, or the RPC handler validates the storage names match before the write occurs.

The only place that would catch a cross-storage alternate is at *read* time, in `internal/git/dirs.go`, which rejects any resolved alternate path that is outside the storage root with `alternateOutsideStorageError` [5](#0-4) [6](#0-5) . This means the repository is left in a broken state only when Git objects are subsequently accessed, mirroring the original finding's pattern (an operation "succeeds" without validating compatibility, and the resulting inconsistency is discovered too late for the affected resource — here, the linked repository — to function).

A partial mitigating check exists in the WAL/transaction middleware (`beginTransactionForRepository`), which enforces `alternateStorageName == targetRepo.GetStorageName()` when an "additional repository" is extracted from the request via proto annotations [7](#0-6) . I could not confirm from the available index whether `LinkRepositoryToObjectPoolRequest.ObjectPool` is annotated as an `additional_repository` field consumed by `methodInfo.AdditionalRepo`, so it is uncertain whether this middleware check actually covers this specific RPC, or only applies when transactions/WAL are enabled (it clearly does not apply to `WithDisablePraefect()` / non-transactional legacy code paths used in the RPC's own unit tests [8](#0-7) ).

### Impact Explanation
If the storage-name check is not actually enforced for this RPC (or is bypassed in non-transactional storage configurations), a caller can link a repository to an object pool residing on a different storage. The write to `objects/info/alternates` succeeds silently, but subsequent Git operations on the repository (`ObjectDirectories`/`AlternateObjectDirectories`) will fail with `alternateOutsideStorageError`, rendering the repository's object access broken — a denial-of-service on that repository until an operator manually repairs the alternates file. This matches the spirit of the original report: the operation that "connects" two resources doesn't validate they're of the same base/storage, and the affected resource loses functional access to the state it was supposed to gain (or, worse, its own object resolution breaks).

### Likelihood Explanation
`LinkRepositoryToObjectPool` and `ObjectPool` proto messages are populated with client-supplied `StorageName`/`RelativePath` fields for both the target repository and the object pool [9](#0-8) , so a caller (e.g. a crafted RPC as part of a fork/import flow, where these calls are legitimately used) controls both storage names. Whether this is actually exploitable depends on whether the transaction middleware's storage-match check universally applies to this RPC — this could not be conclusively verified from the indexed code, which is a meaningful gap in this analysis.

### Recommendation
Add an explicit check in the `LinkRepositoryToObjectPool` handler (`internal/gitaly/service/objectpool/link.go`) and/or in `objectpool.Link` requiring `pool.GetStorageName() == repo.GetStorageName()` before proceeding, independent of whether transactional middleware performs an equivalent check. This closes the gap for any storage/transaction configuration where the middleware-level check does not apply.

### Proof of Concept
Not independently reproduced. This is a static-analysis finding based on:
- `objectpool.FromProto` never comparing the pool's storage to any other repository's storage [1](#0-0) .
- `LinkRepositoryToObjectPool` calling `pool.Link(ctx, repo)` with no storage-match validation [10](#0-9) .
- `getRelativeObjectPath` computing a relative alternates path via unguarded `filepath.Rel` [3](#0-2) .
- `alternateOutsideStorageError` only being raised later, at read time, in `internal/git/dirs.go` [6](#0-5) .

I was unable to confirm, given index limits, whether `LinkRepositoryToObjectPoolRequest`'s object-pool field is registered as an `additional_repository` for the transactional storage-match enforcement in `middleware.go`; verifying the proto annotations (`proto/object_pool.proto`) and `protoregistry` method info for this RPC would be necessary to determine whether the middleware-level guard already fully mitigates this in WAL-enabled deployments.

func (s *server) LinkRepositoryToObjectPool(ctx context.Context, req *gitalypb.LinkRepositoryToObjectPoolRequest) (*gitalypb.LinkRepositoryToObjectPoolResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	pool, err := s.poolForRequest(ctx, req)
	if err != nil {
		return nil, err
	}

	repo := s.localRepoFactory.Build(repository)

	if err := pool.Link(ctx, repo); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	return &gitalypb.LinkRepositoryToObjectPoolResponse{}, nil

func getRelativeObjectPath(ctx context.Context, pool, repo *localrepo.Repo) (string, error) {
	poolPath, err := pool.Path(ctx)
	if err != nil {
		return "", fmt.Errorf("getting object pool path: %w", err)
	}

	repoPath, err := repo.Path(ctx)
	if err != nil {
		return "", fmt.Errorf("getting repository path: %w", err)
	}

	relPath, err := filepath.Rel(filepath.Join(repoPath, "objects"), poolPath)
	if err != nil {
		return "", err
	}

	return filepath.Join(relPath, "objects"), nil
}
