### Title
Floor-rounding in `MarketSellAssetActuator.matchSingleOrder` lets an order-book taker under-pay for a filled maker order - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
`MarketSellAssetActuator` implements TRON's on-chain order-book exchange (`MarketSellAssetContract`, reachable by any account that broadcasts a sell-order transaction). When a taker order consumes a maker order's *entire* remaining sell quantity, the taker receives the exact, un-rounded remaining token amount from the maker, while the amount debited from the taker (i.e. what the taker pays the maker) is computed with `MarketUtils.multiplyAndDivide`, which performs a floor division. This is the same asymmetric-rounding pattern as the reported RubiconMarket `buy()` bug: the quantity delivered is exact, but the quantity paid is rounded down, letting the payer keep the rounding remainder as risk-free profit.

### Finding Description
In `matchSingleOrder` [1](#0-0) , when the taker's remaining sell amount exactly matches the maker's remaining sell quantity ("taker == maker" branch), the code does: [2](#0-1) 

`takerBuyTokenQuantityReceive` is set to the **exact** `makerOrderCapsule.getSellTokenQuantityRemain()` (no rounding), while `makerBuyTokenQuantityReceive` — the amount actually deducted from the taker's sell balance and credited to the maker — is computed via `MarketUtils.multiplyAndDivide(makerSellRemainQuantity, makerBuyQuantity, makerSellQuantity, ...)`, which floors the result: [3](#0-2) 

The identical pattern recurs in the "taker > maker" branch [4](#0-3) , where the taker again receives the maker's *full, exact* remaining sell quantity while paying only the floor-rounded `makerBuyTokenQuantityReceive`.

Because the taker receives the exact quantity but pays a floor-rounded price, the difference between the true (fractional) price and the rounded-down price is pocketed by the taker on every fill. This mirrors the report's root cause exactly: `spend = mul(quantity, buy_amt) / pay_amt` rounded down in `RubiconMarket.buy()`.

### Impact Explanation
An account can place a maker sell order and later act as (or collude with) the taker, splitting fills into many small matches that each land on the exact-remainder branch, harvesting the floor-rounding remainder each time. As in the referenced report, the absolute per-trade profit is tiny, but is repeatable an unbounded number of times across independent transactions/blocks with no privileged access required, draining value from counter-parties/maker liquidity over time — an unauthorized transfer of value (theft) enabled purely by transaction broadcasting. This satisfies a Medium-severity, fund-theft-via-rounding-error analog, consistent with the judged severity of the original finding.

### Likelihood Explanation
Any account can create a `MarketSellAssetContract` order (maker) and a matching one (taker); no special permissions, SR/witness status, or trusted role is required — this is purely an order-placer capability already reachable through `MarketSellAssetActuator.execute`/`validate`. Repeated small-quantity trades (choosing sell/buy quantities with a poor GCD ratio to maximize the rounding remainder, as demonstrated in the report's WBTC/GUSD PoC) make the attack practical and profitable when the low decimals / ratio of the token pair are favorable, and TRON's low, predictable energy/bandwidth costs make repeated execution economical.

### Recommendation
Round `makerBuyTokenQuantityReceive` (and the analogous debit-from-taker computations) up rather than down whenever the delivered (`takerBuyTokenQuantityReceive`) side is not itself rounded, i.e. make `MarketUtils.multiplyAndDivide` (or a dedicated ceil-variant) round the amount charged to the payer up to at least preserve the exchange ratio, mirroring the recommended fix of rounding `spend` up in the original report.

### Proof of Concept
1. Attacker (or accomplice) creates a maker sell order for token A with `sellTokenQuantity` and `buyTokenQuantity` chosen such that `buyTokenQuantity / sellTokenQuantity` is a non-terminating/rounding-lossy ratio (e.g., analogous to WBTC/GUSD low-decimal pairing).
2. Attacker submits a taker `MarketSellAssetContract` selling exactly `makerOrderCapsule.getSellTokenQuantityRemain()`'s equivalent quantity so the "taker == maker" branch in `matchSingleOrder` is triggered.
3. `takerBuyTokenQuantityReceive` = exact full remaining token A from maker; `makerBuyTokenQuantityReceive` = `MarketUtils.multiplyAndDivide(...)`, floor-rounded, deducted from taker.
4. Repeat step 2 across many small orders/transactions; each fill leaves a rounding remainder in favor of the taker, which accumulates into net profit exceeding transaction/energy costs, exactly as demonstrated by the original report's repeated-`buy()` PoC.

  public static long multiplyAndDivide(long a, long b, long c, boolean disableMath) {
    try {
      long tmp = multiplyExact(a, b, disableMath);
      return floorDiv(tmp, c, disableMath);
    } catch (ArithmeticException ex) {
      // do nothing here, because we will use BigInteger to compute again
    }

    BigInteger aBig = BigInteger.valueOf(a);
    BigInteger bBig = BigInteger.valueOf(b);
    BigInteger cBig = BigInteger.valueOf(c);

    return aBig.multiply(bBig).divide(cBig).longValue();
  }
