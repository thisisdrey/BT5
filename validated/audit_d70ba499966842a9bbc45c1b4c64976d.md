### Title
Active-permission delegate can hijack full account ownership via AccountPermissionUpdateContract - (File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java)

### Summary
The multisig "required rights" check for `AccountPermissionUpdateContract` (the contract that rewrites an account's Owner/Witness/Active permissions) is exactly the same coarse, bitmap-based `ContractType` gate used for every other contract type. It does not recognize that this particular contract type is special: it can rewrite the account's Owner permission itself, i.e., it can grant its invoker root-level control over the account, not just the privilege level of the permission slot they were given.

### Finding Description
Every transaction's authorization is decided by `TransactionCapsule.checkPermission`/`checkPermissionOperations` (mirrored in `WalletUtil.checkPermissionOperations` and `TransactionUtil.checkPermissionOperations`), which simply tests whether the bit for the transaction's `ContractType` is set in the signer's `Permission.operations` bitmap: [2](#0-1) [3](#0-2) 

`AccountPermissionUpdateContract` (`ContractType` #46) is a normal, addressable entry in that bitmap and is included in the node's `getAvailableContractType()` set, so it can legally be enabled on a non-owner **Active** permission, as shown by the actuator/test enumeration: [4](#0-3) 

Once an Active permission has that single bit set, any keyholder in that Active permission (which can have a threshold as low as 1-of-N and does not require Owner-level trust) can submit an `AccountPermissionUpdateContract` transaction. `AccountPermissionUpdateActuator.validate()` only checks structural well-formedness of the new permissions (key counts, weights, threshold, operations bitmap validity) — it never checks that the *signer's own privilege* is sufficient to author a new Owner permission: [5](#0-4) 

`execute()` then unconditionally applies the attacker-supplied Owner/Witness/Active permissions via `AccountCapsule.updatePermissions`, which fully replaces the Owner permission: [6](#0-5) [1](#0-0) 

This is the same class of bug as the XWiki advisory: a generic "required-rights"/permission classifier enumerates operations by coarse type (ContractType bit / TextArea property) but fails to recognize that one specific instance of that type carries the ability to re-grant elevated rights to itself, so the classifier's pass/fail decision does not reflect the actual privilege being exercised.

### Impact Explanation
Any account owner who grants an Active permission the `AccountPermissionUpdateContract` operation bit (a legitimate, supported configuration intended for delegated permission management) inadvertently gives that Active keyholder full Owner-equivalent control of the account: they can rewrite the Owner permission's keys/threshold to ones they control, lock out the legitimate owner, and reassign every other Active/Witness permission and its operations bitmap (including granting themselves rights over `TransferContract`, `FreezeBalanceContract`, `WithdrawBalanceContract`, etc.). This is a full unauthorized-account-takeover / theft-of-funds primitive reachable by a single signed transaction from a lower-tier keyholder, with no additional signatures or waiting period required beyond the Active permission's own threshold.

### Likelihood Explanation
Exploitation requires only that the account owner has configured an Active permission with the `AccountPermissionUpdateContract` bit enabled — a supported, documented multisig delegation pattern that operators may reasonably adopt (e.g., "let this key manage the active permission set") without realizing it also implies unrestricted rewrite of the Owner permission. Once configured, exploitation is a single, unprivileged, node-reachable transaction (`AccountPermissionUpdateContract`) requiring only the Active permission's threshold of signatures.

### Recommendation
`AccountPermissionUpdateActuator.validate()`/`execute()` should verify that the signer's own permission (the `permission_id` used to authorize this transaction) is at least as privileged as, and does not exceed the scope of, the Owner permission being set — e.g., require that changes to the Owner permission (and to the operations bitmap of other Active permissions) can only be authorized by the Owner permission itself, never by a delegated Active permission, regardless of whether the `AccountPermissionUpdateContract` bit happens to be enabled on that Active permission's operations bitmap.

### Proof of Concept
1. Owner account `A` creates an Active permission `P2` (threshold 1) for a "helper" key `K`, and sets `P2.operations` bit 46 (`AccountPermissionUpdateContract`) — a configuration that passes all current validation in `AccountPermissionUpdateActuator.checkPermission`.
2. Attacker controlling `K` crafts a transaction: `AccountPermissionUpdateContract{owner_address = A, owner = Permission{keys=[K], threshold=1}, actives=[...]}`, signs it with `K`, sets `permission_id = 2` (referencing `P2`).
3. `TransactionCapsule.validateSignature` → `checkPermission` passes because `checkPermissionOperations` finds bit 46 set in `P2.operations`.
4. `AccountPermissionUpdateActuator.execute()` calls `account.updatePermissions(newOwner, ...)`, fully replacing `A`'s Owner permission with one controlled solely by `K`.
5. `K` now has full Owner-level control of account `A`, including the ability to transfer/freeze/withdraw all of `A`'s funds.

  public void updatePermissions(Permission owner, Permission witness, List<Permission> actives) {
    Builder builder = this.account.toBuilder();

    owner = owner.toBuilder().setId(0).build();
    builder.setOwnerPermission(owner);
    if (witness != null && builder.getIsWitness()) {
      witness = witness.toBuilder().setId(1).build();
      builder.setWitnessPermission(witness);
    }

    builder.clearActivePermission();
    if (actives != null) {
      for (int i = 0; i < actives.size(); i++) {
        Permission permission = actives.get(i).toBuilder().setId(i + 2).build();
        builder.addActivePermission(permission);
      }
    }

    this.account = builder.build();
  }

  @Override
  public boolean validate() throws ContractValidateException {

    if (chainBaseManager == null) {
      throw new ContractValidateException(ActuatorConstant.STORE_NOT_EXIST);
    }

    if (this.any == null) {
      throw new ContractValidateException(ActuatorConstant.CONTRACT_NOT_EXIST);
    }

    AccountStore accountStore = chainBaseManager.getAccountStore();
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();

    if (dynamicStore.getAllowMultiSign() != 1) {
      throw new ContractValidateException("multi sign is not allowed, "
          + "need to be opened by the committee");
    }
    if (!this.any.is(AccountPermissionUpdateContract.class)) {
      throw new ContractValidateException(
          "contract type error,expected type [AccountPermissionUpdateContract],real type["
              + any.getClass() + "]");
    }
    final AccountPermissionUpdateContract accountPermissionUpdateContract;
    try {
      accountPermissionUpdateContract = any.unpack(AccountPermissionUpdateContract.class);
    } catch (InvalidProtocolBufferException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractValidateException(e.getMessage());
    }
    byte[] ownerAddress = accountPermissionUpdateContract.getOwnerAddress().toByteArray();
    if (!DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("invalidate ownerAddress");
    }
    AccountCapsule accountCapsule = accountStore.get(ownerAddress);
    if (accountCapsule == null) {
      throw new ContractValidateException("ownerAddress account does not exist");
    }

    if (!accountPermissionUpdateContract.hasOwner()) {
      throw new ContractValidateException("owner permission is missed");
    }

    if (accountCapsule.getIsWitness()) {
      if (!accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("witness permission is missed");
      }
    } else {
      if (accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("account isn't witness can't set witness permission");
      }
    }

    if (accountPermissionUpdateContract.getActivesCount() == 0) {
      throw new ContractValidateException("active permission is missed");
    }
    if (accountPermissionUpdateContract.getActivesCount() > 8) {
      throw new ContractValidateException("active permission is too many");
    }

    Permission owner = accountPermissionUpdateContract.getOwner();
    Permission witness = accountPermissionUpdateContract.getWitness();
    List<Permission> actives = accountPermissionUpdateContract.getActivesList();

    if (owner.getType() != PermissionType.Owner) {
      throw new ContractValidateException("owner permission type is error");
    }
    checkPermission(owner);
    if (accountCapsule.getIsWitness()) {
      if (witness.getType() != PermissionType.Witness) {
        throw new ContractValidateException("witness permission type is error");
      }
      checkPermission(witness);
    }
    for (Permission permission : actives) {
      if (permission.getType() != PermissionType.Active) {
        throw new ContractValidateException("active permission type is error");
      }
      checkPermission(permission);
    }
    return true;
