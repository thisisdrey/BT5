### Title
ETH-Implicit Wallet Contract's EVM `chain_id` Check Does Not Bind to the NEAR Network, Enabling Cross-Network Transaction Replay - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs])

### Summary
The `Wallet Contract` (NEP-518) that is deployed on ETH-implicit accounts validates an embedded Ethereum-style transaction by checking `tx.chain_id` against a compile-time constant `CHAIN_ID`. This constant is baked into the WASM binary at build time and only takes three concrete values: one for mainnet, one for official testnet, and a single shared value (399) for every other NEAR network ("localnet"). Because every non-mainnet/non-testnet NEAR network reuses the exact same WASM binary and the exact same accepted `CHAIN_ID`, and because the ETH-implicit account address is derived purely from the user's Secp256k1 public key (independent of the NEAR network), a signed Ethereum transaction intended for one such network is equally valid on any other network using the "localnet" wallet contract variant.

### Finding Description
`rlp_execute` decodes the RLP transaction and delegates validation to `validate_tx_relayer_data`, which enforces: [1](#0-0) 

The `CHAIN_ID` constant checked here is not derived from the NEAR chain the contract is running on at execution time; it is a value baked into the WASM binary during `cargo build`: [2](#0-1) 

The build script produces exactly three binaries — mainnet (397), testnet (398), and a single "localnet" binary (399) used for every other NEAR network: [3](#0-2) 

At runtime, `eth_wallet_global_contract_hash` resolves the wallet-contract code hash used for a given NEAR `chain_id`. Mainnet and testnet get their own dedicated hashes, but every other `chain_id` (any custom/private/forked NEAR network, sandboxes, alternate testnets, etc.) falls into the same catch-all branch and receives the identical `LOCALNET` contract hash/binary: [4](#0-3) 

This is the exact analog of the external report's root cause: a signed message/transaction is validated using data that does not uniquely bind to the chain it is meant to run on (there `address(this)` without `chainId`; here an EVM `chain_id` field checked against a value that is identical across many distinct NEAR networks). Since the ETH-implicit account ID (and hence the deployed contract's address/context) is derived only from the Secp256k1 public key — not from any NEAR chain identifier — the same key pair produces the same account ID and the same contract on every NEAR network, and a `rlp_execute`-wrapped Ethereum transaction accepted on one "localnet"-class network passes identical validation on any other "localnet"-class network.

### Impact Explanation
Any two NEAR networks that are not the two blessed `mainnet`/`testnet` chain IDs (e.g., a private testnet, a sandbox fork, a staging network, or any other network operators deploy nearcore for) share:
- the same Wallet Contract WASM/hash (`eth_wallet_global_contract_hash` fallback),
- the same accepted EVM `CHAIN_ID` (399),
- the same account-derivation scheme (address == `derive_eth_implicit_account_id(pubkey)`).

If a user (or relayer) holding a valid signed Ethereum transaction for their ETH-implicit account on one such network submits (or an observer replays) that same transaction to another such network where the account has been independently created with matching nonce state (a realistic scenario for shared test fixtures, sandbox environments seeded from the same accounts, or multiple deployments of the same network configuration), the transaction executes identically there too — a replay across chains. This can cause unintended duplicate execution of a signed action (transfer, function call, key management) that the user only intended to authorize once, matching the "double-spend/replay" impact class.

### Likelihood Explanation
This requires two independently-operated, non-official NEAR networks to both use the default "localnet" wallet-contract fallback (the common case for any network that isn't literally `mainnet` or `testnet`) and for the victim account to exist with compatible nonce state on both. This is a realistic condition for NEAR's own sandbox/test tooling and third-party forks/private networks, all of which are legitimate, unprivileged deployments rather than operator-only or malicious-node scenarios.

### Recommendation
Bind the accepted `chain_id` (and/or the wallet-contract's account derivation/validation) to the actual NEAR network identity at build or, preferably, at runtime — e.g., derive the expected EVM `chain_id` from the genesis `chain_id`/network ID rather than a hardcoded fallback shared by all non-mainnet/non-testnet networks, ensuring each distinct NEAR network gets a distinct, non-reusable `CHAIN_ID` value the same way mainnet and testnet already do.

### Proof of Concept
1. Deploy nearcore Network A with `chain_id = "network-a"` and Network B with `chain_id = "network-b"` (neither is `mainnet`/`testnet`/`mocknet`).
2. Both resolve `eth_wallet_global_contract_hash` to the same `LOCALNET` hash/binary (`runtime/near-wallet-contract/src/lib.rs:103`), which enforces `CHAIN_ID == 399` (`internal.rs:20`, `build.rs:16`).
3. Create the same ETH-implicit account (derived from one Secp256k1 key) with matching balance/nonce state on both networks.
4. Sign one Ethereum transaction (`chain_id = 399`, matching nonce) authorizing a transfer/action, and submit it via `rlp_execute` on Network A — it succeeds.
5. Submit the identical RLP-encoded transaction via `rlp_execute` on Network B — `validate_tx_relayer_data`'s `chain_id`/nonce/target checks all pass identically, and the action executes again, demonstrating cross-network replay of the same signed message.

fn validate_tx_relayer_data<'a>(
    tx: &NormalizedEthTransaction,
    target: &'a AccountId,
    context: &ExecutionContext,
    expected_nonce: u64,
) -> Result<TargetKind<'a>, Error> {
    if tx.address.raw() != context.current_address {
        return Err(Error::Relayer(RelayerError::InvalidSender));
    }

    if tx.chain_id != Some(CHAIN_ID) {
