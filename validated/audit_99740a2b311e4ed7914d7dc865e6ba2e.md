### Title
Double-precision reward/brokerage math causes precision loss in SR reward distribution - (File: chainbase/src/main/java/org/tron/core/service/MortgageService.java)

### Summary
`MortgageService` computes witness reward payouts and voter reward withdrawals using Java `double` arithmetic (division followed by multiplication) instead of exact integer or `BigInteger` math. This mirrors the reported `LibUbiquityPool::getDollarInCollateral` class of bug: performing floating-point/rounded division and multiplication in sequence introduces precision loss that can produce incorrect payout amounts, reachable from a normal unprivileged user's `WithdrawBalanceActuator`/`UnfreezeBalance(V2)Actuator`/`VoteWitnessActuator` transactions and from block application (`Manager`) paying standby-witness/block/transaction-fee rewards every cycle.

### Finding Description
Three call sites in `MortgageService` use `double` for reward-related math where the rest of the codebase (e.g. `VoteRewardUtil.computeReward`, the "new" reward algorithm branch in `MortgageService.computeReward(long,long,AccountCapsule)`) correctly uses `BigInteger` with a fixed-point `DECIMAL_OF_VI_REWARD` scaling factor:

- `payReward` computes the brokerage share with `double`: [1](#0-0) 

- `payStandbyWitness` distributes the fixed per-block SR-127 pay pool proportionally to vote count using `double eachVotePay = (double) totalPay / voteSum;` then `(long) (w.getVoteCount() * eachVotePay)`: [2](#0-1) 

- The "old" reward algorithm branch (still used for any cycle prior to `getNewRewardAlgorithmEffectiveCycle()`) computes each voter's share with `double voteRate = (double) userVote / totalVote; reward += voteRate * totalReward;`: [3](#0-2) 

This is invoked from `computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule)` for the pre-new-algorithm cycle range: [4](#0-3) 

Just like `getDollarInCollateral`'s `.div(missingDecimals).div(collateralPrice)` pattern, dividing first (losing precision to a `double`'s ~15-17 significant digits) and then multiplying by a large `totalReward`/`totalPay`/`value` compounds rounding error, and truncation on the final `(long)` cast discards any fractional remainder rather than accounting for it. Because this happens per-witness per-cycle (`payStandbyWitness`, `payReward`) or per-vote per-cycle (`getOldReward`), the sum of all individual payouts will generally not equal the original pool (`totalPay`/`totalReward`/`value`), meaning some SUN value is silently lost or double-counted across the population of stakers/witnesses.

### Impact Explanation
Reward/brokerage math directly affects real TRX balances (`delegationStore.addReward`, `adjustAllowance` → `AccountCapsule.setAllowance` → eventual balance credit on withdraw). Because `double` cannot exactly represent most integer ratios and results are truncated with `(long)`, sums of distributed rewards across all voters/witnesses can diverge from the actual reward pool value that was deducted from the block reward / transaction fee pool. This can lead to under- or over-crediting of voter/witness balances — a form of unbacked-balance / value-leakage bug affecting stake and reward accounting, which is explicitly in-scope ("stake/delegation/reward math"). The magnitude scales with the number of cycles/voters/witnesses affected (particularly all cycles processed before `getNewRewardAlgorithmEffectiveCycle()`, which by construction is retained for legacy chains/testnets and historical cycles).

### Likelihood Explanation
This code path executes automatically on every maintenance cycle boundary (`payStandbyWitness`/`payBlockReward`/`payTransactionFeeReward` from `Manager` block application) and on every voter-initiated reward withdrawal (`WithdrawBalanceActuator`, `UnfreezeBalanceActuator`, `UnfreezeBalanceV2Actuator`, `VoteWitnessActuator`, and the TVM `withdrawReward`/`vote` opcodes) for cycles prior to the new-reward-algorithm cutover — i.e., it is reached by ordinary unprivileged users signing standard transactions, and it fires deterministically (not requiring any adversarial input), so likelihood of triggering rounding drift is effectively certain over time; the only uncertainty is the magnitude of accumulated drift for any given account/witness.

### Recommendation
Replace the `double`-based ratio computations in `MortgageService.payReward`, `payStandbyWitness`, and the old-algorithm branch of `computeReward` with integer/`BigInteger` fixed-point arithmetic that multiplies before dividing (as already done in the new reward algorithm and in `VoteRewardUtil.computeReward`), e.g. `BigInteger.valueOf(totalReward).multiply(BigInteger.valueOf(userVote)).divide(BigInteger.valueOf(totalVote))`. This eliminates floating point rounding error and keeps the sum of distributed shares consistent with the deducted pool amount (subject to controlled, auditable integer truncation/remainder handling).

### Proof of Concept
Given `totalReward = 1_000_000_000L` (1000 TRX, in SUN) split among voters with `totalVote = 3` and three voters each with `userVote = 1`:
- Using `double`: `voteRate = 1.0/3.0 = 0.3333333333333333`; `reward = (long)(0.3333333333333333 * 1_000_000_000) = 333333333` for each voter, summing to `999999999`, one SUN short of `totalReward` — demonstrating an unaccounted-for-value leak analogous to the report's sequential-division rounding loss (`.div(A).div(B)` vs. combined `.div(A*B)`), except here it's `.div(B)` then `.mul(A)` in floating point instead of `BigInteger` fixed-point math used elsewhere in the same class for the "new" algorithm.     long cycle = dynamicPropertiesStore.getCurrentCycleNumber();
    int brokerage = delegationStore.getBrokerage(cycle, witnessAddress);
    double brokerageRate = (double) brokerage / 100;
    long brokerageAmount = (long) (brokerageRate * value);

    delegationStore.addReward(cycle, witnessAddress, value);

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }
