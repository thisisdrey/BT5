Confirmed: `VaultShareToken` inherits `Rescuable` (which provides `GuardianAccessControl`/`Pausable`), but its `transfer`, `transferFrom`, and `_update` ( [1](#0-0) ) never call `whenNotPaused` — the pause capability exists on the contract but is never wired into the token-movement path, unlike `LoansNFT`, which has no `Pausable` machinery at all ( [2](#0-1) ).

### Title
Missing `whenNotPaused` on `VaultShareToken` transfers lets share movement continue during an emergency pause - (File: contracts/VaultShareToken.sol)

### Summary
`VaultShareToken` is `Rescuable` (and therefore `GuardianAccessControl`/OZ `Pausable`)-derived, and its own `rescueERC20Tokens`/`rescueERC721Tokens` are gated `whenNotPaused` [3](#0-2) , but the core value-moving path — ERC20 `transfer`/`transferFrom` via `_update` — has no `whenNotPaused` modifier [1](#0-0) . This mirrors the LensHub finding: every other externally reachable state-changing surface in the protocol's pause matrix is deliberately blocked while paused (see `PortfolioVault`, `Loans`, `LoansExchange`, `TrustedSpender` pause tables in `specs/vault.md`, `specs/loan_permissions.md`, `specs/trusted-spender.md`), but share transfers on `VaultShareToken` slip through.

### Finding Description
`VaultShareToken.pause()`/`unpause()` come from `GuardianAccessControl` and set the contract's `Pausable` state, but that state is only checked by `rescueERC20Tokens`/`rescueERC721Tokens` in `Rescuable`. The actual share-transfer entry points (`transfer`, `transferFrom`, inherited unmodified from OZ `ERC20`) call `_update`, which only enforces the `SHAREHOLDER_ROLE` gate — it never checks `paused()` [4](#0-3) . So calling `vault.pause()` (or pausing `VaultShareToken` directly) halts deposits/redemptions/NAV updates in `PortfolioVault` per its documented pause table [5](#0-4) , but two `SHAREHOLDER_ROLE`-holding accounts can still freely transfer shares between each other while the vault believes it has halted all activity.

### Impact Explanation
If a shareholder's key is compromised or an incident requires an immediate halt of value movement, governance can pause the vault and `Loans`/`LoansExchange`, expecting all state-changing paths to freeze, but a compromised shareholder or attacker with `SHAREHOLDER_ROLE` can still move shares out of a targeted account to another whitelisted address (e.g., a colluding or attacker-controlled shareholder) before the compromised access is revoked. This undermines the incident-response invariant the pause mechanism is meant to provide, similar to how the LensHub bug let profile NFTs move during a governance-declared halt. However, note that `specs/vault.md` explicitly documents "Share transfers restricted to `SHAREHOLDER_ROLE` holders only" as the sole transfer control and does not list share transfer under the `whenNotPaused` table at all [6](#0-5)  — this could reflect either an unintentional gap or an accepted design choice (shares are not directly redeemable for assets without going through `redeem`/`withdraw`, which ARE `whenNotPaused`-gated). Since redemption itself is blocked when paused, the material impact is limited to reassignment of share ownership among already-whitelisted shareholders, not a direct drain of USDC/vault assets.

### Likelihood Explanation
Low-to-medium. It requires (a) the attacker or compromised party to already hold `SHAREHOLDER_ROLE` (a privileged/whitelisted status gated by `WHITELISTER_ROLE`), and (b) a scenario where governance relies on `pause()` to stop share reassignment specifically. Given `SHAREHOLDER_ROLE` is itself a permissioned allowlist controlled by `WHITELISTER_ROLE`, and the actual redemption of value (`redeem`/`withdraw`) is correctly gated, this weakens rather than eliminates the emergency-response guarantee.

### Recommendation
Add a `whenNotPaused` check to `VaultShareToken._update` (or override `transfer`/`transferFrom`) so that share transfers are blocked while the token (or its linked vault) is paused, consistent with how `Loans`, `PortfolioVault`, `LoansExchange`, and `TrustedSpender` gate their respective transfer/value-moving surfaces.

### Proof of Concept
1. Guardian/Admin grants `SHAREHOLDER_ROLE` to `attacker` and `victim` is already a shareholder holding shares.
2. `victim`'s key is compromised, or governance detects suspicious activity and calls `vault.pause()` (or `shareToken.pause()` if pausable independently), expecting all state-changing operations to halt.
3. Attacker (from compromised `victim` account or a colluding shareholder) calls `shareToken.transferFrom(victim, attacker, amount)` or `shareToken.transfer(attacker, amount)` — this succeeds because `_update` never checks `paused()`, despite `Pausable.EnforcedPause()` being expected to halt all value movement.
4. Shares are now reassigned to `attacker`, who can wait for unpause and then `requestRedeem`/`redeem` normally, having successfully moved ownership during what governance believed was a full halt.

Note: I could not fully confirm from the indexed contents whether `VaultShareToken` exposes its own standalone `pause()`/`unpause()` (via `GuardianAccessControl`) independent from `PortfolioVault.pause()`, or whether the two are meant to be triggered together operationally — the `specs/vault.md` documentation only describes `PortfolioVault`'s own pause table and does not explicitly cross-reference `VaultShareToken.pause()` in that list. If `VaultShareToken` pausing is intentionally out of scope for share-transfer restriction (by design, since transfers are meant to remain available for compliance operations), this finding should be treated as a documentation/intent question rather than a bug — a Devin session with the actual SECURITY.md / repository would be needed to confirm the intended threat model here.

  function rescueERC20Tokens(
    address token,
    uint256 amount
  ) external whenNotPaused onlyRole(GUARDIAN_ROLE) returns (uint256 rescued) {
    require(recoveryAddress != address(0), RecoveryAddressNotSet());
    uint256 balance = IERC20(token).balanceOf(address(this));
    rescued = amount >= balance ? balance : amount;
    if (rescued > 0) {
      IERC20(token).safeTransfer(recoveryAddress, rescued);
      emit ERC20TokensRescued(token, rescued, recoveryAddress);
    }
  }

  /// @inheritdoc IRescuable
  function rescueERC721Tokens(address token, uint256 tokenId) external whenNotPaused onlyRole(GUARDIAN_ROLE) {
    require(recoveryAddress != address(0), RecoveryAddressNotSet());
    IERC721(token).safeTransferFrom(address(this), recoveryAddress, tokenId);
    emit ERC721TokensRescued(token, tokenId, recoveryAddress);
  }
