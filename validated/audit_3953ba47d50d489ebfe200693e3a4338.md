### Title
Dust `DepositToken` transfers let an attacker fill a victim's per-account token list, griefing `deposit`/`issue` via `MAX_TOKENS_PER_USER` - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
The kernel report is a liveness/DoS regression: a defensive change added "just to silence a sanitizer splat" introduced deadlocks on a previously working path. The Metronome analog is `Pool.onlyIfAdditionWillNotReachMaxTokens` — a defensive cap (`MAX_TOKENS_PER_USER = 30`) added to bound iteration in `debtPositionOf`/`depositOf`/`debtOf`. Because `DepositToken._transfer` unconditionally calls `pool.addToDepositTokensOfAccount(recipient)` whenever a recipient's balance goes 0 → >0, any unprivileged user can force entries into another account's list with dust transfers, until the cap is hit. Once `debtTokensOfAccount + depositTokensOfAccount == 30` for the victim, every subsequent `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` reverts with `UserReachedMaxTokens`, which in turn reverts `DepositToken.deposit(onBehalfOf_=victim)`, `DepositToken.transfer(to=victim)`, `DebtToken.issue` for a new synthetic, and `DepositToken.seize(to=victim)` during liquidation.

### Finding Description
`Pool.addToDepositTokensOfAccount` is guarded by `onlyIfAdditionWillNotReachMaxTokens(account_)`, which reverts when the combined length reaches 30: [1](#0-0) [2](#0-1) 

`DepositToken._transfer` calls it on any first-time receive — no opt-in from the recipient: [3](#0-2) 

`DepositToken.transfer` only checks the *sender's* unlocked balance (`_revertIfLocked(_msgSender, amount_)`), so a debt-free attacker can freely move dust: [4](#0-3) 

Attack path (unprivileged EOA):
1. For each of the pool's listed `DepositToken`s, attacker calls `deposit(dust, attacker)` (attacker bears only dust + deposit fee).
2. Attacker calls `depositToken.transfer(victim, 1)` for each token, filling `depositTokensOfAccount[victim]` up to `30 - debtTokensOfAccount[victim].length`.
3. Thereafter: any `deposit(_, victim)` on a token the victim doesn't already hold reverts; `DebtToken.issue`/`SmartFarmingManager.leverage` for any synthetic the victim doesn't already hold reverts inside `_mint` → `addToDebtTokensOfAccount`; and `Pool.liquidate(...)` seizing into a liquidator account at cap reverts.

The invariant broken is liveness: a mechanism intended to bound iteration cost becomes an attacker-controlled freeze on an account's ability to take new positions. The pause/shutdown flags, `nonReentrant`, `SynthContext` checks, and `_revertIfLocked` do not stop it — the attack uses only the normal `transfer` path. Effectiveness depends on the deployed configuration: it fully blocks new deposit-token types only when the number of listed deposit tokens plus the victim's existing debt tokens can reach 30; with fewer listed collaterals the attacker can still deny any *new* `DebtToken` issuance once the combined count hits the cap (debt tokens are not transferable, so debt slots can't be forced).

### Impact Explanation
Temporary freezing/liveness denial of the victim's protocol usage: the victim cannot receive any new collateral type (including via liquidation `seize`) and cannot mint any new synthetic debt until they notice and manually transfer the dust away (their dust balance is unlocked since the tokens carry no debt, so `transfer` succeeds and `removeFromDepositTokensOfAccount` frees the slot). No theft of funds; impact is a per-account griefing DoS with low attacker cost (dust deposits + gas).

### Likelihood Explanation
Low-to-moderate. Requires the pool to list enough deposit tokens to reach the 30-slot cap together with the victim's debt tokens, and the victim cannot be permanently harmed — they can self-recover by sending the dust onward. The attack is repeatable after every cleanup, so it can be used to keep a targeted account (e.g., a liquidator or leveraged-position holder) unable to open new debt positions.

### Recommendation
Do not revert inside `addTo*TokensOfAccount` on behalf of the recipient; instead enforce the cap only where it is actually needed (e.g., skip list insertion for dust below a threshold, or make `debtPositionOf` iterate over a bounded view). Alternatively, let `DepositToken._transfer` tolerate the cap (emit the transfer but skip registration when full) so unsolicited dust cannot block the recipient, and keep the hard revert only in `deposit`/`issue` initiated by the account owner.

### Proof of Concept
Reproducible in Hardhat using the existing fixture pattern from `test/Pool.test.ts` ("should revert when reach max tokens"):
1. Deploy pool with N real `DepositToken`s (or the maximum 30).
2. Attacker: for each `depositToken_i`: `depositToken_i.deposit(1, attacker)` then `depositToken_i.transfer(victim, 1)` until `pool.getDepositTokensOfAccount(victim).length + getDebtTokensOfAccount(victim).length == 30`.
3. Assert: `depositToken_new.deposit(1, victim)` reverts `UserReachedMaxTokens`; `debtToken_new.issue(1, victim)` reverts `UserReachedMaxTokens`; a `pool.liquidate` seizing into a capped liquidator reverts.
4. Assert recovery: `depositToken_i.connect(victim).transfer(attacker, 1)` frees a slot.
