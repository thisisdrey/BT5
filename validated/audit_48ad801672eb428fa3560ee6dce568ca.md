### Title
Attacker can permanently/DoS-block a victim's collateral deposits and debt minting by filling the victim's `MAX_TOKENS_PER_USER` account list via dust deposits/transfers - ([File: contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
The Vim `ex_buffer_all` null-pointer dereference is a crash-style DoS triggered through a reachable code path. The closest reachable analog in Metronome is the account-token-list cap: every `DepositToken.deposit`, `transfer`/`transferFrom`, `seize`, and `DebtToken.issue` adds the token to the recipient's `depositTokensOfAccount`/`debtTokensOfAccount` set in `Pool`, and `Pool.addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` reverts with `UserReachedMaxTokens` once the combined count reaches `MAX_TOKENS_PER_USER = 30`. An unprivileged attacker can fill a victim's list with dust, causing all subsequent deposits of new collateral types and mints of new debt tokens for that victim to revert. [1](#0-0) [2](#0-1) 

### Finding Description
`DepositToken.deposit(amount_, onBehalfOf_)` accepts any `onBehalfOf_` (only a zero-address check) and calls `_mint(onBehalfOf_, ...)`, which calls `pool.addToDepositTokensOfAccount(account_)` whenever the recipient's prior balance was zero. [3](#0-2) [4](#0-3) 

`addToDepositTokensOfAccount` enforces `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) < MAX_TOKENS_PER_USER` and reverts otherwise — and this revert propagates up through `_mint`, reverting the entire `deposit`. [1](#0-0) [5](#0-4) 

The same accounting exists on the debt side: `DebtToken._mint` calls `pool.addToDebtTokensOfAccount(account_)` on a first-time mint, and `DebtToken._burn` only removes the entry when the account's balance hits exactly zero. [6](#0-5) [7](#0-6) 

Attack path (all unprivileged, no privileged role needed):

1. Pool has N listed deposit tokens (governor-capped at 30, so up to 30 entries are possible).
2. Attacker calls `depositToken_i.deposit(dust, victim)` for each listed deposit token the victim does not yet hold. Each call mints dust to the victim and appends the token to `depositTokensOfAccount[victim]`.
3. Alternatively/additionally, the attacker deposits for themselves and calls `transfer(victim, dust)`; `_transfer` also appends to the recipient's list. `seize` during liquidation likewise appends to the liquidator's list.
4. Once the victim's combined list length hits 30, every `deposit`/`issue`/`mint`/`transfer`/`seize` that would add a *new* token to the victim's account reverts with `UserReachedMaxTokens`.

### Impact Explanation
This is a liveness/availability break of the protocol's core invariant that any user can post collateral and mint debt:

- The victim cannot deposit any collateral token not already in their list, and cannot mint any new debt token. During adverse price movement the victim cannot add a different collateral type to restore health, so a position that would have been saved is forcibly liquidated — indirect loss of user funds.
- Liquidations can also be griefed in the reverse direction: `Pool.liquidate` → `DepositToken.seize` → `_transfer` → `addToDepositTokensOfAccount(liquidator)` reverts if the liquidator's list is full, reverting the liquidation transaction.
- Clearing entries requires the victim to fully zero each dust balance (transfer/withdraw each token), and each dust deposit can be repeated by the attacker cheaply, so the DoS is renewable. Attacker cost is dust + gas; blocked operations are unbounded in value.

### Likelihood Explanation
Medium-low likelihood but trivially executable:

- Requires only standard public entry points (`DepositToken.deposit` with `onBehalfOf_ = victim`, or `transfer`), no privileged role, no oracle manipulation, no malformed inputs.
- Requires the pool to list enough deposit tokens to fill the 30-slot cap (debt tokens count too, but debt tokens are non-transferable and only enter the victim's list via `issue`, which requires the victim's own healthy position — so the deposit-token side is the practical vector).
- Mitigation: the victim can evict dust entries by zeroing balances, so the DoS is temporary rather than permanent; however, the attacker can front-run remediation with fresh dust deposits.
- No modifier blocks it: `deposit` is `whenNotPaused nonReentrant onlyIfDepositTokenExists`, none of which prevent third-party `onBehalfOf_` deposits; `transfer` only checks the *sender's* unlocked balance via `_revertIfLocked`. [8](#0-7) [9](#0-8) 

### Recommendation
- Do not add tokens to the recipient's account list for zero/dust-effective amounts, or gate `addTo*TokensOfAccount` behind a minimum amount in USD terms.
- Make `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` non-reverting on cap (return bool and skip accounting) and instead bound iteration in `debtPositionOf`/`depositOf`/`debtOf`, so a full list cannot revert balance-changing operations.
- Alternatively restrict `deposit`'s `onBehalfOf_` and `seize`'s recipient list-add so third parties cannot grow a victim's list without consent (e.g., only add on the recipient's own first deposit).

### Proof of Concept
Hardhat sketch against deployed/forked contracts:

```ts
// assume `pool` lists depositTokens[0..k] and victim holds none of them
for (const dt of depositTokens) {
  await underlying(dt).approve(dt.address, 1);
  // mint 1 wei of msdToken to the victim -> adds dt to victim's list
  await dt.connect(attacker).deposit(1, victim.address);
}
// victim's combined list is now at MAX_TOKENS_PER_USER
await expect(
  otherDepositToken.connect(victim).deposit(parseEther('1'), victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// victim also cannot mint a new debt token type
await expect(
  newDebtToken.connect(victim).issue(amount, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// liquidations paying a not-yet-held deposit token to a full liquidator also revert
await expect(
  pool.connect(liquidator).liquidate(synth, victim, debtToCover, fullLiquidatorDepositToken)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

Caveat: severity depends on deployed pool configuration (enough listed deposit tokens to reach 30 combined entries); if fewer than 30 tokens are listed, the cap is unreachable and this specific vector does not apply.
