### Title
Floating-point precision loss in TRC10 bancor-style exchange calculation allows value extraction from the pool - (File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java)

### Summary
The Zoth incident stemmed from a flawed collateral/balance calculation that let an attacker withdraw more value than they deposited. The analogous unprivileged, reachable calculation in java-tron is the TRC10 bancor-relay exchange pricing formula used by `ExchangeTransactionContract`, `ExchangeInjectContract`, and `ExchangeWithdrawContract`, all triggerable by any signed transaction / `/wallet/exchangetransaction` API call.

### Finding Description
`ExchangeTransactionActuator.execute()` computes the counter-token amount owed to the caller via `exchangeCapsule.transaction(tokenID, tokenQuant, dynamicStore.allowStrictMath(), allowHarden())` [1](#0-0) , which is the same amount already fetched (and applied to the exchange balances) inside `doValidate()` [2](#0-1) .

When `allowHarden()` is false (the non-hardened code path, gated by `AbstractExchangeActuator.allowHarden()` reading `allowHardenExchangeCalculation()` off the `DynamicPropertiesStore`) [3](#0-2) , `ExchangeCapsule.transaction()` uses the legacy `ExchangeProcessor`, which implements the bancor relay pricing with native Java `double` arithmetic and `Maths.pow`: [4](#0-3) 

This float-based calculation is well known to suffer rounding/precision loss for small trade sizes and extreme pool ratios; repeatedly executing many small `ExchangeTransactionContract` trades against the same TRC10 exchange lets an attacker accumulate a systematic rounding bias in their favor, extracting more of the counter-asset from the exchange pool than their supplied token is actually worth — directly analogous to Zoth's flawed collateral-calculation bug that let a user redeem more collateral than deposited.

The codebase already contains a fix for this exact bug class: `SafeExchangeProcessor`, which redoes the same formula using `BigDecimal` with explicit scale/rounding control instead of raw doubles [5](#0-4) , and `ExchangeCapsule.transaction()` only uses this safe path when `hardenedCalc` is true [6](#0-5) . This confirms the maintainers themselves recognize the legacy `ExchangeProcessor` double-math path as unsafe/imprecise; any chain instance or period where the hardening proposal (`allowHardenExchangeCalculation`) is not yet activated remains exposed to the precision-based extraction.

### Impact Explanation
An attacker able to submit `ExchangeTransactionContract` transactions (any account, unprivileged) can repeatedly trade tiny amounts against a TRC10 exchange to accumulate rounding-error profit, draining real TRX/TRC10 value from the pool — an unbacked-balance / theft-of-funds condition matching the required "concrete unauthorized account operation, theft ... of funds" bar.

### Likelihood Explanation
Exploitability depends entirely on whether `allowHardenExchangeCalculation` is active on the target chain (mainnet has since enabled the hardened path via the corresponding hard-fork proposal, mirrored by `ProposalUtil`/`ProposalService` references) [7](#0-6) . On any deployment/fork where this proposal has not been activated (default/legacy state), every `ExchangeTransactionContract`, `ExchangeInjectContract`, and `ExchangeWithdrawContract` call still executes the vulnerable double-math `ExchangeProcessor`, requiring no special privilege — just the ability to broadcast a signed transaction, making likelihood high on any not-yet-hardened chain.

### Recommendation
Ensure `allowHardenExchangeCalculation` is unconditionally enabled (or remove the legacy double-math `ExchangeProcessor` code path entirely) so all TRC10 exchange trade/withdraw/inject calculations always route through `SafeExchangeProcessor`'s `BigDecimal`-based, explicitly-rounded arithmetic, closing the precision-extraction window for any environment that has not yet activated the hardening proposal.

### Proof of Concept
1. On a chain/fork where `allowHardenExchangeCalculation` is not activated, create or locate a TRC10 `Exchange` pool.
2. Repeatedly submit small `ExchangeTransactionContract` trades (`quant` values chosen to maximize rounding bias in `exchangeToSupply`/`exchangeFromSupply`'s `double` conversions) via `/wallet/exchangetransaction`.
3. Observe that, over many iterations, the attacker's cumulative received counter-token amount exceeds the fair-value output computed by the `BigDecimal`-based `SafeExchangeProcessor` reference implementation, demonstrating value extraction from the pool's reserves at the expense of other liquidity participants.

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }
