### Title
`GET /v2/attachments/<hash>` serves any `AtlasDB` row with `was_instantiated = 1` with no check against `attachment_instances`, breaking the BNS attachment/hash commitment invariant - (File: `stackslib/src/net/api/getattachment.rs`, `stackslib/src/net/atlas/db.rs`)

### Summary
`RPCGetAttachmentRequestHandler::try_handle_request` resolves an attachment purely via `AtlasDB::find_attachment`, which only checks the `attachments.was_instantiated` flag and never joins/validates against the `attachment_instances` table (the table that records on-chain BNS/Atlas commitments). Any attachment content that ends up marked `was_instantiated = 1` in the `attachments` table — including content inserted via `insert_instantiated_attachment` without a corresponding on-chain `AttachmentInstance` — is served as a 200 response to any anonymous remote client.

### Finding Description
The intended invariant is: bytes served at `GET /v2/attachments/<hash>` == bytes committed on-chain by some BNS/Atlas contract call (an `AttachmentInstance` with `content_hash == hash`). The handler code shows this equality is not enforced at the serving layer at all: [1](#0-0) 

and the backing query: [2](#0-1) 

`find_attachment` runs `SELECT content, hash FROM attachments WHERE hash = ?1 AND was_instantiated = 1` — it never references `attachment_instances`, so it cannot distinguish "content whose hash matches a real on-chain commitment" from "content that was merely written into the `attachments` table with `was_instantiated=1`."

The only gate that is supposed to prevent uncommitted content from reaching `was_instantiated=1` is upstream, in the Atlas downloader (`stackslib/src/net/atlas/download.rs`). In `AttachmentsDownloader::run`, once a batch finishes, every attachment in `context.attachments` is unconditionally written via `insert_instantiated_attachment`, and `find_all_attachment_instances` is only used to gather instances to notify — its result is not used to gate the insert: [3](#0-2) 

Likewise in `check_attachment_instances`, an "inboxed" (uninstantiated) attachment is promoted to instantiated as soon as any `AttachmentInstance` references its hash — but this path relies on `context.attachments`/inbox content actually having been validated against the requested `content_hash` when downloaded from a peer. The response parser used when fetching an attachment from a remote peer does not itself verify that the returned bytes hash to the requested `content_hash`: [4](#0-3) 

Given the premise established by the referenced prior finding (that a malicious peer's `GetAttachmentResponse` can be persisted via `insert_instantiated_attachment` without any content-hash verification against the on-chain `content_hash` it was requested for), the `attachments` table can end up containing a row with `was_instantiated=1` for a hash that was never emitted by any on-chain `AttachmentInstance`/BNS operation. Because `RPCGetAttachmentRequestHandler`/`find_attachment` performs no cross-check against `attachment_instances`, that uncommitted content is then served to any unauthenticated remote client as if it were BNS-committed data.

### Impact Explanation
Any remote, unauthenticated client can retrieve attacker-controlled bytes from `GET /v2/attachments/<hash>` and receive a `200 OK` with `GetAttachmentResponse{ attachment }` containing content that no on-chain name/zonefile operation ever committed to. This breaks the "attachment/BNS mismatch" invariant explicitly listed as a High-severity impact category: the node serves non-canonical state (attacker-supplied bytes) as if it were canonical BNS-committed data. This is repeatable per hash and does not require any privileged role — it only requires the attacker to have gotten the poisoned row into the peer's `AtlasDB` beforehand (via the separate, already-established insertion vulnerability) and then issue a plain HTTP GET.

### Likelihood Explanation
- Preconditions: the victim node's `AtlasDB` already contains a `was_instantiated=1` row for a hash with no corresponding `attachment_instances` entry (established by the referenced prior finding on `insert_instantiated_attachment`/peer response handling).
- Attacker cost: a single HTTP GET to a node's public RPC port (`/v2/attachments/<hash>`), no secret/auth token required, no special role.
- Reachability: `/v2/attachments/:hash` is a registered public RPC endpoint with no auth gate (`getattachment::RPCGetAttachmentRequestHandler::new()` registered without `auth_token`), confirmed at: [5](#0-4) 
- Repeatable: yes, for every poisoned hash, indefinitely, until the row is evicted.

### Recommendation
Modify `AtlasDB::find_attachment` (or the RPC handler) to require that the requested hash correspond to at least one `Checked`, `is_available` row in `attachment_instances` (i.e. join `attachments` with `attachment_instances WHERE content_hash = ?1 AND status = Checked`) before serving content. Additionally, harden `AttachmentsDownloader` (`insert_instantiated_attachment` call sites in `download.rs`) to only persist downloaded attachment content when `attachment.hash()` matches the `content_hash` of the specific `AttachmentRequest`/`AttachmentInstance` that solicited it, and never write to the `attachments` table for hashes with zero corresponding `attachment_instances` rows.

### Proof of Concept
Rust test in `stackslib/src/net/api/tests/getattachment.rs` (or a new test module):
1. Construct an in-memory `AtlasDB::connect_memory(...)`.
2. Call `atlas_db.insert_instantiated_attachment(&Attachment{content: b"attacker-content".to_vec()})` directly — simulating the prior finding's outcome — without ever inserting any matching row into `attachment_instances`.
3. Confirm precondition: `atlas_db.find_all_attachment_instances(&attacker_attachment.hash())` returns an empty `Vec` (no on-chain commitment exists).
4. Build a `StacksHttpRequest::new_getattachment(host, attacker_attachment.hash())`, run it through `test_rpc` (as in `test_try_make_response`), and assert:
   - Response status code is `200`, not `404`.
   - `response.decode_atlas_get_attachment().unwrap().attachment.content == b"attacker-content"`.

This demonstrates that `RPCGetAttachmentRequestHandler` serves attacker content for a hash with no `AttachmentInstance` backing, violating the attachment/BNS commitment equality.
