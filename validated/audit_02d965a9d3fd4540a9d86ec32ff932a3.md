### Title
Locked collateral can be withdrawn while debt remains via same-transaction inflation of `unlockedBalanceOf` / post-check `debtPositionOf` (File: contracts/DepositToken.sol, contracts/SmartFarmingManager.sol)

### Summary
Metronome does not snapshot "locked" collateral — `lockedBalanceOf`/`unlockedBalanceOf` are computed *dynamically* from the spot oracle every time `withdraw`, `transfer`, `withdrawFrom`, or `SmartFarmingManager.flashRepay` is executed. Analogous to the Carapace issue (backing funds released while obligations remain), any condition that transiently inflates the collateral's oracle price or deflates the synthetic-debt price causes collateral that must back outstanding debt to be released to the depositor, leaving the pool with unbacked (bad) debt.

### Finding Description
`DepositToken.withdraw` only enforces `_revertIfLocked`, which reads `unlockedBalanceOf` (`contracts/DepositToken.sol:383-398`):

```
_unlockedBalance = Math.min(
    balanceOf[account_],
    _pool.masterOracle().quoteUsdToToken(address(underlying), _issuableInUsd.wadDiv(collateralFactor))
);
```

`_issuableInUsd` comes from `Pool.debtPositionOf` (`contracts/Pool.sol:248-266`), which is a pure spot-oracle computation: `_depositInUsd` and `_debtInUsd` are priced through `masterOracle().quoteTokenToUsd` at call time (`Pool.depositOf` / `Pool.debtOf`, `Pool.sol:227-288`).

There is no persistence of how much collateral is obligated — if the oracle momentarily reports a higher collateral price (e.g., a vault-share/interest-bearing collateral whose `pricePerShare`/exchange-rate oracle component is inflatable by a same-transaction donation, or a collateral priced through a manipulable DEX-derived feed), `unlockedBalanceOf` returns up to the full balance and the user withdraws collateral that is still needed to back debt. After prices normalize, `debtPositionOf` shows debt > issuable limit: the funds that were supposed to back the obligation have left the `Treasury` (`DepositToken._withdraw` → `treasury().pull`, `DepositToken.sol:541-554`).

The same pattern exists in `SmartFarmingManager.flashRepay` (`SmartFarmingManager.sol:98-144`): `depositToken_.flashWithdraw` deliberately skips `_revertIfLocked` (`DepositToken.sol:245-250` — no lock check), so the *only* thing preventing extraction of debt-backing collateral is the final spot `debtPositionOf` health check, which is equally price-manipulable in the same transaction. `SmartFarmingManager.leverage` (`SmartFarmingManager.sol:155-211`) has the same terminal check, so a manipulated collateral price also lets the caller mint debt against phantom collateral value and keep the swapped-out real assets.

### Impact Explanation
Direct protocol insolvency: collateral backing live debt exits the Treasury while the synthetic debt remains outstanding. After the price reverts, the position is deeply unhealthy but the collateral is gone, so liquidation cannot recover it — the loss is socialized across synthetic-token holders and other depositors. This is exactly the impact class of the Carapace report (backing released while coverage still required), realized through Metronome's purely oracle-driven lock accounting.

### Likelihood Explanation
Reachable by any unprivileged EOA in a single transaction: deposit → issue debt → manipulate the collateral's spot oracle component (donation to a share-price-based collateral vault, or AMM-priced feed) → `withdraw`/`flashRepay`/`leverage` → restore price. It requires that at least one deployed collateral's `MasterOracle` quote path is same-transaction manipulable; the code provides no TWAP, cooldown, or margin to mitigate this — the lock is recomputed live on every call. If all configured collaterals are priced exclusively by manipulation-resistant push oracles (e.g., Chainlink), the exploit path is not reachable and this degrades to a design dependency on oracle correctness rather than an exploitable bug — this dependency on external oracle configuration is the main uncertainty of this finding.

### Recommendation
Do not derive the releasable collateral purely from the instantaneous oracle. Options: (a) apply an additional safety margin (e.g., require `debt < issuableLimit * margin` after withdrawal instead of `<=`), (b) enforce `_revertIfLocked` inside `flashWithdraw`/`withdrawFrom` as well and repay debt *before* releasing collateral in `flashRepay`, and (c) ensure `MasterOracle` pricing for share-type collateral uses manipulation-resistant rates (e.g., total-assets-based NAV with donation resistance) rather than spot exchange rates.

### Proof of Concept
Hardhat fork sketch (using the repo's test harness pattern from `test/Pool.test.ts`):

```ts
// attacker deposits collateral C (priced via manipulable share-rate oracle)
await c.approve(msdC.address, MaxUint256);
await msdC.deposit(amount, attacker.address);
// issue debt up to limit
const { _issuableInUsd } = await pool.debtPositionOf(attacker.address);
await msXDebt.issue(maxIssuableSynth, attacker.address);

// same tx or next block: inflate collateral price
// e.g., donate underlying to the yield vault whose pricePerShare feeds the oracle,
// or manipulate the AMM the oracle reads
await underlying.transfer(vPool.address, donation); // bumps share price

// unlockedBalanceOf now covers (nearly) the whole balance
const unlocked = await msdC.unlockedBalanceOf(attacker.address);
await msdC.withdraw(unlocked, attacker.address); // passes _revertIfLocked

// oracle price reverts
// assert: (await pool.debtPositionOf(attacker))._isHealthy == false
// assert: attacker holds the collateral, debt remains unbacked -> bad debt
```

The analogous flashRepay variant calls `smartFarmingManager.flashRepay(msX, msdC, fullBalance, 0)` under an inflated collateral price so the terminal `PositionIsNotHealthy` check is bypassed.
