### Title
Missing Preorder Traversal in `verify_field_definition` Allows `Vector<Function(...)>` Struct Fields to Bypass Feature Gate — (`third_party/move/move-bytecode-verifier/src/features.rs`)

---

### Summary

`FeatureVerifier::verify_field_definition` calls `verify_signature_token` on the **top-level** `SignatureToken` of a struct field without recursive traversal. `verify_signature_token` only matches `SignatureToken::Function(..)` at the root. A field typed `Vector(Box<Function(...)>)` has `Vector` at the root, so the check passes silently. This allows a `CompiledModule` with a function-typed struct field to be published on-chain when `enable_function_values=false`, violating the invariant the feature gate is meant to enforce.

---

### Finding Description

**The gap:**

`verify_field_definition` (line 104):
```rust
self.verify_signature_token(&field.signature.0)
```
passes only the root token. `verify_signature_token` (line 174):
```rust
if !self.config.enable_function_values && matches!(tok, SignatureToken::Function(..)) {
```
matches only the root. `Vector(Box<Function(...)>)` has root `Vector`, so it returns `Ok(())`.

**Contrast with `verify_signatures`** (lines 162–165), which correctly uses preorder traversal:
```rust
for t in tok.preorder_traversal() {
    self.verify_signature_token(t)...
}
```

**Why `verify_signatures` does not cover this:** `verify_signatures` iterates `self.code.signatures()`, which is the `Signature` table (locals, type arguments). Struct field types are stored as `TypeSignature` directly inside `FieldDefinition.signature` — they are **not** entries in the `Signature` table. So the preorder-traversal path in `verify_signatures` never sees struct field tokens.

**Concrete attack:**
1. Craft a `CompiledModule` with a struct field `signature: TypeSignature(Vector(Box<Function([], [], AbilitySet::EMPTY)>))`.
2. Submit a package-publish transaction.
3. `verify_module_with_config` → `FeatureVerifier::verify_module` → `verify_struct_defs` → `verify_field_definition` → `verify_signature_token(Vector(...))` → `Ok(())`.
4. Module is committed to the write set with a function-typed struct field while `enable_function_values=false`.

---

### Impact Explanation

The module is published with a type that the feature gate is explicitly designed to prohibit. This is an unauthorized state transition caused by broken bytecode verification. The committed module write set contains a module that violates the mainnet invariant for the `enable_function_values` feature flag.

Secondary exploitation is constrained: `verify_code` blocks `PackClosure`/`PackClosureGeneric`/`CallClosure` bytecodes, so no function value can be created or invoked at runtime. However, the published module permanently embeds a disallowed type in on-chain state, and once the feature is enabled the module's struct fields become live with function types that were never subject to the full ability/safety checks that would normally accompany a feature-enabled publish.

---

### Likelihood Explanation

Any unprivileged account can submit a package-publish transaction. Constructing a `CompiledModule` in memory with the described field type requires no special access — it is a straightforward binary format manipulation, as demonstrated by existing test infrastructure in the same repo. The bypass is deterministic and reproducible.

---

### Recommendation

Replace the flat call in `verify_field_definition` with a preorder traversal, mirroring `verify_signatures`:

```rust
fn verify_field_definition(&self, struct_idx: usize, field: &FieldDefinition) -> PartialVMResult<()> {
    for tok in field.signature.0.preorder_traversal() {
        self.verify_signature_token(tok)
            .map_err(|e| e.at_index(IndexKind::StructDefinition, struct_idx as u16))?;
    }
    Ok(())
}
```
