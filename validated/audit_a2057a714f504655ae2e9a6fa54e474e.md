### Title
Unauthenticated `header.RecvError` with guessed `RemoteIndex` and spoofed source address can tear down a legitimate tunnel - ([File: outside.go])

### Summary
`Interface.handleRecvError` accepts `header.RecvError` packets before any handshake/AEAD authentication and looks up the tunnel purely from `h.RemoteIndex` via `f.hostMap.QueryReverseIndex`, then checks only that the UDP source address matches `hostinfo.GetRemote()`. An attacker who guesses a live 32-bit `RemoteIndex` and spoofs the source UDP address to match the victim's current remote endpoint can trigger `f.closeTunnel(hostinfo)` and `f.handshakeManager.DeleteHostInfo(hostinfo)`, tearing down an authenticated session without possessing any keys.

### Finding Description
In `outside.go`, `readOutsidePackets` dispatches `header.RecvError` packets to `handleRecvError` before any decryption or handshake state check [1](#0-0) . `handleRecvError` then:
1. Gates on `acceptRecvErrorConfig.ShouldRecvError(addr)`, which for the default `"always"` config always returns `true` [2](#0-1) .
2. Looks up the hostinfo purely from the attacker-supplied `h.RemoteIndex` via `f.hostMap.QueryReverseIndex(h.RemoteIndex)` [3](#0-2) .
3. Compares only `hostinfo.GetRemote()` against the UDP source address of the packet (`hr != addr`) [4](#0-3) .
4. If they match, calls `f.closeTunnel(hostinfo)` and `f.handshakeManager.DeleteHostInfo(hostinfo)`, which deletes the hostinfo from the hostmap and pending handshake state [5](#0-4) [6](#0-5) .

None of these checks constitute cryptographic authentication — `RemoteIndex` is a locally-assigned 32-bit index sent in cleartext on every packet (observable to an on-path/network attacker or guessable by brute force against a small active session count), and UDP source address is trivially spoofable for a connectionless protocol. This is a documented, known tradeoff in Nebula's design: `handleRecvError` explicitly logs `"Someone spoofing recv_errors?"` when the address check fails, showing that the authors already anticipated and accepted this as a known best-effort (not authenticated) check [4](#0-3) .

### Impact Explanation
This is an unauthenticated remote DoS: an attacker who can spoof UDP source addresses and either observe or brute-force a live `RemoteIndex` can force teardown of an established, authenticated tunnel between two legitimate peers, requiring them to re-handshake. It does not break encryption, authentication, or allow data exfiltration/injection — the impact is limited to local teardown of hostmap state (session disruption), which nebula's own default config (`listen.accept_recv_error: always`) and code comments treat as an accepted risk. Operators concerned about this can already set `listen.accept_recv_error: never` or `private` to mitigate.

### Likelihood Explanation
Requires (a) spoofing the UDP source address to match the victim's current remote endpoint — feasible on networks without egress source-address filtering (BCP38 not enforced), and (b) guessing/observing a valid `RemoteIndex` for an active session — a 32-bit value, sent in cleartext in every packet header, so on-path observation is trivial and blind brute force is impractical at scale but easier if the attacker can observe any packet from the flow. This is a real but already partially-acknowledged and mitigatable weakness rather than a bypass of some invariant nebula claims to enforce; the code's own defensive log message ("spoofing recv_errors?") shows the authors treat this check as heuristic best-effort, not a security boundary.

### Recommendation
Nothing to add beyond what's already configurable: operators wanting stronger protection should set `listen.accept_recv_error: never` (already supported) to fully disable processing of `RecvError` packets, since no cleartext field in the `RecvError` packet can be made attacker-unforgeable without adding cryptographic authentication (e.g., binding `RecvError` to a MAC over the AEAD key, which would be a larger protocol change out of scope for a targeted fix).

### Proof of Concept
Unit test in `outside_test.go` (or new test file) using a real `Interface`/`HostMap` fixture:
1. Establish a hostinfo in `f.hostMap` with `ConnectionState` set and `SetRemote(addr)` to some `netip.AddrPort` `A`, and register its `localIndexId`/`RemoteIndex` in the reverse index (`f.hostMap.Indexes`).
2. Set `f.acceptRecvErrorConfig = recvErrorAlways`.
3. Call `f.handleRecvError(A, &header.H{RemoteIndex: <that index>})` from a synthetic caller with no possession of `hostinfo.ConnectionState` keys, spoofing source `addr = A`.
4. Assert `f.hostMap.QueryVpnAddr(vpnAddr)` returns `nil` afterward (proving `closeTunnel` executed) — expected: it does execute, confirming the documented spoof-address-match teardown path.
5. Repeat with `addr != A` and assert the hostinfo is **not** removed, confirming the mismatch branch at `outside.go:564-570` is the only protection, and that `ShouldRecvError`/`acceptRecvErrorConfig = recvErrorNever` fully blocks the path (`outside.go:542-548`).

func (s recvErrorConfig) ShouldRecvError(endpoint netip.AddrPort) bool {
	switch s {
	case recvErrorPrivate:
		return endpoint.Addr().IsPrivate()
	case recvErrorAlways:
		return true
	case recvErrorNever:
		return false
