I found a solid analog: the `ExchangeInjectActuator` and `ExchangeWithdrawActuator` for TRON's built-in Bancor-style token exchange compute a proportional "other side" token amount at execution time with no user-supplied slippage bound, unlike `ExchangeTransactionActuator`, which explicitly has an `expected` field to guard against this exact class of bug.

### Title
Exchange inject/withdraw lack slippage protection, letting the pool state change between submission and execution cause unexpected value transfer — ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java])

### Summary
`ExchangeInjectContract` and `ExchangeWithdrawContract` only carry a `quant` field for the token side the caller specifies; the "other token" amount is derived purely from the exchange pool's current balances at validate/execute time [1](#0-0) . This mirrors the reported Tokemak issue where `previewMint`'s output depends on volatile contract state between the moment the user decides on an amount and the moment the transaction executes, so the user can receive/pay a materially different amount than intended, with no way to bound it.

### Finding Description
In `ExchangeInjectActuator.execute`, `anotherTokenQuant` is computed from the live `firstTokenBalance`/`secondTokenBalance` of the `ExchangeCapsule` fetched inside the same execute call: [2](#0-1) 

The same pattern (no bound) exists in `doValidate`, where the ratio is recomputed from the exchange's balances at validation time: [3](#0-2) 

`ExchangeWithdrawActuator` has the identical pattern — `anotherTokenQuant` derived from current pool balances with no minimum/maximum guard: [4](#0-3) 

Contrast this with `ExchangeTransactionActuator`, which was explicitly designed with a slippage guard: the caller supplies `expected`, and `doValidate` rejects the transaction if the computed `anotherTokenQuant` is less than that: [5](#0-4) 

Because `ExchangeInjectContract`/`ExchangeWithdrawContract` protobuf messages have no analogous `expected`/minimum field [6](#0-5) , any unprivileged party can broadcast `ExchangeTransactionContract` trades against the same exchange (this is a public, unprivileged operation, not creator-restricted, per `ExchangeTransactionActuator.doValidate`) to shift `firstTokenBalance`/`secondTokenBalance` between the time the injector/withdrawer signs their transaction and the time it is actually applied in a block. When the inject/withdraw transaction is finally processed, the actuator recomputes the ratio against the shifted pool state and moves funds accordingly — with the caller having had no way to cap the amount they contribute or floor the amount they receive.

### Impact Explanation
- For `ExchangeInjectActuator`: the exchange creator (only the creator may call inject, per `accountCapsule.getAddress().equals(exchangeCapsule.getCreatorAddress())` check) can be forced to contribute far more of the "other token" than they intended to maintain the pool ratio, since `anotherTokenQuant` is deducted directly from their account balance with no cap [7](#0-6) .
- For `ExchangeWithdrawActuator`: the creator can receive less of the "other token" than expected when withdrawing liquidity, because `anotherTokenQuant` is credited back based on the live ratio, with no minimum floor [8](#0-7) .
This results in concrete, unbacked value loss for the account performing the operation — actual on-chain balance movement determined by a manipulable/racing pool state, not by the value the user intended to commit or accept.

### Likelihood Explanation
Any unprivileged account can broadcast `ExchangeTransactionContract` trades to shift the pool ratio between when the victim signs an inject/withdraw transaction and when it lands in a block; multiple `ExchangeTransactionContract`s can execute in the same block ahead of the inject/withdraw, and there's no re-check of caller intent since no minimum/maximum bound field exists on `ExchangeInjectContract`/`ExchangeWithdrawContract`. This makes the scenario readily and repeatably triggerable by ordinary transaction broadcasters, with no special privilege beyond knowing which exchange to trade against.

### Recommendation
Add a `expected_another_quant` (or min/max) bound field to `ExchangeInjectContract` and `ExchangeWithdrawContract`, and validate the computed `anotherTokenQuant` against it in `ExchangeInjectActuator.doValidate`/`ExchangeWithdrawActuator.doValidate`, mirroring the existing `expected` check already implemented in `ExchangeTransactionActuator.doValidate` [5](#0-4) .

### Proof of Concept
1. Attacker/other user observes exchange `X` with balances `(A, B)`.
2. Creator of exchange `X` signs an `ExchangeInjectContract` (or `ExchangeWithdrawContract`) transaction expecting ratio `A:B` to compute `anotherTokenQuant`.
3. Before that transaction is included, the attacker broadcasts one or more `ExchangeTransactionContract` trades against exchange `X`, shifting the balances to `(A', B')` — a legitimate, unprivileged operation validated purely by `ExchangeTransactionActuator.doValidate` [5](#0-4) .
4. The creator's inject/withdraw transaction then executes against `(A', B')` in `ExchangeInjectActuator.execute`/`ExchangeWithdrawActuator.execute`, deducting/crediting an `anotherTokenQuant` computed from the shifted state [2](#0-1) , with no on-chain mechanism for the creator to have bounded that amount.
