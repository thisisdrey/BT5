### Title
Unbounded, zero-fee accumulation of `DelegatedResource`/`DelegatedResourceAccountIndex` records enables permanent chain-state bloat (Denial of Service) - (File: actuator/src/main/java/org/tron/core/actuator/DelegateResourceActuator.java)

### Summary
`DelegateResourceContract` (and the analogous TVM-native `delegateresource` opcode / `FreezeBalanceActuator` legacy path) lets any account that owns at least 1 TRX of frozen resource create a permanent, uniquely-keyed record for every distinct `(owner, receiver)` pair it delegates to. Neither the number of distinct receivers, nor the number of `DelegatedResource`/`DelegatedResourceAccountIndex` records an account can create, is bounded. Unlike `VoteWitnessActuator`, which caps votes at `MAX_VOTE_NUMBER` [3](#0-2) , or `FreezeBalanceActuator`, which caps `frozenCount` to 0/1 [4](#0-3) , delegation has no such cap. This mirrors the Eclipse Milo bug class (CVE-2022-25897): a cheap, attacker-controlled operation that permanently accumulates server-side state with no automatic reclamation, eventually exhausting storage/memory across every full node that maintains chain state.

### Finding Description
`DelegateResourceActuator.execute()` calls `delegateResource()`, which for every `(ownerAddress, receiverAddress)` pair:
1. Creates/updates a `DelegatedResourceCapsule` keyed by `DelegatedResourceCapsule.createDbKeyV2(from, to, lock)` [5](#0-4) [6](#0-5) .
2. Creates two additional persistent index records in `DelegatedResourceAccountIndexStore` via `delegateV2()`, one keyed by `V2_FROM_PREFIX+from+to` and one by `V2_TO_PREFIX+to+from` [7](#0-6) .

`calcFee()` for this actuator returns `0` [8](#0-7) , so the only cost to the attacker is ordinary bandwidth/energy consumption of a small transaction — which can be paid entirely out of free daily bandwidth quota. Validation only checks that `receiverAddress != ownerAddress`, that the receiver account exists, is non-contract, and that the minimum frozen/delegated balance (as low as 1 TRX, `TRX_PRECISION`) is available [9](#0-8) . There is no limit on the number of *distinct* receiver addresses a single owner can delegate to, and no limit on the number of owners that can delegate to a single receiver.

Because each new `(owner, receiver)` pair produces new DB keys (not an update to an existing bounded-size list), an attacker can:
- Pre-fund/create many receiver accounts (a one-time, self-funded cost), then
- Repeatedly issue `DelegateResourceContract` transactions from one or many owner accounts to those receivers, each creating brand-new, permanent entries in `DelegatedResourceStore` and `DelegatedResourceAccountIndexStore`.

These records are only removed by an explicit, separate `UnDelegateResourceContract`/`UnfreezeBalanceActuator` transaction issued by the same owner [10](#0-9)  — the attacker simply never sends it, exactly paralleling the Milo PoC that leaves subscriptions open by never closing them with `deleteSubscription=True`.

Additionally, the `DelegatedResourceAccountIndexStore.getV2Index()` used to answer the public `getDelegatedResourceAccountIndexV2` gRPC/HTTP API performs an unbounded `prefixQuery` scan over all records for the queried address and sorts them in memory [11](#0-10) , so as the attacker inflates one address's fan-out, that address's own account-index queries (reachable by any anonymous API client) become increasingly expensive.

### Impact Explanation
This allows an unprivileged, low-cost attacker to permanently and unboundedly grow two on-chain state stores (`DelegatedResourceStore`, `DelegatedResourceAccountIndexStore`) that every full node, solidity node, and PBFT node must persist and load into its state database indefinitely. Over time this leads to unbounded disk/database growth, degraded snapshot/sync times, and increasingly expensive linear scans on the `getDelegatedResourceAccountIndexV2` query path — a resource-exhaustion condition consistent with CWE-770, ultimately threatening node stability/availability (the same "Denial of Service" impact class as the referenced Milo advisory), rated High under the same rationale used for CVE-2022-25897 (network-reachable, no privileges required, availability impact).

### Likelihood Explanation
High. The only requirements are (a) 1 TRX minimum in frozen/delegatable balance per unique receiver relationship, and (b) enough bandwidth/energy for the transaction itself, both of which are attainable using free daily bandwidth quota and minimal TRX. No special privileges (SR/witness/committee) are required — any ordinary account can broadcast `DelegateResourceContract` transactions.

### Recommendation
Introduce a hard cap (similar to `MAX_VOTE_NUMBER` for votes, or `frozenCount` for freezing) on the number of distinct delegation relationships (`toAccounts`/`fromAccounts`) an address may maintain simultaneously in `DelegatedResourceAccountIndexStore`, and/or charge a real fee (non-zero `calcFee()`) proportional to the marginal state growth for `DelegateResourceContract`, so that creating new persistent `(owner, receiver)` records is not effectively free. Additionally, consider paginating/limiting `DelegatedResourceAccountIndexStore.getV2Index()`'s `prefixQuery` result set exposed via the public API to bound query cost.

### Proof of Concept
1. Attacker account `A` freezes the minimum bandwidth/energy balance (1 TRX, satisfying `frozenBalance >= TRX_PRECISION`).
2. Attacker creates (or reuses) `N` receiver accounts `R1..RN` (each a normal, non-contract account).
3. Attacker repeatedly broadcasts `DelegateResourceContract{owner=A, receiver=Ri, balance=1_000_000 (1 TRX in sun), resource=BANDWIDTH}` for `i=1..N`, paying only ordinary bandwidth (satisfiable from free daily quota), never issuing `UnDelegateResourceContract`.
4. Each call inserts one `DelegatedResourceCapsule` and two `DelegatedResourceAccountIndexCapsule` records that are never cleaned up (see `DelegateResourceActuator.delegateResource()` [12](#0-11) ).
5. Repeating with many distinct owner/receiver address pairs (addresses are free to generate) grows `DelegatedResourceStore`/`DelegatedResourceAccountIndexStore` without bound across the network, and querying `getDelegatedResourceAccountIndexV2(A)` becomes progressively more expensive as `N` grows (`prefixQuery` scan over all `N` entries) [13](#0-12) .
