Audit Report

## Title
Fee-refund conversion in `pallet-asset-conversion-tx-payment` uses unprotected post-dispatch AMM spot price, letting a user's own call manipulate their fee refund - (File: `substrate/frame/transaction-payment/asset-conversion-tx-payment/src/payment.rs`)

## Summary
`SwapAssetAdapter::correct_and_deposit_fee` quotes the native-to-`asset_id` refund conversion via `S::quote_price_exact_tokens_for_tokens(A::get(), asset_id, refund_amount, true)` strictly after the user's own dispatched `call` has executed, using the pool's live post-dispatch reserves. Since the same extrinsic's `call` can move the reserves of the exact pool used for this refund conversion (e.g., via `swap_exact_tokens_for_tokens` in the same or a `utility.batch` call), the refund is priced off a value the caller directly influenced moments earlier, with no bound tying it back to the pre-dispatch quote used at `withdraw_fee` time.

## Finding Description
`withdraw_fee` (payment.rs L142-146) quotes and withdraws the fee asset using `quote_price_tokens_for_exact_tokens` before the call dispatches, so this step is unaffected by manipulation inside the call. [1](#0-0) 

`post_dispatch_details` in `lib.rs` calls `correct_and_deposit_fee` only after the call has already been dispatched. [2](#0-1) 

Inside `correct_and_deposit_fee`, the refund is re-quoted from the pool's *current* reserves via `S::quote_price_exact_tokens_for_tokens`, and this quote is then used as the `amount_out_min` for the immediately-following `swap_exact_tokens_for_tokens` call. [3](#0-2) 

`get_reserves`/`quote_price_exact_tokens_for_tokens` in `pallet-asset-conversion` read the pool account's instantaneous balances with no averaging or TWAP. [4](#0-3) 

The quote-then-swap pair executes atomically within the same extrinsic (no other party can intervene between them), so the only exploitable window is the caller's own dispatched `call`, which runs strictly before this quote and can shift the pool's reserves. There is no mechanism comparing the post-dispatch quote to the pre-dispatch quote from `withdraw_fee`, and the only validation performed (`F::can_deposit`) checks depositability, not fairness of the price. This confirms the reported flaw: the refund conversion price is taken from a spot source that the same transaction's own logic can move before it is read.

## Impact Explanation
This falls under "public underpriced work" / value-conservation issues for `pallet-asset-conversion` pools: an unprivileged account paying fees in a non-native asset can bias the native→`asset_id` refund swap price by moving that pool's reserves within its own dispatched call, extracting more `asset_id` from pool liquidity than a fair-price refund would yield. This is a genuine design gap: the refund quote is not anchored to the pre-dispatch price and has no slippage/TWAP protection against self-manipulation.

## Likelihood Explanation
The attack requires the attacker's own call to materially move the specific `native`/`asset_id` pool's reserves, and requires `refund_amount` to be non-trivial (i.e., actual post-dispatch weight noticeably less than the estimated weight) for the extractable value to be non-negligible. Because the same pool must be moved and (implicitly) reverted afterward by the attacker to realize profit, and AMM swap fees are paid on both legs of that round trip, net profitability depends heavily on the refund size relative to the capital/fees needed to move and restore the pool — this is not automatically profitable in the general case, unlike a typical unbacked-mint bug. The mechanism is real, but its practical exploitability is conditional on pool depth, fee tier, and refund magnitude, which the report does not quantify.

## Recommendation
- Anchor the post-dispatch refund conversion to the pre-dispatch quoted rate (e.g., cap `refund_asset_amount` by the rate captured in `withdraw_fee`), or
- Return unused fee-asset credit directly instead of re-swapping post-dispatch, or
- Use a manipulation-resistant price reference (time-weighted) for the refund leg rather than instantaneous reserves.

## Proof of Concept
1. Attacker configures `ChargeAssetTxPayment` with `asset_id = X`, where the `X`/native pool `P` has limited liquidity.
2. `withdraw_fee` quotes/withdraws `asset_fee` of `X` at `P`'s pre-manipulation price (payment.rs L142-146).
3. The dispatched `call` (or a `utility.batch` sub-call) swaps a large amount of `X` for native in `P`, pushing `P`'s reserves so that native→`X` becomes more favorable.
4. `correct_and_deposit_fee` computes a non-zero `refund_amount` (native) and requotes `refund_asset_amount` from `P`'s now-skewed reserves (payment.rs L262-265), then executes `swap_exact_tokens_for_tokens` at that skewed rate, paying the attacker more `X` than a fair-price refund would (payment.rs L283-297).
5. In a later transaction, the attacker reverses the step-3 swap; net profitability depends on pool depth/fees versus the size of the manipulated refund, which would need to be measured via an integration/property test constructing this exact sequence against `pallet-asset-conversion` and `SwapAssetAdapter`.
