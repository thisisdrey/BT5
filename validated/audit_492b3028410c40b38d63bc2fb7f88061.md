### Title
Attachment response hash never validated before reliability scoring in `AttachmentsBatchStateContext::extend_with_attachments` - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`extend_with_attachments` calls `response.decode_atlas_get_attachment()` and, on successful decode, unconditionally calls `report.bump_successful_requests()` without ever comparing the returned attachment's actual hash to the requested `request.content_hash`. Any peer can return arbitrary attachment bytes that merely decode successfully (any content) and still be credited as a "successful" response, inflating its `ReliabilityReport` score used for peer prioritization.

### Finding Description
In `extend_with_attachments`: [1](#0-0) 
the loop only checks: (1) is there a response at all (else `bump_failed_requests`), and (2) does `decode_atlas_get_attachment()` succeed (else `bump_failed_requests`). If decoding succeeds, `self.attachments.insert(response.attachment)` and `report.bump_successful_requests()` are called with no comparison against `request.content_hash` (the `AttachmentRequest` struct that was used to issue the request, which carries the expected `content_hash`) [2](#0-1) .

This is asymmetric with the equivalent inventory-response handling (`extend_with_inventories`), which has the identical "decode succeeds -> bump_successful_requests" pattern but for inventories there is no per-item content hash to check, so this is the first spot in this batch-processing pipeline where an actual content-integrity check against a wire-independent value (`content_hash`) would be expected and is missing.

`ReliabilityReport::bump_successful_requests` increments both `total_requests_sent` and `total_requests_success` [3](#0-2) , directly raising `ReliabilityReport::score()` [4](#0-3) , which is the sole basis for `Ord`/`PartialOrd` on `ReliabilityReport` [5](#0-4)  and consequently for `AttachmentRequest::cmp`, which picks the "most reliable source" via `get_most_reliable_source` (`max_by_key(|(_,v)| v.score())`) [6](#0-5) . The updated reports are persisted into `self.reliability_reports` in `AttachmentsDownloader::run` and reused across future batches [7](#0-6)  and also feed `AttachmentsInventoryRequest::cmp` ordering for inventory-page requests [8](#0-7) .

**Mitigating factor found during trace:** Although the reliability score can be gamed, the wrong-hash attachment does not get mis-attributed to the requested content. Downstream, `AttachmentsDownloader::run` resolves pending instances using `attachment.hash()` (the actual hash of the bytes the peer returned) via `context.attachments_batch.resolve_attachment(&attachment.hash())`, not `request.content_hash` [9](#0-8) . So a bad-hash payload cannot be substituted for the genuinely-requested content — it is simply stored in the atlasdb under its own (real) hash, unrelated to the instance that was actually being resolved, and the originally-requested attachment instance remains unresolved and gets retried. This means the vulnerability does **not** result in forged/wrong content being served as canonical attachment data for a specific BNS name/instance; its effect is confined to peer reliability-score poisoning.

### Impact Explanation
A malicious peer can repeatedly return any decodable-but-wrong-hash attachment payload to gain undeserved reliability credit, causing the node to prefer that peer (via `get_most_reliable_source`/`AttachmentRequest::cmp` and `AttachmentsInventoryRequest::cmp`) for future attachment and inventory requests over honest peers. This wastes the node's request budget on a peer that never actually supplies the correct data (each attempt fails to resolve the real instance and the batch is retried, up to `max_attachment_retry_count`), delaying legitimate BNS attachment resolution. However, because the actual instance-resolution step re-derives the hash from the returned bytes rather than trusting `request.content_hash`, no wrong data is ever stored as the canonical content for a given attachment instance/name. This is a lower-severity peer-selection integrity issue rather than a genuine "serving wrong state as canonical" or "attachment/BNS mismatch" bug as defined in scope.

### Likelihood Explanation
Trivially reachable: any peer configured as a data-URL source for Atlas sync (an outbound sync peer with a reachable `data-url`) can respond to `/v2/attachments/{content_hash}` GET requests with arbitrary bytes that merely parse as a valid attachment payload. No secret, signature, or privileged role is required — this matches the "unprivileged remote peer" threat model. The attack is repeatable indefinitely across sync batches.

### Recommendation
In `extend_with_attachments`, after `decode_atlas_get_attachment()` succeeds, compute `response.attachment.hash()` and compare it to `request.content_hash` before calling `report.bump_successful_requests()`; treat a mismatch identically to a failed/undecodable response (`report.bump_failed_requests()`), and do not insert the attachment into `self.attachments`.

### Proof of Concept
Add a test in `stackslib/src/net/atlas/tests.rs` that constructs an `AttachmentRequest` with a known `content_hash`, builds a `BatchedRequestsResult` whose `succeeded` map contains that request paired with an HTTP response encoding a *different* attachment payload (mismatched hash), calls `AttachmentsBatchStateContext::extend_with_attachments`, and asserts that the resulting `ReliabilityReport.total_requests_success` is **not** incremented (currently it is, demonstrating the bug) — i.e., assert `report.total_requests_success == 0` after the call, which fails against current code showing `total_requests_success == 1`.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }
