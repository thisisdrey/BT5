Audit Report

## Title
Forgeable `sender` in `EthereumSystemV2::register_token`/`add_tip` lets any AssetHub account impersonate the system-frontend pallet and spoof the message origin sent to Ethereum - (File: `bridges/snowbridge/pallets/system-v2/src/lib.rs`)

## Summary
`snowbridge_pallet_system_v2::register_token` (and `add_tip`) only checks `T::FrontendOrigin::ensure_origin(origin)`, i.e., that the XCM origin equals `Location::new(1,[Parachain(ASSET_HUB_ID), PalletInstance(FRONTEND_PALLET_INDEX)])`, but never binds the call-data `sender: Box<VersionedLocation>` argument to that authenticated origin. [1](#0-0) [2](#0-1)  Both the `DescendOrigin` instruction and the `WithComputedOrigin` barrier wrapper treat `DescendOrigin` as an unconditional, universally-permitted origin transformation with no authorization check, confirmed directly in the executor: `DescendOrigin(who) => self.do_descend_origin(who)` simply appends the junction to the current origin with no `Aliasers`/permission gate. [3](#0-2) [4](#0-3)  The Bridge Hub `WithComputedOrigin` barrier likewise applies leading `DescendOrigin`/`UniversalOrigin` prefixes to the transport-layer origin before evaluating `AllowExplicitUnpaidExecutionFrom<... Equals<SnowbridgeFrontendLocation> ...>`, confirmed generically by its implementation and test suite (`computed_origin_should_work`, `allow_explicit_unpaid_with_computed_origin`). [5](#0-4) [6](#0-5)  This confirms the claim's core technical premise: any message from AssetHub carrying a leading `DescendOrigin(PalletInstance(FRONTEND_PALLET_INDEX))` will pass both the Barrier and `FrontendOrigin::ensure_origin` check regardless of which account or pallet inside AssetHub actually authored the message, since the transport-level origin for any message from AssetHub is always `Location::new(1,[Parachain(ASSET_HUB_ID)])` before `DescendOrigin` is applied.

## Finding Description
The generic XCM executor semantics substantiate the exploit mechanism claimed: `DescendOrigin` performs `self.context.origin.append_with(who)` unconditionally on whatever the current context origin is, with no check against `Aliasers` or any other gate. [4](#0-3)  `Transact` then converts this fully attacker-composable origin via `Config::OriginConverter::convert_origin` and dispatches the call with it. [7](#0-6)  Bridge Hub's `Barrier` uses `WithComputedOrigin` to evaluate the inner `AllowExplicitUnpaidExecutionFrom<(..., Equals<SnowbridgeFrontendLocation>, ...)>` against the origin *after* leading `DescendOrigin`/`UniversalOrigin` instructions are folded in — this is exactly what the `WithComputedOrigin` code and its own doc-comment describe ("any barriers... interpreted based on the computed origin rather than the original message origin"). [8](#0-7) [6](#0-5)  The regression test cited in the claim demonstrates that an ordinary signed AssetHub account can, via `PolkadotXcm::execute` + `InitiateTransfer`, cause a fully attacker-supplied `remote_xcm` to be executed by a destination chain's XCM executor. [9](#0-8)  That test only targets `AliasOrigin`, and the corresponding fix (`AllowedAliasOrigin`, `prdoc/pr_12159.prdoc`) is scoped specifically to the `EthereumBlobExporter`/`XcmConverter`'s export-to-Ethereum path — it does not gate `DescendOrigin`-based forgery of a `Transact` call targeting `snowbridge_pallet_system_v2::register_token` on Bridge Hub itself, which is a structurally distinct code path (ordinary inbound XCMP execution on Bridge Hub, not `ExportMessage`). This is consistent with the claim's assertion that the fix does not cover this gap.

I was unable to fully confirm two remaining pieces within the available tool budget: (1) the exact value/type of `SnowbridgeFrontendLocation` used in the `AllowExplicitUnpaidExecutionFrom` list at Bridge Hub versus `AllowFromEthereumFrontend`'s check (both appear to reference the AssetHub/system-frontend pallet location, but I could not retrieve the literal constant definition before the tool budget ran out), and (2) whether AssetHub's own outbound-message-construction path (`InitiateTransfer`, or another instruction capable of relaying to Bridge Hub) is reachable by a signed user with a fully attacker-controlled `remote_xcm` targeting Bridge Hub specifically (as opposed to only Ethereum, which is what the located test exercises). The generic mechanism (`WithComputedOrigin` + unconditional `DescendOrigin`) is confirmed at the primitive level, and the test proves the general capability of signed users to relay attacker-chosen `remote_xcm` payloads through `InitiateTransfer`, but I could not fully trace AssetHub's `Barrier`/`SafeCallFilter` config to rule out any AssetHub-side restriction on which destinations/payloads a signed user's `execute()` call may relay.

## Impact Explanation
If exploitable as described, this allows an unprivileged AssetHub account to bypass `RegisterTokenOrigin::ensure_origin` and fee/tip burn logic in `snowbridge-pallet-system-frontend`, and to submit an arbitrary, unauthenticated `sender` location directly to Bridge Hub's `EthereumSystemV2::register_token`/`add_tip`. This forged `sender` becomes the `origin` of the outbound `Message` sent to the Ethereum Gateway, which determines agent/channel attribution and (for `add_tip`) credited/blamed accounts — a case of unauthorized execution/origin escalation in cross-chain message routing, matching the "unauthorized execution or origin escalation" and "forged or mis-bound proof or state acceptance" categories in the impact gate.

## Likelihood Explanation
The exploit primitive (unconditional `DescendOrigin`, computed-origin barrier evaluation, and unauthenticated `Transact` call dispatch) is confirmed to exist generically in the XCM executor and Bridge Hub's barrier configuration. The specific end-to-end reachability from an ordinary signed AssetHub account to a `Transact{ EthereumSystemCall::RegisterToken }` landing on Bridge Hub with the required `DescendOrigin(PalletInstance(FRONTEND_PALLET_INDEX))` prefix was not fully re-verified against AssetHub's outbound filtering/Barrier configuration in this session, matching the uncertainty already flagged in the claim itself. Given the demonstrated general capability (via the cited existing test) of signed users to relay attacker-controlled `remote_xcm` payloads to other chains through `InitiateTransfer`, likelihood is plausible but not fully confirmed end-to-end within the scope investigated here.

## Recommendation
Do not trust the unauthenticated `sender` field passed in `EthereumSystemV2::register_token`/`add_tip` call data. Either derive `message_origin` solely from the authenticated post-`DescendOrigin` XCM origin (requiring the frontend pallet to encode the real caller's identity into the origin path itself, not as call-data), or add an explicit filter/barrier at Bridge Hub that restricts inbound `Transact` calls targeting `snowbridge_pallet_system_v2::register_token`/`add_tip` to exactly the instruction sequence produced by `system-frontend::build_remote_xcm`, rejecting any other `DescendOrigin`-then-`Transact` composition from AssetHub.

## Proof of Concept
1. On AssetHub, a signed user submits `PolkadotXcm::execute` with a program using `InitiateTransfer` (or another XCM-relaying instruction) targeting Bridge Hub, with `remote_xcm = [DescendOrigin(PalletInstance(FRONTEND_PALLET_INDEX)), Transact{ call: EthereumSystemCall::RegisterToken{ sender: <arbitrary Location>, ... } }]`.
2. On arrival at Bridge Hub, the transport-level origin `Location::new(1,[Parachain(ASSET_HUB_ID)])` is narrowed by `DescendOrigin` to `Location::new(1,[Parachain(ASSET_HUB_ID), PalletInstance(FRONTEND_PALLET_INDEX)])`, satisfying both `WithComputedOrigin`'s barrier check and `T::FrontendOrigin::ensure_origin` inside `register_token`.
3. `register_token` proceeds using the attacker-chosen `sender_location`, bypassing `RegisterTokenOrigin::ensure_origin` and fee-burn logic entirely, and dispatches a `Message` to Ethereum with a forged `origin`.
4. This would need to be confirmed with an integration test analogous to `signed_assethub_user_cannot_bypass_origin_alteration_when_routing_to_ethereum`, but targeting Bridge Hub's `EthereumSystemV2::register_token` instead of the `AliasOrigin`/Ethereum-export path, to fully establish reachability from AssetHub's actual Barrier/filter configuration.

/// A derivative barrier, which scans the first `MaxPrefixes` instructions for origin-alterers and
/// then evaluates `should_execute` of the `InnerBarrier` based on the remaining instructions and
/// the newly computed origin.
///
/// This effectively allows for the possibility of distinguishing an origin which is acting as a
/// router for its derivative locations (or as a bridge for a remote location) and an origin which
/// is actually trying to send a message for itself. In the former case, the message will be
/// prefixed with origin-mutating instructions.
///
/// Any barriers which should be interpreted based on the computed origin rather than the original
/// message origin should be subject to this. This is the case for most barriers since the
/// effective origin is generally more important than the routing origin. Any other barriers, and
/// especially those which should be interpreted only the routing origin should not be subject to
/// this.
///
/// E.g.
/// ```nocompile
/// type MyBarrier = (
/// 	TakeWeightCredit,
/// 	AllowTopLevelPaidExecutionFrom<DirectCustomerLocations>,
/// 	WithComputedOrigin<(
/// 		AllowTopLevelPaidExecutionFrom<DerivativeCustomerLocations>,
/// 		AllowUnpaidExecutionFrom<ParentLocation>,
/// 		AllowSubscriptionsFrom<AllowedSubscribers>,
/// 		AllowKnownQueryResponses<TheResponseHandler>,
/// 	)>,
/// );
/// ```
///
/// In the above example, `AllowUnpaidExecutionFrom` appears once underneath
/// `WithComputedOrigin`. This is in order to distinguish between messages which are notionally
/// from a derivative location of `ParentLocation` but that just happened to be sent via
/// `ParentLocation` rather than messages that were sent by the parent.
///
/// Similarly `AllowTopLevelPaidExecutionFrom` appears twice: once inside of `WithComputedOrigin`
/// where we provide the list of origins which are derivative origins, and then secondly outside
/// of `WithComputedOrigin` where we provide the list of locations which are direct origins. It's
/// reasonable for these lists to be merged into one and that used both inside and out.
///
/// Finally, we see `AllowSubscriptionsFrom` and `AllowKnownQueryResponses` are both inside of
/// `WithComputedOrigin`. This means that if a message begins with origin-mutating instructions,
/// then it must be the finally computed origin which we accept subscriptions or expect a query
/// response from. For example, even if an origin appeared in the `AllowedSubscribers` list, we
/// would ignore this rule if it began with origin mutators and they changed the origin to something
/// which was not on the list.
pub struct WithComputedOrigin<InnerBarrier, LocalUniversal, MaxPrefixes>(
	PhantomData<(InnerBarrier, LocalUniversal, MaxPrefixes)>,
);
impl<InnerBarrier: ShouldExecute, LocalUniversal: Get<InteriorLocation>, MaxPrefixes: Get<u32>>
	ShouldExecute for WithComputedOrigin<InnerBarrier, LocalUniversal, MaxPrefixes>
{
	fn should_execute<Call>(
		origin: &Location,
		instructions: &mut [Instruction<Call>],
		max_weight: Weight,
		properties: &mut Properties,
	) -> Result<(), ProcessMessageError> {
		tracing::trace!(
			target: "xcm::barriers",
			?origin,
			?instructions,
			?max_weight,
			?properties,
			"WithComputedOrigin"
		);
		let mut actual_origin = origin.clone();
		let skipped = Cell::new(0usize);
		// NOTE: We do not check the validity of `UniversalOrigin` here, meaning that a malicious
		// origin could place a `UniversalOrigin` in order to spoof some location which gets free
		// execution. This technical could get it past the barrier condition, but the execution
		// would instantly fail since the first instruction would cause an error with the
		// invalid UniversalOrigin.
		instructions.matcher().match_next_inst_while(
			|_| skipped.get() < MaxPrefixes::get() as usize,
			|inst| {
				match inst {
					UniversalOrigin(new_global) => {
						// Note the origin is *relative to local consensus*! So we need to escape
						// local consensus with the `parents` before diving in into the
						// `universal_location`.
						actual_origin =
							Junctions::from([*new_global]).relative_to(&LocalUniversal::get());
					},
					DescendOrigin(j) => {
						let Ok(_) = actual_origin.append_with(j.clone()) else {
							return Err(ProcessMessageError::Unsupported);
						};
					},
					_ => return Ok(ControlFlow::Break(())),
				};
				skipped.set(skipped.get() + 1);
				Ok(ControlFlow::Continue(()))
			},
		)?;
		InnerBarrier::should_execute(
			&actual_origin,
			&mut instructions[skipped.get()..],
			max_weight,
			properties,
		)
	}
}
