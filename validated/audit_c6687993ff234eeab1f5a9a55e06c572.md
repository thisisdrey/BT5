## Title
Improper scope handling in Active-permission "operations" bitmap when validated through the `ValidateMultiSign`/`BatchValidateSign` TVM precompiles - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
TRON's multi-signature account model scopes an `Active` `Permission` to a specific set of transaction types via a 256-bit `operations` bitmap, enforced by `checkPermissionOperations`/`checkPermission` whenever a transaction is broadcast or signed. The `ValidateMultiSign` precompiled contract (address `0x0a`), which any smart contract can invoke via `CALL` to ask "does this signature set satisfy this account's permission threshold", never checks that bitmap. It only validates key weight against the permission's threshold, so a permission key that the account owner deliberately scoped to a narrow set of operations can be used through this precompile to satisfy authorization logic for actions the key was never granted, exactly mirroring the "read-scoped token used to gain write access" pattern in the reported CVE.

### Finding Description
The `Active` permission model exists specifically to scope what a given signer/key may authorize. Every legitimate authorization path enforces this scope:
- `WalletUtil.checkPermissionOperations` [1](#0-0) 
- `TransactionUtil.checkPermissionOperations` used in `getTransactionSignWeight` [2](#0-1) 
- `TransactionCapsule.checkPermission`, invoked from both `validateSignature` (block/mempool signature verification) and `addSign` [3](#0-2) 
- `Wallet.getTransactionApprovedList` [4](#0-3) 

All of these reject an operation whenever the caller's permission `operations` bitmap does not have the bit set for the target `ContractType`.

The `ValidateMultiSign` precompile, however, takes an arbitrary `address` and `permissionId` supplied by calldata from any smart contract, looks up that account's `Permission` (which may be an `Active` permission deliberately scoped to a narrow `operations` bitmap, e.g. only `TransferContract`), and only checks accumulated key weight against the threshold — it never calls `checkPermissionOperations`/`checkPermission`: [5](#0-4) 

Because smart contracts commonly use this precompile as a general-purpose "does this key/threshold authorize this action" building block (multisig wallets, custodial contracts, DeFi authorization gates), any contract that relies on `ValidateMultiSign` to gate an unrelated, higher-privilege action will treat weight-threshold satisfaction as full authorization — even though the on-chain account owner scoped that specific permission's `operations` bitmap to exclude exactly that kind of action. The `BatchValidateSign` precompile in the same file follows the identical pattern (weight/threshold only, no operations check).

### Impact Explanation
An account owner who configures a narrowly-scoped `Active` permission (e.g. a hot-wallet/automation key restricted via `operations` to only `TransferContract`) reasonably expects that key can never be leveraged to authorize other actions such as `AccountPermissionUpdateContract`, `WitnessCreateContract`, `ExchangeTransactionContract`, or arbitrary custom logic inside a smart contract. Because `ValidateMultiSign`/`BatchValidateSign` ignore the `operations` scope entirely, any contract built on top of these precompiles for authorization purposes can be tricked (or is inherently unsafe) into accepting that scoped key as sufficient proof of authorization for unrelated, higher-value operations, enabling unauthorized account operations and potential theft of funds when relied upon by wallet/custody contracts — consistent with a Medium-severity privilege-scope bypass matching CVE-2024-11483's class.

### Likelihood Explanation
Reachable from a single `TriggerSmartContract`/`TriggerConstantContract` call by any anonymous account: an attacker (or a legitimate but naive contract author) only needs a contract that calls the precompile at address `0x0a`/`0x09` with an `address`/`permissionId` pair and enough real signatures meeting the threshold — no special privilege, node role, or timing condition is required. The scoped key holder's cooperation (providing valid signatures for whatever hash the contract expects) is the only external dependency, which is exactly the scenario the `operations` bitmap is meant to prevent from being exploitable outside its intended scope.

### Recommendation
Add an `operations`/`ContractType` scope check to `ValidateMultiSign.execute` and `BatchValidateSign` consistent with `WalletUtil.checkPermissionOperations`, or explicitly document that these precompiles only assert weight/threshold and must not be used by contract authors as a substitute for `operations`-scoped authorization. Preferably, pass the intended `ContractType`/action context into the precompile call so it can check the bit against `permission.getOperations()` before returning success.

### Proof of Concept
1. Account `A` creates an `Active` permission (id=2) with `operations` bitmap allowing only `TransferContract`, backed by key `K`.
2. Deploy any smart contract `C` that calls precompile `0x0a` (`validatemultisign(address,uint256,bytes32,bytes[])`) with `A`, `permissionId=2`, an arbitrary `hash`, and signatures from `K` meeting the threshold — exactly as done in `ValidateMultiSignContractTest.testDifferentCase` [6](#0-5) , but have `C` use the `true` result to gate an unrelated privileged action (e.g., releasing funds, changing config).
3. The precompile returns `true` (`DataWord.ONE()`) purely because weight ≥ threshold, with no check that `operations` authorizes the action `C` is gating — demonstrating the scope bypass.

  public static boolean checkPermissionOperations(Permission permission, Contract contract)
      throws PermissionException {
    ByteString operations = permission.getOperations();
    if (operations.size() != 32) {
      throw new PermissionException(String.format("operations size must 32, actual: %d",
          operations.size()));
    }
    int contractType = contract.getTypeValue();
    boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
    return b;
  }
