Audit Report

## Title
Snowbridge outbound-queue-v2 pays relayer reward regardless of delivery success (`DeliveryReceipt::success` never checked) - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
`Pallet::process_delivery_receipt` decodes a `DeliveryReceipt` containing a `success: bool` field sourced from the Ethereum `InboundMessageDispatched` event, but the payout logic only checks `T::GatewayAddress::get() == receipt.gateway` and `order.fee > 0` before calling `T::RewardPayment::register_reward`, never inspecting `receipt.success`. This means a relayer whose message dispatch failed on Ethereum (`success = false`) is paid identically to one whose dispatch succeeded, as long as a valid Merkle/Beefy proof for the emitted log is submitted.

## Finding Description
The `DeliveryReceipt` struct explicitly carries a `success` field populated straight from the Solidity event `InboundMessageDispatched(uint64 indexed nonce, bytes32 topic, bool success, bytes32 reward_address)` via `TryFrom<&Log>` [1](#0-0) .

The extrinsic `submit_delivery_receipt` verifies the log inclusion proof via `T::Verifier::verify`, decodes the log into a `DeliveryReceipt`, and forwards it to `process_delivery_receipt` [2](#0-1) . `T::Verifier::verify` only attests that the event log was included/finalized on the Ethereum side — it says nothing about the `success` flag's value.

`process_delivery_receipt` then performs only two checks — gateway address match and pending-order existence — before unconditionally paying `order.fee` to the reward account and removing the pending order: [3](#0-2) . The `receipt.success` field is never read in this function, so a receipt proving a failed dispatch (`success = false`) follows the exact same code path and payout as a receipt proving a successful dispatch.

The `PendingOrder` is created with the fee at message-enqueue time in `do_process_message` [4](#0-3) , and is settled — with reward paid — purely on proof of *log emission*, not proof of *dispatch success*.

## Impact Explanation
This breaks the invariant that message queues, bridge markers, receipts, and payout state must only advance after execution and settlement succeed. Since the Gateway contract emits `InboundMessageDispatched` with `success = false` on failed dispatches while the pallet still pays `order.fee` in full, relayers are rewarded for public work regardless of whether it was completed correctly, draining the bridge's fee pool to relayers who did not deliver a successful cross-chain message. This is a reward-conservation violation: payout does not correctly correspond to correctness of the settlement outcome.

## Likelihood Explanation
`submit_delivery_receipt` is a public, unprivileged extrinsic requiring only `ensure_signed(origin)` and a valid Merkle/Beefy proof of an event log that already exists once the relayer's Ethereum transaction is included, regardless of dispatch outcome. No privileged role, collusion, or off-chain infrastructure control is required beyond normal relayer operation, making this readily reachable by any relayer whose dispatch fails on Ethereum.

## Recommendation
Condition the reward payout on `receipt.success`. Only call `T::RewardPayment::register_reward` when `receipt.success == true`; for `false`, either withhold/reduce the fee, refund it to the original message committer, or otherwise avoid crediting the relayer for a failed dispatch, so payout state only advances after successful execution.

## Proof of Concept
1. A message is enqueued via `do_process_message`, creating `PendingOrder { nonce, fee, .. }` [5](#0-4) .
2. A relayer submits the message to Ethereum's Gateway; the dispatch of commands fails, but the Gateway still emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. The relayer builds an `EventProof` for this log and calls `submit_delivery_receipt`; `T::Verifier::verify` succeeds since it only checks log inclusion [6](#0-5) .
4. `DeliveryReceipt::try_from` decodes `success = false` correctly [7](#0-6) .
5. `process_delivery_receipt` pays `order.fee` unconditionally since `receipt.success` is never checked [8](#0-7) , identical to the existing test flow that constructs a `DeliveryReceipt` with `success: true` and observes `RewardRegistered` [9](#0-8) ; setting `success: false` in that same test would produce an identical `RewardRegistered` event, confirming the missing check.

```rust
/// Delivery receipt
#[derive(Clone, Debug)]
pub struct DeliveryReceipt {
	/// The address of the outbound queue on Ethereum that emitted this message as an event log
	pub gateway: H160,
	/// The nonce of the dispatched message
	pub nonce: u64,
	/// Message topic
	pub topic: H256,
	/// Delivery status
	pub success: bool,
	/// The reward address
	pub reward_address: [u8; 32],
}

#[derive(Copy, Clone, Encode, Decode, Eq, PartialEq, Debug, TypeInfo)]
pub enum DeliveryReceiptDecodeError {
	DecodeLogFailed,
	DecodeAccountFailed,
}

impl TryFrom<&Log> for DeliveryReceipt {
	type Error = DeliveryReceiptDecodeError;

	fn try_from(log: &Log) -> Result<Self, Self::Error> {
		let topics: Vec<B256> = log.topics.iter().map(|x| B256::from_slice(x.as_ref())).collect();

		let event = InboundMessageDispatched::decode_raw_log_validate(topics, &log.data)
			.map_err(|_| DeliveryReceiptDecodeError::DecodeLogFailed)?;

		Ok(Self {
			gateway: log.address,
			nonce: event.nonce,
			topic: H256::from_slice(event.topic.as_ref()),
			success: event.success,
			reward_address: event.reward_address.0,
		})
	}
```

```rust
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
```
