### Title
Forced `protocol.file.allow=always` in Git submodule fetching enables attacker-controlled `.gitmodules` to exfiltrate arbitrary local files - (File: `tools/build_defs/repo/git_worker.bzl`)

### Summary
Bazel's `git_repository`/`new_git_repository` rules delegate submodule fetching to `update_submodules()` in `tools/build_defs/repo/git_worker.bzl`, which unconditionally injects `-c protocol.file.allow=always` into the `git submodule update` invocation [1](#0-0) . This overrides Git's own default hardening (`protocol.file.allow=user`, introduced after CVE-2018-11235/CVE-2017-1000117-class submodule attacks) that normally prevents automated/recursive `git submodule update` from silently following `file://` URLs found in an untrusted repository's `.gitmodules`.

### Finding Description
When a victim declares `git_repository(..., init_submodules = True)` or `recursive_init_submodules = True` [2](#0-1) , and Bazel builds from a `remote` whose content an outsider can influence (e.g. an untrusted branch that CI builds, consistent with the in-scope threat model), Bazel calls:

```
git -c protocol.file.allow=always submodule update --init [--recursive] --checkout --force
``` [1](#0-0) 

Git normally restricts `file://` (and `ext::`) submodule URLs during automated/recursive submodule operations via `protocol.file.allow=user` specifically to stop a malicious `.gitmodules` from directing Git to silently clone arbitrary local paths. Bazel's hard-coded `protocol.file.allow=always` disables this protection for every `git_repository` fetch that enables submodules, regardless of how trustworthy the `remote` content actually is. The `.gitmodules` file — including `url` and `path` fields for each submodule — is fully attacker-controlled content coming from the fetched repository, not from the trusted root `MODULE.bazel`/`BUILD` files. An attacker who can push/serve content the victim's `git_repository` fetches (a public mirror, a compromised/park-typo remote, or any untrusted branch built by CI) can add a `.gitmodules` entry such as:

```
[submodule "leak"]
    path = leak
    url = file:///home/victim/.ssh
```

or point at any other local Git repository reachable by the build user (other checkouts, private repo clones, CI workspace directories containing credentials in `.git/config`). Because `protocol.file.allow=always` is forced, Git clones that local repository's contents into the submodule directory inside the fetched external repo, making previously-inaccessible local file/repo content readable as ordinary repository files that subsequent `BUILD` targets (e.g. `filegroup`/`genrule`) can read and exfiltrate through build outputs.

### Impact Explanation
This breaks the "untrusted content stays data" and containment invariants: content read via `file://` submodule cloning originates from paths entirely outside the fetched repository, the exec root, and the output base, yet becomes visible inside the sandboxed checkout as ordinary tracked files. Depending on what other Git-tracked directories exist on the build host (developer checkouts, CI workspace clones with embedded credentials, SSH config repos, etc.), this can lead to disclosure of secrets or source code the victim never intended to expose to the dependency being fetched — a concrete read outside the repository, achieved purely by content served by an unprivileged attacker-controlled Git remote.

### Likelihood Explanation
`init_submodules`/`recursive_init_submodules` are documented, commonly used options for `git_repository` [2](#0-1) , and the vulnerable code path executes unconditionally whenever submodules are enabled — there is no check that `remote` is a fully trusted, single-maintainer source, nor any validation of URLs discovered in `.gitmodules`. Any project fetching git dependencies with submodules from a mirror, fork, or CI branch that an outside contributor can influence is exposed by default, since the override is silent and undocumented to end users of `git_repository`.

### Recommendation
Do not force `protocol.file.allow=always` broadly. Only allow local-file submodule protocol for known same-origin/local test scenarios (e.g., gate it behind an explicit rule attribute, or restrict it to remotes that are themselves `file://` paths under the same trust boundary), and otherwise leave Git's default `protocol.file.allow=user`/`never` posture in place for submodules fetched from remote, potentially attacker-influenced repositories.

### Proof of Concept
A `src/test/shell/bazel/starlark_git_repository_test.sh`-style integration test can reproduce this:
1. Create a local git repo `secret_repo` containing a sensitive file (simulating another checkout on the build host).
2. Create `outer_repo` with a `.gitmodules` entry `url = file:///abs/path/to/secret_repo`, `path = leaked`.
3. Declare `git_repository(name="outer", remote="$outer_repo_dir", init_submodules = True, build_file_content = "filegroup(name='leak', srcs=['leaked/<secret_file>'], visibility=['//visibility:public'])")`.
4. Build a target depending on `@outer//:leak` and observe that the secret file's contents from `secret_repo` (external to `outer_repo`) are readable in the build output — confirming `protocol.file.allow=always` let Git clone from `file://` despite the submodule URL never being explicitly trusted by the victim's `MODULE.bazel`.
