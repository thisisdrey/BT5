### Title
TRC10 DEX order matching uses floor-division for quantity conversion, causing traders to permanently lose small amounts of asset value on every match - ([File: chainbase/src/main/java/org/tron/core/capsule/utils/MarketUtils.java])

### Summary
`MarketUtils.multiplyAndDivide()` — the core quantity-conversion helper used by `MarketSellAssetActuator` to settle TRC10 exchange (DEX) order matches — always truncates (floors) the result of `a*b/c`, exactly like the `PrbMath.mulDiv18()` rounding-down issue described in the external report. Because this conversion is used to compute both the taker's and maker's received quantities on *every* order match, the fractional remainder from the division is never credited to either party. It simply disappears from both accounts' balances each time a match occurs.

### Finding Description
`MarketUtils.multiplyAndDivide()` computes `floorDiv(a*b, c)` (with a `BigInteger.divide()` fallback on overflow, which truncates toward zero — the same rounding direction for positive operands): [1](#0-0) 

This helper is called from `MarketSellAssetActuator.matchSingleOrder()` in three places to compute how much of the buy-token each side of a match receives: [2](#0-1) [3](#0-2) [4](#0-3) 

The results are then directly credited to the taker's and maker's accounts via `addTrxOrToken()`: [5](#0-4) 

Whenever `a*b` is not exactly divisible by `c` (i.e., whenever the sell/buy quantities of the taker and maker orders don't align to an exact integer ratio — which is the common case for arbitrary user-chosen order sizes), the computed `takerBuyTokenQuantityReceive` / `makerBuyTokenQuantityReceive` is rounded down. The corresponding "sell" side of the same match consumes the *full* remaining quantity (e.g. `takerOrderCapsule.setSellTokenQuantityRemain(0)`), so the counter-party gives up 100% of what they committed but the other side receives a rounded-down amount. The fractional shortfall is not credited to anyone — the taker, the maker, nor the protocol/blackhole. It is simply lost.

Unlike `OrderFees.percentageFeeForValue()` in the external report — where rounding down benefits the trader at the treasury's expense — here rounding down benefits *no one*; each match silently destroys a small amount of value belonging to the order participants. This is functionally the same bug class (rounding direction not chosen deliberately in the safe direction for a financial settlement calculation), and it compounds identically: "the more the system is used, the greater the cumulative value leak becomes," since every single DEX match (an anonymous, unprivileged operation reachable via `MarketSellAssetContract`) incurs this rounding loss.

### Impact Explanation
Every TRC10 exchange match executed through `MarketSellAssetActuator` can silently destroy fractional token/TRX amounts that are debited from one account's order but never credited to the counter-party or anywhere else. While each individual loss is small (bounded by rounding granularity), it is systemic and occurs on essentially every partial/complete match with non-exact ratios, across all TRC10 trading pairs and users, with no way for affected users to recover the lost value. This constitutes a permanent, protocol-wide micro-freezing/destruction of user funds that compounds with usage.

### Likelihood Explanation
High likelihood of triggering: any user submitting a `MarketSellAssetContract` order that matches against an existing maker order with a sell:buy ratio not evenly divisible produces this rounding loss. Given typical use of the TRC10 DEX with arbitrary user-chosen quantities, exact-ratio matches are the exception rather than the rule, so this occurs routinely in normal trading activity requiring no special privileges — just any account placing and matching a sell order.

### Recommendation
Decide, for each conversion in `matchSingleOrder()`, which side the rounding should protect (typically round in favor of the account that is fully consuming its order, or track and settle residual dust rather than discarding it), and adjust `MarketUtils.multiplyAndDivide()` (or add a rounding-mode variant) accordingly instead of unconditionally flooring. Alternatively, accumulate the discarded remainder and settle/return it to the appropriate order owner instead of letting it vanish on every match.

### Proof of Concept
1. Maker places a sell order via `MarketSellAssetContract`: sell 3 units of token A for 2 units of token B (`makerSellQuantity=3`, `makerBuyQuantity=2`).
2. Taker places an order that fully matches the maker's remaining quantity, going through the "taker > maker" or "taker == maker" branch in `matchSingleOrder()`.
3. `makerBuyTokenQuantityReceive = MarketUtils.multiplyAndDivide(makerSellRemainQuantity=3, makerBuyQuantity=2, makerSellQuantity=3, ...)` = `floor(3*2/3)` = `2` — exact in this case, but consider `makerSellRemainQuantity=1` with the same ratio: `floor(1*2/3) = 0`.
4. In that case `makerOrderCapsule.getSellTokenQuantityRemain()` (i.e., 1 unit of A) is fully consumed/zeroed while the maker receives `0` of token B for it — the value of that 1 unit of A (proportionally worth 2/3 unit of B) is permanently lost, credited to nobody, as seen in the `makerBuyTokenQuantityReceive == 0` early-return path at [6](#0-5)  (this specific guard only returns the *sell-remain* dust to the maker when the *result* of the computation is exactly 0, but does not address the more general fractional-rounding loss occurring on every non-exact-ratio match elsewhere in the function).

    try {
      long tmp = multiplyExact(a, b, disableMath);

      // do nothing here, because we will use BigInteger to compute again
    }

    BigInteger aBig = BigInteger.valueOf(a);

    BigInteger cBig = BigInteger.valueOf(c);

    return aBig.multiply(bBig).divide(cBig).longValue();
  }
