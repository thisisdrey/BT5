## Finding

### Title
Unprotected internal AMM swap during XCM weight refund enables sandwich extraction of refunded value - ([File: cumulus/primitives/utility/src/lib.rs])

### Summary
`SwapFirstAssetTrader`, a `WeightTrader` implementation used to let XCM messages pay execution fees in a non-target fungible asset by swapping through `pallet-asset-conversion`, protects the *purchase* leg of the swap with an exact-output amount (`swap_tokens_for_exact_tokens`), but its *refund* leg calls `SwapCredit::swap_exact_tokens_for_tokens` with `amount_out_min` hard-coded to `None`. This is functionally identical to the reported `Berabot` bug: an internal swap is triggered as a side effect of an unrelated operation (there, `_transfer()`; here, XCM weight refunding) with no minimum-amount-out guard, letting a sandwich attacker extract the swap's value at the expense of the intended beneficiary.

### Finding Description
`SwapFirstAssetTrader::buy_weight` withdraws the user's non-target asset and swaps it for the `Target` asset using `SwapCredit::swap_tokens_for_exact_tokens`, an exact-output swap that bounds how much of the input asset is consumed for the deterministic weight fee [1](#0-0) .

When the executed message consumes less weight than purchased, `refund_weight` swaps the unspent `Target` credit back into the asset that was originally used, via `SwapCredit::swap_exact_tokens_for_tokens(vec![Target::get(), refund_swap_asset], refund, None)` — passing `None` for `amount_out_min` [2](#0-1) .

`SwapCredit::swap_exact_tokens_for_tokens` in `pallet-asset-conversion` treats `amount_out_min: None` as "no minimum enforced" and returns whatever the pool yields at current reserves: `Self::do_swap_exact_credit_tokens_for_tokens` only checks `amount_out >= amount_out_min` when `amount_out_min` is `Some(_)` [3](#0-2) . The `Swap`/`SwapCredit` traits explicitly document this behavior as "expected to be atomic" per-call, but atomicity of a single swap call does not protect against price manipulation across separate extrinsics/messages executed earlier in the same block [4](#0-3) .

Because the refunded credit is later wrapped back into the holding register (`AssetsInHolding::new_from_fungible_credit(refund_asset.id, ...)`), the amount ultimately deposited to the message's designated beneficiary (or trapped) is whatever the unprotected swap returns at the moment `refund_weight` executes [5](#0-4) . Unlike the pallet's public `swap_exact_tokens_for_tokens`/`swap_tokens_for_exact_tokens` extrinsics — which require the caller to supply `amount_out_min`/`amount_in_max` themselves [6](#0-5)  — the refund path in `SwapFirstAssetTrader` gives the affected party (the original sender/beneficiary of the XCM message) no say in slippage tolerance at all.

### Impact Explanation
An unprivileged party who can place ordinary transactions into the same block as an XCM message that will trigger a `refund_weight` call (e.g. by monitoring the mempool/pending message queue) can:
1. Front-run: submit a transaction that skews the `Target`/`refund_swap_asset` pool reserves (a large one-sided swap) immediately before the message is executed.
2. Let the unprotected `refund_weight` swap execute at the manipulated price, returning far less of `refund_swap_asset` than the fair-market quote.
3. Back-run: submit a transaction that reverses the initial skew, capturing the price impact as profit.

This directly extracts value that should have gone to the legitimate recipient of the XCM refund (fund loss to an unprivileged intended beneficiary), matching the "Impact" required by the pivots (value not conserved / not settled to the rightful beneficiary/amount) without requiring a malicious validator, collator, relayer, or admin — only an ordinary account able to submit transactions and observe pending block content.

### Likelihood Explanation
Requires: (a) a runtime configuring `SwapFirstAssetTrader` with a low-liquidity or thinly-traded pool for the involved asset pair, and (b) predictable/observable timing of XCM message execution relative to attacker-submitted extrinsics within a block. Both conditions are realistic on parachains that accept diverse fee assets for XCM execution and rely on `pallet-asset-conversion` pools, which by design can have shallow liquidity for many asset pairs. The `buy_weight` leg is already hardened (exact-output swap); only the refund leg lacks protection, making this a narrow but concrete unmitigated code path rather than a purely theoretical one.

### Recommendation
Do not pass `None` for `amount_out_min` in `refund_weight`. Compute an acceptable minimum via `QuotePrice::quote_price_exact_tokens_for_tokens` (already used elsewhere in this same file for `quote_weight`) immediately before the swap and pass it as `Some(min_amount)`, or apply a configurable maximum slippage tolerance, so the refund swap fails safely (returning the credit into `total_fee`/holding rather than sacrificing value) instead of executing at an arbitrarily manipulated price.

### Proof of Concept
1. Configure a parachain runtime with `SwapFirstAssetTrader<Target = NativeAsset, SwapCredit = AssetConversion, ...>` and a shallow-liquidity pool for `(NativeAsset, ForeignAssetX)`.
2. Attacker observes an incoming XCM message (e.g. reserve-asset-transfer or `Transact`) paying its execution fee in `ForeignAssetX` with `BuyExecution { weight_limit: ... }` that overestimates weight, guaranteeing a `refund_weight` call once the message finishes executing with surplus.
3. In the same block, before the message is processed, attacker submits `AssetConversion::swap_exact_tokens_for_tokens` buying a large amount of `NativeAsset` with `ForeignAssetX`, skewing the pool price so `NativeAsset` is now expensive in terms of `ForeignAssetX`.
4. The XCM executor processes the message; `refund_weight` swaps the `total_fee` surplus (`NativeAsset`) back into `ForeignAssetX` via `swap_exact_tokens_for_tokens(..., None)` — receiving far less `ForeignAssetX` than a fair quote would predict, at line [7](#0-6) , because no floor was set.
5. Attacker submits a second transaction reversing the pool skew, realizing the price-impact profit extracted from the refund amount that should have gone to the XCM message's beneficiary.
