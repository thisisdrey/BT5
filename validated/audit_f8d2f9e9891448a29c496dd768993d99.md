### Title
Firewall conntrack timeout of `0` causes an integer divide-by-zero panic in `NewTimerWheel`, crashing the node - (File: `timeout.go`)

### Summary
`NewFirewall` builds its conntrack `TimerWheel` from three admin-controlled duration settings (`firewall.conntrack.tcp_timeout`, `udp_timeout`, `default_timeout`). If the smallest of these ("min") is `0`, `NewTimerWheel` performs `max / min`, an integer division by zero, which panics and crashes the whole nebula process. This mirrors the `M-08` bug class: an operator-controlled numeric parameter that has no lower-bound validation (`collateralFactorBps == 0`), whose zero value silently flips the code into a broken/locking state instead of being explicitly rejected.

### Finding Description
`NewFirewall` computes `tmin`/`tmax` from the three timeout durations with no floor check, then passes them straight into `NewTimerWheel`: [1](#0-0) 

`NewTimerWheel` has an explicit `//TODO: error on 0 duration` acknowledging the missing guard, and then unconditionally computes `wLen := int((max / min) + 2)`: [2](#0-1) 

If `min` is `0` (e.g., an operator sets `firewall.conntrack.tcp_timeout: 0s`, `udp_timeout: 0s`, or `default_timeout: 0s` in the config, or provides a malformed duration that parses to `0`), `max / min` is an integer divide-by-zero, which Go turns into an unrecoverable runtime panic rather than an error return. This is invoked both at firewall construction time and any time the firewall is reloaded from a changed config: [3](#0-2) 

This is the direct analog of the reported issue: `collateralFactorBps == 0` was accepted by the setter and silently produced a locked state (`return 0` in the withdrawal-limit check) instead of being rejected outright; here, a `0` duration is likewise accepted by `NewFirewallFromConfig`/`NewFirewall` with no minimum-value validation, and instead of degrading gracefully it panics the process.

### Impact Explanation
A panic in `NewTimerWheel` is fatal — it is not caught anywhere in the call chain from `main.Main` → `NewFirewallFromConfig` → `NewFirewall` → `NewTimerWheel`, nor in the config-reload callback path (`f.reloadFirewall` → firewall rebuild). This crashes the entire nebula node, taking down all existing tunnels and firewall enforcement for that host, i.e. a full denial of service of the mesh node. This matches the "remote crash impact" / firewall-enforcement class explicitly listed as in scope.

### Likelihood Explanation
Likelihood is limited to configuration-time (or config-reload-time) misconfiguration by whoever controls the node's config file — there is no attacker-controlled network input that can set these durations. It is analogous to the original disclosure, where the trigger is also an operator/governance action rather than a remote attacker payload. Given the explicit `//TODO: error on 0 duration` comment already present in the code, the maintainers are aware the input is unguarded, but no minimum enforcement exists in either the constructor or the config loader (`c.GetDuration("firewall.conntrack.tcp_timeout", ...)` accepts `0` without validation).

### Recommendation
Add explicit validation in `NewFirewall`/`NewFirewallFromConfig` (and `NewTimerWheel`) rejecting a `0` (or negative) `tcpTimeout`, `udpTimeout`, or `defaultTimeout`, returning a configuration error instead of silently proceeding into `NewTimerWheel`. `NewTimerWheel` itself should return an `error` when `min <= 0` rather than panicking on integer division.

### Proof of Concept
1. Configure nebula with:
```yaml
firewall:
  conntrack:
    tcp_timeout: 0s
    udp_timeout: 3m
    default_timeout: 10m
```
2. Start nebula (or trigger a config reload with this setting on a running node).
3. `NewFirewallFromConfig` calls `NewFirewall(l, 0, 3*time.Minute, 10*time.Minute, cert)`; `tmin` resolves to `0`.
4. `NewTimerWheel[firewall.Packet](0, 10*time.Minute)` executes `wLen := int((max / min) + 2)`, dividing by zero, causing:
```
panic: runtime error: integer divide by zero
```
5. The node process crashes, tearing down all tunnels. [4](#0-3) [5](#0-4)
