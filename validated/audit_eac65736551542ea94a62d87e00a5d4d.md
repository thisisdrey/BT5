### Title
Non-clamped total resource weight can reach zero/negative on legacy path, causing division-by-zero / unbounded resource-limit calculation in `EnergyProcessor`/`BandwidthProcessor` - (File: `chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java`)

### Summary
`EnergyProcessor.calculateGlobalEnergyLimit` and `BandwidthProcessor.calculateGlobalNetLimit` guard against a zero/negative total resource weight only when the `allowNewReward` chain parameter is enabled. When it is not, the guard is replaced by a Java `assert`, which is a no-op in production (assertions are disabled by default), so execution falls through to a division that uses the possibly zero/negative `totalEnergyWeight`/`totalNetWeight`. This is the same bug class as the reported `MultiStrategy.removeStrategy` issue: a running total is decremented (here, via ordinary unfreeze transactions) without being clamped/validated before it is consumed by a division elsewhere in the same code path.

### Finding Description
`DynamicPropertiesStore.addTotalEnergyWeight`/`addTotalNetWeight` only clamp the total weight to a minimum of zero when `allowNewReward()` is true: [1](#0-0) 

When `allowNewReward()` is false, ordinary `UnfreezeBalanceActuator`/`UnfreezeBalanceV2Actuator`/native-contract `UnfreezeBalanceV2Processor` calls (reachable by any unprivileged account unfreezing its stake) can drive `totalEnergyWeight`/`totalNetWeight` down to zero or below with no clamping: [2](#0-1) 

Later, when energy/bandwidth limits are recalculated for any account (during ordinary transaction processing via `useEnergy`/`consume`, or via the `getAccountResource` RPC), `calculateGlobalEnergyLimit` only returns 0 early if `allowNewReward()` is true; otherwise it hits a no-op `assert` and proceeds to divide by the unguarded weight: [3](#0-2) 

If the hardened calculation path is active (`allowHardenResourceCalculation`), the division is performed with `BigInteger`, which throws an uncaught `ArithmeticException: BigInteger is divide by zero` when `totalEnergyWeight == 0`: [4](#0-3) 

If the legacy double-precision path is active instead, `(double) totalEnergyLimit / totalEnergyWeight` with `totalEnergyWeight == 0` yields `Infinity` (not an exception), and `(long) (energyWeight * Infinity)` saturates to `Long.MAX_VALUE`, granting an effectively unlimited energy/bandwidth limit to any account with frozen balance. The identical pattern exists in `BandwidthProcessor.calculateGlobalNetLimit`: [5](#0-4) 

### Impact Explanation
- With hardened calculation enabled, an uncaught `ArithmeticException` inside `useEnergy`/`consume`, which run for essentially every transaction that consumes energy/bandwidth, would propagate out of deterministic block-application logic. Since every full node executes the same code deterministically, this can crash/halt block processing across the network (node crash / chain halt), matching the severity class required.
- With the legacy path, an account can obtain a `Long.MAX_VALUE` energy/bandwidth limit — an unbacked resource grant that lets it execute unlimited contract calls or bandwidth-consuming transactions without paying for or staking the corresponding TRX, which is a concrete "unbacked balance"-style resource issuance bug.
- The root cause mirrors the external report precisely: a total accumulator (`_totalWeight` vs. `totalEnergyWeight`/`totalNetWeight`) is allowed to reach zero because the safety clamp is conditioned on a flag/order of operations, and a later division over the (now zero) total is not defensively guarded in all code paths.

### Likelihood Explanation
This path is only reachable when `allowNewReward()` is false, which is a network-wide dynamic parameter that has been permanently enabled on TRON mainnet for a long time (activated via a `ProposalApprove`/hard-fork parameter). On current mainnet this specific branch is therefore dormant. However, the underlying flaw is present in the shipped code and is directly reachable on any private/test java-tron network, or genesis configuration, where `allowNewReward` has not yet been enabled — no special SR/witness/deployer privilege is required; only ordinary freeze/unfreeze and normal transactions are needed to trigger it. Because of the mainnet-parameter dependency, likelihood on live mainnet today is low, but the code path itself is a real, unguarded bug of the same class as the reported finding.

### Recommendation
Remove the dependency on the (no-op in production) `assert` and the `allowNewReward()` flag for safety: always clamp/guard `totalEnergyWeight`/`totalNetWeight` to a non-negative value in `addTotalEnergyWeight`/`addTotalNetWeight`, and always return 0 (instead of dividing) whenever the total weight is `<= 0` in `calculateGlobalEnergyLimit`/`calculateGlobalNetLimit`, regardless of the `allowNewReward` flag.

### Proof of Concept
1. Deploy/operate a java-tron network where `allowNewReward` has not been activated (its default/pre-hardfork state) and `allowHardenResourceCalculation` is enabled.
2. Have the sole/majority account(s) providing `totalEnergyWeight` fully unfreeze their `ENERGY`-type frozen balance via `UnfreezeBalanceV2Contract`, driving `dynamicPropertiesStore.getTotalEnergyWeight()` to exactly `0` (no clamp is applied since `allowNewReward()` is false, per `DynamicPropertiesStore.addTotalEnergyWeight`).
3. Any subsequent transaction from any account that still has frozen energy balance triggers `EnergyProcessor.useEnergy` → `calculateGlobalEnergyLimit`, which calls `calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, 0)`, causing `BigInteger.divide(BigInteger.valueOf(0))` to throw `ArithmeticException`.
4. If `allowHardenResourceCalculation` is disabled instead, the same scenario returns `(long)(energyWeight * Infinity) == Long.MAX_VALUE` as the account's energy limit, granting effectively unlimited free energy.

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalEnergyLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }

    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
    long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
      return 0;
    } else {
      assert totalEnergyWeight > 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }

  protected long calculateGlobalLimitV1(long frozeBalance,
      long totalLimit, long totalWeight) {
    long weight = frozeBalance / TRX_PRECISION;
    return BigInteger.valueOf(weight)
        .multiply(BigInteger.valueOf(totalLimit))
        .divide(BigInteger.valueOf(totalWeight))
        .longValueExact();
  }
