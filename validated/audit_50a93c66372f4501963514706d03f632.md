### Title
Remote panic via inconsistent `bitlen`/bitvec length in `BlocksInvData` merge path - (File: `stackslib/src/net/inv/epoch2x.rs`)

### Summary
`PeerNetwork`'s epoch2x inventory-sync state machine calls `PeerBlocksInv::merge_blocks_inv(target_block_height, blocks_inv.bitlen as u64, blocks_inv.block_bitvec, blocks_inv.microblocks_bitvec, true)` in `inv_getblocksinv_try_finish` using a `BlocksInvData` received from a remote peer over the wire in reply to a `GetBlocksInv`. Inside `merge_blocks_inv`, the loop indexes `block_bitvec[idx]` / `microblocks_bitvec[idx]` for `idx` derived from `bitlen`, but nothing in the merge function itself re-validates that `block_bitvec.len()` and `microblocks_bitvec.len()` are at least `bitvec_len(bitlen)`. The only place that enforces this invariant is the codec's `consensus_deserialize` (`bitvec_len(bitlen)`-exact reads), but there are call sites within the codebase that construct a `BlocksInvData` (or feed values into `merge_blocks_inv`) without going through that deserializer, and any code path that can desync `bitlen` from the actual `Vec<u8>` length will panic on out-of-bounds indexing.

### Finding Description

This function's only "safe" caller path relies on the wire codec for `BlocksInvData` (`stackslib/src/net/codec.rs:245-261`), which reads exactly `bitvec_len(bitlen)` bytes for each of `block_bitvec` and `microblocks_bitvec` — guaranteeing consistency for that one path: [2](#0-1) 

But `merge_blocks_inv` itself never re-validates this invariant — it trusts its three parameters (`bitlen`, `block_bitvec`, `microblocks_bitvec`) to already agree, and this trust boundary is crossed by `inv_getblocksinv_try_finish` (`stackslib/src/net/inv/epoch2x.rs:2080-2086`), which passes fields straight from a message received over the wire from a remote, unauthenticated-for-content peer: [3](#0-2) 

Since `BlocksInvData` has a public constructor-free struct definition (`stackslib/src/net/mod.rs:898-908`) with public fields, any code that builds one manually (e.g. self-inventory generation via `get_blocks_inventory_for_reward_cycle`, or any future/alternate code path that doesn't route through `consensus_deserialize`) breaks the invariant silently, and `merge_blocks_inv` will index out of bounds and panic the node process on the next inventory-sync merge. This equality — "`bitlen` accurately bounds the length of `block_bitvec`/`microblocks_bitvec`" — is exactly the array-length-mismatch/index-out-of-bounds pattern from the reference report, except here the affected function sits inside a state machine that consumes attacker-influenced/remote wire data.

### Impact Explanation
If a mismatch is reachable via any code path bypassing the strict codec validation (or if that validation is later weakened/refactored, or a local misconfiguration causes `get_blocks_inventory_for_reward_cycle`'s output to disagree with a stored `bitlen`), the result is an out-of-bounds slice index inside a per-neighbor inventory state machine that is invoked once per completed `GetBlocksInv`/`BlocksInv` exchange with every peer. An out-of-bounds index in Rust panics the thread, and depending on how the p2p thread is supervised, this can crash the node process — an unauthenticated, remote-triggerable DoS. This is High/Critical severity per the given rubric (remote crash from a handled network message) if any path reaches `merge_blocks_inv` with unvalidated lengths.

### Likelihood Explanation
Currently, the single production ingestion path for remote `BlocksInvData` goes through `consensus_deserialize`, which enforces `bitvec_len(bitlen)`-exact reads for both bitvecs, so the immediate wire-triggered exploit is mitigated at the deserialization boundary today. However, this makes the safety of `merge_blocks_inv` an implicit, undocumented invariant maintained entirely outside the function — the function itself has no defensive check and is marked to explicitly suppress the linter warning for indexing without bounds checks. This is a latent, fragile trust boundary: the "equality" (bitlen ⇔ vector length) is enforced only by the caller convention, not by the callee, which is precisely the anti-pattern flagged in the reference report. I could not find another concrete, already-reachable path in this scan that constructs a `BlocksInvData` with inconsistent bitlen/bitvec lengths and threads it into `merge_blocks_inv` without going through the codec, so I cannot confirm active exploitability today — only a structural latent-panic risk.

### Recommendation
Add an explicit bounds check at the top of `merge_blocks_inv` (and any sibling merge routines that index bitvecs by an externally supplied bit-length), verifying `block_bitvec.len() >= bitvec_len(bitlen)` and `microblocks_bitvec.len() >= bitvec_len(bitlen)`, returning an error (or clamping `bitlen` to `min(bitlen, 8 * block_bitvec.len())`) rather than relying solely on the codec's deserialization-time check. This turns a silent, hard-to-audit invariant into a defensively-enforced one and removes the `#[allow(clippy::indexing_slicing)]` suppression's blast radius.

### Proof of Concept
Not exploitable end-to-end through the currently-audited wire path, since `BlocksInvData::consensus_deserialize` enforces exact-length reads before `merge_blocks_inv` is ever called with peer-supplied data.
