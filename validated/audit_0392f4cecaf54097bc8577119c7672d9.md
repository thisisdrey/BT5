Confirmed: `SignerEventReceiver::next_event` in `libsigner/src/events.rs` has no authentication check whatsoever on the HTTP server it binds — no auth token, no header check, no source verification. Any of the `/stackerdb_chunks`, `/proposal_response`, `/new_burn_block`, `/new_block`, and especially `/shutdown` routes are processed for anyone who can reach the listening socket.

### Title
Unauthenticated Remote Shutdown of Signer Event Receiver via `POST /shutdown` — ([File: libsigner/src/events.rs])

### Summary
`SignerEventReceiver::next_event` in `libsigner/src/events.rs` accepts plain HTTP POST requests on the signer's event-listener socket and dispatches on `request.url()` with no authentication, source validation, or session/ownership binding of any kind.

### Finding Description
This is the same bug class as the reported Ruby MCP SDK issue: a component that should only act on requests originating from a specific trusted peer (the Stacks node) instead accepts and acts on any request delivered to its listening socket, because there is no check that ties the request to the legitimate session/peer.

`SignerEventReceiver::bind()` opens a plain `HttpServer` on the configured `endpoint` [1](#0-0) , which per the shipped sample configs defaults to listening on all interfaces (`endpoint = "0.0.0.0:30000"`), not just loopback [2](#0-1) .

`next_event()` then reads any inbound HTTP request and dispatches purely by URL path, with zero checks that the request came from the paired stacks-node (no auth token, no shared secret, no TLS client cert, no IP allowlist enforcement in code): [3](#0-2) 

Critically, the `/shutdown` path immediately sets the stop signal and terminates the event-receiver loop for *any* caller:
```rust
} else if request.url() == "/shutdown" {
    event_receiver.stop_signal.store(true, Ordering::SeqCst);
    Err(EventError::Terminated)
}
``` [4](#0-3) 

This mirrors exactly the "session poisoning" fault class from the report: the transport fails to verify that the party issuing a control/state-changing request (here, "shut down my event stream") is the legitimate session owner (the paired node), and instead accepts it from anyone who can open a TCP connection to the port. Where the Ruby SDK bug let an attacker execute tool calls under a victim's session, here an attacker can terminate the signer's entire event-ingestion pipeline under the guise of the node's own shutdown signal — the equality broken is "authenticated node request" vs. "any reachable client request."

The other routes (`/stackerdb_chunks`, `/proposal_response`, `/new_burn_block`, `/new_block`) also accept arbitrary bodies without verifying the sender is the local node [5](#0-4) , though the actual `StackerDBChunkData` payloads carried inside `StackerDBChunksEvent` still require valid per-slot signer signatures to be acted upon downstream, which limits the blast radius of forged StackerDB content. The `/shutdown` path has no such secondary safeguard.

### Impact Explanation
A single unauthenticated `POST /shutdown` to the signer's event-listener port permanently halts `main_loop()` for that `EventReceiver`, cutting the signer off from all subsequent node-pushed events (StackerDB chunks, burn blocks, new blocks, block-validation responses) until the operator manually restarts the signer process. This is a remote, unauthenticated, single-request denial of service against a component (`stacks-signer`) that participates in Nakamoto block signing — degrading that signer's ability to see and act on chain events. This matches the "Critical - remote crash/unauthenticated DoS from few messages" bucket, since it requires exactly one crafted HTTP request and no credentials.

### Likelihood Explanation
Likelihood is high wherever the signer's event endpoint is reachable from an untrusted network (the shipped sample config binds `0.0.0.0`, i.e., all interfaces, rather than `127.0.0.1`). No cryptographic material, secrets, or guessing is required — the path `/shutdown` is fixed and publicly known from the open-source code.

### Recommendation
Bind the signer's event-receiver socket to loopback by default and document that it must never be exposed beyond a trusted network. Independently, require the shared `auth_token`/`auth_password` (already used for the node→signer proposal-validation RPC) to be checked on every inbound request to `SignerEventReceiver`, especially `/shutdown`, before acting on it, so that only the paired node can control the receiver's lifecycle.

### Proof of Concept
```bash
# Given a running stacks-signer with event listener on <signer-host>:<port>
printf 'POST /shutdown HTTP/1.1\r\nHost: <signer-host>:<port>\r\nConnection: close\r\nContent-Length: 5\r\nContent-Type: text/plain\r\n\r\nhello' \
  | nc <signer-host> <port>
# The signer's event_receiver main_loop() observes EventError::Terminated and exits,
# permanently stopping ingestion of node-pushed events for this signer instance.
```
This reproduces the exact code path exercised by the built-in `SignerStopSignaler::send()` [6](#0-5) , but from an arbitrary, unauthenticated remote client instead of the signer's own shutdown-signal mechanism.

            let request = http_server.recv()?;
            debug!("Got request"; "method" => %request.method(), "path" => request.url());

            if request.url() == "/status" {

                .expect("response failed");
                return Ok(SignerEvent::StatusCheck);
            }

                return Err(EventError::MalformedRequest(format!(
                    "Unrecognized method '{}'",
                    request.method(),
                )));

                process_event::<T, StackerDBChunksEvent>(request)
