### Title
Dust DepositToken transfers let an unprivileged attacker fill a victim's `MAX_TOKENS_PER_USER` slots, blocking new deposits/borrows and preventing rescue of liquidatable positions - (File: contracts/Pool.sol)

### Summary
`Pool` enforces `MAX_TOKENS_PER_USER = 30` across `depositTokensOfAccount + debtTokensOfAccount` via `onlyIfAdditionWillNotReachMaxTokens`. `DepositToken._transfer` and `_mint` unconditionally call `pool.addToDepositTokensOfAccount(recipient_)` for any first-time balance, with no minimum amount. An attacker can deposit dust of every listed collateral and transfer it to a victim, filling the victim's set. Once full, any `addTo*` reverts, so the victim cannot receive new collateral types or take new debt positions. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
- `DepositToken.transfer`/`transferFrom`/`seize`/`_mint` all funnel into `_transfer`/`_mint`, which call `pool.addToDepositTokensOfAccount` whenever `balanceOf[recipient] == 0 && amount > 0` — dust of 1 wei suffices. [4](#0-3) 
- `Pool.addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` revert with `UserReachedMaxTokens` once the combined count reaches 30. Removal (`removeFromDepositTokensOfAccount` on zero balance) is unguarded, but an attacker can keep refilling slots, and removal only happens when the *victim's* balance hits zero — the victim can burn dust themselves, but each new token type transferred re-adds a slot.
- Critically, `DepositToken.deposit(amount, onBehalfOf)` lets a griefer deposit dust *directly on behalf of the victim* (`_mint(onBehalfOf_, ...)`) — no victim action or approval needed, and no way for the victim to opt out. [5](#0-4) 
- With the set full: depositing any not-yet-held collateral reverts in `_mint → addToDepositTokensOfAccount`, and `DebtToken` minting of a new synthetic reverts in `addToDebtTokensOfAccount`. A victim with an unhealthy position cannot add a different collateral type to restore health, so `Pool.liquidate` proceeds against them.

### Impact Explanation
Temporary freezing / forced loss of funds: a victim holding a leveraged position can be prevented from topping up with any collateral type they don't already hold, making them liquidatable when they otherwise would have recovered. New borrows (`DebtToken.issue`/`mint` on unheld synthetics) and new deposits revert entirely. Recovery is possible only by fully zeroing dust balances, which an attacker can race to refill, and every new `DepositToken` added by governance gives the attacker a fresh slot to grief.

### Likelihood Explanation
Attack cost is proportional to dust × (number of DepositTokens + reachable DebtToken slots). Feasibility depends on the deployed pool listing enough distinct DepositTokens to approach 30 slots; on pools with many collaterals this is cheap and fully permissionless — no privileged role, oracle manipulation, or flash loan required. The check exists in the deployed configuration and nothing else (reentrancy guards, pause flags, `SynthContext` sender resolution) blocks it since `deposit` is `onBehalfOf`-enabled and transfers are permissionless.

### Recommendation
Require a minimum meaningful amount (or only add on `deposit`, not on `transfer`/`onBehalfOf` dust); alternatively add an opt-in registry, allow `removeFromDepositTokensOfAccount` to be called by the account itself, or exempt `onBehalfOf_` mints below a dust threshold from set insertion. Capping per-account enumeration for gas was the intent, but the cap should not be externally fillable by third parties.

### Proof of Concept
Hardhat sketch (mock setup as in `test/Pool.test.ts:1386`):

```ts
// victim holds an open position with 1 deposit token + 1 debt token
for (const dt of allDepositTokens /* incl. tokens victim doesn't hold */) {
  // attacker deposits 1 wei of underlying directly for the victim
  await underlying.approve(dt.address, 1)
  await dt.deposit(1, victim.address)   // _mint -> addToDepositTokensOfAccount(victim)
}
// repeat until getDepositTokensOfAccount(victim).length +
//         getDebtTokensOfAccount(victim).length == 30

// now revert:
await expect(otherDepositToken.deposit(amount, victim.address))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens')
await expect(newDebtToken.connect(victim).issue(1))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens')
// victim's unhealthy position is liquidatable; topping-up collateral reverts
await pool.connect(liquidator).liquidate(synth, victim, depositToken, amount)
```

Note: whether the cap is reachable depends on the number of listed DepositTokens in the target pool deployment (DebtToken slots can't be filled by the attacker since debt tokens are non-transferable); on pools with ≥30 reachable token types the full lock is achievable, otherwise the attack proportionally shrinks the victim's usable slots.
