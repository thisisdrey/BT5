### Title
Unbounded growth of `Manager.ownerAddressSet` from attacker-issued `AccountPermissionUpdateContract` transactions causes a memory-leak/DoS - (File: framework/src/main/java/org/tron/core/db/Manager.java)

### Summary
`Manager.processTransaction` adds the hex-encoded owner address of every successfully processed `AccountPermissionUpdateContract` transaction into an in-memory `Set<String> ownerAddressSet` [1](#0-0) . This set is read later in `filterOwnerAddress` and `getVerifyTxs` to force re-verification of multi-sign transactions [2](#0-1) [3](#0-2) . Across the read code I could not find any point where entries are ever removed from `ownerAddressSet` — it is only ever added to, never cleared or pruned by size/time. This is analogous to the CVE-2017-17887 pattern: an attacker-controlled input causes a cache/tracking structure to accumulate objects that are never released, leading to unbounded memory growth and eventual denial of service.

### Finding Description
Any account can broadcast an `AccountPermissionUpdateContract` transaction — this is a standard, unprivileged, permissionless operation (updating one's own account permissions). Each time such a transaction is processed, `isMultiSignTransaction()` returns `true` for `AccountPermissionUpdateContract` [4](#0-3) , and the owner's hex address is unconditionally inserted into `ownerAddressSet`: [1](#0-0) 

An attacker can generate an unlimited number of new TRON addresses (free, off-chain key generation) and, for each one, fund it minimally and broadcast a single `AccountPermissionUpdateContract` transaction. Every such transaction adds one new, unique string entry to `ownerAddressSet` that is never evicted. Because entries are keyed by unique owner address strings, the set grows monotonically with the number of distinct attacker addresses used, with no cap, expiration, or removal logic found anywhere in `Manager.java`.

This structure is also read on every block-verification and block-generation path (`getVerifyTxs`, `filterOwnerAddress`, `generateBlock`), so as it grows it also imposes a permanently increasing CPU/memory cost per block on every node that processes the resulting blocks — a full-node-wide effect that compounds the memory-leak DoS with degraded verification throughput.

### Impact Explanation
An unbounded, permanently-growing `HashSet<String>` held in a live `Manager` singleton is a classic heap-exhaustion memory leak. Given enough attacker-issued cheap transactions (bounded only by bandwidth/energy cost of an `AccountPermissionUpdateContract`, which is a low-cost standard transaction), the set will consume increasing heap over the node's lifetime until the node experiences GC pressure, degraded throughput, or an eventual `OutOfMemoryError`/crash — a denial of service against the full node (and, since every node processes the same chain, this affects the whole network's nodes uniformly, which can lead to a broad availability incident). This matches the "node crash or halt" impact bar required by the validation rules.

### Likelihood Explanation
High likelihood of reachability: `AccountPermissionUpdateContract` is a normal user-facing operation, requiring no special privilege, and any unprivileged party can create new addresses for free and repeatedly broadcast the minimal transaction needed to trigger the leak. The cost to the attacker is only the bandwidth/energy fee of ordinary transactions, which is comparatively cheap versus the disproportionate, permanent memory cost imposed on every full node. However, I was not able to fully verify with 100% certainty that there is no separate reset/cleanup mechanism (e.g., during a periodic maintenance task, on `Manager` re-initialization, or in `eraseBlock`/checkpoint logic) since I did not have visibility into every remaining part of `Manager.java` due to tool/iteration limits — this should be double-checked in the full file before treating this as fully confirmed.

### Recommendation
Bound `ownerAddressSet` with an eviction policy — e.g., replace it with a time/size-bounded structure (such as a `Cache` with `expireAfterWrite`/`maximumSize`, similar to the LRU caches already used in `TronJsonRpcImpl`), or remove entries once the corresponding transaction leaves `pendingTransactions`/is no longer relevant for re-verification. At minimum, cap the set's size and evict oldest entries (or entries whose transactions have already been finalized in a block) to prevent unbounded growth from repeated `AccountPermissionUpdateContract` broadcasts.

### Proof of Concept
1. Generate N new key pairs / addresses (no on-chain cost).
2. For each address, fund minimally and broadcast one `AccountPermissionUpdateContract` transaction (a standard, unprivileged operation) that gets processed successfully by any full node.
3. Each processed transaction adds one new entry to `Manager.ownerAddressSet` via the code path in `processTransaction` [1](#0-0) , with no discovered removal path.
4. Repeating this indefinitely (e.g., over days/weeks, limited only by transaction fees) causes `ownerAddressSet` to grow without bound, consuming increasing heap on every full node and degrading `getVerifyTxs`/`generateBlock` performance until memory exhaustion or severe slowdown occurs.
