Audit Report

## Title
`process_delivery_receipt` ignores `receipt.success` and pays relayer reward for failed Ethereum executions - (File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs)

## Summary
The Snowbridge outbound queue v2 pallet's `process_delivery_receipt` function pays the relayer reward and removes the `PendingOrder` after verifying a delivery receipt's proof, but never inspects the `receipt.success` field decoded from the Ethereum `InboundMessageDispatched` event. This allows relayers to be paid for messages whose Ethereum-side execution failed.

## Finding Description
`submit_delivery_receipt` verifies the event log proof via `T::Verifier::verify` and decodes a `DeliveryReceipt` via `DeliveryReceipt::try_from`, then calls `process_delivery_receipt` [3](#0-2) . The `DeliveryReceipt` struct correctly decodes the `success` boolean from the Solidity `InboundMessageDispatched(uint64 indexed nonce, bytes32 topic, bool success, bytes32 reward_address)` event [5](#0-4) .

However, `process_delivery_receipt` only checks `receipt.gateway == T::GatewayAddress::get()`, resolves the reward account from `receipt.reward_address` (or falls back to the relayer), loads the `PendingOrder` by `receipt.nonce`, pays `order.fee` via `T::RewardPayment::register_reward` if `fee > 0`, removes the order, and emits `MessageDelivered` — at no point does it check `receipt.success` [2](#0-1) . The verifier (`T::Verifier::verify`) only proves the event log's authenticity (that it was genuinely emitted by the Gateway contract and included in a valid receipt/beacon proof) — it does not, and cannot, interpret application-level semantics like the `success` flag. That responsibility falls entirely on the pallet logic, which omits it.

## Impact Explanation
This is an unauthorized/unbacked payout: relayers receive the full `order.fee` reward for messages that reverted on Ethereum, violating the intended invariant that rewards are paid only for successful cross-chain delivery. This matches the "theft or unbacked mint/unlock" and "runtime bugs that compromise intended behavior" categories of the impact gate. The fee amount is bounded by whatever the message sender set, so this is a leak of relayer-reward funds rather than an unbounded mint, but it is a real conservation-of-value violation with no privileged action required to trigger.

## Likelihood Explanation
Any signed account can call the public `submit_delivery_receipt` extrinsic. Once a message execution fails on Ethereum (revert), the Gateway still emits `InboundMessageDispatched` with `success=false`, and that event is just as provable via the receipt/beacon proof pipeline as a successful one. A relayer has direct financial incentive to submit these receipts since the code pays out unconditionally on `fee > 0`, regardless of `success`. No existing check in `process_delivery_receipt` or `submit_delivery_receipt` mitigates this.

## Recommendation
Add `ensure!(receipt.success, Error::<T>::DeliveryFailed);` at the start of `process_delivery_receipt`, before reward-account computation and order lookup. Add a `DeliveryFailed` variant to `Error<T>`. Decide the design for failed deliveries: whether the `PendingOrder` should still be removed (to prevent indefinite retry) without payout, or retained for retry/incentivized re-delivery. Add regression tests covering both `success == false` (no payout) and `success == true` (normal payout) paths, extending the existing `mock_valid_event_proof`/`submit_delivery_receipt_succeeds_after_unhalt` test patterns with a `success=false` variant.

## Proof of Concept
1. A message is enqueued via `do_process_message`, creating `PendingOrder { nonce: N, fee: F, .. }` in storage [6](#0-5) .
2. The message is relayed to Ethereum but reverts; the Gateway emits `InboundMessageDispatched(nonce=N, topic=T, success=false, reward_address=R)`.
3. A relayer constructs a valid `EventProof` for that log (analogous to `mock_valid_event_proof` in the test file) and calls `submit_delivery_receipt(origin, proof)`.
4. `T::Verifier::verify` succeeds because the log is genuinely emitted by the Gateway; `DeliveryReceipt::try_from` decodes `success: false` correctly.
5. `process_delivery_receipt` loads `PendingOrders[N]`, sees `fee > 0`, and calls `register_reward(&reward_account, kind, F)`, paying the relayer despite `success == false`.
6. A unit test analogous to `submit_delivery_receipt_succeeds_after_unhalt` but with a mock event encoding `success=false` would demonstrate `assert_ok!` payout occurring alongside a false success flag — this is the missing regression case in `bridges/snowbridge/pallets/outbound-queue-v2/src/test.rs`.

		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
