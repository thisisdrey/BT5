## Title
Unauthenticated `RecvError` packet with attacker-controlled `RemoteIndex` triggers destructive tunnel teardown before any decryption/authentication - ([File: outside.go])

### Summary
The external report describes a public, unauthenticated entry point (`ClearingHouse.safeTransferFrom`) that trusts a caller-supplied identifier to select a critical value (`paymentToken`) and, on that basis, performs an irreversible state-cleanup (paying debt, deleting `CollateralToken`/`LienToken` records), permanently locking the NFT. The common bug class is: **an unauthenticated message path accepts an attacker-controlled index/identifier and uses it to look up and destroy live protocol state, without any cryptographic binding of the sender to that state.**

Nebula has a directly analogous unauthenticated path: `header.RecvError` packets are processed by `Interface.handleRecvError` in [1](#0-0)  *before* any Noise decryption or authentication occurs — this dispatch happens right after header parsing, alongside the handshake dispatch, and precedes the `hostinfo == nil` / decrypt gate that protects all other message types.

### Finding Description
`readOutsidePackets` parses the wire header and, for `header.RecvError`, immediately calls `f.handleRecvError(via.UdpAddr, h)` without requiring the packet to be decrypted or authenticated by any `ConnectionState`/AEAD key: [2](#0-1) 

`handleRecvError` then uses the attacker-supplied 32-bit `h.RemoteIndex` field to look up a live `HostInfo` via `QueryReverseIndex`, and if found, tears the tunnel down: [3](#0-2) 

The only "authentication" performed is comparing the UDP source address (`addr`) against `hostinfo.GetRemote()` — and even that check is skipped whenever `hr.IsValid()` is false (i.e., before the tunnel has learned/confirmed a remote, such as immediately after handshake or before roaming has occurred):
```go
hr := hostinfo.GetRemote()
if hr.IsValid() && hr != addr {
    ...
    return
}
f.closeTunnel(hostinfo)
f.handshakeManager.DeleteHostInfo(hostinfo)
```
UDP source addresses are trivially spoofable, so this check provides no real protection even when `hr` is valid — an off-path attacker who can inject UDP packets to the target's listening port (spoofing the peer's real address) satisfies it. The remaining gate, `ShouldRecvError`, is a config-driven allow-list on the source IP/CIDR (`listen.accept_recv_error` in `interface.go`), not a cryptographic authentication mechanism, and cannot bind the packet to a genuine peer, index, or handshake epoch.

This mirrors the report's root cause precisely: a public, unauthenticated function trusts an attacker-supplied identifier (`RemoteIndex`, analogous to the forged `paymentToken` identifier) and uses it to permanently destroy live session state (`closeTunnel` + `DeleteHostInfo`, analogous to `LienToken`/`CollateralToken` deletion) with no verification that the caller is the legitimate remote party that owns that index.

### Impact Explanation
An attacker with no valid certificate and no established tunnel can send a bare, unencrypted UDP packet of `header.RecvError` type with a guessed/observed `RemoteIndex` to force termination of an active, legitimate tunnel between two Nebula nodes. Because `RemoteIndex` values are allocated sequentially/randomly per-tunnel and are visible on the wire in every packet of an active flow (they are not secret and not authenticated), an attacker positioned to observe or intercept even one packet of a target flow (e.g., on a shared network segment, or by traffic analysis) can extract the index and forge a teardown. This is a remote, unauthenticated denial-of-service against arbitrary established tunnels — directly analogous to the report's "lock collateral / block liquidations forever" impact, here manifesting as forced session state destruction and connection disruption without any certificate or handshake being performed by the attacker.

### Likelihood Explanation
Likelihood is moderate-to-high in adversarial network positions: no cryptographic material, certificate, or CA trust is required to construct the packet; only the numeric `RemoteIndex` (and, if `hr.IsValid()`, spoofing the peer's known UDP address) is needed, both of which are observable or spoofable by a network-adjacent/on-path attacker. The project's own changelog shows repeated hardening attempts around this path (e.g., "Disable sending `recv_error` messages when a packet is received outside the allowable counter window" and configurable `accept_recv_error`/`send_recv_error`), indicating this is a recognized sensitive area, though the fundamental lack of cryptographic binding for `RecvError` acceptance remains.

### Recommendation
- Do not act on `RecvError` (or any unauthenticated control message) based solely on an unauthenticated index and a spoofable source-address comparison.
- Require that `RecvError` handling either be cryptographically bound (e.g., signed/MAC'd with a key derived from the tunnel's current session, or only accepted for a short window immediately following a locally-sent packet that could plausibly have triggered it) or be rate-limited/quarantined and never used as the sole trigger for `DeleteHostInfo`.
- Strengthen the roaming/remote check so it is not skippable via `!hr.IsValid()`, and consider requiring corroborating evidence (e.g., recent traffic gap, matching outbound message counter) before tearing down a live tunnel from an unauthenticated packet type.

### Proof of Concept
1. Establish a live Nebula tunnel between `me` and `them` (valid certs, completed handshake).
2. As an attacker with no certificate, observe or infer `them`'s `RemoteIndex` as seen by `me` (visible on the wire in every packet `me` sends to `them`, or vice versa).
3. Craft a raw UDP packet with `header.RecvError` type/subtype and that `RemoteIndex`, sourced from (or spoofing) an address for which `ShouldRecvError`/roaming checks pass — this is directly demonstrated by the existing test harness pattern that constructs raw headers and injects them via UDP, e.g. the bogus-`CloseTunnel` injection in `TestCloseTunnelAuthenticated` [4](#0-3) , adapted to `header.RecvError` and a real/guessed index.
4. Observe `handleRecvError` executes `closeTunnel` + `DeleteHostInfo` on the legitimate `HostInfo`, tearing down the live tunnel without any decryption or certificate check — the same "public function trusts unauthenticated identifier to destroy live state" pattern as the original report.

Note: I could not execute this PoC or fully trace `ShouldRecvError`'s exact filtering logic (in `interface.go`) within the available indexed content; its precise default configuration (e.g., default enabled/disabled, default CIDR scope) could not be confirmed from the excerpts retrieved, which may affect real-world exploitability under default settings. A Devin session with full repository access would be needed to confirm the default `listen.accept_recv_error`/`send_recv_error` configuration and validate the PoC end-to-end.

```go
func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
```
