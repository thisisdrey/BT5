### Title
Unbounded-length digit string triggers quadratic `BigInteger` parsing in JSON transaction field decoding (CPU DoS) - ([File: framework/src/main/java/org/tron/core/services/http/JsonFormat.java])

### Summary
`JsonFormat.parseInteger()` — the routine that every HTTP `/wallet/*` create-transaction servlet uses to decode int64/uint64 numeric fields out of client-submitted JSON (via `JsonFormat.merge()`) — falls back to `new BigInteger(numberText, radix)` for any numeric token whose textual length is 16 characters or more, with no upper bound on `numberText.length()` before that call is made. This mirrors the CVE-2016-0797 root cause: an attacker-controlled long digit string is fed straight into a `BigInteger`/`BN_*` style parser whose CPU cost grows quadratically with input length, with no length pre-check.

### Finding Description
`JsonFormat.parseInteger(String text, boolean isSigned, boolean isLong)` is the shared integer-token parser used by `consumeInt64`, `consumeUInt64`, `consumeInt32`, and `consumeUInt32` while parsing a text-format/JSON-ish request body into a protobuf `Message` via `JsonFormat.merge()`: [1](#0-0) 

For tokens 16 characters or longer, the code skips the fast, bounded `Long.parseLong` path and calls `new BigInteger(numberText, radix)` directly on the raw, attacker-supplied string, with `numberText` unbounded in length: [2](#0-1) 

`JsonFormat.merge()` is the JSON body deserializer invoked by essentially every write-capable HTTP servlet in `framework/src/main/java/org/tron/core/services/http/`, including transaction-creation endpoints such as `CreateCommonTransactionServlet`, `FreezeBalanceServlet`, `FreezeBalanceV2Servlet`, `ExchangeCreateServlet`, `ExchangeInjectServlet`, `ExchangeTransactionServlet`, `ExchangeWithdrawServlet`, `DelegateResourceServlet`, `CreateAssetIssueServlet`, `DeployContractServlet`, `EstimateEnergyServlet`, `AccountPermissionUpdateServlet`, and dozens of `Get*Servlet` query endpoints. Any of these that includes an int64/uint64 field in the incoming JSON payload will route the raw client string through `consumeInt64`/`consumeUInt64` → `parseInteger` → `new BigInteger(...)`.

Because `java.math.BigInteger`'s string constructor performs repeated digit-group multiplication with cost that scales roughly quadratically (and worse in older/naive JDK implementations) with the number of digits, an attacker can submit a JSON body where a numeric field is populated with a multi-megabyte digit string (e.g. millions of `9`s), causing the parsing thread to spend substantial CPU time on a single HTTP request before any semantic/bounds validation (`bitLength()` checks) ever executes — those checks happen only *after* the expensive `BigInteger` construction has already completed.

### Impact Explanation
This is a synchronous, single-request CPU-exhaustion vector reachable by any anonymous HTTP client with no authentication or prior stake, hitting the full-node's request-handling thread for the duration of the `BigInteger` parse. Repeated concurrent requests with maximal-length digit payloads can degrade or stall the node's HTTP API responsiveness, denying legitimate query/broadcast traffic (an availability/DoS impact on an API the node can no longer serve promptly), analogous in bug class and impact to CVE-2016-0797's DoS via `BN_dec2bn`/`BN_hex2bn`.

### Likelihood Explanation
High likelihood of reachability: the vulnerable code path is a generic protobuf-JSON parsing utility exercised by nearly all POST-based `/wallet/*` HTTP servlets, requires no signature or account balance, and needs only a crafted HTTP request body with an oversized numeric string in any int64/uint64 field. No allow-list length check exists upstream of `parseInteger`, unlike the JSON-RPC layer's `JsonRpcApiUtil.parseBlockNumber`, which explicitly caps input length (`MAX_BLOCK_NUM_HEX_LEN`) specifically to guard against this class of quadratic `BigInteger` parsing cost: [3](#0-2) 
That mitigation was applied to the JSON-RPC block-number path but not to the HTTP `JsonFormat` text/JSON field parser, leaving the latter exposed.

### Recommendation
Add a maximum-length guard on `numberText` (e.g., reject or short-circuit tokens longer than ~20 characters, sufficient to cover the full int64/uint64 range) before invoking the `BigInteger` fallback branch in `JsonFormat.parseInteger`, mirroring the `MAX_BLOCK_NUM_HEX_LEN` pattern already used in `JsonRpcApiUtil.parseBlockNumber`. Throw a `NumberFormatException`/parse error immediately for over-length tokens instead of constructing a `BigInteger` from them.

### Proof of Concept
1. Send an HTTP POST to any write servlet that parses JSON via `JsonFormat.merge()` and contains an int64/uint64 field, e.g. `/wallet/freezebalancev2`, with the numeric field value replaced by a synthetically long digit string (several million digits), while all other required fields are valid enough to reach field parsing.
2. Observe that request processing time and CPU usage spike disproportionately to payload size before any `JsonRpcInvalidParamsException`/`ContractValidateException` is thrown, because the cost is incurred inside `new BigInteger(numberText, radix)` in `parseInteger` prior to the subsequent `bitLength()` bounds check.
3. Repeating this concurrently from multiple connections degrades the node's HTTP API responsiveness for other legitimate callers.
