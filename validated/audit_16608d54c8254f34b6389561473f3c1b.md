### Title
Integer overflow in default (non-hardened) TRC10 Exchange (Bancor-style AMM) actuators allows draining/minting token reserves beyond backing — ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java])

### Summary
java-tron's built-in TRC10 "Exchange" (a Bancor-formula AMM reachable by any signed account via `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract`) contains a feature-flagged fix (`allowHardenExchangeCalculation`) that adds `addExact`/`subtractExact` overflow checks and a safe `BigDecimal`-based processor. When this flag is off — which is its default state — all pool-balance arithmetic and the swap-amount computation fall back to raw `long` `+`/`-` and floating-point math with no overflow protection, closely mirroring the exact bug class described in the PIZZA/eCurve incident (unchecked overflow when minting/crediting AMM market-making balances "out of thin air").

### Finding Description
The `AbstractExchangeActuator` helper methods used by all Exchange actuators silently disable overflow checking unless the chain-parameter flag is enabled: [1](#0-0) 

`ExchangeCapsule.transaction()` — the core swap routine used by `ExchangeTransactionActuator.execute()`/`doValidate()` — selects between a safe `SafeExchangeProcessor` and a legacy `ExchangeProcessor` based on this same flag, and only applies `StrictMathWrapper.addExact/subtractExact` to the pool balances when `hardenedCalc` is true; otherwise it uses plain `firstTokenBalance + sellTokenQuant` / `secondTokenBalance - buyTokenQuant`: [2](#0-1) 

The legacy `ExchangeProcessor` (used by default) computes the swap output using unchecked `long` arithmetic combined with floating point `Math.pow`: [3](#0-2) 

Critically, in `ExchangeTransactionActuator.doValidate()`, the balance-limit check that is supposed to bound pool growth also relies on the actuator's own `addExact` wrapper, which is unguarded when `allowHarden()` is false: [4](#0-3) 

Because a transaction submitter fully controls `tokenQuant` (bounded only by their own asset balance, which for TRC10 tokens can be as large as `Long.MAX_VALUE`), a sell quantity chosen so that `tokenBalance + tokenQuant` wraps past `Long.MAX_VALUE` into a negative number defeats the `> balanceLimit` guard entirely (a negative number is never `> balanceLimit`). The same unguarded addition/subtraction happens again inside `ExchangeCapsule.transaction()` for updating `firstTokenBalance`/`secondTokenBalance`, and the legacy processor's floating-point formula operating on a wrapped/corrupted `newBalance` can yield an `anotherTokenQuant` that is inconsistent with the real reserve, allowing the caller to extract (or credit) TRC10 token amounts disconnected from the actual backing of the pool — the same "mint/extract via overflow" pattern used in the PIZZA/eCurve exploit. `ExchangeInjectActuator` and `ExchangeWithdrawActuator` share the identical unguarded-by-default pattern.

The repository's own test suite explicitly documents that the guard only fires when the "hardened" flag is turned on (`saveAllowHardenExchangeCalculation(1)`), confirming the default path is unguarded: [5](#0-4) 

### Impact Explanation
An unprivileged account holding (or having issued) a TRC10 token can submit `ExchangeTransactionContract`/`ExchangeInjectContract` transactions with a crafted `quant` designed to overflow the pool-balance arithmetic. Under the default (non-hardened) configuration this can (a) bypass the `getExchangeBalanceLimit()` safety check via signed-overflow wraparound, and (b) drive the legacy floating-point Bancor formula to return an inflated `anotherTokenQuant`, letting the attacker withdraw more of the counter-token than the pool actually holds. This is a direct theft/unbacked-balance vector against any TRC10 Exchange pool on the network — Medium/High severity depending on pool value, matching the "unbacked balance / theft of funds" impact bar.

### Likelihood Explanation
Reachable by any account with a signed `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` transaction — no special privilege, SR status, or node compromise required. The only precondition is that the network parameter `allowHardenExchangeCalculation` has not been turned on via proposal (it defaults to 0/off, per `DynamicPropertiesStore` and the test setup that must explicitly enable it to demonstrate the "hardened" guard). Exploitability additionally requires the attacker to acquire a very large TRC10 token quantity (feasible for any TRC10 issuer, or via `AssetIssueContract` self-issuance, since the actuator only checks `assetBalanceEnoughV2`, not any global sanity bound tied to `Long.MAX_VALUE`).

### Recommendation
- Make the overflow-checked path (`StrictMathWrapper.addExact/subtractExact`, `SafeExchangeProcessor`) unconditional in `AbstractExchangeActuator`, `ExchangeCapsule.transaction()`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator`, rather than gating it behind the `allowHardenExchangeCalculation` dynamic parameter.
- If the flag must be retained for backward-compatibility/consensus reasons, ensure it is enabled by default on all networks and add validation that rejects transactions when `tokenQuant` could cause the unguarded intermediate sum to overflow, independent of the flag state.
- Add a hard upper bound check on `tokenQuant`/`exchangeInjectContract.getQuant()` relative to `Long.MAX_VALUE - currentBalance` before any addition, in both `validate()` and `execute()`.

### Proof of Concept
Conceptual (network with `allowHardenExchangeCalculation` at its default/off value):
1. Attacker issues or otherwise acquires a TRC10 token with a balance close to `Long.MAX_VALUE` (e.g., issue with `TotalSupply = Long.MAX_VALUE`).
2. Attacker (or colluding account) creates/joins an `Exchange` pool pairing this token with a valuable token/TRX.
3. Attacker submits `ExchangeTransactionContract` (or `ExchangeInjectContract`) selling a `quant` chosen such that `currentTokenBalance + quant` exceeds `Long.MAX_VALUE`, wrapping to a negative `long`.
4. In `ExchangeTransactionActuator.doValidate()`, `tokenBalance = addExact(tokenBalance, tokenQuant)` (unguarded when not hardened) evaluates to a negative number, which trivially passes `tokenBalance > balanceLimit`.
5. `ExchangeCapsule.transaction()` recomputes the pool balances with plain `+`/`-` (again unguarded) and the legacy `ExchangeProcessor`, whose floating-point formula operating on the corrupted balance can return an `anotherTokenQuant` disconnected from real reserves.
6. The attacker's account is credited `anotherTokenQuant` of the counter-asset via `accountCapsule.addAssetAmountV2(...)`, extracting value not actually backed by the pool.

Note: I was not able to execute this against a live/test network to confirm the exact numeric overflow boundary conditions (e.g., precise `tokenQuant` value needed given the floating-point formula's behavior near overflow) — this would require dynamic testing in a Devin session with access to build/test tooling to fully validate exploitability end-to-end.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
